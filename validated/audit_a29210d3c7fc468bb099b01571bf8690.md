### Title
Gas/CPU griefing via unbounded-cost Sierra-to-CASM compilation performed before nonce/balance validation - (File: `crates/apollo_gateway/src/gateway.rs`)

### Summary
The Apollo Gateway performs the CPU- and memory-intensive Sierra-to-CASM compilation for `Declare` transactions before it validates the transaction's nonce, resource bounds, or fee-token balance. An unprivileged transaction sender can therefore submit `Declare` transactions from unfunded/underfunded accounts, or with invalid nonces, and force the gateway (and the shared Sierra compiler service) to burn CPU/memory compiling contract classes that are certain to be rejected once the cheap state-dependent checks finally run. This mirrors the reported zAuction/zNS pattern, where expensive computation is performed before a check that depends on the caller's ability to actually pay/participate, enabling gas/resource griefing of the party that must perform the on-chain (here: node-side) work.

### Finding Description
In `GenericGateway::add_tx_inner`, the flow is:
1. `stateless_tx_validator.validate(&tx)` — cheap, format-only checks (lengths, DA modes, sierra version, etc.), no state access.
2. `convert_rpc_tx_to_internal_and_executable_txs(...)`, which for `Declare` transactions triggers Sierra-to-CASM compilation via the contract class manager/compiler.
3. Only afterward is `stateful_tx_validator_factory.instantiate_validator(...)` and `extract_state_nonce_and_run_validations(...)` invoked, which performs nonce validation, resource-bound/balance checks (`validate_resource_bounds`, `perform_pre_validation_stage` → `verify_can_pay_committed_bounds`), and the CPU-heavy `__validate__` entry-point call. [1](#0-0) 

The code base itself documents this ordering and its risk directly in the config comment for `max_concurrent_declare_compilations`: [2](#0-1) 

The only mitigation is a global `Semaphore` (`declare_compilation_semaphore`) bounding the number of concurrent compilations (default 40), which throttles concurrency but does not reorder checks: nonce/balance validation still runs strictly after compilation for every accepted declare, and the semaphore itself can be exhausted/held by a stream of doomed-to-fail declares from unfunded accounts, causing legitimate declares to be rejected with `TransactionLimitExceeded` while the CPU/memory-expensive compilation work is wasted on transactions that always fail the subsequent cheap nonce/balance checks. [3](#0-2) [4](#0-3) 

This is structurally identical to the reported bug class: an operation whose success depends on cheap, caller-specific preconditions (bidder identity/funds in the original report; sender nonce/balance here) is preceded by expensive computation (bid recovery/signature checks there; Sierra→CASM compilation here), letting an attacker who knows the transaction will fail cause the party performing the expensive step to pay for it anyway.

### Impact Explanation
Repeated submission of `Declare` transactions (with valid Sierra classes to pass stateless checks, and large/complex enough classes to maximize compile cost) from accounts with insufficient balance or invalid nonces forces the gateway and its backing Sierra-compiler workers to repeatedly perform expensive compilation that is discarded once nonce/balance validation fails. Because the compilation permit is only released after compilation completes and before the (cheap) state checks run, an attacker can saturate `max_concurrent_declare_compilations`, causing legitimate declare transactions from properly-funded accounts to be rejected (`TransactionLimitExceeded`) and degrading gateway throughput/availability for declare-transaction ingestion network-wide (each honest node runs the same validation order), which can manifest as the network becoming unable to admit new declare transactions during sustained abuse.

### Likelihood Explanation
This is reachable by any unprivileged transaction sender simply by submitting well-formed but underfunded/invalid-nonce `Declare` transactions; no privileged role, mempool/consensus manipulation, or special network position is required. The attack cost to the attacker (transaction construction + no fee actually collected, since the tx never gets far enough to charge fees) is much lower than the CPU cost imposed on the sequencer, which is the classic hallmark of a griefing vector, and the existing semaphore-based mitigation caps concurrency but does not address the fundamental ordering issue.

### Recommendation
Move cheap, sender-dependent checks (nonce validity, resource-bound sufficiency, fee-token balance sufficiency) ahead of the CPU/memory-intensive Sierra-to-CASM compilation step in `add_tx_inner`/`convert_rpc_tx_to_internal_and_executable_txs`, so that declares from unfunded or nonce-invalid senders are rejected before compilation is triggered. If compilation must occur before full state validation (e.g., because the class hash must be derived from the class before other checks), perform a lightweight balance/nonce pre-check using already-available state data prior to acquiring the compilation permit and invoking the compiler.

### Proof of Concept
1. Create an account with zero (or insufficient) fee-token balance, or use a nonce known to be invalid for an existing account.
2. Craft a `Declare` v3 transaction with a large, valid Sierra program (to maximize compilation cost) and pass it through `stateless_tx_validator.validate` (satisfy length/version/format checks).
3. Submit many such transactions concurrently to `apollo_gateway::add_tx`; each will acquire the `declare_compilation_semaphore`, invoke `convert_rpc_tx_to_internal_and_executable_txs` (triggering full Sierra→CASM compilation), and only then fail in `extract_state_nonce_and_run_validations` due to insufficient balance/invalid nonce.
4. Observe that CPU/memory is consumed compiling classes for every request, and that once the semaphore (`max_concurrent_declare_compilations`, default 40) is saturated, subsequent legitimate declare transactions are rejected with `TransactionLimitExceeded` as shown in `test_declare_compilation_concurrency_limit`. // Compiling a declared Sierra class to CASM is CPU- and memory-intensive, and it happens during
// transaction ingestion before the transaction's signature and balance are verified. Bound the
// number of compilations running concurrently to protect the node from resource exhaustion.
//
// Derivation: compilations are served by the sierracompiler instances, so the safe per-gateway
// bound is the sierracompiler fleet's headroom divided across the gateway fleet, i.e.
// `per_instance_capacity * num_sierracompiler_instances / num_gateway_instances`. Observed
// sierracompiler usage per compilation is small (memory spike ~0.75% of an instance), so a single
// instance can absorb many concurrent compilations. 40 stays well within that envelope while still
// capping the blast radius of a declare flood; retune via the formula above if the
// sierracompiler/gateway instance ratio or per-instance capacity changes.
const DEFAULT_MAX_CONCURRENT_DECLARE_COMPILATIONS: usize = 40;

#[rstest]
#[tokio::test(flavor = "multi_thread")]
async fn test_declare_compilation_concurrency_limit(mut mock_dependencies: MockDependencies) {
    mock_dependencies.config.static_config.max_concurrent_declare_compilations = 1;

    // Both declares run stateless validation, so replace the fixture's single-call mock with one
    // that accepts repeated calls.
    let mut mock_stateless_transaction_validator = MockStatelessTransactionValidatorTrait::new();
    mock_stateless_transaction_validator.expect_validate().returning(|_| Ok(()));
    mock_dependencies.mock_stateless_transaction_validator = mock_stateless_transaction_validator;

    // The first declare's conversion performs the Sierra-to-CASM compilation while holding the
    // single permit. Make that conversion block so the second declare arrives while the permit is
    // still held: `compilation_started_sender` signals that the permit is held, and the conversion
    // then parks on `release_compilation_receiver` until the test lets it finish.
    let (compilation_started_sender, compilation_started_receiver) =
        tokio::sync::oneshot::channel();
    let (release_compilation_sender, release_compilation_receiver) = std::sync::mpsc::channel();
    mock_dependencies
        .mock_transaction_converter
        .expect_convert_rpc_tx_to_internal_rpc_tx()
        .return_once(move |_| {
            compilation_started_sender.send(()).unwrap();
            release_compilation_receiver.recv().unwrap();
            // Fail the conversion so the first declare short-circuits here instead of running the
            // full admission path; its outcome is irrelevant, so the specific error is arbitrary.
            Err(TransactionConverterError::ClassNotFound { class_hash: ClassHash::default() })
        });

    let gateway = Arc::new(mock_dependencies.gateway());

    // Spawn the first declare and wait until it holds the permit inside compilation.
    let first_declare_task = {
        let gateway = gateway.clone();
        tokio::spawn(async move { gateway.add_tx(declare_tx(), None).await })
    };
    compilation_started_receiver.await.unwrap();

    // The second declare cannot acquire a permit and must be rejected immediately.
    let second_declare_error = gateway.add_tx(declare_tx(), None).await.unwrap_err();
    assert_eq!(
        second_declare_error.code,
        StarknetErrorCode::KnownErrorCode(KnownStarknetErrorCode::TransactionLimitExceeded)
    );

    // Release the first declare so its task and the blocked worker thread can wind down.
    release_compilation_sender.send(()).unwrap();
    let _ = first_declare_task.await;
