Based on my research, I found a viable analog matching the "cached value not invalidated when its source moves" pattern in the Zest market contract's `last-borrow-block` same-block liquidation guard.

### Title
`last-borrow-block` Frontrunning Guard Reads a Position Snapshot Taken Before Accrual, Allowing Same-Block Borrow-Then-Liquidate Bypass Timing to Diverge From Debt Update Timing - (File: `local-testing/contracts/market/market.clar`, also `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate` reads `last-borrow-block` from a `position` snapshot fetched via `get-liquidation-position` at the very start of the call [1](#0-0) , then compares it against `stacks-block-height` to block same-block borrow→liquidate flash-loan attacks [2](#0-1) . However, the health values used to actually decide whether liquidation proceeds (`total-collateral-usd`, `total-debt-usd`, `current-ltv`) are computed later from `accrue-user-debts`/`accrue-user-collateral` and `get-notional-evaluation`, which mutate the accrual/index cache (`accrue-and-cache`) as a side effect [3](#0-2) . The guard's source-of-truth (`last-borrow-block` on the pre-accrual `position`) and the value it is meant to protect (post-accrual debt/collateral valuation) are captured at different points in the same transaction, relying on `position` and `pos-full` staying consistent with each other across the accrual step.

### Finding Description
In `borrow`, `debt-add-scaled` is called only after `vault-system-borrow`, and the market-vault records the new debt including (presumably) updating `last-borrow-block` for the account. In `liquidate`, `position` (used for `mask` and `last-borrow-block`) is fetched via `get-liquidation-position borrower` before `pos-full` (used for accrual and notional valuation) is fetched via `get-full-position borrower` [4](#0-3) . Both reads happen in the same `let`-bindings sequence, and per Clarity evaluation order, `position` is bound before `pos-full`, before `accrue-user-debts`/`accrue-user-collateral` are invoked and before the `same-block-check` assertion runs [5](#0-4) . Because `position` is read from `market-vault` independently of `pos-full`, and the same-block check is only asserted after accrual mutates cache/vault state, the guard value (`last-borrow-block`) is a value bound from a data source (`get-liquidation-position`) that is separate from the debt/collateral data source (`get-full-position` + accrual) used for the actual health/LTV computation that determines whether the liquidation is allowed and how much can be seized. If these two reads can observe different underlying states for the same borrower/account (e.g., `get-liquidation-position` returning a mask/`last-borrow-block` computed differently than `get-full-position`), the guard could pass while the health computation reflects account state from a different point, undermining the intended flash-loan/same-block protection.

### Impact Explanation
If the `last-borrow-block` snapshot and the debt/collateral snapshot used for the liquidation math diverge, a liquidator could execute the intended-to-be-blocked same-block borrow-then-liquidate sequence, or a legitimate borrower could be liquidated using stale health data despite the guard passing, resulting in unintended penalty extraction. This falls under the in-scope "temporary freezing of funds"/"theft of unclaimed yield" class since it affects position-holder outcomes at liquidation, not an outright fund-draining exploit, and remains bounded because vault index accrual is deterministic per block via `stacks-block-time`-keyed caching [3](#0-2) .

### Likelihood Explanation
The likelihood depends on whether `get-liquidation-position` and `get-full-position` can genuinely disagree about `last-borrow-block` or the account's held debt/collateral within a single transaction — I could not confirm the implementations of `get-liquidation-position` or `get-full-position` in `market-vault.clar` from the available index, so I cannot verify whether they are guaranteed to be consistent snapshots of the same account state at the same point in the call.

### Recommendation
Given the uncertainty above, I cannot assert this rises to a confirmed, exploitable vulnerability without inspecting `market-vault.clar`'s `get-liquidation-position` and `get-full-position` definitions to determine if they can diverge for the same account within one transaction.

### Proof of Concept
Not constructible without confirming the `market-vault.clar` read functions referenced above; a full PoC would require verifying whether `last-borrow-block` in `get-liquidation-position`'s returned tuple can be stale/mismatched relative to the debt list returned by `get-full-position` for the same account and block.

**Note:** Due to index size limits, I could not retrieve the contents of `market-vault.clar` (specifically `get-liquidation-position`/`get-full-position`) or the mainnet `v0-market-vault.clar` equivalents to confirm or refute the divergence. I recommend starting a full Devin session to inspect those files directly before treating this as a validated finding — my confidence here is Low given this gap, and I would not present this as a definitively confirmed vulnerability.
