### Title
Missing floor-at-zero guard on `RepositoryImpl.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` allows global resource-weight corruption via TVM native contracts - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The C4 finding describes a farm contract that blindly trusts a monotonically-non-decreasing delta (`currentBalance - previousBalance`) computed from an external component, with no defensive check, causing an unguarded subtraction to underflow and permanently brick core operations. java-tron contains the same structural pattern in its global resource-accounting layer: two implementations of the same conceptual operation (`addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight`) exist, but only one of them was hardened with a floor-at-zero clamp after a known historical bug, while the other — reachable from unprivileged TVM contract calls — was not.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` (used by the classic `FreezeBalanceActuator`/`UnfreezeBalanceActuator`/`FreezeBalanceV2Actuator` transaction actuators) explicitly clamps the accumulated global weight to be non-negative: [1](#0-0) 

The `UnfreezeBalanceActuator` code even carries a comment referencing a prior incident ("used to be a bug here") near this exact accounting logic: [2](#0-1) 

However, `RepositoryImpl` — the state-access layer used by all TVM **native contract processors** (`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `DelegateResourceProcessor`, `UnDelegateResourceProcessor`, `CancelAllUnfreezeV2Processor`) that back the freeze/unfreeze/delegate/undelegate resource precompiles callable from arbitrary smart contract bytecode — implements the equivalent methods with **no such guard**: [3](#0-2) 

These unguarded methods are exactly what the native contract processors call to update the chain-wide `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT`/`TOTAL_TRON_POWER_WEIGHT` dynamic properties, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

Exactly like the JPEG'd farm assuming `vault.balanceOfJPEG()` always returns a value `>= previousBalance` without defending against divergence, these TVM-path processors assume the per-account weight delta (`newWeight - oldWeight`) computed from account-level frozen/delegated balances always keeps the *global* accumulator non-negative — but unlike the sibling `DynamicPropertiesStore` path (which was patched with `max(0, …)` after being found buggy), the `RepositoryImpl` path was never given the same protection. This is a genuine asymmetric-hardening bug: the same conceptual invariant is enforced in one accounting implementation and silently omitted in the other, unprivileged-reachable one.

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight` are chain-wide dynamic properties used to compute every account's available bandwidth/energy allowance (`usageToBalance` in `RepositoryImpl`, and the equivalent logic in `BandwidthProcessor`/`EnergyProcessor`). If a bug in accounting for a single account (rounding edge case, reentrant/partial state during a TVM call, or a future change to the delegate/undelegate flow) causes the delta subtracted from the global weight to exceed the true contribution of that account, the guarded (`DynamicPropertiesStore`) path would clamp to zero and lose only precision, but the unguarded (`RepositoryImpl`) path lets the global weight go negative and stay negative — corrupting network-wide resource-limit computations (division by/near a negative or zero weight, incorrect bandwidth/energy allowances for every account) until manually corrected via a hard fork/chain parameter fix. Because this property is part of consensus state, a divergence in how nodes compute it (e.g., inconsistent negative values across different execution paths) directly threatens chain-state integrity.

### Likelihood Explanation
Reaching the `RepositoryImpl` path requires only that a smart contract invoke the freeze/unfreeze/delegate/undelegate-resource TVM native contracts — actions available to any unprivileged account, not requiring witness or committee privileges. The `checkUnfreezeBalance`/`checkUndelegateResource` guards in normal call flows reduce the odds of triggering an inconsistent delta today, but the structural gap (no floor at zero in `RepositoryImpl`, unlike its sibling in `DynamicPropertiesStore`) means any future edge case, rounding discrepancy, or state-divergence bug in these TVM-only code paths is not defended against at all, whereas the same bug class in the classical actuators already was patched.

### Recommendation
Add the same `max(0, …)` floor-at-zero clamp used in `DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` to the corresponding methods in `RepositoryImpl` (and its `ContractState` delegate), so that both accounting paths enforce the identical non-negativity invariant on the chain-wide resource weight properties.

### Proof of Concept
Concrete reproduction was not verified end-to-end (would require crafting a specific sequence of freeze/delegate/undelegate operations through the TVM precompiles that produces a per-call weight delta exceeding the actual global contribution); this is flagged as unverified. The structural evidence — the deliberate `max(0, …)` fix present only in `DynamicPropertiesStore` and absent in the parallel `RepositoryImpl` implementation used by TVM-reachable native contracts — is confirmed by direct code comparison cited above.
