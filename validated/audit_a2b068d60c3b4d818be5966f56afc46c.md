### Title
Unbounded recursive receipt-graph traversal in `get_recursive_transaction_results` causes stack-overflow DoS on tx-status queries - ([File: chain/chain/src/chain.rs])

### Summary
`Chain::get_recursive_transaction_results` (`chain/chain/src/chain.rs:3190-3207`) recursively walks the receipt DAG produced by a transaction, calling itself once per child `receipt_id` with no depth limit and no iterative/heap-based rewrite. It is invoked by `Chain::get_final_transaction_result` (`chain/chain/src/chain.rs:3211-3225`), which backs the `tx`/`EXPERIMENTAL_tx_status` JSON-RPC calls that any unauthenticated RPC caller can invoke by simply submitting a transaction hash. This mirrors the CVE-2018-17581 bug class: an externally reachable, unbounded recursive function that consumes stack proportional to attacker-influenced input depth. [1](#0-0) 

### Finding Description
`get_recursive_transaction_results` pushes the outcome for `id`, then for every `receipt_id` produced by that outcome recurses into `get_recursive_transaction_results` again: [2](#0-1) 

There is no depth counter and no conversion to an explicit stack/queue, unlike other DAG/tree walkers in the codebase that were deliberately rewritten to avoid stack overflow (e.g. `get_subtree_size` in `core/store/src/trie/trie_recording.rs:302` explicitly notes "Non recursive approach to avoid any potential stack overflows", and `TrieStorageUpdate::flatten_nodes` in `core/store/src/trie/trie_storage_update.rs` uses an explicit `Vec`-based stack machine instead of native recursion).

A single transaction can trigger an arbitrarily deep *chain* of dependent receipts (not merely wide fan-out) by using self cross-contract calls: the test contract's `max_self_recursion_delay` demonstrates a contract-controlled, unbounded-looking promise chain (A→B→B→B…) that keeps re-issuing itself as long as gas remains, and the test explicitly documents recursion depths in the hundreds even under current gas costs, with the comment noting the depth "varies depending on the set of enabled features" and is expected only to stay under some soft bound, not a hard protocol-enforced limit: [3](#0-2) [4](#0-3) 

Because receipt-chain depth is bounded only by gas economics (which improve over protocol versions, e.g. cheaper function-call base costs), and not by an explicit protocol-level chain-depth limit, an attacker can craft a transaction that produces a long linear chain of action receipts. Later, any RPC caller (no special privilege needed) querying that transaction's status via `tx`/`EXPERIMENTAL_tx_status` causes the view node to run `get_final_transaction_result` → `get_recursive_transaction_results`, recursing once per hop in the chain. If the chain is long enough, this native (non-tail-call-guaranteed) Rust recursion can exhaust the thread's stack and crash the RPC/view-client process handling the request.

Note: I could not, within the available search scope, exactly measure the maximum achievable linear receipt-chain length under current gas parameters, nor find an explicit MAX_DEPTH-style guard analogous to the one already present in the sibling `ReceiptToTx` code path (`GetReceiptToTxError::DepthExceeded`, `chain/client-primitives/src/types.rs:1056`, enforced with `MAX_DEPTH=1000` per `test-loop-tests/src/tests/receipt_to_tx/errors.rs:157-228`). The presence of that explicit depth guard on a very similar receipt-chain-walking RPC path, and its conspicuous absence on `get_recursive_transaction_results`, is the strongest evidence that this recursive traversal was not designed with an adversarial chain length in mind. [5](#0-4) [6](#0-5) 

### Impact Explanation
A crash of the view-client/RPC-serving thread or process is a transaction-triggered halt of node-serving functionality (denial of service) for any node processing `tx`/`EXPERIMENTAL_tx_status` for the crafted transaction. Since RPC-serving processes are commonly shared across many client queries, and validators also run view-client logic for stateless queries, a stack overflow here can degrade or crash RPC availability network-wide once nodes replicate the offending transaction/receipt chain. This satisfies the "transaction-triggered halt" acceptance criterion, though it is scoped to RPC/view-client availability rather than consensus state divergence or fund loss.

### Likelihood Explanation
Likelihood depends on whether an attacker can actually construct a receipt chain long enough (thousands+ of linear hops) within a single transaction's gas budget to overflow a typical thread stack (usually multiple MB, and each recursive frame here is small — pushing to a `Vec`, matching on a `Result`, and reading an outcome). Given each hop requires a full cross-contract function-call receipt (with non-trivial minimum gas cost per hop), reaching a stack-overflow-triggering depth may require very large gas allowances or improved gas-cost efficiency, and this could not be conclusively confirmed from the code alone.

### Recommendation
Rewrite `get_recursive_transaction_results` as an explicit iterative traversal (e.g., a `Vec`/`VecDeque`-based worklist), following the same pattern already used in `TrieStorageUpdate::flatten_nodes` and `TrieRecorder::get_subtree_size` elsewhere in this codebase. Alternatively/additionally, impose an explicit maximum traversal depth (mirroring the `MAX_DEPTH` guard already used by the analogous `GetReceiptToTx` handler) and return a `TxStatusError`/`Error` when exceeded, rather than recursing without bound.

### Proof of Concept
Conceptual (not executed): submit a transaction whose function call recursively creates self-directed promise/receipt chains (as `max_self_recursion_delay` in `runtime/near-test-contracts/test-contract-rs/src/lib.rs:887-921` demonstrates is possible) sized to the maximum gas budget so the resulting execution-outcome chain has as many linear hops as gas allows. Once the chain is finalized on-chain, issue a `tx`/`EXPERIMENTAL_tx_status` JSON-RPC request for the original transaction hash against any RPC node. The node calls `Chain::get_final_transaction_result` → `Chain::get_recursive_transaction_results`, recursing once per receipt hop; if the chain length exceeds the thread's stack capacity for this frame size, the serving thread/process crashes.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,

    ) -> Result<(), Error> {

        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;

            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }

    // Sanity: receipt_2 (999 FromReceipt + 1 terminal = 1000 iter) succeeds
    // — exactly at limit.
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[2]));
    assert!(result.is_ok(), "1000 hops succeed, got: {result:?}");
    let response = result.unwrap();
    assert_eq!(response.transaction_hash, CryptoHash::hash_bytes(b"tx"));
    assert_eq!(response.sender_account_id.as_str(), "sender");
}
