### Title
Receipt size validation bypassed after `output_data_receivers`/promise-return mutation allows oversized receipts into state and cross-shard forwarding - (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/congestion_control.rs`)

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces `max_receipt_size` only at the moment a new receipt is validated [1](#0-0) . The runtime, however, mutates already-validated action receipts afterward (adding `output_data_receivers` when a promise result is returned to a caller), which can push a receipt that exactly matched the size limit above it, without re-validation. This is the same bug class as the Erlang OTP CVE-2025-26618: a size check is performed on a component before it is fully assembled/mutated, but the final combined artifact is never re-checked against the same limit, allowing an oversized object into the system.

### Finding Description
`validate_receipt` computes `borsh::object_length(receipt)` and rejects receipts over `limit_config.max_receipt_size` — but only in `ValidateReceiptMode::NewReceipt` mode, i.e., at receipt-creation time [2](#0-1) . `ValidateReceiptMode::ExistingReceipt` is explicitly documented as more lenient specifically *because* of this bug, referencing issue #12606: "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed" [3](#0-2) .

The maintainers' own workaround code confirms the root cause and its reach into cross-shard forwarding:
- In `try_forward` (`congestion_control.rs`), the receiver's outgoing-size accounting explicitly clamps any receipt whose size exceeds `max_receipt_size` down to `max_receipt_size` "to avoid receipts getting stuck," citing #12606 [4](#0-3) .
- The same clamp is applied when generating bandwidth-scheduler requests from buffered receipt sizes, again citing #12606, "so these requests would never be fulfilled" otherwise [5](#0-4) .

The test suite reproduces the exact "combine after validate" pattern:
- `test_max_receipt_size_promise_return`: a function call generates a receipt whose size is validated at exactly `max_receipt_size`; the DAG then rewires so `output_data_receivers` is appended to that already-validated receipt, pushing it over the limit — and the comment states this "should be rejected, but currently isn't because of a bug" [6](#0-5) .
- `test_max_receipt_size_value_return` shows the analogous case via a returned value wrapped in a `Data` receipt exceeding the limit [7](#0-6) .
- Both tests assert that an oversized receipt actually appears as an *incoming receipt proof* on-chain (`assert_oversized_receipt_occurred`), i.e., it is accepted into the receipt pipeline and cross-shard receipt proofs despite exceeding the hard limit [8](#0-7) .

This maps precisely to the CVE class: individually-validated components (the base receipt at creation time) are later combined/mutated (output-data linkage) into a final artifact that is never re-checked against the same size limit that gated the original validation, and the oversized artifact is propagated through downstream systems (congestion control, bandwidth scheduler, cross-shard receipt proofs) that were never designed to handle it, requiring ad hoc clamps rather than a fix at the source.

### Impact Explanation
`ChunkStateWitness` and the whole size-limit regime documented in `docs/misc/state_witness_size_limits.md` are built on the invariant that no receipt exceeds `max_receipt_size` (4 MiB) [9](#0-8) . An unprivileged contract-calling account can trigger this bug via a promise-return DAG or large returned value to create a receipt that exceeds `max_receipt_size` after passing the size check [10](#0-9) . Because the size limit is one of the load-bearing bounds used to keep total witness size under ~21 MiB, oversized receipts persisted this way inflate `ChunkStateWitness`/`source_receipt_proofs`, undermine the accounting used by congestion control and the bandwidth scheduler (whose code explicitly says unpatched sizes would never fit under outgoing limits and receipts would get permanently "stuck") [4](#0-3) , and risks resource-exhaustion / oversized-witness conditions analogous to the unbounded-memory-allocation impact in the original CVE.

### Likelihood Explanation
High reachability: the trigger is a normal, unprivileged `FunctionCall` action that returns a large value or issues a promise chain ending in a promise-return, both of which are exercised directly by the existing `max_receipt_size` test suite without any special privilege [11](#0-10) . The bug is a known, currently-unfixed issue (nearcore #12606) referenced from three separate call sites in the current tree, confirming it is still live in this codebase rather than historical.

### Recommendation
Re-validate receipt size (`max_receipt_size`) after any post-creation mutation (`output_data_receivers` append, promise-return rewiring, and data-receipt/value-return construction) before the receipt is persisted, forwarded, or included in outgoing receipt proofs — i.e., call `validate_receipt` (or an equivalent size check) as the final step of `create_action_receipt` / receipt-manager finalization in `runtime/runtime/src/receipt_manager.rs` and `runtime/runtime/src/lib.rs`, rather than only at initial creation. Once enforced, the compensating clamps in `try_forward` and `generate_bandwidth_request` (`congestion_control.rs`) that pretend oversized receipts are `max_receipt_size` should be revisited, since they currently mask the invariant violation rather than reject it.

### Proof of Concept
1. Deploy a test contract exposing a method that returns a value or promise chain sized to `max_receipt_size` minus a small margin (as in `max_receipt_size_promise_return_method1` / `max_receipt_size_value_return_method`) [12](#0-11) .
2. Call the method so the initially created receipt is validated at (or just under) `max_receipt_size`, then have the runtime append `output_data_receivers` / wrap the returned value, pushing the final receipt over the hard limit.
3. Observe (as `test_max_receipt_size_promise_return`/`test_max_receipt_size_value_return` do) that no `ReceiptSizeExceeded` error is raised and that a receipt above `max_receipt_size` subsequently appears in on-chain incoming receipt proofs, confirming the check was bypassed [8](#0-7) .

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // The DAG changes to: [C ->then-> B]

    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),

            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),

        account,

        "".into(),
        Gas::from_teragas(300),

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
