### Title
Method-id upgrade replay across `Network::Nightly` and `Network::TestNetworkWithForks` due to identical chain-id and default DA authority keys - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same value `5665`, and the default (env-unset) `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` constants for both networks are identical. `run_l1_block`'s chain-id gate therefore cannot distinguish a `BatchProofMethodId` body signed for one network from one intended for the other, and the identical default security-council keys mean signature verification also succeeds cross-network, breaking the function's own documented purpose of "prevent[ing] cross network replay attacks."

### Finding Description
The binding the code intends to enforce is:
`citrea_network_to_chain_id(N) == body.chain_id` should hold **only if** the body was signed for network `N`, i.e. chain_id must uniquely identify the network.

In `citrea_network_to_chain_id`: [1](#0-0) 
`Network::Nightly => 5665` and `Network::TestNetworkWithForks => 5665` — the two distinct enum variants collide on the same chain_id, violating the uniqueness the comment above the function claims to rely on: [2](#0-1) 

In `run_l1_block`, the gate that is supposed to reject a cross-network replay only checks this non-unique chain_id: [3](#0-2) 
then immediately calls `verify_method_id_security_council` with `method_id_upgrade_authority_da_public_keys` and, on success, performs [4](#0-3) 

Compounding this, the default (no-env-var) DA public keys for the method-id upgrade authority are identical between the two networks — same private-key-derived pubkeys `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5`: [5](#0-4) [6](#0-5) 
Both are selected via `InitialValueProvider<BitcoinSpec>::method_id_upgrade_authority_da_public_keys` based on the `Network` match arm: [7](#0-6) 

`Network::TestNetworkWithForks` is not test-only scaffolding excluded by the audit scope — it is a first-class `Network` enum variant wired into production binaries and node/prover configuration (`bin/citrea/src/rollup/bitcoin.rs`, `bin/citrea/src/main.rs`, `crates/primitives/src/forks.rs`, `crates/bitcoin-da/src/service.rs`, `crates/bitcoin-da/src/verifier.rs`, `crates/sovereign-sdk/module-system/sov-modules-stf-blueprint/src/lib.rs`), i.e. a real deployable network configuration, not a mock or test fixture.

Exploit flow: the security council signs a `BatchProofMethodIdBody{ chain_id: 5665, activation_l2_height: H, method_id: M }` intending to authorize method-id `M` at height `H` specifically for `Network::Nightly`. This body, together with its 3-of-5 signatures, is inscribed on the Bitcoin DA feed Nightly watches. Any party (an unprivileged attacker, or simply the natural relay of the same DA chain if Nightly and TestNetworkWithForks share infrastructure, as they explicitly do in default/test deployment configs) causes the identical inscription bytes to also be observed by a light-client prover configured with `network = TestNetworkWithForks`. In that prover's `run_l1_block` call: `circuit_chain_id = citrea_network_to_chain_id(TestNetworkWithForks) = 5665 == body.chain_id (5665)` passes; `verify_method_id_security_council` passes because the default `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` equal `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS`; `BatchProofMethodIdAccessor::insert` is then invoked, installing a method-id/activation-height pair the council never authorized for `TestNetworkWithForks`.

No existing guard catches this: the only network-discriminating check in the loop is the chain_id comparison, which is defeated by the collision, and there is no per-network domain separation added to the signed message (`body.serialize()` contains `method_id`, `activation_l2_height`, `chain_id` only — no network discriminant beyond the colliding chain_id).

### Impact Explanation
Two honest light-client provers running different `Network` configurations (`Nightly` vs `TestNetworkWithForks`) but observing overlapping/shared DA data will accept different, unauthorized method-id sets into their JMT state via `BatchProofMethodIdAccessor::insert`, causing them to use different `batch_proof_method_id` values when verifying batch proofs at the same L2 heights in `process_complete_proof`. This is exactly the "light client proof split where two honest provers commit different outputs for the same L1 block" category, and also constitutes "a method-id upgrade accepted that was never authorised" for the receiving network. This is repeatable for every method-id upgrade transaction the council issues on Nightly while a `TestNetworkWithForks` prover is live on shared/overlapping DA infrastructure.

### Likelihood Explanation
Requires: (1) a `TestNetworkWithForks` light-client prover deployed with default (unset) `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` env vars, matching stock config; (2) that instance's DA watch overlapping with Nightly's DA feed — plausible in shared test/staging Bitcoin regtest/signet infrastructure, as is common for internal/test networks; (3) an actual council-signed Nightly method-id upgrade to replay. No attacker key material, no forged signatures, and no cost beyond observing/relaying already-public inscription data are needed — this is a configuration-triggered code defect rather than a cryptographic bypass, so likelihood depends entirely on deployment topology, which the code itself does nothing to prevent.

### Recommendation
Give `Network::Nightly` and `Network::TestNetworkWithForks` distinct chain_id values in `citrea_network_to_chain_id`, and/or include an explicit network discriminant (not just chain_id) in the signed `BatchProofMethodIdBody` and in the message verified by `verify_method_id_security_council`, so a body signed for one network can never validate under another network's `run_l1_block` invocation regardless of DA feed overlap. Additionally, `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` should not silently default to the same keys as `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS`.
