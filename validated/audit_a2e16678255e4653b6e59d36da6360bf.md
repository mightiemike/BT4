### Title
Attacker-supplied `RevertInstructions.fund_recipient = 0x0` permanently freezes bridged funds in `ABORTED` outbound state - (File: x/uexecutor/keeper/outbound.go)

### Summary
`Inbound.revert_instructions.fund_recipient` is a free-form string supplied by whoever deposits into the gateway on the source chain — it is relayed and voted on by honest Universal Validators exactly as submitted, with no zero-address or format validation anywhere in the vote/finalize path. When a bridged deposit later has to be reverted (failed inbound execution, or a failed outbound requiring re-mint), the keeper unconditionally prefers this attacker-controlled string over the safe fallback (`Sender`) as long as it is non-empty, and feeds it straight into `common.HexToAddress(...)` for a PRC20 mint call. If the value canonicalizes to the zero address, the mint call is expected to revert (standard ERC20/PRC20 zero-recipient guard, mirroring the USDT zero-address check in the original report), and the keeper's only recourse is to mark the outbound `ABORTED`, which is a terminal, non-automatically-recoverable state.

### Finding Description
- `Inbound.RevertInstructions.FundRecipient` (proto: `RevertInstructions.fund_recipient`, `proto/uexecutor/v1/types.proto:95-100`) is attacker-supplied inbound metadata with no address validation. [1](#0-0) 
- In `handleFailedOutbound`, the revert-recipient selection prefers this field over the safe `outbound.Sender` fallback whenever it is non-empty, with no zero-address check: [2](#0-1) 
- If the resulting `CallPRC20Deposit` (re-mint for revert) fails — which is expected for a zero-address recipient on a PRC20 with a standard zero-address guard — the code path terminates in `AbortOutbound`, which sets `Status_ABORTED` and explicitly requires manual/admin intervention rather than any automatic retry or refund: [3](#0-2) [4](#0-3) 
- The same unguarded recipient-selection pattern (`FundRecipient` preferred over `Sender` with only an empty-string check) also appears in `buildRevertOutbound` (used for both normal inbound-execution failures and the admin `RevertStuckInbound` escape hatch) and in `applyGasRefund`: [5](#0-4) [6](#0-5) 
- Once ABORTED, there is no code path shown in `x/uexecutor` that reprocesses or refunds an aborted outbound automatically — `AbortOutbound` only removes the entry from `PendingOutbounds` and emits a monitoring event, i.e. the bridged tokens for that outbound are stuck pending manual/governance action. [7](#0-6) 

This directly parallels the Bracket/StopLimit root cause: an unprivileged, user-controlled "recipient" field with no zero-address constraint is fed into a token-transfer call inside a failure/cancellation code path, and the transfer's expected revert on `address(0)` converts the cancellation/revert flow into a stuck, unresolvable state that only a privileged actor can attempt to clear.

### Impact Explanation
This falls under the in-scope impact "permanent freezing ... of user or protocol-controlled funds" and "corruption of ... revert destination ... or canonical UniversalTx state." An outbound that should have refunded a user (either the bridged principal on `handleFailedOutbound`'s revert leg, or an admin-triggered `RevertStuckInbound`) instead becomes permanently `ABORTED`, with the underlying PRC20 tokens neither delivered to a recipient nor returned automatically. Unlike the original Bracket/StopLimit report (whose primary effect is a growing-array gas DoS), here the analogous effect is fund immobilization on a per-UTX basis — each such crafted deposit permanently locks its own bridged value in an ABORTED state pending manual operator action, which is a stronger unauthorized-freezing impact.

### Likelihood Explanation
Any depositor sets their own `RevertInstructions.fund_recipient` when initiating a deposit on the source chain (or in the raw/decoded payload the gateway relays); no permission is required, and honest Universal Validators simply relay and vote on whatever value was observed — they do not reject or sanitize it. The only conditions required are (a) the inbound later needs a revert/re-mint (a common code path already exercised for validation failures, failed outbound observations, and admin `RevertStuckInbound`), and (b) the destination PRC20 contract reverts on `mint(0x0, amount)` following standard ERC20 semantics, consistent with the assumption in the original report. The PRC20 contract implementation itself is not present in this repository's indexed Go/proto sources, so this exact revert behavior could not be directly confirmed from the scanned code — it is inferred from standard token semantics referenced by the seed report.

### Recommendation
Validate `RevertInstructions.fund_recipient` (and any other attacker-supplied recipient field consumed by mint/deposit calls) against the zero address — and any other unrecoverable/burn addresses — at the point of use in `handleFailedOutbound`, `buildRevertOutbound`, and `applyGasRefund`. If the field is zero/invalid, fall back to `Sender` unconditionally instead of trusting a non-empty-but-invalid value, and/or reject/normalize the field during inbound canonicalization so ballots never carry an unusable recipient.

### Proof of Concept
1. Attacker deposits into the gateway on a source chain and sets `revert_instructions.fund_recipient = "0x0000000000000000000000000000000000000000"` in the payload that becomes `Inbound.RevertInstructions.FundRecipient`.
2. Honest UVs observe and vote the inbound as-is (no format/zero check exists in the vote-finalize path); the UTX and (if funds-related) an outbound are created normally.
3. Trigger any failure path that reverts the outbound/inbound funds — e.g. destination-chain execution fails and UVs vote `MsgVoteOutbound` with `success=false` (`handleFailedOutbound`), or the inbound execution itself fails (`handleFailedInboundValidation` / `ExecuteInboundFunds`), or an admin later calls `RevertStuckInbound` for a stuck ballot.
4. The revert/re-mint call is made to `common.HexToAddress("0x000...000")`; on a PRC20 with standard OZ-style zero-address guards this reverts.
5. In the `handleFailedOutbound` case, this results in `AbortOutbound` marking the outbound `Status_ABORTED` — the bridged funds are stuck, with no automatic recovery path, matching the permanent-freezing pattern of the seed report.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}
