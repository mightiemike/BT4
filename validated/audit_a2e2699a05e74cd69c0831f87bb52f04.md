Confirmed: `validate_delete_action` (`runtime/runtime/src/action_validation.rs:447-451`) only checks that `beneficiary_id` is a syntactically valid account ID via `validate_action_account_id`, never that the account actually exists. This is the root cause enabling the analog.

### Title
Permanent loss of an account's balance when `DeleteAccount`'s `beneficiary_id` does not exist on-chain - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction.beneficiary_id` is only checked for syntactic validity at admission time, never for existence. `action_delete_account` unconditionally builds a system-predecessor "balance refund" receipt to that address for the account's full remaining balance. If the beneficiary account does not exist when this refund receipt executes, the refund transfer is rejected by `check_account_existence` (refunds may never implicitly create an account), and because it is a system/refund receipt, the deposit is unconditionally burned rather than returned to anyone.

### Finding Description
Any account holder can submit a `DeleteAccountAction { beneficiary_id }` transaction, and `beneficiary_id` is validated only for account-id syntax: [1](#0-0) 

When the delete executes, the account's current balance is unconditionally wrapped into a system balance-refund receipt addressed to `beneficiary_id`, with no existence check performed before creating it: [2](#0-1) 

`Receipt::new_balance_refund` marks the receipt's predecessor as `"system"`: [3](#0-2) 

When this refund receipt is later processed, `check_account_existence` treats it as a `Transfer` to a possibly-missing account, gated by `implicit_creation_allowed`, which explicitly forbids account creation for any refund receipt regardless of account type: [4](#0-3) [5](#0-4) 

If `beneficiary_id` is a named account that doesn't exist (never created, or itself deleted between the delete transaction being signed and executed), the transfer action fails with `AccountDoesNotExist`. Because the failing receipt's predecessor is `"system"`, the runtime does not generate a further refund for it — it burns the deposit outright: [6](#0-5) 

This burn-on-failed-refund behavior is documented as intentional for refunds in general (`docs/RuntimeSpec/Refunds.md:12`) and is exercised by an existing unit test that confirms a refund to a nonexistent (universal) account fails with `AccountDoesNotExist` and creates nothing: [7](#0-6) 

### Impact Explanation
This is the direct nearcore analog of the reported UXD bug: a value-transfer target chosen by an ordinary, unprivileged transaction signer (the account owner deleting their own account) is never checked for existence, and if invalid the transferred funds are permanently destroyed rather than returned to the sender. Unlike an ordinary `Transfer` action to a nonexistent named account — which fails the whole receipt and lets the deposit refund back to the predecessor (`test_refund_on_send_money_to_non_existent_account`) — `DeleteAccountAction`'s payout has no such recourse: it is generated as an unconditional system refund, and a failed refund is simply burned. Any user's entire account balance (all of `amount()`) can be irrecoverably lost through a single mistyped, deleted, or never-existing `beneficiary_id`, satisfying "permanently frozen/destroyed funds."

### Likelihood Explanation
Trivial to trigger accidentally (typo in beneficiary, or beneficiary account deleted/never created between signing and execution — races are plausible on a live chain), and requires only a single ordinary `DeleteAccount` transaction signed by the account owner. No privileged role, validator behavior, or multi-party coordination is needed.

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` refers to an existing (and, per current implicit-creation rules, appropriately initialized) account, and fail the `DeleteAccount` action with a clear error (e.g. `BeneficiaryDoesNotExist`) if not — mirroring how a plain `Transfer` to a nonexistent named account is rejected — rather than allowing the funds to be silently and irrecoverably burned via the refund-failure path.

### Proof of Concept
1. Account `alice.near` holds a nonzero balance and no locked stake.
2. `alice.near` signs `SignedTransaction { actions: [Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })] }` where `nonexistent.near` was never created (or has since been deleted).
3. `validate_delete_action` accepts it (valid syntax only) — `runtime/runtime/src/action_validation.rs:447-451`.
4. `action_delete_account` removes `alice.near` and enqueues `Receipt::new_balance_refund(&"nonexistent.near", alice_balance)` — `runtime/runtime/src/actions.rs:380-386`.
5. That system receipt executes against `nonexistent.near`; `check_account_existence`/`implicit_creation_allowed` reject the transfer because refunds can never create an account — `runtime/runtime/src/actions.rs:928-934`.
6. Because `receipt.predecessor_id().is_system()` and `result.result.is_err()`, the entire `alice_balance` is added to `other_burnt_amount` and permanently lost — `runtime/runtime/src/lib.rs:1047-1055`. This exact mechanic (refund to a missing account fails and creates nothing) is already validated by `refund_may_not_create_universal_account` in `runtime/runtime/src/tests/apply.rs:6880-6926`, which can be adapted with a named (non-universal) missing beneficiary to directly reproduce total balance loss.

            .apply(
