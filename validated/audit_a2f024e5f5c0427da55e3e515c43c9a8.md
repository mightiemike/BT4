### Title
Stake-reward recalculation after snapshot restore reads *live* `StakesCache` state instead of the frozen reward-epoch snapshot, letting stake activity in the recalculation window divert yield ("JIT deposit" analog) - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The Sturdy report describes an attacker timing a large deposit immediately before a fixed-size yield pool is divided, capturing yield without having contributed to earning it, then withdrawing. Agave's partitioned epoch-rewards recalculation path has a structurally analogous flaw: when a validator restarts from a snapshot while a `EpochRewards` distribution is still active, it recomputes each stake account's share of the *already-fixed* reward pool using the bank's **current** `StakesCache` instead of the pinned reward-epoch-boundary state, while the pool total (`total_rewards`/`total_points`) is frozen from the original calculation.

### Finding Description
`recalculate_partitioned_rewards_if_active` / `recalculate_stake_rewards` is invoked from `initialize_after_snapshot_restore`, which runs when a bank is rebuilt from a snapshot mid-distribution. [1](#0-0) 

`recalculate_stake_rewards` re-derives `point_value` from the sysvar (fixed, computed at the original epoch boundary) but pulls `stake_delegations` from `self.stakes_cache.stakes()` — the bank's *current*, live delegation set at the restart slot, not a frozen copy from the rewarded epoch: [2](#0-1) 

The function's own comment acknowledges the resulting reward-commission output is unreliable for exactly this reason ("the commission account is loaded from the current bank, and not the start of the epoch... should NOT be used ever"): [3](#0-2) 

The same root cause was independently identified and specifically patched for the Alpenglow block-reward denominator, whose comment explicitly states that during recalculation "`distribution_epoch_vote_accounts` already includes updated stake activation values from after the new epoch calculation," requiring a pinned `RewardEpochDelegatedStakes` denominator instead of the live one: [4](#0-3) 

A regression test was added to lock in that one fix (recalculation after partial distribution must reuse the *original* AG delegated-stake denominator): [5](#0-4) 

However, the Tower-style (non-Alpenglow) points computation feeding `calculate_stake_rewards_and_commissions` still consumes `stake_delegations` sourced directly from the live `self.stakes_cache.stakes()` at recalculation time: [6](#0-5) [7](#0-6) 

Because the point pool (`total_rewards`/`total_points`) is frozen while the per-account inputs (`stake_delegations`, commission-collector routing) are re-read from whatever state the bank happens to be in at the restart slot, any state change that occurs between the original in-memory calculation and a later restart-triggered recalculation (e.g., stake merges that combine already-activated stake into a larger delegation still counted "active" at `rewarded_epoch`, or a commission-collector reassignment via `custom_commission_collector`) changes what a restarted node computes for the still-undistributed partitions, versus what a non-restarted honest node already computed and is paying out from its original in-memory `all_stake_rewards`. This is directly analogous to the Sturdy JIT-deposit bug: yield is divided using inputs measured at the moment of division, not at the moment the yield-generating snapshot was actually taken, so parties can shift measured inputs in the interim to grab a larger share of a fixed pool.

### Impact Explanation
This causes an **honest-node snapshot-vs-replay mismatch**: two honest validators computing rewards for the identical rewarded epoch (one that never restarted, one that restarted from a snapshot taken mid-distribution) can arrive at different `PartitionedStakeReward` values for the same stake accounts in the still-undistributed partitions, since the fixed reward pool is divided against different underlying delegation/commission inputs. This can silently change individual stakers' balances/lamports minted relative to what other nodes computed, and — because reward-commission outputs from this path are explicitly documented as untrustworthy — can also feed incorrect commission-account crediting if that path were ever relied upon. Given rewards affect capitalization and consensus-relevant account balances, divergence here is a capitalization/consistency hazard, not merely a UX inconvenience.

### Likelihood Explanation
Exploitation requires the specific, narrow condition that a validator restarts from a snapshot while the `EpochRewards` sysvar is still active (mid partitioned-distribution) — a normal, non-adversarial operational occurrence (validator crash/restart, fastboot, ledger-tool bank reconstruction). An attacker cannot force another honest validator to restart at will, but can benefit passively any time such a restart occurs naturally during the distribution window by having already performed stake operations (merges, delegation changes, commission-collector switches) that shift the live `stake_delegations`/commission routing prior to that restart. Because this is contingent on external restart timing, likelihood is moderate rather than trivially and reliably triggerable by an unprivileged actor alone.

### Recommendation
`recalculate_stake_rewards` should reconstruct/re-derive its stake-delegation and commission-collector inputs from state pinned at the reward epoch boundary (analogous to `RewardEpochDelegatedStakes`, which was already added for the Alpenglow block-reward path), rather than reading `self.stakes_cache.stakes()` live at recalculation time. At minimum, the function's own caveat that "`RewardCommissionAccounts`... should NOT be used ever" indicates the design already recognizes divergence risk in this exact call path and should be extended to cover the stake-rewards/points computation with a similarly pinned denominator/inputs, or the recalculation should be made to reproduce the originally-computed `all_stake_rewards` bit-for-bit rather than recomputing from potentially-mutated live state.

### Proof of Concept
1. Node A reaches an epoch boundary; `calculate_rewards`/`compute_new_epoch_caches_and_rewards` computes `PartitionedStakeRewards` for all delegations and begins distributing them across partitions over subsequent blocks (`EpochRewardPhase::Calculation` → `Distribution`), as exercised by `test_recalculate_stake_rewards` and `test_initialize_after_snapshot_restore`. [8](#0-7) 
2. Before all partitions are distributed, a staker performs a stake-account merge that increases the `Delegation.stake` amount of an already fully-activated stake account (so `delegation_effective_stake` at `rewarded_epoch` reflects the larger merged amount), or changes their vote account's commission-collector via `custom_commission_collector`.
3. A validator crashes/restarts and loads a bank snapshot taken after step 2 but still within the active `EpochRewards` window; `initialize_after_snapshot_restore` calls `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards`, which reads the now-mutated `stakes_cache` while still dividing the original, fixed `total_rewards`/`total_points`. [9](#0-8) 
4. The restarted validator's recomputed `stake_rewards` for the remaining partitions differ from what a non-restarted honest validator already computed and is distributing for the same stake accounts, producing a divergence in delivered rewards for identical epoch/partition indices — verifiable by comparing `calculation_status.all_stake_rewards` (pre-restart) against the output of `recalculate_stake_rewards` (post-restart) when the intervening stake mutation described in step 2 is injected, following the pattern already used in `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` but for the Tower/non-Alpenglow path, which lacks that test's pinned-denominator protection. [10](#0-9)

    /// Calculates epoch reward points from stake/vote accounts.
    /// Returns reward lamports and points for the epoch or none if points == 0.
    fn calculate_reward_points_partitioned<'a>(
        &self,
        stake_history: &StakeHistory,
        stake_delegations: &Vec<(&'a Pubkey, &'a StakeAccount<Delegation>)>,
        cached_vote_accounts: &CachedVoteAccounts<'_>,
        epoch_inflation_rewards: u64,
        ag_epoch_type: &AlpenglowEpochType,
        thread_pool: &ThreadPool,
        metrics: &RewardsMetrics,
    ) -> Option<PointValue> {
        let CachedVoteAccounts {
            distribution_epoch_vote_accounts,
            ..
        } = cached_vote_accounts;

        let solana_vote_program: Pubkey = solana_vote_program::id();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        match ag_epoch_type {
            AlpenglowEpochType::Alpenglow { .. } => {
                // In alpenglow, we do not need to compute `PointValue::points` as the final
                // rewards are simply the total credits stored in the vote account.  We just need
                // to return a `Some` value with valid rewards.
                return Some(PointValue {
                    rewards: epoch_inflation_rewards,
                    points: 0,
                });
            }
            AlpenglowEpochType::Tower => {
                // For tower we need to compute the valid `PointValue::points`.
            }
            AlpenglowEpochType::MigrationEpoch { .. } => {
                // For the migrating epoch, we need to compute the tower portion of `PointValue::points`.
            }
        }

        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        let (points, measure_us) = measure_us!(thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .map(|(_stake_pubkey, stake_account)| {
                    let vote_pubkey = stake_account.delegation().voter_pubkey;

                    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey)
                    else {
                        return 0;
                    };
                    if vote_account.owner() != &solana_vote_program {
                        return 0;
                    }

                    calculate_points_for_tower(
                        stake_account.stake_state(),
                        DelegatedVoteState::from(vote_account.vote_state_view()),
                        stake_history,
                        new_warmup_cooldown_rate_epoch,
                        use_fixed_point_stake_math,
                    )
                    .unwrap_or(0)
                })
                .sum::<u128>()
        }));
