### Title
Unauthenticated, fee-free class declaration via the hardcoded `'BOOTSTRAP'` sender-address bypass - (File: `crates/starknet_api/src/executable_transaction.rs`)

### Summary
The `is_bootstrap_declare` check that is meant to let the sequencer bootstrap a brand-new chain with a single privileged, fee-free `Declare` transaction is gated only by transaction-supplied fields (`sender_address == 'BOOTSTRAP'`, `nonce == 0`, `charge_fee == false`) rather than by any real authorization, deployed-account check, or chain-height/genesis restriction. Because `sender_address` and the resource bounds that determine `charge_fee` are both attacker-controlled fields of an ordinary `RpcTransaction::Declare` submitted to the gateway, any unprivileged user can craft a `Declare` transaction that satisfies this predicate and have the sequencer skip `__validate_declare__`, skip the nonce check/increment, and skip fee charging entirely.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` is defined as: [1](#0-0) 

and the constant address it compares against is simply a hardcoded felt, not tied to any deployed contract, signer, or role: [2](#0-1) 

This predicate is consumed directly in the blockifier's main transaction-execution path, `AccountTransaction::execute_raw`, which is reached for every `Declare` transaction included in a block by the sequencer/batcher: [3](#0-2) 

When the predicate is true, the code path completely bypasses:
- `perform_pre_validation_stage` (which performs the nonce check/increment and fee-bound checks), and
- `validate_tx`/`__validate_declare__` (the account authentication entry point that would normally verify a signature),

and instead runs `tx.run_execute(...)` directly, i.e., only the "declare the class" storage effect is applied, with no signature, nonce, or fee verification at all. The equivalent unauthenticated fast-path also exists in the Starknet OS Cairo re-execution code, confirming that both the Rust sequencer/blockifier and the OS agree on skipping validation for this address/nonce/fee combination: [4](#0-3) 

The three conditions required to hit this bypass are all attacker-controlled at the gateway boundary:
1. `sender_address == bootstrap_address()` — any submitter can put this literal address in a normal `Declare` V3 transaction; it requires no private key or account deployment.
2. `nonce == 0` — trivially satisfiable, and because the bypass path never increments state nonce for this special address (the nonce-increment logic is entirely skipped), the state nonce for `'BOOTSTRAP'` never advances, so this condition remains satisfiable indefinitely, not just once at genesis.
3. `!charge_fee` — `charge_fee` is derived from `enforce_fee(executable_tx, only_query)`, which is false whenever the transaction's resource bounds are set to enforce no fee (an attacker fully controls `resource_bounds` on their own transaction).

There is no check anywhere in the gateway (`crates/apollo_gateway/src/stateless_transaction_validator.rs`, `crates/apollo_gateway/src/stateful_transaction_validator.rs`) or in the mempool admission path that rejects a `Declare` transaction whose `sender_address` equals the reserved bootstrap constant, nor any restriction tying this behavior to genesis/block 0 or to an operator-only submission channel. The intended use is described only in a code comment and an integration test (`crates/apollo_integration_tests/tests/bootstrap_declare.rs`) — it is not structurally enforced.

### Impact Explanation
Any unprivileged transaction sender can repeatedly declare arbitrary Sierra/CASM classes at zero fee and with no signature/authentication check, by simply setting `sender_address = 'BOOTSTRAP'`, `nonce = 0`, and zero-fee resource bounds on a `Declare` transaction. This is a direct analog of the CVE's "authentication bypass ... enable escalation of privilege via network access": an entry point intended to be usable only by the trusted bootstrap process is reachable and repeatable by any network client, without any credential.
Concrete effects:
- Complete bypass of the network's declare-transaction fee market (an unlimited, free resource-consumption channel: attackers can declare classes — including large ones — without paying, undermining the fee-based DoS-resistance model of the sequencer/bouncer).
- Because the nonce is never incremented for the bootstrap sender inside the bypass branch, this is not a one-time genesis-only exploit; it is repeatable for as long as class hashes are available to declare (the `dict_update{... prev_value=0}` only prevents re-declaring the *same* class hash, not reuse of the bypass itself with new class hashes).
- This allows flooding blocks with free class declarations, degrading normal users' ability to get transactions included (a form of "network unable to confirm new transactions at expected cost/rate") and enables an attacker to effectively act as a privileged "system bootstrap" entity without authorization.

### Likelihood Explanation
High likelihood of reachability: the only requirements are knowledge of the fixed `'BOOTSTRAP'` address constant (public in source code) and the ability to submit an ordinary `Declare` V3 RPC transaction through the public gateway — both trivially available to any unprivileged network user. No cryptographic break, no privileged access, and no race condition is required.

### Recommendation
Restrict the bootstrap-declare fast path so it cannot be triggered by externally submitted transactions post-genesis:
- Enforce that this bypass is only permitted when the current state nonce read from state (not the attacker-supplied transaction nonce) for the bootstrap address is `0` AND the chain/block is still in its bootstrap phase (e.g., gate by block number == 0, or by a one-shot flag persisted in state once bootstrapping completes).
- Reject any incoming `Declare` transaction at the gateway/mempool layer whose `sender_address` equals `DeclareTransaction::bootstrap_address()` unless it originates from a trusted, out-of-band bootstrap process (not the public RPC/P2P gateway).
- Ensure the nonce for the bootstrap address is actually incremented/consumed after first use so the bypass cannot be exercised more than once.

### Proof of Concept
1. Craft an `RpcTransaction::Declare` (V3) with:
   - `sender_address = ContractAddress::from(0x424f4f545354524150_u128)` (the literal `'BOOTSTRAP'` constant from `bootstrap_address()`),
   - `nonce = 0`,
   - `resource_bounds` set such that `enforce_fee` evaluates to `false` (e.g., zero/no-fee-enforcement bounds, mirroring `ValidResourceBounds::create_for_testing_no_fee_enforcement()` used in `generate_bootstrap_declare()` in `crates/mempool_test_utils/src/starknet_api_test_utils.rs`, lines 585-595),
   - any arbitrary valid Sierra class and matching `compiled_class_hash`,
   - no valid signature (leave signature empty/default).
2. Submit via the standard `add_transaction` gateway endpoint.
3. The gateway's stateless/stateful validators do not reject the special sender address; when the transaction reaches `AccountTransaction::execute_raw` during block building, `is_bootstrap_declare` returns `true`, so `__validate_declare__` (signature check), nonce validation, and fee charging are all skipped, and the class is declared successfully at zero cost with no authentication.
4. Repeat with new class hashes (since state nonce for the bootstrap address is never incremented in this branch) to keep abusing the bypass.

        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
