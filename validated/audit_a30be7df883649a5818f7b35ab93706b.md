### Title
Flat-cost `VOTEWITNESS` TVM opcode enables sub-linear-cost DoS via oversized witness arrays before `MAX_VOTE_NUMBER` validation - (File: `actuator/src/main/java/org/tron/core/vm/EnergyCost.java`, `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The reported bug class is: an externally reachable, unbounded array-processing function is charged a cost that does not scale with the actual work performed, allowing an attacker to force disproportionate node computation for cheap. The closest analog in java-tron is the TVM `VOTEWITNESS` opcode path (`Program.voteWitness`), whose energy cost (`EnergyCost.getVoteWitnessCost`/`Cost2`/`Cost3`) charges a flat `VOTE_WITNESS` base fee (30000) plus only memory-expansion energy for the witness/amount arrays, while the O(n) iteration over the arrays (`Program.voteWitness`, `VoteWitnessProcessor.execute`) happens regardless, and the `MAX_VOTE_NUMBER` bound is enforced only inside `VoteWitnessProcessor.validate`, i.e. after the array has already been fully materialized and looped over in `Program.voteWitness`.

### Finding Description
`Program.voteWitness(int witnessArrayOffset, int witnessArrayLength, int amountArrayOffset, int amountArrayLength)` [1](#0-0)  is invoked directly by any smart contract via the `VOTEWITNESS` TVM opcode. It only checks that `witnessArrayLength == amountArrayLength` and that both match the declared array-length operands on the stack; it does **not** bound `witnessArrayLength` against `MAX_VOTE_NUMBER` before reading `witnessArrayData`/`amountArrayData` and looping `for (int i = 0; i < witnessArrayLength; i++)` to build a `VoteWitnessParam` [2](#0-1) .

The `MAX_VOTE_NUMBER` bound is only enforced afterward, inside `VoteWitnessProcessor.validate`, once the full param object has already been built via the O(n) loop [3](#0-2) .

The energy pre-charge for this opcode, computed in `EnergyCost.getVoteWitnessCost`/`getVoteWitnessCost2`/`getVoteWitnessCost3`, only adds `VOTE_WITNESS` (a flat 30000) plus the standard EVM-style memory-expansion cost for the max of the witness/amount array footprints — it does **not** charge per-element energy proportional to `witnessArrayLength` for the subsequent CPU work of decoding each `DataWord`, building `Protocol.Vote` objects, and iterating them in `VoteWitnessProcessor.execute` (address decode, `LongMath.checkedAdd`, `HashMap` merge) [4](#0-3) . Memory-expansion cost does scale quadratically with total memory words touched, but that charge is capped/bounded by the `MEM_LIMIT` (3MB) check [5](#0-4) , which permits up to `~3MB / 64 bytes-per-vote ≈ 46,000` witness/amount word-pairs to be memory-allocated and then linearly parsed/hashed/summed in `VoteWitnessProcessor.execute` before the `MAX_VOTE_NUMBER` rejection is even reached — for a memory-expansion energy cost that is dominated by the quadratic memory term, not the linear parsing/HashMap/BigMath work actually performed.

This mirrors the reported bug class: exposed array-processing logic (`_addCredIdPerAddress`/`_removeCredIdPerAddress`) that any caller can invoke to force disproportionate iteration/state growth relative to the gas/energy actually charged, and whose bound-check (`indexToRemove`/`credId_` validation) happens only deep inside the function after cheap-but-unbounded work has already begun.

### Impact Explanation
An attacker-controlled contract can repeatedly call `VOTEWITNESS` with witness/amount arrays sized close to the `MEM_LIMIT`-permitted maximum, paying energy dominated by the flat 30000 base fee plus quadratic memory-expansion cost, while forcing the node to execute a full O(n) `DataWord` decode/loop in `Program.voteWitness` and a second O(n) address-decode + `HashMap` merge + `LongMath` loop in `VoteWitnessProcessor.execute`, before the transaction is ultimately rejected by the `MAX_VOTE_NUMBER` check. Because the rejection happens late, the CPU cost of the rejected call is not proportional to the flat+quadratic-memory energy charged for it, allowing cheap, repeated CPU-heavy calls — a computational DoS vector against block-producing/validating nodes, consistent with the "forcing a block gas limit" and "repeated failing transactions" scenarios described in the source report.

### Likelihood Explanation
The opcode is reachable by any account via a simple smart contract (no privileged role, no leaked key, no P2P/node compromise needed), matching the "reachable from a broadcast transaction / contract call" requirement. Exploitation only requires deploying a contract that calls `VOTEWITNESS` with large, well-formed (but ultimately over-limit) arrays, making likelihood moderate-to-high for automated abuse, though the `MEM_LIMIT` cap (3MB) bounds the maximum per-call array size, limiting the worst-case blow-up per individual transaction.

### Recommendation
- In `Program.voteWitness`, validate `witnessArrayLength` (and `amountArrayLength`) against `MAX_VOTE_NUMBER` immediately after reading the length operands, before allocating/reading `witnessArrayData`/`amountArrayData` or entering the parsing loop, so oversized calls fail fast with minimal work performed.
- In `EnergyCost.getVoteWitnessCost`/`Cost2`/`Cost3`, add an explicit per-element energy component proportional to `witnessArrayLength` (mirroring `LOG_DATA_ENERGY`-style linear charging used elsewhere in the file), so that the charged energy is proportional to the actual parsing/looping work done in `Program.voteWitness` and `VoteWitnessProcessor.execute`, independent of whether the memory-expansion formula happens to be small for a given array layout.

### Proof of Concept
1. Deploy a contract that invokes the `VOTEWITNESS` opcode with `witnessArrayLength == amountArrayLength` set to a large value (e.g., tens of thousands), sized so the resulting memory footprint stays just under the 3MB `MEM_LIMIT` in `EnergyCost.checkMemorySize`.
2. `Program.voteWitness` reads and decodes all `witnessArrayLength` `DataWord` pairs into a `VoteWitnessParam`, performing O(n) work, before calling `VoteWitnessProcessor.validate`, which only then rejects the call because `param.getVotes().size() > MAX_VOTE_NUMBER`.
3. Repeat the call from many transactions/blocks; each call pays energy dominated by the flat `VOTE_WITNESS` (30000) constant plus quadratic memory-expansion energy, while the node performs O(n) decode/loop work per call — a mismatch between charged energy and actual CPU cost that can be repeated cheaply.

Note: I was not able to execute or benchmark this path in the given environment; the analysis is based on static reading of `Program.voteWitness`, `EnergyCost.getVoteWitnessCost*`, and `VoteWitnessProcessor`. Confirming the actual exploitable magnitude (energy paid vs. wall-clock/CPU cost per call) would require running a local TVM benchmark, which a Devin session with code-execution access could perform.

  public static long getVoteWitnessCost(Program program) {
    Stack stack = program.getStack();
    long oldMemSize = program.getMemSize();
    DataWord amountArrayLength = stack.get(stack.size() - 1).clone();
    DataWord amountArrayOffset = stack.get(stack.size() - 2);
    DataWord witnessArrayLength = stack.get(stack.size() - 3).clone();
    DataWord witnessArrayOffset = stack.get(stack.size() - 4);

    DataWord wordSize = new DataWord(DataWord.WORD_SIZE);

    amountArrayLength.mul(wordSize);
    BigInteger amountArrayMemoryNeeded = memNeeded(amountArrayOffset, amountArrayLength);

    witnessArrayLength.mul(wordSize);
    BigInteger witnessArrayMemoryNeeded = memNeeded(witnessArrayOffset, witnessArrayLength);

    return VOTE_WITNESS + calcMemEnergy(oldMemSize,
        (amountArrayMemoryNeeded.compareTo(witnessArrayMemoryNeeded) > 0
            ? amountArrayMemoryNeeded : witnessArrayMemoryNeeded), 0, Op.VOTEWITNESS);
  }
