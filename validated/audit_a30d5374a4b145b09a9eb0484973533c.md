### Title
Unbounded shared `IdempotentPromiseHandler.identifiers` map causes CPU/latency DoS across all shops during token-exchange authentication - (File: `packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts`)

### Summary
`IdempotentPromiseHandler` is instantiated exactly once per `shopifyApp()` call and stored on the shared, process-wide `config` object, so it is reused across every shop/tenant served by the app instance [1](#0-0) . Every token-exchange authentication (both the legacy Auth Code strategy path in `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router`) calls `handlePromise` keyed by the raw session token string whenever the `afterAuth` hook fires [2](#0-1) [3](#0-2) .

### Finding Description
`IdempotentPromiseHandler` keeps every seen identifier in a single `Map<string, number>` and only prunes stale entries reactively, on every single call to `handlePromise`, by iterating the entire map with `this.identifiers.forEach(...)`: [4](#0-3) 

This is structurally the same bug class as the report: an attacker-influenced, ever-growing collection (`_withdrawalQueue` in the report vs. `identifiers` Map here) is fully iterated on every request into the affected function, with no cap on how large the collection can grow within the TTL window (60 seconds, `IDENTIFIER_TTL_MS`). Because the map is keyed by the full session-token string (a fresh JWT with unique `jti`/timestamp claims each time App Bridge reissues one), and because the handler instance is shared globally by `deriveConfig` for the whole app process rather than scoped per shop, any legitimate merchant who repeatedly triggers token exchange (e.g., by repeatedly loading/reloading the embedded app, or scripting many token-exchange requests with distinct valid session tokens within the 60-second window) adds a new entry per request. Each subsequent `handlePromise` call — including calls made on behalf of unrelated shops sharing the same app process — pays the cost of iterating the full, growing map before it can complete.

Reaching this requires only a single merchant with a normal embedded-app session (an unprivileged actor relative to the app's other tenants): they don't need any special access beyond installing/using their own instance of the app and repeatedly forcing offline/online token exchange (e.g., by invalidating their own session or hammering the auth entrypoint), each time with a distinct, validly-signed session token.

### Impact Explanation
Because the `IdempotentPromiseHandler` instance is shared across all shops served by one app deployment/process, unbounded growth of `identifiers` degrades `clearStaleIdentifiers`'s O(n) full-map iteration for every tenant's authentication flow, not just the attacker's own shop. In a busy multi-tenant deployment this becomes a CPU-bound bottleneck on the hot path of `authenticate.admin`/`performTokenExchange`, increasing authentication latency and potentially causing request timeouts for unrelated merchants — a denial-of-service condition on the app's authentication handler, analogous to the reported gas-DoS via unbounded queue iteration.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker (or curious/malicious merchant) to script repeated requests to a route that triggers token exchange while supplying a fresh, validly-signed session token each time. Obtaining fresh valid session tokens as a legitimate merchant of one's own installed app is straightforward (App Bridge reissues them frequently, and a script can also request a stale/expiring one repeatedly). Because entries only expire after 60 seconds and are only cleaned reactively (not proactively/periodically or bounded by a max size), a moderate request rate is sufficient to keep the map large indefinitely.

### Recommendation
- Bound the size of `identifiers` (e.g., LRU eviction or a hard cap) and/or clean up expired entries with a proactive timer instead of relying on `forEach` during every `handlePromise` call.
- Avoid a single globally-shared `IdempotentPromiseHandler` across all tenants; scope it per shop/session (or use a wall-clock/interval-based sweep instead of doing a full-map scan on every invocation).
- Consider using a `Map` ordered by insertion and only checking/evicting the oldest entries lazily (bounded work per call) rather than scanning the whole collection each time.

### Proof of Concept
1. Deploy a `shopify-app-remix` (or `-express`/`-react-router`) app configured with `unstable_newEmbeddedAuthStrategy` (token exchange) enabled and embedded.
2. As a merchant with a live embedded session, script a client to repeatedly obtain fresh session tokens from App Bridge (or replay newly-signed but distinct JWTs, each satisfying `decodeSessionToken`) and hit an authenticated route so that `performTokenExchange`/`TokenExchangeStrategy.authenticate` is invoked and the offline session is treated as invalid/expiring each time, forcing `handleAfterAuthHook`/`callAfterAuthHook` → `idempotentPromiseHandler.handlePromise({identifier: sessionToken})` to run [5](#0-4) .
3. Repeat quickly (many distinct tokens within the 60-second TTL window) to grow `identifiers` to a large size.
4. Observe that concurrent authentication requests for other shops sharing the same app process now incur a linearly increasing delay in `clearStaleIdentifiers`'s `forEach` scan, degrading throughput/latency of the shared auth handler for all tenants.

Note: I was unable to execute this scenario in a live environment (no runtime/terminal access here) to empirically measure the exact latency impact; this assessment is based on static code review of `idempotent-promise-handler.ts` and its call sites, and confidence would be strengthened by load-testing a real deployment.

```typescript
  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
}
```
