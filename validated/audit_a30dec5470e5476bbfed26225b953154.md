## Analysis Result

### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` JSON-RPC methods allow any caller to mutate sequencer commitment-posting state - (File: `crates/sequencer/src/rpc.rs`)

### Summary
The `EmissionScheduler#epochEmission` bug class is "a state-mutating function that should be restricted to a privileged caller (`minter`) has no access control, so any unprivileged caller can invoke it and corrupt protocol state." The reachable analog in this repository is the sequencer's `citrea_haltCommitments` and `citrea_resumeCommitments` JSON-RPC methods, which mutate the sequencer's commitment-posting behavior and carry no access-control check whatsoever.

### Finding Description
The sequencer RPC server exposes `halt_commitments` and `resume_commitments`, which unconditionally forward `SequencerRpcMessage::HaltCommitments` / `SequencerRpcMessage::ResumeCommitments` to the sequencer's control loop: [1](#0-0) 

Unlike `publish_test_block`, which is gated by `self.context.test_mode`: [2](#0-1) 

`halt_commitments` and `resume_commitments` have **no equivalent guard at all** — no `test_mode` check, no signature/authorization requirement, nothing.

The only authentication layer in the codebase is the `Auth` RPC middleware, which whitelists just three protected methods (`backup_create`, `backup_validate`, `backup_info`) and passes every other method straight through to the handler unauthenticated: [3](#0-2) 

`citrea_haltCommitments`/`citrea_resumeCommitments` are not in `PROTECTED_METHODS`, so any client with network access to the sequencer's JSON-RPC endpoint can call them, exactly mirroring the reported bug class: a state-mutating function meant for a privileged role (here, the sequencer operator/admin) is reachable by anyone.

### Impact Explanation
This matches the explicitly listed High-severity class: "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`." An unprivileged attacker can call `citrea_haltCommitments` to indefinitely stop the sequencer from posting sequencer commitments to L1 (breaking the binding between L2 block production and L1 commitment posting that downstream provers/full nodes and the bridge rely on), or call `citrea_resumeCommitments` to interfere with an operator's intentional halt (e.g., during an incident response), all without any credential.

### Likelihood Explanation
High. No secret, signature, or configuration bypass is required — the vulnerable methods are on the standard sequencer RPC surface and are trivially reachable by any client that can reach the RPC port, the same way `eth_sendRawTransaction` is reachable.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other operator-only control-plane RPC methods) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or otherwise require the same API-key/authorization check applied to `backup_create`/`backup_validate`/`backup_info` before forwarding these messages in `crates/sequencer/src/rpc.rs`.

### Proof of Concept
1. Start a Citrea sequencer node with its RPC endpoint reachable.
2. As an unauthenticated party, send: `curl -X POST <sequencer_rpc> -d '{"jsonrpc":"2.0","method":"citrea_haltCommitments","params":[],"id":1}'`.
3. The call succeeds (no auth error), and the sequencer immediately stops posting sequencer commitments to L1, since `halt_commitments` unconditionally dispatches `SequencerRpcMessage::HaltCommitments` with no caller check [4](#0-3) .
4. Compare with `Auth`'s `PROTECTED_METHODS` list, confirming `citrea_haltCommitments` is absent and thus unauthenticated [5](#0-4) .

pub struct Auth<S> {

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,

    type Future = BoxFuture<'a, MethodResponse>;
