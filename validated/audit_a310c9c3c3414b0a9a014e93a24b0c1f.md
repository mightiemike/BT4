## Analysis

The reported JOJO bug is fundamentally: a mandatory, unconditional value transfer to a specific account (embedded inside a larger, atomic financial-state-transition), whose execution depends on external/receiver-side conditions the initiator can influence, can be made to fail — and that failure blocks/reverts the entire critical operation, causing a stuck protocol state.

The closest structurally-analogous, reachable-by-an-ordinary-signer pattern in `nearcore` is in `update_validator_accounts`, the mandatory per-epoch-boundary step that pays out the protocol treasury's share of validator rewards [1](#0-0) . Unlike the stake-return and validator-reward paths (which explicitly tolerate an uninitialized/absent account, see the "skip" logic at lines 1722–1747), the protocol-treasury branch unconditionally requires the account to exist and turns a missing account into a fatal `StorageError::StorageInconsistentState` [2](#0-1) .

`DeleteAccount` is an ordinary, unprivileged action available to any account holder as long as the account has no locked (staked) balance [3](#0-2) ; nothing in `check_account_existence`/`check_actor_permissions` special-cases the protocol treasury account. If the account that genesis designates as `protocol_treasury_account` is deleted while it is not itself a current validator (the common case — treasury accounts typically don't stake), the very next epoch boundary at which that account's shard applies `ValidatorAccountsUpdate` will hit `get_account(...).ok_or_else(StorageInconsistentState)` and fail [4](#0-3) .

That `StorageError` is not handled gracefully by the chain layer: `apply_chunk` explicitly panics on any `Error::StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue` [5](#0-4) , and `chain/chain/src/runtime/mod.rs` itself also panics on some `RuntimeError` variants in the apply path [6](#0-5) . Because every honest node applies the same state transition deterministically, this is not a single-node crash — it is a network-wide halt of the shard hosting the treasury account, triggered entirely by a single, valid, unprivileged `DeleteAccount` transaction.

### Title
Deleting the protocol-treasury account triggers a fatal `StorageInconsistentState` panic at the next epoch boundary, halting chunk application on its shard - ([File: runtime/runtime/src/lib.rs])

### Summary
`update_validator_accounts` pays the protocol treasury its epoch reward by unconditionally fetching the treasury account and treating its absence as an unrecoverable storage-inconsistency error, unlike every other account-lookup in the same function which tolerates a missing/uninitialized account. Since the treasury account can be deleted like any other account via a normal `DeleteAccount` action (as long as it holds no stake), any signer controlling that account's keys can delete it, and the next epoch-boundary apply on its shard will deterministically panic on every node.

### Finding Description
`update_validator_accounts` runs once per epoch boundary as part of `ValidatorAccountsUpdate`. For validators with `stake_info`, a missing/uninitialized account is explicitly tolerated as long as nothing is owed (max-of-stakes, reward, and last proposal are all zero) [7](#0-6) . But the protocol-treasury payout branch has no such tolerance:

```
if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
    if !validator_accounts_update.stake_info.contains_key(account_id) {
        let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Protocol treasury account {} is not found",
                account_id
            ))
        })?;
``` [8](#0-7) 

`protocol_treasury_account_id` is populated (`Some`) on the shard that currently hosts the treasury account, and is looked up every epoch regardless of whether the account still exists on-chain.

The treasury account is an ordinary NEAR account from the runtime's point of view. `DeleteAccountAction` deletion is permitted for any account whose actor matches and which has zero locked (staked) balance; `action_delete_account` unconditionally removes the account and queues a balance-refund receipt to the chosen beneficiary [3](#0-2) . There is no special-case guard anywhere in `check_account_existence` / `check_actor_permissions` protecting `protocol_treasury_account` from deletion.

If the treasury account (which typically does not stake) is deleted by whoever controls its access key, the account is gone from state. At the very next epoch boundary that this shard processes, `update_validator_accounts` calls `get_account` for the treasury id, gets `None`, and returns `Err(StorageError::StorageInconsistentState(...))`.

This error is not classified as an ordinary/recoverable condition by the surrounding chain code. `apply_chunk` treats any `Error::StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue` as fatal and panics:
```
Err(e) => match e {
    Error::StorageError(err) => match &err {
        StorageError::FlatStorageBlockNotSupported(_)
        | StorageError::MissingTrieValue(..) => Err(err.into()),
        _ => panic!("{err}"),
    },
    _ => Err(e),
},
``` [5](#0-4) 

and other apply call sites panic directly on `RuntimeError::UnexpectedIntegerOverflow`/`ReceiptValidationError`, treating `StorageError` (when it does surface as `Error::StorageError`) as an unrecoverable condition as well [6](#0-5) .

Because chunk application is deterministic and every honest validator/tracking node executes the identical epoch-boundary logic against the identical state, all of them hit the same `StorageInconsistentState` and panic in lock-step — this is a transaction-triggered halt of the affected shard, not a localized node bug.

### Impact Explanation
This is a transaction-triggered halt: a single, cheap, entirely valid transaction (deleting one's own unstaked account) submitted by whoever controls the protocol treasury account's keys causes every node tracking that shard to panic at the next epoch boundary, once the panic path is reached via `apply_chunk`/`Runtime::apply` error propagation. This meets the "transaction-triggered halt" acceptance criterion directly — no forking, no malicious validator collusion, and no privileged role is required beyond holding the treasury account's private key (which is an ordinary account key, not a protocol-level permission).

### Likelihood Explanation
The likelihood is bounded by one precondition: the actor must control the private key of whichever account genesis (or any config update) designates as `protocol_treasury_account`, and that account must not currently be staking (have zero `locked` balance) so `DeleteAccountAction` is permitted. On most configured networks the treasury account is not a staking validator, so this condition is commonly satisfied. Given that, the rest of the trigger path (delete the account, wait for the next epoch boundary) requires no special timing, no race condition, and no cooperation from other parties.

### Recommendation
Make the protocol-treasury reward-payout path in `update_validator_accounts` tolerant of a missing/uninitialized account the same way the stake_info loop already is: if the account does not exist, and nothing is actually owed (or by design, silently forgo/burn the reward, or credit it once the account is recreated) rather than raising a fatal `StorageInconsistentState`. Additionally, consider explicitly disallowing deletion of the configured `protocol_treasury_account` (and similarly protected system accounts) in `check_actor_permissions`/`action_delete_account`, so the account cannot silently disappear out from under a subsystem that assumes its permanent existence.

### Proof of Concept
1. Identify/assume control of the account matching `genesis_config.protocol_treasury_account` (e.g. via its access key) on a network where that account currently has `locked == 0`.
2. Submit an ordinary `SignedTransaction` with a `DeleteAccount { beneficiary_id: <any_account> }` action signed by that account's key. This action succeeds unconditionally per `action_delete_account` (no special protection exists for the treasury id) [3](#0-2) .
3. Wait for the next epoch boundary to be processed on the shard that used to host the treasury account.
4. `update_validator_accounts` calls `get_account` for `protocol_treasury_account_id`, receives `None`, and returns `Err(StorageError::StorageInconsistentState(...))` [8](#0-7) .
5. `apply_chunk` on every node tracking that shard reaches the catch-all `panic!("{err}")` branch [5](#0-4) , crashing all such nodes deterministically and halting the shard.
