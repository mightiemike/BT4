Confirmed: `x/uexecutor` (the module that mints PRC20 tokens on inbound execution) has zero references to `LiquidityCap`/`liquidity_cap` anywhere in its code. The cap declared in `uregistry`'s `TokenConfig` is validated only for non-emptiness at config-write time [1](#0-0)  and is never read or enforced during minting.

### Title
Unbounded PRC20 minting bypasses the declared `liquidity_cap` on every inbound deposit - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uregistry/types/token_config.go`)

### Summary
`uregistry.TokenConfig` declares a `liquidity_cap` field intended to bound the total amount of a bridged token that can exist as PRC20 supply on Push Chain [2](#0-1) . However, the mint path in `x/uexecutor` (`CallPRC20Deposit` / `gasAndPayloadDepositAutoSwap`, invoked from `ExecuteInboundGasAndPayload`) never reads or checks this value before minting PRC20 tokens to a recipient on a finalized inbound [3](#0-2) . This is structurally the same defect as the reported Hifi bug: a declared ceiling on token issuance (`debtCeiling` / `liquidity_cap`) exists in one contract/module, but a separate mint-capable code path (`HToken.depositUnderlying()` / `uexecutor`'s inbound deposit) increases supply with no reference to that ceiling.

### Finding Description
`x/uregistry` stores, per (chain, token), a `LiquidityCap` string intended as "max supply cap for this token" [4](#0-3) . `ValidateBasic` on `TokenConfig` only checks that the string is non-empty; it does not parse it as a bound that's compared against anything at write time or read time [1](#0-0) .

The actual minting flow is driven by `x/uexecutor`. When 2/3+ Universal Validators finalize an inbound, `ExecuteInboundGasAndPayload` resolves the token's `NativeRepresentation.ContractAddress` (the PRC20 contract) and calls `gasAndPayloadDepositAutoSwap`, which ultimately drives `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` derived EVM calls to mint PRC20 to the recipient [5](#0-4) ; these derived calls are documented as module-originated mints with no cap check described anywhere in the mint helpers [6](#0-5) . A full-text search of `x/uexecutor` for any reference to the liquidity cap returns no results, confirming the value is never consulted on the mint path.

Because inbound amounts are attacker-influenced (a user can bridge funds from any registered external chain, and the observed `Amount` on the source-chain event directly becomes the minted PRC20 amount once honestly voted by UVs), an unprivileged user can, over repeated ordinary bridge deposits, mint PRC20 total supply for a token far past the `liquidity_cap` recorded in `uregistry`, with no on-chain enforcement stopping it.

### Impact Explanation
This corrupts PRC20 accounting invariants relied on by the rest of the protocol (auto-swap routing, quoting, and any risk/collateral assumptions downstream that treat `liquidity_cap` as authoritative). If any other module or off-chain risk system (e.g., swap routers, bridging limits, insurance/backstop sizing) assumes PRC20 supply is bounded by the registered cap, that assumption is silently false, enabling over-minted synthetic tokens to be swapped/drained against under-collateralized reserves. This maps to the "corruption of PRC20 ... accounting" and "unauthorized mint" impact categories in scope.

### Likelihood Explanation
High reachability: the mint path is exercised by every ordinary bridging deposit, requires no privileged action, and simply accumulating deposits over time (or a single large one) exceeds any declared cap since the cap is never read. The only friction is the normal honest-UV finalization threshold, which is explicitly assumed honest per the scope.

### Recommendation
Enforce `TokenConfig.LiquidityCap` in the mint path: before executing `CallPRC20Deposit`/`gasAndPayloadDepositAutoSwap` in `x/uexecutor`, query the token's current PRC20 total supply (via `totalSupply()` on the PRC20 contract or an accounting counter kept in `uexecutor`/`uregistry`), and reject/queue-for-refund any inbound whose execution would push total minted supply above `LiquidityCap`. Parse `LiquidityCap` as a `big.Int` at config-write time so malformed values are rejected early, matching the check pattern shown in the Hifi report's recommendation for `HToken.depositUnderlying()`.

### Proof of Concept
1. Admin registers a token in `uregistry` with `LiquidityCap = "1000000000000000000"` (1 token, 18 decimals) via `MsgAddTokenConfig`.
2. An unprivileged user bridges 1,000 tokens' worth of value from the registered external chain in a single (or repeated) inbound transfer(s); the source-chain gateway event reports `Amount = 1000000000000000000000`.
3. Universal Validators (honest, per scope) observe and vote `MsgVoteInbound` for this event; 2/3 threshold is reached normally.
4. `x/uexecutor.ExecuteInboundGasAndPayload` -> `gasAndPayloadDepositAutoSwap` -> `CallPRC20Deposit` mints the full `1000000000000000000000` PRC20 amount to the recipient/UEA, 1000x over the configured `LiquidityCap`, with no error or rejection anywhere in the call path [5](#0-4) .
5. Query `uregistry`'s `TokenConfig` for the token: `LiquidityCap` still shows `1000000000000000000`, while the PRC20 contract's `totalSupply()` shows `1000000000000000000000`, demonstrating the cap was never enforced.
