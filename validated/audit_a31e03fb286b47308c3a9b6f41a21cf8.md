**Analysis basis:** `shrink_collect` computes `alive_total_bytes` and `tombstones_total_bytes` by summing `stored_size()` directly over the same `alive_accounts` and `tombstones_to_carry_forward` collections that are later passed unchanged to `store_accounts_for_shrink` and `store_tombstones` in `shrink_storage` [1](#0-0) . The write path in `shrink_storage` reuses `shrink_collect.alive_accounts.alive_accounts()` and `shrink_collect.tombstones_to_carry_forward` verbatim to build the storables that are actually rewritten [2](#0-1) , so the byte totals and the bytes actually written are derived from the identical account lists — there is no code path where the counted size can diverge from the rewritten content.

The `can_purge_zero_lamport_single_ref_after_shrink(slot) == false` scenario described (zeroing accounts in a slot newer than `latest_full_snapshot_slot`) is exactly the routing logic in `shrink_collect`/`load_accounts_index_for_shrink`, which pushes such accounts into `tombstones_to_carry_forward` rather than dropping them [3](#0-2) [4](#0-3) . This exact scenario is already covered by existing unit tests that assert `tombstones_total_bytes`/`alive_total_bytes` equal the sum of serialized sizes of the actually-carried-forward/alive accounts, matching the PoC proposed in the question — and these tests pass, confirming the invariant holds:
- `test_shrink_collect_carries_forward_existing_tombstones` [5](#0-4) 
- `test_shrink_collect_simple` [6](#0-5) 
- `test_shrink_converts_zero_lamport_single_ref_account_to_tombstone` [7](#0-6) 

No reachable path allows an unprivileged attacker (who can only create/zero/rewrite their own accounts) to cause the computed byte totals to disagree with what's rewritten, since both are computed from the same in-memory account references with no intervening mutation.
