### Title
Global resource-weight ratio used in `UnDelegateResource` can be manipulated in the same block to corrupt bandwidth/energy usage accounting - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
Like the Reserve `RToken` bug where a globally-tracked, freely inflatable counter (`totalSupply`) is fed directly into a rate-limiting formula (`RedemptionBattery.currentCharge`) that is then exploited by re-ordering transactions within a block, java-tron's `UnDelegateResource` flow computes an "allowed usage transfer" cap directly from the mutable, chain-wide `TotalEnergyWeight`/`TotalNetWeight` counters. These counters can be freely and instantly changed by any unprivileged account issuing `FreezeBalanceV2Contract`/`UnfreezeBalanceV2Contract` transactions in the same block, and then consumed by `UnDelegateResourceContract` before the state is recomputed, letting a searcher/attacker distort the resource-accounting invariant between a delegator and delegatee.

### Finding Description
`UnDelegateResourceProcessor.execute()` (and the equivalent `UnDelegateResourceActuator.execute()`) computes how much previously-consumed bandwidth/energy "usage" is clawed back from the receiver to the owner when a delegation is revoked. The cap on this transfer, `unDelegateMaxUsage`, is derived from the **global** weight aggregates: [1](#0-0) 

```
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * dynamicStore.getTotalEnergyCurrentLimit() / repo.getTotalEnergyWeight());
transferUsage = (long) (receiverCapsule.getEnergyUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForEnergy()));
transferUsage = min(unDelegateMaxUsage, transferUsage, VMConfig.disableJavaLangMath());
```

This is structurally identical to the Reserve bug's `amtPerHour = supply * battery.scalingRedemptionRate / FIX_ONE_256` — a per-transaction cap computed from a shared, network-wide accumulator (`TotalEnergyWeight`/`TotalNetWeight` here, `totalSupply` there).

`TotalEnergyWeight`/`TotalNetWeight` are ordinary mutable dynamic properties that any account can move up or down, with no cooldown or reentrancy protection, via unprivileged, anonymously-broadcastable transactions:
- `FreezeBalanceV2Processor.execute()` increases the weight: [2](#0-1) 
- `UnfreezeBalanceV2Processor.updateTotalResourceWeight()` decreases the weight: [3](#0-2) 
- `CancelAllUnfreezeV2Processor.updateFrozenInfoAndTotalResourceWeight()` also mutates it: [4](#0-3) 

Because block producers (or any party who can influence transaction ordering within a block, e.g. via fee/priority or simply being first to broadcast) can sequence a large `UnfreezeBalanceV2Contract`/`CancelAllUnfreezeV2Contract` burst immediately before their own `UnDelegateResourceContract`, they can transiently shrink `TotalEnergyWeight` (denominator), inflating `unDelegateMaxUsage`, and thereby raise the bound on how much "usage" can be pulled back from the receiver's account into the owner's — mirroring exactly how the Reserve attacker inflated `totalSupply` right before the vulnerable `redeem` call to lift the `RedemptionBattery` cap.

This same divisor is also used elsewhere for real resource-limit computation (e.g., `EnergyProcessor.calculateGlobalEnergyLimit`), so any block-local skew in `TotalEnergyWeight`/`TotalNetWeight` propagates into how much energy/bandwidth every account is entitled to at that instant: [5](#0-4) 

### Impact Explanation
Bandwidth/energy is a scarce resource with direct monetary value (it is acquired by freezing/staking TRX or paying TRX-denominated fees otherwise). If the accounting split of "used" resource between a resource-delegation owner and receiver can be skewed by transiently manipulating the network-wide weight divisor, an attacker can unfairly reclaim usage credit (effectively shifting who is treated as having consumed bandwidth/energy) at the expense of the counterparty's future usage window, corrupting the resource accounting invariant network-wide. This is analogous to how the Reserve exploit converted an inflated global counter into an unfairly large redemption allowance, causing a net transfer from the honest counterparty.

### Likelihood Explanation
The precondition is a delegator/receiver relationship with active usage plus the ability to order a `FreezeBalanceV2`/`UnfreezeBalanceV2`/`CancelAllUnfreezeV2` burst ahead of an `UnDelegateResourceContract` within the same block — all reachable through ordinary, anonymous, unprivileged broadcast transactions requiring no special role. It requires enough capital to meaningfully move `TotalEnergyWeight`/`TotalNetWeight` in a single block and favorable transaction ordering (self-controlled or MEV-assisted), which is a non-trivial but realistic bar, similar in spirit ("particular sequence of events required") to the original Medium-severity Reserve finding.

### Recommendation
Avoid using a live, freely-mutable global aggregate (`TotalEnergyWeight`/`TotalNetWeight`) as the divisor for a per-transaction cap computed and applied within the same block as other transactions that mutate that aggregate. Snapshot the divisor at a fixed cadence (e.g., per-cycle, as is already done for `TotalEnergyCurrentLimit`'s adaptive adjustment) rather than reading it live in `UnDelegateResourceProcessor`, or bound `unDelegateMaxUsage` using per-relationship (owner/receiver) state only rather than mixing in a manipulable global denominator.

### Proof of Concept
1. Alice delegates ENERGY to Bob via `DelegateResourceContract`; Bob consumes a large share of it (`receiverCapsule.getEnergyUsage()` grows).
2. Attacker (Alice, or a colluding block producer) observes Alice's pending `UnDelegateResourceContract` in the mempool.
3. Attacker inserts/organizes several `UnfreezeBalanceV2Contract` (or `CancelAllUnfreezeV2Contract`) transactions earlier in the same block from large-frozen-balance accounts, shrinking `dynamicStore.getTotalEnergyWeight()` via `UnfreezeBalanceV2Processor.updateTotalResourceWeight` [3](#0-2) .
4. Alice's `UnDelegateResourceContract` then executes with an inflated `unDelegateMaxUsage` (per the formula in `UnDelegateResourceProcessor.execute`), allowing `transferUsage` to reach values that would not be possible under the pre-manipulation `TotalEnergyWeight`, shifting more "used energy" credit from Bob back to Alice than the honest network-wide accounting would allow [1](#0-0) .

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
