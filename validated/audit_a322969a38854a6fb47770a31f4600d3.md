### Title
DelegateAction / meta-transaction signatures omit chain-specific replay protection (chain_id / genesis hash) - (File: core/primitives/src/action/delegate.rs, core/primitives/src/signable_message.rs)

### Summary
NEAR's meta-transaction scheme (NEP-366/NEP-611) signs a `DelegateAction`/`DelegateActionV2` payload with `SignableMessage`, whose Borsh-serialized bytes consist only of a `MessageDiscriminant` (a fixed NEP-number constant) and the `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). No chain-specific value (`chain_id`, genesis hash, or similar) is included in the hash that is signed. This mirrors the reported TAP bug class where `messageHash` omitted `chainId`, enabling a signed authorization to be replayed on a different chain that shares the same signing key and account/state layout.

### Finding Description
The signature covering a meta-transaction is built here: [1](#0-0) 

and the discriminant is a static NEP-number constant, not tied to any chain identity: [2](#0-1) 

The `DelegateAction` struct that gets hashed contains no chain-binding field: [3](#0-2) 

and `verify`/`sign` simply hash this struct plus the discriminant, with nothing chain-specific mixed in: [4](#0-3) 

By contrast, nearcore's own EVM-compatibility component (the Wallet Contract, which relays Ethereum-style `Transaction2930` payloads) explicitly checks `chain_id` in the signed payload and treats a mismatch as a bannable relayer offense: [5](#0-4) 

This shows nearcore engineers recognize chain-id binding as a necessary anti-replay control for signed, relayer-submitted payloads in one code path, but the native `DelegateAction`/meta-transaction signing scheme (NEP-366/611) lacks the analogous protection. Ordinary NEAR transactions get some chain-locality indirectly through `block_hash` (which must reference a recent block on the chain the transaction is submitted to) as part of transaction validity checks, but `DelegateAction` replaces that mechanism with `max_block_height`, a value relative to the sender's own block-height counter, not tied to a specific chain's genesis/identity. Because nearcore is deployed as many independently operated chains (mainnet, testnet, and numerous other permissionless or private networks built from the same codebase) that can share account IDs, public keys, and even nonce state (e.g., freshly created accounts, testnets forked from mainnet state, or shared development/staging networks), a `SignedDelegateAction` produced for use as a meta-transaction on one network is not cryptographically bound to that network and could be replayed verbatim on another network where the same `sender_id`/`public_key`/`nonce` state coincides.

### Impact Explanation
If a `SignedDelegateAction` intended for network A is replayed as-is on network B (same account id, key, and current nonce state), the relayer on network B can execute the exact same delegated actions (e.g., `AddKeyAction` granting a full-access key, `TransferAction`, or arbitrary function calls) against the victim's account on B without a fresh authorization, since access-key/nonce validation (`validate_delegate_action_key`) only checks the internal nonce and never a chain identity: [6](#0-5) 
This constitutes unauthorized cross-network state mutation/value movement (e.g., an attacker-controlled relayer replaying a "add full access key" or "transfer" delegate action authorized for one network on another network where it was never intended to be valid).

### Likelihood Explanation
Exploitation requires the specific precondition that the same account id/public key/nonce state exists identically across two networks derived from nearcore (a realistic but non-default scenario, e.g., testnets seeded from mainnet snapshots, private/enterprise nearcore-based chains, or shared development environments using identical genesis account sets). It is not exploitable against two independently-initialized production networks with divergent account/nonce histories out of the box, which limits, but does not eliminate, real-world likelihood.

### Recommendation
Bind the signed message to the specific chain by mixing a chain identity (e.g., the genesis `chain_id` string from `GenesisConfig`, as already used to answer the `chain_id` host function) into the `SignableMessage`/`DelegateAction` (and `DelegateActionV2`) payload before hashing, analogous to how the Wallet Contract validates `chain_id` in relayed EVM transactions. This should be introduced as a protocol-versioned change (new discriminant / new delegate-action version) to avoid breaking existing signing flows.

### Proof of Concept
1. Operate two nearcore-based networks, A and B, initialized so that account `alice.near` has the same `public_key` and identical current `AccessKey.nonce` on both (e.g., B is a fork/clone of A's genesis state, or a shared account seed is used across a mainnet/testnet pair).
2. Alice signs a `DelegateAction` (e.g., `AddKeyAction` granting a full-access key to a relayer-controlled key) intended only for network A, using `SignedDelegateAction::sign` per `core/primitives/src/action/delegate.rs` lines 83-96.
3. A relayer submits the identical `SignedDelegateAction` bytes inside a `SignedTransaction::from_actions(..., Action::Delegate(...))` to network B.
4. `validate_delegate_action_key` in `runtime/runtime/src/actions.rs` (lines 579-605) accepts it because the nonce and access key match on B too, and `verify()` succeeds because the hash never encoded which chain it was meant for — the delegated action (e.g., adding the attacker's full-access key) executes on network B without Alice's consent for that network.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

async fn test_relayer_wrong_chain_id() -> anyhow::Result<()> {

        gas_limit: 0.into(),
        to: Some(Address::new(wallet_address)),

        .concat(),
        chain_id: CHAIN_ID + 1,
        access_list: Vec::new(),

    let signed_transaction = crypto::sign_transaction(transaction, &wallet_sk);
