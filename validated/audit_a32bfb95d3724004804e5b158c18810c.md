### Title
Flat SLOAD energy cost ignores cache-miss DB read cost, enabling I/O-amplification DoS via ordinary contract calls - (File: `Storage.java`)

### Summary
`Storage.getValue(DataWord key)` performs a `store.get(compose(...))` RocksDB/LevelDB lookup whenever the accessed slot is not already in `rowCache`, and `EnergyCost.getSloadCost()` charges a fixed 50 energy for every `SLOAD` regardless of whether the read is served from the in-memory `rowCache` or requires a random-access disk read. An attacker can deploy and call a contract that performs many `SLOAD`s on distinct, never-written (or newly-created contract) storage slots, forcing one DB read per opcode at the same energy price as a cache hit, which lets energy-cheap bytecode drive disproportionate disk I/O.

### Finding Description
`Storage.getValue` checks `rowCache` first and only falls back to `store.get(compose(key.getData(), addrHash))` on a miss, caching the result only after a successful read: [1](#0-0) . Every `SLOAD` op is charged the same constant `SLOAD = 50` energy via `EnergyCost.getSloadCost` irrespective of whether the underlying call was a cache hit or triggered a real database read: [2](#0-1) . There is no cold/warm access-list style differential pricing (comparable to Ethereum's EIP-2929) anywhere in `EnergyCost`, `OperationRegistry`, or `Storage`/`RepositoryImpl`. The call path is fully attacker-reachable through an ordinary `TriggerSmartContract`: `VMActuator.call()` builds a `Program` bound to `RepositoryImpl`, which routes `getStorageValue` -> `getStorageInternal` -> `Storage.getValue` for every `SLOAD` [3](#0-2) . None of the existing protections (`TransactionCapsule.validateSignature`, actuator `validate()`, fork gates, bandwidth/energy accounting) address per-opcode I/O cost — they only gate signature validity, contract structure, and aggregate energy/bandwidth consumption, none of which reflect real disk-access cost per distinct storage slot touched.

### Impact Explanation
This matches the "DoS via the TRON protocol implementation" bounty class: because the energy price of `SLOAD` is a flat constant unrelated to whether the read is a cache hit or a genuine disk-backed lookup, an attacker paying for `N * 50` energy (a small, predictable, purely bandwidth/energy-cheap cost) can force `N` random-access RocksDB/LevelDB reads within a single transaction/block, at up to the block's energy limit. Since block validation is sequential and every full node re-executing the block must perform the same I/O, this can increase per-block processing latency across all full nodes disproportionately to the metered energy cost, creating a processing-latency/stall vector bounded only by the (large, adaptive) total block energy limit rather than by real I/O cost.

### Likelihood Explanation
The attacker only needs to be an ordinary funded account able to deploy a contract and broadcast a `TriggerSmartContract`, both unprivileged and already permitted operations. The only "cost" is standard energy fees (feeLimit paid in TRX or from frozen energy), which are cheap relative to the disk I/O forced, especially with distinct pseudo-random keys guaranteeing no shared cache locality within `rowCache`. This is repeatable every block, limited only by the network's total/per-tx energy limit (`getTotalEnergyLimit`, `TotalEnergyCurrentLimit`), which is large and adaptive rather than tied to actual I/O capacity. The main mitigating factor is that block energy limits do impose an overall ceiling and node operators can tune RocksDB/LevelDB caching, so the severity is proportional to the accessible energy limit rather than unbounded.

### Recommendation
Introduce access-list-style differential energy pricing for `SLOAD`/storage access, analogous to EIP-2929 cold/warm access lists: charge a higher "cold" cost the first time a given `(address, key)` pair is touched within a transaction (i.e., when `Storage.getValue` must fall back to `store.get`), and a lower "warm" cost for subsequent `rowCache` hits on the same key, so the fixed 50 energy cost cannot be used to buy disproportionately many DB reads.

  public DataWord getValue(DataWord key) {
    if (rowCache.containsKey(key)) {
      return new DataWord(rowCache.get(key).getValue());
    } else {
      StorageRowCapsule row = store.get(compose(key.getData(), addrHash));
      if (row == null || row.getInstance() == null) {
        return null;
      }
      rowCache.put(key, row);
      return new DataWord(row.getValue());
    }
  }
