### Title
Gateway-only enforcement of `allow_client_side_proving` lets a user bypass the client-side-proving restriction via mempool re-propagation / direct execution path - (File: crates/apollo_gateway/src/stateless_transaction_validator.rs)

### Summary
The restriction that disables client-side proving (`config.allow_client_side_proving == false`) is enforced only in the peripheral `StatelessTransactionValidator::validate` function in the gateway, exactly analogous to the reported bug where a mint-whitelist restriction lived only in the peripheral `ArrakisV2Router` and not in the core `ArrakisV2` vault. No equivalent check exists in the core transaction-processing path (`blockifier`, `StatefulValidator`, or the Starknet OS Cairo program), which is the actual authoritative state-transition logic executed/re-executed by every node.

### Finding Description
`StatelessTransactionValidator::validate` runs `validate_client_side_proving_allowed` and `validate_proof_facts_and_proof_consistency` only for `RpcInvokeTransaction`, and only when the transaction is submitted through the gateway's stateless validation entry point: [1](#0-0) 

The relevant check: [2](#0-1) 

Notice the contrast with other fields in the same file (`account_deployment_data`, `paymaster_data`, DA modes), each of which is explicitly documented as being *also* enforced deeper, in the Starknet OS itself — the gateway check exists purely as an early UX rejection to avoid a wasted OS failure: [3](#0-2) [4](#0-3) [5](#0-4) 

No such comment or redundant enforcement exists for `validate_client_side_proving_allowed` / `validate_proof_facts_and_proof_consistency`. I was unable to locate any check on `allow_client_side_proving` (or a corresponding proof-facts/proof consistency invariant) inside `blockifier`'s `StatefulValidator` (`crates/blockifier/src/blockifier/stateful_validator.rs`), the transaction execution path (`crates/blockifier/src/transaction/account_transaction.rs`), or the Starknet OS Cairo re-execution logic (`crates/apollo_starknet_os_program/.../execution/transaction_impls.cairo`), even though `proof_facts` is consumed extensively in all of those layers. `allow_client_side_proving` itself is referenced only in the gateway config and its tests: [6](#0-5) 

Because the stateful/blockifier validation path and OS re-execution never re-check `allow_client_side_proving`, once a transaction with proof data reaches the mempool/blockifier/consensus pipeline by any avenue other than `StatelessTransactionValidator::validate` (e.g., a peer node relaying it over the mempool p2p protocol whose local `add_tx` flow does not re-run the identical stateless gate before block inclusion, or any code path that constructs an `ExecutableTransaction`/`AccountTransaction` directly for `run_validate_entry_point`/`StatefulValidator` without going through `StatelessTransactionValidator`), the "client-side proving disabled" policy is silently bypassed — the transaction validates and executes normally, exactly as an ArrakisV2 mint bypasses the router's whitelist by calling the vault directly.

### Impact Explanation
On chains/sequencers configured with `allow_client_side_proving = false` (a deliberate operator policy — likely disabled because client-side proof verification carries different trust/resource assumptions than server-side proving), an unprivileged transaction sender who reaches blockifier/OS execution without passing through the gateway's stateless check can submit an invoke transaction carrying `proof`/`proof_facts` data that should have been rejected. Since the actual runtime semantics of proof_facts are consumed deep in the OS (`transaction_impls.cairo`, `execution_constraints.cairo`) as part of execution, this is a policy-enforcement bypass of a chain-level trust/verification restriction — analogous in class to the reported "restriction lives in the peripheral component, not the core" bug — potentially enabling execution effects the operator explicitly intended to disallow. This does not immediately prove state-root divergence (all conforming honest sequencer instances share the same gateway code), but it does mean the guarantee "no client-side-proven transaction is ever admitted/executed" is not actually enforced by the state-transition function itself, only by an optional front-door filter.

### Likelihood Explanation
Medium: exploitation requires a submission path that reaches `blockifier`'s `StatefulValidator`/execution or OS re-execution without transiting `StatelessTransactionValidator::validate` (e.g., relay/propagation logic, or any internal construction of `AccountTransaction`/`ExecutableTransaction` for validation as seen in `crates/apollo_gateway/src/stateful_transaction_validator.rs`). I could not fully confirm from the indexed code whether every code path that ultimately reaches `StatefulValidator::create`/`perform_validations` is guaranteed to have first passed `StatelessTransactionValidator::validate` in this codebase version — this would need to be verified in the full `apollo_gateway::gateway` / mempool p2p ingestion code, which was only partially covered by the search index.

### Recommendation
Move the `allow_client_side_proving` policy check (and the `proof_facts`/`proof` consistency invariant) out of the gateway-only `StatelessTransactionValidator` and into the core state-transition path — either as an explicit check in `blockifier`'s `AccountTransaction`/`StatefulValidator::perform_validations`, or preferably enforced natively by the Starknet OS Cairo program during transaction execution — so that the restriction cannot be bypassed by any transaction that reaches execution without transiting the gateway's stateless validator, mirroring how `account_deployment_data`, `paymaster_data`, and the DA-mode fields are already double-enforced (gateway pre-check + authoritative OS enforcement).

### Proof of Concept
Not independently reproducible from static analysis alone; the report's shape maps directly to the code structure:
1. Gateway path: `StatelessTransactionValidator::validate` rejects an `RpcInvokeTransaction::V3` with non-empty `proof`/`proof_facts` when `config.allow_client_side_proving == false`. [2](#0-1) 
2. Core path: `StatefulTransactionValidator::run_validate_entry_point` builds an `AccountTransaction` and hands it to `StatefulValidator::create(...).validate(account_tx)` with no re-check of `allow_client_side_proving` or proof-facts consistency. [7](#0-6) 
3. Any invocation of this core path that is not preceded by step 1 (e.g., a differently-wired ingestion route, or a future/alternate entry point into the mempool/blockifier) admits and executes a client-side-proven transaction despite the operator's policy — the sequencer analog of calling `ArrakisV2.mint()` directly instead of `ArrakisV2Router._addLiquidity()`.

    fn validate_client_side_proving_allowed(
        &self,
        tx: &RpcInvokeTransaction,
    ) -> StatelessTransactionValidatorResult<()> {
        if self.config.allow_client_side_proving {
            return Ok(());
        }

        // Reject V3 transactions with proofs when client-side proving is disabled.
        let RpcInvokeTransaction::V3(tx) = tx;
        let has_proof_data = !tx.proof_facts.is_empty() || !tx.proof.is_empty();
        if has_proof_data {
            return Err(StatelessTransactionValidatorError::ClientSideProvingNotAllowed);
        }

        Ok(())
    }
