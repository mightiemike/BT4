### Title
Session token verification result discarded in `tokenExchange`, allowing shop/tenant confusion and secret leakage to an attacker-chosen domain - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
`tokenExchange()` decodes/verifies the caller's session token but throws away the verified payload instead of using its cryptographically-bound `dest` (shop) claim. The `shop` value actually used to build the outbound OAuth token-exchange request — and to construct the resulting `Session` object/ID — is instead taken from a separate, caller-supplied `shop` parameter that is never cross-checked against the verified token. This mirrors the reported bug class: a security-relevant return value (`receiveToken`'s actual transferred amount / here, `decodeSessionToken`'s verified `dest`) is computed but ignored, and a different, less-trusted value is used downstream instead.

### Finding Description
`decodeSessionToken` cryptographically verifies the JWT session token's signature (HS256 with `apiSecretKey`) and returns a `JwtPayload` containing the trustworthy `dest` field (the shop the token was actually issued for). [1](#0-0) 

In `tokenExchange()`, this verified payload is discarded:
```
await decodeSessionToken(config)(sessionToken);
...
const cleanShop = sanitizeShop(config)(shop, true)!;
```
`shop` here is the function's own parameter, not `payload.dest`. [2](#0-1) 

The official usage example in the library's own docs sources `shop` from the request query string, completely independent of the session token:
```
const shop = shopify.utils.sanitizeShop(req.query.shop, true);
...
await shopify.auth.tokenExchange({ sessionToken, shop, ... });
``` [3](#0-2) 

`sanitizeShop` only validates that the string matches a `*.myshopify.com`/`*.shopify.com`/`*.myshopify.io`/`*.shop.dev` (or configured transformation) domain pattern — it does not verify the domain corresponds to the shop that issued the session token. [4](#0-3) 

The resulting `cleanShop` (attacker-controllable, as long as it matches the domain regex) is used both to build the outbound request URL, which is sent together with `client_id`/`client_secret` in the POST body, and to create the returned `Session` (`shop: cleanShop`), whose `id` is later derived as `offline_{shop}` and used as the session-storage key. [5](#0-4) [6](#0-5) 

In the officially-shipped middleware/strategy integrations (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`), `shop` is instead always derived from the verified session-token's `dest` claim before calling `tokenExchange`, so the built-in framework wrappers are not directly exploitable this way. [7](#0-6) [8](#0-7) 

However, `shopify.auth.tokenExchange` is a public, directly-callable API, and the library's own reference documentation instructs developers to pass an independently-sourced `shop` (from `req.query.shop`) rather than the verified token's `dest`. Any app built by following this documented pattern inherits the vulnerability: a merchant/customer holding *any* valid session token (trivially obtainable for their own installed shop) can supply an arbitrary `shop` domain matching the accepted suffix list, causing the app server to send the shared `client_secret` and the caller's session token to a domain of the attacker's choosing, and/or to create/overwrite a `Session` keyed by an arbitrary shop ID in the app's session storage.

### Impact Explanation
- Cross-tenant session storage confusion: an attacker can cause the library to build and store a `Session` object keyed to a shop domain they choose, not the shop that actually issued the session token, because `dest` is never compared to `shop`.
- Secret/token disclosure risk: because `shop` is not bound to the verified `dest`, and `sanitizeShop` only checks a domain suffix (not that it is *the caller's own* shop), the OAuth token-exchange POST request — containing `client_id`, `client_secret`, and the raw `subject_token` (the user's session token) — can be directed to any hostname ending in an accepted suffix (e.g., an attacker-registered `*.myshopify.io` in non-production configs, or any domain when `domainTransformations` is configured), leaking the app's `client_secret` and the victim's session token to a third party.
- This is high severity because `client_secret` is a long-lived, shared app credential; leaking it undermines the app's entire OAuth trust model.

### Likelihood Explanation
Likelihood is high for any app built by following the SDK's own documented pattern (`shop` from query params), since this is the exact usage shown in `tokenExchange.md`. It requires only a single authenticated request from any merchant/customer with a valid session token for some shop, with an attacker-supplied `shop` parameter — no special privileges needed. Apps using the higher-level `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` packages are not affected because those wrappers always pass the verified `dest` as `shop`, which somewhat limits the practical blast radius to apps calling `shopify.auth.tokenExchange` directly per the documented example.

### Recommendation
In `tokenExchange()` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), capture and use the verified payload's `dest` field instead of discarding it:
```ts
const payload = await decodeSessionToken(config)(sessionToken);
const verifiedShop = new URL(payload.dest).hostname;
if (sanitizeShop(config)(shop, true) !== sanitizeShop(config)(verifiedShop, true)) {
  throw new ShopifyErrors.InvalidJwtError('shop parameter does not match session token');
}
```
Additionally, update the reference documentation (`tokenExchange.md`) to source `shop` from the verified session token's `dest` claim rather than `req.query.shop`, consistent with how `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` already do it.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and obtains a valid, signed session token issued to them (via normal App Bridge flow — no special access needed).
2. Attacker calls the app's endpoint that wraps `shopify.auth.tokenExchange` (built per the documented pattern), supplying:
   - `sessionToken`: their own valid token (`dest = attacker.myshopify.com`)
   - `shop` (query param): `victim.myshopify.com` (or any domain matching the accepted suffix regex)
3. `tokenExchange()` verifies the JWT signature succeeds (it's a legitimately-issued token, just not for `victim.myshopify.com`), discards the payload, and proceeds to POST `client_id`, `client_secret`, and `subject_token` to `https://victim.myshopify.com/admin/oauth/access_token`.
4. If the resulting response is accepted (e.g., in a test/mock environment or where the receiving `shop` is under attacker control), a `Session` object with `shop: "victim.myshopify.com"` is created/stored — even though it was never verified that the caller actually represents that shop, and the app's `client_secret` has been transmitted to a domain not verified to be the legitimate target of this specific session token.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };

export function sanitizeShop(config: ConfigInterface) {
  return (shop: string, throwOnInvalid = false): string | null => {
    let shopUrl = shop;
    const domainsRegex = [
      'myshopify\\.com',
      'shopify\\.com',
      'myshopify\\.io',
      'shop\\.dev',
    ];

    // Add domains from transformations (both source and target)
    if (config.domainTransformations) {
      domainsRegex.push(...getTransformationDomains(config));
    }

    const shopUrlRegex = new RegExp(
      `^[a-zA-Z0-9][a-zA-Z0-9-_]*\\.(${domainsRegex.join('|')})[/]*$`,
    );

    const shopAdminRegex = new RegExp(
      `^admin\\.(${domainsRegex.join('|')})/store/([a-zA-Z0-9][a-zA-Z0-9-_]*)$`,
    );

    const isShopAdminUrl = shopAdminRegex.test(shopUrl);
    if (isShopAdminUrl) {
      shopUrl = shopAdminUrlToLegacyUrl(shopUrl) || '';
    }

    const sanitizedShop = shopUrlRegex.test(shopUrl) ? shopUrl : null;
    if (!sanitizedShop && throwOnInvalid) {
      throw new InvalidShopError('Received invalid shop argument');
    }

    if (sanitizedShop && config.domainTransformations) {
      return applyDomainTransformations(sanitizedShop, config);
    }

    return sanitizedShop;
  };
