`ensure_match_transaction_info` never checks the state-checkpoint (SMT) root, so chunk-executor and backup replay-verification cannot detect state-root divergence - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness gate used by the chunk-executor's "verify execution" fast-sync path and by `db-tool`'s `replay_on_archive`/`replay-verify` tooling to confirm that locally re-executed transactions reproduce the accumulator-proven historical ledger. The function checks status, gas, write-set hash (`state_change_hash`) and event root hash, but explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually commit to the resulting global state (Sparse-Merkle/Jellyfish root). This gap is called out by the code itself as a known, currently-live gap, not merely a hypothetical.

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` compares a freshly produced `TransactionOutput` against the trusted `TransactionInfo` taken from the accumulator-anchored proof/backup manifest: [1](#0-0) 

It validates `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash, but the trailing comment explicitly documents that it does **not** validate `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`: [2](#0-1) 

This function is used in two state-integrity-critical, unprivileged-verification paths:

1. `ChunkExecutorInner::verify_execution`, invoked from `remove_and_replay_epoch` whenever `verify_execution_mode.should_verify()` is set (the "execute-and-verify" fast-sync / replay path). This path calls `DoGetExecutionOutput::by_transaction_execution` directly and checks only `ensure_match_transaction_info` per transaction — it never calls `DoStateCheckpoint`/`ApplyExecutionOutput`, i.e., it never independently recomputes the SMT/JMT root and compares it to the trusted `state_checkpoint_hash`: [3](#0-2) [4](#0-3) 

2. `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, the tool operators run to confirm that replaying an entire archived chain history against the VM reproduces the recorded, ledger-info-proven results: [5](#0-4) 

Both call sites rely exclusively on `ensure_match_transaction_info`, so a state-root divergence between the locally recomputed ledger state and the historically committed/proven state (e.g. caused by a JMT/Sparse-Merkle update bug, hot-state or the newer "trading-native" position-state logic, a storage schema bug, or any silent non-determinism in `DoStateCheckpoint`) will be silently accepted as "verified" by both the fast-sync execute-and-verify path and the offline replay-verify tool, as long as the write set bytes and events happen to match.

This is distinct from — and independently provable beyond — the PRBMath-style rounding bug: it is a self-acknowledged, structural gap in Aptos's own proof/commitment cross-check, not a copy of the external report.

### Impact Explanation
`state_checkpoint_hash` is the field that binds a `TransactionInfo` (and thus the accumulator/ledger-info) to the actual Merkle/Jellyfish state root. The entire purpose of "verify execution" (fast sync) and `replay-verify` (backup/archive integrity tooling) is to give node operators and auditors a *proof-backed* guarantee that re-executing history reproduces the authenticated ledger state. Because these tools never re-derive and compare the state root, a genuine state-computation bug (hard-fork-class divergence) between the historically accepted chain and current node software would go undetected by exactly the mechanisms designed to catch such divergences. This falls squarely under "hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated ... proof-bearing responses must stay bound to the right ... root" from the state-integrity gate: the verification tooling can report success while the "authenticated" root is not actually re-verified, giving false assurance of ledger integrity to anyone relying on `replay-verify`/fast-sync execution-verification as a safety net (e.g., before promoting a new binary, or vetting a downloaded backup/archive).

### Likelihood Explanation
The gap is not theoretical: it is explicitly documented in the code as a currently-existing hole ("this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's replay_on_archive) can report a successful replay even when the authenticated position state root diverges from local execution"), and both consuming call sites (`chunk_executor::verify_execution` and `replay_on_archive::execute_and_verify`) are confirmed to only call this comparator without any separate state-root recomputation/verification step. The comment scopes its immediate urgency to "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS," but the same comparator has *always* omitted the plain `state_checkpoint_hash` (main state SMT root) and `hot_state_checkpoint_hash` checks, which are independent of that new feature flag and are already exercised on mainnet history.

### Recommendation
Extend `ensure_match_transaction_info` (or its callers) to independently recompute the state-checkpoint hash(es) at checkpoint boundaries — i.e., invoke the same `DoStateCheckpoint` logic used in the commit path — and assert equality with `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` where applicable) before returning success, in both `ChunkExecutorInner::verify_execution` and `replay_on_archive::Verifier::execute_and_verify`.

### Proof of Concept
Not applicable as a runtime exploit — this is a verification-logic gap. It can be demonstrated by unit test: construct a `TransactionOutput` whose write set matches `txn_info.state_change_hash()` and whose events match `txn_info.event_root_hash()`, but whose write-set contents would resolve to a different Sparse-Merkle root than the trusted `txn_info.state_checkpoint_hash()` (e.g. crafting a scenario where `DoStateCheckpoint::run` on the two txn outputs would yield different SMT roots while `CryptoHash::hash(write_set)` collides is not required — simply feed differing pre-state such that the recomputed SMT root differs). `ensure_match_transaction_info` will return `Ok(())` in both `chunk_executor::verify_execution` and `replay_on_archive::execute_and_verify`, confirming the state-root check is never exercised.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",

            version,
            event_root_hash,

            expected_events,

        // local execution. Validate the checkpoint hashes here before enabling
