### Title
Unbounded gzip decompression of user-supplied Declare V1 `program` in RPC execution/simulation path enables memory-exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The JSON-RPC execution/simulation path that converts a client-submitted `BroadcastedDeclareTransaction::V1` into an executable transaction decompresses the attacker-controlled, base64+gzip-encoded legacy `program` field via `decompress_program` with no size or time bound, unlike every other decompression path in the codebase which uses the bounded `decode_and_decompress_with_size_limit`. A single unprivileged RPC caller (e.g. calling `starknet_estimateFee` / `starknet_simulateTransactions` / trace-simulation endpoints with a crafted `BroadcastedDeclareV1Transaction`) can submit a small gzip payload that decompresses to an enormous size, exhausting node memory/CPU — directly analogous to the Apache Neethi CVE-2026-66144 bug class (remote/attacker-supplied compressed data fetched/decompressed without resource bounds).

### Finding Description
`decompress_program` performs base64-decoding followed by unbounded gzip decompression: [1](#0-0) 

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which is reached when converting a `BroadcastedDeclareTransaction::V1` (a user-supplied, not-yet-mined transaction submitted for simulation/estimation/tracing) into an `ExecutableTransactionInput`: [2](#0-1) 

The `contract_class.program` field is a base64-encoded, gzip-compressed JSON program supplied directly by the untrusted RPC caller. `GzDecoder::read_to_end` in `decompress_program` reads the fully decompressed output into memory with no cap — the code even contains an explicit acknowledgement of the missing bound: `// TODO(dan): add time and size limits.`

By contrast, every other decompression path for user- or network-supplied compressed data in this codebase enforces an explicit `max_size` bound, e.g.: [3](#0-2) 

and its use for the analogous Sierra program path: [4](#0-3) 

`decompress_program` is the one remaining unbounded decompression sink reachable from an unprivileged, unauthenticated caller.

### Impact Explanation
A single RPC request from any unprivileged client can trigger unbounded memory allocation on the node servicing `estimateFee`/`simulateTransactions`/trace-style RPC calls that accept a `BroadcastedDeclareTransaction::V1`. A gzip payload of a few hundred KB to a few MB (well within any request-body size limit) can expand by orders of magnitude (a "zip bomb"), driving the process to allocate gigabytes of memory and consume significant CPU decompressing it, causing the RPC service (and potentially the host, if memory is shared with other sequencer components) to become unresponsive — a denial-of-service condition matching the "network unable to confirm new transactions" / availability-loss impact class.

### Likelihood Explanation
High likelihood: the endpoint is reachable without any special privileges — it is a standard read-style JSON-RPC method (fee estimation / simulation / tracing) that any client of the node's RPC interface can call. No on-chain transaction needs to be broadcast or accepted; the malicious payload only needs to be well-formed enough to pass base64 decoding and gzip framing, and does not need to result in a valid class (the size-bomb happens before any semantic validation of the decompressed JSON).

### Recommendation
Replace the unbounded decode/decompress logic in `decompress_program` (crates/apollo_rpc/src/v0_8/api/mod.rs) with the existing bounded utility `decode_and_decompress_with_size_limit` (crates/starknet_api/src/compression_utils.rs), applying the same maximum decompressed-size limit used elsewhere for Cairo0/legacy programs and Sierra programs (e.g. the configured `max_sierra_program_size` / equivalent legacy-program bound), returning a client error instead of attempting unbounded decompression when the limit is exceeded.

### Proof of Concept
1. Craft a `BroadcastedDeclareV1Transaction` whose `contract_class.program` field is set to a base64-encoded gzip stream that decompresses to a very large payload (a classic "gzip bomb": a small compressed input expanding to gigabytes, e.g. repeated zero bytes compress at extremely high ratios).
2. Send this transaction object as the `request` parameter to an RPC method that performs simulation/estimation using `TryFrom<BroadcastedDeclareTransaction>` (e.g. `starknet_estimateFee`, `starknet_simulateTransactions`).
3. Observe that `decompress_program` (crates/apollo_rpc/src/v0_8/api/mod.rs:671-682) calls `GzDecoder::read_to_end` with no size limit, causing the node process to allocate memory proportional to the decompressed size before any validation occurs, exhausting available memory/CPU and degrading or crashing the RPC service.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
