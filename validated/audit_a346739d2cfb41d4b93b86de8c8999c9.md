### Title
DeployAccount transactions can be permanently griefed via front-run address squatting using the generic `deploy_syscall` - ([File: crates/blockifier/src/execution/execution_utils.rs])

### Summary
A `DeployAccount` transaction's target contract address is fully deterministic from public inputs (`class_hash`, `contract_address_salt`, `constructor_calldata`, with `deployer_address = 0`). Any unprivileged transaction sender can pre-compute this exact address and call the generic `deploy_syscall` (with `deploy_from_zero=true`) from an already-deployed contract to occupy that address first. Because contract deployment permanently fails once an address's class hash is non-zero, this front-run permanently blocks the victim's `DeployAccount` transaction from ever succeeding — the same "make the exact-state-dependent call fail forever via a cheap front-run" bug class described in the external report (there, an LP-balance-zero assertion; here, a zero-class-hash precondition).

### Finding Description
The account address for a `DeployAccount` transaction is computed with `deployer_address = ContractAddress::default()` (zero), exactly like a generic `deploy_syscall` invoked with `deploy_from_zero = true`: [1](#0-0) [2](#0-1) 

This means any contract already deployed on-chain can call `deploy_syscall(class_hash, contract_address_salt, constructor_calldata, deploy_from_zero=true)` and land on precisely the same address that will be computed for a future `DeployAccount` transaction that uses the same `class_hash`, `contract_address_salt`, and `constructor_calldata` (all of which are visible in the mempool/pending pool, or predictable off-chain since wallets commonly derive salt from the account's public key).

Deployment enforces a strict precondition that the target address currently has a zero class hash: [3](#0-2) 

If an attacker's front-run transaction executes first and writes any non-zero class hash to that address, the subsequent legitimate `DeployAccount` transaction execution fails with `StateError::UnavailableContractAddress`, and the whole transaction execution errors out (not merely reverts with fee charged): [4](#0-3) 

Since deployment writes a permanent state change (a non-zero class hash) to that specific address, there is no way for the honest account to ever be deployed at that same, deterministically-derived address again. The attack costs only the minimal fee for a trivial `deploy_syscall` call from any already-deployed contract, i.e., a "smallest unit" griefing action analogous to sending the smallest unit of LP token in the original report.

### Impact Explanation
Wallets and users frequently pre-fund a "counterfactual" account address before it's actually deployed (a common Starknet UX pattern, since the deployment fee itself is often paid from that address's own pre-funded balance, or third parties send assets to the address ahead of time). If an attacker front-runs and squats the address with a dummy deployed contract:
- The victim's `DeployAccount` transaction becomes permanently unexecutable at that address (`StateError::UnavailableContractAddress` is a hard, permanent failure — the class hash slot is now non-zero forever).
- Any funds already sent to that pre-computed address before the squatting attack become permanently frozen, since the intended owner's account can never be deployed there to access them.
- This is a concrete, low-cost, unprivileged griefing DoS with permanent freezing-of-funds impact, reachable by any transaction sender submitting an ordinary `Invoke` transaction that calls `deploy_syscall`.

### Likelihood Explanation
Likelihood is high: the attack requires no special privileges — merely an already-deployed contract (any account can call `deploy_syscall`) and knowledge of the victim's future `(class_hash, salt, constructor_calldata)` tuple. This information is exposed either by observing the pending `DeployAccount` transaction in the mempool before inclusion, or is predictable in advance for common wallet salt derivation schemes (e.g., salt = public key). The cost to the attacker is a single cheap transaction.

### Recommendation
Consider decoupling the security of counterfactual-address funding from the generic `deploy_syscall` address-collision behavior, e.g., by:
- Reserving computed `DeployAccount` addresses at time of `AddTransaction`/mempool acceptance so a colliding generic `deploy_syscall` targeting a reserved address is rejected, or
- Documenting/mitigating at the wallet level that salts must include unpredictable/private entropy (not just the public key) so addresses cannot be front-run before the owner's first transaction is broadcast, and warning against pre-funding counterfactual addresses.
This is fundamentally the same "front-run to permanently break an address/state precondition" bug class as the referenced `exitTempusAMM` griefing report, differing only in that the affected precondition is deployment's "target address must have zero class hash" invariant rather than an LP balance-zero assertion.

### Proof of Concept
1. Attacker observes (or predicts) a pending `DeployAccount` transaction with `(class_hash=C, contract_address_salt=S, constructor_calldata=D)`.
2. Attacker computes the deterministic address `addr = calculate_contract_address(S, C, D, ContractAddress::default())` (same formula used in `syscall_base.rs::deploy`, see `crates/blockifier/src/execution/syscalls/syscall_base.rs` lines 400-410).
3. Attacker submits (and gets included first, e.g., via fee bump) an `Invoke` transaction from any already-deployed contract calling `deploy_syscall(C, S, D, deploy_from_zero=true)`.
4. This writes a non-zero class hash at `addr` (per `execute_deployment` in `crates/blockifier/src/execution/execution_utils.rs` lines 337-373).
5. The victim's original `DeployAccount` transaction, when executed, now fails permanently with `StateError::UnavailableContractAddress` (as demonstrated by the "deploy to an existing address" negative-flow test in `crates/blockifier/src/transaction/transactions_test.rs` lines 2312-2338), and can never succeed at that address again.
