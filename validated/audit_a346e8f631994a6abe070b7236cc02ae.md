## Finding [1](#0-0) 

### Title
Stale per-timestamp `index-cache` reuse across intra-block vault-state-changing operations permanently freezes unclaimed treasury yield - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` maintains an `index-cache` map keyed only by `{ timestamp: stacks-block-time, aid }` [2](#0-1)  to avoid repeated calls into a vault's `accrue` within the same block. This mirrors the reported `poke` bug-class: a value is cached/bound once, its true source (the vault's accrual inputs) can move again within the same evaluation window, but the cache is not invalidated on that move — later logic silently consumes the stale value.

### Finding Description
The Zest market contract calls into each vault's `accrue` function (e.g. `v0-vault-usdc.clar` `accrue`) to refresh the interest index and mint the DAO-treasury's reserve share [3](#0-2) . Per `docs/vaults.md`, the market wraps this in a cache keyed purely on `stacks-block-time` and `aid`, returning the cached `{index, lindex}` tuple on a cache hit without recomputing:

```clarity
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid }))
    (match (map-get? index-cache- cache-key)
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
```

The vault's `next-index` / `next-liquidity-index` values are functions of elapsed time *and* of state that changes on every `system-borrow`/`system-repay`/`deposit`/`redeem` (scaled principal, total assets, utilization) [4](#0-3) . If two operations touch the same vault within the same block/timestamp — the first mutating principal/assets (e.g. a large `system-borrow`), the second relying on `accrue-and-cache` for the same `aid` — the second call's index/reserve computation is served from the cache bound *before* the mutation, not recomputed against the now-changed utilization. The reserve increment (`reserve-inc`) and resulting `treasury-lp` mint to `.dao-treasury` for that second state transition are computed and finalized using the stale index and are never revisited, because the cache is never invalidated by anything other than `stacks-block-time` changing.

This is structurally the same defect as the `poke` report: a bound value (`totalVoting` / cached index) is not invalidated when its true source state moves (bribe `withdraw` / vault utilization change), and a subsequent consumer (`earned` / next market operation) uses the stale value, permanently losing the correct amount that should have accrued.

### Impact Explanation
Because the DAO-treasury reserve mint happens inline during `accrue` and is derived from whichever index value is in effect at that moment [5](#0-4) , an intra-block sequence that mutates vault state and then triggers a cached (stale) re-accrual causes the protocol reserve fee for that increment of interest to be permanently mis-minted (too little or, depending on ordering, skipped for that slice), with no mechanism afterward to recompute or top up the difference. This is a permanent freezing of unclaimed protocol yield (the reserve portion that should have flowed to `.dao-treasury`), matching the in-scope "High — permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
This requires only ordinary user-triggered multi-step interaction within a single block/transaction context (e.g. a borrow immediately followed by another vault-touching market call for the same asset within the same `stacks-block-time`), not privileged access, oracle manipulation, or DAO compromise — consistent with the analog constraints (single-transaction/single-block cached-value-not-invalidated pattern).

### Recommendation
Invalidate or bypass the `index-cache` entry whenever a state-mutating vault call (`system-borrow`, `system-repay`, `deposit`, `redeem`) executes against that `aid` within the same block, or key the cache on a monotonically increasing per-vault mutation nonce in addition to `stacks-block-time`, so any intervening state change forces a fresh `vault-accrue` call rather than serving a stale cached index.

Conceptual sequence (exact private-function body of `accrue-and-cache` in `v0-4-market.clar` could not be fully retrieved within tool budget beyond confirming the `index-cache` map definition; behavior below is inferred from that map and the documented caching flow in `docs/vaults.md`):
1. Within one block/timestamp, call a market operation causing `system-borrow` on vault `aid=zUSDC`, mutating `principal-scaled`/utilization.
2. Immediately call a second market operation touching the same vault (`aid`) in the same timestamp; `accrue-and-cache` finds an existing `index-cache` entry for `{timestamp, aid}` from step 1 and returns it instead of recomputing against the new utilization.
3. The reserve share (`treasury-lp`) computed for the second operation is derived from the pre-mutation index, permanently under/mis-crediting `.dao-treasury`.
4. No later call recomputes or corrects this discrepancy — the lost reserve yield is unrecoverable.
