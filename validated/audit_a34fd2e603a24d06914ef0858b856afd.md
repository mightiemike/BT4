## Analysis

The Sherlock finding centers on a permissionless value-transfer function that lacks validation of the destination address, allowing funds to be irrecoverably burned when the address is invalid/zero. The closest reachable analog in `nearcore` is the `DeleteAccountAction` beneficiary-transfer path, which has the exact same missing-validation shape: the destination account (`beneficiary_id`) is only checked for AccountId *syntax*, never for *existence*, and the resulting transfer is executed as a refund receipt that can never create an account and, on failure, unconditionally burns the deposit.

### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` permanently burns the deleted account's remaining balance instead of failing the deletion or refunding the signer - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally issues a `Receipt::new_balance_refund` to the caller-supplied `beneficiary_id` for the full remaining balance of the account being deleted, with no check that `beneficiary_id` refers to an existing account. Because this transfer is dispatched as a system-predecessor "refund" receipt, implicit account creation is disabled for it by design, and if `beneficiary_id` does not exist, the transfer action fails with `AccountDoesNotExist`. The runtime's refund-receipt-failure path then permanently burns the deposit rather than returning it to anyone.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) computes the account's balance and, if non-zero, pushes a refund receipt to the chosen beneficiary: [1](#0-0) 

This receipt is a "balance refund" (`Receipt::new_balance_refund`), whose `predecessor_id` is `system`. In `apply_action`, `is_refund` is derived from `receipt.predecessor_id().is_system()` and passed into `check_account_existence`/`implicit_creation_allowed`, which explicitly disallows implicit account creation for refunds: [2](#0-1) 

Validation of `DeleteAccountAction` only checks that `beneficiary_id` is a syntactically valid `AccountId` — never that it exists on-chain — as documented: [3](#0-2) 

When the refund receipt's `Transfer` action targets a non-existent `beneficiary_id`, `check_account_existence` rejects it with `AccountDoesNotExist` (confirmed by the existing regression test for the `0u` universal-account case, but the underlying `implicit_creation_allowed`/`is_refund` gate applies to every account type, including ordinary named accounts): [4](#0-3) 

Finally, in `apply_action_receipt`, any failed receipt whose predecessor is `system` (i.e., any failed refund, including this beneficiary transfer) has its deposit **burned** rather than refunded or retried: [5](#0-4) 

There is no fallback that returns the funds to the deleted account's former owner or to the transaction signer — the entire balance is added to `stats.balance.other_burnt_amount` and permanently removed from total supply, exactly mirroring the reported pattern of an unchecked recipient address causing unrecoverable fee/fund destruction.

### Impact Explanation
Any account holder who submits a `DeleteAccountAction` (directly, via a batched promise, or via a meta-transaction/relayer) with a `beneficiary_id` that is syntactically valid but does not correspond to an existing account — due to a typo, a deleted/never-created account, or deliberate construction — causes their entire remaining native NEAR balance to be permanently and irrecoverably burned. This is a direct "permanently frozen/lost funds" outcome caused by the absence of a destination-existence check, matching the accepted impact category (unrecoverable burn of value that should have gone to a recipient or been safely refunded).

### Likelihood Explanation
This requires only a single, unprivileged transaction from the account owner (or a relayer executing a signed `DelegateAction`/meta-transaction on the owner's behalf) specifying an account-deletion with an unchecked beneficiary. No special privileges, validator status, or network position are needed — only crafting (or mistakenly using) a non-existent `beneficiary_id`, which is trivial.

### Recommendation
Before dispatching the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or otherwise disallow non-existent beneficiaries at validation time, similar to how `InvalidAccountId` is already checked). Alternatively, change the refund-failure handling for the beneficiary transfer specifically so that, on `AccountDoesNotExist`, the account deletion itself fails (aborting the whole action) instead of silently burning the balance.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance.
2. Submit a transaction from `alice.near` containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })`, where `nonexistent.near` has never been created.
3. `action_delete_account` pushes `Receipt::new_balance_refund(&"nonexistent.near", account_balance)` and removes `alice.near` from state.
4. When the refund receipt executes, `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist` because `implicit_creation_allowed` returns `false` for refund receipts.
5. In `apply_action_receipt`, since `receipt.predecessor_id().is_system()` is true and `result.result.is_err()`, `stats.balance.other_burnt_amount` is increased by the full `account_balance` — the funds are burned forever, with `alice.near` already deleted and `nonexistent.near` never credited. /// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
