## Title
Liquidator can seize a borrower's entire collateral balance for a given asset while only repaying debt sized for the smaller, correctly-capped liquidation amount, due to a rounding "dust" override that updates `coll-final` without updating `debt-to-repay` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
In `liquidate()`, the collateral amount actually seized (`coll-final`) and the debt amount actually repaid (`debt-to-repay`) are computed through a multi-step pipeline (`process-collateral-asset` → `calc-final-liquidation-amounts` → `scale-debt-for-liquidation`) that keeps the two values proportionally tied together. A final "dust" adjustment then overrides `coll-final` to the borrower's *full* collateral balance whenever the *leftover* collateral converts to `0` debt tokens after rounding — but it does **not** recompute `debt-to-repay` to match the larger collateral amount now being seized. [1](#0-0) 

### Finding Description
The pipeline computes `coll-final-raw` (the collateral proportional to the debt actually being repaid) via `scale-debt-for-liquidation`: [2](#0-1) 

`debt-to-repay` returned from that same function is fixed and tied to `coll-final-raw`. The function then computes the leftover, unseized collateral (`coll-remaining = user-coll-balance - coll-final-raw`) and its "would-be" debt value (`remaining-debt-to-repay`): [3](#0-2) 

If `remaining-debt-to-repay` rounds down to `0`, the code sets the final `coll-final` to the entire `user-coll-balance` instead of `coll-final-raw`: [4](#0-3) 

However, `debt-to-repay` (used both for `vault-system-repay` and for the return value/event) is **never re-derived** from this larger `coll-final`. It stays computed from the original, smaller `coll-final-raw`. This is exactly the same bug class as the reported H-4: a quantity (`coll-final`) that plays a "constraint" role earlier in the calculation is silently swapped for a materially different, final value in one branch, while its paired downstream value (`debt-to-repay`) is left stale and not recomputed to be consistent with the new value — instead of ensuring `debt-to-repay` = `f(coll-final)` uniformly across all branches, like `scaledQuoteTokenAmount` was supposed to equal `C * p` uniformly across all branches in the Ajna report.

`vault-system-repay` is then called with the stale, too-small `debt-to-repay`, while `collateral-remove` seizes the full `coll-final` (= `user-coll-balance`): [5](#0-4) 

This "dust" override is reachable whenever the *value* (in the debt asset's token units) represented by `coll-remaining` rounds to zero. Because `coll-remaining` is measured in the *collateral asset's* raw token units while the zero-check is performed on the *debt asset's* raw token units, a low-priced/high-decimal collateral asset can have a large raw-token `coll-remaining` that still converts to `0` debt tokens (`mul-div-down rem-debt-usd (pow u10 debt-decimals) debt-price` rounding down), especially when `debt-decimals` is small or `debt-price` is large. A liquidator can influence this outcome by choosing `debt-amount` (which drives `debt-actual-usd`, `coll-expected`, `coll-actual`, and therefore `coll-final-raw`/`coll-remaining`), making the “leave a large dust chunk of cheap collateral to be given away for free” outcome achievable rather than purely accidental.

### Impact Explanation
This allows a liquidator to seize the borrower's entire remaining collateral balance in the liquidated asset while only repaying the smaller `debt-to-repay` amount computed for the intentionally-capped, proportional liquidation. The excess collateral (up to the full `user-coll-balance` minus `coll-final-raw`) is transferred to the liquidator without any corresponding debt repayment — a direct transfer of borrower funds to the liquidator. This is theft of user funds at rest, matching the Critical impact class.

### Likelihood Explanation
The trigger condition depends only on values computable/observable before submission (oracle price, `debt-amount`, and asset decimals) within a single `liquidate()` call — no multi-block timing or privileged access is required. Any liquidator can choose `debt-amount` to try to land in the rounding window where `remaining-debt-to-repay` computes to `0`. The condition is more easily reachable for low-decimal/high-price debt assets paired with high-decimal/low-price collateral assets, which exist in this protocol's asset set.

### Recommendation
When the dust-override branch is taken and `coll-final` is expanded to `user-coll-balance`, recompute `debt-to-repay` (and `debt-final-usd`, `scaled-to-remove`) consistently for the new, larger `coll-final`, mirroring how `calc-final-liquidation-amounts` and `scale-debt-for-liquidation` keep collateral and debt proportionally tied in the non-dust branches. Alternatively, only allow the "give away all collateral" dust-forgiveness when the corresponding *collateral* value itself (not just its rounded debt-token equivalent) is below a safe minimal threshold, and always charge the liquidator for whatever extra collateral is actually transferred.

### Proof of Concept
1. Borrower has collateral `C` of a low-price, high-decimal asset (e.g., a token priced at fractions of a cent with 18 decimals) and outstanding debt in a low-decimal/high-price debt asset (e.g., 6 decimals, high USD price per token).
2. Liquidator calls `liquidate()` requesting a `debt-amount` that is capped by `max-debt-usd` at a partial-liquidation percentage (`liq-pct-scaled < 100%`), so `coll-actual`/`coll-final-raw` is only a fraction of `user-coll-balance`.
3. `coll-remaining = user-coll-balance - coll-final-raw` is a large quantity of raw collateral tokens but converts (via `normalize`, `div-bps-down`, and `mul-div-down` with the debt asset's decimals/price) to `0` debt tokens due to rounding.
4. `remaining-debt-to-repay` evaluates to `u0`, so `coll-final` is set to the full `user-coll-balance` at line 1486, while `debt-to-repay` remains the smaller amount from step 2.
5. `vault-system-repay` is called with the small `debt-to-repay`; `collateral-remove` transfers the liquidator the entire `user-coll-balance` — more collateral than the repaid debt entitles them to, at the borrower's expense. [6](#0-5)

(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))
