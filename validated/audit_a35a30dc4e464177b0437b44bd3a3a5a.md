Found a solid local analog. The bug-class from the report (missing `x == 0` / `y == 0` early-exit checks in `pow()` leading to values silently accepted without validating the boundary condition) maps to a missing boundary/residual check in Aptos's Merkle accumulator proof verification.

### Title
Accumulator proof verification never checks the residual leaf index, allowing version/index spoofing in authenticated proofs - (File: `types/src/proof/definition.rs`)

### Summary
`AccumulatorProof::verify()` folds over the sibling hash list, consuming the low-order bits of `element_index` one per sibling (via `index % 2` / `index / 2`), but never checks that the *remaining* value of `index` after all siblings are consumed is `0`. This means any `element_index` congruent modulo `2^(number_of_siblings)` to the leaf's true position will produce an identical, successfully-verifying proof, regardless of its high-order bits. Because callers (e.g. `TransactionWithProof::verify`, `verify_transaction_info`) pass an attacker/peer-supplied version number directly as `element_index`, this breaks the binding between an authenticated proof and the version/index it claims to represent.

### Finding Description
`AccumulatorProof::verify` at [1](#0-0)  computes:
```rust
let actual_root_hash = self.siblings.iter().fold(
    (element_hash, element_index),
    |(hash, index), sibling_hash| {
        (
            if index % 2 == 0 { ... } else { ... },
            index / 2,
        )
    },
).0;
```
Only the resulting hash (`.0`) of the fold is used; the final residual index (`.1`, equal to `element_index >> siblings.len()`) is discarded and never checked to be zero. Consequently, for a proof with `d = siblings.len()` siblings, `verify(root, hash, index)` and `verify(root, hash, index + k * 2^d)` for any integer `k` are indistinguishable — both compute the exact same `actual_root_hash` and both succeed if it matches `expected_root_hash`.

This is structurally the same class of bug as the reported `pow()` issue: a boundary/edge value (`0` remainder) is never explicitly validated, and the function silently proceeds to return a result that appears valid but doesn't actually correspond to the input as the caller intends.

The unchecked `element_index` is not an internal detail — it flows directly from untrusted, attacker/peer-controlled data. `TransactionWithProof::verify` passes `self.version` — a plain, wire-deserialized field with no independent derivation — straight into the proof: [2](#0-1)  and `verify_transaction_info` similarly forwards the caller-supplied `transaction_version` as `element_index`: [3](#0-2) .

### Impact Explanation
A malicious or compromised full node (or any code path deserializing an untrusted `TransactionWithProof`/`TransactionInfoWithProof`/event proof from the network or REST API) can present a transaction/event/proof pinned to a real, valid accumulator hash chain, but claim a different, forged version/index for it — as long as that forged value agrees with the true leaf position in its low-order `d` bits. A downstream consumer (light client, indexer, or any authenticated API caller who calls `.verify()` and trusts a successful result) can be made to accept a proof as authenticating the wrong version/object binding while the cryptographic-looking check reports success. This is exactly the "authenticated API or state-view output bound to the wrong version, object, or proof context" impact category, since the accumulator proof is meant to durably bind a leaf's content to a specific position in the ledger.

### Likelihood Explanation
Exploitation only requires controlling the "version"/"index" field alongside an otherwise-legitimate (unmodified) hash-chain proof — something naturally available to any dishonest peer serving REST/state-sync responses, without any privileged access, and without needing to forge cryptographic hashes. The magnitude of usable "wrong" index deltas is `2^d` where `d` is the accumulator proof depth for that leaf (which grows with ledger size), so on a live, large mainnet ledger with billions of transactions this window can be large enough to matter for spoofing purposes, and even a difference of exactly `2^d` is a real, exploitable mismatch that current code accepts.

### Recommendation
In `AccumulatorProof::verify` (and any structurally similar accumulator/proof verification code), explicitly check that the residual index after consuming all siblings equals zero, e.g.:
```rust
let (actual_root_hash, remaining_index) = self.siblings.iter().fold(
    (element_hash, element_index),
    |(hash, index), sibling_hash| { ... },
);
ensure!(remaining_index == 0, "Element index has extra unverified high bits.");
ensure!(actual_root_hash == expected_root_hash, ...);
```
This mirrors, in spirit, the recommended fix in the referenced report: don't skip validating a boundary condition (there, `x == 0`/`y == 0`; here, the residual/high-order index bits) that changes the semantic correctness of the function's result.

### Proof of Concept
1. Build (or observe) a real `AccumulatorProof` with `d` siblings authenticating leaf `hash` at true index `i` under `root_hash` (as in the existing test `test_verify_two_element_accumulator` at [4](#0-3) , where `d = 1`).
2. Call `proof.verify(root_hash, hash, i)` — succeeds (expected).
3. Call `proof.verify(root_hash, hash, i + (1 << d))` — this **also** succeeds, because `(i + (1<<d)) % 2 == i % 2` at level 0, and the shifted value at the next fold step is identical to what `i` alone would have produced; the extra bit is silently dropped without ever being validated as `0`.
4. Any caller such as `TransactionWithProof::verify(ledger_info)` at [2](#0-1)  that trusts an attacker-set `self.version` field will accept `self.version = i + (1<<d)` as valid, even though the true leaf is at position `i`.

    pub fn verify(
        &self,
        expected_root_hash: HashValue,
        element_hash: HashValue,
        element_index: u64,
    ) -> Result<()> {
        ensure!(
            self.siblings.len() <= MAX_ACCUMULATOR_PROOF_DEPTH,
            "Accumulator proof has more than {} ({}) siblings.",
            MAX_ACCUMULATOR_PROOF_DEPTH,
            self.siblings.len()
        );

        let actual_root_hash = self
            .siblings
            .iter()
            .fold(
                (element_hash, element_index),
                // `index` denotes the index of the ancestor of the element at the current level.
                |(hash, index), sibling_hash| {
                    (
                        if index % 2 == 0 {
                            // the current node is a left child.
                            MerkleTreeInternalNode::<H>::new(hash, *sibling_hash).hash()
                        } else {
                            // the current node is a right child.
                            MerkleTreeInternalNode::<H>::new(*sibling_hash, hash).hash()
                        },
                        // The index of the parent at its level.
                        index / 2,
                    )
                },
            )
            .0;
        ensure!(
            actual_root_hash == expected_root_hash,
            "{}: Root hashes do not match. Actual root hash: {:x}. Expected root hash: {:x}.",
            type_name::<Self>(),
            actual_root_hash,
            expected_root_hash
        );

        Ok(())
    }
