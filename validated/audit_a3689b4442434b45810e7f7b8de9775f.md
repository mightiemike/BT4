## Title
Replay-verification comparator silently ignores state-checkpoint hashes, allowing corrupted/divergent state roots to pass as "verified" - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the chunk-executor's `verify_execution` path (backup replay-verify / `verify_execution_mode`) and by `aptos-debugger`'s `print_mismatches`/replay tooling to confirm that locally re-executed transaction outputs match the `TransactionInfo` recorded on an untrusted backup/archive. This function explicitly does **not** compare the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields, which are the fields that authenticate the actual committed state (Jellyfish Merkle / hot-state / position-state) root produced by a checkpoint transaction. [1](#0-0) [2](#0-1) 

### Finding Description
`ensure_match_transaction_info` checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against the supplied `TransactionInfo`, but it stops short of validating the state-checkpoint-related hashes: [3](#0-2) 

This function is invoked from `ChunkExecutorInner::verify_execution`, which re-executes a chunk of transactions taken from an (untrusted) backup and is supposed to prove that the archived `TransactionInfo`/write-sets are consistent with independent VM execution: [4](#0-3) 

Because the checkpoint-hash fields are never compared, a checkpoint transaction whose `state_checkpoint_hash` (or, once trading-native landed, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) in the archived `TransactionInfo` diverges from the value that independent re-execution would produce will still be reported as "matching" by this comparator, as long as the write-set, events, gas, and status happen to align. The `TransactionInfo::hash()` embeds these fields, so at the accumulator/root-hash layer a tampered or buggy checkpoint hash would eventually be caught by Merkle-proof verification against a trusted `LedgerInfo`, but the *local, VM-driven cross-check* that `verify_execution`/`ensure_match_transaction_info` performs is the one specific mechanism meant to catch a divergence between "what the archived ledger claims the state root is" and "what independent execution computes the state root to be" — and it is bypassed for the checkpoint-hash class of fields.

The gap is self-acknowledged in code: [5](#0-4) 

### Impact Explanation
If replay-verify (`storage/backup/backup-cli`'s replay/verify-execution flows and `db-tool`'s `replay_on_archive`) is relied upon to attest that an archived/backed-up ledger's state roots are consistent with correct VM execution, this comparator gap means a corrupted or hard-fork-diverged state checkpoint hash embedded in a `TransactionInfo` can pass verification silently. This directly undermines one of the "Proof And Storage Pivots" called out in the task (VM outputs and transaction infos must survive executor-to-storage/replay handoff unchanged, and replay paths must not accept a wrong state root as valid) for the specific sub-check that `verify_execution_mode`/`ensure_match_transaction_info` is supposed to provide. However, because the overall `TransactionInfoWithProof`/accumulator verification (`verify_transaction_info` in `types/src/proof/mod.rs`) still authenticates `TransactionInfo::hash()` — which includes the checkpoint hash fields — against a validator-signed `LedgerInfo`, a *cryptographically forged* mismatch would still be caught at that higher layer. The concretely exploitable gap is narrower: it affects tooling whose entire purpose is to detect *local execution divergence* from an already-accepted (validator-signed) archive, i.e., it can mask a genuine consensus/state-root bug (or an as-yet-undetected hard-fork divergence) in checkpoint-hash computation during replay-verify, rather than allowing an attacker to directly forge a fake proof past cryptographic accumulator checks.

### Likelihood Explanation
This requires either (a) a real state-root computation bug in Aptos affecting checkpoint hashes that would otherwise be surfaced by replay-verify tooling, or (b) an operator relying on `verify_execution`/`ensure_match_transaction_info` to certify state-root correctness of a backup before restoring it. The trigger condition is not attacker-controlled in the sense of bypassing consensus; it depends on this comparator being used as the sole detection mechanism for checkpoint-hash divergence, which the code's own `TODO(trading-native)` comment confirms is presently the case, gated on the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on either side) between the locally computed `TransactionOutput`/checkpoint and the expected `TransactionInfo`, consistent with the other fields already checked (write-set hash, event root hash, gas, status), before any trading-native state-root features are enabled.

### Proof of Concept
Not independently constructed a working exploit; the finding is based on static analysis of `ensure_match_transaction_info` and its callers (`ChunkExecutorInner::verify_execution`, `aptos-debugger`'s `print_mismatches`). A conceptual PoC: craft a backup chunk where the transaction's write-set/events/gas/status match correct execution but the recorded `TransactionInfo.state_checkpoint_hash` is altered; `verify_execution`/`ensure_match_transaction_info` would report a match despite the state-checkpoint divergence.

**Confidence note:** I was unable to fully confirm (due to running out of tool iterations) whether the primary consensus/commit path (`do_state_checkpoint.rs`) independently validates checkpoint hashes elsewhere in a way that fully compensates for this gap outside of the replay-verify tooling, and whether `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields are populated at all on current mainnet given `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is not yet enabled. This limits the finding to a "likely low-to-moderate severity, tooling-scoped" issue rather than a confirmed high/critical mainnet-committed-state divergence, and it should be treated as a candidate for further verification rather than a fully proven critical vulnerability.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
