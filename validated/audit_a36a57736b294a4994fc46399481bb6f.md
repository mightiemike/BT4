### Title
`DeleteAccount` beneficiary is only syntax-checked, never checked for existence — refund to a non-existent beneficiary permanently burns the account balance - ([File: runtime/runtime/src/action_validation.rs])

### Summary
`DeleteAccountAction.beneficiary_id` (the "recipient" of a deleted account's remaining balance) is validated only for account-id syntax, never for whether the account actually exists. The balance payout is sent as a system "refund" receipt, and refund receipts are structurally forbidden from creating an account. If the chosen beneficiary does not exist, the payout receipt fails and — per the documented refund-failure rule — its deposit is burned rather than returned to anyone. This mirrors the reported Dinari issue: an unvalidated recipient address lets value become permanently unrecoverable.

### Finding Description
When a transaction signer submits `Action::DeleteAccount(DeleteAccountAction { beneficiary_id })`, the only pre-execution validation is a syntax check: [1](#0-0) 

There is no check that `beneficiary_id` corresponds to an existing (or even initialized) account. During execution, `action_delete_account` unconditionally schedules the remaining balance as a "balance refund" receipt to that address: [2](#0-1) 

That payout is a `Receipt::new_balance_refund`, i.e. a system-predecessor "refund" receipt. `check_account_existence`'s `implicit_creation_allowed` helper explicitly forbids refund receipts from creating any account, no matter the account-id type: [3](#0-2) 

So if `beneficiary_id` is a named account that was never created (or any account type where the refund can't create it), the resulting `Transfer` action inside the refund receipt fails with `ActionErrorKind::AccountDoesNotExist`. The protocol's documented behavior for a failing refund receipt is not "return to sender" — it is burned: [4](#0-3) [5](#0-4) 

This is confirmed by the test harness, which notes that using a non-existent beneficiary would make the transfer "come straight back as a refund" only if handled carefully — the comment explicitly calls out that tests must pre-create the beneficiary or the balance is lost: [6](#0-5) 

### Impact Explanation
An unprivileged transaction signer (the account owner deleting their own account, or in a chain of nested actions/relayed transactions where the account is deleted with attacker-influenced `beneficiary_id`) can cause the account's entire remaining NEAR balance to be permanently and irrecoverably burned instead of transferred, with zero prior warning from the protocol beyond a generic "invalid account id" syntax check. This is a direct analog of the Dinari finding: a recipient/beneficiary field is accepted into a value-transferring action without existence validation, and the failure mode is silent, permanent loss of funds ("frozen"/burned funds) rather than a safe revert of the whole transaction. Because `DeleteAccount` must be the terminal action, the account is deleted (state removed) regardless of whether the beneficiary transfer receipt later fails — the deletion and the (failed) payout are two separate receipts, so users cannot simply retry: the account is already gone and the burned funds cannot be recovered.

### Likelihood Explanation
High reachability: any user can trigger this with an ordinary `DeleteAccountAction` transaction where `beneficiary_id` is a syntactically valid but non-existent (or unreachable-for-refund-creation) account id — e.g. a typo'd account, an account that was never funded, or a temporarily-not-yet-created sub-account. No special privileges, staking, or contract logic are needed; it is a single-transaction, single-signer action. The failure/burn path is deterministic given `implicit_creation_allowed` always returning `false` for refunds.

### Recommendation
Before scheduling the beneficiary payout in `action_delete_account`, verify that `beneficiary_id` refers to an existing account (or is a named/implicit account type that the refund path is actually capable of crediting), and reject the `DeleteAccount` action with an explicit error (e.g. an `ActionErrorKind::AccountDoesNotExist`-style validation error surfaced before the account is destroyed) if the beneficiary cannot receive the refund. Alternatively, change the "failed refund" semantics for delete-account payouts specifically so that instead of burning silently, the funds are held/returned via a mechanism recoverable by the original owner (though this is a broader protocol change). At minimum, this behavior should be prominently documented as a foot-gun given its resemblance to a fund-loss bug class.

### Proof of Concept
1. Account `alice.near` holds a `DeleteAccountAction` transaction with `beneficiary_id = "nonexistent.near"` (a syntactically valid, never-created named account).
2. `validate_delete_action` passes (only checks `AccountId` syntax) — see `runtime/runtime/src/action_validation.rs:447-451`.
3. `action_delete_account` executes: `alice.near`'s account is removed from state, and a `Receipt::new_balance_refund("nonexistent.near", alice_balance)` is queued — `runtime/runtime/src/actions.rs:380-386`.
4. When that refund receipt is later applied, `check_account_existence` for its inner `Transfer` action calls `implicit_creation_allowed`, which returns `false` because `is_refund == true` — `runtime/runtime/src/actions.rs:928-933` — so the transfer fails with `AccountDoesNotExist`.
5. Per the documented refund-failure rule, "a failed refund burns its deposit into `other_burnt_amount`" — `protocol-model/spec/runtime-execution.md:69,152` — so `alice`'s entire remaining balance is burned rather than returned to `alice` or credited to any account.

Note: I could not directly inspect the exact burn code path (`runtime/runtime/src/lib.rs` around the refund-processing branch referenced by the spec, e.g. line ~929/972) due to index truncation in this session; the burn-on-failed-refund behavior is corroborated by the protocol-model spec document and the accompanying test comment, but a full Devin session with file access would be needed to pinpoint and verify the exact runtime/runtime/src/lib.rs line numbers implementing the burn.
