## Title
Duplicate Witness Addresses in `VoteWitnessContract` Not Merged in `VoteWitnessActuator` (Legacy TX Path) — Inconsistent With the Native TVM Vote Path - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

## Summary
`VoteWitnessActuator.validate()`/`countVoteAccount()` processes each `Vote` entry in `VoteWitnessContract.getVotesList()` independently and does not check for, or merge, duplicate `vote_address` entries. This mirrors the reported bug class exactly: a caller-controlled array (`votes`) with repeated "keys" (witness addresses) is summed/validated per-item without de-duplication, while the parallel/newer implementation for the same operation (`VoteWitnessProcessor`, used by the TVM native `voteWitness` precompile) explicitly merges duplicate witness addresses via a `Map<ByteString, Long> voteMap` before applying them.

## Finding Description
In `VoteWitnessActuator.validate()`: [1](#0-0) 
the code iterates `contract.getVotesList()`, validates each vote's address/witness/count, and simply accumulates `sum` (fine for the aggregate tron-power check), but never checks whether the same `voteAddress` appears more than once in the list.

In `countVoteAccount()` (execute path): [2](#0-1) 
each `Vote` entry is applied individually via `votesCapsule.addNewVotes(...)` and `accountCapsule.addVotes(...)` — with no merging step for repeated witness addresses.

By contrast, `VoteWitnessProcessor` (used by the native/TVM `voteWitness` contract call path) explicitly guards against this exact scenario: [3](#0-2) 
The comment `// merge vote for same witness` and the `voteMap` accumulation logic demonstrate that java-tron's own team identified and fixed this duplicate-element class of bug for the TVM path, but the legacy `Actuator` path (used for ordinary broadcast `VoteWitnessContract` transactions) still lacks this fix.

This is structurally identical to the reported `RevenueManagement.setOutputTokensConfig` issue: a list-based configuration/instruction (`_outputTokens` there, `votes` here) is trusted to have unique keys, the aggregate/limit check (100% sum / tronPower sum) is computed correctly across duplicates, but the per-key application/storage step is not deduplicated, so the final persisted per-key state depends on how repeated entries interact with storage rather than being validated/rejected outright.

## Impact Explanation
If a user crafts a `VoteWitnessContract` with the same witness address repeated many times (up to `MAX_VOTE_NUMBER` = 30 entries), each occurrence is separately appended to `VotesCapsule.newVotes` (a repeated protobuf field) and to the account's votes list via `accountCapsule.addVotes(...)`. Whether or not this produces double-counted vote totals at DPoS maintenance time depends on how `MaintenanceManager`/witness vote tallying reconciles `oldVotes` vs `newVotes` per witness address — logic that was not fully traceable within the remaining investigation budget. However, the fact that the TVM-facing implementation of the identical operation had to add explicit per-address merging to be correct is strong evidence that the un-merged legacy `Actuator` path can produce inconsistent per-witness vote accounting (i.e., the number of `Vote` records for one witness in a single account's vote list no longer matches "one vote entry per witness" as other code paths (and downstream vote-diffing logic) may assume). This risks incorrect witness vote tallies feeding into DPoS witness selection — a consensus-affecting accounting bug — rather than a simple limit-bypass.

## Likelihood Explanation
Likely reachable: any account can broadcast a `VoteWitnessContract` with a `votes` list containing duplicate `vote_address` entries; `validate()` places no restriction preventing duplicates (only a cap of `MAX_VOTE_NUMBER` on list length and per-account tronPower bound on the total). This requires no privileged role — any anonymous account with sufficient TronPower and RPC access to broadcast a transaction can trigger it.

## Recommendation
Add a de-duplication/merge step in `VoteWitnessActuator.validate()` and `countVoteAccount()` identical to the one already implemented in `VoteWitnessProcessor` — i.e., merge votes by `vote_address` into a map before applying/validating, or explicitly reject transactions containing duplicate `vote_address` entries in the `votes` list, so that the legacy actuator path and the TVM native path behave consistently.

## Proof of Concept
1. Construct a `VoteWitnessContract` for `OWNER_ADDRESS` with `votes` containing the same `WITNESS_ADDRESS` repeated N times (N ≤ `MAX_VOTE_NUMBER`), each with `voteCount = V`, such that `N*V*TRX_PRECISION <= tronPower` (as in the existing test helper `getRepeateContract` in `VoteWitnessActuatorTest`): [4](#0-3) 
2. Call `actuator.validate()` — it passes because the aggregate `sum` check does not inspect per-address duplication.
3. Call `actuator.execute()` — `countVoteAccount` appends N separate `Vote` entries for the same witness to both `AccountCapsule` and `VotesCapsule` rather than one consolidated entry, diverging from the deduplicated behavior enforced in `VoteWitnessProcessor.execute()`.

Note: full confirmation of the downstream maintenance-time vote-tally corruption (exact reconciliation logic in `MaintenanceManager`) could not be completed within the available investigation steps; the finding is based on the confirmed absence of duplicate-address handling in `VoteWitnessActuator` contrasted with the confirmed presence of such handling in `VoteWitnessProcessor` for the equivalent operation.
