### Title
Energy underpricing in `ValidateMultiSign.execute()` via aliased signature offsets bypassing `getEnergyForData` length-based accounting - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`ValidateMultiSign.getEnergyForData()` charges energy purely as a function of `rawData.length` (`(data.length/32 - 5)/5 * 1500`), assuming each accounted "slot" corresponds to one distinct signature that will be run through `recoverAddrBySign`. Because `extractSigArray` resolves each signature's byte offset from fully attacker-controlled `DataWord` values that can alias the same underlying bytes, an attacker can craft a short `rawData` that still yields the maximum `MAX_SIZE = 5` signature array while triggering 5 real `recoverAddrBySign` (ECDSA recovery) calls, at a fraction of the energy that a "5 real signatures" layout would normally cost.

### Finding Description
`getEnergyForData` is defined as: [1](#0-0) 

It derives the expected signature count solely from `data.length`, assuming the standard ABI layout of 5 header words + 5 words per signature item (`ABI_ITEM_WORDS = 5`).

In `execute()`, when `VMConfig.allowTvmSelfdestructRestriction()` is active (an already-activated TVM feature flag, not attacker-controlled but part of the current production code path), the real signature array is built via `extractSigArray`: [2](#0-1) 

`extractSigArray` reads `len` from `words[offset]` (capped at `MAX_SIZE = 5` by the check above it) and then, for each of the `len` items, independently reads an offset word `words[offset + i + 1]` to locate the 65-byte signature blob: [3](#0-2) 

Nothing constrains these `len` offset words to point to distinct, non-overlapping regions of `data` — an attacker can set all 5 offset words to the same value so all 5 "signatures" alias the identical 65-byte blob. This lets the attacker satisfy `sigArraySize == 5` (the maximum allowed) with a `rawData` far shorter than the length that `getEnergyForData` assumes is required to encode 5 distinct signature items.

Crucially, the main loop in `execute()` invokes `recoverAddrBySign` (an actual ECDSA public-key recovery, CPU-equivalent to `ECRecover.execute`) unconditionally for every entry in the `signatures` array, *before* any duplicate-signature short-circuiting: [4](#0-3) 

So 5 real signature-recovery operations are performed even though every entry is byte-for-byte identical, while `getEnergyForData` — driven only by `rawData.length` — can be made to report a lower slot count (e.g., 1) by keeping `rawData` short. No other guard checks that the offsets used in `extractSigArray` are consistent with `rawData.length` or with each other, so the accounting invariant "energy charged ≥ actual CPU-equivalent operations performed" is violated.

### Impact Explanation
Any unprivileged caller (contract or transaction) invoking the `ValidateMultiSign` precompile (address `0x...0a`) can force up to 5 real ECDSA-recovery operations for a fraction of the energy that this workload is priced at (`1500` per sign per the code's own comment "one sign 1500, half of ecrecover"). This is a materially underpriced-work condition: an attacker can pack many such calls into a block/transaction at reduced energy cost, consuming disproportionate CPU on validating/full nodes relative to the energy paid, which is a DoS/economic-abuse vector against network resource pricing.

### Likelihood Explanation
- No special privileges are required — a standard smart contract call to the `ValidateMultiSign` precompiled address triggers this path.
- `VMConfig.allowTvmSelfdestructRestriction()` gates the `extractSigArray` code path; this is a feature flag activated network-wide once the corresponding chain parameter/proposal is enabled (a normal hard-fork-style toggle, not something the attacker needs to control), so once active on a network this is directly exploitable by any user.
- Crafting the aliased offset words is straightforward and fully deterministic; no race conditions or timing dependencies are involved, making it 100% repeatable.

### Recommendation
Compute `getEnergyForData` (or validate energy at execute-time) based on the actual `signatures.length` extracted from the parsed structure rather than purely from `data.length`, or alternatively validate that all signature offsets referenced by `extractSigArray` are strictly increasing / point to non-overlapping regions consistent with `ABI_ITEM_WORDS` before accepting the array, so that the length-derived energy formula always upper-bounds the real number of `recoverAddrBySign` invocations. A minimal fix is to charge `signatures.length * ENGERYPERSIGN` after extraction (with a cap check) instead of, or in addition to, the pre-extraction length-based estimate — mirroring `BatchValidateSign`'s equivalent formula which has the identical decoupling flaw.

  // performs 5 real recoverAddrBySign calls internally.

  contract.setRepository(RepositoryImpl.createRoot(StoreFactory.getInstance()));
  contract.setVmShouldEndInUs(System.nanoTime() / 1000 + 2_000_000);
  int[] recoverCallCount = {0};

  // assert 5 invocations occurred despite chargedEnergy implying 1.
  Pair<Boolean, byte[]> result = contract.execute(rawData);
