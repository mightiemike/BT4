### Title
Multi-store actuator mutations lack per-transaction atomicity, causing storage corruption on mid-execution failure - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
The external report flags the Substrate anti-pattern of executing multiple storage writes inside a single extrinsic without `#[transactional]`, so a failure partway through leaves committed, inconsistent state. The java-tron analog is the actuator pattern: an actuator's `execute()` method performs several independent `Store.put()` calls directly against `TronStoreWithRevoking`-backed stores, which write straight into the revoking `Chainbase`/`SnapshotRoot` layer [1](#0-0) . There is no session/transaction wrapper inside `execute()` that groups these writes and rolls them back together if a later statement in the same method throws.

### Finding Description
`AssetIssueActuator.execute()` performs a sequence of store mutations that are not atomic with respect to each other: it increments and persists the global `tokenIdNum` counter, writes the new asset into `assetIssueStore`/`assetIssueV2Store`, deducts the fee balance (and burns/transfers it to the blackhole), and only afterwards mutates the owner's `AccountCapsule` (frozen supply list, asset amounts, `AssetIssuedName`/`AssetIssuedID`) before finally calling `accountStore.put()`: [2](#0-1) [3](#0-2) 

Each individual `store.put()` call writes immediately into the revoking database layer (`revokingDB.put(...)`), which is the persistence unit that gets rolled back only at the granularity of a whole block/session (via `RevokingDatabase.revoke()`), not per-actuator or per-statement: [1](#0-0) 

If any exception is thrown after some of these `put()` calls have already executed but before the method completes (e.g., an `ArithmeticException` from the account-capsule bookkeeping performed near the end of the method, such as `addAsset`/`addAssetV2`), the `catch` block only sets the result status to `FAILED` and re-throws `ContractExeException`—it does not undo the `dynamicStore.saveTokenIdNum(tokenIdNum)`, the `assetIssueStore`/`assetIssueV2Store` puts, or the fee deduction/burn that already ran: [4](#0-3) 

This is structurally the same defect class as the reported bug: several storage mutations inside one "extrinsic" (actuator) without an all-or-nothing wrapper, so a mid-method exception commits partial state.

### Impact Explanation
A partially-applied `AssetIssueActuator` execution would leave the chain in an inconsistent state: the token ID counter is consumed and an `AssetIssueCapsule` is persisted in `assetIssueStore`/`assetIssueV2Store` as if the asset issuance succeeded, and the owner's TRX fee has already been deducted/burned, yet the owner's `AccountCapsule` never receives `AssetIssuedName`/`AssetIssuedID`/asset balance or frozen-supply updates because the transaction is ultimately marked `FAILED`. This produces a "ghost" asset that exists in the asset stores but is not properly owned/backed by any account balance — a divergence between asset-issuance state and account state that corrupts accounting invariants (assets in circulation vs. supply owned) and could be exploited to create tokens that are not properly attributed, or simply cause consensus-relevant state (token numbering, DB indexes) to drift from the intended semantics.

However, I could not fully verify within the available tool budget whether the outer actuator dispatch loop (e.g., in `Manager.java`, not fully inspected due to iteration limits) wraps each transaction's actuator execution in a rollback session that would revert all `revokingDB.put()` calls made by an actuator whose `execute()` throws. If such a wrapper exists and reverts per-transaction (not just per-block), the partial-write concern would be substantially mitigated. I was unable to confirm this before running out of iterations, so the severity assessment above should be treated as conditional on that unresolved detail.

### Likelihood Explanation
Triggering the partial-write path in `AssetIssueActuator` requires reaching the account-mutation section after already committing the earlier `put()`s — an unprivileged user could in principle craft an asset-issuance transaction whose frozen-supply/asset-amount computation overflows (`ArithmeticException`) in the account-capsule methods, but this depends on specific overflow conditions in `AccountCapsule.addAsset`/`addAssetV2` that I did not fully trace to a concrete reachable input within this session.

### Recommendation
Group all storage mutations performed by a single actuator's `execute()` into one atomic unit: perform validation/computation first, then apply all `store.put()` calls only after all fallible operations (arithmetic, protobuf unpacking) have succeeded, or explicitly stage changes and commit them only at the end of `execute()` so that any exception thrown mid-method leaves no partial `store.put()` calls applied. Verify and, if necessary, harden the transaction-processing wrapper (in `Manager.java`/block-application code) to guarantee it reverts *all* store writes made during a failed actuator's `execute()`, not just at block granularity.

### Proof of Concept
Not independently reproduced — a concrete PoC requires confirming (1) an achievable overflow/exception path inside the account-mutation section of `AssetIssueActuator.execute()` after the earlier `put()` calls, and (2) that the transaction-processing wrapper does not already revert those earlier writes on that exception. Both points require further investigation of `Manager.java`'s transaction-processing/session logic, which was not completed due to tool-call limits.
