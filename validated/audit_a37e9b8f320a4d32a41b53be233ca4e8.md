### Title
Unbounded `eth_getLogs` block range combined with post-hoc `MAX_RESULT` check causes O(chain height) memory/CPU allocation - (File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java)

### Summary
`LogFilterWrapper.validateBlockRange` only rejects wide block ranges when `Args.getInstance().getJsonRpcMaxBlockRange() > 0`; when that config is `0` (disabled) the range cap is skipped entirely. In that state, an unprivileged `eth_getLogs` call with `fromBlock=0`/`toBlock=latest` reaches `LogBlockQuery`, which computes `minSection=0` and `maxSection=currentMaxBlockNum/BLOCK_PER_SECTION`, allocates a `BitSet` sized to the whole chain height, and — critically — builds the entire `blockNumList` result (up to chain-height size) before ever checking the `MAX_RESULT` cap.

### Finding Description
`LogFilterWrapper`'s constructor only enforces a range cap when `checkBlockRange` is true, and even then `validateBlockRange` is a no-op unless `maxBlockRange > 0`: [1](#0-0) 

With that check disabled, `LogBlockQuery`'s constructor sets `minSection`/`maxSection` directly from the requested (or default) `fromBlock`/`toBlock`, unbounded by any range cap: [2](#0-1) 

`getPossibleBlock()` then allocates a `BitSet` of `capacity = (maxSection - minSection + 1) * BLOCK_PER_SECTION` and sets the full range, and — more importantly — the loop that materializes `blockNumList` iterates over the *entire* `blockNumBitSet` range and only checks `blockNumList.size() >= MAX_RESULT` **after** the loop completes, not incrementally during iteration: [3](#0-2) 

If the filter has no address/topic conditions (`allConditionsIndex` is empty), the `for (int[][] conditionsIndex : allConditionsIndex)` AND-loop never executes, so `blockNumBitSet` remains fully set across the whole requested range; every block number in `[minBlock, maxBlock]` gets boxed into `blockNumList` (a `List<Long>`) before the size check finally throws `JsonRpcTooManyResultException`. This means the `MAX_RESULT` guard does not bound the work performed — it only bounds the error being thrown afterward. For a chain with tens of millions of blocks, this is O(chain height) BitSet allocation/iteration plus O(chain height) `Long` boxing/list growth, all triggered by a single unauthenticated `eth_getLogs` call.

### Impact Explanation
A single unauthenticated JSON-RPC caller can force the node to allocate and iterate a BitSet plus an `ArrayList<Long>` sized proportionally to the entire chain height (tens of millions of entries) in one synchronous request handler thread, causing CPU spikes and heap pressure. Repeated concurrent requests amplify this into a straightforward node degradation/DoS vector, entirely reachable through the public JSON-RPC API with no special privileges.

### Likelihood Explanation
This requires the node operator to have `jsonRpcMaxBlockRange <= 0` (config-dependent, not an attacker-controlled setting) and a filter without address/topic narrowing so the whole range is "matched." Given `jsonRpcMaxBlockRange` is a runtime-configurable value documented in `docs/configuration.md`, some deployments may run with it disabled (default value could not be fully confirmed from available index, but the code path unconditionally allows this when the value is non-positive). The exploit itself, once the precondition holds, is trivially and repeatably triggerable by any external client with one HTTP JSON-RPC request.

### Recommendation
- Check `MAX_RESULT` incrementally inside the `blockNumBitSet.nextSetBit` loop in `getPossibleBlock()` and abort as soon as the threshold is exceeded, instead of after materializing the full list.
- Enforce a hard, non-configurable upper bound on `(maxSection - minSection)` / requested block range for `eth_getLogs` regardless of `jsonRpcMaxBlockRange` configuration, so operators cannot inadvertently disable all protection.
- Consider bounding `BitSet` capacity construction itself (e.g., reject before allocating if range exceeds a sane absolute limit).

  public LogBlockQuery(LogFilterWrapper logFilterWrapper, SectionBloomStore sectionBloomStore,
      long currentMaxBlockNum, ExecutorService executor) {
    this.logFilterWrapper = logFilterWrapper;
    this.sectionBloomStore = sectionBloomStore;
    this.sectionExecutor = executor;
    this.currentMaxBlockNum = currentMaxBlockNum;

    if (logFilterWrapper.getFromBlock() == Long.MAX_VALUE) {
      minBlock = currentMaxBlockNum;
    } else {
      minBlock = logFilterWrapper.getFromBlock();
    }
    minSection = (int) (minBlock / Bloom.BLOOM_BIT_SIZE);

    if (logFilterWrapper.getToBlock() == Long.MAX_VALUE) {
      maxBlock = currentMaxBlockNum;
    } else {
      maxBlock = logFilterWrapper.getToBlock();
      if (maxBlock > currentMaxBlockNum) {
        maxBlock = currentMaxBlockNum;
      }
    }
    maxSection = (int) (maxBlock / Bloom.BLOOM_BIT_SIZE);
  }
