### Title
Missing voting-window enforcement in `vote-for-aggregate-public-key` lets any historically-set signer stack a stale vote onto an unrelated reward cycle - ([File: stackslib/src/chainstate/stacks/boot/signers-voting.clar])

### Summary
`signers-voting.clar` defines a helper `is-in-voting-window`, whose doc comment states the vote for a reward cycle's aggregate key "must happen after the list of signers has been set by the node, which occurs in the first block of the prepare phase," but the public entry point `vote-for-aggregate-public-key` never calls it. As a result the equality the contract is supposed to enforce — *"a vote is only valid if `reward-cycle == last-set-cycle` AND `burn-block-height` is within that cycle's prepare phase"* — is never checked on-chain.

### Finding Description
`vote-for-aggregate-public-key` performs these checks only: [1](#0-0) 
- the key not yet approved for that `reward-cycle`
- key length == 33
- key not reused across cycles
- signer hasn't voted in this `reward-cycle`/`round`
- round increases by at most 1

It never calls `is-in-voting-window`, which is the only place that checks `reward-cycle == (get-last-set-cycle)` and `is-in-prepare-phase burn-block-height`: [2](#0-1) 

Signer-weight validation for an arbitrary caller-supplied `reward-cycle` is delegated to `.signers get-signer-by-index`: [3](#0-2) 

The `.signers` contract's `cycle-signer-set` map is populated once per cycle when the prepare phase starts and is never cleared for old cycles: [4](#0-3) 

Consequently, any principal that was ever a signer for *some* cycle `C` (even one long past, whose voting round never reached the 70% threshold and therefore has no `aggregate-public-keys` entry) can call `vote-for-aggregate-public-key` for `reward-cycle = C` at any later burn height — not just during `C`'s prepare phase, and without `C` needing to be `last-set-cycle`. This is unprivileged (any past signer) and requires no majority, only the caller's own signer weight from that cycle, matching the "signer weight below threshold or from the wrong set" pattern used to break protocol equalities.

### Impact Explanation
The direct consequence is that `tally`, `rounds`, `round-data`, `used-aggregate-public-keys`, and (if the stale weight reaches the recomputed threshold) `aggregate-public-keys` for that stale cycle can be mutated arbitrarily far outside the window the protocol design assumes ("sale can be extended indefinitely" analog: the voting window for a given reward cycle never actually closes). Whether this rises to a Critical/High chain-split or reward-loss impact depends on whether any downstream consensus-critical code path (miner/signer commit validation, sBTC peg wallet key selection) reads `get-approved-aggregate-key` for historical cycles. My search found the aggregate-key call sites concentrated in test harnesses (`pox_4_tests.rs`, `test_signers.rs`) and boot-contract setup code (`stackslib/src/chainstate/stacks/boot/mod.rs`, `nakamoto/signer_set.rs`, `nakamoto/mod.rs`), but I could not confirm from the index whether any live Nakamoto block-validation or peg-wallet-selection logic re-reads a *past* cycle's `get-approved-aggregate-key` after the fact in a way that would cause two honest nodes to disagree on a state root or accept/reject a block differently. This is a genuine unenforced invariant in-repo, but I cannot substantiate a concrete state-root divergence or reward-theft path with the available index, so I am not confident this clears the bar for Critical/High impact as strictly defined by the rules.

### Likelihood Explanation
Trivially triggerable by any account that was ever a member of any historical signer set (`cycle-signer-set` entries are never pruned), requiring no majority and no privileged key — only a normal signed contract-call transaction. No special timing or race condition is needed beyond calling after the intended window has closed.

### Recommendation
Add an explicit `(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))` at the top of `vote-for-aggregate-public-key`, matching the documented invariant, so that votes are only accepted for `reward-cycle == last-set-cycle` and only while `is-in-prepare-phase` is true.

### Proof of Concept
1. Let cycle `C` be a past reward cycle whose signer set was set via `.signers set-signers` (so `cycle-signer-set` has an entry for `C`), but whose vote never reached `threshold-consensus` (no `aggregate-public-keys` entry for `C` exists).
2. Any principal `S` that was in `C`'s signer set can, at any later burn height (long after `C`'s prepare phase and even after many subsequent reward cycles), call `(contract-call? .signers-voting vote-for-aggregate-public-key signer-index key round C)`.
3. Because `is-in-voting-window` is never invoked, none of the four checks in the function body reject this call: the key-not-yet-set, length, novelty, duplicate-vote, and round checks all pass on a fresh `(round, cycle)` pair, and `get-signer-weight` still succeeds because `.signers get-signer-by-index` looks up the never-pruned `cycle-signer-set` for `C`.
4. The vote is recorded and tallied for a reward cycle that, by the contract's own documentation, should no longer be open for voting.

I was not able to fully verify, given the size limits on the code index, whether any consensus-critical Rust code re-reads a stale-cycle's `get-approved-aggregate-key` in a way that would translate this into a chain-split or reward-loss; a Devin session with full repo access would be needed to trace all downstream readers of `get-approved-aggregate-key` (e.g., sBTC peg wallet selection, signer coordination) to confirm or rule out a Critical/High-severity consensus impact.

(define-private (is-in-voting-window (height uint) (reward-cycle uint))
    (let ((last-cycle (unwrap-panic (contract-call? .signers get-last-set-cycle))))
        (and (is-eq last-cycle reward-cycle)
            (is-in-prepare-phase height))))
