### Title
In-memory, per-process `RequestReplayGuard` allows replay of a captured signed Vault JSON-RPC request across independent gateway/DON-node processes - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
`RequestReplayGuard` deduplicates authorized Vault JSON-RPC requests using an in-process `sync.Mutex`-guarded `map[string]int64` with no persistence or cross-process sharing. Every `Authorizer` (one per gateway-side `vault.NewHandler`, one per node-side `vault.NewGatewayHandler`) constructs its own private `RequestReplayGuard` via `NewAuthorizer`, so a digest accepted by one gateway process or one DON node's authorizer is completely unknown to any other gateway process or node process.

### Finding Description
`RequestReplayGuard.CheckAndRecord` records `digest → expiresAt` in a local map (`core/capabilities/vault/request_replay_guard.go:16-47`) that is created fresh per `Authorizer` instance: [1](#0-0) 
Both the gateway public handler (`core/services/gateway/handlers/vault/handler.go:207`, `authorizer := vaultcap.NewAuthorizer(...)`) and the node-side gateway connector handler (`core/capabilities/vault/gw_handler.go:108-111`, `authorizer = NewAuthorizer(...)`) each independently instantiate their own `Authorizer`/`RequestReplayGuard`. There is no shared store (DB, Redis, or DON-wide broadcast) backing this guard — it is explicitly documented as an in-memory, per-instance structure: [2](#0-1) 

The call sequence matches the reported path: `authorizer.AuthorizeRequest` invokes `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` at `core/capabilities/vault/authorizer.go:109`, which is per-authorizer-instance, not DON-wide. Because a JWT-authorized request's digest is bound only via the `authorization_details` claim and checked against this local map, replaying the identical signed request (still within JWT expiry) to a second, independent gateway process (or a DON node with a physically disjoint shard membership, per `config.ShardedDONConfig.Shards`) hits a *different* `RequestReplayGuard` instance that has never seen the digest, and `CheckAndRecord` succeeds there too — passing authorization a second time and reaching the privileged write handlers (`handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete` in `gw_handler.go`).

Existing tests confirm replay is only rejected *within a single authorizer instance* (`TestAuthorizer_RejectsJWTReplay`, `TestRequestReplayGuard_DuplicateRejected` in `core/capabilities/vault/authorizer_test.go` / `request_replay_guard_test.go`) — none test or enforce cross-process/cross-shard uniqueness.

Note: currently `handler_factory.go`'s `NewHandler` for `VaultHandlerType` only wires up `shardsConnMgrs[0][0]` (the first DON's first shard) per handler instance: [3](#0-2) 
so true multi-shard fan-out isn't fully wired for a single Gateway process today, but the underlying replay-guard gap is real and directly exploitable across any two independently-deployed Gateway processes / DON node processes that a client or DON operator can reach (e.g. redundant Gateway operators forwarding into disjoint node sets), matching the stated preconditions.

### Impact Explanation
An authorized (non-expired) signed Vault write request can be processed more than once DON-wide because replay protection is scoped to a single process's memory rather than being DON- or vault-wide. This can cause duplicate privileged vault actions (duplicate `secrets.create`/`update`/`delete` executions) to be persisted independently by different gateway/node processes, corresponding to the Chainlink bounty category of unauthorized/duplicated transaction or workflow execution and data-integrity tampering within the vault subsystem.

### Likelihood Explanation
Requires only: (1) a genuine, previously-authorized signed request (with a still-valid JWT expiry window) that the attacker can capture — including a legitimate user replaying their own captured traffic — and (2) network access to submit that same raw request to a second independent gateway endpoint or node path lacking shared replay state. No privileged keys, mock/test-only code, or admin access are required; this is a pure architecture/replay-scope gap confirmed directly in `request_replay_guard.go` and its two independent call sites in `authorizer.go`/`gw_handler.go`/`handler.go`.

### Recommendation
Back `RequestReplayGuard` with a shared, durable store (e.g., a DB table or distributed cache keyed by digest+expiry) accessible to all gateway and DON node processes, or otherwise bind replay-protection state to a DON-wide consensus mechanism (e.g., only accept a digest once quorum/OCR agreement is reached) rather than per-process memory. At minimum, document and enforce that sharded DON deployments must share a common replay store when serving the same logical vault.

### Proof of Concept
Integration/invariant test plan:
1. Construct two independent `GatewayVaultRequestProcessor` instances (mirroring `gw_handler.go`'s `NewGatewayHandler`), each with its own `NewAuthorizer(...)` (hence independent `RequestReplayGuard`), sharing the same JWT validator config/public key so both accept the same token.
2. Build one signed JSON-RPC `vault.secrets.create` request with a JWT whose `authorization_details` digest claim matches `req.Digest()`, and an `exp` in the future.
3. Call `processorA.ProcessRequest(ctx, &req, publicKey)` — assert success (`err == nil`).
4. Call `processorB.ProcessRequest(ctx, &req, publicKey)` with the identical raw request/token — assert it **also** succeeds (`err == nil`), demonstrating the digest is not rejected DON-wide.
5. Contrast with a single shared authorizer/guard scenario (`processorA` reused twice) where the second call returns `vault.ErrRequestAlreadySeen`, proving the guard works correctly only when instance state is shared — establishing the invariant that must hold DON-wide but currently does not across processes.

```go
// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}
```
