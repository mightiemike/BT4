### Title
Gas-Metering Bypass via Contract Instantiation Cost (Unbounded Globals/Data-Segments/Element-Segments Not Charged by Gas) - ([File: runtime/near-vm-runner/src/logic/gas_counter.rs])

### Summary
CVE-2020-2928 is a MySQL optimizer bug in which specially-crafted (but otherwise permitted) input causes a disproportionate amount of server-side work relative to what the request "pays for", producing a hang/crash DoS. The nearcore analog is in the WASM contract-loading/instantiation path: the only fee charged for loading a contract is `contract_loading_base + contract_loading_bytes * code_len` [1](#0-0)  — a fee proportional purely to the *serialized byte size* of the WASM module. However, per-invocation instantiation work (zero-initializing globals, populating data segments, populating element/table segments) scales with the *count* of these entities, not their byte-encoded size, and this cost is explicitly acknowledged in the codebase as **not covered by gas**: [2](#0-1) .

### Finding Description
A contract deployer can craft a WASM module with tens of thousands of globals, active data segments, or active element segments, each of which encodes to only a few bytes in the module (e.g., a zero-initialized global is a fixed small number of bytes regardless of how many globals are declared) [3](#0-2) . Module preparation only enforces a *count* limit (`max_globals_per_contract`, `max_elements_per_contract_table`, etc.) at `prepare_v3`, not a cost proportional to that count: [4](#0-3) .

Once such a contract is deployed and passes preparation (staying under the configured count limits, e.g. 50,000 globals/data segments or 10,000 element segments — well under the ~100k threshold that would otherwise be caught by Wasmtime's `max_core_instance_size` pooling-allocator backstop and turned into a `LoadingError` abort), every subsequent function call to that contract pays only the byte-size-based loading fee via `add_contract_loading_fee`/`before_loading_executable` [5](#0-4) , while the actual Wasmtime module instantiation re-initializes all globals/data-segments/element-segments on every call. This mismatch between charged gas and real CPU work is exactly the class of bug the runtime-params-estimator authors flagged: "Exposes unbounded per-call Wasmtime global re-initialization not covered by gas," "Exposes unbounded per-call data-segment initialization not covered by gas," and "Exposes unbounded per-call table-initialization work not covered by gas" [2](#0-1) .

Because every validator executes the same deterministic contract call when applying a chunk, an attacker who deploys such a contract and repeatedly calls it with minimal attached gas can force every honest validator applying that shard to spend CPU time on instantiation that is disproportionate to the gas actually burnt and paid for. This is conceptually the network-wide analog of a single "high-privileged" query causing a repeatable hang — here, a single unprivileged deployer + caller pair.

Note that nearcore has already partially hardened one related edge (loading *failures* at `Module::deserialize`, e.g. when instance size breaches the 1MiB pooling-allocator slot) via `FixContractLoadingError`, ensuring a `LoadingError` becomes a gas-bearing abort rather than a free zero-gas nop [6](#0-5) . That fix addresses only the *failed-load* case; it does not add a cost model for the *successful* instantiation of many globals/segments below the failure threshold, which remains uncharged in per-call gas.

### Impact Explanation
This is a gas-metering/fee bypass: the true CPU cost of contract execution (module instantiation) is not covered by the amount of gas burnt/charged. An attacker can submit inexpensive transactions that consume disproportionate validator compute, degrading or halting chunk production across the network relative to what was paid for — a DoS analogous to CVE-2020-2928's availability impact, reachable by any unprivileged contract deployer/caller without special permissions.

### Likelihood Explanation
Deploying a WASM contract with tens of thousands of globals/data-segments/element-segments (below the count limits enforced at `prepare_v3`) and then repeatedly calling it are both actions available to any account with minimal balance to pay deployment/gas fees. No validator or protocol-level privilege is required, matching the "network access, no special privileges" profile of the original CVE (aside from the fixed CVE's higher-privilege requirement, this nearcore analog is reachable by an ordinary user).

### Recommendation
Introduce a gas cost component in `before_loading_executable`/`add_contract_loading_fee` (or an additional instantiation-fee charged post-load) that scales with the number of globals, active data segments, and active element segments declared by the module, rather than only the WASM byte size. Calibrate this using the existing `AdversarialLoadManyGlobals`, `AdversarialLoadManyDataSegments`, and `AdversarialLoadManyElementSegments` estimator benchmarks already present in `runtime/runtime-params-estimator/src/vm_estimator.rs`, and enforce it as a protocol-level fee so instantiation cost is fully covered by gas for every call, not just for failed loads.

### Proof of Concept
1. Build a WASM contract using `near_test_contracts::contract_with_num_globals(N)` (or the data/element-segment equivalents) with `N` set just below the configured `max_globals_per_contract` limit — small enough to deserialize successfully via Wasmtime (avoiding the `max_core_instance_size` backstop), e.g. 50,000 globals [7](#0-6) .
2. Deploy this contract from an ordinary account.
3. Repeatedly submit cheap `FunctionCall` transactions invoking a trivial exported method on this contract.
4. Measure gas charged (`contract_loading_base + contract_loading_bytes * code_len`, a small fixed amount since the byte-encoding of many zero-initialized globals is compact) versus wall-clock/CPU cost incurred by every validator's Wasmtime instantiation of the module for each call, as already quantified by the `adversarial_load_many_globals`/`adversarial_load_many_data_segments`/`adversarial_load_many_element_segments` estimators [8](#0-7) .
5. Observe the disparity: gas charged does not scale with the real per-call instantiation cost, demonstrating the gas bypass.

    ///
    /// This cost does not consider the structure of the contract code, only the
    /// size. This is currently the only loading fee. A fee that takes the code

    pub(crate) fn add_contract_loading_fee(&mut self, code_len: u64) -> Result<()> {
        self.pay_per(ExtCosts::contract_loading_bytes, code_len)?;
        self.pay_base(ExtCosts::contract_loading_base)
    }

    /// VM independent setup before loading the executable.
    ///
    /// Does VM independent checks that happen after the host state has been set
    /// up but before loading the executable. This includes pre-charging gas
    /// costs for loading the executable, which depends on the size of the WASM code.
    #[cfg(feature = "wasmtime_vm")]
    pub(crate) fn before_loading_executable(
        &mut self,
        config: &near_parameters::vm::Config,
        method_name: &str,
        wasm_code_bytes: u64,
    ) -> std::result::Result<(), super::errors::FunctionCallError> {
        if method_name.is_empty() {
            let error = super::errors::FunctionCallError::MethodResolveError(
                super::errors::MethodResolveError::MethodEmptyName,
            );
            return Err(error);
        }
        if config.fix_contract_loading_cost {
            if self.add_contract_loading_fee(wasm_code_bytes).is_err() {
                let error =
                    super::errors::FunctionCallError::HostError(super::HostError::GasExceeded);
                return Err(error);
            }
        }
        Ok(())
    }
