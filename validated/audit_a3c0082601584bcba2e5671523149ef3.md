### Title
Unbounded per-owner key-space growth via zero-fee DelegateResourceContract enables unauthorized-cost public query amplification in `getWithPrefix` - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
An attacker can call `DelegateResourceActuator`, whose `calcFee()` returns `0`, repeatedly with distinct receiver addresses to add unbounded numbers of entries under the `V2_FROM_PREFIX`/`FROM_PREFIX` key-space for a single owner address in `DelegatedResourceAccountIndexStore`. Any public caller of `GetDelegatedResourceAccountIndex(V2)` (HTTP/gRPC/JSON-RPC) then triggers `getWithPrefix`, which performs an unbounded `prefixQuery` scan plus a full `List.sort` with no size cap, causing query cost to grow linearly with attacker-controlled state rather than being bounded.

### Finding Description
`DelegateResourceActuator.execute()` calls `delegateResource()`, which calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, ...)` [1](#0-0) . Each call inserts a new key `Bytes.concat(V2_FROM_PREFIX, from, to)` into the revoking DB [2](#0-1) , so a distinct `to` (receiver) address produces a distinct persistent key that is never removed unless `unDelegateV2` is explicitly called for that exact pair.

`DelegateResourceActuator.calcFee()` unconditionally returns `0` [3](#0-2) , meaning the only cost to the attacker for growing this key-space is ordinary bandwidth/energy consumption of a normal transaction — no fee scales with the number of distinct index entries created.

The read path, `getWithPrefix`, performs `this.prefixQuery(key)` for both the from- and to- prefixes, wraps the entire result map into an `ArrayList`, and then does `tmpToList.sort(Comparator.comparing(...))` with no limit, pagination, or cap on the number of returned/sorted items [4](#0-3) . This is reachable from any unauthenticated caller via `Wallet.getDelegatedResourceAccountIndexV2()` → `getV2Index()` → `getWithPrefix()` [5](#0-4) , which is exposed over HTTP (`/wallet/getdelegatedresourceaccountindexv2`, `/walletsolidity/...`) via `GetDelegatedResourceAccountIndexV2Servlet` [6](#0-5) , as well as over gRPC via `RpcApiService.getDelegatedResourceAccountIndexV2` [7](#0-6) . No rate-limiting or result-size cap exists in these servlets beyond the generic `RateLimiterServlet` request-rate throttling; there is no cap on the amount of work performed per accepted request.

There are real preconditions/costs an attacker must satisfy that partially limit exploitability: `validate()` requires the receiver account to already exist on-chain (`accountStore.get(receiverAddress) != null`), the receiver must not be a smart contract, must differ from the owner, and each delegation requires `delegateBalance >= 1 TRX` covered by the owner's available frozen V2 balance for the chosen resource [8](#0-7) . However, none of these checks are proportional to, or bound, the number of *distinct* index entries that can accumulate for one owner over many transactions/blocks — an attacker can create many receiver accounts cheaply and issue many low-fee delegate transactions over time, each adding one permanent index entry.

### Impact Explanation
Once N distinct delegate index entries exist for an owner, every future call to `GetDelegatedResourceAccountIndexV2` for that owner performs an O(N) `prefixQuery` scan plus an O(N log N) sort in `getWithPrefix`, with no cap. This is public, unauthenticated read work whose cost is entirely attacker-controlled and not represented in the price the attacker paid (bandwidth/energy for N cheap transactions vs. unbounded CPU/latency imposed on every future caller of a public getter, repeated per query). This can degrade node latency/CPU for legitimate callers of the HTTP/gRPC/JSON-RPC endpoint targeting the affected owner address, and in aggregate across many addresses could impose meaningful load on full nodes/SR nodes serving these APIs.

### Likelihood Explanation
Feasible for any unprivileged account: it requires only (1) creating/using N distinct receiver accounts, (2) owning enough frozen V2 balance to satisfy the ≥1 TRX per-delegation minimum for each of N delegations (which can be reused/rotated across many small delegations over time or amortized via `unDelegateV2`+re-delegate cycles targeting new receivers), and (3) issuing N ordinary `DelegateResourceContract` transactions, each with a real `calcFee()` of 0. This is fully repeatable and does not require any privileged role, and the growth is monotonic and persistent absent explicit `unDelegateV2` calls for every one of the N pairs.

### Recommendation
Bound the cost of `getWithPrefix`/`getIndex`/`getV2Index` and their transitive callers:
- Add a hard cap (e.g., `prefixQueryLimit`) on the number of entries scanned/returned per prefix in `getWithPrefix`, and/or paginate the underlying `prefixQuery` call in `Chainbase`/`IRevokingDB`.
- Alternatively/additionally, enforce an upper bound on the number of distinct delegate relationships a single owner can accumulate under `V2_FROM_PREFIX`/`V2_TO_PREFIX` (e.g., validate against a max-delegatee-count in `DelegateResourceActuator.validate()`), independent of balance checks.
- Consider avoiding full in-memory `sort` over unbounded lists; if timestamp ordering is required, maintain the ordering in the storage layout instead of via a runtime full sort.

### Proof of Concept
Java unit/integration test plan:
1. `DelegatedResourceAccountIndexStoreScalingTest` (chainbase module): create N synthetic delegate entries for one owner via `store.delegateV2(owner, receiver_i, i)` for `i in 1..N`, for `N in {10, 1_000, 100_000}`. Measure wall-clock time and allocation count of `store.getV2Index(owner)` for each N using JMH or simple `System.nanoTime()` timing plus a heap-allocation profiler (e.g., `-Xss`/async-profiler), and assert that latency/allocations scale ~linearly with N with no cap (e.g., assert `time(N=100_000) / time(N=1_000) ≈ 100`, demonstrating no server-side limit).
2. Integration test extending `GetDelegatedResourceAccountIndexServletTest`/`GetDelegatedResourceAccountIndexV2ServletTest` pattern: populate the store with N=100_000 synthetic `delegateV2` entries for a fixed owner (bypassing full actuator execution for speed, since the actuator path is already proven reachable in `DelegateResourceActuatorTest.testDelegateResourceForCpu`), then issue an HTTP POST to `/wallet/getdelegatedresourceaccountindexv2` for that owner and assert the response time exceeds a normal single-digit-millisecond baseline (e.g., by an order of magnitude), confirming no server-side result-size or scan limit is enforced before reaching `DelegatedResourceAccountIndexStore.getWithPrefix`.
3. End-to-end actuator-driven variant (slower but fully realistic): loop `DelegateResourceActuator.validate()`/`execute()` N times with N distinct freshly created receiver accounts (each funded/activated) and a fixed owner with sufficient frozen V2 balance, confirming each transaction's `calcFee()` returns `0` [3](#0-2) , then repeat step 2's timing assertion against `Wallet.getDelegatedResourceAccountIndexV2`.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
