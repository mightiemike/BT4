## Title
Deposit accounting credits shares/assets using the nominal transfer amount instead of the actual tokens received — ([File: local-testing/contracts/vault/vault-sbtc.clar])

### Summary
The vault `deposit` function mints zTokens and increments the internal `assets` accounting variable based on the caller-supplied `amount` parameter, never verifying how many underlying tokens the vault actually received from `receive-underlying`. If the underlying SIP-010 asset takes any cut on transfer (fee-on-transfer, rebasing, or a proxy/upgrade to such behavior), the vault credits shares for tokens it never actually holds — the exact bug class described in the VADER report (crediting more than what the contract actually receives).

### Finding Description
`deposit` in the vault contracts computes shares from the raw `amount` argument, calls `receive-underlying`, and then unconditionally bumps the `assets` variable by that same nominal `amount`: [1](#0-0) 

`receive-underlying` simply performs the transfer and returns `(ok true)` — it never measures the vault's balance before/after to learn how many tokens actually arrived: [2](#0-1) 

So the sequence is:
1. Attacker (or any depositor) calls `deposit(amount, min-out, recipient)`.
2. `inkind` (shares to mint) is computed as `(convert-to-shares-preview amount)` — using the *nominal* `amount`, before any transfer happens.
3. `receive-underlying` transfers `amount` from the depositor to the vault. If the underlying token takes a fee/tax on transfer, the vault's actual token balance increases by `amount - fee`, not `amount`.
4. `ft-mint? zft inkind recipient` mints shares as if the full nominal `amount` had arrived.
5. `(var-set assets (+ current-assets amount))` — the internal `assets` ledger (used later by `total-assets`/`convert-to-assets-preview`/`get-available-assets` for redemption pricing) is inflated by the nominal `amount`, not the true received amount.

The value bound here is `assets` / `inkind` (shares), computed from `amount` at step 2–5. The event that should invalidate/adjust it — an actual-balance check after the transfer completes in step 3 — never happens. The later use is every subsequent `redeem` call, where `convert-to-assets-preview` and `get-available-assets` rely on the inflated `assets` ledger to compute payouts, and `send-underlying` moves real tokens out of a pool that is smaller than the ledger believes.

This is a single-transaction/single-call sequencing bug: the mutation (`ft-mint?` + `var-set assets`) is evaluated using a value bound *before* the guard/measurement that would reveal the real amount transferred (the actual post-transfer balance). Under Clarity's sequential evaluation, `receive-underlying` is `try!`'d and returns `(ok true)` regardless of how much was actually moved (SIP-010 `transfer` does not report actual amount if the token implements a fee internally while still returning success), so nothing downstream ever discovers the discrepancy.

### Impact Explanation
Every deposit into a fee-charging/rebasing underlying inflates the `assets` ledger and share supply relative to the vault's real token holdings. This permanently mis-prices `convert-to-assets-preview`/`convert-to-shares-preview` for all users, meaning some depositors' shares become backed by fewer real tokens than the accounting implies. Later redeemers can be unable to withdraw their rightful entitlement (temporary/permanent freezing of funds) once the shortfall is exposed by `available-assets`/`ERR-INSUFFICIENT-LIQUIDITY`, and the first users to redeem after the deposit effectively drain real tokens that rightfully belong to other depositors — protocol insolvency for the vault's underlying pool. This lands squarely in the in-scope "permanent freezing of funds / protocol insolvency" impact class. This applies identically to every vault variant that exhibits the same `deposit`/`receive-underlying` pattern (`vault-sbtc.clar`, `vault-ststx.clar`, `vault-ststxbtc.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-stx.clar`, and their mainnet `v0-vault-*.clar` counterparts).

### Likelihood Explanation
Likelihood depends entirely on whether any of the whitelisted underlying assets (sBTC, stSTX, stSTXbtc, USDC, USDH, or a future added asset) ever behaves as fee-on-transfer/rebasing — either natively, through a future token upgrade, or through a compromised/updated token contract (all of which are realistic for third-party SIP-010 tokens whose implementation is outside the vault's control). The vault code makes no assumption-check (e.g., balance-before/balance-after assertion) to defend against this even as a bug/regression in a token it depends on, so the vulnerability is latent and triggers automatically the moment such a token property exists, without requiring any DAO compromise or privileged action.

### Recommendation
Measure the vault's actual underlying balance immediately before and after calling `receive-underlying`, and use `(- balance-after balance-before)` — not the nominal `amount` argument — for both `convert-to-shares-preview` share minting and the `(var-set assets ...)` update. Reject/revert if the delta is less than `amount` and the difference exceeds a defined tolerance (or simply always use the actual delta), analogous to the recommended fix in the referenced report ("pre and post checks on balances to get the real amount").

### Proof of Concept
1. Deploy/point a vault (e.g. `vault-usdc.clar`) at an underlying SIP-010 token that charges a 1% fee on transfer (or simulate this by upgrading/replacing the token behind the same principal, or using a token whose `transfer` silently burns a cut, e.g., a rebasing/tax token).
2. Attacker (or a normal user) calls `deposit(amount: 1000, min-out: 0, recipient: attacker)`.
   - `inkind = convert-to-shares-preview(1000)` — since this is the first deposit, `inkind = 1000` shares.
   - `receive-underlying(1000, attacker)` transfers 1000 nominal, but the vault's real USDC balance only increases by 990 (10 taken as fee).
   - `ft-mint? zft 1000 attacker` — attacker is minted 1000 shares.
   - `(var-set assets (+ 0 1000))` — ledger says 1000 assets, but only 990 real tokens sit in the vault.
3. Attacker immediately calls `redeem(amount: 1000, min-out: 0, recipient: attacker)`. `convert-to-assets-preview(1000)` returns 1000 (1:1, ts==inkind). If `get-available-assets`/liquidity checks pass (vault may have residual liquidity from other assets/flows), `send-underlying(1000, attacker)` attempts to send 1000 real tokens out while only 990 came in — draining 10 tokens belonging to other depositors, or reverting later for the next legitimate redeemer once the shortfall is exposed, permanently freezing their funds.

Note: The exact downstream propagation of the shortfall into `get-available-assets` could not be fully confirmed in this pass (its definition lives in `protocol-data.clar`/`v0-1-data.clar`, which time ran out to inspect), but the root-cause defect — `deposit` crediting shares/assets from the pre-transfer nominal `amount` rather than the verified post-transfer balance delta — is confirmed directly in the vault source shown above.
