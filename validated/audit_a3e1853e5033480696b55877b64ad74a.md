### Title
Flat loader CU charge decoupled from `RequisiteVerifier` ELF-verification cost enables CPU-amplification DoS via crafted max-size programs - (File: `program-runtime/src/deploy.rs`, `programs/bpf_loader/src/lib.rs`)

### Summary
`deploy_program` in `program-runtime/src/deploy.rs` runs `executable.verify::<RequisiteVerifier>()` over the full uploaded ELF (up to `MAX_PERMITTED_DATA_LENGTH`), whose CPU cost scales with the number/complexity of instructions and control-flow edges being verified. This verification step, along with `Executable::load`, is charged only the fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS` (2,370 CUs) consumed unconditionally at instruction entry in `programs/bpf_loader/src/lib.rs`, so program size/complexity has no bearing on the metered cost of deployment.

### Finding Description
`process_instruction_inner` in `programs/bpf_loader/src/lib.rs` charges a fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS` (2,370 CU) via `invoke_context.compute_meter.consume_checked(...)` at the very top of loader-management instruction handling, before `process_loader_upgradeable_instruction` dispatches to `DeployWithMaxDataLen` (or `Upgrade`), regardless of what those instructions subsequently do. [1](#0-0) 

The `DeployWithMaxDataLen` handler eventually invokes the `deploy_program!` macro, which calls `deploy_program` in `program-runtime/src/deploy.rs`. That function loads the ELF via `Executable::<InvokeContext>::load` and then runs `executable.verify::<RequisiteVerifier>()` over the entire program — a step whose CPU cost is a function of the bytecode's instruction count and control-flow graph complexity, not a fixed constant. [2](#0-1) 

Because the CU charge is levied before (and independent of) this verification work, an attacker can submit a maximal-size ELF (bounded by `MAX_PERMITTED_DATA_LENGTH`) engineered to maximize `RequisiteVerifier`'s work (e.g., densely packed branch instructions, deeply nested control flow, many basic blocks) via the standard `CreateBuffer` → chunked `Write` → `DeployWithMaxDataLen` sequence (or `bpf_loader_upgradeable::upgrade`). The fixed 2,370 CU charge does not scale to compensate leader CPU time for the disproportionately expensive verification pass.

### Impact Explanation
This is a liveness/availability concern: repeated deployment or upgrade transactions using worst-case-verification ELFs let an attacker spend CU budget cheaply (fixed cost) while forcing leaders to spend CPU time disproportionate to that charge during `verify::<RequisiteVerifier>()`. At scale (e.g., packing many such deploy/upgrade instructions across a block, submitted by a single funded keypair reusing programdata/buffer accounts across slots) this could degrade leader block-production throughput relative to the CUs actually billed, corresponding to a compute/liveness degradation-class DoS rather than a funds-loss or consensus-safety issue.

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: a funded keypair, rent-exemption lamports for a buffer/programdata account, and a crafted ELF that passes `Executable::load`/`RequisiteVerifier` (i.e., a legitimate but worst-case-shaped bytecode, not a malformed one that would simply fail verification). The transaction sequence (`CreateBuffer`, chunked `Write`, `DeployWithMaxDataLen`) is standard, publicly documented deployment tooling behavior — see `cli/src/program.rs`'s `read_and_verify_elf`/`verify_elf`, which itself calls `executable.verify::<RequisiteVerifier>()` as the CLI-side check. [3](#0-2)  This is fully repeatable and requires no validator/network privileges.

### Recommendation
Scale the compute cost charged for `DeployWithMaxDataLen`/`Upgrade`/`Write` instructions (or the deployment-time verification pass specifically) to the size/complexity of the ELF being verified, rather than a single flat constant, e.g., by adding a per-byte or per-instruction-count component derived from actual `RequisiteVerifier` traversal cost, and/or capping/metering verification work directly inside `deploy_program`.

### Proof of Concept

2. In a Rust bench/unit test, directly invoke `program_runtime::deploy::deploy_program` (or `Executable::verify::<RequisiteVerifier>` alone) on both ELFs using the same `ProgramRuntimeEnvironment`, and measure wall-clock time for the `verify_code_time` phase (the crate already instruments this under the `metrics` feature as `load_program_metrics.verify_code_us`). [4](#0-3) 
3. Assert that `verify_code_us` for (b) is significantly larger (e.g., orders of magnitude) than for (a), despite both instructions being charged the identical fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS` constant defined in `programs/bpf_loader/src/lib.rs`. [5](#0-4) 
4. Optionally extend to a bank/SVM integration test that submits `CreateBuffer` → `Write` (chunked) → `DeployWithMaxDataLen` for ELF (b) and confirms the transaction succeeds while consuming only the fixed CU charge, demonstrating the CPU/CU cost mismatch end-to-end.
