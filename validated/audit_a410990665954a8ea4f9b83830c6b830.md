## Title
`TransactionOutput::ensure_match_transaction_info` silently skips checkpoint-hash verification, allowing corrupted state/hot-state/position roots to pass replay-verify and restore consistency checks - (File: types/src/transaction/mod.rs)

### Summary
The state-integrity gate `ensure_match_transaction_info` — used by `db-tool replay-on-archive`, the aptos-debugger, and CLI replay tooling to confirm that locally re-executed VM output matches the authenticated `TransactionInfo` recorded in the ledger — only checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`. It never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which is explicitly acknowledged in a `TODO` comment in the code itself.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  is the authoritative comparator between locally recomputed `TransactionOutput` and the committed, accumulator-authenticated `TransactionInfo`. It validates transaction status, gas used, write-set hash (`state_change_hash`), and event root hash, but the code contains this explicit acknowledgment: [2](#0-1) 

This comparator ignores the checkpoint hashes — `state_checkpoint_hash` (Sparse Merkle Tree / JMT root at checkpoint boundaries), `hot_state_checkpoint_hash` (gated by `HOT_STATE_ROOT_IN_TXN_INFO`), and `position_state_checkpoint_hash` (gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) — none of which are cross-checked against the locally recomputed state summary.

This function is invoked directly by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which is the core loop of the `replay-verify` tool used to validate mainnet/testnet archives: [3](#0-2) 

It is also used by `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` for similar replay-verification purposes.

The state-checkpoint hash is exactly the value that must match between the committed `TransactionInfo` and re-execution to prove that the persisted Jellyfish Merkle Tree state actually reflects VM output — it is the mechanism by which `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are threaded through `DoStateCheckpoint::run` and `DoLedgerUpdate::run` into the accumulator-committed `TransactionInfoV1`: [4](#0-3) [5](#0-4) 

Because `ensure_match_transaction_info` never re-derives and compares these checkpoint roots, replay-verify tooling can report a transaction range as a "successful replay" even when:
1. The persisted state-checkpoint (SMT/JMT) root diverges from what the VM output should produce.
2. Once `HOT_STATE_ROOT_IN_TXN_INFO` or `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are turned on (both permanent-lifetime feature flags per `aptos-move/framework/move-stdlib/sources/configs/features.move` lines 949-961), a bug in hot-state or native-position root computation that produces a wrong `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` — silently written into `TransactionInfoV1` and consensus-committed to the ledger accumulator — would go completely undetected by the tool whose entire purpose is to catch exactly this class of divergence.

This mirrors the structure of the seed bug: a security-critical field (the composed cross-chain message / here, the checkpoint root) is conditionally excluded from an otherwise-authoritative code path (the `unwrap`-gated composer / here, the verifier), defeating the very guarantee the mechanism exists to provide.

### Impact Explanation
This does not itself cause the wrong state to be committed by validators (block-executor commit path independently derives `state_checkpoint_hash` and includes it in `TransactionInfoV1`, which participates in the ledger accumulator and is signed by validators through normal consensus). The direct impact is on **the integrity tooling that is supposed to catch state-commitment corruption after the fact**: `replay-verify`, `aptos-debugger`, and CLI replay commands are Aptos's primary defense mechanism for detecting non-determinism or state-root corruption bugs across historical mainnet data before they are exploited or before hard-fork decisions are made. If a state-checkpoint-root computation bug exists anywhere in the JMT/hot-state/position-state pipeline (all newly introduced, feature-flagged, permanent-lifetime code paths), this verifier will not flag it, allowing a corrupted committed root to be treated as verified/trusted. Given that `HOT_STATE_ROOT_IN_TXN_INFO` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are being rolled out as consensus-verified permanent features, an undetected divergence here would blind operators to a genuine state-integrity bug in production, satisfying "hard-fork-only divergence during ... replay ... proof verification" from the impact list.

### Likelihood Explanation
Likelihood is moderate: this is not remotely triggerable by an unprivileged attacker to directly corrupt state, but it is a real, currently-present gap (confirmed by the developers' own inline TODO) in code that will become load-bearing the moment `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet (the comment explicitly says: "Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"). Since the feature is already merged and the gate is a "TODO" rather than a design decision, the risk is latent but concrete — any independent bug in the new hot-state/position-state root computation is currently guaranteed to escape replay-verify detection.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values embedded in `txn_info` whenever they are present, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and ideally before broader `HOT_STATE_ROOT_IN_TXN_INFO` rollout) on mainnet, per the code's own inline TODO at [6](#0-5) .

### Proof of Concept
Not directly exploitable as a standalone PoC by an external attacker — this is a gap in an internal verification tool, not a consensus-path bug. Conceptual reproduction:
1. Introduce (hypothetically, or via a genuine bug) a discrepancy between the locally recomputed state-checkpoint/hot-state/position-state root and the one recorded in a historical `TransactionInfoV1` on an archive.
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify` at lines 388-406) over that version range.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` despite the checkpoint-hash mismatch, because it only inspects `status`, `gas_used`, `state_change_hash`, and `event_root_hash` — never `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` — confirming the verification gap exists exactly as documented in the code's own TODO.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
