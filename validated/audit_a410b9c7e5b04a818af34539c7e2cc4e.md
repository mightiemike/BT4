### Title
Unauthorized destruction of delegated/frozen TRX resources via CREATE2 address collision with pre-funded account - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.createContractImpl` (via the `isContractExist` gate) decides whether a pre-existing account occupying a predicted CREATE2 address should have its state reset when a contract is deployed there. When that pre-existing account has resources delegated to it (via `DelegateResourceContract`), the reset path calls `existingAccount.clearDelegatedResource()` without reversing the corresponding entries in `DelegatedResourceStore` / `DelegatedResourceAccountIndexStore`, destroying the delegator's frozen TRX-backed resource allocation instead of returning it.

### Finding Description
`Program.java` contains both the `isContractExist` check and the call to `clearDelegatedResource()` used during contract creation [1](#0-0) . `AccountCapsule.clearDelegatedResource()` mutates the account's delegated-resource bookkeeping fields (acquired/delegated bandwidth and energy) directly on the `AccountCapsule` object [2](#0-1) . Because CREATE2 addresses are deterministically derivable before deployment (`keccak256(0xff, sender, salt, init_code_hash)`), an attacker or third party can pre-fund/pre-delegate resources to a predicted victim contract address using an unprivileged `DelegateResourceContract` transaction. When the victim later deploys to that address, `createContractImpl` detects the account already exists and, per the described gate logic, resets the account's delegation-related fields to prepare it for contract use — but this reset only touches the in-memory/committed `AccountCapsule` fields, not the separate `DelegatedResourceStore` entry (which still records the original delegator → this address delegation) or the `DelegatedResourceAccountIndexStore` index. This produces an inconsistency between the account's resource counters (zeroed) and the store's delegation record (still present, now pointing at a contract account that cannot claim/undelegate the resource in the expected way), effectively orphaning the frozen TRX backing that delegation. No existing check (`TransactionCapsule.validateSignature`, actuator `validate()`, energy/bandwidth accounting, `ForkController` gates) inspects whether a target CREATE2 address has outstanding delegated-resource records before allowing account-state clearing during contract creation.

### Impact Explanation
This maps to an "asset/accounting corruption" / unauthorized destruction of value class of impact: a third party's frozen TRX-backed bandwidth/energy delegation to an address can be silently orphaned/destroyed as a side effect of a completely unrelated party's contract deployment, with no path to reclaim or undelegate the frozen TRX. This is a real fund-safety issue distinct from griefing, since the delegator never authorized or could anticipate contract deployment at that address.

### Likelihood Explanation
The attack requires only unprivileged actions available to any funded account: (1) knowledge of a to-be-deployed contract's deployer address, salt, and init code (all derivable from public mempool/broadcast data before the CREATE2 deployment transaction is mined, or simply chosen by an attacker who controls the target salt indirectly, e.g. front-running), and (2) a standard `DelegateResourceContract` transaction to the predicted address. This is inexpensive (only requires enough frozen TRX to delegate) and repeatable against any CREATE2 deployment whose target address can be predicted ahead of confirmation.

### Recommendation
Before clearing an existing account's delegated-resource fields in the CREATE2 collision path of `createContractImpl`, check `DelegatedResourceStore` for outstanding delegation entries pointing at the target address; if present, either (a) reject/defer contract creation until delegations are unwound, or (b) programmatically reverse the delegation (return frozen balance and bandwidth/energy to the original delegator, remove `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` entries) atomically with the `clearDelegatedResource()` call so no value is destroyed without being credited back.
