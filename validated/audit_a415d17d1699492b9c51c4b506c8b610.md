Based on my investigation, I found a genuine local integrity break, but I could not fully verify all the invariants needed to confirm it's exploitable end-to-end (see caveats below).

### Title
`WriteSet::add_hotness` can silently drop hot-state data on the V0 variant without affecting the write-set hash - ([File: types/src/write_set.rs])

### Summary
`WriteSetV0` marks its `hotness` and `extensions` fields with `#[serde(skip)]` [1](#0-0) , on the stated assumption that these fields are always empty for the V0 variant and only meaningfully populated on `WriteSetV1` [2](#0-1) . However, `WriteSet::add_hotness` is implemented generically over both enum variants via `hotness_mut()`, which returns a mutable reference into `WriteSetV0::hotness` just as readily as into `WriteSetV1::hotness` [3](#0-2) [4](#0-3) . Nothing in `add_hotness` enforces that the receiver is a `V1` variant.

### Finding Description
If `add_hotness` (or the equivalent `add_native_positions`, which pushes into `extensions`, also `#[serde(skip)]` on V0) is ever called on a `WriteSet::V0` value instead of one that has first been converted via `into_v1()`, the hotness/extension data is written into memory fields that are structurally excluded from BCS serialization. Consequences:
- `encode_value` (`ValueCodec<WriteSetSchema>::encode_value`, which calls `bcs::to_bytes(self)`) [5](#0-4)  will silently omit the hotness/extension content from the persisted bytes — the data never reaches disk.
- The `BCSCryptoHash` derived for `WriteSet` [6](#0-5)  is computed over the same BCS-serialized bytes, so the write-set hash embedded in `TransactionInfo` is computed as if hotness/extensions were empty — even though the in-memory value used elsewhere in the same execution pipeline (e.g. for building the block epilogue's hot-state promotion set) is non-empty.

This creates a divergence between what execution "intends" to commit (the populated hotness/extension state) and what is actually hashed/persisted (empty), which is exactly the same *root-cause class* as the seed report: a code path silently substitutes a default/empty value in place of the real state under specific conditions, and that default is what ends up bound into the authenticated/committed artifact.

### Impact Explanation
If reachable on the V0 path, this would mean: (a) hot-state promotion metadata computed by the executor is dropped without error, causing the persisted `WriteSet` to diverge from the value actually used to update in-memory execution state, and (b) the `TransactionInfo.write_set_hash` no longer commits to the real content, which could mask this divergence from proof verification. This matches the "committed state differs from correct VM result" and "authenticated hash bound to wrong content" impact categories in the gate.

### Likelihood Explanation
I could **not confirm** that any current call site actually invokes `add_hotness`/`add_native_positions` on a `WriteSet::V0` without first calling `into_v1()`. My tool budget was exhausted before I could fully trace `execution/executor/src/workflow/do_get_execution_output.rs` (the one call site found) and the feature-flag-gated `HOTNESS_IN_EPILOGUE` path to verify whether the executor always converts to `V1` before calling `add_hotness`, or whether some code path (e.g., tests, or a legacy/disabled-feature branch) calls it directly on a freshly-constructed `V0` value. The doc comments in `types/src/write_set.rs` strongly suggest the invariant "hotness/extensions only meaningful under V1" is intended to be enforced by callers, not by the type system — which is inherently fragile and exactly the kind of implicit invariant that regressed in the curve-stablecoin analog (an unenforced assumption about when a fallback/default path is safe).

### Recommendation
- Make `add_hotness` and `add_native_positions` only callable on `WriteSetV1` (e.g. move them to be inherent methods on `WriteSetV1` only, or have `add_hotness`/`add_native_positions` internally call `self = self.clone().into_v1()` before mutating, guaranteeing the data is never written to a variant that serde will skip).
- Add a debug assertion / runtime check that `WriteSetV0::hotness` and `WriteSetV0::extensions` are always empty at serialization or hashing time, so any violation fails loudly instead of silently dropping data.
- Add a unit test that calls `add_hotness` on a `WriteSet::V0` and asserts the hotness survives an `encode_value`/`decode_value` round trip and is reflected in `CryptoHash::hash()`.

### Proof of Concept
```rust
// Conceptual PoC (not run — construct in a test within types/src/write_set.rs or its test module)
let mut ws = WriteSet::V0(WriteSetV0::default()); // still V0
ws.add_hotness([StateKey::raw(b"hot1")].into_iter().collect()); // succeeds: hotness_mut() matches V0 too
let hash_before = ws.hash(); // CryptoHash over bcs bytes

let bytes = bcs::to_bytes(&ws).unwrap();
// bytes omit `hotness` entirely because WriteSetV0::hotness is #[serde(skip)]
let decoded: WriteSet = bcs::from_bytes(&bytes).unwrap();
assert!(decoded.hotness_keys().next().is_none()); // hotness silently lost
assert_eq!(decoded.hash(), hash_before); // hash unaffected by whether hotness was ever set
```

**Caveat / uncertainty:** I was not able to confirm within my available budget whether production code ever actually calls `add_hotness`/`add_native_positions` on a `WriteSet::V0` value in practice (the one call site I found, in `execution/executor/src/workflow/do_get_execution_output.rs`, was not fully traced to confirm it always operates on an already-`into_v1()`-converted value). If that call site (and all others) always converts to `V1` first, this is a latent/defensive-programming issue rather than an actively triggered one, and would not meet the "exact corrupted value + reachable trigger" bar required by the gate. I recommend a Devin session with full-repo access to trace all `add_hotness`/`add_native_positions` call sites and the `HOTNESS_IN_EPILOGUE` feature-gated code path to confirm reachability before treating this as a confirmed high/critical finding.
