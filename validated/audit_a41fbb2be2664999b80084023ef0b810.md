### Title
JSON-RPC batch requests bypass per-endpoint/IP rate limiting, allowing throughput amplification DoS - (File: framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java)

### Summary
`RateLimiterServlet.service()` gates only the outer HTTP request (one `acquirePermit()` call per POST) before delegating to `JsonRpcServlet.doPost()`, but `doPost()` accepts a JSON array (batch) of up to `jsonRpcMaxBatchSize` sub-requests and executes each one via `rpcServer.handleRequest()` inside `handleBatch()` without any additional per-call rate limiting. An attacker can therefore execute `jsonRpcMaxBatchSize` RPC method invocations for the cost of a single rate-limited HTTP request.

### Finding Description
The rate limiting flow is: `RateLimiterServlet.service()` calls `rateLimiter.acquirePermit(runtimeData)` (per-endpoint, e.g. `DefaultBaseQqsAdapter`/`QpsRateLimiterAdapter`) and then `GlobalRateLimiter.acquirePermit(runtimeData)` (global + per-IP QPS), both counted once per HTTP request [1](#0-0) . After these checks pass, `super.service()` is invoked, which eventually reaches `JsonRpcServlet.doPost()` [2](#0-1) .

`doPost()` parses the request body and, if it is a JSON array, treats it as a batch request, only checking against `parameter.getJsonRpcMaxBatchSize()` for the array size (a size cap, not a rate cap) [3](#0-2) . `handleBatch()` then loops over every sub-request and calls `rpcServer.handleRequest()` for each one, fully executing each JSON-RPC method with no additional acquisition of any rate limiter permit [4](#0-3) .

This means the per-endpoint/IP QPS limiters, tuned assuming "1 request = 1 RPC call," are defeated: a single permitted HTTP POST can smuggle up to `jsonRpcMaxBatchSize` real RPC invocations, each of which can be a moderately expensive call (e.g., `eth_call`, `eth_getLogs`, `eth_estimateGas`) that consumes node CPU/DB resources. No code path in `handleBatch()` re-checks `GlobalRateLimiter` or the per-endpoint `IRateLimiter` for each sub-request, so the accounting is bypassed by construction.

### Impact Explanation
This is a DoS via RPC-API: the effective RPC-call throughput an attacker can drive is amplified by a factor of up to `jsonRpcMaxBatchSize` relative to the configured `http_` QPS/IP-QPS limiter intent, allowing resource exhaustion (CPU, DB read load, thread pool saturation) on a full/JSON-RPC node while nominally staying within the configured outer-request rate limit. This does not lead to consensus divergence, fund loss, or key disclosure — it is a resource-exhaustion / rate-limiter-bypass issue scoped to the JSON-RPC service.

### Likelihood Explanation
Exploitability requires no privileged access — any anonymous client that can reach the JSON-RPC HTTP endpoint can send batched arrays, which is standard JSON-RPC 2.0 behavior explicitly supported by `handleBatch()`. The severity depends entirely on node configuration: `jsonRpcMaxBatchSize` and the QPS values are operator-configured (via `Args`/`CommonParameter`), so the amplification factor scales with whatever batch size is allowed. If an operator sets a large batch size while relying on the per-request QPS number as their capacity-planning assumption, the bypass is fully repeatable at will and costs the attacker nothing beyond normal HTTP requests (JSON-RPC reads are not fee-metered by TRON's bandwidth/energy accounting since they're off-chain queries, not broadcast transactions).

### Recommendation
Meter batch sub-requests against the rate limiter, not just the outer HTTP request. Concretely, in `JsonRpcServlet.doPost()` (or `handleBatch()`), either: (1) require the caller to acquire additional permits from the per-endpoint `IRateLimiter` / `GlobalRateLimiter` for each sub-request in the batch (e.g., loop `acquirePermit()` calls, failing fast with `EXCEED_LIMIT` if unavailable), or (2) weight the single outer permit acquisition by the batch size (e.g., treat batch cost as N acquire calls before processing), or (3) lower the effective concurrent per-IP throughput by capping `jsonRpcMaxBatchSize` in proportion to configured QPS so a batch cannot exceed the intended per-window RPC-call budget.

### Proof of Concept
Request-level PoC (assuming `jsonRpcMaxBatchSize` = 100 and JsonRpcServlet's configured QPS = 10/s):
```
POST /jsonrpc HTTP/1.1
Content-Type: application/json

[
  {"jsonrpc":"2.0","id":1,"method":"eth_getLogs","params":[{"fromBlock":"0x0","toBlock":"latest"}]},
  {"jsonrpc":"2.0","id":2,"method":"eth_getLogs","params":[{"fromBlock":"0x0","toBlock":"latest"}]},
  ... (100 entries total)
]
```
Expected (per rate-limiter intent): at most 10 RPC calls processed per second.
Observed (per code path traced above): `RateLimiterServlet.service()` consumes exactly one permit for this POST, then `handleBatch()` executes all 100 `eth_getLogs` calls synchronously in the loop at lines 181-224 of `JsonRpcServlet.java`, so sending 10 such batched POSTs per second yields 1000 executed RPC calls/second — a 100x amplification over the configured 10 QPS cap.   private void handleBatch(HttpServletResponse resp, JsonNode rootNode, int maxResponseSize)
      throws IOException {

    ArrayNode batchResult = MAPPER.createArrayNode();
    int accumulatedSize = 2; // "[]"
    boolean overflow = false;

    for (int i = 0; i < rootNode.size(); i++) {
      JsonNode subRequest = rootNode.get(i);

      if (overflow) {
        if (!subRequest.isObject()) {
          batchResult.add(buildErrorNode(JsonRpcError.INVALID_REQUEST, "Invalid Request", null));
        } else if (subRequest.has("id")) {
          // Notifications (no "id") do not get a response even on overflow.
          batchResult.add(buildErrorNode(JsonRpcError.RESPONSE_TOO_LARGE,
              "Response exceeds the limit of " + maxResponseSize + " bytes",
              subRequest.get("id")));
        }
        continue;
      }

      if (!subRequest.isObject()) {
        ObjectNode errNode = buildErrorNode(JsonRpcError.INVALID_REQUEST, "Invalid Request", null);
        byte[] errBytes = MAPPER.writeValueAsBytes(errNode);
        int addition = errBytes.length + (!batchResult.isEmpty() ? 1 : 0);
        if (maxResponseSize > 0 && accumulatedSize + addition > maxResponseSize) {
          overflow = true;
        } else {
          accumulatedSize += addition;
        }
        batchResult.add(errNode);
        continue;
      }

      byte[] subBody;
      try {
        subBody = MAPPER.writeValueAsBytes(subRequest);
      } catch (JsonProcessingException e) {
        writeJsonRpcError(resp, JsonRpcError.INTERNAL_ERROR, "Internal error", null, true);
        return;
      }

      ByteArrayOutputStream subOutput = new ByteArrayOutputStream();
      try {
        rpcServer.handleRequest(new ByteArrayInputStream(subBody), subOutput);
      } catch (RuntimeException e) {
        logger.error("RPC execution failed for batch sub-request {}", i, e);
        writeJsonRpcError(resp, JsonRpcError.INTERNAL_ERROR, "Internal error", null, true);
        return;
      }
