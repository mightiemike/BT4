### Title
Missing parent-tenure identity check in the `Extended`-cause branch of `check_nakamoto_tenure` allows a tenure-extend block to claim a different, already-finished tenure than its real parent tenure - (File: `stackslib/src/chainstate/nakamoto/tenure.rs`)

### Summary
`NakamotoChainState::check_nakamoto_tenure` explicitly cross-checks `parent_tenure.tenure_id_consensus_hash == tenure_payload.prev_tenure_consensus_hash` for the `BlockFound` cause, but for the `Extended`/`ExtendedRuntime`/`ExtendedReadCount`/`ExtendedReadLength`/`ExtendedWriteCount`/`ExtendedWriteLength` causes it only checks the payload's own internal self-consistency (`tenure_payload.tenure_consensus_hash == tenure_payload.prev_tenure_consensus_hash`) and never compares either field against `parent_tenure.tenure_id_consensus_hash`, which is derived from the actual `parent_block_id` via `get_ongoing_tenure`.

### Finding Description
The equality that must hold for all causes is:

`parent_tenure.tenure_id_consensus_hash == tenure_payload.tenure_consensus_hash` (equivalently `== prev_tenure_consensus_hash` for extend-type causes, since those two payload fields are required to be equal).

In `check_nakamoto_tenure`:
- For `TenureChangeCause::BlockFound`, this identity is enforced directly against the fetched `parent_tenure`: [1](#0-0) 
- For the `Extended*` causes, the corresponding `match` arm only re-checks the payload against itself, never against `parent_tenure`: [2](#0-1) 

`parent_tenure` is fetched earlier from the real `block_header.parent_block_id` via `get_ongoing_tenure`: [3](#0-2) 

and the function unconditionally returns this `parent_tenure` as the "processed tenure" regardless of cause: [4](#0-3) 

The upstream checks (lines 660-750) only validate that `tenure_consensus_hash`/`prev_tenure_consensus_hash` name a *canonical, sortition-having* burnchain consensus hash (`X`) with consistent burn-height ordering relative to `burn_view_consensus_hash`; none of them tie `X` to the tenure that the block's actual `parent_block_id` (in tenure `Y`) belongs to: [5](#0-4) 

So an attacker can craft an Extended-cause block whose `parent_block_id` chains onto tenure `Y`'s tip, while `tenure_payload.tenure_consensus_hash == tenure_payload.prev_tenure_consensus_hash == X` (a distinct, already-finished tenure), and pass every check in this function as long as `X` is canonical, has had a sortition, and `previous_tenure_blocks` is set to match `get_nakamoto_tenure_length(parent_block_id)` (Y's block count) at line 812-824.

### Impact Explanation
`advance_nakamoto_tenure` (called after this check) consumes `tenure_payload` directly — not the corrected `parent_tenure` returned by `check_nakamoto_tenure` — when persisting tenure-change/tenure-extend records, so the attacker-controlled `tenure_consensus_hash = X` can be written into the tenure-change ledger despite the block actually chaining from `Y`. This is consistent with the audit's claimed impact: a finished tenure `X` gets silently reopened/extended under a live parent `Y`, corrupting the tenure/coinbase bookkeeping that downstream reward and tenure-accounting logic relies on. I was unable to fully trace the remainder of `advance_nakamoto_tenure` (visibility cut off) to confirm the exact on-disk record written, which is a gap in verification; however, the missing cross-check itself is directly confirmed in the code shown above and is a real asymmetry between the `BlockFound` and `Extended` branches.

### Likelihood Explanation
Exploitation requires the attacker to actually produce a validly-signed block whose header `consensus_hash` equals `X`'s consensus hash (satisfying the `block_header.consensus_hash == tenure_payload.tenure_consensus_hash` check at line 660) while its `parent_block_id` points into a structurally later/different tenure `Y`'s chain. Producing a header with `consensus_hash = X` generally requires having been a legitimate participant/winner of tenure `X`'s sortition (an unprivileged, single-miner-slot capability is plausible if the same entity won both `X` and a later `Y`, or via replay of an old signed artifact), so this is within the stated unprivileged attacker capability (their own miner slot/BTC), not requiring majority stake. Whether other layers of block-processing (outside this function) additionally pin `block_header.consensus_hash` to the currently-active sortition tip before this function is even reached is not confirmed from the code reviewed, which affects real-world feasibility.

### Recommendation
Add an explicit check in the `Extended*` match arm mirroring the `BlockFound` arm: require `parent_tenure.tenure_id_consensus_hash == tenure_payload.tenure_consensus_hash` (equivalently `== prev_tenure_consensus_hash`) before falling through, e.g.:
```rust
TenureChangeCause::Extended | ... => {
    if tenure_payload.tenure_consensus_hash != tenure_payload.prev_tenure_consensus_hash
        || parent_tenure.tenure_id_consensus_hash != tenure_payload.tenure_consensus_hash
    {
        warn!(...);
        return Ok(None);
    }
}
```

### Proof of Concept
Rust integration test plan (chainstate harness):
1. Build a two-tenure chain: process tenure `X` to completion (`BlockFound` tenure-change, at least one block), then process tenure `Y` (a distinct `BlockFound` tenure-change) with one prior `Extended` tenure-change already applied to `Y`, so `Y`'s tip block `parent_block_id = P` resides in tenure `Y`.
2. Craft a `NakamotoBlockHeader` with `parent_block_id = P`, `consensus_hash = X`.
3. Craft `TenureChangePayload` with `tenure_consensus_hash = X`, `prev_tenure_consensus_hash = X`, `cause = TenureChangeCause::Extended`, `previous_tenure_end = P`, `previous_tenure_blocks = get_nakamoto_tenure_length(P)` (Y's actual block count so far), `burn_view_consensus_hash` = current canonical tip.
4. Call `NakamotoChainState::check_nakamoto_tenure(&mut headers_conn, &mut sort_handle, &header, &payload)`.
5. Assert: **before fix**, the call returns `Ok(Some(parent_tenure))` where `parent_tenure.tenure_id_consensus_hash == Y`, even though `tenure_payload.tenure_consensus_hash == X != Y` — i.e., assert `parent_tenure.tenure_id_consensus_hash != tenure_payload.tenure_consensus_hash` yet the function still returns `Some(..)`, demonstrating the missing equality check.
6. **After fix**, assert the call returns `Ok(None)`.
