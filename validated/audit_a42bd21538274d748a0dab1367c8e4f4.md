### Title
Ancient-slot squash silently discards zero-lamport tombstones instead of carrying them forward - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`AccountsDb::combine_ancient_slots_packed` "merges" (squashes) multiple ancient-slot append vecs into fewer, larger append vecs — analogous to `CollateralPool.merge` combining two pools. Just as the collateral-pool bug dropped the child pool's withdrawal limits when funds were transferred to the parent, the ancient-squash write path drops each source slot's zero-lamport "tombstone" records when their accounts are repacked into a new storage, relying only on a `debug_assert!` (a no-op in release builds) instead of enforcing/propagating the invariant.

### Finding Description
When a normal (non-ancient) slot is shrunk, `shrink_collect` computes `tombstones_to_carry_forward`: zero-lamport, single-ref accounts whose index entry was dropped, but whose on-disk record must be rewritten into the new storage as a "tombstone" if the slot is still newer than `latest_full_snapshot_slot` — otherwise an incremental snapshot could fail to propagate the deletion of that account: [1](#0-0) 

`shrink_storage` (the normal shrink path) correctly writes these carried-forward tombstones into the new storage via `store_tombstones`: [2](#0-1) 

However, the ancient-squash "merge" path (`calc_accounts_to_combine` → `write_packed_storages` → `finish_combine_ancient_slots_packed_internal`) calls the exact same `shrink_collect` function to gather each source slot's accounts, which populates `tombstones_to_carry_forward` identically: [3](#0-2) 

But `write_packed_storages` / `write_one_packed_storage` / `PackedAncientStorage::pack` only ever consume `alive_accounts.one_ref` / `many_refs_this_is_newest_alive` accounts (via `PackedAncientStorage::pack`), never `tombstones_to_carry_forward`. The finishing routine explicitly acknowledges this gap, but only guards it with a `debug_assert!`, not a real safeguard: [4](#0-3) 

The comment states the assumption that ancient squash "only runs on slots far older than the latest full snapshot, where tombstones are purgeable," so this "should never" have a non-empty `tombstones_to_carry_forward` list. This is precisely the unchecked-invariant pattern described in the report: instead of transferring the withdrawal-limit-equivalent state (the tombstone) from the "child" (source slot being merged/shrunk away) to any surviving state, the code assumes it will always be empty and, if that assumption is wrong, the tombstone bytes are simply never written and the slot's storage is dropped by `remove_old_stores_shrink`, permanently and silently losing the tombstone.

### Impact Explanation
If ancient squash ever processes a slot that is not yet older than `latest_full_snapshot_slot` (e.g., due to a large ancient-slot backlog, aggressive ancient-append-vec settings, or timing where `max_ancient_slots`/`shrink_ancient_stats` selection picks a slot before it crosses `can_purge_zero_lamport_single_ref_after_shrink`), the zero-lamport tombstone for a previously-deleted account is dropped instead of being carried into the new packed storage. Consequences:
- An incremental snapshot taken afterward would no longer contain the deletion marker for that account, so a node restoring from that incremental snapshot could see a stale (resurrected) non-zero balance for an account that should read as deleted/zero — a concrete "stale account load" / "silent balance change" scenario.
- On a snapshot generated after this loss, this could also manifest as an accounts lt-hash / capitalization mismatch relative to a node that never dropped the tombstone, i.e. an honest-node snapshot-vs-replay divergence.

### Likelihood Explanation
The safeguard is only a `debug_assert!`, which is compiled out in release validator builds — the exact configuration used in production. The code comment itself flags this as an assumption rather than an enforced guarantee ("Ancient squash only runs on slots far older than the latest full snapshot… The squash write path has no tombstone handling"). Whether the precondition can actually be violated in practice depends on internal ancient-slot selection heuristics (`collect_sort_filter_ancient_slots`, `max_ancient_storages`, epoch-based ancient threshold) that were not fully verified in this pass — I could not fully confirm within this investigation whether the "epoch-old" ancient threshold guarantees the slot is always past `latest_full_snapshot_slot` in all configurations (e.g., custom `--full-snapshot-interval-slots`, snapshots disabled then re-enabled, or minimal snapshot testing configs). This is the main remaining uncertainty.

### Recommendation
Do not rely on a `debug_assert!` to enforce that `tombstones_to_carry_forward` is empty during ancient squash. Either:
1. Make `write_packed_storages`/`PackedAncientStorage::pack` tombstone-aware, writing any carried-forward tombstones into the destination packed storage the same way `shrink_storage` does via `store_tombstones`, or
2. Explicitly exclude ancient slots that are not yet purgeable (`!can_purge_zero_lamport_single_ref_after_shrink(slot)`) and still hold pending tombstones from ancient-squash candidacy, with a hard (non-debug) check, so slots requiring tombstone carry-forward are never selected for the write-only-alive-accounts ancient squash path.

### Proof of Concept
Not independently reproduced against a running validator in this investigation (index-only analysis). The existing unit test `test_shrink_collect_carries_forward_existing_tombstones` demonstrates that `shrink_collect` legitimately produces non-empty `tombstones_to_carry_forward` when a slot is newer than `latest_full_snapshot_slot`: [5](#0-4) 
A PoC would extend this by constructing a similar zero-lamport tombstone scenario in a slot that also becomes an ancient-squash candidate (e.g., forcing `max_ancient_storages`/aging so `combine_ancient_slots_packed_internal` selects that slot) while `latest_full_snapshot_slot` is still behind it, then asserting the tombstone bytes are absent from the resulting packed storage and that a follow-on incremental snapshot fails to reflect the deletion — this final construction/execution was not completed here due to iteration limits.

#[test]
fn test_shrink_collect_carries_forward_existing_tombstones() {
    let accounts_db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    let slot = 2;
    // Latest full snapshot older than `slot`: tombstones are not yet purgeable.
    accounts_db.set_latest_full_snapshot_slot(slot - 1);

    let alive_pubkey = Pubkey::new_unique();
    let tombstone_pubkey = Pubkey::new_unique();
    let alive_account = AccountSharedData::new(1, 0, &Pubkey::default());
    let zero_lamport_account = AccountSharedData::new(0, 0, &Pubkey::default());

    let (_temp_dirs, paths) = get_temp_accounts_paths(1).unwrap();
    let storage = Arc::new(AccountStorageEntry::new(
        &paths[0],
        slot,
        100,
        DEFAULT_FILE_SIZE,
        accounts_db.accounts_file_provider,
    ));
    // An ordinary alive account, present in the index.
    append_single_account_with_default_hash(
        &storage,
        &alive_pubkey,
        &alive_account,
        true,
        Some(&accounts_db.accounts_index),
    );
    // A zero-lamport account physically in the storage but NOT in the index: i.e. a tombstone
    // carried forward by a prior shrink of an even-older storage.
    append_single_account_with_default_hash(
        &storage,
        &tombstone_pubkey,
        &zero_lamport_account,
        true,
        None,
    );
    accounts_db.storage.insert(Arc::clone(&storage));
    accounts_db.add_root(slot);

    // Record the tombstone account's offset on the storage's tombstone list, as a prior shrink
    // would have.
    let mut tombstone_offset = None;
    storage
        .accounts
        .scan_accounts_without_data(|offset, account| {
            if account.pubkey == &tombstone_pubkey {
                tombstone_offset = Some(offset);
            }
        })
        .unwrap();
    storage.batch_insert_tombstone_offsets([tombstone_offset.unwrap()]);
    assert_eq!(storage.num_zero_lamport_single_ref_accounts(), 1);

    // Newer than the latest full snapshot: the tombstone must be carried forward, not dropped and
    // not mis-routed into the alive set.
    let mut unique_accounts =
        accounts_db.get_unique_accounts_from_storage_for_shrink(&storage, &ShrinkStats::default());
    let shrink_collect = accounts_db.shrink_collect::<AliveAccounts<'_>>(
        &storage,
        &mut unique_accounts,
        &ShrinkStats::default(),
    );
    assert_eq!(shrink_collect.tombstones_to_carry_forward.len(), 1);
    assert!(shrink_collect.tombstones_total_bytes > 0);
    assert_eq!(
        shrink_collect
            .alive_accounts
            .accounts
            .iter()
            .map(|account| *account.pubkey())
            .collect::<Vec<_>>(),
        vec![alive_pubkey],
    );

    // Once the full snapshot advances to `slot`, the tombstone is purgeable and must be dropped
    // rather than carried forward.
    accounts_db.set_latest_full_snapshot_slot(slot);
    let mut unique_accounts =
        accounts_db.get_unique_accounts_from_storage_for_shrink(&storage, &ShrinkStats::default());
    let shrink_collect = accounts_db.shrink_collect::<AliveAccounts<'_>>(
        &storage,
        &mut unique_accounts,
        &ShrinkStats::default(),
    );
    assert!(shrink_collect.tombstones_to_carry_forward.is_empty());
    assert_eq!(shrink_collect.tombstones_total_bytes, 0);
}
