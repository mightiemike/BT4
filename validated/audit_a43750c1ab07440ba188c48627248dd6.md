### Title
Zero-address deposit recipient bypasses `failedDepositVault` safety net, permanently burning minted cBTC - (File: `crates/evm/src/evm/system_contracts/src/Bridge.sol`)

### Summary
`Bridge.deposit()` extracts a 20-byte recipient address straight from the Bitcoin witness script via `extractRecipientAddress()` and sends `depositAmount` of native cBTC to it with a low-level `call`. There is no check that this address is non-zero. Because a `call{value:x}("")` to `address(0)` (an account with no code) always returns `success == true`, the intended safety mechanism — redirecting funds to `failedDepositVault` when the transfer "fails" — is never triggered for a zero-address recipient. The cBTC is instead sent to `address(0)` and is permanently and irrecoverably lost, exactly mirroring the reported class of bug where a missing `address(0)` guard silently swallows a transfer that should have reverted or redirected.

### Finding Description
`extractRecipientAddress()` performs no validation on the parsed address: [1](#0-0) 

`deposit()` then uses this unchecked value as the transfer target and only falls back to `failedDepositVault` if the low-level call itself returns `false`: [2](#0-1) 

A `call` with value to `address(0)` (or any codeless address) always succeeds at the EVM level — there is no code to revert. So when the recipient encoded in the deposit script is `address(0)`, `success` is `true`, the `Deposit` event fires as if everything worked, and the `depositAmount` of freshly minted cBTC is sent to `address(0)`, where it can never be moved, spent, or recovered by anyone (not even via `failedDepositVault`, which exists specifically to preserve funds when delivery to the recipient is not possible).

This is the same root cause as the reported `SEuroOffering.transferCollateral()` bug: a destination address of `address(0)` is treated as a "normal" success path instead of being explicitly guarded against, so value that should be protected (via a `require`/fallback) is instead silently consumed by the zero address.

### Impact Explanation
This directly breaks the "cBTC credited versus a Bitcoin deposit that actually happened" binding: a valid, verified Bitcoin-side deposit (proven via `LIGHT_CLIENT.verifyInclusion` and the N-of-N Schnorr signature) results in the corresponding cBTC being permanently destroyed rather than credited to the depositor or safely quarantined in `failedDepositVault`. This is a Critical-severity "funds permanently frozen" outcome, since the burned cBTC can never be recovered and the depositor never receives their bridged BTC value.

### Likelihood Explanation
The recipient address is embedded in the Bitcoin witness script by whoever constructs the deposit transaction (the depositing user, or tooling acting on their behalf) and is only checked for length/format (`prefixLen + 20 + suffixLen`) and prefix/suffix match — never for being non-zero. A malformed deposit script (e.g. produced by a buggy wallet/tool, or a griefing depositor) with a zero-filled 20-byte recipient segment would pass all existing checks (`Invalid script length`, `Invalid deposit script`, `Invalid script suffix`, signature verification) and reach the vulnerable transfer path. No privileged role, sequencer, or prover compromise is required — just an attacker/user able to author the Bitcoin-side deposit witness.

### Recommendation
Add an explicit check in `deposit()` (or in `extractRecipientAddress()`) that reverts, e.g. `require(recipient != address(0), "Invalid recipient")`, before attempting the transfer — or treat a zero-address recipient the same as a failed transfer by routing it to `failedDepositVault` instead of relying on `call` success semantics.

### Proof of Concept
1. Construct a Bitcoin deposit `moveTx` whose witness script matches `depositPrefix` + `bytes20(0)` + `depositSuffix`, correctly signed by the N-of-N per `verifySigInTx`.
2. Get this transaction included in a Bitcoin block and relayed with a valid Merkle inclusion proof (as in `Bridge.t.sol`'s `doDeposit()` helper flow).
3. Call `Bridge.deposit(moveTx, proof, shaScriptPubkeys)` — all `require` checks pass (`Only one input allowed`, `txId already spent`, `Invalid witness items`, `Invalid script length`, `Invalid deposit script`, `Invalid script suffix`, `isSchnorrSigValid`).
4. `extractRecipientAddress(script)` returns `address(0)`; `(bool success,) = address(0).call{value: depositAmount}("")` returns `success == true`.
5. The `Deposit` event is emitted, `depositAmount` cBTC is sent to `address(0)` and is now unrecoverable — no `DepositTransferFailed` event fires and `failedDepositVault` never receives the funds, unlike the `testDepositRedirectsWhenReceiverReverts` scenario in `Bridge.t.sol` (lines 615-641) which only covers a *reverting* receiver, not a zero-address one.

        uint256 offset = depositPrefix.length;
