### Title
Replay-verify's `ensure_match_transaction_info` omits state-checkpoint hash checks, letting a diverging state root pass as "verified" - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by replay/verification tooling (`db-tool replay_on_archive`, `aptos-debugger`, `aptos` CLI) to confirm that locally re-executed transaction output matches the transaction info that was already agreed upon and committed by consensus. It checks status, gas, write-set hash and event-root hash, but it deliberately skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the resulting Merkle/Sparse-Merkle state roots. This mirrors the external report's core defect class: a commitment check that omits fields it should validate, so a payload (here, a locally-computed execution result) can diverge from the truth while the check still reports success.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only a subset of the fields inside `TransactionInfo`: [2](#0-1) 

It never compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (V1), or `txn_info.position_state_checkpoint_hash()` against anything computed locally. The code itself documents the gap: [3](#0-2) 

This function is the authoritative comparator wired into `storage/db-tool`'s replay-verify path, which re-executes archived transactions with the VM and calls it to decide pass/fail: [4](#0-3) 

Because the check never inspects the checkpoint hashes, any divergence in how the local node computes the post-execution state root (Sparse Merkle Tree root, hot-state root, or the new "trading-native" position Merkle root) relative to the already-signed, historically committed `TransactionInfo` is invisible to this verification path. The write-set bytes and event root can match exactly while the actual state root diverges (e.g. due to a state-computation bug, an incorrectly-guarded feature flag, or a hard-fork-only behavior change), and `ensure_match_transaction_info` will still return `Ok(())`.

### Impact Explanation
This breaks the "hard-fork-only divergence during replay/restore/proof verification" invariant: it is exactly the safety net that is supposed to catch consensus-vs-local execution divergence in ledger-state commitment, and it structurally cannot catch divergence in the state-checkpoint root. Because `state_checkpoint_hash` is the field that is supposed to bind execution results to the actual Sparse Merkle Tree / Jellyfish Merkle root recorded in the authenticated `TransactionInfo`/accumulator, a silent gap here means a real state-divergence bug (the kind hard-fork detection tooling exists specifically to catch) can pass replay-verify undetected. This does not corrupt already-committed ledger data by itself, but it defeats the detection mechanism relied upon to prevent/discover state-root corruption before it propagates (e.g., during archive replay validation, before promoting new node builds, or when validating db-tool bootstrap/backup pipelines). Given that state-root integrity is squarely in scope ("Wrong ... state proof accepted as valid", "Hard-fork-only divergence during commit, replay, restore, or proof verification"), and the consequence of a missed detection is that a state-corrupting bug can reach further into the fleet before being caught, this is a high-impact, low-likelihood-of-immediate-exploit but high-value verification blind spot.

### Likelihood Explanation
This isn't attacker-triggered in the traditional sense — it requires an actual pre-existing state-computation divergence bug (e.g., from a change gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or the hot-state/position-checkpoint logic) to exist first. The likelihood of the underlying divergence occurring is unrelated to this bug, but *given* such a divergence exists, the likelihood that this checker fails to flag it is effectively 100%, since the check is unconditionally skipped rather than conditionally validated. The code comment confirms the aptos engineers are aware of this and intend to close the gap before turning on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which corroborates that this is a real, currently-unmitigated integrity gap rather than a false positive.

### Recommendation
Extend `ensure_match_transaction_info` to validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding locally-computed root is available (i.e., whenever the caller can supply it, similar to how `expected_write_set`/`expected_events` are threaded through). At minimum, gate the enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and any other feature depending on this path for correctness guarantees) on closing this validation gap, as the existing TODO already states.

### Proof of Concept
Not independently reproducible without a concrete state-root-divergence bug to trigger it (this finding is about the missing detection mechanism, not a directly attacker-triggerable state corruption). Conceptually:
1. A locally executed transaction produces a write set and events identical to the archived `TransactionInfo`'s `write_set_hash`/`event_root_hash`, but the resulting Sparse Merkle Tree / hot-state / position-tree root differs from `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` (e.g., due to a bug in state-root computation reachable via `COMPUTE_TRADING_NATIVE_STATE_ROOTS`).
2. `replay_on_archive`'s `execute_and_verify` calls `ensure_match_transaction_info` [5](#0-4) , which only checks status/gas/write-set-hash/event-root-hash.
3. The function returns `Ok(())` despite the state-root mismatch, so the replay-verify tool reports success even though the ledger's authenticated state commitment has silently diverged from local execution.

I could not fully trace every downstream consumer (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm whether any of them layer additional checkpoint-hash validation on top before/after calling this function; a full pass would require reading those call sites, which I was not able to inspect in the remaining time.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
