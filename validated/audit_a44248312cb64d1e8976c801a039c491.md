### Title
Meta-transaction relayer deposit theft via predecessor-based balance refund - (File: `runtime/runtime/src/actions.rs`)

### Summary
When a relayer submits a `SignedDelegateAction` on behalf of a sender ("Alice"), the relayer pays all attached deposits and gas up front, but the runtime routes any resulting deposit refund (on execution failure) to the `predecessor_id` of the newly generated receipt, which is set to the DelegateAction's `sender_id` (Alice), not the relayer. This mirrors the reported "incentive token" bug class: a value-bearing object is created/paid for by one party but a fixed, hard-coded identity assumption ("refund goes to the depositor/predecessor") causes a different, unintended party to receive it — enabling a transferable-value / unauthorized-redirection issue instead of a benign UX complaint.

### Finding Description
In `apply_delegate_action`, the runtime builds a new `Receipt` for the inner actions with `predecessor_id: sender_id.clone()` (Alice), even though the relayer is the one who funded the deposit and gas for these actions: [1](#0-0) 

The accompanying comment explicitly acknowledges the consequence: *"Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit."* [2](#0-1) 

Deposit refunds are generated generically by `refund_unspent_gas_and_deposits`, which sends the failed-execution deposit to `receipt.balance_refund_receiver()` — defaulting to the receipt's predecessor unless a `refund_to` override was explicitly set on the `ActionReceiptV2`: [3](#0-2) 

The protocol architecture doc for meta-transactions independently documents this exact scenario as an accepted risk: the relayer pays for the attached deposit, but if the inner action fails on the receiver's shard, the predecessor (Alice) — not the relayer — receives the refund, creating "a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [4](#0-3) 

Although the protocol later added a `promise_set_refund_to` / `refund_to_account_id` host-function mechanism allowing a promise's predecessor to redirect its own refund target (used, for example, by the `sharded-contract` test contract to preserve the correct refund recipient when forwarding a deposit) [5](#0-4) , this mechanism is not applied by the runtime itself when it constructs the synthetic receipt inside `apply_delegate_action`. The relayer has no way to set `refund_to` on that receipt, because the receipt is built directly by protocol code, not by a WASM promise the relayer controls. The relayer's only defense is out-of-band trust/verification of the DelegateAction contents before submission — exactly analogous to the audited incentive-token bug where the "identity" tied to the value (the depositor) breaks the intended payer/recipient relationship once a third party is legitimately involved.

### Impact Explanation
A malicious meta-transaction sender (Alice) can craft a `SignedDelegateAction` with a large attached deposit targeting an action that she knows (or engineers) to fail on the receiver's shard (e.g., targeting a non-existent method, an account that will reject the call, or a contract in a state that causes revert). The relayer, having verified the transaction looks legitimate and paid for the deposit and gas up front, ends up having that deposit refunded to Alice instead of being returned to the relayer. This is a concrete unauthorized value movement: value paid by the relayer is captured by the sender, not through any bug the relayer can detect at submission time if the failure condition depends on receiver-shard state that changes after inspection (e.g., a race, contract state manipulated by Alice herself, or a target contract designed to intermittently reject calls). This can drain relayer funds without any compensating mechanism at the protocol level.

### Likelihood Explanation
Any unprivileged account can act as "Alice" and construct a `DelegateAction` for a relayer to sign and submit; relayers are a first-class, expected component of the meta-transaction (NEP-366) feature. The condition (inner action fails on the receiver's shard) is fully within Alice's control if she can influence receiver-side state (her own contract, or a call designed to always fail after some condition), making repeated exploitation straightforward. This is explicitly called out in the architecture docs as a known risk requiring "trust between the relayer and its user," indicating the underlying mechanism is real and reachable, though relayer implementations are expected to mitigate it through business-level trust rather than a protocol-level fix.

### Recommendation
Route deposit refunds for DelegateAction-derived receipts to the relayer (the transaction signer who actually funded the deposit) rather than to the DelegateAction's `sender_id`, or have the runtime automatically set `refund_to` on the synthetic receipt created in `apply_delegate_action` to the outer transaction's `signer_id`/relayer. Alternatively, expose an explicit, relayer-controlled `refund_to` field on `DelegateAction` itself so relayers do not have to rely purely on off-chain trust.

### Proof of Concept
1. Relayer receives a `SignedDelegateAction` from Alice with `sender_id = alice`, `receiver_id = bob`, and an inner `FunctionCall` action carrying a large attached deposit intended for `bob`.
2. Relayer wraps it in a transaction and submits it, paying the gas and deposit as the transaction signer.
3. On Alice's shard, `apply_delegate_action` runs and forwards a new receipt to `bob` with `predecessor_id = alice` (see `runtime/runtime/src/actions.rs:499-519`).
4. The forwarded call to `bob` fails (deliberately arranged by Alice, e.g., `bob` briefly rejects calls, or the method name is invalid).
5. `refund_unspent_gas_and_deposits` issues a deposit refund to `receipt.balance_refund_receiver()`, which resolves to `alice` (the predecessor), per `runtime/runtime/src/lib.rs:1402-1407`.
6. Alice receives the deposit the relayer paid for, with no mechanism for the relayer to redirect it, confirming unauthorized value transfer from relayer to sender.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
