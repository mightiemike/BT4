### Title
Unbounded recursion in bytecode-segment hashing/structuring allows stack-exhaustion DoS on declared-class hash computation - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`SierraCompiler::compile` (invoked for every `DECLARE` transaction) compiles an attacker-submitted Sierra program to CASM in a resource-limited subprocess, then — back in the main sequencer process, with no resource sandboxing — computes the compiled-class hash by calling `CasmContractClass::hash()`, which walks the `bytecode_segment_lengths: NestedIntList` tree via the recursive helper `bytecode_hash_node` [1](#0-0)  with no depth limit, mirroring the Faraday `dehash` bug class (CWE-674, uncontrolled recursion on an attacker-influenced nested structure).

### Finding Description
`SierraCompiler::compile` performs Sierra→CASM compilation in an isolated, resource-limited subprocess [2](#0-1) , but immediately afterwards computes the executable class hash **in the calling (unsandboxed) process**: [3](#0-2) 

That hash computation, `CasmContractClass::hash(&HashVersion::V2)`, ultimately calls `hash_inner` → `bytecode_hash` → `bytecode_hash_node`: [4](#0-3) 

`bytecode_hash_node` recurses once per nesting level of the `NestedIntList` (`bytecode_segment_lengths`) tree with **no depth bound**. That field is populated on `CasmContractClass::from_contract_class` by the underlying `cairo-lang` compiler based on the structural segmentation of the Sierra program's functions/branches — it is not validated or depth-limited anywhere in this repository (`get_bytecode_segment_lengths` simply returns whatever the compiler produced, or a flat leaf) [5](#0-4) . Since the compiler's segmentation strategy is a function of the shape/nesting of user-authored code (e.g., deeply nested function/branch structures), a maliciously crafted Sierra program can be engineered to yield a pathologically deep segment tree while staying within the `max_bytecode_size` limit (81,920 felts) enforced by the sandboxed compile step [6](#0-5) .

The equivalent unbounded-recursion pattern also exists in the Starknet OS's own bytecode-segment-structure builder, used during OS re-execution of declared classes: [7](#0-6) 

Notably, the blockifier's analogous structure-building code (`NestedFeltCounts::new_inner`) explicitly asserts a maximum segmentation depth of 1 (`assert!(segmentation_depth <= 1, ...)`) [8](#0-7) , showing that the sequencer team is aware unconstrained nesting is dangerous here — yet the same protection is absent from `bytecode_hash_node` (compiled_class_hash.rs) and `create_bytecode_segment_structure_inner` (starknet_os utils.rs).

### Impact Explanation
`bytecode_hash_node` executes in-process (not in the resource-limited compiler subprocess) as part of every `DECLARE` transaction's compiled-class-hash computation in the sierra-compiler/class-manager component, and `create_bytecode_segment_structure_inner` runs during Starknet OS re-execution of any block containing the malicious declared class. A sufficiently deep `NestedIntList` tree causes uncontrolled native-stack growth, terminating in a Rust `SystemStackError`/SIGSEGV-style abort of the hosting process (class manager / gateway / OS runner) rather than a clean, catchable error. This is a process crash reachable by any account submitting a single `DECLARE` transaction — an unauthenticated, low-cost denial-of-service against sequencer availability (a node "unable to confirm new transactions" while the affected component restarts/recovers), satisfying the CVSS "Availability: High" characterization of the analog Faraday CVE.

### Likelihood Explanation
Likelihood is Medium: exploitation requires an attacker to construct a Sierra/Cairo program whose compiler-generated segmentation tree is deep enough to exhaust the stack, while the flattened bytecode still respects `max_bytecode_size`. This requires understanding of the cairo-lang compiler's segmentation heuristic (function/branch based, generally scales with the number of distinct functions/branches in the program), but is feasible for a determined attacker using many small nested functions, and is fully achievable within the gas/size constraints of a normal `DECLARE` transaction (no special privileges needed).

### Recommendation
- Add explicit recursion-depth guards (or convert to an iterative/worklist algorithm) in `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs`) and `create_bytecode_segment_structure_inner` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`), returning a hard error instead of recursing unbounded, consistent with the existing `assert!(segmentation_depth <= 1, ...)` guard already used in `crates/blockifier/src/execution/contract_class.rs`.
- Validate/bound the maximum nesting depth of `bytecode_segment_lengths` immediately after Sierra→CASM compilation, before it is used for hashing or OS structuring, rejecting classes whose segment tree exceeds a sane depth (analogous to bytecode size limits already enforced).
- Consider performing the post-compilation hash computation inside the same resource-isolated subprocess/thread with a bounded stack, so a crash there does not take down the main sequencer process.

### Proof of Concept
Conceptual (cannot be executed without a live cairo-lang compiler toolchain, but the code path is deterministic):
1. Author a Cairo/Sierra source with `N` (e.g., tens of thousands) deeply nested function definitions/branches such that the `cairo-lang` compiler's bytecode segmentation produces a `NestedIntList::Node` chain of depth `N`, while total bytecode stays under `max_bytecode_size` (81,920 felts).
2. Submit this class via a `DECLARE` transaction to the gateway; `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`) successfully compiles it in the sandboxed subprocess (bounded by size/CPU/memory), then calls `executable_class.hash(&HashVersion::V2)` in the parent process.
3. `hash_inner` → `bytecode_hash` → `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132`) recurses `N` times, exhausting the native stack and crashing the class-manager/gateway process (unsandboxed), producing a denial of service for the declare pipeline and any component sharing that process.

fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
