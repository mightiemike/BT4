### Title
Attacker-controlled NEP-141/registrar response can permanently stall the NEAR ETH-Wallet Contract's in-flight flag, freezing the account forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the NEAR "eth-implicit" wallet used to emulate Ethereum transactions) guards re-entrant use with a single boolean, `has_in_flight_tx`, which is only ever cleared inside callback methods that are invoked asynchronously after a cross-contract call to a target account chosen inside the signed Ethereum transaction (a NEP-141 token contract for `ERC20Transfer` or the address registrar for base-token transfers). Because that target is attacker-influenceable and the callback is executed with a small, fixed static-gas budget, an attacker who controls (or later takes over/re-deploys) the target account can shape its response so that the wallet's callback runs out of gas and panics. Per NEAR's atomic function-call semantics, a panicking receipt rolls back *all* state changes made in that call, including the `has_in_flight_tx = false` reset performed at the very top of the callback. The flag is then permanently stuck at `true`, and every subsequent `rlp_execute` call is rejected forever with `"transaction already in progress"`, with no exposed function to reset it. [1](#0-0) 

### Finding Description
`rlp_execute` is the sole entry point of the wallet and immediately rejects any call while `has_in_flight_tx` is `true`: [2](#0-1) 

The flag is set to `true` right before a multi-hop promise chain is dispatched to an externally controlled `target`/`token_id` account and is only cleared inside the corresponding `#[private]` callback, e.g. `nep_141_storage_balance_callback` / `address_check_callback` / `rlp_execute_callback`: [3](#0-2) [4](#0-3) 

Each callback is dispatched with a small, hard-coded static gas budget that has to cover both host-side result copying and on-guest `serde_json` deserialization of the external contract's arbitrary response: [5](#0-4) [6](#0-5) 

The callback reads and parses `env::promise_result(0)` returned by the (attacker-influenced) target contract: [7](#0-6) 

Only malformed/failed responses are handled gracefully (caught `Result`s); an oversized or deeply structured payload that exhausts the callback's fixed gas budget during copy/deserialization instead triggers a genuine `GasExceeded`/`WasmTrap` runtime failure. NEAR's runtime treats a function-call failure as fully non-committing: none of the state writes performed during that receipt (including the `has_in_flight_tx = false` write at function entry) are applied. Because this is the *only* code path that clears the flag, and there is no privileged/administrative reset function in the contract, the wallet becomes permanently unable to process any future `rlp_execute` call.

### Impact Explanation
This is a transaction-triggered permanent freeze of user funds reachable purely by an ordinary account submitting a signed Ethereum-style transaction through the wallet contract's public `rlp_execute` entry point, targeting a NEP-141 token (or registrar) account that an attacker controls or has re-purposed (e.g., an unsolicited "airdropped" token contract, a common social-engineering vector already mirrored from EVM ecosystems). Once triggered, the affected wallet's `has_in_flight_tx` invariant is stuck `true` forever, permanently blocking all further asset movement (not just interactions with the malicious token) out of that eth-implicit account — a concrete, protocol-reachable case of permanently frozen funds, matching the "malicious lender always defaults the loan" bug class from the source report (an externally-influenced callback that can be made to revert/fail, permanently corrupting an internal state invariant that gates all future operations).

### Likelihood Explanation
The attacker only needs to deploy or control one NEAR account acting as the `target`/`token_id`, and to induce (or wait for) a wallet owner to route an `rlp_execute` call through it (e.g., a scam/airdrop token the owner later tries to transfer away). No validator or node collusion is required, and the callback gas budgets are fixed constants that any large/adversarially-shaped JSON response can plausibly exceed given `max_length_returned_data`-sized payloads. This is a self-contained, single-transaction interaction pattern.

### Recommendation
- Reserve a minimum gas buffer independent of the untrusted response size (e.g., cap and pre-validate `promise_result` length before attempting `serde_json` parsing, or move the `has_in_flight_tx = false` reset to a separate, cheap, always-successful pre-step that cannot be rolled back by a later panic in the same callback).
- Bound/validate the size and structure of external contract responses before deserializing them, and fail closed on oversized payloads rather than attempting to parse them under a fixed gas ceiling.
- Provide a privileged (or time-locked) recovery path to clear `has_in_flight_tx` if a callback receipt is ever lost or fails catastrophically, so that no single failed callback can permanently brick the wallet.

### Proof of Concept
1. Attacker deploys a NEAR contract implementing `storage_balance_of` that returns an extremely large/adversarial JSON payload (up to the protocol's `max_length_returned_data` bound) crafted to maximize `serde_json` deserialization cost.
2. Victim owns an eth-implicit `WalletContract` and signs (or is tricked into signing) an `EthEmulationKind::ERC20Transfer` Ethereum transaction whose `target` is the attacker's contract, then calls `rlp_execute`.
3. `rlp_execute` sets `has_in_flight_tx = true` and dispatches `storage_balance_of` → `nep_141_storage_balance_callback`, budgeted with the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`. [8](#0-7) 
4. The callback receipt runs out of gas while copying/deserializing the attacker's oversized response and aborts with a `FunctionCallError`; all of its state changes (including the `has_in_flight_tx = false` write) are discarded by the runtime.
5. `has_in_flight_tx` remains `true` forever; every subsequent `rlp_execute` call from the victim now immediately returns `"Error: transaction already in progress, please try again later."`, permanently disabling the wallet.
