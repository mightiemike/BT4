## Analog Found

### Title
Local wall-clock time (not deterministic block time) decides L1Handler cancellation-timelock expiry, causing honest-node validation divergence - (File: `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
The reported issue is block-timestamp dependence for computing offer expiry (SWC-116: using an unreliable time source for a state-transition that gates transaction validity). The analogous pattern in this sequencer codebase is the L1 handler transaction lifecycle: whether a cancellation request has "expired" (i.e., the transaction becomes `CancelledOnL2` and therefore invalid/excluded from a block) is decided using each node's own local system clock (`self.clock.unix_now()`), not a value derived from the committed/proposed block itself.

### Finding Description
`L1EventsProvider::validate` and `L1EventsProvider::get_txs` — the two entry points reachable while validating or proposing a block for any incoming L1Handler transaction — pass `self.clock.unix_now()` into the transaction manager: [1](#0-0) 

That value flows into `TransactionManager::validate_tx`, which calls `record.update_time_based_state(unix_now, policy)`: [2](#0-1) 

`update_time_based_state` compares this node-local `unix_now` against `cancellation_requested_at + cancellation_timelock` to decide if the transaction has transitioned into `CancelledOnL2` — a state that makes the transaction non-`is_validatable`, i.e. it can no longer be proposed or validated into a block: [3](#0-2) [4](#0-3) 

Unlike `cancellation_requested_at`, `consumed_at`, and `created_at_block_timestamp`, which are all `BlockTimestamp` values derived from L1/L2 block data, `unix_now` is sourced from `Clock::unix_now()`, i.e., the calling node's own OS/system clock (`DefaultClock` by default): [5](#0-4) 

Because this is a per-node wall-clock read rather than a value agreed upon by consensus (e.g., the proposed block's timestamp), two honest nodes with even modest clock skew, NTP drift, or scheduling delay can reach a different `ValidationStatus` for the exact same L1Handler transaction at the exact same logical point in the protocol: one node's `unix_now` may be past the cancellation timelock boundary while another's is not.

### Impact Explanation
If a proposer's local clock is such that a given L1Handler transaction is still valid (before the cancellation timelock deadline) and it includes that transaction via `get_txs`, a validating node whose local clock has advanced slightly further past the deadline will see the transaction as `Invalid(CancelledOnL2)` in `validate`. Per the flow documented in `docs/diagrams/06-l1-handler-flow.html`, any `Invalid` result on an L1Handler tx during validation fails block validation for that node: [6](#0-5) 

This produces honest-node divergence at consensus-relevant timelock boundaries — nodes disagree on the validity of a proposed block purely due to unsynchronized local clocks, rather than any deterministic, block-derived state. This can stall block confirmation around the timelock boundary (network unable to confirm the proposed block) or cause a validator to reject an otherwise-valid proposal from an honest proposer.

### Likelihood Explanation
This triggers deterministically whenever a proposal is built and validated close to a cancellation timelock expiry boundary (`cancellation_requested_at + cancellation_timelock_seconds`), which is a routine, attacker-uncontrolled but naturally-occurring race condition in normal operation — no malicious behavior is required, only ordinary clock skew/drift between independent sequencer nodes, which is a realistic condition in distributed systems.

### Recommendation
Do not gate transaction validity/expiry transitions on a per-node wall-clock read. Instead, derive `unix_now` deterministically from block-level data (e.g., the block being validated/proposed's own timestamp, or a synchronized/consensus-derived time value) so that all honest nodes evaluating the same tx at the same logical block height compute an identical `ValidationStatus`.

### Proof of Concept
1. Node A (proposer) at local time `t0` calls `get_txs`, where `t0 < cancellation_requested_at + timelock`; tx X is proposable (`Pending`), gets included in the proposal.
2. Node B (validator), due to clock skew/drift or processing delay, calls `validate(tx_hash_X, height)` at local time `t1 >= cancellation_requested_at + timelock`.
3. In `update_time_based_state`, Node B's check `unix_now >= requested_at.saturating_add(cancellation_timelock)` evaluates true, transitioning the record to `CancelledOnL2`.
4. `validate_tx` returns `Invalid(CancelledOnL2)` for tx X on Node B, while Node A included it as valid — the proposal fails validation on Node B though it was legitimately built by Node A, purely due to clock disagreement, not any malicious action or protocol violation.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
