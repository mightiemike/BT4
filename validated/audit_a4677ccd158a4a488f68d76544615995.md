## Title
`TransactionOutput::ensure_match_transaction_info` omits state-checkpoint hash validation, allowing replay/chunk-verification to accept a divergent state root - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by chunk executor replay and the `db-tool replay-on-archive` verifier to confirm that locally re-executed transaction outputs match the authenticated `TransactionInfo` recorded on-chain (i.e., committed by consensus and covered by the transaction accumulator/ledger-info signatures). It explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

## Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates:
- execution status match
- gas used match
- write-set hash (`state_change_hash`) match
- event root hash match
- transaction hash match (in the batch `verify` variant)

but the function contains an explicit acknowledgment that it skips the state proof fields: [2](#0-1) 
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

`TransactionInfo` carries `state_checkpoint_hash` (and, for V1, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) which are the Jellyfish-Merkle/SMT state roots produced at checkpoint boundaries and are what get folded into the transaction-info hash that is itself accumulated into the ledger's transaction accumulator and signed by validators via the `LedgerInfo` (see [3](#0-2) ). This is precisely the authenticated state-commitment root that the "Proof And Storage Pivots" section calls out as needing to "survive executor-to-storage handoff unchanged" and be validated on replay.

`ensure_match_transaction_info` is invoked from two integrity-relevant call sites:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` at [4](#0-3) , which is the tool operators run to confirm archived history matches VM execution.
- `execution/executor/src/chunk_executor/mod.rs`, which uses the same comparator when verifying chunks during state-sync/backup restore.

Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a divergence between the locally recomputed state (Merkle/SMT) root and the authenticated root recorded in the historical `TransactionInfo` will not be flagged as a verification failure by this code path, as long as the write set, events, gas, and status still match. This can happen, for example, if a bug elsewhere in state-checkpoint construction (e.g. `execution/executor/src/workflow/do_state_checkpoint.rs`, hot-state or "position_state" trading-native features noted in the same TODO) produces a wrong root while the write set itself is unaffected — that class of bug would go undetected by `replay-verify`/`replay_on_archive`, silently certifying a corrupted or diverged state root as correct.

## Impact Explanation
This breaks the "authenticated API/state-view output must stay bound to the right ledger version, root, object" and "proof/root acceptance" invariants required by the task: an authenticated state root (state_checkpoint_hash / hot_state_checkpoint_hash / position_state_checkpoint_hash) that no longer matches what a correct VM re-execution and checkpoint construction would produce is accepted as valid by the primary tooling designed to catch exactly this divergence. In the archive-node replay-verify pipeline and chunk-executor restore verification, this means a hard-fork-only or checkpoint-construction bug affecting the state Merkle root (but not the write set contents) would pass verification undetected, defeating the safety net that operators and CI rely on to catch state-root divergence during restore/replay. The TODO itself flags this as a known gap gating the "trading-native"/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature, confirming the maintainers recognize it as a real, unresolved integrity gap rather than an intentional design choice for these fields.

## Likelihood Explanation
The comparator function itself always skips the checkpoint-hash comparison — there's no need for an attacker to "trigger" a special path; the missing check is unconditional. The residual likelihood of *actual* silent corruption being missed depends on some other independent bug injecting a wrong checkpoint hash while leaving the write set/events/status intact (e.g., a bug in hot-state or position-state checkpoint hash assembly in `do_state_checkpoint.rs`, both of which are called out by name in the very same TODO as not-yet-validated by this comparator). That said, the gap is unconditionally present in shipped, non-test, non-experimental code and directly undermines the intended purpose of the replay-verify/chunk-executor verification tooling.

## Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed checkpoint (from `do_state_checkpoint`) and the `txn_info` passed in, returning an error on mismatch, consistent with how `write_set_hash` and `event_root_hash` are already checked. This should be enabled before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / position-state features are turned on, as the TODO itself states.

## Proof of Concept
Local code demonstration (no external network needed): call `ensure_match_transaction_info` with a `TransactionOutput` whose write set, events, gas, and status match `txn_info`, but where `txn_info.state_checkpoint_hash()` differs from the actual root that would be computed by `do_state_checkpoint::DoStateCheckpoint` for the given execution output — the function returns `Ok(())` at [1](#0-0)  despite the state root mismatch, and callers such as `replay_on_archive.rs`'s `execute_and_verify` at [5](#0-4)  treat the chunk as verified (no error added to `total_failed_txns`).

**Note on verification limits**: I was unable to fully trace whether `execution/executor/src/chunk_executor/mod.rs`'s call site independently re-validates checkpoint hashes elsewhere in its pipeline before or after invoking `ensure_match_transaction_info` (the tool budget did not allow reading that full file); this could mitigate impact for the chunk-executor path specifically even though the `db-tool replay_on_archive` path clearly has no such independent check. This should be confirmed with a full read of `chunk_executor/mod.rs` in a follow-up session.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
