### Title
Detected witness double-block-production (equivocation) is never penalized or excluded from consensus - (File: framework/src/main/java/org/tron/core/services/WitnessProductBlockService.java)

### Summary
`WitnessProductBlockService.validWitnessProductTwoBlock` detects when a Super Representative (witness) signs and broadcasts two different blocks for the same block number/slot at the same timestamp — a classic equivocation/double-production Byzantine fault. The evidence is only stored in an in-memory `cheatWitnessInfoMap` and exposed via `queryCheatWitnessInfo()`; no slashing, suspension, vote-weight reduction, or removal from the active witness set is triggered anywhere in the codebase.

### Finding Description
`BlockMsgHandler.processBlock` calls `witnessProductBlockService.validWitnessProductTwoBlock(block)` after every successfully processed block [1](#0-0) . Inside `validWitnessProductTwoBlock`, if a cached block at the same height was produced by the same witness address but with a different block hash at the same timestamp, the code records a `CheatWitnessInfo` entry keyed by the witness's hex address [3](#0-2) .

This is functionally the on-chain analog of the "no slashing" concern in the external report: a participating node (witness/SR) can be caught red-handed violating the single-block-per-slot protocol rule, yet the system takes zero remedial action against it. The witness scheduling logic (`DposService.updateWitness`, `MaintenanceManager.doMaintenance`) only rotates the active set based on vote counts collected via `countVote(votesStore)` [4](#0-3)  — it never consults `cheatWitnessInfoMap` or any equivalent misbehavior record. `StatisticManager.applyBlock`, which tracks `totalMissed`/`totalProduced` for scheduling statistics, also has no connection to the cheat-detection service [5](#0-4) .

Grepping the codebase confirms `queryCheatWitnessInfo`/`cheatWitnessInfoMap` are never read anywhere outside the service's own test file — there is no HTTP/gRPC endpoint, no actuator, and no maintenance-cycle hook that consumes this detected misbehavior to affect voting eligibility, rewards, or active-set membership.

### Impact Explanation
A malicious or compromised Super Representative can equivocate (sign two conflicting blocks at the same slot) — potentially to profit from double-broadcasting different transaction sets, to attempt short-range forks, or to grief network consistency — and remain a fully active, fully rewarded witness indefinitely. The chain records the fact of the violation but applies no consequence: no reduction of `voteCount`, no forced `isJobs=false`, no exclusion from the next `MAX_ACTIVE_WITNESS_NUM` selection, and no loss of block-reward payouts via `incentiveManager.reward(...)`. This matches the report's core concern: detection without enforcement provides no real deterrent, and repeated equivocation can degrade solid-block confirmation (`updateSolidBlock` in `DposService`) and consensus integrity over time.

### Likelihood Explanation
Reaching this code path requires only that an attacker control (or bribe/compromise) an already-elected witness — the same "malicious signer" precondition assumed in the original TSS report, translated here to TRON's DPoS witness role. Given that witness selection is vote-based and not permission-gated by security vetting at the protocol level, and that the misbehavior detection exists but is dead-ended, the likelihood of this gap mattering in practice depends on witness compromise, which is a realistic threat model for any PoS-style validator set.

### Recommendation
Wire `WitnessProductBlockService`'s detected `CheatWitnessInfo` events into the consensus maintenance cycle (e.g., in `MaintenanceManager.doMaintenance` or `DposService.updateWitness`) so that confirmed double-production evidence results in concrete penalties: temporary removal from the active witness set (`isJobs=false`), forfeiture of rewards for the offending cycle in `IncentiveManager.reward`, and/or a vote-count/stake penalty recorded on the `WitnessCapsule`. Persist the cheat evidence (currently only in-memory, lost on restart) so penalties survive node restarts, and expose it through governance/API so the community can independently verify enforcement.

### Proof of Concept
1. Control a witness private key (or run two nodes sharing the same witness identity/key).
2. At the witness's scheduled slot, produce and broadcast two different blocks (differing e.g. in included transactions) with the same block number and timestamp to different peer sets.
3. Peers receiving both blocks via `BlockMsgHandler.processMessage` → `processBlock` will each call `validWitnessProductTwoBlock`, which detects the mismatch and stores it in `cheatWitnessInfoMap` [6](#0-5) .
4. Observe that the witness remains in `getActiveWitnesses()`, continues receiving block rewards via `incentiveManager.reward(...)`, and its `voteCount`/`isJobs` status is unaffected by the detected equivocation across subsequent `MaintenanceManager.doMaintenance()` cycles [7](#0-6) , confirming no penalty is ever enacted.

  public void validWitnessProductTwoBlock(BlockCapsule block) {
    try {
      BlockCapsule blockCapsule = historyBlockCapsuleCache.getIfPresent(block.getNum());
      if (blockCapsule != null && Arrays.equals(blockCapsule.getWitnessAddress().toByteArray(),
          block.getWitnessAddress().toByteArray()) && !Arrays.equals(block.getBlockId().getBytes(),
          blockCapsule.getBlockId().getBytes())) {
        String key = ByteArray.toHexString(block.getWitnessAddress().toByteArray());
        if (!cheatWitnessInfoMap.containsKey(key)) {
          CheatWitnessInfo cheatWitnessInfo = new CheatWitnessInfo();
          cheatWitnessInfoMap.put(key, cheatWitnessInfo);
        }
        cheatWitnessInfoMap.get(key).clear().setTime(System.currentTimeMillis())
            .setLatestBlockNum(block.getNum()).add(block).add(blockCapsule).increment();
      } else {
        historyBlockCapsuleCache.put(block.getNum(), new BlockCapsule(block.getInstance()));
      }
    } catch (Exception e) {
      logger.error("valid witness same time product two block fail! blockNum: {}, blockHash: {}",
          block.getNum(), block.getBlockId().toString(), e);
    }
  }

  public Map<String, CheatWitnessInfo> queryCheatWitnessInfo() {
    return cheatWitnessInfoMap;
  }
