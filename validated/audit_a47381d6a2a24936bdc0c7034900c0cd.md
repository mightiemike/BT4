### Title
Lack of protection against user overpayment leads to permanently locked funds in AddressRegistrar - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
The `AddressRegistrar::register` method, reachable by any unprivileged transaction signer via a payable function call, only validates that the attached deposit meets the *minimum* required storage cost but never refunds the excess when the caller overpays on the success (newly-registered) path. This directly mirrors the reported `FootiumAcademy.mintPlayers` bug class: a payable entry point checks `deposit >= required_amount` instead of `deposit == required_amount`, and any surplus is silently absorbed by the contract with no refund and no withdrawal mechanism.

### Finding Description
In `register` [1](#0-0) , the contract computes `required_deposit` from storage bytes and only panics if `given_deposit < required_deposit`. Any amount attached above `required_deposit` passes this check.

The subsequent match on the `LookupMap` entry handles the two possible outcomes asymmetrically:
- On `Entry::Occupied` (collision — no storage written), the full `given_deposit` is explicitly refunded via a transfer promise to the predecessor. [2](#0-1) 
- On `Entry::Vacant` (the normal success path — storage is written), the account entry is inserted and the address returned, but the excess `given_deposit - required_deposit` is **never refunded**. [3](#0-2) 

There is no other method on `AddressRegistrar` (only `new`, `register`, `lookup`, `get_address`) that could withdraw or reclaim this surplus balance — it has no owner, no withdraw function, and is not upgradable via any exposed method. [4](#0-3) 

This contract is called by the NEAR Wallet Contract's eth-emulation flow to check for address collisions (`address_check_callback`) [5](#0-4) , but `register` itself is a plain `#[payable]` public method that any account (a normal unprivileged transaction signer / RPC caller) can call directly with an arbitrarily large attached deposit.

### Impact Explanation
Any caller who overestimates the required storage deposit (e.g., due to a client-side estimation bug, a stale storage-byte-cost constant, or simply attaching a round/safety-margin amount as is common practice for payable calls) permanently loses the excess deposit into the `AddressRegistrar` account with no recovery path — the funds become irrecoverably locked, since there is no owner-only or public withdraw entrypoint. This is a direct violation of the "no permanently frozen funds" invariant expected of value-accepting entry points reachable by unprivileged callers.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the contract is invoked programmatically by relayers/wallets acting on behalf of end users during the Wallet Contract's eth-implicit-account collision-check flow, and any caller attaching a deposit larger than the exact computed storage cost (a very easy mistake, since `storage_byte_cost` can change or callers may round up) will have the surplus silently swallowed rather than returned, unlike the symmetric refund that already exists on the collision path.

### Recommendation
Mirror the refund behavior already implemented for the `Entry::Occupied` branch: on the `Entry::Vacant` success path, compute `refund = given_deposit.saturating_sub(required_deposit)` and, if non-zero, issue a `promise_batch_action_transfer` back to `env::predecessor_account_id()`, exactly as is already done for the collision case. Alternatively, change the check to require `given_deposit == required_deposit` and reject (revert) on mismatch, consistent with the audit's suggested fix.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `new()`.
2. An unprivileged account (e.g. via the Wallet Contract's relayer flow, or directly) calls `register(account_id)` attaching `given_deposit = required_deposit + X` yoctoNEAR, where `required_deposit` is computed as in `register` (`storage_byte_cost * (20 + account_id.len())`).
3. Since `address` for `account_id` is not yet in `self.addresses` (`Entry::Vacant`), the entry is inserted and `Some(address)` is returned — the full `given_deposit` (including the extra `X`) is retained by the contract; no transfer of `X` back to the caller occurs. [3](#0-2) 
4. The caller has no way to recover `X`: there is no owner/withdraw method on the contract. The surplus is permanently locked in the `AddressRegistrar` account's balance.

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
