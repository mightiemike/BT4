### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant forged webhook requests - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
This is the analog of the "unvalidated ProposerIndex" bug class: an identity/routing field (`X-Shopify-Shop-Domain`) is trusted and propagated to downstream authorization logic (offline session lookup, admin API client, webhook handler callback) without being cryptographically bound to the same signature that authenticates the rest of the request, exactly as `ProposerIndex` was trusted without being tied to the verified RANDAO signature.

### Finding Description
Webhook authenticity is validated solely by computing an HMAC over the raw request body and comparing it to the `X-Shopify-Hmac-Sha256`/events HMAC header: [1](#0-0) 

The shop identity, however, is read straight from the `domain` header (`X-Shopify-Shop-Domain`) and is never included in the HMAC input, nor cross-checked against anything the signature covers: [2](#0-1) 

That unverified `domain` value is then used, unmodified, to:
1. Select/log the acting shop.
2. Look up and load the offline session/access token for that shop.
3. Build an authenticated Admin API client bound to that (attacker-chosen) shop for the handler invocation. [3](#0-2) [4](#0-3) 

Because the API secret key (`config.apiSecretKey`) is a single value shared across all shops that installed the app, an attacker who owns/controls any shop with the app installed can trigger a legitimate webhook event on their own store, capture the resulting `(rawBody, hmac)` pair, and then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and other non-signed headers like topic/webhook-id, if they choose a topic they also registered) to point at a victim shop that has the same app installed. `validateHmacFromRequestFactory` will report the request as valid, since it only checks `hmac(secret, rawBody)` — it has no notion of which shop the body "belongs to."

### Impact Explanation
This is analogous to the `ProposerIndex` bug: the identity field used for authorization decisions is only implicitly and incompletely tied to the cryptographic proof. Concretely, this permits:
- Accepted forged Shopify requests: attacker-controlled webhook bodies are accepted as if genuinely originating from the victim shop.
- Cross-tenant access: the webhook handler is invoked with `webhookCheck.domain` set to the victim shop and (in the shopify-app-remix/react-router SDKs) an `admin` client authenticated with the victim's offline access token, while the actual payload content is attacker-chosen (from their own store's event). Depending on how the app's handler uses payload data (e.g., resource IDs, customer/order references) combined with the victim's authenticated Admin client, this can lead to unauthorized reads/writes against the victim's store data, or corruption of the victim's app-side state (since the app believes the event happened on the victim's shop).
- This requires no prior authentication beyond the attacker being any merchant capable of installing the app on their own (potentially free/dev) store — matching the "single merchant" reachable-actor requirement.

### Likelihood Explanation
Moderate-to-high: the attacker needs (a) their own shop with the app installed to legitimately capture a real `(body, hmac)` pair for a webhook topic the app also has registered for the victim, and (b) knowledge of the victim's `myshopify.com` domain (typically discoverable/guessable or public). No secret material needs to be stolen — the whole point is that the HMAC scheme does not bind the header-based shop identity to the signed payload, so nothing prevents mixing a valid signature from shop A with a domain claim of shop B.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` header as trusted merely because the body HMAC validates. At minimum:
- Cross-check the `domain` header against an expected/allow-listed value known independently (e.g., only accept webhooks for shops with an active, previously-established offline session, and treat a domain mismatch with any other signed identifier as invalid) before invoking handlers or building the Admin client.
- Where possible, incorporate the shop domain into the data that is authenticated (e.g., validate that the webhook's declared shop matches an app-specific per-shop secret/session context) rather than relying on a single shared `apiSecretKey`.
- Document this constraint prominently and provide a stricter validation mode for multi-tenant apps that is enabled by default in the `validateFactory`/`process` codepaths.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers, e.g., the `PRODUCTS_CREATE` topic.
2. Attacker triggers a product creation on their own store, capturing the real webhook request Shopify sends to the app: `rawBody`, and header `X-Shopify-Hmac-Sha256: HMAC(secret, rawBody)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: products/create`, `X-Shopify-Webhook-Id: <id>`.
3. Attacker replays the exact same `rawBody` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `validateHmacFromRequestFactory` (packages/apps/shopify-api/lib/utils/hmac-validator.ts, lines 168-200) validates successfully because it only checks `hmac(secret, rawBody)`.
5. `checkWebhooksHeaders` (packages/apps/shopify-api/lib/webhooks/validate.ts, lines 99-146) returns `domain: 'victim.myshopify.com'` as-is.
6. Downstream (packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts, lines 35-96), the app loads the victim's offline session and builds an Admin API client scoped to the victim shop, then hands the attacker-controlled body to the registered handler as if it were a genuine event from the victim's store.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
