## Finding

### Title
Account::account's stateless-fallback reads the *latest* `DEFAULT_ACCOUNT_RESOURCE` feature flag instead of the flag state at the requested `ledger_version`, misbinding the authenticated response to the wrong version - (File: `api/src/accounts.rs`)

### Summary
`Account::account` first tries to fetch the `AccountResource` state value at the caller-specified `self.ledger_version`. If no state exists at that historical version, it falls back to checking whether the `DEFAULT_ACCOUNT_RESOURCE` feature is enabled via `self.context.feature_enabled(FeatureFlag::DEFAULT_ACCOUNT_RESOURCE)` and, if so, synthesizes a stateless `AccountResource` via `AccountResource::new_stateless`. [1](#0-0) 

### Finding Description
The call `self.context.feature_enabled(FeatureFlag::DEFAULT_ACCOUNT_RESOURCE)` takes no ledger-version argument, so it evaluates the feature flag as currently/latest known, not the flag state at `self.ledger_version` (the historical version the caller explicitly requested and which was already used to pin `latest_ledger_info`/`requested_version` in `Account::new`). [2](#0-1) [3](#0-2) 

Because of this, a request for a historical `ledger_version` that predates the on-chain activation of `DEFAULT_ACCOUNT_RESOURCE` — at which point the correct answer for a non-existent account is `account_not_found` — can instead return a fabricated `AccountData` (sequence_number 0, address-derived authentication key, `guid_creation_num = 2`) once the flag is later enabled on the live chain, since the fallback consults present-day feature state rather than the state effective at the queried version. [4](#0-3) 

This is consistent with the Move-level semantics of the same flag, where `exists_at`/`get_sequence_number` intentionally change behavior based on `features::is_default_account_resource_enabled()` at execution time — a per-version, deterministic on-chain check — whereas the API-layer equivalent check in `Account::account` is not scoped to the requested version. [5](#0-4) [6](#0-5) 

**Uncertainty**: I was unable to retrieve the body of `Context::feature_enabled` in `api/src/context.rs` (the search tool returned only the file header) to confirm definitively whether it resolves features against the latest on-chain config or supports (and is passed) a version parameter elsewhere in the call chain. The conclusion above is inferred from the call site signature at `api/src/accounts.rs:280-284`, which passes only the `FeatureFlag` and no version. This should be verified directly against `api/src/context.rs`'s `feature_enabled` implementation before treating this as fully confirmed.

### Impact Explanation
If confirmed, this is a version-misbinding bug in an authenticated read API: the response for a fixed, historical `ledger_version` is influenced by state (the feature flag) outside that version's frame, causing `Account::account` to fabricate account existence/sequence-number data for a version where the real committed answer was "not found." This does not corrupt committed ledger state, accumulator roots, or proofs, and does not create validator-side commit/replay/proof divergence — the divergence, if any, is purely in this read-only API's view construction, not in consensus-relevant state.

### Likelihood Explanation
Low ambiguity in the code path (unprivileged callers can request arbitrary historical `ledger_version` values freely), but the actual severity hinges on confirming `feature_enabled`'s implementation, which I could not verify in this pass.

### Recommendation
Confirm the implementation of `feature_enabled` in `api/src/context.rs`; if it indeed reads the latest/current feature configuration rather than the on-chain `Features` state as committed at `self.ledger_version`, thread the requested version through so the stateless-fallback decision matches the flag state in effect at that historical version (mirroring the Move-level per-version evaluation in `account.move`).

### Proof of Concept
1. Pick an address with no `Account` resource ever published.
2. Query `GET /accounts/{address}?ledger_version=V` where `V` is before `DEFAULT_ACCOUNT_RESOURCE` was activated on-chain.
3. Before activation, expect `404 account_not_found`.
4. After activation (querying the same historical `V` again), if `feature_enabled` is not version-scoped, the response would flip to a synthesized `200 OK` `AccountData` (sequence_number 0) for the same historical version — demonstrating the response is bound to present flag state, not the state at `V`.

---
Given the caveat above, this finding is best classified as a **potential, unverified API-layer version-binding defect** rather than a definitively confirmed state-integrity/consensus-divergence vulnerability meeting the strict "hard-fork-only divergence" bar in the Decision Standard. I could not confirm via the available tools whether `feature_enabled` is version-aware, so I cannot assert with full confidence that this crosses the State-Integrity Gate (it does not corrupt committed state, proofs, or cause replay/consensus divergence — at most it misbinds a read-only authenticated response to the wrong version).

        // Retrieve the Account resource and convert it accordingly
        let state_value_opt = self.get_account_resource()?;

        let account_resource = if let Some(state_value) = &state_value_opt {
            let account_resource: AccountResource = bcs::from_bytes(state_value)
                .context("Internal error deserializing response from DB")
                .map_err(|err| {
                    BasicErrorWith404::internal_with_code(
                        err,
                        AptosErrorCode::InternalError,
                        &self.latest_ledger_info,
                    )
                })?;
            account_resource
        } else {
            let stateless_account_enabled = self
                .context
                .feature_enabled(
                    aptos_types::on_chain_config::FeatureFlag::DEFAULT_ACCOUNT_RESOURCE,
                )
                .context("Failed to check if stateless account is enabled")
                .map_err(|_| {
                    BasicErrorWith404::internal_with_code(
                        "Failed to check if stateless account is enabled",
                        AptosErrorCode::InternalError,
                        &self.latest_ledger_info,
                    )
                })?;
            if stateless_account_enabled {
                AccountResource::new_stateless(*self.address.inner())
            } else {
                Err(account_not_found(
                    self.address,
                    self.ledger_version,
                    &self.latest_ledger_info,
                ))?
            }

    /// Returns whether an account exists at `addr`.
    ///
    /// When the `default_account_resource` feature flag is enabled:
    /// - Always returns true, indicating that any address can be treated as a valid account
    /// - This reflects a change in the account model where accounts are now considered to exist implicitly
    /// - The sequence number and other account properties will return default values (0) for addresses without an Account resource
    ///
    /// When the feature flag is disabled:
    /// - Returns true only if an Account resource exists at `addr`
    /// - This is the legacy behavior where accounts must be explicitly created
    public fun exists_at(addr: address): bool {
        features::is_default_account_resource_enabled() || exists<Account>(addr)
    }
