### Title
Unbounded Growth of `zero_lamport_accounts_to_purge_after_full_snapshot` Causes Disproportionate CPU Cost on Full-Snapshot Advance - (File: `accounts-db/src/accounts_db.rs`)

### Summary
The `[H-03]` Splitter report shows that an attacker can drive a monotonically-increasing, unbounded counter (`currentWindow`) that a maintenance function (`claimForAllWindows`) must fully iterate, eventually making that function too expensive to call. Agave's `AccountsDb` has an analogous unprivileged-user-reachable pattern: `zero_lamport_accounts_to_purge_after_full_snapshot`, a set that any user can grow by cheaply creating and zeroing out (closing) accounts across many slots, which is fully iterated in one shot when the full snapshot slot advances.

### Finding Description
During `clean_accounts()`, `filter_zero_lamport_clean_for_incremental_snapshots()` defers purging any zero-lamport account whose newest update is in a slot above the `latest_full_snapshot_slot`, inserting `(slot, pubkey)` into `self.zero_lamport_accounts_to_purge_after_full_snapshot` instead of purging it immediately: [1](#0-0) 

This set is never bounded or capped — every zero-lamport account update produced after the last full snapshot and before the next one adds an entry. Any unprivileged user can trivially create this condition by opening and then zeroing (closing) accounts repeatedly across many slots (e.g., rent-exempt token/system accounts created then drained to zero lamports), each such closure contributing one entry to the set, with no cost beyond ordinary transaction fees.

The set is only drained when the full snapshot slot advances (`latest_full_snapshot_slot_advanced_since_clean`), at which point the *entire* set is iterated in a single `retain()` call inside `construct_candidate_clean_keys()`, on the `AccountsBackgroundService`'s clean path: [2](#0-1) 

Because full snapshots are taken relatively infrequently (on the order of tens of thousands of slots), an attacker has a long window in which to accumulate an arbitrarily large number of entries in this set before that single `retain()` call must walk the entire, now-huge structure — directly analogous to `currentWindow` being pumped up via repeated cheap `incrementWindow()` calls before `claimForAllWindows()` is invoked.

### Impact Explanation
This falls under "disproportionate storage and CPU cost": the cost of a normal background maintenance operation (`clean_accounts` on the tick where the full snapshot slot advances) scales linearly with attacker-controlled input that costs the attacker only ordinary transaction fees to produce. A sufficiently large set can cause a multi-second (or worse) stall of the background cleaning/shrink pipeline on that tick, delaying account cleanup, shrink candidate discovery, and consequently increasing storage bloat and slowing subsequent snapshot generation — all without requiring any validator/peer/operator privilege, and reachable purely through unprivileged, honest-transaction-shaped user activity (open/close many accounts across many slots).

### Likelihood Explanation
Likelihood is moderate: an attacker needs sustained but ordinary transaction activity (creating and zeroing accounts) sustained across a large fraction of a full-snapshot interval, which is inexpensive in aggregate (well-funded or moderately funded attacker) but does require sustained on-chain activity over an extended period rather than a single transaction, and the growth is only "cashed in" once per full-snapshot cycle rather than on every operation (unlike the original `claimForAllWindows` bug, which is checked on every call). This reduces severity relative to the original report but the underlying unbounded-collection-with-single-shot-drain pattern is the same bug class.

### Recommendation
Bound or incrementally process `zero_lamport_accounts_to_purge_after_full_snapshot`:
- Process it in bounded batches per clean cycle instead of draining the whole set in one `retain()` call when the full snapshot slot advances.
- Alternatively, cap the number of entries retained and fall back to a full index rescan if the cap is exceeded, so a single tick's cost is bounded regardless of how many zero-lamport closures were produced during the interval.

### Proof of Concept
Not independently executed; based on static code review of:
- `filter_zero_lamport_clean_for_incremental_snapshots` inserting unboundedly into `zero_lamport_accounts_to_purge_after_full_snapshot` [1](#0-0) 
- The single, unbatched `retain()` drain triggered on full-snapshot-slot advance [3](#0-2) 

Conceptual PoC: an unprivileged wallet repeatedly (a) creates a small rent-exempt account, (b) transfers out its lamports to zero it, in a loop spanning tens of thousands of slots (roughly one full-snapshot interval). Each closure adds an entry to the never-capped set. When the validator's next full snapshot slot advances, `clean_accounts()` must `retain()` over the entire accumulated set in one pass, producing a CPU spike proportional to the attacker's sustained (but individually cheap) transaction volume.
