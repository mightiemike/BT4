**Analysis:**

The proposed exploit requires finding two distinct secp256r1 public keys whose serialized bytes produce colliding SHA3-256 outputs when passed through `AuthenticationKey::from_preimage`. This reduces to breaking SHA3-256 collision/second-preimage resistance over a 256-bit output space — a cryptographic hardness assumption, not a code defect.

Key facts that rule this out as a code-level bug:

1. `Secp256r1EcdsaPublicKey::from_bytes_unchecked` actually validates the input is a well-formed point on the P-256 curve via `p256::ecdsa::VerifyingKey::from_sec1_bytes` — it is not "unchecked" in the sense of accepting arbitrary bytes; despite its name, malformed/off-curve bytes are rejected. [1](#0-0) 

2. Address/authentication-key derivation for a `SingleKey` authenticator hashes the full BCS-serialized `AnyPublicKey` enum (including the scheme discriminant byte) via SHA3-256: [2](#0-1) [3](#0-2) 

3. Even granting a hash collision existed, the attacker would additionally need a valid ECDSA/WebAuthn signature over the raw transaction verifiable under the colliding public key — signature verification in `AnySignature::verify` is bound to the specific `AnyPublicKey` variant supplied, and `SingleKeySignature::verify` in the API layer requires the (public_key, signature) pair to type- and cryptographically-match before conversion to `AccountAuthenticator`: [4](#0-3) [5](#0-4) 

4. AptosVM's prologue independently re-derives the authentication key from the submitted public key and checks it against the sender account's on-chain authentication key before executing the transaction — this is the actual binding check the exploit claims is missing, and it exists per `authentication_key()`/`authentication_proof()` on `AccountAuthenticator`: [6](#0-5) 

Since finding a SHA3-256 collision is computationally infeasible (≈2^128 work for birthday collision, far beyond any feasible attacker budget), and no code path skips the authentication-key binding check, this does not meet the bar of "unprivileged input can corrupt committed state" — it depends entirely on breaking an underlying cryptographic primitive, which is out of scope per the review's standard (rejecting findings that don't stem from an actual code/logic defect).
