## Title
`ensure_match_transaction_info` never validates state-checkpoint roots, letting archive-based replay/restore-verification tools accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by `aptos-debugger`, the `aptos-cli replay` command, and `db-tool`'s `replay-on-archive`) is the function that decides whether a locally re-executed transaction "matches" the archived/authenticated `TransactionInfo`. It checks status, gas used, write-set hash, and event root hash, but deliberately skips `state_checkpoint_hash` (and the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), as the code's own TODO admits.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks four invariants (status, gas, write-set hash, event root) but the function ends with: [2](#0-1) 

The comment explicitly states this comparator "ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole correctness check used by:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes a chunk of archived transactions via `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` against the archived `expected_txn_infos` to decide pass/fail: [3](#0-2) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`'s `print_mismatches`: [4](#0-3) 
- `aptos-move/cli/src/commands.rs`'s transaction replay command: [5](#0-4) 

By contrast, the general proof-verification path `TransactionOutputListWithProof::verify` (used when clients consume authenticated API responses) also does **not** check `state_checkpoint_hash` either [6](#0-5) ; it relies on the fact that `TransactionInfo` (which embeds `state_checkpoint_hash`) is itself hashed and proven against the ledger-info-signed accumulator root via `self.proof.verify(...)` at line 3018-3019. That is: consensus-committed `TransactionInfo`s are cryptographically bound to validator signatures through the accumulator, so a *tampered* `state_checkpoint_hash` cannot be smuggled into an API response without also breaking the accumulator proof — the state-checkpoint hash itself is still "authentic" in that path, it's just not independently recomputed/compared to a local root.

The real gap is specific to **replay tooling** (`replay-on-archive`, debugger, CLI replay): there, `TransactionInfo` comes from a backup/archive file (not itself re-verified against a live quorum-certified ledger info within this code path — `replay_on_archive.rs`'s `Verifier` reads directly from a `BackupHandler`/local `arc_db`), and the tool's entire purpose is to confirm that local VM execution reproduces the *same* state root as what's recorded. Since `state_checkpoint_hash` is never recomputed and compared, a divergence between the locally-computed state root and the archived one is silently accepted as "match", even though gas/status/write-set-hash/event-hash still line up.

### Impact Explanation
This breaks the "replay/restore must preserve deterministic proof binding" invariant called out in the assignment's scope. A state root divergence (e.g., from a JMT/state-summary bug introduced in `execution/executor/src/workflow/do_state_checkpoint.rs`'s checkpoint hashing logic, or from a bug in `LedgerWithSummary`/`ProvableStateSummary` extension logic) would not be caught by `replay-on-archive`, `aptos-debugger`, or the CLI replay tool, even though these are exactly the tools operators and auditors rely on to catch consensus-invisible state-root regressions before/after hard forks. Because `state_checkpoint_hash` is the field that authenticates the entire world-state Sparse-Merkle-Tree root for a version, silently not comparing it means these verification tools provide false assurance of correctness for the single most important post-execution invariant (the state root), while giving the impression (their whole purpose) of validating exactly that.

This is a data-integrity/verification gap rather than a directly exploitable "corrupt committed ledger" bug on mainnet (mainnet consensus commit paths bind `TransactionInfo.state_checkpoint_hash` cryptographically into the accumulator/ledger-info signature, so a malicious validator quorum cannot forge it without breaking BFT safety). The concrete, provable harm is: replay-verify / replay-on-archive / debugger tools can and will report success on a chunk whose recomputed state root differs from the archived one, undermining the detection of state-divergent bugs during upgrades, hard forks, or DB restore validation — which is squarely one of the listed in-scope impacts ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

### Likelihood Explanation
High likelihood of silent occurrence: the gap is unconditional (not gated behind any feature flag) — `ensure_match_transaction_info` never checks `state_checkpoint_hash` regardless of whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled. Any bug that causes a divergent state root computation (e.g., a subtle SMT update or checkpoint-index bug in `do_state_checkpoint.rs`) would go completely undetected by every tool that calls this function, and the codebase's own comment confirms the authors are aware this is an outstanding gap.

### Recommendation
Add an explicit comparison of `self.write_set()`-derived expected state root (where the caller can supply the recomputed checkpoint root, similar to `expected_write_set`) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (for `TransactionInfoV1`), and `txn_info.position_state_checkpoint_hash()` whenever `Some`. Since `ensure_match_transaction_info` doesn't currently receive the recomputed checkpoint hash as an argument, the checkpoint-hash comparison should be threaded through from `replay_on_archive.rs`'s executor output (which does have access to computed checkpoint roots via `LedgerUpdateOutput`/`StateCheckpointOutput`) rather than added blindly at the `TransactionOutput` level, which lacks this context today.

### Proof of Concept
Not independently exploitable as a state-corruption PoC on mainnet (the gap is a verification-tooling omission, not a consensus-commit bug). Demonstrable locally as: construct a `TransactionOutput` with correct status/gas/write-set/events but wrap it with a `TransactionInfo` whose `state_checkpoint_hash` is `Some(HashValue::random())` (mismatched), and observe `ensure_match_transaction_info` at [1](#0-0)  returning `Ok(())` — confirming that `replay-on-archive`'s `execute_and_verify` at [7](#0-6)  would treat the transaction as a full match despite the diverging state root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
