## Analog Found: `TokenConfig.liquidity_cap` is validated but never enforced during PRC20 minting

### Title
Unbounded PRC20 minting: `TokenConfig.LiquidityCap` is required but never checked before `depositPRC20`/`CallPRC20Deposit` mints tokens - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/evm.go`)

### Summary
This is a direct analog of the GovNFT `maxBridge` bug: a per-asset supply/bridge cap field exists in configuration, is required by validation, but is never read or enforced anywhere in the actual mint/deposit execution path.

### Finding Description
`TokenConfig` in `uregistry` defines `LiquidityCap` ("max supply cap for this token") and `ValidateBasic` even enforces that it must be non-empty when a token is registered [1](#0-0) . The field is stored on-chain per (chain, token) and surfaced via getters like `GetLiquidityCap` [2](#0-1) .

However, when an inbound is processed and PRC20 tokens are actually minted to a recipient, `depositPRC20` only fetches the `TokenConfig` to resolve the `NativeRepresentation.ContractAddress`; it never reads or compares against `LiquidityCap`: [3](#0-2) . The mint itself, `CallPRC20Deposit`, unconditionally calls `depositPRC20Token` on `UniversalCore` with the attacker/relayer-supplied `amount` from the inbound vote, with no cap check anywhere in the call chain: [4](#0-3) . A grep across `x/uexecutor` confirms `LiquidityCap`/`GetLiquidityCap` is never referenced outside `x/uregistry`'s own types package — it is write-only state that has no consumer.

The same unbounded minting also occurs on the `handleFailedOutbound` re-mint path, which likewise calls `CallPRC20Deposit` with the outbound's `Amount` and no cap check [5](#0-4) .

### Impact Explanation
`LiquidityCap` is documented as a max-supply guardrail for wrapped/synthetic PRC20 assets. Because it's never enforced, an honest-validator-finalized inbound (i.e., an ordinary, unprivileged user depositing on a source chain and having it voted through by honest UVs) can mint PRC20 supply on Push Chain without any check against the configured cap, corrupting the intended PRC20 accounting invariant that governance/registry set for that asset. This matches the "corruption of PRC20 ... accounting" and "unauthorized mint" categories in scope — the mint is technically "authorized" by a valid inbound vote, but the configured supply ceiling meant to bound that authorization is bypassed entirely, an unbounded-mint condition structurally identical to the ineffective `maxBridge` in the source report.

### Likelihood Explanation
High reachability: no privileged action is required. Any user who can get a legitimate inbound deposit voted through the normal honest-validator flow (the standard, expected path for every bridge deposit) will have their PRC20 minted with zero reference to `LiquidityCap`. The bug is deterministic and triggers on every single deposit, not an edge case.

### Recommendation
Before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`, `depositPRC20` (and the outbound re-mint path in `handleFailedOutbound`) should read `tokenConfig.LiquidityCap`, track cumulative minted supply for that token (e.g., via a keeper-tracked total-supply counter or by querying the PRC20 contract's `totalSupply`), and reject/revert the inbound (or clamp) when minting would exceed the configured cap.

### Proof of Concept
1. Registry admin sets a `TokenConfig` for `USDC` on `eip155:11155111` with `liquidity_cap = "1000000000000000000000000"`.
2. A user deposits an amount on the source chain that would, cumulatively across multiple deposits, exceed that cap.
3. Honest validators vote the inbound(s) through normally; `ExecuteInboundFundsAndPayload` → `depositPRC20` → `CallPRC20Deposit` mints the full requested amount every time, with no read of `LiquidityCap` anywhere in the call path [6](#0-5) .
4. Total minted PRC20 supply exceeds the configured `liquidity_cap` with no error, no revert, and no on-chain signal that the invariant was violated.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
