### Title
`DeleteAccountAction` sends account balance to an unvalidated `beneficiary_id`, causing permanent token loss if the beneficiary does not exist - (File: runtime/runtime/src/actions.rs)

### Summary
`action_delete_account` pays out a deleted account's full balance to `delete_account.beneficiary_id` by emitting `Receipt::new_balance_refund`, without ever validating that `beneficiary_id` refers to an existing account. Because the payout is implemented as a *refund* receipt, and refund receipts burn their deposit on failure rather than bouncing back to the sender, a `DeleteAccount` action naming a non-existent (or misspelled) beneficiary permanently destroys the deleted account's remaining NEAR balance. This mirrors the reported `mint`/`safeMint` bug class: value is sent to a receiver without any check that the receiver can actually accept it, and it is unrecoverably lost.

### Finding Description
When a `DeleteAccountAction` is executed, the runtime takes the current account balance and, if positive, queues a system-level balance-refund receipt addressed to `beneficiary_id`, then deletes the account: [1](#0-0) 

There is no existence check on `beneficiary_id` anywhere in this path or in `action_validation.rs`; any syntactically valid `AccountId` is accepted. `Receipt::new_balance_refund` builds a `Transfer` action receipt whose `predecessor_id` is `"system"`: [2](#0-1) 

Refund receipts (`predecessor_id == "system"`) are documented to burn their funds on execution failure rather than being retried or redirected: [3](#0-2) 

This is confirmed by the runtime test showing that a refund receipt addressed to a non-existent account fails with `AccountDoesNotExist` and does not create the account: [4](#0-3) 

And the burn-on-failure logic itself, gated on `receipt.predecessor_id().is_system()`: [5](#0-4) 

The `beneficiary_id` field is fully attacker/user controlled — it can be set directly via a signed `DeleteAccount` transaction, via a meta-transaction/delegate action, via `promise_batch_action_delete_account` from a contract, or via the Rosetta RPC `RefundDeleteAccount`/`DeleteAccount` operation flow: [6](#0-5) [7](#0-6) 

None of these entry points validate that `beneficiary_id` is an existing (or even creatable) account before the delete executes and the balance-refund receipt is generated.

### Impact Explanation
Any account owner (or delegate/meta-tx sender acting on their behalf) who deletes their own account and specifies a `beneficiary_id` that does not exist — through typo, wrong network prefix, or a malformed contract-driven promise batch — has their entire remaining NEAR balance permanently burned instead of returned to a live account. Because the deleting account is already removed by the time the refund receipt executes, there is no fallback recipient (unlike a normal `Transfer` to a nonexistent account, whose failure/refund path returns funds to the *still-existing* sender - see `test_refund_on_send_money_to_non_existent_account`). This is an irreversible, unauthorized-in-effect loss of user funds triggered by a single transaction, satisfying the "permanently frozen/burned funds" impact class.

### Likelihood Explanation
Likelihood is non-trivial: `beneficiary_id` is a plain user-supplied `AccountId` with no existence check, and typos or stale/renamed beneficiary accounts are a realistic real-world scenario (analogous to sending funds to a wrong address). It is also reachable programmatically by any contract using `promise_batch_action_delete_account` with a dynamically computed beneficiary that turns out not to exist, and via Rosetta-driven wallet/exchange tooling that constructs `DeleteAccount`+`RefundDeleteAccount` operations from user input.

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, validate that `beneficiary_id` corresponds to an account that exists (or, if implicit-account semantics permit, is a valid implicit account that can be created). If the beneficiary does not exist, either reject the `DeleteAccount` action outright (fail the whole receipt, similar to how transfers to nonexistent named accounts fail) or route the failed refund back to a recoverable account instead of unconditionally burning it on `predecessor_id().is_system()` failure paths.

### Proof of Concept
1. Attacker/user account `victim.near` holds a positive balance.
2. `victim.near` submits (or a relayer submits via meta-transaction) a `DeleteAccount` action with `beneficiary_id = "typo-target.near"`, an account that has never been created.
3. `action_delete_account` computes `account_balance > 0` and pushes `Receipt::new_balance_refund(&"typo-target.near", account_balance)`, then removes `victim.near` from state: [8](#0-7) 
4. The refund receipt executes with `predecessor_id == "system"` against a `Transfer` to `typo-target.near`; because that account does not exist, the transfer fails with `AccountDoesNotExist`, and because it is a refund receipt, the deposit is burned rather than returned: [5](#0-4) 
5. `victim.near` no longer exists, `typo-target.near` was never created, and the funds are gone — confirmed by the existing test demonstrating refunds to missing accounts fail without creating the account, i.e., without ever crediting anyone: [9](#0-8)

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
