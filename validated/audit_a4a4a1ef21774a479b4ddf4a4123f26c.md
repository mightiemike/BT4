### Title
OAuth callback HMAC validation and shop resolution use different duplicate-parameter values, allowing HTTP Parameter Pollution to desynchronize the validated shop from the shop acted upon - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
The GMX bug allowed an attacker to bypass a security check (virtual price impact) by structuring an action so the value being validated differed from the value actually being acted upon. The `callback()` function in `oauth.ts` has the same class of bug: it extracts the `shop` query parameter twice using two different semantics — `URLSearchParams.get('shop')` (first occurrence) for the values that drive state-cookie error reporting and the outbound token-exchange request, but `Object.fromEntries(query.entries())` (last occurrence wins) for the value that is actually HMAC-validated. A request with a duplicated `shop` parameter can therefore pass the HMAC/state check computed against one shop value while the library performs the OAuth token exchange, session creation, and shop binding using a *different* shop value from the same request.

### Finding Description
In `callback()`:
```ts
const query = new URL(request.url, ...).searchParams;
const shop = query.get('shop')!;                     // <- FIRST occurrence
...
const authQuery: AuthQuery = Object.fromEntries(query.entries()); // <- LAST occurrence wins
if (!(await validQuery({config, query: authQuery, stateFromCookie}))) { ... }
...
const cleanShop = sanitizeShop(config)(query.get('shop')!, true)!;  // <- FIRST occurrence again
``` [1](#0-0) [2](#0-1) [3](#0-2) 

`validateHmac`'s `normalizeQuery` only rejects duplicate/array-valued parameters when `signator === 'appProxy'`; for the default `'admin'` signator used by OAuth, and when the input is already a plain object (not `URLSearchParams`), no duplicate-parameter check is performed at all: [4](#0-3) 

`JavaScript`'s `Object.fromEntries` on an iterator of `[key, value]` pairs keeps the **last** value for a repeated key, while `URLSearchParams.get()` returns the **first** value. Because `oauth.ts` mixes these two extraction methods on the same raw query, an attacker who supplies `?shop=A&shop=B&...` causes:
- HMAC/state validation (`validQuery`) to be checked against `shop=B` (the value Shopify actually signed, e.g. from a legitimate callback the attacker owns/replays).
- The OAuth error logging (`shop` at line 147) and, critically, the token-exchange endpoint URL and resulting `Session.shop` (`cleanShop` at line 194, `sanitizeShop(query.get('shop'))`) to use `shop=A` — a value that was never checked against the Shopify-computed HMAC.

This is structurally identical to the GMX finding: the code path that decides "is this authorized" evaluates one representation of the input, while the code path that performs the state-changing action (session creation, outbound request to `https://{shop}/admin/oauth/access_token`) operates on a different representation drawn from the same request, allowing the check to be satisfied without constraining the value that is actually used.

### Impact Explanation
This breaks the core invariant of the OAuth callback handler: "only requests whose `shop` parameter was validated by Shopify's HMAC are processed for that shop." An attacker can craft a callback request where the shop value bound to the resulting `Session` (and used to build the outbound `/admin/oauth/access_token` request) is attacker-chosen and was never actually covered by a Shopify-issued signature. Even though Shopify's OAuth code-exchange endpoint itself would reject a code/shop mismatch (limiting full account takeover), this is a genuine authentication-logic defect in the library's own validation path — an "accepted forged Shopify request" where the checked value and the acted-upon value diverge — and it can be leveraged for confusing/poisoning error logs, session `shop` binding, and cookie-scoped domain handling (`cookiePath`, `SESSION_COOKIE_NAME` binding) with an unauthenticated shop value, and represents an authentication-boundary defect that downstream integrators may not anticipate.

### Likelihood Explanation
The OAuth callback endpoint is a public, unauthenticated HTTP endpoint that any external actor can hit directly with an arbitrary query string. No privileged access is required to add a duplicate `shop` query parameter — this only requires the attacker to also supply a query the app will treat as HMAC-valid for at least one of the duplicated values (e.g., a callback replayed/crafted from an app the attacker legitimately installed on their own store), which is realistic for any developer/attacker who can install the target app.

### Recommendation
Extract the `shop` parameter using a single, consistent method throughout `callback()`, and explicitly reject requests containing duplicate values for security-relevant parameters (`shop`, `hmac`, `state`, `code`, `timestamp`) for the `'admin'` signator, mirroring the existing protection already implemented for `'appProxy'` in `normalizeQuery` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`). The value passed into `validateHmac` should be the exact same value later used to build `cleanShop` and the outbound token-exchange URL.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, and captures the legitimate OAuth callback redirect from Shopify: `.../auth/callback?shop=attacker.myshopify.com&code=C&state=S&timestamp=T&hmac=H` (H is a valid Shopify-issued HMAC for this exact query).
2. Attacker crafts a new URL against the target app's callback endpoint, injecting a duplicate `shop` parameter before the legitimate one, but keeping `code`, `state`, `timestamp`, and `hmac` unchanged:
   `.../auth/callback?shop=other-target.myshopify.com&shop=attacker.myshopify.com&code=C&state=S&timestamp=T&hmac=H`
3. `Object.fromEntries(query.entries())` collapses this to `{shop: 'attacker.myshopify.com', ...}` (last wins), so `validateHmac`/`safeCompare` succeed against the value Shopify actually signed.
4. `query.get('shop')` returns `'other-target.myshopify.com'` (first wins) at both line 147 (logging) and line 194 (`cleanShop`), so the library proceeds to build a `Session` and issue an outbound POST to `https://other-target.myshopify.com/admin/oauth/access_token` — a shop value that was never bound to the validated HMAC — demonstrating the check/use divergence.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }
