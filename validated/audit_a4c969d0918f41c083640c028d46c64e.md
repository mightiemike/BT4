## Title
Attacker-controlled inbound payload gas usage drains arbitrary Push Chain smart-contract recipient's native UPC balance without consent - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
Any unprivileged sender on an external chain can craft a cross-chain deposit/message (`IsCEA=true`) that targets an **arbitrary already-deployed EVM contract on Push Chain** as `Recipient`, without that contract ever opting in. If the recipient has any code, `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` invoke `executeUniversalTx` on it with attacker-supplied `payload.Data`, and then `DeductGasFeesFromReceipt` bills the **recipient contract's own native UPC balance** for whatever gas was consumed, based on attacker-supplied `GasLimit`/`MaxFeePerGas`/`MaxPriorityFeePerGas`. This mirrors the referenced C4 finding: a third party controls the gas-wasting execution path, and its cost is billed to a victim who never consented to that specific interaction.

### Finding Description
In `ExecuteInboundFundsAndPayload`, when `utx.InboundTx.IsCEA` is true and the recipient is not a UEA, the code only checks whether the recipient address has *any* deployed bytecode: [1](#0-0) 

There is no registry, allow-list, or interface-compliance check confirming the recipient contract intends to receive cross-chain calls. Any contract with code — a DEX, vault, or any user's deployed contract — qualifies as `isSmartContract` purely because it has bytecode.

The subsequent smart-contract branch calls `CallExecuteUniversalTx` with attacker-controlled `payload` bytes and then unconditionally deducts a gas fee from the recipient's own account, calculated from the actual `receipt.GasUsed` of that call: [2](#0-1) 

`CallExecuteUniversalTx` forwards the raw payload bytes to the recipient's `executeUniversalTx` entrypoint: [3](#0-2) 

`DeductGasFeesFromReceipt` computes the bill directly from `receipt.GasUsed` and the `MaxFeePerGas`/`GasLimit` values taken from the inbound's `UniversalPayload` — fields that originate from the source-chain event the attacker emitted, not from the recipient: [4](#0-3) 

The only "cap" is `abiPayload.GasLimit`, but that limit is itself attacker-supplied (part of the inbound message the attacker's own source-chain transaction produced), so it constrains nothing from the victim's perspective — the attacker can set it as high as they want and then craft `payload.Data` that makes the recipient's `executeUniversalTx` (or its fallback, if it lacks that selector) consume gas up to that limit.

This is the direct Push Chain analog of the C4 finding: in the original bug, a malicious seller's token wastes gas during `safeTransferFrom`, and the resulting cost is billed to an unwitting buyer. Here, an attacker's crafted cross-chain payload wastes gas inside (or against) a victim's already-deployed contract, and the resulting cost is billed to that victim's own native UPC balance — a balance the victim never approved for this specific interaction, driven entirely by unprivileged external input (a source-chain event that Universal Validators must faithfully relay).

### Impact Explanation
This falls squarely within the allowed impact gate: "unauthorized module-originated EVM execution" and "corruption of ... gas fee accounting ... reachable from ordinary user deposits, payloads, contracts, or default transaction submission paths alone." An attacker with no privileges can:
- Force execution of code inside any deployed contract on Push Chain that happens to have a callable `executeUniversalTx`-shaped surface (or otherwise burn gas via fallback/dispatch reverts), and
- Drain that contract's native UPC balance to pay for gas the contract's owner never authorized, up to the attacker's chosen `GasLimit × effectiveGasPrice`.

Repeated low-cost attacks (each costs the attacker only a cheap source-chain event/deposit) can be used to grief and drain balances of arbitrary deployed contracts that integrate with the Push Chain gateway, or even contracts that don't intend to integrate at all but happen to have deployed bytecode at that address.

### Likelihood Explanation
Reaching this path requires no validator, admin, or TSS collusion — only an honest quorum of Universal Validators faithfully relaying a real (attacker-authored) source-chain event, which is the expected honest-node behavior. The attacker fully controls `Recipient`, `Data`, `GasLimit`, `MaxFeePerGas`, and `MaxPriorityFeePerGas` in their own outbound message on the source chain. The only precondition is that the target Push Chain contract holds a native UPC balance and has any bytecode (`isSmartContract` check has no further authentication).

### Recommendation
- Require recipient contracts to explicitly opt in (e.g., via a registry or supported-interface check such as ERC-165) before `executeUniversalTx` is invoked and before any gas fee is auto-deducted from their balance.
- Do not let the attacker's own inbound-message fields (`GasLimit`, `MaxFeePerGas`, `MaxPriorityFeePerGas`) dictate the fee charged against a third-party recipient; instead cap it to a small owner/registry-defined maximum, or require the recipient to pre-fund/approve a specific gas budget for cross-chain calls.
- Consider billing the depositor/attacker's own bridged funds (deducted from the amount being delivered) instead of the destination contract's unrelated native balance, closing the parallel to the original "buyer pays for seller-controlled gas waste" bug class.

### Proof of Concept
1. Attacker deploys nothing new; picks any existing Push Chain contract `V` with a nonzero `upc` balance and any bytecode (does not need to implement `executeUniversalTx` — even a revert path or fallback consumes gas that is metered by the EVM call, and any implementer of `executeUniversalTx` for legitimate cross-chain support is directly exposed).
2. Attacker sends a source-chain transaction to the registered gateway emitting an inbound event with `IsCEA=true`, `Recipient = V`, `TxType=FUNDS_AND_PAYLOAD` (or `GAS_AND_PAYLOAD`), and a `UniversalPayload` with attacker-chosen `Data` (crafted to be expensive if `V` does implement the entrypoint), `GasLimit` set high, and `MaxFeePerGas` set to the current base fee (satisfying `CalculateGasCost`'s `>= baseFee` check).
3. Honest Universal Validators observe and vote the inbound; `ExecuteInboundFundsAndPayload` runs, calls `CallExecuteUniversalTx(V, ...)`, and `DeductGasFeesFromReceipt` deducts `gasUsed × baseFee` upc directly from `V`'s balance — see `test/integration/uexecutor/inbound_cea_smart_contract_test.go` lines 315-352, which already demonstrates the mechanics of "gas fees deducted from smart contract recipient after executeUniversalTx" with a pre-funded, unrelated recipient balance being drained. [5](#0-4) 
4. Repeating this with a high `GasLimit` and gas-expensive `Data` drains `V`'s upc balance over one or a few inbound messages, entirely at the attacker's discretion and cost.

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}

// DeductGasFeesFromReceipt calculates and deducts gas fees from a recipient address
// based on the EVM receipt and universal payload parameters.
// Returns nil if receipt is nil (Go-level error, no EVM tx was created).
// Returns error with gas details if deduction fails (insufficient balance, etc).
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}

	t.Run("gas fees deducted from smart contract recipient after executeUniversalTx", func(t *testing.T) {
