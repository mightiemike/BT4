### Title
Hardcoded gas stipends in the NEAR Wallet Contract's cross-contract call chain can be insufficient for external NEP-141/registrar contracts, causing user token/deposit loss - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract (the NEAR analog of an EVM smart-contract wallet, used to emulate Ethereum transactions for eth-implicit accounts) hardcodes several fixed gas stipends for calls to external, untrusted contracts (NEP-141 tokens and the address registrar), mirroring the audited Solidity pattern of hardcoding `gas: 50000` for an outgoing call. If these hardcoded values become insufficient — because a token contract's `storage_balance_of`/`storage_deposit` implementation is more expensive than assumed, or because future NEAR protocol gas repricing raises the cost of the WASM operations performed — the downstream call fails with an out-of-gas error, and the wallet's own promise-chain error handling misattributes/loses value in specific paths.

### Finding Description
`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` hardcodes several `Gas` constants used exclusively for calls to external, potentially malicious contracts: [1](#0-0) 

- `NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, `REGISTRAR_LOOKUP_GAS` are all fixed at `5 Tgas`, and are attached to calls made to arbitrary NEP-141 token contracts (`storage_balance_of`, `storage_deposit`) and the address registrar contract, neither of which is controlled by the wallet contract's code: [2](#0-1) [3](#0-2) [4](#0-3) 

This is directly analogous to the reported bug class: a fixed gas amount attached to an external call that the caller does not control the implementation of, which can become insufficient due to (a) the callee doing more work than assumed, or (b) future changes to gas costs (in nearcore's case, WASM host-function gas repricing via protocol upgrades, which is explicitly called out as a first-class mechanism in this codebase, e.g. `docs/architecture/how/gas.md`) — the same "fork/repricing" risk cited in the original report.

Reachability: any unprivileged user or relayer can trigger this path by calling `rlp_execute` on a deployed Wallet Contract with an RLP-encoded Ethereum ERC-20-style transfer, which is routed through `inner_rlp_execute` into the `ERC20Transfer` branch that uses these hardcoded gas values: [5](#0-4) 

If `storage_balance_of` or `storage_deposit` on the target NEP-141 contract requires more than 5 Tgas (plausible for tokens with non-trivial logic, or after a protocol upgrade that increases the cost of storage/host-function operations), the sub-call fails with `GasExceeded`, which surfaces as `PromiseResult::Failed` in `nep_141_storage_balance_callback`: [6](#0-5) 

Critically, in the `storage_deposit` + `ft_transfer` batched-promise branch, the `NEP_141_STORAGE_DEPOSIT_AMOUNT` (1_250 microNEAR) deposit is attached to the `storage_deposit` action of a two-action batch promise before the `ft_transfer` action. If the `storage_deposit` call itself runs out of the hardcoded 5 Tgas mid-execution (e.g., a token whose `storage_deposit` does extra bookkeeping), the entire receipt fails, and the whole batch (both `storage_deposit` and `ft_transfer`) is reverted together — this specific failure mode is handled by `rlp_execute_callback`'s explicit refund-to-caller logic: [7](#0-6) 

However, this refund logic only refunds `caller_deposit` (the value attached by the caller of `rlp_execute`, i.e. the relayer's `attached_deposit`), not the `NEP_141_STORAGE_DEPOSIT_AMOUNT` NEAR taken from the wallet's own balance for the failed `storage_deposit` call — that deposit is refunded by the standard NEAR deposit-refund mechanism only if the *action itself* fails, but if the action fails purely due to insufficient *attached* gas (`GasExceeded`), NEAR's runtime still generates a balance refund back to the predecessor (the Wallet Contract) per `Receipt::new_balance_refund`, so token/NEAR balance loss from that specific angle is mitigated by NEAR's protocol-level deposit-refund guarantee — unlike the EVM finding, where a failed low-level `.call` does not automatically refund an attached value.

### Impact Explanation
The primary concrete impact is functional breakage / denial of the user's intended cross-contract action (their ERC-20-emulated transfer, or address-registrar-gated base-token transfer) whenever the hardcoded 5 Tgas stipend proves insufficient for the specific token/registrar contract being called. Because this is silently and unpredictably dependent on the implementation details of contracts the Wallet Contract does not control, and on protocol-level gas repricing that nearcore explicitly reserves the right to perform, this can also flip from "always works" to "always fails" for a class of users after a network-wide protocol upgrade repricing WASM host costs — a transaction-triggered inability to execute previously-valid, signed user transactions. Unlike the Solidity original where the recipient permanently loses the ability to receive funds via that path (since NEAR refunds unused/failed deposit at protocol level), the analog here is degraded to a liveness/availability impact rather than a clean value-theft bug once NEAR's automatic balance-refund-on-failure is taken into account; residual real-money risk is confined to the relayer-refund `fee` transfer sent unconditionally in `inner_rlp_execute` regardless of whether the wrapped action later fails due to gas exhaustion: [8](#0-7) 
— i.e., the relayer is always paid its fee even when the user's actual transfer subsequently fails for insufficient hardcoded gas, which is a genuine value-transfer inconsistency reachable by any relayer/attacker who can construct a NEP-141 token whose `storage_balance_of`/`storage_deposit` exceeds 5 Tgas.

### Likelihood Explanation
Likelihood is moderate: this requires either (1) a NEP-141 token contract with an unusually gas-expensive `storage_balance_of`/`storage_deposit` implementation (achievable by an attacker deploying their own token contract and directing a victim/relayer through the Wallet Contract to interact with it) or (2) a nearcore protocol upgrade that increases per-operation gas costs for common WASM host functions, which the repo's own documentation acknowledges is an explicit, foreseeable event class (`docs/architecture/how/gas.md`, "chunk producers can change... any client implementation such as nearcore must compute..."). The relayer-fee-always-paid inconsistency requires no adversarial gas repricing at all — any attacker deploying a token with an intentionally gas-heavy `storage_balance_of` can reliably trigger fee extraction while the user's transfer fails.

### Recommendation
- Do not hardcode fixed gas stipends for calls into arbitrary, un-trusted external contracts (NEP-141 tokens, registrar). Either (a) allow the gas value to be a configurable/attached-gas-derived amount forwarded from the overall `rlp_execute` prepaid gas (similar to how `action.gas()` is already added on top for the user's actual action), or (b) require callers to explicitly specify/attach sufficient gas for these auxiliary calls and validate it up-front the same way `validate_tx_relayer_data` already checks `InsufficientGas` for the user's requested gas.
- Move the relayer `fee` refund logic so it is only paid out after the final `rlp_execute_callback` confirms the user's action succeeded, rather than unconditionally in `inner_rlp_execute` before the action executes.
- Add estimator/benchmarks (similar to `runtime/runtime-params-estimator`) to validate that `NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, and `REGISTRAR_LOOKUP_GAS` remain sufficient across supported token implementations and are revisited whenever NEAR's `ExtCosts`/action gas parameters are updated via protocol version bumps.

### Proof of Concept
1. Deploy a NEP-141 token contract whose `storage_balance_of` method performs extra work (e.g., iterates a large collection) such that it consumes more than 5 Tgas to execute.
2. As a relayer, submit an RLP-encoded Ethereum ERC-20 "transfer" transaction targeting this token through the Wallet Contract's `rlp_execute`, including a non-zero relayer `fee` as permitted by `inner_rlp_execute`.
3. `inner_rlp_execute` immediately schedules and sends the relayer's `fee` transfer (`env::promise_batch_action_transfer`) unconditionally, then schedules the `storage_balance_of` call with `NEP_141_STORAGE_BALANCE_OF_GAS` (5 Tgas).
4. The `storage_balance_of` call runs out of gas and returns `PromiseResult::Failed`, causing `nep_141_storage_balance_callback` to report `"Call to NEP-141 ... storage_balance_of failed"` and abort the transfer.
5. Result: the relayer has already been paid its `fee`, but the user's intended token transfer never executed — a value transfer occurred without the corresponding intended action completing, reachable purely by an ordinary relayer/RPC caller with no special privileges.
