## Title
`ensure_match_transaction_info` never checks `state_checkpoint_hash` — replay-verify and debugger tooling accept a corrupted/divergent world-state root as valid - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the sole consistency check used by `db-tool replay-on-archive`, the Aptos debugger, and the CLI to confirm that freshly re-executed transactions match the authenticated `TransactionInfo` fetched from backup/archive. It validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but it explicitly skips comparing `state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), which is the Sparse-Merkle-Tree root committing the entire world state at a checkpoint version. This is a self-documented gap left in the code.

## Finding Description
In `types/src/transaction/mod.rs`, `ensure_match_transaction_info` checks the transaction status, gas, write-set hash, and event root hash against the expected `TransactionInfo`, then returns `Ok(())` without validating the checkpoint hashes: [1](#0-0) 

The code's own comment acknowledges the gap: [2](#0-1) 

This function is the exclusive verification primitive used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` against the `expected_txn_info` pulled from a backup (itself authenticated by an accumulator/waypoint at backup-creation time): [3](#0-2) 

Because `state_checkpoint_hash` is the field that commits the post-execution world state (the Sparse Merkle Tree root, as documented on `TransactionInfoV0`): [4](#0-3) 

any divergence between the locally re-executed state root and the authenticated archived state root — caused by a VM non-determinism bug, a storage/backup corruption, or a malicious/faulty archive source — is silently ignored by this comparator. The same blind spot propagates into `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, which also call `ensure_match_transaction_info` as their correctness oracle.

## Impact Explanation
Replay-verify tooling exists specifically to catch state-commitment divergence between independent re-execution and the authenticated historical ledger. By omitting the `state_checkpoint_hash` (and the newer hot-state/position-state checkpoint hashes) from the match check, a state root that is wrong — whether from a consensus/execution bug, a corrupted archive, or tampered backup data — will still pass `replay_on_archive`, `aptos-debugger`, and CLI replay checks as "matching." This directly undermines the "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "restore paths must preserve deterministic proof binding" integrity gates: the very tool relied upon to detect committed-state corruption during restore/replay cannot detect corruption in the most important field, the state root itself.

## Likelihood Explanation
This triggers on every normal invocation of `replay_on_archive`, the debugger's txn-info verification path, and CLI replay commands — no attacker action is needed to reach the code; the gap is unconditional and always present when these tools run against any dataset whose state-checkpoint hash has diverged from local execution.

## Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()` (and, where applicable, `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`) against the locally computed state checkpoint root for checkpoint transactions, returning an error on mismatch just as is done for `state_change_hash` and `event_root_hash`, before any code path (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) begins relying on this comparator for state-root assurance.

## Proof of Concept
1. Take an archived/backed-up chain segment whose `TransactionInfo.state_checkpoint_hash` at some checkpoint version has been corrupted (e.g., by a storage bug, or by an adversarial backup source) while `state_change_hash`, `event_root_hash`, `status`, and `gas_used` remain valid/matching for that specific txn info entry (or where the actual world state produced downstream differs though those other fields still align, e.g., a benign-looking write set combined with a wrong tree merge).
2. Run `db-tool replay-on-archive` (or `aptos-debugger`) over that range.
3. `execute_and_verify` → `ensure_match_transaction_info` returns `Ok(())` for every transaction because `state_checkpoint_hash` is never compared, so the tool reports a fully successful replay/verification despite the authenticated world-state root diverging from what local execution actually computed.
