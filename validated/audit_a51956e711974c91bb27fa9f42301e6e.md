Confirmed finding: `CallExecuteUniversalTx` always passes a hardcoded `nil` gas limit to `DerivedEVMCall`, regardless of the user-supplied `UniversalPayload.GasLimit` field, for the isCEA smart-contract-recipient path, and there is no admin/retry mechanism for this specific failure mode (unlike the non-isCEA revert path).

## Title
Hardcoded/ignored gas limit for `CallExecuteUniversalTx` on isCEA smart-contract recipients causes permanently stuck deposited funds with no revert or retry path - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
For `isCEA` inbounds whose `Recipient` resolves to a deployed smart contract (not a UEA), Push Chain deposits the PRC20 to the recipient and then calls the recipient's `executeUniversalTx` via `Keeper.CallExecuteUniversalTx`. That function always passes a hardcoded `nil` gas limit to `DerivedEVMCall`, ignoring the gas budget carried in the inbound's own `UniversalPayload.GasLimit` field [1](#0-0) . This mirrors the Stargate bug class: a fixed/unconfigurable gas parameter for a downstream callback (`sgReceive` / `executeUniversalTx`) causes the callback to run out of gas and revert while the funds transfer itself (the PRC20 deposit) has already committed, leaving value stuck at the destination.

### Finding Description
The two isCEA-smart-contract execution paths (`ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`) both deposit PRC20 tokens to the recipient contract first, then call `k.CallExecuteUniversalTx` inside a `CacheContext` [2](#0-1) [3](#0-2) . Unlike `CallUEAExecutePayload`, which parses and forwards the caller-supplied `universal_payload.GasLimit` as the EVM `gasLimit` [4](#0-3) , `CallExecuteUniversalTx` passes `nil` unconditionally [1](#0-0) , meaning the module's fork-default "sensible" gas limit is used regardless of how much gas the recipient contract's `executeUniversalTx` implementation actually needs to run the attacker/user-controlled `payload`.

Because the recipient contract address, its `executeUniversalTx` implementation, and the size/complexity of `payload` are all attacker-controlled inputs reachable through an ordinary inbound (any external-chain sender can pick any deployed contract as `Recipient` and set `IsCEA=true`), an attacker can trivially construct a payload whose execution cost exceeds the fixed default gas limit. The deposit already committed before this call (it happens above/before the cache scope) [5](#0-4) , so the PRC20 tokens land in the recipient contract regardless of whether `executeUniversalTx` succeeds. When it reverts due to insufficient gas, `contractErr != nil` and the code just records a `FAILED` PCTx [6](#0-5) .

Critically, the isCEA path *never* creates an `INBOUND_REVERT` outbound by design ("isCEA failures never create an INBOUND_REVERT outbound") [7](#0-6) , and there is no mechanism anywhere in the codebase that re-attempts `CallExecuteUniversalTx` with a larger gas limit. The only generic recovery mechanism found, `RevertStuckInbound`, is scoped to stuck ballots (quorum/eligible-voter issues), not to post-execution EVM-call failures [8](#0-7) . As a result, funds deposited to a smart-contract recipient whose `executeUniversalTx` needs more gas than the hardcoded default become permanently stuck: they are neither returned to the sender (no revert path for isCEA) nor delivered to the intended payload logic (the call keeps reverting on every retry attempt since there is no retry with adjustable gas, and there's no way for anyone — including the recipient contract owner — to re-trigger `executeUniversalTx` with a different gas limit).

### Impact Explanation
This is a permanent-freezing-of-funds condition reachable by an ordinary, unprivileged inbound: any external-chain user can construct an inbound with `IsCEA=true`, `Recipient` set to any deployed contract, and a `payload`/`Data` whose execution genuinely requires more gas than the fixed module-side default. The PRC20 deposit commits unconditionally before the call, so value transfer already occurred; the subsequent `executeUniversalTx` invocation is capped at a value the sender cannot control and the protocol never adjusts, so it deterministically reverts, and the isCEA branch is explicitly excluded from creating a revert outbound. This satisfies the "permanent freezing of user or protocol-controlled funds" impact category for an unprivileged attacker with only a standard inbound flow, mirroring the Stargate hardcoded `dstGasForCall` bug class where a fixed downstream-callback gas parameter causes funds to become stuck at the destination with no automatic recovery.

### Likelihood Explanation
Likelihood is high for accidental occurrence (any recipient contract whose `executeUniversalTx` implementation is even moderately complex, or that itself makes further external calls, can exceed the fixed default) and it is also deterministically triggerable by a malicious actor who deploys a controlled "recipient" contract with an intentionally gas-heavy `executeUniversalTx` implementation, then sends themselves (or a victim) funds via an isCEA inbound targeting it — no validator or admin collusion is required, and honest Universal Validators voting the observed inbound faithfully produce this outcome.

### Recommendation
Thread the inbound's own gas budget (analogous to `UniversalPayload.GasLimit` used for the UEA path) into `CallExecuteUniversalTx` instead of hardcoding `nil`, so the caller/sender can express and pay for the gas their `executeUniversalTx` invocation actually needs. Additionally, add an isCEA-aware recovery path — either allow an `INBOUND_REVERT` (returning the already-deposited PRC20) when `executeUniversalTx` fails due to gas exhaustion, or expose an explicit "retry `executeUniversalTx` with a caller-specified gas limit" message so funds deposited to a smart-contract recipient are never permanently unreachable.

### Proof of Concept
1. Deploy a contract `R` implementing the expected recipient interface whose `executeUniversalTx` function performs enough computation/storage writes (or nested external calls) to require gas above the module's hardcoded default (the value used when `DerivedEVMCall`'s `gasLimit` argument is `nil`).
2. Submit (via the normal external-chain gateway flow that Universal Validators observe and vote on) an inbound with `IsCEA=true`, `Recipient=R`, `TxType=FUNDS_AND_PAYLOAD` (or `GAS_AND_PAYLOAD`), a non-zero `Amount`, and a `UniversalPayload.Data` that drives `R.executeUniversalTx` past the fixed gas cap.
3. Once quorum is reached and `ExecuteInboundFundsAndPayload` runs: the PRC20 deposit to `R` commits (as seen in existing test `deposit and executeUniversalTx called for EOA recipient when isCEA is true`-style flows) [9](#0-8) ; `CallExecuteUniversalTx` then reverts out-of-gas, `contractErr != nil`, and the PCTx is recorded `FAILED` with no `INBOUND_REVERT` outbound ever attached [6](#0-5) .
4. Confirm the deposited PRC20 balance remains on `R` indefinitely (query `balanceOf(R)`), that no `OutboundTx` of type `INBOUND_REVERT` exists on the `UniversalTx`, and that no message in the codebase allows re-invoking `executeUniversalTx` on `R` for this `UniversalTx` with a different gas limit.

// RevertStuckInbound is the admin escape hatch — see Keeper.RevertStuckInbound.
func (ms msgServer) RevertStuckInbound(ctx context.Context, msg *types.MsgRevertStuckInbound) (*types.MsgRevertStuckInboundResponse, error) {
	ms.k.Logger().Info("msg: RevertStuckInbound", "signer", msg.Signer)

	admin, err := ms.k.uvalidatorKeeper.GetAdmin(ctx)
	if err != nil {
		return nil, errors.Wrap(err, "failed to read uvalidator admin")
	}
	if admin != msg.Signer {
		return nil, errors.Wrapf(govtypes.ErrInvalidSigner, "invalid admin; expected %s, got %s", admin, msg.Signer)
	}

	if msg.Inbound == nil {
		return nil, errors.Wrap(sdkErrors.ErrInvalidRequest, "inbound is required")
	}

	utxId, outboundId, err := ms.k.RevertStuckInbound(ctx, *msg.Inbound)
	if err != nil {
		return nil, err
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"inbound_reverted_by_admin",
		sdk.NewAttribute("admin", msg.Signer),
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outboundId),
		sdk.NewAttribute("source_chain", msg.Inbound.SourceChain),
		sdk.NewAttribute("amount", msg.Inbound.Amount),
	))

	return &types.MsgRevertStuckInboundResponse{
		UtxId:      utxId,
		OutboundId: outboundId,
	}, nil
}
