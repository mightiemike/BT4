### Title
Unbounded Gzip Decompression of User-Submitted Declare V1 Contract Program Enables Memory/CPU Exhaustion - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The Starknet JSON-RPC `estimateFee` (and any other path that converts a `BroadcastedDeclareTransaction::V1` into an `ExecutableTransactionInput`) decompresses the user-supplied, base64+gzip-encoded Cairo0 `program` field via `decompress_program` without any size or time limit, unlike every other decompression path in the codebase (which explicitly caps decompressed size). A small, highly-compressible payload can expand to an arbitrary amount of memory during decompression, exhausting node memory/CPU from a single unauthenticated RPC call.

### Finding Description
`decompress_program` reads a base64-decoded, gzip-compressed program directly into an unbounded `Vec<u8>` using `GzDecoder::read_to_end`: [1](#0-0) 

The function carries an explicit acknowledgment of the missing protection: `// TODO(dan): add time and size limits.` This is called from `user_deprecated_contract_class_to_sn_api`: [2](#0-1) 

which is invoked when converting a `BroadcastedDeclareTransaction::V1` into an `ExecutableTransactionInput` for local execution/fee estimation: [3](#0-2) 

This conversion is reached from the public `estimateFee` JSON-RPC method, which accepts a `Vec<BroadcastedTransaction>` from any caller and converts each one with `tx.try_into()` before executing them in a blocking task: [4](#0-3) 

Note that the codebase already recognizes this exact bug class and has a fix pattern applied elsewhere: `decompress_with_size_limit`/`decode_and_decompress_with_size_limit` in `starknet_api::compression_utils` bound the number of decompressed bytes using `.take(max_size + 1)` before failing with `CompressionError::SizeLimitExceeded`: [5](#0-4) 

That size-limited helper is used for Sierra programs (`MAX_CAIRO0_PROGRAM_SIZE`/`max_size` bound) in the protobuf class converter and the deprecated-gateway Sierra conversion path: [6](#0-5) [7](#0-6) 

`decompress_program` in `apollo_rpc` is the one remaining path that bypasses this protection entirely: it is not routed through `decode_and_decompress_with_size_limit`, has no cap on the decompressed size, and no cap on decompression time.

### Impact Explanation
An unauthenticated caller of the RPC node's `estimateFee` method can submit a `DECLARE` V1 transaction whose `program` field is a small, maximally-compressed gzip payload (a classic "gzip/zip bomb"). `decompress_program` will decompress it fully into memory with no bound, regardless of how large the decompressed output is (potentially many gigabytes from a payload well under any request-body size limit). This can exhaust the RPC node's memory, causing an OOM kill or severe degradation of the process, denying legitimate transaction fee-estimation/query service — a resource-consumption/availability impact on a node that is part of production sequencer infrastructure.

### Likelihood Explanation
The path is trivially reachable: no special role or prior stateful setup is required, only a well-formed `DECLARE` V1 transaction body accepted by the public `estimateFee` JSON-RPC method, and there is no size/time enforcement in the decompression routine itself (unlike every other decompression call site in the repository, which explicitly enforces a maximum decompressed size). The size of the request body needed is minimal because gzip compression ratios for repetitive data can be extremely high.

### Recommendation
Route `decompress_program` through the existing bounded decompression utility (`decode_and_decompress_with_size_limit` / `decompress_with_size_limit` pattern already used elsewhere in the codebase) so decompression is capped (e.g., to `MAX_CAIRO0_PROGRAM_SIZE` or an equivalent configured limit) and fails fast with an RPC error instead of allocating unbounded memory. Consider also adding a decompression time budget.

### Proof of Concept
1. Construct a `DECLARE` transaction of version `0x1` (`BroadcastedDeclareV1Transaction`) with a `contract_class.program` field set to the base64 encoding of a gzip stream that decompresses to a very large, highly repetitive buffer (a "gzip bomb"), while the compressed payload itself remains small enough to pass the HTTP body size limit.
2. Submit it via the RPC node's `starknet_estimateFee` method (or any other path that calls `TryFrom<BroadcastedDeclareTransaction> for ExecutableTransactionInput` for a V1 declare, e.g. simulate/execute-adjacent endpoints).
3. Observe `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) decompress the payload with `GzDecoder::read_to_end` into an unbounded `Vec<u8>`, consuming memory proportional to the decompressed size rather than the request size, leading to excessive memory allocation/OOM on the node process.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
