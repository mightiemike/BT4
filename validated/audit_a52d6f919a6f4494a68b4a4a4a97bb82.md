## Title
Silent, permanent skip of the `afterAuth` hook after a single failure blocks legitimate OAuth/token-exchange completions for the TTL window - (File: `packages/apps/shopify-app-express/src/helpers/idempotent-promise-handler.ts` and `packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts` / `packages/apps/shopify-app-react-router/src/server/authenticate/helpers/idempotent-promise-handler.ts`)

### Summary
`IdempotentPromiseHandler.handlePromise` marks an `identifier` (the raw session token JWT) as "consumed" the moment it is first seen, *before* the wrapped `promiseFunction` (the `afterAuth` hook) is known to have succeeded. If that first invocation throws, the identifier is not removed from the map — it is only ever cleared by a time-based sweep (`IDENTIFIER_TTL_MS = 60000`). Any subsequent call with the same identifier during that window silently no-ops instead of re-running the hook, so the auth-completion side effects the app relies on (webhook registration, billing checks, provisioning, etc.) are never retried, and the caller has no way to know this happened.

### Finding Description
`isPromiseRunnable` returns `true` and records the identifier the first time it's seen, unconditionally: [1](#0-0) 

`clearStaleIdentifiers` only removes entries once they are older than 60 seconds — it does **not** distinguish between successful and failed executions: [2](#0-1) 

This is confirmed by the test explicitly asserting the identifier survives a thrown error and is only removed by the TTL sweep: [3](#0-2) 

The handler wraps the `afterAuth` hook in both the Express token-exchange middleware and the Remix/React Router token-exchange strategy, keyed by the raw `sessionToken` (the App Bridge-issued JWT), which is commonly cached and re-sent unchanged by the client for the duration of its validity window: [4](#0-3) [5](#0-4) 

The caller treats a thrown error from `callAfterAuthHook`/`handleAfterAuthHook` as a hard failure (500 or a re-thrown `Response`): [6](#0-5) 

Because the identifier is already marked "seen" after the first (failed) attempt, every subsequent token-exchange call carrying the same session token within the 60-second window will find `isPromiseRunnable(identifier) === false` and skip calling `promiseFunction` entirely — silently returning success without ever having run `afterAuth`.

### Impact Explanation
This mirrors the reported bug class: a single failure during a critical, one-time completion step (here, `afterAuth`) leaves shared state (the in-memory identifier map) in a condition that prevents the operation from being correctly retried, and the failure mode is silent rather than visible. Any transient error inside an app's `afterAuth` hook (a DB hiccup, a slow third-party API, a bug triggered by unusual but legitimate session data) causes the hook to be permanently skipped for that identifier for up to a minute, even though the request-handling code otherwise reports success (`next()` is called / no error surfaced) on retries. Apps that rely on `afterAuth` for security- or billing-relevant setup (webhook registration, GDPR compliance registration, license/billing checks) can silently proceed as if onboarding completed when it did not.

### Likelihood Explanation
Triggering requires only a single failing `afterAuth` execution (which can happen from ordinary transient conditions, not just attacker action) combined with the client naturally resending the same, still-valid session token — a normal App Bridge behavior. No privileged access or secret compromise is needed to reach this code path.

### Recommendation
Only record an identifier as "consumed" after `promiseFunction` resolves successfully (or otherwise track success/failure state explicitly), and surface an error to the caller on retry rather than silently no-op'ing so the hook can be correctly retried.

### Proof of Concept
1. Configure an app with an `afterAuth` hook that throws once (e.g., due to a flaky dependency).
2. Trigger token exchange (`performTokenExchange` / `TokenExchangeStrategy.authenticate`) with session token `T`; the hook throws, `callAfterAuthHook` propagates the error, and the middleware returns 500 — but `T` is now recorded in `IdempotentPromiseHandler.identifiers`.
3. Within 60 seconds, resend the same request with the still-valid token `T` (a normal client retry/App Bridge cached token reuse). `isPromiseRunnable(T)` now returns `false`, so `afterAuth` is skipped, yet the request proceeds through `next()` as if everything completed successfully — confirmed by the handler test showing the identifier persists after a thrown error: [3](#0-2) .

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
