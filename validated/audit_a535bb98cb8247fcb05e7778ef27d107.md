### Title
Collected multi-sig signatures become permanently invalid if account permission changes between signing and broadcast — analogous to Wormhole guardian-set rotation invalidating queued VAAs (`File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
The Moonwell bug is a two-phase-validation problem: a message is verified once against a mutable signer set (Wormhole guardians) when queued, then re-verified against the *current* signer set at execution time. If the signer set changes in between, a legitimately-processed message permanently fails and must restart the entire delay cycle.

java-tron's multi-signature account permission system has the same structural pattern. A transaction is signed offline against a specific `Permission` (identified by `permissionId`) and gathers weighted signatures from multiple keys over time via `TransactionCapsule.addSign`/`Wallet.getTransactionApprovedList`/`TransactionUtil.getTransactionSignWeight`. These calls re-fetch the account's *current* `Permission` from `AccountStore` every single time rather than binding to the permission version active when the first signature was collected: [1](#0-0) 

Final on-chain execution repeats the same "current state" re-verification in `validateSignature`: [2](#0-1) 

with weight checking performed in `checkWeight`: [3](#0-2) 

### Finding Description
If the `Permission` object for an account (owner or an `Active` permission) is changed via `AccountPermissionUpdateContract` (processed by `AccountPermissionUpdateActuator`) at any point between the time co-signers begin collecting signatures offline and the time the fully-signed transaction is broadcast/executed, the previously valid partial or complete set of signatures is silently invalidated:

- `getWeight` looks up a signer's weight by scanning the **current** `Permission.getKeysList()` for the account [4](#0-3) .
- `checkWeight`, called both while incrementally adding signatures (`addSign`) and while verifying on broadcast (`validateSignature`, `getTransactionApprovedList`, `getTransactionSignWeight`), throws `PermissionException` for any signer whose weight is now `0` under the new permission, i.e., any signer removed by the permission update [5](#0-4) .
- Even if all original signers remain in the updated permission, a changed `threshold` or reweighted keys can make an otherwise-complete signature set fall below the new threshold, so `validateSignature` returns `false` and the whole transaction must be discarded and re-collected from scratch [6](#0-5) .

This mirrors the report's root cause exactly: a message/transaction is validated against a signer/threshold set that is checked again at a later point in time against mutable on-chain state, with no mechanism to pin validation to the signer set that was authoritative when the message was first accepted/queued.

### Impact Explanation
Any legitimate multi-signature wallet or exchange cold-storage flow that collects `k`-of-`n` signatures asynchronously (common for treasuries/exchanges) can have an in-flight, otherwise fully-authorized transaction permanently rejected at broadcast time if any signer's key is rotated or the threshold is adjusted via a routine `AccountPermissionUpdateContract` in the interim — even though this is a completely benign, expected administrative action by the account owner. The affected transaction cannot be salvaged; every co-signer must re-sign from zero, which is operationally severe for high-value/high-threshold multisig accounts (the exact "lengthy re-doing of the process" impact called out in the original report).

### Likelihood Explanation
This requires no attacker action — it is triggered by ordinary account-permission maintenance (e.g., rotating a compromised or departing signer's key, or adjusting a threshold), which is standard practice for any long-lived multisig setup. Given java-tron actively documents and tests permission updates (`AccountPermissionUpdateActuator`, `TransactionUtil.getTransactionSignWeight`, `Wallet.getTransactionApprovedList`), and multisig transactions can take arbitrary time to collect enough signatures, the window for such an intervening change is realistic for active production accounts.

### Recommendation
Bind partially-collected signature sets to the specific permission version (e.g., a permission id + a version/nonce, or a hash of the permission at collection time) rather than re-resolving `Permission` from live account state at every signature-collection and validation step. Reject stale-permission-version transactions explicitly with a clear error rather than silently invalidating individual signatures, and consider exposing this permission-version binding through `TransactionSignWeight`/`TransactionApprovedList` RPC responses so client tooling can detect drift early instead of discovering failure only at final broadcast.

### Proof of Concept
1. Create account `X` with `Active` permission `P1` (threshold 2, signers A, B, C each weight 1).
2. Client begins collecting an offline multisig transfer transaction `T` under `permissionId` referencing `P1`; A and B sign via `TransactionCapsule.addSign`, satisfying threshold 2.
3. Before `T` is broadcast, account owner submits a routine `AccountPermissionUpdateContract` (processed by `AccountPermissionUpdateActuator`) that removes signer B or raises the threshold to 3, producing `Permission` `P2`.
4. Client broadcasts `T`. `Wallet.broadcastTransaction` → `TransactionCapsule.validateSignature` → `checkWeight` fetches the account's **current** permission (`P2`) via `accountStore.get(owner)` / `account.getPermissionById(permissionId)` [7](#0-6) .
5. Under `P2`, either B's signature yields weight `0` (throws `PermissionException`) or the combined weight of A+B no longer meets the new threshold, so `validateSignature` returns `false`/throws, and `T` is rejected — despite having been fully and correctly authorized under `P1` at collection time.

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
