## Title
Minority signer can permanently poison aggregate-public-key voting for a reward cycle - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

## Summary
`vote-for-aggregate-public-key` in the `signers-voting` boot contract records a candidate aggregate public key as "used" (`used-aggregate-public-keys`) on **every individual vote**, before consensus is reached, rather than only when the key is actually approved. Because the anti-replay check `is-novel-aggregate-public-key` keys off this global, unscoped map, a single low-weight, unprivileged signer can pre-claim a key value for the wrong reward cycle and permanently deny the legitimate signer set from ever finalizing that same key for its intended cycle — the same "claim the resource before the legitimate party can" pattern as the `LaunchEvent.createPair` griefing report, where anyone could call `factory.createPair` first to block the legitimate pool creation.

Key excerpt of the relevant assertions and side effects:
- Novelty check: `(asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))` [2](#0-1) 
- The `used-aggregate-public-keys` map is written **unconditionally** after a single successful vote, *before* the code even checks whether the vote reached the consensus threshold: [3](#0-2) 

`is-novel-aggregate-public-key` treats a key as "used" for whichever reward cycle first wrote it into the map, regardless of whether that write came from a winning (threshold-reaching) vote or a single minority vote: [4](#0-3) 

Also notably, the private helper `is-in-voting-window`, which would restrict votes to the correct reward cycle's active prepare-phase window, is defined but is never called from `vote-for-aggregate-public-key`: [5](#0-4) 
The only cycle-scoping check present is `ERR_OUT_OF_VOTING_WINDOW`, which merely verifies that *that* cycle's key hasn't already been finalized — it does not verify that `reward-cycle` is the caller's current/next cycle: [6](#0-5) 

**Equality broken:** the protocol's intended invariant is "a given aggregate public key K becomes permanently associated with reward-cycle C only if the signer set reaches consensus-weight threshold on K for C." The contract instead lets `used-aggregate-public-keys[K]` be set by *any single vote* for K, for *any* reward cycle the caller is a registered signer in, without a threshold check and without the window binding `reward-cycle` to a specific active cycle.

## Impact Explanation
A registered signer with arbitrarily small weight (a minority participant, unprivileged relative to the rest of the signer set) can, upon learning or guessing the candidate aggregate key K that the honest signer set is converging on for reward cycle N+1 (DKG round messages are exchanged off-chain via stackerdb/p2p before the on-chain vote lands, so K is observable before consensus finalizes on-chain), submit their own `vote-for-aggregate-public-key` call for the **same key K** but tagged with a different `reward-cycle` value (e.g., an already-elapsed cycle, or a cycle for which they hold a valid signer-index). This single call:
1. Passes `is-novel-aggregate-public-key` (K has not been used yet).
2. Writes `used-aggregate-public-keys[K] = <attacker-chosen cycle>` unconditionally, without reaching the threshold.

Every subsequent honest vote for K in the *actual* target reward cycle N+1 then fails `is-novel-aggregate-public-key` with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY`, because the map lookup returns the attacker's cycle rather than N+1. The legitimate signer set can never finalize K for the cycle it was actually generated for, and since real key generation is bound to specific DKG randomness, the whole cycle's aggregate-key voting is denied — mirroring the reported bug class of an unprivileged party permanently blocking a legitimate one-time state transition (pair/pool creation vs. aggregate-key approval), forcing operational/manual remediation for that reward cycle's signer set.

This is a minority-triggerable divergence in the signer-set voting process (falls under "signer weight below threshold" class): no majority weight is needed to *deny*, only to *approve*; a single vote is enough to poison the shared `used-aggregate-public-keys` map.

## Likelihood Explanation
Requires only: (a) being a registered signer for some reward cycle (any signer, however small their weight, qualifies, since `get-signer-weight` only checks registration, not a minimum), and (b) knowledge of the candidate key value K before the honest quorum's on-chain vote is mined — plausible since DKG round proposals/gossip typically precede the burn-op/contract-call submission. No privileged role or majority collusion is required, and the same primitive (any single vote call) both satisfies the "novel key" check and immediately writes the poisoning entry.

## Recommendation
Only write to `used-aggregate-public-keys` when the aggregate key is actually approved (inside the `(if (>= new-total threshold-weight) ...)` branch, in the same `map-insert` that sets `aggregate-public-keys`), not on every individual vote. Additionally, invoke the existing but unused `is-in-voting-window` check inside `vote-for-aggregate-public-key` to bind the supplied `reward-cycle` to the caller's actual current/next reward cycle, closing the ability to submit stray votes for arbitrary cycles.

## Proof of Concept
1. Reward cycle N+1's signer set is computed at prepare-phase start; off-chain DKG produces candidate key `K` that the honest quorum intends to approve for cycle N+1.
2. Attacker (a registered signer in cycle N, with a valid signer-index there) observes `K` off-chain and calls:
   `(contract-call? .signers-voting vote-for-aggregate-public-key attacker-index K 0 N)`
   — passing `reward-cycle = N` (a cycle the attacker legitimately belongs to, distinct from N+1). This call succeeds and executes `(map-set used-aggregate-public-keys K N)` per [7](#0-6) , without ever reaching a threshold.
3. Honest signers in cycle N+1 subsequently call `vote-for-aggregate-public-key ... K ... (N+1)`. Each call fails `is-novel-aggregate-public-key K (N+1)` (which now evaluates `(is-eq N (N+1))` = false) and returns `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` per [2](#0-1) .
4. Cycle N+1 can never approve `K`; the signer set must fall back to generating and re-broadcasting a brand-new key, and the attack can be repeated against each newly observed candidate key, indefinitely delaying finalization.
