### Title
Signer griefs aggregate-key DKG consensus by front-running `used-aggregate-public-keys` in `signers-voting.clar` - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
`vote-for-aggregate-public-key` in `signers-voting.clar` unconditionally records every voted-for candidate key into the global `used-aggregate-public-keys` map — even a single, weight-irrelevant vote that is nowhere near the consensus threshold — and permanently forbids that exact key value from ever being voted on again for any *other* reward cycle. Any signer who holds a slot in *some* reward cycle (no majority, no admin rights required) can pick an arbitrary `(buff 33)` value, or copy one it observes in another signer's pending `VoteForAggregateKeyOp` burn transaction, and "claim" it for its own (unrelated) cycle first. If the real DKG round for the targeted cycle later needs to propose that exact key, every vote for it will permanently revert with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY`, exactly mirroring the Alchemix `Bribe.swapOutRewardToken` griefing pattern where a cheap, unprivileged "claim" transaction poisons a uniqueness check that a legitimate privileged action later depends on.

### Finding Description
`vote-for-aggregate-public-key` gates re-use of an aggregate key across cycles via: [1](#0-0) 

```
(define-read-only (is-novel-aggregate-public-key (key (buff 33)) (reward-cycle uint))
    (is-eq (default-to reward-cycle (map-get? used-aggregate-public-keys key)) reward-cycle))
```

and enforces it before accepting any vote: [2](#0-1) 

Crucially, the map write that poisons a key is unconditional and happens on **every** successful vote regardless of the accumulated tally weight: [3](#0-2) 

```
(map-set tally tally-key new-total)
...
(map-set used-aggregate-public-keys key reward-cycle)
```

The only gate on *who* can vote is that the caller must be a registered signer, for *some* reward cycle, at *some* index — checked purely against the caller's own reward cycle, not the cycle being griefed: [4](#0-3) 

```
(define-read-only (get-signer-weight (signer-index uint) (reward-cycle uint))
    (let ((details (unwrap! (try! (contract-call? .signers get-signer-by-index reward-cycle signer-index)) (err ERR_INVALID_SIGNER_INDEX))))
        (asserts! (is-eq (get signer details) tx-sender) (err ERR_SIGNER_INDEX_MISMATCH))
        (ok (get weight details))))
```

There is no requirement that the caller's weight be a majority, nor that the caller be a signer for the cycle that is later being griefed — only that they are a signer for *their own* chosen `reward-cycle` argument. The equality this breaks is the intended one-key-per-attempt invariant: "the key a quorum ultimately settles on for cycle M is the key that the honest majority chose," but instead any single minority signer can pre-empt that specific key value for a different cycle N, permanently forcing `is-novel-aggregate-public-key` to reject it for M.

Votes are driven by `VoteForAggregateKeyOp` Bitcoin burnchain operations processed in `process_vote_for_aggregate_key_ops`, which run the contract call with attacker-controlled `aggregate_key`, `round`, and `reward_cycle` fields: [5](#0-4) 

Because these are burnchain (Bitcoin) transactions, they are visible in the Bitcoin mempool before confirmation, giving any signer (of any cycle, any weight) the opportunity to observe a soon-to-be-proposed candidate key and front-run it with their own vote tagged to a different cycle they belong to, or simply guess/reuse a key value they know will recur (e.g., static or reused DKG key material across cycles). Once poisoned, `used-aggregate-public-keys[key]` can never be reset — there is no admin/removal function for this map — so the block is permanent for that key value.

### Impact Explanation
This is a minority-triggerable divergence in the signer-set aggregate-key voting process. A single signer with a small weight, in a cycle unrelated to the one being attacked, can permanently prevent the honest signer quorum's chosen candidate key from ever being accepted for a different cycle by making every vote for that key hit `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` at line 159. The affected cycle's DKG round must abandon the poisoned key and burn a round (`update-last-round`, `ERR_INVALID_ROUND` bounds this to +1 round increments), and if the attacker can repeat this for successive proposed keys within the same cycle's prepare-phase window, the cycle can fail to converge on any `get-approved-aggregate-key` value before it starts. Since the aggregate key is required by the `.signers`/PoX-4 signing machinery for that reward cycle, this stalls signer-driven block signing for that cycle — a temporary but network-wide disagreement/stall bounded to signer-set liveness, matching the "signer weight below threshold or from the wrong set" / "temporary tip disagreement" category rather than a fee-bounded loss.

### Likelihood Explanation
Exploitation only requires being a signer with any nonzero weight in any reward cycle (no majority, no admin key) and the ability to submit a cheap `VoteForAggregateKeyOp` burn transaction with a chosen `(buff 33)` key value and a cycle number under the attacker's control — well within reach of any single minority signer, matching the report's "griefing, no profit motive" impact class exactly.

### Recommendation
Scope `used-aggregate-public-keys` uniqueness per-cycle-and-key pair keyed to actual consensus (i.e., only write the map when `map-insert aggregate-public-keys reward-cycle key` succeeds, meaning threshold was actually reached), or drop the cross-cycle uniqueness requirement entirely and rely on `aggregate-public-keys` (one key per cycle, immutable once set) as the sole consensus record, since that map already prevents any real double-use once a key is finalized.

### Proof of Concept
1. Reward cycle N has signer S with any nonzero weight; reward cycle M (M != N) is approaching its DKG round and the honest quorum intends to vote for candidate key K (observed by S via the Bitcoin mempool, or reused deterministically across cycles).
2. S submits `vote-for-aggregate-public-key(S_index, K, round=0, reward_cycle=N)` — passes all checks (`is-novel-aggregate-public-key` is true since K is unseen), and unconditionally sets `used-aggregate-public-keys[K] = N` at line 171, regardless of S's tiny weight vs. `threshold-weight`.
3. Honest signers of cycle M call `vote-for-aggregate-public-key(idx, K, round, M)`; `is-novel-aggregate-public-key(K, M)` now evaluates `(is-eq N M)` = false, so every such vote reverts with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` (line 159) forever, for that key value, with no recovery path in the contract.
