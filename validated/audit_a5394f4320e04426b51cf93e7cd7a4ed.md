Based on my investigation, I found a genuine analog: the market's per-timestamp `index-cache` in `v0-4-market.clar` is populated by `accrue-and-cache` on first read for a given `(timestamp, aid)` and reused for the rest of the transaction/block, but a subsequent liquidation-driven `socialize-debt` operation mutates the vault's real `lindex`/`index` and explicitly refreshes the cache for that specific case — implying that *other* code paths that mutate a vault's index within the same block (e.g. a normal `system-borrow`/`system-repay` executed as part of the same transaction chain, or by a prior transaction earlier in the same block) do not get this refresh, and later `convert-to-scaled-debt` / `resolve-ztoken` / `scale-debt-for-liquidation` calls read the stale cached tuple via `get-cached-indexes`/`unwrap-panic`.

### Title
Stale per-block liquidity/borrow index cache used after a vault mutation within the same block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`accrue-and-cache` caches `{index, lindex}` per `(stacks-block-time, aid)` the first time any operation touches an asset, and every subsequent call in the *same block* returns the cached tuple instead of re-querying the vault, even if a vault-mutating call (`system-borrow`, `system-repay`, a prior user's borrow/repay in an earlier transaction of the same block) has since changed the vault's real index.

### Finding Description
`accrue-and-cache` implements a cache keyed only by `{ timestamp: stacks-block-time, aid: aid }`: [1](#0-0) 

On cache HIT it returns the stored tuple without calling the vault again; on MISS it calls `vault-accrue`, which mutates the vault's `index`/`lindex` state vars and its `last-update` timestamp: [2](#0-1) 

Downstream consumers (`convert-to-scaled-debt`, `resolve-ztoken`, `scale-debt-for-liquidation`) all read this cache via `get-cached-indexes`/`accrue-and-cache` rather than re-deriving from the vault's current on-chain state: [3](#0-2) [4](#0-3) 

The developers were aware that mutating a vault's index invalidates the market's cache — the liquidation `socialize-debt-asset` path explicitly re-populates `index-cache` immediately after a `vault-socialize-debt` write-down that changes `lindex`: [5](#0-4) 

That explicit refresh is a targeted patch for one specific mutation path. It does not exist for the other vault-mutating entry points reachable from the market — `vault-system-borrow` and `vault-system-repay` — both of which call the vault's public `accrue`/`system-borrow`/`system-repay` and change `index`/`lindex`/`last-update` on the vault directly: [6](#0-5) 

Because the market's cache key is `stacks-block-time` (not a per-call nonce), any transaction earlier in the same block that borrows or repays against a vault will have caused that vault's real index to advance, but if the market's `index-cache` map for that `(timestamp, aid)` was already populated (cache HIT) by an even earlier read in that same block, later transactions in that same block that read via `accrue-and-cache`/`get-cached-indexes` get the older, now-incorrect index instead of the vault's current value — the source (the vault's index) moved, but the market's cached copy was never invalidated because the invalidation trigger the code implements (a *new block*) never fires within-block.

### Impact Explanation
Debt/collateral valuation functions such as `convert-to-scaled-debt`, `resolve-ztoken`, and `scale-debt-for-liquidation` use this stale index to compute a user's scaled debt, ztoken price, or liquidation repay amount. An outdated (too-low) borrow index understates a borrower's actual debt when converting to scaled units, which can let a borrower withdraw/borrow beyond what their true health factor should allow, or let a liquidator seize less/more collateral than the current on-chain state warrants — a temporary miscalculation of freezing/loss of funds within the affected block window until the next block's fresh cache key takes over.

### Likelihood Explanation
This requires only ordinary single-block transaction ordering (no privileged access, no DAO compromise): one user's borrow/repay transaction advances a vault's index, and a second transaction in the same block (or a chain of internal calls within one complex transaction touching the same `aid` twice) reads the market's already-populated cache for that block's timestamp. Stacks blocks can contain multiple transactions, so this ordering is plausible under normal usage, though the actual index drift within one block is typically small (bounded by the vault's per-second interest accrual), limiting severity somewhat.

### Recommendation
Either (a) invalidate/refresh the market's `index-cache` whenever a mutating vault call (`system-borrow`, `system-repay`) occurs within the same transaction/block, mirroring the explicit refresh already done for `socialize-debt-asset`, or (b) remove the per-block cache assumption entirely and always read the vault's authoritative current index for any calculation that determines solvency/liquidation amounts.

### Proof of Concept
1. Block N, tx1: User A calls a market function against vault `USDC` that triggers `accrue-and-cache` → cache MISS → `vault-accrue` runs, sets vault index to `I1`, market caches `{timestamp: T, aid: USDC} -> {index: I1, lindex: L1}`.
2. Block N, tx2 (later in the same block): User B calls `system-borrow`/`system-repay` on the `USDC` vault directly (or through the market), which mutates the vault's `index`/`lindex` state to `I2 != I1` via `accrue` in `v0-vault-usdc.clar`. [7](#0-6) 
3. Block N, tx3 (same block, same timestamp `T`): A borrow/withdraw/liquidation call for a different user against `USDC` triggers `accrue-and-cache { timestamp: T, aid: USDC }` → cache HIT → returns stale `{index: I1, lindex: L1}` instead of the vault's now-current `I2`/`L2`. [1](#0-0) 
4. `convert-to-scaled-debt`/`scale-debt-for-liquidation` compute the user's scaled debt and liquidation repay amount using `I1` instead of `I2`, producing a temporarily incorrect solvency/liquidation calculation for the rest of block N.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
