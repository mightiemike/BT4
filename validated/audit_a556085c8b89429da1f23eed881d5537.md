### Title
Bancor-curve `ExchangeProcessor` double→long cast clamps overflow, enabling mispriced/unlimited token exchange - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeProcessor` computes TRC10 Bancor-relay pricing entirely in `double` and truncates the result to `long` via a plain narrowing cast, exactly the bug class described in the report (`get_reserve` returning `i64` from an `f64` calculation that silently clamps on overflow). When the computed `double` result exceeds `Long.MAX_VALUE` (or becomes `Infinity`), the Java cast `(long) x` clamps to `Long.MAX_VALUE` instead of throwing, producing a grossly wrong trade amount that is then used, unchecked, to update exchange-pool balances and credit/debit user account balances.

### Finding Description
`ExchangeProcessor.exchangeFromSupply` raises `(1 + supplyQuant / supply)` to the power `2000.0` in double precision: [1](#0-0) 

For a bonding-curve exponent of 2000, even a modest ratio (e.g. `supplyQuant/supply` in the range of a few percent) makes `Maths.pow(base, 2000.0, ...)` blow up to values far beyond `Double`'s exactly-representable long range, and for larger ratios the result becomes `Double.POSITIVE_INFINITY`. The subsequent narrowing cast `(long) exchangeBalance` at line 38 then silently clamps to `Long.MAX_VALUE` per the JLS narrowing conversion rules for double→long — the same "value too big, clamped to max i64" failure mode identified in the external report for `get_reserve`.

This processor is invoked by `ExchangeCapsule.transaction()` on the **default/legacy path** whenever the chain-parameter proposal `AllowHardenExchangeCalculation` has not been activated: [2](#0-1) 

The gate is a proposal-controlled boolean checked per-actuator: [3](#0-2) 

On this legacy path, both the pool-balance update and the account credit use raw (non-`Math.*Exact`) arithmetic: [4](#0-3) 

There is no validation that the returned `buyTokenQuant`/`anotherTokenQuant` is sane relative to the actual pool reserves before it is subtracted from `secondTokenBalance`/`firstTokenBalance` and persisted, and before it is credited to the trader's account via `ExchangeTransactionActuator`: [5](#0-4) 

A later `SafeExchangeProcessor` was added, which recomputes the same curve with `BigDecimal` to avoid this exact overflow-clamp defect: [6](#0-5) 

The existence of `SafeExchangeProcessor`, gated behind `allowHardenExchangeCalculation()`, confirms java-tron's own developers recognized this exact overflow-clamp bug class in the exchange pricing code — but the fix is not the default; it only takes effect after committee activation of the corresponding proposal.

### Impact Explanation
Any unprivileged user issuing an `ExchangeTransactionContract` (or `ExchangeInjectContract`) against a TRC10 Bancor `Exchange` pool that still runs on the legacy (non-hardened) processor can craft a `sellTokenQuant` that drives the pow-2000 curve past the double/long representable range. The clamped `Long.MAX_VALUE` "price" is then:
- Subtracted from the pool's actual (small) counter-token balance using plain `long` subtraction (no overflow guard on this path), driving the on-chain `ExchangeCapsule` balance to a corrupted/negative state, and
- Credited to the trader's own asset balance via `addAssetAmountV2`, effectively minting an attacker-controlled amount of the counter token far beyond what the bonding curve should allow.

This is a direct settlement/accounting violation reachable by any account with a small amount of the sell-side token — matching the reported impact category of underpriced/mispriced public exchange operations leading to user fund loss and attacker value extraction.

### Likelihood Explanation
Exploitability depends on whether the `AllowHardenExchangeCalculation` proposal has been activated on the target network. Where it has not (the default state until committee activation), the vulnerable `ExchangeProcessor` path is used unconditionally for every exchange transaction, making the bug directly reachable by any user who creates or trades against a Bancor `Exchange` with a suitable balance ratio. Where the proposal has been activated, `SafeExchangeProcessor`'s `BigDecimal` path with `longValueExact()` throws `ArithmeticException` on overflow instead of silently clamping, which the actuators explicitly catch and convert into a failed transaction — mitigating the issue on hardened chains.

### Recommendation
Ensure `SafeExchangeProcessor` (or equivalent overflow-checked arithmetic) is the sole/default exchange pricing path rather than an opt-in, proposal-gated hardening flag, so that legacy `ExchangeProcessor`'s unchecked double→long cast can never be reached in production. Additionally, add explicit bounds/sanity checks (e.g., reject if the computed quant exceeds a reasonable fraction of pool reserves) before mutating `ExchangeCapsule` balances, independent of which processor computed the price.

### Proof of Concept
Conceptually mirrors `ExchangeProcessorTest.testHardenedOverflowDetection` [7](#0-6) , but using the legacy `ExchangeProcessor` (non-hardened) instead of `SafeExchangeProcessor`:
1. Create/find a TRC10 `Exchange` pool with a small `supply` remaining relative to the desired trade (or a normal pool where a large `sellTokenQuant` is submitted).
2. Call `ExchangeProcessor.exchange(sellTokenBalance, buyTokenBalance, sellTokenQuant)` with a `sellTokenQuant` large enough that `supplyQuant/supply` pushed into `Maths.pow(base, 2000.0, ...)` overflows double range.
3. Observe `exchangeFromSupply` returns `(long) Double.POSITIVE_INFINITY` == `Long.MAX_VALUE`, instead of throwing, unlike the hardened path which throws `ArithmeticException` on `longValueExact()`.
4. This clamped value is then used unchecked in `ExchangeCapsule.transaction()`'s non-hardened branch, corrupting pool balances and crediting the trader with an inflated asset amount.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
