This confirms it: `LiquidityCap` is a required field on `TokenConfig` (enforced only for non-emptiness in `ValidateBasic`), but I found no code path in `x/uexecutor/keeper/handler.go`'s `depositPRC20`, `CallPRC20Deposit`, `CallPRC20DepositAutoSwap`, or `execute_inbound_funds*.go` that ever reads `tokenConfig.LiquidityCap` and compares it against cumulative minted supply or the current inbound amount before minting. The mint amount is taken directly from `inbound.Amount` (attacker-influenced observation from the external chain, validated only for being a non-negative uint256 string in `ValidateForExecution`), with no cap enforcement anywhere in the mint path.

### Title
Unenforced `TokenConfig.LiquidityCap` allows unbounded PRC20 minting via honest-validator-attested inbounds - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/evm.go`)

### Summary
`uregistry`'s `TokenConfig.LiquidityCap` field [1](#0-0)  is documented as "max supply cap for this token" and is required to be non-empty at config time [2](#0-1) , but it is never read or enforced anywhere in the PRC20 minting path. `depositPRC20` parses the raw inbound amount string and calls `CallPRC20Deposit` unconditionally, with no lookup or comparison against `tokenConfig.LiquidityCap` or against a running total of minted supply [3](#0-2) .

### Finding Description
The intended invariant, evidenced by the field's name/comment and by `x/uregistry`'s own README ("liquidity cap" listed as part of the per-token accounting data) [4](#0-3) , is that total minted PRC20 supply for a given source-chain token should never exceed `liquidity_cap`. In practice, `ExecuteInboundFunds` and `ExecuteInboundFundsAndPayload` both call `k.depositPRC20(...)` directly using `inbound.Amount` as the mint amount [5](#0-4) [6](#0-5) , and `depositPRC20` only fetches `tokenConfig.NativeRepresentation.ContractAddress`, never `tokenConfig.LiquidityCap` [7](#0-6) . `Inbound.ValidateForExecution` only checks that `Amount` is a valid non-negative uint256 string; it performs no cap check [8](#0-7) . The test suite confirms unbounded accumulation is the actual observed behavior ("multiple solana FUNDS inbounds accumulate balance", asserting balance = 2x with no cap rejection) even though the same test's `TokenConfig` declares a `LiquidityCap` of `1000000000000000000000000` [9](#0-8) .

This is the direct analog of the reported "owner can set unlimited amount" bug class: a registry field intended to bound the mintable amount for an asset exists but is decorative, not enforced, at the fund-minting point.

However, note the trigger path here requires an inbound to be voted through 2/3 of honest Universal Validators observing the real amount emitted by an external chain's gateway event — an ordinary unprivileged attacker cannot arbitrarily inflate `inbound.Amount` past what actually happened on the source chain, since honest UVs would refuse to attest to a forged amount. The only way this becomes attacker-triggerable without any privileged/malicious-validator assumption is if a user can legitimately deposit and cause a real gateway event whose reported `Amount` field, cumulatively across many honest inbounds, exceeds `LiquidityCap` — which is not a "vulnerability" so much as a missing intended safety rail. There is no code path where an unprivileged external attacker alone, without cooperating with a malicious validator, can mint an amount disproportionate to real deposited value.

### Impact Explanation
If exploitable, unbounded minting relative to the declared `LiquidityCap` would let cumulative PRC20 supply for a token diverge without limit from its intended backing/liquidity ceiling, which could affect downstream accounting, swap pricing (`GetSwapQuote`/auto-swap), and the protocol's risk assumptions about redeemable liquidity per token. But because the ordinary mint amount is bound to real gateway event data attested by honest UVs, the practical impact for an *unprivileged, honest-validator* threat model is limited to a missing defense-in-depth control rather than a directly attacker-triggerable fund-draining or minting bug.

### Likelihood Explanation
Low, under the mandated honest-validator/unprivileged-attacker assumption. Reaching this gap requires either (a) organic cumulative deposits across many honest inbounds exceeding the cap (an operational/governance concern, not an attack), or (b) a malicious/compromised Universal Validator forging the `Amount` field — which is explicitly out of scope per the task's threat model ("malicious universal validators... out of scope").

### Recommendation
Enforce `TokenConfig.LiquidityCap` at the point of mint: before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`, `depositPRC20` (or its caller) should track/query cumulative minted supply per `(chain, tokenAddress)` and reject (or clamp/queue) inbound execution when the post-mint total would exceed `liquidity_cap`, producing a `FAILED` PCTx + revert outbound consistent with the existing failure-handling pattern used for missing token configs.

### Proof of Concept
Not applicable as a standalone unprivileged exploit — reproducing unbounded accumulation only requires running the existing integration test twice more: `test/integration/uexecutor/inbound_solana_test.go`'s "multiple solana FUNDS inbounds accumulate balance" subtest shows balance growing without any `LiquidityCap`-based rejection despite a configured cap of `1000000000000000000000000` [9](#0-8) ; repeating additional honest inbounds indefinitely accumulates PRC20 supply past the configured cap with no enforcement anywhere in the codebase.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
