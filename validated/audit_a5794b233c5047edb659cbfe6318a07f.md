### Title
`citrea_network_to_chain_id` is not injective (`Nightly` and `TestNetworkWithForks` collide on chain id 5665), breaking the network-binding check in `run_l1_block`'s `DataOnDa::BatchProofMethodId` branch - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same value `5665`, so the equality check `circuit_chain_id != batch_proof_method_id.body.chain_id` in `run_l1_block` does not uniquely bind a signed `BatchProofMethodIdBody` to one `Network` variant. A body correctly signed by the security council for one of these two networks would pass the chain-id check on the other.

### Finding Description
The intended binding is: `body.chain_id == citrea_network_to_chain_id(network)` should uniquely identify the `Network` the circuit is running. [1](#0-0) 

confirms this is false: `Network::Nightly => 5665` and `Network::TestNetworkWithForks => 5665` both resolve to the same chain id, while `Mainnet` (4114), `Testnet` (5115), and `Devnet` (62298) are distinct.

In `run_l1_block`'s `DataOnDa::BatchProofMethodId` handling: [2](#0-1) 

the code computes `circuit_chain_id = citrea_network_to_chain_id(network)` and compares it against `body.chain_id`; if they match, it proceeds to `verify_method_id_security_council` using `body.serialize()` bytes, and on success calls `BatchProofMethodIdAccessor::insert`, applying the new method id unconditionally on whichever network the node happens to be running. Because the mapping is not injective for `Nightly`/`TestNetworkWithForks`, a body+signature bundle produced for one of these two networks would satisfy the chain-id check when replayed on the other.

The `verify_method_id_security_council` check itself does not add a network-specific input — it only checks 3-of-5 ECDSA signatures over `body.serialize()` against `method_id_upgrade_authority_da_public_keys`: [3](#0-2) 

so the only defense against cross-network replay is the chain-id equality, which is broken for this specific pair.

### Impact Explanation
For the collision to be exploitable, an attacker would also need the two colliding deployments to actually share the same `method_id_upgrade_authority_da_public_keys` (a runtime constant passed into `run_l1_block`/`run_circuit`, not derived from the `Network` enum). `TestNetworkWithForks` is explicitly documented as "All forks from genesis to Nightly / This is used for testing purposes only" in [4](#0-3) , and none of `Mainnet`, `Testnet`, or `Devnet` collide with each other or with `Nightly`/`TestNetworkWithForks`. I could not fully verify (within available tooling) whether any real, value-bearing deployment configures `TestNetworkWithForks` with the same security council keys as a `Nightly` deployment sharing the same Bitcoin DA stream — that would require inspecting `crates/light-client-prover/src/circuit/initial_values.rs` and the rollup config wiring in `bin/citrea/src/rollup/bitcoin.rs`, which reference `TestNetworkWithForks` but appear tied to test/dev tooling rather than a persistent public bridge network.

Given that, the concrete, demonstrable defect is confined to two non-mainnet, non-testnet (i.e., not real value-bearing per the stated preconditions) network identifiers, both explicitly test/nightly-oriented. There is no demonstrated path where `Mainnet` or the public `Testnet` chain id collides with anything, so no cross-network method-id forgery against value-bearing chains is shown.

### Likelihood Explanation
Low/uncertain in practice. The mapping defect (`citrea_network_to_chain_id` not injective) is real and verifiable directly in code, but exploitation additionally requires two live deployments that (a) run `Nightly` and `TestNetworkWithForks` respectively, (b) share the identical security-council public keys, and (c) observe each other's DA (Bitcoin) transactions. `TestNetworkWithForks` being testing-only per its doc comment suggests it is not typically run as a persistent, independently keyed network alongside `Nightly` in a way that would let an unprivileged attacker cause real fund loss or a proof split on a value-bearing chain.

### Recommendation
Make `citrea_network_to_chain_id` injective — assign `TestNetworkWithForks` a distinct chain id from `Nightly` (e.g., a dedicated test id), and add a `cfg`/unit-level invariant test asserting all `Network` variants map to unique ids so future additions cannot silently reintroduce a collision.

use sov_rollup_interface::Network;

fn citrea_network_to_chain_id_is_injective() {
    let all = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];
    let mut seen = HashSet::new();
    for n in all {
        let id = citrea_network_to_chain_id(n);
        assert!(seen.insert(id), "chain id {id} is not unique for network {n:?}");
    }
}
