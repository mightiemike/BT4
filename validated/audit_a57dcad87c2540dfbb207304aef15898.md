### Title
`accrue()` reserve-fee computation can underflow due to `socialize-debt` mutating vault state without accruing first, permanently reverting all vault operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Every state-changing entry point in the vault contracts (`deposit`, `redeem`, `system-borrow`, `system-repay`, `set-fee-reserve`, `set-points-util`, `set-points-rate`, `set-pause-states`, `transfer`) calls `try! (accrue))` first, so that `index`/`last-update`/`assets`/`total-borrowed`/`principal-scaled` are kept consistent before any further math is performed. `socialize-debt` is the single exception: it directly mutates `principal-scaled`, `total-borrowed`, `assets`, and `lindex` using the stale `index` value, without calling `accrue()` first and without bumping `last-update`. The very next call to `accrue()` (triggered from any of the other entry points) computes `debt-delta` and the fee-reserve mint amount `reserve-inc` against these freshly-slashed values, then unconditionally subtracts `reserve-inc` from `total-assets-preview` (`ta-preview`) with no “can’t go below zero” guard, unlike the sibling helper `get-available-assets`, which does guard its own subtraction.

### Finding Description
`calc-treasury-lp-preview` and the identical inline logic in `accrue()` compute: [1](#0-0) 

```
(define-private (calc-treasury-lp-preview)
  (let ((scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (next (next-index))
        (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
        (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
        (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
        (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
        (ta-preview (total-assets-preview)))
    (if (> reserve-inc u0)
        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
```

and, inline, in `accrue()`: [2](#0-1) 

`(- ta-preview reserve-inc)` / `(- (total-assets-preview) reserve-inc)` is exactly the same pattern the external report flags: an unguarded subtraction of a fee/reserve-derived amount from a "total" value that is not guaranteed to be at least as large. Clarity uses checked `uint` arithmetic, so if `reserve-inc` exceeds `ta-preview`, the subtraction aborts the whole transaction. Contrast this with the deliberately-guarded pattern used a few lines above for the analogous case: [3](#0-2) 

The value that can desynchronize `ta-preview` from `reserve-inc` is written by `socialize-debt`, which is the only mutator of `assets`/`total-borrowed`/`principal-scaled` that does **not** call `accrue()` first (compare with `deposit`, `redeem`, `system-borrow`, `system-repay` which all begin with `(u (try! (accrue)))`): [4](#0-3) 

Because `socialize-debt` computes its `debt-reduction`/`principal-reduction` off the stale `index` (not `next-index`) and never updates `index`/`last-update`, any interest that has silently accrued between the last `accrue()` and the `socialize-debt` call is not reflected in the write-down ratio applied to `assets`/`total-borrowed`/`principal-scaled`. The next time any ordinary user action (`deposit`, `redeem`, a `transfer`, `system-borrow`, `system-repay`) triggers `accrue()`, that call computes `next-index` over the *entire* unaccounted time span against the *already-reduced* `principal-scaled`, producing a `debt-delta` (and therefore `reserve-inc`) that is disproportionately large relative to the freshly slashed `assets`/`total-borrowed` feeding `ta-preview`. This is the classic "cached value not invalidated when its source moves" pattern: `index`/`last-update` are the cached values, `socialize-debt` is the event that moves the underlying state without invalidating them, and the later `accrue()` call is the use that can underflow.

### Impact Explanation
`accrue()` is invoked unconditionally at the top of essentially every vault entry point. If `(- ta-preview reserve-inc)` underflows, the entire enclosing transaction reverts with a runtime arithmetic error. Since `last-update`/`index` are never advanced when this condition holds (the transaction aborts before any `var-set`), every subsequent call to `deposit`, `redeem`, `system-borrow`, `system-repay`, and `transfer` will hit the identical underflow and revert as well, indefinitely bricking the affected vault (deposits, withdrawals, borrows and repayments) — this is a temporary/potentially permanent freezing of user funds (deposits become unwithdrawable and borrowers cannot access/repay liquidity) in-scope under the "temporary freezing of funds" impact class.

### Likelihood Explanation
`socialize-debt` is reachable by any `authorized-contracts` caller (a normal, intended protocol operation for writing off bad debt, not a DAO-compromise scenario), and it is architecturally the only mutator in the file that bypasses the `accrue()`-first pattern. Any dormant period between the last `accrue()` and a `socialize-debt` call (which is realistic, since nothing forces accrual immediately beforehand) is sufficient to desynchronize `index`/`last-update` from the freshly written-down `assets`/`total-borrowed`/`principal-scaled`, and the subsequent unconditional `accrue()` call on the very next vault interaction is guaranteed to execute the vulnerable subtraction.

### Recommendation
1. Make `socialize-debt` call `(try! (accrue))` first, exactly like every other state-mutating vault entry point, so that `index`/`last-update` are always synchronized with `assets`/`total-borrowed`/`principal-scaled` before any write-down is applied.
2. Guard the subtraction the same way `get-available-assets` already does:
```clarity
(if (>= ta-preview reserve-inc) (- ta-preview reserve-inc) u0)
```
applied both inside `calc-treasury-lp-preview` and inline in `accrue()`.

### Proof of Concept
1. Vault is live with `index`/`last-update` last synchronized at time `T0`, `principal-scaled = P`, `total-borrowed = B ≈ debt`, `assets = A`.
2. No one calls any vault function for a long interval `Δt` (interest silently accrues, unrealized since `index` is only updated inside `accrue()`).
3. An authorized contract calls `socialize-debt(S)` to write off bad debt. Because `socialize-debt` uses the stale `(var-get index)` (not `next-index`), it computes `debt-reduction`/`principal-reduction` ignoring the unaccounted `Δt` interest, then directly sets `principal-scaled`, `total-borrowed`, and `assets` to reduced values — all without touching `index`/`last-update`.
4. Any user now calls `deposit`, `redeem`, `system-borrow`, `system-repay`, or `transfer`. Each begins with `(try! (accrue))`.
5. Inside `accrue()`, `next-index` is computed against the *entire* elapsed `Δt` (including the pre-`socialize-debt` unaccounted period) applied to the newly slashed `principal-scaled`, yielding `debt-delta`/`reserve-inc`, while `ta-preview` is computed from the newly slashed `assets`/`total-borrowed`.
6. `(- ta-preview reserve-inc)` underflows because `reserve-inc` (sized off the desynchronized, elapsed-time-heavy `debt-delta`) exceeds the freshly slashed `ta-preview`. The transaction reverts.
7. Every subsequent call to any of `deposit`/`redeem`/`system-borrow`/`system-repay`/`transfer` re-triggers the same failing `accrue()` path (since `index`/`last-update` were never advanced by the failed transaction), permanently freezing the vault.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
