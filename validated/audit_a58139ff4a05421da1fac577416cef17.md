### Title
`liquidate-multi` uses bare (non-`contract-call?`) invocation of `liquidate`, so a late-stage `asserts!` failure inside a batched liquidation does not unwind the already-executed debt/collateral mutations - ([File: local-testing/contracts/market/market.clar], mirrored in [File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` batches liquidations by mapping over positions and calling `call-liquidate`, which invokes the public function `liquidate` as a **bare local function call** (no `contract-call?`), and wraps the whole result in `(ok (map call-liquidate positions))` unconditionally. [1](#0-0) [2](#0-1) 

### Finding Description
Inside `liquidate`, all the *pre*-mutation preconditions (`ERR-LIQUIDATION-PAUSED`, `ERR-AUTHORIZATION`, `ERR-AMOUNT-ZERO`, `ERR-ZERO-LIQUIDATION-AMOUNTS`, `ERR-SLIPPAGE`) are checked before any state-mutating cross-contract calls. [3](#0-2) 

But after those checks pass, `liquidate` performs `vault-system-repay`, then `market-vault debt-remove-scaled`, then `market-vault collateral-remove` — i.e. it repays debt in the vault and transfers seized collateral to the liquidator — and **only afterward**, if the position ends up with `no-collateral-left`, attempts bad-debt socialization for any remaining debt assets via a `fold` over `socialize-debt-asset`, asserting success at the very end with `ERR-BAD-DEBT-SOCIALIZATION-FAILED`. [4](#0-3) [5](#0-4) 

`socialize-debt-asset` itself calls `.vault-* socialize-debt` and `market-vault debt-remove-scaled` for each remaining debt asset, using `unwrap!` to short-circuit on failure. [6](#0-5) 

When `liquidate` is called directly by a user through `contract-call?`, Clarity's per-`contract-call?` rollback guarantee means that if the final `asserts!` (`ERR-BAD-DEBT-SOCIALIZATION-FAILED`) fails, the entire call frame — including the earlier `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` mutations that already succeeded — is unwound, because `liquidate` itself is the boundary of that `contract-call?`.

However, `liquidate-multi` does not call `liquidate` through `contract-call?`; `call-liquidate` invokes it as a bare, same-contract function application: [2](#0-1) 

A bare function call does not establish its own rollback frame the way `contract-call?` does. The rollback boundary in this batched path is the *entry point* `liquidate-multi`, not the inlined `liquidate` execution. Because `liquidate-multi` unconditionally wraps the mapped results in `(ok ...)` regardless of whether any individual `liquidate` invocation returned `(err ...)`, and because the comment explicitly documents this as intentional ("Failed liquidations return error codes but don't revert entire batch"), the top-level transaction commits successfully even when one entry's `liquidate` execution failed partway through its own body — after its debt/collateral mutations to `.vault-*` and `.market-vault` had already been made via genuine (and therefore committed) `contract-call?`s, but before the corresponding bad-debt write-off completed. [7](#0-6) 

This is the "fold/map that absorbs failure" pattern: the batch wrapper is designed to let individual failures produce an error entry, but the design assumption (that a failing `liquidate` leaves no partial state) only holds for the single-call path invoked via `contract-call?`; it silently breaks for the bare-call batched path, because the mutations that occurred earlier in the same `liquidate` execution (debt repayment in the vault, collateral transfer to the liquidator, and debt removal in `market-vault`) are not covered by any rollback boundary when the terminal bad-debt-socialization `asserts!` trips.

### Impact Explanation
If a batched liquidation entry reaches the point where the position has no collateral left and the fold-based bad-debt socialization for the *remaining* debt assets fails (e.g., a targeted vault's `socialize-debt` rejects the call under some edge condition), the transaction as a whole still returns `(ok ...)`. In that entry:
- The debt asset actually being liquidated has already been repaid in the vault and removed from the borrower's scaled debt via `market-vault debt-remove-scaled`.
- The collateral has already been transferred to the liquidator via `market-vault collateral-remove`.
- The *other* remaining debt on the now-collateral-less borrower is never written off (bad debt not socialized), so the vault(s) continue to carry that debt as a recoverable receivable indefinitely, even though the position has zero collateral backing it.

This permanently corrupts vault accounting (liabilities overstated relative to recoverable assets), which is a form of protocol insolvency and can lead to later suppliers being unable to redeem correctly — falling under the in-scope "protocol insolvency" / "permanent freezing of funds" impact classes.

### Likelihood Explanation
Exploitation requires: (a) a borrower position that is liquidatable and ends up fully collateral-drained by the liquidation (`no-collateral-left`), (b) more than one debt asset on that position so the fold has something to socialize, and (c) the ability to make the nested `vault-*.socialize-debt` call fail for the remaining debt asset (e.g. a caps/authorization/pause edge condition in that specific vault at that time). This is a specific but reachable combination reachable purely through normal `liquidate-multi` usage by any liquidator — no privileged access, oracle manipulation, or flashloan required. Likelihood is moderate: it depends on being able to trigger the inner vault call's failure deliberately or via a race, but the batch entry point itself is unauthenticated and public.

### Recommendation
Route batched liquidation through the same rollback boundary the single-call path relies on, e.g. call `liquidate` via `(as-contract? ... (contract-call? .market liquidate ...))` (or an equivalent explicit `contract-call?` self-reference) inside `call-liquidate`, so a failing `asserts!` anywhere inside that invocation correctly unwinds all of its own state mutations before the error is captured into the batch's response list. Alternatively, restructure `liquidate` so all mutation-causing operations (vault repay, debt/collateral removal, bad-debt socialization) are validated/attempted atomically before any of them commit, rather than relying on a trailing `asserts!` to catch failures after the state has already changed.

### Proof of Concept
1. Liquidator calls `liquidate-multi` with one position `P` for borrower `B`, who holds debt in two assets (`debt-aid` being liquidated, plus a second `other-debt-aid`), and whose collateral will be fully exhausted by this single liquidation (`no-collateral-left` becomes true). [8](#0-7) 
2. `call-liquidate` invokes `(liquidate B ...)` as a bare call (no `contract-call?`). [2](#0-1) 
3. Inside `liquidate`, preconditions pass, then `vault-system-repay`, `market-vault debt-remove-scaled`, and `market-vault collateral-remove` all execute successfully, transferring `B`'s remaining collateral to the liquidator and clearing the liquidated debt asset. [9](#0-8) 
4. Because `no-collateral-left` is true, the code attempts to socialize `other-debt-aid` via the `fold` over `socialize-debt-asset`; the nested `.vault-* socialize-debt` call for `other-debt-aid` fails (e.g. due to a vault-level guard), so `socialization-result` has `success: false`, and the trailing `asserts!` returns `ERR-BAD-DEBT-SOCIALIZATION-FAILED` from `liquidate`. [10](#0-9) 
5. Because `liquidate` was invoked as a bare call (step 2), this `err` return does not unwind the mutations already committed in step 3. `call-liquidate` returns this error response as an ordinary value, `map` collects it into the results list, and `liquidate-multi` still returns `(ok (list ... (err u...) ...))` for the whole transaction. [1](#0-0) 
6. Net effect: the liquidator keeps the seized collateral and the liquidated debt is cleared, but `B`'s `other-debt-aid` debt remains recorded on a position with zero collateral and is never socialized, permanently corrupting that vault's liability accounting.

;; Liquidates multiple positions atomically
