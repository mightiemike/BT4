Attached deposit is permanently lost when the Wallet Contract's address-registrar cross-contract call fails during an ETH-emulated base-token transfer to another eth-implicit account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract's `rlp_execute` entry point can be called by any unprivileged relayer/caller who attaches a NEAR deposit to fund an emulated Ethereum base-token transfer. `CallerDeposit` is tracked precisely so it can be refunded if the downstream cross-contract call fails [1](#0-0) . However, when the transfer target is another eth-implicit account, `inner_rlp_execute` first calls a hardcoded external "address registrar" account (`ADDRESS_REGISTRAR_ACCOUNT_ID`) via `.lookup(...)`, and only forwards to the deposit-aware `rlp_execute_callback` path if that lookup succeeds and the target is not already registered [2](#0-1) . If that registrar call itself fails (`PromiseResult::Failed`), `address_check_callback` returns an error response directly without ever inspecting or refunding `caller_deposit` [3](#0-2) .

### Finding Description
`rlp_execute` computes `caller_deposit` from the attached deposit and the predecessor account (i.e. whoever paid), specifically to guarantee a refund if the subsequent cross-contract call fails [4](#0-3) . This "refund on failure" invariant is only implemented in one place, `rlp_execute_callback`, which checks `PromiseResult::Failed` and issues a `promise_batch_action_transfer` back to `account_id` before returning failure [5](#0-4) .

But for `EOABaseTokenTransfer { address_check: Some(address), .. }` (a base-token transfer whose target is another eth-implicit account), execution is routed instead through the address-registrar lookup and `address_check_callback`, not through `rlp_execute_callback`, on the failure path [2](#0-1) . `address_check_callback` receives `caller_deposit` as a parameter [6](#0-5) , but on `PromiseResult::Failed` (i.e., the registrar call itself fails — which will always happen if the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` account does not exist, is not deployed, or does not implement the expected `lookup` interface — directly analogous to the external report's hardcoded/misconfigured oracle address that doesn't expose the expected function) it silently drops `caller_deposit` and returns a failure response without issuing any refund [7](#0-6) . The `Unexpected response from account registrar` deserialization-failure branch has the exact same problem [8](#0-7) .

The existing test suite (`test_caller_refunds`) only validates that a refund occurs when the ultimate action's cross-contract call fails through `rlp_execute_callback`; it does not exercise the address-registrar failure branch of `address_check_callback` at all [9](#0-8) , confirming this refund gap is untested and unhandled.

Because the deposit is transferred from the caller's account to the wallet contract account atomically as part of the receipt when `rlp_execute` is invoked (this is standard NEAR attached-deposit semantics — the deposit is credited to the receiver before contract logic runs, and only refunded by an explicit follow-up transfer the contract issues), any code path that terminates without issuing that follow-up transfer permanently strands the caller's yoctoNEAR in the wallet contract's balance with no way to reclaim it (the contract exposes no method to withdraw or reprocess these stranded funds).

### Impact Explanation
This is a concrete, transaction-triggered unauthorized-value-freeze: an external caller's attached NEAR deposit (used to fund gas/fees for relaying an EVM-emulated transfer) is permanently and irrecoverably locked in the Wallet Contract's account whenever the hardcoded address-registrar cross-contract call fails or returns malformed data — which is guaranteed to happen for any misconfigured/undeployed/wrong-interface registrar account, and can also be triggered intermittently by legitimate registrar outages or gas exhaustion on that call. Every relayer submitting this specific transaction pattern (`EOABaseTokenTransfer` to another eth-implicit account) loses their deposit with no recourse, matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
High. This requires no privileged access — any account (a normal unprivileged relayer or the account owner themself) can submit an `rlp_execute` call with `target` set to another eth-implicit account and a non-zero attached deposit. The only trigger condition is that the registrar cross-contract call fails or its response fails to deserialize into `Option<AccountId>`, both of which are entirely plausible operational conditions (wrong/undeployed registrar account, registrar contract upgrade changing its return schema, registrar running out of gas, etc.), not requiring any malicious validator/node behavior.

### Recommendation
In `address_check_callback`, mirror the refund logic from `rlp_execute_callback` on both the `PromiseResult::Failed` branch and the response-deserialization-failure branch: if `caller_deposit` is `Some(CallerDeposit { account_id, yocto_near })`, issue a `promise_batch_action_transfer` back to `account_id` for `yocto_near` before returning the `ExecuteResponse` in each of those early-return paths, exactly as done in `rlp_execute_callback` [5](#0-4) .

### Proof of Concept
1. Deploy the Wallet Contract normally on an eth-implicit account `A`, with the compiled-in `ADDRESS_REGISTRAR_ACCOUNT_ID` pointing at an account that either does not exist, is not deployed, or does not implement `lookup(address: String) -> Option<AccountId>` (this can occur simply because that constant is baked into the WASM at build time via `include_str!`, so any environment where the registrar account differs from the one used at compile time reproduces this deterministically) [10](#0-9) [11](#0-10) .
2. As any external caller `C`, sign and submit an RLP transaction representing a base-token transfer whose `to` address corresponds to a different eth-implicit account `B` (not `A`), and call `A.rlp_execute(target=B, tx_bytes_b64=..)` attaching a NEAR deposit (e.g. 3 NEAR), as in the existing `test_caller_refunds` harness [12](#0-11) .
3. `inner_rlp_execute` detects `EOABaseTokenTransfer { address_check: Some(address), .. }` and issues the registrar `.lookup(...)` call, chaining `address_check_callback` [2](#0-1) .
4. Because the registrar account is misconfigured/unreachable, its cross-contract call resolves to `PromiseResult::Failed`.
5. `address_check_callback` matches this case and returns `ExecuteResponse { success: false, ... }` without ever emitting a transfer back to `C` [7](#0-6) .
6. Observe `C`'s account balance: it is reduced by the full attached deposit with no refund receipt ever generated, contrasted with the `test_caller_refunds` test's first scenario where a failing downstream call *does* refund the caller through `rlp_execute_callback` [13](#0-12) .

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
