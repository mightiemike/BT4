## Title
Missing slippage/minimum-output protection in `ExchangeWithdrawContract` enables front-running/sandwich extraction of exchange liquidity - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The TRON on-chain "Exchange" (a Bancor-style constant-relay-based token-pair AMM) allows an exchange creator to withdraw both sides of the pool proportionally via `ExchangeWithdrawContract`. Unlike `ExchangeTransactionContract`, which carries an `expected` field to bound the minimum output received from a trade, `ExchangeWithdrawContract` has no equivalent slippage/minimum parameter for the computed `anotherTokenQuant`. This is the same bug class as the Curve `ThreePoolStrategy` finding: a withdrawal operation that computes a paired amount from pool state at execution time, with no caller-supplied floor to guard against that state being manipulated between submission and inclusion.

### Finding Description
`ExchangeWithdrawContract` only carries `exchange_id`, `token_id`, and `quant` (the amount of one side of the pool to withdraw) — there is no `expected`/minimum field, as confirmed by the protobuf definition: [1](#0-0) 

In `ExchangeWithdrawActuator.doValidate()`, the paired `anotherTokenQuant` is derived purely from the *current* `firstTokenBalance`/`secondTokenBalance` ratio of the exchange at validation time: [2](#0-1) 

`execute()` then independently *recomputes* `anotherTokenQuant` from whatever the exchange balances are at execution time: [3](#0-2) 

Because the two computations use live pool state rather than a caller-fixed minimum, any transaction that changes the pool ratio (e.g., an `ExchangeTransactionContract` trade) executed immediately before the withdrawal within the same block will change how much of `anotherTokenID` the withdrawer actually receives — and the withdrawer has no on-chain mechanism to reject an unfavorable outcome. This mirrors the Curve 3Pool report precisely: the withdrawal path lacks a caller-supplied minimum-output guard, so the value received is whatever the instantaneous (potentially manipulated) pool state yields, not a value the user can protect.

By contrast, `ExchangeTransactionActuator` explicitly validates `anotherTokenQuant >= tokenExpected` to protect traders: [4](#0-3) 

No such check exists for withdrawals or injections (`ExchangeInjectActuator` has the identical gap): [5](#0-4) 

### Impact Explanation
An attacker who can order transactions ahead of a pending `ExchangeWithdrawContract` (a block producer, or any actor able to submit a same-block trade before the withdrawal is packed) can shift the pool ratio via `ExchangeTransactionContract` trades, causing the withdrawer's `anotherTokenQuant` payout to be computed against a distorted ratio. This is a settlement/accounting impact: the withdrawer receives less value than the pool's fair-market ratio implied at submission time, and the attacker (via a follow-up trade reverting the ratio) can extract the difference — a classic sandwich attack against liquidity withdrawal, with no protocol-level minimum-output guard to prevent it, unlike the analogous `ExchangeTransactionContract` path.

### Likelihood Explanation
Any account can create an `Exchange` (the "creator" role checked in `doValidate()` — `!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` — is not a privileged system role, just ownership of a self-created pool), and any account can trade against it via `ExchangeTransactionContract`. Sandwiching a withdrawal only requires observing a pending withdrawal transaction and submitting trades before/after it in the same block, which is within reach of any network participant with transaction-ordering influence (including block-producing witnesses, who are part of the normal consensus set, not privileged in the "trusted internal" sense excluded by scope).

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (and `ExchangeInjectContract`), and enforce in `ExchangeWithdrawActuator.doValidate()`/`execute()` that the computed `anotherTokenQuant` is not less than the caller-supplied minimum, mirroring the check already present in `ExchangeTransactionActuator`: [4](#0-3) 

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from the exchange creator for `exchange_id=X`, `token_id=A`, `quant=Q`.
2. Attacker submits an `ExchangeTransactionContract` trade that shifts the `A:B` balance ratio in `exchange_id=X` unfavorably for the withdrawer, executed before the withdrawal in the same block (front-run).
3. The withdrawal executes: `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the now-skewed balances — see the ratio computation at: [6](#0-5) 
Since `ExchangeWithdrawContract` has no `expected` field, the withdrawal succeeds despite the unfavorable payout, unlike a trade which would have reverted via the `token required must greater than expected` check.
4. Attacker submits a second trade restoring the ratio, capturing the value difference extracted from the withdrawer.
