### Title
Gas fee bypass via integer truncation in `CalculateGasCost` allows free UEA/CEA payload execution when base fee < 1 upc - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` unwraps the feemarket base fee from its `LegacyDec` (18-decimal fixed point) representation by doing raw integer division by `1e18`, assuming the base fee is always a whole number of `upc`. If the dynamically-adjusted EIP-1559-style base fee is ever less than `1.0 upc` (a valid, non-privileged, protocol-computed value), the division truncates to `0`, making `effectiveGasPrice = 0` and `gasCost = 0` regardless of how much gas was actually consumed. This causes `DeductGasFeesFromReceipt` to silently skip charging the recipient, reopening exactly the "free execution" gap that the surrounding code explicitly says it closes.

### Finding Description
`CalculateGasCost` in [1](#0-0)  computes the effective gas price as:

```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```

The inline comment asserts "the base fee is always a whole number of upc — no fractional upc exists," but nothing in the codebase enforces that the feemarket's dynamically-computed `base_fee` (a `LegacyDec`, adjusted per block based on network utilization per EIP-1559 semantics) stays ≥ `1.0`. If `base_fee` decimal value is, say, `0.5`, its raw `LegacyDec` internal integer is `5×10^17`; dividing by `1e18` with Go's truncating integer division yields `0`. This zero then flows straight through as `effectiveGasPrice`, so:

```go
gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig) // == 0
```

`DeductGasFeesFromReceipt` at [2](#0-1)  then hits:

```go
if gasCost.Sign() <= 0 {
    return nil
}
```

and returns without charging anything, even though `receipt.GasUsed > 0` — i.e., the recipient/UEA consumed real EVM computation but the module never recovers the corresponding fee.

This mechanism is the sole safeguard against free execution for module-originated EVM calls. `ExecutePayloadV2` explicitly documents this intent: [3](#0-2)  — "closes the free-execution gap when the UEA has no native UPC to cover gas." The truncation bug reopens precisely this gap under a different (but easily reachable, non-privileged) condition: a low base fee, rather than an empty UEA balance.

The same `CalculateGasCost`/`DeductGasFeesFromReceipt` pair is also invoked from the inbound funds+payload and gas+payload execution paths ( [4](#0-3)  and [5](#0-4) ), so the bypass applies broadly to universal execution, not just `MsgExecutePayload`.

### Impact Explanation
When the feemarket's dynamic base fee decimal value drops below `1.0 upc` (which can occur naturally during sustained low block utilization per the EIP-1559-style adjustment algorithm, without any admin/validator/attacker privilege), every UEA/CEA payload execution routed through `ExecutePayloadV2` or the inbound execution keepers becomes fee-free regardless of `GasUsed`. An unprivileged attacker can submit arbitrarily gas-heavy universal payloads (up to `GasLimit`) that consume real module-account-funded EVM computation while paying zero `upc`, draining protocol resources and breaking the gas-fee accounting invariant (`gas accounting must not misroute value / must not allow unauthorized fee-free module-originated EVM execution`). This is a corruption of gas fee accounting reachable purely through ordinary user payload submission with honest validators/nodes.

### Likelihood Explanation
Reaching a base fee below `1.0 upc` requires no attacker privilege — it is a natural steady-state outcome of an EIP-1559-style base-fee-decrease mechanism during periods of low network usage, especially early in the chain's life or during quiet periods, given `upc` is the base (non-fractional, atto-like) denomination. The only "action" needed by the attacker is to wait for/observe such a period and then submit a normal, unprivileged payload execution transaction — no malicious peer, validator, or governance action is required.

### Recommendation
Do not silently truncate the base fee to `0`; instead:
- Round up (`Ceil`) the `LegacyDec` base fee, or preserve the fractional/wei-level precision through the whole computation (e.g., multiply `gasUsed` first, then divide once at the end), so a positive base fee never collapses to a zero effective gas price.
- Alternatively, enforce a protocol-level floor (e.g., minimum `1 upc`) on the feemarket base fee value consumed by `CalculateGasCost`, or explicitly reject/charge a minimum nonzero fee whenever `baseFee.IsPositive()` but the truncated integer would be zero.
- Add a regression test asserting that any `baseFee` in `(0, 1.0)` upc combined with nonzero `gasUsed` produces a strictly positive `gasCost`.

### Proof of Concept
1. Let the feemarket base fee (via normal EIP-1559-style adjustment, no privileged action) settle at a decimal value `0.9` `upc` (raw `LegacyDec` internal value `9×10^17`).
2. Attacker submits (or triggers via inbound vote flow) a `MsgExecutePayload`/inbound payload with `GasLimit` sufficient for substantial computation, e.g. consuming `500,000` gas in `CallUEAExecutePayload`.
3. In `CalculateGasCost`: `baseFeeBig.Div(9e17, 1e18) == 0` → `effectiveGasPrice = 0` → `gasCost = 0 * 500000 = 0`.
4. `DeductGasFeesFromReceipt` sees `gasCost.Sign() <= 0` and returns `nil` without deducting/burning any `upc` from the recipient.
5. `writeCache()` commits the full EVM state changes from the executed payload — the attacker obtained real, non-trivial EVM execution against the module account entirely free of gas cost.

	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	// This division unwraps the LegacyDec encoding back to the actual upc amount.
