### Title
Underflow-triggered chunk-apply halt when subsidized zero-balance-account (ZBA) deductions exceed total burnt balance - ([File: chain/chain/src/runtime/mod.rs])

### Summary
`chain/chain/src/runtime/mod.rs` computes `total_balance_burnt` by subtracting the chunk's accumulated `subsidized_amount` (tokens effectively minted by skipping the 1-yoctoNEAR deduction on zero-balance accounts) from the sum of burnt balances, using `checked_sub` that returns a hard `Error::Other` on underflow instead of clamping to zero, unlike the Centrifuge fix that clamps a similarly "should never happen" NAV subtraction to zero.

### Finding Description
The `subsidized_amount` mechanism (`one_yocto_on_promise`) allows a zero-balance deterministic account to skip the 1-yoctoNEAR balance deduction when attaching exactly 1 yoctoNEAR to a promise function call, tracked via `ExecutionResultState::subsidized_amount` and aggregated into `ChunkApplyStatsV1.subsidized_amount` as documented at [1](#0-0) . This exemption fires in `promise_batch_action_function_call_weight` and the yield/resume equivalent whenever `current_account_balance.is_zero()` and the attached amount is exactly 1 yoctoNEAR, incrementing `subsidized_amount` instead of calling `deduct_balance` [2](#0-1) .

At the end of chunk application, `chain/chain/src/runtime/mod.rs` computes the total burnt balance and then subtracts the cumulative subsidized amount from it: [3](#0-2) 

The comment explicitly acknowledges the underflow is "theoretically" possible ("this may become negative but the subsidized amount is many orders of magnitude lower than the burned amount... so it should not happen") — the exact same class of assumption that caused the Centrifuge NAV bug ("should never happen", but a miscomputed intermediate value led to underflow). Unlike Centrifuge's fix (clamp to zero), nearcore's handling here converts the underflow into a hard `Error::Other("subsidized amount exceeds total burnt balance")`, which propagates up from `apply_chunks`/`apply_transactions` as an unrecoverable chain error, unlike the graceful invalid-tx rejection paths used elsewhere.

Because a single account can be driven to zero balance and then repeatedly invoke a function-call promise or yield-resume promise attaching exactly 1 yoctoNEAR (each such invocation increments `subsidized_amount` per receipt, and stats are aggregated across all receipts processed in the chunk — see the multi-account accumulation test at [4](#0-3) ), an attacker who controls many zero-balance accounts (or repeatedly zeroes and re-triggers the exemption across many receipts in the same chunk) can inflate the chunk-level `subsidized_amount` counter. If the aggregate ever exceeds the chunk's total burnt balance (`tx_burnt_amount + other_burnt_amount + slashed_burnt_amount`), the `checked_sub` at line 406 returns `None`, producing an `Error::Other`.

### Impact Explanation
If this error path is reachable by a chunk composed largely of many low-cost/high-count subsidized 1-yocto promise calls relative to burnt gas fees (e.g., minimal gas usage per call keeping `tx_burnt_amount` low while `subsidized_amount` accumulates per-receipt), then this becomes a transaction-triggered chunk-apply failure. Given the surrounding error-handling pattern in this file, unhandled/`Other` errors from chunk application are treated as chain-level failures rather than being rejected as an invalid transaction — this is a state-transition acceptance/halt-class issue rather than a value-movement bug, since the subtraction is clamped to error instead of proceeding, differing from the Centrifuge case (which continued with clamped value); here it instead aborts the chunk apply.

### Likelihood Explanation
The exemption is capped at exactly 1 yoctoNEAR per triggering call and only applies once per receipt when the account balance is exactly zero, so accumulating enough `subsidized_amount` to exceed the chunk's total burnt balance requires an extremely large number of qualifying receipts within a single chunk with disproportionately small gas burn per receipt — a scenario that is gas-limited by the chunk gas limit and each call still burns non-trivial gas for the promise/function-call actions themselves (base + per-byte + prepaid gas costs are still charged, as seen in `pay_action_base`/`pay_action_per_byte`/`prepay_gas` calls surrounding the skip-deduct branch at [5](#0-4) ). This makes the burnt-gas denominator grow roughly in proportion to the subsidized numerator, which likely keeps the subtraction non-negative in practice — consistent with the code comment's assumption. I could not fully verify the exact gas/subsidy ratio bounds or whether any path allows burning near-zero gas while still qualifying for the subsidy exemption, so the exploitability of actually reaching the underflow condition remains unconfirmed.

### Recommendation
Given the same "should never happen but if it does, don't crash the chain" philosophy as the Centrifuge fix, consider replacing the `checked_sub(...).ok_or_else(...)` pattern in `chain/chain/src/runtime/mod.rs` (lines 405-408) with a `saturating_sub`, while logging/alerting on the underflow condition rather than converting it into a hard chain error, to avoid a transaction-triggered halt if the invariant is ever violated (e.g., through a future protocol change to the subsidy mechanism, a bug in per-receipt aggregation, or an unforeseen combination of receipts). Any such change is itself a protocol-relevant modification and should be gated behind a protocol feature/version if adopted.

### Proof of Concept
Not concretely demonstrated — I could not construct a proof of concept showing the underflow is practically reachable within a single chunk's gas limit, since each subsidized call still burns non-negligible gas for the promise/function-call action itself. The finding is presented as the closest structural analog to the reported bug class (an underflow-guarding subtraction predicated on an assumption that "should never happen"), but confirming actual exploitability would require chunk-level gas/fee-cost modeling that is outside what I could verify with the available context.
