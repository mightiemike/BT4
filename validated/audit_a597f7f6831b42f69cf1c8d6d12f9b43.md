### Title
Nonce-check ordering in `validate_tx_relayer_data` allows unlimited nonce exhaustion via a single user-signed deploy-format transaction — (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

---

### Summary

In `validate_tx_relayer_data`, the `tx.to == None` guard that produces `Error::User(UserError::EvmDeployDisallowed)` fires at line 332, **before** the nonce-equality check at lines 352–358. Because `inner_rlp_execute` unconditionally increments the wallet nonce for every `Error::User(_)` variant, and because `has_in_flight_tx` is **not** set on that error path, an attacker who obtains a single user-signed deploy-format transaction can replay it an unlimited number of times, incrementing the wallet nonce by 1 on each submission until `u64::MAX` is reached and the wallet is permanently bricked.

---

### Finding Description

**Step 1 — Ordering of checks in `validate_tx_relayer_data`**

The function performs checks in this order:

1. Signature / sender check (line 324) — must pass; requires a valid user signature.
2. Chain-ID check (lines 328–330).
3. **`tx.to` check (line 332)** — returns `Err(Error::User(UserError::EvmDeployDisallowed))` immediately if `tx.to == None`.
4. Nonce check (lines 352–358) — **never reached** when `tx.to == None`. [1](#0-0) 

Because the function returns at line 332, the transaction's embedded nonce (`tx.nonce`) is never compared against `expected_nonce`. The wallet's own nonce counter is therefore incremented without any proof that the submitted transaction's nonce matches the current wallet state.

**Step 2 — Unconditional nonce increment on `Error::User`**

Back in `inner_rlp_execute`, the `Err(err @ Error::User(_))` arm increments `*nonce` and returns the error: [2](#0-1) 

**Step 3 — `has_in_flight_tx` is not set on this error path**

In `rlp_execute`, only the `Ok(promise)` branch and the `Err(Error::Relayer(_))` branch set `self.has_in_flight_tx = true`. The `Err(e) => PromiseOrValue::Value(e.into())` arm — which handles `Error::User` — leaves `has_in_flight_tx = false`: [3](#0-2) 

This means there is no in-flight guard preventing the attacker from immediately resubmitting the same signed bytes.

**Step 4 — Replay loop**

Because the transaction's nonce is never validated for the `EvmDeployDisallowed` path, the exact same RLP-encoded bytes (same signature, same `tx.nonce` field, e.g. `999`) can be submitted repeatedly. Each submission:

- passes the signature check (valid user signature),
- passes the chain-ID check,
- hits line 332 and returns `EvmDeployDisallowed`,
- increments the wallet's `self.nonce` by 1,
- leaves `has_in_flight_tx = false`.

The attacker repeats until `self.nonce == u64::MAX`, at which point `inner_rlp_execute` returns `Error::AccountNonceExhausted` on every future call: [4](#0-3) 

The wallet is permanently unable to execute any action.

---

### Impact Explanation

A single user-signed deploy-format Ethereum transaction is sufficient for an attacker to exhaust the wallet's 64-bit nonce space. Once `self.nonce` reaches `u64::MAX`, every subsequent call to `rlp_execute` returns `AccountNonceExhausted` and no Near action can ever be dispatched from that wallet again. All funds locked in the wallet become inaccessible through the normal execution path. This is a permanent, irreversible contract execution flow breakage for the targeted account.

---

### Likelihood Explanation

The attacker must obtain one user-signed Ethereum transaction with `tx.to == None`. A malicious or compromised dApp front-end can present such a transaction as a routine interaction (e.g., disguised as a contract deployment the user believes is harmless). Once obtained, the replay requires no further user interaction and costs only gas for the attacker. The `has_in_flight_tx` guard provides no protection because it is not set on the `Error::User` path.

---

### Recommendation

Move the nonce equality check **before** the `tx.to` check inside `validate_tx_relayer_data`. A transaction whose nonce does not match the expected wallet nonce should be rejected as a `RelayerError::InvalidNonce` (which does not increment the wallet nonce) before any user-error classification is attempted. This ensures that even a deploy-format transaction with a mismatched nonce cannot consume a wallet nonce slot, and that a correctly-nonced deploy-format transaction can only consume the nonce once (since the next submission will have a stale nonce and be rejected as a relayer error).
