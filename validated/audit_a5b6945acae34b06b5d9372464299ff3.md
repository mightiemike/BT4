Based on the investigation, I found a genuine analog. The rescue-funds flow contains a "duplicate rescue" guard that operates exactly like the original bug's "special counter always wins" pattern: whichever `RescueFundsOnSourceChain` event lands first claims the `PENDING` slot for the UTX and blocks every subsequent (possibly correct/higher-value) rescue attempt until the first one resolves to `REVERTED`.

### Title
Rescue-outbound "first wins" lock lets any caller front-run and grief a stuck UTX's rescue slot, delaying fund recovery for the rightful depositor - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`AttachRescueOutboundFromReceipt` attaches a `RESCUE_FUNDS` outbound to a stuck `UniversalTx` whenever it observes a `RescueFundsOnSourceChain` event from `UniversalGatewayPC`. Eligibility is keyed purely off the *UTX's* state (deposit `FAILED` for CEA, or `INBOUND_REVERT` = `REVERTED` for non-CEA) — not off who calls `rescueFunds()` on the source chain. Once one such event is processed, a duplicate-guard blocks all further rescue attachments for that UTX until the first one reaches a terminal `REVERTED` state, mirroring the reported bug's "special counter always wins the subgame" pattern where whoever lands the qualifying call first locks out everyone else regardless of merit. [1](#0-0) 

### Finding Description
`AttachRescueOutboundFromReceipt` is invoked from the EVM post-processing hook on every transaction (`EVMHooks.PostTxProcessing`), so any log emitted by the real `UniversalGatewayPC` contract with the `RescueFundsOnSourceChain` signature is processed automatically and permissionlessly for whichever `universalTxId` it references: [2](#0-1) 

The eligibility check only inspects the *target UTX's* own status fields (`PcTx[0].Status == "FAILED"` for CEA, or an existing `REVERTED` `INBOUND_REVERT` outbound for non-CEA) — it does not require the caller of `rescueFunds()` on the source-chain gateway to be the original depositor or `RevertInstructions.FundRecipient`: [3](#0-2) 

Immediately after eligibility passes, the code enforces a strict "only one active rescue at a time" invariant per UTX, rejecting any second `RescueFundsOnSourceChain` event while the first rescue outbound is `PENDING` or `OBSERVED`: [1](#0-0) 

Because the gas parameters (`GasFee`, `GasPrice`, `GasLimit`) attached to the outbound are taken verbatim from the event data supplied by whoever triggered the source-chain `rescueFunds()` call (not validated against the original inbound's amounts), any unprivileged party who can trigger this event first — e.g. with a minimal/insufficient `gasLimit`/`gasFee` — occupies the rescue slot for that UTX. This mirrors the external report's root cause precisely: a "special" fast path exists whose *first caller* wins priority over the state machine, regardless of whether that caller is the legitimate beneficiary, and it blocks the rightful party's competing (correct) action from being recorded until the first one plays out and fails: [4](#0-3) 

The recipient of the eventual payout is still bound to `originalUtx.InboundTx.RevertInstructions.FundRecipient` (or the original sender) regardless of who triggered the rescue, so funds cannot be stolen outright — [5](#0-4)  — but the *timing* and *gas parameters* of the recovery attempt are entirely controlled by whichever unprivileged caller reaches the gateway first, which is the same "priority hijack" class of bug as `challengeRootL2Block`.

### Impact Explanation
This does not enable theft of funds (recipient is fixed by the original inbound's `RevertInstructions`), so it falls short of "unauthorized release"/"unauthorized refund" in the strict sense. Its concrete impact is: an unprivileged attacker can grief the recovery of *any* stuck UTX system-wide by front-running the legitimate rescue with a garbage/no-op rescue call (e.g., trivial gas parameters likely to fail or stall on the source chain), locking the `RESCUE_FUNDS` slot to `PENDING`/`OBSERVED` and delaying the rightful party's real recovery attempt until the attacker's junk attempt resolves to `REVERTED`. This is a denial-of-service on the rescue/recovery path for locked user funds, reachable without any privileged role.

### Likelihood Explanation
Likely low-to-medium in practice: the attacker must be able to call the source-chain gateway's `rescueFunds()` for an arbitrary `universalTxId` (that part lives in Solidity, outside this repo's scope, so whether it is truly permissionless per-UTX cannot be fully confirmed from the Go code alone) and must race the legitimate caller to be first. The Go-side guard itself (`AttachRescueOutboundFromReceipt`'s "already has an active rescue outbound" check) unconditionally enforces the lock with no distinction between caller identities, so once the precondition (permissionless `rescueFunds` call) holds, the griefing is trivial and repeatable per stuck UTX.

### Recommendation
Either (a) scope the duplicate-rescue guard per-caller/per-fund-recipient so a non-beneficiary's rescue attempt cannot block the legitimate depositor's own rescue attempt, or (b) require the source-chain `rescueFunds()` caller to match `RevertInstructions.FundRecipient`/original sender before the event is honored on the Push Chain side, or (c) allow the legitimate recipient to supersede/cancel a pending rescue outbound that was not initiated by them.

### Proof of Concept
1. A UTX becomes rescue-eligible (CEA deposit `FAILED`, or non-CEA `INBOUND_REVERT` reaches `REVERTED`).
2. An unprivileged attacker (anyone able to call the source-chain gateway's `rescueFunds` for that `universalTxId`) triggers a `RescueFundsOnSourceChain` event with minimal/garbage `gasFee`/`gasLimit` before the legitimate depositor does.
3. `AttachRescueOutboundFromReceipt` attaches a `RESCUE_FUNDS` outbound in `PENDING` status, as shown by the existing test `TestRescueFunds/second_rescue_is_rejected_when_first_is_PENDING` [6](#0-5) .
4. The legitimate depositor's subsequent (correctly-funded) rescue attempt is rejected with `"already has an active rescue outbound"` until the attacker's junk rescue resolves to `REVERTED` on the destination chain, delaying real fund recovery with no cost/authorization required from the attacker.

// RescueFundsOnSourceChainEvent holds decoded data from the RescueFundsOnSourceChain
// event emitted by UniversalGatewayPC when a user initiates a rescue on the source chain.
type RescueFundsOnSourceChainEvent struct {
	UniversalTxId  string   // 0x-prefixed bytes32 — the original UTX whose funds are stuck
	PRC20          string   // 0x-prefixed address — PRC20 token whose counterpart is locked
	ChainNamespace string   // source chain namespace (e.g. "eip155")
	Sender         string   // 0x-prefixed address — user who initiated the rescue
	TxType         TxType   // always TxType_RESCUE_FUNDS
	GasFee         *big.Int // gas fee charged (in gas-token units)
	GasPrice       *big.Int // gas price on the source chain
	GasLimit       *big.Int // gas limit used for the rescue execution
}
