### Title
`ProtocolVersionTooOld` Re-Entry Bar Expires After One Epoch, Allowing a Kicked Validator to Re-Enter Without Upgrading — (`chain/epoch-manager/src/validator_selection.rs`)

---

### Summary

`apply_epoch_update_to_proposals` guards against immediate re-entry of a validator kicked for `ProtocolVersionTooOld` by checking `prev_epoch_info.validator_kickout()`. Because `prev_epoch_info` is always the EpochInfo for the epoch immediately preceding the one being computed, this guard covers exactly **one** epoch transition. A validator kicked in epoch T can bypass the guard entirely by submitting a re-stake proposal in epoch T+2, re-entering the validator set in T+4 without ever upgrading their protocol version.

---

### Finding Description

**The T+2 rule.** `finalize_epoch` at the end of epoch T computes EpochInfo for T+2 and passes `next_epoch_info` (T+1's EpochInfo) as `prev_epoch_info` to `proposals_to_epoch_info`: [1](#0-0) 

Inside `apply_epoch_update_to_proposals`, two checks gate a proposal: [2](#0-1) 

**Epoch-by-epoch trace:**

| Epoch boundary | `prev_epoch_info` | `validator_kickout` (current) | Attacker's proposal outcome |
|---|---|---|---|
| End of T → computing T+2 | T+1's EpochInfo | Contains attacker (`ProtocolVersionTooOld`) | Blocked by check 1 (`validator_kickout`). T+2's EpochInfo stores attacker in its `validator_kickout`. |
| End of T+1 → computing T+3 | T+2's EpochInfo | Does NOT contain attacker (not a validator in T+1) | Blocked by check 2 (`prev_epoch_info.validator_kickout()` = T+2's kickout, which has attacker). T+3's EpochInfo does NOT store attacker in its `validator_kickout`. |
| End of T+2 → computing T+4 | T+3's EpochInfo | Does NOT contain attacker (not a validator in T+2) | **Neither check fires.** T+3's kickout has no entry for the attacker. Proposal accepted. Attacker enters T+4's validator set. |

The comment at line 306 says "it is not allowed back in T" (one epoch), which is exactly what the code enforces — and exactly one epoch short of what is needed to close the two-epoch window. [3](#0-2) 

The existing test `test_version_switch_kickout_old_version` only asserts that a proposal submitted in T+1 is rejected. It does not test the T+2 proposal path, leaving the bypass untested. [4](#0-3) 

---

### Impact Explanation

- **Balance manipulation / staking reward bypass**: The attacker earns staking rewards in T+4 (and every subsequent T+4k) without upgrading their node. Reward magnitude scales with the attacker's stake.
- **Consensus disruption**: An old-version node is admitted into the active validator set. If the running binary is incompatible with the current protocol version (e.g., does not enforce `EnforcePerReceiptStorageProofLimit` at v86), it may produce chunks or blocks that honest nodes reject, causing missed-block/chunk penalties and potential short-term liveness degradation for the shards the attacker is assigned to. The attacker is kicked again at the end of T+4, so the disruption is bounded to one epoch per cycle.

---

### Likelihood Explanation

Any account that was previously a validator and was kicked for `ProtocolVersionTooOld` can exploit this by submitting a standard `Stake` action two epochs later — no privileged access, no key compromise, no off-chain coordination required. The action is a normal runtime transaction available to any staker.

---

### Recommendation

Extend the `ProtocolVersionTooOld` bar to cover the full two-epoch window. One approach: in `apply_epoch_update_to_proposals`, also check the kickout stored in the epoch before `prev_epoch_info` (i.e., `prev_prev_epoch_info.validator_kickout()`), or pass a dedicated `stale_version_accounts` set that persists the bar for two transitions. Alternatively, record a `ProtocolVersionTooOld` kickout in T+3's EpochInfo for accounts whose T+1 proposal was silently dropped, so the check fires again at the T+2 boundary.

fn apply_epoch_update_to_proposals(
    proposals: Vec<ValidatorStake>,
    prev_epoch_info: &EpochInfo,
    validator_reward: &HashMap<AccountId, Balance>,
    validator_kickout: &HashMap<AccountId, ValidatorKickoutReason>,
    stake_change: &mut BTreeMap<AccountId, Balance>,
) -> HashMap<AccountId, ValidatorStake> {
    let mut proposals_by_account = HashMap::new();
    for p in proposals {
        let account_id = p.account_id();
        if validator_kickout.contains_key(account_id) {
            let account_id = p.take_account_id();
            stake_change.insert(account_id, Balance::ZERO);
        } else if let Some(ValidatorKickoutReason::ProtocolVersionTooOld { .. }) =
            prev_epoch_info.validator_kickout().get(account_id)
        {
            // If the validator was kicked out because of an old protocol version in T-1,
            // it is not allowed back in T.
            continue;
        } else {
            stake_change.insert(account_id.clone(), p.stake());
            proposals_by_account.insert(account_id.clone(), p);
        }
    }
