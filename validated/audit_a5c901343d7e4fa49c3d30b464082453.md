## Title
Ancient-slot squash can silently drop carry-forward tombstones for not-yet-purgeable zero-lamport accounts, causing a snapshot-vs-replay hash mismatch - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
This is analogous to the Sherlock finding where a code path (`swivelLendPremium`) silently skips a required accounting step (protocol fee extraction) that its sibling code path always performs. In agave's ancient-append-vec squashing path, `finish_combine_ancient_slots_packed_internal` silently drops any `tombstones_to_carry_forward` produced by `shrink_collect`, relying only on a `debug_assert!` (compiled out in release builds) to guarantee this never happens, whereas the normal (non-ancient) shrink path in `remove_old_stores_shrink` / `shrink_collect` correctly rewrites these tombstones when they are not yet purgeable.

### Finding Description
`shrink_collect` computes, for each storage being shrunk, a `tombstones_to_carry_forward` list: zero-lamport, single-ref accounts whose slot is **newer** than `latest_full_snapshot_slot` and therefore cannot yet be purged from the index — they must be rewritten as "tombstones" so an incremental snapshot can still observe the deletion event [1](#0-0) , with the not-yet-purgeable case explicitly pushing into `tombstones_to_carry_forward` [2](#0-1) .

The normal shrink path threads this list through and writes it back into the new storage (verified by `test_shrink_collect_carries_forward_existing_tombstones`, which shows tombstones are carried forward when the slot is newer than the latest full snapshot slot and dropped only once the full snapshot advances past that slot) [3](#0-2) .

However, the ancient-append-vec "packed squash" path (`combine_ancient_slots_packed_internal` → `calc_accounts_to_combine` → `finish_combine_ancient_slots_packed_internal`) also calls `shrink_collect` on each ancient storage [4](#0-3) , but the resulting `tombstones_to_carry_forward` is never fed into `write_packed_storages`/`PackedAncientStorage` — the pack path only forwards `alive_accounts` [5](#0-4) . The only safeguard is a `debug_assert!` in `finish_combine_ancient_slots_packed_internal` that explicitly documents the danger: "The squash write path has no tombstone handling, so a non-empty list here would be silently lost" [6](#0-5) .

Because `debug_assert!` compiles to a no-op in release builds (which is how production validators run), if this invariant is ever violated — i.e., an ancient slot selected for packing is newer than `latest_full_snapshot_slot` and contains a zero-lamport single-ref account — the tombstone is silently discarded instead of being rewritten, with no panic, no log, and no metric in production.

### Impact Explanation
If a tombstone is silently lost:
- The account's index entry is still removed (as with normal purging) via `remove_zero_lamport_single_ref_accounts_after_shrink`, called unconditionally regardless of whether the tombstone was written [7](#0-6) .
- Because the physical byte record of the zero-lamport deletion event was not carried into the packed ancient storage, a subsequent **incremental snapshot** taken relative to a full snapshot at or before that slot would not contain evidence that the account was zeroed out in that slot range.
- A node restoring from that full+incremental snapshot pair would end up with a different (stale/incorrect) view of that account versus a node that replayed the ledger continuously — an honest-node snapshot-vs-replay divergence, and potentially an accounts-hash/lattice-hash mismatch on `verify_accounts`/`calculate_accounts_lt_hash_at_startup_from_index` [8](#0-7) .

This matches the class of "silent balance/state change" and "hash divergence" impact required by the validation rules, and lives squarely in the accounts-db shrink/cache and lattice-hashing/snapshot-generation surface that is in scope.

### Likelihood Explanation
The comment and `debug_assert!` in the code itself acknowledge the developers' belief that ancient squash "only runs on slots far older than the latest full snapshot" so tombstones should already be purgeable and the carry-forward list empty by construction. Whether this invariant can actually be violated in production depends on the ordering/synchronization between `latest_full_snapshot_slot` updates and ancient-slot selection (`collect_sort_filter_ancient_slots`/`calc_ancient_slot_info`), which I was not able to fully trace before running out of tool budget — I could not confirm or rule out a race or edge case (e.g., `latest_full_snapshot_slot` being updated concurrently, or ancient slot selection thresholds overlapping with recent full-snapshot slots) that would let a not-yet-purgeable slot reach this path. This is a genuine gap in my verification: the finding rests on a defensive-but-unenforced invariant, and I cannot assert with certainty how easily it is violated in practice.

### Recommendation
- Either make the invariant a hard, always-on check (e.g., `assert!` instead of `debug_assert!`, or an explicit early bail-out that reroutes any slot with a non-empty `tombstones_to_carry_forward` away from ancient packing) so a violation fails loudly instead of silently discarding data in release builds, or
- Implement actual tombstone handling in the ancient squash/pack write path (mirroring what normal shrink does) so tombstones are correctly carried into `PackedAncientStorage` regardless of whether the invariant currently holds.

### Proof of Concept
No concrete production trigger was verified within the available investigation — the analysis identifies the unguarded code path and the developers' own acknowledgment of the risk (`debug_assert!` + comment), but I was unable to construct or confirm the exact sequence of `latest_full_snapshot_slot` updates versus ancient-slot selection that would cause a non-empty `tombstones_to_carry_forward` to reach `finish_combine_ancient_slots_packed_internal` in a release build. A Devin session with build/test access would be needed to attempt to construct such a test case (e.g., adapting `test_finish_combine_ancient_slots_packed_internal` to include a zero-lamport single-ref account in a slot newer than `latest_full_snapshot_slot` and routing it through `combine_ancient_slots_packed_internal` instead of directly calling `finish_combine_ancient_slots_packed_internal`) to confirm whether the assert can actually be tripped.
