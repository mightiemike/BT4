This confirms the ancient-slot selection is based purely on **slot age** (`get_oldest_non_ancient_slot`, an epoch-based cutoff independent of `latest_full_snapshot_slot`), while the tombstone-loss guard in `finish_combine_ancient_slots_packed_internal` is only a `debug_assert!` that silently compiles away in release builds. This is a solid, root-caused analog to the "silent loss on an un-recovered code path" bug class from the Zetachain report.

### Title
Silent loss of zero-lamport tombstone accounts during ancient squash breaks incremental-snapshot deletion propagation - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
`combine_ancient_slots_packed_internal` selects ancient slots to squash purely by slot age via `get_sorted_potential_ancient_slots`/`get_oldest_non_ancient_slot`, with no check against `latest_full_snapshot_slot`. However, `shrink_collect` (shared by both the normal shrink path and the ancient-squash path) will populate `tombstones_to_carry_forward` with zero-lamport single-ref accounts whenever `can_purge_zero_lamport_single_ref_after_shrink(slot)` is false, i.e. whenever the slot being processed is newer than `latest_full_snapshot_slot`. The ancient-squash write path (`write_packed_storages`/`finish_combine_ancient_slots_packed_internal`) has no code to write these tombstones into the new packed storage — it only guards the invariant with a `debug_assert!`, which is compiled out in release builds.

### Finding Description
The tombstone mechanism exists specifically to prevent stale-balance resurrection: when a zero-lamport, single-ref account is shrunk in a slot *newer* than the latest full snapshot, its bytes must be retained (as a "tombstone") in the new storage so a later incremental snapshot still observes and propagates the deletion, per [1](#0-0) . `shrink_collect`, used by both `shrink_storage` and the ancient combine path, produces this same `tombstones_to_carry_forward` list based solely on `can_purge_zero_lamport_single_ref_after_shrink(slot)`, which only compares `slot` to `latest_full_snapshot_slot`, with no dependency on how the slot was selected for shrink/squash: [2](#0-1) .

The normal shrink path (`shrink_storage`) does handle these tombstones correctly by writing them into the new storage via `store_tombstones`: [3](#0-2) .

The ancient-squash path, however, has no equivalent call. `finish_combine_ancient_slots_packed_internal` merely asserts (in debug builds only) that `tombstones_to_carry_forward` is empty, explicitly acknowledging that a non-empty list would be "silently lost" if this ever happens in production: [4](#0-3) .

Crucially, the assumption backing this `debug_assert!` — that ancient squash "only runs on slots far older than the latest full snapshot" — is not enforced anywhere in the ancient-slot-selection code path. `shrink_ancient_slots` selects candidate slots using `get_oldest_non_ancient_slot(epoch_schedule)`, a purely age-based (epoch-relative) cutoff: [5](#0-4) , and `get_sorted_potential_ancient_slots` filters only by that age cutoff, not by `latest_full_snapshot_slot`: [6](#0-5) . `latest_full_snapshot_slot` is advanced independently, driven by whenever full snapshots are actually taken (an operator/config-controlled cadence), so there is no structural guarantee that every slot old enough to be "ancient" (more than roughly one epoch old) has already been covered by a full snapshot. If full-snapshot cadence is slow, disabled temporarily, delayed, or an operator sets a long `--snapshot-interval-slots`, an ancient slot can legitimately be squashed while still newer than `latest_full_snapshot_slot`, hitting the exact `tombstones_to_carry_forward`-non-empty condition the `debug_assert!` warns about — and in a release binary (the shipped validator), that assert is compiled out, so the tombstone bytes are silently dropped instead of being written to the new packed storage.

### Impact Explanation
When a tombstone is dropped during ancient squash instead of carried forward, the zero-lamport account's deletion record disappears from the storage the incremental snapshot would scan. As explicitly documented by the surrounding code comments, the consequence is a stale-balance resurrection: a subsequent incremental snapshot (taken after the dropped tombstone's slot but based on the older full snapshot) will fail to see the deletion, so restoring from full+incremental snapshots resurrects the account with its old, non-zero balance from the full snapshot — an honest-node snapshot-vs-replay state divergence and a silent balance change, matching the exact resurrection scenario this tombstone mechanism was built to prevent (see the intent test): [7](#0-6) .

### Likelihood Explanation
This requires the ancient-slot age cutoff to outpace the operator's full-snapshot cadence, which is a config/operational condition rather than a contrived edge case — it is entirely plausible on validators with lengthened snapshot intervals or during any window where full-snapshot production lags (e.g. under load, disk pressure, or explicit configuration to reduce snapshot overhead). The bug is latent (protected only by a `debug_assert!`) and would not manifest at all in debug/test builds, making it easy to miss in testing while still reachable in production release builds.

### Recommendation
Either (a) make ancient-slot selection additionally bounded by `latest_full_snapshot_slot` so `can_purge_zero_lamport_single_ref_after_shrink` is guaranteed true for every slot reaching squash, or (b) implement tombstone carry-forward in the ancient-squash write path (mirroring `store_tombstones` in `shrink_storage`) so the case is handled correctly instead of merely asserted against, and upgrade the `debug_assert!` to a runtime check/`assert!` that fails safe (e.g., skip squashing that slot) rather than silently losing data in release builds.

### Proof of Concept
1. Configure a validator with a full-snapshot interval slower than one epoch (or otherwise let `latest_full_snapshot_slot` lag by more than an epoch).
2. Fund an account, then zero it out in a slot, and let that slot age past `get_oldest_non_ancient_slot` while `latest_full_snapshot_slot` is still older than that slot.
3. Let `shrink_ancient_slots`/`combine_ancient_slots_packed` run on that slot; `shrink_collect` will populate `tombstones_to_carry_forward` for the zero-lamport account, but `finish_combine_ancient_slots_packed_internal` (in a release build, `debug_assert!` compiled out) drops it silently, per [8](#0-7) .
4. Take an incremental snapshot after this point, then a full+incremental snapshot restore. The account balance reappears with its pre-zero value instead of remaining deleted, matching the exact regression scenario asserted against in [9](#0-8) .
