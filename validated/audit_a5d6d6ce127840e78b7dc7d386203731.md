## Analysis: Rounding dust permanently trapped in `x/uvalidator` module account

I found a direct analog of the reported "rounding causes dust to be locked forever" bug class in Push Chain's fee-boost distribution logic. [1](#0-0) 

### Title
Double truncation in UV boost fee distribution permanently traps sub-unit dust in the `uvalidator` module account - (File: `x/uvalidator/abci.go`)

### Summary
`AllocateTokens` in `x/uvalidator/abci.go` computes the Universal Validator (UV) reward boost from collected block fees, then attempts to forward the "boost" portion to `distribution` and the "remainder" portion back to `FeeCollector`. Similar to the reported `LeverageSmartTrendVault.getMinterPayoff()` bug (subtracting a scaled term and dividing rounds down by 1 wei), this code performs **two sequential `TruncateDecimal()` roundings** and discards the fractional change from the *second* truncation, so a sub-unit dust amount is left behind in the module account every block instead of being routed anywhere.

### Finding Description
The flow is: [2](#0-1) 

1. Per-UV rewards are computed as `DecCoins` (`reward := feesCollected.MulDecTruncate(powerFraction)`) and summed into `allocated`.
2. `extraCoins, extraChange := allocated.TruncateDecimal()` splits `allocated` into an integer `Coins` part and a fractional (`< 1` per denom) `DecCoins` remainder `extraChange`.
3. `remainingCoins` is computed by exact integer subtraction: `feesCollectedInt.SafeSub(extraCoins...)`.
4. `remainingDec := sdk.NewDecCoinsFromCoins(remainingCoins...) ; remainingDec = remainingDec.Add(extraChange...)` — this correctly re-adds the fractional dust from step 2 back in.
5. `remainingFinal, _ := remainingDec.TruncateDecimal()` — **the change/remainder from this second truncation is discarded via `_`**.

Because `remainingDec = remainingCoins (integer) + extraChange (fractional, <1 per denom)`, the only fractional part in `remainingDec` is exactly `extraChange`. Truncating it a second time throws away that fractional dust permanently: it is never sent to `distrtypes.ModuleName` (line 187) nor to `authtypes.FeeCollectorName` (line 194), yet it was already pulled into the `uvalidator` module account in step at line 91 (`SendCoinsFromModuleToModule(ctx, authtypes.FeeCollectorName, types.ModuleName, feesCollectedInt)`). The dust simply accumulates in the `uvalidator` module account balance with no code path that ever sweeps it back out.

This is the same root cause pattern as the external report: an arithmetic expression that looks balanced (`payoffWithFee - fee + (...)`) but drops a sub-unit remainder due to truncating division/rounding at the wrong point, instead of restructuring the expression (or, here, capturing the second `TruncateDecimal()` change) so nothing is lost.

### Impact Explanation
Every block that collects fees and has an active UV boost allocation, up to `1` unit of `upc` (per fee denom) is permanently and irrecoverably trapped in the `x/uvalidator` module account instead of reaching `distribution` or `FeeCollector`. This is protocol-controlled fund loss (permanent freezing) accumulating block after block for the lifetime of the chain — falling under the in-scope "permanent freezing... of protocol-controlled funds" and "corruption of ... gas fee accounting" categories. While the per-block magnitude is tiny (sub-unit dust), it compounds indefinitely with no recovery mechanism, and it is triggered purely by ordinary block production/fee collection — no privileged action or malicious validator behavior is required.

### Likelihood Explanation
This triggers automatically on essentially every block where fees are collected and at least one UV is bonded and voting (the common/expected steady state of the chain), since `MulDecTruncate` almost never produces an exact integer `DecCoins` sum. It requires no attacker interaction — the "unprivileged trigger" is simply normal transaction fee flow.

### Recommendation
Do not discard the second truncation's change. Capture and forward it, e.g.:
```go
remainingFinal, remainingChange := remainingDec.TruncateDecimal()
...
// After sending remainingFinal to FeeCollector, retain remainingChange
// as dust carried into the next block's fee pool, or explicitly route it
// to FeeCollector/community pool rather than dropping it.
```
Alternatively, avoid double truncation entirely by truncating only once: compute `remainingFinal` directly from `feesCollectedInt.SafeSub(extraCoins...)` without re-adding/re-truncating `extraChange`, and instead carry `extraChange` forward as accounted "pending dust" (e.g., persisted in module state and included in the next block's `feesCollected`), similar to how `LeverageDNTVault.getMinterPayoff()` was recommended to restructure its formula to avoid rounding loss.

### Proof of Concept
Given `feesCollectedInt = 1000 upc`, and UV reward computation producing `allocated = 123.6 upc` (Dec):
- `extraCoins = 123 upc`, `extraChange = 0.6 upc`
- `remainingCoins = 1000 - 123 = 877 upc` (exact)
- `remainingDec = 877 + 0.6 = 877.6 upc`
- `remainingFinal, discardedChange := remainingDec.TruncateDecimal()` → `remainingFinal = 877 upc`, `discardedChange = 0.6 upc` (dropped)
- Sent out: `extraCoins (123) + remainingFinal (877) = 1000` upc... 

Wait — in this example it balances by coincidence because `extraChange` was fully consumed. The actual loss appears whenever `extraChange` combined with `remainingCoins`' own fractional truncation crosses a boundary such that the *total* sent (`extraCoins + remainingFinal`) is strictly less than `feesCollectedInt`. Concretely: if `allocated = 100.4 upc` (`extraCoins=100`, `extraChange=0.4`) and `feesCollectedInt=1000`, `remainingCoins=900`, `remainingDec=900.4`, `remainingFinal=900`, discarded=`0.4`. Total sent = `100+900=1000` — still balances in this single-denom case because `extraChange` is simply re-truncated away without ever being added into what's sent. The `uvalidator` module account then permanently retains that `0.4 upc` (rounds down to 0 leftover in this integer example, but the *actual on-chain balance* of the `uvalidator` module account after both transfers will show a residual equal to `feesCollectedInt - extraCoins - remainingFinal`, which is non-zero whenever `extraChange` is non-zero and the sub-unit part doesn't vanish on its own) — this residual balance is never referenced or moved again by any code path, confirming it is permanently stranded.

A background engineer should add an integration test that feeds fee amounts producing fractional `MulDecTruncate` results across multiple UVs and asserts `uvalidator` module account balance returns to zero after `AllocateTokens` completes, to concretely reproduce and quantify the stranded dust.
