### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay-verify tooling accept a divergent authenticated state root — (File: `types/src/transaction/mod.rs`)

### Summary
The reduced invariant from the external report is: *a state-mutating capability gate must be checked symmetrically everywhere the corresponding integrity/return check is checked, or a component can silently escape enforcement.* The Aptos analog is in `TransactionOutput::ensure_match_transaction_info` [1](#0-0) , which is the function used by replay/verification tooling to assert that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded in the ledger/backup. This function checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap that is called out in-code as a known TODO.

### Finding Description
`ensure_match_transaction_info` computes and compares `write_set_hash` against `txn_info.state_change_hash()` and `event_root_hash` against `txn_info.event_root_hash()`, but the function returns `Ok(())` without ever comparing the state-checkpoint-related hash fields of `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) against anything independently recomputed [2](#0-1) . The code contains its own admission of this:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This function is consumed directly by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` as the sole correctness gate before declaring a chunk of re-executed transactions "matching" the archived, ledger-info-authenticated `TransactionInfo` list [4](#0-3) . It is also used by the Move CLI transaction-replay path (`aptos-move/cli/src/commands.rs`) as the pass/fail check for a single replayed transaction [5](#0-4) .

Meanwhile, the actual commit-time construction of `TransactionInfo` (`assemble_transaction_infos` in `do_ledger_update.rs`) *does* populate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (feature-gated) `position_state_checkpoint_hash` as first-class fields of the committed, accumulator-hashed `TransactionInfo` [6](#0-5) , and `execution_output.rs` carries a `compute_trading_native_state_roots` flag governing whether the new native-position state root is computed and embedded in the committed `TransactionInfo` [7](#0-6) . So the checkpoint hashes are a real, committed, accumulator-bound part of ledger state — but the "manage"-equivalent enforcement point (the replay-verification comparator) does not check them, exactly mirroring the BranchPort pattern of two supposedly-symmetric checks (one strict, one silently permissive) over the same protected resource.

### Impact Explanation
If/when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native "position"/order-book state) is enabled, a local execution engine (e.g. a full node performing `db-tool replay-on-archive`, or an auditor using the CLI replay path) that produces a **different** `position_state_checkpoint_hash` or `state_checkpoint_hash`/`hot_state_checkpoint_hash` than what is stored in the authenticated backup/DB will still be reported as "verified"/"matching," because `ensure_match_transaction_info` never inspects those fields. This breaks the "authenticated API/proof-bearing output must stay bound to the correct ledger version/root" invariant for the specific field that is supposed to authenticate off-chain-derived/native state (position state). A divergence here (e.g. from non-determinism, a bug in native-position replay, or a malicious archive with tampered — but still accumulator-consistent through this weaker check — data) would go undetected by the very tool meant to catch exactly this class of bug, undermining confidence in replay-verify results used to validate mainnet history and potentially masking a genuine hard-fork-class state divergence in the native-position subsystem.

### Likelihood Explanation
This is not a hypothetical bug: the code contains a first-party TODO acknowledging the gap must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." As long as this flag is gated off, the impact is latent; once the feature is turned on (which the code is clearly staged for, given `hot_state_root_in_txn_info` / `compute_trading_native_state_roots` plumbing already exists throughout `do_ledger_update.rs`, `do_state_checkpoint.rs`, and `execution_output.rs`), the gap becomes immediately live for anyone using `replay_on_archive` or the CLI replay path — both of which are standard tools for verifying mainnet archive integrity.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute (or accept as parameters) `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from the locally-produced result state / hot-state / position-state and assert equality against the corresponding `TransactionInfo` fields, mirroring the strict checks already done for `write_set_hash` and `event_root_hash`. This should be landed and enabled prior to (or atomically with) turning on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, and `replay_on_archive`/CLI callers should propagate the necessary checkpoint hashes so the comparison is exercised in production replay-verify runs.

### Proof of Concept
Not independently reproducible as a live exploit from static analysis alone: the vulnerable comparison path is dormant until `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/native-position state roots are enabled network-wide, and I could not find (within index limits) the exact call site that supplies `position_state_checkpoint_hash` inputs into `ensure_match_transaction_info`'s current parameter list, since the function signature does not currently accept them at all — that omission is precisely the bug. A concrete PoC would require: (1) constructing a `TransactionInfo` with a `position_state_checkpoint_hash` that differs from the hash of a locally re-derived native-position state, (2) calling `ensure_match_transaction_info`/`execute_and_verify` with a `TransactionOutput` reflecting the differing local position state, and (3) observing that the function returns `Ok(())` despite the mismatch — as directly implied by the code path shown at [2](#0-1)  and its caller at [4](#0-3) .
