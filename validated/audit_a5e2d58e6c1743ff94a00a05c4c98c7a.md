## Finding: Unbounded per-address delegation-index list growth causes disproportionate iteration cost in `UnfreezeBalanceActuator` / `DelegatedResourceAccountIndexStore.convert` — (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
The reported bug class ("processDepositQueue"/"processWithdrawalQueue" looping over an attacker-inflatable queue with no cap) has a concrete analog in java-tron's legacy resource-delegation index. `FreezeBalanceActuator.delegateResource` appends one entry per distinct (owner, receiver) pair into a `DelegatedResourceAccountIndexCapsule`'s `toAccountsList` / `fromAccountsList` with no upper bound on list size, and that list is later iterated in full by consensus-critical actuator code (`UnfreezeBalanceActuator`) or by the migration routine `DelegatedResourceAccountIndexStore.convert`.

### Finding Description
`FreezeBalanceContract` lets any account freeze its own balance and delegate the resulting bandwidth/energy to an **arbitrary receiver address, without that receiver's consent**: [1](#0-0) 

When delegating (and the network has not yet enabled `AllowDelegateOptimization`), each call appends the counter-party address into the owner's `toAccountsList` and the receiver's `fromAccountsList`, deduplicating only against the *current* owner's own entry, not globally: [2](#0-1) 

Because the freeze fee is a fixed 1 TRX minimum with no cap on the number of distinct owner accounts that may target the same `receiverAddress`, an attacker can create many accounts (or reuse freeze/unfreeze cycles) and delegate small amounts to a single victim address, growing that victim's `fromAccountsList` (and symmetrically any address's `toAccountsList`) without bound, since `DelegatedResourceAccountIndexCapsule` stores these as plain repeated protobuf fields with no size limit enforced anywhere: [3](#0-2) 

This inflated list is later processed in full, in a consensus-critical actuator, in at least two places:

1. `UnfreezeBalanceActuator` copies the whole list into a new `ArrayList` and does a linear `remove` scan whenever the delegated resource is freed: [4](#0-3) 

2. `DelegatedResourceAccountIndexStore.convert`, used when the network transitions to `AllowDelegateOptimization`, iterates the entire (potentially attacker-inflated) `toList`/`fromList` for the address being migrated: [5](#0-4) 

This mirrors the FCNProduct.sol pattern exactly: a state-mutating loop bound to a collection size that an attacker fully controls, with no maximum enforced, executed as part of normal, unprivileged transaction processing (`processTransaction` → actuator `execute`), i.e., every full node must pay this cost during block validation.

### Impact Explanation
Any node validating a block containing a `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction (or the one-time delegate-optimization migration) that touches an address with an attacker-inflated index list must perform O(n) work proportional to the attacker-chosen list size, while the transaction's declared bandwidth/energy fee remains fixed and small. This is a resource-accounting/DoS-class issue: it allows disproportionate CPU consumption during consensus-critical transaction execution relative to the fee paid, potentially degrading node performance or block processing time under repeated abuse (analogous to the reported "attacker exceeds block gas limit" scenario, but here manifesting as unmetered CPU work rather than metered gas overflow, since the old freeze/delegate contract charges 0 fee — see `calcFee()` returning 0).

### Likelihood Explanation
Reachable by any unprivileged account via ordinary broadcast transactions (`FreezeBalanceContract` with a `receiverAddress`), requiring only the 1 TRX minimum freeze amount per delegation and no receiver cooperation. The `FreezeBalanceContract` path is legacy (superseded by `FreezeBalanceV2Contract`/`DelegateResourceContract`, and validation rejects it once `supportUnfreezeDelay()` is active), so exploitability is time-bound to networks/chains where the old freeze/delegate contract is still enabled — but on any such network (or during migration windows), the attack is cheap and requires no special privilege.

### Recommendation
- Enforce an explicit maximum on the number of distinct delegation counter-parties tracked per address in `DelegatedResourceAccountIndexCapsule` (similar to the `MAX_VOTE_NUMBER`/`UNFREEZE_MAX_TIMES`/`MAX_MATCH_NUM` caps already used elsewhere in the codebase for the same bug class).
- Reject new delegations once an address's `toAccountsList`/`fromAccountsList` reaches the cap, or migrate to a per-relationship keyed store (as the V2 `DelegateResourceContract`/`DelegateResourceProcessor` already does) rather than a single aggregated repeated-field record.
- Charge a fee proportional to list size for operations that must touch the full list (e.g., `convert`), or bound the work performed per transaction and defer/paginate the remainder.

### Proof of Concept
1. Create N distinct funded accounts A_1..A_N (minimal 1 TRX each).
2. For each A_i, broadcast `FreezeBalanceContract{ownerAddress=A_i, receiverAddress=Victim, frozenBalance=1_000_000, resource=BANDWIDTH}` (network with `AllowDelegateOptimization` not yet enabled).
3. Each transaction succeeds cheaply and appends `A_i` to `Victim`'s `fromAccountsList` (see `FreezeBalanceActuator.delegateResource`, lines 334-345).
4. After N is large (e.g., tens of thousands), any subsequent `UnfreezeBalanceContract` from `Victim` (or the network-wide `AllowDelegateOptimization` migration touching `Victim`) forces a full O(N) copy/scan of the list during actuator execution — demonstrated structurally by the existing test `testMultiFreezeDelegatedBalanceForBandwidth`, which already builds a 100-entry list and shows it is fully copied/iterated during `convert()`/execute().

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
