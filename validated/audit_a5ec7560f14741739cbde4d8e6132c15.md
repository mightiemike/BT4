### Title
Shadow-parent burnchain validation is order-dependent, permissively accepting a child block that should be rejected - (File: stackslib/src/chainstate/nakamoto/shadow.rs)

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` decides whether to enforce the shadow-parent block-commit rules (`parent_vtxindex == 0`, `parent_block_ptr == parent_sn.block_height`) based solely on whether `staging_db.get_nakamoto_block_header(&block.header.parent_block_id)` currently returns a header for the parent. If the parent (a shadow block) has not yet been staged locally, the function silently returns `Ok(())`, treating the situation identically to "the parent is not a Nakamoto/shadow block" even though the two cases are semantically different.

### Finding Description
The broken equality is: `verdict(validate_normal_nakamoto_block_burnchain(child, node_A_state)) == verdict(validate_normal_nakamoto_block_burnchain(child, node_B_state))` for the same `child` block and the same eventual global chainstate, which should hold regardless of local delivery order.

The root cause is that "parent not found in staging DB" is conflated with "parent is not a shadow block" / "parent is not a Nakamoto block." In reality "not found" can also mean "not yet received/relayed to this node," which is a purely local, timing-dependent condition, not a property of the block or the burnchain. An attacker who controls (or colludes with) the true shadow-parent chain of a tenure can construct a legitimate-looking child block whose block-commit `parent_vtxindex`/`parent_block_ptr` do NOT actually match the shadow parent's sortition (i.e., a commit that would be rejected under the strict check), then race its delivery to different nodes relative to the shadow parent block's arrival:
- Node A receives/stages the child before the shadow parent is present locally → `validate_shadow_parent_burnchain` returns `Ok(())` (no-op) → the block-commit's mismatched `parent_vtxindex`/`parent_block_ptr` are never checked → the child can pass burnchain validation and be staged/accepted.
- Node B receives the shadow parent first (already staged) → the strict checks execute and reject the same child with `InvalidStacksBlock`.

Existing guards do not close this gap: `common_validate_against_burnchain` and `check_tenure_tx` validate consensus_hash/burn totals/tenure-change consistency but not the shadow-specific block-commit vtxindex/ptr fields, and `validate_nakamoto_block_static` performs only self-contained static checks unrelated to the block-commit's relationship to a shadow parent. The permissive branch is reachable purely by controlling network delivery timing to an honest node, which is within the unprivileged attacker's capability (broadcasting the block-commit and the Nakamoto block via P2P).

### Impact Explanation
If Node A stages/accepts the malformed child (because the check was skipped) and later processes it into its chainstate once its parent is also processed, while Node B permanently rejects the same block, the two nodes' local views of the canonical Nakamoto chain tip diverge irreconcilably — a chain split rooted in the point where the malformed child is/isn't appended. This matches the Critical category ("a chain split or deep fork," "an invalid block accepted or a valid block rejected network-wide").

### Likelihood Explanation
The attacker needs only: (1) knowledge that a shadow tenure exists in the chain history (public information, since shadow blocks are inserted via a public SIP/schema update and are eventually known to all nodes), (2) the ability to broadcast a block-commit and a Nakamoto block with an inconsistent `parent_vtxindex`/`parent_block_ptr`, and (3) control over delivery order/timing to different peers (e.g., direct-connecting to a subset of nodes before others catch up on IBD or after temporary partition). No majority stake, signer majority, or node-operator privilege is required — this is achievable by any single unprivileged participant able to broadcast blocks and burn operations, making it a realistic minority-triggerable divergence given the right timing window (e.g., immediately after a shadow-tenure-driven emergency upgrade, before all nodes have caught up on IBD/replay of the shadow blocks).

### Recommendation
Do not treat "parent header not found in local staging DB" as equivalent to "parent is not a shadow block." Instead:
- If the parent header cannot be found locally, defer validation of this block (do not accept it into staging as burnchain-valid) until the parent is available, or explicitly re-validate `validate_shadow_parent_burnchain` at the point the block is actually appended/processed (when the parent is guaranteed to be resolved), not only at initial staging-acceptance time.
- Alternatively, look up whether the parent tenure is a shadow tenure via `is_shadow_tenure`/sortition data (which is a burnchain-derived fact, not staging-order-derived) rather than relying on `nakamoto_staging_blocks` presence, so that the shadow/non-shadow determination is independent of local block-arrival order.

### Proof of Concept
Rust integration test plan (two-node harness or two separate `StacksChainState`/`SortitionDB` instances derived from the same burnchain state):
1. Set up a shared burnchain/sortition history that includes a shadow tenure at consensus hash `CH_shadow`, with its `parent_sn.block_height = H`.
2. Construct a normal (non-shadow) child block `B_child` whose `header.parent_block_id` points to the shadow tenure's terminal block, but whose tenure's block-commit has `parent_vtxindex != 0` (or `parent_block_ptr != H`) — i.e., a commit that should fail the strict check.
3. Node A: call `NakamotoChainState::validate_normal_nakamoto_block_burnchain(..., B_child, ...)` (or the encompassing accept-block path) BEFORE inserting the shadow parent block into `nakamoto_staging_blocks`. Assert `Ok(())` is returned (permissive path taken).
4. Node B: insert/stage the shadow parent block into `nakamoto_staging_blocks` first, then call the same validation function on `B_child`. Assert `Err(ChainstateError::InvalidStacksBlock(_))` is returned.
5. Assert `verdict(NodeA) != verdict(NodeB)` for the identical `B_child` and identical burnchain state, demonstrating the order-dependent divergence.
