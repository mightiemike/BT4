### Title
Cheap ReceiveDescription size checks executed after expensive spend-proof verification - ([File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java])

### Summary
In `checkProof()`, the loop over `SpendDescription`s (each triggering the expensive native `JLibrustzcash.librustzcashSaplingCheckSpend` pairing-crypto call) executes unconditionally before the loop over `ReceiveDescription`s that performs the cheap `getCEnc().size()`/`getCOut().size()` structural check. An attacker can therefore force full spend-proof verification to run on a transaction that is guaranteed to be rejected on a trivial size mismatch, wasting CPU cycles that a fail-fast ordering would have avoided.

### Finding Description
`ShieldedTransferActuator.validate()` calls `checkReceiver()` [1](#0-0)  which only bounds `receiveDescriptionCount` to `[1,2]`, and later performs a cheap duplicate-`NoteCommitment` check [2](#0-1) . Neither of these validates `CEnc`/`COut` byte-array sizes.

Those size checks only happen deep inside `checkProof()`, and critically, only *after* the full spend loop has already run: [3](#0-2) 

The spend loop (lines 293-306) invokes `JLibrustzcash.librustzcashSaplingCheckSpend` — a native elliptic-curve pairing verification — for every `SpendDescription` before the receive loop's cheap size guard (lines 309-312) is ever reached. Prior checks (`merkleContainer.merkleRootExist`, `nullifierStore.has`) are indeed cheap and executed first (lines 238-243), but they do not gate the expensive spend-proof crypto itself — they only validate ancillary spend metadata, not receive well-formedness. As a result, a transaction with one syntactically valid (correctly-sized) `SpendDescription` and one malformed `ReceiveDescription` (wrong `CEnc`/`COut` size) will still pay the full cost of `librustzcashSaplingCheckSpend` before being rejected.

### Impact Explanation
This is a CPU-amplification issue affecting `ContractValidateException`-triggering validation, matching the "DoS via the TRON protocol implementation" impact class: an attacker can force nodes to perform native elliptic-curve pairing verification (the most expensive part of Sapling proof checking) on transactions that are trivially and cheaply detectable as invalid, by simply mis-sizing the `CEnc`/`COut` fields of a `ReceiveDescription`. At scale (many such transactions), this consumes disproportionate CPU relative to the cost the attacker incurs, though the impact is limited to at most one spend-description per shielded transaction (`checkSender()` enforces `spendDescriptionCount <= 1`) [4](#0-3) , so the maximum amplification per transaction is bounded to a single `checkSpend` call, not an unbounded loop.

### Likelihood Explanation
Reachable by any unprivileged account (no witness/SR/committee role needed) that can broadcast a `ShieldedTransferContract` transaction, provided shielded transactions are enabled on the network (`dynamicStore.supportShieldedTransaction()`, a committee-gated but commonly-enabled mainnet feature) [5](#0-4) . I was not able to fully verify, within the available tooling, whether transactions that fail in `validate()` (as opposed to `execute()`) consume the sender's bandwidth/energy or incur any fee before being dropped — this materially affects the real-world cost/repeatability of the attack and would need confirmation via `Manager`/`TransactionCapsule` push-transaction flow, which I could not fully trace before running out of iterations. Absent that fee-charging confirmation, the amplification is real per-transaction (spend check always precedes the cheap receive-size check) but bounded to a single extra native call per malformed transaction, which is a modest, not severe, amplification factor.

### Recommendation
Move the `CEnc`/`COut` size validation for `ReceiveDescription` into `checkReceiver()` (structural validation phase) or otherwise perform it before entering the spend-verification loop in `checkProof()`, so malformed receive descriptions are rejected before any `librustzcashSaplingVerificationCtxInit()`/`librustzcashSaplingCheckSpend` calls are made.
