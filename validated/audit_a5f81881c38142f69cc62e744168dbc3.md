## Title
`Runtime::apply_action_receipt` panics on `tx_burnt_amount.checked_sub(receiver_reward).unwrap()` when the contract-reward is priced higher than the burnt-gas pool it is subtracted from - (File: `runtime/runtime/src/lib.rs`)

## Summary
`Runtime::apply_action_receipt` computes a validator/burn pool (`tx_burnt_amount`) and then subtracts a contract "gas reward" (`receiver_reward`) from that pool, exactly mirroring the Sushi `ConcentratedLiquidityPoolManager` pattern where a reward proportional to one metric is subtracted from an unclaimed pool that can be smaller than the reward. In the pre-`AccountCostIncrease` code path, the two amounts are priced with two *different* gas prices, which lets `receiver_reward` exceed `tx_burnt_amount`, causing an unwrap-panic instead of a graceful clamp.

## Finding Description
In `runtime/runtime/src/lib.rs`, after a receipt executes, the burnt-token pool for the receipt is built as: [1](#0-0) 

```
let mut tx_burnt_amount = safe_gas_to_balance(gas_burn_price, gas_burnt)?
    .checked_sub(gas_refund_result.price_deficit)
    .unwrap();
if !ProtocolFeature::AccountCostIncrease.enabled(...) {
    tx_burnt_amount = safe_add_balance(tx_burnt_amount, gas_refund_result.price_surplus)?;
}
tx_burnt_amount = safe_add_balance(tx_burnt_amount, gas_refund_result.refund_penalty)?;
...
```

Then the contract's share of the burnt gas is computed and subtracted from that same pool: [2](#0-1) 

```
let receiver_gas_reward = result.gas_burnt_for_function_call
    .checked_mul(*apply_state.config.fees.burnt_gas_reward.numer() as u64).unwrap()
    .checked_div(*apply_state.config.fees.burnt_gas_reward.denom() as u64).unwrap();
let receiver_reward =
    if ProtocolFeature::AccountCostIncrease.enabled(...) {
        safe_gas_to_balance(gas_burn_price, receiver_gas_reward)?
    } else {
        // pre-AccountCostIncrease: use the receipt's *purchase* price, not the burn price
        safe_gas_to_balance(gas_purchase_price, receiver_gas_reward)?
    };
if receiver_reward > Balance::ZERO {
    ...
    tx_burnt_amount = tx_burnt_amount.checked_sub(receiver_reward).unwrap();
    ...
}
```

`gas_burn_price` is the price used to build `tx_burnt_amount`'s base term (`gas_burn_price * gas_burnt`), while, pre‑`AccountCostIncrease`, `receiver_reward` — a fraction of the *same* burnt gas (`gas_burnt_for_function_call ⊆ gas_burnt`) — is priced at `gas_purchase_price` (the price recorded on the receipt when it was created/purchased, which can differ arbitrarily from the current block's `gas_burn_price` due to gas-price drift across blocks/congestion). The code comment at the `gas_burn_price` definition explicitly acknowledges the danger of this mismatch: [3](#0-2) 

```
let gas_burn_price =
    if ProtocolFeature::AccountCostIncrease.enabled(...) {
        // should always be <= gas_purchase_price, otherwise receiver_reward might underflow
        // or mint new tokens.
        std::cmp::min(gas_purchase_price, apply_state.gas_price)
    } else {
        apply_state.gas_price
    };
```

This comment confirms the invariant `gas_burn_price ≤ gas_purchase_price` is required to avoid underflow, but that invariant is only *enforced* under `AccountCostIncrease`. In the `else` branch (pre-`AccountCostIncrease`, still compiled and reachable for any protocol version below v85, e.g. `MIN_SUPPORTED_PROTOCOL_VERSION = 83`/84), `gas_burn_price = apply_state.gas_price` (the current block's price) with no relation enforced to `gas_purchase_price`. If the block gas price has fallen since the receipt was purchased (`gas_purchase_price > gas_burn_price`), `receiver_reward` (priced at the higher `gas_purchase_price`) can exceed the fraction of `tx_burnt_amount` attributable to the same gas amount, and once `price_deficit`/`price_surplus` adjustments are folded in, `tx_burnt_amount.checked_sub(receiver_reward).unwrap()` can underflow and panic.

This is structurally identical to the reported bug class: a value ("rewards"/"receiver_reward") computed proportionally to one metric (function-call gas × a fixed ratio) can exceed the pool it is deducted from ("incentive.rewardsUnclaimed"/"tx_burnt_amount") because the two quantities are not computed with consistent, mutually-bounded units (liquidity-weighted seconds vs. price-weighted gas).

## Impact Explanation
`apply_action_receipt` runs deterministically inside chunk application for every action receipt on every honest node. An `unwrap()` panic here is not a soft error returned to the caller — it aborts the node process applying the chunk. Because this is deterministic given chain state, it would either (a) cause all honest nodes at the affected protocol version to panic identically when applying the same chunk (a transaction/receipt-triggered chain halt), or (b) if only some nodes hit the divergent price condition due to differing block observation timing, contribute to inconsistent state application across the network. Either outcome falls within the accepted "transaction-triggered halt" / "state-root divergence" impact categories.

## Likelihood Explanation
This requires: (1) operation on a protocol version where `AccountCostIncrease` is not yet enabled (any network at PV < 85, including testnets/new chains bootstrapped below v85, since `MIN_SUPPORTED_PROTOCOL_VERSION = 83`), and (2) a receipt whose `gas_purchase_price` (recorded at receipt creation) is meaningfully higher than the `gas_burn_price` (current block price) at execution time — realistic when gas price has been decreasing across blocks between receipt creation and execution (e.g., after a period of high congestion followed by a drop in load), combined with a function call that burns a large amount of gas (maximizing `receiver_gas_reward`). This is triggerable by any ordinary function-call transaction; no privileged access is required, only timing of gas price movement relative to receipt buffering across blocks/shards.

## Recommendation
Price `receiver_reward` at `min(gas_burn_price, gas_purchase_price)` (or otherwise clamp `receiver_reward` to `tx_burnt_amount`) in the pre-`AccountCostIncrease` branch as well, mirroring the safety comment already present for the `AccountCostIncrease` branch, and replace the final `checked_sub(receiver_reward).unwrap()` with an explicit clamp (`receiver_reward.min(tx_burnt_amount)`) so a pricing mismatch degrades gracefully instead of panicking.

## Proof of Concept
Not independently reproduced in a running node (index-only investigation); the arithmetic mismatch is demonstrated directly from the code:
1. Chain runs at protocol version < 85 (`AccountCostIncrease` disabled) — legitimate for any network below v85, still within `MIN_SUPPORTED_PROTOCOL_VERSION`.
2. A function-call receipt is created (and its receipt/data buffered, e.g. due to congestion or cross-shard delay) while the block gas price is high, recording `gas_purchase_price = P_high` on the receipt (`action_receipt.gas_price()`).
3. By the time the receipt executes, the block's gas price has dropped to `apply_state.gas_price = P_low`, so `gas_burn_price = P_low` (line 1044).
4. `tx_burnt_amount` is built from `gas_burn_price (P_low) * gas_burnt` (lines 1093-1102).
5. `receiver_reward` is built from `gas_purchase_price (P_high) * receiver_gas_reward_gas` (line 1123), where `receiver_gas_reward_gas` is a fixed fraction of `gas_burnt_for_function_call ≤ gas_burnt`.
6. For a sufficiently large price gap `P_high / P_low` and a receipt whose gas is almost entirely function-call gas, `receiver_reward (priced at P_high)` exceeds `tx_burnt_amount (priced at P_low, plus/minus deficit/surplus adjustments)`, triggering the panic at line 1132: `tx_burnt_amount.checked_sub(receiver_reward).unwrap()`.

Uncertainty: exact numeric feasibility (whether real gas-price-adjustment bounds and `burnt_gas_reward` ratio (`3/10` on mainnet) allow the gap to be large enough in one block-to-block step) was not verified against the concrete `gas_price_adjustment_rate` clamp logic; this would require a runtime/integration test (`chain/chain/src/runtime/tests.rs`-style harness) driving successive blocks with decreasing load to shrink `gas_price` between receipt creation and execution, then submitting a heavy function-call transaction, to confirm the panic is reachable within the gas-price adjustment rate limits.
