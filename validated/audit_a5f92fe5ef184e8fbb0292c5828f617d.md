## Finding

The Push Chain analog to the sNOTE `_mintFromAssets()` slippage issue is the auto-swap minimum-output calculation used by `x/uexecutor` when it swaps a user's bridged gas token into native PC on their behalf.

### Title
Spot-price-derived `minPCOut` slippage bound is trivially bypassable via same-block AMM price manipulation, allowing value extraction from user gas-token deposits and gas refunds — (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
For `GAS` and `GAS_AND_PAYLOAD` inbound flows, and for post-outbound excess-gas refunds, `x/uexecutor` swaps a PRC20 gas token for native PC through a Uniswap V3 pool on behalf of the user/protocol. The minimum acceptable output (`minPCOut`) is computed as 95% of a spot quote fetched from `QuoterV2.quoteExactInputSingle` **in the same keeper call, immediately before executing the swap**, with no TWAP, no pool-liquidity/deviation sanity check, and no user-supplied or externally-verified minimum.

### Finding Description
`k.GetSwapQuote` [1](#0-0)  calls the Uniswap V3 `QuoterV2` for a live, instantaneous (spot) quote. Immediately afterward, `minPCOut` is derived purely from that spot quote with a fixed 5% haircut:

```go
// 5% slippage: minPCOut = quote * 95 / 100
minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
minPCOut.Div(minPCOut, big.NewInt(100))
``` [2](#0-1) 

The same pattern is repeated in `gasAndPayloadDepositAutoSwap` [3](#0-2)  and in `applyGasRefund`'s swap-refund leg [4](#0-3) .

This is executed deterministically as part of ordinary, unprivileged user-triggered flows:
- `ExecuteInboundGas`/`ExecuteInboundGasAndPayload` run when honest Universal Validators reach quorum on a `MsgVoteInbound` for a bridged gas-token deposit — something any unprivileged user can trigger simply by depositing tokens on a source chain.
- `applyGasRefund` runs on every successful/failed outbound observation that has excess gas.

Because the quote and the swap both occur within the same Cosmos-SDK transaction/keeper call (via `CallEVM` then `DerivedEVMCall`), the "protection" band is computed from whatever the pool's price is *at that exact moment* — not from a manipulation-resistant reference (TWAP, external oracle, or governance-set bound). An unprivileged actor who can predict when the quorum-triggering vote transaction (or the refund-triggering vote) will land in a block — which is observable, since votes/quorum accumulation and pending mempool transactions are public — can submit an ordinary EVM swap transaction against the same Uniswap V3 pool immediately before the module's swap executes, moving the spot price down, and reverse the trade immediately after. The subsequently fetched `quote`/`minPCOut` is computed on the manipulated price, so the module's swap still satisfies its own (manipulated) 95% floor while the module account/protocol systematically receives a discounted `amountOut`, and the sandwiching attacker captures the difference. There is no code path that rejects a manipulated spot price or falls back to a safer reference price.

This is the direct architectural analog of the sNOTE bug: a swap executed with no manipulation-resistant slippage guard, letting a front-runner extract value from the transaction. The difference from the original finding (which hardcoded `minimumBPT=0`) is only cosmetic — Push Chain added a 5%-of-spot-quote floor, but since both the quote and the swap are attacker-influenceable within the same block, the floor provides no real protection beyond bounding the attacker's own manipulation depth to a single-block price swing plus 5%, which for typical AMM depths is easily exceeded by a modestly funded MEV actor.

### Impact Explanation
Each gas-token deposit inbound and each outbound gas refund with a swap leg mints fewer PC tokens to the user's UEA (or refund recipient) than the fair market rate justifies, with the difference captured by the attacker. This directly corrupts native-asset accounting for bridged funds (`CallPRC20DepositAutoSwap` / `refundUnusedGas` outcomes feed into `PCTx`/`OutboundTx.PcRefundExecution` state) and results in unauthorized value extraction from user/protocol-controlled funds, reachable by an ordinary unprivileged user or MEV bot with no privileged role — squarely in scope under "corruption of PRC20 or native asset accounting" and "permanent loss...of user or protocol-controlled funds."

### Likelihood Explanation
High for any pool with modest liquidity relative to swap sizes: the attack requires no validator collusion, no key compromise, and no special access — only capital to move the pool price and priority-fee bidding to land transactions around the module's swap in the same block. Inbound gas-token deposits happen routinely as part of normal bridging traffic, giving the attacker frequent, low-cost opportunities.

### Recommendation
Do not derive `minPCOut` solely from a same-block spot quote. Use a manipulation-resistant reference price (e.g., a TWAP over multiple blocks, or a governance/oracle-set reference price with a bounded deviation check against the spot quote), and/or make the slippage tolerance and reference price configurable/auditable rather than a hardcoded 5%-of-spot-quote. Consider capping the maximum acceptable price impact per swap and reverting (falling back to a non-swap deposit path, which already exists) if the observed spot price deviates materially from the reference.

### Proof of Concept
1. Attacker monitors Push Chain's mempool/vote state for a `MsgVoteInbound` (or `MsgVoteOutbound`) that is about to reach quorum on a `GAS`/`GAS_AND_PAYLOAD` inbound (or a refund with excess gas).
2. Immediately before that transaction is included, attacker submits a large `swapExactInputSingle`-style trade against the same PRC20/WPC Uniswap V3 pool (deployed as described in `e2e-tests/setup.sh` `step_setup_swap_amm`) to push the spot price down, paying a higher priority fee to guarantee ordering ahead of the quorum tx.
3. The quorum tx executes `ExecuteInboundGas` → `GetSwapQuote` (spot, post-manipulation) → `minPCOut = quote*95/100` → `CallPRC20DepositAutoSwap`, which succeeds against the manipulated floor.
4. Attacker immediately reverses their trade in a following transaction in the same or next block, restoring the price and capturing the spread; the user's UEA (or refund recipient) receives less PC than the pre-manipulation fair value would have provided.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
```
