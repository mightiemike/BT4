## Finding

### Title
PRC20 minted 1:1 against the raw gateway `amount` field with no reconciliation against tokens actually escrowed, enabling vault insolvency for fee-on-transfer/deflationary ERC20s - (File: `x/uexecutor/keeper/handler.go`)

### Summary
Push Chain mints PRC20 supply strictly from the `amount` value encoded in the source-chain Gateway event, without ever checking or recording how many underlying tokens the Gateway/vault contract actually retained. For any whitelisted ERC20 that charges a transfer fee (or is later upgraded/re-pegged to do so), the PRC20 supply minted on Push Chain permanently exceeds the tokens actually custodied on the source chain — the exact accounting mismatch described in the wfCash `M-14` report, just moved from an fCash lending flow to Push Chain's inbound-deposit/mint flow.

### Finding Description
Universal Validators parse the Gateway's `sendFunds`/`addFunds` log and lift the `amount` word directly into `Inbound.Amount`, with no reference to any balance-before/after delta on the vault: [1](#0-0) [2](#0-1) 

That `Inbound.Amount` is voted on by Universal Validators and, once quorum is reached, is passed straight into the deposit path with no further reconciliation: [3](#0-2) 

`depositPRC20` converts the string amount and calls `CallPRC20Deposit` for that exact amount — it never queries the vault's actual token balance, never accounts for any deflationary/fee-on-transfer behavior of the underlying ERC20, and never diffs "amount requested by user" against "amount actually escrowed by the vault": [4](#0-3) 

`CallPRC20Deposit` then mints exactly that amount of PRC20 into the recipient's UEA/contract via `depositPRC20Token` on the `UNIVERSAL_CORE` handler contract: [5](#0-4) 

This is structurally identical to the wfCash bug: the `wfCash` vault minted `fCashAmount` shares 1:1 against the deposit *requested*, while the underlying custody credited to the vault (`actualTransferExternal` in `TokenHandler`) was `depositAmount - transferFee` for fee-on-transfer tokens — so total shares outstanding permanently exceeded backing assets. Here, `Inbound.Amount` plays the role of "requested deposit" and the PRC20 mint plays the role of "shares issued"; nothing in the `x/uexecutor` scope reconciles it against what the Gateway/vault contract on the source chain actually retained after any token-level transfer fee.

The `x/uregistry` `TokenConfig` registry only records `NativeRepresentation.ContractAddress`, decimals, and a liquidity cap — none of which is a fee-on-transfer flag or a balance-based accounting mechanism: [6](#0-5) 

Once a token is whitelisted (a one-time admin action unrelated to the exploit trigger — matching the original report's acceptance despite requiring a fee-on-transfer asset), any ordinary unprivileged user who deposits through the Gateway using that token causes the PRC20 supply on Push Chain to permanently exceed the custody the Gateway/vault actually holds, whether because the token already charges a transfer fee or because an upgradeable/pausable ERC20 enables one after listing (e.g. USDT-style `basisPointsRate`). No privileged Push Chain action is needed at deposit time — the mismatch is baked into the blind trust of the event's `amount` field.

### Impact Explanation
- Total PRC20 supply for the affected token can no longer be backed 1:1 by the tokens actually escrowed by the Gateway/vault on the source chain — this is a direct corruption of PRC20 accounting, matching the "Registry and accounting path" invariant in scope (`token mapping ... must not misroute value or attach the wrong asset semantics`).
- The deficit compounds with every deposit of the affected token; the last holders attempting to bridge PRC20 back out (via outbound/withdraw) will be unable to redeem, because the vault does not hold enough of the underlying asset — an unauthorized/uncollateralized mint from the perspective of the vault's actual holdings.
- No governance/admin misbehavior is required at trigger time — an ordinary, unprivileged depositor using an already-whitelisted token is sufficient once that token's transfer-fee behavior is active.

### Likelihood Explanation
Likelihood depends on whether any currently/future-whitelisted `TokenConfig` entry corresponds to an ERC20 (or SPL token with a transfer-fee extension) that charges a transfer fee, either at listing time or after an upgrade. Given `x/uregistry` supports arbitrary admin-added ERC20/SPL tokens and there is no fee-on-transfer flag, guard, or balance-verification step anywhere in the inbound deposit path, this is readily triggerable for any such token without additional privileged conditions.

### Recommendation
- Have the event listener / Gateway integration capture and vote on the *actual* amount the vault contract received (e.g., balance-before/after on the vault, mirroring the fix direction the original report recommended for `wfCashERC4626`), rather than trusting the `amount` word emitted by the source-chain event.
- Alternatively, add an explicit `IsFeeOnTransfer`/`TransferFeeBps` (or "requires balance-diff accounting") flag on `TokenConfig`, and reject/adjust minting for such tokens until verified reconciliation is implemented, consistent with Notional's chosen fix of disallowing lend-at-zero (i.e., disallowing 1:1 amount-based minting) for fee-on-transfer assets.
- As defense in depth, periodically reconcile per-token PRC20 total supply against the Gateway/vault's on-chain custodied balance and alert/halt inbound processing for a token if a persistent deficit is detected.

### Proof of Concept
1. Admin whitelists an ERC20 token `T` in `x/uregistry` `TokenConfig` with `NativeRepresentation` pointing to PRC20 `pT` (a one-time listing action, not part of the exploit trigger).
2. Token `T`'s contract (already deployed on the source chain, outside Push Chain's control) charges a 2% transfer fee — either from day one or via a later fee-toggle the token contract owner enables (independent of Push Chain governance).
3. An ordinary unprivileged user calls the Gateway's `addFunds`/`sendFunds` with `amount = 1_000_000` of `T`. The Gateway contract's `transferFrom` only actually receives `980_000` `T` due to the transfer fee, but its emitted event still encodes `amount = 1_000_000` (assuming the Gateway does not do a balance-diff check, which is outside Push Chain's own scoped code).
4. Universal Validators parse the log via `parseUniversalTxEvent`/`parseSendFundsEvent`, extract `Amount = "1000000"`, and vote it via `MsgVoteInbound`.
5. Once quorum passes, `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints `1_000_000` `pT` to the recipient — 20,000 more than what the vault actually escrowed.
6. Repeating this deposit accumulates an ever-growing shortfall between `pT` total supply and `T` tokens actually held by the Gateway/vault, so later PRC20 holders cannot fully redeem/withdraw — mirroring the wfCash insolvency scenario exactly.

// parseUniversalTxEvent parses a UniversalTx event from log data.
func parseUniversalTxEvent(event *store.Event, log *types.Log, chainID string, logger zerolog.Logger) {
	if len(log.Topics) < 3 {
		logger.Warn().Msg("not enough indexed fields; nothing to do")
		return
	}

	payload := common.UniversalTx{
		SourceChain: chainID,
		Sender:      ethcommon.BytesToAddress(log.Topics[1].Bytes()).Hex(),
		Recipient:   ethcommon.BytesToAddress(log.Topics[2].Bytes()).Hex(),
		LogIndex:    log.Index,
	}

	if len(log.Data) < 32*5 {
		b, _ := json.Marshal(payload)
		event.EventData = b
		return
	}

	// Parse common static fields: token (Word 0), amount (Word 1)
	payload.Token = ethcommon.BytesToAddress(log.Data[0*32+12 : 0*32+32]).Hex()
	payload.Amount = new(big.Int).SetBytes(log.Data[1*32 : 2*32]).String()

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
