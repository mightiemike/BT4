### Title
Failed deposits are permanently removed from mempool without being credited - ([File: crates/sequencer/src/runner.rs])

### Summary
`deposit_data` fetched from the mempool (runner.rs:517-520) is passed unmodified into `dry_run_transactions`/`process_sys_txs`, and after the block is committed the *entire original* `deposit_data` set is passed to `remove_deposits` (runner.rs:636-638), even though `process_sys_txs` can `continue` past a deposit whose system transaction reverted (runner.rs:1682-1696) without pushing it into `all_txs` (runner.rs:1702). The removal set is not filtered down to the deposits that actually succeeded, so a deposit that failed inside the EVM (e.g. depositing to a non-EOA/contract address) is deleted from the mempool forever without cBTC ever being credited.

### Finding Description
The binding that should hold is: `deposits_removed_from_mempool == deposits_whose_system_tx_is_in_all_txs (i.e. actually included in l2_block.txs)`. Tracing the code shows this binding is broken:

- `deposit_data` is fetched once at runner.rs:517-520 via `fetch_deposits`, which does not remove anything [1](#0-0) .
- `deposit_data` is passed by reference into `dry_run_transactions` at runner.rs:549-556, eventually reaching `process_sys_txs`.
- Inside `process_sys_txs`, for each system event (including `SystemEvent::BridgeDeposit`), the corresponding system transaction is applied; if it fails with `EvmSystemTransactionNotSuccessful` and it's a deposit, the working set is reverted and the loop `continue`s without appending to `all_txs` [2](#0-1) . This means the deposit's system transaction never lands in the committed L2 block's transaction list.
- After the block is finalized and saved (runner.rs:634), the sequencer unconditionally calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the *original, unfiltered* `deposit_data` fetched before `process_sys_txs` ran [3](#0-2) .
- `remove_deposits` matches deposits purely by `calc_tx_id` against the caller-supplied slice and removes every match from `accepted_deposit_txs` and `pending_deposits`, with no knowledge of which deposits were actually included in `all_txs` [4](#0-3) .

There is no code path that re-adds a failed deposit back to the mempool or otherwise records it for retry; once `remove_deposits` runs, that deposit's raw data is gone from `accepted_deposit_txs`/`pending_deposits`, and since `add_deposit_tx` only rejects true duplicates (via `pending_deposits`), the deposit is not "duplicate-blocked" — it's simply discarded and can never be resubmitted through the normal deposit RPC path relying on the mempool's own accounting, because the sequencer's local record of "pending" no longer contains it and no other component tracks that this specific Bitcoin deposit still needs processing.

### Impact Explanation
A depositor whose `BridgeDeposit` system transaction reverts (e.g., due to a bridge contract-side condition causing `EvmSystemTransactionNotSuccessful`) has their deposit silently dropped from the sequencer's mempool while cBTC is never minted. This is a fund-freezing bug: the underlying Bitcoin deposit already occurred (BTC is locked on the Bitcoin side / moved to the bridge), but the L2 credit that should follow never happens and the record is deleted, so the deposit can't be retried by the sequencer's own accounting. This matches the "funds permanently frozen" Critical impact category. The bug is repeatable for every deposit that hits this revert path across blocks.

### Likelihood Explanation
This requires only that a `BridgeDeposit` system transaction fails validation/execution inside `process_sys_txs` (the code comment explicitly acknowledges "deposits to non-EOA addresses can revert" as an expected failure mode), which an attacker (or even an honest user with a misconfigured recipient) can trigger by crafting/submitting a deposit whose EVM-side crediting call reverts. No special privilege is needed beyond normal deposit submission via `citrea_sendRawDepositTransaction`, and the condition is fully attacker-triggerable and repeatable.

### Recommendation
Track which deposits actually succeeded (i.e., correspond to entries pushed into `all_txs` in `process_sys_txs`) and only call `remove_deposits` with that successfully-included subset, not the full `deposit_data` fetched before processing. Failed deposits should either remain in the mempool for retry, or be explicitly moved to a separate "failed/needs-manual-intervention" record rather than being silently discarded.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
