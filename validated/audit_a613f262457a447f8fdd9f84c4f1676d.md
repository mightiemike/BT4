This confirms the analog. The `ScanFilter::OnlyAbnormal` mode is explicitly documented as "assuming that on-disk accounts index contains only normal accounts index entry" (`ref_count == 1` and `slot_list.len() == 1`) [1](#0-0) , and `load_accounts_index_for_shrink` relies on exactly this unverified assumption when scan returns `None` [2](#0-1) . The `OnlyAbnormalWithVerify` variant exists specifically to double check this assumption against the on-disk index [3](#0-2) , and `only-abnormal` (without verify) is documented as a "debug option" that explicitly "assumes" the on-disk invariant holds without checking it [4](#0-3) .

### Title
Shrink's zero-lamport single-ref purge trusts an unverified "on-disk entries are always normal" invariant under `ScanFilter::OnlyAbnormal` - (File: accounts-db/src/accounts_db.rs)

### Summary
`load_accounts_index_for_shrink()` decides whether a zero-lamport account can be safely dropped from the index by checking `ref_count == 1` from `self.accounts_index.scan(...)` [5](#0-4) . When the configured `ScanFilter` is `OnlyAbnormal`, a `None` result from `scan()` is *assumed* — not verified — to mean the on-disk index entry is "normal" (`ref_count == 1`, `slot_list.len() == 1`) [2](#0-1) , and the code hardcodes `ref_count = 1` and a single-element `slot_list` for that case instead of reading the actual disk entry [6](#0-5) . This is analogous to the reported Solidity bug: code that indexes/treats a single element as authoritative (`solverOps[0]` implying "exactly one solver") without enforcing that invariant; here, `ref_count == 1` from a purely in-memory scan is treated as proof of a "lone instance" without confirming the on-disk slot list truly has exactly one entry, relying purely on convention plus the docs' own admission that this is an "assumption."

### Finding Description
`ScanFilter::OnlyAbnormal` is documented to only scan the in-memory index and to "skip scanning on-disk accounts index by assuming that on-disk accounts index contains only normal accounts index entry" [7](#0-6) . The `scan()` implementation enforces this literally: for `OnlyAbnormal`/`OnlyAbnormalTest`, if the pubkey is not in memory, the callback is invoked with `None` without ever consulting the disk-backed index [6](#0-5) . Only the separate `OnlyAbnormalWithVerify` filter actually reads back the disk entry and asserts `ref_count == 1 && slot_list.len() == 1` [3](#0-2) ; plain `OnlyAbnormal` performs no such verification.

`load_accounts_index_for_shrink()` consumes this `None` result and unconditionally treats it as "ref_count=1 and slot_list.len()=1," per its own comment: "getting None here means the account is 'normal'... This means it must have ref_count=1 and slot_list.len() = 1" [8](#0-7) . Combined with `is_zero_lamport() && ref_count == 1`, this path pushes the pubkey into `zero_lamport_single_ref_pubkeys`, and subsequently `remove_zero_lamport_single_ref_accounts_after_shrink()` calls `purge_keys_exact([(pubkey, slot)])` to fully remove the index entry [9](#0-8) . If for any reason (e.g. a bug elsewhere in ref-counting/index maintenance, or an operator running with `--accounts-db-scan-filter-for-shrinking only-abnormal` on data whose invariant was violated) the on-disk index entry actually holds more than one slot, this purge removes state for an account that is still referenced by another slot, effectively acting on stale/incorrect data — same root-cause shape as the auditor's report: consuming an assumed-singleton without enforcing it, only asserted as correct in a differently-configured "with verify" code path, exactly like the fix in PR 172 moved the "exactly one" enforcement into a dedicated check rather than relying on convention.

### Impact Explanation
If the unverified "on-disk-implies-normal" assumption is ever violated, `remove_zero_lamport_single_ref_accounts_after_shrink()` purges the pubkey's index entry entirely via `purge_keys_exact` [9](#0-8) , silently dropping any surviving slot-list entries for that pubkey that were never scanned. This is a silent, incorrect divergence in accounts-index state (a stale/wrong-version account load or effective balance loss for the dropped slot reference), which could propagate into hash calculation or snapshot generation mismatches between the pruned in-memory view and what disk actually contains.

### Likelihood Explanation
This is gated behind the non-default `ScanFilter::OnlyAbnormal` configuration (`--accounts-db-scan-filter-for-shrinking only-abnormal`), which the code explicitly labels a debug option relying on an assumption [4](#0-3) ; the default is `ScanFilter::All`, which fully scans on-disk and does not hit this path [10](#0-9) . Triggering the unsafe behavior additionally requires the underlying invariant (every disk-only entry has `ref_count==1`/`slot_list.len()==1`) to actually be false, which the codebase otherwise works hard to guarantee elsewhere (e.g. `test_generate_index_duplicates_within_slot` panics on duplicates [11](#0-10) , and `exhaustively_verify_refcounts` exists purely to catch such mismatches [12](#0-11) ). Given the maturity of the ref-count invariant enforcement, exploitability under normal operation is low; the residual risk is a latent correctness bug if that invariant is ever broken (by a future regression) combined with an operator opting into `only-abnormal` mode, at which point `OnlyAbnormalWithVerify` provides no runtime safety net since it's a distinct, unused-by-default option.

### Recommendation
Either remove the non-verifying `ScanFilter::OnlyAbnormal` option (keeping only `OnlyAbnormalWithVerify` or `All` as safe choices), or have `load_accounts_index_for_shrink()`/`can_purge_zero_lamport_single_ref_after_shrink` paths always assert the disk invariant (as `OnlyAbnormalWithVerify` already does) before purging based on an assumed single reference, similar to how the Solidity fix moved the "exactly one" enforcement into an explicit runtime check (`_verifyAuctioneer()`) rather than relying on convention that `solverOps[0]` implies a singleton.

### Proof of Concept
1. Configure a validator/ledger-tool run with `--accounts-db-scan-filter-for-shrinking only-abnormal` [13](#0-12) .
2. Through any latent bug that leaves an on-disk index entry with `slot_list.len() > 1` for a pubkey that is not currently held in memory (i.e., not "abnormal" per the in-memory bookkeeping), trigger a shrink of a slot containing a zero-lamport version of that account.
3. `self.accounts_index.scan(..., ScanFilter::OnlyAbnormal)` returns `None` for that pubkey (since it isn't in memory) without checking disk [6](#0-5) .
4. `load_accounts_index_for_shrink()` treats this as `ref_count = 1`, adds the pubkey to `zero_lamport_single_ref_pubkeys` [2](#0-1) .
5. `remove_zero_lamport_single_ref_accounts_after_shrink()` purges the pubkey's index entry entirely, discarding the unscanned slot-list entries and any account data they represent [9](#0-8) .
