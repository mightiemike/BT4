### Title
`replay-verify` tooling silently accepts divergent state/hot-state/position checkpoint roots because `ensure_match_transaction_info` skips checkpoint-hash comparison - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by `db-tool`'s `replay_on_archive`, `aptos-debugger`, and the CLI's replay/verify commands) is the authenticated check that a locally re-executed transaction's output matches the persisted, ledger-proof-bound `TransactionInfo` for a version. It verifies `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`, but explicitly does **not** verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the state-commitment roots that are actually written into the accumulator and bound by ledger proofs. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` performs field-by-field comparison between the locally-computed `TransactionOutput` and the on-disk/archived `TransactionInfo`: [2](#0-1) 

It checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event-accumulator root (`event_root_hash`). Immediately after, the code has an explicit comment acknowledging the gap: [3](#0-2) 

This means the function returns `Ok(())` even when the locally recomputed state root (`state_checkpoint_hash`), the hot-state root (`hot_state_checkpoint_hash`), or the native-position state root (`position_state_checkpoint_hash`) diverge from what is committed/authenticated in the archived `TransactionInfo`. These three fields are exactly the fields that get embedded in the transaction-accumulator leaf and are thus covered by `TransactionAccumulatorProof`/`TransactionInfoWithProof` verification elsewhere in the codebase (see `verify_transaction_info` in `types/src/proof/mod.rs`) — i.e., they are the state-commitment values whose correctness matters for consensus/state-sync/back-up integrity.

`ensure_match_transaction_info` is used by tooling whose entire purpose is to detect exactly this kind of divergence: `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. These tools re-execute historical transactions against archived VM outputs to confirm that local execution reproduces the authenticated on-chain result — the standard "replay-verify" mechanism used to detect state-divergence bugs (including hard-fork-class divergence) before they reach production, or to audit the correctness of past state roots. Because the state/hot-state/position checkpoint hashes are excluded from the comparison, this tool would report "match" (successful replay) even if the locally computed state root differs from the one committed on-chain.

### Impact Explanation
If the local VM/state-computation logic diverges from what actually got committed (e.g., an execution/storage bug corrupting state values, an incorrect state-checkpoint materialization, or in particular a bug specific to the newer hot-state/position-state-root ("trading-native") feature under active development in this fork), `replay_on_archive` and similar debugger/CLI replay tools would falsely report the historical execution as consistent. This defeats the primary purpose of that tool — catching state-commitment corruption or hard-fork-only divergence between execution result and durable ledger data — and could let a corrupted, incorrectly-computed state root go undetected during audits or upgrade validation, even though the root cause (a state-computation bug) genuinely produces the wrong committed value. The comment itself flags this as unsafe to leave unresolved before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, i.e., the authors are aware this must be fixed before the position/hot-state root feature becomes commitment-critical in this feature branch.

### Likelihood Explanation
Likelihood of the gap being triggered is tied to the presence of a genuine state-computation defect (e.g., in the hot-state / native-position-state-root code paths, which are explicitly called out as under development, "not yet run in consensus or state-sync on mainnet/testnet" per adjacent comments). On its own, this is not an attacker-triggerable exploit; it's an integrity gap in a *verification tool*, so its severity depends on whether an actual state-corruption bug exists elsewhere to be masked. As a standalone code defect, however, it unconditionally silences detection of any divergence in these three commitment fields, which is a deterministic, always-reproducible verification-integrity gap. Below the high-severity impact threshold for a hard state-execution exploit, but a real proof-verification-integrity flaw whose consequence is "wrong committed root accepted as matching."

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding locally-recomputed values (when available/applicable), gating the comparison on whichever of `hot_state_root_in_txn_info`/`compute_trading_native_state_roots` on-chain configs are active, consistent with what the code's own TODO says must be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled. This closes the gap before it is relied upon in production verification workflows.

### Proof of Concept
Not applicable as a live exploit — this is a code-inspection finding in `ensure_match_transaction_info`. To reproduce the gap: construct a `TransactionOutput`/`TransactionInfo` pair where `state_change_hash` and `event_root_hash` match but `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) differ, and observe that `ensure_match_transaction_info` returns `Ok(())` per the logic at [4](#0-3) , i.e. no comparison of these fields is performed before returning success.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
