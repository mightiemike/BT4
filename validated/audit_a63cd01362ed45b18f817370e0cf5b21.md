### Title
Replay-verify integrity check never validates the state-checkpoint root, allowing state-root corruption to pass as a "verified" replay - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole invariant used by Aptos's replay-verify safety net (`storage/db-tool/src/replay_on_archive.rs` and `ChunkExecutor::verify_execution` in `execution/executor/src/chunk_executor/mod.rs`) to decide whether a locally re-executed transaction matches the authenticated, on-chain `TransactionInfo`. The function checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but never checks `state_checkpoint_hash` (nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against a locally recomputed state root. This mirrors the external report's bug class exactly: a validation step exists and looks authoritative, but the actual value that matters (here the merklized state root, there the payout percentage) is silently excluded from the check, so the checked invariant diverges from ledger reality.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs. `txn_info.state_change_hash()`
- event root hash vs. `txn_info.event_root_hash()`

The function's own trailing comment documents the gap directly: [2](#0-1)  — it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This comparator is the only correctness check performed by two independent replay/verification call sites that do **not** go through the authoritative state-checkpoint pipeline (`DoStateCheckpoint`/`get_state_checkpoint_hashes`, which does correctly compare a computed root against known hashes at [3](#0-2) ):

1. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes a chunk with `AptosVMBlockExecutor::execute_block` and calls only `ensure_match_transaction_info` per transaction, with no separate state-root recomputation/comparison: [4](#0-3) .
2. `ChunkExecutor::verify_execution` (used by `TransactionReplayer::enqueue_chunks`, the replay path exercised during restore/backup replay verification) likewise only calls `ensure_match_transaction_info` per transaction after `DoGetExecutionOutput::by_transaction_execution`, again without any check that the resulting state tree root matches `txn_info.state_checkpoint_hash()`: [5](#0-4) .

Because write-set contents (`state_change_hash`) can be byte-for-byte identical to the archived write set while the *merklization* of those writes into the Jellyfish Merkle state tree diverges (e.g., a bug in SMT leaf ordering, key-hash collision handling, or checkpoint-boundary selection that doesn't touch the write set itself but does touch how it's folded into the tree), `ensure_match_transaction_info` would report success even though the true state root differs from the one committed on mainnet.

### Impact Explanation
Aptos's replay-verify tooling exists specifically to catch "hard-fork-only" divergence — bugs in state-tree/root computation that don't manifest until enough validators run different code and disagree on state — before they reach production and before feature flags depending on new tree structures are enabled. Because the comparator used by both the archival replay-verify tool and the chunk-executor's transaction-level replay verification never re-derives and compares the state-checkpoint root (`state_checkpoint_hash`, and by the code's own admission also `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`), a state-root-corrupting bug that leaves write-set contents intact would silently pass CI/backup-verification as a "successful replay." This directly undermines the "Proof and Storage Pivots" invariant that "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding," since the tooling meant to enforce that binding does not actually check it at the per-transaction level.

### Likelihood Explanation
The gap is not hypothetical: it is called out explicitly in the shipped code comment as a known, currently-unaddressed limitation that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — but the comment's own wording, and the code as-is, shows the state/hot-state checkpoint hashes are *already* excluded from the check today, independent of that future feature flag. Any executor/state-merklization bug that preserves write-set byte content but corrupts the resulting tree root would go undetected by both call sites shown above, since no other code path in `replay_on_archive.rs` or `ChunkExecutor::verify_execution` cross-checks the state root.

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check invoked alongside it) to independently recompute the state-checkpoint root for checkpoint transactions and assert it equals `txn_info.state_checkpoint_hash()` (and equivalently for `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` once those roots are locally derivable in this code path), so that both `replay_on_archive` and `ChunkExecutor::verify_execution` cannot report a "successful" replay when the authenticated state root diverges from local re-execution.

### Proof of Concept
No dynamic PoC was run; this is a static code-path analysis. The root cause is directly demonstrated by:
- The comparator's implementation omitting any `state_checkpoint_hash` comparison: [6](#0-5) .
- Its two callers using it as the sole correctness gate for a chunk of re-executed transactions without independently validating the state root: [7](#0-6) , [8](#0-7) .

Note: I was unable to further verify whether any other layer in the `replay_on_archive` binary (outside the excerpted file) performs a supplemental state-root check; based on the available indexed contents of `storage/db-tool/src/replay_on_archive.rs`, no such check exists in that file. If a hidden/second validation exists elsewhere and is not indexed, it could mitigate this finding — I could not locate one with available tools and note this uncertainty explicitly.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
