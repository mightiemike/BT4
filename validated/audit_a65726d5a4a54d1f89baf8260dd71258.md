## Finding: Backup‑restore path commits write sets without validating them against the transaction‑info's `state_change_hash`

### Summary
The transaction-backup restore path (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`) authenticates the accumulator/ledger-info binding for transactions, transaction-infos and events, but never re-derives or checks that the `WriteSet` bytes read from the backup chunk actually hash to the `state_change_hash` recorded in the (authenticated) `TransactionInfo`. The write set is then persisted verbatim through `WriteSetDb::put_write_set` with no further verification.

### Finding Description
In `LoadedChunk::load` [1](#0-0) , each backup record is deserialized into `(txn, aux_info, txn_info, events, write_set)`. The `write_set` is pushed into its own `Vec<WriteSet>` that is kept completely separate from the data structure used for cryptographic verification.

Only `txns`, `events`, and `txn_infos` are packed into a `TransactionListWithProofV2` and verified against the accumulator range proof and the (epoch-history-checked) `LedgerInfoWithSignatures`: [2](#0-1) 

This verification proves that `txn_infos[i]` (which internally contains a `state_change_hash` field committing to the write set produced by executing `txns[i]`) is correctly bound to the accumulator root in `ledger_info`. It does **not** take `write_sets` as an input at all, so it cannot detect a mismatch between the returned `write_sets` vector and the `state_change_hash` inside the now-authenticated `txn_infos`.

After loading, `LoadedChunk::unpack` returns the untouched `write_sets` [3](#0-2) , which flow straight into `restore_handler.save_transactions(...)` [4](#0-3) .

`RestoreHandler::save_transactions` forwards to `restore_utils::save_transactions` with no hash check [5](#0-4) .

`save_transactions_impl` then persists the write sets one-to-one by version using `WriteSetDb::put_write_set`, again with no comparison to `txn_info.state_change_hash`: [6](#0-5) .

`WriteSetDb::put_write_set` itself is a raw, unconditional DB write [7](#0-6) , identical to the path used for normally-executed `commit_write_sets` [8](#0-7) .

Net effect: as long as the backup-file's `txn`, `txn_info`, and `events` records are internally consistent with a valid accumulator proof/ledger info (which an attacker able to influence backup-storage content can construct once, since these are independent leaf hashes that don't cover write-set bytes at all in the verification call graph used here), the `write_set` bytes accompanying that record can be arbitrary and will be written into `WriteSetDb` unchecked.

### Impact Explanation
A restored node's `WriteSetDb` for the affected version(s) would contain a `WriteSet` that does not match the one actually produced by VM execution / attested to by `state_change_hash`, i.e., committed data diverges from the authoritative ledger content. Any downstream consumer of `get_write_set`/`get_write_sets` (e.g., replay, indexing, state reconstruction, `db-restore` KV-replay path in `save_transactions_impl` which calls `calculate_state_and_put_updates` using these very write sets) would derive incorrect state — this is a durable, silent corruption of ledger data on the restored node, matching the "committed state differs from the correct VM result / corrupts durable ledger data" impact category.

### Likelihood Explanation
Requires the restore process to consume a backup chunk file whose `write_set` bytes for a given transaction have been altered/desynchronized from the txn/txn_info/events records while keeping the latter three internally consistent with a valid accumulator proof (an attacker able to influence what an unprivileged/externally-served backup blob contains, as posited in the question, can do this deterministically because the write_set is never covered by the proof verification that gates acceptance).

### Recommendation
Before persisting write sets in `LoadedChunk::load` (or in `restore_utils::save_transactions`), recompute the write-set hash for each transaction and assert it equals `txn_infos[i].state_change_hash()` (the field name may vary; it is the write-set-hash field of `TransactionInfo`), rejecting the chunk on mismatch — mirroring how `txn`/`event` hashes are already checked by `TransactionListWithProofV2::verify`.

### Proof of Concept
1. Take a valid transaction backup chunk file (raw record stream consumed by `LoadedChunk::load`).
2. For one record, replace the serialized `WriteSet` bytes with an arbitrary different `WriteSet` while leaving `txn`, `aux_info`, `txn_info`, and `events` untouched (so `TransactionInfo`'s `state_change_hash`, the accumulator proof, and the `LedgerInfoWithSignatures` all remain internally valid/unchanged).
3. Feed the tampered chunk through `TransactionRestoreController::run` → `LoadedChunk::load` → `txn_list_with_proof.verify(...)` — verification succeeds because it never inspects `write_sets`.
4. Observe `restore_handler.save_transactions` commits the tampered `WriteSet` via `WriteSetDb::put_write_set` for that version.
5. Compare `AptosDB::get_write_set(version)` on the restored node against the write set implied by `txn_info.state_change_hash` (or against an independently re-executed VM result) — they differ, confirming corruption went undetected.

Note: I was unable to retrieve the full `TransactionInfo` struct definition (`types/src/transaction/mod.rs`) content in this session due to tool output truncation, so the exact field name (`state_change_hash`) and its exact semantics should be double-checked by a reviewer with full file access, though this is consistent with Aptos's standard `TransactionInfo` layout.

    /// Commits write sets starting from `first_version` to the database.
    pub(crate) fn commit_write_sets(
        &self,
        first_version: Version,
        transaction_outputs: &[TransactionOutput],
    ) -> Result<()> {
        let _timer = OTHER_TIMERS_SECONDS.timer_with(&["commit_write_sets"]);

        let chunk_size = transaction_outputs.len() / 4 + 1;
        let batches = transaction_outputs
            .par_chunks(chunk_size)
            .enumerate()
            .map(|(chunk_idx, chunk)| {
                let mut batch = self.db().new_native_batch();
                let chunk_first_version = first_version + (chunk_idx * chunk_size) as Version;

                chunk.iter().enumerate().try_for_each(|(i, txn_out)| {
                    Self::put_write_set(
                        chunk_first_version + i as Version,
                        txn_out.write_set(),
                        &mut batch,
                    )
                })?;
                Ok(batch)
            })
            .collect::<Result<Vec<_>>>()?;

        {
            let _timer = OTHER_TIMERS_SECONDS.timer_with(&["commit_write_sets___commit"]);
            for batch in batches {
                self.db().write_schemas(batch)?
            }
            Ok(())
        }
    }
