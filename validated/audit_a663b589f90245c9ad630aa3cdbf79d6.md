### Title
Witness Private Keys Are Accepted and Held in Plaintext Memory via CLI/Config, With No In-Memory Protection - ([File: framework/src/main/java/org/tron/core/config/args/CLIParameter.java])

### Summary
java-tron's witness/SR (Super Representative) node signing key can be supplied as a raw plaintext hex string via the `-p/--private-key` command-line flag or the `localwitness` config array, and is then held for the life of the process as plaintext `String` objects inside `LocalWitnesses.privateKeys`, with no encryption-at-rest-in-memory and no secure wipe, mirroring the in3-server key-management weaknesses described in the report.

### Finding Description
The CLI exposes a plaintext private-key option: [1](#0-0) 

This is consumed by `WitnessInitializer.initFromCLIPrivateKey`, which wraps the raw string in `LocalWitnesses` without ever encrypting it: [2](#0-1) 

The config-file path is equally permissive — `docs/configuration.md` documents a `localwitness` array holding the plain private key directly in `config.conf`, only recommending (not enforcing) the keystore alternative: [3](#0-2) 

That path also goes through `WitnessInitializer.initFromCFGPrivateKey`, storing keys unmodified: [4](#0-3) 

`LocalWitnesses` itself stores the key material as an immutable `String` in a `List<String>` field for the lifetime of the running node, with no encryption wrapper and no ability to zero the memory (Java `String`s cannot be reliably wiped, unlike the `byte[]` key material that the newer `KeystoreImport`/`KeystoreUpdate` tools explicitly zero after use): [5](#0-4) [6](#0-5) 

Every time a block is signed, `getPrivateKey()` returns this plaintext string directly, and `getPublicKey()`/`initWitnessAccountAddress()` re-derive the address from the private key on demand rather than caching only the derived address — exactly the anti-pattern (recomputing address from key instead of storing the address) called out in the original report's "store the keys eth-address instead of re-calculating it" recommendation: [7](#0-6) [8](#0-7) 

By contrast, the newer `Toolkit.jar keystore import` path treats key material as `byte[]` and explicitly zeroes it after use — showing the project is aware of the secure pattern but does not apply it to the primary witness/signer bootstrap path: [9](#0-8) 

### Impact Explanation
A witness/SR private key controls block-signing authority and, if compromised, can be used to forge blocks, sign malicious data, or be otherwise abused to undermine consensus integrity for that node's stake — the same class of impact (impersonation, malicious signing, fund/authority loss) the original in3-server report describes. Passing the key via `-p/--private-key` on the command line exposes it to shell history and to any local user able to enumerate process arguments (e.g., via `/proc/<pid>/cmdline` or `ps`), and storing it as plaintext in `config.conf` risks accidental disclosure through backups, version control, or misconfigured file permissions. Holding the key as an immutable Java `String` for the process lifetime also means it cannot be scrubbed from memory, increasing the window in which a memory-dump/core-dump-capable attacker (e.g., via a separate vulnerability, swap file, or crash dump) could recover the raw key.

### Likelihood Explanation
The `-p/--private-key` CLI flag and `localwitness` config array are the officially documented, first-class ways to start a witness node (the config docs literally show the plaintext key as the primary example, with the keystore file commented out as a "recommended" alternative). This means plaintext key usage is not an edge case but the default/expected operational path for many SR node operators, making exposure highly likely in real deployments, especially given how commonly private keys leak into shell history, CI logs, or committed config files in practice (as also evidenced elsewhere in this codebase's history of hardcoded/test private keys being remediated).

### Recommendation
- Deprecate and eventually remove the plaintext `-p/--private-key` CLI option and the plaintext `localwitness` config entries, or at minimum emit a strong startup warning (similar to the `--keystore-factory` deprecation warning) urging migration to `localwitnesskeystore`.
- Store witness keys only in `byte[]` form, zero them immediately after deriving the `SignInterface`/address, and cache only the derived address in `LocalWitnesses`, following the same pattern already used in `KeystoreImport`/`KeystoreUpdate`.
- Avoid re-deriving the address from the raw key on every access (`getPublicKey()`); compute once at initialization and discard the raw key reference where possible.
- Document explicitly (as done for `keystore` plugin) that CLI-supplied plaintext keys persist in shell history and process argument listings.

### Proof of Concept
1. Start a witness node with `java -jar FullNode.jar -p 0x<64-hex-chars> --witness`.
2. On Linux, run `cat /proc/<pid>/cmdline | tr '\0' ' '` as another local user with permission to read `/proc/<pid>` (or `ps -ef | grep FullNode`) — the raw private key is visible in the process argument list.
3. Alternatively, configure `localwitness = ["<hex-private-key>"]` in `config.conf` and observe the key persists in plaintext on disk and is loaded unmodified into `LocalWitnesses.privateKeys` at [10](#0-9) , remaining in that plaintext `String` form for the entire lifetime of the JVM process.
