### Title
`CheckUnDelegateResource` precompile returns bandwidth/energy usage estimates that diverge from the usage actually removed by `UnDelegateResourceActuator` - ([File: actuator/src/main/java/org/tron/core/vm/utils/FreezeV2Util.java])

### Summary
The `CheckUnDelegateResource` TVM precompile is a "view"-style helper meant to let a contract preview how much bandwidth/energy usage will be cleared/retained if it un-delegates a given amount of frozen balance. Like `View::queryAssetBalances` in the Ammplify report, it computes an estimate using a formula that is *not* the same formula the state-changing actuator (`UnDelegateResourceActuator`) actually applies when the un-delegation executes, so the previewed value and the real on-chain effect diverge.

### Finding Description
`FreezeV2Util.checkUndelegateResource` (called from `PrecompiledContracts.CheckUnDelegateResource`) computes the "usage to be cleaned" purely from the **owner's own** usage/limit ratio: [1](#0-0) 

```
usagePair = getAccountNetUsageBalanceAndRestoreSeconds(accountCapsule)   // owner's own usage
resourceLimit = accountCapsule.getAllFrozenBalanceForBandwidth()          // owner's total frozen balance
...
clean = amount * ((resourceLimit - usage) / resourceLimit)
```

The actual state transition performed by `UnDelegateResourceActuator.execute`, however, computes the usage that is transferred back from the **receiver** using a completely different formula, based on the receiver's usage, the receiver's total frozen balance, and a cap derived from `TotalNetLimit`/`TotalNetWeight`: [2](#0-1) 

```
unDelegateMaxUsage = (unDelegateBalance / TRX_PRECISION) * (TotalNetLimit / TotalNetWeight)
transferUsage = receiverCapsule.getNetUsage() * (unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth())
transferUsage = min(unDelegateMaxUsage, transferUsage)
```

The two computations use different accounts (owner vs. receiver) and different bases (`resourceLimit` on the owner vs. `getAllFrozenBalanceForBandwidth()` on the receiver, plus a `TotalNetLimit/TotalNetWeight` cap that the view function never applies). The precompile's value is therefore not derived from the same state transition path that `execute()` performs at settlement time — mirroring the Ammplify root cause where the view function's balance calculation skipped a step (`FeeLib.applyJITPenalties`) that is only applied in the real state-changing path (`removeMaker`).

### Impact Explanation
Any TVM smart contract that calls the `CheckUnDelegateResource` precompile to decide how much bandwidth/energy usage it will retain/lose before issuing an `UnDelegateResourceContract` transaction will receive an incorrect estimate. Because on-chain contracts often make irreversible decisions (e.g., choosing an un-delegation amount to avoid falling below a required usage threshold, or computing downstream accounting) based on this precompile's return value, an incorrect estimate can lead to contracts under- or over-un-delegating, triggering unexpected bandwidth/energy shortfalls or incorrect accounting inside the calling contract. This is a resource-accounting correctness bug reachable from ordinary contract calls (no privileged actor needed), consistent with the Medium-severity classification given to the analogous `queryAssetBalances` issue (incorrect return value diverging from the real state-changing result).

### Likelihood Explanation
The divergence is deterministic and will occur any time a receiver's usage/frozen-balance ratio differs from the owner's, or whenever `TotalNetLimit/TotalNetWeight` caps the transferable usage — both of which are the normal, expected case for actively used delegated resources. Any contract that legitimately calls this precompile before un-delegating will observe the mismatch, so likelihood of hitting the bug is high; the only requirement is that a smart contract actually calls `CheckUnDelegateResource` and relies on the value for downstream logic.

### Recommendation
Align `FreezeV2Util.checkUndelegateResource` with the actual logic in `UnDelegateResourceActuator.execute`: base the usage estimate on the receiver's `getNetUsage()`/`getAllFrozenBalanceForBandwidth()` (or energy equivalent) ratio and apply the same `unDelegateMaxUsage` cap derived from `TotalNetLimit`/`TotalNetWeight` (or `TotalEnergyCurrentLimit`/`TotalEnergyWeight`), rather than computing the estimate from the owner's own usage ratio. Add regression tests comparing the precompile's returned value against the actual `transferUsage` computed by `UnDelegateResourceActuator` for the same delegation state.

### Proof of Concept
1. Account A delegates frozen balance for BANDWIDTH to account B.
2. B has heavy bandwidth usage relative to its total frozen balance (`getNetUsage()/getAllFrozenBalanceForBandwidth()` is high), while A's own usage ratio is low or zero.
3. A contract owned by A calls the `CheckUnDelegateResource` precompile before un-delegating; the precompile returns a "clean"/"remain" split computed from A's own low usage ratio (e.g., near-zero usage cleaned).
4. A then submits the actual `UnDelegateResourceContract`; `UnDelegateResourceActuator.execute` computes `transferUsage` from B's high usage ratio (capped by `unDelegateMaxUsage`), removing a materially different (larger) amount of usage from B/A's effective bandwidth than the precompile predicted.
5. The contract's on-chain decision made in step 3 is now invalidated by the real state change in step 4, demonstrating the estimate/execution mismatch.
