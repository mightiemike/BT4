## Title
Replay-verification of committed transactions never checks the state-checkpoint (Merkle root) hash, allowing an undetected state-root divergence to be reported as a successful replay — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the routine used by db-tool's replay/verify path to confirm that locally re-executed transactions match the transaction infos committed on-chain, never compares `state_checkpoint_hash` (the Sparse-Merkle-Tree/world-state root recorded for checkpoint transactions). It validates status, gas used, write-set hash and event root hash, but silently skips the one field that actually authenticates the resulting global state.

### Finding Description
`ensure_match_transaction_info` is the authoritative "does my local execution match the authenticated ledger" check: [1](#0-0) 

It asserts `status`, `gas_used`, `write_set_hash` (via `state_change_hash`), and `event_root_hash`, but there is no comparison of `self`'s locally-computed state-checkpoint hash against `txn_info.state_checkpoint_hash()` (nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`). The code even contains a self-documenting acknowledgment of the gap, but frames it only around the *not-yet-enabled* `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature — it does not call out that the base `state_checkpoint_hash` field, which is populated for every ordinary block-boundary/reconfiguration transaction today, is also unchecked: [2](#0-1) 

The `state_checkpoint_hash` is a real, currently-used, consensus-authenticated field: it is populated for every checkpoint transaction when transaction infos are assembled during normal block execution/commit, [3](#0-2) 

and it is the state root that goes into the `TransactionInfo` hashed into the transaction accumulator (i.e., it is part of what LedgerInfo ultimately certifies). This function is the sole verification gate used by the archive replay-verify tool: [4](#0-3) 

Because `ensure_match_transaction_info` never checks `state_checkpoint_hash`, a bug in the VM/executor/state-view pipeline that produces the correct write set and events but a divergent Sparse Merkle Tree root (e.g. wrong key hashing, mis-ordered writes affecting root computation, or a bad state-checkpoint algorithm) would pass `execute_and_verify` cleanly. The replay tool would report the replayed range as fully verified even though the reconstructed world state differs from the state authenticated by the real network at that checkpoint.

### Impact Explanation
This breaks the "authenticated ledger data must survive independent re-verification unchanged" invariant for exactly the field (`state_checkpoint_hash`) that binds the accumulator/TransactionInfo to the real world state at a block boundary. `replay_on_archive`/replay-verify is the safety mechanism operators and CI rely on to catch state-divergence bugs (including hard-fork-triggering ones) before or after they occur on mainnet. If the world-state root silently diverges due to an executor/storage bug, this tool — by design supposed to catch such divergence — will not flag it, because it only checks write-set hash, event hash, gas, and status, not the state-checkpoint hash that actually reflects the resulting Merkle state root. This directly matches the state-integrity gate's category of "wrong accumulator root ... accepted as valid" and "hard-fork-only divergence during ... replay ... not caught by the replay-verify tool.

### Likelihood Explanation
This is not attacker-triggerable directly; it requires an underlying (potentially rare) state-computation divergence bug elsewhere in the execution/storage pipeline. However, given that `state_checkpoint_hash` is exactly the class of value most likely to be corrupted by any subtle storage/JMT/SMT bug, and that this is the only automated safety net designed to catch that class of bug, the likelihood that such a bug (if it exists or is introduced later) goes undetected is high — the check is a no-op for the most important field it should validate.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s reconstructed state-checkpoint hash (and, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state or position-state roots are enabled, those too) against `txn_info.state_checkpoint_hash()` whenever the expected value is `Some(..)`, failing the comparison (and thus flagging the replay as broken) on any mismatch, rather than silently ignoring it.

### Proof of Concept
Conceptual reproduction (requires the ability to feed a divergent state-checkpoint hash through `execute_and_verify`):
1. Take any block whose last transaction is a checkpoint (i.e. has `Some(state_checkpoint_hash)` in the backed-up `TransactionInfo`).
2. Force the locally-executed state to produce identical events/write-set/gas/status, but a different SMT root (e.g. by patching `DoStateCheckpoint`/its inputs, or corrupting parent state before replay).
3. Run `replay_on_archive` (`storage/db-tool/src/replay_on_archive.rs`, `Verifier::execute_and_verify` calling `ensure_match_transaction_info`) over that range.
4. Observe that no error is returned even though the actual Merkle root recorded on-chain (`expected_txn_infos[idx].state_checkpoint_hash()`) differs from the locally recomputed one — the tool declares the block "verified" despite the state-root corruption.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
