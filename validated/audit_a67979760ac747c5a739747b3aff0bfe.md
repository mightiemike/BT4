### Title
Manipulable spot-price swap quote (`GetSwapQuote`/`QuoterV2`) with fixed 5% slippage lets an unprivileged user extract value from protocol gas refunds and deposit auto-swaps - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/outbound.go`, `x/uexecutor/keeper/execute_inbound_gas.go`)

### Summary
The Sherlock report describes a market-price-dependent value transfer (funding premium) computed from an easily-influenced instantaneous/short-window price, protected only by generic economic disincentives rather than a robust price-manipulation defense. Push Chain has a structurally similar pattern: several fund-moving flows (`applyGasRefund` for outbound gas refunds, `ExecuteInboundGas`/`ExecuteInboundGasAndPayload` for gas-abstraction deposits) fetch a live spot quote from an on-chain Uniswap V3 `QuoterV2.quoteExactInputSingle` pool via `GetSwapQuote`, and use only a fixed `quote * 95/100` slippage bound as the swap's `minPCOut` protection [1](#0-0) . Any unprivileged user who can trade against the same PRC20/WPC pool (a normal, permissionless PRC20 pool on Push Chain's own EVM) can move the spot price immediately before the protocol's swap executes, since the quote is taken from the current pool state rather than a manipulation-resistant TWAP.

### Finding Description
`GetSwapQuote` calls `QuoterV2.quoteExactInputSingle` with `sqrtPriceLimitX96 = 0`, reading whatever the pool's instantaneous price is at call time [4](#0-3) . This quote then becomes `minPCOut = quote * 95 / 100` in three separate flows:

1. `applyGasRefund` — refunding excess outbound gas fee to a user/relayer, swapping `gasToken → PC` [2](#0-1) .
2. `ExecuteInboundGas` — gas-abstraction inbound deposit-and-autoswap [3](#0-2) .
3. `gasAndPayloadDepositAutoSwap` — the combined gas+payload inbound route (same pattern, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`).

All three execute the resulting swap via a module-originated `DerivedEVMCall` (`CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas`) immediately after computing the quote, with no TWAP averaging, no re-check of price staleness, and only a flat 5% band. Because the pool that provides this quote is a normal Uniswap V3 pool deployed for the token pair (reachable and tradeable by any unprivileged user), an attacker can push the spot price by 5%+ in the direction that benefits them, wait for (or trigger, by being the sender of the qualifying inbound, or simply trading right before an outbound observation vote finalizes on a pending, publicly-visible `PendingOutbounds`/inbound entry) the protocol-driven swap to execute against the manipulated price, and then trade back — capturing the difference between the true market price and the manipulated 5%-band price at the victim swap's expense. This mirrors the audited bug's core weakness: a value calculation trusts a spot/short-horizon price that ordinary, unprivileged trading activity can move, with insufficient economic/structural friction (here, a fixed percentage band instead of a TWAP or dynamically-sized band) to prevent extraction.

### Impact Explanation
Successful manipulation results in either (a) the protocol/refund recipient receiving less PC than the fair-market value of the swapped PRC20 (silent value loss for the outbound sender/relayer whose excess gas is being refunded, or the gas-abstraction depositor), or (b) the swap failing to meet minPCOut and falling back to a no-swap raw PRC20 deposit — degrading UX/value for the affected user while the attacker profits from the temporary price dislocation. Funds are moved through legitimate, non-privileged, protocol-invoked EVM calls, so this is within scope as "corruption of ... gas fee accounting, refund accounting ... token mapping" reachable by an unprivileged trader.

### Likelihood Explanation
Exploitability depends on pool liquidity depth relative to attacker capital and on whether the timing of `MsgVoteOutbound`/inbound finalization (driven by honest UV votes, which is public/predictable state — `PendingOutbounds`/`PendingInbounds` are queryable) gives the attacker a window to move price beforehand. Since UV votes are gasless but publicly observable in mempool/chain state prior to finalization, and the swap executes deterministically once 2/3 UVs finalize, an attacker monitoring `PendingOutbounds` for a large refund on a shallow-liquidity gas-token pool has a realistic, non-privileged window to front-run. This requires no compromise of validators, UVs, or admin keys — only ordinary DEX trading capability on Push Chain's own EVM. I could not fully verify from the available code/index how strictly `PendingOutbounds`/`PendingInbounds` state is exposed pre-finalization or whether block-production timing in this Cosmos-SDK chain (no public EVM mempool, `GetMempool` returns nil) meaningfully limits front-running opportunities — this reduces certainty on the likelihood versus the pure "manipulate the pool now, wait for a large-refund event" strategy, which does not require precise front-running at all.

### Recommendation
Replace the raw spot quote from `QuoterV2.quoteExactInputSingle` with a TWAP-based quote (e.g., Uniswap V3 `observe`/oracle cardinality-based average over a window resistant to single-block manipulation), and/or make the slippage tolerance dynamic based on realized pool volatility/liquidity depth rather than a fixed 5%. Consider also capping the maximum swap size relative to pool liquidity, and adding a minimum time lag or randomized execution ordering between when `PendingOutbounds`/inbound gas routes become eligible and when the swap is actually executed, to reduce the value of front-running the on-chain quote.

### Proof of Concept
Conceptual sequence (not verified against a live testnet due to index limitations on runtime mempool/timing behavior):
1. Attacker identifies a `PendingOutbounds` entry (or submits/observes a large gas-abstraction inbound) whose `GasToken`/`WPC` Uniswap V3 pool has shallow liquidity.
2. Attacker swaps a large amount of `GasToken` for `WPC` (or vice versa) in that pool, moving the spot price such that `quoteExactInputSingle` will return a skewed quote in the attacker's favor for the upcoming protocol swap direction.
3. UVs finalize the outbound vote (or the inbound gas route executes); `applyGasRefund`/`ExecuteInboundGas` calls `GetSwapQuote` against the now-skewed pool and computes `minPCOut = quote*95/100`, then executes `CallUniversalCoreRefundUnusedGas`/`CallPRC20DepositAutoSwap` at the manipulated price.
4. Attacker reverses their initial trade, extracting the value difference between the manipulated and fair price, while the refund recipient/depositor receives correspondingly less value than the true market rate.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
