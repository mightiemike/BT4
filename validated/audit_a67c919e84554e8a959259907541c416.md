### Title
Accrual pause freezes `last-update` instead of advancing it, causing the full paused duration to be charged as interest on resume - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
Every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, and their `local-testing` counterparts) implements an "accrue pause" pass-through: when `pause-states.accrue` is `true`, `accrue()` returns the current `index`/`lindex` without updating them and, critically, without updating `last-update`. When the pause is later lifted, the next `accrue()` call computes `time-delta = stacks-block-time - last-update`, which now spans the *entire paused interval* plus the time since. This is the same root-cause shape as the Sherlock M-12 finding: a duration-based multiplier is computed from a bound timestamp that was never re-anchored to the point where "real" activity resumed, silently absorbing an interval during which nothing should have accrued.

### Finding Description
The vaults track interest with a scaled index and a `last-update` timestamp: [1](#0-0) 

```clarity
(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta rate time-delta true))))
          (calc-index-next idx multiplier)))))
```

and the public entrypoint: [2](#0-1) 

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                ...)
            ...
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
```

The value bound is `last-update` (the epoch anchor for interest accrual). The event that should invalidate/re-anchor it is the admin toggling `pause-states.accrue` off (resuming normal operation) at time `T_resume`, which is strictly later than the time the pause was engaged, `T_pause`. Because `accrue()` exits early during the paused branch, `last-update` is never touched between `T_pause` and `T_resume`. The later use is the very next non-paused `accrue()` call after resume, which computes `time-delta = block-time - last-update`, i.e., `(block-time - T_pause_start_anchor)`, silently re-including the entire `[T_pause_start_anchor, T_resume]` window as if the vault had been accruing interest continuously, even though the pause was specifically meant to freeze accrual.

This is directly analogous to the PoolTogether `finishDraw` bug: there, `startDrawAuction.closedAt` was used as the auction-start anchor even though the "real" clock should have started once the randomness became available; here, `last-update` is used as the accrual-start anchor even though the "real" clock should restart once the vault is un-paused. In both cases the elapsed-time input to a reward/interest multiplier wrongly spans a period during which the modeled process was not actually progressing, and in both cases the deviation is a strict overpayment (never an underpayment), because `calc-multiplier-delta`/`_computeFinishDrawReward` are monotonically increasing in elapsed time.

### Impact Explanation
Every vault's index/liquidity-index (and thus every borrower's owed debt and every supplier's owed yield) is computed from these accrual functions. If the DAO pauses accrual (e.g., during an oracle incident or an emergency response) for any nontrivial duration, resuming accrual will apply the full skipped period's worth of interest in one shot on the next call, retroactively charging borrowers interest and crediting the treasury/suppliers yield for time when the protocol had deliberately signaled "no accrual should occur." This inflates supplier-side unclaimed yield (and the treasury reserve minted alongside it) beyond what should have accumulated, and it forces borrowers into (invisibly) higher debt for a period of intentional freeze - a case of theft of unclaimed yield/incorrect accounting rather than direct principal theft, landing in the **High** impact tier (theft/inflation of unclaimed yield).

### Likelihood Explanation
This triggers automatically and deterministically on every accrual-pause/unpause cycle - no attacker action, race condition, or malicious actor is required; it fires the first time `accrue()` (or any function calling it, e.g. `system-borrow`, `system-repay`, liquidation) is invoked after unpausing. Given that pausing accrual is an explicitly built and documented feature (intended for incident response), any use of that feature for more than a trivial duration reproduces the bug with certainty.

### Recommendation
When toggling `pause-states.accrue` off (or, more robustly, when toggling it on), re-anchor `last-update` to `stacks-block-time` so that the paused interval is excluded from the next `time-delta` computation:
```clarity
(define-public (set-pause-states (new-states {...}))
  (begin
    (try! (check-dao-auth))
    ;; if resuming accrual after a pause, reset the clock so paused time is not charged
    (if (and (get accrue (var-get pause-states)) (not (get accrue new-states)))
        (var-set last-update stacks-block-time)
        false)
    (var-set pause-states new-states)
    (ok true)))
```
Alternatively, track `pause-started-at`/`pause-total-duration` and subtract the accumulated paused duration from `time-delta` inside `next-index`/`next-liquidity-index`.

### Proof of Concept
1. At `t0`, vault's `last-update = t0`, `index = I0`.
2. DAO calls the accrue-pause setter, setting `pause-states.accrue = true` at `t1` (`t1 > t0`). No accrual has happened between `t0` and `t1` yet other than what a normal `accrue()` at `t1` would have captured (assume it was captured, so `last-update = t1` at pause time for simplicity).
3. Vault remains paused for a long interval, e.g., 30 days, until `t2 = t1 + 30 days`. During this whole window every call to `accrue()` hits the paused branch in [3](#0-2) , returning `{index: I0, lindex: L0}` and never updating `last-update`.
4. DAO unpauses at `t2`, setting `pause-states.accrue = false`.
5. Any user action right after unpause (e.g., a borrow) calls `accrue()`; since `pause-states.accrue` is now `false`, it hits `next-index`, computing `time-delta = t2 - last-update = t2 - t1 = 30 days`, and applies the full 30-day interest multiplier via `calc-multiplier-delta` in a single block, even though the pause was meant to prevent accrual entirely during that window.
6. Borrower debt and treasury/supplier yield jump instantly to reflect 30 days of interest that should never have accrued, confirming the overpayment/incorrect-accounting root cause identical in shape to the referenced Sherlock M-12 report.
