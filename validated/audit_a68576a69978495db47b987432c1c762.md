### Title
Zero-validator early return in `RewardCalculator::calculate_reward` credits protocol-treasury reward without minting matching supply — ([File: chain/epoch-manager/src/reward_calculator.rs])

### Summary
`RewardCalculator::calculate_reward` inserts the protocol-treasury's epoch reward into its returned rewards map *before* checking whether there are any validators to reward, and if there are none it returns early with that map intact but reports the "actual minted" amount as `Balance::ZERO`. Because `EpochInfo::minted_amount()` (used to adjust total supply) and `EpochInfo::validator_reward()` (used to credit the treasury account's balance) are two independently-consumed outputs of the same call, this creates a structural mismatch analogous to the Stakehouse `Syndicate.updateAccruedETHPerShares` bug: an accounting bucket (`numberOfRegisteredKnots == 0` / `num_validators == 0`) is special-cased with a `return`/`else` branch that does not reconcile a value (EIP-1559 rewards / treasury reward) that was already recorded elsewhere. [1](#0-0) 

### Finding Description
`calculate_reward` computes `epoch_protocol_treasury` and immediately inserts it into the `res` map keyed by `protocol_treasury_account`: [2](#0-1) 

If `num_validators == 0`, the function returns `(res, Balance::ZERO)` — i.e., the map still contains a non-zero treasury reward, but the second return value (`epoch_actual_reward`, later called `minted_amount`) is zero.

Downstream, these two outputs are consumed independently:
- `minted_amount` is stored on the next-next `EpochInfo` and used to adjust total supply: `new_total_supply = prev.total_supply + minted_amount − balance_burnt` [3](#0-2) 
- `validator_reward` (the `res` map, including the treasury entry) is later read via `EpochManager::compute_stake_return_info` and passed into `ValidatorAccountsUpdate.validator_rewards`, which the runtime uses to directly credit the treasury account's balance at the first block of the new epoch: [4](#0-3) 

Because `minted_amount` was `Balance::ZERO` for that epoch while `validator_reward[treasury]` was `epoch_protocol_treasury` (non-zero), the treasury account's balance can increase by `epoch_protocol_treasury` yoctoNEAR while total supply is not increased to match — the same class of bug as the report: the `else`/zero-count branch fails to reconcile a value that a separate code path still applies. In the Stakehouse case this loses ETH; here it instead mints/credits tokens to an account without a corresponding, reconciled supply increase, i.e. a supply-accounting divergence that would show up as a state-root/invariant mismatch on nodes computing total-supply-consistency checks.

### Impact Explanation
If reached, this breaks the fundamental invariant that `total_supply` changes deterministically track credited balances (`Behavior §3` in the economics spec), which is exactly the kind of "supply inflation" / "invalid state transition acceptance" impact this exercise accepts. A treasury balance increase untracked by `minted_amount` is a real (if narrow) accounting bug in the core validator-reward code path shared by the whole network — every node computing this deterministically would derive the same wrong result, so it would not immediately cause a fork by itself, but it does violate the documented supply invariant and represents free/uncounted token creation for the treasury account.

### Likelihood Explanation
This is Low-likelihood/hard-to-trigger in practice. `num_validators` here is `validator_block_chunk_stats.len()`, which is derived from the current epoch's actual validator set after `compute_validators_to_reward_and_kickout` removes only those kicked for `NotEnoughBlocks`/`NotEnoughChunks`/`NotEnoughChunkEndorsements` [5](#0-4) . The epoch-manager's "never kick everyone" safeguard guarantees at least one validator is always exempted from such kickouts [6](#0-5) , so in the normal, non-genesis epoch-manager flow, `validator_block_chunk_stats` (and hence `num_validators`) should never legitimately reach zero. I could not find a concrete, transaction-triggerable path (e.g., via `Stake` actions alone) that drives `num_validators` to 0 through the production `finalize_epoch` pipeline — the `num_validators == 0` branch appears to be defensive/dead code for the mainline flow, exercised only by the direct unit test `test_zero_produced_and_expected` [7](#0-6) . I was not able to fully verify whether some other caller (e.g. genesis bootstrapping, or `chain/epoch-manager/src/genesis.rs`) can pass an empty stats map into `calculate_reward` outside of tests, so genuine unprivileged-transaction reachability remains unconfirmed.

### Recommendation
In `RewardCalculator::calculate_reward`, when `num_validators == 0`, either (a) do not insert the treasury reward into `res` unless it is also reflected in the returned `epoch_actual_reward`/minted amount, or (b) include `epoch_protocol_treasury` in the returned second value so that `minted_amount` and the treasury's `validator_reward` entry always stay consistent, mirroring the recommended fix pattern from the source report (reconcile the "else"/zero-count branch instead of silently short-circuiting it).

### Proof of Concept
Not independently reproducible end-to-end: the unit test `test_zero_produced_and_expected` in `chain/epoch-manager/src/reward_calculator.rs:158-212` directly calls `calculate_reward` with an empty `validator_block_chunk_stats` and `max_inflation_rate = 0`, which masks the treasury/minted mismatch (both are zero in that test). Demonstrating the actual divergence would require calling `calculate_reward` with `max_inflation_rate > 0` and an empty stats map (yielding `res = {treasury: epoch_protocol_treasury}`, `epoch_actual_reward = Balance::ZERO`), then tracing that mismatched pair through `finalize_epoch` → `EpochInfo` → `compute_stake_return_info` → `runtime/runtime/src/lib.rs:1807-1833`. I was unable to confirm, within the scope of this review, a concrete production code path (reachable from a single `Stake` transaction) that populates `finalize_epoch` with a truly empty `validator_block_chunk_stats`, given the "never kick everyone" safeguard; this should be validated further (e.g., with a live Devin session able to run the epoch-manager test harness) before treating this as a confirmed, exploitable issue.

### 3. Total-supply change per block
`new_total_supply = prev.total_supply + minted_amount − balance_burnt` (`core/primitives/src/block.rs:193`). `minted_amount` is `Some` only on the first block of an epoch, taken from the epoch info populated by `calculate_reward` (`chain/chain/src/chain.rs:2519`). `balance_burnt` is the sum of each included chunk's `prev_balance_burnt()` (`block.rs:152`). Thus inflation *adds* to supply once per epoch, and burnt fees *subtract* every block; the difference is net issuance.

Two safety valves cap kickouts:
- **Stake cap**: at most `validator_max_kickout_stake_perc` of total validator stake may be kicked. `compute_exempted_kickout` exempts validators (ordered by online ratio, then stake, then account id — `validator_comparator`, `lib.rs:427`) until the exempt set reaches `100 - validator_max_kickout_stake_perc` of stake (`lib.rs:452`).
