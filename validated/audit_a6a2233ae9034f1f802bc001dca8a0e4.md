This is critical: the documentation itself for `shopify.auth.tokenExchange` demonstrates the exact anti-pattern shown in the H-04 analog — `shop` is taken from `req.query.shop` (attacker-controlled, unauthenticated) as an independent parameter, while `sessionToken` is a separate value, and the library never checks that the `shop` parameter matches the shop encoded in the validated session token's `dest` claim.

### Title
Token Exchange accepts an unverified `shop` parameter that is not checked against the authenticated session token's `dest` claim - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`tokenExchange()` decodes and validates the `sessionToken` JWT but discards the result instead of comparing its `dest` (shop) claim to the separately supplied `shop` parameter. If any caller sources `shop` from an untrusted, independently controllable value (as the library's own documented example does — `shopify.utils.sanitizeShop(req.query.shop, true)`), the library performs the access-token exchange against a merchant domain that was never actually authenticated by the presented session token.

### Finding Description
`tokenExchange()` in [1](#0-0)  does:
```ts
return async ({shop, sessionToken, requestedTokenType, expiring}: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);
    ...
    const cleanShop = sanitizeShop(config)(shop, true)!;
    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`, ...
```
The call to `decodeSessionToken` validates the JWT's signature/expiry/audience, but its return value (the payload, including the `dest` field that identifies the shop the token was actually issued for) is never captured or compared against the caller-supplied `shop` string [2](#0-1) . This is structurally identical to the Gondi `refinanceFromLoanExecutionData` bug: a validation step is performed on one identifier (the session token's embedded shop) while a completely separate, unchecked identifier (`shop`) is used to perform the sensitive action (issuing an OAuth access-token exchange request).

The library's own documentation for this API instructs callers to build `shop` from `req.query.shop` [3](#0-2)  — i.e., directly from an anonymous, attacker-controlled query string parameter, entirely independent of the `sessionToken`'s `dest` claim.

By contrast, the two first-party framework integrations shipped in this monorepo (`shopify-app-remix` and `shopify-app-react-router`) do NOT follow this unsafe pattern for their embedded-admin flow: they derive `shop` from `new URL(payload.dest).hostname` after validating the session token, so `shop` and the token's `dest` are always consistent in that code path [4](#0-3) . `shopify-app-express`'s `performTokenExchange` does the same [5](#0-4) .

### Impact Explanation
Within this repository, I could not find an anonymous/unprivileged HTTP path in the shipped `shopify-app-express`, `shopify-app-remix`, or `shopify-app-react-router` packages that actually supplies a `shop` value independent of the validated session token's `dest` claim to `tokenExchange()` — all first-party call sites derive `shop` from the decoded payload, not from request query parameters. The vulnerable pattern exists only in the low-level `shopify-api` library's public `tokenExchange` function and is actively encouraged by its own documentation example. A developer following that documented example literally (using `req.query.shop` instead of the token's `dest`) would introduce a shop/session-token mismatch, but this requires a downstream integrator to misuse the documented pattern rather than being directly reachable through an anonymous request against the code shipped in this repo's own auth handlers.

### Likelihood Explanation
Low-to-moderate as a directly reachable exploit in this repo's own request-authentication handlers, since the shipped frameworks correctly derive `shop` from the validated payload. However, likelihood is elevated by the fact that the library's own reference documentation models the unsafe pattern (`shop` from `req.query.shop`), making it plausible that third-party integrators building directly on `shopify-api` (rather than `shopify-app-remix`/`shopify-app-express`) will replicate the insecure example.

### Recommendation
In `tokenExchange()`, capture the decoded payload and assert that `new URL(payload.dest).hostname` (after sanitization) matches the `sanitizeShop`-normalized `shop` parameter before proceeding to call the `/admin/oauth/access_token` endpoint; throw `InvalidJwtError` (or a new dedicated error) on mismatch. Additionally, update the `tokenExchange.md` documentation example to derive `shop` from the decoded session token instead of `req.query.shop`, so integrators are not guided toward the unsafe pattern.

### Proof of Concept
1. A developer wires an `/auth` route per the documented example: `shop = shopify.utils.sanitizeShop(req.query.shop, true)`, and `sessionToken` from the `Authorization` header [3](#0-2) .
2. An anonymous caller (or a merchant of shop A) submits `?shop=shop-b.myshopify.com` together with a validly-signed session token whose `dest` is `shop-a.myshopify.com`.
3. `tokenExchange()` validates the token's signature only, ignores the mismatch between `payload.dest` and the caller-supplied `shop`, and issues the token-exchange POST to `https://shop-b.myshopify.com/admin/oauth/access_token` [6](#0-5) .
4. Whether this ultimately succeeds depends on Shopify's own OAuth server enforcing token/shop binding, but the shopify-api library itself performs no such check, violating the defense-in-depth expectation established by the referenced Gondi mitigation ("Added `tokenIdCheck`").

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,

      subject_token: sessionToken,

      {
