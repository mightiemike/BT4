### Title
JWT replay protection (`jti`) is per-process/local, allowing a captured RequestJWT to be replayed against a different Gateway DON node to re-trigger a workflow - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` enforces JWT replay protection via `jwtReplayCache`, an in-memory `map[string]time.Time` guarded by a `sync.RWMutex` that lives entirely inside a single `WorkflowMetadataHandler` process. Chainlink explicitly supports multi-gateway-DON deployments (e.g. `gateway_don_us` / `gateway_don_eu`), so a valid signed `RequestJWT` accepted by one gateway node's cache is not recorded anywhere shared, and can be replayed against another independent gateway node/DON to re-authorize and re-trigger the same workflow execution.

### Finding Description
`Authorize` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` verifies the JWT signature/digest via `utils.VerifyRequestJWT`, then checks `h.jwtCache.isReplay(claims.ID)` and, if not present, calls `h.jwtCache.recordUsage(claims.ID)`. `jwtReplayCache` is constructed per-`WorkflowMetadataHandler` instance in `NewWorkflowMetadataHandler` (`jwtCache: newJWTReplayCache(...)`), and its `cache` field is a plain local Go map with no external/shared backing store (Redis, DB, etc.). Each gateway node process running its own `WorkflowMetadataHandler` therefore has its own independent replay cache.

The repo's own deployment configs (e.g. `core/scripts/cre/environment/configs/workflow-gateway-capabilities-multi-gateway-don.toml`) define multiple independent gateway DON nodesets (`bootstrap-gateway-us` with `gateway_don_id = "gateway_don_us"`, and `gateway-eu` with `gateway_don_id = "gateway_don_eu"`) that front the same underlying capabilities/workflow nodeset. Each gateway node runs its own ingress `httpTriggerHandler`/`WorkflowMetadataHandler` pair which independently calls `Authorize` once per incoming user request (`http_trigger_handler.go` `authorizeRequest` → `workflowMetadataHandler.Authorize`) before fanning the trigger out to the shared workflow capability DON members via `sendWithRetries`/`SendToNode`.

Because `jti` tracking is authoritative only within a single node's local map, an attacker who intercepts one valid signed JWT (in transit, or via a compromised low-trust vantage point) can submit it to a *different* gateway node/DON endpoint that has not seen that `jti` before. That second node's `isReplay` check returns `false`, the signature/digest checks still pass (they don't depend on prior state), and the request is authorized and dispatched to the workflow capability nodes again — resulting in duplicate/unauthorized workflow trigger execution.

### Impact Explanation
This allows replay-triggered re-execution of a workflow using a token that should only be usable once, bypassing the documented replay-protection invariant ("Please generate a new one with new id (jti)"). Depending on the workflow's side effects (on-chain transactions, external calls, state mutations), this can cause duplicate unauthorized workflow executions/transactions — matching a "unauthorized transaction or workflow execution" bounty impact category. It does not require key compromise, only interception of an already-issued token plus knowledge that multiple independent gateway ingress points exist.

### Likelihood Explanation
Feasibility depends on: (1) a multi-gateway-DON deployment (which is an explicitly supported and documented topology in this repo), (2) the attacker being able to capture one valid signed token before/as it's used, and (3) submitting it to a sibling gateway node before that node's local cache happens to already contain the `jti` (which it never will, since caches aren't shared) and before token expiry (`exp`). Given documented multi-region gateway DON configs and no cross-node synchronization of `jwtCache`, this is repeatable for the life of the token (bounded by `maxJWTExpiryDuration`), not a one-off race condition.

### Recommendation
Back the JWT replay cache with a cluster-wide/shared store (e.g., a shared database, Redis, or an authenticated broadcast of used `jti`s among DON gateway members) so `isReplay`/`recordUsage` are authoritative across all gateway nodes serving the same workflow/DON, not just within one process's local map.

### Proof of Concept
Integration test plan:
1. Construct two independent `WorkflowMetadataHandler` instances (`handlerA`, `handlerB`) each via `NewWorkflowMetadataHandler`, simulating two gateway nodes in a multi-gateway-DON deployment, both configured with the same authorized signer/workflow (mirroring `registerWorkflow` helper used in `workflow_metadata_handler_test.go`).
2. Create one signed `RequestJWT` via `utils.CreateRequestJWT` + `token.SignedString(privateKey)` for a given `jsonrpc.Request`.
3. Call `handlerA.Authorize(workflowID, tokenString, req)` — assert `err == nil` and a valid key is returned (first use accepted, mirroring existing `TestWorkflowMetadataHandler_Authorize/JWT replay protection` for a single instance).
4. Call `handlerB.Authorize(workflowID, tokenString, req)` with the *same* token — currently this succeeds (`err == nil`) because `handlerB.jwtCache` never saw this `jti`.
5. Assert this second call should fail with "JWT token has already been used" (expected behavior for a cluster-wide replay guard) — demonstrating that, without a shared jti store, the second independent instance incorrectly accepts the replayed token. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func newJWTReplayCache(cleanupPeriod time.Duration) *jwtReplayCache {
	return &jwtReplayCache{
		cache:         make(map[string]time.Time),
		cleanupPeriod: cleanupPeriod,
	}
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
