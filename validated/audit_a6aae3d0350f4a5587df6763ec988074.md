### Title
Poison-microblock evidence is not validated for genuine equivocation at the consensus (state-transition) layer, allowing reward misdirection - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
The consensus-critical handler for `TransactionPayload::PoisonMicroblock`, `handle_poison_microblock`, only checks that the two submitted microblock headers were signed by the same public key. It never checks that the two headers actually conflict (same `sequence`/`prev_block`/`version` but different content/hash) — the only place that check exists (`PoisonMicroblocksDoNotConflict`) lives in the mempool admission path, not in block/state-transition processing.

### Finding Description
`handle_poison_microblock` in `stackslib/src/chainstate/stacks/db/transactions.rs` calls `check_microblock_header_signer(mblock_header_1, mblock_header_2)` [1](#0-0)  which only verifies `pkh1 == pkh2` (the two headers recover to the same signer public key) [2](#0-1) . It never checks that `mblock_header_1.sequence == mblock_header_2.sequence`, that `prev_block`/`version` match, or that the two headers actually differ — i.e. that this is genuine equivocation evidence rather than a duplicate of the same header (or two headers describing unrelated points in the stream).

That structural equality check does exist elsewhere — but only in the mempool/RPC admission path (`MemPoolRejection::PoisonMicroblocksDoNotConflict`) [3](#0-2) , which is a client-side gatekeeping function used before a tx is accepted into a mempool, not a consensus rule enforced during actual transaction/block processing. Any node building a block directly (or a peer relaying a raw transaction bypassing mempool re-validation) can include a `PoisonMicroblock` transaction whose two headers are literally identical (or otherwise non-conflicting) as long as they recover to the same public key — trivially true for `header_1 == header_2`, or for any two distinct-but-non-conflicting headers honestly produced by the same miner across unrelated tenures (same microblock signing key can be reused legitimately over its `MINER_REWARD_MATURITY` validity window).

`handle_poison_microblock` then looks up whether that public key hash has been seen (`get_microblock_pubkey_hash_height`) and, if within the maturity window, unconditionally records the sender as the punishing "poison reporter" for that miner's coinbase at that height [4](#0-3) . This directly determines reward routing: `find_mature_miner_rewards` reads the recorded poison report and redirects the miner's/participants' coinbase reward to the "reporter" instead of the legitimate miner [5](#0-4) [6](#0-5) .

This mirrors the reported bug class exactly: "evidence submitted... is not checked at all," letting an attacker present technically-valid-but-non-conflicting material (a signature verifying against the correct key) to trigger a slashing/reward-redirection path meant only for genuine fork proofs.

### Impact Explanation
This causes a reward mis-payment: an honest miner who never equivocated has their coinbase (and their user-burn-supporters' shares) diverted to an attacker's address, and the remainder is destroyed (`punished = true` path zeroes out user rewards) [7](#0-6) . Because this is evaluated deterministically by every node from the same transaction bytes, it does not cause a chain split by itself, but it is a concrete, minority-triggerable reward-diversion/loss bounded to a single tenure's coinbase — matching the "reward paid... to the wrong party" / "poison or reward mis-payment bounded to fees" category (High).

### Likelihood Explanation
Exploitation requires only that an attacker construct a `PoisonMicroblock` transaction with two headers that both recover to a real, previously-seen microblock signing key, and get it included in a block — e.g. by mining it themselves, or by transaction relay/miner acceptance paths that don't independently re-run the mempool's `PoisonMicroblocksDoNotConflict` check before block construction. No majority collusion, no admin key, and no privileged position is needed; a single unprivileged actor who observes any historical microblock header (public data) can forge the “evidence” trivially by reusing that same header twice.

### Recommendation
Move the structural-conflict check (`sequence`, `prev_block`, `version` equality and header inequality) out of the mempool-only `MemPoolRejection` path and into `handle_poison_microblock`/`check_microblock_header_signer` itself, so it is enforced as part of the consensus state transition regardless of how the transaction reached the block, not merely at mempool admission time.

### Proof of Concept
1. Identify any microblock public key hash `pubkh` that has been used within the last `MINER_REWARD_MATURITY` blocks (this is public chain data, retrievable via `get_microblock_pubkey_hash_height`).
2. Take any single legitimately-signed `StacksMicroblockHeader` from that miner (`mblock_header_1`), and pass a byte-identical (or otherwise non-conflicting, e.g. different sequence entirely) copy as `mblock_header_2`.
3. Build a `TransactionPayload::PoisonMicroblock(mblock_header_1, mblock_header_2)` transaction and mine it directly into a block (bypassing mempool `static_check_transaction`/`PoisonMicroblocksDoNotConflict`), or submit it to a relay path that doesn't re-run that specific mempool gate before inclusion.
4. `handle_poison_microblock` passes because `check_microblock_header_signer` only requires `pkh1 == pkh2`, which trivially holds; it registers the attacker as the poison-reporter for `pubkh`'s coinbase.
5. At maturity, `find_mature_miner_rewards`/`calculate_miner_reward` redirect the legitimate miner's coinbase reward (a commission fraction) to the attacker and burn the remainder, even though no actual microblock fork ever occurred.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
