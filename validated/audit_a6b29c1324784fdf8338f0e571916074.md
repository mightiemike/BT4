### Title
Pausing vault interest accrual (`accrue: true`) causes retroactive interest to be applied for the entire paused duration when accrual resumes, because `last-update` is never advanced while paused - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent per-asset vaults)

### Summary
Each vault's `accrue` function is designed to "pass through without reverting" when accrual is administratively paused, per the comment `;; PAUSED: Pass-through without reverting`. In this branch it returns the current `index`/`lindex` unchanged and, critically, does **not** update the `last-update` timestamp. `last-update` is the cached reference point from which `next-index`/`next-liquidity-index` compute `time-delta = stacks-block-time - (var-get last-update)`. Because the clock (`stacks-block-time`) keeps moving while `last-update` is frozen, the very next non-paused `accrue` call computes a `time-delta` spanning the *entire* paused interval plus any time since unpausing, and applies interest for that whole span in one shot as if the vault had been actively accruing the whole time.

### Finding Description
`accrue` in each vault (e.g. `mainnet/contracts/vault/v0-vault-usdc.clar:833-861`, and identically in `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, and their `local-testing` counterparts) reads pause state and, when `(get accrue states)` is true, short-circuits:

`last-update` is the only value that "invalidates" the cached `index`/`lindex` reading — it marks the point up to which interest has already been applied. When accrual is paused, `last-update` is frozen at its pre-pause value while `stacks-block-time` (the source it was tracking) continues to advance for the whole pause duration. The pause branch never re-anchors `last-update` to the current time, so the staleness is silently accumulating during every block the vault stays paused.

When accrual is later un-paused (a DAO/governance action, not user-controlled, but the exploit window itself does not require any privileged action — it is purely a consequence of resuming a state the DAO already set), the next call to `accrue` (triggered by any user calling `borrow`, `repay`, `system-borrow`, `deposit`, etc., or the market's `accrue-and-cache`) computes `time-delta = stacks-block-time - last-update`, which spans the *entire* pause window. The vault then applies compounding interest for that whole span in a single step, as though borrowers had been continuously accruing debt/interest throughout the pause — even though the explicit intent of pausing `accrue` is to freeze interest.

This is structurally the same "stale reference variable, source moves, next use replays the drift all at once" pattern as the Autonomint `lastEthprice` bug: a value (`last-update`) that is supposed to be re-anchored whenever its source (accrual state / block time) changes is instead left stale across a state transition, and the very next computation that consumes it absorbs the entire accumulated delta in one shot, distorting the derived value (`index`/`lindex`, hence debt and collateral valuations feeding health checks and liquidations) far beyond what should be possible in the intervening period.

### Impact Explanation
Because `index`/`lindex` directly determine actual debt (`mul-div-down scaled-principal idx INDEX-PRECISION`) and zToken collateral value (via `resolve-ztoken`'s cached `lindex`), a large retroactive interest jump immediately after an accrual pause:
- Can push previously healthy borrower positions into instant insolvency/liquidation the moment accrual resumes, even though no real time-weighted risk accrued during the freeze (since the freeze was meant to *stop* interest, not defer and compound it).
- Can inflate `total-borrowed`/debt and treasury `treasury-lp` minting (`reserve-inc`, `debt-delta`) computed from the same jump, understating/overstating protocol reserves and effectively causing a temporary mis-accounting of protocol solvency and misallocation of yield ("freezing/mis-crediting of unclaimed yield" for depositors and unexpected debt inflation for borrowers) the moment the pause is lifted.

This lands in the **High** impact bucket: temporary freezing/mis-crediting of funds (unclaimed yield) and abrupt, unwarranted change in borrower solvency status directly caused by the stale `last-update` cache not being invalidated across the pause/unpause transition.

### Likelihood Explanation
Pausing `accrue` is an explicit governance lever exposed via `pause-states`, and is a normal operational tool (e.g., pausing during an incident or an oracle outage). Any period during which accrual is paused — however short or long — followed by unpausing and a single subsequent transaction that triggers `accrue` (any borrow/repay/deposit/redeem call, or `market.clar`'s `accrue-and-cache`) will trigger the retroactive interest jump. No attacker action beyond ordinary usage (calling `borrow`/`repay` right after unpause) is needed to realize the impact, making the likelihood high whenever the pause switch is toggled off, which is a routine, expected DAO operation, not a compromise.

### Recommendation
When entering or exiting the `accrue: true` (paused) state, re-anchor `last-update` to `stacks-block-time` so that the frozen period contributes zero elapsed time to the next `next-index`/`next-liquidity-index` computation. Concretely:
- On transition into pause, set `last-update` to the current `stacks-block-time`.
- On transition out of pause (or inside the paused branch of `accrue` itself, every time it executes while paused), also set `last-update` to `stacks-block-time`, so `time-delta` measured after unpausing reflects only genuinely elapsed accruing time, not the paused interval.

### Proof of Concept
1. Vault `v0-vault-usdc` is operating normally; `last-update = T0`, `index = I0`.
2. DAO calls the pause-state setter to set `accrue: true` at time `T1` (pause begins). `last-update` remains `T0` (not updated).
3. Time passes; many blocks elapse while paused (`stacks-block-time` moves from `T1` to `T2`, a long interval, e.g. days).
4. DAO unpauses accrual (`accrue: false`) at `T2`. `last-update` is still `T0`.
5. Any user calls `borrow`/`repay`/`deposit` triggering `accrue()`: since `(get accrue states)` is now false, the "NOT PAUSED" branch runs and computes `time-delta = stacks-block-time (≈T2+ε) - last-update (T0)`, i.e., the delta spans the pre-pause active period PLUS the entire paused duration.
6. `next-index`/`next-liquidity-index` apply interest-rate compounding over this inflated `time-delta`, producing a large one-time jump in `index`/`lindex` that did not reflect real accruing time during the pause window.
7. This jump immediately changes computed debt (`mul-div-down scaled-principal idx INDEX-PRECISION`) and zToken collateral valuation for every position in the market that references this vault, potentially flipping healthy positions into liquidatable ones or vice versa, purely as an artifact of the stale `last-update` cache.
