### Title
Missing TLS Certificate Validation in External Blocking-Check Client Enables MITM Bypass/Forgery of Transaction Blocking Decisions - (File: crates/starknet_transaction_prover/src/blocking_check.rs)

### Summary
The `BlockingCheckClient` used by the Starknet transaction prover to decide whether a submitted transaction should be proven or blocked is built with `danger_accept_invalid_certs(true)`, which disables TLS certificate validation entirely for the external `starknet_checkTransaction` JSON-RPC call.

### Finding Description
`BlockingCheckClient::new` explicitly configures the `reqwest::Client` to accept any TLS certificate: [1](#0-0) 

This client is used on the `prove_transaction` path — the same code path exercised when a caller submits a transaction for proving (`VirtualSnosProver::prove_transaction`), which optionally consults the external blocking-check service before proving/allowing the transaction to proceed: [2](#0-1) 

The actual decision logic in `prove_with_blocking_check` trusts the response from this unauthenticated (certificate-wise) TLS channel to decide `Allowed`/`Blocked`/fail-open/fail-close: [3](#0-2) 

Because `danger_accept_invalid_certs(true)` disables hostname and certificate-chain verification, any network-path attacker able to intercept traffic between the prover node and the configured blocking-check URL (e.g. via DNS spoofing, ARP poisoning, a compromised intermediate proxy, or a rogue endpoint impersonating the configured host) can present an arbitrary self-signed/forged certificate and impersonate the blocking-check service. This directly matches the reported bug class (CWE-295, CVE-2019-1010206): TLS is established without validating that the remote party is who it claims to be, enabling certificate spoofing.

### Impact Explanation
An attacker capable of intercepting the TLS connection to the blocking-check endpoint can:
- Force every `starknet_checkTransaction` call to return a success/`Allowed` response, unconditionally bypassing an operator's transaction-blocking security control and causing transactions that should have been blocked (e.g. known-malicious or sanctioned transactions) to be proven and accepted.
- Alternatively, force `Blocked` or malformed responses for legitimate transactions, causing denial of proving/inclusion for honest transactions (fail-close policy), which impedes the network's ability to confirm otherwise-valid transactions if `fail_open` is disabled.

This subverts the integrity guarantee the blocking-check mechanism is meant to provide, which is reachable per single submitted transaction through the normal proving flow.

### Likelihood Explanation
Exploitation requires an attacker positioned on the network path between the prover and the configured blocking-check service (matching the CVSS `AC:H` vector of the original advisory) — e.g., DNS hijacking, a compromised load balancer/proxy in front of the check service, or interception on an untrusted network segment. No privileged operator or protocol-level compromise is required beyond network position; the vulnerability is a straightforward missing-validation configuration rather than a logic bug requiring complex preconditions.

### Recommendation
Remove `danger_accept_invalid_certs(true)` from `BlockingCheckClient::new` and use the platform's default certificate validation (or pin a specific CA/certificate for the internal blocking-check service). If self-signed certificates are required for internal deployments, explicitly load and trust only the specific expected CA certificate via `reqwest::Client::builder().add_root_certificate(...)` rather than disabling validation globally.

### Proof of Concept
1. Deploy the transaction prover with a `BlockingCheckClient` pointed at `https://blocking-check.internal`.
2. As a network-positioned attacker, intercept DNS or routing for `blocking-check.internal` and stand up a rogue HTTPS server presenting a self-signed certificate for that hostname.
3. Submit any transaction for proving (`prove_transaction`); the prover's TLS client accepts the rogue server's forged certificate without error (due to `danger_accept_invalid_certs(true)`), and the attacker's server returns `{"jsonrpc":"2.0","result":{},"id":1}`, which `prove_with_blocking_check` interprets as `Allowed`, per the logic at [4](#0-3) , causing the transaction to be proven despite the legitimate blocking-check service (had it been actually contacted) potentially returning `Blocked`.

    async fn prove_with_blocking_check(
        &self,
        client: &BlockingCheckClient,
        block_id: BlockId,
        transaction: RpcTransaction,
        invoke_tx: InvokeTransaction,
    ) -> Result<ProveTransactionResult, VirtualSnosProverError> {
        // Kick off proving in parallel with the check. Clone is cheap: inner fields are
        // Arcs or small configs.
        let prover = self.clone();
        let prove_handle =
            tokio::spawn(async move { prover.run_and_prove(block_id, vec![invoke_tx]).await });

        let timeout_duration = std::time::Duration::from_millis(client.timeout_millis);
        let check_outcome =
            tokio::time::timeout(timeout_duration, client.check_transaction(block_id, transaction))
                .await;

        // A transaction allowed via the fail-open policy (inconclusive check or
        // timeout) carries no additional_data.
        let (allow, additional_data) = match check_outcome {
            Ok(BlockingCheckResult::Blocked) => {
                info!("Transaction blocked by external check");
                (false, None)
            }
            Ok(BlockingCheckResult::Allowed(additional_data)) => {
                info!("Transaction allowed by external check");
                (true, additional_data)
            }
            Ok(BlockingCheckResult::Inconclusive) => {
                info!(fail_open = client.fail_open, "Blocking check inconclusive");
                (client.fail_open, None)
            }
            Err(_) => {
                info!(fail_open = client.fail_open, "Blocking check timed out");
                (client.fail_open, None)
            }
        };
