The reported LUSDToken issue is about a missing `DOMAIN_SEPARATOR()` binding EIP-2612 signatures to chain/contract context, allowing signature replay across contexts. There is a structurally analogous issue in this repo's webhook HMAC verification: the signature is computed only over the raw request body and never binds to the shop/domain context, so a validly-signed payload from one shop can be replayed with a forged domain header to impersonate a different shop.

### Title
Webhook HMAC does not bind to shop domain, enabling cross-tenant webhook forgery - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`validateHmacFromRequestFactory` computes the webhook HMAC solely over `rawBody` using the app's shared `apiSecretKey`, and never incorporates the `X-Shopify-Shop-Domain` (or topic/webhook-id) header into the signed material. `validate.ts` only checks that these headers are *present*, not that they are cryptographically bound to the HMAC. Because the app secret is shared across every shop that installs the app, an attacker who legitimately receives one genuine webhook for their own store (a valid `rawBody` + `X-Shopify-Hmac-Sha256` pair) can resend that exact body/HMAC pair directly to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. Validation succeeds because the domain was never part of the signed data — this is the same class of defect as a missing domain separator: the signature fails to scope itself to the intended "domain" (in this case, the shop), enabling replay across trust boundaries.

### Finding Description
- `validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` (lines 168-201) validates HMAC via `validateHmacString(config, rawBody, hmac, HashFormat.Base64)`, which only hashes `rawBody` with `config.apiSecretKey`: [1](#0-0) 
- `validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` runs this body-only HMAC check first, then separately calls `checkWebhookHeaders`, which merely checks the `domain`/`topic`/`webhookId` headers are non-empty — not that they match anything the HMAC covers: [2](#0-1) 
- The resulting `check.domain` (fully attacker-controllable once a valid body/HMAC pair is obtained) is passed straight into `ensureValidOfflineSession(params, check.domain)` in the webhook authenticate handlers, which loads/creates the offline session and builds an authenticated Admin API client scoped to that (attacker-chosen) shop: [3](#0-2) 
- `ensureValidOfflineSession` simply loads or creates an offline session for whatever `shop` string it is given, with no verification that the HMAC actually originated for that shop: [4](#0-3) 

### Impact Explanation
Since the API secret key is shared across all installs of a given app, any merchant who has installed the app can obtain a legitimately-signed `(rawBody, hmac)` pair for their own store (e.g., by triggering any registered webhook topic on their own shop and capturing the raw POST). That pair can then be replayed directly against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim shop the attacker does not control. The request passes HMAC validation and header-presence checks, causing the app to run its webhook handler logic (e.g., cleanup, data redaction, session teardown, business logic tied to a topic) against the victim shop's session/admin context — a cross-tenant forged-webhook condition. This can lead to unauthorized state changes or a denial-of-service against another merchant's app installation, entirely from a single, unprivileged merchant account.

### Likelihood Explanation
Reachable by any single merchant with a legitimate but low-privilege relationship to the app (they only need one real webhook delivery from their own shop, which is standard and automatic). No secret leakage, MITM, or privileged access is required — the webhook endpoint is a public HTTP handler, and the domain header is attacker-controlled in the forged, direct HTTP request. The `X-Shopify-Shop-Domain` header is not otherwise authenticated anywhere in the validated path.

### Recommendation
Bind the shop/domain context into the signed material verified for webhook authenticity — e.g., verify the domain header against Shopify's registered webhook delivery source, or require an out-of-band correlation between the HMAC and the domain (such as re-deriving/verifying against a per-shop expected value, or rejecting requests whose `domain` header doesn't match a shop associated with a currently pending/expected webhook), rather than trusting the `X-Shopify-Shop-Domain` header purely on the basis of a body-only HMAC that is valid across all tenants of the app.

### Proof of Concept
1. Install the app on Shop A; trigger any topic (e.g., `products/create`) to receive a genuine webhook POST with a valid `rawBody` and `X-Shopify-Hmac-Sha256` header (both derived only from `rawBody` + shared `apiSecretKey`, per `validateHmacString`).
2. Replay that exact `rawBody` and `X-Shopify-Hmac-Sha256` value directly to the app's `/webhooks` endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and keep/adjust `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as needed to pass presence checks).
3. `validateHmacFromRequestFactory` validates successfully because domain is not part of the signed content; `checkWebhooksHeaders` only checks presence, so `validate()` returns `valid: true, domain: 'victim-shop.myshopify.com'`.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading/creating a session and admin client scoped to the victim shop, and dispatches the (attacker-supplied) payload to the app's topic handler under the victim shop's identity.

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
