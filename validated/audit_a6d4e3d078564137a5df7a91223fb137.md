### Title
Unbounded per-cycle loop in reward computation can exhaust energy / stall block processing - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.withdrawReward()`/`queryReward()` and their TVM counterpart `VoteRewardUtil.withdrawReward()`/`queryReward()` compute rewards by calling `computeReward(beginCycle, endCycle, accountCapsule)`, which in turn falls back to `getOldReward(begin, end, votes)` when the account's un-withdrawn cycles predate the VI (per-cycle reward index) optimization. This fallback loops **once per governance cycle** between `beginCycle` and `newRewardAlgorithmEffectiveCycle`, and for each cycle iterates the account's full vote list, doing two store reads per witness (`getReward`, `getWitnessVote`). [1](#0-0) 

### Finding Description
`MortgageService.withdrawReward(address)` is called on every ordinary user path that touches an account's frozen/voted balance — `UnfreezeBalanceActuator.execute` and `WithdrawBalanceActuator.execute` for legacy accounts, and `VoteRewardUtil.withdrawReward` from the TVM `withdrawReward` native contract used by smart-contract-based freezing/voting. [2](#0-1) [3](#0-2) 

Both `MortgageService.computeReward` and `VoteRewardUtil.computeReward` split the cycle range at `newRewardAlgorithmEffectiveCycle`: cycles after that boundary use an O(1) VI-delta lookup, but cycles before it fall back to the legacy path, `getOldReward`, which contains an explicit per-cycle loop:
```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
}
``` [1](#0-0) 

Unlike the marginswap report where `lastUpdatedDay` was simply never initialized (defaulting to 0 and forcing the loop to iterate every day since epoch), here `beginCycle` legitimately defaults to `0` when an address has never previously interacted with the delegation/vote system, as seen in `DelegationStore.getBeginCycle`: [4](#0-3) 

For any account that voted long ago (e.g. at/near genesis or before `allowChangeDelegation`/the VI algorithm was activated) and never calls `withdrawReward`, `beginCycle` stays at (or near) `0`/its first-vote cycle indefinitely — the state is only advanced when `withdrawReward` executes. When such an account finally triggers withdrawal (unfreeze, vote-clear, or explicit `WithdrawBalanceContract`), `computeReward` must walk every cycle from `beginCycle` up to `newRewardAlgorithmEffectiveCycle`, doing two RocksDB reads per witness voted for (bounded by `MAX_VOTE_NUMBER`) for every single cycle in that range. On a long-running mainnet with cycles occurring roughly every 6 hours since genesis, this range can span tens of thousands of cycles, so the total number of store reads is `O((endCycle-beginCycle) * MAX_VOTE_NUMBER * 2)`, which is not bounded by the size of the request or the caller's resources in the same way the rest of TVM/native-contract energy accounting assumes.

The intended mitigation for this — `rewardViCalService` precomputing VI values so `allowOldRewardOpt()` short-circuits to O(1) — only helps once the background computation `isDone()`; if that flag is not enabled network-wide, or for chains/testnets where `allowOldRewardOpt` was never toggled on, the raw per-cycle loop executes on every relevant transaction. [5](#0-4) 

### Impact Explanation
An account (a normal, unprivileged user) that has an old, un-updated `beginCycle` and calls `UnfreezeBalanceContract`, `WithdrawBalanceContract`, or the TVM `withdrawReward`/`queryReward` native contracts can force the node to perform a very large number of sequential DB reads inside actuator execution / native-contract execution. Because `WithdrawBalanceActuator`/`UnfreezeBalanceActuator` execution happens in the actuator pipeline (not fully energy-metered like TVM opcodes) while block processing is time-bounded, this can:
- cause the transaction to run out of energy/exceed CPU-time budget when invoked via the TVM path (`WithdrawRewardProcessor`/`VoteRewardUtil`), making legitimate reward withdrawal impossible for the affected account (denial of service against that specific account, analogous to the reported bug), and
- slow down validation of blocks containing such transactions across all full nodes replaying the chain, which is a broader availability concern if `allowOldRewardOpt` is not active.

### Likelihood Explanation
Likelihood is moderate: it requires an account with a stale `beginCycle` spanning many un-withdrawn cycles and depends on whether `allowOldRewardOpt` has been activated on the target network (mainnet has activated most reward-related proposals historically, which would mitigate this in practice). On networks/private chains where this proposal is not yet enabled, or for accounts whose `beginCycle` predates the VI cut-over by a large margin, the condition is trivially reachable by simply not calling withdraw for a long time and then submitting an ordinary transaction.

### Recommendation
- Ensure `getOldReward`'s legacy branch cannot be reached with an unbounded cycle range independent of `allowOldRewardOpt`; either always precompute/cap the VI-less cycles or hard-limit the number of cycles processed per call (forcing multi-step incremental withdrawal instead of a single unbounded loop), similar to periodically checkpointing `beginCycle` even without an explicit withdrawal.
- Meter/charge resources for actuator-side store iteration proportional to the cycle range walked, or reject/require chunked withdrawal when the pending range exceeds a safe bound.
- Confirm `allowOldRewardOpt` is enabled by default (or made mandatory) rather than conditionally gated, to guarantee the O(1) VI path is always used.

### Proof of Concept
Not independently reproduced in this analysis (no test harness run). Conceptually: deploy/seed an account that votes for the maximum number of witnesses (`MAX_VOTE_NUMBER`) at an early cycle, disable/never-enable `allowOldRewardOpt`, advance `currentCycleNumber` by tens of thousands of cycles without the account withdrawing, then call `withdrawReward` (via `WithdrawBalanceContract`, `UnfreezeBalanceContract`, or the TVM `withdrawReward` native contract) — this will drive `computeReward` into the `getOldReward` per-cycle loop across the entire stale range, reading two store entries per witness per cycle.   private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
