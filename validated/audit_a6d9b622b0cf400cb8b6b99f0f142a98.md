The `ParticipateAssetIssueActuator` is the strongest analog to the reported Solidity `mint()` overpayment issue.

### Title
Overpayment not returned when buyer's TRX amount doesn't evenly convert to whole token units in `ParticipateAssetIssueActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
In `ParticipateAssetIssueActuator.execute()`, the buyer's full TRX `cost` (`participateAssetIssueContract.getAmount()`) is deducted from the buyer's balance and unconditionally credited in full to the issuer (`toAccount`), while the number of TRC10 tokens returned to the buyer is computed using integer floor division (`exchangeAmount = floorDiv(cost * num, trxNum)`). When `cost * num` is not an exact multiple of `trxNum`, the fractional remainder of TRX paid by the buyer yields no additional tokens, yet that TRX is still fully transferred to the issuer and never refunded to the buyer — directly analogous to the reported `mint()` bug where overpayment is not returned.

### Finding Description
`execute()` computes: [1](#0-0) 
The `cost` (buyer-specified TRX amount) is subtracted from the owner's balance in full, but `exchangeAmount` — the number of tokens the buyer actually receives — is `floorDiv(cost * num, trxNum)`, truncating any remainder. The full `cost`, including the truncated fraction, is then credited to `toAccount` (the issuer): [2](#0-1) 
There is no logic anywhere in `execute()` or `validate()` that computes the "exact" TRX cost for the truncated token amount and refunds the difference to the buyer; `validate()` only checks `exchangeAmount <= 0` to reject entirely-non-convertible amounts, not partial remainders: [3](#0-2) 
The existing test suite explicitly documents and accepts this truncation behavior without any refund, confirming the root cause is by design and unaddressed: [4](#0-3) 

### Impact Explanation
Any anonymous account that broadcasts a `ParticipateAssetIssueContract` transaction with an `amount` that is not an exact multiple of `trxNum/num` for the target asset systematically overpays TRX relative to the tokens received, and the excess TRX is transferred to the asset issuer instead of being returned to the buyer. Because `trxNum` and `num` are attacker/issuer-controlled fields set at asset-issuance time (via `AssetIssueActuator`), an issuer can create assets with ratios engineered to maximize rounding loss per participation transaction, and repeated/automated buys (e.g., from bots or dApps that don't account for this) result in continuous, silent fund loss for buyers with no on-chain refund path.

### Likelihood Explanation
This is trivially reachable by any account via a standard `ParticipateAssetIssueContract` broadcast transaction — no privileged role or special conditions are required beyond choosing (or being given by a dApp) an `amount` that doesn't divide evenly, which is the common case for most `trxNum`/`num` ratios and most user-chosen amounts.

### Recommendation
Modify `ParticipateAssetIssueActuator.execute()` to compute the exact TRX cost corresponding to the floor-divided `exchangeAmount` (i.e., `exactCost = ceil(exchangeAmount * trxNum / num)` or equivalently only deduct/transfer the TRX portion that maps exactly to whole tokens) and refund the remainder back to the buyer's balance instead of transferring the full requested `cost` to the issuer.

### Proof of Concept
Using the existing test asset configuration (`TRX_NUM = 2`, `NUM = 2147483647`), the test `sameTokenNameCloseExchangeDevisibleTest` sends `999` sun as `cost`: [5](#0-4) 
`exchangeAmount = floorDiv(999 * 2147483647, 2) = floorDiv(2145338163333, wait` — concretely, `(999L * NUM) / TRX_NUM` truncates the fractional sun's worth of tokens, yet the full 999 sun is deducted from the buyer and added to `toAccount.balance` per the `execute()` logic at lines 66-69 and 82-84, with no path returning the truncated remainder to the buyer.
