I found a strong analog to the "declared cap not enforced" bug pattern: the `max_receipt_size` cap is declared and enforced at receipt creation time (`validate_receipt` with `NewReceipt` mode), but the code explicitly documents and works around a known gap where a receipt can be mutated *after* passing that check (e.g., via `output_data_receivers` being appended, or a large returned value being wrapped into a `Data` receipt) so the final on-the-wire/on-trie receipt exceeds `max_receipt_size` — this is a single-transaction/contract-reachable path (issue #12606), unlike the validator-only or network-layer bugs excluded by the rules.

### Title
`max_receipt_size` cap can be silently violated after validation via promise `output_data_receivers`/return-value mutation - (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/lib.rs`, `runtime/runtime/src/congestion_control.rs`)

### Summary
`LimitConfig::max_receipt_size` is the declared hard cap meant to bound every receipt so the `ChunkStateWitness` stays within its ~21 MiB budget [1](#0-0) . It is enforced once, at receipt-creation time, in `validate_receipt` under `ValidateReceiptMode::NewReceipt` [2](#0-1) , called right after each action executes and produces new receipts [3](#0-2) . However, a receipt's `output_data_receivers` (and its wrapped return value, for `Data` receipts) can be appended or resolved *after* that validation point in the promise DAG's execution pipeline, growing the receipt beyond `max_receipt_size` without ever being re-checked.

### Finding Description
The cap is only checked once, immediately when a new receipt object is created (`ValidateReceiptMode::NewReceipt`) [4](#0-3) . `ReceiptManager::create_action_receipt` can subsequently push additional `DataReceiver` entries onto an already-created receipt's `output_data_receivers` [5](#0-4) , and output data / return values can later be wrapped into `Data` receipts [6](#0-5) . Neither of these later mutations re-invokes `validate_receipt`, so the resulting borsh-serialized receipt can exceed `max_receipt_size` while the cap's own setter/config still claims the value is bounded. The runtime is aware of this: `try_forward` in `congestion_control.rs` explicitly clamps oversized receipts to `max_receipt_size` for its own accounting "to avoid receipts getting stuck," citing the unresolved bug [7](#0-6) , and `ValidateReceiptMode::ExistingReceipt` is documented as deliberately more lenient specifically to tolerate these already-oversized receipts [8](#0-7) . This is directly analogous to the `OmoVault` report: a cap (`supplyCap` / `max_receipt_size`) exists and has enforcement code, but a specific code path (post-creation mutation) bypasses it entirely, and the bypass is reachable from an ordinary, unprivileged contract call (a promise DAG built via `promise_create`/`promise_return`/`promise_batch_action_function_call`), not from a validator or network-layer actor.

### Impact Explanation
An oversized receipt bloats the `ChunkStateWitness` beyond the size budget the limits were designed to enforce (~21 MiB target) [9](#0-8) ; the outgoing-forwarding size accounting is also then falsified because `try_forward` pretends the receipt is only `max_receipt_size` bytes when decrementing the per-shard `OutgoingLimit.size` budget [10](#0-9) , meaning a shard can send more actual bytes than its granted bandwidth allowance believes it consumed. This degrades state-witness size guarantees relied upon for chunk validation and can inflate memory/bandwidth usage beyond configured protocol bounds, though it is already a known, tracked, and mitigated issue rather than an unbounded value-movement or double-spend bug.

### Likelihood Explanation
This is reachable by any account submitting a single transaction that deploys/calls a contract building a promise DAG (`promise_create` → `promise_return`, or a return-value large enough to become an oversized `Data` receipt) — no validator, network, or privileged role is required. The nearcore test suite itself reproduces this deterministically for both the `output_data_receivers` mutation and the large value-return paths [11](#0-10) [12](#0-11) , confirming high likelihood of triggering given a straightforward, permissionless contract interaction.

### Recommendation
Re-validate the final, fully-mutated receipt (after `output_data_receivers` are attached and any return-value `Data` receipt is constructed) against `max_receipt_size` before it is queued/forwarded, rather than only at initial creation; reject or split receipts that would exceed the limit at that later point, and remove the compensating clamp in `try_forward` once the root cause is fixed, per the tracked issue referenced in the code (https://github.com/near/nearcore/issues/12606).

### Proof of Concept
The existing regression tests demonstrate the exact path: `test_max_receipt_size_promise_return` builds a promise DAG `A -then-> B` where a spawned promise `C`'s `output_data_receivers` are populated after `C`'s receipt was already validated at exactly `max_receipt_size`, pushing it over the limit [13](#0-12) ; `test_max_receipt_size_value_return` shows the same effect via a large returned value wrapped into an oversized `Data` receipt [14](#0-13) . Both tests assert the oversized receipt is actually observed on-chain via `assert_oversized_receipt_occurred`, confirming the cap enforcement gap is live and exploitable from ordinary transactions.

    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =

            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }
