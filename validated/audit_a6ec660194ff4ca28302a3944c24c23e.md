### Title
Reverted PRC20 deposit/executeUniversalTx EVM calls treated as SUCCESS due to unchecked VmError - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go, x/uexecutor/keeper/execute_inbound_funds.go)

### Summary
Push Chain's `x/uexecutor` module drives module-originated EVM writes (PRC20 mint/deposit, `executeUniversalTx` calls) through `DerivedEVMCall`, which returns a `*evmtypes.MsgEthereumTxResponse` plus a Go `error`. Every call site in the inbound-execution flow classifies the resulting `PCTx.Status` as `"SUCCESS"` purely based on whether the Go `error` is `nil`, never inspecting the receipt itself for an EVM-level revert (`VmError`) — the same class of bug as the ERC20 report's unchecked `asset.transfer` boolean.

### Finding Description
`CallPRC20Deposit`, `CallPRC20DepositAutoSwap`, and `CallExecuteUniversalTx` ( [1](#0-0) , [2](#0-1) ) all just `return k.evmKeeper.DerivedEVMCall(...)` directly, forwarding whatever `(*evmtypes.MsgEthereumTxResponse, error)` pair the EVM keeper produces.

In the callers that consume these receipts — `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload` — the code consistently does:
```go
if execErr != nil {
    pcTx.Status = "FAILED"
    pcTx.ErrorMsg = execErr.Error()
} else {
    pcTx.Status = "SUCCESS"
}
``` [3](#0-2) [4](#0-3) [5](#0-4) 

Nowhere in the indexed code does the module check `receipt.VmError` (or an equivalent "reverted" flag on `MsgEthereumTxResponse`) before marking a `PCTx` as `SUCCESS`. This is architecturally identical to the reported bug: an underlying value-transfer primitive can complete without a Go-level error while still failing at the semantic level (an EVM revert is the exact analog of an ERC20 `transfer` returning `false`), and the caller doesn't check that secondary signal.

Whether this is actually exploitable depends on how `DerivedEVMCall` is implemented in the pinned `github.com/pushchain/evm` fork — specifically whether it converts a non-empty `VmError` into a returned Go `error`. That fork's source is not present in this indexed repository, so I could not directly confirm its behavior; `x/uexecutor` treats `DerivedEVMCall` purely as an opaque `(response, error)` pair and never reads `VmError` off the response even though the response type carries it. Standard cosmos-evm `CallEVM`/`ApplyMessage` semantics generally return `err == nil` alongside a populated `Ret`/`VmError` for a reverted-but-otherwise-valid call (that's the whole point of a receipt existing for a "failed" transaction), which is why upstream code normally must check `res.VmError` (or `res.Failed()`in go-ethereum receipt terms) explicitly. If this fork follows that same convention — and there is no code here overriding or checking for it — then `x/uexecutor` would record `SUCCESS` PCTx entries, skip the revert/refund logic, and finalize the UniversalTx as executed even though the PRC20 mint/deposit or contract call actually reverted on-chain.

### Impact Explanation
If a PRC20 deposit or `executeUniversalTx` call reverts inside the EVM (e.g., recipient contract rejects the call, gas limit is insufficient inside the derived tx, or the PRC20 contract's internal logic reverts) but `DerivedEVMCall` returns `err == nil` with a non-empty `VmError`, the module would:
- Record the `PCTx` as `"SUCCESS"` [3](#0-2) .
- Skip building an `INBOUND_REVERT` outbound, since revert logic is keyed off `execErr != nil` [6](#0-5) .
- Mark the UniversalTx as finalized/executed while no PRC20 tokens were actually minted to the recipient — a permanent loss for the user (funds bridged in but never credited) and a canonical UTX state that diverges from the real on-chain outcome. This maps directly to the "corruption of PRC20 accounting / canonical UniversalTx state" impact category in scope.

### Likelihood Explanation
Trigger conditions (recipient contract that reverts on `executeUniversalTx`, or a PRC20/handler contract call that reverts due to state constraints) are reachable by any unprivileged user submitting an ordinary inbound deposit or CEA payload — no privileged actor is required. The likelihood that this is a *live* bug hinges entirely on the unverified behavior of `DerivedEVMCall` in the `pushchain/evm` fork, which is outside the indexed source. I was not able to confirm from the available code whether that fork already promotes `VmError` into a Go `error` (which would make this a non-issue) or leaves it unpropagated (which would make this a real, medium/high-severity accounting bug). This uncertainty is the main reason to flag it for direct verification rather than assert it with full confidence.

### Recommendation
- Confirm the exact semantics of `DerivedEVMCall`/`CallEVM` in `github.com/pushchain/evm` regarding `VmError`.
- If `VmError` is not converted to a Go error, add an explicit check at every `x/uexecutor` call site that consumes a `MsgEthereumTxResponse` (`ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`, `ExecutePayloadV2`) to treat `receipt.VmError != ""` the same as `err != nil`: mark `PCTx.Status = "FAILED"`, populate `ErrorMsg`, and route into the existing revert/refund path instead of `SUCCESS`.
- Add integration tests using a recipient contract engineered to revert inside `executeUniversalTx`/PRC20 deposit to confirm the resulting `PCTx.Status` and outbound behavior match the actual on-chain outcome.

### Proof of Concept
Not directly executable without access to the `pushchain/evm` fork's `DerivedEVMCall` source to confirm `VmError` propagation. Conceptually:
1. Submit an inbound with `IsCEA=true` whose `Recipient` is a smart contract that reverts inside its `executeUniversalTx` handler after being credited with a PRC20 deposit that itself reverts (e.g., temporarily paused/insufficient state on the PRC20 contract).
2. If `CallExecuteUniversalTx`/`depositPRC20` returns `(receipt with VmError set, err=nil)`, `execErr`/`contractErr` remain `nil` in `ExecuteInboundFundsAndPayload` ( [7](#0-6) ), and `callPcTx.Status` is set to `"SUCCESS"` despite no state change on-chain.
3. Verify via `balanceOf` that the recipient's PRC20 balance did not change while the `UniversalTx.PcTx` shows `SUCCESS`.

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
