### Title
Unbounded reliance on manipulable single-block Uniswap V3 spot quote for `depositPRC20WithAutoSwap` / `refundUnusedGas` minimum-output enables repeated value extraction from UniversalCore's swap reserves - (File: x/uexecutor/keeper/evm.go)

### Summary
Every `GAS` and `GAS_AND_PAYLOAD` inbound (and every outbound gas refund with excess) triggers a live, unhedged spot-price read from Uniswap V3's `QuoterV2.quoteExactInputSingle` and uses it, unmodified apart from a flat 5% haircut, as `minPCOut` for a real swap the `uexecutor` module executes on behalf of the user via `depositPRC20WithAutoSwap`/`refundUnusedGas`. Because the quote and the actual swap execute in the same Push Chain block/transaction with no TWAP, staleness check, or external price cross-check, an attacker who can move the pool's spot price immediately beforehand (e.g., via a large swap against the same Uniswap pool, funded with their own capital or a flash loan) can inflate the quote used to floor the module's swap. Repeating this pattern across many small, cheaply-triggered gas-only inbounds lets the attacker iteratively convert bridged gas-top-up value into an inflated PC payout, extracting real reserves from the module's swap path — the same "repeat a self-reinforcing manipulation to exceed the true collateral value, over and over, until a cap is hit" pattern as the referenced perpetuals report, just substituting "mark price from own orders" with "spot AMM price from own swaps."

### Finding Description
`GetSwapQuote` (`x/uexecutor/keeper/evm.go:500-538`) is a bare `quoteExactInputSingle` call against whatever the current pool state is: [1](#0-0) 

This value flows straight into `minPCOut = quote * 95 / 100` at each of the three call sites — `ExecuteInboundGas` (`x/uexecutor/keeper/execute_inbound_gas.go:104-153`), `gasAndPayloadDepositAutoSwap` (`x/uexecutor/keeper/execute_inbound_gas_and_payload.go:347-379`), and `applyGasRefund`/`getSwapQuoteForRefund` (`x/uexecutor/keeper/outbound.go:174-270`) — and is passed as the floor to `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas`, which perform the actual on-chain Uniswap swap through `UniversalCore.depositPRC20WithAutoSwap` / `.refundUnusedGas`: [2](#0-1) [3](#0-2) 

Since the quote is read and the swap executed in the same finalize-inbound / finalize-outbound flow with no independent price oracle, no maximum-deviation bound versus a longer-window price, and no cap on how large a single deposit/refund swap can be, an attacker who manipulates the underlying pool's instantaneous price (by trading against it right before their own gas-inbound gets voted/finalized, or by using flash-loaned capital) causes the module's swap to execute at the manipulated rate. The attacker's own capital used to move the price is returned to them (minus swap fees) once they reverse the trade, while the module's swap — sized off the manipulated quote — pays out more PC than the bridged deposit is actually worth at the pool's undistorted price. This is directly analogous to the reported bug's core mechanic: a user-triggerable action inflates a value (mark price / unrealized PnL there, spot AMM price here) that is then fed back into the same flow's collateral/margin (minPCOut / swap payout here) to extract more value than deposited, and the attack is trivially repeatable across many inbounds to compound the drain, exactly like the reported iteration loop that runs until `maxOpenInterest`/pool depth is exhausted.

### Impact Explanation
This is in-scope under "corruption of PRC20 or native asset accounting, gas fee accounting, refund accounting... or canonical UniversalTx state" and "unauthorized module-originated EVM execution" — the module (an honest, correctly-functioning validator set) is tricked into executing swaps priced off attacker-manipulated state, draining PC/WPC value that should have stayed in UniversalCore's swap reserves. Repeated over many inbounds this can materially drain protocol-controlled swap liquidity, matching the "draining the protocol fully" impact class of the source report.

### Likelihood Explanation
Triggering an inbound gas top-up or causing an outbound with excess gas fee is a fully unprivileged, ordinary user action (the attacker just needs to deposit small real value on a source chain that Universal Validators will honestly vote on — no validator collusion required). Moving a Uniswap V3 pool's spot price is a standard, cheap, and well-understood MEV technique, especially if pool depth for the specific PRC20/WPC pair is thin (likely for many bridged tokens). The main open uncertainty is the actual depth/liquidity of each configured Uniswap pool and whether `TokenConfig.LiquidityCap` (seen referenced across `uregistry` but whose enforcement point I did not have time to trace fully) or per-tx deposit-size limits meaningfully cap the exploitable amount per inbound — this would need to be verified in code before treating the impact as unconditionally "protocol-draining" versus "bounded per-tx slippage extraction, compounding only via inbound count and gas cost of repeated attacks."

### Recommendation
- Replace or supplement the instantaneous `quoteExactInputSingle` spot quote with a TWAP-based price (Uniswap V3 `observe`) or an independent oracle, and reject swaps where the spot price deviates beyond a bounded threshold from the TWAP.
- Consider using `exactInput` with router-enforced `amountOutMinimum` derived from a manipulation-resistant reference price rather than deriving both the floor and the execution from the same single-block read.
- Add a per-inbound / per-block cap on total swap notional through `depositPRC20WithAutoSwap`/`refundUnusedGas` for a given PRC20/pool pair, so a single manipulated price window can only extract a bounded amount regardless of repetition count.
- Verify and, if necessary, enforce `TokenConfig.LiquidityCap` (or an equivalent) directly against the swap notional at the point `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` execute, not just at deposit registration time.

### Proof of Concept
I could not construct or run an executable PoC within this ask-only session (no code execution / test-harness access here). A concrete PoC would need to: (1) deploy/fork the `UniversalCore` + Uniswap V3 pool test fixtures used in `test/integration/uexecutor/execute_inbound_gas_test.go`, (2) execute a large swap against the PRC20/WPC pool from an attacker-controlled account to skew the spot price, (3) within the same block, submit and vote-finalize a `GAS` inbound so `ExecuteInboundGas` reads the skewed `GetSwapQuote` and executes `CallPRC20DepositAutoSwap` at the inflated rate, (4) reverse the attacker's initial swap, and (5) measure whether the module's net PC payout to the attacker's UEA exceeds the pre-manipulation fair value of the bridged deposit. This should be validated by a Devin session with repo execution access before being treated as a confirmed, exploitable finding — the theoretical mechanism is sound based on the code read, but pool depth, `LiquidityCap` enforcement, and any slippage-bound checks in the (not-included-in-index) `UniversalCore` Solidity contract itself are unverified.
