### Title
`DelegateAction` Signed Payload Omits Chain Identity, Enabling Cross-Chain/Fork Replay of Meta-Transactions — (`core/primitives/src/action/delegate.rs`)

### Summary

The `DelegateAction` (meta-transaction) signed payload does not include any chain-specific identifier (`chain_id` or `block_hash`). A `SignedDelegateAction` created on one NEAR chain (e.g., mainnet) is cryptographically valid on any fork or other NEAR network where the signer's nonce is still below the signed value and the block height is below `max_block_height`. A relayer or any party holding the signed bytes can replay the action on the forked chain without the user's knowledge, executing arbitrary token transfers or contract calls on behalf of the user.

### Finding Description

`DelegateAction` (NEP-366 meta-transactions) is the mechanism by which a user signs an off-chain payload that a relayer submits on-chain. The struct that the user signs is:

```rust
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
}
``` [1](#0-0) 

The hash signed by the user is computed as:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
``` [2](#0-1) 

`SignableMessage` prepends only a fixed NEP discriminant (`u32` constant `1073742222` for NEP-366), not any chain-specific value:

```rust
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}
``` [3](#0-2) 

The discriminant is a compile-time constant derived only from the NEP number, not from the chain's genesis `chain_id`: [4](#0-3) 

At execution time, `apply_delegate_action` validates only:
1. Signature over the chain-agnostic hash above
2. `block_height > max_block_height` (block height, not block hash — heights are shared across forks)
3. `sender_id` match
4. Nonce strictly greater than the access key's stored nonce

```rust
if !signed_delegate_action.verify() { ... }
if apply_state.block_height > delegate_action.max_block_height() { ... }
if delegate_action.sender_id().as_str() != sender_id.as_str() { ... }
validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
``` [5](#0-4) 

There is no check against any chain-specific identifier. By contrast, regular `SignedTransaction` embeds a `block_hash` that must exist in the canonical chain within `transaction_validity_period` blocks, making cross-fork replay impossible: [6](#0-5) 

`DelegateActionV2` has the identical omission — its `DelegateActionV2` struct also contains no chain-specific field: [7](#0-6) 

### Impact Explanation

An attacker (relayer or any party who observed the signed bytes) can replay a `SignedDelegateAction` on a forked NEAR chain or on testnet/betanet if the user's nonce on that chain is still below the signed nonce and the block height is below `max_block_height`. The replayed action executes with the user as `sender_id`, so any token transfer, FT transfer, or contract call inside the delegate action is executed on the fork without the user's consent. This constitutes **unauthorized transaction execution** and potential **theft of funds** on the forked chain.

### Likelihood Explanation

- Requires a hard fork or chain split where both chains share the same account state up to the fork point (nonces are identical at fork time).
- The attacker must possess the `SignedDelegateAction` bytes — trivially available to any relayer, and also observable from on-chain data on the original chain.
- `max_block_height` is typically set to a future block height (e.g., current height + a few hundred blocks), so the window is bounded but real.
- NEAR has had protocol upgrades and the testnet/mainnet distinction already provides a live cross-network replay surface for any user who signs a `DelegateAction` on testnet and whose account exists on mainnet with a lower nonce.

### Recommendation

Include the chain's `chain_id` (available from genesis config, e.g., `"mainnet"`, `"testnet"`) in the `DelegateAction` signed payload, analogous to how EIP-155 added `chainId` to Ethereum transaction signing. Concretely:

- Add a `chain_id: String` field to `DelegateAction` and `DelegateActionV2`.
- Include it in the borsh-serialized body that `get_nep461_hash()` hashes.
- In `apply_delegate_action`, verify that `delegate_action.chain_id == apply_state.chain_id` before accepting the signature.

This mirrors the short-term fix recommended for ERC20Permit and makes cross-chain/cross-fork replay cryptographically impossible.

### Proof of Concept

1. On mainnet (chain_id = `"mainnet"`), Alice signs a `DelegateAction` authorizing a relayer to call `ft_transfer` sending 1000 NEAR-FT to Bob. Her access key nonce is currently `19000000`; she signs with nonce `19000001` and `max_block_height = current_height + 200`.

2. A hard fork occurs at block height `H`. Both chains now have Alice's account with nonce `19000000`.

3. On the fork chain, the relayer (or any observer who captured the signed bytes from mainnet) submits the same `SignedDelegateAction` bytes.

4. `apply_delegate_action` is called. `signed_delegate_action.verify()` passes — the hash is identical on both chains because `DelegateAction` contains no chain-specific field. The nonce `19000001 > 19000000` passes. The block height check passes if the fork is still below `max_block_height`.

5. Alice's 1000 FT are transferred to Bob on the fork chain without Alice's authorization.

The signed payload that is replayed is exactly:
```
hash(borsh(u32(1073742222) || sender_id || receiver_id || actions || nonce || max_block_height || public_key))
``` [8](#0-7) 

No field in this payload is chain-specific, confirming the replay is unconditionally valid on any NEAR fork sharing the same account state at fork time.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
