### Title
Caller's Excess Attached Deposit Is Permanently Retained by the Wallet Contract on Successful Execution - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `CallerDeposit` refund mechanism only returns an external caller's attached deposit when the underlying cross-contract promise fails outright. It never refunds any portion of the deposit that exceeds what the emulated Ethereum-style action actually needed when that action succeeds, mirroring the `depositNative()` bug where `msg.value > _amount` is silently absorbed instead of returned.

### Finding Description
`inner_rlp_execute` captures the caller's full `attached_deposit` into a `CallerDeposit { account_id, yocto_near }` struct, explicitly documented as existing "to refund the caller's deposit if the cross-contract call fails": [1](#0-0) 

This `caller_deposit` is threaded through every callback path (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`): [2](#0-1) 

The only place a refund is actually issued is in `rlp_execute_callback`, and only on the `PromiseResult::Failed` branch: [3](#0-2) 

On the `PromiseResult::Successful` branch, the caller's deposit is never examined against the actual value the eth-emulated action needed — no excess is computed or returned: [4](#0-3) 

This is exactly the class of bug in the report: the contract accepts an attached value (`msg.value` analog = `attached_deposit`), performs an action that only requires part of it (analog = `_amount`), and has no mechanism to return the surplus once the call is "successful" — it enforces "deposit is enough" but never "deposit == what's needed" nor issues a partial refund. The project's own test suite documents this behavior as intentional/expected rather than a caught bug: [5](#0-4) 

The comment on that assertion literally states: "External caller does not get a refund when their tokens are spent," and the test only checks that the balance *decreased by at least* `deposit_amount` — it does not verify (and the contract does not guarantee) that any unused fraction of the deposit is returned when the action succeeds but consumes less than the full attached amount.

### Impact Explanation
Any relayer/RPC caller invoking `rlp_execute` on behalf of a user (or an external caller directly attaching a deposit) who over-attaches NEAR relative to what the underlying eth-style action actually transfers will have the excess permanently retained by the Wallet Contract, with no code path to recover it. This is a concrete, protocol-adjacent "permanently frozen funds" condition for callers of the wallet contract — funds are not being tracked/escrowed correctly and there is no accounting path for a partial refund once the promise resolves successfully.

### Likelihood Explanation
This is trivially reachable: any external caller (unprivileged, no special permission needed) invoking `rlp_execute` with `attached_deposit` greater than the yoctoNEAR value implied by the RLP-encoded eth transaction's `value`/fee fields will trigger this path whenever the target promise succeeds. No adversarial validator or node behavior is required — it is purely a function of a single transaction/call from a normal caller.

### Recommendation
Compute the exact yoctoNEAR amount actually required by the resolved `Action` (transfer value + fee, or function-call deposit) versus the full `attached_deposit` captured in `CallerDeposit`. On success, refund `attached_deposit - amount_actually_used` to the caller in the same way the failure path refunds the full deposit, or require `attached_deposit == amount_actually_used` at parse time and reject calls that over-attach, forcing calling relayers to submit exact deposits.

### Proof of Concept
1. An external, non-self caller (`predecessor_account_id != current_account_id`) calls `rlp_execute`/`rlp_execute_from` on the Wallet Contract attaching `deposit_amount` NEAR, as in `test_caller_refunds`.
2. The RLP-encoded action targets an account/method that requires strictly less NEAR than `deposit_amount` to succeed (e.g., a `FunctionCall` action with `yocto_near: 0` as used in the existing test, or any action whose actual on-chain deposit is less than the attached amount).
3. `inner_rlp_execute` records the full `deposit_amount` in `CallerDeposit` and dispatches the promise via `action_to_promise(...).then(ext.rlp_execute_callback(caller_deposit))`.
4. The promise succeeds (`PromiseResult::Successful`), so `rlp_execute_callback` returns `ExecuteResponse { success: true, ... }` without ever computing or returning the unused portion of `deposit_amount`.
5. As demonstrated by the existing test assertion `pre_tx_account_balance - post_tx_account_balance >= deposit_amount.as_yoctonear()` (i.e., no refund), the caller's excess funds are irreversibly retained by the Wallet Contract. [5](#0-4)

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
