### Title
CANCELALLUNFREEZEV2 TVM opcode bypasses the `AllowCancelAllUnfreezeV2` hard-fork gate enforced by the normal-transaction actuator - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/CancelAllUnfreezeV2Processor.java])

### Finding Description
`CancelAllUnfreezeV2Processor.validate` only checks that the repository is non-null, that the owner address is valid, and that the account exists: [1](#0-0) 

It never calls `repo.getDynamicPropertiesStore().supportAllowCancelAllUnfreezeV2()`. In contrast, the normal-transaction entrypoint `CancelAllUnfreezeV2Actuator.validate` explicitly gates the feature behind the hard fork flag: [2](#0-1) 

I confirmed the discrepancy at the two actuator/processor `validate` methods directly. I was not able to fully load and inspect the body of `Program.cancelAllUnfreezeV2Action` in `actuator/src/main/java/org/tron/core/vm/program/Program.java` (only its imports were retrieved before the tool budget ran out), so I cannot state with certainty whether that wrapper method independently re-checks `supportAllowCancelAllUnfreezeV2()` before delegating to `CancelAllUnfreezeV2Processor.validate/execute`. However, a search of the opcode dispatch layer (`actuator/src/main/java/org/tron/core/vm/OperationActions.java` and `actuator/src/main/java/org/tron/core/vm/Op.java`) found no references to `CancelAllUnfreezeV2`/`allowCancelAllUnfreezeV2` gating logic, which suggests the flag check is not duplicated at the opcode-dispatch level either. This leaves the `Processor.validate` method as the most likely sole gatekeeper for the TVM call path, and it is missing the check present in the transaction-actuator path.

### Impact Explanation
If confirmed that `Program.cancelAllUnfreezeV2Action` does not itself gate on `supportAllowCancelAllUnfreezeV2()`, then a contract could invoke the `CANCELALLUNFREEZEV2` opcode and successfully cancel all pending unfreeze-v2 entries (restoring frozen balance / resource weight) before the feature is enabled by committee vote, causing state divergence between the transaction path (blocked) and the TVM path (allowed), and premature activation of an accounting change gated by governance.

### Likelihood Explanation
This requires the hard fork flag to be un-set (a real precondition today/at some past height) and requires the attacker to own a contract with `unfrozenV2List` entries and to execute the `CANCELALLUNFREEZEV2` opcode from a contract call — both are unprivileged, realistic actions if the opcode is reachable without the gate.

### Recommendation
Add the same check present in `CancelAllUnfreezeV2Actuator.validate` to `CancelAllUnfreezeV2Processor.validate`:
```java
if (!repo.getDynamicPropertiesStore().supportAllowCancelAllUnfreezeV2()) {
  throw new ContractValidateException("Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee");
}
```
This should be verified together with a full read of `Program.cancelAllUnfreezeV2Action` to confirm whether it already performs this check independently — if it does, the divergence described here would already be closed at that layer and the `Processor.validate` gap would be purely defensive, not exploitable.
