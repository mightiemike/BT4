### Title
`get-assets` panics entirely if any single enabled collateral asset's oracle price is stale, bricking `borrow`/`repay`/`collateral-remove`/`liquidate` for every user sharing that egroup - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`get-assets` builds the price list for *all* enabled collateral/debt assets in the global bitmask (not just the asset the caller is operating on) via `price-multi-resolve`, and unconditionally `unwrap-panic`s the result. If price resolution for even one of those assets fails (e.g., its Pyth/DIA feed goes stale relative to its configured `max-staleness`), the whole call panics and aborts the transaction — for every account whose position mask includes that asset, and for every core action that calls `get-assets` (`borrow`, `collateral-remove`, `liquidate`, `collateral-add`'s capacity check).

### Finding Description
`get-assets` computes the list of enabled assets under the safe mask, resolves oracle data for each, and calls `price-multi-resolve` and immediately `unwrap-panic`s its response: [1](#0-0) 

`price-multi-resolve` folds `iter-price-multi` over every oracle entry, and any single `price-resolve` failure (stale timestamp, illegal/zero price, oracle-callcode error) sets `valid: false`, which causes `price-multi-resolve` to `asserts!` on `valid` and return `ERR-ORACLE-MULTI`: [2](#0-1) 

Because `get-assets` wraps this in `unwrap-panic` rather than propagating the error via `try!`, a single stale/invalid asset price turns into an unrecoverable panic that aborts the entire transaction, rather than a controlled `err` that could allow the caller to fall back or the manager to intervene.

`get-assets` (and therefore this failure mode) is reachable from every core lending action that resolves prices for the position's enabled mask, not just for the specific asset being acted on:
- `borrow` calls `get-assets mask` over the user's full position mask before allowing any borrow: [3](#0-2) 
- `collateral-remove` (when the user has debt) calls `get-assets position-mask`: [4](#0-3) 
- `liquidate` calls `get-assets mask` for the borrower's liquidation-relevant mask before computing health/liquidation parameters: [5](#0-4) 
- `collateral-add`'s capacity check for new collateral also calls `get-assets current-mask`: [6](#0-5) 

This mirrors the Notional bug class exactly: a fold (`iter-price-multi`/`price-multi-resolve`) over a list of sub-operations (per-asset price resolutions) whose failure is absorbed only up to a point and then converted into an unconditional panic (`unwrap-panic` in `get-assets`), so that one bad element (one stale oracle feed for one asset in the shared egroup/bitmask) blocks the whole class of core operations (borrow, repay-adjacent collateral removal, liquidation, collateral-add capacity checks) for every account whose enabled mask includes that asset — not because two users interact, but because the health/valuation step is evaluated eagerly over the entire mask before the guarded operation, and any one failure there strands all dependent flows.

### Impact Explanation
If a single supported asset's oracle feed becomes stale (exceeds its configured `max-staleness`) or returns an illegal (zero) price and does not get refreshed in-band (e.g., liquidity issues with providing a fresh Pyth payload, misconfigured `max-staleness`, or a temporarily broken feed/callcode chain such as `resolve-ststx`/`resolve-ztoken`), then:
- Users with that asset enabled in their bitmask cannot `borrow` against or `collateral-remove` any of their collateral (their entire position's health check panics), even though they may want to withdraw an unrelated, healthy asset or exit their position entirely.
- `liquidate` also panics for any borrower whose mask includes the broken asset, meaning under-collateralized positions cannot be liquidated during the outage, risking protocol insolvency (bad debt) building up unnoticed.
- This is a temporary freezing of funds (users' collateral/borrow capacity locked) and, in the liquidation-blocking scenario, a path to protocol insolvency if bad positions cannot be liquidated while the feed is broken.

### Likelihood Explanation
Oracle staleness is a foreseeable, externally-triggered condition (feed downtime, network congestion preventing in-band Pyth updates, `max-staleness` misconfigured too tight for an asset's actual publish cadence) rather than a contrived edge case. Given the protocol's own documentation stresses in-band price updates specifically to avoid staleness-driven failures, the existence of an `unwrap-panic` path in `get-assets` that still hard-panics instead of gracefully failing indicates the underlying assumption (feeds are always fresh or always refreshable in-band) is not guaranteed to hold, especially across all assets in a shared egroup simultaneously.

### Recommendation
Avoid using `unwrap-panic` on `price-multi-resolve` in `get-assets`; propagate the error via `try!`/`unwrap!` up through `borrow`, `collateral-remove`, `liquidate`, and `collateral-add`. Additionally, consider decoupling the health-check price resolution from unrelated assets in the mask — e.g., only require fresh prices for the assets actually mutated/liquidated in the current call rather than all enabled assets in the position's mask — so a single broken feed cannot brick every core action for every affected account, and provide an explicit "resolve-safe" fallback (analogous to `resolve-safe` in `market-vault`) for withdrawal/liquidation paths under oracle failure.

### Proof of Concept
1. An asset (say `zstSTX`, whose price resolution chains through `resolve-ststx` calling `call-ststx-ratio`, then `resolve-ztoken`) has its underlying Pyth feed go stale past its configured `max-staleness`, or its `call-ststx-ratio` external call starts erroring: [7](#0-6) 
2. Any account with this asset enabled in their collateral bitmask (e.g., another unrelated user, or the account under liquidation) triggers `borrow`, `collateral-remove`, `liquidate`, or `collateral-add`.
3. Each of these calls `get-assets mask`, which resolves prices for **all** enabled assets in the mask via `price-multi-resolve`: [1](#0-0) 
4. `price-resolve` for the broken asset fails the staleness/legality `asserts!` and returns `ERR-ORACLE-INVARIANT`, `iter-price-multi` marks `valid: false`, and `price-multi-resolve` returns `(err ERR-ORACLE-MULTI)`: [8](#0-7) 
5. `get-assets`'s `unwrap-panic` on that `err` result causes the entire transaction to panic/abort — not a graceful `err` return — so `borrow`, `collateral-remove`, `liquidate`, and the `collateral-add` capacity path all fail for every account, even accounts that only wanted to touch an unrelated healthy asset, and liquidators cannot liquidate unhealthy positions sharing that mask while the feed remains broken.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
