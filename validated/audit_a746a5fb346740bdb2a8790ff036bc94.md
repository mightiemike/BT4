### Title
`afterAuth` hook failures silently skip execution on retry due to `IdempotentPromiseHandler` never clearing failed identifiers - (File: packages/apps/shopify-app-express/src/helpers/idempotent-promise-handler.ts)

### Summary
The token-exchange authentication flow in `shopify-app-express`, `shopify-app-react-router`, and `shopify-app-remix` uses an `IdempotentPromiseHandler` to prevent the `afterAuth` hook from running twice for the same session token. However, once a session token is registered as "in progress," it is **never removed if the wrapped promise throws** — it stays in the map until a fixed TTL expires. Any retry that arrives with the same identifier during that window is silently treated as "already handled" and the hook is skipped entirely, yet the caller receives no error, masking the fact that the required post-auth step never completed. This mirrors the reNFT bug class: a single failure in an operation (there, an ERC20 transfer; here, the `afterAuth` hook, which itself frequently performs external calls such as webhook registration or billing checks) permanently blocks the completion of a required state transition for a fixed window, while the surrounding code proceeds as though nothing went wrong.

### Finding Description
`IdempotentPromiseHandler.handlePromise` marks an `identifier` as "consumed" **before** invoking the wrapped `promiseFunction`, and only removes identifiers when they become stale (`IDENTIFIER_TTL_MS = 60000`) — it does **not** remove the identifier if the promise throws: [1](#0-0) 

This handler is used to guard the `afterAuth` hook invocation, keyed by the raw `sessionToken`, in both the Express token-exchange middleware: [2](#0-1) 

and in the React Router / Remix token-exchange strategy: [3](#0-2) 

Flow:
1. A request completes offline/online token exchange and stores the new session via `config.sessionStorage.storeSession(...)`.
2. `callAfterAuthHook`/`handleAfterAuthHook` calls `idempotentPromiseHandler.handlePromise({promiseFunction: () => config.hooks.afterAuth(...), identifier: sessionToken})`.
3. If `afterAuth` throws (e.g. due to a transient failure in webhook registration, a billing check, or any other external/side-effecting call the app performs there), the exception propagates and the outer catch responds with a 500: [4](#0-3) 
   — but the `sessionToken` identifier is **already left in the map**, since it was inserted by `isPromiseRunnable` prior to execution and is only cleaned up on TTL expiry, not on failure.
4. If the client retries with the same `sessionToken` (which is expected client behavior after receiving a 500, and is explicit protocol for `InvalidJwtError`/`invalid_subject_token` via `retryRequest: true` elsewhere in the same handler), `isPromiseRunnable` returns `false`, so `promiseFunction` (the `afterAuth` hook) is **not invoked again**, and `handlePromise` resolves successfully with no indication that the hook never ran.
5. The caller (`performTokenExchange` / `authenticate`) treats this as success and proceeds to `next()` / returns the session as authenticated, even though the mandatory post-auth step was silently skipped.

### Impact Explanation
Any app that relies on `afterAuth` to perform security- or state-relevant setup (registering mandatory webhooks, enforcing billing checks, provisioning per-shop records, revoking old grants, etc.) can have that step silently bypassed for up to 60 seconds after a single failure, while the request pipeline reports success and lets the request continue as fully authenticated. This is directly analogous to the reNFT class of bug: a failure in one external/side-effecting operation, instead of being surfaced or retried, leaves the surrounding state machine believing a required transition succeeded, allowing a requester to proceed without the safeguard actually having executed. Since the guard is per-request and self-inflicted, no elevated privilege is required — any single request/session-token pair experiencing one hook failure (which can be triggered by conditions outside the caller's control, e.g. a transient external dependency call inside `afterAuth`) creates this bypass window for subsequent retries using the same token.

### Likelihood Explanation
Requires: (1) an app's `afterAuth` hook to throw at least once for a given `sessionToken`/request (a plausible occurrence given `afterAuth` typically performs network calls like webhook registration), and (2) a retry with the identical `sessionToken` within the 60-second TTL window — which is the very reconnection behavior the surrounding code encourages (e.g. `respondToInvalidSessionToken` with `retryRequest: true` for related error paths). No privileged access or secret knowledge is needed; it can occur from ordinary retry/backoff behavior of any client completing OAuth/token exchange.

### Recommendation
- Remove (or otherwise reset) the identifier from `IdempotentPromiseHandler`'s map immediately when `promiseFunction` throws, rather than leaving it until TTL expiry, so that retries can genuinely re-attempt the `afterAuth` hook.
- Alternatively, track and propagate failure state per-identifier so that skipped/duplicate calls surface the original failure to the caller instead of resolving silently.
- Ensure `performTokenExchange`/`authenticate` do not mark a request as successfully authenticated/`next()`-ed unless `afterAuth` is confirmed to have completed (or is confirmed idempotent-safe to skip).

### Proof of Concept
1. Configure an app with `hooks.afterAuth` that throws on its first invocation for a shop (simulating a transient external failure, e.g. webhook registration timeout).
2. Complete token exchange for a shop; the first request fails with 500 as shown in `performTokenExchange`'s catch block (`packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts:123-129`) — but by then `idempotentPromiseHandler.identifiers` already contains the `sessionToken`.
3. Immediately retry the request with the same `sessionToken` (well within `IDENTIFIER_TTL_MS = 60000`).
4. Observe that `isPromiseRunnable` returns `false` in `packages/apps/shopify-app-express/src/helpers/idempotent-promise-handler.ts:30-36`, `promiseFunction` (the `afterAuth` hook) is never invoked a second time, and `handlePromise` resolves without error — `performTokenExchange` proceeds to `res.locals.shopify = {...}; next();` as if `afterAuth` had succeeded, despite it having never completed.

```typescript
  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
```
