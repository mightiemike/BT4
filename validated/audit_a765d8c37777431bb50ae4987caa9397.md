## Title
First delegator to a vote account can claim the entire pre-accumulated `pending_delegator_rewards` pool regardless of stake size - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Vote accounts accumulate a lamport-denominated reward pool, `pending_delegator_rewards`, that is credited independently of whether the vote account has any active delegated stake. When stake becomes active for that vote account, the entire pool is split among current delegators in proportion to `stake / total_active_stake`. Because `total_active_stake` (not the pool balance) gates distribution, a single new delegator staking a trivial amount to a previously "virgin" (or long-unstaked) vote account can capture the whole `pending_delegator_rewards` balance accumulated while `total_active_stake == 0`, exactly mirroring the wxETH "first staker claims all drops" pattern.

### Finding Description
`pending_delegator_rewards` on a `VoteStateV4` account can be incremented in two ways, neither of which requires the vote account to have any active delegated stake:

1. Anyone can permissionlessly call the `DepositDelegatorRewards` instruction, which transfers lamports from any signer into the vote account and bumps `pending_delegator_rewards`, with no check on `total_active_stake`: [1](#0-0) 

2. Block/priority fees are automatically deposited into `pending_delegator_rewards` every block via `deposit_delegator_fees`, again with no dependency on whether the vote account currently has active stake: [2](#0-1) 

At epoch-reward time, `calculate_block_reward` distributes the accumulated `pending_delegator_rewards` to each stake delegated to the vote account, proportional to `stake / total_active_stake`: [3](#0-2) 

Crucially, the guard is `if total_active_stake == 0 { 0 }` — i.e. the pool simply accrues untouched while nobody is staked to that voter, rather than being reduced/reset. This is structurally identical to `_accrueDrip()` in the wxETH report: the reward-generating mechanism (`DepositDelegatorRewards` deposits, block-fee deposits) is completely decoupled from `total_active_stake`, so a pool can build up while the "denominator" (delegated stake) is zero. As soon as `total_active_stake` becomes non-zero — e.g. an attacker delegates 1 lamport of stake to that vote account for one epoch — the payout formula `pending_delegator_rewards * stake / total_active_stake` collapses to `pending_delegator_rewards * stake/stake` for the sole delegator, letting them redeem the entire pool despite holding a trivial, freshly-created stake.

### Impact Explanation
This allows an unprivileged actor to steal lamports that were intended to reward long-term delegators of a validator (or, for the auto-fee-deposit path, network/block-fee delegator rewards). By momentarily creating and delegating a dust stake account to a vote account with an accumulated `pending_delegator_rewards` balance and zero active stake (or where existing stakers deactivated), the attacker can redeem 100% of the pool via the normal `calculate_block_reward` / `calculate_stake_rewards_and_commissions` path, which pays lamports directly into the staker's stake account. This is a concrete theft-of-funds/incorrect lamport-distribution bug reachable purely through ordinary client transactions (the permissionless `DepositDelegatorRewards` instruction plus a normal `DelegateStake`), without any special privilege.

### Likelihood Explanation
Likelihood is comparable to the original Medium-severity C4 finding: it requires a vote account to have `total_active_stake == 0` (or negligible) while `pending_delegator_rewards` has accumulated — a state that is easy to engineer deliberately (e.g., a validator operator creates a fresh vote account, deposits/accrues fees via normal block production before any delegator stakes to it, then delegates their own dust stake) rather than relying on chance timing.

### Recommendation
Do not allow `pending_delegator_rewards` to accrue (via `DepositDelegatorRewards` or `deposit_delegator_fees`) while `total_active_stake` for the vote account is zero — either reject/burn/redirect such deposits, or track accrual per-active-stake-epoch so that lamports deposited during a zero-stake period are not later paid out entirely to the first staker who reactivates the account. Analogous to the wxETH mitigation of gating `_accrueDrip()` on `totalSupply() > 0`, gate crediting of `pending_delegator_rewards`/block-reward accrual on `total_active_stake > 0` at deposit time, and/or checkpoint the pool so that only rewards accrued after a delegator's stake became active are distributable to that delegator.

### Proof of Concept
1. Create a new vote account `V` (no stake ever delegated to it).
2. Call `DepositDelegatorRewards` (permissionless, any signer) repeatedly, or simply let block production route fees to `V` via `deposit_delegator_fees`, accumulating a large `pending_delegator_rewards` balance while `total_active_stake` for `V` is `0`.
3. Delegate a stake account with 1 lamport (or minimal stake) to `V`; wait for it to become active.
4. At the next epoch boundary, `calculate_block_reward` computes `pending_delegator_rewards * stake / total_active_stake`. Since this delegator is the only active stake, `total_active_stake == stake`, so the payout equals the entire `pending_delegator_rewards` balance, which is credited to the attacker's stake account via `build_updated_stake_reward`: [4](#0-3) 
5. The attacker can then deactivate/withdraw the stake, having captured lamports never earned through actual proportional staking over the accrual period.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    // Deposits delegator fees into the specified vote account and increments
    // pending delegator rewards. If successful, returns the new balance of that
    // account
    fn deposit_delegator_fees(
        &self,
        vote_address: &Pubkey,
        fees: u64,
    ) -> Result<u64, DepositFeeError> {
        let mut account = self
            .get_account_with_fixed_root_no_cache(vote_address)
            .ok_or(DepositFeeError::InvalidVoteAccount)?;

        if *account.owner() != solana_sdk_ids::vote::id() {
            return Err(DepositFeeError::InvalidVoteAccount);
        }

        let account_data = account.data_as_mut_slice();
        let mut vote_state = VoteStateViewMut::new_v4(account_data)
            .map_err(|_| DepositFeeError::InvalidVoteAccount)?;

        vote_state
            .increment_pending_delegator_rewards_checked(fees)
            .ok_or(DepositFeeError::LamportOverflow)?;

        account
            .checked_add_lamports(fees)
            .map_err(|_| DepositFeeError::LamportOverflow)?;

        self.store_account(vote_address, &account);
        Ok(account.lamports())
    }
