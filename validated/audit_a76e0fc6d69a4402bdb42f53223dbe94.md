This confirms the strongest analog: `ExchangeTransactionActuator.doValidate()` at [1](#0-0)  enforces a global `balanceLimit` (from `dynamicStore.getExchangeBalanceLimit()`) on the exchange pool's token balances, and this check is reachable by **any unprivileged account** submitting an `ExchangeTransactionContract` (unlike `ExchangeInjectActuator`, which is restricted to the exchange creator per the check at [2](#0-1) ).

### Title
Any user can DoS other traders' exchange transactions by front-running the pool up to `ExchangeBalanceLimit` - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
The TRC10 bancor-style `Exchange` market enforces a hard cap (`ExchangeBalanceLimit`, a chain-wide dynamic parameter) on the size either token reserve in a trading pair may reach. Any account can submit an `ExchangeTransactionContract` that pushes one side of the pool close to this cap, causing subsequent legitimate traders' transactions in the same pair to revert with `"token balance must less than " + balanceLimit"`, exactly mirroring the reported `maxContractBalance` deposit-blocking pattern.

### Finding Description
`ExchangeTransactionActuator.doValidate()` computes the resulting reserve balance for the token being sold into the pool and rejects the transaction if it would exceed `dynamicStore.getExchangeBalanceLimit()`: [1](#0-0) 
This check is identical in spirit to the reported `maxContractBalance` check: a single global ceiling on a pooled balance that any transaction can push toward the limit. Because `ExchangeTransactionContract` is callable by any account (no creator/owner restriction, unlike `ExchangeInjectActuator` which requires `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` at [2](#0-1) ), an attacker can:
1. Observe a victim's pending `ExchangeTransactionContract` in the mempool that would sell token A into the pool.
2. Broadcast their own competing trade that sells the same token A, sized so the resulting pool reserve lands just under `balanceLimit`.
3. Get it included first (via fee/bandwidth prioritization, block packing order, or same-block ordering by the block-producing witness).
4. The victim's transaction then fails validation with `"token balance must less than " + balanceLimit"`.
5. The attacker can later submit a `ExchangeWithdrawContract` to pull liquidity back out, repeating the attack indefinitely.

This is the same "abuse of an aggregate cap to selectively deny a targeted counterparty" bug class as the referenced Reality Cards report, adapted to java-tron's on-chain AMM-like `Exchange` actuators.

### Impact Explanation
An attacker can selectively and repeatedly block any specific trader from executing trades against a given `Exchange` pool, which can be used to manipulate trade execution order/pricing or to censor competitors from arbitraging/rebalancing a pool, causing denial of service and potential market manipulation for TRC10 asset trading via the on-chain exchange. This does not directly corrupt account balances but denies legitimate market participation, which the scan's "Validate" criteria classifies as a form of DoS via protocol implementation.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to have TRX/token liquidity to size a spoiling trade and reasonable confidence about victim transaction ordering (mempool visibility, witness cooperation, or same-block reordering), similar to the front-running assumptions in the original report. `ExchangeBalanceLimit` is a fixed, publicly-known dynamic parameter, making the target easy to compute exactly.

### Recommendation
Avoid using a hard global cap that any unprivileged trade can saturate. Options include: removing the `ExchangeBalanceLimit` check for `ExchangeTransactionActuator` trades (retain it only for pool-creation/injection sizing), replacing it with a per-account or per-block rate limit, or making the limit a soft/backpressure mechanism (e.g., partial fill or fee scaling) rather than an outright transaction failure.

### Proof of Concept
1. Attacker monitors the network for a pending `ExchangeTransactionContract` from victim V trading token A into exchange pool E.
2. Attacker crafts and broadcasts their own `ExchangeTransactionContract` selling token A into pool E with `tokenQuant` chosen so that `firstTokenBalance/secondTokenBalance + tokenQuant` lands as close as possible below `dynamicStore.getExchangeBalanceLimit()` (see the arithmetic at `ExchangeTransactionActuator.java:200-205`).
3. Assuming the attacker's transaction is ordered before V's (via fee bump, same-block flashbundle-style ordering, or witness cooperation), V's transaction now fails validation: `addExact(tokenBalance, tokenQuant) > balanceLimit` throws `"token balance must less than " + balanceLimit`.
4. Attacker later submits `ExchangeWithdrawContract` to withdraw the injected liquidity, repeating step 2 against future victim transactions.
