## Analog Found

### Title
Attached NEAR deposit is permanently lost when `rlp_execute()` fails validation before a promise is created - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is a `#[payable]`, externally callable entry point that accepts an attached NEAR deposit from any predecessor (not just the wallet owner or an authorized relayer) [1](#0-0) . The contract tracks this "caller deposit" via `CallerDeposit::new(&context)` specifically so it can be refunded if the downstream cross-contract call fails [2](#0-1) , but that refund logic is only wired into the success path (inside `rlp_execute_callback`) [3](#0-2) . When validation fails *before* a promise is ever created (i.e. `inner_rlp_execute` returns `Err`), the `caller_deposit` value computed inside `inner_rlp_execute` is simply dropped, and `rlp_execute` returns a non-panicking `ExecuteResponse` value with no compensating transfer [4](#0-3) .

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the attached deposit up front [5](#0-4) , then attempts to parse and validate the RLP transaction via `parse_rlp_tx_to_action`. Many validation failures are possible and return `Err` directly without ever using `caller_deposit`: `RelayerError::InvalidNonce`, `InvalidSender`, `InvalidTarget`, `InvalidChainId`, `InsufficientGas`, `TxParsing`/`InvalidBase64`, `AccountIdError` variants, `AccountNonceExhausted`, and every `UserError` variant (`ExcessYoctoNear`, `ValueTooLarge`, `UnknownFunctionSelector`, `InvalidAbiEncodedData`, `UnknownPublicKeyKind`, invalid keys, `UnsupportedAction`, etc.) [6](#0-5) [7](#0-6) .

Back in `rlp_execute`, the top-level match only special-cases `Err(Error::Relayer(_))` when the *signer* equals the current account (self-relaying), which triggers a ban-relayer promise but still does not refund any attached deposit; every other error (including all `Error::User` and most `Error::Relayer` cases) falls into `Err(e) => PromiseOrValue::Value(e.into())` [4](#0-3) . Because `near_bindgen` treats a returned `Value` (not a panic) as a successful function-call execution, the NEAR runtime does not generate an automatic deposit refund receipt for this receipt—refunds are only auto-generated by the runtime when the receipt execution itself fails [8](#0-7) . The deposit that had already been credited to the wallet contract's account balance when the `FunctionCall` receipt began executing therefore remains stuck there permanently, with no code path that ever moves it back to the caller.

This mirrors the reported Solidity issue exactly: a `payable` entry point that is meant to safely handle/track incoming value (analogous to `payback()`), but has a code path where value is accepted without a corresponding accounting/refund, leading to unrecoverable loss for the sender.

### Impact Explanation
Any unprivileged account — a relayer, a DEX, or any other contract/user — that calls `rlp_execute` on someone else's Wallet Contract with an attached NEAR deposit (e.g., to cover the deposit needed for a cross-contract call embedded in the emulated Ethereum transaction) will permanently lose that deposit whenever the transaction fails any of the numerous validation checks that occur prior to promise creation. This is a direct, unauthorized-value-loss bug reachable by a single external `FunctionCall` transaction/receipt with no participation from the wallet owner required.

### Likelihood Explanation
Likelihood is high: `rlp_execute` is the sole external entry point of every ETH-implicit account's Wallet Contract and is explicitly `#[payable]`, inviting deposits from third parties acting on behalf of the wallet owner (e.g., paying an NEP-141 `storage_deposit` fee, or a fee for the cross-contract action) [1](#0-0) . The set of failure conditions that skip the refund (bad nonce, wrong target, wrong chain id, insufficient gas, malformed RLP, oversized value, excess yocto-near, unknown selector, etc.) is large and easy to trigger unintentionally by any caller providing slightly incorrect parameters, or trivially triggered maliciously by a caller who wants to also grief the deposit source.

### Recommendation
In `rlp_execute`, when `inner_rlp_execute` returns any `Err` and a non-zero attached deposit was present from an external predecessor, issue a refund `Promise` (mirroring the logic already used in `rlp_execute_callback`'s `PromiseResult::Failed` branch) before returning the `ExecuteResponse`. Concretely, compute/propagate `CallerDeposit` out of `inner_rlp_execute`'s error path (or recompute it in `rlp_execute` from `env::attached_deposit()`/`env::predecessor_account_id()`) and always schedule a transfer back to `predecessor_account_id` for the full attached deposit whenever the function is about to return `PromiseOrValue::Value(...)` after a failure.

### Proof of Concept
1. Deploy/observe an ETH-implicit account `0xabc...` with the Wallet Contract, current `nonce = N`.
2. From any external account `attacker.near` (unprivileged, no relationship to the wallet), call:
   ```
   0xabc....rlp_execute(target, tx_bytes_b64) with attached_deposit = 5 NEAR
   ```
   where `tx_bytes_b64` encodes a validly-formed but incorrect Ethereum transaction — e.g. one signed with `nonce != N` (triggers `RelayerError::InvalidNonce`), or one whose `chain_id` doesn't match `CHAIN_ID` (triggers `RelayerError::InvalidChainId`), or one requesting `yocto_near >= MAX_YOCTO_NEAR` (triggers `UserError::ExcessYoctoNear`) [9](#0-8) .
3. `inner_rlp_execute` computes `caller_deposit = Some(CallerDeposit { account_id: attacker.near, yocto_near: 5 NEAR })` [5](#0-4)  but then returns `Err(Error::Relayer(RelayerError::InvalidNonce))` (or the User error) without ever using it.
4. `rlp_execute` falls into the generic `Err(e) => PromiseOrValue::Value(e.into())` branch, returning a normal (non-panicking) `ExecuteResponse{ success: false, ... }` [10](#0-9) .
5. The FunctionCall receipt succeeds from the runtime's perspective (no panic), so no automatic deposit-refund receipt is generated; the 5 NEAR remains permanently in the wallet contract's account balance and `attacker.near`'s deposit is unrecoverable.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
