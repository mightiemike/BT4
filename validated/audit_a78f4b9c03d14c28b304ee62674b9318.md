## Title
`TransactionOutput::ensure_match_transaction_info` never checks `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, letting chunk-executor replay/verification accept locally-computed state that diverges from the committed ledger root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the single invariant check used by state-sync's chunk executor and the `replay_on_archive`/`db-tool` replay-verify path to confirm that a locally re-executed (or applied) `TransactionOutput` matches the authenticated `TransactionInfo` fetched from a peer/backup and already proven against a signed `LedgerInfo`. It checks status, gas, the write-set hash (`state_change_hash`), and the event root hash, but — as the function's own comment documents — it deliberately skips `state_checkpoint_hash` (and the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields), which are exactly the fields that authenticate the post-execution *state* root committed into the transaction-accumulator leaf hash.

### Finding Description
`TransactionInfo` commits several hashes into the leaf that is chained into the transaction accumulator (whose root is embedded in the signed `LedgerInfo`): `transaction_hash`, `state_change_hash` (write-set hash), `event_root_hash`, and, when present, `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`. These state-checkpoint hashes are exactly the values produced independently by `DoStateCheckpoint`/`DoLedgerUpdate` (`execution/executor/src/workflow/do_ledger_update.rs:95-121`) from the locally-computed Sparse Merkle/Jellyfish Merkle state root, hot-state root and position-state root — i.e. they are the *only* on-chain-committed authentication of "the state after this transaction is X".

`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is the function used to compare a `TransactionOutput` (freshly computed by re-executing a transaction, or accepted as an applied output) against the trusted, proof-verified `TransactionInfo`. It explicitly:
```rust
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [1](#0-0) 

This comparator is used as the sole per-transaction integrity gate in two live, non-test code paths:

1. `execution/executor/src/chunk_executor/mod.rs::verify_execution` — the chunk executor's transaction-replayer path re-executes transactions from a backup/local DB and calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` to decide whether the replay matches the archived `TransactionInfo` before committing it as the canonical output for that version. [2](#0-1) 

2. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` — the "replay verify" tool that re-executes archived transactions against a target DB and uses `ensure_match_transaction_info` as the acceptance check for whether the re-executed output matches the archived `expected_txn_infos[idx]`. [3](#0-2) 

Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, if the locally re-executed state root (SMT/JMT root, hot-state root, or the newer "position state" root introduced by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) diverges from what is embedded in the archived, signature-proven `TransactionInfo` — due to a state-computation bug, a schema/format mismatch, a hot-state divergence, or a malicious/corrupted backup source feeding `write_sets`/`expected_txn_infos` independently (note `replay_on_archive` reads `expected_writeset`/`expected_txn_info` straight from the `BackupHandler`'s transaction iterator, not from a proof-verified accumulator range in that code path) — the mismatch is silently accepted. Contrast this with the analogous, complete check performed by `TransactionOutputListWithProof::verify` for state-sync's live-outputs path, which does check `write_set_hash == txn_info.state_change_hash()` but likewise has no state-checkpoint-hash verification at all in that struct (`types/src/transaction/mod.rs:2970-3019`), because `TransactionInfoListWithProof::verify` only authenticates that the `TransactionInfo` objects as a whole hash into the accumulator — it does not independently recompute or re-check the state root against locally derived state.

This is the same bug *class* as the external report: a validation routine that is supposed to fully bind a piece of data to an invariant but, by construction/comment, only checks a subset of the fields, leaving a documented, acknowledged gap that lets a specific kind of divergent value pass unnoticed.

### Impact Explanation
If the local state-root computation (state, hot-state, or the trading-native "position state" root) ever diverges from the value recorded in the historical/backup `TransactionInfo` — whether from a genuine state-computation bug, a backup/restore-path corruption, or a compromised/malicious backup source used for chunk replay — `ensure_match_transaction_info` will not detect it. The chunk executor's replay path (`verify_execution`) will treat the divergent output as verified and go on to commit the *archived* `write_set`/status via `remove_and_apply`, silently masking that the state root behind that commit no longer matches what a correctly executing node would produce. This is exactly the "authenticated proof/commitment accepted despite wrong underlying state" impact called out in the task's State-Integrity Gate: an accumulator leaf (`TransactionInfo`) can encode a state root that the comparator never revalidates, so replay/verify tooling and the chunk-executor's verify-and-replay flow report success even when durable ledger state is wrong. Because this only manifests when the checked-in comment's precondition (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state features enabled, or a corrupted backup) actually triggers a real divergence, I cannot independently confirm from static code alone that a concrete state-root divergence is currently reachable on mainnet configuration — the maintainers' own comment flags this as a known gap to close "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", implying it is not yet fully exploitable in the current default feature configuration.

### Likelihood Explanation
Low-to-moderate today: the gap is real and acknowledged in the code, but currently gated behind features (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that appear to be in-progress/not fully enabled on mainnet. It becomes a concrete integrity risk the moment those features are turned on, or in any deployment that runs `db-tool replay-on-archive` against an untrusted/corrupted backup, since neither of the two call sites revalidates the state-checkpoint hash before accepting a replayed/applied transaction as matching.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s locally computed state checkpoint hash(es) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` whenever the corresponding value(s) are present/derivable, and fail loudly (as with the other checks) on mismatch, before any code path is allowed to gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or rely on chunk-replay from backups as an integrity boundary. At minimum, gate/deny the "replay success" outcome in `replay_on_archive.rs` and `chunk_executor::verify_execution` when these hashes are present but unchecked.

### Proof of Concept
No standalone runnable PoC is provided: reaching a concrete state-root divergence requires either (a) enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state features and inducing a genuine local vs. archived state-root mismatch, or (b) supplying a corrupted backup dataset to `db-tool replay-on-archive`/chunk-executor replay so that `expected_txn_infos`/`write_sets` carry a state-checkpoint hash inconsistent with true post-execution state. The local code trace establishing the gap is:
- `types/src/transaction/mod.rs:2139-2204` (`ensure_match_transaction_info` — comment self-documents the missing checks)
- `execution/executor/src/chunk_executor/mod.rs:684-708` (`verify_execution` uses it as the sole replay-acceptance gate)
- `storage/db-tool/src/replay_on_archive.rs:392-405` (`execute_and_verify` uses it as the sole replay-verify gate)
- `execution/executor/src/workflow/do_ledger_update.rs:95-121` (shows `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are genuine, independently-computed state-root fields embedded in `TransactionInfo`, confirming they are meaningful commitments that the comparator omits).     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
