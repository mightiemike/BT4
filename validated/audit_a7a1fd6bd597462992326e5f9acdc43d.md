### Title
Unbounded single-threaded slot sweep in `sweep_slots_after_snapshot` causes disproportionate CPU cost and lock contention when the full-snapshot interval is large or full snapshots are delayed - (File: accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb::clean_accounts` gates zero-lamport account purging on the "latest full snapshot slot" to keep incremental snapshots correct, mirroring the report's theme of a mechanism whose correctness/cost depends on a periodic checkpoint arriving within an expected window. Whenever the full snapshot slot advances, `clean_accounts` invokes `sweep_slots_after_snapshot`, which iterates every single slot number between the last-swept full-snapshot slot and the new one, single-threaded, while holding the `shrink_candidate_slots` lock. The size of this gap is controlled by the user-configurable `--full-snapshot-interval-slots` and by however long full-snapshot generation is actually delayed — neither of which is bounded — so the cost of this "catch-up" scan grows unboundedly with the checkpoint interval, exactly like the reported blockhash-availability window growing unboundedly relative to a slow "checkpoint manager."

### Finding Description
`clean_accounts` calls `sweep_slots_after_snapshot(last_swept_full_snapshot_slot, latest_full_snapshot_slot)` whenever the full snapshot slot has advanced since the previous clean: [1](#0-0) 

`sweep_slots_after_snapshot` then loops `for slot in start..=latest_full_snapshot_slot`, doing a `get_slot_storage_entry` lookup (and potentially a purge or shrink-candidate insert) for **every** slot number in that range, all while holding `self.shrink_candidate_slots.lock()`: [2](#0-1) 

The number of slots swept equals the gap between the last full-snapshot slot processed and the newly observed one. This gap is driven by:
1. The configured `--full-snapshot-interval-slots`, which has no enforced maximum — the CLI only validates non-zero and merely warns if it exceeds `DEFAULT_SLOTS_PER_EPOCH`: [3](#0-2) 
2. Any real-world delay in actually producing a full snapshot (disk contention, packaging backlog, etc.), which is unbounded in practice.

Because the loop is O(gap) and performed synchronously inside `clean_accounts` (itself run periodically by `AccountsBackgroundService` or directly by the snapshot request handler), a large or delayed full-snapshot interval turns this "sweep" into a long, single-threaded operation that holds `shrink_candidate_slots.lock()` for its entire duration, blocking `shrink_candidate_slots()`'s access to the same lock and delaying subsequent clean/shrink cycles.

This is directly analogous to the reported bug class: a subsystem assumes a periodic checkpoint (the full snapshot slot advancing) occurs within a "reasonable" window, but nothing enforces or bounds that window, so if it is exceeded, the cost of catching up becomes disproportionate rather than the operation failing outright.

### Impact Explanation
The impact is a disproportionate, single-threaded CPU cost (and lock contention against `shrink_candidate_slots`) that scales with the number of slots elapsed since the last full-snapshot sweep, rather than with useful work performed (only slots that actually have storage entries do meaningful work; the loop still visits every slot number regardless). On a validator misconfigured with a very large `--full-snapshot-interval-slots`, or one that experiences delays in full snapshot generation, `clean_accounts` calls can stall behind this sweep, degrading the accounts-db background cleanup pipeline (clean/shrink) validator-wide.

### Likelihood Explanation
This is reachable by any operator who sets a large `--full-snapshot-interval-slots` (no upper bound enforced, only a log warning above `DEFAULT_SLOTS_PER_EPOCH`), or naturally whenever full-snapshot production is delayed relative to slot advancement in production operation — no attacker action or malicious input required, matching the "unprivileged/self-inflicted, no explicit protection" nature of the analog.

### Recommendation
Bound the work performed by `sweep_slots_after_snapshot` independent of the raw slot-number gap — e.g., only iterate slots that actually have storage entries (via the storage map's slot index) rather than every integer slot in `[start, latest_full_snapshot_slot]`, and avoid holding `shrink_candidate_slots.lock()` for the entire scan. Additionally, consider enforcing (not just warning about) a sane upper bound on `--full-snapshot-interval-slots` relative to an epoch, and document explicitly that the cost of the post-full-snapshot sweep in `clean_accounts` scales with the full-snapshot interval / delay.

### Proof of Concept
1. Configure a validator with a very large `--full-snapshot-interval-slots` (e.g., far beyond `DEFAULT_SLOTS_PER_EPOCH`), or simulate a full-snapshot generation delay so that `latest_full_snapshot_slot` jumps by a very large number of slots between two `clean_accounts` invocations.
2. Observe `clean_accounts` → `sweep_slots_after_snapshot` iterating `start..=latest_full_snapshot_slot`, i.e., a range whose size equals the slot gap, while holding `shrink_candidate_slots.lock()` per [4](#0-3) .
3. Measure the `zero_lamport_sweep_us` datapoint emitted by `clean_accounts` (`("zero_lamport_sweep_us", key_timings.zero_lamport_sweep_us, i64)`), which grows proportionally with the configured/actual full-snapshot gap, and observe contention on `shrink_candidate_slots()` during this window.

    /// Loop through slots in `[last_swept_full_snapshot_slot + 1, latest_full_snapshot_slot]` and
    /// re-examine each storage now that a full snapshot has advanced past its slot:
    /// 1) if it holds only tombstones, purge it directly; or
    /// 2) if its dead zero-lamport accounts made it shrinkable, add it to the shrink candidates.
    ///
    /// Advances `last_swept_full_snapshot_slot` to `latest_full_snapshot_slot` on completion.
    ///
    /// Returns the count of storages that were added to the shrink candidates set.
    fn sweep_slots_after_snapshot(
        &self,
        last_swept_full_snapshot_slot: Slot,
        latest_full_snapshot_slot: Slot,
    ) -> u64 {
        let start = last_swept_full_snapshot_slot.saturating_add(1);

        let mut added_to_shrink_count = 0;
        {
            // Held for the scan. Safe because the only paths that take this lock in production
            // validator code run in earlier/later phases of the same AccountsBackgroundService
            // iteration, never concurrently with clean_accounts.
            let mut shrink_candidates = self.shrink_candidate_slots.lock().unwrap();
            for slot in start..=latest_full_snapshot_slot {
                if let Some(store) = self.storage.get_slot_storage_entry(slot) {
                    if store.has_only_tombstones() {
                        // Now just contains tombstones and no live index entries: purge
                        self.purge_dead_slots_from_storage(
                            iter::once(&slot),
                            &self.clean_accounts_stats.purge_stats,
                        );
                    } else if self.is_shrinking_productive(&store)
                        && self.is_candidate_for_shrink(&store)
                        && shrink_candidates.insert(slot)
                    {
                        added_to_shrink_count += 1;
                    }
                }
            }
        }

        self.last_swept_full_snapshot_slot
            .store(latest_full_snapshot_slot, Ordering::Relaxed);
        added_to_shrink_count
    }
