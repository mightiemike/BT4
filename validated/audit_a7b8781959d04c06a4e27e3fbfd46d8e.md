Based on the investigation, I found a genuine local integrity gap that closely mirrors the external bug's pattern: a state-invariant check (`_checkBalances`) applied on some code paths but silently skipped on others. Here the analog is `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs`, which validates status, gas, write-set hash, and event-root hash against the authenticated `TransactionInfo`, but explicitly (per its own TODO comment) omits validating the state-checkpoint / hot-state-checkpoint / position-state-checkpoint hashes — the fields that actually summarize the post-execution global state Merkle root.

### Title
Replay-verification omits state-checkpoint root validation, allowing state-root divergence to go undetected - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs::verify_execution`, `aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that locally re-executed transaction outputs match the authenticated, on-chain `TransactionInfo` stored in the accumulator. It checks status, gas used, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that commit to the full post-execution state tree root, not just this transaction's own write set.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  performs four checks (status, gas, write-set hash, event root hash) and then has an explicit TODO acknowledging the gap: [2](#0-1) 

Because `write_set_hash` only commits to *this transaction's own* write operations, and `state_checkpoint_hash` commits to the *entire resulting global state Merkle tree* (computed periodically, e.g. at block checkpoints), the two are not redundant: a divergence introduced by an earlier transaction (e.g., an incorrect prior write, an aggregator/resource-group merge bug, or a hot-state/position-state promotion bug) can leave the current transaction's own write-set hash intact while the accumulated state tree root has already diverged. This is exactly the class of "committed state that differs from the correct VM result" that replay-verify tooling is meant to catch before a hard fork, and it is invoked at:
- `storage/db-tool/src/replay_on_archive.rs` line 392 [3](#0-2) 
- `execution/executor/src/chunk_executor/mod.rs::verify_execution` [4](#0-3) 

Both are used specifically to confirm that independent re-execution reproduces the authenticated on-chain result — the precise integrity invariant this bug class targets — yet neither path can detect a state-root divergence because the shared comparator never checks it.

### Impact Explanation
This affects the mainnet-facing "replay determinism" guarantee used ahead of protocol/hard-fork upgrades and for offline auditing of historical execution. If a VM or executor change silently alters resulting state (without changing the touched write set's own hash — e.g., an aggregator/resource-group squash bug, or a hot-state/position-state checkpoint computation bug) — `replay_on_archive` and `verify_execution` will both report success even though the locally computed state tree diverges from the state committed and signed by validators historically. This is a "hard-fork-only divergence during commit/replay/verification" going undetected, which is explicitly in scope, and could let a state-corrupting bug ship to mainnet undetected by the primary safety-net tooling designed to catch it.

### Likelihood Explanation
The gap is deterministic and always present — every invocation of `ensure_match_transaction_info` from these tools skips checkpoint-hash validation, not just under rare conditions. The likelihood of a *triggering* underlying VM/state bug is separate, but the detection gap itself is unconditional and already flagged by the code's own TODO as blocking the (upcoming, per the comment) `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed transaction info and the expected/authenticated `txn_info` whenever those fields are `Some` in either object (i.e., at checkpoint boundaries), returning an error on mismatch, mirroring the existing pattern used for `write_set_hash` and `event_root_hash`.

### Proof of Concept
1. Take a chunk of historical transactions ending in a block-epilogue/state-checkpoint transaction.
2. Replay them locally with a deliberately introduced discrepancy that does not change the checkpoint transaction's own write set (e.g., alter how an earlier transaction's resource-group/aggregator write is merged into the global state, such that the final full-state Merkle root differs, while the just-committed write set's hash for the checkpoint transaction remains identical).
3. Run `storage/db-tool/src/replay_on_archive.rs` (`Verifier::execute_and_verify`) or `chunk_executor::verify_execution` against the expected `TransactionInfo` list.
4. Observe `ensure_match_transaction_info` returns `Ok(())` despite the local `state_checkpoint_hash` differing from `txn_info.state_checkpoint_hash()`, because that comparison is never performed — confirming replay-verify reports false success on a genuine state-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
