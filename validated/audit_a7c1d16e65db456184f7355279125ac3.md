## Title
DeleteAccount transfers the account's balance to `beneficiary_id` without verifying it exists, permanently burning funds if it doesn't - (File: runtime/runtime/src/actions.rs)

## Summary
`action_delete_account` refunds the deleted account's remaining balance to `delete_account.beneficiary_id` by emitting a `Receipt::new_balance_refund`, with no validation that `beneficiary_id` refers to an existing (or even creatable) account. If the beneficiary account does not exist, the resulting refund receipt fails and the funds are permanently burnt rather than returned to anyone. This mirrors the reported class of bug ("no check for `paymentReceiver == address(0)`" causing lost funds) — here the unchecked destination is `beneficiary_id` instead of a Solidity payment-receiver address.

## Finding Description
When a `DeleteAccount` action executes, the runtime pays out the account's balance to the beneficiary as a special balance-refund receipt, without any existence check on `beneficiary_id`: [1](#0-0) 

The only validation ever performed on `beneficiary_id` is a syntactic account-id format check at transaction/receipt validation time — never an existence check: [2](#0-1) 

Balance-refund receipts are special "system" receipts (`predecessor_id == "system"`), and the runtime explicitly documents that a failed refund burns the funds instead of retrying or bouncing them further: [3](#0-2) 

This is implemented directly in the receipt-application path: for refund receipts (`predecessor_id().is_system()`), any execution failure adds the deposit to `other_burnt_amount` rather than generating any further refund: [4](#0-3) 

The actual failure mode for a transfer refund to a nonexistent account is confirmed by `check_account_existence`: a `Transfer` action targeting a nonexistent account only succeeds if implicit-account creation is allowed for the given receipt shape; refund receipts are explicitly excluded from that allowance, so a refund transfer to any nonexistent account (named or even implicit) fails with `AccountDoesNotExist`: [5](#0-4) 

This exact scenario — a refund to a missing account failing rather than creating it — is unit-tested and confirmed: [6](#0-5) 

And the test-suite comment for `DeleteAccount` explicitly acknowledges that the beneficiary must pre-exist, otherwise the balance would not reach it: [7](#0-6) [8](#0-7) 

Putting these together: any signer who submits a `DeleteAccount` action naming a `beneficiary_id` that does not currently exist (a typo, an already-deleted account, or an account that was never created) causes their entire remaining account balance to be minted into a refund receipt that then fails and is permanently burnt — with no path back to the user, the intended beneficiary, or anyone else.

## Impact Explanation
This causes unconditional, permanent loss of the deleted account's remaining native-token balance whenever `beneficiary_id` does not exist at execution time. Because `DeleteAccount` execution and its check of "does `beneficiary_id` exist" happen at receipt-processing time (not at transaction submission time), a beneficiary account that existed when the transaction was signed could be deleted before the `DeleteAccount` receipt executes, or a user could simply mistype/misremember an account id, unconditionally burning their balance. Given the amounts involved can be an account's entire balance, this is a direct value-loss vulnerability reachable by any ordinary transaction signer, not merely a resource/no-impact issue.

## Likelihood Explanation
Trivial to trigger: any account holder can submit a `DeleteAccount` action (self-deletion is the common case) specifying an arbitrary `beneficiary_id`. No special privileges, staking, or protocol version gating are required. It requires only that `beneficiary_id` not exist when the receipt is applied — easily caused by a typo or a race with another deletion.

## Recommendation
Before emitting the balance-refund receipt in `action_delete_account` (`runtime/runtime/src/actions.rs`), verify that `beneficiary_id` corresponds to an existing account (or reject/require pre-verified existence at validation time, similar to how the format check is done), and reject the `DeleteAccount` action (e.g., with a new `ActionErrorKind` such as `BeneficiaryAccountDoesNotExist`) if it does not exist, rather than relying on the balance ending up in a system refund receipt that silently burns tokens on failure.

## Proof of Concept
1. Alice creates account `bob.alice.near` and immediately deletes another arbitrary account, say `nonexistent.alice.near`, or funds an account and later deletes it with `beneficiary_id = "typo123.near"` which was never created.
2. Submit `SignedTransaction` with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "typo123.near".parse().unwrap() })` as demonstrated by the transaction builder: [9](#0-8) 
3. `action_delete_account` computes `account_balance = account_ref.amount()` and pushes `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`: [1](#0-0) 
4. When that refund receipt is applied, `check_account_existence` for the `Transfer` action rejects it with `AccountDoesNotExist` since `implicit_creation_allowed` excludes refund receipts: [5](#0-4) 
5. Because the receipt's predecessor is `system`, the failure path in `apply_action_receipt` adds the entire deposit to `other_burnt_amount` instead of refunding it anywhere: [4](#0-3) 
6. Net effect: Alice's account balance is deleted from her account and permanently burnt from total supply, benefiting nobody — matching the exact test assertion pattern already present in `refund_may_not_create_universal_account`: [10](#0-9)

    fn refund_may_not_create_universal_account() {
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],

            Balance::ZERO,
            Gas::from_teragas(1000),

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.

        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
