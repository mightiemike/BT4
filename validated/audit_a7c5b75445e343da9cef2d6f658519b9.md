## Analog Found

### Title
Malicious meta-transaction sender can invalidate a `DelegateAction` after signing but before the relayer's transaction is applied, burning the relayer's prepaid gas with no compensation - ([File: runtime/runtime/src/actions.rs])

### Summary
NEP-366 meta transactions let a relayer pay all gas/deposit costs for actions authored and signed off-chain by a user (the delegate `sender_id`), who submits the `SignedDelegateAction` to the relayer, which wraps and submits it as a transaction on-chain [1](#0-0) . Between the moment the user signs the `DelegateAction` and the moment the relayer's outer transaction is actually applied on the sender's shard, the sender fully controls their own access key/nonce and can unilaterally invalidate the signed delegate action (e.g. by deleting the signing key, or by consuming the key's nonce with another transaction), causing `validate_delegate_action_key` to reject it with `DelegateActionAccessKeyError` or `DelegateActionInvalidNonce` [2](#0-1) . This is the exact same bug class as the GMX report: an unprivileged party can cancel/invalidate a pending action right before the gas-paying executor (keeper/relayer) acts on it, so the executor's already-spent gas is wasted.

### Finding Description
The relayer purchases gas for the `DelegateAction` wrapper and all inner actions at transaction-conversion time on its own shard; this "send" cost and the delegate action's own exec fee are burnt unconditionally, as documented directly in the code:
```
// Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
// If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
// Gas is refunded to the signer, this is Relayer.
// ...
// Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.
``` [3](#0-2) 

When the wrapped receipt reaches the sender's shard, `apply_delegate_action` first verifies the signature and expiry, then calls `validate_delegate_action_key`, which looks up the access key by `public_key`/`sender_id` and checks the nonce [4](#0-3) . Because the sender fully controls this access key and nonce, they can:
- Delete the signing access key via `DeleteKey` → `DelegateActionAccessKeyError::AccessKeyNotFound` [5](#0-4) 
- Or submit any other transaction using the same key to bump its nonce past the signed `delegate_action.nonce` → `DelegateActionInvalidNonce` [6](#0-5) 

Either way, `apply_delegate_action` sets `result.result = Err(...)` and returns without generating the inner-action receipt [7](#0-6) . The exec fee for the delegate action itself, seeded unconditionally at the start of `apply_action` (`result.gas_used = exec_fees.gas; result.gas_burnt = exec_fees.gas;`), is burnt regardless of the validation outcome [8](#0-7) , and the SEND-phase fees for the wrapper were already non-refundably burnt on the relayer's shard at transaction-conversion time [9](#0-8) . There is no on-chain mechanism forcing a delay or giving the relayer any way to "lock in" the validity of the delegate action against a race by the sender — analogous to the missing cancellation delay for limit orders in the GMX report.

### Impact Explanation
A malicious meta-transaction sender can, at will, race and grief any relayer: sign a `DelegateAction`, hand it to the relayer, then immediately delete the signing key or spend its nonce with a cheap transaction of their own, right before the relayer's transaction lands. The relayer's prepaid SEND fees and the delegate-action EXEC fee are burnt with zero useful work performed and no compensation to the relayer — a pure gas-fee loss for the unprivileged gas-paying party, matching the "Loss of keeper funds" impact class in the source report. Because this can be repeated at negligible cost by the sender (their own key/nonce operations are cheap), it enables systematic griefing of relayer economics.

### Likelihood Explanation
Fully reachable by an ordinary user/attacker with a single transaction (`DeleteKey`, `AddKey`, or any other transaction using the signing access key) sent from their own account, requiring no privileged role, validator status, or protocol bug beyond normal transaction submission and timing/ordering variance across shards. The nearcore documentation itself acknowledges the underlying trust gap between relayer and user in the meta-transaction design [10](#0-9) , but the specific griefing vector (key deletion/nonce burn to nullify an already-signed, in-flight `DelegateAction`) imposes a concrete, unmitigated gas cost directly on the relayer with no defense at the protocol level.

### Recommendation
Consider adding a short "reveal/commit" delay or requiring the relayer to co-sign a freshness proof close to submission time, or let relayers register an expected-nonce/key-hash commitment that the runtime checks atomically at the same block height the relayer intended, reducing the window for this race. Alternatively, document (and clearly warn integrators) that relayers must independently re-verify the sender's access key/nonce state immediately before submission and should treat any observed delay as a griefing risk, similar to the GMX recommendation of introducing a minimum delay before a pending action can be invalidated.

### Proof of Concept
1. Alice creates access key `K` on her account and signs `DelegateAction { sender_id: Alice, actions: [...], nonce: N, public_key: K, ... }`, sending it off-chain to Relayer.
2. Relayer wraps it into a transaction and submits it, burning SEND fees at conversion time [9](#0-8) .
3. Before the relayer's transaction is applied on Alice's shard, Alice submits her own transaction using key `K` (e.g. a cheap `Transfer` with nonce `N`, or a `DeleteKey(K)`), which either bumps the access key's nonce past `N` or removes `K` entirely.
4. When the relayer's delegated receipt is later applied, `validate_delegate_action_key` fails with `DelegateActionInvalidNonce` or `DelegateActionAccessKeyError::AccessKeyNotFound` [11](#0-10) , and `apply_delegate_action` returns early without spawning the inner-action receipt [7](#0-6) .
5. The relayer's SEND-phase fees and the delegate action's EXEC fee remain burnt with no refund and no work performed for Alice, confirming the gas-griefing outcome.

fn validate_delegate_action_key(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    delegate_action: VersionedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let sender_id = delegate_action.sender_id();
    let public_key = delegate_action.public_key();
    // 'sender_id' account existence must be checked by a caller
    let mut access_key = match get_access_key(state_update, sender_id, public_key)? {
        Some(access_key) => access_key,
        None => {
            result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                InvalidAccessKeyError::AccessKeyNotFound {
                    account_id: sender_id.clone(),
                    public_key: public_key.clone().into(),
                },
            )
            .into());
            return Ok(());
        }
    };

    // A plain nonce advances the single access_key.nonce and forbids gas keys;
    // a gas key nonce advances one of the gas key's nonces selected by
    // nonce_index.
    let delegate_nonce = delegate_action.nonce();
    let (current_nonce, nonce_update) = match delegate_nonce {
        TransactionNonce::Nonce { .. } => {
            if access_key.gas_key_info().is_some() {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresNonGasKey,
                )
                .into());
                return Ok(());
            }
            (access_key.nonce, DelegateNonceUpdate::AccessKey)
        }
        TransactionNonce::GasKeyNonce { nonce_index, .. } => {
            let Some(gas_key_info) = access_key.gas_key_info() else {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {
                result.result = Err(ActionErrorKind::DelegateActionInvalidNonceIndex {
                    nonce_index,
                    num_nonces: gas_key_info.num_nonces,
                }
                .into());
                return Ok(());
            }
            // The index is range-checked above and gas keys initialize every
            // nonce row at creation, so a missing row is inconsistent state.
            let current_nonce =
                get_gas_key_nonce(state_update, sender_id, public_key, nonce_index)?.ok_or_else(
                    || {
                        StorageError::StorageInconsistentState(format!(
                            "gas key nonce row missing for {} {} at in-range index {nonce_index} (num_nonces {})",
                            sender_id, public_key, gas_key_info.num_nonces,
                        ))
                    },
                )?;
            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
        }
    };

    if delegate_nonce.nonce() <= current_nonce {
        result.result = Err(ActionErrorKind::DelegateActionInvalidNonce {
            delegate_nonce: delegate_nonce.nonce(),
            ak_nonce: current_nonce,
        }
        .into());
        return Ok(());
    }
