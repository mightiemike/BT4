### Title
`TOTAL_ENERGY_LIMIT` governance proposal updates the base energy limit without regenerating the derived `TotalEnergyTargetLimit`, causing stale adaptive-energy capacity thresholds - (File: `framework/src/main/java/org/tron/core/consensus/ProposalService.java`)

### Summary
This mirrors the Olympus `Operator::setReserveFactor` bug class: a governance-controlled base parameter is updated, but a *derived* threshold value that depends on it is not regenerated, leaving the system operating on a stale, inconsistent value until an unrelated event happens to refresh it.

### Finding Description
When the `TOTAL_ENERGY_LIMIT` proposal type is processed, `ProposalService.process` only saves the new base limit: [1](#0-0) 

By contrast, when `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` is changed, the code explicitly recomputes the dependent `TotalEnergyTargetLimit` from the (then-current) `TotalEnergyLimit`: [2](#0-1) 

and the same recomputation is performed once, at first activation, inside the `ALLOW_ADAPTIVE_ENERGY` branch: [3](#0-2) 

`TotalEnergyTargetLimit` is exactly analogous to the Olympus `RANGE` capacity threshold: it is the value that `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` compares against the rolling average energy usage every block to decide whether the network-wide *current* energy limit (`TotalEnergyCurrentLimit`) should contract or expand: [4](#0-3) 

Because `TOTAL_ENERGY_LIMIT` proposals do not call `saveTotalEnergyTargetLimit(getTotalEnergyLimit() / ratio)` after updating the base limit, `TotalEnergyTargetLimit` continues to reflect the *old* `TotalEnergyLimit` value (divided by the target ratio) until either `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` or the one-time `ALLOW_ADAPTIVE_ENERGY` activation happens to run again. If witnesses raise `TOTAL_ENERGY_LIMIT` significantly (e.g., to relieve network congestion), the stale, now much smaller `TotalEnergyTargetLimit` will make `totalEnergyAverageUsage > targetTotalEnergyLimit` trivially true, forcing `updateAdaptiveTotalEnergyLimit()` to perpetually contract `TotalEnergyCurrentLimit` via the `CONTRACT_RATE_NUMERATOR/DENOMINATOR` branch instead of expanding it — the opposite of governance's intent. Conversely, if `TOTAL_ENERGY_LIMIT` is lowered, the stale (now too-generous) target keeps the adaptive limit expanding well past what the new base limit's `upperBound = totalEnergyLimit * AdaptiveResourceLimitMultiplier` should allow it to represent as "normal" usage, deferring throttling.

This directly parallels the reported bug: a base parameter (`reserveFactor` / `TOTAL_ENERGY_LIMIT`) is changed by a privileged/governance action, but the dependent regeneration step (`_regenerate` / `saveTotalEnergyTargetLimit`) that other code paths perform explicitly is skipped for this particular setter.

### Impact Explanation
`TotalEnergyCurrentLimit` directly bounds `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`, which determine how much energy every frozen-TRX account is allowed to consume for TVM execution network-wide: [5](#0-4) 

A stuck-low or wrongly-inflated `TotalEnergyCurrentLimit` causes either unwarranted denial-of-service to legitimate contract calls (accounts unable to get energy despite frozen balance) or an inconsistency between intended and actual resource accounting network-wide, affecting all nodes identically (so it does not cause a consensus fork, but it is a protocol-level resource-accounting correctness bug reachable purely through normal governance parameter changes).

### Likelihood Explanation
`TOTAL_ENERGY_LIMIT` is a standard, frequently-adjusted witness-approved proposal (used, historically, to raise network capacity). Any time it is changed while `ALLOW_ADAPTIVE_ENERGY` is already enabled (the current mainnet default) and without also/immediately re-proposing `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO`, the described mismatch occurs. This is a realistic, easily triggered operational scenario, not a contrived edge case.

### Recommendation
In the `TOTAL_ENERGY_LIMIT` case of `ProposalService.process`, after saving the new limit, also recompute and save the dependent `TotalEnergyTargetLimit` using the current `AdaptiveResourceLimitTargetRatio`, mirroring the logic already used in the `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` and `ALLOW_ADAPTIVE_ENERGY` branches:
```java
case TOTAL_ENERGY_LIMIT: {
  manager.getDynamicPropertiesStore().saveTotalEnergyLimit(entry.getValue());
  long ratio = manager.getDynamicPropertiesStore().getAdaptiveResourceLimitTargetRatio();
  manager.getDynamicPropertiesStore().saveTotalEnergyTargetLimit(entry.getValue() / ratio);
  break;
}
```

### Proof of Concept
1. Assume `ALLOW_ADAPTIVE_ENERGY = 1` and `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` already set (target ratio fixed at, e.g., 2880), giving `TotalEnergyTargetLimit = oldTotalEnergyLimit / 2880`.
2. Witnesses pass a `TOTAL_ENERGY_LIMIT` proposal that significantly raises the base limit (e.g., 5x) via `ProposalService.process`, hitting the code at lines 111-114, which calls only `saveTotalEnergyLimit`.
3. `TotalEnergyTargetLimit` is not updated, so it still equals `oldTotalEnergyLimit / 2880` — five times smaller than what it should be relative to the new base limit.
4. On the next block, `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` runs; with normal network usage now easily exceeding the stale, too-small `targetTotalEnergyLimit`, it takes the `CONTRACT_RATE_NUMERATOR/DENOMINATOR` branch every cycle, continually shrinking `TotalEnergyCurrentLimit` instead of allowing it to grow toward the new, larger `upperBound`.
5. Result: the network-wide energy limit stays contracted despite governance's explicit intent to raise capacity, until a subsequent `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` proposal happens to correct `TotalEnergyTargetLimit`.

  public void updateAdaptiveTotalEnergyLimit() {
    long totalEnergyAverageUsage = dynamicPropertiesStore
        .getTotalEnergyAverageUsage();
    long targetTotalEnergyLimit = dynamicPropertiesStore.getTotalEnergyTargetLimit();
    long totalEnergyCurrentLimit = dynamicPropertiesStore
        .getTotalEnergyCurrentLimit();
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyLimit();

    long result;
    if (totalEnergyAverageUsage > targetTotalEnergyLimit) {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_DENOMINATOR);
    } else {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.EXPAND_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.EXPAND_RATE_DENOMINATOR);
    }
    long upperBound = hardenCalculation()
        ? BigInteger.valueOf(totalEnergyLimit).multiply(BigInteger.valueOf(
            dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier())).longValueExact()
        : totalEnergyLimit * dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier();
    result = min(max(result, totalEnergyLimit, this.disableJavaLangMath()),
        upperBound, this.disableJavaLangMath());

    dynamicPropertiesStore.saveTotalEnergyCurrentLimit(result);
    logger.debug("Adjust totalEnergyCurrentLimit, old: {}, new: {}.",
        totalEnergyCurrentLimit, result);
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimitV2(long frozeBalance) {
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (totalEnergyWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV2(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    double energyWeight = (double) frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
