### Title
Legacy `GasPrice` query returns a stale/mismatched median gas price (from all-time votes) that diverges from the actually-applied EVM oracle price used for outbound fee accounting - (File: `x/uexecutor/keeper/chain_meta.go`)

### Summary
This is a genuine analog to the report's core bug class ("stale/mismatched price kept forever while a fresher on-chain value exists, opening arbitrage/fee-mispricing"), but with a caveat: I could not fully verify that the diverged value is consumed by an unprivileged-user-reachable fund-moving code path before running out of investigation budget, so this should be treated as a **medium-confidence, partially-verified** finding rather than a fully proven exploit chain.

### Finding Description
`VoteChainMeta` maintains two different "median" computations over the same `ChainMeta` entry:

1. The value actually pushed on-chain via `CallUniversalCoreSetChainMeta` (the price `UniversalCore.gasPriceByChainNamespace` uses for real fee accounting, e.g. in `GetOutboundTxGasAndFees`) is `medianPrice`, computed **only over `fresh` votes** (votes stamped within `chainMetaVoteStalenessSeconds` = 300s): [1](#0-0) [2](#0-1) 

2. `entry.MedianIndex`, stored on the `ChainMeta` record and returned by the `GasPrice`/`AllGasPrices` gRPC queries, is computed over **the full, unfiltered `entry.Prices` slice** (including stale votes that were excluded from the EVM update): [3](#0-2) 

The integration test explicitly documents this divergence and works around it by reading the EVM contract directly instead of trusting the query response: [4](#0-3) 

The `GasPrice` query server (`x/uexecutor/keeper/query_server.go`, `chainMetaToGasPrice`) exposes `Prices[MedianIndex]` from this same full/stale slice as "the" gas price for a chain to any external caller of the gRPC/REST query: [5](#0-4) 

This is structurally identical to the report's core complaint: a subsystem computes a "safe"/"canonical" price for one purpose (on-chain fee application via `min`/median over fresh data) while a different, staler value keeps being surfaced elsewhere (`lastGoodPrice` kept "forever" in `CompositePriceFeed._fetchPriceETHUSDxCanonical`), creating a gap between the price actually enforced on-chain and the price an external actor observes/relies on.

### Impact Explanation
If any user-reachable, fund-affecting logic (e.g., relayer fee estimation, gasless-admission fee thresholds, or client-side gas-price display used to decide transaction parameters) trusts the `GasPrice`/`AllGasPrices` query response instead of the EVM-applied value, it could compute an outbound gas fee/refund expectation that diverges from what `UniversalCore.getOutboundTxGasAndFees` actually charges, potentially causing under/over-refunds in `applyGasRefund` (`x/uexecutor/keeper/outbound.go`) or mispriced expectations for gasless admission. **I was not able to confirm, within the tool budget, that any unprivileged-user-reachable code path (as opposed to internal relayer/CLI-only tooling) actually consumes the divergent `MedianIndex`/`Prices` field for a fund-moving decision** — the only confirmed on-chain fee-accounting caller (`GetOutboundTxGasAndFees` / `applyGasRefund`) reads gas price from the EVM `UniversalCore` contract directly, not from this query.

### Likelihood Explanation
The divergence itself is proven directly by the codebase's own integration test comment ("MedianIndex on the stored entry reflects the full-slice median, so we must query the contract directly for the actually-applied value"), so the code-level bug is real and self-acknowledged. Whether it is *exploitable* for unauthorized fund impact depends on unverified downstream consumers of the `GasPrice` query.

### Recommendation
Compute and store `MedianIndex` (and/or a `Prices`/`ChainHeights` view) from the same `fresh` vote pool used for the EVM write, so that the legacy `GasPrice` query never surfaces a value that has already been superseded and excluded from the actually-applied oracle price. Alternatively, deprecate the query in favor of one that reads the EVM-applied value directly, removing the two-sources-of-truth pattern that caused the original Liquity-class bug.

### Proof of Concept
Not independently reproduced beyond the existing integration test evidence (`test/integration/uexecutor/vote_chain_meta_test.go:221-263`), which already demonstrates the divergence between `stored.MedianIndex`/`Prices` and the EVM-applied median under a stale-vote scenario (3 validators vote, one goes stale, only the fresh vote's price is applied on-chain while the full-slice median differs).
