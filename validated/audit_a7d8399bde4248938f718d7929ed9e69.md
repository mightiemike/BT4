### Title
Wall-clock-based L1 handler cancellation timelock check enables honest-node validation divergence - (File: crates/apollo_l1_events/src/l1_events_provider.rs, crates/apollo_l1_events/src/transaction_manager.rs, crates/apollo_time/src/time.rs)

### Summary
The `L1EventsProvider::validate` path uses each node's own local wall-clock time (`self.clock.unix_now()`, backed by `chrono::Utc::now()`) rather than a consensus-agreed reference (e.g., block timestamp) to decide whether a L1-handler transaction's cancellation timelock has expired. This is directly analogous to the reported Timelock `GRACE_PERIOD`/`eta` staleness check being evaluated against `block.timestamp`, which can diverge across observers — except here the divergence is across sequencer nodes' independent local clocks, not miner-manipulated block time.

### Finding Description
`validate_tx` in `crates/apollo_l1_events/src/transaction_manager.rs` calls `record.update_time_based_state(unix_now, policy)` where `unix_now` is passed in from `L1EventsProvider::validate` as `self.clock.unix_now()`: [1](#0-0) 

`unix_now` is derived purely from the node's local wall clock via `DefaultClock`, which wraps `chrono::Utc::now()` — a per-machine value with no consensus guarantee of agreement across nodes (clock drift, NTP misconfiguration, VM clock skew, etc.): [2](#0-1) 

The state transition itself is a hard boundary check with no tolerance/margin: [3](#0-2) 

```
let is_cancellation_timelock_passed =
    unix_now >= *requested_at.saturating_add(cancellation_timelock);
```

Because each validating node evaluates this boundary against its own local clock rather than a value all nodes are guaranteed to agree on, two honest nodes validating the exact same proposal at nearly the same real time can compute different `ValidationStatus` results (`Validated` vs `Invalid(CancelledOnL2)`) for the same `tx_hash` if their local clocks straddle the `requested_at + cancellation_timelock` boundary. This is reachable entirely by an unprivileged L1 message sender: they control both `l1_handler_tx` submission and the timing of the `TransactionCancellationStarted` request, and can deliberately submit a cancellation such that, by the time the transaction is proposed/validated on L2, different nodes' clocks land on opposite sides of the timelock boundary (a matter of node clock skew of even a fraction of a second, not requiring any large attack window).

### Impact Explanation
When a proposer node's clock places a transaction as still valid (or already cancelled) while some validator nodes' clocks disagree, the `TxProv::validate` call in the L1-handler validation phase (see `docs/diagrams/06-l1-handler-flow.md`) will return different results across nodes: [4](#0-3) 

This causes honest-node divergence in block validation outcomes for the identical proposal: a subset of validators will accept the block (transaction still "Validated") while others reject it ("Fail block validation" per `CancelledOnL2`). Depending on which side has quorum, this can either stall consensus on legitimate proposals (network unable to confirm new blocks/transactions) repeatedly around the timelock boundary, or allow inconsistent decisions about whether an L1 handler transaction is includable, undermining the integrity of the timelock-based cancellation guarantee.

### Likelihood Explanation
The condition requires clock skew between the proposer and some validators of only the width of network/processing latency around a caller-chosen `cancellation_timelock` boundary — the attacker (any L1 message sender) fully controls the cancellation request timing and thus can aim the boundary at will. This does not require a malicious operator, proposer, or peer — only an ordinary L1 message sender exploiting normal clock skew that exists across independently operated nodes.

### Recommendation
Do not gate consensus-relevant, cross-node-agreed validity decisions (like whether an L1 handler cancellation timelock has expired) on each node's local wall clock. Instead, derive `unix_now` from a consensus-committed value (e.g., the block timestamp being built/validated, or `current_height`'s committed L1/L2 timestamp) so all honest nodes evaluate the exact same boundary condition. If wall-clock time must be used operationally, add an explicit tolerance window and ensure the check is deterministic given the block's agreed-upon fields, not `Instant`/`chrono::Utc::now()`.

### Proof of Concept
1. An L1 sender sends a message to L2, creating an `L1HandlerTransaction` tracked by `L1EventsProvider`/`TransactionManager` (see `add_events`, `Event::L1HandlerTransaction` handling): [5](#0-4) 
2. The same sender issues an L1 cancellation request (`TransactionCancellationStarted`) at a self-chosen `cancellation_request_timestamp`: [6](#0-5) 
3. As the network approaches `requested_at + l1_handler_cancellation_timelock_seconds`, the proposer node (using its local clock) includes the tx as still valid in a proposal while some validators (whose local clocks are slightly ahead) independently compute `is_cancellation_timelock_passed == true` and reject the proposal as invalid via `validate_tx` returning `CancelledOnL2`, exactly the boundary behavior exercised in the existing test `validate_tx_cancellation_requested_validated_then_expired_returns_cancelled`, which demonstrates that validation result flips purely based on the clock value passed at call time: [7](#0-6) 
4. Because production nodes use `DefaultClock` (`chrono::Utc::now()`) rather than a shared/consensus clock, this divergence can occur naturally across the validator set without any single malicious actor beyond the ordinary L1 sender choosing timing, resulting in honest-node disagreement on block validity around the timelock boundary.

        &mut self,
        tx_hash: TransactionHash,
        height: BlockNumber,
    ) -> L1EventsProviderResult<ValidationStatus> {
        if self.state.is_uninitialized() {
            return Err(L1EventsProviderError::Uninitialized);
        }

        self.check_height_with_error(height)?;
        match self.state {
            ProviderState::Validate => {
                Ok(self.tx_manager.validate_tx(tx_hash, self.clock.unix_now()))
            }
            _ => Err(L1EventsProviderError::UnexpectedProviderState {
                expected: ProviderState::Validate,
                found: self.state,
            }),
        }
    }

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

#[test]
fn validate_tx_cancellation_requested_validated_then_expired_returns_cancelled() {
    // Setup.
    let tx_1 = l1_handler(1);
    let clock = Arc::new(FakeClock::new(5));
    let mut l1_events_provider = L1EventsProviderContentBuilder::new()
        .with_clock(clock.clone())
        .with_nonzero_timelock_setup()
        .with_cancel_requested_txs([tx_1.clone()])
        .with_state(ProviderState::Validate)
        .build_into_l1_provider();

    // Test.

    // Should be validatable before expiry,
    let status =
        l1_events_provider.validate(tx_1.tx_hash, l1_events_provider.current_height).unwrap();
    assert_eq!(status, ValidationStatus::Validated);
    // Now, advance time past expiry and validate again,
    // This tests the edge case: a tx can be validatable before expiry, but if validated again after
    // expiry, it should return the cancellation error.
    clock.advance(Duration::from_secs(
        l1_events_provider.config.l1_handler_cancellation_timelock_seconds.as_secs(),
    ));
    let status2 =
        l1_events_provider.validate(tx_1.tx_hash, l1_events_provider.current_height).unwrap();
    assert_eq!(status2, InvalidValidationStatus::CancelledOnL2.into());
}
