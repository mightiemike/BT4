### Title
`citrea_network_to_chain_id` maps `Network::Nightly` and `Network::TestNetworkWithForks` to the same chain id (5665), enabling cross-network method-id upgrade replay - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`citrea_network_to_chain_id` returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`. Since `run_l1_block`'s only network-binding check for `DataOnDa::BatchProofMethodId` is `circuit_chain_id == body.chain_id`, a council-signed method-id body created for one of these networks is accepted verbatim by a full node running the other network.

### Finding Description
The intended binding is: for all `n1 != n2` in `Network`, `citrea_network_to_chain_id(n1) != citrea_network_to_chain_id(n2)`. This binding is violated: `citrea_network_to_chain_id(Network::Nightly) == citrea_network_to_chain_id(Network::TestNetworkWithForks) == 5665` [2](#0-1) .

In `run_l1_block`, when a `DataOnDa::BatchProofMethodId` blob is encountered, the circuit computes `circuit_chain_id = citrea_network_to_chain_id(network)` and only proceeds to verify council signatures and insert the new method id if `circuit_chain_id == batch_proof_method_id.body.chain_id` [3](#0-2) . The message that the council signs, `body.serialize()`, embeds `chain_id` but not any other network-distinguishing tag, and `verify_method_id_security_council` only checks ECDSA signatures against the message bytes and pubkey set — it has no independent knowledge of which `Network` variant is running [4](#0-3) .

Because both networks resolve to chain id 5665, a `BatchProofMethodIdBody { chain_id: 5665, .. }` signed by the 5-member council for a Nightly deployment passes the exact same equality check, and the exact same signature verification (since the council keyset is shared per the stated precondition), on a `TestNetworkWithForks` node. `BatchProofMethodIdAccessor::insert` then applies the upgrade unconditionally once these two gates pass [5](#0-4) .

### Impact Explanation
An unauthorized (for that specific network) but validly-signed batch-proof method-id upgrade is accepted onto a `TestNetworkWithForks` node's light-client JMT state, changing which zkVM method id is trusted to verify future batch proofs at a given L2 activation height. This is a "method-id upgrade accepted that was never authorised" for the receiving network, matching the stated Critical impact category. Since this is deterministic circuit logic (not a signature/key compromise), it is reproducible on every node/prover running `TestNetworkWithForks` (or any future network sharing the constant) for every replayed Nightly-signed body, and vice versa.

### Likelihood Explanation
Exploitation requires only that the same 5-of-5 council keys are configured for both `Nightly` and `TestNetworkWithForks` — a realistic staging/testnet key-reuse scenario explicitly named as a precondition, not a key compromise (the keys are legitimately held by the council, just reused across two logically distinct network configs). No majority hashrate, TLS interception, or code execution privilege is needed; an attacker merely needs to have observed or obtained one legitimately-published, correctly-signed `BatchProofMethodId` inscription (e.g., a real Nightly upgrade broadcast on Bitcoin) and rebroadcast/replay the identical bytes as a DA inscription targeting a `TestNetworkWithForks`-configured node. This is purely a code-level chain-id collision, not a config error by the operator, and is not excluded by the out-of-scope rules (not a mock, test file, or build artifact).

### Recommendation
Give every `Network` variant a distinct chain id in `citrea_network_to_chain_id` (e.g., assign `TestNetworkWithForks` its own unique constant instead of reusing `5665`), and add a compile-time or unit-test assertion enumerating all variants to guarantee uniqueness so this cannot regress silently when new network variants are added.

### Proof of Concept
```rust
// crates/light-client-prover/src/circuit/mod.rs (or a new test module)
use sov_rollup_interface::Network;
use crate::circuit::citrea_network_to_chain_id;

#[test]
fn chain_ids_must_be_unique_per_network() {
    let variants = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];
    for i in 0..variants.len() {
        for j in (i + 1)..variants.len() {
            assert_ne!(
                citrea_network_to_chain_id(variants[i]),
                citrea_network_to_chain_id(variants[j]),
                "chain_id collision between {:?} and {:?}",
                variants[i],
                variants[j]
            );
        }
    }
}
```
This test currently fails because `citrea_network_to_chain_id(Network::Nightly) == citrea_network_to_chain_id(Network::TestNetworkWithForks) == 5665`, directly demonstrating the collision described above.
