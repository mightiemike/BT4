### Title
Deeply-nested JSON-RPC payload causes unbounded recursion / stack exhaustion in `axum::Json<Message>` deserialization - ([File: chain/jsonrpc/src/lib.rs])

### Summary
The JSON-RPC `/` endpoint deserializes the request body directly into `Message` (a `#[serde(untagged)]` enum whose `Request`/`Notification`/`Batch` variants carry a raw `serde_json::Value` for `params`) via the axum `Json<Message>` extractor. `serde_json`'s `Value`/enum deserialization is a classic recursive-descent parser with no built-in depth limit: each `[` or `{` byte in the body descends one more stack frame. The only guard in front of this parser is a body-size limit (`RequestBodyLimitLayer::new(limits_config.json_payload_max_size)`), which bounds total bytes but not nesting depth — a payload consisting almost entirely of `[` characters (2 bytes per nesting level, e.g. `[[[[[...]]]]]`) can reach extremely deep nesting well within any reasonable size cap, exactly analogous to the Go `go/parser` stack-exhaustion bug (deeply nested literals overflow the parser's call stack).

### Finding Description
`rpc_handler()` is registered as the POST handler for `/` and takes the body straight as `Json<Message>`: [1](#0-0) 

`Message` is defined as an untagged enum wrapping `Request { params: Value, .. }`, `Notification`, and `Batch(Vec<Message>)`: [2](#0-1) 

The only middleware protecting this route is CORS and a byte-size body limit: [3](#0-2) 

`serde_json`'s `Value` deserializer recurses once per array/object nesting level with no depth cap, and `Message`'s `Batch(Vec<Message>)` variant adds further recursive enum descent. Unlike the borsh-based protocol layer, which has explicit anti-recursion protections (e.g. `NonDelegateAction`'s custom `deserialize_reader` specifically added "to avoid the recursion when Action/DelegateAction is deserialized" — [4](#0-3) ), no equivalent depth guard exists for the JSON path that every RPC caller reaches before any application-level validation runs.

### Impact Explanation
A stack overflow in Rust is not a catchable `panic!` — the runtime aborts the process on stack-guard-page violation. Because the JSON-RPC server and the node's core actors (`ClientActor`, `ViewClientActor`, `RpcHandlerActor`) run in the same process, an unauthenticated RPC caller can send one small, deeply-nested JSON body to `/` and abort the entire node process, not merely fail the request. This is a transaction/RPC-triggered halt reachable by any anonymous network caller with no authentication, no stake, and no prior state — a low-cost, high-impact denial of service against validators and RPC nodes alike.

### Likelihood Explanation
High. The `/` endpoint is public, unauthenticated, and specifically designed to accept arbitrary caller-supplied JSON (`params: Value`). No legitimate use case requires deep nesting, so no existing validation intercepts it before `serde_json` recurses. Constructing the payload is trivial (a string of `[` characters within the configured byte-size limit) and requires no protocol knowledge beyond basic HTTP.

### Recommendation
- Deserialize the request body with a `serde_json::Deserializer` configured with `.disable_recursion_limit()` disabled (i.e., keep/enforce a strict recursion limit) or explicitly set `serde_json`'s recursion limit low enough to fit comfortably within the thread stack, and reject payloads exceeding it before full deserialization.
- Alternatively, validate/reject deeply nested JSON structurally (max nesting depth check) prior to invoking `serde_json::from_slice`/`Json<Message>` extraction, or run request deserialization in a context with a guaranteed larger, dedicated stack that can safely fail without crashing the whole process.
- Apply the same nesting-depth guard to the Rosetta RPC server (`chain/rosetta-rpc/src/lib.rs`), which uses the same `axum::Json` extraction pattern.

### Proof of Concept
```
POST / HTTP/1.1
Host: <node>:3030
Content-Type: application/json
Content-Length: <N>

{"jsonrpc":"2.0","method":"status","id":1,"params": [[[[[[[[[[[[[[[[[[[[ ... (repeated to depth of several hundred thousand, within json_payload_max_size) ... ]]]]]]]]]]]]]]]]]]]] }
```
Sending this to the node's JSON-RPC port causes `serde_json`'s recursive descent parser (invoked via `Json<Message>` in `rpc_handler`) to overflow the worker thread's stack, aborting the process.

**Note on verification limits:** I was unable to confirm the exact configured default value of `json_payload_max_size` (`RpcLimitsConfig`) within the available context — the grep matches in `chain/jsonrpc/src/lib.rs` and example config files were not fully inspected due to the tool-call budget running out. This value determines exactly how deep the nesting can go for a given body-size cap, but even a modest cap (single-digit MB, as documented at "request body size limit (default 10MB)" in `chain/jsonrpc/RPC_ARCHITECTURE.md`) is more than sufficient to reach a nesting depth that exhausts a typical 8 MB thread stack, since each nesting level costs only ~2 bytes of payload versus one stack frame.

/// This struct is needed to avoid the recursion when Action/DelegateAction is deserialized.
