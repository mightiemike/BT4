### Title
Owner-Permission Threshold Reduction Enables Single-Signer Takeover of Multi-Sig Accounts - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
java-tron's multi-signature account model (`AccountPermissionUpdateContract` / `AccountPermissionUpdateActuator`) allows any owner-permission update that satisfies only the *current* threshold, without comparing the new threshold/weight distribution against the previous one. This reproduces the exact "threshold conflicts with removing controllers" bug class from the external report: a controller who obtains a co-signed threshold-lowering transaction can subsequently use their own reduced-threshold weight to unilaterally strip other controllers from the account, capturing full control.

### Finding Description
An account's owner permission is a weighted multi-sig: a list of `Key{address, weight}` entries plus a `threshold` [1](#0-0) . Any change to this permission (adding/removing keys, changing weights, or changing the threshold) is made via a single `AccountPermissionUpdateContract`, whose `validate()`/`checkPermission()` only enforces that the *new* permission's summed key weights are `>= newThreshold` — it never compares the new threshold or weight distribution to the *old* one [2](#0-1) . The actuator's `execute()` then blindly overwrites the account's owner permission with whatever was supplied [3](#0-2) .

Critically, whether a transaction is authorized to execute is decided by `TransactionCapsule.validateSignature`, which always checks the signatures against the permission that exists on-chain **at the time the transaction is processed** (i.e., the current threshold), not the permission that existed when the transaction was signed [4](#0-3) . `checkWeight` simply sums the weights of valid signers and compares to `permission.getThreshold()` [5](#0-4) .

This reproduces the report's attack precisely:
1. Owner permission: `A(weight=50)`, `B(weight=50)`, `threshold=100` (2-of-2 required).
2. B obtains A's signature on a transaction TX1 that only lowers `threshold` to 50 (keys unchanged) — framed as an innocuous adjustment. TX1 requires weight ≥ 100, satisfied jointly by A + B, and is confirmed on-chain.
3. Owner permission is now `A(50)`, `B(50)`, `threshold=50`.
4. B alone crafts and signs TX2, another `AccountPermissionUpdateContract`, setting owner permission to `keys=[B(50)]`, `threshold=50`. TX2 requires weight ≥ 50, which B's own signature satisfies alone — `validateSignature` accepts it since it only checks against the *current* (already-lowered) threshold.
5. TX2 executes via `AccountCapsule.updatePermissions`, fully removing A from the account [6](#0-5) .

B has now captured sole control of the account using only one co-signed "harmless" threshold-lowering transaction plus one self-signed follow-up, exactly mirroring the "decrease Threshold then remove controller in two steps" exploit described in the report.

### Impact Explanation
This allows any co-controller of a TRON multi-sig account to permanently and unilaterally seize full control of the account (owner permission), removing all other controllers, once they can get any single threshold-lowering signature from another party. Given TRON's owner permission also gates changes to the witness and active permissions, and controls the account's funds and delegated resources, this is a high-impact account/asset takeover.

### Likelihood Explanation
Medium: it requires a specific weight configuration (the remaining attacker's own weight must be ≥ the new threshold after reduction) and requires social-engineering at least one other controller into co-signing what looks like an innocuous threshold change. This is realistic in real multi-sig setups where controllers periodically adjust thresholds (e.g., to add members, or lower friction), and the reduction and removal do not need to be broadcast together — they can be separated by any amount of time.

### Recommendation
When validating an `AccountPermissionUpdateContract`, compare the new owner permission's threshold/weight distribution against the currently stored one, and reject changes where a single existing key (or any weight-subset smaller than the old threshold) would newly satisfy the updated threshold. Alternatively, require that any permission update reducing `threshold` cannot be combined, even across multiple transactions, with removal or weight-reduction of keys unless re-authorized under the original (higher) threshold — e.g., by imposing a time-lock/delay between a threshold reduction and any subsequent permission change to the same permission, or by requiring the *original* threshold to still be satisfied whenever weights held by any previously-authorized key are decreased or removed within some cooldown window following a threshold reduction.

### Proof of Concept
1. Create account `X` with owner permission `keys=[A:50, B:50]`, `threshold=100`.
2. A signs `AccountPermissionUpdateContract` TX1 (owner permission `keys=[A:50,B:50]`, `threshold=50`); B co-signs and broadcasts TX1. Confirm `validateSignature` accepts it (weight 100 ≥ old threshold 100) via `TransactionCapsule.checkWeight` [5](#0-4) .
3. B alone signs and broadcasts TX2: `AccountPermissionUpdateContract` setting owner permission to `keys=[B:50]`, `threshold=50`.
4. Observe `AccountPermissionUpdateActuator.validate()` accepts TX2 because `weightSum(50) >= threshold(50)` [7](#0-6) , and `validateSignature` accepts TX2 because B's weight (50) meets the current (already-lowered) threshold (50).
5. `execute()` applies `updatePermissions`, and account `X`'s owner permission now contains only `B` — A has been unilaterally and irreversibly removed.

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
