This confirms the index-generation-then-verify-then-clean ordering: `generate_index` dedups only *duplicate* pubkeys across slots (via `populate_and_retrieve_duplicate_keys_from_startup` / `unique_pubkeys_by_bin`), leaving exactly one (possibly zero-lamport) index entry per historical pubkey, and `verify_snapshot_bank` runs `verify_accounts` (→ `calculate_accounts_lt_hash_at_startup_from_index`) *before* `clean_accounts`.

### Title
Startup accounts lt-hash verification cost scales with total historical (churned) accounts, not final live-account count - ([File: `runtime/src/bank.rs`, `accounts-db/src/accounts_db.rs`])

### Summary
`Bank::verify_snapshot_bank` calls `verify_accounts` (which invokes `AccountsDb::calculate_accounts_lt_hash_at_startup_from_index`) *before* it calls `clean_accounts`. Because the accounts index built by `generate_index` retains one entry per unique pubkey ever rooted (only true intra-pubkey *duplicates* across slots are collapsed, not zero-lamport/dead entries), an attacker who churns through many short-lived accounts before a snapshot slot forces the lt-hash computation to iterate and perform an index lookup for every dead pubkey, even though its contribution to the hash is ultimately skipped.

### Finding Description
`AccountsDb::generate_index` rebuilds `accounts_index.account_maps` from the snapshot's storages, and only removes *duplicate* prior-slot versions of the same pubkey via `populate_and_retrieve_duplicate_keys_from_startup` / `mark_obsolete_accounts_at_startup` [1](#0-0) . A pubkey whose *final rooted* version is zero-lamport (i.e., closed by the attacker before the snapshot) is not removed here — it remains as a live index entry, since this pass only unrefs stale/duplicate slot versions, not dead accounts, and only `mark_obsolete_accounts_at_startup`'s reclaim of duplicates is invoked at this stage [2](#0-1) .

`calculate_accounts_lt_hash_at_startup_from_index` then iterates every key in every `accounts_index.account_maps` bin in parallel, doing an index lookup (`get_with_and_then`) per pubkey, and only *after* the lookup checks `!account_info.is_zero_lamport()` to decide whether to contribute to the hash [3](#0-2) . Dead/zero-lamport pubkeys thus still cost an index-bin lookup each, even though they add nothing to the final hash.

Critically, `Bank::verify_snapshot_bank` performs this expensive verification pass *before* running `clean_accounts`, which is the mechanism that would otherwise purge dead zero-lamport entries from the index: `verify_accounts(...)` executes first, and `clean_accounts(Some(latest_full_snapshot_slot), true)` only runs afterward [4](#0-3) . So any zero-lamport account that rooted but was not yet cleaned prior to the snapshot (a normal consequence of the "zero-lamport accounts can't be purged past the latest full snapshot slot" invariant demonstrated in `test_accounts_db_purge1`, which requires `set_latest_full_snapshot_slot` before `clean_accounts_for_tests` removes a zero-lamport pubkey [5](#0-4) ) will still be present in the freshly generated index when `verify_snapshot_bank` computes the lt-hash on restart.

An unprivileged attacker who repeatedly creates and zero-lamports M distinct accounts across many slots, ensuring the closing transactions root shortly before the snapshot slot (so they cannot yet be cleaned), forces every subsequent node restart from that snapshot to pay for M index-bin lookups during `calculate_accounts_lt_hash_at_startup_from_index`, regardless of how small the final live-account set is.

### Impact Explanation
This is a disproportionate CPU-cost/availability impact scoped to `verify_snapshot_bank`/`calculate_accounts_lt_hash_at_startup_from_index`: startup accounts verification time scales with total historical account churn M rather than the final live-account footprint, delaying node startup for every operator loading that snapshot (bootstrap and warm restarts alike, since this path is exercised on every `bank_from_snapshot_archives`/`bank_from_snapshot_dir` call, not only initial bootstrap) [6](#0-5) [7](#0-6) .

### Likelihood Explanation
Feasible for any unprivileged user with enough SOL to pay rent/fees for creating and closing accounts across many slots; fully repeatable since it only depends on ordinary transaction execution (create account, zero its lamports, let it root) timed relative to snapshot cadence, no special privileges or config needed. The magnitude is bounded by the attacker's fee/rent budget and by how many slots elapse between account churn and the next full snapshot (since clean can only reclaim zero-lamport accounts up to the latest full-snapshot slot).

### Recommendation
Reorder `verify_snapshot_bank` to run (or at least allow) a clean pass — restricted to reclaiming purely zero-lamport, already-obsolete entries that don't affect the expected lt-hash — before computing `calculate_accounts_lt_hash_at_startup_from_index`, or have `generate_index`/`mark_obsolete_accounts_at_startup` also drop index entries for pubkeys whose final rooted version is zero-lamport (subject to the same "not past latest full snapshot slot" safety bound), so the lt-hash loop only visits pubkeys that can actually contribute.

#[test]
fn test_lt_hash_startup_cost_scales_with_churn() {
    let accounts = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    accounts.add_root(0);

    // Baseline: few live accounts, no churn.
    let mut slot = 1;
    let live_pubkeys: Vec<_> = (0..10).map(|_| solana_pubkey::new_rand()).collect();
    for pk in &live_pubkeys {
        accounts.store_for_tests((slot, [(pk, &AccountSharedData::new(1, 0, &Pubkey::default()))].as_slice()));
    }
    accounts.add_root_and_flush_write_cache(slot);
    let ancestors = linear_ancestors(slot);
    let t0 = std::time::Instant::now();
    let _ = accounts.calculate_accounts_lt_hash_at_startup_from_index(&ancestors);
    let baseline = t0.elapsed();

    // Churn case: create+close M accounts across many slots, then keep same 10 live accounts,
    // WITHOUT calling clean_accounts (simulating pre-clean state right after snapshot restore).
    let churned = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    churned.add_root(0);
    let mut slot = 1;
    for pk in &live_pubkeys {
        churned.store_for_tests((slot, [(pk, &AccountSharedData::new(1, 0, &Pubkey::default()))].as_slice()));
    }
    churned.add_root_and_flush_write_cache(slot);
    for _ in 0..M /* e.g. 100_000 */ {
        slot += 1;
        let pk = solana_pubkey::new_rand();
        churned.store_for_tests((slot, [(&pk, &AccountSharedData::new(1, 0, &Pubkey::default()))].as_slice()));
        slot += 1;
        churned.store_for_tests((slot, [(&pk, &AccountSharedData::new(0, 0, &Pubkey::default()))].as_slice()));
        churned.add_root_and_flush_write_cache(slot);
    }
    let ancestors = linear_ancestors(slot);
    // Note: intentionally do NOT call clean_accounts_for_tests() here, mirroring
    // verify_snapshot_bank's ordering (verify before clean).
    let t1 = std::time::Instant::now();
    let _ = churned.calculate_accounts_lt_hash_at_startup_from_index(&ancestors);
    let churned_time = t1.elapsed();

    // Expect churned_time >> baseline, despite identical final live-account count (10),
    // demonstrating cost is proportional to M, not final state.
    assert!(churned_time > baseline * 100, "startup verification cost should not scale with churn: baseline={baseline:?} churned={churned_time:?}");
}
