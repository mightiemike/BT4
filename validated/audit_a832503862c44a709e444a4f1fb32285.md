### Title
Metering fails open into unmetered billing mode on any unrecognized spend/resource type, allowing unlimited free capability consumption - (File: `core/services/workflows/metering/balance_store.go`, `core/services/workflows/metering/metering.go`)

### Summary
The Chainlink CRE workflow metering/billing subsystem converts capability-reported resource spend into universal credits using a per-workflow rate card. When a resource type reported by a capability is not present in that rate card, the conversion function returns the raw amount unmodified (a 1:1 fallback) together with `ErrResourceTypeNotFound`, and the caller responds by permanently switching the entire workflow execution into "metering mode," which disables credit enforcement for the rest of the execution.

### Finding Description
`balanceStore.convertToBalance` / `convertFromBalance` fall back to treating an unrecognized resource dimension as worth exactly 1 unit-per-credit when no rate exists in the `conversions` map: [1](#0-0) 

This mirrors the reported bug class: a value from one domain (a capability-reported "spend unit"/quantity) is normalized into the accounting domain (universal credits) using an unconditional 1:1 assumption instead of the actual configured/market rate, whenever the mapping is missing.

In `Report.Settle`, this fallback error is not merely logged — it triggers `switchToMeteringMode`, which is sticky and disables double-spend/balance enforcement for the remainder of the execution ("meteringMode == true allows negative balances"): [2](#0-1) [3](#0-2) [4](#0-3) 

The resource/spend unit driving this path (`metadata.Metering[].SpendUnit`) originates from capability execution results reported back into the workflow engine at the `Settle` call site, and is grouped per unit before conversion: [5](#0-4) 

Because any capability invocation whose reported `SpendUnit` is not present in the workflow's rate card (fetched once per execution from the billing service via `GetWorkflowExecutionRates`) causes this fallback, a workflow author can choose to invoke a capability configuration whose spend types are not covered by their rate card (e.g., a capability not fully priced for that workflow/org, or a newly introduced spend dimension not yet reflected server-side), which immediately and irreversibly disables billing enforcement for that execution — no further balance checks or deductions are meaningful.

### Impact Explanation
Once `meteringMode` is set, `Deduct`/`Settle` no longer enforce or subtract from the local credit balance (`if r.meteringMode { return ... }` paths throughout `ByResource`, `ByDerivedAvailability`, and `Settle`). This allows a workflow execution to continue consuming paid node capabilities without being charged, and the balance is allowed to go negative, per the documented invariant comment. This is a billing/metering integrity bypass, directly analogous to the reported issue where a naive 1:1 conversion assumption, once triggered, is exploitable to obtain more value than intended (here: unmetered capability execution instead of accurately priced execution).

### Likelihood Explanation
Triggering the fallback only requires a workflow (or capability provider under the workflow author's control) to report a `SpendUnit`/resource type string that the rate card doesn't recognize — no privileged access is required beyond normal workflow submission via the workflow registry (job/workflow ingestion trust boundary). This can happen either intentionally (crafted to bypass billing) or as a side effect of capability/rate-card version skew, making it a plausible, non-exotic trigger.

### Recommendation
Do not use a value-preserving 1:1 fallback for unknown resource types combined with a global fail-open mode switch. Instead:
- Treat an unrecognized spend/resource type as a hard billing error that halts or rejects further capability execution (fail closed) rather than disabling enforcement for the remainder of the execution.
- Alternatively, if fail-open is intentional for availability, cap the "metering mode" fallback to the single unresolvable step rather than switching the entire report/execution into an unenforced state, and surface/alert distinctly from a normal metering error so it cannot be reliably induced by workflow configuration choices.

### Proof of Concept
1. A workflow author configures a workflow to invoke a capability whose `CapabilityInfo.SpendTypes` includes a resource dimension not present in the billing service's rate card response for that workflow owner (e.g., due to version skew or a capability not yet fully priced).
2. During execution, `Report.Settle` is called with `metadata.Metering` containing that unrecognized `SpendUnit`. [6](#0-5) 
3. `r.balance.ConvertToBalance(unit, value)` returns `(value, ErrResourceTypeNotFound)`, causing `switchToMeteringMode` to be invoked.
4. All subsequent `Deduct`/`Settle` calls for the remainder of the execution skip balance enforcement (`if r.meteringMode { return ... }`), letting the workflow continue consuming capabilities without further credit deduction and permitting negative balances.

// convertToBalance converts a resource dimension amount to a credit amount.
// This method should only be used under a read lock.
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}

func (r *Report) switchToMeteringMode(err error) {
	// add to the reported errors to indicate all errors encountered during metering
	r.meteringModeErr = errors.Join(r.meteringModeErr, err)

	if r.meteringMode {
		return
	}

	// only log a single metering mode switch error. this error should indicate the first metering related error
	// encountered
	r.lggr.Errorw("switching to metering mode", "err", err)

	r.meteringMode = true
}
