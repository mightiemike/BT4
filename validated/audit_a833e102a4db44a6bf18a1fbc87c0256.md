### Title
Unbounded blocking `GlobalRateLimiter.acquire()` in default (blocking) mode enables gRPC thread/connection exhaustion DoS - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/GlobalRateLimiter.java])

### Summary
When `rate.limiter.apiNonBlocking` is `false` (the shipped default), `RateLimiterInterceptor.interceptCall` invokes `GlobalRateLimiter.acquirePermit()` synchronously on the gRPC call-handling thread, which dispatches to `GlobalRateLimiter.acquire()`. This method calls Guava's blocking `RateLimiter.acquire()` with no timeout, so the calling thread sleeps until a global token becomes available. An unprivileged client can flood the node with cheap RPCs to keep the global limiter saturated, causing every concurrent call (including from other clients) to block indefinitely inside the interceptor before `next.startCall()` is ever invoked, tying up gRPC executor threads and per-connection call slots.

### Finding Description
`GlobalRateLimiter.acquirePermit` dispatches to `tryAcquire` (non-blocking) or `acquire` (blocking) based on `Args.getInstance().isRateLimiterApiNonBlocking()` [2](#0-1) . In blocking mode, `acquire()` calls `r.acquire()` on the per-IP limiter and then `rateLimiter.acquire()` on the global limiter, both of which are Guava blocking calls with no deadline [3](#0-2) . This is invoked directly and synchronously inside `RateLimiterInterceptor.interceptCall`, on the gRPC executor thread, before `next.startCall(call, headers)` runs: `boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);` [4](#0-3) .

Because the per-endpoint `IPreemptibleRateLimiter` permit is already acquired before the global check runs, that per-endpoint permit (and the underlying gRPC call/stream, counted against `maxConcurrentCallsPerConnection`) is held open for the entire duration the thread blocks in `GlobalRateLimiter.acquire()`. Nothing bounds this wait: no timeout is passed to Guava's `RateLimiter.acquire()`, and there is no deadline check against the gRPC call's own deadline before or during the block. `RpcService` configures a fixed-size executor (`rpcThreadNum`) or otherwise uses gRPC's default executor for running interceptors/handlers [5](#0-4) ; once enough concurrently blocked `acquire()` calls occupy all available threads in that pool, the interceptor itself — which runs before any handler logic and before the per-endpoint semaphore is released — cannot make progress for new calls either, effectively stalling gRPC service for all clients, not just the attacker.

An unprivileged, anonymous gRPC client can trigger this without any special permission: simply issue many concurrent low-cost RPCs (e.g., `GetNowBlock`) fast enough to keep the shared, node-wide `GlobalRateLimiter` (`QPS` global token bucket, default 50000 QPS but configurable/lower in various deployments) permanently saturated, then open additional concurrent calls that will queue behind the exhausted global bucket. Existing protections do not stop this: the per-endpoint limiter is intentionally checked first and does not prevent the subsequent global blocking wait; there is no RPC-level timeout wrapping the `acquire()` call; and `maxConnectionAgeInMillis`/`maxConnectionIdleInMillis` default to `0` (no limit) [6](#0-5) , so connections held open by blocked calls are not proactively terminated.

### Impact Explanation
This is a DoS via the RPC-API: sustained blocking inside a shared, bounded executor can exhaust available gRPC-handling threads and per-connection call slots, causing legitimate client requests to stall or time out even though they never individually exceed `maxConcurrentCallsPerConnection`. This matches the "DoS via RPC-API" bounty impact class — a resource/connection-slot exhaustion distinct from CPU-exhaustion DoS, achievable purely by an anonymous client without any signed transaction, fee payment, or privileged role.

### Likelihood Explanation
Preconditions require only default configuration (`apiNonBlocking=false` is the shipped default) and the node's global QPS bucket being saturated, which any anonymous, well-resourced client can accomplish by issuing a sufficiently high rate of cheap read-only RPC calls (e.g., `GetNowBlock`) — no fee or on-chain cost is involved for RPC calls. The attack is fully repeatable and requires no privileged access, no leaked keys, and no protocol-level (P2P) assumptions — only network access to the node's gRPC port, matching the allowed unprivileged-attacker model.

### Recommendation
Bound the wait in `GlobalRateLimiter.acquire()`/`acquirePermit()` with an explicit timeout (e.g., use Guava's `RateLimiter.tryAcquire(timeout, unit)` even in "blocking" mode, or tie the timeout to the gRPC call's deadline) and reject/close the call with `RESOURCE_EXHAUSTED` if the timeout elapses, ensuring the per-endpoint permit is still released via the existing cleanup path. Alternatively, move the blocking acquire off the gRPC handling thread pool (e.g., dedicated async scheduling with a bounded queue) so a saturated global limiter cannot consume threads needed to service unrelated calls.
