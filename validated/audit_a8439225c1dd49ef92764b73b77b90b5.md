### Title
Deterministic, unsalted pubkey→bucket assignment in `BucketMap::bucket_ix` lets an attacker grind pubkeys to overload a single AccountsIndex disk bucket - ([File: bucket_map/src/bucket_map.rs])

### Summary
`BucketMap::bucket_ix` (the top-level sharding function used by the on-disk accounts-index bucket map) computes a pubkey's bucket purely from the raw bytes of the pubkey, with no per-node randomization. Every pubkey is fully attacker-controlled (any keypair, or any address that ends up receiving/holding lamports), so an attacker can offline-grind pubkeys whose bucket assignment collides, then create real, funded (rent-exempt) accounts under those addresses on-chain. All resulting index entries land in the same bucket, producing severe, disproportionate size growth, resizing and lookup cost concentrated in one shard of the accounts index — the same "predictable identifier bucket that a user can deliberately target" root cause as the Curves finding, just applied to `AccountsIndex`'s disk bucket map instead of a token-symbol counter.

### Finding Description
`BucketMap::bucket_ix` determines which of the `2^max_buckets_pow2` top-level buckets a pubkey is routed to: [1](#0-0) 

```rust
pub fn bucket_ix(&self, key: &Pubkey) -> usize {
    if self.max_buckets_pow2 > 0 {
        let location = read_be_u64(key.as_ref());
        (location >> (u64::BITS - self.max_buckets_pow2 as u32)) as usize
    } else {
        0
    }
}
```

This reads the top 8 bytes of the raw pubkey and shifts out the top `max_buckets_pow2` bits — a purely deterministic function of the pubkey with no per-validator secret or salt.

Contrast this with `Bucket::bucket_index_ix`, which computes the *position within* a bucket, and which the codebase explicitly documents as security-sensitive and salts with a per-instance random value for exactly this reason: [2](#0-1) 

```rust
fn bucket_index_ix(key: &Pubkey, random: u64) -> u64 {
    // the locally generated random will make it hard for an attacker
    // to deterministically cause all the pubkeys to land in the same
    // location in any bucket on all validators
    let hasher_builder = ahash::RandomState::with_seeds(random, random, random, random);
    hasher_builder.hash_one(key)
}
```

The comment shows the developers were aware of and mitigated the "attacker forces many pubkeys into the same slot" attack class for intra-bucket placement, but the same mitigation was never applied to the coarser, and more consequential, top-level bucket selection in `bucket_map.rs`. Since bucket selection happens before intra-bucket hashing, an attacker who can predict/target `bucket_ix` can concentrate an arbitrary number of distinct pubkeys into one bucket regardless of the in-bucket randomization.

This is exactly analogous to the Curves bug pattern: a deterministic, user-visible mapping (symbol → counter slot / pubkey → bucket index) that is meant to spread load/identifiers evenly, but which any unprivileged actor can reverse-engineer and deliberately target to concentrate load onto one specific "slot" (a curve token name / an AccountsIndex bucket), degrading or breaking the system's assumption of uniform distribution.

### Impact Explanation
Concentrating a large number of accounts into a single bucket causes that specific `Bucket`'s index file to grow far beyond its fair share, forcing repeated `grow()`/resize operations, longer `max_search` linear probes on inserts and reads (`find_index_entry`, `bucket_create_key`), and increased disk I/O and lock contention isolated to that shard, all while other buckets remain lightly loaded. Because Solana account creation is permissionless (anyone can fund a new keypair-derived address for the rent-exempt minimum), this is trivially reachable by any user with a small amount of SOL and offline pubkey-grinding, producing disproportionate storage and CPU cost on validators running with the disk-based accounts index, consistent with the in-scope "disproportionate storage and CPU cost" impact category.

### Likelihood Explanation
Grinding Ed25519 keypairs to match a fixed number of leading bits is a well-known, cheap, fully offline computation (comparable in cost to vanity-address generation), and `max_buckets_pow2` is bounded (default configurations use a modest number of bits), making mass collision into one bucket practical without any special privileges. The attack requires only ordinary system-program account creation/funding transactions, which any unprivileged user can submit.

### Recommendation
Apply the same per-instance random salt used in `Bucket::bucket_index_ix` to the top-level bucket selection in `BucketMap::bucket_ix` (e.g., hash the pubkey with an ahash `RandomState` seeded by a validator-local random value before extracting the top bits), so bucket assignment cannot be predicted or targeted by an external actor, while remaining internally deterministic and stable for a given running validator instance.

### Proof of Concept
1. Offline, for a target validator's configured `max_buckets_pow2` (e.g. via `read_be_u64(pubkey) >> (64 - max_buckets_pow2)`), grind Ed25519 keypairs until many thousands of distinct pubkeys map to the same value of `bucket_ix`.
2. Fund/create real accounts (e.g., via `SystemProgram::create_account` at the rent-exempt minimum) for each of these ground pubkeys through ordinary transactions.
3. Observe that all resulting `AccountsIndex` entries are routed into a single `BucketMap` bucket (`bucket_map.rs` `get_bucket`/`bucket_ix`), causing that bucket's `BucketStorage` to require repeated growth (`Bucket::grow`) and degraded lookup/insert performance relative to buckets receiving a normal, non-adversarial pubkey distribution.
