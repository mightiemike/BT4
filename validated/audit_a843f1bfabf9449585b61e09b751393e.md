### Title
Wallet Contract's `has_in_flight_tx` in-progress lock has no recovery/emergency-unlock path if a callback receipt itself fails before the reset — permanent freeze of the eth-implicit wallet account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used to emulate Ethereum-style accounts for eth-implicit accounts, reachable by any meta-transaction relayer submitting an RLP-encoded transaction) uses a single boolean flag, `has_in_flight_tx`, to serialize execution: `rlp_execute` refuses any new transaction while the flag is `true`, and the flag is only ever cleared inside the private callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). [1](#0-0)  There is no admin function, timeout, or any other mechanism to reset this flag if the reset never happens — i.e. no "emergency stop"/recovery mechanism analogous to the reported issue.

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` and returns a scheduled `Promise` chain; the flag is only cleared as the very first statement of the follow-up private callback: [2](#0-1) [3](#0-2) 

Each intermediate callback (`address_check_callback`, `nep_141_storage_balance_callback`) is scheduled with a hard-coded, fixed static gas budget (`ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `RLP_EXECUTE_CALLBACK_GAS`), independent of the caller: [4](#0-3)  These constants are baked-in assumptions about the cost of function-call base fees, contract loading, and deserialization for that specific callback receipt.

If any callback receipt fails at the WASM/host-function level before user code executes (e.g. `GasExceeded` because the fixed static gas is insufficient to cover base function-call/contract-loading costs at execution time — costs that are not validated at promise-creation time and can differ over time because of protocol config changes such as `Wasmtime`/`FixContractLoadingCost`, or state growth), the receipt's state changes are entirely discarded, per the documented NEAR runtime rule that a function call failure "No changes are persisted on chain" [5](#0-4) . Crucially, this discards the very `self.has_in_flight_tx = false;` reset that would otherwise happen first thing in the callback. Because `has_in_flight_tx` was already committed as `true` by the prior receipt, and `rlp_execute` unconditionally rejects any further call while it is `true`, the wallet account is now permanently locked out of ever using `rlp_execute` again, with no owner/relayer/anyone-callable function to clear the flag.

This is architecturally analogous to the reported "No Emergency Stop Mechanism": the contract that (via `rlp_execute`) moves value and executes actions on behalf of users has no way to pause/unstick itself, and no privileged recovery path exists once the guard variable is desynchronized from the actual on-chain in-flight state.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the affected eth-implicit account can never again execute any Ethereum-emulated action (transfers, ERC-20 transfers, key management) through this wallet contract, because `rlp_execute` immediately short-circuits with "transaction already in progress" for every future call, forever. [6](#0-5)  Any $NEAR or NEP-141 tokens held by that eth-implicit account become effectively frozen with respect to this interface, since no alternate unlock/admin method is exposed in the contract. This matches the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Triggering this requires a callback receipt itself (not the inner cross-contract call it forwards to) to fail due to insufficient gas at execution time versus the hard-coded static-gas constants. The existing test suite explicitly verifies the "outer call runs out of gas" case is safe (`test_insufficient_gas`, contract "is still usable afterwards") [7](#0-6) , but there is no equivalent test proving the *callback receipt's own* fixed gas budget can never be exhausted — this is an unverified, hard-coded assumption (`Gas::from_tgas(5)` for `RLP_EXECUTE_CALLBACK_GAS`) that is only correct as long as base/loading gas costs never rise above it, which is not something the contract enforces or protects against. The README itself flags the contract as a temporary placeholder "Must not use in production" [8](#0-7) , underscoring that this kind of hardening gap has not yet been fully addressed.

### Recommendation
- Add a privileged/owner-callable (or time-based) recovery method that can clear `has_in_flight_tx` if it remains `true` for longer than a reasonable number of blocks, so a stuck state does not permanently disable the account.
- Alternatively, avoid relying on a single persisted boolean guard for atomicity across receipts; use a mechanism that tolerates a receipt-level failure of the callback itself (e.g. validate/increase static gas margins with safety buffers verified against current runtime config, or attach a fallback/self-heal on the next `rlp_execute` call rather than an unconditional reject).
- Add regression tests specifically simulating callback-receipt gas exhaustion (not just the outer call) to confirm the flag is not permanently stuck.

### Proof of Concept
1. Register a relayer key on a target eth-implicit wallet account. [9](#0-8) 
2. Submit an RLP-encoded transaction via `rlp_execute` that routes through `address_check_callback` or `nep_141_storage_balance_callback` (e.g. an ERC-20 transfer to an unregistered receiver), causing `has_in_flight_tx` to be set `true` and a callback receipt scheduled with the fixed static gas constant. [10](#0-9) 
3. If, at execution time, the fixed static gas allocated to that callback receipt (`ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`RLP_EXECUTE_CALLBACK_GAS`) is insufficient to cover the actual base function-call + contract-loading + deserialization cost for that receipt (achievable through protocol-level cost changes or contract/account state growth), the callback fails with `GasExceeded` before reaching `self.has_in_flight_tx = false;`, and that state change is discarded per NEAR's atomic-receipt-failure semantics. [5](#0-4) 
4. Any subsequent call to `rlp_execute` on this account now permanently fails with "transaction already in progress, please try again later" since no code path exists to reset the flag. [6](#0-5)

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

#[tokio::test]
async fn test_insufficient_gas() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    // If not enough gas is attached to the `rlp_execute` call then the action fails.
    let target = "some.account.near".to_string();
    let action = Action::FunctionCall {
        receiver_id: target.clone(),
        method_name: "greet".into(),
        args: br#"{"name": "Aurora"}"#.to_vec(),
        gas: 5_000_000_000_000,
        yocto_near: 0,
    };
    let signed_transaction = utils::create_signed_transaction(
        0,
        &target.parse().unwrap(),
        Wei::zero(),
        action,
        &wallet_sk,
    );

    let error = wallet_contract
        .inner
        .call(crate::tests::RLP_EXECUTE)
        .args_json(serde_json::json!({
            "target": target,
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_gas::NearGas::from_tgas(7))
        .transact()
        .await
        .unwrap()
        .raw_bytes()
        .unwrap_err();

    assert!(
        error.to_string().contains("Exceeded the prepaid gas."),
        "Error should be that there was not enough gas"
    );

    // But the contract is still usable afterwards.
    utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 0).await?;

    Ok(())
}
