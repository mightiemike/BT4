## Analysis

The reported bug class is: **a state-mutating function omits an existence/validity check that other components of the same system enforce, allowing an action to succeed on data that should have caused a rejection**, and this creates an incorrect state result. The closest reachable analog in this sequencer is a **missing "class is declared" check in the Starknet OS (SNOS) Cairo implementation of the `replace_class` syscall**, while the Rust `blockifier` — which is the component that actually decides what mutations occur when building/validating a block — enforces that check.

- `blockifier`'s deprecated syscall handler explicitly requires the class to be declared before mutating state: `syscall_handler.state.get_compiled_class(request.class_hash)?;` before `set_class_hash_at`. [1](#0-0) 

- The SNOS Cairo re-implementation of the very same syscall, used to re-execute the block and produce the STARK proof of the state transition, performs **no such check** — it directly reads the state entry via the `GetContractAddressStateEntry` hint and writes the caller-supplied `class_hash` into `contract_state_changes`, with a developer TODO acknowledging the gap: [2](#0-1) 

- The duplicated (deprecated-syscall) code path has the identical omission: [3](#0-2) 

- Whether OS-level syscalls execute at all for a transaction is driven purely by a hint-supplied `is_reverted` flag taken from the actual (already-decided) `blockifier` execution result, not recomputed by the OS itself: [4](#0-3) 

In Cairo 1, a syscall failure returns a `Result` that a caller contract can catch without panicking (see `Result::Err` handling pattern used throughout feature contracts, e.g. `handle_error_catch`), meaning the **overall transaction is not necessarily reverted** just because one inner `replace_class` syscall fails in `blockifier`. In that scenario, `blockifier` leaves the class hash of the contract unchanged (the syscall returned an error, state untouched), but the OS — lacking the "declared class" check — would unconditionally apply the class-hash mutation when re-executing/proving the same transaction, since it never fetches or validates the compiled class before writing the new `StateEntry`.

### Title
Starknet OS `execute_replace_class` Omits the "Class Declared" Check Enforced by Blockifier, Enabling State-Diff Divergence via a Caught Syscall Error - (`crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The SNOS Cairo implementation of the `replace_class` syscall mutates `contract_state_changes` with an attacker-supplied `class_hash` without verifying that a compiled class exists for that hash — a check that `blockifier` (the component that actually governs what state transition is committed) does perform before mutating state.

### Finding Description
`blockifier`'s `replace_class` handler calls `state.get_compiled_class(request.class_hash)?` and only proceeds to `set_class_hash_at` if the class is declared; an undeclared class hash causes this specific syscall invocation to return an error rather than mutating state. [1](#0-0) 

The corresponding SNOS Cairo function `execute_replace_class` (used to re-execute the same block for proof generation) has an explicit `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` and unconditionally writes the new state entry regardless of whether the class was ever declared. [5](#0-4) 

The same pattern exists in the deprecated-syscall Cairo path. [3](#0-2) 

A Cairo 1 caller contract can invoke `replace_class` and catch a `SyscallResult::Err` without panicking the whole transaction (this pattern is used elsewhere in the codebase, e.g. `handle_error_catch`), so a syscall-level failure in `blockifier` does not necessarily set the transaction-wide `is_reverted` flag that gates OS execution. [4](#0-3) 

Because the OS decides whether to run a transaction's syscalls at all purely from the externally-supplied `is_reverted` hint (mirroring the already-computed `blockifier` outcome) rather than re-deriving per-syscall failures, an inner `replace_class` call that fails in `blockifier` (leaving class hash unchanged and continuing the transaction) will, when replayed by the OS, succeed and mutate the class hash — since the OS-side function performs no equivalent validation.

### Impact Explanation
This produces a genuine divergence between the state diff actually committed by `blockifier`/the sequencer (class hash unchanged) and the state diff computed/proved by the Starknet OS for the identical transaction (class hash changed to the attacker-chosen, undeclared value). Since SNOS re-execution is the basis for the block's proof of correctness, this is a soundness gap that can let a proof attest to a state transition that does not match the state actually committed on-chain — a "wrong committed root" class of impact.

### Likelihood Explanation
Reachable directly from a single, ordinary transaction: any account contract can call the `replace_class` syscall with an arbitrary/undeclared `class_hash` and wrap the call so a syscall-level error is caught rather than propagated as a transaction revert. No privileged role, no proposer/operator misbehavior, and no multi-party coordination is required — only knowledge of an undeclared class hash and standard Cairo 1 error-catching in the caller contract.

### Recommendation
Add the same "class is declared" validation to the SNOS Cairo `execute_replace_class` implementations (both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`) that `blockifier` performs, e.g. asserting the guessed/hinted compiled-class fact for `request.class_hash` before writing the new `StateEntry`, so OS-side execution can never diverge from `blockifier`'s per-syscall outcome. Resolve the existing `TODO(Yoni, 1/1/2026)` comment as part of this fix.

### Proof of Concept
1. Declare a class hash is never actually declared by the attacker (or use any hash with no corresponding compiled class).
2. Deploy/own a Cairo 1 account or contract whose `__execute__`/entry point calls `replace_class_syscall(undeclared_hash)` and wraps the result, e.g. via `match syscalls::replace_class_syscall(...) { Result::Ok(_) => ..., Result::Err(_) => /* swallow error, continue */ }`.
3. Submit this as a normal transaction. In `blockifier`, `get_compiled_class` fails, so `replace_class` returns `Err`; the caller catches it and the transaction as a whole executes successfully and is committed with the contract's class hash unchanged.
4. When SNOS re-executes/proves this same transaction (driven by the recorded non-reverted `is_reverted` flag), `execute_replace_class` in `syscall_impls.cairo`/`deprecated_execute_syscalls.cairo` performs no declared-class check and unconditionally updates `contract_state_changes` with the undeclared `class_hash`, producing a state diff inconsistent with what `blockifier` actually committed.
