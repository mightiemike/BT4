## Title
Rounding errors in resource-usage transfer during undelegation can drive `netUsage`/`energyUsage` negative, granting free bandwidth/energy - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`, `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The skale-manager report describes a bug class where a value (e.g. `_delegatedByHolderToValidator`) is reduced by a *proportionally computed* amount derived from a different rounding path than the value it's later reconciled against, causing either underflow or "should-be-zero-but-isn't" drift. java-tron's `UnDelegateResourceProcessor`/`UnDelegateResourceActuator` contains the same structural pattern: `transferUsage`, an amount subtracted from the receiver's `netUsage`/`energyUsage`, is computed via an independent floating-point proportional calculation rather than being derived exactly from the state it is subtracted from.

### Finding Description
When resources are un-delegated, the receiver's bandwidth/energy usage is proportionally "clawed back" using floating point math: [1](#0-0) 

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * dynamicStore.getTotalNetLimit() / repo.getTotalNetWeight());
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage, VMConfig.disableJavaLangMath());

receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(-unDelegateBalance);
```

`transferUsage` is then subtracted from the receiver's current `netUsage`: [2](#0-1) 

The identical pattern exists in `UnDelegateResourceActuator` for the legacy (non-VM) path: [3](#0-2) 

This mirrors the skale-manager bug class exactly: `transferUsage` is computed as `netUsage * (unDelegateBalance / allFrozenBalance)`, a value derived independently through double-precision division rather than being tracked exactly alongside `netUsage`/`acquiredDelegatedFrozenV2BalanceForBandwidth`. Because `getAllFrozenBalanceForBandwidth()` (the denominator) itself changes across delegate/undelegate cycles (it is a sum including v1/v2 frozen and delegated balances that get mutated by many different actuators), and because `TRX_PRECISION` integer division truncates repeatedly, `transferUsage` accumulated over many partial `DelegateResource`/`UnDelegateResource` calls does not track `netUsage` reductions exactly. Unlike the skale-manager case, Java `long` subtraction does not revert on underflow — it silently wraps into an unintended negative value: [4](#0-3) 

A negative `netUsage`/`energyUsage` is never re-clamped to zero anywhere in `BandwidthProcessor`/`EnergyProcessor`. It is subsequently used directly in resource-limit comparisons, e.g.: [5](#0-4) 

If `newNetUsage` (derived from a negative persisted `netUsage`) is negative, `netLimit - newNetUsage` becomes larger than the true remaining bandwidth, letting the account consume more bandwidth/energy than it is entitled to — a direct analog of the "amount smaller than it should be, impossible to compare to zero" scenario from the report, here manifesting as free/extra resource rather than a reverted transaction (since java-tron's arithmetic silently drifts instead of throwing).

### Impact Explanation
An account that repeatedly delegates and un-delegates small amounts of frozen balance for bandwidth/energy to itself-controlled receiver accounts can accumulate rounding drift in `netUsage`/`energyUsage` until the value goes negative. This grants effectively unlimited free bandwidth/energy to that account, which:
- corrupts the resource-accounting invariant that `netUsage`/`energyUsage` reflects real consumption,
- can be leveraged as a low-cost bandwidth/energy DoS vector: an attacker gets free capacity to flood the network with transactions or heavy TVM execution while bypassing normal resource-fee mechanisms.

This is reachable purely through broadcast transactions (`DelegateResourceContract`/`UnDelegateResourceContract`, or their TVM native-contract equivalents `delegateResource`/`unDelegateResource`), requiring no privileged role.

### Likelihood Explanation
Exploitation requires many repeated delegate/undelegate cycles with carefully chosen fractional amounts to accumulate enough rounding drift to flip `netUsage`/`energyUsage` negative. Each call is a normal, permissionless transaction, so the attack is feasible for a patient/well-resourced attacker but requires numerous transactions and careful amount selection, making it a real but non-trivial-to-execute path.

### Recommendation
1. Clamp `newNetUsage`/`newEnergyUsage` to a minimum of `0` after every subtraction (`Math.max(0, netUsage - transferUsage)`), rather than trusting the floating-point-derived `transferUsage` to always be bounded correctly.
2. Avoid deriving `transferUsage` via independent double-precision division from a ratio of mutable balances; instead compute it deterministically from the same accounting units used for `netUsage`/`energyUsage`, or use BigInteger/BigDecimal with explicit rounding direction (always round down) consistent across all related fields, as was done for reward `Vi` accounting elsewhere in the codebase.
3. Add invariant checks (e.g., in `updateUsage`) that treat any negative persisted `netUsage`/`energyUsage` as `0` defensively, to fail closed rather than granting extra capacity.

### Proof of Concept
1. Freeze balance for bandwidth as owner A, delegate a chosen `delegateBalance` to receiver B via `DelegateResourceContract` (or TVM `delegateResource`), causing B's `acquiredDelegatedFrozenV2BalanceForBandwidth` and effective `netLimit` to increase.
2. Have B consume bandwidth so `netUsage` grows close to, but below, its frozen-derived limit.
3. Repeatedly perform small `UnDelegateResourceContract` calls with amounts chosen so that `(double) unDelegateBalance / getAllFrozenBalanceForBandwidth()` rounds `transferUsage` upward relative to the true proportional share (achievable due to double-precision truncation across many iterations and changing denominator as balances are undelegated).
4. After sufficient iterations, `receiverCapsule.getNetUsage() - transferUsage` in [6](#0-5)  goes negative and is persisted via `setNetUsage`.
5. Subsequent transactions from B pass the `bytes > (netLimit - newNetUsage)` check in `BandwidthProcessor.useAccountNet` with an inflated effective limit, consuming bandwidth without proper accounting/fee payment.
