### Title
Front-running of `SetAccountIdContract` allows griefing via unique `accountId` squatting - ([File: actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java])

### Summary
`SetAccountIdActuator` lets any account permanently bind an arbitrary, user-chosen `accountId` to itself, with global uniqueness enforced only by a check-then-act pattern (`accountIdIndexStore.has(accountId)` in `validate()`, then `accountIdIndexStore.put(account)` in `execute()`). Because transactions are visible in the public broadcast/mempool before being packed into a block, an attacker can observe a victim's pending `SetAccountIdContract` transaction and submit a copy with the same `accountId`, racing to have it confirmed first. This mirrors the reported bug class in the external report: an unprivileged actor chooses an arbitrary identifier, and a speed/visibility gap between transaction submission and confirmation lets an attacker front-run and permanently claim that identifier, causing the legitimate requester's transaction to revert and the identifier to become permanently unavailable to them (since `accountId`, once set, cannot be changed — "This account id already set").

### Finding Description
`SetAccountIdActuator.validate()` performs the uniqueness check: [1](#0-0) 
and `execute()` writes the binding without any reservation step protecting against a race between validation and commit across competing transactions: [2](#0-1) 

There is no restriction on which `accountId` bytes a caller may choose beyond format validation via `TransactionUtil.validAccountId`, and the binding is irrevocable once set: [3](#0-2) 

This is confirmed by the existing test demonstrating that a second actor's attempt with the same `accountId` reverts with `"This id has existed"` once the first has been committed: [4](#0-3) 

Just as in the reported bridge scenario — where an attacker observes a victim's pending `createLoanAndDeposit` transaction on a slower path and races it on a faster path using the same `loanId` — here an attacker can observe a victim's pending `SetAccountIdContract` transaction in the public transaction pool and submit a copy with identical `accountId` bytes, aiming to get it included in an earlier block or earlier position. Since account IDs function as scarce, permanently-owned identifiers with no reservation/commit-scheme protection, the first-confirmed transaction wins and the second irreversibly fails.

### Impact Explanation
This qualifies as griefing under the accepted impact categories: an attacker with no direct profit motive can deny a victim their intended `accountId`, causing the victim's transaction (and its associated bandwidth/fee cost) to be wasted, and — because the binding is one-time and permanent — the desired identifier is irretrievably lost to the victim once claimed by the attacker. This does not involve direct token custody like the loan example, so it stops short of causing direct fund loss, but it is a concrete, reachable unprivileged griefing/DoS vector against a normal actuator state transition triggered by an ordinary broadcast transaction.

### Likelihood Explanation
Likelihood is moderate: any node operator or attacker monitoring the public mempool (or receiving/relaying broadcast transactions) can see pending `SetAccountIdContract` transactions and their plaintext `accountId` payload before confirmation, then submit a competing transaction with the same `accountId` and a more attractive fee/priority to win block inclusion first. No special privileges, keys, or trusted role are required — only observation of the P2P/broadcast layer and normal transaction submission via the public RPC, which is standard capability for any network participant.

### Recommendation
Introduce a commit-reveal or first-come reservation scheme decoupled from the plaintext identifier (e.g., commit a hash of `accountId + salt` first, reveal later), or otherwise remove the ability for front-running to matter, such as scoping `accountId` uniqueness per-owner instead of globally, or allowing an already-`set` account's `accountId` to be updated/re-claimed under owner-controlled conditions rather than being permanently locked to whichever transaction confirms first.

### Proof of Concept
1. Victim broadcasts a `SetAccountIdContract` transaction with `accountId = "desired-id"` from address `A`.
2. Attacker observes this pending transaction (e.g., via P2P transaction relay or public API) before it is packed into a block.
3. Attacker broadcasts their own `SetAccountIdContract` transaction with the identical `accountId = "desired-id"` from address `B`, with equal or higher priority so it is included first.
4. `SetAccountIdActuator.execute()` for attacker's transaction succeeds, calling `accountIdIndexStore.put(account)` and binding `"desired-id"` to `B`: [2](#0-1) 
5. When the victim's transaction is later validated, `accountIdIndexStore.has(accountId)` now returns true, so `validate()` throws `ContractValidateException("This id has existed")`: [5](#0-4) 
6. The victim's transaction fails, they lose the bandwidth/fee cost, and — since `accountId` can only be set once per account — they can never obtain `"desired-id"` for address `A`.
