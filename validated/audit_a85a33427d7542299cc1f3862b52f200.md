### Title
Missing minimum sell-amount ("dust") check in `MarketSellAssetActuator.validate()` allows unbounded dust orders in the on-chain order book - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.validate()` only enforces `sellTokenQuantity > 0` and an upper bound (`quantityLimit`), but there is no minimum-quantity ("dust") threshold analogous to Rubicon's `require(_dust[address(pay_gem)] <= pay_amt)` check. Any account can broadcast a `MarketSellAssetContract` transaction with `sellTokenQuantity` as low as `1`, creating negligible orders that persist in the on-chain order book and price/pair index structures.

### Finding Description
In `validate()`, the only quantity checks performed are: [1](#0-0) 
There is no lower bound analogous to Rubicon's dust check — any strictly positive `sellTokenQuantity`/`buyTokenQuantity` (even `1`) passes validation. `execute()` then unconditionally creates and persists an order via `createAndSaveOrder`, inserting entries into `MarketAccountStore`, `MarketOrderStore`, `MarketPairToPriceStore`, and `MarketPairPriceToOrderStore`: [2](#0-1) 
If the order does not fully match, the remainder is persisted into the order book via `saveRemainOrder`, and the only per-account cap is `MAX_ACTIVE_ORDER_NUM = 100`: [3](#0-2) [4](#0-3) 
Because this cap is per-owner-address and TRON accounts are cheap to create/activate, an attacker can distribute dust orders across many addresses without bound, unlike Rubicon's per-token dust floor which caps dust regardless of the number of callers. Additionally, dust-sized sell quantities interact with `matchSingleOrder`'s integer-division price matching (`MarketUtils.multiplyAndDivide`), which can yield `takerBuyTokenQuantityRemain == 0` and force the code path that force-inactivates and refunds the order: [5](#0-4) 
This shows the codebase itself recognizes dust-quantity edge cases exist in the matching math, yet does not prevent their creation at the entry point (`validate()`), unlike the analogous Rubicon `offer()`/`_dust` check that the report highlights.

### Impact Explanation
Unbounded dust orders can be persisted cheaply (bounded only by the market sell fee `dynamicStore.getMarketSellFee()`), inflating `MarketOrderStore`, `MarketPairToPriceStore`, and `MarketPairPriceToOrderStore` and degrading order book iteration/matching performance (`matchOrder`'s `MAX_MATCH_NUM` loop, `pairPriceToOrderStore.getPriceKeysList`). This is a resource/state-bloat and market-book quality issue (denial-of-service-adjacent via order book pollution and increased iteration costs for other traders), not asset loss, since balances/fees are still properly debited/credited.

### Likelihood Explanation
Any account holding a nonzero balance of a listed TRC10 asset (or TRX) and the market sell fee can trigger this via a normal broadcast transaction; no privileged role is required, and the cost per dust order is just the fixed `MarketSellFee`. The attack is cheap to repeat across many addresses since the 100-orders-per-account cap does not limit total dust across the network.

### Recommendation
Add a minimum-quantity ("dust") check in `MarketSellAssetActuator.validate()`, analogous to Rubicon's `require(_dust[address(pay_gem)] <= pay_amt)`, e.g. introduce a `dynamicStore`-configurable minimum sell/buy quantity per token (or a global minimum) and reject orders below it:
```java
long quantityFloor = dynamicStore.getMarketQuantityMinimum(); // new config
if (sellTokenQuantity < quantityFloor || buyTokenQuantity < quantityFloor) {
  throw new ContractValidateException("token quantity must be greater than or equal to " + quantityFloor);
}
```

### Proof of Concept
1. Fund account `A` with `1` unit of TRC10 token `X` and the current `MarketSellFee` in TRX.
2. Broadcast `MarketSellAssetContract{ownerAddress: A, sellTokenId: X, sellTokenQuantity: 1, buyTokenId: "_", buyTokenQuantity: 1}`.
3. `validate()` passes because `sellTokenQuantity(1) > 0` and `1 <= quantityLimit` — no dust floor exists — see `MarketSellAssetActuator.validate()` at [1](#0-0) .
4. `execute()` persists the 1-unit order into `MarketOrderStore`/`MarketPairToPriceStore`/`MarketPairPriceToOrderStore` via `createAndSaveOrder` and `saveRemainOrder` — see [2](#0-1) .
5. Repeat with fresh accounts to bypass the 100-order-per-account cap, growing order-book storage and iteration cost with negligible-value orders.

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
  }
