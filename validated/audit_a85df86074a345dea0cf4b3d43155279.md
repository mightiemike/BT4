### Title
ECDSA signature malleability allows double-counting of a single co-signer's weight in `ValidateMultiSign` precompile - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompile deduplicates supplied signatures by hashing/matching the concatenation of the recovered address and the *raw signature bytes* (`sign = merge(recoveredAddr, rawSignature)`) via `ByteArray.matrixContains(executedSignList, sign)`, rather than deduplicating on the recovered address alone. Because ECDSA signatures are malleable (a valid `(r, s, v)` triple has a corresponding valid `(r, n-s, 1-v)` triple that recovers to the *same* address), an attacker who controls a single valid signature over the target hash can derive a second, byte-distinct signature that recovers to the identical co-signer address, causing that address's `weight` to be counted twice toward `totalWeight`.

### Finding Description
The relevant loop in `PrecompiledContracts.ValidateMultiSign.execute` iterates over the caller-supplied `signatures` array, recovers an address for each entry, and skips it only if the exact `merge(recoveredAddr, sign)` byte sequence was already seen in `executedSignList`. Because the dedup key includes the raw signature bytes (not just the address), two signatures that are cryptographically distinct as byte strings but recover to the same address are not recognized as duplicates. secp256k1/ECDSA signature malleability lets an attacker, holding one valid signature `(r, s)` over the hash, trivially compute `(r, n-s)` with the flipped recovery id — both are valid 65-byte signatures recovering to the same address, yet differ in their raw bytes, so the `merge(addr, sign)` dedup check treats them as unrelated entries. This lets the same permission key's `weight` be added to `totalWeight` twice (or, if multiple `k` values were used to sign, more), letting an attacker cross `permission.getThreshold()` using only one genuinely authorized signer instead of the intended distinct co-signer set.

None of the existing safeguards catch this: `SIG_LENGTH`/format checks pass on both malleable variants, `TransactionCapsule.validateSignature` is not involved (this executes purely inside the TVM precompile call path), and there is no canonical low-S enforcement or address-level (rather than signature-level) dedup in the loop.

### Impact Explanation
This breaks the `AUTHORIZATION_ENFORCED` invariant for multisig accounts/permissions: a single co-signer (not a majority or threshold-satisfying set of distinct keys) can make `ValidateMultiSign` return success by supplying two malleable variants of their own signature. Any smart contract logic gating asset transfers, permission changes, or other privileged actions on this precompile's boolean result can be tricked into believing a full multisig threshold was met, enabling unauthorized contract-mediated asset movement or state changes — matching the "unauthorized account operations / asset movement" bounty impact class.

### Likelihood Explanation
The attacker needs only to be one of the legitimate co-signers (or otherwise possess one valid signature over the hash for the account/permission being checked) with nonzero weight — no privileged role, no leaked keys beyond their own, and no non-default configuration. Deriving the malleable `(r, n-s)` counterpart signature is a pure, cheap, deterministic elliptic-curve computation requiring no interaction with the chain. The exploit is fully repeatable and only costs a normal contract call's energy/bandwidth. The only limiting factor is that malleability yields at most one extra malleable variant per underlying `(r,s)` pair, so this specifically enables doubling one signer's weight — sufficient to bypass thresholds set at or below that doubled value (e.g., 2-of-N schemes where one signer's weight already covers half the threshold).

### Recommendation
Deduplicate on the recovered address alone (e.g., add `recoveredAddr` to a `Set<ByteString>`/list and skip if already present) rather than on `merge(recoveredAddr, sign)`. Additionally, enforce canonical low-S signatures during recovery/validation (reject `s > n/2`) so malleable variants are rejected outright before address recovery, consistent with standard anti-malleability practice.

@Test
public void testMalleableSignatureDoubleCountsWeight() {
    // 1. Set up a permission with threshold T where signerA's weight == T/2 (not enough alone)
    //    and no other real co-signer participates.
    byte[] hash = ...; // digest passed to ValidateMultiSign
    ECKey signerA = ...; // attacker's own key with weight T/2

    ECDSASignature sig = signerA.sign(hash);          // (r, s)
    ECDSASignature malleable = new ECDSASignature(
        sig.r, CURVE.getN().subtract(sig.s));          // (r, n-s), flips recovery id

    byte[] rawSig1 = toBytes(sig, recoveryId0);
    byte[] rawSig2 = toBytes(malleable, recoveryId1);

    // Both rawSig1 and rawSig2 recover to signerA.getAddress()
    List<byte[]> signatures = List.of(rawSig1, rawSig2);

    Pair<Boolean, byte[]> result = ValidateMultiSign.execute(
        buildInput(ownerAddress, permissionId, hash, signatures));

    // Expected (correct) behavior: totalWeight should equal T/2 (only counted once) -> returns false
    // Actual (vulnerable) behavior: totalWeight == T (counted twice) -> returns true
    assertFalse(decodeBoolean(result.getRight())); // fails on vulnerable code, proving double count
}
