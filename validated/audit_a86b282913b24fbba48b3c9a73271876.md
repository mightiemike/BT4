## Title
DeleteAccount beneficiary refund to a non-existent account permanently burns the account's remaining balance instead of failing safely - (File: `runtime/runtime/src/actions.rs`)

### Summary
The reported Sudoswap issue is a class of bug where a value transfer is dispatched to a recipient before that recipient's validity/type is checked, so the funds can be permanently misdirected or lost. The nearcore analog is in `action_delete_account`, which unconditionally emits a system "refund" receipt carrying the deleted account's entire remaining balance to the caller-supplied `beneficiary_id`, without verifying that account exists or can receive it. Because system-predecessor ("refund") receipts are never allowed to create the destination account and a failed refund is burned rather than bounced back anywhere, a `DeleteAccountAction` whose `beneficiary_id` does not resolve to a live account causes the deleted account's balance to be permanently destroyed.

### Finding Description
`action_delete_account` computes the account's balance and, if positive, pushes an unconditional balance-refund receipt to `delete_account.beneficiary_id` before the account is removed: [1](#0-0) 

The only validation performed on `beneficiary_id` prior to this point is syntactic `AccountId` well-formedness (checked when the action/receipt is created), not whether the account actually exists or is of a type that can receive value implicitly: [2](#0-1) 

When this generated `Receipt::new_balance_refund` is later processed as its own action receipt, `check_account_existence` is invoked with `receipt_shape.is_refund = true` (since its predecessor is `"system"`): [3](#0-2) 

`implicit_creation_allowed` explicitly forbids account creation for refunds regardless of account type: [4](#0-3) 

So if `beneficiary_id` does not already exist as an account, the transfer action inside the refund receipt fails with `AccountDoesNotExist`. Critically, failed refund receipts are not retried or redirected to any other account — they are simply burned: [5](#0-4) [6](#0-5) 

This mirrors the audited Sudoswap pattern precisely: the "deposit" (here, the deleted account's balance) is transferred toward a recipient before/without validating that the recipient is a valid, existing target capable of receiving it, and the lack of that check leads to an unrecoverable loss.

### Impact Explanation
Any account owner (or holder of a full-access key) who submits a single `DeleteAccountAction` with a `beneficiary_id` that does not correspond to an existing account (e.g., a typo, a not-yet-created named account, or an implicit-style id nobody has funded) causes the entirety of that account's remaining NEAR balance to be irrecoverably burned instead of returned to the signer or the beneficiary. This is a direct, transaction-triggered, permanent loss of funds ("permanently frozen funds" per the accepted impact categories), reachable by any single unprivileged transaction signer controlling the account being deleted.

### Likelihood Explanation
High reachability: `DeleteAccountAction` is a standard, unprivileged action available to any account with sufficient permission over itself; `beneficiary_id` is fully attacker/user-controlled and only syntactically validated. No special network conditions, validator collusion, or multi-step exploitation is required — a single crafted transaction triggers the loss.

### Recommendation
Before emitting the balance-refund receipt in `action_delete_account`, validate that `beneficiary_id` resolves to an existing (or creatable, non-refund) account, or route the balance through a mechanism that allows account creation/fallback (e.g., refund to the predecessor/signer) when the beneficiary does not exist, rather than relying on the refund-receipt failure path that unconditionally burns the deposit.

### Proof of Concept
1. Create account `alice.near` and fund it with `N` NEAR.
2. From `alice.near`, submit a transaction with a single `DeleteAccountAction { beneficiary_id: "nonexistent123456.near" }`, where `nonexistent123456.near` has never been created.
3. `action_delete_account` pushes `Receipt::new_balance_refund("nonexistent123456.near", N)` and deletes `alice.near` [1](#0-0) .
4. When the refund receipt executes, `check_account_existence` rejects the transfer (`AccountDoesNotExist`) because refunds cannot create accounts [7](#0-6) [4](#0-3) .
5. Because the receipt's predecessor is `"system"`, the failed refund's deposit is added to `other_burnt_amount` rather than refunded anywhere [6](#0-5) .
6. Net effect: `N` NEAR that belonged to `alice.near` is permanently destroyed, with no account — including the original owner — ever receiving it.
