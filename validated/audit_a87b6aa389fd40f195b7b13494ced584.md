### Title
Single failing sub-request in a JSON-RPC batch call aborts the entire batch, discarding already-computed results for other valid requests - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java`)

### Summary
`JsonRpcServlet.handleBatch` iterates over every sub-request in an anonymous JSON-RPC batch call and accumulates per-request results into `batchResult`. If any single sub-request causes `rpcServer.handleRequest` to throw an uncaught `RuntimeException`, the loop's `catch` block immediately writes a single internal-error response and returns, discarding all previously accumulated results and skipping all remaining sub-requests in the batch. This mirrors the reported offchain-order bug class: a batch of independent, user-supplied items processed in a loop without per-item isolation, where one bad item denies service to every other (honest) item bundled in the same call.

### Finding Description
`handleBatch` builds `batchResult` incrementally across the JSON-RPC batch array: [1](#0-0) 

For each sub-request it calls into the underlying `JsonRpcServer`: [2](#0-1) 

Unlike the malformed-JSON-object branch (which just adds an error node for *that* sub-request and `continue`s), the `RuntimeException` branch here calls `writeJsonRpcError(...)` (which overwrites the whole HTTP response with a brand-new single-element error array) and `return`s from `handleBatch` entirely — abandoning the `batchResult` array built so far and never processing the remaining sub-requests: [3](#0-2) 

This is exactly analogous to the offchain-order loop in the report: a per-item loop over externally supplied requests that has no isolation/try-catch-continue semantics for exceptions raised deeper in item execution, so the whole batch fails once one item misbehaves. The codebase's own regression test confirms this is reachable and produces a batch-wide failure rather than a per-item error: [4](#0-3) 

Any anonymous caller of the public JSON-RPC HTTP endpoint (`doPost`) can submit a batch mixing legitimate calls with one call that triggers a `RuntimeException` deep inside `TronJsonRpc`/`TronJsonRpcImpl` (e.g. an unexpected NPE/`ArithmeticException`/other unchecked exception not mapped by `JsonRpcErrorResolver`/`@JsonRpcErrors`), causing every other sub-request in that batch — including ones from unrelated, honest requests bundled by a batching client/proxy — to be denied a proper response, replaced with a generic internal error.

### Impact Explanation
This is a Denial-of-Service against the JSON-RPC batch endpoint: a single crafted or edge-case sub-request can wipe out the results of all sibling requests in the same batch call, forcing legitimate callers to retry (potentially hitting the same poison request again if their client resends the same batch, or losing time-sensitive query results such as `eth_blockNumber`/`eth_getLogs` used by downstream services/bridges/indexers that rely on JSON-RPC batching). While it doesn't corrupt on-chain state, it degrades the RPC-API's availability/correctness guarantees for a common client pattern (JSON-RPC batching), matching the "DoS via RPC-API" acceptance criterion.

### Likelihood Explanation
Reachable by any anonymous HTTP client hitting the JSON-RPC servlet with no authentication or special privilege — only requires finding one method/argument combination in the large `TronJsonRpc` surface (many methods, many parameter-parsing paths) that throws an unmapped `RuntimeException` instead of one of the declared checked `JsonRpc*Exception`s. Given the breadth of `TronJsonRpcImpl`, likelihood of at least one such edge case existing (or being introduced in future changes) is non-trivial, and the failure mode (batch-wide abort) is deterministic once triggered, unlike a subtle race condition.

### Recommendation
In `handleBatch`, when `rpcServer.handleRequest` throws a `RuntimeException` for a given sub-request, do not abort the whole batch: log the error, append a per-sub-request error node with the sub-request's own `id` (mirroring the handling already used for the `!subRequest.isObject()` case), and `continue` the loop so remaining sub-requests are still processed and previously accumulated results in `batchResult` are preserved.

### Proof of Concept
1. Send a JSON-RPC batch POST to the servlet containing two requests: `[{"jsonrpc":"2.0","method":"eth_blockNumber","id":1}, {"jsonrpc":"2.0","method":"<method-triggering-unchecked-RuntimeException>","id":2}]`.
2. Observe that instead of receiving `[{"id":1,"result":...}, {"id":2,"error":{...}}]`, the response is a single-element array `[{"error":{"code":-32603,...}}]` as demonstrated by the existing test `batchRpcServerThrows_internalErrorIsArray` in `JsonRpcServletTest.java` (lines 158-167), confirming that the valid `eth_blockNumber` result for request `id=1` is discarded once any sub-request throws.

  private void writeJsonRpcError(HttpServletResponse resp, JsonRpcError error, String message,
      JsonNode id, boolean isBatch) throws IOException {
    ObjectNode errorObj = buildErrorNode(error, message, id);
    byte[] bytes;
    if (isBatch) {
      ArrayNode arr = MAPPER.createArrayNode();
      arr.add(errorObj);
      bytes = MAPPER.writeValueAsBytes(arr);
    } else {
      bytes = MAPPER.writeValueAsBytes(errorObj);
    }
    resp.setContentType("application/json-rpc");
    resp.setStatus(HttpServletResponse.SC_OK);
    resp.setContentLength(bytes.length);
    resp.getOutputStream().write(bytes);
    resp.getOutputStream().flush();
  }
