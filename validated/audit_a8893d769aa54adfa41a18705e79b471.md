### Title
Missing minimum order size in TRC10 DEX (`MarketSellAssetContract`) enables order-book dust flooding that permanently DoS's order matching via `MAX_MATCH_NUM` - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator`, the actuator behind java-tron's on-chain TRC10 order-book market, only enforces an *upper* bound on order size (`getMarketQuantityLimit()`) and a "greater than zero" check, but no *minimum* order size. Combined with a hard cap on the number of maker orders a taker transaction may walk through when matching (`MAX_MATCH_NUM = 20`), this allows a griefer to flood the best price levels of a token pair with a large number of dust (quantity = 1) resting orders spread across many attacker-controlled accounts, permanently preventing legitimate takers from executing market orders against that pair.

### Finding Description
In `validate()`, the only quantity checks are: [1](#0-0) 

```
    if (sellTokenQuantity <= 0 || buyTokenQuantity <= 0) {
      throw new ContractValidateException("token quantity must greater than zero");
    }

    long quantityLimit = dynamicStore.getMarketQuantityLimit();
    if (sellTokenQuantity > quantityLimit || buyTokenQuantity > quantityLimit) {
      throw new ContractValidateException("token quantity must less than " + quantityLimit);
    }
```

There is no floor value, so an order such as `sellTokenQuantity = 1` at any legal price is accepted. The per-account order cap only limits how many *active* orders a single account may hold: [2](#0-1) 

```
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(ownerAddress);
    if (marketAccountOrderCapsule != null
        && marketAccountOrderCapsule.getCount() >= MAX_ACTIVE_ORDER_NUM) {
      throw new ContractValidateException(
          "Maximum number of orders exceeded，" + MAX_ACTIVE_ORDER_NUM);
    }
```

Because this cap is per-account, an attacker can trivially create unlimited additional throwaway accounts (each account only needs enough balance/asset for a dust order plus the `MarketSellFee`) to place an unbounded number of tiny resting orders at the best (lowest) price for a token pair.

When any subsequent taker (a legitimate trader) submits a `MarketSellAssetContract` that crosses this price, `matchOrder()` walks the resting maker orders one at a time and aborts the *entire transaction* once more than `MAX_MATCH_NUM` (20) maker orders have been consumed at that price level: [3](#0-2) 

```
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }
      }
```

`ContractValidateException` here is thrown from inside `execute()` and is caught only to mark the result as `FAILED` and rethrow as `ContractExeException`: [4](#0-3) 

The 20-order cap (`MAX_MATCH_NUM`) is a hard limit per taker transaction (no batching mechanism exists for a taker to "skip" dust and continue), so once ≥21 dust orders sit at the best price for a pair, every legitimate market order that would cross that price permanently fails with "Too many matches," until someone (anyone, paying gas each time) cancels the maker orders one by one via `MarketCancelOrderActuator` — an actuator that can only cancel one order per transaction and only by its owner: [5](#0-4) 

Since the attacker controls the dust-order-owning accounts, they have no incentive to cancel, and no other party can remove those orders. This mirrors the Debita "no minimum size" griefing pattern: an unprivileged, anonymous actor (any account able to broadcast a `MarketSellAssetContract`/`MarketCancelOrderContract`) can fragment the market into countless tiny orders that other unprivileged users must interact with, at a cost asymmetry that favors the attacker (cheap to create dust orders, hard-capped `MAX_MATCH_NUM` makes it structurally impossible — not just expensive — for victims to trade through them).

### Impact Explanation
Any TRC10 token pair traded through java-tron's on-chain order book (`MarketSellAssetContract`/`MarketCancelOrderContract`) can be rendered permanently untradeable at the best price by an attacker willing to fund >20 accounts with minimal balances. This is a protocol-level Denial of Service against the exchange/market feature: legitimate takers' transactions revert deterministically (each paying the market sell fee before the match failure is caught), and no privileged action or governance parameter exists to bypass or raise `MAX_MATCH_NUM` per-transaction, nor is there a minimum order size parameter to prevent dust order creation. This affects resource/asset market accounting and order-book availability for any user of the DEX feature, not just a specific victim who set up an offer (unlike the Debita case where only borrower/lender parties were harmed) — it broadly denies market functionality for a token pair.

### Likelihood Explanation
Likelihood is high: the attack requires only ordinary, unprivileged transactions (`MarketSellAssetContract` to place dust orders, no special permission needed) reachable from any account via broadcast transaction. `dynamicStore.supportAllowMarketTransaction()` must be enabled by the committee, but once enabled — which is the intended operating mode of the feature — the attack path requires no elevated privilege. The cost to the attacker is small: `MarketSellFee` (a small TRX fee) plus a minimal quantity of the traded asset per dust order, multiplied by however many orders exceed `MAX_MATCH_NUM=20` at the given price level, spread across as many funded accounts as needed to bypass `MAX_ACTIVE_ORDER_NUM=100` per account (which is not even necessary if attacker uses a single account holding up to 100 dust orders, already 5x the `MAX_MATCH_NUM` threshold).

### Recommendation
Add a minimum order size validation in `MarketSellAssetActuator.validate()` analogous to the existing `quantityLimit` upper-bound check, rejecting `sellTokenQuantity`/`buyTokenQuantity` below a configurable minimum (e.g., a new `dynamicStore.getMarketQuantityMin()` committee-controlled parameter). Additionally/alternatively, make `matchOrder()` resilient to partial matching: instead of aborting the whole transaction when `MAX_MATCH_NUM` is exceeded, allow the taker's remaining unmatched quantity to rest in the order book (as already supported by `saveRemainOrder`) rather than throwing `ContractValidateException`, so dust orders cannot indefinitely block all trading for a pair.

### Proof of Concept
Conceptual reproduction using existing test harness patterns (see `framework/src/test/java/org/tron/core/actuator/MarketSellAssetActuatorTest.java`):
1. Enable market transactions (`saveAllowMarketTransaction(1)`).
2. Using 21+ distinct funded accounts (or a single account, since `MAX_ACTIVE_ORDER_NUM=100 > MAX_MATCH_NUM=20`), each submits a `MarketSellAssetContract` selling `TOKEN_ID_ONE` quantity `1` for `TOKEN_ID_TWO` quantity `1` (or any minimal ratio), all at the identical best price — these succeed under current validation since there is no minimum-size check.
3. A legitimate user submits a `MarketSellAssetContract` selling a large quantity of `TOKEN_ID_TWO` for `TOKEN_ID_ONE` at a matching/crossing price.
4. `matchOrder()` iterates the 21 resting dust orders; on the 21st match (`matchOrderCount > MAX_MATCH_NUM`), it throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")`, causing `execute()` to fail the entire transaction (`ContractExeException`), while the dust orders remain intact in the order book for reuse against future takers.
