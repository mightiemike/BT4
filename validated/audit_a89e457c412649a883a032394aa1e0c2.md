## Title
Panic-on-`None` in `SierraToNativeCompiler::compile` crashes the sequencer process on attacker-supplied Sierra during native compilation - (File: `crates/apollo_compile_to_native/src/compiler.rs`)

### Summary
`SierraToNativeCompiler::compile` runs the Cairo-Native compiler binary in a resource-limited *subprocess* (mirroring the "sandboxed compile" pattern used for Sierra→CASM), but after the subprocess exits successfully it unconditionally unwraps the loaded executor with `.unwrap()` on an `Option`, in the *parent* process: [1](#0-0) 

This is directly analogous to the GPAC CVE-2021-40563 bug class: a null/`None` value returned from a parsing/decoding step on attacker-influenced input is dereferenced/unwrapped without a graceful error path, crashing the process that processes the input.

### Finding Description
`SierraToNativeCompiler::compile` takes an untrusted `ContractClass` (Sierra), serializes it, and invokes the external `cairo-native` compiler binary via `compile_with_args`, which applies CPU/memory/file-size resource limits to the child process: [2](#0-1) 

If the subprocess exits with a non-zero status, an `Err` is correctly propagated. However, if the subprocess exits successfully but the resulting output file does not yield a valid `AotContractExecutor` (i.e., `AotContractExecutor::from_path` returns `Ok(None)` rather than `Ok(Some(_))` or `Err`), the code does:
```rust
Ok(AotContractExecutor::from_path(output_file.path())
    .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
    .unwrap())
``` [1](#0-0) 

The `.unwrap()` panics unconditionally on `None`, and unlike `Err` from `compile_with_args`/subprocess failure, this failure path is *not* isolated to the sandboxed subprocess — it executes in the calling (sequencer) process. This compilation path is reachable from a single, unprivileged declare transaction: whenever the sequencer's Cairo-Native mode is `WaitOnCompilation` or `LazyCompilation`, every declared Sierra class flows through `NativeClassManager::set_and_compile` → `process_compilation_request` → `SierraToNativeCompiler::compile`: [3](#0-2) 

In `WaitOnCompilation` mode compilation happens synchronously in the calling execution/validation path (e.g., gateway stateful validation or block building), so a panic there would abort the thread performing that work; in synchronous, single-threaded critical paths (or if the workspace/binary is configured with `panic = "abort"`), this can bring down the entire sequencer process rather than just failing one request.

### Impact Explanation
A successfully-exiting but malformed native-compiler output (e.g., due to a compiler edge case, truncated/corrupted output file, incompatible target, or any input that causes the compiler to write an incomplete artifact while still returning exit code 0) triggers an unconditional panic in the sequencer's own process rather than a contained `CompilationUtilError`. This is a denial-of-service vector reachable by any account able to submit a `DECLARE` transaction with a crafted Sierra program, matching the "Medium" DoS class of the referenced CVE (null/`None` dereference causing crash on malformed/attacker-influenced input during a decode/compile step). Depending on deployment (native compilation mode, panic strategy, and whether this runs on the main validation/execution thread), the practical impact ranges from crashing a background compilation worker thread to crashing the whole sequencer process, disrupting block production / transaction confirmation for that node.

### Likelihood Explanation
Likelihood depends on whether an attacker can reliably produce a Sierra program that makes the external `cairo-native` binary exit 0 while producing an output file that fails to load as a valid `AotContractExecutor`. This requires either a bug/edge-case in the `cairo-native` binary's own success/failure semantics, or a race/partial-write scenario. The `.unwrap()` is a clear code defect (turning any such case into a guaranteed panic instead of a `CompilationUtilError`), and it is exactly the same defensive-coding gap that GPAC's `naludmx_create_avc_decoder_config` had (successful-looking parse that leaves a value unset/`NULL`, later dereferenced unconditionally). Confirming an exact triggering input would require experimentation with the specific `cairo-native` compiler binary/version in use, which could not be verified from the indexed source alone.

### Recommendation
Replace the `.unwrap()` in `SierraToNativeCompiler::compile` with a proper error conversion (e.g., `.ok_or_else(|| CompilationUtilError::CompilationError("Compiler produced no output".into()))?`), so that any `None` result from `AotContractExecutor::from_path` is surfaced as a recoverable `CompilationUtilError` instead of panicking the calling process. Additionally, audit all other `.unwrap()`/`.expect()` calls on compiler output derived from attacker-controlled Sierra along this and the CASM compilation path to ensure none can panic outside the sandboxed subprocess.

### Proof of Concept
Not independently reproducible from the indexed codebase alone (requires the actual `cairo-native` compiler binary to determine an input that yields exit-code 0 with an unusable output file). Conceptually:
1. Submit a `DECLARE` transaction with a Sierra program crafted so `cairo-native`'s compile subprocess returns success (exit 0) but writes an output file that `AotContractExecutor::from_path` parses as `Ok(None)`.
2. On a sequencer configured with `CairoNativeMode::WaitOnCompilation` or `LazyCompilation`, `set_and_compile`/`process_compilation_request` invokes `SierraToNativeCompiler::compile`, hitting the `.unwrap()` and panicking in the sequencer process. [3](#0-2) [1](#0-0)
