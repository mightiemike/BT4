## Title
Missing `signatures_required` validation in `deserialize_multi_key` allows creation of a MultiKey with 0 required signatures - (File: aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move)

### Summary
`new_public_key_from_bytes` deserializes a `MultiKey` via `deserialize_multi_key`, which reads `signatures_required` directly off the wire with no bounds check, unlike the sibling constructor `new_multi_key_from_single_keys`, which explicitly asserts `signatures_required <= num_keys` (and implicitly requires `num_keys > 0`). [1](#0-0) 

### Finding Description
`new_multi_key_from_single_keys` validates that the number of keys is non-zero, does not exceed `MAX_NUMBER_OF_PUBLIC_KEYS`, and that `signatures_required <= num_keys`: [2](#0-1) 

However `deserialize_multi_key`, used by `new_public_key_from_bytes` for parsing attacker-supplied bytes (e.g., from a transaction authenticator or a key-rotation payload), performs none of these checks — it simply reads a `vector<u8>` of public keys and a `u8` for `signatures_required` and constructs the struct unconditionally: [3](#0-2) 

So a caller can feed a BCS blob with `signatures_required = 0` (or a value greater than the key count) through `new_public_key_from_bytes` and obtain a `MultiKey` value that violates the invariant enforced elsewhere in the codebase.

### Impact Explanation
This is a real gap in `multi_key.move`, but I was unable to verify, within the available tool budget, that `account::rotate_authentication_key_from_public_key` (or any other production entry point) actually calls `multi_key::new_public_key_from_bytes`/`deserialize_multi_key` on attacker-controlled bytes and then commits the resulting `to_authentication_key()` hash as the account's `authentication_key` without any additional signature-count validation at the VM/authenticator level. The grep for `rotate_authentication_key_from_public_key` in `account.move` only matched an unrelated line, and I could not locate the actual call chain that constructs an `AnyPublicKey`/`MultiKey` from raw public-key-scheme bytes and threads it into the account's stored authentication key before the review turn ended.

Separately, even if a `MultiKey` with `signatures_required = 0` is constructed, `to_authentication_key` only computes `sha3_256(bcs(self) || scheme_id)` — a hash — so the resulting authentication key is deterministic and no different in "unauthenticatable-ness" from any other value; whether it actually corrupts consensus-committed state or merely creates an account that can never be validly signed for (a self-inflicted, permanently-locked account, not a divergence from correct VM behavior) is a question of transaction-authenticator semantics that I could not verify from `multi_key.move` alone. Bricking one's own account via a malformed self-chosen key is generally a user self-DoS, not a corruption of ledger state relative to the correct VM result, unless the authenticator layer trusts `signatures_required` for something more consequential (e.g., skipping signature verification counts) — which was not confirmed here.

### Likelihood Explanation
Cannot be assessed with confidence without confirming the call path from `account::rotate_authentication_key_from_public_key` (or equivalent) into `multi_key::new_public_key_from_bytes`, and without confirming whether/how the transaction authenticator/signature-verification logic (in the VM, not in `multi_key.move`) uses `signatures_required` at verification time versus purely at key-derivation time.

### Recommendation
Regardless of the exploitability of the specific downstream path, `deserialize_multi_key` should enforce the same invariants as `new_multi_key_from_single_keys` (non-empty keys, `num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS`, `1 <= signatures_required <= num_keys`) so that no code path — direct construction or BCS deserialization — can produce an invalid `MultiKey`.

### Proof of Concept
A Move unit test constructing a BCS blob for `MultiKey { public_keys: [<one AnyPublicKey>], signatures_required: 0 }` and calling `multi_key::new_public_key_from_bytes` on it would succeed and return a `MultiKey` value, whereas `new_multi_key_from_single_keys` with the same inputs would abort with `E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED`. This demonstrates the asymmetric validation in `multi_key.move` itself: [4](#0-3) 

**Caveat**: I could not confirm within this session that this deserialization gap actually reaches `account::rotate_authentication_key_from_public_key` and corrupts the committed `authentication_key` write set in a way that constitutes ledger-state corruption per the State-Integrity Gate (as opposed to a self-inflicted account lockout, which is out of scope as it depends on the account owner's own malformed rotation transaction, not a third-party attack on committed state). Confirming the full call chain (`account.move` → `single_key.move`/`multi_key.move` → authenticator verification logic in the VM) would require further investigation that I did not have remaining tool budget to complete.

    /// Parses the input bytes into a MultiKey public key.
    public fun new_public_key_from_bytes(bytes: vector<u8>): MultiKey {
        let stream = bcs_stream::new(bytes);
        let pk = deserialize_multi_key(&mut stream);
        assert!(!bcs_stream::has_remaining(&mut stream), error::invalid_argument(E_INVALID_MULTI_KEY_EXTRA_BYTES));
        pk
    }

    /// Creates a new MultiKey public key from a vector of single key public keys and a number representing the number of signatures required to authenticate a transaction.
    public fun new_multi_key_from_single_keys(single_keys: vector<single_key::AnyPublicKey>, signatures_required: u8): MultiKey {
        let num_keys = single_keys.length();
        assert!(
            num_keys > 0,
            error::invalid_argument(E_INVALID_MULTI_KEY_NO_KEYS)
        );
        assert!(
            num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS,
            error::invalid_argument(E_INVALID_MULTI_KEY_TOO_MANY_KEYS)
        );
        assert!(
            (signatures_required as u64) <= num_keys,
            error::invalid_argument(E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED)
        );
        MultiKey { public_keys: single_keys, signatures_required }
    }

    /// Deserializes a MultiKey public key from a BCS stream.
    public fun deserialize_multi_key(stream: &mut bcs_stream::BCSStream): MultiKey {
        let public_keys = bcs_stream::deserialize_vector(stream, |x| single_key::deserialize_any_public_key(x));
        let signatures_required = bcs_stream::deserialize_u8(stream);
        MultiKey { public_keys, signatures_required }
    }
