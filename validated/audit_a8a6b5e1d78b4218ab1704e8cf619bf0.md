### Title
Unbounded attacker-controlled spends list causes linear-time native JNI signing loop with no server-side cap - (File: `framework/src/main/java/org/tron/core/zen/ZenTransactionBuilder.java`)

### Summary
`ZenTransactionBuilder.createSpendAuth(byte[])` iterates over the entire `spends` list and invokes the native JNI call `JLibrustzcash.librustzcashSaplingSpendSig` once per entry, with no size cap enforced anywhere in the visible code path before `build()`/`build(boolean)` is invoked. This method is reachable from `CreateShieldedTransactionServlet` and `CreateShieldedTransactionWithoutSpendAuthSigServlet`, which are unauthenticated HTTP endpoints that merge attacker-supplied JSON directly into `PrivateParameters`/`PrivateParametersWithoutAsk` protobufs.

### Finding Description
`CreateShieldedTransactionServlet.doPost` and `CreateShieldedTransactionWithoutSpendAuthSigServlet.doPost` parse untrusted JSON POST bodies into `PrivateParameters.Builder`/`PrivateParametersWithoutAsk.Builder` via `JsonFormat.merge` and immediately call `wallet.createShieldedTransaction(...)` / `wallet.createShieldedTransactionWithoutSpendAuthSig(...)` [1](#0-0) [2](#0-1) . Both servlets only extend `RateLimiterServlet`, which throttles request rate/frequency, not the size or complexity of an individual request's payload.

Downstream, `ZenTransactionBuilder.build(boolean withAsk)` loops over `spends` to call `generateSpendProof` for every entry (a zk-SNARK proof generation, the most expensive step) and, if `withAsk` is true, calls `createSpendAuth(dataHashToBeSigned)`, which itself loops `for (int i = 0; i < spends.size(); i++)` and calls the native `JLibrustzcash.librustzcashSaplingSpendSig` once per spend [3](#0-2) . No bound on `spends.size()` (e.g., a `MAX_INPUT_NUM`-style check) is present in `ZenTransactionBuilder` itself.

I was unable to fully confirm within the available search results whether `Wallet.createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig` (in `framework/src/main/java/org/tron/core/Wallet.java`) apply any explicit size validation on the number of shielded spends taken from the incoming `PrivateParameters` before constructing the `ZenTransactionBuilder` — the file was located but its body was not retrieved in the investigation. This is a gap in verification, not a confirmed absence of a check.

### Impact Explanation
If no upstream cap exists, an unauthenticated client can submit a single `PrivateParameters`/`PrivateParametersWithoutAsk` request with a very large `shieldedSpends` repeated field. Each spend requires a Merkle-path voucher and note data, and each triggers both an expensive zk-SNARK spend-proof computation (`generateSpendProof` → `librustzcashSaplingSpendProof`) and a native signature computation (`createSpendAuth` → `librustzcashSaplingSpendSig`), all executed synchronously on the servlet's request-handling thread. This matches an RPC-API DoS via CPU exhaustion, since the thread pool serving `CreateShieldedTransactionServlet`/`CreateShieldedTransactionWithoutSpendAuthSigServlet` (and potentially shared with other HTTP API servlets) can be starved by a small number of maximal-size requests.

### Likelihood Explanation
Preconditions are minimal: the endpoints are reachable without authentication, require no privileged role, and the attacker only needs to construct a valid-shaped JSON payload with many spend entries (each including a plausible Merkle voucher and spending key material, which does not need to be valid/spendable, only well-formed enough to survive JSON parsing and reach the loop before invalid-signature/proof errors would occur). The `RateLimiterServlet` base class limits request frequency, not payload complexity, so a single or few requests could already produce significant CPU load, and the attack is trivially repeatable. However, the exact severity depends on unconfirmed factors: HTTP body size limits configured on the underlying servlet container, JSON parsing depth/size limits, and any input-count validation in `Wallet.java` that I could not verify due to search/read limitations in this session.

### Recommendation
Enforce an explicit upper bound on the number of shielded spends (and outputs) accepted in `PrivateParameters`/`PrivateParametersWithoutAsk` before constructing/invoking `ZenTransactionBuilder.build()`, ideally at the earliest point in `Wallet.createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig`, rejecting requests exceeding a small, protocol-reasonable limit (e.g., matching any consensus-level max input count for shielded transactions). Additionally, consider adding a defensive size check directly in `ZenTransactionBuilder.build(boolean)`/`createSpendAuth` as a second line of defense, and ensure HTTP servlet container request body size limits are configured to bound worst-case payload size regardless of code-level checks.

  public TransactionCapsule build(boolean withAsk) throws ZksnarkException {
    TransactionCapsule transactionCapsule;
    long ctx = JLibrustzcash.librustzcashSaplingProvingCtxInit();

    try {
      // Create SpendDescriptions
      for (SpendDescriptionInfo spend : spends) {
        SpendDescriptionCapsule spendDescriptionCapsule = generateSpendProof(spend, ctx);
        contractBuilder.addSpendDescription(spendDescriptionCapsule.getInstance());
      }

      // Create OutputDescriptions
      for (ReceiveDescriptionInfo receive : receives) {
        ReceiveDescriptionCapsule receiveDescriptionCapsule = generateOutputProof(receive, ctx);
        contractBuilder.addReceiveDescription(receiveDescriptionCapsule.getInstance());
      }

      // Empty output script
      byte[] dataHashToBeSigned; //256
      transactionCapsule = wallet.createTransactionCapsuleWithoutValidate(
          contractBuilder.build(), ContractType.ShieldedTransferContract, timeout);

      dataHashToBeSigned = TransactionCapsule
          .getShieldTransactionHashIgnoreTypeException(transactionCapsule.getInstance());

      if (dataHashToBeSigned == null) {
        throw new ZksnarkException("cal transaction hash failed");
      }

      // Create spendAuth and binding signatures
      if (withAsk) {
        createSpendAuth(dataHashToBeSigned);
      }

      byte[] bindingSig = new byte[64];
      JLibrustzcash.librustzcashSaplingBindingSig(
          new BindingSigParams(ctx,
              valueBalance,
              dataHashToBeSigned,
              bindingSig)
      );
      contractBuilder.setBindingSignature(ByteString.copyFrom(bindingSig));
    } catch (ZksnarkException e) {
      throw e;
    } finally {
      JLibrustzcash.librustzcashSaplingProvingCtxFree(ctx);
    }
    Transaction.raw.Builder rawBuilder = transactionCapsule.getInstance().toBuilder()
        .getRawDataBuilder()
        .clearContract()
        .addContract(
            Transaction.Contract.newBuilder().setType(ContractType.ShieldedTransferContract)
                .setParameter(
                    Any.pack(contractBuilder.build())).build());
    Transaction transaction = transactionCapsule.getInstance().toBuilder().clearRawData()
        .setRawData(rawBuilder).build();
    return new TransactionCapsule(transaction);
  }

  public void createSpendAuth(byte[] dataToBeSigned) throws ZksnarkException {
    for (int i = 0; i < spends.size(); i++) {
      byte[] result = new byte[64];
      JLibrustzcash.librustzcashSaplingSpendSig(
          new SpendSigParams(spends.get(i).expsk.getAsk(),
              spends.get(i).alpha,
              dataToBeSigned,
              result));
      contractBuilder.getSpendDescriptionBuilder(i)
          .setSpendAuthoritySignature(ByteString.copyFrom(result));
    }
  }
