### Title
`ExchangeTransactionActuator`/`ExchangeCapsule.transaction` legacy Bancor calculation can drain (or overdraw) an exchange pool's reserve because no invariant check enforces `buyTokenQuant < buyTokenBalance` - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The reported bug is that `NormalStrategyLib.tradingFunction` silently returns a wrong (zero instead of ±∞) invariant term when a reserve hits its boundary (0 or 1e18/K), letting an attacker swap out 100% of a reserve because the code never checks that reserves stay strictly inside their valid domain. The java-tron TRX "bancor" `Exchange` feature has the analogous structural weakness: the legacy (default) swap math path performs the exchange calculation with IEEE-754 `double` arithmetic and never validates that the resulting new reserve is still a valid, non-zero/non-negative amount before it is persisted, unlike the newer "hardened" path which was added specifically to fix this.

### Finding Description
`ExchangeCapsule.transaction()` computes the swap output via a `Processor` (Bancor-style constant-reserve-ratio formula) and then updates `firstTokenBalance`/`secondTokenBalance` directly: [1](#0-0) 

The legacy `ExchangeProcessor` performs the whole calculation using `double`: [2](#0-1) 

Critically, in the non-hardened (`hardenedCalc == false`, i.e. `allowHardenExchangeCalculation()` disabled) branch of `transaction()`, there is **no check at all** that `newFirstTokenBalance`/`newSecondTokenBalance` are non-negative or non-zero — the `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` guard only fires when `hardenedCalc` is true: [3](#0-2) 

`allowHardenExchangeCalculation()` is a chain parameter/proposal flag (`AbstractExchangeActuator.allowHarden()`) that is off by default and only becomes active via a governance proposal: [4](#0-3) 

This mirrors exactly the reported bug class: a boundary condition of the trading-curve math (buy-side reserve going to/near 0) is not defended against by the trading function itself, and the fix ("Primitive"/"Spearbit" fix in the report — add a check that reverts if a reserve becomes 0) only exists in the newer/optional "hardened" code path (`SafeExchangeProcessor` + the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard), not in the default path that all exchanges still use unless the community-approved hard fork proposal is active.

The only pre-trade validation in `ExchangeTransactionActuator.doValidate()` checks that `firstTokenBalance == 0 || secondTokenBalance == 0` *before* the trade (rejecting already-closed pools) and that `tokenQuant`/`tokenExpected` are positive, and that `anotherTokenQuant >= tokenExpected`, but it never checks that the **post-trade** buy-side balance remains > 0: [5](#0-4) 

Because `exchangeFromSupply()` in the legacy `ExchangeProcessor` computes `balance * (pow(1 + supplyQuant/supply, 2000.0) - 1.0)` using floating-point `double` and casts the result to `long` via truncation, for sufficiently large `sellTokenQuant` (which is only bounded by the sender's asset balance and the `exchangeBalanceLimit`, not by any bound relative to the buy-side reserve) the computed `buyTokenQuant` can equal or, due to double-precision rounding at the asymptote, even slightly exceed `buyTokenBalance`. Because the update path `secondTokenBalance - buyTokenQuant` (or the symmetric `firstTokenBalance - buyTokenQuant`) is done with plain `long` subtraction and unguarded in the non-hardened branch, this can drive a reserve to zero or negative, which is then persisted via `Commons.putExchangeCapsule(...)`. This is functionally the same "reserve hits its boundary and the trading math doesn't defend against it" defect as the original report, applied to java-tron's on-chain AMM feature (`Exchange*Contract` actuators), which are reachable by any account via a signed, broadcast `ExchangeTransactionContract` transaction — no privileged role required.

### Impact Explanation
An attacker who can afford the `tokenQuant` of the sell-side asset (which may be a worthless/attacker-controlled TRC-10 token, since `ExchangeCreateActuator` lets any account create an exchange pair with a self-issued token) can drive the counter-asset (which may be TRX or a valuable token) reserve of the pool down to zero or into an inconsistent/negative state. Once a reserve reaches or crosses zero:
- Further swaps against the pool operate on a corrupted state (division/precision issues, or `firstTokenBalance == 0 || secondTokenBalance == 0` rejecting all future legitimate trades — pool permanently bricked), and
- Because the balance is a `long` and the update in the non-hardened path is `secondTokenBalance - buyTokenQuant` without any floor check, a computed `buyTokenQuant` that exceeds the actual reserve results in real value (TRX/tokens) being paid out to the attacker's account (via `addAssetAmountV2`/`setBalance` in `ExchangeTransactionActuator.execute`) beyond what the pool can honestly back, i.e. asset/accounting corruption and value extraction from other liquidity participants.

This satisfies "asset or accounting corruption" reachable from an unprivileged broadcast transaction.

### Likelihood Explanation
Medium-High. Any account can call `createExchange`/`exchangeTransaction` via ordinary broadcast transactions; no special permission is required. The vulnerable legacy math path is the **default** (the hardened path requires `allowHardenExchangeCalculation` to be enabled via community proposal, and the repo's own tests show that flag defaults to 0 and is only enabled/disabled temporarily in tests). Exploitation requires crafting sell quantities that push the Bancor curve near its asymptote to trigger floating-point overshoot/precision loss — this is a deliberate, repeatable computation an attacker fully controls (choose `tokenQuant` to sell), not a probabilistic race condition.

### Recommendation
- Apply the same fix the report recommends to the *default* code path, not only to an optional hardened mode gated behind a governance proposal: reject swaps in `ExchangeCapsule.transaction()` (and in the pre-trade validation in `ExchangeTransactionActuator.doValidate()`) whenever the resulting `newFirstTokenBalance` or `newSecondTokenBalance` would be `<= 0`, regardless of `hardenedCalc`.
- Alternatively, make `allowHardenExchangeCalculation()` (and the `SafeExchangeProcessor`/`BigDecimal`-based calculation) mandatory rather than an optional hard-fork toggle, since it is the only path that currently guards reserves from going non-positive.
- Add an explicit assertion that `buyTokenQuant < buyTokenBalance` before committing the new balances in every code path, mirroring the recommendation to disallow swapping out all/more-than-available reserves.

### Proof of Concept
Not independently executable from the index alone (no live node/RPC harness available here), but the existing repository tests demonstrate the underlying arithmetic behavior that supports the finding: [6](#0-5)  shows that only the *hardened* processor is explicitly tested/asserted to keep `result < buyBalance`; the legacy `ExchangeProcessor` (used by default, `hardenedCalc=false`) has no equivalent invariant test or runtime check, and `ExchangeCapsule.transaction()` only guards negative balances `if (hardenedCalc && ...)`: [7](#0-6) 

To reproduce on a running node/testnet:
1. Create an `Exchange` pair with a small buy-side reserve (e.g. via `ExchangeCreateContract`) using an attacker-issued TRC-10 token as the sell-side asset.
2. Issue an `ExchangeTransactionContract` selling a very large quantity of the attacker's own token (bounded only by `exchangeBalanceLimit` and the attacker's asset balance, both attacker-controllable since the token is self-issued) without the `AllowHardenExchangeCalculation` proposal active.
3. Observe that `exchangeFromSupply`'s double-precision computation drives `buyTokenQuant` to/near `buyTokenBalance`, and that the resulting `secondTokenBalance` (or `firstTokenBalance`) is set to 0 or a corrupted value with no revert, while the attacker's account balance is credited via `addAssetAmountV2`/`setBalance` in `ExchangeTransactionActuator.execute` — [8](#0-7) .

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
