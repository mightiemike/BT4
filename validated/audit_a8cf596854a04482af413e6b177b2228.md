### Title
Unseeded, non-deterministic `RandomEcPoint` core-hint handling in blockifier causes honest-node execution divergence - (File: crates/blockifier/src/execution/syscalls/hint_processor.rs)

### Summary
The Gameboy incident involved a contract that seeded its "random" outcome with a value the attacker could predict/control, letting the attacker win deterministically. The equivalent sequencer-side risk is not attacker-controlled randomness but attacker-*reachable* non-determinism: any Cairo1 class containing the `CoreHint::RandomEcPoint` hint is executed by blockifier through the stock, unseeded cairo-lang-runner implementation, while the Starknet OS deliberately replaces this exact hint with a deterministic, block-hash-seeded implementation.

### Finding Description
In blockifier's Cairo1 hint dispatch, all `Hint::Core` hints (including `CoreHint::RandomEcPoint`) are forwarded verbatim to the upstream `execute_core_hint_base` helper with no override: [1](#0-0) 

By contrast, the Starknet OS/aggregator hint processor macro explicitly special-cases `CoreHint::RandomEcPoint` and replaces it with output derived from a `StdRng` seeded from the poseidon hash of the block hash(es) plus a salt, specifically because it must be reproducible: [2](#0-1) 

The seed itself is computed deterministically from `new_block_hash` values: [3](#0-2) 

This asymmetry is called out in the code's own `TODO(Dori)` comment noting that the Cairo1 handling (and by extension `get_rng`) probably belongs only in the block-execution-time hint processor, i.e., the authors were aware that blockifier and the OS handle this hint differently. Because a class containing this core hint (a legitimate, compiler-emitted `Core` hint, not an `External`/test-only hint that would be rejected) is a class any account can declare and any contract can call into, the non-deterministic value produced during actual sequencer execution can leak into execution outputs (return data, storage writes, emitted events) if the calling Cairo code uses it for anything beyond throwaway internal computation.

### Impact Explanation
If the value produced by `RandomEcPoint` affects the transaction's committed outputs, different sequencer executions of the exact same transaction (e.g., proposer vs. validators re-executing to check the block, or the same node re-executing later) can legitimately compute different state changes. This is a state/consensus-divergence class bug: honest nodes running identical inputs would disagree on the resulting state root because blockifier — unlike the OS — never anchors this specific source of entropy to any deterministic value, so it will differ between any two separate executions of the same block/transaction.

### Likelihood Explanation
Reaching the hint only requires declaring/calling a class whose compiled CASM contains this specific core hint, which is fully within the reach of an ordinary declare/invoke transaction; no special privileges, node role, or timing is needed. The main uncertainty is how often normal compiler output emits this exact hint and whether its result reliably escapes into observable outputs, which is why this is flagged at Medium rather than higher severity.

### Recommendation
Mirror the OS's approach in blockifier: override `CoreHint::RandomEcPoint` (and any other core hints with the same nondeterminism property) with a deterministic, block-context-seeded implementation before falling back to `execute_core_hint_base`, ensuring the same seeding strategy (or an equivalently deterministic one anchored to consensus-agreed data) is used consistently between blockifier's real execution and the OS's re-execution/proving path.

### Proof of Concept
1. Compile a Cairo1 contract whose logic path invokes the corelib/library function that lowers to `CoreHint::RandomEcPoint` (a `Core`, non-external hint permitted in ordinary declared classes), storing or returning the resulting `(x, y)` values.
2. Declare and deploy the contract, then invoke the entry point twice under two independent blockifier executions (e.g., simulate as both proposer-side execution and a separate validator re-execution of the identical transaction/block).
3. Observe that `execute_core_hint_base`'s handling of `RandomEcPoint` in `crates/blockifier/src/execution/syscalls/hint_processor.rs` yields different `(x, y)` in each run (unseeded), while the OS re-execution path in `crates/starknet_os/src/hint_processor/common_hint_processor.rs` would instead have produced one specific deterministic value — demonstrating that blockifier itself has no deterministic anchor, so two blockifier executions of the same transaction can diverge in committed state.

impl HintProcessorLogic for SyscallHintProcessor<'_> {
    fn execute_hint(
        &mut self,
        vm: &mut VirtualMachine,
        exec_scopes: &mut ExecutionScopes,
        hint_data: &Box<dyn Any>,
    ) -> HintExecutionResult {
        let hint = hint_data.downcast_ref::<Hint>().ok_or(HintError::WrongHintData)?;
        // Segment arena finalization is relevant only for proof so there is no need to allocate
        // memory segments for it in the sequencer.
        let no_temporary_segments = true;
        match hint {
            Hint::Core(hint) => {
                execute_core_hint_base(vm, exec_scopes, hint, no_temporary_segments)
            }
            Hint::Starknet(hint) => Ok(execute_next_syscall(self, vm, hint)?),
            Hint::External(_) => {
                panic!("starknet should never accept classes with external hints!")
            }
        }
    }

    /// Hashes the block hashes of the given block inputs to get a seed for the random number
    /// generator.
    fn rng_seed(os_block_inputs: &[&'a OsBlockInput], rng_seed_salt: &Option<Felt>) -> Felt {
        Poseidon::hash_array(
            &os_block_inputs
                .iter()
                .map(|block_input| block_input.new_block_hash.0)
                .chain([rng_seed_salt.unwrap_or_default()])
