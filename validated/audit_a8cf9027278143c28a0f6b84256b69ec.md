### Title
Deposit mempool `remove_deposits` evicts fetched deposits unconditionally regardless of on-chain execution success, causing permanent fund freeze - ([File: crates/sequencer/src/runner.rs])

### Summary
`produce_l2_block_inner` fetches a batch of pending deposits via `fetch_deposits`, but the code that runs afterward at `runner.rs:636-643` calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the *entire fetched list* rather than only the deposits that were actually included and successfully processed in the produced block. If a deposit's system transaction reverts at the EVM level during execution (e.g. `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful`, referenced in `crates/evm/src/evm/executor.rs`, `crates/sovereign-sdk/rollup-interface/src/state_machine/stf.rs`, and `crates/sequencer/src/runner.rs`) and is skipped rather than included, its raw bytes are still passed into `remove_deposits`, which matches by `calc_tx_id` and removes it from `accepted_deposit_txs`/`pending_deposits` regardless of inclusion outcome.

### Finding Description
The binding that must hold is: **deposit removed from `DepositDataMempool` == deposit successfully included in a produced L2 block**. Tracing the code:

- `produce_l2_block_inner` fetches candidate deposits without removing them: `deposit_data = self.deposit_mempool.lock().fetch_deposits(...)` [1](#0-0) .
- `deposit_data` (the *full fetched list*) is passed down into transaction preparation (`dry_run_transactions`) and ultimately into system-transaction application, but after the block is produced and saved, `remove_deposits` is invoked using the same original `deposit_data` variable, not a filtered subset reflecting what was actually applied successfully: [2](#0-1) .
- `DepositDataMempool::remove_deposits` computes `calc_tx_id` for every deposit passed in and unconditionally evicts matching entries from `accepted_deposit_txs` and `pending_deposits`: [3](#0-2) . There is no parameter or mechanism here to distinguish "included/succeeded" deposits from "skipped/failed" ones — the function's only input is the deposit list itself.
- `add_deposit_tx`, once a deposit's `calc_tx_id` is removed from `pending_deposits`, would allow the *same bytes* to be re-added — but the raw deposit blob is never given back to the caller/RPC layer or resubmitted automatically anywhere in this file; the only place `add_deposit_tx` is invoked is via the `citrea_sendRawDepositTransaction` RPC path, which requires the original submitter to resubmit. If nothing resubmits it, it is gone permanently (`pending_deposits` set no longer blocks a duplicate add, but nothing triggers a re-add).

The report's premise about `EvmSystemTransactionNotSuccessful` triggering a "skip and continue without including in `all_txs`" branch could not be fully verified in this pass because the exact `process_sys_txs` function body and the `Evm::execute_call` success-check in `crates/evm/src/call.rs` were not read line-by-line (only confirmed via grep to exist and reference this error variant in `crates/evm/src/evm/executor.rs`, `crates/sequencer/src/runner.rs`, `crates/sovereign-sdk/rollup-interface/src/state_machine/stf.rs`). However, the mempool-side removal logic is independently confirmed to be unconditional and keyed only on the input list `deposit_data`, which is the full fetched batch, not a filtered "successfully applied" set — this is directly verifiable and is the load-bearing part of the described bug.

### Impact Explanation
If any fetched deposit fails to be included in the produced block for any reason (EVM-level revert of the system transaction, a system-transaction application error, or any other skip condition upstream of `remove_deposits`), that deposit is still removed from the sequencer's deposit mempool because `remove_deposits` is called with the unfiltered `deposit_data`. Since the corresponding Bitcoin-side `moveTx` funds are already irrevocably committed by Clementine before the deposit blob is ever submitted to `citrea_sendRawDepositTransaction`, and the deposit bytes are not persisted or automatically retried elsewhere in this codebase once evicted from the in-memory mempool, this results in a real Bitcoin deposit that is never counted or mintable on L2 — a permanent freeze of depositor funds. This is a Critical-severity outcome per the stated impact categories (funds permanently frozen), and it is repeatable for every deposit blob that hits any skip/failure path in this batch, not gated by attacker privilege since the deposit is submitted by an ordinary depositor and the failure condition can be triggered by conditions outside the depositor's control (e.g., a recipient contract's bytecode changing between `eth_call` simulation and inclusion).

### Likelihood Explanation
Whether this is actually exploitable/triggerable depends on details not fully verified in this session: specifically, whether the upstream deposit-processing code (`process_sys_txs`, `Evm::execute_call` in `crates/evm/src/call.rs`) can, on a real code path, skip a fetched deposit without including it in `all_txs`/the produced block while still leaving it inside the `deposit_data` vector passed to `remove_deposits`. If such a skip path exists, no special privilege is needed to trigger it (any account can be a deposit recipient), and the removal bug in `remove_deposits`/`runner.rs:636-643` guarantees mempool eviction happens regardless of block-inclusion success, since the call always uses the full pre-fetch list.

### Recommendation
Change `produce_l2_block_inner` to track precisely which deposits were actually applied/included successfully in the block (e.g., collect the subset of `deposit_data` entries corresponding to system transactions that returned success), and pass only that filtered subset into `remove_deposits`, instead of the full pre-fetch `deposit_data` list at `crates/sequencer/src/runner.rs:636-643`. Any deposit whose system transaction did not succeed should remain in the mempool (or be moved to a dedicated retry/dead-letter queue) so it can be retried in a future block rather than silently and permanently evicted.

### Proof of Concept
This requires verifying the upstream skip behavior in `crates/evm/src/call.rs`/`process_sys_txs` (not confirmed in this session) in addition to the mempool-side bug, which is confirmed. A cargo test in `crates/sequencer` should:
1. Construct two deposit blobs, D1 (valid, executes successfully) and D2 (crafted so the system transaction execution reverts, e.g. `EvmSystemTransactionNotSuccessful`), both accepted via `add_deposit_tx`.
2. Run `produce_l2_block_inner` (or the runner harness equivalent) with both in `deposit_mempool`.
3. Assert on both sides of the binding: (a) inspect `l2_block_result`/`all_txs`/receipts to confirm D2's system tx was NOT successfully included in the block, and (b) inspect `deposit_mempool.accepted_deposit_txs`/`pending_deposits` after block production to check whether D2 was removed via `remove_deposits` despite (a).
4. If D2 is absent from the mempool after the block despite never having succeeded on-chain, the binding is broken and the vulnerability is confirmed as described.

Because the exact skip-without-inclusion behavior in `process_sys_txs`/`Evm::execute_call` was not directly read/confirmed in this pass, I cannot certify with full confidence that step (a) is reachable — only that step (b)'s mempool removal logic (`crates/sequencer/src/deposit_data_mempool.rs:79-109` and its unconditional invocation at `crates/sequencer/src/runner.rs:636-643`) is unconditional and would produce this freeze if (a) is reachable. A Devin session with full repo access should read `crates/evm/src/call.rs::execute_call` and the actual `process_sys_txs` function body (grep showed it only in `runner.rs`, contradicting the report's claim it's a separate function — this needs direct file inspection) to close this gap before treating the finding as fully proven.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
