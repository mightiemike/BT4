### Title
Default (non-hardened) Exchange bonding-curve math loses precision via `double` arithmetic and unchecked `long` overflow, enabling silently incorrect swap accounting - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Mantra `calculate_stableswap_y` finding is about an intermediate-precision type (`Uint256`) being too small for legitimate large-value AMM math, causing either overflow reverts or silent inaccuracy. In java-tron's bancor-style `Exchange` (TRC10 AMM) actuators, the *default* execution path for `ExchangeTransactionContract` / `ExchangeInjectContract` / `ExchangeWithdrawContract` performs the equivalent bonding-curve math using raw Java `double` and unchecked `long` arithmetic, with no overflow/precision protection unless a chain-governance flag (`allowHarden`) is enabled.

### Finding Description
`ExchangeCapsule.transaction()` selects the math engine based on `hardenedCalc`: [1](#0-0) 

When `hardenedCalc` is `false` (the default path unless the `AllowHardenExchangeCalculation` proposal is active), the legacy `ExchangeProcessor` is used, which computes the bonding-curve relay/output amounts entirely in `double`, and updates balances with unchecked `long + long`: [2](#0-1) 

This is the direct analog of the StableSwap issue: instead of an undersized fixed-point integer type (`Uint256`) causing overflow, java-tron's default path uses IEEE-754 `double` (53-bit mantissa, ~15-17 significant decimal digits) to represent ratios of pool balances that can be as large as `Long.MAX_VALUE` (~9.22e18) for TRC10 asset quantities/TRX sun amounts. Once pool balances or swap quantities exceed the precision window of `double`, the `Math.pow(1 + quant/newBalance, 0.0005)` and `Math.pow(1 + supplyQuant/supply, 2000.0)` computations lose significant digits, and the unguarded `balance + quant` / `balance -= supplyQuant` operations can silently wrap on overflow (no `addExact`/`subtractExact`), unlike the hardened path which explicitly uses `StrictMathWrapper.addExact/subtractExact` and `BigDecimal`: [3](#0-2) 

The codebase's own hardened implementation and its regression tests (`hardenedExecuteOverflowThrowsArithmeticException`, `testHardenedTransactionNegativeBalanceThrows`) confirm that the legacy/default path is precisely the one lacking these overflow/precision guards: [4](#0-3) 

Reachability: any account can broadcast an `ExchangeTransactionContract`, which is routed through `ExchangeTransactionActuator.execute()` → `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, where `allowHarden()` reflects the chain-wide `AllowHardenExchangeCalculation` maintenance parameter (off unless a super-representative proposal enabled it): [5](#0-4) 

### Impact Explanation
On chains/networks where `AllowHardenExchangeCalculation` has not been activated (the default/legacy behavior), pools that accumulate large balances (via repeated `ExchangeInjectContract` up to `dynamicStore.getExchangeBalanceLimit()`) can produce swap outputs computed from a `double`-precision bonding curve that diverges from the mathematically correct integer result, and balance bookkeeping additions are not overflow-checked. This can result in economically incorrect exchange settlement amounts credited/debited to accounts, i.e., accounting corruption within the on-chain TRC10 Exchange feature, without requiring any privileged role — any user can trigger it by injecting/trading against a pool with sufficiently large balances.

### Likelihood Explanation
Likelihood is moderate: it requires the network's `AllowHardenExchangeCalculation` maintenance parameter to still be disabled (its default state) and pool balances/quantities large enough to exceed `double`'s effective precision (double loses exact integer representation above 2^53 ≈ 9.007e15, well within the `long` range used for TRC10 balances and TRX sun amounts, and reachable given `getExchangeBalanceLimit()` governs the injectable ceiling). No special privileges or crafted transactions beyond normal `ExchangeInject`/`ExchangeTransaction` contracts are needed.

### Recommendation
Make the `BigDecimal`/overflow-checked (`SafeExchangeProcessor`) path the default, unconditional implementation for all Exchange actuators rather than an opt-in governance flag, and remove the `double`-based `ExchangeProcessor` computation entirely (or restrict it to only the historically-frozen contracts under `dynamicStore.getAllowSameTokenName() == 0`), ensuring bonding-curve math never silently loses precision for large balances/quantities regardless of proposal state.

### Proof of Concept
1. Ensure `AllowHardenExchangeCalculation` is not enabled (default state).
2. Create an Exchange pool (`ExchangeCreateContract`) and repeatedly `ExchangeInjectContract` to raise `firstTokenBalance`/`secondTokenBalance` close to `dynamicStore.getExchangeBalanceLimit()` (large enough that ratios exceed `double`'s 2^53 precision boundary).
3. Broadcast an `ExchangeTransactionContract` with a large `quant`; because `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(..., allowHarden()=false)`, the swap is computed via `ExchangeProcessor.exchange()` using `double` math and unguarded `long` addition [6](#0-5) , producing a settlement amount that diverges from the exact integer bonding-curve result (or, in overflow edge cases, wraps silently since no `addExact` is used, unlike the hardened path demonstrated to throw in `hardenedExecuteOverflowThrowsArithmeticException`) [7](#0-6) .

*Note: I could not directly verify the exact default numeric value of `dynamicStore.getExchangeBalanceLimit()` or the default on/off state of `AllowHardenExchangeCalculation` from the available index (the `DynamicPropertiesStore.java` default-value initializers were not retrievable in this session), so the precise minimum pool size needed to trigger measurable precision loss is not fully confirmed and should be validated directly against `DynamicPropertiesStore` before treating this as conclusively exploitable at current default limits.*

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
