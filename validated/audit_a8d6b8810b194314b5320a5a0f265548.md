### Title
Non-hardened exchange balance update can drive `ExchangeCapsule` token balances negative, permanently breaking future trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The reported Juicebox bug is a class of "derived-state subtraction that assumes monotonic growth, but can go negative once the reverse operation (burn/redeem) occurs, permanently breaking the shared function." The closest reachable analog in java-tron is `ExchangeCapsule.transaction()`, which updates a **shared, market-wide** bancor-style token pool (`firstTokenBalance`/`secondTokenBalance`) using plain `long` subtraction in the default (non-hardened) path, with no floor/guard against the computed balance going negative.

### Finding Description
`ExchangeCapsule.transaction()` computes the resulting pool balances after a trade: [1](#0-0) 

When `hardenedCalc` is `false` (the default, legacy path still used unless the chain parameter is explicitly enabled), the new balances are computed with plain `long` arithmetic:
```
newSecondTokenBalance = secondTokenBalance - buyTokenQuant;
...
newFirstTokenBalance = firstTokenBalance - buyTokenQuant;
```
There is **no check** in this branch that the resulting balance is non‑negative — the `hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)` guard only fires when hardened mode is enabled. `buyTokenQuant` itself comes from `ExchangeProcessor.exchange()`, a bancor-relay formula using `double` math with `Maths.pow`, which under specific input ratios (large `sellTokenQuant` relative to `buyTokenBalance`, or repeated rounding) can return a `buyTokenQuant` that exceeds the actual pool reserve, especially for edge-case ratios not covered by `ExchangeTransactionActuator`'s validate-time checks (which only bound `tokenExpected`/slippage and balance limits, not the exact bancor output against the opposing reserve).

Once one side's balance is negative and persisted via `Commons.putExchangeCapsule`, every subsequent trade against that exchange pool re-enters `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which divides by `newBalance` (`balance + quant`) and computes `Math.pow(1 + quant/newBalance, ...)`. With a corrupted (negative) `balance`, these computations become undefined/erratic (NaN, Infinity, or wildly wrong values cast to `long`), and validation checks like `firstTokenBalance == 0 || secondTokenBalance == 0` (checked in `ExchangeTransactionActuator.doValidate`) do not catch a *negative* balance — only a zero one. This mirrors the Juicebox root cause: a derived quantity computed from state that is only ever validated for the "growing" direction, with no defensive floor for the "shrinking" direction, permanently corrupting a shared accounting structure that all future callers depend on. [2](#0-1) 

### Impact Explanation
If a pool's `firstTokenBalance`/`secondTokenBalance` is driven negative, the exchange pool becomes permanently unusable/corrupted for all participants (any transaction, injection, or withdrawal against that `exchangeId` now operates on invalid negative reserves), which is an availability/accounting-corruption impact analogous to the Juicebox "minting and redeeming break forever" bug — except here it affects a specific on-chain TRX/TRC-10 exchange market rather than an NFT tier.

### Likelihood Explanation
This requires the non-hardened path to be active (i.e., `allowHardenExchangeCalculation` not enabled on the network) and requires finding specific quantities/ratios where the bancor `double`-based `ExchangeProcessor.exchange()` computes a `buyTokenQuant` exceeding the actual reserve, which the existing test suite (`ExchangeProcessorTest`, hardened-mode tests) suggests the project is already aware of and actively hardening against via `SafeExchangeProcessor`/`hardenedCalc`. I could not fully verify with concrete numeric inputs (due to running out of tool iterations) whether such an overshoot is actually reachable in the non-hardened path on the current default configuration, so likelihood is **uncertain/moderate** rather than confirmed.

### Recommendation
Enforce the same non-negative-balance invariant in the non-hardened path as in `hardenedCalc`, i.e., always validate `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` (or migrate fully to `SafeExchangeProcessor`/hardened math) before persisting `ExchangeCapsule` balances, regardless of the `allowHardenExchangeCalculation` flag.

### Proof of Concept
Not independently reproduced with concrete numbers — this requires constructing sell/buy quantities that make `ExchangeProcessor.exchange()`'s double-precision bancor formula return a `buyTokenQuant` greater than the opposing reserve while passing `ExchangeTransactionActuator.doValidate()`'s existing checks (`tokenExpected`, `balanceLimit`, non-zero reserves). This should be validated further (e.g., via `ExchangeProcessorTest`-style differential testing against `SafeExchangeProcessor`) before treating this as a confirmed, exploitable analog.

    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();
