### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by HMAC verification, enabling cross-tenant webhook replay/confusion - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
The Beacon-Kit report describes a class of bug where a security check validates one piece of data (a deposit) but never binds that validated data to the specific context it is later trusted for (the deposit contract/execution payload), letting an attacker supply a validly-signed artifact and have it applied to the wrong context. The analogous flaw in shopify-app-js is in webhook processing: the webhook HMAC only authenticates the raw request body, but the shop identity (`X-Shopify-Shop-Domain` header) that the app uses to look up which merchant's session/access token to act on is never included in that signature.

### Finding Description
`validateHmacFromRequestFactory` computes and checks the webhook HMAC exclusively over `rawBody`: [1](#0-0) 

The `domain`, `topic`, `apiVersion`, and `webhookId` headers are read and trusted separately, after HMAC validation, with no cryptographic binding to the signed body: [2](#0-1) 

Both the app-remix and app-react-router webhook authenticators then use the unauthenticated `check.domain` value directly to look up (and, in the offline-session path, refresh/act with) the merchant's stored access token, and hand callers an `admin` client scoped to that shop: [3](#0-2) [4](#0-3) 

Because `apiSecretKey` is shared across all shops that install a given app, any attacker who legitimately operates a shop with the app installed can capture a genuinely Shopify-signed `(rawBody, hmac)` pair from their own store's webhook deliveries. Since the HMAC never covers the `domain` header, that same `(rawBody, hmac)` pair remains valid when replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to an arbitrary victim shop that also has the app installed. The validation logic in `validate.ts`/`hmac-validator.ts` only checks that the body was signed by *some* legitimately-Shopify-originated webhook for the app — never that the signed body actually originated for the shop claimed in the domain header — exactly mirroring the deposit-contract report's root cause: a valid signature is accepted without verifying it corresponds to the specific entity/context it is later trusted to represent.

The test suite shows the authors are aware of adjacent confusion attacks (they explicitly test that an OAuth state-cookie signature cannot be replayed as a webhook HMAC): [5](#0-4) 
but there is no equivalent protection or test covering domain-header substitution across two different shops that both have valid webhook deliveries for the same app.

### Impact Explanation
An attacker who controls one shop with the app installed can craft a webhook delivery whose body content they control (e.g., trigger `customers/redact`, `orders/create`, or any subscribed topic on their own store, capturing the resulting `(body, hmac)`), then replay that exact request to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain`/`shopify-events-shop-domain` header for any other installed shop. The webhook handler will authenticate this as valid, load the *victim* shop's offline session/access token via `ensureValidOfflineSession(params, check.domain)`, and process the attacker-controlled payload as though it originated from the victim, using the victim's `admin` API credentials. Depending on how the app's webhook handlers use the payload (e.g. writing data, deleting resources, triggering downstream actions keyed off payload fields), this can result in cross-tenant data corruption, unauthorized actions performed with another merchant's access token, or state confusion between tenants — reachable from a fully anonymous HTTP POST requiring no privileged access, satisfying "accepted forged Shopify request" / "cross-tenant access."

### Likelihood Explanation
Exploitation requires the attacker to operate (or install the app on) at least one shop to obtain a genuinely-signed `(body, hmac)` pair, which is realistic for any public/multi-tenant Shopify app since installation is generally open. No secret material needs to be recovered; only header substitution on replay is needed, and the webhook endpoint is unauthenticated and reachable directly over HTTP. This is a moderate-likelihood, network-reachable, anonymous-actor issue.

### Recommendation
Bind the trusted shop/topic identity to the same value that is cryptographically verified. Options:
- Include the `domain` (and ideally `topic`, `webhookId`) header values as part of the HMAC-signed payload comparison, or
- After HMAC success, independently confirm that `check.domain` actually owns a subscription for `check.webhookId`/`check.topic` (e.g., cross-check against the app's own webhook registry or Shopify's Admin API) before using it to load a session, or
- At minimum, ensure the offline session lookup for a given `domain` also validates that a previously-issued, still-valid webhook registration/token exists for that shop and topic combination, rejecting replays where the claimed domain does not match provenance of the signed body.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`, and separately identify/observe that the app is also installed on victim shop `victim.myshopify.com` (e.g., because both are public app installs).
2. Trigger a subscribed webhook topic (e.g. `orders/create`) on `attacker.myshopify.com` with attacker-controlled order data; capture the raw POST including the `X-Shopify-Hmac-Sha256` header and body that Shopify sends to the app's webhook URL.
3. Replay that exact POST body and `X-Shopify-Hmac-Sha256` header to the same webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `validateHmacFromRequestFactory` accepts the request (HMAC matches body), `checkWebhookHeaders` extracts `domain = victim.myshopify.com`, and `authenticateWebhookFactory` loads `victim`'s offline session and builds an `admin` client scoped to `victim`, then invokes the app's webhook handler with the attacker's payload as if it came from `victim`.
