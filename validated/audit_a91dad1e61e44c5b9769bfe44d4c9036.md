### Title
Bancor-curve rounding/precision errors in TRC10 `Exchange` swaps can corrupt pool balances and diverge across nodes - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The TRC10 `Exchange` feature implements a Bancor-style bonding curve (the java-tron analog of a Proteus/AMM identity curve) that any account can trade against via a broadcast `ExchangeTransactionContract`. The core math in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` uses `double`-precision `Math.pow` and truncates the result to `long` with a raw cast, exactly the kind of unreviewed rounding-direction choice the external report flags as dangerous for identity-curve/AMM implementations.

### Finding Description
`ExchangeCapsule.transaction()` selects between two swap implementations based on a governance-gated flag: the legacy `ExchangeProcessor` (double math, optionally `StrictMath`) or the newer `SafeExchangeProcessor` (BigDecimal, explicit `RoundingMode`), guarded by `dynamicStore.allowHardenExchangeCalculation()`/`allowStrictMath()`. [1](#0-0) 

In the legacy path, both curve steps compute a floating-point result and truncate toward zero via an unchecked `(long)` cast, with no explicit, documented rounding-direction policy: [2](#0-1) 

The project's own test suite proves this is not merely a theoretical concern: for identical `(sellBalance, buyBalance, sellQuant)` inputs, switching only the `useStrictMath` flag yields a *different* settled swap amount, and the results only match the BigDecimal `SafeExchangeProcessor` when `useStrictMath` is enabled: [3](#0-2) 

This mirrors the report's root cause exactly: an integer/floating-point division/rounding step whose direction and precision were never formally specified, verified only empirically by fuzzing-style tests after the fact, and only fixed by introducing a second "hardened" implementation (`SafeExchangeProcessor`) rather than by proving the original math correct. The hardened path is opt-in via a chain parameter (`allowHardenExchangeCalculation`) and `dynamicStore.allowStrictMath()` toggles which JDK `pow` implementation is used underneath; per-architecture wrappers (`platform/.../arm/.../MathWrapper.java`, `platform/.../x86/.../MathWrapper.java`) exist specifically because `Math.pow` is not guaranteed bit-identical across CPU/JIT implementations, while `StrictMath.pow` is. Any exchange still executing on the legacy, non-hardened, non-strict path is exposed to (a) balance-corrupting truncation error in the curve output and (b) platform-dependent floating-point results for the same transaction.

### Impact Explanation
- Accounting corruption: because the swap output is derived from two chained floating-point curve evaluations each truncated independently, the amount credited to the trader and the amount left in the pool's `firstTokenBalance`/`secondTokenBalance` can drift from the "true" curve value, similar to how Alice's LP deposit in the report yielded a USD 90 credit instead of USD 100. Over many swaps (especially near extreme balance ratios, analogous to the report's "close to the X/Y asymptote" observation), the exchange's on-chain reserves can diverge materially from the value implied by the bonding curve, degrading the pool for the exchange creator and future traders.
- Consensus-divergence risk: if `allowStrictMath()`/`allowHardenExchangeCalculation()` are not uniformly enabled across the network (they are proposal-gated chain parameters, meaning historically or on forks/private chains they can be off), nodes could theoretically compute different `(long)`-truncated results for the same `ExchangeTransactionContract` if the underlying non-strict `Math.pow` is not bit-reproducible across the JVM/CPU architectures the network runs on — this is precisely why per-architecture `MathWrapper` classes exist in this codebase.
- Reachability: `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` for every account-submitted swap; no privileged role is required. [4](#0-3) 

### Likelihood Explanation
Low-to-moderate. Exploitability depends on the state of the `allowHardenExchangeCalculation`/`allowStrictMath` chain parameters on a given deployment; where hardening is fully active, the BigDecimal `SafeExchangeProcessor` mitigates most of the risk. However, the legacy path remains reachable by any account and the test-proven output divergence between math modes demonstrates the rounding behavior was never formally specified before being patched, exactly the auditing gap the external report calls out.

### Recommendation
- Document and unit-test the required rounding direction (must always round in the pool's favor, never the trader's) for every step of `exchangeToSupply`/`exchangeFromSupply`, for both `ExchangeProcessor` and `SafeExchangeProcessor`.
- Deprecate/retire the non-hardened `ExchangeProcessor` double-math path entirely (rather than gating it behind an optional proposal) once `SafeExchangeProcessor` is confirmed correct, to eliminate cross-architecture floating-point risk.
- Add property/fuzz tests (per the report's "Appendix C" recommendation) that assert invariants such as "pool value (in terms of the bonding curve) never decreases after a swap" and "trader never receives more than the exact curve output," across a wide range of balances, not just the fixed magnitudes in the current test data.

### Proof of Concept
Not applicable as a working exploit transaction — this analysis is based on static review of `ExchangeProcessor`/`SafeExchangeProcessor`/`ExchangeCapsule` and the existing `ExchangeProcessorTest.testStrictMath` unit test, which already empirically demonstrates that identical exchange inputs produce different settled amounts depending on the `useStrictMath` flag: [5](#0-4)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
