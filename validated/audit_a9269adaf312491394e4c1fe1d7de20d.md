### Title
Exchange pool ratio can be sandwiched to grief the pool creator's `ExchangeWithdraw` calls - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
java-tron's built-in TRC10 "Exchange" (a bancor-style, on-chain liquidity pool) lets only the pool creator withdraw liquidity via `ExchangeWithdrawActuator`. The withdrawal's validity is gated by a "precision" check computed from the *current* on-chain token-balance ratio of the pool at execution time. Any unprivileged account can shift that ratio in the same block via the public `ExchangeTransactionActuator` (buy/sell), sandwiching the creator's withdraw transaction so its ratio-based precision check fails and the withdrawal reverts, exactly mirroring the reported `reduceWeight` griefing pattern where a privileged action is gated on a live, publicly-manipulable pool value.

### Finding Description
The creator-only withdraw path recomputes `anotherTokenQuant` from the exchange's live balances and requires the client-supplied `tokenQuant`/expected ratio to match within a very tight tolerance (0.01%), or the transaction is rejected as "Not precise enough": [1](#0-0) 

This ratio (`firstTokenBalance` / `secondTokenBalance`) is exactly the pool state that the report's `getMarketCap()` (`reserveBalance / reserve.weight`) analog represents in DynamicLiquidTokenConverter — a value derived from mutable pool reserves that is read fresh at execution time, not committed/locked when the privileged transaction is built. Because only the exchange creator may withdraw (`account[...] is not creator`), this is the privileged "owner" role analogous to the converter owner: [2](#0-1) 

Any unprivileged account, however, can freely change `firstTokenBalance`/`secondTokenBalance` before the creator's withdraw executes by calling the public `ExchangeTransactionActuator`, which directly mutates the pool balances via the bancor-relay formula in `ExchangeCapsule.transaction`: [3](#0-2) 

Because the creator computes and signs the withdraw transaction (choosing `tokenQuant`) based on the pool ratio observed at submission time, and validators/block producers can reorder or a third party can front-run/back-run the transaction within the same block, an attacker can buy/sell against the pool immediately before the creator's withdraw is packed, shifting the ratio just enough that the recomputed `anotherTokenQuant` no longer lies within the 0.01% tolerance band, causing `ContractValidateException("Not precise enough")` and reverting the creator's withdrawal — a direct, reachable analog of the bandit's marketcap-sandwich griefing of `reduceWeight`.

### Impact Explanation
This allows any unprivileged actor to deny/grief the pool creator's liquidity withdrawal transactions by manipulating the pool ratio around them, forcing repeated failed transactions (wasted fees/bandwidth) and blocking timely liquidity withdrawal — an availability/griefing impact on a privileged, owner-only accounting operation, matching the "Acknowledged" severity class of the original finding (owner-risk griefing via sandwich rather than fund theft).

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to hold sufficient balance to move the pool ratio meaningfully and to time their buy/sell transactions around the creator's withdraw in the same block (feasible for any account observing pending transactions/mempool), and the cost is limited to bancor-style conversion loss and transaction fees, similar to the acknowledged low-cost griefing described in the original report.

### Recommendation
Widen or remove the tight ratio-precision tolerance check that depends on live pool state at execution time, or let the withdrawer specify an acceptable slippage/tolerance range (as is already done for `ExchangeTransactionActuator`'s `expected` field) rather than relying on values that can shift from unrelated public buy/sell transactions between transaction construction and execution.

### Proof of Concept
1. Attacker observes the exchange creator's pending `ExchangeWithdrawContract` transaction (built using pool balances at time T, expecting `anotherTokenQuant` within 0.01% tolerance).
2. Attacker submits an `ExchangeTransactionContract` (buy or sell) that lands in the same block before the creator's withdraw, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction` [4](#0-3) .
3. When the creator's withdraw executes, `ExchangeWithdrawActuator.doValidate()` recomputes `anotherTokenQuant` from the now-shifted balances; the deviation from the creator's originally intended amount exceeds the 0.01% tolerance, throwing `ContractValidateException("Not precise enough")` [5](#0-4) , reverting the creator's withdrawal while the attacker pays only conversion/fee costs.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
