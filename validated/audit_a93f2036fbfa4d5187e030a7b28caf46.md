## Finding

### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify to accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (chunk executor replay, `aptos-debugger`, and the CLI) to confirm that a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` retrieved from a backup/archive. The function validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but by its own documented admission does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) [2](#0-1) 

### Finding Description
The comment left in the code is explicit:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

`TransactionInfo` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields that summarize the Jellyfish Merkle / hot-state / native-position roots at that version. [4](#0-3) 

These fields are exactly the invariant that state-restore/replay is supposed to protect (per the "Proof And Storage Pivots" gate): the committed root must match what execution produced. In the normal block-commit path, `DoStateCheckpoint::get_state_checkpoint_hashes` does compare "known" checkpoint hashes (from `TransactionInfo`) against locally computed ones and errors on mismatch. [5](#0-4) 

However, `ensure_match_transaction_info` is a separate, narrower comparator used specifically by replay/debug tooling (`aptos-debugger`, `cli/src/commands.rs`, and `chunk_executor/mod.rs`) to validate a `TransactionOutput` obtained independently (e.g., from replaying an archived transaction) against the trusted `TransactionInfo`. Because this comparator omits the checkpoint-hash fields, any tool relying solely on it (rather than the full `DoStateCheckpoint` pipeline) can report "match" even when the locally computed state/hot-state/position Merkle root differs from the authenticated one recorded in the accumulator-backed `TransactionInfo`.

### Impact Explanation
If a downstream consumer of `ensure_match_transaction_info` (verification/replay tooling) treats a "match" as proof that local execution reproduced the exact committed ledger state, this comparator gives a false positive: a divergent state root (JMT root, hot-state root, or the new native-position root) is silently accepted. This directly matches the "Committed state that differs from the correct VM result" and "Authenticated ... output bound to the wrong ... proof context" impact categories in the gate — a proof-bearing/verification codepath does not actually bind to the correct root, undermining the guarantee that replay-verify or archive-based reconstruction is asset/ledger-state consistent.

### Likelihood Explanation
This is a real, currently-shipped gap acknowledged in-code (not speculative): the comment states this is a live limitation gated only by whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, and it explicitly calls out `db-tool`'s `replay_on_archive` as an affected caller. I was not able to fully trace, within the available iterations, every call site (e.g. the exact code in `aptos-debugger/src/aptos_debugger.rs` and `db-tool/src/replay_verify.rs`) to confirm whether an additional independent state-root check is layered on top before this comparator's result is treated as final. That verification is necessary to determine whether this gap is currently exploitable in the default replay-verify path or only in the not-yet-enabled trading-native feature. Given the indexing limits, I recommend a full read of `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_verify.rs` to confirm there is no redundant state-checkpoint-hash check guarding these call sites.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values (when available) before any callers treat a match as validating full ledger-state equivalence, particularly before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled in production.

### Proof of Concept
Not independently constructed — this is a static-code-review finding based on the explicit TODO/comment plus the field definitions; a concrete PoC would require exercising `db-tool`'s `replay_on_archive` (or `aptos-debugger`) with a crafted transaction output whose write-set/event hashes match but whose resulting state root diverges, to demonstrate that verification reports success. I could not confirm this end-to-end within the available tool budget.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),

            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {

        let num_txns = execution_output.to_commit.len();

                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,

                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
