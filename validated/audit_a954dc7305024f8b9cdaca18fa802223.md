This confirms the vulnerability: `LenientCanonicalizeTxHash`/`LenientCanonicalizeAddress` are lenient — for unparseable/non-eip155/non-solana namespace chains (the `default` case), the "canonicalization" of `TxHash`, `LogIndex`, and `SourceChain` is only `strings.TrimSpace`, with **no character restriction, and specifically no rejection of the `:` delimiter**. `ValidateBasic()` on `Inbound` also only requires `TxHash` and `LogIndex` to be non-empty strings, and requires `SourceChain` to merely `strings.Contains(chain, ":")` — it does not restrict the number of colons or the character set of any of these three fields.

### Title
Delimiter-injection collision in `GetInboundUniversalTxKey` allows a UTX identity clash across distinct logical inbound events - (File: `x/uexecutor/types/keys.go`)

### Summary
`GetInboundUniversalTxKey` builds the canonical identity of a `UniversalTx` by naively concatenating three attacker-influenced string fields with a `:` separator before hashing, exactly the JSON-injection root cause from the external report (unescaped delimiter characters in attacker-controlled fields shifting the parsed field boundary). Unlike the ballot-key derivation function in the same file, `hashFields`, which was explicitly designed to be "injective" against this exact class of bug, `GetInboundUniversalTxKey` does not use it.

### Finding Description [1](#0-0) 
```go

```
The comment directly above `hashFields` in the same file explains why per-field hashing is required [2](#0-1) , but `GetInboundUniversalTxKey` predates/bypasses that protection and instead does a single `Sprintf` + one `sha256`, exactly the pattern the codebase's own doc warns against.

`SourceChain`, `TxHash`, and `LogIndex` are all submitted by Universal Validators from `MsgVoteInbound`, ultimately derived from source-chain event data (`RawPayload`, sender-controlled fields on external chains such as Solana memo/instruction data, or non-eip155/non-solana namespaces which fall into the `default:` branch of `CanonicalizeTxHashByNamespace`/`CanonicalizeAddressByNamespace`) — see [3](#0-2) . For any chain namespace other than `eip155` or `solana`, canonicalization is a no-op `default: return addr, nil` / `default: return txHash, nil`, so a colon embedded in `TxHash` or `LogIndex` (or extra colons embedded in `SourceChain`, which is only checked to `Contains(":")`, per [4](#0-3) ) passes straight through unmodified.

Because `ValidateBasic` only requires these three fields be non-empty/contain `:` — never restricting character content or count of separators — an attacker who controls the txHash/logIndex/tx metadata on a non-EVM/non-Solana registered source chain (or any chain string reaching the `default` canonicalization branch) can craft two logically distinct inbound events whose `(chain, txHash, logIndex)` tuples serialize to the identical `"%s:%s:%s"` string, e.g.:
- Event A: `chain="x:1"`, `txHash="abc:2"`, `logIndex=""`
- Event B: `chain="x:1"`, `txHash="abc"`, `logIndex="2"`

Both produce `data = "x:1:abc:2"` (note the empty `logIndex` field silently vanishes into the format string), and thus the identical sha256 UTX key.

### Impact Explanation
`GetInboundUniversalTxKey` is the canonical identity used to look up/merge `UniversalTx` records (`PendingInbounds`, `UniversalTx` collection) across the inbound lifecycle. A colon-boundary collision lets an attacker's crafted second event resolve to (and mutate/append to) the same `UniversalTx` record as a prior, unrelated, honestly-observed inbound — this can cross-link independent inbound observations into one UTX, corrupting `UniversalTx` state, double counting/merging PCTx or outbound entries under the wrong UTX id, or letting a bogus event piggyback the identity of a legitimate high-value deposit's UTX record. This falls squarely under the "forged, replayed, mismatched, or cross-linked inbound ... state accepted through user-reachable flows" and "corruption of ... canonical UniversalTx state" categories in scope.

### Likelihood Explanation
Exploitability depends on whether any currently-registered `ChainConfig` uses a `chain` string whose CAIP-2 namespace isn't `eip155` or `solana` (hits the no-op `default` canonicalization branch), and whether the source-chain event parser for that VM type passes through attacker-influenced strings for `TxHash`/`LogIndex` without further hex/format enforcement before `MsgVoteInbound` is submitted. `x/uregistry` currently only documents EVM/SVM types being live, so likelihood is currently constrained by which chains are actually onboarded (admin-controlled, but chain onboarding itself is out of scope — only the missing intra-repo invariant is in scope here). Given the explicit defensive comment on `hashFields` acknowledging this exact bug class was already fixed for ballot keys but missed for the UTX identity key, this is a real gap rather than a theoretical one.

### Recommendation
Route `GetInboundUniversalTxKey` (and `GetPcUniversalTxKey`, `GetOutboundRevertId`, `GetRescueFundsOutboundId`, which have the same raw `Sprintf`+single-hash pattern) through the existing `hashFields` per-field-hashing helper, exactly as `GetInboundBallotKey`/`GetOutboundBallotKey` already do, so no field value can ever shift a delimiter boundary and collide with a different logical tuple.

### Proof of Concept
1. Register (or otherwise reach) a source chain whose CAIP-2 namespace is not `eip155`/`solana` so `CanonicalizeTxHashByNamespace`/`CanonicalizeAddressByNamespace` fall through to their `default` no-op branches.
2. Submit `MsgVoteInbound` for Event A with `SourceChain="x:1"`, `TxHash="abc:2"`, `LogIndex=""`, and get it voted to finality, producing UTX key `sha256("x:1:abc:2")`.
3. Submit a second, unrelated `MsgVoteInbound` for Event B with `SourceChain="x:1"`, `TxHash="abc"`, `LogIndex="2"`. `GetInboundUniversalTxKey` computes the identical string `"x:1:abc:2"` → identical sha256 key, causing Event B's finalization logic to read/update the `UniversalTx` record that legitimately belongs to Event A.

*Caveat*: I could not fully verify from the index which chain-namespace configs are live in the current registry deployment (only `eip155`/`solana` canonicalizers exist in `utils/canonical.go`), so exploitability may currently be limited to chains not yet supported end-to-end. The root-cause code defect (delimiter injection in `GetInboundUniversalTxKey`) is confirmed and present regardless.

// hashFields = sha256( hex(sha256(domain)) : hex(sha256(f0)) : ... ). Per-field
// hashing makes it injective — a sub-hash can't contain ':', so no field value
// can shift a boundary and collide with a different tuple.
func hashFields(domain collections.Prefix, parts ...string) string {
	hashed := make([]string, 0, len(parts)+1)
	d := sha256.Sum256(domain.Bytes())
	hashed = append(hashed, hex.EncodeToString(d[:]))
	for _, p := range parts {
		sum := sha256.Sum256([]byte(p))
		hashed = append(hashed, hex.EncodeToString(sum[:]))
	}
	final := sha256.Sum256([]byte(strings.Join(hashed, ":")))
	return hex.EncodeToString(final[:])
}
