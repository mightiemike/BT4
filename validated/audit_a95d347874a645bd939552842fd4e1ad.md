### Title
Panic/crash of the L1 events transaction manager caused by a fee-zero L1→L2 message ("many uncancelable/undismissable L1 handler transactions") - (File: `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
The external report describes a griefing bug class: an attacker crafts a resource (a malicious order/token) that, when the protocol later tries to process/clean it up, always reverts, permanently corrupting protocol bookkeeping. The analogous, reachable path in this sequencer is the **L1 handler transaction commit flow**: an unprivileged L1 message sender can create an `L1HandlerTransaction` whose `paid_fee_on_l1` is `0`. When such a transaction is executed by any sequencer node (proposer or validator), the transaction is simultaneously classified as both "consumed" and "rejected." Feeding both classifications into `TransactionManager::commit_txs` triggers a hard `assert!` panic in `TransactionRecord::mark_rejected`, crashing every node that processes the block.

### Finding Description
In `crates/blockifier/src/transaction/l1_handler_transaction.rs` (lines ~92-113), after successfully executing the L1 handler call and **committing** the transactional state, the code performs a fee-check: [1](#0-0) 
If `paid_fee_on_l1 == Fee(0)` — a value fully controlled by whoever sends the L1→L2 message on L1 (an unprivileged L1 message sender) — `execute_raw` returns `Err(TransactionExecutionError::TransactionFeeError(...))`, even though the state was already committed as successful.

In `crates/apollo_batcher/src/block_builder.rs`, `collect_execution_results_and_stream_txs` unconditionally records **every** `L1Handler` transaction hash into `consumed_l1_handler_tx_hashes`, *before* checking whether execution succeeded or failed: [2](#0-1) 
Then, if the result is `Err` (as in the fee-zero case above), the same tx hash is *also* inserted into `rejected_tx_hashes`: [3](#0-2) 

In `crates/apollo_batcher/src/batcher.rs`, `commit_proposal_and_block` derives `rejected_l1_handler_tx_hashes` as the **intersection** of `rejected_tx_hashes` and `consumed_l1_handler_tx_hashes` — i.e., exactly the tx hashes that are simultaneously "consumed" and "rejected" — and passes both `consumed_l1_handler_tx_hashes` (as `committed_txs`) and this intersection (as `rejected_txs`) to the L1 events provider's `commit_block`: [4](#0-3) 

`TransactionManager::commit_txs` then processes `committed_txs` first (calling `mark_committed`, which sets `record.committed = true`), and afterwards processes `rejected_txs` (calling `mark_rejected` on the *same* tx hash, since it is in both sets): [5](#0-4) 

`TransactionRecord::mark_rejected` explicitly asserts the transaction was never already committed: [6](#0-5) 

Because the tx hash was already marked committed one line earlier in the same `commit_txs` call, this assertion **always fails**, causing a panic.

### Impact Explanation
This is triggerable by any unprivileged L1 message sender (a party who calls `sendMessageToL2` on the Starknet core contract on L1 with zero fee attached) and reachable purely through the normal L1-handler transaction pipeline — no operator/proposer misbehavior is required. Since `commit_block`/`commit_txs` is executed by **every** node that processes the corresponding L2 block (the proposer building the block and every validator validating/committing it), a single malformed/fee-zero L1 message causes a synchronized panic across the network at the moment that block is committed. This is not a bounded local failure — it is an honest-node-wide crash that prevents the chain from progressing, matching the "network unable to confirm new transactions" acceptance criterion, and is strictly worse than the referenced report's "gas-griefing" impact, since it is a full liveness failure rather than wasted gas.

### Likelihood Explanation
High. The only precondition is sending an L1→L2 message with `paid_fee_on_l1 == Fee(0)` (fully attacker-controlled on L1) targeting any valid selector/contract that executes without reverting on L2. This requires no special privileges, no coordination with sequencer operators, and no race conditions — it is deterministic given the fee-check logic in `l1_handler_transaction.rs` and the unconditional "consumed" tagging plus intersection-based "rejected" tagging in the batcher.

### Recommendation
- In `collect_execution_results_and_stream_txs`, only add an `L1Handler` transaction hash to `consumed_l1_handler_tx_hashes` when execution actually succeeded (`Ok` branch), not unconditionally before checking the result.
- Ensure a given transaction hash is never present in both the "committed" and "rejected" sets passed to `TransactionManager::commit_txs`; these sets must be mutually exclusive by construction.
- Alternatively/additionally, make `TransactionRecord::mark_rejected`/`mark_committed` tolerant (or explicitly reconcile the fee-error-after-commit case) rather than relying on an `assert!` that can be hit by adversarial-but-otherwise-valid L1 input, since a panic here is a liveness-critical failure mode.
- Reconsider treating the "insufficient L1 fee" case: since the state is already committed by the time this check runs, consider treating it consistently as `Committed`/rejected-with-revert rather than an `Err` result that reaches the rejected-set logic at all.

### Proof of Concept
1. Attacker calls `sendMessageToL2` (or equivalent) on the L1 Starknet core contract targeting any valid L2 contract/selector that would execute successfully, but sets the L1 message fee to `0`.
2. The scraper/L1 events provider picks up this message and creates an `L1HandlerTransaction` with `paid_fee_on_l1 = Fee(0)`.
3. When a sequencer node (proposer or validator) includes this transaction in a block, `execute_raw` in `crates/blockifier/src/transaction/l1_handler_transaction.rs` executes the call successfully, commits the state, then hits the `paid_fee == Fee(0)` branch and returns `Err(TransactionFeeError::InsufficientFee)`.
4. `collect_execution_results_and_stream_txs` in `crates/apollo_batcher/src/block_builder.rs` puts the tx hash into `consumed_l1_handler_tx_hashes` (unconditional) and into `rejected_tx_hashes` (because of the `Err`).
5. `commit_proposal_and_block` in `crates/apollo_batcher/src/batcher.rs` computes `rejected_l1_handler_tx_hashes` as the intersection, containing this tx hash, and calls `l1_events_provider_client.commit_block(consumed_l1_handler_tx_hashes, rejected_l1_handler_tx_hashes, height)`.
6. `TransactionManager::commit_txs` in `crates/apollo_l1_events/src/transaction_manager.rs` calls `mark_committed()` on the tx hash (from the `committed_txs`/consumed set), then calls `mark_rejected()` on the same hash (from the rejected set).
7. `TransactionRecord::mark_rejected` in `crates/apollo_l1_events/src/transaction_record.rs` executes `assert!(!self.committed, ...)`, which fails since `committed` was just set to `true`, causing a panic on every node processing this block's commit.

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(
                "Rejected L1 handler tx has no record. Unreachable: all L1 handler txs in a \
                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }
    }
