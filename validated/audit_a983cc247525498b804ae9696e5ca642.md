### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/verify-execution tooling accept state-root divergence - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2204` is the sole comparator used by replay/verify-execution tooling to confirm a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` taken from a signed chunk/ledger proof. It checks status, gas used, write-set hash, and event root hash, but the code contains an explicit `TODO(trading-native)` acknowledging that it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed local values.

### Finding Description
`ensure_match_transaction_info` is called from:
- `execution/executor/src/chunk_executor/mod.rs:692` inside `verify_execution`, which is the code path exercised by chunk-executor "verify execution" replay mode.
- `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`, all of which are used to validate that local re-execution of historical mainnet transactions matches the authenticated, validator-signed `TransactionInfo` stored in the archive.

The function body [1](#0-0)  validates `status`, `gas_used`, `write_set_hash` (via `state_change_hash`), and `event_root_hash`, then explicitly documents the gap: [2](#0-1) 

`TransactionInfo` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as authenticated fields (`TransactionInfoV1`): [3](#0-2) . These are the Sparse-Merkle/JMT roots summarizing world state (including the new "native position" state managed via `StateKeyInner::TradingNative`, see `types/src/state_store/state_key/inner.rs:93-100`). Because `ensure_match_transaction_info` never compares these fields to what the local execution/state-checkpoint pipeline produces, a divergence between the locally-computed state root and the authenticated one recorded on-chain will not be flagged as an error by any of the four call sites above.

By contrast, the online chunk-executor commit path (`DoLedgerUpdate`/`DoStateCheckpoint`) does compute these hashes and folds them into the `TransactionInfo` that is hashed and chained into the transaction accumulator (`execution/executor/src/workflow/do_ledger_update.rs:82-121`), so accumulator-proof integrity for these fields is enforced only through the transaction-info hash used during normal consensus-driven execution — not during independent replay verification, which is exactly the mechanism meant to catch a hard-fork-causing divergence after the fact.

### Impact Explanation
Replay/verify-execution tooling (`replay_on_archive`, chunk-executor `verify_execution`, `aptos-debugger`, CLI replay commands) is the primary mechanism operators and auditors use to confirm that a node's local VM/state-checkpoint computation reproduces the exact same ledger state as what was actually committed and signed by validators. Because checkpoint/state-root fields are silently excluded from the comparison, these tools can report a "successful" replay even when the locally computed state root (standard SMT root, hot-state root, or native-position root) diverges from the authenticated one. This masks exactly the class of bug the state-integrity gate cares about: a hard-fork-causing divergence during replay/verification going undetected, undermining confidence in replay-based auditing and could delay detection of a consensus-breaking bug in state-checkpoint computation (e.g., in the new trading-native/position state pipeline) until it manifests as an actual node/validator crash or state fork.

### Likelihood Explanation
The gap is not theoretical — it's the exact path exercised whenever `verify_execution_mode` is used in the chunk executor, or when `replay_on_archive` is run against mainnet archive data. It applies without any special privilege; any operator running these standard tools is affected, and any bug elsewhere in the (relatively new/refactored) hot-state or native-position checkpoint code would be a silent miss instead of a caught replay failure.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/enabled) against the values carried in `txn_info`, mirroring the treatment already given to `state_change_hash` and `event_root_hash`. This requires plumbing through the locally-computed checkpoint hashes to the call sites (chunk executor, replay tooling) so the comparison can be performed per-transaction/per-checkpoint boundary, not just skipped with a TODO.

### Proof of Concept
Not directly exploitable as a state-corruption primitive by itself (no code path silently accepts a *forged* proof for consensus/commit); the concrete demonstration is a logical PoC: run chunk-executor `verify_execution` (or `db-tool replay-on-archive`) against a chunk where the target `TransactionInfo.state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) differs from what local re-execution computes, while `status`, `gas_used`, `state_change_hash`, and `event_root_hash` all still match. `ensure_match_transaction_info` returns `Ok(())` in this case since none of the checkpoint-hash fields are read at all in the function body [1](#0-0) , so the divergence goes unreported by every one of its four callers (`execution/executor/src/chunk_executor/mod.rs:692`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`).

Note: I could not fully trace whether `position_state_checkpoint_hash` is gated entirely behind an as-yet-unshipped `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag (in which case only that specific field is currently dormant/inactive on mainnet) versus `state_checkpoint_hash`/`hot_state_checkpoint_hash` being always-active and thus already exposed to this gap today; confirming the exact on-chain feature-flag status of `HOT_STATE_ROOT_IN_TXN_INFO` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` would require deeper investigation of `types/src/on_chain_config/aptos_features.rs` and current mainnet feature activation, which I was unable to complete within the available tool budget.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
