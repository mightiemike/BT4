### Title
Missing verification that `shop` parameter matches session-token `dest` in `tokenExchange` - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`shopify.auth.tokenExchange()` decodes and cryptographically verifies the caller-supplied session token, but only checks its signature/expiry/audience — it never verifies that the token's `dest` (the shop that actually issued it) matches the separately supplied `shop` argument used to build the token-exchange request and the resulting `Session`. This mirrors the reported bug class: two identifiers that are supposed to refer to the same "namespace" (here, shop domain) are never cross-checked, so a value trusted for one purpose (`sessionToken`, proving *a* valid Shopify-issued identity) can be silently paired with an attacker-controlled value for another (`shop`, which shop to exchange with / label the resulting session as).

### Finding Description
`decodeSessionToken` in [1](#0-0)  only validates the JWT's HMAC signature, `exp`/`nbf`, and optionally `aud === apiKey`. It never inspects or returns a validated relationship to the `shop` used elsewhere.

`tokenExchange()` calls this decode purely to check the signature is valid, then immediately discards the payload and uses the untouched, caller-supplied `shop` parameter to construct the OAuth request URL and the final `Session`: [2](#0-1) 

By contrast, other call sites in this same repo (which are effectively the "correct" pattern) derive `shop` directly from the verified JWT payload instead of trusting a separately supplied value: [3](#0-2) [4](#0-3) 

The library's own public documentation for `shopify.auth.tokenExchange` explicitly instructs developers to source `shop` from an **unauthenticated query parameter** (`req.query.shop`) rather than from the verified token, reinforcing that this is the documented, expected usage pattern rather than an edge case: [5](#0-4) 

`createSession()` then unconditionally uses this unverified `shop` to build the session ID (`getOfflineId(config)(shop)` / `getJwtSessionId(config)(shop, ...)`) and to set `Session.shop`: [6](#0-5) 

### Impact Explanation
If an app built directly against this documented pattern takes `shop` from an anonymous request parameter (as the official docs show) instead of deriving it from the verified `sessionToken.dest`, an attacker who holds any legitimately-issued session token (e.g., for their own installed shop) can submit it alongside a different, attacker-chosen `shop` value. The library will happily build a token-exchange request to `https://{attacker-chosen-shop}/admin/oauth/access_token` using the attacker's own token as `subject_token`, and — if the request succeeds — will store the resulting `Session` keyed under the attacker-chosen shop rather than under the shop that actually issued the token, corrupting the app's session storage keying/tenant boundary (cross-tenant session storage confusion) for any app that doesn't independently re-validate `shop` against the decoded token.

### Likelihood Explanation
The final gate that actually prevents token exfiltration/impersonation is Shopify's own OAuth server, which is expected to reject `subject_token`/target-domain mismatches — this repo has no test coverage proving that expectation, and the library itself performs zero local defense-in-depth check. Because the documented usage pattern explicitly pulls `shop` from the query string (an anonymous/unauthenticated input) rather than the token payload, any app following the docs literally inherits this gap, and reachability requires only a single legitimate session token plus an arbitrary `shop` value in the request — no privileged access needed.

### Recommendation
In `tokenExchange()` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), capture the payload returned by `decodeSessionToken` and assert `new URL(payload.dest).hostname === sanitizeShop(config)(shop, true)` before proceeding, throwing an `InvalidJwtError`/`InvalidOAuthError` on mismatch — mirroring the pattern already used in `perform-token-exchange.ts` and the remix/react-router `authenticate.ts` files, which derive `shop` from the verified token rather than trusting a separate parameter. Update the `tokenExchange.md` documentation example to stop sourcing `shop` from `req.query.shop` directly.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and obtains a valid App Bridge session token `T` (properly signed, `aud` = app's API key, `dest = https://attacker-shop.myshopify.com`).
2. Attacker calls the app's `/auth` endpoint (which follows the documented pattern) with `?shop=victim-shop.myshopify.com` while presenting `T` as the session token/Authorization header.
3. `shopify.auth.tokenExchange({ sessionToken: T, shop: 'victim-shop.myshopify.com', requestedTokenType })` passes signature/audience validation (since `T` is a genuinely valid token for the app) and issues `POST https://victim-shop.myshopify.com/admin/oauth/access_token` with `subject_token: T`, `client_id`/`client_secret` of the app.
4. Whatever Shopify returns (success or failure) is wrapped into a `Session` with `shop: 'victim-shop.myshopify.com'` — i.e., the app's session storage is keyed by an attacker-supplied shop with no local proof the token was ever issued for that shop.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
