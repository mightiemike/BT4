### Title
Unbounded recursion in `bytecode_hash_node` during compiled-class hashing enables stack-overflow DoS from a crafted declared class - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
`bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recursively walks a `NestedIntList`/`HashableNestedIntList` bytecode-segment structure with no depth bound, mirroring the Monero `tree_hash` bug class: an attacker-influenced structure size directly drives unbounded native-stack consumption during a cryptographic hash computation that a node must perform to validate untrusted input. [1](#0-0) 

### Finding Description
`bytecode_hash_node` recurses once per nesting level of the `NestedIntList` (or `NestedFeltCounts`) describing how a contract's CASM bytecode is segmented for selective loading/hashing: [1](#0-0) 

This function is invoked from `bytecode_hash`, which is called from `hash_inner`, the core of `CompiledClassHash` computation for any `CasmContractClass` (the compiled representation of a Cairo 1 declared class): [2](#0-1) 

There is no depth check anywhere in this recursive walk. By contrast, a related structure (`NestedFeltCounts`, used for gas metering) explicitly asserts `segmentation_depth <= 1` when built in the blockifier: [3](#0-2) 

That assertion is a strong signal that the codebase's own authors believe legitimate segment structures never exceed depth 1 — yet `bytecode_hash_node` in `starknet_api`, which is the function actually used to compute/verify `CompiledClassHash`, enforces no such bound. If the segmentation structure supplied together with a class (produced by the Sierra→CASM compiler pipeline reachable from a `DECLARE` transaction) can be driven to many nesting levels — e.g., via a Sierra program with deeply nested function/branch structure that the compiler segments recursively — the corresponding `bytecode_hash_node` call chain would consume one native stack frame per level with no cap, unlike the Cairo-Native execution path where the sequencer explicitly pre-allocates and monitors a bounded thread stack size specifically to guard against deep-recursion stack overflows: [4](#0-3) 

No equivalent stack-size provisioning or depth guard exists around the compiled-class-hash computation path.

The analogous Cairo (`.cairo`) implementations of the same bytecode-segment hashing (`bytecode_hash_internal_node` in both the Blake and Poseidon variants used by the Starknet OS) are tail-recursive over sibling segments and only recurse into child segments through `bytecode_hash_node`/`bytecode_hash_internal_node`, i.e. the same unbounded-depth pattern exists in the OS re-execution path as well: [5](#0-4) 

### Impact Explanation
If a class declarer can cause the compiled-class hash computation to recurse to a depth sufficient to exhaust the native call stack, the sequencer process computing the hash (during gateway validation of a `DECLARE` transaction, class-hash verification, or replay/re-execution) would crash. This is an "Uncontrolled Resource Consumption" issue in the same class as the cited Monero report: a value derived from attacker-supplied input directly controls unbounded stack usage in a hashing routine that must run on untrusted input before/while validating a transaction. A crash of the sequencer process while validating a submitted transaction would constitute a network node being unable to process new transactions, matching the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
This is rated with lower confidence because I could not fully confirm, within the available indexed code, whether the actual Sierra→CASM compiler used by the sequencer (`apollo_compile_to_casm`) can be driven to emit a `NestedIntList` with unbounded/attacker-controlled nesting depth, or whether it structurally caps segmentation depth (the depth-1 assertion elsewhere suggests real compiler output is always shallow). If the compiler enforces shallow segmentation for all valid Sierra input, this reduces to a defense-in-depth gap rather than an exploitable path. Confirming exploitability requires inspecting the segment-length-generation logic inside `cairo-lang-starknet-classes`/`apollo_compile_to_casm`, which was not fully retrievable via the indexed search.

### Recommendation
Add an explicit maximum recursion depth (or convert `bytecode_hash_node`/`create_bytecode_segment_structure_inner` to an iterative/explicit-stack implementation) in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`, and reject any declared class whose `bytecode_segment_lengths` structure exceeds that bound during gateway validation, before it reaches hash computation. Apply the same bound to the corresponding Cairo OS hash functions (`bytecode_hash_node`/`bytecode_hash_internal_node` in the Poseidon/Blake `.cairo` files) so OS re-execution is likewise protected.

### Proof of Concept
Not able to construct a concrete, validated PoC transaction from indexed code alone: doing so requires confirming whether `apollo_compile_to_casm`'s Sierra→CASM compiler can be made to emit a `NestedIntList::Node` chain of depth N (e.g., N = 100,000) for some valid or near-valid Sierra program, which was not available in the indexed context. Conceptually, the PoC would be: craft a Sierra class whose function/branch structure causes the compiler's bytecode segmentation to nest to depth N, submit it via `DECLARE`, and trigger `hash_inner`/`bytecode_hash_node` on it (e.g., via gateway class-hash validation), causing a native stack overflow and process crash.

fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Trait for types that can be hashed as a Starknet compiled class.
/// Used to abstract over different contract class representations.
pub trait HashableCompiledClass<EH: EntryPointHashable, NL: HashableNestedIntList>: Sized {
    fn get_hashable_l1_entry_points(&self) -> &[EH];
    fn get_hashable_external_entry_points(&self) -> &[EH];
    fn get_hashable_constructor_entry_points(&self) -> &[EH];
    fn get_bytecode(&self) -> Vec<Felt>;
    fn get_bytecode_segment_lengths(&self) -> Cow<'_, NL>;

    /// Returns the compiled class hash using the specified hash version.
    fn hash(&self, hash_version: &HashVersion) -> CompiledClassHash {
        match hash_version {
            HashVersion::V1 => hash_inner::<Poseidon, EH, NL>(self),
            HashVersion::V2 => hash_inner::<Blake2Felt252, EH, NL>(self),
        }
    }
}

/// Computes the compiled class hash for a given hashable class using the specified hash algorithm.
fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}

// structure.
// is_segment_used_callback: A callback that returns whether a segment is used.
func bytecode_hash_node{range_check_ptr, poseidon_ptr: PoseidonBuiltin*}(
    data_ptr: felt*, data_length: felt, full_contract: felt
) -> felt {
    alloc_locals;

    local is_leaf;

    %{ IsLeaf %}

    // Guess if the bytecode is a leaf or an internal node in the tree.
    if (is_leaf != FALSE) {
        // If the bytecode is a leaf, it must be loaded into memory. Compute its hash.
        let (hash) = poseidon_hash_many(n=data_length, elements=data_ptr);
        return hash;
    }

    %{ AssignBytecodeSegments %}

    // Use the poseidon builtin directly for performance reasons.
    let poseidon_state = PoseidonBuiltinState(s0=0, s1=0, s2=0);
    bytecode_hash_internal_node{poseidon_state=poseidon_state}(
        data_ptr=data_ptr, data_length=data_length, full_contract=full_contract
    );

    // Pad input with [1, 0]. See implementation of poseidon_hash_many().
    assert poseidon_ptr.input = PoseidonBuiltinState(
        s0=poseidon_state.s0 + 1, s1=poseidon_state.s1, s2=poseidon_state.s2
    );
    let segmented_hash = poseidon_ptr.output.s0;
    let poseidon_ptr = &poseidon_ptr[1];

    // Add 1 to segmented_hash to avoid collisions with the hash of a leaf (domain separation).
    return segmented_hash + 1;
}
