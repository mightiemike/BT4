## Finding: Pagination cursor mismatch when a resource group is the boundary item [1](#0-0) 

### Title
Incorrect pagination cursor construction for resource groups causes account resource listing pages to skip or duplicate entries - (File: `api/src/context.rs`)

### Summary
`Context::get_resources_by_pagination`, which backs `Account::resources` / `GET /accounts/{address}/resources`, computes the "next page" cursor (`next_key`) from the raw `StructTag` of the item just past the page boundary. When that boundary item is a **resource group** entry, the cursor is reconstructed with the wrong `Path` variant, producing a `StateKey` whose on-disk encoding does not match the actual state key stored for that resource group. Clients that use this cursor to fetch the next page will resume iteration from the wrong position in the account's key space, causing entries to be skipped or duplicated across pages.

### Finding Description
`get_resources_by_pagination` filters the raw prefixed state iterator into `(StructTag, Vec<u8>)` pairs, treating both individual resources and resource groups uniformly at this stage: [2](#0-1) 

Note that for a resource-group entry, the extracted `struct_tag` is the *group's* tag (e.g. `0x1::object::ObjectGroup`), taken from `Path::ResourceGroup(struct_tag)`. After collecting up to `limit` items, the code peeks at the (limit+1)-th item to build the pagination cursor: [3](#0-2) 

`next_key` is built with `StateKey::resource(&address, &struct_tag)`, which always constructs a `Path::Resource(struct_tag)` access path: [4](#0-3) 

But if the boundary item was actually a resource group, its real on-disk key was built with `Path::ResourceGroup(struct_tag)` via `StateKey::resource_group`: [5](#0-4) 

`Path` is a BCS-serialized enum with `Code`, `Resource`, `ResourceGroup` variants, each carrying a distinct discriminant byte: [6](#0-5) 

Because `Path::Resource(tag)` and `Path::ResourceGroup(tag)` serialize to different byte sequences even for the same `StructTag`, the reconstructed cursor `StateKey` has a different `encoded()`/`crypto_hash_ref()` than the true underlying key for that resource group. This mismatched key is exposed to the client as the `X-Aptos-Cursor` response header (see `resources()` in `api/src/accounts.rs`, `.with_cursor(next_state_key)`): [7](#0-6) 

When the client submits this cursor back via `?start=...`, it is deserialized into a `StateKey` and passed as `prev_state_key` to `get_prefixed_state_value_iterator`: [8](#0-7) 

Since the fake cursor key does not correspond to any real on-disk position, the iterator resumes from a different point in the account's key ordering than intended, causing the next page to either skip resources that fall between the true and fake position, or re-return resources already delivered in a prior page — whenever a resource group happens to land exactly at a `limit`/`limit+1` page boundary.

### Impact Explanation
This breaks the invariant that iterating all pages of `GET /accounts/{address}/resources` for a fixed `ledger_version` is a lossless partition of that account's resources. Indexers, wallets, or any client that reconstructs a full account snapshot by walking pages via the `X-Aptos-Cursor` header can silently miss or duplicate a resource (or an entire resource group's contents) whenever the group happens to fall on a page boundary. This does **not** corrupt the actual committed ledger state, accumulator root, or any Merkle/transaction/event/state proof — the API in question returns plain JSON/BCS data bound to a correctly-resolved `ledger_version` and is not proof-bearing. The corruption is confined to the derived, non-authenticated pagination view assembled client-side from repeated calls to this convenience endpoint.

### Likelihood Explanation
Triggering requires only unprivileged read access to the public REST API (`limit`/`start` are freely controllable request parameters) and an account whose on-chain resources happen to place a resource-group entry at the edge of a chosen page size — a state condition attackers can engineer at will simply by publishing/using accounts with resource groups (e.g. `ObjectGroup`) and picking `limit` to land the group at the boundary.

### Recommendation
When the peeked boundary item originated from a `Path::ResourceGroup`, reconstruct `next_key` using `StateKey::resource_group(&address, &struct_tag)` instead of `StateKey::resource(...)`. This requires threading through whether each yielded `(StructTag, Vec<u8>)` pair came from a `Path::Resource` or `Path::ResourceGroup` variant (rather than discarding that distinction in the initial `filter_map`), so the correct `StateKey` constructor is used for the cursor.

### Proof of Concept
1. Publish/select an account whose resource list, in on-disk key order, has a resource-group entry (e.g. `ObjectGroup`) landing as the `(limit+1)`-th item for some chosen `limit`.
2. Call `GET /accounts/{address}/resources?limit={limit}` and capture the `X-Aptos-Cursor` header.
3. Decode the cursor and compare its BCS-encoded bytes/hash against the actual on-disk `StateKey` for that resource group (obtainable via `StateKey::resource_group(&address, &group_tag)`); they differ because the cursor was built via `StateKey::resource`.
4. Call `GET /accounts/{address}/resources?start={cursor}&limit=...` and compare the union of all pages against a single unpaginated fetch at the same `ledger_version` — the sets diverge (skip or duplicate) whenever the resource group is a boundary item, contradicting the expected lossless-partition property described in the exploit question.

    pub fn get_resources_by_pagination(
        &self,
        address: AccountAddress,
        prev_state_key: Option<&StateKey>,
        version: u64,
        limit: u64,
    ) -> Result<(Vec<(StructTag, Vec<u8>)>, Option<StateKey>)> {
        let account_iter = self
            .indexer_reader
            .as_ref()
            .ok_or_else(|| format_err!("Indexer reader doesn't exist"))?
            .get_prefixed_state_value_iterator(
                &StateKeyPrefix::from(address),
                prev_state_key,
                version,
            )?;
        // TODO: Consider rewriting this to consider resource groups:
        // * If a resource group is found, expand
        // * Return Option<Result<(PathType, StructTag, Vec<u8>)>>
        // * Count resources and only include a resource group if it can completely fit
        // * Get next_key as the first struct_tag not included
        let mut resource_iter = account_iter
            .filter_map(|res| match res {
                Ok((k, v)) => match k.inner() {
                    StateKeyInner::AccessPath(AccessPath { address: _, path }) => {
                        match Path::try_from(path.as_slice()) {
                            Ok(Path::Resource(struct_tag)) => {
                                Some(Ok((struct_tag, v.bytes().to_vec())))
                            }
                            // TODO: Consider expanding to Path::Resource
                            Ok(Path::ResourceGroup(struct_tag)) => {
                                Some(Ok((struct_tag, v.bytes().to_vec())))
                            }
                            Ok(Path::Code(_)) => None,
                            Err(e) => Some(Err(anyhow::Error::from(e))),
                        }
                    }
                    _ => {
                        error!("storage prefix scan return inconsistent key ({:?}) with expected key prefix ({:?}).", k, StateKeyPrefix::from(address));
                        Some(Err(format_err!( "storage prefix scan return inconsistent key ({:?})", k )))
                    }
                },
                Err(e) => Some(Err(e)),
            })
            .take(limit as usize + 1);
        let kvs = resource_iter
            .by_ref()
            .take(limit as usize)
            .collect::<Result<Vec<(StructTag, Vec<u8>)>>>()?;

        // We should be able to do an unwrap here, otherwise the above db read would fail.
        let state_view = self.state_view_at_version(version)?;
        let converter = state_view.as_converter(self.db.clone(), self.indexer_reader.clone());

        // Extract resources from resource groups and flatten into all resources
        let kvs = kvs
            .into_iter()
            .map(|(tag, value)| {
                if converter.is_resource_group(&tag) {
                    // An error here means a storage invariant has been violated
                    bcs::from_bytes::<ResourceGroup>(&value)
                        .map(|map| map.into_iter().collect::<Vec<_>>())
                        .map_err(|e| e.into())
                } else {
                    Ok(vec![(tag, value)])
                }
            })
            .collect::<Result<Vec<Vec<(StructTag, Vec<u8>)>>>>()?
            .into_iter()
            .flatten()
            .collect();

        let next_key = if let Some((struct_tag, _v)) = resource_iter.next().transpose()? {
            Some(StateKey::resource(&address, &struct_tag)?)
        } else {
            None
        };
        Ok((kvs, next_key))
    }
