Based on my research, I found a genuine analog to the "missing zero-address validation in constructor" bug class, mapped to Push Chain's revert/refund routing in `x/uexecutor`.

### Title
Unvalidated `RevertInstructions.FundRecipient` / recipient address allows attacker-triggered permanent burn of bridged/gas-refund funds - (File: `x/uexecutor/keeper/build_revert_outbound.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
Like the `USDKG` constructor that accepted `owner`/`compliance` as raw addresses with no non-zero check, Push Chain's inbound/outbound revert and gas-refund logic accepts an attacker-supplied `RevertInstructions.FundRecipient` string and converts it directly to an EVM address with `common.HexToAddress(...)` without ever validating that it is a well-formed, non-zero address, before minting PRC20 tokens or issuing a native-chain refund to it.

### Finding Description
`RevertInstructions.FundRecipient` is part of the user-originated `Inbound` payload (populated from the source-chain gateway event, which is attacker-controlled input relayed by honest Universal Validators). The only guard on this field is an emptiness check: [1](#0-0) 

The same "only check `!= \"\"`" pattern is repeated at every place this field is consumed: [2](#0-1) [3](#0-2) 

None of these call sites validate that `FundRecipient` (or the fallback `recipient` derived from it) is a syntactically valid, non-zero hex address before calling `common.HexToAddress(recipient)` and minting PRC20 tokens (`CallPRC20Deposit`) or issuing `CallUniversalCoreRefundUnusedGas`. `common.HexToAddress` silently accepts malformed/short/zero-valued hex strings and returns the canonical zero address (`0x000...000`) without error — exactly the "silently accept the zero/invalid value" failure mode the external report calls out for the `USDKG` constructor.

`Inbound.ValidateForExecution` validates `Recipient` for `FUNDS`/`GAS` types via `utils.IsValidAddress` [4](#0-3)  but this validation is never applied to `RevertInstructions.FundRecipient`, which is the address actually used for fund-recovery/refund paths (`buildRevertOutbound`, `handleFailedOutbound`, `applyGasRefund`).

### Impact Explanation
Because `FundRecipient` is attacker-supplied via the inbound's source-chain payload and is never checked to be a valid non-zero address, any inbound that later fails execution (e.g., invalid asset config, zero-amount misuse, or contract-call failure) and needs a refund/revert can be routed to the zero address. On the destination-chain revert path this causes `CallPRC20Deposit`/`CallUniversalCoreRefundUnusedGas` to permanently mint tokens or refund gas to `0x0`, which is an unrecoverable burn (permanent loss of protocol/user-bridged funds) — falling squarely into the "permanent freezing/loss of user or protocol-controlled funds" allowed-impact category. On the source-chain revert path (`buildRevertOutbound`), the malformed/zero recipient is propagated as the outbound `Recipient` field that Universal Validators will eventually sign via TSS and broadcast, meaning honest validators would converge on and execute a transfer to an unspendable/burn address.

### Likelihood Explanation
The `FundRecipient` value on the `Inbound` originates from data an ordinary, unprivileged user supplies when calling the source-chain gateway (e.g. `addFunds`), and is passed through Universal Validator voting as attacker-controlled payload data — no privileged actor is required to trigger this path. The most likely trigger is a user setting an invalid/zero `fund_recipient` (accidentally or maliciously) and then triggering an execution failure downstream (e.g., unsupported token, format issue, temporary registry misconfiguration), causing the revert/refund flow to silently target the zero address instead of failing safe.

### Recommendation
Add explicit non-zero/well-formed address validation for `RevertInstructions.FundRecipient` (and any derived `recipient` variable) at both ingestion (`Inbound.ValidateForExecution`/`Canonicalize`) and at every consumption site (`buildRevertOutbound`, `handleFailedOutbound`, `applyGasRefund`) using the same `utils.IsValidAddress` check (and explicitly reject `types.EvmZeroAddress`) already used for `Recipient`. If the address is invalid or zero, fall back to `inbound.Sender`/`outbound.Sender` (as already done for the empty-string case) rather than silently converting to the zero address.

### Proof of Concept
1. An unprivileged user calls the source-chain gateway `addFunds` (or equivalent) specifying `RevertInstructions.FundRecipient = "0x0000000000000000000000000000000000000000"` (a syntactically valid, non-empty hex string that passes the `!= ""` check) along with a deposit that is guaranteed to fail post-quorum validation (e.g., referencing an asset with a misconfigured/removed token config, or hitting `ExecuteInboundFunds`/`ExecuteInboundGasAndPayload` failure branches).
2. Universal Validators vote and reach quorum on the inbound (`MsgVoteInbound`) as usual — this is honest-validator behavior, no privileged action required.
3. Because execution fails, `handleFailedInboundValidation`/`handleFailedOutbound` calls `buildRevertOutbound`/`CallPRC20Deposit`, which resolves `recipient` to the literal zero address via `common.HexToAddress("0x000...000")`.
4. The resulting PRC20 mint (`CallPRC20Deposit`) or gas refund (`CallUniversalCoreRefundUnusedGas`) is sent to `0x0`, permanently destroying the funds that should have been returned to the user, with no on-chain guard preventing it.

Note: I was unable to fully verify the exact upstream flow that populates `RevertInstructions.FundRecipient` from raw gateway-event bytes (the event-parsing code in `universalClient/chains/*/event_parser.go`) within the available tool budget, so the precise degree of attacker control over this field (versus a value fixed by the gateway contract itself) should be double-checked in a follow-up session before treating this as fully confirmed.
