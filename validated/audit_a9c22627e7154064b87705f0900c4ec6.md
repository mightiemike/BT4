### Title
Witness rewards are permanently lost when a witness's vote count is 0 at Vi accumulation time - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
The new reward algorithm in java-tron accumulates a per-witness reward index (`Vi`, analogous to Solidity's `rewardPerTokenStored`) once per cycle in `DelegationStore.accumulateWitnessVi()`. When a witness's `voteCount` is 0 at the moment this accumulation runs, the function skips adding any delta and simply forwards the previous `Vi` value, discarding whatever reward (`getReward(cycle, address)`) had already been credited to that witness for the cycle. This mirrors the reported `AbstractRewarder::_updateReward()` bug: reward is generated but the "index" update path silently drops it instead of queuing it for later distribution.

### Finding Description
`DelegationStore.accumulateWitnessVi()` is the `rewardPerToken()` analog: [1](#0-0) 

It is invoked once per maintenance cycle for every witness, using the witness's current `voteCount` (analog of `totalSupply()`): [2](#0-1) 

Rewards for a witness are accumulated independently of its vote count via `MortgageService.payReward()` → `delegationStore.addReward(cycle, witnessAddress, value)`, which fires whenever the witness produces a block or receives a standby payment: [3](#0-2) [4](#0-3) 

The active super-representative (SR) set and each witness's remaining voters are fixed only at maintenance boundaries, not continuously. Any unprivileged account can withdraw its entire vote-backing stake at any time via `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor`, which reduces `witness.getVoteCount()` to 0 mid-cycle while the witness remains scheduled to produce blocks (and thus keeps earning block/standby rewards) until the next maintenance: [5](#0-4) 

When `MaintenanceManager.doMaintenance()` subsequently calls `accumulateWitnessVi(curCycle, witness, 0)` for that witness, the accumulated `reward` for the cycle is thrown away — it is neither divided into `Vi` (so no current/future voter can claim it) nor queued/rolled forward the way the report's remediation suggests (`queuedRewards += newRewards`). The reward amount already recorded via `delegationStore.addReward()` becomes permanently unreachable dead accounting state, exactly the "supply is 0 but reward already accrued" scenario described in the report.

### Impact Explanation
This is a concrete accounting/loss-of-funds bug reachable purely by unprivileged actions (vote + unfreeze), not a trusted role. Legitimate reward TRX intended for voters/witnesses becomes stranded and undistributable, permanently reducing payouts below the protocol's intended emission — a direct parallel to the "500 rewards lost in the contract" impact in the original report. It does not grant an attacker's own gain, but it causes systemic reward loss and inconsistent accounting between `delegationStore.getReward()` (which still holds the value) and `Vi` (which never reflects it), a form of accounting divergence.

### Likelihood Explanation
Requires a witness to be an elected/active SR (or in the standby-27 payment set) while all its voters unfreeze their entire stake within the same voting cycle, driving `voteCount` to 0 before `doMaintenance()` runs for that cycle. This is achievable by any set of unprivileged accounts coordinating (or even a single dominant voter for a smaller witness) and does not require any special privilege — it is a normal sequence of public actuator calls (`VoteWitnessContract`, `UnfreezeBalanceV2Contract`). Likelihood is moderate: it requires specific timing but no privileged access or complex exploit machinery.

### Recommendation
Mirror the report's remediation: when `voteCount == 0` in `accumulateWitnessVi()` but `reward > 0`, do not silently drop the reward. Instead, roll it forward into the next cycle's reward bucket (e.g., `addReward(cycle + 1, address, reward)`) or maintain an explicit "queued rewards" accumulator per witness that gets folded into `Vi` once `voteCount` becomes nonzero again, ensuring no reward is permanently lost when a witness's vote count transiently reaches 0.

### Proof of Concept
1. Witness `W` is elected active SR with all votes coming from voter `V`.
2. During cycle `N`, `W` produces blocks, and `MortgageService.payReward()` calls `delegationStore.addReward(N, W, X)` for some `X > 0` (from `payBlockReward`/`payTransactionFeeReward`).
3. Before `doMaintenance()` runs for cycle `N`, `V` calls `UnfreezeBalanceV2Contract` to unfreeze its entire TRON Power backing the vote for `W`, which via `UnfreezeBalanceV2Processor.updateVote()`/`UnfreezeBalanceV2Actuator.updateVote()` reduces `W`'s effective vote count to 0 (see [5](#0-4) , `totalVote == 0` → early return leaving `witnessCapsule.voteCount` at 0 for the underlying witness once countVote no longer credits it).
4. At maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)`. Since `voteCount == 0`, the function forwards the previous `Vi` unchanged ( [1](#0-0) ), so `X` is never converted into `deltaVi` for cycle `N`.
5. `V` (or any future voter for `W`) computes rewards via `MortgageService.computeReward()`, which only derives reward from `Vi` deltas — the `X` TRX credited in step 2 is unrecoverable from any account's `queryReward()`/`withdrawReward()` path, resulting in a permanent loss of that reward amount.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
