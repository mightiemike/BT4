### Title
`replay_on_archive` verification silently ignores state/hot-state/position checkpoint hashes, allowing corrupted state-checkpoint roots to pass replay-verify - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function `storage/db-tool/src/replay_on_archive.rs` uses to check that a freshly re-executed `TransactionOutput` matches the historical, ledger-committed `TransactionInfo` — only checks `status`, `gas_used`, `write_set_hash` (`state_change_hash`), and `event_root_hash`. It never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, even though these are consensus-authenticated fields of `TransactionInfoV1` that get hashed into the transaction accumulator and are therefore part of the chain's committed proof material.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  explicitly compares only a subset of fields between the locally re-executed `TransactionOutput` and the archival `TransactionInfo` fetched from the backup/ledger. The function's own comment documents the gap: [2](#0-1) 

This comparator is the sole verification step used by `db-tool`'s `replay_on_archive`/`replay-verify` tool, which re-executes historical transactions from an archive and is meant to catch any divergence between local re-execution and the authenticated ledger data: [3](#0-2) . The tool fetches `expected_txn_info` from the backup handler (containing the real, chain-committed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`), but `ensure_match_transaction_info` never uses these values for anything beyond passing them in as unused “expected(if known)” parameters that are not actually checked against locally computed roots.

This matters because the codebase has introduced a new, feature-gated commitment: `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (feature 122) causes execution to compute a native-position Merkle root and commit it into `TransactionInfoV1.position_state_checkpoint_hash`, which becomes part of the accumulator-authenticated ledger state [4](#0-3) . The state-checkpoint/position-state pipeline (`DoStateCheckpoint`, `assemble_transaction_infos`) computes these roots from the JMT / native-position tree during normal chunk execution [5](#0-4) [6](#0-5) . If a bug exists anywhere in this new, less mature computation path (state summary merge, delta computation, sharding, or the position tree's `make_delta`/`merklize_snapshot` logic in [7](#0-6) ), producing a wrong checkpoint hash committed on mainnet, `replay_on_archive` — the tool operators would run specifically to catch such state-commitment divergences — would report success anyway, because it never re-derives or compares these checkpoint hashes.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant that replay/verification tooling must detect any divergence between locally recomputed ledger state and the authenticated, consensus-committed state. A wrong `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` committed to mainnet (e.g., via a bug in the newly added hot-state or native-position root computation) would go undetected by the primary automated tool designed to catch exactly this class of error, delaying or preventing detection of ledger corruption, hard-fork-triggering divergence, or a corrupted authenticated proof root reaching archive nodes and light clients that rely on `TransactionInfoWithProof`/accumulator proofs.

### Likelihood Explanation
This is a real code gap (not speculative): the comment in the source explicitly acknowledges it as a known, currently-unaddressed limitation ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"). The trigger condition is any state-checkpoint-hash bug in the (new, more complex) hot-state/native-position/state-checkpoint pipeline reaching a version being replay-verified while `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `HOT_STATE_ROOT_IN_TXN_INFO` is enabled on mainnet — plausible given how new and actively-changing this subsystem is (multiple placeholder fields reserved in `TransactionInfoV1`, feature flags 122/123 newly added). It requires no attacker action; it's a monitoring/detection gap that silently widens the blast radius of any unrelated commit-path bug.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against locally derived values, or explicitly require callers like `replay_on_archive` to pass in a freshly assembled `TransactionInfo` (via the same `assemble_transaction_infos`/`DoStateCheckpoint` path used in normal execution) and compare full `TransactionInfo::hash()` rather than a hand-picked subset of fields. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` from being enabled on any network where `replay_on_archive` is relied upon until this check is completed, as noted in the existing TODO.

### Proof of Concept
Not applicable as a runnable exploit — this is a detection-gap flaw in verification tooling. The proof is the direct code trace showing the comparator's field list [8](#0-7)  omits `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, and that `replay_on_archive.rs::execute_and_verify` calls exactly this function as its only correctness check, discarding `expected_txn_infos[idx]`'s checkpoint-hash fields without further use [9](#0-8) . I was not able to trace whether any other caller (e.g., `aptos-debugger` or `aptos-move/cli`) independently re-validates these checkpoint hashes; if none do, the gap is unconditional for any tool built on `ensure_match_transaction_info`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

/// Advances `*last_snapshot` on success.
pub(crate) fn merklize_position(
    merkle_db: &PositionMerkleDb,
    ledger_db: &LedgerDb,
    last_snapshot: &mut PositionStateWithSummary,
    snapshot: PositionSnapshotToCommit,
) -> Result<PositionMerkleCommit> {
    let new_state = snapshot.snapshot;
    let version = new_state
        .version()
        .expect("snapshot enqueued for merklize must have a concrete version");
    let previous_epoch_ending_version = ledger_db
        .metadata_db()
        .get_previous_epoch_ending(version)?
        .map(|(v, _e)| v);
    let base_version = last_snapshot.version();

    let updates = new_state.make_delta(last_snapshot);

    let all_updates = pre_shard_jmt_updates(
        updates
            .iter()
            .map(|(key_hash, slot)| leaf_entry_to_jmt_update(*key_hash, slot)),
    );

    let (root_hash, _leaf_count, top_levels_batch, batches_for_shards) = merkle_db
        .merklize_snapshot(
            base_version,
            version,
            &last_snapshot.summary().global_state_summary,
            &new_state.summary().global_state_summary,
            all_updates,
            previous_epoch_ending_version,
        )
        .map_err(|e| AptosDbError::Other(format!("position JMT merklize_snapshot failed: {e}")))?;

    *last_snapshot = new_state.clone();

    Ok(PositionMerkleCommit {
        version,
        root_hash,
        batch: crate::common::MerkleBatch {
            top_levels_batch,
            batches_for_shards,
        },
        snapshot: new_state,
    })
