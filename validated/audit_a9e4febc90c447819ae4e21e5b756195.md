Now I have enough evidence. This is a directly analogous, already-documented, unfixed bug in the nearcore codebase (tracked as [near/nearcore#12606](https://github.com/near/nearcore/issues/12606)): the `max_receipt_size` limit — analogous to `DAOConfig.maxMembers` — is declared as a hard cap but is **not actually enforced** for receipts generated as a side-effect of `value_return`/promise chaining, exactly mirroring the external report's pattern of "a config limit exists but nothing enforces it end-to-end."

### Title
`max_receipt_size` limit is not enforced when `output_data_receivers` are appended after receipt-size validation, allowing oversized receipts into the chain - (File: runtime/runtime/src/lib.rs)

### Summary
`LimitConfig::max_receipt_size` is meant to bound the size of every receipt so that a `ChunkStateWitness` never grows unboundedly large [1](#0-0) . However, the runtime validates the new receipt's size in `process_receipt`/`apply_action` and only afterwards mutates that same receipt by appending `output_data_receivers`, so the size check is bypassed for the growth added after validation.

### Finding Description
When executing a `FunctionCall` action whose result is `ReturnData::Value`, the runtime builds `Data` receipts (or attaches `output_data_receivers`) to the freshly-created action receipt **after** `validate_receipt` has already been run on the new receipts: [2](#0-1) 
The mutation that appends `output_data_receivers` onto an already-validated new receipt happens later in the same function: [3](#0-2) 
This means a receipt can be created at exactly `max_receipt_size` (passing the `NewReceipt` check in `validate_receipt`), and then grow past the limit once `output_data_receivers` is appended, or a returned value up to `max_length_returned_data` can be wrapped into a `Data` receipt whose total size still exceeds `max_receipt_size` [4](#0-3) . The `validate_data_receipt` path only checks `max_length_returned_data`, never `max_receipt_size` for `Data` receipts [5](#0-4) .

The codebase openly documents this as a live, unfixed bug (tracked as near/nearcore#12606) and works around its symptoms rather than fixing the root cause: [6](#0-5) [7](#0-6) [8](#0-7) 

Two dedicated test-loop tests demonstrate that a contract-controlled receipt can be pushed above `max_receipt_size` and still end up included as an incoming receipt on-chain, unrejected: [9](#0-8) [10](#0-9) 
Both tests end by asserting that an oversized receipt was actually found on-chain (`assert_oversized_receipt_occurred`), rather than that the transaction failed [11](#0-10) .

### Impact Explanation
Any unprivileged account that deploys a contract and calls a method that returns a large value or chains promises can cause the runtime to generate and accept receipts larger than the protocol's declared `max_receipt_size` hard limit. Because state-witness size budgeting assumes `max_receipt_size` (4 MiB) is an enforced hard cap for every individual receipt component of the 21 MiB `ChunkStateWitness` budget [12](#0-11) , an attacker-controlled oversized receipt undermines this accounting and forces defensive "pretend it's `max_receipt_size`" workarounds in the congestion-control and bandwidth-scheduling code paths just to avoid receipts getting permanently stuck [13](#0-12) . This is the direct analog of the reported DAO bug: a documented cap (`maxMembers` / `max_receipt_size`) exists in configuration but the code path that actually creates the bounded entity does not enforce it, so the invariant can be silently exceeded by an ordinary transaction sender.

### Likelihood Explanation
High likelihood of reachability: this requires only deploying an ordinary WASM contract and calling a method that returns a value close to `max_length_returned_data`/`max_receipt_size` or that creates a promise chain with `output_data_receivers`, both of which are exercised by the existing regression tests `test_max_receipt_size_value_return` and `test_max_receipt_size_promise_return` using nothing more privileged than a standard signed transaction [14](#0-13) .

### Recommendation
Re-run (or move) the `max_receipt_size` validation for `NewReceipt` mode after `output_data_receivers` are appended in `process_action_receipt`/`apply_action`, or split the check into a pre-mutation and post-mutation validation, so the hard limit is enforced on the receipt's final, fully-mutated form before it is queued for outgoing/local delivery, and remove the size-clamping workarounds in `congestion_control.rs` once the root cause is fixed.

### Proof of Concept
The existing in-repo regression test `test_max_receipt_size_value_return` is a ready proof of concept: it deploys a contract, calls `max_receipt_size_value_return_method` with `value_size = max_receipt_size` (4,194,304 bytes), and then calls `assert_test_completed`; the helper `assert_oversized_receipt_occurred` walks the chain and confirms an incoming receipt above `max_receipt_size` was actually accepted on-chain rather than rejected [15](#0-14) .

## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.

    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
