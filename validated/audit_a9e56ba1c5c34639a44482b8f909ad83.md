Based on my investigation, I found a valid structural analog to the TOKE-28 bug class in the Push Chain node's autoswap/deposit path.

### Title
On-chain quote-then-swap deposit/refund path uses a fixed 5% slippage tolerance with no protection against same-block/adjacent-block price manipulation of the permissionless WPC/PRC20 Uniswap V3 pool - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
Push Chain's gas top-up flow (`ExecuteInboundGas`), `GAS_AND_PAYLOAD` deposit flow (`gasAndPayloadDepositAutoSwap`), and gas-refund flow (`applyGasRefund`) all fetch a live spot quote from a permissionless Uniswap V3 `QuoterV2` contract immediately before executing the real swap, then bound the swap only by a hardcoded `minPCOut = quote * 95 / 100` (5% slippage). This mirrors the TOKE-28 pattern of "price snapshot immediately preceding an unprotected/loosely-protected swap" — except here the price source is a live AMM pool that any unprivileged user can move via ordinary swaps, rather than a stale cached debt value. An attacker who controls the timing of their own inbound (they choose when to submit the source-chain deposit that triggers `MsgVoteInbound`/finalization) can pre-position a large swap against the WPC/PRC20 pool to skew the quoted price by more than 5% right before their own module-driven autoswap executes, extracting value from the pool (and, depending on WPC's backing, from protocol-held liquidity) at the manipulated rate, then reverse the trade afterward.

### Finding Description
The relevant code: [1](#0-0) [2](#0-1) [3](#0-2) 

`GetSwapQuote` performs a static `CallEVM` (`commit=false`) against `QuoterV2.quoteExactInputSingle` to read the *current* on-chain price of the PRC20-gas-token/WPC Uniswap V3 pool: [4](#0-3) 

That quote is used to derive `minPCOut` with a fixed 5% tolerance, and the actual swap is then committed via `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas` (real `DerivedEVMCall`s), executed by the `uexecutor` module account against `UniversalCore.depositPRC20WithAutoSwap` / `refundUnusedGas`, which route through the Uniswap V3 `SwapRouter`: [5](#0-4) 

The WPC/token pools are standard, permissionless Uniswap V3 pools created against WPC with normal liquidity (per the e2e setup, e.g. `pool-manager.js create-pool`), meaning any address can submit ordinary swap transactions against them: [6](#0-5) 

Because the quote fetch and the committed swap are two separate EVM calls executed sequentially as part of finalizing an inbound (a state transition an unprivileged user can trigger simply by depositing on the source chain and waiting for Universal Validators to reach vote quorum), an attacker who is also the depositor can:
1. Submit their bridging deposit on the source chain, which they know will eventually trigger `ExecuteInboundGas`/`gasAndPayloadDepositAutoSwap` for their own recipient UEA.
2. Time or front-run a large swap against the WPC/gasToken pool to push the spot price outside the 5% band right as (or immediately before) the module executes the deposit+autoswap in the same or an adjacent block.
3. Let the module's autoswap execute at the manipulated price (still within the 5%-tolerant `minPCOut`), receiving inflated WPC into their own UEA.
4. Reverse the manipulation trade, walking away with value extracted from the pool's liquidity.

This is structurally identical to the TOKE-28 root cause: a price value is fetched moments before an actual swap is committed, and the slippage bound applied is not tied to any independently verified/aggregated price (e.g., the chain-meta oracle or an external TWAP), so it does not protect against manipulation of the very pool being quoted.

### Impact Explanation
If exploited, the attacker can extract WPC (or PC-denominated value) from the Uniswap V3 pool liquidity beyond what their genuinely deposited/refunded gas token is worth, at the expense of pool liquidity providers and ultimately of protocol-funded/backed liquidity, since these are Push Chain's own system-created pools. Repeated exploitation across every `GAS`, `GAS_AND_PAYLOAD` inbound, and gas-refund event that hits `applyGasRefund` could produce material fund loss from the swap liquidity backing the protocol's gas-abstraction feature.

### Likelihood Explanation
The likelihood depends heavily on real-world pool depth and fee-tier liquidity versus the manipulable size at the 5% band, and on whether an attacker can reliably land their manipulation swap in the same or adjacent block as their own inbound's finalization (finalization timing is controlled by Universal Validator vote quorum, not directly by the attacker, which reduces but does not eliminate exploitability — the attacker still controls the source-chain deposit trigger and can retry cheaply). This is lower likelihood than the original TOKE-28 report (which had zero slippage protection), because a 5% band already blocks small/moderate manipulations, but for low-liquidity token pools (e.g. `pSOL/WPC`, `USDT.sol/WPC` in the e2e setup with amounts like `1`/`4`) a 5% move is easy to achieve with modest capital.

### Recommendation
- Source the swap-bound price from the aggregated, multi-validator `ChainMeta`/gas-price oracle (already implemented with staleness and median-vote protections in `x/uexecutor/keeper/chain_meta.go`) rather than a live spot quote from the same pool being swapped against, or additionally cross-check the quoter's spot price against a TWAP from the pool itself.
- Increase minimum liquidity requirements or apply a maximum swap amount cap relative to pool depth for gas-abstraction swaps.
- Consider tightening the slippage tolerance dynamically based on observed liquidity depth rather than a fixed 5%.

### Proof of Concept
1. Deploy/observe a low-liquidity WPC/tokenX Uniswap V3 pool (as created by `step_create_all_wpc_pools` with amounts like `1 tokenX / 4 WPC`).
2. Attacker submits a large `tokenX -> WPC` swap directly against the pool to skew price beyond +5%.
3. In the same or next block, attacker's own previously-submitted source-chain `GAS` deposit reaches UV vote quorum, triggering `ExecuteInboundGas` → `GetSwapQuote` (reads the now-skewed price) → `CallPRC20DepositAutoSwap` with `minPCOut = quote*0.95`, executing the module's tokenX→WPC swap at the manipulated rate into attacker's UEA.
4. Attacker reverses their manipulation swap (`WPC -> tokenX`), restoring price and pocketing the WPC surplus minted/paid out by the pool during the manipulated window.

```go
// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
```
