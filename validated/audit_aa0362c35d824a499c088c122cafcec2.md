### Title
Unbounded per-asset map iteration in `getAccountResource` causes O(N) DB reads and response-size amplification - (`framework/src/main/java/org/tron/core/services/http/GetAccountResourceServlet.java`)

### Summary
`GetAccountResourceServlet.fillResponse` calls `Wallet.getAccountResource`, which builds `assetNetUsed`/`assetNetLimit` maps by iterating every distinct asset the queried account has recorded free-bandwidth usage for, issuing one extra store lookup per asset and embedding one entry per asset in the JSON response. Neither the map construction nor the JSON serialization enforces any cap on the number of entries, so a single, fixed-size HTTP request against an account holding many distinct assets forces the node to perform O(N) database reads and emit an O(N)-sized response.

### Finding Description
`GetAccountResourceServlet.fillResponse` invokes `wallet.getAccountResource(address)` and serializes the result with `JsonFormat.printToString(reply, visible)` with no size limiting: [1](#0-0) 

`Wallet.getAccountResource` calls `setAssetNetLimit`, which pulls `accountCapsule.getAllFreeAssetNetUsageV2()` (a `map<string,int64>` keyed per distinct asset held/used by the account) and, for every key in that map, performs an additional `AssetIssueV2Store.get(key)` lookup to populate `assetNetLimitMap`, before both maps are attached to the response via `putAllAssetNetUsed`/`putAllAssetNetLimit`: [2](#0-1) [3](#0-2) 

The underlying map fields are unbounded protobuf maps declared without any size constraints: [4](#0-3) 

The `free_asset_net_usageV2` map on `AccountCapsule` grows one entry per distinct TRC10 asset the account has sent via `TransferAssetContract` while consuming free bandwidth for that asset (see `BandwidthProcessor.useAssetAccountNet`), and there is no cap on how many distinct assets an account may hold or transact with: [5](#0-4) 

The only protection on this HTTP endpoint is `RateLimiterServlet`, which limits request *rate* (QPS/global permits), not the computational/response cost of an individual accepted request: [6](#0-5) 

Since an attacker can accumulate balances across many distinct pre-existing TRC10 assets (via `ParticipateAssetIssueContract`) and then issue one `TransferAssetContract` per asset as owner to populate the free-asset-net-usage map entry for that asset, the account's `getaccountresource` response size and the per-request DB read count both scale linearly with the number of distinct assets the attacker chooses to touch. This lets a small, fixed-size read request (just an address) trigger disproportionate node-side work (N extra key-value store lookups) and network egress (N map entries in the JSON payload), repeatable at the endpoint's allowed request rate.

### Impact Explanation
An attacker who builds up (or already controls) an account interacting with many thousands of distinct TRC10 assets can repeatedly call `/wallet/getaccountresource` (or the gRPC `GetAccountResource`) to force the full node to perform thousands of extra store reads and serialize a proportionally large JSON response per request. Repeated at the endpoint's allowed QPS, this produces amplified CPU (asset-store lookups, map construction, JSON serialization) and outbound bandwidth costs on the node compared to the trivial cost of the request itself, degrading availability for other API consumers.

### Likelihood Explanation
Feasibility depends on the attacker first accumulating balances in many distinct existing TRC10 tokens (via `ParticipateAssetIssueContract`, which only requires TRX to participate) and issuing one `TransferAssetContract` per token to populate a free-asset-net-usage entry. This is not free but is achievable at scale on networks with many TRC10 assets already issued, and no on-chain or off-chain mechanism caps the number of distinct assets or bounds the resulting map size. Once built, the endpoint can be hit repeatedly (bounded only by generic QPS rate limiting, not per-request cost), making the DoS effect repeatable.

### Recommendation
Cap the number of asset entries returned by `getAccountResource`/`getAccountNet` (e.g., truncate or paginate `assetNetUsed`/`assetNetLimit`), or move large per-asset breakdowns to a separate paginated endpoint. Additionally, consider a request-cost-aware rate limiter for endpoints whose response size scales with account-controlled state (e.g., weight QPS budget by number of assets/maps returned) rather than relying solely on flat QPS limiting in `RateLimiterServlet`.

### Proof of Concept
Integration test plan (JUnit, extending `WalletTest`/`GetAccountResourceServletTest` patterns already in the repo):
1. Programmatically issue or fabricate N (e.g., 1,000–10,000) distinct `AssetIssueCapsule` entries in `AssetIssueV2Store` with non-zero `free_asset_net_limit`.
2. For a synthetic `AccountCapsule`, populate `free_asset_net_usageV2` with one entry per asset (directly via capsule builder, mirroring what `BandwidthProcessor.useAssetAccountNet` would persist after N real `TransferAssetContract` transactions).
3. Store the account and call `wallet.getAccountResource(address)`; measure:
   - number of `AssetIssueV2Store.get()` calls performed (should equal N, confirming O(N) DB reads),
   - `System.nanoTime()` around `JsonFormat.printToString(reply, visible)` and the resulting output byte length.
4. Assert that response byte size and serialization time grow linearly with N (e.g., fit slope > 0, and byte size for N=10,000 is roughly 10x that for N=1,000), demonstrating the disproportionate response-size/compute-cost scaling versus the fixed, tiny request payload (`{"address": "..."}`).

  private Map<String, Long> setAssetNetLimit(Map<String, Long> assetNetLimitMap,
      AccountCapsule accountCapsule) {
    Map<String, Long> allFreeAssetNetUsage;
    if (chainBaseManager.getDynamicPropertiesStore().getAllowSameTokenName() == 0) {
      allFreeAssetNetUsage = accountCapsule.getAllFreeAssetNetUsage();
      allFreeAssetNetUsage.keySet().forEach(asset -> {
        byte[] key = ByteArray.fromString(asset);
        assetNetLimitMap
            .put(asset, chainBaseManager.getAssetIssueStore().get(key).getFreeAssetNetLimit());
      });
    } else {
      allFreeAssetNetUsage = accountCapsule.getAllFreeAssetNetUsageV2();
      allFreeAssetNetUsage.keySet().forEach(asset -> {
        byte[] key = ByteArray.fromString(asset);
        assetNetLimitMap
            .put(asset, chainBaseManager.getAssetIssueV2Store().get(key).getFreeAssetNetLimit());
      });
    }
    return allFreeAssetNetUsage;
  }
