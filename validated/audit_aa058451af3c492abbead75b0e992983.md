Based on my research, I found a concrete analog in the `ValidateMultiSign` precompiled contract's signature-deduplication logic.

### Title
ECDSA Signature Malleability Allows Multi-Sig Weight Double-Counting in `ValidateMultiSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompile deduplicates submitted signatures by comparing raw signature *bytes*, rather than deduplicating by recovered signer address alone. Because `ECKey.ECDSASignature.validateComponents()` does not enforce the canonical/low-`s` form of ECDSA signatures, a single valid signature `(r, s, v)` can be trivially transformed into a second, distinct byte sequence `(r, n-s, v')` that recovers to the *same* address [1](#0-0) . The dedup check in `ValidateMultiSign.execute` only skips counting a signature twice if the *exact byte sequence* was already seen for that address; a malleable variant bypasses this and has its weight added again [2](#0-1) .

### Finding Description
`ValidateMultiSign.execute` iterates over the caller-supplied signature array, recovers an address for each, and tracks which (address, signature-bytes) pairs have already been counted via `executedSignList`:

```java
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
``` [3](#0-2) 

The intent of `matrixContains(executedSignList, recoveredAddr)` followed by `matrixContains(executedSignList, sign)` is clearly to allow one weight-contribution per signer address — the `continue` only fires when the exact same signature bytes reappear. If the recovered address matches an address already counted, but the raw signature bytes differ, execution falls through to `MUtil.checkCPUTime()` and the weight is added **again** for the same underlying key.

The root cause is that `ECDSASignature.validateComponents()` only checks that `r` and `s` are within `[1, SECP256K1N)`; it does not reject the malleable high-`s` form [1](#0-0) . For secp256k1, `(r, s, v)` and `(r, n-s, v XOR 1)` are both valid signatures of the same message by the same key, yielding two different byte encodings that recover to the identical address. This is the same bug class as the OpenZeppelin advisory: code that treats "have we seen this exact signature bytes" as the authorization/replay unit, instead of "have we seen this signer," is bypassable by producing an alternate valid encoding of the same signature.

### Impact Explanation
An attacker holding just one valid signer's signature over the multi-sig message can flip it to its malleable counterpart and submit both encodings in the `ValidateMultiSign` (or `BatchValidateSign`) precompile call. `totalWeight` is incremented twice for a single real signer, which can let an attacker satisfy the `permission.getThreshold()` check with fewer genuine co-signers than actually required — a direct authorization/threshold-bypass impact for any smart contract relying on TVM's `ValidateMultiSign` precompile (address `0x66` family) for multi-signature authorization logic.

### Likelihood Explanation
Likelihood is high for any contract that uses `ValidateMultiSign` with a multi-key permission and a threshold greater than a single key's weight: generating the malleable counterpart signature (`s' = n - s`, `v' = v XOR 1`) is a purely local, permissionless computation requiring no private key access — it only needs one already-obtained valid signature.

### Recommendation
Enforce canonical/low-`s` signatures before accepting them in `ValidateMultiSign`/`BatchValidateSign`, e.g., reject `s > HALF_CURVE_ORDER` in `ECDSASignature.validateComponents()` (mirroring `toCanonicalised()`'s bound, already present in the class at [4](#0-3) ), or change the dedup key in the precompile loop to be solely the recovered address rather than address+raw-signature-bytes, so a second signature from the same signer never increases `totalWeight`.

### Proof of Concept
1. Signer A signs message hash `h` producing `(r, s, v)`, valid per `ECDSASignature.validateComponents` and recovering to address `A`.
2. Attacker computes the malleable counterpart `s' = SECP256K1N - s`, `v' = v XOR 1` (flip recovery id), producing a second byte-distinct signature that also recovers to address `A`.
3. Attacker calls `ValidateMultiSign` with signature array `[sig1, sig2]` for a permission where `A`'s weight alone is below `threshold` but `2 * weight(A) >= threshold`.
4. In `ValidateMultiSign.execute`, the first iteration adds `weight(A)`. In the second iteration, `recoveredAddr == A` is already in `executedSignList`, but the raw signature bytes differ from `sig1`, so the inner `continue` is skipped, `MUtil.checkCPUTime()` runs, and `weight(A)` is added a second time. `totalWeight` now reaches `threshold` using only one real signer, and `execute` returns `dataOne()` (success) [5](#0-4) .

Note: I was not able to fully locate/verify the exact implementation of `recoverAddrBySign`/`merge`/`extractSigArray` (they appear referenced but their body was not returned by the index), so the exact byte-level format handling (e.g. whether `merge` normalizes signatures before comparison) could not be 100% confirmed from the available index; a Devin session with full file access would be needed to confirm no additional normalization step is applied to `sign` before the `matrixContains` byte comparison.
