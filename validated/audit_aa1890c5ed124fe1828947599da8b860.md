### Title
Stale globally-cached Cairo0 (deprecated) compiled classes are never re-verified against on-chain declaration state, unlike Cairo1 classes - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` explicitly re-verifies a cache-hit against `is_declared` **only** for Cairo1 (non-`V0`) classes, with an explicit comment stating the cache "might contain a declared class from a reverted block." For Cairo0/`V0` classes the same stale-cache risk exists but the verification branch is skipped, so a cached V0 class remains authoritative forever regardless of whether the class is still actually declared in the current (possibly reverted/reorged) state — exactly the Ajna-style bug pattern: an invalidation event occurs (block revert removes the declaration) but a previously-cached/"deposited" entry is still treated as valid because the freshness check isn't applied uniformly.

### Finding Description
`get_compiled_from_class_manager` in `crates/blockifier/src/state/state_reader_and_contract_manager.rs` (lines 65-104) is the single chokepoint blockifier execution uses to resolve a `ClassHash` into a `RunnableCompiledClass` for any node process that keeps this process-global `ContractClassManager` cache warm across multiple block-building/validation attempts (proposer building several candidate blocks, or a validator re-processing a reorg'd/reverted proposal):

```rust
if let Some(runnable_class) =
    self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
{
    match &runnable_class {
        RunnableCompiledClass::V0(_) => {}
        _ => {
            // The Cairo1 class is cached; verify it is declared,
            // since existence in the cache does not guarantee that
            // (it might contain a declared class from a reverted block, for example).
            if !self.state_reader.is_declared(class_hash)? {
                return Err(StateError::UndeclaredClassHash(class_hash));
            }
        }
    }
    ...
    return Ok(runnable_class);
}
``` [1](#0-0) 

The comment itself documents the threat model: a class can be inserted into the process-wide cache (`self.contract_class_manager.set_and_compile`) while executing a proposal/validation attempt that is later discarded (block build fails, proposal is rejected, or state is reverted). The `is_declared` re-check exists precisely to close that gap for Cairo1 classes: [2](#0-1) 

But `FetchCompiledClasses::is_declared` is documented and implemented to always cover this only for Cairo1: "Cairo 0 classes always return `false`." [2](#0-1)  Consequently the `RunnableCompiledClass::V0(_) => {}` branch performs **no** freshness check at all, so a Cairo0 class placed in the cache from a discarded attempt remains servable from the shared `ContractClassManager` (`TrivialClassManager`/`NativeClassManager`) cache indefinitely: [3](#0-2) . The cache is a simple LRU keyed only by `ClassHash` with no notion of "committed" vs "speculative" state — set once, served forever until evicted by capacity, exactly like the Ajna bucket LP remaining valid after `bankruptcyTime` because the deposit-time check only applied in one direction.

The existing regression test suite even enumerates this exact asymmetry and encodes it as expected/accepted behavior rather than fixing it: `cairo_1_declared_then_verification_failed_after_reorg` re-verifies and fails for V1, while `cairo_0_cached_scenario` supplies `is_declared_result: None` (no call expected) and still returns success unconditionally: [4](#0-3) 

### Impact Explanation
Any deployed/declared Cairo0 class hash that gets cached during a discarded/reverted block-building or validation attempt can continue to be executed as "declared" on nodes whose process retained that cache entry, even after the chain state (via reorg, failed proposal, or `revert_state_diff`) no longer shows it as declared — see the storage layer explicitly deleting declared-class records on revert: [5](#0-4) . Because whether a given sequencer node's local cache happens to be warm or cold for a particular class hash is a function of local execution history (which proposals it previously built/validated), different honest nodes can reach different execution results (`UndeclaredClassHash` error vs. successful execution) for the same transaction/class hash at the same height — an honest-node divergence in transaction outcome, execution trace, and therefore state root/commitment.

### Likelihood Explanation
This is reachable purely through the normal, unprivileged transaction path: any account can submit a `DECLARE` transaction for a Cairo0 class. If that declare is included in a proposal that is subsequently discarded (e.g., consensus round fails, validator rejects the proposal, or the chain reorganizes), the class is already resident in the process-global `ContractClassManager` cache of every node that attempted to build/validate/execute that proposal (since `set_and_compile` is called unconditionally on first `get_compiled_classes` cache miss, prior to any commit). No malicious operator/peer/staker action is required; ordinary block-building contention or a natural reorg is sufficient to create the divergence.

### Recommendation
Remove the `RunnableCompiledClass::V0(_) => {}` exemption and re-verify Cairo0 cache hits against on-chain declaration state the same way Cairo1 classes are verified, or extend `FetchCompiledClasses::is_declared` to also check Cairo0 declarations (rather than hard-coding it to always return `false`), so that a stale cache entry (from a discarded/reverted attempt) can never be served as authoritative for either class version.

### Proof of Concept
1. Node N is a proposer/validator that receives a `DECLARE` transaction for a fresh Cairo0 class `C` (not previously declared on-chain).
2. During candidate-block execution, `get_compiled_from_class_manager` misses the cache, calls `state_reader.get_compiled_classes(C)`, and populates the shared `ContractClassManager` cache via `set_and_compile` [6](#0-5) .
3. That candidate proposal is discarded (consensus round times out / proposal rejected / block reverted via `revert_state_diff`, which deletes the declared-class record) [7](#0-6) .
4. A later transaction (from any sender) references class hash `C` (e.g., `deploy` or `replace_class`) even though `C` is genuinely not declared in the now-canonical state.
5. On node N, `get_compiled_from_class_manager` hits the warm cache, takes the `RunnableCompiledClass::V0(_) => {}` branch, performs no `is_declared` check, and returns the cached class successfully — executing code for a class hash the rest of the network (whose caches never got warmed, or were, differently) would reject with `StateError::UndeclaredClassHash`. This produces divergent execution outcomes between honest nodes for the identical block/transaction.

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }

fn delete_declared_classes_block<'env>(
    txn: &'env DbTransaction<'env, RW>,
    thin_state_diff: &ThinStateDiff,
    declared_classes_block_table: &'env DeclaredClassesBlockTable<'env>,
    block_number: BlockNumber,
) -> StorageResult<Vec<ClassHash>> {
    let mut deleted_data = Vec::new();
    for class_hash in thin_state_diff.class_hash_to_compiled_class_hash.keys() {
        let class_block_entry =
            declared_classes_block_table.get(txn, class_hash)?.ok_or_else(|| {
                StorageError::DBInconsistency {
                    msg: format!(
                        "Attempting to revert declaration of class {class_hash} but it doesn't \
                         exist in the DB"
                    ),
                }
            })?;
        if class_block_entry == block_number {
            declared_classes_block_table.delete(txn, class_hash)?;
            deleted_data.push(*class_hash);
        }
    }
    Ok(deleted_data)
}

fn delete_declared_classes<'env>(
    txn: &'env DbTransaction<'env, RW>,
    thin_state_diff: &ThinStateDiff,
    declared_classes_table: &'env DeclaredClassesTable<'env>,
    file_handlers: &FileHandlers<RW>,
) -> StorageResult<IndexMap<ClassHash, SierraContractClass>> {
    let mut deleted_data = IndexMap::new();
    for class_hash in thin_state_diff.class_hash_to_compiled_class_hash.keys() {
        let Some(contract_class_location) = declared_classes_table.get(txn, class_hash)? else {
            continue;
        };
        deleted_data.insert(
            *class_hash,
            file_handlers.get_contract_class_unchecked(contract_class_location)?,
        );
        declared_classes_table.delete(txn, class_hash)?;
    }

    Ok(deleted_data)
}
