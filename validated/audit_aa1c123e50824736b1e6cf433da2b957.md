### Title
Disk-backed accounts-index (`BucketMap`) growth panics the validator when the underlying storage cannot allocate a new mmap file - ([File: bucket_map/src/bucket_storage.rs])

### Summary
The Chainlink oracle bug class is: a function unconditionally trusts an external resource to be available, has no fallback/error-handling path when that resource becomes unavailable, and thus reverts/DOSes core functionality. The analogous pattern in Agave is `BucketStorage::map_open_file`, used every time the disk-backed `BucketMap` (accounts index) creates or grows a bucket file. When file creation or the `mmap` call fails, the code `panic!`s instead of returning a recoverable error, crashing the whole validator process rather than just failing one operation.

### Finding Description
`BucketStorage::map_open_file` opens (and optionally creates) a backing file for a bucket and then mmaps it: [1](#0-0) 
If `OpenOptions::open` fails while `create == true` (e.g., disk full, out of inodes, out of file descriptors, permission/IO error), the function panics with `panic!("Unable to create data file ...")` rather than propagating an error. Similarly, if the subsequent `MmapMut::map_mut` fails, it panics as well: [2](#0-1) 

This code path is reached from `BucketStorage::new_map`, which itself is `unwrap()`-ed: [3](#0-2) 

`new_map` is invoked both for initial bucket allocation (`new_with_capacity`) and for bucket growth/resize (`new_resized`, used when an index or data bucket must grow to accommodate more entries): [4](#0-3) [5](#0-4) 

The `BucketMap`/`BucketStorage` machinery backs the on-disk `AccountsIndex` when `IndexLimit::Minimal` or `IndexLimit::Threshold` is configured: [6](#0-5) 
Every account insertion/update that grows a bin beyond its current bucket capacity (i.e., ordinary transaction processing that creates new accounts) can trigger a bucket grow, which allocates a new mmap'd file via this same panicking code path. Unlike the Solidity `Oracle` contract where a `require`/revert only fails a single call (and the report was rated Medium because of temporary DOS), here the fallback-less failure is a Rust `panic!` that aborts the entire validator process — a full node crash, not merely one failed call.

### Impact Explanation
An unhandled `panic!` on a routine, externally-influenced condition (disk space exhaustion, fd/mmap limits, transient IO errors) in the hot path of accounts-index maintenance crashes the entire validator process. Because index/data bucket growth is driven directly by ordinary account creation from user transactions, an unprivileged combination of normal cluster load and disk pressure (not a maliciously crafted snapshot, not a config-only/bootstrap-only issue) can trigger this panic during regular operation of any validator that opts into the disk-backed index (`--accounts-index-memory-limit-mb` / disk index config). This matches the accepted "node panic" impact category for this scan.

### Likelihood Explanation
Reaching this path requires: (1) the validator being configured with `IndexLimit::Minimal` or `IndexLimit::Threshold` (i.e., using the disk-backed accounts index, a supported, non-default but common configuration for memory-constrained nodes), and (2) the underlying disk/mmap subsystem failing to satisfy a new-file/mmap request (disk full, fd exhaustion, filesystem error). Bucket growth happens continuously as new accounts are created cluster-wide, so any transient storage pressure — which is plausible in long-running production nodes as account counts grow — can hit this panic without any attacker action beyond normal transaction volume. This is not a bootstrap-only or config-fixable-only condition; it can occur at any point during steady-state operation as the index naturally grows.

### Recommendation
Change `map_open_file`, `new_map`, and their callers (`new_with_capacity`, `new_resized`, `Bucket::new`) to propagate a `Result`/recoverable error instead of `panic!`/`unwrap()` on file-open or mmap failure. On failure, the accounts index should apply fallback logic analogous to what the oracle report recommends: e.g., retry after clearing space, fall back to a smaller allocation, surface a clear operator-actionable error, or gracefully reject the specific insert/grow operation instead of aborting the whole process.

### Proof of Concept
Conceptual reproduction (exact steps could not be fully validated without running the code, so this is presented as a code-path trace rather than a demonstrated exploit):
1. Configure a validator with a disk-backed accounts index (`IndexLimit::Minimal`/`Threshold`), pointing `accounts-index-path` at a filesystem that is near-full or has restrictive fd limits. [7](#0-6) 
2. Drive ordinary transaction load that creates enough new accounts to force an index bin to exceed its current bucket capacity, triggering `Bucket`/`BucketStorage` growth (`new_resized` → `new_with_capacity` → `new_map`).
3. When the filesystem cannot satisfy the new file creation or `mmap` call (e.g., `ENOSPC`), `map_open_file` panics: [8](#0-7) 
4. The panic unwinds/aborts the validator process, taking the node offline — analogous to the Oracle contract reverting `viewPrice`/`getPrice` with no fallback, except here the entire node (not just one call) goes down.

    fn new_map(drives: &[PathBuf], bytes: u64, stats: &BucketStats) -> (MmapMut, PathBuf, u128) {
        let r = rng().random_range(0..drives.len());
        let drive = &drives[r];
        let file_random = rng().random_range(0..u128::MAX);
        let pos = format!("{file_random}");
        let file = drive.join(pos);
        let res = Self::map_open_file(file.clone(), true, bytes, stats).unwrap();

        (res, file, file_random)
    }
