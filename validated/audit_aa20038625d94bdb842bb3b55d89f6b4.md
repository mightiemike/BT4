### Title
Alias allocation in `finalize_block` mutates state diff after bouncer weights are finalized, causing state-diff size to be undercounted against the block's `state_diff_size`/DA capacity - (File: crates/blockifier/src/blockifier/transaction_executor.rs)

### Summary
`finalize_block` calls `allocate_aliases_in_storage` to write new alias entries into the alias contract's storage **after** all per-transaction bouncer accounting has already completed, and the block's final `bouncer_weights` (including `state_diff_size`) is taken from the bouncer's accumulated per-transaction weights rather than recomputed from the actual, alias-augmented state diff that is ultimately committed and hashed.

### Finding Description
During block building, each transaction's contribution to the `state_diff_size` bouncer weight is computed per-transaction in `get_tx_weights` from that transaction's marginal `StateChangesKeys` [1](#0-0) , and accumulated into `Bouncer.accumulated_weights.bouncer_weights` via `try_update`/`update` as each transaction is admitted to the block [2](#0-1) .

At block finalization, `finalize_block` first (optionally) allocates aliases in storage for all new addresses/keys touched during the block via `allocate_aliases_in_storage`, which performs additional `set_storage_at` writes into the alias contract (new alias entries plus the alias counter) directly on `block_state` [3](#0-2) , [4](#0-3) . Only *after* this mutation does the function compute `state_diff = block_state.to_state_diff()?.state_maps`, i.e., the final committed state diff *does* include these extra alias-contract storage writes [5](#0-4) .

However, the `bouncer_weights` returned in the same `BlockExecutionSummary` is simply read from the bouncer object that was locked at the very start of `finalize_block`, i.e., it is the sum of the per-transaction `state_diff_size` weights computed *before* any alias allocation happened: `bouncer_weights: *bouncer.get_bouncer_weights()` [6](#0-5) . Nowhere in `finalize_block` is the bouncer's `state_diff_size` (or `accumulated_weights`) updated to reflect the additional storage keys written by `allocate_aliases_in_storage` (the alias-contract counter key and one alias key per new address/storage key).

This mirrors the reported bug class exactly: an aggregate quantity used for downstream accounting/limits (`quorumVotes` / here `state_diff_size`) is snapshotted **before** a subsequent state mutation (`sunsetCollection` burn / here `allocate_aliases_in_storage`) that changes the very data the snapshot was supposed to represent, so the recorded value diverges from the true post-mutation state.

### Impact Explanation
The bouncer's `state_diff_size` weight (and the related `BouncerConfig.block_max_capacity.state_diff_size`) exists specifically to bound the size of the state diff that will be committed on-chain, since this diff size directly affects L1 data-availability cost accounting, Patricia-tree update resource estimation, and the OS's ability to re-execute/verify the block. Because the alias-contract writes performed in `finalize_block` are not reflected back into the bouncer's tracked weights, a block can be built and accepted by the bouncer as "within capacity" while its actual, final committed state diff (post-alias-allocation) is larger than what was measured/allowed. When `enable_stateful_compression` is active, this can push the true state diff past `block_max_capacity.state_diff_size` without the bouncer ever rejecting the responsible transactions, since the check happens strictly before the extra writes exist. Depending on how tightly downstream consumers (DA cost, Patricia commitment sizing, OS re-execution resource budgets) rely on the bouncer's reported `state_diff_size` matching the actual diff, this can lead to under-accounted DA/resource costs for a block and a state-diff size that silently exceeds the intended block capacity - a resource/limit-enforcement inconsistency between the value used for admission control and the value that is actually committed and hashed.

### Likelihood Explanation
This path is reachable by any set of unprivileged transactions: an attacker only needs to submit enough distinct new contract addresses/storage keys (each triggering a new alias allocation) close to the bouncer's `state_diff_size` capacity boundary so that the extra alias-contract writes performed in `finalize_block` push the real diff over the limit that was supposedly enforced. No special/privileged operator, proposer, or network behavior is required - only that `enable_stateful_compression` is enabled (a normal, non-adversarial protocol configuration) and that the block's marginal state changes are near the configured capacity.

### Recommendation
Move the bouncer's final `state_diff_size` bookkeeping to occur after `allocate_aliases_in_storage` (and any other post-hoc state mutations) have been applied, e.g., by recomputing/adjusting `accumulated_weights.bouncer_weights.state_diff_size` (and any other affected weight) from the marginal storage keys touched by alias allocation before reading `bouncer.get_bouncer_weights()` for the `BlockExecutionSummary`, or by re-deriving `state_diff_size` directly from the final `state_diff` computed at the end of `finalize_block` rather than from the pre-mutation accumulated bouncer state.

### Proof of Concept
Not executed (index-only analysis). Conceptually: enable `enable_stateful_compression`, submit a sequence of transactions that each touch new (previously-unaliased) contract addresses/storage keys such that the bouncer's accumulated `state_diff_size` sits just under `block_max_capacity.state_diff_size`. When `finalize_block` runs `allocate_aliases_in_storage`, it writes one new alias entry per unaliased key plus the alias-counter update directly into `block_state`, which are included in the final `state_diff` (and hashed/committed) but were never added back into `bouncer.accumulated_weights.bouncer_weights.state_diff_size`, demonstrating the discrepancy between the enforced limit and the actual committed diff size [7](#0-6) , [4](#0-3) .

pub fn allocate_aliases_in_storage<S: StateReader>(
    state: &mut CachedState<S>,
    alias_contract_address: ContractAddress,
) -> StateResult<()> {
    let state_diff = state.to_state_diff()?.state_maps;

    // Collect the contract addresses and the storage keys that need aliases.
    let contract_addresses: BTreeSet<ContractAddress> =
        state_diff.get_contract_addresses().into_iter().collect();
    let mut contract_address_to_sorted_storage_keys = HashMap::new();
    for (contract_address, storage_key) in state_diff.storage.keys() {
        if contract_address > &MAX_NON_COMPRESSED_CONTRACT_ADDRESS {
            contract_address_to_sorted_storage_keys
                .entry(contract_address)
                .or_insert_with(BTreeSet::new)
                .insert(storage_key);
        }
    }

    // Iterate over the addresses and the storage keys and update the aliases.
    let mut alias_updater = AliasUpdater::new(state, alias_contract_address)?;
    for contract_address in contract_addresses {
        if let Some(storage_keys) = contract_address_to_sorted_storage_keys.get(&contract_address) {
            for key in storage_keys {
                alias_updater.insert_alias(key)?;
            }
        }
        alias_updater.insert_alias(&StorageKey(contract_address.0))?;
    }

    alias_updater.finalize_updates()
}
