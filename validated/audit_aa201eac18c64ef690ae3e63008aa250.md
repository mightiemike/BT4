### Title
Miner-controlled 0x80 "shadow" bit in `NakamotoBlockHeader::version` lets an ordinary block skip signer-signature (and miner-signature/VRF) verification and be accepted with fabricated full reward-set signing weight - (File: `stackslib/src/chainstate/nakamoto/mod.rs`, `stackslib/src/chainstate/nakamoto/shadow.rs`)

### Summary
`is_shadow_block()` is defined purely as `version & 0x80 != 0` with no cross-check tying it to an authorized/emergency-SIP origin, and `verify_signer_signatures` (as well as `check_miner_signature` and `check_shadow_coinbase_tx`) each independently short-circuit their own verification whenever this bit is set, crediting full reward-set weight (`get_shadow_signer_weight`) without inspecting `signer_signature` at all. The only defense I could locate against an attacker exploiting this is a DB-level check inside `add_shadow_block` (tenure must be empty or already a shadow tenure), and I could not confirm that this check — or any equivalent gate — is enforced on the generic network block-acceptance path that calls `verify_signer_signatures` (`stackslib/src/chainstate/nakamoto/mod.rs:2917`) or on the tenure-download verification paths (`tenure_downloader.rs`, `tenure_downloader_unconfirmed.rs`) that also call `verify_signer_signatures` directly.

### Finding Description
The claimed equality is: `total_weight_signed` returned by `verify_signer_signatures` should equal the sum of weights of signers whose signatures are cryptographically verified and present, distinct, in `self.signer_signature`, and `>= threshold`. For a shadow-flagged block this equality is broken by design: [1](#0-0) 

```rust
// if this is a shadow block, then its signing weight is as if every signer signed it, even
// though the signature vector is undefined.
if self.is_shadow_block() {
    return Ok(self.get_shadow_signer_weight(reward_set)?);
}
```

`is_shadow_block()` is a pure bit test with no other precondition: [2](#0-1) 

The same unconditional bypass pattern (based solely on the version bit, with no origin check) also exists in `check_miner_signature` (confirmed by the test asserting a shadow-flagged block with a signature from the *wrong* key still passes `check_miner_signature`) and in `check_shadow_coinbase_tx` (which explicitly skips VRF-proof authenticity checks): [3](#0-2) 

`validate_header_static` masks off the high bit before checking the version against the epoch-expected version, so setting the bit does not by itself fail static header validation: [4](#0-3) 

The generic block-acceptance code path that stores a block into staging (used for normally mined/relayed/downloaded blocks) calls `verify_signer_signatures` directly and stores the returned "signing weight" verbatim: [5](#0-4) 

The only place I found that enforces an eligibility precondition tying the shadow bit to a legitimate, out-of-band origination process is `add_shadow_block`'s DB check that a shadow block can only enter an empty tenure or one that is already flagged as a shadow tenure: [6](#0-5) 

That guard lives in `add_shadow_block`, a dedicated insertion wrapper used only by the emergency shadow-tooling code path (e.g. `make_shadow_tenure`), not inside `store_block_if_better` or the generic staging/relay/download pathway. `verify_signer_signatures` is also called directly from tenure-download verification code (`tenure_downloader.rs`, `tenure_downloader_unconfirmed.rs`) with no visible `is_shadow_block`/obtain-method cross-check before that call. I was not able to fully retrieve the enclosing function/caller context around `mod.rs:2917` or the full body of the tenure-downloader call sites within the available iterations, so I cannot state with certainty whether some other, not-yet-located caller-level gate (e.g., an explicit `if block.is_shadow_block() { reject }` in the P2P ingestion code, `net/relay.rs`, or `net/download`) exists to prevent externally-received blocks from ever reaching `verify_signer_signatures` with the shadow bit set. A targeted search of `net/relay.rs` for any shadow-related handling returned no matches, which is consistent with (but does not conclusively prove) the absence of such a gate.

### Impact Explanation
If no such gate exists, an attacker miner who legitimately wins a sortition, builds and signs a normal block, then flips `header.version |= 0x80` before broadcast, would have that block accepted by conforming nodes with `total_weight_signed == full reward-set weight` despite an empty/irrelevant `signer_signature` vector — i.e., a block that never received the required 70%-weight signer quorum gets treated as fully approved. This would let an attacker single-handedly finalize blocks (e.g., double-spends, censorship, or otherwise-rejected transactions) without needing any signer cooperation, which is a critical invalid-block-accepted / signer-threshold-bypass condition, and if honest signers/nodes reject the same block via the normal path while other nodes accept it via the shadow-branch bypass, it produces a chain split.

### Likelihood Explanation
Preconditions: attacker needs only a single miner slot capable of winning at least one sortition (not majority stake), and knowledge of the version byte layout (public). No signer keys, no majority stake, no admin access needed — this matches the "unprivileged, single miner slot" attacker model. However, this finding's severity is entirely contingent on the unconfirmed premise that no upstream caller (in the network relay/download/accept-block code) rejects a block for merely being version-flagged as shadow without being sourced from the trusted shadow-tooling path. I could not conclusively confirm or refute that gate's existence/absence given the remaining tool budget.

### Recommendation
Add an explicit, non-bypassable precondition wherever a block/tenure is accepted from the network (relay, download, unsolicited-block handling) that rejects any block with `is_shadow_block() == true` unless it is being inserted via the dedicated `add_shadow_block` path (`obtain_method == NakamotoBlockObtainMethod::Shadow`), before `verify_signer_signatures`/`check_miner_signature`/`check_shadow_coinbase_tx` are ever invoked. Alternatively, tie shadow eligibility to a node-local, non-network-controllable flag (e.g., only allow shadow-bit blocks constructed by trusted in-process tooling, never accept them from `NetworkResult`/peer-received data at all), rather than trusting the header byte alone.

### Proof of Concept
```rust
// stackslib/src/chainstate/nakamoto/mod.rs (test module)
#[test]
fn shadow_bit_flip_bypasses_signer_signature_check() {
    // 1. Build a normally-tenured, non-shadow-eligible block with a valid
    //    tenure-change/coinbase but an EMPTY signer_signature vector.
    let mut header = make_normal_header(); // helper constructing a realistic header
    header.signer_signature = vec![];
    assert!(!header.is_shadow_block());

    // 2. Flip the high bit post-construction/post-signing, simulating an
    //    attacker miner who is NOT shadow-eligible (no SIP tooling, no
    //    add_shadow_block call, no reward-set participation).
    header.version |= 0x80;
    assert!(header.is_shadow_block());

    let reward_set = make_reward_set_with_nonzero_signers();
    let full_weight = reward_set
        .signers()
        .unwrap()
        .iter()
        .fold(0u32, |acc, s| acc + s.weight);

    // 3. Call verify_signer_signatures directly, as done by the generic
    //    block-acceptance path (mod.rs:2917-2925) and by tenure_downloader.rs.
    let result = header.verify_signer_signatures(&reward_set, StacksEpochId::Epoch30);

    // Equality under test: total_weight_signed should require >=70% of
    // ACTUAL, verified, distinct signatures. Instead:
    assert_eq!(result.unwrap(), full_weight, "BUG: shadow bit bypass credited full weight with zero real signatures");
}
```
This test demonstrates the broken equality inside `verify_signer_signatures` itself. To fully confirm exploitability at the network-consensus level, a companion two-node integration test is needed: node A crafts and relays/downloads such a block through the ordinary P2P path (not via `add_shadow_block`) and asserts it is stored/accepted with `signing_weight == u32::MAX`/full weight, while node B (running a patched node with a hypothetical gate) rejects it — if both nodes reject it identically, the upstream gate exists and this finding is invalid; if node A accepts it, the vulnerability is confirmed at the network level. I was unable to complete this second half of validation within the available tool budget, so the network-reachability claim (versus purely being a unit-level property of `verify_signer_signatures`) remains unconfirmed.
