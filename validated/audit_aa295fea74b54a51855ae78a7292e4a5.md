Based on my investigation, I found a genuine ordering issue in the native-position commit path that mirrors the report's bug class: an operation that finalizes/exposes state runs, and a related bookkeeping step (which should have gated it) runs *before* the state it depends on is fully advanced — leaving a window where a consumer can observe pruned or premature data.

### Title
Native-position pruner target is advanced before the persisted position summary is updated, allowing serviceable-node pruning ahead of the exposed base - (File: storage/aptosdb/src/position_merkle_batch_committer.rs)

### Summary
In `PositionMerkleBatchCommitter::run`, the position merkle pruners' target version is bumped to the just-committed `version` *before* `PositionPersistedState::set(snapshot)` is called to advance the base that execution reads via `PositionPersistedState::get()`. [1](#0-0) 

### Finding Description
`commit_native_position` enqueues a `PositionMerkleCommit{version, root_hash, batch, snapshot}` to the batch committer thread whenever a chunk with native-position writes is committed. [2](#0-1) 

Inside the committer's `run`, the sequence is:
1. `merkle_db.commit(version, ...)` — persist the new JMT nodes (and mark superseded nodes from the *previous* version as stale via `StaleNodeIndexSchema`, as shown by `merkle_pruner_in_group_prunes_stale_nodes` in `storage/aptosdb/src/position_pruner.rs`).
2. `position_pruner.state_merkle_pruner.maybe_set_pruner_target_db_version(version)` and `position_pruner.epoch_snapshot_pruner.maybe_set_pruner_target_db_version(version)` — this can immediately wake the pruner thread and prune all nodes marked `stale_since_version <= version`.
3. Only *after* that, `persisted.set(snapshot)` advances `PositionPersistedState`, the shared base that concurrent readers get via `PositionPersistedState::get()` and that execution uses "as the freeze base and proof source" per its own doc comment in `storage/storage-interface/src/lib.rs`. [3](#0-2) 

Between steps 2 and 3 there is a window in which:
- A concurrent reader that already called `PositionPersistedState::get()` and obtained the **old** (pre-commit) snapshot may still be reading nodes from the old base version. If `state_merkle_pruner_config.prune_window == 0` (a legal, tested configuration — see the `merkle_pruner_in_group_prunes_stale_nodes` test using `prune_window: 0`), the pruner can delete those exact stale nodes the instant step 2 fires, i.e. before step 3 has republished the "safe" base.
- The comment directly above `persisted.set(snapshot)` even documents the intended invariant being violated: *"Advance the persisted base only now that the JMT nodes at `version` are on disk, so cold-key proofs against this base are serviceable."* That comment only accounts for node-durability ordering, not pruner-driven deletion ordering, so activating the pruner before this line breaks the same invariant it is trying to protect. [4](#0-3) 

This is structurally the same bug class as the referenced report: an unprivileged, always-on background process (`withdrawRemainingTokens` there, the pruner-wake here) performs a state-changing action based on the *latest committed version* without accounting for consumers whose reference point (the pending receipt / the not-yet-updated `PositionPersistedState`) hasn't been advanced to match, causing correct-at-the-time in-flight work to fail against ledger data that has since been reinterpreted/removed.

### Impact Explanation
If a concurrent `get_position_state_proof_by_version_ext` / cold-key proof read (routed through `ProvablePositionStateSummary::new_persisted` in `execution/executor/src/chunk_executor/mod.rs`) is in-flight against the old `PositionPersistedState` snapshot when the pruner races ahead and deletes the referenced JMT nodes, the read will fail to find the nodes or (in a debug-assert-off build) could silently return proof data inconsistent with the exposed root, producing a proof that cannot be verified against the version it claims to represent. That falls squarely into the "wrong accumulator root / Merkle proof / state proof accepted as valid" and "authenticated API response bound to the wrong version" impact categories, since native-position proofs are consumed as durable ledger/proof material for the trading-native feature.

### Likelihood Explanation
This requires: (a) native-position storage enabled (`ENABLE_TRADING_NATIVE`), (b) an aggressive/zero pruning window (explicitly a supported and tested configuration), and (c) a reader racing the commit-pipeline's background thread within the narrow window between steps 2 and 3. This is a genuine internal race condition rather than something an external attacker directly triggers, so likelihood is low-to-moderate and depends on operational pruner configuration; I was not able to fully trace every caller of `PositionPersistedState::get()` to confirm a concrete reachable reader in the current mainnet code path (the feature appears gated/experimental), so I cannot claim certainty about exploitability at Critical severity.

### Recommendation
Reorder the committer so `persisted.set(snapshot)` happens **before** `maybe_set_pruner_target_db_version` calls, mirroring the intent already documented in the code, so the pruner can never advance past a version that concurrent readers might still be pinned to. Alternatively, have `PositionPersistedState::get()` register a live-reader guard (similar to the `old_views` tracking mechanism used in `storage/aptosdb/src/state_store/hot_state.rs`) that the pruner must respect before deleting stale nodes.

### Proof of Concept
Not independently reproducible with static analysis alone — this requires a runtime race (thread interleaving) between the `position_merkle_batch_committer` thread and a concurrent `PositionPersistedState::get()` caller under `prune_window: 0`, which I could not execute in this read-only investigation. The `merkle_pruner_in_group_prunes_stale_nodes` test in `storage/aptosdb/src/position_pruner.rs` confirms that stale-node pruning is immediate and synchronous under `prune_window: 0`, supporting the theoretical race, but I did not verify an end-to-end failing reproduction.

    fn commit_native_position(&self, chunk: &ChunkToCommit, sync_commit: bool) -> Result<()> {
        let _timer = OTHER_TIMERS_SECONDS.timer_with(&["commit_native_position"]);
        let Some(bundle) = self.position.as_ref() else {
            return Ok(());
        };
        if chunk.transaction_outputs.is_empty() {
            return Ok(());
        }
        let committer = NativeStateCommitter::new(bundle.kv_db.clone());

        let chunk_first = chunk.first_version;
        let chunk_last_inclusive = chunk_first + chunk.transaction_outputs.len() as Version - 1;

        // Persist the position KV values + stale index.
        let mut sharded_kv_batches = new_sharded_kv_batches();
        let mut in_chunk_prior = InChunkPriorVersions::new();
        for (i, output) in chunk.transaction_outputs.iter().enumerate() {
            let version = chunk_first + i as Version;
            let position_writes: Vec<_> = output
                .write_set()
                .native_position_iter()
                .map(|(k, op)| (k.clone(), op.as_write_op().clone()))
                .collect();
            if !position_writes.is_empty() {
                committer
                    .apply(
                        version,
                        position_writes,
                        &mut sharded_kv_batches,
                        &mut in_chunk_prior,
                    )
                    .map_err(|e| AptosDbError::Other(format!("native commit: {e}")))?;
            }
        }
        bundle
            .kv_db
            .commit(chunk_last_inclusive, None, sharded_kv_batches)
            .map_err(|e| AptosDbError::Other(format!("position_db commit failed: {e}")))?;

        // Advance the position pipeline (merklize + persist + advance the base).
        // Flag on: the summary comes from execution on the chunk; off: compute
        // it here so the tree still tracks forward (not consensus-committed).
        if let Some(store) = bundle.state_store.as_ref() {
            let new_state = match chunk.position_state_summary {
                Some(summary) => summary.clone(),
                None => self.position_summary_at_commit(chunk)?,
            };
            let estimated_items = chunk.transaction_outputs.len();
            let mut bufstate = store.buffered_state_locked();
            bufstate.update(
                new_state,
                (),
                estimated_items,
                sync_commit || chunk.is_reconfig,
            )?;
        }
        Ok(())
