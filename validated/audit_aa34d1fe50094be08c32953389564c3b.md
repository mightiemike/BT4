### Title
No vulnerability — P2WSH/P2TR code-data confusion in `deposit` is already mitigated by `verifySigInTx` Schnorr re-verification - ([File: crates/evm/src/evm/system_contracts/src/Bridge.sol])

### Summary
The question describes a historical, documented vulnerability (P2WSH `OP_2DROP OP_TRUE` script substituted for a real P2TR witness to fake a deposit). The currently deployed `deposit` function calls `verifySigInTx` **before** trusting any parsed script contents, which independently reconstructs the BIP-341 message hash and validates the N-of-N Schnorr signature against the aggregated key via the precompile at `0x200`. This closes the exact gap the question probes.

### Finding Description
The binding claimed to be at risk: `cBTC credited via recipient.call{value: depositAmount}` (in `Bridge.sol` deposit) `== an actual N-of-N-signed moveTx spending real BTC into the bridge`.

Tracing `deposit(Transaction calldata moveTx, MerkleProof calldata proof, bytes32 shaScriptPubkeys)`:
1. `validateAndCheckInclusion` checks `BTCUtils.validateVin`/`validateVout` and Merkle inclusion, returning `nIns`, then `require(nIns == 1, "Only one input allowed")` [1](#0-0) .
2. `witness0` is extracted via `WitnessUtils.extractWitnessAtIndex(moveTx.witness, 0)` [2](#0-1) .
3. Critically, **before** any script/prefix/suffix parsing, `verifySigInTx(input, outputs, witness0, moveTx.version, moveTx.locktime, shaScriptPubkeys)` is called [3](#0-2) .
4. `verifySigInTx` reconstructs the full BIP-341 `TapSighash` message (`shaPrevouts`, `shaAmounts`, `shaSequences`, `shaOutputs`, `tapleafHash` from witness item 1 as script and item 2 as control block, etc.) and calls `isSchnorrSigValid(aggregatedKey, messageHash, signature)` against the Schnorr precompile at `0x200`, reverting with `"Invalid signature"` if it fails [4](#0-3) .
5. Only after this signature check succeeds does the code proceed to nullify the txId, check `nItems == 3`, extract the script via `extractItemFromWitness(witness0, 1)`, and validate `depositPrefix`/`depositSuffix` matching before extracting the recipient address [5](#0-4) .

The attack the question describes (P2WSH `OP_2DROP OP_TRUE` witness with an attacker-crafted script mimicking `depositPrefix`+address+`depositSuffix` as *data* rather than an actual P2TR script-path spend) is exactly the scenario `docs/system-contracts.md`'s "critical vulnerability we found in deposit" section documents [6](#0-5) . The documented mitigation is precisely `verifySigInTx`'s independent Schnorr signature check, which is present in the deployed code. Since the attacker cannot forge a valid N-of-N Schnorr signature over the reconstructed sighash without controlling the multisig's private keys, an attacker-crafted P2WSH witness with an `OP_2DROP OP_TRUE`-style "signature" placeholder fails `require(isSchnorrSigValid(...), "Invalid signature")` before the script-matching logic is ever trusted for recipient extraction.

There is also a regression test explicitly reproducing this exact attack scenario, `testP2TRTransactionTypeConfusionAttack`, which crafts a P2WSH-style witness matching the attack pattern and asserts it reverts with `"Invalid signature length"` (an even earlier failure than `"Invalid signature"` due to signature length checks in `isSchnorrSigValid`), confirming the attacker's balance remains `0` [7](#0-6) .

### Impact Explanation
No impact — the mitigation is present and enforced on every `deposit`/`replaceDeposit` call path (`replaceDeposit` has the identical `verifySigInTx` call before script matching) [8](#0-7) .

### Likelihood Explanation
Not applicable — the described binding holds: cBTC is only minted when the reconstructed Schnorr signature check passes against the currently-configured aggregated N-of-N key, which an unprivileged attacker without the multisig's private key cannot forge.

### Recommendation
No fix needed for this exact question; the existing `verifySigInTx` check (both in `deposit` and `replaceDeposit`) already implements the documented mitigation. Continued diligence should be paid to ensure `verifySigInTx` itself cannot be bypassed (e.g., malformed witness parsing edge cases in `WitnessUtils`), but that is a separate analysis from the one posed here.

### Proof of Concept
The existing test `testP2TRTransactionTypeConfusionAttack` in `crates/evm/src/evm/system_contracts/test/Bridge.t.sol` (lines 724-748) already implements the requested proof: it constructs a P2WSH-style attack witness with a `depositPrefix`+attacker-address+`depositSuffix` payload as data (not a genuine P2TR script-path spend signature), calls `bridge.deposit(...)`, and asserts `vm.expectRevert("Invalid signature length")` followed by `assertEq(attacker.balance, 0 ether)` [9](#0-8) , confirming the fix is landed and enforced in this exact function.

    /// @notice Verifies a P2TR signature by reconstructing the message hash and checking it against the provided signature, see BIP-341
    function verifySigInTx(bytes memory input, bytes memory outputs, bytes memory witness0, bytes4 version, bytes4 locktime, bytes32 shaScriptPubkeys) internal view {
        bytes32 shaPrevouts = sha256(input.extractOutpoint());
        bytes32 shaAmounts = sha256(abi.encodePacked(bytes8(BTCUtils.reverseUint64(uint64(depositAmount/(SAT_TO_WEI)))))); // 1000000000 in LE
        bytes32 shaSequences = sha256(abi.encodePacked(input.extractSequenceLEWitness()));
        bytes32 shaOutputs = sha256(abi.encodePacked(outputs));
        bytes memory script = witness0.extractItemFromWitness(1);
        bytes memory controlBlock = witness0.extractItemFromWitness(2);
        // First byte of the parsed control block is the length of it so it is skipped to get the actual first byte
        // We can safely assume the control block compact size to be single byte as the depth of taproot tree is 1 both for `deposit` and `replaceDeposit`
        bytes1 leafVersion = controlBlock[1] & 0xFE;
        bytes32 tapleafHash = taggedHash("TapLeaf", (abi.encodePacked(leafVersion, script)));
        bytes memory message = abi.encodePacked(EPOCH, SIGHASH_DEFAULT_HASH_TYPE, version, locktime, shaPrevouts, shaAmounts, shaScriptPubkeys, shaSequences, shaOutputs, SPEND_TYPE_EXT, INPUT_INDEX, tapleafHash, KEY_VERSION, CODESEP_POS);
        bytes32 messageHash = taggedHash("TapSighash", message);
        bytes memory signatureWithLen = witness0.extractItemFromWitness(0);
        bytes memory signature = signatureWithLen.slice(1, signatureWithLen.length - 1);
        bytes memory aggregatedKey = getAggregatedKey();
        require(isSchnorrSigValid(aggregatedKey, messageHash, signature), "Invalid signature");

### A critical vulnerability we found in `deposit`

We do this because we discovered an attack. We assume the passed `moveTx` is a [P2TR](https://learnmeabitcoin.com/technical/script/p2tr/) with script path spend type of Bitcoin transaction, which has the signature as its first witness item, the locking script as its second, and the control block as its third.
