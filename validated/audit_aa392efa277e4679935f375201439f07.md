### Title
Panic-based Denial of Service via inconsistent state-sync/class-manager class views during transaction validation - ([File: crates/apollo_gateway/src/sync_state_reader.rs])

### Summary
`SyncStateReader::get_contract_class_from_client` in `crates/apollo_gateway/src/sync_state_reader.rs:77-99` assumes that if the state-sync store reports a class as declared, the (separately maintained) class-manager store must already hold the executable class. When that invariant is violated, the code calls `panic!` instead of returning a recoverable `StateError`. This is directly analogous to CVE-2018-5737, where interaction between two independently-maintained caching subsystems (serve-stale and NSEC aggressive negative caching) in BIND could trigger an assertion failure/panic reachable from normal request processing. [1](#0-0) 

### Finding Description
`get_contract_class_from_client` first queries `state_sync_client.is_class_declared_at` (backed by the synced chain state / Patricia state) and, if it returns `true`, queries `class_manager_client.get_executable` (backed by a separate, independently populated local class store/cache). If the class manager returns `None` in this case, the code does not propagate a `StateError`; it panics:
```
.unwrap_or_else(|| {
    panic!(
        "Class with hash {class_hash:?} doesn't appear in class manager even though \
         it was declared"
    )
});
``` [2](#0-1) 

This "doesn't-appear" panic path is exercised and documented by an explicit `#[should_panic]` regression test, confirming that the code base itself is aware this is a reachable panic, not merely an unreachable defensive assertion: [3](#0-2) 

The two data sources (`state_sync_client` and `class_manager_client`) are updated through different pipelines (chain-state sync vs. class storage sync/compilation), so there is no atomic guarantee that "declared in state" implies "class bytes present in local class manager" at every instant a query is made — e.g., during node startup/resync windows, gaps in class-manager backfill, storage errors returned as `Ok(None)`, or any transient desync between the two components. `get_contract_class_from_client` is invoked from both `FetchCompiledClasses::get_compiled_classes` and `BlockifierStateReader::get_compiled_class`, which are exercised during stateful gateway transaction validation for any transaction (declare, invoke, or account class lookups) whose account/class hash is looked up via `SyncStateReader`, itself constructed per-transaction by `SyncStateReaderFactory` from the latest synced block. [4](#0-3) [5](#0-4) [6](#0-5) 

Because this executes synchronously inside a `self.runtime.block_on(...)`-driven code path handling an incoming transaction's stateful validation, a triggered panic aborts the handling task/thread for that request. Depending on how the gateway wires this blocking work into its async runtime (not fully confirmed by index; `gateway.rs` wiring of `SyncStateReader` was not resolvable within available context), a panic here can either fail a single request or, if unwind boundaries are missing/misconfigured, take down worker threads that serve other pending transaction validations, causing a broader denial of service for new transaction admission — the same class of "operational problems … degradation or denial of service" outcome described for the BIND CVE.

### Impact Explanation
An unprivileged transaction sender who references (in a `declare`, or any transaction whose account/class needs class-hash resolution) a class hash that is legitimately declared on-chain but which the local class-manager instance has not yet backfilled/cached can deterministically trigger this panic during stateful gateway validation. This maps to "a network unable to confirm new transactions" if worker threads/tasks handling gateway validation crash or are poisoned, since the sequencer/gateway becomes unable to process further transaction validations without a restart. Even in the best case (task-scoped panic only), it causes transaction-validation failures for perfectly legitimate transactions, directly harming users' ability to interact with declared classes.

### Likelihood Explanation
This is reachable purely by transaction submission that references any class hash, with no attacker privileges beyond being a normal transaction sender; the triggering condition (a temporary or persistent desync between `state_sync` and `class_manager` views of "is this class known") is an operational reality of a two-component architecture and is explicitly anticipated/tested for in the code base (`sync_state_reader_test.rs`), which increases confidence that this scenario is reachable in production deployments (e.g., during resync, partial backfill, or replication lag between the two services) rather than purely theoretical.

### Recommendation
Replace the `panic!` in `get_contract_class_from_client` with a recoverable `StateError` (e.g., `StateError::StateReadError` or a dedicated "class temporarily unavailable" variant) and handle it in the gateway as a retryable/transient validation failure instead of a fatal crash. Additionally, ensure any async task that calls into `SyncStateReader` from a shared runtime pool cannot poison other in-flight requests upon an internal panic (e.g., via `catch_unwind` at the task boundary or explicit `spawn_blocking` isolation).

### Proof of Concept
1. Bring up a sequencer/gateway instance where `state_sync` has synced a block in which class hash `H` is declared, but the co-located `class_manager` component has not yet persisted/cached the executable bytes for `H` (e.g., simulate by delaying/failing the class-manager backfill, or by restarting the class-manager service after a resync).
2. Submit any transaction (e.g., a `declare` referencing an account class, or an `invoke` whose sender's `class_hash_at` resolves to `H`) to the gateway for stateful validation.
3. `SyncStateReader::get_contract_class_from_client` is invoked; `state_sync_client.is_class_declared_at` returns `true` for `H`, but `class_manager_client.get_executable(H)` returns `Ok(None)`.
4. The `unwrap_or_else` branch executes `panic!("Class with hash {class_hash:?} doesn't appear in class manager even though it was declared")`, matching the exact scenario reproduced by the existing `#[should_panic]` test `test_get_compiled_class_panics_when_class_exists_in_sync_but_not_in_class_manager`.     fn get_contract_class_from_client(&self, class_hash: ClassHash) -> StateResult<ContractClass> {
        let is_class_declared = self
            .runtime
            .block_on(self.state_sync_client.is_class_declared_at(self.block_number, class_hash))
            .map_err(|e| StateError::StateReadError(e.to_string()))?;

        if !is_class_declared {
            return Err(StateError::UndeclaredClassHash(class_hash));
        }

        let contract_class = self
            .runtime
            .block_on(self.class_manager_client.get_executable(class_hash))
            .map_err(|e| StateError::StateReadError(e.to_string()))?
            .unwrap_or_else(|| {
                panic!(
                    "Class with hash {class_hash:?} doesn't appear in class manager even though \
                     it was declared"
                )
            });

        Ok(contract_class)
    }

    async fn get_blockifier_state_reader_and_gateway_fixed_block_from_latest_block(

    ) -> StateSyncClientResult<(

        Self::TGatewayFixedBlockStateReader,
    )> {
        let latest_block_number = self.shared_state_sync_client.get_latest_block_number().await?;

        // If no blocks exist yet, return genesis state readers for bootstrap transactions.

            self.shared_state_sync_client.clone(),
            self.class_manager_client.clone(),
            latest_block_number,

        );
        let gateway_fixed_block_sync_state_client = GatewayFixedBlockSyncStateClient::new(
            self.shared_state_sync_client.clone(),
            latest_block_number,
        );
