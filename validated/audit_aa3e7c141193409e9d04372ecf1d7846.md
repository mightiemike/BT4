## Finding

### Title
Replay-verification skips checkpoint/state-root fields of `TransactionInfo`, letting corrupted state, hot-state, or native-position roots pass verification as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by state-sync's `--verify-execution` chunk path and by the standalone `db-tool replay-on-archive` tool to check that locally re-executed transaction outputs match the `TransactionInfo` objects that were actually committed to the ledger accumulator. The function checks status, gas, write-set hash, and event-root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the exact fields that hold the Merkle roots of the main state tree, hot state tree, and (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) the native-position tree. This mirrors the Perennial M-7 pattern: two paths are meant to compute/validate the same committed value, but one path (verification) silently uses a weaker/partial check than the one that actually commits the value, so a divergence goes undetected.

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` explicitly documents the gap in its own comment: [1](#0-0) 

It only validates status, gas, write-set hash and event-root hash: [2](#0-1) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as consensus-committed, accumulator-hashed fields: [3](#0-2) 

This comparator is the *only* correctness check performed in two real verification code paths:
1. `ChunkExecutor::verify_execution`, used for state-sync's `--verify-execution` mode, re-executes a chunk and calls `ensure_match_transaction_info` per transaction without ever computing or comparing checkpoint hashes: [4](#0-3) 
2. `db-tool`'s standalone `replay_on_archive` verifier re-executes backed-up transactions and calls the same comparator, again with no checkpoint-hash validation: [5](#0-4) 

By contrast, the feature flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is explicitly designed so that the native-position state root is "consensus-verified" by riding in `TransactionInfoV1`: [6](#0-5) 

But that guarantee only holds inside the normal block/chunk commit pipeline (`DoStateCheckpoint`/`DoLedgerUpdate`, which do compute and compare `known_position_state_checkpoints`), not inside the two standalone verification tools above, which rely solely on `ensure_match_transaction_info`.

### Impact Explanation
This breaks the state-integrity/proof-verification invariant: "Wrong accumulator root, Merkle proof, transaction proof... accepted as valid" and "Hard-fork-only divergence during commit, replay, restore, or proof verification." Concretely:
- If a node's local state/hot-state/position Merkle tree diverges from the canonical, consensus-committed root (due to a bug in the JMT/state-store code, a backup/restore corruption, or a bit-flip in an archive), `--verify-execution` fast-sync verification and `db-tool replay-on-archive` will both report success as long as write-set bytes, gas, status, and events match — even though the actual authenticated state root committed on-chain differs from what local execution produces.
- Because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` intentionally moves the native-position root into the consensus-verified `TransactionInfoV1`, an operator (or automated CI/replay-verify pipeline) relying on these two tools to attest "my replayed chain state is byte-for-byte correct including this new state root" gets a false positive, allowing an operator to sync a full node with a silently corrupted position-state tree that will keep diverging on subsequent proof serving (`get_position_state_proof_by_version_ext`) without any tooling catching it.

### Likelihood Explanation
Low-to-moderate likelihood, matching Sherlock's original "very low but still possible" characterization of the analogous Perennial bug: it requires an underlying state-corruption bug or storage/backup defect to actually occur, at which point this comparator's gap prevents it from being detected via the standard verification tooling, rather than causing corruption itself. The bug is real and reachable in unprivileged tooling code (no privileged assumptions needed to trigger the missing check itself), but its downstream impact depends on a separate divergence occurring elsewhere.

### Recommendation
Extend `ensure_match_transaction_info` (or its callers) to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values whenever the relevant feature flags (`TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) are enabled, before shipping/enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on mainnet, as the code's own TODO already recommends.

### Proof of Concept
Not applicable as a runtime exploit PoC — this is a verification-logic gap, demonstrated by the code paths cited above: `ChunkExecutor::verify_execution` and `replay_on_archive::execute_and_verify` both call `ensure_match_transaction_info`, which structurally cannot fail on a checkpoint/state-root mismatch since it never reads those `TransactionInfo` fields.
