There's a documented, known, and still-existing bug in the nearcore codebase that is structurally identical to the qs `arrayLimit` bug: a receipt can be built such that a size check passes at creation time, but a subsequent mutation (adding `output_data_receivers`, or the value-return path) pushes it past `max_receipt_size` — and the enforcement gap is only patched for *new* receipts, not for receipts that grow after the check, exactly like `qs` checking indexed notation but not bracket notation.

### Title
Receipt-size limit bypass via post-validation growth (`output_data_receivers`/return-value) allows unbounded receipt size, contradicting `max_receipt_size` — ([File: runtime/runtime/src/verifier.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`validate_receipt` in `ValidateReceiptMode::NewReceipt` mode checks `max_receipt_size` once, at the moment a receipt is constructed [1](#0-0) . But the runtime subsequently mutates already-validated receipts — appending `output_data_receivers` when resolving a promise return, or filling in a returned value as a `Data` receipt — after this check has run [2](#0-1) . This is exactly the qs `arrayLimit` pattern: one code path (indexed notation / receipt-at-creation) enforces the size cap, while another path (bracket notation / receipt-after-mutation) can grow the same object past the cap without a re-check.

### Finding Description
`validate_receipt` only runs the `max_receipt_size` check under `ValidateReceiptMode::NewReceipt`, immediately after an action produces a receipt [3](#0-2) . This validated set of `new_receipts` is captured before the surrounding `apply_action_receipt` continues to step 10 ("Output data": `output_data_receivers` absorbed into the returned `ReceiptIndex` receipt, or `Data` receipts appended with the return value) [2](#0-1) . Because that later mutation happens after the size check already passed, the receipt's serialized (borsh) size can exceed `max_receipt_size` without any subsequent re-validation catching it. `ValidateReceiptMode::ExistingReceipt` explicitly documents that it must tolerate this: "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606" [4](#0-3) . This is functionally identical to the qs vulnerability class: `arrayLimit` was enforced on one construction path (indexed `a[0]=`) but not on another that mutates the same logical structure (bracket `a[]=`), letting the bound be silently exceeded.

### Impact Explanation
Oversized receipts must still be forwarded and stored (the code has an explicit workaround treating them as exactly `max_receipt_size` for congestion/bandwidth purposes so they don't get stuck) [5](#0-4) . This means a contract call can produce receipts larger than the protocol-intended `max_receipt_size` bound in a way that is repeatable and attacker-controlled (via `promise_return` or large return values), inflating storage-proof/bandwidth/witness accounting beyond the configured limit — a resource-exhaustion vector reachable from a single unprivileged contract call, matching the qs report's DoS-via-limit-bypass classification.

### Likelihood Explanation
This is not hypothetical — nearcore's own test suite (`test-loop-tests/src/tests/max_receipt_size.rs`) reproduces it today via `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`, both of which comment that oversized receipts are produced and only pass because of the size-limit bug, referencing the open tracking issue [6](#0-5) . Any account that deploys a contract and calls `promise_return`/returns a large value can trigger it.

### Recommendation
Re-run the `max_receipt_size` check in `validate_receipt` after any post-construction mutation of a receipt (specifically after `output_data_receivers` are attached and after `Data`/return-value receipts are built), not only at the initial `NewReceipt` validation point in `apply_action_receipt`. This closes the gap the same way qs's fix applies `arrayLimit` uniformly across both bracket and indexed notations, rather than checking only at one specific construction site.

### Proof of Concept
Following the existing repro in `test-loop-tests/src/tests/max_receipt_size.rs`: deploy a contract, then call a method that (a) creates a promise chain where an intermediate receipt is validated at exactly `max_receipt_size`, then `promise_return` causes `output_data_receivers` to be appended, pushing it over the limit (`test_max_receipt_size_promise_return`), or (b) returns a value whose size makes the resulting `Data` receipt exceed `max_receipt_size` (`test_max_receipt_size_value_return`) [7](#0-6) . Both tests assert (`assert_oversized_receipt_occurred`) that a receipt above `max_receipt_size` does in fact occur on-chain, confirming the bypass is live in this codebase.

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
