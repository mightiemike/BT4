### Title
Legacy non-strict `Math.pow` path in `ExchangeProcessor.exchange()` causes platform-dependent floating-point divergence and consensus fork - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
When the chain parameters `ALLOW_STRICT_MATH` and `ALLOW_HARDEN_EXCHANGE_CALCULATION` are both disabled (the legacy/default state until activated by proposal), `ExchangeProcessor.exchange()` computes `Math.pow`-based bancor pricing via `Maths.pow(a, b, false)`, which resolves to platform-specific `MathWrapper.pow()`. The x86 build calls raw `Math.pow`, while the ARM build calls `StrictMath.pow` patched with a hardcoded historical correction table, meaning any input triple not already recorded in that table can legitimately yield different `long` results on different node platforms for the exact same transaction, causing state divergence.

### Finding Description
`ExchangeProcessor.exchangeToSupply()` and `exchangeFromSupply()` both call `Maths.pow(base, exponent, this.useStrictMath)`: [1](#0-0) 

`Maths.pow` dispatches to either `StrictMathWrapper.pow` (guaranteed `StrictMath.pow`, bit-identical across all conforming JVMs) or `MathWrapper.pow` when `useStrictMath` is `false`: [2](#0-1) 

The platform module supplies two different implementations of `MathWrapper.pow`. On x86 it calls raw `Math.pow(a, b)`, which is explicitly *not* required by the JLS to be bit-identical across platforms/JIT implementations: [3](#0-2) 

On ARM it calls `StrictMath.pow` and then overrides the result with a hardcoded lookup table (`powData`) built from historically observed mainnet block divergences — direct evidence that this exact `Math.pow`/`StrictMath.pow` divergence has previously caused real cross-platform result mismatches on java-tron mainnet: [4](#0-3) [5](#0-4) 

The `useStrictMath`/`hardenedCalc` flags are read directly from `dynamicStore.allowStrictMath()` and `allowHarden()` at the actuator call site, so whichever value is currently active on-chain governs every node's computation path identically — but as long as `ALLOW_STRICT_MATH` has not been activated (it can only be turned on once via a one-way committee proposal per `ProposalUtil`), the legacy `Math.pow` path remains reachable for every plain user transaction: [6](#0-5) [7](#0-6) 

An unprivileged attacker only needs to submit a standard `ExchangeTransactionContract` (or `ExchangeInjectContract`/`ExchangeWithdrawContract`, which share the same `ExchangeCapsule.transaction`/`ExchangeProcessor.exchange` code path) choosing `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` such that the intermediate `base = 1.0 + quant/newBalance` lands on an input not present in the ARM correction table. `ExchangeTransactionActuator.validate()`/`execute()` perform no bounds/rounding check beyond balance-limit and expected-amount checks — none of which detect or prevent floating-point non-determinism: [8](#0-7) 

The test file `ExchangeProcessorTest.testStrictMath` explicitly demonstrates that the non-strict (`useStrictMath=false`) result differs from the strict (`useStrictMath=true`/`SafeExchangeProcessor`) result for numerous realistic inputs, confirming the double-precision divergence is measurable and reproducible within this exact codebase, not merely theoretical: [9](#0-8) 

### Impact Explanation
If two honest full nodes execute the identical broadcast transaction with different `Math.pow` implementations (different CPU architecture, JVM vendor/version, or JIT intrinsic behavior) while `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION` are inactive, `ExchangeProcessor.exchange()` can return different `long anotherTokenQuant` values. This value is written directly into account/asset balances and the `Exchange` capsule balances (`Commons.putExchangeCapsule`), producing divergent post-state (different account balances, different `stateRoot`) between nodes — a deterministic-execution violation that can fork the chain or halt block confirmation once SRs disagree on block validity.

### Likelihood Explanation
This is not a hypothetical concern: the ARM `MathWrapper`'s hardcoded `powData` table with associated real mainnet block numbers is direct proof that this exact class of divergence has already manifested in production and had to be patched retroactively for specific known inputs. Any new input triple that hits a similarly divergent floating-point rounding boundary and is *not* in the fixed historical table remains fully exploitable today whenever the network is still on the legacy path (`ALLOW_STRICT_MATH`/hardened-calc not yet activated). No privilege is required — any account with sufficient token/TRX balance and an existing exchange pair can submit the triggering transaction. The main precondition is that the network's `ALLOW_STRICT_MATH` (and hardened-calc) proposal has not yet been passed, which is the deterministic on-chain default state the question specifies.

### Recommendation
- Retire the legacy `MathWrapper`/`Math.pow` code path from `ExchangeProcessor` entirely (not just gate it behind a flag), since it is fundamentally reachable by any user until governance activates the strict-math parameter.
- Prefer immediate migration to `SafeExchangeProcessor`'s `BigDecimal`-based fixed-point computation (already implemented) as the sole exchange pricing engine, eliminating double/`Math.pow` non-determinism altogether rather than relying on ad hoc post-hoc correction tables.
- If `ALLOW_STRICT_MATH` has not yet been activated on the target network, treat this as urgent: propose and pass `ALLOW_STRICT_MATH` and `ALLOW_HARDEN_EXCHANGE_CALCULATION` to force `StrictMathWrapper`/`SafeExchangeProcessor` usage network-wide, closing the exposure window.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
