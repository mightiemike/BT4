## Title
Panic on empty-calldata L1 handler message hashing causes denial of service - (File: crates/starknet_api/src/hash.rs)

### Summary
`l1_handler_message_hash` in `crates/starknet_api/src/hash.rs` computes the L1↔L2 message hash for an `L1HandlerTransaction` by unconditionally taking the first calldata element as the `from_address`: [1](#0-0) 

```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
```

`Calldata` has no non-empty invariant, and `L1HandlerTransaction` derives `Deserialize`, so a transaction with empty calldata is constructible without failing deserialization. Calling `calc_msg_hash()` on such a transaction triggers `Option::expect` on `None`, panicking the process.

### Finding Description
`L1HandlerTransaction::calc_msg_hash` directly forwards to `l1_handler_message_hash`: [2](#0-1) 

The codebase already recognizes that `Calldata` for `L1HandlerTransaction` can legitimately be empty — a sibling function `payload_size()` was explicitly hardened against this exact case with a code comment describing the same underlying issue: [3](#0-2) 
and a regression test exists for that fix: [4](#0-3) 

However, `l1_handler_message_hash` was not given the same treatment: it still `.expect()`s a non-empty calldata vector, so it panics instead of returning a `Result` or gracefully handling the empty case. This is directly analogous to the CVE's dissector crash: a malformed/adversarial input field (here, a missing "from_address" element in a deserializable `L1HandlerTransaction`) is not validated before it reaches a routine that assumes a minimum length, causing an unhandled panic (denial of service) rather than a clean error.

`L1HandlerTransaction` is deserializable and flows through the sequencer as `starknet_api::executable_transaction::L1HandlerTransaction` (constructed via `L1HandlerTransaction::create`, which computes `tx_hash` but does not validate calldata is non-empty): [5](#0-4) 

The stateless gateway validator (`crates/apollo_gateway/src/stateless_transaction_validator.rs`) validates size/format for `RpcTransaction` variants (Invoke/Declare/DeployAccount) but has no dedicated `RpcTransaction::L1Handler` variant to validate (L1 handler transactions do not arrive through the RPC gateway path at all — they are constructed internally from L1 events). I could not fully trace, within the tool budget, every single code path that constructs an `L1HandlerTransaction` from an L1 event and calls `calc_msg_hash`, so it is uncertain whether the L1 event ingestion pipeline (`apollo_l1_provider` / L1 scraper) itself guarantees a non-empty calldata before this point, or whether it is possible for an internally/externally malformed L1 event (e.g. a `from_address`-less payload from a malicious/buggy L1 contract call, or a manually crafted `L1HandlerTransaction` used in OS re-execution / RPC-execution tooling like `apollo_rpc_execution`, `blockifier_reexecution`, or `starknet_os_flow_tests`) can carry zero-length calldata all the way to `calc_msg_hash()`.

### Impact Explanation
If reached, this is an unrecoverable `panic!` (via `.expect()`), crashing the calling process. Depending on which component invokes `calc_msg_hash` (mempool/L1 provider ingestion, OS re-execution, block building, or RPC execution), this could crash sequencer components processing L1 messages, causing denial of service and potentially halting block production for L1 handler transactions — matching the "network unable to confirm new transactions" impact class.

### Likelihood Explanation
Medium confidence/likelihood: the vulnerable code pattern (`.expect()` on `split_first()` for calldata that is known — per the codebase's own comments/tests elsewhere — to be constructible as empty) is real and unguarded. However, I was not able to fully confirm within the available searches that an attacker-controlled or externally-triggerable path (as opposed to only internally-trusted flows) can supply an `L1HandlerTransaction` with empty calldata to `calc_msg_hash` before any other validation rejects it. This uncertainty should be resolved by tracing all callers of `calc_msg_hash`/`l1_handler_message_hash` across `apollo_l1_provider`, `apollo_l1_gas_price`, and OS re-execution code.

### Recommendation
Change `l1_handler_message_hash` to return a `Result` (or use a safe fallback) instead of `.expect()`-panicking on empty calldata, mirroring the fix already applied to `L1HandlerTransaction::payload_size`. Additionally, validate that `calldata` is non-empty (contains at least the `from_address` field) at the earliest possible point when an `L1HandlerTransaction` is constructed (e.g., in `L1HandlerTransaction::create`), so malformed/empty-calldata L1 handler transactions are rejected with a typed error rather than reaching hash computation.

### Proof of Concept
```rust
use starknet_api::core::{ContractAddress, Nonce};
use starknet_api::core::EntryPointSelector;
use starknet_api::hash::l1_handler_message_hash;
use starknet_api::transaction::fields::Calldata;
use std::sync::Arc;

// Empty calldata is a valid, deserializable value for `Calldata` — no non-empty invariant enforced.
let empty_calldata = Calldata(Arc::new(vec![]));

// Panics with: "Invalid calldata, expected at least from_address"
let _ = l1_handler_message_hash(
    &ContractAddress::default(),
    Nonce::default(),
    &EntryPointSelector::default(),
    &empty_calldata,
);
```
This reproduces the panic directly against `l1_handler_message_hash` (referenced at [1](#0-0) ), showing that any code path constructing an `L1HandlerTransaction` with empty calldata and subsequently calling `.calc_msg_hash()` will crash the process.

```rust
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());
```
