### Title
Missing post-trade liquidity/reserve validation in TRC10 Bancor-style Exchange lets a trade drive a reserve to zero or negative, bricking the pool - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
The TRC10 `Exchange` (Bancor-relay AMM) contract family — `ExchangeCreateActuator`, `ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator` — is java-tron's on-chain analog of the audited `UniV2TWAMMPair` liquidity pool. Just like the TWAMM report, the code checks that a pool's *current* reserves are non-zero before starting a trade, but by default it never checks that the *post-trade* reserves stay above zero, so a single trade against thin/legacy liquidity can zero-out or corrupt a reserve, bricking the exchange for everyone until it is manually re-injected.

### Finding Description
`ExchangeTransactionActuator.doValidate()` only guards the pre-trade state: [1](#0-0) 

It never re-checks the reserves the Bancor formula computes for *after* the trade. The actual balance mutation happens in `ExchangeCapsule.transaction()`: [2](#0-1) 

The `hardenedCalc` flag (gated by the `allowHarden()`/`AllowHardenExchangeCalculation` chain parameter, off by default — enabled only via an explicit `saveAllowHardenExchangeCalculation(1)` call as seen in the test suite) is the *only* path that verifies `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` before persisting state: [3](#0-2) 

When `hardenedCalc` is false (the default, non-hardened `ExchangeProcessor` path), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `long` arithmetic and stored unconditionally, with no floor check: [4](#0-3) 

This is the direct analog of the TWAMM bug: the audited `performLongTermSwap` only validated the *selling* side (`sellingRate > 0`) and never the reserves being *bought*, so a trade against inadequate liquidity produced a division-by-zero in `computeVirtualBalances` and permanently bricked pool operations. Here, `doValidate()` only validates that the pool is not *already* closed (`firstTokenBalance == 0 || secondTokenBalance == 0`), never that the trade won't drive a balance to zero/negative. The Bancor relay math in `ExchangeProcessor.exchangeFromSupply()` — `balance * (pow(1 + supplyQuant/supply, 2000.0) - 1.0)` — can, for pools with very small reserves (e.g. any exchange created via `ExchangeCreateActuator` with `firstTokenBalance`/`secondTokenBalance` as low as `1`, which is a legal value since `doValidate()` only requires `> 0`), return a `buyTokenQuant` that consumes the entire opposite-side reserve or overshoots it due to floating-point (`double`) rounding in the non-hardened processor: [5](#0-4) 

Once a reserve reaches exactly `0`, `doValidate()`'s check at line 194 permanently blocks every future `ExchangeTransactionContract`, `ExchangeInjectContract` (same `firstTokenBalance == 0 || secondTokenBalance == 0` guard exists in `ExchangeInjectActuator.doValidate()`), and `ExchangeWithdrawActuator.doValidate()` on that pool — mirroring the TWAMM report's "all pool operations will revert until … tokens … are added" outcome. If the non-hardened path drives a balance *negative* (possible because there is no clamp in the non-hardened branch, only in `hardenedCalc`), the corrupted negative balance is persisted to `ExchangeStore`/`ExchangeV2Store` via `Commons.putExchangeCapsule`, producing an invalid on-chain state that further arithmetic (BigInteger/BigDecimal divisions in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) will operate on inconsistently.

### Impact Explanation
This is a concrete invalid-state/halt impact on a live, unprivileged-user-reachable market feature (TRC10 Exchange), not a theoretical or trusted-role-only issue:
- Any account can create an `Exchange` pool with the statutory minimum non-zero balances (e.g., `firstTokenBalance = 1`) via `ExchangeCreateActuator`, since the only floor check is `> 0`. [6](#0-5) 
- Any unprivileged user can then submit an `ExchangeTransactionContract` against that thin pool; because the non-hardened processor performs no post-trade solvency check, the trade can zero out (or, absent overflow guards on that path, corrupt) a reserve.
- Once zeroed, `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all reject further calls on that exchange ID, permanently freezing any tokens still recorded in it and denying service to all other users of that specific pool — an availability/DoS and accounting-integrity impact consistent with "invalid-state/halt" in an unprivileged, publicly reachable actuator path.

### Likelihood Explanation
Likelihood is high for newly created or thinly-funded pools: `ExchangeCreateActuator` permits creation with arbitrarily small (as low as `1`) initial balances, and `AllowHardenExchangeCalculation` (the only mitigation that adds a reserve floor check) defaults to disabled and must be turned on by a chain-parameter proposal — matching the TWAMM report's finding that the safety mechanism exists but "is enabled by default" in the wrong direction (there, the pause is off by default; here, the safety math is off by default). Any user can grief a newly created exchange before liquidity is deepened, exactly as described in the report's exploit scenario.

### Recommendation
- Make the reserve floor check (currently only inside the `hardenedCalc`/`SafeExchangeProcessor` branch) unconditional in `ExchangeCapsule.transaction()`, rejecting any trade whose result would bring `newFirstTokenBalance` or `newSecondTokenBalance` to `<= 0` regardless of the `AllowHardenExchangeCalculation` flag.
- Consider raising `ExchangeCreateActuator`'s minimum initial balance requirement above a trivial `1` to reduce griefing surface on freshly created pools.
- Enable `AllowHardenExchangeCalculation` (or equivalent) by default rather than requiring an explicit governance proposal, consistent with the audit's recommendation to close default-unsafe states.

### Proof of Concept
1. Attacker creates an `Exchange` via `ExchangeCreateActuator` with `firstTokenBalance = 1`, `secondTokenBalance = <small amount>` (both `> 0`, satisfying `doValidate()`'s only floor check at `actuator/.../ExchangeCreateActuator.java:201-203`).
2. Attacker (or any user) submits `ExchangeTransactionContract` selling a modest amount of the second token; `ExchangeCapsule.transaction()` (non-hardened, default) computes `buyTokenQuant` via the Bancor relay math in `ExchangeProcessor`, which can equal or exceed `firstTokenBalance`, driving `newFirstTokenBalance` to `0` (or negative, since the non-hardened branch never checks).
3. `Commons.putExchangeCapsule` persists the corrupted state.
4. Any subsequent `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` referencing this exchange ID now fails validation at the `firstTokenBalance == 0 || secondTokenBalance == 0` guard in each actuator's `doValidate()`, permanently freezing the pool.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
