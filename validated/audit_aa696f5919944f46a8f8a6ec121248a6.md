### Title
Precompile signature-verification fee/cost is computed and permanently cached from the pre-ALT `SanitizedTransactionView`, allowing a precompile invoked via an ALT-resolved program id to execute (and be metered by the SVM) without ever being counted in `TransactionSignatureDetails` - (File: runtime-transaction/src/runtime_transaction/transaction_view.rs, runtime-transaction/src/instruction_meta.rs, runtime-transaction/src/signature_details.rs)

### Summary
`RuntimeTransaction<SanitizedTransactionView<D>>::try_new` computes `InstructionMeta`/`TransactionSignatureDetails` by iterating `transaction.program_instructions_iter()` on the **statically-loaded, pre-ALT-resolution** view, before address-table lookups have been resolved. That cached `meta.signature_details` is then carried unchanged into `RuntimeTransaction<ResolvedTransactionView<D>>` after ALT resolution and is never recomputed, while execution (`InvokeContext::process_message`) evaluates `is_precompile`/`process_precompile` against the fully resolved, post-ALT program id. A precompile referenced only via an ALT-resolved index is therefore invisible to fee/signature accounting but still fully executes its (expensive) signature-verification work.

### Finding Description
The static-metadata path is:
- `from_sanitized_transaction_view` builds `InstructionMeta::try_new(transaction.program_instructions_iter())` on the `SanitizedTransactionView<D>` [1](#0-0) 
- `InstructionMeta::try_new` feeds every instruction's `(program_id, instruction)` pair into `PrecompileSignatureDetailsBuilder::process_instruction`, which only recognizes secp256k1/ed25519/secp256r1 by comparing the `program_id` value it is handed for that instruction against the hard-coded precompile ids [2](#0-1) [3](#0-2) 
- At this point in the pipeline, ALT addresses have not yet been loaded: `translate_to_runtime_view` first builds `RuntimeTransaction::<SanitizedTransactionView<_>>::try_new` (which triggers the signature-details computation above) and only afterwards calls `load_addresses_for_view`/`RuntimeTransaction::<ResolvedTransactionView<_>>::try_new` [4](#0-3) 
- When wrapping into `ResolvedTransactionView`, the cached `meta` (containing `signature_details`) is passed through unchanged and never recalculated against the resolved program ids: `let RuntimeTransaction { transaction, meta } = statically_loaded_runtime_tx; ... let tx = Self { transaction, meta };` [5](#0-4) 
- `RuntimeTransaction<T>`'s `SVMStaticMessage` implementation subsequently always reports `num_secp256k1_signatures`/`num_ed25519_signatures`/`num_secp256r1_signatures` from that frozen `meta.signature_details`, not from a live re-scan of the resolved account keys [6](#0-5) 
- Execution, however, operates on the fully resolved `SVMMessage` and determines precompile-ness (and therefore performs the actual, expensive `process_precompile` signature verification) using the post-ALT-resolution program id at that instruction index [7](#0-6) 

Because an attacker can create their own Address Lookup Table (ALT `extend` accepts arbitrary pubkeys, including well-known program ids such as `secp256k1_program::ID`, `ed25519_program::ID`, or `secp256r1_program::ID`, with no ownership check on the referenced address) and then compile a v0 message whose top-level instruction's `program_id_index` points at that ALT-resolved slot rather than a static account key, the instruction is fully invisible to the precompile-signature-counting pass that runs on the un-resolved view, while it is fully recognized and executed as a precompile at runtime.

### Impact Explanation
This is a signature-verification fee/metering undercharge: an attacker can get the validator to perform arbitrarily many (up to the packed-instruction/CU limits) expensive secp256k1/ed25519/secp256r1 signature verifications while paying for zero of the associated `lamports_per_signature` fee and while the cost-model's `total_signatures()`-derived cost component (used for block-limit accounting, e.g. `cost-model/src/transaction_cost.rs` and `core/src/forwarding_stage.rs`'s `calculate_priority`) also undercounts the transaction's true cost. This falls under "value conservation / metering totality" - a metering/fee-bypass bug enabling cheap spam of expensive precompile verification work, matching the "resource exhaustion via fee evasion" bounty category rather than direct fund theft.

### Likelihood Explanation
Preconditions are all attacker-controllable with only a funded keypair and no special privileges: create/extend an ALT with a precompile program id as one of its addresses, then submit a v0 transaction whose instruction addresses that program via the lookup index. The attack is fully repeatable and cheap (ALT creation/extension is a one-time, low-cost setup that can be reused across many subsequent transactions).

### Recommendation
Compute (or re-verify) `TransactionSignatureDetails`/precompile-signature counts against the fully **resolved** account-key list (post-ALT) rather than caching results computed from the pre-resolution `SanitizedTransactionView`. Concretely, `RuntimeTransaction<ResolvedTransactionView<D>>::try_new` should recompute `InstructionMeta`/`signature_details` from `transaction.program_instructions_iter()` on the resolved view (or the precompile-detection logic should explicitly reject/flag instructions whose `program_id_index` resolves to a lookup-table address matching a precompile id) before caching `meta`.

### Proof of Concept
Integration test plan (bank/SVM level):
1. Fund a keypair; create and extend an `AddressLookupTable` whose sole address is `solana_sdk_ids::secp256k1_program::ID`.
2. Build a v0 `VersionedTransaction` with one instruction whose `program_id_index` resolves via the ALT to the secp256k1 program id, with instruction data encoding, e.g., `num_signatures = 4` (packed secp256k1 verify data), and compile with `v0::Message::try_compile` using the ALT.
3. Run this transaction through `translate_to_runtime_view` (or the equivalent `RuntimeTransaction::<SanitizedTransactionView>::try_new` → ALT resolution → `RuntimeTransaction::<ResolvedTransactionView>::try_new` pipeline) and assert `tx.meta.signature_details.num_secp256k1_instruction_signatures() == 0`.
4. Build a control transaction that references the same secp256k1 instruction via a **static** account key (no ALT) and assert `num_secp256k1_instruction_signatures() == 4`.
5. Execute both transactions through the bank/SVM and assert that in both cases `process_precompile` actually runs and performs verification work (e.g., via `execute_timings`/compute-unit accounting or by observing `InstructionError` outcomes for malformed vs. well-formed offsets), showing identical execution work but divergent (0 vs 4) signature-fee accounting - demonstrating the fee/metering discrepancy.

impl InstructionMeta {
    pub fn try_new<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
    ) -> Result<Self, TransactionError> {
        let mut precompile_signature_details_builder = PrecompileSignatureDetailsBuilder::default();
        let mut instruction_data_len_builder = InstructionDataLenBuilder::default();
        for (program_id, instruction) in instructions {
            precompile_signature_details_builder.process_instruction(program_id, &instruction);
            instruction_data_len_builder.process_instruction(program_id, &instruction);
        }

        Ok(Self {
            precompile_signature_details: precompile_signature_details_builder.build(),
            instruction_data_len: instruction_data_len_builder.build(),
        })
    }

pub(crate) fn translate_to_runtime_view<D: TransactionData>(
    data: D,
    bank: &Bank,
    transaction_account_lock_limit: usize,
    sanitize_config: &SanitizeConfig,
) -> Result<(RuntimeTransaction<ResolvedTransactionView<D>>, u64), PacketHandlingError> {
    // Parsing and basic sanitization checks
    let Ok(view) = SanitizedTransactionView::try_new_sanitized(data, sanitize_config) else {
        return Err(PacketHandlingError::Sanitization);
    };

    let Ok(view) = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Discard non-vote packets if in vote-only mode.
    if bank.vote_only_bank() && !view.is_simple_vote_transaction() {
        return Err(PacketHandlingError::Sanitization);
    }

    if usize::from(view.total_num_accounts()) > transaction_account_lock_limit {
        return Err(PacketHandlingError::LockValidation);
    }

    let (loaded_addresses, deactivation_slot) = load_addresses_for_view(&view, bank)?;

    let Ok(view) = RuntimeTransaction::<ResolvedTransactionView<_>>::try_new(
        view,
        loaded_addresses,
        bank.get_reserved_account_keys(),
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Validate no duplicate accounts (must be after resolution to catch ALT duplicates)
    if validate_account_locks(view.account_keys(), transaction_account_lock_limit).is_err() {
        return Err(PacketHandlingError::LockValidation);
    }

    Ok((view, deactivation_slot))
}
