## Title
Burn-Distribution Smoothing Window Silently Collapses to Single-Block After Every Post-3.0 Epoch Boundary, Letting a Minority Miner Win Sortition Outside the Documented Burn-Weight Function - (File: `stackslib/src/burnchains/burnchain.rs`)

### Summary
The burn-distribution windowing logic that assembles the miner-commitment history used to compute each sortition's effective burn silently degrades to a 1-block window for up to `mining_commitment_window()` (6) blocks after *every* Stacks epoch transition from Epoch 3.0 onward — not just major upgrades. During that window, the intended `min(median_burn, most_recent_burn)` smoothing formula is bypassed entirely, so a miner who has built no commitment history can win a disproportionate share of a sortition with a single burst commit, reducing the effective share (and thus rewards) of miners who were mining consistently, exactly analogous to the reported pattern of an attacker exploiting an unguarded reward-weighting rule to dilute other participants' share without the intended cost/penalty.

### Finding Description
`process_block_ops`/burn-distribution assembly in `stackslib/src/burnchains/burnchain.rs` decides whether to build the full 6-block commitment window or fall back to a single-block window: [1](#0-0) 

Specifically:
```rust

let window_start_epoch_id = SortitionDB::get_stacks_epoch(
    sort_tx,
    parent_snapshot.block_height.saturating_sub(epoch_id.mining_commitment_window().into()),
)?...epoch_id;
...
if !burnchain.is_in_prepare_phase(...)
    && !burnchain.pox_constants.is_after_pox_sunset_end(...)
    && (epoch_id < StacksEpochId::Epoch30 || window_start_epoch_id == epoch_id)
{
    // build full mining_commitment_window() worth of history
} else {
    // "PoX reward-phase is not active, or we're starting a new epoch" -> 1-block window only
}
```
`mining_commitment_window()` returns the constant `MINING_COMMITMENT_WINDOW = 6` for every epoch: [2](#0-1) 

Because the window size never changes across epochs, the guard `window_start_epoch_id == epoch_id` is false for the first ~6 blocks after *any* Epoch ≥ 3.0 boundary (Epoch30→31→32→33→34→40→41), since the block 6 heights back still belongs to the prior epoch. In that state, the code takes the `else` branch and asserts a 1-block window: [3](#0-2) 

This 1-block window is fed straight into `BurnSamplePoint::make_min_median_distribution`, whose entire purpose is to compute `burns := min(median_burn, most_recent_burn)` over the window so that a miner's *effective* burn reflects sustained commitment, not a single spike: [4](#0-3) 

With a window of length 1, `median_burn == most_recent_burn == last_burn`, so smoothing is a no-op: the entire sortition-weighting scheme collapses to raw last-block burn for every miner in that block. Any miner that has not been building up multi-block commit history — including one who has just started committing, or one who deliberately withholds committing until this window opens — gets full credit for a single large one-off burn, exactly the credit a sustained miner would normally only get after passing several blocks of the smoothing window. This directly changes the range each candidate occupies in `make_sortition_ranges` (`stackslib/src/chainstate/burn/distribution.rs:381-427`), and hence who wins `select_winning_block`/`sample_burn_distribution` in `stackslib/src/chainstate/burn/sortition.rs:122-149,192-220`.

The purpose-built regression test `stacks-node/src/tests/signer/v0/epoch_4_0_multi_miner_distribution.rs` explicitly documents that "a windowing bug at the boundary surfaces as a failure mode the test can catch" and asserts the smoothed burns match configured per-miner fees across the Epoch 4.0 boundary — confirming this is a known-sensitive area of the code: [5](#0-4) 

### Impact Explanation
This breaks the equality the burn-weight function is supposed to guarantee: *effective burn = min(median, last) over the commitment window*, for every sortition landing within `mining_commitment_window()` blocks of a post-3.0 epoch boundary. A minority miner (no majority hash power required) can time a single, larger-than-usual commit to land in this window and win sortition/claim a bigger burn-weighted share than the smoothing rule would otherwise allow, at the direct expense of miners who were consistently committing and whose share of that sortition is diluted relative to the documented formula. This is a minority-triggerable sortition/burn-weight divergence — a High-severity class per the accepted-analog criteria (reward mis-payment/temporary tip disagreement bounded to that sortition round). It does not require majority hash power, a node operator, or another party's key — only correctly-timed commit transactions around a known, deterministic epoch-boundary height.

### Likelihood Explanation
Epoch boundary heights are public, deterministic chain parameters known to all miners in advance (`StacksEpoch.start_height`). Any miner can compute exactly which burn-block heights fall within the `mining_commitment_window()`-block post-boundary zone and simply schedule an outsized one-off commit there — no privileged access, no majority stake, and no mempool front-running sophistication beyond normal commit-transaction timing is required. The condition triggers on *every* epoch bump from 3.0 onward (Epoch30/31/32/33/34/40/41), not only major releases, so the exploitable window recurs with each protocol upgrade.

### Recommendation
Do not let the smoothing window collapse merely because the epoch id changed within the lookback range. Instead, only shrink the window when `mining_commitment_window()` itself differs between the current epoch and the epoch at the window start (i.e., compare window *sizes*, not raw epoch identifiers), or clamp/carry over commit history across epoch boundaries when the window size is unchanged, so the `min(median, last)` invariant continues to hold across epoch transitions instead of silently degrading to a 1-block, unsmoothed window.

### Proof of Concept
1. Let `H` be the first burn-block height of any Epoch ≥ 3.0 transition (e.g., Epoch30→Epoch31, or Epoch40→Epoch41).
2. For blocks `H` through `H+5` (6 = `MINING_COMMITMENT_WINDOW`), `window_start_epoch_id` (computed at `block_height - 6`) still resolves to the *previous* epoch while `epoch_id` resolves to the *new* epoch, so `window_start_epoch_id == epoch_id` is false and the `else` branch in `stackslib/src/burnchains/burnchain.rs:238-304` is taken, forcing a 1-block window.
3. A miner who has not committed in the preceding window submits a single block-commit at height `H+k` (`0 <= k <= 5`) with a much larger burn than their historical average.
4. `BurnSamplePoint::make_min_median_distribution` is called with `mining_commitment_window = 1` worth of commits, so `median_burn == most_recent_burn` for every candidate — the miner's full one-off burn is credited with no smoothing penalty, unlike blocks outside this boundary window where the same one-off burn would be capped by the historical median.
5. This shifts `range_start`/`range_end` in `make_sortition_ranges` in the miner's favor for that sortition, diverging from the burn-weight function that governs sortition everywhere else in the chain's lifetime, at the expense of other committing miners' effective share of that sortition's reward.
