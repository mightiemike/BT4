### Title
Committee proposal approval uses truncating integer division for the 70% supermajority threshold, allowing proposals to pass below the intended threshold - (File: `chainbase/src/main/java/org/tron/core/capsule/ProposalCapsule.java`)

### Summary
`ProposalCapsule.hasMostApprovals()` computes the required approval count for a committee/witness proposal using `activeWitnesses.size() * 7 / 10`, which truncates (floors) instead of rounding up to the nearest whole approval. This is the same class of bug as the reported `div_ceil(2)` issue: a threshold that should represent "more than X%" is instead computed with a rounding operation that can under-count the required votes, letting fewer-than-intended approvers finalize a governance decision.

### Finding Description
The intended semantics of `hasMostApprovals` is that a proposal needs at least 70% of active witnesses (super representatives) to approve it before its dynamic parameters take effect: [1](#0-0) 

```
public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    ...
    return count >= activeWitnesses.size() * 7 / 10;
}
```

`activeWitnesses.size() * 7 / 10` is integer arithmetic performed left-to-right: `size * 7` first, then divided by `10` with truncation toward zero (equivalent to `Math.floor` for non-negative values). For `MAX_ACTIVE_WITNESS_NUM = 27` (the fixed production witness count): [2](#0-1) 

`27 * 7 / 10 = 189 / 10 = 18` (integer division truncates `18.9` down to `18`).

True 70% of 27 is `18.9`, so a genuine supermajority requires **19** approvals (ceiling). The code instead accepts **18**, which is only `66.7%` of the active witness set — below the intended 70% threshold. This is analytically identical to the reported bug: a percentage/majority threshold computed via a rounding operation that favors the minority side (floor) instead of the side that guarantees the stated majority (ceiling).

This threshold gates `ProposalController.processProposal`, which calls `hasMostApprovals` and, if true, applies the proposal's parameter changes via `setDynamicParameters`/`ProposalService.process`: [3](#0-2) 

### Impact Explanation
Proposals control critical, chain-wide dynamic parameters (e.g., account creation fee, transaction fee, energy price, resource ratios, and other economic/consensus parameters processed by `ProposalService`). Because the required approval count is silently one vote lower than the documented/intended 70% supermajority whenever `activeWitnesses.size() * 7` is not an exact multiple of 10 (true for the standard 27-witness set), a proposal can be approved and applied to the network with only 18/27 (66.7%) witness approvals instead of the required 19/27 (70.4%). This weakens the governance security margin for changes that affect fee structure, resource accounting, and overall protocol economics — a systemic under-enforcement of the supermajority requirement across the network, not dependent on any single malicious or compromised witness.

### Likelihood Explanation
The condition is deterministic and always present for the standard active-witness count of 27 (`MAX_ACTIVE_WITNESS_NUM`), so it triggers on every proposal vote tally in production, not just an edge case — any proposal reaching exactly 18 approvals out of 27 will be incorrectly treated as having met the 70% threshold. No attacker action or privileged compromise is needed beyond the normal, expected use of the on-chain proposal-approval mechanism (`ProposalApproveContract`) by witnesses, which is a standard, reachable protocol flow.

### Recommendation
Replace the truncating integer computation with a ceiling-based (or otherwise correctly rounded) threshold calculation, e.g.:
```java
long threshold = (activeWitnesses.size() * 7 + 9) / 10; // ceiling of 70%
return count >= threshold;
```
or use a shared helper (analogous to the `strict_majority(n)` fix in the referenced report) that explicitly documents and enforces "at least X% rounded up" semantics, and add regression tests covering witness counts where `size * 7` is not evenly divisible by 10 (e.g., 27, as used in production).

### Proof of Concept
1. Set `activeWitnesses` to the standard production list of 27 SR addresses (`MAX_ACTIVE_WITNESS_NUM`).
2. Submit exactly 18 valid `ApproveProposal` approvals for a pending proposal from 18 distinct active witnesses.
3. Call `ProposalController.processProposal(proposalCapsule)` (invoked automatically at maintenance time via `processProposals`).
4. Observe `ProposalCapsule.hasMostApprovals` returns `true` because `18 >= 27 * 7 / 10 (=18)`, and the proposal transitions to `State.APPROVED`, applying its parameter changes—despite only 66.7% of witnesses approving, short of the intended 70% supermajority (19/27).

  public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    if (count != this.proposal.getApprovalsCount()) {
      List<ByteString> InvalidApprovalList = this.proposal.getApprovalsList().stream()
          .filter(witness -> !activeWitnesses.contains(witness)).collect(Collectors.toList());
      logger.info("InvalidApprovalList:" + getAddressStringList(InvalidApprovalList));
    }
    if (activeWitnesses.size() != MAX_ACTIVE_WITNESS_NUM) {
      logger.info("activeWitnesses size = {}", activeWitnesses.size());
    }
    return count >= activeWitnesses.size() * 7 / 10;
  }

    List<ByteString> activeWitnesses = this.manager.getWitnessScheduleStore().getActiveWitnesses();
    if (proposalCapsule.hasMostApprovals(activeWitnesses)) {
      logger.info(
          "Processing proposal,id:{},it has received most approvals, "

          proposalCapsule.getID(), proposalCapsule.getParameters());
      setDynamicParameters(proposalCapsule);
      proposalCapsule.setState(State.APPROVED);
      manager.getProposalStore().put(proposalCapsule.createDbKey(), proposalCapsule);

      logger.info(
          "Processing proposal,id:{}, "
              + "it has not received enough approvals, set proposal state as DISAPPROVED",
