### Title
Denial of Service for pending client-side proofs when `allowed_virtual_os_program_hashes` is bumped by a protocol upgrade - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
The sequencer accepts Invoke V3 transactions that carry client-side generated "virtual OS" proofs (`proof_facts` + `proof`), used by privacy-pool style contracts (e.g. the mainnet `apply_actions`/`validate_proof` flow) to attest to an off-chain computation. Acceptance of such a proof is gated on a single, protocol-version-controlled allow-list, `allowed_virtual_os_program_hashes`, which is *replaced* (not extended) on every versioned-constants bump. Any already-generated, not-yet-submitted proof that references the previous program hash becomes permanently rejected the moment the next protocol version activates, exactly mirroring the reported Avail `vectorx` DOS pattern where changing a single trusted reference value orphans previously valid, already-committed proofs.

### Finding Description
`TransactionPreValidationError::InvalidProofFacts` — `validate_proof_facts` in `AccountTransaction` checks the `program_hash` embedded in a transaction's `proof_facts` against `block_context.versioned_constants.os_constants.allowed_virtual_os_program_hashes`: [1](#0-0) 

The Cairo-side mirror of this check hard-codes the allow-list to a single entry (`ALLOWED_VIRTUAL_OS_PROGRAM_HASHES_LEN == 1`): [2](#0-1) [3](#0-2) 

Across successive protocol versions, this value is not additive: the versioned-constants regression diffs show the allowed program hash and allowed proof version being *changed in place* (`~`) rather than appended (`+`) when moving from 0.14.2 to 0.14.3: [4](#0-3) [5](#0-4) [6](#0-5) 

Client-side proofs are produced off-chain by `starknet_transaction_prover` and are meaningful in production for privacy-pool style contracts (the `apply_actions`/`validate_proof` mainnet flow referenced in test comments), where the sequencer's on-chain verification of `proof_facts` is what a contract like a privacy pool relies on to authorize an action: [7](#0-6) 

Once a node upgrades to a new protocol version that swaps in a new `allowed_virtual_os_program_hashes` entry, any user holding a previously generated, not-yet-submitted proof (bound to the old program hash) will have their transaction permanently rejected during pre-validation — this is exactly analogous to the Avail Bridge issue where changing the single trusted `vectorx` reference orphans previously valid but not-yet-processed proofs, with no mechanism to accept both the old and new value simultaneously.

### Impact Explanation
A user who generated a client-side proof (which may attest to a privacy-pool action tied to a specific historical state/nullifier) but has not yet submitted the corresponding invoke transaction before a protocol upgrade will find that transaction permanently unprocessable: `validate_proof_facts` rejects it with `InvalidProofFacts` at pre-validation, before it can reach the mempool/block. Because the allow-list is a single hard-coded replaced value (not additive), there is no backward-compatibility window. If the action encoded in the proof cannot be safely regenerated against updated pool state (e.g. the underlying privacy-pool state has since moved, other actions consumed shared resources, or the private witness/base block combination is no longer reproducible against the newly required program hash), the value/action attested by that proof is permanently denied service — a Medium-severity DOS on in-flight client-side-proven actions, without requiring any privileged actor.

### Likelihood Explanation
This requires no attacker action beyond ordinary transaction submission timing: any legitimate user with an in-flight client-side proof at the moment of a protocol/versioned-constants upgrade is affected. Protocol upgrades that bump `allowed_virtual_os_program_hashes`/`allowed_proof_versions` are a normal, expected part of the sequencer's lifecycle (as evidenced by the 0.14.2→0.14.3 diff), making this a realistic recurring exposure rather than a contrived edge case.

### Recommendation
Allow `allowed_virtual_os_program_hashes` (and `allowed_proof_versions`) to hold multiple concurrently-valid entries across a transition/deprecation window instead of being replaced wholesale on each protocol bump, so proofs generated under the immediately preceding version remain acceptable for a grace period. Alternatively, provide an explicit, bounded overlap period during upgrades and document/enforce it in `check_proof_facts`/`validate_proof_facts` and the `ALLOWED_VIRTUAL_OS_PROGRAM_HASHES_LEN` Cairo constant, so pending proofs are not silently and permanently orphaned by an upgrade.

### Proof of Concept
1. A user runs `starknet_transaction_prover` to generate `proof_facts`/`proof` for an Invoke V3 transaction against protocol version N, where `program_hash` matches N's `allowed_virtual_os_program_hashes[0]` (e.g. `0x3e98c2d7...` in 0.14.2).
2. Before the user submits the transaction, the network upgrades to protocol version N+1, which replaces the allow-list entry (e.g. to `0x53f6c9fc...` in 0.14.3), per `crates/blockifier/resources/versioned_constants_diff_regression/0.14.2_0.14.3.txt`.
3. The user submits the transaction. `AccountTransaction::validate_proof_facts` checks `allowed_virtual_os_program_hashes.contains(&snos_proof_facts.program_hash)`, which is now `false` for the version-N hash — see `crates/blockifier/src/transaction/account_transaction.rs:322-329`.
4. The transaction is rejected with `TransactionPreValidationError::InvalidProofFacts("Virtual OS program hash ... is not allowed")` at pre-validation, and can never be included; the user must reconstruct and re-attest an equivalent off-chain computation from scratch, which may not be possible if dependent on-chain/pool state has since changed.

// Returns TRUE if the given virtual OS program hash is allowed, FALSE otherwise.
func is_program_hash_allowed(program_hash: felt) -> felt {
    static_assert ALLOWED_VIRTUAL_OS_PROGRAM_HASHES_LEN == 1;
    if (program_hash - ALLOWED_VIRTUAL_OS_PROGRAM_HASHES_0 == 0) {
        return TRUE;
    }
    return FALSE;
}
