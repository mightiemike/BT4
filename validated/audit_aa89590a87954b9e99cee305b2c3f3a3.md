### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists causes resource-exhaustion / high-cost account operations - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
Like the `ink!` bug where a `repeated` collection is stored under a single storage cell that must be fully decoded/encoded on every access (bounded to ~16KB before failing or becoming expensive), java-tron's legacy (non-V2) resource-delegation index stores an unbounded `repeated bytes` list of delegate counterpart addresses inside one protobuf value keyed by a single account address. Every append operation requires deserializing the whole value, mutating the in-memory list, and re-serializing/re-writing it, with no cap on the number of distinct addresses that can accumulate.

### Finding Description
`DelegatedResourceAccountIndexCapsule` wraps the `DelegatedResourceAccountIndex` protobuf message and exposes unconditional append operations with no size bound: [1](#0-0) [2](#0-1) 

This capsule is the legacy (pre-optimization) index used by `FreezeBalanceActuator`/`UnfreezeBalanceActuator` whenever `dynamicStore.supportAllowDelegateOptimization()` is false, storing to/from account lists directly under a single DB key per owner address: [3](#0-2) 

Each call to `FreezeBalanceContract` with a distinct `receiverAddress` appends a new entry to this single-value list (via `delegatedResourceAccountIndexStore` in the non-V2 path), and there is no validation limiting how many distinct receiver addresses an owner can delegate to over time, unlike `VoteWitnessActuator`, which explicitly caps list size with `MAX_VOTE_NUMBER`: [4](#0-3) 

By contrast, the newer "V2" delegate flow was redesigned specifically to avoid this pattern — instead of one unbounded list per account, it stores one small entry per `(from,to)` pair under a distinct key (`V2_FROM_PREFIX`/`V2_TO_PREFIX`), exactly the mitigation the external report recommends ("create another storage collection to store array elements in different slots"): [5](#0-4) 

The existence of a `convert()` migration function that walks the old unbounded `toAccountsList`/`fromAccountsList` and rewrites them into the new per-pair keys is direct evidence that the java-tron team identified this exact unbounded-collection-in-a-single-cell problem and is migrating away from it, but the legacy code path and capsule methods remain present and reachable when the optimization flag is not (yet) enabled for an account/chain state: [6](#0-5) 

Separately, a related pattern with a demonstrated size sensitivity exists for `Account.votes`/`Account.frozen` repeated fields, where an internal test explicitly measures and caps serialized size growth at 1600 bytes, corroborating that unbounded repeated fields inside a single stored `Account`/index value are a recognized risk in this codebase: [7](#0-6) 

### Impact Explanation
An attacker (any account holder, since `FreezeBalanceContract` is a normal broadcast transaction type) can repeatedly freeze the minimal `1 TRX` and delegate it to many distinct newly-created receiver addresses. Because the legacy index capsule has no bound on `toAccountsList`/`fromAccountsList` size, this causes:
- Linear growth of the serialized `DelegatedResourceAccountIndex` value for the owner (and correspondingly for each receiver's `fromAccountsList`), which must be fully protobuf-decoded and re-encoded on every subsequent freeze/delegate/unfreeze touching that account, degrading node performance for any transaction interacting with a "polluted" account (state-processing DoS).
- Increased LevelDB/RocksDB value sizes stored under a single key, disproportionate to the fee paid for the transactions that produced them, since fee/energy accounting is per-transaction, not proportional to the resulting cumulative storage-read/write cost imposed on future operations.
- Potential amplification for full/RPC nodes that expose these accounts via `GetAccount`/`getDelegatedResourceAccountIndex`-style RPCs, where a single query must marshal a growing unbounded list into a gRPC/HTTP response, comparable to the `ink!` decode-limit failure mode.

This is a DoS-class issue via normal broadcast transactions against actuator state transitions and store access, not requiring any privileged role.

### Likelihood Explanation
Moderate. The vulnerable legacy path is only active while `supportAllowDelegateOptimization()` is false for the relevant account/chain state (i.e., before the corresponding committee proposal is activated on a given network, or on any private/test chain that has not enabled it). Where the optimization is active, `delegateV2`/`unDelegateV2` avoid the growth pattern entirely. The exploit requires no special privileges — only funded normal accounts and many freeze transactions to distinct receiver addresses — but is bounded by the cost of creating/funding the distinct receiver accounts and the per-transaction minimum freeze amount and bandwidth/energy fees, which raises the practical cost of the attack somewhat.

### Recommendation
- Cap the number of distinct delegate relationships tracked in the legacy `DelegatedResourceAccountIndexCapsule` (analogous to `MAX_VOTE_NUMBER` for votes), or reject new `FreezeBalanceContract` delegations once a configurable maximum list size is reached for an owner/receiver.
- Accelerate migration/enforcement of the V2 per-pair storage model (`delegateV2`/`unDelegateV2`) as the only supported path, and disable the unbounded legacy `addToAccount`/`addFromAccount` growth path chain-wide.
- Charge storage/bandwidth fees proportional to the resulting index size growth, so that future read/write costs imposed on the network are internalized by the actor who grows the collection.

### Proof of Concept
1. Attacker account A freezes `1 TRX` for BANDWIDTH via `FreezeBalanceContract` with `receiverAddress = R1` (a fresh, funded account), while `dynamicStore.supportAllowDelegateOptimization()` is false — this appends `R1` to A's `DelegatedResourceAccountIndexCapsule.toAccountsList` and `A` to `R1`'s `fromAccountsList` (see `UnfreezeBalanceActuator.java:163-182` for the corresponding removal-side logic showing the same list-based structure is used on freeze).
2. Repeat step 1 with `R2, R3, ..., Rn` for large `n`, each in a separate transaction (kept below `1 TRX` per delegation, minimizing attacker cost).
3. A's `DelegatedResourceAccountIndex` value now contains `n` addresses in `toAccountsList`; every subsequent `FreezeBalanceActuator`/`UnfreezeBalanceActuator` operation touching A must fully deserialize/reserialize this ever-growing single protobuf value, and any RPC/service that surfaces this index must marshal the full list, reproducing the "single storage cell, unbounded collection" cost blow-up described in the external `ink!` report.

    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
