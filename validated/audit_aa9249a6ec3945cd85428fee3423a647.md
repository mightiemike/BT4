### Title
Starknet OS `execute_replace_class` does not verify the new class hash is declared, unlike blockifier's `replace_class` — ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The `replace_class` syscall handler in the Starknet OS Cairo program (used for OS re-execution / state-commitment proving) blindly overwrites a contract's class hash without validating that the class hash is actually declared, while the blockifier's Rust implementation of the same syscall explicitly performs this check before mutating state. This is the sequencer analog of the reported bug class: a state-mutating operation proceeds without validating a critical value (the report's "unchecked zero address" implementation pointer) that another, parallel/duplicate implementation of the same logic does check.

### Finding Description
In `execute_replace_class`, the OS reads the requested `class_hash` and immediately writes it into the contract's new `StateEntry`, with only a `TODO` comment noting the missing validation: [1](#0-0) 

```
    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );
```

By contrast, the blockifier implementation (used by the sequencer for real execution and fee/validity decisions) explicitly ensures the class exists (and is Cairo1) before performing the same mutation: [2](#0-1) 

```
    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
```

Tests confirm blockifier rejects `replace_class` with an undeclared class hash ("is not declared") and with a mismatched Cairo version ("Cannot replace V1 class hash with V0 class hash"): [3](#0-2) 

The OS is the component responsible for re-executing the block and producing the committed state root/tree updates that anchor the block hash (analogous to the ProgramFactory `create()` mutating on-chain state without validating the value it depends on). Because the OS path has no equivalent guard, it will happily commit a `class_hash` value into the state tree that was never validated as a declared class (including 0/`UNINITIALIZED_CLASS_HASH`, or a V0/Cairo0 class where V1 is required), creating a semantic gap between what blockifier permits during execution and what the OS is willing to attest to when re-computing and committing state.

### Impact Explanation
If the OS accepts and commits a `replace_class` state update that blockifier's stricter, declared-class-aware logic would have rejected, the two execution engines can diverge on whether a given block/state transition is valid:
- A contract's class hash could be set to an undeclared or zero value in the committed state tree, permanently bricking the contract (its future calls dispatch to code that either doesn't exist or is the "uninitialized" placeholder), which can permanently freeze any funds/logic tied to that contract.
- Because this check is asymmetric between the sequencer's blockifier and the OS that re-executes/proves the block, the state root committed by the OS could diverge from what an honest re-execution using blockifier's rules would produce, undermining the guarantee that the OS-computed commitment matches the intended, policy-enforced state transition.

### Likelihood Explanation
`replace_class_syscall` is directly callable by any deployed contract in response to an ordinary, unprivileged transaction (no special privileges required) — see the Cairo1 test contract's trivial wrapper: [4](#0-3) 

Reaching the vulnerable OS code path only requires a normal invoke transaction that calls a contract exposing `replace_class_syscall`, which is a standard, commonly-used entry point pattern (proxy/upgradeable contracts). The gap is explicitly flagged by the code's own `TODO` comment, confirming it is a known, currently-unaddressed omission rather than a hardened invariant enforced elsewhere in the OS.

### Recommendation
Add an explicit check in `execute_replace_class` (mirroring blockifier's `replace_class` in `crates/blockifier/src/execution/syscalls/syscall_base.rs`) that reads the contract-class dictionary/state to confirm the requested `class_hash` corresponds to a declared class (and matches the expected Cairo version) before performing the `dict_update` on `contract_state_changes`, ensuring OS-side state commitment enforces the same invariant as blockifier execution.

### Proof of Concept
1. Deploy a contract exposing `test_replace_class(class_hash)` which calls `replace_class_syscall(class_hash)` (e.g., the test contract at `crates/blockifier_test_utils/resources/feature_contracts/cairo1/cairo_steps_test_contract.cairo:200-203`).
2. Submit an invoke transaction calling `test_replace_class` with an undeclared/zero `class_hash`.
3. Under blockifier (`crates/blockifier/src/execution/syscalls/syscall_base.rs:369-378`), this call fails with an "is not declared" error and reverts.
4. Trace the same operation through the OS's `execute_replace_class` (`crates/apollo_starknet_os_program/.../syscall_impls.cairo:881-920`): no declared-class assertion exists before `dict_update` writes the new `class_hash` into `contract_state_changes`, demonstrating the OS path lacks the guard that blockifier enforces for the identical operation.
