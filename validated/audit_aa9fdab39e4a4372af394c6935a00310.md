### Title
Unpausing liquidation never clears the pause flag, permanently freezing liquidations after a single unpause call - (File: `mainnet/contracts/market/v0-4-market.clar`, `local-testing/contracts/market/market.clar`)

### Summary
`set-pause-liquidation` in the market contract has a branch that is supposed to *unpause* liquidations but never writes `false` to the `pause-liquidation` data-var. This mirrors the `[M-18]` bug class: a status/state variable that is supposed to flip on a given code path is silently left unchanged, so downstream logic keeps reading the stale value forever.

### Finding Description
The pause/unpause entry point is:

```clarity
(define-data-var pause-liquidation bool false)
(define-data-var liquidation-grace-end uint u0)

(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (if (and was-paused (not paused))
        ;; When unpausing, set grace period
        (var-set liquidation-grace-end
                 (+ stacks-block-time grace-period))
        (var-set pause-liquidation paused))))

(define-read-only (liquidation-paused)
  (let ((manual-pause (var-get pause-liquidation))
        (grace-active (< stacks-block-time
                         (var-get liquidation-grace-end))))
    (or manual-pause grace-active)))
``` [1](#0-0) 

Walk through the two branches of `set-pause-liquidation`:

1. Pause path (`was-paused=false`, `paused=true`) or the "re-affirm" path (`was-paused=true`, `paused=true`): falls into the `else` branch, `(var-set pause-liquidation paused)` runs and `pause-liquidation` becomes/stays `true`. This is correct.
2. Unpause path (`was-paused=true`, `paused=false`): the `(and was-paused (not paused))` condition is true, so execution takes the **first** branch, which only does `(var-set liquidation-grace-end (+ stacks-block-time grace-period))`. `pause-liquidation` itself is **never** set to `false` in this branch.

Because `liquidation-paused` computes `(or manual-pause grace-active)`, and `manual-pause` (i.e. `(var-get pause-liquidation)`) is still `true` from step 2, liquidations remain permanently paused — the grace-end timestamp is irrelevant since the `or` short-circuits on `manual-pause` regardless of whether the grace period has elapsed. The only way to actually clear `pause-liquidation` would be to call `set-pause-liquidation` again with `paused=true` and then again with `paused=false` while `was-paused` was `false` at call time — but that's inconsistent/impossible to reach since after the first unpause attempt `pause-liquidation` is still `true`, so any subsequent call always re-enters the same branch that never clears the flag. There is no code path that ever writes `false` to `pause-liquidation` once it has been set to `true`.

This is structurally identical to the `[M-18]` root cause: a conditional branch inside a state-transition function that is supposed to update a status flag but instead only updates a secondary/derived value (grace-end timestamp instead of the flag itself), leaving the primary status stuck.

### Impact Explanation
Once liquidations are paused and an unpause is attempted via the intended API, liquidations can never be re-enabled through this function again. Since liquidations are how the protocol converts unhealthy positions back into performing debt/collateral and are one of the safety valves for protocol solvency, a permanently stuck pause causes **temporary freezing of funds** — under-collateralized positions cannot be liquidated, and any interest/yield tied to timely liquidation (bad-debt socialization, penalty fees) becomes unclaimable until a code fix/redeploy occurs. This matches the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
This requires no attacker — it triggers deterministically the first time the DAO/pause admin calls `set-pause-liquidation` to un-pause after having paused (a standard, expected operational sequence: pause during an incident, then unpause once resolved). Any protocol operator following the documented pause/unpause flow will trigger it.

### Recommendation
In the unpause branch, explicitly clear the flag in addition to (or instead of) only setting the grace-end timestamp, e.g.:
```clarity
(if (and was-paused (not paused))
    (begin
      (var-set liquidation-grace-end (+ stacks-block-time grace-period))
      (var-set pause-liquidation false))
    (var-set pause-liquidation paused))
```

### Proof of Concept
1. Admin calls `set-pause-liquidation(true, 0)` → `pause-liquidation = true`.
2. Admin calls `set-pause-liquidation(false, 3600)` intending to unpause with a 1-hour grace period → only `liquidation-grace-end` is updated; `pause-liquidation` remains `true`.
3. Call `liquidation-paused` at any later time (even after the grace period has fully elapsed) → returns `true` because `manual-pause` is still `true`, so the `or` in `liquidation-paused` never resolves to `false`.
4. Any attempt to liquidate an unhealthy position reverts/`is-blocked` because `liquidation-paused` is stuck `true`, with no further call available to reset it.

Note: the exact logic was confirmed via [1](#0-0) , and the same identifiers (`pause-liquidation`, `liquidation-grace-end`, `set-pause-liquidation`) were confirmed present in both `mainnet/contracts/market/v0-4-market.clar` and `local-testing/contracts/market/market.clar` via repository search, though the exact line numbers inside those `.clar` files could not be pulled before the tool budget was exhausted. A full Devin session with file access would be needed to confirm the exact line numbers in the production `.clar` source and to verify no other code path clears `pause-liquidation`.
