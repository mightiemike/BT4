### Title
Unbounded native-stack recursion in `Chain::get_recursive_transaction_results` allows a single transaction to crash an RPC/view node on tx-status query - (File: chain/chain/src/chain.rs)

### Summary
`Chain::get_recursive_transaction_results` walks the receipt tree produced by a transaction using genuine Rust function-call recursion (one stack frame per receipt), with no depth limit, unlike the parallel `ReceiptToTx` lookup path which explicitly enforces a `MAX_DEPTH = 1000` (as shown by `RpcReceiptToTxError::DepthExceeded` and the `test_receipt_to_tx_depth_exceeded` test). This function is reached from `Chain::get_final_transaction_result`, which backs the JSON-RPC transaction-status / `EXPERIMENTAL_tx_status` queries served by the view client. Any account can submit a single transaction that causes a long linear chain of receipts (e.g. via chained cross-contract callback promises), then query its status via RPC to force the node to recurse once per receipt in the chain, exhausting the stack and crashing the node process.

### Finding Description
`get_recursive_transaction_results` is a plain recursive function: [1](#0-0) 

For each outcome it iterates over `outcome.receipt_ids` and recurses into every child id (line 3204), with the recursion depth being exactly the length of the receipt chain generated by the original transaction/receipt. There is no depth counter, no iteration limit, and no conversion to an explicit heap-allocated stack (`Vec`/`VecDeque`) — contrast this with other trie-walking code in the same codebase that was specifically rewritten to avoid stack overflow risk, e.g. `TrieRecorder::get_subtree_size`: [2](#0-1) 

which explicitly says "Non recursive approach to avoid any potential stack overflows." The `ReceiptToTx` reverse-lookup feature added the same protection with an explicit `MAX_DEPTH=1000` and a dedicated `DepthExceeded` error: [3](#0-2) [4](#0-3) 

but `get_recursive_transaction_results` — used for the forward tx→receipt walk that answers ordinary transaction status queries — has no equivalent guard: [5](#0-4) 

An attacker-controlled contract can chain a long sequence of receipts from a single signed transaction (each action receipt creating exactly one follow-up action receipt via a promise, i.e., a simple linear chain, not a fan-out), which is permitted by the protocol's per-receipt and per-chunk gas/action limits but not by any bound on total chain *length* across the transaction's lifetime (delayed receipts, congestion buffering, and cross-shard forwarding processing let such long serial receipt chains execute over many blocks). Once a sufficiently long chain (thousands of hops) has executed, any RPC caller — not just the transaction's signer — can call the standard "get transaction status with receipts" JSON-RPC method for that transaction hash, which invokes `get_final_transaction_result` → `get_recursive_transaction_results`, causing thousands of nested native stack frames. Rust does not guard against stack overflow from user-controlled recursion depth; this typically manifests as a SIGSEGV/abort that kills the node process — a hard crash rather than a graceful error, matching the "hang or frequently repeatable crash (complete DOS)" characteristic in CVE-2024-20974 for the analogous query-execution component (the transaction/receipt "optimizer"/outcome-resolution path).

### Impact Explanation
Any RPC node or validator that has `save_tx_outcomes`/`save_receipt_to_tx` enabled (the default outcome-tracking path used by `get_execution_outcome`) and receives a status query for a transaction with a sufficiently long receipt chain will crash. Because standard JSON-RPC nodes are exposed to arbitrary callers, and the crash is repeatable (querying the same or a similarly-shaped tx hash again reproduces it), this is a transaction-triggered denial-of-service against RPC/view-serving nodes: an unprivileged signer creates the poison transaction once, then any RPC caller (including the attacker) can crash the node repeatedly by querying its status. This meets the required "transaction-triggered halt" impact category.

### Likelihood Explanation
Medium: constructing a transaction whose execution generates a very long serial chain of receipts requires either a contract designed to recursively schedule follow-up promises (easy to write and deploy without special privilege) or many blocks of execution while gas/congestion limits throttle throughput, so the attack requires some patience/gas budget but no special permissions, matching a network-reachable, high-effort-but-feasible profile similar to the original CVE's exploitability characterization.

### Recommendation
Convert `get_recursive_transaction_results` to an explicit iterative traversal (e.g., a `VecDeque`/stack-based BFS/DFS as already used elsewhere in the codebase, such as `TrieRecorder::get_subtree_size`) and/or apply the same kind of `MAX_DEPTH` bound and `DepthExceeded`-style error already used by the `ReceiptToTx` reverse-lookup path, returning a graceful RPC error instead of recursing without bound.

### Proof of Concept
1. Deploy a contract whose method, when called, schedules exactly one follow-up promise to itself (or another contract) with `receiver_id != signer_id` so that receipts propagate across several blocks/shards rather than resolving instantly.
2. Submit one signed transaction invoking this method with a large loop counter encoded in state so the chain continues for N ≈ several thousand hops (bounded only by attached gas × number of blocks the attacker is willing to wait for, not by any single-chunk or single-receipt limit).
3. After the chain has executed (or partially executed with outcomes recorded), call the JSON-RPC transaction-status method (`tx`/`EXPERIMENTAL_tx_status`) for the original transaction hash against any RPC node that stores execution outcomes.
4. The RPC/view-client node's `Chain::get_final_transaction_result` invokes `get_recursive_transaction_results`, recursing once per receipt in the chain; with enough hops this exhausts the thread stack and crashes the node process, reproducible on every subsequent query of the same hash.
