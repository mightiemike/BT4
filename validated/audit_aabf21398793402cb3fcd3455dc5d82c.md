### Title
Empty-but-`Some` Nakamoto Signer Set Collapses the Block-Approval Threshold to Zero, Allowing Unsigned Blocks to Pass Signature Verification - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
The Validium report's bug class ("an empty committee validates any message because `requiredAmountOfSignatures` is derived from committee size and floors to zero") has a direct analog in the Nakamoto signer-set / block-approval path. `NakamotoBlockHeader::verify_signer_signatures` only rejects a reward set when `reward_set.signers()` is `None` — it does **not** reject a reward set whose signer vector is present but empty (`Some(vec![])`). When that happens, `total_signing_weight()` returns `Ok(0)`, `compute_voting_weight_threshold(0)` returns `0`, and a block with zero signer signatures satisfies `total_weight_signed (0) < threshold (0)` as `false`, so the block is accepted as fully signed.

### Finding Description
`RewardSet::signers()` distinguishes "no signer set at all" (`None`) from "signer set present, just empty" (`Some(vec![])`): [1](#0-0) 

`total_signing_weight()` treats an empty `Some` vector as a valid weight of `0` rather than an error, since it only checks for `None`: [2](#0-1) 

`verify_signer_signatures` follows the same pattern — it errors out only on `None`, then proceeds to compute `total_weight = reward_set.total_signing_weight()` (which is `0` for an empty vec), computes `threshold = compute_voting_weight_threshold(0)`, and compares `total_weight_signed < threshold`: [3](#0-2) [4](#0-3) 

`compute_voting_weight_threshold` for `total_weight = 0` computes `ceil(0 * 7 / 10) = 0`: [5](#0-4) 

So with an empty (but `Some`) signer vector and a block carrying zero (or any number of unmatched) signatures, `total_weight_signed = 0` is **not less than** `threshold = 0`, and the function returns `Ok(0)` — i.e., the block is accepted as validly signed with no signatures at all. This is structurally identical to the Validium report: the "required signatures" quantity is derived from committee/weight size, and an empty set silently degrades the requirement to zero rather than being rejected outright.

The reward set can legitimately end up in this `Some(empty vec)` state. `StacksChainState::make_signer_set` (used by the PoX-4 path) returns `None` only when the input `entries` list itself is empty; if `entries` is non-empty but every entry's computed `weight = stacked_amt / threshold` floors to `0`, the `filter_map` drops all of them, and the function returns `Some(vec![])`: [6](#0-5) 

This is then propagated unchecked through `pox_4_compute_and_update_signers`, which does not check for an empty resulting signer set before writing it into the `.signers` contract and returning it as the effective `RewardSet`: [7](#0-6) 

Notably, the newer PoX-5 path (`pox_5_compute_and_update_signers`) explicitly guards against exactly this condition — treating an empty `signer_set` as a fatal network condition and refusing to continue — confirming the development team recognizes this exact class of bug as dangerous, but the guard is absent from the still-reachable PoX-4 code path: [8](#0-7) 

### Impact Explanation
If a reward cycle's signer set collapses to `Some(vec![])` (e.g., extremely low/fragmented stacking participation under PoX-4 such that every stacker's `stacked_amt / threshold` floors to zero, while at least one stacker record exists so `make_signer_set` doesn't return `None`), `verify_signer_signatures` accepts **any** Nakamoto block for that reward cycle regardless of `signer_signature` content — an unsigned or arbitrarily-signed block passes network-wide signer validation. This breaks the core Nakamoto consensus invariant that a block must carry threshold-weighted signer approval, and every node evaluating the same on-chain reward-set state would independently reach the same (wrong) "accepted" verdict, i.e., an invalid block accepted network-wide. This matches the Critical impact criterion of "an invalid block accepted network-wide."

### Likelihood Explanation
This is not attacker-forgeable at will (the reward set is derived from on-chain PoX-4 stacking state, not attacker-supplied input directly), but it is a reachable degenerate state of legitimate, permissionless stacking behavior (many small stackers, or a stacking distribution where the PoX threshold outstrips per-stacker locked amounts), which requires no majority collusion, no admin key, and no privileged action — it can arise from ordinary minority participation patterns. The team's own fix for the equivalent PoX-5 case ("Fatal network condition: reward set computed with an empty signer set") is direct internal evidence that this exact scenario is considered realistic and dangerous, yet the check is missing on the (still-supported) PoX-4 path used by `check_and_handle_prepare_phase_start` before PoX-5 activation.

### Recommendation
Add the same guard used in `pox_5_compute_and_update_signers` to `pox_4_compute_and_update_signers` (and/or centrally in `verify_signer_signatures`/`total_signing_weight`): treat `Some(vec![])` identically to `None` — reject/abort reward-set computation rather than propagating an empty, weight-zero signer set that trivially satisfies the `>= threshold` check. Additionally, harden `verify_signer_signatures` to explicitly reject blocks when `total_weight == 0` or `signers.is_empty()`, independent of how the reward set was produced, so the signature-verification code path does not rely solely on upstream reward-set construction being correct.

### Proof of Concept
1. Drive PoX-4 stacking participation into a state where `make_signer_set`'s input `entries` is non-empty (at least one stacker record with a `signer` key set) but every entry's `stacked_amt / threshold` computes to `0` (e.g., many stackers each locking far less than the per-slot threshold). `make_signer_set` returns `Some(vec![])` — see `stackslib/src/chainstate/stacks/boot/mod.rs:1020-1071`.
2. `pox_4_compute_and_update_signers` stores and returns this `RewardSet` unchanged (no emptiness check) — `stackslib/src/chainstate/nakamoto/signer_set.rs:699-738`.
3. For the next reward cycle, produce/relay a `NakamotoBlock` with `signer_signature = vec![]` (or any signatures, since none will be checked against an empty set) referencing this reward set.
4. Call `block.header.verify_signer_signatures(&reward_set, epoch_id)`:
   - `reward_set.signers()` returns `Some(&vec![])`, passing the `None` check at `stackslib/src/chainstate/nakamoto/mod.rs:1103-1107`.
   - `total_weight = reward_set.total_signing_weight()` = `Ok(0)`.
   - `threshold = compute_voting_weight_threshold(0)` = `0`.
   - `total_weight_signed = 0` (no signatures processed).
   - `0 < 0` is `false`, so the function returns `Ok(0)` — the block is treated as validly signed.

        threshold: u128,
        entries: &[RawRewardSetEntry],
    ) -> Option<Vec<NakamotoSignerEntry>> {
        let Some(first_entry) = entries.first() else {
            // entries is empty: there's no signer set
            return None;
        };
        // signing keys must be all-or-nothing in the reward set
        let expects_signing_keys = first_entry.signer.is_some();
        for entry in entries.iter() {
            if entry.signer.is_some() != expects_signing_keys {
                panic!("FATAL: stacking-set contains mismatched entries with and without signing keys.");
            }
        }
        if !expects_signing_keys {
            return None;
        }

        let mut signer_set = BTreeMap::new();
        for entry in entries.iter() {
            let signing_key = entry
                .signer
                .expect("BUG: signing keys should all be set in reward-sets with any signing keys");
            if let Some(existing_entry) = signer_set.get_mut(&signing_key) {
                *existing_entry += entry.amount_stacked;
            } else {
                signer_set.insert(signing_key, entry.amount_stacked);
            };
        }

        let mut signer_set: Vec<_> = signer_set
            .into_iter()
            .filter_map(|(signing_key, stacked_amt)| {
                let weight = u32::try_from(stacked_amt / threshold)
                    .expect("CORRUPTION: Stacker claimed > u32::max() reward slots");
                if weight == 0 {
                    return None;
                }
                Some(NakamotoSignerEntry {
                    signing_key,
                    stacked_amt,
                    weight,
                })
            })
            .collect();

        // finally, we must sort the signer set: the signer participation bit vector depends
        //  on a consensus-critical ordering of the signer set.
        signer_set.sort_by_key(|entry| entry.signing_key);

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
