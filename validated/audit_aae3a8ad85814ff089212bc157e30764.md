### Title
`ValidateMultiSign`/`BatchValidateSign` Precompiles Sign Over a Hash With No Domain Separation, Enabling Cross-Contract Signature Replay - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiles `ValidateMultiSign` (address `0x0a`) and `BatchValidateSign` (address `0x09`) let any deployed smart contract verify off-chain ECDSA signatures against a TRON account's on-chain `Permission`. The hash that is actually signed by end users/backends is `sha256(address || permissionId || data)` — exactly the same class of bug as the report: it commits only to the target account, the permission id, and a caller-supplied payload, but never to the identity of the *verifying/calling contract*, `block.chainid`-equivalent context, or any TIP/contract-specific session tag. Because these fields are absent from the signed preimage, a signature produced to authorize one contract's action can be replayed verbatim against any other deployed contract that calls `validatemultisign`/`batchvalidatesign` with the same `(address, permissionId, data)` triple, exactly mirroring the "cross-deployment replay" root cause in the external report.

### Finding Description
`ValidateMultiSign.execute()` builds the signed message as:

```java
byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), combine);
``` [1](#0-0) 

and then recovers each signer and checks accumulated `Permission` weight:

```java
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
...
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
``` [2](#0-1) 

The preimage `address || permissionId || data` never includes:
- the address of the contract that is calling the precompile (analogous to `address(this)` in the report),
- any chain/network domain tag,
- any nonce, session id, or expiry enforced by the precompile itself.

The test suite confirms this exact construction is the one users are expected to sign off-chain:

```java
byte[] merged = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] toSign = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), merged);
``` [3](#0-2) 

Because `address`, `permissionId`, and `data` are all caller-supplied and there is no protocol-enforced binding to the verifying contract, any contract deployed on-chain that accepts a `(bytes32 data, bytes[] signatures)` pair from a user and forwards it to `validatemultisign(address, permissionId, data, signatures)` is vulnerable to replay: a signature originally produced (by the account owner, or by any backend holding delegated keys under that `Permission`) to authorize action in Contract A can be resubmitted verbatim to Contract B (a different, unrelated deployed contract, or a redeployed/upgraded version of the same contract) as long as B happens to compute the same `data` value — which is trivial when `data` is a hash of otherwise-public parameters (order id, uid, amount, etc.) that don't themselves encode the destination contract.

This is structurally identical to the reported bug: the signed payload is a "join"-style authorization hash lacking `address(this)`/domain-separation fields, so intra-chain cross-deployment replay is possible whenever `data` doesn't already carry contract-identity/session context — and the precompile gives every calling contract a false sense that "verified signature ⇒ intended for me."

### Impact Explanation
Any anonymous user can trigger this via a `TriggerSmartContract` transaction against a contract that uses `validatemultisign`/`batchvalidatesign` for authorization (common pattern for multisig wallets, escrow, order-matching, or backend-gated actions on TRON). If two different deployed contracts (or two versions of the same contract across an upgrade/migration) share overlapping `data` semantics, a signature intended to gate one contract's action can be replayed to authorize the same weighted action in the other, bypassing the intended one-time/one-context authorization the account owner or backend believed they were granting — this is an unauthorized-account-operation class impact, consistent with the "Recommendation/Impact" of the original finding (weakened gatekeeping, unintended reuse of an authorization bound to a specific environment/context).

### Likelihood Explanation
Reachable by any unprivileged actor able to broadcast a `TriggerSmartContract` transaction that invokes a contract using this precompile, and by any unprivileged actor able to observe/replay a previously-used `(data, signatures)` pair (these are public once submitted in a prior on-chain call). No privileged keys or node access are required — only a contract in the ecosystem that follows the precompile's documented signing pattern without independently adding domain separation, which the precompile design does nothing to prevent or even warn about.

### Recommendation
Extend the precompile's signed preimage to include domain-separation fields analogous to the report's fix, e.g., bind the hash to the *calling* contract address (`msg.sender`/`this` at the point of the `STATICCALL`/`CALL` into the precompile) in addition to the target account and permission id:

```java
byte[] combine = ByteUtil.merge(
    callerContractAddress, address, ByteArray.fromInt(permissionId), data);
```

Since changing the precompile's hash formula is a breaking/consensus change, this should be introduced behind a new TIP/hard-fork activation flag (similar to `VMConfig.allowTvmOsaka()`/`allowTvmSelfdestructRestriction()` gating already used for other behavioral changes in this same file), and documented so contract authors relying on `validatemultisign` are required to additionally namespace `data` with their own contract address/session identifiers until the flag activates.

### Proof of Concept
1. Deploy Contract A that calls `validatemultisign(accountAddr, permissionId, dataHash, signatures)` to gate a withdrawal keyed by `dataHash = sha256(orderId)`.
2. Account owner (or backend under a delegated `Permission`) signs `sha256(accountAddr || permissionId || dataHash)` intending to authorize a specific withdrawal in Contract A for `orderId`.
3. Deploy Contract B (attacker-controlled or a copy/fork of A) that independently derives the same `dataHash = sha256(orderId)` for its own unrelated action and calls the same precompile with the same `(accountAddr, permissionId, dataHash)`.
4. Submit the previously observed `signatures` (public from A's on-chain call) to Contract B via a normal `TriggerSmartContract` transaction; `ValidateMultiSign.execute()` recomputes the identical hash, recovers the same signer, and returns `dataOne()` (success), letting Contract B execute a weighted action never intended for it — all performed by an anonymous unprivileged caller broadcasting a normal transaction.
