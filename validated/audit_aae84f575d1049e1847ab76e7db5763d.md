### Title
`replace_class` syscall in the Starknet OS does not validate that the target class hash is declared before committing the state change - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Cairo-side implementation of the `replace_class` syscall in the Starknet OS program updates a contract's class hash in `contract_state_changes` using an unvalidated, hint-supplied `class_hash`, with an explicit `TODO` acknowledging the missing declared-class check. This mirrors the reported bug class: a state-mutating "setter" (here, the contract's associated "strategy"/class) is allowed to be applied without first validating the sanity/existence of the referenced entity, unlike the corresponding Rust blockifier implementation, which does perform this check.

### Finding Description
`execute_replace_class` in `syscall_impls.cairo` reads a `class_hash` from calldata and directly writes it into the contract's `StateEntry` via `dict_update`, without checking that a contract class with that hash was ever declared: [1](#0-0) 

The comment on line 902, `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.`, explicitly documents this gap.

By contrast, the equivalent Rust `blockifier` implementation that actually executes transactions during block building enforces this invariant: it calls `get_compiled_class` to ensure the class is declared and rejects non-Cairo1 (V0) targets before mutating state: [2](#0-1) 

The deprecated (Cairo 0) syscall path in the OS program has the same omission — it updates `contract_state_changes` unconditionally with the caller-provided `class_hash`, with no existence check: [3](#0-2) 

Since the Starknet OS is the program that re-executes a block to produce the proven, committed state transition (used in proving and in Starknet OS re-execution paths), any divergence between what the blockifier accepted when building/validating the block and what the OS accepts when proving it can create a discrepancy between the state that the sequencer/blockifier computed and the state that the OS commits to as canonical.

### Impact Explanation
Any account contract invoked by an ordinary transaction can call the `replace_class` syscall with an arbitrary felt as `class_hash`, reachable by any unprivileged transaction sender. If the blockifier (execution engine used for block building/validation) and the Starknet OS (used for proving/re-execution) diverge on whether an undeclared or invalid class hash is accepted for `replace_class`:
- The OS could commit a state root that reflects a contract being "replaced" with an undeclared/invalid class hash that the blockifier would have rejected (transaction would revert in blockifier but the OS path lacks the same guard), leading to a wrong committed state root/block hash relative to what honest blockifier-based nodes computed, i.e., honest-node divergence between the block-building/validating engine and the OS re-execution/proving engine.
- This can result in a contract effectively becoming permanently associated with a non-existent class, since subsequent calls to it would be unable to resolve compiled code — a form of loss/freezing of the contract's functionality, and a mismatch with the "sane" invariant that a contract's class must always be declared.

The severity depends on whether such a discrepancy is actually exploitable to produce a state root mismatch (i.e., whether other layers, such as `contract_class_changes` dict validation elsewhere in the OS, would catch an undeclared class before finalization). This could not be fully confirmed from the available code excerpts, since the full "declare" bookkeeping and later cross-checks (e.g., `contract_class_changes` dict validation logic in `state.cairo` or `os.cairo`) were not exhaustively traced given tool budget constraints.

### Likelihood Explanation
Reachability is direct and requires no privilege: any contract that includes a call to `replace_class_syscall` (a standard, public Starknet syscall available to all Cairo 1 contracts) can trigger this code path with attacker-chosen `class_hash` values. The TODO comment in the source indicates the maintainers are aware this check is currently missing and planned as future work (dated 1/1/2026), which corroborates that the gap exists in the current code and has not yet been remediated.

### Recommendation
Add an explicit check in `execute_replace_class` (both the Cairo1 path in `syscall_impls.cairo` and the deprecated Cairo0 path in `deprecated_execute_syscalls.cairo`) that the supplied `class_hash` corresponds to a declared class before updating `contract_state_changes`, mirroring the check already performed in `blockifier/src/execution/syscalls/syscall_base.rs::replace_class` (`get_compiled_class` + Cairo1-only enforcement). This keeps the OS's accepted state transitions consistent with what the blockifier enforces during block building/validation, preventing any possibility of committing an invalid class replacement to the canonical state root.

### Proof of Concept
1. Deploy a Cairo1 account/contract that exposes an entry point calling `replace_class_syscall(class_hash)` (e.g., the existing test helper `test_replace_class` in `blockifier_test_utils/resources/feature_contracts/cairo1/cairo_steps_test_contract.cairo:201-203`, confirming this call is a normal, unprivileged, externally-invokable transaction path): [4](#0-3) 
2. Submit an ordinary `invoke` transaction from any unprivileged sender that calls this entry point with an arbitrary, never-declared `class_hash`.
3. In the blockifier execution path (used for block building/validation), this call reverts because `get_compiled_class` fails for the undeclared hash — confirmed by `blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29` (`undeclared_class_hash` test, asserting `"is not declared"`): [5](#0-4) 
4. In the Starknet OS Cairo implementation, the equivalent `execute_replace_class` function performs no such declared-class check before committing the `StateEntry` update in `contract_state_changes`, as shown at lines 900-914 of `syscall_impls.cairo`. This is a code-level asymmetry between the two execution engines for the same transaction/syscall semantics, and the source itself documents this gap via the inline `TODO`.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }

func execute_replace_class{contract_state_changes: DictAccess*, revert_log: RevertLogEntry*}(
    contract_address, syscall_ptr: ReplaceClass*

    alloc_locals;
    let class_hash = syscall_ptr.class_hash;

    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,

    );

    let revert_log = &revert_log[1];

}
