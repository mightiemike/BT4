## Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify report success despite a diverging position/state checkpoint root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the core state-integrity check used by `db-tool`'s `replay_on_archive` (`storage/db-tool/src/replay_on_archive.rs`) and by the chunk executor's `verify_execution` path (`execution/executor/src/chunk_executor/mod.rs`) to confirm that a locally re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed/authenticated on-chain. The function validates status, gas used, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` fields carried by `TransactionInfoV1`.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and checks four properties: execution status [2](#0-1) , gas used [3](#0-2) , write-set hash against `state_change_hash` [4](#0-3) , and event-root hash [5](#0-4) . It then returns `Ok(())` without ever comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, a gap the code itself documents: [6](#0-5) 

These checkpoint hashes are exactly the fields that authenticate the Sparse-Merkle/Jellyfish-Merkle state root (and, with the new "trading-native" position state, the `position_state_checkpoint_hash`) that is supposed to bind a `TransactionInfo` to the actual post-execution world state — see the field definitions in `TransactionInfoV0`/`TransactionInfoV1` [7](#0-6) .

This comparator is the sole state-divergence check used by two independent, unprivileged verification tools:
1. `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` on the result to decide pass/fail for the entire replay-verify run [8](#0-7) .
2. The chunk executor's `verify_execution`, used when verifying a replayed/backup chunk against expected `TransactionInfo`s, gas, write sets, and events [9](#0-8) .

Because neither call site independently checks the state/hot-state/position checkpoint hashes, if local re-execution produces a state root that diverges from the archived/committed `TransactionInfo` (e.g., due to a JMT/state-summary computation bug, a corrupted backup, or a bug introduced when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` features are enabled — see `do_state_checkpoint.rs`'s per-txn checkpoint hash computation [10](#0-9)  and the position-state root computation [11](#0-10) ), `ensure_match_transaction_info` will still return `Ok(())` and the verification tooling will report the transaction as successfully replayed.

The state-sync bootstrapper explicitly relies on `position_state_checkpoint_hash` as the authenticated target root for the "Position" state kind [12](#0-11) , confirming this field is treated elsewhere as a real, security-relevant proof-binding value — yet the one Rust-level "does execution match the persisted TransactionInfo" check skips it entirely.

### Impact Explanation
This falls squarely in the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "restore paths must not reinterpret committed data into a different ledger state" categories. `replay_on_archive` and chunk `verify_execution` are the primary tools operators and auditors use to confirm that an archived/backed-up ledger's committed state matches what local execution produces. A state root divergence (from a state-checkpoint computation bug, buggy restore, or corrupted backup data) that only manifests in `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` — without also changing the write set, events, gas, or status — will be silently accepted as "verified", masking a genuine ledger state divergence that could otherwise be a critical, hard-fork-class integrity bug. This directly undermines confidence in replay-verify results and restore validation, both explicitly listed proof/storage pivots.

### Likelihood Explanation
The gap is unconditional and always present in the current code — it doesn't require any attacker action, only a state-checkpoint-affecting bug or corruption to exist somewhere else in the stack (e.g., JMT computation, hot-state, or the newly introduced native-position feature gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). The developers' own `TODO(trading-native)` comment confirms this is a known, currently-unaddressed gap that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [6](#0-5) , indicating the feature may currently be off but the verification code path itself is already reachable and defective today for the existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields as well.

### Recommendation
Extend `ensure_match_transaction_info` to also assert that the locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present), and `position_state_checkpoint_hash` (when present) match the corresponding fields on `txn_info`, mirroring the existing `state_change_hash`/`event_root_hash` checks, before enabling any feature (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on this verification path for integrity guarantees.

### Proof of Concept
1. In `storage/db-tool/src/replay_on_archive.rs`, run `Verifier::verify` against an archive whose `TransactionInfo.state_checkpoint_hash` (or `position_state_checkpoint_hash`) was corrupted or produced by a buggy state-checkpoint computation, while write set, events, gas, and status remain byte-identical to what local re-execution produces.
2. `execute_and_verify` calls `executed_outputs[idx].ensure_match_transaction_info(...)` [13](#0-12) , which only compares status, gas, write-set hash, and event-root hash.
3. Because the checkpoint-hash fields are never compared, the call returns `Ok(())`, `execute_and_verify` reports no error, and `Verifier::run` reports zero failed transactions — even though the archived ledger's authenticated state root diverges from what local execution actually computed.

Note: I was unable to trace whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` are currently enabled on mainnet, so the severity of the `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` portion of this gap may be gated by feature flags; the `state_checkpoint_hash` (V0-era, always active) omission, however, applies unconditionally today.

    fn compute_position_checkpoint(
        execution_output: &ExecutionOutput,
        parent: Option<&LedgerWithSummary<PositionStateWithSummary>>,
        persisted: &ProvablePositionStateSummary,
        known_position_state_checkpoints: Option<Vec<Option<HashValue>>>,
    ) -> Result<(
        LedgerWithSummary<PositionStateWithSummary>,
        Vec<Option<HashValue>>,
    )> {
        let _timer = OTHER_TIMERS.timer_with(&["get_position_checkpoint_hashes"]);

        let num_txns = execution_output.to_commit.len();
        let first_version = execution_output.first_version;
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();
        let base_summary = persisted.summary();
        // No in-memory parent at genesis / first block after enabling: seed
        // from the pre-committed position tip (covers committed writes the
        // merklized snapshot may lag).
        let parent_latest =
            parent.map_or_else(|| persisted.base().latest().clone(), |p| p.latest().clone());
        let parent_last_checkpoint = parent.map_or_else(
            || persisted.base().last_checkpoint().clone(),
            |p| p.last_checkpoint().clone(),
        );

        // Empty chunk: nothing to extend (avoids the `num_txns - 1` underflow).
        if num_txns == 0 {
            let summary = LedgerWithSummary::from_latest_and_last_checkpoint(
                parent_latest,
                parent_last_checkpoint,
            );
            return Ok((summary, vec![]));
        }

        // Collapse position writes (latest-per-key) over a version range into
        // SMT leaf updates.
        let collect = |range: std::ops::Range<usize>| -> Vec<(HashValue, PositionSlot)> {
            let mut latest: HashMap<HashValue, PositionSlot> = HashMap::new();
            for i in range {
                for (key, op) in execution_output.to_commit.transaction_outputs[i]
                    .write_set()
                    .native_position_iter()
                {
                    let value_hash = op.as_write_op().as_state_value_opt().map(StateValue::hash);
                    latest.insert(key.hash(), PositionSlot {
                        state_key: key.clone(),
                        value_hash,
                        value: None,
                    });
                }
            }
            latest.into_iter().collect()
        };

        let (new_latest, new_last_checkpoint) = if let Some(ci) = last_checkpoint_index {
            let checkpoint_version = first_version + ci as u64;
            let new_ckpt = parent_latest.extend(
                checkpoint_version,
                collect(0..ci + 1),
                base_summary,
                persisted,
            )?;
            if ci + 1 == num_txns {
                (new_ckpt.clone(), new_ckpt)
            } else {
                let last_version = first_version + num_txns as u64 - 1;
                let new_latest = new_ckpt.extend(
                    last_version,
                    collect(ci + 1..num_txns),
                    base_summary,
                    persisted,
                )?;
                (new_latest, new_ckpt)
            }
        } else {
            // No checkpoint in this chunk: only the latest advances.
            let last_version = first_version + num_txns as u64 - 1;
            let new_latest = parent_latest.extend(
                last_version,
                collect(0..num_txns),
                base_summary,
                persisted,
            )?;
            (new_latest, parent_last_checkpoint)
        };

        // Per-tx hash vector + known-hash validation (shared with main/hot state).
        let hashes = Self::get_state_checkpoint_hashes(
            execution_output,
            known_position_state_checkpoints,
            new_last_checkpoint.root_hash(),
            "position_state",
        )?;

        let summary =
            LedgerWithSummary::from_latest_and_last_checkpoint(new_latest, new_last_checkpoint);
        Ok((summary, hashes))
