### Title
Unbounded duplicate accumulation in `KVSessionStorage`'s shop-session index causes accounting corruption and DoS of session lookups/token exchange - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage.addShopIds` appends a session id to the per-shop id list on every `storeSession()` call without checking whether that id is already present in the list, unlike the sibling Redis implementation which explicitly guards against duplicates.

### Finding Description
`storeSession` unconditionally calls `addShopIds(session.shop, [session.id])`, which reads the existing shop→id list from KV and appends the new id(s) with a plain spread, with no de-duplication check: [1](#0-0) [2](#0-1) 

Compare this to `RedisSessionStorage.addKeyToShopList`, which explicitly checks `!idKeysArray.includes(idKey)` before pushing: [3](#0-2) 

`storeSession` is invoked repeatedly for the *same* session id as part of the normal, unprivileged authenticated request flow — specifically the token-exchange strategy used by embedded apps, which re-stores the offline/online session every time the current session is missing or inactive (e.g., an online session token expiring, a stale/invalidated offline token, or a transient storage read failure): [4](#0-3) [5](#0-4) 

Because the offline session id is deterministic (`offline_<shop>`) and the online session id is deterministic (`<shop>_<userId>`), every re-exchange for the same shop/user pushes the identical id into the shop's KV list again, growing it monotonically. This directly mirrors the reported bug class: pushing the same identifier into an accounting/index list without existence checks inflates the derived collection (here, the list backing `findSessionsByShop`) instead of a financial total.

`findSessionsByShop` then loads a session once per entry in that list, so a shop with N duplicate entries yields N duplicate `Session` objects for what is really one session: [6](#0-5) 

`findSessionsByShop`/`deleteSessions` are relied upon by app-level logic that determines whether a shop is "installed" and drives uninstall cleanup: [7](#0-6) 

### Impact Explanation
- **Accounting/consistency corruption**: `findSessionsByShop` returns duplicate `Session` entries for a single logical session, corrupting any logic that counts, iterates, or aggregates over a shop's sessions (installation checks, bulk cleanup, session listing).
- **Unbounded storage growth / DoS of the auth path**: because the duplicate check is missing, the per-shop id array grows without bound on every normal token-exchange refresh cycle over the life of the merchant's installation. Each `storeSession`/`addShopIds` call re-reads, re-serializes, and re-writes an ever-larger JSON array, degrading latency on every authenticated request and eventually risking write failures once the value approaches the underlying KV value-size limit — effectively a denial of service against `storeSession`/token-exchange (an auth handler) for that shop, requiring no privileged action, just normal continued app usage.
- No malicious actor or elevated privilege is required; a single merchant's ordinary, repeated authenticated use of the embedded app is sufficient to trigger the growth.

### Likelihood Explanation
High for long-lived installations using `KVSessionStorage` (e.g., Cloudflare Workers deployments) combined with the token-exchange auth strategy, since every session refresh (online token expiry, offline token invalidation/retry) re-triggers `storeSession` for the same deterministic id, and nothing in the code path ever deduplicates or resets the list outside of `deleteSession`, which is not called during normal refresh.

### Recommendation
Mirror the Redis implementation's guard in `addShopIds`: check `shopIds.includes(id)` (or use a `Set`) before appending, so repeated `storeSession` calls for the same session id are no-ops with respect to the shop index:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Deploy an app using `KVSessionStorage` with the token-exchange auth strategy (e.g., `shopify-app-remix`/`shopify-app-react-router` on Cloudflare Workers).
2. As a normal merchant, load the embedded app; `performTokenExchange`/`createTokenExchangeStrategy.authenticate` stores the offline session via `storeSession(offlineSession)` with id `offline_<shop>`.
3. Let the stored session become inactive (or force it, e.g. via `WITHIN_MILLISECONDS_OF_EXPIRY` window) and reload the app; the same `offline_<shop>` id is stored again via `storeSession`.
4. Inspect the KV entry at key `shop:<shop>` — it now contains `["offline_<shop>", "offline_<shop>"]` (duplicated), growing by one entry every refresh cycle with no bound.
5. Call `findSessionsByShop(shop)` — it returns two identical `Session` objects instead of one, demonstrating the inflated/duplicated accounting; repeating step 3 indefinitely demonstrates unbounded growth toward storage/performance DoS.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

      await this.sessionStorage.findSessionsByShop!(shopDomain);
