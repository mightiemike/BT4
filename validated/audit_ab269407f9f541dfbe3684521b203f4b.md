### Title
Full energy-fee billing on `OUT_OF_TIME` results driven by non-consensus, per-node `minTimeRatio`/`maxTimeRatio` config - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
Like the reported issue where a solver is billed gas costs for conditions outside their control (bundler-chosen deadline/gas price), java-tron's `VMActuator` bills a transaction sender the full energy fee for an `OUT_OF_TIME` execution outcome even when that outcome is determined by a locally-configurable CPU-time-ratio parameter rather than anything the sender can control.

### Finding Description
The CPU time budget given to a transaction during execution/verification is scaled by `getCpuLimitInUsRatio()`: [1](#0-0) 

For the "self-witness or other witness or fullnode verifies block" path, the ratio applied is either `CommonParameter.getInstance().getMinTimeRatio()` (if the already-recorded `contractResult` is `OUT_OF_TIME`) or `getMaxTimeRatio()` otherwise. These two values are locally configurable, per-node parameters (`--min-time-ratio` / `--max-time-ratio`, defaulting to `0.0` / `5.0`), not on-chain committee-governed parameters: [2](#0-1) [3](#0-2) 

`checkCPUTimeLimit()` in `Program` throws `Exception.notEnoughTime(opName)` once the wall-clock time exceeds `vmShouldEndInUs`, which is derived from this ratio: [4](#0-3) [5](#0-4) 

Whether a transaction ends as `OUT_OF_TIME` therefore depends on real-time server load/CPU speed of whichever witness happened to pack or re-verify it, and on that node's local `minTimeRatio`/`maxTimeRatio` settings — factors entirely outside the transaction sender's/contract caller's control, analogous to a bundler unilaterally setting a deadline or gas price that a solver cannot influence.

Despite this, `ReceiptCapsule.payEnergyBill()` charges the sender the full energy fee for the energy consumed up to the timeout, deducting it from the account balance exactly as it would for any other failed/successful execution, with only a narrow special case (routing the fee to the black hole / burn instead of the transaction fee pool) rather than reducing or waiving the fee: [6](#0-5) 

Additionally, when a witness replays its own already-signed block, it doesn't even re-run the VM if the previously-recorded result was `OUT_OF_TIME` — it unconditionally spends all remaining energy and throws, baking in the original (potentially load-dependent) verdict as final: [7](#0-6) 

### Impact Explanation
Senders/callers can be billed the full energy fee (in TRX, burned or sent to black hole) for a transaction that fails purely because of the timing/load characteristics of the specific node that happened to pack or verify it, not because of any fault in the transaction's own gas usage relative to its `feeLimit`/`energyLimit`. Because `minTimeRatio`/`maxTimeRatio` are node-local settings rather than consensus parameters, different nodes can in principle compute a different `contractResult` for what is otherwise a borderline-timing transaction, creating an accounting-fairness problem and a potential inconsistency vector between how a producing node and a verifying node price the same transaction (energy fee charged and destination of the fee — burn/black hole vs. fee pool — both depend on whether the local recomputation lands on `OUT_OF_TIME`).

### Likelihood Explanation
This is reachable by any ordinary contract-call transaction (`TriggerSmartContract`) broadcast to the network; no privileged role is required. The condition is most likely to manifest for transactions whose energy usage sits close to `maxCpuTimeOfOneTx` under load, which is a normal, unprivileged occurrence during network congestion or on slower witness nodes — not an exotic edge case.

### Recommendation
- Avoid charging the full energy fee (or route it back to the sender/fee pool rather than burning/black-holing it) when the failure reason is `OUT_OF_TIME`, since this outcome is not attributable to the sender's contract logic exceeding its declared `energyLimit`/`feeLimit`, but to node-local timing budgets.
- Make the CPU-time ratio parameters (`minTimeRatio`/`maxTimeRatio`) either fixed/deterministic constants or committee-governed on-chain parameters, so that `OUT_OF_TIME` determination (and its fee consequences) does not vary by node configuration.
- Consider tightening the shortcut in `VMActuator.execute()` (lines 178-190) so that a previously recorded `OUT_OF_TIME` from the packing witness is not mechanically re-applied as a foregone conclusion on replay, without re-validating against the current node's own consistent, deterministic budget.

### Proof of Concept
Not applicable in the traditional sense (no exploit primitive is being demonstrated); the concern is a design/fairness issue reachable by any normal `TriggerSmartContract` transaction whose execution time is close to `maxCpuTimeOfOneTx`. Existing repository tests already exercise and assert on this exact billing behavior for `OUT_OF_TIME`, confirming the mechanics described above: [8](#0-7) [9](#0-8)

  private double getCpuLimitInUsRatio() {

    double cpuLimitRatio;

    if (ExecutorType.ET_NORMAL_TYPE == executorType) {
      // self witness generates block
      if (blockCap != null && blockCap.generatedByMyself
          && !blockCap.hasWitnessSignature()) {
        cpuLimitRatio = 1.0;
      } else {
        // self witness or other witness or fullnode verifies block
        if (trx.getRet(0).getContractRet() == contractResult.OUT_OF_TIME) {
          cpuLimitRatio = CommonParameter.getInstance().getMinTimeRatio();
        } else {
          cpuLimitRatio = CommonParameter.getInstance().getMaxTimeRatio();
        }
      }
    } else {
      // self witness or other witness or fullnode receives tx
      cpuLimitRatio = 1.0;
    }

    return cpuLimitRatio;
  }
