### Title
Uncontrolled Memory Allocation via Unbounded `SignedTransaction` Borsh Decode in JSON-RPC (`decode_signed_transaction`) - ([File: chain/jsonrpc/src/api/transactions.rs])

### Summary
The JSON-RPC transaction-submission path decodes an attacker-supplied base64 string directly into a `SignedTransaction` via `borsh` with no upper bound on the encoded size, unlike the equivalent P2P network path which was explicitly hardened against exactly this class of attack.

### Finding Description
`decode_signed_transaction` in `chain/jsonrpc/src/api/transactions.rs` is the parsing entry point used by `RpcSendTransactionRequest::parse` and `RpcTransactionStatusRequest::parse` (used by `send_tx`, `send_tx_commit`, `broadcast_tx_async`, `broadcast_tx_commit`, and `tx` RPC methods): [1](#0-0) 

It base64-decodes the caller-supplied string and immediately calls `SignedTransaction::try_from_slice(&bytes)` with no pre-check on `bytes.len()` against any size limit. The same pattern exists in the `serde::Deserialize` impl for `SignedTransaction` used elsewhere (e.g. Rosetta RPC, `TransactionInfo`): [2](#0-1) [3](#0-2) 

By contrast, the P2P network layer's own proto-to-struct conversion for the exact same `SignedTransaction` type explicitly guards against this: it bounds the encoded size *before* invoking borsh decode, with an in-code comment stating the rationale is to prevent "a maliciously inflated peer payload" from "forc[ing] a large allocation at decode time": [4](#0-3) [5](#0-4) [6](#0-5) 

The network layer even has a regression test (`transaction_size_gate`) specifically documenting that "an oversized body is rejected before it is Borsh-decoded, so the inflated nested-action `Vec` is never materialized at decode time": [7](#0-6) 

The actual `max_transaction_size` protocol limit check only happens *after* the transaction has already been fully deserialized into memory, inside `ValidatedTransaction::check_valid_for_config`: [8](#0-7) 

This means the RPC ingestion path lacks the same decode-time allocation gate that the network layer deliberately added. My search of `chain/jsonrpc/**` found no HTTP body-size limit or middleware configured on the JSON-RPC server (`max_body_size`, `max_request_size`, etc. all returned no matches), so there is no other layer confirmed to bound the payload size before it reaches `decode_signed_transaction`. This mirrors CVE-2021-27906's root cause: a length/structure-controlled field is used to drive allocation before the object's semantic validity (including size limits) is checked.

### Impact Explanation
An unauthenticated RPC caller can submit `send_tx`/`broadcast_tx_async`/`broadcast_tx_commit`/`tx` requests whose `signed_tx_base64` field decodes to an oversized or maliciously structured borsh payload (e.g., deeply nested `Vec<Action>` with an inflated but still-parseable structure), forcing a large heap allocation on every request before `max_transaction_size` is ever checked. Because each RPC-handler thread (`RpcHandlerActor`) processes requests independently and the check only trips after allocation, an attacker can repeatedly submit such requests to exhaust node memory. This is resource-exhaustion / denial-of-service against a validator or RPC node's transaction-admission path, reachable purely from an unprivileged RPC caller — no signature validity, balance, or nonce correctness is required to reach the vulnerable code (decoding happens before signature verification and before any state access).

### Likelihood Explanation
High reachability: it requires a single unauthenticated HTTP JSON-RPC request with a crafted base64 string; no special privileges, staking, or prior on-chain state are needed. The lack of any discovered body-size limiter on the JSON-RPC HTTP server increases likelihood that a large payload reaches the decode call unimpeded.

### Recommendation
Apply the same `try_from_slice_with_limit`-style guard used in `chain/network/src/network_protocol/proto_conv/util.rs` to `decode_signed_transaction` in `chain/jsonrpc/src/api/transactions.rs` and to the `serde::Deserialize` impl for `SignedTransaction` in `core/primitives/src/transaction.rs`, rejecting any base64-decoded byte length above a small constant multiple of `max_transaction_size` (mirroring `MAX_TRANSACTION_SIZE_BYTES` = 16 MiB) before invoking borsh deserialization. Additionally, confirm/add an HTTP-level request body size cap on the JSON-RPC server as defense in depth.

### Proof of Concept
1. Construct a base64 string that borsh-decodes to a `SignedTransaction` with an oversized `Transaction::actions` vector (e.g., many `FunctionCall` actions with large `args`), well beyond `max_transaction_size` (default ~1.5–4 MiB per config snapshots), but keep the encoding syntactically valid so `try_from_slice` succeeds and allocates the full structure in memory.
2. POST to the JSON-RPC endpoint: `{"jsonrpc":"2.0","id":"1","method":"broadcast_tx_async","params":["<oversized_base64>"]}`.
3. Observe that `decode_signed_transaction` (`chain/jsonrpc/src/api/transactions.rs:71-76`) allocates and fully materializes the oversized transaction object in memory before `check_valid_for_config`'s `max_transaction_size` check (`core/primitives/src/transaction.rs:377-384`) rejects it.
4. Repeat concurrently/at high rate to demonstrate memory pressure/DoS on the RPC node, analogous to the PDFBox OOM trigger from a crafted file.

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}
