**Rationale:** The premise depends on a hypothetical, unbuilt "batching harness" that would zip `fixed_base_msms::Trait::batch_normalize`'s output against a list of DKG session identifiers to construct an authenticated API response. No such caller exists in the codebase. `batch_normalize` (and its callers `normalize_output`/`normalize_outputs`) is purely an internal cryptographic primitive used inside `crates/aptos-dkg/src/pcs/univariate_kzg.rs`, `univariate_hiding_kzg.rs`, `chunked_elgamal.rs`, and `chunked_scalar_mul.rs` to batch-normalize MSM outputs (projective → affine points) for a *single* homomorphism's own codomain shape [1](#0-0) . All call sites invoke it with a single, self-contained `Codomain`/`CodomainShape` structure that carries its own ordering derived from one homomorphism's `msm_terms`, not from an externally supplied, independently-indexed list of DKG session identifiers [2](#0-1) .

There is no code in the DKG on-chain module (`dkg.move`), the DKG session state types (`types/src/dkg/randomness_dkg.rs`), or any API/response layer that pairs `batch_normalize`'s output with a list of session identifiers to build a version-bound authenticated response [3](#0-2) . DKG session state and completion binding are handled separately, through `dkg::finish`/`DKGState.last_completed`/`in_progress` fields keyed by `dealer_epoch`/`target_epoch`, not through any MSM-batch-normalize/session-identifier zip [4](#0-3) .

Since the described "batching harness" and "API response object" that zips `batch_normalize` output against session identifiers does not exist anywhere in the reviewed scope (production proof, storage, restore, or authenticated-response code), the exploit path is speculative rather than grounded in an actual unprivileged-input-reachable code path. Per the decision standard, this does not meet the bar for acceptance.
