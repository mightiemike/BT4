### Title
Cross-tenant session hijack via unsigned `X-Shopify-Shop-Domain` header in fulfillment-service authentication - (File: packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts)

### Summary
The Templedao exploit's root cause was a function that trusted an attacker-supplied identifier (the beneficiary address) without validating that it actually corresponded to the caller, letting an unprivileged caller redirect fund movement to itself. The equivalent pattern exists in `authenticateFulfillmentServiceFactory`: the HMAC signature is validated over the raw body only, while the `shop` value used to fetch and authenticate with another merchant's offline session comes from an **unsigned header** (`X-Shopify-Shop-Domain`). Any actor holding one valid signed payload can substitute a different shop domain header and obtain a session/admin client scoped to that other shop.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC solely over `rawBody` and compares it to the value in the `X-Shopify-Hmac-Sha256` header — no other header (including the shop-identifying header) is part of the signed material: [1](#0-0) 

`shopify.fulfillmentService.validate` delegates directly to this factory with `HmacValidationType.FulfillmentService`, so it inherits the same "body-only" signature scope: [2](#0-1) 

`authenticateFulfillmentServiceFactory` then reads the shop identity from the request header **after** validation succeeds, and immediately uses it to look up and refresh that shop's offline session, returning an authenticated `admin` API client bound to it: [3](#0-2) [4](#0-3) 

The identical pattern exists in the React Router package: [5](#0-4) 

Because the app's HMAC secret (`apiSecretKey`) is a single, app-wide secret shared across every installed shop (not a per-shop secret), a merchant who has installed the app receives real, validly-signed fulfillment-order-notification requests for their own shop. Since the domain header is not covered by the signature, that merchant can capture one legitimate `(body, hmac)` pair and replay it to the app's endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `validate()` still reports `valid: true` (the body/HMAC pair is legitimate), and `authenticate()` uses the attacker-controlled domain header to load and return the victim's offline session and an authenticated Admin API client — a classic confused-deputy: the "signed" part of the message (analogous to Templedao's LP balance amount) is correct, but the "beneficiary" (shop/account, analogous to Templedao's caller-supplied migration address) is unauthenticated and attacker-controlled.

### Impact Explanation
An attacker who is merely a merchant with the app installed (unprivileged relative to other tenants) can obtain another shop's cached offline access token indirectly by causing the library to hand back an `admin` client scoped to the victim shop's session. This is a cross-tenant access vulnerability: reading/writing data via the Admin API as another merchant, using only the attacker's own valid app-signed webhook traffic and a header value they fully control.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that expose a fulfillment-service endpoint: it requires the attacker to be an installed merchant (achievable by anyone who installs a public app), capture one legitimately delivered request (trivial, since it's delivered to their own server), and replay it with a different `X-Shopify-Shop-Domain` value pointing at any other shop that has also installed the app and has a stored offline session. No cryptographic secret needs to be broken — only the unsigned header needs to be changed.

### Recommendation
Bind the shop/session-selecting header(s) into the HMAC-signed material (or otherwise cryptographically verify that the shop domain used to select the session matches data that Shopify actually signed), rather than trusting `X-Shopify-Shop-Domain`/`ShopifyHeader.Domain` post-hoc. At minimum, cross-check the header against a shop identifier embedded in the validated body payload before calling `ensureValidOfflineSession`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures a fulfillment service, causing Shopify to POST a legitimate `fulfillment_order_notification` request to the app with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's `apiSecretKey`.
2. Attacker captures `(rawBody, hmac)` from that legitimate delivery.
3. Attacker sends a new POST request directly to the app's fulfillment-service endpoint, reusing the same `rawBody`/`X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `api.fulfillmentService.validate` returns `valid: true` because only `rawBody` is checked [6](#0-5) .
5. `authenticate()` reads `shop = 'victim-shop.myshopify.com'` from the header and calls `ensureValidOfflineSession(params, shop)`, returning `victim-shop`'s session and an authenticated `admin` client to the attacker's request handler [7](#0-6) .

```typescript
export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
```

```typescript
import {ConfigInterface} from '../base-types';
import {validateHmacFromRequestFactory} from '../utils/hmac-validator';
import {
  HmacValidationType,
  ValidateParams,
  ValidationInvalid,
  ValidationValid,
} from '../utils/types';

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    return validateHmacFromRequestFactory(config)({
      type: HmacValidationType.FulfillmentService,
      rawBody,
      ...adapterArgs,
    });
  };
}
```
