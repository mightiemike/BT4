### Title
Panic-inducing out-of-bounds slice access in stateless-compression `decompress` when parsing OS state-diff output - (File: `crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs`)

### Summary
`decompress` reconstructs a state diff from a Felt stream produced by the OS/prover output. It slices and indexes several `Vec<usize>`/`Vec<Felt>` collections (`header[2..2+N_UNIQUE_BUCKETS]`, `unique_value_bucket_lengths[i]`, `all_values[*offset]`, `unique_values[*ptr]`, `bucket_offset_trackers[bucket_index]`) whose lengths and index values are derived directly from header fields taken from the (attacker-influenced) compressed felt stream, with no bounds validation before indexing. [1](#0-0) 

### Finding Description
`decompress` is invoked from `PartialOsStateDiff::try_from_output_iter`, which is used to parse the OS output (state diff) that is fed by external data (the prover/OS output stream), including when re-executing/verifying `PartialOsStateDiff` blocks. [2](#0-1) 
Inside `decompress`, `header` is parsed from the compressed stream with `unpack_chunk_to_usize`, and then slice/index operations use these attacker-controlled values directly:
- `header[2..2 + N_UNIQUE_BUCKETS]` assumes `header.len() >= 2 + N_UNIQUE_BUCKETS`.
- `unique_value_bucket_lengths[0..5]` assumes the vector has exactly 6 entries.
- `all_values[*offset]` and `unique_values[*ptr]` assume `offset`/`ptr` are within bounds of `all_values`/`unique_values`.
- `bucket_offset_trackers[bucket_index]` assumes `bucket_index < bucket_offset_trackers.len()`.

None of these are validated before indexing, unlike the corresponding Cairo implementation (`compression.cairo`), which explicitly documents and enforces bucket-offset bounds via `dict_squash`/`dict_update` verification (see comment "Verify there was no out-of-bound access to `all_values` array..."). [3](#0-2) 

In safe Rust, an out-of-bounds index does not cause memory corruption (unlike the C-style `ordnung`/`compact::Vec` bug) — it triggers an immediate panic. So the practical effect here is a panic/crash rather than a memory-safety violation.

### Impact Explanation
If this path is reachable with attacker/prover-controlled data (e.g. a malformed `PartialOsStateDiff` felt stream processed during OS output parsing/re-execution), a crafted header/bucket-length/pointer value can force a Rust panic (index out of bounds), crashing the process that parses OS output. Depending on where this parsing runs (aggregator, OS re-execution/verification tooling), this could halt processing of new blocks/state diffs, which would qualify as "network unable to confirm new transactions" if it runs in a sequencer-critical path.

However, I could not fully confirm within available context whether `PartialOsStateDiff::try_from_output_iter` is invoked on a path reachable by an untrusted transaction sender/contract deployer/L1 message sender at consensus time (vs. only by the block proposer/prover's own generated output, or by downstream tooling like the aggregator that consumes trusted OS output). The function itself is also marked `#[allow(dead_code)]`, and its only exercised caller found is `os_output_types.rs`, whose call sites (aggregator/consumer of OS output) were not fully traced in this session.

### Likelihood Explanation
Low-to-medium confidence: the vulnerable indexing logic clearly exists and lacks bounds checks, but the reachability from a single unprivileged transaction/L1 message was not conclusively established — this content is OS/prover-generated output, not a raw user-submitted structure, so it is unclear whether an unprivileged actor can control the bytes fed into `decompress`.

### Recommendation
Add explicit bounds checks (returning an error instead of panicking) before all slice/index operations in `decompress`, mirroring the `dict_squash` bounds verification performed in the Cairo reference implementation, so malformed or malicious input results in a graceful `Result::Err` rather than a panic.

### Proof of Concept
Not fully constructible without confirming the exact reachable entry point and trust boundary of the felt-stream input to `PartialOsStateDiff::try_from_output_iter`; a concrete PoC would require crafting a `header` felt sequence with `unique_value_bucket_lengths` or `n_repeating_values`/pointer values exceeding the actual data length, causing `unique_values[*ptr]` or `bucket_offset_trackers[bucket_index]` to panic — but I could not verify from the available index whether this input is attacker-reachable at the required trust boundary.
