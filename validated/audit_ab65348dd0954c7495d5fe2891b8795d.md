## Title
Vote account `pending_delegator_rewards` distributed by current-epoch effective stake without decrementing the pooled balance, allowing late/large stake delegators to dilute long-term delegators' unclaimed block rewards - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The GLP Strategy bug describes a "pooled unclaimed rewards" balance whose distribution is calculated from a share ratio at withdrawal/deposit time, without properly accounting for what each depositor actually contributed to earning that pool. Agave's SIMD‑0123 block-revenue-sharing mechanism has a structurally identical pattern: a vote account accumulates a single pooled `pending_delegator_rewards` balance (via `deposit_delegator_rewards`, an instruction reachable by any signer/ordinary transaction) [1](#0-0) , and at each epoch's reward calculation, this whole pool is split among *currently* effective delegators in proportion to their live stake at that moment, not in proportion to how long they contributed to the pool [2](#0-1) .

### Finding Description
`calculate_block_reward` computes each stake account's share of a vote account's `pending_delegator_rewards` as:
```
(pending_delegator_rewards * stake / total_active_stake).min(pending_delegator_rewards)
``` [3](#0-2) 

`pending_delegator_rewards` is a single running total on the vote account, incremented by anyone via `deposit_delegator_rewards` (a permissionless system-transfer-then-state-update instruction) [1](#0-0) . It represents lamports "owed" to delegators of that vote account but not yet apportioned to any specific stake account — directly analogous to Tapioca's unclaimed/undistributed strategy rewards sitting in the GLP strategy contract.

The apportionment logic uses `total_active_stake` from `RewardEpochDelegatedStakes`, which is the *effective* delegated stake to the vote account for the rewarded epoch [4](#0-3) . Because a stake account's proportional claim depends purely on `stake / total_active_stake` at the moment of calculation, and not on any accounting of *when* the pool was funded relative to *when* the stake became active, a delegator who activates stake to a vote account can claim a proportional share of `pending_delegator_rewards` that accumulated entirely before their stake existed, so long as their stake is "effective" as of `rewarded_epoch`. Existing tests only exercise the isolated arithmetic of `calculate_block_reward` with a fixed, pre-set `pending_delegator_rewards` value [5](#0-4)  and do not verify that stakers who joined after the pool was funded are excluded or given a time-weighted share — mirroring the GLP Strategy's `_currentBalance` failing to distinguish "rewards that existed before this depositor arrived" from the pool total.

I was unable to fully locate/verify the exact code path that decrements `pending_delegator_rewards` after a partition is distributed (searches for a subtraction of the distributed amount from `pending_delegator_rewards` after `distribute_epoch_rewards_in_partition` did not return a match within the available iterations), so I cannot confirm whether under-distribution/double counting across partial partitioned distributions (multiple blocks) could compound this further. This is a gap in my analysis that would need direct code confirmation (e.g., in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` or `programs/vote/src/vote_state/mod.rs`) before treating it as separately confirmed.

### Impact Explanation
If confirmed, this allows an attacker to:
1. Observe (or predict) that a vote account has accumulated a large `pending_delegator_rewards` balance (deposited by the validator or protocol as block-revenue-sharing).
2. Delegate/redelegate a large stake to that vote account, wait for the stake to become effective (one warm-up epoch), and then receive a proportional share of `pending_delegator_rewards` at the next reward calculation — a pool that was funded by revenue attributable to prior epochs/prior delegators, not the attacker's own participation.
3. This dilutes rewards owed to long-term delegators and effectively lets a large, late depositor "front-run" a portion of a shared reward pool, similar to Tapioca's share-price manipulation — a concrete lamport-value misallocation reachable from ordinary (non-privileged) stake-delegate transactions plus a permissionless `DepositDelegatorRewards` instruction.

Because the mechanism (SIMD-0123 / block revenue sharing) is currently feature-gated (`block_revenue_sharing`, `custom_commission_collector`, `commission_rate_in_basis_points` must all be active) [6](#0-5) , real-world exploitability depends on those features being enabled on a live cluster.

### Likelihood Explanation
Requires: (a) the relevant SIMD-0123 features active, (b) a vote account with meaningful `pending_delegator_rewards` accumulated (fundable by anyone via `deposit_delegator_rewards`, even the attacker), and (c) the attacker being able to delegate/redelegate stake and wait one epoch's warm-up. All of these are achievable with ordinary, unprivileged transactions and no special permissions, making the likelihood non-trivial once the feature set is enabled, though it is currently limited by feature-gate rollout status.

### Recommendation
Track `pending_delegator_rewards` contributions with a time/epoch-weighted or per-depositor accounting mechanism (analogous to `credits_observed` for inflation rewards) so that only stake effective *during the period the rewards accrued* is eligible to claim them, rather than using a single mutable pool balance split by point-in-time stake ratio. At minimum, add tests that confirm delegators who activate stake to a vote account strictly after `pending_delegator_rewards` accumulation are excluded (or given a correctly time-weighted, not full pro-rata, share) from that portion of the pool, and formally verify the decrement/consumption logic for `pending_delegator_rewards` across partitioned, multi-block distribution.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to unresolved decrement-path confirmation):
1. Fund a vote account's `pending_delegator_rewards` via `DepositDelegatorRewards` (permissionless) to a large value, e.g. 1000 SOL, while it currently has only a small amount of effective stake delegated to it.
2. Attacker delegates a very large stake amount to that vote account (dwarfing the existing effective stake) and waits one epoch for warm-up so it becomes part of `total_active_stake` for `rewarded_epoch`.
3. At the next epoch-boundary reward calculation, `calculate_block_reward` computes attacker's share as `pending_delegator_rewards * attacker_stake / total_active_stake`, giving the attacker the large majority of the 1000 SOL pool despite having contributed none of the "reward-generating" activity [3](#0-2) .
4. Attacker then deactivates/withdraws the stake, retaining the diluted reward share taken from long-term delegators.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
