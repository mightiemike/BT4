### Title
Unvalidated `deltaStage` value in transmission config collapses `oneAtATime` scheduling into simultaneous multi-peer execution - ([File: core/capabilities/transmission/transmission.go])

### Summary
`ExtractTransmissionConfig` parses the attacker-supplied `deltaStage` string with `time.ParseDuration` without any sign or bound validation, and this raw `time.Duration` is later multiplied by peer position and passed straight into `time.After`/`time.NewTimer` in `LocalTargetCapability.Execute` and the remote client request path. A negative `deltaStage` causes every peer's computed delay to be `<= 0`, which fires immediately in Go's `time.After`, defeating the intended per-peer staggering ("oneAtATime") and making all workflow DON members invoke the underlying target capability at effectively the same time.

### Finding Description
`ExtractTransmissionConfig` (`core/capabilities/transmission/transmission.go:33-60`) unwraps `Config.Underlying["deltaStage"]` and calls `time.ParseDuration(tc.DeltaStage)`, accepting any syntactically valid Go duration string, including negative values (e.g. `"-1h"`) or extremely large ones, with no clamping or range check. [1](#0-0) 

This `TransmissionConfig.DeltaStage` flows into `GetPeerIDToTransmissionDelaysForConfig` → `delayFor`, which computes `result := time.Duration(i) * deltaStage` for each peer position `i` in the schedule: [2](#0-1) 

With schedule `oneAtATime`, the schedule slots peers at positions `0..N-1`, and the intended behavior is staggered delays `0, deltaStage, 2*deltaStage, ...`. If `deltaStage` is negative, every non-zero position yields a negative `time.Duration`. Both `LocalTargetCapability.Execute` (`time.After(delay)`) and the remote client request path (`time.NewTimer(delay)`) treat non-positive durations as "fire immediately" — this is documented Go `time` package behavior. As a result, all DON members with a non-empty delay entry execute the target capability essentially simultaneously instead of being serialized. [3](#0-2) [4](#0-3) 

The `schedule` field itself is bounded — `createTransmissionSchedule` only accepts the two known enum strings and errors otherwise (`core/capabilities/transmission/transmission.go:122-134`), so the attacker cannot inject an arbitrary schedule shape. But there is no equivalent validation of `deltaStage`, so the intended anti-collision/staggering property of `oneAtATime` can be nullified purely via the numeric magnitude/sign of `deltaStage`, which is fully attacker-controlled through the workflow/job spec's target step `Config`.

For the "extremely large delay" half of the question: an oversized `deltaStage` does increase wait time for later peers, but `LocalTargetCapability.Execute` selects on `ctx.Done()` concurrently with `time.After(delay)`, so the call returns with `ctx.Err()` once the context deadline is hit rather than blocking indefinitely; this bounds the DoS impact to normal execution-timeout failure rather than resource exhaustion. [5](#0-4) 

### Impact Explanation
A malicious/careless workflow author can set `Config.Underlying["deltaStage"]` to a negative duration string for a target capability step, forcing all DON member nodes' `LocalTargetCapability.Execute` (and the equivalent remote executable client path) to submit their on-chain target transaction near-simultaneously rather than in the serialized order the `oneAtATime` schedule is designed to enforce. This defeats the purpose of the scheduling mechanism (avoiding redundant/duplicate submissions and wasted gas from multiple nodes racing to write the same report on-chain), and can lead to duplicate on-chain write attempts (e.g., duplicate CCIP/OCR report submissions) and increased gas expenditure/contention across the capability DON.

### Likelihood Explanation
This requires only the ability to author a workflow/job spec that sets a target capability's `Config.schedule`/`deltaStage`, which is an ordinary, low-privilege action in the CRE workflow model (no node-operator, key, or peer compromise needed). The bug is deterministic and trivially reproducible — it does not depend on race conditions or environment specifics, only on supplying a negative-duration string that `time.ParseDuration` accepts.

### Recommendation
In `ExtractTransmissionConfig` (`core/capabilities/transmission/transmission.go`), validate the parsed `DeltaStage`: reject negative durations and enforce a sane upper bound (e.g., consistent with `defaultDelayMargin`/expected request timeouts) before returning `TransmissionConfig`. Also consider validating `deltaStage * (donMemberCount-1)` against the request timeout to prevent inconsistent scheduling behavior.

func GetPeerIDToTransmissionDelaysForConfig(donPeerIDs []types.PeerID, transmissionID string, tc TransmissionConfig) (map[types.PeerID]time.Duration, error) {
	donMemberCount := len(donPeerIDs)
	key := transmissionScheduleSeed(transmissionID)
	schedule, err := createTransmissionSchedule(tc.Schedule, donMemberCount)
	if err != nil {
		return nil, err
	}

	picked := permutation.Permutation(donMemberCount, key)

	peerIDToTransmissionDelay := map[types.PeerID]time.Duration{}
	for i, peerID := range donPeerIDs {
		delay := delayFor(i, schedule, picked, tc.DeltaStage)
		if delay != nil {
			peerIDToTransmissionDelay[peerID] = *delay
		}
	}
	return peerIDToTransmissionDelay, nil
}

func delayFor(position int, schedule []int, permutation []int, deltaStage time.Duration) *time.Duration {
	sum := 0
	for i, s := range schedule {
		sum += s
		if permutation[position] < sum {
			result := time.Duration(i) * deltaStage
			return &result
		}
	}

	return nil
}
