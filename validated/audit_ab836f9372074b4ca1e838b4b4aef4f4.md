## Title
Paused interest accrual returns stale index/lindex instead of reverting, letting `system-borrow`/`system-repay`/`deposit`/`redeem` execute against out-of-date indexes - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

## Summary
The bug-class hint describes a value (a P-Chain validator's `validationID`) becoming stale relative to a later state-changing event and the code path silently continuing with default/zero behavior instead of detecting the inconsistency, corrupting protocol accounting. The closest single-transaction analog in Zest's Clarity vaults is the `accrue` private function's pause branch, which is explicitly called out as an allowed analog pattern ("a pause that passes through instead of reverting").

## Finding Description
Every asset vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts) implements `accrue` with this branch:

```clarity
(if (get accrue states)
    ;; PAUSED: Pass-through without reverting
    (ok { index: idx, lindex: lidx })
    ;; NOT PAUSED: Normal accrual logic
    (let (...)
      ...
      (ok { index: next, lindex: nliq })))
``` [1](#0-0) 

When `accrue` is paused (`pause-states.accrue == true`), the function returns the **currently stored** `index`/`lindex` (`idx`, `lidx`, both read from `var-get` before the branch) as if they were freshly computed, and — critically — it does **not** update `last-update` in this branch. Every state-mutating entry point (`system-borrow`, `system-repay`, `deposit`, `redeem`, `transfer`) unconditionally calls `(try! (accrue))` first and then proceeds to use `idx`/scaled-principal math based on whatever `accrue` returned:

```clarity
(define-public (system-borrow (amount uint) (receiver principal))
  (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      ...
      (idx (var-get index))
      ...
``` [2](#0-1) 

The value bound here is the vault's `index`/`lindex` interest-accrual state, captured via `var-get index`/`var-get lindex` inside `accrue`. The event that should invalidate/refresh it is the passage of block-time since `last-update` — normally `accrue` advances `index` to `next-index()` and bumps `last-update` to `stacks-block-time`. But while `accrue` is paused, this invalidation is skipped: `accrue` "checks" the pause state and then immediately returns the old index as a legitimate response (`(ok {...})`), rather than reverting or refusing to proceed. Callers such as `system-borrow`/`system-repay`/`deposit` then use this pass-through value to compute `scaled-amount`, `total-borrowed`, share conversions, etc., persisting new debt/supply state keyed to a frozen index while wall-clock time (and, in the market layer, oracle prices and `stacks-block-time`) continues to move.

This mirrors the reported bug class: a lookup (`nodePendingRemoval[valID]`) silently returns a default/no-op result instead of surfacing the invalidated state, and downstream accounting (the vault's scaled-principal/index bookkeeping here, analogous to `operatorNodesArray`) becomes permanently desynchronized from real economic time once accrual is later unpaused, because interest that should have accrued (or, in the socialize-debt / index-cache path in `market.clar`, interest that other code paths assume is fresh) is silently frozen and reported as current rather than causing the whole operation to be rejected.

## Impact Explanation
Because `system-borrow`, `system-repay`, `deposit`, and `redeem` all proceed to execute (transferring funds, minting/burning `ztokens`, adjusting `principal-scaled`/`total-borrowed`) using a stale index while `accrue` is paused, and because `market.clar`'s `accrue-and-cache` caches this pass-through value per-block for cross-contract reuse:

```clarity
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [3](#0-2) 

positions can be borrowed against, repaid, or have collateral valued using an index that does not reflect real accrued interest for the paused duration. Debt scaled during the pause is under-accounted relative to what should have accrued, and once accrual resumes the jump in `index` at the next non-paused block is applied against principal recorded during the freeze, mispricing debt/collateral for the pause window. This falls under temporary/permanent freezing or misstatement of unclaimed yield (interest) — a High-severity impact class per the accepted categories (freezing/misstatement of unclaimed yield), rather than a design choice, because the code explicitly documents intent to "pass through" state instead of rejecting mutating calls while paused.

## Likelihood Explanation
This does not require any privileged compromise beyond the normal, intended use of the existing `set-pause-states` DAO/governance toggle to pause `accrue` (a legitimate operational action, e.g. during an incident response), combined with any user calling `system-borrow`/`deposit`/`repay` during that pause window — all single-block/single-transaction interactions with code already present and reachable in every vault contract. The likelihood of the pause being engaged is operational (not attacker controlled), but the resulting inconsistency in accrued interest is a deterministic, mechanical consequence of the accrue function's design whenever the pause is active during any mutating call, so it is highly likely to occur whenever `accrue` pause is used as intended by an operator.

## Recommendation
Change the paused branch of `accrue` to either (a) revert the encompassing call (e.g., `ERR-PAUSED`) instead of returning a synthetic `(ok {...})` with the frozen index, so that state-mutating functions cannot execute against unaccrued interest; or (b) explicitly document/enforce that all financial calculations depending on `index`/`lindex` are disabled while `accrue` is paused (i.e., also pause `deposit`/`redeem`/`system-borrow`/`system-repay` together with `accrue`, and require the DAO to `accrue` once before unpausing, matching the compensating logic already present in `set-pause-states` for the pause/unpause transition of `accrue` itself).

## Proof of Concept
1. DAO calls `set-pause-states` on `v0-vault-stx` (or another vault) with `{ accrue: true, ... }`, which per the pause-toggle logic runs one final `accrue` and then sets `pause-states` — see `set-pause-states` and the "When pausing accrue, accrue first to capture pending interest" comment. [4](#0-3) 
2. Time (and Stacks blocks) elapses. `next-index()`/`next-liquidity-index()` would normally have grown, but nothing in storage reflects this because `accrue` never runs its real branch while paused.
3. A user calls `system-borrow` (via `market.clar`'s `borrow`). `accrue` is invoked, hits the paused branch, and returns the old `idx`/`lidx` as `(ok {...})` without reverting: `(ok { index: idx, lindex: lidx })`. [5](#0-4) 
4. `system-borrow` proceeds using `(idx (var-get index))` — the same stale value — to compute `scaled-amount` and update `principal-scaled`/`total-borrowed`, and `market.clar` caches this same stale pair via `accrue-and-cache` for every other call in the same block that also uses this asset.
5. When the DAO later unpauses `accrue`, `set-pause-states`'s unpause branch jumps `last-update` forward to `stacks-block-time` to "skip the paused period" [6](#0-5)  — meaning interest for the entire paused duration is permanently lost/never applied to the scaled debt recorded in step 4, even though the underlying borrow/repay activity during the pause was allowed to proceed as if the index were current.
