### Title
`ValidateMultiSign` Precompiled Contract Computes Signature Digest Without Chain Domain Separator, Enabling Cross‑Chain Signature Replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (exposed to TVM contracts, e.g. via Solidity's `validatemultisign`) computes the message digest to be verified as `sha256(address || permissionId || data)` with no chain/network identifier included. Any smart contract that relies on this precompile to authenticate off‑chain-signed messages (e.g. meta-transactions, permit-style withdrawals, multisig approvals) inherits a replay weakness identical in nature to the reported "withdraw" bug: the signed payload is valid on every TRON-derived network (mainnet, testnets, or any private/forked chain) sharing the same account address and permission configuration, because nothing in the digest binds the signature to a specific chain.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` builds the hash to verify like this: [1](#0-0) 

```
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
```

It then recovers the signer for each supplied signature and checks the recovered address's weight against the account's `Permission`: [2](#0-1) 

The digest is composed only of `address`, `permissionId`, and caller-supplied `data` — there is no chain identifier, genesis hash, or any other domain-separation value mixed in. This mirrors exactly the root cause in the external report: a signed authorization message omits a chain-binding value, so the same signature is valid wherever an account with the same address/permission configuration exists — i.e., on any other TRON-protocol chain (public testnets such as Nile/Shasta, or any privately forked/sidechain deployment that reuses accounts/keys, e.g. through the same mnemonic/keypair).

This precompile is a first-class, protocol-level building block (unlike `ECRecover` which mirrors Ethereum's raw crypto primitive), and TRON dApps commonly use it for account-based multisig/permission verification of off-chain-signed payloads (e.g., authorizing withdrawals, approvals, gasless transactions) without adding their own chain-id domain separation, because the precompile is advertised as an authoritative signature/permission check tied to the account.

### Impact Explanation
Any application-layer contract that uses `validatemultisign` for authorization (e.g., withdraw/approval flows keyed off `data`) is exposed to cross-chain replay: a message authorized for withdrawal or another privileged action on one network can be resubmitted on a second network that has the same account/permission state, resulting in double execution of financial or state-changing operations — the same class of impact ("withdraw twice") described in the original report, now generalized to any consumer of the `ValidateMultiSign` (and equivalently `BatchValidateSign`) precompile.

### Likelihood Explanation
Reachable by any unprivileged user via ordinary contract calls (no privileged actor, peer, or leaked key required): an attacker only needs to observe a validly-signed message on chain A and resubmit it as `data`/signature input to `validatemultisign` on chain B where the same account/permission exists. This is directly exploitable whenever a project (or the same operators) deploy contracts using this precompile on multiple TRON-protocol networks (mainnet + testnets, or forks/sidechains sharing account state) — a realistic and common deployment pattern.

### Recommendation
Add a chain-binding value (e.g., the node's `chainId` as already exposed by `VMConfig`/`getChainId()` on the TVM, or the genesis block hash) into the digest computed by `ValidateMultiSign`/`BatchValidateSign` before hashing, e.g. `combine = merge(address, permissionId, chainId, data)`. Document clearly for dApp developers that this precompile provides no domain separation on its own and update the digest format under a hard fork/feature-gate (similar to `VMConfig.allowTvmSelfdestructRestriction()`/`allowTvmOsaka()`) to avoid breaking existing signatures.

### Proof of Concept
1. Deploy Contract `C` on chain A (e.g. mainnet) that calls `validatemultisign(address, permissionId, data, signatures)` to authorize a withdrawal keyed by `data` (e.g., encoding recipient+amount+nonce, but no chain id).
2. User signs `data` off-chain for account `address` with permission `permissionId`; contract executes the withdrawal on chain A.
3. Deploy the identical contract bytecode on chain B (e.g. a TRON testnet or fork) where the same `address`/private key and equivalent `Permission` (same key/threshold) is provisioned.
4. Submit the same `data` and previously-captured `signatures` to contract `C` on chain B; `ValidateMultiSign.execute` recomputes the same `sha256(address || permissionId || data)` (identical on both chains) and successfully re-validates the signature, letting the user withdraw a second time.
