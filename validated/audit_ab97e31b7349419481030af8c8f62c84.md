## Title
Replay-verification of transaction output ignores `state_checkpoint_hash`, allowing a corrupted world-state root to be accepted as valid - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk-executor replay/verification paths (invoked from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`) to check that a locally re-executed transaction's output matches the authenticated `TransactionInfo` that is committed to the ledger/accumulator. This function validates the execution status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never compares the `state_checkpoint_hash` (the Sparse-Merkle/Jellyfish state root committed for that transaction) against a locally computed one.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (computed from `self.write_set()`) vs `txn_info.state_change_hash()`
- `event_root_hash` (computed from `self.events()`) vs `txn_info.event_root_hash()`

It never fetches or compares `txn_info.state_checkpoint_hash()` (nor `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`) to any locally computed state root. This gap is explicitly acknowledged in a TODO directly inside the function: [2](#0-1) 

The `state_checkpoint_hash` is precisely the field meant to authenticate the entire world state (Jellyfish Merkle root) as of that transaction/checkpoint — see its definition and role: [3](#0-2) . This value is produced independently during normal execution by `DoStateCheckpoint::run`, which folds writes into a `LedgerStateSummary` and derives `state_checkpoint_hashes` from the resulting root hash: [4](#0-3) . That computed hash is what ultimately becomes part of each `TransactionInfo`'s `state_change_hash`/`state_checkpoint_hash` fields, is fed into the transaction accumulator (`DoLedgerUpdate::run`, [5](#0-4) ), and is authenticated by the accumulator root hash that ledger infos and consensus certify.

The chunk executor's replay path calls `ensure_match_transaction_info` (confirmed via grep at `execution/executor/src/chunk_executor/mod.rs`) to decide whether a locally re-executed transaction matches the transaction info stored on the ledger/backup. Because this check omits `state_checkpoint_hash`, any divergence between the locally recomputed world-state root and the authenticated one committed on-chain will not be flagged as a mismatch by this check — the write-set and event root can match exactly while the state root differs (e.g., due to a state-merkle corruption, a divergent JMT node write, or a bug specific to the checkpoint-hash computation path that does not affect the write set itself).

### Impact Explanation
This directly weakens the state-proof integrity gate: it is a case where "committed state that differs from the correct VM result... [could go undetected]" and where "authenticated API or state-view output bound to the wrong version, object, or proof context" is not actually validated by the tool whose entire purpose is to catch such divergence. Tools such as `db-tool replay-verify` / `replay-on-archive` (in `storage/db-tool/src/replay_verify.rs`, `storage/db-tool/src/replay_on_archive.rs`) and the Move CLI/debugger replay commands rely on this comparator as their correctness oracle. If the persisted state-checkpoint hash (i.e., the JMT root propagated into `TransactionInfo`) were ever corrupted or diverged from actual write-set application — whether from a storage bug, a restore/backup bug, or a hard-fork-related state-computation change — replay-verify would report success even though the state root is wrong, masking a genuine ledger state corruption from the exact tooling designed to detect it.

This does not, by itself, allow a wrong state root to be accepted by consensus (that path is governed by independent BFT execution and signature validation, and is out of scope), but it does break the auditing/verification invariant that the exact corrupted value (the state-checkpoint root) must be checked before a "successful" verification is reported, which is squarely inside the "Proof And Storage Pivots" the gate calls out for state-view and replay validation.

### Likelihood Explanation
The comment is a maintainer-acknowledged, intentional gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), i.e., it is a real, currently-shipped limitation rather than a hypothetical. It requires no attacker action — it is a latent verification blind spot that would only manifest if state roots diverge for any reason (bug, storage corruption, incomplete replay of a feature like `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). Likelihood of the underlying divergence occurring is not attacker-controlled and is presumably rare, but the check itself unconditionally omits the comparison regardless of feature flags, so whenever a state-root divergence does occur, this specific safety net will not catch it.

### Recommendation
Add comparisons of `txn_info.state_checkpoint_hash()` (and, where applicable, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`) against a locally computed state-checkpoint root inside `ensure_match_transaction_info`, mirroring the existing `write_set_hash`/`event_root_hash` checks, so that replay-verify tooling cannot report success while the authenticated world-state root diverges from the locally re-executed one.

### Proof of Concept
Not exploitable via an external transaction; this is a verification-logic gap. Conceptual PoC:
1. Construct (or simulate via test) a backup/ledger state where a given version's committed `TransactionInfo.state_checkpoint_hash` does not match the actual JMT root implied by applying that version's write set on top of the correct parent state (e.g., by injecting a corrupted state-merkle node or a bug in checkpoint computation while leaving the write set/events unchanged).
2. Run `db-tool replay-verify` or `aptos-debugger`/CLI replay against this data.
3. Observe that `ensure_match_transaction_info` at [1](#0-0)  returns `Ok(())` because it never inspects `state_checkpoint_hash`, despite the state root being wrong — demonstrating the tool would falsely report a successful replay/verify.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
