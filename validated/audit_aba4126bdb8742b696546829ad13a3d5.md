### Title
L1Handler fee-payment check is bypassed by validators re-executing transactions received via consensus, allowing honest-node state divergence - (File: `crates/apollo_transaction_converter/src/transaction_converter.rs`)

### Summary
`AdvancedOrderEngine` allows a `Facilitator` to be handed borrowed assets from a vault without any code-level check that the assets are ever repaid; the client's defense is that the incentive/repayment model guarantees this never happens in practice. The sequencer analog is the `paid_fee_on_l1` field of an `L1HandlerTransaction`: the protocol is supposed to guarantee that L2 execution resources granted to an L1-triggered call are "paid for" via the fee sent with the L1 `sendMessageToL2` call. However, when a transaction crosses the consensus wire (proposer → validators), the real `paid_fee_on_l1` value is dropped and replaced with a hardcoded placeholder, so the repayment/fee check that should gate execution success is effectively bypassed for every validator, while the block *proposer* (who builds the transaction from the real, scraped L1 event) evaluates the same check against the true fee.

### Finding Description
An `L1HandlerTransaction`'s `paid_fee_on_l1` is meant to reflect the ETH actually attached to the corresponding `sendMessageToL2` call on L1 [1](#0-0) . On the execution side, `blockifier`'s `L1HandlerTransaction::execute_raw` only enforces that the paid fee is non-zero: [2](#0-1) 

This is already a loose check ("For now, assert only that any amount of fee was paid"), but it is the *only* gate that ties L2 resource consumption to L1 payment for this transaction type — analogous to the missing repayment check for `Facilitator` borrowing in the original report.

Crucially, this fee value is not carried over the consensus wire protocol at all. When a proposer serializes an `InternalConsensusTransaction::L1Handler` for network transmission, it only sends the inner `transaction::L1HandlerTransaction` (which has no fee field) and drops `paid_fee_on_l1` entirely: [3](#0-2) 

When any node (validator, or a node re-processing a proposal) converts that wire-format transaction back to the executable/internal representation, it unconditionally re-attaches a **hardcoded** `Fee(1)`, regardless of what was truly paid on L1: [4](#0-3) 

This function is invoked directly in the proposal-validation path, where the validating node converts every transaction batch received from the network before sending it to the batcher for re-execution: [5](#0-4) .

By contrast, the proposer builds its proposal from its local mempool/batcher, whose `L1HandlerTransaction` originates from the L1 events scraper carrying the *real* fee (`paid_fee_on_l1: Fee(fee.into())`) [1](#0-0) , and only converts to the wire format when broadcasting (dropping the fee) [6](#0-5) .

### Impact Explanation
Any unprivileged L1 account can call `sendMessageToL2` with `msg.value = 0`, i.e., pay no fee for the resulting L1Handler transaction. If the proposer includes this transaction in a block, its local execution (using the real, zero fee) triggers `TransactionFeeError::InsufficientFee`, causing the proposer to treat the transaction as reverted (no state change, matching the OS's `is_reverted` skip path) [7](#0-6) . When this same transaction is disseminated to other consensus participants for validation, they reconstruct it with the hardcoded `Fee(1)` placeholder, which always satisfies the `paid_fee == Fee(0)` check — so validators execute the entry point and apply its state changes instead of treating it as reverted. This produces divergent state diffs/execution results for the identical logical transaction between the proposer and validating nodes, which can manifest as a `ProposalFinMismatch` (block rejected, degrading liveness / inability to confirm new blocks) or, if commitment checks were weaker, a wrong committed state root. This is a concrete honest-node divergence bug reachable purely from an L1 message sender's unprivileged action.

### Likelihood Explanation
Triggering the divergence requires only a standard, permissionless L1 call (`sendMessageToL2` with zero or insufficient fee) which any user can perform; no privileged role, malicious operator, or malicious proposer/validator behavior is required — the bug reproduces with fully honest nodes following the protocol, only differing in whether they process the transaction via the scraper path (proposer) or the consensus-wire path (validators). The `// TODO(Gilad): Change this once we put real value in paid_fee_on_l1.` comment confirms this is a known, still-unaddressed placeholder in production code.

### Recommendation
Include the real `paid_fee_on_l1` value in the wire-format `ConsensusTransaction::L1Handler` representation (or otherwise let validators independently derive/verify it, e.g., from their own L1 event view) instead of hardcoding `Fee(1)` in `convert_consensus_l1_handler_to_internal_l1_handler`. Additionally, strengthen the fee check in `L1HandlerTransaction::execute_raw` beyond "non-zero" to actually compare the paid fee against the computed cost, consistent with the resource-bound check already performed via `l1_handler_max_amount_bounds`.

### Proof of Concept
1. On L1, call `sendMessageToL2(l2_contract, l2_selector, payload)` with `value = 0` (or a value below the true cost), as any unprivileged L1 account.
2. The L1 events scraper picks this up and constructs an `ExecutableL1HandlerTransaction` with `paid_fee_on_l1 = Fee(0)` [8](#0-7) .
3. The block proposer includes this transaction; its local execution via `execute_raw` hits `paid_fee == Fee(0)` and marks it reverted, producing no state change [7](#0-6) .
4. The proposer streams the transaction to the network using `convert_internal_consensus_tx_to_consensus_tx`, which strips `paid_fee_on_l1` [9](#0-8) .
5. A validating node receives it and calls `convert_consensus_tx_to_internal_consensus_tx` → `convert_consensus_l1_handler_to_internal_l1_handler`, which reconstructs the transaction with hardcoded `Fee(1)` [4](#0-3) .
6. The validator's batcher re-executes with `paid_fee_on_l1 = Fee(1) ≠ Fee(0)`, passing the check and applying the entry point's state changes — diverging from the proposer's reverted outcome, leading to a commitment mismatch in `validate_proposal` [10](#0-9) .
