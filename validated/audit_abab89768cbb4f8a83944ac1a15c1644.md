### Title
Node crash via `.unwrap()` panic on `receiver_shard_id()` when a `GlobalContractDistribution` receipt is delayed across shard-layout transitions it cannot be resolved against - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
An unprivileged account can deploy a global contract, which creates a `GlobalContractDistribution` receipt carrying a fixed `target_shard`. If that receipt is delayed in the delayed-receipt queue (which any account can induce by saturating a shard's compute budget) across shard-layout changes that its `target_shard` cannot be resolved against, the deterministic `.unwrap()` in `receipt_filter_fn` panics, crashing every honest node processing that shard — a full chain halt triggered purely by a submitted transaction and normal chunk processing timing.

### Finding Description
`ReceiptEnum::receiver_shard_id()` resolves the destination shard of a receipt for the current shard layout [1](#0-0) . For an `Action`/`Data`/`PromiseYield`/etc. receipt this is trivial (`account_id_to_shard_id`), but for `GlobalContractDistribution` receipts it uses a stored `target_shard` that may originate from an old, stale shard layout (because such receipts get forwarded shard-by-shard and can sit in the delayed-receipt queue across resharding events): [2](#0-1) 

When `target_shard` is not part of the current layout, it calls `shard_layout.resolve_to_current_shard(target_shard)`. For `ShardLayoutV3` (dynamic resharding), this walks the complete cumulative split history recursively and can resolve arbitrarily many resharding generations [3](#0-2) . However, for legacy `V0`/`V1`/`V2` layouts (used for protocol-version-driven "static" resharding), `resolve_to_current_shard` explicitly only supports a **single generation**: [4](#0-3) 

If a `GlobalContractDistribution` receipt survives across **two or more** static-resharding shard-layout transitions (two protocol upgrades that each split shards) while parked in the delayed-receipt queue, `resolve_to_current_shard` returns `None` on the second hop, and `receiver_shard_id()` legitimately returns `Err(EpochError::ShardingError(...))`.

The caller of this function inside the delayed-receipt pop path does **not** propagate that error — it unconditionally `.unwrap()`s it: [5](#0-4) 

This `receipt_filter_fn` runs on every delayed-receipt `pop()` during `Runtime::apply` for the affected shard [6](#0-5) , which is executed by every validator/RPC node applying that chunk. A panic here is deterministic and reproducible on any node that processes the chunk, i.e., a transaction-triggered halt rather than a benign per-node crash.

This closely parallels CVE-2019-10162's bug class: a value the attacker controls (via a normal, authorized operation — deploying a global contract) is later consumed by internal processing logic that assumes an invariant ("the target shard is always resolvable") which does not universally hold, and the failure mode is an unconditional process-crashing `unwrap`/`expect` instead of a graceful error path.

The project's own regression test explicitly documents and defends against exactly this failure mode for the V3 (two-generation dynamic-resharding) case, and states the fix "only works with V3 shard layouts", implying legacy/static layouts remain exposed to the multi-generation gap: [7](#0-6) [8](#0-7) 

### Impact Explanation
A successful trigger causes every node applying the affected shard's chunk to panic in `Runtime::apply` while popping the stale delayed `GlobalContractDistribution` receipt, i.e., a **transaction-triggered halt** of chunk production for that shard (and potentially the whole chain if the shard cannot progress). This matches the "transaction-triggered halt" acceptance criterion — comparable in class and severity to CVE-2019-10162 (an authorized action causing a deterministic parsing/processing error to crash the server).

### Likelihood Explanation
- Deploying a global contract (`DeployGlobalContract` action) is available to any unprivileged account.
- Delaying the resulting `GlobalContractDistribution` receipt is achievable by any account saturating a shard's compute budget across several blocks (as demonstrated by the project's own test harness for the V3 case).
- The remaining precondition — that the receipt survives across **two or more static-resharding layout generations** — depends on the network actually undergoing static resharding (a protocol-upgrade-driven event outside attacker control in the short term), so exploitation timing is not fully attacker-controlled. This lowers immediate likelihood relative to the V3 case (which the team has already hardened and tested), but the code path (`resolve_to_current_shard` single-generation limitation for V0/V1/V2 plus the unconditional `.unwrap()`) remains present and unguarded for legacy layouts.

### Recommendation
- Replace the `.unwrap()` in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs`) with proper error propagation (`?`) so `RuntimeError` surfaces instead of panicking.
- Extend `resolve_to_current_shard` for `V0`/`V1`/`V2` shard layouts to walk multiple historical generations (mirroring the V3 cumulative-split-history approach), or migrate global-contract-distribution shard resolution to always use full split-history lookups regardless of layout version.
- Add a regression test analogous to `test_stale_global_contract_distribution_after_double_resharding`, but exercising two (or more) **static** (protocol-version-driven) resharding transitions rather than dynamic/V3 ones, to confirm the legacy code path is also hardened.

### Proof of Concept
1. Configure a network using static (protocol-version-driven) resharding with at least two scheduled shard splits across two protocol upgrades, where the same shard is targeted (or its descendant becomes disjoint from `target_shard`'s ancestry) in both splits.
2. As an unprivileged user, submit `DeployGlobalContract` from an account on the shard scheduled to be split first; this emits a `GlobalContractDistribution` receipt with `target_shard` set to that shard's current (soon-to-be-retired) id, per `apply_global_contract_distribution_receipt` / `forward_distribution_next_shard` in `runtime/runtime/src/global_contracts.rs`.
3. Flood the same shard with compute-heavy transactions every block so the incoming `GlobalContractDistribution` receipt is pushed into the delayed-receipt queue (`process_incoming_receipts` in `runtime/runtime/src/lib.rs`) and remains there.
4. Let both protocol upgrades/shard splits complete while the receipt stays delayed.
5. Stop flooding and let the delayed queue drain; when `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, `receiver_shard_id()` returns `Err` because the two-generation-old `target_shard` cannot be resolved via the single-generation `resolve_to_current_shard` for legacy layouts, and the `.unwrap()` panics, crashing the node applying that chunk (`runtime/runtime/src/congestion_control.rs:876`).

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }

    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }
