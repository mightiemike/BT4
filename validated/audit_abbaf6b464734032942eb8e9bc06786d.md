### Title
`ensure_match_transaction_info` skips state-checkpoint hash comparison, allowing replay-verify to accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by replay/verification tooling to confirm that a locally re-executed transaction output matches the authenticated, committed `TransactionInfo`, checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is analogous to the NFTX bug class where a check/selection ignores a critical dimension (`quantity1155`) of the data it is supposed to validate — here the check ignores the state root fields that bind a transaction's execution to the ledger's committed state tree.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and verifies a `TransactionOutput` against a `TransactionInfo` by comparing status, gas used, write-set hash, and event root hash: [2](#0-1) 

Immediately after these checks, the function has an explicit TODO acknowledging that it does not validate the checkpoint hashes: [3](#0-2) 

This means the state root fields carried in `TransactionInfo` — `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — which bind a transaction's execution result to the actual persisted state tree at that version, are never cross-checked against the locally computed values in this comparator.

This function is the authoritative correctness check used by `db-tool`'s replay-verify (`replay_on_archive.rs`), which calls it directly on freshly executed outputs: [4](#0-3) 

It is also used in `aptos-debugger` and the `aptos-move/cli` commands as a generic "did the VM output match the recorded transaction info" check, so any consumer relying on `ensure_match_transaction_info` to detect state divergence during replay will silently pass even if the state Merkle root diverges.

### Impact Explanation
Replay-verify is the primary tool used to confirm that historical or newly-produced VM execution deterministically reproduces the exact state committed to the ledger (including after protocol upgrades, hard forks, VM changes, or state-tree schema changes such as the "trading-native"/hot-state or position-state features referenced in the TODO). Because `ensure_match_transaction_info` omits the state-checkpoint hash comparisons, a bug in state-tree construction, hot-state checkpointing, or position-state checkpointing that produces a different Jellyfish Merkle root than the one originally committed would not be flagged by this comparator. This directly weakens the state-commitment integrity guarantee this tool exists to provide: an authenticated state root divergence (a hard-fork-class bug) could go undetected by the exact tooling meant to catch it before mainnet rollout, matching the "wrong accumulator/state root accepted as valid" impact category.

### Likelihood Explanation
The gap is unconditional and always present for any caller of `ensure_match_transaction_info` — it is not gated behind a rare configuration. The TODO itself confirms the codebase authors are aware the check is incomplete and that it is a live gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), i.e., it is expected to matter as new state-root features (hot state, position state) roll out. I was not able to fully trace whether every replay path also independently verifies the accumulator/state roots through a separate mechanism (e.g., higher-level ledger accumulator checks elsewhere in the executor), so it's possible another layer partially mitigates this in some flows; this couldn't be fully confirmed from the code reachable in this investigation.

### Recommendation
Extend `ensure_match_transaction_info` to compute the actual `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` for the re-executed transaction and compare them against the corresponding fields in `txn_info`, returning an error on mismatch, mirroring the pattern already used for `write_set_hash` and `event_root_hash`. Gate this additional check behind whatever feature/version flags are needed so it activates correctly only when the fields are populated (V1 transaction info / hot-state / position-state enabled), but ensure it cannot be silently skipped for versions where these fields should be present.

### Proof of Concept
1. Introduce (hypothetically) a bug that alters how the hot-state or position-state checkpoint root is computed on replay (e.g., an off-by-one in leaf ordering) while write set, gas, status, and events remain unchanged.
2. Run `db-tool replay-on-archive` over the affected version range.
3. `execute_and_verify` calls `ensure_match_transaction_info` at [5](#0-4) , which only checks status/gas/write-set-hash/event-root-hash.
4. Because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared (per the TODO at [3](#0-2) ), the replay reports success even though the locally computed state root diverges from the one committed and authenticated on-chain — exactly the "commit differs from correct VM result but is accepted" outcome this tooling is meant to prevent.
