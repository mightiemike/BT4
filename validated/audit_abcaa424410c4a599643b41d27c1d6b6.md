### Title
`sanitizeHost` throws an uncaught exception instead of returning null for malformed base64 host params, causing DoS in auth/host-validation paths - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` query parameter with a permissive regex (`base64regex`) that only checks the character set, not proper base64 length/padding, and does not wrap the subsequent `decodeHost`/`new URL()` calls in a try/catch. An attacker can craft a `host` value that passes the regex but causes `atob()` (via `decodeHost`) or the WHATWG `URL` constructor to throw, propagating an unhandled exception out of `sanitizeHost` instead of returning `null` or `InvalidHostError`.

### Finding Description
`sanitizeHost` in [1](#0-0)  validates `host` using `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/`, which only enforces the allowed character set and optional padding count, not that the string length is a valid base64 length. It then unconditionally calls `decodeHost(sanitizedHost)` (which is a plain `atob(host)` wrapper, see [2](#0-1) ) and immediately constructs `new URL(\`https://${decoded}\`)`. Neither call is inside a try/catch block.

`atob` implements the WHATWG forgiving-base64 decode algorithm, which throws (`InvalidCharacterError`/`DOMException` in browsers, or a `TypeError` in Node's implementation) when the input length (modulo padding) is not a valid base64 length — e.g. a single character like `"a"` matches `base64regex` but is not decodable and will throw. Separately, even when `atob` succeeds, the decoded bytes can contain control characters, unpaired surrogates, or other bytes that are invalid in a URL host component; passing such a value into the WHATWG `URL` constructor can throw a `TypeError`.

Callers of `sanitizeHost`, such as `validateShopAndHostParams` in the Remix and React Router adapters ( [3](#0-2) ), invoke `api.utils.sanitizeHost(url.searchParams.get('host')!)` directly on attacker-controlled query string data with no surrounding try/catch for exceptions other than the library's own `InvalidHostError`. If `sanitizeHost` throws a raw `TypeError`/`DOMException` instead of `InvalidHostError`, this exception is not the expected control-flow signal and can propagate unhandled up through the request handler, crashing or 500-ing the request path (and potentially the process/worker depending on the host framework's error handling), which is a DoS in an authentication-adjacent handler that requires no credentials to trigger.

The existing regression tests (`packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts`) only cover a non-base64 string, a bad-suffix string, and a validly-decodable but wrong-domain host — none test malformed-but-regex-passing base64 (e.g. odd length, or decoded bytes with invalid URL host characters), so this gap is not currently caught.

### Impact Explanation
This matches Shopify's "Denial of Service" bounty impact class for a request-authentication-adjacent path: an anonymous, unauthenticated attacker can send a single crafted `host` query parameter to any endpoint that calls `sanitizeHost` (e.g. embedded-app auth/login/callback flows in `shopify-app-remix`/`shopify-app-react-router`) and cause an unhandled exception instead of the expected graceful `null`/`InvalidHostError` handling. Depending on how the surrounding framework/host app handles uncaught exceptions, this can manifest as an unhandled promise rejection or process crash rather than a clean 4xx response, degrading availability of the auth flow for legitimate users.

### Likelihood Explanation
Preconditions are minimal: default configuration, no credentials or secrets needed, and the attacker only needs to control the `host` query string of a single HTTP request to a route that calls `sanitizeHost` (directly or via `validateShopAndHostParams`). Crafting a `base64regex`-passing-but-non-decodable string (e.g. a single character, or an odd-length string) is trivial and fully repeatable.

### Recommendation
Wrap the `decodeHost`/`URL` construction logic in `sanitizeHost` in a try/catch, treating any thrown error (from `atob` or `URL`) as an invalid host — i.e., set `sanitizedHost = null` (or throw `InvalidHostError` if `throwOnInvalid` is set) rather than letting the raw exception propagate. Additionally, tighten `base64regex` to also validate that the string length is a multiple of 4 (standard base64 length constraint) to reject cases like `"a"` before attempting to decode.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost does not throw for malformed base64 that passes base64regex', () => {
  const shopify = shopifyApi(testConfig());

  // Single character: matches /^[0-9a-zA-Z+/]+={0,2}$/ but is not a valid
  // base64-encoded string length, so atob() throws instead of decoding.
  expect(() => shopify.utils.sanitizeHost('a')).not.toThrow();
  expect(shopify.utils.sanitizeHost('a')).toBeNull();
});
```
Expected (per fail-closed invariant): `sanitizeHost('a')` should return `null` (or throw `InvalidHostError` when `throwOnInvalid` is true). Actual (per current code): calling `decodeHost('a')` → `atob('a')` throws an uncaught `DOMException`/`TypeError` that is not caught anywhere in `sanitizeHost`, causing the test/request to fail with an unhandled exception rather than a controlled `null`/`InvalidHostError` result.
