### Title
Any error from the L1 events provider client during L1Handler validation is collapsed into a definitive "Invalid" status, causing honest validators to wrongly reject valid blocks - ([File: crates/apollo_batcher/src/transaction_provider.rs])

### Summary
`ValidateTransactionProvider::get_txs` calls `l1_events_provider_client.validate(...)` for every `L1Handler` transaction received from consensus during block validation. Any error returned by that call — regardless of whether it reflects a real invalidity condition or a transient/internal error (timeout, component-channel error, provider not yet initialized/caught up, etc.) — is unconditionally coerced into `L1ValidationStatus::Invalid(L1InvalidValidationStatus::L1EventsProviderError)`, which then causes the validator to fail the entire block's validation.

### Finding Description
In `ValidateTransactionProvider::get_txs`: [1](#0-0) 
the validation result is obtained via:
```rust
let l1_validation_status = self
    .l1_events_provider_client
    .validate(tx.tx_hash, self.height)
    .await
    .inspect_err(|err| { ... })
    .unwrap_or(L1ValidationStatus::Invalid(
        L1InvalidValidationStatus::L1EventsProviderError,
    ));
if let L1ValidationStatus::Invalid(validation_status) = l1_validation_status {
    return Err(TransactionProviderError::L1HandlerTransactionValidationFailed {
        tx_hash: tx.tx_hash,
        validation_status,
    });
}
```
This is the same bug class as the reported `maybeResendFromStore` issue: a fail-safe branch that is supposed to only trigger on a specific, well-defined negative outcome (in the original report: "transaction not found"; here: the L1 message being genuinely invalid — cancelled, consumed, already included, or not found) is instead triggered by *any* error the underlying call can produce, including errors caused by RPC/IPC/timeout/component problems that carry no information about the actual validity of the transaction.

The `L1EventsProviderClient`/`L1EventsProviderError` types include states such as `Uninitialized` (the provider hasn't finished scraping/catching up yet) as shown in test code: [2](#0-1) 
and the client-to-component call itself can fail from generic infra/component-client errors (timeouts, channel errors) unrelated to whether the L1 message is actually consumed/cancelled/valid. None of these conditions imply the transaction is actually invalid — yet `unwrap_or` treats them identically to a proven-invalid L1Handler transaction.

### Impact Explanation
Because `get_txs` runs independently on every validating node, a transient failure of the `l1_events_provider_client.validate` call on some (but not necessarily all) validator nodes — e.g., because that node's L1 events provider component is momentarily busy, still catching up, or the call times out — will cause only those affected nodes to reject the proposed block via `TransactionProviderError::L1HandlerTransactionValidationFailed`, while other honest nodes (whose provider call succeeds, or whose provider is the proposer of the block) accept it. This produces divergence among honest validating nodes on whether a valid block containing a legitimate `L1Handler` transaction is accepted, which can stall consensus on that height or force fallback/re-proposal, degrading the network's ability to confirm new transactions in a timely, consistent manner. This matches the "honest-node divergence" / "network unable to confirm new transactions" impact categories.

### Likelihood Explanation
The condition is reachable purely by an L1 message sender submitting a message to L2 that is picked up as an `L1Handler` transaction and included by any proposer; no privileged or malicious actor is required. The trigger is any transient failure of the internal L1 events provider client/component (timeout, channel congestion, restart/catch-up), which is a normal operational occurrence in a distributed node (component clients communicating over channels/network), making this more than a purely theoretical edge case, though it depends on timing/infrastructure conditions rather than being deterministically triggerable by an attacker.

### Recommendation
Distinguish between:
1. A definitive, provider-returned `Invalid` status (`AlreadyIncludedOnL2`, `CancelledOnL2`, `ConsumedOnL1`, `NotFound`, `AlreadyIncludedInProposedBlock`) — these should fail the transaction/block validation as currently done, and
2. An error from the client call itself (timeouts, channel errors, `Uninitialized`/catching-up states) — these should not be treated as proof of invalidity. Instead, propagate a distinct, retryable error (or block on/await the provider), or fail validation of that specific block attempt without asserting the tx is invalid, so that transient infra failures don't cause a node to permanently and incorrectly mark a valid L1Handler transaction/block as invalid relative to peers that didn't hit the transient failure.

### Proof of Concept
1. A user sends a message from L1 to L2 that results in a legitimate `L1Handler` transaction; a proposer includes it in a block proposal.
2. During validation, a validating node's `l1_events_provider_client.validate(tx_hash, height)` call fails transiently (e.g., the L1 events provider component is still catching up after a restart, returning `L1EventsProviderError::Uninitialized`, or the component-client call times out due to load).
3. `unwrap_or(L1ValidationStatus::Invalid(L1EventsProviderError))` in `transaction_provider.rs` converts this transient failure into a definitive "Invalid" verdict.
4. `get_txs` returns `Err(TransactionProviderError::L1HandlerTransactionValidationFailed { .. })`, causing this validator to reject a block that other honest validators (without the transient failure) accept — producing disagreement among honest nodes on the validity of the same block.
