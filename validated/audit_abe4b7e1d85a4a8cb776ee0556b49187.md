### Title
OAuth `shopify_app_state` cookie collision across concurrently-initiated shops causes legitimate OAuth callbacks to fail - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
`shopify.auth.begin` writes the OAuth CSRF nonce into a single, fixed-name cookie (`shopify_app_state`) scoped only by `callbackPath`, never by shop. If a single user/browser triggers two OAuth flows for different shops that share the same `callbackPath` (e.g. two install/re-auth tabs, or an app that supports multiple shops per browser), the second `begin` call silently overwrites the first shop's state cookie before the first flow's callback is completed, causing the first, legitimate OAuth transaction to fail with `InvalidOAuthError`. This mirrors the reported analog: two independent execution paths write into a shared identifier namespace with no partitioning, so one flow's write clobbers the other and causes an otherwise-valid operation to fail.

### Finding Description
`begin()` in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` generates a nonce and stores it via a signed cookie: [1](#0-0) 

The cookie name is fixed (`STATE_COOKIE_NAME = 'shopify_app_state'`) and is not namespaced by shop — only `callbackPath` (developer-configured, normally constant for the whole app) is used as the cookie path: [2](#0-1) 

In `callback()`, the state cookie is read, deleted, and compared against the `state` query parameter from Shopify: [3](#0-2) [4](#0-3) 

Because the cookie is keyed only by name+path (not by shop), any second `begin()` call issued by the same browser for a different shop before the first callback completes overwrites the cookie value with the new shop's nonce. When the first shop's OAuth callback arrives, `stateFromCookie` no longer matches the `state` query param for that flow, causing `validQuery` to fail and the whole OAuth transaction to be rejected with `InvalidOAuthError` — even though the request itself was legitimate and correctly signed by Shopify.

This is the same bug class as the `batchId` collision: two logically independent transactions/flows share a single mutable slot in a namespace (there, the nonce map keyed by `batchId`; here, the cookie keyed by name+path) with no partitioning, so activity from one flow poisons the state needed to validate the other.

Notably, the maintainers already recognized and partially fixed an almost identical collision for the *session* cookie (`shopify_app_session`) via the `cookiePath` config option, explicitly describing the same failure mode: "all shops shared a single `shopify_app_session` cookie at `path=/`, so authenticating a new shop would silently overwrite the previous shop's session": [5](#0-4) 

That fix, however, only addresses `SESSION_COOKIE_NAME`; the `STATE_COOKIE_NAME` cookie used during the `begin`/`callback` OAuth handshake still uses a single shop-agnostic path (`callbackPath`), so the same class of collision remains reachable there.

### Impact Explanation
When triggered, a legitimate OAuth (re-)authentication flow for one shop fails and the merchant/user is shown an `InvalidOAuthError` ("Invalid OAuth callback"), forcing them to restart the OAuth flow. For apps intentionally supporting multiple shops per browser session (a documented, supported scenario given the `cookiePath` fix for the session cookie), this is a straightforward and repeatable denial-of-service against the authentication handler itself — the exact class of impact the validation rules explicitly accept ("DoS of an auth handler"). It does not lead to token theft, cross-tenant session access, or forged authentication, only interruption/failure of otherwise-valid OAuth transactions.

### Likelihood Explanation
Likelihood is moderate and requires no privileged access: any single user opening OAuth flows for two shops in the same browser in close succession (e.g., installing/reinstalling the app for shop A, then immediately doing so for shop B, or an app deliberately built for multi-shop use) will reproduce this. Because `callbackPath` is normally a fixed route (e.g. `/auth/callback`) shared by all shops, no attacker-controlled input is even needed beyond ordinary concurrent usage. This is lower-severity than a forged-session or cross-tenant vulnerability, but it is a real, reachable functional/availability defect in the OAuth handler with a root cause identical to the reported bug class.

### Recommendation
Extend the same mitigation already applied to `SESSION_COOKIE_NAME` via `cookiePath` to `STATE_COOKIE_NAME`: scope the OAuth state cookie's path (or otherwise namespace its key) per-shop, e.g. by incorporating the sanitized shop domain into the cookie path or name during `begin()`, and use the corresponding shop-scoped path when reading/verifying it in `callback()`. This prevents concurrent OAuth flows for different shops in the same browser from overwriting each other's state cookie.

### Proof of Concept
1. Configure an app with a fixed `callbackPath` (e.g. `/auth/callback`), non-embedded, single browser.
2. Call `shopify.auth.begin({shop: 'shop-a.myshopify.com', callbackPath: '/auth/callback', ...})`; the browser stores `shopify_app_state=<nonceA>` at `path=/auth/callback`.
3. Before completing shop A's callback, call `shopify.auth.begin({shop: 'shop-b.myshopify.com', callbackPath: '/auth/callback', ...})`; this overwrites the cookie with `<nonceB>` at the same path (see `oauth.ts` lines 93-100 above).
4. Complete Shopify's redirect back to `/auth/callback?...&state=<nonceA>&shop=shop-a.myshopify.com...` (a fully valid, correctly-HMAC-signed callback from Shopify for shop A).
5. `callback()` reads `stateFromCookie` = `<nonceB>` (overwritten), compares it against `state=<nonceA>` in `validQuery`, and the safeCompare fails, throwing `ShopifyErrors.InvalidOAuthError` for a legitimate, unmodified Shopify OAuth callback — reproducing the "transaction fails due to collision" pattern from the analog report. - c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
