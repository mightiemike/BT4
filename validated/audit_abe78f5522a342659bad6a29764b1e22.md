### Title
Witness reward is permanently lost when a witness's vote count is zero at maintenance time - (File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
`DelegationStore.accumulateWitnessVi` silently discards a witness's already-earned block/transaction-fee reward for a cycle whenever the witness's vote count is zero at the moment `MaintenanceManager` runs its per-cycle accumulation. This is the same "advance the accounting index without crediting the interim reward when the denominator (liquidity/votes) is zero" bug class described in the RangePool.sync report: the reward has already been recorded (`delegationStore.addReward`) but the reward-per-vote index (`Vi`) is never bumped, so it can never be claimed by any past or future voter — the value is stranded forever in the `DelegationStore`'s reward key.

### Finding Description
`MortgageService.payReward` credits each cycle's non-brokerage witness reward into `DelegationStore` via `addReward(cycle, witnessAddress, value)`. [1](#0-0) 

At each maintenance boundary, `MaintenanceManager.doMaintenance()` (invoked automatically every maintenance interval, i.e. unconditionally as part of normal block/consensus processing, no privileged actor required) accumulates the reward-per-vote index for every active witness using the witness's *current, live* `voteCount` field: [2](#0-1) 

That live vote count on `WitnessCapsule` is mutated in real time by any account broadcasting a `VoteWitnessContract` (`VoteWitnessActuator.countVoteAccount`), which withdraws/clears/changes votes at will and immediately updates the witness's vote count: [3](#0-2) 

The actual accumulation logic in `DelegationStore.accumulateWitnessVi` is:
```java
public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
  BigInteger preVi = getWitnessVi(cycle - 1, address);
  long reward = getReward(cycle, address);
  if (reward == 0 || voteCount == 0) { // Just forward pre vi
    if (!BigInteger.ZERO.equals(preVi)) {
      setWitnessVi(cycle, address, preVi);
    }
  } else {
    BigInteger deltaVi = BigInteger.valueOf(reward)
        .multiply(DECIMAL_OF_VI_REWARD)
        .divide(BigInteger.valueOf(voteCount));
    setWitnessVi(cycle, address, preVi.add(deltaVi));
  }
}
``` [4](#0-3) 

This mirrors `RangePool::sync` exactly: a reward amount (`reward = getReward(cycle, address)`, analogous to the streamed BMX amount for the elapsed window) has already accrued for the cycle, but if the divisor (`voteCount`, analogous to `self.liquidity`) is zero at the time the index is advanced, the `Vi` accumulator is left unchanged (`preVi` forwarded) instead of preserving the pending `reward` for a later cycle when votes reappear. The `reward` value stored via `addReward` is never cleared/rolled forward either — it is simply orphaned: no voter's `computeReward` (which walks `deltaVi = endVi - beginVi` across `[beginCycle, endCycle)`) can ever recover it because the `Vi` delta for that cycle is exactly 0.

Because `voteCount` here is the witness's *live, mutable* vote count (not a per-cycle-committed snapshot of votes at the *start* of the cycle when the reward was earned), a normal, permissionless sequence of votes/un-votes by ordinary accounts can zero it out right before maintenance runs, even though the witness held non-zero votes (and produced reward-earning blocks) during most of the cycle.

### Impact Explanation
This is a protocol-level reward accounting corruption reachable purely through ordinary, unprivileged `VoteWitnessContract` broadcast transactions plus normal block production/maintenance — no privileged actor, leaked key, or malicious peer is required. The impact:
- Reward TRX that has legitimately accrued to a witness's voters for a cycle becomes permanently unclaimable by any voter, current or future.
- This creates a systemic, protocol-wide (consensus-level) discrepancy between reward amounts recorded in `DelegationStore` (`addReward`) and amounts actually distributable via the `Vi` mechanism used by `MortgageService.computeReward` / `VoteRewardUtil.computeReward`, i.e. a consensus-visible accounting corruption affecting all java-tron nodes identically (deterministic, not a fork risk, but a real, permanent value-loss/DoS-on-rewards issue).

### Likelihood Explanation
Any account can trigger `VoteWitnessContract` to vote for or clear votes from a witness at any time, and maintenance runs automatically on a fixed schedule. A witness whose voters withdraw/clear their votes shortly before a maintenance cycle boundary — a scenario with no special preconditions beyond ordinary user behavior — will trip `voteCount == 0` while `reward != 0`, causing the loss deterministically every time this occurs.

### Recommendation
Do not silently drop the cycle's reward when `voteCount == 0`. Instead, carry the un-distributable `reward` amount forward (e.g., accumulate it into the next cycle's `reward` value via `addReward(cycle + 1, address, reward)` before zeroing/leaving the current cycle's reward, or explicitly credit it back to the witness/brokerage) so funds are not permanently stranded, mirroring the RangePool fix of not consuming the elapsed-window amount when the divisor is zero and instead deferring it to when votes (liquidity) return.

### Proof of Concept
1. A witness has voters and earns block reward during cycle `N` via `MortgageService.payReward` → `delegationStore.addReward(N, witness, value)`.
2. All voters for that witness broadcast `VoteWitnessContract` clearing their votes before the next maintenance runs, immediately zeroing `WitnessCapsule.voteCount` via `VoteWitnessActuator.countVoteAccount`.
3. At maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, witness, 0)`.
4. Inside `accumulateWitnessVi`, since `voteCount == 0`, the `else` branch (delta-Vi accumulation) is skipped; `Vi[N]` is only ever set equal to `Vi[N-1]` (or left unset).
5. `getReward(N, witness)` remains non-zero in storage forever, but no voter's `computeReward` call (which relies solely on `Vi` deltas) can ever recover this value — the reward is permanently lost. [4](#0-3) [2](#0-1)

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
