### Title
Exchange Creator Can Unilaterally Rewrite AMM Pool Ratio via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, Breaking Pending Trade Expectations - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
Java-tron's bancor-style exchange (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) lets the exchange creator unilaterally change the pool's `firstTokenBalance`/`secondTokenBalance` ratio at any time, with no freeze, cooldown, or consent mechanism, while other unprivileged users' `ExchangeTransactionContract` trades are pending. This is the same root-cause pattern as the reported `setWhitelistReserve()` bug: an actor with control over one allocation/settlement parameter can rewrite it after other participants have committed funds based on the pre-change state, without any lock or notice period.

### Finding Description
`ExchangeCreateActuator` allows any account to become the "creator" of an exchange pool — this is not a privileged/consensus role, just the account that funded the initial pool. That creator can then call `ExchangeInjectContract` or `ExchangeWithdrawContract` at any time to add or remove liquidity, directly mutating the pool balances used to price every subsequent trade: [1](#0-0) [2](#0-1) 

Validation only checks that the caller is the exchange's creator — there is no restriction tied to sale/settlement phase, no time-lock, and no requirement that the pool be otherwise idle: [3](#0-2) 

Meanwhile, ordinary users submit `ExchangeTransactionContract` trades expecting a certain conversion rate based on the pool state at submission time. The actual exchange rate is computed against whatever pool balances exist when the transaction executes: [4](#0-3) [5](#0-4) 

Because transaction ordering within a block is determined by the block producer (not the submitter), and because `ExchangeInjectContract`/`ExchangeWithdrawContract` can be broadcast and packed ahead of a pending `ExchangeTransactionContract`, the creator can reshape the pool ratio immediately before another user's trade executes — exactly analogous to changing `whitelistReserve` after deposits are already committed. The user has no way to withdraw or cancel once their trade is broadcast, and no consent/warning mechanism exists for the ratio change.

### Impact Explanation
- A user submits an `ExchangeTransactionContract` expecting a given `anotherTokenQuant` based on the current pool ratio.
- The creator injects or withdraws liquidity via `ExchangeInjectActuator`/`ExchangeWithdrawActuator` to shift the ratio in their favor before the user's trade lands in the same or an adjacent block.
- The user's trade executes against the manipulated ratio, receiving a worse-than-expected `anotherTokenQuant`, while the creator profits from the price shift (sandwich-style extraction) — a concrete accounting/settlement mismatch between what the user expected and what they receive.
- This directly parallels Scenario 1/2 in the original report: economic expectations set at commit time are broken by a unilateral parameter change with no consent mechanism and no ability to withdraw after the fact.

### Likelihood Explanation
Any account can create an exchange (`ExchangeCreateActuator`) and become its creator, and inject/withdraw actions require no elevated permission beyond being that creator — this is fully reachable by unprivileged users. The `ExchangeInjectContract`/`ExchangeWithdrawContract` validation logic imposes no timing restriction relative to pending trades, only a balance-limit cap: [6](#0-5) 

Exploitation requires only observing a pending trade in the mempool and submitting an inject/withdraw transaction before it is packed — a standard front-running technique already broadly documented against AMM-style pools.

### Recommendation
- Add a time-lock or cooldown between the exchange creator's inject/withdraw actions and subsequent trade execution (e.g., require injects/withdraws to only apply starting the next block), similar to freezing `whitelistReserve` once the sale phase begins.
- Alternatively, bound the maximum ratio-shift per inject/withdraw operation, or require inject/withdraw operations to be batched/settled atomically with pending trades rather than allowing arbitrary reordering.
- Consider disallowing creator-only inject/withdraw entirely in favor of a permissionless liquidity provisioning model with slippage protection enforced on `ExchangeTransactionContract` (an `expected` minimum is already present but does not fully prevent sandwiching within the same tolerance band).

### Proof of Concept
1. Account A creates an exchange pool with tokens X/Y via `ExchangeCreateContract`, becoming the creator.
2. Account B broadcasts `ExchangeTransactionContract` to sell token X for Y, expecting rate R based on current pool balances.
3. Before B's transaction is packed, A broadcasts `ExchangeWithdrawContract` (or `ExchangeInjectContract`) that shifts the pool ratio unfavorably for B — validated solely via the creator check in `ExchangeWithdrawActuator.doValidate()`.
4. Both transactions land in the same/adjacent block; B's trade executes against the shifted ratio in `ExchangeCapsule.transaction()`, yielding materially less `anotherTokenQuant` than expected, while A immediately reverses the injection/withdrawal to capture the spread.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
