### Title
Missing cross-check between session-token `dest` claim and caller-supplied `shop` parameter allows shop/session confusion in token exchange - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
The bug class in the report is "act first, validate the relevant data second" — a state-changing operation (`apply_diff`) is performed using data that is only validated afterward, and the validation ends up checking a state that has already been polluted by the very operation it's supposed to gate. The `tokenExchange` flow in `shopify-app-js` has an analogous ordering problem: it performs the security-sensitive operation (exchanging a session token for an access token at `https://{shop}/admin/oauth/access_token`, then keying/creating a `Session`) using a caller-supplied `shop` value, while the one piece of data that actually authenticates which shop the token belongs to (the verified JWT's `dest`/`iss` claim) is decoded but never compared against that `shop` value.

### Finding Description
`tokenExchange` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` does: [1](#0-0) 

It calls `await decodeSessionToken(config)(sessionToken);` purely to verify the JWT signature/audience, and discards the returned payload. It then derives `cleanShop` solely from the `shop` argument passed in by the caller, uses it to build the token-exchange HTTP request, and uses it again to construct the resulting `Session`: [2](#0-1) 

`decodeSessionToken` only validates the signature and (optionally) the `aud` claim — it never validates `dest`/`iss` against the shop being acted upon: [3](#0-2) 

The `shop` value that reaches this function in the Remix/React Router strategies is taken straight from the unauthenticated `?shop=` query parameter of the incoming HTTP request, not from the verified token: [4](#0-3) 

That `shop` is passed straight through the token-exchange strategy into `exchangeToken`/`api.auth.tokenExchange` and then into `config.sessionStorage!.storeSession(...)`: [5](#0-4) 

So, just like `_execute_transfer` applies `position_diff_sender` before validating the sender's post-state health, this code performs the state-changing action (calling Shopify's OAuth token endpoint for `shop`, then persisting a `Session` keyed by `shop`) before/without validating that `shop` is the same tenant the presented, cryptographically-verified session token was actually issued for.

### Impact Explanation
If Shopify's own `/admin/oauth/access_token` endpoint does not independently reject a `subject_token` whose `dest`/`iss` doesn't match the shop in the URL, this ordering bug would let a request bearing a valid session token for shop A cause the app to exchange it against shop B's endpoint and store/associate the resulting session under shop B (session-storage keying/cross-tenant confusion) — because the local app code never checks `payload.dest` against the incoming `shop` parameter before acting. This falls into the "cross-tenant access / session-storage injection" category called out as in-scope.

### Likelihood Explanation
Likelihood is uncertain and cannot be fully confirmed from this codebase alone: Shopify's remote OAuth token-exchange endpoint may itself enforce that the `subject_token`'s destination matches the shop in the request URL, which would prevent exploitation server-side even though the local `shopify-app-js` code performs no such check. Because this repository has no visibility into Shopify's server-side enforcement, the app-level code should not rely solely on that external guarantee — the missing local validation is a defense-in-depth gap rather than a confirmed exploitable path.

### Recommendation
In `tokenExchange` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), use the `payload` returned by `decodeSessionToken` and assert that `shop`/`cleanShop` matches the shop derived from `payload.dest` (or `payload.iss`) before issuing the token-exchange request or constructing the `Session`. Reject the request (throw an `InvalidJwtError`/`InvalidShopError`) if they don't match, mirroring how `_execute_transfer` should validate before, not after, applying its diff.

### Proof of Concept
Conceptual PoC (cannot be executed against this index, but derivable from the cited code paths):
1. Obtain a valid session token (`sessionToken`) legitimately issued by Shopify for `shop-a.myshopify.com` (e.g., via App Bridge on that shop).
2. Send a request to the app's authenticated route with `?shop=shop-b.myshopify.com` and `Authorization: Bearer <sessionToken-for-shop-a>` (or `id_token` query param).
3. `getShopFromRequest` extracts `shop-b.myshopify.com` from the query string — this value is never cross-checked against the token.
4. `tokenExchange` calls `decodeSessionToken` (which only checks signature/`aud`, both shop-independent) and proceeds to call `https://shop-b.myshopify.com/admin/oauth/access_token` and to build/store a `Session` for `shop-b.myshopify.com` using the token that was actually issued for `shop-a.myshopify.com`.
5. Whether step 4 ultimately succeeds depends on whether Shopify's remote token endpoint independently rejects the mismatched `dest`; the local code provides no such check itself.

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
