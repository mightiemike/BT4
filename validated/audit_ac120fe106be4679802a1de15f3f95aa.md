### Title
Unauthenticated `batchProver_setCommitments` RPC Method Allows Forging Sequencer Commitments - (File: `crates/batch-prover/src/rpc.rs`)

### Summary
The batch prover exposes a JSON-RPC method, `batchProver_setCommitments`, that directly overwrites the ledger database's sequencer-commitment records (merkle root, L2 end height, L1 height, pending-proof queue) with attacker-supplied values, with **no authentication and no verification that the commitment actually originated from the sequencer's signed L1 commitment**. Unlike the `backup_create`/`backup_validate`/`backup_info` endpoints, which are explicitly gated behind an API key in the shared `Auth` RPC middleware, `setCommitments` is a state-mutating "capability" that was left out of the protected-method list — mirroring the WooCommerce bug class where a sensitive capability (`edit_users`) was left ungated while a comparable one was correctly restricted.

### Finding Description
The RPC `Auth` middleware only protects three hard-coded methods: [1](#0-0) 

Every other registered method, including all batch-prover RPCs, passes straight through to the handler unauthenticated: [2](#0-1) 

`batchProver_setCommitments` is declared as a normal, unauthenticated method in the batch-prover RPC trait: [3](#0-2) 

Its implementation takes attacker-controlled `merkle_root`, `index`, and `l2_end_block_number` values and writes them straight into the ledger DB's commitment tables and the prover's pending-commitment queue, with no signature check against the sequencer's public key and no cross-check against commitments actually observed on L1: [4](#0-3) 

This breaks the binding that should hold between "sequencer commitment authorised by the sequencer's key" and "commitment the batch prover treats as pending/valid to prove," since anyone who can reach the batch prover's RPC port can inject or override that commitment record directly, bypassing the entire L1-scanning/signature-verification pipeline that normally populates these tables.

### Impact Explanation
An unauthenticated network caller can overwrite a legitimate sequencer commitment's `merkle_root` (or inject a bogus index/height pair) and mark it `prover_pending`. Subsequent calls to `prove`/`createCircuitInput`/`submitFakeProof` operate on this poisoned commitment data: [5](#0-4) 

This can cause the prover to build/prove/submit a batch proof over a forged commitment rather than the one actually authorised by the sequencer's key, directly matching the "unauthorised sequencer commitment" / "false state transition proved" impact class. At minimum it always satisfies the "High" bar: an unauthenticated JSON-RPC call mutates critical node state and bypasses `Auth`.

### Likelihood Explanation
No credentials, roles, or special access are required — only network reachability to the batch prover's already-listening JSON-RPC endpoint, the same reachability an attacker would need for the correctly-protected `backup_*` methods. The method is registered unconditionally whenever the batch-prover RPC module is built, with no feature flag or config gate visible in `crates/batch-prover/src/rpc.rs`.

### Recommendation
Add `setCommitments` (and other state-mutating batch-prover admin RPCs such as `submitFakeProof`, `pauseProving`, `retryProvingJob`) to the `PROTECTED_METHODS` list in `crates/common/src/rpc/auth.rs`, or otherwise require API-key/local-only authentication before these handlers can mutate the ledger DB or prover queue. Additionally, `set_commitments` should verify the supplied commitment against a real sequencer-signed source before persisting it.

### Proof of Concept
1. Reach the batch prover's JSON-RPC endpoint (no API key needed, since `setCommitments` isn't in `PROTECTED_METHODS`).
2. Call:
```json
{"jsonrpc":"2.0","id":1,"method":"batchProver_setCommitments","params":[[{"merkle_root":"0x<attacker_root>","index":<existing_index>,"l2_end_block_number":<n>,"l1_height":<h>}]]}
```
3. The handler at `crates/batch-prover/src/rpc.rs:345-378` overwrites `put_commitment_by_index`, `put_commitment_index_by_l1`, and `put_prover_pending_commitment` with the attacker's data — no signature or L1 cross-check is performed.
4. Trigger `batchProver_prove` or `batchProver_submitFakeProof` on the poisoned index to have the prover act on the forged commitment.

    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }
