## Analysis

The Vault report's root cause is: unbounded, unchecked growth of a per-entity list (deposits) triggered by cheap, repeatable, unprivileged actions, which degrades the batch-processing mechanism that must load/iterate the whole list.

The closest concrete analog in `shopify-app-js` is in the OAuth online-session ID generation combined with the session-storage adapters' shop-session index list, which grows without any bound or size limit as a single authorized actor repeats the (non-embedded) OAuth online flow.

### Title
Unbounded Growth of Shop Session Index Enables Storage/Auth-Handler DoS via Repeated Online OAuth - (File: packages/apps/shopify-api/lib/auth/oauth/create-session.ts)

### Summary
For non-embedded apps, every completed online-access OAuth callback generates a brand-new random session ID (`crypto.randomUUID()`) instead of a deterministic, per-user ID. Each `storeSession()` call for that ID unconditionally appends the new ID to a per-shop index list (`addKeyToShopList` in Redis, `addShopIds` in the Cloudflare KV adapter) with no cap, deduplication-by-user, or expiry pruning. A single authorized (but otherwise unprivileged) app user can script repeated `/auth?...&isOnline=true` round-trips to make this per-shop index grow without bound, mirroring the Vault bug where unchecked minimal deposits accumulate in an unbounded processing array.

This is directly analogous to the Vault's `depositToProcess`/`deposits` arrays growing unbounded because `userDeposit()` never enforced a minimum-size (or here, a maximum-count / dedup) check, which then degraded `startBatchProcess`/`continueBatchProcess`.

### Impact Explanation
As the shop's session-index array grows (each entry is a full session ID string), operations that must load and rewrite it degrade linearly, then may hit provider value-size limits (e.g., Cloudflare KV ~25MB per value, Redis string practical limits) causing `storeSession()`/`addShopIds()`/`addKeyToShopList()` to fail outright. Since `storeSession()` is called synchronously inside the OAuth callback handler (`auth-code-flow.ts` line 197) before the app can complete authentication, a sufficiently bloated shop index effectively **breaks the OAuth callback / auth handler for that shop** — a denial of service of the authentication pipeline — and also degrades or breaks `findSessionsByShop()`, which is used by cleanup/uninstall and GDPR webhook handlers across the framework adapters.

### Likelihood Explanation
The action required (repeatedly completing the non-embedded online OAuth flow for the same shop/user) needs only normal, already-granted staff/customer access to the app — no secret disclosure, no signature forgery, and no elevated privilege. Since an already-installed app typically auto-approves reauthorization without further Shopify-side friction, a single actor can script this loop to add an arbitrary number of entries per run, making growth to problematic size a low-effort, low-cost, and fully automatable path — the same pattern used in the analogous Vault DoS (unlimited cheap deposits, no size/count cap).

### Recommendation
- Make online session IDs deterministic and reusable for a given shop+user in the non-embedded path as well (mirroring the embedded JWT-based `getJwtSessionId` approach), so repeated logins overwrite rather than append.
- Enforce a maximum size/count on the per-shop session index list in each `SessionStorage` adapter (Redis, KV, and others using similar index lists), pruning expired/duplicate entries on write.
- Add rate limiting to the OAuth begin/callback endpoints for a given shop+user to prevent rapid repeated re-authentication from ballooning storage structures.

### Proof of Concept
1. Deploy a non-embedded app configuration (`isEmbeddedApp: false`) using `RedisSessionStorage` or `KVSessionStorage`.
2. As an authorized staff user of an installed shop, repeatedly hit `GET /auth?shop=<shop>&isOnline=true` followed by completing the resulting `/auth/callback` redirect (scriptable via a loop reusing the shop's already-granted authorization).
3. Each iteration produces a new `crypto.randomUUID()` session ID (`create-session.ts` line 40), calling `storeSession()`, which appends to the shop's index array with no limit (`redis.ts` `addKeyToShopList`, lines 151-166).
4. Observe the per-shop index key (`shopKey` in Redis, `shop:<shop>` in KV) grow linearly with each loop iteration, with no cap; continued execution demonstrates unbounded growth, increasing latency of subsequent `storeSession`/`findSessionsByShop` calls and eventually risking write failures once provider value-size limits are hit, breaking the OAuth callback flow for that shop.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    await this.ready;

    const idKeysArrayString = await this.client.get(shop);
    if (!idKeysArrayString) return [];

    const idKeysArray = JSON.parse(idKeysArrayString);
    const results: Session[] = [];
    for (const idKey of idKeysArray) {
      const rawResult = await this.client.get(idKey, false);
      if (!rawResult) continue;

      const session = Session.fromPropertyArray(JSON.parse(rawResult), true);
      results.push(session);
    }

    return results;
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
