### Title
Wallet Contract pays the relayer's emulated-transaction fee unconditionally before the target action is verified or executed, allowing fee extraction on failed/replayed transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
This is the closest reachable analog to the reported "DAI is assumed to have the same price as DAIx" bug class: a token value transfer is fired for one leg of a two-leg operation (fee-to-relayer) without being conditioned on the success of the other, logically-coupled leg (the user's actual emulated action). In the original report, DAI and DAIx were both moved as if they represented one unit of value with no invariant tying them together; here, the wallet contract's relayer-fee `Transfer` promise is dispatched unconditionally in `inner_rlp_execute`, decoupled from whether the target action (including the async `address_check_callback`/`nep_141_storage_balance_callback` verification chain) ultimately succeeds or is later judged to be a "faulty relayer" attempt.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) parses the RLP-encoded Ethereum transaction and, for `EOABaseTokenTransfer` and `ERC20Transfer` emulation kinds carrying a non-zero `fee`, immediately fires a fee-transfer promise to the predecessor (relayer): [1](#0-0) 

This fee payment happens *before* the actual target action promise is constructed and *before* any asynchronous verification of the target address completes. Specifically, when `address_check: Some(address)` (i.e. the target resolves to another eth-implicit account requiring a registrar lookup), the nonce is deliberately **not** incremented at this point: [2](#0-1) 

The registrar lookup and its outcome are only resolved later in `address_check_callback`, which — if the address turns out to correspond to an existing named account (i.e., the relayer supplied a bad `target`) — bans the relayer and does not increment the nonce, explicitly to allow the same user-signed transaction to be resubmitted by "an honest relayer": [3](#0-2) 

Because the fee-transfer promise in `inner_rlp_execute` was already dispatched at the very start of the flow — unconditionally, and prior to the address_check outcome and prior to the nonce being consumed — the relayer fee is paid out of the wallet contract's own balance regardless of whether:
1. the target-address check subsequently fails ("faulty relayer"), or
2. the underlying action (e.g., ERC-20 `ft_transfer`, or the storage-deposit + transfer chain in `nep_141_storage_balance_callback`) subsequently fails in `rlp_execute_callback`, in which case only the *external caller's attached deposit* is refunded via `CallerDeposit`, never the fee already paid to the relayer: [4](#0-3) 

Since the nonce is not incremented in the "faulty relayer" / address-check-failure path, the same signed Ethereum transaction (and therefore the same fee-bearing payload) remains valid and can be resubmitted an unbounded number of times by any relayer — each resubmission triggers the same unconditional fee payment from the wallet's balance in `inner_rlp_execute`, independent of whether the eventual execution succeeds.

### Impact Explanation
`rlp_execute` is callable by any unprivileged account acting as a relayer (confirmed by `rlp_execute_from` being invoked from an arbitrary `caller: &Account` in the test suite, with no special access-key requirement for external callers). A relayer can therefore repeatedly submit (or cause replay of) the user's signed transaction whose `target` deliberately resolves through the `address_check: Some(address)` path, collecting the fee payment from the wallet contract's balance each time, before the address-check callback determines the relayer is "faulty" and bans it — but without the nonce being consumed, allowing the drain to repeat. This constitutes unauthorized value movement out of the ETH-implicit account's NEAR balance, decoupled from the wallet owner's actual, successfully-executed intent, directly analogous to the original bug where two coupled token movements (DAI/DAIx) were not enforced to represent a single, atomic value transfer.

### Likelihood Explanation
Reaching this path requires only: (1) an eth-implicit account with a deployed Wallet Contract holding a NEAR balance, (2) a signed Ethereum transaction (which a user must have produced) specifying a non-zero fee for an `EOABaseTokenTransfer` targeting another eth-implicit account, and (3) any account acting as relayer submitting it via `rlp_execute`/`rlp_execute_from`, no special privileges needed. The precondition that a user must have signed a fee-bearing transaction narrows likelihood somewhat, but there is no invariant in the contract that prevents a colluding or malicious relayer from repeatedly resubmitting the same non-nonce-consuming transaction to keep extracting the fee before/without triggering successful completion.

### Recommendation
Do not dispatch the relayer-fee transfer as an independent, unconditional promise at the start of `inner_rlp_execute`. Instead, chain the fee-transfer as a dependent step of the same promise (e.g., only executed within `rlp_execute_callback` conditioned on `PromiseResult::Successful`), or track the fee similarly to `CallerDeposit` so that it can be reconciled/reverted if the target action or address-check ultimately fails. Additionally, consider consuming the nonce (or otherwise recording a single-use marker) as soon as the fee-bearing promise is dispatched, so that a "faulty relayer" outcome cannot be paired with an unbounded number of fee-collecting replays.

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account `W` funded with NEAR balance, owned by user `U`.
2. `U` signs an Ethereum-style `EOABaseTokenTransfer` transaction with `to` set to an address that plausibly maps to another eth-implicit account, and with a non-zero `fee` for the relayer, at the current nonce `n`.
3. Attacker `R1` (unprivileged, arbitrary NEAR account) calls `rlp_execute(target = "<crafted-account>", tx_bytes_b64 = ...)` where `target` is chosen so `address_check: Some(address)` triggers.
4. `inner_rlp_execute` immediately creates a promise transferring `fee` NEAR from `W` to `R1` (`lib.rs:381-384`), then dispatches the registrar lookup + `address_check_callback` chain, without incrementing `nonce` (`lib.rs:358-365`).
5. `address_check_callback` resolves that `address` actually corresponds to an existing named account, deeming `R1` a "faulty relayer"; `R1`'s key (if any) is banned but the nonce is **not** incremented.
6. Because the nonce is unchanged, the same signed transaction (still valid for nonce `n`) can be resubmitted via `rlp_execute` by attacker-controlled account `R2` (or `R1` via a fresh call from a different account without a registered relaying key), re-triggering step 4's fee payment again.
7. Repeat steps 3–6 to repeatedly drain `fee` amounts from `W`'s balance without the user's intended action ever completing successfully.

**Note on completeness**: I was unable to fully trace whether `create_ban_relayer_promise`'s account-level effects (beyond key-revocation for access-key relayers) prevent replay by a *different* unprivileged NEAR account acting as an external caller (i.e., whether the "single in-flight transaction" invariant `has_in_flight_tx` or some other mechanism blocks this specific replay path for non-access-key relayers). This should be verified with a live Devin session against the full `runtime/near-wallet-contract` implementation and its `tests/relayer.rs` suite before treating this as a fully confirmed, unconditionally repeatable drain.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
