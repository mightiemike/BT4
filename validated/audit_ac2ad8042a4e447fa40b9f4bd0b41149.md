### Title
Nightly and TestNetworkWithForks share chain_id 5665, allowing cross-network replay of a security-council-signed `BatchProofMethodId` upgrade - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the identical constant `5665`. In `run_l1_block`'s `DataOnDa::BatchProofMethodId` handling, the only network-binding check is `circuit_chain_id != batch_proof_method_id.body.chain_id`, so a council-signed method-id upgrade blob authorized with `chain_id = 5665` for one of these networks is also accepted by the other, since the signed message body only contains `chain_id`, not a network discriminant.

### Finding Description
The claimed binding is: `body.chain_id == chain_id of the single network the council intended to authorise`. In code, this reduces to `citrea_network_to_chain_id(network) == body.chain_id`, checked at [1](#0-0) . Since `citrea_network_to_chain_id` returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks` [2](#0-1) , this equality holds identically for both networks given the same signed body. The security-council signature covers only `batch_proof_method_id.body.serialize()`, i.e. `{method_id, activation_l2_height, chain_id}` [3](#0-2) , with no network tag distinguishing Nightly from TestNetworkWithForks. Consequently the same inscribed blob, if replayed on a light-client-prover instance configured for the other network (with the same `method_id_upgrade_authority_da_public_keys`), passes both the chain-id check and the signature verification identically.

### Impact Explanation
This lets a method-id upgrade signed by the security council for one test network be silently activated on the other network sharing chain id 5665, without renewed council consent for that specific target — this is the "method-id upgrade accepted that was never authorised" category. However, the practical blast radius is constrained by the code comment itself: `TestNetworkWithForks` is explicitly documented as "used for testing purposes only" [4](#0-3)  and drives a distinct, accelerated fork schedule (`ALL_FORKS`, activation heights 100/200/210/220) versus Nightly's single-fork schedule (`NIGHTLY_FORKS`) [5](#0-4) , indicating it is a local/test-harness configuration rather than a persistently co-deployed live network alongside Nightly. Whether Nightly and TestNetworkWithForks are ever simultaneously live public deployments sharing the same council DA public keys is a deployment/ops configuration question outside what the repository code can confirm — I could not find evidence in-repo of both being deployed concurrently with identical `method_id_upgrade_authority_da_public_keys`.

### Likelihood Explanation
Exploitation requires: (1) both networks to be live simultaneously, (2) both configured with the identical security council DA public keys, and (3) the attacker to obtain and inscribe a genuinely 3-of-5 council-signed blob targeting one of the networks and relay/mine the identical bytes as a DA transaction against the other network's honest full nodes. Given `TestNetworkWithForks` is marked test-only tooling rather than a standing public network, and no repo evidence shows both networks being run concurrently with shared council keys in production, live-exploitability is uncertain from code alone.

### Recommendation
Bind the signed `BatchProofMethodIdBody` (or the message passed to `verify_method_id_security_council`) to a network-specific discriminant distinct from the numeric chain id — e.g. use the `Network` enum variant name/genesis hash as part of the signed payload, or assign `TestNetworkWithForks` its own unique chain id constant instead of reusing `5665`.
