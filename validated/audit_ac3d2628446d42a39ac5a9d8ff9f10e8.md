### Title
Outbound `gas_price` is snapshotted once at PC-execution time and never re-priced before TSS-signing/broadcast, permanently stalling fund delivery under rising destination-chain gas — ([File: x/uexecutor/keeper/create_outbound.go], [File: universalClient/chains/evm/tx_builder.go])

### Summary
This is the direct on-chain analog of the reported `sigFees`/`tx.gasprice` issue: Push Chain fixes the destination-chain `gas_price` for an outbound at the moment the outbound is created on Push Chain (from a single `UniversalCore.getOutboundTxGasAndFees` read), bakes that exact value into the legacy (`type-0`) transaction that the TSS committee signs, and never revisits it. If the destination chain's real gas price rises before the TSS-signed transaction is mined, the transaction is underpriced, cannot be replaced (the signature covers the price), and the resolver logic offers no re-pricing path — only re-broadcast of the identical, still-underpriced transaction.

### Finding Description
When an inbound execution produces an outbound (a withdrawal/finalize/revert/rescue call to the destination-chain Vault), the keeper snapshots `gasPrice` from `UniversalCore.getOutboundTxGasAndFees` at that single block and stores it immutably on the `OutboundTx` record and in the emitted `OutboundCreatedEvent`: [1](#0-0) [2](#0-1) 

That snapshot is placed on `PendingOutbounds` and picked up later by the Universal Client's TSS coordinator, whenever a coordinator becomes available and a signing session succeeds — this can be an arbitrary number of blocks after outbound creation: [3](#0-2) 

The EVM `TxBuilder` then builds a **legacy** (`types.NewTransaction`, no EIP-1559 fields) transaction using that stale `data.GasPrice` value verbatim, and the TSS committee signs the resulting hash: [4](#0-3) 

Because the gas price is part of the signed transaction body, once TSS has produced a signature over that hash, the price can never be bumped without an entirely new signing ceremony — and no such re-pricing/re-signing flow exists. `BroadcastOutboundSigningRequest` reuses the same fixed `data.GasPrice` to reassemble and re-apply the existing signature on every (re)broadcast attempt: [5](#0-4) 

The only feedback loop after broadcast is the resolver, which either detects the nonce was consumed (funds "lost"/reverted) or, if the nonce is still available, simply rewinds the event back to `SIGNED` so the broadcaster **resubmits the identical, identically-priced transaction**: [6](#0-5) 

If the destination chain's gas price has risen above the snapshotted value (network congestion, MEV, gas spikes — none of which require any attacker action), the transaction sits underpriced in every subsequent broadcast attempt with no automatic remediation. The module's own documentation confirms `PendingOutbounds` entries are **not** auto-resolved on stagnation — resolution is explicitly "governance-driven, not chain-driven": [7](#0-6) 

This is architecturally identical to the reported bug class: a `gasPrice`-based fee is fixed once, ahead of time, and never adjusted for real execution-time market conditions, so a legitimate, ordinary user's cross-chain transfer can become permanently un-deliverable purely from network gas fluctuation, with no in-protocol recovery mechanism (no bump-fee, no re-sign, no auto-refund/abort).

### Impact Explanation
User-initiated outbounds (fund withdrawals, reverts, rescues) can become permanently stuck if the destination-chain gas price rises between outbound creation and TSS broadcast completion. Because `PendingOutbounds` entries are never auto-cleared on stagnation and resolution requires manual governance intervention, this results in indefinite freezing of the underlying user funds already committed on Push Chain's side (PRC20 burned / vault liability created) with no destination-chain delivery and no automatic refund path.

### Likelihood Explanation
No attacker action is required — ordinary gas-price volatility on any moderately congested destination chain (the exact scenario in the source report) is sufficient. The wider the delay between outbound creation and successful TSS signing/broadcast (validator rotation, signing-session retries, coordinator downtime), the higher the chance the snapshotted price is stale by the time of broadcast.

### Recommendation
Do not permanently bind a gas price into the TSS-signed payload from a single stale snapshot. Options: (1) migrate outbound broadcasting to EIP-1559 dynamic fee transactions with headroom, refreshed at broadcast time rather than at outbound-creation time; (2) support a re-quote-and-re-sign flow that lets validators, upon detecting a stuck/underpriced pending outbound (e.g., past a max wait or several failed mine attempts), trigger a new signing session with an updated gas price for the same nonce; (3) add an automated escalation/abort-and-refund path for outbounds stuck past a bounded timeout, instead of relying solely on manual governance intervention.

### Proof of Concept
1. A user submits an inbound that produces an `OutboundTx` targeting `eip155:X`; at that block, `GetOutboundTxGasAndFees` returns `gasPrice = P0` (current market price), stored on the outbound and emitted in `OutboundCreatedEvent`.
2. Before the TSS coordinator completes a signing session for this outbound (e.g., due to committee rotation, an interrupted DKLS session, or simply queueing behind other pending outbounds), gas price on chain `X` rises to `P1 > P0` due to normal congestion.
3. TSS signs the outbound transaction using the stale `P0` (`GetOutboundSigningRequest`), and the broadcaster submits it (`BroadcastOutboundSigningRequest`) — the tx sits in the destination mempool underpriced relative to `P1`.
4. `resolveOutboundEVM` finds the tx `not found` and the nonce still available (`NonceAvailable`), so it rewinds the event to `SIGNED`; the broadcaster resubmits the exact same underpriced, already-signed transaction on every subsequent tick.
5. As long as gas price on chain `X` stays at or above `P0`, the transaction never mines. `PendingOutbounds` retains the entry indefinitely (per README, ballot/entry expiry does not clean it up), and the user's funds remain undelivered with no automatic recovery.

func (k Keeper) GetOutboundTxGasAndFees(ctx sdk.Context, prc20 common.Address, gasLimitWithBaseLimit *big.Int) (*GasFeeInfo, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	ucABI, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UniversalCore ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	receipt, err := k.evmKeeper.CallEVM(ctx, ucABI, ueModuleAccAddress, handlerAddr, false, nil,
		"getOutboundTxGasAndFees", prc20, gasLimitWithBaseLimit)
	if err != nil {
		return nil, errors.Wrap(err, "failed to call getOutboundTxGasAndFees")
	}

	results, err := ucABI.Methods["getOutboundTxGasAndFees"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack getOutboundTxGasAndFees result")
	}

	gasToken := results[0].(common.Address)
	gasFee := results[1].(*big.Int)
	// protocolFee := results[2].(*big.Int) — not needed for outbound fields
	gasPrice := results[3].(*big.Int)
	// chainNamespace := results[4].(string) — not needed for outbound fields
	// gasLimitUsed (results[5]) is the exact gas limit the contract resolved
	// (caller-supplied or per-chain baseGasLimitByChainNamespace fallback).
	// Reading it directly avoids the gasFee/gasPrice round-trip and keeps us
	// in lock-step with the contract's own resolution.
	gasLimit := results[5].(*big.Int)

	return &GasFeeInfo{
		GasToken: gasToken,
		GasFee:   gasFee,
		GasPrice: gasPrice,
		GasLimit: gasLimit,
	}, nil
}

- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.
