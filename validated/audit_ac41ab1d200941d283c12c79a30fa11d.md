Based on my investigation, I found a genuine analog of the Zebra bug class in nearcore. Both cases share the exact CWE-696 "Incorrect Behavior Order" pattern: a validation check that should cleanly reject bad input exists in the code, but a *different* code path reaches an unrecoverable `panic!` before that validation runs — for input that a single attacker-controlled cross-shard receipt can produce.

### Title
Malicious cross-shard receipt with an oversized payload triggers a process-halting `panic!` in `apply_chunk` instead of clean rejection - ([File: chain/chain/src/runtime/mod.rs])

### Summary
`Runtime::apply` validates every **new** receipt created during action execution via `validate_receipt(..., ValidateReceiptMode::NewReceipt)` [1](#0-0) , and it validates every **incoming** cross-shard receipt via `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)`, converting a failure directly into `RuntimeError::ReceiptValidationError` [2](#0-1) . `ReceiptValidationError` is explicitly documented as "the incoming receipt didn't pass the validation, it's likely a malicious behavior" [3](#0-2) , i.e. this is the intended, graceful rejection path for a malicious/invalid receipt.

However, the caller of `Runtime::apply` at the chunk-application layer maps this exact, expected error variant to a hard `panic!`, tagged with a TODO admitting it should be handled gracefully:

```rust
// TODO(#2152): process gracefully
RuntimeError::ReceiptValidationError(e) => panic!("{}", e),
``` [4](#0-3) 

### Finding Description
The bug-class match to the Zebra report is precise: Zebra has a nullifier-uniqueness check in `Chain::push` that *would* correctly reject the duplicate transaction, but an earlier `assert_eq!` on the `tx_loc_by_hash` index fires first and aborts the process. In nearcore, `validate_receipt` *would* correctly reject an oversized/malformed receipt with `ReceiptValidationError`, and that error even propagates correctly out of `Runtime::apply` as `Result::Err` — but the immediate caller in `NightshadeRuntime::apply_chunk` (via the `map_err` in the code path that invokes `self.runtime.apply(...)`) converts that clean, structured rejection into an unconditional `panic!("{}", e)` [5](#0-4) .

This is reachable from an ordinary transaction/contract call: a `FunctionCall` action can create a new outgoing action receipt (e.g., via a cross-contract promise) that is checked against `max_receipt_size`, `max_number_input_data_dependencies`, `max_length_returned_data`, or an invalid `refund_to`/`receiver_id` account id [6](#0-5) . `test_max_receipt_size_yield_resume` demonstrates that a contract call can be made to generate a receipt that trips `ReceiptSizeExceeded` [7](#0-6) ; that specific case is caught in `apply_action` before the receipt leaves the shard (turned into an `ActionErrorKind::NewReceiptValidationError` on the *same* chunk, so the *producing* shard doesn't panic there) [1](#0-0) .

The genuinely dangerous path is `ExistingReceipt`/incoming validation: `validate_receipt` is explicitly documented as tolerating receipts that "wouldn't pass new validation" because of "a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed" (referencing `near/nearcore#12606`) [8](#0-7) . This comment is itself an admission that receipts violating current limits can already exist/arrive from another shard as legitimate incoming traffic (e.g. created under an older, more permissive limit, or through the acknowledged bug), meaning `process_incoming_receipts` can hit `RuntimeError::ReceiptValidationError` on the **receiving** shard for a receipt that was accepted as valid on the **sending** shard. When that happens, the receiving validator's `apply_chunk` panics via the code cited above — an abort of the entire node process, not a rejection of a single chunk.

### Impact Explanation
This is a transaction/receipt-triggered halt: any validator applying the chunk that consumes the malformed incoming receipt panics. Because chunk application happens on every node tracking the shard, this can knock multiple/all nodes tracking a shard offline simultaneously — a liveness (denial-of-service) impact analogous to Zebra's node-abort, reachable without any privileged network/validator role, purely by getting a bad receipt onto the wire between shards.

### Likelihood Explanation
Medium. The comment in `verifier.rs` confirms this isn't purely theoretical — there is a documented history of receipts violating size limits reaching the incoming-receipt validation path under `ExistingReceipt` mode [8](#0-7) . Any mismatch between what's enforced at receipt-creation time on the sending shard and what `ExistingReceipt` mode checks on the receiving shard (e.g., due to a protocol-version-gated validation rule change, or the referenced historical bug) is enough to trigger the panic on every receiving validator. The TODO `#2152` explicitly documents this exact `panic!("{}", e)` on `ReceiptValidationError` as a known-bad handling pattern awaiting a real fix.

### Recommendation
Change `chain/chain/src/runtime/mod.rs`'s handling of `RuntimeError::ReceiptValidationError` to return a proper `Error` (e.g. treat the chunk as invalid / `Error::InvalidChunk` or similar) instead of `panic!`, mirroring how `RuntimeError::InvalidTxError` is already handled gracefully in the same match block [9](#0-8) . Additionally, audit `ValidateReceiptMode::ExistingReceipt` to confirm no currently-reachable path can produce a receipt on one shard that fails validation on the receiving shard; if such a gap exists (as the code comment suggests it historically did), it should be closed or the receiving side should downgrade the receipt to a delayed/rejected state rather than aborting.

### Proof of Concept
1. Deploy a contract that issues a `FunctionCall` promise to a receiver on a different shard, with parameters chosen to make the resulting receipt violate one of the `ExistingReceipt`-mode checks on the destination shard (e.g. crafted to exploit the referenced pre-fix condition in `near/nearcore#12606` that allowed oversized receipts to be created, or via a protocol-version boundary where the sending shard is on an older/looser rule set than the receiving shard).
2. The producing shard creates and forwards the receipt (it passed `NewReceipt`-mode validation there, or the historical bug bypassed it).
3. When the destination shard applies the chunk containing this receipt, `process_incoming_receipts` calls `validate_receipt(..., ExistingReceipt)`, which fails and returns `RuntimeError::ReceiptValidationError` [2](#0-1) .
4. `NightshadeRuntime::apply_chunk`'s error-mapping panics the process: `RuntimeError::ReceiptValidationError(e) => panic!("{}", e)` [4](#0-3) .
5. Every validator tracking that shard crashes when it applies the same chunk, producing a coordinated liveness outage.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
}
