The claim requires an attacker-controlled path that calls `set_ledger_update_output` with a `LedgerUpdateOutput` derived from an `ExecutionOutput` that differs from the one stored in the same `PartialStateComputeResult`. I traced every caller of `set_ledger_update_output` and `set_state_checkpoint_output` in the codebase, and none of them do this:

- `execution/executor/src/workflow/mod.rs` (`ApplyExecutionOutput::run`) builds `state_checkpoint_output`/`ledger_update_output` via `DoStateCheckpoint::run`/`DoLedgerUpdate::run` using the very same `execution_output` local variable that is then wrapped into `PartialStateComputeResult::new(execution_output)`, so they are always consistent. [1](#0-0) 
- `execution/executor/src/block_executor/mod.rs` (`ledger_update`) calls `DoLedgerUpdate::run(&output.execution_output, output.ensure_state_checkpoint_output()?, parent_out...)` — again derived from `output.execution_output`, the same struct's own field, and the accumulator chain comes from the immediate parent block's output. [2](#0-1) 
- `execution/executor/src/chunk_executor/mod.rs` (`update_ledger`) similarly calls `DoLedgerUpdate::run(&output.execution_output, &state_checkpoint_output, parent_accumulator.clone())`, using the chunk's own `execution_output`. [3](#0-2) 

In every call site, `DoLedgerUpdate::run` is fed the exact `ExecutionOutput` that already lives inside the same `PartialStateComputeResult` (`execution/executor/src/types/partial_state_compute_result.rs`), and the accumulator basis is chained from the correct parent (`parent_accumulator.num_leaves` == expected `first_version`), enforced structurally by the block tree (`block_executor/mod.rs`) and the chunk commit queue (`chunk_commit_queue.rs`). There is no code path reachable from unprivileged transaction/chunk input that supplies a `LedgerUpdateOutput` built from a *different* `ExecutionOutput` than the one stored alongside it — the two are always constructed together from the same source in a single synchronous call. The `OnceCell` semantics in `set_ledger_update_output`/`set_state_checkpoint_output` (`expect("... already set")`) additionally prevent any second, inconsistent write. [4](#0-3) 

Additionally, `LedgerUpdateOutput::ensure_transaction_infos_match` and chunk verifiers (`ReplayChunkVerifier::verify_chunk_result`) independently cross-check assembled transaction infos/version alignment against externally-supplied expected data during replay, giving an additional consistency check where untrusted chunk data is involved. [5](#0-4) [6](#0-5) 

Since no unprivileged-input-reachable path can force a mismatched pairing before `get_complete_result`/`expect_complete_result` composes the `StateComputeResult`, the proposed exploit is not reachable in this codebase.

            );
            version += 1;
        }
