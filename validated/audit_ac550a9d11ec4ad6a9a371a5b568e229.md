### Title
Vault `deposit` can mint 0 zft shares for a real underlying deposit, permanently freezing the depositor's funds - (File: mainnet/contracts/vault/v0-vault-stx.clar)

### Summary
Every mainnet vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) implements the same `deposit` function that computes the shares to mint (`inkind`) via `convert-to-shares-preview`, but — unlike the mirror-image `redeem` function in the same contracts — never asserts that the computed output is non-zero before minting and transferring funds. This is a direct analog of the ACOToken class of bug: a rounding-down conversion can yield `0` while the corresponding value transfer (here, real underlying tokens) is non-zero, and the missing `!= 0` guard lets the state-changing operation proceed anyway.

### Finding Description
`convert-to-shares-preview` rounds down when total shares (`ts`) and total assets (`ta`) are both non-zero: [1](#0-0) 

The `deposit` function uses this value directly to mint zft tokens, guarding only `amount > 0` and a slippage check against caller-supplied `min-out`, but never `inkind > 0`: [2](#0-1) 

By contrast, the `redeem` function in the exact same contract does perform this guard (`ERR-OUTPUT-ZERO`), showing the protection pattern exists in the codebase but was omitted from `deposit`: [3](#0-2) 

Sequence:
1. Vault has accrued value over time so `total-assets-preview() / total-supply-preview() > 1` (normal state for any vault that has earned interest).
2. A caller invokes `deposit(amount, min-out, recipient)` with a small `amount` and `min-out = 0` (the value used by the protocol's own test helpers, e.g. `vaultUsdc.deposit(1000000000000n, 0n, bob)`), such that `mul-div-down(amount, ts, ta)` rounds down to `0`.
3. `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` passes because `amount > 0`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially because `0 >= 0`.
5. There is no `(asserts! (> inkind u0) ...)` check in `deposit` (unlike `redeem`), so execution proceeds.
6. `(try! (receive-underlying amount account))` pulls the real underlying tokens from the depositor.
7. `(try! (ft-mint? zft inkind recipient))` mints exactly `0` zft tokens.
8. `(var-set assets (+ current-assets amount))` permanently records the depositor's underlying as vault assets with no share issued to redeem it against.

The depositor's principal is absorbed into the vault's asset pool with zero corresponding claim — value that cannot be recovered by that depositor since no zft was minted to represent it.

### Impact Explanation
This is a permanent freezing of the depositor's own funds within a single transaction: real underlying tokens leave the depositor and enter vault custody, but no fungible share token is minted to represent a redeemable claim over that value. It maps to the "permanent freezing of funds" impact class. It mirrors the exact root cause flagged in the referenced ACOToken report — a rounding-down conversion producing `0` that is not rejected before the state-changing mint/transfer occurs — and the codebase's own `redeem` function shows the maintainers are aware such a guard is needed, but it was not applied symmetrically to `deposit`.

### Likelihood Explanation
Triggerable by any single caller in a single transaction against any of the six mainnet vaults, with no special privileges, oracle interaction, or multi-party coordination required — only a vault state where `ta/ts > 1` (true for any vault that has accrued interest) and a small enough `amount`. The protocol's own test helpers pass `min-out = 0`, showing this is a realistic calling pattern that provides no protection against the missing check.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` to the `deposit` function in each of `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, and `v0-vault-usdh.clar`, mirroring the guard already present in the corresponding `redeem` function.

### Proof of Concept
1. Deploy/seed a vault (e.g. `v0-vault-usdc`) and let it accrue interest so that `total-assets-preview() > total-supply-preview()` (i.e., `ta/ts > 1`).
2. Call `deposit(amount, 0, recipient)` with `amount` small enough that `mul-div-down(amount, ts, ta) == 0` (e.g. `amount = 1` when `ta/ts` is sufficiently large).
3. Observe: `receive-underlying` succeeds, transferring `amount` from the caller into the vault; `ft-mint? zft 0 recipient` mints zero shares; `assets` is incremented by `amount`.
4. The caller's `amount` is now unrecoverable — they hold no zft shares representing it, while `var-get assets` reflects it as vault-owned.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
