### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a divergent authenticated state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by `db-tool`'s `replay_on_archive` and by `execution/executor/src/chunk_executor/mod.rs` during chunk replay/verify) checks transaction status, gas used, write-set hash, and event-root hash against the persisted `TransactionInfo`, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is called out in-line by the code's own authors as a known gap.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` is the integrity check used to confirm that a freshly-produced `TransactionOutput` (from local VM re-execution) matches the authenticated `TransactionInfo` stored/fetched from an (potentially archival/backup) source, before accepting the replay as correct. It validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

It does **not** compare `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or the newer `position_state_checkpoint_hash()` against locally computed values, a gap explicitly documented in the trailing `TODO(trading-native)` comment: [2](#0-1) , which states that "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is invoked from `execution/executor/src/chunk_executor/mod.rs` (verify_execution path used during backup/state-sync chunk replay) and from `storage/db-tool/src/replay_on_archive.rs` (offline replay-verification tool), and also referenced by `aptos-move/cli/src/commands.rs`. These are exactly the "restore/replay verification" surfaces called out in the state-integrity gate.

The state-checkpoint hash (and related hot-state / position-state checkpoint hashes introduced alongside the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature, per [3](#0-2) ) is the field in `TransactionInfo` that authenticates the resulting Jellyfish Merkle root / position-state root after a checkpoint transaction, per `assemble_transaction_infos` in `do_ledger_update.rs`: [4](#0-3) . Since `ensure_match_transaction_info` never compares this field, a replay/verify run whose locally computed state (or hot-state, or position-state) root differs from what's committed in the archived `TransactionInfo` will still be reported as a *successful* verification.

### Impact Explanation
If the local state/hot-state/position-state root diverges from the authenticated on-chain value (due to a bug in state-checkpoint computation, a non-determinism in a new "trading-native" position-state feature, or corrupted/incompatible replay data), `replay_on_archive` and the chunk-executor's replay-verification would not detect it — they would only catch divergences in write-set hash, event hash, status, or gas, but not in the committed state root. This means a broken state-commitment (wrong accumulator/Merkle root for the state tree) could pass verification tooling that is specifically meant to catch exactly this class of divergence, undermining a proof/replay-integrity safeguard. The comment is explicit that this is a live risk pending `COMPUTE_TRADING_NATIVE_STATE_ROOTS` enablement.

### Likelihood Explanation
This is not a currently-exploitable-by-anyone bug on unmodified mainnet consensus (it does not corrupt the committed ledger state itself — the executor's actual commit path does compute and store checkpoint hashes, per `do_ledger_update.rs`/`do_state_checkpoint.rs`). The gap is confined to an **offline verification/replay tool** (`db-tool`'s `replay_on_archive`, chunk-executor's replay verification), and is explicitly gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which per the comment is not yet enabled. I could not confirm from available code whether this feature flag is currently active on mainnet or what its exact rollout status is — this needs to be verified further (e.g., checking `aptos_features.rs` default flag state and whether `replay_on_archive`/chunk executor's verify paths are used in mainnet-critical replay/consistency-checking flows, such as node bootstrapping from backups, where undetected root divergence could have concrete impact).

### Recommendation
In `types/src/transaction/mod.rs::ensure_match_transaction_info`, add comparisons of the locally-derived `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionOutput`'s state-checkpoint output) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, mirroring the existing `ensure!`-based pattern for write-set and event-root hashes, before allowing `COMPUTE_TRADING_NATIVE_STATE_ROOTS` to be enabled.

### Proof of Concept
Not independently reproducible from static analysis alone: this requires (1) confirming the exact call sites in `chunk_executor/mod.rs` and `replay_on_archive.rs` pass a `TransactionOutput` from local re-execution whose checkpoint hash differs from the fetched `TransactionInfo`'s, and (2) confirming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` current activation status — both of which I was unable to fully verify within available tool calls. Given the code's own explicit acknowledgment of the gap and the constraint that this affects replay/verification tooling rather than direct consensus commit correctness, I am reporting this as a **documented, code-confirmed gap of Medium-to-High likelihood but uncertain current exploitability**, and recommend a Devin session with full repo access to confirm feature-flag status and downstream blast radius before treating it as a confirmed High/Critical mainnet finding.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
