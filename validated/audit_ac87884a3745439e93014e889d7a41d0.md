Based on my investigation, I found a concrete analog of the CVE's delimiter-injection bug class in the NEAR wallet contract.

### Title
Delimiter Injection in `FunctionCallPermission::method_names` via `join(",")` in NEAR Wallet Contract Grants Unauthorized Method-Call Access - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The wallet contract's `action_to_promise` function serializes an attacker-controlled `Vec<String>` of method names into a single comma-delimited string via `.join(",")` before passing it to the low-level `Promise::add_access_key_allowance_with_nonce` API, which is re-split on `,` by the runtime host function boundary. Since individual method-name entries are never validated to exclude the `,` separator, an Ethereum-style transaction signer can craft a single method-name entry containing embedded commas to smuggle additional, unintended method names into the resulting `FunctionCallPermission` on-chain.

### Finding Description
The CVE describes a class of bug where user-controlled data is joined into a delimiter-separated command string without escaping/validating that the data does not itself contain the delimiter, allowing injection of extra directives. The identical pattern exists in nearcore's wallet contract:

1. A user submits an RLP-encoded Ethereum transaction to `rlp_execute`, which is ABI-decoded into a `near_action::Action::AddKey` with a `FunctionCallPermission` whose `method_names: Vec<String>` field is fully attacker-controlled (decoded via `ethabi::Token::Array(ParamType::String)`), with no validation that entries don't contain commas: [1](#0-0) [2](#0-1) 

2. `action_to_promise` then joins this list with `,` into a single string before calling the SDK's access-key-allowance promise builder: [3](#0-2) 

3. On the runtime side, `promise_batch_action_add_key_with_function_call` treats the incoming bytes as a `,`-delimited list and calls `split_method_names` to re-derive the `Vec<String>` that becomes the on-chain `FunctionCallPermission.method_names`: [4](#0-3) 

Because the wallet contract never rejects or escapes commas inside an individual `method_names` entry, a caller can submit `method_names = ["transfer,ft_transfer_call"]` (a single logical entry containing an embedded comma). After `.join(",")` this becomes the string `"transfer,ft_transfer_call"`, which is indistinguishable from two-legitimate-entries input `["transfer", "ft_transfer_call"]`. When the runtime's `split_method_names` re-parses it, the resulting on-chain `FunctionCallPermission` grants access to **both** `transfer` and `ft_transfer_call`, even though the original (signed, RLP-decoded) intent from the Ethereum wallet owner may have only listed a single string that was meant to be treated as one opaque token (e.g., if any upstream tooling/relayer assembles the `method_names` array from a single delimited field, or if an intermediate encoding layer collapses/concatenates a legitimate single entry with attacker-supplied data). More directly: it demonstrates that the security boundary between "one method name" and "many method names" is a `,` character with no escaping, so any code path (now or introduced later) that builds a single `method_names` entry from partially trusted substrings is vulnerable to smuggling extra permissions past the intended access-key restriction.

### Impact Explanation
A `FunctionCallPermission` access key restricts a compromised/limited relayer key to calling only specific methods on a specific receiver (e.g., only `ft_transfer_call`, capped by an allowance). If additional method names can be smuggled in via comma injection (e.g., appending `transfer` or a privileged admin method name), the resulting access key silently grants call permissions beyond what was authorized/reviewed, enabling unauthorized value movement or privileged operations on the target contract using a supposedly limited-scope key. This matches the "unauthorized value movement" / "invalid state transition acceptance" impact bar, since the on-chain `AddKey` action's `method_names` field ends up with content that does not match the original discrete list the user intended to authorize.

### Likelihood Explanation
Exploitation requires control over at least one `method_names` string entry that is later joined with `,` — reachable by any account driving the wallet contract's `rlp_execute` entrypoint (an RLP-decoded Ethereum-style transaction, i.e., an ordinary unprivileged signer interacting with a deployed wallet contract instance). No special privileges, validator status, or network position are needed. However, actual damage depends on whether some component in the flow (relayer tooling, additional contracts) treats a single logical method-name value as attacker-influenced/concatenated data rather than a hardcoded literal — the core protocol itself does not prevent the comma from being embedded in a single ABI-decoded string element.

### Recommendation
- Reject (or percent-encode/escape) any `method_names` entry containing the `,` separator character before calling `.join(",")` in `action_to_promise`, returning `Error::User(UserError::...)` if a comma is found.
- Alternatively, switch the wallet contract to use whichever SDK API accepts `Vec<String>` directly instead of a comma-joined `String`, eliminating the serialization/deserialization round-trip entirely.
- Add validation in `near-vm-runner`'s `split_method_names`/parsing path (or in `FunctionCallPermission` construction) to reject method names containing the delimiter character, defense-in-depth against any future caller making the same mistake.

### Proof of Concept
1. Construct an Ethereum-style RLP transaction whose ABI-encoded `AddKey` action has `method_names = ["transfer,ft_transfer_call"]` (one array element containing an embedded comma).
2. Submit it via `rlp_execute(target, tx_bytes_b64)` to a deployed wallet contract instance.
3. `types.rs::try_into_near_action` copies this directly into `FunctionCallPermission.method_names` without validation: [5](#0-4) 
4. `action_to_promise` joins it: `access.method_names.join(",")` → `"transfer,ft_transfer_call"`, which is passed to the SDK promise builder: [6](#0-5) 
5. The runtime's `split_method_names` parses the resulting host-function bytes as two independent method names, `"transfer"` and `"ft_transfer_call"`, and stores both in the final `AddKeyAction`'s `FunctionCallPermission` on-chain: [4](#0-3) 
6. The resulting access key on `target` now permits calling `transfer` (or any other method the attacker appends via embedded commas) in addition to the intended method, despite the caller's ABI array nominally containing only one string element.
