### No vulnerability found for this question.

Analysis: the tie-break in `set_stacks_block_accepted_at_tip` [1](#0-0)  compares `sn_current.block_height` and `sn_accepted.block_height`, i.e., the sortition (burn) heights of the two competing tenures, not the order in which the blocks were locally processed. Working through both possible arrival orders (B-then-C vs C-then-B) shows the comparison is symmetric: whichever tenure has the higher `block_height` always wins regardless of which one was already stored as `cur_ch` when the second one arrives. This matches the documented intent in the surrounding comment, which explicitly anticipates the "miner A / miner B / miner C" scenario as a "benign fork" that self-resolves once both nodes ingest the same full set of blocks [2](#0-1) .

Consequently, node A and node B — after ingesting the identical block set in reversed order — converge on the same `(consensus_hash, block_hash)` tip; the equality the question claims is broken does not actually diverge. The scenario is a known, intentional, order-independent tie-break, not an attacker-triggerable node-disagreement bug.
