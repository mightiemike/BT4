### Title
Unbounded-recursion stack overflow via deeply nested JSON in JSON-RPC request body - (File: `chain/jsonrpc/src/lib.rs`)

### Summary
The `rpc_handler` endpoint in `chain/jsonrpc/src/lib.rs` deserializes every incoming JSON-RPC POST body into `Message` via axum's `Json<Message>` extractor, which uses `serde_json`'s recursive descent deserializer under the hood. `Message`/`Request`/`Notification` contain a `params: Value` field [1](#0-0) , and `serde_json::Value` deserialization recurses once per nested array/object level with no depth limit, mirroring the same bug class as TensorFlow's `ParseAttrValue` (CVE-2021-29615): an attacker-controlled, arbitrarily nested structure is parsed with naive recursion and no depth cap.

### Finding Description
`rpc_handler` accepts `Json(request): Json<Message>` directly from the network [2](#0-1) . The only documented protective control on this endpoint is a request body size limit ("Middleware: CORS ... and request body size limit (default 10MB)") [3](#0-2)  — there is no JSON nesting-depth limit anywhere in the RPC stack (no `recursion_limit`/`max_depth` guard was found for `serde_json` parsing in `chain/jsonrpc` or `chain/jsonrpc-primitives`). A payload such as `{"jsonrpc":"2.0","method":"x","id":1,"params":[[[[[...]]]]]}` with hundreds of thousands of nested `[` characters is well under 10MB (each nesting level costs 1–2 bytes) but drives `serde_json`'s recursive `Deserialize` implementation for `Value` to a stack depth proportional to nesting depth. Because `serde_json`'s value parser has no built-in recursion-depth guard, sufficiently deep nesting overflows the thread stack.

A stack overflow in Rust cannot be caught by `catch_unwind`/panic handling — it results in immediate process abort (SIGSEGV/SIGABRT). Since the JSON-RPC HTTP server, `ClientActor`, and other consensus-relevant actors typically run in the same `neard` process (the JSON-RPC server is wired up alongside the node's actors in `nearcore/src/lib.rs`, per the RPC architecture doc [4](#0-3) ), a crash triggered on the axum/tokio worker parsing the request can take down the entire node process, not merely the HTTP handler.

This is architecturally different from the WASM/prepare and trie-traversal code in the same codebase, which has clearly been hardened against exactly this bug class: contract WASM parsing enforces explicit `max_blocks_per_function`/`max_blocks_per_contract` limits [5](#0-4) , `DelegateAction` nesting is structurally forbidden via `NonDelegateAction`'s custom Borsh deserializer [6](#0-5) , and trie traversal code has been explicitly converted to iterative stack-based algorithms with comments noting "Non recursive approach to avoid any potential stack overflows" [7](#0-6) . The JSON-RPC message parsing path has no equivalent protection.

### Impact Explanation
Any unauthenticated RPC caller can send a single crafted HTTP POST to the public JSON-RPC endpoint (port 3030 by default) and crash the `neard` process hosting it. If this is a validator's own RPC-enabled node (a common deployment, and RPC is enabled by default per the routes table), this is a transaction/request-triggered halt of that node with no privileged access required — directly matching the "transaction-triggered halt" impact class called out as in-scope. At scale, an attacker could target the RPC endpoints of multiple validators/seed nodes to degrade or halt significant portions of network availability, since only network reachability to the RPC port is required.

### Likelihood Explanation
High reachability: any external, unprivileged client can reach `rpc_handler` with a single POST request; no wallet, keys, or gas are required. The only barrier is the 10MB body-size limit, which a nested-array payload sufficient to overflow a typical (multi-MB) thread stack easily satisfies (nesting depth in the hundreds of thousands requires only hundreds of KB of `[` characters). This makes the analog concretely triggerable, matching the "specially crafted input" trigger condition from the original report.

### Recommendation
- Enforce an explicit maximum JSON nesting depth before/while deserializing RPC request bodies (e.g., use a bounded/iterative JSON parser configuration, or pre-scan bracket/brace nesting depth and reject before invoking `serde_json`'s recursive deserializer).
- Alternatively, run request deserialization on a dedicated thread with a small, bounded stack combined with a hard depth limit, or adopt a `serde_json` wrapper crate that enforces `RecursionLimit` (as available in some JSON libraries) for all `Value`-typed fields in `chain/jsonrpc-primitives/src/message.rs`.
- Apply the same fix to any other endpoint that accepts open-ended `serde_json::Value` (e.g., `params` in RPC method-specific request types, Rosetta RPC endpoints) since these transitively rely on the same recursive parser.

### Proof of Concept
```
POST / HTTP/1.1
Host: <node>:3030
Content-Type: application/json
Content-Length: <small>

{"jsonrpc":"2.0","method":"status","id":1,"params":"AAA...<repeat '[' N times>...AAA"}
```
Concretely: send a body of the form
```
{"jsonrpc":"2.0","id":1,"method":"status","params":[[[[[ ... (repeated ~500,000 times) ... ]]]]]}
```
This is well under the 10MB body limit but forces `serde_json`'s `Value` deserializer, invoked via axum's `Json<Message>` extractor in `rpc_handler` (`chain/jsonrpc/src/lib.rs:2928-2938`), to recurse ~500,000 times, exhausting the worker thread's stack and aborting the process.

Note: I was not able to execute this PoC in a live environment (no runtime/filesystem access in this session) or confirm the exact default stack size of the tokio/axum worker threads in this deployment; the claim relies on the well-documented absence of depth limiting in `serde_json`'s `Value` deserialization and the absence of any depth-limiting logic found in the indexed RPC code paths (`chain/jsonrpc/`, `chain/jsonrpc-primitives/`). A Devin session with full repo/runtime access would be needed to empirically confirm the crash and precise required nesting depth on the current `serde_json` version pinned in `Cargo.lock`.
