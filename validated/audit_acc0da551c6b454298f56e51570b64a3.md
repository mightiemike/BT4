**Rationale:**

The premise requires an existing caching layer that keys on `ConfigID` alone (ignoring ledger version) and is consumed during execution instead of a fresh `fetch_config` call. That architecture does not exist in this codebase.

- `AptosVersion` implements `OnChainConfig` with no custom caching; every read goes through `OnChainConfig::fetch_config`/`fetch_config_and_bytes`, which calls `ConfigStorage::fetch_config_bytes` on the current `StateView` and deserializes fresh bytes each call — there is no static or `ConfigID`-keyed cache in this path. [1](#0-0) [2](#0-1) [3](#0-2) 
- The only caches found for on-chain configs (`gas_schedule_cache`, `gas_limit_cache` in the API context) are keyed by **epoch**, not by `ConfigID`, and they explicitly compare `ledger_info.epoch.0` to the cached epoch before returning stale data, refreshing from a freshly-constructed `state_view_at_version` otherwise. [4](#0-3) [5](#0-4) 
- The `InMemoryOnChainConfig`/`OnChainConfigPayload` provider used for reconfiguration notifications is keyed by `ConfigID` but is constructed fresh per notified `version`/epoch via `read_on_chain_configs`, not persisted and reused across versions. [6](#0-5) [7](#0-6) 

Since `ConfigID` derives `Eq`/`Hash` itself (making it usable as a `HashMap` key independent of `AptosVersion`'s own trait derives), the absence of `Hash`/`Eq` on `AptosVersion` is irrelevant to any caching correctness concern — no code path needs to hash or key by the `AptosVersion` value itself. [8](#0-7) 

The version-gating logic in the Move framework (`aptos_framework::version`) also only mutates the `Version` resource synchronously at genesis or via the config-buffer/epoch-boundary mechanism, and `on_new_epoch` applies buffered updates atomically at reconfiguration — there's no separate Rust-side long-lived cache in the commit path that could diverge from the state view being executed against. [9](#0-8) 

Because the described caching layer is hypothetical and not present in the actual state-read/execution path, there is no unprivileged-input-driven mechanism here that corrupts committed state, proof material, or an authenticated response.

        Ok(OnChainConfigPayload::new(
            epoch,

    public entry fun set_for_next_epoch(account: &signer, major: u64) acquires Version {
        assert!(exists<SetVersionCapability>(signer::address_of(account)), error::permission_denied(ENOT_AUTHORIZED));
        let old_major = borrow_global<Version>(@aptos_framework).major;
        assert!(old_major < major, error::invalid_argument(EINVALID_MAJOR_VERSION_NUMBER));
        config_buffer::upsert(Version {major});
    }

    /// Only used in reconfigurations to apply the pending `Version`, if there is any.
    public(friend) fun on_new_epoch(framework: &signer) acquires Version {
        system_addresses::assert_aptos_framework(framework);
        if (config_buffer::does_exist<Version>()) {
            let new_value = config_buffer::extract_v2<Version>();
            if (exists<Version>(@aptos_framework)) {
                *borrow_global_mut<Version>(@aptos_framework) = new_value;
            } else {
                move_to(framework, new_value);
            }
        }
