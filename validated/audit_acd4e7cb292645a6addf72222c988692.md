### Title
Wallet Contract's `has_in_flight_tx` lock can be permanently stuck due to fixed-gas callback processing an attacker-controlled external return value - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::nep_141_storage_balance_callback` is scheduled with a fixed, non-scaling gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) and immediately deserializes the raw bytes returned by an attacker-controlled `token_id::storage_balance_of` call before it can reset the `has_in_flight_tx` guard. If the target token contract returns an oversized/malformed payload, `serde_json::from_slice` can consume more gas than was attached, causing the whole callback receipt to fail with `GasExceeded`. Because NEAR only commits state mutations of a function call that completes successfully, the `self.has_in_flight_tx = false;` reset at the top of the callback is rolled back together with everything else, permanently locking the wallet.

### Finding Description
`WalletContract` enforces a single-in-flight-transaction invariant via the `has_in_flight_tx` boolean, documented explicitly as an invariant that must be reset by every code path that sets it to `true`: [1](#0-0) 

`rlp_execute` refuses to process any further user transaction while this flag is `true`: [2](#0-1) 

For an emulated ERC-20 transfer, the wallet contract schedules a cross-contract call to `token_id::storage_balance_of` where `token_id` is the (attacker-controllable) `target` account chosen by the transaction the wallet owner signs, and the follow-up callback is attached a **fixed** gas amount that does not scale with the size of the value that will be returned: [3](#0-2) [4](#0-3) 

Inside `nep_141_storage_balance_callback`, `has_in_flight_tx` is reset as the very first statement, and then the (attacker-controlled) `PromiseResult::Successful(value)` bytes are immediately deserialized with `serde_json::from_slice`: [5](#0-4) 

The `Err(_)` deserialization branch is designed to gracefully catch a malformed response — this is the NEAR analog of the report's `try/catch`. However, that "catch" only works if the callback has enough gas budget to *finish* attempting the parse and return a value. If the target contract returns a payload large enough that JSON parsing itself exhausts the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget before `serde_json::from_slice` returns (Ok or Err), the whole `FunctionCall` receipt for the callback aborts with `HostError::GasExceeded`. NEAR only persists state changes made by a function call if it completes without error, so the earlier `self.has_in_flight_tx = false;` write is rolled back along with everything else, leaving the invariant flag permanently `true`. No other code path can ever unset it again, since `rlp_execute` immediately short-circuits on `has_in_flight_tx == true` before scheduling any new callback that could reset it.

### Impact Explanation
This permanently freezes the wallet contract for its owner: every subsequent call to `rlp_execute` (i.e. every future transaction the owner tries to sign and relay, including plain transfers, key management, or any other action) is rejected with "transaction already in progress," with no recovery path. Since the wallet contract holds the user's $NEAR balance and access keys, this results in permanently frozen funds/functionality triggered by a single interaction with a malicious or buggy `token_id` contract during an ERC-20 emulation transfer — directly analogous to the external report's griefing vector where an untrusted callee is used to trap the caller into a state from which they can never recover.

### Likelihood Explanation
Reachable by any account: an attacker only needs to get the wallet owner (or a relayer acting on the owner's signed transaction) to perform one ERC-20-emulated transfer/interaction whose `to` address resolves to a malicious contract they control (e.g., a scam/airdropped token, a common real-world social-engineering vector). The attacker's contract simply needs to implement `storage_balance_of` to return an oversized JSON blob (bounded only by the protocol's `max_length_returned_data`/`ReturnedValueLengthExceeded` limit), which is fully within reach of a standard contract deployment and view-return; no special privileges or network-level capability are required.

### Recommendation
- Scale the gas attached to `nep_141_storage_balance_callback` (and similar callbacks that parse externally supplied return data) proportionally to the maximum possible size of the returned value, or bound/validate the raw return-value length before attempting to deserialize it.
- More robustly, decouple the `has_in_flight_tx` reset from any code that can fail after it, e.g. persist `has_in_flight_tx = false` in a way not dependent on the remainder of the callback completing, or add a dedicated, cheap "unstick" callback with generous fixed gas whose only job is to clear the flag once a receipt is known to have resolved (successfully or not), independent of downstream parsing logic.

### Proof of Concept
1. Attacker deploys a NEAR contract at some `token_id` account and implements `storage_balance_of` such that on invocation it returns a very large byte string (e.g. tens/hundreds of KB — within NEAR's max return length) that is not valid `StorageBalance` JSON.
2. The wallet owner signs (or a relayer submits on their behalf) an Ethereum-style transaction emulating an ERC-20 transfer where `to`/`target` maps to the attacker's `token_id` account, reaching `EthEmulationKind::ERC20Transfer` in `internal.rs`.
3. `inner_rlp_execute` schedules `Promise::new(token_id).function_call("storage_balance_of", ...)` followed by `.then(nep_141_storage_balance_callback)`, attaching the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, and sets `has_in_flight_tx = true`.
4. The attacker's `storage_balance_of` returns the oversized payload; `nep_141_storage_balance_callback` starts, resets `has_in_flight_tx = false` (uncommitted), then calls `serde_json::from_slice` on the huge payload, exhausting the attached gas and aborting the receipt with `GasExceeded`.
5. Because the receipt failed, the entire state diff of the callback call — including the `has_in_flight_tx = false` write — is discarded; `has_in_flight_tx` remains `true` in committed state.
6. Any subsequent call to `rlp_execute` from the wallet owner now returns `"transaction already in progress, please try again later."` indefinitely, since there is no remaining path that can ever reset the flag.

    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
