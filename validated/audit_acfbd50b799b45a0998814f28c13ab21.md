### Title
Missing origin validation in `provisioning_page.ts` `onMessageReceived_` allows arbitrary web content to request device info and spoof carrier portal status - (`ash/webui/common/resources/cellular_setup/provisioning_page.ts`)

### Summary
The `ProvisioningPageElement` in the Chrome OS cellular setup flow listens for `postMessage` events from a carrier payment `<webview>` but does not validate `event.origin`. Any web content that can send a `postMessage` to the hosting `chrome://` page can request the user's cellular device identifiers (carrier, MEID, IMEI, MDN) and dispatch a spoofed `on-carrier-portal-result` event, because the handler accepts messages from any sender.

### Finding Description
`ProvisioningPageElement.loadPortal_()` registers a global `window.addEventListener('message', this.onMessageReceived_.bind(this))` listener at line 146. The handler `onMessageReceived_` (lines 195-224) processes two message types:

- `requestDeviceInfoMsg`: replies by posting `carrier`, `MEID`, `IMEI`, and `MDN` to `contentWindow` of the portal webview.
- `reportTransactionStatusMsg`: dispatches a `CustomEvent('on-carrier-portal-result', {detail: success})` that drives the activation flow.

Neither branch inspects `event.origin`, `event.source`, or any other sender identifier. This is the Chromium analog of the Solidity bug class "receive() accepts funds from any sender instead of only the trusted WETH contract": the message handler acts on input from any origin rather than restricting it to the expected carrier portal origin (`cellularMetadata.paymentUrl`).

### Impact Explanation
A malicious renderer or cross-origin page that can target the `chrome://` hosting window with `postMessage` can:

1. Exfiltrate cellular device identifiers by sending `{type: 'requestDeviceInfoMsg'}` and receiving the reply (the reply is posted to `contentWindow` with `this.cellularMetadata.paymentUrl` as target origin, but the attacker controls the `source` window if it can frame or open the target).
2. Spoof a successful or failed carrier portal transaction by sending `{type: 'reportTransactionStatusMsg', status: 'ok'}` (or any non-`'ok'` value), causing the UI to advance or error out incorrectly.

This is a cross-origin disclosure / SOP bypass within the WebUI context and can affect the cellular activation state machine.

### Likelihood Explanation
The listener is attached to `window`, not to the `<webview>` element, so any `postMessage` delivered to the WebUI window is processed. Because the carrier portal is loaded in a `<webview>` whose `src` is `cellularMetadata.paymentUrl`, the legitimate messages originate from that URL. However, the handler does not enforce that, so any other frame, popup, or compromised renderer that can send a message to this `chrome://` window can trigger the handler. The WebUI is a privileged `chrome://` context, making mistaken or malicious origin spoofing plausible.

### Recommendation
Validate `event.origin` against `this.cellularMetadata.paymentUrl` (or its origin) before handling either message type, and also verify `event.source` matches the portal webview's `contentWindow`. For example:

```ts
private onMessageReceived_(event: MessageEvent) {
  const portalWebview = this.getPortalWebview();
  if (!portalWebview || event.source !== portalWebview.contentWindow) {
    return;
  }
  if (event.origin !== new URL(this.cellularMetadata!.paymentUrl).origin) {
    return;
  }
  // ... existing message handling
}
```

### Proof of Concept
From any page able to obtain a reference to the `chrome://` WebUI window (e.g., via `window.opener` or `window.parent` in a nested scenario, or by targeting the WebUI window from a same-browser popup), the following script triggers the vulnerable handler:

```js
const target = /* reference to the chrome:// provisioning page window */;
target.postMessage({type: 'requestDeviceInfoMsg'}, '*');
// The handler will reply with {carrier, MEID, IMEI, MDN} to the source window.

target.postMessage({type: 'reportTransactionStatusMsg', status: 'ok'}, '*');
// The handler dispatches 'on-carrier-portal-result' with detail=true.
```

The vulnerable code is at `ash/webui/common/resources/cellular_setup/provisioning_page.ts` lines 146 and 195-224.
