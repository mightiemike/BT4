### Title
Hard-coded `ExchangeBalanceLimit` cap permanently freezes AMM exchange rate updates once one side of a TRC10 exchange pool is saturated - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
The external report describes a class of bug where a fixed "allowance"/headroom parameter, once exhausted, prevents timely updates of an on-chain exchange rate, degrading protocol health until the allowance replenishes. In java-tron's built-in TRC10 bancor-style `Exchange` feature, `ExchangeTransactionActuator` and `ExchangeInjectActuator` enforce a hard ceiling (`dynamicStore.getExchangeBalanceLimit()`) on either token balance in the pool. Any unprivileged user can broadcast trades that push one side of the pool toward this ceiling; once reached, all further trades and injections in that direction are permanently rejected, freezing the AMM price and preventing the exchange rate from being corrected back toward the true market price — directly analogous to the "insufficient allowance blocks rate update" bug class from the report, but reachable purely via ordinary broadcast transactions rather than a privileged oracle key.

### Finding Description
`ExchangeTransactionActuator.doValidate()` computes the resulting token balance after a proposed trade and rejects the transaction if it would exceed a global `balanceLimit`: [1](#0-0) 

The same hard limit is enforced in `ExchangeInjectActuator`: [2](#0-1) 

Unlike a coin/RateLimit contract's `allowance` field, which naturally replenishes over time, `ExchangeBalanceLimit` is a static ceiling with no time-based recovery mechanism tied to trading activity itself — the only way to reduce a token's balance below the limit is for someone to trade or withdraw *in the opposite direction*, which becomes economically irrational once the AMM price has drifted far from market price (the bancor curve in `ExchangeCapsule.transaction()` / `ExchangeProcessor`/`SafeExchangeProcessor` makes reverse trades increasingly unattractive as the pool becomes imbalanced): [3](#0-2) 

Because any unprivileged account can submit `ExchangeTransactionContract` transactions (buy/sell) that monotonically push one side's balance upward, a sufficiently large or repeated set of one-directional trades (which requires no special permission, just token/TRX balance) can drive a token balance to the `ExchangeBalanceLimit` ceiling. From that point on, the pool cannot accept any further trade or injection that would increase that balance, which is precisely the trade direction needed to correct or continue moving the exchange rate in that direction — effectively freezing the on-chain exchange rate for that pair, mirroring the report's scenario where insufficient allowance blocks a timely rate update.

### Impact Explanation
Once frozen, the AMM price for the affected TRC10 pair stops reflecting real market conditions. Any protocol, actuator, or off-chain integrator relying on this exchange's live price for valuation, liquidation, or accounting purposes would operate on stale/incorrect data — an accounting/market-math corruption analogous to the report's "on-chain exchange rate may become out of date" concern. Unlike the original report (where a cold key with high allowance mitigates the risk), java-tron's `ExchangeBalanceLimit` has no privileged bypass or automatic relief mechanism once hit in the field, other than a governance-level `ExchangeCreateActuator`/proposal change to raise the limit, which is a much slower, privileged remediation path.

### Likelihood Explanation
Reaching the limit requires sustained directional trading volume, which is more likely for popular/volatile TRC10 pairs, and it is fully reachable by any unprivileged broadcast transaction — no admin key, no bug in signature/permission checks needed. The severity depends on how close `ExchangeBalanceLimit` is configured relative to realistic trading volume for a given pair, similar to how the report notes severity depends on caller allowance parameters and count.

### Recommendation
Consider replacing (or augmenting) the static `ExchangeBalanceLimit` hard-stop with a mechanism that allows the pool to keep repricing (e.g., dynamically raising the limit via governance ahead of demand, or allowing controlled overflow with additional fees/slippage) so that legitimate one-directional trading does not permanently stall exchange-rate discovery for a pair. At minimum, monitoring/alerting should be added so operators can react (via a `ProposalCreateActuator` update to `dynamicStore`'s limit) before a pool is fully saturated.

### Proof of Concept
1. Create a TRC10 `Exchange` pool via `ExchangeCreateActuator` with initial balances near, but below, `dynamicStore.getExchangeBalanceLimit()`.
2. Any unprivileged account repeatedly submits `ExchangeTransactionContract` trades selling token A into the pool (buying token B), each valid individually.
3. Each trade increases token A's balance in the pool per `ExchangeCapsule.transaction()`'s bancor curve update.
4. Once token A's balance would exceed `balanceLimit`, `ExchangeTransactionActuator.doValidate()` throws `"token balance must less than " + balanceLimit"` for *any* further sell of A (or inject of A), regardless of trader — see line range cited above.
5. From this point, the exchange rate for A/B cannot move further in that direction through any user transaction; the on-chain rate is frozen even though real-world market pricing continues to move, reproducing the report's "insufficient allowance/limit prevents timely exchange rate update" condition without requiring any privileged actor.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
