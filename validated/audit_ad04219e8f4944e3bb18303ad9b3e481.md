Based on my analysis, I found a strong analog to the Lido zero-balance bug class in java-tron's energy resource calculation code.

### Title
Missing zero-check for `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` relies on disabled JVM assertions, enabling divide-by-zero/DoS - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` guards against a zero `totalEnergyWeight` denominator only with a Java `assert` statement, which is disabled by default in production JVMs (`-ea` not typically set). If `totalEnergyWeight` reaches zero, the subsequent division (`BigInteger.divide` or double division) executes without the intended guard.

### Finding Description
`calculateGlobalEnergyLimit` computes an account's energy quota by dividing `energyWeight * totalEnergyLimit` by `totalEnergyWeight`: [1](#0-0) 

The only safeguard against `totalEnergyWeight == 0` is a Java `assert` statement, which is a no-op unless the JVM is started with `-ea`. In contrast, the equivalent logic in `EnergyProcessor.calculateGlobalEnergyLimit` explicitly checks `totalEnergyWeight <= 0` (or `== 0` in the V2 path) and returns `0` before performing the division: [2](#0-1) 

This shows the codebase already recognizes this exact class of bug (zero-denominator on a shared/reward-like resource pool) and fixed it in `EnergyProcessor`, but the fix was not applied to the analogous method in `RepositoryImpl`, which is used by the TVM path when computing free energy for a contract-invoking account (`ContractState.calculateGlobalEnergyLimit` delegates directly to it): [3](#0-2) 

If `totalEnergyWeight` (the global energy weight, driven by all frozen-for-energy balances network-wide) were to reach `0` — e.g., through a sequence of legitimate `UnfreezeBalance`/`UnfreezeBalanceV2` operations reducing `TotalEnergyWeight` to zero (a network-wide accounting value, not a single trusted actor's balance) — the `BigInteger.valueOf(totalEnergyWeight)` divisor becomes zero, causing `ArithmeticException: / by zero` on the hardened path, or `NaN`/division-by-zero double arithmetic on the legacy path, when any subsequent smart-contract transaction attempts to query energy limits.

### Impact Explanation
An `ArithmeticException` thrown deep inside repository/VM code during energy-limit calculation for a contract call is not a normal validation exception; it would propagate as an unexpected runtime exception during transaction processing, potentially causing node crashes/divergence, or at minimum reliably reverting/blocking energy accounting for TVM execution paths that rely on `Repository.calculateGlobalEnergyLimit`. Because energy limit computation gates whether user contract calls can execute, this is an invalid-state/halt-class impact reachable by unprivileged users triggering ordinary contract execution once the global weight collapses to zero.

### Likelihood Explanation
Likelihood depends on `totalEnergyWeight` actually reaching zero on a live network, which requires essentially all frozen-for-energy TRX to be unfrozen — a low-probability but not impossible network state, especially on testnets/private chains or in adversarial conditions. The fact that `EnergyProcessor` already needed an explicit fix for the same scenario indicates the underlying condition is realistically reachable in this codebase's history/design, and the `RepositoryImpl` copy was simply never updated to match.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check, mirroring `EnergyProcessor`:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```

### Proof of Concept
1. Drive network state such that `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (all frozen-for-energy balance unfrozen network-wide via `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`, which call `repo.addTotalEnergyWeight(-...)`). [4](#0-3) 
2. Any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` invokes a smart contract, triggering `Repository.calculateGlobalEnergyLimit` via `ContractState`.
3. With `hardenResourceCalculation()` enabled, `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` throws `ArithmeticException`; with it disabled, `(double) totalEnergyLimit / 0` yields `Infinity`, producing an incorrect (unbounded) energy limit instead of the intended `0`, since the `assert` guard is not enforced in production.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
