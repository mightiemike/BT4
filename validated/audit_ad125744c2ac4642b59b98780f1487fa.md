**Reasoning summary:**

The premise assumes a tenure-extend implies "a length beyond what the single winning sortition authorised," but there is no such invariant in the codebase — a sortition's VRF proof authorizes *who wins the right to mine*, not a fixed block count for that tenure. The `TenureChangeCause::Extended` (and its `ExtendedRuntime`/`ExtendedReadCount`/etc. variants) explicitly do **not** start a new tenure: `check_nakamoto_tenure` enforces `tenure_payload.tenure_consensus_hash == tenure_payload.prev_tenure_consensus_hash` for all Extended causes, rejecting the tenure-change outright if the extend tries to introduce a new tenure ID. [1](#0-0) 

Because an extend never changes `tenure_id_consensus_hash`, the inventory bit semantics in `from_inventory` are unaffected: bits mark sortitions that produced a *new* tenure-start block, and extend-blocks are correctly folded into the same `tenure_id_consensus_hash` bucket as the original tenure without requiring any new bit. [2](#0-1) 

Additionally, a well-formed tenure-extend block is explicitly required to have no coinbase transaction, so extending a tenure grants no additional coinbase reward — the miner only continues collecting ordinary transaction fees for blocks that must still be signed by the signer set for every block, which is outside the single-miner-slot attacker's control. [3](#0-2) 

`get_ongoing_tenure` and `check_tenure_continuity` consistently resolve to the same `tenure_id_consensus_hash` across block-found and extend boundaries, matching the download layer's treatment — there is no divergence between the two sides of the claimed equality. [4](#0-3) [5](#0-4) 

Since tenure-extend is an intended mechanism (allowing the same already-authorized miner to keep producing signer-approved blocks when no new sortition winner is available), and it carries no extra coinbase/reward beyond ordinary fees, there is no reward-accounting violation and no chain-split/reward-theft impact reachable by an unprivileged single-miner-slot attacker.
