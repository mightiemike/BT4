**Reasoning:**

The scenario described requires a trusted restore/replay tool to deliberately reinsert malformed `event_data` bytes under the `MUTATE_PROPERTY_MAP_TYPE` type tag while bypassing the normal `MoveEventV2Type::create_event_v2` construction path. This does not originate from an unprivileged transaction, API, view, bytecode, or proof input as required by the scope rules.

Two independent facts make this non-exploitable through any unprivileged path:

1. **Hash verification is intentionally content-agnostic.** `verify_events_against_root_hash` computes `CryptoHash::hash` over the raw `ContractEvent` bytes and checks the resulting accumulator root against `transaction_info.event_root_hash()` [1](#0-0) . This hash is computed over whatever bytes are present in the event — it does not attempt BCS deserialization into `MutatePropertyMap`. This is standard content-addressed hashing behavior for accumulator proofs, not a defect: `bcs::from_bytes::<MutatePropertyMap>()` is a separate, optional interpretation step used by consumers (e.g., the indexer's `MutatePropertyMapTranslator` in `storage/indexer/src/event_v2_translator.rs`), and its success or failure has no bearing on proof-integrity guarantees, which only bind bytes to a root hash, not bytes to "correct decodability."

2. **No unprivileged path lets an attacker forge mismatched type_tag/data.** During normal execution, the `MutatePropertyMap` event is emitted directly by `token.move`'s `mutate_one_token` via `event::emit(MutatePropertyMap { ... })` [2](#0-1) , where the Move VM serializes the struct's fields per its on-chain type layout — an unprivileged transaction cannot cause the VM to associate `MUTATE_PROPERTY_MAP_TYPE` with arbitrary/malformed bytes, since the type tag is derived from the actual struct being emitted and the data is its exact BCS serialization [3](#0-2) .

The only way to actually produce the described inconsistency is for a restore/replay tool to bypass this VM-enforced binding and hand-craft corrupted bytes directly — this is precisely a "trusted operator mistake" (or a bug in privileged tooling) explicitly excluded by the Decision Standard ("Reject anything that depends on trusted operator mistakes alone"). It does not represent a path from unprivileged input to state corruption, proof corruption, or misbound authenticated response.

fn verify_events_against_root_hash(
    events: &[ContractEvent],
    transaction_info: &TransactionInfo,
) -> Result<()> {
    let event_hashes: Vec<_> = events.iter().map(CryptoHash::hash).collect();
    let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash();
    ensure!(
        event_root_hash == transaction_info.event_root_hash(),
        "The event root hash calculated doesn't match that carried on the \
                         transaction info! Calculated hash {:?}, transaction info hash {:?}",
        event_root_hash,
        transaction_info.event_root_hash()
    );
    Ok(())
}
