### Title
Unprivileged `SetAccountIdContract` can front-run the one-time Turkish-key migration, permanently orphaning legacy account IDs - (File: `framework/src/main/java/org/tron/core/db/api/MigrateTurkishKeyHelper.java`)

### Summary
`MigrateTurkishKeyHelper` performs a one-time migration of legacy `AccountIdIndexStore` keys (written under a Turkish locale, which lower-cases `I` to a dotless `ı` instead of `i`) into their canonical ROOT-locale form. The migration only writes the canonical key **if it is not already present**. Because `SetAccountIdActuator` lets any unprivileged account permanently claim an `accountId` in ROOT-normalized form with no awareness of pending legacy (un-migrated) Turkish-keyed accounts, an ordinary user can pre-claim the canonical key before the migration runs. When the migration later executes, it silently skips writing the canonical entry for the legacy account, permanently orphaning that account's ID and leaving the attacker in possession of the identifier. This mirrors the Lens bug class: an entity that has not yet been "migrated" can be permanently blocked/corrupted because a normal (non-migration) creation path can claim the same unique identifier first, and the migration logic assumes first-write-wins without any cross-check against legacy pending state.

### Finding Description
`AccountIdIndexStore.put()`/`has()`/`get()` always normalize keys using `Locale.ROOT`: [1](#0-0) 

`SetAccountIdActuator` allows any account holder (no privileged-role check) to permanently set their own `accountId`, guarded only by "has this account already set an id" and "does this exact ROOT-normalized id already exist": [2](#0-1) 

Legacy accounts created on nodes running under a Turkish/Azerbaijani JVM locale had their `accountId` index keys stored using the Turkish lower-casing rule (dotless `ı`), which differs byte-for-byte from the ROOT-normalized form used by all new/global lookups. `MigrateTurkishKeyHelper.doWork()` is the one-time remediation: it scans for keys containing the Turkish dotless-`ı`, and for each one computes the ROOT-equivalent key, writing it **only if the ROOT key does not already exist**, then deletes the legacy key: [3](#0-2) 

Because ordinary `SetAccountIdContract` transactions always write/read using ROOT normalization, any user can submit a transaction claiming the exact string that a not-yet-migrated legacy Turkish-keyed account is expecting to be normalized to. If that claim lands before `MigrateTurkishKeyHelper.doWork()` runs (gated by the one-time `TURKISH_KEY_MIGRATION_DONE` flag, checked via `needToMigrateTurkishKeys()`): [4](#0-3) 

then Phase 2 of the migration finds the ROOT key already occupied by the attacker's write and silently skips populating it for the legacy account, while unconditionally deleting the legacy key regardless of whether the write succeeded: [5](#0-4) 

This is structurally identical to the Lens root cause: a normal, unprivileged "create" path (`mintHandle()` in Lens / `SetAccountIdContract` here) is not validated against the pending set of not-yet-migrated legacy identifiers, so it can consume the exact identifier the migration needs, and the migration's `only-write-if-absent` semantics (mirroring `migrateHandle()`'s single-mint-per-handle semantics) make the collision permanent and unrecoverable through code paths available to the affected legacy account holder (they cannot re-set an `accountId`, `SetAccountIdActuator` line 91-93 rejects "This account id already set").

### Impact Explanation
The legacy account's `accountId` index entry is permanently lost/orphaned (its stale Turkish-locale key is deleted, and the canonical ROOT key is never populated), while an unrelated user retains the canonical identifier. This is an unrecoverable state divergence/accounting inconsistency in a consensus-relevant store (`AccountIdIndexStore` extends `TronStoreWithRevoking`, meaning it participates in chain state and snapshotting), and it silently corrupts the mapping rather than reverting — arguably worse than the Lens case, where the failure was at least a loud revert rather than silent state loss. The severity is bounded because `accountId` is a convenience alias (not a balance/asset field), so no direct fund loss occurs, but any downstream tooling or contract logic relying on `accountId` uniqueness/permanence for the legacy account is broken indefinitely.

### Likelihood Explanation
Exploitation requires the attacker to know (or guess) which accountId strings correspond to pre-existing Turkish-locale-keyed entries and to submit a `SetAccountIdContract` transaction for the ROOT-normalized form before the node-local migration executes. Since `MigrateTurkishKeyHelper.doWork()` runs unconditionally at `Manager.init()` (gated only by a one-time done-flag) rather than being enforced atomically at a fixed hard-fork block height across all nodes, the timing window during which this race is possible is uncertain from the available code and could not be fully confirmed — this is a notable gap in verification. Given the migration is described as intended for legacy data cleanup, the affected key set is likely small and this may already be effectively closed on long-running networks, which somewhat lowers real-world likelihood.

### Recommendation
- Before or during migration, `SetAccountIdActuator.validate()` should also reject new registrations whose ROOT-normalized `accountId` corresponds to any still-pending (un-migrated) legacy Turkish-keyed entry, analogous to Lens's off-chain/pre-flight check against not-yet-migrated V1 profiles.
- Alternatively, perform the Turkish-key migration atomically and deterministically as part of consensus-enforced block processing (e.g., gated to a specific block/hardfork) rather than as a node-local, non-deterministic startup routine, and reject colliding `SetAccountIdContract` transactions once the migration is scheduled/pending.
- Log/alert (rather than silently skip) when Phase 2 of `MigrateTurkishKeyHelper.doWork()` finds the ROOT key already occupied, so operators are aware that a legacy identifier failed to migrate.

  @Test
  @SuppressWarnings("StringCaseLocaleUsage")
  public void testKeysMigration() {
    String[]accountIds = {"", "12345678", "543838383", "BitTorrent",
        "Converse", "HelloWorld", "InfStonesSSRWallet", "ISSRWallet", "JustDoIt",
        "JustinSun", "JustinSunTron", "RtytIturtet", "TronBetFestival", "vena_family"
    };

    byte[][] addresses = new byte[accountIds.length][];
    byte[][] turkishKeys = new byte[accountIds.length][];

    for (int i = 0; i < accountIds.length; i++) {
      addresses[i] = randomBytes(21);
      String turkishLower = accountIds[i].toLowerCase(TURKISH);
      turkishKeys[i] = turkishLower.getBytes(StandardCharsets.UTF_8);
      accountIdIndexStore.put(turkishKeys[i], new BytesCapsule(addresses[i]));
    }

    for (int i = 0; i < accountIds.length; i++) {
      String rootLower = accountIds[i].toLowerCase(Locale.ROOT);
      String turkishLower = accountIds[i].toLowerCase(TURKISH);
      boolean shouldMiss = !rootLower.equals(turkishLower);
      if (shouldMiss) {
        Assert.assertNull(
            "pre-migrate: ROOT query should miss for " + accountIds[i],
            accountIdIndexStore.get(ByteString.copyFrom(
                accountIds[i].getBytes(StandardCharsets.UTF_8))));
      } else {
        Assert.assertArrayEquals(
            "pre-migrate: ROOT query should hit for " + accountIds[i],
            addresses[i],
            accountIdIndexStore.get(ByteString.copyFrom(
                accountIds[i].getBytes(StandardCharsets.UTF_8))));
      }
    }

    new MigrateTurkishKeyHelper(chainBaseManager).doWork();

    for (int i = 0; i < accountIds.length; i++) {
      Assert.assertArrayEquals(
          "post-migrate: get(" + accountIds[i] + ")",
          addresses[i],
          accountIdIndexStore.get(ByteString.copyFrom(
              accountIds[i].getBytes(StandardCharsets.UTF_8))));
      String lower = accountIds[i].toLowerCase(Locale.ROOT);
      Assert.assertTrue(
          "post-migrate: has(" + lower + ")",
          accountIdIndexStore.has(lower.getBytes(StandardCharsets.UTF_8)));
      String upper = accountIds[i].toUpperCase(Locale.ROOT);
      Assert.assertTrue(
          "post-migrate: has(" + upper + ")",
          accountIdIndexStore.has(upper.getBytes(StandardCharsets.UTF_8)));
    }
  }
