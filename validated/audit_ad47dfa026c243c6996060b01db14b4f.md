### Title
Hardcoded, non-chain-specific `ADDRESS_REGISTRAR_ACCOUNT_ID` in the Wallet Contract can silently disable the anti-faulty-relayer address check, enabling relayer-directed value redirection - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (NEP-518 ETH-implicit account contract) relies on a single, compile-time constant `ADDRESS_REGISTRAR_ACCOUNT_ID` — baked into the WASM via `include_str!` from a static file — as the sole "oracle" of which named NEAR accounts are properly registered addresses. Unlike other network-dependent constants in the same crate (e.g. `eth_wallet_global_contract_hash`, which is explicitly branched per `MAINNET`/`TESTNET`/`LOCALNET`), this registrar reference is a single flat value used unconditionally across every chain the contract is deployed to. If this hardcoded reference is wrong or stale for the network it is actually deployed on (analogous to the Sherlock report's wrong hardcoded price-feed address), the on-chain "faulty relayer" security check silently degrades, letting a relayer redirect a user's Ethereum-emulated transaction to an unregistered/attacker-chosen account without being banned.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is defined as a compile-time constant: [1](#0-0) 

It is parsed and used directly, with any parse failure only causing a panic — there is no runtime cross-check against the actual chain/network the contract is running on: [2](#0-1) 

This contrasts with how the sibling crate correctly branches equivalent chain-specific values by `chain_id`: [3](#0-2) 

The registrar lookup result directly determines whether a relayer is banned for failing to properly resolve a named account, in `address_check_callback`: [4](#0-3) 

If the registrar lookup fails (wrong/non-existent account, or an account that returns unexpected data because it was never actually deployed there), the callback simply reports an error and does **not** ban the relayer: [5](#0-4) 

The comments in `internal.rs` make explicit that checking the registrar is the *only* mechanism preventing a "lazy"/faulty relayer from redirecting a transaction meant for a named account to an unregistered target instead: [6](#0-5) 

and the corresponding test explicitly demonstrates that a relayer who fails to consult the registrar correctly is only caught, and banned, *because* the registrar lookup succeeds and returns the expected mapping: [7](#0-6) 

If `ADDRESS_REGISTRAR_ACCOUNT_ID` is misconfigured for the network in question (wrong account name baked into the deployed WASM/global contract for that chain_id, or the registrar contract not actually deployed there), the `lookup` call fails or returns `None` unconditionally, which the callback treats identically to "not registered" — i.e., the anti-fraud check is effectively neutered network-wide for every ETH-implicit account using that WASM.

### Impact Explanation
A relayer holding only a limited `FunctionCall` access key granted by the user (see `near_action::AccessKeyPermission::FunctionCall` grants in `action_to_promise`) can act as an unprivileged meta-transaction sender. With the registrar check disabled by misconfiguration, such a relayer (or any relayer, faulty or malicious) can set an incorrect `target` for a base-token transfer that was supposed to hash-check against a registered named account, redirecting the user's transfer to an account other than the intended recipient — all while evading the `ban_relayer` mechanism that is supposed to detect and punish exactly this behavior. This is unauthorized redirection/movement of user value through a code path reachable by any relayer submitting an RLP-encoded meta-transaction, with the safety net (banning) permanently defeated for the affected deployment.

### Likelihood Explanation
This requires the registrar constant to actually be wrong for the deployed chain — but the design pattern itself (single global constant instead of chain_id-branched values, contrasted with the correctly-branched `eth_wallet_global_contract_hash`) makes this a latent, easy-to-introduce misconfiguration in exactly the way the analog report describes (one wrong hardcoded address silently breaking a validation dependency). Any release/build process that reuses the WASM/global contract across networks without regenerating this file is exposed.

### Recommendation
Branch `ADDRESS_REGISTRAR_ACCOUNT_ID` per `chain_id` the same way `eth_wallet_global_contract_hash` does in `runtime/near-wallet-contract/src/lib.rs`, and fail closed (ban the relayer, or reject the transaction) rather than fail open when the registrar call fails/returns unexpected data in `address_check_callback`.

### Proof of Concept
1. Build/deploy the Wallet Contract WASM as a global contract for network B while `ADDRESS_REGISTRAR_ACCOUNT_ID` still contains the registrar account name valid only for network A (or an account that does not exist on B).
2. A user grants a relayer a `FunctionCall` access key and signs an Ethereum-style transaction whose `to` address corresponds to a NEP-141 token account that would be registered in the (correct) address registrar.
3. Relayer submits `rlp_execute` with `target` set to an account of its choosing instead of resolving the registered account.
4. `address_check_callback` receives `PromiseResult::Failed` (registrar doesn't exist on B) or an unexpected response, and returns an error response without invoking `create_ban_relayer_promise`, leaving the relayer's key active and the mis-targeted action processed as shown in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:140-174`.

// Tests the situation where the relayer sets `target == tx.to` when it should have
// looked up the named account corresponding to `tx.to`. In this case the relayer
// should be banned for being lazy.
#[tokio::test]
async fn test_relayer_invalid_address_target() -> anyhow::Result<()> {
    let TestContext {
        worker,
        mut wallet_contract,
        wallet_sk,
        wallet_address,
        address_registrar,
        ..
    } = TestContext::new().await?;

    // Deploy a NEP-141 contract and register its address.
    // Registering should prevent a lazy relayer from setting the target incorrectly.
    let token_contract = nep141::Nep141::deploy(&worker).await?;
    let register_output: Option<String> = address_registrar
        .call("register")
        .args_json(serde_json::json!({
            "account_id": token_contract.contract.id().as_str()
        }))
        .max_gas()
        .deposit(NearToken::from_millinear(1))
        .transact()
        .await?
        .json()?;
    let token_address: [u8; 20] =
        hex::decode(register_output.as_ref().unwrap().strip_prefix("0x").unwrap())?
            .try_into()
            .unwrap();
    assert_eq!(
        token_address,
        account_id_to_address(&token_contract.contract.id().as_str().parse().unwrap(),).0
    );

    // Set up a relayer with control to send transactions via the Wallet Contract account.
    let relayer_pk = wallet_contract.register_relayer(&worker).await?;

    // The user submits a transaction to interact with the NEP-141 contract.
    let transaction = aurora_engine_transactions::eip_2930::Transaction2930 {
        nonce: 0.into(),
        gas_price: 0.into(),
        gas_limit: 0.into(),
        to: Some(Address::from_array(token_address)),
        value: Wei::zero(),
        data: [
            crate::eth_emulation::ERC20_BALANCE_OF_SELECTOR.to_vec(),
            ethabi::encode(&[ethabi::Token::Address(wallet_address)]),
        ]
        .concat(),
        chain_id: CHAIN_ID,
        access_list: Vec::new(),
    };
    let signed_transaction = crypto::sign_transaction(transaction, &wallet_sk);

    // Relayer fails to set `target` correctly
    let result =
        wallet_contract.rlp_execute(register_output.unwrap().as_str(), &signed_transaction).await?;

    assert!(!result.success);
    assert_eq!(result.error.as_deref(), Some("Error: faulty relayer"));

    assert_revoked_key(&wallet_contract.inner, &relayer_pk).await;

    Ok(())
}
