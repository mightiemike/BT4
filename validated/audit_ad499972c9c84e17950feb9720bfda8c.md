### Title
`finalize_cancellation` deletes an already-Committed L1 handler transaction record, allowing a consumed L1→L2 message to become proposable again - (File: crates/apollo_l1_events/src/transaction_manager.rs)

### Summary
`TransactionManager::finalize_cancellation` unconditionally removes a transaction's `TransactionRecord` from `records` whenever an L1 `MessageToL2Canceled` event arrives, regardless of the record's actual lifecycle state. This mirrors the referenced bug class ("deleting a struct erases state that should have been preserved/guarded"): here, deleting the record erases the `Committed` marker that is the sequencer's sole protection against re-treating an already-executed L1 handler transaction as a fresh, proposable transaction.

### Finding Description
`request_cancellation` → `TransactionRecord::mark_cancellation_request` explicitly tolerates being called on an already-`Committed` record: it only logs a warning and leaves `state == Committed`, while still recording `cancellation_requested_at`: [1](#0-0) 

`finalize_cancellation` is then invoked from `MessageToL2Canceled` (L1 event, triggerable by the original L1 message sender via the bridge contract's `cancelL1ToL2Message`, an unprivileged L1 sender action). It checks the state only to emit a warning — it does **not** abort — and then deletes the record unconditionally: [2](#0-1) 

Once removed, `is_committed(tx_hash)` and `exists(tx_hash)` both return `false`: [3](#0-2) 

If the same `LogMessageToL2` event is scraped again (re-scrape after restart, delayed/duplicate scrape, or state-sync catch-up feeding `add_tx`), `add_tx` treats the (now-absent) hash as brand new via `create_record_if_not_exist`, and re-creates a fresh `Pending`, proposable record for a transaction whose L1→L2 message was already executed on L2: [4](#0-3) 

This is exactly analogous to the referenced Biconomy bug: a state-clearing operation (`delete nftInfo` / `self.records.remove(&tx_hash)`) is executed without first checking/preserving critical accounting state (`unpaidRewards` / `Committed` status) that a later legitimate actor needs to rely on.

### Impact Explanation
If the tx-hash becomes proposable again and is included in a future block, the sequencer would attempt to re-execute an L1 handler whose L1→L2 message was already consumed. Whether this manifests as a reverted L1-handler transaction (wasted block space / minor DoS on that slot) or as a genuine double-execution depends on downstream replay protection in the OS's message-consumption bookkeeping, which independently decrements a per-message counter — this repo's blockifier code checks `paid_fee`/fee bounds but the concrete consumption-count guard lives in the Starknet OS Cairo program, which was not fully traceable within the available index. Regardless of whether the OS-level counter fully blocks fund-level double-spend, the sequencer's own bookkeeping is corrupted: a legitimately `Committed` transaction is silently treated as never-executed, `is_committed()` becomes wrong, and the transaction can be resurrected into `Pending`/proposable state — a violation of the invariant documented at `records: /// Storage of all l1 handler transactions --- keeps transactions until they can be safely removed, like when they are consumed on L1, or fully cancelled on L1` and of the state machine invariant that `CancellationFinalizedOnL1`/deletion should only occur for a genuinely-cancelled (not committed) transaction. At minimum this causes wasted/failed block proposals (liveness impact); at worst (if OS-level replay protection has any gap for the re-proposed case) it enables re-execution of a message whose funds/effects were already applied on L2.

### Likelihood Explanation
Reachable from a single, unprivileged actor path: the original L1 message sender (who can always call `cancelL1ToL2Message`/`requestL1ToL2MessageCancellation` on the bridge contract for their own message) combined with the sequencer's own normal transaction commitment. No malicious operator/proposer/peer is required — only ordinary races between "my message got included on L2" and "I already asked L1 to cancel it because I gave up waiting," which is a realistic user behavior, especially near the cancellation timelock boundary. The additional re-scrape/re-add trigger (state-sync catch-up or scraper restart re-observing the same `LogMessageToL2` log) is a normal operational occurrence, not an adversarial one.

### Recommendation
In `finalize_cancellation` (and `mark_cancellation_finalized_on_l1`), refuse to delete (or even transition) a record whose state is `Committed`: if `record.is_committed()`, log at a higher severity and return early without calling `self.records.remove(&tx_hash)`, preserving the committed marker permanently (analogous to guarding `delete nftInfo` with `require(unpaidRewards == 0)`). Consider also hardening `add_tx`/`create_record_if_not_exist` to consult a permanent (never-pruned, or separately-persisted) "known committed tx hashes" set, so that even if a record is transiently missing, a previously committed L1 handler hash can never be re-admitted as `Pending`.

### Proof of Concept
1. L1 sender emits `LogMessageToL2` for tx `T`. Scraper delivers it; `add_tx` creates `Pending` record for `T`.
2. `T` is proposed and committed on L2: `commit_txs` calls `mark_committed()`, setting `state = Committed`, `committed = true` (`crates/apollo_l1_events/src/transaction_record.rs:50-60`).
3. The L1 sender, unaware or indifferent to L2 commitment, calls `requestL1ToL2MessageCancellation` on the bridge; after the L1 contract's own timelock, calls `cancelL1ToL2Message`.
4. The scraper delivers `TransactionCancellationStarted` for `T`: `request_cancellation` → `mark_cancellation_request` sees `is_committed() == true`, only warns, leaves `state = Committed` (`transaction_record.rs:77-101`).
5. The scraper later delivers `TransactionCanceled` for `T`: `finalize_cancellation` sees `record.state != CancellationStartedOnL2` (it's `Committed`), only warns, but still calls `mark_cancellation_finalized_on_l1()` and `self.records.remove(&tx_hash)` (`transaction_manager.rs:221-245`).
6. `T`'s record is gone: `exists(T) == false`, `is_committed(T) == false`.
7. A re-scrape of the original `LogMessageToL2` log for `T` (e.g., scraper restart, catch-up sync) calls `add_tx(T, ...)`; `create_record_if_not_exist` sees no existing record and creates a fresh `Pending` (proposable) record for `T` (`transaction_manager.rs:173-209`), even though `T` was already committed to L2 in step 2.

    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }

    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }

    pub fn finalize_cancellation(&mut self, tx_hash: TransactionHash) {
        let Some(record) = self.records.get(&tx_hash) else {
            info!(
                "Attempted to finalize cancellation for non-existent transaction: {tx_hash}. This \
                 can happen if the transaction was too old to be scraped (e.g. it was created \
                 before we started scraping)."
            );
            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).
        if record.state != TransactionState::CancellationStartedOnL2 {
            warn!(
                "Attempted to finalize cancellation for transaction {tx_hash} that is not in the \
                 cancellation started on L2 state, but in the {:?} state.",
                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
        self.records.remove(&tx_hash);
    }
