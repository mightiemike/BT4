### Title
Zero-lamport accounts remain permanently un-purgeable and their storage un-reclaimable when the full-snapshot interval is large, causing unbounded disk growth - (File: accounts-db/src/accounts_db.rs)

### Summary
Analogous to the ExManager bug — where a bonded asset is deposited into a mechanism that is designed to release it only after a specific lifecycle event, but no code path exists to actually reclaim it once that event is delayed or never happens — `AccountsDb` defers reclamation of zero-lamport accounts behind the arrival of a *full* snapshot. Any account made zero-lamport by ordinary, unprivileged transaction activity is placed into `zero_lamport_accounts_to_purge_after_full_snapshot` and its backing storage is kept alive indefinitely until `latest_full_snapshot_slot` advances past its slot. If the full-snapshot interval is large (a configuration the validator itself warns is dangerous) or otherwise stalls, this "bonded" garbage accumulates without limit, and the storage/space it occupies cannot be recovered — mirroring the "locked with no redemption path" bug class from the external report.

### Finding Description
`filter_zero_lamport_clean_for_incremental_snapshots` gates the purge of zero-lamport accounts to protect incremental-snapshot correctness: any zero-lamport account whose write slot is above `latest_full_snapshot_slot` is not purged and is instead stashed in `zero_lamport_accounts_to_purge_after_full_snapshot`: [1](#0-0) 

This deferred set is only drained inside `construct_candidate_clean_keys`, and only when `latest_full_snapshot_slot_advanced_since_clean` is true (i.e., only after a *new* full snapshot has actually been produced): [2](#0-1) 

The backing `AccountStorageEntry` for these slots is likewise retained by clean (`can_purge_zero_lamport_single_ref_after_shrink` and the tombstone-purge path in `construct_candidate_clean_keys` both check the slot against `latest_full_snapshot_slot`), so until a full snapshot advances, both the index entries and the on-disk storage bytes for these garbage accounts are pinned: [3](#0-2) [4](#0-3) 

Whether/how often this release condition is even reachable is entirely a function of the operator's snapshot configuration, which is exposed via the `--full-snapshot-interval-slots` CLI flag. The validator's own startup code explicitly warns that setting this interval too large will hurt AccountsDB cleanup: [5](#0-4) 

and `SnapshotConfig` allows generating only incremental snapshots while never producing a full one is disallowed by `is_snapshot_config_valid`, but nothing prevents an operator from setting an extremely large, valid full-snapshot interval (there is no upper bound enforced, only a warning): [6](#0-5) 

Because ordinary unprivileged users create zero-lamport accounts simply through normal account lifecycle operations (e.g., closing token accounts, spending an account to zero balance), any user's routine transaction activity feeds `zero_lamport_accounts_to_purge_after_full_snapshot` and the associated retained storage. As with the ExManager bond, the deposit (garbage creation) is unconditional and immediate, but the release mechanism (full-snapshot-gated clean) is conditional on an external, potentially indefinitely-delayed event, with no alternate recovery path in `AccountsDb`.

### Impact Explanation
This is a disproportionate storage/CPU cost issue: garbage created cheaply by ordinary transactions is retained in both the in-memory accounts index and on-disk append-vec storage for as long as the configured (or stalled) full-snapshot interval lasts, growing without bound during that window. This directly matches the "disproportionate storage and CPU cost" acceptance criterion — it does not require multiple RPC clients or crafted snapshots, only sustained ordinary zero-lamport account churn combined with a large full-snapshot interval, which the codebase itself flags as a real, reachable, config-driven risk.

### Likelihood Explanation
Likelihood is moderate: it requires an operator-chosen (but permitted and not size-limited) large `full_snapshot_archive_interval_slots`, combined with organic zero-lamport account creation by any unprivileged user during that window. The validator explicitly documents this as a real operational risk ("This will negatively impact the background cleanup tasks in accounts-db"), indicating the scenario is anticipated as reachable in production rather than purely theoretical.

### Recommendation
Consider adding an independent, time/slot-bounded reclamation path for `zero_lamport_accounts_to_purge_after_full_snapshot` and its retained storages that does not depend solely on the next full snapshot completing (e.g., a size- or age-based fallback sweep, or an enforced maximum full-snapshot interval), so that garbage accumulation is bounded even if full snapshots are delayed or configured very infrequently.

### Proof of Concept
1. Configure a validator with `--full-snapshot-interval-slots` set to a very large value (well beyond `DEFAULT_SLOTS_PER_EPOCH`, which the code itself calls out as risky).
2. As an ordinary unprivileged user, repeatedly create and then zero-out (close/drain) accounts across many slots.
3. Observe that `clean_accounts`/`filter_zero_lamport_clean_for_incremental_snapshots` routes these into `zero_lamport_accounts_to_purge_after_full_snapshot` and their storages remain in `self.storage` because `can_purge_zero_lamport_single_ref_after_shrink` returns `false` for all these slots.
4. Storage usage and index memory grow proportionally to attacker/user-generated zero-lamport churn until the next full snapshot slot is reached, which — given the configured interval — may be arbitrarily far in the future.

pub fn is_snapshot_config_valid(snapshot_config: &SnapshotConfig) -> bool {
    // if the snapshot config is configured to *not* take snapshots, then it is valid
    if !snapshot_config.should_generate_snapshots() {
        return true;
    }

    let SnapshotInterval::Slots(full_snapshot_interval_slots) =
        snapshot_config.full_snapshot_archive_interval
    else {
        // if we *are* generating snapshots, then the full snapshot interval cannot be disabled
        return false;
    };

    match snapshot_config.incremental_snapshot_archive_interval {
        SnapshotInterval::Disabled => true,
        SnapshotInterval::Slots(incremental_snapshot_interval_slots) => {
            full_snapshot_interval_slots > incremental_snapshot_interval_slots
        }
    }
}
