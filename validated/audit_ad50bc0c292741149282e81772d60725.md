Based on my investigation, I found a concrete analog to the Lido `MAX_STETH_WITHDRAWAL_AMOUNT` issue: the SVM outbound path enforces a hard `u64` amount ceiling (`amount.IsUint64()`) that PRC20/uint256 accounting can legitimately exceed, and unlike EVM (which has no such cap and a documented fund-migration/refund path), a SVM outbound that fails this check has **no automatic remediation** — per `x/uexecutor/README.md`, ballot expiry does *not* remove `PendingOutbounds` entries and auto-refund is explicitly avoided as "governance-driven, not chain-driven."

### Title
Outbound funds permanently stuck when SVM destination amount exceeds `u64` max with no automatic revert path - (File: `universalClient/chains/svm/tx_builder.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
`GetOutboundSigningRequest` (and its duplicated parsing in `BuildOutboundTransaction`/`BuildRefRouteTransactions`) rejects any outbound whose `Amount` does not fit in a Solana `u64`: [1](#0-0) 
This mirrors the Lido bug class exactly: Push Chain's PRC20/uint256 token accounting on the EVM side allows minting/bridging amounts far larger than Solana's native `u64` transfer capacity (`18,446,744,073,709,551,615` base units), just as Lido's `stETH` balance can exceed `MAX_STETH_WITHDRAWAL_AMOUNT`.

### Finding Description
An inbound deposit or a large PRC20 balance destined for a Solana outbound is created via `BuildOutboundsFromReceipt`, which copies `event.Amount.String()` verbatim into the `OutboundTx.Amount` field with no upper-bound validation against the destination chain's numeric limits: [2](#0-1) 
`OutboundTx.ValidateBasic()` only checks that the amount is a *positive* uint256 — it never checks it against destination-chain-specific ceilings such as Solana's `u64`: [3](#0-2) 

Once this outbound reaches `PendingOutbounds` and a Universal Validator/coordinator attempts to sign it via `GetOutboundSigningRequest`, every validator's SVM `TxBuilder` will deterministically fail with `"amount exceeds u64 max"` — the signing session can never complete, so the funds locked in the Solana vault for this outbound (or the PRC20/user claim on Push Chain side) can never be released through the ordinary outbound pipeline.

Critically, the project's own documented design explicitly states there is **no automatic recovery** for a stuck outbound: ballot expiry does not remove the `PendingOutbounds` entry, and auto-refund/auto-retry are intentionally avoided because "there is no safe automatic resolution": [4](#0-3) 

This is the direct analog of the Lido bug: an ordinary, unprivileged large-value cross-chain transfer produces an outbound amount that structurally cannot be finalized on the destination chain, and the protocol has no chain-level path to unwind or refund it — the value becomes stuck pending manual/governance intervention.

### Impact Explanation
Under the "Allowed Impact Gate," this qualifies as **permanent freezing of user or protocol-controlled funds** reachable via a normal unprivileged user action (bridging/depositing an amount that legitimately exceeds `u64` when routed to an SVM destination — e.g., a whale deposit, a large PRC20 balance being withdrawn to Solana, or amounts inflated via decimal-scaling between chains). Once created, the outbound is permanently un-signable by honest, correctly-functioning validators; no malicious actor is required.

### Likelihood Explanation
Likelihood is constrained by the fact that `u64::MAX` (~1.8×10^19) is still a very large threshold in base units, and most legitimate token amounts (even with 18 decimals) will not exceed it under normal circumstances — analogous to how the judge downgraded the original Lido finding to Medium due to reduced likelihood of such large amounts. It is more likely to be triggered by tokens with unusual decimal configurations, PRC20 mis-scaling, or intentionally large transfers, rather than typical everyday usage.

### Recommendation
Add a destination-chain-aware maximum-amount check in `OutboundTx.ValidateBasic()` (or in `BuildOutboundsFromReceipt` before appending the outbound) that rejects/reroutes outbound amounts exceeding `math.MaxUint64` when `DestinationChain` resolves to an SVM chain, and automatically create an `INBOUND_REVERT`/refund path (mirroring the zero-amount pre-execution failure handling already used elsewhere) instead of leaving the entry permanently pending with no resolution.

### Proof of Concept
1. Attacker (or any user) triggers an inbound deposit/payload on an EVM source chain that results in a `UniversalTxOutbound` event with `Amount > 18,446,744,073,709,551,615` (uint256) targeting a Solana `DestinationChain`.
2. `BuildOutboundsFromReceipt` creates the `OutboundTx` unconditionally (no upper-bound check) and it is added to `PendingOutbounds`.
3. `ValidateBasic()` passes since the amount is a valid positive uint256.
4. Every Universal Validator's SVM `TxBuilder.GetOutboundSigningRequest` deterministically returns `"amount exceeds u64 max"` when the coordinator attempts to build the signing request; the TSS signing session can never complete for this outbound.
5. Per the documented design in `x/uexecutor/README.md`, the `PendingOutbounds` entry is never auto-removed/auto-refunded on ballot expiry — the corresponding value remains locked with no on-chain resolution path.
