### Title
Unauthenticated WorkflowDonID spoofing when workflowDONBindingGate is disabled allows cross-DON capability execution authorization bypass - ([File: core/capabilities/remote/executable/request/server_request.go])

### Summary
`executeCapabilityRequest` only binds `capabilityRequest.Metadata.WorkflowDonID` to the authenticated `callingDonID` when `workflowDONBindingGate.Limit(ctx)` returns `enabled=true`. Since the gate is feature-flagged and can be off (its own test suite explicitly exercises and asserts the disabled-gate case as "still executes"), any low-privilege member of a legitimate calling DON can set an arbitrary `WorkflowDonID` in the request metadata and have `capability.Execute` run as if the request came from a different DON.

### Finding Description
`OnMessage` (`core/capabilities/remote/executable/request/server_request.go:178-214`) accepts messages from peers that are members of the authenticated `callingDon` (`addRequester`, line 259-273, checks `slices.Contains(e.callingDon.Members, from)`), so the *sender* identity is legitimately verified against DON membership/peer identity. However, once quorum (`F+1`) is reached, `executeRequest` calls `executeCapabilityRequest` passing `e.callingDon.ID` and `e.workflowDONBindingGate` [1](#0-0) .

Inside `executeCapabilityRequest`, the payload — fully attacker/DON-peer-controlled since it comes from `msg.Payload` sent by a workflow-DON peer — is unmarshalled into `capabilityRequest`, whose `Metadata.WorkflowDonID` is caller-supplied. The binding check is conditioned on the gate:
```go
enabled, gerr := workflowDONBindingGate.Limit(ctx)
...
if enabled && capabilityRequest.Metadata.WorkflowDonID != callingDonID {
    ... return error
}
...
capResponse, err := capability.Execute(ctx, capabilityRequest)
``` [2](#0-1) 

When `enabled == false` (gate off/default), the mismatch check is skipped entirely, and `capability.Execute` is invoked with the forged `WorkflowDonID` while only the true `callingDonID` was verified against peer membership. The underlying capability (and any downstream DON-scoped authorization logic that trusts `Metadata.WorkflowDonID`, e.g. capabilities that key off `WorkflowDonID` for scoping/consensus/secrets) will treat the request as originating from the spoofed DON.

This is confirmed by the repo's own test `Test_ServerRequest_WorkflowDONBinding`, subtest `"gate disabled, WorkflowDonID mismatch still executes"`, which constructs a request with `callingDonID+99` as the metadata `WorkflowDonID` while the gate is `limits.NewGateLimiter(false)`, and asserts `d.msgs[0].Error == types.Error_OK` — i.e., execution proceeds despite the mismatch [3](#0-2) . The contrasting `"gate enabled"` subtest shows the intended protection only fires when the gate is on [4](#0-3) .

The gate defaults to off unless explicitly enabled via settings (`workflowDONBindingGate` is a `limits.GateLimiter` constructed and passed in from `NewServer`/`launcher.go`, feature-flag controlled), meaning in default/unrolled-out configurations this binding invariant does not hold.

Note: I could not fully verify from the index which specific downstream capabilities key authorization/business logic directly off `Metadata.WorkflowDonID` beyond what's referenced (e.g. `core/capabilities/vault/zone_b_restriction.go` explicitly does NOT trust caller-supplied WorkflowDonID and instead re-resolves DON membership via `capabilitiesRegistry.DONByID`, which is a mitigating pattern elsewhere in the codebase, `core/capabilities/vault/zone_b_restriction.go:97-122`) — so the severity of concrete downstream impact depends on which specific `ExecutableCapability` implementations trust the metadata field directly. This would require further investigation via a Devin session for a complete downstream impact assessment.

### Impact Explanation
A legitimate but low-privileged member of workflow-DON A can cause the executable capability server to execute a capability request "as" workflow-DON B (or any arbitrary `WorkflowDonID`) whenever the binding gate is disabled. For any capability whose execution logic or downstream effects (rate limiting, secrets scoping, resource attribution, billing/metrics, per-DON restrictions) rely on `Metadata.WorkflowDonID` being trustworthy, this permits unauthorized cross-DON attribution and potential bypass of DON-scoped authorization boundaries — matching a privilege-escalation / unauthorized-workflow-execution class of impact.

### Likelihood Explanation
Feasibility is high and requires no special privilege beyond being one of the `F+1` legitimate members of an already-registered calling DON (`addRequester` only checks DON membership, not metadata authenticity). The only precondition is that `workflowDONBindingGate.Limit(ctx)` evaluates to `false`, which is the default/pre-rollout state of this specific feature flag as evidenced by the gate's own test coverage and rollout-oriented design (comment: "When enabled, bind the caller-supplied WorkflowDonID..."). This is fully reproducible and deterministic — not a race or timing-dependent condition.

### Recommendation
Make the `WorkflowDonID` binding check unconditional (remove the `enabled &&` gate condition on the security-critical rejection at `server_request.go:362`), so that `Metadata.WorkflowDonID` is always bound to the authenticated `callingDonID` regardless of feature-flag rollout state. If a rollout mechanism is still desired for observability/telemetry purposes, gate only logging/metrics, not the actual authorization decision.

### Proof of Concept
Already present in-repo: `core/capabilities/remote/executable/request/server_request_binding_test.go`, subtest `"gate disabled, WorkflowDonID mismatch still executes"` (lines 91-95) constructs a quorum of `F+1` requests from legitimate `callingDon` peers with `Metadata.WorkflowDonID = callingDonID + 99` and gate `limits.NewGateLimiter(false)`, then asserts `d.msgs[0].Error == types.Error_OK`, proving capability execution proceeds with the spoofed `WorkflowDonID` unchecked. Contrast with the `"gate enabled"` subtest (lines 78-83) which asserts rejection under identical spoofing when the gate is `true`. This existing pair of tests is sufficient to document the gap; no new test is needed beyond flipping the gate default in production configuration to close it.
