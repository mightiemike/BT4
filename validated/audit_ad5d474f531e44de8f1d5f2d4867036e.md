## Title
Bancor-relay exchange formula (`ExchangeProcessor`) truncates supply/balance via unchecked `double`→`long` casts, letting an unprivileged trader accumulate rounding-favorable dust across repeated `ExchangeTransactionActuator` calls - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The Rolla report's root cause is implicit, unaudited rounding in chained fixed-point `mul`/`div` operations, exploited by splitting a large economic operation into many tiny operations so that per-operation truncation systematically favors the attacker, and by an unsafe numeric conversion (`intToUint` behaving as `abs`) that can flip a real deficit into an apparent (and payable) surplus. The strongest reachable analog in this java-tron fork is the legacy TRC10 AMM bonding-curve arithmetic in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which performs `pow`/`double` math and then truncates with a bare `(long)` cast with no explicit, direction-aware rounding policy, unlike the hardened `SafeExchangeProcessor` path that exists alongside it.

### Finding Description
`ExchangeProcessor` implements the Bancor-style relay-token math backing `Exchange`/`ExchangeCapsule.transaction`, used by TRC10 exchange contracts (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and the trade actuator that calls `ExchangeCapsule.transaction`). The two core steps are: [1](#0-0) [2](#0-1) 

Both `exchangeToSupply` and `exchangeFromSupply` compute a `double` via `Maths.pow(...)` and then truncate toward zero with `(long) issuedSupply` / `(long) exchangeBalance` — there is no explicit round-up/round-down policy analogous to Rolla's `toScaledUint(_roundDown)`. This is structurally the same class of bug as the report's bug 1: the implicit truncation happens *inside* the `mul`/`div`(here, `pow`/cast) primitive rather than being controlled at the call site, and the truncation direction is not chosen to always favor the pool (Controller-equivalent). Compare this to the parallel, explicitly-hardened `SafeExchangeProcessor`, which uses `BigDecimal` with an explicit `RoundingMode.DOWN` when converting from supply back to a balance: [3](#0-2) 

The existence of a "hardened" (`hardenedCalc`/`SafeExchangeProcessor`) code path selectable via `dynamicStore`/`allowStrictMath`/hardening flags, next to the still-reachable legacy `ExchangeProcessor` path, is itself evidence that the java-tron maintainers recognized precision/rounding hazards in this exact formula and mitigated them only behind a feature flag — the legacy path remains reachable by any unprivileged user issuing `ExchangeInject`, `ExchangeWithdraw`, or trade transactions when the hardening flag is not enabled, exactly mirroring the pre-mitigation Rolla contracts.

Additionally, `ExchangeCapsule.transaction` chooses between the two processors based on a `hardenedCalc` boolean, but the balance invariant check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is only enforced `if (hardenedCalc && ...)`: [4](#0-3) 

meaning the legacy `double`-based path has no post-hoc invariant check either — a direct structural analog to the Rolla report's underlying weakness (rounding errors compounding without a final sanity/invariant check).

### Impact Explanation
An attacker repeatedly executing small `ExchangeInject`/`ExchangeWithdraw`/trade operations against the same `Exchange` pool via the legacy (`double`-based) `ExchangeProcessor` can exploit the direction-unaware truncation in `exchangeToSupply`/`exchangeFromSupply` to bias the relay-supply/balance conversion in their favor over many iterations, extracting TRX/TRC10 token value from the pool's balances that is not backed by an equivalent deposit — i.e., value conjured via accumulated rounding, the same accounting-divergence impact class as the Rolla H-02 finding (tokens effectively stolen from the shared pool/"Controller"-equivalent). Because `ExchangeCapsule.transaction`'s negative-balance guard is gated behind `hardenedCalc`, the legacy path can also drive a pool balance negative without a chain-level revert, which is a stronger, invalid-state impact.

### Likelihood Explanation
Likelihood is **low-to-moderate**: the legacy path must still be selectable (i.e., `hardenedCalc`/related dynamic-store hardening flags not yet universally enforced/immutable), any single trade's rounding error is on the order of 1 unit (of TRX/token precision) per operation, and — exactly as the Rolla writeup itself concedes — practical extraction requires many repeated transactions (gas/bandwidth cost) and specific pool-balance ratios to make truncation favor the attacker consistently. This mirrors the Rolla report's own caveat that the exploit, while mathematically real, is "too costly to exploit under current [chain] environment," but the risk is not theoretical: it is directly reachable by any unprivileged account owning TRX/TRC10 tokens through public `ExchangeInjectContract`/`ExchangeWithdrawContract`/trade contracts, with no privileged role required.

### Recommendation
1. Confirm whether `hardenedCalc`/`allowStrictMath`/the `SafeExchangeProcessor` selection has been made mandatory (non-optional) on all networks; if the legacy `ExchangeProcessor` path is still reachable, deprecate and disable it entirely rather than gating it behind a runtime flag.
2. In `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, replace the bare `(long)` truncation with an explicit, direction-aware rounding function (round down when tokens flow out of the pool to the user, round up when they flow into the pool), matching the pattern already used in `SafeExchangeProcessor`/`RoundingMode.DOWN`.
3. Enforce the non-negative balance invariant unconditionally in `ExchangeCapsule.transaction`, not only when `hardenedCalc` is true, so any rounding/overflow error results in a hard failure instead of a silently corrupted pool state.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without a live node/testnet):
1. Create an `Exchange` pool with `ExchangeCreateActuator` using two tokens (e.g., TRX and a TRC10 asset) and deposit initial liquidity so that `firstTokenBalance`/`secondTokenBalance` are set via `ExchangeCapsule.setBalance`.
2. Ensure the network is running without the hardened resource/exchange calculation flag enabled (or that `hardenedCalc` resolves to `false` for the transaction path), so trades route through `ExchangeProcessor.exchange` (`chainbase/.../ExchangeProcessor.java` lines 41-45) instead of `SafeExchangeProcessor`.
3. Repeatedly submit small `sellTokenQuant` trades (or `ExchangeInjectContract`/`ExchangeWithdrawContract` pairs) chosen so that `exchangeToSupply`'s `(long) issuedSupply` truncation and `exchangeFromSupply`'s `(long) exchangeBalance` truncation both round in the trader's favor for the chosen balance ratios (analogous to the Rolla PoC's search for `X`, `Y`, `Z` ranges that make truncation favorable).
4. Observe, over many iterations, that the trader's aggregate token balance increases beyond what a single exact (BigDecimal, round-consistent) computation would allow, while the pool's `firstTokenBalance`/`secondTokenBalance` sum decreases correspondingly — demonstrating value extraction driven purely by uncontrolled truncation direction rather than an actual favorable trade.

Note: I was not able to execute this PoC in a live/test environment; the above is a structural argument grounded in the cited source, following the same methodology as the external report (splitting large transfers into repeated small ones to accumulate rounding bias). Verifying the exact profitability bound and confirming whether the hardened path is now mandatory on mainnet would require running the actual `ExchangeProcessorTest`/`ExchangeCapsuleTest` suites and current chain configuration, which is outside the scope of static code review.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
