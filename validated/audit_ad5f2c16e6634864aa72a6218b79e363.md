### Title
Paginated asset-issue query performs full O(n) iteration and O(n log n) sort regardless of requested `limit` - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
`GetPaginatedAssetIssueListServlet.fillResponse` forwards attacker-controlled `offset`/`limit` to `Wallet.getAssetIssueList(long, long)`, which calls `AssetIssueStore#getAssetIssuesPaginated`. That method always materializes the *entire* asset-issue table via `getAllAssetIssues()` and sorts it in full before slicing out the requested page, so a request with `limit=1` costs the same CPU as `limit=ASSET_ISSUE_COUNT_LIMIT_MAX`.

### Finding Description
The HTTP entrypoint `/wallet/getpaginatedassetissuelist` is handled by `GetPaginatedAssetIssueListServlet.doGet`/`doPost`, which parses `offset`/`limit` directly from request parameters and calls `fillResponse` → `wallet.getAssetIssueList(offset, limit)`: [1](#0-0) 

`Wallet.getAssetIssueList(long, long)` delegates directly to `getAssetIssuesPaginated`: [2](#0-1) 

`AssetIssueStore#getAssetIssuesPaginated(offset, limit)` calls the private overload with `getAllAssetIssues()`, which iterates the *entire* underlying RocksDB-backed store (an O(n) scan) before any offset/limit is applied: [3](#0-2) 

The private method then unconditionally sorts the full `assetIssueList` (O(n log n)) via a custom comparator, and only *after* the full iteration+sort does it clamp `limit` to `ASSET_ISSUE_COUNT_LIMIT_MAX` and slice `[offset, end)`: [4](#0-3) 

So the `ASSET_ISSUE_COUNT_LIMIT_MAX` cap only bounds the *response size*, not the *work performed*: the full scan and sort happen regardless of what `limit` the caller passes. An attacker requesting `limit=1` triggers the same CPU cost as requesting the maximum page size.

The endpoint is only protected by `RateLimiterServlet`, which throttles *request frequency* (QPS/IP-based), not per-request computational cost: [5](#0-4) 

This confirms there is no cost-scaling guard tying CPU work to the requested page size — only a frequency limiter that treats a cheap-looking `limit=1` request identically (in permit cost) to any other call to the same servlet.

### Impact Explanation
Since asset issuance is a normal, fee-paying user action (`AssetIssueContract` via `AssetIssueActuator`), any user can inflate `AssetIssueStore`/`AssetIssueV2Store` size over time: [6](#0-5) 

Once the store is large, every call to `/wallet/getpaginatedassetissuelist` (or the analogous gRPC `GetPaginatedAssetIssueList`, and the Solidity/PBFT variants) forces a full-table scan and sort on the node, even for `limit=1`. Repeated small-limit requests within the rate limiter's allowed QPS let an attacker sustain CPU cost proportional to the full asset list size per request, rather than to the tiny page requested — a public-HTTP CPU amplification/exhaustion vector affecting full nodes, solidity nodes, and PBFT nodes serving this API.

### Likelihood Explanation
- No special privileges are needed: any account that can pay the `AssetIssueContract` fee can create assets to grow the store size.
- The pagination servlet is public, unauthenticated HTTP (also exposed via gRPC `WalletSolidityApi`, `RpcApiServiceOnSolidity`, `RpcApiServiceOnPBFT`), reachable with a trivial `offset=0&limit=1` GET request.
- The only mitigation present (`RateLimiterServlet`) limits request *rate*, not request *cost*, so it does not decouple attacker cost from node cost — the attacker still gets full-scan work per permitted request.
- This is fully reproducible with a simple benchmark comparing `limit=1` vs `limit=ASSET_ISSUE_COUNT_LIMIT_MAX` timings at a fixed large store size.

### Recommendation
Redesign `getAssetIssuesPaginated` to avoid a full materialize+sort per call:
- Maintain a persistently sorted index/iterator (e.g., a store keyed by the sort order) so pagination can seek directly to `offset` instead of scanning and sorting the whole table.
- Alternatively, cache the sorted list and invalidate/rebuild it only when the asset-issue store changes (rebuild triggered by `AssetIssueActuator` writes), instead of rebuilding it on every read request.
- At minimum, bound the acceptable `offset` and apply a computational-cost-based rate limiter for this endpoint (e.g., limiter keyed on estimated store size) so cost scales with actual work rather than solely on request count.

### Proof of Concept
Java integration test (JMH-style or plain timing assertions) in `framework/src/test/java/org/tron/core/db/AssetIssueStoreTest.java` style:
1. Populate `AssetIssueStore` with N (e.g., 200,000) `AssetIssueCapsule` entries via `assetIssueStore.put(...)`.
2. Measure wall-clock time of `assetIssueStore.getAssetIssuesPaginated(0, 1)`.
3. Measure wall-clock time of `assetIssueStore.getAssetIssuesPaginated(0, Commons.ASSET_ISSUE_COUNT_LIMIT_MAX)`.
4. Assert the two measured times are statistically indistinguishable (e.g., within a small percentage of each other), and both scale linearly with N when repeated for N and 2N — demonstrating that `limit` does not reduce cost, i.e., cost is O(n) regardless of requested page size.
5. Optionally repeat via the HTTP path (`GetPaginatedAssetIssueListServlet.fillResponse`) using a mocked `HttpServletRequest`/`HttpServletResponse` to confirm the same behavior end-to-end.

  public List<AssetIssueCapsule> getAllAssetIssues() {
    return Streams.stream(iterator())
        .map(Entry::getValue)
        .collect(Collectors.toList());
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
