### Title
Sequencer permanently discards deposits from the deposit mempool even when the corresponding `BridgeDeposit` system transaction failed on-chain - (File: `crates/sequencer/src/runner.rs`)

### Summary
`produce_l2_block_inner` fetches a batch of deposit blobs from `DepositDataMempool`, runs them as `BridgeDeposit` system transactions, and then unconditionally removes the entire fetched batch from the mempool after block production, regardless of whether each individual deposit transaction actually succeeded on-chain.

### Finding Description
`process_sys_txs` at [1](#0-0)  explicitly handles the case where a deposit's system transaction fails: it reverts the working set, decrements the nonce, and `continue`s without adding the failed deposit's tx to `all_txs`. This means a deposit can fail execution (e.g. `Bridge.sol::deposit()` reverting due to a malformed/edge-case script, failed recipient call combined with a failing `failedDepositVault`, or any other revert path in the deposit call) without being included in the produced L2 block.

However, at the block-finalization step, `runner.rs::produce_l2_block_inner` calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the original `deposit_data` slice fetched at the top of the function via `fetch_deposits` [2](#0-1) , not a filtered list reflecting which deposits' system transactions actually succeeded and were appended to `all_txs`. The removal call is unconditional over the whole fetched batch: [3](#0-2) .

`DepositDataMempool::remove_deposits` deletes the deposit from both `accepted_deposit_txs` and `pending_deposits` [4](#0-3) , and `add_deposit_tx` refuses to re-add a deposit still marked pending / already removed-as-processed [5](#0-4) . Once removed, there is no other path shown in the sequencer that reintroduces a Bitcoin-side deposit that failed its on-chain crediting step; the accounting invariant broken is: **cBTC credited on Citrea must equal the set of Bitcoin deposits that were successfully applied** — here a Bitcoin deposit that was *not* applied (reverted `BridgeDeposit` system tx) is nonetheless treated as consumed/settled by the sequencer's mempool bookkeeping, exactly analogous to `emergencyRevoke` deleting a schedule without correcting `categoryUsed`: an internal "already handled" counter/set is updated even though the real state-changing effect did not happen.

### Impact Explanation
If a deposit's `BridgeDeposit` system transaction reverts for any reason during `process_sys_txs`, the deposit is dropped from `deposit_data` bookkeeping as "included" by the unconditional `remove_deposits(&deposit_data)` call, even though it was never actually applied on-chain (no `all_txs` entry, no state change, no cBTC credited). The user's Bitcoin deposit is silently and permanently lost from the sequencer's perspective — it will never be resubmitted, and the recipient never receives their cBTC, despite Bitcoin-side funds having moved to the bridge multisig. This is a direct violation of the "cBTC credited versus a Bitcoin deposit that actually happened" binding, resulting in funds effectively frozen from the user's perspective (no cBTC minted for a real deposit, and no automatic retry mechanism visible in this code path).

### Likelihood Explanation
This requires only that a `BridgeDeposit` system transaction constructed from an already-Bitcoin-included deposit fails on execution — a path Citrea's own code explicitly anticipates and handles ("deposits to non-EOA addresses can revert", per the comment at [6](#0-5) ). No privileged role, sequencer misbehavior, or malicious operator is required — the sequencer runs its normal, honest block-production logic; the bug lies purely in the mismatch between what `process_sys_txs` marks as executed versus what `produce_l2_block_inner` marks as removed from the deposit mempool. An attacker or ordinary user could trigger this simply by causing their deposit's target recipient/script to hit any revert branch in `Bridge.sol::deposit()` (e.g., crafting a smart-contract recipient whose fallback reverts, while `failedDepositVault` transfer also fails, or another revertible edge case in the deposit call), producing the described unrecoverable loss for their own deposit — or, more concerningly, if the batch contains multiple deposits, a single reverting deposit could still get incorrectly removed from mempool while all deposits fetched in the same batch are removed unconditionally regardless of individual success.

### Recommendation
Track which specific deposit blobs correspond to successfully applied `BridgeDeposit` system transactions in `process_sys_txs`/`produce_and_run_system_transactions`, and propagate only that successful subset back to `produce_l2_block_inner` for removal via `remove_deposits`. Deposits whose system transactions failed should remain in the `DepositDataMempool` (or be explicitly re-queued) so they can be retried in a subsequent block, ensuring the mempool's notion of "processed" deposits always matches the actual on-chain effect.

### Proof of Concept
Not independently reproduced in this review (would require a running sequencer + Bitcoin regtest harness), but the logical trace is:
1. A deposit's Bitcoin transaction is included and picked up by `DepositDataMempool::add_deposit_tx`.
2. `fetch_deposits` returns it as part of `deposit_data` in `produce_l2_block_inner` (`runner.rs:517-520`).
3. In `process_sys_txs`, the corresponding `BridgeDeposit` system transaction reverts (e.g., `Bridge.sol::deposit()` require/revert path), causing the branch at `runner.rs:1678-1697` to skip adding it to `all_txs`.
4. Block production finalizes without that deposit's state change ever being applied.
5. `produce_l2_block_inner` still calls `remove_deposits(&deposit_data)` with the original, unfiltered list (`runner.rs:636-643`), permanently deleting the failed deposit from `pending_deposits`/`accepted_deposit_txs`.
6. The deposit can never be resubmitted (rejected as duplicate is no longer possible since it's removed, but there is no other retry path shown), and the user's Bitcoin funds are never credited as cBTC.

Note: full confirmation that no other retry/backfill mechanism exists elsewhere in the sequencer (outside the indexed scope) could not be completed due to index size limits; a Devin session with full repository access could verify whether any compensating retry logic exists elsewhere in `crates/sequencer/**`.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }

    pub fn add_deposit_tx(&mut self, req: Deposit) -> anyhow::Result<bool> {
        let txid = Self::calc_tx_id(&req)?;

        debug!("Adding deposit with tx: {}", hex::encode(txid));

        // Check if deposit is already pending
        if !self.pending_deposits.insert(txid.to_vec()) {
            tracing::debug!("Deposit already pending in mempool");
            return Ok(false);
        }

        self.accepted_deposit_txs.push_back(req);
        SM.deposit_data_mempool_txs_inc.increment(1);
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        Ok(true)
    }
