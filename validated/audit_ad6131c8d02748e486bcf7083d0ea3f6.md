### Title
Precision loss in standby-witness reward distribution via divide-before-multiply double arithmetic - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.payStandbyWitness()` computes a per-vote payout by first dividing `totalPay` by `voteSum` to get a `double` rate, then multiplying that rate by each witness's vote count and truncating to `long`. This is structurally identical to the esMETA `unstakeRate = amount * nonSlashRate / 100 / timeToExit` bug: a division is performed first (losing precision), and the result is reused as a multiplier for many downstream computations, so truncation error accumulates across every recipient instead of being confined to a single, final division.

### Finding Description [1](#0-0) 

```java
public void payStandbyWitness() {
  List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(...);
  long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
  if (voteSum < 1) return;
  long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
  double eachVotePay = (double) totalPay / voteSum;
  for (WitnessCapsule w : witnessStandbys) {
    long pay = (long) (w.getVoteCount() * eachVotePay);
    payReward(w.getAddress().toByteArray(), pay);
  }
}
```

The division `totalPay / voteSum` is performed once, producing a fractional rate (`eachVotePay`) that inherently cannot represent the exact ratio in most cases (analogous to `unstakeRatio = amount / timeToExit` in the report). That imprecise rate is then multiplied by each witness's `voteCount` and truncated to a `long`, so:
1. Every standby witness receives strictly `<=` their exact proportional share, and the sum of all payouts is `<=` `totalPay`.
2. The shortfall is neither tracked nor returned anywhere — the truncated remainder for each of up to 127 witnesses, computed every time this runs (each maintenance/voting cycle), is simply discarded from the reward pool bookkeeping (unlike `WithdrawExpireUnfreezeActuator`-style flows where remainders are explicitly retained in state).

This mirrors the reported root cause exactly: a rate derived by dividing a total by a share-count (instead of deferring the division to the final multiply-then-divide step) causes systematic underpayment that compounds because it is executed repeatedly (each maintenance cycle here, each unstake call in the original report).

Compare this to the codebase's own fix pattern for VI-based delegation rewards, which explicitly guards against this same class of bug by scaling the rate up before dividing and dividing back down only once, using `BigInteger`: [2](#0-1) 

```java
public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
  ...
  BigInteger deltaVi = BigInteger.valueOf(reward)
      .multiply(DECIMAL_OF_VI_REWARD)
      .divide(BigInteger.valueOf(voteCount));
  setWitnessVi(cycle, address, preVi.add(deltaVi));
}
```

Here the numerator is scaled by `DECIMAL_OF_VI_REWARD` before dividing, and the resulting scaled value (`deltaVi`) is multiplied by the recipient's vote count and divided back down by the same scale only at the very end in `VoteRewardUtil.computeReward` / `MortgageService.computeReward`: [3](#0-2) 

This is exactly the "extend the accuracy by a scale factor, divide back at the end" fix recommended in the report — but it was applied only to the per-vote (VI-based) delegation-reward path, not to `payStandbyWitness`, which still performs the unscaled `double` divide-then-multiply.

### Impact Explanation
Every SR/standby-witness reward distribution silently loses a small amount of the `totalPay` pool to floating-point truncation. Because `payStandbyWitness()` runs every maintenance cycle (periodically, unconditionally, for up to 127 standby witnesses each time), the truncation errors compound over the life of the chain, exactly matching the reported impact language ("errors are accumulated to cause imbalance"). This is state/accounting-affecting logic — it directly determines how much TRX is credited to witness `allowance` balances (which back real, withdrawable balance) — and is not an admin-only/mocked code path; it fires automatically as part of normal chain operation, not requiring any special privilege to trigger.

### Likelihood Explanation
This code path executes automatically and unconditionally on every maintenance cycle handled by `Manager`/consensus flow whenever standby witnesses have votes (`voteSum >= 1`), which is the normal steady state of the network. No attacker action or special permission is required — it is a systemic accounting defect rather than an exploit requiring adversarial input, so likelihood of occurrence is effectively certain (it fires every cycle), though the per-cycle magnitude is small (bounded by `voteSum - 1` sun-equivalent units of drift in the worst case per witness, i.e. at most a few sun lost, but this recurs every maintenance cycle indefinitely).

### Recommendation
Apply the same fix pattern already used in `DelegationStore.accumulateWitnessVi` / `VoteRewardUtil.computeReward`: avoid computing an intermediate per-unit rate via `double` division. Instead compute each witness's payout directly as `pay = totalPay * voteCount / voteSum` using integer/`BigInteger` arithmetic (single truncation at the end, and only for each individual payee, rather than pre-truncating a shared rate), e.g.:

```java
BigInteger pay = BigInteger.valueOf(totalPay)
    .multiply(BigInteger.valueOf(w.getVoteCount()))
    .divide(BigInteger.valueOf(voteSum));
payReward(w.getAddress().toByteArray(), pay.longValueExact());
```

This removes the shared, pre-truncated `eachVotePay` rate and instead performs multiply-then-divide per recipient, matching the recommended fix pattern from the report (defer/right-size the division) and the fix already adopted elsewhere in the codebase for VI-based rewards.

### Proof of Concept
Given `witnessStandbys` with vote counts `[3, 3, 4]` and `totalPay = 10`:
- `voteSum = 10`
- `eachVotePay = 10.0 / 10 = 1.0` — in this trivial case there's no loss, but consider `totalPay = 10`, `voteSum = 3` (single witness with `voteCount = 3` among others):
  - `eachVotePay = 10.0 / 3 = 3.333333333333335`
  - For a witness with `voteCount = 1`: `pay = (long)(1 * 3.333333333333335) = 3` (should be `10*1/3 = 3` exact-ish, fine)
  - For a witness with `voteCount = 2`: `pay = (long)(2 * 3.333333333333335) = 6` while `10*2/3 = 6` (integer division would also give 6) — but note the intermediate `double` computation for large `totalPay`/`voteSum` values (e.g. `totalPay = 16_000_000`, `voteSum = 999_999_999`) accumulates rounding error across the 127 witnesses because `eachVotePay` is repeatedly multiplied by large `voteCount` values and each result independently truncated, rather than each witness's exact fractional share (`totalPay * voteCount / voteSum`) being computed with a single final truncation. Over many maintenance cycles (multiple per day, indefinitely), the aggregate shortfall against `totalPay` accumulates, analogous to the report's demonstrated `2080000` wei shortfall recurring "across users for all unstaking processes."
