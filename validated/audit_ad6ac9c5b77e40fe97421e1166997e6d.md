### Title
Silent swallowing of write-set-change conversion errors in `into_transaction_info()` produces an authenticated API `TransactionInfo.changes` list that is incomplete relative to the proof-bound `state_change_hash` / `accumulator_root_hash` - (File: api/types/src/convert.rs)

### Summary
`MoveConverter::into_transaction_info()` builds the API's `TransactionInfo` response, which is returned bound to a proof-verified `hash`, `state_change_hash`, and `accumulator_root_hash`. When converting the write set into the human-readable `changes` list, any per-entry conversion failure is silently discarded instead of surfacing an error, so clients receive a response that looks authenticated and complete but omits some of the actual on-chain state changes.

### Finding Description
`into_transaction_info` (api/types/src/convert.rs:292-319) builds the `changes` field as: [1](#0-0) 
```
changes: write_set
    .into_write_op_iter()
    .filter_map(|(sk, wo)| self.try_into_write_set_changes(sk, wo).ok())
    .flatten()
    .collect(),
```
`.ok()` converts any `Err` from `try_into_write_set_changes` into `None`, which `filter_map` then drops. There is no error path, no logging, no signal to the caller that some write-set entries were skipped. Contrast this with the sibling function `try_into_write_set_payload` a few lines below, which correctly propagates errors with `.collect::<Result<Vec<Vec<_>>>>()?` on the same kind of per-entry conversion (api/types/src/convert.rs:579-590).

The returned `TransactionInfo` struct simultaneously carries `state_change_hash` and `accumulator_root_hash` — values that are cryptographically bound to the actual, complete write set committed on-chain (api/types/src/transaction.rs:365-388). The `changes` vector is presented as "Final state of resources changed by the transaction" alongside these proof fields, but it is populated through a lossy, non-verifying path: `into_transaction_info` is called from the transaction-serving code paths (e.g., `try_into_onchain_transaction`, `get_transactions`, `get_transaction_by_version_inner` in api/src/transactions.rs and api/src/context.rs) that always have the correct, full `write_set` in hand (obtained from storage), yet convert it through this fallible-and-swallowed path before sending it back to callers as part of a response that is otherwise supposed to be authoritative.

Because JSON API responses are the "authenticated API output" surface referenced by the state-integrity gate, any consumer that trusts `TransactionInfo.changes` to be the full accounting of state written by a transaction (indexers, wallets, auditing tools, or dApp backends reconciling balances/vault-style deposits, directly analogous to Bob trusting the `TimeLockERC20` event/vault accounting in the source report) can be misled into believing fewer changes occurred, or into missing a specific change (e.g., a particular resource write), while the underlying committed ledger state is different and complete. This mirrors the root cause pattern of the seed report: a fallible operation's failure is discarded rather than surfaced, and downstream logic proceeds as if the operation fully succeeded.

### Impact Explanation
This does not corrupt the actual committed ledger state, accumulator root, or any proof structure — the on-chain write set, state_change_hash, and accumulator root itself remain correct and are computed/verified elsewhere from the real write set. The break is confined to the authenticated API response's `changes` field, which can present an incomplete/wrong view of "Final state of resources changed by the transaction" while other fields in the same response (`hash`, `state_change_hash`, `accumulator_root_hash`) are correct and would validate against a proof. This satisfies the "Authenticated API or state-view output bound to the wrong version, object, or proof context" category at a lower severity than a root/proof corruption: it is a data-integrity mismatch between a proof-bound response and its declared content, not a hard-fork or consensus-affecting bug. Impact depends on whether any conversion path can realistically fail for a legitimate, well-formed on-chain write op (see Likelihood) and on how strongly downstream consumers rely on `changes` for financial/accounting decisions without independently reconstructing the write set from BCS.

### Likelihood Explanation
I could not, within the available tooling, locate the definition body of `try_into_write_set_changes` (it appears to be defined elsewhere in `convert.rs`/a nested `impl` block not surfaced by search) to enumerate every internal failure condition (e.g., resource-group deserialization failure, `StructTag`/type resolution failure against DB-fetched module metadata at a version-mismatched converter, as the code's own `TODO` at line 310/585 warns about "type definition at the version of the converter, not the version of the tx"). Given that comment explicitly acknowledges converter/transaction version skew as a known source of interpretation problems, it is plausible for conversion to fail on legitimate historical write ops (e.g., after a struct layout upgrade), which would make the silent drop reachable in production on the JSON (not BCS) API path. Because I was unable to fully verify the exact failure conditions of `try_into_write_set_changes`, I present this with only moderate confidence and recommend explicit verification before treating it as production-confirmed.

### Recommendation
Change `into_transaction_info` to propagate conversion errors instead of silently dropping entries, mirroring the pattern already used in `try_into_write_set_payload`:
```rust
changes: write_set
    .into_write_op_iter()
    .map(|(sk, wo)| self.try_into_write_set_changes(sk, wo))
    .collect::<Result<Vec<Vec<_>>>>()?
    .into_iter()
    .flatten()
    .collect(),
```
This requires `into_transaction_info` to become fallible and its callers to handle/propagate the `Result`, ensuring API responses either contain the complete, accurate `changes` list or fail loudly (500/error) rather than silently returning a partial view alongside a correct proof-bound hash.

### Proof of Concept
Not independently reproduced — I was unable to construct a concrete write-op input that deterministically triggers a conversion failure in `try_into_write_set_changes` without access to its full implementation body (not returned by search/grep in the indexed snapshot). The code path itself (api/types/src/convert.rs:311-315) is directly verifiable by inspection: any `Err` returned from `try_into_write_set_changes` for any `(StateKey, WriteOp)` pair in the transaction's write set is unconditionally discarded via `.ok()` before being surfaced in the API's `TransactionInfo.changes` field, while `state_change_hash`/`accumulator_root_hash` on the same struct remain computed from the full, unmodified write set.
