### Title
Front-runnable shielded nullifier registration causes double-spend rejection / DoS of legitimate shielded transfers - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
`ShieldedTransferActuator.validate()` and `executeShielded()` reject/consume a shielded transaction based solely on whether its `SpendDescription.nullifier` is already present in `NullifierStore`, with no binding to who broadcast the transaction. Because a `SpendDescription` (zk-proof + `spendAuthoritySignature`) is self-contained and self-authorizing, anyone who observes a pending shielded transaction (e.g., in the p2p relay/mempool) can copy its `SpendDescription`/`ReceiveDescription` set into their own wrapping transaction and get it mined first, causing the nullifier to be written to `NullifierStore` before the original transaction is processed — the original then fails with "note has been spend in this transaction".

### Finding Description
Validation logic checks only the nullifier store state, not the origin of the request: [1](#0-0) 
And execution unconditionally marks the nullifier as spent for whichever transaction reaches the actuator first: [2](#0-1) 

This is structurally analogous to the reported `postDispatch` bug: a state-mutating function (`executeShielded`, gated only by `validate()`'s nullifier-presence check) accepts an externally-supplied identifier (`nullifier`, analogous to `messageId`) and marks it processed without verifying that the caller is the legitimate originator of that identifier. Since the `SpendDescription` fields (`zkproof`, `spendAuthoritySignature`, `nullifier`, `anchor`, `rk`, `valueCommitment`) are fully self-verifying and are not bound to the transparent transaction's owner/signer, any unprivileged party who can observe a pending transaction (via p2p broadcast/relay, e.g. `TransactionsMsgHandler.processMessage`) can extract that `SpendDescription` and resubmit it inside a new transaction of their own construction, exactly reproducing the original semantics but consuming the nullifier under a different, attacker-controlled transaction id. [3](#0-2) 

### Impact Explanation
Once the copied transaction lands first, `nullifierStore.has(...)` returns true for the original transaction, causing it to hard-fail validation with "note has been spend in this transaction": [4](#0-3) 
This is a denial-of-service against the legitimate sender's shielded transfer — funds already committed to `to_amount`/receive descriptions in the original transaction never settle under the sender's transaction, and the sender must reconstruct and rebroadcast a new shielded transaction (new proof generation), which is computationally expensive. It maps to the "message delivery DoS" impact category from the reference report: a legitimately-crafted state transition is pre-empted and permanently blocked by an unprivileged third party.

### Likelihood Explanation
Exploitation requires only the ability to observe a pending/broadcast shielded transaction (via the public p2p network before it's included in a block) and resubmit its `SpendDescription`/`ReceiveDescription` payload in an attacker's own transaction with sufficient fee/priority to be mined first — no special privilege, key material, or trusted role is required, since the shielded spend authorization is embedded in the description itself. This is a well-known class of front-running risk in nullifier-based shielded-pool designs (shared with Zcash-style protocols) rather than a novel implementation defect, which somewhat tempers likelihood/novelty, but the actuator code provides no additional binding (e.g., requiring the shielded proof to commit to the outer transaction's owner/signature) that would mitigate it.

### Recommendation
Bind the shielded spend authorization to the wrapping transaction so that copied `SpendDescription` data from an observed transaction cannot be replayed by a different submitter — e.g., include a commitment to the transaction's other fields (signer, transparent addresses, or transaction hash) inside the value being signed by `spendAuthoritySignature`/bound by the zk-proof's public inputs, so a third party cannot detach and resubmit a valid `SpendDescription` under a different transaction. Alternatively/additionally, consider mempool-level protections (e.g., first-seen propagation preference or private relay for shielded transactions) to reduce front-running windows.

### Proof of Concept
1. Attacker runs a modified full node or monitors the p2p network and intercepts `TransactionsMessage` broadcasts before block inclusion (`TransactionsMsgHandler.processMessage`).
2. Attacker extracts the `ShieldedTransferContract`'s `SpendDescription` (and `ReceiveDescription`) list from the observed pending transaction — these are self-verifying (`zkproof`, `spendAuthoritySignature`, `nullifier`, `anchor`, `rk`) and are not bound to the original sender's outer transaction fields.
3. Attacker constructs a new `Transaction` wrapping the identical `SpendDescription`/`ReceiveDescription` set (with attacker-chosen transparent to/from addresses if any), signs it as its own transaction, and broadcasts it with higher fee/priority.
4. If the attacker's transaction is processed first, `ShieldedTransferActuator.executeShielded` (`actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java:163-172`) writes the nullifier into `NullifierStore`.
5. When the original victim transaction is subsequently validated, `ShieldedTransferActuator.validate` (`actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java:241-243`) finds `nullifierStore.has(...) == true` and throws `ContractValidateException("note has been spend in this transaction")`, permanently rejecting the legitimate transaction.

Note: I was not able to fully trace whether an additional signature-binding check on the overall transaction's owner exists elsewhere in the transaction-processing pipeline (outside the actuator) that could bind the shielded proof to the broadcasting party; this would require reviewing `TransactionCapsule`/signature-validation code in more depth than the available index coverage allowed, and a Devin session with full repository access would be needed to conclusively rule this mitigation in or out.
