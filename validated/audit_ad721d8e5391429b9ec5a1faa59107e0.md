Based on my investigation, I found a genuine analog to the bug class: the webhook HMAC signature covers only the raw body, not the `X-Shopify-Shop-Domain` (or `X-Shopify-Event-Domain`) header used to select the tenant. This mirrors the root cause of the reference finding — a check performed against one identity (the data that is actually authenticated) is used to authorize/attribute an action to a *different*, unauthenticated identity (the shop domain claimed in a header).

### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant webhook/session confusion - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`validateHmacFromRequestFactory` verifies a webhook request solely by recomputing the HMAC over `rawBody` with the app's shared secret; it never binds the `X-Shopify-Shop-Domain` (or event `Domain`) header into that signature. `webhooks/validate.ts` and the `authenticate.ts` webhook handlers in `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` then trust that unauthenticated `domain` value to select which shop's offline session/access token to load and hand to the handler/`admin` client.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  only reads the HMAC header, verifies it against `rawBody`, and returns `valid: true` — it never inspects or authenticates `ShopifyHeader.Domain`/`ShopifyEventsHeader.Domain`. `checkWebhookHeaders` in `webhooks/validate.ts` then extracts `domain` straight from the (now "valid") headers alongside `topic` and `webhookId` and returns them as trusted `WebhookValidationValid` fields [2](#0-1) .

Downstream, `authenticateWebhookFactory` (shared logic across `shopify-app-remix`/`shopify-app-react-router`) passes this unauthenticated `check.domain` directly to `ensureValidOfflineSession`, which loads the real offline access token for that shop from the app's session storage and constructs a live `admin` client scoped to it [3](#0-2) . The same unauthenticated `shop_domain` is also passed straight into user-supplied `callback` handlers in `webhooks/process.ts` [4](#0-3) .

Because the shared secret is the app's single API secret (not per-shop), any party who has legitimately received one authentic webhook delivery (body + valid HMAC) — trivially true for any merchant/tenant with the app installed — possesses a body/HMAC pair that remains cryptographically valid no matter what shop domain is later claimed in the header. This is structurally identical to the reference bug: the state used to pass validation (`rawBody`+HMAC, analogous to `msg.sender`'s proposed-withdrawal info) belongs to one identity, but the code applies the result of that check to authorize/attribute an operation to a *different*, attacker-chosen identity (`owner`/target shop), because there is no explicit equality check binding the two.

### Impact Explanation
By replaying a captured valid webhook body+HMAC pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop that also has the app installed, an attacker can cause:
- The app to load and use the victim shop's real offline access token via `ensureValidOfflineSession`/`admin` client inside the webhook handler.
- Application-level webhook business logic (e.g., data sync, order/product mutations, GDPR handling) to execute as if triggered by the victim shop, using attacker-controlled body content.
This is a cross-tenant confusion / potential unauthorized-action vector, since the "check" (HMAC-of-body) doesn't attest to the tenant identity used for authorization.

### Likelihood Explanation
Requires the attacker to be an unprivileged but genuine tenant of the app (any merchant who installs the app can legitimately receive at least one real webhook delivery with body+HMAC), plus knowledge that the victim shop also has the app installed and is reachable via the same webhook endpoint (public apps in the Shopify App Store satisfy this trivially). No secret leakage or MITM is required — only reuse of a legitimately-received webhook payload with a forged header on a normal HTTP request to the app's own public webhook endpoint. This matches Shopify's own documented webhook verification method (HMAC is only ever computed over the body, per Shopify's official spec), so the weakness is inherent to the verification design as implemented, not a coding slip specific to a single call site — but the library exposes `domain` as a trusted field of `WebhookValidationValid` without any caveat or optional binding mechanism, which downstream consumers (`ensureValidOfflineSession`) then trust implicitly for session/tenant selection.

### Recommendation
- Do not treat `domain`/`shop_domain` extracted from webhook headers as an authenticated tenant identifier by itself. Where feasible, cross-check it against the shop associated with a currently valid stored offline session, or additionally verify shop identity via a Shopify-side lookup (e.g., re-validate via GraphQL admin API using the loaded token) before granting the `admin` client / running side-effecting business logic.
- Consider rate limiting / deduplication of webhook payloads by (topic, webhookId) idempotency key so identical body+HMAC replays cannot be reprocessed against a different claimed domain.
- Document explicitly for app developers that `domain` returned by `shopify.webhooks.validate`/`process` is not cryptographically bound to the HMAC and must not be trusted for security-sensitive branching without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver one real webhook (e.g., `APP_UNINSTALLED` or any subscribed topic) to the app's `/webhooks` endpoint. Attacker captures the exact `rawBody` and the `X-Shopify-Hmac-Sha256` header value from that delivery (they control the receiving server or can proxy/log it).
2. Attacker crafts a new HTTP POST to the same `/webhooks` endpoint, reusing the identical `rawBody` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop known to have the app installed) and any desired `X-Shopify-Topic`.
3. `validateHmacFromRequestFactory` recomputes HMAC over `rawBody` only [5](#0-4)  — validation succeeds because the secret and body are unchanged.
4. `checkWebhookHeaders` returns `domain: 'victim.myshopify.com'` as part of a `valid: true` result.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim.myshopify.com')`, loading the victim's real offline access token and exposing an authenticated `admin` client for `victim.myshopify.com` to the app's webhook handler code, driven entirely by attacker-supplied body content [6](#0-5) .

  return async function validateHmacFromRequest({
    type,

      : ShopifyHeader.Hmac;

      HashFormat.Base64,
    );

  };
