### Title
Missing chain/network identifier in NEP-366/NEP-611 meta-transaction (`DelegateAction`) signing payload enables cross-network signature replay - (File: core/primitives/src/signable_message.rs, core/primitives/src/action/delegate.rs)

### Summary
The reported DODO GSP issue is that `DOMAIN_SEPARATOR` binds a `permit()` signature to a `chainId` captured once at deployment, so if the chain later forks, the old chain's signature stays valid on the new chain and can be replayed. The analogous nearcore construct is the meta-transaction ("relayed transaction") signing scheme defined by NEP-461/NEP-366/NEP-611, implemented in `SignableMessage` and `DelegateAction`/`DelegateActionV2`. Just like the Solidity domain separator, this scheme is meant to scope a signature to a specific execution context, but it never includes any chain- or network-specific value (no `chain_id`, no genesis hash, no genesis config hash).

### Finding Description
`SignableMessage::sign`/`SignedDelegateAction::verify` hash exactly: a 4-byte NEP discriminant plus the borsh-serialized `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). [1](#0-0) [2](#0-1) 

`DelegateAction` itself carries no field identifying which NEAR network/chain the action is meant for: [3](#0-2) 

Unlike ordinary `SignedTransaction`s, which are bound to a specific chain state via a recent `block_hash` supplied at signing time (which differs per network), the delegate-action signature is only bound to `nonce` (the access-key nonce) and `max_block_height` (an absolute height, not a chain-specific hash). Because nearcore is deployed as the identical protocol binary across many independently operated networks (mainnet, testnet, and any number of privately operated forks/copies that share genesis state, e.g. mirrored/forked chains such as those built with `tools/mirror`), the same `(sender_id, public_key)` pair can exist with the same current nonce on two different networks. This is exactly the "hardcoded chainId / no dynamic chain binding" class of bug: the domain of the signed message never captures which chain it is valid for, so it is reachable by any relayer that receives a `SignedDelegateAction` from a user and later (or simultaneously) submits it as `Action::Delegate`/`Action::DelegateV2` on a different network sharing the same account/key state. [4](#0-3) [5](#0-4) 

The runtime-side validation (`runtime/runtime/src/actions.rs`) only checks the signature against the `DelegateAction` payload, matches `nonce` against the on-chain access key nonce, and checks `max_block_height` against the current block height — none of these checks are chain-specific, so a signature produced on one network verifies identically on any other network where the same account/access key/nonce state exists.

### Impact Explanation
If the same account id and access key (nonce state included) exist on two NEAR networks that a relayer interacts with (this is a realistic operational scenario for testnets that are periodically re-seeded from mainnet state, or private/enterprise forks that copy mainnet or testnet genesis/account state for testing), a `SignedDelegateAction` a user authorized for actions on Network A can be replayed verbatim as a valid, fully-verified delegate action on Network B, executing the exact same actions (transfers, function calls, key additions, etc.) on the user's behalf on the "wrong" network without any new authorization. This is unauthorized value movement / unauthorized action execution attributable purely to a missing chain-binding value in the signed payload, matching the "concrete unauthorized value movement" acceptance criterion.

### Likelihood Explanation
This requires an attacker/relayer to have access to a `SignedDelegateAction` and for the sender's account/access-key/nonce state to coincide across two networks running the same nearcore protocol — a condition that is realistic for testnet resets from mainnet snapshots or for teams that maintain forked/mirrored networks (nearcore ships `tools/mirror` specifically to replicate one chain's state/keys onto another, which is a first-party acknowledgment that account/key state duplication across networks is a supported nearcore workflow). The likelihood is not "high" in the sense of a trivial single-transaction exploit against mainnet alone, but it is a directly reachable, protocol-level design gap rather than a hypothetical.

### Recommendation
Include a network-specific, deterministic value in the `DelegateAction`/`SignableMessage` payload — e.g., the genesis hash or a `chain_id`-equivalent (NEAR networks already have a canonical `chain_id` string in genesis config) — so that the NEP-366/NEP-611 signing domain is bound to the specific network, mirroring how `SignedTransaction` binds to a recent `block_hash`. This should be versioned similarly to how `DelegateActionV2`/`VersionedDelegateActionPayload` were introduced, so old clients/relayers are not broken while new ones get chain-bound signatures.

### Proof of Concept
1. Two NEAR-protocol networks, N1 and N2, share identical account state for `alice.near` including access key `pk` with nonce `k` (e.g., N2 is a testnet reseeded from N1's mainnet snapshot, or a mirrored fork produced via `tools/mirror/src/genesis.rs`, which nearcore ships specifically to copy keys/accounts across networks). [6](#0-5) 
2. Alice signs a `DelegateAction { sender_id: alice.near, receiver_id: bob.near, actions: [Transfer], nonce: k+1, max_block_height: h+100, public_key: pk }` intending it to run only on N1, using `DelegateAction::get_nep461_hash()`/`SignedDelegateAction::sign`. [2](#0-1) 
3. A relayer wraps this `SignedDelegateAction` in an `Action::Delegate` inside an outer `SignedTransaction` and submits it to N1 — it executes as intended.
4. The same relayer (or any party who intercepts the `SignedDelegateAction`) wraps the identical, unmodified payload into an outer transaction addressed to N2 and submits it there. Because `SignedDelegateAction::verify()` only checks the ed25519 signature against the NEP-461-tagged `DelegateAction` bytes — which contain no chain identifier — and N2's copy of `alice.near`'s access key has the same nonce `k`, the signature verifies and the transfer/action executes on N2 as well, without Alice ever authorizing an action on N2. [4](#0-3)

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

impl DelegateAction {
    pub fn get_actions(&self) -> Vec<Action> {
        self.actions.iter().map(|a| a.clone().into()).collect()
    }

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
    }
}
