### Title
`action_delete_account` fails to purge parked `PromiseYield` state, allowing a stale yielded receipt to execute against a recreated account - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`action_delete_account` deletes an account via `remove_account`, which only clears the `Account`, `ContractCode`, access/gas keys, and `ContractData` trie entries. It never clears `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`, or the pending `PromiseYieldTimeout` queue entry associated with the deleted `account_id`. If the account is later recreated under the same `AccountId` (a supported, anticipated scenario in nearcore — access-key nonces are explicitly seeded to avoid tx-hash collisions "on re-creation"), the stale parked receipt from the old incarnation is still resolvable by a `PromiseResume` (either an attacker-submitted resume or the automatic timeout), causing the runtime to execute the *original* yielded `ActionReceipt` against the *new* account's state.

### Finding Description
`action_delete_account` computes storage/gas-key checks and then calls `remove_account`, clearing only a fixed set of trie keys: [1](#0-0) [2](#0-1) 

`remove_account` iterates and removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [3](#0-2) 

However, the trie schema explicitly lists `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` as account-scoped columns (i.e., keyed by `account_id`/`receiver_id`): [4](#0-3) 

None of these are removed when the account is deleted. `action_delete_account` performs no check for outstanding parked yields (`PromiseYieldReceipt`) before allowing deletion — it only checks storage-usage size and gas-key burn totals: [5](#0-4) 

A `PromiseYield` receipt is stored keyed by `(receiver_id, data_id)` and simply awaits a resume: [6](#0-5) 

When a matching `PromiseResume` later arrives (either from an explicit `yield_resume` call or from the automatic timeout path), the runtime looks the stale receipt up purely by `(account_id, data_id)`, with no validation that the account is still the same incarnation that created the yield, and executes it: [7](#0-6) 

The timeout path is equally unaware of account deletion/recreation: `resolve_promise_yield_timeouts` checks only whether the `PromiseYieldReceipt` key still exists in the trie, which it does (since it was never cleared), and unconditionally synthesizes a `PromiseResume` destined for `queue_entry.account_id`: [8](#0-7) 

### Impact Explanation
Because the parked yield/receipt data is never purged on `DeleteAccount`, the following sequence is possible with a single account deletion plus a normal recreation flow (e.g. a parent account deleting and recreating a sub-account, or any account-recreation pattern the protocol already anticipates via nonce seeding):

1. Account `A` (old incarnation) issues a `FunctionCall` that creates a `PromiseYield` receipt awaiting resume/timeout — this receipt contains arbitrary actions (e.g., `Transfer`, `FunctionCall` moving funds) with predecessor/receiver bound at creation time.
2. Account `A` is deleted via `DeleteAccountAction` (refunding balance to a beneficiary). All bookkeeping tied to the pending yield (`PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout` entry) survives untouched in the trie under the same account id.
3. Account `A` is recreated (same `AccountId`) and funded again.
4. When the timeout fires (or the original caller/attacker submits the matching resume), the stale `PromiseYieldReceipt` is found under `A`'s trie key and its captured actions are executed with the *new* account `A`'s live balance/state as receiver — an invalid state transition that the honest re-creator of the account never authorized, resulting in unauthorized value movement out of the recreated account or execution of stale/attacker-favorable logic against fresh account state.

This is reachable purely through the standard action set (`DeleteAccount`, `CreateAccount`, `FunctionCall` yield/resume) available to any transaction signer — no validator, network, or operator privilege is required.

### Likelihood Explanation
Account deletion and recreation under the same `AccountId` is an explicitly supported pattern in nearcore (the nonce-seeding comment in `access_keys.rs` exists specifically to avoid collisions "on re-creation"). Any contract using `yield_create`/`yield_resume` in combination with account deletion (a common pattern for sub-account lifecycle management, e.g. factories that delete and redeploy sub-accounts) can trigger this without any special privilege — it only requires ordinary transaction submission.

### Recommendation
When deleting an account, also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries scoped to that `account_id` (mirroring the existing iteration pattern already used for access keys/contract data in `remove_account`), and/or reject `DeleteAccount` while the account still has any outstanding parked `PromiseYield` receipts, analogous to the existing `DeleteAccountStaking` check for locked stake.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
