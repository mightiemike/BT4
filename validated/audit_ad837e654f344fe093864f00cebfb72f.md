Based on my research, I found a genuine local integrity gap that matches the requested bug class: a validation function that checks some but not all of the hash fields that bind execution output to committed `TransactionInfo`, with the gap explicitly acknowledged by the code authors as unfixed.

### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay/chunk-apply to accept a `TransactionOutput` whose state root diverges from the authenticated ledger - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk execution and replay-verification tooling to confirm that a locally-produced (or externally supplied) `TransactionOutput` matches the authenticated `TransactionInfo` proven in the ledger/accumulator. It validates status, gas used, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that bind the write set to the resulting Merkle/JMT state root.

### Finding Description [1](#0-0) 

The function checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`: [2](#0-1) 

but then contains an explicit acknowledgement that checkpoint hashes are skipped: [3](#0-2) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```

This function is called from at least four consumers I confirmed via search: `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are fields on `TransactionInfoV0`/`TransactionInfoV1` that are folded into the `TransactionInfo` hash stored in the transaction accumulator, per the builder definitions: [4](#0-3) 

This mirrors exactly the structure of the external report: a "deviation/consistency check" (here, `ensure_match_transaction_info`) validates a subset of the fields that another code path (state-root/accumulator computation, e.g. `DoStateCheckpoint::run` and `compute_position_checkpoint` in `execution/executor/src/workflow/do_state_checkpoint.rs`) actually commits and hashes into the ledger. Because the checkpoint hashes are excluded from the comparator, a chunk-execution or replay-verify consumer can accept a `TransactionOutput` (and therefore treat local state as verified/consistent) even though its resulting state root/position state root differs from the one embedded in the authenticated `TransactionInfo`/accumulator proof.

### Impact Explanation
If chunk-apply (state sync) or replay-verify tooling relies on `ensure_match_transaction_info` as its correctness gate without independently re-deriving and comparing checkpoint hashes elsewhere, a node could commit/accept a durable state tree whose root diverges from the one the network agreed on via consensus/accumulator, while reporting success. This is a "committed state differs from correct VM result" / "hard-fork-only divergence during commit, replay, restore" class issue, which the task explicitly calls high/critical impact when proven.

### Likelihood Explanation
This is **not confirmed to be currently exploitable on mainnet** — I could not fully verify (within available tool calls) that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / the "trading-native" position-state-root feature is already active in the mainnet code path, and I was unable to read the full body of `execution/executor/src/chunk_executor/mod.rs` to see whether it independently re-validates `state_checkpoint_hash`/`hot_state_checkpoint_hash` through a separate mechanism (e.g., accumulator inclusion proof checked afterward) that would compensate for this comparator's gap. The comment itself frames this as a pre-existing, developer-acknowledged gap to be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," suggesting the position-state-root feature is not yet fully enabled, which would limit current impact to that specific rollout path and to db-tool/debugger replay-verification confidence (which could give false assurance of correctness rather than corrupt already-committed mainnet state).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against locally recomputed values before returning `Ok(())`, consistent with how `state_change_hash` and `event_root_hash` are already validated, and gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this fix as the comment itself specifies.

### Proof of Concept
Not independently constructed — this finding is based on static analysis of the comparator logic and its explicit self-documented gap; I did not have access to a runnable environment to demonstrate an actual accepted-but-divergent replay in this session.

**Confidence caveat:** Because I could not read the contents of `execution/executor/src/chunk_executor/mod.rs` (tool returned empty content) to confirm whether this gap is compensated elsewhere, and could not confirm the current mainnet activation state of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, I cannot assert this as a fully proven, currently-exploitable mainnet vulnerability with certainty — only that the code contains a self-acknowledged, unresolved integrity-check gap matching the requested bug class.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
