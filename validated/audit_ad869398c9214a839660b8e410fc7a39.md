### Title
Attacker-controlled `RevertInstructions.FundRecipient` can permanently strand bridged funds by forcing `handleFailedOutbound` into `AbortOutbound` - (File: x/uexecutor/keeper/outbound.go)

### Summary
The external report describes `Wallet.refund` in fs_core: a fund-crediting path that trusts an unvalidated `_tokenAddress`/decimals assumption, so a caller can cause tokens to become permanently stuck in the contract, fixable only by an upgrade. The Push Chain analog is the revert/refund path for a failed outbound: `FundRecipient` is a user-supplied, only leniently-canonicalized string that is later blindly converted with `common.HexToAddress` and used as the mint target for `CallPRC20Deposit`. If that deposit call reverts (e.g. because `recipient` doesn't correspond to any of the intended values, or because of a downstream contract-level revert), the outbound keeper does not retry cleanly to the safe fallback (the sender) — it calls `AbortOutbound`, which permanently marks the outbound `ABORTED` and requires "manual intervention," i.e. an operator/upgrade-level action to recover the funds.

### Finding Description
`Inbound.RevertInstructions.FundRecipient` is set by the source-chain event/user and is only lightly canonicalized via `utils.LenientCanonicalizeAddress` in `Canonicalize()` [1](#0-0) . Unlike `Recipient` for `FUNDS`/`GAS` inbound types, there is no `ValidateForExecution` check that `FundRecipient` is a well-formed address [2](#0-1) .

When an outbound created from that inbound is later observed as failed, `handleFailedOutbound` selects `outbound.RevertInstructions.FundRecipient` (falling back to `Sender` only if empty) and calls `common.HexToAddress(recipient)` directly, with no validity check, before minting PRC20 back via `CallPRC20Deposit`: [3](#0-2) 

If that mint call errors (e.g. downstream target reverts, is a non-existent/blacklisted contract-style address, or any other on-chain revert condition reachable through an attacker-chosen `FundRecipient`), the keeper does not fall back to a known-safe recipient (like the original `Sender`) — it immediately aborts the outbound for manual intervention: [4](#0-3) 

`AbortOutbound` sets `Status_ABORTED` and only emits an event; there is no further automated recovery path in this code: [5](#0-4) 

This mirrors the `Wallet.refund` bug-class exactly: a user-controlled parameter (there, the token/decimals; here, the revert-fund recipient) is trusted without adequate validation in a fund-return path, and a failure mode leaves bridged value stuck in module-controlled state, recoverable only through privileged/manual (effectively "upgrade-like") remediation rather than automatically returning funds to the honest original sender.

### Impact Explanation
An unprivileged inbound submitter (or the event data they control on the source chain) sets an adversarial `RevertInstructions.FundRecipient`. If the corresponding outbound is later voted as failed by honest validators, the automatic re-mint to that attacker-chosen recipient can fail, and instead of falling back to the safe `Sender` address, the entire outbound (and the bridged funds it represents) is marked `ABORTED`, permanently freezing user/protocol funds pending manual/administrative recovery. This is a "permanent freezing of user or protocol-controlled funds" impact, matching the Allowed Impact Gate.

### Likelihood Explanation
This requires: (1) an inbound with `RevertInstructions.FundRecipient` set to a value that later causes `CallPRC20Deposit` to revert, and (2) honest validators subsequently voting the corresponding outbound as failed via `MsgVoteOutbound`. Both are reachable through the default, unprivileged inbound-submission and honest-validator voting flow described in the module's own lifecycle documentation, without requiring any privileged actor. The main uncertainty (not fully verified from the available code) is exactly which recipient values reliably make `CallPRC20Deposit`/`depositPRC20Token` revert on the `UniversalCore`/PRC20 contract side — that logic lives in the external Solidity contracts, which the index does not contain, so the precise revert trigger could not be confirmed here.

### Recommendation
- Validate `RevertInstructions.FundRecipient` as a well-formed EVM hex address during `ValidateForExecution` (as is already done for `Recipient` on `FUNDS`/`GAS` types), rejecting malformed values before they can ever be used in a revert/refund path.
- In `handleFailedOutbound`, if the re-mint to `FundRecipient` fails, retry with a known-safe fallback recipient (`outbound.Sender`) before resorting to `AbortOutbound`, so a bad `FundRecipient` cannot strand funds that could otherwise be safely returned.
- Consider adding an automated/permissionless "rescue" retry path analogous to `RESCUE_FUNDS`/`AttachRescueOutboundFromReceipt` specifically for `ABORTED` outbounds caused by revert-recipient failures, rather than requiring ad hoc manual intervention.

### Proof of Concept
Conceptual sequence (full contract-level revert trigger not verified due to indexing limits on the Solidity `UniversalCore`/PRC20 contracts):
1. Attacker submits/observes a source-chain event producing an `Inbound` with `TxType=FUNDS` (or `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD`) and `RevertInstructions.FundRecipient` set to a value chosen to make `depositPRC20Token` revert on-chain (e.g., an address that is a non-UEA, non-EOA contract with logic that reverts on receiving the PRC20 mint, or another value outside the set the contract accepts).
2. Honest validators vote the inbound in; an `OutboundTx` is created carrying that `RevertInstructions`.
3. The destination-chain leg fails; honest validators submit `MsgVoteOutbound` with `success=false`.
4. `FinalizeOutbound` → `handleFailedOutbound` attempts `CallPRC20Deposit(prc20, HexToAddress(FundRecipient), amount)` [6](#0-5) ; the call errors.
5. `AbortOutbound` is invoked, setting `Status_ABORTED` permanently [7](#0-6)  — the bridged funds are now stuck pending manual intervention, with no automatic fallback to the honest `Sender`.

// ValidateForExecution checks fields that are required for actual execution of the inbound.
// Called after ballot finalization, before ExecuteInbound. Failures here produce a failed
// PCTx and (for non-isCEA) a revert outbound, rather than dropping the vote.
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}
