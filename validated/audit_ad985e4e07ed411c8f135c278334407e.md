### Title
`__execute__` direct-call protection (`block_direct_execute_call`) is enforced only in `call_contract`, not in `library_call` - (File: `crates/blockifier/src/execution/syscalls/syscall_base.rs`)

### Summary
The Node.js report shows that `process.mainModule.require()` is guarded by the permission system, but the semantically equivalent `process.mainModule.__proto__.require()` reaches the same privileged function through an unchecked alternate reference and bypasses the check entirely. The sequencer contains a structurally identical pattern: the `EXECUTE_ENTRY_POINT_NAME` ("`__execute__`") direct-invocation guard, `maybe_block_direct_execute_call`, is called from the `call_contract` syscall implementation in every syscall handler variant, but the parallel `library_call` syscall — which reaches the exact same entry-point dispatch/execution machinery — never calls this guard.

### Finding Description
`maybe_block_direct_execute_call` is defined once in `SyscallHandlerBase` and is meant to stop any contract from directly invoking another (or its own) account's `__execute__` entry point via a syscall, when `versioned_constants.block_direct_execute_call` is enabled: [1](#0-0) 

This guard is explicitly invoked inside `call_contract` in the standard VM syscall hint processor: [2](#0-1) 

and in the Cairo-Native syscall handler's `call_contract`: [3](#0-2) 

and the deprecated (Cairo0) `call_contract` implementation performs the identical check inline: [4](#0-3) 

The Starknet OS (Cairo) re-execution path mirrors this: the OS's `CALL_CONTRACT_SELECTOR` handler for deprecated (Cairo0) contracts explicitly asserts the callee selector is not `EXECUTE_ENTRY_POINT_SELECTOR`: [5](#0-4) 
and the Cairo1 OS `call_contract` syscall implementation also rejects the `EXECUTE_ENTRY_POINT_SELECTOR` before dispatch: [6](#0-5) 

However, the `library_call` syscall — which builds an equivalent `CallEntryPoint`/execution context targeting an arbitrary `class_hash` and arbitrary `entry_point_selector` (including `__execute__`) — has no such check anywhere in the codebase:
- Native handler `library_call`: no call to `maybe_block_direct_execute_call` or any selector check. [7](#0-6) 
- Standard VM syscall hint processor `library_call`: same, no selector restriction. [8](#0-7) 
- Deprecated (Cairo0) `execute_library_call`: same, no restriction. [9](#0-8) 
- The Starknet OS Cairo implementations of `LIBRARY_CALL_SELECTOR` (both `execute_library_call` in `syscall_impls.cairo` and `execute_library_call_syscall` in `deprecated_execute_syscalls.cairo`) build the execution context and dispatch it with no comparison of `call_req.function_selector`/`request.selector` against `EXECUTE_ENTRY_POINT_SELECTOR`, unlike the `CALL_CONTRACT_SELECTOR` branches immediately preceding them in the same dispatch functions. [10](#0-9) [11](#0-10) 

This is exactly analogous to the HackerOne report: `call_contract` (`process.mainModule.require()`) is the "checked" front door, while `library_call` (`process.mainModule.__proto__.require()`) is an unchecked side door reaching functionally equivalent dispatch logic (the entry-point-type/selector search and Cairo-jump into `__execute__`'s compiled code, `contract_call_helper`/`execute_inner_call`) for the very same entry point that the protocol explicitly protects.

### Impact Explanation
`block_direct_execute_call` exists to guarantee that `__execute__` is invoked only through the canonical top-level transaction flow (`run_execute` in `transactions.rs`, with `caller_address == 0`), not via an arbitrary contract-to-contract syscall. Account contracts (as documented/tested in the feature contracts, e.g. `account_with_dummy_validate.cairo`'s `assert(starknet::get_caller_address().is_zero(), 'INVALID_CALLER')`) rely on this invariant to prevent re-entrant/impersonated invocation of `__execute__` outside the sequencer-orchestrated validate→execute pipeline (fee accounting, nonce bump, and validate/execute ordering are all tied to the outer transaction, not to an inner syscall call). Any code path that lets a contract invoke `__execute__` (or dispatch to a class whose `__execute__` was compiled for the "trusted" flow) while sidestepping this restriction breaks that invariant — an attacker-deployed contract, or any transaction, could target `__execute__`-shaped entry points on classes reachable via `library_call`, causing state transitions the OS/blockifier developers explicitly intended to forbid at the protocol level. Since `library_call` executes borrowed code with delegated storage context (`call_type: Delegate`, `storage_address`/`caller_address` unchanged from the caller), the bypass reaches the guarded dispatch surface with a different combination of call semantics than `call_contract`, but it is nonetheless the same forbidden selector reaching the same execution machinery that the check is designed to block universally per `versioned_constants.block_direct_execute_call`. Because the restriction is a protocol-level invariant enforced identically by the Starknet OS during re-execution (both `call_contract` OS syscall handlers explicitly reject `EXECUTE_ENTRY_POINT_SELECTOR`), the missing symmetrical check in `library_call` (both in blockifier and the OS Cairo code) is a genuine gap in the "no direct calls to `__execute__`" guarantee, reachable by any submitted transaction that triggers a contract to issue a `library_call` with `function_selector = selector_from_name("__execute__")`.

### Likelihood Explanation
This is trivially reachable: any account or contract execution path that issues a `library_call` syscall with an attacker-chosen `class_hash` and `function_selector` (fully attacker-controlled calldata inputs to the syscall, as shown by `library_call_syscall` usage in feature contracts) can set `function_selector` to `selector_from_name("__execute__")` without any additional privilege. No special conditions, timing, or governance access are required — a single ordinary invoke transaction calling a contract that performs a `library_call` is sufficient to trigger the unguarded path in both the blockifier execution and the Starknet OS re-execution.

### Recommendation
Add the same `EXECUTE_ENTRY_POINT_NAME`/`maybe_block_direct_execute_call` check to all `library_call` implementations, mirroring the `call_contract` guard:
- `crates/blockifier/src/execution/syscalls/hint_processor.rs::library_call` (standard VM handler)
- `crates/blockifier/src/execution/native/syscall_handler.rs::library_call` (Cairo-Native handler)
- `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs::execute_library_call` (Cairo0 handler)
- The Starknet OS Cairo implementations `execute_library_call` (`syscall_impls.cairo`) and `execute_library_call_syscall` (`deprecated_execute_syscalls.cairo`), adding an `assert_not_equal`/selector-rejection check symmetric to the existing `CALL_CONTRACT_SELECTOR` branches.

Since this affects consensus-critical execution (blockifier vs. OS agreement) and requires a versioned-constants flag change, it should go through a coordinated protocol version bump so that both blockifier and the Starknet OS enforce the restriction identically to avoid a divergence between sequencer execution and OS re-execution.

### Proof of Concept
I was not able to fully trace end-to-end whether an unrestricted `library_call` to `__execute__` produces a concrete state-changing/loss-of-funds outcome versus merely re-executing code in the caller's own storage context (since `library_call` uses `CallType::Delegate` with `storage_address`/`caller_address` unchanged from the caller, rather than the target's own storage as `call_contract` would use). This distinction is material to the actual severity and I could not confirm from the indexed code alone whether any account/class in the codebase (or a maliciously crafted class) can leverage a delegated `__execute__` invocation to achieve unauthorized state changes equivalent to the `call_contract` bypass that `block_direct_execute_call` was introduced to prevent. Confirming full exploitability (e.g., constructing a contract that `library_call`s a victim account class's `__execute__` and demonstrating unauthorized action) would require running the blockifier/OS test harness (e.g., extending `crates/blockifier/src/execution/syscalls/syscall_tests/call_contract.rs::test_direct_execute_call` with a `library_call`-based variant) to observe actual execution behavior, which is beyond what can be verified through static code search alone.

    pub(crate) fn maybe_block_direct_execute_call(
        &mut self,
        selector: EntryPointSelector,
    ) -> SyscallResult<()> {
        let versioned_constants = &self.context.tx_context.block_context.versioned_constants;
        if versioned_constants.block_direct_execute_call
            && selector == selector_from_name(EXECUTE_ENTRY_POINT_NAME)

        }
        Ok(())

pub fn execute_library_call(
    syscall_handler: &mut DeprecatedSyscallHintProcessor<'_>,

        if call_to_external { EntryPointType::External } else { EntryPointType::L1Handler };

        caller_address: syscall_handler.caller_address,

    };

    execute_inner_call(entry_point, vm, syscall_handler).map_err(|error| {
        error.as_lib_call_execution_error(
            class_hash,
            syscall_handler.storage_address,
            entry_point_selector,
        )
    })
}

        remaining_gas=remaining_gas,
