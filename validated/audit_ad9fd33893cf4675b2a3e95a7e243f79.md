**Reasoning:**

The `RandomnessConfig` resource follows the exact same generic path as every other Move resource for executor-to-storage handoff, storage encoding, and proof binding — there is no special-cased serialization/deserialization logic for this resource that could introduce a truncation bug.

- `current()` in `randomness_config.move` reads via ordinary `borrow_global<RandomnessConfig>`/`copyable_any` unpack logic, with no bespoke truncation path [1](#0-0) .
- The `variant: Any` field is a `copyable_any::Any` wrapping BCS bytes, packed/unpacked generically the same way any other config's `Any` field would be [2](#0-1) .
- On the executor side, resource values are serialized into bytes via the standard `ValueSerDeContext` serialization in `session/mod.rs`'s `finish()`, which applies uniformly across all resource types, not just `RandomnessConfig` — there's no per-resource truncation logic [3](#0-2) .
- Storage-side write-set persistence uses the generic `WriteOp`/`StateValue` byte-preserving encode/decode path with no special-casing by resource type [4](#0-3) , and `WriteOp::bytes()` is a straight pass-through of the stored bytes [5](#0-4) .
- The `RandomnessConfigMoveStruct` (`types/src/on_chain_config/randomness_config.rs`) that off-chain/API code uses to interpret the resource is a lossless, round-trippable wrapper over the same `Any`/BCS bytes with `TryFrom`/`From` conversions that do not manipulate length or truncate data [6](#0-5) .

The question's premise — that `variant.data` could be "truncated during executor-to-storage handoff" — has no supporting code path. All resource state values, including `RandomnessConfig`, pass through the same generic, resource-type-agnostic BCS serialize/deserialize and write-op/state-value plumbing that is shared and heavily used across the entire framework; a truncation bug specific to this resource would require a distinct, unproven code path that does not exist in this codebase. Additionally, this scenario does not originate from unprivileged transaction/API/bytecode input corrupting committed state — it hypothesizes an internal handoff bug without identifying an actual wrong write set, proof node, root, or version, as required by the Review Path.

        // TODO(HotState): we could simply use `bcs::from_bytes` for everything once the latest

                    Ok(ws)
                },
                Err(e) => Err(e.into()),
            },

    type Error = anyhow::Error;

    fn try_from(value: RandomnessConfigMoveStruct) -> Result<Self, Self::Error> {
        let RandomnessConfigMoveStruct { variant } = value;
        let variant_type_name = variant.type_name.as_str();
        match variant_type_name {
            ConfigOff::MOVE_TYPE_NAME => Ok(Self::Off),
            ConfigV1::MOVE_TYPE_NAME => {
                let v1 = MoveAny::unpack(ConfigV1::MOVE_TYPE_NAME, variant)
                    .map_err(|e| anyhow!("unpack as v1 failed: {e}"))?;
                Ok(Self::V1(v1))
            },
            ConfigV2::MOVE_TYPE_NAME => {
                let v2 = MoveAny::unpack(ConfigV2::MOVE_TYPE_NAME, variant)
                    .map_err(|e| anyhow!("unpack as v2 failed: {e}"))?;
                Ok(Self::V2(v2))
            },
            _ => Err(anyhow!("unknown variant type")),
        }
    }
}
