### Title
`ValidateMultiSign.execute` double-counts weight for a single key via malleable-signature bypass of its byte-exact duplicate check, diverging from `TransactionCapsule.checkWeight`'s address-based duplicate rejection - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.ValidateMultiSign.execute` deduplicates signatures using `ByteArray.matrixContains` on the raw concatenated `(address || sign)` bytes, only skipping a signature if the *exact same signature bytes* for an already-seen address are repeated. `TransactionCapsule.checkWeight` instead deduplicates strictly by the *recovered address* (via `addMap.containsKey(base64/encode58Check(address))`) and throws `PermissionException` on any second occurrence of the same signer address, regardless of signature bytes. Because ECDSA signatures are malleable (two different valid `(r,s,v)` byte sequences can recover to the same address for the same hash), an attacker controlling one private key can submit two distinct signatures from that single key, both of which recover to the same address; `validateMultiSign` will count that key's weight twice while `checkWeight` would reject the transaction outright as "signed twice."

### Finding Description
In `ValidateMultiSign.execute`: [1](#0-0) 
the loop recovers the address for each signature (`recoverAddrBySign`), then checks `matrixContains(executedSignList, recoveredAddr)` — if the address was seen before, it only `continue`s (skips adding weight) when `matrixContains(executedSignList, sign)` (the exact merged `address||signature` byte blob) is also already present. If the address repeats but the signature bytes differ (e.g. a malleable variant of the same key's signature over the same hash), the code falls through, calls `MUtil.checkCPUTime()` (not a rejection, just a compute-time guard), and then unconditionally adds the key's `weight` to `totalWeight` again via `TransactionCapsule.getWeight(permission, recoveredAddr)` at line 1098, appending both entries to `executedSignList`.

In contrast, `TransactionCapsule.checkWeight` (used for real on-chain transaction/multi-sig authorization, e.g. `validateSignature`/`addSign`) tracks seen addresses in `addMap` keyed by the recovered address (post fork `VERSION_4_7_1`, keyed by `encode58Check(address)`), and throws `PermissionException("... has signed twice!")` the moment the *same address* appears twice, independent of whether the underlying signature bytes differ: [2](#0-1) 

This is a genuine logic divergence between the two "same class of signature/weight validation" code paths reachable by an unprivileged actor: any account or contract can call the `validatemultisign` precompile (address `0x...a`) with attacker-supplied `(address, permissionId, hash, signatures[])` ABI-encoded input, as exercised by `ValidateMultiSignContractTest` and `OperationsTest`: [3](#0-2) 
The test at line 119-121 even demonstrates a "repetitive" signature case, but it uses *identical* signature bytes (`key1.sign(toSign)` called once and reused is not what's shown — it calls `key1.sign()` twice, producing two potentially different signature encodings for the same key, and the test still asserts success), which is consistent with the double-count/duplicate-tolerant behavior being present and accepted rather than rejected, unlike what `checkWeight` would do for a genuine second signing by the same key.

### Impact Explanation
A smart contract that uses `validatemultisign` (address `0xa` precompile) to gate privileged on-chain logic (e.g., releasing funds, authorizing an action) based on an account's Active/Permission weight/threshold can be tricked into believing a multi-sig threshold was met when, in TRON's canonical transaction-authorization semantics (`checkWeight`), the equivalent signature set would be rejected as a duplicate signer and never reach threshold. This lets an attacker holding only `M` distinct private keys satisfy a threshold that nominally requires more distinct weighted signers, because a single key's weight can be counted multiple times by supplying multiple malleable-but-valid signature encodings of that key over the same hash. This is a cross-path authorization-decision divergence affecting any contract that trusts `validatemultisign`'s boolean result as equivalent to genuine on-chain multi-sig authorization.

### Likelihood Explanation
Preconditions: attacker needs (1) a target account/permission with a known `permissionId` and known member keys/weights (all public on-chain state), and (2) the ability to produce, for at least one key they control, two distinct valid `(r,s,v)` byte encodings that both recover to the same address for the same `hash` (standard ECDSA signature malleability — flipping `s -> n-s` with the corresponding `v` flip, unless `validateComponents()`'s low-S enforcement blocks the negated-s variant, which could reduce but not necessarily eliminate the class of producible malleable variants depending on implementation). The call itself only requires public access to the precompile from any transaction/contract — no privileged network or state access is needed. This is triggerable by any unprivileged actor issuing a `TriggerSmartContract` call.

### Recommendation
Change `ValidateMultiSign.execute`'s duplicate-detection to match `checkWeight`'s semantics: dedupe strictly by `recoveredAddr` (skip/reject on any repeat of the same address), not by exact signature bytes, so both code paths converge on the same authorization decision for identical `(permission, signatures, hash)` inputs.

### Proof of Concept
```java
// Differential test: same (permission, hash, two sigs from ONE key) fed to both paths.
@Test
public void testValidateMultiSignVsCheckWeightDivergence() throws Exception {
    ECKey key1 = new ECKey();
    // Build permission with key1 weight=1, threshold=2 (so a single key must NOT pass alone)
    Protocol.Permission permission = Protocol.Permission.newBuilder()
        .setType(Protocol.Permission.PermissionType.Active)
        .setThreshold(2)
        .addKeys(Protocol.Key.newBuilder()
            .setAddress(ByteString.copyFrom(key1.getAddress())).setWeight(1).build())
        .build();

    byte[] hash = Sha256Hash.hash(true, "test".getBytes());

    // Produce two distinct-byte signatures from key1 over the same hash
    // (e.g. via malleability: (r, s, v) and (r, n-s, v') both recovering to key1's address)
    byte[] sigA = key1.sign(hash).toByteArray();
    byte[] sigB = maleate(sigA); // flip s -> n - s and adjust recovery id

    // checkWeight: must reject as "has signed twice"
    List<ByteString> sigs = Arrays.asList(ByteString.copyFrom(sigA), ByteString.copyFrom(sigB));
    assertThrows(PermissionException.class,
        () -> TransactionCapsule.checkWeight(permission, sigs, hash, null));

    // ValidateMultiSign precompile: build equivalent calldata and expect it to ALSO fail (weight < threshold)
    Pair<Boolean, byte[]> result = validateMultiSignPrecompile(account, permissionId, hash,
        Arrays.asList(sigA, sigB));
    // BUG: currently totalWeight becomes 1+1=2 >= threshold(2) -> returns true (DataOne)
    // Correct behavior (post-fix) should return DATA_FALSE, matching checkWeight's rejection.
    Assert.assertArrayEquals(DataWord.ZERO().getData(), result.getValue());
}
```
Expected assertion (currently failing): `ValidateMultiSign.execute` returns `DataWord.ONE()` while `TransactionCapsule.checkWeight` throws `PermissionException`, proving the divergence.
