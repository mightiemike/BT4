## Analog Found: Unbounded Recursion in Compiled-Class-Hash Computation

CVE-2017-9209 is a stack-exhaustion DoS caused by unbounded recursive parsing of an attacker-crafted, deeply-nested structure (`QPDFObjectHandle::parseInternal`). The sequencer has a directly analogous unguarded recursive function that walks an attacker-influenced nested structure during compiled-class-hash computation, a step every node performs while processing declare transactions and while re-executing blocks.

### Title
Unbounded recursion in `bytecode_hash_node` over attacker-influenced `NestedIntList` segment structure can exhaust the stack during compiled-class hashing - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
`bytecode_hash_node` recursively walks a `HashableNestedIntList` (`NestedIntList`) tree that describes how a CASM contract's bytecode is segmented for hashing, with no depth bound and no iterative fallback. [1](#0-0) 
This tree's shape is derived by the Sierra→CASM compiler from the submitted Sierra program's control-flow structure, so its nesting depth is influenced by the class a user declares, not by a fixed, sequencer-chosen bound.

### Finding Description
The hashing routine has no explicit depth limit: [2](#0-1) 
It is reached from `HashableCompiledClass::hash`, which every consumer of a compiled class calls to obtain the compiled_class_hash: [3](#0-2) 

Critically, unlike the actual Sierra→CASM *compilation* step (which the sequencer intentionally runs in a resource-limited, CPU/memory-bounded subprocess so a crash there is contained): [4](#0-3) 
the class-hash computation over the resulting `bytecode_segment_lengths` happens **in-process**, immediately after that sandboxed compilation, inside the `SierraCompiler` component itself: [5](#0-4) 
A comment elsewhere in the codebase confirms process isolation is only applied to compilation, not to downstream in-process operations on the compiler's output: "unlike the sequencer gateway (which compiles user-submitted classes in a resource-limited subprocess), no process isolation is needed" for post-compilation steps. [6](#0-5) 

The same unguarded hashing is also invoked in-process on every block builder/full node when re-verifying a declare transaction's stated `compiled_class_hash`: [7](#0-6) 
and via the general state-reader utility used during execution: [8](#0-7) 

Notably, the codebase's own gas-estimation code for the same structure explicitly asserts it only handles one level of nesting and panics otherwise ("Only supported for segmentation depth at most 1."), an implicit admission that deeper segmentation structures than one level can arise from real compiled classes: [9](#0-8) 
This is in sharp contrast to how the codebase treats other recursive, attacker-reachable paths — e.g., contract-call recursion is explicitly bounded with a `RecursionDepthGuard` and gas gates it before it can approach stack limits: [10](#0-9) 
and native execution threads pre-allocate a bounded stack specifically to make deep recursion hit an "Out of gas" condition before overflowing the real stack: [11](#0-10) 
No equivalent guard (depth counter, iterative rewrite, or gas-metered recursion) exists for `bytecode_hash_node`.

### Impact Explanation
A Rust stack overflow from unbounded recursion is not a catchable panic — it aborts the whole process. If a declared class produces (or is fabricated to produce, in code paths that deserialize `CasmContractClass` directly, e.g. `native_blockifier/src/storage.rs`) a `bytecode_segment_lengths` tree deep enough to exhaust the thread's stack, then every gateway/sequencer instance and every full node that computes or re-verifies the compiled_class_hash for that class during declare admission, block building, or re-execution would crash. Because this affects every honest node identically, it functions as a network-wide denial of service ("a network unable to confirm new transactions") rather than merely revert-and-move-on transaction failure. [1](#0-0) 

### Likelihood Explanation
Reachable from a single, unprivileged declare transaction; a declarer only needs a Sierra program whose compiler-derived bytecode segmentation is deep. Sierra-to-CASM compilation itself is sandboxed with CPU/memory limits, but the subsequent hash computation on the compiler's own output is not, so the sandbox does not protect this step: [12](#0-11) 
The bytecode size is bounded (`max_bytecode_size`, default ~80K felts), but the segmentation tree's *depth* (as opposed to total size) is not independently bounded anywhere in the reviewed code, and the gas-estimation code's own assertion suggests depths beyond a single level are a real possibility for compiler output.

### Recommendation
Rewrite `bytecode_hash_node` (and `HashableNestedIntList` consumers generally) as an explicit iterative traversal with a worklist/stack on the heap instead of native call-stack recursion, or impose and enforce a hard maximum nesting depth for `bytecode_segment_lengths` at compilation/validation time, rejecting classes that exceed it before any unguarded recursive hashing runs.

### Proof of Concept
Construct (or directly compile) a `CasmContractClass` whose `bytecode_segment_lengths` is a `NestedIntList::Node` chain nested to a depth on the order of the thread's stack-frame capacity (e.g., tens of thousands of levels), then call `.hash(&HashVersion::V1/V2)` on it — reachable in-process via declaring such a class (`SierraCompiler::compile` → `hash`) or via any code path that deserializes an untrusted `CasmContractClass` and calls `.hash(...)`, e.g. `crates/native_blockifier/src/storage.rs:199-200`. [13](#0-12)

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}

    pub fn execute_txs_sequentially(
        &mut self,
        txs: &[Transaction],
        execution_deadline: Option<Instant>,
    ) -> Vec<TransactionExecutorResult<TransactionExecutionOutput>> {
        #[cfg(not(feature = "cairo_native"))]
        return self.execute_txs_sequentially_inner(txs, execution_deadline);
        #[cfg(feature = "cairo_native")]
        {
            // TODO(meshi): find a way to access the contract class manager config from transaction
            // executor.
            let txs = txs.to_vec();
            std::thread::scope(|s| {
                std::thread::Builder::new()
                    // when running Cairo natively, the real stack is used and could get overflowed
                    // (unlike the VM where the stack is simulated in the heap as a memory segment).
                    //
                    // We pre-allocate the stack here, and not during Native execution (not trivial), so it
                    // needs to be big enough ahead.
                    // However, making it very big is wasteful (especially with multi-threading).
                    // So, the stack size should support calls with a reasonable gas limit, for extremely deep
                    // recursions to reach out-of-gas before hitting the bottom of the recursion.
                    //
                    // The gas upper bound is MAX_POSSIBLE_SIERRA_GAS, and sequencers must not raise it without
                    // adjusting the stack size.
                    .stack_size(self.config.stack_size)
                    .spawn_scoped(s, || self.execute_txs_sequentially_inner(&txs, execution_deadline))
                    .expect("Failed to spawn thread")
                    .join()
                    .expect("Failed to join thread.")
            })
        }
    }
