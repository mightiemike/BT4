Confirmed: no actuator under `actuator/src/main/java/org/tron/core/actuator/` performs its own permission-operations check — that check exists only once, at transaction-level signature validation (`TransactionCapsule.checkPermission`/`WalletUtil.checkPermissionOperations`), gated on the *outer* `Contract.getType()`. This is the exact structural analog of the reported Solidity bug (permission checked against the "entry" call rather than the "current" operation).

### Title
Active-permission operations bitmask is enforced only against the outer transaction contract type, not against system operations (freeze/unfreeze/vote) triggered from inside TVM execution - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
Multi-signature "Active" permissions restrict which `ContractType`s a key may authorize via a 256-bit `operations` bitmap, checked once per transaction against `contract.getTypeValue()` of the transaction's single top-level `Contract` [1](#0-0) . Analogous to the reported `msg.sig`-based `auth` bug — where permission is validated against the *entry* call selector rather than the function that ultimately executes — java-tron validates permission only against the outer `TriggerSmartContract`/`CreateSmartContract` type, then lets the TVM internally execute system-level state transitions (freeze, unfreeze, freezeV2) as if the permission bitmap had authorized those specific operations types.

### Finding Description
Permission enforcement happens exactly once, at `TransactionCapsule.checkPermission`, driven off `contract.getTypeValue()` of contract index 0 [2](#0-1) . `Manager.processTransaction` additionally enforces exactly one contract per transaction [3](#0-2) , so this is the sole permission gate for the whole transaction.

When that single top-level contract is `TriggerSmartContract`, execution is routed to `VMActuator` instead of the standard actuator list [4](#0-3) . Inside TVM execution, the `FREEZE`/`UNFREEZE`/`FREEZEBALANCEV2` opcodes call `Program.freeze`/`unfreeze`/`freezeBalanceV2`, which directly instantiate and run `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor`/`FreezeBalanceV2Processor` against the *contract's* repository [5](#0-4) [6](#0-5) . None of these processors, nor any actuator in `actuator/src/main/java/org/tron/core/actuator/`, perform a second `checkPermissionOperations` check keyed to `FreezeBalanceContract`/`UnfreezeBalanceContract`/`VoteWitnessContract` — that check exists solely on the outer `TriggerSmartContract` type.

This means: a multisig "Active" permission key whose `operations` bitmap authorizes only `TriggerSmartContract` (i.e., explicitly does NOT authorize `FreezeBalanceContract`, `UnfreezeBalanceContract`, or `VoteWitnessContract` types) can nonetheless cause freeze/unfreeze/vote state changes by signing a `TriggerSmartContract` transaction that calls a contract exercising the `FREEZE`/`UNFREEZE`/vote-related precompiles, because the bitmap check never re-executes for the "true" underlying operation — exactly mirroring the `auth`/`msg.sig` flaw where a permission check bound at the "outer call" is silently reused for a different "inner" operation.

### Impact Explanation
A governance/multisig account owner who deliberately restricts an Active-permission key to only `TriggerSmartContract` operations (e.g., a bot key meant only to interact with dApps) can have that key used to freeze/unfreeze TRX for bandwidth/energy or manipulate SR votes on the account's behalf — actions the owner explicitly excluded from that key's authorized operation set. This is an unauthorized-account-operation / permission-bypass issue that corrupts the intended access-control model without needing any privileged actor, leaked key, or malicious peer — only a normal smart-contract call using an under-permissioned signing key.

### Likelihood Explanation
Any account using TRON's multisig "Active" permission with a restricted `operations` bitmap that allows smart-contract triggering but excludes freeze/unfreeze/vote contract types is affected as soon as such a key signs a `TriggerSmartContract` transaction to any contract using the freeze/unfreeze/vote TVM opcodes. This requires no special privilege and is reachable directly via `wallet/broadcasttransaction` with a `TriggerSmartContract`.

### Recommendation
Add an explicit operations-bitmap check inside `Program.freeze`, `Program.unfreeze`, `Program.freezeBalanceV2` (and any TVM-reachable vote/precompile action) against the signing account's Active permission for the transaction, analogous to `checkPermissionOperations`, using the *actual* underlying `ContractType` (e.g. `FreezeBalanceContract`) rather than relying on the outer `TriggerSmartContract` authorization already validated at signature time. Alternatively, explicitly document and/or block Active permissions with restricted `operations` bitmaps from being used to sign `TriggerSmartContract` transactions that can reach these internal state-changing opcodes, since the permission model cannot presently distinguish "this key may call contracts" from "this key may freeze/unfreeze/vote via a contract."

### Proof of Concept
1. Create an account with an Active permission whose `operations` bitmap has the bit set only for `ContractType.TriggerSmartContract` (bit index corresponding to that type, per `checkPermissionOperations`) and NOT for `FreezeBalanceContract`/`UnfreezeBalanceContract`/`VoteWitnessContract`.
2. Deploy a smart contract exposing a function that calls the TVM `FREEZE`/`UNFREEZE` opcode (as exercised in `framework/src/test/java/org/tron/common/runtime/vm/FreezeTest.java`, e.g. `freezeForSelf`/`freezeForOther`) [7](#0-6) .
3. Sign a `TriggerSmartContract` transaction calling that function with the restricted Active-permission key (`permission_id` referencing that Active permission).
4. Observe that `TransactionCapsule.checkPermission` only validates the bit for `TriggerSmartContract` and passes [2](#0-1) ; the transaction succeeds and `Program.freeze` executes `FreezeBalanceProcessor` unconditionally on behalf of the account, despite the permission bitmap never authorizing `FreezeBalanceContract`.

Note: I was unable to independently trace whether TVM's vote-related precompiles (`voteWitness`, `rewardBalance`, etc., referenced in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`) perform their own permission gate before mutating vote state, due to index size limits on precompiled-contract implementations; a Devin session with full repo access could confirm this by inspecting the `Vote`/`VoteWitness` precompiled-contract `execute()` implementations directly.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,

    FreezeBalanceParam param = new FreezeBalanceParam();
    param.setOwnerAddress(owner);
    param.setReceiverAddress(receiver);
    boolean needCheckFrozenTime = CommonParameter.getInstance()
        .getCheckFrozenTime() == 1; // for test
    param.setFrozenDuration(needCheckFrozenTime
        ? repository.getDynamicPropertiesStore().getMinFrozenTime() : 0);
    param.setResourceType(parseResourceCode(resourceType));
    try {
      FreezeBalanceProcessor processor = new FreezeBalanceProcessor();
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;

      logger.warn("TVM Freeze: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM Freeze: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
