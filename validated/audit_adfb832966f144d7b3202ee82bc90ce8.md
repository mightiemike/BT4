### Title
Unauthenticated, fee-free contract declaration via BOOTSTRAP sender-address impersonation - (File: crates/starknet_api/src/executable_transaction.rs)

### Summary
Any unprivileged sender can submit a `Declare` transaction using the constant `sender_address = BOOTSTRAP` with `nonce = 0` and zero resource bounds. This transaction path is executed without ever invoking `__validate_declare__` (no signature/authentication check at all) and without any nonce increment, allowing repeated, unauthenticated, fee-free class declarations — an authentication bypass analogous to the CAS-auth issue where a party is authenticated using credentials/identity that were never verified as belonging to it.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` treats any declare transaction whose `sender_address` equals the well-known constant `bootstrap_address()` (`0x424f4f545354524150`, ASCII "BOOTSTRAP"), with `nonce == 0` and `charge_fee == false`, as a special genesis-bootstrap transaction: [1](#0-0) 

In `AccountTransaction::execute_raw`, when this condition holds, the transaction is executed directly via `run_execute` and returns immediately — **skipping `perform_pre_validation_stage` (nonce check/increment) and skipping the entire `__validate_declare__` call** that would normally authenticate the sender via a signature: [2](#0-1) 

Because `sender_address` is a hard-coded constant, not a real deployed account contract, and because this path bypasses `__validate_declare__` entirely, **no signature or authentication credential of any kind is required** to submit a valid declare transaction "as" this identity — unlike normal accounts, which prove ownership by satisfying `__validate_declare__` with a proper signature (see the real-signature account pattern used for comparison): [3](#0-2) 

The gateway's `check_declare_permissions` is the only sender-based gate applied to declare transactions, and it defaults to allowing any address (`authorized_declarer_accounts: None` ⇒ `is_authorized_declarer` returns `true` for every address), so by default configuration this BOOTSTRAP-identity path is fully open to any submitter: [4](#0-3) [5](#0-4) 

The gateway's stateful validator fully executes `Declare`/`DeployAccount` transactions during admission-time validation (not merely `__validate__`), explicitly because "the class was not declared before" must be checked — meaning this bootstrap branch is exercised at the gateway/mempool-admission layer as well as at block-execution/OS-replay time: [6](#0-5) 

Crucially, because no account-related action (including nonce increment) is performed for a successful bootstrap declare, the on-chain nonce for the BOOTSTRAP address never advances past `0`: [7](#0-6) 

This means the "nonce == 0" gating condition can be satisfied indefinitely — not just once at genesis. An attacker can therefore submit a new declare transaction (with a new, not-yet-declared `class_hash`, zero resource bounds, `sender_address = BOOTSTRAP`, `nonce = 0`, and an arbitrary/empty signature) in every subsequent block, forever, each time succeeding because:
1. `get_nonce_from_state(BOOTSTRAP)` always returns `0`, so the pre-check `incoming_tx_nonce == account_nonce` passes.
2. `is_bootstrap_declare` is satisfied (`sender_address == BOOTSTRAP`, `nonce == 0`, `charge_fee == false`).
3. Execution completely skips `__validate_declare__`, so no signature is ever checked.
4. The OS re-execution path (`transaction_impls.cairo`) mirrors this exact bypass, so proposer and re-execution agree and would not diverge, making this fully valid at the OS/consensus layer, not merely a gateway quirk: [8](#0-7) 

The only "declared once" backstop is `dict_update{... prev_value=0 ...}` per class hash, which prevents re-declaring the *same* class hash twice, but does **not** stop an attacker from perpetually declaring new distinct classes under the BOOTSTRAP identity with zero fee and zero authentication.

### Impact Explanation
This is an authentication bypass on the `Declare` transaction type: any unprivileged network participant can act "as" the BOOTSTRAP identity indefinitely without ever proving knowledge of any private key, because `__validate_declare__` is never invoked for this class of transaction. This directly matches the reachable-path categories (gateway validation, mempool admission, blockifier execution, and Starknet OS re-execution) called out as in-scope. The practical consequences:
- Unauthorized action performed under a privileged/system-reserved identity (BOOTSTRAP) with no credentials, an authentication-bypass class bug.
- Perpetual free (fee-bypassing) contract declarations, which can be used to flood block space with declare transactions that cost the attacker nothing, degrading the network's ability to process legitimate transactions (resembles "network unable to confirm new transactions" under sustained abuse), since Sierra→CASM compilation and class-hash computation for each declare is nontrivial CPU/memory work performed for free per the gateway's own semaphore-limiting comment on declare compilation cost.

### Likelihood Explanation
High likelihood: the only preconditions are (1) `sender_address == BOOTSTRAP`, (2) `nonce == 0` (always true on-chain because bootstrap declares never increment the sender's nonce), and (3) zero resource bounds (`charge_fee == false`), all of which are directly attacker-controlled fields of a submitted `RpcTransaction::Declare`. No signature, private key, or special network position is required. The gateway's declarer allow-list defaults to unrestricted (`authorized_declarer_accounts: None`), so no additional configuration is needed to reach this path in a default deployment.

### Recommendation
- Gate the bootstrap-declare bypass so it can only apply exactly once (e.g., only when the sender's contract/account state entry does not yet exist / genesis block number, or by consuming/incrementing a persistent "bootstrap used" flag), rather than relying solely on the sender's nonce staying at zero indefinitely.
- Alternatively, require the bootstrap declare path to be restricted at the protocol/consensus level (e.g., only permitted as part of block 0 / a designated genesis block), and reject it unconditionally afterward regardless of the reported nonce.
- Ensure the fix is applied consistently in both the Rust blockifier (`AccountTransaction::execute_raw`) and the Cairo Starknet OS (`transaction_impls.cairo`) so that proposer and re-execution stay in agreement.

### Proof of Concept
1. Construct an `RpcTransaction::Declare` (V3) with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`)
   - `nonce = Nonce(Felt::ZERO)`
   - `resource_bounds` set so `compute_max_possible_fee(tx_info) == 0` (e.g., `ValidResourceBounds::create_for_testing_no_fee_enforcement()`, as used in `generate_bootstrap_declare()`): [9](#0-8) 
   - Any arbitrary/empty `signature` (it is never checked) and a fresh, never-declared `class_hash`/`compiled_class_hash`.
2. Submit this transaction to the gateway `add_tx`. Since `authorized_declarer_accounts` is `None` by default, `check_declare_permissions` passes.
3. The stateful validator fully executes the declare (per `StatefulValidator::perform_validations`), hitting `is_bootstrap_declare` and skipping `__validate_declare__`; the class is declared successfully with zero fee and no signature check.
4. Repeat with a new distinct `class_hash` in a subsequent block — since the sender's nonce is never incremented, step 2–3 succeeds again indefinitely.

**Note on verification limits:** I was not able to fully trace whether any additional out-of-band gate (e.g., a genesis-only flag enforced by the batcher/consensus outside the files inspected) restricts this path to strictly the first block in the current deployment; the code inspected (blockifier execution and the Starknet OS Cairo implementation) shows no such restriction beyond the nonce/fee/sender-address conditions. If such an external genesis gate exists elsewhere in the batcher or genesis-initialization code, it was not located within index coverage and should be confirmed before treating this as fully exploitable in production.

    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }
