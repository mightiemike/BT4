### Title
Unauthenticated Request-ID Squatting in Gateway ConfidentialRelay Handler Blocks Legitimate Secret/Capability Requests - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

### Summary
The confidential-relay gateway handler registers a user-supplied `req.ID` into its `activeRequests` map before performing any authentication, attestation, or Workflow-DON-quorum authorization check. Any caller able to reach `HandleJSONRPCUserMessage` can claim an arbitrary request ID first, causing the legitimate DON/agent's subsequent request with the same ID to be rejected with `"request ID already exists"`. This mirrors the reported "signed credential front-running" bug class: an unprivileged actor can pre-empt the ID slot a legitimate party needs, denying them the credential/response they require.

### Finding Description
`HandleJSONRPCUserMessage` in `core/services/gateway/handlers/confidentialrelay/handler.go` immediately calls `h.newActiveRequest(req, callback)` and then fans the request out to nodes — with no authorization performed beforehand: [1](#0-0) 

`newActiveRequest` keys solely on the raw, caller-controlled `req.ID` and rejects any second request using the same ID, regardless of who submitted it or whether it is authorized: [2](#0-1) 

Only *after* an active-request slot for a given ID has been reserved does the DON-level `verifyWorkflowAuthorization` check (which validates 2F+1 signed compute requests and owner/workflow match) ever get evaluated by the receiving nodes — this happens downstream/out-of-band, per node, not as a gate before ID reservation at the gateway: [3](#0-2) 

This is in contrast to the sibling `vault` gateway handler, which explicitly authorizes the request (`h.requestProcessor.ProcessRequest`) *before* calling `newActiveRequest`, closing this exact race: [4](#0-3) 

The existing test `TestConfidentialRelayHandler_DuplicateRequestID` demonstrates the exact collision behavior (second call with the same ID is rejected), but only exercises a single caller — it does not test the cross-tenant/unauthenticated squatting scenario: [5](#0-4) 

If request IDs used for `MethodSecretsGet` / `MethodCapabilityExec` are deterministic or predictable (e.g., derived from `WorkflowID`/`WorkflowExecutionID`/`ReferenceID`, as is done for the analogous vault flow via `BuildWorkflowGetSecretsRequestID`), an attacker who can reach the gateway's user-facing endpoint can pre-submit a bogus/garbage request using the same ID before the legitimate Workflow DON does, permanently occupying that slot until timeout and causing the legitimate request to fail outright.

### Impact Explanation
A successful ID-squatting attack causes legitimate `Workflow DON` secrets-get or capability-exec requests to fail with "request ID already exists," denying availability of confidential relay/secrets functionality for that specific request ID/execution. This is a denial-of-service against a specific workflow execution's secret retrieval or capability call — directly analogous to the reported bug's impact of preventing an Agent from generating credentials it needs. It does not on its own leak secrets or forge authorization (verifyWorkflowAuthorization still protects the actual response contents), but it can be leveraged to persistently block execution of a targeted workflow/owner's confidential operations.

### Likelihood Explanation
Exploitability depends on (a) whether the gateway's HTTP/JSON-RPC ingress for this handler is reachable by unauthenticated/arbitrary external callers (typical for gateway "user message" endpoints prior to handler-level authorization) and (b) whether request IDs for this handler are predictable/derivable by a third party. I was not able to fully confirm the exact construction of request IDs specifically for the `MethodSecretsGet`/`MethodCapabilityExec` gateway path in the available index (the deterministic ID builder `BuildWorkflowGetSecretsRequestID` was confirmed for the vault capability path, not conclusively for this gateway handler), so likelihood is moderate and requires further verification of ID sourcing/predictability and ingress access control for this specific handler.

### Recommendation
Move any available authentication/authorization check (e.g., DON membership verification, attestation validation) ahead of `newActiveRequest` in `core/services/gateway/handlers/confidentialrelay/handler.go`, mirroring the pattern already used in `core/services/gateway/handlers/vault/handler.go` where `ProcessRequest` authorization happens before the request ID is reserved. Where full authorization cannot be performed synchronously at the gateway, consider namespacing the `activeRequests` key by authenticated caller/DON identity (similar to the vault gateway's owner-prefixed request ID scheme: `authorizedOwner + separator + originalRequestID`) so an unauthenticated ID collision cannot block a legitimate, distinct caller's request.

### Proof of Concept
Conceptual (not executed, based on code review):
1. Attacker determines or predicts the `req.ID` a target Workflow DON will use for an upcoming `MethodSecretsGet`/`MethodCapabilityExec` confidential relay request (e.g., derived from known `WorkflowID`/`ExecutionID`/`ReferenceID`).
2. Attacker sends a `HandleJSONRPCUserMessage` call to the gateway with that `req.ID` and arbitrary/garbage params before the legitimate DON's request arrives.
3. `newActiveRequest` (core/services/gateway/handlers/confidentialrelay/handler.go:368-383) succeeds and reserves the ID with no authorization check performed.
4. When the legitimate Workflow DON later submits the real request with the same `req.ID`, `newActiveRequest` returns `"request ID already exists"`, and the legitimate request is rejected/denied — exactly as shown by the existing regression test `TestConfidentialRelayHandler_DuplicateRequestID` (core/services/gateway/handlers/confidentialrelay/handler_test.go:767-785), but here triggered by an unauthorized third party rather than the same authorized caller retrying.

	if err != nil {
		return err
	}

}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

// verifyWorkflowAuthorization is the PRIV-433 check beyond attestation. Attestation only
// proves the request came from genuine enclave code; it does not prove the Workflow DON
// authorized fetching this owner's secrets. A compromised TEE would still pass attestation
// while self-asserting a victim's owner.
//
// The enclave forwards the Workflow-DON-signed compute requests it executed (a 2*F+1 quorum,
// where F is the Workflow DON fault tolerance). Each node signs the same ComputeRequest.Hash();
// we reconstruct that hash, verify each signature against the onchain Workflow DON signer set,
// and require the quorum of unique signers. The signed PublicData names the authorized owner
// and workflow, which must match this request. A breached enclave cannot forge a Workflow DON
// quorum over a different owner.
//
// All failures here are client errors: the request is unauthorized. The caller fetches the
// Workflow DON (a server-side concern) and passes it in, so registry failures stay internal.
func (h *Handler) verifyWorkflowAuthorization(don capabilities.DON, params confidentialrelaytypes.SecretsRequestParams) error {
	if len(params.SignedComputeRequests) == 0 {
		return errors.New("missing signed compute requests")
	}

	// Match the enclave's own quorum. With requireBFTQuorum the relay demands a
	// Byzantine quorum of 2*F+1 unique signers; otherwise a crash-fault quorum of
	// F+1 suffices.
	threshold := int(don.F) + 1
	if h.requireBFTQuorum {
		threshold = 2*int(don.F) + 1
	}

	// The forwarded requests differ only in their signature; they all sign one shared
	// ComputeRequest hash. Reconstruct that hash once and verify each signature over it.
	hash := params.SignedComputeRequests[0].Hash()
	payload := confidentialrelaytypes.SignedComputeRequestSignaturePayload(hash)

	signers := make(map[string]struct{})
	for _, scr := range params.SignedComputeRequests {
		if scr.Hash() != hash {
			return errors.New("forwarded signed compute requests do not share one compute request")
		}
		for _, member := range don.Members {
			if ed25519.Verify(ed25519.PublicKey(member[:]), payload, scr.Signature) {
				signers[member.String()] = struct{}{}
				break
			}
		}
	}
	if len(signers) < threshold {
		return fmt.Errorf("insufficient Workflow DON signatures: %d unique signers, need %d", len(signers), threshold)
	}

	// The signed request authorizes a specific owner and workflow; the secrets request must
	// match both, or a breached enclave could fetch another owner's secrets.
	var execution confidentialworkflow.WorkflowExecution
	if err := proto.Unmarshal(params.SignedComputeRequests[0].PublicData, &execution); err != nil {
		return fmt.Errorf("failed to unmarshal workflow execution from public data: %w", err)
	}
	if !common.IsHexAddress(params.Owner) || !common.IsHexAddress(execution.GetOwner()) {
		return errors.New("invalid owner address")
	}
	if common.HexToAddress(execution.GetOwner()) != common.HexToAddress(params.Owner) {
		return fmt.Errorf("owner not authorized: request %q vs signed %q", params.Owner, execution.GetOwner())
	}
	if execution.GetWorkflowId() != params.WorkflowID {
		return fmt.Errorf("workflow_id not authorized: request %q vs signed %q", params.WorkflowID, execution.GetWorkflowId())
	}
	return nil
}

func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
