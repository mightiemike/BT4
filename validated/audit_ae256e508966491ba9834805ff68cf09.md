### Title
`L1HandlerTransaction::calc_msg_hash` panics on empty calldata via unchecked `split_first().expect(...)` - ([File: crates/starknet_api/src/hash.rs])

### Summary
`l1_handler_message_hash` (invoked via `L1HandlerTransaction::calc_msg_hash`) calls `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")` on the transaction's calldata. If an `L1HandlerTransaction` is ever constructed/re-executed with empty calldata, this call panics instead of returning an error, mirroring the yaml-cpp `Scanner::peek` pattern where malformed/edge-case input triggers an unhandled assertion/panic rather than a graceful error path. [1](#0-0) 

### Finding Description
`l1_handler_message_hash` unconditionally assumes `calldata.0` has at least one element (the `from_address`):

```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
``` [2](#0-1) 

Notably, the sibling method on the same struct, `payload_size()`, was already patched to defend against exactly this edge case with `saturating_sub`, with an explicit comment stating the danger:

> "`saturating_sub` guards the empty-calldata case (which would otherwise underflow to `usize::MAX` in release): `L1HandlerTransaction` derives `Deserialize` and `Calldata` has no non-empty invariant." [3](#0-2) 

This comment confirms the codebase's own threat model: `Calldata`/`L1HandlerTransaction` derive `Deserialize` and carry **no invariant enforcing non-empty calldata** at the type level. `calc_msg_hash` was missed when this class of bug was fixed elsewhere, and still uses `.expect(...)`, which panics (process abort in debug, and in blockifier code panics propagate as process-level unwinds unless caught) instead of returning a `Result`.

`calc_msg_hash` is reachable from `apollo_rpc` (`v0_8/api/api_impl.rs`), which computes/exposes the L1↔L2 message hash for RPC consumers, and from `apollo_l1_events` (`l1_scraper.rs`, `l1_events_provider.rs`), which processes/re-derives L1 handler transactions scraped from L1 events. While `L1HandlerTransaction` is normally constructed from real L1 `sendMessageToL2` calls (where the L1 contract structurally always includes `from_address`), the Rust type itself has no such guarantee — `Calldata` is a plain `Vec<Felt>` deserializable from arbitrary JSON/RPC input, and `L1HandlerTransaction` derives `Deserialize`. Any code path that builds/re-executes an L1 handler transaction from externally-supplied or replayed/serialized data (e.g., re-execution tooling, RPC-supplied transaction objects, or malformed/adversarial L1 event replay) without re-validating calldata length can hit this panic.

### Impact Explanation
A panic in a sequencer/RPC process handling transaction-derived data is a denial-of-service: if reachable from an RPC endpoint or from L1 event/transaction re-execution paths without upstream length validation, a single malformed transaction record (empty calldata) crashes the process computing the hash, potentially disrupting the node's ability to serve requests or process L1 messages — directly analogous to the yaml-cpp assertion-failure DoS. This satisfies the "network unable to confirm new transactions" / DoS impact class if the panic occurs in a component handling this data on the hot path (RPC or the L1 events pipeline) without prior recovery/catch_unwind boundaries.

### Likelihood Explanation
Likelihood is constrained by the fact that in the primary production path, `L1HandlerTransaction`s are constructed via `ExecutableTransaction::create`/`EventData::try_from` from genuine L1 `sendMessageToL2` logs, which structurally always include the sender address as first calldata element, making the panic hard to trigger through the canonical scraper flow. The exposure is therefore most plausible through secondary paths — RPC-supplied/deserialized transaction objects or re-execution/testing tooling that construct `L1HandlerTransaction` directly from arbitrary `Calldata` — which was exactly the reasoning the project used to justify the `saturating_sub` fix in `payload_size()`. I was not able to fully trace every call site of `calc_msg_hash` (e.g., whether `apollo_rpc`'s `api_impl.rs` validates calldata non-emptiness before calling it) due to remaining tool-call budget, so likelihood should be treated as **moderate and unverified for the RPC path** — this needs confirmation against `crates/apollo_rpc/src/v0_8/api/api_impl.rs` before treating it as immediately exploitable.

### Recommendation
Replace the `.expect(...)` panic in `l1_handler_message_hash` with a `Result`-returning check (mirroring the `payload_size()` fix), e.g. return a `StarknetApiError` variant for empty calldata, and propagate that error through `calc_msg_hash` and all call sites (`apollo_rpc`, `apollo_l1_events`). Additionally, audit all `calc_msg_hash`/`l1_handler_message_hash` call sites to confirm whether any of them receive `Calldata` deserialized directly from external/RPC input, and add an explicit non-empty-calldata invariant at construction time for `L1HandlerTransaction` if none currently exists.

### Proof of Concept
```rust
use starknet_api::transaction::L1HandlerTransaction;
use starknet_api::transaction::fields::Calldata;

let tx = L1HandlerTransaction {
    calldata: Calldata(vec![].into()), // empty calldata, valid per the type (Vec<Felt>, no invariant)
    ..Default::default()
};

// Panics: "Invalid calldata, expected at least from_address"
let _ = tx.calc_msg_hash();
```
This demonstrates that the type system permits an `L1HandlerTransaction` with empty `calldata`, and `calc_msg_hash` panics rather than returning an error on this input — the exact "malformed low-level field triggers an assertion/panic instead of a validation error" pattern described in JLSEC-2026-22.

/// Calculating the message hash of L1 -> L2 message.
/// For more info: <https://docs.starknet.io/documentation/architecture_and_concepts/Network_Architecture/messaging-mechanism/#structure_and_hashing_l1-l2>
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());
```
