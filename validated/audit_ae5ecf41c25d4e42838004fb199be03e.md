### Title
Missing chain/network domain-separator in NEP-366/611 meta-transaction signing scheme allows cross-chain replay of `SignedDelegateAction` - (File: core/primitives/src/signable_message.rs)

### Summary
The EIP712 bug is about a missing domain separator (`name`/`version`) that binds a signature to a specific contract/chain context, so signatures become valid across unintended domains. The closest reachable analog in nearcore is the `MessageDiscriminant`/`SignableMessage` scheme used to sign `DelegateAction`/`DelegateActionV2` (NEP-366/611 meta-transactions): the signed payload never includes any chain-identifying value (no genesis hash, chain id, or even a recent `block_hash` as normal `SignedTransaction`s do), so a signature is only bound to `(discriminant, sender_id, receiver_id, actions, nonce, max_block_height, public_key)`.

### Finding Description
`SignableMessage` is the construct that plays the role of EIP712's domain separator: it prefixes the signed struct with a `MessageDiscriminant` derived only from the NEP number and on/off-chain flag [1](#0-0) . `DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash` hash exactly this tagged struct and nothing else identifies the target network: [2](#0-1)  and [3](#0-2) .

Contrast this with ordinary `SignedTransaction`s, which are always constructed with the chain's `last_block_hash` bound into the signed payload (`SignedTransaction::from_actions(..., tip.last_block_hash)`), giving them implicit chain-domain separation because block hashes are unique per chain history [4](#0-3) . `DelegateAction`/`DelegateActionV2` instead only carry `nonce` and `max_block_height` — a bare integer height, not a chain-specific hash — plus `sender_id`/`receiver_id`/`public_key` [5](#0-4) . Verification (`SignedDelegateAction::verify`, `VersionedSignedDelegateAction::verify`) checks only the signature against this chain-agnostic hash [6](#0-5) [7](#0-6) .

As a result, exactly like the missing `__EIP712_init` leaving `name`/`version` at default values (so a signature valid on one deployment/version is accepted on another), a `SignedDelegateAction` produced for one NEAR-protocol network is structurally indistinguishable from — and cryptographically valid on — any other nearcore-based network that shares the same account id, public key, and access-key nonce state (e.g., a state-forked/cloned chain, a test/staging replica seeded from mainnet state, or another chain instance built from the same nearcore codebase). `apply_delegate_action` performs no network/chain-binding check before accepting the signature — it only checks `signed_delegate_action.verify()`, `max_block_height` against local `block_height`, and `sender_id` match, then dispatches nonce validation in `validate_delegate_action_key` (`runtime/runtime/src/actions.rs`) [8](#0-7) .

### Impact Explanation
If an attacker (or the user themselves) can present the exact same `SignedDelegateAction` bytes to two independent nearcore-derived networks that happen to share matching sender account/access-key/nonce state (e.g., a mainnet state clone used for a rollup/appchain, disaster-recovery replica, or migration target), the meta-transaction — including token transfers, key additions, or other delegated actions — will be replayed and accepted a second time on the other network without a fresh signature from the sender. This is unauthorized value movement/state mutation authorized by a signature the sender never intended to be valid there, directly matching the "invalid state transition acceptance" / "unauthorized value movement" bar, since nothing in the signed payload or on-chain validation logic distinguishes the two networks.

### Likelihood Explanation
The likelihood is constrained: exploitation requires two live networks (both derived from nearcore, sharing the meta-tx feature) with coincidentally or deliberately identical account state (same `sender_id`, same `public_key` registered as an access key, and matching nonce at replay time) — a scenario that realistically occurs with state-forked or cloned networks (common in NEAR's ecosystem for testing, migrations, or appchains bootstrapped from mainnet state) rather than on arbitrary unrelated chains. Given meta-transactions are a stable, widely used primitive (NEP-366) and the domain lacks any explicit network-binding field by design, this is a real, reachable structural gap rather than a hypothetical one.

### Recommendation
Include a chain/network-binding value (e.g., genesis hash or a protocol-level chain id) inside the `SignableMessage`/`MessageDiscriminant` construction used for `DelegateAction` and `DelegateActionV2`, analogous to adding `name`/`version` via `__EIP712_init` in the EIP712 case, so that signatures produced for one nearcore-based network cannot be replayed as valid on another network that happens to share account/key/nonce state.

### Proof of Concept
1. Network A and Network B are both nearcore-based chains where account `alice.near` exists with the same full-access `public_key` and identical current nonce (e.g., B is a state-forked/cloned replica of A, or a migration/appchain bootstrapped from A's state).
2. Alice signs a `DelegateAction` for network A using `SignableMessage::new(&delegate_action, SignableMessageType::DelegateAction).sign(&signer)` as shown in the test/helper flow [9](#0-8) .
3. A relayer submits the resulting `SignedDelegateAction` bytes unchanged as the `Action::Delegate` payload of a transaction on network B.
4. `apply_delegate_action` on network B calls `signed_delegate_action.verify()` [10](#0-9) , which succeeds because the hashed payload contains no network-identifying data, and — provided B's `max_block_height`/nonce checks also pass because the state matches A — the delegated actions execute on B, replaying value/state changes never authorized for network B.
