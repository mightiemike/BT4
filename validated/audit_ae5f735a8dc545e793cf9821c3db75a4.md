### Title
Balance refunds redirected via `promise_set_refund_to` to a nonexistent/invalid `refund_to` account are permanently burnt instead of returned to the depositor - (File: `runtime/runtime/src/lib.rs`)

### Summary
NEAR lets a contract redirect the balance refund of an outgoing receipt to an arbitrary account using the host function `promise_set_refund_to`, instead of the default `predecessor_id`. If the receipt that carries the deposit later fails and the refund is generated with `predecessor_id == "system"` (i.e., it *is* the refund receipt) targeting that redirected `refund_to` account, and that account does not exist (or fails to accept the transfer for any reason resolved by `check_account_existence`), the refund receipt itself fails. Per the documented and implemented rule, a failed refund is not retried or redirected back to the original depositor — its entire deposit amount is unconditionally burnt.

### Finding Description
The host function `promise_set_refund_to` [1](#0-0)  lets the *predecessor* of an outgoing receipt (any ordinary contract, reachable from any unprivileged `FunctionCall` action) set `refund_to` on that receipt, redirecting where the deposit-refund receipt is sent if the receipt fails, per `receipt.balance_refund_receiver()` [2](#0-1) .

The system documents and implements: "If the execution of a refund fails, the refund amount is burnt" [3](#0-2) . This is implemented directly in `apply_action_receipt`: when the receipt being applied is itself a refund (`receipt.predecessor_id().is_system()`) and its execution result is an `Err`, the runtime does not attempt any fallback — it adds the entire deposit to `other_burnt_amount`, i.e., burns it out of total supply: [4](#0-3) 

A refund receipt fails when its single `Transfer` action targets an account that `check_account_existence` rejects — e.g., the `refund_to` account never existed, was never funded, or was deleted between the time the original receipt was sent and the time the refund was generated (a window entirely outside the depositor's control, analogous to the "blocklisted after queuing" scenario in the reported bug). This is confirmed directly by an existing unit test showing a refund receipt to a missing account fails with `AccountDoesNotExist` and never creates the account: [5](#0-4)  and by the general rule that refunds are barred from implicit account creation: [6](#0-5) .

The exact analog to the SolverVaults bug: the caller (predecessor) that attaches a deposit and calls `promise_set_refund_to(promise_idx, receiver_len, receiver_ptr)` picks the refund destination for money that is *not yet theirs* to redirect risk-free — if that destination is invalid at refund time, the depositor's principal (their deposit) is destroyed rather than returned to them, exactly as SVT holders in the report lose their tokens irrecoverably when the receiver is blocklisted at claim time.

### Impact Explanation
This causes permanent, unrecoverable value destruction (token burn) of a legitimate depositor's funds through a code path reachable by any unprivileged contract call chain: a normal `FunctionCall` action can create a promise, attach a deposit, and call `promise_set_refund_to` to point the refund at any account id string, including one that does not exist or one under adversarial control that can be deleted at will (e.g., a fresh named account created and then deleted, or a still-nonexistent named/implicit account). When the downstream receipt fails (deliberately triggerable, e.g., by calling a non-existing method as demonstrated in `test_refund_to`), the deposit refund is sent to the attacker-chosen/invalid `refund_to` and is burnt entirely instead of returning to the original depositor. This is a supply-decreasing, fund-loss bug meeting the "permanently frozen funds" / "unauthorized value movement" bar.

### Likelihood Explanation
High reachability: `promise_set_refund_to` is a stable, unprivileged host function usable by any deployed contract from a normal transaction/contract call; no validator or node privilege is required. Triggering a downstream receipt failure is fully within the caller's control (e.g., calling a nonexistent method, as already exercised in the test suite via `test_refund_to`). The only additional requirement is that the redirected `refund_to` account not exist (or be removed) at refund time — trivially achievable since account existence is checked at execution time, not at receipt-creation time.

### Proof of Concept
1. Contract `A` (attacker or careless integrator) receives a deposit from `Alice`, e.g., via a function call attaching a deposit.
2. `A` creates a promise batch to some contract `B`, attaches the deposit, and calls `promise_batch_action_function_call` targeting a method that is designed/known to fail (or simply a `non_existing_function`, as in `test_refund_to` [7](#0-6) ).
3. `A` calls `promise_set_refund_to(promise_idx, len, ptr)` pointing to an account id that does not exist (e.g., a fresh unused named account, or one `A` plans to delete before the refund lands).
4. The receipt to `B` fails (missing method). The runtime generates a deposit-refund receipt whose receiver is the `refund_to` account chosen in step 3, per `balance_refund_receiver`.
5. When that refund receipt executes, `check_account_existence` rejects the `Transfer` to the nonexistent account (`AccountDoesNotExist`), the refund receipt itself fails, and per `runtime/runtime/src/lib.rs:1047-1055` the entire deposit is added to `other_burnt_amount` — permanently destroyed. Alice's deposit is gone; it is not credited to her, to `A`, or to anyone else, and total supply is reduced accordingly.

pub fn promise_set_refund_to(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    account_id_len: u64,
    account_id_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_set_refund_to".to_string(),
        }
        .into());
    }
    let refund_to = read_and_parse_account_id(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        &ctx.config,
        account_id_ptr,
        account_id_len,
    )?;
    let promise = ctx
        .promises
        .get(promise_idx as usize)
        .ok_or(HostError::InvalidPromiseIndex { promise_idx })?;

    let receipt_idx = match &promise {
        Promise::Receipt(receipt_idx) => Ok(*receipt_idx),
        Promise::NotReceipt(_) => Err(HostError::CannotSetRefundToOnJointPromise),
    }?;

    ctx.ext.set_refund_to(receipt_idx, refund_to);
    Ok(())
