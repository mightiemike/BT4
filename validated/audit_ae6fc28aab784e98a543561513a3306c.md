### Title
Unbounded recursion in `bytecode_hash_node` during compiled class hash computation causes stack overflow DoS - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` recursively walks the `NestedIntList` segment structure describing a CASM bytecode's segmentation into hashable chunks, with recursion depth equal to the nesting depth of that structure and no depth limit enforced anywhere in the hashing path. [1](#0-0) 

### Finding Description
`bytecode_hash_node` recurses once per level of `NestedIntList::Node` nesting via `node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child))`. [2](#0-1) 

This is invoked from `bytecode_hash`, which is called by `hash_inner` — the compiled-class-hash computation path used whenever a class's `CompiledClassHash` must be derived from its bytecode and `bytecode_segment_lengths`. [3](#0-2) 

The `bytecode_segment_lengths` field comes from `CasmContractEntryPoint`/`CasmContractClass::bytecode_segment_lengths` (from the `cairo_lang_starknet_classes` crate), and is populated from the class produced by Sierra-to-CASM compilation. There is no explicit bound in this code on how deeply the `Node` variant of `NestedIntList` may be nested before `hash_inner`/`bytecode_hash` is invoked. This class hash computation is precisely analogous to the CVE's `parse_comparison` bug class: a recursive-descent style walk over an attacker-influenced tree structure (there, a parsed comparison expression AST; here, a nested bytecode-segmentation tree) with no depth guard, terminating only when the native call stack is exhausted.

By contrast, other similar bytecode-segment recursion in this codebase (`NestedFeltCounts::new_inner` in `crates/blockifier/src/execution/contract_class.rs`) explicitly asserts a maximum segmentation depth of 1 before recursing, showing the codebase is aware of this class of hazard elsewhere but the guard is not applied on the `bytecode_hash_node` path. [4](#0-3) 

If a class declarer can cause the Sierra-to-CASM compiler (or a manually crafted/legacy class artifact) to produce (or if the segmentation structure is otherwise attacker-influenced/deeply nested), `bytecode_hash` will recurse to a depth proportional to that nesting when computing `CompiledClassHash`, exhausting the thread stack and crashing the sequencer process handling that computation.

### Impact Explanation
A stack overflow in a Rust process is undefined behavior/an abort, not a catchable panic — a class declaration (or any code path re-deriving a class hash, e.g. Starknet OS re-execution or state commitment validation of declared classes) that triggers deep enough nesting can crash the sequencer process performing the hash, causing a denial of service and potential inability to process/confirm transactions if this occurs mid-block-building or during OS re-execution/consensus-critical hashing.

### Likelihood Explanation
Likelihood depends on whether the nesting depth of `bytecode_segment_lengths` is bounded elsewhere (e.g., by the Sierra-to-CASM compiler's segmentation logic or by a class-size/complexity limit enforced during gateway validation) — I could not locate such a bound within this repository's code for the `bytecode_hash_node` path specifically, unlike the analogous `NestedFeltCounts` structure which explicitly caps depth at 1. Since the `cairo_lang_starknet_classes` compiler (external dependency) determines the actual segmentation structure, the true reachable maximum nesting depth from a single declared class could not be fully confirmed from this codebase alone.

### Recommendation
Add an explicit maximum recursion/nesting-depth check for `NestedIntList`/`HashableNestedIntList` before or during `bytecode_hash_node`, mirroring the depth assertion already used in `NestedFeltCounts::new_inner`, and reject compiled classes whose segment structure exceeds the bound during declare-time validation rather than only at hash-computation time. Consider also converting the recursive walk into an explicit iterative stack-based traversal to eliminate native stack growth entirely.

### Proof of Concept
Not independently reproducible from this analysis alone: a concrete PoC requires confirming, via the `cairo_lang_starknet_classes` compiler and/or gateway class validation, that a class declarer can produce a `CasmContractClass` whose `bytecode_segment_lengths` contains `NestedIntList::Node` nesting deep enough (e.g., tens of thousands of levels) to overflow the default thread stack when `hash_inner`/`bytecode_hash`/`bytecode_hash_node` is invoked on it. I could not verify from the available index whether the compiler or a preceding validation step already caps this nesting depth.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Computes the compiled class hash for a given hashable class using the specified hash algorithm.
fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}
