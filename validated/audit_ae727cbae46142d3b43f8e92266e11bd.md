### Title
Unbounded Iteration Over TRC10 Token Balances in `SUICIDE` Opcode Handling Can Exhaust Energy/Cause DoS - (File: `actuator/src/main/java/org/tron/core/vm/utils/MUtil.java`)

### Summary
`MUtil.transferAllToken()` is invoked when a smart contract self-destructs (the TVM `SUICIDE`/`0xff` opcode) to move all of the contract's TRC10 token balances to the beneficiary address. The method iterates over every entry in the contract's `assetV2` map with no upper bound on the number of distinct token IDs a single account can accumulate, mirroring the `BalanceSheetV2.getHypotheticalAccountLiquidity()` unbounded-collateral-iteration pattern described in the external report.

### Finding Description
`transferAllToken` retrieves the full `assetV2` map of the self-destructing account and iterates over it with a `forEach`, mutating both the source and destination account builders for every token entry: [1](#0-0) 

The number of distinct TRC10 tokens (`assetV2` map keys) an account can hold is not bounded anywhere in the account model — any address, including a contract address, can be made to receive an arbitrary number of different TRC10 token types via ordinary `TransferAssetContract`/`TransferTokenContract` operations, similar to how anyone can send arbitrary collateral tokens to a HiFi vault. This is confirmed by the underlying storage/accessor code that has no cap on map size: [2](#0-1) [3](#0-2) 

While the number of *bond-like* resources (frozen entries for bandwidth/energy) is intrinsically small (bounded to a handful of `Frozen`/`FreezeV2` records per resource type, as seen in `UnfreezeBalanceActuator`/`CancelAllUnfreezeV2Processor`), the TRC10 asset map has no analogous cap — precisely the asymmetry the external report calls out between bounded bonds (`maxBonds`) and unbounded collateral assets.

`SUICIDE` is priced as a flat, constant energy cost in `EnergyCost.java` (a fixed base cost for the opcode, not scaled by the number of token types the contract holds), so a contract address that has been sent a very large number of distinct TRC10 token IDs prior to self-destructing would force the executing node to perform O(n) map operations (`forEach`, `putAssetV2` builder rebuilds which are themselves O(map size) for protobuf builders) for energy priced as O(1).

### Impact Explanation
An attacker can pre-fund an attacker-controlled contract address with tiny amounts of a very large number of distinct TRC10 tokens (issuing many token types has a fixed TRX fee but is otherwise unrestricted, and transferring 1 unit of an existing token is cheap bandwidth-wise) and then trigger `SUICIDE` from that contract. Because the opcode's energy cost does not scale with the number of assets being moved, this creates a mismatch between metered cost and actual work performed, which can be used to degrade node performance during block execution (CPU/time consumption disproportionate to energy charged) — a resource-accounting/DoS class issue in TVM execution and energy metering, directly analogous to the reported unbounded collateral iteration causing out-of-gas/DoS in HiFi's `BalanceSheetV2`.

### Likelihood Explanation
Reachable entirely through normal, permissionless operations: (1) issue/acquire many TRC10 token IDs, (2) transfer minimal amounts of each to a target contract address via broadcast `TransferAssetContract`/`TransferTokenContract` transactions, (3) deploy/trigger a contract to execute `SUICIDE` from that address. No privileged role, leaked key, or malicious peer is required — it is achievable by any account willing to pay the (relatively low, linear, non-prohibitive) TRC10 issuance/transfer fees. This raises the likelihood above a purely theoretical concern, though the practical severity depends on how large a token-map an attacker can economically build up, which was not something I could fully quantify from the available code/config (e.g., exact TRC10 issuance fee and whether it scales to deter large-scale spamming).

### Recommendation
- Introduce an upper bound on the number of distinct TRC10 token types (`assetV2` map entries) any single account (especially contract accounts subject to `SUICIDE`) may hold, or reject/ignore transfers that would push an account over that bound.
- Scale the `SUICIDE` opcode's energy cost dynamically based on the number of asset map entries being transferred in `transferAllToken`, rather than a flat constant, so the metering matches the O(n) work performed in `MUtil.transferAllToken`.
- Consider capping the number of `putAssetV2` builder mutations performed per `SUICIDE` execution, or moving the token-consolidation logic to a batched, gas-metered per-entry model similar to how frozen resource lists are already inherently bounded to a small fixed set of resource types.

### Proof of Concept
Conceptual PoC (would require live network access to fully execute, not verifiable via static code review alone):
1. Deploy a large number of TRC10 tokens (`AssetIssueContract`) under attacker control — bounded only by TRX issuance fee.
2. Deploy a simple contract `C`.
3. From many different owner accounts, broadcast `TransferAssetContract`/`TransferTokenContract` transactions sending a minimal amount of each distinct TRC10 token to `C`'s address, building up thousands of entries in `C`'s `assetV2` map (confirmed unbounded by `AccountCapsule.getAssetMapV2()`/`AccountAssetStore.getAllAssets()`, which impose no size limit).
4. Call `C` with a method that executes `SUICIDE`, which the TVM implementation resolves to `MUtil.transferAllToken(deposit, fromAddress, toAddress)` — iterating the full unbounded `assetV2` map while being charged the fixed `SUICIDE` energy cost from `EnergyCost.java`.
5. Measure that the wall-clock/CPU cost of processing this transaction is disproportionate to the energy charged, demonstrating the metering mismatch.

Note: I was not able to independently confirm the exact caller site that maps the `SUICIDE` opcode to `MUtil.transferAllToken` (i.e., the specific line in `Program.java`/`OperationActions`), nor the exact flat energy cost constant used for `SUICIDE`, within the available search budget — these should be verified directly in `actuator/src/main/java/org/tron/core/vm/EnergyCost.java` and `actuator/src/main/java/org/tron/core/vm/OperationActions.java` before treating this as fully proven.

```java
  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
```

```java
  public Map<String, Long> getAllAssets(Protocol.Account account) {
    Map<String, Long> assets = new HashMap<>();
    if (account.getAssetOptimized()) {
      Map<WrappedByteArray, byte[]> map = prefixQuery(account.getAddress().toByteArray());
      map.forEach((k, v) -> {
        byte[] assetID = ByteArray.subArray(k.getBytes(),
                account.getAddress().toByteArray().length, k.getBytes().length);
        assets.put(ByteArray.toStr(assetID), Longs.fromByteArray(v));
      });
    }
    account.getAssetV2Map().forEach((k, v) -> assets.put(k, v));
    return assets;
  }
```
