### Title
Meta-Transaction (`DelegateAction`/NEP-366) Signatures Lack Chain-Binding, Enabling Cross-Network Replay - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary
The NEP-366/NEP-461 meta-transaction signing scheme used for `DelegateAction`/`DelegateActionV2` never binds the signed payload to any chain-specific identifier (no genesis hash, network ID, or even a recent `block_hash` as regular `SignedTransaction`s use). The signed hash is derived only from `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`, and a NEP-number discriminant. Because NEAR implicit accounts derive their `AccountId` deterministically from the public key, the same account/key/nonce state can exist identically on two independent NEAR-protocol networks (mainnet, testnet, or any other network sharing the protocol/genesis format), allowing a signed `DelegateAction` intended for one network to be replayed verbatim on the other.

### Finding Description
`SignedDelegateAction::verify` and `VersionedSignedDelegateAction::verify` check the ed25519 (or gas-key) signature against `delegate_action.get_nep461_hash()`: [1](#0-0) [2](#0-1) 

That hash is computed purely from the `SignableMessage` wrapper (a NEP discriminant plus the borsh-serialized `DelegateAction`/`DelegateActionV2`), with no chain-identifying field anywhere in the struct: [3](#0-2) [4](#0-3) 

On execution, `apply_delegate_action` only re-verifies the signature, expiry (`max_block_height`), and that `sender_id` matches the receipt's receiver — again nothing chain-specific: [5](#0-4) 

By contrast, regular `SignedTransaction`s at least embed a recent `block_hash` from the specific chain being targeted, giving some (weak but present) chain-context binding as noted in the docs: [6](#0-5) 

`DelegateAction` has no equivalent field at all — only a plain integer `max_block_height`, which is meaningless outside the context of "some chain's" block numbering. This is precisely the class of bug flagged in the referenced report: an off-chain-signed message whose hash omits any chain/network identifier, permitting replay of the exact same signed payload against a different chain that happens to share the same account/key state.

The `tools/mirror` utility independently corroborates that `DelegateAction` payloads are chain-agnostic by design — the mirroring tool must explicitly re-sign every delegate action to remap it from one chain to another, implying that if it did *not* re-sign, the original signature would still verify against the new chain because the scheme carries no chain identity of its own: [7](#0-6) 

### Impact Explanation
NEAR implicit accounts are simply the hex encoding of an ed25519/secp256k1 public key, so identical account IDs with identical (zero-initialized) nonces naturally exist across separate NEAR networks that share genesis/protocol format (e.g. a permissioned NEAR-based chain forked from mainnet's binary/protocol, a disaster-recovery/duplicate network, or any two networks a user interacts with using the same keypair once an implicit account is created on both). A `SignedDelegateAction` crafted and relayed on chain A (e.g., an `AddKey` granting access, or a `Transfer`/`FunctionCall` action) can be captured and resubmitted by any relayer on chain B, where it will pass `verify()` and `apply_delegate_action` checks identically, causing unauthorized state changes (e.g., attacker-controlled key added, funds moved, or actions executed) on the second network without the user's intent for that specific chain — a form of unauthorized value movement / invalid state transition on the replayed chain.

### Likelihood Explanation
This requires that the identical `(sender_id, public_key, nonce)` triple be valid on two live networks, which is a real and not merely theoretical scenario for NEAR implicit accounts, and requires no cooperation from the original signer or the target chain's operators — only a party that has observed a `SignedDelegateAction` (which is, by design, passed to third-party relayers and thus not confidential) and access to submit transactions to another compatible network. Because relayers are explicitly trusted with these signed payloads in the normal meta-transaction flow, and any relayer/observer can attempt replay, likelihood is moderate.

### Recommendation
Include a chain-binding value (e.g., the network/chain genesis hash, or the `block_hash` field already used by ordinary `SignedTransaction`s) inside `DelegateAction`/`DelegateActionV2` and fold it into the NEP-461 `SignableMessage` hash computed by `get_nep461_hash`. Reject delegate actions during `apply_delegate_action` whose embedded chain identifier does not match the executing chain's own identifier, mirroring EIP-4337's recommended fix of hashing `chainid` into the signed payload.

### Proof of Concept
1. Create implicit account `IMPLICIT_ID = hex(pubkey)` with a full-access key `pubkey` on network A and, independently, an identically-derived account with the same key material on network B (both networks running unmodified nearcore, sharing genesis/protocol layout, e.g. two forks or a mirrored/duplicated deployment).
2. On network A, sign `DelegateAction { sender_id: IMPLICIT_ID, receiver_id: IMPLICIT_ID, actions: [AddKey(attacker_pubkey, FullAccess)], nonce: N, max_block_height: H, public_key: pubkey }` as in `SignedDelegateAction::sign` (`core/primitives/src/action/delegate.rs:92-95`) and submit via a relayer to network A.
3. Take the identical `SignedDelegateAction` bytes and submit them (wrapped in a fresh outer transaction paid for by any relayer on network B) to network B, where the same `sender_id`/`public_key`/nonce state exists.
4. `apply_delegate_action` on network B verifies the signature successfully (`runtime/runtime/src/actions.rs:474-491`) since nothing in the hash or checks references network identity, and the `AddKey` action executes, granting the attacker access on network B as well — despite the user never intending to authorize anything on network B.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
