### Title
Front-running asset-name registration permanently bricks a victim's `AssetIssueContract` issuance - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
When `AllowSameTokenName` is disabled, `AssetIssueActuator#validate` rejects any asset issuance whose `name` is already present in `AssetIssueStore`, and each account may issue only one asset ever. Because the asset name is fully attacker-controlled and the check-then-create is not protected against front-running, an adversary who observes a pending `AssetIssueContract` broadcast (or simply predicts/guesses a name a project intends to use) can submit their own `AssetIssueContract` with the identical name first. Since name uniqueness is enforced permanently and there is no retry/alternate-key mechanism, the original issuer's transaction is permanently rejected with `"Token exists"`, mirroring the AutoRoller bug class: a permissionless, deterministically-keyed "create once" resource can be squatted by an adversary to permanently brick a legitimate participant's create operation.

### Finding Description
`AssetIssueActuator#validate` enforces global uniqueness of the raw asset `name` bytes when the network parameter `AllowSameTokenName == 0`: [1](#0-0) 

and separately enforces "one asset per account" via `AccountCapsule#setAssetIssuedName`/related checks exercised in `assetIssueNameTest`: [2](#0-1) 

The `execute()` path unconditionally writes to `AssetIssueStore` keyed by the exact `name` bytes as soon as `validate()` passes: [3](#0-2) 

Because (1) the key (`name`) is entirely chosen/controlled by the caller and easily predictable/observable (e.g., publicly announced ticker/token name, or visible in the mempool as a pending, unconfirmed transaction), (2) the store slot can only ever be claimed once with no expiry, and (3) validation only checks for prior existence without any reservation/commitment scheme, any unprivileged account can broadcast an `AssetIssueContract` with the same `name` first. This is structurally identical to the reported bug class: a deterministically-keyed, single-use resource creation (`SpaceFactory.create(adapter, maturity)` in the original report vs. `AssetIssueStore` keyed by `name` here) that reverts on collision (`POOL_ALREADY_EXISTS` vs. `"Token exists"`), letting an adversary permanently deny a targeted, legitimate creation.

### Impact Explanation
A victim who intends to issue a TRC10 token under a specific name can be permanently blocked from ever issuing that asset (name squatting/griefing), since the check is a one-time, non-expiring global reservation and the account is limited to one asset issuance ever in the `AllowSameTokenName == 0` regime. This is a protocol-level DoS on a core actuator (`AssetIssueActuator`) reachable from any anonymous broadcast transaction, at the cost of only the `AssetIssueFee` and the token's `FrozenSupply`/other issuance requirements to the attacker, causing denial-of-service to the target's expected token launch and potential reputational/financial harm to projects relying on a specific asset name.

### Likelihood Explanation
Exploitation requires only broadcasting a standard `AssetIssueContract` transaction with the desired name (observable via mempool sniffing of the victim's pending transaction, or simply guessed/pre-empted based on public announcements) — no privileged role or special access is needed. The primary caveat is that this uniqueness constraint is gated by the `AllowSameTokenName` dynamic parameter (`== 0`); in that mode it's a straightforward, always-reachable griefing vector, while under `AllowSameTokenName == 1` each issuance instead gets a unique internal numeric ID and this specific name-collision DoS path is not applicable (asset name collisions are no longer store keys). I was not able to fully verify from the indexed code what value `AllowSameTokenName` currently holds by default on the live/mainnet chain configuration for this fork (no default assignment for it was found in `DynamicPropertiesStore.java` in the indexed context), so likelihood is conditional on this legacy mode being active for the deployment in question (e.g., private/consortium chains or test networks that have not enabled `AllowSameTokenName`).

### Recommendation
- Do not treat raw user-supplied `name` bytes as a permanent, irrevocable global reservation without protection against front-running (e.g., commit-reveal for name registration, or fee/stake scaling with contention).
- Consider decoupling the human-readable `name` from the actual unique key (as already done for the `AllowSameTokenName == 1` path via numeric token IDs), and deprecate/remove the legacy name-keyed uniqueness path (`AssetIssueStore` keyed directly by `name`) to eliminate this griefing vector entirely.
- If backward compatibility requires keeping the legacy path, add mitigations such as a reservation/priority mechanism tied to account history, or make repeated identical-name submissions from unrelated accounts more costly to deter squatting.

### Proof of Concept
1. Attacker monitors the mempool (or otherwise learns) that account `A` intends to broadcast an `AssetIssueContract` with `name = "PROJECTX"` while `AllowSameTokenName == 0`.
2. Attacker immediately broadcasts their own `AssetIssueContract` with the identical `name = "PROJECTX"` (satisfying the minimal validation requirements shown in `AssetIssueActuator#validate`, e.g. non-empty valid name, valid start/end time, positive `totalSupply`, etc.) — see the reference test setup pattern: [4](#0-3) 
3. If the attacker's transaction is included first, `AssetIssueStore.put(assetIssueCapsule.createDbKey(), assetIssueCapsule)` claims the `"PROJECTX"` key permanently: [5](#0-4) 
4. Account `A`'s subsequent (or even earlier-broadcast-but-later-included) `AssetIssueContract` for `"PROJECTX"` now fails validation permanently with `"Token exists"`: [1](#0-0) , matching the behavior demonstrated in `IssueSameTokenNameAssert`: [6](#0-5)
