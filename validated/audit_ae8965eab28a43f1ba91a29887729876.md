### Title
Deposit mempool de-duplicates by `moveTx` fields only, letting a stuck malformed deposit permanently block a legitimate resubmission for the same Bitcoin move-tx - (File: `crates/sequencer/src/deposit_data_mempool.rs`)

### Summary
`DepositDataMempool::calc_tx_id` derives the mempool de-duplication key solely from `moveTx.{version, vin, vout, locktime}`, discarding `proof` and `shaScriptPubkeys` entirely. Because there is no eviction path for a deposit blob that keeps failing at actual block-inclusion time, a stuck malformed/invalid blob can permanently occupy the `calc_tx_id` slot for a given real Bitcoin move-transaction and cause `add_deposit_tx` to reject every later, correctly-proven resubmission of the same deposit as a duplicate.

### Finding Description
The binding that should hold is: *for every real Bitcoin move-to-vault transaction `T` that Clementine actually presigned, exactly one corresponding EVM Bridge deposit call eventually succeeds and credits cBTC* (`credited_cBTC_events(T) == 1`). This is broken when `credited_cBTC_events(T) == 0` forever because the mempool slot for `T` is permanently occupied by an unbankable blob.

Code path:
- `send_raw_deposit_transaction` (`crates/sequencer/src/rpc.rs:330-388`) simulates the deposit via `evm.get_call` against `BlockId::pending()` and, only on success, calls `deposit_mempool.add_deposit_tx(...)`.
- `add_deposit_tx` (`crates/sequencer/src/deposit_data_mempool.rs:119-136`) computes `txid = calc_tx_id(&req)` and does `pending_deposits.insert(txid.to_vec())`; if this returns `false` (already present), it returns `Ok(false)` without ever inspecting the new blob's `proof`/`shaScriptPubkeys`.
- `calc_tx_id` (`crates/sequencer/src/deposit_data_mempool.rs:146-164`) decodes only `call.moveTx` and hashes `version || vin || vout || locktime`, explicitly never touching `call.proof` or `call.shaScriptPubkeys`.
- `remove_deposits` (`crates/sequencer/src/deposit_data_mempool.rs:79-109`) is the only path that frees a `pending_deposits` slot, and it is driven by the block-builder's "successfully included" list — a blob that fails simulation at actual inclusion time (in the runner, using post-state-change context different from the RPC-time `eth_call`) is never passed to `remove_deposits` and stays in `accepted_deposit_txs`/`pending_deposits` indefinitely.

Exploit/failure flow: a blob1 for move-tx `T` passes the RPC-time `eth_call` simulation and is accepted into the mempool, but later fails simulation when the runner actually tries to include it in a block (e.g., because required light-client/proof state has since changed or blob1 carries subtly wrong `proof`/`shaScriptPubkeys` that only manifest as invalid at inclusion time). Since nothing removes it, it stays queued and retried every block, forever failing. A second submission, blob2, for the identical Bitcoin transaction `T` (same `version/vin/vout/locktime`, but corrected `proof`/`shaScriptPubkeys`) computes to the same `calc_tx_id`. `add_deposit_tx` sees the slot already occupied and returns `Ok(false)`, so `send_raw_deposit_transaction` returns the RPC error `"Deposit already pending in mempool"` and blob2 is never queued. The legitimate, correctly-proven deposit for `T` can never be resubmitted successfully as long as blob1 sits stuck, because the mempool has no mechanism to detect that the pending entry for `T` is unbankable and needs to be replaced.

None of the existing guards (`BitcoinVerifier::verify_transactions`, `Auth`, EVM `is_system_caller`, batch/commitment relation checks) address this, because the defect is purely in the sequencer's local, pre-inclusion mempool bookkeeping — it is one hop removed from consensus/proof logic and never reaches those checks for the blocked legitimate deposit.

### Impact Explanation
The real Bitcoin funds moved to the vault by transaction `T` are never credited as cBTC on L2, because the only mempool slot keyed to `T` is permanently occupied by a blob that can never pass block-inclusion simulation, and the legitimate corrected resubmission is rejected as a duplicate before it is ever queued. This matches the Critical category "funds permanently frozen" — the deposit is unbankable for as long as the sequencer process's in-memory `DepositDataMempool` retains the stuck entry (which, absent a sequencer restart clearing in-memory state, is indefinite). The blast radius is limited to the specific move-tx(es) affected, but is total for those deposits: no partial or delayed crediting is possible.

### Likelihood Explanation
Exploitability hinges on being able to get a blob accepted at RPC submission time (passing `evm.get_call` against `BlockId::pending()`) that will later, deterministically, fail simulation at actual runner inclusion time. I could not fully confirm the exact runner code path (`crates/sequencer/src/runner.rs` was not inspected within the tool budget) that determines whether/why a queued deposit can pass initial `eth_call` but permanently fail on inclusion, nor could I fully verify the on-chain `Bridge.sol` proof-verification logic to determine whether a malformed `proof`/`shaScriptPubkeys` blob could ever pass the RPC-time simulation in the first place. If `Bridge.sol`'s deposit validation deterministically and synchronously rejects any invalid proof (making the RPC-time `eth_call` fail immediately for any bad blob), the "stuck blob" precondition may never arise, which would significantly reduce or eliminate real-world likelihood. This uncertainty should be resolved by reading `crates/evm/src/evm/system_contracts/src/Bridge.sol`'s deposit function and `crates/sequencer/src/runner.rs` before treating this as confirmed-exploitable; the `calc_tx_id` design flaw itself (ignoring `proof`/`shaScriptPubkeys`) is confirmed and reproducible in isolation, but the end-to-end "permanently stuck first, permanently blocked second" scenario depends on runner behavior I was unable to fully trace in this session.

### Recommendation
Change `DepositDataMempool` de-duplication so that a permanently-failing entry can be evicted and replaced: e.g., track a full-blob hash or the pair (`calc_tx_id`, blob bytes) so a resubmission with different `proof`/`shaScriptPubkeys` for the same `moveTx` is treated as a distinct candidate rather than colliding forever; and/or add re-validation logic in the runner that evicts (`remove_deposits`-equivalent) deposits which fail inclusion simulation N consecutive times, allowing a corrected resubmission for the same `moveTx` to take over the slot.

### Proof of Concept
```rust
// crates/sequencer/src/deposit_data_mempool.rs (new test)
#[test]
fn test_stuck_deposit_blocks_corrected_resubmission() {
    let mut mempool = DepositDataMempool::new();
    // deposit_bad: valid moveTx fields, but proof/shaScriptPubkeys crafted so that
    // it will always fail at actual block-inclusion simulation (simulated here by
    // never being passed to remove_deposits).
    let deposit_bad = hex::decode(DEPOSIT_BAD_PROOF).unwrap();
    // deposit_good: identical moveTx.{version,vin,vout,locktime} bytes as deposit_bad,
    // but correct proof/shaScriptPubkeys.
    let deposit_good = hex::decode(DEPOSIT_GOOD_PROOF).unwrap();

    assert_eq!(
        DepositDataMempool::calc_tx_id(&deposit_bad).unwrap(),
        DepositDataMempool::calc_tx_id(&deposit_good).unwrap(),
        "calc_tx_id ignores proof/shaScriptPubkeys, so both blobs collide"
    );

    // deposit_bad is accepted into the mempool (simulates having passed RPC-time eth_call).
    assert!(mempool.add_deposit_tx(deposit_bad.clone()).unwrap());

    // deposit_bad is never included in a block, so remove_deposits is never called for it.

    // The corrected, legitimate blob for the SAME underlying Bitcoin transaction
    // is rejected as a duplicate, even though it would pass inclusion simulation.
    let added = mempool.add_deposit_tx(deposit_good.clone()).unwrap();
    assert_eq!(
        added, false,
        "BUG: legitimate corrected deposit is rejected because calc_tx_id collides \
         with the permanently-stuck malformed blob, freezing the underlying funds"
    );
    // Expected/fixed behavior: `added` should be `true` once dedup accounts for
    // proof/shaScriptPubkeys or the runner evicts permanently-failing entries.
}
```
Note: this test isolates and confirms the `calc_tx_id` collision defect deterministically. Fully proving the "permanently stuck at inclusion time" precondition end-to-end requires exercising `crates/sequencer/src/runner.rs`'s block-building/`remove_deposits` interaction, which was not verified in this session and should be validated separately.
