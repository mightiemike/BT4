### Title
`ensure_match_transaction_info` skips validating `state_checkpoint_hash`/`position_state_checkpoint_hash`, letting replay-verify accept a corrupted authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check that binds a freshly-executed `TransactionOutput` to the authenticated `TransactionInfo` stored in the ledger (accumulator leaf). It validates status, gas, write-set hash (`state_change_hash`), and event root hash, but its own inline comment states it deliberately **does not** validate `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash = CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but explicitly skips the state/hot-state checkpoint hash and the newer `position_state_checkpoint_hash` field that is part of `TransactionInfoV1` [2](#0-1) . The code comment itself flags this as a known integrity gap:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole state-commitment consistency check used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` to decide pass/fail for each transaction against the persisted, ledger-info-authenticated `TransactionInfo` [3](#0-2) . It's also referenced by `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` for similar replay/verification purposes.

Because the state checkpoint hash (and the "position state checkpoint hash" that presumably commits to a JMT/position-tree state root under the upcoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature) is never compared, a divergence purely in the committed state tree — one that doesn't show up in the write-set hash, events, gas, or status — is invisible to this checker. Since write-set hash equality only proves the *raw* KV write-set matches, but not that the *resulting Merkle/JMT root committed to storage* matches, this is a real gap between "the write-set operations are the same" and "the durable, authenticated state root is the same."

### Impact Explanation
This breaks the "Committed state that differs from the correct VM result... accepted as valid" and "authenticated proof/state-view output bound to the wrong version/root" invariants called out in the state-integrity gate. If any subsystem that derives `state_checkpoint_hash`/`position_state_checkpoint_hash` diverges from the local re-execution (e.g., due to a bug in state-checkpoint computation, hot-state hashing, or the position-tree feature), replay-verify tooling will silently report success, masking a real ledger state divergence rather than catching it — undermining the purpose of the check entirely on mainnet-relevant tooling paths.

### Likelihood Explanation
Medium: this is not remotely triggerable by an unprivileged network attacker in a single transaction — it requires an actual pre-existing divergence in checkpoint-hash computation (e.g., a future bug when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, or any hot-state/position-tree hashing regression) to matter. It is a latent verification gap: the code path that is supposed to be the safety net for exactly this class of bug is disabled by design, so the bug is not itself state corruption, but a broken proof/verification invariant that would fail to catch state corruption if it occurred.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s locally-computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on `txn_info`) against the values produced by local execution, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any consumer relying on `position_state_checkpoint_hash`) is enabled, exactly as the existing TODO comment recommends.

### Proof of Concept
Not independently reproducible as a live-network attack — it requires a genuine checkpoint-hash computation divergence to already exist elsewhere (e.g., a hot-state or position-tree hashing bug). Given that, the sequence is:
1. Local re-execution of a chunk of transactions during `replay_on_archive` produces a `TransactionOutput` whose write set, events, gas, and status match the archived `TransactionInfo`, but whose true state-checkpoint/position-state root (not checked) would differ.
2. `execute_and_verify` calls `ensure_match_transaction_info` at `storage/db-tool/src/replay_on_archive.rs:392-397`, which returns `Ok(())` because it never compares the checkpoint hash fields.
3. The tool reports a clean replay despite the underlying committed state root being wrong — exactly the scenario the code's own TODO comment warns about.

Note: I could not fully trace how/where `position_state_checkpoint_hash` is computed and populated (the "trading-native"/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature appears to be in-progress, gated behind `aptos_features.rs`), so I cannot confirm this is exploitable *today* in production versus being a documented gap for an in-flight feature. This should be treated as a verification-gap finding tied to the explicit TODO in the code rather than a demonstrated live state-corruption exploit.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
