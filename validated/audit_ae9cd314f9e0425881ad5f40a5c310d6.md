### Title
Missing Post-Swap Invariant Check in Bancor-Style TRC10 Exchange Allows Pool Value Drain via Floating-Point Rounding - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`java-tron`'s TRC10 Bancor-style exchange (`ExchangeCapsule.transaction`) computes swap output using floating-point `Math.pow` in `ExchangeProcessor` and only validates the trader's own minimum-received amount, but never checks that the pool's constant-product/value invariant (`firstTokenBalance * secondTokenBalance`, adjusted for the Bancor formula) is preserved or improved after a swap — directly analogous to the reported Aftermath Finance issue where `calc_swap_fixed_in`/`out` lacked an `invariant_after >= invariant` assertion.

### Finding Description
`ExchangeTransactionActuator.doValidate()` calls `exchangeCapsule.transaction(...)` and only enforces `anotherTokenQuant >= tokenExpected` [1](#0-0) . This check only protects the individual caller against slippage relative to their own supplied minimum; it does not protect the shared pool's economic invariant.

The actual swap math in the default (non-"hardened") path is computed with double-precision `Math.pow` in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [2](#0-1) , which is inherently susceptible to floating-point rounding error, exactly the kind of numerical approximation issue that caused the invariant regression in the original report (there via Newton's method iteration limits, here via floating point `pow`). After the swap, `ExchangeCapsule.transaction` only asserts that resulting balances are non-negative in the "hardened" branch — it never recomputes and compares the pool's bonding-curve invariant before and after the trade [3](#0-2) .

By contrast, `ExchangeWithdrawActuator` explicitly implements a "precision" guard comparing the BigDecimal-exact proportional withdrawal against the rounded value and rejects the transaction if it drifts by more than 0.01% [4](#0-3) . No equivalent invariant/precision safeguard exists for the swap path (`ExchangeTransactionActuator`), which is the highest-frequency, most attacker-controlled operation (arbitrary sell token/quant chosen by an unprivileged caller). `ExchangeProcessorTest.testStrictMath` even demonstrates that legacy (`useStrictMath=false`) and strict (`useStrictMath=true`)/hardened results diverge for identical inputs [5](#0-4) , confirming that floating-point divergence in the swap formula is a real, observable phenomenon in this codebase, not merely theoretical.

The mitigation for arithmetic-safety issues here (`allowHardenExchangeCalculation`, `SafeExchangeProcessor`, `StrictMathWrapper`) only guards against overflow/underflow and negative balances [6](#0-5) ; it does not add any check equivalent to the report's recommended fix ("Check whether the invariant is decreased after the swap"). Even the "hardened" `SafeExchangeProcessor` path, which uses `BigDecimal`, still only guards against negative balances/overflow, not overall pool-value preservation.

### Impact Explanation
An unprivileged caller of `ExchangeTransactionContract` can execute a sequence of swaps (sizes/directions chosen adversarially, exploiting rounding in `Maths.pow`/`Math.pow`) that leave the exchange pool's `firstTokenBalance`/`secondTokenBalance` product/value strictly worse off than before the trade, without any on-chain check preventing it. Because `ExchangeCapsule` state is shared across all users of a given `exchangeId`, repeated exploitation extracts value from other liquidity participants (accounting/economic-invariant violation), which matches the "Underpriced public work / accounting divergence" impact class.

### Likelihood Explanation
The swap function is fully public and unprivileged — any account can submit `ExchangeTransactionContract` transactions with attacker-chosen `tokenId`/`quant` against any existing exchange pool [7](#0-6) . The only gating factor is whether `allowHardenExchangeCalculation`/hardened math is active network-wide; the legacy floating-point path (`ExchangeProcessor` with `useStrictMath=false`) remains reachable and is demonstrably imprecise per the divergence shown in `ExchangeProcessorTest`. No invariant assertion exists in either the legacy or hardened path, so likelihood is not eliminated even under hardening — hardening only prevents overflow/negative balances, not invariant decrease.

### Recommendation
Add an explicit post-swap invariant check in `ExchangeCapsule.transaction` (or in the actuator's `doValidate`/`execute`), computing the pool's pre-swap and post-swap bonding-curve value (e.g., `firstTokenBalance * secondTokenBalance` scaled appropriately for the Bancor relay-token model) and rejecting the transaction (`ContractValidateException`) if the post-swap invariant is smaller than the pre-swap invariant beyond the expected/declared fee. This mirrors the recommended fix from the source report: "Check whether the invariant is decreased after the swap."

### Proof of Concept
Conceptual reproduction, following the pattern in `ExchangeProcessorTest.testStrictMath` [8](#0-7) :
1. Create an `ExchangeCapsule` pool with balances `(firstTokenBalance, secondTokenBalance)`.
2. Call `exchangeCapsule.transaction(sellTokenId, sellQuant, useStrictMath=false, hardenedCalc=false)` for a `sellQuant`/balance ratio chosen to maximize floating-point `Math.pow` rounding error (as in `ExchangeProcessorTest.testStrictMath`, where legacy and strict results differ for identical inputs).
3. Compute `oldValue = firstTokenBalance * secondTokenBalance` before the call and `newValue = newFirstTokenBalance * newSecondTokenBalance` after.
4. Observe `newValue < oldValue` (invariant decreased) even though `ExchangeTransactionActuator.doValidate()`'s only check (`anotherTokenQuant >= tokenExpected`) passes, because that check only bounds the trader's own minimum received amount, not the pool's aggregate value.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
