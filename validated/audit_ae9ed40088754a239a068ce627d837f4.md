### Title
`DeleteAccountAction` sends account funds to an unchecked `beneficiary_id`, permanently burning them if the beneficiary does not exist - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` transfers the deleted account's entire remaining balance to a caller-supplied `beneficiary_id` without verifying that account exists. The transfer is implemented as a refund receipt (`predecessor_id == "system"`), and refund receipts that fail (e.g. because the target account does not exist) have their deposit permanently burned rather than returned to anyone. This mirrors the reported class of bug where a mint/transfer destination is never validated, resulting in unrecoverable loss of funds.

### Finding Description
When `DeleteAccount` executes, the runtime takes the account's current balance and pushes a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`, then immediately deletes the account: [1](#0-0) 

The only validation ever performed on `beneficiary_id` is a syntactic `InvalidAccountId` check at transaction verification time — there is no check that the account actually exists on chain: [2](#0-1) 

The balance transfer to `beneficiary_id` is generated as a refund receipt (predecessor is the special `system` account), and refunds are documented to be free of gas but unrecoverable on failure: [3](#0-2) 

This is directly enforced in the runtime: when a receipt whose predecessor is `system` (i.e. a refund receipt) fails, its deposit is added to `other_burnt_amount` instead of being refunded again: [4](#0-3) 

A refund receipt targeting a non-existent named account fails with `AccountDoesNotExist` (transfers/refunds are never allowed to implicitly create a named account), as confirmed by the test asserting a refund to a missing account fails and the account is not created: [5](#0-4) 

Consequently, if a transaction signer (or contract issuing `promise_batch_action_delete_account`) supplies a `beneficiary_id` that is syntactically valid but does not exist — e.g. a typo, a mistyped sub-account, or an account that was itself deleted between construction and execution of the receipt — the entire remaining balance of the deleted account is silently and permanently burned instead of being credited to anyone.

### Impact Explanation
This causes concrete, permanent loss of funds: the deleted account's full remaining NEAR balance is burned rather than delivered to any account, with no way to recover it. This is triggerable by any unprivileged transaction signer (deleting their own account) or by a contract executing `promise_batch_action_delete_account`, exactly matching the "permanently frozen/destroyed funds" impact bar, analogous to the original ERC20 mint-to-unknown-address report where an unchecked receiver address results in irrecoverable loss of value.

### Likelihood Explanation
Likelihood is driven by user/relayer/contract error: a typo'd or stale `beneficiary_id` is a plausible real-world mistake, especially in automated flows (relayers, meta-transactions, or contracts computing a beneficiary programmatically) where a wrong account id can be supplied unintentionally. No special privilege is required — any account owner performing `DeleteAccount`, or any contract calling `promise_batch_action_delete_account`, can trigger this loss.

### Recommendation
Before generating the balance-refund receipt for `DeleteAccount`, validate that `beneficiary_id` refers to an existing account (or explicitly document/require using an account known to exist, and consider failing the `DeleteAccount` action itself with an `ActionErrorKind` such as `AccountDoesNotExist` for the beneficiary rather than allowing the delete to proceed and silently burning the balance in a doomed refund receipt).

### Proof of Concept
1. Create account `victim.near` funded with `N` NEAR.
2. `victim.near` submits `DeleteAccountAction { beneficiary_id: "typo-target.near" }` where `typo-target.near` does not exist (as demonstrated for transfers/refunds in `refund_may_not_create_universal_account` and `test_refund_on_send_money_to_non_existent_account`, refunds to non-existent accounts fail rather than create them).
3. `action_delete_account` removes `victim.near` and enqueues a `Receipt::new_balance_refund("typo-target.near", N)` (`runtime/runtime/src/actions.rs:380-386`).
4. That refund receipt executes with `predecessor_id == "system"`; since `typo-target.near` does not exist, the transfer action fails with `AccountDoesNotExist`.
5. Because the failing receipt is a refund (`runtime/runtime/src/lib.rs:1047-1055`), its deposit `N` is added to `other_burnt_amount` and permanently destroyed — no account, including `victim.near` or `typo-target.near`, ever receives it.

    /// The other half of the old gate, untouched by the relaxation: refunds are
    /// free, so they must not create an account, a `0u` one included.
    #[test]
    fn refund_may_not_create_universal_account() {
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {
            panic!("the refund receipt must produce exactly one outcome, got {:?}", result.outcomes)
        };
        assert_matches!(
            &outcome.outcome.status,
            ExecutionStatus::Failure(TxExecutionError::ActionError(err))
                if matches!(err.kind, ActionErrorKind::AccountDoesNotExist { .. }),
            "a refund to a missing `0u` id must fail with AccountDoesNotExist",
        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
