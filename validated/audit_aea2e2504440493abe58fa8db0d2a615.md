## Finding Confirmed

The exploit path described is real. Here's the trace:

### Root cause

`WriteSetV0.extensions` (and `hotness`) are marked `#[serde(skip)]`: [1](#0-0) 

This means the field is **never serialized to bytes in the first place** — not merely dropped on decode. The comment even documents the intent: *"Skipped from serde so `TransactionInfo` hashes and the on-disk WriteSet format are unaffected."*

`WriteSetSchema` (used by `write_set_db`) encodes/decodes `WriteSet` via plain `bcs::to_bytes` / `bcs::from_bytes`: [2](#0-1) 

So any `WriteSet` round-tripped through `write_set_db` (i.e. `commit_write_sets` → `get_write_sets`/`get_write_set`) comes back with `extensions == Vec::new()`, regardless of what was populated via `add_native_positions` at execution time: [3](#0-2) [4](#0-3) 

### Where this bites: crash-recovery replay

`replay_position_after_snapshot` is invoked from `init_native_position` on every DB open whenever the persisted position-merkle snapshot lags the ledger's `OverallCommitProgress` (a normal occurrence, since `commit_native_position` uses buffered, non-sync commits by default): [5](#0-4) [6](#0-5) 

The replay reads its source data exclusively from `write_set_db().get_write_sets(...)` and calls `native_position_iter()` on the disk-reloaded `WriteSet`s: [7](#0-6) 

Since `native_position_iter()` depends on `extensions`, which is always empty for any `WriteSet` loaded from `write_set_db`, `pending_leaf_updates` is always empty for this path, and the function silently returns `Ok(())` without ever extending the Merkle tree — even though the corresponding KV values were already correctly committed to `position_db` by `commit_native_position` using the *original* in-memory `WriteSet` (before it ever touched storage): [8](#0-7) 

### Impact

After a validator/fullnode crash or restart that lands in the window between a position KV commit and its buffered Merkle-snapshot flush, `replay_position_after_snapshot` can never recover the missing leaf updates. The position Merkle tree's `latest`/`last_checkpoint` state becomes permanently stale relative to `position_db`'s actual committed key/value data for the affected `StateKey`s. Any subsequent state proof or authenticated response derived from the position Merkle root (`ProvablePositionStateSummary`, `PositionSlot.value_hash`, leaf iteration in `get_state_value_chunk_iter` with `StateKind::Position`) is bound to the wrong root/version for those keys — a genuine proof-integrity/authenticated-response corruption triggered purely by an unprivileged transaction that uses the position-native module (`add_native_positions`) combined with the node's own ordinary restart/crash-recovery code path (not an operator mistake).

### Title
Position-native `WriteSet` extensions are never persisted to `write_set_db`, causing crash-recovery replay to silently skip native-position Merkle leaf updates — ([File: types/src/write_set.rs], [File: storage/aptosdb/src/db/aptosdb_native_position.rs])

### Summary
`WriteSetV0.extensions` (carrying `Extension::NativePosition`) is `#[serde(skip)]`, so it is never written to the `write_set_db` on-disk schema. `replay_position_after_snapshot`, the crash-recovery path that catches the position Merkle tree up to the KV tip on every DB open, sources its updates exclusively from `write_set_db().get_write_sets(...)`, so it can never see any native-position writes and silently no-ops whenever a catch-up is actually needed.

### Finding Description
`add_native_positions` populates `WriteSetV0.extensions` at VM-output time. `commit_native_position` correctly persists the KV values/stale-index using this in-memory `WriteSet` before it is ever serialized. Separately, `commit_write_sets` persists the same `WriteSet` to `write_set_db` via BCS, which drops `extensions` entirely due to `#[serde(skip)]`. On restart, if the position-merkle snapshot lags the ledger tip (the normal buffered-commit case), `replay_position_after_snapshot` reconstructs missing leaf updates solely from `write_set_db`-loaded `WriteSet`s via `native_position_iter()`, which is always empty for these reloaded objects, so the replay is a no-op regardless of how many position writes actually occurred in the gap.

### Impact Explanation
The position Merkle tree's root/leaves become stale relative to the already-committed `position_db` KV state for any keys written in the un-flushed gap. Any state-proof or state-view response built from the position Merkle summary after such a restart is bound to the wrong (stale) root/version for the affected keys — matching "Wrong accumulator root/Merkle proof accepted as valid" and "Authenticated API or state-view output bound to the wrong version, object, or proof context."

### Likelihood Explanation
Triggerable by any ordinary transaction exercising the position-native module plus a normal node restart/crash within the routine buffered-commit lag window — no privileged access or malicious peer behavior required.

### Recommendation
Do not rely on `write_set_db` for native-position replay. Either stop skipping `extensions` in the on-disk `WriteSet` format used for position replay (e.g., persist a dedicated log analogous to `PositionValueSchema`/`StalePositionValueIndex` and replay from that), or make `replay_position_after_snapshot` read from `position_db`'s own persisted KV/stale-index history for the version range instead of `write_set_db`.

### Proof of Concept
1. Build a `WriteSetV0` and call `add_native_positions` with a populated map for a `StateKey`.
2. Serialize via `WriteSetSchema::encode_value` (`bcs::to_bytes`) and decode via `decode_value`.
3. Assert `decoded.native_position_iter().count() == 0` while the original had entries — confirming extensions never survive the round trip.
4. Trace `replay_position_after_snapshot` (`storage/aptosdb/src/db/aptosdb_native_position.rs:250-266`) to show it sources exclusively from `write_set_db().get_write_sets(...)`, which returns exactly such round-tripped `WriteSet`s.

impl ValueCodec<WriteSetSchema> for WriteSet {
    fn encode_value(&self) -> Result<Vec<u8>> {
        bcs::to_bytes(self).map_err(Into::into)
    }

    fn decode_value(data: &[u8]) -> Result<Self> {
        // TODO(HotState): we could simply use `bcs::from_bytes` for everything once the latest
        // release branch does not write LegacyWriteSetV1Payload and forge-compat test would not
        // fail in CI.
        match data.first() {
            Some(&1) => match bcs::from_bytes::<WriteSet>(data) {
                Ok(ws) => Ok(ws),
                // Legacy V1 payload lacks the trailing `extensions` field, so the new decoder
                // runs out of bytes while reading it. Any other error indicates real corruption
                // and should propagate.
                Err(bcs::Error::Eof) => {
                    let legacy: LegacyWriteSetV1Payload = bcs::from_bytes(&data[1..])?;
                    let mut ws = WriteSet::V0(legacy.value);
                    ws.add_hotness(legacy.hotness);
                    Ok(ws)
                },
                Err(e) => Err(e.into()),
            },
            _ => bcs::from_bytes::<WriteSet>(data).map_err(Into::into),
        }
    }
}
