Replay-verify's `ensure_match_transaction_info` silently skips checkpoint-hash validation, letting a corrupted/diverged state root pass authenticated replay verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used by Aptos's replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that re-executing a transaction against a `DbReader`-backed state view reproduces the exact `TransactionInfo` that is committed and Merkle-accumulated on disk (and thus authenticated by validator signatures via `LedgerInfo`). The comparator checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but by its own acknowledged `TODO`, it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the resulting global state (Sparse-Merkle/Jellyfish-Merkle) root. [2](#0-1) [3](#0-2) 

### Finding Description
`ensure_match_transaction_info` validates four properties between a locally re-executed `TransactionOutput` and the archived `TransactionInfo`: execution status, gas used, `write_set_hash == txn_info.state_change_hash()`, and `event_root_hash == txn_info.event_root_hash()`. [4](#0-3) 

It deliberately omits comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the hashes committing to the Sparse Merkle / Jellyfish Merkle state root that the archived `TransactionInfoV0`/`V1` carries as proof of the post-transaction global state. [5](#0-4) [1](#0-0) 

This comparator is the sole correctness gate used by `replay_on_archive`'s `Verifier::execute_and_verify`, which re-executes chunks of archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` against the `expected_txn_infos` pulled from the target archive DB: [6](#0-5) 

It is also used by `aptos-debugger` (`aptos_debugger.rs`) for the same style of offline replay verification. In both cases the entire point of the tool is to detect divergence between locally computed execution and the trusted, ledger-info-signed history stored in an (possibly backup-restored, possibly tampered, possibly corrupted) archive database. Since the state-checkpoint hash fields are silently ignored, a `TransactionInfo` whose `state_checkpoint_hash` differs from what correct re-execution would produce — e.g., due to storage/restore corruption, a JMT/Merkle bug, non-determinism, or a maliciously altered archive — will still pass `ensure_match_transaction_info` as long as gas, status, write-set bytes, and events match. The tool will report "replay verified" even though the authenticated state root is wrong.

Note that the actual live consensus/commit path (`DoStateCheckpoint::run` / `DoLedgerUpdate::run`) does independently compute and does cross-check `state_checkpoint_hash`/`hot_state_checkpoint_hash` against `known_state_checkpoints` when provided: [7](#0-6) 

So this bug does not corrupt the primary commit/consensus path itself — the gap is specifically in the standalone replay-verification comparator relied upon by operators/tooling to detect state divergence after the fact (e.g. auditing backups, validating archive integrity, detecting non-determinism bugs). This matches the "restore flows" / "replay" integrity-pivot category: a proof-bearing/committed value (`state_checkpoint_hash`) is allowed to silently diverge from the correct VM result during a replay-verification flow that exists precisely to catch such divergence.

### Impact Explanation
Replay-verify tooling is the primary defense used to certify that an archived/backed-up ledger's committed state precisely matches deterministic re-execution, and it's frequently used before trusting a restored archive or diagnosing state-root divergence bugs (hard forks, non-determinism, storage bugs). Because the comparator ignores `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a corrupted or manipulated `TransactionInfo.state_checkpoint_hash` in the target DB (which is exactly the kind of corruption these tools exist to catch) will not be flagged, as long as write-set bytes/events/status/gas happen to match. This is a proof-integrity blind-spot: an authenticated field (bound into the transaction-accumulator leaf hash, and ultimately signed via `LedgerInfo`) is treated as trusted without verification in the one place designed to independently verify it. This can mask ledger-state corruption (e.g., during a hard-fork-only divergence, backup/restore data corruption, or a subtle JMT bug) that would otherwise be silently accepted as "verified."

### Likelihood Explanation
The path is unprivileged: `replay_on_archive` and `aptos-debugger` are ordinary operator/tooling entry points that take a local or downloaded target DB and replay a version range — no special permissions beyond running the tool are required. The bug triggers whenever the archived `state_checkpoint_hash` differs from the correctly recomputed one while other fields coincidentally match, which is plausible for any bug/corruption localized to state-tree/storage layers (as opposed to write-set generation) — precisely the scenario replay-verify is meant to catch. The code's own `TODO(trading-native)` comment explicitly confirms this exact gap and names `replay_on_archive` as affected.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when present/expected) between the locally computed checkpoint output and the archived `TransactionInfo`, gating on whichever feature flags govern their presence (e.g. `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) so replay-verify tooling cannot report success on a state-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
