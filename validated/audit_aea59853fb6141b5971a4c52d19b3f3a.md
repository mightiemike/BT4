### Title
Per-surface rate limiter duplication allows aggregate TVM-executing throughput to exceed configured per-operation ceiling - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/RateLimiterContainer.java])

### Summary
`RateLimiterContainer` keys rate limiters by `KEY_PREFIX_HTTP + name` and `KEY_PREFIX_RPC + name` independently, so the HTTP servlet `TriggerConstantContractServlet` and the gRPC method `protocol.Wallet/TriggerConstantContract` — which both invoke the same `Wallet.triggerConstantContract` TVM-executing backend — get two separate, independently-configured quota buckets rather than one shared quota for the operation. An operator who configures a restrictive per-endpoint limit on one surface to protect the shared TVM/executor/DB backend does not automatically get that protection on the other surface, since each surface's `@PostConstruct`/`init()` registration path (`RateLimiterServlet.addRateContainer`, `RateLimiterInterceptor.init`) populates the container with its own key.

### Finding Description
`RateLimiterServlet.service()` looks up the per-endpoint limiter via `container.get(KEY_PREFIX_HTTP, getClass().getSimpleName())` [1](#0-0) , while `RateLimiterInterceptor.interceptCall()` looks it up via `container.get(KEY_PREFIX_RPC, call.getMethodDescriptor().getFullMethodName())` [2](#0-1) . `RateLimiterContainer.get`/`add` simply concatenate `prefix+method` as the map key [3](#0-2) , so `http_TriggerConstantContractServlet` and `rpc_protocol.Wallet/TriggerConstantContract` are two fully independent buckets even though both dispatch into the identical `Wallet.triggerConstantContract(...)` code path (as seen in `TriggerConstantContractServlet.doPost`) [4](#0-3) .

The `reference.conf` documentation explicitly frames per-component `http` and `rpc` entries as the mechanism for capping expensive endpoints, and shows examples for both surfaces separately, confirming this is the intended/supported administration mechanism, not a misconfiguration [5](#0-4) . If an operator (or the default 1000-qps `DefaultBaseQqsAdapter` fallback, which is applied identically and independently per surface when nothing is configured) intends a ceiling of N qps for the constant-contract TVM execution path, the actual achievable aggregate is up to 2N (N via HTTP + N via gRPC), because nothing ties the two buckets together.

The only shared backstop is `GlobalRateLimiter`, a process-wide static `RateLimiter` plus per-IP cache used identically from both `RateLimiterServlet.service` and `RateLimiterInterceptor.interceptCall` [6](#0-5) . This does bound total aggregate request rate across all endpoints/surfaces combined, but it is a blunt, endpoint-agnostic global cap — it cannot substitute for a per-operation ceiling that an operator specifically configured to protect the shared TVM/executor/DB resource from one heavy call type, since the global QPS budget is shared with every other RPC/HTTP call on the node. An attacker splitting `TriggerConstantContract` traffic evenly between HTTP and gRPC therefore can consume up to double the per-surface-configured quota for that specific expensive operation before hitting only the coarse global ceiling (or the per-IP global ceiling, avoidable by using multiple source IPs).

### Impact Explanation
This is a DoS-via-RPC-API class issue: aggregate CPU/TVM/DB load from `triggerConstantContract` calls can reach up to 2x the ceiling an administrator configured for a single surface, before being limited only by the coarse, shared `GlobalRateLimiter`. On a node where the operator relies on per-endpoint tuning (as `reference.conf` documents and recommends) to protect the shared TVM engine/executor from being saturated by this specific expensive call, this control can be substantially undermined, degrading node responsiveness/stalling processing of legitimate requests.

### Likelihood Explanation
No privileged access is required — any anonymous HTTP and gRPC client can concurrently call `TriggerConstantContractServlet` and `protocol.Wallet/TriggerConstantContract`. The attack costs nothing (constant-contract calls are read-only queries, no on-chain fee/energy is charged since no transaction is broadcast). Exploitability depends on the operator having configured (or relying on the default 1000 qps) a per-operation ceiling that is meant to reflect the operation's total safe throughput on the shared backend; the two independent buckets always exist by design, so the gap is present out of the box, but its practical severity scales with how aggressively the operator has tuned each surface's limiter relative to `GlobalRateLimiter`'s configured QPS.

### Recommendation
Unify per-operation rate limiting for logically-equivalent HTTP/gRPC endpoints: key `RateLimiterContainer` entries by the underlying operation (e.g. a shared `TriggerConstantContract` key) rather than by transport-specific class/method name, or have both `RateLimiterServlet` and `RateLimiterInterceptor` consult a single shared limiter instance for known operation-pairs. Alternatively, document and enforce that operators must configure matching, combined-aware quotas for both `http` and `rpc` entries of the same operation, and consider adding an explicit "logical operation" grouping in `RateLimiterInitialization` so a single configured qps/permit value is enforced across both KEY_PREFIX_HTTP and KEY_PREFIX_RPC buckets for the same backend call.

```
#   http:  { component = "TriggerConstantContractServlet", strategy = "QpsRateLimiterAdapter", paramString = "qps=5" }
#   rpc:   { component = "protocol.Wallet/TriggerConstantContract", strategy = "QpsRateLimiterAdapter", paramString = "qps=5" }
# Intent: cap constant-contract TVM execution at 5 qps total on this node.

# Concurrent load test:
for i in $(seq 1 5); do
  curl -s -X POST http://NODE:8090/wallet/triggerconstantcontract -d '{...}' &
done
# simultaneously
for i in $(seq 1 5); do
  grpcurl -plaintext -d '{...}' NODE:50051 protocol.Wallet/TriggerConstantContract &
done

# Expected (buggy) result: both surfaces accept ~5 qps each => ~10 qps aggregate
# TVM execution load, exceeding the single-surface 5 qps design ceiling,
# bounded only by GlobalRateLimiter's separately-configured global QPS.
```
JUnit-level verification: instantiate `RateLimiterContainer`, add a `QpsRateLimiterAdapter("qps=5")` under `("http_", "TriggerConstantContractServlet")` and a second, independent `QpsRateLimiterAdapter("qps=5")` under `("rpc_", "protocol.Wallet/TriggerConstantContract")`; drive `acquirePermit` on both concurrently and observe the combined accepted throughput is ~10 qps, not 5 qps, confirming `RateLimiterContainer.get` returns two unlinked instances for the same underlying wallet operation.

```java
public class GlobalRateLimiter {

  private static double QPS = Args.getInstance().getRateLimiterGlobalQps();

  private static double IP_QPS = Args.getInstance().getRateLimiterGlobalIpQps();

  private static Cache<String, RateLimiter> cache = CacheBuilder.newBuilder()
      .maximumSize(10000).expireAfterWrite(1, TimeUnit.HOURS).build();

  private static RateLimiter rateLimiter = RateLimiter.create(QPS);

  public static boolean tryAcquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null || !r.tryAcquire()) {
        return false;
      }
    }
    return rateLimiter.tryAcquire();
  }

  public static boolean acquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null) {
        return false;
      }
      r.acquire();
    }
    rateLimiter.acquire();
    return true;
  }

  public static boolean acquirePermit(RuntimeData runtimeData) {
    return Args.getInstance().isRateLimiterApiNonBlocking()
        ? tryAcquire(runtimeData)
        : acquire(runtimeData);
  }
```
