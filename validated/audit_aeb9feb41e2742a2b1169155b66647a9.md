### Title
Local-clock-dependent reorg-timing check in `check_parent_tenure_choice` causes signers to disagree on whether a tenure reorg is permitted - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
The signer-side tenure-reorg gate `SortitionData::check_parent_tenure_choice` decides whether a new miner is allowed to reorg a prior tenure by comparing a duration computed from two node-local timestamps against the configured `first_proposal_burn_block_timing` threshold. Because these timestamps (`get_burn_block_receive_time`, `approved_time`) are recorded independently by each signer based on when *that signer* observed events, not on any value carried in the burn chain or agreed upon by the network, different signers can compute durations that fall on opposite sides of the threshold for the exact same reorg attempt. This breaks the equality that "all honest signers reach the same reorg verdict for the same tenure change," producing a signer-set split and a temporary tip disagreement.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  is invoked whenever a miner's tenure-change block does not build off the most recently known sortition (i.e., it proposes a reorg). For each reorged tenure that already mined a block, the function computes:

```
proposal_to_sortition = sortition_state_received_time - approved_at
```

using `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` and the locally stored `local_block_info.approved_time`, then compares it against `first_proposal_burn_block_timing`: [2](#0-1) 

Both timestamps are purely local bookkeeping values:
- `sortition_state_received_time` is stamped by each signer independently at the moment *that signer's* stacks-node/signer process received/recorded the new burn block, via `get_burn_block_receive_time` (referenced in [3](#0-2) ).
- `approved_time` is stamped when *that signer* pre-committed/approved the earlier block, not a network-agreed value.

Because signers do not share a synchronized clock and do not receive burn blocks/proposals at identical wall-clock times (network latency, peering topology, load), the computed `proposal_to_sortition` value differs from signer to signer for the same underlying event. When the true timing is close to the `first_proposal_burn_block_timing` boundary, some signers will compute a value just under the threshold (declaring the reorg "poorly timed" and thus ALLOWED, marking the tenure superseded) while others compute a value just over it (declaring the reorg DENIED, returning `RejectReason::ReorgNotAllowed` from `validate_tenure_change_payload`, see [4](#0-3) ).

This is a genuine boundary-straddling divergence, not a majority-driven event: an attacking miner only needs to time its competing block-commit/tenure-change broadcast so that its arrival lands near the configured threshold across the signer population (which is realistic given the wide variance in configured values, e.g. default `first_proposal_burn_block_timing_secs = 60` documented in [5](#0-4) ). No collusion or majority signer control is required — the miner simply exploits normal network-latency variance among honest signers.

### Impact Explanation
When signers disagree on whether a reorg is permitted:
- A subset of signers will sign/approve blocks descending from the reorging tenure (because they judged the reorg as permitted / the older tenure "poorly timed"), while another subset rejects those same blocks and instead continue to expect blocks from the original tenure.
- This directly produces a temporary tip disagreement across the signer set: two groups of signers endorse two different chain views for the same burn view, until the block-proposal/tenure timeout logic eventually resolves it (or it is resolved by whichever branch gathers enough weighted signatures first).
- This matches the specified High-severity impact category: "a minority-triggerable ... static-validation divergence ... temporary tip disagreement," since the discrepancy stems from independently-computed local timestamps rather than a shared consensus value, and can be nudged by an unprivileged miner controlling only proposal/broadcast timing.

### Likelihood Explanation
This is triggerable by any single miner (no signer-key or majority-signer control needed) simply by carefully timing tenure-change/reorg attempts so that the elapsed time between block-approval and burn-block-receipt lands near `first_proposal_burn_block_timing` for a meaningful fraction of the signer population. Because different signers naturally have differing message-propagation and processing delays, "landing near the threshold" for some signers while other signers see a value on the other side of it is a normal and reproducible occurrence, not an edge case requiring 51% control.

### Recommendation
Base the reorg-timing decision on a value that all signers can agree comes from the same source of truth — e.g., a burnchain-derived timestamp (already available as `burn_header_timestamp` on `SortitionData`) compared against another chain-derived value, rather than each signer's independently recorded wall-clock receipt/approval time. Alternatively, require the timing check to also be validated/enforced by the stacks-node against consensus-visible burn-block timestamps rather than signer-local receipt times, so that all signers converge on the identical accept/reject verdict for a given reorg attempt.

### Proof of Concept
1. Miner A produces tenure T1's first (and only) block; different signers approve/pre-commit it at slightly different local times due to normal network propagation (`approved_time` recorded per-signer).
2. A new sortition happens (tenure T2) with a burn block whose receipt/observation is likewise skewed across signers (`get_burn_block_receive_time` recorded per-signer).
3. Miner B (winner of T2, or a colluding/adjacent miner racing a tenure-change) issues a tenure-change reorging T1, timed so that `sortition_state_received_time - approved_at` computed in `check_parent_tenure_choice` ( [2](#0-1) ) is just below `first_proposal_burn_block_timing` for roughly half the signer set and just above it for the rest.
4. Signers on one side of the boundary mark T1 superseded and sign blocks building on the reorg; signers on the other side return `RejectReason::ReorgNotAllowed` ( [6](#0-5) ) and continue expecting T1's continuation.
5. The signer set is now split on the canonical tip until additional timeouts/blocks force resolution, demonstrating a validation-verdict divergence triggerable by ordinary network timing variance rather than a majority attack.

# Reorg protection window. Measures the time between when the first block
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60
