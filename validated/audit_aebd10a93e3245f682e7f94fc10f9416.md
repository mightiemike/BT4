### Title
`BuildOutboundsFromReceipt` aborts the whole receipt on one bad log, silently dropping already-decoded, valid withdraw outbounds from earlier in the same EVM transaction — (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`BuildOutboundsFromReceipt` iterates over every log in an EVM receipt looking for `UniversalTxOutboundEvent` emissions from the Universal Gateway, decoding each into an `OutboundTx`. Instead of skipping a single problematic log with `continue`, the loop uses `return nil, err` on decode failure, an "outbound disabled for chain" check, or a token-config lookup miss. This discards the entire `outbounds` slice already accumulated for that transaction and aborts processing of any remaining logs, even though the underlying EVM state change (the Gateway withdraw/burn) for all those events has already been committed.

### Finding Description
`BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:16-105`) walks `receipt.Logs`, filters for Gateway-emitted `UniversalTxOutboundEvent` logs, and for each one: [1](#0-0) 
```
event, err := types.DecodeUniversalTxOutboundFromLog(lg)
if err != nil {
    return nil, fmt.Errorf(...)
}
outboundEnabled, err := k.uregistryKeeper.IsChainOutboundEnabled(ctx, event.ChainId)
if err != nil { return nil, ... }
if !outboundEnabled { return nil, fmt.Errorf(...) }
```
and then a token-config lookup: [2](#0-1) 

A single `UniversalPayload` execution can trigger a contract that internally performs multiple distinct Gateway withdraws to different destination chains/tokens in one call (a "batch withdraw" helper), producing multiple `UniversalTxOutboundEvent` logs in one receipt. If any one of these logs corresponds to a chain that is disabled, or a PRC20/token pairing missing from `x/uregistry` (`GetTokenConfigByPRC20` returning `collections.ErrNotFound`), the function returns an error and discards **all** previously appended `outbounds` — including ones for enabled chains that were already validated and built earlier in the log list — and never even inspects subsequent logs.

This function is invoked from both the direct-`MsgExecutePayload` path and the inbound-execution path, always **after** the EVM call itself has already succeeded and its state changes are (or are about to be) committed: [3](#0-2) [4](#0-3) 

In the inbound `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` execution paths, the failure of `AttachOutboundsToExistingUniversalTx` is caught but only recorded as `u.RevertError` on the UTX — execution is not rolled back and the function returns `nil`: [5](#0-4) 

In the direct `MsgExecutePayload` path, `CreateUniversalTxFromReceiptIfOutbound` returning an error propagates up and reverts the whole Cosmos tx (`msg_execute_payload.go:116-118`), but by then the underlying `CallUEAExecutePayload` EVM call (`msg_execute_payload.go:87`) has already run in the same state-machine context as everything committed by `ctx` at that point — the gas fee has already been deducted and, depending on the EVM sub-call path (e.g. `writeCache()` committed earlier in the CEA smart-contract branch), Gateway-side withdraw/burn accounting has already taken effect for **all** the batched withdraw events, not just the failing one.

### Impact Explanation
This is the same bug class as the Debita `updateFunds` M-21 finding: a loop over a set of independently-valid items uses `return` instead of `continue`/`error-isolation`, so one bad element (disabled destination chain, missing token config, or malformed log) causes legitimate, already-processed elements to be silently dropped. Here the dropped elements are `OutboundTx` records — the *only* mechanism that schedules TSS-signed release of funds on the destination chain. Because the corresponding Gateway-side withdraw/burn on Push Chain has already executed (or, in the CEA smart-contract branch, is committed via `writeCache()` before this stage), the funds tied to the other, unrelated, valid withdraw events in the same receipt become permanently stranded — burned/locked on Push Chain with no `OutboundTx`/`PendingOutbounds` entry ever created to trigger their release on the external chain. This is a permanent loss/freezing of user funds, matching the "Allowed Impact Gate" criteria (permanent freezing / loss of user funds via a state-transition bug in the universal execution / outbound-creation flow), triggerable by an ordinary unprivileged user submitting a normal payload through a batching helper contract — no privileged actor or malicious validator required.

### Likelihood Explanation
Requires only an ordinary user to submit a `MsgExecutePayload` (or an inbound `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD`) whose target contract triggers ≥2 Gateway withdraw calls in one EVM transaction, where at least one destination chain/token pairing is disabled or unconfigured while another is valid. This is plausible in real usage (e.g., third-party "router"/"multi-withdraw" contracts built on top of the Gateway) and requires no validator collusion, no privileged control, and no external-chain compromise — purely a consequence of ordinary payload execution reaching `BuildOutboundsFromReceipt`.

### Recommendation
Change the error-handling inside the loop in `BuildOutboundsFromReceipt` so that a failure on one log (decode error, disabled destination chain, or missing token config) results in that individual outbound being skipped/recorded as a failed/aborted outbound (or reverted independently), via `continue`, rather than discarding the whole `outbounds` slice and aborting the loop with a hard `return nil, err`. Ensure any log-specific failure is still surfaced (e.g., as a per-log warning/PCTx entry) so operators can investigate, but valid, already-decoded outbounds from the same receipt must still be attached to the UTX and enter the pending-outbound/TSS-signing flow.

### Proof of Concept
Conceptual (not executed, since this requires deploying a batching Gateway-caller contract and cannot be validated purely from static code review):
1. Configure `x/uregistry` so `eip155:1` outbound is enabled and `eip155:56` outbound is disabled (or simply has no matching `TokenConfig` for the PRC20 used).
2. Deploy a helper "batch withdraw" contract that, in a single call, invokes `UniversalGateway.withdraw(...)` twice: once targeting `eip155:1` (valid) and once targeting `eip155:56` (disabled/misconfigured).
3. Submit a `MsgExecutePayload` (or inbound `FUNDS_AND_PAYLOAD`) whose `UniversalPayload.Data` calls this batch contract; the EVM call succeeds and both `UniversalTxOutboundEvent` logs are emitted in the resulting receipt, with the Gateway-side withdraw/burn accounting for both destinations already taking effect.
4. `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` processes the log list; upon reaching the `eip155:56` log it hits `!outboundEnabled` and returns `nil, err`, discarding the already-built `eip155:1` outbound too.
5. Observe that no `OutboundTx`/`PendingOutbounds` entry exists for the `eip155:1` withdraw despite its Gateway-side funds having moved — those funds can never be released via TSS signing, resulting in a permanent loss for that recipient.

// AttachOutboundsToExistingUniversalTx
// Used when UniversalTx already exists (e.g. inbound execution)
// It attaches outbounds extracted from receipt to the existing utx.
func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
