### Title
Missing zero-address check on inbound `Recipient` allows permanent loss of bridged funds via `depositPRC20` to `0x0` - (File: x/uexecutor/types/inbound.go, x/uexecutor/keeper/execute_inbound_funds.go)

### Summary
`Inbound.ValidateForExecution()` validates that `Recipient` is a syntactically valid hex address using `utils.IsValidAddress(p.Recipient, utils.HEX)`, which wraps `common.IsHexAddress`. This function only checks format (40 hex chars, optional `0x` prefix) and explicitly accepts `0x0000000000000000000000000000000000000000` as valid. There is no additional check anywhere in the inbound-execution pipeline that rejects the zero address before it is used as the mint destination for PRC20 deposits.

### Finding Description
The relevant validation is in `ValidateForExecution`: [3](#0-2) 

`IsValidAddress(addr, HEX)` simply calls `common.IsHexAddress(addr)`: [4](#0-3) 

`common.IsHexAddress` from go-ethereum only checks length/hex-charset, not that the address is non-zero. Once `ValidateForExecution` passes, `ExecuteInboundFunds` calls `depositPRC20` directly with `common.HexToAddress(inbound.Recipient)`: [5](#0-4) 

which in turn calls `CallPRC20Deposit`, minting the PRC20 representation to that address via a module-signed `DerivedEVMCall`: [6](#0-5) 

If a user (or a malicious/malformed relayed inbound event) sets `Recipient = "0x0000000000000000000000000000000000000000"`, the inbound passes `ValidateForExecution`, the ballot finalizes normally with honest validators (they are just relaying the observed on-chain event data, which is attacker-controlled — the `Recipient` field on an EVM gateway `addFunds`-style event can be set to whatever the depositor supplies), and the deposit mints PRC20 tokens to the burn/zero address. The same gap exists in the CEA path checks, which only verify `strings.HasPrefix(..., "0x")` and that `Recipient` is non-empty, again not rejecting the zero address: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go` lines 53-61, and the same pattern in `execute_inbound_gas_and_payload.go` lines 60-68.

Also relevant: `RevertInstructions.FundRecipient` (used to route refunds on the source chain) and `handleFailedOutbound`'s recipient re-mint path have the identical class of gap — the refund path uses `outbound.Sender`/`RevertInstructions.FundRecipient` as-is: [7](#0-6) 

### Impact Explanation
This is a genuine unrecoverable-fund-loss vector under the "In scope" criteria (permanent loss/permanent freezing of user or protocol-controlled funds): PRC20 tokens minted to the zero address are irrecoverable, and the original depositor's cross-chain funds are effectively burned with no revert path recovering them (a zero-recipient FUNDS inbound is a normal ValidateForExecution pass, not a failure, so no `INBOUND_REVERT` outbound is generated). The severity is bounded by the fact that it requires the depositor/relayed event data itself to supply a zero recipient — this harms the depositor (self-inflicted) rather than letting an attacker steal others' funds, but it still constitutes a protocol-level "unauthorized/permanent loss" bug matching the seed report's bug class (missing zero-address input validation) and Push Chain's own registry/accounting invariants around PRC20 minting correctness.

### Likelihood Explanation
Likelihood is best characterized as low-to-moderate: it requires an inbound event whose `recipient` field on the source-chain gateway contract is the zero address, which is unusual but not prevented by any layer (source-chain gateway contract, event parsing, `ValidateBasic`, `ValidateForExecution`, or `depositPRC20`/`CallPRC20Deposit`). It is reachable purely through the standard user deposit path with no privileged actor required, satisfying the "ordinary user deposit" reachability requirement.

### Recommendation
Add an explicit zero-address rejection alongside the existing `IsValidAddress` checks in `Inbound.ValidateForExecution` (and the CEA-specific recipient checks in `execute_inbound_funds_and_payload.go` / `execute_inbound_gas_and_payload.go`), e.g. compare against `types.EvmZeroAddress` (already defined at `x/uexecutor/types/inbound.go:14`) or `(common.Address{})` after `common.HexToAddress`. Apply the same check to `RevertInstructions.FundRecipient` before it's used as a refund/re-mint target in `buildRevertOutbound` and `handleFailedOutbound`.

### Proof of Concept
1. Submit (or have an honest Universal Validator relay) an `Inbound` with `TxType = TxType_FUNDS`, a well-formed `AssetAddr`/`Amount`, and `Recipient = "0x0000000000000000000000000000000000000000"`.
2. `ValidateBasic()` does not check `Recipient` at all; `ValidateForExecution()` passes because `common.IsHexAddress("0x000...000")` returns `true`.
3. Ballot reaches quorum; `ExecuteInboundFunds` runs `depositPRC20(..., common.HexToAddress("0x0"), amount)`, which mints `amount` PRC20 tokens to the zero address via `CallPRC20Deposit`.
4. PCTx is recorded `SUCCESS`; no `INBOUND_REVERT` outbound is created (only failures create reverts), so the bridged value is permanently unrecoverable.

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
