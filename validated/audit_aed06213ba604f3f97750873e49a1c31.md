### Title
Silent proof-verification bypass in `DbStateView::get` when proof fetch fails but value fetch succeeds - (File: storage/storage-interface/src/state_store/state_view/db_state_view.rs)

### Summary
`DbStateView::get` is supposed to cryptographically verify every returned `StateValue` against `maybe_verify_against_state_root_hash` before returning it. The verification is guarded by an `if let Ok(...)` on the result of `get_state_value_with_proof_by_version`, and the subsequent unconditional call to `get_state_value_with_version_by_version` is what actually produces the returned value. If the two DB calls diverge — the proof-bearing call returns `Err` while the plain value call returns `Ok(Some(..))` — the function silently returns an **unverified** value while callers believe it was verified.

### Finding Description
```rust
// storage/storage-interface/src/state_store/state_view/db_state_view.rs:26-46
fn get(&self, key: &StateKey) -> StateViewResult<Option<(Version, StateValue)>> {
    if let Some(version) = self.version {
        if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
            if let Ok((value, proof)) =
                self.db.get_state_value_with_proof_by_version(key, version)
            {
                proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
            }
            // <-- if the call above returns Err, execution falls through here
            // with NO verification performed and NO error propagated.
        }
        Ok(self
            .db
            .get_state_value_with_version_by_version(key, version)?)
    } else {
        Ok(None)
    }
}
``` [1](#0-0) 

The intent of the `verified_state_view_at_version` constructor is clearly to bind every value returned through this `DbStateView` to a proof-verified state root obtained from a verified transaction proof:

```rust
// storage/storage-interface/src/state_store/state_view/db_state_view.rs:118-149
let state_root_hash = txn_with_proof
    .proof
    .transaction_info
    .state_checkpoint_hash()
    ...
Ok(DbStateView {
    db,
    version: Some(version),
    maybe_verify_against_state_root_hash: Some(state_root_hash),
})
``` [2](#0-1) 

The bug is the `if let Ok(...)` pattern: it treats an `Err` from `get_state_value_with_proof_by_version` as "nothing to verify" instead of propagating the error or refusing to serve the value. Because the fallback read `get_state_value_with_version_by_version` uses a different code path (in `aptosdb`, the plain value lookup reads directly from the State KV DB/shard while the proof lookup additionally needs the corresponding Jellyfish Merkle tree nodes), the two calls can genuinely diverge whenever the underlying storage state for the tree side and the raw KV side are not perfectly in lock-step (e.g. differing pruning windows between the state-merkle pruner and the state-KV pruner, partially restored/backfilled tree shards, or any other JMT-node-missing condition that does not also remove the raw KV record). In such a case:

- `get_state_value_with_proof_by_version(key, version)` → `Err` (e.g. `MissingRootError`/"node not found" from the JMT reader) → falls into the `if let Some(root_hash) = ...` block but the inner `if let Ok(...)` never executes its body, so `proof.verify(...)` is never called and no error is raised.
- `get_state_value_with_version_by_version(key, version)` → `Ok(Some(value))` — read straight from the KV store, no Merkle involvement.
- The function returns `Ok(Some(value))` as if it had verified the value against `root_hash`, when in fact it verified nothing.

This exactly inverts the guarantee documented by the comment above the struct field (`maybe_verify_against_state_root_hash`) and relied upon by every caller that constructs a `DbStateView` via `verified_state_view_at_version` expecting authenticated reads.

### Impact Explanation
Any code path that trusts `DbStateView` constructed with `maybe_verify_against_state_root_hash: Some(..)` to return only proof-verified values (transaction pre/execution validation, light-client-style state reads, etc.) can be silently handed an unauthenticated `StateValue` for a given `StateKey`/version without any indication that verification was skipped. This breaks the "every value returned by a verified state view is proof-bound to `root_hash`" invariant described in the file, which is exactly the class of bug the review targets (wrong/absent proof accepted as valid).

### Likelihood Explanation
Triggering the divergence requires the two underlying DB reads to actually disagree — this is a genuine state/config divergence (e.g. mismatched pruner windows between state-merkle and state-KV stores, or a JMT node missing for other reasons) rather than something purely computable from an arbitrary unprivileged key with no special DB state. I was not able to fully verify, within the available search budget, the exact conditions under which `aptosdb`'s `get_state_value_with_proof_by_version` returns `Err` while `get_state_value_with_version_by_version` returns `Ok(Some(..))` for the same key/version in this repository's current pruner configuration (`storage/aptosdb/src/state_store/mod.rs`, `storage/aptosdb/src/state_kv_db.rs`) — this needs further code review to confirm feasibility on a real running node versus only being reachable via already-invalid/mismatched storage. Regardless of exact trigger frequency, the code as written contains no error propagation or defensive check for this divergence, which is a genuine logic defect in the verification gate itself.

### Recommendation
Change the `if let Ok(...)` to propagate the `Err` (e.g. `let (value, proof) = self.db.get_state_value_with_proof_by_version(key, version)?;`) so any failure to obtain a proof for a version that is supposed to be verified aborts the read with an error instead of silently returning an unverified value. If a legitimate "proof not available for buffered state" fallback is intended (per the existing `TODO` comments), that fallback must be an explicit, narrowly-scoped case (e.g. only for versions known to be unpersisted/buffered) rather than silently swallowing any `Err` from the proof-fetching call.

### Proof of Concept
Mock a `DbReader` where:
- `get_state_value_with_proof_by_version(key, version)` returns `Err(AptosDbError::NotFound("state merkle node missing".into()))`
- `get_state_value_with_version_by_version(key, version)` returns `Ok(Some((version, some_state_value)))`

Construct `DbStateView { db: mock, version: Some(version), maybe_verify_against_state_root_hash: Some(root_hash) }` and call `.get_state_slot(&key)` (which calls the private `get`). The call returns `Ok` with the mocked value populated, with no `proof.verify` call ever invoked and no error surfaced — demonstrating the silent bypass described in the exploit question. [3](#0-2)
