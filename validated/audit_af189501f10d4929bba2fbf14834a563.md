### Title
Unbounded gzip decompression of user-supplied `BroadcastedDeclareTransaction::V1.contract_class.compressed_program` in JSON-RPC `estimateFee`/`simulateTransactions` enables memory-exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The `apollo_rpc` node implements a `decompress_program` helper that gzip-decompresses a user-controlled, base64-encoded `compressed_program` field with **no output-size cap**, unlike the equivalent hardened helper `decode_and_decompress_with_size_limit` used elsewhere in the codebase (e.g. for Sierra program decompression in the gateway and P2P class sync). This unbounded path is reachable by any unauthenticated JSON-RPC caller submitting a `BroadcastedDeclareTransaction::V1` for fee estimation/simulation, allowing a small gzip "bomb" to expand to a huge in-memory buffer.

### Finding Description
`decompress_program` reads the entire decompressed gzip stream into a `Vec<u8>` with a `TODO` comment acknowledging the missing bound: [1](#0-0) 

It is invoked directly on attacker-supplied bytes via `user_deprecated_contract_class_to_sn_api`, which converts a client-submitted `apollo_starknet_client::writer::objects::transaction::DeprecatedContractClass.compressed_program` into the executable program used for a `DeclareTransactionV0V1`: [2](#0-1) 

This is the `TryFrom<BroadcastedDeclareTransaction>` conversion that feeds simulation/fee-estimation execution paths (`ExecutableTransactionInput`), meaning any unprivileged RPC client can trigger it by calling the standard `starknet_estimateFee` / `starknet_simulateTransactions` JSON-RPC methods with a crafted `DECLARE` (V1) payload containing a highly compressed `program`.

This is the same bug class as the reported http4k advisory (CWE-409, unbounded gzip decompression from an untrusted request), but it is **not merely a dependency issue** — it is a first-party helper in this repo with an explicit unresolved TODO. Notably, the codebase already recognizes and mitigates this exact class of bug elsewhere: `starknet_api::compression_utils::decode_and_decompress_with_size_limit` caps decompressed output and returns `SizeLimitExceeded`, and `apollo_protobuf::converters::class` caps Cairo0 program decompression at 4MB: [3](#0-2) [4](#0-3) 

`decompress_program` is the one straggler path that was never upgraded to use a bounded decompressor.

### Impact Explanation
An unauthenticated RPC client can submit a crafted, small (KB-scale) gzip payload as the `program` field of a legacy (Cairo0) declare transaction to `starknet_estimateFee` or `starknet_simulateTransactions`. Because `decoder.read_to_end(&mut decompressed, ...)` has no size limit, the decompression can expand to gigabytes, exhausting the RPC node's heap/memory and causing the process (or co-located services) to crash or become unresponsive — a denial-of-service against a node that serves clients and (depending on deployment) participates in transaction submission/read infrastructure for the network.

### Likelihood Explanation
High. The path requires no special privileges — just a standard JSON-RPC call — and no on-chain state, fees, or signature validity checks gate the decompression step, which happens during the conversion into an executable transaction before any signature/fee-bound validation of the (unsupported-for-real-broadcast) declare transaction. A single request with a small payload can trigger large memory allocation, and the request can be repeated cheaply to amplify the effect.

### Recommendation
Replace the manual `GzDecoder::read_to_end` call in `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) with a size-bounded decompression routine, consistent with `starknet_api::compression_utils::decompress_with_size_limit`/`decode_and_decompress_with_size_limit` (which use `.take(max_size + 1)` and return an explicit `SizeLimitExceeded`/oversize error instead of unbounded `read_to_end`). Enforce a maximum decompressed program size (e.g., matching the `MAX_CAIRO0_PROGRAM_SIZE` = 4MB constant already used in `apollo_protobuf::converters::class`), and reject with an appropriate JSON-RPC error rather than allocating unbounded memory.

### Proof of Concept
1. Craft a `BroadcastedDeclareTransaction::V1` JSON body whose `contract_class.program` field is a base64-encoded gzip stream of a few KB that decompresses to several GB (e.g., a highly repetitive JSON structure, gzip compression ratio can exceed 1000:1).
2. Send it to the target node's JSON-RPC endpoint via `starknet_estimateFee` (or `starknet_simulateTransactions`) with this transaction in the request.
3. `user_deprecated_contract_class_to_sn_api` → `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) decompresses the payload with no cap, allocating the full decompressed size in memory before any further validation occurs.
4. Repeating this with concurrent requests exhausts the node's memory, causing OOM kill / crash / degraded service for all users of that RPC node.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
