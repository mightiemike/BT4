### Title
Unbounded recursion in bytecode segment hashing during compiled-class-hash computation for attacker-declared Sierra classes - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
`compiled_class_hash.rs::bytecode_hash_node` recursively walks the `NestedIntList` bytecode segment structure attached to a `CasmContractClass` to compute the class's compiled-class hash. The recursion depth is dictated purely by the shape of `bytecode_segment_lengths`, a structure the Sierra→CASM compiler derives from the *declared contract's own code structure* (nested function/branch segmentation). There is no explicit maximum-depth check anywhere in this function or its caller chain before recursing.

### Finding Description
`bytecode_hash_node` recurses once per nesting level of the segment tree: [1](#0-0) 

This is invoked from `bytecode_hash` → `hash_inner` → `HashableCompiledClass::hash`, which computes the compiled class hash for every `CasmContractClass`: [2](#0-1) [3](#0-2) 

This hash is computed synchronously as part of transaction ingestion, immediately after Sierra→CASM compilation of an attacker-submitted Declare transaction's class, before the transaction's signature/fee/nonce is verified: [4](#0-3) 

and again independently during on-chain execution/re-declaration checks: [5](#0-4) 

Unlike contract-call recursion in the VM/Native execution path — which is explicitly protected by `RecursionDepthGuard`/`max_recursion_depth` and further bounded by step/gas resource accounting (verified by the `test_stack_overflow` test showing recursion is terminated by resource bounds before a native stack overflow occurs) — [6](#0-5) [7](#0-6) 
the bytecode-segment hashing path has **no equivalent depth guard**. `NestedIntList` is generated by the Sierra→CASM compiler based on the submitted Sierra program's control-flow/function nesting; only the total serialized/compressed bytecode size is bounded (`max_bytecode_size`), not the nesting depth of the segment tree, so a specially crafted Sierra program (e.g., deeply nested inline function calls or match/branch chains) can in principle produce a segment tree whose depth is large enough to exhaust the Rust call stack during `bytecode_hash_node`'s recursive descent — directly analogous to CVE-2015-8874's unbounded-recursion stack consumption in `imagefilltoborder`.

### Impact Explanation
If this recursion depth can be driven high enough (bounded ultimately by bytecode size limits, but not directly by any recursion-depth cap), the compiling/gateway or executing node process will crash with a stack overflow when computing the compiled class hash for the malicious class — a denial of service reachable by any account submitting a Declare transaction. Because the same `CasmContractClass::hash` function is called both in the sequencer's compilation service (`apollo_compile_to_casm`) during ingestion and inside blockifier execution/OS re-execution when validating `compiled_class_hash`, a crash here can affect gateway nodes, executing nodes, and re-execution/proving nodes alike — potentially causing a network-wide inability to process the offending Declare transaction (a network unable to confirm new transactions if this hits consensus nodes uniformly).

### Likelihood Explanation
Likelihood is **uncertain/moderate** rather than confirmed: exploitability depends on (a) whether the external `cairo-lang-starknet-classes` Sierra→CASM compiler (an out-of-scope dependency) can be coerced into producing a segment tree whose *nesting depth* — not just total size — scales with attacker-controlled code structure, and (b) whether `max_bytecode_size` (`DEFAULT_MAX_BYTECODE_SIZE`, configurable) is large enough to allow sufficient nesting depth before hitting the size cap. I was not able to fully verify the segment-generation logic (it lives in the external `cairo-lang-starknet-classes` crate, outside this repo's index) or empirically determine the maximum achievable recursion depth for a given `max_bytecode_size`, so this should be treated as a plausible bug-class analog requiring further verification (e.g., testing with a crafted Sierra program near the size limit) rather than a fully proven exploit.

### Recommendation
Add an explicit maximum-depth check while descending `NestedIntList` in `bytecode_hash_node` (mirroring the `RecursionDepthGuard` pattern used for contract-call recursion), or convert the recursive traversal to an explicit iterative/worklist algorithm with a bounded stack, so that no attacker-controlled Sierra/CASM structure can cause unbounded native recursion regardless of the compiler's segment-generation behavior.

### Proof of Concept
Not fully constructible from static analysis alone: reproducing the crash requires generating (via the external Sierra→CASM compiler) a `CasmContractClass` whose `bytecode_segment_lengths` `NestedIntList` has a deep nesting chain (e.g., via deeply nested inlined function calls/match branches in a Cairo1 contract) within the `max_bytecode_size` budget, then invoking `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`) or `DeclareTransaction::check_compile_class_hash_v2_declaration` (`crates/starknet_api/src/executable_transaction.rs:228-244`) on it and observing whether `bytecode_hash_node`'s recursion (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132`) exhausts the stack before other resource limits intervene. Confirming actual exploitability requires access to the external compiler's segmentation algorithm, which is outside this repository's index.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

        &*hashable_class.get_bytecode_segment_lengths(),

        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,

    ]))

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}

/// Tests that Native can handle deep recursion calls without causing a stack overflow.
/// The recursive function must be complex enough to prevent the compiler from optimizing it into a
/// loop. This function was manually tested with increased maximum gas to ensure it reaches a stack
/// overflow.

fn test_stack_overflow(#[values(true, false)] concurrency_enabled: bool) {
    let block_context = BlockContext::create_for_account_testing();
    let cairo_version = CairoVersion::Cairo1(RunnableCairo1::Native);
    let TestInitData { state, account_address, contract_address, mut nonce_manager } =
        create_test_init_data(&block_context.chain_info, cairo_version);
    let depth = felt!(1000000_u128);
    let entry_point_args = vec![depth];
    let calldata = create_calldata(contract_address, "test_stack_overflow", &entry_point_args);
    let invoke_tx = executable_invoke_tx(invoke_tx_args! {
        sender_address: account_address,
        calldata,
        nonce: nonce_manager.next(account_address),
        resource_bounds: ValidResourceBounds::create_for_testing_no_fee_enforcement(),
    });
    let account_tx = AccountTransaction::new_for_sequencing(invoke_tx);
    // Ensure the transaction is allocated the maximum gas limits.
    assert!(
        account_tx.resource_bounds().get_l2_bounds().max_amount
            >= block_context.versioned_constants.os_constants.execute_max_sierra_gas
                + block_context.versioned_constants.os_constants.validate_max_sierra_gas
    );
    // Run.
    let config = TransactionExecutorConfig::create_for_testing(concurrency_enabled);
    let mut executor = TransactionExecutor::new(state, block_context, config);
    let results = executor.execute_txs(&[account_tx.into()], None);

    let (tx_execution_info, _state_diff) = results[0].as_ref().unwrap();
    assert!(tx_execution_info.is_reverted());
    let err = tx_execution_info.revert_error.clone().unwrap().to_string();

    // Recursion is terminated by resource bounds before stack overflow occurs.
    assert!(err.contains("'Out of gas'"));
}
