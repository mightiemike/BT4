Confirmed: `TransactionListWithProof::verify` (used by the transaction-backup restore path) checks the transaction hash against `txn_info.transaction_hash()` and, if present, checks event root hashes, but it **never checks `write_set` against `txn_info.state_change_hash()`** [1](#0-0) . This is unlike `TransactionOutputListWithProof::verify`, which explicitly checks `write_set_hash == txn_info.state_change_hash()` [2](#0-1) .

In the transaction-backup restore path, `LoadedChunk::load` parses `(txn, aux_info, txn_info, events, write_set)` tuples from the backup file, then builds a `TransactionListWithProofV2` **without the write_set** and calls `.verify(ledger_info.ledger_info(), ...)`, which only authenticates `txns`/`events`/`txn_infos` against the ledger info's accumulator root — the `write_sets` vector is carried alongside, entirely outside the authenticated structure [3](#0-2) . After verification succeeds, `save_transactions_impl` writes these unauthenticated `write_sets` straight into `WriteSetDb` [4](#0-3) , and separately writes the (authenticated) `txn_infos` into `TransactionAccumulatorSchema`/frozen subtrees via `confirm_or_save_frozen_subtrees_impl`, which only compares hashes it already has and blindly inserts new ones without any independent check against a `LedgerInfoWithSignatures` [5](#0-4) .

The result: the accumulator (frozen subtrees, `TransactionAccumulatorSchema`) is authentic and matches the trusted `LedgerInfoWithSignatures`/epoch history (via `EpochHistory::verify_ledger_info`) [6](#0-5) , but the `write_set` stored in `write_set_db` for each version can be **anything** an unprivileged/permissionless backup-storage provider chooses, since it is never bound to `txn_info.state_change_hash()` on restore. This breaks the state-commitment binding: `TransactionInfo.state_change_hash` is supposed to be "hash of the output write set" [7](#0-6)  but restore never checks it.

### Title
Restore accepts unauthenticated write sets that are never checked against `TransactionInfo.state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`, `storage/aptosdb/src/backup/restore_utils.rs`)

### Summary
When restoring from a transaction backup (verify-only or actual restore without replay, i.e. `replay_from_version` not covering the affected range), `LoadedChunk::load` verifies transactions/events/txn-infos against an authenticated `LedgerInfoWithSignatures` via `TransactionListWithProofV2::verify`, but the `write_set` field parsed from the same untrusted backup record is excluded from that verified structure and is never checked against `txn_info.state_change_hash()`. Restore then persists this attacker-controlled write set directly into `write_set_db` while the (correctly authenticated) transaction accumulator/frozen subtrees are saved separately and unconditionally accepted for new positions in `confirm_or_save_frozen_subtrees_impl`.

### Finding Description
`confirm_or_save_frozen_subtrees_impl` only cross-checks a supplied frozen-subtree hash against one already present in the DB (`h == &_h`); for previously-unseen positions it just `batch.put`s the value with no independent verification tying it to a `LedgerInfoWithSignatures` [8](#0-7) . This by itself is normally safe because the frozen-subtree values that reach it originate from txn_infos that *were* separately verified against the accumulator hash in a trusted `LedgerInfoWithSignatures`. The actual gap is one layer up: the write sets that get committed into `write_set_db` alongside those verified txn_infos are never checked to be consistent with `txn_info.state_change_hash()` during restore/verify, because `TransactionListWithProof::verify` (unlike `TransactionOutputListWithProof::verify`) omits that check [1](#0-0) . A permissionless backup source (anyone able to serve backup data to a restoring/verifying node — e.g. a public/community backup bucket used for state-sync-from-backup) can therefore supply arbitrary write sets for versions whose txn_info/accumulator are legitimately signed, and the restoring node will accept and store them without complaint, while accumulator roots stay internally consistent and match the true `LedgerInfoWithSignatures`.

### Impact Explanation
A node performing `db-restore`/`db-restore verify` (or replay in non-kv-replay mode where write sets are directly applied rather than re-executed) can end up with a `write_set_db` whose contents do not match what was actually agreed upon by consensus for a given version, while the ledger metadata, accumulator, and `LedgerInfoWithSignatures` all look correct. Any downstream logic, RPC, or indexing tool that reads write sets for a "verified" restored version (e.g., `get_transaction_outputs`, event derivation for state, replay tooling) can be fed forged state-change data for that version, corrupting downstream consumers' view of state while the on-disk accumulator continues to pass consistency checks. This does not corrupt actual mainnet consensus (validators execute transactions from the VM, not from restored write sets) but corrupts what a restoring/verifying full node or indexer reports as ground truth after a backup-driven restore.

### Likelihood Explanation
Requires the restoring node to source backup data from an untrusted/permissionless backup location and to run in a restore/verify mode that does not replay-execute transactions to regenerate write sets independently (kv_replay/execution-replay would recompute and thus reject mismatched write sets via `ensure_match_transaction_info`, per `execution/executor/src/chunk_executor/mod.rs`). This is a realistic scenario for `db-restore verify` or non-replay portions of restore, which are explicitly designed to trust the manifest+proof rather than re-execute.

### Recommendation
Add a check in `LoadedChunk::load` (or in `TransactionListWithProof`/`TransactionListWithProofV2::verify`) that `CryptoHash::hash(write_set) == txn_info.state_change_hash()` for every transaction, mirroring the check already present in `TransactionOutputListWithProof::verify` and `TransactionOutput::ensure_match_transaction_info`, before write sets are handed to `save_transactions_impl`/`WriteSetDb::put_write_set`.

### Proof of Concept
1. Take a legitimate transaction backup chunk for a given version range with a valid `TransactionAccumulatorRangeProof` and `LedgerInfoWithSignatures`.
2. Modify only the `write_set` bytes of one record in the chunk's transaction file (leave `txn_info`, `txn`, and `events` untouched so their hashes still match the accumulator proof).
3. Run `db-restore` (or `db-restore verify`) against this tampered backup, pointed at a storage endpoint you control.
4. Observe that `LoadedChunk::load` succeeds (`txn_list_with_proof.verify` passes because it never touches `write_set`), `confirm_or_save_frozen_subtrees_impl`/accumulator checks pass, and the tampered `write_set` is persisted into `write_set_db` for that version — while `db.get_accumulator_root_hash(version)` still equals `ledger_info.transaction_accumulator_hash()`.

fn confirm_or_save_frozen_subtrees_impl(
    transaction_accumulator_db: &DB,
    frozen_subtrees: &[HashValue],
    positions: Vec<Position>,
    batch: &mut SchemaBatch,
) -> Result<()> {
    positions
        .iter()
        .zip(frozen_subtrees.iter().rev())
        .map(|(p, h)| {
            if let Some(_h) = transaction_accumulator_db.get::<TransactionAccumulatorSchema>(p)? {
                ensure!(
                        h == &_h,
                        "Frozen subtree root does not match that already in DB. Provided: {}, in db: {}.",
                        h,
                        _h,
                    );
            } else {
                batch.put::<TransactionAccumulatorSchema>(p, h)?;
            }
            Ok(())
        })
        .collect::<Result<Vec<_>>>()?;

    Ok(())
}

    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
        if epoch == 0 {
            ensure!(
                li_with_sigs.ledger_info() == &self.epoch_endings[0],
                "Genesis epoch LedgerInfo info doesn't match.",
            );
        } else if let Some(wp_trusted) = self
            .trusted_waypoints
            .get(&li_with_sigs.ledger_info().version())
        {
            let wp_li = Waypoint::new_any(li_with_sigs.ledger_info());
            ensure!(
                *wp_trusted == wp_li,
                "Waypoints don't match. In backup: {}, trusted: {}",
                wp_li,
                wp_trusted,
            );
        } else {
            self.epoch_endings[epoch as usize - 1]
                .next_epoch_state()
                .ok_or_else(|| anyhow!("Shouldn't contain non- epoch bumping LIs."))?
                .verify(li_with_sigs)?;
        };
        Ok(())
    }
