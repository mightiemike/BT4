### Title
`UnfreezeBalanceV2Processor.validate` omits the `supportUnfreezeDelay()` feature-gate check enforced by `UnfreezeBalanceV2Actuator.validate` - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java`)

### Summary
`UnfreezeBalanceV2Actuator.validate()` explicitly rejects unfreeze-V2 transactions when `dynamicStore.supportUnfreezeDelay()` is false with `"Not support UnfreezeV2 transaction, need to be opened by the committee"` [1](#0-0) . The TVM-native counterpart, `UnfreezeBalanceV2Processor.validate()`, performs address/account/resource/balance checks but never calls or checks `dynamicStore.supportUnfreezeDelay()` anywhere in its body [2](#0-1) .

### Finding Description
The two validate paths for logically equivalent operations diverge: the HTTP/gRPC broadcast path (`UnfreezeBalanceV2Actuator`) enforces the committee-controlled `UNFREEZE_DELAY`/new-resource-model feature switch before allowing any UnfreezeBalanceV2 semantics, while the native-contract processor invoked from TVM opcode execution (`UnfreezeBalanceV2Processor`, referenced from `Program.java`) does not re-check this flag. If a network state existed where the TVM opcode enabling flag (`VMConfig.allowTvmFreezeV2()`, populated from a proposal via `ConfigLoader`) were active while `supportUnfreezeDelay()` were still false, a contract call reaching `UnfreezeBalanceV2Processor.execute` would bypass the feature gate that the actuator enforces, producing behavior unreachable via the standard actuator path and inconsistent semantics between the two code paths.

I was not able to fully confirm within the available search results whether `Program.java`'s opcode dispatch for the native unfreeze-v2 call independently re-checks `supportUnfreezeDelay()` before invoking `UnfreezeBalanceV2Processor`, nor whether `ConfigLoader.java` ties `VMConfig.allowTvmFreezeV2()` to `supportUnfreezeDelay()` at proposal-application time (both flags appeared in `ConfigLoader.java` per search results, but I could not read the exact wiring). In real TRON history, the TVM-freeze-v2 opcode proposal was activated only after the Stake 2.0 (unfreeze-delay) hard fork was already live on mainnet, which would make `supportUnfreezeDelay()==false && allowTvmFreezeV2()==true` a state that does not occur under normal committee proposal ordering. This significantly reduces or eliminates real-world exploitability even though the code-level check is missing.

### Impact Explanation
If the preconditions could occur (feature flags in an inconsistent combination), an attacker's contract could invoke unfreeze-V2 semantics before the corresponding non-TVM transaction type would be accepted anywhere else, causing consensus/state divergence between the intended feature-gated behavior and contract-triggered execution. This would map to a "state/consensus divergence" class impact. However, this depends entirely on an artificial committee-configuration state that, per known deployment ordering of these two features, does not arise in practice.

### Likelihood Explanation
Low. The precondition (`allowTvmFreezeV2()` true while `supportUnfreezeDelay()` false) requires a specific and, per the codebase's real feature-activation history, effectively unreachable committee configuration — the TVM opcode for freeze/unfreeze V2 was only ever proposed after the underlying unfreeze-delay feature was already active. No unprivileged attacker action alone can produce this precondition; it depends purely on committee/proposal state, which is outside the "unprivileged attacker" threat model specified for this audit. I could not verify with certainty (due to tool-call limits) whether `ConfigLoader.java` or `Program.java` independently closes this gap, so the missing check remains a genuine code-hygiene/defense-in-depth gap, but not a demonstrated exploitable vulnerability under the stated unprivileged-attacker constraints.

### Recommendation
Add an explicit `if (!dynamicStore.supportUnfreezeDelay()) { throw new ContractValidateException(...); }` check at the start of `UnfreezeBalanceV2Processor.validate()`, mirroring `UnfreezeBalanceV2Actuator.validate()`, so that feature-gate enforcement does not rely on an assumption about proposal-activation ordering between `ALLOW_TVM_FREEZE_V2` (or equivalent) and `UNFREEZE_DELAY_DAYS`/new-resource-model proposals.

### Proof of Concept
Not conclusively reproducible as a real exploit: no known way exists for an unprivileged attacker to independently set `supportUnfreezeDelay()==false` while `VMConfig.allowTvmFreezeV2()==true`, since these are both committee-controlled proposals whose real-world activation order (per project history) prevents this combination. A JUnit test can demonstrate the code-level discrepancy (calling `UnfreezeBalanceV2Processor.validate()` directly with `supportUnfreezeDelay()` stubbed false and observing no exception, versus `UnfreezeBalanceV2Actuator.validate()` throwing), but this does not by itself constitute an attacker-reachable exploit given the stated unprivileged-attacker-only threat model and the required committee-configuration precondition.

  public void validate(UnfreezeBalanceV2Param param, Repository repo)
      throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (accountCapsule == null) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + readableOwnerAddress + "] does not exist");
    }
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    int unfreezingCount = accountCapsule.getUnfreezingV2Count(now);
    if (UnfreezeBalanceV2Actuator.getUNFREEZE_MAX_TIMES() <= unfreezingCount) {
      throw new ContractValidateException("Invalid unfreeze operation, unfreezing times is over limit");
    }
    switch (param.getResourceType()) {
      case BANDWIDTH:
        // validate frozen balance
        if (!this.checkExistFrozenBalance(accountCapsule, Common.ResourceCode.BANDWIDTH)) {
          throw new ContractValidateException("no frozenBalance(BANDWIDTH)");
        }
        break;
      case ENERGY:
        // validate frozen balance
        if (!this.checkExistFrozenBalance(accountCapsule, Common.ResourceCode.ENERGY)) {
          throw new ContractValidateException("no frozenBalance(ENERGY)");
        }
        break;
      case TRON_POWER:
        if (dynamicStore.supportAllowNewResourceModel()) {
          if (!this.checkExistFrozenBalance(accountCapsule, Common.ResourceCode.TRON_POWER)) {
            throw new ContractValidateException("no frozenBalance(TRON_POWER)");
          }
        } else {
          throw new ContractValidateException("Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
        }
        break;
      default:
        if (dynamicStore.supportAllowNewResourceModel()) {
          throw new ContractValidateException("Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY、TRON_POWER]");
        } else {
          throw new ContractValidateException("Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
        }
    }

    if (!checkUnfreezeBalance(accountCapsule, param.getUnfreezeBalance(), param.getResourceType())) {
      throw new ContractValidateException(
          "Invalid unfreeze_balance, [" + param.getUnfreezeBalance() + "] is invalid");
    }
  }
