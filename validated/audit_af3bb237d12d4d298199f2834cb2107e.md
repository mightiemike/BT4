## Title
`ProposalEvalConfig` conversion silently drops `block_proposal_max_age_secs`, disabling the stale-proposal freshness check - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SignerConfig` documents and carries a `block_proposal_max_age_secs` field [1](#0-0) , intended to reject block proposals whose header timestamp is older than a configured threshold (`RejectReason::ProposalTooOld` exists specifically for this) [2](#0-1) . However, the `From<&SignerConfig> for ProposalEvalConfig` impl that builds the actual verification policy used by `SortitionsView::check_proposal` copies every other timing field but omits `block_proposal_max_age_secs` entirely [3](#0-2) .

### Finding Description
`ProposalEvalConfig` is the struct that "Captures the configuration settings used by the signer when evaluating block proposals" [4](#0-3) , and it is constructed from the richer `SignerConfig`/`GlobalConfig`, both of which explicitly declare `block_proposal_max_age_secs` with clear intent ("The maximum age of a block proposal in seconds that will be processed by the signer") [1](#0-0) [5](#0-4) . The `From` impl that performs this construction lists eight fields but never reads or assigns `block_proposal_max_age_secs`, so the value present in `SignerConfig` never reaches `ProposalEvalConfig` [3](#0-2) . This mirrors the sigstore pattern exactly: a documented constraint accepted into a configuration object is discarded before it reaches the code path that is supposed to enforce it.

Since `ProposalEvalConfig` — not `SignerConfig` — is what `SortitionsView` actually holds and consults during `check_proposal`, any check gated on the age field is either permanently absent from that struct or (if implemented elsewhere against a zero/default value) always evaluates against an unset/default threshold rather than the operator-configured one. Operators who tighten `block_proposal_max_age_secs` to bound how stale a proposal they will sign get no enforcement of that bound in the sortition-view proposal-evaluation path, because the field silently never survives the config-to-policy conversion.

### Impact Explanation
This is a validation-verdict divergence bounded to signer-side policy: a signer relying on `block_proposal_max_age_secs` to reject overly-stale proposals will instead accept them if the other `check_proposal` predicates pass, since the age threshold is not part of the `ProposalEvalConfig` used by that check. This can cause a minority of signers (or all signers depending on config propagation) to sign/accept block proposals that operators intended to reject, which is a "temporary tip disagreement"/policy-enforcement-bypass class finding rather than a chain split, since block acceptance still requires reaching the normal signer weight threshold elsewhere.

### Likelihood Explanation
This is deterministic and always reproducible: any code path that builds a `ProposalEvalConfig` via `From<&SignerConfig>` will produce a value lacking the operator's configured max-age semantics, on every signer that uses this conversion path, with no attacker input required beyond proposing an old block.

### Recommendation
Add `block_proposal_max_age_secs` to `ProposalEvalConfig` (or to whatever struct actually consumes it in `check_proposal`) and copy it in the `From<&SignerConfig>` impl at `stacks-signer/src/chainstate/mod.rs:97-111`, then verify a corresponding age check exists and is exercised in `SortitionsView::check_proposal`/`v1.rs`/`v2.rs`.

### Proof of Concept
1. Construct a `SignerConfig` with `block_proposal_max_age_secs = 30`.
2. Call `ProposalEvalConfig::from(&signer_config)` as done throughout the signer (e.g. `stacks-signer/src/chainstate/mod.rs:97`).
3. Observe the resulting `ProposalEvalConfig` has no field corresponding to the max-age setting — confirm by inspecting the struct definition [4](#0-3)  versus the source `SignerConfig` field [1](#0-0) .
4. Propose a block whose header timestamp is far older than 30 seconds; because `check_proposal` operates on `ProposalEvalConfig`, no `ProposalTooOld` rejection is produced by this path even though the operator configured a 30-second bound.
