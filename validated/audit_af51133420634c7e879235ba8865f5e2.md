Confirmed: `ExchangeInjectContract` and `ExchangeWithdrawContract` lack any `expected`/limit field, unlike `ExchangeTransactionContract` which explicitly has `expected` [1](#0-0) .

### Title
Front-runnable exchange withdraw ratio with no slippage protection leads to creator fund loss - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator` (and `ExchangeInjectActuator`) compute the amount of the "other" token to return/require based on the exchange pool's *current* token ratio at execution time, but the `ExchangeWithdrawContract`/`ExchangeInjectContract` protobuf messages carry no `expected`/minimum-amount parameter to bound this calculation, unlike `ExchangeTransactionContract` which explicitly has one.

### Finding Description
When a bancor-style exchange creator withdraws liquidity, `ExchangeWithdrawActuator.execute` reads the live pool balances (`firstTokenBalance`, `secondTokenBalance`) and derives `anotherTokenQuant` proportionally from the ratio at the moment the transaction is executed [2](#0-1) . The `doValidate` method only checks generic sanity conditions (balances non-zero, quant positive, precision) — it never compares the derived `anotherTokenQuant` against any caller-supplied minimum, because `ExchangeWithdrawContract` has no such field [3](#0-2) .

By contrast, `ExchangeTransactionActuator` (buy/sell against the pool) explicitly guards against exactly this class of bug: it takes a `tokenExpected` value from the contract and rejects the transaction if the actual computed output is worse than expected: `if (anotherTokenQuant < tokenExpected) { throw new ContractValidateException("token required must greater than expected"); }` [4](#0-3) . This is the exact "hard limit passed as a parameter" mitigation recommended in the external report. `ExchangeWithdrawActuator` and `ExchangeInjectActuator` were not given the same protection, even though they perform the same class of "ratio-at-execution-time" computation via `exchangeCapsule.getFirstTokenBalance()`/`getSecondTokenBalance()` [5](#0-4) .

Any anonymous actor can broadcast an `ExchangeTransactionContract` (buy/sell) transaction that shifts the pool ratio immediately before a pending `ExchangeWithdrawContract` transaction from the exchange creator is packed into the same or a later block, since `ExchangeCapsule.transaction` directly mutates `firstTokenBalance`/`secondTokenBalance` on the shared, publicly-writable `ExchangeStore`/`ExchangeV2Store` [6](#0-5) . This is analogous to the reported "front-run the buyer to change price" bug class, but here it manifests as changing the token composition a liquidity withdrawer receives.

### Impact Explanation
An attacker who observes a pending `ExchangeWithdrawContract` in the mempool can front-run it with a large `ExchangeTransactionContract` trade against the same exchange pair, skewing the pool ratio so the withdrawer/creator receives a much less favorable split of `tokenID`/`anotherTokenID` than expected at submission time — an unpredictable, unbounded economic loss for the withdrawing party, with no way to cap it via the transaction itself. The same applies to `ExchangeInjectActuator`, where an injector can be forced to deposit an unexpectedly large or small counterpart amount. This falls under "asset or accounting corruption" via manipulation of publicly-writable exchange state reachable from any broadcast transaction.

### Likelihood Explanation
Exploitation requires only the ability to observe pending transactions (mempool visibility) and broadcast an ordinary `ExchangeTransactionContract` transaction ahead of the target's withdraw/inject transaction — no privileged role, leaked key, or malicious node/peer behavior is needed. This is a standard front-running pattern already explicitly anticipated and partially mitigated for `ExchangeTransactionActuator` in this same codebase (via `expected`), but the mitigation was not applied consistently to the sibling actuators.

### Recommendation
Add a caller-supplied minimum/maximum bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring the `expected` field already present on `ExchangeTransactionContract`), and validate the execution-time-computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate` / `ExchangeWithdrawActuator.doValidate`, rejecting the transaction if the actual ratio deviates unfavorably beyond the caller's tolerance.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeWithdrawContract{exchangeId, tokenId=A, quant=Q}` expecting to receive `X` of token B based on the current pool ratio.
2. Attacker observes this pending transaction and broadcasts `ExchangeTransactionContract{exchangeId, tokenId=A, quant=largeAmount, expected=...}` with a higher gas/priority so it lands first, calling `ExchangeCapsule.transaction` and shifting `firstTokenBalance`/`secondTokenBalance` [7](#0-6) .
3. The withdraw transaction executes afterward using the now-skewed ratio in `ExchangeWithdrawActuator.execute`, at line 79-88, computing `anotherTokenQuant` far below `X`, with no on-chain field available to have prevented or capped this outcome [8](#0-7) .

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
