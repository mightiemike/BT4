I found a concrete analog to the reported bug class: `AccountsDb::load()` implements a zero-lamport filter that its sibling read paths (`scan_accounts` and `index_scan_accounts`'s `do_load` fallback) do not consistently apply.

### Title
Zero-lamport (deleted) accounts are not filtered by `index_scan_accounts`, unlike `load()`/`load_while_filtering` - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::load()` is documented and implemented to strip zero-lamport accounts from results ("note this returns None for accounts with zero lamports"), applying `.filter(|(account, _)| !account.is_zero_lamport())` on top of `do_load()`. [1](#0-0)  However, `index_scan_accounts()`, the path used for secondary-index (program-id / SPL-token owner / mint) scans, calls `self.do_load(...)` directly and passes whatever it returns straight to `scan_func`, bypassing the zero-lamport filter entirely. [2](#0-1)  This mirrors the reported `VotingEscrow` pattern where a protective check (`balanceOfNFT`'s flash-loan guard) exists in one accessor but is missing from sibling accessors (`balanceOfNFTAt`, `_balanceOfNFT`) that traverse the same underlying state.

### Finding Description
`do_load()` is the low-level accessor that reads from the write cache, read-only cache, or storage/index, with no notion of "deleted" accounts. [3](#0-2)  The higher-level `load()` wrapper is the one that establishes the invariant that a lamports==0 account (Solana's convention for a "closed"/deleted account) is treated as non-existent, by filtering it after calling `do_load`. [1](#0-0) 

Both `scan_accounts()` and `index_scan_accounts()` are alternate "sibling" accessors intended to enumerate the same underlying account state visible from a set of `ancestors`, analogous to `balanceOfNFTAt`/`_balanceOfNFT` mirroring `balanceOfNFT`. `scan_accounts()` calls `accounts_index.scan_accounts` and passes the raw loaded account to `scan_func` without ever checking `is_zero_lamport()`. [4](#0-3)  `index_scan_accounts()` similarly calls `do_load` directly (not `load()`), so a zero-lamport, i.e., closed, account referenced from the secondary program-id/SPL-token index will still be surfaced to `scan_func`. [5](#0-4) 

Consumers of these two scan entry points apply filtering inconsistently at the call-site level rather than centrally: `Accounts::load_largest_accounts` explicitly re-checks `account.lamports() == 0` and skips the account, [6](#0-5)  and `Accounts::load_while_filtering` (used by `load_by_program`/`load_by_program_with_filter`) checks `account.is_loadable()`, which presumably also excludes zero-lamport accounts. [7](#0-6)  But `Accounts::load_by_index_key_with_filter`, which is the caller of `index_scan_accounts`, only applies the caller-supplied `filter` closure and its own byte-size accounting — it does not itself check `is_loadable()`/zero-lamports before accepting the account into `collector`. [8](#0-7)  Since the protection against returning zero-lamport (deleted) accounts lives only in `load()` and in some call sites' bespoke re-checks — not in the shared `scan_accounts`/`index_scan_accounts` core — any caller of the secondary-index scan path that does not itself re-implement the zero-lamport check will surface a "resurrected" (already-closed) account.

### Impact Explanation
An account whose lamports have been reduced to zero is Solana's convention for "closed"; RPC's `getProgramAccounts` and other index-based lookups routed through `index_scan_accounts` are expected to treat it as non-existent, mirroring `load()`'s behavior. Because the check is not centralized, a caller of `load_by_index_key_with_filter` (indexed-lookup path for `getProgramAccounts` with `program-id`/`spl-token-owner`/`spl-token-mint` filters) can silently receive and return a closed account's last stored state as if it were live — a silent, incorrect account existence/balance result to external callers, without any storage or index corruption.

### Likelihood Explanation
This triggers whenever secondary account indexes (`--account-index`) are enabled and a previously indexed account is later closed (lamports set to zero) but its index entry has not yet been purged by `clean`/`purge`, which is a normal, frequent occurrence during operation, not a special adversarial condition. The lattice-hash/consensus-critical paths (`calculate_accounts_lt_hash_at_startup_from_index`, `verify_accounts`) are unaffected because they use `get_with_and_then` directly and separately filter zero-lamport lt-hash contributions, [9](#0-8)  so this is scoped to the RPC/secondary-index scan surface rather than consensus state.

### Recommendation
Apply the same zero-lamport filtering uniformly across all account-read/scan entry points that are meant to represent "does this account currently exist," consistent with `load()`'s `.filter(|(account, _)| !account.is_zero_lamport())`. Either move the filter into `do_load()` itself (if no caller legitimately needs to see zero-lamport rows), or explicitly filter inside `scan_accounts()` and `index_scan_accounts()` before invoking `scan_func`, and remove the ad hoc, easily-missed zero-lamport re-checks scattered across individual call sites in `accounts.rs`.

### Proof of Concept
1. Enable `--account-index program-id`.
2. Store an account owned by program `P` with a nonzero balance, then let it be indexed.
3. Transfer all lamports out of the account (lamports → 0) and root/flush the slot, but do not yet run `clean` to purge the index entry (or run `clean` before the zero-lamport version's ref-count drops to remove it — the tombstone/zero-lamport-single-ref removal in `clean_accounts` runs on its own schedule, e.g. gated by `latest_full_snapshot_slot` as seen in `can_purge_zero_lamport_single_ref_after_shrink`). [10](#0-9) 
4. Call `Accounts::load_by_index_key_with_filter` (as used by the `getProgramAccounts` RPC path with a secondary index) for program `P`.
5. Observe that `AccountsDb::index_scan_accounts` → `do_load` returns the closed account (lamports=0, but with its last stored data/owner) and, because `load_by_index_key_with_filter` does not itself drop zero-lamport accounts, this appears in the result set — unlike an equivalent non-indexed `load_by_program` call, which goes through `load_while_filtering`'s `is_loadable()` check and is expected to exclude it.
