### Title
Unbounded recursion in transaction final-outcome assembly allows stack-overflow DoS via deep receipt chains - ([File: chain/chain/src/chain.rs])

### Summary
`Chain::get_recursive_transaction_results` walks the outcome tree of a transaction by recursing once per receipt in the DAG, with no depth limit, mirroring the CVE-2017-9208 class of bug (unbounded recursive resolution causing stack exhaustion on attacker-influenced input). [1](#0-0)  The recursion depth is driven entirely by the length of the receipt/promise chain that a transaction produced, which an unprivileged account can grow arbitrarily by chaining self cross-contract calls (`promise_then`/`promise_batch_then`) across many transactions/blocks, as demonstrated by the existing test helper `max_self_recursion_delay` that recursively re-invokes itself via promises. [2](#0-1) 

### Finding Description
`get_final_transaction_result` (used to answer the `tx`/`EXPERIMENTAL_tx_status` JSON-RPC query, invoked from `TxStatus` handling in `chain/client`) calls `get_recursive_transaction_results`, which for each outcome recursively calls itself once per `receipt_ids` entry, with no bound on recursion depth: [3](#0-2) 

```rust
fn get_recursive_transaction_results(...) -> Result<(), Error> {
    ...
    for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
        let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
        self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
    }
    Ok(())
}
```

This differs from the sibling `ReceiptToTx` traversal path in `near_chain::receipt_to_tx`, which the codebase authors explicitly hardened with a `MAX_DEPTH = 1000` limit and a `DepthExceeded` error to prevent exactly this class of issue, as shown by the dedicated regression test constructing a 1002-hop chain: [4](#0-3)  No equivalent depth check exists for `get_recursive_transaction_results`.

A transaction's receipt chain length is bounded only by gas/time and account balance, not by protocol-level depth limits enforced at this RPC layer; an attacker controlling a contract account can generate deep receipt DAGs by chaining self-calls over many blocks (the `promise_then`/`promise_batch_then` primitives allow this, and the codebase already ships a test contract method whose explicit purpose is to recurse via self cross-contract calls "for as long as possible"). [5](#0-4) [2](#0-1) 

### Impact Explanation
Any unprivileged RPC caller who knows (or guesses) the hash of a transaction with a sufficiently deep receipt chain can trigger `get_final_transaction_result`, causing the RPC/view-client node's thread to recurse deeply and potentially exhaust the stack, crashing that node process (denial of service). Because this can be triggered purely by a transaction hash lookup over JSON-RPC by any caller, and the attacker fully controls how deep the chain is (by deploying/calling a self-recursing contract), this is a transaction/RPC-triggered node halt reachable without any special privileges — matching the required "transaction-triggered halt" impact category.

### Likelihood Explanation
Medium: creating a very deep receipt/promise chain requires the attacker to spend gas across multiple transactions/blocks (each hop costs gas and consumes multiple blocks due to cross-shard/receipt scheduling), so building a stack-overflow-depth chain is not free, but it is entirely achievable with a simple self-recursing contract funded with enough gas/NEAR, and no protocol limit at this specific code path prevents it (unlike the parallel `ReceiptToTx` path, which was already patched with `MAX_DEPTH`).

### Recommendation
Convert `get_recursive_transaction_results` to an iterative (stack/queue-based) traversal, or add an explicit depth/count limit (returning an error such as `DepthExceeded`, consistent with the pattern already used in `near_chain::receipt_to_tx`) before recursing further. [6](#0-5) 

### Proof of Concept
1. Deploy a contract exposing a method equivalent to `max_self_recursion_delay`, which on each invocation issues a `promise_batch_create`/`promise_batch_action_function_call_weight` call to itself, recursing until gas runs out. [2](#0-1) 
2. Repeatedly invoke this method across many blocks (each top-level call chains further self-calls), accumulating a receipt DAG whose depth (chain of `SuccessReceiptId`/`receipt_ids` links) grows into the thousands.
3. Call the JSON-RPC `tx`/`EXPERIMENTAL_tx_status` endpoint for the originating transaction hash, which drives `Chain::get_final_transaction_result` → `get_recursive_transaction_results`. [7](#0-6) 
4. The unbounded recursive walk over the receipt chain causes stack growth proportional to chain depth, leading to stack overflow and crash of the querying node's process once depth exceeds the thread's stack capacity.

Note: I could not fully trace the exact call path from the JSON-RPC handler through `view_client_actor.rs`'s `TxStatus`/`TxStatusOutcome` handling to `get_final_transaction_result` within the available search iterations (the identifiers didn't directly match in `view_client_actor.rs`, suggesting the call may go through `chain/client/src/lib.rs` or `TxStatusRequest`/`TxStatusResponse` network types). This should be verified with direct file reads of `chain/client/src/lib.rs` and `chain/jsonrpc/src/api/transactions.rs` before treating this as fully confirmed.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Returns FinalExecutionOutcomeView for the given transaction.
    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);

    let promise_idx = promise_batch_create(u64::MAX, 1);

    let gas_fixed = 0;
    let gas_weight = 1;

        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );

/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded

#[test]
fn test_receipt_to_tx_depth_exceeded() {

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),

    for i in 0..chain_len - 1 {

#### promise_then

```rust
promise_then(promise_idx: u64,
             account_id_len: u64,
             account_id_ptr: u64,
             method_name_len: u64,
             method_name_ptr: u64,
             arguments_len: u64,
             arguments_ptr: u64,

Attaches the callback that is executed after promise pointed by `promise_idx` is complete.

###### Panics

- If `promise_idx` does not correspond to an existing promise panics with `InvalidPromiseIndex`.
- If `account_id_len + account_id_ptr` or `method_name_len + method_name_ptr` or `arguments_len + arguments_ptr`
  or `amount_ptr + 16` points outside the memory of the guest or host, with `MemoryAccessViolation`.
- If called in a view function panics with `ProhibitedInView`.

###### Returns

- Index of the new promise that uniquely identifies it within the current execution of the method.
