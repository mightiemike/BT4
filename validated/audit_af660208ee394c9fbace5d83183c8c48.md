### Title
Bancor-style Exchange market math uses lossy floating-point arithmetic with no reserve-drift/bad-debt safeguard - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
TRON's on-chain token exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract`) prices trades using a Bancor-style relay-supply formula computed with Java `double` arithmetic in the default (non-hardened) path [1](#0-0) . There is no mechanism to detect, cap, or socialize the cumulative rounding drift this introduces into the pool's internal reserve accounting (`firstTokenBalance`/`secondTokenBalance`), and no insurance/backstop exists for the case where accumulated drift makes the internal accounting inconsistent with what the exact-math withdraw/inject paths expect.

### Finding Description
`ExchangeCapsule.transaction()` executes a trade by calling `Processor.exchange()`, which by default resolves to `ExchangeProcessor` (not `SafeExchangeProcessor`) unless the `hardenedCalc`/`AllowHardenExchangeCalculation` flag is enabled [2](#0-1) . `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the trade output using `double`-based `Maths.pow` and division, then cast the `double` result to `long`, silently truncating and accumulating floating-point rounding error on every trade [1](#0-0) .

By contrast, `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-token amount using exact `BigInteger`/`BigDecimal` proportional math against the *current* `firstTokenBalance`/`secondTokenBalance` fields [3](#0-2) [4](#0-3) . Because the reserve numbers that these exact-math actuators trust were themselves produced by the lossy, non-reconciled `ExchangeProcessor` trade path, repeated trading (analogous to the report's "small, uneconomical positions accumulating over time") gradually pushes the recorded reserve away from the value that would keep the pool's constant-ratio invariant consistent. The protocol has no equivalent of an "insurance fund" or "loss socialization" step to true-up this drift — the only mitigation is the opt-in `SafeExchangeProcessor`/`hardenedCalc` path, which is not the default and is gated behind `dynamicStore.supportAllowHardenExchangeCalculation()`-style flags, matching the report's core complaint that bad-debt mechanisms are absent by default [5](#0-4) .

### Impact Explanation
This is reachable from an ordinary, unprivileged `ExchangeTransactionContract` broadcast transaction — any account can trade against a public exchange pool. Over many trades the pool's tracked reserves can diverge from what a fair constant-product/relay accounting would imply. Whichever party (typically the pool creator, since TRON's on-chain Exchange has a single owner who created/injected the reserves) attempts a later `ExchangeWithdrawContract` is validated and executed against the drifted, floating-point-derived reserve figures rather than the true economic backing, so the outcome of a withdrawal silently reflects accumulated rounding loss instead of the exact reserve. There is no accounting mechanism to flag, cap, or compensate for this loss.

### Likelihood Explanation
Likelihood is **Medium**: the drift accumulates gradually and requires many trades (or extreme-ratio, large-quant trades that maximize `Math.pow`-based rounding error) to become material; TRON operators can also mitigate by enabling the hardened calculation path. However, the vulnerable default path (`ExchangeProcessor`, not `SafeExchangeProcessor`) is reachable by any unprivileged trader via a normal broadcast transaction, requires no special permission, and the drift is monotonic/unrecoverable since nothing reconciles it.

### Recommendation
- **Short term**: Make the exact, overflow-safe `SafeExchangeProcessor` the default (or only) execution path for `ExchangeTransactionActuator`, removing the lossy `double`-based `ExchangeProcessor` from production use, matching the constraint checks (`newFirstTokenBalance < 0`) already present only in the hardened path [6](#0-5) .
- **Long term**: Add invariant/reconciliation checks after each trade (e.g., verifying the constant-product/relay-supply invariant holds within a strict tolerance) and reject or clamp trades that would push the pool's book balance out of sync with the value that inject/withdraw math assumes, so no unrecoverable drift can accumulate without detection.

### Proof of Concept
Not independently executed against a live node; based on static analysis of `ExchangeProcessor.exchange()` (double/`Math.pow`-based) versus the exact BigInteger/BigDecimal math used in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation, and the existence of `ExchangeProcessorTest` cases explicitly probing overflow/precision boundaries confirming the non-hardened path's rounding behavior [7](#0-6) . A full PoC (many sequential `ExchangeTransactionContract` calls with extreme ratios followed by an `ExchangeWithdrawContract`) would require live-node execution, which is out of scope for this analysis — a Devin session with access to a running/test java-tron node would be needed to quantify the actual drift magnitude and confirm exploitability at scale.

    logger.debug("balance: " + balance);

    logger.debug("balance + quant: " + newBalance);

    long out = (long) issuedSupply;
    supply += out;

  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}

  @Test
  public void testSafeProcessorNoOvershootForTypicalInputs() {
