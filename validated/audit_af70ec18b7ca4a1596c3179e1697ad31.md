### Title
Unmetered CPU cost of ELF parsing/verification in loader-v3 `DeployWithMaxDataLen` breaks compute metering totality - ([File: program-runtime/src/deploy.rs])

### Summary
`deploy_program` in `program-runtime/src/deploy.rs` performs `Executable::<InvokeContext>::load()` and `executable.verify::<RequisiteVerifier>()` over the full programdata buffer without ever calling `invoke_context.consume_compute()`, so this CPU work is invisible to the compute-unit budget. Separately, `CostModel::get_instructions_data_cost` only charges based on the tiny outer `DeployWithMaxDataLen` instruction payload, not the actual buffer/programdata size, so the block-cost estimate and the post-execution "actual" cost both fail to reflect real CPU work that scales with attacker-controlled program size.

### Finding Description
The `UpgradeableLoaderInstruction::DeployWithMaxDataLen` handler in `programs/bpf_loader/src/lib.rs` validates buffer/program accounts and then, via the `deploy_program!` macro, invokes `program-runtime/src/deploy.rs::deploy_program`, which does: [1](#0-0) 

Note there is no `invoke_context.consume_compute(...)` call anywhere in `deploy_program`, unlike other CPU-bound VM operations elsewhere in the runtime. `Executable::load` parses the ELF header/sections and `verify::<RequisiteVerifier>` walks every instruction in the program — both scale with the size of `programdata`, which for `DeployWithMaxDataLen` is the full buffer content (up to the account's data length), assembled beforehand via chunked `Write` instructions.

On the cost-model side, the *estimated* cost for the transaction is computed via `CostModel::get_instructions_data_cost`, which only measures the outer instruction's own byte length: [2](#0-1) [3](#0-2) 

`DeployWithMaxDataLen`'s own instruction data only contains the `max_data_len` field (a handful of bytes), so `data_bytes_cost` is negligible regardless of how large the referenced buffer/programdata actually is — the programdata is an *account*, not instruction data, so it is never counted here.

For builtins, the estimated `programs_execution_cost` is either the user-requested CU limit or a fixed per-program constant (`UPGRADEABLE_LOADER_COMPUTE_UNITS`), confirmed by the existing test harness which asserts a fixed CU adjustment independent of buffer size: [4](#0-3) [5](#0-4) 

Because `deploy_program` never calls `consume_compute`, the *actual* executed compute units (`executed_units`) used later by `CostModel::calculate_cost_for_executed_transaction` also does not reflect the ELF-parsing/verification work — this cost is genuinely metering-invisible, not merely mis-estimated ahead of time. As a result, neither the pre-execution cost-model estimate nor the post-execution recorded cost captures CPU work that scales with the size of an attacker-controlled program.

An unprivileged attacker with a funded keypair can: (1) create and fully populate a buffer account up to the maximum permitted account size via ordinary `Write` instructions (standard, permissionless flow used by every SBF program deployer), and (2) submit a single `DeployWithMaxDataLen` instruction referencing that buffer. All existing checks (authority signature, buffer ownership, rent-exemption) are satisfied by an ordinary deployer and do nothing to bound or meter the ELF-parsing cost.

### Impact Explanation
This is a metering-totality violation: CPU-intensive, attacker-sized work (ELF parse + verify) executes inside a builtin instruction handler without being charged against the compute budget or reflected in the cost model, and it is also invisible to `executed_units` used for post-hoc cost recording. A validator/leader can pack many `DeployWithMaxDataLen` instructions — each accounted at only a small fixed compute-unit cost — into a block up to `MAX_BLOCK_UNITS`, while each instruction actually performs multi-megabyte ELF parsing/verification. This lets an attacker force validators to perform CPU work disproportionate to the CU cost charged, degrading block-processing time relative to the cost-model's expectations — a resource-exhaustion/liveness-degradation vector, matching Solana's "computational resource exhaustion / cost model divergence" bounty category rather than a funds-theft or consensus-divergence bug.

### Likelihood Explanation
Preconditions are trivial and fully within reach of an unprivileged attacker: a funded keypair, a rent-exempt buffer account populated via standard `Write` instructions, and a rent-exempt uninitialized program account — this is the exact deployment path every SBF developer already uses (`cli/src/program.rs::do_process_program_deploy`, `programs/bpf_loader/src/lib.rs` `DeployWithMaxDataLen` handler). The cost to the attacker is the normal deployment rent/fees; the attack is trivially repeatable by deploying many large programs. The repo's own `core/tests/scheduler_cost_adjustment.rs` test harness was purpose-built to measure exactly this class of divergence between cost-model estimate/adjustment and real execution, indicating the underlying concern is already known and instrumented in this codebase, but not fixed for the ELF-load/verify cost specifically.

### Recommendation
Meter the ELF loading and verification cost explicitly inside `deploy_program` (e.g., call `invoke_context.consume_compute()` proportional to `programdata.len()` before/while calling `Executable::load` and `verify::<RequisiteVerifier>`), and/or have `CostModel` account for the referenced buffer/programdata length (not just instruction data length) when estimating cost for `DeployWithMaxDataLen`/`Upgrade` instructions, so that both the pre-execution estimate and the post-execution actual cost scale with the real CPU work performed.

### Proof of Concept
Extend `core/tests/scheduler_cost_adjustment.rs`'s `TestSetup::deploy_with_max_data_len_ix` to parameterize the buffer/program size (e.g., from a small memo-sized program up to `MAX_PERMITTED_DATA_LENGTH`), and add a test that:
1. Builds and deploys buffers of varying sizes (e.g., 1 KB, 1 MB, 10 MB).
2. Measures wall-clock time of `execute_test_transaction` for each size (or directly benchmarks `deploy::deploy_program`).
3. Reads `cost_adjustment`/`executed_units` reported by the harness for each size.
4. Asserts that while `cost_adjustment`/`executed_units` remain flat (equal to `UPGRADEABLE_LOADER_COMPUTE_UNITS`) across all sizes, measured wall-clock execution time grows roughly linearly with buffer size — demonstrating that CPU cost is not reflected in CU accounting, i.e., metering totality is violated.
