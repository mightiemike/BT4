### Title
Incoming/delayed cross-shard receipt that fails re-validation panics the runtime instead of being handled gracefully - ([File: chain/chain/src/runtime/mod.rs])

### Summary
This is the same bug class as CVE-2021-47145: an error path that should return a recoverable error instead hits a hard `panic!`/`BUG_ON`-equivalent, turning a normal error condition into a crash. In nearcore, `RuntimeError::ReceiptValidationError` and `RuntimeError::UnexpectedIntegerOverflow` returned from `Runtime::apply` are explicitly converted into `panic!()` calls rather than being surfaced as recoverable errors.

### Finding Description
`Runtime::apply` validates every incoming and delayed cross-shard receipt with `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)` before executing it: [1](#0-0) 

and for delayed receipts: [2](#0-1) 

If this validation fails for an *incoming* receipt, `Runtime::apply` returns `Err(RuntimeError::ReceiptValidationError(e))` (propagated via `?` from `process_incoming_receipts`). The caller in `chain/chain/src/runtime/mod.rs` explicitly turns this into a hard panic instead of a handled error, with an inline TODO acknowledging this is a known-bad shortcut: [3](#0-2) 

The same anti-pattern exists in `RuntimeUser::process_transaction` (used by the test/user harness that exercises the same runtime code paths): [4](#0-3) 

The codebase's own protocol-model documentation confirms this class of failure is intentionally routed to a fatal path rather than a soft error: "a delayed receipt that fails `validate_receipt` on dequeue is treated as `StorageInconsistentState`" and "an incoming or delayed receipt that fails validation is a `RuntimeError`, not an action error, so enforcing this ... would fail the whole chunk": [5](#0-4) [6](#0-5) 

The test comment at `action_validation.rs:1817-1823` demonstrates the developers are aware of at least one concrete way this triggers: `ValidateReceiptMode::NewReceipt` enforces a stricter entry-count limit than `ValidateReceiptMode::ExistingReceipt`, and this asymmetry exists specifically because a receipt created under an older protocol version (before a new validation rule activated) can still be in flight (delayed/buffered/forwarded across shards) when the new rule activates on the receiving shard. Any receipt that is legitimately produced by a normal user transaction/contract call (any account, no special privilege required) as an outgoing receipt, gets buffered or delayed across a chunk/epoch boundary, and then fails the (potentially stricter, protocol-version-dependent, or config-dependent) `ExistingReceipt` validation on dequeue/incoming-processing will cause every honest validator processing that shard to panic on `chain/chain/src/runtime/mod.rs:372` — a crash triggered purely by transaction/contract-call activity, not by malicious validator/network behavior.

### Impact Explanation
A panic inside `Runtime::apply` is not a "reject this receipt" outcome — it aborts the node process (or in test/RPC-node contexts, the `chunk view` client) that is applying that chunk. Since all correctly-functioning validators tracking the shard execute the identical deterministic state transition, they would all hit the same panic when processing the same receipt, producing a synchronized, transaction-triggered chain halt for that shard (denial of service against the whole network for that shard, not just one operator). This matches the "Accept only... a transaction-triggered halt" bar in the validation rules. Because `apply` is also invoked by RPC-serving nodes (e.g. via `runtime/mod.rs`) and test/relay harnesses (`runtime_user.rs`), the crash surface is broader than block production alone.

### Likelihood Explanation
Reachability requires only a normal user constructing a cross-contract call whose resulting receipt legitimately validates under `NewReceipt` mode at creation time but no longer validates under `ExistingReceipt` mode by the time it is dequeued (e.g., across a protocol-version upgrade boundary, or via any future validation-rule tightening that isn't correctly version-gated for `ExistingReceipt`). The devs' own regression test (`action_validation.rs` `test_..._receipt_size_validation`-style logic at lines 1809-1823) demonstrates this exact scenario is a known, previously-hit failure mode for at least one validation rule (nested-delegate action-count limit), which had to be special-cased to avoid the panic. This shows the general pattern is realistic and has already manifested once; any future new validation rule added to `validate_receipt` without equally careful `ExistingReceipt` gating reproduces the same crash. Likelihood is Medium: it is not exploitable today with a single simple transaction against the current rule set as far as can be confirmed from the index, but the underlying defect (treating a receipt-validation error as an unconditional `panic!` in the runtime caller, rather than a controlled degrade/reject) is present in production code today and has already required an ad hoc workaround for one rule.

### Recommendation
Do not `panic!()` on `RuntimeError::ReceiptValidationError` / `RuntimeError::UnexpectedIntegerOverflow` in `chain/chain/src/runtime/mod.rs` (and the equivalent path in `integration-tests/src/user/runtime_user.rs`). Instead:
- Treat these as `Error::StorageError`-equivalent fatal-but-non-panicking errors that stop chunk application gracefully (as is already done for `RuntimeError::StorageError`), or
- Ensure every validation rule added to `validate_receipt` is unconditionally protocol-version-gated identically for `ValidateReceiptMode::ExistingReceipt` as it was at `NewReceipt` time, so an already-in-flight receipt can never retroactively fail validation.
- Resolve the referenced `TODO(#2152)` by implementing "process gracefully" as originally intended rather than leaving the panic in place.

### Proof of Concept
Not independently reproducible from the indexed code alone — the exact conditions require either (a) a future/careless addition of a validation rule to `validate_receipt` without matching `ExistingReceipt`-mode version gating, or (b) confirming a currently-shippable transaction sequence that straddles a protocol-version activation boundary for one of the rules gated only for `NewReceipt`.
