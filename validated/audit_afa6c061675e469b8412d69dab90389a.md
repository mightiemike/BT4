### Title
Node-restart config change to `l1_handler_cancellation_timelock_seconds` retroactively alters pending L1-handler cancellation outcomes - ([File: crates/apollo_l1_events/src/transaction_record.rs])

### Summary
`TransactionRecord::update_time_based_state` computes whether a cancellation-requested L1 handler transaction has become fully `CancelledOnL2` by adding the *current* `l1_handler_cancellation_timelock_seconds` config value to the stored `cancellation_requested_at` timestamp, rather than a value captured at the moment the cancellation was requested. If an operator changes this config (via redeploy/restart, since `L1EventsProviderConfig` is loaded from static config files, e.g. `crates/apollo_deployments/resources/app_configs/l1_events_provider_config.json`), transactions whose cancellation was already requested get re-evaluated against the new timelock value, not the one in effect when the cancellation was initiated.

### Finding Description
The lifecycle logic is:
1. `mark_cancellation_request` in `crates/apollo_l1_events/src/transaction_record.rs` (lines 77-101) stores only `cancellation_requested_at = Some(timestamp)` — it does not snapshot the timelock duration in effect at request time.
2. `update_time_based_state` (lines 194-208) later computes `is_cancellation_timelock_passed` using `policy.cancellation_timelock`, where `policy` is built fresh on every call in `TransactionManager::validate_tx` (`crates/apollo_l1_events/src/transaction_manager.rs` lines 116-121):
```
let policy = TransactionRecordPolicy {
    cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
};
```
This reads `self.config.l1_handler_cancellation_timelock_seconds` live, at call time, from `TransactionManagerConfig`, which is itself derived from `L1EventsProviderConfig` (`crates/apollo_l1_events_config/src/config.rs` lines 79-104). Because this is a node-level configuration value (not a per-tx-committed on-chain parameter), if the value is changed and the node restarted, an in-flight cancellation record initiated under the old timelock is subsequently evaluated with the new timelock value. ### Impact Explanation
The concrete impact is bidirectional and node-state-affecting:
- If the timelock is **increased**, a cancellation-requested transaction that would have flipped to `CancelledOnL2` (and thus become non-`is_validatable`, `crates/apollo_l1_events/src/transaction_record.rs` line 179-181) under the old value stays validatable/proposable for longer than the L1 canceller intended, potentially allowing the L1 handler transaction to still be proposed/included on L2 after the user/L1 canceller believed cancellation would take effect.
- If the timelock is **decreased**, a transaction is cancelled earlier than the original policy promised, which could unexpectedly block inclusion of a transaction that should still have been includable, causing message-processing freezing/delay inconsistent with the guarantee at request time.

Since each node independently applies its own locally configured `l1_handler_cancellation_timelock_seconds` (this is a static per-node config, not part of consensus-agreed state), if different sequencer/validator nodes are running with different config values (e.g., during a staged rollout where some nodes have updated config and others haven't) they will disagree on whether the same L1 handler transaction is `CancelledOnL2` or still `Pending`, causing divergent `is_validatable` results and validation-status responses (`ValidationStatus::Validated` vs `CancelledOnL2`) across nodes for the same transaction — an honest-node divergence in a value that feeds directly into block validation.

### Likelihood Explanation
Likelihood is Medium: this requires an operator to change `l1_handler_cancellation_timelock_seconds` while cancellation-requested transactions are in flight, which is an operational/config-rollout event rather than an attacker-triggered one per se, but it is deterministic and guaranteed to occur whenever such a rollout happens with any in-flight cancellation. The config is applied per-node from a static JSON file loaded at startup, so a rolling restart during a config change naturally produces a window of inter-node inconsistency.

### Recommendation
Snapshot the cancellation timelock (or the resulting cancellation-effective timestamp, i.e. `requested_at + cancellation_timelock`) into the `TransactionRecord` at the moment `mark_cancellation_request` is called, rather than reading it live from `self.config` in `update_time_based_state`/`validate_tx`. This ensures any given cancellation request is judged against the policy that was in force in effect when it was initiated, consistent with the semantics of the analogous bug in the referenced report (freezing the delay applicable to a request at its initiation time, not at use time).

### Proof of Concept
1. Node A is running with `l1_handler_cancellation_timelock_seconds = 300` (5 minutes, the default in `crates/apollo_l1_events_config/src/config.rs` line 30).
2. An L1 cancellation request for L1 handler tx `T` arrives; `mark_cancellation_request` records `cancellation_requested_at = t0` and sets state `CancellationStartedOnL2`.
3. Before 300 seconds elapse, the operator updates the deployed config (e.g. `crates/apollo_deployments/resources/app_configs/l1_events_provider_config.json`) to `l1_handler_cancellation_timelock_seconds = 30` and restarts the node (or a subset of nodes in the fleet, given rolling restarts).
4. At `t0 + 40s`, `validate_tx` is called for `T`; `update_time_based_state` computes `policy.cancellation_timelock = 30s` (the new value), concludes the timelock has passed, and marks `T` as `CancelledOnL2` — 260 seconds earlier than the guarantee in effect when the cancellation was requested.
5. Meanwhile, a node that has not yet restarted with the new config still uses `300s`, and at `t0+40s` still reports `T` as validatable (`ValidationStatus::Validated`), diverging from the restarted node's `CancelledOnL2` result for the identical transaction and identical wall-clock time — an honest-node divergence in validation status caused solely by config-reload timing, not by any protocol-level disagreement.     pub fn mark_cancellation_request(
```rust
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }
```

```rust
    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
```

```rust
    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }
```
