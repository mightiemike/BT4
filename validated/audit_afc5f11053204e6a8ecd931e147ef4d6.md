## Title
`PoisonMicroblock` consensus validation accepts non-conflicting microblock headers from unrelated tenures, enabling wrongful coinbase slashing after key reuse across forks - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

## Summary
`TransactionPayload::PoisonMicroblock` deserialization in `stacks-codec/src/transaction.rs` only rejects a header pair when **both** `sequence` differs **and** `prev_block` differs, and `check_microblock_header_signer`/`handle_poison_microblock` in `stackslib/src/chainstate/stacks/db/transactions.rs` never re-check that `prev_block` matches either. This means two microblock headers that merely share a `sequence` number but were built on **different parent blocks** (i.e., from two genuinely distinct, non-conflicting tenures) are accepted as "proof" of equivocation as long as they were signed by the same key. If a miner ever reuses the same microblock private key across two different tenures (e.g. on sibling forks around a Bitcoin reorg), anyone can assemble two of that miner's perfectly legitimate, non-conflicting first microblocks (both `sequence == 0`, different `prev_block`) into a `PoisonMicroblock` transaction and slash the coinbase of whichever tenure used that pubkey hash on the now-canonical fork.

## Finding Description
The intended equality for a valid poison report is: *the two presented headers must represent two different continuations from the exact same point in the exact same microblock stream* (i.e. same `prev_block`), proving the signer of `pubkh` actually double-signed within one stream. The code breaks this equality:

- Codec-level guard (only rejects if *both* diverge): [1](#0-0) 
```
// must have the same sequence number or same block parent
if h1.sequence != h2.sequence && h1.prev_block != h2.prev_block {
    return Err(... "microblock headers do not identify a fork" ...);
}
```
This accepts pairs where `sequence` matches but `prev_block` differs — headers from two unrelated tenures.

- `check_microblock_header_signer` only checks that both headers recover to the same pubkey hash; it never inspects `prev_block`: [2](#0-1) 

- `handle_poison_microblock` then only checks that `pubkh` was *ever* used somewhere in the **current fork's** own MARF-backed state (`get_microblock_pubkey_hash_height`) and that it's within the maturity window — it never checks that `mblock_header_1`/`mblock_header_2` actually belong to the microblock stream descended from the specific anchored block that used `pubkh` at `mblock_pubk_height`: [3](#0-2) 

A stricter, matching check *does* exist — but only as a **mempool relay-time filter**, not a consensus/execution-time rule: [4](#0-3) 
```
if microblock_header_1.sequence != microblock_header_2.sequence
    || microblock_header_1.prev_block != microblock_header_2.prev_block
    || microblock_header_1.version != microblock_header_2.version
{
    return Err(MemPoolRejection::PoisonMicroblocksDoNotConflict);
}
```
Because this lives in `will_admit_mempool_tx` (mempool admission only), an attacker who is themselves a miner (or who convinces/pays any miner to include a raw transaction) bypasses this filter entirely by putting the crafted `PoisonMicroblock` transaction directly into their own block. Nothing in `append_block` → `process_transaction` → `handle_poison_microblock` re-applies the `prev_block` equality check.

Exploit flow: a miner (attacker or accidental key-reuse victim) uses the same microblock private key for the first microblock (`sequence = 0`) of two different tenures — one on an abandoned fork X, one on the now-canonical fork Y (this can happen naturally around a Bitcoin reorg, or a malicious minority miner can force it deliberately). Both headers are individually valid, signed, non-conflicting microblocks. An attacker collects header `h_X` (fork X, `sequence=0`, `prev_block = parentBlockX`) and header `h_Y` (fork Y, `sequence=0`, `prev_block = parentBlockY`, honestly mined). Because `h_X.sequence == h_Y.sequence` (both 0) even though `prev_block` differs, the codec accepts the pair; `check_microblock_header_signer` recovers the same `pubkh` for both. `handle_poison_microblock`, running in the context of fork Y's block, finds `pubkh` used at `mblock_pubk_height` (the height of the miner's honest tenure on fork Y) and slashes that tenure's coinbase — even though no actual double-signing occurred within fork Y's own microblock stream.

## Impact Explanation
This lets an unprivileged attacker redirect an honest (or merely key-reusing but non-malicious) miner's matured coinbase reward to the reporter's address on the canonical chain, based on evidence that does not prove any equivocation within that tenure's stream. This is direct block-reward theft/mis-payment on the canonical fork, matching the "Critical – block-reward theft/mis-payment" / "High – poison or reward mis-payment bounded to fees" categories depending on severity framing; because it redirects the entire matured coinbase (not just a fee), it lands in the reward-theft category. All full nodes following consensus rules apply the same wrongful slash deterministically (it's a valid state transition per the current rules), so there's no state-root divergence between honest nodes — the damage is economic (wrong recipient of miner reward), not a chain split.

## Likelihood Explanation
Requires only: (1) the ability to observe two microblocks signed by the same private key with matching `sequence` but differing `prev_block` (from any two tenures, including sibling forks around a natural Bitcoin reorg or an attacker deliberately reusing a key across two of their own tenure attempts), and (2) the ability to include a `PoisonMicroblock` transaction in a block — trivially satisfiable by an unprivileged single-slot miner including it in their own block, bypassing the mempool-only guard. No majority stake, no signer collusion, and no privileged role are needed. The main precondition — microblock-key reuse across tenures — is not automatically enforced/prevented anywhere in the codebase found; it depends on operational key hygiene, but the protocol itself provides no cryptographic or consensus-level barrier against it, and the checks that exist (`has_microblock_pubkey_hash` in `blocks.rs:5553-5568`) only prevent reuse *within a single fork's history*, not across forks/tenures, which is exactly the gap the question targets.

## Recommendation
Enforce the stricter equality used by the mempool filter as an actual consensus rule in `handle_poison_microblock`/`check_microblock_header_signer` (and/or in the codec's `consensus_deserialize`): require `mblock_header_1.prev_block == mblock_header_2.prev_block` (not an OR with sequence) so that only headers proven to be sibling continuations of the *same* point in the *same* microblock stream can constitute valid poison evidence. Additionally, verify that this shared `prev_block` actually chains back (directly or transitively) to the anchored block recorded at `mblock_pubk_height` in the current fork, closing the gap between "pubkh used somewhere in this fork" and "pubkh's *specific* tenure produced this fork."

## Proof of Concept
Rust integration test plan (extending the existing `process_poison_microblock_*` tests in `stackslib/src/chainstate/stacks/db/transactions.rs`):
1. Generate a single microblock private key `k` and its pubkey hash `pubkh`.
2. Build two independent, honestly-signed microblocks with `sequence = 0` but different `prev_block`: `h_X` (as if descending from anchored block `A_X` on "fork X") and `h_Y` (as if descending from anchored block `A_Y` on "fork Y"), both signed with `k`. Assert `h_X.prev_block != h_Y.prev_block` and `h_X != h_Y`.
3. Assert `TransactionPayload::consensus_deserialize` on a `PoisonMicroblock(h_X, h_Y)` payload **succeeds** (demonstrating the codec bug: `assert!(h_X.sequence == h_Y.sequence); assert!(h_X.prev_block != h_Y.prev_block);` yet deserialization does not error).
4. Set up a chainstate where `insert_microblock_pubkey_hash(&mut conn, height_Y, &pubkh)` was called for the (honest) fork-Y tenure only (simulating that fork Y's miner used `pubkh`, matching an actually-honest, non-conflicting stream).
5. Submit the crafted `PoisonMicroblock(h_X, h_Y)` transaction via `StacksChainState::process_transaction`.
6. Assert it is accepted (`Ok`) and that `StacksChainState::get_poison_microblock_report(&mut conn, height_Y)` now returns `Some((reporter_addr, 0))` — i.e., the equality `slashed_tenure(height_Y) == tenure_whose_miner_double_signed` is **false** (no double-sign ever occurred in fork Y's stream), yet the slash record was created, proving the vulnerability.
7. Contrast with `will_admit_mempool_tx`, showing the same transaction is rejected (`MemPoolRejection::PoisonMicroblocksDoNotConflict`) at the mempool layer, confirming the inconsistency between the relay-time guard and the consensus-time (`process_transaction`) guard.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
