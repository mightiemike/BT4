### Title
Blocking `GlobalPreemptibleStrategy.acquire()` can be flooded to exhaust the shared gRPC/HTTP worker thread pool - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/strategy/GlobalPreemptibleStrategy.java])

### Summary
`GlobalPreemptibleStrategy.acquire()` blocks the calling worker thread for up to `DEFAULT_ACQUIRE_TIMEOUT=2` seconds via `sp.tryAcquire(2, TimeUnit.SECONDS)` when `rate.limiter.apiNonBlocking=false` (the default). Any endpoint configured with `GlobalPreemptibleAdapter` and hit with more concurrent requests than its configured permit count will cause each excess request's handling thread to sit blocked for up to 2 seconds inside `RateLimiterServlet.service()` or `RateLimiterInterceptor.interceptCall()`.

### Finding Description
`GlobalPreemptibleAdapter.acquire(data)` delegates to `GlobalPreemptibleStrategy.acquire()`, which calls the blocking `Semaphore.tryAcquire(2, TimeUnit.SECONDS)`. [1](#0-0) 

`IRateLimiter.acquirePermit()` selects blocking vs non-blocking based on the `rate.limiter.apiNonBlocking` config flag, which defaults to `false`: [2](#0-1) [3](#0-2) 

Both `RateLimiterServlet.service()` (HTTP path, Jetty/Tomcat servlet thread) and `RateLimiterInterceptor.interceptCall()` (gRPC path, executor thread) call `rateLimiter.acquirePermit(runtimeData)` synchronously on the request-handling thread before proceeding: [4](#0-3) [5](#0-4) 

So the exploit chain is real and matches the description: an unprivileged client opens more concurrent connections than the configured permit count against any endpoint whose adapter is `GlobalPreemptibleAdapter` with `apiNonBlocking=false` (default), and every excess connection's worker thread blocks for up to 2 seconds. This is confirmed as a genuine, intentional design behavior — the non-blocking alternative (`apiNonBlocking=true`, using `tryAcquire()`) exists specifically to avoid this cost, per the comments in the code itself: "Non-blocking: immediately rejects if no permit is available. Used when the apiNonBlocking switch is on, to shed overload instead of tying up Netty IO / gRPC executor threads while waiting for a permit." [6](#0-5) 

However, I was **unable to verify within the available context** which specific RPC methods or HTTP servlets are actually configured (by default, out-of-the-box config) to use `GlobalPreemptibleAdapter`, nor whether the gRPC/HTTP thread pool sizing (`RpcApiService`/Jetty thread pool config) is bounded tightly enough, or shared broadly enough with unrelated endpoints, for this blocking to cause node-wide stalls versus only affecting the specific limited endpoint's own worker slice. The file `RpcApiService.java` is very large and I could not locate the executor/thread-pool sizing configuration within the excerpt read. This is a gap in verification, not a refutation of the mechanism.

### Impact Explanation
If a `GlobalPreemptibleAdapter`-protected endpoint is reachable by unprivileged/anonymous clients (default node config does not require authentication for HTTP/gRPC APIs) and the request-handling thread pool is shared with other endpoints, this matches a DoS via RPC-API bounty class: an unprivileged client can degrade or stall shared executor threads for up to 2 seconds per excess concurrent connection, with no economic cost (unlike on-chain transactions, HTTP/gRPC API calls do not consume bandwidth/energy).

### Likelihood Explanation
Preconditions are exactly the ones stated: `rate.limiter.apiNonBlocking=false` (default per `RateLimiterConfig.apiNonBlocking`) and at least one endpoint configured with `GlobalPreemptibleAdapter` and a small permit count (e.g., `DEFAULT_PERMIT_NUM=1`). An attacker needs no privileges — just the ability to open many concurrent TCP/HTTP2 connections to the node's public RPC/HTTP port, which is cheap and highly repeatable (no fee, no signature, no on-chain footprint required, since this is a read-side API surface).

### Recommendation
Set `rate.limiter.apiNonBlocking=true` as the default, or bound `DEFAULT_ACQUIRE_TIMEOUT` much lower (or to 0), and/or isolate rate-limited endpoints onto a dedicated bounded executor separate from the main HTTP/gRPC worker pool so that blocking on a permit cannot starve unrelated endpoints. Alternatively, replace the blocking wait with an async/non-blocking permit-queue mechanism that does not tie up a worker thread while waiting.

### Proof of Concept
```java
// JUnit-style PoC using GlobalPreemptibleStrategy directly
@Test
public void testAcquireBlocksWorkerThreadUnderFlood() throws InterruptedException {
  GlobalPreemptibleStrategy strategy = new GlobalPreemptibleStrategy("permit=1");
  int concurrentRequests = 200;
  ExecutorService pool = Executors.newFixedThreadPool(concurrentRequests);
  CountDownLatch latch = new CountDownLatch(concurrentRequests);
  long start = System.currentTimeMillis();
  AtomicInteger blockedCount = new AtomicInteger();

  // Hold the single permit for the whole test window to force others to block
  strategy.acquire();

  for (int i = 0; i < concurrentRequests; i++) {
    pool.submit(() -> {
      long t0 = System.currentTimeMillis();
      boolean acquired = strategy.acquire(); // blocks up to 2s each
      long elapsed = System.currentTimeMillis() - t0;
      if (elapsed >= 1900) {
        blockedCount.incrementAndGet();
      }
      if (acquired) {
        strategy.release();
      }
      latch.countDown();
    });
  }
  latch.await(10, TimeUnit.SECONDS);
  pool.shutdown();

  // Expected: nearly all of the 200 threads were blocked for ~2s each,
  // demonstrating that 200 worker threads were tied up simultaneously.
  assertTrue(blockedCount.get() > concurrentRequests * 0.9);
}
```
Expected result: with `permit=1` and the held permit never released during the test window, all N submitted threads block for the full 2-second `DEFAULT_ACQUIRE_TIMEOUT` before returning `false`, demonstrating N worker threads occupied simultaneously for the duration — this is the mechanism by which flooding a `GlobalPreemptibleAdapter`-protected endpoint ties up N request-handling threads in `RateLimiterServlet.service()`/`RateLimiterInterceptor.interceptCall()`.
