### Title
Reachable panic via `.expect()` on empty L1 handler calldata in `l1_handler_message_hash` - (File: crates/starknet_api/src/hash.rs)

### Summary
`l1_handler_message_hash` (used by `L1HandlerTransaction::calc_msg_hash`) unconditionally calls `calldata.0.split_first().expect(...)`, which panics if the L1 handler transaction's calldata is empty. `Calldata` has no non-empty invariant enforced at the type level, and this exact gap was already identified and partially fixed in a sibling function (`payload_size`) but not in `calc_msg_hash`.

### Finding Description
`l1_handler_message_hash` extracts the `from_address` via `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")`: [1](#0-0) 

If `calldata` is empty, `split_first()` returns `None` and the `.expect()` panics. The codebase itself documents that `Calldata` has no non-empty invariant and that `L1HandlerTransaction` derives `Deserialize`, so an empty-calldata L1 handler transaction is constructible — this is explicitly called out in a nearby fix for `payload_size`, which uses `saturating_sub` specifically "to guard the empty-calldata case": [2](#0-1) [3](#0-2) 

However, `calc_msg_hash` (which calls `l1_handler_message_hash`) was not given the same treatment and still panics on empty calldata: [4](#0-3) 

This is reachable from an L1 message sender: an L1 `sendMessageToL2`-style call (or any deserialization path producing an `L1HandlerTransaction` with empty `calldata`) can produce a transaction that the sequencer must hash. The L1 events scraper computes this hash for every scraped `LogMessageToL2` event when logging diagnostics: [5](#0-4) 

Nothing in the L1 event parsing path (`EventData`/`L1HandlerTransaction::from`) enforces that calldata is non-empty before this hash is computed, since the `Calldata` type itself carries no such invariant.

### Impact Explanation
A malformed or empty-payload `LogMessageToL2` event on L1 (constructible by any L1 sender, since Starknet's L1 core contract accepts an arbitrary payload for `sendMessageToL2`, and calldata composition on L2 origin is not enforced to be non-empty at the L1 contract layer) can cause `calc_msg_hash` to panic when the sequencer's L1 events scraper processes it. Since `L1EventsScraper::run` propagates unexpected errors and the component's `start()` wraps `run()` in `.unwrap_or_else(|e| panic!(...))`, and more critically the underlying panic here is a raw Rust panic (not a caught `Result`) inside `fetch_events`, this crashes the scraper task/process. A crashed L1 events scraper halts ingestion of new L1-to-L2 messages, which can lead to a sequencer/full node unable to process new L1 handler transactions — a form of denial of service reachable by a single crafted L1 message, analogous to the NASM NULL-pointer crash from a mishandled/unvalidated directive value.

### Likelihood Explanation
Likelihood is moderate: it requires sending an L1 message with empty payload to the Starknet core contract, which is a normal permissionless L1 interaction (no special privilege needed), and it depends on whether the L1 core contract itself enforces non-empty payload (this specific check lives outside this repo's scope and could not be verified here). Within this repository, no defensive check exists before `calc_msg_hash` is invoked, and the codebase explicitly acknowledges the "no non-empty invariant" gap elsewhere but did not close it in this call path.

### Recommendation
Change `l1_handler_message_hash` to return a `Result` (or otherwise handle the empty-calldata case gracefully) instead of using `.expect()`, mirroring the `saturating_sub` guard already applied in `L1HandlerTransaction::payload_size`. Validate calldata non-emptiness as early as possible in the L1 event ingestion path (e.g., in `EventData`/`L1HandlerTransaction::from` construction) so malformed L1 messages are rejected/logged rather than causing a panic deep in hash computation.

### Proof of Concept
1. Craft/observe an L1 `LogMessageToL2` event whose payload results in an `L1HandlerTransaction` with `calldata = Calldata(Arc::new(vec![]))` (empty calldata), e.g. via a call to the core contract's `sendMessageToL2` with an empty payload array, or in this repo directly by constructing such a transaction as done in the existing test: [6](#0-5) 
2. Call `tx.calc_msg_hash()` (or trigger `L1EventsScraper::fetch_events`, which calls it on every scraped `LogMessageToL2` event): [5](#0-4) 
3. Observe the panic: `"Invalid calldata, expected at least from_address"` from: [7](#0-6) 

**Note on uncertainty:** I was unable to fully verify from this codebase whether the L1 core contract (out of scope, on L1) enforces non-empty payloads before emitting `LogMessageToL2`, which would gate whether an attacker can actually get an empty-calldata event onto L1. If the L1 contract already enforces a non-empty payload, this specific path would not be externally triggerable, though the panic-on-empty-calldata gap in `l1_handler_message_hash` remains a latent robustness issue that contradicts the fix applied to the neighboring `payload_size` function.

```rust
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());
```
