### Title
Sandwiching an Exchange creator's liquidity inject/withdraw leaks pool value to an unprivileged trader - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
java-tron's TRC10 `Exchange` feature implements a constant-product AMM (`ExchangeCapsule.transaction`) over `firstTokenBalance`/`secondTokenBalance`. The exchange creator can call `ExchangeInjectContract`/`ExchangeWithdrawContract` to add or remove liquidity while preserving the price ratio but changing the pool's depth (its constant-product invariant `k`). Any unprivileged account can call the public `ExchangeTransactionContract` to trade against the pool at any time. Exactly like the TermMax `setLsf` finding — where a market-owner-controlled parameter changes the AMM's effective depth and is exploitable via sandwiching — a trader can buy into the pool while it is shallow (accepting slippage), wait for the creator to inject liquidity (increasing depth while keeping the ratio unchanged), then sell back into the now-deeper pool at far less slippage, extracting the injected liquidity's value as risk-free profit.

### Finding Description
`ExchangeCapsule.transaction()` computes swap outputs from `firstTokenBalance`/`secondTokenBalance` using `ExchangeProcessor`/`SafeExchangeProcessor`, a bancor/constant-product-style curve [1](#0-0) .

`ExchangeInjectActuator.execute` lets the exchange **creator** add liquidity: the injected amount of the other token is computed proportionally to the current balance ratio (`anotherTokenQuant = secondTokenBalance*tokenQuant/firstTokenBalance`), so the ratio is preserved but both balances (i.e., pool depth/`k`) grow [2](#0-1) . Only the exchange creator may call it: `if (!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())) throw ...` [3](#0-2) .

`ExchangeWithdrawActuator.execute` performs the symmetric operation, shrinking depth proportionally while also being restricted to the creator [4](#0-3) [5](#0-4) .

`ExchangeTransactionActuator.execute`, in contrast, is a **fully public/unprivileged** actuator — any account holding the tokens can buy/sell against the pool at any time [6](#0-5) .

This mirrors the TermMax root cause precisely: a party who controls a market-scoped parameter (creator/inject-withdraw, analogous to `market.lsf`) can change the AMM's effective depth without moving the instantaneous price, while an unprivileged party (any trader, via `ExchangeTransactionContract`) can freely trade before and after that change. In a constant-product AMM, increasing `k` between a user's buy and sell of the same pair transfers value from whoever supplied the new liquidity to the trader who sandwiches the change: buying against a shallow pool locks in an unfavorable (high-slippage) rate, and then selling the same amount back into a suddenly deeper pool (same ratio, larger `k`) returns close to the *pre-slippage* rate, netting the slippage back as profit funded by the newly injected liquidity.

Concrete numeric illustration (x·y=k, no fees): pool `x0=100, y0=100, k=10000`. Attacker sends `100 x` and receives `50 y` (`x=200,y=50`). Creator injects liquidity proportionally to reach `x=400,y=100` (ratio unchanged, `k` now 40000). Attacker sells the `50 y` back: new `y=150`, `x=400*100/150≈266.67`, so attacker receives `≈133.33 x` back — a profit of `≈33.33 x` versus the `100 x` originally spent, funded entirely by the creator's injected liquidity.

### Impact Explanation
This is a direct, unprivileged value-leak from Exchange liquidity into an attacker's wallet, matching the report's "High impact" characterization: the AMM invariant (`k`/depth) can be manipulated by a market-scoped role (the exchange creator) and sandwiched by any ordinary account through the fully public `ExchangeTransactionContract`, resulting in guaranteed extraction of value from the pool's newly-added liquidity. This is analogous to underpriced/mispriced public swap execution and improper accounting between depth changes and trade settlement — the two impact classes the rules explicitly recognize (accounting/settlement).

### Likelihood Explanation
Likelihood is Medium: it requires an exchange creator to call `ExchangeInjectContract` or `ExchangeWithdrawContract` after a trader has already taken a position, and both contracts are ordinary, frequently-used TRC10 liquidity-management operations rather than rare governance actions. Because the injection/withdrawal transaction is a normal, publicly observable mempool transaction, an attacker can trivially front-run/back-run it (the exact "purchase → wait for the parameter/depth change → sell" pattern described in the original report).

### Recommendation
Either (a) disallow arbitrary-sized single-transaction liquidity injections/withdrawals from unbalancing effective slippage exposure for open positions (e.g., cap the relative depth change per block, or use a time-weighted/vested liquidity change), or (b) require that inject/withdraw operations be executed atomically with any pending trade ordering protection (e.g., a minimum number of blocks between a trade and a depth change on the same exchange, or applying inject/withdraw effects only after a delay), so a single trader cannot deterministically sandwich a depth change within adjacent transactions.

### Proof of Concept
1. Attacker calls `ExchangeTransactionContract` selling `tokenA` for `tokenB` against exchange `id`, incurring high slippage against the current (shallow) `firstTokenBalance`/`secondTokenBalance` [7](#0-6) .
2. The exchange creator calls `ExchangeInjectContract`, adding liquidity proportionally and thereby increasing pool depth (`k`) while preserving the price ratio [2](#0-1) .
3. Attacker immediately calls `ExchangeTransactionContract` again, selling the `tokenB` received in step 1 back into the now-deeper pool, receiving materially more `tokenA` than the round-trip would have cost absent the depth change, netting a risk-free profit funded by the creator's injected liquidity (per the numeric walkthrough above using `ExchangeCapsule.transaction`'s constant-product math [1](#0-0) ).
