## Title
Zero-fee TRC10 Bancor-style Exchange enables free sandwich/DoS reverts against `ExchangeTransactionContract` swaps - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Tron's built-in TRC10 asset exchange (the `Exchange`/`ExchangeV2` AMM, using a Bancor-relay constant-formula pricing curve) charges **zero protocol fee** on swaps (`calcFee()` returns `0`), exactly mirroring the "Well" AMM bug: any user's slippage-protected swap can be sandwiched by a searcher/witness at negligible cost, forcing the victim's transaction to revert on the `expected` (minAmountOut) check, while the attacker profits by reversing the price impact.

### Finding Description
`ExchangeTransactionContract` lets any account swap one TRC10 token for another against an `ExchangeCapsule` pool, specifying `quant` (amount to sell) and `expected` (minimum amount to receive) [1](#0-0) .

The price is computed via `ExchangeCapsule.transaction()`, which routes through `ExchangeProcessor`/`SafeExchangeProcessor`, a Bancor-relay curve that moves the pool balances instantaneously based on `sellTokenQuant` [2](#0-1) . This formula has no fee subtraction baked in — it purely reflects the price-impact curve [3](#0-2) .

Critically, `ExchangeTransactionActuator.calcFee()` hard-codes a **zero fee** for the swap itself [4](#0-3) . The only validation protecting the user is the on-chain slippage check comparing the freshly recomputed `anotherTokenQuant` against the user-specified `tokenExpected`, which throws and reverts if not met [1](#0-0) .

This reproduces all three preconditions from the reported bug class:
1. No swap fee — cost of manipulating the pool is limited to ordinary bandwidth/energy transaction cost, not a proportional trading fee.
2. Instantaneous, deterministic price updates via the constant-formula curve (no TWAP/oracle smoothing).
3. Pending swap transactions (with their `expected` slippage bound) are visible before inclusion, since they sit in the node's transaction pool prior to block packing by a Super Representative (witness), similarly to a public mempool.

An attacker (or a colluding witness who controls transaction ordering within their produced block) can therefore: (a) submit a same-direction swap to push the pool price beyond the victim's `expected` bound, (b) let the victim's `ExchangeTransactionContract` fail validation/execution and revert, (c) submit an opposite-direction swap immediately after to restore the pool to (near) its original state, extracting the victim's foregone price impact as profit — at the cost of only two ordinary TRX transactions with no protocol swap fee.

### Impact Explanation
Any TRC10 exchange swap with a `expected` slippage bound can be economically DoS'd/sandwiched at will, since there is zero protocol fee to make the attack costly, unlike fee-bearing AMMs where LP fees make bracket attacks unprofitable at scale. This can be used to persistently block user swaps (forcing users into ever-tighter or looser slippage tolerances, which then become directly exploitable), degrading usability of the on-chain TRC10 exchange market feature and enabling repeated value extraction from users attempting to trade through it.

### Likelihood Explanation
The TRC10 `Exchange` actuators (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) are permissionless and reachable by any account; swap transactions with a chosen `expected` value are exactly the attack surface described. The lack of fee is unconditional (`calcFee()` always returns `0`) [4](#0-3) , so the attack economics hold on any active TRC10 exchange pair with sufficient liquidity to matter, requiring only ordinary transaction fees/bandwidth for the bracketing transactions.

### Recommendation
Introduce a proportional trading fee (deducted from `anotherTokenQuant` or built into the Bancor-relay curve calculation in `ExchangeProcessor`/`SafeExchangeProcessor`) so that bracketing a victim's swap costs more than the extractable price-impact profit, consistent with standard AMM fee design; alternatively, consider TWAP-style price smoothing or per-block price-impact caps for the TRC10 exchange to reduce the attacker's ability to move price instantaneously within a single block.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` swap with `tokenId=A`, `quant=Q`, `expected=E` (direction A→B).
2. Attacker submits swap #1, same direction (A→B), sized to move the pool such that `exchangeCapsule.transaction()` for the victim's parameters would now return `< E` [2](#0-1) .
3. Victim's transaction executes/validates and fails the check `anotherTokenQuant < tokenExpected`, reverting with `ContractValidateException` [1](#0-0) .
4. Attacker submits swap #2, opposite direction (B→A), restoring the pool near its original state and capturing the price-impact profit from swap #1, paying zero protocol swap fee (`calcFee()==0`) for either of the two swaps [4](#0-3) .

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }
