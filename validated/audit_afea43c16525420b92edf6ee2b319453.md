### Title
Floor-rounded resource-usage estimate in `DelegateResourceActuator`/`DelegateResourceProcessor` under-represents locked resource, allowing over-delegation - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
The gfx-ssl bug class is: a locked/consumed quantity is converted with a rounding direction that under-represents the locked amount, letting a check that should be conservative (`available >= requested`) pass when it shouldn't. The `DelegateResourceActuator.doValidate()` and its VM-native twin `DelegateResourceProcessor.validate()` compute the account's currently "used" bandwidth/energy (the portion of frozen balance that is not free to delegate) via floating point and a `(long)` truncating cast, then subtract that estimate from the account's `FrozenV2Balance` to decide whether `delegateBalance` is allowed.

### Finding Description
In `DelegateResourceActuator.java`, the BANDWIDTH branch computes: [1](#0-0) 
and the ENERGY branch does the analogous computation: [2](#0-1) 
Both use `(long) (... * TRX_PRECISION * ((double) totalWeight / totalLimit))`, i.e. a `double` multiplication truncated toward zero on cast — always a floor for positive values, never rounding up. The same non-hardened pattern exists in the VM-callable `DelegateResourceProcessor.validate()`. [3](#0-2) [4](#0-3) 

This floor-rounded `netUsage`/`energyUsage` is fed into `getV2NetUsage`/`getV2EnergyUsage`, which subtract already-frozen/acquired-delegated amounts to derive the "v2 usage" portion that must remain locked and non-delegable: [5](#0-4) 

The validate check is `frozenV2Balance - v2Usage < delegateBalance` → reject. Because `v2Usage` is derived from a floor-truncated `netUsage`/`energyUsage`, it can be smaller than the true locked amount, which makes `frozenV2Balance - v2Usage` larger than it should be — precisely analogous to `scale_decimal` rounding down `pt_minted` in the original report, which under-represents the locked/liability amount in a `require_gte` check. This is the exact same bug shape: a value that represents "how much must stay locked/unavailable" is computed with the wrong (floor, not ceiling) rounding direction before being used in a `>=`/`<` guard that gates how much a user may extract or commit elsewhere.

Notably, the codebase already contains a "hardened" precise mode for structurally identical resource-usage math elsewhere (`hardenResourceCalculation()` / `hardenCalculation()` using `BigInteger` in `RepositoryImpl.getUsage`/`calculateGlobalEnergyLimit` and `EnergyProcessor.scaleByRate`/`ResourceProcessor.getUsage`), which strongly suggests floating-point precision loss in this class of computation was previously identified as risky and mitigated in those call sites — but the `netUsage`/`energyUsage` computation inside `DelegateResourceActuator`/`DelegateResourceProcessor` was not migrated to that hardened, BigInteger-based path. [6](#0-5) 

### Impact Explanation
If the floor-truncated usage estimate under-counts consumed bandwidth/energy, an account could pass the `delegateBalance <= FrozenV2Balance - usage` check and delegate away resource capacity that is, in reality, still needed to cover its own consumption. This can allow a user to over-delegate resource relative to their true free/frozen balance, an internal state/accounting-consistency issue in the resource delegation subsystem (bandwidth/energy accounting is part of TRON's core resource-market economics). The magnitude of any single rounding error is small (loses at most a fraction of a `TRX_PRECISION` unit of usage per calculation) and is bounded by floating-point precision at this scale, so a single call would not usually cause large drainage, but it is a genuine incorrect-rounding-direction defect in an unprivileged, publicly reachable path (`DelegateResourceContract` executed by any account, and the identical logic reachable from Solidity contracts via TVM native "delegate resource" precompile/opcode).

### Likelihood Explanation
The path is reachable by any unprivileged account submitting a `DelegateResourceContract` transaction, or by any smart contract invoking the native delegate-resource precompile that hits `DelegateResourceProcessor`. No special privilege is required. However, I could not fully verify (within available tool/search budget) the exact magnitude of exploitable drift produced by the double-based computation versus the BigInteger "hardened" computation across realistic `TotalNetWeight`/`TotalNetLimit` ratios, nor whether downstream invariants (e.g., total resource accounting, negative-balance guards elsewhere) already absorb or neutralize this discrepancy before it becomes observable/exploitable at scale. This uncertainty means I cannot assert with confidence that this rises to a directly exploitable, material fund-loss bug rather than a benign, self-correcting rounding artifact — it is offered as the strongest structural analog to the reported bug class found in the indexed code.

### Recommendation
Migrate the `netUsage`/`energyUsage` computation in `DelegateResourceActuator.doValidate()` and `DelegateResourceProcessor.validate()` to the same `BigInteger`-based, ceiling-aware calculation pattern already used in `RepositoryImpl`/`ResourceProcessor`/`EnergyProcessor` (i.e., `divideCeil`/`divideCeilExact` style rounding), so that the "used/locked" amount is never under-counted before being subtracted from delegable balance.

### Proof of Concept
I was unable to construct or verify a concrete numeric transaction sequence that demonstrates an observable balance/resource discrepancy within the available investigation budget; doing so would require exercising `DelegateResourceActuator` against specific `TotalNetWeight`/`TotalNetLimit`/`NetUsage` values inside a running node or the existing test harness (e.g., extending `framework/src/test/java/org/tron/core/actuator/DelegateResourceActuatorTest.java`) to compare the double-based vs. BigInteger-hardened usage results and show a case where `frozenV2Balance - v2NetUsage >= delegateBalance` passes only due to floor truncation. This would need to be validated with a Devin session that can run the project's test suite.
