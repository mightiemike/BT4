### Title
Replay/execution-verification skips authenticated state-checkpoint root comparison, letting a diverging post-state pass as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by both the chunk executor's replay-verification path and the `db-tool replay-on-archive` tool, deliberately omits comparing the `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields of the authenticated `TransactionInfo` against the locally recomputed state. This is the same bug class as the Olympus H-02 report: a critical invariant check ("does my recomputed result match the authenticated on-chain commitment?") that is supposed to gate acceptance instead trivially "passes" because part of the comparison was never implemented, so a real divergence is silently accepted as verified.

### Finding Description
`ensure_match_transaction_info` checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash` against the `TransactionInfo`, but explicitly does not check the state/hot-state checkpoint hash fields, as documented in its own TODO: [1](#0-0) 

This function is the sole correctness gate in two important places:
1. `execution/executor/src/chunk_executor/mod.rs::verify_execution`, used during chunk-executor replay verification (state-sync/backup restore path) to confirm that re-executing a chunk of transactions with the VM produces the exact `TransactionInfo` recorded on the authenticated ledger: [2](#0-1) 

2. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the exact tool named in the code's own TODO comment ("db-tool's `replay_on_archive`"), used to validate historical replay integrity against archived, authenticated `TransactionInfo`s: [3](#0-2) 

Because `state_checkpoint_hash` (the Sparse/Jellyfish Merkle root of world state at a checkpoint) and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared, any divergence in how the local executor computes these post-execution state roots — from a VM/state-tree bug, a hot-state or position-state computation bug, or a maliciously/accidentally corrupted local state tree — will not be detected by either replay-verification tool. Both call sites will report success (`Ok(())`), even though the actual state root differs from the one authenticated by validator signatures.

### Impact Explanation
This breaks the "proof and storage pivot" invariant that "VM outputs, transaction infos... must survive executor-to-storage handoff unchanged" and that "replay paths... must not reinterpret committed data into a different ledger state." A tool whose entire purpose is to detect state-root divergence between local execution and the authenticated chain (used for post-incident forensics, archive-node integrity checks, and hard-fork/bug detection) can report a clean, verified replay while the locally computed state-checkpoint root is silently wrong. This directly undermines the mechanism operators rely on to catch state-corrupting bugs (e.g., a bug in hot-state tracking or JMT construction) before or after they manifest on mainnet — a false "verified" signal on a wrong ledger state is a state-integrity/proof-binding failure with high severity, since it can mask an already-diverged or corrupted durable state root from being caught by the designated verification tooling.

### Likelihood Explanation
The missing check is unconditional and applies to every replay-verification run of `verify_execution` and `replay_on_archive`, not a rare edge case; the flaw is triggered any time the state-checkpoint hash differs on replay (e.g., due to a bug in the hot-state or position-state checkpoint hashing path currently being developed per the surrounding "trading-native"/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature work) while write-set/event/gas/status match. The code authors' own comment acknowledges the gap exists today and is expected to matter before the related feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled, indicating this is a known, currently-live gap rather than a hypothetical.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` computed by the local executor/state-checkpoint output against the corresponding fields in `txn_info`, returning an error on mismatch (mirroring how `state_change_hash` and `event_root_hash` are already validated), before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or relying on `replay_on_archive` for state-root integrity guarantees.

### Proof of Concept
Conceptual (no local repro executed, since this requires constructing a mismatched hot/position-state checkpoint hash in a controlled DB):
1. Prepare an archived ledger segment with authentic `TransactionInfo`s including a non-trivial `state_checkpoint_hash`/`hot_state_checkpoint_hash`.
2. Run `replay_on_archive` (or trigger chunk-executor `verify_execution`) against a target DB whose local state tree has been perturbed so the write set, events, gas, and status still match, but the resulting checkpoint hash differs (e.g., a hot-state entry omitted/duplicated, or JMT node arrangement altered).
3. Observe `ensure_match_transaction_info` returns `Ok(())` for that transaction/version despite the true state root diverging, because the function's checks never reach `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` — confirmed directly from the function body: [4](#0-3) 

I was not able to fully verify at what pipeline stage (if any) `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or another currently-unmerged validation independently re-checks this hash outside of `ensure_match_transaction_info` in `execution/executor/src/chunk_executor/mod.rs` — no state-checkpoint-hash references were found there — so I cannot rule out a not-yet-visible external guard being added elsewhere in the codebase.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
