### Title
Legacy withdraw-cadence lockout (24h `witnessAllowanceFrozenTime` check) is enforced only by `WithdrawBalanceActuator` and completely bypassed by the TVM `WITHDRAWREWARD` opcode path - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java])

### Summary
`WithdrawBalanceActuator.validate()` rejects a reward withdrawal if `now - latestWithdrawTime < witnessAllowanceFrozenTime` (default 24h, `FROZEN_PERIOD`), but `WithdrawRewardProcessor.validate()`/`execute()` (invoked via the TVM `withdrawReward()` opcode in `Program.java`) performs no such check at all. Any unprivileged account/contract can therefore repeatedly drain its `allowance` via the TVM opcode within the lockout window, even though the exact same withdrawal would be rejected through the legacy `WithdrawBalanceContract` transaction path.

### Finding Description
`WithdrawBalanceActuator.validate()` enforces a mandatory cadence gate before allowing a reward withdrawal: [1](#0-0) 

This check reads `accountCapsule.getLatestWithdrawTime()`, compares it against `dynamicStore.getLatestBlockHeaderTimestamp()` and `dynamicStore.getWitnessAllowanceFrozenTime() * FROZEN_PERIOD`, and throws `ContractValidateException` if the interval hasn't elapsed.

In contrast, `WithdrawRewardProcessor.validate()` (the code path taken by the TVM `WITHDRAWREWARD` opcode) only checks whether the address is a genesis guard-representative — it has no equivalent time-interval check: [2](#0-1) 

`execute()` then unconditionally adds `allowance` to `balance`, zeroes `allowance`, and updates `latestWithdrawTime`, with no gate on how recently a previous withdrawal occurred: [3](#0-2) 

This is reachable by any contract that calls the TVM opcode `withdrawReward()`, exposed in `Program.java`: [4](#0-3) 

Because reward accrual (`VoteRewardUtil.withdrawReward` / `adjustAllowance`) happens on a per-cycle basis and can add new `allowance` between blocks/cycles, the missing cadence gate lets an attacker call the opcode far more frequently than once per `witnessAllowanceFrozenTime` interval to withdraw accrued allowance as soon as it appears, whereas the same account would be rejected under `WithdrawBalanceActuator` until the interval elapses.

### Impact Explanation
This breaks the invariant that all reward-withdrawal entry points enforce identical cadence rules (DETERMINISM/AUTHORIZATION_ENFORCED). It doesn't allow theft of un-earned funds (allowance is still bounded by actual accrued reward via `VoteRewardUtil`), but it does let an attacker bypass an economic/anti-spam safeguard that the protocol designers intentionally placed on withdrawals, resulting in inconsistent state transitions and rule enforcement across the legacy actuator path and the TVM opcode path. This matches TRON's "unauthorized account operations" / rule-enforcement-divergence impact class rather than direct fund theft.

### Likelihood Explanation
Trivial and fully repeatable: no privileged role is needed — any funded account can deploy a trivial contract that calls the `WITHDRAWREWARD` opcode, or interact with an already-deployed generic contract exposing it. Cost is limited to ordinary TVM energy/bandwidth fees for the call. It is deterministic and reproducible on every node running default configuration.

### Recommendation
Add the same `witnessAllowanceFrozenTime`/`FROZEN_PERIOD` cadence check to `WithdrawRewardProcessor.validate()` (or `execute()`) using `repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp()` / current timestamp against `accountCapsule.getLatestWithdrawTime()` and `dynamicStore.getWitnessAllowanceFrozenTime() * FROZEN_PERIOD`, mirroring `WithdrawBalanceActuator.validate()`, so both entry points enforce identical withdrawal cadence rules.

```java
// Differential JUnit test (add to framework/src/test/java/org/tron/core/vm/nativecontract/)
@Test
public void differentialWithdrawCadenceTest() throws Exception {
  byte[] address = ByteArray.fromHexString(OWNER_ADDRESS);
  long now = System.currentTimeMillis();
  dbManager.getDynamicPropertiesStore().saveLatestBlockHeaderTimestamp(now);

  // Set latestWithdrawTime to "now" so both paths are inside the 24h lockout window
  AccountCapsule account = dbManager.getAccountStore().get(address);
  account.setLatestWithdrawTime(now);
  dbManager.getMortgageService().adjustAllowance(dbManager.getAccountStore(), address, 1000L);
  dbManager.getAccountStore().put(address, account);

  // 1) Legacy actuator path: expect rejection
  WithdrawBalanceActuator actuator = new WithdrawBalanceActuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(OWNER_ADDRESS));
  try {
    actuator.validate();
    fail("legacy actuator should reject withdrawal inside lockout window");
  } catch (ContractValidateException e) {
    // expected
  }

  // 2) TVM opcode path: WithdrawRewardProcessor, same account state, same timestamp
  WithdrawRewardParam param = new WithdrawRewardParam();
  param.setOwnerAddress(address);
  param.setNowInMs(now);
  WithdrawRewardProcessor processor = new WithdrawRewardProcessor();
  processor.validate(param, repository); // does NOT throw -- no cadence check
  long withdrawn = processor.execute(param, repository); // succeeds, allowance drained

  Assert.assertEquals(1000L, withdrawn); // demonstrates bypass of the legacy lockout
}
```
Expected result confirming the finding: step 1 throws `ContractValidateException` ("The last withdraw time is ... less than 24 hours"), while step 2 completes successfully and returns the full allowance, demonstrating the TVM path allows withdrawal that the legacy actuator would reject for identical account state.

```java
  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
```

```java
  public long withdrawReward() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawReward", nonce, null);

    WithdrawRewardParam param = new WithdrawRewardParam();
    param.setOwnerAddress(owner);
    param.setNowInMs(getTimestamp().longValue() * 1000);
    try {
      WithdrawRewardProcessor processor = new WithdrawRewardProcessor();
      processor.validate(param, repository);
      long allowance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(allowance);
      }
      return allowance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawReward: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawReward: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }
```
