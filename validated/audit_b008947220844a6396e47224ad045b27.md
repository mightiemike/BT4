### Title
Failed `BridgeDeposit` system transactions are dropped from the deposit mempool despite never being included in the block, permanently freezing the depositor's cBTC - ([File: crates/sequencer/src/runner.rs])

### Summary
`produce_l2_block_inner` fetches a batch of deposits via `fetch_deposits`, hands the same immutable `deposit_data` slice to `process_sys_txs`, and unconditionally calls `remove_deposits(&deposit_data)` after the block is saved, regardless of whether each individual deposit's `BridgeDeposit` system transaction actually succeeded or was skipped in `process_sys_txs`. Any deposit that fails during on-chain application (whether due to gas-context divergence at the `SYSTEM_TX_GAS_LIMIT` boundary as described, or any other execution divergence between the isolated `eth_call` simulation and `process_sys_txs`'s cumulative working set) is silently dropped from the mempool with no cBTC minted and no retry path, while the corresponding Bitcoin-side moveTx has already been presigned/spent by Clementine.

### Finding Description
The binding that must hold is: for every deposit blob `d` accepted by `citrea_sendRawDepositTransaction` whose corresponding Bitcoin moveTx was presigned/spent by Clementine, either `d` remains in the mempool for retry, or `d`'s `BridgeWrapper::deposit` call was actually executed successfully and credited cBTC in a committed L2 block. Concretely: `d ∈ deposit_mempool` XOR (`d`'s deposit tx ∈ all_txs of a finalized block AND cBTC minted`)`.

Trace:
1. `send_raw_deposit_transaction` (`crates/sequencer/src/rpc.rs:330-388`) simulates via `evm.get_call(dep_tx, Some(BlockId::pending()), ...)` with `dep_tx` built by `DepositDataMempool::make_deposit_tx_from_data` which fixes `gas: Some(SYSTEM_TX_GAS_LIMIT)` (`crates/sequencer/src/deposit_data_mempool.rs:40-48`). On success it calls `add_deposit_tx`, storing the raw deposit blob in `accepted_deposit_txs`.
2. `produce_l2_block_inner` fetches deposits with `fetch_deposits` (`crates/sequencer/src/runner.rs:517-520`) into `deposit_data`, which does NOT remove them from the mempool.
3. `produce_and_run_system_transactions` → `process_sys_txs` (`crates/sequencer/src/runner.rs:1552-1706`) converts each deposit into a `BridgeDeposit` system tx with `gas_limit: SYSTEM_TX_GAS_LIMIT` (`crates/evm/src/evm/system_events.rs:73-82`) and applies it via `apply_l2_block_txs` against a working set that already carries state from prior system/user txs in the same block. If this returns `EvmSystemTransactionNotSuccessful` and it's a deposit, the code explicitly reverts the checkpoint and `continue`s (`runner.rs:1678-1697`) - the failed deposit's tx is never pushed into `all_txs`, i.e. it is not included in the produced block at all.
4. After the block is committed, `produce_l2_block_inner` unconditionally calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` (`runner.rs:636-643`), where `deposit_data` is the *original full fetched batch* from step 2 — not the subset that was actually included in `all_txs`/the block. `remove_deposits` (`crates/sequencer/src/deposit_data_mempool.rs:79-101`) removes every deposit in that list from `accepted_deposit_txs` and `pending_deposits` by `calc_tx_id`, with no distinction between succeeded and failed/skipped deposits.

Root cause: the code comment at `runner.rs:636` claims "Remove successfully included deposits from the mempool," but the implementation removes *all fetched* deposits, not only those that succeeded. Any divergence between the `eth_call` simulation (isolated `WorkingSet`, `BlockId::pending()`) and actual inclusion in `process_sys_txs` (cumulative working set with warm/cold storage state from prior system and user txs in the block) — including but not limited to gas accounting divergence near the `SYSTEM_TX_GAS_LIMIT` boundary — causes the deposit to revert with `EvmSystemTransactionNotSuccessful`, get skipped from the block, yet still be permanently purged from the mempool.

No existing guard catches this: `apply_l2_block_txs`/`process_sys_txs` correctly reverts and continues for deposit failures (to protect subsequent txs), but the downstream removal logic in `produce_l2_block_inner` does not consult which deposits were actually included before evicting them from the retry queue.

### Impact Explanation
This is Critical: a real Bitcoin-side deposit (BTC already locked/moved by Clementine's presigned moveTx) can be permanently rejected on Citrea with cBTC never minted and no automatic retry, since `remove_deposits` deletes the blob from `pending_deposits`/`accepted_deposit_txs` unconditionally. The depositor would need to notice the loss and manually resubmit via `citrea_sendRawDepositTransaction` (if even aware); absent that, the funds are frozen — matching "funds permanently frozen" in the Critical category. This affects any deposit whose on-chain application fails for any reason during `process_sys_txs` (gas-boundary divergence is one concrete trigger), and is repeatable across blocks/deposits since the flawed removal logic runs on every block production cycle that includes deposits.

### Likelihood Explanation
Preconditions require only that the sequencer include multiple system transactions/deposits in the same block context, and that at least one deposit's actual execution differs from its isolated simulation (e.g., gas usage crossing `SYSTEM_TX_GAS_LIMIT` due to warm/cold slot differences, or any other state-dependent effect not present in the isolated `eth_call`). No privileged role is needed — this is triggered by ordinary sequencer block production logic once a legitimately-submitted deposit's real inclusion diverges from its simulation. It requires no attacker cost beyond crafting a deposit blob that happens to sit near the gas boundary (or any other execution-context-sensitive path) and getting it accepted by `citrea_sendRawDepositTransaction`, which is a routine, unprivileged RPC call.

### Recommendation
In `process_sys_txs`, track which deposits from `deposit_data` were actually included in `all_txs` (e.g., return a set/list of successfully applied deposit blobs or their `calc_tx_id`s alongside `all_txs`). In `produce_l2_block_inner`, call `remove_deposits` only with that successfully-included subset, leaving failed/skipped deposits in the mempool for retry in a future block (optionally with a retry-count/backoff to avoid indefinite blocking on a permanently-invalid deposit).

    fn send_raw_deposit_transaction(&self, deposit: Bytes) -> RpcResult<()> {
        debug!("Sequencer: citrea_sendRawDepositTransaction");

        let deposit_tx_size = deposit.len();
        SM.deposit_tx_size.record(deposit_tx_size as f64);

        let evm = Evm::<DefaultContext>::default();
        let mut working_set = WorkingSet::new(self.context.storage.clone());

        let dep_tx = self
            .context
            .deposit_mempool
            .lock()
            .make_deposit_tx_from_data(deposit.clone().into());

        let start = std::time::Instant::now();
        let tx_res = evm.get_call(
            dep_tx,
            Some(BlockId::pending()),
            None,
            None,
            &mut working_set,
            &self.context.ledger,
        );
        let deposit_tx_call_duration = Instant::now()
            .saturating_duration_since(start)
            .as_secs_f64();
        SM.deposit_tx_call_duration.record(deposit_tx_call_duration);

        match tx_res {
            Ok(hex_res) => {
                tracing::debug!("Deposit tx processed successfully {}", hex_res);
                let add_result = self
                    .context
                    .deposit_mempool
                    .lock()
                    .add_deposit_tx(Deposit::from(deposit.to_vec()));

                match add_result {
                    Ok(true) => Ok(()),
                    Ok(false) => Err(jsonrpsee::types::error::ErrorObject::owned(
                        jsonrpsee::types::error::INVALID_PARAMS_CODE,
                        "Deposit already pending in mempool",
                        None::<()>,
                    )),
                    Err(_) => Err(jsonrpsee::types::error::ErrorObject::owned(
                        jsonrpsee::types::error::INVALID_PARAMS_CODE,
                        "Invalid deposit",
                        None::<()>,
                    )),
                }
            }
            Err(e) => {
                error!("Error processing deposit tx: {:?}", e);
                SM.unaccepted_deposit_txs.increment(1);
                Err(e)
            }
        }
    }

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });
