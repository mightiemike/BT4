### Title
Delegated resource unfreeze can be permanently DoS'd when receiver's acquired-balance accounting diverges from delegator's record - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java])

### Summary
The legacy `UnfreezeBalanceActuator` (`ContractType.UnfreezeBalanceContract`) permanently blocks a resource delegator from reclaiming their delegated frozen TRX whenever the receiver account's `AcquiredDelegatedFrozenBalanceForBandwidth`/`Energy` accounting falls below the amount recorded in the delegator's `DelegatedResourceCapsule`. This is structurally the same failure class as the Morpho report: a withdrawal-style action has a hard validation check against a second piece of state that can legitimately diverge from the first, and once it diverges, the withdraw path throws unconditionally with no remediation path, permanently locking the user's frozen TRX.

### Finding Description
In `validate()`, when unfreezing a *delegated* resource, the actuator requires the receiver's acquired-delegated balance to be at least as large as what the delegator recorded as delegated: [1](#0-0) 

If `receiverCapsule.getAcquiredDelegatedFrozenBalanceForBandwidth() < delegatedResourceCapsule.getFrozenBalanceForBandwidth()`, it throws `ContractValidateException` unconditionally — there is no code path in this actuator that reconciles or resets the mismatch, unlike its newer `V2` counterpart.

The mismatch is not hypothetical: it is explicitly reachable through a TVM contract self-destruct/re-create sequence. When a contract that received a delegation self-destructs, its acquired-delegated balance is cleared/re-initialized; if the address is later re-created (e.g., via `CREATE2`), the new account can end up with an `AcquiredDelegatedFrozenBalanceForBandwidth`/`Energy` value that no longer matches what the original delegator's `DelegatedResourceCapsule` records, because these two values are updated by independent code paths (delegator's `DelegatedResourceStore` entry vs. receiver's `AccountCapsule` fields), and `Program.suicide`/`suicide2` only handle the `V2` frozen model reconciliation, not the legacy delegated-resource model in all cases: [2](#0-1) 

This exact scenario is validated by the project's own tests, which show the legacy actuator throwing a permanent, un-recoverable validation error once the receiver's acquired balance is smaller than the delegator's recorded delegated balance: [3](#0-2) 

By contrast, the project's own newer implementation for the equivalent operation (`UnDelegateResourceActuator`/`UnDelegateResourceProcessor`) explicitly recognizes and gracefully handles this exact "TVM contract suicide, re-create" scenario by resetting the receiver's acquired balance to 0 rather than throwing, allowing the owner to always reclaim funds: [4](#0-3) 

This asymmetry demonstrates that the legacy `UnfreezeBalanceActuator` path (still an active, non-deprecated `ContractType`) retains the unresolved defect: an owner's ability to unfreeze delegated TRX can become permanently blocked by a state divergence they do not control (the receiver contract's lifecycle), with no on-chain recovery mechanism, mirroring the Morpho bug's "cannot withdraw and cannot fix the underlying state" failure mode.

### Impact Explanation
An account that delegated BANDWIDTH or ENERGY to a contract receiver can have its TRX permanently locked (never unfreezable through this contract type) once the receiver's acquired-balance state diverges from the delegator's record via a suicide/recreate cycle. This is an asset-lock/DoS on the delegator's funds reachable purely through normal broadcast transactions (delegate, then the receiver contract's owner triggers `SELFDESTRUCT`/`CREATE2` recreation) — no privileged actor or leaked key required.

### Likelihood Explanation
Medium. It requires: (1) a delegator to delegate BANDWIDTH/ENERGY to a smart-contract receiver, and (2) the receiver contract's deployer to self-destruct and later redeploy at the same address via `CREATE2` (a legitimate, permissionless TVM operation), producing the exact "recreated receiver" state the project's own tests already construct and validate against. The delegator has no control over whether the receiver contract does this, but any interaction with an untrusted/malicious contract receiver exposes the delegator to this lock.

### Recommendation
Apply the same reconciliation logic used in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` to the legacy `UnfreezeBalanceActuator`: when `receiverCapsule.getAcquiredDelegatedFrozenBalanceForBandwidth()/Energy() < delegatedResourceCapsule.getFrozenBalanceFor...()`, reset the receiver's acquired balance to 0 (or otherwise reconcile) instead of throwing `ContractValidateException`, so the delegator can always recover their frozen TRX regardless of receiver-side state changes.

### Proof of Concept
1. Account A delegates BANDWIDTH to contract address R via `FreezeBalanceContract` with `receiver_address = R` (legacy delegate-resource flow), recorded in `DelegatedResourceCapsule(A, R)`.
2. R is a TVM contract; it calls `SELFDESTRUCT`, clearing/altering its `AcquiredDelegatedFrozenBalanceForBandwidth`.
3. R's address is redeployed via `CREATE2` (as demonstrated in `framework/src/test/java/org/tron/core/actuator/UnfreezeBalanceActuatorTest.java` `testUnfreezeDelegatedBalanceForBandwidthSameTokenNameClose`/`testUnfreezeDelegatedBalanceForCpuWithRecreatedReceiver`), leaving the new account's `AcquiredDelegatedFrozenBalanceForBandwidth` smaller than `DelegatedResourceCapsule(A, R).getFrozenBalanceForBandwidth()`.
4. Account A submits `UnfreezeBalanceContract` with `receiver_address = R`; `UnfreezeBalanceActuator.validate()` throws `"AcquiredDelegatedFrozenBalanceForBandwidth[...] < delegatedBandwidth[...]"` every time, permanently preventing A from reclaiming the frozen TRX through this contract type.   private void transferDelegatedResourceToInheritor(byte[] ownerAddr, byte[] inheritorAddr, Repository repo) {

    // delegated resource from sender to owner, just abandon
    // in order to making that sender can unfreeze their balance in future
    // nothing will be deleted

    // delegated resource from owner to receiver
    // there cannot be any resource when suicide

    AccountCapsule ownerCapsule = repo.getAccount(ownerAddr);

    // transfer owner`s frozen balance for bandwidth to inheritor
    long frozenBalanceForBandwidthOfOwner = 0;
    // check if frozen for bandwidth exists
    if (ownerCapsule.getFrozenCount() != 0) {
      frozenBalanceForBandwidthOfOwner = ownerCapsule.getFrozenList().get(0).getFrozenBalance();
    }
    repo.addTotalNetWeight(-frozenBalanceForBandwidthOfOwner / TRX_PRECISION);

    long frozenBalanceForEnergyOfOwner =
        ownerCapsule.getAccountResource().getFrozenBalanceForEnergy().getFrozenBalance();
    repo.addTotalEnergyWeight(-frozenBalanceForEnergyOfOwner / TRX_PRECISION);

    // transfer all kinds of frozen balance to BlackHole
    repo.addBalance(inheritorAddr, frozenBalanceForBandwidthOfOwner + frozenBalanceForEnergyOfOwner);

    if (VMConfig.allowTvmSelfdestructRestriction()) {
      clearOwnerFreeze(ownerCapsule);
      repo.updateAccount(ownerAddr, ownerCapsule);
    }
  }
