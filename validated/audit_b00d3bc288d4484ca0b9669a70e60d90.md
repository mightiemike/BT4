## Title
Duplicate-signatory weight inflation in `ValidateMultiSign` TVM precompile allows single key to satisfy a weighted multi-sig threshold — (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, which lets any TVM smart contract verify a weighted multi-signature permission on-chain, deduplicates signatures by comparing the *raw signature bytes* (recovered address + signature blob) rather than by the *recovered signer address* alone. Because ECDSA signatures for the same message/key are not forced into a single canonical form here, an attacker can produce two byte-different but both-valid signatures that recover to the same address, causing that single signer's weight to be counted twice (or more). This is the exact bug class described in the external report: quorum/threshold logic that sums weight per signature instead of per unique signer, allowing one signer to inflate their effective weight and pass a threshold meant to require multiple independent signers.

### Finding Description
`ValidateMultiSign.execute` accumulates weight across the supplied `signatures` array: [1](#0-0) 

For each signature it recovers the signer address via `recoverAddrBySign`, then merges `recoveredAddr` with the raw signature bytes into `sign`. It checks `executedSignList` for `recoveredAddr` — if the address was seen before, it only skips adding weight when the exact merged `sign` bytes were seen before too (`ByteArray.matrixContains(executedSignList, sign)`). If the address repeats but the raw signature bytes differ, the code does not skip: it calls `MUtil.checkCPUTime()` (a CPU-abuse guard) and then falls through to add the signer's weight to `totalWeight` again.

This means the "duplicate" check is keyed on signature-byte-equality, not signer-identity. ECDSA signatures are not inherently unique per (key, message) pair: the classic signature malleability trick (`s' = n - s` with a complementary recovery id) produces a second, distinct signature that still recovers to the same address, and outright re-signing (if the signing routine ever uses non-deterministic nonces, or if two different messages hash-collide into the padded input, or a wallet-provided signature and its malleable counterpart are both supplied) can also yield distinct byte sequences for the same signer. `recoverAddrBySign` calls `SignUtils.fromComponents(...).validateComponents()` before recovering the address: [2](#0-1) 

Whether `validateComponents()` (in `ECKey.ECDSASignature`) enforces canonical low-`s` values was not confirmed in this review — I found the method exists (`crypto/src/main/java/org/tron/common/crypto/ECKey.java`) but could not verify from available context whether it rejects the high-`s` malleable form. If it does not reject it (which is the common historical behavior for this style of Tron/Ethereum ECDSA validation), the malleable duplicate is trivially producible by anyone holding a single private key, with no cooperation from other validators needed.

Contrast this with the correct implementation used for `TransactionCapsule.checkWeight` (used for on-chain transaction multi-sig, e.g., `AccountPermissionUpdateActuator`/`addSign` paths), which deduplicates strictly by recovered *address*: [3](#0-2) 

That function throws `PermissionException("... has signed twice!")` the moment the same address appears twice, regardless of the exact signature bytes — the correct, address-keyed uniqueness check. The `ValidateMultiSign` precompile does not apply this same address-only rule; it only prevents literal byte-for-byte replay of an identical signature, not distinct valid signatures from the same key.

### Impact Explanation
`ValidateMultiSign` is a public precompiled contract callable by any smart contract/EOA on the TVM (see `ValidateMultiSignContractTest`, callable as `validatemultisign(address,uint256,bytes32,bytes[])`). It is intended to let a smart contract certify that a TRON account's weighted multi-signature `Permission` (threshold + list of weighted keys) has been satisfied by a quorum of distinct authorized signers — exactly analogous to the checkpoint-signing quorum in the referenced report. Because the code only deduplicates by exact signature bytes, a single malicious key holder can supply the same message signed with itself plus a malleable/alternate-form signature (or otherwise produce two distinct valid signature encodings) to be counted as if two different authorized signers approved, inflating their effective weight and potentially satisfying the threshold alone. Any on-chain contract relying on this precompile for authorization/governance/multi-party-approval logic (custody wallets, DAOs, escrow, bridges) would then execute privileged actions with insufficient real quorum — an authentication/authorization bypass with concrete state-changing impact (auth bypass class explicitly listed as accepted impact).

### Likelihood Explanation
Likelihood is high for any account/permission configured with `keysCount` > 1 but where a single key's weight is close to (or, via repeated counting, can reach) the threshold. The attacker needs only their own private key (no privileged role, no cooperation from other key-holders) and knowledge of ECDSA signature malleability (a standard, widely known technique), or simply two distinct valid signature encodings for the same hash. This is directly reachable from a plain Solidity/TVM contract call — no special permissions are required to invoke the precompile.

### Recommendation
Change the duplicate check in `ValidateMultiSign.execute` to deduplicate strictly by `recoveredAddr` (not by the merged address+signature bytes), mirroring the address-only uniqueness enforcement already used in `TransactionCapsule.checkWeight`. Concretely: track a set of already-counted addresses; if `recoveredAddr` is already present, skip adding weight (do not fall through and add it again) regardless of whether the specific signature bytes differ. Additionally, verify/confirm that `ECDSASignature.validateComponents()` enforces canonical low-`s` (rejects malleable duplicates) to close this at the signature-recovery layer as a defense-in-depth measure.

### Proof of Concept
1. Create an account with an `Active` permission containing key `K` with weight `W1` and a threshold `T` such that `2*W1 >= T > W1` (i.e., one signer alone should not meet quorum).
2. Compute `hash = sha256(address || permissionId || data)` as done in `ValidateMultiSign.execute`.
3. Produce two distinct, both-valid signatures over `hash` from the single private key `K` — e.g., the standard signature `(r, s, v)` and its malleable counterpart `(r, n-s, v')`, both of which recover to the same address `K` when passed through `recoverAddrBySign`.
4. Call the `validatemultisign(address, permissionId, data, [sig1, sig2])` precompile with these two signatures.
5. In the loop, iteration 1 adds `K`'s weight `W1` and records `(K, sig1)`. Iteration 2 recovers the same `K`, finds `K` in `executedSignList` but the merged bytes for `sig2` differ from `sig1`'s, so `matrixContains(executedSignList, sign)` is false — the code does not `continue`; it proceeds to add `W1` again, making `totalWeight = 2*W1 >= T`.
6. The precompile returns "success" (`dataOne()`), even though only a single actual key/signer participated — confirming the quorum bypass.

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
