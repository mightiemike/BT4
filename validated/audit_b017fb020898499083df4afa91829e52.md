Based on my investigation, I found a concrete, code-documented integrity gap in the transaction-info verification path used by replay/verify tooling, analogous to the reported bug class (a state-commitment check that silently omits validation of a component that must match the authenticated root).

### Title
`ensure_match_transaction_info` omits verification of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, letting replay-verify report success on a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function that binds a locally re-executed `TransactionOutput` to the authenticated on-chain `TransactionInfo` for a given version, checking status, gas, write-set hash, and event root hash. [1](#0-0) 
It never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields carried on `TransactionInfoV0`/`TransactionInfoV1` that are supposed to bind the accumulator entry to the resulting state/hot-state/trading-native (position) Merkle roots. [2](#0-1) 
The gap is explicitly acknowledged in the code itself with a `TODO(trading-native)` comment stating that replay-verify tooling can therefore report success even when the authenticated position state root diverges from local execution. [3](#0-2) 

### Finding Description
`ensure_match_transaction_info` is called from the chunk executor and debugger/CLI replay-verify tooling to confirm that a locally computed `TransactionOutput` matches the committed `TransactionInfo` at a version. [4](#0-3) 
The position (trading-native) state root is computed separately in `DoStateCheckpoint::run`/`compute_position_checkpoint` and stored as `position_state_checkpoint_hash` on `TransactionInfoV1`, guarded by the `compute_trading_native_state_roots` onchain-config flag. [5](#0-4) [6](#0-5) 
Because `ensure_match_transaction_info` never re-derives and compares this hash (or the plain `state_checkpoint_hash`/`hot_state_checkpoint_hash`), any consumer relying solely on this function to validate re-executed output against the authenticated `TransactionInfo` — most notably `aptos-debugger`'s and the CLI's replay verification, and the chunk executor's output verification path — will accept a transaction as "matching" even if the resulting state, hot-state, or position Merkle root differs from what was actually committed on-chain. [7](#0-6) [8](#0-7) 

### Impact Explanation
This breaks the "authenticated API/state-view output bound to the right ledger version, root, and object" invariant: a divergence in the committed state root, hot-state root, or trading-native position root would not be caught by this verification helper, so tools built on it (replay-on-archive, debugger-based auditing, CLI verification) can silently certify a corrupted or incorrectly-executed chunk as valid. Since checkpoint-hash mismatches are exactly the class of bug that indicates non-determinism or a VM/storage divergence, this gap directly undermines the guarantee that "committed state differs from the correct VM result" would be detected — which is one of the explicitly in-scope impacts.

### Likelihood Explanation
The gap is only exercised when a consumer treats `ensure_match_transaction_info`'s `Ok(())` as a complete state-root check; whether the main consensus/execution commit path independently re-verifies these checkpoint hashes elsewhere was not something I could fully confirm within this investigation, so the state-commit path itself may still be safe. The concrete, provable weakness is scoped to the replay/verification tooling paths (`aptos-debugger`, CLI commands, chunk executor call site) that rely on this specific function. The trading-native/position-checkpoint portion is additionally gated behind the `compute_trading_native_state_roots` feature, so its practical exposure depends on that flag's enablement status, which I could not conclusively verify as enabled or disabled by default before running out of investigation budget.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when `TransactionInfoV1` is in use), and `position_state_checkpoint_hash` (when `compute_trading_native_state_roots` is active) against the values supplied by the caller, exactly as already done for `state_change_hash` and `event_root_hash`, before removing or resolving the existing `TODO(trading-native)` comment.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap, not a state-transition bug. The proof is the diff between what the function checks (`status`, `gas_used`, `state_change_hash`, `event_root_hash`) and what `TransactionInfo` actually carries (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), combined with the code's own acknowledgment of the gap in the `TODO(trading-native)` comment. [9](#0-8)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
