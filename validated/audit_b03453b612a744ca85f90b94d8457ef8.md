### Title
Unbounded `prefixQuery` in `DelegatedResourceAccountIndexStore.getWithPrefix` allows free, repeatable, attacker-inflated memory allocation via public read APIs - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix` (used by `getIndex`/`getV2Index`) calls `this.prefixQuery(key)` with no result-count limit, unlike `getKeysNext`/`getNext` which take an explicit `limit`. An attacker can pay a one-time, linear on-chain cost to create an arbitrarily large number of delegation-index entries under a single address prefix, then repeatedly invoke the free, unauthenticated `GetDelegatedResourceAccountIndexV2` HTTP/gRPC endpoint to force the node to materialize the entire prefix-matched key set into a `HashMap` on every call.

### Finding Description
`getWithPrefix` builds a key of `prefix + address` and calls `this.prefixQuery(key)` twice (for the from/to sides), collecting all matches into `ArrayList`s with no cap: [1](#0-0) 

This delegates to `TronStoreWithRevoking.prefixQuery`, which itself has no limit parameter and converts the full `revokingDB.prefixQuery(key)` result into another map: [2](#0-1) 

By contrast, other range-read paths on the same interface (`getKeysNext`, `getNext`) accept and enforce an explicit `limit`: [3](#0-2) [4](#0-3) 

The underlying LevelDB implementation confirms `prefixQuery` iterates and materializes every matching key/value pair into a `HashMap` with no size bound: [5](#0-4) 

**Reachable entry point:** `Wallet.getDelegatedResourceAccountIndexV2` calls `getV2Index`, which always uses `getWithPrefix`/`prefixQuery` (no fallback single-key lookup like the legacy `getIndex`): [6](#0-5) 
This is exposed unauthenticated over HTTP via `GetDelegatedResourceAccountIndexV2Servlet.fillResponse`: [7](#0-6) 
and equivalently via gRPC/Solidity/PBFT read replicas (`RpcApiService`, `RpcApiServiceOnSolidity`, `RpcApiServiceOnPBFT`, and their HTTP equivalents), none of which impose pagination or a result-count cap.

**Attacker-controlled inflation:** each delegate-index entry is created by a real `DelegateResourceContract` transaction, gated only by `delegateBalance >= 1 TRX` and sufficient frozen V2 balance on the owner: [8](#0-7) 
Each successful delegation adds one persistent entry under `V2_FROM_PREFIX+owner` (and `V2_TO_PREFIX+receiver`) via `delegateV2`, and these entries are never capped in count — an attacker who freezes `N` TRX and delegates 1 TRX each to `N` distinct receiver accounts creates `N` permanent index rows under one address prefix: [9](#0-8) 

Once created, this `N`-sized prefix is queryable for free, unauthenticated, and repeatable an unlimited number of times, each triggering an `O(N)` iterator scan and `O(N)` heap allocation on the node — the write cost (`N` TRX + bandwidth) is paid once by the attacker, but the read cost (`O(N)` server-side memory/CPU) is incurred anew, for free, on every subsequent query, by the attacker or anyone else who knows the inflated address.

### Impact Explanation
This is a resource-exhaustion / DoS amplification vector rather than a fund-theft or consensus-divergence bug: a bounded, attacker-paid write (linear TRX cost) can be leveraged into unbounded, free, repeatable read-side memory/CPU cost against any full node, solidity node, or PBFT node serving `GetDelegatedResourceAccountIndexV2`. Sustained repeated queries against a sufficiently inflated index address could degrade node responsiveness/availability for that public API, and by extension other requests served by the same node/thread pool.

### Likelihood Explanation
Feasible for any unprivileged account with modest TRX to freeze (linear in the desired `N`) and the ability to send `DelegateResourceContract` transactions to `N` existing receiver accounts (which the attacker can create cheaply themselves). No governance/admin access is required, and the query endpoint is public and repeatable without rate limiting beyond generic `RateLimiterServlet` (per-IP/time throttling, not per-result-size cost). The one-time setup cost scales with `N`, but is a fixed cost regardless of how many times the resulting expensive query is subsequently replayed for free — this cost asymmetry is the core of the finding.

### Recommendation
Add an explicit, bounded limit to `getWithPrefix`/`prefixQuery` calls used by publicly reachable query paths (`getIndex`, `getV2Index`), mirroring the `limit` parameter already used by `getKeysNext`/`getNext`, and enforce a maximum returned/iterated entry count (with pagination or truncation) at both the `TronStoreWithRevoking.prefixQuery` and `IRevokingDB`/`LevelDbDataSourceImpl`/`RocksDB` implementation layers so no single public API call can force unbounded materialization.

  private Map<byte[], byte[]> getNext(Snapshot head, byte[] key, long limit) {
    if (limit <= 0) {
      return Collections.emptyMap();
    }

    Map<WrappedByteArray, WrappedByteArray> collection = new HashMap<>();
    if (head.getPrevious() != null) {
      ((SnapshotImpl) head).collect(collection);
    }

    Map<WrappedByteArray, WrappedByteArray> levelDBMap = new HashMap<>();

    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().getNext(key, limit).entrySet().stream()
          .map(e -> Maps
              .immutableEntry(WrappedByteArray.of(e.getKey()), WrappedByteArray.of(e.getValue())))
          .forEach(e -> levelDBMap.put(e.getKey(), e.getValue()));
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().getNext(key, limit).entrySet().stream()
          .map(e -> Maps
              .immutableEntry(WrappedByteArray.of(e.getKey()), WrappedByteArray.of(e.getValue())))
          .forEach(e -> levelDBMap.put(e.getKey(), e.getValue()));
    }

    levelDBMap.putAll(collection);

    return levelDBMap.entrySet().stream()
        .map(e -> Maps.immutableEntry(e.getKey().getBytes(), e.getValue().getBytes()))
        .sorted((e1, e2) -> ByteUtil.compare(e1.getKey(), e2.getKey()))
        .filter(e -> ByteUtil.greaterOrEquals(e.getKey(), key))
        .limit(limit)
        .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue));
  }

  @Override
  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    resetDbLock.readLock().lock();
    try (DBIterator iterator = getDBIterator()) {
      Map<WrappedByteArray, byte[]> result = new HashMap<>();
      for (iterator.seek(key); iterator.hasNext(); iterator.next()) {
        Entry<byte[], byte[]> entry = iterator.peekNext();
        if (Bytes.indexOf(entry.getKey(), key) == 0) {
          result.put(WrappedByteArray.of(entry.getKey()), entry.getValue());
        } else {
          return result;
        }
      }
      return result;
    } catch (IOException e) {
      throw new RuntimeException(e);
    } finally {
      resetDbLock.readLock().unlock();
    }
  }
