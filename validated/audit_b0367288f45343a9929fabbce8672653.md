### Title
Startup accounts-lt-hash/capitalization calculation panics on unwrap if the account is removed from storage between index lookup and load - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::calculate_accounts_lt_hash_at_startup_from_index()` and `AccountsDb::calculate_capitalization_at_startup_from_index()` both walk the accounts index and, for every pubkey found in the index, load the actual account contents directly via `get_account_accessor(...).get_loaded_account(...)` and immediately call `.unwrap()` on the result. Unlike the normal read path (`do_load()` / `retry_to_get_account_accessor()`), which has an explicit retry/fallback loop to tolerate races with `clean_accounts()`/`shrink`/`purge_slots()` removing the underlying storage entry after the index lookup, these startup-hash functions have no such guard — the `.unwrap()` will panic if the storage entry has been concurrently removed.

### Finding Description
In `calculate_capitalization_at_startup_from_index()`, the `stored_lamports` closure does: [1](#0-0) 

```
self.get_account_accessor(slot, &account_info.storage_location())
    .get_loaded_account(|loaded_account| loaded_account.lamports())
    // SAFETY: The index said this pubkey exists, so
    // there must be an account to load.
    .unwrap()
```

The comment asserts that because the index says the pubkey exists, the storage must still contain it — but this assumption is exactly the invariant that the *ordinary* load path does not trust. `retry_to_get_account_accessor()` documents at length (in the same file) that shrink, clean, and purge can remove a storage entry between an index read and the subsequent storage access, and implements a bounded retry loop specifically to re-consult the index and, only after exhausting retries, escalate to a controlled `panic!`/`assert!` with rich diagnostic context: [2](#0-1) [3](#0-2) 

The startup capitalization/lt-hash routines bypass all of that retry machinery and call the accessor directly: [4](#0-3) 

This is precisely the "two calls with (nearly) the same inputs, one of them protected against failure and one not" pattern from the external report: the guarded call is the production read path (`do_load`/`retry_to_get_account_accessor`), and the unguarded call is the startup-verification path that reuses the same index-then-storage-lookup sequence without the retry/tolerance logic, so a legitimate concurrent background operation turns into an unwrap panic instead of a graceful retry.

The functions are documented as "only intended to be called at startup... NOT safe to call concurrently with flush operations", but they are reachable from `Bank::verify_accounts()` / `Bank::verify_snapshot_bank()`, which run as part of ledger-tool/snapshot verification and startup index generation — a period during which background AccountsBackgroundService threads (clean, shrink, ancient-pack) can already be active depending on startup sequencing: [5](#0-4) 

### Impact Explanation
If clean/shrink/purge removes the account's storage entry (e.g. because the account became zero-lamport and was cleaned, or the slot was shrunk) between the index scan and the subsequent `get_loaded_account()` call, the `.unwrap()` will panic, crashing the validator/ledger-tool process performing startup verification. This is a node panic caused by a normal, honest state transition racing with startup hash verification — matching the "node panic" and "honest-node snapshot-vs-replay mismatch" acceptance criteria, since the mismatch here manifests as a crash instead of a hash comparison result.

### Likelihood Explanation
Likelihood is moderate: it requires a race between the startup accounts-hash-verification pass and a concurrent clean/shrink pass touching the exact account being summed. Because these functions are explicitly commented as unsafe to run concurrently with flush operations, the window is presumably intended to be closed by callers, but no code enforces this at the call sites reviewed (`Bank::verify_accounts`), and the accessor logic itself contains no defensive retry the way the main read path does.

### Recommendation
Route `calculate_capitalization_at_startup_from_index()` and `calculate_accounts_lt_hash_at_startup_from_index()` through the same guarded/retryable accessor path as `load()`/`do_load()` (i.e., `retry_to_get_account_accessor()`), or explicitly re-check the index entry and skip/retry the pubkey if the storage entry is missing, instead of unconditionally unwrapping. At minimum, replace the bare `.unwrap()` with a bounded retry against the index (mirroring `retry_to_get_account_accessor`) before treating a missing storage entry as a corruption.

### Proof of Concept
Not independently reproduced in this analysis (would require orchestrating a concurrent `clean_accounts()`/shrink call against a bank while `verify_accounts()`/`calculate_capitalization_at_startup_from_index()` is running, similar to the existing regression test `accounts-db/tests/accounts_db.rs::test_load_after_remove_unrooted_and_restore_to_same_slot`, which demonstrates the same underlying storage-removal race for the ordinary load path): [6](#0-5)
