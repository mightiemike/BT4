### Title
JWT session-token verification errors leak internal library details and reflect the raw attacker-supplied token back to unauthenticated clients - ([File: packages/apps/shopify-api/lib/session/decode-session-token.ts](packages/apps/shopify-api/lib/session/decode-session-token.ts))

### Summary
`decodeSessionToken` wraps any failure from the `jose` JWT library into an `InvalidJwtError` whose message embeds both the raw, attacker-controlled token string and the underlying `jose` library's internal error text. This composed message is sent verbatim in HTTP error responses to anonymous/unauthenticated callers in `shopify-app-express`.

### Finding Description
In `decodeSessionToken`, any failure thrown by `jose.jwtVerify` (malformed token, bad signature, wrong algorithm, expired/not-yet-valid claims, etc.) is caught and re-thrown as: [1](#0-0) 
This message interpolates `error.message` straight from the `jose` library, and includes the raw `token` value supplied by the caller.

This exception propagates to `shopify-app-express`'s `validate-authenticated-session.ts`, which sends `error.message` directly to the client with no sanitization: [2](#0-1) 

The same unsanitized `error.message` reflection also happens for storage errors on that path: [3](#0-2) 

Reachability: any anonymous request that sets an `Authorization: Bearer <token>` header against an app route protected by `validateAuthenticatedSession` middleware will trigger `api.session.getCurrentId` → `decodeSessionToken`. Supplying any malformed/garbage token causes a 401 response whose body is `Failed to parse session token '<attacker-supplied-token>': <jose-internal-error-message>`. This is confirmed by an existing test asserting exactly this behavior: [4](#0-3) 

The `jose` library's internal error messages/class names (e.g. distinctive phrasing tied to its JWS/JWT validation internals) are exposed verbatim to the caller, revealing that the app uses the `jose` package for JWT verification and its specific failure semantics — directly matching the reported bug class of "error messages disclosing internal library implementation details." Additionally, echoing the raw token back is itself poor practice (reflects attacker input verbatim in a response, aiding blind-injection/log-forging style probing), compounding the disclosure.

Similar unsanitized propagation exists in the React Router / Remix packages' `validate-session-token.ts` helpers, though those log at `debug` level server-side rather than sending to the client: [5](#0-4) 
— that path is not directly attacker-observable and is a lower-severity analog by comparison to the Express one.

### Impact Explanation
An anonymous requester can trivially fingerprint the JWT verification library (`jose`) and observe its specific error taxonomy (expired vs. malformed vs. bad signature vs. wrong algorithm) by sending different malformed tokens and diffing the returned messages. This gives attackers a low-cost oracle to (a) confirm the exact JWT verification library and version-family behavior in use, (b) narrow down which validation branch failed (useful for crafting forged/near-valid tokens to bypass checks, e.g. distinguishing "wrong audience" vs. "signature invalid" vs. "expired"), and (c) target known CVEs in the fingerprinted dependency. It does not directly grant access without a valid signing key, but it materially assists reconnaissance and forgery attempts against the OAuth/session-token authentication boundary, which is the core defense keeping request authentication safe in embedded apps.

### Likelihood Explanation
High likelihood of exploitation as a reconnaissance step: no privileges are required, the endpoint is reachable by anonymous HTTP requests carrying any `Authorization: Bearer` header, and the behavior is deterministic and already covered/asserted by the project's own test suite, confirming it is intentional current behavior rather than an edge case.

### Recommendation
Replace the detailed library-derived message with a generic, non-sensitive message:
- In `decodeSessionToken` (`packages/apps/shopify-api/lib/session/decode-session-token.ts`), catch the `jose` error, log the full detail server-side only (e.g., via the configured logger), and throw `InvalidJwtError('Invalid session token')` without interpolating `error.message` or the raw `token`.
- In `validate-authenticated-session.ts`'s `handleSessionError` (`packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts`), stop sending `error.message` to the client for both the `InvalidJwtError` and default/storage-error branches; respond with a fixed generic string (e.g., `"Unauthorized"` / `"Internal Server Error"`) and log the real error server-side.

### Proof of Concept
1. Deploy an app using `@shopify/shopify-app-express` with a route protected by `validateAuthenticatedSession`.
2. Send: `GET /any-protected-route?shop=my-shop.myshopify.io` with header `Authorization: Bearer not_a_valid_token`.
3. Observe a `401` response whose body is `Failed to parse session token 'not_a_valid_token': <internal jose error message>` — confirmed by the existing test expectation `expect((response.error as any).text).toMatch('Failed to parse session token')` at [4](#0-3) .
4. Repeat with different malformed tokens (bad signature, expired `exp`, wrong `alg`) to observe distinct `jose`-specific error strings returned in the response body, confirming library/behavior fingerprinting without any authentication.
