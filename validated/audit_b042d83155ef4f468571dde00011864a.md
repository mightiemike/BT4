## Analog Found

### Title
KEYGEN/REFRESH finalization has no guard against in-flight outbound signing, causing signed-but-unbroadcastable outbounds with no automatic refund - (File: x/utss/keeper/msg_vote_tss_key_process.go, universalClient/tss/coordinator/coordinator.go, universalClient/tss/coordinator/msg_handler.go)

### Summary
The external report's root cause is a mutable, globally-scoped authority reference (`stakingContract`) that can be swapped while per-user state (`PendingGame`) created under the old reference is still in flight, leaving that state unrefundable and un-completable. The Push Chain analog is the TSS signing key: `x/uexecutor` creates `PendingOutbounds`/`OutboundTx` entries that must eventually be signed by "the" TSS key, but the signing/verification code always resolves "the current TSS key" (`GetCurrentTssKey` / `GetCurrentTSSKey`) at signing time rather than the key that was active when the outbound was created. `x/utss` lets a `KEYGEN` process finalize (`SetCurrentTssKey`) with no check that no outbounds are currently pending signature — unlike `InitiateFundMigration`, which explicitly requires `IsChainOutboundEnabled == false` and `HasPendingOutboundsForChain == false` before it will run. This asymmetry means an outbound created by an ordinary, unprivileged user shortly before a routine (non-malicious) key rotation finalizes can end up signed with a TSS key that the destination-chain vault does not yet trust, permanently stranding the outbound.

### Finding Description
- `x/uexecutor` creates an `OutboundTx`/`PendingOutbounds` entry from an ordinary user-triggered `UniversalTxOutbound` event [1](#0-0) . This entry carries no reference to which TSS key/process it should be signed under.
- `x/uexecutor/README.md` documents that `PendingOutbounds` is removed **only** on validator consensus of the observation, and that ballot expiry does **not** clean it up: "there is no safe automatic resolution... resolution is governance-driven, not chain-driven" [2](#0-1) .
- When the Universal Validator client actually signs an outbound, it always fetches the **current** TSS key rather than a key pinned at outbound-creation time, both when the coordinator builds the sign setup (`createSignSetup`) [3](#0-2)  and when the coordinator determines which pubkey a `SIGN_OUTBOUND` event should be verified against (`verifyingPubkey`) [4](#0-3) .
- `x/utss.InitiateFundMigration` explicitly guards against draining/rotating funds while outbounds are still in flight for a chain — it requires outbound disabled and `HasPendingOutboundsForChain == false` [5](#0-4) . This proves the module authors recognize "pending outbound + key/authority change" as a hazard that needs an explicit guard.
- However, that guard only protects the **fund migration** step (sweeping the old vault balance to the new TSS address). It does not gate **`SetCurrentTssKey`** itself, which is what actually flips which key is "current" and therefore which key `createSignSetup`/`verifyingPubkey` will use for all subsequent outbound signing [6](#0-5) . A `KEYGEN`/`REFRESH` process can finalize and call `SetCurrentTssKey` with pending outbounds for other chains (or even the same chain, if the migration precondition is evaluated before the outbound arrives) still unsigned.
- Once the new key becomes "current", any outbound whose sign event had not yet been processed will be signed with the new key. If the destination-chain vault's authorized signer has not yet been rotated (vault-side `setTSS` / on-chain fund migration for that specific chain has not completed — this is a per-chain, asynchronous, admin/relayer-driven step, see `e2e-tests/setup.sh` `step_sync_vault_tss_on_anvil`), the resulting signature will not be recognized by the vault contract, so the outbound broadcast will be rejected on the destination chain.
- Because `PendingOutbounds` entries are never auto-cleaned or auto-refunded (per the README excerpt above), this outbound is now permanently stuck: it cannot be re-signed with the old (now rotated-out) key by honest validators (the client always asks for the "current" key), and there is no on-chain refund/cancel path in `x/uexecutor` for a signed-but-unbroadcastable outbound.

### Impact Explanation
User or protocol-controlled funds that are already committed to an outbound (withdrawal of PRC20/native value back to an external chain) can become permanently unable to complete and permanently unable to be refunded, mirroring the "unauthorized... permanent freezing... refund" impact category. This is reachable purely from an ordinary user's withdrawal/outbound-creating transaction combined with the protocol's own scheduled key-rotation lifecycle (not malicious admin/validator behavior) — the same "impact of a normal admin operation" framing as the source Flip report.

### Likelihood Explanation
Likelihood is Medium/Low-Medium: it requires the timing window between outbound creation and the outbound's sign event being processed to overlap with a `KEYGEN`/`REFRESH` finalization, and requires the destination vault not yet trusting the new key at that instant. This is a narrow race, but `KEYGEN`/`REFRESH` are ordinary, periodic protocol operations (README: "lets the protocol periodically rotate the master key as a security uplift") [7](#0-6) , so the window recurs regularly, and outbound creation is fully attacker/user-controlled and can be timed to coincide with a known rotation window.

### Recommendation
- Pin the TSS `key_id`/pubkey (or process ID) that should sign an outbound at the moment the `OutboundTx`/`PendingOutbounds` entry is created (analogous to the report's recommendation to record the staking contract address in `PendingGame`), and have `createSignSetup`/`verifyingPubkey` use that pinned key rather than always re-resolving `GetCurrentTssKey`.
- Extend the guard already present in `InitiateFundMigration` (`HasPendingOutboundsForChain`) to also gate `SetCurrentTssKey`/key-process finalization itself, so a `KEYGEN`/`REFRESH` cannot become "current" while any chain still has outbounds pending signature, or provide an explicit drain/failover mechanism so outbounds signed under a now-superseded key are automatically re-queued and re-signed with the correct (still vault-trusted) key.
- Add an explicit refund/cancel path in `x/uexecutor` for outbounds that fail to broadcast due to signer mismatch, instead of relying purely on manual governance intervention.

### Proof of Concept
Not independently reproduced in this pass; this is a design/timing-race analysis based on reading `x/uexecutor`, `x/utss`, and `universalClient/tss` source. Confirming exploitability would require verifying, in the actual finalization code path for `MsgVoteTssKeyProcess` → `SetCurrentTssKey` (not fully retrieved due to iteration limits), whether any hidden gate on pending outbounds exists there, and confirming the exact timing of when a destination vault's trusted TSS address is rotated relative to `CurrentTssKey` becoming active on Push Chain.   destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.

// SetCurrentTssKey stores the finalized active TSS key.
func (k Keeper) SetCurrentTssKey(ctx context.Context, key types.TssKey) error {
	if err := key.ValidateBasic(); err != nil {
		return fmt.Errorf("invalid tss key: %w", err)
	}

	if err := k.CurrentTssKey.Set(ctx, key); err != nil {
		return fmt.Errorf("failed to set current tss key: %w", err)
	}

	// Also store in TssKeyHistory for reference
	if err := k.TssKeyHistory.Set(ctx, key.KeyId, key); err != nil {
		return fmt.Errorf("failed to record tss key history: %w", err)
	}

	k.Logger().Info("tss key stored",
		"key_id", key.KeyId,
		"process_id", key.ProcessId,
		"pubkey", key.TssPubkey,
		"participant_count", len(key.Participants),
	)
	return nil
}
