### Title
Stale-session-based token invalidation can clobber a concurrently refreshed valid access token (TOCTOU on session storage) - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
The reported bug class is a classic time-of-check-to-time-of-use (TOCTOU) flaw: a piece of state that is supposed to be protected against tampering during an in-flight async operation (`token.locked`) is not re-checked before a later mutating operation (`kick_tokens`) overwrites it, letting a delayed/late-arriving message destroy state that has since moved on. The analogous pattern in `shopify-app-js` is the access-token invalidation logic in the token-exchange authentication strategies: a `Session` object captured **before** one or more `await`s is later written back to session storage unconditionally on error, without re-reading/validating the *current* stored session first.

### Finding Description
In `performTokenExchange` (Express) the session is loaded once and held in a local variable that is reused across the whole async flow: [1](#0-0) 

Later, on error, this same possibly-stale `sessionToInvalidate` object is force-written back to storage, clearing its access token, with no check of what is currently persisted: [2](#0-1) [3](#0-2) 

The same shape exists in the Remix/React-Router `TokenExchangeStrategy.handleClientError`, where a `session` object obtained from `sessionContext` earlier in the request lifecycle is unconditionally invalidated and re-persisted on any 401 from the Admin API, again without checking whether storage already holds a newer, valid session (e.g. written by a concurrent token exchange for the same shop): [4](#0-3) [5](#0-4) 

`storeSession` implementations perform a blind upsert (`onConflictDoUpdate`/`INSERT ... ON CONFLICT`) keyed only by session `id`, with no optimistic-concurrency/version check and no locking, so any writer can overwrite whatever the current row holds: [6](#0-5) [7](#0-6) 

This mirrors `kick_tokens` exactly: `help_transfer` sets `token.locked = true` and expects no other path to mutate the token before the async payout resolves, but `kick_tokens` mutates the token anyway because it never checks the current `locked` flag before acting — it acts on a view of the token that is no longer authoritative. Here, `invalidateAccessToken` acts on a `Session` object captured at an earlier point in time and unconditionally persists it, without first re-loading/comparing against the current row in `sessionStorage`, so it can stomp a freshly-refreshed, valid access token written by a concurrent request for the same offline/online session id.

### Impact Explanation
If two requests for the same shop/session race (e.g., an embedded app firing multiple concurrent authenticated fetches right after a session expires, or a slow/late-arriving 401 from a stale in-flight Admin API call that was made against an old, now-refreshed session), the following can occur:
1. Request A loads an expired session, begins token exchange.
2. Request B also sees the (still) expired/invalid session, begins its own token exchange, succeeds, and stores a fresh, valid session for the shop.
3. Request A's earlier in-flight Admin API/token-exchange call eventually fails with 401 against the old token; the code invalidates its stale in-memory `Session` object (clearing `accessToken`) and writes it back to storage — overwriting the valid session B just stored.

The net effect is that the merchant's stored offline (or online) access token is nulled out even though a good token exists, forcing the app into a broken/looping re-auth state for that shop (denial of service of the auth handler) until another successful token exchange happens. This is state corruption caused entirely by ordinary concurrent, unprivileged application traffic — not by any privileged actor — matching the report's emphasis that this class of bug is "more likely to occur by accident rather than by...intentional attack."

### Likelihood Explanation
This requires only two roughly-concurrent authenticated requests to the app for the same shop while its session token/OAuth session is near expiry or invalid — a normal, unprivileged, non-malicious scenario in embedded Shopify apps (App Bridge frequently fires multiple simultaneous fetches). No secret, credential leak, or privileged access is needed; it is purely a race between ordinary request-authentication flows, closely paralleling the original report's note that the delay/race is "not within the control of individual users" and thus more accidental than adversarial.

### Recommendation
Before invalidating/overwriting a session's access token, re-load the current session from `sessionStorage` and only invalidate/store if the currently persisted `accessToken` still matches the one that produced the 401 (i.e., add an equality/version check analogous to `token.assert_not_locked()`), rather than blindly persisting a captured-in-memory `Session` object. Alternatively, use a conditional update (compare-and-swap on `accessToken`/an updated timestamp or version column) in the session-storage `storeSession` implementations so stale writes are rejected rather than silently overwriting newer state.

### Proof of Concept
Conceptual race (cannot be fully demonstrated without a live multi-request harness, but reachable via normal embedded-app traffic):
1. Shop's offline session is near/at expiry.
2. Two nearly-simultaneous authenticated requests hit `performTokenExchange`/`TokenExchangeStrategy.authenticate` for the same shop.
3. Request 1's outstanding Admin API call (made with the pre-refresh token) returns a 401 slightly after Request 2 has already completed a fresh token exchange and called `storeSession` with a valid new session.
4. Request 1's error handler calls `invalidateAccessToken` on its captured (stale) `Session` object and calls `storeSession`, clearing the `accessToken` field that Request 2 had just set — for code, see: [2](#0-1) [3](#0-2) 

Note: I could not execute a live concurrency test against the repository (no runtime/terminal access), so this is a code-level TOCTOU analysis based on the exact control-flow shown above rather than an observed runtime exploit trace.

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}

import {Session} from '@shopify/shopify-api';

import type {BasicParams} from '../../types';

export async function invalidateAccessToken(
  params: BasicParams,
  session: Session,
): Promise<void> {
  const {logger, config} = params;

  logger.debug(`Invalidating access token for session - ${session.id}`, {
    shop: session.shop,
  });

  session.accessToken = undefined;
  await config.sessionStorage!.storeSession(session);
