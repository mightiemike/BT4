### Title
Floating-point precision in the TRX/TRC10 exchange's Bancor-style price calculation permits value-extraction arbitrage - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Immunefi report describes a bug class where a swap function computes exchange rates in a way that a caller can exploit for profitable, value-extracting arbitrage. In java-tron's built-in decentralized exchange (a Bancor-style constant-power AMM for TRX/TRC10 pairs), the default swap-rate calculation is performed with IEEE-754 `double` floating-point arithmetic rather than exact/rounded decimal arithmetic, and this path is reachable by any unprivileged account, not just a privileged role.

### Finding Description
The exchange module (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) lets any account create liquidity pools and swap between TRX and TRC10 tokens. The core rate calculation lives in `ExchangeCapsule.transaction()`, which selects one of two processors depending on the `hardenedCalc` flag: [1](#0-0) 

By default (until the `allowHardenExchangeCalculation` chain parameter is enabled by committee proposal), `hardenedCalc` is `false`, and the price is computed by `ExchangeProcessor`, which uses `double` and `Maths.pow` for the Bancor relay-token math: [2](#0-1) 

whereas the "safe" variant, `SafeExchangeProcessor`, performs the identical formula with `BigDecimal` at controlled precision and rounding: [3](#0-2) 

The codebase's own regression test confirms the two implementations diverge on real inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), meaning the default floating-point path yields a different (and by construction less precise/rounded) swap output than the hardened, decimal-exact path for the same reserves and trade size: [4](#0-3) 

This swap path is invoked directly from `ExchangeTransactionActuator.execute()`, which is reachable by any account via a normal, unprivileged `ExchangeTransactionContract` transaction: [5](#0-4) 

and whether hardened math is used is controlled by a global toggle (`allowHardenExchangeCalculation`), not a per-caller permission: [6](#0-5) 

Because the pool balances (`firstTokenBalance`/`secondTokenBalance`) are shared state funded by the exchange creator and other traders, any unprivileged user who can predict or trigger favorable floating-point rounding in `exchangeToSupply`/`exchangeFromSupply` extracts value at the expense of the pool's other participants — structurally the same "price-calculation arbitrage" bug class as the external report, except the privileged-role element is absent here: exploitation requires no special role, satisfying the "unprivileged-user" analog requirement.

### Impact Explanation
If the floating-point rounding in `ExchangeProcessor` can be steered (e.g., through repeated small/large trade sizing) to yield outputs above the exact decimal-correct amount, a user can repeatedly drain TRX/TRC10 reserves from an exchange pool, extracting value that rightfully belongs to the pool (its creator/other traders). This is a direct state/accounting impact on funds held in the `Exchange`/`ExchangeV2` store, reachable by any TRON account with no special permission.

### Likelihood Explanation
Likelihood is only moderate to prove without direct experimentation: the presence of the `allowHardenExchangeCalculation` flag and `SafeExchangeProcessor` — built specifically to replace the double-based math with `BigDecimal` — strongly suggests the java-tron team already identified and hardened against a real precision-related arbitrage/rounding issue in this exact code path. However, the flag defaults to disabled unless the committee has activated it, so the exposure window and current-network state (whether the flag is enabled in the live/current chain) could not be confirmed with the available tools.

### Recommendation
Ensure `allowHardenExchangeCalculation` is enabled network-wide (or make `SafeExchangeProcessor`/`BigDecimal` the sole and default calculation path), removing `ExchangeProcessor`'s floating-point implementation entirely so no configuration state can leave the non-hardened, precision-vulnerable formula active. Additionally, add invariant checks (e.g., constant-product/constant-power monotonicity assertions) after each swap to reject any output that would violate the pool's economic invariant, independent of the arithmetic backend used.

### Proof of Concept
Not independently reproducible with the tools available (no execution/terminal access). The strongest static evidence is the test `testStrictMath` in `ExchangeProcessorTest.java`, which demonstrates that the non-hardened (`double`) processor and the hardened (`BigDecimal`) processor produce different results (`assertNotEquals`) for identical pool reserves and trade sizes across dozens of real-world-scale inputs, confirming a rounding/precision divergence exists in the default swap path exercised by any unprivileged `ExchangeTransactionContract` call.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
