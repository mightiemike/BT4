### Title
Base-fee unit-conversion truncation in `CalculateGasCost` can zero out gas fees for module-originated EVM execution - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` in `x/uexecutor/keeper/fees.go` unwraps the feemarket's `LegacyDec` base fee back to a raw `upc` integer by doing `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))`, relying on the comment's assumption that "the base fee is always a whole number of upc -- no fractional upc exists." [1](#0-0)  This is the same class of bug as the Sherlock report: a value is divided/truncated in native/raw precision without accounting for the possibility that the true quantity is fractional relative to the divisor, silently flooring to zero and breaking downstream invariants.

### Finding Description
`CalculateGasCost` receives `baseFee sdkmath.LegacyDec` (fetched via `k.feemarketKeeper.GetBaseFee(sdkCtx)`) and immediately divides its internal 18-decimal-precision raw integer by `1e18` to "unwrap" it into a whole `upc` amount: [2](#0-1) 

The feemarket base fee is a dynamically adjusted EIP-1559-style value (adjusted per block based on gas-used ratios using `LegacyDec` arithmetic), so there is no protocol-level guarantee that it remains an exact integer multiple of `1e18` (i.e., a whole number of `upc`) at all times — it can easily be sub-1-`upc` (e.g., `0.5` `upc`/gas) depending on parameters/adjustment history. If `baseFee < 1e18`, `baseFeeBig.Div(...)` truncates to `0`.

Once `baseFeeBig` becomes `0`:
- The validation `maxFeePerGas.Cmp(baseFeeBig) < 0` at line 63 trivially passes for essentially any `maxFeePerGas >= 0` supplied by the payload.
- `effectiveGasPrice` becomes `0`.
- `gasCost = effectiveGasPrice * gasUsed = 0`.

This flows into `DeductGasFeesFromReceipt`, which explicitly short-circuits when `gasCost.Sign() <= 0` and returns `nil` without deducting or burning any fee: [3](#0-2) 

`DeductGasFeesFromReceipt` is invoked from the universal execution flow (`execute_payload.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`, `msg_execute_payload.go`) to charge the recipient's smart account for the EVM gas consumed by their `UniversalPayload` execution. If the truncation condition is hit, module-originated EVM execution (`DerivedEVMCall`) consumes real gas/resources on-chain while the corresponding account pays zero `upc` for it.

### Impact Explanation
This falls under "corruption of ... gas fee accounting ... or canonical UniversalTx state" and effectively allows unpriced/free module-originated EVM execution reachable by any ordinary user submitting a `UniversalPayload` whenever the network's base fee for this specific charge path is below 1 `upc`/gas unit. That is a permanent loss for the protocol (fees expected to be burned are never collected) and an unfair/unauthorized zero-cost execution advantage for users transacting during such periods — undermining the gas-accounting invariant that execution must be paid for.

### Likelihood Explanation
Likelihood depends on whether the feemarket base fee can actually land below `1e18` raw units (< 1 `upc`) in production. Genesis/test configs observed in the repo set base fee at large integer `upc` values (e.g., `1000000000` `upc`) [4](#0-3) , which would need to decay significantly via the dynamic adjustment algorithm to cross below 1 `upc`, but the code contains no defensive floor/ceiling or explicit protocol invariant enforcing base fee stays an integer multiple of `1e18`; it merely assumes it via comment. I was not able to locate or fully verify the feemarket's `CalculateBaseFee`/adjustment implementation in this repo (it likely lives in the imported `cosmos/evm` x/feemarket module, outside this repo's indexed code), so I cannot confirm with certainty how far/fast the base fee can drift below 1 `upc` under realistic gas-usage patterns, or whether an external module-level minimum prevents this. This uncertainty should be resolved before treating this as a confirmed, immediately-exploitable issue.

### Recommendation
Do not floor-divide the base fee to a whole `upc` before comparison/multiplication. Instead, perform the `maxFeePerGas` comparison and the `effectiveGasPrice * gasUsed` multiplication using the full-precision `LegacyDec` representation of the base fee (or scale `maxFeePerGas`/`gasUsed` up to the same 18-decimal precision before dividing back down at the very end), only rounding the final `upc` gas cost — and round up (ceiling), not down, to avoid undercharging. This mirrors the normalization fix recommended in the referenced report (normalize to a common precision before comparing/computing, and round consistently rather than truncating raw values mid-calculation).

### Proof of Concept
Conceptual trace (I could not execute code in this environment, so this is a logical walkthrough of the existing code paths cited above):
1. Feemarket's `GetBaseFee` returns a `LegacyDec` representing `0.9` `upc` per gas (raw internal value `900000000000000000`), reachable during normal base-fee adjustment cycles.
2. A user submits a `UniversalPayload` with `maxFeePerGas = 1` (or even `0`) and a receipt with non-zero `GasUsed` (e.g., `50000`).
3. In `CalculateGasCost`: `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` → `900000000000000000 / 1000000000000000000 = 0` (integer division truncates). [5](#0-4) 
4. `maxFeePerGas.Cmp(baseFeeBig)` → `1 >= 0` passes validation. [6](#0-5) 
5. `effectiveGasPrice = 0`; `gasCost = 0 * 50000 = 0`. [7](#0-6) 
6. `DeductGasFeesFromReceipt` sees `gasCost.Sign() <= 0` and returns `nil` — no `SendCoinsFromAccountToModule`/`BurnCoins` call occurs. [3](#0-2) 

Result: the EVM gas actually consumed by the module-originated execution is never charged to the recipient account, in every block where the feemarket base fee is below 1 `upc`.
