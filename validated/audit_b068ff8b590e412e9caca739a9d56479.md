Based on my investigation, I found a genuine analog of the report's bug class: a computed "penalty/fee" amount that isn't consistently applied to fund flows, creating a mismatch between what's deducted for accounting purposes versus what's actually transferred — in this case in the outbound gas-refund path.

### Title
Excess gas refund is computed from user-supplied `GasFee` and unauthenticated `gasFeeUsed`, allowing self-inflated refunds that mint value out of the protocol - (File: `x/uexecutor/keeper/outbound.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
`GasFee` and `GasToken` for a normal (non-revert) outbound are taken directly from the `UniversalTxWithdraw` EVM event emitted by `UniversalGatewayPC`, which is populated from user-supplied call parameters to the gateway contract [1](#0-0) . Later, `applyGasRefund` computes `refundAmount = GasFee - gasFeeUsed` and calls `CallUniversalCoreRefundUnusedGas`, which mints/swaps and sends `refundAmount` worth of value to the sender/recipient [2](#0-1) .

### Finding Description
In the liquidation report, the vulnerability was that a fee/penalty was correctly *subtracted* for debt-accounting purposes but never applied to the *amount actually transferred out*, so the caller received more value out than the protocol accounted for taking in. The Push Chain analog is structurally similar: the `GasFee` figure that anchors the refund computation is attacker-influenced (it comes from the same contract call that originates the outbound, driven by whatever `gasFee`/`gasToken`/`gasLimit` the user's transaction passed to the gateway), while `gasFeeUsed` is the only figure independently attested by Universal Validators via `MsgVoteOutbound` [3](#0-2) . If a user (or a contract executing on their behalf during `executeUniversalTx`) sets an inflated `GasFee` on the outbound event relative to what will actually be consumed on the destination chain, `applyGasRefund` will compute a large positive `refundAmount` and mint/refund that difference back to the sender or the `RevertInstructions.FundRecipient` — an address fully controlled by the attacker [4](#0-3) .

Unlike the revert-outbound path, where `GasFee` is derived on-chain from `GetGasFeeInfoForRevertOutbound` (calling `UniversalCore.getOutboundTxGasAndFees`, a protocol-controlled source) [5](#0-4) , the normal outbound path takes `GasFee`/`GasToken`/`GasLimit`/`GasPrice` verbatim from the decoded contract event without cross-checking them against the registry-derived fee schedule [1](#0-0) . I was not able to fully trace, within the available index, whether `UniversalGatewayPC` (the Solidity contract itself, outside this Go repo's index) independently validates/clamps the `gasFee` parameter against `getOutboundTxGasAndFees` before emitting the event, or whether it trusts caller input. That contract's source is not part of this repository's indexed content, so I cannot confirm from this codebase alone whether the Solidity-side guard exists.

### Impact Explanation
If the gateway contract does not strictly clamp the emitted `GasFee` to the protocol's own fee schedule, an attacker could inflate `GasFee` on their own outbound, then have Universal Validators observe (truthfully) a low `gasFeeUsed` on the destination chain, triggering `CallUniversalCoreRefundUnusedGas` to mint/return the inflated difference to an attacker-controlled address — a direct unauthorized mint/drain of protocol-held value, matching the "unauthorized mint" and "PRC20/native asset accounting corruption" impact categories in scope.

### Likelihood Explanation
This requires confirming that `UniversalGatewayPC.sol` (not present in this Go-only index) does not itself bound `gasFee` to a protocol-computed value before emission. If the Solidity contract already re-derives `gasFee` from `getOutboundTxGasAndFees` internally rather than accepting an arbitrary caller-supplied fee, this finding is invalidated and the Go-side code is safe by construction, since it never validates `GasFee` before storing/using it.

### Recommendation
In the Go keeper (defense-in-depth, in case the Solidity contract does not fully constrain input), cross-check `event.GasFee`/`event.GasToken` in `BuildOutboundsFromReceipt` against a keeper-side call to `GetOutboundTxGasAndFees` for the resolved PRC20/gas token, rejecting or clamping outbounds whose declared `GasFee` exceeds the registry-computed maximum for the given `GasLimit`/destination chain, mirroring what `buildRevertOutbound` already does correctly.

### Proof of Concept
Not verified end-to-end because `UniversalGatewayPC.sol`'s emission logic (whether it independently computes `gasFee` or accepts caller input) is outside this repository's indexed scope. The conceptual PoC:
1. Attacker calls the gateway's outbound-initiating function specifying an inflated `gasFee`/`gasToken` and a `RevertInstructions.FundRecipient` they control.
2. `BuildOutboundsFromReceipt` stores this attacker-supplied `GasFee` verbatim onto the `OutboundTx` [6](#0-5) .
3. Honest Universal Validators observe the real (low) `gasFeeUsed` on the destination chain and vote it via `MsgVoteOutbound`.
4. `applyGasRefund` computes a large `refundAmount = GasFee - gasFeeUsed` and mints/swaps that value to the attacker's recipient [7](#0-6) .

Given the unresolved dependency on the out-of-scope Solidity contract, I flag this as a candidate finding requiring confirmation of the gateway contract's input handling rather than a fully verified vulnerability.

func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

	refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
	gasToken := common.HexToAddress(outbound.GasToken)

	// Refund recipient: prefer fund_recipient in revert_instructions, fall back to sender
	refundRecipient := outbound.Sender
	if outbound.RevertInstructions != nil && outbound.RevertInstructions.FundRecipient != "" {
		refundRecipient = outbound.RevertInstructions.FundRecipient
	}
	recipientAddr := common.HexToAddress(refundRecipient)

	refundPcTx := &types.PCTx{
		Sender:      outbound.Sender,
		BlockHeight: uint64(ctx.BlockHeight()),
	}

	// Step 1: try refund with swap (gasToken → PC native)
	fee, swapErr := k.GetDefaultFeeTierForToken(ctx, gasToken)
	var swapFallbackReason string

	if swapErr == nil {
		quote, quoteErr := k.getSwapQuoteForRefund(ctx, gasToken, fee, refundAmount)
		if quoteErr == nil {
			minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
			minPCOut.Div(minPCOut, big.NewInt(100))

			resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, true, fee, minPCOut)
			if err == nil {
				refundPcTx.TxHash = resp.Hash
				refundPcTx.GasUsed = resp.GasUsed
				refundPcTx.Status = "SUCCESS"
				outbound.PcRefundExecution = refundPcTx
				return
			}
