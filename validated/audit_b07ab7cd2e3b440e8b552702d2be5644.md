Based on my investigation, I found a concrete, self-documented integrity-check gap that matches the required bug class (proof/state-commitment field silently unvalidated).

### Title
`ensure_match_transaction_info` Skips Validation of State/Hot-State/Position Checkpoint Hashes During Replay Verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to confirm that a locally re-executed `TransactionOutput` matches an authenticated, accumulator-committed `TransactionInfo`. [1](#0-0)  It validates status, gas used, write-set hash, and event root hash, but never validates `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents. [2](#0-1) 

### Finding Description
`TransactionInfo`/`TransactionInfoV1` carries multiple checkpoint-hash fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) that are part of the leaf hashed into the transaction accumulator and therefore covered by the ledger's authenticated proof structure. [3](#0-2)  `ensure_match_transaction_info` is the comparator meant to assert that a re-executed output is consistent with that authenticated `TransactionInfo`, but it only checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`: [4](#0-3) 

The function's own comment states the gap explicitly: it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and flags this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." [5](#0-4) 

This function is called from the `db-tool`'s `replay_on_archive` command, which is the tool operators/auditors use to independently re-execute historical mainnet transactions against an archive and confirm the results match the chain's authenticated `TransactionInfo` records.  Because the position/hot-state checkpoint hash — gated behind the `compute_trading_native_state_roots` on-chain config flag used during block execution and state-checkpoint computation — is skipped in this comparator, a divergence between the authenticated on-chain checkpoint root and the locally recomputed root will not be detected. [6](#0-5) 

### Impact Explanation
This is an instance of the exact bug class targeted: an integrity/validation routine that checks some but not all fields backing a proof-bearing, accumulator-committed structure, exactly analogous to `validateMaxInNegative` skipping slippage checks on positive `balanceDelta`. Here, `ensure_match_transaction_info` skips checkpoint-hash fields that are part of the authenticated `TransactionInfo` leaf. If the `position_state_checkpoint_hash` (or hot-state/state checkpoint hash) computed by local re-execution diverges from the value recorded on-chain — due to a nondeterminism bug, storage corruption, or a hard-fork-only divergence in the trading-native state root computation — `replay_on_archive` would report the replay as successful and the two ledgers as consistent, masking a real state-commitment divergence. This directly matches the required "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Wrong ... proof accepted as valid" impact categories.

### Likelihood Explanation
The severity is bounded by two factors I could confirm but not fully resolve without further exploration: (1) the gap is already flagged in-code as a known TODO rather than a hidden defect, and (2) the affected checkpoint hash is tied to `compute_trading_native_state_roots`, an on-chain config flag whose current mainnet-enabled status I was not able to confirm from the available code (referenced in `types/src/block_executor/config.rs` and `types/src/on_chain_config/aptos_features.rs`, but I could not retrieve file contents to verify activation status). If this flag is not yet active on mainnet, current-day impact is limited to future risk; if it is active, the gap is live today in the `replay_on_archive` auditing/verification tool path.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed values and `txn_info`'s recorded values whenever those fields are present (`TransactionInfoV1`), consistent with the TODO's own guidance, before `compute_trading_native_state_roots`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet.

### Proof of Concept
Not independently reproducible from static review alone: exercising this requires (1) an execution path where `compute_trading_native_state_roots` is active and produces a `position_state_checkpoint_hash` that differs between two independent re-executions of the same committed transaction (e.g., via a nondeterminism bug in position-state accumulation in `execution/executor/src/workflow/do_state_checkpoint.rs`), and (2) invoking `db-tool replay_on_archive`, which calls `ensure_match_transaction_info` and would report success despite the mismatched checkpoint hash. I confirmed the missing comparisons in code but did not have tooling access to run `replay_on_archive` end-to-end to demonstrate a live divergence being masked.
