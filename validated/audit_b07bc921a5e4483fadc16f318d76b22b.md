### Title
Vault deposit/redeem/borrow accounting trusts the nominal transfer `amount` instead of the actual balance delta, breaking for tokens whose balance changes outside of transfers - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Every Zest vault (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-usdc`, `v0-vault-usdh`) keeps an internal accounting ledger, `assets`, that is supposed to mirror the underlying token balance actually held by the vault. `deposit`, `redeem`, and `system-borrow` all update `assets` and mint/burn shares using the caller-supplied `amount` parameter, never the balance actually observed before/after the underlying `transfer` call. This is the same "assumed 1:1 relationship between escrowed/ledgered tokens and actual token balance" root cause described in the Nibiru finding, applied within a single transaction to Zest's `receive-underlying` / `send-underlying` helpers.

### Finding Description
`receive-underlying` and `send-underlying` in every vault simply forward the nominal `amount` to `transfer` and discard any information about what was actually moved: [1](#0-0) 

`deposit` then uses that same nominal `amount` to (a) preview shares via `convert-to-shares-preview amount`, (b) mint `inkind` shares, and (c) bump the ledger `(var-set assets (+ current-assets amount))` - all without ever comparing the vault's real underlying balance (`ubalance`) before and after the call: [2](#0-1) 

`redeem` mirrors this: it burns `amount` shares, calls `send-underlying inkind recipient`, then sets `(var-set assets (- current-assets inkind))`, again trusting that exactly `inkind` units left the vault: [3](#0-2) 

`system-borrow` follows the identical pattern, incrementing `principal-scaled`/`total-borrowed` by the nominal `amount` and then calling `send-underlying amount receiver`: [4](#0-3) 

The `ubalance` helper, which queries the real on-chain balance of the underlying token held by the vault, exists in every vault but is never invoked inside `deposit`/`redeem`/`system-borrow` to reconcile the ledger: [5](#0-4) 

This is functionally the same defect Nibiru had before it queried `actualSentAmount` via balance-before/after in `convertCoinToEvmBornERC20` - Zest's `receive-underlying`/`send-underlying` never do that balance check at all, for any vault, on any of the six supported underlyings (wSTX, sBTC, stSTX, USDC, USDH, stSTXbtc). If any of these underlying `<ft-trait>` implementations (or a future one added by DAO governance without code changes to the vault) ever moves a different amount than the nominal `amount` during the `transfer` call itself - e.g., a fee-on-transfer deduction, a hook-triggered rebase, or any balance mutation that fires synchronously inside the SIP-010 `transfer` call - the ledger (`assets`) and the shares/debt accounting diverge from the real balance within that single transaction, since the guard (`amount`/`inkind` value used for all bookkeeping) is evaluated and committed before/without ever being invalidated by the actual balance change that transfer produced.

### Impact Explanation
If the divergence is positive (vault ends up holding more than the ledger records), the surplus is permanently unaccounted for and effectively stranded/unclaimable through normal vault mechanics - a temporary/permanent freezing of those funds from the protocol's perspective. If negative (vault ends up holding less than the ledger records), `get-available-assets`/`total-assets` overstate real liquidity, so later `redeem`/`system-borrow` calls can be authorized against liquidity that doesn't exist, causing insufficient-balance reverts, or worse, other legitimate depositors' redemptions failing once the shortfall surfaces - a form of fund freezing/insolvency for the shared vault ledger. This lands in the **Temporary/permanent freezing of funds** impact class.

### Likelihood Explanation
Likelihood depends entirely on whether any underlying token onboarded to a vault (currently hardcoded per vault but changeable only through new vault deployments) can move a different amount than requested during its `transfer` call. Since the vault code makes no attempt to defend against this class of token behavior anywhere (`ubalance` is defined but unused for reconciliation in the hot paths), the contracts are unconditionally exposed the moment such a token is used, exactly mirroring the disputed-but-ultimately-valid Nibiru report where the mitigating "actual sent amount" check was the deciding factor of severity.

### Recommendation
In `receive-underlying`/`send-underlying` (or immediately around their call sites in `deposit`, `redeem`, `system-borrow`, and `system-repay`), capture `ubalance` before and after the underlying `transfer` and use the observed delta - not the nominal `amount`/`inkind` parameter - for all `assets`, share-mint/burn, and debt-ledger updates. Alternatively, explicitly restrict onboardable underlyings to tokens verified not to alter balances outside of a plain, fee-free transfer.

### Proof of Concept
1. DAO (or vault deployment) selects an underlying token for a new vault whose SIP-010 `transfer` implementation deducts an internal fee or otherwise changes the sender/recipient balance by an amount different from the `amount` argument (a fee-on-transfer or synchronously-rebasing token).
2. A user calls `deposit amount min-out recipient` on that vault.
3. `receive-underlying amount account` executes `transfer amount account current-contract none)`; the vault's real underlying balance increases by `amount - fee`, not `amount`.
4. `deposit` nonetheless mints `inkind` shares computed via `convert-to-shares-preview amount` and does `(var-set assets (+ current-assets amount))`, using the full nominal `amount`.
5. The ledger `assets` now overstates the vault's real underlying balance by `fee`, all within this single transaction - no invalidation of the previously-computed `amount`/`inkind` values ever occurs.
6. Subsequent `redeem` calls rely on `get-available-assets` (derived from the inflated `assets`) to authorize withdrawals, eventually causing `send-underlying` to attempt sending more than the vault actually holds, reverting or starving later redeemers of their rightful liquidity.

(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)

  (try! (ft-burn? zft amount account))
  (try! (send-underlying inkind recipient))
  (var-set assets (- current-assets inkind))

      recipient: recipient,
      shares-burned: amount,
      amount-received: inkind,

(define-public (system-borrow (amount uint) (receiver principal))
  (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (CAP-DEBT (var-get cap-debt))
      (available-assets (get-available-assets))
      (scaled-principal (var-get principal-scaled))
      (idx (var-get index))
      (debt (total-debt))
      (scaled-amount (mul-div-up amount INDEX-PRECISION idx))
      (updated-scaled-principal (+ scaled-principal scaled-amount)))

    (try! (check-caller-auth))
    (asserts! (not (get borrow states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (<= amount available-assets) ERR-INSUFFICIENT-VAULT-LIQUIDITY)
    (asserts! (<= (+ debt amount) CAP-DEBT) ERR-DEBT-CAP-EXCEEDED)

    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed (+ (var-get total-borrowed) amount))
    (try! (send-underlying amount receiver))

    (print {
      action: "system-borrow",
      caller: contract-caller,
      data: {
        receiver: receiver,
        amount: amount,
        scaled-amount: scaled-amount,
        principal-scaled: updated-scaled-principal,
        total-borrowed: (var-get total-borrowed),
        index: idx
      }
    })

    (ok true)))
