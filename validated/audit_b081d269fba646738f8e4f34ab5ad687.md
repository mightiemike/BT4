### Title
Voting reward accounting lets a voter capture a full cycle's Vi-based reward for freezing/voting only moments before the reward-cycle boundary, then withdraw immediately after maintenance - ([File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java])

### Summary
The reported Sherlock bug is a class of "stale batch-recalculated exchange rate" front-running: a state variable (`exchangeRate`) is only updated once per period during a privileged/periodic recalculation, while deposits/withdrawals meanwhile use the stale rate, letting an attacker deposit right before the recalculation and withdraw right after to capture already-realized profit without having borne the risk. The closest analog in java-tron is the DPoS vote-reward accounting mechanism, where `witnessVi` (the per-witness reward index) is recalculated only once per maintenance cycle, and a voter's reward share is computed by multiplying the "current" vote weight (`AccountCapsule.getVotesList()`/`vote.getVoteCount()`) by `deltaVi` accumulated over the whole `[beginCycle, endCycle)` window, without any check that the voter actually held that vote weight for the entire window.

### Finding Description
`accumulateWitnessVi()` recalculates and stores the reward index (`Vi`) for a witness once per maintenance cycle, based on the total reward paid to that witness in that cycle divided by the witness's total vote count that cycle: [1](#0-0) 

This is triggered from `MaintenanceManager.doMaintenance()` right at the maintenance/period boundary: [2](#0-1) 

An account's earned reward is then computed by `VoteRewardUtil.computeReward` / `MortgageService.computeReward`, which multiplies the *account's current vote count for a witness* by the delta of `Vi` between `beginCycle-1` and `endCycle-1` — i.e. the entire span since the account last withdrew/synced — with no verification that the vote was actually cast/held for that whole span: [3](#0-2) [4](#0-3) 

Critically, `VoteWitnessActuator`/`VoteWitnessProcessor` do **not** reset `beginCycle`/`endCycle` to the current cycle when a new vote is cast; they only call `mortgageService.withdrawReward(ownerAddress)` (which syncs the reward ledger for prior cycles) and then overwrite the account's vote list: [5](#0-4) [6](#0-5) 

Because `withdrawReward` is called *before* the new vote is recorded, and afterward `beginCycle` is advanced only to `endCycle` (the last already-settled cycle), the newly cast vote's weight becomes eligible to earn `deltaVi` for the *upcoming* cycle boundary computed at the *next* maintenance call — even if the vote was cast a single block before that maintenance runs. Since `Vi` for a witness depends on `getReward(cycle, address)` (block rewards + brokerage-adjusted transaction fee rewards, all publicly observable in real time via public reward pools) divided by the witness's total vote count for that cycle (also public via `WitnessCapsule.getVoteCount()`/`DelegationStore.getWitnessVote`), an attacker can precisely estimate the impending `deltaVi` for the current cycle before the maintenance boundary is reached.

### Impact Explanation
An attacker can:
1. Monitor the accumulated (but not-yet-applied) `reward`/`voteCount` for a witness (all public reads on `DelegationStore`/`WitnessCapsule`).
2. Freeze balance and cast a large vote for that witness in the last block(s) before the next maintenance triggers `doMaintenance()`.
3. When maintenance runs, `accumulateWitnessVi` immediately credits `deltaVi` for the just-closed cycle using the witness's total vote count — which now includes the attacker's freshly-added vote weight for that already-elapsed cycle's rewards (since the account's `beginCycle`/`endCycle` bookkeeping treats the whole span as reward-eligible once the vote exists at settlement time).
4. The attacker calls `withdrawReward`/`WithdrawRewardProcessor.execute` right after maintenance to claim `allowance` and can further unfreeze immediately (subject to unfreeze delay rules) diluting the reward that should have accrued only to voters who held their vote for the full cycle.

This dilutes the rewards of honest, long-term voters/delegators, and effectively extracts value (already-materialized block/tx-fee rewards) that the attacker did not economically earn by holding TRON Power at risk for the reward period — directly matching the impact class of the referenced report (free profit at the expense of other participants, "accounting corruption"/asset-value dilution among delegators).

### Likelihood Explanation
Likelihood is credible but conditional:
- All inputs needed to time the attack (witness reward accumulation, existing vote counts, maintenance schedule/`getNextMaintenanceTime`) are public and readable without any privileged access.
- The attack requires freezing TRX to obtain TRON Power and casting a vote via a normal, permissionless `VoteWitnessContract`/`voteWitness` TVM call — well within "anonymous broadcast transaction" reach.
- However, execution is constrained by real-world timing (must land the vote transaction in a block immediately preceding the maintenance-triggering block) and by TRON's unfreeze delay (`supportUnfreezeDelay`), which limits how quickly the attacker can exit the frozen principal, though the reward itself (`allowance`) can be withdrawn immediately after maintenance regardless of unfreeze status.

### Recommendation
- Snapshot/lock the voter's `voteCount` contribution used for `Vi` distribution at the boundary that corresponds to when the vote was actually cast, not merely at the next `beginCycle`/`endCycle` settlement.
- When `VoteWitnessActuator`/`VoteWitnessProcessor` register a new vote, explicitly synchronize `beginCycle` to `currentCycle + 1` (i.e., the vote should only start earning `Vi` for cycles strictly after the cycle in which it was cast), rather than relying solely on `withdrawReward`'s implicit bookkeeping.
- Consider a time-weighted or minimum-holding-period requirement before votes become reward-eligible, analogous to the report's recommendation of processing deposits/withdrawals against the *next* period's rate rather than the currently stale one.

### Proof of Concept
1. Observe (via public `DelegationStore.getReward(currentCycle, srAddress)` and `WitnessCapsule.getVoteCount()`, both public state) that witness `SR1` has accumulated a large unclaimed `reward` for the current cycle, close to the next maintenance boundary (`ConsensusDelegate.getNextMaintenanceTime()`).
2. Attacker freezes TRX to obtain TRON Power, then broadcasts `VoteWitnessContract` votes for `SR1` (via `VoteWitnessActuator.execute` → `countVoteAccount`), which internally calls `mortgageService.withdrawReward(ownerAddress)` (settling prior cycles with zero vote) then records the new vote weight into `AccountCapsule`/`VotesCapsule` — see `VoteWitnessActuator.java:152-191`.
3. On the next block that crosses `nextMaintenanceTime`, `MaintenanceManager.doMaintenance()` runs `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` — `MaintenanceManager.java:96-101` — which now includes the attacker's added vote weight in the `voteCount` denominator/eligibility used to derive `Vi` for the freshly closed cycle.
4. Attacker calls the reward-withdraw path (`WithdrawRewardProcessor.execute` / `MortgageService.withdrawReward`) to move `allowance` into spendable `balance` — `WithdrawRewardProcessor.java:38-68`, `MortgageService.java:89-134` — capturing reward for a cycle in which the vote was held for only a fraction of the period.
5. Attacker can then unvote/unfreeze (subject to unfreeze delay) to exit, having captured reward disproportionate to actual time-weighted participation, diluting long-term voters of `SR1`.

Note: I was not able to fully trace every edge case in `RewardViCalService`'s legacy vs. new-algorithm cycle-boundary handling within the available indexed context, so there may be additional guardrails (e.g., cycle-transition ordering nuances) not fully visible in the excerpts reviewed; a full Devin session with complete repository access would be needed to conclusively confirm exploitability against current mainnet parameters (e.g., exact unfreeze-delay duration) and to rule out any implicit protections in `countVote`/`RewardViCalService.accumulateWitnessReward` ordering that could mitigate this within a single cycle.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  public void execute(VoteWitnessParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getVoterAddress();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);

    VotesCapsule votesCapsule = repo.getVotes(ownerAddress);
    if (votesCapsule == null) {
      votesCapsule = new VotesCapsule(ByteString.copyFrom(ownerAddress),
          accountCapsule.getVotesList());
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    Map<ByteString, Long> voteMap = new HashMap<>();
    Iterator<Protocol.Vote> iterator = param.getVotes().iterator();
    try {
      long sum = 0;
      while (iterator.hasNext()) {
        Protocol.Vote vote = iterator.next();

        byte[] witnessAddress = vote.getVoteAddress().toByteArray();
        /*
          Already covered while doing maintenance in MaintenanceManager.java, for tvm performance,
          we remove the account check
         */
//        if (repo.getAccount(witnessAddress) == null) {
//          throw new ContractValidateException(
//              ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
//        }
        if (repo.getWitness(witnessAddress) == null) {
          throw new ContractExeException(
              WITNESS_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
        }

        long voteCount = vote.getVoteCount();
        if (voteCount < 0) {
          throw new ContractExeException("Vote count must not be less than 0");
        } else if (voteCount == 0) {
          iterator.remove();
        } else {
          sum = LongMath.checkedAdd(sum, voteCount);
          // merge vote for same witness
          voteMap.put(vote.getVoteAddress(),
              LongMath.checkedAdd(voteMap.getOrDefault(vote.getVoteAddress(), 0L), voteCount));
        }
      }

      long tronPower;
      if (repo.getDynamicPropertiesStore().supportUnfreezeDelay()
          && repo.getDynamicPropertiesStore().supportAllowNewResourceModel()) {
        tronPower = accountCapsule.getAllTronPower();
      } else {
        tronPower = accountCapsule.getTronPower();
      }
      sum =  LongMath.checkedMultiply(sum, TRX_PRECISION);
      if (sum > tronPower) {
        throw new ContractExeException(
            "The total number of votes[" + sum + "] is greater than the tronPower[" + tronPower
                + "]");
      }
    } catch (ArithmeticException e) {
      throw new ContractExeException(e.getMessage());
    }

    for (Map.Entry<ByteString, Long> entry : voteMap.entrySet()) {
      accountCapsule.addVotes(entry.getKey(), entry.getValue());
      votesCapsule.addNewVotes(entry.getKey(), entry.getValue());
    }
    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    repo.updateVotes(ownerAddress, votesCapsule);
  }
