### Title
DoS via unbounded AssetIssueV2Store iteration in `getAllAssetIssues()` used by `Wallet.getAssetIssueList`/`getAssetIssueByAccount`/`getAssetIssueByName`/`getAssetIssueListByName` - (chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java)

### Summary
`AssetIssueStore.getAllAssetIssues()` performs a full, uncapped iteration of the entire on-disk asset store via `Streams.stream(iterator()).map(Entry::getValue).collect(Collectors.toList())`, and this method is called by several unauthenticated read RPC/HTTP endpoints (`getAssetIssueList()`, `getAssetIssueByAccount`, `getAssetIssueByName`, `getAssetIssueListByName`) with no size cap, unlike `getAssetIssuesPaginated` which only limits after fully materializing the list. However, the practical attacker cost to inflate this store is significantly higher than the question assumes, because `AssetIssueActuator.validate()` enforces "an account can only issue one asset," forcing the attacker to fund and activate a brand-new account per asset in addition to paying `assetIssueFee`.

### Finding Description
`getAllAssetIssues()` at [1](#0-0)  iterates the full LevelDB/RocksDB store and materializes every `AssetIssueCapsule` into a `List`, with no cap. `getAssetIssuesPaginated` at [2](#0-1)  internally calls `getAllAssetIssues()` first and applies `ASSET_ISSUE_COUNT_LIMIT_MAX` only after the full list is built and sorted — confirming the cap is not applied at the iteration level.

This unbounded method is reachable from several unauthenticated wallet APIs:
- `Wallet.getAssetIssueList()` [3](#0-2) 
- `Wallet.getAssetIssueByAccount()` [4](#0-3) 
- `Wallet.getAssetIssueByName()` and `Wallet.getAssetIssueListByName()` [5](#0-4) 

These are exposed via HTTP servlets (e.g. `GetAssetIssueListServlet`) [6](#0-5)  and gRPC `WalletSolidityApi`/`WalletApi`/PBFT wrappers [7](#0-6) [8](#0-7) , all reachable without authentication (only generic `RateLimiterServlet` QPS-based rate limiting applies, not a per-request cost cap tied to state size) [9](#0-8) .

However, the attacker's ability to cheaply inflate the store is constrained: `AssetIssueActuator.validate()` rejects any account that has already issued an asset — "An account can only issue one asset" [10](#0-9) . This means the attacker cannot just resend `AssetIssueContract` transactions from a single funded account; each new asset requires a distinct, newly-activated account paying both account-activation cost and `dynamicStore.getAssetIssueFee()` (charged and burned/sent to blackhole in `execute()`) [11](#0-10) . This raises the attacker's cost per inflated entry substantially compared to the premise of "N * assetIssueFee" from one account, but does not eliminate the underlying algorithmic issue — an attacker with enough capital/automation to create N accounts can still inflate the store to N entries, and every subsequent unauthenticated `getAssetIssueList`/`getAssetIssueByAccount`/`getAssetIssueByName` call will pay O(N) iteration/serialization cost with no per-request limit.

### Impact Explanation
This matches "DoS via RPC-API" — attacker-inflatable, unauthenticated-reachable state causes unbounded CPU/memory/bandwidth cost per query (`BandwidthProcessor.updateUsage` runs once per capsule for every returned asset in `getAssetIssueList`/`getAssetIssueByAccount`/`getAssetIssueListByName`), degrading node responsiveness for all RPC/HTTP clients hitting these endpoints.

### Likelihood Explanation
Feasible but with materially higher cost than described in the question: the attacker needs N funded, activated accounts (not just N transactions from one account), each paying `assetIssueFee` plus standard account-creation/activation bandwidth costs, before this becomes economically expensive at scale. It is still achievable by a moderately funded, patient attacker (e.g. scripted account creation + one asset-issue tx per account), and there is no protocol-level cap on the total number of distinct assets issuable chain-wide. Repeatability is high once achieved, since the inflated store persists permanently (no deletion path for issued assets) and every future unauthenticated query pays the cost.

### Recommendation
- Enforce `ASSET_ISSUE_COUNT_LIMIT_MAX` (or a similar bound) during iteration/collection in `getAllAssetIssues()`/`getAssetIssuesPaginated()`, not after full materialization.
- Require `offset`/`limit` on `getAssetIssueList` and deprecate/cap the no-argument overload to a bounded result size.
- Consider adding a per-endpoint cost-aware rate limiter (e.g., scaling with current asset count) in addition to the existing QPS-based `RateLimiterServlet`.
- Consider adding a global or per-account cap on total number of assets issuable network-wide, or an increasing/burned issuance fee, to bound worst-case store growth.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public AssetIssueContract getAssetIssueByName(ByteString assetName)
      throws NonUniqueObjectException {
    if (assetName == null || assetName.isEmpty()) {
      return null;
    }

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    if (chainBaseManager.getDynamicPropertiesStore().getAllowSameTokenName() == 0) {
      // fetch from old DB, same as old logic ops
      AssetIssueCapsule assetIssueCapsule =
          chainBaseManager.getAssetIssueStore().get(assetName.toByteArray());
      if (assetIssueCapsule != null) {
        processor.updateUsage(assetIssueCapsule);
        return assetIssueCapsule.getInstance();
      } else {
        return null;
      }
    } else {
      // get asset issue by name from new DB
      List<AssetIssueCapsule> assetIssueCapsuleList =
          chainBaseManager.getAssetIssueV2Store().getAllAssetIssues();
      AssetIssueList.Builder builder = AssetIssueList.newBuilder();
      assetIssueCapsuleList
          .stream()
          .filter(assetIssueCapsule -> assetIssueCapsule.getName().equals(assetName))
          .forEach(
              issueCapsule -> {
                processor.updateUsage(issueCapsule);
                builder.addAssetIssue(issueCapsule.getInstance());
              });

      // check count
      if (builder.getAssetIssueCount() > 1) {
        throw new NonUniqueObjectException(
            "To get more than one asset, please use getAssetIssueById syntax");
      } else {
        // fetch from DB by assetName as id
        AssetIssueCapsule assetIssueCapsule =
            chainBaseManager.getAssetIssueV2Store().get(assetName.toByteArray());

        if (assetIssueCapsule != null) {
          processor.updateUsage(assetIssueCapsule);

          // check already fetch
          if (builder.getAssetIssueCount() > 0
              && builder.getAssetIssue(0).getId()
              .equals(assetIssueCapsule.getInstance().getId())) {
            return assetIssueCapsule.getInstance();
          }

          builder.addAssetIssue(assetIssueCapsule.getInstance());
          // check count
          if (builder.getAssetIssueCount() > 1) {
            throw new NonUniqueObjectException(
                "To get more than one asset, please use getAssetIssueById syntax");
          }
        }
      }

      if (builder.getAssetIssueCount() > 0) {
        return builder.getAssetIssue(0);
      } else {
        return null;
      }
    }
  }
