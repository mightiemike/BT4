### Title
Unbounded user-supplied `tip`/`max_price_per_unit` can overflow fee/gas-cost arithmetic and panic the sequencer during transaction validation - (File: crates/blockifier/src/transaction/objects.rs, crates/starknet_api/src/execution_resources.rs)

### Summary
The gateway's stateless validation only enforces a *lower* bound on `resource_bounds.l2_gas.max_price_per_unit` (`min_gas_price`) and no upper bound at all on `max_price_per_unit` for any resource, nor on `tip`. [1](#0-0) 
Meanwhile, several fee/gas-cost computation paths that run during transaction validation and execution use `unwrap_or_else(|| panic!(...))` on arithmetic that combines these attacker-supplied, effectively-unbounded values (`GasPrice`/`Fee` are `u128`), rather than returning a graceful error. [2](#0-1) 

### Finding Description
`GasVector::cost` computes `tipped_l2_gas_price = gas_prices.l2_gas_price + tip`, then multiplies each gas amount by its price and sums the results, panicking on any overflow instead of returning a `Result`: [3](#0-2) 

The `tip` field, and the `max_price_per_unit` for L1/L1-data/L2 gas, are attacker-controlled fields of a submitted V3 transaction. The gateway's `validate_resource_bounds` function only checks that the total possible fee is non-zero and that `l2_gas.max_price_per_unit` is not below `min_gas_price` — there is no upper-bound check on `tip` or on `max_price_per_unit` for any resource: [4](#0-3) 

Related panic-on-overflow arithmetic exists throughout the fee-computation code paths that are reached before/while validating a transaction, e.g. `to_l1_gas_for_fee` (adds discounted L1 gas and converted L2 gas, panicking on overflow) and `to_discounted_l1_gas` (multiplies/divides by `l1_data_gas_price`, panicking on overflow), both of which are invoked from `check_can_pay_fee` / `estimate_minimal_gas_vector` in the transaction pre-validation flow: [5](#0-4) [6](#0-5) [7](#0-6) 

These panics are deliberately used as "should never happen" invariant assertions elsewhere in the code (e.g. `get_fee_by_gas_vector`'s test explicitly demonstrates the overflow panic when a gas price near `2*u64::MAX` is supplied): [8](#0-7) 

But since `resource_bounds.max_price_per_unit` (a `GasPrice(u128)`) and `tip` are not upper-bounded by stateless validation, and the fee/pre-validation checks (`check_can_pay_fee`) read the resource-bounds values directly from the transaction before/while comparing them to the computed minimal gas vector, an attacker can submit a transaction whose `max_price_per_unit`/`tip` are large enough to overflow the arithmetic in `GasVector::cost`, `to_l1_gas_for_fee`, or `to_discounted_l1_gas`, triggering a Rust panic. If this panic occurs inside a `spawn_blocking` task used by the gateway's stateful validator (`run_validate_entry_point`) or in the mempool/blockifier during block-building, it can crash the worker thread (and potentially the process depending on panic-handling configuration), constituting a denial-of-service reachable from a single unprivileged, unauthenticated transaction submission — directly analogous to the referenced MariaDB CVE-2017-10378, where an unprivileged query triggers a crash/hang in the server via unchecked internal computation.

### Impact Explanation
A crash triggered from a single submitted transaction in the gateway's validation path or during block building denies service to legitimate transaction senders (a sequencer unable to confirm new transactions), meeting the "network unable to confirm new transactions" bar. Depending on Rust panic-unwind vs. abort configuration and whether the panic occurs in a `spawn_blocking` task (which would just fail that task, per `run_validate_entry_point`'s `JoinError` handling) versus an untrapped path in block-building/consensus, severity can range from a single transaction rejection to a sequencer-wide crash. This is uncertain without further verification of exact panic-catching boundaries at each call site (particularly outside the gateway, e.g. in block-building/mempool eviction paths that call the same fee-computation code without a `catch_unwind`/`spawn_blocking` boundary).

### Likelihood Explanation
The `tip` and `max_price_per_unit` fields are directly attacker-controlled with no upper bound enforced anywhere in the validated code path shown, making the precondition trivial to satisfy (submit resource bounds/tip near `u128::MAX`). Whether the arithmetic actually overflows in production depends on exact multiplication paths and whether they are gated behind other lower-level checks not fully explored in this pass (e.g., additional length/format validation on `resource_bounds` upstream, or a possible `u128`→`u64`-narrowing conversion that would instead fail gracefully with an error). This uncertainty should be resolved by tracing the full call chain from `RpcTransaction` deserialization through `check_can_pay_fee`/`GasVector::cost` with concrete maximal values.

### Recommendation
- Add explicit upper-bound validation on `tip` and on `max_price_per_unit` for all resources (L1 gas, L1 data gas, L2 gas) in `StatelessTransactionValidator::validate_resource_bounds`, symmetric to the existing `min_gas_price` check.
- Replace `panic!`-on-overflow in `GasVector::cost`, `to_l1_gas_for_fee`, and `to_discounted_l1_gas` with `checked_*` arithmetic that returns a `Result`/`TransactionFeeError` variant, so malformed/adversarial resource bounds are rejected as an ordinary validation error rather than causing a runtime panic.
- Audit all callers of these fee-vector helper functions (pre-validation, mempool, block-building, and Starknet OS re-execution paths) to ensure a panic here cannot escape a `catch_unwind`/`spawn_blocking` boundary and crash a sequencer worker or the whole process.

### Proof of Concept
Not independently executed; based on static analysis of the panic-on-overflow arithmetic and the confirmed absence of an upper bound on `max_price_per_unit`/`tip` in `stateless_transaction_validator.rs`. The existing unit test `test_get_fee_by_gas_vector_overflow` in `crates/blockifier/src/fee/fee_test.rs` (lines 354-386) already demonstrates the panic is reachable with a sufficiently large gas price value, confirming the underlying arithmetic is not overflow-safe; a full end-to-end PoC would require constructing an `RpcInvokeTransaction` (or Declare/DeployAccount) with `resource_bounds.max_price_per_unit` set to a large `u128` value (e.g. near `u128::MAX / small_amount`) and submitting it through the gateway to confirm whether the panic is reached before being intercepted by an unexplored intermediate check.

    /// Computes the cost (in fee token units) of the gas vector (panicking on overflow).
    pub fn cost(&self, gas_prices: &GasPriceVector, tip: Tip) -> Fee {
        let tipped_l2_gas_price =
            gas_prices.l2_gas_price.checked_add(tip.into()).unwrap_or_else(|| {
                panic!(
                    "Tip overflowed: addition of L2 gas price ({}) and tip ({}) resulted in \
                     overflow.",
                    gas_prices.l2_gas_price, tip
                )
            });

        let mut sum = Fee(0);
        for (gas, price, resource) in [
            (self.l1_gas, gas_prices.l1_gas_price, Resource::L1Gas),
            (self.l1_data_gas, gas_prices.l1_data_gas_price, Resource::L1DataGas),
            (self.l2_gas, tipped_l2_gas_price, Resource::L2Gas),
        ] {
            let cost = gas.checked_mul(price.get()).unwrap_or_else(|| {
                panic!(
                    "{resource} cost overflowed: multiplication of gas amount ({gas}) by price \
                     per unit ({price}) resulted in overflow."
                )
            });
            sum = sum.checked_add(cost).unwrap_or_else(|| {
                panic!(
                    "Total cost overflowed: addition of current sum ({sum}) and cost of \
                     {resource} ({cost}) resulted in overflow."
                )
            });
        }
        sum
    }

fn test_get_fee_by_gas_vector_overflow(
    #[case] l1_gas: u64,
    #[case] l1_data_gas: u64,
    #[case] l2_gas: u64,

    block_info.gas_prices = GasPrices {
        eth_gas_prices: GasPriceVector {
            l1_gas_price: huge_gas_price,
            l1_data_gas_price: huge_gas_price,
            l2_gas_price: huge_gas_price,
        },
        strk_gas_prices: GasPriceVector {
            l1_gas_price: huge_gas_price,
            l1_data_gas_price: huge_gas_price,
            l2_gas_price: huge_gas_price,
        },
    };
    let gas_vector =

        get_fee_by_gas_vector(&block_info, gas_vector, &FeeType::Eth, Tip::ZERO),

    );
