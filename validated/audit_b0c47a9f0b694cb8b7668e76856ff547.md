Confirmed: `next_durable_nonce()` (and `DurableNonce::from_blockhash(&last_hash)`) is derived from the bank's current `last_blockhash`, which is shared across the entire slot/cluster — every nonce account advanced in the same slot receives the identical `DurableNonce` value [1](#0-0) , and `advance_nonce_account` explicitly derives it from `invoke_context.environment_config.blockhash` [2](#0-1) . Durable nonces do not expire the way ordinary recent blockhashes do, which the code itself acknowledges: "unlike `clear_slot_entries()`, `purge_slots()` can't overlap with regular blockhashes since they'd have expired by the time roots are old enough to be purged. However, nonces don't expire, so they can overlap" [3](#0-2) .

### Title
Unbounded per-blockhash `KeyMap` growth via durable-nonce blockhash reuse across `add_root`/`purge_roots` cycles - (File: runtime/src/status_cache.rs)

### Summary
`StatusCache::insert` tracks only a single blockhash-level `max_slot` per cache bucket, and `purge_roots` decides whether to evict an *entire* blockhash bucket (and every stale key inside it) based solely on that `max_slot` compared to the root cutoff. An unprivileged user who periodically submits any transaction reusing a shared durable-nonce blockhash keeps `max_slot` artificially fresh, preventing eviction of the whole `KeyMap<T>` bucket while continuing to accumulate unboundedly many distinct-key entries whose own slots have long since been purged from `self.roots`.

### Finding Description
`StatusCache::insert` looks up (or creates) the cache entry for a blockhash and only updates the bucket-wide `max_slot`, never a per-key slot cutoff: [4](#0-3) 

`purge_roots` computes a cutoff from `self.roots` and retains cache buckets purely by comparing this single `max_slot` against the cutoff — the entire `KeyMap<T>` for a blockhash is kept or dropped as one unit, regardless of how old individual keys inside it are: [5](#0-4) 

Regular (non-nonce) transaction blockhashes cannot be exploited this way because `check_transaction_age` rejects a blockhash once it falls outside `BlockhashQueue`'s bounded age window [6](#0-5) , so such blockhash buckets naturally cannot keep receiving new inserts long after their `max_slot` is exceeded by the root cutoff — the code comment explicitly says regular blockhashes "would have expired by the time roots are old enough to be purged" [3](#0-2) .

Durable nonces are different: `check_nonce_transaction_validity`/`validate_transaction_nonce` accept a transaction whose `recent_blockhash` equals the value stored in *any* nonce account, and that value never becomes "too old" as long as the nonce account hasn't been re-advanced [7](#0-6) [8](#0-7) . Critically, `next_durable_nonce()`/`DurableNonce::from_blockhash` is derived from the bank's shared `last_hash`, so any number of distinct nonce accounts advanced in the same slot end up storing the identical durable-nonce hash value [1](#0-0) [2](#0-1) .

Exploit flow:
1. Attacker (unprivileged, self-funded) creates `N` nonce accounts and advances/initializes them all within the same slot, so they all hold identical `DurableNonce` value `DN1`.
2. Over time, the attacker periodically (roughly once per `MAX_ROOT_ENTRIES` slots) submits one nonce transaction using `DN1` as `recent_blockhash` (using any nonce account not yet advanced). Each successful transaction causes `Bank::update_transaction_statuses` to call `status_cache.insert(tx.recent_blockhash(), tx.message_hash(), self.slot(), ...)` [9](#0-8) , which bumps `max_slot` for bucket `DN1` to the current slot and adds one more distinct key to that bucket's `KeyMap`.
3. Because `max_slot` for `DN1` is refreshed by this cheap, low-frequency traffic, `purge_roots`'s check `*fork > cutoff` at [10](#0-9)  never evicts the bucket, so every previously inserted key (from long-purged root slots) in that `KeyMap` is retained indefinitely.
4. The attacker can insert an arbitrarily large number of distinct keys into this one never-purged bucket over the node's uptime — each insertion costs one transaction fee, but the *retention* of already-inserted stale entries costs the attacker nothing beyond the periodic "keep-alive" transaction, decoupling ongoing memory retention from ongoing fee payment.

### Impact Explanation
This is a disproportionate storage-cost issue: `KeyMap<T>` entries for the reused blockhash grow with the total historical count of distinct keys ever inserted under it, not bounded by `MAX_ROOT_ENTRIES`/`max_root_entries`, and old entries persist even after their originating root slot has been purged from `self.roots`. Over a long enough operating window this produces unbounded heap growth inside `StatusCache::cache`, held under `Bank::status_cache` and serialized into every snapshot's `slot_deltas`/`root_slot_deltas` via `append`/`root_slot_deltas` [11](#0-10) . This matches a "disproportionate storage and CPU cost" resource-exhaustion category rather than a direct consensus or fund-safety bug — it is a memory/performance degradation issue, not a balance-forgery or hash-divergence bug.

### Likelihood Explanation
Feasibility requires: (a) creating and rent-funding `N` nonce accounts (attacker-controlled, low cost per account), (b) advancing them within a common slot (achievable by submitting many `advance_nonce_account` transactions in one block, or via repeated attempts across blocks since it only requires *some* slot where several nonce accounts share the same advance blockhash — actually since `next_durable_nonce` is the same for the whole slot, any nonce accounts advanced in that slot converge automatically), and (c) submitting one cheap "keep-alive" transaction roughly every `MAX_ROOT_ENTRIES` slots. This is entirely within a single unprivileged user's capability with no special access, and is confirmed as a known, intentional design gap by the existing code comment about nonces not expiring and being able to "overlap" purged roots [3](#0-2) , plus the `do_test_shuttle_purge_nonce_overlap` test that specifically exercises this exact overlap scenario [12](#0-11) .

### Recommendation
Track per-key insertion slots for pruning purposes instead of relying solely on the blockhash-bucket `max_slot`, or bound the number of live keys retained per blockhash bucket (e.g., cap `KeyMap` size per blockhash and evict oldest `ForkStatus` entries), or force nonce-account cache entries to be evicted based on the *individual* key's own recorded slot vs. root cutoff rather than the bucket-wide `max_slot`. Any fix should preserve correctness of `AlreadyProcessed` replay-protection for nonce transactions while bounding worst-case memory to be proportional to `max_root_entries` and actual live nonce accounts, not to lifetime transaction count.

```rust
fn test_reused_blockhash_keymap_unbounded_growth() {
    let mut status_cache = BankStatusCache::default();
    let shared_nonce_blockhash = Hash::new_unique(); // simulates one slot's shared DurableNonce
    let max_root_entries = status_cache.max_root_entries() as u64;

    let mut slot: u64 = 0;
    // simulate periodic "keep-alive" nonce txs across many more slots than max_root_entries,
    // each with a distinct key (as would happen with distinct nonce-advance message hashes)
    for i in 0..(max_root_entries * 50) {
        let key = Hash::new_unique();
        status_cache.insert(&shared_nonce_blockhash, key, slot, ());
        slot += 1;
        status_cache.add_root(slot); // refresh roots/cutoff every insert, mimicking real cadence
    }

    // Bucket should have been evicted/bounded like any other stale blockhash, but isn't:
    let (max_slot, _, key_map) = status_cache
        .cache
        .get(&shared_nonce_blockhash)
        .expect("bucket should still exist because it was kept 'fresh'");
    assert!(*max_slot > slot - max_root_entries);
    // Assert the bug: key_map size grows with total historical inserts (50x max_root_entries),
    // not bounded by max_root_entries as the invariant requires.
    assert!(
        key_map.len() as u64 > max_root_entries,
        "expected bounded KeyMap size <= {}, got {} (unbounded growth)",
        max_root_entries,
        key_map.len()
    );
}
```
Expected result on current code: the assertion demonstrating `key_map.len()` exceeding `max_root_entries` passes, confirming unbounded growth for a single reused blockhash bucket, whereas a correctly bounded cache should keep `key_map.len()` proportional to `max_root_entries` (or to genuinely live nonce accounts), not to the full historical insert count.

```rust
        // the transaction. This is the same as if it was used in different batches in the same slot.
        // It is possible that the nonce account was used, closed, closed and reopened, closed and
```
