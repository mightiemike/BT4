### Title
Missing duplicate check in `KVSessionStorage.addShopIds` causes unbounded shop-session-id list growth — ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage.storeSession` unconditionally appends the session id to the shop's session-id index on every call, with no check for whether that id is already present. Because `storeSession` is invoked on every OAuth/token-exchange completion or refresh — and the offline/online session id is deterministic per shop (and per shop+user) — a merchant simply re-authenticating or the app's normal online-token refresh cycle will keep appending the same id to the list repeatedly, growing it without bound and corrupting `findSessionsByShop` results.

### Finding Description
`storeSession` calls `addShopIds(session.shop, [session.id])` on every store, and `addShopIds` does: [1](#0-0) [2](#0-1) 

It reads the existing `shopIds` array and blindly concatenates the new id(s) with no `includes()`/dedup check, then writes the array back. This is exactly the same root-cause pattern as the reference report: an "add" operation that should be idempotent for a given key/id instead unconditionally appends/overwrites shared accounting state (here, the shop→session-ids index) every time it's invoked.

This is confirmed to be an oversight specific to this adapter, since the sibling `RedisSessionStorage.addKeyToShopList` implements the same feature correctly, explicitly guarding against duplicates: [3](#0-2) 

Since `session.id` is deterministic (`offline_${shop}` for offline sessions, `${shop}_${userId}` for online/JWT sessions via `getOfflineId`/`getJwtSessionId`), any repeated `storeSession` call for the same shop/user (which happens on every OAuth re-auth, every token-exchange refresh near expiry, or an app reinstall) re-adds the identical id to the array instead of being a no-op. [4](#0-3) 

`findSessionsByShop` then loads and returns one `Session` per entry in that (now duplicated) array: [5](#0-4) 

### Impact Explanation
- **Corrupted accounting/results**: Any app logic that iterates `findSessionsByShop` (e.g. batch webhook processing, billing checks, per-shop maintenance jobs) will process the same session multiple times, duplicating side effects (duplicate webhook registrations, duplicate GraphQL mutations, duplicate emails, etc.) for a single merchant/session — directly analogous to the incentive system's corrupted accounting from repeated index pushes.
- **Denial of service on session storage**: Because token-exchange access tokens are periodically refreshed automatically by the library (`performTokenExchange` re-stores the offline/online session whenever it is near expiry), the shop-id array grows without bound over the life of an installation. Cloudflare KV values have hard size limits; once the JSON-encoded array for a shop exceeds that limit, `namespace.put`/`get` for that shop's index will start failing, breaking `storeSession`/`findSessionsByShop` for that shop — a DoS of the session-storage layer triggerable purely by the normal, unprivileged operation of the merchant's own installed app over time (no attacker privilege escalation required).
- This is reachable by any single merchant's normal usage of the app (repeated authorization/browser sessions, or simply time passing while online tokens refresh), matching the "single merchant" unprivileged-actor requirement.

### Likelihood Explanation
High for corrupted/duplicated array entries — it occurs on every `storeSession` call for a shop/session id that has been stored before, which is a normal, frequent occurrence (token refresh, reinstall, multiple online sessions). The full DoS from unbounded growth requires more elapsed time/refresh cycles but is a direct, deterministic consequence of the missing check, not a probabilistic condition.

### Recommendation
Match the pattern already used in `RedisSessionStorage.addKeyToShopList`: check whether the id is already present before appending, and similarly ensure `deleteSession`/`removeShopIds` remain reachable to purge duplicates already present:

```diff
 private async addShopIds(shop: string, ids: string[]) {
   const key = this.getShopSessionIdsKey(shop);
   const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
-  await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
+  const merged = new Set(shopIds);
+  for (const id of ids) merged.add(id);
+  await this.namespace.put(key, JSON.stringify([...merged]));
 }
```

### Proof of Concept
1. Configure an app using `KVSessionStorage` for offline session storage.
2. Complete OAuth for a shop, producing session id `offline_<shop>` and calling `storeSession`.
3. Simulate the library's automatic token-exchange refresh (or simply have the merchant re-run `/auth`) so `storeSession` is invoked again with the same session id.
4. Call `findSessionsByShop(shop)` — observe it returns N duplicate `Session` objects for the same session id after N `storeSession` calls, instead of exactly one, and the underlying KV value for the shop key grows linearly with the number of re-auth/refresh events.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
