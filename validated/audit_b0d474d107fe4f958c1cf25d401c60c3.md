## Title
Replay-verify skips state/hot-state/position checkpoint hash comparison, allowing an undetected state-root divergence between committed ledger and local execution - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by the chunk-executor's replay-verify path (and by `db-tool`/debugger verification tooling) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` on the ledger, checks status, gas, write-set hash, and event root hash — but explicitly does **not** check the state-checkpoint hash, hot-state checkpoint hash, or the native-position checkpoint hash. The code itself documents this gap in a `TODO(trading-native)` comment. As a result, any divergence between the locally computed state-checkpoint/hot-state/position state root and the one actually committed to `TransactionInfoV1` on-chain will not be flagged as a verification failure by this comparator.

## Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It verifies status, gas used, write-set hash (`state_change_hash`) and event root hash against the `TransactionInfo`, but the function's own trailing comment states:

"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution. Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS." [2](#0-1) 

This comparator is invoked from `ChunkExecutorInner::verify_execution`, the chunk-executor's replay/verify entry point that re-executes a range of transactions against locally maintained state and checks the result against the persisted `TransactionInfo`s and write sets pulled from storage/backup: [3](#0-2) . It is also referenced from `aptos-debugger`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs`, i.e., the primary tools used to detect execution/consensus divergence against real chain data.

`TransactionInfoV1` carries the state-checkpoint hash, an optional hot-state checkpoint hash, and (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) a `position_state_checkpoint_hash` that is consensus-verified as part of the authenticated ledger commitment, computed in `DoStateCheckpoint::run` [4](#0-3) . `BlockExecutorConfigFromOnchain::with_features` shows that `compute_trading_native_state_roots` is a live, feature-gated on-chain flag [5](#0-4) , meaning the position-state root is an authenticated, consensus-committed value once the feature is on.

Because `ensure_match_transaction_info` never compares these checkpoint hash fields, replay-verify (and any other caller relying on this function to detect execution divergence) will silently accept a `TransactionOutput` whose resulting state-checkpoint/hot-state/position state root differs from the one actually committed on the authenticated ledger.

## Impact Explanation
This breaks the "committed state that differs from the correct VM result... must not go undetected" integrity invariant for the state-checkpoint, hot-state, and native-position roots. In particular:
- Once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, a bug (or malicious construction) that causes the native-position (or hot-state) tree root committed on-chain to diverge from what honest execution would produce cannot be caught by replay-verify tooling, because the very function meant to detect such divergence ignores these fields.
- This directly undermines the primary safety net (replay-verify / `db-tool replay_on_archive`) used to catch hard-fork-causing divergence in committed ledger state, silently masking an integrity failure rather than causing loud, visible failure.
- Given that these checkpoint roots are consensus-committed values (part of `TransactionInfoV1`, itself accumulator-committed and signed by validators), an unnoticed divergence here means downstream consumers of position/hot-state proofs could be trusting a root that does not actually match honest execution, without any tooling raising an alarm.

## Likelihood Explanation
The gap is unconditional whenever `ensure_match_transaction_info` is invoked (every chunk-executor `verify_execution` call and every `db-tool replay_on_archive`/debugger verify invocation), and becomes concretely exploitable/impactful once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and `HOT_STATE_ROOT_IN_TXN_INFO`) feature flags are enabled on-chain, which the code base explicitly anticipates ("before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"). The bug is self-documented by the authors as a known, currently-open gap, i.e., it's not a hypothetical construction but a code-verified missing invariant.

## Recommendation
Extend `ensure_match_transaction_info` to also compare `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, and (when applicable) `position_state_checkpoint_hash()` against locally computed equivalents before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet, exactly as the existing TODO comment recommends.

## Proof of Concept
1. Enable (or simulate a future state where) `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is on, so `TransactionInfoV1.position_state_checkpoint_hash` is a real, consensus-verified field.
2. Construct/replay a chunk of transactions whose write set and event hashes match the persisted `TransactionInfo` (so `write_set_hash`/`event_root_hash`/gas/status all match), but whose native-position tree ends up with a different root than the one recorded on-chain (e.g., due to a local execution bug, or a backup/archive with tampered position-tree state that is internally consistent with the write set but not with the "real" position root).
3. Run `ChunkExecutorInner::verify_execution` (or `db-tool replay_on_archive`) over this chunk: [6](#0-5)  calls `ensure_match_transaction_info`, which — per [7](#0-6)  — never inspects the checkpoint hash fields.
4. Observe that verification reports success even though the position/hot-state checkpoint root diverges from what honest execution would produce, confirming the tooling fails to detect the state-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
