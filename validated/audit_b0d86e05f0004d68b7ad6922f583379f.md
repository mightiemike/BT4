### Title
SR quorum check in `validPbftSign` counts distinct signature byte blobs instead of distinct signer addresses, allowing malleable-signature duplication to fake quorum - ([File: framework/src/main/java/org/tron/core/net/messagehandler/PbftDataSyncHandler.java])

### Finding Description
`validPbftSign` builds `srSignSet` as a `Set<ByteString>` populated directly from the raw signature bytes received in `srSignList`, then compares `srSignSet.size()` against `Param.getInstance().getAgreeNodeCount()` to enforce the 2/3+1 SR quorum: [1](#0-0) 

Deduplication here is performed on the **raw signature byte content** (`ByteString` equality), not on the **recovered SR address**. Each signature is only mapped to an address inside `ValidPbftSignTask.call()`, which recovers `srAddress` via `ECKey.signatureToAddress` and checks membership in `srSet` (the current witness list), but never accumulates or checks the *set of distinct addresses* recovered — it only removes the matching byte-string entry from `srSignSet` and returns `true`/`false` per-signature: [2](#0-1) 

The final consistency check (`srSignSet.size() != 0`) only verifies that every distinct byte-string in the set was successfully validated against some SR address — it does not verify that the addresses recovered are pairwise distinct: [3](#0-2) 

ECDSA/secp256k1 signatures used by `ECKey` are malleable: for any valid `(r, s, v)` signature over a message, `(r, n-s, v XOR 1)` is also a valid signature recoverable to the *same* address, and can be computed by anyone from a captured signature without the private key. Because the quorum check operates on distinct signature bytes rather than distinct recovered addresses, an attacker who observes/relays valid PBFT commit signatures from fewer than `agreeNodeCount` real SRs can algebraically derive malleable twins of each captured signature and inject them into `srSignList`. This doubles the number of distinct `ByteString` entries in `srSignSet` without adding any new real signer, potentially pushing `srSignSet.size()` at or above `agreeNodeCount` while the number of distinct SR addresses backing the commit remains below the required 2/3+1 threshold.

### Impact Explanation
If exploited, `processPBFTCommitMessage` would accept and persist (`pbftSignDataStore.putBlockSignData` / `putSrSignData`) a PBFT commit result for a block or SR list as if it had reached the legitimate 2/3+1 SR quorum, when in fact fewer distinct SRs actually signed it. This weakens the light-client/PBFT sync trust assumption enforced by this store, potentially enabling acceptance of an under-quorum block/SRL commit into local PBFT state.

### Likelihood Explanation
Requires the attacker to be a network participant capable of receiving/relaying `PbftCommitMessage`s (unprivileged P2P peer) and to have captured at least `ceil(agreeNodeCount/2)` genuine valid SR signatures for a given `Raw` payload — a realistic scenario during normal gossip since these commit messages are broadcast over the network per `processMessage`. Producing malleable twins is a pure arithmetic operation on public signature values, requiring no key material, making this practically feasible whenever the attacker can gather signatures from slightly less than a full quorum of real signers.

### Recommendation
Change the quorum/dedup logic to operate on recovered SR addresses rather than raw signature bytes: recover the address for every signature first, insert addresses (not signature `ByteString`s) into the set used for the size/threshold check, and reject signatures whose recovered address is already present in that set (to prevent a malleable duplicate of the same signer's signature from being counted twice). Additionally, enforce canonical (low-s) signature form when validating PBFT sign payloads to eliminate the malleability itself.

### Proof of Concept
Java unit test plan (JUnit) for `PbftDataSyncHandlerTest`:
1. Generate `M` `ECKey` pairs (`M < agreeNodeCount`), configure them as `currentSrList`/`srSet`.
2. Build a `Raw` payload; compute `dataHash = Sha256Hash.hash(true, raw.toByteArray())`.
3. For each of the `M` keys, sign `dataHash` to get a canonical `ECDSASignature(r, s, v)`.
4. For each signature, derive the malleable twin: `s' = CURVE.getN().subtract(s)`, `v' = v == 27 ? 28 : 27`; serialize both original and twin to the wire `ByteString` format expected by `srSignList`.
5. Build `srSignList` containing all `2M` byte strings (originals + twins), where `2M >= agreeNodeCount` but `M < agreeNodeCount`.
6. Call `validPbftSign(raw, srSignList, currentSrList)` via reflection (private method) or through `processPBFTCommitMessage`.
7. Assert current behavior: method returns `true` (quorum incorrectly satisfied) — demonstrating the bug.
8. After applying the fix (dedup by recovered address), assert `validPbftSign` returns `false` since only `M` distinct addresses signed, which is `< agreeNodeCount`.
