### Title
Stale per-block `index-cache` in `market.clar` is not invalidated when `socialize-debt` rewrites a vault's `lindex`, letting zToken collateral be overvalued within the same block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches vault accrual results (`index`, `lindex`) in the `index-cache` map, keyed only by `{ timestamp: stacks-block-time, aid }`, and reuses that cached value for the remainder of the block instead of re-querying the vault. `socialize-debt` on the vault contracts writes down `lindex` directly via `var-set`, completely outside the `accrue`/`accrue-and-cache` path that populates this cache. If `socialize-debt` executes after the cache for that `aid`/block has already been populated, every subsequent zToken price resolution in the same block (`resolve-ztoken`) keeps returning the pre-write-down `lindex`, overvaluing the zToken collateral for health checks and liquidation math for the rest of that block.

### Finding Description
The cache is defined and read/written as:
```
(define-map index-cache
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)                 ;; cache HIT: stale reuse
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [1](#0-0) 

zToken price resolution reads exactly this cache instead of the vault's live state:
```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
``` [2](#0-1) 

Meanwhile, the vault's `socialize-debt` mutates `lindex` directly to write down value lost to bad debt, independent of `accrue`:
```
(define-public (socialize-debt (scaled-amount uint))
  (let ((...)
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
    (try! (check-caller-auth))
    ...
``` [3](#0-2) 

`socialize-debt` is routed from the market via `vault-socialize-debt`, a plain private dispatcher with no interaction with `index-cache`:
```
(define-private (vault-socialize-debt (aid uint) (amount uint))
  (if (is-eq aid STX) (contract-call? .v0-vault-stx socialize-debt amount)
  ...
``` [4](#0-3) 

Because `index-cache` keys only on `{ stacks-block-time, aid }`, once any call within a block has populated the cache for a given `aid` (e.g. via a normal `accrue-and-cache` call for pricing/health-check purposes), a later call in the *same block* that invokes `socialize-debt` on that vault changes the vault's real `lindex` but leaves the cached entry untouched. Any further `resolve-ztoken` call for that `aid` in the same block (subsequent transaction in the same block, or later in the same transaction if socialize-debt and health-check are combined in one liquidation call) returns the old, higher `lindex`, i.e. the zToken is priced richer than its true post-write-down value.

### Impact Explanation
Overvaluing zToken collateral due to the stale cache means:
- A borrower whose zToken-backed position should be classified unhealthy and liquidatable (because collateral backing was already partially socialized/written down) can continue to appear healthy for the remainder of the block, blocking timely liquidation.
- Health/LTV calculations and any new borrows against that zToken in the same block use inflated collateral value, allowing new debt to be issued against value that no longer exists.

This produces temporary freezing of the ability to liquidate under-collateralized debt and can allow new under-collateralized borrowing, both of which contribute to protocol insolvency risk if bad debt continues to accrue unchecked during that window.

### Likelihood Explanation
This requires only a normal sequence of protocol operations within a single block/transaction context: a vault suffering socialized bad debt (a designed, reachable code path) combined with a price/health check for the same asset earlier in the same block. No privileged access or DAO compromise is needed; both `accrue`-driven pricing and `socialize-debt` are part of ordinary market operation. Likelihood is conditioned on socialize-debt being triggered and a same-block price read occurring afterward, so it is not guaranteed on every block but is fully within reach during stress/liquidation cascades - the scenario where this cache staleness matters most.

### Recommendation
Invalidate or bypass the `index-cache` entry whenever a vault's `lindex`/`index` changes outside the normal `accrue` path (i.e., inside `socialize-debt`), for example by having `socialize-debt` also call back into the market to `map-delete` (or `map-set` with fresh values) the corresponding `index-cache` entry for that block, or by removing the cache's reliance on `stacks-block-time` alone and instead validating the cached value against the vault's authoritative state before use in `resolve-ztoken`.

### Proof of Concept
1. Within block `T`, a vault (e.g. `v0-vault-stx`) is holding zSTX collateral for several borrowers.
2. Market performs a health check / liquidation preview for account A, calling `accrue-and-cache(STX)` -> caches `{timestamp: T, aid: STX} -> {index, lindex: L1}` and prices A's zSTX collateral using `L1`. [1](#0-0) 
3. Still within block `T`, a bad-debt event on the same vault triggers `vault-socialize-debt(STX, amount)` -> `v0-vault-stx.socialize-debt` writes `lindex` down to `L2 < L1` via direct `var-set`, bypassing `accrue-and-cache`. [3](#0-2) 
4. Later in block `T` (subsequent transaction, or same liquidation flow if it batches multiple accounts), the market checks account B's health, again resolving zSTX price via `resolve-ztoken` -> `get-cached-indexes(STX)` returns the stale cached `{lindex: L1}` instead of the true `L2`. [2](#0-1) 
5. Account B's zSTX collateral is valued using `L1` (too high), so B's position is judged healthier than it actually is, preventing a legitimate liquidation or permitting further borrowing against overstated collateral for the rest of block `T`.
