### Title
Authorization/extra-header leak on same-host cross-port (and cross-scheme) redirect in AwURLLoaderThrottle - (File: android_webview/browser/network_service/aw_url_loader_throttle.cc)

### Summary
`AwURLLoaderThrottle` decides whether to strip embedder-injected extra headers (which may include `Authorization`, session tokens, etc., set via the WebView `setExtraHeadersForUrl`/`loadUrl(extraHeaders)` API) on redirect using `net::registry_controlled_domains::SameDomainOrHost()`. This function only compares hostnames and completely ignores the URL scheme and port, so a same-host redirect from `https://example.com:443` to `http://example.com:8080` (or any other port/scheme combination on the same registrable host) is treated as "same domain," and the sensitive headers are retained and forwarded to the new origin.

### Finding Description
`AwURLLoaderThrottle::WillStartRequest` records `original_origin_` and injects extra headers (potentially `Authorization`) via `AddExtraHeadersIfNeeded` [3](#0-2) . On redirect, `WillRedirectRequest` only removes the added headers when `SameDomainOrHost` returns false [1](#0-0) . `SameDomainOrHost` is implemented purely in terms of `host1`/`host2` string/eTLD+1 comparison — no scheme, no port [2](#0-1) . This is structurally identical to the reported Mechanize bug: an origin/security boundary check that omits port (and here also scheme) as part of the same-site decision that gates credential/header forwarding across a server-controlled redirect.

Because the URL is entirely attacker/server-controlled at redirect time (an HTTP 30x `Location` response from the network), a compromised or malicious server for `example.com` (or one that can be man-in-the-middled at the network layer... though we exclude MITM per scope) can redirect same-host traffic to a different port serving attacker content — e.g., a non-privileged port an attacker controls on shared or multi-tenant hosting, or a different service co-located on the same host — and receive the `Authorization` header intended for the original endpoint. The plaintext (`http`) case is also not excluded, so a redirect from `https://example.com` to `http://example.com` on a different port would leak the header over an unencrypted channel as well.

### Impact Explanation
This causes cross-port/cross-scheme disclosure of the `Authorization` header (and any other embedder-configured sensitive extra header) to a destination that is not actually the same authorization boundary as intended by the app embedding WebView, matching CWE-200/CWE-522 (information exposure of sensitive header/credential material), consistent with CVSS Medium severity of the analog (confidentiality impact, no integrity/availability impact).

### Likelihood Explanation
Reachable purely via a standard HTTP redirect response (`Location` header) from remote content the WebView loads with app-configured extra headers — no special flags, extensions, or local access required. It requires the app to have used WebView's extra-headers API for a URL containing sensitive tokens and to be interacting with a page that can trigger a redirect to a different port/scheme on the same host (e.g., a compromised/malicious CDN edge, shared-hosting neighbor, or an open redirect on the same host to a listener on another port).

### Recommendation
Change the same-site check gating header removal in `AwURLLoaderThrottle::WillRedirectRequest` to require full origin equality (scheme + host + port), e.g. compare `url::Origin::Create(redirect_info->new_url)` against `original_origin_` directly rather than `SameDomainOrHost`, so that any change of port or scheme forces the added headers to be stripped, matching the mechanize fix's tightened port-aware redirect check.

### Proof of Concept
1. In an embedding app, call the WebView navigation API with extra headers including `Authorization: <secret>` for `https://example.com/start`.
2. Have the server at `https://example.com/start` respond with `302 Found` and `Location: https://example.com:9443/attacker` (or `http://example.com:8080/attacker`), where port 9443/8080 is controlled by the attacker (e.g., a different tenant/service on the same shared host).
3. Observe in `AwURLLoaderThrottle::WillRedirectRequest` that `SameDomainOrHost(redirect_info->new_url, original_origin_, ...)` returns `true` because only hostnames are compared, so `added_headers_` is not added to `removed_headers`, and the `Authorization` header is sent to the attacker-controlled port.

bool SameDomainOrHost(std::string_view host1,
                      std::string_view host2,
                      PrivateRegistryFilter filter) {
  // Quickly reject cases where either host is empty.
  if (host1.empty() || host2.empty()) {
    return false;
  }

  // Check for exact host matches, which is faster than looking up the domain
  // and registry.
  if (host1 == host2) {
    return true;
  }

  // Check for a domain and registry match.
  std::string_view domain1 = GetDomainAndRegistryAsStringPiece(host1, filter);
  return !domain1.empty() &&
         (domain1 == GetDomainAndRegistryAsStringPiece(host2, filter));
}
