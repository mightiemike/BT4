### Title
Starknet OS `replace_class` syscall handler omits the "class must be declared" check enforced by Blockifier - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The external report's bug class is "an update function accepts new state without validating it against required invariants of the prior/expected state." The closest reachable analog in this sequencer is the `replace_class` syscall: Blockifier (the execution engine that actually processes transactions on sequencer/full nodes) enforces that a contract can only be redirected to a class hash that has actually been declared (and rejects V1→V0 downgrades), while the Starknet OS's own Cairo implementation of the same syscall — which independently re-executes contract code for proof generation / state commitment — updates `contract_state_changes` unconditionally, with an explicit TODO acknowledging the missing check.

### Finding Description
Blockifier's `replace_class` syscall handling reads the compiled class before updating the class hash, causing failure if the class is undeclared: [1](#0-0) 

This is confirmed by dedicated tests that assert both an "is not declared" failure for undeclared classes and a Cairo0/Cairo1 compatibility check ("Cannot replace V1 class hash with V0 class hash") for the non-deprecated syscall path: [2](#0-1) 

In contrast, the Starknet OS's Cairo implementation of the same syscall (`execute_replace_class`, used by the Cairo program that is executed/proved for block state-transition verification) performs no such check — it directly writes the requested `class_hash` into `contract_state_changes`, with the missing validation explicitly flagged by the maintainers themselves: [3](#0-2) 

The same gap exists in the deprecated (Cairo0) syscall path of the OS program: [4](#0-3) 

This mirrors the reported bug class precisely: a state-mutating entry point (`updateProposal` in the original report, `execute_replace_class` here) accepts a caller-supplied new value and commits it to persistent state without validating it against the invariant that governs legitimate state transitions (in this case, "the target class must be declared"), where an equivalent, stricter check already exists in a parallel/authoritative code path (Blockifier).

### Impact Explanation
The Starknet OS's Cairo implementation is the specification that gets executed inside the STARK-provable program used to attest to a block's state transition (state commitment / root computation) and is intended to independently re-derive and validate the same semantics Blockifier enforces during normal sequencer execution. If the OS's own syscall semantics are looser than Blockifier's (missing the "declared class" and "no V1→V0 downgrade" checks), a state transition that Blockifier would reject/revert can be treated as valid by the OS. This falls under the accepted impact categories of "wrong committed root" and "honest-node divergence," since two supposedly-equivalent execution engines that must agree bit-for-bit on the resulting state diff can disagree specifically on this syscall's outcome.

### Likelihood Explanation
This is a concrete, currently-existing gap in the codebase (marked with an explicit `TODO(Yoni, 1/1/2026)` comment acknowledging the check is missing), not a hypothetical construction. It is reachable directly from an ordinary Cairo1 contract simply invoking the `replace_class_syscall` with an arbitrary class hash — no special privileges, node compromise, or malicious operator/proposer behavior is required to trigger the divergent code path in the OS program itself. The remaining uncertainty is whether the actual production STARK-proving pipeline always feeds the OS a pre-validated trace originating from Blockifier's own successful execution (in which case the undeclared-class scenario would never physically arise during honest re-proving) or whether the OS's Cairo interpreter independently re-executes the contract bytecode from scratch reaching this code path with attacker-influenced inputs. I could not fully verify this pipeline detail with the available tools within the iteration budget — this is a limitation of my analysis, not a claim that the divergence is provably exploitable end-to-end.

### Recommendation
Add the same validation performed by Blockifier to `execute_replace_class` in both `crates/apollo_starknet_os_program/.../syscall_impls.cairo` and `.../deprecated_execute_syscalls.cairo`: verify a compiled class exists for the requested `class_hash` (mirroring `get_compiled_class`/`get_contract_class` checks) and enforce the same Cairo0/Cairo1 compatibility constraint before committing the state update, closing the parity gap between Blockifier and the Starknet OS for this syscall.

// Replaces the class.
func execute_replace_class{
    range_check_ptr,
    syscall_ptr: felt*,
    contract_state_changes: DictAccess*,
    revert_log: RevertLogEntry*,
}(contract_address: felt) {
    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, ReplaceClassRequest*);

    // Reduce gas.
    let success = reduce_syscall_gas_and_write_response_header(
        total_gas_cost=REPLACE_CLASS_GAS_COST, request_struct_size=ReplaceClassRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );

    assert [revert_log] = RevertLogEntry(selector=CHANGE_CLASS_ENTRY, value=state_entry.class_hash);
    let revert_log = &revert_log[1];

    return ();
}
