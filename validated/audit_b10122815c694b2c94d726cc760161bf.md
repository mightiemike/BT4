### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify tooling accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is the shared invariant check used by offline state-integrity tools (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain. The function checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the resulting Jellyfish-Merkle state root. This is acknowledged in-code with a `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` compares only four properties between a computed `TransactionOutput` and the trusted `TransactionInfo` pulled from an accumulator-proven ledger: [1](#0-0) 

It stops short of validating the state/hot-state/position checkpoint hashes, with the gap called out directly in the source: [2](#0-1) 

`state_checkpoint_hash` is the field that binds a `TransactionInfo` to the actual resulting global state (the JMT root after applying the write set), separately from `state_change_hash` (which only hashes the write set contents, not the derived tree). Because `write_set_hash` equality does not imply `state_checkpoint_hash` equality — the state root also depends on the pre-existing state tree, sharding/versioning of unrelated keys, and the state-summary/merklization logic in `execution/executor/src/workflow/do_state_checkpoint.rs` — a bug in state-tree construction, sharded JMT updates, or state-summary composition could produce an identical write set but a different Merkle root without `ensure_match_transaction_info` ever detecting it.

This comparator is consumed by the state-integrity verification entry point `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which is exactly the tool meant to catch divergence between locally executed results and the trusted/archived ledger: [3](#0-2) 

The same comparator is reused by `aptos-move/cli/src/commands.rs` (transaction replay) and `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches`, both of which are used to sanity-check re-executed transaction results against the authenticated on-chain record. None of these call sites pass the state checkpoint hashes for comparison, so all three tools inherit the same blind spot.

### Impact Explanation
If a bug elsewhere in the storage/state-summary path (e.g., in `DoStateCheckpoint::run`/`get_state_checkpoint_hashes` in `execution/executor/src/workflow/do_state_checkpoint.rs`, or in sharded-JMT computation) produced a state root that diverges from the correct one while still producing the same write set, this verification path would report success (`Ok(())`), masking the divergence. Since `replay_on_archive` is the tool operators/auditors rely on to detect state-integrity regressions against historical, accumulator-proven data, a corrupted or hard-fork-diverging state root would go undetected by this specific tool — directly matching the "Wrong ... state proof accepted as valid" and "Authenticated API... output bound to the wrong version/object/proof" impact categories in scope.

However, this is **not** a consensus-path vulnerability: `ensure_match_transaction_info` is not used by the live block-execution/commit path, and it is not the mechanism that authenticates ledger state during normal sync (i.e., it does not itself let a malicious peer forge accepted state — the accumulator proof over `TransactionInfo` objects is still what nodes trust). Its impact is confined to weakening a debugging/verification utility's ability to *detect* state divergence, which is valuable for catching a hard-fork-class bug but is not itself an attacker-triggerable state corruption. This limits the severity below a full state-commitment break; it is best characterized as a Medium-severity integrity-verification gap (an authenticated verification aid that silently under-checks a proof-bound field), not a mainnet consensus-safety bug.

### Likelihood Explanation
The gap is deterministic and always present (not an edge case) whenever `ensure_match_transaction_info` is invoked without also independently comparing the state/hot-state/position checkpoint hashes, which is the case in every current call site. It would only manifest as a real-world problem in conjunction with a second, independent bug that causes state-root divergence, so exploitability is contingent on such a divergence existing; the code author's own comment confirms this is a known, intentional TODO rather than a novel exploitable primitive, and it's already gated ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`").

### Recommendation
Extend `ensure_match_transaction_info` (and its three call sites) to also compare `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present) against independently computed values, so that `replay_on_archive`, the CLI replay tool, and `aptos-debugger` can actually detect state-root divergence rather than only write-set/event/gas/status divergence. This should be completed before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as the in-code TODO already recommends.

### Proof of Concept
Not applicable as a directly triggerable exploit — this is a verification-logic gap, not an externally triggerable state-corruption primitive. Demonstrating real impact requires a second bug that causes the computed state checkpoint hash to diverge from the correct one while leaving the write set/events/gas/status unchanged; `ensure_match_transaction_info`'s current implementation (`types/src/transaction/mod.rs:2139-2204`) would then return `Ok(())` in `replay_on_archive::execute_and_verify` despite the divergence, which can be confirmed by unit-testing `ensure_match_transaction_info` with a `TransactionOutput`/`TransactionInfo` pair that share write-set/event/gas/status but differ only in `state_checkpoint_hash`.
