### Title
Unbounded growth of per-shop session-ID list in `KVSessionStorage`/`RedisSessionStorage` can permanently break session storage for a shop - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` unconditionally appends every new session id to a single serialized array stored under the key `shop:<shop>` via `addShopIds`, with no deduplication and no upper bound. Because a normal legitimate action — completing OAuth (installing the app, reinstalling, refreshing an offline token, or creating a new online session) — calls `storeSession` every time, a single merchant can repeatedly trigger the OAuth begin/callback flow to make this per-shop value grow without limit, eventually breaking `storeSession`/`findSessionsByShop` for that shop once the value exceeds the backing store's size limits.

### Finding Description
`KVSessionStorage.storeSession` stores the session, then calls `addShopIds`: [1](#0-0) 

`addShopIds` reads the existing array under `shop:<shop>` and blindly appends the incoming id(s), with no check for duplicates and no cap on array length: [2](#0-1) 

Every OAuth completion (`shopify.auth.callback`) calls `createSession` and eventually `SessionStorage.storeSession` for that shop: [3](#0-2) 

Since KV's `addShopIds` has no deduplication, even repeatedly re-authorizing the same offline session id (a routine, legitimate action — reinstall, token refresh, re-consent) appends a new duplicate entry to the `shop:<shop>` array on every call, without ever shrinking it (only `deleteSession` prunes ids, and only for ids actually removed). This mirrors the root cause pattern in the referenced report: a single unbounded shared data structure that every "deposit"/session-store operation appends to, with no cap and no alternate handling once it grows too large.

The analogous sibling implementation, `RedisSessionStorage.addKeyToShopList`, at least deduplicates via `idKeysArray.includes(idKey)`, but is still an unbounded single JSON-serialized value with no growth cap: [4](#0-3) 

### Impact Explanation
Once the serialized `shop:<shop>` value grows large enough to exceed the underlying store's per-value limits (e.g., Cloudflare Workers KV's 25 MiB per-value limit), `namespace.put` in `addShopIds`/`storeSession` will begin failing for that shop, and `findSessionsByShop` will fail to parse/return sessions. This denies the ability to store or enumerate sessions for that shop going forward — a DoS of the authentication/session-storage handler scoped to that tenant, impacting not just the initiating actor but any staff/collaborator user whose online/offline session creation subsequently hits the same shop key. Even well before hitting a hard size limit, every `storeSession` call becomes progressively more expensive (O(n) read-modify-write of a growing JSON blob), degrading OAuth completion latency/reliability for the shop over time.

### Likelihood Explanation
The growth path requires no exotic access: a single merchant/admin can simply re-run the app's standard OAuth flow (install, "log in with Shopify", token refresh, or add-on staff logins for online mode) repeatedly. No privileged access, secret leakage, or MITM is needed — it's driven entirely through the normal `begin`/`callback` OAuth endpoints that any app exposes to its own merchant. The KV adapter's total lack of deduplication makes this trivially and cheaply reachable (no distinct users required, unlike Redis which at least skips exact-duplicate ids).

### Recommendation
- Deduplicate session ids before appending in `KVSessionStorage.addShopIds` (mirroring the Redis adapter's `includes` check).
- Bound the maximum number of tracked session ids per shop (e.g., cap and evict oldest/expired entries, or move to a paginated/indexed structure instead of a single JSON blob) so a single value can never exceed the backing store's size limits.
- Consider proactively pruning expired sessions from the per-shop index during `storeSession`/`addShopIds` rather than relying solely on explicit `deleteSession` calls.

### Proof of Concept
1. Configure an app to use `KVSessionStorage` as `sessionStorage`.
2. As the shop's admin, repeatedly complete the OAuth flow for the same shop (e.g., automate hitting `/auth` then `/auth/callback` in a loop), each time producing a `storeSession` call for an offline (or new online) session.
3. Observe that `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`'s `addShopIds` (lines 75-79) appends every call's id(s) to the `shop:<shop>` KV entry with no deduplication or cap.
4. After enough iterations, the JSON-serialized array under `shop:<shop>` approaches/exceeds the KV value size limit, causing subsequent `namespace.put` calls in `storeSession`/`addShopIds` to fail and `findSessionsByShop` (line 56-69) to fail to load/parse the id list — blocking session storage/retrieval for that shop going forward.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
