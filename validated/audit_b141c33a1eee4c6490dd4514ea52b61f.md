### Title
Lack of Slippage Protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` allow a user to add or remove liquidity from a TRC10 token-pair exchange pool by specifying only the `quant` of one token. The counter-token amount (`anotherTokenQuant`) is computed on-chain at execution time from the pool's current ratio, with no user-supplied bound on the acceptable output/cost. This is the same bug class as the ERC4626 `deposit()`/`mint()` report: users cannot express a minimum-received or maximum-paid tolerance, so if the pool ratio shifts between transaction submission and execution (e.g. due to another `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` being processed first/same block), they can receive/pay a significantly different amount than intended, with no on-chain guard to abort the transaction.

### Finding Description
In `ExchangeInjectActuator.execute()`, the counter-token amount is derived purely from the live pool balances at execution time: [1](#0-0) 

`doValidate()` for inject only checks that the pool is not closed and that the resulting balance stays under `balanceLimit`; it performs no comparison against any user-specified expected/min/max counter-token amount: [2](#0-1) 

Similarly, `ExchangeWithdrawActuator.execute()` computes the counter-token amount from the current pool ratio with no bound: [3](#0-2) 

Notably, `ExchangeTransactionActuator` — the sibling actuator for swaps in the same pool — *does* implement this protection via an `expected` field in `ExchangeTransactionContract` that is validated against the computed `anotherTokenQuant`: [4](#0-3) 

But `ExchangeInjectContract` and `ExchangeWithdrawContract` (as defined in the protocol) carry only `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/`min`/`max` field equivalent to `ExchangeTransactionContract.expected`: [5](#0-4) 

This mirrors the external report's root cause exactly: the vault's `deposit()`/`mint()` compute the counterpart amount via `previewDeposit()`/`previewMint()` at execution time with no user-supplied slippage bound, and here `ExchangeInjectActuator`/`ExchangeWithdrawActuator` compute the counterpart token amount via the live pool ratio at execution time with no user-supplied bound.

### Impact Explanation
A user broadcasting an `ExchangeInjectContract` or `ExchangeWithdrawContract` has no way to guarantee a minimum received amount (withdraw) or maximum required amount (inject) if the pool ratio moves before the transaction is packed into a block. Because transactions are visible in the pending pool, another network participant can submit an `ExchangeTransactionContract` (or additional inject/withdraw) that shifts `firstTokenBalance`/`secondTokenBalance` ahead of the victim's transaction in the same block, causing the victim to withdraw fewer counter-tokens than expected or inject a disproportionate amount relative to the pool's true value — a sandwich-style value extraction against liquidity providers. This is a direct asset/accounting risk to users of the TRC10 exchange feature, consistent with the "medium risk" classification of the analogous report.

### Likelihood Explanation
The exchange contracts are processed by ordinary, unprivileged actuators reachable by any account via standard broadcast transactions (`wallet/exchangeinject`, `wallet/exchangewithdraw` HTTP/RPC endpoints and the underlying `ExchangeInjectContract`/`ExchangeWithdrawContract` protocol messages), so no privileged role or node compromise is required. The pool ratio is influenced by TRX/TRC10 balances that any account with sufficient assets can move via `ExchangeTransactionContract`, making the underlying front-running/ratio-shift precondition realistically achievable, particularly for lower-liquidity pools.

### Recommendation
Add a slippage-protection field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, analogous to the `expected` field already present on `ExchangeTransactionContract`:
- For `ExchangeWithdrawContract`, add a minimum acceptable `anotherTokenQuant` and revert in `ExchangeWithdrawActuator.doValidate()`/`execute()` if the computed amount is below it.
- For `ExchangeInjectContract`, add a maximum acceptable `anotherTokenQuant` and revert if the computed required counter-token amount exceeds it.

### Proof of Concept
1. Account A submits `ExchangeWithdrawContract` for `exchangeId=X`, `tokenId=firstToken`, `quant=Q`, expecting `anotherTokenQuant ≈ secondTokenBalance*Q/firstTokenBalance` based on the pool state at submission time, as computed in `ExchangeWithdrawActuator.execute()`.
2. Before A's transaction is included, account B submits and gets included an `ExchangeTransactionContract` (or `ExchangeInjectContract`) that shifts `firstTokenBalance`/`secondTokenBalance` significantly (e.g., a large swap in the same pool), see the ratio-dependent computation at [6](#0-5) .
3. A's `ExchangeWithdrawContract` then executes against the new, shifted pool ratio in `ExchangeWithdrawActuator.execute()` lines 74-89, yielding a much smaller `anotherTokenQuant` than A anticipated, with no validation step available to reject this outcome (compare the withdraw `doValidate()` which lacks any expected-amount check, unlike `ExchangeTransactionActuator.doValidate()` line 219 `if (anotherTokenQuant < tokenExpected) { throw ... }`).
