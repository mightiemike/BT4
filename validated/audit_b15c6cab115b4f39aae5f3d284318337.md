### Title
Order-book flooding can force `MarketSellAssetActuator` to abort mid-match, griefing takers and partially-matched makers - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` (TRON's on-chain TRC10 order-matching engine) matches one taker order against up to `MAX_MATCH_NUM` (20) resting maker orders inside a single actuator execution, applying state changes for each matched maker order incrementally rather than atomically validating the whole match before writing anything. If the loop needs to consume more than 20 maker orders to satisfy the taker's requested quantity, it throws a `ContractValidateException` mid-loop, which aborts the whole transaction as `FAILED` — after several maker orders in that same loop have already had their state mutated. This is the same "batch processing that can be griefed by a single failing/expensive item in the batch" class of bug described in the external LibFillResults.sol report, reachable here by any unprivileged user via ordinary order placement.

### Finding Description
`matchOrder()` walks the maker order book price level by price level and calls `matchSingleOrder()` for each candidate maker order, incrementing `matchOrderCount` on every match: [1](#0-0) 

If more than `MAX_MATCH_NUM` (20) maker orders are required to fill the taker's requested quantity, the loop throws: [2](#0-1) 

Critically, `matchSingleOrder()` does not buffer its effects until the whole match succeeds — it writes the maker order back to the store and credits both taker and maker accounts as each pairing is resolved: [3](#0-2) 

So by the time the 21st match attempt throws `ContractValidateException`, up to 20 prior maker orders and their owners' account balances have already been mutated and persisted to `orderStore`/`accountStore`, while the transaction itself is still reported as failed to the actuator framework: [4](#0-3) 

Note that `transferBalanceOrToken()` (deducting the taker's sell asset) and order creation both occur *before* `matchOrder()` is invoked in `execute()`: [5](#0-4) 

This mirrors the reported bug class exactly: a batch of order-matching sub-operations (here, matching against up to N maker orders) is not made "NoThrow" or fully validated before mutation, so a single triggering condition (exceeding `MAX_MATCH_NUM`) reverts the transaction outcome to `FAILED` even though a large portion of the underlying state changes for that batch have already been applied and the taker still pays the transaction fee (`ret.setStatus(fee, code.FAILED)`).

### Impact Explanation
An attacker (or ordinary market participant, intentionally or not) can populate the order book with more than `MAX_MATCH_NUM` (20) small resting orders at the best price for a trading pair. Any taker whose sell quantity, at that price, would require matching against more than 20 of those orders will have their `MarketSellAssetContract` transaction fail with `ContractValidateException`/`code.FAILED`, while:
- the taker's fee is still charged (`calcFee()` deducted regardless of the eventual failure path),
- the taker's sell-side balance/tokens have already been debited and a new taker order record created before the failure is detected,
- several maker orders processed earlier in the same loop have already had their balances updated and order records mutated/removed.

This is a concrete griefing/state-inconsistency vector against an unprivileged, reachable actuator (no special role required to place many small orders or to submit a large taker order), matching the report's "batch processing revert causes delays and loss of fees" impact class.

### Likelihood Explanation
Placing many small resting orders at a chosen price is a normal, permissionless operation available to any account via `MarketSellAssetActuator`/`MarketCancelOrderActuator`, so an attacker can deliberately engineer the order book to exceed `MAX_MATCH_NUM` at a specific price for a targeted pair. Any taker order that needs to sweep more than 20 price-matching maker orders will hit this failure path without any special timing or front-running required (unlike the 0x scenario, which needed front-running of allowance reduction — here the condition is purely order-book depth, making it arguably easier to trigger).

### Recommendation
- Pre-validate (dry-run) the total number of maker orders that will be consumed before mutating any state, and only commit changes once it is confirmed the match can complete within `MAX_MATCH_NUM`, or make partial-fill-and-stop behavior explicit (fill up to `MAX_MATCH_NUM` and return the remainder to the taker as an open order, rather than throwing).
- Ensure `matchOrder`/`matchSingleOrder` state writes are staged and only flushed atomically once the whole match (or the intended partial match) is determined to be valid, so a failure partway through cannot leave some maker orders/balances mutated while the overall transaction is reported as `FAILED`.
- Verify the fee-charging logic does not charge takers full fees for order-matching failures caused solely by order-book depth exceeding `MAX_MATCH_NUM`.

### Proof of Concept
1. Attacker submits 25 separate `MarketSellAssetContract` orders selling token A for token B at the same best price, each for a small quantity (each a distinct maker order in `MarketOrderStore`/`MarketPairPriceToOrderStore`).
2. A legitimate taker submits a `MarketSellAssetContract` selling token B for token A with a quantity large enough that, at the best price, it must match against more than 20 of the attacker's resting orders to be filled.
3. `MarketSellAssetActuator.execute()` runs: `transferBalanceOrToken()` debits the taker's token B, `createAndSaveOrder()` persists the taker's order, then `matchOrder()` begins looping through the attacker's maker orders via `matchSingleOrder()`, writing state (`orderStore.put`, account balance updates) for each of the first 20 matches.
4. On the 21st match attempt, `matchOrderCount > MAX_MATCH_NUM` triggers `ContractValidateException("Too many matches...")` at `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:358`, which is caught in `execute()`'s catch block, setting `ret.setStatus(fee, code.FAILED)` and throwing `ContractExeException`.
5. Result: the taker's transaction is recorded as `FAILED` (fee charged) despite token B already being deducted from their balance and 20 maker orders/balances already having been mutated in the same execution — an inconsistent, grief-able outcome directly analogous to the reported "batch reverts, fees lost, delays" scenario.

**Note on verification limits:** I was unable to fully confirm within the available tooling whether TRON's outer transaction/block processing pipeline (`TransactionTrace`/`RuntimeImpl`/`Manager.processTransaction`) wraps non-VM system actuators like `MarketSellAssetActuator` in any additional atomic rollback mechanism beyond what the actuator code itself performs. If such an outer rollback exists and fully reverts all store writes for any transaction that ultimately returns `ContractExeException`, the "orphaned partial state" portion of this impact would not materialize (though the fee-loss/failed-transaction griefing via `MAX_MATCH_NUM` would still hold). Recommend a Devin session with full repository/test access to trace `RuntimeImpl.execute()` and the surrounding session/commit logic to conclusively confirm or rule out the partial-state-persistence claim.
