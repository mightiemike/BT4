## Title
Unbounded gzip decompression in Cairo0 declare transaction handling bypasses size limits and allows memory-exhaustion DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
`decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs` decompresses a user-supplied gzip payload with `GzDecoder::read_to_end` and **no output-size cap**, exactly matching the reported bug class (gzip decompression bomb bypassing declared size limits). This function is invoked when converting a client-submitted `BroadcastedDeclareV1Transaction`'s `compressed_program` field into an executable `starknet_api::deprecated_contract_class::ContractClass` for local execution (fee estimation / simulation), via `user_deprecated_contract_class_to_sn_api`.

Unlike the proper declare-transaction ingestion path used by the gateway/mempool (`apollo_gateway`'s `StatelessTransactionValidator::validate_class_length`, which enforces `max_contract_bytecode_size`/`max_contract_class_object_size` before touching decompressed content, and `starknet_api::compression_utils::decode_and_decompress_with_size_limit`, which correctly bounds decompression output via `.take(max_size + 1)`), this RPC-facing conversion path for legacy Cairo0 declare transactions applies **no size bound whatsoever** to the decompressed program bytes. The `TODO(dan): add time and size limits` comment on the exact line confirms this is a known, unaddressed gap — directly analogous to the `usp/helpers.py:239` `gzip_lib.decompress(data)` call in the external report, which also lacked an output-size guard despite an intended limit elsewhere in the pipeline.

An attacker (any unauthenticated RPC caller) can submit a `BroadcastedDeclareV1Transaction` with a small, highly-compressed `compressed_program` field to `starknet_estimateFee` or `starknet_simulateTransactions`. The payload decompresses into an unbounded in-memory buffer before any size validation occurs, matching the "compressed_size < limit passes gate, decompressed_size unbounded" pattern from the report.

### Impact Explanation
A single unauthenticated JSON-RPC request (no fee paid, no on-chain transaction required) can cause the RPC node process to allocate an attacker-controlled amount of memory (limited only by available compressed-payload size, e.g. a few hundred KB expanding to hundreds of MB or more), leading to process memory exhaustion / crash. This is a resource-exhaustion vulnerability triggered purely by unprivileged, single-request user input reaching the blockifier-execution/simulation path (CWE-400), consistent with the severity class of the original report.

### Likelihood Explanation
High likelihood: the vulnerable function is reachable directly from a standard, publicly exposed JSON-RPC method (`starknet_estimateFee`/`starknet_simulateTransactions`) with a `BROADCASTED_DECLARE_TXN` of version 1, requires no authentication, no fee payment, and no special network conditions — only a single JSON-RPC call with a crafted gzip bomb in the `contract_class.program` field.

### Recommendation
Apply the same bounded-decompression pattern already used elsewhere in the codebase (`starknet_api::compression_utils::decompress_with_size_limit`, which uses `.take(max_size + 1)` and rejects output exceeding the limit) inside `decompress_program`, enforcing a maximum decompressed program size (e.g., matching `max_contract_bytecode_size`/`max_contract_class_object_size` used by the gateway's stateless validator) before or during the `read_to_end` call, and return an RPC error instead of allocating unbounded memory.

### Proof of Concept
1. Craft a `compressed_program` value: gzip-compress a large JSON program (e.g., 200+ MB of repeated whitespace/padding within a valid Cairo0 `Program` JSON structure) at a high compression ratio, producing a payload of a few hundred KB, then base64-encode it.
2. Submit a JSON-RPC request to `starknet_estimateFee` or `starknet_simulateTransactions` with a `BROADCASTED_DECLARE_TXN` (version `0x1`) whose `contract_class.program` field is the crafted base64 gzip payload.
3. Observe that `decompress_program` (crates/apollo_rpc/src/v0_8/api/mod.rs:671-682) decodes and decompresses the payload with `GzDecoder::read_to_end` with no size limit, causing the process to allocate hundreds of MB (or more) for a single request, exactly as demonstrated in the external report's PoC against `gzip_lib.decompress`.

Note: I was unable to fully trace the exact call sites in `crates/apollo_rpc/src/v0_8/api/api_impl.rs` that invoke `estimate_fee`/`simulate_transactions` due to running out of tool iterations; confirming the precise handler wiring for these RPC methods would benefit from further inspection of that file in a full Devin session.
