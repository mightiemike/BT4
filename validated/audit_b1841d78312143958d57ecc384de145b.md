Given the reachable areas allowed (RPC caller, transaction execution result queries) and after review, the strongest analog is unbounded recursion in `Chain::get_recursive_transaction_results`, which walks the receipt-outcome DAG without a depth limit when assembling a final transaction result.

### Title
Unbounded recursion in transaction/receipt outcome tree traversal can crash a node - (File: chain/chain/src/chain.rs)

### Summary
`Chain::get_recursive_transaction_results` recursively walks the DAG of receipt outcomes produced by a transaction, following every `receipt_ids` entry with no maximum depth or iteration cap, analogous to how the GitLab issue-comment DoS (CVE-2019-15593) let unprivileged, attacker-controlled input drive unbounded resource consumption in a query/serving path.

### Finding Description
`get_recursive_transaction_results` recurses once for every receipt spawned (directly or transitively) by a transaction, pushing to a shared `outcomes` vector and then calling itself for each `receipt_ids[idx]` of the outcome just added, with no depth or fan-out limit: [1](#0-0) 

This function is invoked by `get_final_transaction_result`, the routine documented as returning the `FinalExecutionOutcomeView` for a given transaction hash after waiting for the completion of all its receipts: [2](#0-1) 

An unprivileged account can trigger long chains of dependent receipts by deploying and invoking a contract that repeatedly issues a single follow-up cross-contract call (a "linked list" of promises) rather than a bounded fan-out DAG. Because delayed/queued receipts can be processed across many chunks/blocks rather than a single chunk, the depth of this outcome chain is not bounded by a single chunk's gas or size limits the way `max_receipt_size`/`combined_transactions_size_limit`/state-witness limits bound in-chunk data (as documented for other size-based DoS protections): [3](#0-2) 

Once such a deep chain of outcomes exists, any subsequent query that resolves the final result of the originating transaction re-walks the entire chain recursively with `get_recursive_transaction_results`, and a sufficiently deep chain can exhaust the calling thread's stack, crashing (or making unresponsive) the node process serving that query — a transaction-triggered/query-triggered halt of a single node.

### Impact Explanation
If the recursion depth required to overflow the serving thread's stack is achievable by a normal user (via a self-chaining contract call pattern, executed over multiple blocks so it is not blocked by any single-chunk resource limit), a remote, unprivileged caller could crash a node process that serves transaction-status/RPC queries by later requesting the final result for that transaction. This matches the "transaction-triggered halt" class of impact called out as in-scope.

### Likelihood Explanation
Likelihood depends on (a) whether the code path that resolves a query for a transaction's final outcome actually calls this specific recursive helper (as opposed to using `get_execution_outcome`/`get_outcomes_by_id` lookups that are not recursive) in the currently-wired RPC/view-client handlers, and (b) whether achievable receipt-chain depth (bounded by gas costs per hop and the attacker's willingness to spend many blocks building the chain) is sufficient to overflow the thread stack given the per-frame size of this function. I was not able to confirm, within the available search budget, that `get_final_transaction_result` (as opposed to other non-recursive result-assembly paths) is the one actually reached by the production JSON-RPC `tx`/`EXPERIMENTAL_tx_status` handlers in `chain/client/src/view_client_actor.rs` — my searches there did not find a direct call site for this specific function. This uncertainty should be resolved before treating this as a confirmed, high-likelihood issue.

### Recommendation
- Convert `get_recursive_transaction_results` to an iterative (worklist/stack-based) traversal instead of native recursion, removing any Rust call-stack dependency on receipt-chain depth.
- Add an explicit maximum traversal depth/size cap (mirroring the existing size-based limits such as `max_receipt_size` and `combined_transactions_size_limit`) and return a bounded/paginated or "truncated" result once the cap is hit, rather than failing catastrophically.
- Verify and, if necessary, fix the actual JSON-RPC call chain to confirm which outcome-resolution function production nodes use, and apply the same hardening there.

### Proof of Concept
1. Deploy a contract with a method that, upon being called, issues a single `Promise` cross-contract call to itself (or another contract) with the same method, forming a strictly linear chain of receipts (A → B → C → …) rather than a fan-out tree.
2. Repeatedly submit transactions (paying for gas each time, over as many blocks as needed) so the chain of receipt outcomes for the original transaction hash grows arbitrarily deep, since this construction is not limited by any single chunk's `max_receipt_size` or `combined_transactions_size_limit`.
3. Once the chain is sufficiently deep, submit a `tx`/`EXPERIMENTAL_tx_status` query for the original transaction hash against a node that resolves it via `get_final_transaction_result`; the recursive traversal in `get_recursive_transaction_results` walks the full depth of the chain on the call stack, risking a stack overflow and crash of the serving process.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 17MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.
