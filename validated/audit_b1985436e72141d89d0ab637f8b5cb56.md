### Title
Unauthenticated `BOOTSTRAP`-address declare bypasses `__validate_declare__`, nonce, and fee enforcement - (File: `crates/starknet_api/src/executable_transaction.rs`)

### Summary
A declare transaction whose `sender_address` equals the well-known constant `bootstrap_address()` (the ASCII short-string `'BOOTSTRAP'`), with `nonce == 0`, `version == 3`, and zero resource bounds (`max_possible_fee == 0`), is treated by both the blockifier (`AccountTransaction::execute_raw`) and the Starknet OS (`execute_declare_transaction` in `transaction_impls.cairo`) as a privileged "genesis bootstrap" declare that skips `__validate_declare__`, nonce incrementing, and fee charging.

### Finding Description
The gate that decides whether this privileged path is taken is `DeclareTransaction::is_bootstrap_declare`, which only checks `sender_address == Self::bootstrap_address() && nonce == 0 && !charge_fee` [2](#0-1) . `bootstrap_address()` is a publicly known, fixed constant derived from the ASCII string `"BOOTSTRAP"` [3](#0-2) , not a secret or an address whose private key anyone must possess.

In `AccountTransaction::execute_raw`, whenever `is_bootstrap_declare` returns true, the code runs the declare's `run_execute` directly and returns, entirely bypassing `perform_pre_validation_stage` (which normally checks nonce/fee) and the account's `__validate_declare__` entry point [4](#0-3) . The Starknet OS mirrors the same unauthenticated shortcut: if `sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, and `max_possible_fee == 0`, it directly writes the class hash into `contract_class_changes` and calls `%{ SkipTx %}`, without ever invoking `VALIDATE_DECLARE_ENTRY_POINT_SELECTOR` or `check_and_increment_nonce` [5](#0-4) .

Because `charge_fee` is controlled by the transaction's own `enforce_fee`/execution flags (derived from resource bounds set by the sender) and `nonce` is a value the sender also chooses, an unprivileged sender who simply crafts a Declare V3 transaction with `sender_address = bootstrap_address()`, `nonce = 0`, and all-zero resource bounds can trigger this path — there is no possession-of-private-key requirement analogous to normal `__validate_declare__` signature checks, and there is no restriction limiting this behavior to genesis/block 0. This mirrors the Karak root cause: a code path grants privileged behavior (skip authentication/validation, escalate to a "trusted" role) based purely on an unvalidated/self-supplied field (there, `extraData`'s `manager`; here, the `sender_address` field of a self-crafted transaction), rather than on cryptographic proof of authorization.

The comments in `apollo_integration_tests/tests/bootstrap_declare.rs` confirm bootstrap-declare transactions are treated as ordinary transactions that flow through the standard mempool/gateway/batcher pipeline (not a special genesis-only injection mechanism) [6](#0-5) .

Notably, the gateway's `check_declare_permissions`, which restricts who may submit Declare transactions via `is_authorized_declarer`, does not appear (from what was found) to special-case the bootstrap address to prevent an unauthorized declarer from using it [7](#0-6) .

### Impact Explanation
If reachable in production (i.e., if `authorized_declarer_accounts` is not configured to exclude the bootstrap address, or is unset/disabled — the default config shows `authorized_declarer_accounts.#is_none: true`, meaning no allow-list restriction by default) [8](#0-7) , any unprivileged sender can declare arbitrary classes for free, without ever needing to prove ownership of the bootstrap address via signature/`__validate_declare__`, and without paying fees or advancing a nonce — a form of unauthorized account action and fee-enforcement/resource-accounting bypass reachable directly from a single submitted transaction.

### Likelihood Explanation
The bootstrap address is a compile-time constant, publicly derivable from the string `"BOOTSTRAP"` [9](#0-8) . Crafting a V3 declare transaction with this `sender_address`, `nonce = 0`, and zero resource bounds requires no special access. Whether this is actually exploitable in a live deployment depends on the `authorized_declarer_accounts` allow-list configuration and any other out-of-band restrictions not found in this pass — this is the main uncertainty, since I could not locate an explicit runtime check excluding `bootstrap_address()` from authorized declarers, nor a check limiting the bootstrap path to genesis/block-zero only.

### Recommendation
Restrict the bootstrap-declare shortcut so it can only be exercised during genesis initialization (e.g., gate it on `block_number == 0` in addition to the existing checks), and/or have the gateway's `check_declare_permissions` explicitly reject any Declare transaction using `bootstrap_address()` as `sender_address` outside of the genesis/bootstrap flow, so that no ordinary user-submitted transaction can reach this privileged skip-validation/skip-fee path.

### Proof of Concept
1. Construct a `DeclareTransaction::V3` with `sender_address = DeclareTransaction::bootstrap_address()`, `nonce = Nonce(Felt::ZERO)`, `resource_bounds` set so that `compute_max_possible_fee` evaluates to zero (e.g., via `ValidResourceBounds::create_for_testing_no_fee_enforcement()`, matching the pattern in `generate_bootstrap_declare` at `crates/mempool_test_utils/src/starknet_api_test_utils.rs:586-595`).
2. Submit through the standard gateway `add_tx` flow, as done in `crates/apollo_integration_tests/tests/bootstrap_declare.rs`.
3. Observe that `is_bootstrap_declare` returns true, causing `AccountTransaction::execute_raw` to skip `perform_pre_validation_stage` and `__validate_declare__`, directly declaring the class hash for free, without any proof that the sender controls the `BOOTSTRAP` address [10](#0-9) .
