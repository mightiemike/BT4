### Title
Chunk-executor / replay-verify output-equivalence check silently ignores `position_state_checkpoint_hash` (and other checkpoint hashes) - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the chunk executor and by the `replay_on_archive` / db-tool replay-verify tooling to confirm that a locally re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed to the ledger (and authenticated by the accumulator/ledger-info signatures). The function explicitly checks `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash`, but its own comment admits it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

This is the equivalence check that guards commit/replay paths (`execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`) that consume a `TransactionInfo` fetched from storage/backup and compare it against locally recomputed `TransactionOutput`. The new `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature (`types/src/on_chain_config/aptos_features.rs`) commits an additional authenticated root — the native-position Merkle root — into `TransactionInfoV1.position_state_checkpoint_hash` ( [2](#0-1) ), which flows into the transaction-info hash and therefore into the transaction accumulator root that is signed by validators (`execution/executor/src/workflow/do_ledger_update.rs` lines 95-121, `execution/executor/src/workflow/do_state_checkpoint.rs` lines 62-83). Because this root is part of the signed commitment, any code path that is supposed to certify "my local execution/replay matches what was committed" must compare it. `ensure_match_transaction_info` is that certification function, and it does not compare it (nor `state_checkpoint_hash`/`hot_state_checkpoint_hash`).

### Impact Explanation
If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and the prerequisite `TRANSACTION_INFO_V1`/`HOTNESS_IN_EPILOGUE`) is enabled, a node or tool relying on `ensure_match_transaction_info` for validation — chunk-executor's replay of transaction lists/outputs during fast-sync/backup-restore, and the `db-tool replay_on_archive` auditing tool — will report a successful, "verified" replay even if the locally computed native-position (trading) state root diverges from the authenticated on-chain root. This defeats the entire purpose of chunk-executor equivalence checking and of replay-verify: it authenticates the write-set/events/gas/status but not the position-state commitment, so a divergence in the native-position Jellyfish Merkle tree (a hard-fork/non-determinism bug, or a bug in `compute_position_checkpoint`) would go undetected, silently accepting corrupted/incorrect position state as valid during restore or archive audits. This is exactly the class of bug the task's Proof And Storage Pivots section calls out: "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and "restore paths must preserve deterministic proof binding" — here the check meant to enforce that binding has a documented hole.

### Likelihood Explanation
The gap is explicit and acknowledged in the code's own TODO comment, so it is not speculative — it's a real omission the developers flagged themselves as a pre-condition ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS") that has apparently not yet been implemented while the feature flag already exists and is wired through `BlockExecutorConfigFromOnchain`/`Features`. The bug only manifests once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on (currently likely testnet/experimental given "trading-native" naming), so today's mainnet exposure is limited to nodes/tools running with that flag enabled; however the check itself is a latent state-integrity gap ready to trigger silently the moment the feature ships, and is unprivileged (any code path exercising chunk-executor replay/backup-restore or db-tool audit is affected without special access).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the recomputed output/state summary and `txn_info`, failing loudly on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `HOT_STATE_ROOT_IN_TXN_INFO`) is enabled on any network relying on this function for integrity verification.

### Proof of Concept
Not independently reproducible as a mainnet exploit today because it only matters when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled (not a default-on feature per `BlockExecutorConfigFromOnchain::new*` constructors, all of which default it to `false`) [3](#0-2) . The root cause is demonstrated purely by code inspection of `ensure_match_transaction_info`, which the maintainers' own comment confirms is incomplete: constructing two `TransactionOutput`s with identical write set/events/gas/status but differing only in the position-state writes that feed `position_state_checkpoint_hash` would make `ensure_match_transaction_info` return `Ok(())` for both against the same on-chain `TransactionInfo`, even though only one of them is the real state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
