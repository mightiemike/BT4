### Title
Divergent canonical `signer_signature` vectors for identical `block_id` due to unbound signature list in `signer_signature_hash` and weight-tie handling in `store_block_if_better` - (File: stackslib/src/chainstate/nakamoto/staging_blocks.rs)

### Summary
`NakamotoBlockHeader::signer_signature_hash` excludes the `signer_signature` field itself, so any subset/reordering of a valid signature set that still recovers to reward-set keys with total weight ≥ threshold verifies successfully under `verify_signer_signatures`, and multiple byte-distinct `NakamotoBlock` values share the same `block_hash()`/`block_id()`. The staging DB layer (`NakamotoStagingBlocksTx::store_block_if_better` in `stackslib/src/chainstate/nakamoto/staging_blocks.rs`) stores whichever signature vector for a given `block_hash`/`consensus_hash` arrives first, and explicitly refuses to replace it with an alternate vector of equal weight, so two honest nodes that first receive different (but equally-valid) subsets/orderings of signatures permanently retain different `signer_signature` vectors for the same `block_id`.

### Finding Description
The claimed equality is: for a fixed `block_id()`, all honest nodes must persist the same `signer_signature` vector. This is broken as follows.

`signer_signature_hash_inner`/`signer_signature_hash` compute the signing digest over the header fields excluding `signer_signature`, so the message signers sign never commits to *which* signatures, how many, or in what order will accompany the header — only to the header content. `verify_signer_signatures` (stackslib/src/chainstate/nakamoto/mod.rs) recovers each entry of `self.signer_signature` against `signer_signature_hash()` and sums the weight of matched reward-set keys, requiring only `total_weight_signed >= threshold`. Nothing in this check requires the vector to equal a specific canonical set/order — any valid subset or permutation of a validly-signed set that still meets the weight threshold passes.

At the storage layer, `store_block_if_better`:
- Case 1: `try_store_block_with_new_signer_sighash` — if no row exists for `(consensus_hash, block_hash)`, the block is stored unconditionally (`store_block`), regardless of which specific signature subset/order it carries.
- Case 2: if a row already exists, `replace_block` overwrites the stored `data` (which includes `signer_signature`) *only if* the incoming `signing_weight` is strictly greater than the existing one. If the weights are equal, the code explicitly takes the "no-op" branch: `"Will not store duplicate copy of block ..."` and keeps whatever was stored first.

Because `block_hash`/`index_block_hash` are derived from the header exclusive of `signer_signature`, this means: if node A first receives signature vector `[s1, s2]` (weight = threshold) and node B first receives a different valid vector `[s0, s2]` (also weight = threshold) for the identical header/block_id, both pass `verify_signer_signatures`, both are accepted via the "case 1" path on their respective nodes, and neither will ever be replaced by the other because the tie-breaking rule in `store_block_if_better` only replaces on strictly *greater* weight. The two nodes now permanently and irreversibly disagree on which `signer_signature` vector is "the" accepted one for that `block_id`.

Existing guards do not prevent this: `verify_signer_signatures` only checks aggregate weight, not vector identity or order; `store_block_if_better`/`try_store_block_with_new_signer_sighash`/`replace_block` operate purely on `(block_hash, consensus_hash)` and `signing_weight`, with no mechanism to canonicalize or deduplicate signature content across equal-weight alternatives.

### Impact Explanation
Block execution (state transition, MARF root, and reward calculation) does not consume the contents of `signer_signature` — only the header fields covered by `signer_signature_hash` matter for consensus state. Therefore this divergence does not directly cause a different state root or double-spend; the actual `NakamotoBlock` applied to chainstate is identical in effect. The impact is bounded to metadata/bookkeeping that keys off the exact stored `signer_signature` vector — e.g., `NakamotoStagingBlocksConnRef::get_block_processed_and_signed_weight`/`signing_weight` records, downstream signer-status/`BlockAccepted` stackerdb records, and any consumer that treats the persisted `data` blob (including its full signature list) as canonical per `block_id`. This matches the "temporary tip disagreement" / metadata-divergence category (High), not a Critical chain split, since the state root and applied transactions remain identical across nodes.

### Likelihood Explanation
This requires no majority stake or privileged role: an unprivileged relayer that observes a validly-signed block and a superset of valid signer signatures for it can simply forward two different subsets/orderings to different peers (e.g., via normal p2p block push), as long as each variant's summed weight ≥ threshold. This is fully repeatable and only requires the relayer to control message delivery order/content to different peers — a capability any network participant has. No BTC spend or stake is required beyond normal block relay.

### Recommendation
Bind the contents of `signer_signature` into a value that determines block/storage identity, or otherwise canonicalize the accepted signature set deterministically: e.g., require a canonical, sorted, deduplicated signature ordering (e.g., sorted by signer index) that `verify_signer_signatures` enforces (rejecting non-canonical order/composition) rather than accepting any qualifying subset/permutation, or store the accepted signature vector as append-only merged/superset per `block_id` (union of validly-recovered signatures) rather than "first-writer-wins-with-a-tie", so that all honest nodes that see enough independently-valid signatures converge to the same recorded vector.

### Proof of Concept
Rust integration test outline (two-node/two-fork harness or direct staging DB unit test):
1. Build a `NakamotoBlockHeader` `H` and compute `sighash = H.signer_signature_hash()`.
2. Generate signer keys `k0..k2` in the reward set with weights such that any 2-of-3 meets `threshold`.
3. Sign `sighash` with all three keys to get `sig0, sig1, sig2`.
4. Construct `blockA = NakamotoBlock { header: H.clone(), signer_signature: vec![sig1, sig2], .. }` and `blockB = NakamotoBlock { header: H.clone(), signer_signature: vec![sig0, sig2], .. }`.
5. Assert `blockA.header.block_id() == blockB.header.block_id()` and `blockA.header.block_hash() == blockB.header.block_hash()`.
6. Call `NakamotoBlockHeader::verify_signer_signatures` (or the chainstate-level equivalent) on both against the same reward set/threshold and assert both `Ok(())`/accept.
7. In two separate `StacksChainState`/staging DB instances (simulating node A and node B), call `store_block_if_better(&blockA, ..., signing_weight_A, ...)` on node A and `store_block_if_better(&blockB, ..., signing_weight_B, ...)` on node B, with `signing_weight_A == signing_weight_B`.
8. Assert both `store_block_if_better` calls return `true` (stored).
9. Fetch `get_nakamoto_block(&block_id)` from each node's staging DB and assert `node_A_block.signer_signature != node_B_block.signer_signature` while `node_A_block.header.block_id() == node_B_block.header.block_id()` — demonstrating the broken equality: identical `block_id`, divergent canonical `signer_signature`.
