### Title
Missing minimum-output (slippage) protection in `ExchangeWithdrawActuator` liquidity withdrawal - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract`, unlike `ExchangeTransactionContract`, has no field allowing the caller to specify a minimum acceptable amount of the counter-token to receive when withdrawing liquidity from a bancor-style TRX/TRC10 `Exchange` pool. The computed payout is fully dependent on the pool's current balances at execution time, exposing the withdrawing account to slippage/front-running loss between transaction submission and on-chain execution, exactly the same bug class as the reported `SecuritizeVault.liquidate()` missing `minOutputAmount`.

### Finding Description
`ExchangeTransactionContract` explicitly carries an `expected` field used as a slippage guard: `doValidate()` in `ExchangeTransactionActuator` computes `anotherTokenQuant` from the current pool ratio and rejects the transaction if `anotherTokenQuant < tokenExpected`. [1](#0-0) [2](#0-1) 

By contrast, `ExchangeWithdrawContract` has no equivalent minimum-output field: [3](#0-2) 

`ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` purely from the pool's live `firstTokenBalance`/`secondTokenBalance` at the moment the transaction is actually processed (i.e., at block-inclusion time, not at submission time), and pays it out unconditionally — there is no user-supplied floor to enforce: [4](#0-3) 

The same unguarded computation is repeated in `doValidate()`, where the only checks performed are balance sufficiency and a "Not precise enough" rounding-precision check — never a minimum-expected-output check: [5](#0-4) 

Because pool ratios can shift between the time a user signs/broadcasts an `ExchangeWithdrawContract` transaction and the time it is packed into a block (e.g., due to intervening `ExchangeTransactionContract`, `ExchangeInjectContract`, or other `ExchangeWithdrawContract` transactions changing `firstTokenBalance`/`secondTokenBalance`), the withdrawing user has no way to bound the worst acceptable output, unlike users of `ExchangeTransactionContract`.

### Impact Explanation
A user submitting `ExchangeWithdrawContract` to redeem their share of a TRX/TRC10 exchange pool can receive a counter-token amount smaller than they anticipated at signing time if the pool ratio moves (due to concurrent trades, injects, or withdrawals) before their transaction executes. This is a direct, unguarded value-loss vector reachable by any ordinary account broadcasting a standard protocol transaction — the same "no slippage protection" defect the external report flags for `SecuritizeVault.liquidate()`, just manifesting in java-tron's native bancor exchange withdrawal path instead of a smart-contract vault.

### Likelihood Explanation
Likelihood is moderate: it requires either adversarial transaction ordering/front-running around a pending withdrawal, or simply high pool activity/latency causing the ratio to move between submission and inclusion — both plausible on a live chain with these legacy `Exchange` contracts (TRX/TRC10 bancor pools created via `ExchangeCreateContract`). No privileged access, malicious peer, or leaked key is needed; any account holding pool tokens/pending withdrawals is affected.

### Recommendation
Add an `expected`/`min_another_token_quant` field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and in `ExchangeWithdrawActuator.doValidate()`/`execute()` reject the transaction if the computed `anotherTokenQuant` (or `tokenQuant` payout, depending on withdrawal direction) falls below the user-specified minimum, consistent with the existing pattern already implemented for `ExchangeTransactionActuator`.

### Proof of Concept
1. Alice observes a pool with `firstTokenBalance = 100,000,000` / `secondTokenBalance = 200,000,000` and computes an expected `anotherTokenQuant` for withdrawing `firstTokenQuant = X` of the first token.
2. Alice signs and broadcasts `ExchangeWithdrawContract{exchange_id, token_id=firstTokenID, quant=X}`.
3. Before Alice's transaction is packed into a block, another account submits `ExchangeTransactionContract` or `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions that shift the pool ratio (this is exactly the ratio-dependent computation shown in `ExchangeWithdrawActuator.execute()`, lines 77-89).
4. When Alice's transaction executes, `anotherTokenQuant` is recomputed from the now-changed `firstTokenBalance`/`secondTokenBalance`, and — since there is no `expected`/minimum field in `ExchangeWithdrawContract` to enforce a floor — Alice's withdrawal succeeds with a smaller payout than she expected, with no on-chain mechanism to prevent or detect this loss. [6](#0-5)
