## Analysis

The AZTEC bug class is: **a discriminating field that changes the meaning/effect of an authorized action is not cryptographically bound into the signature used to authenticate the request**, allowing a validly-signed message to be "inverted" or repurposed by resubmitting it with a different context.

The closest reachable analog in `shopify-app-js` is in webhook authentication: the HMAC only signs the **raw request body**, never the `shop`/`topic`/`webhook-id` headers that determine *which tenant* and *which action* the payload applies to, and the app's `apiSecretKey` (the HMAC key) is shared across every shop that installs the app — not shop-specific. Downstream, the webhook authenticator trusts the unauthenticated `shop` header to fetch and attach a live, privileged Admin API session.

### Root cause chain

1. `validateHmacFromRequestFactory` computes/validates the HMAC over `rawBody` only, using `config.apiSecretKey`. The `shop`, `topic`, `webhook-id`, and `api-version` headers are never included in the HMAC input: [1](#0-0) 

2. `validateFactory` calls the HMAC check on `rawBody` and only *afterward*, separately and without cryptographic linkage, calls `checkWebhookHeaders(request.headers, webhookType)` to confirm the discriminating headers are merely *present* (not that they are authentic or bound to the signed body): [2](#0-1) 

3. Both `shopify-app-remix` and `shopify-app-react-router`'s `authenticateWebhookFactory` take the unauthenticated `check.domain` value and use it to fetch/refresh a stored **offline session** — including its live access token — then hand callers a privileged `admin` API client scoped to that shop: [3](#0-2) [4](#0-3) 

Because `apiSecretKey` is one shared value across all shops installing the same app, any party who legitimately obtains **one** valid `(rawBody, hmac)` pair (e.g. by installing their own copy of the app on a store they control and triggering any webhook) can replay that exact body+HMAC pair to the app's public webhook endpoint while spoofing the `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers to name a **different, victim** shop. The HMAC check still passes (it only proves "some shop using this app produced this body"), `checkWebhookHeaders` only validates presence, and the webhook handler is then invoked with an `admin` client authenticated as the victim shop, using the victim's real, previously-stored access token.

### Why this maps to the report

- The AZTEC bug: `_status` (give/revoke) is not tied to the signature → same signature can flip role.
- Here: `shop`/`topic` (which tenant/what action) are not tied to the HMAC → same signature can be replayed against an arbitrary tenant/topic.

### Caveats / what is unverified

- This reflects Shopify's documented webhook HMAC design (body-only signing) rather than a shopify-app-js-introduced defect; I could not verify from the index whether `checkWebhookHeaders` or any other layer performs additional shop-binding (e.g., confirming the webhook actually originated from Shopify's IP ranges or TLS client, which would mitigate replay from outside Shopify's infrastructure). I was not able to fully inspect `ensureValidOfflineSession` implementations (only located, not read) to confirm there is no additional check tying the resolved session back to the request's authenticity.
- Exploitability requires: (a) attacker can obtain at least one valid `(rawBody, hmac)` pair for the shared app secret (trivial if they can install/use the app on any shop, including a free/dev store), and (b) the target victim shop must already have an active stored offline session for this app.

### Title
Webhook HMAC signs only the request body, not the shop/topic headers, enabling cross-tenant webhook forgery - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`shopify-app-js`'s webhook authentication computes and validates the `X-Shopify-Hmac-Sha256` value over the raw body alone, using the app's single shared `apiSecretKey`. The `shop`, `topic`, and `webhook-id` headers — which determine which tenant and which action the payload represents — are validated only for *presence*, never bound into the signature. `authenticate.webhook` in the Remix/React Router packages then uses the unauthenticated `shop` header to load and attach a live, privileged Admin API session to the webhook handler.

### Finding Description
`validateHmacFromRequestFactory`/`validateHmacString` sign/verify `rawBody` only: [5](#0-4) 
`validate()` performs the body HMAC check, then independently checks header presence via `checkWebhookHeaders`, with no cryptographic link between the two: [6](#0-5) 
The webhook authenticator trusts `check.domain` (sourced from the unauthenticated header) to resolve a real offline session/admin client: [7](#0-6) 

Since `apiSecretKey` is shared by the app across all installing shops (it is not shop-scoped), a signature valid for one shop's payload is indistinguishable, at the HMAC layer, from a signature intended for any other shop or topic — directly analogous to `_status` not being bound into the AZTEC signature.

### Impact Explanation
An attacker who can obtain any single valid `(rawBody, hmac)` pair for the target app (e.g., by installing the app themselves) can forge a POST directly to the app's public webhook endpoint, spoofing `X-Shopify-Shop-Domain` to a victim shop and `X-Shopify-Topic` to any registered topic. If the victim shop has an active offline session, the webhook handler executes with a live `admin` client authorized against the victim's real access token — a cross-tenant access/data-integrity issue (e.g., triggering `APP_UNINSTALLED`-style cleanup logic, or any custom handler side effects, against a shop the attacker doesn't control).

### Likelihood Explanation
Moderate: requires the attacker to be able to trigger at least one legitimate webhook delivery for the target app (achievable by installing a dev/trial copy of most public apps) and requires the victim shop to have an existing stored offline session, which is the common state for any actively-installed app.

### Recommendation
Bind the discriminating headers (`shop`, `topic`, `webhook-id`) into the HMAC-covered material (or otherwise cryptographically associate them with the delivery, e.g., via a per-shop-derived signing key or an out-of-band idempotency/replay cache keyed on `webhook-id`), so a signature computed for one shop/topic cannot be revalidated for another. Additionally, maintain a replay-protection store keyed by `webhook-id` to reject resubmission of previously processed webhook bodies.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) development store `attacker.myshopify.io`, receiving a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(apiSecretKey, B)`.
2. Attacker sends `POST /webhooks` directly to the app's public endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged/still valid), but `X-Shopify-Shop-Domain: victim.myshopify.io` and `X-Shopify-Topic: <any registered topic>`.
3. `validateHmacFromRequestFactory` validates `H` against `B` successfully (per `hmac-validator.ts:189-199`), and `checkWebhookHeaders` only checks the spoofed headers are present.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim.myshopify.io')`, obtaining `victim`'s real offline access token, and invokes the app's webhook handler with an authenticated `admin` client scoped to `victim.myshopify.io`.

    type,

    webhookType,
    ...adapterArgs

    const hmacHeaderName = webhookType

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
