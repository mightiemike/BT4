### Title
`citrea_network_to_chain_id` maps `Network::Nightly` and `Network::TestNetworkWithForks` to the same chain id, enabling cross-network replay of `BatchProofMethodId` council authorizations - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`citrea_network_to_chain_id` is meant to enforce the binding `body.chain_id == citrea_network_to_chain_id(this circuit's network) and only that network`, but it returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`. A council-signed `BatchProofMethodId` body produced for one of these networks passes the chain-id gate in `run_l1_block` on a light client prover configured for the other network, and — since the two networks' default `method_id_upgrade_authority_da_public_keys` are derived from the exact same environment-variable names/default constants — the signature check in `verify_method_id_security_council` also succeeds.

### Finding Description
The claimed binding is:
`body.chain_id == citrea_network_to_chain_id(network)` for exactly the one `network` value this light client circuit instance is running as.

In `crates/light-client-prover/src/circuit/mod.rs`:
```
pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}
``` [1](#0-0) 

`Network::Nightly` and `Network::TestNetworkWithForks` both map to `5665`, breaking pairwise distinctness. In `run_l1_block`, the gate is:
```
let circuit_chain_id = citrea_network_to_chain_id(network);
if circuit_chain_id != batch_proof_method_id.body.chain_id {
    continue;
}
if !verify_method_id_security_council(*method_id_upgrade_authority_da_public_keys, ...) { continue; }
BatchProofMethodIdAccessor::<S>::insert(...);
``` [2](#0-1) 

`verify_method_id_security_council` only checks that 3-of-5 EIP-191 signatures over `body.serialize()` match the pubkeys passed in; it has no notion of which network the message was intended for beyond the caller-supplied chain-id equality already checked above. [3](#0-2) 

The council keys for the two colliding networks are defined with identical default values sourced from the same env-var names (`METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5`):
```
pub const NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS: [...] = [ ... option_env!("METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1") ... ];
pub const TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS: [...] = [ ... option_env!("METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1") ... ];
``` [4](#0-3) 

Exploit flow: the council legitimately signs a `BatchProofMethodIdBody{ method_id, activation_l2_height, chain_id: citrea_network_to_chain_id(Network::Nightly) = 5665 }` and inscribes it for Nightly. This inscription (blob bytes, signatures) is publicly observable on the Nightly DA. An attacker — who only needs the unprivileged ability to inscribe/mine an arbitrary Bitcoin transaction — copies that exact `BatchProofMethodId` (body + `signatures_with_index`) into a new DA inscription targeting the DA chain observed by a light-client-prover instance running with `network = Network::TestNetworkWithForks` (or vice versa). In `run_l1_block` for that instance: `circuit_chain_id = citrea_network_to_chain_id(Network::TestNetworkWithForks) = 5665 == body.chain_id (5665)` → gate passes; `verify_method_id_security_council` succeeds because the default council pubkeys for `TestNetworkWithForks` are the same as for `Nightly`. As long as `body.activation_l2_height` exceeds the last recorded activation height on the target network's own `BatchProofMethodIdAccessor` state (an easy condition to satisfy on a fresh/low-height instance), `BatchProofMethodIdAccessor::insert` applies the method id activation on the target network's light client JMT state, even though the council never authorized anything for that network.

### Impact Explanation
This is a method-id upgrade accepted on a network that the security council never authorized for that network — matching the Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised." The `BatchProofMethodIdAccessor` entries for `TestNetworkWithForks` (or `Nightly`) diverge from what that network's council actually approved, which downstream affects which batch-proof method id is trusted for verifying batch proofs and, ultimately, the L2 state root the light client circuit commits to. Repeatable across any L1 block/height where the replayed activation height exceeds the target's current one; it affects every light client prover instance configured for the colliding network, causing them to diverge from what would have happened had the chain-id check truly been network-unique.

### Likelihood Explanation
Preconditions: a genuine, publicly observable council-signed `BatchProofMethodId` body for one of the two colliding networks (`Nightly`/`TestNetworkWithForks`), and a light client prover instance running the other of the pair with the same (unmodified/default) council keys — both defaults are baked in via identical `option_env!` names, so unless operators deliberately override these env vars differently per network build, the keys are identical. Attacker cost is only Bitcoin inscription fees for one transaction; no privileged role, node key, or council key is required — the attacker just relays already-public signed bytes to a different DA context. Both colliding networks are explicitly test/dev-oriented (`TestNetworkWithForks` is documented as "used for testing purposes only"), which lowers real-world blast radius versus a Mainnet/Testnet collision, but the code path itself is production code, not test-only code, and the underlying defect (non-injective `citrea_network_to_chain_id`) is a genuine violation of the intended binding.

### Recommendation
Make `citrea_network_to_chain_id` injective across all `Network` variants (e.g., assign `TestNetworkWithForks` its own distinct chain id, such as a value disjoint from `Nightly`'s `5665`), and add a compile-time or unit-test assertion that all `Network` variants map to pairwise-distinct chain ids so this cannot regress silently.

### Proof of Concept
```rust
// crates/light-client-prover/src/circuit/mod.rs (or a new test module)
#[test]
fn test_citrea_network_to_chain_id_pairwise_distinct() {
    use sov_rollup_interface::Network;
    let all = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];
    for i in 0..all.len() {
        for j in (i + 1)..all.len() {
            let a = citrea_network_to_chain_id(all[i]);
            let b = citrea_network_to_chain_id(all[j]);
            assert_ne!(
                a, b,
                "Network::{:?} and Network::{:?} collide on chain_id {}",
                all[i], all[j], a
            );
        }
    }
}
```
Running this test on the current code fails: `Network::Nightly` and `Network::TestNetworkWithForks` both produce `5665`, proving the binding `body.chain_id == citrea_network_to_chain_id(exact network)` is not enforced injectively across networks. A full end-to-end reproduction additionally constructs a `BatchProofMethodId` with `chain_id: citrea_network_to_chain_id(Network::Nightly)`, signs it with the shared default council keys (`NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` / `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS`, identical by default), and feeds the identical blob into `run_l1_block` invoked with `network = Network::TestNetworkWithForks`, asserting that `BatchProofMethodIdAccessor::get` reflects the injected method id despite no council authorization for `TestNetworkWithForks`.

```rust
pub fn verify_method_id_security_council(
    initial_da_pubkeys: [[u8; SECURITY_COUNCIL_COMPRESSED_PUBKEY_SIZE];
        SECURITY_COUNCIL_MEMBER_COUNT],
    msg: &[u8],
    signatures_with_idx: &[([u8; SECURITY_COUNCIL_SIGNATURE_SIZE], u8);
         SECURITY_COUNCIL_SIGNATURE_THRESHOLD],
) -> bool {
    // EIP-191 prefix + keccak256 → 32-byte prehash
    let prehash = eip191_hash_message(msg);

    // Check that signature indices are within bounds
    for &(_, index) in signatures_with_idx {
        if index >= 5 {
            log!("Invalid signature index: {}", index);
            return false;
        }
    }

    // Make sure the indexes are in ascending order to prevent duplicates
    for i in 0..signatures_with_idx.len() - 1 {
        if signatures_with_idx[i].1 >= signatures_with_idx[i + 1].1 {
            log!(
                "Signature indices are not in ascending order, failing indices: {}, {}",
                signatures_with_idx[i].1,
                signatures_with_idx[i + 1].1
            );
            return false;
        }
    }

    for signature_with_idx in signatures_with_idx.iter() {
        let signature = signature_with_idx.0;
        let pubkey_idx = signature_with_idx.1;
        let const_pubkey = initial_da_pubkeys[pubkey_idx as usize];

        // ensure the inscription pubkey matches the expected constant (compressed 33B)
        let verifying_key = VerifyingKey::from_sec1_bytes(const_pubkey.as_slice())
            .expect("Initial DA pubkeys must be parsable to k256 VerifyingKey form sec1 bytes");

        let Ok(parsed_sig) = Signature::from_bytes(&signature.into()) else {
            log!("Invalid signature format");
            return false; // invalid signature format, fail
        };

        // verify prehash with the matching verifying key
        if verifying_key
            .verify_prehash(prehash.as_slice(), &parsed_sig)
            .is_err()
        {
            log!("Signature verification failed for index: {}", pubkey_idx);
            return false;
        }
    }

    true
