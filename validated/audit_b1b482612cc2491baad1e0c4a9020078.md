Found: `merchant-custom-app.ts`'s `authenticate()` builds a `Session` purely from `sessionContext.shop`, and for `AppDistribution.ShopifyAdmin` that `shop` value is taken directly from the unauthenticated URL query string with no HMAC/session-token verification and no call to `sanitizeShop`.

### Title
Unauthenticated `shop` query parameter accepted as trusted session identity for merchant-custom (ShopifyAdmin distribution) apps - (File: packages/apps/shopify-app-react-router/src/server/authenticate/admin/authenticate.ts)

### Summary
For apps configured with `AppDistribution.ShopifyAdmin`, `getSessionTokenContext()` skips session-token/JWT verification entirely and takes the `shop` used to build the session context straight from `url.searchParams.get('shop')`, unsanitized and unauthenticated. [1](#0-0) 

### Finding Description
In the non-`ShopifyAdmin` branch, the `shop` is derived from a cryptographically verified JWT session token (`validateSessionToken` → `dest` claim), which is the trusted source of shop identity. [2](#0-1) 
For `AppDistribution.ShopifyAdmin`, that verification is bypassed and `shop` is read directly from the query string with no `api.utils.sanitizeShop` call and no HMAC/JWT check on this code path. [3](#0-2) 
This `shop` value flows straight into `strategy.authenticate(request, {session, sessionToken, shop})`, and for the merchant-custom-app strategy (used for `SingleMerchant`/custom apps, the same class of app that `ShopifyAdmin`-embedded custom apps rely on), the returned `Session` is built directly with `api.session.customAppSession(shop)` — i.e., the session's `shop` field is set from the caller-supplied, unauthenticated value. [4](#0-3) 
This is directly analogous to the Caviar root cause: a value that should only ever originate from a privileged/verified source (the pool's own Factory-issued NFT ID, verified in-protocol) is instead accepted from an untrusted caller-supplied path and then used to construct a "trusted" object (a private pool / here, a `Session`) that downstream code treats as authoritative. In both cases, the missing check is "is this identifier something we should not blindly trust as coming from a verified/privileged path."

### Impact Explanation
`customAppSession()` builds a `Session` object with `isOnline: false` and an empty `state`; since this is the custom/merchant-app configuration, the app's configured `accessToken` is typically wired in elsewhere via config (not part of this synthesized session), so the concrete blast radius depends on how the app's admin API client resolves credentials from this session. At minimum, an unauthenticated caller controls the `shop` value baked into a `Session` object used for subsequent admin-context construction (`createContext`), billing checks, and logging keyed on `shop` — enabling shop-identity spoofing/confusion in the admin context for the `ShopifyAdmin`/merchant-custom-app code path, without any HMAC or session-token proof that the request actually originates from that shop.

### Likelihood Explanation
Any HTTP GET to an app route configured with `AppDistribution.ShopifyAdmin` can trigger this path merely by supplying `?shop=<attacker-value>`; there is no authentication gate before `getSessionTokenContext` reads the query param and hands it to the strategy. [5](#0-4) 

### Recommendation
For the `AppDistribution.ShopifyAdmin` branch, validate the `shop` query parameter with `api.utils.sanitizeShop(shop, true)` before use, and ensure it is cross-checked against the loaded session's `shop` (as is done elsewhere, e.g. in the Express middleware's `session.shop !== shop` check) before it is used to construct a `Session` or admin context. [6](#0-5) 

### Proof of Concept
1. Configure an app with `distribution: AppDistribution.ShopifyAdmin`.
2. Send `GET /app?shop=attacker-controlled-value` without any Authorization header or valid session token.
3. `getSessionTokenContext` reads `shop` unsanitized from the query string. [7](#0-6) 
4. `strategy.authenticate` (merchant-custom-app strategy) builds a `Session` from this unauthenticated `shop` value via `api.session.customAppSession(shop)`. [8](#0-7) 
5. Downstream context/logging/billing logic proceeds using this attacker-influenced `shop` value without any cryptographic proof it originated from the claimed shop.
