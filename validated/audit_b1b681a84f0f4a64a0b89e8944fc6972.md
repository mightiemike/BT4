### Title
Tombstone-accumulation gate in `check_flush_trigger` can indefinitely suppress in-mem accounts-index eviction, causing unbounded memory growth per bin - ([File: accounts-db/src/accounts_index/in_mem_accounts_index.rs])

### Summary
`InMemAccountsIndex::check_flush_trigger` (`accounts-db/src/accounts_index/in_mem_accounts_index.rs:1306-1337`) gates the low-free-entries eviction signal behind a growth check: if a bin's hashmap `capacity` is below `threshold_entries_per_bin.high_water_mark`, the function unconditionally returns `false`, regardless of how low `free_entries` is. The design assumes tombstone-caused capacity loss will eventually force the entry count `len()` past `high_water_mark` and be "caught later" by the count-based backstop. However, entries can be removed from the bin's map via `remove_if_slot_list_empty` (`in_mem_accounts_index.rs:372-386`), invoked from `AccountsIndex::handle_dead_keys` (`accounts_index.rs:325-343`) during normal clean/purge/shrink operations (`accounts_db.rs:1391-1450`, `accounts_db.rs:2673-2687`), independent of `check_flush_trigger` or eviction. This means a bin whose live entry count stays permanently below the high-water mark can still accumulate tombstones from routine account deletion, yet the eviction/reallocation path (`reallocate_to_clear_tombstones`, `in_mem_accounts_index.rs:1464-1491`) is only reachable through `evict_from_cache`, which is only invoked when `check_flush_trigger` returns `true`. Because the gate short-circuits before the free-entries check whenever `capacity < high_water_mark`, and capacity for such a bin may never grow (since `len()` also never grows), the condition can persist indefinitely — closely paralleling the `_setRewardsDuration` pattern where a guard meant to gate a rare state ends up almost never releasing due to routine, frequent activity.

### Finding Description
`check_flush_trigger` is the sole entry point that authorizes both dirty-entry write-through/eviction and, downstream, the tombstone-clearing `reallocate_to_clear_tombstones` call in `evict_from_cache` (`in_mem_accounts_index.rs:1444-1455`, `1493-1533`). Its logic:
```
if let Some(thresholds) = &self.storage.threshold_entries_per_bin
    && capacity < thresholds.high_water_mark
{
    return false;
}
```
(`in_mem_accounts_index.rs:1315-1319`)

This early-return is justified in the code comment by the claim that "if tombstones do force a doubling before `len` crosses HWM, the count check catches it later once `len` grows past HWM." That reasoning depends on `len()` (the live entry count) eventually crossing `high_water_mark`. But entries are removed from the same `map_internal` HashMap by `remove_if_slot_list_empty` whenever an account's slot list becomes empty (i.e., account fully purged/cleaned/shrunk-away) — a routine, frequent event during clean/shrink/purge operations that happens completely outside of, and unsynchronized with, `check_flush_trigger`/eviction. For a bin whose steady-state distinct-pubkey count never needs to exceed `high_water_mark` (e.g., a validator with an account working set below the configured per-bin threshold, but high account churn/turnover from opens+closes), `len()` never crosses `high_water_mark`, so the gate at line 1316 remains permanently `true`, and `check_flush_trigger` never returns `true` via the free-entries path for that bin. Consequently `reallocate_to_clear_tombstones` — the only mechanism that rebuilds the map to reclaim tombstone-occupied capacity — is never invoked for that bin, even though `should_evict_based_on_free_entries` (line 133-143) would otherwise correctly flag it.

### Impact Explanation
Unlike a functional/liveness bug in a smart-contract owner function, this manifests as accumulating, unreclaimed hashmap tombstones in specific accounts-index bins on a live validator running with `IndexLimit::Threshold` (disk-index memory threshold mode). Tombstones consume slots in the underlying `hashbrown` table without being counted in `len()`, so the effective usable capacity of that bin degrades over time. This is a disproportionate/unbounded memory cost issue for the in-memory accounts index — the exact category of impact ("disproportionate storage and CPU cost") accepted by the validation rubric — rather than a correctness bug affecting balances or hashes.

### Likelihood Explanation
This requires the `Threshold` index-limit configuration (memory-bounded disk index) to be enabled, and requires a bin whose distinct-pubkey occupancy stays below its configured `high_water_mark` while experiencing repeated account creation/closure (common for ephemeral accounts, e.g., temporary token accounts, program-derived accounts that get closed). This is a plausible but not universally-triggered condition — it depends on the specific per-bin occupancy pattern relative to the configured threshold, which in turn depends on operator-set index-limit config (not a default-always-on path for `InMemOnly`/`Minimal` modes, where `threshold_entries_per_bin` is `None` and the gate does not apply at all, per lines 124-127/134-136).

### Recommendation
Decouple the "avoid premature eviction scanning during initial growth" heuristic from the tombstone/free-entries signal: track tombstone count (or `capacity - len` accumulated since last reallocation) independently of the `capacity < high_water_mark` initial-growth gate, and allow `reallocate_to_clear_tombstones` to fire based on tombstone accumulation alone, regardless of whether `len()` has ever crossed `high_water_mark`. Alternatively, only apply the initial-growth short-circuit once (before the bin has ever reached its target size), and thereafter always evaluate `should_evict_based_on_free_entries` unconditionally.

### Proof of Concept
Not directly reproducible from static analysis alone; a concrete PoC would require: (1) configuring `AccountsIndexConfig::index_limit = IndexLimit::Threshold(...)` with a `high_water_mark` for a bin, (2) inserting and then removing (via `store` + `clean_accounts`/`purge_keys_exact`) enough distinct pubkeys in that specific bin to create tombstones while keeping `len()` always below `high_water_mark`, and (3) observing via `map_internal.read().unwrap().capacity()` that capacity/tombstone count keeps growing while `index.check_flush_trigger()` (per bin) remains `false` indefinitely and `num_hashmap_reallocates` never increments — analogous to the existing unit test `test_check_flush_trigger_below_hwm_gate` (`in_mem_accounts_index.rs:2994-3029`), extended to repeatedly insert-then-remove entries via `remove_if_slot_list_empty` rather than a single insert pass, to show the gate persists across many churn cycles.

**Caveat**: I was not able to fully trace, within the available search budget, whether other periodic maintenance (e.g., `age`-based flush cycles, full index rebuild at snapshot restore, or bin-level "startup" reprocessing) independently resets or bounds tombstone accumulation for bins stuck below `high_water_mark`, which could mitigate or eliminate the practical severity of this finding. This should be verified against the full source before treating this as a confirmed, exploitable resource-exhaustion issue.
