### Title
Unbounded recursion in compiled-class-hash computation over attacker-controlled bytecode segment tree - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
When a class is declared, the sequencer compiles the submitted Sierra program to CASM in a resource-limited subprocess, then computes the compiled class hash of the returned `CasmContractClass` in the *parent* process via `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash` → `bytecode_hash_node`. `bytecode_hash_node` recurses once per nesting level of the `NestedIntList` bytecode-segment-length tree that the untrusted compiler subprocess produced for the class. This recursive hashing step runs unprotected by the CPU/memory `ResourceLimits` that only apply to the child compilation subprocess, so a Sierra program engineered to yield a deeply nested segment tree can drive `bytecode_hash_node` to a stack overflow in the sequencer's main class-manager/compiler process — the same bug class as Suricata's CVE-2026-22260 (unbounded recursion during decompression/parsing causing a stack overflow crash).

### Finding Description
- `bytecode_hash_node` is a plain recursive function with no depth bound: [1](#0-0) 
- It is invoked from `bytecode_hash`, which is called by `hash_inner`, which is called by `HashableCompiledClass::hash`, the function that computes a class's `CompiledClassHash`: [2](#0-1) 
- The segment tree it recurses over, `bytecode_segment_lengths: Option<NestedIntList>`, is taken directly from the `CasmContractClass` produced by compiling the submitted Sierra program, with no depth validation: [3](#0-2) 
- `SierraCompiler::compile` performs the actual Sierra→CASM compilation in a subprocess (`self.compiler.compile(class)?`), and only *afterwards*, back in the parent process, calls `.hash(&HashVersion::V2)` on the resulting `CasmContractClass` — i.e., the recursive hashing is not covered by subprocess resource isolation: [4](#0-3) 
- The CPU-time/memory limits (`ResourceLimits`) applied via `rlimit::setrlimit` are set only on the child compiler process before `exec`, not on the parent process that later runs `bytecode_hash_node`: [5](#0-4) [6](#0-5) 
- `ClassManager::add_class` drives this same path for every declared class handled by the class manager component: it compiles via `self.compiler.compile(class.clone())`, which internally performs the vulnerable hash computation: [7](#0-6) 
- Elsewhere in the codebase, the project explicitly acknowledges this bug class matters: the blockifier pre-allocates a large thread stack specifically to avoid native-execution stack overflows from deep recursion, and a code comment in `casm_hash_estimation.rs` notes the estimator "only supports at most one level of segmentation" — implying the actual segment tree depth is not itself bounded to one level, only the *estimator's* assumption is: [8](#0-7) [9](#0-8) 

An attacker who declares a class (i.e., an unprivileged declarer, one of the explicitly in-scope reachable roles) can submit Sierra source producing a CASM program whose bytecode is decomposed by the compiler into a deeply and unevenly nested function/branch segment structure (e.g., via many levels of nested function calls/branches within the contract's compiled bytecode size limit). Once this class is compiled, every sequencer node that processes the same Declare transaction (gateway validation and/or class manager) will independently execute the same recursive `bytecode_hash_node` walk over the resulting segment tree and crash with a stack overflow.

### Impact Explanation
A stack overflow in `bytecode_hash_node` aborts the sequencer process (Rust stack overflows are non-recoverable process aborts, not catchable panics). Because every honest node performs the identical compiled-class-hash computation over the identical CASM segment tree when it independently validates/compiles the same declared class, this is a deterministic, network-wide crash trigger reachable purely from a single class declaration — not a single-operator or single-peer bug. This can repeatedly take down sequencer gateway/class-manager processes across the network, matching the "network unable to confirm new transactions" impact criterion.

### Likelihood Explanation
Likelihood is high: a class declaration is a normal, permissionless, unprivileged transaction type (`DECLARE`), requiring no special access. The only constraint is producing Cairo/Sierra source that compiles within the network's `max_bytecode_size` limit while yielding a deeply nested bytecode segmentation (achievable by writing many small nested functions/branches, which is a source-level construct fully controlled by the declarer).

### Recommendation
Bound the recursion in `bytecode_hash_node` (and its Cairo/OS counterparts `bytecode_hash_internal_node` in the Poseidon/Blake compiled-class-hash Cairo modules) either by converting to an explicit iterative/worklist algorithm, or by enforcing and validating a maximum nesting depth on `NestedIntList`/`bytecode_segment_lengths` immediately after compilation and before any hashing occurs, rejecting classes whose segment tree exceeds the bound. Additionally, apply the same CPU-time/memory/stack constraints used for the compiler subprocess to the post-compilation hashing step, or move hashing into the resource-limited subprocess itself so a crash there does not affect the parent process.

### Proof of Concept
1. Author a Cairo 1 contract whose logic is expressed as a long chain of many small, distinctly-branching nested functions (e.g., thousands of levels of `if`/nested function calls), staying within `DEFAULT_MAX_BYTECODE_SIZE` total instructions but maximizing the depth of the compiler-generated bytecode segmentation tree.
2. Compile it with the sequencer's `SierraToCasmCompiler` (as done by `SierraCompiler::compile` / `ClassManager::add_class`) to obtain a `CasmContractClass` with a deeply nested `bytecode_segment_lengths: Some(NestedIntList::Node(...))` tree of matching depth.
3. Submit this class via a `DECLARE` transaction to the network.
4. Every node's `SierraCompiler::compile` path calls `executable_class.hash(&HashVersion::V2)`, which walks `bytecode_hash_node` recursively to the tree's depth; with sufficiently many nesting levels, the process stack is exhausted and the sequencer process aborts.

Note: I was not able to directly execute the compiler to empirically measure how deep a segment tree the reference `cairo-lang-starknet-classes` crate produces for a given source pattern, nor pin down the exact per-frame stack cost of `bytecode_hash_node`; a background agent with build/run access should compile a maximal-depth test contract and confirm the crash empirically to fully validate exploitability at production `max_bytecode_size` limits.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}

    /// Apply the resource limits to a given command object. This moves the [`ResourceLimits`]
    /// struct into a closure that is held by the given command. The closure is executed in the
    /// child process spawned by the command, right before it invokes the `exec` system call.
    pub fn apply(self, command: &mut Command) -> &mut Command {
        if self.cpu_time.is_none() && self.file_size.is_none() && self.memory_size.is_none() {
            return command;
        }
        unsafe {
            // The `pre_exec` method runs a given closure after the parent process has been forked
            // but before the child process calls `exec`.
            //
            // This closure runs in the child process after a `fork`, which primarily means that any
            // modifications made to memory on behalf of this closure will **not** be visible to the
            // parent process. This environment is often very constrained. Normal operations--such
            // as using `malloc`, accessing environment variables through [`std::env`] or acquiring
            // a mutex--are not guaranteed to work, because after `fork`, only one thread exists in
            // the child process, while there may be multiple threads in the parent process.
            //
            // This closure is considered safe for the following reasons:
            // 1. The [`ResourceLimits`] struct is fully constructed and moved into the closure.
            // 2. No heap allocations occur in the `set` method.
            // 3. `setrlimit` is an async-signal-safe system call, which means it is safe to invoke
            //   after `fork`. This is established in the POSIX `fork` specification:
            //   > ... the child process may only execute async-signal-safe operations until such
            //    time as one of the `exec` functions is called.
            //   (See <https://pubs.opengroup.org/onlinepubs/9699919799/functions/fork.html>)
            command.pre_exec(move || self.set())
        }
    }
