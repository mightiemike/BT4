### Title
Permissionless `HandleLegacyUserMessage` in WebAPI capability gateway handler fans out unauthenticated requests to every DON node - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The WebAPI capabilities gateway `handler.HandleLegacyUserMessage` accepts a signed `web_api_trigger` message from any sender and, after only checking payload shape and message staleness, forwards the request to **every** node in the DON — with an explicit `// TODO: apply allowlist and rate-limiting here` marking the missing authorization check.

### Finding Description
`handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` validates that the payload can be unmarshalled into a `webapicap.TriggerRequestPayload`, checks that `Timestamp != 0`, and checks that the message is not older than `MaxAllowedMessageAgeSec`. It then checks `msg.Body.Method != MethodWebAPITrigger`, and if it matches, proceeds to broadcast the request to `don.SendToNode` for every member of `h.donConfig.Members`:

```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
    ...
}
...
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()

// Send original request to all nodes
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [3](#0-2) 

Unlike the sibling `functions` handler, which enforces an `allowlist.Allow(sender)` check and a `userRateLimiter.Allow(...)` check before doing any work [4](#0-3) , the WebAPI capabilities `HandlerConfig` struct only contains `NodeRateLimiter` (limiting outbound gateway→node HTTP calls) and `MaxAllowedMessageAgeSec`. It has no allowlist and no per-sender/user rate limiter field at all [1](#0-0) .

This means any address that can produce a validly-signed `api.Message` (the message just needs a valid ECDSA signature — `msg.Validate()` only checks signature correctness, not sender identity against any permission list) can repeatedly call the gateway's `/user` HTTP endpoint with `web_api_trigger` messages. Each such call:
- Stores an entry in `h.savedCallbacks` (bounded eventually by pruning, but consumes memory until then),
- Triggers a JSON-RPC/websocket write to **every DON node** via `don.SendToNode`, unconditionally, with no cost or per-sender throttling.

This is directly analogous to the reported `Middleware.sendCurrentOperatorsKeys()` issue: a state-changing/resource-consuming operation that fans out to a distributed set of privileged actors (there: Ethereum gateway/bridge outbound channel; here: every DON node) is reachable by any unauthenticated/unprivileged caller, with the missing-check explicitly flagged as a TODO in the source.

### Impact Explanation
An unprivileged user can repeatedly invoke this handler to flood every node of a DON with WebAPI trigger requests, forcing all DON nodes to process (and workflow engines to attempt to execute) attacker-controlled trigger payloads. This can cause resource exhaustion on DON nodes, workflow engine noise/log spam, and denial-of-service pressure on the entire DON, not just the gateway. Because it fans out to *all* DON members simultaneously, the blast radius is the full DON rather than a single node.

### Likelihood Explanation
Likelihood is high: the only requirements are producing a validly-signed `api.Message` (attacker can sign with any key they control, since there is no allowlist gating signer identity) and a `Timestamp` within `MaxAllowedMessageAgeSec`. No balance, fee, or allowlist gating exists for this handler, and the missing control is explicitly marked as an unresolved `TODO` in the code, confirming this is a known, unaddressed gap in production code.

### Recommendation
Add an allowlist check (as already done in the `functions` handler via `h.allowlist.Allow(sender)`) and a per-sender rate limiter to `handler.HandleLegacyUserMessage` before forwarding requests to `don.SendToNode`. Consider also capping requests per DON per time window and validating that the DON actually accepts triggers from arbitrary senders (vs. only from workflow owners/registered senders), mirroring the workflow registry / signer allowlist pattern used elsewhere in the codebase (e.g. `UpdateAllowedSignersOp` in `deployment/cre/workflow_registry/v2/changeset/operations/contracts/configure_workflow_registry_ops.go`).

### Proof of Concept
1. Generate an ECDSA keypair (no registration/allowlisting needed).
2. Construct an `api.Message` with `Body.Method = "web_api_trigger"`, a valid `webapicap.TriggerRequestPayload` (with current `Timestamp`), and any `DonId` known to be served by a gateway.
3. Sign the message with the generated key (`msg.Sign(key)`), matching the flow used in tests such as `triggerRequest` in `core/services/gateway/handlers/capabilities/handler_test.go` (lines 192-233).
4. Submit the signed legacy request repeatedly (e.g., via `POST /user` on the gateway HTTP server, as demonstrated in `core/scripts/gateway/client/send_request.go`).
5. Observe that `HandleLegacyUserMessage` accepts the message (no allowlist rejection possible) and calls `don.SendToNode` for every configured DON member, for each repeated submission, with no fee or fine-grained per-sender throttling — demonstrating the permissionless fan-out to the entire DON.
