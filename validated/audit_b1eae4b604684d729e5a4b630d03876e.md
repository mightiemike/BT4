### Title
Removed multisig signer's stale approval still counts toward execution threshold - (File: `mainnet/contracts/dao/dao-multisig.clar`)

### Summary
`dao-multisig.clar` binds signer approvals to a proposal at the moment `approve` is called, but never re-validates the signer's status when the proposal is later executed. If a signer is removed via `remove-signer` after approving a pending proposal, `execute` still counts that stale approval toward the required threshold, exactly mirroring the reported bug class where a caller's privileged status is captured at initiation time and never revalidated at completion time.

### Finding Description
`approve` appends `tx-sender` to the proposal's `approvals` list after only checking `is-signer tx-sender` at that instant: [1](#0-0) 

`remove-signer` deletes the address from the `signers` map and decrements `signer-count`, but does not touch any `proposals` entries that already contain that address in their `approvals` list: [2](#0-1) 

`execute` then determines whether the threshold is met purely from the length of the stored `approvals` list, without re-checking that each entry is still a current signer: [3](#0-2) 

This is the same class of bug as the reported issue: a value (the caller's authorized role/status) is captured and relied upon at one point in time (`approve`), the source of that authorization moves (`remove-signer` revokes the role), and a later privileged action (`execute`) still trusts the stale captured value instead of revalidating current status.

### Impact Explanation
`execute` triggers `contract-call? .dao-executor execute-proposal script`, which runs an arbitrary DAO-approved script with full DAO privileges. If a proposal reaches the configured threshold partly or wholly through approvals from signers who have since been removed (e.g., due to compromised keys, role rotation, or intentional removal), the proposal can still execute even though the *current* signer set never actually reached consensus. Since DAO-executed scripts can reconfigure protocol parameters, assets, or treasury operations, this can lead to unauthorized privileged actions that were not actually approved by the legitimate current quorum, creating a path to fund freezing or protocol-level manipulation without requiring compromise of any currently-valid signer key.

### Likelihood Explanation
This requires only routine multisig operations: a normal proposal approval followed by a normal signer removal (e.g., during signer-set rotation, which is an expected administrative action) while the proposal is still pending. No malicious collusion beyond the removed signer's already-cast approval is needed, and the flaw is deterministic — any time a signer is removed after approving a still-pending proposal, that approval remains counted.

### Recommendation
In `execute` (and optionally `approve`), filter/re-validate the `approvals` list against the current `signers` map before comparing its length to `current-threshold`, e.g. by counting only entries for which `is-signer` is still true, or by pruning a removed signer's approvals from all pending proposals inside `remove-signer`.

### Proof of Concept
1. Signers {A, B, C}, threshold = 2.
2. A calls `propose` creating proposal `id`, `approvals = [A]`.
3. A calls `approve(id)` — no-op here since A is proposer; assume B also calls `approve(id)` → `approvals = [A, B]`, reaching threshold 2.
4. DAO calls `remove-signer(B)` because B's key is being rotated — `signers` map no longer contains B, `signer-count` decreases, but proposal `id`'s `approvals` list `[A, B]` is untouched.
5. Any current signer (e.g., A) calls `execute(id, script)`. The check `(>= approvals current-threshold)` uses `(len (get approvals proposal))` = 2, which is `>= 2`, so execution succeeds even though only one currently-valid signer (A) actually stands behind the approval — B's revoked approval still counts. [3](#0-2)

(define-public (approve (id uint))
  (let ((proposal   (unwrap-panic (map-get? proposals id)))
        (approvals  (get approvals proposal))
        (napprovals (unwrap-panic (as-max-len? (append approvals tx-sender) u20))))
    (try! (check-signer-auth))

    ;; Check expiration first (fail-fast)
    (asserts! (< stacks-block-time (get expires-at proposal)) ERR-PROPOSAL-EXPIRED)

    (asserts! (and
        (not (get executed proposal))
        (is-none (index-of approvals tx-sender))) 
      ERR-SANITY-PROPOSAL)
    
    (map-set proposals id (merge proposal { approvals: napprovals }))
    (ok true)))

(define-public (execute (id uint) (script <proposal-script>))
  (let ((proposal (unwrap-panic (map-get? proposals id)))
        (created-at (get created-at proposal))
        (expires-at (get expires-at proposal))
        (mature-at (+ created-at TIMELOCK))
        (current-threshold (var-get threshold))
        (approvals (len (get approvals proposal))))
    (try! (check-signer-auth))

    ;; check expiration
    (asserts! (< stacks-block-time expires-at) ERR-PROPOSAL-EXPIRED)

    (asserts! 
      (and
        (not (get executed proposal))
        (is-eq (contract-of script) (get script proposal))
        (>= approvals current-threshold)
        (or
          (>= stacks-block-time mature-at)
          (get urgent proposal)))
      ERR-SANITY-PROPOSAL)

    (map-set proposals id (merge proposal { executed: true }))
    (contract-call? .dao-executor execute-proposal script)))
