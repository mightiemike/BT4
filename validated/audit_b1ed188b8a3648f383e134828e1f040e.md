### Title
Inconsistent originEnergyUsage reporting between GetTransactionInfoById and GetTransactionInfoByBlockNum for the same receipt - ([File: chainbase/src/main/java/org/tron/core/store/TransactionRetStore.java])

### Summary
`TransactionRetStore.getTransactionInfo(byte[] key)` clears `receipt.originEnergyUsage` whenever `energyUsageTotal == 0` and `originEnergyUsage > 0`, but `TransactionRetStore.getTransactionInfoByBlockNum(byte[] key)` returns the raw, unmodified `TransactionRetCapsule` with no equivalent normalization. Because `GetTransactionInfoByIdServlet` uses the former path and `GetTransactionInfoByBlockNumServlet` uses the latter, the same on-disk transaction receipt is presented with two different `originEnergyUsage` values depending on which read-only API is queried.

### Finding Description
`GetTransactionInfoByIdServlet.doGet/doPost` calls `wallet.getTransactionInfoById(...)`, which is backed by `TransactionRetStore.getTransactionInfo(byte[] key)`. That method iterates the `TransactionInfo` list, and for the matching id it applies a "dirty origin usage" fix: if `receipt.getEnergyUsageTotal() == 0 && receipt.getOriginEnergyUsage() > 0`, it rebuilds the receipt with `clearOriginEnergyUsage()` [1](#0-0) .

`GetTransactionInfoByBlockNumServlet.doGet/doPost` calls `wallet.getTransactionInfoByBlockNum(num)`, which is backed by `TransactionRetStore.getTransactionInfoByBlockNum(byte[] key)`. This method simply deserializes the stored `TransactionRetCapsule` and returns it verbatim, with no normalization of `originEnergyUsage` [2](#0-1) .

Consequently, for a transaction whose receipt has `energyUsageTotal == 0` and `originEnergyUsage > 0` ("dirty" state), querying by transaction id yields `originEnergyUsage == 0` while querying by block number yields the original non-zero `originEnergyUsage` for the exact same underlying receipt object. There is no reconciliation, versioning, or shared normalization layer between these two read paths — the divergence is baked into `TransactionRetStore` itself, and both HTTP servlets pass the underlying protobuf field through unchanged to their JSON output [3](#0-2) [4](#0-3) .

### Impact Explanation
Any unprivileged caller of these public read-only HTTP endpoints can observe two different values for the same accounting field (`originEnergyUsage`) for the same settlement event, simply by choosing which endpoint to query. Off-chain systems (exchanges, indexers, energy-rental/reimbursement services) that rely on `originEnergyUsage` for fee/energy reconciliation can be made to see inconsistent data depending on which API path they integrate with, enabling arbitrage between systems or disputed/duplicated reimbursement claims based on which "official" value is presented. This does not alter on-chain state or actual fees charged — it is a divergence in the informational read APIs, not a fund-transfer or consensus bug.

### Likelihood Explanation
Trivially reproducible and fully attacker-controlled from a read perspective: it requires no privilege beyond making two ordinary public HTTP GET/POST calls to the full node. The precondition (`energyUsageTotal == 0 && originEnergyUsage > 0`) is a specific but real receipt state that the code explicitly calls "dirty," implying it does occur in practice; every transaction naturally matching that receipt state, once historical data is retained by the node, is affected each time it is queried.

### Recommendation
Move the "dirty origin usage" normalization out of `getTransactionInfo` and into a shared helper applied uniformly by both `getTransactionInfo(byte[] key)` and `getTransactionInfoByBlockNum(byte[] key)` (or normalize once at write time when the receipt is persisted), so that every read path returns a consistent, deterministic receipt for the same transaction.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/db/TransactionRetStoreDivergenceTest.java
@Test
public void testOriginEnergyUsageDivergenceBetweenReadPaths() throws Exception {
  // Craft a TransactionInfo whose receipt has energyUsageTotal == 0, originEnergyUsage > 0
  Protocol.ResourceReceipt receipt = Protocol.ResourceReceipt.newBuilder()
      .setEnergyUsageTotal(0)
      .setOriginEnergyUsage(1000L)
      .build();
  Protocol.TransactionInfo txInfo = Protocol.TransactionInfo.newBuilder()
      .setId(txId)
      .setReceipt(receipt)
      .build();
  // Persist via TransactionRetCapsule at blockNum, and index txId -> blockNum in transactionStore

  TransactionInfoCapsule byId = transactionRetStore.getTransactionInfo(txId.toByteArray());
  TransactionRetCapsule byBlockNum =
      transactionRetStore.getTransactionInfoByBlockNum(ByteArray.fromLong(blockNum));
  Protocol.TransactionInfo infoFromBlockNum = byBlockNum.getInstance()
      .getTransactioninfoList().stream()
      .filter(ti -> ti.getId().equals(txId)).findFirst().get();

  // Assert divergence: byId has originEnergyUsage cleared, byBlockNum retains it
  assertEquals(0, byId.getInstance().getReceipt().getOriginEnergyUsage());
  assertEquals(1000L, infoFromBlockNum.getReceipt().getOriginEnergyUsage());
  // This inequality demonstrates the same receipt yields two different accounting values
  assertNotEquals(byId.getInstance().getReceipt().getOriginEnergyUsage(),
      infoFromBlockNum.getReceipt().getOriginEnergyUsage());
}
```
Expected result: the assertion `assertNotEquals(...)` passes, proving the two API paths return different `originEnergyUsage` for the identical stored receipt.
