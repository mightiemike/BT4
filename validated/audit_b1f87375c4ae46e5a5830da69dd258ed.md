### Title
Excess deposit sent to `AddressRegistrar::register` is not refunded and is permanently retained by the contract - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar` contract, deployed alongside the Wallet Contract to let eth-implicit accounts resolve to named NEAR accounts, accepts an attached deposit in its `register` method and only verifies that the deposit is *at least* the required storage cost (`given_deposit < required_deposit`), never that it is *exactly* equal. On the success path (new address registered), any excess deposit above `required_deposit` is silently kept by the contract instead of being refunded to the caller.

### Finding Description
`register` computes `required_deposit` from the storage bytes needed to store the `address -> account_id` mapping, then checks: [4](#0-3) 
If `given_deposit >= required_deposit` the call proceeds. On the `Entry::Vacant` (successful registration) branch, the entry is simply inserted with no reference to `given_deposit` at all — the full attached deposit, including any excess above `required_deposit`, becomes part of the contract account's balance permanently: [5](#0-4) 
Only the `Entry::Occupied` (collision) branch explicitly refunds the deposit, and even then it refunds the *entire* `given_deposit`, not the excess: [6](#0-5) 
This is the same root-cause pattern as the reported Footium issue: a `<` (or here `<`) comparison instead of an exact-equality/refund-the-difference model, causing any caller-supplied excess to be trapped in the contract with no code path to reclaim it. This is corroborated by the existing test, which explicitly asserts the excess is retained by the contract (`post_tx_account_balance - pre_tx_account_balance >= deposit_amount`, i.e., the entire attached deposit stays even though only `required_deposit` was needed): [7](#0-6) 

### Impact Explanation
Any unprivileged account (an EOA/eth-implicit account owner, or their relayer via the Wallet Contract's `rlp_execute`, or any direct NEAR caller) that attaches more than the exact storage cost when calling `register` permanently loses the difference — the excess NEAR becomes unrecoverable to the caller and is retained by the `AddressRegistrar` contract account. There is no owner/admin withdrawal mechanism shown in this contract, so the excess is effectively frozen funds from the caller's perspective. Because callers (e.g., relayers acting on behalf of eth-implicit account users through the Wallet Contract) may not control the exact deposit amount precisely, or may over-provision defensively, this is a realistic path to accidental fund loss triggered purely by a single transaction/contract call — no privileged access required.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `register` is a `#[payable]` public method invocable by any account (directly or through the Wallet Contract's cross-contract call flow), and nothing in the interface signals to callers that they must supply the *exact* deposit — the natural expectation from `#[payable]` methods that only check a minimum is that any excess would be refunded (as is done elsewhere in this same wallet-contract system for failed cross-contract calls, e.g. `CallerDeposit`/`rlp_execute_callback` refund-on-failure logic at [8](#0-7) ). A caller rounding up their deposit (e.g., using a fixed constant instead of computing the exact byte cost) will trigger fund loss on every successful registration.

### Recommendation
Change the check in `register` to refund the excess rather than silently absorb it: after validating `given_deposit >= required_deposit`, on the `Entry::Vacant` success path, if `given_deposit > required_deposit`, issue a transfer of `given_deposit - required_deposit` back to `env::predecessor_account_id()` (mirroring the refund pattern already used in the `Entry::Occupied` branch), so only the exact storage cost is retained by the contract.

### Proof of Concept
1. Deploy `AddressRegistrar` (as done for the Wallet Contract test harness).
2. Compute `required_deposit` for a target `account_id` as `storage_byte_cost * (20 + len(account_id))`.
3. Call `register(account_id)` attaching `deposit_amount > required_deposit` (as in the existing `test_register_without_deposit` test, which attaches a fixed `320000000000000000000` yoctoNEAR regardless of the exact byte cost) — see [9](#0-8) .
4. Observe that the registrar's account balance increases by the *entire* `deposit_amount`, not by `required_deposit`; the caller's excess (`deposit_amount - required_deposit`) is never returned, confirmed by the assertion `post_tx_account_balance - pre_tx_account_balance >= deposit_amount.as_yoctonear()` rather than an exact-equality check.

/// Test asserting the address registrar requires a deposit.
#[tokio::test]
async fn test_register_without_deposit() -> anyhow::Result<()> {
    let TestContext { worker, address_registrar, .. } = TestContext::new().await?;

    let method = "register";
    let args = br#"{"account_id": "birchmd.near"}"#;
    let result = address_registrar.call(method).args(args.to_vec()).transact().await?;
    assert!(result.is_failure(), "Call without deposit must fail");

    let pre_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    let deposit_amount = NearToken::from_yoctonear(320000000000000000000);
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output.as_deref(), Some("0x4bfcff9a964925adf801c866f6ada98bd7ec40ca"));
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    // Sending a duplicate transaction does not take the deposit again.
    let pre_tx_account_balance = post_tx_account_balance;
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output, None);
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    Ok(())
}
