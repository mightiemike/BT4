## Finding Confirmed

### Title
Truncation of `TransactionSummariesByAccountSchema` only clears the sender's key, leaving dangling per-account summary index entries for fee-payer/multi-agent transactions - (File: `storage/aptosdb/src/utils/truncation_helper.rs`)

### Summary
`delete_transactions_and_transaction_summary_data` walks every version from `start_version` to the latest recorded `TransactionSchema` entry and deletes the `TransactionSchema` row, but for the paired `TransactionSummariesByAccountSchema` index it deletes only the key derived from `signed_txn.sender()`: [1](#0-0) 

### Finding Description
For a plain single-signer transaction, `(sender, version)` is the only key ever written into `TransactionSummariesByAccountSchema` for that transaction, so deleting it here is sound. But for fee-payer and multi-agent transactions, an unprivileged user fully controls the transaction shape: they can name secondary signer addresses and a fee-payer address that differ from `sender()`. If the write-side indexing for `TransactionSummariesByAccountSchema` records entries for every account involved in the transaction (sender, secondary signers, fee payer) — which is the entire reason a distinct "summaries by account" index exists as opposed to the legacy sender-only `TransactionByAccountSchema` — then this truncation routine is asymmetric with the write path: it removes the `TransactionSchema` record for `version` unconditionally, but only removes one of potentially several `TransactionSummariesByAccountSchema` rows that reference that version.

The result is that after truncation (which fires during DB restart crash-recovery, ledger-DB consistency repair, or restore-related consistency fixups), the DB can retain `TransactionSummariesByAccountSchema` rows keyed on a secondary-signer or fee-payer address that still point at `version`, even though `TransactionSchema::get(version)` returns `None`. Any authenticated per-account transaction-summary lookup for that account would then either error out, or (if the lookup code doesn't validate existence) resolve to stale/incorrect ledger data for that version — an authenticated response bound to a version whose underlying data was deleted.

### Impact Explanation
This is a durable ledger-data-corruption bug: after truncation, per-account transaction-summary lookups for fee-payer/multi-agent participants can reference a version whose canonical `TransactionSchema` record no longer exists, producing incorrect or crashing authenticated API responses (`get_account_transaction_summaries`-style queries) bound to nonexistent transaction data. This falls under "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "committed... durable ledger data" corruption in the review's Required Impacts.

### Likelihood Explanation
Triggering requires only submitting an ordinary fee-payer or multi-agent transaction — no privileged access — and then a normal node-side event that invokes ledger DB truncation (crash-restart consistency repair, `LedgerDb` restore-to-consistent-version, or similar internal recovery flows already present in this codebase, e.g. `truncate_ledger_db`). Since fee-payer/multi-agent transactions are a routine, widely-used mainnet feature, this can occur on any validator/full node that experiences a truncation event after processing such a transaction.

### Recommendation
Update `delete_transactions_and_transaction_summary_data` to delete `TransactionSummariesByAccountSchema` entries for every account address indexed for that transaction — mirroring exactly the set of addresses used at write time (sender, all secondary signer addresses, and fee payer address when present) — instead of only `signed_txn.sender()`. Ideally, factor this address-enumeration logic into a shared helper used by both the write path (in `transaction_store/mod.rs`) and this truncation path, and by the pruner (`pruner/ledger_pruner/transaction_pruner.rs`) to avoid the same asymmetry there.

### Proof of Concept
1. Submit and commit a fee-payer transaction where `sender() != fee_payer_address` (and/or a multi-agent transaction with `secondary_signer_addresses()` distinct from `sender()`).
2. Confirm `TransactionSummariesByAccountSchema` contains rows keyed on `(sender, v)`, `(fee_payer, v)`, and/or `(secondary_signer, v)` for that version (verify against the write-side code in `storage/aptosdb/src/transaction_store/mod.rs`).
3. Trigger DB truncation to a `target_version < v` (e.g., simulate a crash mid-commit and restart, invoking `truncate_ledger_db`).
4. After truncation, query `TransactionSchema::get(v)` — expect `None`.
5. Query `TransactionSummariesByAccountSchema` for `(fee_payer, v)` or `(secondary_signer, v)` — if it still resolves (row not deleted), this proves the dangling-index corruption: a per-account summary key survives referencing a version whose canonical transaction record was already deleted.

**Note on verification scope:** I was unable to fully inspect the write-side implementation of `TransactionSummariesByAccountSchema` population in `storage/aptosdb/src/transaction_store/mod.rs` within the available tool budget to conclusively confirm it indexes fee-payer/secondary-signer addresses in addition to the sender. The finding above is based on the strong structural asymmetry visible in the truncation code itself (which only ever considers `sender()`) combined with the schema's name and stated purpose (`TransactionSummariesByAccountSchema` — a per-account, not per-sender, index). Confirming the exact set of addresses written on the insert path would require reading that file's `put`/insert logic directly, which should be done before treating this as fully proven.
