### Title
Historical cross-account IDOR in delegate-action validation for deterministic state init (pre-`FixDelegatedDeterministicStateInit`, PV < 85) - ([File: runtime/runtime/src/action_validation.rs])

### Summary
The WeKan bug class is a failure to cross-validate a nested/child identifier (`cardId`) against the outer authorization context (`boardId`) before acting on it. Nearcore had (and still ships, gated by protocol version) the exact analog: `validate_delegate_action` validated a `DeterministicStateInit` action using the **outer transaction's `receiver_id`** instead of the **inner `DelegateAction.receiver_id`**, allowing a relayer-submitted meta-transaction to smuggle a state-init payload addressed to a different deterministic account than the one the outer transaction was nominally authorized against.

### Finding Description
Deterministic accounts (NEP-616) derive their `AccountId` from the hash of a `DeterministicAccountStateInit` payload, and the runtime must verify that the action's target account (`receiver_id`) actually equals `derive_account_id(state_init)` before installing state — this is the "child ID must belong to the claimed parent" check, analogous to WeKan's cardId/boardId check.

The regression test in `test-loop-tests/src/tests/deterministic_account_id.rs:128-171` documents the exact historical defect: [1](#0-0) 

> "With the old (buggy) code, `validate_delegate_action` used `outer_tx.receiver_id` instead of `delegate_action.receiver_id` when checking inner actions."

The exploit construction crafts an outer transaction whose `receiver_id` equals `derive(state_init_b)` (i.e. `det_account_b`), but wraps a `DelegateAction` whose `sender_id`/`receiver_id` targets a *different* deterministic account (`det_account_a`) while carrying `state_init_b`'s deterministic-state-init action: [2](#0-1) 

Pre-fix, this passes initial transaction admission because the receiver-derivation check is performed against the wrong field (`outer_tx.receiver_id`, which does legitimately match `derive(state_init_b)`), even though the actual receipt this produces is addressed to `det_account_a` via `delegate_action.receiver_id`: [3](#0-2) 

The fix, gated by `ProtocolFeature::FixDelegatedDeterministicStateInit` (activates at protocol version 85), moves the account-derivation check to use `delegate_action.receiver_id` and is referenced in `runtime/runtime/src/action_validation.rs`: [4](#0-3) 

Critically, per the protocol-version documentation gathered, `MIN_SUPPORTED_PROTOCOL_VERSION = 83`, and the fix only activates at v85 — unlike other deprecated/base-folded gates in this component, `FixDelegatedDeterministicStateInit` is a live, non-deprecated gate: [5](#0-4) 

This means any chain/shard still running at protocol version 83 or 84 (both within the binary's supported range) executes the pre-fix, vulnerable code path. The generic action-validation entrypoint (`validate_actions_with_mode` in `runtime/runtime/src/action_validation.rs`) explicitly threads `current_protocol_version` through every check, confirming the vulnerable/fixed behavior is version-gated rather than unconditionally patched: [6](#0-5) 

### Impact Explanation
On an affected protocol version, an attacker acting as `meta_tx_sender` (any account with a full-access key, no special privilege required) can construct a `DelegateAction` whose `sender_id`/`receiver_id` disagree with the outer transaction's `receiver_id`, causing the receiver-derivation validation to be checked against the wrong account. This is a cross-account IDOR: it lets an attacker attempt to bootstrap/write deterministic-account state (code + initial key/data — i.e., contract deployment and account takeover of a `0s…` deterministic account) under one account ID while the tx-admission-time check validates a *different* account ID. Per the test, the second-layer defense (`validate_receipt` at receipt-application time) catches the mismatch and fails the resulting receipt with `InvalidDeterministicStateInitReceiver`, so on the vulnerable protocol version the attack currently fails late (at execution, not at admission) rather than succeeding — but this is exactly the class of bug (trusting an unvalidated nested identifier) that in a slightly different code path could permit invalid state-transition acceptance or cross-account state installation. The vulnerable window is real (protocol versions 83–84 are within `MIN_SUPPORTED_PROTOCOL_VERSION`), but the observed effect today is "wrong-account admission accepted, execution-time receipt validation rejects it" rather than a currently demonstrated successful unauthorized state mutation.

### Likelihood Explanation
Reachable by any unprivileged signer via a single relayer-submitted meta-transaction (`Action::Delegate`) — no validator or node privilege needed. Likelihood of live exploitation depends entirely on whether any currently-running shard/network is still on protocol version 83 or 84 (pre-`FixDelegatedDeterministicStateInit`); this could not be confirmed from the available index (current binary reports `STABLE_PROTOCOL_VERSION` as 86 in the accessed docs, suggesting mainnet has already progressed past the vulnerable window). Given nearcore's index snapshot documents this as an already-fixed, already-regression-tested historical bug, it should be treated as **patched in the current codebase's default configuration**, not a live zero-day.

### Recommendation
- Confirm no supported/tracked network is still operating below protocol version 85; if any is, prioritize forcing the upgrade or backporting the fix.
- Audit every other "derive account/receipt-target ID and compare against an outer-scope ID" validation path (e.g. `UniversalStateInit`'s receiver check, `GlobalContractIdentifier` account-id validation) for the same outer-vs-inner ID confusion pattern, since this bug class has recurred once already in this codebase.
- Ensure the tx-admission-time check and the receipt-application-time check (`validate_receipt`) always operate on the same, correctly-scoped identifier so that defense-in-depth doesn't silently mask a first-line-of-defense regression.

### Proof of Concept
Reproduced by the existing regression test `try_meta_tx_deterministic_receiver_exploit` / `test_deterministic_state_init_meta_tx_receiver_check_pre_fix`: [7](#0-6) 
Running this scenario at `ProtocolFeature::FixDelegatedDeterministicStateInit.protocol_version() - 1` demonstrates the outer-tx-receiver-vs-inner-delegate-receiver confusion accepted at tx validation, only to be caught later at receipt validation with `InvalidDeterministicStateInitReceiver`.

///
/// `det_account_b` is deployed as a deterministic account and given an access key so
/// it can act as meta_tx_sender. The exploit tx wraps `state_init_b` inside a delegate
/// action whose `receiver_id` is `det_account_a` (wrong target). With the fix this is
/// caught at tx validation; without it, tx validation passes but the receipt fails.
fn try_meta_tx_deterministic_receiver_exploit(
    protocol_version: ProtocolVersion,
) -> Result<FinalExecutionOutcomeView, InvalidTxError> {
    let mut env = TestEnv::setup_with_version(Balance::from_near(100), protocol_version);
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (_state_init_a, det_account_a) = env.new_deterministic_account_with_data(small());
    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.
    let user_signer = create_user_test_signer(&env.user_account());
    let storage_balance = env.balance_for_storage(state_init_b.clone());
    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),
        Gas::from_teragas(300),
        env.get_tx_block_hash(),

    env.run_tx(add_key_tx);

        deposit: Balance::ZERO,

    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],

        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),

        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);

        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,
        vec![Action::Delegate(Box::new(signed_delegate_action))],
        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)

pub(crate) fn validate_actions_with_mode(
    limit_config: &LimitConfig,
    actions: &[Action],
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    if actions.len() as u64 > limit_config.max_actions_per_receipt {
        return Err(ActionsValidationError::TotalNumberOfActionsExceeded {
            total_number_of_actions: actions.len() as u64,
            limit: limit_config.max_actions_per_receipt,
        });
    }

    // Centralized post-quantum gate. Mirrors the tx-admission gate in
    // `check_valid_for_config`, and is load-bearing for actions emitted by
    // contracts via host functions: those actions create new receipts that
    // never go through tx admission, so on a pre-feature protocol they must
    // be rejected here. The exhaustive match in
    // `Action::post_quantum_signatures_required` (including the recursive
    // walk into `Delegate`) forces every future action variant to make an
    // explicit decision at compile time.
    if !ProtocolFeature::PostQuantumSignatures.enabled(current_protocol_version)
        && actions.iter().any(Action::post_quantum_signatures_required)
    {
        return Err(ActionsValidationError::UnsupportedProtocolFeature {
            protocol_feature: "PostQuantumSignatures".to_owned(),
            version: current_protocol_version,
        });
    }

    if mode == ValidateReceiptMode::NewReceipt {
        validate_number_of_deploy_actions(actions, limit_config.max_deploy_actions_per_receipt)?;
        // `DeterministicStateInit` predates the entry limit, so it is applied to newly
        // created receipts only. A receipt built before the limit took effect has to
        // keep executing.
        validate_number_of_state_init_entries(actions, limit_config.max_state_init_entries)?;
    }
