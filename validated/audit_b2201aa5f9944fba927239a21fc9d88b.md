### Title
Panic on empty-calldata L1 handler transaction in message hash and Cende recording code - ([File: crates/starknet_api/src/hash.rs], [File: crates/apollo_batcher/src/cende_client_types.rs])

### Summary
`L1HandlerTransaction::calldata` (`Calldata`, a `Vec<Felt>`) has no non-empty invariant enforced by its type or `Deserialize` impl, exactly like the missing length check in `mbedtls_lms_import_public_key`. Two reachable code paths index/split this vector assuming it always contains at least one element (the `from_address`), without checking length first, causing a panic (crash) when a truncated/empty calldata reaches them.

### Finding Description
`l1_handler_message_hash` unconditionally does `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")` [1](#0-0) . Similarly, `L1ToL2Message::from(L1HandlerTransaction)` in the batcher does `calldata.0[0].try_into().expect(...)` and `calldata.0[1..]` without any length check [2](#0-1) . The codebase itself acknowledges this exact bug class exists: `L1HandlerTransaction::payload_size` had to be patched with `saturating_sub` specifically because "`Calldata` has no non-empty invariant" and an empty calldata "would otherwise underflow ... in release" [3](#0-2) , with an explicit regression test confirming the fix [4](#0-3) . However, that fix only covers `payload_size`; `calc_msg_hash`/`l1_handler_message_hash` and the batcher's `L1ToL2Message` conversion were not fixed and still panic on empty calldata, mirroring the mbedtls pattern where one call site checks the length (analogous to properly-guarded callers) but another (`mbedtls_lms_import_public_key`) reads the fixed header before validating length.

`calc_msg_hash` is called on `L1HandlerTransaction` to compute the L1↔L2 message hash [5](#0-4) , a path reachable whenever a sequencer builds or records an L1 handler transaction that originated from an L1 message with an empty payload (i.e., `calldata` containing zero felts, since only the L1 sender prepends `from_address`; if the original L1 message had zero elements total, i.e., improperly constructed/relayed, calldata length can be 0). The Cende recording path in the batcher is invoked whenever building the pre-confirmed block payload sent to the recording service.

### Impact Explanation
A panic (`.expect()`) on a value derived directly from an L1 message payload will crash the sequencer process handling that transaction. If triggered deterministically for all sequencers processing the same L1 event (which they must, to stay in consensus), this can halt block production network-wide — a "network unable to confirm new transactions" condition. This is reachable without any special privilege: any L1 message can, if constructed with a fully empty payload, produce an `L1HandlerTransaction` with `calldata.len() == 0`.

### Likelihood Explanation
Medium: the sender_address is normally always prepended by the sequencer itself when converting an `EventData`/`MessageFromL1` into `L1HandlerTransaction` (see `From<EventData> for L1HandlerTransaction`) [6](#0-5) , and `From<MessageFromL1> for L1HandlerTransaction` also always prepends the sender [7](#0-6) , so under the current L1 ingestion paths calldata is likely never actually empty in production. The panic is reachable primarily through direct construction of `L1HandlerTransaction` with empty `Calldata` (which the type permits, as proven by the existing regression test), e.g. via deserialization of an RPC/JSON-RPC `MessageFromL1`-derived object, or crafted internal transaction objects that bypass the "prepend sender" step. I could not fully confirm within the available context whether any external-facing deserialization path (e.g., JSON-RPC `starknet_estimateMessageFee` input, or gateway ingestion of `L1HandlerTransaction`) allows submitting a `Calldata` with zero elements that reaches `calc_msg_hash` or the Cende conversion before any non-empty check. This uncertainty affects likelihood but not the root-cause finding itself.

### Recommendation
Apply the same `saturating_sub`/explicit-check pattern already used in `L1HandlerTransaction::payload_size` to `l1_handler_message_hash` and `L1ToL2Message::from`: validate `calldata.0` is non-empty (returning an error or a defined default) before calling `split_first()`/indexing `[0]`/`[1..]`, instead of using `.expect()`/direct indexing that panics on empty input.

### Proof of Concept
1. Construct an `L1HandlerTransaction` (starknet_api) with `calldata: Calldata(Arc::new(vec![]))` (permitted by the type, as already demonstrated by the existing test `l1_handler_payload_size_empty_calldata_does_not_underflow` [8](#0-7) ).
2. Call `tx.calc_msg_hash()` — this calls `l1_handler_message_hash`, which executes `calldata.0.split_first().expect(...)` and panics because the vector is empty [9](#0-8) .
3. Alternatively, pass the same transaction through `L1ToL2Message::from(l1_handler_transaction)` in the batcher — `calldata.0[0]` panics with an out-of-bounds index [10](#0-9) .
