### Title
Wallet Contract build hardcodes `ADDRESS_REGISTRAR_ACCOUNT_ID` for all networks while only `CHAIN_ID` is network-parameterized - ([File: runtime/near-wallet-contract/build.rs])

### Summary
The `near-wallet-contract` build process (`build.rs`) deliberately varies the `CHAIN_ID` file per network (mainnet/testnet/localnet), but the `ADDRESS_REGISTRAR_ACCOUNT_ID` file, which is baked into the compiled Wallet Contract WASM via `include_str!`, is never varied per network. This is the same bug class as the reported WETH hardcoding issue: a single external contract address is hardcoded into logic that is deployed across multiple independent networks/deployments where that address is only valid on one of them.

### Finding Description
`near-wallet-contract/build.rs` builds three separate WASM artifacts (`wallet_contract_mainnet`, `wallet_contract_testnet`, `wallet_contract_localnet`) and explicitly overwrites the `CHAIN_ID` source file with the correct per-network EVM chain id before each build: [1](#0-0) [2](#0-1) 

However, the wallet-contract's `lib.rs` also bakes in a second network-specific value, `ADDRESS_REGISTRAR_ACCOUNT_ID`, sourced from a single static file, and this file is **not** touched by `build_contract` at all: [3](#0-2) 

The file itself contains a single, unconditional account id: [4](#0-3) 

This account id is used at runtime to resolve/parse into an `AccountId` and make a cross-contract call for the eth-emulation "address check" flow (used when transferring the emulated base token to an eth-implicit address), which gates whether an incoming transfer of a user's attached deposit is executed as a plain transfer or handled specially: [5](#0-4) 

Because `build.rs` produces the mainnet, testnet, and localnet WASM images from the same source tree without ever rewriting `ADDRESS_REGISTRAR_ACCOUNT_ID`, all three network builds embed the identical account id (`address-map.near`). This is analogous to the reported Derby issue: a value that is only correct for one deployment target (there: Ethereum mainnet's WETH; here: the mainnet address-registrar account) is hardcoded into code that is compiled/deployed identically across multiple independent networks (there: Polygon/Arbitrum/etc.; here: NEAR testnet/localnet), where the hardcoded address either does not exist or refers to an unrelated/uncontrolled account.

### Impact Explanation
On any non-mainnet NEAR network (testnet, localnet, or any other deployment of the eth-implicit-accounts/Wallet Contract feature), every Wallet Contract instance will attempt to call `address-map.near` — a mainnet-only account id — for the address-registrar lookup used in `EOABaseTokenTransfer` flows. If that account does not exist (or exists but is controlled by an unrelated/unaudited party on that network), the cross-contract call will fail or resolve against the wrong contract, breaking the address-check gating that decides how a user's attached NEAR deposit is routed. Because `build.rs` explicitly shows the intended pattern of parameterizing per-network constants (as done for `CHAIN_ID`) but omits doing so for the address registrar, this is a genuine cross-network correctness defect in a component that handles user-attached deposits during eth-emulated transfers.

### Likelihood Explanation
This triggers automatically and deterministically for every user (an unprivileged relayer/EOA-transaction sender) attempting an `EOABaseTokenTransfer` with `address_check` on any network other than the one the hardcoded registrar was actually deployed against (mainnet). No attacker action beyond a normal transaction is required — it is a systemic deployment-configuration bug reachable by any ordinary Wallet Contract user on testnet/localnet.

### Recommendation
Mirror the `CHAIN_ID` pattern in `build.rs`: parameterize `ADDRESS_REGISTRAR_ACCOUNT_ID` per network build (mainnet/testnet/localnet) the same way `chain_id` is rewritten before each `docker_build` invocation, and restore the original file afterward, ensuring each network's Wallet Contract WASM references the address-registrar account that actually exists on that network.

### Proof of Concept
Conceptual/config-level PoC (not a runtime exploit, but a build/config verification):
1. Inspect `runtime/near-wallet-contract/build.rs`: three calls to `build_contract` produce `wallet_contract_mainnet`, `wallet_contract_testnet`, `wallet_contract_localnet`, only passing a distinct `chain_id` argument that is written into `CHAIN_ID` before each docker build and restored after.
2. Note that no equivalent rewrite happens for `implementation/wallet-contract/src/ADDRESS_REGISTRAR_ACCOUNT_ID`, so all three artifacts embed the same value (`address-map.near`) via `include_str!` in `lib.rs`.
3. Deploy the `wallet_contract_testnet.wasm` artifact to a testnet eth-implicit account and trigger an `EOABaseTokenTransfer` with `address_check` set; the contract will attempt `ext_registrar::ext("address-map.near".parse().unwrap())`, i.e., call a mainnet-designated account id on testnet, which is not guaranteed to be the correct/intended registrar for that network — confirming the cross-network hardcoding defect described above.

I was unable to inspect the exact `address_check_callback` handler logic within the remaining iteration budget, so I cannot confirm with certainty whether a failed/misdirected lookup leads to permanent loss of the attached deposit versus a safe refund path; this would need to be verified in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` (the `address_check_callback` function) before treating this as a guaranteed fund-loss bug rather than a correctness/availability defect.
