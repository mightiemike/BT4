### Title
Unauthenticated CPU-exhaustion via garbage `ShieldedTransferContract` proofs bypasses cheap checks and forces expensive zk-SNARK verification - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
The external report describes a class of bug where a function's success depends on a third party's authorization/funds, but the transaction can be submitted by anyone with fabricated inputs, forcing the party that must process it to burn resources on a transaction that is bound to fail. The closest analog in java-tron is `ShieldedTransferActuator.validate()`, which performs relatively cheap structural checks first, but for any `ShieldedTransferContract` that contains `SpendDescription`/`ReceiveDescription` entries it must always invoke `checkProof()`, which calls into the native `JLibrustzcash` zk-SNARK verification routines (elliptic-curve pairing checks) — one of the most CPU-expensive operations in the codebase. Critically, for a purely-shielded transfer (no `transparentFromAddress`), `getOwnerAddress()` returns `null`, meaning there is no real on-chain account that must sign/own the transaction, which weakens the assumption that submitting garbage input costs the attacker meaningful resources.

### Finding Description
`ShieldedTransferActuator.validate()` [1](#0-0)  performs a sequence of checks: feature-flag checks, `checkSender`/`checkReceiver` structural checks, `validateTransparent`, duplicate-nullifier/merkle-root checks, and finally `checkProof(spendDescriptions, receiveDescriptions, fee)` [2](#0-1) .

`checkProof` invokes native cryptographic verification for every `SpendDescription` and `ReceiveDescription` via `JLibrustzcash.librustzcashSaplingCheckSpend`/`librustzcashSaplingCheckOutput`/`librustzcashSaplingFinalCheck` [3](#0-2) . These are elliptic-curve pairing operations, substantially more expensive than ordinary balance/signature checks (analogous to the "gas-intensive computation" mentioned in the report).

The size/structural checks (`checkSender`, `checkReceiver`, duplicate-nullifier set, merkle-root existence) are all cheap and can be satisfied with syntactically well-formed but cryptographically bogus data (correct byte lengths, non-duplicate random nullifiers, and a currently-valid merkle root) [4](#0-3) . Only after passing all of these cheap gates does the actuator perform the very expensive proof verification.

For a purely shielded transfer (no `transparentFromAddress`/`transparentToAddress`), `getOwnerAddress()` returns `null` [5](#0-4) , and the fee/balance requirement in `validateTransparent` is only enforced `if (hasTransparentFrom)` [6](#0-5) . This means the "identity" that would normally need to prove funds/ownership (analogous to the "bidder" in the report) is not required to exist or be validated before the expensive cryptographic check runs — the actuator's cheap gating logic does not reject purely-shielded, fee-free, fabricated proof data before paying the cost of the pairing check.

This mirrors the report's root cause exactly: cheap, attacker-controllable fields (sizes, uniqueness, root existence) are checked first, but the actual authorization proof (the expensive part) is validated last, and the party bearing the resource cost of validation (every full node / SR that processes the broadcast transaction) is not the party who benefits from having crafted the fake proof.

### Impact Explanation
An attacker who can reach the broadcast-transaction RPC path (`Wallet.broadcastTransaction` → `dbManager.pushTransaction` → actuator `validate()`) [7](#0-6)  can submit `ShieldedTransferContract` transactions with syntactically valid but cryptographically invalid spend/receive descriptions. Each such transaction forces every node that receives/validates it to execute native zk-SNARK pairing verification (`checkProof`) before ultimately rejecting it. Because this is reachable via an ordinary, low-cost broadcast transaction and does not require the submitter to hold or prove control of any real shielded funds for the pure-shielded case, it can be used to impose disproportionate CPU cost on validating nodes relative to the cost paid by the attacker — a DoS/gas-griefing pattern against the protocol implementation rather than a specific victim contract.

### Likelihood Explanation
Exploitability requires only the ability to construct a `ShieldedTransferContract` with correctly-sized nullifiers/commitments/proof blobs (structurally valid, e.g., copied length constants) and a currently valid merkle root (obtainable from public chain state), all of which are inexpensive to produce. No private key material for a legitimate shielded note is needed to trigger the expensive verification path for a purely-shielded transfer. This makes the likelihood of exploitation moderate-to-high assuming shielded transactions are enabled (`dynamicStore.supportShieldedTransaction()`), which is a network parameter, not an attacker-controlled precondition.

### Recommendation
- Reorder/strengthen the validation so cheaper, attacker-detectable anomalies (e.g., malformed sizes, non-existent merkle roots, duplicate nullifiers already recorded on-chain) are checked, and add lightweight pre-filters (e.g., rate limiting per submitting peer/IP, minimum fee/bandwidth cost even for pure-shielded transactions) before the expensive `JLibrustzcash` verification is invoked.
- Consider requiring a minimum non-zero fee/bandwidth cost for every `ShieldedTransferContract`, including purely shielded transfers, so that flooding with garbage proofs is not free.
- Cache/memoize proof-verification failures by transaction id (already partially done via `ZKProofStore`/`recordProof`) to prevent repeated re-verification of the same fabricated transaction across re-broadcasts, and consider network-level throttling for `ShieldedTransferContract` messages specifically given their asymmetric verification cost.

### Proof of Concept
1. Enable `AllowShieldedTransaction` on a test network.
2. Construct a `ShieldedTransferContract` with no `transparentFromAddress`/`transparentToAddress`, one `SpendDescription` referencing a currently valid merkle root (`anchor`) but with a randomly generated (invalid) `nullifier`, `rk`, `zkproof`, and `spendAuthoritySignature` of correct byte lengths, and one `ReceiveDescription` with correctly sized but random `cEnc`/`cOut`/`zkproof`/`noteCommitment` fields.
3. Sign/broadcast the transaction via the gRPC `BroadcastTransaction` API (no requirement to control real shielded funds since `getOwnerAddress()` is `null` for this shape).
4. Observe that `ShieldedTransferActuator.validate()` passes `checkSender`, `checkReceiver`, `validateTransparent`, and the nullifier/merkle-root loop, then enters `checkProof`, invoking native `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` before finally failing.
5. Repeat at volume from multiple submitters/IPs to measure the CPU cost imposed on validating nodes versus the near-zero cost paid by the attacker, demonstrating the resource asymmetry (gas-griefing/DoS analog).

Note: I was unable to fully trace `TransactionCapsule.validateSignature`'s exact behavior when `getOwnerAddress()` returns `null` (i.e., confirm whether zero signatures are strictly required for a pure-shielded contract) within the available search iterations; this should be verified in a full code checkout to confirm the exact signature-count enforcement path before treating this as fully confirmed.
