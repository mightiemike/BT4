### Title
`replay_on_archive`'s `ensure_match_transaction_info` skips checkpoint-hash validation, letting state-root divergence pass as a successful replay — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the check used by `db-tool replay-on-archive`, `aptos-debugger`, and `aptos-move/cli` to confirm that re-executing an archived transaction reproduces the authenticated result recorded on-chain. It validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the corresponding hashes carried in the on-chain `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` compares only a subset of the fields that make up a `TransactionInfo` leaf: [1](#0-0) 

Concretely, it checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`, but the state checkpoint roots (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are never compared. The code itself documents this gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

The `TransactionInfoV1` struct explicitly carries the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields that are supposed to authenticate the Sparse-Merkle/JMT state root, hot-state root, and native-position state root at that version: [3](#0-2) 

`storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify` re-executes archived transactions and relies solely on `ensure_match_transaction_info` to decide pass/fail for each transaction: [4](#0-3) 

Because the state-checkpoint hashes are excluded from the comparison, a replay whose write set, events, gas, and status all match the recorded `TransactionInfo` — but whose resulting Merkle state root (or hot-state/position-state root) actually diverges from the authenticated on-chain root — will be reported as a **successful verification** by this tool.

### Impact Explanation
This breaks the intended proof-integrity guarantee of replay-verify: the state-checkpoint hash is the committed, ledger-info-anchored proof binding the replayed execution to the authenticated Merkle state root. If replay execution produces a state tree that differs from the one committed on mainnet (due to a state-computation bug, a non-deterministic native, or a subtly corrupted archive), this tooling will not flag it as long as the write set/events/gas/status happen to match, silently certifying a divergent state root as correct. This directly matches the "Wrong accumulator root ... accepted as valid" and "Hard-fork-only divergence during commit, replay, restore, or proof verification" categories in scope, since replay-verify is the safety net used to catch consensus/state divergence bugs before or after they reach mainnet.

### Likelihood Explanation
The comparator is unconditionally used by every current caller of `ensure_match_transaction_info` (`replay_on_archive.rs`, `aptos-debugger`, `aptos-move/cli`), and the gap is unconditional — it is not gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS` alone; even the base `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields, which exist and are populated today, are skipped. Any scenario in which a bug causes the *state tree* to diverge while write set/events/gas/status remain (perhaps coincidentally) matching would go undetected by this tool today.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`-side (locally recomputed) checkpoint hashes against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` whenever these are `Some` on the recorded `TransactionInfo`, so replay-verify tooling and debuggers fail loudly on any state-root divergence rather than only on write-set/event/gas/status mismatches.

### Proof of Concept
Not directly demonstrable from static analysis alone — I could not find/run a live divergent-state-root replay scenario in this environment; the finding is grounded in the code's own comparator logic and the explicit maintainer TODO acknowledging the exact gap, but I was not able to construct or execute an actual repro producing a state-root mismatch that this checker fails to catch. This is a code-audit-only assessment; a background Devin session with the full repo and a running toolchain would be needed to fabricate a concrete write-set-matching/state-root-diverging transaction pair and confirm `replay_on_archive` reports success.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
