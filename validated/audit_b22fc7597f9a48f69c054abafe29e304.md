### Title
Fixed static callback gas allocation in the NEAR Wallet Contract can leave `has_in_flight_tx` permanently stuck, permanently halting the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract gates all future `rlp_execute` calls on a single boolean flag, `has_in_flight_tx`, which is only cleared inside the promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). These callbacks are scheduled with **fixed, hard-coded static gas amounts** (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`), analogous to Solidity's fixed 2300-gas stipend from `address.transfer()`. If a callback's actual gas need exceeds its statically reserved budget, the callback receipt fails outright (panics/`GasExceeded`) before it can execute the line that resets `self.has_in_flight_tx = false`. Because that state mutation never commits, the flag stays `true` forever, and the unconditional guard at the top of `rlp_execute` will reject every subsequent transaction for that account.

### Finding Description
`WalletContract::rlp_execute` unconditionally short-circuits whenever `has_in_flight_tx` is `true`: [1](#0-0) 

The flag is set to `true` right before a promise is returned: [2](#0-1) 

It is only cleared as the *first* statement of each `#[private]` callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`): [3](#0-2) [4](#0-3) [5](#0-4) 

Each of these callbacks is itself a receipt that must run within a fixed, statically-reserved gas budget defined by hard-coded constants: [6](#0-5) 

`address_check_callback` and `nep_141_storage_balance_callback` do more than trivial bookkeeping inside this fixed budget: they deserialize an untrusted cross-contract response (`serde_json::from_slice`), and then synchronously schedule the user's target action plus the next `.then()` callback, all funded out of the *same* receipt's prepaid gas: [7](#0-6) 

If the gas actually required by this in-callback logic (JSON parsing of an attacker/relayer-influenceable response, plus dispatching a `FunctionCall`/`Transfer` batch action whose byte-cost scales with the size of `action` fields such as `method_name`/`args`/`receiver_id`) exceeds the statically reserved allocation, the callback receipt fails with a gas-exceeded error. Because NEAR rolls back *all* state changes of a failed receipt, the `self.has_in_flight_tx = false` assignment that already executed at the top of the function is rolled back along with everything else, leaving the flag at its prior value of `true`. Since there is no independent recovery path, timeout, or admin/self-reset function for `has_in_flight_tx`, and `rlp_execute`'s very first check rejects any further call while the flag is `true`, this account's Wallet Contract becomes permanently unusable for submitting any further Ethereum-style transaction. This is analogous to the reported Solidity bug: a fixed/insufficient gas stipend attached to a value/state-critical call causes it to revert, but here the consequence is worse because there is no alternative "call with forwarded gas" path and no way to retry, since the guard blocking re-entry is set unconditionally and only clearable from inside the very call that can fail.

### Impact Explanation
This is a transaction-triggered, permanent halt of a specific account's ability to interact with the chain through its Wallet Contract instance (used for ETH-style transaction emulation). Once `has_in_flight_tx` is stuck at `true`, the account can never again execute `rlp_execute`, meaning any future base-token transfers, ERC-20 emulation, or other actions routed through this Wallet Contract are permanently blocked — effectively freezing the account's ability to move funds through this mechanism, which matches the "permanently frozen funds" / "transaction-triggered halt" impact classes.

### Likelihood Explanation
The relayer/gas checks in `validate_tx_relayer_data` only verify that the *outer* prepaid gas covers the user-requested `gas_limit * GAS_MULTIPLIER` for the wrapped action itself; they do not verify that sufficient margin remains for the multi-hop callback chain's dynamic costs (JSON deserialization of an untrusted response, and per-byte dispatch cost of the wrapped action's fields). A relayer or attacker who controls the RLP-encoded transaction contents (`method_name`, `args`, `receiver_id` sizes) or who is also the target/registrar contract returning a large/adversarial response can tune these sizes to just barely exceed the fixed `RLP_EXECUTE_CALLBACK_GAS` / `ADDRESS_CHECK_CALLBACK_GAS` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` allocations, deterministically triggering the callback failure.

### Recommendation
- Reserve callback gas dynamically based on the size of variable-length action fields (method name, args, receiver id) rather than fixed constants, or attach substantially larger safety margins.
- Add a fallback/failure-handling `.then()` on every promise chain segment so that if a downstream callback fails for any reason, a guaranteed low-gas, minimal-logic recovery receipt still clears `has_in_flight_tx`.
- Alternatively, decouple `has_in_flight_tx` from a single flag cleared deep inside chained promises; e.g., add a self-callback with `PromiseResult::Failed`/panic-safe handling as the very first `.then()` in every chain, guaranteed to run with modest, fixed, safety-margin gas independent of downstream call sizes.

### Proof of Concept
1. An attacker (or a relayer acting for/against the user) submits an RLP-encoded Ethereum transaction whose decoded `Action::FunctionCall` has large `method_name`/`args`/`receiver_id` fields, targeting an account requiring the address-registrar lookup path (`address_check_callback`) or the NEP-141 storage-balance check path (`nep_141_storage_balance_callback`).
2. `rlp_execute` passes the outer gas check in `validate_tx_relayer_data` (`internal.rs:361-365`) because it only checks against `tx.gas_limit`, sets `has_in_flight_tx = true` and returns the promise (`lib.rs:116-127`).
3. The first cross-contract call (registrar lookup / `storage_balance_of`) resolves, invoking `address_check_callback`/`nep_141_storage_balance_callback`, which is itself allocated only `ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (+ `action.gas()`) as its prepaid gas (`lib.rs:417-432`).
4. Inside that callback, `self.has_in_flight_tx = false` executes first, but the subsequent JSON parsing of the (possibly attacker-influenced) response plus scheduling of the large wrapped action and the trailing `.then()` callback exhausts the receipt's fixed gas budget, causing the whole receipt to fail with a gas-exceeded error.
5. Because the receipt failed, all of its state changes — including `has_in_flight_tx = false` — are rolled back, leaving the persisted `has_in_flight_tx` at `true`.
6. Any subsequent call to `rlp_execute` on this account immediately returns `"Error: transaction already in progress, please try again later."` (`lib.rs:97-105`) forever, since nothing in the contract can ever clear the flag again.
