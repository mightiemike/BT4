`PendingInbounds` entries are created on the **first** validator vote for any unique inbound observation (`RecordInboundVote`, called from `VoteInbound`) and persist until the corresponding ballot reaches quorum or expires. An unprivileged external attacker can trivially cause many honest validators to create many distinct `PendingInboundEntry` records by emitting many distinct real (or dust) gateway deposit events on any connected external chain — each unique `(source_chain, tx_hash, log_index)` becomes its own tracked entry, and each unique encoded payload becomes its own `InboundVariant`/ballot. None of this requires privileged access; it only requires paying gas on the external chain to emit events that the Push Chain Gateway will pick up. [2](#0-1) 

Once the attacker has inflated `PendingInbounds` with a large number of entries, **every subsequent ballot expiry** (which fires automatically as part of `CreateBallot`, i.e., on essentially every new vote for any other, unrelated inbound/outbound) forces the chain to perform an O(N) walk over the full attacker-inflated `PendingInbounds` collection. This is the direct architectural analog of the Beta Finance bug: an attacker-controlled, unbounded collection (there, `enterMarkets`; here, `PendingInbounds`) is walked in full by an unrelated, otherwise-cheap operation (there, liquidation's `accrue()` loop; here, ballot finalization's terminal-hook lookup), imposing gas/compute costs on honest participants (validators voting on unrelated inbounds) that grow linearly with attacker-injected state, with no bound on `PendingInbounds` size and no cost to the attacker beyond ordinary deposit gas on the source chain.

### Title
Unbounded `PendingInbounds.Walk` in ballot-expiry hook enables attacker-inflated gas griefing on unrelated inbound/outbound finalization - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
`afterInboundBallotTerminal` performs a full linear scan of the `PendingInbounds` collection every time any inbound ballot reaches a terminal state (including expiry, which is auto-triggered on every new ballot creation). An unprivileged attacker can grow `PendingInbounds` without bound by submitting many low-value or dust cross-chain deposits, each producing a distinct `PendingInboundEntry`/`InboundVariant` that lingers until its ballot passes or expires. Because the entry lookup by ballot ID requires a full walk (ballot IDs are one-way hashes), the cost of finalizing *any* unrelated ballot grows with the attacker-controlled size of `PendingInbounds`.

### Finding Description
1. `RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-87`) is called for the first validator vote on every unique inbound payload, and appends a new `InboundVariant` (or new `PendingInboundEntry`) keyed by `utx_key = sha256(source_chain:tx_hash:log_index)`. An attacker who triggers many distinct gateway deposit events on an external chain (only requiring gas on that external chain, no privileged Push Chain access) causes honest validators to create many distinct entries.
2. These entries remain in `PendingInbounds` until their corresponding ballot reaches quorum (`PASSED`) or expires (`EXPIRED`) via `k.uvalidatorKeeper.VoteOnBallot`'s expiry logic.
3. `CreateBallot` (`x/uvalidator/keeper/ballot.go:36-39`) unconditionally calls `ExpireBallotsBeforeHeight` on **every** new ballot creation — i.e., practically on every vote for any inbound/outbound observation by any validator, including ones completely unrelated to the attacker's spam.
4. `ExpireBallotsBeforeHeight` calls `MarkBallotExpired` for each stale active ballot, which fires `BallotHooks.AfterBallotTerminal` → `afterInboundBallotTerminal`.
5. `afterInboundBallotTerminal` cannot reverse a ballot ID to its owning `utx_key`, so it performs `h.k.PendingInbounds.Walk(ctx, nil, ...)` over the **entire** `PendingInbounds` collection for every single terminal transition.
6. If the attacker has inflated `PendingInbounds` with a large number of live entries (each entry can itself also carry many `InboundVariant`s, since each unique encoding/payload the attacker/validators observe creates a new variant), this walk cost scales linearly (or worse) with attacker-injected state and is repeated on every block in which any ballot expires — a routine, frequent, unprivileged-triggerable event.

### Impact Explanation
This is a compute/gas-griefing vector against the consensus-critical hot path of inbound/outbound ballot finalization, executed inside `VoteInbound`/`VoteOutbound` message handling (which is gasless for validators per `app/txpolicy/gasless.go`, meaning validators bear no fee but the chain still bears the CPU/gas-metering cost during block execution). As `PendingInbounds` grows unbounded, the per-transaction cost of processing any vote (since it can trigger `CreateBallot` → `ExpireBallotsBeforeHeight` → potentially many `MarkBallotExpired` calls, each doing a full walk) increases, degrading block production throughput for the whole network and potentially pushing validator vote-processing transactions toward gas/time limits — a network-wide, non-privileged, materially reachable DoS vector against the universal-execution finalization pipeline, consistent with the in-scope "denial of service...reachable without privileged control" criterion.

### Likelihood Explanation
Likelihood is moderate-to-high: creating many distinct source-chain deposit events is cheap for an attacker (limited by external-chain gas, not Push Chain), there is no minimum-amount or rate-limit check preventing an unbounded number of `PendingInboundEntry`/`InboundVariant` records, and the vulnerable full-collection walk is triggered automatically and repeatedly via the routine `CreateBallot` path rather than requiring any special attacker action against Push Chain itself.

### Recommendation
Avoid full-collection walks in the terminal-hook path: index `PendingInbounds` (or a supplementary lookup table) by `ballot_id -> utx_key` so `afterInboundBallotTerminal` can do an O(1)/O(log n) lookup instead of `Walk`ing the entire collection. Separately, consider bounding the number of concurrent `PendingInboundEntry`/variants (e.g., a cap on distinct pending inbound events, or minimum-value/anti-dust thresholds) and/or decoupling ballot-expiry sweeping from the hot `CreateBallot` path (e.g., process expiries in `EndBlocker` with a bounded batch size per block) to prevent attacker-inflated state from imposing unbounded per-vote costs on the network.

### Proof of Concept
1. Attacker repeatedly emits gateway deposit events on a connected external chain with unique `tx_hash`/`log_index` values (dust amounts acceptable), causing validators to call `VoteInbound` → `RecordInboundVote`, each producing a new `PendingInboundEntry` in `x/uexecutor/keeper/inbound.go`.
2. Attacker withholds enough of these from reaching 2/3 quorum quickly (e.g., ensures some encodings diverge into extra `InboundVariant`s per entry, or simply floods faster than validators can converge), so `PendingInbounds` accumulates a large number of live entries over time.
3. Any honest validator votes on an unrelated, legitimate inbound or outbound event. This calls `VoteOnInboundBallot`/`VoteOnOutboundBallot` → `GetOrCreateBallot`/`CreateBallot` (`x/uvalidator/keeper/ballot.go:36-39`), which unconditionally invokes `ExpireBallotsBeforeHeight`.
4. If any ballots (including the attacker's own spam ballots, once past their `BlockHeightExpiry`) are due for expiry, `MarkBallotExpired` fires the `BallotHooks.AfterBallotTerminal` callback, which performs `PendingInbounds.Walk` over the now-inflated collection (`x/uexecutor/keeper/ballot_hooks.go:86-94`), demonstrably scaling gas/CPU cost with the number of attacker-created entries — directly analogous to the unbounded `enterMarkets`-driven `accrue()` loop in the original Beta Finance report.

func (k Keeper) MarkBallotExpired(ctx context.Context, id string) error {
	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as expired",
		"ballot_id", id,
		"expiry_height", ballot.BlockHeightExpiry,
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.ExpiredBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = types.BallotStatus_BALLOT_STATUS_EXPIRED
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, types.BallotStatus_BALLOT_STATUS_EXPIRED)
	return nil
