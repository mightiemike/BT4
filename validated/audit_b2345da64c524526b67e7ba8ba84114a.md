## Analog Found: Meta‑transaction (NEP‑366) balance refunds are misdirected away from the party that funded the deposit

### Title
Meta-transaction deposit refunds are sent to the DelegateAction sender instead of the relayer who paid, allowing a malicious signer to drain relayer funds - (File: `runtime/runtime/src/actions.rs`)

### Summary
The reported PoolTogether bug is that `excessFeeRefundAddress`/`callValueRefundAddress` are hardcoded to `msg.sender` (the calling contract) even though the entity that should logically receive a refund of unused/failed value is not always able to receive it, causing loss of the funder's money. NEAR's meta-transaction (NEP-366) mechanism has a structurally analogous flaw: the relayer pays for the deposit/gas of a `DelegateAction`, but when the inner action fails, the protocol's hardcoded refund routing sends the deposit refund to the `predecessor_id` of the failed receipt — which for delegated actions is the DelegateAction's `sender_id` (e.g. "Alice"), not the relayer who actually supplied the funds.

### Finding Description
When a relayer submits a `SignedDelegateAction` on behalf of a sender, the relayer's account is charged for all attached deposits and gas of the inner actions (`runtime/runtime/src/config.rs:651-667`, `total_deposit`), but `apply_delegate_action` constructs the spawned receipt with `predecessor_id: sender_id.clone()` (the delegated sender, e.g. Alice), not the relayer: [1](#0-0) 

The comment in the code even documents this explicitly:
"Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit."

Deposit refunds are generic and always route to `receipt.balance_refund_receiver()`, which defaults to `predecessor_id()` unless the receiver contract explicitly redirects with `refund_to`: [2](#0-1) [3](#0-2) 

Since the receipt's `predecessor_id` for delegated inner actions is the DelegateAction's `sender_id`, a failed inner action (e.g. calling a nonexistent method on the receiver, or an action engineered to revert) refunds the attached deposit to the sender who never actually paid it — the relayer's balance is permanently reduced with no recourse.

This is architecturally the same class of bug as the PoolTogether report: a hardcoded refund-recipient assumption (`msg.sender` in Arbitrum's case, `predecessor_id` in NEAR's case) does not match the actual party that funded the value, so the funder's money is unrecoverably lost/diverted whenever the downstream call fails.

### Impact Explanation
A malicious meta-transaction sender ("Alice") can:
1. Construct a `DelegateAction` with a large attached deposit on an inner action designed to fail on the receiver's shard (e.g., a nonexistent method, a contract that explicitly panics, or supplying a receiver account that doesn't exist).
2. Get an unsuspecting/naive relayer to submit it, paying the deposit out of the relayer's own balance.
3. Because the inner action fails, the deposit refund is sent back to Alice (`sender_id`/`predecessor_id`) rather than to the relayer who funded it.

This is a concrete unauthorized value movement: value that belongs to the relayer ends up credited to the DelegateAction sender, with no protocol-level safeguard preventing it. It is reachable purely by an unprivileged transaction signer (the relayer) submitting a delegate transaction crafted/signed by another unprivileged party (the sender), i.e., exactly the "meta-transaction sender" surface named as in-scope.

### Likelihood Explanation
This is not a corner case requiring adversarial infrastructure — it only requires a malicious or compromised `DelegateAction` sender and an automated/naive relayer service (which is the expected operational model for meta-transactions, since relayers are meant to be application-layer, third-party, general-purpose services). The nearcore documentation itself flags this exact risk: [4](#0-3) 

"there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard" — this is the protocol authors' own acknowledgement of the exact fund-diversion vector, comparable in severity framing to the original finding (judged Medium given "the contract would leak value").

### Recommendation
Route deposit refunds for delegated inner-action receipts to the relayer (the actual payer, i.e., `action_receipt.signer_id()`) by default, or require relayers to explicitly opt into risk only when they choose not to use the existing `promise_set_refund_to` mechanism. At minimum, expose a first-class way for relayers to pre-set `refund_to` on the delegate-spawned receipt itself (currently `refund_to` can only be set by a contract acting on its own outgoing promises, not applied automatically to relayer-funded delegate receipts), closing the gap between "who pays" and "who is refunded."

### Proof of Concept
1. Relayer submits a transaction containing `Action::Delegate(SignedDelegateAction)` where `delegate_action.sender_id = "alice"`, `receiver_id = "victim-contract"`, and `actions` includes a `FunctionCall` with a large `deposit` calling a method that is guaranteed to fail (e.g., `"nonexistent_method"`, mirroring the existing test setup in `generate_delegate_actions`): [5](#0-4) 
2. The relayer's balance is debited for the deposit + gas when converting the transaction to a receipt (`total_deposit` sums delegate-inner deposits, `runtime/runtime/src/config.rs:651-667`).
3. `apply_delegate_action` spawns the inner-action receipt with `predecessor_id: sender_id` = "alice" (`runtime/runtime/src/actions.rs:500-513`).
4. The inner `FunctionCall` fails on `victim-contract`'s shard (nonexistent method / explicit panic).
5. `refund_unspent_gas_and_deposits` issues `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, and `balance_refund_receiver()` returns `predecessor_id()` = "alice" (`core/primitives/src/receipt.rs:428-430`, `runtime/runtime/src/lib.rs:1402-1407`), crediting Alice with the deposit the relayer paid.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
