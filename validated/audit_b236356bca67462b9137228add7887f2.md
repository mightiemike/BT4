### Title
`validate_shadow_parent_burnchain` silently skips the shadow-linkage check when the parent header isn't yet staged, letting a malformed block-commit pass on lagging nodes - ([File: stackslib/src/chainstate/nakamoto/shadow.rs])

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` treats "parent header not found in the staging DB" identically to "parent is not a shadow block," returning `Ok(())` in both cases [1](#0-0) . This means the mandatory check that a block-commit's `parent_vtxindex`/`parent_block_ptr` correctly reference a shadow-parent tenure is only enforced on nodes that already have the shadow parent block staged, and is silently bypassed on nodes that haven't staged it yet.

### Finding Description
The equality that should hold is: *acceptance verdict of `validate_normal_nakamoto_block_burnchain` for a given child block is identical regardless of a node's local staging-DB contents*. This equality is broken.

`validate_shadow_parent_burnchain` is called from `validate_normal_nakamoto_block_burnchain`, which is documented as running "before inserting the block into the staging DB" [2](#0-1) . Inside it:

```
let Some(parent_header) =
    staging_db.get_nakamoto_block_header(&block.header.parent_block_id)?
else {
    return Ok(());
};
if !parent_header.is_shadow_block() {
    return Ok(());
}
``` [1](#0-0) 

If the parent header is present and is a shadow block, the function enforces `block_commit.parent_vtxindex == 0` and `block_commit.parent_block_ptr == parent_sn.block_height` [3](#0-2) . If the parent header is simply absent from the local staging DB (e.g., because the shadow block hasn't been ingested yet), the function returns `Ok(())` without performing this check at all - identical to the legitimate "parent is not a shadow block" case.

This is consequential because the burnchain (sortition) layer itself does *not* verify that a `parent_vtxindex == 0`/`parent_block_ptr` combination genuinely points at a real shadow-block tenure - it defers that verification explicitly to this Stacks-level check, per the comment in `leader_block_commit.rs`: "the block validation logic will check that the parent block is indeed a shadow block, and that `self.parent_block_ptr` points to the shadow block's tenure's burnchain block" [4](#0-3) . At the sortition level, `maybe_shadow_parent = parent_block_ptr != 0 && parent_vtxindex == 0` is accepted unconditionally as "descended from anchor" for PoX purposes [5](#0-4)  and block-commit parent-existence checks also special-case `parent_vtxindex == 0` as a shadow-parent possibility without confirming a real shadow-block linkage [6](#0-5) . So `validate_shadow_parent_burnchain` in `shadow.rs` is the *sole* enforcement point for this consistency, and it is called once at intake, with no evidence of a repeated check at block-append/connect time.

An attacker who mines the tenure following a shadow block can therefore submit a `NakamotoBlock` whose block-commit has an invalid `parent_vtxindex`/`parent_block_ptr` (not matching the actual shadow parent's sortition height). Nodes that have already staged that shadow block will correctly reject the child at intake. Nodes that haven't yet staged it (e.g., during a staged rollout of a shadow-block-bearing software update, or simply because the shadow block hasn't propagated/been ingested locally yet) will accept the same block into staging unconditionally, since the check trivially returns `Ok(())`.

### Impact Explanation
Nodes disagree on whether to accept an objectively malformed block into their chainstate for the same block content and the same underlying burnchain state - a genuine two-node inconsistency, not attacker-controlled input differing between nodes. If the block that is wrongly accepted on lagging nodes is subsequently built upon, and the check is never re-run once the shadow parent becomes staged (no confirmed re-validation path was found at block-append time), those nodes can extend a chain tip that upgraded nodes will never accept, producing a persistent fork between the two node populations until manual/social intervention or a later software fix. This matches the "invalid block accepted / valid block rejected network-wide" and "chain split" Critical categories.

### Likelihood Explanation
The preconditions are realistic and low-cost for the attacker: any miner (single miner slot, no majority stake needed) can craft a tenure's block-commit fields directly, and the divergence condition (asynchronous knowledge of a specific shadow block across the network, e.g. during a staged software rollout that introduces a new shadow-repair block) is an expected operational state during upgrades, not a contrived edge case. No signer majority, no privileged role, and no Bitcoin-consensus assumptions are required - only that the attacker's crafted block reaches both an "aware" and an "unaware" node before the rollout completes.

### Recommendation
Do not treat "parent header not found in staging DB" the same as "parent is not a shadow block." If the parent header cannot be resolved locally, `validate_shadow_parent_burnchain` should either (a) defer/reject the block until the parent is known (treat as not-yet-processable rather than automatically valid), or (b) independently resolve whether the parent tenure's sortition was a shadow sortition using sortition-DB state (which is available regardless of local Nakamoto staging status) instead of relying solely on the presence of a staged `NakamotoBlockHeader`. Additionally, re-validate this linkage at block-append/connect time using the now-available parent header, so that no window exists where the check is permanently skipped for a given block.

### Proof of Concept
Rust integration test plan (two-node/two-fork harness):
1. Build a chain with a shadow-block tenure at height `H` on Node A only; Node B has not ingested the shadow block for `H` (simulating a rollout lag).
2. Construct a child `NakamotoBlock` whose tenure's block-commit has `parent_vtxindex = 1` (invalid; should be `0`) or `parent_block_ptr` not equal to the shadow parent's sortition `block_height`.
3. On Node A: call `NakamotoChainState::validate_normal_nakamoto_block_burnchain(...)` with the staging DB that contains the shadow block header for `H`; assert it returns `Err(ChainstateError::InvalidStacksBlock(_))`.
4. On Node B: call the same function with a staging DB lacking that shadow block header; assert it returns `Ok(())`.
5. Assert the two results differ (`res_a.is_err() != res_b.is_ok()`) for the identical `block` and `block_commit`, demonstrating the broken equality between the two nodes' acceptance verdicts.
