### Title
Order state mutated before unbounded-match failure check causes late-stage `ContractExeException` in `MarketSellAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` mirrors the SteadeFi bug pattern: it performs balance/asset deduction and persists the new order to state (`marketAccountStore`, `orderStore`) *before* the order-matching loop discovers that the attacker-controlled order parameters require more matches than the fixed `MAX_MATCH_NUM` limit, at which point it throws deep inside a later processing phase rather than failing validation up front.

### Finding Description
`MarketSellAssetActuator.execute()` runs its steps in this order:
1. Deduct fee and transfer/withdraw the sell asset from the owner account — `transferBalanceOrToken(accountCapsule)` [1](#0-0) 
2. Create and persist the new order into `marketAccountStore`/`orderStore` (increments the account's order count, writes the order object) — `createAndSaveOrder(...)` [2](#0-1) [3](#0-2) 
3. Only *after* those state mutations does it attempt matching against the resting order book via `matchOrder(...)` [4](#0-3) 

Inside `matchOrder`, the number of matches performed against maker orders is only bounded reactively: if the taker order (controlled entirely by the caller's `sellTokenQuantity`/`buyTokenQuantity`, combined with pre-existing resting orders at various prices) requires more than `MAX_MATCH_NUM` (20) individual maker fills, the loop throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM)` [5](#0-4) . This is caught in `execute()`'s `catch` clause and re-thrown as `ContractExeException` [6](#0-5) .

Just like the SteadeFi report — where `minSharesAmt` is accepted and the state is advanced to `Deposit` before a later, un-simulated check (`processDeposit`) reverts — `validate()` for `MarketSellAssetContract` does not simulate or bound the number of matches the order will require against the current order book; the failure is discoverable only during `execute()`, after two state-mutating steps have already run. The existing regression test `exceedMaxMatchNumLimit` confirms this is a reachable, deterministic failure mode triggered purely by user-supplied contract fields plus a pre-seeded order book [7](#0-6) .

### Impact Explanation
An attacker can (a) seed many small resting orders on a token pair from throwaway accounts, then (b) submit a single `MarketSellAssetContract` whose quantities are crafted to require more than `MAX_MATCH_NUM` fills against that book. `validate()` passes because it performs no look-ahead of the order book; `execute()` fails only after `transferBalanceOrToken` and `createAndSaveOrder` have already run, forcing an exception path deep in transaction execution. In `Manager.processBlock`, transactions are applied via `processTransaction` in a simple loop with no per-transaction isolation — `ContractExeException` from `execute()` propagates directly out of `processBlock`, `applyBlock`, and `pushBlock` (declared through their `throws` clauses) [8](#0-7) . If such a transaction is ever included in a produced block (e.g. mempool state differs slightly between the producing witness and other nodes, or the producing witness's own `pushTransaction` session masked the failure differently than block-application would), nodes replaying/applying that block hit the same exception and can fail block application, unlike the graceful per-transaction rollback that exists for `pushTransaction` at the mempool stage (which discards its `tmpSession` on exception before merging) [9](#0-8) .

Even setting aside the more severe block-application path (which I was not able to fully trace to its ultimate handling within the time available), the minimum confirmed impact is: attacker-controlled orders reliably force a late-stage `ContractExeException` after two effectful state writes have already executed inside a single actuator invocation, exactly matching the reported bug class of "state advances, then a downstream, unbounded/user-influenced check fails."

### Likelihood Explanation
Likelihood is high for the mempool-level effect: any unprivileged account can broadcast `MarketSellAssetContract` transactions and pre-seed the order book with small maker orders from its own accounts, deterministically forcing `matchOrderCount > MAX_MATCH_NUM`. The test `exceedMaxMatchNumLimit` demonstrates this is trivially reachable with ordinary user actions and no special privileges [10](#0-9) . Whether this can be escalated to a block-application-level chain-halt depends on witness/mempool consistency behavior that I could not fully verify given the remaining investigation budget.

### Recommendation
- Validate, during `validate()`, an upper bound / pre-check on the number of maker orders the taker order could touch (e.g., cap based on `pairToPriceStore.getPriceNum` and per-price order counts) before any state mutation occurs, and reject the transaction up front if it would exceed `MAX_MATCH_NUM`.
- Reorder `execute()` so that `matchOrder` (or an equivalent dry-run/simulation) executes before `transferBalanceOrToken` and `createAndSaveOrder`, or make the write operations atomic/rollback-safe within a single actuator invocation so a downstream failure cannot leave partial state changes exposed to any code path that does not use a discardable session.
- Add explicit test coverage that exercises this scenario at the `processBlock`/`applyBlock` level (not just direct actuator `execute()` calls) to confirm block application in these edge cases does not propagate exceptions in a way that diverges node behavior.

### Proof of Concept
Using the existing test harness pattern from `MarketSellAssetActuatorTest.exceedMaxMatchNumLimit`: seed `MarketSellAssetActuator.getMAX_MATCH_NUM() + 1` (21) resting maker orders on a token pair from `OWNER_ADDRESS_SECOND`, each at an incrementally different price, then submit a single `MarketSellAssetContract` from `OWNER_ADDRESS_FIRST` sized to match across all of them. `validate()` succeeds; `execute()` deducts the seller's asset and persists the new order, then throws `ContractExeException("Too many matches. MAX_MATCH_NUM = 20")` from within `matchOrder` [10](#0-9) .

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,

    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
