### Title
Write-methods gate check occurs after replay-guard digest consumption, enabling DoS via digest exhaustion - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
In `handler.HandleJSONRPCUserMessage`, `h.requestProcessor.ProcessRequest` authorizes the request and records its replay digest via the replay guard *before* the write-methods feature gate is checked. Since the `writeMethodsEnabled.AllowErr(ctx)` check only happens inside `handleSecretsCreate`/`handleSecretsUpdate`/`handleSecretsDelete`, a request rejected solely because writes are administratively disabled still permanently consumes the one-time replay digest, causing the legitimate owner's subsequent valid retry to fail with `ErrRequestAlreadySeen`.

### Finding Description
The request pipeline in `HandleJSONRPCUserMessage` is:
1. `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)` [1](#0-0)  — for `MethodSecretsCreate`/`Update`/`Delete` this dispatches into `processCreateSecretsRequest`/etc., which validate params and then call `authorizeAndStamp` [2](#0-1) .
2. `authorizeAndStamp` calls `p.authorizer.AuthorizeRequest(ctx, *req)`, which — per the documented pipeline invariant "AuthorizeRequest runs while params are still digest-safe. It also applies the replay guard (digest deduplication)" — invokes `RequestReplayGuard.CheckAndRecord` and records the request's digest as seen [3](#0-2) [4](#0-3) . Once recorded, `CheckAndRecord` will return `ErrRequestAlreadySeen` for any future request with the same digest until expiry, with no undo/rollback API exposed by `RequestReplayGuard` [5](#0-4) .
3. After successful authorization, `authorizeAndStamp` mutates `req.ID` (prefixes it with the authorized owner) and stamps `req.Params` [6](#0-5) , then returns success back to `HandleJSONRPCUserMessage`.
4. Only *after* this point does the handler dispatch to `handleSecretsCreate` (or Update/Delete), which performs the feature-gate check `h.writeMethodsEnabled.AllowErr(ctx)` [7](#0-6) . If the gate is disabled (`cresettings.Default.GatewayVaultManagementEnabled` is false), the handler returns `api.UnsupportedMethodError` to the user [8](#0-7)  — but the replay-guard digest recorded in step 2 is never rolled back.

The result: any request (even an unprivileged attacker who merely knows/observes a legitimate allowlisted digest, e.g. by inspecting a public workflow spec) that reaches `ProcessRequest` successfully will burn that digest permanently in the replay guard, regardless of whether the request is later rejected by an unrelated gate check. This violates the invariant that authorization/replay state should only be mutated by requests that are ultimately accepted (or at least not for requests rejected for reasons unrelated to authorization/replay validity).

### Impact Explanation
This is a denial-of-service vector against legitimate vault secret write operations: once write methods are disabled (a normal administrative/operational state, e.g., during a maintenance window or incident response), any attacker who submits a request using a valid allowlisted digest (which may be observable via public workflow metadata) will permanently exhaust that digest in the replay guard. When the write gate is later re-enabled, the legitimate owner's genuine retry with the same digest is rejected with `ErrRequestAlreadySeen`, blocking their secret create/update/delete operation until the digest naturally expires. This matches a scoped "DoS on legitimate secret writes via digest exhaustion" impact — not secret disclosure or unauthorized writes, but availability degradation of a security-sensitive control path.

### Likelihood Explanation
The precondition (`GatewayVaultManagementEnabled` gate false) is an operator-controlled, non-adversarial condition that can legitimately occur (e.g., temporary lockdown). The attacker needs no elevated privileges — only a valid allowlisted digest, which per the threat model can be obtained by observing a public workflow spec. The exploit is a single JSON-RPC call to the gateway with no rate-limiting or replay-state safeguard preventing it, making this reliably and repeatably triggerable whenever the gate is off.

### Recommendation
Move the `h.writeMethodsEnabled.AllowErr(ctx)` feature-gate check to occur *before* `h.requestProcessor.ProcessRequest` is invoked (or otherwise before `authorizeAndStamp`/`CheckAndRecord` runs) for `MethodSecretsCreate`/`Update`/`Delete`, so that administratively-gated methods are rejected prior to any authorization/replay-state mutation. Alternatively, provide a rollback/`Release(digest)` method on `RequestReplayGuard` invoked whenever a request is rejected for a reason unrelated to authorization/replay validity (e.g., feature gate disabled), ensuring the digest remains usable for a legitimate retry.

### Proof of Concept
Integration test in `core/services/gateway/handlers/vault/handler_test.go`:
1. Construct a `handler` with `writeMethodsEnabled` gate configured to return `false` (disabled) and a valid allowlist authorizer/digest for a test workflow owner.
2. Submit a `MethodSecretsCreate` JSON-RPC request with a valid, allowlisted digest through `HandleJSONRPCUserMessage`.
3. Assert the response is `api.UnsupportedMethodError` (write methods disabled) — confirming `ProcessRequest`/`authorizeAndStamp`/`CheckAndRecord` ran and recorded the digest before the gate rejected it.
4. Toggle the `writeMethodsEnabled` gate to enabled (true).
5. Resubmit the identical `MethodSecretsCreate` request (same digest/body) as the legitimate owner.
6. Expected (desired) behavior: the request should succeed and be forwarded to vault nodes. Actual (current buggy) behavior: `ProcessRequest` returns an authorization error wrapping `ErrRequestAlreadySeen`, demonstrating the digest was consumed by the earlier, ultimately-rejected request.

func (h *handler) handleSecretsCreate(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	err := h.writeMethodsEnabled.AllowErr(ctx)
	if errors.Is(err, limits.ErrorNotAllowed{}) {
		l.Warnw("secrets write method called but write methods are disabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.UnsupportedMethodError, errors.New("vault write methods(create/update/delete) are disabled: "+err.Error()), nil))
	} else if err != nil {
		l.Errorw("error checking if write methods are enabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("error checking if write methods are enabled: "+err.Error()), nil))
	}

	return h.fanOutToVaultNodes(ctx, l, ar)
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
}

var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
