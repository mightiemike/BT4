## Analysis

The full parse path is: `EventListener.processSignatureBatch` fetches an SVM transaction via `GetTransaction` and iterates `tx.Meta.LogMessages`, calling `determineEventType(log)` on each individual log line to select a discriminator, then `ParseEvent` (`universalClient/chains/svm/event_parser.go:46`) dispatches to `parseSendFundsEvent` or `parseOutboundObservationEvent` based purely on that string-prefix + 8-byte-discriminator match.

<cite repo="patrichyt/push-chain-node--002" path="universalClient/chains/svm/event_listener.go" start="298="308" end="308" /> [1](#0-0) 

Critically, `GetSignaturesForAddress(gatewayAddr, ...)` is only used to enumerate **transaction signatures** that touch the gateway address; once a signature is selected, `processSignatureBatch` reads **every** `LogMessage` in that whole transaction's `tx.Meta.LogMessages`, without any check that a given `"Program data: ..."` line was actually emitted by a CPI from the gateway program (Solana's `sol_log_data`self-invoke pattern would normally be bounded by `Program <id> invoke [depth]` / `Program <id> success` markers in the log stream, but neither `event_listener.go` nor `event_parser.go` correlates a given log line back to its emitting program ID). [2](#0-1) 

`determineEventType`/`ParseEvent` only check: (1) the `"Program data: "` prefix, (2) valid base64, (3) the first 8 bytes matching a discriminator that is public knowledge (published in `chain.json`, e.g. `event_identifier` values, and Anchor discriminators are `sha256("event:<Name>")[:8]`, derivable by anyone). Nothing binds the log entry cryptographically or positionally to an actual invocation of the configured `gatewayAddress` program. [3](#0-2) 

Since a single Solana transaction can invoke multiple programs (one trivial/no-op call to the real gateway program to make the tx show up in `GetSignaturesForAddress`, and a second, attacker-deployed program that calls `sol_log_data`/`msg!` to emit an arbitrary `"Program data: <base64>"` line with a forged 8-byte discriminator matching `send_funds` and attacker-chosen sender/recipient/amount/token bytes), the parser has no way to distinguish this forged log line from a genuine gateway-emitted deposit event. That fabricated line is real, immutable on-chain data — every honest RPC node and every honest universal validator observes the exact same bytes, so this is not an honest-validator-assumption violation; it is a missing origin/authentication check in scoped code (`event_parser.go` / `event_listener.go`).

Downstream, this flows to `parseSendFundsEvent` → `store.Event` (Type=INBOUND, Status=PENDING) → `EventProcessor.processInboundEvent` → `constructInbound` → `MsgVoteInbound`, which honest bonded validators sign based purely on this observed (but fabricated) log data. [4](#0-3) [5](#0-4) 

There is no visible check elsewhere (vault balance delta, account-ownership check, program-invoke-boundary parsing) in the scoped SVM client code that ties a `send_funds` event's sender/amount/token back to an actual balance movement into the gateway's vault PDA — the parser trusts the raw decoded bytes verbatim. I could not find, within the indexed portion of the repo, any code that validates the log's emitting program before decoding it; this may exist in code not covered by the index, so this should be verified by a Devin session directly with the actual gateway/on-chain program and full log-boundary parsing logic, but based on everything retrievable here, no such check exists in `event_parser.go` or `event_listener.go`.

This satisfies the required impact: unauthorized mint (a UEA/CEA mint corresponding to a fabricated "deposit" that never happened) reachable by an ordinary unprivileged attacker who merely submits a self-crafted Solana transaction touching the gateway address once and a malicious program the rest of the time — no malicious validator, TSS signer, or admin is required.

### Title
Unauthenticated program-data log injection lets an attacker forge SVM gateway deposit/outbound events and mint funds without locking real assets - (File: universalClient/chains/svm/event_parser.go, universalClient/chains/svm/event_listener.go)

### Summary
`EventListener.processSignatureBatch` scans **every** log line of a Solana transaction that merely references the gateway address, and `ParseEvent`/`determineEventType` accept any `"Program data: <base64>"` line whose first 8 bytes match a public Anchor event discriminator — with no verification that the line was actually emitted (via `sol_log_data` self-CPI) by the configured gateway program.

### Finding Description
Because Solana transactions can contain multiple top-level instructions invoking different programs, and `tx.Meta.LogMessages` interleaves logs from all of them, an attacker can:
1. Include one trivial/no-op instruction that touches the real gateway program (to satisfy `GetSignaturesForAddress` filtering, ensuring the transaction is picked up).
2. Include a second instruction that invokes an attacker-deployed program which emits a raw `"Program data: <base64>"` log line with the discriminator for `send_funds` (or `finalize_universal_tx`/`revert_universal_tx`/`funds_rescued`) followed by attacker-chosen Borsh-encoded fields (sender, recipient, token, amount, tx IDs, gas figures).

`determineEventType` and `ParseEvent`/`parseSendFundsEvent`/`parseOutboundObservationEvent` never check which program produced a given log line — they only check the string prefix and discriminator bytes. This event is then persisted via `InsertEventIfNotExists` and routed into the normal honest-validator vote pipeline (`processInboundEvent`/`constructInbound`/`MsgVoteInbound`), where all honest validators independently observe the identical (forged) on-chain log data and vote it through, since nothing in the flow distinguishes "genuinely emitted by gateway" from "emitted by any other invoked program in the same transaction."

### Impact Explanation
A successful forged `send_funds` event lets an attacker mint value on Push Chain (or trigger outbound release/refund flows for `finalize_universal_tx`/`revert_universal_tx`/`funds_rescued`) without ever locking real funds in the SVM vault, since the parser has no linkage back to an actual vault balance change or verified emitting program. This is a direct unauthorized-mint / unauthorized-release vulnerability meeting the required impact bar.

### Likelihood Explanation
High, if confirmed against the actual gateway program's log layout — deploying an SPL/Solana program that emits a crafted `sol_log_data` line is trivial and fully permissionless; the discriminators are public (derivable via `sha256("event:<Name>")[:8]` or already published in `chain.json`). The main open question (not resolvable from the indexed code alone) is whether the gateway program's own log boundaries (`Program <id> invoke`/`success`) are somehow implicitly relied upon elsewhere in the pipeline that I could not find — this needs direct verification against the full transaction log-parsing logic and the on-chain gateway program.

### Recommendation
In `event_listener.go`/`event_parser.go`, only accept `"Program data:"` lines that fall between the `"Program <gatewayAddress> invoke [...]"` and its matching `"Program <gatewayAddress> success"` boundary at the correct call depth, and/or cross-check parsed event fields (amount, token, sender) against an actual balance delta on the gateway vault PDA read from `tx.Meta.PreTokenBalances`/`PostTokenBalances`/`PreBalances`/`PostBalances` before trusting the decoded payload.

### Proof of Concept
Fast validation per the question's own suggestion: on a local Solana validator, submit one transaction containing (a) a no-op CPI to the deployed gateway program, and (b) a call to a second, attacker-controlled program that does `sol_log_data(discriminator_send_funds || attacker_recipient || huge_amount || ...)`. Run the actual `universalClient` SVM listener/parser against this transaction's signature and confirm that `store.Event`/`store.EventTypeInbound` gets created and reaches `MsgVoteInbound` construction despite no real vault deposit occurring.

**Caveat**: I was unable to fully confirm whether any log-boundary/program-origin check exists elsewhere in the SVM client pipeline outside the indexed snippets (e.g., in code not surfaced by search). This should be verified directly in a full checkout before treating this as conclusively exploitable — I recommend starting a Devin session with full repository access to confirm the absence of any origin-binding check across the entire `universalClient/chains/svm` package and the on-chain gateway program's log emission behavior.

// determineEventType determines the event type based on the log discriminator
func (el *EventListener) determineEventType(log string) string {
	if !strings.HasPrefix(log, "Program data: ") {
		return ""
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return ""
	}

	if len(decoded) < 8 {
		return ""
	}

	discriminator := strings.ToLower(hex.EncodeToString(decoded[:8]))

	// Look up event type from discriminator map
	eventType, ok := el.discriminatorToEventType[discriminator]
	if !ok {
		return ""
	}

	return eventType

	}

// constructInbound creates an Inbound message from event data
func (ep *EventProcessor) constructInbound(event *store.Event) (*uexecutortypes.Inbound, error) {
	var eventData UniversalTx

	if event == nil {
		return nil, fmt.Errorf("event is nil")
	}

	if event.EventData == nil {
		return nil, fmt.Errorf("event data is missing for event_id: %s", event.EventID)
	}

	if err := json.Unmarshal(event.EventData, &eventData); err != nil {
		return nil, fmt.Errorf("failed to unmarshal event data: %w", err)
	}

	// Map txType from eventData to proper enum value
	txType := uexecutortypes.TxType_UNSPECIFIED_TX
	switch eventData.TxType {
	case 0:
		txType = uexecutortypes.TxType_GAS
	case 1:
		txType = uexecutortypes.TxType_GAS_AND_PAYLOAD
	case 2:
		txType = uexecutortypes.TxType_FUNDS
	case 3:
		txType = uexecutortypes.TxType_FUNDS_AND_PAYLOAD
	default:
		txType = uexecutortypes.TxType_UNSPECIFIED_TX
	}

	// Extract txHash from EventID (format: "txHash:logIndex")
	txHash := ""
	parts := strings.Split(event.EventID, ":")
	if len(parts) > 0 {
		txHash = parts[0]
	}

	// Convert txHash to hex format if it's in base58
	txHashHex, err := ep.base58ToHex(txHash)
	if err != nil {
		ep.logger.Warn().
			Str("tx_hash", txHash).
			Err(err).
			Msg("failed to convert txHash to hex, using original value")
		txHashHex = txHash
	}

	inboundMsg := &uexecutortypes.Inbound{
		SourceChain: eventData.SourceChain,
		TxHash:      txHashHex,
		Sender:      eventData.Sender,
		Recipient:   eventData.Recipient,
		Amount:      eventData.Amount,
		AssetAddr:   eventData.Token,
		LogIndex:    strconv.FormatUint(uint64(eventData.LogIndex), 10),
		TxType:      txType,
		IsCEA:       eventData.FromCEA,
		RawPayload:  eventData.RawPayload,
	}
