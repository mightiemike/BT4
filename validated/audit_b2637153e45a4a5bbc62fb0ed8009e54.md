### Title
Governance change to Dynamic Energy parameters retroactively rewrites past-cycle congestion penalty, allowing unprivileged callers to arbitrage TVM energy pricing - (File: chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java)

### Summary
`ContractStateCapsule.catchUpToCycle` recomputes a contract's "dynamic energy" congestion-penalty factor lazily, on the next call to that contract, by applying the *current* global `threshold`/`increaseFactor`/`maxFactor` parameters across every cycle since the contract was last touched. Because these parameters can change mid-flight via governance proposals (`DYNAMIC_ENERGY_THRESHOLD`, `DYNAMIC_ENERGY_INCREASE_FACTOR`, `DYNAMIC_ENERGY_MAX_FACTOR`) that take effect immediately for all future calls, an unprivileged caller can trigger the catch-up computation either just before or just after such a parameter change to have the entire backlog of "skipped" cycles settled under whichever parameter set benefits them, rather than under the parameters that were actually in effect during those historical cycles. This is the same root-cause pattern as the referenced finding: a rate/degradation-like coefficient is changed without first "closing the books" on the state it governs, letting an unprivileged transaction author front-run/back-run the effect for gain.

### Finding Description
The per-contract congestion penalty state is stored in `ContractStateCapsule`: [1](#0-0) 

`catchUpToCycle` increases the factor if usage in the last active cycle exceeded `threshold`, then decays the factor exponentially over `cycleCount = newCycle - lastCycle` skipped cycles using `increaseFactor`: [2](#0-1) 

This method is invoked from `Program.updateContextContractFactor()` on every TVM `CALL`-style opcode when dynamic energy is enabled, using the **current** `VMConfig` values (not the values that were in effect for each of the skipped cycles): [3](#0-2) 

The resulting `contextContractFactor` is then applied as a direct multiplier on the caller's energy cost in `EnergyCost.getCalculateCallCost`: [4](#0-3) 

The `threshold`/`increaseFactor`/`maxFactor` values are chain parameters settable by governance proposals (`ProposalType.DYNAMIC_ENERGY_THRESHOLD` / `DYNAMIC_ENERGY_INCREASE_FACTOR` / `DYNAMIC_ENERGY_MAX_FACTOR`, validated in `ProposalUtil.validator`): [5](#0-4) 

and are pushed into the VM's live `VMConfig.Snapshot` (used process-wide from the next block) via `ConfigLoader.load`: [6](#0-5) 

Because `ContractStateCapsule` only stores `energyUsage`, `energyFactor`, and `updateCycle` — with no record of the parameter values that applied to each historical cycle — any contract that has gone untouched for one or more cycles will have its *entire* backlog settled using whichever global parameters are active at the moment someone finally calls it again, exactly mirroring the ReaperVaultV2 bug where `lockedProfit`/`lastReport` were not settled before `lockedProfitDegradation` changed.

### Impact Explanation
This corrupts the intended TVM "resource and reward accounting" / energy metering invariant that congestion pricing reflects the historical usage pattern under the rules that were in force at the time. Concretely:
- If a popular/congested contract's factor is near `maxFactor` under the old `increaseFactor`, and governance later lowers `increaseFactor` (faster decay) or `maxFactor`, the *first* unprivileged caller after the change causes `catchUpToCycle` to apply the new, much faster decay retroactively across all the skipped cycles, collapsing the penalty far below what should have accumulated under the historical parameters — effectively letting that caller (and anyone who calls right after) buy artificially cheap energy on a contract that was, moments before under the old rules, supposed to carry a heavy congestion surcharge.
- Conversely, a caller could pre-emptively "lock in" a favorable low factor by triggering the catch-up right before an unfavorable parameter change takes effect, since the settlement is opportunistic and lazy rather than deterministic per elapsed cycle.
- This is reachable purely through unprivileged, ordinary contract-call transactions (`CALL`/`STATICCALL`/etc. against a smart contract) — no special role or malicious peer is required, matching the "TVM execution and energy metering" / "resource and reward accounting" categories.

The severity is bounded by the fact that it only affects the size of the energy-cost multiplier for calling specific contracts (it does not, by itself, allow theft of principal balances or unauthorized account operations), which parallels the disputed medium/high severity discussion in the original report.

### Likelihood Explanation
Exploitation requires:
1. A governance proposal changing `DYNAMIC_ENERGY_THRESHOLD`/`DYNAMIC_ENERGY_INCREASE_FACTOR`/`DYNAMIC_ENERGY_MAX_FACTOR` to take effect (a normal, expected chain-governance event, not attacker-controlled, but publicly observable in advance since proposals are on-chain and have a fixed effective/expiration time).
2. A target contract whose `ContractStateCapsule.updateCycle` is stale relative to the change (common for less-frequently-called but still congestion-flagged contracts).
3. An attacker submitting an ordinary call transaction at the right moment relative to the maintenance cycle boundary — a low-cost, fully unprivileged action requiring no special capital (unlike the original ReaperVault PoC, which needed large TVL to front-run).

Because on-chain proposals are visible before they take effect (there is a public voting/expiration window), timing the triggering transaction is straightforward, making this more readily exploitable than the original disputed finding, though the resulting benefit (energy-fee savings) is smaller in absolute value than a "steal principal" exploit.

### Recommendation
Before/at the point a `DYNAMIC_ENERGY_THRESHOLD`/`DYNAMIC_ENERGY_INCREASE_FACTOR`/`DYNAMIC_ENERGY_MAX_FACTOR` proposal is applied (in `ProposalService.process`), the pending per-contract `ContractStateCapsule` states should be caught up ("settled") to the current cycle using the *old* parameter values first, then the new parameters should be adopted for subsequent cycles — analogous to updating `lockedProfit`/`lastReport` before writing the new `lockedProfitDegradation`. Alternatively, `ContractStateCapsule` could be extended to catch up cycle-by-cycle against a per-cycle parameter history instead of collapsing multiple skipped cycles under a single "current" parameter set.

### Proof of Concept
Conceptual sequence (cannot be executed without a running/testable node, but derivable directly from the cited code paths):
1. Contract `C` becomes congested; repeated calls raise `ContractStateCapsule.energyFactor` toward `maxFactor_old` under `increaseFactor_old` (`ContractStateCapsule.catchUpToCycle`, lines 110-120).
2. No one calls `C` for `N` cycles (`updateCycle` becomes stale). A governance proposal reduces `DYNAMIC_ENERGY_INCREASE_FACTOR` (and/or `DYNAMIC_ENERGY_MAX_FACTOR`), validated by `ProposalUtil.validator` (lines 649-689) and applied to the live `VMConfig.Snapshot` via `ConfigLoader.load` (lines 40-43) at the next maintenance cycle.
3. Attacker submits an ordinary transaction invoking `C`. `VM`/`Program.updateContextContractFactor()` calls `catchUpToCycle(newCycle, threshold_new, increaseFactor_new, maxFactor_new, ...)` (Program.java lines 2360-2383), which computes `decreasePercent = pow(1 - increaseFactor_new/DECREASE_DIVISION/precision, cycleCount)` over the entire `N`-cycle backlog using the *new* (weaker) factor, collapsing `energyFactor` far below what the old parameters would have produced for those same `N` cycles.
4. The attacker's subsequent calls to `C` are charged using this artificially low `contextContractFactor` in `EnergyCost.getCalculateCallCost` (lines 513-523), paying less than the congestion penalty that should have applied under the parameter regime in force during most of the elapsed cycles.

```java
  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }
```

```java
  public long updateContextContractFactor() {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
      if (contractStateCapsule.catchUpToCycle(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber(),
          VMConfig.getDynamicEnergyThreshold(),
          VMConfig.getDynamicEnergyIncreaseFactor(),
          VMConfig.getDynamicEnergyMaxFactor(),
          VMConfig.allowStrictMath(),
          VMConfig.disableJavaLangMath())) {
        contractState.updateContractState(getContextAddress(), contractStateCapsule
        );
      }
    }
    contextContractFactor = contractStateCapsule.getEnergyFactor()
        + Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
    return contextContractFactor;
  }
```
