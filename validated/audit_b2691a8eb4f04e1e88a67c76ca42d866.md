Citrea's basefee mechanism is a standard Ethereum-style EIP-1559 implementation using `alloy_eips::eip1559::calc_next_block_base_fee` with `BaseFeeParams` (max_change_denominator, elasticity_multiplier), invoked from `calculate_next_block_base_fee` in `crates/primitives/src/basefee.rs`, and applied per L2 block in `begin_l2_block_hook` in `crates/evm/src/hooks.rs`. [1](#0-0) [2](#0-1) 

This is architecturally unrelated to the Taiko exponential-AMM EIP-1559 formula described in the report: there is no `gas_excess`/`lastSyncedBlock` accumulator, no periodic (every-N-L1-block) gas issuance to smooth or de-smooth, and no `b0 = 1/(T*A)` scaling constant to correct. Citrea instead ticks the basefee once per L2 block based on the previous block's `gas_used`/`gas_limit`, floored at a `min_base_fee_per_gas` per spec. [3](#0-2) [4](#0-3) 

Since the reported bug class (AMM-curve/exponential 1559 mismatch, `lastSyncedBlock` gas-issuance batching, incorrect `b0`) has no corresponding mechanism in this codebase, there is no reachable path that breaks any of the required rollup bindings (cBTC custody, proof/journal correctness, DA-blob correctness, sequencer/method-id authority, or state-root determinism). This also falls under the "best-practice notes / feature requests / theoretical findings" exclusion in the rules.

use alloy_eips::eip1559::{calc_next_block_base_fee, BaseFeeParams};
use sov_rollup_interface::spec::SpecId;

use crate::min_base_fee_per_gas;

pub fn calculate_next_block_base_fee(
    gas_used: u64,
    gas_limit: u64,
    base_fee: u64,
    base_fee_params: BaseFeeParams,
    spec_id: SpecId,
) -> u64 {
    std::cmp::max(
        min_base_fee_per_gas(spec_id),
        calc_next_block_base_fee(gas_used, gas_limit, base_fee, base_fee_params),
    )
}
