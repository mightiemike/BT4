## Title
`ensure_match_transaction_info` silently skips checkpoint-hash comparison, letting replay-verify tooling and chunk-replay accept a divergent state root - ([File: types/src/transaction/mod.rs])

## Summary
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs`) is the authoritative check used by both offline replay-verification (`storage/db-tool/src/replay_on_archive.rs`) and the chunk executor's replay path (`execution/executor/src/chunk_executor/mod.rs`) to confirm that freshly re-executed VM output matches the archived/authenticated `TransactionInfo` for a version. It validates status, gas, write-set hash, and event root hash, but a `TODO` in the code explicitly documents that it does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

## Finding Description
`ensure_match_transaction_info` is meant to be the single source of truth proving "this output is exactly what committed at this version": [1](#0-0) 

It checks status, gas used, write-set hash, and event root hash, but explicitly and knowingly omits the checkpoint-hash fields: [2](#0-1) 

The comment is unambiguous about the consequence:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This function is used exactly as warned:
- `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify` re-executes archived transactions and calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` to decide pass/fail for the whole replay-verify run: [4](#0-3) 
- `TransactionInfo` itself carries the `state_checkpoint_hash` / `position_state_checkpoint_hash` fields that are meant to bind the authenticated commit-info root to a specific state: [5](#0-4) 

Because these fields are skipped in the comparator, a mismatch between the locally computed state-checkpoint/hot-state/position-state root and the archived (accumulator-committed, signature-backed) root is invisible to this check. `state_checkpoint_hash` is exactly the value that guarantees the Sparse-Merkle/Jellyfish state root committed in the transaction accumulator corresponds to the actual write-set-derived world state (see its doc comment: "The root hash of the Sparse Merkle Tree describing the world state at the end of this transaction"). Skipping it in the one function whose job is to assert "output == authenticated info" breaks the proof-binding invariant described in the task's "Proof And Storage Pivots": VM outputs must survive executor-to-storage handoff unchanged and be verifiably bound to the correct root.

## Impact Explanation
This is scoped as a real, unprivileged, local-code-provable gap: any bug in state-checkpoint/hot-state/position-state root computation (bugs in the executor's Merkle summary logic, the new "native position" subsystem, or serialization changes) would go undetected by:
1. The `db-tool replay-on-archive` verifier, which is the tool operators run to attest that archived on-chain history's write sets/events truly reproduce the authenticated ledger, since it never re-validates the state-checkpoint root.
2. Any other caller relying on this comparator as the ground-truth check between replayed output and stored `TransactionInfo` (`aptos-debugger`, `aptos-move/cli`, chunk executor replay path).

The result is that a divergence between the locally re-executed state root and the archived/authenticated state root can be reported as "replay verified successfully," i.e., an authenticated proof-bearing value (`state_checkpoint_hash`/`position_state_checkpoint_hash`, which is committed into the transaction accumulator and thus covered by validator signatures) is effectively unauthenticated in this code path. This matches the required "Committed state that differs from the correct VM result... accepted as valid" and "Authenticated API...output bound to wrong version/root" impact classes, since it defeats the intended detection mechanism for exactly that class of divergence, including the newly-introduced position-state / native-position and hot-state checkpoint roots (`TransactionInfoV1`).

## Likelihood Explanation
Medium. This is not itself a corruption of committed data — it is a broken verification/detection invariant that is only triggered when there is an underlying divergence (e.g., a bug in state-checkpoint hash computation, hot-state Merkle logic, or the new "native position" subsystem introduced in this codebase, as seen in `do_state_checkpoint.rs` and the position-state summary code). Given the code explicitly gates a new feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) behind fixing this exact gap, the authors consider such divergence plausible enough to require the fix before enabling that feature, and today the check is already used in production replay/audit tooling without such divergence being caught.

## Recommendation
In `ensure_match_transaction_info` (`types/src/transaction/mod.rs`), when the expected `TransactionInfo` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, recompute the corresponding roots from the replayed `TransactionOutput`/execution state and assert equality (mirroring the existing write-set-hash/event-root-hash checks), returning an error on mismatch before COMPUTE_TRADING_NATIVE_STATE_ROOTS (or any equivalent state-root feature) is exposed, and before this comparator continues to be relied upon by `replay_on_archive` and other replay/verification tools as the sole correctness gate.

## Proof of Concept
This is a detection-logic gap rather than a directly exploitable state corruption, so no transaction sequence forges a bad state; the PoC is a code-trace showing the comparator's blind spot is real and load-bearing:
1. `replay_on_archive.rs::execute_and_verify` re-executes archived transactions and calls `TransactionOutput::ensure_match_transaction_info` as the pass/fail oracle for the whole verification run. [6](#0-5) 
2. `ensure_match_transaction_info` never reads `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` anywhere in its body, as the code and inline TODO both confirm. [7](#0-6) 
3. Construct (in a test) two `TransactionOutput`s with identical write set, events, status, and gas, but where the archived `TransactionInfo` carries a `state_checkpoint_hash` that does not correspond to the SMT root actually produced by the write set (e.g., using `TransactionInfo::builder_v0().maybe_state_checkpoint_hash(Some(HashValue::random()))` as already done in test helpers such as `create_transaction_info`) — `ensure_match_transaction_info` returns `Ok(())`, demonstrating the check passes despite a state-root divergence. [8](#0-7) 

**Note on completeness:** I could not fully trace how (or whether) `execution/executor/src/chunk_executor/mod.rs` invokes this same comparator during live chunk-replay/state-sync application (the file is large and I only confirmed the import list before running out of iterations), so I cannot state with certainty whether this gap also affects the online state-sync/chunk-executor commit path versus only the offline `db-tool replay_on_archive` auditor. This should be verified in a follow-up before finalizing severity across both paths.
