Unrestricted CEA/FUNDS recipient allows attacker-directed PRC20 minting into `UNIVERSAL_CORE` and other system contracts, corrupting protocol accounting — (File: `x/uexecutor/types/inbound.go`, `x/uexecutor/keeper/execute_inbound_funds.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
The external report describes a vault that can be made to "deposit into itself," minting new units backed by tokens it already controls, with no check that the depositor/recipient isn't the vault itself. The Push Chain analog is the inbound-deposit path in `x/uexecutor`: the `Recipient` field of an `Inbound` (fully attacker-controlled — it is arbitrary calldata from a source-chain event that Universal Validators merely observe and vote on for existence/content, not for "safety" of the target) is used, unchecked against the protocol's own system-contract addresses, as the mint target for `depositPRC20Token` / `depositPRC20WithAutoSwap` on the `UNIVERSAL_CORE` handler contract (address `0x...C0`, the contract that also functions as the module's own auto-swap/liquidity/gas-refund vault).

### Finding Description
`Inbound.ValidateForExecution` in [1](#0-0)  only validates that `Recipient` is non-empty and a syntactically valid hex address. It never checks whether `Recipient` equals a Push Chain system contract such as `UNIVERSAL_CORE` (`0x...C0`), `UNIVERSAL_GATEWAY_PC` (`0x...C1`), the `FactoryV1` proxy (`0x...eA`), or the `uexecutor` module's own EVM address, as defined in [2](#0-1)  and [3](#0-2) .

Because `IsCEA=true` bypasses the normal factory/UEA-origin lookup and uses the attacker-supplied `Recipient` directly, an attacker can set `Recipient = UNIVERSAL_CORE's address` on a real (honestly observed) source-chain event. The finalized inbound then flows to `ExecuteInboundFunds` / `ExecuteInboundFundsAndPayload` / `ExecuteInboundGasAndPayload`, all of which call `depositPRC20`/`gasAndPayloadDepositAutoSwap` with that address as `to`: [4](#0-3) [5](#0-4) 

`depositPRC20` resolves the token config and calls `CallPRC20Deposit`, which issues a `DerivedEVMCall` to `UNIVERSAL_CORE.depositPRC20Token(prc20, amount, target)` as the module account: [6](#0-5) [7](#0-6) 

Because the recipient (`target`) is unchecked, this mint can be pointed directly at `UNIVERSAL_CORE`'s own address — the same contract that internally functions as the swap router / liquidity vault for `depositPRC20WithAutoSwap` and `refundUnusedGas` (see `CallPRC20DepositAutoSwap`, `CallUniversalCoreRefundUnusedGas`: [8](#0-7) ). Additionally, in the non-UEA branch of the CEA path the code detects that the recipient has code and treats it as a generic "smart contract recipient," then calls `executeUniversalTx` on it (`CallExecuteUniversalTx`), unaware that the target is actually a privileged Push Chain system contract rather than an ordinary user contract: [9](#0-8) 

The test suite explicitly documents that the isCEA path "uses recipient directly without factory lookup" and lands funds "at the explicitly passed recipient... regardless of sender identity," confirming there is no allowlist/denylist enforced anywhere along this path: [10](#0-9) 

### Impact Explanation
Minting PRC20 balance directly into `UNIVERSAL_CORE`'s own address corrupts the protocol's internal accounting for that contract:
- `UNIVERSAL_CORE` is also the contract that executes `depositPRC20WithAutoSwap`, quotes swaps via `GetSwapQuote`, and pays `refundUnusedGas` — functions that (based on the visible ABI) operate over PRC20 balances the contract holds. An attacker-inflated, unbacked PRC20 balance sitting in `UNIVERSAL_CORE`'s own account is indistinguishable, from the module's Go-side bookkeeping perspective, from genuine deposits, since `depositPRC20Token` on that same contract is the identical function used for legitimate deposits.
- This is a concrete "protocol-controlled funds" impact under the allowed scope: it corrupts "PRC20 or native asset accounting" and "token mapping" invariants for a system contract that other unprivileged users' subsequent inbound legs (auto-swap quoting, gas refunds) rely on.
- Because Solidity-level access control inside `UNIVERSAL_CORE` (the actual Solidity implementation is outside this Go repository's index and could not be verified) is the only remaining backstop, this repository's own recipient-validation layer provides zero protection — the Go-side `ValidateForExecution` and the `IsCEA` dispatch logic never reject a system-contract recipient.

### Likelihood Explanation
High reachability: the attacker only needs to emit one ordinary, real cross-chain deposit event on a supported source chain with `Recipient` set to a well-known, publicly documented, fixed system-contract address (`0x...C0`, `0x...C1`, `0x...eA`, etc., all hardcoded in `x/uregistry/types/constants.go` / `x/uexecutor/types/constants.go`), and get it honestly observed and voted on by Universal Validators exactly like any normal inbound — no validator collusion or privileged action is required. `IsCEA=true` bypasses the sender-derived UEA lookup entirely, so any external sender/asset can trigger this.

### Recommendation
In `Inbound.ValidateForExecution` (and/or centrally in the CEA dispatch logic in `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`), reject inbounds whose `Recipient` resolves to any address in `uregistrytypes.SYSTEM_CONTRACTS` (or the `uexecutor`/`uregistry` module accounts, or the `FactoryV1` proxy/impl addresses). This mirrors the Aera fix pattern of explicitly disallowing the "vault" (here, the protocol's own system/vault contracts) as a valid deposit target.

### Proof of Concept
1. Attacker sends a normal token transfer/deposit event on a supported source chain (e.g. Sepolia) with an inbound payload whose `Recipient = "0x00000000000000000000000000000000000000C0"` (the `UNIVERSAL_CORE` address) and `IsCEA = true`, `TxType = FUNDS` (or `FUNDS_AND_PAYLOAD`).
2. Universal Validators honestly observe and vote on this real event; quorum is reached via normal `MsgVoteInbound` flow — no malicious validator behavior required.
3. `Inbound.ValidateForExecution` passes because `0x...C0` is a syntactically valid hex address ( [11](#0-10) ).
4. `ExecuteInboundFunds` calls `depositPRC20(..., recipient=0x...C0, ...)`, which calls `CallPRC20Deposit`, issuing `depositPRC20Token(prc20, amount, 0x...C0)` as the module account ( [4](#0-3) , [12](#0-11) ).
5. PRC20 tokens are minted directly to `UNIVERSAL_CORE`'s own balance instead of any real user account, inflating the system contract's holdings with no matching real economic backing check at the Go/module layer.

Note: I could not verify from this repository's index whether the Solidity implementation of `UNIVERSAL_CORE` (only its ABI is present in `x/uexecutor/types/abi.go`) contains its own internal `require(target != address(this))` guard, since the actual contract source lives in the separate `pushchain/evm` fork repository, not in this indexed codebase. If such a guard already exists at the Solidity layer, the practical exploitability would be blocked there instead — this could not be confirmed from the available index.

// Called after ballot finalization, before ExecuteInbound. Failures here produce a failed
// PCTx and (for non-isCEA) a revert outbound, rather than dropping the vote.
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
