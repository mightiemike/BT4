### Title
Declare-transaction compilation semaphore can be permanently exhausted by a hung class-manager/compiler request, causing indefinite denial-of-service for new Declare transactions - ([File: crates/apollo_gateway/src/gateway.rs])

### Summary
`Gateway::add_tx_inner` acquires a permit from `declare_compilation_semaphore` before converting a `Declare` transaction, and only releases it (`drop(compilation_permit)`) after `convert_rpc_tx_to_internal_and_executable_txs` returns. [1](#0-0) 
That conversion calls `class_manager_client.add_class`, which in turn calls the Sierra compiler component (`self.compiler.compile(class.clone()).await`) over an async component-client channel. [2](#0-1) 
If that call never resolves — exactly the class of bug reported in the external report, where an external/async request that is awaited indefinitely never completes and is never cancelled — the semaphore permit is held forever. This is directly analogous to the "pending request never times out, blocking the state machine and any resubmission" bug class described in the external report.

### Finding Description
`add_tx_inner` performs, for `Declare` transactions only:
```
let compilation_permit = ... self.declare_compilation_semaphore.try_acquire() ...
let (internal_tx, executable_tx, proof_data) =
    self.convert_rpc_tx_to_internal_and_executable_txs(tx, &tx_signature).await?;
drop(compilation_permit);
``` [3](#0-2) 

`convert_rpc_tx_to_internal_and_executable_txs` awaits `self.transaction_converter.convert_rpc_tx_to_internal_rpc_tx(tx)`, which for `Declare` transactions calls `self.class_manager_client.add_class(tx.contract_class).await?`. [4](#0-3) 

`ClassManager::add_class` awaits `self.compiler.compile(class.clone()).await`, a call to a separate compiler component (potentially reached over a remote or local in-process component-client channel). [5](#0-4) 

The codebase itself documents, in an analogous (already-patched) code path, that in-process component channels to a class manager "carry no request timeout of [their] own" and that a stalled component can leave a caller awaiting forever: [6](#0-5) 
That fix (`ClassReader::deadline` / `block_on_request`) was applied only to the read path used by state readers, not to the Gateway's declare-time compilation call chain (`add_tx_inner` → `convert_rpc_tx_to_internal_and_executable_txs` → `add_class` → `compiler.compile`), which has no analogous timeout. [7](#0-6) 

The semaphore is deliberately small and fixed (`gateway_config.static_config.max_concurrent_declare_compilations`, default 40) specifically to bound CPU/memory usage of concurrent compilations: [8](#0-7) 
and the codebase's own test explicitly demonstrates that when all permits are held (e.g., by a stuck conversion), any further declare is rejected outright with `TransactionLimitExceeded`, with no mechanism to detect or recover a permit whose holder has stalled: [9](#0-8) 

Because `try_acquire` fails fast (rather than queueing) once permits run out, and there is no timeout anywhere on the awaited `add_class`/`compile` call, a small number of Declare transactions (at most `max_concurrent_declare_compilations`, e.g. 40) whose compilation stalls indefinitely (compiler subprocess hang, deadlocked/overloaded remote Sierra-compiler component, or a stalled in-process channel as the codebase's own comments describe) permanently exhausts the semaphore. From that point, every legitimate user submitting a Declare transaction is rejected forever, and the gateway has no cancellation/retry path (unlike the recommended mitigation in the external report — cancel the stuck request and let the caller resubmit).

### Impact Explanation
This is a persistent denial-of-service specific to Declare transaction admission on the affected sequencer node: once the small, fixed pool of compilation permits is exhausted by stuck requests, the node can never again accept new Declare transactions (network unable to confirm new Declare transactions) until the process is restarted. Unlike a resource-only slowdown, this is a hard, permanent block on transaction-type admission reachable by any unprivileged sender submitting ordinary Declare transactions, with no automatic recovery.

### Likelihood Explanation
Reaching the semaphore-exhaustion state requires a small number (up to `max_concurrent_declare_compilations`, default 40) of Declare transactions whose compilation call never completes. Any transient stall of the Sierra-compiler component (overload, deadlock on certain crafted Sierra input, restart race, or a partitioned remote compiler) that hangs rather than erroring out for even a handful of concurrent declares can trigger the permanent lock, since there is no timeout to break the hang and release the permit.

### Recommendation
Bound the compilation call awaited while holding `compilation_permit` with an explicit timeout (analogous to the `ClassReader::deadline`/`block_on_request` pattern already used elsewhere in the codebase), releasing the permit and returning an error to the caller (and letting the underlying compile task finish in the background) if the class-manager/compiler round trip does not complete within a bounded time. This prevents any single stalled compilation from permanently holding one of the limited slots.

### Proof of Concept
1. Configure/observe a sequencer with `max_concurrent_declare_compilations = N` (default 40). [8](#0-7) 
2. Submit N Declare transactions whose Sierra payload causes the compiler component to hang (e.g., compiler-level deadlock/overload, or a partitioned/stalled class-manager/compiler channel) so that `self.compiler.compile(...).await` inside `add_class` never returns. [5](#0-4) 
3. Each of these N calls holds its `compilation_permit` forever since `drop(compilation_permit)` in `add_tx_inner` is never reached. [3](#0-2) 
4. Any subsequent Declare transaction from any user now fails `declare_compilation_semaphore.try_acquire()` and is rejected with `too_many_concurrent_declare_compilations`/`TransactionLimitExceeded`, exactly as demonstrated by the existing test `test_declare_compilation_concurrency_limit`, but with no way for the permits to ever be released. [9](#0-8)

impl ClassReader {
    /// Runs `request` on `self.runtime`, bounding it by `self.deadline` when set.
    ///
    /// Spawns `request` rather than awaiting it directly: a local class manager is reached
    /// through a channel whose response sender the server already holds once the request is
    /// sent (see `LocalComponentClient::send`), and the server panics if that channel's receiver
    /// is dropped before the response is sent — "considered a bug" by its own comment, since a
    /// well-behaved client always waits for its response. Racing `request` itself against the
    /// deadline with `tokio::time::timeout` would drop it, and that receiver, the moment the
    /// deadline passed. Spawning first means only our wait is bounded; `request` keeps running
    /// to completion in the background so the server never observes a closed channel.
    fn block_on_request<Fut>(&self, request: Fut) -> StateResult<Fut::Output>
    where
        Fut: Future + Send + 'static,
        Fut::Output: Send + 'static,
    {
        let Some(deadline) = self.deadline else {
            return Ok(self.runtime.block_on(request));
        };

        self.runtime.block_on(async {
            let request_task = self.runtime.spawn(request);
            match tokio::time::timeout_at(deadline.into(), request_task).await {
                Ok(join_result) => join_result.map_err(|join_error| {
                    StateError::StateReadError(format!(
                        "Class manager request task panicked: {join_error}"
                    ))
                }),
                Err(_elapsed) => Err(StateError::StateReadError(
                    "Class manager request timed out; the reader's deadline passed.".to_string(),
                )),
            }
        })
    }

#[rstest]
#[tokio::test(flavor = "multi_thread")]
async fn test_declare_compilation_concurrency_limit(mut mock_dependencies: MockDependencies) {
    mock_dependencies.config.static_config.max_concurrent_declare_compilations = 1;

    // Both declares run stateless validation, so replace the fixture's single-call mock with one
    // that accepts repeated calls.
    let mut mock_stateless_transaction_validator = MockStatelessTransactionValidatorTrait::new();
    mock_stateless_transaction_validator.expect_validate().returning(|_| Ok(()));
    mock_dependencies.mock_stateless_transaction_validator = mock_stateless_transaction_validator;

    // The first declare's conversion performs the Sierra-to-CASM compilation while holding the
    // single permit. Make that conversion block so the second declare arrives while the permit is
    // still held: `compilation_started_sender` signals that the permit is held, and the conversion
    // then parks on `release_compilation_receiver` until the test lets it finish.
    let (compilation_started_sender, compilation_started_receiver) =
        tokio::sync::oneshot::channel();
    let (release_compilation_sender, release_compilation_receiver) = std::sync::mpsc::channel();
    mock_dependencies
        .mock_transaction_converter
        .expect_convert_rpc_tx_to_internal_rpc_tx()
        .return_once(move |_| {
            compilation_started_sender.send(()).unwrap();
            release_compilation_receiver.recv().unwrap();
            // Fail the conversion so the first declare short-circuits here instead of running the
            // full admission path; its outcome is irrelevant, so the specific error is arbitrary.
            Err(TransactionConverterError::ClassNotFound { class_hash: ClassHash::default() })
        });

    let gateway = Arc::new(mock_dependencies.gateway());

    // Spawn the first declare and wait until it holds the permit inside compilation.
    let first_declare_task = {
        let gateway = gateway.clone();
        tokio::spawn(async move { gateway.add_tx(declare_tx(), None).await })
    };
    compilation_started_receiver.await.unwrap();

    // The second declare cannot acquire a permit and must be rejected immediately.
    let second_declare_error = gateway.add_tx(declare_tx(), None).await.unwrap_err();
    assert_eq!(
        second_declare_error.code,
        StarknetErrorCode::KnownErrorCode(KnownStarknetErrorCode::TransactionLimitExceeded)
    );

    // Release the first declare so its task and the blocked worker thread can wind down.
    release_compilation_sender.send(()).unwrap();
    let _ = first_declare_task.await;
}
