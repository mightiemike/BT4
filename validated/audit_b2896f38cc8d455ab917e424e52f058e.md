### Title
Sequential, permissionless Exchange IDs allow a chain re-org to substitute a malicious pool for a pending Exchange trade - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator` assigns new exchange (AMM pool) instances a purely sequential ID derived from `dynamicStore.getLatestExchangeNum()`, with no binding to the content (token pair) that was used to create it. `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all resolve the exchange to operate on solely by this numeric `exchangeId`. Because java-tron implements a genuine reorg/fork-switch mechanism (`Manager.switchFork` / `eraseBlock`), an exchange creation transaction can be reverted and replaced by a different `ExchangeCreateContract` that receives the exact same sequential ID but a different token pair, causing later `ExchangeTransactionContract`s that reference that ID to execute against unintended, potentially malicious/worthless assets.

### Finding Description
`ExchangeCreateActuator.execute()` computes the new exchange's identifier as:
```java
long id = addExact(dynamicStore.getLatestExchangeNum(), 1);
...
dynamicStore.saveLatestExchangeNum(id);
``` [2](#0-1) 

This `id` is a monotonically increasing counter stored in `DynamicPropertiesStore`, not a hash of the exchange's parameters (creator, token pair, initial balances). Exchange creation is fully permissionless — any account with sufficient balance/assets can call it, mirroring the "permissionless market creation" precondition in the original report.

All downstream actuators that operate on an existing exchange look it up purely by this numeric ID:
```java
ExchangeCapsule exchangeCapsule = Commons
    .getExchangeStoreFinal(dynamicStore, exchangeStore, exchangeV2Store)
    .get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()));
``` [4](#0-3) 

There is no verification that the exchange retrieved is the same instance (same token pair / same creator / same creation block) the caller originally observed when constructing their `ExchangeTransactionContract`. The only content check performed in `doValidate()` is that the trader's chosen `tokenID` matches one of the *current* exchange's two token IDs:
```java
if (!Arrays.equals(tokenID, firstTokenID) && !Arrays.equals(tokenID, secondTokenID)) {
  throw new ContractValidateException("token is not in exchange");
}
``` [5](#0-4) 

This check validates against whatever exchange currently occupies that ID slot — it provides no guarantee the pool is the one the user intended.

java-tron has a real, exercised reorg path: `Manager.pushBlock` detects a competing heavier branch and calls `switchFork`, which erases the current head's blocks via `eraseBlock()`/`revokingStore.fastPop()` and replays the new branch's blocks via `applyBlock`, re-executing all of its transactions (including re-verifying signatures via the `setVerified(false)` reset added for exactly this replay path): [1](#0-0) [6](#0-5) 

This is corroborated by the test `switchForkShouldPostFullNodeFilterForNewBranch`, which drives a real reorg that discards one branch (`A`) and replays a heavier competing branch (`B1`, `B2`), confirming the mechanism is live and testable, not theoretical. [7](#0-6) 

Attack scenario:
1. Honest user Alice creates Exchange `id=N` (e.g., TRX/GoodToken) via `ExchangeCreateContract`.
2. Trader Bob observes exchange `N` and broadcasts an `ExchangeTransactionContract` referencing `exchangeId=N`, `tokenId=TRX`, intending to receive `GoodToken`.
3. Before Bob's transaction is confirmed/solidified, a reorg occurs (`switchFork`) that reverts the branch containing Alice's `ExchangeCreateContract`.
4. A malicious actor Mallory quickly issues her own `ExchangeCreateContract` on the new canonical branch. Because `getLatestExchangeNum()` was rewound by the reorg, Mallory's exchange is assigned the same sequential `id=N`, but with a token pair of `TRX`/`WorthlessToken` that Mallory fully controls.
5. Bob's still-pending `ExchangeTransactionContract` (`exchangeId=N`, `tokenId=TRX`) is included on the new branch. It passes `doValidate()` because `TRX` is still one of the two tokens in Mallory's exchange, and `ExchangeTransactionActuator.execute()` debits Bob's TRX and credits him with `anotherTokenID` = `WorthlessToken` instead of the `GoodToken` he intended.
6. Mallory can seed her exchange with a favorable trade curve so that Bob's TRX flows into her pool and she withdraws/drains it, realizing the stolen funds.

This directly mirrors the Royco/RecipeKernel bug class: sequential, non-content-bound identifiers referenced by pending user intents, combined with a re-org that lets an attacker re-mint the identifier with malicious semantics.

### Impact Explanation
A successful exploitation results in direct loss of user funds (TRX or tokens) during an `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` executed against a substituted, attacker-controlled pool instead of the one the user intended — a concrete settlement/accounting impact matching the "underpriced-public-work"/settlement categories (funds move to unintended, attacker-controlled destinations because the referenced state object's identity is not authenticated). It also creates a re-org-incentivization dynamic identical to the original report: attackers are financially motivated to induce or race reorgs around exchange creation to steal from pending traders.

### Likelihood Explanation
Requires: (a) an in-flight reorg (feasible in DPoS chains as demonstrated by the live `switchFork` mechanism and its dedicated tests), (b) a victim who submitted an `ExchangeTransactionContract`/inject/withdraw against a very recently created exchange before it reached a safe confirmation depth, and (c) an attacker able to race a new `ExchangeCreateContract` into the replacement branch before the victim's queued transaction gets mined. This is a timing-dependent, opportunistic attack rather than a guaranteed one-click exploit, but the primitives (permissionless exchange creation, ID-only referencing, and a real reorg/fork-switch code path) are all present and exercised in tests, making it a credible, non-theoretical risk for exchanges created shortly before a reorg window.

### Recommendation
Bind exchange references to content, not just the sequential counter: derive the exchange identifier (or an additional check performed during `validate()`) from a hash of the immutable creation parameters (creator address, first/second token IDs, creation block/timestamp), and have `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` verify this hash against the stored `ExchangeCapsule` before executing, rejecting the transaction if the referenced exchange's content no longer matches what the caller expects (analogous to the Royco fix of replacing `numMarkets`-based lookups with hash-based lookups). Alternatively/additionally, require a minimum confirmation depth on the exchange's creation block before it can be traded against, so recently created exchanges cannot be immediately exploited during a reorg window.

### Proof of Concept
1. Deploy/checkout a private java-tron chain with two witnesses able to produce competing branches (as exercised in `ManagerTest#switchForkShouldPostFullNodeFilterForNewBranch`).
2. On branch A: broadcast `ExchangeCreateContract` from Alice for `TRX/GoodToken`, which is assigned `exchangeId = N` (verify via `dynamicStore.getLatestExchangeNum()`), then broadcast (but do not yet let solidify) Bob's `ExchangeTransactionContract` with `exchangeId = N`, `tokenId = TRX_SYMBOL_BYTES`, some `quant`.
3. Force a reorg by having a heavier competing branch B (as in the test, `p -> b1 -> b2`) that does not include Alice's `ExchangeCreateContract`, causing `Manager.switchFork` to call `eraseBlock`/rewind `dynamicStore`'s `LatestExchangeNum`.
4. On branch B, broadcast Mallory's `ExchangeCreateContract` for `TRX/WorthlessToken`; confirm it also receives `exchangeId = N` (same `dynamicStore.getLatestExchangeNum()+1` value as before the reorg).
5. Allow Bob's previously-broadcast `ExchangeTransactionContract` (still referencing `exchangeId = N`, `tokenId = TRX`) to be included on branch B.
6. Assert `ExchangeTransactionActuator.execute()` succeeds and Bob's account balance shows a debit of TRX and a credit of `WorthlessToken` (`anotherTokenID` derived from Mallory's exchange) rather than `GoodToken`, confirming that Bob's trade was silently rerouted to the attacker's substituted pool at the same `exchangeId`.
