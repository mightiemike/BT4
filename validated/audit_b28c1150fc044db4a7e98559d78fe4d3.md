## Analog Found: Removing a whitelisted token config permanently freezes users' bridged PRC20 balances

### Title
Unrecoverable freeze of already-minted PRC20 balances when `MsgRemoveTokenConfig` deletes a token still in circulation - (File: `x/uregistry/keeper/msg_remove_token_config.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
`x/uregistry`'s `RemoveTokenConfig` deletes a `TokenConfig` row (and its `PRC20Index` entry) with no check for outstanding PRC20 supply or open UniversalTx state, mirroring the audited ERD/Quantstamp finding where `CollateralManager.removeCollateral()` removes support for an asset that users still hold, causing a sudden, unrecoverable break in accounting for those users.

### Finding Description
`RemoveTokenConfig` unconditionally deletes the `(chain, tokenAddress)` row from `TokenConfigs`, which also drops the reverse `PRC20Index` entry used to resolve a PRC20 contract address back to its external-chain token: [1](#0-0) 

Once removed, `GetTokenConfigByPRC20` can never resolve that PRC20 address again — this is confirmed by the module's own tests: [2](#0-1) 

The outbound-creation path in `x/uexecutor` (triggered by an ordinary, unprivileged user withdrawing their PRC20 balance back to the source chain through `UniversalGatewayPC`) depends on this exact lookup with no fallback: [3](#0-2) 

If `GetTokenConfigByPRC20` errors, `BuildOutboundsFromReceipt` hard-fails and the entire outbound construction aborts, propagating up through `AttachOutboundsToExistingUniversalTx` / `CreateUniversalTxFromReceiptIfOutbound`: [4](#0-3) 

This is inconsistent with how the same module handles a missing token config on the *inbound-revert* path, where `buildRevertOutbound` treats a `GetTokenConfig` failure as non-fatal and still emits the outbound (just without gas fields): [5](#0-4) 

No equivalent tolerance exists for the withdrawal/outbound-creation path. As long as `MsgRemoveTokenConfig` (admin-authorized, but with no check for outstanding supply) has deleted a token config, any unprivileged holder of that PRC20 permanently loses the only mechanism to redeem it back to the native asset on the source chain — the withdrawal call will fail deterministically, forever, for every retry, since the missing registry row can never be resolved again through ordinary channels.

### Impact Explanation
This matches the "permanent freezing … of user … funds" category in the allowed impact gate. Users holding the now-unsupported PRC20 cannot bridge it out; their asset is economically stranded on Push Chain with no protocol-provided recovery path once the token config is removed, exactly analogous to the original report's "if a user has deposited only stETH and it becomes unsupported, their [position] would drop to zero" — here the position (redeemable value) drops to zero because the reverse mapping needed to construct a valid outbound no longer exists.

### Likelihood Explanation
The trigger requires an admin to call `MsgRemoveTokenConfig` while PRC20 supply for that token is still outstanding — this is a normal, foreseeable operational action (deprecating a legacy token/chain integration) rather than key compromise or malicious governance, so it is a realistic and not merely theoretical scenario. The subsequent freeze is then triggered purely by an unprivileged user's ordinary withdrawal attempt, which deterministically fails.

### Recommendation
- Add a guard in `RemoveTokenConfig` (or its `MsgServer` handler) that rejects removal while the corresponding PRC20 has non-zero total supply, or requires migrating/burning outstanding supply first.
- Alternatively, make `BuildOutboundsFromReceipt` tolerant of a missing `TokenConfig`, mirroring `buildRevertOutbound`'s graceful degradation, so a withdrawal can still complete (e.g., by falling back to a raw PRC20 address instead of the resolved external asset address) rather than failing permanently.

### Proof of Concept
1. User bridges `TokenX` from `eip155:1` to Push Chain; a PRC20 representation is minted to their UEA.
2. Admin calls `MsgRemoveTokenConfig{chain: "eip155:1", token_address: TokenX}` (a legitimate, authorized admin config-management action, not privileged abuse) — supported by the existing integration test that removes a token config mid-flow (`test/integration/uexecutor/inbound_synthetic_bridge_test.go:368-372`, demonstrating the codebase already exercises this exact removal scenario for the inbound side).
3. User attempts to withdraw their PRC20 balance for `TokenX` back to `eip155:1` via `UniversalGatewayPC`.
4. `BuildOutboundsFromReceipt` calls `GetTokenConfigByPRC20(ctx, "eip155:1", <TokenX PRC20 addr>)`, which now returns `collections.ErrNotFound` (per `TestGetTokenConfigByPRC20_RemoveDropsIndexEntry`).
5. Outbound creation aborts; the user's PRC20 balance can never be withdrawn through this path again, for as long as the token config remains removed.

// RemoveTokenConfig removes an existing token configuration in the uregistry.
func (k Keeper) RemoveTokenConfig(ctx context.Context, chain, tokenAddress string) error {
	storageKey := types.GetTokenConfigsStorageKey(chain, tokenAddress)

	// Check if the token config exists
	if has, err := k.TokenConfigs.Has(ctx, storageKey); err != nil {
		return err
	} else if !has {
		return fmt.Errorf("token config for %s on chain %s does not exist", tokenAddress, chain)
	}

	if err := k.TokenConfigs.Remove(ctx, storageKey); err != nil {
		return err
	}
	k.Logger().Info("token config removed",
		"chain", chain,
		"token_address", tokenAddress,
	)
	return nil
}

// TestGetTokenConfigByPRC20_RemoveDropsIndexEntry: removing a TokenConfig
// must drop its PRC20Index entry (otherwise lookup would return a non-existent

func TestGetTokenConfigByPRC20_RemoveDropsIndexEntry(t *testing.T) {
	ctx, k, _ := setupPRC20Keeper(t)

	key := types.GetTokenConfigsStorageKey(tcChainA, "0xUSDC")
	require.NoError(t, k.TokenConfigs.Set(ctx, key, makeTokenCfg(tcChainA, "0xUSDC", "0xPRC20")))

	got, err := k.GetTokenConfigByPRC20(ctx, tcChainA, "0xPRC20")
	require.NoError(t, err)
	require.Equal(t, "0xUSDC", got.Address)

	require.NoError(t, k.TokenConfigs.Remove(ctx, key))

	_, err = k.GetTokenConfigByPRC20(ctx, tcChainA, "0xPRC20")
	require.ErrorIs(t, err, collections.ErrNotFound, "remove must drop the index entry")
}

// AttachOutboundsToExistingUniversalTx
// Used when UniversalTx already exists (e.g. inbound execution)
// It attaches outbounds extracted from receipt to the existing utx.
func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}

// CreateUniversalTxFromReceiptIfOutbound
// Creates a UniversalTx ONLY if outbound events exist in the receipt.
// Safe to call from ExecutePayload, EVM hooks
func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
