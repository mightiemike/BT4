## Analysis

The reported class (residual/leftover division remainder silently dropped from an accounting ledger, low impact but high-likelihood because it recurs on every invocation) maps directly onto the UV reward-boost logic in `x/uvalidator/abci.go`'s `AllocateTokens`, which runs in `BeginBlocker` on every block that collects transaction fees — a flow triggered purely by ordinary user transactions paying gas, with no privileged actor involved.

### Title
Precision loss in `AllocateTokens` under-funds the distribution module relative to its recorded validator reward ledger - (File: `x/uvalidator/abci.go`)

### Summary
`AllocateTokens` computes each active Universal Validator's boosted reward as a `sdk.DecCoins` value and credits it directly into the distribution module's internal (decimal) accounting via `AllocateTokensToValidator`, then separately computes how many *whole* coins to physically transfer from the `uvalidator` module account to back that credit. The whole-coin amount actually transferred is truncated twice, and the truncated fractional remainder is discarded instead of being carried forward, so the bank balance backing the distribution module's ledger becomes permanently short by that fraction every block.

### Finding Description
In `AllocateTokens` [1](#0-0) , for every active UV the code computes a `reward` as `sdk.DecCoins` and immediately calls `k.DistributionKeeper.AllocateTokensToValidator(ctx, validator, reward)` [2](#0-1) . This credits the *exact* decimal amount into the distribution module's internal ledger (`ValidatorCurrentRewards`), per `DistributionKeeper.AllocateTokensToValidator(ctx, val, tokens sdk.DecCoins)` [3](#0-2) .

The code then sums these per-validator decimal rewards into `allocated` and truncates it once to get the whole-coin amount to actually move to the distribution module account:
```
extraCoins, extraChange := allocated.TruncateDecimal()
``` [4](#0-3) 

`extraChange` (the fractional remainder of the sum of individually-truncated `AllocateTokensToValidator` calls) is folded into `remainingDec` and truncated a second time when computing `remainingFinal`, with its own fractional discard silently ignored:
```
remainingDec = remainingDec.Add(extraChange...)
remainingFinal, _ := remainingDec.TruncateDecimal()
``` [5](#0-4) 

Only `extraCoins` (the whole-coin floor of `allocated`) is transferred to the distribution module account:
```
if !extraCoins.IsZero() {
    err = k.BankKeeper.SendCoinsFromModuleToModule(ctx, types.ModuleName, distrtypes.ModuleName, extraCoins)
``` [6](#0-5) 

The bank-side bookkeeping is exact for integer `sdk.Coins` (feesCollectedInt is fully split between `extraCoins` and `remainingFinal`, and the module test confirms `distrGain + FeeCollector == feeAmount` at the integer level) [7](#0-6) . However, the distribution module's *internal decimal ledger* was already credited with the un-truncated `reward` for every UV via `AllocateTokensToValidator`, which sums to `allocated` — strictly greater than or equal to `extraCoins`. The fractional gap (`extraChange`, discarded at line 172) is never transferred to the distribution module account, and is never re-queued anywhere (no `rewardResidual`-style carry-forward exists). The distribution module's bank balance therefore becomes short of the amount its own accounting believes it holds for validators, by exactly this discarded fraction, on every block that has at least one active UV and nonzero collected fees.

This is the direct structural analog of the MultiRewards bug: a `TruncateDecimal`/division remainder that is computed but never carried into any residual/back-filling mechanism, silently vanishing from the ledger that's supposed to reconcile it.

### Impact Explanation
Low per-block, since the discarded amount is strictly less than 1 `upc` per denom (`extraChange` is always `< 1` before the final truncation). This constitutes corruption of the protocol's own reward accounting: the distribution module's `ValidatorCurrentRewards`/`ValidatorOutstandingRewards` ledger records more claimable value than the module account was ever funded with, i.e. an aggregate under-collateralization of protocol-controlled funds that is permanent (never corrected in a later block).

### Likelihood Explanation
High, because `AllocateTokens` runs in `BeginBlocker` [8](#0-7)  every block that has at least one active UV, is reachable purely through ordinary users paying transaction fees (no privileged action required), and accumulates deterministically block after block, exactly matching the "irrecoverable rewards keep accumulating on every invocation" likelihood description from the source report.

### Recommendation
Track the fractional remainder discarded at `remainingDec.TruncateDecimal()` (and/or `allocated.TruncateDecimal()`) as a persisted residual (analogous to `rewardResidual` in the original report) and fold it into the *next* block's `AllocateTokens` computation — or, at minimum, transfer `allocated`'s ceiling (rather than floor) of whole coins to the distribution module account so the module account is never short of what its internal decimal ledger promises.

### Proof of Concept
1. Configure 2+ active UVs with different voting powers so `powerFraction` per UV is non-terminating in binary/decimal (e.g. powers 100/200/150/50 as in the existing test) [9](#0-8) .
2. Each block, collect an odd `feeAmount` (e.g. 999) in the FeeCollector via ordinary user transaction fees.
3. Observe that `allocated` (sum of `reward` DecCoins credited via `AllocateTokensToValidator`) has a non-zero fractional part `extraChange` each block.
4. Confirm that `extraChange` is added into `remainingDec` and discarded at the second `TruncateDecimal()` call, and never appears in either `extraCoins` (sent to distribution) or `remainingFinal` (sent to FeeCollector) — i.e., trace that the distribution module's module account balance grows by `extraCoins` each block while `AllocateTokensToValidator` recorded `extraCoins + extraChange` of claimable decimal reward, with `extraChange` permanently unaccounted for and repeating every block.

func BeginBlocker(ctx sdk.Context, uvalidatorKeeper keeper.Keeper) error {
	defer telemetry.ModuleMeasureSince(types.ModuleName, time.Now(), telemetry.MetricKeyBeginBlocker)

	ctx.Logger().Debug("uvalidator BeginBlocker started", "block_height", ctx.BlockHeight())

	// determine the total power signing the block
	var previousTotalPower int64
	for _, voteInfo := range ctx.VoteInfos() {
		previousTotalPower += voteInfo.Validator.Power
	}

	// full amount will be allocated to community pool by distribution module itself
	if previousTotalPower == 0 {
		ctx.Logger().Debug("uvalidator BeginBlocker: no voting power, skipping token allocation", "block_height", ctx.BlockHeight())
		return nil
	}

	height := ctx.BlockHeight()
	if height > 1 {
		ctx.Logger().Info("uvalidator BeginBlocker: allocating tokens",
			"block_height", height,
			"total_previous_power", previousTotalPower,
			"vote_infos_count", len(ctx.VoteInfos()),
		)
		if err := AllocateTokens(ctx, previousTotalPower, ctx.VoteInfos(), uvalidatorKeeper); err != nil {
			ctx.Logger().Error("uvalidator BeginBlocker: token allocation failed",
				"block_height", height,
				"error", err.Error(),
			)
			return err
		}
		ctx.Logger().Info("uvalidator BeginBlocker: token allocation complete", "block_height", height)
	}

	return nil
}
