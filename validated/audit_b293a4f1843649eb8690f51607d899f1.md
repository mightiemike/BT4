### Title
Starknet OS `execute_replace_class` never verifies the class hash is declared before rewriting a contract's class - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The `replace_class` syscall is supposed to let a contract update its own class only to a class hash that actually corresponds to a declared class. The Rust Blockifier enforces this by reading the compiled class before writing the new class hash, but the equivalent logic in the Starknet OS Cairo program — the code that re-executes transactions to derive the committed state diff / state root — skips this check entirely, leaving a `TODO` acknowledging the gap. This mirrors the "follow a deleted profile" bug class: an identifier (class hash) is accepted and persisted into state without verifying it currently resolves to a real, existing entity (a declared class), because the validating check exists on one code path but is missing on the semantically-equivalent path that actually produces the committed state.

### Finding Description
The Blockifier's `replace_class` syscall implementation explicitly ensures the class exists before mutating state: [1](#0-0) 

```
fn replace_class(...) -> DeprecatedSyscallResult<ReplaceClassResponse> {
    // Ensure the class is declared (by reading it).
    syscall_handler.state.get_compiled_class(request.class_hash)?;
    syscall_handler.state.set_class_hash_at(syscall_handler.storage_address, request.class_hash)?;
    ...
}
```

`get_compiled_class` returns `StateError::UndeclaredClassHash` if the class hash was never declared, causing the syscall — and the whole transaction — to fail, as verified by the test `test_replace_class` (`crates/blockifier/src/execution/deprecated_syscalls/deprecated_syscalls_test.rs:375-391`) and `undeclared_class_hash` (`crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29`).

In contrast, the Starknet OS Cairo implementation of this same syscall — `execute_replace_class` — reads the requested `class_hash` from the syscall request and directly writes it into the contract's `StateEntry` without any equivalent existence check: [2](#0-1) 

```
func execute_replace_class{...}(contract_address: felt) {
    ...
    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );
    ...
}
```

The comment at line 902 explicitly documents that the "declared class" check is not yet implemented in the OS. This function is reached whenever any account or contract executes a `replace_class` syscall (invoked via `execute_deprecated_syscalls` / `REPLACE_CLASS_SELECTOR` dispatch, `crates/apollo_starknet_os_program/.../deprecated_execute_syscalls.cairo:676-688`), i.e. from a single, unprivileged transaction.

### Impact Explanation
The `contract_state_changes` dictionary written here directly feeds the state diff that the OS commits — it is the authoritative structure used to derive the new contracts trie / state root during Starknet OS re-execution and proof generation. If the OS's own logic for validating a `replace_class` syscall is weaker than the Blockifier's (which is what actually builds/executes the block during sequencing), it becomes a latent honest-node-divergence hazard on the "state reads and aliasing" / "Starknet OS re-execution" path explicitly in scope: any place where the OS is expected to *independently* re-derive validity of a state transition (rather than merely replay Blockifier's already-validated decisions) can accept a `replace_class` update to an undeclared/nonexistent class hash that the Blockifier would have rejected with `UndeclaredClassHash`, silently producing a contract whose recorded class hash does not correspond to any compiled class. Any subsequent call into that contract (or any component relying on `get_class_hash_at` returning a resolvable class) cannot be executed correctly, since no compiled program exists for that hash — the analogue of "following a deleted profile": an operation is permitted against an identifier that was never validated to still (or ever) correspond to a real underlying entity.

### Likelihood Explanation
The `replace_class` syscall is callable by any contract with no privilege requirements, and the affected function is on the syscall's normal execution path (no special preconditions beyond invoking the syscall with an arbitrary felt as `class_hash`). The gap is explicitly flagged by the code's own `TODO` comment, confirming it is a known, unaddressed omission rather than a hypothetical one. The blast radius is bounded by the extent to which the OS Cairo replay is treated as authoritative versus Blockifier being the sole enforcement point — this repo's structure (a separate, hint-driven Cairo re-implementation of every syscall) is exactly the kind of place such divergences are introduced and then reappear as security regressions the moment any OS-side validation is assumed to substitute for Blockifier's.

### Recommendation
Add the missing check in `execute_replace_class`: before writing the `new_state_entry`, verify (via a hint plus corresponding Cairo assertion, mirroring `finalize_class_hash`/`contract_class_component_hashes` checks used in declare) that `class_hash` corresponds to a class actually present in `contract_class_changes` or the committed class table for the current state, and revert/fail the syscall analogous to Blockifier's `UndeclaredClassHash` error path if it does not.

### Proof of Concept
1. Deploy any contract `C` that forwards to `replace_class_syscall(class_hash)` with an attacker-supplied `class_hash` (e.g. `test_contract.cairo`'s `test_replace_class`/`test_forbidden_syscall_in_virtual_mode` entrypoints already demonstrate the call site: `crates/blockifier_test_utils/resources/feature_contracts/cairo1/test_contract.cairo:1490-1491`).
2. Submit an invoke transaction from an account calling `C`'s replace-class entry point with a `class_hash` value that has never been declared on-chain.
3. In the Blockifier path, `syscall_handler.state.get_compiled_class(request.class_hash)` fails with `StateError::UndeclaredClassHash`, and the transaction reverts — this is verified behavior (`crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29`).
4. Inspect the OS Cairo implementation `execute_replace_class` (`crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo:881-920`): it performs no equivalent lookup/assertion before `dict_update`, confirmed by the explicit `TODO(Yoni, 1/1/2026)` comment at line 902 — i.e., were the OS Cairo logic ever relied upon to independently validate this transition (rather than simply replaying an already-Blockifier-validated trace), it would accept the undeclared class hash where the Blockifier would not.
