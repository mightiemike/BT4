### Title
Global contract-class cache lets a `CompiledClasses::V0` entry from a reverted/aborted block be treated as declared, bypassing the `is_declared` re-check applied to Cairo1 classes - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` explicitly documents and handles the case where the shared, process-wide `GlobalContractCache` can retain a class "from a reverted block" by re-verifying `is_declared` for Cairo1 (`RunnableCompiledClass::V1`/`V1Native`) hits, but the same re-check is skipped entirely for Cairo0 (`RunnableCompiledClass::V0`) hits.

### Finding Description
`get_compiled_from_class_manager` reads from `self.contract_class_manager` (a `NativeClassManager` wrapping a `GlobalContractCache`, i.e. an LRU cache keyed only by `ClassHash`, `crates/starknet_api/src/class_cache.rs`). This cache is process-global and long-lived: it is shared, via `contract_class_manager.clone()`, between the batcher's block-building/validating executors (`crates/apollo_batcher/src/block_builder.rs:788-800`) and the gateway's stateful transaction validator (`crates/apollo_gateway/src/stateful_transaction_validator.rs`), and it is never cleared on `revert_block` (`crates/apollo_batcher/src/batcher.rs:1426-1457` only calls `storage_writer.revert_block(height)`, not any class-cache invalidation). [1](#0-0) 

The code comment for the `_ =>` (Cairo1) branch states the exact threat model: "existence in the cache does not guarantee that [the class is declared] (it might contain a declared class from a reverted block, for example)" and therefore calls `self.state_reader.is_declared(class_hash)?` before trusting the cache. The `RunnableCompiledClass::V0(_) => {}` branch performs no equivalent check and unconditionally returns the cached class.

This is functionally analogous to the CVE's use-after-free bug class: an object (`CompiledClasses::V0`) that should have been invalidated when its underlying declaration was rolled back (revert/abort) is still reachable and used as if valid, because the code path responsible for invalidation-on-reuse only covers one of two variants.

Any flow that populates the global cache with a V0 entry for a class hash that never becomes canonically declared can poison the cache for that class hash indefinitely (bounded only by LRU eviction), because Cairo0 declare transactions are allowed to skip the "not already declared" check in some configurations (`crates/blockifier/src/transaction/transactions.rs:164-175`, gated by `disable_cairo0_redeclaration`), and because `set_and_compile` is invoked as soon as a class is fetched from `state_reader.get_compiled_classes` regardless of whether the surrounding transaction/block ultimately commits (`crates/blockifier/src/state/state_reader_and_contract_manager.rs:90-91`, `crates/blockifier/src/state/native_class_manager.rs:159-161`).

### Impact Explanation
If a V0 class hash is cached but the corresponding declaration never lands in the canonical committed state (e.g., speculative gateway/mempool validation of a Declare/Invoke that references it, or a batcher proposal/validate-block flow that is aborted or reverted via `revert_block` after warming the class cache), subsequent transactions on the same node (e.g. `DeployAccount`, `deploy` syscall, or `replace_class` for a still-Cairo0-tolerant path) that reference that class hash can succeed via `get_compiled_class` returning `Ok(...)` instead of `StateError::UndeclaredClassHash`, because the V0 branch never re-validates declaration status. Since the cache state differs from node to node (populated only on nodes that happened to execute/validate the reverted/aborted proposal, and subject to independent LRU eviction), this creates non-deterministic, node-local divergence in whether such a transaction succeeds or fails — i.e., honest nodes can disagree on transaction validity/outcome for the same input, which can lead to differing state roots / block hashes across otherwise-honest sequencers, or unauthorized deployment/execution of a contract class that was never actually declared on-chain.

### Likelihood Explanation
Reaching this requires: (1) getting a V0 class into the shared `contract_class_manager` cache via a code path that fetches it from a state reader without the corresponding declare committing (gateway stateful validation runs full blockifier execution against a `StateReaderAndContractManager` sharing this cache before mempool admission, and batcher proposals can be aborted/reverted after populating it), and (2) subsequently issuing a transaction that reads `get_compiled_class` for that same hash while the entry is still cached. Both are transaction-sender-reachable: nothing here requires operator/prover/p2p privilege. The main uncertainty is the precise reachable sequence that leaves a residual V0 cache entry while genuinely leaving the class permanently undeclared on the canonical chain (this is dependent on internal execution/validation scheduling not fully traced here), which affects the likelihood but not the presence of the missing check itself. This should be assessed as Medium-High likelihood given the explicit acknowledgment of the "reverted block" cache staleness scenario in the surrounding V1 code, paired with the demonstrable absence of the equivalent guard for V0.

### Recommendation
Apply the same `is_declared` re-validation to `RunnableCompiledClass::V0` cache hits as is already done for Cairo1/Native hits in `get_compiled_from_class_manager`, i.e., remove the `RunnableCompiledClass::V0(_) => {}` no-op branch and route V0 through the same `is_declared` check (or a V0-specific equivalent), so that a global-cache hit can never substitute for authoritative on-chain declaration status regardless of class version. Additionally, consider invalidating or partitioning the relevant cache entries on `revert_block` / proposal abort so that speculative executions of ultimately-non-committed blocks cannot leave permanently reachable state in the shared, cross-block-role cache.

### Proof of Concept
Not independently reproduced in this review (would require driving the gateway's stateful validator or a batcher validate/abort cycle to populate the shared `contract_class_manager` cache with a V0 class hash that never gets committed, then issuing a `DeployAccount`/`deploy`-syscall transaction against that hash on the same node) — the code-level gap (missing `is_declared` check for the `V0` branch, contrasted with the explicit check and comment for the Cairo1 branches) is directly verifiable at `crates/blockifier/src/state/state_reader_and_contract_manager.rs:70-87`.

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
