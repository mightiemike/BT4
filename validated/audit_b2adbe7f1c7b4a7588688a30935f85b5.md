### Title
Unhandled `receiver_shard_id` lookup failure panics the chunk-processing loop on stale `GlobalContractDistribution` receipts after resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the `Result` returned by `Receipt::receiver_shard_id`. For `GlobalContractDistribution` receipts, that call can legitimately return `Err(EpochError::ShardingError)` when the receipt's `target_shard` cannot be mapped into the current shard layout's split history — exactly analogous to CVE-2022-41860, where a lookup that can fail (unknown EAP-SIM dictionary entry) was not checked before being dereferenced, crashing the server. Here the "dictionary lookup" is the shard-layout split-history resolution, and the missing check is a bare `.unwrap()` instead of error propagation.

### Finding Description
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) computes the receiving shard for a receipt. For ordinary receipts it maps `receiver_id` to a shard; for `ReceiptEnum::GlobalContractDistribution` it uses the receipt's `target_shard`, and if that shard no longer exists in the current layout, falls back to `shard_layout.resolve_to_current_shard(target_shard)`: [1](#0-0) 

`resolve_to_current_shard` walks the shard layout's split history to find a descendant of an older shard id. This lookup is explicitly designed to fail when the target shard "does not exist in the shard layout or its split history" and returns `Err(EpochError::ShardingError(...))` in that case — this is the fallible "dictionary lookup."

The caller that matters for chunk processing, `DelayedReceiptQueueWrapper::receipt_filter_fn`, does not check for that failure — it unwraps directly: [2](#0-1) 

This function is invoked from `DelayedReceiptQueueWrapper::pop` (`runtime/runtime/src/congestion_control.rs:880-910`), which is called every chunk while draining the persistent delayed-receipt queue during `Runtime::process_delayed_receipts` (per the architecture doc, `runtime/runtime/src/lib.rs:2441` area). Any node applying that chunk — validator or otherwise — panics identically, which is a deterministic, chain-wide crash rather than a divergence, i.e., a transaction/receipt-triggered halt.

A `GlobalContractDistribution` receipt is created by any account's own `DeployGlobalContractAction`, a fully unprivileged action available to any transaction signer/contract deployer. If that receipt is delayed (pushed to the persistent delayed-receipts queue because the receiving shard is congested/compute-limited) across **two or more** resharding generations before it is popped, `target_shard` becomes a shard id from an arbitrarily old layout that the current layout's bounded split-history walk (`resolve_to_current_shard`) cannot resolve, producing the `Err` that then panics `receipt_filter_fn`'s `.unwrap()`.

This exact scenario is reproduced and explicitly documented as the vulnerability being guarded against in the test suite: [3](#0-2) 

The test's setup shows the entire trigger path is composed of unprivileged actions: deploying a contract, deploying a global contract (creating the distribution receipt with `target_shard` pinned to the deploying account's shard), and then submitting ordinary `FunctionCall` transactions to saturate the shard's compute budget so the receipt stays delayed through resharding: [4](#0-3) 

### Impact Explanation
If the target shard cannot be resolved (receipt stale across ≥2 resharding generations), every node processing the delayed queue for that shard hits `Err` in `receiver_shard_id` and panics on the `.unwrap()` in `receipt_filter_fn`. Because delayed-receipt draining happens deterministically for every chunk producer/validator applying that shard's chunks, this becomes a synchronized, transaction-triggered chain halt (all nodes crash while applying the same chunk), matching the accepted "transaction-triggered halt" impact category. No unauthorized value movement occurs, but chain liveness for the affected shard (and potentially the whole chain, since block production requires all shard chunks) stops until the affected binaries are patched/restarted — this is a critical availability failure directly analogous to the CVSS 7.5/high-severity DoS in the FreeRADIUS CVE.

### Likelihood Explanation
The trigger requires two independent, but individually cheap, conditions that are both reachable purely through submitted transactions:
1. Deploying a global contract from an account whose shard will be split (an ordinary `DeployGlobalContractAction`).
2. Keeping the resulting `GlobalContractDistribution` receipt in the delayed queue long enough to survive two resharding events — achievable by any account submitting enough compute-heavy transactions to keep the shard's chunk gas/compute budget saturated (an ordinary pattern of spamming `FunctionCall` transactions), as demonstrated by the reproduction test.

Resharding itself is an automatic, threshold-driven protocol mechanism (dynamic resharding based on shard memory usage) rather than an operator-privileged action, so an attacker does not need validator/operator access — they only need to time an ordinary global-contract deployment relative to the chain's natural (or attacker-accelerated, via storage-usage growth) resharding schedule. This makes the bug realistically reachable from the unprivileged transaction-sender surface, though it does require the chain to undergo two resharding generations while the receipt is pinned in the queue, which is a timing/liveness precondition rather than a purely instantaneous single-transaction trigger.

### Recommendation
- Change `receipt_filter_fn` to propagate the error instead of unwrapping: have `DelayedReceiptQueueWrapper::pop` return `Result<Option<...>, RuntimeError>` reflecting the `EpochError` (mapping it to a `RuntimeError`/`StorageError::StorageInconsistentState`-style variant) rather than panicking.
- More fundamentally, fix `resolve_to_current_shard` / the shard-layout split-history retention so that `target_shard` can always be resolved regardless of how many resharding generations have elapsed while the receipt was delayed (e.g., retain full split lineage or re-stamp `target_shard` to the current layout whenever it is re-buffered/re-queued across a resharding boundary), removing the root cause rather than only guarding the symptom.
- Add regression coverage equivalent to `test_stale_global_contract_distribution_after_double_resharding` to CI so any regression is caught before release.

### Proof of Concept
The existing test in the codebase is itself the proof of concept and directly exercises the unprivileged transaction path:
1. An unprivileged account (`user0`) deploys a global contract, producing a `GlobalContractDistribution` receipt whose `target_shard` is `user0`'s current shard.
2. The same/any account submits ordinary heavy `FunctionCall` transactions (`burn_gas_raw`) every block to keep that shard's compute budget saturated, forcing the distribution receipt to sit in the persistent delayed-receipts queue.
3. Dynamic resharding is configured/allowed to split shards twice while the receipt remains delayed.
4. Once saturation stops and the delayed queue drains, `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` → `Receipt::receiver_shard_id` hits the `Err(EpochError::ShardingError)` path because the receipt's `target_shard` is two resharding generations stale, and the bare `.unwrap()` panics, stalling chain height (verified by the test's assertion that `head_height >= drain_end` would fail if the panic occurs). [5](#0-4)

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
