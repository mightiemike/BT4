## Finding

### Title
Rescue-outbound builder trusts attacker-supplied `prc20` from `RescueFundsOnSourceChain` without binding it to the original stuck asset - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`AttachRescueOutboundFromReceipt` is the module's analog to a "rescue mistakenly-stuck funds" mechanism (comparable to the reported `Reservoir` bug-class). It correctly ties the rescue *recipient* to server-stored state (`originalUtx.InboundTx.Sender` / `RevertInstructions.FundRecipient`), but it derives the rescue *asset* solely from the attacker-controllable `event.PRC20` field of the `RescueFundsOnSourceChain` log, never cross-checking it against the asset actually recorded for the stuck `UniversalTx`.

### Finding Description
In `x/uexecutor/keeper/create_outbound.go`, `AttachRescueOutboundFromReceipt` decodes the `RescueFundsOnSourceChain` event and, once it validates that the referenced `originalUtx` is genuinely stuck (CEA deposit `FAILED`, or non-CEA auto-revert `REVERTED`), builds the rescue outbound like this: [1](#0-0) 

The token used for the outbound (`ExternalAssetAddr`, `Prc20AssetAddr`) is resolved purely from `event.PRC20` — a field taken directly from the event log, which any unprivileged caller can supply when invoking the `UniversalGatewayPC` rescue entrypoint on Push Chain — via `GetTokenConfigByPRC20(ctx, originalUtx.InboundTx.SourceChain, event.PRC20)`. There is no check that `event.PRC20` matches the PRC20/native representation actually associated with `originalUtx.InboundTx.AssetAddr` (the token config that failed to deposit or whose auto-revert failed).

The amount used, however, is pulled from the original stuck deposit: [2](#0-1) 

So an attacker can submit a legitimate rescue call referencing *any* other user's genuinely-stuck `universalTxId` (this data is public — UTX ids and statuses are queryable), but pass an arbitrary, unrelated, already-registered `prc20` address for the same source chain. The keeper will happily build and persist a `RESCUE_FUNDS` outbound instructing the destination chain (`originalUtx.InboundTx.SourceChain`) to release `originalUtx.InboundTx.Amount` units of the *wrong* token to the legitimate stuck-fund owner, once the honest universal validators sign and relay it.

### Impact Explanation
This breaks the "Registry and accounting path" invariant explicitly called out in scope: token config / PRC20 mapping must not misroute value or attach the wrong asset semantics to an outbound. Because `Prc20AssetAddr`/`ExternalAssetAddr` are decoupled from the original deposit's actual token, TSS-signed outbound execution on the source chain will be instructed to release funds of an asset that was never locked for that `UniversalTx`. Depending on how the source-chain vault authorizes releases against the signed outbound payload, this can result in unauthorized release of a completely unrelated token's escrowed balance (funds belonging to other depositors of that token), i.e. protocol-controlled-fund misappropriation/drain triggered purely by an unprivileged Push Chain transaction — not by the attacker gaining the funds directly, but by corrupting canonical `UniversalTx`/outbound state and causing wrong-asset fund release.

### Likelihood Explanation
The only prerequisite is a genuinely stuck UTX (which occurs organically whenever a CEA deposit fails or an inbound auto-revert itself reverts — both are reachable through ordinary, unprivileged inbound flows, as shown by the existing `setupRescueFundsTest`/`setupRevertStuckInbound` test fixtures) and the ability to call the gateway's rescue entrypoint with an attacker-chosen `prc20` parameter for any `universalTxId`. Nothing in `AttachRescueOutboundFromReceipt` restricts the caller to the original depositor or checks the token consistency, so this is trivially reachable by any external, unprivileged actor.

### Recommendation
Before building the rescue outbound, resolve the token config from `originalUtx.InboundTx.SourceChain` + `originalUtx.InboundTx.AssetAddr` (the *original* deposit asset) and assert that its `NativeRepresentation.ContractAddress` equals `event.PRC20`. Reject the rescue (return an error, do not attach an outbound) on mismatch, exactly mirroring the deposit-vs-config binding already enforced elsewhere (e.g. `depositPRC20`, `k.uregistryKeeper.GetTokenConfig`).

### Proof of Concept
1. Drive a CEA inbound with an unregistered `AssetAddr` to quorum so `PcTx[0].Status == "FAILED"` (as in `setupRescueFundsTest`), leaving the UTX genuinely rescue-eligible.
2. As an unrelated unprivileged user, submit an EVM tx to `UniversalGatewayPC` invoking the rescue entrypoint, passing the victim's `universalTxId` but a `prc20` address for a *different*, unrelated, registered token on the same source chain (any address for which `GetTokenConfigByPRC20` succeeds).
3. `AttachRescueOutboundFromReceipt` accepts the event, passes all eligibility/duplicate checks (they only look at `originalUtx` status, not at `event.PRC20`), and attaches a `RESCUE_FUNDS` outbound with `ExternalAssetAddr`/`Prc20AssetAddr` set to the unrelated token and `Amount` equal to the original stuck deposit amount — as demonstrated by the existing `TestRescueFunds` fixtures, which never assert that the token supplied in the log matches the original `Inbound.AssetAddr`.
4. Once honest validators observe and finalize this outbound, TSS/relayer flow is instructed to release the wrong asset on the source chain for this UTX.
