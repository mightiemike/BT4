### Title
Unauthenticated front-runnable `initialize(address)` on the UEA Factory proxy lets any unprivileged account seize factory ownership at genesis - (File: `x/uexecutor/keeper/genesis.go`, `x/uexecutor/types/abi.go`)

### Summary
`x/uexecutor`'s `InitGenesis` deploys the UEA Factory proxy/implementation/proxy-admin contracts on fresh genesis via `deployFactoryEA` but never calls the Factory's `initialize(address initialOwner)` function during that same genesis operation. The Factory's `initialize` (per `FactoryV1ABI`) takes an attacker-controllable `initialOwner` argument with no caller restriction — exactly the class of bug described in the external report (unvalidated, front-runnable `initialize`). Because the chain begins accepting ordinary transactions immediately after genesis, and the Factory proxy is live with no owner set, any unprivileged external account can be first to submit an EVM call invoking `initialize(attackerAddress)` on the Factory before the legitimate operator does so.

### Finding Description
`deployFactoryEA` (`x/uexecutor/keeper/genesis.go:100-108`) only performs raw `SetAccount`/`SetCode`/`SetState` operations to place bytecode and set the `ProxyAdmin`'s `Ownable` slot directly: [1](#0-0) 

Notice that `deployProxyAdminContract` sets the `ProxyAdmin`'s owner slot directly with `evmKeeper.SetState` — a safe pattern that bypasses any callable initializer. But `deployFactoryProxy`/`deployFactoryImplContract` do **not** do the same for the Factory's `Ownable` owner slot; they only wire the proxy's implementation/admin slots: [2](#0-1) 

The Factory contract exposes a still-callable `initialize(address initialOwner)` (from `FactoryV1ABI`) with no on-chain restriction on who may call it or what value they may pass: [3](#0-2) 

The only place in the codebase that calls `initialize` on this Factory is test-only setup code, executed as a manual, separate EVM call after genesis deployment, using an explicit `owner` argument: [4](#0-3) 

No equivalent production code path was found that atomically initializes the Factory owner as part of `InitGenesis` or any block-0 transaction. `InitGenesis` itself only validates `Params` and restores KV state — it performs no Factory ownership bootstrapping: [5](#0-4) 

Given standard OpenZeppelin `Initializable` semantics (the `initializer` modifier only prevents *re*-initialization, not restricting the *first* caller's identity), this leaves a window between genesis block execution and whenever the legitimate deployer/admin transaction calling `initialize(legitimateOwner)` lands on-chain. Any unprivileged party who submits a competing `initialize(attacker)` transaction with sufficient priority (equal-or-higher gas price, faster relay, or simply being first to broadcast) becomes the Factory's `owner`.

### Impact Explanation
Once an attacker becomes Factory owner, the read-only/state-changing owner-gated functions on the same ABI become attacker-controlled:
- `setUEAProxyImplementation` — attacker can point all future UEA proxies at a malicious implementation contract.
- `registerNewChain` / `registerUEA` — attacker can bind arbitrary (malicious) implementation contracts as the canonical UEA implementation for any `chainHash`/`vmHash` pair.

Every subsequent `MsgExecutePayload` inbound execution and `DeployUEAV2`/`DeployUEA` call (the core "universal execution" path) routes through this same Factory (`types.FACTORY_PROXY_ADDRESS_HEX`) to resolve or deploy each user's Universal Executor Account: [6](#0-5) [7](#0-6) 

A malicious implementation registered by the rogue owner would let the attacker control the code deployed for every user's UEA going forward, which sits at the center of "hosting Universal Executor Accounts" and "PRC20 deposit/execute" flows described in the module design: [8](#0-7) 

This maps directly to the in-scope impact categories: unauthorized UEA execution, unauthorized module-originated EVM execution, and consequent draining/theft of user funds routed through UEAs — reachable by an ordinary unprivileged user racing a normal transaction against genesis/deployment, with no privileged access required.

### Likelihood Explanation
Likelihood depends entirely on operational practice not visible in this repository: if the deployment tooling submits the legitimate `initialize(owner)` call inside the same genesis block / cannot be preceded by any other transaction (e.g., if the chain's first block is produced with only pre-authorized transactions, or if `min-gas-prices`/permissioned mempool prevents outside submission before the admin tx lands), the front-run window may be zero in practice. I could not find such a guarantee in the searched code, deployment scripts, or `local-native`/`local-multi-validator` setup scripts — the only `initialize` invocation found anywhere is the manual test-harness call in `test/utils/contracts_setup.go`, executed as an explicit, separate step. Because I could not locate the actual mainnet/testnet deployment runbook or a guarantee that the initializing transaction is bundled atomically with genesis (this may live in off-repo deployment automation or in a file the index did not fully cover), I cannot confirm with certainty whether this window is exploitable in the live deployment process, only that the on-chain code contains no protection against it.

### Recommendation
- Set the Factory's `Ownable` owner storage slot directly at genesis via `evmKeeper.SetState`, exactly as already done for the `ProxyAdmin` contract in `deployProxyAdminContract`, instead of relying on a separate, racier `initialize` transaction.
- If an `initialize` call must remain, restrict it to a known deployer/module address (mirroring the external report's suggested `require(msg.sender == <trusted>)` pattern) and validate `initialOwner != address(0)`.
- Audit all other system contracts deployed via `x/uregistry`'s `deploySystemContracts` and any other genesis-time proxy deployments for the same "deployed-but-not-atomically-initialized" pattern.

### Proof of Concept
1. Observe that `deployFactoryEA` (`x/uexecutor/keeper/genesis.go`) deploys the Factory proxy/impl/admin at genesis but never calls `initialize` on the Factory proxy.
2. As soon as the chain accepts transactions, submit an EVM transaction calling `initialize(attackerAddress)` (ABI in `x/uexecutor/types/abi.go`) against `FACTORY_PROXY_ADDRESS_HEX` before the operator's own initialization transaction is included.
3. Query `owner()` on the Factory — it now returns `attackerAddress` (mirrors the test flow in `test/utils/contracts_setup.go:118-125`, but performed by an attacker instead of the legitimate deployer).
4. As owner, call `setUEAProxyImplementation`/`registerUEA` with attacker-controlled bytecode addresses.
5. Subsequent `DeployUEAV2` calls triggered by ordinary inbound processing or `MsgExecutePayload` deploy UEAs using the attacker's implementation, compromising universal execution and funds routed through those UEAs.

func deployFactoryProxy(ctx context.Context, evmKeeper types.EVMKeeper) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	proxyAddress := common.HexToAddress(types.FACTORY_PROXY_ADDRESS_HEX)
	proxyAdminOwner := common.HexToAddress(types.PROXY_ADMIN_ADDRESS_HEX)
	factoryImplAddress := common.HexToAddress(types.FACTORY_IMPL_ADDRESS_HEX)

	// Compute the code hash from the runtime bytecode
	codeHash := crypto.Keccak256(types.ProxyRuntimeBytecode)

	// Create the EVM account object
	evmAccount := statedb.Account{
		Nonce:    1,             // to prevent tx nonce=0 conflicts
		Balance:  new(uint256.Int), // zero balance by default
		CodeHash: codeHash,      // link to deployed code
	}

	// Set the EVM account with the factory proxy contract
	err := evmKeeper.SetAccount(sdkCtx, proxyAddress, evmAccount)
	if err != nil {
		panic("failed to set factory proxy contract account: " + err.Error())
	}

	// Store the runtime bytecode linked to the code hash
	evmKeeper.SetCode(sdkCtx, codeHash, types.ProxyRuntimeBytecode)

	// Update proxyAdmin Slot with the proxyAdmin owner address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_ADMIN_SLOT, common.LeftPadBytes(proxyAdminOwner.Bytes(), 32))

	// Update proxyImplementation Slot with the factory implementation address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_IMPLEMENTATION_SLOT, common.LeftPadBytes(factoryImplAddress.Bytes(), 32))
}

	}

// InitGenesis initializes the module's state from a genesis state.
func (k *Keeper) InitGenesis(ctx context.Context, data *types.GenesisState) error {

	if err := data.Params.ValidateBasic(); err != nil {
		return err
	}

	// Only deploy factory contracts on fresh genesis, not on import from export.
	// Re-deploying on import would overwrite existing EVM state or cause nonce collisions.
	if !data.Exported {
		deployFactoryEA(ctx, k.evmKeeper)
	}

	if err := k.Params.Set(ctx, data.Params); err != nil {
		return err
	}

// CallFactoryToDeployUEA deploys a new UEA using factory contract
// Returns deployment response or error if deployment fails
func (k Keeper) CallFactoryToDeployUEA(
	ctx sdk.Context,
	from, factoryAddr common.Address,
	universalAccount *types.UniversalAccountId,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: deployUEA",
		"factory", factoryAddr.Hex(),
		"chain_namespace", universalAccount.ChainNamespace,
		"chain_id", universalAccount.ChainId,
		"owner", universalAccount.Owner,
	)

	abi, err := types.ParseFactoryABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse factory ABI")
	}

	abiUniversalAccount, err := types.NewAbiUniversalAccountId(universalAccount)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal account")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,        // who is sending the transaction
		factoryAddr, // destination: FactoryV1 contract
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"deployUEA",
		abiUniversalAccount,
	)
}

# Core Validator

Push Chain's L1 node binary (`pchaind`). Four custom Cosmos SDK modules and one custom EVM precompile turn the chain into the universal-execution layer that coordinates inbounds, outbounds, and TSS-signed crosschain transactions.

- **Produces** blocks via CometBFT consensus and runs the EVM execution engine for both standard and universal traffic
- **Coordinates** the crosschain protocol — collects votes from Universal Validators on inbounds/outbounds/chain meta, finalizes ballots, drives TSS keygen and fund migration, and rewards UV operators with a boosted fee share
- **Hosts** Universal Executor Accounts (UEAs) and the chain-meta oracle on its EVM, giving any source-chain user a deterministic Push Chain identity and predictable gas pricing across networks
