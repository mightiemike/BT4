### Title
`UpdateAccountActuator` never clears the old account name from `AccountIndexStore`, permanently squatting the name and corrupting the name-registry index - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateAccountActuator.java])

### Summary
`AccountIndexStore` is a name→address registry used to look up accounts by their human-readable `accountName`. When an account renames itself via `AccountUpdateContract`, `UpdateAccountActuator.execute()` writes the new `name → address` mapping into `AccountIndexStore` but never deletes the old `name → address` entry that pointed to the same account under its previous name. This is directly analogous to the Tokemak `LMPVaultRegistry.removeVault` bug: an entity is "removed" (in this case, an account stops using a given name) from one bookkeeping structure while a secondary index that only supports insert-and-existence-check semantics is left with a stale entry, which then blocks legitimate future use of that identifier and returns incorrect data to lookups.

### Finding Description
`UpdateAccountActuator.execute()` performs: [1](#0-0) 
```
byte[] ownerAddress = accountUpdateContract.getOwnerAddress().toByteArray();
AccountCapsule account = chainBaseManager.getAccountStore().get(ownerAddress);

account.setAccountName(accountUpdateContract.getAccountName().toByteArray());
chainBaseManager.getAccountStore().put(ownerAddress, account);
chainBaseManager.getAccountIndexStore().put(account);
```
It only ever calls `put()` on `AccountIndexStore`; there is no corresponding `delete()` of the account's previous name key. `AccountIndexStore` itself exposes only `put`/`get`/`has` — no API to remove a stale key on rename: [2](#0-1) 

Because `AllowUpdateAccountName` (a dynamic/committee-controlled chain parameter) governs whether renaming is even allowed multiple times, once it is enabled any account can freely change its `accountName` repeatedly: [3](#0-2) 
```
if (account.getAccountName() != null && !account.getAccountName().isEmpty()
    && chainBaseManager.getDynamicPropertiesStore().getAllowUpdateAccountName() == 0) {
  throw new ContractValidateException("This account name is already existed");
}

if (chainBaseManager.getAccountIndexStore().has(accountName)
    && chainBaseManager.getDynamicPropertiesStore().getAllowUpdateAccountName() == 0) {
  throw new ContractValidateException("This name is existed");
}
```
Each rename leaves the account's previous name permanently mapped to the account's address in `AccountIndexStore`. This is exactly the "removal without clearing the secondary mapping" pattern from the Tokemak report: the account has conceptually vacated the old name (its `AccountCapsule.accountName` field no longer holds it), but the `_vaultsByType`-equivalent index (`AccountIndexStore`) is never purged of the stale entry.

### Impact Explanation
- **Registry corruption / stale data reachable via RPC**: `AccountIndexStore` backs name-based account lookups exposed through the wallet/gRPC and HTTP APIs. After a rename, a query for the old name still resolves to the renaming account's address even though that account no longer identifies with that name, returning incorrect account-identity information to any unprivileged caller.
- **Permanent name squatting / DoS on the namespace**: If `AllowUpdateAccountName` is later disabled (or was already `0` for a subsequent claimant), `validate()`'s `accountIndexStore.has(accountName)` check will forever reject any other account trying to adopt that now-abandoned name, exactly mirroring the original bug where `addVault` could never re-register a previously removed vault because of a stale existence check on a secondary mapping. This is triggerable by any account via a normal broadcast `AccountUpdateContract` transaction — no privileged role required.
- Over time, repeated renames (by design allowed when `AllowUpdateAccountName == 1`) accumulate an ever-growing set of orphaned, unreclaimable name entries in `AccountIndexStore`, permanently degrading the usability and correctness of the name index for the entire network.

### Likelihood Explanation
High likelihood of occurrence given normal use: `AccountUpdateContract` is a standard, unprivileged, publicly broadcastable transaction type available to every account owner, requiring no special permission (`AbstractActuator` / `ContractType.AccountUpdateContract`). The bug manifests on every single rename operation once a name has previously been set — no attacker-crafted edge case is needed, only that `AllowUpdateAccountName` allows a rename (which is itself an on-chain configurable, intended feature), or simply that the initial single rename (name empty → name X) is enough to leave name X orphaned when the account is later abandoned/its balance drained/reused. The stale mapping is silent — no error, no revert — making it easy to trigger unintentionally as normal user behavior.

### Recommendation
When `UpdateAccountActuator.execute()` sets a new account name, capture and delete the previous name entry from `AccountIndexStore` before/while writing the new one:
```java
byte[] oldAccountName = account.getAccountName().toByteArray();
if (oldAccountName.length > 0) {
  chainBaseManager.getAccountIndexStore().delete(oldAccountName);
}
account.setAccountName(accountUpdateContract.getAccountName().toByteArray());
chainBaseManager.getAccountStore().put(ownerAddress, account);
chainBaseManager.getAccountIndexStore().put(account);
```
This requires adding a `delete`-by-name helper (or using the inherited `delete(byte[])` from `TronStoreWithRevoking`) to `AccountIndexStore`, mirroring the fix pattern in the original report (explicitly clearing the stale secondary-index entry on removal/replacement).

### Proof of Concept
1. Account `A` (address `addr_A`) sends `AccountUpdateContract` with `accountName = "alice"`. `AccountIndexStore["alice"] = addr_A`.
2. Chain committee enables `AllowUpdateAccountName = 1` (a normal governance parameter toggle already exercised in `UpdateAccountActuatorTest#twiceUpdateAccountSuccess`, see [4](#0-3) ).
3. Account `A` sends another `AccountUpdateContract` with `accountName = "alice2"`. Execution succeeds: `AccountIndexStore["alice2"] = addr_A`, but `AccountIndexStore["alice"]` is **never deleted** and still resolves to `addr_A`.
4. Committee later sets `AllowUpdateAccountName = 0` again. Any other account `B` now attempts to claim the name `"alice"` (which account `A` no longer uses). `validate()` finds `accountIndexStore.has("alice") == true` and rejects with `"This name is existed"`, permanently blocking `B` (or anyone) from ever using `"alice"`, and any lookup of account name `"alice"` via the wallet/API still returns `addr_A`, which is stale/incorrect.

```java
@Component
public class AccountIndexStore extends TronStoreWithRevoking<BytesCapsule> {

  @Autowired
  public AccountIndexStore(@Value("account-index") String dbName) {
    super(dbName);
  }

  public void put(AccountCapsule accountCapsule) {
    put(accountCapsule.getAccountName().toByteArray(),
        new BytesCapsule(accountCapsule.getAddress().toByteArray()));
  }

  public byte[] get(ByteString name) {
    BytesCapsule bytesCapsule = get(name.toByteArray());
    if (Objects.nonNull(bytesCapsule)) {
      return bytesCapsule.getData();
    }
    return null;
  }

  @Override
  public BytesCapsule get(byte[] key) {
    byte[] value = revokingDB.getUnchecked(key);
    if (ArrayUtils.isEmpty(value)) {
      return null;
    }
    return new BytesCapsule(value);
  }

  @Override
  public boolean has(byte[] key) {
    byte[] value = revokingDB.getUnchecked(key);
    return !ArrayUtils.isEmpty(value);
  }
}
```
