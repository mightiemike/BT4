### Title
`mark_cancellation_request` overwrites a consumed L1 handler transaction's state without checking `is_consumed()` - ([File: crates/apollo_l1_events/src/transaction_record.rs])

### Summary
Analogous to the `DepositManagerV1::refundDeposit()` issue (a state-changing action performed without checking a terminal status flag), `TransactionRecord::mark_cancellation_request` only checks `is_committed()` before transitioning the transaction's `state` to `CancellationStartedOnL2`, but does not check `is_consumed()`. This lets an L1-triggered cancellation request overwrite the terminal `Consumed` state of an L1 handler transaction.

### Finding Description
`TransactionManager::request_cancellation` unconditionally calls `mark_cancellation_request` on the record for a given `tx_hash` whenever a cancellation-request event is scraped from L1, with no guard on the record's current lifecycle state: [1](#0-0) 

Inside `mark_cancellation_request`, the only terminal-state guard is against `is_committed()`. If the record is instead in the `Consumed` state (set via `mark_consumed`, e.g. after `consume_tx` runs), this check does not prevent the transition, and `self.state` is unconditionally overwritten to `TransactionState::CancellationStartedOnL2`: [2](#0-1) 

The state machine only special-cases `Committed`, not `Consumed`: [3](#0-2) 

Once overwritten, `update_time_based_state` and `is_validatable` operate purely on `self.state` (and the separate `committed` boolean, not a `consumed` boolean), so a `Consumed` transaction that gets its state flipped to `CancellationStartedOnL2` and then (after the cancellation timelock) to `CancelledOnL2` will subsequently be treated by `validate_tx` as "already cancelled" (`InvalidValidationStatus::CancelledOnL2`) rather than "already consumed": [4](#0-3) [5](#0-4) 

This is the same bug class as the reported `refundDeposit()` issue: a critical action (`mark_cancellation_request`) is performed without verifying the entity's terminal/closed status (`is_consumed()`), only checking one of several terminal states (`is_committed()`).

### Impact Explanation
This corrupts the internal lifecycle bookkeeping (`TransactionState`) for an L1 handler message that has already been consumed on L1 — i.e., the transaction was already delivered/processed. While `Consumed` transactions are not proposable (`is_proposable` only matches `Pending`), the divergence between `is_committed()` (used for guarding overwrite) and the full set of terminal states (`Committed`/`Consumed`) means the transaction record's `state` field no longer accurately reflects the ledger of what actually happened to that L1 message. Any downstream logic, monitoring, snapshot construction (`snapshot()` classifies strictly by `self.state`), or future logic that trusts `TransactionState::Consumed` to always represent finality can be misled into believing a consumed message was instead cancelled, which is a correctness/consistency issue in the sequencer's L1 message bookkeeping. This is not a fund-loss or double-spend by itself (the transaction cannot be re-validated because `is_validatable` already excludes `Consumed`/`CancelledOnL2` alike), so the practical severity is bounded to state/observability corruption rather than direct loss of funds — I could not find any code path where this incorrect state re-enables execution or acceptance of an already-consumed L1 message.

### Likelihood Explanation
Triggering this requires only that an L1 message sender request cancellation on L1 for a message hash after that same message was already consumed — a legitimate, unprivileged action on L1 that any L1 message sender can perform, and the scraper will faithfully replay the event into `request_cancellation`. No malicious operator/proposer/node behavior is needed.

### Recommendation
Guard `mark_cancellation_request` (or `request_cancellation` in `TransactionManager`) against all terminal states, not just `is_committed()`:
```rust
pub fn mark_cancellation_request(&mut self, timestamp: BlockTimestamp) -> Option<BlockTimestamp> {
    let tx_hash = self.tx.tx_hash();
    if self.is_committed() || self.is_consumed() {
        warn!("L1 handler transaction {tx_hash} was not marked for cancellation as it is already {:?}.", self.state);
    } else {
        ...
    }
}
```

### Proof of Concept
1. Add an L1 handler tx via `TransactionManager::add_tx`.
2. Call `consume_tx(tx_hash, consumed_at, unix_now)` — record state becomes `TransactionState::Consumed` ( [6](#0-5) ).
3. Call `request_cancellation(tx_hash, block_timestamp)` — despite the tx being `Consumed`, `mark_cancellation_request` only checks `is_committed()` (false here), so it proceeds to set `self.state = TransactionState::CancellationStartedOnL2` ( [7](#0-6) ), silently discarding the `Consumed` state.
4. Subsequent calls to `validate_tx`/`update_time_based_state` and `snapshot()` now classify this transaction as being in the cancellation lifecycle instead of `Consumed`, corrupting the transaction manager's bookkeeping of L1 handler message lifecycle state.

    /// Mark a cancellation request for this transaction.
    /// Returns the existing cancellation timestamp if one exists, `None` if this is the first
    /// request.
    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }

    /// Answers whether any node can include this transaction in a block. This is generally possible
    /// in all states in its lifecycle, except after it had already been added to block, or a short
    /// time after it's cancellation was requested on L1. In particular, this includes states
    /// like: a rejected transaction, a new timelocked transaction, a
    /// transaction whose cancellation was requested on L1 too recently (there will be a
    /// timelock for this).
    pub fn is_validatable(&self) -> bool {
        !self.is_committed() && !self.is_cancelled() && !self.is_consumed()
    }

    pub fn is_staged(&self, epoch: StagingEpoch) -> bool {
        self.staged_epoch == epoch
    }

    pub fn get_consumed_at_timestamp(&self) -> Option<BlockTimestamp> {
        self.consumed_at
    }

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
