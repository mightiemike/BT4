### Title
Zero allowance silently upgraded to `Allowance::Unlimited` in `AddKey` action — (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
When a user submits an `AddKey` ABI payload with `is_limited_allowance=true` and `allowance=0`, the wallet contract silently creates a function-call access key with `Allowance::Unlimited` instead of a zero (or rejected) allowance. Any party that receives this key gains unlimited NEAR-spending power from the wallet, violating the user's explicit intent.

### Finding Description
The conversion chain is:

1. `abi_decode` with `ADD_KEY_SIGNATURE` accepts `allowance=0` as a valid `u128` — no guard exists.
2. `try_into_near_action` maps `is_limited_allowance=true` to `Some(0u128)`, then to `Some(NearToken::from_yoctonear(0))` in `FunctionCallPermission.allowance`.
3. `action_to_promise` evaluates `access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited)`. Because `Allowance::limited` is defined in near_sdk as `NonZeroU128::new(amount.as_yoctonear()).map(Self::Limited)`, it returns `None` for a zero-yoctoNEAR input. The `.unwrap_or(Allowance::Unlimited)` fallback then produces an unlimited allowance.

The user's signed transaction explicitly set `is_limited_allowance=true`, signalling intent for a restricted key. The runtime ignores this intent when `allowance=0`. [4](#0-3) [5](#0-4) 

### Impact Explanation
A function-call access key with `Allowance::Unlimited` can pay gas for any number of calls to the specified `receiver_id` contract, drawing from the wallet's NEAR balance without bound. If the user creates such a key for a dApp or third party (a normal use case for the wallet contract), that party receives unlimited spending authority when the user intended zero. This constitutes **balance manipulation** and enables **unauthorized transactions** against the wallet owner's funds.

### Likelihood Explanation
The `AddKey` action is a first-class, documented feature of the wallet contract. Any Ethereum tooling that constructs an `addKey` call with `is_limited_allowance=true` and `allowance=0` (e.g., to express "no budget" or as a default zero value) will silently produce an unlimited key. The path requires no privileged access — only a valid signed Ethereum transaction submitted through `rlp_execute`. [6](#0-5) 

### Recommendation
In `action_to_promise`, before calling `Allowance::limited`, explicitly reject or handle the `is_limited_allowance=true` + `allowance=0` combination. The cleanest fix is to add a validation step in `try_into_near_action` (or `parse_tx_data`) that returns `Error::User(UserError::InvalidAbiEncodedData)` (or a dedicated error variant) when `is_limited_allowance=true` and `allowance == 0`. Alternatively, the `action_to_promise` expression should be changed so that a `Some(NearToken::from_yoctonear(0))` allowance is treated as an explicit error rather than silently falling through to `Allowance::Unlimited`. [7](#0-6)
