## Analog Found

### Title
Unchecked return value of `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` allows silent asset-accounting failure in `ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator.execute()` calls the boolean-returning asset mutation methods `reduceAssetAmountV2` and `addAssetAmountV2` on `AccountCapsule` but discards their return value, unlike the sibling `TransferAssetActuator`, which checks the same call and throws `ContractExeException` on failure. This mirrors the reported `_swapTokenExactOutput`/`_swapTokenExactInput` bug class: a state-mutating helper can fail (return `false`/`0`) while the caller proceeds as if it succeeded, leaving persisted state inconsistent with the fee/exchange-pool bookkeeping that already assumed success.

### Finding Description
In `ExchangeTransactionActuator.execute()`: [1](#0-0) 
the results of `accountCapsule.reduceAssetAmountV2(...)` and `accountCapsule.addAssetAmountV2(...)` are never checked. Immediately after, the mutated `accountCapsule` is persisted and the `ExchangeCapsule` (which independently tracks pool balances via `exchangeCapsule.transaction(...)`) is also persisted: [2](#0-1) 

Contrast this with `TransferAssetActuator`, which performs the identical call but explicitly validates the boolean result and aborts the transaction if it is `false`: [3](#0-2) 

This is exactly the "similar context reverts, but this one doesn't check" pattern described in the report: the same private/helper mutation (`reduceAssetAmountV2`/`addAssetAmountV2`) is checked in one actuator and silently ignored in another that mutates account and exchange-pool state together.

`doValidate()` in `ExchangeTransactionActuator` only verifies the seller has enough of the token being sold via `assetBalanceEnoughV2`: [4](#0-3) 
It never validates that the receiving account's V2 asset map can safely accept `anotherTokenQuant` (e.g., overflow of the buyer's existing balance for `anotherTokenID`) before `execute()` runs `addAssetAmountV2`. If that add fails and returns `false`, execution continues: the actor's TRX balance has already been debited for the fee/sold amount (`setBalance` calls happen unconditionally above), and `exchangeCapsule.transaction(...)` has already mutated and will be persisted with updated pool balances — while the actual purchased token never lands in the account's asset map.

### Impact Explanation
If `addAssetAmountV2`/`reduceAssetAmountV2` returns `false` in this call path, the on-chain outcome diverges from what the exchange pool and transaction result (`ret.setExchangeReceivedAmount`) report as having happened: the account's TRX/fee and the exchange pool's token balances are updated as if the swap succeeded, but the actual token balance change on one side of the trade is dropped. This is an accounting corruption in the exchange subsystem reachable directly from a broadcast `ExchangeTransactionContract` transaction — no privileged actor required.

### Likelihood Explanation
Likelihood is moderate-to-low because `doValidate()` does perform an asset-balance-sufficiency check for the token being sold, and pool/token quantities are bounded by `getExchangeBalanceLimit()`. However, the receiving side (`addAssetAmountV2`) has no equivalent pre-check for the destination account's asset map capacity/overflow, and the return value is unconditionally ignored in `execute()`, so any internal condition inside `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` that causes it to return `false` (e.g., precision/overflow guards inside those methods) would be silently swallowed rather than aborting the transaction, unlike the equivalent code path in `TransferAssetActuator`. I was not able to fully inspect the body of `AccountCapsule.reduceAssetAmountV2`/`addAssetAmountV2` in this pass to enumerate every internal `false`-return condition, so the exact triggering scenario is not fully confirmed.

### Recommendation
Check the boolean return values of `reduceAssetAmountV2` and `addAssetAmountV2` in `ExchangeTransactionActuator.execute()` and throw `ContractExeException` on failure, mirroring the pattern already used in `TransferAssetActuator`. Additionally, add a `doValidate()` check confirming the receiving account can safely absorb `anotherTokenQuant` before mutating exchange-pool state.

### Proof of Concept
Not independently reproduced; this report is based on static code-path analysis identifying that `execute()` in `ExchangeTransactionActuator` discards the boolean results of `reduceAssetAmountV2`/`addAssetAmountV2` while persisting dependent fee/pool state unconditionally, in contrast to `TransferAssetActuator`, which validates the identical call. Confirming an exploitable trigger would require inspecting the full implementation of `AccountCapsule.reduceAssetAmountV2`/`addAssetAmountV2` for the exact conditions under which they return `false`, which was not available in this pass.
