### Title
Selective energy-burn skip for `TransferException` lets an attacker cascade a cheap failure through nested CALLs while paying less than the mandated full-energy-burn-on-failure penalty - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.execute()` and `VM.play()` both special-case `Program.TransferException` to skip `program.spendAllEnergy()`, while every other fatal execution failure (`OutOfTimeException`, `JVMStackOverFlowException`, generic `Throwable`, and by implication `OutOfEnergyException`) forces the whole `energyLimit` to be burned. Because `TransferException` is thrown directly inside `callToAddress()`/`suicide()` before the nested sub-call's `VM.play()` executes, and that nested `VM.play()` invocation is *not* wrapped in a try/catch in `Program.callToAddress`, the exception propagates un-mediated through every enclosing call frame's own `VM.play()` catch block, each of which re-applies the same "skip `spendAllEnergy` for `TransferException`" rule and rethrows. The transaction can therefore fail at the top level while being billed only for energy actually consumed by the opcodes executed up to the failure point, instead of the full `energyLimit` that the protocol otherwise mandates for any halting failure.

### Finding Description
`VMActuator.execute()` contains the special case: [1](#0-0) 
and the identical pattern in the generic `catch (Throwable e)` block: [2](#0-1) 

`VM.play()` applies the same skip at every opcode-execution frame: [3](#0-2) 

`Program.TransferException` is thrown from `callToAddress()` in three attacker-reachable situations: endowment value overflow, failed TRX transfer validation, and failed TRC10 transfer validation — all *after* the sub-call's allocated energy has already been refunded via `refundEnergy(msg.getEnergy()...)`: [4](#0-3) [5](#0-4) 

Critically, `Program.callToAddress()` invokes the sub-call's own `VM.play(program, ...)` without any try/catch: [6](#0-5) 
so if a `TransferException` is thrown by a deeper nested program's own `VM.play()` (per the pattern above), it is not converted into the normal "push zero and continue" call-failure semantics used for e.g. insufficient balance (lines 1050–1066 of the same file); instead it escapes `callToAddress()` entirely and is caught by the *caller's* own `VM.play()` loop, which again skips `spendAllEnergy()` for that caller's own energy pool and rethrows. This repeats at every nesting level up to `VMActuator.execute()`, so a `TransferException` engineered at depth N causes the "burn full energy on failure" invariant to be skipped at every one of the N call frames plus the top-level transaction.

This is inconsistent with `OutOfTimeException`/`JVMStackOverFlowException`/other `Throwable`s, which always force `program.spendAllEnergy()` regardless of depth, guaranteeing full energy is charged for those failure classes.

### Impact Explanation
An attacker can deliberately construct a nested-CALL contract chain where the innermost call fails via one of the three `TransferException` triggers (e.g., an endowment `DataWord` whose `longValueExact()` overflows a `long`, or a TRX/TRC10 transfer that fails `VMUtils.validateForSmartContract`). The resulting top-level failed transaction is billed only for the energy actually spent executing opcodes up to the failure, not the full `feeLimit`-derived `energyLimit`, unlike a functionally equivalent failure caused by exhausting energy or any other exception type. This is a real underpricing of failed/reverted execution relative to the protocol's own designed penalty for halting failures, letting an attacker submit transactions that consume node CPU/storage-diff/log-processing work for constructing and unwinding deep call chains at a fraction of the normal "burn-everything" cost.

### Likelihood Explanation
The path requires only an unprivileged smart-contract deployment and a normal `TriggerSmartContract` transaction — no special privileges. `allowTvmConstantinople()` (a long-standing, generally-enabled hard fork flag) must be on, which it is on all mainnet-equivalent chains today for this code path to use `TransferException` rather than `BytecodeExecutionException`. Triggering the endowment overflow or transfer-validation failure at a chosen depth is fully deterministic and repeatable by the attacker, and can be scripted as a straightforward Solidity contract chain that self-calls or calls a set of proxy contracts with a value/endowment engineered to fail at the desired depth.

### Recommendation
Remove the `TransferException` special case in both `VM.java` (lines 93-100) and `VMActuator.java` (lines 240-245 and 281-284) so that `program.spendAllEnergy()` is invoked unconditionally on any halting exception, consistent with all other failure classes, unless there is a documented, intentional design reason (e.g., matching upstream EVM semantics for reverted sub-calls) — in which case `TransferException` should be caught and converted to a "push zero, continue execution" outcome directly inside `callToAddress()`/`suicide()` (mirroring the existing insufficient-balance handling) instead of being allowed to escape as an uncaught `RuntimeException` that unwinds arbitrarily many stack frames.
