### Title
Vault `deposit` can mint zero shares while consuming the depositor's underlying tokens - permanent loss of deposited funds - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`)

### Summary
Every Zest vault's `deposit` function computes shares via `convert-to-shares-preview`, a rounding-down division, but never asserts the resulting share amount is non-zero before transferring the user's underlying tokens and minting shares. `redeem` in the same contracts explicitly guards against this with `ERR-OUTPUT-ZERO`, but the symmetric guard is missing on the deposit path. This is the same bug class as the referenced Lido `WstETH.sol` report, where `wrap()`/`unwrap()` could silently produce zero shares/assets due to rounding.

### Finding Description
`convert-to-shares-preview` rounds down when converting deposited `amount` into vault shares once the vault has existing supply and assets: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

`mul-div-down amount ts ta` truncates towards zero. Once the vault's price-per-share (`ta/ts`) exceeds 1 (which happens naturally after any interest accrual, since `total-assets` grows relative to `total-supply`), a sufficiently small `amount` yields `inkind = 0`.

In `deposit`, this `inkind` value is used to mint shares and is only checked against `min-out`, not against zero: [2](#0-1) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
    (ok inkind)))
```

There is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. If `min-out` is `u0` (the natural default for a caller who doesn't anticipate rounding, e.g. the market's internal `vault-deposit` helper used by `supply-collateral-add`), the slippage check `(>= inkind min-out)` becomes `(>= u0 u0)`, which passes trivially. `receive-underlying` still pulls the full `amount` of real tokens from the depositor, `current-assets` is still incremented by `amount`, but `ft-mint? zft u0 recipient` mints nothing. The depositor's tokens are absorbed into the vault's asset pool without any corresponding share, permanently socializing the loss to existing shareholders and leaving the depositor with zero claim on their own deposit — with no revert to recover it.

By contrast, the `redeem` path in the same file explicitly protects against the mirrored zero case: [3](#0-2) 

```
(asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
(asserts! (not (get redeem states)) ERR-PAUSED)
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
```

This asymmetry confirms the omission on `deposit` is a genuine gap rather than an intended design choice, and it is present identically across `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, and `v0-vault-usdh.clar` (and their `local-testing/` mirrors).

### Impact Explanation
This falls under **temporary/permanent freezing of funds** (and effectively theft, since the value is transferred out of the depositor's control into the vault's asset pool for the benefit of other shareholders): the depositor irrevocably loses the deposited underlying amount for zero shares in a single transaction, with no revert path since `min-out` of `u0` legitimately satisfies the slippage check.

### Likelihood Explanation
The condition requires the vault's `total-assets/total-supply` ratio to be greater than 1 (true for any vault after normal interest accrual) and a deposit `amount` small enough that `amount * ts / ta` rounds to zero. This can happen naturally for small deposits/dust amounts, or can be deliberately triggered by an attacker who inflates `ta/ts` (e.g., via `supply-collateral-add`'s automated `min-shares` defaults) or targets other users' dust-value deposits through front-running/integration flows that pass `min-out = 0`. Given the protocol's own internal call site (`supply-collateral-add`) forwards a caller-supplied `min-shares` that could be zero, this is directly reachable through production entry points.

### Recommendation
Add an explicit zero-shares guard to `deposit` (and any other minting entry point using `convert-to-shares-preview`) in all six vault contracts, mirroring the existing `redeem` protection:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `ERR-AMOUNT-ZERO`/`ERR-SLIPPAGE` checks in `deposit`, before `receive-underlying` transfers funds.

### Proof of Concept
1. Vault has existing supply such that `total-assets-preview` / `total-supply-preview` > 1 (e.g., after accrued interest, 1 share = 1.10 underlying).
2. Attacker or unaware user calls `deposit(amount, min-out=u0, recipient)` where `amount` is small enough that `mul-div-down(amount, ts, ta)` rounds down to `u0` — e.g. `amount = 1` unit while `ta/ts` ratio ≥ 2.
3. `inkind` (shares) = `u0`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` → `(>= u0 u0)` passes.
5. `(try! (receive-underlying amount account))` pulls the real `amount` from the user.
6. `(try! (ft-mint? zft inkind recipient))` mints `u0` shares — recipient receives nothing.
7. `(var-set assets (+ current-assets amount))` — the vault's internal accounting still increases by the full `amount`, silently redistributing it to existing shareholders.
8. Transaction completes successfully (`(ok inkind)` returns `u0`), and the user has irreversibly lost their deposited `amount`. [4](#0-3)
