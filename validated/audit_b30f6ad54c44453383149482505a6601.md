### Title
Meta-transaction relayer fee-griefing via front-run replay of an observed `SignedDelegateAction` - (File: `runtime/runtime/src/actions.rs`)

### Summary
`SignedDelegateAction`/`VersionedSignedDelegateAction` binds a NEP-366 meta-transaction only to `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — it never binds the identity of the outer-transaction signer (the relayer) that is supposed to submit it. [1](#0-0)  The signature check only verifies the NEP-461 hash of these fields against `public_key`, with no constraint on who wraps and submits the action. [2](#0-1)  Anti-replay is enforced purely by the sender's access-key/gas-key nonce, checked and incremented only when the `DelegateAction` receipt lands on the sender's shard, inside `validate_delegate_action_key`. [3](#0-2) [4](#0-3)  Because the nonce check happens later and on a different shard than fee collection, an unauthorized third party who observes a `SignedDelegateAction` (in the mempool, via gossip, or leaked by the sender/receiver) can wrap the exact same bytes into their own transaction and submit it first.

### Finding Description
Fee accounting for the relayer's outer transaction happens at transaction-to-receipt conversion time, on the relayer's own shard, unconditionally: "Send fees are burnt here, on the signer's shard, at conversion time" before the delegate action's nonce is ever validated. [5](#0-4)  The nonce/signature replay check for the inner `DelegateAction` only happens afterward, when the resulting receipt is processed against the sender's access key on the sender's shard. [6](#0-5) 

This produces exactly the pattern in the reported Solidity bug: a value-authorizing signature (the `SignedDelegateAction`) is decoupled from the party who ultimately triggers its on-chain effect, and the payment/accounting step (fee burn) is not conditioned on that trigger succeeding for the intended actor. A legitimate relayer A composes a transaction wrapping `SignedDelegateAction` and broadcasts it; before it lands in a chunk, an unauthorized party B copies the identical `SignedDelegateAction` bytes (visible in the mempool/gossip) into B's own transaction and gets it included first. B's transaction consumes the sender's access-key nonce inside `validate_delegate_action_key`, causing A's later transaction to fail with `DelegateActionInvalidNonce` once it reaches the sender's shard — but A's send-side fees were already unconditionally burnt at conversion time on A's own shard, as documented above. A loses real NEAR value for a service that never executed on A's behalf, while B (who did nothing but copy the signed bytes and pay its own fees) obtains the useful effect (or grief target) instead.

### Impact Explanation
This is a concrete unauthorized value loss reachable by any unprivileged party who can observe network traffic or mempool contents containing a `SignedDelegateAction` — no special privilege, validator role, or malicious-node capability is required, since mempool/gossip visibility of pending transactions is a normal capability of any network participant submitting via RPC. The honest relayer's already-burnt gas fee is a real, permanent loss of NEAR tokens with no compensating service rendered, satisfying "fee bypass"/"unauthorized value movement" from a reachable, unprivileged path (an RPC-submitted meta-transaction). This is directly analogous to the reported permit2 issue: signature-authorized value movement can be triggered by an unauthorized third party ahead of the intended submitter, and the intended submitter's already-committed value (permit2 tokens / here, burnt relay fees) is lost due to replay protection blocking the "real" path afterward.

### Likelihood Explanation
Likelihood is moderate-to-high in any environment where meta-transactions/relayers are used competitively (e.g., multiple relayer services bidding to service the same `SignedDelegateAction`, or a malicious observer wanting to grief a specific relayer). No cryptographic secrets need to be broken — the attacker only needs to observe already-public signed bytes in the mempool and resubmit them faster, which is a standard front-running capability on any blockchain with a visible transaction pool.

### Recommendation
Bind the `DelegateAction`/`DelegateActionV2` signature (or a wrapping check enforced during `validate_delegate_action_key`) to an authorized relayer identity (e.g., include the outer transaction's `signer_id` in the NEP-461 signed payload, or require it to match a `relayer_id` field carried by the `DelegateAction`), so that only the intended relayer's transaction can successfully consume the nonce. Alternatively, defer/refund the relayer's send-side fee burn until the delegate nonce check succeeds, so an unauthorized front-run does not cause the legitimate relayer to lose already-spent fees.

### Proof of Concept
1. Alice signs a `SignedDelegateAction` (nonce N, `max_block_height` H) intending relayer A to submit it and pay gas/deposit, per the documented meta-transaction flow. [7](#0-6) 
2. Relayer A wraps it into transaction T_A (`Action::DelegateV2`) with A as signer/relayer and broadcasts T_A.
3. Attacker B observes T_A's `SignedDelegateAction` bytes in the mempool (unmodified, since the signature does not bind the relayer identity) and immediately creates transaction T_B, wrapping the identical `SignedDelegateAction`, signed and paid for by B, and gets it included in an earlier chunk.
4. B's receipt reaches Alice's shard first; `validate_delegate_action_key` succeeds and increments Alice's access-key/gas-key nonce to N. [4](#0-3) 
5. T_A's send-side fees were already burnt at conversion time on A's shard (step 51-52 of the runtime-execution spec), before A's receipt reaches Alice's shard. [5](#0-4) 
6. When T_A's resulting receipt reaches Alice's shard, `validate_delegate_action_key` now sees `delegate_nonce.nonce() <= current_nonce` (since B already consumed N) and fails with `DelegateActionInvalidNonce`, exactly as demonstrated by the existing replay test for gas-key meta-transactions. [8](#0-7) [3](#0-2) 
7. Net effect: A permanently lost the NEAR tokens burnt for its send fees with zero benefit to Alice or itself, while B obtained the effect (or simply griefed A) using nothing but observed public signed bytes.

### Transaction validation and conversion (`process_transactions`, `runtime/runtime/src/lib.rs:1882`)

1. In parallel (rayon), each tx is stateless-validated via `validate_transaction` (`runtime/runtime/src/verifier.rs:109`) — action validation + `ValidatedTransaction::new` (signature, version, action limits) — and signer accounts/access-keys/gas-key nonces are prefetched into `DashMap`s (`runtime/runtime/src/lib.rs:1893`-`1977`). Expired txs are marked `InvalidTxError::Expired`.
2. Sequentially, for each tx: if `UniqueChunkTransactions` is enabled, skip any repeat of a tx hash already seen in this chunk (`runtime/runtime/src/lib.rs:1988`). Stateless-validation failures produce a failed outcome (recorded per `register_outcome`, below) and skip the tx (`runtime/runtime/src/lib.rs:1994`).
3. Compute `tx_cost` (`runtime/runtime/src/config.rs:400`); on overflow → `CostOverflow` failed outcome (`runtime/runtime/src/lib.rs:2010`).
4. Look up prefetched account / access key; missing account → `InvalidSignerId`, missing key → `AccessKeyNotFound` (`runtime/runtime/src/lib.rs:2030`-`2075`).
5. Charge: gas-key txs (nonce carries a `nonce_index`) use `verify_and_charge_gas_key_tx_ephemeral` (`runtime/runtime/src/verifier.rs:383`); regular txs use `verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:272`). Both are pure (no state mutation) and return a `TxVerdict`.
6. On `TxVerdict::Success`, build the receipt via `Receipt::from_tx` with `receipt_gas_price` and the tx's actions (`runtime/runtime/src/lib.rs:2151`). If `receiver_id == signer_id` the receipt is a **local receipt** pushed to `local_receipts`; otherwise it is handed to `ReceiptSink::forward_or_buffer_receipt` (`runtime/runtime/src/lib.rs:2187`-`2195`). The outcome is `SuccessReceiptId`.
7. On `TxVerdict::DepositFailed` (gas-key only): gas is still burnt, a failed-with-gas outcome is emitted, no receipt is created (`runtime/runtime/src/lib.rs:2130`). On `TxVerdict::Failed`: failed outcome, tx skipped (`runtime/runtime/src/lib.rs:2199`).
8. On success, `result.apply` mutates the in-memory signer account + access key, then `set_account`/`set_access_key`/(gas-key `set_gas_key_nonce`) write them and the update commits with `StateChangeCause::TransactionProcessing` (`runtime/runtime/src/lib.rs:2241`-`2265`).

**Send fees are burnt here, on the signer's shard, at conversion time.** `calculate_tx_cost` (`runtime/runtime/src/config.rs:417`) sets `burnt = new_action_receipt send_fee + total_send_fees(actions) + signature_verification_cost`, all burnt at `current_gas_price`; `gas_remaining` (prepaid gas + prepaid send/exec fees + receipt exec fee) is attached to the receipt and purchased at `receipt_gas_price = max(current_gas_price, min_gas_purchase_price)` (`runtime/runtime/src/config.rs:459`-`465`). `sender_is_receiver` (sir) selects the cheaper send-fee column (`runtime/runtime/src/config.rs:425`).

**File:** docs/architecture/how/meta-tx.md (L40-52)
```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.
```
