### Title
Empty `authz.MsgExec.Msgs` vacuously satisfies `IsGaslessTx`, letting an unprivileged sender bypass fee deduction and the min-gas-price check - (File: app/txpolicy/gasless.go)

### Summary
The Radiant `loop(loopCount=0)` bug is a class of "iterate-N-times-then-flip-an-exempt-flag" logic where a caller-controlled count of `0` skips the loop body entirely and leaves a security-relevant guard in its permissive default state. Push Chain's gasless-transaction classifier, `IsGaslessTx` in `app/txpolicy/gasless.go`, has the same shape: it iterates over the caller-controlled `authz.MsgExec.Msgs` slice and only returns `false` (non-gasless) from *inside* that inner loop. If the slice is empty, the loop body never executes and the function falls through to `return true`, incorrectly classifying the transaction as gasless.

### Finding Description
`IsGaslessTx` first checks that the *outer* `tx.GetMsgs()` is non-empty [1](#0-0) , but it never applies the same non-empty check to the *inner* messages of an `authz.MsgExec`: [2](#0-1) 

For an outer message of type `*authz.MsgExec`, gaslessness is decided purely by "does any inner message fail the whitelist check" — if `m.Msgs` is empty, that inner `for` loop never executes, no `return false` is ever hit, and the switch statement falls through to the function's default `return true` at the end. This is structurally identical to the Radiant bug: a caller-controlled iteration count (`loopCount` / `len(m.Msgs)`) of `0` skips the loop that is supposed to enforce/reset the exemption, leaving the exempt state (`isGasless == true`) in its permissive default.

This gasless classification directly feeds two ante decorators that grant real, unprivileged, fund-affecting exemptions:
- `MinGasPriceDecorator` skips the fee-market minimum-fee check for gasless txs [3](#0-2) 
- `DeductFeeDecorator` skips balance-based fee deduction entirely for gasless txs [4](#0-3) 

Both are reached before any signature/authorization check that validates whether `MsgExec` actually grants the claimed authorization; an `authz.MsgExec` with a zero-length `Msgs` field is a syntactically valid Cosmos SDK message from `IsGaslessTx`'s point of view (the function itself performs no `ValidateBasic`-style rejection of empty `Msgs`).

### Impact Explanation
If an `authz.MsgExec` transaction with an empty `Msgs` slice reaches `IsGaslessTx` before being rejected elsewhere in the pipeline (e.g., by `ValidateBasic` decorators or by the `authz` keeper's own execution logic), an unprivileged sender pays zero fee and bypasses the network's minimum-gas-price floor for that transaction. This is a fee/spam-resistance bypass rather than a direct fund-theft primitive (there is no PRC20 mint/burn or ballot state involved), so it maps to the "gasless allowlisting … must not turn attacker input into accepted authorization" admission-path invariant rather than a fund-drain invariant.

### Likelihood Explanation
This is uncertain without runtime verification, which the available tooling does not support:
- It is unclear whether `ante.NewValidateBasicDecorator()` (which runs before `NewDeductFeeDecorator`/`MinGasPriceDecorator` in the chain, see `app/ante/ante_cosmos.go`) or the standard Cosmos SDK `authz.MsgExec.ValidateBasic()` already rejects a `MsgExec` with zero inner messages. If it does, this specific path is not reachable and the vacuous-truth bug in `IsGaslessTx`, while a real logic defect, would not be practically exploitable via `MsgExec`.
- Even if a zero-`Msgs` `MsgExec` reaches deep enough to affect fee decorators, the actual monetary benefit is limited to what a single (largely no-op) transaction would have cost in fees/min-gas-price, since a `MsgExec` with no inner messages executes nothing of substance in `x/authz`.

### Recommendation
Change `IsGaslessTx` to reject an `authz.MsgExec` with zero inner messages (mirroring the outer `len(msgs) == 0 → return false` check), e.g.:
```go
case *authz.MsgExec:
    if len(m.Msgs) == 0 {
        return false
    }
    for _, innerMsg := range m.Msgs {
        if !slices.Contains(GaslessMsgTypes, innerMsg.TypeUrl) {
            return false
        }
    }
```
This closes the vacuous-truth condition regardless of whether upstream `ValidateBasic` already blocks empty `MsgExec.Msgs`, consistent with defense-in-depth against the exact bug class the report describes (a zero-iteration loop leaving a security exemption in its default-permissive state).

### Proof of Concept
Not independently confirmed end-to-end due to the indexed tooling's inability to trace whether `ValidateBasic`/`authz` keeper validation intercepts an empty `MsgExec.Msgs` before `IsGaslessTx` is evaluated. The logic defect itself is directly demonstrable as a unit test against `app/txpolicy/gasless.go`:
```go
tx := &mockFeeTx{msgs: []sdk.Msg{&authz.MsgExec{Grantee: attacker, Msgs: nil}}}
require.True(t, txpolicy.IsGaslessTx(tx)) // vacuously true — no inner messages to fail the whitelist check
```
A background Devin session with access to a running node/CLI would be needed to confirm whether this transaction is rejected earlier in the ante/authz pipeline before it reaches `IsGaslessTx`, which determines whether this is a live, exploitable finding or a latent logic defect.
