### Title
Unbounded Native Recursion in `get_recursive_transaction_results` Causes RPC-Node Stack Overflow via Deep Receipt Chains - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` [1](#0-0)  performs a plain (non-tail, non-iterative) Rust function recursion that descends one stack frame per receipt-DFS level, following `outcome.receipt_ids` chains with no maximum-depth guard. This function is the sole engine behind `get_final_transaction_result` and `get_partial_transaction_result_option` [2](#0-1) [3](#0-2) , which back the public `tx` / `tx_status` JSON-RPC endpoints through `ViewClientActor::get_tx_status` [4](#0-3) .

### Finding Description
Any account can submit a transaction whose contract logic recursively schedules a chain of cross-contract call receipts (a supported, documented technique — see the test contract's `max_self_recursion_delay`, explicitly built "to delay completion of the receipt for as long as possible through self cross-contract calls") [5](#0-4) . Each receipt in that chain records exactly one child `receipt_id`, forming a long linear DFS chain rather than a bounded tree.

When any RPC caller later queries `tx` or `tx_status` for that transaction hash, `get_tx_status` calls `chain.get_partial_transaction_result_option`, which calls `get_recursive_transaction_results` [6](#0-5) . That function recurses once per receipt in the chain:
```
for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
    let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
    self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
}
``` [7](#0-6) 
There is no depth counter, no iterative worklist, and no bound tied to any consensus limit (e.g. `max_actions_per_receipt`) — unlike the analogous trie/BFS code elsewhere in the codebase which was deliberately rewritten to a queue "to avoid any potential stack overflows" [8](#0-7) . Each recursion level consumes real Rust stack frames in the `neard` process serving RPC/view-client requests; with a sufficiently long receipt chain, this exhausts the thread stack and aborts the process (Rust recursion overflow is not a catchable exception — it is a hard process abort), exactly analogous to Python's `RecursionError` crash in the reported Mistune advisory.

### Impact Explanation
A stack-overflow abort in the `neard` process handling RPC/view-client queries constitutes a transaction-triggered denial of service: any RPC node (including nodes also acting as chunk producers/validators, since view-client logic runs in the same binary) that observes and later serves a `tx`/`tx_status` query for a maliciously constructed long-receipt-chain transaction can be crashed. This meets the "transaction-triggered halt" acceptance criterion — an unprivileged transaction signer creates the receipt chain, and any unprivileged RPC caller (including the attacker themselves) triggers the crash merely by querying transaction status, with no special privileges required.

### Likelihood Explanation
Building an arbitrarily long linear receipt chain is a supported, low-cost technique (see `max_self_recursion_delay`) bounded only by available prepaid gas, which can be refilled across many transactions/blocks by continuously forwarding gas to the next hop. Because the depth is attacker-controlled and grows with the number of self cross-contract calls the attacker is willing to pay gas for, reaching stack-exhausting depths (thousands of frames) is realistic over a modest number of blocks, and every subsequent `tx`/`tx_status` RPC call against that transaction hash (from anyone, including automated indexers/wallets) reliably retriggers the crash until the code is fixed.

### Recommendation
Rewrite `get_recursive_transaction_results` as an iterative traversal using an explicit worklist/queue (mirroring the pattern already used in `get_subtree_size` in `trie_recording.rs`), removing the dependency on native call-stack depth entirely. As defense in depth, also enforce/track a maximum receipt-chain traversal depth or total-outcomes cap consistent with existing consensus limits (e.g., `max_actions_per_receipt`/gas-derived bounds) so pathological chains fail gracefully with an RPC error instead of exhausting the stack.

### Proof of Concept
1. Deploy the existing `max_self_recursion_delay` test-contract method (or an equivalent contract) and submit a transaction that self-invokes via `promise_batch_action_function_call` in a loop, refunding gas each hop, to build a receipt chain N levels deep (N on the order of a few thousand, bounded only by gas/blocks available) [9](#0-8) .
2. Once the chain has executed (or partially executed) on a node, issue a `tx` or `tx_status` JSON-RPC request for the originating transaction hash against that node [10](#0-9) .
3. `get_partial_transaction_result_option` → `get_recursive_transaction_results` recurses N times with no depth limit [1](#0-0) , and for large enough N the `neard` process's stack is exhausted, aborting the process and denying service to all clients of that RPC node.

        }

pub unsafe fn max_self_recursion_delay() {

        argument_bytes.as_ptr() as u64,

        gas_fixed,
