The `filter_zero_lamport_clean_for_incremental_snapshots` function exists specifically to prevent this scenario. The `cannot_purge` check gates any zero-lamport account whose slot is greater than `latest_full_snapshot_slot` from being purged during `clean_accounts`, and instead defers it to `zero_lamport_accounts_to_purge_after_full_snapshot` until a later full snapshot subsumes that slot. [1](#0-0) 

Tracing the exact attacker scenario: store nonzero at S0, full snapshot at S0 (`latest_full_snapshot_slot = S0`), store zero at S1 > S0, then `clean_accounts(Some(S1))`. Inside `filter_zero_lamport_clean_for_incremental_snapshots`, `should_filter_for_incremental_snapshots` becomes true since `max_clean_root_inclusive (S1) > latest_full_snapshot_slot (S0)`, and `cannot_purge = S1 > S0 = true`, so the pubkey is retained (not purged) and pushed into `zero_lamport_accounts_to_purge_after_full_snapshot` instead. This is exactly "Scenario 4" validated by the unit test `test_filter_zero_lamport_clean_for_incremental_snapshots`. [2](#0-1) 

The end-to-end round trip (full snapshot at S0 containing the account, zero at S1, incremental snapshot at S1, deserialize/rebuild, further clean at a later slot) is already covered as an integration test that asserts the account does not resurrect. [3](#0-2) [4](#0-3) 

Additionally, the attacker does not control `latest_full_snapshot_slot`: this value is only advanced by the node itself when it actually completes taking a full snapshot, via `set_latest_full_snapshot_slot`, not by any user-triggered transaction. Furthermore, the background service that calls `clean_accounts` explicitly caps `max_clean_root_inclusive` at `next_snapshot_request_slot - 1`, ensuring clean never runs past a slot that could contain zero-lamport accounts not yet captured by an upcoming snapshot. [5](#0-4) 

This is not an exploitable gap — it's the exact protection the codebase's comments describe ("Very bad!" scenario) and it is enforced correctly with existing tests (`test_clean_purges_zero_lamport_single_ref_at_reclaim`, `test_filter_zero_lamport_clean_for_incremental_snapshots`, `test_incremental_snapshots_handle_zero_lamport_accounts`) confirming the guard holds. There is no reachable attacker-controlled path that bypasses `cannot_purge` or manipulates `latest_full_snapshot_slot`/`max_clean_root_inclusive` bounds to defeat this gating.
