### Title
Stale market index-cache reused for a later liquidation after `socialize-debt` mutates the vault's index mid-batch, causing mispriced liquidations in `liquidate-multi` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` (mainnet mirror `v0-4-market.clar`) caches each vault's borrow/liquidity index once per block in `index-cache`, keyed only by `{ timestamp: stacks-block-time, aid }`. The cache is populated by `accrue-and-cache` and thereafter served on every subsequent lookup within the same block via a cache-hit short-circuit that returns the already-stored value without checking whether the vault's real index has moved since it was cached. `liquidate-multi` executes several `liquidate` calls for possibly different borrowers but the **same debt asset** inside one transaction/block via `(map call-liquidate positions)`. If an earlier entry in the batch triggers full bad-debt socialization, the vault's `socialize-debt` function directly mutates the vault's `lindex`/`principal-scaled`/`total-borrowed` state, bypassing the market's cache entirely. Because the cache is only invalidated by block boundary, not by this in-block state mutation, every subsequent liquidation in the same `liquidate-multi` batch for that asset keeps reading the pre-socialization index from `index-cache`, mispricing debt/zToken collateral for later positions in the batch.

### Finding Description
The market's index cache is populated lazily and reused for the rest of the block: [1](#0-0) 

```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)          ;; cache HIT: stale value reused
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

This value is used later inside `liquidate` for bad-debt / remaining-debt math via `get-cached-indexes`: [2](#0-1) 

Bad-debt socialization, triggered when a liquidation leaves a borrower with no collateral, calls into the vault's `socialize-debt`, which writes directly to the vault's `lindex`/`principal-scaled`/`total-borrowed` state — completely independent of the market's `index-cache` map: [3](#0-2) 

`liquidate-multi` runs multiple `call-liquidate` invocations for arbitrary borrower/asset combinations in one transaction: [4](#0-3) 

Sequence:
1. Liquidator submits `liquidate-multi` with position #1 = an undercollateralized borrower A whose debt asset is, e.g., USDC, structured so that after seizing all collateral no collateral remains (`no-collateral-left` = true).
2. Processing position #1: `accrue-user-debts`/`accrue-and-cache` populates `index-cache` for `{timestamp: stacks-block-time, aid: USDC}` with the current vault index/lindex. Liquidation proceeds, and because no collateral remains, the bad-debt path runs `(fold socialize-debt-asset fresh-debt-list ...)`, which calls the vault's `socialize-debt`, mutating the vault's real `lindex`/`principal-scaled`/`total-borrowed` directly — the *source* of the cached index has now moved.
3. `map` continues to position #2 = borrower B, who also has USDC debt/zUSDC collateral in the same batch.
4. Position #2's `accrue-user-debts`/`accrue-collateral-asset` call `accrue-and-cache` for USDC again; `map-get?` finds the entry cached in step 2 and returns it unchanged (cache HIT), even though the vault's actual index/lindex has already been updated by the socialize-debt from position #1.
5. Borrower B's debt valuation, zToken collateral price resolution, and liquidation math (`process-debt-asset`, `process-collateral-asset`, `get-cached-indexes`-based remaining-debt calculations) are all computed against this stale, pre-socialization index instead of the vault's true current state.

### Impact Explanation
Depending on the direction of the index drift caused by socialization (debt write-off reduces `total-borrowed`/`principal-scaled`, potentially changing the effective borrow index trajectory and the liquidity index used to price zToken collateral), a liquidator can order a batch so an earlier bad-debt event skews the cached index, then have a later position in the same `liquidate-multi` batch under-value the borrower's real debt or over-value the liquidator's expected collateral payout, causing the protocol/vault to release more collateral than the debt repaid actually justifies. This is a direct extraction of protocol/vault funds through a single mispriced liquidation call — Critical impact (theft of funds at rest).

### Likelihood Explanation
Requires: (a) an attacker capable of arranging or triggering a batch containing a bad-debt-inducing liquidation followed by a second liquidation on the same debt asset within one `liquidate-multi` call, and (b) at least one borrower position eligible for full collateral seizure/bad-debt socialization on the target asset. Both are attacker-controllable preconditions (the attacker can be their own second borrower, or wait for a naturally occurring bad-debt position) and no privileged access or oracle manipulation is required, only correct ordering of `positions` in the `liquidate-multi` list — which the caller fully controls. This makes the precondition realistic though it requires deliberate setup by a sophisticated actor.

### Recommendation
Invalidate or refresh the market's `index-cache` entry for an asset immediately whenever a vault mutation that changes `index`/`lindex` occurs outside the normal `accrue-and-cache` path — in particular, immediately after `vault-socialize-debt`/`socialize-debt-asset` runs, `map-set` (or `map-delete`) the corresponding `index-cache` entry for that `aid` so subsequent lookups in the same block re-accrue instead of reusing the pre-mutation snapshot. Alternatively, route `socialize-debt` itself through `accrue-and-cache` (or have it return fresh indexes for the caller to re-cache) so the cache and the vault's real state can never diverge within a single transaction/block.

### Proof of Concept
Conceptual reproduction (exact numeric parameters need a testnet fixture but the control-flow proof is direct from code):
1. Set up borrower A with USDC debt and non-USDC-priced collateral such that a `liquidate` call fully seizes A's collateral and triggers `no-collateral-left` → bad-debt socialization on the USDC vault.
2. Set up borrower B with USDC debt and zUSDC (or other USDC-priced) collateral, positioned to be liquidatable.
3. Liquidator calls `liquidate-multi` with `positions = [A-liquidation, B-liquidation]` in that order, both referencing the USDC debt asset.
4. During A's processing, `index-cache` for USDC is populated, then `socialize-debt` mutates the USDC vault's `lindex`/`principal-scaled` directly.
5. During B's processing (same transaction), `accrue-and-cache` for USDC returns the stale cached value from step 4 (cache HIT) rather than the vault's post-socialization state, causing B's liquidation math (`process-debt-asset`, `process-collateral-asset`, `calc-final-liquidation-amounts`) to run against outdated indexes, letting the liquidator extract more collateral or repay less debt than the vault's true state warrants.

*Note: full internals of `socialize-debt-asset`'s wrapper inside `market.clar`/`v0-4-market.clar` were not completely inspected due to tool-call limits; the vault-level `socialize-debt` mutation of `lindex`/`principal-scaled` and the market's `index-cache` cache-hit shortcut were directly verified and are sufficient to establish the divergence mechanism described above.*
