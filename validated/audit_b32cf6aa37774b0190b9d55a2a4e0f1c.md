### Title
Stale `storage_cache` entries survive account destruction in `ExecutionCache::insert_state`, causing wrong storage reads for redeployed contracts - (File: `crates/engine/execution-cache/src/cached_state.rs`)

### Summary
`ExecutionCache::insert_state` updates the shared, cross-block `account_cache` and `storage_cache` independently, and when an account is destroyed without previously-existing code (the EIP-6780 "created and destroyed in the same transaction" case), it removes only the `account_cache` entry and explicitly skips clearing any `storage_cache` entries for that address, based on the comment "no storage exists for it." That assumption does not hold when the shared cache was already populated with storage for that same address during this block's execution (via prewarming/fill-on-miss reads before the self-destruct was known), leaving stale `(address, key) -> value` entries in `storage_cache` that persist indefinitely across blocks in the shared `ExecutionCache`/`SavedCache`.

### Finding Description
`CachedStateProvider` keeps two logically-linked but independently-keyed caches: `account_cache: FixedCache<Address, Option<Account>>` and `storage_cache: FixedCache<(Address, StorageKey), StorageValue>` [1](#0-0) .

`insert_state` is responsible for keeping these two caches consistent after each block's `BundleState` is produced. For a destroyed account, the logic branches on whether the account *originally* had code: [2](#0-1) 

- If the account originally had code, the entire cache (`account_cache` **and** `storage_cache`) is cleared via `self.clear()`.
- If the account did not originally have code (the EIP-6780 "contract created and self-destructed within the same transaction" case), only `self.0.account_cache.remove(addr)` is called, and the function `continue`s without touching `storage_cache` at all, based on the assumption stated in the module doc comment that "Since EIP-6780, SELFDESTRUCT only works within the same transaction where the contract was created, so we don't need to handle clearing the storage" [3](#0-2) .

This assumption is only valid if `storage_cache` was never populated for that address during the block. But `storage_cache` can be populated independently of `insert_state`, through `get_or_try_insert_storage_with` when `CacheFillMode::FillOnMiss` is used — which happens during prewarming (`CachedStateProvider::new_prewarm`) and during BAL/parallel execution paths [4](#0-3) [5](#0-4) . Prewarm workers speculatively execute transactions and read/cache storage for a transient contract before it is known that the same transaction will later self-destruct that contract. When the block finishes and `insert_state` runs, the ephemeral contract is correctly removed from `account_cache`, but the storage values it wrote (and that were cached during speculative reads) are never evicted from `storage_cache`, because `insert_state` explicitly skips clearing storage for the no-original-code destroy path.

Because `ExecutionCache` is a long-lived, cross-block cache carried forward via `SavedCache` and reused by later blocks (both for prewarming and for the canonical execution path in `CacheFillMode::LookupOnly`, which reads directly from `storage_cache` without consulting the underlying provider) [6](#0-5) , if the same address is later redeployed (e.g. via deterministic `CREATE`/`CREATE2` after the account's nonce/state was reset following destruction), a subsequent block's storage reads for that address can be served the stale values left over from the previous, destroyed instance instead of the correct empty/re-initialized storage — breaking the invariant that the execution cache's output must equal a full/serial recompute against the actual post-state.

### Impact Explanation
This breaks the equality between the cache-assisted execution path and true state: a cached/prewarmed storage read can silently diverge from what a full state recompute would produce, since `storage_cache` for a previously-destroyed address is never invalidated. When the `LookupOnly` fill mode is used for canonical block execution and returns the stale cached value directly (bypassing the underlying provider) [7](#0-6) , this can lead to an incorrect account/storage read feeding into transaction execution, ultimately producing a wrong state root for a node relying on this cache — a Critical/High class impact per the accepted categories (state divergence between cached and serial execution, and potentially a wrong state root).

### Likelihood Explanation
Requires: (1) a contract created and self-destructed within the same transaction (a legitimate EIP-6780 pattern, not requiring any privileged actor), whose storage got read/cached via prewarming before the self-destruct was applied, and (2) the same address being reused/redeployed later while the shared `ExecutionCache`/`SavedCache` instance is still alive and not evicted/cleared for unrelated reasons (e.g. a subsequent selfdestruct-with-code event triggering `self.clear()`). This is plausible in normal contract deployment patterns (e.g. deterministic factories that create-and-destroy helper contracts, or CREATE2 redeploy patterns), and does not require a malicious peer, RPC caller, or operator action — it can occur purely from ordinary transaction execution.

### Recommendation
- Short term: when removing a destroyed account with no original code, also purge any `storage_cache` entries keyed by that `Address` (or use a `remove_by_address` sweep, or track per-address storage keys written during the block so they can be evicted together with the account), rather than assuming "no storage exists for it."
- Long term: make `account_cache` and `storage_cache` bookkeeping for a given address updated atomically/consistently (e.g., a single invalidation routine keyed by address that always clears both maps for any destroyed account), and add invariant tests (e.g. via property-based/fuzz testing) that verify: after a create-and-destroy-in-same-tx sequence, no stale storage entries remain cached for that address, and that a later redeploy at the same address produces state identical to a full serial recompute.

### Proof of Concept
1. Execute a block containing a transaction that: (a) triggers prewarming to read storage for a to-be-created contract address `X` (e.g., another tx in the prewarm batch touches `X`'s eventual storage speculatively), and (b) within a single transaction, `CREATE`s a contract at `X`, writes to a storage slot `S`, then `SELFDESTRUCT`s it — satisfying EIP-6780's same-tx destroy rule, so `original_info` for `X` has no code and `insert_state` takes the "remove account only" branch, leaving `storage_cache[(X, S)]` populated with the stale value.
2. In a later block, redeploy a new contract at the same address `X` (e.g., via `CREATE2` with the same salt/deployer, or after nonce reset) that never sets slot `S`, then read slot `S` through a `CachedStateProvider` in `LookupOnly` mode.
3. Observe that the cached read returns the stale value left from step 1's destroyed contract instead of the correct zero/empty value that a full state recompute against the real post-state would return, demonstrating divergence between the cache-backed path and a serial state recompute.

    fn storage(
        &self,
        account: Address,
        storage_key: StorageKey,
    ) -> ProviderResult<Option<StorageValue>> {
        if let Some(snapshot) = &self.txpool_snapshot {
            if let Some(value) = snapshot.storage(account, storage_key) {
                self.record_txpool_storage_hit();
                return Ok(nonzero_storage_value(value))
            }
            self.record_txpool_storage_miss();
        }

        if self.should_fill_on_miss() {
            match self.caches.get_or_try_insert_storage_with(account, storage_key, || {
                self.state_provider.storage(account, storage_key).map(Option::unwrap_or_default)
            })? {
                CachedStatus::NotCached(value) => {
                    self.record_storage_miss();
                    Ok(nonzero_storage_value(value))
                }
                CachedStatus::Cached(value) => {
                    self.record_storage_hit();
                    Ok(nonzero_storage_value(value))
                }
            }
        } else if let Some(value) = self.caches.0.storage_cache.get(&(account, storage_key)) {
            self.record_storage_hit();
            Ok(nonzero_storage_value(value))
        } else {
            self.record_storage_miss();
            self.state_provider.storage(account, storage_key)
        }
    }
