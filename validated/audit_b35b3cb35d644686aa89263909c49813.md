## Title
External caller deposits are permanently absorbed into the Wallet Contract instead of being refunded on registrar/NEP-141 lookup failures - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (deployed on ETH-implicit accounts to process Ethereum-style transactions, see NEP-518) is a `#[payable]` entry point (`rlp_execute`) that can receive an attached deposit from an external caller/relayer. It is designed to refund that deposit to the caller if the underlying cross-contract action ultimately fails, using the `CallerDeposit` bookkeeping struct. However, two of the intermediate callback functions in the execution pipeline — `address_check_callback` and `nep_141_storage_balance_callback` — have early-return failure branches that discard the `caller_deposit` parameter instead of issuing the refund, unlike the terminal `rlp_execute_callback` which correctly refunds on failure.

### Finding Description
`CallerDeposit::new` captures an external (non-self) caller's `attached_deposit` so it can later be refunded if the requested action fails [1](#0-0) . This value is threaded through the multi-step promise chains for two transaction kinds: emulated EOA transfers requiring an address-registrar lookup, and emulated ERC-20 transfers requiring a NEP-141 `storage_balance_of` check [2](#0-1) .

In the only path that is actually refund-aware, `rlp_execute_callback`, a `PromiseResult::Failed` explicitly triggers a `promise_batch_action_transfer` back to the caller: [3](#0-2) 

But `address_check_callback`, which runs *before* `rlp_execute_callback` in the address-check flow, drops `caller_deposit` entirely on both of its failure branches (registrar call failed, or malformed registrar response) without issuing any refund: [4](#0-3) 

Likewise, `nep_141_storage_balance_callback` drops `caller_deposit` on its failure branches (NEP-141 `storage_balance_of` call failed, or malformed response): [5](#0-4) 

In all of these early-return cases the function returns `PromiseOrValue::Value(ExecuteResponse { success: false, ... })` directly — never scheduling a transfer back to the original `predecessor_account_id` that funded `caller_deposit`. Because the deposit was already credited to the ETH-implicit (wallet contract) account's balance when the original transaction was accepted, the money is not lost from the network, but it is permanently absorbed into the wallet account with no protocol-level mechanism returning it to the caller who attached it — mirroring the reported class of bug ("payable" entry point receives value with no corresponding withdraw/refund path on certain failure branches).

The existing test suite only exercises the refund on the final callback's failure (`rlp_execute_callback`) [6](#0-5) , and does not cover the address-registrar or NEP-141 storage-balance failure branches, which is consistent with this refund gap not being caught.

### Impact Explanation
Any unprivileged relayer/caller that submits an RLP-encoded Ethereum transaction with an attached deposit on behalf of a user (a normal, permissionless operation of this contract) can have that deposit silently and irrecoverably swallowed by the target ETH-implicit account whenever:
- the address-registrar lookup call fails or returns an unparsable response, or
- the NEP-141 `storage_balance_of` call fails or returns an unparsable response.

This is a concrete instance of value moving to an unintended party without consent (the caller's funds end up controlled by the wallet's owner instead of returning to the caller), which can also be triggered adversarially by a malicious/slow registrar or token contract to strip relayers of their attached deposits. This qualifies as unauthorized value movement / permanently frozen funds for the depositing party, reachable purely via a transaction to the public `rlp_execute` entry point.

### Likelihood Explanation
Both failure conditions (a failed cross-contract call, or a malformed/rejected JSON response from the registrar or an NEP-141 token) are realistic and not access-controlled — they can occur due to gas exhaustion, a paused/malicious token contract, or a misbehaving registrar, all of which are externally triggerable by any caller choosing which token/target account to interact with. No validator or node compromise is required; a single crafted or opportunistically-timed transaction from an ordinary account is sufficient.

### Recommendation
Thread the refund logic used in `rlp_execute_callback` into the early-return failure branches of `address_check_callback` and `nep_141_storage_balance_callback` so that `caller_deposit` is refunded to `predecessor_account_id` whenever any callback in the chain terminates in failure, not only the final one.

### Proof of Concept
1. An external relayer account (not the wallet owner) calls `rlp_execute` on an ETH-implicit account's Wallet Contract, attaching a deposit, with a transaction that emulates an EOA base-token transfer requiring an address-registrar lookup (`EOABaseTokenTransfer { address_check: Some(_), .. }`).
2. The address-registrar cross-contract call fails (e.g., registrar contract is paused, out of gas, or returns malformed data).
3. `address_check_callback` is invoked with `PromiseResult::Failed` (or an unparsable `Successful` value) and returns `ExecuteResponse { success: false, .. }` directly, per [4](#0-3) , without ever transferring the tracked `caller_deposit` back to the relayer.
4. The relayer's attached deposit remains credited to the target wallet contract's account balance permanently, with no mechanism refunding it to the relayer — an analog of ETH getting stuck with no withdraw path in the original report.

    pub fn new(context: &ExecutionContext) -> Option<Self> {

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
