### Title
Nakamoto block signature threshold collapses to zero when the reward-set signer list floors to empty - ([File: stackslib/src/chainstate/stacks/boot/mod.rs])

### Summary
`RewardSet::make_signer_set` and `RewardSet::total_signing_weight` conflate "no signers were computed" (`None`) with "a signers list exists but every entry floored to weight 0" (`Some(vec![])`). The latter case is treated by `NakamotoBlockHeader::compute_voting_weight_threshold` as a valid, non-degenerate reward set with `total_weight == 0`, which yields a required signing `threshold == 0`. `verify_signer_signatures` then accepts a block whose `signer_signature` is empty, because `0 < 0` is false. This mirrors the TensorFlow `simplifyBroadcast` class of bug: an aggregate (`maxRank`/`total_weight`) degenerates to `0` for an input set that is non-empty in form but empty in substance, and downstream code fails to special-case that degenerate `0`, producing unsafe behavior instead of an error.

### Finding Description
`RewardSet::make_signer_set` (`stackslib/src/chainstate/stacks/boot/mod.rs:1020-1073`) builds a `BTreeMap` of `(signing_key -> stacked_amt)`, then computes `weight = stacked_amt / threshold` for each entry and drops entries with `weight == 0`: [1](#0-0) 

If `threshold` is larger than every individual `stacked_amt` (e.g. because the PoX participation/threshold calculation is based on total liquid uSTX and reward-slot count rather than on the actual set of `stacked_amt` entries), every entry is filtered out by `if weight == 0 { return None; }`, and the function returns `Some(vec![])` — a non-`None` result — because the early-return for "no entries at all" only triggers on an empty *input* (`entries.first()`), not on an all-filtered-to-zero *output*: [2](#0-1) 

This `Some(vec![])` is then stored as the reward set's `signers` field and later consumed by `RewardSet::signers()` / `RewardSet::total_signing_weight()`: [3](#0-2) 

`total_signing_weight()` explicitly distinguishes `None` (error) from `Some(signers)`, but for `Some(vec![])` it happily folds an empty iterator to `0` and returns `Ok(0)` — it does not treat an empty-but-present signer list as an error the way `pox_5_compute_and_update_signers` does for the Waterfall path (`stackslib/src/chainstate/nakamoto/signer_set.rs:763-766`, which explicitly guards `if signer_set.is_empty() { return Err(...) }`). The PoX-4 path (`pox_4_compute_and_update_signers`, `stackslib/src/chainstate/nakamoto/signer_set.rs:703-738`) has no equivalent guard on the `RewardSet` it stores; it just calls `StacksChainState::make_reward_set(...)` (which wraps `make_signer_set`) and stores whatever it returns.

Downstream, `NakamotoBlockHeader::compute_voting_weight_threshold` takes this `total_weight` and computes: [4](#0-3) 
For `total_weight == 0`, `(0 * threshold) % 10 == 0`, so `ceil = 0`, and the result is `0`.

Finally, `verify_signer_signatures` (`stackslib/src/chainstate/nakamoto/mod.rs:1096-1190`) computes `total_weight_signed` from the block's actual signatures (which is `0` for a block with an empty `signer_signature` vector, as produced by `NakamotoBlockHeader::from_parent_empty`, `stackslib/src/chainstate/nakamoto/mod.rs:1212-1236`, `signer_signature: vec![]`) and only rejects if `total_weight_signed < threshold`: [5](#0-4) 
With `threshold == 0` and `total_weight_signed == 0`, the check `0 < 0` is false, so the block is accepted as having "enough" signatures — i.e., zero signer approvals are treated as satisfying the consensus threshold.

This breaks the core equality that a Nakamoto block's signer-weight-signed must meet or exceed the reward-cycle's approval threshold; here the threshold itself silently degenerates to zero due to an aggregate-over-empty-set bug, exactly analogous to `maxRank` degenerating to `0` for all-scalar shapes in the reported TensorFlow bug.

### Impact Explanation
Since the reward set is computed deterministically from on-chain PoX/stacking state, every honest node would compute the same degenerate `Some(vec![])` signer set and the same `threshold == 0` for the affected reward cycle. This is not a "two nodes disagree" scenario — it is a network-wide acceptance of an effectively unsigned/unapproved Nakamoto block for that reward cycle, which is a Critical-class outcome per the ruleset ("an invalid block accepted... network-wide"). At minimum it represents a signer-weight-threshold divergence from the intended protocol invariant (every block must carry signatures worth ≥ threshold weight), falling under "signer weight below threshold... from the wrong set."

### Likelihood Explanation
Triggering requires the PoX-4 (or any non-Waterfall) `pox_ustx_threshold` computation to exceed every individual stacker's `stacked_amt` for a given reward cycle — e.g., a reward cycle where liquidity/participation assumptions used to derive `threshold` diverge from the actual set of signers who stacked (many small stackers, or an unusually high threshold relative to actual locked amounts). This does not require a majority of stake or an admin key — it can arise from ordinary, legitimate small-scale stacking activity relative to the network's total liquid supply, i.e., it is reachable by unprivileged participants shaping their own stacking amounts. However, I was not able to fully trace `StacksChainState::make_reward_set` / `get_reward_threshold_and_participation` (the wrapper that calls `make_signer_set` for the PoX-4 path) within the available tool budget, so I cannot confirm with certainty whether an additional guard exists there that prevents this specific "all-filtered-to-zero" case from being stored into the on-chain reward set. This is the main residual uncertainty in this finding.

### Recommendation
In `make_signer_set`, treat an all-filtered-to-empty result as equivalent to "no signer set" (`return None` if the post-filter `signer_set` is empty, not just if the input `entries` slice is empty). Additionally, harden `RewardSet::total_signing_weight()` to return an error when `signers()` returns `Some(v)` with `v.is_empty()`, mirroring the explicit empty-set guard already present in `pox_5_compute_and_update_signers`. This ensures `compute_voting_weight_threshold` can never be invoked with `total_weight == 0`, and that a reward cycle with no viable signers is treated as `ChainstateError::NoRegisteredSigners` rather than silently producing a zero-signature-threshold block-acceptance rule.

### Proof of Concept
1. Arrange stacking transactions for a reward cycle such that the PoX-4 threshold computed by `get_reward_threshold_and_participation` (from total liquid uSTX and reward-slot count) exceeds every individual stacker's locked amount (feasible with several small, independent stackers rather than one large one).
2. `pox_4_compute_and_update_signers` calls `make_reward_set` → `make_signer_set`, which filters every entry to `weight == 0` and returns `Some(vec![])` (`stackslib/src/chainstate/stacks/boot/mod.rs:1051-1071`) instead of `None`.
3. The resulting `RewardSet` is stored on-chain for the cycle; `total_signing_weight()` returns `Ok(0)` (`stackslib/src/chainstate/stacks/boot/mod.rs:495-503`).
4. Any miner assembles a Nakamoto block for that reward cycle with `signer_signature: vec![]` (as in `from_parent_empty`, `stackslib/src/chainstate/nakamoto/mod.rs:1212-1236`).
5. `verify_signer_signatures` computes `threshold = compute_voting_weight_threshold(0) = 0` and `total_weight_signed = 0`; the check `total_weight_signed < threshold` (`stackslib/src/chainstate/nakamoto/mod.rs:1182`) is `0 < 0 == false`, so the function returns `Ok(0)` — the block is accepted as sufficiently signed by every node, despite carrying zero signer approvals.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
