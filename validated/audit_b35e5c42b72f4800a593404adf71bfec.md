### Title
Floating-point precision loss in `ExchangeProcessor`'s Bancor-formula `pow` calculations enables inaccurate swap accounting in TRON's built-in Exchange - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
TRON's on-chain Bancor-style Exchange (TRC10 token market) computes swap outputs using `Math.pow`/`StrictMath.pow` on `double` values with exponents `0.0005` and `2000.0`. This is the same bug class as the reported weighted-math vulnerability: floating-point `pow` loses precision at these balance/exponent magnitudes, and the loss compounds through two chained `pow` calls (`exchangeToSupply` → `exchangeFromSupply`), producing swap amounts that diverge from the correct Bancor-formula result — including rounding to values far from expected (potentially favoring the trader over pool liquidity providers, or vice versa) for realistic token balances.

### Finding Description
The default (`ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal value = 0) swap path is:

- `ExchangeCapsule.transaction()` [1](#0-0)  instantiates `new ExchangeProcessor(supply, useStrictMath)` when `hardenedCalc` is false, and calls `processor.exchange(...)`.
- `ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute the Bancor formula entirely in `double` arithmetic using `Maths.pow(base, 0.0005, useStrictMath)` and `Maths.pow(base, 2000.0, useStrictMath)`: [2](#0-1) 
- `Maths.pow` simply forwards to `Math.pow`/`StrictMath.pow`: [3](#0-2) [4](#0-3) 
- This exact double-precision `pow` limitation is documented in the codebase itself, which marks `Maths`/`MathWrapper` as `@Deprecated` and recommends `StrictMathWrapper` "especially for floating-point calculations" [5](#0-4) , and the platform-specific `MathWrapper` even hard-codes a lookup table of known-bad `(a,b)->result` pairs recorded from historical mainnet blocks to patch specific precision mismatches between platforms [6](#0-5) , confirming that `pow`-precision divergence in this exact swap formula has already caused real consensus/accuracy issues on mainnet.
- This path is directly reachable by any unprivileged account via a broadcast `ExchangeTransactionContract`, processed by `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`: [7](#0-6) 
- The project's own remediation (`SafeExchangeProcessor`, using `BigDecimal` with 18-digit scale before converting to `double` only for the final `pow`) is gated behind `ALLOW_HARDEN_EXCHANGE_CALCULATION`, a chain parameter that defaults to `0` (unhardened) unless a super-representative committee proposal explicitly sets it to `1`: [8](#0-7) 

Anyone can create an Exchange pool with attacker-chosen initial balances (via `ExchangeCreateActuator`, not shown above but part of the same actuator family) and then trade against it with attacker-chosen `sellTokenQuant`, directly controlling the inputs to the vulnerable `pow` calls — mirroring the report's PoC of choosing balances/amounts to trigger precision loss.

### Impact Explanation
Incorrect Bancor-formula outputs corrupt on-chain token accounting: a trader can receive more `anotherTokenQuant` than the pool should mathematically owe (draining value from other participants / the pool reserve), or in adversarial configurations, output can round to values inconsistent with the invariant the Bancor curve is supposed to preserve. Because `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` all mutate `AccountCapsule` balances and `ExchangeCapsule` reserves based on this computation, systematic rounding abuse constitutes real asset/accounting corruption on an unprivileged, permissionless DEX feature built into the protocol.

### Likelihood Explanation
High reachability: no privileged role is required — any account can create an exchange pool and issue `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions with attacker-chosen quantities, and the vulnerable unhardened `ExchangeProcessor` path is the default unless the committee proposal `ALLOW_HARDEN_EXCHANGE_CALCULATION` has been separately enacted on that network. The codebase's own hard-coded historical `pow` mismatch table is direct evidence this exact computation has already diverged from the mathematically correct result on production data.

### Recommendation
- Enact/verify `ALLOW_HARDEN_EXCHANGE_CALCULATION` = 1 on all networks so `SafeExchangeProcessor` (BigDecimal-based, higher-precision) is the mandatory swap path, removing the legacy `ExchangeProcessor`/`Maths.pow` path entirely rather than leaving it as an opt-in toggle.
- In `SafeExchangeProcessor`/any successor, avoid falling back to `double`-based `StrictMathWrapper.pow` for the final exponentiation; use a fixed-point/BigDecimal `pow` implementation with sufficient guard digits, and short-circuit `pow(x, 1)` to return `x` exactly, as recommended in the referenced patch.
- Add an invariant check ensuring the effective exchange rate/product does not decrease disadvantageously to the pool after a swap, rejecting the transaction otherwise (mirroring the "non-decreasing invariant" remediation in the report).

### Proof of Concept
1. Create an `Exchange` with large TRC10/TRX balances on both sides (attacker fully controls both amounts since they create the pool via `ExchangeCreateActuator`).
2. Submit an `ExchangeTransactionContract` with `sellTokenQuant` chosen such that `quant / newBalance` and `supplyQuant / supply` fall into ranges where `Math.pow(1+ratio, 0.0005)` / `Math.pow(1+ratio, 2000.0)` lose precision (as in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, [2](#0-1) ).
3. Compare the actuator's computed `anotherTokenQuant` against the exact Bancor-formula value computed with arbitrary precision; for balances/amounts analogous to the report's PoC (large balances, moderate swap sizes), the two diverge, and `ExchangeTransactionActuator`'s only guard is `anotherTokenQuant < tokenExpected` [9](#0-8) , which does not prevent the attacker from setting `tokenExpected` low and profiting from favorable rounding.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
