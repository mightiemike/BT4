### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` causes uncaught `ArithmeticException` during TVM execution - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` (a dynamic, network-wide store value) without validating it is non-zero before performing the division. The only guard is a Java `assert`, which is compiled out and inert unless the node process is started with `-ea`, so it provides no runtime protection in a standard production deployment.

### Finding Description
The method reads `totalEnergyWeight` from `DynamicPropertiesStore` and immediately uses it as a divisor: [1](#0-0) 

When `hardenResourceCalculation()` (`VMConfig.allowHardenResourceCalculation()`) is enabled, the divisor is used in `BigInteger.divide(...)`, which throws `ArithmeticException: BigInteger divide by zero` if `totalEnergyWeight` is `0`. This exactly mirrors the reported bug class: a reward/limit calculation performs `value / totalSupply`-style division without checking for a zero denominator, relying on an implicit assumption ("total weight/supply is always positive") that is not actually enforced at the call site.

The `assert totalEnergyWeight > 0;` statement at line 976 is not a safeguard in production: Java assertions are disabled by default and must be explicitly enabled with the `-ea` JVM flag, which java-tron does not set for its node startup scripts. Therefore this line has no effect on mainnet/production nodes.

`totalEnergyWeight` is not a hardcoded chain constant — it is a dynamic property tracked in `DynamicPropertiesStore` and mutated as accounts freeze/unfreeze TRX for energy. It can transiently become `0` (e.g., on freshly bootstrapped/private chains before any account has frozen balance for energy, or in theoretically achievable edge states where all frozen-for-energy balance is unwound), which is directly analogous to the reported scenario where `supplyCheckpoints` becomes `0` after a `poke()`-style state transition zeroes out the accounted supply.

This method is invoked from TVM-facing code paths such as `ContractState`, which is used during contract execution (`VMActuator`), meaning the divide-by-zero is reachable from a broadcast smart-contract transaction, not merely from privileged/internal code: [2](#0-1) 

### Impact Explanation
If `totalEnergyWeight` is `0` at the time `calculateGlobalEnergyLimit` is invoked while the harden-resource-calculation chain parameter is active, any TVM execution path that reaches this method (via `ContractState`/`VMActuator`) throws an uncaught `ArithmeticException`. Depending on how deep in the TVM execution stack this exception propagates and whether it is caught generically as a transaction failure versus escaping to node-level exception handling, this can cause transaction processing failures or, in the worst case, contribute to node instability/DoS for any node executing that contract call — impacting all validating nodes identically (a consensus-relevant computation), which is a high-impact class of bug.

### Likelihood Explanation
Likelihood is low under normal mainnet conditions because `totalEnergyWeight` is generally kept positive by long-established freezing activity across the network. However, it is a realistic risk on private/test networks, immediately after genesis/bootstrap, or in any future protocol change that could transiently zero out `totalEnergyWeight` (analogous to the "poke" state transition in the original report that zeroes checkpoint supply). Because the safeguard is only a disabled `assert`, there is no actual runtime check preventing this whenever the harden flag is enabled and the weight is legitimately zero.

### Recommendation
Add an explicit runtime guard before the division, independent of Java assertions, e.g.:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```
This mirrors the recommended fix pattern in the original report (defaulting the divisor to a safe fallback instead of relying on an assumption that can be violated), and should also be applied consistently to any other consumer of `getTotalEnergyWeight()`/`getTotalNetWeight()` that performs unguarded division in `hardenResourceCalculation()` branches.

### Proof of Concept
Not directly reproducible from the indexed context alone (would require reproducing a network state with `totalEnergyWeight == 0` and `VMConfig.allowHardenResourceCalculation()` enabled, then triggering a TVM call path that invokes `calculateGlobalEnergyLimit`). Given index size limits, some full call-chain files (`ContractState.java`, `VMActuator.java`) were only partially inspected; a Devin session with full repository access is recommended to trace the exact opcode/precompile entry point and build a runnable PoC test analogous to the `RepositoryImplHardenTest` suite already present in the codebase: [3](#0-2)

```java
  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
```
