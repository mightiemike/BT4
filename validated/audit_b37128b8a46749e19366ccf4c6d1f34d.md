### Title
Missing enforcement of the voting-window check in `vote-for-aggregate-public-key` allows aggregate-key votes outside the intended prepare-phase window - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
The `.signers-voting` contract defines a helper, `is-in-voting-window`, whose stated purpose is to restrict aggregate-public-key voting to signers of the *currently active* reward cycle during the prepare phase. That helper is never called by the only public entrypoint that performs voting, `vote-for-aggregate-public-key`. This mirrors the external report's core bug class: a delay/window that is defined in code but not enforced at the call site, letting a state-changing action (here, a consensus vote instead of a reward-weight update) be performed outside its intended timing window.

### Finding Description
`is-in-voting-window` combines two checks that are supposed to gate voting: [1](#0-0) 
1. `last-cycle == reward-cycle` — the reward cycle being voted on must be the one whose signer set was most recently finalized by the node (`get-last-set-cycle` in `.signers`).
2. `is-in-prepare-phase height` — the vote must occur in the prepare phase.

However, `vote-for-aggregate-public-key` never calls `is-in-voting-window` (nor `is-in-prepare-phase` directly). Its only "window" guard is: [2](#0-1) 
which merely checks that no aggregate key has *already* been approved for that `reward-cycle` — it says nothing about whether the current burn height is inside that cycle's prepare phase, or whether `reward-cycle` is even the currently-active cycle being finalized. The rest of the function (weight lookup, tally update, threshold check) proceeds unconditionally: [3](#0-2) 

Because `ERR_OUT_OF_VOTING_WINDOW` is the error code documented for "out of voting window" but is actually returned only by the "key already set" check, the timing invariant the contract's own comment promises ("The vote must happen after the list of signers has been set... which occurs in the first block of the prepare phase") is not actually enforced anywhere in the public function.

### Impact Explanation
This breaks the intended equality "a vote for reward-cycle `N` is only valid while `N` is the actively-finalizing cycle and burn-height is within `N`'s prepare phase." Any signer registered for a not-yet-approved `reward-cycle` (past, present, or a cycle whose signer set has already been computed but is not the "current" one per `get-last-set-cycle`) can cast a vote for that cycle at any later time, as long as `.signers get-signer-by-index`/`get-signers` still has data for it and no key has been approved yet. This can let stale rounds/votes finalize an aggregate public key outside the window signers and nodes assume is authoritative, or let a round that failed to reach consensus during the correct window be revived and pushed over threshold much later — a scenario the rest of the system (miners, other signers, `stacks-signer` clients) does not expect, since they rely on `is-in-prepare-phase`/`get-last-set-cycle` semantics being enforced on-chain. This is a minority-triggerable divergence in what different nodes/signers observe as the "approved" aggregate key for a cycle, i.e., a temporary tip/state disagreement class of issue, bounded to the signer-voting mechanism (not a direct fund-loss or chain-split by itself).

### Likelihood Explanation
Likelihood is moderate: the only defense against out-of-window voting is that `.signers get-signer-by-index`/`get-signers` for a given `reward-cycle` must return valid data, and that no aggregate key has yet been recorded for that cycle. Any single already-registered signer for a still-unresolved reward cycle (one whose vote never reached the 70% `threshold-consensus`) can trigger this without needing majority collusion — a single vote call is sufficient to demonstrate the missing window check; reaching consensus outside the window would need enough signer weight, but even a single unauthorized-timing vote already violates the invariant and can perturb `round-data`/`used-aggregate-public-keys` state.

### Recommendation
Add an explicit `(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))` call at the top of `vote-for-aggregate-public-key`, so that the timing guard the helper was written for is actually enforced, matching the function's own documentation.

### Proof of Concept
Note: I could not run the Clarity test suite in this environment to produce an executed trace; the following is a source-level reachability argument based on the code cited above.
1. Wait for the `.signers` contract to finalize the signer set for reward-cycle `N` (this occurs at cycle-boundary processing, independent of `.signers-voting`).
2. As a registered signer for cycle `N`, do **not** vote during cycle `N`'s prepare phase (so no aggregate key is approved for `N`).
3. After the prepare phase for `N` has ended (i.e., outside the window `is-in-voting-window` would have required), call `vote-for-aggregate-public-key` with `reward-cycle = N`. Because the function never checks `is-in-voting-window`/`is-in-prepare-phase`, the call succeeds (subject only to the `is-none aggregate-public-keys` check), updating `tally`, `round-data`, and potentially `aggregate-public-keys` for `N` long after the window nodes/clients assume is closed.

(define-public (vote-for-aggregate-public-key (signer-index uint) (key (buff 33)) (round uint) (reward-cycle uint))
    (let ((tally-key {reward-cycle: reward-cycle, round: round, aggregate-public-key: key})
            ;; vote by signer weight
            (signer-weight (try! (get-signer-weight signer-index reward-cycle)))
            (new-total (+ signer-weight (default-to u0 (map-get? tally tally-key))))
            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))
            (threshold-weight (get-threshold-weight reward-cycle))
            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))
        ;; Check that aggregate public key has not been used in a previous reward cycle
        (asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))
        ;; Check that signer hasn't voted in this reward-cycle & round
        (asserts! (map-insert votes {reward-cycle: reward-cycle, round: round, signer: tx-sender} {aggregate-public-key: key, signer-weight: signer-weight}) (err ERR_DUPLICATE_VOTE))
        ;; Check that the round is incremented by at most 1
        (try! (update-last-round reward-cycle round))
        ;; Update the tally for this aggregate public key candidate
        (map-set tally tally-key new-total)
        ;; Update the current round data
        (map-set round-data {reward-cycle: reward-cycle, round: round} {
            votes-count: (+ (get votes-count current-round) u1),
            votes-weight: (+ (get votes-weight current-round) signer-weight)})
        ;; Update used aggregate public keys
        (map-set used-aggregate-public-keys key reward-cycle)
        (print {
            event: "voted",
            signer: tx-sender,
            reward-cycle: reward-cycle,
            round: round,
            key: key,
            new-total: new-total,
        })
        ;; If the new total weight is greater than or equal to the threshold consensus
        (if (>= new-total threshold-weight)
            ;; Save this approved aggregate public key for this reward cycle.
            ;; If there is not already a key for this cycle, the insert will
            ;; return true and an event will be created.
            (if (map-insert aggregate-public-keys reward-cycle key)
                (begin
                    ;; Create an event for the approved aggregate public key
                    (print {
                        event: "approved-aggregate-public-key",
                        reward-cycle: reward-cycle,
                        round: round,
                        key: key,
                    })
                    true)
                false
            )
            false
        )
        (ok true)))
