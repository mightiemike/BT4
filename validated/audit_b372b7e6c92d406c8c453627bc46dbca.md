## Title
Gas-refund penalty (NEP-536) truncates instead of rounding up, letting more value than intended escape burning on every gas refund - (File: `core/parameters/src/cost.rs`)

### Summary
`RuntimeFeesConfig::gas_penalty_for_gas_refund` computes the NEP-536 refund penalty — a "fee" that is supposed to be burnt (not returned to the user) out of every unspent-gas refund — using plain integer division, which truncates (rounds toward zero) instead of rounding up in favor of the protocol. This is the exact bug class described in the external report: a percentage-based fee computed with a rounding-down division instead of rounding up, causing value to leak away from the protocol/burn mechanism on every single occurrence, cumulatively, forever.

### Finding Description
The penalty is computed as: [1](#0-0) 

```rust
pub fn gas_penalty_for_gas_refund(&self, gas_refund: Gas) -> Gas {
    let relative_cost = Gas::from_gas(
        (u128::from(gas_refund.as_gas()) * *self.gas_refund_penalty.numer() as u128
            / *self.gas_refund_penalty.denom() as u128)
            .try_into()
            .unwrap(),
    );
    let penalty = std::cmp::max(relative_cost, self.min_gas_refund_penalty);
    std::cmp::min(penalty, gas_refund)
}
```

`gas_refund * numer / denom` is integer (floor) division, so any fractional remainder of the intended percentage penalty is discarded rather than rounded up. This function is invoked from `refund_unspent_gas_and_deposits`, where the resulting `refund_penalty` is subtracted from the amount refunded to the transaction signer — i.e., it directly determines how much of the unspent gas is *not* returned (effectively burnt/withheld) versus how much *is* returned to the user: [2](#0-1) 

This mirrors `OrderFees.percentageFeeForValue()` in the referenced report exactly: a percentage fee meant to accrue to the protocol side is computed with a rounding-down division (`PrbMath.mulDiv18` in the analog, plain `/` here), so the fee collected is always `<=` the mathematically correct value, and the difference is instead handed back to the counterparty (the refund recipient) rather than to the protocol.

The protocol's own economics documentation confirms the intended formula and its purpose (discouraging over-attachment of gas / compensating the network for issuing a refund receipt): [3](#0-2) 

### Impact Explanation
Every single receipt execution that leaves unspent gas and triggers a gas refund (which is the common case for function calls, since attaching exactly the right amount of gas is impractical) computes this NEP-536 penalty with floor division. Each occurrence lets a fraction-of-a-yoctoNEAR-equivalent-in-gas escape the intended burn, and this happens on essentially every transaction network-wide. As the report argues for the analog, no single instance is large, but the leak compounds continuously with network usage: the total amount actually withheld from refunds systematically falls short of `gas_refund_penalty * unspent_gas`, meaning users retain slightly more value than the protocol's specified economic model dictates. This is a violation of the intended fee/burn accounting invariant that is supposed to hold at `runtime/runtime/src/lib.rs:1319` (`refund_penalty ≤ intended penalty`, but never `<`), and is reachable by any account simply submitting an ordinary function-call transaction with excess attached gas — no special privileges needed.

### Likelihood Explanation
Reachability is trivial: any unprivileged user can trigger a gas refund by attaching more gas than a function call consumes, which is normal, common behavior (the docs note that attaching the exact right amount of gas is "tricky"). The only caveat is that on the current mainnet snapshot the parameters are `gas_refund_penalty = 0/100` and `min_gas_refund_penalty = 0`, per the documented rollout plan, so the penalty and thus the rounding defect are currently inert in practice: [4](#0-3) 

However, the code path is live and will activate automatically once these parameters are set to their planned non-zero values (5% / 1 Tgas) via a future runtime-config update, at which point the rounding-down defect becomes active on every refund-generating transaction across the network without any additional code change or governance decision about rounding direction.

### Recommendation
Round the penalty calculation up (ceiling division) instead of down, e.g.:
```rust
let numer = *self.gas_refund_penalty.numer() as u128;
let denom = *self.gas_refund_penalty.denom() as u128;
let gas = u128::from(gas_refund.as_gas());
let relative_cost = Gas::from_gas(((gas * numer + denom - 1) / denom).try_into().unwrap());
```
This ensures the amount withheld from the refund (and thus not returned to the user) is always `>=` the mathematically exact intended percentage, consistent with the general principle that protocol-favoring fees must round up, matching the fix pattern recommended in the external report (Uniswap-style `mulDivRoundingUp`).

### Proof of Concept
1. Set `gas_refund_penalty = 5/100` (the documented target value from NEP-536) and `min_gas_refund_penalty = 0`.
2. Submit a function call with `gas_refund = 19` (gas units) unspent.
3. `relative_cost = 19 * 5 / 100 = 95 / 100 = 0` (floor), so `penalty = max(0, min_gas_refund_penalty) = 0`, even though the true intended fee is `0.95` gas units that should round up to `1`.
4. The user receives the full `19` gas units back as a refund instead of `18`, and the protocol accrues zero penalty instead of the intended non-zero amount — repeated across every refund on the network, this compounds into a persistent value leak away from the protocol's designed burn schedule.

```markdown
### Gas Refund Fee

After executing the transaction, there might be unspent gas left. For function
calls, this is the normal case, since attaching exactly the right amount of gas
is tricky. Additionally, in case of receipt failure, some actions that did not
start execution will have the execution gas unspent. This gas is converted back
to NEAR tokens and sent as a refund transfer to the original signer.

Before protocol version 78, the full gas amount would be refunded and the refund
transfer action was executed for free. With [NEP-536](https://github.com/near/NEPs/pull/536)
which was implemented in version 78, the plan was to have the network charge a
fee of 5% of unspent gas or a minimum of 1 Tgas. This often removes the need to
send a refund, which avoids additional load on the network, and it compensates
for the load of the refund receipt when it needs to be issued. This is intended
to discourage users from attaching more gas than needed to their transactions.
In the nearcore code, you will find this fee under the name `gas_refund_penalty`.
```
