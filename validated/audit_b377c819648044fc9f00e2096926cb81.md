### Title
Global-contract `AccountId` identifier survives owner-account deletion, enabling silent takeover of shared code trusted by other accounts - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
NEAR's global-contract feature lets an account deploy WASM code once and have many other accounts reference it via `AccountContract::GlobalByAccount(owner_id)` instead of storing a local copy — functionally analogous to a shared "implementation contract" that many proxy-like accounts delegate execution to. The Biconomy report describes destruction/hijack of a shared implementation contract silently breaking or compromising every dependent proxy. The nearcore analog is not destruction of WASM bytecode itself (there is no delete action for global contracts), but takeover: the `GlobalContractCode`/`GlobalContractNonce` trie entries keyed by `GlobalContractIdentifier::AccountId(owner_id)` are never cleaned up when `owner_id`'s account is deleted, and the owner's account name can later be re-registered by an unrelated party who can then deploy new, attacker-controlled code under the very same identifier that other, unrelated accounts still reference via `UseGlobalContract`.

### Finding Description
`GlobalContractDeployMode::AccountId` intentionally lets the owning account update the global contract for everyone referencing it — that part is documented and consensual (`core/primitives/src/action/mod.rs:135-144`). The gap is what happens when the owner account itself is deleted:

- `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) calls `remove_account`, which deletes `TrieKey::Account`, `TrieKey::ContractCode`, access keys, gas-key nonces and contract data for `account_id` [4](#0-3) , but it never removes `TrieKey::GlobalContractCode { identifier: AccountId(account_id) }` or the paired `TrieKey::GlobalContractNonce`. Those keys are namespaced under the *account id string*, not under the `Account` record.
- Once `account_id` is deleted, it can be re-created through the normal account-creation path (`action_create_account`, `runtime/runtime/src/actions.rs:166-209`), which imposes no check for a "previously owned a global contract" flag and starts the new account fresh with `AccountContract::None`.
- The new controller of `account_id` (or the original attacker after a self-inflicted delete-and-reclaim) can then submit `DeployGlobalContractAction { deploy_mode: AccountId }` again. `initiate_distribution` derives the identifier purely from the caller's `account_id` string (`GlobalContractIdentifier::AccountId(account_id.clone())`, `runtime/runtime/src/global_contracts.rs:143-158`), and `apply_distribution_current_shard` unconditionally overwrites `TrieKey::GlobalContractCode` at that identifier as long as the nonce is fresh, which it will be since the nonce entry also survived the deletion and simply increments (`runtime/runtime/src/global_contracts.rs:173-227`).
- Every other, unrelated account that previously ran `UseGlobalContract { GlobalContractIdentifier::AccountId(account_id) }` (`runtime/runtime/src/global_contracts.rs:76-108`) still has `AccountContract::GlobalByAccount(account_id)` stored on its own account and will silently start executing whatever new code the new controller deploys — with no new action, consent, or transaction from those referencing accounts.

This mirrors the Biconomy bug's structural weakness: a shared/singleton code artifact that many independent accounts trust by reference can be taken over by an unauthorized party through a state transition (account deletion + re-creation + redeploy) that the protocol accepts as fully valid, silently changing the code executed on behalf of accounts that never authorized the new owner.

### Impact Explanation
Any account referencing a `GlobalByAccount` identifier whose owner account is later deleted and re-registered will execute arbitrary code chosen by the new registrant the next time a `FunctionCall` (or any receipt relying on that account's contract) is processed. Because `AccountContract::GlobalByAccount` code runs with the referencing account's own storage and balance context, the attacker-controlled code can drain balances, corrupt contract data, or otherwise act as that account — i.e., unauthorized value movement affecting every account that adopted the reused identifier, without any action on their part. This is a High-severity impact class matching "unauthorized value movement" / permanent compromise of dependent accounts.

### Likelihood Explanation
Reachable entirely through ordinary, unprivileged transactions: `DeployGlobalContractAction`, `UseGlobalContractAction`, `DeleteAccountAction`, and `CreateAccountAction` are all standard actions available to any signer with a full-access key on their own account, requiring no validator/operator/protocol privilege. The only preconditions are (1) the original owner account eventually being deleted (voluntarily, e.g. after "retiring" a well-adopted global contract, or as a deliberate rug-pull by the original deployer who is also the attacker) and (2) that account name being re-registrable (true for top-level names of sufficient length or subaccounts under a cooperating/careless parent). No leaked keys, malicious validators, or network-level assumptions are required.

### Recommendation
When deleting an account that owns an `AccountId`-mode global contract (or more precisely: on any `DeleteAccountAction`, and defensively at `DeployGlobalContractAction`/`UseGlobalContract` time), account for the `GlobalContractCode`/`GlobalContractNonce` entries keyed by that account id:
- Either forbid deleting an account that has ever deployed an `AccountId`-mode global contract still referenced by other accounts (requires tracking a reference count/flag), or
- Explicitly invalidate/tombstone the `GlobalContractCode{AccountId}` entry on account deletion so that redeploys after re-creation are treated as a brand-new, distinguishable identifier (e.g., mix in an account "generation"/creation nonce into the `GlobalContractIdentifier::AccountId` derivation), or
- At minimum, document and surface to `UseGlobalContract` callers that the `AccountId` identifier's trust is not tied to the currently-existing account and can be silently reassigned across account deletion/re-creation, and provide a way for dependents to detect such reassignment (e.g., expose the global contract's own creation/version nonce via view calls so integrators can pin to a specific deployment).

### Proof of Concept
1. Attacker/owner `A` (a normal named account, e.g. `shared.near`) submits `DeployGlobalContractAction { code: benign_wasm, deploy_mode: AccountId }`; this reaches `action_deploy_global_contract` → `initiate_distribution`, creating `GlobalContractCode{AccountId("shared.near")}` and `GlobalContractNonce{AccountId("shared.near")} = 1`.
2. Victim accounts `V1`, `V2`, ... submit `UseGlobalContractAction { contract_identifier: AccountId("shared.near") }`, setting their `AccountContract` to `GlobalByAccount("shared.near")` (`runtime/runtime/src/global_contracts.rs:76-108`).
3. `A` submits `DeleteAccountAction` on `shared.near`. `action_delete_account`/`remove_account` deletes the `Account`, local `ContractCode`, keys, and data for `shared.near`, but leaves `GlobalContractCode{AccountId("shared.near")}` and its nonce untouched (`core/store/src/utils/mod.rs:504-574`).
4. Some other party (or `A` itself with a new key) submits `CreateAccountAction` for `shared.near` again (permitted by ordinary account-creation rules, `runtime/runtime/src/actions.rs:166-209`), then `DeployGlobalContractAction { code: malicious_wasm, deploy_mode: AccountId }`. Since the stored nonce only increments and is never reset, this passes the freshness check and overwrites `GlobalContractCode{AccountId("shared.near")}` with `malicious_wasm` (`runtime/runtime/src/global_contracts.rs:191-227`).
5. The next `FunctionCall` receipt sent to `V1` or `V2` executes `malicious_wasm` in `V1`/`V2`'s own account context — with no new consent, key compromise, or transaction from `V1`/`V2` — demonstrating unauthorized code execution/value movement against accounts that never approved the new deployer.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
