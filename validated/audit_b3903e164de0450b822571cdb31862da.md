### Title
Unbounded full-store iteration in `Wallet.getAssetIssueListByName` bypasses the `ASSET_ISSUE_COUNT_LIMIT_MAX` cost cap enforced on `Wallet.getAssetIssueList(offset, limit)` - (File: `framework/src/main/java/org/tron/core/services/http/GetAssetIssueListByNameServlet.java`)

### Summary
`GetAssetIssueListByNameServlet` calls `Wallet.getAssetIssueListByName(ByteString)` which takes no offset/limit parameters and, unlike the paginated `getAssetIssueList`/`getAssetIssuesPaginated` path, has no cap applied to the number of `AssetIssueCapsule` records scanned or serialized. Since `AssetIssueStore.getAssetIssuesPaginated` explicitly clamps `limit` to `Commons.ASSET_ISSUE_COUNT_LIMIT_MAX` [1](#0-0) , while the by-name lookup path used by the servlet has no equivalent bound, an unprivileged caller can always choose the by-name endpoint to force full-store iteration regardless of how the paginated endpoints are rate-limited per request.

### Finding Description
`GetAssetIssueListByNameServlet.fillResponse` takes only a `value` (asset name) parameter and directly invokes `wallet.getAssetIssueListByName(ByteString.copyFrom(...))` with no `offset`/`limit` arguments at all [2](#0-1) . Both `doGet` and `doPost` reach this same unbounded call [3](#0-2) .

In contrast, the paginated read path — `AssetIssueStore.getAssetIssuesPaginated(offset, limit)` — always sorts the full in-memory list and then explicitly clamps the client-supplied `limit` to `ASSET_ISSUE_COUNT_LIMIT_MAX` before slicing the result [4](#0-3) . This shows the codebase's intended cost model for asset-issue listing APIs is "clamp to `ASSET_ISSUE_COUNT_LIMIT_MAX` regardless of attacker input."

The by-name servlet's underlying `Wallet.getAssetIssueListByName` method does not go through `getAssetIssuesPaginated`; it is a separate code path that filters by name over the full asset-issue set with no analogous cap. Both `RateLimiterServlet`-derived endpoints only throttle at the *request* level (via `RateLimiterServlet`), not the *per-request cost* level — so per-request cost asymmetry between the two APIs directly translates into an asymmetry in resource consumption per unit of allowed request rate. An unprivileged attacker who wants to force maximal server-side iteration/serialization work per allowed request will always prefer `GetAssetIssueListByName` over `GetAssetIssueList`, since the latter's cost is capped at `ASSET_ISSUE_COUNT_LIMIT_MAX` but the former's is not.

### Impact Explanation
On a chain/fixture with a large number of registered asset issues, each call to `GetAssetIssueListByName` forces the node to scan (and potentially serialize into the JSON/protobuf response) a number of `AssetIssueCapsule` records proportional to total store size, rather than the bounded `ASSET_ISSUE_COUNT_LIMIT_MAX`. This is a materially underpriced public read operation compared to its sibling API operating on the same store, and can be used to amplify CPU/IO cost per allowed request under any rate limiter that treats the two endpoints equivalently.

### Likelihood Explanation
No privileges are required — `GetAssetIssueListByNameServlet` is a public, unauthenticated HTTP endpoint [5](#0-4) . The gap is deterministic and repeatable: it only requires populating the `AssetIssueStore` with many entries (an on-chain, permissionless action — registering asset issues) and then issuing repeated by-name queries.

### Recommendation
Apply an equivalent bound (`Commons.ASSET_ISSUE_COUNT_LIMIT_MAX` or a dedicated cap) to the number of records scanned/returned by `Wallet.getAssetIssueListByName`, or route it through the same `getAssetIssuesPaginated`-style clamped path used by `getAssetIssueList(offset, limit)`, so that all public asset-issue read APIs over the same store share a uniform worst-case cost bound.

### Proof of Concept
Java integration test plan (using existing test infra similar to `GetAssetIssueListByNameServletTest`/`WalletTest`):
1. Populate `AssetIssueStore` with `N >> ASSET_ISSUE_COUNT_LIMIT_MAX` `AssetIssueCapsule` entries sharing/matching the queried `name` prefix logic used by `getAssetIssueListByName`.
2. Invoke `wallet.getAssetIssueList(0, ASSET_ISSUE_COUNT_LIMIT_MAX + 1)` and assert the returned list size is capped at `ASSET_ISSUE_COUNT_LIMIT_MAX` (verifies existing cap, per `AssetIssueStore.getAssetIssuesPaginated` clamp logic).
3. Invoke `wallet.getAssetIssueListByName(ByteString.copyFromUtf8(name))` against the same fixture and assert the returned list size (or measured scan count/latency) scales with `N` and is **not** bounded by `ASSET_ISSUE_COUNT_LIMIT_MAX`.
4. Assert/measure that step 3's CPU/IO cost (e.g., elapsed time or number of capsules deserialized) grows unbounded with `N` while step 2 stays flat beyond `N > ASSET_ISSUE_COUNT_LIMIT_MAX`, demonstrating the differential-cost gap.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
