### Title
`promise_yield_create_with_id` shares a single yield-ID namespace scoped only by receiver account, allowing any caller to grief a pending/expected yield resumption - (File: `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`, `runtime/runtime/src/ext.rs`)

### Summary
`promise_yield_create_with_id` lets a contract create a `PromiseYield` receipt keyed by a caller-influenced 32-byte `user_yield_id`, but the duplicate-detection mapping (`YieldIdToDataId`) is keyed only by the receiver account, not by the caller/predecessor or by the specific business context that chose the ID. Any unprivileged account able to trigger the receiver's code path that calls `promise_yield_create_with_id` with an attacker-chosen or attacker-predictable `yield_id` can pre-occupy that ID slot, causing the legitimate call that later tries to create a yield with the same ID to fail silently. This mirrors the reported `NFTMintSaleMultiple` bug class: two independent actors share one ID namespace on a single resource, and an external actor occupying an ID in that space blocks/breaks the legitimate flow that depended on it being free.

### Finding Description
`create_promise_yield_receipt_with_id` in `runtime/runtime/src/ext.rs` (lines 374-403) checks for an existing yield-ID mapping in the trie, scoped by `receiver_id` only:

```
runtime/runtime/src/ext.rs:378-385
if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
    .map_err(wrap_storage_error)?
{
    return Ok(None);
}
```

The check has no notion of which predecessor/caller "owns" a given `yield_id` — the mapping's key is `(receiver_id, user_yield_id)` (see `core/primitives/src/trie_key.rs`, `YieldIdToDataId`). This means the ID space for a given receiver account is effectively global across every caller and every cross-contract call that ever reaches that receiver.

In `runtime/near-vm-runner/src/wasmtime_runner/logic.rs` (`promise_yield_create_with_id`, lines 4259-4268), when the mapping already exists the call does not fail/abort — it silently returns a sentinel `u64::MAX` (documented at lines 4259-4261: "Returns None when a yield with the same user_yield_id is already pending... we return a sentinel without charging for receipt creation"). No `PromiseYield` receipt is created, the callback the caller expected to eventually run never fires, and (per the test `create_with_id_duplicate_in_same_call_returns_sentinel` in `integration-tests/.../test_yield_resume.rs`) the transaction still reports success — there is no visible error to the caller unless application code explicitly checks the returned promise index for the sentinel value.

If a contract derives `yield_id` from any value that is (a) supplied by the calling account, or (b) predictable/enumerable ahead of time (e.g., an order id, escrow id, auction id, or any application-level correlation id passed as a function-call argument), then any unrelated unprivileged account can call the same receiver contract first with a colliding `yield_id`, permanently occupying that slot until the pending yield is resumed or times out. Because the mapping is keyed purely on `(receiver_id, yield_id)`, the collision is trivial to engineer by any caller who can reach the receiver's public entry point and control (even partially) the value fed into `promise_yield_create_with_id`.

This is directly analogous to the reported vulnerability: `NFTMintSaleMultiple` shared a single token-id namespace between the sale contract and any external minter of the same NFT contract, so an external minter occupying an id blocked the sale contract's `mintWithId` call. Here, the shared resource is the per-receiver yield-ID namespace of `promise_yield_create_with_id`, and the "external minter" is any unprivileged account that can invoke a method on the receiver that ends up creating a yield with an attacker-predictable id.

### Impact Explanation
A legitimate business flow relying on `promise_yield_create_with_id` (e.g., an escrow/order/auction protocol that yields on a deterministic or caller-supplied ID to correlate an off-chain resume) can be denied service: the expected yield receipt is never created, its callback never executes, and the transaction that intended to create it returns success with a sentinel value that many contracts may not check. Depending on what the yielded flow guards (e.g., release of funds, unlocking of state), this can result in funds becoming stuck/unresolvable until the yield times out, or a permanent inability to complete the intended cross-contract workflow for that ID — a transaction-triggered denial of a legitimate protocol action, without any privileged access required by the attacker.

### Likelihood Explanation
Likelihood is Medium: the exploit requires a specific application design (deriving/exposing `yield_id` from caller-controlled or predictable input), which is a reasonably common pattern encouraged by the API's own purpose (allowing a "user-provided 32-byte yield identifier" for external correlation, per `dependencies.rs:246-260`). Any contract built on `promise_yield_create_with_id` that does not additionally namespace the ID by predecessor/account is vulnerable, and the griefing action itself requires nothing more than a single unprivileged function call from any account.

### Recommendation
Namespace the yield-ID duplicate-detection mapping (and the underlying trie key) by `(receiver_id, predecessor_id, user_yield_id)` rather than `(receiver_id, user_yield_id)` alone, or document and enforce that `yield_id` must be derived by the receiving contract from non-caller-controlled entropy. At minimum, surface the "duplicate id" condition as an explicit host error (rather than a silent sentinel `u64::MAX` promise index) so calling contracts are forced to handle the collision instead of the transaction silently "succeeding" while dropping the intended receipt.

### Proof of Concept
1. Contract `C` implements a flow where, on some public method, it calls `promise_yield_create_with_id` using a `yield_id` derived from caller input (e.g., an order/escrow identifier passed in the function-call arguments) — a pattern explicitly supported by the API (see `promise_yield_create_with_id` and the "user-provided 32-byte yield identifier" semantics in `runtime/near-vm-runner/src/logic/dependencies.rs:246-260`).
2. Attacker account `A`, with no special privileges, predicts or learns the `order_id` that victim `B` is about to use and calls `C`'s method first with that same `yield_id`, successfully creating a `PromiseYield` receipt and writing the `(C, order_id) -> data_id` mapping (`set_yield_id_mapping`, `runtime/runtime/src/ext.rs:390`).
3. Victim `B` calls `C`'s method with the same `order_id`. `has_yield_id_mapping` returns `true` (`runtime/runtime/src/ext.rs:381`), so `create_promise_yield_receipt_with_id` returns `None`, and `promise_yield_create_with_id` in `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:4262-4268` returns the sentinel `u64::MAX` instead of creating `B`'s intended receipt — confirmed by the existing test `create_with_id_duplicate_in_same_call_returns_sentinel` (`integration-tests/src/tests/runtime/test_yield_resume.rs:361-386`), which asserts the transaction still reports `SuccessValue` even though no new yield was created for the duplicate id.
4. `B`'s intended off-chain-correlated callback never executes for `order_id`, and the transaction gives no error signal unless `C`'s code explicitly checks for the sentinel — resulting in denial of the intended workflow for that ID. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }
