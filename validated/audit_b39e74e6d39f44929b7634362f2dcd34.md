Based on my investigation, I found a self-documented integrity gap in the transaction-output verification routine used by Aptos' backup/replay-verify tooling. I was not able to fully confirm every downstream consequence (see caveats below), but the core defect — an incomplete state-authentication check where a documented `TODO` in the code itself proves the invariant is broken — is verifiable directly in the codebase.

### Title
`ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting corrupted state roots pass replay-verify - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to verify that a freshly re-executed transaction's result matches an externally supplied `TransactionInfo` (e.g., one loaded from a backup manifest during `replay-verify`/backup restore). It checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash, but — by its own inline comment — deliberately skips comparing the checkpoint hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) that authenticate the actual resulting ledger state tree.

### Finding Description
`ensure_match_transaction_info` performs four `ensure!` checks — status, gas_used, write-set hash, event root hash — and then stops, with the comment explicitly acknowledging the gap: [1](#0-0) 

This function is the sole cross-check used by `ChunkExecutorInner::verify_execution`, which is the mechanism the `replay-verify` tool (`db-tool/src/replay_verify.rs` → `ReplayVerifyCoordinator`) relies on to detect whether a backup's claimed transaction results match a deterministic, from-scratch VM re-execution: [2](#0-1) 

Because `state_checkpoint_hash` — the Jellyfish Merkle root that all state proofs, `get_state_proof`, and account/resource authenticated reads are ultimately anchored to — is never independently recomputed and compared against the backup-provided `TransactionInfo` in this path, a backup or replay-provided `TransactionInfo` with a correct write-set/event/gas footprint but a corrupted or stale `state_checkpoint_hash` (and therefore a wrong accumulator leaf/root once committed) would pass `verify_execution` undetected.

### Impact Explanation
The `TransactionInfo` supplied to `verify_execution` is the same object used to build the transaction accumulator during restore (`DoLedgerUpdate::run` hashes and appends `TransactionInfo`s to the accumulator; see `transaction_info_hashes`/`transaction_accumulator` construction at [3](#0-2) ). If its `state_checkpoint_hash` is wrong, the accumulator root and any transaction/state proofs served from a node restored this way would be internally self-consistent but bound to the wrong state — exactly the "wrong accumulator root / state proof accepted as valid" class of impact called out by the state-integrity gate. Operators who run `replay-verify` specifically to confirm the integrity of an archive/backup before trusting it for disaster recovery or state-sync bootstrapping would get a false "success", because this is the one place designed to catch such a divergence.

### Likelihood Explanation
I could not fully confirm within available tool budget whether `DoStateCheckpoint`'s "known checkpoint hashes" comparison (fed from the same `TransactionInfo`s during `update_ledger`) performs an independent hard-`ensure!` against its own freshly computed checkpoint hash, which would determine whether this gap is confined to the audit tool's false-positive report or could also let wrong data land in a restored DB outside of `verify_execution`'s scope. I was unable to locate the body of `DoStateCheckpoint::get_state_checkpoint_hashes`/its known-hash equality check in the time available, so this specific path remains unverified. The gap in `ensure_match_transaction_info` itself, however, is directly confirmed in code and is reachable any time `replay-verify` (`VerifyExecutionMode::Verify`) is used, which is a normal, unprivileged operational tool (not requiring special access), making the audit-tool-level likelihood high; the acknowledged, currently-scoped TODO wording ("before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS") suggests the authors consider the position-checkpoint slice of this low-impact today, but the comment does not scope out the base `state_checkpoint_hash`/`hot_state_checkpoint_hash` omission, which applies unconditionally.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/known) against values recomputed from the locally re-executed state, rather than only checking status/gas/write-set/event hashes. This closes the gap noted in the existing TODO and ensures `replay-verify` genuinely authenticates the full committed state, not just the per-transaction write/event footprint.

### Proof of Concept
1. Construct (or corrupt) a transaction backup manifest whose per-transaction write set, events, gas_used, and status are all correct, but whose `TransactionInfo::state_checkpoint_hash` (and/or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) is replaced with an arbitrary/incorrect hash.
2. Run `db-tool replay-verify` (`VerifyExecutionMode::verify_all`/`verify_except`) against this manifest.
3. Observe that `ChunkExecutorInner::verify_execution` → `TransactionOutput::ensure_match_transaction_info` returns `Ok(())` for every transaction because it never compares the checkpoint hash fields, at [4](#0-3)  and [5](#0-4) , despite the backup's declared state root being wrong.

**Caveat:** Full confirmation that this leads to persisted (not just audit-reported) state corruption would require tracing `DoStateCheckpoint`'s known-checkpoint comparison logic, which I could not locate/verify in the time available; I'm reporting the confirmed, self-acknowledged gap in the verification comparator itself rather than asserting the downstream commit-path consequence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
