### Title
`ensure_match_transaction_info` does not validate state/hot-state/position checkpoint hashes during replay-verify - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-consistency check used by replay/backup verification tools (e.g. `replay_on_archive`, `aptos-debugger`, `aptos-move/cli`) to confirm that a re-executed `TransactionOutput` matches the committed `TransactionInfo` stored in the ledger accumulator. The function checks status, gas, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, per the author's own TODO comment.

### Finding Description [1](#0-0) 

The function walks through several `ensure!` checks binding the re-executed `TransactionOutput` to the on-chain `TransactionInfo`: status [2](#0-1) , gas used [3](#0-2) , write-set hash vs `state_change_hash` [4](#0-3) , and event root hash [5](#0-4) . It never recomputes or compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields that exist on `TransactionInfoV0`/`TransactionInfoV1` [6](#0-5) . The author's own comment documents this exact gap: [7](#0-6) 

This means the function's implicit "state-commitment matches VM output" invariant only covers write-set and event data, not the Sparse-Merkle/Jellyfish-Merkle state root or the newer position-state root that is meant to be authenticated per-transaction. Callers of this function — `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — rely on it as their sole per-transaction correctness oracle during replay/backup verification.

### Impact Explanation
If a state root (the field that actually commits the account/resource state, i.e. `state_checkpoint_hash`, or the new `position_state_checkpoint_hash` guarded by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature referenced in `types/src/on_chain_config/aptos_features.rs` and `storage/aptosdb/src/db/aptosdb_writer.rs`/`aptosdb_reader.rs`) diverges between local re-execution and what was persisted/broadcast (due to a storage bug, non-determinism, or corruption on the archive/backup side), `ensure_match_transaction_info` will still return `Ok(())` because it only checks write-set/event hashes, not the checkpoint roots. This directly violates the "committed state that differs from correct VM result" and "hard-fork-only divergence during commit/replay" criteria in the state-integrity gate: replay-verify tooling used to certify archives/backups and detect consensus divergence would silently pass even when the authenticated state or position root is wrong, undermining the primary safety net for these subsystems.

### Likelihood Explanation
This is a real, currently-shipped code path (not hidden behind `experimental` or excluded AIP flags) exercised by production tooling (`replay_on_archive`, `aptos-debugger`, `cli`) any time someone verifies a backup or replays history. The gap is self-acknowledged by the code owners via the TODO, indicating it is a known-but-unfixed limitation gating the rollout of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. However, note this is a detection/verification gap, not a scenario that lets an unprivileged attacker directly corrupt consensus-committed state on mainnet — its severity is contingent on a separate root cause (a storage/executor bug) actually producing a wrong checkpoint hash somewhere, which this check would then fail to catch. I was not able to fully confirm within the available context whether `state_checkpoint_hash` is validated elsewhere in the executor/chunk_executor pipeline for the mainline (non-position) state root — this needs to be verified in `execution/executor/src/chunk_executor/mod.rs` and `execution/executor/src/workflow/do_state_checkpoint.rs`, which I could not fully inspect before this session ended.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the state checkpoint hash (and hot-state/position checkpoint hash when the corresponding feature is enabled) from the locally re-executed state and assert equality against `txn_info.state_checkpoint_hash()` / `txn_info.hot_state_checkpoint_hash()` / `txn_info.position_state_checkpoint_hash()`, mirroring the pattern already used for `state_change_hash` and `event_root_hash`, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production.

### Proof of Concept
Not independently exploitable by an unprivileged actor without a separate root cause producing a divergent checkpoint hash; the concrete "PoC" is the code path itself:
1. Re-execute a transaction whose resulting state root differs from the persisted `TransactionInfo.state_checkpoint_hash` (e.g., due to a storage/executor discrepancy).
2. Call `ensure_match_transaction_info` as done in `storage/db-tool/src/replay_on_archive.rs` / `aptos-move/aptos-debugger/src/aptos_debugger.rs`.
3. Observe `Ok(())` is returned despite the state-root mismatch, because the checks at [8](#0-7)  never touch `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
