### Title
Chunk-replay verification (`ensure_match_transaction_info`) skips state/hot-state/position checkpoint hash comparison, allowing a corrupted or malicious backup's state root to pass `replay-verify` - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info`, used by the chunk executor's `verify_execution` path (invoked from backup replay-verify tooling and the debugger/CLI), checks status, gas, write-set hash, and event-root hash against the expected `TransactionInfo`, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is called out by name in a `TODO(trading-native)` comment in the code itself.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  verifies transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against a supplied `TransactionInfo`, but the trailing comment explicitly documents that it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [2](#0-1) .

This function is invoked by `ChunkExecutor::verify_execution`, the routine used to re-execute a batch of backed-up transactions and compare the freshly computed `TransactionOutput`s against the `TransactionInfo`s taken from the backup/replay manifest [3](#0-2) . This is the exact code path exercised by `storage/db-tool/src/replay_verify.rs` and `ReplayVerifyCoordinator`, whose entire purpose is to authenticate that a backup's committed data (including its Merkle state root) is consistent with independent re-execution [4](#0-3) .

Separately, `DoStateCheckpoint::get_state_checkpoint_hashes` *does* correctly cross-check a recomputed state root against a `known_state_checkpoints` value when one is supplied [5](#0-4) , but `ensure_match_transaction_info` (the actual comparator used for the "does re-execution match transaction info" check in `verify_execution`) never inspects the checkpoint-hash fields of `TransactionInfo` at all, so any divergence there is silently accepted regardless of whether `known_state_checkpoints` machinery elsewhere catches it.

### Impact Explanation
If a backup archive (or an untrusted/attacker-influenced source of transactions+outputs+`TransactionInfo`) contains a `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` that does not match the actual Jellyfish Merkle root produced by re-executing the corresponding transactions, `replay-verify` will still report success, because none of these fields are compared in `ensure_match_transaction_info`. This defeats the core state-commitment integrity guarantee that `replay-verify` is meant to provide: that the ledger's authenticated state root at every version is reproducible from independent execution. A wrong accumulator/state root could therefore be accepted as "verified" by operators or auditors relying on this tool, masking hard-fork-class divergence or corrupted archived data.

### Likelihood Explanation
This is a code-level gap only exercised through `verify_execution_mode.verify_all()` / `db-tool replay-verify` and CLI/debugger flows [6](#0-5) [7](#0-6) , so it does not directly corrupt a live validator's committed ledger state in real time — normal consensus/state-sync commit paths (`StateSyncChunkVerifier::verify_chunk_result`) separately validate the transaction-info accumulator against a trusted signed `LedgerInfo` [8](#0-7) . However, for anyone relying on `replay-verify`/backup-restore tooling as an integrity check of archived data (a documented, security-relevant workflow), the gap is unconditionally present and requires no special privilege to trigger — merely feeding it a backup/manifest with a tampered checkpoint hash. This is explicitly acknowledged as unresolved in the source comment, indicating the maintainers are aware but have not yet closed it.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` (or the call site in `ChunkExecutor::verify_execution`) to also recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values in the target `TransactionInfo`, consistent with what `DoStateCheckpoint::get_state_checkpoint_hashes` already does for the `known_state_checkpoints` path, before enabling/relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any workflow that treats `replay-verify` success as proof of authenticated state-root correctness.

### Proof of Concept
Conceptual, based on static code reading (not executed):
1. Construct a backup manifest / transaction chunk where the `TransactionInfo.state_checkpoint_hash` field is deliberately wrong for a state-checkpoint transaction, while `state_change_hash` (write-set), `event_root_hash`, `gas_used`, and `status` are left correct.
2. Run `db-tool replay-verify` (or `TransactionRestoreController` with `VerifyExecutionMode::verify_all()`), which calls `ChunkExecutor::verify_execution` → `TransactionOutput::ensure_match_transaction_info` for each transaction [9](#0-8) .
3. Because `ensure_match_transaction_info` never compares `state_checkpoint_hash` [10](#0-9) , the check passes despite the actual computed state root (from `DoStateCheckpoint`) diverging from what is claimed in the manifest, unless a separate `known_state_checkpoints` comparison happens to also be wired in for that exact code path (unverified from available context whether `verify_execution`'s `by_transaction_execution` call supplies `known_state_checkpoints`/`known_hot_state_checkpoints` derived from the untrusted `transaction_infos` being verified — this could not be fully confirmed within available search results, so this final wiring detail should be double-checked by a maintainer).

Note: I was unable to fully trace whether `by_transaction_execution` inside `verify_execution` passes `known_state_checkpoints` sourced from the (untrusted) `transaction_infos` argument into `DoStateCheckpoint`, which would determine whether the `DoStateCheckpoint` "known hash" cross-check independently catches this case. This should be verified directly in a full checkout of `execution/executor/src/chunk_executor/mod.rs` and `do_get_execution_output.rs::by_transaction_execution`, since the index's truncated view of `chunk_executor/mod.rs` did not expose the full builder call chain for `verify_execution`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())

    fn verify_execution(
        &self,
        transactions: &[Transaction],
        persisted_aux_info: &[PersistedAuxiliaryInfo],
        transaction_infos: &[TransactionInfo],
        write_sets: &[WriteSet],
        event_vecs: &[Vec<ContractEvent>],
        begin_version: Version,
        end_version: Version,
        verify_execution_mode: &VerifyExecutionMode,
    ) -> Result<Version> {
        // Execute transactions.
        let parent_state = self.commit_queue.lock().latest_state().clone();
        let state_view = self.state_view(parent_state.latest())?;
        let txns = transactions
            .iter()
            .take((end_version - begin_version) as usize)
            .cloned()
            .map(|t| t.into())
            .collect::<Vec<SignatureVerifiedTransaction>>();

        let auxiliary_info = persisted_aux_info
            .iter()
            .take((end_version - begin_version) as usize)
            .map(|persisted_aux_info| AuxiliaryInfo::new(*persisted_aux_info, None))
            .collect::<Vec<_>>();
        let onchain_config = chunk_onchain_config(&state_view)?;
        let execution_output = DoGetExecutionOutput::by_transaction_execution::<V>(
            &V::new(),
            txns.into(),
            auxiliary_info,
            &parent_state,
            state_view,
            onchain_config,
            TransactionSliceMetadata::chunk(begin_version, end_version),
        )?;
        // not `zip_eq`, deliberately
        for (version, txn_out, txn_info, write_set, events) in multizip((
            begin_version..end_version,
            &execution_output.to_commit.transaction_outputs,
            transaction_infos.iter(),
            write_sets.iter(),
            event_vecs.iter(),
        )) {
            if let Err(err) = txn_out.ensure_match_transaction_info(
                version,
                txn_info,
                Some(write_set),
                Some(events),
            ) {
                return if verify_execution_mode.is_lazy_quit() {
                    error!("(Not quitting right away.) {}", err);
                    verify_execution_mode.mark_seen_error();
                    Ok(version + 1)
                } else {
                    Err(err)
                };
            }
        }

impl ChunkResultVerifier for StateSyncChunkVerifier {
    fn verify_chunk_result(
        &self,
        parent_accumulator: &InMemoryTransactionAccumulator,
        ledger_update_output: &LedgerUpdateOutput,
    ) -> Result<()> {
        // In consensus-only mode, we cannot verify the proof against the executed output,
        // because the proof returned by the remote peer is an empty one.
        if cfg!(feature = "consensus-only-perf-test") {
            return Ok(());
        }

        THREAD_MANAGER.get_exe_cpu_pool().install(|| {
            let first_version = parent_accumulator.num_leaves();

            // Verify the chunk extends the parent accumulator.
            let parent_root_hash = parent_accumulator.root_hash();
            let num_overlap = self.txn_infos_with_proof.verify_extends_ledger(
                first_version,
                parent_root_hash,
                Some(first_version),
            )?;
            assert_eq!(num_overlap, 0, "overlapped chunks");

            // Verify transaction infos match
            ledger_update_output
                .ensure_transaction_infos_match(&self.txn_infos_with_proof.transaction_infos)?;

            Ok(())
        })
    }
