### Title
Unbounded recursion in compiled-class bytecode-segment hashing/traversal enables stack-overflow DoS on class declaration and OS re-execution - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
Compiled-class hash computation (`bytecode_hash_node`) and Starknet-OS bytecode-segment structure construction (`create_bytecode_segment_structure_inner`) both recurse over a `NestedIntList`/`bytecode_segment_lengths` tree with **no depth bound**, unlike the analogous cache-building code in blockifier which explicitly asserts `segmentation_depth <= 1`. This mirrors CVE-2016-4421's bug class: a recursive-descent parser/walker with no nesting-depth limit, reachable via attacker-influenced structured input, leading to stack exhaustion and process crash.

### Finding Description
`bytecode_hash_node` walks the `bytecode_segment_lengths` tree that accompanies a compiled (CASM) class and recurses once per nesting level with no depth cap: [1](#0-0) 

This function is invoked directly from `hash_inner`, which is the function used to compute every declared class's compiled-class hash: [2](#0-1) 

`hash_inner`/`hash` is called from the Sierra compiler's `compile` path in `apollo_compile_to_casm`, i.e. on the class-declaration path reachable by any unprivileged declarer: [3](#0-2) 

The equivalent Starknet-OS-side function, `create_bytecode_segment_structure_inner`, used during OS re-execution/proving, has the identical unbounded-recursion pattern: [4](#0-3) 

By contrast, the blockifier's own nested-structure builder for the same kind of tree explicitly bounds recursion to depth 1, indicating the maintainers are aware this structure can be arbitrarily nested and consider deep nesting outside supported bounds for that code path: [5](#0-4) 

The `bytecode_segment_lengths` tree's shape is a function of the compiled Sierra program's control-flow structure (produced by the trusted `cairo-lang-starknet-classes` compiler from an externally-supplied Sierra program). A declarer fully controls the Sierra source, and by crafting deeply nested branch/segment structures (e.g., long chains of nested conditionals or function calls each contributing a minimal segment), the resulting `NestedIntList` can be made deep, bounded only by the max-bytecode-size limit rather than any explicit nesting-depth check: [6](#0-5) 

### Impact Explanation
- On the declare-transaction path, `bytecode_hash_node` runs synchronously as part of computing the `compiled_class_hash` for a new class inside the class-manager/sequencer process. A crafted class that produces sufficiently deep segment nesting can exhaust the call stack and crash the compiling process (class manager / gateway component), a denial of service on legitimate class declaration.
- On the Starknet-OS side, `create_bytecode_segment_structure_inner` runs during block re-execution for proving. A crash here during required OS re-execution could prevent block proving/finalization for a block containing the malicious class, i.e. "a network unable to confirm new transactions" for that path, once such a class is declared and later invoked in a block that must be proven.
- Because this is a plain (non-tail) recursive function without an explicit depth guard (unlike the `RecursionDepthGuard` pattern used elsewhere in blockifier for entry-point call recursion, and unlike the `assert!(segmentation_depth <= 1)` restriction in `NestedFeltCounts`), there is no built-in mitigation analogous to the resource/step/gas limits that protect Cairo-level recursion (`recurse`/`recursive_syscall` tests) or the `stack_size` preallocation used for Cairo Native.

### Likelihood Explanation
Reachable from a single, unprivileged `declare` transaction/class submission — no special privileges, no multi-party coordination, and no reliance on malicious operators/peers. The exact required nesting depth to exhaust a typical thread stack depends on the sequencer's configured stack size and per-frame size of `bytecode_hash_node`/`create_bytecode_segment_structure_inner`, which I could not fully verify from the index (no explicit stack-size configuration was found for the class-manager/compiler threads or for the OS re-execution path, unlike the deliberate `stack_size` handling for Cairo Native execution). This uncertainty means the practical exploitability (how deep must the segment tree be, and whether the compiler itself would realistically emit such deep nesting for a bounded-size program) is not fully confirmed from static analysis alone.

### Recommendation
Add an explicit recursion-depth bound (mirroring the `assert!(segmentation_depth <= 1)` pattern already used in `NestedFeltCounts::new_inner`) to both `bytecode_hash_node` (crates/starknet_api/src/contract_class/compiled_class_hash.rs) and `create_bytecode_segment_structure_inner` (crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs), rejecting/erroring out classes whose segment structure exceeds the supported depth instead of recursing unboundedly. Alternatively, convert these functions to iterative (worklist/stack-based) traversal, as already done for the OriginalSkeletonTree traversal (`fetch_patricia_paths_inner`) and Patricia tree update code in `starknet_committer`, to remove the native-call-stack dependency entirely.

### Proof of Concept
Not independently executable from static analysis alone; conceptually:
1. Craft a Sierra program whose compiled CASM bytecode segmentation (as produced by the Cairo compiler) forms a deeply right-nested `NestedIntList::Node([... NestedIntList::Node([...]) ...])` chain (e.g., via long chains of nested match/if branches each isolated into its own segment).
2. Submit this class via a `declare` transaction.
3. When the sequencer computes `compiled_class_hash` via `SierraCompiler::compile` → `hash()` → `hash_inner` → `bytecode_hash` → `bytecode_hash_node`, the recursive call chain grows with the nesting depth of the segment tree; sufficiently deep nesting exhausts the thread stack and crashes the compiling process.
4. Equivalently, once such a class is included in a block, Starknet-OS re-execution/proving calls `create_bytecode_segment_structure` → `create_bytecode_segment_structure_inner`, which recurses the same way and can crash the prover/re-execution process.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

#[test]
fn test_max_bytecode_size() {
    let contract_class = get_test_contract();
    let expected_casm_bytecode_length = 1965;

    // Positive flow.
    let compiler = SierraToCasmCompiler::new(SierraCompilationConfig {
        max_bytecode_size: expected_casm_bytecode_length,
        max_memory_usage: DEFAULT_MAX_MEMORY_USAGE,
        max_cpu_time: DEFAULT_MAX_CPU_TIME,
        audited_libfuncs_only: false,
    });
    let casm_contract_class = compiler
        .compile(contract_class.clone())
        .expect("Failed to compile contract class. Probably an issue with the max_bytecode_size.");
    assert_eq!(casm_contract_class.bytecode.len(), expected_casm_bytecode_length);

    // Negative flow.
    let compiler = SierraToCasmCompiler::new(SierraCompilationConfig {
        max_bytecode_size: expected_casm_bytecode_length - 1,
        max_memory_usage: DEFAULT_MAX_MEMORY_USAGE,
        max_cpu_time: DEFAULT_MAX_CPU_TIME,
        audited_libfuncs_only: false,
    });
    let result = compiler.compile(contract_class);
    assert_matches!(result, Err(CompilationUtilError::CompilationError(string))
        if string.contains("Code size limit exceeded.")
    );
}
