Based on my analysis, there is a plausible analog to this Next.js Server Actions hanging-request DoS in the sequencer's public transaction-submission HTTP server.

### Title
Public gateway HTTP server has no request/connection timeout, allowing slow-body connections to hang indefinitely - (File: crates/apollo_http_server/src/http_server.rs)

### Summary
The `apollo_http_server` crate exposes the externally-reachable `/gateway/add_rpc_transaction` and `/gateway/add_transaction` endpoints via `axum::serve(listener, app)` [1](#0-0)  with only body-*size* limiting layers (`RequestBodyLimitLayer`, `DefaultBodyLimit`) [2](#0-1) , but no per-request or per-connection *timeout* layer is applied to this server, unlike the internal `RemoteComponentServer` used for inter-component RPC, which explicitly configures HTTP/2 `keep_alive_interval`/`keep_alive_timeout` to evict stalled connections [3](#0-2) .

### Finding Description
This is the same bug class as GHSA-7m27-7ghc-44w9 (Next.js Server Actions DoS): a request whose body never completes (e.g., valid `Content-Length` header but the client trickles bytes extremely slowly, or simply stops sending) is held open by the server for as long as the client is willing to keep the socket alive, because there is no `TimeoutLayer`/idle-timeout configured on `HttpServer::app()` or on the `axum::serve` call. Any unprivileged remote client can open a TCP connection to the gateway's HTTP port and start (but never finish) a POST to `/gateway/add_rpc_transaction`, tying up a server-side task/connection indefinitely at near-zero cost to the attacker, since `RequestBodyLimitLayer`/`DefaultBodyLimit` only bound the number of bytes accepted, not the time taken to receive them.

### Impact Explanation
Because there is no bound on the number of such slow/hanging connections nor a timeout, an attacker can open many parallel connections against the gateway with near-zero bandwidth, exhausting the server's available sockets/tasks and preventing legitimate transaction submissions from being processed — this corresponds to "a network unable to confirm new transactions" if this is the node's externally facing entry point for user-submitted transactions.

### Likelihood Explanation
Trivial to exploit: it requires only opening HTTP connections and slow-writing (or stalling) the request body — no valid transaction, signature, or fee is needed since the stall can occur before the JSON body is parsed by the `Json<RpcTransaction>` extractor [4](#0-3) . No authentication or special privileges are required to reach the gateway HTTP server.

### Recommendation
Add a `tower_http::timeout::TimeoutLayer` (or equivalent hyper/axum connection idle timeout) to `HttpServer::app()`/`run()` in `crates/apollo_http_server/src/http_server.rs`, mirroring the keepalive/timeout protections already present in `RemoteComponentServer` [5](#0-4) , and consider bounding total concurrent connections/in-flight requests on the public gateway server the same way `RemoteComponentServer` limits concurrency via a semaphore [6](#0-5) .

### Proof of Concept
1. Connect to the gateway's HTTP port and send: `POST /gateway/add_rpc_transaction HTTP/1.1\r\nContent-Length: 1000000\r\n\r\n`.
2. Send 1 byte of body, then stop sending further data (or send bytes at a very slow rate, e.g. one byte per few seconds).
3. Observe the connection/task remains open on the server with no timeout closing it, since `axum::serve(listener, app)` is invoked without any `TimeoutLayer` [7](#0-6) .
4. Repeat concurrently to exhaust server resources/connection capacity used for legitimate transaction submission.
