### Title
`MarketCancelOrderActuator` recomputes the cancel fee from the current governance parameter instead of using the value fixed at order-placement time, allowing governance fee changes to lock users out of cancelling stale orders - (File: `actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java`)

### Summary
`MarketCancelOrderActuator.calcFee()` returns `dynamicStore.getMarketCancelFee()` — the *current* value of the governance-controlled `MARKET_CANCEL_FEE` parameter — at the moment a `MarketCancelOrderContract` is validated/executed, rather than any value fixed when the order was originally created via `MarketSellAssetActuator`. This mirrors the reported bug class: a value that should be tied to conditions at creation time is instead recomputed from a mutable governance parameter at a later action, causing reverts or unexpected accounting when that parameter changes in between.

### Finding Description
When a user places a market order, no cancel fee is reserved or stored on the `MarketOrderCapsule`; the fee is only computed later, at cancellation time, straight from the live `DynamicPropertiesStore`: [1](#0-0) 

That fee is charged in both `validate()` and `execute()`: [2](#0-1) [3](#0-2) 

`MARKET_CANCEL_FEE` is a governance parameter that any witness-committee proposal can change at any time via `ProposalService`: [4](#0-3) 
and it is persisted/read through `DynamicPropertiesStore.saveMarketCancelFee`/`getMarketCancelFee`: [5](#0-4) 

This is structurally identical to the reported root cause: a governance-controlled parameter (`MARKET_CANCEL_FEE`, analogous to Superfluid's minimum deposit / liquidation period) is re-read at a later state-transition (`cancelProgram()` / `MarketCancelOrderActuator.execute()`) instead of using a value fixed at the time the resource was created (program funding / order placement). Any user can create an order via `MarketSellAssetActuator`, then, if governance raises `MARKET_CANCEL_FEE` before the user cancels, the cancellation is validated against the new, higher fee.

### Impact Explanation
If the committee raises `MARKET_CANCEL_FEE` after an order was placed, a user whose balance was sufficient at placement time may no longer have enough balance to pay the now-higher cancel fee, causing `validate()` to throw `"No enough balance !"` as demonstrated by the existing test: [6](#0-5) 
This locks the user's sell-side tokens/TRX inside the open order indefinitely (a limited DoS on the affected order/account) until the user tops up their balance, purely as a side effect of an unrelated governance action, with no way for the user to have anticipated or budgeted for it at order-placement time. Conversely, if the fee is lowered, cancellations become cheaper than intended at placement time, an accounting/economic inconsistency versus the assumption baked into the order. This is reachable by any account via a standard broadcast `MarketCancelOrderContract` transaction — no privileged actor or leaked key is required to trigger the condition (only the committee proposal is privileged, which is the expected/normal governance action, not an attack).

### Likelihood Explanation
Requires the witness committee to change `MARKET_CANCEL_FEE` via a normal governance proposal while a user has an outstanding market order — a plausible, non-adversarial sequence of events given `MARKET_CANCEL_FEE` is an explicitly adjustable chain parameter. No malicious collusion or exploit crafting is needed beyond ordinary use of the market feature combined with a parameter change.

### Recommendation
Store the applicable cancel fee (or a fee reserved amount) on `MarketOrderCapsule` at order-creation time in `MarketSellAssetActuator`, and have `MarketCancelOrderActuator.calcFee()`/`execute()` use that stored value instead of re-reading the live `dynamicStore.getMarketCancelFee()` at cancellation time, so the fee charged is deterministic and independent of subsequent governance changes.

### Proof of Concept
1. User calls `MarketSellAssetActuator` to place an order while `MARKET_CANCEL_FEE = 0` (or low).
2. Committee passes a proposal raising `MARKET_CANCEL_FEE` (`ProposalService` `MARKET_CANCEL_FEE` case), which is persisted via `DynamicPropertiesStore.saveMarketCancelFee`.
3. User later submits `MarketCancelOrderContract` to cancel the order; `MarketCancelOrderActuator.validate()` calls `calcFee()` which now returns the new, higher fee.
4. If the user's current balance is less than the new fee, `validate()` throws `"No enough balance !"` (as reproduced in `MarketCancelOrderActuatorTest.noEnoughBalance`), and the order cannot be cancelled until the balance is topped up — despite being fully affordable when the order was originally placed.

  public void saveMarketCancelFee(long fee) {
    this.put(MARKET_CANCEL_FEE,
        new BytesCapsule(ByteArray.fromLong(fee)));
  }

  public long getMarketCancelFee() {
    return Optional.ofNullable(getUnchecked(MARKET_CANCEL_FEE))
        .map(BytesCapsule::getData)
        .map(ByteArray::toLong)
        .orElseThrow(
            () -> new IllegalArgumentException("not found MARKET_CANCEL_FEE"));
  }

  @Test
  public void noEnoughBalance() throws Exception {
    InitAsset();

    //prepare env
    addOrder(TOKEN_ID_ONE, 100L, TOKEN_ID_TWO,
        200L, OWNER_ADDRESS_FIRST);

    ChainBaseManager chainBaseManager = dbManager.getChainBaseManager();
    MarketAccountStore marketAccountStore = chainBaseManager.getMarketAccountStore();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    AccountCapsule accountCapsule = accountStore.get(ByteArray.fromHexString(OWNER_ADDRESS_FIRST));
    accountCapsule.setBalance(0L);
    accountStore.put(ByteArray.fromHexString(OWNER_ADDRESS_FIRST), accountCapsule);

    MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
        .get(ByteArray.fromHexString(OWNER_ADDRESS_FIRST));
    ByteString orderId = accountOrderCapsule.getOrdersList().get(0);

    MarketCancelOrderActuator actuator = new MarketCancelOrderActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, orderId));

    // set fee
    dbManager.getDynamicPropertiesStore().saveMarketCancelFee(1L);

    TransactionResultCapsule ret = new TransactionResultCapsule();

    try {
      actuator.validate();
      actuator.execute(ret);
      Assert.fail("No enough balance !");
    } catch (ContractValidateException e) {
      Assert.assertEquals("No enough balance !", e.getMessage());
    } catch (ContractExeException e) {
      Assert.fail();
    } finally {
      // reset fee
      dbManager.getDynamicPropertiesStore().saveMarketCancelFee(0L);
    }
  }
