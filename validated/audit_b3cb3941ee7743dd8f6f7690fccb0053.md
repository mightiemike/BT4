## Analog Found: First-Cycle Witness Voting Rewards Are Permanently Unclaimable in java-tron's Delegation/Reward System

### Title
Loss of Witness Voting Rewards Accrued in Cycle 0 Due to Missing Vote-Count Checkpoint - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
java-tron's SR (witness) voting reward mechanism (`MortgageService`/`DelegationStore`, and its TVM counterpart `VoteRewardUtil`) computes a voter's reward for a cycle by dividing the total reward accrued by a witness in that cycle by the witness's **vote count recorded for that same cycle**. However, the very first cycle (cycle `0`) never has a vote-count checkpoint written for it, so any block/transaction-fee rewards paid to witnesses during that cycle can never be attributed to any voter and are permanently stuck — the same "rewards distributed for a period before any balance/vote checkpoint exists" bug class as the reported `RewardsDistributor` first-epoch issue.

### Finding Description
Block and transaction-fee rewards paid to a witness are recorded per-cycle via `payReward`, which tags the reward with the *current* cycle number: [1](#0-0) 

When a voter later withdraws/queries rewards, `computeReward` (old algorithm) divides that per-cycle reward pool by the witness's **vote count for that exact cycle**, skipping the cycle entirely if no vote-count checkpoint exists: [2](#0-1) 

The vote-count checkpoint for a cycle is only ever written for the **next** cycle, at the end of `doMaintenance()`, and only once `allowChangeDelegation` is active: [3](#0-2) 

Because `setWitnessVote` is always called with `nextCycle = currentCycle + 1`, cycle `0`'s vote count (`DelegationStore.getWitnessVote(0, srAddress)`) is **never set**. `DelegationStore.getWitnessVote` returns the sentinel `REMARK` (`-1`) when nothing was ever written: [4](#0-3) [5](#0-4) 

Meanwhile, any voter's `beginCycle` defaults to `0` the first time they interact with the reward system (never explicitly initialized): [6](#0-5) 

Consequently, when `computeReward` is later evaluated for a range that includes cycle `0`, it always hits:
```
long totalVote = delegationStore.getWitnessVote(cycle, srAddress); // == REMARK for cycle 0
if (totalVote == DelegationStore.REMARK || totalVote == 0) {
  continue; // reward for cycle 0 is skipped forever
}
```
This is structurally identical to the reported `RewardsDistributor` bug: rewards are physically transferred into the reward pool (`delegationStore.addReward(0, witnessAddress, value)`) for a period, but the balance/vote checkpoint that would let anyone claim a proportional share of that period was never captured, since the checkpoint mechanism only records state going forward from cycle 1 onward. The identical skip logic is duplicated in the TVM-facing `VoteRewardUtil.computeReward`, and the new Vi-based algorithm (`DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`) has the same "vote count for the current cycle" dependency, since `MaintenanceManager.doMaintenance()` calls `accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` using the witness's live vote count without any prior checkpoint validation for cycle 0: [7](#0-6) [8](#0-7) 

### Impact Explanation
Any ALCX-analog reward (block reward, transaction fee reward) that accrues to a witness during cycle `0` — i.e., from the moment `allowChangeDelegation`/the new reward algorithm activates until the first `doMaintenance()` cycle rollover — becomes permanently unclaimable by any voter of that witness. The funds remain recorded in `DelegationStore` (`addReward` key for cycle 0) but no voter's `computeReward` path can ever attribute them, because the vote-count checkpoint for cycle 0 is never created. This is a permanent freezing of protocol-distributed rewards, matching the "Permanent freezing of unclaimed yield" impact class in the original report.

### Likelihood Explanation
This occurs deterministically on every network (or sidechain/private chain) the first time the delegation-based voting reward feature (`allowChangeDelegation`) is activated — it is not a probabilistic or attacker-triggered condition, it is a guaranteed structural gap for cycle 0 on activation. It requires no privileged action beyond the normal chain governance proposal that turns on `ALLOW_CHANGE_DELEGATION`, which is a standard, expected operational event, not an edge case.

### Recommendation
Initialize the cycle-0 vote-count checkpoint (`DelegationStore.setWitnessVote(0, witness, voteCount)`) at the same time `allowChangeDelegation` is activated (or immediately before rewards can begin accruing), so that `computeReward`/`accumulateWitnessVi` has a valid, non-`REMARK` vote count to divide cycle-0 rewards by. Alternatively, defer reward accrual (`payReward`) until after the first vote-count checkpoint has been written, so no reward is ever tagged to a cycle lacking a checkpoint.

### Proof of Concept
Analogous to the reported PoC, this can be reproduced conceptually:
1. Deploy/activate chain with `allowChangeDelegation` proposal freshly enabled at cycle `0` (default `getCurrentCycleNumber() == 0`, `DelegationStore.getWitnessVote(0, sr)` unset → `REMARK`).
2. Have a witness produce blocks / receive transaction fees during cycle 0: `MortgageService.payBlockReward(sr, value)` → `delegationStore.addReward(0, sr, value)`.
3. Let `doMaintenance()` run, rolling `currentCycleNumber` to `1` and setting `delegationStore.setWitnessVote(1, sr, voteCount)` — cycle `0`'s vote count is still never set.
4. A voter who voted for `sr` calls `MortgageService.queryReward`/`withdrawReward`. Trace `computeReward(0, 1, accountCapsule)`: `totalVote = getWitnessVote(0, sr) == REMARK` → `continue` → reward for cycle 0 is `0`, even though `delegationStore.getReward(0, sr) > 0`.
5. This mirrors the reported test `testLostRewardsFirstEpoch`: the reward pool balance (`getReward(0, sr)`) is strictly greater than what any voter can ever claim, and that delta is permanently stuck. [9](#0-8)

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

```java
  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
```
