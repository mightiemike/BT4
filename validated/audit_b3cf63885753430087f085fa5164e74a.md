Replay-Verify Integrity Check Silently Ignores State/Position Checkpoint Root Divergence - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by Aptos's replay-verify tooling to confirm that locally re-executed VM output matches the historically committed `TransactionInfo` for a version. It checks status, gas, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is acknowledged directly in the code's own TODO comment [1](#0-0) .

### Finding Description
`ensure_match_transaction_info` performs four checks — status, gas, write-set hash (`state_change_hash`), and event root hash — and then returns `Ok(())` without comparing any of the checkpoint-hash fields carried in `TransactionInfoV1` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) [2](#0-1) . These checkpoint hashes are the authenticated roots of the Sparse/Jellyfish Merkle state tree and the newly-added "native trading position" state tree, and they are part of the hashed `TransactionInfo` that is anchored to the transaction accumulator root in every `LedgerInfo`.

This comparator is the sole per-transaction correctness check used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, invoked from the chunk-executor's replay path (`remove_and_replay_epoch`) whenever `VerifyExecutionMode::should_verify()` is set [3](#0-2) .
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, used by the standalone `replay-on-archive` tool [4](#0-3) .
- `aptos-move/cli/src/commands.rs`, used by the `aptos move replay` / debugger commands [5](#0-4) .

Critically, `verify_execution` is wired into `ReplayVerifyCoordinator` (`storage/db-tool/src/replay_verify.rs`), which is Aptos's mainnet-history replay-verify infrastructure — the mechanism specifically designed to catch VM/state-computation divergences (including hard-fork-causing bugs) before a new binary is rolled out to validators [6](#0-5) .

By contrast, the *actual* commit path (`execution/executor/src/workflow/do_state_checkpoint.rs::get_state_checkpoint_hashes`) does correctly compare locally-computed checkpoint roots against `known_state_checkpoints`/`known_position_state_checkpoints` derived from trusted `TransactionInfo`s [7](#0-6) , and `execution/executor/src/chunk_executor/mod.rs::update_ledger` feeds these into that check [8](#0-7) . So the gap is isolated to the `ensure_match_transaction_info` comparator itself, not the on-chain commit/consensus path.

### Impact Explanation
This is a genuine, code-acknowledged blind spot in a proof/state-integrity verification tool rather than in the block-commit path itself. If a future VM change produces the correct write set, events, gas, and status for a transaction, but computes a different post-execution state root or a different "trading native position" state root (`position_state_checkpoint_hash`) than what mainnet historically committed, `ensure_match_transaction_info` would report the replay as a full match. Since replay-verify against mainnet history is exactly the safety net meant to catch exactly this class of divergence before a release goes out, a real state-computation bug (e.g., in the newer `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / native position subsystem) could pass CI undetected and later cause a consensus split/hard fork once deployed, because different validators computing different roots would disagree on the true block state. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" category in scope.

I was not able to confirm from the available index whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and the corresponding `position_state_checkpoint_hash`/native-position feature) is already enabled on mainnet or still gated/experimental (the feature and Move module live under `aptos-move/framework/aptos-experimental/...`, suggesting it may not yet be live). This materially affects the current severity: if the feature is not yet enabled on mainnet, the gap is a pre-production hardening issue that must be fixed before the feature is turned on (as the code's own TODO states), rather than an active mainnet risk today.

### Likelihood Explanation
Likelihood is low under normal operation because the ordinary consensus commit and chunk-executor commit paths use the correct `get_state_checkpoint_hashes` check that would catch the same divergence. The exposure is specific to reliance on `ensure_match_transaction_info` as a state-integrity gate in replay-verify tooling; it would only manifest if a VM/state-computation bug that changes checkpoint/position roots (but preserves write-set/event/gas/status equality) is introduced and relied upon to be caught by replay-verify before rollout.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the given `TransactionInfo` and known to the caller) against the values computed by the replayed `TransactionOutput`/execution output, as the existing TODO already recommends, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet.

### Proof of Concept
Not applicable as an exploit against a live network — this is a gap in an internal verification/tooling function, not an externally triggerable state-corruption path. The proof of the gap is structural: `ensure_match_transaction_info`'s own comment documents that a divergence in `position_state_checkpoint_hash` will not cause a replay-verify failure [1](#0-0) , and tracing its only production caller in the replay/verify tooling (`chunk_executor::verify_execution` → `db-tool/replay_verify.rs`) confirms no other check compensates for this omission in that code path.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
