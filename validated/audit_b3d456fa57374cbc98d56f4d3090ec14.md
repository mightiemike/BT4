### Title
A single crafted transaction that panics inside a worker thread permanently disables the shared `WorkerPool`, halting all future block building - ([File: crates/blockifier/src/concurrency/worker_pool.rs])

### Summary
The Y2K report describes a queue whose processing halts forever because one attacker-controlled item can force a revert inside the loop that services the queue. The sequencer has a structural analog: `WorkerPool` is created **once** for the batcher's whole lifetime and is shared across every subsequent block [1](#0-0) . If any transaction causes a worker thread to panic while executing it, the pool is marked as permanently poisoned (`a_thread_panicked`), and this flag is *never reset*. From that point on, every call to `check_panic()` (invoked after each `add_txs_and_wait`/`get_new_results` in every future block, on any height) will itself panic, so the batcher can no longer build or validate any block.

### Finding Description
`ConcurrentTransactionExecutor` calls `self.worker_pool.check_panic()` after every batch of new results [2](#0-1) . `WorkerPool::check_panic` panics if the shared `a_thread_panicked` atomic is `true`:

```
pub fn check_panic(&self) {
    if self.a_thread_panicked.load(Ordering::Acquire) {
        panic!("One of the threads panicked.");
    }
}
``` [3](#0-2) 

The flag is set the first time any worker thread panics while executing a transaction, inside `WorkerThread::_run_executor`, and is **never cleared** afterward:

```
if let Err(err) = res {
    self.a_thread_panicked.store(true, Ordering::Release);
    worker_executor.scheduler.halt();
    abort_guard.release();
    panic::resume_unwind(err);
}
``` [4](#0-3) 

Crucially, this `WorkerPool` is not created per-block; it is created a single time when the batcher starts up and shared via `Arc` for the process's entire lifetime, being passed into `BlockBuilderFactory` and reused for every `ConcurrentTransactionExecutor::start_block` call thereafter:
```
let worker_pool = Arc::new(WorkerPool::start(execute_config));
...
let block_builder_factory = Box::new(BlockBuilderFactory { ..., worker_pool });
``` [5](#0-4) 
```
let executor = ConcurrentTransactionExecutor::start_block(
    state_reader,
    block_context,
    block_metadata.retrospective_block_hash,
    self.worker_pool.clone(),
    None,
)?;
``` [6](#0-5) 

The codebase already contains "panic-on-overflow" arithmetic used inside fee/gas accounting that is exercised during per-transaction execution with values partly influenced by the submitted transaction (tip, resource bounds, VM resource counters, e.g. `GasVector::cost`, `checked_add_panic_on_overflow`, `vm_resource_to_gas_amount`) [7](#0-6) [8](#0-7) . If any code path reachable from a single submitted transaction's execution (validate/execute/fee-charging) hits an unhandled panic (`panic!`, `.unwrap()`, `.expect()`, arithmetic overflow, index-out-of-bounds, etc.) instead of returning a `TransactionExecutionError`, the worker thread panics, `a_thread_panicked` is permanently set, and every future block-building attempt on that node is doomed to panic in `check_panic()`.

This mirrors the Y2K bug class precisely: a single, adversarial, unprivileged transaction turns a per-item error into a **permanent, sticky failure state for the entire processing pipeline**, except here the blast radius is larger — the "queue" being blocked is the sequencer's whole block-production capability rather than one deposit queue, since the pool is never re-created or its panic flag reset between blocks.

### Impact Explanation
If reachable, this is a network-availability bug: a single unprivileged transaction can push a proposer/validator node's batcher into a state where `WorkerPool::check_panic()` panics on every subsequent block-building attempt for the remainder of the process's lifetime, since the poisoned flag is shared and never cleared. This matches "a network unable to confirm new transactions" (if it propagates broadly across sequencer nodes) or at minimum causes repeated node crashes/restarts requiring operator intervention — a permanent denial-of-service analog to the funds-lock bug in the reference report, but affecting the entire block-building pipeline instead of one queue.

### Likelihood Explanation
The likelihood hinges entirely on whether there exists a genuinely reachable, transaction-controlled panic path inside transaction execution (validate/execute/fee-charging) that is not already converted into a `Result`/`TransactionExecutionError`. The code style guidelines explicitly mandate "never panic on data reachable from requests" [9](#0-8) , and the `TransactionExecutor::execute` sequential path explicitly wraps execution errors as `Err(...)` rather than panicking [10](#0-9) , and per-tx failures are shown by tests to not halt block building or the executor in the sequential/committer paths [11](#0-10) . I was **not able to confirm** a concrete, currently-exploitable panic reachable purely from adversarial transaction fields (e.g., tip/resource-bounds overflow) that bypasses upstream gateway/mempool validation (`apollo_gateway`'s stateless/stateful validators appear to bound these fields) — this would require deeper tracing of every numeric conversion touched during execution of a crafted transaction, which the available index did not fully cover. The structural weakness (poisoned pool never resets, shared across the process lifetime) is confirmed and real; whether a concrete panic-trigger currently exists in a reachable path is unconfirmed.

### Recommendation
- Treat any panic inside a worker thread as scoped to the current block/chunk only: recreate a fresh `WorkerPool` (or reset `a_thread_panicked` and restart worker threads) automatically after a panic is detected, instead of leaving the shared flag permanently poisoned.
- Audit all arithmetic/overflow `panic!`/`unwrap()`/`expect()` calls reachable from per-transaction execution (fee/gas accounting, resource-bounds conversions, bouncer weight computation) and convert them to `Result`-returning checked operations so a malformed/adversarial transaction can only fail that single transaction, consistent with the project's own "never panic on data reachable from requests" guideline.
- Add a supervised-restart mechanism for the worker pool so that a single panicking transaction cannot permanently disable block production for the node's remaining lifetime.

### Proof of Concept
Not executable from the available index — a full PoC requires identifying a concrete transaction-controlled input that reaches an un-guarded panic during validate/execute/fee-charging (e.g., a resource-bounds/tip value that reaches `GasVector::cost`'s `checked_mul`/`checked_add` overflow panics without being rejected upstream by the gateway's static validator). Conceptually:
1. Submit a transaction with resource bounds/tip crafted to overflow a `checked_add`/`checked_mul` panic path during execution's fee computation (if such a path is reachable past gateway validation).
2. The worker thread executing this transaction panics; `WorkerThread::_run_executor` sets `a_thread_panicked = true` permanently on the shared `WorkerPool`.
3. Any subsequent block (any height) calls `ConcurrentTransactionExecutor::get_new_results`/`add_txs_and_wait`, which call `worker_pool.check_panic()`, which now always panics — the batcher can no longer build/validate blocks until manually restarted.

/// Converts 'amount' of resource units into Sierra gas, given a per-unit rate.
fn vm_resource_to_gas_amount(amount: usize, gas_per_unit: u64, name: &str) -> GasAmount {
    let amount_u64 = u64_from_usize(amount);
    let gas = amount_u64.checked_mul(gas_per_unit).unwrap_or_else(|| {
        panic!(
            "Multiplication overflow converting {name} to gas. units: {amount_u64}, gas per unit: \
             {gas_per_unit}."

    });

    GasAmount(gas)
}
