### Title
RESCUE_FUNDS outbound bypasses the outbound-enablement check performed on all normal outbounds - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
Normal outbound creation (`BuildOutboundsFromReceipt`) enforces `k.uregistryKeeper.IsChainOutboundEnabled(ctx, event.ChainId)` before ever emitting a PENDING outbound. `AttachRescueOutboundFromReceipt`, which is the only other producer of `PENDING` `OutboundTx` entries in the module, has no such check and unconditionally attaches a `RESCUE_FUNDS` outbound for whatever `originalUtx.InboundTx.SourceChain` is recorded.

### Finding Description
`BuildOutboundsFromReceipt` at [1](#0-0)  explicitly checks `IsChainOutboundEnabled` and refuses to build an outbound (returning an error) if outbound is disabled for the destination chain.

`AttachRescueOutboundFromReceipt`, however, builds and attaches a `PENDING` `RESCUE_FUNDS` outbound purely from ballot/UTX-state checks (deposit-failed for CEA, or reverted inbound-revert for non-CEA) and duplicate-rescue guards, at [2](#0-1) , with no call to `IsChainOutboundEnabled` anywhere in the function. The resulting outbound is attached via the same `attachOutboundsToUtx` helper used by the normal path ( [3](#0-2) ), which writes it into `PendingOutbounds` and triggers the normal TSS-signing/broadcast lifecycle regardless of whether the destination chain has outbound disabled.

This mirrors the report's bug class exactly: a safety/eligibility check (`checkWithdrawLimits` analog here is `IsChainOutboundEnabled`) that was correctly wired into one fund-movement entry point but omitted from a second, newer entry point that reaches the same fund-releasing state (`PendingOutbounds` → TSS signing → broadcast to the source chain).

### Impact Explanation
`IsChainOutboundEnabled` exists to let honest node operators/registry configuration halt fund egress to a given chain (e.g., during an incident, a compromised bridge contract, or chain-specific maintenance). Because the rescue path skips this check, an attacker (or ordinary user) who triggers the `RescueFundsOnSourceChain` event on a chain that has been deliberately disabled for outbound can still cause a legitimate `PENDING` outbound to be created, signed by TSS, and broadcast — releasing funds on a chain the registry explicitly marked as unsafe/disabled for outbound. This is an unauthorized-release/bypassed-control impact on protocol-controlled funds, since the disable flag is the only mechanism to stop such releases once outbound is administratively turned off.

### Likelihood Explanation
Reachability requires only that (a) a user has a UTX eligible for rescue (CEA deposit failed, or non-CEA inbound-revert reverted — both are ordinary unprivileged outcomes reachable from routine inbound execution failures) and (b) the destination chain's outbound flag is disabled in the registry at the time of rescue. Given that `IsChainOutboundEnabled` is meant to be an emergency/administrative control, the most dangerous window is exactly when it's flipped off — and the rescue path ignores it. No privileged actor is required to trigger the rescue call itself; it is driven by the `RescueFundsOnSourceChain` event, which is user-reachable via `RescueFundsOnSourceChain` invocation on the source-chain gateway contract.

### Recommendation
Add the same `IsChainOutboundEnabled` check to `AttachRescueOutboundFromReceipt` before constructing/attaching the `RESCUE_FUNDS` outbound, mirroring the check already present in `BuildOutboundsFromReceipt`:
```go
outboundEnabled, err := k.uregistryKeeper.IsChainOutboundEnabled(ctx, originalUtx.InboundTx.SourceChain)
if err != nil {
    return fmt.Errorf("rescue: failed to check outbound enabled for chain %s: %w", originalUtx.InboundTx.SourceChain, err)
}
if !outboundEnabled {
    return fmt.Errorf("rescue: outbound is disabled for chain %s", originalUtx.InboundTx.SourceChain)
}
```

### Proof of Concept
1. Registry disables outbound for chain `eip155:11155111` via `IsChainOutboundEnabled`-backing config (e.g., an incident response action).
2. A user's earlier CEA inbound had its deposit fail (`originalUtx.PcTx[0].Status == "FAILED"`), making it rescue-eligible per the check at [4](#0-3) .
3. The user calls `rescue_funds`/emits `RescueFundsOnSourceChain` on the gateway; the resulting PC tx receipt is processed by `AttachRescueOutboundFromReceipt`.
4. Despite outbound being disabled for `eip155:11155111`, the function proceeds past all its checks (none of which reference `IsChainOutboundEnabled`) and calls `k.attachOutboundsToUtx`, writing a `PENDING` `RESCUE_FUNDS` outbound into `PendingOutbounds` — which Universal Validators will then sign via TSS and broadcast, releasing funds on the disabled chain.

I could not verify from the index whether there is a downstream, later-stage guard (e.g., in the TSS signing/broadcast pipeline in `universalClient/`) that separately re-checks outbound-enablement before broadcasting a `PENDING` outbound; if such a redundant check exists elsewhere it could mitigate this, but I found no evidence of it in `x/uexecutor` keeper code, and `attachOutboundsToUtx` treats rescue and normal outbounds identically once created.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}
