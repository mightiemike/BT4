### Title
Stale `GlobalContractDistribution` receipt with unmapped `target_shard` after repeated resharding panics `receipt_filter_fn`, halting the chain - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
A `GlobalContractDistribution` receipt that is pushed into the delayed-receipt queue and stays there across two consecutive dynamic-resharding (shard-split) events can end up carrying a `target_shard` id that no longer maps cleanly onto any shard in the current shard layout. When the delayed queue is later drained, `DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()` on that stale receipt. If the id cannot be remapped, this `unwrap()` panics inside chunk application, which aborts the node process for every honest validator applying that chunk — a deterministic, transaction-triggered chain halt. This is directly analogous to the Linux XFRM CVE-2025-21720 bug class: a leftover "already handled" marker on a packet (there, `secpath`; here, a stale `target_shard` embedded in a queued receipt) is not cleaned up/remapped before the packet/receipt re-enters the same processing path, and the code dereferences/unwraps state that is no longer valid for the new context, causing a kernel/node panic.

### Finding Description
`DelayedReceiptQueueWrapper::pop` iterates the persistent delayed-receipt trie queue and, for every popped entry (needed to keep gas/byte accounting correct even for skipped items), calls `receipt_filter_fn` to decide whether the receipt belongs to the current shard: [1](#0-0) 

`receipt_filter_fn` unconditionally unwraps both the current shard layout lookup and `receiver_shard_id(&shard_layout)`: [2](#0-1) 

The comment directly above acknowledges that ReshardingV3 can leave delayed receipts in a shard that technically belongs to a sibling shard after a split, but the guarded filtering logic assumes `receiver_shard_id` always succeeds — it only guards against *misdirection*, not against *failure to resolve* a shard id at all. A `GlobalContractDistribution` receipt carries a fixed `target_shard` field set at receipt-creation time (per `protocol-model/spec/cross-shard-congestion.md`, this kind is "routed by `target_shard`"), which is exactly the kind of embedded shard reference that is not automatically remapped when the shard layout changes underneath it — analogous to the XFRM secpath being stamped once and never re-validated for the new packet/forwarding path.

A test committed in this codebase reproduces exactly this scenario end-to-end: a global-contract deployer's `GlobalContractDistribution` receipt is deliberately kept in the delayed queue (by saturating compute on the target shard every block) while two sequential dynamic-resharding splits occur, and the test explicitly documents the expected failure mode: [3](#0-2) 

and the setup / trigger conditions: [4](#0-3) 

The test's own docstring states: "The fix only works with V3 shard layouts (dynamic resharding). With static resharding, the shard layout doesn't maintain a full split history," which indicates this exact stale-receipt-panic class was a real, previously-encountered issue, and its full remediation depends on shard-layout split-history tracking. I was not able to confirm (due to tool-call limits) whether `receiver_shard_id`'s implementation in `core/primitives/src/receipt.rs` has been updated in this specific tree to correctly remap `target_shard` across *arbitrary* numbers of resharding generations, or whether the guard is complete only for the double-split case exercised by this test — that remains unverified and should be checked directly against `receiver_shard_id`'s body and its resharding-history remap logic before treating this as fully fixed.

### Impact Explanation
If the remap logic has any remaining gap (e.g. more than two sequential splits, or a split ordering not covered by the fix), any account can trigger a permanent chain halt by: (1) deploying a global contract to create a `GlobalContractDistribution` receipt targeting its own shard, and (2) saturating that shard's chunk gas so the receipt is pushed to the delayed queue and survives across resharding events triggered by protocol/config changes. Because `receipt_filter_fn` runs during normal chunk apply on every validator, an unhandled unwrap panic there is a synchronized, chain-wide halt — a transaction-triggered denial of liveness for the entire network, not merely a single node crash.

### Likelihood Explanation
Triggering requires dynamic resharding to be enabled and enough attacker-controlled traffic to delay a receipt across two split boundaries, which is a real but non-trivial precondition (dynamic resharding is a protocol feature gated by `ProtocolFeature::DynamicResharding`). The precise likelihood depends on whether the fix referenced in the test's comment fully closes the gap for all resharding depths — this could not be conclusively verified from the available code excerpts.

### Recommendation
- Confirm `receiver_shard_id` (and any resharding-history remap table it relies on) correctly resolves `target_shard` for `GlobalContractDistribution` receipts across an arbitrary number of shard splits, not just two.
- Replace the `.unwrap()` calls in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-877`) with explicit error handling that either drops/redirects genuinely unresolvable stale receipts or returns a `RuntimeError` instead of panicking, so that a remap gap degrades gracefully instead of halting the chain.
- Extend `test_stale_global_contract_distribution_after_double_resharding` (and equivalent tests) to cover 3+ sequential resharding generations to validate the remap logic's generality.

### Proof of Concept
The existing test in this repository is itself the proof of concept for the bug class: [5](#0-4) 
It deploys a global contract (`tx_deploy_global_contract`) from an unprivileged account, saturates its shard's gas via repeated `burn_gas_raw` calls to force the resulting `GlobalContractDistribution` receipt into the delayed queue, drives the network through two forced shard splits, and then asserts the chain head continues to advance past the point where the stale receipt is drained — with the test comment stating that a panic in `receipt_filter_fn()` (due to `receiver_shard_id()` failing to remap the old `target_shard`) is the exact failure this guards against.

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
