**Analysis:**

The `inner_mut()` method defined in `AptosErrorResponse` trait [1](#0-0)  and implemented by the `generate_error_response!` macro [2](#0-1)  returns a mutable reference to the `AptosError` payload contained in whichever enum variant was constructed. However, searching the codebase for actual call sites of `inner_mut()` on any `AptosErrorResponse`-implementing type (e.g. `BasicError`, `BasicErrorWith404`) found no usages at all — the only match for `inner_mut()` in the whole repo is an unrelated method on `TransactionOutput` in `aptos-move/aptos-vm-types/src/tests/test_output.rs`, which has nothing to do with API error responses.

Since no handler, helper, or "error-code-remapping helper" in the API crate actually invokes `AptosErrorResponse::inner_mut()` to mutate the `AptosError` after construction, there is no code path by which an unprivileged client request could cause a later mutation of `error_code` while the already-finalized `ledger_info`-derived headers remain unchanged. All of the constructors generated by the macro (`*_with_code`, `*_with_code_no_info`, `*_with_vm_status`, `*_from_aptos_error`) build the `AptosError` payload and the header values from the same `ledger_info`/error-code inputs atomically in a single expression [3](#0-2) [4](#0-3) , so there is no split between "headers finalized" and "payload later remapped" in the actual response construction flow.

Because the described exploit requires a call site that uses `inner_mut()` to remap `error_code` post-construction, and no such call site exists in production code, the premise of the question does not hold against this codebase. This is a presentation-layer trait capability with no exercised misuse path, not a corruption of committed ledger state, proof material, or authenticated response binding.
