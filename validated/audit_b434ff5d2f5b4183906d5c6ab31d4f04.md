### Title
Replay/state-sync execution verification skips checkpoint (state-root) hash comparison, allowing divergent local ledger state to pass as "verified" - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by the chunk executor to compare a freshly re-executed transaction output against the trusted, accumulator-proven `TransactionInfo` during state-sync chunk execution and backup replay-verify — checks transaction status, gas used, write-set hash, and event-root hash, but explicitly **does not** check the `state_checkpoint_hash` field of `TransactionInfo`. This is called out in-code by a TODO admitting the gap.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  verifies a locally re-executed `TransactionOutput` against a `TransactionInfo` that was already authenticated by an accumulator/ledger-info proof (obtained from a peer during state sync, or from a backup during restore). It checks:
- execution status [2](#0-1) 
- gas used [3](#0-2) 
- write-set hash vs `state_change_hash` [4](#0-3) 
- event root hash [5](#0-4) 

It never compares the locally computed state/JMT root against `txn_info.state_checkpoint_hash()`. The function's own comment acknowledges this:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
``` [6](#0-5) 

This function is the sole per-transaction integrity check used by `ChunkExecutorInner::verify_execution`, which re-executes chunks of transactions via the VM during state-sync/backup replay and compares outputs to the pre-authenticated `TransactionInfo`s: [7](#0-6) . Because the state-checkpoint hash is never checked here, a locally computed state tree that has diverged from the authenticated ledger (due to VM non-determinism, a storage/executor bug, or a corrupted/rolled-back JMT) will not be caught by this verification path, and the divergent transactions will still be committed via `remove_and_apply`.

### Impact Explanation
The `state_checkpoint_hash` inside `TransactionInfo` is the authenticated commitment to the post-execution state root (JMT root and, per the comment, `position_state_checkpoint_hash` for the trading-native "position" state tree). It is covered by the accumulator/ledger-info signature chain, so it is meant to be the ground truth a syncing/replaying node cross-checks its own computed state root against. Skipping this comparison means a node that (for whatever reason — an executor bug, an un-upgraded feature flag, a differently-configured `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, or corrupted intermediate state) computes a different state root than the network will still pass local `verify_execution` and `db-tool replay-verify` checks, silently persisting a state view that is inconsistent with the authenticated ledger. This is exactly the "committed state that differs from the correct VM result... accepted as valid" scenario in scope, and it undermines the primary safety net (replay/chunk verification) meant to catch state divergence before or during restore.

### Likelihood Explanation
This gap only manifests when local state-root computation genuinely diverges from the network (e.g., due to another bug, a partial feature rollout, or storage corruption); it is not by itself independently triggerable by an unprivileged network attacker feeding malformed data, since `TransactionInfo` itself is already accumulator/signature-authenticated before reaching this comparison. Its real danger is as a **second line of defense that has been silently disabled**: any other bug that causes state-root divergence during replay/restore will go undetected here, rather than being caught immediately as intended. Likelihood of the underlying divergence is not proven here (I could not verify a concrete unprivileged trigger for a state-root divergence within this scan), so likelihood is Low/Medium, but the impact if that divergence exists is High (silent ledger corruption acceptance during restore/replay-verify).

### Recommendation
Restore the checkpoint-hash comparison in `ensure_match_transaction_info`: compute the local state/hot-state checkpoint root (and `position_state_checkpoint_hash` when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or the relevant feature is enabled) and assert it equals `txn_info.state_checkpoint_hash()` (and the position-state hash field), failing verification/replay when they differ, exactly as the existing TODO says needs to happen "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this gap requires an actual state-root divergence to originate elsewhere (e.g., a VM/executor bug or corrupted snapshot) which I could not manufacture or confirm within this code-search-only investigation. The finding is the *missing check* itself — demonstrated directly by the code and its self-documenting TODO at [8](#0-7)  and its call site at [9](#0-8) , rather than a runnable exploit chain triggerable purely by an unprivileged actor. I flag this as uncertain/lower-confidence for meeting the "high or critical impact, independently provable root cause" bar requested, since the trigger condition (an actual divergent state computation) is external to this code path.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
