### Title
Unhandled `Err` from `Receipt::receiver_shard_id()` causes a panic in `receipt_filter_fn`, allowing a stale `GlobalContractDistribution` receipt to halt chunk processing after static (V2) resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`Receipt::receiver_shard_id()` can return `Err(EpochError::ShardingError(..))` when a `GlobalContractDistribution` receipt's `target_shard` can no longer be resolved to a shard in the current layout. The delayed-receipt dequeue path in `DelayedReceiptQueueWrapper::receipt_filter_fn` calls this function and immediately `.unwrap()`s the result, so any input that produces the `Err` branch panics every node applying that chunk — the exact bug class described in CVE-2024-34088 (a function that can return an unhandled "no result" value crashes the daemon).

### Finding Description
`receiver_shard_id` special-cases `GlobalContractDistribution` receipts: if the recorded `target_shard` is not part of the current `shard_layout`, it calls `shard_layout.resolve_to_current_shard(target_shard)` to walk the shard's split history and find the current descendant shard. If that lookup fails, the function deliberately returns an `Err`, not a panic: [1](#0-0) 

The delayed-receipt queue, however, does not treat this as a recoverable error — it unwraps the result on every pop and every peek: [2](#0-1) [3](#0-2) 

`resolve_to_current_shard` relies on shard split-history that is only fully maintained for the newer, V3/"dynamic resharding" shard layout. The repository's own regression test for this exact scenario states that the fix "only works with V3 shard layouts (dynamic resharding)" because "with static resharding, the shard layout doesn't maintain a full split history": [4](#0-3) 

The reachable attack path:
1. Any unprivileged account submits a `DeployGlobalContract` transaction; the runtime creates an outgoing `GlobalContractDistribution` receipt whose `target_shard` is fixed to the sender's shard at deploy time.
2. The attacker (or ordinary network conditions) delays draining of that receipt — the existing test achieves this deterministically by saturating the shard's compute budget every block with cheap `FunctionCall` receipts, forcing the distribution receipt into the delayed queue: [5](#0-4) 

3. A shard split (resharding) happens under a **static/V2** shard layout while the receipt is still delayed. Because V2 layouts do not retain full split-history, `resolve_to_current_shard` cannot find a descendant for the stale `target_shard`.
4. When the delayed queue is next drained, `receipt_filter_fn` calls `receiver_shard_id`, gets `Err`, and `.unwrap()`s it — panicking in the runtime's `pop`/`peek_iter` used inside `process_receipts` for every validator applying that chunk, since it is on the deterministic apply path.

### Impact Explanation
Because `receipt_filter_fn` runs identically on every honest node applying the shard (it is invoked from the deterministic delayed-receipt drain/peek logic used by all validators for state-witness generation and chunk application), a triggered panic is not a single-node crash but a synchronized, transaction-triggered halt of all nodes tracking that shard. This matches the "transaction-triggered halt" impact category: an unprivileged account can, purely through a permissionless `DeployGlobalContract` call plus ordinary gas-saturating transactions, cause a shard-wide denial of service once a static resharding event occurs while the receipt is delayed.

### Likelihood Explanation
Triggering requires: (a) a global contract deployment (fully permissionless), (b) the resulting distribution receipt remaining in the delayed queue across a resharding boundary (achievable by an attacker saturating compute, as demonstrated by the existing test harness), and (c) that resharding event using a static/V2 shard layout (the repository test explicitly documents that the fix does not cover this case). Dynamic/V3 resharding networks are protected because `resolve_to_current_shard` retains split history there; static resharding networks or nodes not yet moved to V3 layouts remain exposed. Likelihood is therefore conditioned on chain configuration (whether resharding is static or dynamic) but the trigger itself requires no special privilege.

### Recommendation
- In `receipt_filter_fn` (and any other caller of `receiver_shard_id` on untrusted/delayed receipts), replace `.unwrap()` with proper error propagation (`Result`) so an unresolved shard produces a recoverable `RuntimeError`/`StorageError` instead of a panic.
- Extend split-history retention (or an equivalent fallback resolution mechanism) to static (V2) shard layouts, or reject/redirect `GlobalContractDistribution` receipts whose `target_shard` cannot be resolved, rather than leaving `resolve_to_current_shard` unable to recover in that mode.
- Add a regression test mirroring `test_stale_global_contract_distribution_after_double_resharding` but exercising a **static** resharding boundary (single split) to confirm the panic no longer occurs.

### Proof of Concept
Reuse the harness already present in the repository as a starting point (it demonstrates delayed-queue saturation and shard-split timing) but configure it for **static** resharding (`ShardLayoutConfig` without `Dynamic`, i.e. the `derive_new_epoch_config_from_boundary` path used elsewhere in the test suite) instead of the V3/dynamic path that is guarded against: [6](#0-5) 
1. Deploy a global contract from `deploy_user`, generating a `GlobalContractDistribution` receipt targeting `deploy_user`'s shard.
2. Saturate that shard's compute budget every block (as in the existing test) so the receipt sits in the delayed queue.
3. Trigger a static shard split of `deploy_user`'s shard (single resharding event, not dynamic/V3).
4. Stop saturating and let the delayed queue drain; because static layouts lack split-history, `resolve_to_current_shard` fails, `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics, halting all nodes applying that shard.

Note: I was unable to fully inspect `ShardLayout::resolve_to_current_shard`'s implementation in `core/primitives/src/shard_layout/mod.rs` and `v3.rs` within the available tool budget to confirm there is no additional guard specific to V2 layouts; the finding rests primarily on the explicit comment/test evidence in the repository itself stating the fix is V3-only. A Devin session with full file access should verify the V2 code path directly before treating this as fully confirmed.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }
