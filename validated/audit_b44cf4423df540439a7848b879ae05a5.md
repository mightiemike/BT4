### Title
Unbounded queuing on shared `sectionExecutor` fixed thread pool allows RPC-API DoS via concurrent `eth_getLogs`/`eth_getFilterLogs` requests - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Summary
`LogBlockQuery.partialMatch` submits one `Future` per unique bloom bit-index for every bloom section in the queried block range to a single shared `ExecutorService` (`sectionExecutor`), fixed at 5 threads with Java's default unbounded `LinkedBlockingQueue`. Because there is no semaphore, rate limiter, or per-request/global concurrency cap on how many `eth_getLogs`/`eth_getFilterLogs` requests can be in flight simultaneously, an unprivileged attacker issuing many concurrent wide-range log queries can enqueue a large, unbounded number of tasks on this shared pool, causing queuing delays for all other RPC callers that use the same executor.

### Finding Description
`TronJsonRpcImpl` creates a single shared pool: `this.sectionExecutor = ExecutorServiceManager.newFixedThreadPool(esName, 5)` [1](#0-0) , and this same instance is passed into every `LogBlockQuery` created for `getLogs`/`getFilterLogs` calls [2](#0-1) .

`ExecutorServiceManager.newFixedThreadPool` is a thin wrapper over `Executors.newFixedThreadPool`, which uses an unbounded `LinkedBlockingQueue` internally [3](#0-2) .

Inside `LogBlockQuery.partialMatch`, for every section in `[minSection, maxSection]` and every unique bloom bit index derived from the filter's addresses/topics, a new `Future` is submitted and then blocked on via `.get()`: [4](#0-3) . `subMatch` loops this per section serially [5](#0-4) , and `getPossibleBlock` loops `subMatch` per condition [6](#0-5) .

The only existing mitigation on scope is `LogFilterWrapper.validateBlockRange`, which caps a single request's `toBlock - fromBlock` span against `Args.getInstance().getJsonRpcMaxBlockRange()` [7](#0-6) . This check is only per-request and bounds the number of sections/tasks a *single* query can generate; it does nothing to bound the number of *concurrent* requests a client (or multiple sockets) can fire, nor how many outstanding `Future` objects can be queued against the shared 5-thread pool at once. Because the queue is unbounded, tasks are never rejected — they simply queue, and callers block in `.get()` waiting for a thread to become free, propagating latency to every other RPC handler thread that happens to route through the same `sectionExecutor` (this pool is shared globally across all fullnode/solidity JSON-RPC log queries, not per-request).

I was not able to fully verify the configured default value of `jsonRpcMaxBlockRange` in `Args.java` within this investigation (only located references to it, not the default numeric value), so the exact per-request task ceiling is unconfirmed; however, even with a nonzero cap, concurrency is unbounded by design, since nothing limits how many simultaneous `eth_getLogs` calls can each independently submit up to `(maxBlockRange/BLOOM_BIT_SIZE) * distinct_bitIndexes` futures to the same 5-thread executor.

### Impact Explanation
This is a DoS via RPC-API resource-exhaustion pattern: an unprivileged, unauthenticated JSON-RPC client can fire many concurrent `eth_getLogs` calls, each enqueuing many tasks onto a shared fixed-size (5-thread) executor with an unbounded queue. This causes queuing/backlog that increases latency and can stall other RPC handler threads calling into `sectionExecutor` (including unrelated `eth_getFilterLogs` requests from other clients), degrading availability of the JSON-RPC log-query surface. This matches the "DoS via RPC-API" bounty impact class, scoped to RPC-API stall/backlog rather than node crash or consensus impact.

### Likelihood Explanation
Preconditions are default config and only require network access to the exposed JSON-RPC endpoint — no privileged role, no fees (JSON-RPC reads are free), and no transaction broadcast needed. The attack is trivially repeatable by opening many concurrent HTTP connections and issuing `eth_getLogs` with wide (but individually range-capped) block ranges. The severity is moderated by the existence of `validateBlockRange`, which limits each individual request's task fan-out, so the practical impact is a throughput/latency degradation proportional to attacker concurrency rather than unbounded memory exhaustion — full exploitability to the point of OOM was not conclusively confirmed and would depend on the actual configured `jsonRpcMaxBlockRange` default, which I could not verify in this pass.

### Recommendation
Add an explicit concurrency guard around JSON-RPC log queries independent of the executor's internal queue: e.g., wrap `sectionExecutor` submissions with a bounded queue + `RejectedExecutionHandler` (reject/backpressure) via `ExecutorServiceManager.newThreadPoolExecutor` instead of `newFixedThreadPool`, and/or add a global semaphore limiting the number of concurrent `eth_getLogs`/`eth_getFilterLogs` requests being processed, returning a rate-limit error to excess callers instead of queuing indefinitely.

### Proof of Concept
Not fully reproducible in this pass without access to the running node/config to confirm the default `jsonRpcMaxBlockRange` value and executor queue growth under load; a JUnit load test would need to: instantiate `TronJsonRpcImpl` with default config, launch N (e.g., 100) concurrent threads each calling `getLogs`/`getLogsByLogFilterWrapper` with `fromBlock`/`toBlock` spanning the maximum allowed range, and assert on `sectionExecutor`'s queue size (via reflection on the underlying `ThreadPoolExecutor`) and observed request latency to confirm unbounded growth/stalling — this was not executed as part of this investigation.
