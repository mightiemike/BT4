### Title
Exchange liquidity injection rounds the paired-token contribution down instead of up, letting the injecting party skew the pool ratio in their favor - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` (the TRX "Bancor-style" on-chain Exchange feature) computes how much of the paired token a liquidity injector must also contribute to keep the exchange's price ratio unchanged. This calculation uses floor/truncating integer division instead of rounding up, so the injector systematically contributes slightly less of the second token than the exact proportional amount required — the same rounding-direction defect flagged in the Mellow `ratiosX96Value` finding, where rounding a ratio-derived quantity down shifts value away from the pool and toward the acting party.

### Finding Description
When a user injects liquidity into an Exchange pair, the amount of the "other" token that must be added to preserve the current price ratio is computed as: [1](#0-0) 

```java
if (Arrays.equals(tokenID, firstTokenID)) {
  anotherTokenID = secondTokenID;
  anotherTokenQuant = floorDiv(multiplyExact(
      secondTokenBalance, tokenQuant), firstTokenBalance);
  ...
} else {
  anotherTokenID = firstTokenID;
  anotherTokenQuant = floorDiv(multiplyExact(
      firstTokenBalance, tokenQuant), secondTokenBalance);
  ...
}
```

`floorDiv` truncates toward zero for positive operands, i.e. it always rounds `anotherTokenQuant` **down**. The same rounding direction is repeated in `doValidate()`, which uses plain `BigInteger.divide()` (also truncating) to derive `anotherTokenQuant` for the pre-execution checks: [2](#0-1) 

Because `anotherTokenQuant` is the amount debited from the injector and added to the exchange's paired-token reserve, rounding it down means the injector deposits marginally less of the second token than the exact ratio `secondTokenBalance * tokenQuant / firstTokenBalance` demands. The resulting reserve ratio (`newSecondTokenBalance / newFirstTokenBalance`) after injection is therefore slightly lower than the pre-injection ratio, i.e., the injected liquidity understates the price of the injected token in terms of the paired token. This is structurally identical to the Mellow bug class: a ratio/denominator-derived quantity is rounded toward the actor performing the operation instead of toward the pool, letting value leak out of the shared reserve on every call.

Contrast this with `ExchangeWithdrawActuator`, whose `doValidate()` includes an explicit 0.01% precision check (`"Not precise enough"`) comparing the rounded result against a `RoundingMode.HALF_UP` computation to bound drift for withdrawals — no equivalent safeguard exists for injections in `ExchangeInjectActuator`.

### Impact Explanation
Any account that creates an Exchange pair (`ExchangeCreateActuator`, unprivileged/permissionless) can repeatedly call `ExchangeInjectContract` with amounts chosen so `secondTokenBalance * tokenQuant` is not evenly divisible by `firstTokenBalance`, deliberately maximizing the rounding-down remainder each time. Each call shifts the pool's price ratio infinitesimally in the injector's favor at the exchange's expense. Because the creator (or any account trading against the pool immediately after an injection) can capture this favorable price delta via a subsequent trade (`MarketSellAssetActuator`/`ExchangeTransactionActuator` style flows use the reserve ratio directly), repeated injections let value be systematically extracted from the exchange's reserves — the on-chain analog of vault insolvency described in the source report. This is an accounting/settlement-integrity issue in a public, permissionless market primitive, not a theoretical concern, since the exchange's price and settlement amounts for every future trade derive directly from `firstTokenBalance`/`secondTokenBalance`.

### Likelihood Explanation
High: creating an exchange and calling `ExchangeInjectContract` requires no special privilege — the "creator" check in `doValidate()` only restricts injection to whoever created that specific pair, which any account can do via the permissionless `ExchangeCreateActuator`. An attacker fully controls both the pair and the injected quantities, so triggering the worst-case rounding remainder on every call is trivial and repeatable at low cost (`calcFee()` for inject is `0`).

### Recommendation
Round `anotherTokenQuant` up (ceiling division) in both `execute()` and `doValidate()` of `ExchangeInjectActuator`, mirroring the fix applied upstream for the analogous Mellow issue (`mulDivRoundingUp`). Concretely, replace `floorDiv(...)`/`BigInteger.divide()` with a ceiling-division helper (e.g., `(numerator + denominator - 1) / denominator` guarded for overflow, or `BigInteger` `divideAndRemainder` plus `+1` when remainder is nonzero, as already implemented elsewhere in the codebase, e.g. `divideCeilExact` in `RepositoryImpl`/`ResourceProcessor`), so the injector is required to contribute at least the proportional amount, never less.

### Proof of Concept
1. Attacker calls `ExchangeCreateActuator` to create pair `(A, B)` with `firstTokenBalance = 3`, `secondTokenBalance = 10`.
2. Attacker calls `ExchangeInjectContract` with `tokenID = A`, `tokenQuant = 1`.
3. `anotherTokenQuant = floorDiv(10 * 1, 3) = 3` (exact value is `3.33...`), so the attacker only contributes `3` units of `B` instead of the required `~3.33`.
4. New ratio `secondTokenBalance/firstTokenBalance = 13/4 = 3.25` versus the original `10/3 = 3.33...` — the price of `A` in terms of `B` has dropped purely from rounding, at the reserve's expense.
5. Repeating steps 2–4 with quantities chosen to always leave a nonzero remainder accumulates a rounding "discount" on every injection, which can be harvested by trading against the pool (`MarketSellAssetActuator`) or by later withdrawing (`ExchangeWithdrawActuator`) at the now-skewed ratio.
