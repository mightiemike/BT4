### Title
Function-call access key `allowance` limit is completely bypassed when the key is used to sign a `DelegateAction` (meta transaction) - (File: `runtime/runtime/src/actions.rs`)

### Summary
`propose()` vs `proposeWithModule()` in the referenced report illustrates a pattern where a protocol offers two paths to reach the same authorized outcome, but one path enforces materially weaker constraints than the "normal" one, letting an unprivileged actor achieve something the primary path would never allow. Nearcore has a structurally identical pattern between (a) a direct, self-signed transaction using a `FunctionCall`-restricted access key, and (b) the same key used inside a `DelegateAction` (meta transaction/NEP-366). The `allowance` field of `FunctionCallPermission` is the safety limit an account owner (or an app minting a device/session key) relies on to bound how much of the account's balance a leaked or limited-scope key can ever spend on gas. This limit is enforced on the direct path but is not checked at all on the delegate/meta-transaction path.

### Finding Description
When a `FunctionCall` access key signs a transaction directly, the runtime's key-usage validation is expected to consult and decrement `allowance` so the key can never spend more than the owner budgeted for it. When the very same key is instead used to sign the inner action of a `DelegateAction`/`DelegateV2`, the dedicated validation routine `validate_delegate_action_key` in `runtime/runtime/src/actions.rs` checks access-key existence, nonce/gas-key bookkeeping, "single FunctionCall action" restriction, zero-deposit requirement, `receiver_id` match, and `method_names` match — but it never reads or enforces `function_call_permission.allowance` anywhere in its logic: [1](#0-0) 

This is corroborated by the project's own architecture documentation, which explicitly states the allowance is not checked for meta transactions because "all costs have been covered by the relayer," and that a key intentionally limited to a "very small allowance" is "circumventable by going through a relayer": [2](#0-1) 

The delegate-action spec in `docs/RuntimeSpec/Actions.md` confirms the enumerated validation/execution errors for `DelegateAction` (`AccessKeyNotFound`, `InvalidNonce`, `NonceTooLarge`, signature/receiver checks, etc.) with no allowance-related error listed: [3](#0-2) 

This mirrors the report's bug class exactly: two routes exist to invoke the same authorized capability (calling a specific method on a specific contract with a `FunctionCall`-restricted key), and the "weaker" route (`proposeWithModule()` / delegate action) omits a hard limit (`no`-vote quorum / `allowance`) that the "normal" route (`propose()` / direct signed transaction) enforces.

### Impact Explanation
`allowance` is the mechanism NEAR account owners and wallet/app developers rely on to bound the blast radius of a compromised or intentionally scope-limited `FunctionCall` access key (e.g., a mobile/web session key deliberately capped to a small NEAR budget). Because `validate_delegate_action_key` never checks or decrements `allowance`, an attacker who obtains such a limited key can route calls through any relayer (including one they control themselves) and invoke the permitted method on the permitted contract an unbounded number of times, entirely defeating the owner-configured spending/usage cap — a fee/gas-limit bypass of a security control that the direct-transaction path enforces. This degrades a documented account-security guarantee at the runtime/action-validation layer reachable from any transaction signer, without requiring any privileged, validator-only, or network-layer capability.

### Likelihood Explanation
This is trivially reachable by any unprivileged party who possesses a `FunctionCall`-restricted access key (whether legitimately issued with a deliberately small allowance, or obtained through leakage) and any relayer account (which can be the same attacker-controlled account acting as the meta-transaction signer). No special protocol privileges, validator status, or network manipulation is required — only submitting a normally-formed `DelegateAction`/`DelegateV2` transaction, a path fully exercised in the test suite (`integration-tests/src/tests/features/delegate_action.rs`, `test-loop-tests/src/tests/gas_keys.rs`). The behavior is also explicitly acknowledged in project documentation as an existing, non-hardened gap rather than a hypothetical.

### Recommendation
Ensure the requirements for authorizing an action through a `DelegateAction` are always at least as strict as the direct-transaction path. Specifically, `validate_delegate_action_key` should look up and enforce (and appropriately decrement/persist) `function_call_permission.allowance` the same way the direct-signed-transaction verifier does, rejecting the delegate action (e.g., with a `NotEnoughAllowance`-style error) when the key's remaining allowance cannot cover the inner action's cost — closing the gap between the "normal" and the meta-transaction path.

### Proof of Concept
1. Account `alice` adds a `FunctionCall` access key to herself with `receiver_id = "app.near"`, `method_names = ["do_thing"]`, and a small `allowance` (e.g., 1 yoctoNEAR-equivalent gas budget) — intended so a leaked copy of this key can only trigger `do_thing` a handful of times before running dry.
2. This key leaks to an attacker (or the attacker is a malicious relayer/app operator).
3. Instead of signing `do_thing` calls directly with the key (which would fail once `allowance` is exhausted, per the direct-path enforcement), the attacker wraps each call in a `DelegateAction`/`DelegateV2` with `sender_id = alice`, signs it with the leaked key, and submits it via any relayer account (potentially attacker-owned) as the outer transaction signer.
4. Because `validate_delegate_action_key` (`runtime/runtime/src/actions.rs:574-728`) never inspects `allowance`, every such delegate action passes validation (subject only to nonce, receiver, and method-name checks) regardless of how small `allowance` was set, letting the attacker invoke `do_thing` an unbounded number of times — completely defeating the owner's configured usage cap, as also acknowledged in `docs/architecture/how/meta-tx.md:258-266`.

## Function access keys in meta transactions

Assume alice sends a meta transaction and signs with a function access key.
How exactly are permissions applied in this case?

Function access keys can limit the allowance, the receiving contract, and the
contract methods. The allowance limitation acts slightly strange with meta
transactions.

But first, both the methods and the receiver will be checked as expected. That
is, when the delegate action is unwrapped on Alice's shard, the access key is
loaded from the DB and compared to the function call. If the receiver or method
is not allowed, the function call action fails.

For allowance, however, there is no check. All costs have been covered by the
relayer. Hence, even if the allowance of the key is insufficient to make the call
directly, indirectly through meta transaction it will still work.

This behavior is in the spirit of allowance limiting how much financial
resources the user can use from a given account. But if someone were to limit a
function access key to one trivial action by setting a very small allowance,
that is circumventable by going through a relayer. An interesting twist that
comes with the addition of meta transactions.
