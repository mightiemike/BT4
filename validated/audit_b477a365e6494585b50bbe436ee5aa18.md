## Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` JSON-RPC calls let any caller stop the sequencer's commitment pipeline - (File: `crates/common/src/rpc/auth.rs`)

### Summary
The reported bug is a missing access-control modifier (`onlyOwner`) on a state-mutating function that any caller could invoke. The direct analog in this repository is the sequencer's JSON-RPC `Auth` middleware, which only gates three backup-related methods behind an API key and leaves every other privileged, state-mutating sequencer method — including `citrea_haltCommitments` and `citrea_resumeCommitments` — completely unauthenticated.

### Finding Description
The RPC server middleware stack applies an `Auth` layer that checks a hard-coded allow-list of `PROTECTED_METHODS`: [1](#0-0) 

Only `"backup_create"`, `"backup_validate"`, `"backup_info"` require the `api_key` parameter; every other method, including the sequencer-only endpoints, passes straight through to the handler with no sender/authority check: [2](#0-1) 

The sequencer exposes `citrea_haltCommitments` and `citrea_resumeCommitments` as public JSON-RPC methods with no additional authorization inside the handler itself: [3](#0-2) [4](#0-3) 

Calling `halt_commitments` simply forwards a `HaltCommitments` message through an internal channel, which the commitment service consumes to stop producing/publishing sequencer commitments to the DA layer entirely, until an (equally unauthenticated) `resume_commitments` call is made: [5](#0-4) [6](#0-5) 

The RPC server itself is bound and started with no other authentication layer besides this `Auth` middleware: [7](#0-6) 

This is the structural equivalent of the `extendTime` bug: a function meant to be restricted to a privileged operator (here, whoever operates the sequencer node/infrastructure) is reachable by any party who can reach the RPC port, with no `onlyOwner`-equivalent check.

### Impact Explanation
Any unauthenticated caller with network access to the sequencer's JSON-RPC endpoint can halt the sequencer's `CommitmentService`, preventing sequencer commitments from being written to the Bitcoin DA layer. Since sequencer commitments are the binding that lets the batch prover and light-client prover recognize and prove L2 state advancement, this directly breaks the liveness of the "committed L2 state published on DA" invariant — an unauthenticated JSON-RPC call mutating node state, matching the explicitly listed High-impact class in scope.

### Likelihood Explanation
This requires no privileged role, key, or node compromise — only network reachability to the sequencer's RPC endpoint (which, depending on deployment, is commonly exposed for standard `eth_*`/`citrea_*` RPC usage). The call is a single unauthenticated JSON-RPC request with no parameters.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other operationally sensitive control methods) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or otherwise gate them behind the existing `api_key` mechanism / a dedicated operator-only authentication layer, so they cannot be invoked by arbitrary unauthenticated RPC clients.

### Proof of Concept
Against a running sequencer RPC endpoint, with no API key or any credentials:
```
curl -X POST http://<sequencer-rpc-host>:<port> \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}'
```
This succeeds and halts commitment submission indefinitely, since `Auth::call` (crates/common/src/rpc/auth.rs) only checks membership in `PROTECTED_METHODS`, which does not include `citrea_haltCommitments`.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
