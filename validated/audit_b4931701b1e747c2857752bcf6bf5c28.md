### Title
Starknet OS `replace_class` Syscall Handler Omits Declared-Class and Cairo1-Type Checks Performed by Blockifier - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Blockifier's Rust implementation of the `replace_class` syscall enforces that the target `class_hash` (a) is actually declared and (b) is a Cairo1 class, rejecting the call otherwise [1](#0-0) . The corresponding Cairo implementation used by the Starknet OS for block re-execution/proving performs neither check before mutating `contract_state_changes`, as explicitly flagged by a TODO in the code [2](#0-1) . The same gap exists in the deprecated syscall path [3](#0-2) .

### Finding Description
Any account contract can invoke the `replace_class` syscall with an arbitrary `class_hash`, from either an old-style Cairo0 contract via the deprecated syscall or a Cairo1 contract via the new syscall.

In Blockifier (the execution engine actually used to build/commit blocks), `replace_class` explicitly:
1. Reads the compiled class for `class_hash`, which fails with `StateError::UndeclaredClassHash` if it was never declared,
2. Rejects the call with `ForbiddenClassReplacement` if the target class is not Cairo1,

before it is allowed to call `set_class_hash_at` [1](#0-0) . A transaction attempting to replace to an undeclared or Cairo0 class hash therefore reverts (or its inner call fails) when actually executed/committed by the sequencer.

The Starknet OS Cairo program re-implements syscall handling independently (it is a Cairo VM program that runs the same CASM/Sierra bytecode and processes syscalls in Cairo, guided by hints for raw state data) so that a STARK proof can be produced attesting to the correctness of the block. Its `execute_replace_class` function for the current syscall set unconditionally reads the requested `class_hash` and writes a new `StateEntry` with that class hash into `contract_state_changes`, with only a TODO comment acknowledging the missing declared-class check and no check at all for whether the class is Cairo1: [4](#0-3) 
The deprecated syscall variant has the identical omission [3](#0-2) .

Downstream, the OS's global state commitment logic (`state_update` in `state.cairo`) simply squashes and commits whatever ends up in `contract_state_changes`/`contract_class_changes` without any independent cross-check that referenced class hashes were declared [5](#0-4) . There is no other validation layer in the OS pipeline that closes this gap for `replace_class` specifically.

This is a control-check asymmetry directly analogous to the reported bug class: a state-mutating action (`replace_class`, changing a contract's class hash, i.e. its executable code) is permitted in one code path (the OS) without the access/precondition check that the authoritative path (Blockifier) enforces before allowing that same mutation.

### Impact Explanation
Because Blockifier and the Starknet OS are supposed to compute identical state transitions for the same block (the OS's job is to attest that the sequencer's execution was correct), this inconsistency is a soundness/consistency bug rather than a simple crash:
- If Blockifier reverts a transaction that calls `replace_class` on an undeclared/Cairo0 class hash (as it does), the actual committed block state does not reflect that class change.
- If the OS's syscall handling for the same call sequence is not gated by the identical checks, any input path that causes the OS to treat the syscall as succeeding when Blockifier's rules dictate it should fail creates a divergence between the block state Blockifier actually committed and the state the OS attests to in its proof/output.
- Such divergence falls squarely into the "wrong committed root or block hash, honest-node divergence" impact category: proofs generated by the OS would either fail to match the real chain state (blocking proof/state finalization) or, in a worst case where enforcement of consistency between execution and OS output is weaker elsewhere, allow a state root that does not correspond to a valid, permission-checked class replacement to be committed.
- Since `replace_class` changes a contract account's executable class hash, an unauthorized/invalid class replacement being accepted by the OS could also translate into unauthorized account behavior (a contract effectively bypassing the Cairo1-only, declared-class invariant that the rest of the system relies on for safe upgrades).

### Likelihood Explanation
The `replace_class` syscall is directly reachable by any contract executed on behalf of any transaction sender — no special privileges, staking, or operator/prover control is required to trigger the code path; a normal `Invoke` transaction whose called contract executes `replace_class_syscall(undeclared_or_cairo0_hash)` is sufficient. The check is missing unconditionally (not behind a feature flag), and it is explicitly flagged in the code with a TODO, confirming the omission is a known incompleteness rather than a deliberate, safe design choice. The main uncertainty is whether some other stage of the OS/committer pipeline (outside what was inspected) independently re-validates class declarations before finalizing block output; this was not found in `state.cairo`, `os.cairo`, or the syscall dispatch files reviewed, but full verification of every consumer of `contract_class_changes` was not exhaustively possible with the available indexing.

### Recommendation
Add the same two checks Blockifier performs to both Cairo `execute_replace_class` implementations before updating `contract_state_changes`:
1. Verify `class_hash` exists in the declared classes state (mirroring `state.get_compiled_class(class_hash)?` semantics) and fail/revert consistently with Blockifier's `UndeclaredClassHash` behavior.
2. For the non-deprecated syscall, additionally verify the class is Cairo1, matching Blockifier's `ForbiddenClassReplacement` check.
Ensure the failure behavior (revert vs. hard failure) exactly matches Blockifier's so that OS re-execution and actual sequencer execution can never diverge for this syscall.

### Proof of Concept
1. Deploy a Cairo1 account/contract whose `__execute__` (or any external entry point invoked mid-transaction) calls `replace_class_syscall(class_hash=X)` where `X` is a class hash that has never been declared on-chain (or is a valid but Cairo0/deprecated class hash).
2. Submit an ordinary `Invoke` transaction from any account calling into this contract.
3. Observe that Blockifier rejects/reverts the inner call due to `StateError::UndeclaredClassHash` (or `ForbiddenClassReplacement` for a Cairo0 target) per `crates/blockifier/src/execution/syscalls/syscall_base.rs:369-378`.
4. Feed the identical CASM/Sierra execution trace to the Starknet OS's syscall handling (`execute_replace_class` in `syscall_impls.cairo:881-920` / `deprecated_execute_syscalls.cairo:307-329`) and observe that, absent the missing check, the OS accepts the syscall and updates `contract_state_changes` with the new (invalid) class hash unconditionally, producing a state/commitment inconsistent with what Blockifier actually computed for the same transaction.
