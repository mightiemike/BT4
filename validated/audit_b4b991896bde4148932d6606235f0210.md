### Title
Zero-Allowance AddKey Silently Upgraded to Unlimited-Allowance Key - (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary

When a wallet owner signs an `AddKey` Ethereum transaction with `is_limited_allowance=true` and `allowance=0`, the resulting NEAR function-call access key is created with `Allowance::Unlimited` instead of the intended zero allowance. The silent upgrade happens because `Allowance::limited(NearToken::from_yoctonear(0))` returns `None` (zero is not a valid `NonZeroU128`), and the subsequent `.unwrap_or(Allowance::Unlimited)` promotes it to unlimited. Any party holding the corresponding private key can then make unbounded function calls spending the wallet's NEAR.

### Finding Description

**Step 1 – User input parsed without validation of zero allowance.**

In `internal.rs`, `parse_tx_data` decodes the ABI-encoded `AddKey` calldata directly into `Action::AddKey { is_limited_allowance: true, allowance: 0, .. }` with no check that `allowance > 0` when `is_limited_allowance` is `true`. [1](#0-0) 

**Step 2 – `try_into_near_action` preserves the zero as `Some(0)`.**

In `types.rs`, the branch `if is_limited_allowance { Some(allowance) } else { None }` produces `Some(0u128)`, which is then wrapped as `Some(NearToken::from_yoctonear(0))` in the `FunctionCallPermission`. [2](#0-1) 

**Step 3 – `action_to_promise` silently converts `Some(0)` → `Allowance::Unlimited`.**

```
access.allowance                          // Some(NearToken(0))
  .and_then(Allowance::limited)           // Allowance::limited(0) == None  (NonZeroU128::new(0) == None)
  .unwrap_or(Allowance::Unlimited)        // → Allowance::Unlimited  ← BUG
``` [3](#0-2) 

The NEAR SDK's `Allowance::limited` is a constructor that wraps `NonZeroU128`; it returns `None` for a zero argument. The `unwrap_or(Allowance::Unlimited)` fallback was intended to handle the `is_limited_allowance=false` case (where `access.allowance` is `None`), but it also fires for the `is_limited_allowance=true, allowance=0` case, producing the wrong result.

### Impact Explanation

A wallet owner who signs an `AddKey` transaction intending to grant a third party (e.g., a relayer or dApp) a function-call key with **zero** spending power instead grants that party a key with **unlimited** spending power. The key holder can subsequently drain the wallet's NEAR balance through repeated function calls, constituting unauthorized transaction execution, fee payment bypass, and balance manipulation.

### Likelihood Explanation

The trigger requires the wallet owner to sign a transaction with `is_limited_allowance=true, allowance=0`. This is an edge case, but it is a valid, user-reachable input through the normal `rlp_execute` entry point — no privileged access, validator role, or key compromise is required. The relayer merely forwards the signed transaction as-is.

### Recommendation

Add an explicit guard in `action_to_promise` (or in `try_into_near_action`) that rejects or errors when `is_limited_allowance=true` and `allowance=0`, rather than silently falling through to `Allowance::Unlimited`. For example, in `action_to_promise`:

```rust
let allowance = match access.allowance {
    Some(a) => Allowance::limited(a)
        .ok_or(Error::User(UserError::ZeroAllowanceNotAllowed))?,
    None => Allowance::Unlimited,
};
```
