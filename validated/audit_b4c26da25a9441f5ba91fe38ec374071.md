### Title
Permanent resource-weight invariant violation when un-delegating V1 frozen balance to a contract receiver - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`)

### Summary
`UnfreezeBalanceActuator.execute` handles the case where an owner reclaims TRX that was frozen-and-delegated (V1 model, `receiverAddress` set) to another account. When the receiver is a contract account (or has been destroyed) and the `AllowTvmConstantinople` feature is active, the actuator skips decrementing the receiver's `AcquiredDelegatedFrozenBalanceForBandwidth/Energy`, but still fully decrements the network-wide `TotalNetWeight`/`TotalEnergyWeight` counters by the same amount. This is the same root-cause pattern as the PoolTogether `TwabController._transferBalance` finding: an individual account's weight is left unchanged while the aggregate/total weight is reduced, breaking the invariant `sum(individual weights) == total weight` that the resource-limit proportional-allocation model depends on.

### Finding Description
In `UnfreezeBalanceActuator.execute`, for the delegated-unfreeze branch:

```java
AccountCapsule receiverCapsule = accountStore.get(receiverAddress);

if (dynamicStore.getAllowTvmConstantinople() == 0 ||
    (receiverCapsule != null && receiverCapsule.getType() != AccountType.Contract)) {
  switch (unfreezeBalanceContract.getResource()) {
    case BANDWIDTH:
      ... receiverCapsule.addAcquiredDelegatedFrozenBalanceForBandwidth(-unfreezeBalance); ...
      decrease = newNetWeight - oldNetWeight;
      break;
    ...
  }
  accountStore.put(receiverCapsule.createDbKey(), receiverCapsule);
} else {
  decrease = -unfreezeBalance / TRX_PRECISION;
}
``` [1](#0-0) 

When `AllowTvmConstantinople == 1` and the receiver is `null` (destroyed, e.g. via `SUICIDE`) or has `AccountType.Contract`, the `else` branch is taken: the receiver's `AcquiredDelegatedFrozenBalanceForBandwidth`/`ForEnergy` field is **never modified and never written back** (no `accountStore.put` for the receiver), but `decrease` is still set to the full `-unfreezeBalance / TRX_PRECISION`.

That value flows into the global weight adjustment further down:
```java
long weight = dynamicStore.allowNewReward() ? decrease : -unfreezeBalance / TRX_PRECISION;
switch (unfreezeBalanceContract.getResource()) {
  case BANDWIDTH:
    dynamicStore.addTotalNetWeight(weight);
    break;
  case ENERGY:
    dynamicStore.addTotalEnergyWeight(weight);
    break;
  ...
}
``` [2](#0-1) 

So the global `TotalNetWeight`/`TotalEnergyWeight` (used as the denominator for every account's proportional bandwidth/energy limit, analogous to `_vaultTwabTotalSupply`) is decreased by the full unfrozen amount, while the specific contract-receiver's `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` (analogous to an individual account's `twab`, the numerator used when computing that account's own resource limit) is left permanently inflated. The receiver keeps a numerator that reflects TRX no longer staked anywhere in the network, against a now-smaller total, permanently over-allocating that account's share of the shared bandwidth/energy pool.

This condition is reachable from an anonymous, unprivileged transaction: the owner side of a V1 delegated freeze (`FreezeBalanceContract` with `receiverAddress` set, handled in `delegateResource`) has no restriction preventing the receiver from being a contract address [3](#0-2)  — unlike the newer `DelegateResourceActuator` (V2 model) which explicitly rejects contract receivers [4](#0-3) . Any user can therefore: (1) freeze-and-delegate to a contract address, (2) trigger the contract's self-destruct or simply wait, and (3) broadcast `UnfreezeBalanceContract` to reclaim, hitting the asymmetric branch above.

### Impact Explanation
Resource limits (`NetLimit`/`EnergyLimit`) for every account on the network are computed proportionally to `TotalNetWeight`/`TotalEnergyWeight`. Once the invariant is broken, the affected contract permanently retains an inflated `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` value that is no longer backed by any actually-staked TRX, while the global total has already been reduced to reflect the un-freeze. This corrupts network-wide resource accounting: it grants that contract (and, cumulatively across the shared pool, distorts the fair proportional share of all other stakers) resource entitlement it did not pay for, indefinitely — a direct on-chain accounting/resource corruption analogous to the reserve-drainage effect described in the referenced report.

### Likelihood Explanation
Reachable purely through two ordinary, unprivileged, already-supported transaction types (`FreezeBalanceContract` with a `receiverAddress`, then `UnfreezeBalanceContract`) once the long-since-activated `AllowTvmConstantinople` hard fork flag is on (which it is on mainnet). No special privileges, leaked keys, or malicious peers are required — only a user delegating to their own or any contract address and later un-delegating. The `else` branch is exercised whenever the receiver is a contract or has been destroyed, which is an easily engineered condition (e.g., via `SUICIDE`).

### Recommendation
Ensure the total-weight decrement in the `else` branch (contract/destroyed receiver) matches the actual net change to the individual side (i.e., zero, since the receiver's field is never persisted), or explicitly and correctly zero/decrement the receiver's `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` in that branch before computing `decrease`, so that `sum(individual acquired weights) == TotalNetWeight/TotalEnergyWeight` is preserved in all branches, mirroring the fix already applied in the V2 `UnfreezeBalanceV2Processor`/`UnDelegateResourceProcessor` accounting.

### Proof of Concept
1. Deploy contract `C`.
2. Account `A` sends `FreezeBalanceContract` with `receiverAddress = C`, resource `BANDWIDTH`, freezing `X` TRX — this calls `delegateResource`, incrementing `C.AcquiredDelegatedFrozenBalanceForBandwidth` by `X` and `TotalNetWeight` by `X/TRX_PRECISION` [5](#0-4) .
3. `C` self-destructs (or is simply of `AccountType.Contract`).
4. After the freeze duration expires, `A` sends `UnfreezeBalanceContract` with the same `receiverAddress = C`.
5. Because `AllowTvmConstantinople == 1` and `C` is a `Contract` (or `null`), the code takes the `else` branch: `C.AcquiredDelegatedFrozenBalanceForBandwidth` is left at `X` (never reset), while `TotalNetWeight` is decremented by `X/TRX_PRECISION`.
6. Result: `TotalNetWeight` no longer equals the sum of all accounts' effective bandwidth weights; `C` retains a `NetLimit` share proportional to `X` TRX that no longer exists anywhere on-chain.
