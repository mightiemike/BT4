### Title
Ancient-pack squash silently drops carry-forward tombstones for zero-lamport single-ref accounts, permitting balance resurrection after an incremental snapshot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`calc_accounts_to_combine` invokes the same `shrink_collect` used by normal shrink, which can populate `tombstones_to_carry_forward` when a zero-lamport single-ref account's slot is newer than `latest_full_snapshot_slot` [1](#0-0) . Unlike `shrink_storage`, which explicitly rewrites `tombstones_to_carry_forward` into the new storage [2](#0-1) , the ancient-pack write path (`PackedAncientStorage::pack` / `write_packed_storages` / `write_ancient_accounts_to_same_slot_multiple_refs`) only consumes `alive_accounts`, never `tombstones_to_carry_forward`. The code base itself acknowledges this gap with a `debug_assert!` in `finish_combine_ancient_slots_packed_internal` stating that a non-empty carry-forward list at that point "would be silently lost" [3](#0-2) .

### Finding Description
`shrink_collect` (shared by both normal shrink and ancient combining) already removes a zero-lamport single-ref pubkey from the accounts index whenever it's the sole reference, regardless of whether the tombstone bytes can be dropped yet [4](#0-3) . If `latest_full_snapshot_slot` has not yet advanced past that slot, `can_purge_zero_lamport_single_ref_after_shrink` returns false and the account bytes must be "carried forward" as a tombstone so an incremental snapshot can still communicate the deletion — this is exactly the invariant validated by `test_shrink_collect_carries_forward_existing_tombstones` and `test_shrink_converts_zero_lamport_single_ref_account_to_tombstone` for the plain-shrink path [5](#0-4) .

`calc_accounts_to_combine` reuses this exact same `shrink_collect` call for ancient packing [1](#0-0) , so `ShrinkCollect::tombstones_to_carry_forward` can be non-empty there too whenever an ancient-eligible slot happens to be newer than `latest_full_snapshot_slot` at the moment ancient packing runs. Nothing in `combine_ancient_slots_packed`/`calc_accounts_to_combine` filters candidate slots by `latest_full_snapshot_slot` before calling `shrink_collect` (no reference to `latest_full_snapshot_slot` exists anywhere in `ancient_append_vecs.rs`). The subsequent packing (`PackedAncientStorage::pack`, consuming `alive_accounts.one_ref`/`many_refs_this_is_newest_alive`) and the "same slot, multiple refs" write path only handle `alive_accounts`; `tombstones_to_carry_forward` is never read or written anywhere in the ancient-pack write pipeline. After packing, `finish_combine_ancient_slots_packed_internal` calls `remove_old_stores_shrink`, which drops the old storage (and thus the physical tombstone bytes) via `mark_dirty_dead_stores`/`dead_storages` [6](#0-5) , while the index entry for the pubkey has already been removed by `remove_zero_lamport_single_ref_accounts_after_shrink` [7](#0-6) .

The result: the account is gone from the index (correct — it's zero lamport) but the physical tombstone that an incremental snapshot needs in order to instruct a restarting node "this account was deleted" is never written into the new ancient storage. If a subsequent incremental snapshot is taken with a base full snapshot from *before* the close (i.e. the full snapshot doesn't yet reflect the close, and the incremental snapshot no longer carries the tombstone because it was dropped during packing rather than shrink), then loading the full+incremental snapshot pair on restart replays the old non-zero balance from the full snapshot with no incremental delta to zero it out — resurrecting the pre-close balance. This is precisely the scenario the code's own `debug_assert!` documents as a silent-loss bug [3](#0-2) , and since it is only a `debug_assert!`, it does not fire in release builds — it neither prevents the bug nor even surfaces it in production.

Preconditions match the question's scenario exactly: an attacker creates a small, ancient-eligible slot containing a zero-lamport single-ref account (a closed account they control), while `latest_full_snapshot_slot` is behind that slot's snapshot progression. This is fully within reach of an unprivileged user who can create/close accounts and control timing of transactions relative to background ancient-packing and snapshot-interval configuration (both are validator-side background processes triggered by slot age/size heuristics, not by attacker RPC calls directly, but the attacker fully controls the account lifecycle events that make their pubkey eligible).

### Impact Explanation
If exploited, a restarting/replaying node would compute account state (balance, owner, data) that diverges from the actual on-chain lifecycle — a closed (zero-lamport) account reappears with its pre-close lamports and data after snapshot load, causing an honest-node snapshot-vs-replay state/hash mismatch and potential capitalization divergence. This matches the "silent balance change / hash-capitalization divergence / honest-node snapshot-vs-replay mismatch" impact category explicitly listed as in-scope in the audit rules.

### Likelihood Explanation
The trigger requires: (1) a zero-lamport single-ref account, achievable by any user closing an account they own; (2) that account's slot becoming eligible for ancient combination (a routine background operation that runs periodically over old slots); (3) `latest_full_snapshot_slot` on the validator lagging behind that slot at the moment ancient packing executes (a normal, frequently-occurring condition since full snapshots are taken periodically, not continuously); (4) an incremental snapshot taken and used for a subsequent restart. None of these require validator/leader privileges — an attacker only needs ordinary account create/close/rewrite capability and patience to let background ancient packing run over their slot before the next full snapshot catches up. The bug is gated by internal AccountsDb timing (snapshot cadence vs. ancient-pack cadence) rather than attacker-controlled RPC timing, making it probabilistic/opportunistic rather than instantly reproducible on demand, but it is a real, reachable code path documented by the codebase's own defensive `debug_assert!`.

### Recommendation
Either (a) prevent `calc_accounts_to_combine`/`shrink_collect` from ever producing a non-empty `tombstones_to_carry_forward` for slots considered by ancient packing by gating ancient-slot selection so it never processes slots newer than `latest_full_snapshot_slot` (mirroring the guard used elsewhere for zero-lamport purging), or (b) make the ancient-pack write path (`PackedAncientStorage::pack`, `write_packed_storages`, `write_ancient_accounts_to_same_slot_multiple_refs`) explicitly carry forward `tombstones_to_carry_forward` into the packed/target storage exactly as `shrink_storage` does via `store_tombstones`. Additionally, upgrade the `debug_assert!` in `finish_combine_ancient_slots_packed_internal` to a hard runtime check (`assert!` or an early bail-out with an error/metric) so this condition cannot silently pass in release builds.

### Proof of Concept
Extend `test_shrink_converts_zero_lamport_single_ref_account_to_tombstone` into an ancient-pack + snapshot round-trip integration test:
1. Create an `AccountsDb` with `set_latest_full_snapshot_slot(slot0)`.
2. Store a closed (zero-lamport) account at `slot1 > slot0`, add root, ensure it's a single ref (`ref_count == 1`).
3. Force `slot1` to be treated as ancient-eligible (mark it small enough / old enough per `collect_sort_filter_ancient_slots` criteria) and call `combine_ancient_slots_packed` (or the public `shrink_ancient_slots`) with `latest_full_snapshot_slot` still `< slot1`.
4. Assert (this is expected to fail today): the resulting ancient storage's `num_tombstones()`/`tombstone_offsets` for the pubkey is `1`, matching the plain-shrink behavior in `test_shrink_converts_zero_lamport_single_ref_account_to_tombstone`.
5. Take a full snapshot (reflecting state at/before `slot0`, i.e., before the close) then an incremental snapshot covering `slot1`.
6. Restart by loading full+incremental snapshot archives (as in `runtime/src/snapshot_bank_utils.rs`'s existing tombstone round-trip test) and assert the account's lamports are `0`/absent, not resurrected to the pre-close balance.
Expected current (buggy) result: step 4's assertion fails (`num_tombstones() == 0`), and step 6 shows the account resurrected with its pre-close lamports — demonstrating the LIFECYCLE_NEUTRALITY violation.
