### Title
Unauthorized `WithdrawFromGasKey` Action Allows Any Account to Drain Another Account's Gas Key Balance - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The `WithdrawFromGasKey` action lacks a check that the transaction signer is the same as the receipt receiver. Any unprivileged user can craft a transaction with `signer_id = attacker`, `receiver_id = victim`, and `Action::WithdrawFromGasKey { public_key: victim_gas_key_pk, amount: X }`. The runtime applies this action against the victim's gas key without verifying that the signer authorized the withdrawal, draining the victim's gas key balance and breaking gas key–funded transaction flows.

### Finding Description
`action_withdraw_from_gas_key` in `runtime/runtime/src/access_keys.rs` operates entirely on the receipt's `account_id` (the receiver). It looks up the gas key by `(account_id, action.public_key)`, subtracts `action.amount` from the gas key's balance, and credits the same amount to the receiver's account balance. [1](#0-0) 

The action is dispatched from `apply_action` in `runtime/runtime/src/lib.rs` with `account_id` set to the receipt receiver, with no check that the predecessor (original transaction signer) equals the receiver. [2](#0-1) 

The only validation performed on the action itself is a protocol-feature gate: [3](#0-2) 

Neither `verify_and_charge_tx_ephemeral` nor `verify_and_charge_gas_key_tx_ephemeral` in `runtime/runtime/src/verifier.rs` contains a check that `signer_id == receiver_id` when the action list includes `WithdrawFromGasKey`. [4](#0-3) 

The design comment on `WithdrawFromGasKeyAction` states the action "must only be available via transactions, not via contract execution," but this restriction addresses only the host-function surface; it does not address the missing signer-equals-receiver invariant. [5](#0-4) 

All existing tests and tooling always set `signer_id == receiver_id` for `WithdrawFromGasKey`, confirming the design intent but also confirming the invariant is never tested for the cross-account case. [6](#0-5) 

### Impact Explanation
An attacker who knows a victim's gas key public key (visible on-chain via `ViewAccessKey`) can submit a valid signed transaction that drains the victim's gas key balance into the victim's main account. The victim's total NEAR is conserved, but:

1. **Balance manipulation**: The attacker redistributes the victim's NEAR between the gas key sub-balance and the main account balance without the victim's consent.
2. **Contract execution flow breakage / meta-transaction disruption**: Gas key transactions and `DelegateV2` meta-transactions rely on the gas key having a non-zero balance. Draining it causes all in-flight and future gas key transactions to fail with `NotEnoughGasKeyBalance` until the victim manually re-funds the key.
3. **Repeated griefing**: The attacker can re-drain the gas key immediately after each re-funding, at the cost of only the attacker's own gas per transaction.

### Likelihood Explanation
The attack requires only a standard signed transaction targeting the victim's account. Gas key public keys are public state. The attacker pays only normal transaction gas. No privileged role, validator access, or special timing is required. The `GasKeys` protocol feature is new and this cross-account path has no test coverage, making it likely to have been overlooked.

### Recommendation
Add a validation check — either in `validate_withdraw_from_gas_key_action` (passing the transaction's `signer_id` and `receiver_id`) or in the transaction-level verifier — that rejects any transaction where `signer_id != receiver_id` and the action list contains `WithdrawFromGasKey`. This mirrors the self-only semantics already enforced by the absence of a host function.

```rust
// In validate_withdraw_from_gas_key_action or the tx verifier:
if tx.signer_id() != tx.receiver_id() {
    return Err(ActionsValidationError::WithdrawFromGasKeyRequiresSelfTransaction);
}
```

### Proof of Concept
1. Alice observes that Bob's account `bob.near` has a gas key with public key `GK_PK` and balance `B`.
2. Alice constructs a transaction:
   - `signer_id = alice.near`
   - `receiver_id = bob.near`
   - `actions = [WithdrawFromGasKey { public_key: GK_PK, amount: B }]`
3. Alice signs and submits the transaction. It passes all current validation checks (valid signature, nonce, Alice has enough balance for gas).
4. The runtime converts the transaction to an action receipt with `receiver_id = bob.near`.
5. `apply_action_receipt` calls `action_withdraw_from_gas_key` with `account_id = bob.near`.
6. The function finds Bob's gas key, subtracts `B` from its balance (now 0), and adds `B` to Bob's account balance.
7. Bob's gas key is now empty. Any subsequent gas key transaction or `DelegateV2` meta-transaction signed with `GK_PK` fails with `NotEnoughGasKeyBalance`.
8. Alice can repeat step 2–7 immediately after Bob re-funds the key, at the cost of one transaction's gas per drain.

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())

pub fn verify_and_charge_tx_ephemeral(
    config: &RuntimeConfig,
    account: &Account,
    access_key: &AccessKey,
    tx: &Transaction,
    transaction_cost: &TransactionCost,
    block_height: Option<BlockHeight>,
    pending: &PendingConstraints,
) -> TxVerdict {
    // It's the caller's responsibility to NOT call this function for transactions with
    // nonce_index (i.e. gas key transactions).
    assert!(
        tx.nonce().nonce_index().is_none(),
        "verify_and_charge_tx_ephemeral called for gas key transaction"
    );
    // Gas keys must be used via gas key transaction path (with nonce_index)
    if let Some(gas_key_info) = access_key.gas_key_info() {
        return TxVerdict::Failed(InvalidTxError::InvalidNonceIndex {
            tx_nonce_index: None,
            num_nonces: gas_key_info.num_nonces,
        });
    }
    let TransactionCost {
        gas_burnt,
        compute_burnt,
        gas_remaining,
        receipt_gas_price,
        total_cost,
        burnt_amount,
        ..
    } = *transaction_cost;
    let account_id = tx.signer_id();
    let tx_nonce = tx.nonce().nonce();
    let effective_nonce = std::cmp::max(access_key.nonce, pending.max_nonce);
    if let Err(e) = verify_nonce(tx_nonce, effective_nonce, block_height, tx.nonce_mode()) {
        return TxVerdict::Failed(e);
    }

    // saturating_sub is fine here: on the consensus path pending constraints
    // are always default (zero), so the subtraction is exact. On the RPC /
    // chunk-production path it is best-effort and does not affect consensus.
    let available_balance = account.amount().saturating_sub(pending.paid_from_balance);
    if available_balance < total_cost {
        return TxVerdict::Failed(InvalidTxError::NotEnoughBalance {
            signer_id: account_id.clone(),
            balance: available_balance,
            cost: total_cost,
        });
    }
    // Debit only this tx's cost, not the pending amount (which was already
    // charged in prior chunks and will be applied at execution time).
    let new_amount = account.amount().checked_sub(total_cost).unwrap();

    let new_allowance = match check_and_compute_new_allowance(
        access_key,
        account_id,
        tx.public_key(),
        total_cost,
    ) {
        Ok(a) => a,
        Err(e) => return TxVerdict::Failed(e),
    };

    match check_storage_stake(account, new_amount, config) {
        Ok(()) => {}
        Err(StorageStakingError::LackBalanceForStorageStaking(amount)) => {
            return TxVerdict::Failed(InvalidTxError::LackBalanceForState {
                signer_id: account_id.clone(),
                amount,
            });
        }
        Err(StorageStakingError::StorageError(err)) => {
            return TxVerdict::Failed(StorageError::StorageInconsistentState(err).into());
        }
    };

    // Validate FunctionCall permission constraints if applicable
    if let Some(function_call_permission) = access_key.permission.function_call_permission()
        && let Err(e) = verify_function_call_permission(function_call_permission, tx)
    {
        return TxVerdict::Failed(e);
    }

    TxVerdict::Success(VerificationResult {
        gas_burnt,
        compute_burnt,
        gas_remaining,
        receipt_gas_price,
        burnt_amount,
        new_account_amount: new_amount,
        access_key_update: AccessKeyUpdate::Regular { nonce: tx_nonce, new_allowance },
    })
}
