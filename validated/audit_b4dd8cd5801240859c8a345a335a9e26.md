### Title
160-bit keccak256 truncation in `derive_near_deterministic_account_id` enables birthday-attack account squatting with silent fund-theft - (File: core/primitives/src/utils.rs)

### Summary

`derive_near_deterministic_account_id` retains only the last 20 bytes (`[12..32]`) of a 256-bit keccak256 digest, reducing the collision-resistance of deterministic (`0s…`) account IDs to 2^80 operations. Because `DeterministicStateInitAction` is explicitly designed to succeed silently when the target account already exists, an attacker who pre-registers a collision address with malicious contract code causes the legitimate deployer's action to return success with no error, leaving the account under attacker-controlled code. Any subsequent fund transfer to that account is then stolen by the malicious contract.

### Finding Description

**Root cause — 160-bit truncation:**

`derive_near_deterministic_account_id` in `core/primitives/src/utils.rs` computes:

```rust
let hash = sha3::Keccak256::digest(&data);
format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
```

Only 160 bits of the 256-bit digest are kept. The birthday bound for a 160-bit space is 2^80 — an attacker needs to find two distinct `DeterministicAccountStateInit` payloads (varying `code` and/or `data`) that produce the same 20-byte suffix.

**Validation path — computed hash, not authoritative lookup:**

`validate_deterministic_state_init` in `runtime/runtime/src/action_validation.rs` accepts a `DeterministicStateInitAction` if and only if:

```rust
let derived_id = derive_near_deterministic_account_id(&action.state_init);
if derived_id != *receiver_id { return Err(...) }
```

This is a pure hash-equality check. Any `state_init` whose keccak256[12..32] equals the target address passes validation, regardless of what code or data it carries.

**Silent-success behavior — the amplifier:**

`check_account_existence` in `runtime/runtime/src/actions.rs` explicitly allows `DeterministicStateInit` to target an already-existing account:

```rust
Action::DeterministicStateInit(_) => {
    // Does not exist => The account will be created by the action.
    // Does exist => Nothing happens but the receipt is not aborted ...
}
```

`action_deterministic_state_init` in `runtime/runtime/src/deterministic_account_id.rs` then skips deployment if the account already has a contract:

```rust
if account.contract().is_none() {
    deploy_deterministic_account(...)
}
```

The receipt is **not aborted**; the transaction returns success. The legitimate deployer receives no signal that their intended code was never installed.

**End-to-end exploit path:**

1. Attacker generates pairs `(state_init_B_i, state_init_A_j)` off-chain — varying `code` (a `GlobalContractIdentifier`) and `data` entries — until `keccak256(borsh(B_i))[12..32] == keccak256(borsh(A_j))[12..32]`. At ~2^80 evaluations this yields a collision with ~50% probability.
2. Attacker submits a normal `DeterministicStateInitAction` with `state_init_B` (malicious global contract + attacker-chosen initial storage) to address `X`. `validate_deterministic_state_init` passes; account `X` is created with attacker-controlled code.
3. Legitimate deployer submits `DeterministicStateInitAction` with `state_init_A` (legitimate code) to the same address `X`. Validation passes (same 20-byte hash). `action_deterministic_state_init` sees `account.contract().is_some()` and skips deployment. **The transaction succeeds with no error.**
4. Legitimate deployer (or an automated on-chain system) sends funds to `X`, believing it holds legitimate code.
5. Malicious contract code executes and drains the deposited funds.

**Corrupted invariant:** The protocol invariant is that a `0s…` account ID uniquely identifies a specific `DeterministicAccountStateInit`. The 160-bit truncation breaks this uniqueness, allowing a different `state_init` to satisfy the receiver-ID check and occupy the address first.

### Impact Explanation

- **Fund theft**: Any NEAR balance sent to a deterministic account whose address was pre-squatted is immediately accessible to the attacker's malicious contract.
- **Contract execution flow breakage**: The legitimate deployer's code is never installed; all subsequent function calls on the account execute attacker-controlled logic.
- **Silent failure**: Because `DeterministicStateInitAction` is idempotent by design, the legitimate deployer's transaction returns success, providing no on-chain signal that the account is compromised. Automated pipelines that check only for transaction success before funding the account are fully exposed.

### Likelihood Explanation

Finding a birthday collision in a 160-bit space requires approximately 2^80 keccak256 evaluations. Using the external report's hardware baseline (255 TH/s Antminer-class hardware at ~$4,200/unit), a single machine takes ~300 years; 300 machines (~$1.26M capex) complete one set in one year. Two sets are needed, so total cost is roughly $4–5M over two years. This is within reach of nation-state actors and well-funded criminal organizations, and the cost falls as hardware improves. The attacker has wide latitude to vary both `GlobalContractIdentifier` (a 32-byte `CodeHash` or an arbitrary `AccountId`) and the `data` `BTreeMap` entries, giving a large input space to search. The attack is submitted as an ordinary unprivileged `DeterministicStateInitAction` transaction — no validator access or privileged key is required.

### Recommendation

Replace the 160-bit truncated encoding with a full-256-bit encoding that still fits within the 64-character account-ID limit. The existing `UAID` codec in `core/primitives-core/src/universal_account_id.rs` already encodes a 32-byte hash as `0u` + 52 Crockford-base32 symbols + 6-symbol Bech32m checksum = 60 characters — well within the limit. Adopting this format for deterministic account IDs raises the birthday bound from 2^80 to 2^128, making collision search computationally infeasible.

Concretely, change `derive_near_deterministic_account_id` to use the full 256-bit digest (e.g., via the UAID codec with a distinct prefix such as `0s`) and update `validate_deterministic_state_init` and all callers accordingly. This is a protocol-breaking change requiring a versioned migration, but the fix is straightforward.

//! Codec for `0u` universal account ids (UAIDs).
//!
//! A UAID encodes a 32-byte hash as
//! `0u` + 52 Crockford-base32 symbols of the hash + a 6-symbol Bech32m BCH checksum
//! = 60 characters, all lowercase `[0-9a-z]`, which is a valid NEAR account id.
//!
//! This is a pure codec: it turns a hash into an address and back and validates
//! the checksum. Hashing a `StateInit` into the 32-byte input lives with the
//! account-id derivation, not here.
//!
//! The base32 and checksum are implemented in this module rather than taken from
//! an external crate. No existing crate fits the whole codec: the `bech32` crates
//! implement full Bech32/Bech32m framing and their own alphabet, which we don't
//! use, and a base32 crate would cover only the encoding half while the checksum
//! still lives here, so it would add a dependency to this foundational crate
//! without shrinking what we maintain. Keeping both halves together also avoids a
//! glyph-to-value pass, since they share one 5-bit symbol pipeline. The
//! implementation was cross-checked against the `data-encoding` crate over 40M
//! random cases with zero correctness divergence and on-par performance.
//!
//! The checksum reuses the Bech32m polymod from
//! [BIP-350](https://github.com/bitcoin/bips/blob/master/bip-0350.mediawiki).
