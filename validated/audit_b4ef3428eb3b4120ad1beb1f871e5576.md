## Title
`ensure_match_transaction_info` silently skips state-checkpoint hash verification, making replay/verify tooling blind to state-root divergence - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that re-executing an archived transaction produces the exact same committed result as the authenticated `TransactionInfo` stored on-chain. The function validates status, gas used, write-set hash, and event-root hash, but never validates the `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields of `TransactionInfo` against the locally recomputed state root.

## Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares four properties between a freshly-executed `TransactionOutput` and the archived, ledger-authenticated `TransactionInfo`: transaction status, gas used, the write-set hash (`state_change_hash`), and the event-root hash. It never touches `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, even though these fields are exactly the authenticated commitments to the post-execution world state (Sparse Merkle Tree root, hot-state root, and position-state root) that a divergent VM execution or storage bug would corrupt. The code has a `TODO(trading-native)` comment acknowledging this gap and stating it "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution," instructing that checkpoint hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [2](#0-1) .

This method is the sole correctness oracle used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` per transaction to decide pass/fail [3](#0-2) . Because the check never inspects the state-checkpoint hash, a state-divergent bug in the VM, storage layer, or resource-group/materialization pipeline (the same categories the executor's `materialize_output`/`try_combine_into_storage_change_set` operate on) that produces a different state root but the same write-set bytes, events, gas, and status would pass `replay_on_archive` verification undetected.

## Impact Explanation
This is exactly the class of bug the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category targets: replay-verify tooling is the operational safety net used to catch state-corrupting non-determinism (consensus-breaking bugs) before/after mainnet incidents. If that safety net structurally cannot detect a state-root mismatch, a real state-divergence bug (e.g., a subtle Move VM or resource-group materialization defect) could pass replay verification silently, delaying detection of an active or historical hard-fork/state-corruption condition on mainnet archives.

## Likelihood Explanation
The gap is deterministic and always present (not dependent on the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` flag) — the state-checkpoint hash comparison is absent from the function today, so this is unconditionally true for every invocation of `ensure_match_transaction_info`, run by all consumers listed. The likelihood of *triggering* an actual state divergence is low (it requires a separate underlying non-determinism/storage bug), but the detection gap itself is present unconditionally today.

## Recommendation
Extend `ensure_match_transaction_info` to also validate the recomputed state-checkpoint hash (and hot-state/position-state checkpoint hashes when applicable) against `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` whenever the output represents a checkpoint boundary, rather than leaving this as an open TODO gated behind an unrelated feature flag. This requires threading the state root computed by `DoStateCheckpoint`/`DoLedgerUpdate` (or the tool's own SMT recomputation) into the comparator so replay/verify tools can actually detect state-root divergence.

## Proof of Concept
Not directly exploitable by an external attacker; this is a detection-gap in verification tooling. Conceptual PoC: construct (or simulate) an execution path where a resource-group/materialized write differs in on-chain state value but happens to produce the same serialized `WriteSet` hash coincidentally is not required — simpler, a genuine state root divergence caused by any bug in `DoStateCheckpoint`/SMT update logic that does not affect gas/status/events/write-set hash equality would satisfy every assertion in `ensure_match_transaction_info` and be reported as "verified" by `replay_on_archive`, while the state_checkpoint_hash actually differs from the archived ledger-authenticated value.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
