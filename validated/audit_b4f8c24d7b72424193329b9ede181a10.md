Based on my investigation, I found a genuine, developer-acknowledged gap in the replay/proof-verification integrity check itself.

## Finding

### Title
Replay-verification of `TransactionOutput` against `TransactionInfo` silently skips all checkpoint-hash fields, allowing divergent ledger state to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the sole function used by db-tool's replay/verification paths (e.g. `replay_on_archive`) to authenticate that a freshly-executed `TransactionOutput` matches the committed, accumulator-authenticated `TransactionInfo` at a given version. It checks status, gas, write-set hash, and event root hash, but explicitly and admittedly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function computes and compares only:
- transaction status (`ensure_match_transaction_info` line 2148-2157)
- `gas_used` (2159-2166)
- write-set hash vs `txn_info.state_change_hash()` (2168-2178)
- event root hash vs `txn_info.event_root_hash()` (2180-2195)

It never re-derives or compares against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (V1 only), or `txn_info.position_state_checkpoint_hash()` (V1 only) — the very fields that summarize the Sparse-Merkle/Jellyfish state-tree roots and the newer "position" (trading-native) state root committed into the transaction-accumulator leaf. This gap is called out directly in the code's own comment:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

`storage/db-tool/src/replay_on_archive.rs` calls exactly this function as the terminal correctness gate for each replayed transaction: [2](#0-1) 

Since `TransactionInfo` (V0/V1) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as the authenticated summaries of the Jellyfish Merkle / hot-state / position-state trees at checkpoint boundaries: [3](#0-2) 

and `DoStateCheckpoint`/`DoLedgerUpdate` are the only places these hashes are computed and folded into the `TransactionInfo` that eventually becomes an accumulator leaf: [4](#0-3) [5](#0-4) 

a replay run whose local execution produces a state-tree/position-tree root that differs from what is embedded in the historical, signature-backed `TransactionInfo` (e.g. due to a divergent Move VM semantics change, a JMT/hot-state bug, or a corrupted db-tool execution path) will still pass `ensure_match_transaction_info` as long as the write-set bytes, gas, status and event root happen to match. The write-set hash check alone is not sufficient because `state_checkpoint_hash` is derived from applying writes to the *persisted* state tree across potentially many transactions and accumulating hot-state eviction/insertion — a class of bugs entirely orthogonal to the raw write-set bytes (e.g. wrong key hashing, wrong tree-path computation, or an incorrect protocol-level state-summary transition) would go undetected.

### Impact Explanation
This breaks the "Committed state that differs from the correct VM result... " and "Hard-fork-only divergence during commit, replay, restore, or proof verification" integrity gate directly: the one tool designed to catch a state-computation divergence between two ledger implementations (used for auditing archived chain history, catching hard-fork bugs, and validating replay determinism) cannot detect a divergence in the state-tree/hot-state/position-state root — exactly the class of bug most likely to cause a silent chain split or an incorrect authenticated state root being accepted downstream (e.g. via state-sync fast-sync target roots or backup/restore verification that trusts these `TransactionInfo` fields). A validator or auditor relying on `replay_on_archive` to certify historical state-transition correctness gets a false "success" despite `state_checkpoint_hash`/`position_state_checkpoint_hash` mismatches, undermining confidence in every downstream proof (state snapshot roots, restore verification) that is ultimately anchored in these same `TransactionInfo` hashes.

### Likelihood Explanation
The gap is deterministic and always present — it is not a race condition or peer-dependent behavior. Any invocation of `replay_on_archive` (or any other future/embedded caller of `ensure_match_transaction_info`) is affected. It requires no privileged access or malicious peer: it's purely a local, unprivileged verification path failing to check fields that are already computed and available (`TransactionInfo::state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, `position_state_checkpoint_hash()`), so the fix is a matter of proof completeness, not implementation complexity. However, actual mainnet consensus commit paths (`DoStateCheckpoint`/`DoLedgerUpdate`) do compute and embed all of these hashes into the accumulator leaf, so the state actually committed to consensus is intact; the gap is confined to the replay/verification auditing surface itself.

### Recommendation
Extend `ensure_match_transaction_info` to also recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info`'s corresponding fields whenever they are `Some` (i.e. at checkpoint boundaries), returning an error identical in spirit to the existing write-set/event-hash mismatches. This closes the tool's own documented gap and ensures replay-verify genuinely certifies full state-tree equivalence, not just event/write-set equivalence.

### Proof of Concept
Local code proof (no external harness needed, self-evident from the function bodies cited above):
1. `execution/executor/src/workflow/do_state_checkpoint.rs::get_state_checkpoint_hashes` and `compute_position_checkpoint` compute `state_checkpoint_hash`/`position_state_checkpoint_hash` from the *state tree*, independent of the write-set bytes.
2. `types/src/transaction/mod.rs::ensure_match_transaction_info` (lines 2139-2204) never reads or compares these two fields (nor `hot_state_checkpoint_hash`), only `state_change_hash` (write-set hash) and `event_root_hash`.
3. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` (lines 392-405) treats a `Ok(())` return from `ensure_match_transaction_info` as full verification success and only surfaces an error on `Err`.
4. Therefore: construct/execute a transaction whose resulting write set and events are byte-identical to the historical record, but whose state-tree-root computation (e.g. due to a JMT traversal bug, or the position-tree accumulation logic in `do_state_checkpoint.rs`) yields a different `state_checkpoint_hash`/`position_state_checkpoint_hash` than the one embedded in the archived `TransactionInfo`. `execute_and_verify` will return `Ok(None)` (no error), silently certifying a replay whose state root has diverged from the authenticated ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
