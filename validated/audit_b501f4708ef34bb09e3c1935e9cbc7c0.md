### Title
Unbounded memory allocation from an attacker-controlled array-size felt in the deprecated (Cairo0) syscall calldata parser - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The deprecated (Cairo0) syscall array parser `read_felt_array` reads a raw `array_size` felt directly from Cairo VM memory and converts it to a `usize` without validating it against any bound (contract-controlled length, remaining calldata budget, or the actual size of the memory segment behind the pointer). This size is then passed straight into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` to materialize a `Vec<Felt>` of that length. This mirrors the OpenEXR CVE-2021-3478 pattern: a small, attacker-controlled length header drives an allocation before the corresponding data is validated to actually exist, allowing a crafted input to trigger excessive memory consumption.

### Finding Description
`read_felt_array` in the deprecated syscalls hint processor implements the legacy Cairo0 `(size, data_ptr)` calldata/array layout: [1](#0-0) 

The `array_size` felt is read from the caller-controlled memory pointed to by `ptr` (i.e., values that a Cairo0 (`__validate__`/`__execute__`/library-call/deploy) contract itself lays out when invoking a syscall such as `call_contract`, `library_call`, or `deploy`, via `read_calldata` → `read_call_params`): [2](#0-1) 

Unlike the newer (Cairo1) `read_felt_array` in `crates/blockifier/src/execution/syscalls/hint_processor.rs`, which derives the array length from the *difference between two relocatable pointers* (`array_data_end_ptr - array_data_start_ptr`) — a value that is at least loosely tied to actual segment layout — the deprecated version derives the length from a single arbitrary felt value with no upper bound check: [3](#0-2) 

The size is then forwarded unchecked to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` — a cairo-vm API that must materialize a Rust `Vec` of `size` elements: [4](#0-3) 

No caller in this path enforces `max_calldata_length` or any other resource-bound cap before this allocation occurs; those limits (`max_calldata_length`, `max_signature_length`, etc.) are only enforced by the gateway's `StatelessTransactionValidator` on the *outer* RPC transaction fields, not on values a deployed Cairo0 contract synthesizes internally during execution and feeds into a nested syscall request: [5](#0-4) 

Because Cairo0 (deprecated) classes remain declarable/callable in the network, any account can deploy or invoke a Cairo0 contract that, during `__validate__` or `__execute__`, issues a syscall whose calldata/array header claims an enormous `array_size` (e.g., close to `usize::MAX`) while pointing at a tiny or otherwise minimal memory region. `usize::try_from` will succeed for any value below `usize::MAX` (64-bit), so the size check does not fail before the allocation attempt.

### Impact Explanation
If `get_integer_range` (in the `cairo-vm` dependency) allocates its output vector eagerly (i.e., `Vec::with_capacity(size)`) before validating that all `size` cells are actually initialized/backed by real memory, a single transaction can force every sequencer/validator/full node that re-executes it (including Starknet OS re-execution during proving) to attempt a multi-gigabyte allocation. This can crash the node process (OOM) or degrade it severely, causing:
- Denial of service on any node that executes or re-executes the transaction (mempool validation, block building, OS re-execution).
- Potential honest-node divergence if some nodes OOM/crash while others (with more memory) succeed, or if the allocation attempt panics rather than returning a graceful `MemoryError`.
- In the worst case, an inability to progress block production if the bug is hit during block building/proving on the sequencer itself.

This satisfies the "network unable to confirm new transactions" / node-crash criterion for a Medium-severity availability issue, directly analogous to the referenced CVE (memory exhaustion from an unvalidated size field before data existence is confirmed).

### Likelihood Explanation
Medium. Reaching this code path requires:
1. Declaring or having access to a deployed Cairo0 (deprecated) class (unprivileged declare capability, publicly available).
2. Crafting a syscall invocation (e.g., `library_call`, `call_contract`, `deploy`) whose calldata/array header felt is maliciously large.

Both actions are within reach of any unprivileged transaction sender/contract deployer. The main uncertainty is whether `cairo-vm`'s `get_integer_range` actually pre-allocates the full `Vec` capacity before validating memory presence, or whether it validates incrementally/lazily (which would reduce impact to a bounded error rather than an allocation spike). This internal behavior lives in the external `cairo-vm` crate and was not directly inspectable in this repository, so the exact allocation strategy of `get_integer_range` could not be fully confirmed from the code available here.

### Recommendation
- In `read_felt_array` (deprecated_syscalls/hint_processor.rs), validate `array_size` against a strict upper bound (e.g., the same `max_calldata_length`/resource-derived constant used for calldata in the gateway, or the remaining gas/step budget) before calling `felt_range_from_ptr`.
- Alternatively, verify that the target memory segment actually contains at least `array_size` allocated felts (e.g., check current segment length via `vm.get_segment_size` or equivalent) prior to invoking `get_integer_range`, mirroring the defensive check already added in `crates/apollo_cairo_utils/src/lib.rs` (`CairoArray::try_from`), which explicitly validates a declared length against remaining data length before calling `Vec::with_capacity`.
- Confirm cairo-vm's `get_integer_range` semantics; if it eagerly allocates, consider replacing it with a chunked/lazy read that bails out on the first missing memory cell rather than allocating the full requested capacity upfront.

### Proof of Concept
1. Declare a Cairo0 (deprecated) contract class whose `__execute__` (or any externally callable entry point) issues a syscall using the legacy `(size, data_ptr)` array encoding — e.g., a `library_call` or `call_contract` syscall — where the caller writes a header felt `array_size = 0xFFFFFFFFFFFF` (a huge value that fits in `usize`) followed by a `data_ptr` pointing to an essentially empty/small memory segment.
2. Deploy this contract and invoke the vulnerable entry point via a normal `INVOKE` transaction.
3. During execution, `execute_next_deprecated_syscall` parses the request via `read_call_params`/`read_calldata`, calling `read_felt_array`, which reads the malicious `array_size` felt and passes it directly to `felt_range_from_ptr(vm, ptr, size)` → `vm.get_integer_range(ptr, size)`.
4. If `get_integer_range` allocates a `Vec` of `size` `Felt`s eagerly, the executing node attempts to allocate on the order of terabytes of memory (each `Felt` is 32 bytes; `0xFFFFFFFFFFFF * 32` bytes far exceeds available RAM), causing an OOM crash or severe resource exhaustion on any node (gateway validator, mempool, block builder, or OS re-execution) that processes this transaction.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

                calldata_length: total_length,
