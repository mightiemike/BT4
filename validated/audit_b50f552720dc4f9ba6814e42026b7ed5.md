### Title
Stale `last-update` timestamp causes overapplied interest when utilization/rate cycles through a stationary index - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
The vault's `accrue` function only advances the `last-update` timestamp when the computed `index`/`lindex` actually differ from their prior values. When utilization (and therefore the interest rate) is zero — e.g., no outstanding debt — `next-index` and `next-liquidity-index` resolve to the same value as the current `index`/`lindex`, so the conditional timestamp update is skipped, exactly mirroring the reported AMKT bug where `lastKnownTimestamp`/`lastKnownMultiplier` were only updated when `inflation > 0`.

### Finding Description
`accrue()` computes the new index values and conditionally writes state: [1](#0-0) 

The timestamp write is gated on whether the index actually changed:
```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
```

`next-index`/`next-liquidity-index` derive the multiplier from `(interest-rate)`, which is a function of `(utilization)`, which is `(calc-utilization (get-available-assets) (total-debt))`: [2](#0-1) 

If utilization is zero (e.g. `total-debt` is zero because there are currently no borrows, analogous to `totalSupply() == 0` in the original report), the interpolated rate at that curve point can be zero, making the compounding multiplier equal to `INDEX-PRECISION` — i.e., `next == idx` and `nliq == lidx`. In that case `last-update` is **not** advanced, exactly as `lastKnownTimestamp`/`lastKnownMultiplier` were not advanced in the AMKT bug when `inflation == 0`.

The danger is the same "stale clock" root cause: `last-update` is left pointing at a point far in the past. Once utilization becomes non-zero again (a new borrow occurs) and the interest rate curve yields a non-zero rate, the very next `accrue()` call computes:
```
(time-delta (- stacks-block-time (var-get last-update)))
```
This `time-delta` spans the *entire* dormant period plus the additional elapsed time up to now, and it gets compounded using the interest rate that is in effect **now** (post-utilization-change), not the (zero) rate that was actually in effect for most of that span. The full stale interval is retroactively charged at the newly active rate, producing an index jump — and hence a debt/interest jump — far larger than what should have legitimately accrued.

### Impact Explanation
This causes overapplication of interest to all outstanding/new borrowers' debt (`total-debt` computed via `calc-cumulative-debt`) and correspondingly inflates the vault share value/treasury-lp minted to `.dao-treasury`, in a single transaction. Borrowers who take on debt right after the dormant period are charged interest for time when there was no debt at all, which is effectively theft of value/miscalculated yield transferred to LPs/treasury and an incorrect debt state for the protocol — a "theft of unclaimed yield" / "protocol insolvency" class impact, matching the same root cause class as the referenced report (retroactive over-application of a rate/multiplier because the checkpoint wasn't advanced when a to-be-applied quantity was momentarily zero).

### Likelihood Explanation
Any market/vault pair naturally reaches zero utilization (all debt repaid) periodically, especially for newer or lower-demand vaults, or right after protocol launch/a pause. No privileged action is required — any user's normal repay-to-zero followed by a new borrow after elapsed time can trigger the stale-timestamp compounding jump. This makes the condition realistically reachable without any admin/DAO action.

### Recommendation
Decouple the timestamp update from whether the index value changed. `last-update` should always be advanced to `stacks-block-time` whenever `accrue()` runs (and is not paused), regardless of whether `idx`/`lidx` moved, so that `time-delta` on the next call reflects only the time since the last accrual call rather than the last time the index happened to change value. Optionally, snapshot the rate on each accrual so that periods with different rates are compounded piecewise rather than jamming the entire elapsed period through the latest rate.

### Proof of Concept
1. Vault starts with `total-debt = 0` (all borrows repaid), so `utilization = 0` and `(interest-rate)` resolves to a rate of `0` at that point on the curve.
2. Any user calls a vault entrypoint (e.g. `deposit`), triggering `accrue()`. `next-index` and `next-liquidity-index` equal the current `index`/`lindex` (multiplier = `INDEX-PRECISION`, i.e., no growth), so the `(var-set last-update ...)` branch is skipped — `last-update` is now stuck at this old timestamp.
3. Time passes (e.g., a long dormant period, `T` seconds), with `total-debt` remaining `0` the whole time — `last-update` never advances because `idx`/`lidx` never move.
4. A borrower calls `system-borrow`, which internally calls `accrue()` first. Now utilization jumps above zero (or the rate curve gives a nonzero rate at the freshly-nonzero utilization for that same call), so `next-index != idx`.
5. `next-index` is computed using `time-delta = stacks-block-time - last-update = T` (the entire dormant span) compounded at the interest rate implied by the state at the moment of this call — inflating `idx` by an amount reflecting `T` seconds of interest that should never have accrued (since debt was zero for that whole span).
6. This inflated `idx` increases `total-debt`, causing the newly-issued (or any pre-existing) debt/treasury-lp minted at that call to reflect an artificially large jump, at the expense of borrower funds / distorted vault accounting in a single transaction. [2](#0-1) [3](#0-2)
