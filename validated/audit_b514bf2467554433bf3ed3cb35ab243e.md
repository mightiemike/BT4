### Title
Unbounded growth of `UniversalTx.OutboundTx` via repeated rescue-outbound attachment causes O(n) linear scans on the hot vote/finalize path - (File: x/uexecutor/keeper/create_outbound.go, x/uexecutor/keeper/msg_vote_outbound.go, x/uexecutor/keeper/outbound.go)

### Summary
The external report describes a DoS where an attacker inflates an unbounded array that a critical function must linearly scan to find/remove an item, making later liquidation/removal operations expensive or unbounded. The closest Push Chain analog is the `OutboundTx` slice embedded in each `UniversalTx`: several core paths (`VoteOutbound`, `UpdateOutbound`, `HasPendingOutboundsForChain`, `AttachRescueOutboundFromReceipt`'s duplicate-rescue guard) linearly scan `utx.OutboundTx` by `Id`, and the rescue-outbound flow can keep appending new entries to the same UTX's array as long as the previous rescue attempt ended in `REVERTED` status. [1](#0-0) 

### Finding Description
`AttachRescueOutboundFromReceipt` only rejects a new rescue outbound if an *active* (`PENDING`/`OBSERVED`) rescue already exists for the target UTX; a `REVERTED` rescue is explicitly allowed to be retried: [1](#0-0) 

Each accepted rescue call appends a brand-new `OutboundTx` entry to `utx.OutboundTx` via `attachOutboundsToUtx`: [2](#0-1) 

Downstream, several functions that are on the honest-validator voting/finalization hot path do a linear `for _, ob := range utx.OutboundTx` scan to find an entry by `Id`: [3](#0-2) [4](#0-3) 

If a user can repeatedly trigger the rescue path against the same UTX (each round: emit a `RescueFundsOnSourceChain` event → wait for the appended outbound to reach `REVERTED` → repeat), the `OutboundTx` slice for that single UTX grows without an apparent upper bound before a fresh rescue can be re-attached. Every subsequent `VoteOutbound` call (needed by every universal validator to finalize *any* outbound tied to that UTX, including the attacker's own bloated entries) then re-scans the entire growing array, and `UpdateOutbound`/`FinalizeOutbound` do so again on write.

### Impact Explanation
If exploitable, this would inflate per-block gas/CPU cost of validator vote-finalization for a targeted UTX, potentially degrading throughput or, in an extreme case, contributing to block-processing slowdown reachable by an unprivileged user's own transactions (their own stuck deposit + repeated triggering of the gateway's rescue function). This maps to the "denial of service...not network-level and...reachable without privileged control" allowed-impact category. However, unlike the original Predy finding (a permissionless Solidity function anyone calls directly with attacker-chosen items), here the growth requires (a) causing one's own deposit to genuinely fail/get stuck, and (b) each rescue outbound to reach `REVERTED` status before a new one can be attached — a state that is normally decided by honest TSS/validator consensus on the destination chain outcome, not purely by the attacker. I was not able to confirm from the available code whether an attacker can force `REVERTED` at will (e.g., by choosing a destination chain/gas parameters that always fail) or how many rescue cycles are practically achievable per block.

### Likelihood Explanation
Uncertain/Low-Medium. I could not verify: (1) whether `RescueFundsOnSourceChain` on the actual gateway contract is rate-limited, requires waiting periods, or costs meaningful funds/gas per call that would make repeated cycling economically impractical; (2) whether there is an explicit maximum on `OutboundTx` length enforced elsewhere in the codebase that I did not locate; (3) whether reaching `REVERTED` status is attacker-controllable or requires honest validator/TSS cooperation (which would make this out-of-scope per the "honest validators and honest nodes" and "malicious peers/validators" exclusions).

### Recommendation
If this path is confirmed reachable by an unprivileged attacker without relying on validator misbehavior: (1) cap the number of `OutboundTx` entries (or specifically `RESCUE_FUNDS`-typed entries) per `UniversalTx`; (2) replace the linear scan over `utx.OutboundTx` in `VoteOutbound`, `UpdateOutbound`, and the rescue duplicate-check with an indexed lookup (e.g., a `collections.Map` keyed by outbound ID, as is already done for `PendingOutbounds`); (3) rate-limit or cool down rescue attempts per UTX (e.g., minimum block-height gap between rescue attachments).

### Proof of Concept
Not confirmed. A full PoC would require: (a) causing a CEA deposit to fail or a non-CEA `INBOUND_REVERT` outbound to reach `REVERTED` (attacker-achievable via a malformed/misconfigured token per existing integration tests such as `test/integration/uexecutor/execute_inbound_gas_test.go`), then (b) repeatedly invoking the gateway's rescue function and observing each rescue outbound also resolve to `REVERTED`, and (c) measuring growth of `utx.OutboundTx` and the resulting gas cost increase in `VoteOutbound`/`UpdateOutbound` over many cycles — none of which I was able to execute or fully trace with the tools available in this session. // AttachRescueOutboundFromReceipt scans the receipt for RescueFundsOnSourceChain events
// emitted by UniversalGatewayPC and, for each one found, attaches a RESCUE_FUNDS outbound
// to the original UTX referenced by the event's universalTxId.
//
// Unlike normal outbounds (which create a new UTX), rescue outbounds are appended to the
// already-existing UTX whose funds are stuck on the source chain.
func (k Keeper) AttachRescueOutboundFromReceipt(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalGatewayPC := strings.ToLower(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_GATEWAY_PC"].Address)

	evmChainID, err := utils.ExtractEvmChainID(ctx.ChainID())
	if err != nil {
		return fmt.Errorf("rescue: failed to extract EVM chain ID: %w", err)
	}
	pushChainCaip := fmt.Sprintf("eip155:%s", evmChainID)

	for _, lg := range receipt.Logs {
		if lg.Removed {
			continue
		}
		if strings.ToLower(lg.Address) != universalGatewayPC {
			continue
		}
		if len(lg.Topics) == 0 {
			continue
		}
		if strings.ToLower(lg.Topics[0]) != strings.ToLower(types.RescueFundsOnSourceChainEventSig) {
			continue
		}

		event, err := types.DecodeRescueFundsOnSourceChainFromLog(lg)
		if err != nil {
			return fmt.Errorf("failed to decode RescueFundsOnSourceChain: %w", err)
		}

		// The universalTxId in the event is a 0x-prefixed bytes32 matching our UTX key.
		originalUtxId := strings.TrimPrefix(event.UniversalTxId, "0x")

		originalUtx, found, err := k.GetUniversalTx(ctx, originalUtxId)
		if err != nil {
			return fmt.Errorf("rescue: failed to fetch UTX %s: %w", originalUtxId, err)
		}
		if !found {
			return fmt.Errorf("rescue: original UTX %s not found", originalUtxId)
		}
		if originalUtx.InboundTx == nil {
			return fmt.Errorf("rescue: UTX %s has no inbound tx", originalUtxId)
		}

		// Rescue eligibility differs by inbound type:
		//
		//  CEA inbounds: the deposit (first PCTx) must have failed, meaning the funds
		//  never arrived on Push Chain and are still locked on the source chain.
		//
		//  Non-CEA inbounds: the auto-generated INBOUND_REVERT outbound must exist and
		//  have reached REVERTED status, meaning TSS could not return the funds to the
		//  source chain and they are stuck (held by the gateway contract or in escrow).
		if originalUtx.InboundTx.IsCEA {
			if len(originalUtx.PcTx) == 0 || originalUtx.PcTx[0] == nil || originalUtx.PcTx[0].Status != "FAILED" {
				return fmt.Errorf("rescue: UTX %s CEA deposit did not fail", originalUtxId)
			}
		} else {
			hasRevertedAutoRevert := false
			for _, ob := range originalUtx.OutboundTx {
				if ob != nil && ob.TxType == types.TxType_INBOUND_REVERT && ob.OutboundStatus == types.Status_REVERTED {
					hasRevertedAutoRevert = true
					break
				}
			}
			if !hasRevertedAutoRevert {
				return fmt.Errorf("rescue: UTX %s has no reverted inbound-revert outbound", originalUtxId)
			}
		}

		k.Logger().Info("rescue outbound detected",
			"original_utx_id", originalUtxId,
			"pc_tx_hash", receipt.Hash,
		)

		// Guard against duplicate rescue outbounds: reject if an active rescue
		// (PENDING or OBSERVED) already exists. A REVERTED rescue may be retried.
		for _, ob := range originalUtx.OutboundTx {
			if ob == nil || ob.TxType != types.TxType_RESCUE_FUNDS {
				continue
			}
			if ob.OutboundStatus == types.Status_PENDING || ob.OutboundStatus == types.Status_OBSERVED {
				k.Logger().Warn("rescue outbound rejected: active rescue already exists",
					"original_utx_id", originalUtxId,
					"existing_outbound_id", ob.Id,
				)
				return fmt.Errorf("rescue: UTX %s already has an active rescue outbound (%s)", originalUtxId, ob.Id)
			}
		}

		// Resolve external asset address from PRC20 → token config for the source chain.
		tokenCfg, err := k.uregistryKeeper.GetTokenConfigByPRC20(
			ctx,
			originalUtx.InboundTx.SourceChain,
			event.PRC20,
		)
		if err != nil {
			return fmt.Errorf("rescue: token config not found for PRC20 %s on %s: %w",
				event.PRC20, originalUtx.InboundTx.SourceChain, err)
		}

		// Rescued funds go to the original revert recipient (or the sender as fallback).
		recipient := originalUtx.InboundTx.Sender
		if originalUtx.InboundTx.RevertInstructions != nil &&
			originalUtx.InboundTx.RevertInstructions.FundRecipient != "" {
			recipient = originalUtx.InboundTx.RevertInstructions.FundRecipient
		}

		logIndex := fmt.Sprintf("%d", lg.Index)
		outbound := &types.OutboundTx{
			Id:                types.GetRescueFundsOutboundId(pushChainCaip, receipt.Hash, logIndex),
			DestinationChain:  originalUtx.InboundTx.SourceChain,
			Recipient:         recipient,
			Amount:            originalUtx.InboundTx.Amount,
			ExternalAssetAddr: tokenCfg.Address,
			Prc20AssetAddr:    event.PRC20,
			Sender:            event.Sender,
			GasFee:            event.GasFee.String(),
			GasPrice:          event.GasPrice.String(),
			GasLimit:          event.GasLimit.String(),
			TxType:            types.TxType_RESCUE_FUNDS,
			OutboundStatus:    types.Status_PENDING,
			PcTx: &types.OriginatingPcTx{
				TxHash:   receipt.Hash,
				LogIndex: logIndex,
			},
		}

		// Record the rescue call as a PCTx on the original UTX so the full
		// PC-side history is visible (deposit FAILED → rescue call → outbound).
		if err := k.UpdateUniversalTx(ctx, originalUtxId, func(utx *types.UniversalTx) error {
			utx.PcTx = append(utx.PcTx, &pcTx)
			return nil
		}); err != nil {
			return fmt.Errorf("rescue: failed to record PCTx on UTX %s: %w", originalUtxId, err)
		}

		if err := k.attachOutboundsToUtx(ctx, originalUtxId, []*types.OutboundTx{outbound}, ""); err != nil {
			return fmt.Errorf("rescue: failed to attach outbound to UTX %s: %w", originalUtxId, err)
		}
	}

	return nil
}
