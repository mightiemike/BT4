### Title
Missing zero-address validation in `AccountPermissionUpdateActuator` permits permanent loss of account control - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator`, the actuator that lets any TRON account holder update their multi-signature `Owner`/`Witness`/`Active` permissions, validates permission key addresses with `DecodeUtil.addressValid()`, which only checks address length and the network prefix byte — it never checks that the address payload is non-zero. A key address consisting of the prefix byte followed by 20 zero bytes therefore passes validation as if it were a normal, controllable address, exactly the class of bug described in the external report (constructors/setters accepting zero-valued critical parameters without reverting).

### Finding Description
`checkPermission()` iterates over each `Key` in a `Permission` and only checks format validity, not whether the address is a real, controllable key: [1](#0-0) 

The underlying validity check performs only a length and prefix-byte comparison, with no check that the 20-byte payload is non-zero: [2](#0-1) 

Because of this, an `Owner` permission (or `Active`/`Witness` permission) can be updated so that one of its keys — including the sole key when `getKeysCount()==1` and it alone meets the `threshold` — is the all-zero address (the TRON network's un-ownable "black hole"-style address using the standard prefix followed by zero bytes). No private key exists for this address, so no one can ever produce a valid signature for it. Since `Owner` permission is required to authorize any future `AccountPermissionUpdateContract` for that account (including reverting the mistake), setting the effective controlling key(s) to the zero address permanently locks the account's ability to update its own permissions, which is a "constructor/setter accepts zero critical parameter -> permanent unusability" scenario directly analogous to the reported Maple bug class (`owner_`, `borrower_`, `lender_`, etc.).

The `execute()` path applies these permissions to storage without any additional server-side re-validation of key material: [3](#0-2) 

### Impact Explanation
If the `Owner` permission's keys resolve to the zero address (e.g., due to a front-end bug that fails to fill in the real address — precisely the exploit scenario described in the source report), the account permanently loses the ability to issue any further `AccountPermissionUpdateContract`, since no signature can ever satisfy the `Owner` permission threshold. This is a permanent loss-of-control/lock condition equivalent to the "funds locked, requiring expensive redeployment" impact in the original report — except here there is no way to "redeploy" a TRON account, making the effect irreversible. Any resources, TRX balance, or delegated authority gated behind that account's owner-level control becomes permanently inaccessible.

### Likelihood Explanation
This is reachable by any unprivileged account holder simply broadcasting an `AccountPermissionUpdateContract` transaction, no special privilege required. It requires either a client-side bug (matching the report's stated exploit scenario) or user/tooling error that leaves an address field unset/zeroed before the key list is submitted. `DecodeUtil.addressValid()` is the single, common address-format guard used throughout the actuator layer, and it structurally cannot detect this case since it only checks length and prefix byte.

### Recommendation
- **Short term:** In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject keys whose 20-byte payload (after the prefix) is all zero, in addition to the existing `DecodeUtil.addressValid()` check.
- **Long term:** Add a reusable "non-zero address" utility (checking that the payload bytes are not all zero) and apply it wherever an address is accepted as a critical, unrecoverable parameter across actuators (e.g., permission keys, delegation receivers, and other owner/beneficiary fields), and add regression tests asserting that zero-payload addresses are rejected.

### Proof of Concept
1. Construct an `AccountPermissionUpdateContract` for an existing account, setting the `Owner` permission with a single `Key` whose address bytes are `0x41` followed by 20 `0x00` bytes (a syntactically valid TRON address per `DecodeUtil.ADDRESS_SIZE`/prefix check) and `weight >= threshold`.
2. Submit/validate the transaction: `AccountPermissionUpdateActuator.validate()` passes because `checkPermission()` only calls `DecodeUtil.addressValid()`, which returns `true` for this address.
3. `execute()` commits the new `Owner` permission via `account.updatePermissions(...)`.
4. Any subsequent attempt to submit a new `AccountPermissionUpdateContract` (needed to revert the mistake) requires a valid signature satisfying the `Owner` permission threshold — which is now permanently impossible because the zero address has no corresponding private key, leaving the account's owner-level control permanently locked.

    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
