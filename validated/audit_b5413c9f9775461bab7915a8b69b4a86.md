### Title
Access-Key Deletion Does Not Persist Nonce, Enabling Transaction Replay After Key Recreation — (File: `runtime/runtime/src/access_keys.rs`)

### Summary
When a `DeleteKey` action removes an access key, its nonce (the anti-replay counter) is discarded entirely rather than persisted. If the account later re-adds an access key with the *same* public key via `AddKey`, the new key's nonce is reset to a fresh, block-height-derived floor instead of resuming from the last nonce actually used by the deleted key. This mirrors the "insufficient session invalidation after logout" bug class in the referenced report: revoking a credential (the access key / "session") does not durably invalidate the authorization state (the nonce) tied to it, so previously valid signed material can become usable again once the same credential is reinstated.

### Finding Description
`action_delete_key` removes the access key record via `remove_access_key` with no persistence of its nonce: [1](#0-0) 

When the same public key is later re-added, `add_regular_key` (and analogously `add_gas_key`) unconditionally sets the new access key's nonce to `initial_nonce_value(block_height)`, with no lookback at what nonce the previous incarnation of that key reached: [2](#0-1) 

```rust
let mut access_key = access_key.clone();
access_key.nonce = initial_nonce_value(block_height);
set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);
```

This directly contradicts the documented invariant for access-key recreation: [3](#0-2) 

> "NOTE: In some cases the access key needs to be recreated. If the new access key reuses the same public key, the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again."

Transaction admission only rejects a nonce if `tx_nonce <= current_nonce` (Monotonic) — it has no memory of the account's/key's nonce history beyond whatever is currently stored on the access key: [4](#0-3) 

The codebase itself flags awareness of this exact class of problem in a test comment for `test_delete_key_last`, calling out that "we forget the nonce when we delete a key": [5](#0-4) 

Because `initial_nonce_value` is only a function of the current block height (`(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, with the multiplier being `1_000_000`), and NEAR access-key nonces are frequently advanced far beyond this coarse per-block floor by normal usage patterns (e.g., wallets/relayers that pick large or timestamp-derived nonces to avoid collisions, or simply many prior transactions), any previously-signed-but-not-yet-submitted transaction bearing an old, larger nonce value remains a valid, correctly-signed authorization against the key material. If the account (voluntarily, via a relayer, or as part of a routine key-rotation/`swap_key` flow) deletes and re-adds an access key with the same public key — a supported and tested operation: [6](#0-5) 

— the freshly reset, lower nonce floor can validate and admit that stale transaction again, because `verify_nonce`/`gap_check_nonce` only compares against the *current* on-chain nonce, which has been reset: [7](#0-6) 

### Impact Explanation
A previously executed or previously signed-but-withheld transaction (e.g., a `Transfer`, `FunctionCall`, or `Stake` action) can be replayed once its signing key is deleted and recreated with the same public key, because the anti-replay nonce is not carried forward. This is concrete unauthorized value movement / duplicate execution: funds can be re-transferred, or a function call with side effects (e.g. token transfer via a contract) can be re-triggered, without the signer's current intent — directly matching the "unauthorized value movement" and "invalid state transition acceptance" impact classes.

### Likelihood Explanation
The precondition — deleting and re-adding an access key with the identical public key — is an explicitly supported, tested user flow (`swap_key`, `test_delete_key`), not an edge case requiring privileged access. Any unprivileged transaction signer who performs key rotation with key reuse, or whose relayer/service does so on their behalf, exposes any of their previously signed transactions (with a nonce above the fresh floor) to replay. The reachable surface is a single submitted transaction pair (`DeleteKey` + `AddKey`) from an ordinary account, satisfying the "single submitted transaction" bar.

### Recommendation
When an `AddKey` action reuses a public key that previously existed on the same account, the runtime should record and reuse the maximum nonce that key (or account, for gas keys) ever reached rather than resetting purely from `initial_nonce_value(block_height)`. This requires either (a) persisting a tombstone/high-water-mark nonce for deleted keys keyed by `(account_id, public_key)`, or (b) taking `max(initial_nonce_value(block_height), last_known_nonce_for_this_public_key)` when re-adding, consistent with the invariant already documented in `docs/DataStructures/AccessKey.md`.

### Proof of Concept
1. Account `alice` creates access key `K` with `AccessKey::full_access()`.
2. `alice` signs (but does not submit) a `Transfer` transaction `T1` to `bob` using key `K` with nonce `N` set intentionally large (e.g., far above the current block-height-derived floor, as many SDKs/relayers do to avoid collisions).
3. `alice` submits and confirms a `DeleteKey(K)` followed immediately (or later) by `AddKey(K, AccessKey::full_access())` reusing the same public key — see `swap_key` at [6](#0-5) . The new key's nonce is reset via `add_regular_key` to `initial_nonce_value(current_block_height)`, which is lower than `N`.
4. `alice` (or anyone who obtained the previously signed bytes of `T1`) submits `T1`. Because `N > current_nonce` per `verify_nonce`, `T1` is accepted and executed again, resulting in a duplicate transfer to `bob` that `alice` did not currently authorize.

fn add_gas_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    // For gas keys, nonce stored on access key is not used and should always be zero
    let mut access_key = access_key.clone();
    access_key.nonce = 0;
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    // Set up nonces for gas key
    let num_nonces = gas_key_info.num_nonces;
    let nonce = initial_nonce_value(block_height);
    for i in 0..num_nonces {
        set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
    }

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(gas_key_storage_cost(fee_config, public_key, &access_key, num_nonces))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
