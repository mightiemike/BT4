### Title
Off-chain constant-call simulation (`triggerconstantcontract`/`estimateenergy`) uses a stale block context and an unrelated energy limit, so on-chain broadcast execution can diverge from the simulated result - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
Callers (SDKs, DApp front-ends, or any bundler-like relayer that submits transactions on behalf of users) typically call `triggerconstantcontract` or `estimateenergy` off-chain to check whether a `TriggerSmartContract` call will succeed before signing/broadcasting the actual transaction via `broadcastTransaction`. The simulation path (`Wallet.callConstantContract`) executes the contract against a different block context and a different energy limit than the one that will apply during real, on-chain execution (`VMActuator.call`). This mirrors the "simulation success does not guarantee on-chain success" bug class: a caller relying on the constant-call result can broadcast a transaction that reverts on-chain, wasting bandwidth/energy fees, or conversely a transaction that fails simulation could still be attempted.

### Finding Description
In `Wallet.callConstantContract`, the simulation always uses the **latest already-confirmed block** as its `TransactionContext` block, and executes with `isConstantCall = true`: [1](#0-0) 

That block (`headBlockCapsule`) supplies `TIMESTAMP`, `NUMBER`, `COINBASE`/witness address, and `BLOCKHASH` values to the TVM via `ProgramInvokeFactory.createProgramInvoke`: [2](#0-1) 

When the transaction is actually broadcast (`Wallet.broadcastTransaction` → `Manager.pushTransaction` → `VMActuator`), it will instead execute in a **future** block whose `TIMESTAMP`, `NUMBER`, and witness (`COINBASE`) will differ from the one used at simulation time: [3](#0-2) [4](#0-3) 

Any contract logic that branches on `block.timestamp`, `block.number`, or the block producer (auctions, time-locks, vesting, per-block randomness, rate limiting keyed to block number) can therefore behave differently between the simulated call and the real execution — exactly the TIMESTAMP/COINBASE-dependent divergence highlighted in the report.

In addition, the energy limit used during simulation is unrelated to the one used for the real transaction. For constant calls, `VMActuator.call()` sets: [5](#0-4) 
i.e. `energyLimit = maxEnergyLimit` (default `100000000`, see `common/src/main/resources/reference.conf`), while the actual broadcast transaction is bound by `getTotalEnergyLimit(creator, caller, contract, feeLimit, callValue)`, which is derived from the account's frozen/staked resources and `feeLimit`. A contract that consumes more energy than the caller's real, resource-based `energyLimit` — but less than the generous `maxEnergyLimitForConstant` used for simulation — will pass `triggerconstantcontract`/`estimateenergy` off-chain yet run out of energy (`OUT_OF_ENERGY`, all consumed energy spent, see `program.spendAllEnergy()` at execute-time) once actually broadcast, burning the caller's bandwidth/energy fee for nothing: [6](#0-5) 

`estimateEnergy` itself performs a binary search purely by repeatedly calling `cleanContextAndTriggerConstantContract` (i.e. the same stale-block/constant-call path), so its "energyRequired" result inherits the same block-context mismatch: [7](#0-6) 

### Impact Explanation
This is a Medium-severity availability/economic issue analogous to the reported one: any relayer, wallet, or DApp that relies on `triggerconstantcontract`/`estimateenergy`/`eth_call`/`eth_estimateGas` results as a pre-broadcast gas-safety check can have its actual on-chain transaction revert or run out of energy despite a successful simulation, because (a) block-dependent opcodes (`TIMESTAMP`, `NUMBER`, `COINBASE`, `BLOCKHASH`) observe a different block at simulation time than at inclusion time, and (b) the energy budget used in simulation (`maxEnergyLimitForConstant`) is decoupled from the real account-based `energyLimit` used on-chain. The caller pays real TRX (bandwidth/energy fee) for a transaction that was "verified" off-chain but fails on-chain — the same wasted-gas concern described in the report, adapted to java-tron's TVM/constant-call architecture. It does not directly cause consensus divergence or fund theft, but it enables resource waste and possibly a griefing vector for malicious contract authors (a contract could be crafted to succeed under `triggerconstantcontract`'s generous energy limit/block context but deliberately revert or exhaust energy at real execution time), consistent with the report's description of a `DAppControl`/user-controlled contract that "tricks simulation."

### Likelihood Explanation
Likelihood is Medium: java-tron does not implement any ERC-7562-style restriction on which opcodes a simulated call may use, nor does it re-simulate against the actual candidate block right before broadcast, nor does it clamp the simulation energy budget to the caller's real resource-based limit. This is an inherent property of the current `triggerconstantcontract`/`estimateenergy` design rather than a rare edge case, and it is reachable purely through public RPC/gRPC/JSON-RPC calls (`TriggerConstantContract`, `EstimateEnergy`, `eth_call`, `eth_estimateGas`) followed by `broadcastTransaction` — no privileged access required.

### Recommendation
- Document explicitly (and expose via API) that `triggerconstantcontract`/`estimateenergy` results are approximate and time/block-sensitive; discourage relying on them as an absolute gas-safety guarantee for contracts using `TIMESTAMP`/`NUMBER`/`COINBASE`.
- Consider re-simulating with an energy limit clamped to the real account-based `getTotalEnergyLimit` (as done for non-constant calls) when `estimateenergy` is used as a pre-flight check for a specific sender/fee-limit, instead of the flat `maxEnergyLimitForConstant`.
- Consider allowing callers to pass an expected future block context (or a safety margin) so `estimateenergy` bounds account for reasonable timestamp/number drift between simulation and inclusion.
- As with Atlas's recommendation, this is difficult to fully eliminate; mitigations should focus on making callers aware of the risk and reducing the gap between simulated and real execution context/energy budget rather than promising full parity.

### Proof of Concept
1. Deploy a contract whose behavior depends on `block.timestamp`/`block.number`, e.g. `require(block.timestamp < deadline)` where `deadline` is close to the current head block's timestamp.
2. Call `triggerconstantcontract` (or `estimateenergy`/`eth_estimateGas`) shortly before `deadline`; because `Wallet.callConstantContract` uses the **current head block**'s timestamp (`headBlockCapsule`, see `Wallet.java:3147-3157`), the simulation succeeds.
3. Sign and `broadcastTransaction` the same call; by the time it is actually included, `block.timestamp` has advanced past `deadline` (a new block was produced), so the real execution reverts, and the caller's energy/bandwidth fee is spent for nothing.
4. Separately, deploy a contract that consumes energy just above the sender's real resource-based energy allowance but below `maxEnergyLimitForConstant` (100,000,000 by default, `common/src/main/resources/reference.conf:783`). `triggerconstantcontract`/`estimateenergy` succeeds (using the inflated `maxEnergyLimit`, `VMActuator.java:517-518`), but the real broadcast transaction fails with `OUT_OF_ENERGY` because `getTotalEnergyLimit` (`VMActuator.java:520-522`) yields a much smaller cap for the actual sender.
