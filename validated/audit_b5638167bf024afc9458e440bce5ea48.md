### Title
Multisig signer authorization uses `tx-sender` instead of `contract-caller`, enabling phishing-based unauthorized proposal approval - (File: `mainnet/contracts/dao/dao-multisig.clar`)

### Summary
`check-signer-auth` in `dao-multisig.clar` authorizes `propose`, `approve`, and `execute` based on `tx-sender` (the original transaction signer) instead of `contract-caller` (the immediate/previous caller in the call chain). This is the exact bug class described in the reference report: using the "signer" identity (Clarity's `tx-sender`, analogous to NEAR's `env::signer_account_id()`) instead of the "predecessor"/immediate-caller identity (Clarity's `contract-caller`, analogous to NEAR's `env::predecessor_account_id()`) for access control.

### Finding Description
`check-signer-auth` is defined as: [1](#0-0) 

and gates the governance-critical functions `propose`, `approve`, and `execute`: [2](#0-1) [3](#0-2) 

In Clarity, `tx-sender` is the account that signed the original transaction and does not change across ordinary nested `contract-call?`s — it only changes when a contract wraps a call in `as-contract`. `contract-caller`, on the other hand, is the immediate/previous principal in the call chain and changes with every contract hop. This is the direct Clarity analog of NEAR's `signer_account_id()` vs `predecessor_account_id()` distinction cited in the report.

Because `check-signer-auth` checks `(is-signer tx-sender)` rather than `(is-signer contract-caller)`, any intermediary contract that a legitimate DAO signer interacts with can silently forward a call into `dao-multisig`'s `propose`/`approve`/`execute` on the signer's behalf. The signer's wallet signs a transaction believing it is interacting with some unrelated contract (e.g., a swap, a claim, an airdrop), but that contract internally issues `(contract-call? .dao-multisig approve id)`. Since `tx-sender` remains the signer's own principal throughout the call chain (the malicious contract doesn't need `as-contract` to preserve this), the check passes even though `contract-caller` at the time of the check is the malicious intermediary contract, not the signer directly.

This mirrors the report precisely: the "owner"/signer can be phished into approving governance actions they never intended to trigger, because the contract checks the transaction signer rather than the direct caller.

### Impact Explanation
Silently accumulating unauthorized approvals from unaware signers can push a malicious proposal over the approval `threshold`. Once matured (or flagged `urgent`), `execute` calls `.dao-executor execute-proposal`, which runs the attacker-supplied `script` under `with-all-assets-unsafe`: [4](#0-3) 
This grants the malicious script full, unchecked access to protocol assets (treasury, vaults), leading to direct theft of protocol funds / insolvency — a Critical impact.

### Likelihood Explanation
Exploitation requires only that a legitimate DAO multisig signer be induced (via a phishing dApp/contract) to sign a single transaction that internally calls the vulnerable `dao-multisig` function — no special privileges, key compromise, or DAO registry manipulation is needed. Repeating this against enough signers (up to `threshold`) is a realistic social-engineering attack surface common to any active multisig signer set.

### Recommendation
Change `check-signer-auth` (and any other identity-based authorization intended to require a direct, first-hop caller) to use `contract-caller` instead of `tx-sender`:
```clarity
(define-private (check-signer-auth)
  (ok (asserts! (is-signer contract-caller) ERR-SIGNER)))
```
This ensures the multisig only accepts approvals/proposals/executions from signers acting as the direct caller, closing the phishing vector where a signer's transaction is silently redirected through an untrusted intermediary contract.

### Proof of Concept
1. Alice is a registered signer in `dao-multisig.clar`'s `signers` map.
2. Attacker deploys contract `M` whose public function `do-something` internally executes `(contract-call? .dao-multisig approve malicious-proposal-id)`.
3. Attacker gets Alice to sign a transaction calling `M.do-something` (e.g., disguised as a routine DeFi interaction).
4. Inside `dao-multisig approve`, `contract-caller` is `M`, but `tx-sender` is still Alice. `check-signer-auth` calls `(is-signer tx-sender)` → true, so Alice's approval is recorded for `malicious-proposal-id` without her intending to interact with the DAO at all: [5](#0-4) 
5. Repeat step 2–4 against enough distinct signers (via similar phishing contracts) to reach `threshold` approvals.
6. Call `execute`, which passes the same flawed `check-signer-auth`, triggering `.dao-executor execute-proposal` with the malicious script under full unsafe asset access, draining protocol funds.

  (let ((id (var-get nonce))

(define-public (approve (id uint))
  (let ((proposal   (unwrap-panic (map-get? proposals id)))
        (approvals  (get approvals proposal))
        (napprovals (unwrap-panic (as-max-len? (append approvals tx-sender) u20))))

    (ok true)))

(define-public (execute (id uint) (script <proposal-script>))
  (let ((proposal (unwrap-panic (map-get? proposals id)))
        (created-at (get created-at proposal))
        (expires-at (get expires-at proposal))
        (mature-at (+ created-at TIMELOCK))
        (current-threshold (var-get threshold))
        (approvals (len (get approvals proposal))))
    (try! (check-signer-auth))

    ;; check expiration
    (asserts! (< stacks-block-time expires-at) ERR-PROPOSAL-EXPIRED)

    (asserts! 
      (and
        (not (get executed proposal))
        (is-eq (contract-of script) (get script proposal))
        (>= approvals current-threshold)
        (or
          (>= stacks-block-time mature-at)
          (get urgent proposal)))
