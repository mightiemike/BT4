### Title
Front-Running a `DeployAccount` Transaction's Precomputed Address via the `deploy` Syscall Permanently Blocks Account Deployment - (File: `crates/blockifier/src/execution/execution_utils.rs`)

### Summary
Starknet's `DeployAccountTransaction` contract address is fully deterministic from public data (`contract_address_salt`, `class_hash`, `constructor_calldata`, deployer=zero) exactly like the CREATE-address prediction in the Berally report. Because this data is visible once the transaction is gossiped/admitted to the mempool but before it is included in a block, any other transaction sender can compute the same target address and race to occupy it first via the ordinary `deploy` syscall, permanently blocking the legitimate `DeployAccount` transaction from ever succeeding at that address.

### Finding Description
The contract address for account deployment is computed with a pure, deterministic function of publicly-known transaction fields: [1](#0-0) 

using a fixed zero deployer address. This same `calculate_contract_address` routine backs both `DeployAccountTransaction` and the general-purpose `deploy` syscall (`deploy_from_zero=true` sets `deployer_address = ContractAddress::default()`), so any account/contract exposing a deploy entry point (e.g. an unprivileged UDC-style contract) that forwards attacker-supplied `class_hash`/`salt`/`calldata` to the `deploy` syscall computes an *identical* address to a pending `DeployAccount` transaction with the same parameters: [2](#0-1) 

Deployment write-once semantics are enforced purely by checking whether the target address already has a non-default class hash: [3](#0-2) 

If an attacker observes a pending `DeployAccount` transaction (its `contract_address_salt`, `class_hash`, and `constructor_calldata` are all plaintext, public fields) and submits an ordinary `invoke` transaction that triggers the `deploy` syscall with the identical parameters and gets it sequenced first, the target address becomes populated. When the original `DeployAccount` transaction subsequently executes, `execute_deployment` observes a non-default `class_hash_at` and fails with `StateError::UnavailableContractAddress`, which propagates as a hard constructor-execution failure: [4](#0-3) 

There is no protection in gateway validation against this: `validate_nonce` only checks that the sender's nonce is still zero and the transaction's nonce is zero — it does not (and cannot, statelessly) detect that a colliding deployment is already in-flight in another transaction: [5](#0-4) 

### Impact Explanation
Because `contract_address_salt`, `class_hash`, and `constructor_calldata` are fixed at the address the user chose (frequently a *counterfactual* address that has already been pre-funded, e.g. bridge deposits or paymaster-sponsored account-abstraction flows), an attacker's front-run occupies that exact address permanently for that (salt, class_hash, calldata) triple — the legitimate `DeployAccount` transaction can never succeed there. The victim is forced to abandon the address and redeploy with a new salt, mirroring the reported impact of "permanently dossed, forcing redeployment." Any funds or off-chain expectations tied to the specific precomputed address (counterfactual funding, cross-chain deposit routing) are disrupted, and applications that rely on address-stability for AA flows lose the ability to complete the intended deployment. This is a Medium-severity denial-of-service on a specific account's deployment path, reachable by any unprivileged transaction sender with no special mempool, prover, or operator privileges.

### Likelihood Explanation
Exploitation only requires: (1) observing a pending `DeployAccount` transaction in the public mempool/gossip layer (all its address-determining fields are unencrypted), and (2) submitting a cheap `invoke` transaction that calls into any contract exposing a generic deploy-forwarding entry point (a common pattern, analogous to Ethereum's Universal Deployer Contract on Starknet) with the same `class_hash`/`salt`/`calldata` and `deploy_from_zero=true`. No special access or timing beyond ordinary transaction submission and fee competition is needed, making this straightforward for any adversarial network participant to attempt whenever a high-value counterfactual account deployment is anticipated.

### Recommendation
Consider whether counterfactual account deployment flows that rely on a fixed, attacker-computable address should be hardened, e.g. by binding `DeployAccount` address computation to the transaction's own signature/hash or another value the deployer cannot replicate from public mempool data, or by having the gateway/mempool treat pending `DeployAccount` transactions and any conflicting `deploy` syscall invocations targeting the same computed address as mutually exclusive at admission/ordering time so the legitimate deployer's transaction is prioritized.

### Proof of Concept
1. Alice submits a `DeployAccount` V3 transaction with `class_hash = C`, `contract_address_salt = S`, `constructor_calldata = D`; the resulting deterministic address is `calculate_contract_address(S, C, D, ContractAddress::ZERO)` per `crates/starknet_api/src/transaction.rs:459-473`.
2. Bob observes Alice's pending transaction in the mempool/p2p layer and computes the same address off-chain.
3. Bob submits an `invoke` transaction from his own already-deployed account calling a contract that performs `deploy_syscall(class_hash=C, contract_address_salt=S, calldata=D, deploy_from_zero=true)`, matching `crates/blockifier/src/execution/syscalls/syscall_base.rs:400-410`.
4. If Bob's transaction is included in a block before Alice's, `execute_deployment` in `crates/blockifier/src/execution/execution_utils.rs:337-356` writes the class hash at that address.
5. When Alice's `DeployAccount` transaction later executes, the same check finds `current_class_hash != ClassHash::default()` and fails with `StateError::UnavailableContractAddress`, exactly as demonstrated in the existing regression test at `crates/blockifier/src/transaction/transactions_test.rs:2312-2338`, permanently preventing Alice's account from being deployed at that address.

    /// Calculates the contract address for the contract deployed by a deploy account transaction.
    /// For more details see:
    /// <https://docs.starknet.io/learn/cheatsheets/transactions-reference#deploy-account-v3>
    fn calculate_contract_address(&self) -> StarknetApiResult<ContractAddress> {
        // When the contract is deployed via a deploy-account transaction, the deployer address is
        // zero.
        const DEPLOYER_ADDRESS: ContractAddress = ContractAddress(PatriciaKey::ZERO);
        calculate_contract_address(
            self.contract_address_salt(),
            self.class_hash(),
            self.constructor_calldata(),
            DEPLOYER_ADDRESS,
        )
    }
