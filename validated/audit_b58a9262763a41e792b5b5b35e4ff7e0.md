### Title
`ensureOfflineTokenIsNotExpired` ignores `storeSession` failure after refreshing an offline token, leaving stale/consumed refresh tokens persisted and causing permanent auth DoS - ([File: packages/apps/shopify-app-remix/src/server/helpers/ensure-offline-token-is-not-expired.ts])

### Summary
`ensureOfflineTokenIsNotExpired` mirrors the Sherlock `updateYieldStrategy` bug class: it performs an external, one-shot state-consuming operation (exchanging the refresh token for a new access token) and then *unconditionally* treats the operation as fully committed, without verifying that the resulting new state (the new session) was actually persisted before the old state (the old refresh token) becomes unusable.

### Finding Description
When an offline access token is close to expiry and `expiringOfflineAccessTokens` is enabled, `ensureOfflineTokenIsNotExpired` calls `refreshToken(...)`, which invokes `api.auth.refreshToken` and performs the OAuth `refresh_token` grant against Shopify [1](#0-0) . That call exchanges the shop's current refresh token for a brand-new access token/refresh token pair, exactly as implemented in `refreshToken` [2](#0-1) .

Immediately after the exchange succeeds, the helper calls `await config.sessionStorage!.storeSession(offlineSession)` and returns the new session unconditionally, without checking the boolean result of `storeSession` [3](#0-2) . Per the `SessionStorage` contract, `storeSession` is explicitly documented to return `false` on failure rather than throw [4](#0-3) , and adapter implementations (e.g. the CSV example, custom DB adapters) do exactly that on write errors [5](#0-4) .

This is structurally identical to the Sherlock finding: `withdrawAll` (here, the refresh-token exchange) is assumed to fully "commit" the switch, and the code unconditionally proceeds to treat the new state as authoritative (here, returning/using the new in-memory session) without confirming that the durable link (persisted session storage) was actually updated. The identical pattern exists in the Express and React Router variants of this helper [6](#0-5) [7](#0-6) .

### Impact Explanation
OAuth `refresh_token` grants are one-shot/rotating: using a refresh token typically invalidates it and issues a new one. If `storeSession` silently fails (returns `false`) after a successful refresh:
- The current request succeeds using the new in-memory session, masking the failure.
- The persisted session in storage still contains the **old, now-consumed** refresh token and the old, expiring/expired access token.
- Every subsequent request for that shop loads the stale persisted session, sees it is expired, and attempts to refresh again using the already-consumed refresh token, which will be rejected by Shopify.
- The shop's offline session becomes permanently unusable for API calls until the merchant re-installs/re-authenticates, constituting a denial of service against the auth handler for that tenant — this is scoped per-shop and reachable purely through normal, unprivileged request traffic (any authenticated request that happens to trigger the refresh path).

This matches the "worst case scenario" language from the original report: a broken link between the current record (session storage) and the actual live credential state, requiring an out-of-band recovery action (full re-auth) to fix.

### Likelihood Explanation
This requires a transient session-storage write failure (e.g., DB connection blip, disk/quota, HA failover) to coincide with a token refresh window, which is plausible in production for any of the network-backed storage adapters (MySQL, Postgres, MongoDB, Redis, DynamoDB, KV) shipped in this monorepo — none of which are guaranteed to always succeed. The lack of a check on `storeSession`'s return value means the library has no fallback/retry/alerting path for this scenario, so the “rough handling” described by the original judge applies directly here.

### Recommendation
- Check the boolean return value of `storeSession` in `ensureOfflineTokenIsNotExpired` (all three implementations: shopify-app-remix, shopify-app-react-router, shopify-app-express).
- If persistence fails, do not silently proceed as if the refresh committed; retry the store, or throw/log a distinguishable error so callers can react (e.g. surface a 5xx and avoid using the freshly obtained token if it cannot be durably recorded), and/or avoid discarding the old session's usability assumptions until the store is confirmed.
- Consider making `storeSession` failures visible to library consumers (e.g., via a callback or thrown error) rather than a boolean the internal helpers ignore.

### Proof of Concept
1. Enable `expiringOfflineAccessTokens` and configure any network-backed `SessionStorage` (e.g., Postgres/Redis).
2. Let a shop's offline session approach expiry with a valid `refreshToken`.
3. Trigger a request that hits `ensureOfflineTokenIsNotExpired`; `refreshToken(...)` succeeds and Shopify issues a new access/refresh token pair (consuming the old refresh token) [8](#0-7) .
4. Simulate `config.sessionStorage.storeSession(offlineSession)` returning `false` (e.g., transient DB outage) — the helper does not check this and returns the new session for the current request only [3](#0-2) .
5. On the next request, the loaded session is still the old, expired one with the now-invalidated refresh token; the refresh attempt against Shopify fails with `invalid_grant`, and the shop is stuck needing full re-authentication — reproducing the "frozen funds until back-and-forth switch" scenario from the original report in the auth-token domain.

```typescript
export async function ensureOfflineTokenIsNotExpired(
  session: Session,
  params: BasicParams,
  shop: string,
) {
  const {config} = params;
  if (
    config.future?.expiringOfflineAccessTokens &&
    session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY) &&
    config.distribution !== AppDistribution.ShopifyAdmin &&
    session.refreshToken
  ) {
    const offlineSession = await refreshToken(
      params,
      shop,
      session.refreshToken,
    );

    await config.sessionStorage!.storeSession(offlineSession);
    return offlineSession;
  }
```

```typescript
export function refreshToken(config: ConfigInterface): RefreshToken {
  return async ({shop, refreshToken}: RefreshTokenParams) => {
    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      refresh_token: refreshToken,
      grant_type: RefreshTokenGrantType,
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
  };
```
