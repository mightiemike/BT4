## Title
Stale session object written back to session storage on token-exchange failure can silently destroy a concurrently-established valid session (TOCTOU race in `invalidateAccessToken`) - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
`performTokenExchange()` loads a session from storage at the start of a request, keeps a reference to it (`sessionToInvalidate`), and — if the subsequent token-exchange call to Shopify later fails with a 401 — unconditionally writes that *stale, pre-exchange* session object back into `sessionStorage` with its `accessToken` cleared. Because `storeSession()` is a blind upsert keyed only by session id, this stale write can overwrite a session that a **concurrent** request has since replaced with a fresh, valid one, destroying that other request's valid access token/session state without ever re-checking what is currently stored.

### Finding Description
In `performTokenExchange`: [1](#0-0) 

`session` (and thus `sessionToInvalidate`) is loaded once, early in the request, keyed by a session id that is shared across all requests for the same shop/user (`getOfflineId(shop)` for offline tokens, or `getJwtSessionId(shop, sub)` for online tokens): [2](#0-1) 

If the session is not active, the middleware calls out to Shopify's token-exchange endpoint (`exchangeToken`), an operation that can take time and can fail: [3](#0-2) 

If that call throws an `HttpResponseError` with code 401, the middleware calls `invalidateAccessToken(sessionToInvalidate, config)`: [4](#0-3) 

`invalidateAccessToken` then clears `accessToken` on the **original, pre-exchange** `Session` object and unconditionally stores it, overwriting whatever is currently in storage for that session id: [5](#0-4) 

All `SessionStorage` implementations perform a blind upsert keyed by `session.id` with no optimistic-concurrency / "still the current session" check, e.g. the in-memory adapter: [6](#0-5) 

and the same unconditional-upsert pattern in the SQL/Mongo/Redis/DynamoDB adapters (`ON DUPLICATE KEY UPDATE` / `ON CONFLICT DO UPDATE` / `findOneAndReplace` / `PutItemCommand`, all keyed solely by `id`).

This is structurally the same bug class as the reported `withdrawNftWithInterest()` issue: an action (deleting/overwriting a shared resource keyed by an id) is performed based on a state snapshot taken earlier ("the NFT is currently in the contract" / "this is the session I loaded"), without re-validating that the snapshot still reflects the resource's current, authoritative state before mutating/destroying it.

### Impact Explanation
Multiple concurrent requests for the same shop (e.g., two embedded-app tabs, retried fetches, or an app-proxy/webhook path racing with a UI request) can interleave as follows:
1. Request A loads the (expired/inactive) session for shop `S`, keeps a reference (`sessionToInvalidate`).
2. Request B, racing concurrently, also loads the inactive session, successfully exchanges it for a fresh, valid access token, and stores the new valid `Session` under the same session id.
3. Request A's own exchange attempt then fails with a 401 (e.g., replayed/expired session token, transient Shopify error, or an attacker deliberately sending an invalid/stale session token to force the 401 path).
4. Request A calls `invalidateAccessToken(sessionToInvalidate, config)`, which stores the **stale pre-exchange session object** with `accessToken = undefined`, clobbering the valid session B just established.

The net effect is a denial-of-service against the authenticated-session handler for that shop: the legitimately re-authenticated session is destroyed, forcing the merchant/app instance to re-authenticate (or looping if the race is repeatable), and potentially discarding a still-valid access token that B's request needed.

### Likelihood Explanation
This requires no special privilege beyond making ordinary authenticated HTTP requests to the app's `authenticate`/token-exchange path — reachable by any embedded app session/tab belonging to a single merchant, and the race window can be widened deliberately by an attacker who controls timing of one of the two concurrent requests (e.g., replaying a stale/invalid session token to force the 401 branch while a legitimate request is in flight). No secrets need to be leaked and no MITM is required; it is a same-endpoint TOCTOU race in the app framework code.

### Recommendation
Before overwriting/invalidating a session in `invalidateAccessToken`, re-load the session from storage and confirm it still matches the access token/session that failed (e.g., compare `accessToken` or another concurrency token) rather than blindly persisting the captured, potentially stale in-memory `Session` object. Alternatively, only clear/delete the specific `accessToken` value that was actually used and failed, using storage-level conditional updates (compare-and-swap) instead of a full unconditional `storeSession` overwrite.

### Proof of Concept
1. Configure `useOnlineTokens: false` (offline session, whose id is shared per shop) and enable token exchange.
2. Fire two concurrent requests for the same shop through `validateWithTokenExchange` → `performTokenExchange`, both hitting the "session not active" branch at once: [7](#0-6) 
3. Let request B complete `exchangeToken` + `storeSession(offlineSession)` successfully first.
4. Force request A's `exchangeToken` call to fail with a 401 `HttpResponseError` (e.g., by supplying a stale/replayed session token for A).
5. Observe that request A's catch handler calls `invalidateAccessToken(sessionToInvalidate, config)` with A's originally-loaded (pre-race) session object, overwriting the session storage entry that B just wrote with a valid token — B's session is now destroyed even though B's exchange succeeded.

```typescript
import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
```
