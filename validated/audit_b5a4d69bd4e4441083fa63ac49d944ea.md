### Title
Failed re-mint during outbound revert permanently freezes bridged funds with no recovery path - (File: x/uexecutor/keeper/outbound.go)

### Summary
When an honest Universal Validator quorum votes that an outbound (`TxType_FUNDS`, `TxType_GAS_AND_PAYLOAD`, or `TxType_FUNDS_AND_PAYLOAD`) failed on the destination chain, `handleFailedOutbound` tries to re-mint the bridged PRC20 back to the user via a single call to `CallPRC20Deposit` → `DerivedEVMCall("depositPRC20Token", ...)` on the `UNIVERSAL_CORE` system contract [1](#0-0) . If that EVM call errors for any reason, the outbound is immediately marked `ABORTED` "for manual intervention" and the function returns, with `VoteOutbound` swallowing the resulting error into a diagnostic `RevertError` field rather than retrying [2](#0-1) [3](#0-2) . This mirrors the Rocket Pool `close()`/`destroyMinipool` bug class: a withdrawal that "should always succeed" for a legitimate user is single-shot-dependent on one external EVM call, with no retry, no fallback, and (as far as could be found) no `MsgServer` message to resolve `ABORTED` outbounds and re-attempt the re-mint.

### Finding Description
`Status_ABORTED` is documented as: "Finalization or revert attachment failed and requires manual intervention" [4](#0-3) . A search of the codebase for a resolution/retry message (`ResolveAborted`, `RetryOutbound`, etc.) turned up no results outside of the definition, tests, and the abort call sites themselves — i.e., no user- or admin-reachable message exists to move an `ABORTED` outbound back into a state where the re-mint is retried. Once `AbortOutbound` fires, the bridged PRC20 (already burned/locked when the original outbound was created) is not re-minted, and the flow stops there permanently [5](#0-4) .

The recipient of the re-mint (`outbound.Sender` or `outbound.RevertInstructions.FundRecipient`) is attacker-controlled input taken directly from the original `UniversalTxOutbound` gateway event / `RevertInstructions` supplied by the depositing user [6](#0-5) . A malformed or otherwise problematic recipient/asset combination that causes `depositPRC20Token` to revert on `UNIVERSAL_CORE` — with no retry logic — converts a transient EVM failure into a **permanent** freeze of the user's own bridged principal, because the single-attempt design has no path back to a working state.

Note: for the auto-generated `INBOUND_REVERT` outbound path (`buildRevertOutbound`), the struct does not populate `Prc20AssetAddr` [7](#0-6) , and `handleFailedOutbound`'s re-mint branch is gated on `TxType_FUNDS`/`TxType_GAS_AND_PAYLOAD`/`TxType_FUNDS_AND_PAYLOAD` only, so `INBOUND_REVERT` does not enter this specific re-mint branch [8](#0-7) . The affected path is specifically the outbound-execution-failure revert for real `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` outbounds created from a PC-side payload's gateway event.

### Impact Explanation
This corresponds to "permanent freezing... of user or protocol-controlled funds" in the allowed impact list. A single failed EVM call on protocol infrastructure (not requiring any governance/privileged action to trigger — any transient revert of `depositPRC20Token`, e.g., due to a PRC20-side condition tied to the recipient address the user themselves supplied) causes user principal that was already locked/burned on the source side to become permanently stuck in `ABORTED` state, since the code path is one-shot with no retry mechanism found in this repository.

### Likelihood Explanation
Likelihood is moderate: it requires the specific EVM call `depositPRC20Token` to fail during outbound finalization, which is not the common case, but the recipient/asset-address fields that feed this call originate from user-supplied `RevertInstructions`/event data set at deposit time, giving an unprivileged user partial influence over whether their own re-mint can be made to fail (and, by extension, whether that failure mode — permanent freeze rather than automatic retry — is exercised).

### Recommendation
Add a retry mechanism (or a permissionless "resolve/retry aborted outbound" message) for `Status_ABORTED` outbounds so the re-mint can be re-attempted after transient failures, consistent with the "always succeed" invariant for user withdrawals. At minimum, follow a `try/catch`-equivalent pattern with automatic re-queuing rather than a terminal `ABORTED` state with no on-chain remediation path, and validate/sanitize the revert-recipient input before it can influence a mint that has no fallback.

### Proof of Concept
Not independently reproduced in this session — full contract-level PRC20/`UNIVERSAL_CORE` behavior (whether `depositPRC20Token` can actually be forced to revert by unprivileged, user-supplied recipient input) and the exhaustive message-server surface (to confirm no retry/resolve message exists anywhere in the repo) could not be fully verified within the available tool budget. A Devin session with full repository/build access should: (1) grep the entire `x/uexecutor` `MsgServer` and CLI for any `ABORTED`-resolution message; (2) inspect the `UNIVERSAL_CORE`/PRC20 Solidity contracts for `depositPRC20Token` revert conditions reachable via attacker-controlled recipient/amount; and (3) write an integration test that forces `CallPRC20Deposit` to fail during `handleFailedOutbound` and confirm the outbound is stuck in `ABORTED` indefinitely.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}

func (k Keeper) handleFailedOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	// Only revert bridged funds for funds-related tx types
	if outbound.TxType == types.TxType_FUNDS || outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
		outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD {

		// Decide revert recipient safely
		recipient := outbound.Sender
		if outbound.RevertInstructions != nil &&
			outbound.RevertInstructions.FundRecipient != "" {
			recipient = outbound.RevertInstructions.FundRecipient
		}

		amount := new(big.Int)
		amount, ok := amount.SetString(outbound.Amount, 10)
		if !ok {
			return fmt.Errorf("invalid amount: %s", outbound.Amount)
		}
		receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)
