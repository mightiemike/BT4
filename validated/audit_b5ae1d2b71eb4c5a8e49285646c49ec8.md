### Title
Unbounded attacker-controlled array length in deprecated (Cairo0) syscall parsing enables memory amplification DoS - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The MessagePack.NET advisory's root cause — allocating/reading a collection whose size is taken directly from an untrusted, attacker-declared length field before validating that the underlying data actually exists — has a structural analog in the Cairo0 (deprecated) syscall request parsing path of `blockifier`. `read_felt_array` reads a raw `Felt` as the declared array size directly from VM memory that the calling contract fully controls, converts it to `usize`, and immediately forwards it to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` to materialize a `Vec<Felt>` of that length — with no bound check against any resource/gas-proportional limit before the read/allocation is attempted.

### Finding Description
`read_felt_array` in the deprecated syscalls hint processor: [1](#0-0) 

reads `array_size` as a raw `Felt` written by the executing (attacker-supplied) Cairo0 contract into its own VM memory immediately before invoking a syscall such as `call_contract`, `library_call`, `emit_event`, or `send_message_to_l1` — this value is unconstrained by any prior validation. It is converted to `usize` and passed straight into `felt_range_from_ptr`: [2](#0-1) 

which calls `vm.get_integer_range(ptr, size)` — a call into the external `cairo-vm` crate that attempts to materialize/read `size` `Felt` values (32 bytes each) before it can determine whether the backing memory actually contains that many elements. Callers such as `read_calldata`/`read_call_params` in the same file (used by `CallContractRequest`, `LibraryCallRequest` in `crates/blockifier/src/execution/deprecated_syscalls/mod.rs`) and `EmitEventRequest`'s `keys`/`data` parsing invoke this helper directly, and any size/gas-proportional validation (e.g. `exceeds_event_size_limit`) is only applied *after* the array has already been read/allocated — mirroring the report's pattern where a header-declared count is trusted for allocation before the corresponding data is verified to exist.

Unlike the newer (Cairo1) syscall path (`crates/blockifier/src/execution/syscalls/hint_processor.rs:860-880`), where array size is derived from the difference between two `Relocatable` pointers that must have actually been produced by real Cairo1 array-construction code (bounded by the transaction's step/gas budget), the deprecated path lets the contract write an arbitrary raw `Felt` value as the "size" with a single memory-store instruction, completely decoupling the declared size from any proportional cost — the same "cheap header, expensive allocation" asymmetry described in the report.

### Impact Explanation
Because Cairo0 classes remain declarable and invokable on Starknet (`DeclareTransaction::V0/V1`, `DeprecatedContractClass` handling is still present, e.g. `crates/apollo_http_server/src/deprecated_gateway_transaction.rs`, `crates/starknet_api/src/serde_utils.rs`), any account can declare and invoke a Cairo0 contract that issues a syscall (`call_contract`, `library_call`, `emit_event`, `send_message_to_l1`) with a maliciously large declared `calldata_size`/`keys_len`/`data_len`, forcing the sequencer's blockifier to attempt a large `Vec<Felt>` allocation/read during transaction execution. Repeated or single large-enough payloads can induce severe GC/allocator pressure or `OutOfMemoryException`-equivalent aborts in the sequencer process executing the block, degrading availability of the node processing transactions — consistent with the "Medium" severity and CWE-405 classification of the original report.

### Likelihood Explanation
Exploitation only requires declaring/using a Cairo0 contract and invoking one of the affected deprecated syscalls with a single crafted memory write establishing an oversized declared length — no special privileges, no proposer/operator control, and no network-level access beyond normal transaction submission are required. This is reachable purely from a single submitted transaction executing untrusted Cairo0 bytecode in the blockifier, which is squarely within the sequencer's transaction-execution attack surface.

### Recommendation
Bound the declared `array_size` in `read_felt_array` (deprecated syscalls) against a sane maximum (e.g., derived from remaining gas/step budget or a hard protocol constant) before calling `felt_range_from_ptr`/`vm.get_integer_range`, mirroring the protective pattern already used in `crates/apollo_cairo_utils/src/lib.rs` (`TryFrom<Retdata> for CairoArray<T>`), which explicitly validates that a declared element count does not exceed the number of remaining Felts before calling `Vec::with_capacity`. Apply the same "validate declared length against available/charged resources before allocating" check to all deprecated syscall array-reading paths (`read_calldata`, `EmitEventRequest::read`, `SendMessageToL1Request::read`).

### Proof of Concept
Conceptual PoC (cannot be executed without live infra access):
1. Compile and declare a Cairo0 contract whose entry point, before calling `emit_event` (or `call_contract`/`library_call`), writes an arbitrarily large raw felt (e.g., `2**40`) into the memory slot that Cairo0's syscall ABI treats as `keys_len` (or `calldata_size`), instead of a value matching real written data.
2. Submit an `INVOKE` transaction that calls this entry point.
3. During blockifier execution, `EmitEventRequest::read` → `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-949`) reads the huge declared size and calls `felt_range_from_ptr(vm, ptr, size)` (`crates/blockifier/src/execution/execution_utils.rs:228-237`) → `vm.get_integer_range`, attempting to read/allocate the declared number of `Felt`s before any size-limit check (`exceeds_event_size_limit`) is applied, causing large memory pressure or failure in the sequencer process handling the transaction.

Note: I could not verify the internal allocation strategy of the external `cairo-vm` crate's `get_integer_range` (e.g., whether it preallocates a `Vec::with_capacity(size)` before validating cell existence), since that implementation lives outside this repository; this is the main uncertainty in confirming the exact allocation amplification factor.

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
```

```rust
pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
```
