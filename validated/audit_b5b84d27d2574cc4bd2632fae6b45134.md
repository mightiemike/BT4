## Analysis

CVE-2018-18701 is a stack-exhaustion bug caused by **unbounded recursion over an attacker-influenced nested structure** (`cplus_demangle_type`/`next_is_type_qual` recursing on nested C++ type mangling). The closest reachable analog in this sequencer is unbounded recursion over the **bytecode-segment tree** (`NestedIntList` / `BytecodeSegmentNode`) that is derived from a user-declared Sierra→CASM contract class, walked without any depth bound both when the gateway computes the compiled-class hash and when the Starknet OS/prover re-executes a `Declare` transaction.

### Title
Unbounded recursion over attacker-controlled CASM bytecode-segment tree causes stack exhaustion in compiled-class hashing and OS re-execution - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs, crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs)

### Summary
`CasmContractClass::hash()` and the Starknet-OS bytecode-segment-structure builder both walk the compiler-produced `bytecode_segment_lengths` (`NestedIntList`) tree with plain, depth-unbounded recursion. The nesting depth of this tree is driven by the nested-scope/branch structure of the Sierra program the caller declares, so a single crafted `Declare` transaction can make this recursion arbitrarily deep, exhausting the real call stack of the gateway process and/or the OS/prover re-execution process — a stack-consumption denial of service, matching the CVE-2018-18701 bug class.

### Finding Description
When a class is declared, `SierraCompiler::compile` runs the Sierra→CASM compiler in a resource-limited subprocess, then, **in the caller's own process** (not resource-limited), immediately computes the compiled-class hash: [1](#0-0) 

That hash computation calls `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash` → `bytecode_hash_node`, which recurses over the `NestedIntList` children with **no depth check whatsoever**: [2](#0-1) 

The `NestedIntList` is taken directly from `CasmContractClass.bytecode_segment_lengths`, which is populated by the compiler based on the nested control-flow/scope structure of the declared Sierra program: [3](#0-2) 

The same unbounded-recursion pattern exists on the Starknet-OS / re-execution side, used when validating declared classes during block re-execution/proving. `create_bytecode_segment_structure_inner` recurses over the same `NestedIntList` with no depth guard: [4](#0-3) 

and `BytecodeSegmentNode::hash` recurses again over the resulting tree, also without a depth bound: [5](#0-4) 

This is invoked from the OS hint that processes every declared compiled class during transaction re-execution: [6](#0-5) 

By contrast, other recursive/DoS-prone paths in this codebase are explicitly guarded — e.g. Cairo call recursion is bounded by a `RecursionDepthGuard`/`max_recursion_depth`, and Cairo Native execution pre-allocates a bounded stack sized to the gas limit: [7](#0-6) [8](#0-7) 
No equivalent guard protects the bytecode-segment recursion, and unlike Cairo-VM execution (which is metered per Cairo step), this recursion happens in native Rust code, outside of any gas/step accounting, so the attacker's recursion cost is not charged or bounded by resource bounds at all.

Elsewhere in `blockifier`, a similar nested structure walk explicitly documents (and asserts) that it only expects a segmentation depth of at most 1, implying the code owners' own assumption is that this tree should be shallow — an assumption that is not actually enforced when the tree is built: [9](#0-8) 

### Impact Explanation
An attacker who submits a single, otherwise-valid `Declare` transaction whose Sierra program compiles to a CASM class with a deeply nested bytecode-segment tree can trigger unbounded native-stack recursion in:
1. The gateway process, immediately after Sierra→CASM compilation, while computing `executable_class_hash` — outside the subprocess sandbox and its CPU/memory limits, and before any per-step gas metering applies.
2. Every sequencer/prover node that re-executes the block containing the `Declare` (Starknet OS re-execution), via `create_bytecode_segment_structure_inner` and `BytecodeSegmentNode::hash`.

A real stack overflow in Rust aborts the process (SIGSEGV/abort), not a catchable panic, so this can crash gateway worker threads/processes handling transaction submission and/or the OS/prover process responsible for producing the block's proof — a network-wide denial of service on the ability to admit or confirm new transactions/blocks, consistent with the "network unable to confirm new transactions" impact category.

### Likelihood Explanation
Likelihood is Medium: it requires only a single unprivileged `Declare` transaction from any contract deployer, no special privileges, no cooperation from other nodes. The attacker needs to craft a Sierra/Cairo1 program whose compiled bytecode naturally segments into a deeply nested tree (e.g., via many nested function scopes/branches) while staying within `max_bytecode_size`; this is a compiler-driven, deterministic and reproducible construction rather than a probabilistic attack, but it does require some reverse-engineering of how the CASM compiler assigns segment nesting to find an efficient nesting-depth-per-byte ratio.

### Recommendation
- Convert `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs`) and `create_bytecode_segment_structure_inner` / `BytecodeSegmentNode::hash` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`) from recursive to iterative (explicit stack/queue) traversals, eliminating dependence on the native call stack.
- Alternatively/additionally, validate and reject `bytecode_segment_lengths` trees whose nesting depth exceeds a small, explicit maximum (mirroring the `segmentation_depth <= 1` assumption already present in `blockifier`'s `NestedFeltCounts`) as part of class validation, before hashing or OS re-execution, returning a proper compilation/validation error instead of allowing unbounded recursion.
- Apply the same stack-size/resource-limit discipline used for Cairo Native execution (pre-allocated bounded stack) to any remaining recursive traversal of compiler-controlled structures that run in the gateway/OS host process.

### Proof of Concept
1. Write a Cairo1 contract whose Sierra program contains many (e.g. tens of thousands of) nested scopes/branches designed to make the Sierra→CASM compiler emit a deeply and linearly nested `bytecode_segment_lengths: NestedIntList::Node(vec![NestedIntList::Node(vec![...])])` tree, while keeping total CASM bytecode size under `DEFAULT_MAX_BYTECODE_SIZE`.
2. Compile locally with the pinned `cairo-lang` compiler used by `apollo_compile_to_casm` and confirm (e.g. via debug print) that `CasmContractClass.bytecode_segment_lengths` has nesting depth proportional to N.
3. Submit the class via a normal `Declare` (v3) transaction to a gateway node.
4. Observe that `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:69`) calling `executable_class.hash(&HashVersion::V2)` recurses to depth N in `bytecode_hash_node`, and, if the block containing the declare is re-executed by the Starknet OS, that `create_bytecode_segment_structure_inner`/`BytecodeSegmentNode::hash` reproduce the same unbounded recursion — crashing the process with a stack overflow once N exceeds the thread's stack budget.

```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```

```rust
pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
```

```rust
// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
```
