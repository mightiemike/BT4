**Analysis:**

The `collect` closure in `do_state_checkpoint.rs` iterates transactions `i` over the range in increasing (deterministic, consensus-ordered) index order, and for each transaction's `write_set().native_position_iter()`, calls `latest.insert(key.hash(), PositionSlot { ..., value_hash, ... })` [1](#0-0) . `HashMap::insert` overwrites any prior entry for the same `key.hash()`, so after the loop completes, the surviving `PositionSlot.value_hash` for any key is always the one from the highest-index transaction in the range that touched that key — i.e., the last write in program order. This is the explicitly documented design: "Collapse position writes (latest-per-key) over a version range into SMT leaf updates" [2](#0-1) .

Two structural facts prevent the described attack:

1. **No intra-transaction duplication is possible.** A single transaction's native-position writes are stored as `Extension::NativePosition(BTreeMap<StateKey, NativePositionOp>)` [3](#0-2) , and `add_native_positions` asserts the extension is installed only once [4](#0-3) . Since it's a `BTreeMap` keyed by `StateKey`, a single transaction cannot contain two conflicting ops (e.g., a `None` deletion interleaved with a `Some` value) for the same key — there is exactly one `WriteOp` per key per transaction.

2. **Cross-transaction ordering is not attacker-controlled beyond normal execution order.** The range `i` in `collect(range)` walks `execution_output.to_commit.transaction_outputs` in block/consensus execution order, which is identical and deterministic across all validators. Because `HashMap::insert` always keeps the most-recently-inserted value for a key, the last op in program order — not an "attacker-preferred earlier one" — is exactly what determines the final `value_hash` fed into `PositionStateWithSummary::extend` → `ShardedJmtState::extend` (SMT leaf update) [5](#0-4) .

This same "latest-wins-per-key via `HashMap::insert` in ascending index order" pattern is used consistently in the related code paths — `position_summary_at_commit` in `aptosdb_writer.rs` [6](#0-5)  and `replay_position_after_snapshot` in `aptosdb_native_position.rs` [7](#0-6)  — so all nodes (execution pipeline, commit path, and restore/replay path) independently converge on the identical, correctly-ordered `value_hash`, preserving deterministic proof binding as required.

The proof idea in the question describes exactly the intended and verified behavior (last write in program order survives), not a deviation from it. There is no code path by which an attacker's write op can be reordered ahead of a later op in the same range, nor duplicate a key within one transaction's write set.
