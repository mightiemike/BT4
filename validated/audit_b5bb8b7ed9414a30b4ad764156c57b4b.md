### Title
Stale `cycle-total-weight` cache in `signers-voting.clar` lets aggregate-key vote consensus be evaluated against the wrong signer weight - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`signers-voting.clar` caches the total signer weight for a reward cycle the first time any signer votes, and never invalidates that cache if the underlying `.signers` contract's `cycle-signer-set` for that same reward cycle is later (re)written with a different signer set/weight distribution. This is the same bug class as the RCTreasury `payout` finding: an action that changes underlying eligibility/weight state (`set-signers`) does not propagate to a dependent cached flag (`cycle-total-weight`), so consensus/threshold logic keeps using stale data.

### Finding Description
`get-and-cache-total-weight` in `signers-voting.clar` reads `cycle-total-weight` for a `reward-cycle`; if present it returns the cached value unconditionally, otherwise it sums weights from `.signers::get-signers` and caches the sum: [1](#0-0) 

This cache is consulted by `vote-for-aggregate-public-key`, which uses `get-threshold-weight` (derived from the same cached `cycle-total-weight`) to decide whether the tally has reached consensus: [2](#0-1) [3](#0-2) 

Meanwhile, the underlying `.signers` contract's `cycle-signer-set` map for a given `reward-cycle` is written by `set-signers`, which only checks that `last-set-cycle` matches the target cycle — it does not forbid being called a second time for the same cycle with a different signer list/weights, and it performs no invalidation of any consumer's cache: [4](#0-3) 

On the Rust side, the reward set (and hence the signer list/weights written via `set-signers`) for a given reward cycle can legitimately be (re)computed and (re)written more than once for the *same* `reward_cycle` number: the coordinator explicitly handles the case where a PoX anchor block was first `SelectedAndUnknown` and only later becomes known, at which point it "needs to update the sortition DB with the newly-processed reward set" — i.e., the reward set for a cycle is not fixed permanently at first computation: [5](#0-4) 

`pox_5_compute_and_update_signers` / `pox_4_compute_and_update_signers` are the Rust entry points that call into `.signers::set-signers` (via `update_signers`) with the freshly computed weight list for a reward cycle: [6](#0-5) [7](#0-6) 

If any signer casts a vote for the aggregate public key of a not-yet-finalized reward cycle before the reward set is finalized/rewritten (e.g. during a burnchain reorg that changes which stackers/participation counted for that cycle, or any repeated recomputation of `set-signers` for the same cycle number), `cycle-total-weight` gets cached against the *old* signer weight total. Any subsequent overwrite of `cycle-signer-set` via `set-signers` for that same cycle is invisible to `signers-voting.clar` — the map is never re-derived. From that point on, `get-threshold-weight`/`vote-for-aggregate-public-key` compute and check consensus against a weight base that no longer matches the actual (post-update) signer set for the cycle. This breaks the intended equality: *aggregate-key consensus threshold == 80% of the real, currently-configured signer weight for the reward cycle*.

### Impact Explanation
This falls squarely into the allowed impact class "a minority-triggerable sortition/VRF/static-validation divergence" / "signer weight below threshold or from the wrong set." Because `cycle-total-weight` is derived from whichever signer-set snapshot happened to exist at the moment the first vote for that cycle was cast, two nodes that observed the burnchain in a different order around a reorg (or around the anchor-block-becomes-known transition) could each cache a different `cycle-total-weight` for the same `reward-cycle`, and therefore reach different verdicts about whether the same set of votes crosses the 80% consensus threshold for the aggregate public key. A materially wrong (too-low) cached total-weight could let a genuine minority of the real signer set unilaterally "confirm" an aggregate public key, since `votes-weight >= threshold-weight` is checked against the stale, smaller total. This directly threatens the "signer weight" invariant the voting contract exists to enforce, with downstream effects on which aggregate key is accepted for the cycle's block signing/verification — a High-impact divergence bounded to the affected reward cycle rather than causing an outright chain split, matching the reward-mispayment/temporary-disagreement severity tier.

### Likelihood Explanation
This requires no majority collusion and no privileged access: any ordinary path that causes the reward set for a given `reward_cycle` to be computed/written to `.signers` more than once (the explicit "anchor block becomes known after being unknown" re-store path documented in the coordinator, or any burnchain-reorg-driven re-derivation of the prepare-phase reward set) combined with at least one signer voting before the final rewrite is sufficient to desynchronize the two contracts' views of "total weight." Because `signers-voting.clar` never re-derives or invalidates `cycle-total-weight`, the staleness is permanent for that cycle once triggered, making the likelihood moderate-to-high for any deployment where anchor-block-unknown-at-first or burnchain reorgs are not vanishingly rare.

### Recommendation
- Invalidate (`map-delete`) `cycle-total-weight` for a `reward-cycle` whenever `.signers::set-signers` is called again for that same cycle, or
- Have `signers.clar`'s `set-signers` reject being called twice for a cycle once any vote has been cast for it (cross-contract check), or
- Have `signers-voting.clar` recompute total weight from `.signers` on every threshold check instead of caching it, accepting the extra read cost, or at minimum re-validate the cached total against the current `.signers` state before using it to gate consensus.

### Proof of Concept
1. Reward cycle `N`'s PoX anchor block is initially `SelectedAndUnknown`; the reward-set computation writes an initial (possibly empty/partial) signer set for cycle `N` via `set-signers`.
2. A signer calls `vote-for-aggregate-public-key` for cycle `N` before the anchor block is fully known; `get-and-cache-total-weight` computes and caches `cycle-total-weight[N]` from this initial, smaller signer set.
3. The anchor block for cycle `N` becomes known; per the coordinator's documented "need_to_store" path, the reward set is recomputed and `set-signers` is called again for cycle `N`, this time with the full, larger, correct signer set and weights (`stackslib/src/chainstate/coordinator/mod.rs:818-844`, `stackslib/src/chainstate/nakamoto/signer_set.rs:699-776`).
4. `signers-voting.clar`'s `cycle-total-weight[N]` is never updated to reflect the new, larger total.
5. Further votes for cycle `N` are now checked against `get-threshold-weight` computed off the stale (smaller) total, so a minority of the *real* signer set can reach `votes-weight >= threshold-weight` and finalize an aggregate public key that does not actually represent 80% of the cycle's true signer weight.

            clarity,
            reward_cycle,
            &signer_set,
            signers_contract,
            signer_set.len() > 0,
            coinbase_height,
            is_mainnet,
