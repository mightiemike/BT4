### Title
`set-pause-liquidation` never clears the manual pause flag when unpausing, permanently freezing liquidations - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`set-pause-liquidation` is implemented as a single conditional that, on the "unpause" transition, only advances the grace-period clock and skips the mutation that actually clears the `pause-liquidation` state variable. Once the protocol has been paused once, the manual-pause flag can never be reset back to `false`, so `liquidation-paused` (which ORs the manual flag with the grace-period check) returns `true` forever, permanently disabling liquidations.

### Finding Description
The pause/grace-period logic is: [1](#0-0) 

```clarity
(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (if (and was-paused (not paused))
        ;; When unpausing, set grace period
        (var-set liquidation-grace-end 
                 (+ stacks-block-time grace-period))
        (var-set pause-liquidation paused))))

(define-read-only (liquidation-paused)
  (let ((manual-pause (var-get pause-liquidation))
        (grace-active (< stacks-block-time 
                         (var-get liquidation-grace-end))))
    (or manual-pause grace-active)))
```

The same identifiers (`set-pause-liquidation`, `pause-liquidation`, `liquidation-grace-end`) are present with the identical match count in the production contract: [2](#0-1) 

Walking through the branches:
1. Admin calls `set-pause-liquidation(true, _)` while unpaused → `was-paused = false` → the `if` takes the else branch → `(var-set pause-liquidation true)`. Protocol is now paused.
2. Admin later calls `set-pause-liquidation(false, grace-period)` to unpause → `was-paused = true`, `paused = false` → `(and was-paused (not paused))` is `true` → the *then* branch executes, which **only** does `(var-set liquidation-grace-end (+ stacks-block-time grace-period))`. It never calls `(var-set pause-liquidation false)`.
3. `pause-liquidation` therefore remains `true` forever after step 1. Every subsequent call to `set-pause-liquidation` with `paused=false` will again observe `was-paused = true` (since it was never cleared) and take the same then-branch, resetting the grace-period clock but never clearing the flag.
4. `liquidation-paused` computes `(or manual-pause grace-active)`; since `manual-pause` is permanently `true`, the result is permanently `true` regardless of the grace period elapsing.

This is the same underlying bug class as the external report: a value assumed to reflect a transition (the sentinel/flag) is used in a downstream decision (`liquidation-paused`) without being invalidated/updated along the one code path that was supposed to update it — the mutation that “de-activates” a stateful flag is skipped on the very branch that is triggered specifically to deactivate it.

### Impact Explanation
Once the DAO pauses liquidations even once, there is no code path that can ever set `pause-liquidation` back to `false`. `liquidation-paused` gates the `liquidate` / `liquidate-multi` / `liquidate-redeem` entry points, so all liquidations become permanently disabled. Underwater positions can never be liquidated, collateral backing bad debt is permanently frozen from being seized/repaid, and the protocol accrues unrecoverable insolvency risk as bad debt grows unchecked. This falls under the in-scope Critical impact class: protocol insolvency / permanent freezing of funds (locked collateral that can never be liquidated).

### Likelihood Explanation
Reaching this state requires only one legitimate use of the intended pause/unpause workflow: pause once, then attempt to unpause. This is a normal operational action (e.g., pausing during an oracle incident or exploit response), not an attack requiring privilege escalation, so the likelihood of triggering it is high whenever the pause feature is used as documented.

### Recommendation
Rewrite `set-pause-liquidation` so the flag mutation and the grace-period mutation are independent, unconditional writes based on the input `paused` value, e.g.:
```clarity
(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (var-set pause-liquidation paused)
    (if (and was-paused (not paused))
        (var-set liquidation-grace-end (+ stacks-block-time grace-period))
        true)
    (ok true)))
```
This ensures `pause-liquidation` is always updated to the caller's intended value while still setting the grace-period clock only on the pause→unpause transition.

### Proof of Concept
1. DAO calls `set-pause-liquidation(true, u0)` → `pause-liquidation` becomes `true`.
2. DAO calls `set-pause-liquidation(false, u100)` intending to resume liquidations after a 100-second grace period → `liquidation-grace-end` is set to `stacks-block-time + 100`, but `pause-liquidation` remains `true`.
3. After 100+ seconds pass, `liquidation-paused` still evaluates `manual-pause = true`, so it returns `true`.
4. Any call to `liquidate` reverts because `liquidation-paused` gates it, permanently, with no further admin action able to clear it (every future `set-pause-liquidation(false, …)` call re-enters the same then-branch). [3](#0-2)
