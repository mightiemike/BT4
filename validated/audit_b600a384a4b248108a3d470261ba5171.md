### Title
Unhandled `EpochError` on `unwrap()` in `receipt_filter_fn` panics chunk processing when a delayed `GlobalContractDistribution` receipt's target shard cannot be remapped across multiple reshardings - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()` on every delayed receipt popped during chunk apply. `Receipt::receiver_shard_id` can return `Err(EpochError::ShardingError(..))` for a `GlobalContractDistribution` receipt whose `target_shard` no longer exists in the current shard layout or its split history. This is directly analogous to the GStreamer NULL-pointer-dereference bug class: a value that should always be validated (a valid, non-null pointer/valid shard mapping) is blindly dereferenced/unwrapped without a defensive check, and a maliciously or naturally occurring edge case (deep resharding history) triggers the crash path during normal, transaction-triggered processing.

### Finding Description
`Receipt::receiver_shard_id` handles `GlobalContractDistribution` receipts specially because their `target_shard` is fixed at receipt-creation time and can become stale relative to the shard layout by the time the receipt is actually processed (it can sit in the delayed-receipts queue across resharding boundaries): [1](#0-0) 

When the `target_shard` is not part of the current layout, the code falls back to `shard_layout.resolve_to_current_shard(target_shard)`, and only returns `Err(EpochError::ShardingError(...))` if that resolution fails (e.g., the shard's split lineage cannot be traced far enough, such as after multiple successive resharding events between when the receipt was created and when it is finally popped).

That `Result` is then blindly `.unwrap()`ed in `DelayedReceiptQueueWrapper::receipt_filter_fn`, which is invoked from `pop()` — the exact function on the hot path of `Runtime::apply` used for every chunk that processes delayed receipts: [2](#0-1) 

Because `pop()` is called unconditionally while draining the delayed-receipt queue in `Runtime::apply` (via `process_receipts`), any node applying a chunk that reaches this receipt in the queue will panic identically — this is a deterministic, all-validators-affected panic, not a single-node crash.

This is functionally the same defect class as GHSL-2024-249: a data structure invariant (`sub` buffer validity / shard resolvability) is assumed to always hold and is dereferenced (`unwrap()`) without checking, and an attacker-influenced or naturally arising edge condition (a receipt whose target has aged across more resharding boundaries than `resolve_to_current_shard`'s lineage-walk can trace) breaks that assumption.

A test already exists exercising this exact scenario across *two* resharding generations and asserting the chain does not stall: [3](#0-2) 

I was not able to fully verify from the index whether `resolve_to_current_shard`'s shard-lineage walk is bounded to a fixed number of generations (which would mean three or more resharding events between deployment and drain could still exceed its resolution capability and hit the `unwrap()` panic), because the implementation body of `resolve_to_current_shard` in `core/primitives/src/shard_layout/mod.rs` and `v3.rs` was not returned by the tools available in this session. The test file's own framing ("If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn()") indicates the underlying `.unwrap()` call and its panic path are real and were considered a genuine risk worth guarding against — but I cannot confirm from the available evidence whether the current `resolve_to_current_shard` logic fully closes the gap for all resharding depths, or only for the two-generation case the test covers.

### Impact Explanation
If `resolve_to_current_shard` can fail to resolve a `GlobalContractDistribution` receipt's stale `target_shard` for some sequence/depth of resharding events, `receipt_filter_fn`'s `unwrap()` panics deterministically on every validator applying that chunk, producing a transaction-triggered halt of chunk production for the affected shard — matching the severity bar of "transaction-triggered halt" required by the validation rules. Because global contract deployment (which creates `GlobalContractDistribution` receipts) is triggered by an ordinary, unprivileged `DeployGlobalContract` action available to any account, and resharding boundaries are a normal part of protocol operation, this is reachable purely through submitted transactions plus normal chain progression — no validator or network-level compromise required.

### Likelihood Explanation
Exploitability requires: (1) deploying a global contract to trigger a `GlobalContractDistribution` receipt, (2) the receipt being delayed (e.g., via congestion) so it sits in the queue, and (3) enough resharding events occurring while it is delayed that `resolve_to_current_shard` cannot trace its lineage back to a live shard. Resharding frequency is controlled by the protocol/validators, not by the attacker directly, so the attacker cannot single-handedly force arbitrarily many reshardings in a short window under normal conditions — this bounds the practical likelihood. However, an attacker can maximize their chance by deploying a global contract and then using congestion-inducing transactions to keep the receipt delayed as long as possible across scheduled reshardings (e.g., dynamic resharding under the `DynamicReshardingConfig`), and the existing test in `test-loop-tests/src/tests/global_contracts_distribution.rs` shows the scenario is realistic enough that engineers built dedicated coverage for it at two-generation depth.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with proper error propagation (e.g., have `receipt_filter_fn` return `Result<bool, RuntimeError>` and propagate `EpochError` up through `pop()`'s existing `Result` return type) so an unresolvable shard produces a graceful `RuntimeError`/`InvalidTxError` rather than a panic. Additionally, audit `resolve_to_current_shard` to confirm it can trace arbitrarily deep resharding lineages (not just a fixed number of generations), or explicitly bound/document the maximum delay a `GlobalContractDistribution` receipt can tolerate and enforce that bound (e.g., forcibly executing or dropping such receipts before that many reshardings occur) so the invariant `receiver_shard_id` relies on can never be violated in practice.

### Proof of Concept
Not independently reproduced in this session beyond the pointer to the existing regression test, which already encodes the reproduction steps for a two-generation case: [4](#0-3) 
1. Deploy a global contract from an account in a shard that will be split by dynamic resharding, to create a `GlobalContractDistribution` receipt whose `target_shard` is a shard from the base layout.
2. Saturate the chain's compute budget with heavy transactions to delay processing of the delayed-receipt queue while multiple resharding events (shard splits) occur, advancing the shard layout multiple generations past the receipt's original `target_shard`.
3. Stop saturating and let the delayed-receipt queue drain; if `resolve_to_current_shard` cannot resolve the now doubly-stale `target_shard`, `receipt_filter_fn`'s `.unwrap()` on `receiver_shard_id` panics, halting chunk production (`chain head` height stalls below the expected drain height).

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)

    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }
