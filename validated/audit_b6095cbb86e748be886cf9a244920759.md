## Analysis Result

I traced the external "trusted-parameter-without-binding-check" bug class into Aptos's authenticated-state-view path and found a concrete analog in `DbStateView::get`.

### Title
Verified state view proves one value but returns a different, unverified value on read - ([File: storage/storage-interface/src/state_store/state_view/db_state_view.rs])

### Summary
`VerifiedStateViewAtVersion::verified_state_view_at_version` constructs a `DbStateView` that is supposed to bind every state read to a proof-verified state root hash obtained from a `TransactionInfoWithProof` [1](#0-0) . However, the actual read path in `DbStateView::get` performs the proof check and the value read as **two separate, independent DB queries**, and only the unverified one is returned to the caller.

### Finding Description
In `DbStateView::get`:
```rust
if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
    if let Ok((value, proof)) =
        self.db.get_state_value_with_proof_by_version(key, version)
    {
        proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
    }
}
Ok(self
    .db
    .get_state_value_with_version_by_version(key, version)?)
``` [2](#0-1) 

The `value` that is cryptographically bound to `root_hash` via `proof.verify(...)` comes from `get_state_value_with_proof_by_version`. But the value actually returned to the VM/consumer comes from a **second, independent call** to `get_state_value_with_version_by_version` [3](#0-2) . There is no code that checks these two reads returned the same `(version, value)` pair. If the underlying DB storage is mutated between the two reads (e.g., pruning, restore/backfill, or any window where the KV store and Merkle store are not perfectly synchronized), the proof would validate against one value while the caller receives a different value that was never authenticated against `root_hash`.

Additionally, if `get_state_value_with_proof_by_version` itself errors (`if let Ok(...)` — note the silent `if let` rather than `?`), verification is skipped entirely and the unverified value from the second call is still returned with no propagated error [4](#0-3) . This means the "verified" state view can silently degrade to an unverified read whenever the proof-generation path fails, with the caller none the wiser.

This view is constructed specifically to bind a state read to a `TransactionInfoWithProof`-derived, ledger-info-anchored root hash [5](#0-4) , i.e. it's meant to be an authenticated view over historical data (used by, e.g., debugger/replay/VM-validator tooling per the callers found in `aptos-move/aptos-debugger`, `aptos-move/cli`, `vm-validator/src/vm_validator.rs`).

### Impact Explanation
Because the value that is proof-checked is not the value that is returned, this component does not actually guarantee "read-value is bound to root_hash/version" — the core invariant proof-backed state views are supposed to provide. If the two backing indices (state-value-by-key-hash-version index vs. the merkle-tree-backed proof lookup) can diverge even momentarily (crash-recovery window, concurrent pruning, or a backfill/restore bug elsewhere in the storage layer), a consumer of `verified_state_view_at_version` — including transaction re-validation/replay/debugger tooling — can silently accept a state value that was never authenticated against the ledger-committed root, defeating the purpose of the "verified" view. In a replay/validation context this is a state-commitment-versus-authenticated-value binding violation.

### Likelihood Explanation
Medium-to-low: under normal steady-state operation the two DB reads should agree since both are served from the same committed ledger version, so this is not trivially triggerable by an unprivileged network attacker on a healthy node. However, the code contains no invariant that actually enforces equality between the two reads, and the silent `if let Ok(...)` swallow of proof-generation errors means a legitimate error condition (e.g., partial pruning) silently disables verification rather than failing safe. This is a broken invariant, not merely defensive redundancy, and the TODO comments in the same function (`sample-verify proof inside DB`, `support returning state proof for buffered state`) confirm the current implementation is acknowledged by the developers to be incomplete/best-effort rather than a hard guarantee.

### Recommendation
Make `DbStateView::get` return the value it actually proved, not a second independently-fetched value:
```rust
if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
    let (value, proof) = self.db.get_state_value_with_proof_by_version(key, version)?;
    proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
    return Ok(value.map(|v| (version, v)));
}
Ok(self.db.get_state_value_with_version_by_version(key, version)?)
```
This removes the silent `if let Ok(...)` swallow (proof-fetch failures should propagate as errors, not disable verification) and ensures the returned `(version, value)` is exactly the one that was cryptographically bound to `root_hash`.

### Proof of Concept
A conceptual reproduction (not executable without storage-layer fault injection):
1. Construct a `DbStateView` via `verified_state_view_at_version(Some(v), ledger_info)`, which fixes `maybe_verify_against_state_root_hash = Some(root_hash)` for version `v`.
2. Mock/patch `DbReader::get_state_value_with_version_by_version` to return a different `StateValue` than `get_state_value_with_proof_by_version` for the same `(key, v)` (simulating a divergence window between the KV index and Merkle index, e.g. during pruning or a restore edge case).
3. Call `DbStateView::get_state_slot(key)`.
4. Observe: `proof.verify(...)` succeeds against the first (correct) value, yet the function returns the second (differing) value with no error — demonstrating the authenticated response is not actually bound to the verified value/root.

**Note:** I could not fully verify whether the two underlying reads (`get_state_value_with_proof_by_version` and `get_state_value_with_version_by_version`) can genuinely diverge in production given `aptosdb`'s current write-atomicity guarantees (both are ultimately backed by data written together per version) — I was unable to find a synchronization/atomicity proof or a documented failure mode confirming actual exploitability, only the missing-invariant code pattern itself. This is reported as the strongest local analog found, but its exploitability depends on storage-layer atomicity assumptions I could not fully confirm within available tool calls.

impl VerifiedStateViewAtVersion for Arc<dyn DbReader> {
    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =
                db.get_transaction_by_version(version, ledger_info.version(), false)?;
            txn_with_proof.verify(ledger_info)?;

            let state_root_hash = txn_with_proof
                .proof
                .transaction_info
                .state_checkpoint_hash()
                .ok_or_else(|| StateViewError::NotFound("state_checkpoint_hash".to_string()))?;

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
            })
        }
    }
