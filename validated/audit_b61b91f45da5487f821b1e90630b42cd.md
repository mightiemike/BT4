### Title
Unchecked subtraction of `execution_context.n_remaining_steps()` from `n_allotted_execution_steps` can underflow and panic the sequencer during transaction execution - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
`run_revertible` computes `execution_steps_consumed` with a raw, unchecked subtraction: `n_allotted_execution_steps - execution_context.n_remaining_steps()`. Every other resource/gas computation in this codebase (bouncer, gas conversion, `SierraGasRevertTracker`, `GasCounter`) is deliberately wrapped in `checked_sub`/`checked_add` with an explicit panic message or graceful fallback, showing the team's established pattern of guarding against exactly this class of bug (the analog of the Float Capital `poolValue` unsafe int→uint cast that made a negative value wrap into a huge unsigned number and blow up downstream arithmetic). This one call site breaks that pattern. [1](#0-0) 

### Finding Description
`n_allotted_execution_steps` is the step budget remaining after subtracting validation and OS-overhead steps (`subtract_validation_and_overhead_steps`, itself calling `subtract_steps`) [2](#0-1) . After `run_execute`, the code computes:
```
let execution_steps_consumed =
    n_allotted_execution_steps - execution_context.n_remaining_steps();
``` [1](#0-0) 

This is a plain `usize` subtraction with no `checked_sub`/`saturating_sub` guard, unlike the equivalent Sierra-gas tracker just a few lines above it, which explicitly panics with a descriptive message on this exact condition: `self.initial_remaining_gas.checked_sub(self.last_seen_remaining_gas).unwrap_or_else(|| panic!("The consumed gas must be non-negative. ..."))` [3](#0-2) . If `execution_context.n_remaining_steps()` can, for any Cairo-steps-tracked transaction (attacker-controlled contract execution flow, VM run-resources bookkeeping edge case, or a resource-limit interaction that leaves more "remaining steps" reported than were allotted for the execute phase), exceed `n_allotted_execution_steps`, the subtraction underflows. In a build with Rust's default debug/overflow-checks-enabled arithmetic (as is standard for security-critical node software and as the surrounding code's proactive `checked_*` guards imply is expected), this underflow triggers an immediate panic rather than the silent-wrap behavior of a release build without overflow checks — mirroring the Solidity bug's outcome where an unexpected negative-turned-huge value causes a revert of the whole flow.

This is invoked from `run_revertible`, which is the interior execution path taken for every account transaction going through `execute_raw`/`execute` in the blockifier — i.e., reachable directly by any submitted transaction that a sequencer executes when building or re-executing a block, including replay in the Starknet OS.

### Impact Explanation
A panic inside transaction execution during block building crashes or aborts the executing task for that transaction/block. Because this code path runs for every account transaction (not behind any privileged/mocked-only gate), an attacker who can construct a transaction/contract call that drives `execution_context.n_remaining_steps()` above `n_allotted_execution_steps` at this checkpoint could cause the sequencer to panic while processing an otherwise ordinary transaction, potentially halting block production (a network unable to confirm new transactions) or causing honest-node divergence if only some nodes panic/recover differently during OS re-execution vs. blockifier execution.

### Likelihood Explanation
Likelihood is uncertain without deeper verification of every caller of `subtract_validation_and_overhead_steps`/`n_remaining_steps()` and all paths that can increase remaining steps mid-execution (e.g., nested call step accounting, syscall step refunds). The surrounding code's heavy, deliberate use of `checked_sub` with explicit panic/fallback messages elsewhere strongly suggests the team is aware this quantity can misbehave and normally guards against it — the plain subtraction here looks like an oversight rather than a proven-safe invariant, but I could not fully trace every producer of `n_remaining_steps()` to confirm it is actually reachable with attacker-controlled inputs in this snapshot.

### Recommendation
Replace the raw subtraction with a checked variant consistent with the rest of the codebase, e.g. `n_allotted_execution_steps.checked_sub(execution_context.n_remaining_steps()).unwrap_or_else(|| panic!(...))` with a descriptive panic (matching the `SierraGasRevertTracker::get_gas_consumed` pattern), or better, `saturating_sub` with a debug log if the invariant is expected to occasionally not hold, so a single transaction cannot crash the executor without at least clear diagnostics — and audit whether `n_remaining_steps()` can genuinely exceed the allotted budget for any reachable execution path.

### Proof of Concept
Not independently reproduced against a running node; the report is based on static code review showing the unguarded arithmetic at `crates/blockifier/src/transaction/account_transaction.rs:749-751` in contrast to the guarded equivalent in `crates/blockifier/src/execution/entry_point.rs:327-334`. Confirming exploitability would require tracing every writer of `execution_context.vm_run_resources`/`n_remaining_steps()` across nested calls, syscalls, and revert flows to construct a transaction that leaves more "remaining steps" than were allotted for the execute phase.

    /// validation and the overhead steps required, among the rest, for fee transfer.
    /// Returns the remaining steps (after the subtraction).
    pub fn subtract_validation_and_overhead_steps(
        &mut self,
        validate_call_info: &Option<CallInfo>,
        tx_type: &TransactionType,
        extended_calldata_length: usize,
    ) -> usize {
        let validate_steps = validate_call_info
            .as_ref()
            .map(|call_info| call_info.resources.vm_resources.n_steps)
            .unwrap_or_default();

        let overhead_steps = self
            .versioned_constants()
            .os_resources_for_tx_type(tx_type, extended_calldata_length)
            .n_steps;
        self.subtract_steps(validate_steps + overhead_steps)
    }
