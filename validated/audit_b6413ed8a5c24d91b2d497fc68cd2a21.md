### Title
Unbounded FIFO pending-event queue with hardcoded LIMIT 1000 allows cheap deposit spam to starve legitimate inbound confirmations - (File: `universalClient/chains/evm/event_confirmer.go`)

### Summary
`EventConfirmer.processPendingEvents` fetches only the oldest 1000 `PENDING` events each poll cycle via `ec.chainStore.GetPendingEvents(1000)`, and `ChainStore.GetPendingEvents` strictly orders by `created_at ASC` with a fixed `Limit(1000)` and no per-sender/per-type fairness or priority mechanism.

### Finding Description
Any unprivileged user can call the source-chain gateway's `sendFunds` method with near-zero value, cheaply generating many `Inbound` events that the `EventListener` stores as `PENDING` rows via `InsertEventIfNotExists` [1](#0-0) . `processPendingEvents` always pulls the oldest 1000 by `created_at` [2](#0-1)  and only events within that fetched batch are checked for confirmation depth and promoted out of `PENDING` [3](#0-2) . If an attacker sustains an injection rate of spam deposits that keeps the total `PENDING` count above 1000 for longer than the confirmation window (5 or 12 confirmations depending on type, per `getRequiredConfirmations`) [4](#0-3) , a legitimate user's newer deposit event will consistently fall outside the fetched 1000-row window and never be checked for confirmation, delaying its finalization for as long as the flood is sustained.

### Impact Explanation
This affects the local per-chain event-processing pipeline that every Universal Validator's `universalClient` runs identically, so the delay is systemic across all honest validators observing that chain, not merely a single node's local queue quirk. However, the attacker's own spam transactions are ordinary, honestly-mined transactions and will themselves clear out of `PENDING` once their own confirmation depth is reached — so the backlog is only sustained as long as the attacker continues paying source-chain gas to keep re-seeding it. There is no fund loss, no accounting corruption, and no unauthorized state transition — legitimate deposits are eventually confirmed once the flood stops or clears. This is a bounded, cost-gated delay of inbound finalization rather than a persistent halt.

### Likelihood Explanation
Feasible for any unprivileged attacker with enough source-chain gas budget to continuously emit `sendFunds` calls at a rate exceeding the chain's confirmation-clearing throughput, since `sendFunds` value can be near-zero and there is no rate limiting, minimum-value gate, or fairness/priority ordering by sender or event-type in `GetPendingEvents`.

### Recommendation
Add fairness controls to the pending-event fetch/processing path, e.g., paginate/process all pending events per poll instead of a hard 1000 cap, or prioritize/interleave fetching across independent buckets (e.g., per event type, or round-robin by sender/tx origin) so a burst of low-value spam cannot monopolize the fixed-size batch indefinitely. Consider also fetching un-checked-in-a-while events preferentially (e.g., ORDER BY combined with a "last checked" watermark) rather than pure `created_at ASC`.

### Proof of Concept
Seed >1000 `PENDING` `Event` rows with old `created_at` timestamps plus one legitimate event with a newer timestamp; call `chainStore.GetPendingEvents(1000)` and observe the legitimate event is excluded from the returned batch, matching the pattern already exercised (with smaller counts) in `TestChainStore_GetPendingEventsLimit` [5](#0-4) ; scaling the backlog beyond 1000 and sustaining it via repeated near-zero `sendFunds` calls demonstrates the starvation described.

// GetPendingEvents fetches pending events ordered by creation time
func (cs *ChainStore) GetPendingEvents(limit int) ([]store.Event, error) {
	if cs.database == nil {
		return nil, fmt.Errorf("database is nil")
	}

	var events []store.Event
	if err := cs.database.Client().
		Where("status = ?", store.StatusPending).
		Order("created_at ASC").
		Limit(limit).
		Find(&events).Error; err != nil {
		return nil, fmt.Errorf("failed to query pending events: %w", err)
	}

	return events, nil
}

// getRequiredConfirmations returns the required number of confirmations based on confirmation type
func (ec *EventConfirmer) getRequiredConfirmations(confirmationType string) uint64 {
	switch confirmationType {
	case store.ConfirmationFast:
		if ec.fastConfirmations >= 0 {
			return ec.fastConfirmations
		}
		return 5
	case store.ConfirmationStandard:
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	default:
		// Default to standard if unknown
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	}
}
