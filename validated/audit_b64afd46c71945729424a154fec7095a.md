## Title
Unbounded allocation from attacker-controlled Cairo0 array length in `read_felt_array` (deprecated syscalls) - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The CVE describes an integer-overflow-style bug where a size value is used to allocate memory without first validating it against the actual available data, leading to under-allocation / oversized allocation. The sequencer has the same bug class in the Cairo0 ("deprecated") syscall array-reading helper: the declared array length is taken directly from VM memory (a felt fully controlled by the executing Cairo0 program) and converted to `usize`, then passed straight into a range read without first checking it against the amount of data actually available in the referenced memory segment.

### Finding Description
`read_felt_array` in the deprecated syscalls hint processor reads a length felt from the VM, converts it to `usize`, and immediately uses it to pull a range of that many felts out of VM memory: [1](#0-0) 

The `array_size` felt is written into memory by the executed Cairo0 program itself (a program supplied by any user via a `declare` transaction), and there is no check that `array_size` is consistent with the amount of memory actually laid out after `array_data_start_ptr` before the value is handed to `felt_range_from_ptr`: [2](#0-1) 

This is functionally the same defect class as the CVE: a length value that is attacker-influenced is used to size a memory read/allocation without validating it against the real backing data first. Notably, this exact class of bug was identified and explicitly fixed elsewhere in this same repository — `CairoArray::try_from` in `apollo_cairo_utils` validates the declared count against the number of remaining felts *before* calling `Vec::with_capacity`, with a comment stating the fix is precisely to prevent "a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`": [3](#0-2) 

The non-deprecated syscall path (`execution/syscalls/hint_processor.rs::read_felt_array`) is safer because it derives `array_size` from the *difference between two pointers* rather than trusting a raw declared length felt, and also handles the null/empty-span edge cases explicitly: [4](#0-3) 

However, the deprecated (Cairo0) path still trusts a raw length felt directly, without a bound like the one added to `CairoArray`.

### Impact Explanation
A malicious contract deployer can craft a Cairo0 contract whose compiled bytecode, when its entry point is invoked (a normal `invoke`/`declare`+`invoke` flow reachable by any unprivileged transaction sender), writes an extremely large `array_size` felt (up to `usize::MAX`) prior to invoking a deprecated syscall that internally calls `read_felt_array`. This causes the sequencer to attempt to read/allocate a felt range of that declared size from VM memory. If this size is large enough, the resulting allocation attempt can exhaust process memory or trigger an allocator abort, crashing the executing sequencer/batcher node process while validating or building a block — a network-wide denial of service (the node becomes unable to confirm new transactions) triggered by a single transaction.

### Likelihood Explanation
Reachability is straightforward: any account can declare and invoke a Cairo0 contract, and the deprecated syscall interface (`deprecated_syscalls`) is still supported for backward compatibility, so any transaction invoking a syscall through this legacy path (e.g., ones handled via `read_felt_array` for array-typed syscall payloads) can trigger it. No special privileges (staker/prover/operator) are required — a normal contract call suffices. This puts it squarely in the "unprivileged transaction sender" reachable category the scan asks for.

### Recommendation
Add the same defensive bound-check pattern used in `apollo_cairo_utils::CairoArray::try_from` to the deprecated `read_felt_array`: before converting the declared `array_size` felt to `usize` and reading/allocating that many felts, validate it against a reasonable upper bound (e.g., the size of the memory segment actually backing `array_data_start_ptr`, or an overall gas/resource-derived cap), and reject with a `DeprecatedSyscallExecutionError` rather than proceeding to allocate.

### Proof of Concept
1. Declare and deploy a Cairo0 contract whose external entry point, prior to calling a deprecated syscall that reads a felt array argument (e.g., one processed via `deprecated_syscalls::hint_processor::read_felt_array`), writes a very large integer (e.g., close to `usize::MAX`, or large enough to exceed available memory) into the memory cell that represents the array's declared length, while leaving the backing data pointer/segment empty or minimal.
2. Invoke that entry point via a normal `INVOKE` transaction.
3. During execution, `read_felt_array` converts the declared length to `usize` and calls `felt_range_from_ptr(vm, array_data_start_ptr, size)`, which calls `vm.get_integer_range(ptr, size)`, attempting to materialize a `Vec` sized to the attacker-declared length rather than the actual backing data — causing excessive memory allocation/allocator abort during transaction execution on the sequencer.

```rust
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,

    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
```

```rust
pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
```

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
```
