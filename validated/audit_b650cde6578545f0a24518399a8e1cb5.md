### Title
Unauthenticated JSON-RPC calls `citrea_haltCommitments` / `citrea_resumeCommitments` mutate sequencer state without access control - ([File: crates/sequencer/src/rpc.rs])

### Summary
`halt_commitments` and `resume_commitments` are exposed as public JSON-RPC methods on the sequencer, and they directly control whether the sequencer submits sequencer commitments to the L1 chain, but they are not subject to any authentication or authorization check. Any unprivileged caller who can reach the sequencer's RPC endpoint can halt or resume commitment submission.

### Finding Description
`SequencerRpc::halt_commitments` and `resume_commitments` simply forward a control message to the sequencer's internal loop with no caller check: [1](#0-0) 

These methods are registered like any other sequencer RPC method via `register_rpc_methods`/`create_rpc_module`, and the only authentication layer applied at the RPC server boundary is `Auth`, which only protects a hard-coded allowlist of methods (`backup_create`, `backup_validate`, `backup_info`): [2](#0-1) [3](#0-2) 

The RPC server wraps all registered methods with this `Auth` middleware, but since `citrea_haltCommitments`/`citrea_resumeCommitments` are not in `PROTECTED_METHODS`, the middleware passes them through untouched regardless of whether an `api_key` is configured: [4](#0-3) 

This mirrors the reported bug class exactly: a privileged-operator-only function (`RM_UpdateReward` in the external report) reachable by any caller because access control was never enforced. Here, an operational control that is meant to be restricted to the sequencer operator (halting/resuming L1 commitment submission) is reachable by any unauthenticated JSON-RPC client.

### Impact Explanation
This breaks the equality between "commitments the sequencer operator intends to submit" and "commitments actually submitted to L1." An attacker with network access to the sequencer's RPC port can call `citrea_haltCommitments` to indefinitely stop the sequencer from publishing new sequencer commitments to Bitcoin, without needing any privileged role, API key, sequencer key, or node-operator access. This matches the "High" impact bucket in scope: "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`." Halting commitments stalls the rollup's proof/finalization pipeline (provers cannot prove new commitments, L1 clients stop seeing state progress), a state-availability/liveness effect on the rollup's DA-integrity binding, distinct from ordinary DoS/rate-limiting concerns since it's a direct authorization gap on a state-mutating admin RPC, not a resource-exhaustion issue.

### Likelihood Explanation
Likelihood is high for any deployment that exposes the sequencer RPC without additional network-level restriction: the vulnerability requires zero privilege, keys, or special conditions—just a plain JSON-RPC call (`citrea_haltCommitments`/`citrea_resumeCommitments`) to the sequencer's RPC endpoint. The `Auth` middleware gives a false sense of protection since it only guards three unrelated backup methods.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other operator-only control-plane RPC methods) to the `PROTECTED_METHODS` list in `crates/common/src/rpc/auth.rs`, or otherwise require the configured `api_key`/an authenticated caller before dispatching `SequencerRpcMessage::HaltCommitments`/`ResumeCommitments`, so that these calls are rejected for unauthenticated senders exactly like `backup_create`/`backup_validate`/`backup_info`.

### Proof of Concept
1. Start the sequencer with RPC enabled and (optionally) an `api_key` configured.
2. From an unauthenticated client with no `api_key`, send:
   ```
   curl -X POST http://<sequencer-rpc>:<port> \
     -H "Content-Type: application/json" \
     -d '{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}'
   ```
3. The call succeeds (returns `Ok(())`) because `citrea_haltCommitments` is absent from `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, so the `Auth` middleware never checks for an API key.
4. The sequencer stops submitting sequencer commitments to L1 until `citrea_resumeCommitments` is called—again reachable by anyone, with no credential required.
