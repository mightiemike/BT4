## Analog Found: Front-Run of Poison-Microblock Reporter Reward

### Title
Poison-Microblock reporter reward is front-runnable, diverting the block-reward slash to whoever copies public mempool data - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
The Stacks poison-microblock mechanism rewards whoever's transaction is first mined with evidence of a forked microblock stream by redirecting a fraction of the offending miner's matured coinbase to that transaction's sender. Because the evidence (two conflicting, already-signed microblock headers) is public data extracted straight from a `PoisonMicroblock` transaction sitting in the mempool, an unprivileged party can copy that data into their own transaction with a higher fee/faster relay and steal the commission from the original discoverer — an exact structural analog of the reported "front-run keeper rewards" bug class (attacker copies public input, resubmits, and captures a reward that isn't theirs to earn).

### Finding Description
`StacksChainState::handle_poison_microblock` records the *transaction sender* — not the original discoverer of the fork — as the entitled `reporter_principal` for a given microblock public-key-hash/sequence: [1](#0-0) 

The only requirement to become the "reporter" is producing a validly-signed `PoisonMicroblock` transaction containing two conflicting microblock headers signed by the same key — data that is entirely public once someone else's `PoisonMicroblock` transaction is broadcast to the mempool. Mempool admission only checks internal consistency of the two headers (same sequence, same prev-block, same version, same recovered pubkey) and that the block has an anchored microblock pubkey hash; it never verifies that the sender actually discovered the fork or was the first to construct the payload: [2](#0-1) 

Later, at reward-maturity time, `find_mature_miner_rewards` looks up whichever principal is recorded via `get_poison_microblock_report` and redirects the `poison_microblock_commission` (5% of the coinbase) to them instead of the miner: [3](#0-2) [4](#0-3) 

The equality that should hold is: *the reward recipient equals the party who discovered/first constructed the fork evidence*. An attacker who monitors the mempool (or reconstructs the two microblock headers themselves once they see them referenced anywhere) and submits their own `PoisonMicroblock` transaction with a higher fee — or simply gets it mined first due to normal transaction-ordering nondeterminism — breaks that equality: the commission is paid to the copier, not the discoverer.

### Impact Explanation
This is a reward-mispayment bounded to a fixed fraction of a single miner's coinbase (`POISON_MICROBLOCK_COMMISSION_FRACTION = 5%`), consistent with the "High — poison or reward mis-payment bounded to fees" category. It does not cause a chain split, an invalid block being accepted, or a non-reproducible state root — every node computes the same (wrong-recipient) result deterministically from the same `PoisonMicroblock` transaction that got mined, so consensus is preserved. The harm is confined to legitimate fork-discoverers losing their commission to a copier.

### Likelihood Explanation
This requires no privileged role, no majority collusion, and no node-operator/admin key. Any single, minority participant who observes a `PoisonMicroblock` transaction in the public mempool (or arrives at the same evidence independently through analysis of published microblocks) can copy the two header structures verbatim into a self-signed transaction and attempt to have it mined first — exactly mirroring the front-running dynamic described in the external report, where the "keeper" work product is public and copyable, so the reward accrues to whoever's transaction lands first rather than whoever did the underlying work.

### Recommendation
Consider one or more of:
- Commit-reveal for poison-microblock reports (submit a hash of the offending headers first, then reveal after inclusion) so front-runners cannot simply copy visible mempool data.
- Splitting the commission among all valid reporters within the same block/tenure rather than "winner take all" for the earliest sequence, to reduce the incentive to front-run.
- Treating this as an accepted trade-off (as the original report's vendor did) given the on-chain fix requires a protocol change; document it as a known limitation rather than a silent assumption.

### Proof of Concept
1. Alice discovers a valid `PoisonMicroblock` fork and broadcasts `tx_A` (`TransactionPayload::PoisonMicroblock(h1, h2)`, signed by Alice, low fee).
2. Bob observes `tx_A` in the mempool, extracts `(h1, h2)` (public data), and immediately broadcasts `tx_B` with the identical `PoisonMicroblock(h1, h2)` payload but signed by himself and a higher fee.
3. Miners/nodes independently order transactions by fee; `tx_B` is included first (or in the same block with a favorable vtxindex). `handle_poison_microblock`'s "first-ever report" branch records Bob as `reporter_principal` at that sequence: [5](#0-4) 
4. At maturity, `calculate_miner_reward` pays the 5% commission to Bob's address instead of Alice's, even though Alice discovered the fork: [6](#0-5)
