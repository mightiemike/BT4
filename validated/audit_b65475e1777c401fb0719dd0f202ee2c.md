### Title
`ensure_match_transaction_info` ignores state/hot-state/position checkpoint hashes, allowing replay-verification to accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by chunk-executor replay verification and the debugger/CLI replay tooling, only checks status, gas used, write-set hash, and event root hash against the persisted `TransactionInfo`. It explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, per the inline TODO comment in the code itself.

### Finding Description
`ensure_match_transaction_info` at `types/src/transaction/mod.rs` lines 2139-2204 validates a locally re-executed `TransactionOutput` against a trusted, previously-committed `TransactionInfo` (which is itself accumulator-bound and authenticated by a `LedgerInfo` signature). The function is invoked from:
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution` (used for backup restore / replay verification and fast-sync verify_execution_mode) [1](#0-0) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` (replay/simulate tooling).

Inside the function, it checks `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`, but the code comment explicitly documents that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)" [2](#0-1) . These checkpoint hashes are the roots that bind a transaction's `TransactionInfo` to the actual post-execution ledger state (JMT state root, hot-state root, and — per the newly added `NATIVE_POSITION`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` feature flags in `types/src/on_chain_config/aptos_features.rs` — the native-trading position-state root and hot-state root) [3](#0-2) . These are exactly the fields produced by `DoLedgerUpdate::assemble_transaction_infos`, which sets `maybe_state_checkpoint_hash`, `maybe_hot_state_checkpoint_hash`, and `maybe_position_state_checkpoint_hash` on `TransactionInfoV1` [4](#0-3) .

Because `ensure_match_transaction_info` never re-derives or compares these checkpoint hashes, a locally computed state root that diverges from what is committed in the authenticated `TransactionInfo`/accumulator (e.g. due to a storage bug, a non-deterministic native, or a bug specific to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) will not be detected by this check. The comment itself flags this as a known gap ("so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution").

### Impact Explanation
This does not by itself corrupt state on a validating node during normal consensus execution — the state root mismatch would still surface via the state-checkpoint/`StateCheckpointOutput` and accumulator hash pipeline during real block execution and consensus voting. However, `ensure_match_transaction_info` is the sole invariant used by chunk-executor replay verification (`verify_execution`) during backup restore / fast sync and by debugger/CLI replay checks. If the on-disk write-set/events hash matches but the state-checkpoint (JMT), hot-state, or position-state root differs from what execution locally derives, this verification path will incorrectly report success. That means a corrupted or forked state root produced by a bug elsewhere in checkpoint computation could pass "replay-verify" and be silently accepted as authentic during restore, defeating one of the intended proof-integrity backstops. This is a gap in a defense-in-depth check rather than a primary consensus-safety violation, since I could not verify (within available context) that this alone causes acceptance of a bad root by a fully-syncing validator that recomputes and votes on the accumulator directly.

### Likelihood Explanation
The gap is unconditional (it is not behind a feature flag) and applies whenever `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` populate these optional hashes. It requires a separate, independent bug that causes local checkpoint-hash computation to diverge from the authenticated one; `ensure_match_transaction_info` merely fails to catch it. I could not confirm from the available index whether any current production path relies on this check as the *only* integrity gate before committing/trusting state (as opposed to consensus itself independently verifying the full accumulator root), so likelihood of an end-to-end mainnet exploit is uncertain without further tracing of the restore/fast-sync commit path.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` when they are present in `expected_write_set`/execution output, consistent with how `write_set_hash` and `event_root_hash` are validated, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production as the comment recommends.

### Proof of Concept
Not independently confirmed with a concrete exploit trace; the gap is directly evidenced by the code and its own TODO comment at [5](#0-4) , but I was unable to trace, within the available tool budget, a concrete unprivileged path from a divergent checkpoint hash all the way to an accepted-as-valid mainnet state commit (e.g., whether normal validator sync independently re-verifies the accumulator root outside of this comparator). Given this uncertainty about full exploitability end-to-end, I present this as the strongest local candidate found, but cannot certify it meets the "high or critical impact" bar without further investigation of the restore/fast-sync commit call sites (`state-sync/state-sync-driver` and `execution/executor` commit paths) that was not completed due to iteration limits.
