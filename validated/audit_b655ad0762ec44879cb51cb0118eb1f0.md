### Title
Fee-transfer success (return value) is never verified during fee charging - only "not reverted" is checked - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo])

### Summary
Both the Starknet OS (Cairo) fee-charging routine and the Rust blockifier's fee-transfer path invoke the fee token's `transfer` entry point and only check that the call did not revert. Neither path inspects the ERC20-style `(success: felt)` return value that the fee token's `transfer`/`ERC20_transfer` returns. This mirrors the reported bug class ("ERC20 token transfer return value is not handled") in an unprivileged-transaction-reachable sequencer path: every account transaction that pays a fee triggers this code.

### Finding Description
In the Starknet OS, `charge_fee` builds a `TransferCallData` and invokes the fee token contract via `non_reverting_select_execute_entry_point_func`, discarding the returned data entirely: [1](#0-0) 

Compare this with `run_validate`, which explicitly checks the retdata content against the expected `VALIDATED` magic value after calling the same non-reverting entry-point helper: [2](#0-1) 

`non_reverting_select_execute_entry_point_func` itself only asserts `is_reverted = 0` and returns the raw `retdata`/`retdata_size`; it does not interpret or validate the payload: [3](#0-2) 

Because `charge_fee` never captures `retdata`/`retdata_size` from the call, there is no equivalent `assert retdata[0] = TRUE` check as exists for `__validate__`.

The reference fee-token ERC20 implementation used across this codebase always returns `(TRUE,)` unconditionally from `transfer`/`transferFrom` and only enforces correctness via `assert_not_zero` calls inside `ERC20_transfer` (which revert on failure rather than returning `FALSE`): [4](#0-3) [5](#0-4) 

On the Rust blockifier side, `execute_fee_transfer` builds a `transfer` `CallEntryPoint` and executes it, propagating only execution *errors* (`Err`), not inspecting the call's `retdata`/success boolean in the resulting `CallInfo`: [6](#0-5) 

Test expectations confirm the accepted pattern is "no revert, plus events emitted" — they check `retdata: retdata![felt!(constants::FELT_TRUE)]` as an *expected value in tests*, but production code never performs this same assertion at runtime: [7](#0-6) 

Because the fee token's `class_hash` is protocol-controlled (`fee_token_address` from `starknet_os_config`), this is not directly exploitable by an unprivileged EOA using the canonical STRK/ETH fee token, since that particular reference contract cannot return `FALSE` without reverting first. However, the sequencer code path itself does not enforce this invariant in a defense-in-depth manner — it silently trusts "no revert" as equivalent to "transfer succeeded," which is exactly the anti-pattern flagged in the original report. If a future fee-token upgrade, or any fee token whose class hash differs from the hard-coded default (some deployments allow governance to change `fee_token_address`), implements `transfer` to return `FALSE` on certain conditions (e.g., paused state, blacklist, partial fill) without reverting, the sequencer would treat the transaction as fully fee-paid while the balance transfer silently did not occur.

### Impact Explanation
If the fee token contract (whose class/address is a chain-config parameter, not immutable code baked into the OS) ever returns `FALSE` from `transfer` instead of reverting under some condition, the sequencer would: (1) accept the transaction as successfully fee-paid, (2) deduct no funds from the sender, (3) still credit the sequencer's fee accounting/increment nonce, and (4) commit state as if the fee was paid. This is a direct path to unauthorized value creation / fee evasion — a concrete loss of funds/permanent value discrepancy in committed state, differing from what a correctly-checking implementation would produce (a reverted or rejected transaction). This is Medium severity because exploitation depends on the deployed fee token's `transfer` semantics differing from the current reference implementation (which cannot return `FALSE` without reverting).

### Likelihood Explanation
Likelihood is low-to-moderate: the currently shipped/reference fee ERC20 (`ERC20_transfer` in `ERC20_base.cairo`) reverts via `assert_not_zero` on insufficient balance rather than returning `FALSE`, so under the *current* fee contract this cannot be triggered by an ordinary user. However, the vulnerability is a structural gap in the OS/blockifier logic (missing "success" check, present for `__validate__` but absent for fee transfer), so likelihood increases if/when the fee token is replaced or upgraded, since nothing in the sequencer code enforces the "must revert, not return false" contract at the OS or blockifier level.

### Recommendation
Add an explicit check of the fee-transfer entry point's return data (`retdata[0] == TRUE`/`FELT_TRUE`) in both:
- `charge_fee` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo`, mirroring the pattern already used in `run_validate` for the `VALIDATED` magic value, and
- `execute_fee_transfer` in `crates/blockifier/src/transaction/account_transaction.rs`, validating `call_info.execution.retdata` equals the expected success value before treating the fee as charged.

### Proof of Concept
Not directly reproducible against the current canonical fee token, since `ERC20_transfer` always reverts rather than returning `FALSE` on failure conditions. Conceptual PoC: deploy/upgrade a fee token whose `transfer` function returns `felt 0` (`FALSE`) instead of reverting when, e.g., the sender is blacklisted or the contract is paused; submit any ordinary invoke transaction from an account holding zero balance under such a token; observe that `charge_fee`/`execute_fee_transfer` do not detect the `FALSE` return and the transaction is committed as fee-paid despite no balance movement.

func ERC20_transfer{syscall_ptr: felt*, pedersen_ptr: HashBuiltin*, range_check_ptr}(
    sender: felt, recipient: felt, amount: Uint256
) {
    alloc_locals;
    assert_not_zero(sender);
    assert_not_zero(recipient);
    uint256_check(amount);  // Almost surely not needed, might remove after confirmation.

    let (local sender_balance: Uint256) = ERC20_balances.read(account=sender);

    // Validates amount <= sender_balance and returns 1 if true.
    let (enough_balance) = uint256_le(amount, sender_balance);
    assert_not_zero(enough_balance);

    // Subtract from sender.
    let (new_sender_balance: Uint256) = uint256_sub(sender_balance, amount);
    ERC20_balances.write(sender, new_sender_balance);

    // Add to recipient's balance.
    let (recipient_balance: Uint256) = ERC20_balances.read(account=recipient);
    // Overflow is not possible because sum is guaranteed by mint to be less than total supply.
    let (new_recipient_balance, _: Uint256) = uint256_add(recipient_balance, amount);
    ERC20_balances.write(recipient, new_recipient_balance);
    Transfer.emit(sender, recipient, amount);
    return ();
}

    fn execute_fee_transfer(
        state: &mut dyn State,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
    ) -> TransactionExecutionResult<CallInfo> {
        // The least significant 128 bits of the amount transferred.
        let lsb_amount = Felt::from(actual_fee.0);
        // The most significant 128 bits of the amount transferred.
        let msb_amount = Felt::ZERO;

        let TransactionContext { block_context, tx_info } = tx_context.as_ref();
        let storage_address = tx_context.fee_token_address();
        // The fee contains the cost of running this transfer, and the token contract is
        // well known to the sequencer, so there is no need to limit its run.
        let mut remaining_gas_for_fee_transfer =
            block_context.versioned_constants.os_constants.gas_costs.base.default_initial_gas_cost;
        let fee_transfer_call = CallEntryPoint {
            class_hash: None,
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector_from_name(constants::TRANSFER_ENTRY_POINT_NAME),
            calldata: calldata![
                *block_context.block_info.sequencer_address.0.key(), // Recipient.
                lsb_amount,
                msb_amount
            ],
            storage_address,
            caller_address: tx_info.sender_address(),
            call_type: CallType::Call,

            initial_gas: remaining_gas_for_fee_transfer,
        };
        let mut context = EntryPointExecutionContext::new_invoke(
            tx_context,
            true,
            SierraGasRevertTracker::new(GasAmount(remaining_gas_for_fee_transfer)),
        );

        Ok(fee_transfer_call
            .execute(state, &mut context, &mut remaining_gas_for_fee_transfer)
            .map_err(|error| Box::new(TransactionFeeError::ExecuteFeeTransferError(error)))?)
    }
