### Title
SVM outbound revert reports zero gas usage, causing full gas-fee refund - (`universalClient/tss/txresolver/svm.go`)

### Summary
`resolveSVM` votes failure for every SVM revert path with a hardcoded `gasFeeUsed="0"`, regardless of whether the destination transaction actually consumed gas. If a Solana transaction is included but reverts without creating the `ExecutedTx` PDA, the chain refunds the entire pre-paid `gasFee` instead of `gasFee - gasUsed`, corrupting gas-fee accounting and causing protocol loss.

### Finding Description
In `universalClient/tss/txresolver/svm.go`, the deadline-expired revert branch calls:

```go
_ = r.voteOutboundFailureAndMarkReverted(ctx, event, txID, utxID, "", 0, "0", "tx not executed on destination chain")
``` [1](#0-0) 

The `OutboundObservation` therefore always has `Success=false` and `GasFeeUsed="0"`. The keeper's `applyGasRefund` subtracts `obs.GasFeeUsed` from `outbound.GasFee` to compute the refund:

```go
refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
``` [2](#0-1) 

With `gasFeeUsed=0`, the refund equals the full `gasFee`. Unlike the EVM resolver, the SVM resolver never queries an actual consumed-gas value (e.g., `builder.GetGasFeeUsed`).

### Impact Explanation
An unprivileged user can submit a standard outbound to an SVM chain with a payload that consumes compute units and then reverts. The resolver only checks for the `ExecutedTx` PDA; a reverted transaction may leave the PDA absent, so the resolver treats it as "not executed" and votes failure with `gasFeeUsed="0"`. Once honest validators converge on that ballot, `FinalizeOutbound` → `handleFailedOutbound` → `applyGasRefund` refunds the entire `gasFee`, even though the protocol already spent destination gas on the reverted Solana transaction. This corrupts gas-fee/refund accounting and can drain the funds the protocol uses to cover destination-chain gas.

### Likelihood Explanation
The exploitability depends on the SVM gateway program creating the `ExecutedTx` PDA only for successful executions. The resolver's own comment maps "PDA exists → COMPLETED", implying a reverted or failed execution leaves the PDA absent. If that holds, any reverting SVM outbound triggers the bug. The attacker needs no privileged role—only the ability to submit an ordinary outbound with a reverting destination payload.

### Recommendation
Query the actual gas consumed for the SVM transaction before voting failure, analogous to the EVM path's use of `builder.GetGasFeeUsed`. If the SVM transaction signature or RPC does not expose this directly, require the gateway program to emit a gas-used value for reverted/failed executions, or use a conservative non-zero estimate derived from the transaction's compute-unit consumption.

### Proof of Concept
1. Attacker deposits/locks funds and creates a `UniversalTx` with an SVM outbound and a non-zero `GasFee`.
2. The broadcaster submits the transaction to Solana; the payload consumes gas and reverts, leaving no `ExecutedTx` PDA.
3. `resolveSVM` sees `executed=false` and `clusterTime > deadline + svmRevertSlackSeconds`.
4. It calls `voteOutboundFailureAndMarkReverted(..., gasFeeUsed="0", ...)`.
5. Honest UVs run the same resolver logic and converge on the same ballot.
6. `VoteOutbound` finalizes the outbound as `OBSERVED` with `obs.Success=false` and `obs.GasFeeUsed="0"`.
7. `FinalizeOutbound` → `handleFailedOutbound` → `applyGasRefund` computes `refundAmount = gasFee - 0 = gasFee` and refunds the full amount, while the protocol has already paid the Solana gas cost.
