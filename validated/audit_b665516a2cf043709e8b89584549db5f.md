### Title
Unprivileged pre-funding of the deterministic ProgramData address permanently blocks `DeployWithMaxDataLen` (DOS) - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
`DeployWithMaxDataLen` derives the target `ProgramData` account address deterministically from the new program's pubkey via `Pubkey::find_program_address(&[new_program_id.as_ref()], program_id)` and then creates it with a plain `system_instruction::create_account` CPI. Because this address is a PDA with no private key, any unprivileged party who learns the intended program pubkey (e.g. by observing a not-yet-landed deploy transaction, or because deployers commonly generate/announce the program keypair ahead of time) can send a normal SOL transfer to that address before the legitimate `DeployWithMaxDataLen` transaction lands. This mirrors the reported bug class in the external report: pre-creating/funding a deterministic account at a known address to force a subsequent privileged `create_account`-style operation to permanently fail.

### Finding Description
Inside `process_loader_upgradeable_instruction` (handling `UpgradeableLoaderInstruction::DeployWithMaxDataLen`), the ProgramData address is derived and validated: [1](#0-0) 

The account is then created via a native CPI to the System Program's `CreateAccount` instruction: [2](#0-1) 

The System Program's `create_account` handler unconditionally rejects the creation if the target account already has any lamports: [3](#0-2) 

Since `programdata_key` is a program-derived address with no signing key, any unprivileged actor can send a plain `SystemInstruction::Transfer` (or any lamport-crediting transaction) to that address before the deployer's `DeployWithMaxDataLen` transaction executes. Once the account holds `lamports > 0`, the subsequent `create_account` CPI inside `DeployWithMaxDataLen` will always return `SystemError::AccountAlreadyInUse`, permanently preventing that specific program pubkey from ever being deployed as an upgradeable program (the address is derived solely from `new_program_id`, so it cannot be changed without abandoning that program keypair entirely).

Notably, the codebase already contains a purpose-built mitigation for exactly this class of pre-funding griefing — `create_account_allow_prefund`/`CreateAccountAllowPrefund`, which explicitly skips the "already has lamports" check: [4](#0-3) 
However, `DeployWithMaxDataLen` in `bpf_loader` still uses the plain, non-prefund-tolerant `system_instruction::create_account` path, so it remains exposed.

### Impact Explanation
This is a griefing/DOS vector reachable from an ordinary, unprivileged client transaction (a simple lamport transfer to a known PDA). It does not cause fund loss or consensus divergence, but it permanently prevents deployment of a specific upgradeable program via `DeployWithMaxDataLen` for that program pubkey, forcing the deployer to discard the announced program keypair and redeploy under a new identity — analogous to the reported LaunchEvent DOS where an attacker front-runs pair creation to permanently block a contract's core functionality.

### Likelihood Explanation
Exploitation requires only knowledge of the intended `new_program_id` before the deploy transaction lands (commonly known in advance, since deployers frequently pre-generate/announce program keypairs, or the transaction can be observed in flight) and the ability to send an ordinary System Program transfer — both trivially available to any network participant with minimal SOL. No privileged role, validator collusion, or race beyond ordinary transaction ordering is required.

### Recommendation
Change `DeployWithMaxDataLen` (and any other loader path that creates a deterministic PDA-derived account) to use the prefund-tolerant creation path (`create_account_allow_prefund` / `CreateAccountAllowPrefund`) instead of the strict `system_instruction::create_account`, so that pre-existing lamports at the derived address do not block legitimate account creation.

### Proof of Concept
1. Attacker observes/derives `new_program_id` for an upcoming deploy (e.g., from a pending `DeployWithMaxDataLen` transaction in the mempool, or a publicly announced program keypair).
2. Attacker computes `programdata_key = find_program_address([new_program_id], bpf_loader_upgradeable::id())`.
3. Attacker submits a plain `SystemInstruction::Transfer` sending 1 lamport to `programdata_key` and it lands before the legitimate deploy transaction.
4. The legitimate `DeployWithMaxDataLen` transaction now fails permanently at the `native_invoke_signed(create_account, ...)` step with `SystemError::AccountAlreadyInUse`, per `programs/system/src/system_processor.rs:161-171`, because `programdata_key` already has `lamports > 0`.
5. The deployer can never deploy an upgradeable program under `new_program_id`; they must pick a new program keypair.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
