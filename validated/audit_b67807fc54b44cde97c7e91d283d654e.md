## Title
Permanently Frozen Funds in Uninitialized Deterministic (`0s…`) Accounts When Their Bound `GlobalContractIdentifier` Never Resolves — (File: `runtime/runtime/src/deterministic_account_id.rs`)

## Summary
NEP‑616 deterministic accounts intentionally support pre‑funding: a `Transfer` action can create an "uninit" `0s…` account before the follow‑up `DeterministicStateInitAction` activates it. The account's contract reference (`GlobalContractIdentifier`, either `CodeHash` or `AccountId`) is baked immutably into the account ID itself (it is part of the hashed `DeterministicAccountStateInit`). If that identifier never resolves to an existing global contract on the receiving shard — because the referenced global contract was never deployed, was deployed on a different shard whose distribution stalls, or the owning account chooses not to deploy it — the `DeterministicStateInitAction` permanently fails with `GlobalContractDoesNotExist`. Since the account ID is a hash of the exact `state_init` (including `code`), the identifier cannot be changed without producing a different account, and an uninit deterministic account has neither an access key nor deployed code, so the previously transferred balance can never be moved, refunded, or reclaimed. This mirrors the Eigenlayer report's root cause: an immutable reference to an externally‑controlled, mutable/absent resource, fixed at "asset creation" time, that can block value that has already been deposited with no recovery path.

## Finding Description
`DeterministicAccountStateInit` embeds a `code: GlobalContractIdentifier` field, and the account ID is derived deterministically from the borsh‑encoded struct via `derive_near_deterministic_account_id` [1](#0-0) , meaning the code reference is permanently fixed for that specific account address and cannot be altered post hoc — exactly like the immutable `asset -> strategy` mapping in `RioLRTAssetRegistry`.

The docs explicitly document the intended two‑step lifecycle: a plain `Transfer` can fund a not‑yet‑existing deterministic account, and "the account will not be usable, however, until the `DeterministicStateInitAction` is also executed" [2](#0-1) .

When the `Transfer` arrives first, `action_implicit_account_creation_transfer` creates the account with `AccountContract::None` and, critically, no access key at all [3](#0-2) , `create_deterministic_account` [4](#0-3) .

When the subsequent `DeterministicStateInitAction` is processed, `deploy_deterministic_account` calls `use_global_contract` with the embedded identifier [5](#0-4) . `use_global_contract` checks whether `TrieKey::GlobalContractCode { identifier }` exists in this shard's state and, if not, sets an unrecoverable `GlobalContractDoesNotExist` action error and returns without changing account state [6](#0-5) . The action documentation itself confirms this is an execution error that can persist arbitrarily: "`GlobalContractDoesNotExist` if the referenced global contract does not exist on the shard of the receiver. (It may take a while for it to propagate to all shards.)" [7](#0-6)  — but if the identifier was never deployed anywhere (wrong/arbitrary hash, or an `AccountId` whose owner never deploys a global contract, or deliberately withholds/retracts the deployment step of a multi‑party protocol such as the `spread()` sharded‑contract pattern that itself constructs such state‑init receipts [8](#0-7) ), this failure is permanent, not transient.

Because the account remains in the "uninit" state (`account.contract().is_none()`), it has no code to call and (per `create_deterministic_account`) no access key, so no future transaction can ever move the funds: `Transfer` targeting an already-existing account works only because a bare `Transfer` action itself doesn't require the receiver to have code or keys to *receive* funds, but there is no way to *originate* an outgoing action from an account with zero access keys and no controllable contract logic.

## Impact Explanation
Funds sent to a deterministic account whose bound `GlobalContractIdentifier` never resolves are permanently and irrecoverably frozen: there is no admin override, no timeout-based refund, and no way to change the identifier without changing the account address itself (it's baked into the hash). This falls squarely into the "permanently frozen funds" impact category validated in the prompt rules, reachable purely through a sequence of ordinary, unprivileged transactions (`Transfer` then `DeterministicStateInitAction`) from a transaction signer or a contract acting on their behalf (e.g., the documented `spread()` pattern that autonomously issues both actions).

## Likelihood Explanation
This requires only two ordinary actions from a single account, exactly as documented/intended by the pre‑funding feature [9](#0-8) ; no validator collusion, network‑layer manipulation, or privileged role is needed. It can occur accidentally (a user or dApp derives/sends to a deterministic address for code that is later never deployed, or whose deployment is delayed/aborted) or can be engineered by a counterparty who controls whether/when the referenced global contract is deployed, mirroring the "third party changes external mutable state after the depositor has committed funds" pattern from the original report.

## Recommendation
Provide a recovery path for uninitialized deterministic accounts whose bound global-contract identifier cannot be resolved, e.g.: allow a `Transfer`/`DeleteAccount`-style refund from an "uninit" deterministic account back to the original sender if `DeterministicStateInitAction` fails with `GlobalContractDoesNotExist` (similar to how `LackBalanceForState` triggers a refund receipt in the same function [10](#0-9) ), or require a validity/liveness proof that the referenced `GlobalContractIdentifier` already exists on-chain (with an explicit propagation timeout and automatic refund) before honoring a `Transfer` to a not-yet-created deterministic account.

## Proof of Concept
1. Craft a `DeterministicAccountStateInit` whose `code` is `GlobalContractIdentifier::CodeHash(H)` for an `H` that has never been deployed via `DeployGlobalContract` (or `GlobalContractIdentifier::AccountId(owner)` where `owner` never deploys one).
2. Derive the deterministic account id with `derive_near_deterministic_account_id(&state_init)` [11](#0-10) .
3. Send a `Transfer` action to this not-yet-existing `0s…` account — this succeeds and funds the "uninit" account, exactly as demonstrated by `test_deterministic_state_init_prepay_for_storage` [12](#0-11) .
4. Send `DeterministicStateInitAction` referencing the same `state_init` — it fails permanently with `ActionErrorKind::GlobalContractDoesNotExist` because `H`/`owner`'s contract is never present in `TrieKey::GlobalContractCode` [13](#0-12) .
5. Because the account has `AccountContract::None` and no access key, and because `code` is fixed inside the address-deriving hash, the deposited balance can never be spent, refunded, or reassigned to a working `code` reference — it is permanently frozen.

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let data = borsh::to_vec(&state_init).expect("borsh must not fail");
    let hash = sha3::Keccak256::digest(&data);
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

### Deterministic account creation

Deterministic accounts cannot be created with a `CreateAccount` nor with a `Transfer` action.
A special action, `DeterministicStateInitAction`, is required.
This action validates that the account id matches its initial state.

As with all account types, you have to attach a large enough deposit to cover for the account storage. If the code and
initial state is small enough to fit below the zero-balance limit, no balance is required. The
`DeterministicStateInitAction` has a field to include a balance specifically to cover storage. Anything above the
required amount to cover storage requirements is refunded.

A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable,
however, until the `DeterministicStateInitAction` is also executed.

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

/// Deploy a new instance of the sharded contract on a different account.
///
/// expect input to be a single string that's the receiver
#[unsafe(no_mangle)]
pub unsafe fn spread() {
    // Owner must be set as input arg
    input(REG_INPUT);
    let owner = register_to_memory(REG_INPUT);

    // derive id to be created
    let state_init = construct_state_init(owner);
    let receiver_id = derive_near_deterministic_account_id(&state_init);

    // Create a new receipt
    let promise_idx = promise_batch_create(receiver_id.len() as u64, receiver_id.as_ptr() as u64);

    // If the predecessor has sent balance, pass it on to fund the new account.
    let attached = {
        let mut buf = [0u8; 16];
        attached_deposit(buf.as_mut_ptr());
        u128::from_le_bytes(buf)
    };
    let send_balance = if attached > 0 {
        // Pass on refund_to, ensuring the predecessor gets the balance back in case of refund.
        refund_to_account_id(REG_A);
        promise_set_refund_to(promise_idx, u64::MAX, REG_A);
        attached
    } else {
        // Use our own balance to send as much balance as needed to the receiver.
        // Keep the refund to ourself.
        std::cmp::min(free_balance(), new_account_storage_cost(&state_init))
    };
    let send_balance_bytes = send_balance.to_le_bytes();

    // Add state init action
    let action_idx = match sharded_contract_id() {
        GlobalContractIdentifier::CodeHash(hash) => promise_batch_action_state_init(
            promise_idx,
            hash.as_bytes().len() as u64,
            hash.as_bytes().as_ptr() as u64,
            send_balance_bytes.as_ptr() as u64,
        ),
        GlobalContractIdentifier::AccountId(account_id) => {
            promise_batch_action_state_init_by_account_id(
                promise_idx,
                account_id.as_bytes().len() as u64,
                account_id.as_bytes().as_ptr() as u64,
                send_balance_bytes.as_ptr() as u64,
            )
        }
    };

    // Add data record to state init action
    set_state_init_data_entry(
        promise_idx,
        action_idx,
        OWNER_KEY.len() as u64,
        OWNER_KEY.as_ptr() as u64,
        // read the value from register rather than memory
        u64::MAX,
        REG_INPUT,
    );

    log(&format!("spreading to {receiver_id}"));
    promise_return(promise_idx);
}

/// Ensure we can pre-pay the balance for a deterministic account.
///
/// It is a required feature that one can send a Transfer to a non-existing
/// deterministic account first and later initialize it without adding balance,
/// even if more storage than the ZBA limit is used.
#[test]
fn test_deterministic_state_init_prepay_for_storage() {
    let mut env = TestEnv::setup(Balance::from_near(100));
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let data = BTreeMap::from_iter([(b"key".to_vec(), vec![0u8; 100_000])]);
    let (state_init, det_account) = env.new_deterministic_account_with_data(data.clone());

    // Try once without pre-paying, must fail.
    let outcome = env
        .try_deploy_deterministic_account_with_data(data.clone(), Balance::ZERO)
        .expect("should be able to send transaction");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::LackBalanceForState { .. },
            index: _
        }))
    );

    // Prepay
    let required_for_storage = env.balance_for_storage(state_init);
    env.fund_with_near_balance(det_account.clone(), required_for_storage);
    assert_eq!(
        required_for_storage,
        env.get_account_state(det_account.clone()).amount,
        "account should have been created and funded now"
    );
