### Title
State-snapshot restore in `KvOnly` mode commits key-value data without verifying the `SparseMerkleRangeProof` against the trusted root hash — ([File: storage/aptosdb/src/state_restore/mod.rs])

### Summary
The Aptos state-snapshot restore path (`StateSnapshotRestore::add_chunk`) is supposed to bind every restored `(key, value)` chunk to a cryptographically-verified `expected_root_hash` via a `SparseMerkleRangeProof`, exactly analogous to the "authenticated proof accepted as valid" invariant in the task scope. When `StateSnapshotRestoreMode::KvOnly` is used, the proof argument is accepted by the API but is never checked before the chunk is written to the state-KV database.

### Finding Description
`StateSnapshotReceiver::add_chunk` dispatches on `restore_mode`: [1](#0-0) 

- In `StateSnapshotRestoreMode::Default`, the code explicitly does `verify_chunk(...)` on the Jellyfish Merkle tree side before writing the chunk into `kv_restore`, then `commit_chunk()` — this correctly binds the raw KV bytes to the proof/root hash.
- In `StateSnapshotRestoreMode::TreeOnly`, `add_chunk_impl` verifies+commits into the tree, but never writes the actual values into the KV store at all (`StateValueRestore` is untouched in this branch).
- In `StateSnapshotRestoreMode::KvOnly`, the code calls `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?` **directly**, with no call to `verify_chunk`/`add_chunk_impl` at all. The `proof: SparseMerkleRangeProof` parameter that was passed in is silently discarded.

`StateValueRestore::add_chunk` itself performs no hashing/verification either — it just writes the raw values to the KV batch and advances progress: [2](#0-1) 

This means in `KvOnly` mode, any `(key, value)` pairs supplied by whoever controls the `BackupStorage` implementation (e.g., an S3/GCS bucket or a custom backup service) are committed to the durable `state_kv_db` with **no cryptographic binding** to the previously-verified snapshot root hash.

This matters because the restore coordinator explicitly performs a two-phase, "KV" + "Tree" split restore that is designed around the assumption that proofs bind the data: [3](#0-2) 

- Phase 1.a restores the KV-only snapshot at `kv_snapshot.version` using `StateSnapshotRestoreMode::KvOnly` — this is precisely the vulnerable path, and it writes the actual queryable/executable state values with no proof check.
- Phase 1.b replays transactions from `kv_snapshot.version+1` to `tree_snapshot.version` to advance those (potentially tampered) KV values.
- Phase 2 later restores the tree at `tree_snapshot.version` using `TreeOnly` mode, which verifies hashes against the manifest's SparseMerkleRangeProof — but crucially `TreeOnly` **never writes or re-reads the actual KV values**, so it cannot catch that phase 1's KV data was unverified. The two phases operate on independent chunk downloads and never cross-check that the persisted `state_kv_db` bytes hash to the values embedded in the verified Merkle tree.

The manifest-level `root_hash` check performed once in `StateSnapshotRestoreController::run_impl` (`txn_info_with_proof.verify(...)`, `ensure!(state_root_hash == manifest.root_hash, ...)`) only authenticates the single root hash claimed by the manifest — it says nothing about whether the individual chunk bytes handed to `add_chunk` actually correspond to that root. That binding is supposed to be enforced per-chunk by `SparseMerkleRangeProof` verification, which is exactly what is skipped in `KvOnly` mode.

### Impact Explanation
This breaks the "restore paths must preserve deterministic proof binding" and "authenticated ... responses must stay bound to the right ... root" invariants explicitly called out in scope. A backup storage backend that is buggy, compromised, or otherwise not fully trusted (which is the entire reason the SparseMerkleRangeProof mechanism exists — to avoid trusting the storage backend) can inject **arbitrary corrupted account/resource state values** into a restoring node's durable ledger state, with zero cryptographic verification, whenever the `KvOnly` restore mode path (used by the standard split-phase backup-restore coordinator) is exercised. Corrupted state persisted this way:
- Is served as authoritative "committed state" via the state-KV database, feeding subsequent VM execution, API state reads, and further ledger operation on the restoring node.
- Can silently diverge from the correct VM/consensus-derived state without being caught later, since the follow-up `TreeOnly` tree restore verifies its own independently downloaded value hashes against the merkle proof, but never re-validates the already-committed KV bytes against those hashes.

This is a direct "committed state that differs from the correct VM result / corrupts durable ledger data" and "restore flow reinterprets committed data into a different ledger state" scenario named in the state-integrity gate.

### Likelihood Explanation
Exploitation requires control over (or compromise of) the `BackupStorage` data source used during a restore that exercises the split KV/Tree restore path (`KvOnly` then `TreeOnly`), which is the standard restore flow whenever a KV-only snapshot precedes the tree snapshot (`do_phase_1` branch in `coordinators/restore.rs`). Since operators regularly restore nodes from durable/cloud backup storage that they may not fully control or that may itself be compromised, and the code explicitly relies on the proof mechanism to avoid needing to trust that storage, this is a realistic misuse of an intentionally-designed trust boundary, not merely an admin-privilege scenario.

### Recommendation
In `StateSnapshotRestore::add_chunk`'s `KvOnly` branch, verify the incoming chunk's `(key, value.hash())` pairs against `expected_root_hash` using the supplied `SparseMerkleRangeProof` (as `Default`/`TreeOnly` already do) before calling `kv_restore.add_chunk`. If per-chunk verification state cannot be maintained without the tree structure, at minimum recompute a range proof check independent of `JellyfishMerkleRestore`, so that no chunk is committed to `state_kv_db` without being bound to the authenticated root hash.

    pub fn add_chunk(&mut self, mut chunk: Vec<(K, V)>) -> Result<()> {
        // load progress
        let progress_opt = self.db.get_progress(self.version)?;

        // skip overlaps
        if let Some(progress) = progress_opt {
            let idx = chunk
                .iter()
                .position(|(k, _v)| CryptoHash::hash(k) > progress.key_hash)
                .unwrap_or(chunk.len());
            chunk = chunk.split_off(idx);
        }

        // quit if all skipped
        if chunk.is_empty() {
            return Ok(());
        }

        // save
        let mut usage = progress_opt.map_or(StateStorageUsage::zero(), |p| p.usage);
        let (last_key, _last_value) = chunk.last().unwrap();
        let last_key_hash = CryptoHash::hash(last_key);

        // In case of TreeOnly Restore, we only restore the usage of KV without actually writing KV into DB
        for (k, v) in chunk.iter() {
            usage.add_item(k.key_size() + v.value_size());
        }

        // prepare the sharded kv batch
        let kv_batch: StateValueBatch<K, Option<V>> = chunk
            .into_iter()
            .map(|(k, v)| ((k, self.version), Some(v)))
            .collect();

        self.db.write_kv_batch(
            self.version,
            &kv_batch,
            StateSnapshotProgress::new(last_key_hash, usage),
        )
    }

    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())
    }
