### Title
Shared `last-update` clock is advanced whenever the debt index changes, permanently starving the liquidity index of accrual time due to rounding — ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
`accrue` in the vault contracts (e.g. `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) computes two independent indexes — the debt `index` and the `lindex` (liquidity index) — from a single shared clock, `last-update`. That clock is only advanced when *either* index actually changes value. Because the debt index rounds its multiplier **up** (`calc-multiplier-delta ... true`) while the liquidity index rounds **down** and is computed from a smaller, fee/utilization-reduced rate, the debt index changes far more easily than the liquidity index. Every time `accrue` is called and the debt index ticks, `last-update` resets to `stacks-block-time`, wiping out the `time-delta` that the liquidity index needed to accumulate before its own rounded-down multiplier could become non-zero. This mirrors the C4 VTVL finding: truncation causes an accrual to be silently rounded to zero, but here the shared "clock" resets before the truncated quantity ever gets a chance to catch up, turning a temporary rounding delay into a potentially indefinite stall.

### Finding Description
`next-index` and `next-liquidity-index` both derive their `time-delta` from the same `last-update` variable: [1](#0-0) 

- `next-index` uses `calc-multiplier-delta rate time-delta true` (round-up), so almost any positive `rate * time-delta` produces a strictly larger-than-`INDEX-PRECISION` multiplier, i.e. the debt `index` changes almost every block it's called with a non-zero rate.
- `next-liquidity-index` uses `calc-multiplier-delta liquidity-rate time-delta false` (round-down), where `liquidity-rate` is `rate` further scaled down by utilization and `(1 - reserve-factor)` via `calc-liquidity-rate`: [2](#0-1) 

`accrue` then updates the shared clock only if either index moved: [3](#0-2) 

Sequence:
1. `accrue` is called (directly or via `system-borrow`/`system-repay`/deposit/redeem flows that call it first).
2. Debt `index` changes (round-up guarantees this whenever `rate > 0` and `time-delta > 0`), so the `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` branch fires and `last-update` is reset to now — even though `lindex` did **not** change.
3. On the next call, `next-liquidity-index`'s `time-delta` is computed from the just-reset `last-update`, so it is small again, and `mul-div-down` (round-down) truncates `liquidity-rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS` back to zero.
4. This repeats on every subsequent call as long as the debt index keeps moving (which it almost always does, since it rounds up), so `lindex` never accumulates enough `time-delta` in one shot to produce a non-zero increment — the liquidity index effectively freezes rather than merely lagging by a bounded number of days as in the original VTVL finding.

The root cause is identical in class to the report: a value (`liquidity-rate * time-delta`) that must exceed a truncation threshold to register, combined with a shared clock (`last-update`) that gets invalidated/reset by an unrelated event (the debt index's own, easier-to-trigger change) before the truncated quantity can cross that threshold.

### Impact Explanation
`lindex` represents accrued yield attributable to depositors/liquidity providers (as distinct from `index`, which tracks borrower debt growth). If `lindex` is perpetually reset before it can grow, depositor-side yield accrual is stalled indefinitely even though borrowers keep accruing debt via `index`. This is a temporary-to-indefinite freezing of unclaimed yield for LPs, since the yield is not being lost from a ledger balance permanently destroyed, but its accrual is stuck as long as the debt index keeps ticking on a shorter cadence than the liquidity index needs. This lands in the **temporary freezing of funds** (unclaimed yield) impact category.

I was not able to fully trace, within the remaining tool budget, every downstream consumer of `lindex` (it is referenced 10 times in `mainnet/contracts/market/v0-4-market.clar`) to confirm the exact user-facing effect (e.g., whether it feeds directly into an exchange-rate/APY calculation for `zft` shares or into a separate liquidity-index-based accounting path). This should be verified before treating severity as final.

### Likelihood Explanation
This requires no attacker action — it is a natural consequence of routine `accrue` calls (triggered by normal borrow/repay/deposit/redeem activity) whenever the interest rate is low-to-moderate or utilization/reserve-factor scaling makes `liquidity-rate` small relative to `rate`. The round-up vs round-down asymmetry between the two indexes means this condition is easily reachable under realistic interest-rate and utilization parameters, not just contrived edge cases.

### Recommendation
Track `last-update` (or an equivalent "last accrued time") independently for `index` and `lindex`, so that a change in one index does not erase the accumulated `time-delta` still needed by the other. Alternatively, always advance the shared clock on every `accrue` call regardless of whether either index changed, but only after safely carrying over the truncated remainder (e.g., accumulate leftover interest in a per-index remainder accumulator) so no accrual window is silently dropped.

### Proof of Concept
1. Configure a reserve-factor/utilization combination such that `liquidity-rate` (from `calc-liquidity-rate`) is meaningfully smaller than `rate`, e.g. high reserve factor and moderate utilization.
2. Call `accrue` (or any action that triggers it) repeatedly at short intervals (a few seconds/blocks apart) with `rate > 0`.
3. Observe that `index` moves every call (due to round-up in `calc-multiplier-delta`), which resets `last-update` to `stacks-block-time` each time per the `accrue` logic at [4](#0-3) .
4. Observe that `lindex` never changes across these calls because `next-liquidity-index`'s `time-delta` is always reset to near-zero before `liquidity-rate * time-delta` can produce a non-zero rounded-down multiplier, per [5](#0-4) .
5. Confirm depositor-side yield tracked via `lindex` remains stuck at `INDEX-PRECISION` indefinitely while borrower debt (`index`) keeps growing.
