## Analysis

The Panoptic bug's root cause is **an automatic callback that re-enters and re-triggers state-mutating logic before the outer transaction finishes**, causing the same operation to be processed twice against inconsistent state. The closest structural analog in Push Chain is not a Solidity reentrancy lock, but the **EVM `PostTxProcessing` hook combined with `DerivedEVMCall`**, which produces a duplicate invocation of the exact same universal-tx/outbound creation logic within a single message handler.

### Title
Double invocation of `CreateUniversalTxFromReceiptIfOutbound` via `EVMHooks.PostTxProcessing` and the explicit `ExecutePayload` call path breaks outbound-creating payload execution - (File: x/uexecutor/keeper/msg_execute_payload.go)

### Summary
`ExecutePayload` calls `k.CallUEAExecutePayload` (a `DerivedEVMCall` with `commit=true`), which the project's own documentation states produces "a JSON-RPC visible receipt... same as a user `MsgEthereumTx`" [1](#0-0) . The chain registers a global EVM hook, `uexecutorkeeper.NewEVMHooks`, that runs `PostTxProcessing` after every committed EVM transaction [2](#0-1) , and that hook unconditionally calls `CreateUniversalTxFromReceiptIfOutbound` on the receipt [3](#0-2) . Immediately after `CallUEAExecutePayload` returns, `ExecutePayload` calls the *same* `CreateUniversalTxFromReceiptIfOutbound` function again, with an equivalent `pcTx` derived from the identical `evmFrom`/`receipt.Hash`/`BlockHeight` [4](#0-3) .

### Finding Description
`CreateUniversalTxFromReceiptIfOutbound` derives a UTX key from the `pcTx` fields, checks `HasUniversalTx`, and returns an explicit error if the key already exists: [5](#0-4) 

If the EVM's `PostTxProcessing` hook fires synchronously as part of applying the derived transaction underlying `CallUEAExecutePayload` (as the documentation implies by describing `DerivedEVMCall` as producing a receipt "same as a normal `MsgEthereumTx`" — the exact hook-invocation point lives in the pinned `github.com/pushchain/evm` fork, which is outside this repository's indexed source and could not be directly verified here), then for any payload whose execution causes the UEA to call the `UniversalGatewayPC` contract's outbound-emitting method:

1. The EVM commit inside `CallUEAExecutePayload` triggers `EVMHooks.PostTxProcessing`, which builds the identical `pcTx` (`Sender=evmFrom`, `TxHash=receipt.Hash`, `BlockHeight`, `Status="SUCCESS"`) and successfully calls `CreateUniversalTxFromReceiptIfOutbound`, creating the `UniversalTx` and attaching the `PendingOutbounds` entry.
2. Control returns to `ExecutePayload`, which computes the same `pcTx` fields and calls `CreateUniversalTxFromReceiptIfOutbound` a second time on the same underlying receipt.
3. `CreateUniversalTxFromPCTx` finds the UTX key already present and returns `"universal tx already exists for pc tx %s"`, which propagates as an error out of `ExecutePayload`.
4. Because Cosmos SDK message handlers are atomic, this error reverts the *entire* transaction — including the `UniversalTx`/`PendingOutbounds` state that was validly created by the hook and the EVM-side effects of the payload (e.g., funds locked/burned in the gateway as part of the legitimate outbound request).

This mirrors the SFPM bug's structural pattern: an automatic re-invocation of core accounting logic (there: `_mint`'s ERC1155 callback re-entering `burn`; here: the global `PostTxProcessing` hook re-entering the same UTX-creation code path invoked explicitly by the caller) causes the invariant "one outbound event -> exactly one `UniversalTx`/outbound record" to be evaluated twice against the same evolving state within one execution, producing an unintended failure mode instead of silent corruption.

### Impact Explanation
Every ordinary, unprivileged user submitting a `MsgExecutePayload` whose payload triggers a UEA call into `UniversalGatewayPC`'s outbound path would have their transaction unconditionally revert with "universal tx already exists," even though the EVM-side outbound-triggering call actually executed correctly. This is a state-machine/availability defect in a user-reachable default flow (`MsgExecutePayload` is any-user, gasless per `x/uexecutor/README.md`), not requiring any privileged actor, and it corrupts the reachability of the canonical `UniversalTx`/outbound creation flow described in the module's own README as the intended lifecycle. If instead of erroring, a variant of this pattern silently succeeded twice (e.g. if the second key derivation ever diverges from the first due to a field difference), it could instead produce a duplicate `OutboundTx`/`PendingOutbounds` entry for the same underlying event, which would corrupt outbound accounting and could lead to a double broadcast/double payout by Universal Validators — the kind of "wrong outbound state" impact called out in the task's allowed-impact list.

### Likelihood Explanation
This requires no privileged access — any user who submits a `UniversalPayload` whose execution reaches the `UniversalGatewayPC` outbound-emitting method (a normal, intended usage pattern of UEAs) would trigger it. The likelihood of actually observing the failure depends entirely on whether the pinned EVM fork invokes registered `EvmHooks.PostTxProcessing` for `DerivedEVMCall`-originated transactions the same way it does for regular `MsgEthereumTx` — this repository's indexed source does not contain the fork implementation of `DerivedEVMCall`/`ApplyTransaction`, so this cannot be conclusively confirmed from within this repo alone.

### Recommendation
- Make `CreateUniversalTxFromReceiptIfOutbound` (and `AttachRescueOutboundFromReceipt`) idempotent by treating "UTX already exists for this pcTx key" as a benign no-op rather than an error when called from `ExecutePayload`/`msg_vote_inbound.go`-style explicit call sites, OR
- Remove the explicit call from `ExecutePayload` (and any other keeper code path that also relies on the receipt-driven EVM hook) and rely solely on the global `EVMHooks.PostTxProcessing` for outbound/UTX creation, so there is a single, unambiguous invocation point for this logic, consistent with the "single source of truth" principle already applied to `ModuleAccountNonce` in this codebase [6](#0-5) .
- Add an integration test that submits a real `MsgExecutePayload` whose payload calls the actual `UniversalGatewayPC` outbound method (not just a synthetic hook-only test like `TestPostTxProcessing_WithSyntheticOutboundEvent` [7](#0-6) ) to confirm whether the hook and the explicit call actually collide end-to-end.

### Proof of Concept
1. Deploy/fund a UEA for `evmFrom` via `MsgExecutePayload` as in `TestExecutePayload` [8](#0-7) .
2. Craft a `UniversalPayload.Data` whose `To` is the `UniversalGatewayPC` system contract and whose calldata invokes its outbound-triggering method (the one that emits `UniversalTxOutbound`, matching `x/uexecutor/types/constants.go`'s `UniversalTxOutboundEventSig` [9](#0-8) ), sign it, and submit via `MsgExecutePayload`.
3. Observe whether `ms.ExecutePayload` returns `"universal tx already exists for pc tx ..."` even though the EVM-side call succeeded — confirming the double-invocation collision — and whether the whole transaction (and the outbound entry created by the hook) is rolled back as a result.

```go
func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}
```
