### Title
Reachable panic in `DelayedReceiptQueueWrapper::receipt_filter_fn` via unbounded `.unwrap()` on `receiver_shard_id()` for stale `GlobalContractDistribution` receipts across multiple reshardings - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`Receipt::receiver_shard_id` can return `Err(EpochError::ShardingError(..))` when a `GlobalContractDistribution` receipt's recorded `target_shard` no longer exists in the current shard layout and cannot be resolved to a descendant shard via `resolve_to_current_shard`. This error path exists specifically to handle receipts that have sat in the delayed-receipt queue across multiple resharding events. However, the only caller in the runtime's congestion-control receipt-draining loop, `DelayedReceiptQueueWrapper::receipt_filter_fn`, discards the `Result` with `.unwrap()`, turning that recoverable error into a validator-crashing panic.

### Finding Description
`receipt_filter_fn` is called from `DelayedReceiptQueueWrapper::pop`, which is used while chunk-producing/applying-chunk nodes drain the persistent delayed-receipt trie queue during normal `apply()` execution of every chunk: [1](#0-0) 

The function it calls, `Receipt::receiver_shard_id`, explicitly documents that a `GlobalContractDistribution` receipt's `target_shard` "may be from an arbitrarily old layout (the receipt could have been delayed across multiple resharding events)" and returns an `Err(EpochError::ShardingError(...))` when `resolve_to_current_shard` cannot map the stale shard id to any shard in the current layout: [2](#0-1) 

Because `receipt_filter_fn` unwraps this `Result` rather than propagating it, any time a `GlobalContractDistribution` receipt becomes "doubly stale" (delayed across two or more resharding events such that its recorded `target_shard` is no longer present in *any* split-history chain reachable from the current layout), popping it from the delayed queue during `apply()` panics the node instead of returning an error.

`GlobalContractDistribution` receipts are created by an ordinary, permissionless action available to any account: deploying a global contract (`DeployGlobalContractAction`/`UseGlobalContract`). If such a receipt gets stuck in the delayed-receipt queue on a shard that is congested (e.g. via `burn_gas_raw`-style compute saturation, entirely achievable by an unprivileged transaction sender), and that shard undergoes two dynamic-resharding splits while the receipt is still delayed, the next time the runtime tries to pop it out of the delayed queue, `receipt_filter_fn` panics.

A repository test (`test_stale_global_contract_distribution_after_double_resharding`) exists specifically to reproduce and guard against this scenario, confirming both that the code path is reachable from ordinary transactions and that the underlying condition ("stale target_shard after double resharding") is a recognized concern in this codebase: [3](#0-2) [4](#0-3) 

The test's own comment makes the panic hazard explicit: [5](#0-4) 

This is analogous in root cause to CVE-2017-7452 (ImageWorsener BMP header parser: a code path that should reject malformed/edge-case input instead dereferences an unchecked null value and crashes). Here, a code path explicitly designed to *handle* an edge case (stale shard mapping) returns a proper `Result::Err`, but the sole call site discards that error handling with `.unwrap()`, causing an uncontrolled panic on attacker/network-triggerable input rather than a graceful rejection.

### Impact Explanation
A panic inside `Runtime::apply` (invoked from the chunk-application path used by every validator/chunk-producer processing that shard) is a transaction-triggered halt: every honest node that reaches the same delayed-receipt state will panic identically when attempting to apply the chunk that pops the stale receipt, producing a consensus-halting/liveness-denial condition for the affected shard (and potentially the whole chain, depending on deployment topology). This meets the "transaction-triggered halt" acceptance criterion — it is not a mere resource-exhaustion or purely operator-side issue; it is a deterministic crash reachable by unprivileged actors deploying global contracts and generating ordinary compute-heavy transactions to keep a receipt delayed across two force/organic resharding events.

### Likelihood Explanation
The trigger requires: (1) a permissionless global contract deployment (any signer can do this), (2) sufficient compute saturation on the target shard to keep the resulting `GlobalContractDistribution` receipt delayed (achievable via arbitrary heavy contract calls — no special privilege), and (3) two shard-split (resharding) events occurring on that shard while the receipt is delayed. Dynamic resharding is a supported protocol feature; whether it triggers organically on mainnet at a given time depends on operator/protocol configuration and epoch cadence, so likelihood is somewhat coupled to how aggressively dynamic resharding is enabled. Given that a dedicated regression test exists for exactly this scenario, the nearcore team has already identified this as a real, reachable hazard rather than a purely theoretical one.

### Recommendation
Do not `.unwrap()` the `Result` returned by `Receipt::receiver_shard_id` inside `receipt_filter_fn`. Instead, propagate the error up through `DelayedReceiptQueueWrapper::pop`'s `Result<Option<..>, RuntimeError>` signature (which already supports fallible returns), converting the `EpochError::ShardingError` into a `RuntimeError`/`StorageError::StorageInconsistentState` so a stuck stale receipt causes a controlled `apply()` error instead of a raw panic. Additionally consider a defensive fallback (e.g., treat an unresolvable `target_shard` as belonging to the current shard, or route it to a fixed "catch-all" shard) so the receipt can still be drained/executed rather than perpetually failing.

### Proof of Concept
1. Deploy a contract to an account `user0` and then deploy a **global contract** from `user0` (`DeployGlobalContractAction`), which creates a `Receipt::GlobalContractDistribution` receipt whose `target_shard` equals `user0`'s current shard.
2. Saturate `user0`'s shard's compute budget every block (e.g., call a contract method that burns close to the full per-chunk compute budget) so the `GlobalContractDistribution` receipt is pushed into, and remains in, the persistent delayed-receipt queue rather than being processed immediately.
3. Configure/force dynamic resharding so that `user0`'s shard is split twice while the receipt remains delayed, such that the receipt's original `target_shard` id is no longer resolvable via `ShardLayout::resolve_to_current_shard` in the shard layout current at the time the receipt is finally popped.
4. When the runtime's delayed-receipt draining logic (`DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`) attempts to pop and classify this receipt, `Receipt::receiver_shard_id` returns `Err(EpochError::ShardingError(..))`, and the `.unwrap()` in `receipt_filter_fn` panics, crashing every node that reaches this state on that shard.

This exact scenario is reproduced end-to-end in the existing test `test_stale_global_contract_distribution_after_double_resharding`: [6](#0-5)

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
