### Title
Cross-tenant offline session/access-token disclosure via unauthenticated `X-Shopify-Shop-Domain` header in fulfillment-service authentication - (File: packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts)

### Summary
`shopify.authenticate.fulfillmentService` verifies the incoming request's HMAC over the raw body only, then reads the shop identity from the `X-Shopify-Shop-Domain` request header — a value that is not part of the HMAC-signed content — and uses it directly to load that shop's offline session/access token and build an authenticated Admin API client.

### Finding Description
`api.fulfillmentService.validate` (`packages/apps/shopify-api/lib/fulfillment-service/validate.ts`) delegates to `validateHmacFromRequestFactory`, which computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it against the `X-Shopify-Hmac-Sha256` header [4](#0-3) . The `X-Shopify-Shop-Domain` header is never included in the signed material.

After this check passes, `authenticateFulfillmentServiceFactory` reads `shop` straight from that header — `const shop = request.headers.get(ShopifyHeader.Domain) || '';` — with no `sanitizeShop` call and no cross-check against the HMAC-signed body, then calls `ensureValidOfflineSession(params, shop)` to fetch that shop's stored offline session and mints an authenticated `admin` GraphQL/REST client from it [5](#0-4) .

Since a fulfillment-order-notification request is a legitimate one-time event that any merchant who enables a fulfillment service can trigger from their own store (their app must expose this public HTTP endpoint), an app developer/merchant able to trigger one such legitimate webhook for their own shop obtains a body + valid HMAC pair. Because the HMAC does not bind to the `X-Shopify-Shop-Domain` header, that same body/HMAC pair can be replayed against the same public endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop that also uses the same app (multi-tenant SaaS app). The library performs no verification that the header matches the shop that actually produced the signed body, so `ensureValidOfflineSession` will look up and return the victim shop's offline session/access token, and `adminClientFactory` will hand back a fully authenticated Admin API client scoped to that victim shop.

This mirrors the reported bug class: a privileged action (constructing an authenticated outbound API client bound to a specific shop's token) is performed using a value (`shop`) supplied by the caller and never cryptographically tied to the thing that was actually verified (the body's HMAC), rather than validated against the trusted, verified association Shopify's servers would have produced.

### Impact Explanation
An attacker who controls, or has one-time access to, a valid HMAC-signed fulfillment-service payload for their own shop (e.g., they run a fulfillment service integration themselves, or capture/replay one such request) can substitute the shop-identifying header to obtain an `admin` API context authenticated as any other shop installed on the same app instance, as long as that shop has a stored offline session. This is a cross-tenant access vulnerability: it can expose another merchant's store data and allow write operations via the Admin GraphQL/REST client returned in the authenticated context.

### Likelihood Explanation
Exploitation requires: (1) the target app to use `shopify-app-remix`/`shopify-app-react-router`'s `authenticate.fulfillmentService` helper, (2) the fulfillment-service endpoint to be reachable (it is, by design, a public HTTP endpoint that Shopify calls), and (3) the attacker to obtain one valid `(rawBody, X-Shopify-Hmac-Sha256)` pair — achievable by being a legitimate fulfillment-service integrator for their own store, since the secret used is the app's own `apiSecretKey`, shared across all shops using the app; no per-shop secret binds the HMAC to a shop. This makes exploitation feasible for any user/merchant who can install/configure the app as a fulfillment service on their own store and then replay the header against other tenants of the same app.

### Recommendation
Bind the shop identity to the verified content instead of trusting an unauthenticated header:
- Include the shop-domain header (or the shop identifier carried in the JSON body, e.g. `kind`/fulfillment order id fields Shopify sends) in the HMAC-signed input, matching how `webhooks.validate` treats `X-Shopify-Shop-Domain` as required-but-still-unauthenticated data, or
- After computing the offline session for the header-derived `shop`, cross-verify that the session/shop actually corresponds to the request by re-deriving/confirming shop identity from a value protected by the signature (e.g., requiring the fulfillment order/shop id embedded in the signed JSON body to match the session's shop), and
- At minimum, run the header value through `sanitizeShop` and document/enforce that `X-Shopify-Shop-Domain` cannot be trusted as an authorization boundary without this additional binding.

### Proof of Concept
1. App "MyFulfillmentApp" is installed on Shop A (attacker-controlled) and Shop B (victim), both using the same app-level `apiSecretKey`.
2. Attacker's Shop A triggers a legitimate fulfillment order notification, producing:
   - `rawBody = '{"kind":"FULFILLMENT_REQUEST", ...}'`
   - `X-Shopify-Hmac-Sha256 = HMAC-SHA256(apiSecretKey, rawBody)` (captured by the attacker's own server, since it's their fulfillment service endpoint)
   - `X-Shopify-Shop-Domain: shop-a.myshopify.com`
3. Attacker resends the same `rawBody` and same `X-Shopify-Hmac-Sha256` to the app's `/fulfillment_order_notification` endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `api.fulfillmentService.validate` recomputes the HMAC over `rawBody` only — it matches, since `rawBody` and the HMAC are unchanged; the header substitution is invisible to this check [6](#0-5) .
5. `authenticateFulfillmentServiceFactory` reads `shop = 'shop-b.myshopify.com'` from the header, loads Shop B's offline session via `ensureValidOfflineSession`, and returns an authenticated `admin` client for Shop B to the attacker-controlled request handler [5](#0-4) .

```typescript
export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
```
