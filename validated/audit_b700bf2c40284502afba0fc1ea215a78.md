## Analog Found: `x/uregistry` `TokenConfig.NativeRepresentation` update while inbounds are in flight

### Title
Unpaused `UpdateTokenConfig` lets an attacker straddle a PRC20 remapping to mint the new representation without backing the deposit that funded the old one — ([File: x/uregistry/keeper/msg_update_token_config.go])

### Summary
The NTE-2 bug is a class of "hot update of a redemption-critical mapping field with no pause and no fund migration, exploitable by racing the update transaction." Push Chain's `uregistry` module has the same shape: `TokenConfig.NativeRepresentation.ContractAddress` (which PRC20 contract a given external `(chain, token)` mints/burns against) can be overwritten via `MsgUpdateTokenConfig` at any time, with no pause on the token, no in-flight-UTX check, and no atomic migration of backing. `ExecuteInboundFunds`/`depositPRC20` re-reads this mapping live at *execution* time rather than at the time the source-chain event was locked/observed, so the PRC20 that gets minted depends on whatever config is active when validator quorum finalizes — not on what was true when the user's funds were actually locked on the source chain.

### Finding Description
`k.uregistryKeeper.UpdateTokenConfig` overwrites the entire `TokenConfig` row, including `NativeRepresentation.ContractAddress`, with only an existence check — no check that the token is disabled, no check for pending inbounds/outbounds referencing it: [1](#0-0) 

The mint path resolves the destination PRC20 by re-fetching `TokenConfig` at the moment of execution: [2](#0-1) 

Execution does not happen when the user's inbound event occurs on the source chain — it happens later, when quorum is reached in `VoteInbound`/`ExecuteInbound`, in the same block as the *finalizing* vote: [3](#0-2) 

Between the first UV vote (ballot creation) and the quorum-reaching vote, real wall-clock time and multiple blocks can elapse (UVs must independently observe, wait for source-chain confirmations, then submit `MsgVoteInbound`). This is the exact window the NTE-2 report describes: a mutable "which asset backs this note" field that can change between when a user's deposit is locked and when the protocol executes/settles it.

The reverse lookup path (`GetTokenConfigByPRC20`, used to resolve outbound assets and revert instructions) has the same characteristic — it is looked up live against whatever `TokenConfig` is currently indexed, not the mapping in effect when the corresponding inbound/outbound was created: [4](#0-3) [5](#0-4) 

### Impact Explanation
If the admin remaps a token's `NativeRepresentation.ContractAddress` from PRC20-A to PRC20-B (e.g., for a legitimate migration) without first disabling the token and draining/reconciling pending inbounds, any inbound that is mid-flight when the remap lands will mint PRC20-B on Push Chain even though the source-chain lock/vault event was for the asset originally backed by PRC20-A. This:
- mints an asset (PRC20-B) with no corresponding source-chain backing for that specific deposit (unauthorized/unbacked mint), and
- leaves the original backing (the funds locked on the source chain under the old mapping) unaccounted for, since nothing on Push Chain records that it should now back PRC20-A holders who redeem later.
This directly matches the reported impact class: "shifted to a different redemption method... not enough funds for all users to redeem... complete loss of funds for some holders," and the sandwich-timing exploitation the report calls out — an unprivileged party can simply time an ordinary deposit to straddle a publicly broadcast `MsgUpdateTokenConfig` transaction.

### Likelihood Explanation
`MsgUpdateTokenConfig` itself requires admin privilege, so a purely privileged-abuse framing is out of scope; the in-scope trigger here is the **unprivileged attacker's own transaction timing** around an otherwise legitimate/expected admin operation (e.g., a token migration), which is exactly the scenario the source report flags as the dangerous pattern. Given inbound execution is multi-block (finality wait + validator vote propagation) and reads the mapping live rather than pinning it at observation time, the race window is real and does not require any consensus-safety violation — only ordinary unprivileged transaction submission timed against a known/observed admin tx.

### Recommendation
- Require a token to be `Enabled=false` (paused) before `UpdateTokenConfig` may change `NativeRepresentation.ContractAddress`, and reject the update while any `PendingInbounds`/`PendingOutbounds` reference that `(chain, address)`.
- Snapshot/pin the resolved `NativeRepresentation.ContractAddress` on the `Inbound`/`UniversalTx` record at ballot-creation (first-vote) time rather than re-resolving it at execution time, so later admin changes cannot retroactively alter which PRC20 an in-flight deposit mints.
- If a remap must happen with tokens still live, require an explicit migration path that moves outstanding PRC20-A supply to PRC20-B (analogous to the report's "properly shift funds... to ensure all users can still redeem") rather than a silent config overwrite.

### Proof of Concept
1. Admin has token `T` on chain `eip155:1` mapped to PRC20 `A` via `TokenConfig.NativeRepresentation.ContractAddress = A`.
2. Attacker locks funds on `eip155:1` for token `T` (ordinary deposit); UV #1 submits `MsgVoteInbound` — ballot is created (`x/uexecutor/keeper/msg_vote_inbound.go` step 1–3), not yet finalized.
3. Before UVs #2/#3 vote (quorum), admin submits `MsgUpdateTokenConfig` for `T` changing `NativeRepresentation.ContractAddress` to `B` — accepted unconditionally since `UpdateTokenConfig` only checks existence (`x/uregistry/keeper/msg_update_token_config.go:11-23`).
4. UV #2/#3 vote, quorum reached; `ExecuteInboundFunds` → `depositPRC20` re-fetches `TokenConfig` and finds `NativeRepresentation.ContractAddress = B` (`x/uexecutor/keeper/handler.go:19-28`), so it mints `B` to the recipient instead of `A`.
5. Result: recipient holds `B` backed by nothing (the locked source-chain funds were intended to back `A`), while any pending redemption logic tied to `A`'s backing is now short by that amount.

// UpdateTokenConfig updates an existing token configuration in the uregistry.
func (k Keeper) UpdateTokenConfig(ctx context.Context, tokenConfig *types.TokenConfig) error {
	storageKey := types.GetTokenConfigsStorageKey(tokenConfig.Chain, tokenConfig.Address)

	// Check if the token config exists
	if has, err := k.TokenConfigs.Has(ctx, storageKey); err != nil {
		return err
	} else if !has {
		return fmt.Errorf("token config for %s on chain %s does not exist", tokenConfig.Address, tokenConfig.Chain)
	}

	if err := k.TokenConfigs.Set(ctx, storageKey, *tokenConfig); err != nil {
		return err
	}

// GetTokenConfigByPRC20 looks up a token config by PRC20 address via the
// PRC20Index (O(1)). Returns ErrNotFound if the registered chain doesn't match.
func (k Keeper) GetTokenConfigByPRC20(
	ctx context.Context,
	chain string,
	prc20Addr string,
) (types.TokenConfig, error) {

	if strings.TrimSpace(prc20Addr) == "" {
		return types.TokenConfig{}, fmt.Errorf("prc20 address is empty")
	}
	// Same canonical form as the index function, so any case variant hits the row.
	prc20Addr = canonicalPRC20(prc20Addr)

	// PRC20 addresses are globally unique by construction; MatchExact returns at most one.
	iter, err := k.TokenConfigs.Indexes.PRC20Index.MatchExact(ctx, prc20Addr)
	if err != nil {
		return types.TokenConfig{}, err
	}
	defer iter.Close()

	for ; iter.Valid(); iter.Next() {
		pk, err := iter.PrimaryKey()
		if err != nil {
			return types.TokenConfig{}, err
		}
		cfg, err := k.TokenConfigs.Get(ctx, pk)
		if err != nil {
			return types.TokenConfig{}, err
		}
		if cfg.Chain == chain {
			return cfg, nil
		}
	}

	return types.TokenConfig{}, collections.ErrNotFound
}
