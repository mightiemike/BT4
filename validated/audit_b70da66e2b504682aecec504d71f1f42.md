The vulnerable path is real and traceable end‑to‑end. `Signature::to_bytes` in `crates/aptos-crypto/src/slh_dsa_sha2_128s/slh_dsa_sigs.rs` is not just a display/API helper — it is the exact function invoked every time a `Transaction` hash is (re)computed for a SLH‑DSA-authenticated transaction.

## Title
Transaction-hash instability across `slh_dsa` crate upgrades due to re-serialization of `Signature::to_bytes` in commit-hash computation - (File: `crates/aptos-crypto/src/slh_dsa_sha2_128s/slh_dsa_sigs.rs`)

### Summary
`Signature::to_bytes` delegates directly to the third-party `slh_dsa::Signature<Sha2_128s>::to_bytes()` [1](#0-0) . This is not a cosmetic accessor: the `SerializeKey` derive macro used by `Signature` serializes via `ValidCryptoMaterial::to_bytes(self)` on every serde/BCS pass, not via cached raw bytes [2](#0-1) . The Aptos-node commit/proof-integrity invariant is that `transaction.committed_hash()` (computed via `bcs::to_bytes(txn)` over the whole `Transaction` enum, then hashed) must remain equal, forever, to the `transaction_hash` stored in `TransactionInfo` at commit time [3](#0-2) . Because that BCS serialization always calls `Signature::to_bytes()` on the in-memory `SlhDsaSignature<Sha2_128s>` object that was itself produced by parsing the stored raw bytes (`SlhDsaSignature::try_from(bytes)` in `from_bytes_unchecked`) [4](#0-3) , the round trip `bytes → parse → to_bytes()` is on the critical path of every hash re-verification, not just a one-time value cached from disk.

### Finding Description
The chain of custody for a committed SLH-DSA signed transaction's hash is:
1. At commit time, node A serializes the transaction (including the `Signature`) via BCS, using `slh_dsa` v_N's `to_bytes()`, producing bytes `X`, and stores `hash(X)` in `TransactionInfo.transaction_hash`.
2. On restore/replay/proof verification, a node (possibly running an upgraded `slh_dsa` v_{N+1} after a routine dependency bump) reads the raw bytes from storage, deserializes them into `SlhDsaSignature<Sha2_128s>` via `TryFrom<&[u8]>`, then recomputes the commit hash by calling `bcs::to_bytes(&Transaction)`, which invokes `Signature::to_bytes()` → `slh_dsa` v_{N+1}'s `to_bytes()`.
3. If `slh_dsa` v_{N+1} changed the *internal* byte layout it emits for a logically-equivalent signature (e.g., reordering FORS/Merkle authentication-path segments) while preserving `verify()` semantics — a legitimate kind of change a crypto crate could make since only `verify` correctness is part of its public contract, not exact byte-for-byte re-serialization identity — then `to_bytes()` would produce bytes `Y != X` for the very same parsed signature.
4. `hash(Y) != hash(X)`, so `committed_hash()` for the same historical transaction diverges from the value in the already-committed, immutable `TransactionInfo`.

This exact equality is checked pervasively throughout proof/restore verification code: `TransactionWithProof::verify` [5](#0-4) , `TransactionListWithProof::verify` [6](#0-5) , `TransactionOutputListWithProof::verify` [7](#0-6) , `verify_committed_transactions` in storage test-helper [8](#0-7) , and `verify_user_txn`/`verify_txn_outputs`/`verify_txn_list` in `fake_aptosdb.rs` [9](#0-8) . All of these would begin failing simultaneously for every historical SLH-DSA-authenticated transaction the moment a node's `slh_dsa` dependency is bumped to a version with a different (but verify-compatible) internal byte layout.

The unprivileged-input path is straightforward: anyone can submit a transaction authenticated with an SLH-DSA signature (this signature scheme is wired into `AccountAuthenticator`/`AnySignature`/`TransactionAuthenticator` and the public REST API type `SlhDsa_Sha2_128sSignature` [10](#0-9) ). Once committed, that transaction's hash-recomputation path is permanently pinned to the exact byte-serialization behavior of whatever `slh_dsa` crate version parses+reserializes it in the future.

### Impact Explanation
This is a hard-fork/consensus-divergence-class defect: nodes running different `slh_dsa` crate versions would compute different `committed_hash()` values for the identical, already-finalized historical transaction. Concretely this breaks:
- State-sync/fast-sync and archive restore (`TransactionWithProof`/`TransactionListWithProof`/`TransactionOutputListWithProof` verification against the accumulator-proven `TransactionInfo.transaction_hash`).
- Any full node/indexer doing `db-tool` replay-verify or `check_txn_info_hashes` debugging, which directly asserts `txn.committed_hash() == txn_info.transaction_hash()`.
- Authenticated API responses that return a `TransactionWithProof`, since the client-side verification of the returned proof would fail against the node's recomputed hash if the two peers/versions disagree.

Because the divergence depends purely on which `slh_dsa` crate version a node links against (an implementation detail with no semver contract for byte-for-byte serialization stability of internal representations, only for `verify()` correctness), this is entirely plausible following an innocuous, unreviewed dependency bump — it does not require any operator error or malicious behavior, satisfying the "hard-fork-only divergence" acceptance criterion.

### Likelihood Explanation
Likelihood depends on whether/when the upstream `slh_dsa` crate changes its internal signature byte layout for logically-equivalent signatures. There is currently no test in the repository that pins `to_bytes()` output against a golden vector; the existing `test_signature_serialization_round_trip` test [11](#0-10)  only exercises round-trip stability within the current dependency version — it would still pass immediately after an upgrade even if the upgrade silently changed the byte layout, because it re-derives the golden bytes from the same (new) crate version rather than comparing against a fixed historical vector.

### Recommendation
- Add a golden-vector regression test that hard-codes a signature byte sequence (from a fixed private key/message pair) produced by the current `slh_dsa` dependency version, and assert `Signature::to_bytes()` continues to produce byte-identical output after any dependency bump.
- Consider caching/preserving the originally-parsed raw signature bytes on the `Signature` struct (similar to how `LazyBlsSignature` retains its exact wire bytes as the canonical identity [12](#0-11) ) and have `to_bytes()` return those cached bytes rather than re-deriving them from the parsed third-party object, decoupling on-chain hash stability from the third-party crate's internal serialization behavior.
- Pin the `slh_dsa` crate to an exact version and treat any upgrade as a protocol-relevant change requiring explicit hash-stability review/testing before release.

### Proof of Concept
1. Generate an SLH-DSA keypair and sign a fixed message under `slh_dsa` crate version `N`; record `sig_bytes_N = signature.to_bytes()`.
2. Commit a `Transaction::UserTransaction` using this signature; record `committed_hash_N = transaction.committed_hash()` and the stored `TransactionInfo.transaction_hash`.
3. Bump the `slh_dsa` dependency to a hypothetical/future version `N+1` that changes internal Merkle-authentication-path ordering while preserving `verify()` correctness.
4. Deserialize the same `sig_bytes_N` via `Signature::try_from` (now using crate version `N+1`), then recompute `transaction.committed_hash()`.
5. Observe `committed_hash_{N+1} != committed_hash_N`, i.e., a mismatch against the immutable `TransactionInfo.transaction_hash` recorded at step 2 — reproducing the exact failure mode asserted against in `verify_committed_transactions` and `TransactionWithProof::verify`.

/// Computes the hash of a Transaction using BCS serialization.
/// This is the single source of truth for Transaction hash computation.
fn compute_transaction_hash(txn: &Transaction) -> HashValue {
    use aptos_crypto::hash::CryptoHasher;
    let bytes = bcs::to_bytes(txn).expect("Transaction serialization should not fail");
    let mut hasher = TransactionHasher::default();
    hasher.update(&bytes);
    hasher.finish()
}
