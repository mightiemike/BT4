### Title
Precompiled contract calls charge TRX/TRC10 endowment before execution and do not roll it back on failure - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress` transfers the call's endowment (TRX via `MUtil.transfer` or TRC10 via `deposit.addTokenBalance`) from the caller to the precompiled-contract address *before* the precompiled contract logic actually runs, with an explicit comment "Charge for endowment - is not reversible by rollback". If the precompiled contract's `execute(data)` subsequently fails (`out.getLeft()` is `false`), the surrounding smart-contract execution is not necessarily reverted — the caller can push zero onto the stack and simply continue — yet the endowment has already been debited from the sender, mirroring the "spend accounted before/independent of the actual effect" root cause described in the report for the streaming enforcers.

### Finding Description
In `Program.callToPrecompiledAddress` [1](#0-0) , a child repository `deposit` is created, and then the endowment transfer is performed unconditionally prior to invoking the precompiled contract: [2](#0-1) 

Only afterward is the actual precompiled logic executed via `contract.execute(data)`: [3](#0-2) 

On success, `deposit.commit()` is called to propagate all state changes (including the endowment transfer) to the parent repository. On failure (`out.getLeft()` is `false`), the code does *not* call `deposit.commit()`, but it also does not explicitly discard/rollback the `deposit` child repository object; it merely pushes zero and only throws if `this.result.getException()` is non-null. If no VM-level exception is set (i.e., the calling contract's Solidity code chooses to treat the failed precompile call as a soft failure and continue, analogous to the `EXECTYPE_TRY` scenario in the report), execution can continue in the parent frame without a revert — while the code path explicitly documents that the "charge for endowment... is not reversible by rollback," indicating that this transfer was designed to persist regardless of whether the precompiled operation actually completed.

This matches the report's root cause exactly: an accounting/balance mutation performed *before* the actual effect (the precompiled operation) completes, in a control-flow branch that permits the caller to continue without reverting the overall transaction when that effect fails.

### Impact Explanation
If a precompiled contract (e.g., a native-bridge, batch, or system precompile reachable via `CALL`) can return `false` from `execute()` in a way that does not set `result.getException()`, a caller contract using low-level `call` semantics (which does not force a revert on nonzero-but-failed precompile calls, similar to Solidity's try/catch or unchecked `.call()`) can repeatedly invoke it with endowment value, have the value permanently deducted from the sender and credited into the precompiled address, without the corresponding operation executing. Depending on which precompile is targeted, this could allow silent draining of TRX/TRC10 balance from unwary callers or "burn" value into a precompiled address with no corresponding action, causing an accounting divergence between expected and actual sender balance.

### Likelihood Explanation
This requires the caller (arbitrary user-deployed smart contract) to invoke a precompiled address with `CALL` + nonzero endowment, and for the underlying precompiled contract execution to be able to return `false` (failure) while leaving `result.getException()` null, and for the enclosing bytecode to continue without reverting on receiving `0` on the stack. Whether such non-exceptional failure return paths exist in java-tron's small set of precompiled contracts is uncertain from the code reviewed — the exact "false, no exception" behavior of specific `PrecompiledContract.execute()` implementations was not fully verified within the available tool budget. This is the main open uncertainty.

### Recommendation
Move the endowment/token transfer to occur only after `contract.execute(data)` returns success (`out.getLeft() == true`), or ensure the `deposit` child repository is unconditionally discarded (never partially applied) on failure so that the endowment charge is not persisted unless the precompiled operation actually succeeds and is committed.
