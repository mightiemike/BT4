### Title
Secondary index (program_id/spl_token_mint/spl_token_owner) forward+reverse maps grow unbounded with write frequency instead of being bounded by current account state - ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
`SecondaryIndex::insert` (`accounts-db/src/accounts_index/secondary.rs:133-171`) appends every distinct historical value written for a given account pubkey to the `reverse_index` Vec and to the corresponding forward `index` maps, and these stale entries are only purged when the account is fully removed from the primary index via `handle_dead_keys`/`purge_secondary_indexes_by_inner_key_if`. Because live-while-alive accounts never trigger this removal path, an attacker can pay only for repeated cheap writes (SPL token transfers/`SetAuthority`/reinitializations that change `owner`/`mint`/`owner-field` bytes) to the same account and cause the forward+reverse index maps to grow proportionally to the number of writes rather than the number of distinct accounts or the fees paid.

### Finding Description
`AccountsIndex::update_secondary_indexes` (`accounts-db/src/accounts_index.rs:614-660`) is called on every account store (`accounts_db.rs:4919` in `update_index_for_flush`, and `accounts_db.rs:4855` in `update_secondary_index_cached_accounts`) when `AccountSecondaryIndexes` are enabled. For an SPL-token/token-2022-owned account, `update_spl_token_secondary_indexes` calls `SecondaryIndex::insert(mint_or_owner, pubkey)` for `spl_token_mint_index`/`spl_token_owner_index`, and `program_id_index.insert(account_owner, pubkey)` for the program-owner. `SecondaryIndex::insert` at `secondary.rs:133-171` pushes a new outer key into `reverse_index[pubkey]` (a `Vec<Pubkey>`, `secondary.rs:61`) whenever the value differs from previously recorded ones (`if !outer_keys.contains(key) { outer_keys.push(*key); }`), and inserts a corresponding forward entry in `index[outer_key]`. Crucially, when an account's mint/owner value changes across writes (even within the same slot or a later slot), the old outer-key mapping is **not removed** — both old and new mappings persist as shown by `run_test_secondary_indexes_same_slot_and_forks` (`accounts_index.rs:2352-2454`), which asserts both `secondary_key1` and `secondary_key2` remain present in the index after both writes and even after a `clean_rooted_entries` pass, with the code comment explicitly stating "even though the account with secondary_key1 was outdated by the update in the later slot ... both secondary keys will still be kept alive." Removal only happens via `remove_by_inner_key_if`/`purge_secondary_indexes_by_inner_key_if`, invoked from `handle_dead_keys` paths (`accounts_index.rs:325-343`, `accounts_db.rs:1391-1411`) when the account's slot list becomes fully empty (i.e., the account is deleted, not merely rewritten). Since the attacker's account remains alive (nonzero lamports) throughout, this dead-key cleanup path never fires, so every distinct owner/mint value the attacker ever writes accumulates permanently in both the forward `index` DashMap and the `reverse_index` Vec for that pubkey.

### Impact Explanation
This matches the "secondary index memory exhaustion driven by write frequency rather than distinct accounts created" scoped impact: an attacker holding a single SPL-token-owned account can, for the fixed on-chain cost of many cheap transactions (e.g., alternating between two mints/owners via reinitialize or transfer/close+reopen cycles that flip indexable byte fields), cause `reverse_index[pubkey]`'s Vec to grow one entry per distinct value ever used, and correspondingly inflate `program_id_index`/`spl_token_mint_index`/`spl_token_owner_index` DashMap entries — memory growth proportional to write count, not to actual current state or account count, since cleanup is gated on account death (`purge_secondary_indexes_by_inner_key_if`) rather than on staleness of a given value.

### Likelihood Explanation
Requires `AccountSecondaryIndexes` to be enabled (validator config, e.g. `--account-index program-id spl-token-mint spl-token-owner`), which is an operator opt-in but not a privileged control over the attacker — the attacker is still an ordinary user issuing self-paid transactions. Given that precondition, the exploit is fully reachable via ordinary token operations (rotating mint/owner-affecting bytes) with no special permissions, and is trivially repeatable at high frequency, bounded only by the attacker's transaction throughput and fee budget.

### Recommendation
When inserting a new outer-key value for a pubkey whose reverse-index entry already exists with a different value obtained from the *current* account state (rather than any historical value ever seen while the account is alive), remove the stale forward-index mapping for the pubkey's previous value at insert time, so that a live account's footprint in the secondary index is bounded by O(1) or O(distinct concurrently-visible slot versions) rather than O(total historical writes). Alternatively, cap the number of retained outer-key values per reverse-index entry and evict oldest entries, accepting scan staleness as already tolerated by post-scan filtering.

    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }

        // explicitly drop the locks so we don't hold them while reporting metrics
        drop(outer_keys);
        drop(reverse_index_entry);

        if self.stats.last_report.should_update(1000) {
            datapoint_info!(
                self.metrics_name,
                ("num_secondary_keys", self.index.len(), i64),

                    i64
                ),
                ("num_reverse_index_keys", self.reverse_index.len(), i64),

    fn purge_secondary_indexes_for_dead_keys<'a>(
        &self,
        removed_keys: impl IntoIterator<Item = &'a Pubkey>,
    ) {
        if self.account_indexes.is_empty() {
            return;
        }
        for key in removed_keys {
            // Purging secondary entries for a key that is still alive in the primary index
            // would leave a live account invisible to secondary-index scans
            debug_assert!(
                !self.accounts_index.contains(key),
                "key removed from the primary index must not be present: {key}"
            );
            self.accounts_index.purge_secondary_indexes_by_inner_key_if(
                key,
                &self.account_indexes,
                || !self.accounts_cache.contains_pubkey(key),
            );
        }
