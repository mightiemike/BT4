### Title
External caller's attached deposit is permanently locked in the wallet contract when `address_check_callback` short-circuits with a failure - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
In the NEAR Wallet Contract (eth-implicit account emulation), an external, unprivileged caller can attach a NEAR deposit when invoking `rlp_execute` for an `EOABaseTokenTransfer` with an address check. `CallerDeposit` is created to guarantee that deposit is refunded if the subsequent cross-contract action fails. However, in `address_check_callback`, several failure branches return an `ExecuteResponse` directly instead of forwarding to the refund logic in `rlp_execute_callback`, causing the caller's deposit to be permanently retained by the wallet contract instead of refunded — the same bug class as the reported Swivel `lend()` issue where `premium` is refunded on one code path but not on a sibling failure path.

### Finding Description
`rlp_execute` is `#[payable]`, so any attached deposit is added to the wallet contract's own balance as soon as the call is made: [2](#0-1) 

`CallerDeposit::new` captures this deposit specifically so it can be refunded to the external predecessor if the relayed action fails: [3](#0-2) 

For the `EOABaseTokenTransfer { address_check: Some(address), .. }` path, the flow schedules a call to the address registrar and then calls back into `address_check_callback`, passing `caller_deposit` along: [4](#0-3) 

Inside `address_check_callback`, only the "happy path" (where the registrar lookup succeeds and returns `None`, i.e. the target is not a named account) actually forwards `caller_deposit` into a subsequent promise chained to `rlp_execute_callback`, which is the only function that performs the deposit refund on failure: [5](#0-4) [6](#0-5) 

But two other reachable branches in `address_check_callback` return a failed `ExecuteResponse` directly, without ever creating a refund `Promise` for `caller_deposit`:
1. `PromiseResult::Failed` (the registrar lookup call itself fails) — `caller_deposit` is simply dropped: [7](#0-6) 
2. Malformed response from the registrar (`serde_json::from_slice` fails) — same drop: [8](#0-7) 
3. `maybe_account_id.is_some()` and the signer is not the wallet owner (i.e., `target` resolves to an existing named account and the caller isn't self-signing) — returns an "Invalid target" error and again never refunds `caller_deposit`: [9](#0-8) 

In all three cases, the deposit that was credited to the wallet contract at the start of `rlp_execute` stays there permanently: no transfer-back promise is ever scheduled for these paths, exactly mirroring the reported issue where `premium` is refunded in the `e == true` branch of `lend()` but forgotten in the `e == false` branch.

### Impact Explanation
Any external account (not the wallet's owner) that attaches a NEAR deposit while calling `rlp_execute` with an `EOABaseTokenTransfer` targeting an eth-implicit address that requires an address-registrar check can have that deposit permanently frozen inside the wallet contract if the registrar call fails/errors, or if the target turns out to correspond to an existing named account and the caller is not the wallet owner. This is a genuine "permanently frozen funds" impact reachable by an unprivileged transaction/contract caller, not merely a griefing/no-impact bug: the deposit is neither returned to the caller nor consumed for its intended purpose.

### Likelihood Explanation
The registrar-lookup failure path (`PromiseResult::Failed`) can occur from ordinary conditions (e.g., the registrar contract being paused, out of gas, or unavailable) and does not require any malicious validator or network behavior — it is directly reachable from a single relayed transaction submitted by any caller. The "invalid target" branch is deterministically reachable whenever a non-owner relayer submits a transaction whose `target` resolves to an already-registered named account, which is a normal, attacker-controllable input (the caller supplies `tx_bytes_b64`/`target`).

### Recommendation
In all failure branches of `address_check_callback` (and analogously in `nep_141_storage_balance_callback`, which has the same pattern for `PromiseResult::Failed`/malformed-response arms), forward `caller_deposit` and issue a refund `Promise` back to `caller_deposit.account_id` before returning the failed `ExecuteResponse`, matching the refund logic already implemented in `rlp_execute_callback`'s `PromiseResult::Failed` arm.

### Proof of Concept
1. An external (non-owner) account submits `rlp_execute(target, tx_bytes_b64)` with an attached NEAR deposit, encoding an `EOABaseTokenTransfer` whose `to` address requires an address-check lookup (`inner_rlp_execute` → `address_check_callback` scheduled, `lib.rs:412-431`).
2. The deposit is already added to the wallet contract's balance because `rlp_execute` is `#[payable]` (`lib.rs:88`).
3. Cause the address-registrar lookup receipt to fail (e.g., registrar contract paused/errors), triggering `PromiseResult::Failed` inside `address_check_callback` (`lib.rs:141-148`), or craft `target` so it resolves to an existing named account while the caller is not the wallet owner, triggering the "Invalid target" branch (`lib.rs:161-173`).
4. `address_check_callback` returns `ExecuteResponse { success: false, .. }` without creating any transfer-back `Promise`.
5. The caller's attached deposit remains in the wallet contract's balance permanently — no receipt is ever produced that returns funds to the caller's account.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
