### Title
Unhandled `RuntimeError::UnexpectedIntegerOverflow` / `ReceiptValidationError` panics on chunk apply crash the node instead of being handled gracefully - ([File: chain/chain/src/runtime/mod.rs])

### Summary
The Chainlink report flags that `getPrice()` calls `latestRoundData()` directly instead of using `try/catch`, so any revert from the untrusted external price feed propagates uncaught and halts the caller (denial of service). The equivalent bug class in nearcore — an untrusted/external condition surfacing as an unhandled failure inside a critical execution path, which the caller does not "catch" but instead lets crash — exists in `Chain::apply_chunk` (via `self.runtime.apply(...)`), where two `RuntimeError` variants returned from `Runtime::apply` are converted into Rust `panic!()` calls instead of being surfaced as a recoverable `Error`.

### Finding Description
`Chain`'s chunk-application code calls `self.runtime.apply(...)` and maps the resulting `Result<_, RuntimeError>` with a `match`. Two of the five `RuntimeError` variants are handled by panicking rather than returning a typed error: [1](#0-0) 

Both branches are explicitly annotated `// TODO(#2152): process gracefully`, i.e. the maintainers already know these are not properly handled — but the code path is still live and reachable during normal chunk application, which is executed by every validator applying every chunk deterministically, and is invoked whenever `apply_chunk` processes a `SignedTransaction`/receipt set (the same call path used for ordinary transaction processing).

- `RuntimeError::UnexpectedIntegerOverflow` is produced deep inside `runtime/runtime/src/lib.rs` and `core/primitives/src/congestion_info.rs` when arithmetic invariants that are supposed to hold by construction (e.g., balance/gas accounting, congestion-info bookkeeping) unexpectedly fail. [2](#0-1) 
- `RuntimeError::ReceiptValidationError` is produced by `runtime/runtime/src/verifier.rs` when a receipt (which can be triggered/shaped indirectly by an attacker-crafted transaction, e.g. via cross-shard receipts, large receipt sizes, or account/data-key/permission edge cases) fails validation during apply, rather than being rejected earlier during admission.

Because these errors reach `Chain::apply_chunk`'s error-mapping closure only as `panic!()`, any single transaction or receipt that can deterministically trigger either condition during `apply` — rather than being caught earlier during transaction validation/admission (analogous to the Chainlink adapter not using `try/catch` around `latestRoundData`) — will cause the node process itself to crash while applying that chunk, instead of returning a controlled `Error` that the caller can react to.

### Impact Explanation
Since chunk application is deterministic and identical inputs are applied by every honest validator/node processing that shard, a transaction/receipt that reaches this path with an unexpected overflow or receipt-validation failure will panic every node that attempts to apply the same chunk, i.e. a transaction-triggered halt/DoS of chunk processing across the network for that shard — the same "block access blocked, no defensive handling" failure mode as the external report, but manifesting as a hard process crash rather than a caught revert. This matches the accepted impact class of "a transaction-triggered halt."

### Likelihood Explanation
Likelihood depends on whether any reachable, attacker-controlled input can still trigger `UnexpectedIntegerOverflow` or `ReceiptValidationError` at `apply` time despite earlier admission-time checks (`validate_transaction`, mempool/chunk-selection checks). The presence of the explicit `TODO(#2152): process gracefully` comments indicates the nearcore team is aware these variants are not yet defensively handled and considers them reachable enough to warrant future graceful handling, which supports non-trivial likelihood, though exploitability requires finding a concrete transaction/receipt shape that reaches `apply` without being rejected earlier — this was not verified with a concrete repro in this analysis.

### Recommendation
Convert the `UnexpectedIntegerOverflow` and `ReceiptValidationError` branches in `Chain::apply_chunk`'s error mapping (`chain/chain/src/runtime/mod.rs:367-372`) into typed `Error` variants that are handled the same defensive way `RuntimeError::InvalidTxError` and `StorageError` already are, instead of `panic!()`, so that a single malformed/edge-case transaction or receipt cannot crash the node — analogous to wrapping the untrusted external call in `try/catch` in the Chainlink report.

### Proof of Concept
No concrete transaction payload reaching `UnexpectedIntegerOverflow` or `ReceiptValidationError` at `apply` time (past earlier admission/validation checks) was constructed or verified in this analysis; this would require tracing every call site in `runtime/runtime/src/lib.rs`, `core/primitives/src/congestion_info.rs`, and `runtime/runtime/src/verifier.rs` that returns these variants and confirming at least one is reachable from an unprivileged transaction that is not already rejected during `validate_transaction`/mempool admission. This limitation should be flagged explicitly if further validation is required.
