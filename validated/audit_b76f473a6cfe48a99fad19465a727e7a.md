### Title
`DelegateAction` (Meta Transaction) Signed Payload Lacks Chain-ID Binding, Enabling Cross-Chain Replay — (`core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary
The `SignedDelegateAction` (NEP-366 meta transaction) signature commits only to a NEP-number discriminant and the action payload fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). No chain ID or network identifier is included in the signed bytes. A receiver of a meta transaction on one NEAR network (e.g., testnet) can extract the `SignedDelegateAction` and replay it on a different NEAR network (e.g., mainnet) by wrapping it in a fresh outer transaction, provided the sender account exists on the target network with the same key and a compatible nonce.

### Finding Description

`DelegateAction.get_nep461_hash()` constructs the signed payload as:

```rust
// core/primitives/src/action/delegate.rs:353-357
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
```

`SignableMessage` serializes as `[discriminant (u32 LE)] ++ borsh(DelegateAction)`:

```rust
// core/primitives/src/signable_message.rs:61-65
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}
```

The `MessageDiscriminant` is a single `u32` derived solely from the NEP number:

```rust
// core/primitives/src/signable_message.rs:117-127
pub fn new_on_chain(nep: u32) -> Result<Self, CreateDiscriminantError> {
    Ok(Self { discriminant: MIN_ON_CHAIN_DISCRIMINANT + nep })
}
```

No chain ID, genesis hash, or network identifier is mixed into the hash. The `DelegateAction` struct itself also contains no chain-binding field:

```rust
// core/primitives/src/action/delegate.rs:46-64
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
}
```

At execution time, `apply_delegate_action()` verifies the signature, checks `max_block_height`, validates the sender, and checks the nonce — but performs no chain-identity check:

```rust
// runtime/runtime/src/actions.rs:430-448

}

}

validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
```

The outer `SignedTransaction` is chain-bound via `block_hash`, but the inner `SignedDelegateAction` is independent of it. An attacker extracts the inner signed payload and wraps it in a new outer transaction on the target network.

### Impact Explanation

An attacker who receives a `SignedDelegateAction` on one NEAR network (e.g., as the `receiver_id` of a token transfer meta transaction on testnet) can submit the identical `SignedDelegateAction` on mainnet by wrapping it in a fresh outer transaction. If the sender (`sender_id`) has the same account and key on mainnet with a nonce lower than the one in the signed action, the inner actions execute on mainnet without the sender's consent for that network. This results in unauthorized token transfers or other state changes (e.g., `AddKey`, `DeleteAccount`, `FunctionCall`) on mainnet, directly causing loss of funds or unauthorized account modification.

### Likelihood Explanation

The conditions required are:
1. The sender has the same named account on both networks (common for NEAR users who mirror testnet/mainnet setups).
2. The sender uses the same key pair on both networks (common practice).
3. The nonce in the signed action is greater than the current access key nonce on the target network (plausible, especially early in an account's life or if the sender is more active on testnet).
4. `max_block_height` is valid on the target network — if the sender sets a large value (as seen in production code patterns like `BlockHeight::MAX`), this is always satisfied.

The attacker is the `receiver_id` of the meta transaction or any party who intercepts the off-chain `SignedDelegateAction` before it is submitted.

### Recommendation

Include the chain ID (genesis block hash or a canonical network identifier) in the signed payload of `DelegateAction` and `DelegateActionV2`. Concretely, add a `chain_id: CryptoHash` field to `DelegateAction` / `DelegateActionV2` (or to `SignableMessage`), populated from `ApplyState` at signing time and verified against `apply_state.genesis_hash` (or equivalent) in `apply_delegate_action()`. This mirrors how `SignedTransaction` binds to a specific `block_hash`.

### Proof of Concept

1. Alice has account `alice.near` on both testnet and mainnet, with the same ED25519 key pair. Her mainnet access key nonce is 5.
2. Alice signs a `DelegateAction` on testnet: transfer 100 NEAR to `bob.near`, nonce=6, `max_block_height=u64::MAX`.
3. Alice sends the `SignedDelegateAction` off-chain to a testnet relayer.
4. Bob (or any party who intercepts the payload) constructs a mainnet `SignedTransaction` with `signer=bob.near`, `receiver=alice.near`, containing `Action::Delegate(signed_delegate_action_from_testnet)`.
5. Bob submits this transaction to mainnet RPC.
6. `apply_delegate_action()` on mainnet: signature verifies (same key, same payload bytes), `block_height <= u64::MAX`, `sender_id == alice.near`, nonce 6 > current nonce 5 → passes all checks.
7. A new receipt is created with `predecessor=alice.near`, `receiver=bob.near`, executing the 100 NEAR transfer — on mainnet, without Alice's mainnet consent. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
