## Title
Token exchange mints/stores a session for a caller-supplied `shop` without verifying it matches the verified session token's `dest` — cross-tenant session-storage injection risk - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

## Summary
The HackerOne report describes a case where a downstream action (store creation) was performed using a caller-supplied identifier (partner account/org id) that was never cross-checked against the authenticated actor's own verified identity — allowing an unconfirmed user to act on behalf of an ID they didn't legitimately own. The structurally analogous pattern exists in `shopify-app-js`'s `tokenExchange` implementation: the `shop` used to build the outbound request and to tag/store the resulting `Session` is taken from a caller-supplied parameter, while the cryptographically verified identity (the session token's `dest` claim) is decoded but never compared against it.

## Finding Description
`tokenExchange()` decodes and verifies the session token's signature/audience/expiry, but discards the decoded payload instead of validating that `payload.dest` matches the `shop` argument: [1](#0-0) 

The `shop` value it trusts is the caller-supplied parameter, which is then used both to build the `POST https://${cleanShop}/admin/oauth/access_token` request and to tag the resulting `Session` object via `createSession({..., shop: cleanShop, ...})`.

Crucially, in the `AppDistribution.ShopifyAdmin` branch of `getSessionTokenContext`, the `shop` passed down to the authorization strategy (and ultimately to `tokenExchange`) comes directly from the URL query string, not from the verified JWT: [2](#0-1) 

This is unlike the non-`ShopifyAdmin` branch, which correctly derives `shop` from the verified `payload.dest`: [3](#0-2) 

The same "decode but don't compare" pattern repeats in the equivalent `shopify-app-remix` token-exchange strategy and the `shopify-app-express` `performTokenExchange` middleware, both of which call `api.auth.tokenExchange({sessionToken, shop, ...})` with a `shop` obtained independently of the token's `dest`: [4](#0-3) [5](#0-4) 

## Impact Explanation
If an embedded/legacy request is authenticated in the `ShopifyAdmin` distribution mode, the app trusts the `shop` query parameter for session-storage bookkeeping while its authentication (`getCurrentId`) is separately keyed by cookie/session-id rather than a verified shop-to-token binding at this call site. Because `tokenExchange()` itself never asserts `new URL(payload.dest).hostname === shop`, the *library-level* API provides no defense-in-depth against a caller supplying a `shop` argument that diverges from the shop embedded in the verified session token. The eventual protection relies entirely on Shopify's own OAuth token endpoint rejecting a mismatched subject_token/shop pair server-side; there is no local, defense-in-depth verification. If any code path (custom domain transformations, spin.dev/shop.dev aliasing, or a future caller that doesn't set `shop` from `dest`) supplies an inconsistent `shop`, `createSession` will persist a `Session` keyed to the wrong shop in the app's session storage — a session-storage integrity issue that can lead to cross-tenant session confusion.

## Likelihood Explanation
Exploitability depends on whether Shopify's real OAuth token-exchange endpoint strictly validates that the subject `id_token`'s `dest` matches the shop domain in the request URL — this is external and cannot be confirmed from this repo. The library-side gap is concrete and reachable by any caller of `shopify.auth.tokenExchange` (all three framework packages route caller/URL-controlled `shop` into it without a match check), so this is a real internal defense-in-depth gap regardless of whether Shopify's backend also enforces the invariant.

## Recommendation
In `tokenExchange()` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), capture the decoded payload and assert that `new URL(payload.dest).hostname` equals the sanitized `shop` argument before proceeding; throw an `InvalidJwtError`/`InvalidOAuthError` on mismatch. Additionally, in `shopify-app-react-router`'s `getSessionTokenContext` (and remix's equivalent), derive `shop` from the verified session token payload rather than the raw URL query parameter whenever a session token is present, mirroring the non-`ShopifyAdmin` branch's approach.

## Proof of Concept
Not independently reproducible against a live Shopify backend from this static analysis; the concrete PoC would require a test harness that:
1. Obtains a valid App Bridge session token for `shop-a.myshopify.com`.
2. Calls the app's token-exchange authentication path with `?shop=shop-b.myshopify.com` while presenting `shop-a`'s session token.
3. Observes whether `tokenExchange()` proceeds to call `https://shop-b.myshopify.com/admin/oauth/access_token` with `shop-a`'s subject token, and whether the resulting session gets stored under `shop-b`'s session id (`createSession({shop: cleanShop=shop-b, ...})`) — since the library performs no local `dest`-vs-`shop` equality check.

I could not confirm from the indexed code whether any framework-level caller already enforces the `dest === shop` invariant upstream of `tokenExchange` in the `ShopifyAdmin` distribution path; this should be verified in a live/full-repo session, as the index may not include every call site.
