### Title
Missing anchor (`rt`) pre-validation before expensive zk-SNARK spend proof generation enables low-cost CPU DoS - (File: `framework/src/main/java/org/tron/core/services/http/CreateShieldedTransactionWithoutSpendAuthSigServlet.java`)

### Summary
The public HTTP endpoint `CreateShieldedTransactionWithoutSpendAuthSigServlet` forwards attacker-controlled `PrivateParametersWithoutAsk` (including spend notes, voucher paths, and anchors) directly into `Wallet.createShieldedTransactionWithoutSpendAuthSig`, which builds a `ZenTransactionBuilder` and calls `generateSpendProof` for every spend before any transaction validation occurs. `generateSpendProof` in `ZenTransactionBuilder.java` unconditionally invokes the computationally expensive `JLibrustzcash.librustzcashSaplingSpendProof` using the caller-supplied `anchor`/`voucher.path()` without first checking that the anchor is a known root in the node's `MerkleContainer`. The only place `rt`/anchor validity is checked ("Rt is invalid.") is later in `ShieldedTransferActuator.validate`, which runs only after the (expensive) proof has already been generated and the transaction constructed.

### Finding Description
- Attacker entrypoint: `CreateShieldedTransactionWithoutSpendAuthSigServlet.doPost` parses `PrivateParametersWithoutAsk` from the raw HTTP POST body and calls `wallet.createShieldedTransactionWithoutSpendAuthSig(build.build())` with no additional server-side gating beyond `allowShieldedTransactionApi` and rate limiting. [1](#0-0) 
- The builder path constructs `SpendDescriptionInfo` objects directly from attacker-provided `ak`/`nsk`/`ovk`/`note`/`alpha`/`anchor`/`voucher`, then `build()` iterates spends and calls `generateSpendProof(spend, ctx)` for each one before any chain-level acceptance check. [2](#0-1) 
- `generateSpendProof` only checks that `cm`/`nf` are non-empty; it never checks whether `spend.anchor` exists as a valid root in the node's `MerkleContainer` before calling the costly `librustzcashSaplingSpendProof` zk-SNARK proving routine. [3](#0-2) 
- The actual anchor/`rt` legitimacy check ("Rt is invalid.") happens only inside `ShieldedTransferActuator.validate`, which is reached only after the transaction (with the already-computed proof) is submitted for broadcast/validation — i.e., strictly after the expensive work is done.

Because the zk-SNARK spend-proof computation (`librustzcashSaplingSpendProof`) is orders of magnitude more CPU-expensive than a Merkle-root/anchor lookup, an attacker can submit arbitrary/random anchors and voucher paths repeatedly to this HTTP endpoint, forcing the node to perform full proof generation for every request even though the request is deterministically going to be rejected downstream for an invalid `rt`.

### Impact Explanation
Each POST to this endpoint with a bogus or stale anchor forces full-cost zk-SNARK spend proof generation on the node before any anchor validity check occurs. Repeated requests amount to a public, low-cost-to-attacker vs. high-cost-to-node CPU exhaustion vector (denial-of-service against the node process handling shielded API calls), matching the "materially underpriced public work" criterion in the audit scope.

### Likelihood Explanation
Preconditions are modest and attacker-controllable: `allowShieldedTransactionApi=true` (a common node configuration for full nodes offering shielded services) and a syntactically valid `ak`/`nsk`/`ovk`/note/voucher payload, none of which require any privileged access — an unprivileged HTTP client can construct these entirely locally. The request is fully repeatable and rate-limiting (`RateLimiterServlet`) only throttles request rate, not the CPU cost per request, so it does not eliminate the cost asymmetry.

### Recommendation
Before calling `generateSpendProof` (i.e., before invoking `librustzcashSaplingSpendProof`), validate that `spend.anchor` corresponds to a currently known/valid Merkle root in the node's `MerkleContainer` (the same check that `ShieldedTransferActuator.validate` performs for `rt`), and reject the request early with a cheap lookup if the anchor is unknown, avoiding wasted proof computation.

### Proof of Concept
Java integration test (using `Wallet` wired to a `MerkleContainer` with only well-known valid anchors):
```java
@Test
public void testUnknownAnchorProofDosCost() {
    // Build PrivateParametersWithoutAsk with a syntactically valid spend note
    // but voucher/anchor NOT present in the node's MerkleContainer.
    PrivateParametersWithoutAsk.Builder params = PrivateParametersWithoutAsk.newBuilder();
    // ... populate ak, nsk, ovk, note fields, and a random/garbage anchor + matching fake voucher path

    long start = System.nanoTime();
    try {
        wallet.createShieldedTransactionWithoutSpendAuthSig(params.build());
        fail("expected rejection for unknown anchor");
    } catch (Exception e) {
        assertTrue(e.getMessage().contains("Rt is invalid") 
            || e.getCause().getMessage().contains("Rt is invalid"));
    }
    long elapsedMs = (System.nanoTime() - start) / 1_000_000;

    // Expected (failing) assertion demonstrating the bug:
    // proof generation happened before rejection, so elapsed time is comparable
    // to a full zk-proof generation (tens/hundreds of ms), not a cheap lookup (<1ms).
    assertTrue("anchor should be validated BEFORE proof generation", elapsedMs < 5);
}
```
Expected result today: the assertion `elapsedMs < 5` fails because full spend-proof generation runs first, confirming the missing pre-validation of `rt` against `MerkleContainer` allows costly work on invalid/unknown anchors.

  public SpendDescriptionCapsule generateSpendProof(SpendDescriptionInfo spend,
      long ctx) throws ZksnarkException {

    byte[] cm = spend.note.cm();

    // check if ak exists
    byte[] ak;
    byte[] nf;
    byte[] nsk;
    if (!ArrayUtils.isEmpty(spend.ak)) {
      ak = spend.ak;
      nf = spend.note.nullifier(ak, JLibrustzcash.librustzcashNskToNk(spend.nsk),
          spend.voucher.position());
      nsk = spend.nsk;
    } else {
      ak = spend.expsk.fullViewingKey().getAk();
      nf = spend.note.nullifier(spend.expsk.fullViewingKey(), spend.voucher.position());
      nsk = spend.expsk.getNsk();
    }

    if (ByteArray.isEmpty(cm) || ByteArray.isEmpty(nf)) {
      throw new ZksnarkException("Spend is invalid");
    }

    byte[] voucherPath = spend.voucher.path().encode();

    byte[] cv = new byte[32];
    byte[] rk = new byte[32];
    byte[] zkproof = new byte[192];
    if (!JLibrustzcash.librustzcashSaplingSpendProof(
        new SpendProofParams(ctx,
            ak,
            nsk,
            spend.note.getD().getData(),
            spend.note.getRcm(),
            spend.alpha,
            spend.note.getValue(),
            spend.anchor,
            voucherPath,
            cv,
            rk,
            zkproof))) {
      throw new ZksnarkException("Spend proof failed");
    }
