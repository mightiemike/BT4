CVE-2018-15864 is a NULL-pointer dereference in xkbcommon's `resolve_keysym` C parser, where a symbol table map might never be allocated before being accessed. This bug class does not transfer meaningfully to protobuf-go for two reasons:

1. **Language semantics differ.** Go maps are safe to read (`Get`, `Has`, range) even when `nil` — a nil map read returns the zero value rather than dereferencing a null pointer and crashing, unlike C. The only Go operation that panics on a nil map is a *write* (`m[k] = v` on a nil map), and every map-decode path in this codebase ensures the map is allocated (`reflect.MakeMap`) before any write occurs.

2. **All discovered map-decode paths in protobuf-go explicitly initialize the map before populating it:**
   - Binary wire decode: `internal/impl/codec_map.go` allocates the map via `reflect.MakeMap` before calling `consumeMap`/`consumeMapOfMessage` if it is nil [1](#0-0) .
   - The generic `proto.Unmarshal` path operates on a `protoreflect.Map` obtained via `m.Mutable(fd).Map()`, which the field accessor lazily allocates on demand [2](#0-1) .
   - `encoding/protojson` and `encoding/prototext` map decoders (`unmarshalMap`/`unmarshalMapEntry`) likewise operate on an already-mutable `protoreflect.Map`, and default/missing keys or values are filled in with sensible defaults rather than left as unresolved pointers [3](#0-2) [4](#0-3) .
   - `dynamicpb`'s map value getter (`Get`) safely returns the zero `protoreflect.Value` for a missing key rather than dereferencing anything unsafe [5](#0-4) .

No reachable code path was found where a map is accessed for read/write before it "was ever created" in a way that causes a nil-pointer/unsafe-memory effect on an unprivileged, trusted-schema request path. The invariant that the CVE hinges on (a NULL pointer being written into or dereferenced from an uninitialized table) simply doesn't have a parallel unsafe-memory consequence in this Go codebase's map handling.
