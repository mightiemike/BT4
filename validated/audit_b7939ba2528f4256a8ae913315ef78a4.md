### Title
Missing zero-check on `totalEnergyWeight` in `calculateGlobalEnergyLimit` relies on a disabled `assert` guard, allowing division-by-zero - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)` divides by `totalEnergyWeight` after only protecting the divisor with a Java `assert` statement rather than an actual conditional check, mirroring the Biconomy `sharesToTokenAmount` bug class where a public/reachable calculation function fails to validate its denominator before dividing.

### Finding Description
`calculateGlobalEnergyLimit` reads `totalEnergyWeight` from the dynamic properties store and then does: [1](#0-0) 

The only protection against `totalEnergyWeight == 0` is `assert totalEnergyWeight > 0;` at line 976, immediately followed by a division (`.divide(BigInteger.valueOf(totalEnergyWeight))` in the hardened path, or `totalEnergyLimit / totalEnergyWeight` in the legacy `double` path) at lines 979-984. Java `assert` statements are no-ops unless the JVM is started with the `-ea` flag, which is not the default runtime configuration for production nodes. This is functionally equivalent to the Biconomy report's missing `if (totalSharesMinted[_tokenAddress] == 0) return 0;` check — the denominator guard exists only as documentation/debugging aid, not as enforced runtime logic, so if `totalEnergyWeight` is ever legitimately zero (e.g., no accounts have frozen balance for energy yet, or `allowNewReward` handling elsewhere resets total weight to 0), the division executes unguarded.

Notably, the codebase itself demonstrates awareness of this exact hazard and fixes it correctly elsewhere: `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` use a real `if (totalEnergyWeight == 0) { return 0; }` check instead of an `assert`: [2](#0-1) 

This inconsistency shows `RepositoryImpl.calculateGlobalEnergyLimit` is the outlier still relying on the ineffective `assert`-based guard, analogous to the missing check that `sharesToTokenAmount` had in the report before its own callers were fixed.

### Impact Explanation
If `totalEnergyWeight` reaches 0 while this code path is invoked, the legacy path performs an integer division by zero (`ArithmeticException`), and the hardened `BigInteger` path throws `ArithmeticException` from `.divide()`. Because the guard is a disabled `assert` in production, this is not caught gracefully and will surface as an unhandled runtime exception in whatever unprivileged call path reaches `RepositoryImpl.calculateGlobalEnergyLimit`, causing a revert/failure of an otherwise-valid operation — the same "should never revert" concern raised in the original report.

### Likelihood Explanation
Likelihood depends on how `totalEnergyWeight` can become zero in practice (e.g., before any TRX has been frozen for energy on a freshly initialized state, or transiently during resource-weight transitions). This is a plausible, low-privilege reachable state rather than a purely theoretical one, since `EnergyProcessor`'s parallel implementation was explicitly hardened against the same zero case, indicating the underlying condition is considered reachable by the codebase's own maintainers.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` at `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java:976` with an explicit runtime check that returns `0` (or another safe default) when `totalEnergyWeight <= 0`, consistent with the guard already implemented in `EnergyProcessor.calculateGlobalEnergyLimitV2` at `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java:171-173`.

### Proof of Concept
1. Reach a state where `dynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., prior to any account freezing TRX for energy, or after all energy-frozen balances are unfrozen).
2. Invoke a code path that calls `RepositoryImpl.calculateGlobalEnergyLimit(accountCapsule)` with `frozeBalance >= TRX_PRECISION` for the queried account.
3. Because `assert` is disabled by default at runtime, execution proceeds past line 976 directly into the division at lines 979-984, throwing `ArithmeticException` and failing the request/operation instead of returning a safe value.

**Note:** I was unable to fully trace, within available tool calls, every external call site that invokes `RepositoryImpl.calculateGlobalEnergyLimit` (e.g., which precompiled contract or TVM opcode path reaches it) — this would need direct grepping of call sites, which I ran out of iterations to complete. The core root-cause defect (assert-only guard before division) is confirmed directly from the file.
