## Finding Confirmed

### Title
Aggregator-Overridden Total Supply Value Leaks Uncorrected into Committed `TransactionOutput` in Sharded Block Executor - (File: `aptos-move/aptos-vm/src/sharded_block_executor/sharded_executor_service.rs`)

### Summary
Each shard executes its sub-blocks against an `AggregatorOverriddenStateView` that substitutes the real total-supply state value with a synthetic placeholder `TOTAL_SUPPLY_AGGR_BASE_VAL = u128::MAX >> 1`. [1](#0-0)  The correction pass that is supposed to remove this override and rebase the value onto the true global total supply — `aggregate_and_update_total_supply` in `sharded_aggregator_service.rs` — is defined but has no call site anywhere in the coordinator/executor client code paths that assemble the final `TransactionOutput`s returned via `CoordinatorClient::send_execution_result` / `ExecutorClient::execute_block`. [2](#0-1) [3](#0-2) 

### Finding Description
`ShardedExecutorService::execute_transactions_with_dependencies` wraps the cross-shard state view in `AggregatorOverriddenStateView::new(cross_shard_state_view.as_ref(), TOTAL_SUPPLY_AGGR_BASE_VAL)` before invoking `AptosVMBlockExecutorWrapper::execute_block`. [4](#0-3)  Any read of `TOTAL_SUPPLY_STATE_KEY` during transaction execution on a shard therefore observes the placeholder base value `u128::MAX >> 1` instead of the real global total supply, and any aggregator delta applied to it produces a `TransactionOutput` whose write set entry for `TOTAL_SUPPLY_STATE_KEY` is computed relative to this placeholder. [5](#0-4) 

The comment in `aggr_overridden_state_view.rs` explicitly acknowledges this is a stopgap ("TODO: Remove this when we have aggregated total supply implementation for remote sharding... after all the txns are executed, the proof checker expects the total_supply to read/written to the tree"), implying a post-processing correction step is required before the sharded results are treated as final. [6](#0-5) 

That correction step exists as `aggregate_and_update_total_supply`, which walks `sharded_output`/`global_output`, computes per-shard/per-round deltas relative to `TOTAL_SUPPLY_AGGR_BASE_VAL`, reads the real `total_supply_base_val` from the (non-overridden) `state_view`, and calls `txn_output.update_total_supply(...)` to rewrite each `TransactionOutput`'s write set with the corrected value. [7](#0-6) 

However, a repository-wide search for `aggregate_and_update_total_supply` found only its own definition — there is no call site in `local_executor_shard.rs`, `mod.rs` (the `ShardedBlockExecutor` orchestration entry point), `executor_client.rs`, or `sharded_executor_service.rs`. The coordinator's `execute_block` path collects raw per-shard results via `get_output_from_shards()` and returns a `ShardedExecutionOutput` without ever invoking the aggregation/correction routine. [8](#0-7) [9](#0-8) 

The result: on the path that begins at `ShardedExecutorService::execute_transactions_with_dependencies` → `AptosVMBlockExecutorWrapper::execute_block` → `self.coordinator_client.send_execution_result(ret)`, the `TransactionOutput`s ultimately handed off to storage/commit contain the aggregator-overridden `TOTAL_SUPPLY_AGGR_BASE_VAL`-derived value rather than the true total supply, unless some other caller I could not locate in this index performs the correction before commit.

### Impact Explanation
If this uncorrected write set is what gets committed, the on-chain `total_supply` aggregator state diverges from the value the non-sharded `AptosVMBlockExecutorWrapper` execution path would produce for the identical block, which is a direct state-commitment/ledger-consistency violation — any block containing an aggregator-heavy transaction (e.g. coin mint/burn, or any resource using the aggregator API on the total-supply table item) processed through the sharded executor would commit a wrong total supply value, corrupting consensus-critical state and diverging from validators/full-nodes that use the non-sharded path.

### Likelihood Explanation
This requires no privileged access — any transaction that reads or writes `TOTAL_SUPPLY_STATE_KEY` (e.g. via the standard coin/aggregator APIs) triggers the code path. The severity is gated entirely on whether `aggregate_and_update_total_supply` is actually wired into the live coordinator flow used in production (e.g., in `execution/executor-service` remote path or validator sharded config) — my search within this indexed snapshot did not find any invocation, but I could not exhaustively verify every caller of `ShardedExecutionOutput`/`send_execution_result` across the full repository (e.g. `remote_executor_client.rs` and coordinator-side aggregation glue may exist outside indexed content). This is a significant caveat: due to index size limits, some file contents (particularly in `execution/executor-service/` and any coordinator-side post-processing invoked after `ExecutorClient::execute_block` returns) may not be fully available to me.

### Recommendation
Confirm whether `aggregate_and_update_total_supply` is invoked by whatever code consumes `ShardedExecutionOutput` (coordinator side) before results are handed to the block executor pipeline that produces the committed `TransactionOutput`s. If it is not called, wire it into the coordinator immediately after collecting `sharded_output`/`global_output` and before returning from `ExecutorClient::execute_block`, or add a debug-assertion/differential test that compares sharded vs. non-sharded execution write sets for the `TOTAL_SUPPLY_STATE_KEY` on every block that touches total supply.

### Proof of Concept
1. Construct a block with several transactions across multiple shards that mint/burn coins (touching `TOTAL_SUPPLY_STATE_KEY`).
2. Execute the block via `ShardedBlockExecutor` (sharded path) and record the final `TransactionOutput.write_set()` value for `TOTAL_SUPPLY_STATE_KEY`.
3. Execute the identical block via `AptosVMBlockExecutorWrapper::execute_block` directly (non-sharded path).
4. Compare the two `total_supply` values — since no code path was found invoking `aggregate_and_update_total_supply` on the sharded coordinator's result before it is returned, the sharded result should reflect `TOTAL_SUPPLY_AGGR_BASE_VAL`-relative deltas rather than the true aggregated value, producing a divergent write set between the two paths.

pub struct AggregatorOverriddenStateView<'a, S> {
    base_view: &'a S,
    total_supply_aggr_base_val: u128,
}

impl<'a, S: StateView + Sync + Send> AggregatorOverriddenStateView<'a, S> {
    pub fn new(base_view: &'a S, total_supply_aggr_base_val: u128) -> Self {
        Self {
            base_view,
            total_supply_aggr_base_val,
        }
    }

    fn total_supply_base_view_override(&self) -> Result<Option<StateValue>> {
        Ok(Some(StateValue::new_legacy(
            bcs::to_bytes(&self.total_supply_aggr_base_val)
                .unwrap()
                .into(),
        )))
    }
}

impl<S: StateView + Sync + Send> TStateView for AggregatorOverriddenStateView<'_, S> {
    type Key = StateKey;

    fn get_state_value(&self, state_key: &StateKey) -> Result<Option<StateValue>> {

            //       proof checker expects the total_supply to read/written to the tree.
            self.base_view.get_state_value(state_key)?;
            return self.total_supply_base_view_override();
        }
        self.base_view.get_state_value(state_key)
    }

pub fn aggregate_and_update_total_supply<S: StateView>(
    sharded_output: &mut Vec<Vec<Vec<TransactionOutput>>>,
    global_output: &mut [TransactionOutput],
    state_view: &S,
    executor_thread_pool: Arc<rayon::ThreadPool>,
) {
    let num_shards = sharded_output.len();
    let num_rounds = sharded_output[0].len();

    // The first element is 0, which is the delta for shard 0 in round 0. +1 element will contain
    // the delta for the global shard
    let mut aggr_total_supply_delta = vec![DeltaU128::default(); num_shards * num_rounds + 1];

    // No need to parallelize this as the runtime is O(num_shards * num_rounds)
    // TODO: Get this from the individual shards while getting 'sharded_output'
    let mut aggr_ts_idx = 1;
    for round in 0..num_rounds {
        sharded_output.iter().for_each(|shard_output| {
            let mut curr_delta = DeltaU128::default();
            // Though we expect all the txn_outputs to have total_supply, there can be
            // exceptions like 'block meta' (first txn in the block) and 'chkpt info' (last txn
            // in the block) which may not have total supply. Hence we iterate till we find the
            // last txn with total supply.
            for txn in shard_output[round].iter().rev() {
                if let Some(last_txn_total_supply) = txn.write_set().get_total_supply() {
                    curr_delta =
                        DeltaU128::get_delta(last_txn_total_supply, TOTAL_SUPPLY_AGGR_BASE_VAL);
                    break;
                }
            }
            aggr_total_supply_delta[aggr_ts_idx] =
                curr_delta + aggr_total_supply_delta[aggr_ts_idx - 1];
            aggr_ts_idx += 1;
        });
    }

    // The txn_outputs contain 'txn_total_supply' with
    // 'CrossShardStateViewAggrOverride::total_supply_aggr_base_val' as the base value.
    // The actual 'total_supply_base_val' is in the state_view.
    // The 'delta' for the shard/round is in aggr_total_supply_delta[round * num_shards + shard_id + 1]
    // For every txn_output, we have to compute
    //      txn_total_supply = txn_total_supply - CrossShardStateViewAggrOverride::total_supply_aggr_base_val + total_supply_base_val + delta
    // While 'txn_total_supply' is u128, the intermediate computation can be negative. So we use
    // DeltaU128 to handle any intermediate underflow of u128.
    let total_supply_base_val: u128 = get_state_value(&TOTAL_SUPPLY_STATE_KEY, state_view).unwrap();
    let base_val_delta = DeltaU128::get_delta(total_supply_base_val, TOTAL_SUPPLY_AGGR_BASE_VAL);

    let aggr_total_supply_delta_ref = &aggr_total_supply_delta;
    // Runtime is O(num_txns), hence parallelized at the shard level and at the txns level.
    executor_thread_pool.scope(|_| {
        sharded_output
            .par_iter_mut()
            .enumerate()
            .for_each(|(shard_id, shard_output)| {
                for (round, txn_outputs) in shard_output.iter_mut().enumerate() {
                    let delta_for_round =
                        aggr_total_supply_delta_ref[round * num_shards + shard_id] + base_val_delta;
                    let num_txn_outputs = txn_outputs.len();
                    txn_outputs
                        .par_iter_mut()
                        .with_min_len(optimal_min_len(num_txn_outputs, 32))
                        .for_each(|txn_output| {
                            if let Some(txn_total_supply) =
                                txn_output.write_set().get_total_supply()
                            {
                                txn_output.update_total_supply(
                                    delta_for_round.add_delta(txn_total_supply),
                                );
                            }
                        });
                }
            });
    });

    let delta_for_global_shard = aggr_total_supply_delta[num_shards * num_rounds] + base_val_delta;
    let delta_for_global_shard_ref = &delta_for_global_shard;
    executor_thread_pool.scope(|_| {
        let num_txn_outputs = global_output.len();
        global_output
            .par_iter_mut()
            .with_min_len(optimal_min_len(num_txn_outputs, 32))
            .for_each(|txn_output| {
                if let Some(txn_total_supply) = txn_output.write_set().get_total_supply() {
                    txn_output.update_total_supply(
                        delta_for_global_shard_ref.add_delta(txn_total_supply),
                    );
                }
            });
    });
}
