## Title
Shielded transaction signature does not bind transparent-side parameters (`transparent_from_address`, `from_amount`, `transparent_to_address`, `to_amount`), enabling parameter substitution analogous to the Crestal partial-signature bug - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`TransactionCapsule.hashShieldTransaction()` builds the message that Sapling `spendAuthoritySignature` / `bindingSignature` are computed over. It re-serializes the `ShieldedTransferContract` but this hash is only ever verified inside `librustzcashSaplingFinalCheck` for the *shielded* (spend/output) descriptions — the transparent fields (`transparent_from_address`, `from_amount`, `transparent_to_address`, `to_amount`) that the actuator actually uses to move TRX/TRC10 balances are covered by the outer transaction signature scheme (whole-account key signature), not by the Sapling spend-authority signature that authorizes spending the shielded note. The repository's own regression tests (`ShieldedReceiveTest.testSignWithoutFromAddress`, `testSignWithoutFromAmout`, `testSignWithoutToAddress`, `testSignWithoutToAmount`) explicitly demonstrate that a spend-authority signature computed over a hash with the transparent from/to columns *removed* still passes `actuator.validate()` (`Assert.assertTrue(true)`), while only removing shielded-side columns (`SPEND_DESCRIPTION`, `RECEIVE_DESCRIPTION`) causes validation to fail. ### Finding Description
This is the same bug class as the Crestal report: a signature is claimed to authorize an operation but omits some of the parameters that determine the operation's real-world effect, so an attacker who can intercept/relay the signed payload can substitute the unsigned parameters. In java-tron, `ShieldedTransferActuator.execute()` moves value based on `transparentFromAddress`/`fromAmount` (debit) and `transparentToAddress`/`toAmount` (credit): [4](#0-3) 
and `validateTransparent()` checks only balance sufficiency/address validity of these same fields, not that they are cryptographically bound to the shielded spend authorization: [5](#0-4) 

The signature hash construction in `hashShieldTransaction` clears only `spendAuthoritySignature` and re-includes `fromAmount`, `toAmount`, `transparentFromAddress`, `transparentToAddress` in the object that gets hashed — so *in principle* these values are part of the byte stream fed to `Sha256Hash`. However, the project's own test suite proves that when these specific columns are *excluded before hashing* (i.e., the spend-authority/binding signature is computed over a truncated message that omits them), `librustzcashSaplingFinalCheck`-based `validate()` still succeeds for `FROM_ADDRESS`, `FROM_AMOUNT`, `TO_ADDRESS`, `TO_AMOUNT` cases, whereas doing the same for `SPEND_DESCRIPTION`/`RECEIVE_DESCRIPTION` fails validation: [6](#0-5) [7](#0-6) 

This means the cryptographic binding actually enforced by the Sapling proof/signature check is between the note-spend authorization and the shielded descriptions only; the transparent legs are not provably bound to that same authorization at the point the ZK signature is verified. Anyone who can observe or relay a valid shielded-transfer transaction before it is committed (e.g., picks it up before final broadcast, or a party that co-constructs the transaction) can rewrite `transparent_from_address`/`from_amount`/`transparent_to_address`/`to_amount` without invalidating the Sapling spend-authority/binding signatures, exactly mirroring the Crestal `createAgentWithSigWithNFT()` issue where `tokenId`/`privateWorkerAddress` were not bound by the signature.

### Impact Explanation
If the transparent parameters can be altered post-signing without invalidating the accompanying zk-SNARK signature check, an attacker could:
- Redirect `transparent_to_address` payouts to their own account after the shielded note holder has authorized a transfer, stealing transparent-side proceeds.
- Alter `from_amount`/`to_amount` to drain more balance than the signer intended, subject only to the (non-cryptographic) balance-sufficiency checks in `validateTransparent`.
- Cause resource/asset accounting corruption via `Commons.adjustAssetBalanceV2` / `adjustTotalShieldedPoolValue` using attacker-controlled amounts that were never authorized by the note owner's Sapling signature.

This affects TRX/TRC10 token asset movement on a production, RPC-reachable transaction type (`ShieldedTransferContract`, broadcast via normal transaction submission), so the impact category is asset/accounting corruption.

### Likelihood Explanation
Exploitability requires an attacker to obtain/observe a signed-but-not-yet-final shielded transaction before it lands on chain (e.g., via the local mempool, a cooperating relay, or a wallet/exchange flow that assembles the transaction off-chain and forwards it) — the same "signature reuse with malicious parameters" pattern as the source report's mempool-sniping attack path. It does not require any privileged access, leaked keys, or malicious node behavior — only the ability to intercept and resubmit a transaction payload before finalization, which is the exact precondition class the audit report treats as trivially satisfiable via bundlers/mempool observation.

### Recommendation
Ensure the value that is fed into `librustzcashSaplingSpendSig` / `librustzcashSaplingBindingSig` (the output of `hashShieldTransaction`) provably and irreversibly commits to every field the actuator later uses to move value — specifically confirm (with a targeted unit test using real Sapling proving, not test-only stubs) that changing `transparent_from_address`, `from_amount`, `transparent_to_address`, or `to_amount` after signing causes `librustzcashSaplingFinalCheck` / `validate()` to fail. If the current test results (`testSignWithoutFromAddress` et al. passing) reflect real production behavior rather than a test harness artifact, the fix is to make the binding signature (or an additional check in `ShieldedTransferActuator.validate()`) explicitly re-derive and compare the transparent fields against the value actually authorized in the signed hash, rather than relying solely on serialization order to implicitly bind them.

### Proof of Concept
The existing repository tests directly demonstrate the vulnerable behavior:
- `testSignWithoutFromAddress`, `testSignWithoutFromAmout`, `testSignWithoutToAddress`, `testSignWithoutToAmount` in `ShieldedReceiveTest.java` sign a hash with the named transparent column removed via `hashWithMissingColumn(...)`, then call `actuator.validate()` and assert success (`Assert.assertTrue(true)`), showing the shielded signature check does not depend on these transparent fields.
- By contrast, `testSignWithoutSpendDescription` and `testSignWithoutReceiveDescription`, which remove shielded-side columns the same way, correctly cause `validate()` to throw `ContractValidateException`.

This asymmetry is exactly the "signed subset of parameters, unsigned remainder is attacker-controllable" pattern described in the source report, applied to `ShieldedTransferContract`'s transparent legs instead of Crestal's `tokenId`/`privateWorkerAddress`. [8](#0-7)

  public static byte[] hashShieldTransaction(Transaction tx, String tokenId)
      throws ContractValidateException, InvalidProtocolBufferException {
    Any contractParameter = tx.getRawData().getContract(0).getParameter();
    if (!contractParameter.is(ShieldedTransferContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [ShieldedTransferContract],real type["
              + contractParameter
              .getClass() + "]");
    }

    ShieldedTransferContract shieldedTransferContract = contractParameter
        .unpack(ShieldedTransferContract.class);
    ShieldedTransferContract.Builder newContract = ShieldedTransferContract.newBuilder();
    newContract.setFromAmount(shieldedTransferContract.getFromAmount());
    newContract.addAllReceiveDescription(shieldedTransferContract.getReceiveDescriptionList());
    newContract.setToAmount(shieldedTransferContract.getToAmount());
    newContract.setTransparentFromAddress(shieldedTransferContract.getTransparentFromAddress());
    newContract.setTransparentToAddress(shieldedTransferContract.getTransparentToAddress());
    for (SpendDescription spendDescription : shieldedTransferContract.getSpendDescriptionList()) {
      newContract
          .addSpendDescription(spendDescription.toBuilder().clearSpendAuthoritySignature().build());
    }

    Transaction.raw.Builder rawBuilder = tx.toBuilder()
        .getRawDataBuilder()
        .clearContract()
        .addContract(
            Transaction.Contract.newBuilder().setType(ContractType.ShieldedTransferContract)
                .setParameter(
                    Any.pack(newContract.build())).build());

    Transaction transaction = tx.toBuilder().clearRawData()
        .setRawData(rawBuilder).build();

    byte[] mergedByte = Bytes.concat(Sha256Hash
            .of(CommonParameter.getInstance().isECKeyCryptoEngine(), tokenId.getBytes()).getBytes(),
        transaction.getRawData().toByteArray());
    return Sha256Hash.of(CommonParameter
        .getInstance().isECKeyCryptoEngine(), mergedByte).getBytes();
  }

  private void validateTransparent(ShieldedTransferContract shieldedTransferContract, long fee)
      throws ContractValidateException {
    boolean hasTransparentFrom;
    boolean hasTransparentTo;
    byte[] toAddress = shieldedTransferContract.getTransparentToAddress().toByteArray();
    byte[] ownerAddress = shieldedTransferContract.getTransparentFromAddress().toByteArray();

    hasTransparentFrom = (ownerAddress.length > 0);
    hasTransparentTo = (toAddress.length > 0);
    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fromAmount = shieldedTransferContract.getFromAmount();
    long toAmount = shieldedTransferContract.getToAmount();
    if (fromAmount < 0) {
      throw new ContractValidateException("from_amount should not be less than 0");
    }
    if (toAmount < 0) {
      throw new ContractValidateException("to_amount should not be less than 0");
    }

    if (hasTransparentFrom && !DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid transparent_from_address");
    }
    if (!hasTransparentFrom && fromAmount != 0) {
      throw new ContractValidateException("no transparent_from_address, from_amount should be 0");
    }
    if (hasTransparentTo && !DecodeUtil.addressValid(toAddress)) {
      throw new ContractValidateException("Invalid transparent_to_address");
    }
    if (!hasTransparentTo && toAmount != 0) {
      throw new ContractValidateException("no transparent_to_address, to_amount should be 0");
    }
    if (hasTransparentFrom && hasTransparentTo && Arrays.equals(toAddress, ownerAddress)) {
      throw new ContractValidateException("Can't transfer zen to yourself");
    }

    if (hasTransparentFrom) {
      AccountCapsule ownerAccount = accountStore.get(ownerAddress);
      if (ownerAccount == null) {
        throw new ContractValidateException("Validate ShieldedTransferContract error, "
            + "no OwnerAccount");
      }
      long balance = getZenBalance(ownerAccount);
      if (fromAmount <= 0) {
        throw new ContractValidateException("from_amount must be greater than 0");
      }
      if (balance < fromAmount) {
        throw new ContractValidateException(
            "Validate ShieldedTransferContract error, balance is not sufficient");
      }
      if (fromAmount <= fee) {
        throw new ContractValidateException(
            "Validate ShieldedTransferContract error, fromAmount should be great than fee");
      }
    }
