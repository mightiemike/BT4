### Title
Division-before-multiplication precision loss in witness brokerage/reward split - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward()` splits each block/transaction-fee reward between the witness's brokerage cut and the shared voter reward pool by first dividing the integer `brokerage` percentage by `100` into a `double`, and only then multiplying by `value`. This is the exact "divide-then-multiply" pattern flagged in the external report: division performed in the middle of the calculation instead of at the end, causing systematic truncation/rounding loss instead of an exact proportional split.

### Finding Description
```java
private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
}
``` [1](#0-0) 

The correct order (matching the report's recommended fix pattern `numerator * numerator / denominator`) would be `brokerageAmount = brokerage * value / 100`, doing all multiplication before any division. Instead, `brokerage / 100` is computed first as a `double`, introducing binary floating-point rounding error before it is multiplied by `value`. This is the same root-cause class as the reported Solidity bug (`feePct = timeDiff * licenseFee / ONE_YEAR` computed before the final multiply/divide).

The same anti-pattern also appears in the standby-witness payout path and the DPoS incentive path, which compute a rate via division first and then multiply:
```java
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
``` [2](#0-1) 

```java
long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
    / voteSum));
``` [3](#0-2) 

Notably, this codebase has already recognized and hardened this exact bug class elsewhere: resource-limit calculations (`calculateGlobalLimitV2`), exchange balance calculations (`SafeExchangeProcessor`), and voter reward accrual (`accumulateWitnessVi`, `computeReward` via `DelegationStore.DECIMAL_OF_VI_REWARD`) all use `BigInteger` multiply-then-divide, and even have dedicated `allowHarden*` feature flags and regression tests (`CalculateGlobalLimitHardenTest`) specifically guarding against double-precision truncation. [4](#0-3) [5](#0-4) 

`payReward`, `payStandbyWitness`, and `IncentiveManager.reward()` were not brought under any such hardening flag and still use the unsafe divide-then-multiply double arithmetic.

### Impact Explanation
Each cycle, block reward, and transaction-fee reward payment to every witness goes through `payReward`, which is called from `payBlockReward` and `payTransactionFeeReward`. [6](#0-5) 
Because `brokerageRate` is rounded to a `double` before multiplication, the brokerage amount taken by the witness versus the amount left for the voter reward pool (`DECIMAL_OF_VI_REWARD`-based `Vi` accounting) is not the mathematically exact proportional split; it accumulates rounding error every cycle, across every witness, for the lifetime of the chain. This causes small but continuous misallocation between SR brokerage and delegator rewards — a real accounting-precision defect in a live consensus/reward-distribution path, not a theoretical one.

### Likelihood Explanation
This code path executes unconditionally on every reward payment for every witness/standby witness in every maintenance cycle, so the precision loss is deterministic and always present (not a rare edge case), matching the "regularly leaking value" concern in the original report.

### Recommendation
Rewrite `payReward` (and the analogous `payStandbyWitness` / `IncentiveManager.reward()` paths) to multiply before dividing, using integer/BigInteger arithmetic instead of `double`:
```java
long brokerageAmount = (long) (BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100)).longValueExact());
```
This mirrors the hardening already applied to `calculateGlobalLimitV2`, `SafeExchangeProcessor`, and `accumulateWitnessVi` elsewhere in the codebase, and should likely be gated the same way (e.g., via a new `allowHarden*` dynamic property) to preserve determinism/consensus compatibility across the upgrade.

### Proof of Concept
For `brokerage = 33`, `value = 100` (SUN):
- Buggy: `brokerageRate = 33/100 = 0.33` (double) → `brokerageAmount = (long)(0.33 * 100) = 33`. Looks fine at small scale, but for values where `brokerage/100` is not exactly representable in binary floating point (e.g., `brokerage = 1`, repeated over billions of reward payments across cycles) the cumulative truncation differs from the exact integer computation `value * brokerage / 100`, which can be demonstrated to diverge for large `value` (as `value` approaches/exceeds `2^53`, double precision itself breaks down entirely, unlike the exact integer path).
