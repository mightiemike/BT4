## Analysis

I reduced the external report's bug class to this invariant: *an authenticated-comparison routine that is supposed to bind "recomputed data" to "trusted committed data" must check every field that is part of the trusted commitment, otherwise divergent underlying state can be accepted as matching.*

Chasing that pattern into Aptos-native proof/replay code, the strongest local candidate is `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs`, which is the sole correctness check used by the `db-tool replay-on-archive` verifier (`storage/db-tool/src/replay_on_archive.rs`) to confirm that VM re-execution reproduces the exact `TransactionInfo` committed to the archived ledger.

### Title
Replay-verification comparator omits state/hot-state/position checkpoint hashes, allowing corrupted state roots to pass as verified - (File: types/src/transaction/mod.rs)

### Summary
`ensure_match_transaction_info` checks status, gas used, write-set hash, and event-root hash against the archived `TransactionInfo`, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, per its own inline TODO.

### Finding Description
`TransactionInfo` (the leaf object committed into the transaction accumulator, `types/src/transaction/mod.rs:2229`) carries several authenticated roots beyond the write-set/event hashes: `state_checkpoint_hash`, `hot_state_checkpoint_hash` (V1), and `position_state_checkpoint_hash` (V1), each representing a Jellyfish-Merkle/state-tree root produced at that version.

`ensure_match_transaction_info` (lines 2139–2204) validates: [1](#0-0) [2](#0-1) 

but then returns `Ok(())` without ever comparing `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` to the archived `txn_info`, and the author has already flagged this gap in a comment: [3](#0-2) 

This function is the exclusive pass/fail oracle in `db-tool`'s `replay_on_archive::Verifier::execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and calls it directly on the freshly executed `TransactionOutput`: [4](#0-3) 

Because the state-tree root fields are skipped, a re-execution that produces the *correct* write set/events (so `state_change_hash` and `event_root_hash` still match) but computes a *different* resulting state tree — e.g., due to a JMT/hot-state/position-state root computation bug, an incorrect state-value materialization step, or a divergence introduced by the (adjacent, explicitly related) `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/native-position feature — will be reported as "verified" by this tool even though the actual committed state root on the archive no longer matches what local execution would produce.

### Impact Explanation
This breaks the "authenticated response bound to the correct proof context" invariant for one of the project's own integrity tools: a hard-fork-only or state-materialization divergence in the JMT root, hot-state root, or native-position state root would not be caught by `replay-on-archive`, silently certifying a corrupted/incorrect state commitment as a faithful VM replay. Given the required "Proof And Storage Pivots" — "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding" — this is exactly the class of gap in scope, and the code's own comment already identifies it as a real, un-mitigated blind spot (not merely theoretical).

### Likelihood Explanation
This is not attacker-triggerable by itself (it requires a pre-existing state-root divergence bug elsewhere, e.g. in state computation, hot-state promotion, or the experimental native-position/trading feature), so likelihood of the *underlying* divergence is uncertain/low today, but the comparator gap means **any** such divergence — including ones introduced by future feature work in the `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` paths that the comment explicitly calls out — will go undetected by the verification tooling that operators rely on to certify replayed history. I could not confirm within this session whether any additional, independent check (elsewhere in `db-tool` or in mainnet's state-sync/executor commit path) redundantly validates these checkpoint hashes during normal chunk execution; `ChunkResultVerifier`/`ensure_transaction_infos_match` in `execution/executor/src/chunk_executor/chunk_result_verifier.rs` does compare full `TransactionInfo` objects (including checkpoint hashes) for state-sync/replay chunk execution, so the gap appears isolated to the `ensure_match_transaction_info` comparator and its `db-tool replay_on_archive` consumer rather than the core commit path.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on the recomputed `TransactionOutput`'s materialized state (when available), matching the treatment already given to `state_change_hash` and `event_root_hash`, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any other feature that depends on this tool for correctness assurance is enabled.

### Proof of Concept
Not independently reproducible as a live exploit within this session — the gap is a verification-oracle omission, confirmed directly from source (the inline TODO at `types/src/transaction/mod.rs:2196-2203` and the call site at `storage/db-tool/src/replay_on_archive.rs:392-406`), rather than a bug that itself corrupts state. A concrete PoC would require constructing/mocking a `TransactionOutput` whose write-set/events hash match an archived `TransactionInfo` but whose (separately computed) state-checkpoint hash differs, and showing `execute_and_verify` returns `Ok(None)` (verified) instead of failing.
