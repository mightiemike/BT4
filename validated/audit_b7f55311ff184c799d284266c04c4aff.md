# Finding: `ensure_match_transaction_info` skips checkpoint-hash validation, letting replay/verification tooling accept a divergent state root

### Title
Missing state/hot-state/position checkpoint hash validation in `TransactionOutput::ensure_match_transaction_info` allows replay-verification to accept a wrong state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-invariant checker used to confirm that a freshly (re-)executed `TransactionOutput` matches the `TransactionInfo` that is committed/authenticated on the accumulator. It checks status, gas, write-set hash, and event root hash, but — per its own trailing comment — it deliberately does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the authenticated `TransactionInfo`. This function is reused by replay/verification tooling (`db-tool`'s `replay_on_archive`), so a local execution that produces a different state root than the one committed/authenticated on-chain can still be reported as a "successful replay."

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It validates `status`, `gas_used`, and `write_set_hash` against the `TransactionInfo`, and separately validates the event root hash [2](#0-1) . Immediately after, the function returns `Ok(())` without ever comparing `txn_info`'s `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` to any locally computed root, and the code explicitly documents this gap: [3](#0-2) 

This comment states verbatim that "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

The function is consumed by multiple integrity-sensitive call sites: `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `execution/executor/src/chunk_executor/mod.rs`. The `state_checkpoint_hash` field is the accumulator-authenticated commitment to the Sparse/Jellyfish Merkle root of ledger state at that transaction, i.e., exactly the kind of "committed state that differs from the correct VM result" that the state-integrity gate calls out. Because `ensure_match_transaction_info` is the primary generic matcher used across these tools to assert "output == info," any caller that relies on it as its sole state-root check will not detect a state-root divergence, even though write-set hash and event hash still match.

### Impact Explanation
Replay-verification is one of the primary safety nets for detecting non-determinism, execution bugs, or storage corruption bugs after the fact (e.g., "hard-fork-only divergence during commit, replay, restore" is explicitly in scope). Because the shared matcher used by this tooling never compares the state/hot-state/position checkpoint hashes, a bug that corrupts the JMT root, a state-view bug affecting only state (not the write set itself, e.g. wrong base state, stale cache, or incorrect state-summary computation), or a divergence introduced by future protocol changes to trading-native/position state, could pass replay verification undetected. This directly undermines the guarantee that "committed state... must match the correct VM result," since the verification path meant to catch such divergences silently ignores the relevant proof field. The comment itself flags this as a live concern relevant to the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature [4](#0-3) , which is under active development in this repo (referenced in `types/src/on_chain_config/aptos_features.rs` and `storage/aptosdb/src/db/aptosdb_reader.rs`).

### Likelihood Explanation
This is not a hypothetical: the gap is acknowledged in the code as a TODO rather than a theoretical construction, meaning the maintainers are aware the check is currently incomplete and that this exact path (`db-tool`'s `replay_on_archive`) is affected today. No malicious actor is needed — any silent bug in JMT/state-summary computation reachable during chunk replay would go unflagged by this specific verification utility.

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check invoked by all its call sites) to compare locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields in the authenticated `TransactionInfo`, gated appropriately behind `transaction_info_v1`/`hot_state_root_in_txn_info`/`compute_trading_native_state_roots` feature flags as those fields become populated, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production. Until then, `replay_on_archive` and similar verification tooling should be treated as **not** validating state-root correctness.

### Proof of Concept
Not applicable in the traditional exploit sense — this is a verification-logic gap rather than an externally triggerable exploit. The proof is the function itself: tracing `ensure_match_transaction_info` shows it checks `status`, `gas_used`, `write_set_hash`, and `event_root_hash` [5](#0-4)  but returns `Ok(())` immediately after, with an explicit code comment acknowledging that checkpoint-hash divergence (including the position/trading-native state root) is not checked and would not be caught by `db-tool`'s replay verification [3](#0-2) .

**Note on completeness:** I could not fully confirm within this investigation whether normal (non-replay-tool) chunk execution commit paths in `execution/executor/src/chunk_executor/mod.rs` perform an independent, separate state-checkpoint-hash comparison elsewhere in the commit pipeline (e.g., via `DoStateCheckpoint`) that would compensate for this gap during live block/chunk execution. If such an independent check exists and is unconditionally enforced on every commit path (not just in `replay_on_archive`), the impact would be limited specifically to offline replay/audit tooling rather than live consensus-critical commit correctness. This distinction affects severity and would benefit from further tracing of `chunk_executor/mod.rs` and `workflow/do_state_checkpoint.rs`, which I was unable to complete before running out of tool budget.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
