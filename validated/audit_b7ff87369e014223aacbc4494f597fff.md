## Analysis

The external report is about **OFT Adapter lack-of-pause**: token lock/burn on the source side can succeed even though the mint/release step on the destination side is impossible (paused), with no automatic unwind — a permanent asset-loss class of bug caused by an unsynchronized two-step bridge.

Push Chain has the exact analog in `x/uexecutor`'s inbound-payload → outbound-creation pipeline.

### Where it lives

- `x/uexecutor/keeper/create_outbound.go`, `BuildOutboundsFromReceipt` gates outbound creation on `uregistryKeeper.IsChainOutboundEnabled` and returns a hard error (`"outbound is disabled for chain %s"`) if the destination chain's outbound flag is off. [1](#0-0) 
- `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `ExecuteInboundFundsAndPayload` runs the user's payload through `ExecutePayloadV2` directly against `ctx` (not inside a `CacheContext`), producing a real, already-committed EVM receipt. [2](#0-1) 
- Immediately after, `AttachOutboundsToExistingUniversalTx` is called to parse the gateway logs from that already-committed receipt and register the resulting outbound. If it errors (e.g. outbound disabled for the target chain), the error is **swallowed**: it's stashed as a string in `UniversalTx.RevertError`, `payloadPcTx.Status` is still marked `"SUCCESS"`, and the function returns `nil`. [3](#0-2) 

Contrast this with the `isSmartContract` branch a few lines above, which deliberately wraps the EVM call and fee deduction in a `sdkCtx.CacheContext()` so they "commit/revert together," explicitly to avoid leaving inconsistent EVM state when a later step fails. [4](#0-3) No equivalent safety net exists for the UEA payload-execution path that leads into `AttachOutboundsToExistingUniversalTx`.

The same swallow-and-continue pattern is present in `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`. [5](#0-4) 

### Why this reproduces the OFT-adapter bug class

Per the module's own README, an outbound is "created as a result of Push Chain logic (smart contract calls, payload execution)" — i.e. the user's UEA payload calling into `UniversalGatewayPC`'s withdraw path is what burns/locks the PRC20 and emits the `UniversalTxOutboundEvent` that `BuildOutboundsFromReceipt` later decodes. [6](#0-5) That burn already happened, uncondtionally, in the committed EVM receipt before `AttachOutboundsToExistingUniversalTx` runs. If the destination chain's outbound is disabled — either because it was already disabled or is disabled by the time this async inbound-execution flow runs (ballot finality can take time; an admin can toggle `IsOutboundEnabled` in between) — no `OutboundTx` is ever created, no `PendingOutbounds` entry exists, and none of the revert/refund machinery (`buildRevertOutbound`, `handleFailedOutbound`, `applyGasRefund`) is invoked. The only trace is a string in `UniversalTx.RevertError`.

This is functionally identical to the reported OFT-adapter bug: the "lock" step (PRC20 burn via the gateway withdraw call inside the payload) commits unconditionally, while the "release" step is blocked by disabled outbound, and there is no automatic unwind path — funds are permanently stranded, discoverable only via manual/offchain inspection of the `RevertError` string.

### Title
Payload-triggered outbound creation silently drops burned funds when destination chain outbound is disabled - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
`ExecuteInboundFundsAndPayload` (and its `execute_inbound_gas_and_payload.go` counterpart) executes the user's UEA payload directly against the live SDK context, letting any PRC20 burn/withdraw performed by the payload's gateway call commit unconditionally. The subsequent step that turns the withdraw event into a tracked `OutboundTx` (`AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt`) can fail if the destination chain's outbound flag is disabled in `x/uregistry`. That failure is caught and recorded only as a string (`UniversalTx.RevertError`); the already-executed PCTx is still marked `"SUCCESS"`, no `OutboundTx`/`PendingOutbounds` entry is created, and none of the mint-back/refund logic runs.

### Finding Description
`BuildOutboundsFromReceipt` returns a hard error the moment it sees a `UniversalTxOutbound` event pointing at a chain with `IsOutboundEnabled=false`. [1](#0-0) That error propagates through `AttachOutboundsToExistingUniversalTx` [7](#0-6) into `ExecuteInboundFundsAndPayload`, where it is caught, stored in `UniversalTx.RevertError`, and then discarded — the function proceeds to record the payload PCTx as `SUCCESS` and returns `nil`. [3](#0-2) 

At that point, the EVM state produced by `ExecutePayloadV2` — including any PRC20 burn performed inside the payload's call into the gateway contract — has already been written to the committed context, since this call runs directly on `ctx`, unlike the `isSmartContract` branch that deliberately uses a `CacheContext` for exactly this atomicity reason. [4](#0-3) 

### Impact Explanation
Funds burned/withdrawn by the user's payload are permanently lost: no `OutboundTx` is created so no relayer/UV ever attempts delivery on the destination chain, and no revert-mint or refund path (`buildRevertOutbound`, `handleFailedOutbound`, `applyGasRefund`) is triggered since those only run on the explicit "deposit failed" or "outbound observed failure" branches, not on this "outbound couldn't even be created" branch. This is a direct, unrecoverable loss of user/protocol-controlled funds.

### Likelihood Explanation
Reachable by an ordinary user submitting an inbound with a payload that calls the gateway's outbound/withdraw path for a target chain. `ChainConfig.Enabled.IsOutboundEnabled` is admin-toggleable and there is normal operational reason to pause outbound to a chain (maintenance, incident response) while inbounds/executions targeting it are already in flight from ballot-finalized-but-not-yet-executed inbounds — this asynchronous window between ballot finalization and inbound execution makes the race practically triggerable without any privileged action by the attacker.

### Recommendation
Wrap the payload execution and `AttachOutboundsToExistingUniversalTx` call in the same `CacheContext`-style atomic unit used in the `isSmartContract` branch, so that if outbound attachment fails, the EVM burn/withdraw is rolled back together with it. Alternatively, treat `AttachOutboundsToExistingUniversalTx` failure as a first-class failure path that triggers the same INBOUND_REVERT/mint-back flow used elsewhere in this file for deposit failures, rather than only recording a string on `RevertError`.

### Proof of Concept
1. Admin adds chain config for `eip155:X` with `IsOutboundEnabled=true`.
2. User submits an inbound (observed/voted by UVs) with a `FUNDS_AND_PAYLOAD` payload whose UEA execution calls the gateway's withdraw method targeting `eip155:X`.
3. Before the ballot finalizes and `ExecuteInboundFundsAndPayload` runs (or concurrently), admin disables outbound for `eip155:X` (`IsOutboundEnabled=false`) — a normal, non-malicious operational action.
4. `ExecutePayloadV2` executes and commits the withdraw (burn) on Push Chain.
5. `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` returns `"outbound is disabled for chain eip155:X"`.
6. `ExecuteInboundFundsAndPayload` stores this string in `UniversalTx.RevertError`, marks the PCTx `SUCCESS`, and returns `nil` — funds are burned with no outbound record and no refund. [3](#0-2)
