### Title
Signer-local wall-clock timing in reorg-permission check can cause divergent block-acceptance verdicts across the signer set - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new tenure is allowed to reorg a previous, already-mined tenure. Just like the reported `pre_deposit_check_regulated` flaw — where a compound condition (`force_full_transfer && from_region == US`) gated an abort without confirming the actual "full transfer" invariant that the check was meant to enforce — this function gates an "is the reorg allowed" verdict on a compound, time-based condition (`proposal_to_sortition < first_proposal_burn_block_timing`) whose inputs (`approved_time`, `sortition_state_received_time`) are *locally observed, per-signer wall-clock values* rather than a value derived from chain state that every signer can reproduce identically.

### Finding Description
In `check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`), when a miner's new tenure does not build off the immediately prior sortition, the signer must decide whether the implied reorg is "valid behavior." The decisive branch is: [1](#0-0) 

Here:
- `sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` — the local time at which *this* signer's node received the burn block.
- `local_block_info.approved_time` is the local time at which *this* signer approved the earlier, reorg-target block.

Both are wall-clock timestamps recorded independently by each signer process, not values that are part of the canonical chain state (unlike `consensus_hash`, `burn_header_timestamp`, block heights, etc., which are the same for every honest node). The comparison `Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing` therefore does not have to evaluate the same way on every signer for the identical input burn block/tenure — one signer may have approved the earlier block sooner (or later) relative to when it received the new sortition than another signer did, due to ordinary network delay, load, or clock skew.

This is structurally the same bug class as the external report: a security-relevant boolean gate is built from a condition (`force_full_transfer && region==US`, respectively `proposal_to_sortition < threshold`) that is evaluated without anchoring it to a value all parties are guaranteed to compute identically. In the Move code this let a false negative wrongly abort valid transfers; here it lets different signers reach different reorg-permission verdicts for the exact same proposed tenure change.

### Impact Explanation
Signers use this verdict to accept or reject a tenure-change block proposal (`validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs:497-504`, which calls `check_parent_tenure_choice` and returns `RejectReason::ReorgNotAllowed` on `false`). If timing observations differ across the signer set close to the `first_proposal_burn_block_timing` boundary, a subset of signers may sign/approve the reorging tenure's block while another subset rejects it as an invalid reorg. This is exactly the "a validation verdict two nodes disagree on" analog called out in scope, and it manifests as a temporary tip disagreement: part of the signer set builds on the new (reorging) tenure, part refuses and continues expecting the old tenure, stalling block finalization until enough weight aligns on one side. This matches the High-impact category ("a poison or reward mis-payment bounded to fees, temporary tip disagreement").

It does not on its own force a majority; a single miner timing the second block's broadcast/approval close to the configured `first_proposal_burn_block_timing` window (a parameter each signer independently configures/observes against local receive times) is enough to put different signers on different sides of the `<` comparison for the same tenure — this requires no signer collusion or majority, only a normally operating minority of the network to have slightly different local timing.

### Likelihood Explanation
The comparison uses seconds-granularity, locally observed timestamps in a distributed system with unavoidable network latency and, for asynchronronously-updated `SignerDb` state, processing skew across dozens of signers. Any tenure change whose proposal happens close to the `first_proposal_burn_block_timing` boundary (a config value, default measured in tens of seconds) will produce inconsistent `proposal_to_sortition` values signer-to-signer even under benign network conditions, so triggering the divergence does not require an attacker to do anything exotic beyond normal chain operation near a Bitcoin block boundary. This makes the likelihood of naturally occurring divergence non-trivial, and a motivated minority actor (e.g. a miner who controls when they broadcast a tenure-change block) can deliberately time it to maximize the chance of split verdicts.

### Recommendation
Base the reorg-permission decision on data that is part of canonical, reproducible chain state rather than per-signer wall-clock timestamps — e.g., derive the "how close to the burn block transition was the first block" measurement from `burn_header_timestamp`/block heights recorded on the burnchain, or otherwise ensure every signer computes the same boundary value from consensus-visible inputs. If local receive-time data must be used as a heuristic, treat it as advisory only and do not let it be the sole determinant of `Ok(true)`/`Ok(false)` in `check_parent_tenure_choice`; require corroboration from a value that is guaranteed identical across signers before permitting or refusing a reorg.

### Proof of Concept
1. Two signers, A and B, both track the reorg-target tenure's earlier block and store their own `approved_time` for it (via `SignerDb`), and later each independently compute `sortition_state_received_time` for the same new burn block hash via `get_burn_block_receive_time`.
2. Because A and B receive/store these events at slightly different wall-clock moments (ordinary network jitter, or a miner deliberately releasing the tenure-change proposal at a moment straddling the timing boundary), signer A computes `proposal_to_sortition_A = t_recv_A - t_approved_A < first_proposal_burn_block_timing` (reorg permitted → `Ok(true)`), while signer B computes `proposal_to_sortition_B = t_recv_B - t_approved_B >= first_proposal_burn_block_timing` (reorg refused → `Ok(false)`).
3. Signer A signs the new tenure's block (accepting the reorg); signer B rejects it via `RejectReason::ReorgNotAllowed` in `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:493-504`).
4. The signer set is now split on whether the new tenure's block is valid, producing a temporary tip disagreement until enough weight accumulates on one branch — reproducible whenever a tenure-change proposal's timing straddles `first_proposal_burn_block_timing` across the signer population's local clocks.

Note: I was unable to fully trace how `approved_time`/`get_burn_block_receive_time` are persisted in `stacks-signer/src/signerdb.rs` (89 matches found but not inspected in this session due to running out of tool budget), so I cannot rule out an existing mitigation (e.g., some rounding/quantization or fallback to a chain-derived value) that narrows this window. This should be verified directly against `stacks-signer/src/signerdb.rs` before treating this as fully confirmed.
