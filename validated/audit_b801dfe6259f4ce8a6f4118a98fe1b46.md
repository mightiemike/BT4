### Title
Webhook shop-domain header is not cryptographically bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
`shopify.webhooks.validate`/`process` authenticates an inbound webhook solely by checking an HMAC of the raw request **body** against the app's shared `apiSecretKey` [1](#0-0) . The `X-Shopify-Shop-Domain` header, which is later used to look up the shop's offline session and attribute the webhook to a specific tenant, is read from the request headers and trusted as-is — it is never included in the HMAC computation [2](#0-1) . Because `apiSecretKey` is a single value shared by the app across *all* shops that install it, any merchant who has legitimately installed the app can capture a validly-signed body+HMAC pair from a webhook delivered to their own store, then replay that exact body/HMAC to the app's public webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value pointing at a victim shop. The signature check still passes because the domain is not part of what is signed, so the request is accepted as if it came from the victim shop.

This is the same bug class as the reported `deliverMarketplaceWithSignatures` issue: a signature/verification step that authenticates *content* but fails to bind that content to the specific identity (there: the priority mech address; here: the shop domain) the system subsequently trusts and acts on behalf of.

### Finding Description
`validateHmacFromRequestFactory` computes and compares an HMAC over `rawBody` only, using the shared `config.apiSecretKey` [1](#0-0) . After this check succeeds, `checkWebhooksHeaders`/`checkEventsHeaders` simply extract the `domain`, `topic`, `webhookId`, etc. straight from the (unauthenticated) headers and return them as trusted fields [2](#0-1) . Nothing ties the `domain` header value to the specific HMAC/body pair that was verified.

Downstream, this `domain` value becomes the shop identity used to load the app's session and admin client:
- In `shopify-app-react-router`/`shopify-app-remix`, `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` and returns `shop: check.domain` plus an authenticated `admin` client bound to that shop's stored access token [3](#0-2) .
- In the core `process()` path, `webhookCheck.domain` is passed directly into the registered handler callback as the `shop_domain` argument used by app business logic [4](#0-3) .

Because a single `apiSecretKey` is shared across every shop install of the app, an attacker who controls (or has a trial/dev install of) their own shop can:
1. Trigger a real event on their own store (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) to receive a webhook with a correctly computed `X-Shopify-Hmac-Sha256` over a body they control/observe.
2. Replay that exact `rawBody` + HMAC to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`) header rewritten to a victim shop's domain.
3. `validateHmacFromRequestFactory` accepts it because the HMAC only ever covered the body [5](#0-4) .
4. The app then loads the victim's offline session/admin client and executes handler logic "on behalf of" the victim shop, using attacker-controlled payload content.

### Impact Explanation
Depending on the app's webhook handlers, this allows cross-tenant impact: forged `app/uninstalled` events could trigger cleanup logic against a victim's stored session/data; forged GDPR/compliance webhooks (`customers/redact`, `shop/redact`) could trigger deletion of a victim's stored data; forged business-topic webhooks (`orders/create`, etc.) processed with the victim's `admin` API client could cause the handler to perform actions (writes, notifications, side effects) attributed to and executed against the victim shop using the victim's own access token, even though the triggering event never actually happened on the victim's store. This is a cross-tenant authentication/attribution flaw directly analogous to the reported unbound-signature issue.

### Likelihood Explanation
The attack requires only an unprivileged actor — a merchant/customer who has installed the app on any shop (including a free dev/trial store) — and a public HTTP POST to the app's already-public webhook endpoint. No secret leakage, MITM, or dependency compromise is required; the attacker legitimately possesses a valid signature for content they generated. The only extra knowledge needed is the victim's `myshopify.com` domain, which is generally guessable/public. This is directly reachable from "a single merchant" per the validation criteria.

### Recommendation
Bind the trusted identity (`shop domain`) cryptographically to the signed content rather than trusting it purely from an unauthenticated header:
- Include the shop domain (and/or webhook id) in the HMAC input when validating webhook requests, or
- Maintain a per-shop verification step (e.g., confirm the `domain` header matches a shop with an active session/subscription that is expected to receive this specific `webhookId`/topic before processing), and reject/log mismatches.
- At minimum, deduplicate and validate `webhookId` uniqueness per shop to prevent naive replay, and treat the `domain` header as untrusted input until corroborated by something bound to the signature.

### Proof of Concept
Conceptual PoC (cannot be executed here, but demonstrates the flow using the library's own test harness pattern):
```ts
// Attacker owns shop-a.myshopify.com and has installed the target app.
// Step 1: Attacker triggers an event on their own store and captures the
// resulting webhook POST, e.g.:
//   body = '{"id":123,"note":"hello"}'
//   X-Shopify-Hmac-Sha256 = createSHA256HMAC(apiSecretKey, body) // valid, shared secret
//   X-Shopify-Shop-Domain = 'shop-a.myshopify.com'

// Step 2: Attacker replays the same body + HMAC to the app's webhook
// endpoint, but swaps the domain header for the victim's shop:
await request(app)
  .post('/webhooks')
  .set({
    'X-Shopify-Hmac-Sha256': capturedHmac,          // still valid - only signs body
    'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // forged, unauthenticated
    'X-Shopify-Topic': 'orders/create',
    'X-Shopify-Api-Version': '2024-01',
    'X-Shopify-Webhook-Id': 'replayed-id',
  })
  .send(body)
  .expect(200); // validateHmacFromRequestFactory + checkWebhooksHeaders both pass,
                 // and handler is invoked with shop_domain = 'victim-shop.myshopify.com'
```
This mirrors `validateHmacFromRequestFactory` ( [1](#0-0) ) and `checkWebhooksHeaders` ( [2](#0-1) ) logic exactly as implemented, confirming the domain header is never verified against the signature.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
