### Title
Missing slippage/expected-output protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` allows front-run victims to trade at an unfavorable, unexpected ratio - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeInject` and `ExchangeWithdraw` contracts compute the counterpart token amount at execution time from the exchange's *current* pool balances, but neither the contract schema nor the actuators let the caller specify a minimum/maximum acceptable counterpart amount. `ExchangeTransactionContract` (a sibling actuator) explicitly protects against this by requiring an `expected` amount and reverting if the computed output is below it, proving the codebase itself recognizes this exact bug class needs a check.

### Finding Description
Both `ExchangeInjectActuator.execute()`/`doValidate()` and `ExchangeWithdrawActuator.execute()`/`doValidate()` derive `anotherTokenQuant` purely from the exchange pool's `firstTokenBalance`/`secondTokenBalance` read at transaction-processing time: [1](#0-0) [2](#0-1) 

This mirrors the root cause pattern in the external report: a user computes an expected outcome off-chain from currently observable on-chain state (`lastHash` in the Tray report; the pool ratio here), broadcasts a transaction, but any other transaction that changes that state before inclusion (e.g. an `ExchangeTransactionContract` trade against the same `exchangeId`, or another `Inject`/`Withdraw`, submitted with higher energy price / by an attacker front-running the mempool) silently changes the amount the user actually gets/gives — with no on-chain check to detect the discrepancy and abort.

Crucially, the actuator that already existed for the plain trading path, `ExchangeTransactionActuator`, demonstrates the codebase's own recognized mitigation: it takes a caller-supplied `tokenExpected` and validates the computed output against it: [3](#0-2) 

`ExchangeInjectContract` and `ExchangeWithdrawContract` (defined in `exchange_contract.proto`) carry no analogous `expected`/`min`/`max` field, so `ExchangeInjectActuator`/`ExchangeWithdrawActuator` cannot perform the equivalent check even if they wanted to — the fix requires both a proto field addition and actuator validation, exactly as the report's `Tray.sol` fix required adding a `_lastHash` parameter plus a `require`.

### Impact Explanation
An LP (only the exchange creator can inject/withdraw, per `doValidate()`'s creator check) intending to inject or withdraw liquidity at a known ratio can be forced into a worse ratio than expected because:
- A pending `ExchangeTransactionContract` (an unprivileged, permissionless trade against the same exchange pool) executed first shifts `firstTokenBalance`/`secondTokenBalance`.
- The inject/withdraw is processed against the new balances, transferring/receiving a different (and possibly much less favorable) `anotherTokenQuant` than the creator anticipated.
- There is no mechanism to detect this and revert; the transaction succeeds and funds/assets move irreversibly at the unexpected rate.

This causes real value loss for the exchange creator (unfavorable liquidity provisioning/removal), and is directly triggerable by any anonymous account broadcasting an `ExchangeTransactionContract` transaction — no privileged actor or malicious node/peer is required, matching the allowed analog categories (exchange/market math).

### Likelihood Explanation
Likelihood is moderate: it requires the attacker (or ordinary market activity) to get an `ExchangeTransactionContract` trade included before the creator's `Inject`/`Withdraw` transaction in the same block window — feasible via normal fee/ordering competition on any TRON node accepting broadcast transactions, without needing any special privilege, similar to the "more gas" or frontrunning scenario described in the source report.

### Recommendation
Add an `expected` (min-out for withdraw, max-in/min-out bound for inject) field to `ExchangeInjectContract` and `ExchangeWithdrawContract` in `exchange_contract.proto`, and have `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate the freshly computed `anotherTokenQuant` against it (mirroring the existing check in `ExchangeTransactionActuator.doValidate()` at lines 217-221), reverting with a `ContractValidateException` when the computed value violates the caller's expectation.

### Proof of Concept
1. Exchange `E` holds TRX/TokenA balances such that 100 TRX ⇄ 100 TokenA.
2. The exchange creator broadcasts `ExchangeInjectContract{exchangeId=E, tokenId=TRX, quant=100}` expecting to also deposit ~100 TokenA (`anotherTokenQuant` computed at broadcast time via `ExchangeInjectActuator.execute()` lines 71-83).
3. Before this transaction is packed, another user broadcasts an `ExchangeTransactionContract` trading heavily against pool `E`, shifting the balance to e.g. 200 TRX / 50 TokenA.
4. The creator's inject transaction is processed against the new ratio, computing `anotherTokenQuant = 25` TokenA instead of the ~100 expected (per `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` in `ExchangeInjectActuator.java` lines 73-74) — with no validation catching the discrepancy, the creator provides liquidity at an unintended, unfavorable ratio and the transaction still succeeds (`ret.setStatus(fee, code.SUCESS)` at line 106).
