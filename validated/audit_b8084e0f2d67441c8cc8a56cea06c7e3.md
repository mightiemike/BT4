### Title
Hardcoded `paid_fee_on_l1 = Fee(1)` on the consensus/validator L1Handler re-execution path bypasses the L1 fee check - ([File: crates/apollo_transaction_converter/src/transaction_converter.rs])

### Summary
The report describes a Uniswap adapter that never lets the caller/validator supply or verify the real swap fee, so an economically meaningful parameter is effectively hardcoded/ignored. The analogous root cause in this sequencer codebase is `convert_consensus_l1_handler_to_internal_l1_handler`, which hardcodes the L1-handler transaction's `paid_fee_on_l1` to `Fee(1)` for every L1 message a validator receives via consensus, instead of using the fee that was actually paid on L1. The only downstream check that consumes this value (`execute_raw` in `l1_handler_transaction.rs`) merely asserts the value is non-zero, so the hardcoded constant trivially and unconditionally satisfies the fee check regardless of the true L1-paid amount.

### Finding Description
When a validator node receives an `L1HandlerTransaction` through the consensus protocol (i.e. from the block proposer, not directly scraped from L1), it converts the wire `ConsensusTransaction` into the internal executable representation via: [1](#0-0) 

```rust
fn convert_consensus_l1_handler_to_internal_l1_handler(
    &self,
    tx: transaction::L1HandlerTransaction,
) -> TransactionConverterResult<executable_transaction::L1HandlerTransaction> {
    Ok(executable_transaction::L1HandlerTransaction::create(
        tx,
        &self.chain_id,
        // TODO(Gilad): Change this once we put real value in paid_fee_on_l1.
        Fee(1),
    )?)
}
```

This hardcodes `paid_fee_on_l1` to `Fee(1)` for *every* consensus-delivered L1 handler transaction, discarding whatever fee was genuinely paid on L1 (or not paid at all). During execution, this field is the sole basis for the L1 fee enforcement check in blockifier: [2](#0-1) 

```rust
let paid_fee = self.paid_fee_on_l1;
// For now, assert only that any amount of fee was paid.
// The error message still indicates the required fee.
if paid_fee == Fee(0) {
    return Err(TransactionExecutionError::TransactionFeeError(Box::new(
        TransactionFeeError::InsufficientFee {
            paid_fee,
            actual_fee: receipt.fee,
        },
    )));
}
```

Because the check only verifies `paid_fee != Fee(0)`, and the converter unconditionally supplies `Fee(1)`, this check can never fail for any L1Handler transaction reaching a validator through consensus — independent of the amount (if any) genuinely paid to the L1 core contract. Any node that only sees a transaction through the consensus/mempool path (rather than re-deriving it from the L1 event log itself) will always accept it as "fee paid," even if the fee amount encoded/verified elsewhere is zero or insufficient.

### Impact Explanation
L1-handler transactions consume a message that was bridged from L1 and their `paid_fee_on_l1` field is meant to reflect (and be checked against) the fee actually paid by the L1 sender to cover L2 execution costs. By hardcoding this to a nonzero placeholder in the consensus-conversion path, validators lose the ability to detect and reject L1 handler transactions whose L1-paid fee was insufficient or spoofed at the point they re-execute them (e.g., during Starknet OS re-execution / validator-side execution after receiving the tx via consensus, as opposed to independently reading it from L1 itself). This weakens the fee-enforcement guarantee for L1→L2 messages network-wide and can allow L1 handler execution to proceed uncompensated, which is a resource/economic-accounting correctness issue affecting the sequencer's execution and fee-charging pipeline.

### Likelihood Explanation
This code path is exercised on every single L1Handler transaction that arrives at a node through the standard consensus transaction flow (the common, expected path for all non-proposing nodes), making it a near-certain (not edge-case) occurrence rather than a rare corner case. The vulnerability is already flagged by the developers via a `TODO` comment, indicating the team was aware the value is a placeholder, which supports that the root cause is real but its exploitation depends on how strictly `paid_fee_on_l1` is meant to be enforced versus this being an accepted temporary simplification.

### Recommendation
Propagate the real fee paid on L1 (as recorded by the L1 events scraper / L1 core contract event data) through the consensus-transaction wire format and `L1HandlerTransaction::create`, rather than hardcoding `Fee(1)` in `convert_consensus_l1_handler_to_internal_l1_handler`. Ensure the fee-check in `l1_handler_transaction.rs` validates against the actual paid amount, not merely its non-zero-ness.

### Proof of Concept
1. A validator node receives an `L1HandlerTransaction` via the consensus channel (`ConsensusTransaction::L1Handler`).
2. `TransactionConverter::convert_consensus_l1_handler_to_internal_l1_handler` is invoked, which always sets `paid_fee_on_l1 = Fee(1)` regardless of the transaction's true L1-paid fee. [1](#0-0) 
3. During execution, `execute_raw` reads `self.paid_fee_on_l1` (now always `Fee(1)`), and the only check performed is `paid_fee == Fee(0)` — which never triggers. [2](#0-1) 
4. Consequently, this validator's re-execution and fee accounting for the L1 message diverges from a node that has authoritative knowledge of the real L1-paid fee (e.g. a node reading the same L1 event directly), since the hardcoded placeholder always "passes" the check irrespective of the genuine amount paid.

Note: I could not fully verify within the available investigation depth whether other paths (e.g. the L1 events scraper flow, `apollo_integration_tests/tests/l1_events_scraper_end_to_end.rs`, or the Starknet OS `AssertTransactionHash`/nonce consumption logic) additionally cross-check `paid_fee_on_l1` against an L1-sourced authoritative value elsewhere in the pipeline, which would mitigate the practical exploitability of this hardcoding. This should be confirmed with a full trace of `L1HandlerTransaction::create` call sites, listed via [3](#0-2)  and [4](#0-3) .
