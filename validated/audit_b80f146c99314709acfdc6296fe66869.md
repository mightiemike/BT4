### Title
Missing negative-balance guard in default `ExchangeProcessor.exchange` path allows asset/accounting corruption on TRX/TRC10 bancor-style exchange orders - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
`ExchangeProcessor.exchange` computes a bancor-curve conversion using `double` arithmetic and truncating `(long)` casts, and unlike the hardened `SafeExchangeProcessor` path, the resulting new pool balances in `ExchangeCapsule.transaction` are only checked for negativity when `hardenedCalc == true`. Since `hardenedCalc` is gated by the network-wide `allowHardenExchangeCalculation` dynamic property (off by default / requires a committee proposal to activate), an ordinary unprivileged account submitting an `ExchangeTransactionContract` through `ExchangeTransactionActuator` can drive the buy-side pool balance negative or otherwise inconsistent via floating-point rounding at extreme sell quantities, with no on-chain check rejecting it.

### Finding Description
`ExchangeCapsule.transaction(...)` selects the processor implementation based on the `hardenedCalc` flag: [1](#0-0) 

Only in the `hardenedCalc` branch are `StrictMathWrapper.addExact`/`subtractExact` used and is there an explicit post-condition check:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

When `hardenedCalc` is `false` (the default), the plain `ExchangeProcessor` is used: [3](#0-2) 

This class performs the bancor "sell → relay supply → buy" computation entirely in `double` precision and truncates results via `(long) issuedSupply` / `(long) exchangeBalance` without any bound-checking against the actual pool balance. `ExchangeTransactionActuator.doValidate()` only checks that the sell-side token balance stays under `dynamicStore.getExchangeBalanceLimit()` and that `anotherTokenQuant >= tokenExpected` (a lower bound, not an upper bound tied to the actual pool reserve): [4](#0-3) 

Nothing in `validate()` or `execute()` verifies that the computed `anotherTokenQuant` (buy-side output) is less than the exchange's current `secondTokenBalance`/`firstTokenBalance`. In the non-hardened path, `ExchangeCapsule.transaction` computes `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (plain long subtraction, no bound check), so if floating-point rounding at the extremes of the curve (very large sell quantity relative to a small pool, driven near the `balanceLimit` cap) causes `buyTokenQuant` to be computed larger than the actual reserve, the resulting negative balance is silently persisted to the store via `Commons.putExchangeCapsule`, and the attacker's account is credited the full (rounded) `anotherTokenQuant` via `addAssetAmountV2`/`setBalance` in `ExchangeTransactionActuator.execute`: [5](#0-4) 

This means the checks that would normally stop such an attack (signature/permission checks, `DecodeUtil.addressValid`, and the actuator's `validate()`) do not verify the invariant that the computed swap output cannot exceed the counter-asset reserve; they only validate address format, balance sufficiency for the *sell* side, and the lower-bound `expected` amount.

### Impact Explanation
If exploitable, this allows an attacker to extract more of the counter-asset (TRX or TRC10 token) from an `Exchange` pool than is actually held in reserve, corrupting the pool's `firstTokenBalance`/`secondTokenBalance` state (potentially negative) and crediting themselves assets that were never backed by real reserves — an asset/accounting corruption impact matching the "Critical" bounty class for created/destroyed value and unauthorized state change.

### Likelihood Explanation
I was not able to fully confirm within the available tooling whether the double-precision bancor formula in `ExchangeProcessor` can, in practice, produce a `buyTokenQuant` that exceeds the actual counter-side pool balance given the `balanceLimit` constraint on sell quantities (default value of `getExchangeBalanceLimit()` was not retrieved) — the formula is asymptotic by design and normally self-limiting. Establishing concrete exploitability requires a numeric/JUnit experiment (as suggested in the question) sweeping extreme `sellTokenQuant` values near the `balanceLimit` boundary against small pool balances to see whether `(long) exchangeBalance` ever exceeds `buyTokenBalance`. The structural weakness (absence of the negative-balance check outside `hardenedCalc`) is confirmed and unambiguous; whether it is triggerable purely through floating-point rounding under real network constraints (transaction fees, `balanceLimit`, and the requirement that pools must first be created/injected with the attacker's own funds) is unconfirmed.

### Recommendation
Apply the same post-condition check used in `SafeExchangeProcessor`'s path unconditionally in `ExchangeCapsule.transaction`, regardless of `hardenedCalc`: reject any transaction where the resulting `newFirstTokenBalance` or `newSecondTokenBalance` would be negative, and consider making the hardened (`BigDecimal`/`StrictMathWrapper`) computation the only supported path rather than one gated behind an optional dynamic property.

### Proof of Concept
Because I could not verify the default value of `getExchangeBalanceLimit()` and could not execute code, here is the JUnit skeleton the question requests to determine exploitability; a background agent with test-execution access should run it with fee/limit values pulled from `DynamicPropertiesStore` defaults:
```java
// framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorOverflowTest.java
@Test
public void extremeQuantShouldNotExceedPoolBalance() {
  long supply = 1_000_000_000_000_000_000L;
  ExchangeProcessor processor = new ExchangeProcessor(supply, false);
  long sellTokenBalance = 1L;               // minimal reserve
  long buyTokenBalance = 1L;                // minimal reserve
  long sellTokenQuant = 1_000_000_000_000_000L; // near default balanceLimit
  long buyTokenQuant = processor.exchange(sellTokenBalance, buyTokenBalance, sellTokenQuant);
  Assert.assertTrue("buyTokenQuant must never exceed buyTokenBalance",
      buyTokenQuant <= buyTokenBalance);
}
```
If this assertion fails for any combination of `sellTokenBalance`/`buyTokenBalance`/`sellTokenQuant` permitted by `ExchangeTransactionActuator.doValidate()`'s `balanceLimit` check, the vulnerability is confirmed exploitable end-to-end via a broadcast `ExchangeTransactionContract`.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,

          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;

          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)

      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
