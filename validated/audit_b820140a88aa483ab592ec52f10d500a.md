### Title
`TransactionOutput::ensure_match_transaction_info` skips state-checkpoint hash validation, allowing replay-verify tooling to accept divergent state/position roots - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single generic invariant checker used to confirm that a locally re-executed `TransactionOutput` matches an authenticated, proof-covered `TransactionInfo` from ledger/backup storage. It checks status, gas used, write-set hash (`state_change_hash`), event root hash, and transaction hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the Sparse-Merkle/Jellyfish state root at a checkpoint. This is explicitly acknowledged in a `TODO(trading-native)` comment in the same function. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates a re-executed `TransactionOutput` against a `TransactionInfo` object pulled from an archive/backup (an authenticated, accumulator-proven record). It verifies:
- execution status [2](#0-1) 
- gas used [3](#0-2) 
- write-set hash vs `state_change_hash` [4](#0-3) 
- event root hash [5](#0-4) 

but the function returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against anything computed from the replayed state. The comment directly above the `Ok(())` states this is a known gap: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [6](#0-5) 

This function is the sole verification gate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` per transaction to decide pass/fail for the replay-verify job: [7](#0-6) 

Because the state-checkpoint hash comparison is entirely absent, if the archived `TransactionInfo.state_checkpoint_hash` (or hot-state/position checkpoint hash) does not match what local re-execution would compute — whether due to corruption in the backup pipeline, a bug in state-root computation, or a divergent VM/state-commit implementation — the tool will still report "successful replay" as long as status/gas/write-set-hash/event-root-hash happen to match. `ensure_match_transaction_info` is also invoked from `aptos-debugger` (per grep match), so the same silent gap propagates to any tool relying on this single check as the ground-truth "did replay match ledger" verdict.

The same file also introduces new, not-yet-fully-wired fields (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) on `TransactionInfoV1`, confirming there is now a "position state root"/"trading-native" state commitment that this checker is supposed to validate but does not. [8](#0-7) 

### Impact Explanation
Replay-verify tooling exists specifically to catch state-commitment divergence — a wrong Merkle/Jellyfish state root, corrupted write-set application, or an execution-layer bug that silently diverges from the canonical, authenticated ledger. Because `ensure_match_transaction_info` never compares checkpoint hashes, a state-root divergence (including a wrong position/hot-state root) at a checkpoint transaction will not be flagged: the tool will report a clean replay even though the durable, proof-bound state commitment has silently diverged from local execution. This directly matches the "Proof and Storage Pivots" invariant that "VM outputs, transaction infos ... must survive executor-to-storage handoff unchanged" and that "authenticated API and proof-bearing responses must stay bound to the right ... root." A masked divergence here can hide a hard-fork-class bug (mainnet nodes computing different state roots) from the very tool meant to detect it, which is a high-impact integrity gap even though it does not by itself corrupt live consensus state.

### Likelihood Explanation
This is not a hypothetical: it is explicitly documented by the code authors themselves as a real, currently-unguarded gap ("ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges"). The gap is unconditionally present in the shipped code today (the `Ok(())` is not behind any feature flag inside `ensure_match_transaction_info`); only the *new* `position_state_checkpoint_hash` computation feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is flagged, but the verifier itself doesn't check the pre-existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` either, so any state-root divergence — old or new — at checkpoint boundaries is unverified by this tool right now.

### Recommendation
In `ensure_match_transaction_info`, when the transaction is a state checkpoint (i.e., `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` is `Some`), compute the corresponding state/hot-state/position root from the locally re-executed state after applying this and prior write sets, and `ensure!` it matches the value in `txn_info`. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, but the existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` checks should be added immediately regardless, since they are unconditionally reachable today via `replay_on_archive` and `aptos-debugger`.

### Proof of Concept
1. Take an archived backup where a checkpoint `TransactionInfo` has a `state_checkpoint_hash` (or `hot_state_checkpoint_hash`) that does not correspond to the actual post-execution state (e.g. corrupted in transit, or produced by a state-root computation bug), but where `state_change_hash` (write-set hash), `event_root_hash`, `gas_used`, and `status` still coincidentally/deliberately match.
2. Run `storage/db-tool/src/replay_on_archive.rs` against this backup.
3. `execute_and_verify` re-executes the transaction and calls `ensure_match_transaction_info` [9](#0-8) .
4. Because the function never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, `ensure_match_transaction_info` returns `Ok(())` and the tool records the replay as successful for that transaction, masking the true state-root divergence.

Note: I could not fully trace how `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are populated end-to-end in `execution/executor-types/src/state_checkpoint_output.rs` and `execution_output.rs` within the available time, so the exact conditions under which `position_state_checkpoint_hash` becomes `Some` in production today are not fully confirmed — this is stated as an open uncertainty. However, the `state_checkpoint_hash` field (legacy Sparse Merkle root) is unconditionally present and unconditionally unchecked by this function, which is sufficient to substantiate the finding independent of the newer "trading-native" fields.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
