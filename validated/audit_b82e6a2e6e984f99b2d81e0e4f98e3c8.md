## Analog Finding

### Title
Stale pre-consumed energy reservation not reconciled before `payEnergyBill` charges real usage, causing double debit of frozen energy and TRX fee overcharge - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ReceiptCapsule.java`, `chainbase/src/main/java/org/tron/core/db/TransactionTrace.java`)

### Summary
Similar to the elfi-protocol bug where an old, already-settled liability value was passed into a downstream pool-settlement call, java-tron's TVM-freeze-v2 energy accounting pre-consumes (reserves) energy from the caller/creator account and persists it to the `AccountStore` *before* the transaction executes, but the subsequent fee-settlement step (`ReceiptCapsule.payEnergyBill`) uses a stale, pre-reservation "energy left" snapshot to compute how much real usage can be covered by frozen energy. The reconciliation step that is supposed to undo the speculative reservation (`TransactionTrace.resetAccountUsage`) is skipped whenever the transaction reverts or throws, leaving the reservation permanently baked into the account's persisted `energyUsage`, while `payEnergyBill` still debits real usage against the outdated snapshot.

### Finding Description
Before VM execution, `getAccountEnergyLimitWithFixRatio` and `getTotalEnergyLimitWithFixRatio` speculatively call `EnergyProcessor.increase()` to reserve the maximum possible energy the caller/creator could consume (based on fee limit), and immediately persist this to the account store: [1](#0-0) [2](#0-1) 

At the same time, the "left" frozen energy (captured *before* this reservation) is stashed on the receipt via `setCallerEnergyLeft`/`setOriginEnergyLeft`: [3](#0-2) 

After execution, `TransactionTrace.pay()` calls `receipt.payEnergyBill()`, which uses these stale, pre-reservation "left" values (`callerEnergyLeft`/`originEnergyLeft`) to decide how much of the *actual* energy usage is covered by frozen energy versus paid in TRX, and then calls `EnergyProcessor.useEnergy()` again to record that actual usage: [4](#0-3) 

The mechanism meant to net out the earlier speculative reservation, `resetAccountUsage`/`resetAccountUsageV2`, is only invoked when the execution neither threw an exception nor reverted: [5](#0-4) 

If the runtime result has an exception or `isRevert()` is true, this reconciliation is skipped entirely, so the speculative reservation from step one remains permanently applied to the account's persisted `energyUsage`/window, on top of which `payEnergyBill` unconditionally adds the real usage a second time via `useEnergy()`.

### Impact Explanation
The account's frozen-energy allowance is effectively debited twice for the same transaction (once by the pre-execution speculative reservation, once by the post-execution real-usage charge), while the fee computation in `payEnergyBill` still relies on the stale, pre-reservation "left" snapshot. This causes the frozen energy window to be consumed faster than it should, forcing the account to pay TRX energy fees (`energyFee`) for usage that should have been covered by already-frozen resources — a direct fee-overcharge analog to the referenced liability-accounting bug. It affects any TVM-freeze-v2 (stake v2) contract call/creation that reverts or throws.

### Likelihood Explanation
Reachable by any anonymous broadcast `TriggerSmartContract`/`CreateSmartContract` transaction on a chain with `allowTvmFreezeV2` and `supportUnfreezeDelay` enabled, whenever the invoked contract reverts or throws an exception — a common, attacker-controllable condition (e.g., deliberately reverting mid-execution after the energy limit has been computed). No privileged role is required.

### Recommendation
Ensure the pre-execution speculative energy reservation performed in `getAccountEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFixRatio` is always reconciled (via `resetAccountUsage`/`resetAccountUsageV2`) regardless of whether the VM execution reverted or threw, or alternatively avoid persisting the speculative reservation to the account store until the real usage is known, so `payEnergyBill` operates on accurate, up-to-date frozen-energy availability rather than a stale pre-reservation snapshot.

### Proof of Concept
Not independently executed/tested; this analysis is based on static code review of the call sequence across `VMActuator`, `ReceiptCapsule`, and `TransactionTrace`. A concrete PoC would require constructing a stake-v2 account, triggering a smart contract call that reverts after `getTotalEnergyLimitWithFixRatio`'s reservation persists, and observing the account's `energyUsage`/`energyFee` after `payEnergyBill` to confirm double-debiting — this dynamic verification was not performed here due to lack of a runtime/test harness in this session.

  private void payEnergyBill(
      DynamicPropertiesStore dynamicPropertiesStore, AccountStore accountStore,
      ForkController forkController,
      AccountCapsule account,
      long usage,
      contractResult contractResult,
      EnergyProcessor energyProcessor,
      long now) throws BalanceInsufficientException {
    long accountEnergyLeft;
    if (dynamicPropertiesStore.getAllowTvmFreeze() == 1
        || dynamicPropertiesStore.supportUnfreezeDelay()) {
      accountEnergyLeft = callerEnergyLeft;
    } else {
      accountEnergyLeft = energyProcessor.getAccountLeftEnergyFromFreeze(account);
    }
    if (accountEnergyLeft >= usage) {
      energyProcessor.useEnergy(account, usage, now);
      this.setEnergyUsage(usage);
    } else {
      energyProcessor.useEnergy(account, accountEnergyLeft, now);

      if (forkController.pass(ForkBlockVersionEnum.VERSION_3_6_5) &&
          dynamicPropertiesStore.getAllowAdaptiveEnergy() == 1) {
        long blockEnergyUsage =
            dynamicPropertiesStore.getBlockEnergyUsage() + (usage - accountEnergyLeft);
        dynamicPropertiesStore.saveBlockEnergyUsage(blockEnergyUsage);
      }

      long sunPerEnergy = Constant.SUN_PER_ENERGY;
      long dynamicEnergyFee = dynamicPropertiesStore.getEnergyFee();
      if (dynamicEnergyFee > 0) {
        sunPerEnergy = dynamicEnergyFee;
      }
      long energyFee =
          (usage - accountEnergyLeft) * sunPerEnergy;
      this.setEnergyUsage(accountEnergyLeft);
      this.setEnergyFee(energyFee);
      long balance = account.getBalance();
      if (balance < energyFee) {
        throw new BalanceInsufficientException(
            StringUtil.createReadableString(account.createDbKey()) + " insufficient balance");
      }
      account.setBalance(balance - energyFee);

      if (dynamicPropertiesStore.supportTransactionFeePool() &&
          !contractResult.equals(contractResult.OUT_OF_TIME)) {
        dynamicPropertiesStore.addTransactionFeePool(energyFee);
      } else if (dynamicPropertiesStore.supportBlackHoleOptimization()) {
        dynamicPropertiesStore.burnTrx(energyFee);
      } else {
        //send to blackHole
        Commons.adjustBalance(accountStore, accountStore.getBlackhole(),
            energyFee, dynamicPropertiesStore.disableJavaLangMath());
      }

    }

    accountStore.put(account.getAddress().toByteArray(), account);
