### Title
Unchecked `reduceAssetAmountV2`/`addAssetAmountV2` boolean return in `ExchangeTransactionActuator`/`ExchangeInjectActuator` can allow silent balance desync - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The external report's root cause—ignoring the boolean/return-value signal of a critical state-changing token operation (`approve()`)—has a structural analog in java-tron. `AccountCapsule.reduceAssetAmountV2()` and `addAssetAmountV2()` are boolean-returning methods that report success/failure of an asset balance mutation instead of throwing, exactly like a non-standard ERC20 `approve()` returning `false` instead of reverting. `ExchangeTransactionActuator.execute()` and `ExchangeInjectActuator.execute()` call these methods and discard the returned boolean, continuing execution and persisting account/exchange state regardless of the outcome.

### Finding Description
`AccountCapsule.reduceAssetAmountV2` returns `false` (without throwing) when the account lacks sufficient asset balance: [1](#0-0) 

In `ExchangeTransactionActuator.execute()`, the returned booleans of `reduceAssetAmountV2` and `addAssetAmountV2` are never checked before the actuator commits the mutated `accountCapsule` and `exchangeCapsule` to their stores and marks the transaction `SUCESS`: [2](#0-1) 

The same unchecked pattern appears twice in `ExchangeInjectActuator.execute()`: [3](#0-2) 

By contrast, other actuators in the same package that use these same boolean-returning capsule methods explicitly check the return value and abort via `ContractExeException` on failure — showing the codebase's own established, intended pattern that these two actuators deviate from: [4](#0-3) [5](#0-4) 
`Commons.adjustAssetBalanceV2` similarly checks the return value and throws `BalanceInsufficientException` on failure: [6](#0-5) 

`ExchangeTransactionActuator.doValidate()` does perform a pre-check via `accountCapsule.assetBalanceEnoughV2(tokenID, tokenQuant, dynamicStore)` before `execute()` runs: [7](#0-6) 
This mitigates the most obvious "sell token you don't have" case for the *sold* token side, similarly to how the reported UDA bug depends on ignoring a call whose success validate()-time checks did not verify. However, `execute()` still calls `addAssetAmountV2` on the *received* token side (line 90) without checking the return value, and there is no explicit runtime assertion tying `validate()`'s balance snapshot to the balance actually present at `execute()` time (multiple transactions from the same account/exchange can be packed in the same block, altering balances between validate and execute of different transactions). This means the actuator's silent-failure path in `reduceAssetAmountV2`/`addAssetAmountV2` remains reachable and unguarded at the `execute()` layer itself, unlike the sibling actuators that assert on the return value directly in `execute()`.

### Impact Explanation
If `reduceAssetAmountV2`/`addAssetAmountV2` silently return `false` in a state that slips past `validate()` (e.g. due to a TOCTOU window across sequential transactions within the same block, or future refactors that call `execute()` without an equivalent pre-check), the actuator will still: commit the (unchanged) `AccountCapsule` to `accountStore`, commit the mutated `ExchangeCapsule` (already updated by `exchangeCapsule.transaction(...)` at line 68/params) to `exchangeStore`/`exchangeV2Store`, and mark the transaction `SUCESS`. This creates a state where the on-chain `Exchange` pool balance has been adjusted (the AMM math already executed) while the user's actual asset balance was never decremented or incremented — a direct book-keeping/asset-accounting divergence between the bonded-curve exchange pool and account ledgers, analogous to the reported "funds locked/miscredited because approval silently failed but the surrounding logic proceeded as if it succeeded."

### Likelihood Explanation
Today the risk is bounded because `validate()` calls `assetBalanceEnoughV2` immediately before `execute()` is invoked for a given transaction, so a standalone single transaction is unlikely to trigger the false-return path. The residual risk is: (1) `addAssetAmountV2`'s return value is never checked at all (only `reduceAssetAmountV2` has a matching pre-check), and (2) the actuator itself has no defensive check in `execute()`, unlike `TransferAssetActuator`/`ParticipateAssetIssueActuator`, meaning the invariant enforcing correctness lives entirely in `validate()` rather than being defense-in-depth at `execute()`. Any future code path change (e.g., internal re-invocation of `execute()`, new call sites, or accounting edge cases in `getAllowSameTokenName`/`importAsset` transitions) could reintroduce the exact silent-failure scenario the external report describes.

### Recommendation
Check the boolean return values of `reduceAssetAmountV2` and `addAssetAmountV2` inside `ExchangeTransactionActuator.execute()` and `ExchangeInjectActuator.execute()`, throwing `ContractExeException` on `false` exactly as done in `TransferAssetActuator` and `ParticipateAssetIssueActuator`, so that `execute()` does not depend solely on `validate()`'s earlier snapshot check.

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this requires constructing a same-block transaction ordering or account-state race where `validate()`'s balance snapshot diverges from the balance present at `execute()` time (e.g. two transactions from the same owner address touching the same asset/exchange in one block), which requires dynamic testing against the actual `Manager`/block-processing pipeline rather than being demonstrable purely from the actuator source. This is a structural/code-quality gap analogous to the reported issue rather than a confirmed exploited state divergence in the current single-transaction `validate → execute` flow.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }

  public static void adjustAssetBalanceV2(AccountCapsule account, String AssetID, long amount,
      AccountStore accountStore, AssetIssueStore assetIssueStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws BalanceInsufficientException {
    if (amount < 0) {
      if (!account.reduceAssetAmountV2(AssetID.getBytes(), -amount, dynamicPropertiesStore,
          assetIssueStore)) {
        throw new BalanceInsufficientException(
            String.format("reduceAssetAmount failed! account: %s",
                    StringUtil.encode58Check(account.createDbKey())));
      }
    } else if (amount > 0 &&
        !account.addAssetAmountV2(AssetID.getBytes(), amount, dynamicPropertiesStore,
            assetIssueStore)) {
      throw new BalanceInsufficientException(
          String.format("addAssetAmount failed! account: %s",
                  StringUtil.encode58Check(account.createDbKey())));
    }
    accountStore.put(account.getAddress().toByteArray(), account);
