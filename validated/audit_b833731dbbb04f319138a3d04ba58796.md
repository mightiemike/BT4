## Title
Missing reentrancy/concurrency guard around token-exchange session minting allows duplicate token exchanges and session-storage races - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts`)

### Summary
The Sherlock finding flags a classic TOCTOU/reentrancy bug: a state-changing operation (mint/deposit) is protected by a check performed *before* an asynchronous external call, but nothing prevents a second concurrent call from re-entering and repeating the state change before the first completes. The `TokenExchangeStrategy.authenticate` method (and its siblings in `shopify-app-express` and `shopify-app-react-router`) has the same structural flaw: it checks whether a valid session exists, and if not, performs an asynchronous token exchange with Shopify and writes the result to session storage — with no lock/guard preventing two concurrent requests carrying the same session token from both passing the check and both executing the exchange + write.

### Finding Description
In `authenticate()`, the guard is a simple, non-atomic check-then-act sequence: [1](#0-0) 

If `!session || !session.isActive(...)`, it proceeds to call `this.exchangeToken(...)` (an outbound HTTP call to Shopify) and then `config.sessionStorage!.storeSession(offlineSession)`: [2](#0-1) 

There is no per-shop/per-session-token mutex around this block. The only concurrency protection in the codebase, `IdempotentPromiseHandler`, is applied *exclusively* to the `afterAuth` hook invocation, not to the `exchangeToken`/`storeSession` sequence itself: [3](#0-2) 

The identical pattern exists in the Express and React Router packages: [4](#0-3) [5](#0-4) 

The `IdempotentPromiseHandler` itself only dedupes by identifier for a single promise call it wraps, and does not span the load-check-exchange-store sequence: [6](#0-5) 

Because this flow is triggered by an unauthenticated frontend session-token check that any embedded app page load can fire multiple times in parallel (e.g., concurrent `fetch` calls from App Bridge before a session is minted), an attacker or even normal race conditions can cause:
- Multiple simultaneous `api.auth.tokenExchange` calls to Shopify for the same shop/session-token, each requesting a fresh offline (and optionally online) access token.
- Concurrent, unsynchronized `storeSession` writes to the configured `SessionStorage` (e.g., Prisma/MySQL/SQLite/memory adapters), where the last write wins and earlier issued tokens can be silently dropped/overwritten, or duplicate rows/log noise get produced depending on the adapter's upsert semantics.

### Impact Explanation
This is a state-corruption / resource-exhaustion class issue analogous to the reentrancy report: an operation meant to run once per shop can be re-entered concurrently, causing duplicate external calls (extra load on Shopify's OAuth token endpoint, which could throttle the app) and non-deterministic overwrites of the stored session/access token. In the worst case, a session established by one request can get clobbered by a slower, redundant exchange from a concurrent request, potentially leaving the app tracking a token that was already invalidated server-side race-wise, or triggering repeated `afterAuth` side effects if the token differs. This is reachable by a single merchant's browser session and does not require privileged access.

### Likelihood Explanation
Likelihood is moderate: it requires two or more concurrent requests bearing the same (or a still-valid) session token to hit `authenticate()` before the first request's `storeSession` completes. This is plausible in normal embedded-app usage where App Bridge can fire multiple parallel fetches on page load, and is trivially reproducible by an attacker or automated client issuing parallel requests during the brief window before a fresh offline session exists in storage.

### Recommendation
Wrap the check-then-exchange-then-store sequence (not just the `afterAuth` hook) in a per-shop (or per-session-token) mutex/lock — for example, extend `IdempotentPromiseHandler` (or a similar keyed lock) to cover the entire block from the `loadSession`/`isActive` check through `storeSession`, so that concurrent requests for the same shop either wait for the in-flight exchange to complete and reuse its result, or are rejected/retried rather than independently re-executing the token exchange and overwriting the stored session.

### Proof of Concept
1. An embedded app renders and its frontend fires two parallel authenticated `fetch` requests before any offline session is stored for the shop (both carrying a valid, not-yet-consumed session token).
2. Both requests hit `TokenExchangeStrategy.authenticate()` (or the Express/React Router equivalents) nearly simultaneously; `config.sessionStorage.loadSession` returns `undefined`/inactive for both, since neither has stored a session yet. [7](#0-6) 
3. Both requests independently call `api.auth.tokenExchange(...)` for `RequestedTokenType.OfflineAccessToken`, and both call `config.sessionStorage!.storeSession(offlineSession)` with their own returned tokens. [8](#0-7) 
4. Depending on which write lands last, the app ends up storing whichever token was returned later, silently discarding the other — with no synchronization to prevent or reconcile the duplicate exchange calls.

export class IdempotentPromiseHandler {
  protected identifiers: Map<string, number>;

  constructor() {
    this.identifiers = new Map<string, number>();
  }

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
