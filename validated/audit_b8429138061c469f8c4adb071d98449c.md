### Title
Incorrect `nextMaintenanceTime` scheduling when `MAINTENANCE_TIME_INTERVAL` changes across a multi-round gap - (File: `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java`)

### Summary
`DynamicPropertiesStore.updateNextMaintenanceTime(long blockTime)` recomputes the next maintenance/epoch boundary using a single, currently-effective `maintenanceTimeInterval` value multiplied across however many intervals have elapsed (`round`). If the interval was changed by an approved `MAINTENANCE_TIME_INTERVAL` proposal for the very same maintenance cycle, the new interval is retroactively applied to the entire elapsed span rather than to only the portion after the change — the same root cause pattern as the reported Maple `WithdrawalManager` bug, where the new `cycleDuration` was multiplied by the number of cycles instead of summing the actual durations that applied to cycles `[currentCycleId, currentCycleId+1, currentCycleId+2]`.

### Finding Description
`updateNextMaintenanceTime` computes:
```java
long maintenanceTimeInterval = getMaintenanceTimeInterval();
long currentMaintenanceTime = getNextMaintenanceTime();
long round = (blockTime - currentMaintenanceTime) / maintenanceTimeInterval;
long nextMaintenanceTime = currentMaintenanceTime + (round + 1) * maintenanceTimeInterval;
saveNextMaintenanceTime(nextMaintenanceTime);
``` [1](#0-0) 

`maintenanceTimeInterval` is a governance-adjustable chain parameter. Witnesses can change it via a normal proposal (`MAINTENANCE_TIME_INTERVAL` case), and once approved it is saved immediately by `ProposalService.process`:
```java
case MAINTENANCE_TIME_INTERVAL: {
  manager.getDynamicPropertiesStore().saveMaintenanceTimeInterval(entry.getValue());
  break;
}
``` [2](#0-1) 

This is analogous to Maple's `config[1]` — a "pending" duration change that becomes active for the current cycle boundary. In `updateNextMaintenanceTime`, if `round > 0` (this happens whenever the node has not produced a maintenance-triggering block for more than one full interval — e.g. after a restart, a long block-production gap, or if the interval was just shrunk), the *entire* multi-interval gap `(round+1) * maintenanceTimeInterval` is computed using only the new interval value, exactly like the Maple bug's `initialCycleTime = now + 3 * cycleDuration_new` instead of summing the actual per-cycle durations `1 day + 7 days + 7 days`. The correct approach — as recommended in the analog report — would be to walk/sum the durations that were actually in effect for each elapsed sub-period rather than assuming a single constant duration for the whole span.

The call site is `MaintenanceManager.applyBlock`, which calls `doMaintenance()` (which is where proposal processing/parameter changes such as `MAINTENANCE_TIME_INTERVAL` take effect for the cycle) and only afterward calls `consensusDelegate.updateNextMaintenanceTime(blockTime)`:
```java
if (blockNum != 1) {
  updateWitnessValue(beforeWitness);
  beforeMaintenanceTime = nextMaintenanceTime;
  doMaintenance();
  updateWitnessValue(currentWitness);
}
consensusDelegate.updateNextMaintenanceTime(blockTime);
``` [3](#0-2) 

This ordering means a freshly-approved `MAINTENANCE_TIME_INTERVAL` change is guaranteed to be the value used by `updateNextMaintenanceTime` for the very same block/cycle boundary in which it was approved, reproducing the "queuing several config updates" scenario from the report.

### Impact Explanation
Because every full node executes the same deterministic sequence (`doMaintenance()` then `updateNextMaintenanceTime()`), this does not directly cause a consensus fork by itself — all nodes compute the same (wrong) value. The impact is functional/scheduling corruption of the epoch boundary: after a `MAINTENANCE_TIME_INTERVAL` proposal takes effect while the node is more than one interval behind (`round > 0`), the next maintenance time can be pushed much further into the future or brought much closer than intended, since the new interval is multiplied across a span that was actually governed by the old interval for part of its duration. This can distort witness reward/epoch cadence, delay proposal expiration handling, and skew cycle-dependent reward accounting (e.g., `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`, `currentCycleNumber` bookkeeping in `MaintenanceManager.doMaintenance`), i.e., a resource/reward-accounting correctness issue analogous in class (not consensus-fork severity) to the original Medium-severity Maple finding.

### Likelihood Explanation
Triggering requires (a) a governance proposal changing `MAINTENANCE_TIME_INTERVAL` to be approved, and (b) the node/network to be more than one maintenance interval behind at the moment the change takes effect (`round > 0`), which realistically occurs after node downtime, chain halts, or if the interval is shortened. This is a plausible operational scenario rather than a contrived one, but it is less frequent than the Maple scenario (which triggers on every scheduling call once a pending config exists), so likelihood is Low-to-Medium.

### Recommendation
Change `updateNextMaintenanceTime` to iterate/sum the historical `maintenanceTimeInterval` values that were in effect for each elapsed sub-period between `currentMaintenanceTime` and `blockTime`, rather than multiplying a single (possibly just-updated) interval by `round + 1`. Alternatively, keep a history of interval changes with their effective times (similar to how `saveEnergyPriceHistory`/`saveBandwidthPriceHistory` already track historical parameter values with effective timestamps) and use that history to compute the correct next maintenance boundary.

### Proof of Concept
1. Let `nextMaintenanceTime` (in store) = `T0`, `maintenanceTimeInterval` = `I_old` (e.g., 1 day).
2. Suppose the node falls behind such that `blockTime = T0 + 3*I_old` (3 intervals have effectively elapsed under the old interval).
3. Before this block is applied, a `MAINTENANCE_TIME_INTERVAL` proposal is approved during `doMaintenance()`, changing the interval to `I_new` (e.g., 7 days), via `ProposalService.process` [2](#0-1) .
4. `updateNextMaintenanceTime(blockTime)` is then called with the now-updated `I_new`: `round = (blockTime - T0) / I_new`, and `nextMaintenanceTime = T0 + (round+1) * I_new` [1](#0-0) .
5. The correct boundary should have summed `I_old` for the periods already elapsed under the old interval and only used `I_new` going forward, exactly mirroring the Maple report's `1 day + 7 days + 7 days` vs. `3 * 1 day` discrepancy — instead the store computes a boundary based solely on `I_new`, producing an incorrect epoch/maintenance schedule.
