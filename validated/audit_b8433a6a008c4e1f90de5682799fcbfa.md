### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant session/access-token reuse via HMAC replay - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
The bypass in the GitLab report worked because the fix validated one artifact (the URL/path via YAML schema) while a *related but separate* input (the CI variable value) that fed into the same sink was left unvalidated, letting the attacker substitute a malicious value that the validation never inspected. The same structural pattern exists in `shopify-app-js`'s webhook verification: `validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` only computes and checks the HMAC over `rawBody` [1](#0-0) , but the `X-Shopify-Shop-Domain` header — which is *not* included in the signed payload — is later trusted as the tenant identifier used to look up and attach a live offline access token to the request.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` verifies the HMAC (computed only from `rawBody`) and then separately extracts headers (including `domain`) via `checkWebhookHeaders`, returning them as trusted fields once the body-only HMAC passes [2](#0-1) . The `WebhookFields` type confirms `domain` is a plain header-derived string, structurally identical to but independent of the signed `hmac` field [3](#0-2) .

Downstream, both the Remix and React Router webhook authenticate helpers take `check.domain` directly (an unsigned header value) and use it to fetch the shop's stored offline session/access token: [4](#0-3) 
This ultimately calls `getOfflineId(shop)` (`offline_${shop}`) and loads the corresponding session from session storage [5](#0-4) , and that session (with its real access token) is then attached to an authenticated `admin` GraphQL/REST client made available to the app's webhook handler [6](#0-5) .

Because the HMAC never covers the `domain` header, an attacker who can obtain **any** valid `(rawBody, hmac)` pair for the shared app secret — trivially possible by installing the app on their own store and triggering a real webhook whose body they control the content of (e.g. product/order fields) — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (or `shopify-shop-domain` for events-type webhooks) with a victim shop's domain. The validator will report `valid: true` and `domain: <victim-shop>`, causing the framework to fetch the victim's stored offline access token and hand it, together with attacker-crafted payload content, to the app's webhook business logic — a cross-tenant impersonation using the victim's own access token.

### Impact Explanation
This allows an unprivileged attacker (any merchant able to install the target app on their own store, which is the normal unprivileged path for a public app) to make the app's webhook handler execute business logic against a **different** installed shop's data/session, using an attacker-influenced payload body, effectively impersonating events "from" the victim shop and reusing the victim's live offline access token inside the app. Depending on what the webhook handler does (creating orders, issuing refunds, mutating data, calling other APIs on the victim's behalf), this can lead to unauthorized cross-tenant actions, data leakage, or corruption — comparable in severity to the original cache-poisoning bypass, since both stem from validating a payload while leaving an adjacent identifier field that drives a sensitive lookup unauthenticated.

### Likelihood Explanation
Likelihood is bounded by two factors I could not fully verify from the indexed code: (1) whether the app's HTTP layer or hosting infra (e.g., reverse proxy IP allowlisting to Shopify's ranges) restricts webhook POSTs to originate only from Shopify's infrastructure — if enforced, this significantly reduces exploitability; (2) how much content of the signed body an attacker can actually control via their own store's real events (webhook bodies are Shopify-generated JSON reflecting real resource state, not free-form attacker text, though resource titles/notes/metafields are attacker-editable). No IP/origin restriction logic was found in the reviewed webhook validation/authenticate code paths, so this should be treated as reachable from an anonymous/self-service unprivileged actor unless mitigated at the infrastructure layer outside this library.

### Recommendation
- Do not treat header-derived `domain` (or `topic`) as authenticated identity data purely because a body-only HMAC passed. If feasible, bind the shop identity to the OAuth/App-installation-issued access token used to complete the webhook subscription, or verify that the resolved session's shop matches an app-side record correlated to the specific webhook subscription (not solely a client-supplied header).
- Where possible, incorporate the shop domain into the HMAC-covered material for webhook types where this library controls verification, or perform a secondary authenticity check binding `domain` to the specific webhook subscription/registration record rather than trusting the raw header value directly for session/token lookup.
- Document and, ideally, enforce origin verification against Shopify's known webhook source IPs at the framework level as defense in depth.

### Proof of Concept
1. Attacker installs the target app on their own controlled store `attacker.myshopify.com`.
2. Attacker triggers a real event (e.g., creates a product with an attacker-chosen title/description) so Shopify sends a legitimate webhook to the app's callback URL with `rawBody = B` and header `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`.
3. Attacker captures `(B, HMAC(secret,B))` from this legitimate delivery (e.g., via their own logging/proxy, since it's their own store's webhook).
4. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `validateHmacFromRequestFactory` recomputes HMAC over `B` only, finds it matches, and returns `valid: true` [7](#0-6) .
6. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` with `check.domain = 'victim-shop.myshopify.com'`, loading the victim's real offline session/access token and passing it to the webhook handler with the attacker-supplied payload `B` [8](#0-7) .

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

import {AppDistribution, BasicParams} from '../types';

export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
}
