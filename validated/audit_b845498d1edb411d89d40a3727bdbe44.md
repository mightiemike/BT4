### Title
Bouncer's Patricia-update resource weighting omits stateful-compression alias writes, letting a transaction under-price its true proving cost - ([File: crates/blockifier/src/bouncer.rs])

### Summary
The bouncer's per-transaction resource accounting (`get_tx_weights` → `get_patricia_update_resources`) computes `sierra_gas`/`proving_gas` and `state_diff_size` from `n_visited_storage_entries` and `state_changes_keys.storage_keys.len()` only. It explicitly does **not** count the additional Patricia-tree/global-alias-contract writes that the OS performs for every newly-touched storage key ≥ `MIN_VALUE_FOR_ALIAS_ALLOC` when stateful compression is enabled, as flagged by the code's own TODO. This mirrors the NFTX `getRandomTokenIdFromFund` bug class: a resource/weight computation that ignores a "quantity" factor (there: `quantity1155`; here: number of aliases allocated per transaction), causing the accounted weight to diverge from the real cost and making it easy for an attacker to submit transactions that are systematically under-priced relative to their true block-building cost.

### Finding Description
`get_tx_weights` builds the `patricia_update_resources` solely from `n_visited_storage_entries` and `state_changes_keys.storage_keys.len()`: [1](#0-0) 

The comment directly above this call states the gap: [2](#0-1) 
"`// TODO(Yoni): consider counting here the global contract tree and the aliases as well.`"

However, when stateful compression is enabled (`enable_stateful_compression`), every new storage key/contract address whose numeric value is ≥ `MIN_VALUE_FOR_ALIAS_ALLOC` triggers an *additional* Patricia-tree write into the dedicated alias contract, performed by `allocate_aliases_in_storage`/`AliasUpdater`: [3](#0-2) [4](#0-3) 

Each alias allocation is a genuine, additional storage write with real Patricia-tree update cost and CASM/builtin execution cost inside the Starknet OS re-execution (see the Cairo implementation in `aliases.cairo`, e.g. `allocate_aliases_for_storage_diff_big_keys`/`maybe_allocate_alias_for_key`), yet this cost is never fed back into `n_visited_storage_entries` or `state_changes_keys` used by `get_tx_weights`/`get_patricia_update_resources`. The number of aliases allocated is a linear function of the number of *distinct large-valued* storage keys/addresses touched by a transaction — i.e., a "quantity" that the bouncer's weight formula does not scale with, exactly as `getRandomTokenIdFromFund` ignored `quantity1155` when computing probability.

### Impact Explanation
Because `sierra_gas`/`proving_gas`/`state_diff_size` (the values the bouncer uses to decide whether a transaction fits in the remaining block capacity, and that feed the fee/resource-bound checks) undercount the true Patricia/alias-write cost, an attacker can craft a transaction that touches many distinct high-valued storage keys (each triggering a fresh alias allocation) while being charged/weighted as if only the "visited storage entries" and "storage key" counts mattered. This can push actual OS/committer proving work and state-diff growth beyond what the bouncer's `BouncerConfig.block_max_capacity` accounted for, risking blocks that exceed the intended proving/resource budget (denial of block-building capacity, or state-diff bloat beyond `state_diff_size` limits) without being rejected by `Bouncer::try_update`/`verify_tx_weights_within_max_capacity`. This is a resource-accounting/fee-accounting correctness bug reachable purely from a single submitted transaction's storage writes, analogous to the "unfair distribution" root cause in the referenced report (a per-unit quantity omitted from a resource/probability formula).

### Likelihood Explanation
Likelihood is moderate: it requires stateful compression to be active for the transaction's storage keys (keys/addresses ≥ `MIN_VALUE_FOR_ALIAS_ALLOC`), and an attacker to specifically maximize the number of distinct qualifying keys touched (e.g., writing 1 non-zero value to many different high-numbered storage slots) to maximize the alias/Patricia-write discrepancy relative to declared weight. No special privileges are needed — any account transaction sender can shape their own calldata/storage writes.

### Recommendation
Extend `get_tx_weights`/`get_patricia_update_resources` in `crates/blockifier/src/bouncer.rs` to include the number of alias allocations (new + existing lookups in the alias contract) triggered by the transaction's storage/contract-address diff when `enable_stateful_compression` is on, resolving the TODO comment at line 933. This additional count should be added to both the `sierra_gas`/`proving_gas` computation inputs and to `state_diff_size`/`state_changes_keys.count()` so that the bouncer's accepted weights reflect the true number of Patricia-tree/global-alias-contract writes performed during block building and OS re-execution.

### Proof of Concept
1. Enable `enable_stateful_compression` (standard for current mainnet versions per `blockifier_versioned_constants.rs`).
2. Submit an `Invoke` transaction whose contract writes non-zero values into N distinct new storage keys, each with a numeric value ≥ `MIN_VALUE_FOR_ALIAS_ALLOC` (`0x80`), e.g., keys `0x80, 0x81, ..., 0x80+N-1`.
3. Observe that `get_tx_weights` computes `patricia_update_resources` from `get_patricia_update_resources(n_visited_storage_entries, state_changes_keys.storage_keys.len())` — see: [1](#0-0) 
   which does not add the N additional alias-contract writes that `allocate_aliases_in_storage` will perform during block finalization/OS execution: [5](#0-4) 
4. Repeating this with many transactions in a block accumulates N-proportional uncounted Patricia/alias-write cost per transaction across `Bouncer::try_update`'s accumulated weights, letting the block's real proving/state-diff cost exceed what `BouncerConfig.block_max_capacity` was designed to bound, without triggering `TransactionExecutorError::BlockFull`/`TransactionTooLarge`.

/// Allocates aliases for the new addresses and storage keys in the alias contract.
/// Iterates over the addresses in ascending order. For each address, sets an alias for the new
/// storage keys (in ascending order) and for the address itself.
pub fn allocate_aliases_in_storage<S: StateReader>(
    state: &mut CachedState<S>,
    alias_contract_address: ContractAddress,
) -> StateResult<()> {
    let state_diff = state.to_state_diff()?.state_maps;

    // Collect the contract addresses and the storage keys that need aliases.
    let contract_addresses: BTreeSet<ContractAddress> =
        state_diff.get_contract_addresses().into_iter().collect();
    let mut contract_address_to_sorted_storage_keys = HashMap::new();
    for (contract_address, storage_key) in state_diff.storage.keys() {
        if contract_address > &MAX_NON_COMPRESSED_CONTRACT_ADDRESS {
            contract_address_to_sorted_storage_keys
                .entry(contract_address)
                .or_insert_with(BTreeSet::new)
                .insert(storage_key);
        }
    }

    // Iterate over the addresses and the storage keys and update the aliases.
    let mut alias_updater = AliasUpdater::new(state, alias_contract_address)?;
    for contract_address in contract_addresses {
        if let Some(storage_keys) = contract_address_to_sorted_storage_keys.get(&contract_address) {
            for key in storage_keys {
                alias_updater.insert_alias(key)?;
            }
        }
        alias_updater.insert_alias(&StorageKey(contract_address.0))?;
    }

    alias_updater.finalize_updates()
