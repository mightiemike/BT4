**Analysis:**

The scenario describes `StateSlot::HotVacant` refresh behavior in `passes_jmt_filter`/`maybe_update_cold_state`: [1](#0-0) 

For `HotVacant`, the filter checks `hot_since_version >= min_version` and, if true, emits `Some(None)` (a delete/no-op) into the cold JMT update set — even when only the `hot_since_version` was refreshed by a read-triggered promotion (via `StateSlot::refresh`), not the value itself. This is explicitly acknowledged and accepted in the source comment: [2](#0-1) 

This does not constitute a valid state-integrity vulnerability for two independent reasons:

1. **Deterministic, not unprivileged-input-exploitable divergence**: `hot_since_version` refreshes are part of the canonical deterministic state-transition function (`State::apply_one_update`, `HotStateLRU`) that every conforming validator/full node executes identically over the same transaction sequence. [3](#0-2)  There is no path for an unprivileged actor to make only *some* validators compute the refresh while others don't — all nodes run the identical reference logic, so no accumulator-root divergence occurs across the honest network.

2. **The extra delete is a mathematical no-op on the JMT root**: `merklize_snapshot`/`batch_update_subtree` treats a deletion (`None` value) as producing no node for that key's subtree position regardless of whether the key was previously present. [4](#0-3)  Deleting an already-absent key yields the identical root hash as omitting the entry entirely (confirmed by `test_insert_to_empty_tree`, which shows delete-to-empty returns to `SPARSE_MERKLE_PLACEHOLDER_HASH`). [5](#0-4)  Consequently, even a hypothetical alternate implementation that "skips" this LRU-only-refresh delete would compute the same root hash as the reference implementation — there is no divergence to exploit.

The premise also implicitly depends on a "divergent-optimizing validator implementation" that deviates from the reviewed reference code — such a variant is out of scope per the review rules (the review covers the actual production implementation, not hypothetical non-conforming alternates), and any divergence from a buggy alternate client is a bug in that client, not a corruption of committed state caused by unprivileged input against the canonical implementation.
