### Title
`ValidateMultiSign` precompile signature scheme lacks chain-id and verifying-contract domain separation, enabling cross-chain and cross-contract signature replay - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x0a`) is TRON's on-chain building block for smart contracts to verify that a set of off-chain-collected signatures meets an account's permission threshold. The message it hashes and verifies against is built purely from `address || permissionId || data`, with no chain identifier and no binding to the calling (verifying) smart contract's address. Any signature a permission key holder produces to authorize an action for one dApp/contract can be replayed verbatim by anyone to satisfy the identical check in a different contract on the same TRON-compatible network, or on any other chain/fork sharing the same account address and permission configuration — the same signature replay class described in the referenced RabbitHole `QuestFactory.mintReceipt` finding.

### Finding Description
`ValidateMultiSign.execute` builds the signed message as: [1](#0-0) 

```
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
```

It then recovers each supplied signature's signer against this `hash` and sums permission weights: [2](#0-1) 

The three components that make up the signed payload — `address` (the TRON account being checked), `permissionId`, and caller-supplied `data` — say nothing about:
1. **Which chain** the verification is happening on (no `chainid`-equivalent). TRON runs multiple networks (Mainnet, Nile, Shasta) plus arbitrary private/forked chains that can all recognize the same account address and permission structure.
2. **Which contract is calling the precompile** (no verifying-contract address, unlike EIP-712's `verifyingContract` domain field). Multiple independently-deployed dApp contracts (e.g. multiple instances of the same factory-style contract, or a legitimate contract and a malicious clone) can all invoke `ValidateMultiSign` with the same `(address, permissionId, data)` tuple and accept the exact same signatures as valid authorization.

This mirrors the original report's root cause precisely: the signed message omits deadline/chain/verifying-contract binding, so a signature intended for one purpose/venue is fungible across other venues that happen to reconstruct the same tuple. `BatchValidateSign` (same file) is even more permissive — it hashes nothing itself and verifies caller-supplied raw hashes directly — but that is fully delegated to the caller by design; `ValidateMultiSign`, in contrast, is the protocol-defined "authoritative" scheme smart contracts are meant to rely on for permission-weighted signature checks, making its lack of domain separation the more direct protocol-level analog.

Contrast this with genuine TRON transaction signing, where the signed hash is `Sha256Hash.hash(rawData)` over the entire `Transaction.raw` (including `ref_block_hash`, `expiration`, and full contract parameters), which naturally scopes each signature to one specific transaction: [3](#0-2) 

No such natural scoping exists for `ValidateMultiSign`, since `data` is opaque, caller-chosen bytes that a dApp author must independently choose to bind to a domain — and the platform itself provides no protocol-level primitive (like a chain id or precompile-injected caller address) to do so.

### Impact Explanation
Any smart contract that uses `ValidateMultiSign` as its authorization mechanism for privileged operations (e.g., approving withdrawals, mint/claim actions, or governance operations gated by an account's on-chain multi-sig permission) is exposed to signature replay:
- Signatures collected off-chain to authorize an action in one deployed contract instance can be resubmitted to a different deployed instance of the same contract (e.g. a redeploy, a fork, or a maliciously cloned contract) that also calls `ValidateMultiSign` with the same address/permissionId/data, since the precompile itself has no way to distinguish the intended caller.
- Signatures produced for one TRON-compatible network can be replayed on another network (mainnet vs. testnet vs. any chain that recognizes the same address/permission), since no chain id enters the hash.

Exploitation results in unauthorized account operations being accepted as validly signed, which can lead to asset/accounting corruption in any contract relying on this precompile for access control.

### Likelihood Explanation
Exploitability requires that an application built on `ValidateMultiSign` reuses the same `data` value (or a value that legitimately recurs, e.g. a hash of static parameters) across multiple contract deployments or networks, and that an attacker can obtain such a signature and resubmit it elsewhere. This is analogous to the original finding's own judged severity (Medium): the replay is real and reachable by any unprivileged caller through ordinary contract calls, but it depends on application-level reuse patterns (same signer/permission/data tuple appearing in more than one venue) rather than being unconditionally exploitable against any single contract instance.

### Recommendation
Incorporate chain-domain separation into the `ValidateMultiSign` combine/hash construction, e.g. include the chain id and the calling contract's address (`msg.sender`/`CALLER` as seen by the precompile) in `combine`, and document that callers should also include a nonce/deadline in `data` for freshness — following an EIP-712-style domain separator pattern — so signatures are cryptographically bound to (chain, verifying contract, account, permission, data) rather than being replayable across arbitrary venues that reconstruct the same tuple.

### Proof of Concept
1. Deploy `ContractA` that calls `ValidateMultiSign(accountAddr, permissionId, dataHash, sigs)` to gate a privileged action (e.g. releasing funds) keyed on `dataHash` = `sha256(actionParams)`.
2. Off-chain, the permission-holder(s) sign the resulting `combine = address || permissionId || dataHash` message and submit it to `ContractA`, authorizing the action; `ContractA` accepts it.
3. Deploy `ContractB` — a different, independently deployed contract (or the same contract redeployed, or deployed on a different TRON-compatible chain/fork) that performs an unrelated privileged action but happens to also invoke `ValidateMultiSign` with the identical `(accountAddr, permissionId, dataHash)` (e.g. because `dataHash` is derived from parameters that legitimately recur, such as a fixed action id).
4. Submit the same previously observed `sigs` to `ContractB`. Because `ValidateMultiSign`'s hash construction only depends on `(address, permissionId, data)` with no chain id or caller/contract binding, `ContractB` recovers the same signer addresses and accepts the signatures as valid, authorizing the unrelated action without the signer's intent.
