### Title
Unbounded TRC10 asset map iteration in `MUtil.transferAllToken` allows CPU-exhaustion DoS via `triggerconstantcontract` - (File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java)

### Summary
`MUtil.transferAllToken` iterates over the entire `assetMapV2` of a contract account with no upper bound and no per-entry cost, and is invoked unconditionally from `SELFDESTRUCT`/`SELFDESTRUCT2` handling in `Program.suicide`/`Program.suicide2`. Because constant calls (`wallet/triggerconstantcontract`) run with a fixed local energy budget and never broadcast a real fee-paying transaction, an attacker can build a contract holding thousands of distinct TRC10 balances and repeatedly trigger its self-destruct via constant calls to force expensive, unmetered CPU work on RPC nodes.

### Finding Description
`MUtil.transferAllToken` does a plain `Map.forEach` over `fromAccountCap.getAssetMapV2()` with no size limit or per-iteration accounting: [1](#0-0) 

This is reached from the `SELFDESTRUCT` opcode path in `Program.suicide` and `Program.suicide2`, both of which call `MUtil.transferAllToken` unconditionally once `VMConfig.allowTvmTransferTrc10()` is enabled (a mainnet-default feature): [2](#0-1) [3](#0-2) 

`suicideAction`/`suicideAction2` in `OperationActions.java` dispatch to these methods as a single opcode step: [4](#0-3) 

The SUICIDE opcode's energy cost model (standard TVM/EVM cost calculation invoked as `op.getEnergyCost(program)` in `VM.play`) is fixed per opcode and does not scale with the size of `assetMapV2`; the loop inside `MUtil.transferAllToken` executes to completion within a single, uninterruptible opcode step with no CPU-time checks inside the loop (unlike `MUtil.checkCPUTime()` guards used elsewhere for specific costly ops such as 0x0a, create2, modExp).

For constant calls, `VMActuator` sets a fixed, high local energy limit (`maxEnergyLimitForConstant`, default clamped to at least 3,000,000, configurable independently of chain fee economics) instead of deriving it from actual account resources: [5](#0-4) [6](#0-5) [7](#0-6) 

The reachable public entry point is `wallet/triggerconstantcontract`, served by `TriggerConstantContractServlet.doPost`, which calls `Wallet.triggerConstantContract` → `Wallet.callConstantContract` → `VMActuator` with `isConstantCall=true`, and never broadcasts a transaction or charges the caller's account balance/bandwidth for execution beyond the request itself: [8](#0-7) [9](#0-8) 

Because a constant call executes and then discards state (no `rootRepository.commit()` for the delete-account/asset-map mutation on the constant-call path in `VMActuator.execute`), the attacker can trigger the same expensive `SELFDESTRUCT` repeatedly on the same pre-built contract state without any economic cost or persistent side effects, and the only defense is the generic `RateLimiterServlet` rate limiting, which throttles request *rate* but does not bound the *cost* of an individual request.

### Impact Explanation
This is a DoS via RPC-API: an unauthenticated/unprivileged caller can force RPC-serving nodes to spend disproportionate CPU time per request by exploiting an unbounded O(N) loop over attacker-controlled state, with N unmetered by the opcode's fixed energy cost. Repeated invocation degrades RPC-handler responsiveness/availability for that node (and potentially the wider fleet if load-balanced), matching the "DoS via RPC-API" bounty class. It does not achieve state corruption, fund theft, or consensus divergence, since constant calls are non-broadcast and non-committing.

### Likelihood Explanation
Preconditions: the attacker needs a contract address holding a large number of distinct TRC10 balances in `assetMapV2`. Building this can be done cheaply by sending small transfers of many *already-issued* TRC10 token IDs (using ordinary, cheap `TransferAssetContract` transactions) to the attacker's own contract, rather than issuing new tokens (which would cost the asset-issue fee per token). Given that historically many thousands of TRC10 tokens exist on TRON mainnet, accumulating thousands of distinct entries is feasible at low cost. Once built, triggering the DoS costs nothing per call beyond the constant-call rate limit, and is fully repeatable since constant calls don't commit state (the account keeps its assets after each destructive test call). This makes the attack cheap and repeatable, though bounded by the API-level rate limiter and by however many distinct TRC10 token IDs the attacker can practically accumulate balances of.

### Recommendation
- Cap the number of TRC10 asset entries a single account may hold, or cap how many entries `MUtil.transferAllToken` will process per call, rejecting/reverting (or charging proportional energy) beyond the cap.
- Charge energy proportional to `assetMapV2.size()` inside `Program.suicide`/`suicide2` before invoking `MUtil.transferAllToken`, similar to how storage-touching opcodes charge per-slot energy.
- Add a CPU-time/iteration check inside the `forEach` loop (akin to `MUtil.checkCPUTime()`), so a single opcode step can be aborted if it runs long, rather than relying solely on inter-opcode checks.
- For constant calls specifically, ensure the CPU-time budget check point in `VMActuator`/`VM.play` cannot be bypassed by a single unbounded native loop within one opcode.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }

  public static void suicideAction(Program program) {
    if (program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }

    if (!program.canSuicide()) {
      program.getResult().setRevert();
    } else {
      DataWord address = program.stackPop();
      program.suicide(address);
    }

    program.stop();
  }

  public Transaction callConstantContract(TransactionCapsule trxCap,
      Builder builder, Return.Builder retBuilder, boolean isEstimating)
      throws ContractValidateException, ContractExeException, HeaderNotFound, VMIllegalException {

    if (!Args.getInstance().isSupportConstant()) {
      throw new ContractValidateException("this node does not support constant");
    }

    Block headBlock;
    List<BlockCapsule> blockCapsuleList = chainBaseManager.getBlockStore()
        .getBlockByLatestNum(1);
    if (CollectionUtils.isEmpty(blockCapsuleList)) {
      throw new HeaderNotFound("latest block not found");
    } else {
      headBlock = blockCapsuleList.get(0).getInstance();
    }

    BlockCapsule headBlockCapsule = new BlockCapsule(headBlock);
    TransactionContext context = new TransactionContext(headBlockCapsule, trxCap,
        StoreFactory.getInstance(), true, false);
    VMActuator vmActuator = new VMActuator(true);

    try {
      vmActuator.validate(context);
      vmActuator.execute(context);
    } finally {
      // constant call runs on a pooled RPC worker; drop its thread-local VM config view so it
      // can never leak into a later (block/broadcast) execution on the same thread.
      VMConfig.clearLocalSnapshot();
    }
