## Analysis: Missing Caller Refund in Multi-Step Wallet Contract Callbacks

The reported "Safe ERC20 / unchecked external call return handling" bug class maps to a genuine, concrete issue in the NEAR Wallet Contract's cross-contract call handling for emulated Ethereum transactions.

### Title
Caller deposit is silently forfeited (not refunded) when the intermediate cross-contract call fails in `address_check_callback` or `nep_141_storage_balance_callback` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's `rlp_execute` entry point tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the emulated transaction ultimately fails [1](#0-0) . This refund is correctly implemented in the terminal callback `rlp_execute_callback`, which refunds `caller_deposit` whenever the final cross-contract promise fails [2](#0-1) . However, the two intermediate multi-step callbacks — `address_check_callback` (used for base-token transfers to unregistered eth-implicit accounts) and `nep_141_storage_balance_callback` (used for emulated ERC-20 transfers) — receive the same `caller_deposit` parameter but simply return an error response without issuing any refund when their own intermediate promise fails or returns unparseable data.

### Finding Description
In `address_check_callback`, when the call to the address registrar contract fails or returns malformed data, the function returns early with `success: false` and drops `caller_deposit` without refunding it [3](#0-2) .

Likewise, in `nep_141_storage_balance_callback`, when the call to the NEP-141 token's `storage_balance_of` fails or the response cannot be deserialized, the function returns early with `success: false`, again dropping `caller_deposit` without refunding it [4](#0-3) .

This is inconsistent with the pattern used everywhere else in the contract: `rlp_execute_callback` treats a failed cross-contract call as a case requiring a caller refund [5](#0-4) , and the test suite explicitly documents and verifies this refund-on-failure invariant for the simple single-hop case [6](#0-5) . No equivalent test exists (or passes) for the two multi-step paths, confirming the gap is unhandled rather than intentional.

### Impact Explanation
Any unprivileged relayer/caller (not necessarily the wallet owner) can call `rlp_execute` with an attached NEAR deposit intended as compensation, targeting: (a) a base-token transfer to an eth-implicit account requiring an address-registrar lookup, or (b) an ERC-20 emulation transfer to an unregistered NEP-141 receiver requiring a `storage_balance_of` check. `CallerDeposit::new` captures this attached deposit specifically to guarantee a refund path on failure for external (non-owner) callers [7](#0-6) . If the registrar or `storage_balance_of` cross-contract call fails (e.g. the token/registrar contract panics, runs out of gas, or returns non-standard data — all fully within control of whichever contract the caller/relayer targets), the caller's attached NEAR deposit is permanently retained by the wallet contract instead of being refunded, while the transaction is reported as failed. This is an unauthorized retention of the caller's value — functionally equivalent to funds becoming permanently stuck/lost for the party who should receive them back.

### Likelihood Explanation
High likelihood: this path is reachable by any external transaction signer without special privileges — simply signing an Ethereum-emulated transaction (base-token transfer to an unregistered eth-implicit address, or an ERC-20 transfer to an unregistered receiver) and submitting it via `rlp_execute` with a nonzero deposit is sufficient. The failure condition of the intermediate promise (registrar lookup / `storage_balance_of`) is easily triggerable by pointing at a non-conforming or adversarial contract, or simply by an honest transient failure (e.g. insufficient callback gas).

### Recommendation
Apply the same refund logic used in `rlp_execute_callback` to the `PromiseResult::Failed` and deserialization-error branches of both `address_check_callback` and `nep_141_storage_balance_callback`, refunding `caller_deposit` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. External caller (relayer) submits `rlp_execute(target, tx_bytes_b64)` with an attached deposit, where the decoded Ethereum transaction is an ERC-20 `transfer` call to a `receiver_id` not yet registered with the target NEP-141 token.
2. `inner_rlp_execute` parses this into `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer)` and schedules a `storage_balance_of` call followed by `.then(nep_141_storage_balance_callback(...))`, passing along the `caller_deposit` captured from the attached deposit [8](#0-7) .
3. The token contract's `storage_balance_of` call fails (e.g., token contract is buggy, under-provisioned with gas, or intentionally reverts).
4. `nep_141_storage_balance_callback` observes `PromiseResult::Failed`, returns `ExecuteResponse { success: false, ... }` at line 205-209, and never issues the refund transfer that `rlp_execute_callback` would have issued in the analogous situation.
5. The caller's attached deposit remains part of the wallet contract's balance permanently, with no compensating action taken.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()

    );

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
