## Title
`TransactionOutput::ensure_match_transaction_info` skips validating state-checkpoint root hashes, letting replay/archive verification tools accept a diverged state root as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`aptos-debugger`, `aptos-move/cli`, and `db-tool`'s `replay_on_archive`) to prove that a freshly re-executed transaction output matches an already-committed, ledger-info-authenticated `TransactionInfo`. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that carry the authenticated state root. A state-root computation bug (in normal state checkpointing, hot state, or the new trading-native "position state" tree) can therefore diverge between the archived/authenticated ledger and locally recomputed state, while these verification tools still report success.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  verifies four properties of a re-executed `TransactionOutput` against the historical, ledger-info-proven `TransactionInfo`: execution status, gas used, write-set hash (`state_change_hash`), and event root hash. The function's own trailing comment acknowledges the gap:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This is not a leftover test helper — it is wired into the primary re-execution/verification paths:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` calls it per-transaction to detect divergence between archived history and freshly executed output, and treats a non-error result as "matches" [3](#0-2) .
- `aptos-debugger`'s `print_mismatches` calls the same function to diagnose divergence when comparing computed vs expected outputs [4](#0-3) .
- `aptos-move/cli`'s replay/simulate flow calls it to assert that a locally re-executed transaction matches the on-chain-committed `TransactionInfo` [5](#0-4) .

Because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are silently excluded from the comparison, any bug in state-summary computation (`state_summary.update(...)` and `compute_position_checkpoint` in [6](#0-5) ) that only manifests on replay (e.g. different code paths, feature flags, or persisted-tree edge cases not exercised during the original block execution/consensus commit) would go undetected by all of these tools, even though it represents committed state that no longer matches the correct VM-computed state root.

Note that the *normal* commit-time path (`DoStateCheckpoint::get_state_checkpoint_hashes`) does cross-check `known_state_checkpoints` against the locally computed root during block/chunk-sync execution [7](#0-6) , so first-time state-sync/consensus execution is protected. The gap is specifically in the independent, after-the-fact verification tooling that re-derives `TransactionOutput` and checks it against archived/authenticated data via `ensure_match_transaction_info`.

### Impact Explanation
This breaks the "authenticated API/state-view output bound to the right version, root, and object" and "replay/restore integrity" invariants: a diverging state root (state, hot-state, or position/trading-native tree) can be silently certified as correct by the very tools (`replay_on_archive`, `aptos-debugger`, CLI replay) whose purpose is to catch exactly this class of divergence. Operators and auditors relying on `db-tool replay-on-archive` to detect a state-root computation bug (a hard-fork-class bug) before it causes wider damage would get a false "all matched" result, delaying detection of a real consensus-breaking state divergence.

### Likelihood Explanation
The gap is deterministic and unconditional — it isn't reliant on a race or malicious input, it's a straightforward code-path omission that will always miss checkpoint-hash mismatches whenever this comparator is used. Its trigger condition is a latent state-root computation bug (e.g., in the newly introduced trading-native/position-state root computation, guarded by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), which the code comment itself flags as an open item that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — i.e., the project is already aware this needs fixing for that feature to be safely enabled.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info`'s corresponding fields whenever they are present (`Option<HashValue>` equality), mirroring the checks already done for `state_change_hash` and `event_root_hash`, before any dependent feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled.

### Proof of Concept
1. Introduce (or trigger via an existing latent bug) a divergence in `DoStateCheckpoint`'s position/hot-state root computation that only manifests during out-of-band replay (e.g., different persisted-tree base state than what consensus saw).
2. Run `db-tool replay-on-archive` (or `aptos-debugger`/CLI replay) over the affected version range; `execute_and_verify` calls `ensure_match_transaction_info` [8](#0-7) .
3. Because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared inside `ensure_match_transaction_info` [9](#0-8) , the call returns `Ok(())` despite the state root diverging from the ledger-info-authenticated `TransactionInfo`, and the tool reports the chunk as successfully verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
