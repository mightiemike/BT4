### Title
Blockifier `replace_class` syscall enforces "class must be declared" check that the Starknet OS (SNOS) Cairo re-execution never performs - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The blockifier's Rust `replace_class` syscall handler rejects a `replace_class` call whose target `class_hash` is not a declared class ("is not declared") and also rejects downgrading a Cairo1 contract to a Cairo0 class hash, as shown by the syscall tests `undeclared_class_hash` and `cairo0_class_hash`. [1](#0-0)  The Cairo implementation of the same syscall inside the Starknet OS program, `execute_replace_class`, performs no such check at all — it contains an explicit unresolved `TODO` acknowledging the missing validation, and unconditionally mutates `contract_state_changes` to set the new (unverified) class hash. [2](#0-1) 

### Finding Description
`replace_class` is a syscall reachable by any deployed contract executed as part of an ordinary invoke/execute transaction — no elevated privilege is required beyond being able to run arbitrary Cairo code in a contract. Exactly analogous to the ArcadeDB bug, where `ALTER TYPE ... CUSTOM`/`... BUCKETSELECTIONSTRATEGY` mutate schema metadata via `setCustomValue`/`setBucketSelectionStrategy` in `LocalDocumentType` while skipping the `UPDATE_SCHEMA` permission check that other schema-mutation paths enforce, here the state-mutation code path in the Starknet OS Cairo re-execution (`execute_replace_class`) mutates a contract's stored `class_hash` in `contract_state_changes` [3](#0-2)  while skipping the validation that the blockifier (the reference/consensus execution engine used to build blocks) performs before allowing the same mutation: that the target `class_hash` corresponds to a previously declared class, and that a Cairo1 contract cannot be replaced with a Cairo0 class hash. [1](#0-0) 

The `TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` comment directly documents the missing enforcement in the OS re-execution path. [4](#0-3) 

### Impact Explanation
Because the Starknet OS is the component that re-executes a proposed block to produce the state commitment/root that ultimately gets committed and proven (Starknet OS re-execution is explicitly listed as an in-scope reachable path), any divergence between what the blockifier accepts/rejects during initial (sequencer) execution and what the OS accepts during re-execution/proving is a correctness-critical bug class:
- If the blockifier's checked `replace_class` rejects an undeclared/incompatible class hash but the OS's unchecked version does not, a maliciously crafted transaction that the blockifier considers invalid for one contract-mode assumption could still be silently accepted by OS re-execution with a different final state (wrong `class_hash` written for the contract), leading to an incorrect state root/committed root relative to what the sequencer network otherwise agrees is valid.
- Conversely, this allows an attacker-controlled contract to set its own on-chain class hash to an arbitrary/undeclared felt value via a single ordinary invoke transaction as long as it's willing to accept the corresponding blockifier-side rejection is bypassed at the OS layer, corrupting the class-hash/state mapping and could permanently break contract functionality tied to `class_hash` validity assumptions or produce honest-node divergence during proof verification.

This matches the required impact bar: wrong committed root, honest-node divergence, or unauthorized state mutation.

### Likelihood Explanation
The path is trivially reachable: any contract that includes a call to `replace_class(new_class_hash)` (a syscall available to every Cairo1 contract) and is invoked via a standard, unprivileged invoke transaction hits this exact code. No special permission, staking, or operator role is required — matching the ArcadeDB analog where a low-privilege authenticated user reaches an under-checked mutation path directly through a standard operation (ALTER TYPE / here, a syscall call). The bug is explicitly and currently marked unresolved via the inline `TODO`, indicating it is a known gap rather than a hypothetical one. [4](#0-3) 

### Recommendation
Add the same validation that blockifier's `replace_class` syscall performs — verifying `class_hash` corresponds to a declared class (and disallowing Cairo1→Cairo0 downgrade) — to `execute_replace_class` in the Starknet OS Cairo program, using `contract_class_changes`/declared-class facts available to the OS, before allowing the `dict_update` that mutates `contract_state_changes`. This keeps the OS's acceptance criteria in lock-step with the blockifier's, eliminating the honest-execution divergence risk.

### Proof of Concept
Conceptual PoC (cannot be executed without a running OS/blockifier harness, but the divergence is directly demonstrated by the existing test suite):
1. Deploy a Cairo1 contract exposing `test_replace_class(new_class_hash)` that calls the `replace_class` syscall (feature contract already used in `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs`).
2. Submit an invoke transaction calling `test_replace_class` with an undeclared/arbitrary `class_hash` (e.g., `1234`).
3. Under blockifier execution (`crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29`), this call fails with "is not declared", i.e. the transaction/entry point is rejected. [5](#0-4) 
4. Under the Starknet OS Cairo execution of `execute_replace_class` (`crates/apollo_starknet_os_program/.../syscall_impls.cairo:881-920`), no such check exists, so the same call would succeed and unconditionally overwrite the `class_hash` in `contract_state_changes`, producing a different accepted/rejected outcome (and different resulting state) than the blockifier for the identical transaction. [3](#0-2) 

Note: I was unable to fully trace whether an additional out-of-Cairo Rust-side hint/validation exists elsewhere in the SNOS hint processor that might compensate for this gap (e.g., in `crates/starknet_os/src/hints/hint_implementation/compiled_class/implementation.rs` or related hint files) — my search covered the direct Cairo execution function and its inline TODO but did not locate any supplementary Rust-side enforcement of "class must be declared" specifically for `replace_class`. This should be verified further before treating the gap as fully confirmed unmitigated.

// Replaces the class.
func execute_replace_class{
    range_check_ptr,
    syscall_ptr: felt*,
    contract_state_changes: DictAccess*,
    revert_log: RevertLogEntry*,
}(contract_address: felt) {
    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, ReplaceClassRequest*);

    // Reduce gas.
    let success = reduce_syscall_gas_and_write_response_header(
        total_gas_cost=REPLACE_CLASS_GAS_COST, request_struct_size=ReplaceClassRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );

    assert [revert_log] = RevertLogEntry(selector=CHANGE_CLASS_ENTRY, value=state_entry.class_hash);
    let revert_log = &revert_log[1];

    return ();
}
