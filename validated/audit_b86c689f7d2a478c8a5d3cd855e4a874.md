### Title
Rounding in `commission_split` silently discards lamports during Tower-epoch stake reward distribution - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
The `commission_split` function, used to divide inflation stake rewards between a voter (validator) and staker during Tower epochs, intentionally truncates fractional lamports on both sides of the split rather than assigning the residual to either party. This mirrors the reported `calcCommissions` rounding issue: repeated truncation across many stake accounts and epochs causes small amounts of lamports to be dropped from circulation on every reward distribution rather than being fully and deterministically accounted for, unlike the fixed sibling function `commission_split_preserve_lamports` which was specifically introduced to avoid this dust loss.

### Finding Description
`commission_split` computes the voter and staker shares independently and symmetrically: [1](#0-0) 
Both `mine` (voter) and `theirs` (staker) are computed via `on * split / MAX_BPS` and `on * (MAX_BPS - split) / MAX_BPS` respectively, using integer division. Because both computations floor-divide independently, `mine + theirs` can be up to 1 lamport less than `on` (the total reward), and that residual lamport is never assigned to either party — it is simply not distributed. The code comment explicitly acknowledges this: "we intentionally discard any residual fractional lamports."

This is called from `calculate_stake_rewards` when `is_tower_epoch` is true: [2](#0-1) 

By contrast, the non-Tower path uses `commission_split_preserve_lamports`, which computes only the staker side via floor division and assigns the voter the exact remainder (`on - staker_rewards`), guaranteeing `voter + staker == on` with zero lamports lost: [3](#0-2) 

The existence of `commission_split_preserve_lamports` as a deliberate fix for the "preserve lamports" property demonstrates that the `commission_split` truncation behavior is a known, unresolved rounding loss for the Tower-epoch code path specifically — precisely the class of bug described in the external report (`admin_amount`/commission rounding dust accumulating over time).

### Impact Explanation
Each Tower-epoch stake reward calculation that hits the `9_900`/`9_999`/other non-boundary commission cases can lose up to 1 lamport of the intended reward (test cases at lines showing "1-lamport truncation" confirm this): [4](#0-3) 
With potentially millions of stake delegations processed every epoch (as noted in the surrounding reward-calculation code comments about "N stake delegations... N is >1,000,000"), this systematically reduces the total lamports actually paid out relative to the intended inflation schedule. Because the loss is deterministic and identical across all validators replaying the same epoch, it does not cause a hash/consensus divergence by itself, but it does represent a genuine, silent, permanent reduction of value transferred to stakers/voters versus the economically intended amount — dust that is neither distributed nor burned nor tracked, analogous to the reported unused/accumulated commission dust in the external report. Over the lifetime of the network and given the historically large validator/stake set, this could sum to a non-trivial amount of permanently unaccounted-for lamports.

### Likelihood Explanation
This code path executes unconditionally for every stake account reward calculation performed during Tower epochs (i.e., whenever `AlpenglowEpochType::Tower` applies) whenever the commission is not exactly 0% or 100% (`was_split == true`), which is the common case. No adversarial action is required — it is a systematic artifact of ordinary reward processing.

### Recommendation
Apply the same remainder-preserving technique already used in `commission_split_preserve_lamports` to `commission_split`: compute one side (e.g., the staker share) via floor division and derive the other side (voter share) as `total - staker_share`, ensuring `voter_rewards + staker_rewards == rewards` exactly, eliminating the currently discarded fractional lamport. If the "cancel entirely on unfair split" semantics of `commission_split` needs to be preserved for legacy Tower behavior, that decision logic should be kept separate from the underlying money-conservation calculation so no lamports are silently lost when a payout does occur.

### Proof of Concept
Using the existing test data in the repository itself: [5](#0-4) 
`commission_split(9_900, 1)` returns `(0, 0, true)` — the single lamport of reward is entirely dropped (neither voter nor staker receives it), demonstrating the exact rounding/truncation loss described in the external report, reproducible deterministically for any `rewards` value where `rewards * bps` is not evenly divisible by `10_000` on both sides of the split.

fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
