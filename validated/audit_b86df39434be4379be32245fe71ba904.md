### Title
Wallet Contract pays the relayer fee unconditionally before the emulated action's outcome is known - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` in the NEAR Wallet Contract fires a `promise_batch_action_transfer` refund of the relayer `fee` immediately when parsing an `EOABaseTokenTransfer`/`ERC20Transfer` action, completely detached from the promise chain that actually performs the user's requested action. The fee payment is not conditioned on, or chained after, the success of the subsequent `action_to_promise`/`address_check_callback`/`nep_141_storage_balance_callback` → `rlp_execute_callback` flow, so the relayer is paid even when the emulated action ultimately fails.

### Finding Description
`inner_rlp_execute` parses the RLP-encoded transaction and, for `EOABaseTokenTransfer`/`ERC20Transfer` kinds with a non-zero `fee`, immediately creates an independent promise batch and transfers `fee` to the predecessor (relayer): [1](#0-0) 

This happens *before* the dispatch of the actual action promise. For the `EOABaseTokenTransfer` case with `address_check: Some(address)`, the flow subsequently calls the address registrar and only afterwards runs `address_check_callback`, which can determine the relayer set an invalid target and ban it as "faulty relayer": [2](#0-1) [3](#0-2) 

Because the fee-transfer promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) is created eagerly and is not part of the same promise chain as the address check / action execution / `rlp_execute_callback`, it executes and completes independently of whatever the later callback determines. If the address check later reveals the relayer supplied an incorrect target (banning the relayer) or if the subsequent `action_to_promise(...).then(rlp_execute_callback)` chain fails (`PromiseResult::Failed` in `rlp_execute_callback`, which only handles refunding a *caller's attached deposit*, not the fee already sent to the relayer): [4](#0-3) 
the relayer fee has already been paid out of the wallet contract's balance and is never reclaimed.

This mirrors the reported bug class: an amount (here, the relayer's fee) is accounted for and paid out based on the "expected" successful outcome of an action, while the actual downstream action can fail or be flagged as invalid, with no balance/result reconciliation tying the payment to the real result.

### Impact Explanation
Any relayer (an unprivileged account able to call `rlp_execute` on a NEAR Wallet Contract instance) can construct or forward a transaction whose `fee` is paid out unconditionally, then let the underlying action fail (e.g., by using an incorrect `target`/address so the address check bans it as faulty, or by causing the wrapped action promise itself to fail). The wallet loses the `fee` amount of NEAR with no corresponding action being executed and no way to recover it — an unauthorized value movement out of the user's wallet contract balance triggered by a malicious relayer.

### Likelihood Explanation
The path is reachable via a single `FunctionCall` to `rlp_execute` from any account acting as relayer; no special privileges are required, and the code paths for `EOABaseTokenTransfer`/`ERC20Transfer` with non-zero fee are used in normal operation (relayer compensation is a documented design feature).

### Recommendation
Chain the relayer fee transfer as part of the same promise sequence gated by the final outcome (e.g., include it in/after `rlp_execute_callback` only on `PromiseResult::Successful`), or otherwise verify actual completion of the target action before releasing the fee to the relayer, instead of firing an unconditional `promise_batch_action_transfer` at parse time.

### Proof of Concept
1. A relayer submits an `EOABaseTokenTransfer` RLP transaction with `address_check: Some(address)` and non-zero `fee` to the Wallet Contract's `rlp_execute`.
2. `inner_rlp_execute` immediately schedules a `promise_batch_action_transfer` sending `fee` to the relayer's account, per lines 374-385 of `lib.rs`.
3. The relayer supplies an `address` that resolves in `address_check_callback` to an existing named account (i.e., deliberately or otherwise providing a bad target), causing the callback to treat it as a "faulty relayer" and ban it via `create_ban_relayer_promise`, per lines 160-192.
4. The user's intended action is never executed (it is replaced by the ban-relayer promise), yet the fee-transfer promise created in step 2 already executed independently and paid the relayer.
5. Net effect: wallet contract balance decreases by `fee` with no corresponding successful action, and no compensating refund logic exists for this fee (only `caller_deposit` refunds are handled in `rlp_execute_callback`, and that logic isn't even in scope for this path since a ban-relayer promise is dispatched instead).
