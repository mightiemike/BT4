### Title
Unchecked `Option::unwrap()` on Cairo-Native compiler output causes sequencer panic on attacker-controlled Declare transaction - (File: `crates/apollo_compile_to_native/src/compiler.rs`)

### Summary
The FFmpeg report describes `avcodec_open2` dereferencing a codec's close-function pointer without checking it is valid, causing a NULL pointer dereference reachable from external input. The structural analog in this repo is `SierraToNativeCompiler::compile`, which invokes an external Sierra→Native compiler subprocess and then blindly unwraps the artifact-loading result without checking whether a valid executor was actually produced, exactly like FFmpeg trusting an unchecked pointer after a nominally-successful operation.

### Finding Description
`SierraToNativeCompiler::compile` runs the `cairo-native` compiler binary via `compile_with_args`, and on subprocess success loads the resulting shared object with `AotContractExecutor::from_path`: [1](#0-0) 

```rust
let _stdout = compile_with_args(...)?;
Ok(AotContractExecutor::from_path(output_file.path())
    .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
    .unwrap())
```

`from_path` returns a `Result<Option<AotContractExecutor>, _>`. The `?` operator only guards against the `Err` case; the `Some`/`None` case is handled with a bare `.unwrap()`. If the subprocess exits successfully (status code 0) but the output artifact at `output_file.path()` is missing, empty, truncated, or otherwise fails to be recognized as a loadable library (e.g., due to attacker-crafted Sierra input that triggers a compiler bug, a partial write, or a race on the temp file), `from_path` can legitimately return `Ok(None)`. The subsequent `.unwrap()` panics, exactly mirroring the FFmpeg bug class: an external subroutine's success is trusted without validating that it produced a well-formed handle before dereferencing/unwrapping it.

This function is invoked from `SierraToNativeCompiler::compile`, which is called from `process_compilation_request` in the native class manager: [2](#0-1) 

`process_compilation_request` is reached in two ways: (1) asynchronously from the lazy-compilation worker thread (`run_compilation_worker`), and (2) synchronously and directly in `set_and_compile` when `cairo_native_mode == WaitOnCompilation`: [3](#0-2) 

`set_and_compile` is invoked as part of caching a newly-declared Cairo1 class, which is on the path triggered directly by a user-submitted Declare transaction reaching the gateway's stateful validator / contract class manager (per the tx submission flow: Declare → Class Manager → Sierra Compiler pipeline): [4](#0-3) 

### Impact Explanation
When `cairo_native_mode` is `WaitOnCompilation`, the `.unwrap()` panic in `compile()` occurs synchronously in the code path that services a Declare transaction submission. An unhandled panic here can propagate up through the calling task, potentially unwinding into the thread that services `add_tx`, terminating in-flight request handling and, depending on how the async executor/task boundary is structured, potentially crashing the worker thread or the whole gateway/sequencer process for that node. Because the panic can be triggered by a compiler artifact anomaly reachable through the *declare-transaction* Sierra program supplied by an unprivileged class declarer, this maps to the "network unable to confirm new transactions" impact criterion if the affected node crashes or its request-handling thread is disabled — every declare hitting that path could be repeatedly weaponized.

### Likelihood Explanation
The exact conditions under which `AotContractExecutor::from_path` returns `Ok(None)` after a "successful" compiler invocation live inside the external `cairo_native` crate, which is outside this repo's index; I could not fully confirm from the indexed code when that `None` branch is actually reachable in practice (e.g., whether `from_path` only checks file extension/metadata versus performing a full dlopen validation). This is the key remaining uncertainty. Given that, likelihood is assessed as **medium**: the code pattern (`Result<Option<T>>` collapsed via `.unwrap()`) is a clear latent defect regardless of exact trigger conditions, but confirming a concrete Sierra program that reliably produces `Ok(None)` (rather than `Err`) would require inspecting the `cairo_native` crate's source, which is not available in this index.

### Recommendation
Replace the `.unwrap()` with proper error propagation, e.g.:
```rust
AotContractExecutor::from_path(output_file.path())
    .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
    .ok_or_else(|| CompilationUtilError::CompilationError(
        "Compiler produced no executable artifact".to_string()
    ))
```
This ensures a missing/invalid artifact surfaces as a normal `CompilationUtilError` (already handled by callers such as `process_compilation_request`, which cache a `CompilationFailed` state and optionally log) instead of panicking the calling thread.

### Proof of Concept
A concrete end-to-end PoC (a Sierra program that makes the `cairo-native` subprocess exit 0 while leaving no/invalid output at `output_file.path()`) cannot be constructed from the indexed code alone, since the compiler binary's internals are external. The code-level PoC is the defect itself: any caller path that reaches `SierraToNativeCompiler::compile` with a compiler exit status of `0` and a missing/invalid output file will panic at the `.unwrap()` on line 60 of `crates/apollo_compile_to_native/src/compiler.rs`, as shown above.

/// Processes a compilation request and caches the result.
fn process_compilation_request(
    class_cache: RawClassCache,
    compiler: Arc<SierraToNativeCompiler>,
    compilation_request: CompilationRequest,
    panic_on_compilation_failure: bool,
) -> Result<(), CompilationUtilError> {
    let (class_hash, sierra, casm) = compilation_request;
    if let Some(CompiledClasses::V1Native(_)) = class_cache.get(&class_hash) {
        // The contract class is already compiled to native - skip the compilation.
        return Ok(());
    }
    let sierra_for_compilation = into_contract_class_for_compilation(sierra.as_ref());
    let start = Instant::now();
    let compilation_result = compiler.compile(sierra_for_compilation);
    let duration = start.elapsed();
    log::info!(
        "Compiling to native contract with class hash: {:#066x}. Duration: {:.3} seconds",
        class_hash.0,
        duration.as_secs_f32()
    );
    match compilation_result {
        Ok(executor) => {
            let native_compiled_class = NativeCompiledClassV1::new(executor, casm);
            class_cache.set(
                class_hash,
                CompiledClasses::V1Native(CachedCairoNative::Compiled(native_compiled_class)),
            );
            log::info!("Compilation succeeded");
            Ok(())
        }
        Err(err) => {
            class_cache.set(
                class_hash,
                CompiledClasses::V1Native(CachedCairoNative::CompilationFailed(casm)),
            );
            log::error!(
                "Error compiling contract class with class hash: {:#066x}: {err}",
                class_hash.0
            );
            NATIVE_COMPILATION_ERROR.increment(1);
            if panic_on_compilation_failure {
                panic!("Compilation of class hash: {:#066x} failed", class_hash.0);
            }
            Err(err)
        }
    }
}
