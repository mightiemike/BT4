### Title
Missing atomicity in `ExecutePayload` allows arbitrary UEA-payload execution to persist even when gas fee deduction fails - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
The external report describes a reentrancy-class bug where state accounting (`_totalSupply`, `saleSupplyMinted`, etc.) is updated *after* an external call (`_safeMint`), letting an attacker re-enter and mint before the invariant is enforced. The Push Chain analog is an atomicity ordering bug in `Keeper.ExecutePayload` (the function backing `MsgExecutePayload`): it performs the externally-triggered EVM execution (`CallUEAExecutePayload`, which can execute arbitrary attacker-supplied payload code through the UEA) directly against the live `sdkCtx`, and only *afterward* attempts to charge gas fees via `DeductGasFeesFromReceipt`. Unlike the sibling function `ExecutePayloadV2`, this path is not wrapped in a `CacheContext`, so if fee deduction fails, the already-executed EVM side effects are not guaranteed to be rolled back together with the accounting failure.

### Finding Description
`MsgExecutePayload` is a gasless, permissionless message — "any user" can submit it [1](#0-0) . Its handler calls `msgServer.ExecutePayload`, which delegates to `Keeper.ExecutePayload` in `x/uexecutor/keeper/msg_execute_payload.go` [2](#0-1) .

Inside `Keeper.ExecutePayload`, Step 3 calls `k.CallUEAExecutePayload(sdkCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)` directly on the live `sdkCtx` — this drives arbitrary EVM execution through the UEA (a smart-contract wallet that will execute whatever call the owner's signed payload specifies). Step 4 only *afterward* calls `k.DeductGasFeesFromReceipt(ctx, sdkCtx, ueaAddr, receipt, universalPayload)` to bill the UEA for gas used [3](#0-2) .

This is precisely the "free-execution gap" pattern the team already identified and fixed elsewhere in the codebase (tracked as `F-2026-16738`): when EVM execution succeeds but subsequent fee deduction fails, the EVM state changes must be discarded together with the fee failure, or the caller gets execution for free. The fix applied to those other paths is to wrap the call + fee deduction in an `sdkCtx.CacheContext()` and only `writeCache()` on full success:
- `ExecutePayloadV2` (used by inbound execution) explicitly does this [4](#0-3) .
- `ExecuteInboundGasAndPayload` and `ExecuteInboundFundsAndPayload` do the same for the CEA smart-contract-recipient path, with an explicit comment referencing the closed gap [5](#0-4) [6](#0-5) .
- A dedicated integration test verifies the fixed behavior for the inbound path: "fee deduction failure rolls back executeUniversalTx, keeps deposit" [7](#0-6) .

`Keeper.ExecutePayload` (the direct, user-reachable `MsgExecutePayload` path) has **no such `CacheContext` wrapper** — it operates directly on `sdkCtx` for both the EVM call and the fee deduction, then simply returns an error on `feeErr` [3](#0-2) . Whether returning that error is sufficient to undo the `DerivedEVMCall`-driven EVM statedb writes depends on whether those writes participate in the same discardable branch as the Cosmos message-level rollback; the fact that the team needed an explicit `CacheContext` fix elsewhere for the identical call sequence (EVM call → fee deduction) strongly indicates that a bare `return err` does **not** reliably undo `DerivedEVMCall` state, i.e., the same free-execution gap is reachable here.

### Impact Explanation
If confirmed, an attacker whose UEA has just enough native `upc` to pass Push Chain's pre-checks could submit a payload that: (1) drains or spends the UEA's native balance during the arbitrary UEA call (e.g., self-transfer, swap, or any contract interaction the payload authorizes), then (2) causes `DeductGasFeesFromReceipt` to fail for insufficient funds. If the EVM execution isn't rolled back with the fee failure, the attacker obtains arbitrary, unpaid UEA-authorized execution — matching the "unauthorized UEA execution" / "corruption of gas fee accounting" impact categories in scope, and is unprivileged and reachable via the ordinary `MsgExecutePayload` message path with honest validators/nodes.

### Likelihood Explanation
`MsgExecutePayload` is open to "any user," is gasless, and requires only a validly signed payload from the UEA owner (or a third-party relaying it) — no privileged role is needed [8](#0-7) . The precondition (payload that spends/drains the UEA's native balance before fee deduction runs) is fully attacker-controlled since UEA payload execution is arbitrary EVM calls.

### Recommendation
Wrap the `CallUEAExecutePayload` + `DeductGasFeesFromReceipt` sequence in `Keeper.ExecutePayload` inside an `sdkCtx.CacheContext()`, mirroring `ExecutePayloadV2`, so that a fee-deduction failure discards the EVM execution atomically instead of relying on the outer Cosmos message error path.

### Proof of Concept
Not independently reproduced — this assessment is based on static comparison of `Keeper.ExecutePayload` (unprotected) against `Keeper.ExecutePayloadV2` and the inbound-execution equivalents (protected via `CacheContext`, with an integration test demonstrating the pre-fix bug class). I was unable to inspect `x/uexecutor/keeper/fees.go` (`DeductGasFeesFromReceipt`'s exact failure conditions) or confirm at the EVM-keeper/statedb level whether a bare Cosmos message error return actually reverts `DerivedEVMCall`-committed state, due to running out of tool-call budget. A background Devin session with repo access should: (1) read `x/uexecutor/keeper/fees.go` to confirm `DeductGasFeesFromReceipt` can fail on insufficient UEA balance, (2) write a unit/integration test analogous to `test/integration/uexecutor/inbound_cea_smart_contract_test.go`'s "fee deduction failure rolls back executeUniversalTx" test, but targeting `Keeper.ExecutePayload` via `MsgExecutePayload` directly, to determine whether EVM state actually persists after the function returns an error.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}

	// Both succeeded — commit EVM state and fee deduction together.
	writeCache()
