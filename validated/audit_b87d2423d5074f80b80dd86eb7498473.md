### Title
Backslash-based open redirect bypass in `sanitizeRedirectUrl`/`isSafe` allows redirecting off the app's own origin - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts)

### Summary
`isSafe()` validates the *raw* `redirectUrl` string for `///` (`FILE_URI_MATCH`) and whitespace, but only checks `INVALID_RELATIVE_URL` (`[/\\][/\\]`) against `url.pathname` **after** the URL has already been resolved with `new URL(redirectUrl, domain)`. Because the WHATWG URL parser treats backslashes as path separators for special schemes (http/https) and switches into "authority" parsing mode when it sees two consecutive slash-like characters (`/` or `\`) at the start of the relative reference, an input like `/\evil.com` gets resolved with `evil.com` as the new **host**, while the resulting `url.pathname` becomes just `/` — which does not match `INVALID_RELATIVE_URL`. All subsequent checks (protocol/SSL) pass because `evil.com` is served over `https`.

### Finding Description
The validation function is: [1](#0-0) 

The check sequence is:
1. `FILE_URI_MATCH`/`WHITESPACE_CHARACTER` run against the raw `redirectUrl` string — `/\evil.com` contains neither three slashes nor whitespace, so it passes.
2. `new URL(redirectUrl, domain)` is invoked. Per the WHATWG URL Standard, for a special scheme (http/https) a relative reference beginning with two "slash-like" characters (any mix of `/` and `\`) is parsed as an authority (host) component, not a path. `/\evil.com` is exactly such an input, so the resulting URL's host becomes `evil.com`, not the original `domain`'s host.
3. `INVALID_RELATIVE_URL` is tested against `url.pathname` (the *already-resolved* path, e.g. `/`), not the raw string — so the backslash pattern that triggered the host takeover is no longer visible to this check and it passes.
4. Protocol/SSL checks pass since the destination is `https://evil.com/`.

`sanitizeRedirectUrl` then returns `new URL(redirectUrl, domain)` — i.e., a URL whose origin is `evil.com`, not `domain` — and the caller trusts it as safe: [2](#0-1) 

This value is consumed by `renderAppBridge`, which is used to redirect the merchant's browser (e.g. as part of the embedded-app/OAuth completion flow) via a `window.open`/`_top` navigation using the "sanitized" destination: [3](#0-2) 

The existing test suite only exercises the double-forward-slash and triple-slash cases, never a backslash/mixed-slash payload, so this bypass path is untested: [4](#0-3) 

### Impact Explanation
An attacker who controls the `redirectUrl`/embedded-redirect query parameter consumed by `renderAppBridge` (and therefore `sanitizeRedirectUrl`) can force the merchant's browser to be redirected to an attacker-controlled origin instead of the app's own domain. Since this redirect happens as part of the OAuth/embedded-app completion flow, this is a classic **open redirect** that can be used to leak sensitive query-string data (state/host params) or chain into phishing/token-theft flows targeting the merchant, matching Shopify's "open redirect with real consequence" bounty class.

### Likelihood Explanation
The attacker only needs to control the value passed as `redirectUrl` (an unprivileged HTTP client crafting a query parameter such as `redirectUrl=/\evil.com`). No secret, no privileged role, and no non-default configuration are required — the flaw is purely in `isSafe`'s check ordering versus the WHATWG URL parser's backslash-normalization behavior. This is deterministically reproducible via a unit test.

### Recommendation
Perform the `INVALID_RELATIVE_URL` (and any "double slash/backslash" style) checks against the **raw** `redirectUrl` input before/independently of URL resolution, and additionally verify after parsing that `url.origin`/`url.host` strictly equals `new URL(domain).origin`/`host` rather than relying solely on pattern matching of `pathname`. The safest fix is to compare `url.origin === new URL(domain).origin` explicitly in `isSafe`.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from '../validate-redirect-url';

it('rejects backslash host-confusion open redirect', () => {
  const domain = 'https://my-app.example.com';
  const evil = sanitizeRedirectUrl(domain, '/\\evil.com', {throwOnInvalid: false});

  // Vulnerable behavior: evil is defined and its origin is NOT the app domain
  expect(evil).toBeDefined();
  expect(evil!.origin).not.toEqual(new URL(domain).origin);
  expect(evil!.host).toEqual('evil.com'); // demonstrates the bypass
});
```
Running this against the current implementation shows `sanitizeRedirectUrl` returns `https://evil.com/` instead of throwing/rejecting, confirming the bypass.

```typescript
function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
```

```typescript
export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
```
