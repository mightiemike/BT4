### Title
Per-primitive proving-gas cost can floor to zero, letting the bouncer under-account real proving load - ([File: crates/blockifier/src/bouncer.rs])

### Summary
`BuiltinInstanceLimits::induced_gas_costs` derives the bouncer's per-instance proving-gas price of each Cairo builtin/opcode as `proving_gas / limit`, an integer floor division. If the configured block-wide `proving_gas` budget is smaller than a builtin's configured instance limit, the derived per-unit cost floors to `0`, exactly analogous to the Notional wrapper bug where `shares * precision / INTERNAL_TOKEN_PRECISION` floors to `0` for small `shares`.

### Finding Description
`induced_gas_costs` computes, for every Cairo primitive, `cost = floor(proving_gas / limit)`: [1](#0-0) 

This is called from `BouncerConfig::builtin_gas_costs`, which feeds `self.block_max_capacity.proving_gas` (the block-wide proving-gas budget) as the numerator: [2](#0-1) 

The resulting per-unit costs are then used to compute a transaction's `proving_gas` contribution via `proving_gas_from_cairo_primitives_and_sierra_gas` / `cairo_primitives_to_gas`, which sums `usage * cost_per_unit` for every builtin/opcode a transaction uses, and this sum is what is checked against the block's remaining `proving_gas` capacity in `Bouncer::try_update`: [3](#0-2) [4](#0-3) 

Just like the Notional case (`assets = shares * precision / INTERNAL_TOKEN_PRECISION` truncating to `0` for small `shares`, letting a depositor mint shares while transferring zero underlying), here a builtin whose `NonZeroU64` instance limit exceeds the configured `proving_gas` budget produces a per-unit proving-gas cost of `0`. Any transaction invoking that builtin then contributes `0` to the bouncer's proving-gas accounting no matter how many instances of the builtin it uses, while the real proof workload (and the SHARP/L2 proving cost) scales linearly with builtin usage. The bouncer's admission decision (`self.bouncer_config.has_room(next_accumulated_weights)`) is thus blind to this resource dimension for that builtin, and unboundedly many builtin invocations can be packed into a block while showing "room" in `proving_gas`.

### Impact Explanation
The bouncer's `proving_gas` capacity exists specifically to bound the actual proof-generation cost of a block so that SHARP/the prover can process it. If a builtin's induced per-unit cost floors to zero, an attacker can submit a transaction (or several) that heavily exercises that under-priced builtin, producing a block whose *actual* proving cost vastly exceeds the intended `block_max_capacity.proving_gas` ceiling while the bouncer's bookkeeping reports it as comfortably within capacity. This can produce blocks that cannot be proven within the expected time/resource budget, i.e., a network that is unable to confirm new transactions/blocks — matching the sanctioned "network unable to confirm new transactions" impact class, reachable purely by an unprivileged transaction sender choosing calldata/opcodes to invoke the affected builtin many times in a single (or many) transactions.

The severity of the underpricing depends entirely on the relationship between `builtin_instance_limits` (per-builtin `NonZeroU64`) and `block_max_capacity.proving_gas` in whatever `BouncerConfig` is deployed. With production defaults, `builtin_instance_limits` values (e.g., pedersen: 2,000,000; range_check: 66,666,666, etc.) are large; whether `block_max_capacity.proving_gas` is configured smaller than any of them in a live deployment could not be fully verified from the index — this needs on-chain/deployed-config verification, since `BouncerConfig::max()` in tests deliberately keeps `proving_gas` at its default specifically "so the induced builtin gas costs stay in a sane range," implying maintainers are aware this ratio matters: [5](#0-4) 

### Likelihood Explanation
Likelihood depends on config: the vulnerability is only live if `block_max_capacity.proving_gas < some_builtin_limit` in the actually deployed `BouncerConfig`. This is a configuration-dependent precondition rather than a code path that is unconditionally exploitable, so it should be validated against production versioned-constants/bouncer-config values before treating it as confirmed-exploitable in the current deployment. The comment in `BouncerConfig::max()` (test-only helper) suggests the maintainers are already aware that an inverted ratio produces "insane" per-builtin costs, consistent with this being a real, if config-gated, footgun in the formula itself.

### Recommendation
- In `BuiltinInstanceLimits::induced_gas_costs`, round up (`div_ceil`) instead of flooring, or enforce a minimum cost of `1` per instance whenever `usage > 0`, mirroring the project's existing pattern of `sierra_gas_to_l1_gas_amount_round_up` / `checked_div_ceil` used elsewhere in the fee/gas-conversion code for exactly this reason.
- Add a construction-time invariant (assert or config validation) that `block_max_capacity.proving_gas >= limit` for every builtin in `BuiltinInstanceLimits`, so a misconfigured `BouncerConfig` cannot silently zero out a builtin's proving-gas price.
- Add a regression test asserting that no builtin's induced cost is `0` for the actual deployed/versioned `BouncerConfig`.

### Proof of Concept
1. Deploy (or configure in tests) a `BouncerConfig` where `block_max_capacity.proving_gas < builtin_instance_limits.<some_builtin>` (e.g., `proving_gas = GasAmount(1_000_000)` while `pedersen` limit stays at its default `2_000_000`).
2. Call `BouncerConfig::builtin_gas_costs()` → `BuiltinInstanceLimits::induced_gas_costs(proving_gas)`; observe `pedersen` cost = `1_000_000 / 2_000_000 = 0` (integer floor), matching the derivation shown at: [6](#0-5) 
3. Submit a transaction that invokes the pedersen builtin a very large number of times (e.g., via repeated hash calls in a loop, bounded only by the transaction's Sierra-gas/step limits, not by `proving_gas`).
4. In `Bouncer::try_update`, the transaction's `tx_bouncer_weights.proving_gas` contribution from pedersen usage is `usage * 0 = 0`, so `has_room` never trips on this dimension even though real proving work for pedersen instances was performed, at: [7](#0-6) 
5. Repeating this across many transactions in a block lets an attacker inflate the block's real proving workload for that builtin far beyond `block_max_capacity.proving_gas` while the bouncer keeps reporting available capacity, risking a block that the prover cannot process in time.

impl BuiltinInstanceLimits {
    /// Induces the per-instance proving-gas cost of each Cairo primitive from its per-block
    /// instance limit: `cost = floor(proving_gas / limit)`.
    pub fn induced_gas_costs(&self, proving_gas: GasAmount) -> BuiltinGasCosts {
        let derive = |limit: NonZeroU64| -> u64 { proving_gas.0 / limit.get() };
        BuiltinGasCosts {
            pedersen: derive(self.pedersen),
            range_check: derive(self.range_check),
            range_check96: derive(self.range_check96),
            poseidon: derive(self.poseidon),
            ecdsa: derive(self.ecdsa),
            ecop: derive(self.ecop),
            bitwise: derive(self.bitwise),
            keccak: derive(self.keccak),
            add_mod: derive(self.add_mod),
            mul_mod: derive(self.mul_mod),
            blake: derive(self.blake),
        }
    }

/// Calculates proving gas from builtin counters and Sierra gas.
fn proving_gas_from_cairo_primitives_and_sierra_gas(
    sierra_gas: GasAmount,
    cairo_primitives_counters: &CairoPrimitiveCounterMap,
    proving_builtin_gas_costs: &BuiltinGasCosts,
    sierra_builtin_gas_costs: &BuiltinGasCosts,
) -> GasAmount {
    let cairo_primitives_proving_gas =
        cairo_primitives_to_gas(cairo_primitives_counters, proving_builtin_gas_costs);
    let steps_proving_gas =
        sierra_gas_to_steps_gas(sierra_gas, cairo_primitives_counters, sierra_builtin_gas_costs);

    steps_proving_gas.checked_add_panic_on_overflow(cairo_primitives_proving_gas)
}
