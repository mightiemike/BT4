Investigation of java-tron's `COINBASE` opcode implementation shows it does **not** reproduce the minievm bug. In `ProgramInvokeFactory.createProgramInvoke`, for both `TRX_CONTRACT_CREATION_TYPE` and `TRX_CONTRACT_CALL_TYPE` under `ET_NORMAL_TYPE`/`ET_PRE_TYPE`, `coinbase` is explicitly set to the block's witness address (`block.getBlockHeader().getRawDataOrBuilder().getWitnessAddress().toByteArray()`), which correctly represents the block proposer, not an empty address. [1](#0-0) 

The `coinBaseAction` opcode handler simply pushes this value from `ProgramInvoke.getCoinbase()`, and `ProgramInvokeImpl.getCoinbase()` returns the stored `coinbase` `DataWord` set at construction time from the witness address. [2](#0-1) [3](#0-2) 

This is confirmed by the existing unit test, which asserts that `COINBASE` returns `invoke.getCoinbase().getLast20Bytes()`, i.e., the actual witness/proposer address, not the zero address. [4](#0-3) 

`coinbase` only remains unset (defaulting to zero/empty) in the `ET_CONSTANT_TYPE` (view/constant call) branch, which mirrors typical simulated/local-call semantics found in many EVM implementations for non-state-changing calls, and does not correspond to a real block-processing or consensus-relevant execution path. [5](#0-4) 

Since the reachable, real-transaction execution path in java-tron already sets `COINBASE` to the correct block proposer (witness) address — and the original minievm finding itself was disputed as intended behavior by the target's team — there is no valid unprivileged-user-impacting analog here.
