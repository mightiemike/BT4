## Analysis

The attack path is real and reachable, though the "unprivileged" framing needs one clarification: `ProposalCreateActuator.validate()` requires the sender address to already be a registered witness via `chainBaseManager.getWitnessStore().has(ownerAddress)` [1](#0-0) . However, becoming a witness in java-tron requires no election, no top-27 SR status, and no privileged action — any account can self-register via `WitnessCreateContract`, gated only by `accountCapsule.getBalance() < dynamicStore.getAccountUpgradeCost()` [2](#0-1) . So the described attacker (self-funded, no SR election) is accurate: pay `AccountUpgradeCost` once, then repeatedly submit `ProposalCreateContract` transactions, each of which costs `calcFee() == 0` [3](#0-2) .

Each accepted proposal is persisted permanently into `ProposalStore` (no expiry-based pruning removes entries; expired ones are only marked, not deleted) via `chainBaseManager.getProposalStore().put(...)` [4](#0-3) .

The public read path `ListProposals` gRPC / `/wallet/listproposals` HTTP servlet both call `Wallet.getProposalList()` [5](#0-4) , which calls `ProposalStore.getAllProposals()` — a full iterate-and-sort over the entire store on every request:

```java
public List<ProposalCapsule> getAllProposals() {
  return Streams.stream(iterator())
      .map(Map.Entry::getValue)
      .sorted(
          (ProposalCapsule a, ProposalCapsule b) -> a.getCreateTime() <= b.getCreateTime() ? 1
              : -1)
      .collect(Collectors.toList());
}
``` [6](#0-5) 

This has two distinct problems beyond simple O(n log n) growth:
1. It's a full unbounded scan with no pagination on the standard `listProposals` endpoint (a bounded `getPaginatedProposalList` exists separately, capped by `PROPOSAL_COUNT_LIMIT_MAX` [7](#0-6) , but `listProposals`/`getProposalList` does not use it).
2. The comparator `a.getCreateTime() <= b.getCreateTime() ? 1 : -1` is not a valid `Comparator`: for equal `createTime` values it returns `1` for both `compare(a,b)` and `compare(b,a)`, violating the required antisymmetry (`compare(a,b) == -compare(b,a)`). Since all proposals created within the same block share the same `createTime` (`now = getLatestBlockHeaderTimestamp()` [8](#0-7) ), an attacker submitting ≥32 `ProposalCreateContract` transactions in the same block (or blocks sharing a timestamp) can trigger Java's `TimSort` "Comparison method violates its general contract!" `IllegalArgumentException` on every subsequent call to `getAllProposals()`, permanently breaking the public `listProposals` endpoint (both gRPC and HTTP) for all callers until the offending data is manually removed.

`GetProposalById` (`Wallet.getProposalById`) is unaffected — it is a direct keyed lookup [9](#0-8)  and does not invoke `getAllProposals`.

### Title
Unbounded/underpriced ProposalStore growth via fee-free ProposalCreateContract enables full-scan DoS and comparator-contract crash of the public listProposals endpoint - (File: chainbase/src/main/java/org/tron/core/store/ProposalStore.java)

### Summary
An attacker can self-register as a witness (no election required, just paying `AccountUpgradeCost`) and then flood the chain with fee-free (`calcFee()==0`) `ProposalCreateContract` transactions, growing `ProposalStore` unbounded. The public `listProposals`/`getProposalList` RPC performs a full store scan and sort on every call via `ProposalStore.getAllProposals()`, degrading with store size, and its comparator is contract-invalid, risking a permanent `IllegalArgumentException` crash of that endpoint once ≥32 proposals share the same `createTime`.

### Finding Description
`ProposalCreateActuator.validate()` only requires the sender to be a registered witness [1](#0-0) , and witness registration (`WitnessCreateActuator`) is open to any funded account with no election/SR requirement [10](#0-9) . `ProposalCreateActuator.calcFee()` returns `0` [3](#0-2) , so proposal creation carries no cost beyond ordinary transaction bandwidth/energy, and there is no cap on the number of proposals a witness may create nor pruning of old entries from `ProposalStore`. The public read path (`ListProposals` gRPC [11](#0-10)  and `/wallet/listproposals` HTTP servlet [12](#0-11) ) calls `Wallet.getProposalList()` → `ProposalStore.getAllProposals()`, which iterates and sorts the *entire* store on every request with no pagination [6](#0-5) . The sort comparator additionally violates the `Comparator` contract for equal `createTime` values, which can throw at runtime for sufficiently large equal-valued batches (Java's `TimSort` validates comparator consistency for arrays ≥32 elements).

### Impact Explanation
Growing `ProposalStore` costs the attacker only ordinary per-transaction bandwidth/energy plus a one-time witness-registration fee, while imposing a recurring, store-size-proportional cost on every caller of the public `listProposals` endpoint on every full node — degrading node responsiveness for all users. In the comparator-violation scenario, the endpoint can be made to throw unhandled exceptions permanently (denial of service) since the malformed data persists in the revoking DB and is re-sorted on every call.

### Likelihood Explanation
Feasible and repeatable by anyone able to fund a single `WitnessCreateContract` (cost = `AccountUpgradeCost`, a fixed, not-large dynamic parameter) and then broadcast arbitrarily many fee-free `ProposalCreateContract` transactions with distinct dummy parameter maps. No governance, election, or privileged access is needed.

### Recommendation
- Add pagination/limits to `getAllProposals()`/`getProposalList()` mirroring the existing `getPaginatedProposalList` bound (`PROPOSAL_COUNT_LIMIT_MAX`), or cap total live proposals per witness/globally.
- Fix the comparator in `ProposalStore.getAllProposals()`/`getSpecifiedProposals()` to be contract-compliant, e.g. `Long.compare(b.getCreateTime(), a.getCreateTime())`.
- Consider pruning/archiving expired or processed proposals from `ProposalStore` instead of retaining them indefinitely.

### Proof of Concept
```java
// Integration-style test targeting ProposalStore directly
@Test
public void testGetAllProposalsThrowsOnDuplicateCreateTime() {
  ProposalStore proposalStore = chainBaseManager.getProposalStore();
  long sharedCreateTime = 1_000_000L;
  for (int i = 1; i <= 40; i++) { // >=32 to trigger TimSort validation
    Protocol.Proposal proto = Protocol.Proposal.newBuilder()
        .setProposalId(i)
        .putParameters(0, i) // distinct dummy parameter values
        .setCreateTime(sharedCreateTime) // identical createTime, as would occur
                                          // for proposals created in the same block
        .build();
    proposalStore.put(ByteArray.fromLong(i), new ProposalCapsule(proto));
  }
  // Expect: either a super-linear latency blow-up as size grows (load-test variant),
  // or (with identical createTime) an IllegalArgumentException:
  // "Comparison method violates its general contract!"
  assertThrows(IllegalArgumentException.class, proposalStore::getAllProposals);
}
```
Load-test variant: repeatedly call `Wallet.getProposalList()` (or hit `/wallet/listproposals`) while incrementally inserting proposals with varying `createTime`, asserting call latency grows linearly/super-linearly with store size, demonstrating the unbounded full-scan cost with zero offsetting fee from `ProposalCreateActuator.calcFee()`.
