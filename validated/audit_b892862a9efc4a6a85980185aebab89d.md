### Title
Unbounded, lock-held single-pass sweep of the full-snapshot gap in `sweep_slots_after_snapshot` can cause a disproportionate CPU/lock-contention burst on the AccountsBackgroundService thread - (File: accounts-db/src/accounts_db.rs)

### Summary
`sweep_slots_after_snapshot` re-examines every slot in the range `[last_swept_full_snapshot_slot + 1, latest_full_snapshot_slot]` in a single synchronous loop each time `clean_accounts` runs, holding the `shrink_candidate_slots` lock for the whole scan. [1](#0-0) 
If the gap between the previously-swept full-snapshot slot and the newly-advanced `latest_full_snapshot_slot` becomes large (e.g. full-snapshot interval increases, snapshot generation/archiving slows down, or a node is restarted/rejoins after a long full-snapshot cadence gap), the very next `clean_accounts` call must process the entire backlog of slots at once with no throttling, batching, or incremental catch-up mechanism.

### Finding Description
This is directly analogous to the reported bug class: a period during which state updates are effectively "paused" (here, the sweep only advances when a full snapshot completes, and `last_swept_full_snapshot_slot` only moves forward inside this function) followed by an unthrottled processing of the entire backlog once the trigger fires, with no grace period or incremental catch-up. The function itself documents that it walks the full inclusive range every time it triggers: [2](#0-1) 
The comment on the lock explicitly states the assumption that this only ever runs from earlier/later phases of the same `AccountsBackgroundService` iteration, never concurrently with `clean_accounts`, meaning this is a serial, blocking operation on the single ABS thread that also performs `clean_accounts`, `shrink_candidate_slots`, and snapshot-request handling: [3](#0-2) 
The ABS main loop is rate-limited only for how often it *starts* a cycle (`MIN_LOOP_INTERVAL`, `CLEAN_INTERVAL`, `SHRINK_INTERVAL`); there is no mechanism to cap or spread out the amount of work done once `sweep_slots_after_snapshot`'s range becomes large — unlike, for example, the deliberate rate limiting comments elsewhere in this file for cleaning cadence. [4](#0-3) 

### Impact Explanation
A sudden, unthrottled processing burst on the AccountsBackgroundService thread increases the risk of the ABS thread falling further behind on `clean_accounts`/`shrink_candidate_slots` for the root bank, since this same thread also handles pending-snapshot-package requests and pruned-bank cleanup. Because `sweep_slots_after_snapshot` holds the `shrink_candidate_slots` lock for the full duration of the sweep, other logic (or tests, given the documented invariant) that also needs the lock is blocked for the entire pass, creating a disproportionate, un-bounded CPU/lock-hold cost proportional to the size of the un-swept gap — mirroring the "root cause is a temporary freeze, but the effect is a burst that users/subsystems cannot react to" reasoning accepted in the referenced report.

### Likelihood Explanation
Likelihood depends on how large the gap between `last_swept_full_snapshot_slot` and `latest_full_snapshot_slot` can realistically grow (e.g. full snapshot interval misconfiguration, snapshot archiving falling behind, or catching up after being offline). I was not able to fully verify, within the available context, the exact production bound on this gap or whether other safeguards elsewhere in the snapshot-request pipeline already prevent it from growing large, so likelihood should be treated as uncertain/moderate rather than confirmed.

### Recommendation
Bound or chunk the sweep in `sweep_slots_after_snapshot` (e.g., process at most N slots per `clean_accounts` invocation, persisting progress via `last_swept_full_snapshot_slot`) so a large backlog is spread across multiple ABS iterations instead of being processed synchronously in one lock-held pass, analogous to adding a "grace period"/incremental catch-up instead of an instantaneous full-backlog flush.

### Proof of Concept
Not independently reproduced; based on static analysis of `sweep_slots_after_snapshot` and the single-threaded `AccountsBackgroundService` loop shown above. A concrete PoC would require constructing a scenario where `latest_full_snapshot_slot` advances by a very large slot delta between two `clean_accounts` calls (e.g., via delayed/batched full-snapshot completion) and measuring ABS loop stall duration during the resulting sweep.

    /// Loop through slots in `[last_swept_full_snapshot_slot + 1, latest_full_snapshot_slot]` and
    /// re-examine each storage now that a full snapshot has advanced past its slot:
    /// 1) if it holds only tombstones, purge it directly; or
    /// 2) if its dead zero-lamport accounts made it shrinkable, add it to the shrink candidates.
    ///
    /// Advances `last_swept_full_snapshot_slot` to `latest_full_snapshot_slot` on completion.
    ///
    /// Returns the count of storages that were added to the shrink candidates set.
    fn sweep_slots_after_snapshot(
        &self,
        last_swept_full_snapshot_slot: Slot,
        latest_full_snapshot_slot: Slot,
    ) -> u64 {
        let start = last_swept_full_snapshot_slot.saturating_add(1);

        let mut added_to_shrink_count = 0;
        {
            // Held for the scan. Safe because the only paths that take this lock in production
            // validator code run in earlier/later phases of the same AccountsBackgroundService
            // iteration, never concurrently with clean_accounts.
            let mut shrink_candidates = self.shrink_candidate_slots.lock().unwrap();
            for slot in start..=latest_full_snapshot_slot {
                if let Some(store) = self.storage.get_slot_storage_entry(slot) {
                    if store.has_only_tombstones() {
                        // Now just contains tombstones and no live index entries: purge
                        self.purge_dead_slots_from_storage(
                            iter::once(&slot),
                            &self.clean_accounts_stats.purge_stats,
                        );
                    } else if self.is_shrinking_productive(&store)
                        && self.is_candidate_for_shrink(&store)
                        && shrink_candidates.insert(slot)
                    {
                        added_to_shrink_count += 1;
                    }
                }
            }
        }

        self.last_swept_full_snapshot_slot
            .store(latest_full_snapshot_slot, Ordering::Relaxed);
        added_to_shrink_count
    }
