### Title
Permanently burnt funds when `DeleteAccount`'s `beneficiary_id` does not exist on-chain - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`DeleteAccount` only validates that `beneficiary_id` is a syntactically valid `AccountId`, never that the account actually exists. When the beneficiary account is missing (never created, previously deleted, mistyped, or simply an account the signer no longer controls — the on-chain analog of an "unreachable/blacklisted" recipient in the original report), the account's remaining balance is routed into a system refund receipt that is guaranteed to fail and whose deposit is then permanently burnt, rather than returned to the (now-deleted) owner.

### Finding Description
`validate_delete_action` only checks the syntactic validity of `beneficiary_id`, not its existence: [1](#0-0) 

At execution time, `action_delete_account` unconditionally sends the account's remaining balance to `beneficiary_id` via a system balance-refund receipt, deletes the account, and returns success — there is no check that `beneficiary_id` exists before the account is destroyed: [2](#0-1) 

When that refund receipt is later processed, `check_account_existence` is invoked for the `Transfer` action. Because the receipt is system-generated (`is_refund: true`), `implicit_creation_allowed` unconditionally returns `false`, so a `Transfer` to a non-existent account always fails with `AccountDoesNotExist`: [3](#0-2) [4](#0-3) 

A test in the codebase explicitly documents that a refund receipt to a missing account fails and does not create it: [5](#0-4) 

The refund/burn semantics are documented: refund receipts are free, and if a refund receipt fails execution, its deposit is burnt rather than retried or returned: [6](#0-5) 

Combining these three facts:
1. `beneficiary_id` existence is never validated at submission time (only its syntax is validated).
2. The source account is deleted unconditionally in the same receipt, before the refund is even attempted.
3. If the beneficiary doesn't exist, the refund fails and the deposit is permanently burnt (protocol-documented behavior), with no retry and no path back to the original owner.

This is the direct nearcore analog of the reported bug class: a transaction signer (the account owner submitting `DeleteAccount`) loses all remaining funds irrecoverably because the intended recipient cannot receive the transfer — exactly the "recipient unreachable → permanently frozen/lost funds" pattern from the Solidity report, mapped onto NEAR's native token-transfer/refund mechanism instead of an ERC-20 blacklist.

### Impact Explanation
Any account balance moved out via `DeleteAccount` with a beneficiary that does not exist at execution time is permanently destroyed (burnt), not merely frozen — this is a direct, unauthorized value loss (effectively a deflationary event) that requires no validator or network misbehavior, only a single signed transaction from the account owner (or anyone who currently controls it) specifying a bogus/non-existent/future/typo'd `beneficiary_id`. Since large "remaining account balance" payouts can be significant, this can destroy arbitrary user funds. This satisfies the "permanently frozen/lost funds" acceptance criterion.

### Likelihood Explanation
The trigger requires nothing more than a single `DeleteAccount` action with a `beneficiary_id` that doesn't currently exist — trivially reachable by any account owner (intentionally or accidentally: typo, account not yet created, or an account that was deleted between transaction construction and execution). No special privilege, validator collusion, or network condition is needed, making this readily reachable through the normal transaction/action-validation and runtime-apply path.

### Recommendation
Before allowing `DeleteAccount` to proceed (or before generating the balance-refund receipt), verify that `beneficiary_id` corresponds to an existing account, or defer the deletion of the source account until the beneficiary refund receipt has been confirmed to succeed. Alternatively, allow "refund" transfer receipts targeting non-existent named/implicit accounts to fall back to creating the account (similar to non-refund transfers) instead of unconditionally burning the deposit, at least when the failure is specifically `AccountDoesNotExist` on a `DeleteAccount` beneficiary refund.

### Proof of Concept
1. Account `alice.near` holds balance `B`.
2. `alice.near` submits `DeleteAccount { beneficiary_id: "nonexistent.near" }` where `nonexistent.near` has never been created.
3. `action_delete_account` deletes `alice.near` immediately and enqueues `Receipt::new_balance_refund("nonexistent.near", B)`.
4. During execution of that refund receipt, `check_account_existence` sees `account.is_none()` and `is_refund == true`, so `implicit_creation_allowed` returns `false`, producing `ActionErrorKind::AccountDoesNotExist`.
5. Per `docs/RuntimeSpec/Refunds.md`, "If the execution of a refund fails, the refund amount is burnt" — balance `B` is permanently destroyed; `alice.near` no longer exists, so there is no account left to receive or reclaim the funds. [7](#0-6) [1](#0-0) [8](#0-7)

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

# Refunds

When execution of a receipt fails or there is some unused amount of prepaid gas left after a function call, the Runtime generates refund receipts.

The are 2 types of refunds:

- Refunds for the failed receipt for attached deposits. Let's call them **deposit refunds**.
- Refunds for the unused gas and fees. Let's call them **gas refunds**.

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
