### Title
Exchange pool balance corruption via floating-point precision drift in `ExchangeProcessor` causes pools to become permanently unusable ("the exchange has been closed") - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The default (non-hardened) `ExchangeProcessor` implements the Bancor-style constant-relay AMM formula using Java `double` arithmetic and `Math.pow`. Every call to `ExchangeTransactionActuator`, `ExchangeInjectActuator`, or `ExchangeWithdrawActuator` re-derives new pool reserves through this floating-point math, which accumulates rounding error on every trade. Because there is no invariant check that both reserves stay balanced/positive in the legacy path (only the hardened path added later checks this), repeated trading can drift one side of the pool toward zero. Once either reserve reaches 0, all three actuators explicitly reject further activity with `"Token balance in exchange is equal with 0, the exchange has been closed"`, permanently freezing the pool for new trades/injections/withdrawals — matching the externally reported symptom of pools becoming "unavailable" after continuous use.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` perform the AMM math with `double` and `Maths.pow`, storing results back with `(long) issuedSupply` / `(long) exchangeBalance` truncation [1](#0-0) . `ExchangeCapsule.transaction()` calls this legacy processor whenever `hardenedCalc` is false, and only in the hardened branch does it validate `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` [2](#0-1) . `hardenedCalc` is controlled by `AbstractExchangeActuator.allowHarden()`, which reads `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()` [3](#0-2)  — a chain-governance proposal flag that must be explicitly activated; the legacy floating-point path remains the default until then. `ExchangeTransactionActuator` invokes `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` from any anonymous broadcast transaction [4](#0-3) . Once a reserve is driven to zero by accumulated rounding error, `ExchangeTransactionActuator.doValidate`, `ExchangeWithdrawActuator.doValidate`, and related actuators all reject the transaction with `"Token balance in exchange is equal with 0, the exchange has been closed"` [5](#0-4) [6](#0-5) , permanently disabling the pool for all users — matching the report's "pools become unavailable" behavior, except here it is triggered by ordinary trading activity rather than an external time-based mechanism.

### Impact Explanation
Any TRX/TRC10 exchange pool created via `ExchangeCreateActuator` can be driven to permanent unavailability through repeated legitimate or adversarial trades, since the floating-point drift is deterministic and can be steered by an attacker choosing trade sizes/ordering. This results in denial of service for a market-making primitive (funds already injected become effectively stuck/unusable for trading, and the pool is bricked for all participants), consistent with the "accounting corruption / DoS" acceptance criteria.

### Likelihood Explanation
The bug is triggered purely by calling standard, unprivileged `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions — no special privileges, keys, or node compromise required. It requires the hardened-calculation proposal to not yet be activated on the target network; if the proposal (`allowHardenExchangeCalculation`) has already been activated on mainnet, this specific legacy path is already mitigated. I could not confirm from the code alone whether this proposal is currently active on the deployed chain(s) this repo represents — that requires checking on-chain proposal state, which is outside the scope of static code review.

### Recommendation
Ensure `allowHardenExchangeCalculation` (and the accompanying `SafeExchangeProcessor`/`ExchangeCapsule` invariant checks) is activated by default (or hard-enabled outright rather than left as an optional governance proposal), so that all exchange balance mutations use the BigDecimal-based, invariant-checked hardened path rather than the legacy `double`-based `ExchangeProcessor`.

### Proof of Concept
Not independently reproduced in this review; conceptually: repeatedly call `ExchangeTransactionActuator` (or `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) against a freshly created exchange pool with `allowHardenExchangeCalculation` disabled (default), choosing sell quantities/token sides to bias floating-point rounding in one direction, until `getFirstTokenBalance()`/`getSecondTokenBalance()` reaches 0 and subsequent transactions fail with `"the exchange has been closed"`, as exercised by the project's own hardened-mode regression tests (e.g. `ExchangeProcessorTest.testStrictMath`, `ExchangeCapsuleTest.testHardenedTransactionNegativeBalanceThrows`) [7](#0-6) [8](#0-7) .

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
