## Finding: Non-deterministic, wall-clock-based cancellation timelock for L1 handler transactions

The report's bug class — a time-sensitive state transition gated on a mutable, attacker-influenceable/racy time source (`block.timestamp` in the Solidity report) — maps to the Starknet sequencer's L1-handler cancellation logic in `apollo_l1_events`.

### Root cause

`TransactionRecord::update_time_based_state` transitions a pending L1 handler transaction to `CancelledOnL2` once `unix_now >= requested_at + cancellation_timelock`: [1](#0-0) 

Crucially, `unix_now` is **not** the deterministic, committed L2 block timestamp — it is each node's own local wall-clock reading, taken independently by the proposer when building a proposal and by every validator when validating it: [2](#0-1) [3](#0-2) 

The cancellation is triggered by an `Event::TransactionCancellationStarted`, which originates from an **L1 message sender** calling the L1 bridge/core-contract cancellation-start function — an unprivileged, externally reachable action: [4](#0-3) 

### Why this diverges from the intended, deterministic design

Everywhere else in this codebase, time-based consensus validity checks are deliberately pinned to the **agreed block timestamp** with an explicit tolerance window, e.g. `is_proposal_init_valid` bounds `init_proposed.timestamp` against `now` and rejects if it drifts too far: [5](#0-4) 

By contrast, the L1-handler cancellation-timelock check uses each node's independent `clock.unix_now()` with **no shared reference and no tolerance window**, so the same underlying transaction can legitimately evaluate to different `ValidationStatus` results (`Validated` vs `Invalid(CancelledOnL2)`) on different honest nodes purely due to normal network propagation delay around the timelock boundary. The test suite even documents the sharp edge behavior (`validate_tx_cancellation_requested_validated_then_expired_returns_cancelled`), confirming the same tx flips status purely based on when `validate` happens to be called: [6](#0-5) 

### Impact

An L1 message sender can time a `TransactionCancellationStarted` request so that its propagation lands near the `l1_handler_cancellation_timelock_seconds` boundary. A proposer node whose local clock is slightly behind will still see the tx as `Pending`/valid and include it in a proposal (`get_txs`), while honest validator nodes whose local clocks are slightly ahead (due to normal clock skew/network latency) will see the same tx as `CancelledOnL2` during `validate()`, causing them to reject the proposal (`ProposalFinMismatch`), forcing a consensus round change. Because this depends only on ordinary clock drift/latency around a boundary the attacker controls (by choosing when to submit the L1 cancellation), it can be repeated to induce honest-node validation divergence and repeated round failures — degrading the network's ability to confirm new blocks/transactions, without requiring any privileged, malicious-operator, or malicious-proposer behavior. [7](#0-6) 

### Recommendation

Replace `self.clock.unix_now()` in `get_txs`/`validate` (and the analogous consumption/proposal-cooldown timelocks) with a value derived from the shared/committed block timestamp (as is already done for `ProposalInit` timestamp validation), or add an explicit agreed tolerance margin so all honest nodes evaluating the same height reach the same cancellation/consumption/cooldown timelock verdict regardless of local wall-clock skew.

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }

fn validate_tx_cancellation_requested_validated_then_expired_returns_cancelled() {
    // Setup.
    let tx_1 = l1_handler(1);
    let clock = Arc::new(FakeClock::new(5));
    let mut l1_events_provider = L1EventsProviderContentBuilder::new()
        .with_clock(clock.clone())
        .with_nonzero_timelock_setup()
        .with_cancel_requested_txs([tx_1.clone()])
        .with_state(ProviderState::Validate)
        .build_into_l1_provider();

    // Test.

    // Should be validatable before expiry,
    let status =
        l1_events_provider.validate(tx_1.tx_hash, l1_events_provider.current_height).unwrap();
    assert_eq!(status, ValidationStatus::Validated);
    // Now, advance time past expiry and validate again,
    // This tests the edge case: a tx can be validatable before expiry, but if validated again after
    // expiry, it should return the cancellation error.
    clock.advance(Duration::from_secs(
        l1_events_provider.config.l1_handler_cancellation_timelock_seconds.as_secs(),
    ));
    let status2 =
        l1_events_provider.validate(tx_1.tx_hash, l1_events_provider.current_height).unwrap();
    assert_eq!(status2, InvalidValidationStatus::CancelledOnL2.into());
}
