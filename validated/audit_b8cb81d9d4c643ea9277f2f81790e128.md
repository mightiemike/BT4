### Title
Front-running account creation via TransferContract/TransferAssetContract permanently blocks intended AccountType assignment - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java`)

### Summary
`TransferActuator.execute` silently creates a recipient account with `AccountType.Normal` whenever a `TransferContract` targets an address that does not yet have an account, mirroring Cosmos SDK's `SendCoins` auto-account-creation behavior referenced in the SEDA report. `CreateAccountActuator.validate` rejects `AccountCreateContract` if the target address already has an account. Because account records cannot be deleted, an attacker can front-run a legitimate `AccountCreateContract` transaction with a cheap `TransferContract` (or `TransferAssetContract`) to the same target address, permanently preventing that address from being created via `AccountCreateContract` with any non-default `AccountType`.

### Finding Description
`TransferActuator.execute` auto-creates the recipient account when it doesn't exist yet, always with `AccountType.Normal`: [1](#0-0) 

`TransferAssetActuator` has the same implicit account-creation behavior for the recipient, confirmed by its `validate()` accounting for the account creation fee when `toAccount == null`: [2](#0-1) 

`CreateAccountActuator.validate` rejects the creation if the target `accountAddress` already exists in the `AccountStore`: [3](#0-2) 

This is proven by the actuator's own unit test, which asserts the exact `"Account has existed"` validation failure once the target address already has an account record: [4](#0-3) 

There is no path in java-tron to delete an `AccountCapsule` from the `AccountStore` once created, so this block is permanent, exactly matching the "recipient permanently blocked" impact in the SEDA report.

### Impact Explanation
Any unprivileged user can observe a pending `AccountCreateContract` transaction (mempool/broadcast) targeting a specific address (e.g., intended to be typed via `AccountCreateContract.setType(...)`), and front-run it with a low-fee `TransferContract` sending a minimal amount of TRX to that address. This causes the recipient account to be created first as plain `AccountType.Normal`, which then makes any subsequent `AccountCreateContract` for that address permanently fail validation with `"Account has existed"`. Since account deletion is not supported, the victim's address is permanently denied the ability to be created through `AccountCreateContract` with the account-holder's originally intended type/name/permission setup — a denial-of-service/griefing outcome on account provisioning, analogous to the SEDA vesting-account blocking issue but scoped to `AccountCreateContract`'s account-type/name assignment rather than fund-locking semantics.

### Likelihood Explanation
The attack requires only a standard `TransferContract` (or `TransferAssetContract`) transaction with trivial fee/amount, no privileged role, and no special preconditions beyond knowing the target address in advance (visible once the victim's `AccountCreateContract` transaction is broadcast/pending, or if the address is otherwise predictable, e.g., a vanity/deterministic address). This makes it straightforward for any unprivileged actor to execute.

### Recommendation
Consider changing `CreateAccountActuator` semantics to allow "upgrading"/setting the account type and metadata (name, permissions) on an existing but not-yet-explicitly-created account (i.e., one that was implicitly created only via `Transfer`/`TransferAsset` with `AccountType.Normal` and default fields), rather than unconditionally rejecting `AccountCreateContract` whenever any account record exists for the address. Alternatively, track whether an account was implicitly created (as a placeholder) versus explicitly created, and only reject `AccountCreateContract` for explicitly-created accounts.

### Proof of Concept
1. Victim broadcasts an `AccountCreateContract` transaction (`CreateAccountActuator`) intending to create address `X` (e.g., with a specific `AccountName`/`AccountType`).
2. Attacker observes address `X` in the pending transaction and immediately broadcasts a `TransferContract` sending a minimal TRX amount from any funded account to `X`, with a higher fee/priority to get mined first.
3. `TransferActuator.execute` creates `X` as `AccountType.Normal` per [5](#0-4) .
4. The victim's original `AccountCreateContract` transaction is processed afterward; `CreateAccountActuator.validate` now finds `accountStore.has(accountAddress)` true and throws `"Account has existed"` per [3](#0-2) , permanently blocking the victim's intended account creation for address `X`.
