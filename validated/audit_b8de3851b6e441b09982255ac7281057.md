### Title
Wallet Contract fails to refund `CallerDeposit` in the faulty-relayer / address-registrar ban path, causing permanent loss of an external caller's attached deposit - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::address_check_callback` drops the `caller_deposit` argument when it detects a faulty relayer (the target's Ethereum address resolves to an already-registered account), routing execution to `create_ban_relayer_promise` / `ban_relayer` instead of `rlp_execute_callback`. Unlike every other failure path in this contract, `ban_relayer` never refunds the tracked `CallerDeposit`, so an external caller's attached NEAR deposit is permanently stuck in the wallet contract.

### Finding Description
The Near Ethereum-emulation Wallet Contract lets an external caller (a relayer, or any signer distinct from the wallet account) submit an RLP-encoded transaction along with an attached deposit. `CallerDeposit::new` records that predecessor's deposit specifically "to refund the caller's deposit if the cross-contract call fails" [1](#0-0) .

In the normal failure path, `rlp_execute_callback` checks `caller_deposit` and issues a transfer back to the caller when the downstream promise fails [2](#0-1) .

However, when the transaction is an `EOABaseTokenTransfer` with an `address_check`, `inner_rlp_execute` schedules `address_check_callback` with `caller_deposit` passed through [3](#0-2) . Inside `address_check_callback`, if the registrar lookup returns `Some(account_id)` (i.e., the target address unexpectedly maps to an existing named account — a "faulty relayer" condition) and the caller is the wallet itself, the code calls `create_ban_relayer_promise(current_account_id)`, which does **not** take or forward `caller_deposit` at all [4](#0-3) , [5](#0-4) .

The resulting `ban_relayer` callback also silently discards `caller_deposit`: [6](#0-5) 

Note that this "faulty relayer" branch is reached whenever `env::signer_account_id() == current_account_id`, i.e. whenever the wallet's own access key signed the transaction — this is exactly the case for a relayer using a `FunctionCallPermission` access key on the wallet, which is the intended primary use case for this contract per its own comments about "relayers with access keys." In that same branch, if the caller (predecessor) is an external account distinct from the wallet (e.g., a relayer paying gas via its own account while using an access key on the wallet, or any account calling `rlp_execute` with an attached deposit that ends up hitting the faulty-relayer condition), `CallerDeposit::new` will have recorded a non-`None` deposit, since it only excludes the case where `predecessor_account_id == current_account_id` [7](#0-6) . That deposit is then dropped for good, because `ban_relayer` never issues a transfer back to it.

This is analogous to the reported Solidity issue where one convenience code path (`depositMax`) fails to handle a payment mechanism (native ETH) that is correctly handled by the other, more general functions in the same contract family — here, one failure-handling path (`address_check_callback` → `ban_relayer`) fails to handle the caller-deposit refund mechanism that every other failure path (`rlp_execute_callback`) correctly implements.

### Impact Explanation
An external, unprivileged caller who attaches a NEAR deposit to `rlp_execute` (or a relayer using an access key attached with a deposit that reaches this specific faulty-relayer branch) can have that deposit become permanently unrecoverable — it remains locked in the wallet contract's account balance with no code path to return it to the caller. This is a concrete "permanently frozen funds" outcome for value that was contributed as part of a single submitted transaction/RPC call, matching the accepted impact criteria.

### Likelihood Explanation
The path is reachable purely through normal usage of the contract's `rlp_execute` entry point by any account with the ability to submit a transaction to the wallet contract with the RLP-encoded transaction targeting an eth-implicit-looking address that happens to already be a registered named account (a condition the audit report treats as an expected "faulty relayer" scenario that the contract already anticipates and explicitly handles by banning the relayer's key) — no special privilege beyond being able to call the contract is required.

### Recommendation
Thread `caller_deposit` through `create_ban_relayer_promise`/`ban_relayer` (mirroring `rlp_execute_callback`) and issue a transfer back to the `CallerDeposit.account_id` before returning the failure `ExecuteResponse`, exactly as is already done in the success/failure branches of `rlp_execute_callback`.

### Proof of Concept
1. Deploy the Wallet Contract and attach a `FunctionCallPermission` access key to it that is used by a relayer with a wallet-signed RLP transaction whose `to` field decodes to `target`.
2. Have an external account call `rlp_execute(target, tx_bytes_b64)` with a non-zero attached NEAR deposit, where `target` resolves (via the address registrar lookup) to an already-registered named account id, and where `env::signer_account_id() == current_account_id` (the access key path).
3. Execution enters `address_check_callback`; since `maybe_account_id.is_some()` and the signer equals the current account, `create_ban_relayer_promise` is invoked, dropping `caller_deposit`.
4. `ban_relayer` executes, sets `has_in_flight_tx = false`, and returns a failure `ExecuteResponse` — no transfer promise refunding the caller's deposit is ever created.
5. Compare against `test_caller_refunds` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:170-229` [8](#0-7) , which verifies refunds occur through `rlp_execute_callback`'s failure branch but has no equivalent coverage for the `ban_relayer` path, confirming the gap is untested and unhandled.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
