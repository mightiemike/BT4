### Title
Irrecoverable TRX loss via `Program.callToPrecompiledAddress` when endowment is charged before precompiled-contract execution result is known - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
When a TVM contract makes a `CALL`/`CALLCODE`/`DELEGATECALL` with a non-zero TRX value (`endowment`) to a Tron precompiled-contract address (e.g. `vote`, freeze/unfreeze, withdraw reward system contracts at fixed low addresses), `Program.callToPrecompiledAddress` moves the TRX from the caller to the precompiled-contract's context address *before* it knows whether the underlying precompiled logic will succeed. If the precompiled contract subsequently fails (`out.getLeft() == false`), the code only pushes `0` onto the EVM stack (mimicking a failed `CALL`) and refunds leftover energy — it never reverses the balance transfer that was already applied. This mirrors the reported bug class: value is moved as a side effect of a call whose failure is "tolerated" (treated like a normal failed external call, not a full revert), and the moved value has no way to come back to the sender.

### Finding Description
In `callToPrecompiledAddress`: [1](#0-0) 

The comment explicitly states the endowment transfer here is `"Charge for endowment - is not reversible by rollback"`, and it is executed via `MUtil.transfer`, which mutates account balances directly on the `deposit` repository: [2](#0-1) 

Immediately afterward, the precompiled contract is invoked, and its outcome is handled like this: [3](#0-2) 

On success (`out.getLeft() == true`), `deposit.commit()` is called, persisting the endowment transfer along with any other precompiled-contract state changes — expected behavior. On failure, however, the code does **not** call any explicit balance-reversal logic; it merely calls `refundEnergy(0, ...)`, pushes `0` on the stack (signaling "call failed" to the calling contract, exactly like a normal failed `CALL` opcode result), and optionally re-throws an exception. Per the comment, the endowment charge is *not* undone by any later rollback of the `deposit` repository child. This is the direct structural analog to the C4 finding: a value-bearing external invocation is wrapped in "tolerant" failure handling (there, a `try/catch`; here, a boolean success flag treated as a soft failure) that lets the outer call continue/return normally while the already-moved value is stranded at the destination, which — being a fixed precompiled-contract address rather than a normal account — has no mechanism to spend or return the TRX.

### Impact Explanation
Any user can deploy or invoke a smart contract that performs a value-bearing `CALL` (or `CALLCODE`/`DELEGATECALL`) to one of Tron's built-in precompiled-contract addresses (vote, freeze/unfreeze/withdraw system contracts) with a call value. If the precompiled contract's business logic rejects the call (e.g., insufficient parameters, invalid vote target, unmet preconditions) after the endowment has already been charged, the TRX is transferred out of the caller's context and credited to the fixed precompiled address, which cannot spend, forward, or return it. This results in a irrecoverable loss of TRX for the calling contract/user, entirely from a normal transaction broadcast through the standard `TriggerSmartContract` path — no privileged actor or leaked key is required.

### Likelihood Explanation
The path is reachable by any externally submitted `TriggerSmartContract` transaction that causes a Solidity-level `.call.value(x)(...)` (or equivalent low-level call) to target a precompiled-contract address. Triggering a failure condition inside the precompiled contract logic after the endowment stage is straightforward (e.g., malformed vote data, invalid target, business-rule rejection), making this practically triggerable by an ordinary user, intentionally or accidentally.

### Recommendation
In `Program.callToPrecompiledAddress`, defer or guard the endowment transfer so that it is only finalized once `contract.execute(data)` reports success, or explicitly reverse the endowment transfer (`MUtil.transfer` back to `senderAddress`) in the failure branch (`out.getLeft() == false`) before pushing `0` onto the stack, ensuring TRX charged for a value-bearing call to a precompiled contract is never left stranded when that call ultimately fails.

### Proof of Concept
Could not be fully validated with a live PoC transaction/test run within this investigation; validation would require exercising `callToPrecompiledAddress` end-to-end (e.g., via `TvmTestUtils.triggerContractAndReturnTvmTestResult`) with a Solidity contract that does `precompiledVoteAddress.call.value(N)(invalidVoteCalldata)`, then asserting that (a) the call returns `0` (failure) on the outer stack, and (b) the caller's balance has still decreased by `N` while the precompiled address's balance increased by `N`, demonstrating the fund loss. This is based on direct code reading of `Program.java` lines 1701–1755 and the explicit "not reversible by rollback" comment; a background Devin session with repo/test execution access would be needed to run and confirm this scenario concretely.
