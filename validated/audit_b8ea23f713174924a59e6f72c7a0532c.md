### Title
Replay-verify accepts state-root divergence as a valid replay because `ensure_match_transaction_info` never checks `state_checkpoint_hash` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness gate used by the mainnet-archive replay-verification tooling (`storage/db-tool/src/replay_on_archive.rs`) and by `aptos-debugger`/`aptos-move/cli` to confirm that locally re-executed transactions produced the exact same result as the one committed and authenticated on-chain. The function checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event-root hash, but it never compares `TransactionInfo::state_checkpoint_hash()` (nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against the recomputed checkpoint root. This is called out directly in a TODO left in the function itself.

### Finding Description
`ensure_match_transaction_info` in [2](#0-1)  performs these checks in order:
- transaction status equality
- gas used equality
- `write_set_hash == txn_info.state_change_hash()`
- `event_root_hash == txn_info.event_root_hash()`

It never reads `txn_info.state_checkpoint_hash()` or the hot-state/position-state checkpoint hash fields at all, and the function comment states explicitly: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [3](#0-2) .

This function is the exact and only correctness check used by the replay-verify pipeline: `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes transactions read from a backup/archive, and calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))`, treating an `Ok` result as proof the replay matched the archived, signed ledger state [4](#0-3) . The `state_checkpoint_hash` field on `TransactionInfo` is precisely the Merkle root binding the entire global state after the transaction (it is what gets folded into the transaction-accumulator leaf and, transitively, the validator-signed `LedgerInfo`); the `write_set_hash` only commits to the individual transaction's own write set, not the cumulative state.

Because `write_set_hash` only reflects the isolated write ops emitted by a single transaction, a bug that corrupts how earlier transactions' writes are folded into the global JMT/state-checkpoint (e.g., in `DoStateCheckpoint`, `update_with_memorized_reads`, hot-state promotion, or trading-native position state roots) can leave every individual transaction's write set byte-identical to the archived expectation while the resulting global state root silently diverges. `ensure_match_transaction_info` would still return `Ok`, since it structurally cannot detect this class of divergence.

### Impact Explanation
This breaks the state-integrity guarantee that "authenticated" replay/verification tooling must reject any locally computed ledger state that does not match the state actually authenticated (signed) on mainnet. The replay-verify job (`testsuite/replay-verify`) is the primary safety net used to detect state-divergence/hard-fork bugs against real mainnet/testnet archives before or after a release. A root-cause bug in checkpoint/state-root computation (VM, executor, or storage-layer) that nonetheless preserves the same write set per-transaction would pass replay-verify undetected, giving false confidence that a new node/execution version reproduces the authenticated chain state, when in fact its global state root has already diverged — a hard-fork-class defect masked by the CI safety net meant to catch exactly this. This is a high-severity gap in the ledger's proof-of-correctness tooling rather than a live-exploit against committed data, but it directly compromises "proof and storage pivot" invariants for replay/verification paths called out in scope.

### Likelihood Explanation
The gap is unconditionally present (not feature-gated) for every call to `ensure_match_transaction_info`; the comment in the source confirms the authors are already aware the check is incomplete for `position_state_checkpoint_hash` under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, but the same missing coverage applies equally to the baseline `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields for ordinary state-checkpoint transactions, which are far more commonly exercised (every block boundary/epilogue). Any latent bug in state-checkpoint/root computation that doesn't also corrupt individual write sets will silently pass replay-verify.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` (when present on the `TransactionInfo`) against the recomputed checkpoint root(s) for that transaction, and thread the recomputed checkpoint hash into all call sites (`replay_on_archive.rs`, `aptos_debugger.rs`, `aptos-move/cli`, and the chunk-executor's `verify_execution`) so replay/verification cannot report success while the global state root diverges.

### Proof of Concept
1. Introduce (or imagine) a bug confined to state-checkpoint root computation (e.g., in `DoStateCheckpoint::run` or JMT commit ordering) that leaves per-transaction write sets unchanged but alters the resulting global state root.
2. Run `db-tool replay-on-archive` against an archived range containing that transaction: `execute_and_verify` re-executes it, computes `write_set_hash`/`event_root_hash` identical to the archive, calls `ensure_match_transaction_info`, and receives `Ok(())`.
3. The tool reports the range as successfully verified even though the recomputed `state_checkpoint_hash` (not checked) differs from `expected_txn_infos[idx].state_checkpoint_hash()`, hiding a real ledger-state divergence. [2](#0-1) [4](#0-3)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
