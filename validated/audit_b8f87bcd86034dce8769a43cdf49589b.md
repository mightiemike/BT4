I found a direct analog in the NEAR Wallet Contract (`near-wallet-contract`), which is explicitly named as an in-scope reachable surface. The bug class matches: a `#[payable]` entry point accepts an attached deposit, but several failure paths silently absorb that deposit into the contract's account balance without refunding the depositor, and — critically — because these failures are returned as *successful* function-call results (an `ExecuteResponse{success:false}` value) rather than actual receipt failures, NEAR's native automatic deposit-refund-on-failure mechanism never triggers either.

### Title
Wallet Contract absorbs external caller's attached deposit with no refund on certain `rlp_execute` failure paths - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is a `#[payable]` method that any account can call with an attached NEAR deposit [1](#0-0) . The contract tracks external deposits via `CallerDeposit` so they can be refunded if the resulting cross-contract action fails [2](#0-1) , and this refund is correctly performed in `rlp_execute_callback` when a promise was actually created and later fails [3](#0-2) . However, several earlier exit points return an error/failure `ExecuteResponse` value directly, without ever creating the deferred transfer back to the caller, and without failing the receipt (so NEAR's protocol-level automatic deposit refund never applies either).

### Finding Description
Two categories of leak exist:

1. **Pre-promise validation failures in `inner_rlp_execute`.** `CallerDeposit::new` captures the attached deposit as soon as `rlp_execute` starts executing [4](#0-3) . If RLP/transaction parsing then fails (bad signature, wrong nonce, invalid chain id, etc.), `inner_rlp_execute` returns `Err(...)` before any `Promise` is built [5](#0-4) . Back in `rlp_execute`, this becomes `Err(e) => PromiseOrValue::Value(e.into())` [6](#0-5) , i.e. the *function call itself succeeds* and simply returns a JSON value describing failure. `caller_deposit` is dropped with no refund promise ever scheduled.

2. **`address_check_callback` "existing named account" branch.** When the address-registrar lookup indicates the target address collides with an existing named account, and the caller is *not* using the wallet's own access key (`env::signer_account_id() != current_account_id` — i.e., an ordinary external caller who attached a deposit), the callback returns a failure value directly and never touches `caller_deposit`: [7](#0-6) 

Because NEAR's protocol-level "deposit refund on receipt failure" only fires when the *receipt itself* fails (see `docs/RuntimeSpec/Refunds.md`) [8](#0-7) , and here the receipt succeeds (it just returns a value indicating logical failure), the attached deposit is permanently merged into the Wallet Contract account's own NEAR balance. This mirrors the reported Solidity issue exactly: a payable entry point accepts value, an error path is reached, and there is no code path that returns/refunds the caller's contribution — the value is absorbed by the contract with no sweep/refund mechanism for that specific case, even though the contract's own design (`CallerDeposit`, `test_caller_refunds`) demonstrates refunding externally-attached deposits on failure is the intended invariant [9](#0-8) .

### Impact Explanation
Any unprivileged account can call `rlp_execute` directly (it is a public `#[payable]` method, reachable by any transaction signer) and attach a deposit. By submitting an intentionally malformed/invalid RLP transaction (case 1) or by targeting an address that collides with a registered named account while calling without the wallet's access key (case 2), the caller's attached NEAR is absorbed into the target Wallet Contract's balance instead of being refunded, in violation of the contract's own documented and tested refund invariant. This is unauthorized value movement from the caller to the wallet-contract-holding account, and from the caller's perspective the funds are unrecoverable (the caller holds no key over the destination account).

### Likelihood Explanation
High reachability: `rlp_execute` is the sole public entry point of the Wallet Contract and is designed to be called by arbitrary relayers/callers on behalf of ETH-implicit accounts [10](#0-9) . Triggering an RLP parse failure or targeting a colliding named account are both fully attacker-controlled and require no special privileges, only a normal signed transaction with an attached deposit.

### Recommendation
Ensure `CallerDeposit` is refunded (or the deposit is never merged past a validation check) on every failure path, including:
- All `Err(...)` returns from `inner_rlp_execute` that occur after `CallerDeposit::new` has captured a non-zero deposit but before a promise is scheduled — issue an explicit `Promise::new(caller).transfer(...)` before returning the error value.
- The "existing named account_id" branch of `address_check_callback` when the caller is external — refund `caller_deposit` there just as `rlp_execute_callback` does on `PromiseResult::Failed`.

### Proof of Concept
1. Caller (any account, not holding the wallet's access key) calls `wallet_account.rlp_execute(target, tx_bytes_b64)` attaching `N` yoctoNEAR, where `tx_bytes_b64` is either (a) malformed/invalid (bad signature or wrong nonce) so `inner_rlp_execute` returns `Err` before creating a promise, or (b) a valid `EOABaseTokenTransfer` whose `to` address happens to collide with an address already registered to a named account in the address registrar.
2. For (a): `rlp_execute` immediately returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})` — the receipt succeeds, `N` yoctoNEAR remains credited to the wallet account, `caller_deposit` is discarded.
3. For (b): execution proceeds to `address_check_callback`; since the caller used their own signer (not the wallet's access key), the `else` branch fires and returns a failure value directly, again discarding `caller_deposit` without any transfer back to the caller.
4. In both cases, querying the caller's account balance afterward shows a loss of `N` yoctoNEAR beyond gas costs, and the funds now sit in the wallet contract's balance with no protocol-level or contract-level path back to the caller.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
