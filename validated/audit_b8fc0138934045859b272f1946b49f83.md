### Title
Meta-transaction sender can pocket relayer-funded deposit refunds via `DelegateAction` failure — (File: `runtime/runtime/src/actions.rs`)

### Summary
In `apply_delegate_action`, a relayer submits and fully pays for a `DelegateAction` on behalf of a `sender_id` (the meta-transaction author). All attached deposits and gas costs for the inner actions are charged to the relayer's account when the outer transaction is converted to a receipt, but the resulting inner-action receipt is created with `predecessor_id: sender_id.clone()` [3](#0-2) . Because balance/deposit refunds for a failed receipt are always sent to `receipt.balance_refund_receiver()`, which defaults to `predecessor_id()` [4](#0-3) , the sender — not the relayer who actually funded the deposit — receives the refund whenever the inner action fails on the receiver's shard.

### Finding Description
`total_deposit` explicitly documents this design: "Relayer pays the deposit but if actions fail, the deposit is refunded to Sender of DelegateAction" [5](#0-4) . The comment inside `apply_delegate_action` reiterates: "Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit" [1](#0-0) .

This is directly analogous to the Gitcoin `_grantAddress` bug: a value-transfer parameter (here, the receipt's implicit "who pays / who gets refunded" identity) is bound to a party (`sender_id`, chosen and signed off-chain by the untrusted meta-tx author) that does not correspond to the party who actually supplied the funds (the relayer). The sender fully controls the actions inside their own `DelegateAction` and can construct them to intentionally fail on the receiver's shard (e.g., attach a deposit to a `FunctionCall` targeting a nonexistent method, or exceed a storage/balance precondition on the receiver), guaranteeing the deposit-refund receipt is created for `sender_id` — the sender — while the relayer's balance was already debited for those tokens at receipt-conversion time on the relayer's shard.

The docs explicitly flag the resulting incentive problem: "There is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard" [6](#0-5) .

### Impact Explanation
An untrusted meta-transaction sender can cause a relayer to lose the full attached-deposit amount of any inner action they choose to fail, receiving that deposit back to their own account instead of the relayer's. This is unauthorized value movement: funds debited from one account (the relayer) end up credited to another (the sender) purely because the sender crafted a self-serving, intentionally-failing action, with no compensating payment from the sender to the relayer. Relayer services processing arbitrary/untrusted `DelegateAction`s (any generic meta-tx relayer) are directly exposed to draining of prepaid balances.

### Likelihood Explanation
Reachable by any unprivileged transaction signer who obtains relayer service: the sender only needs to author and sign a `DelegateAction` with an attached-deposit inner action engineered to fail (e.g., calling a non-existent method, or targeting an account/contract state that will reject the deposit), and have a relayer submit it. No special permissions, validator status, or malicious-peer capability are required — this is a straightforward application of a documented, protocol-level refund-routing rule.

### Recommendation
Route deposit refunds for failed inner actions of a `DelegateAction` to the relayer (the original transaction signer / fee payer) rather than to `sender_id`, mirroring how gas refunds already correctly go to the signer. Alternatively, require relayers to explicitly acknowledge (and the protocol to enforce) that deposits for delegate-action inner actions are non-refundable to the sender, or introduce a `refund_to` override at the `DelegateAction` level that the relayer — not the sender — controls, so the party actually paying determines where their own funds return.

### Proof of Concept
1. Relayer submits a transaction wrapping a `SignedDelegateAction` with `sender_id = Alice`, `receiver_id = Bob`, containing one `FunctionCall` action with a large attached `deposit` and `method_name` set to a method that does not exist on `Bob`'s contract (or omit any contract on `Bob`).
2. At transaction-to-receipt conversion on the relayer's shard, the relayer's account is debited for the deposit and gas per `total_deposit`/fee computation [5](#0-4) .
3. `apply_delegate_action` forwards a new receipt to `Bob`'s shard with `predecessor_id = Alice` [3](#0-2) .
4. The `FunctionCall` fails (method not found / contract absent); the runtime's failure-refund path issues a balance refund to `receipt.balance_refund_receiver()`, which resolves to `predecessor_id` = `Alice` [4](#0-3) .
5. Alice's account receives the deposit back; the relayer's account remains debited by that same amount with nothing to show for it — Alice has effectively extracted funds from the relayer without compensation, exactly mirroring "voting without paying" by directing the refund to the party who didn't actually pay.

## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.

            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }

/// Get the total sum of deposits for given actions.
pub fn total_deposit(actions: &[Action]) -> Result<Balance, IntegerOverflowError> {
    let mut total_balance = Balance::ZERO;
    for action in actions {
        let action_balance;
        if let Some(delegate_action) = delegate_inner_action(action) {
            // Note, here Relayer pays the deposit but if actions fail, the deposit is
            // refunded to Sender of DelegateAction
            let actions = delegate_action.get_actions();
            action_balance = total_deposit(&actions)?;
        } else {
            action_balance = action.get_deposit_balance();
        }

        total_balance = safe_add_balance(total_balance, action_balance)?;
    }
    Ok(total_balance)
}
