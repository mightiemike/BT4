Based on my investigation, I found a genuine analog to the "pass-through instead of reverting" bug class in the Zest v2 vault contracts.

### Title
`accrue()` pause pass-through lets borrow/repay/system operations use stale, un-accrued interest indexes - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`)

### Summary
When the DAO pauses `accrue` via `set-pause-states`, the vault's `accrue` function does not revert callers; instead it silently returns the *stale* cached `index`/`lindex` pair without updating them, and every caller (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`) proceeds using those unresolved values as if accrual had happened.

### Finding Description
`accrue` reads `pause-states`, and when `(get accrue states)` is true it takes the "PAUSED: Pass-through without reverting" branch, returning `(ok { index: idx, lindex: lidx })` using the currently stored (i.e., stale) `index`/`lindex` values instead of computing `next-index`/`next-liquidity-index` or reverting the call [1](#0-0) . Every state-mutating entry point binds `u (try! (accrue))` at the top of its `let`, expecting this to have brought `index`/`lindex` current before reading `(var-get index)`, computing `debt`, `scaled-amount`, or `total-debt` for cap checks [2](#0-1) . Because the pass-through branch never updates `last-update`, `index`, or `lindex`, all subsequent debt/interest math in `system-borrow`, `system-repay`, `deposit`, `redeem`, and `flashloan` is computed against out-of-date indexes for the entire duration accrue remains paused - potentially spanning many blocks - while the functions still execute normally (funds move, principal is recorded, caps are checked against stale debt). This is the "pause that passes through instead of reverting" pattern: the guard exists (`pause-states.accrue`) but its enforcement point silently no-ops instead of blocking dependent state transitions from proceeding on unrefreshed data.

### Impact Explanation
Debt-cap and liquidity-cap checks in `system-borrow` (`CAP-DEBT`, `available-assets`) are evaluated using `total-debt`/`index` that have not accrued interest since the pause began [3](#0-2) . `system-repay`'s `principal-reduction`/`interest-paid` split is likewise computed from the stale `index`/`total-borrowed`, meaning interest that should have accrued during the pause window is never captured into `assets`/`lindex`/`fee-reserve`-minted treasury shares. This causes permanent freezing/loss of accrued yield relative to what should have been collected (treasury `fee-reserve` mint in the non-paused branch is skipped entirely), landing on the in-scope "temporary/permanent freezing of unclaimed yield" impact class rather than a deliberate safety design choice, since the pause is meant to halt state changes, not to let dependent debt/interest math silently operate on frozen indexes.

### Likelihood Explanation
This is reachable with a single DAO-authorized pause action followed by ordinary user/system transactions (borrow, repay, deposit, redeem) during the paused window — no cross-user interference or DAO compromise required, since pausing `accrue` is itself an intended DAO action; the bug is that the *downstream* math trusts `accrue`'s stale return value instead of guarding on it.

### Recommendation
When `accrue` is paused, either (a) have dependent functions (`system-borrow`, `system-repay`, `deposit`, `redeem`, `flashloan`) explicitly detect that no accrual occurred and skip/defer any interest-dependent calculations consistently, or (b) make the pause apply only to the *entry points* that mutate index-dependent state, not silently substitute stale values that are then treated as fresh by every caller in the file, e.g. `system-borrow`/`system-repay` [4](#0-3) .

### Proof of Concept
1. DAO calls `set-pause-states` with `accrue: true`; this triggers one final real accrual via `(try! (accrue))` inside the pause-setter before flipping the flag [5](#0-4) .
2. Time passes (many blocks) while `accrue` stays paused.
3. A borrower calls `system-borrow`; internally `(try! (accrue))` hits the paused branch and returns the old `index`/`lindex` without updating `last-update` [6](#0-5) .
4. `debt`, `CAP-DEBT` check, and `scaled-amount` in `system-borrow` are computed from this stale `index`, understating true owed interest [7](#0-6) .
5. Later, `system-repay` similarly computes `interest-paid`/`principal-repaid` from the still-stale index; the interest that should have accrued over the paused period is never reflected in `assets` or minted to `.dao-treasury`, permanently losing that yield once the position is later closed or index eventually jumps at unpause (`var-set last-update stacks-block-time` on unpause resets the clock without back-filling the missed interest) [8](#0-7) .

**Uncertainty note:** I could not verify from the indexed content whether `mainnet/contracts/market/v0-4-market.clar`'s `get-cached-indexes`/`vault-accrue` (referenced 36 times) interacts with this paused pass-through in a way that compounds the issue further (e.g., ztoken price resolution via `resolve-ztoken` using `get-cached-indexes`) — the file's content beyond the header was not returned by the tool, likely due to index size limits.
