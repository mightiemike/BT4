### Title
Unchecked native multiplication in energy fee computation may yield a negative/wrapped fee, bypassing balance and fee enforcement - (File: chainbase/src/main/java/org/tron/core/capsule/ReceiptCapsule.java)

### Summary
The `MulDivGadget` report describes a class of bug where a fee-relevant multiply/divide is performed without validating the bit-size of its operands or the resulting product, allowing an overflow to silently produce an incorrect (including negative) fee that lets an attacker evade charges. The same bug class is reachable in java-tron's TVM energy-fee billing path: `ReceiptCapsule.payEnergyBill` computes the TRX cost of "over-limit" energy usage using plain, unchecked `long` multiplication instead of an overflow-checked or `BigInteger`-based computation, unlike the parallel, audited computations elsewhere in the same codebase.

### Finding Description
In `ReceiptCapsule.payEnergyBill`, when a caller/creator has already exhausted its frozen energy, the excess is billed in TRX using: [1](#0-0) 
```
long sunPerEnergy = Constant.SUN_PER_ENERGY;
long dynamicEnergyFee = dynamicPropertiesStore.getEnergyFee();
if (dynamicEnergyFee > 0) {
  sunPerEnergy = dynamicEnergyFee;
}
long energyFee =
    (usage - accountEnergyLeft) * sunPerEnergy;
```
This is a plain `long * long` multiplication with no `multiplyExact`/`Math.multiplyExact`, no `BigInteger` fallback, and no bit-size validation of `usage`, `accountEnergyLeft`, or `sunPerEnergy` — the same missing-range-check pattern flagged in the `MulDivGadget` report (no validation of `numBitsValue`, `numBitsNumerator`, `numBitsDenominator`, nor of the bound on the product). If `(usage - accountEnergyLeft) * sunPerEnergy` exceeds `Long.MAX_VALUE`, Java's `long` arithmetic silently wraps around instead of throwing, and `energyFee` can become negative.

This is inconsistent with the rest of the codebase, which treats exactly this class of multiply/divide as security-sensitive and hardens it either with `multiplyExact`/`StrictMathWrapper` or `BigInteger`:
- `JsonRpcApiUtil.calcFeeLimit` explicitly protects `gas * energyFee` with `StrictMathWrapper.multiplyExact` and rejects overflow: [2](#0-1) 
- `RepositoryImpl.calculateGlobalEnergyLimit`/`getUsage` use `BigInteger` under `hardenResourceCalculation()`: [3](#0-2) 
- `ResourceProcessor.increase`/`increaseV2` explicitly guard the identical `usage * precision / windowSize` style computation with `BigInteger` when hardened, precisely because plain-`long` overflow was identified as a bug class: [4](#0-3) 

`payEnergyBill`'s `energyFee` line has no such hardening path at all — it is unconditionally the unguarded `long` multiplication, immediately followed by the actual balance-deduction / fee-charging logic: [5](#0-4) 
```
this.setEnergyUsage(accountEnergyLeft);
this.setEnergyFee(energyFee);
long balance = account.getBalance();
if (balance < energyFee) {
  throw new BalanceInsufficientException(...);
}
account.setBalance(balance - energyFee);
...
dynamicPropertiesStore.addTransactionFeePool(energyFee);
```
If `energyFee` wraps to a negative value, the check `balance < energyFee` is trivially satisfied (any non-negative balance is `>=` a negative number), so the exception is never thrown; `account.setBalance(balance - energyFee)` then *increases* the caller's balance instead of debiting it, and a negative amount is fed into `addTransactionFeePool`/`burnTrx`/`adjustBalance`, corrupting the fee pool / black-hole accounting.

### Impact Explanation
If reachable, this allows an attacker who triggers a TVM contract call to have their (or the contract creator's) account balance *increased* rather than charged for excess energy usage, and corrupts the network's transaction fee pool or burn accounting with a negative value — an accounting/consensus-relevant integrity issue analogous to the "evade fees / set a negative fee" scenario in the original report.

### Likelihood Explanation
Exploitability is uncertain and could not be fully confirmed with the available tools. `usage - accountEnergyLeft` is the portion of energy consumed beyond the account's currently available frozen/free energy, and in normal operation this is bounded by the transaction's `feeLimit / sunPerEnergy` via the energy-limit computations in `VMActuator` (e.g. `getAccountEnergyLimitWithFixRatio`/`getAccountEnergyLimitWithFloatRatio`), which themselves are `min()`-clamped against `feeLimit`. I was not able to locate, within the given search budget, a hard, protocol-level upper bound on `feeLimit` (`TransactionUtil`/proposal-configurable `getMaxFeeLimit`) that would provably keep `(usage - accountEnergyLeft) * sunPerEnergy` under `Long.MAX_VALUE` in all cases (e.g., under a maliciously large but still policy-accepted `feeLimit`, or under an adversarially set `getEnergyFee()` dynamic parameter). Given `Long.MAX_VALUE ≈ 9.2e18`, both operands would need to be very large simultaneously, which is plausible only if `feeLimit`/`getMaxFeeLimit()` can be configured to very large values and `sunPerEnergy` is also large — this needs confirmation against the live `getMaxFeeLimit` proposal bounds and default config, which I could not retrieve in the remaining iterations.

### Recommendation
Replace the unguarded multiplication in `ReceiptCapsule.payEnergyBill` with an overflow-checked computation, consistent with the rest of the codebase's hardening pattern (e.g., `StrictMathWrapper.multiplyExact` or a `BigInteger`-based computation gated by a feature flag such as the existing `hardenResourceCalculation`/`disableJavaLangMath` toggles used elsewhere), and explicitly reject/clamp the result rather than allow silent wraparound before it is used to adjust account balances and the transaction fee pool.

### Proof of Concept
Not independently verified end-to-end (would require confirming the reachable maximum of `feeLimit`/`getEnergyFee()` via a live node/test harness, which is outside the scope of static analysis here). Conceptually: submit a `TriggerSmartContract` transaction with the maximum accepted `fee_limit` against a contract that consumes energy just above the account's available frozen/free energy while the network's `ENERGY_FEE` dynamic parameter is also large, driving `(usage - accountEnergyLeft) * sunPerEnergy` past `Long.MAX_VALUE` in `ReceiptCapsule.payEnergyBill`, and observe whether `energyFee` becomes negative and the balance/fee-pool corruption described above occurs.
