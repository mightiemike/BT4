### Title
Malicious DelegateAction Sender Steals Relayer's Attached Deposit via Deliberately Failing Meta Transaction — (`runtime/runtime/src/actions.rs`)

### Summary

In NEAR's meta transaction (NEP-366) implementation, when a relayer submits a `DelegateAction` whose inner actions carry an attached deposit, and those inner actions fail on the receiver's shard, the deposit refund is sent to the `predecessor_id` of the inner receipt — which is the **sender (Alice)**, not the relayer who actually paid for the deposit. An unprivileged user can deliberately craft a `DelegateAction` with a large attached deposit that is guaranteed to fail on the receiver's shard, causing the relayer to lose the full deposit while the user receives it as a free refund.

### Finding Description

The bug-class seed from the external report is: *a fee/reward is disbursed to a party regardless of whether the underlying execution succeeds, creating a financial incentive to deliberately cause failure*. The nearcore analog is structurally identical but operates through the deposit-refund path of meta transactions.

**Step 1 — Inner receipt is created with Alice as predecessor.**

In `apply_delegate_action`, the new action receipt forwarded to Bob's shard is constructed with `predecessor_id: sender_id.clone()` (Alice): [1](#0-0) 

The comment immediately below this construction explicitly acknowledges the consequence: [2](#0-1) 

**Step 2 — On failure, deposit refund receiver is resolved as `predecessor_id`.**

`balance_refund_receiver()` returns `refund_to` if set, otherwise falls back to `predecessor_id()`: [3](#0-2) 

For a plain `ActionReceipt` (the type generated by `apply_delegate_action`), `refund_to` is always `None`: [4](#0-3) 

So `balance_refund_receiver()` resolves to Alice.

**Step 3 — `refund_unspent_gas_and_deposits` sends the full deposit to Alice.**

When `result.result.is_err()`, `deposit_refund = total_deposit`, and the refund receipt is pushed to Alice: [5](#0-4) [6](#0-5) 

**Step 4 — The protocol documentation acknowledges the financial incentive.**

The architecture documentation explicitly states:

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard**." [7](#0-6) 

**Attack path (concrete):**

1. Alice crafts a `DelegateAction` targeting a receiver contract (`Bob`) with a large `deposit` (e.g., 100 NEAR) attached to a `FunctionCall` action whose method does not exist on Bob's contract, or whose execution is guaranteed to fail (e.g., panics, insufficient storage, etc.).
2. Alice signs the `DelegateAction` and sends it off-chain to a relayer.
3. The relayer, after off-chain validation (which may not catch all on-chain failure conditions), wraps it in a transaction and submits it, paying for gas **and** the attached deposit.
4. On Alice's shard, `apply_delegate_action` succeeds (signature valid, nonce valid, block height valid), creating the inner receipt with `predecessor_id = Alice`.
5. On Bob's shard, the inner action fails. `refund_unspent_gas_and_deposits` issues a deposit refund receipt to `balance_refund_receiver()` = Alice.
6. Alice receives 100 NEAR. The relayer loses 100 NEAR (plus gas costs).

The relayer's gas is refunded to the relayer (via `signer_id`), but the deposit — which can be orders of magnitude larger — goes to Alice.

### Impact Explanation

- **Stealing of funds**: The relayer loses the full attached deposit. Alice gains it. The deposit amount is bounded only by what the relayer is willing to attach, which for legitimate use cases (e.g., storage deposits, FT registration fees) can be substantial.
- **Balance manipulation**: Alice's balance increases by the deposit amount; the relayer's balance decreases by the same amount, with no legitimate service rendered.
- **No cap on loss**: A single `DelegateAction` can carry a deposit up to the relayer's entire balance. Alice can repeat this with different nonces.
- **Unprivileged trigger**: Alice needs only a valid NEAR account and access key. No validator or admin role is required.

### Likelihood Explanation

- Any relayer that accepts `DelegateAction`s with attached deposits from untrusted users is vulnerable.
- The NEP-366 design explicitly envisions relayers accepting actions from users who have no NEAR tokens — precisely the population most likely to be adversarial.
- Off-chain simulation of on-chain execution is imperfect; a malicious user can craft actions that pass simulation but fail on-chain (e.g., by racing a state change between simulation and inclusion).
- The protocol documentation itself flags this as a known financial incentive for abuse, confirming the attack is reachable.

### Recommendation

The root fix is to make the deposit refund receiver the **signer** (relayer) rather than the **predecessor** (Alice) for receipts generated by `apply_delegate_action`. Concretely:

- In `apply_delegate_action`, construct the inner receipt using `ReceiptEnum::ActionV2(ActionReceiptV2 { refund_to: Some(action_receipt.signer_id().clone()), ... })` so that `balance_refund_receiver()` resolves to the relayer instead of Alice.
- Alternatively, introduce a `refund_to` field in the `DelegateAction` struct itself, allowing the relayer to specify where deposit refunds should go, and validate that this field is set to the relayer's account.

Gas refunds already correctly go to the signer (relayer) via `Receipt::new_gas_refund(&action_receipt.signer_id(), ...)`. The deposit refund path should be made consistent with this. [8](#0-7) 

### Proof of Concept

```
Relayer account: relayer.near  (balance: 200 NEAR)
Alice account:   alice.near    (balance: 0 NEAR, has a valid access key)
Bob contract:    bob.near      (deployed contract with no method "steal")

1. Alice constructs:
   DelegateAction {
     sender_id: "alice.near",
     receiver_id: "bob.near",
     actions: [FunctionCall { method_name: "steal", gas: 10 TGas, deposit: 100 NEAR }],
     nonce: <valid>,
     max_block_height: <future>,
     public_key: <alice's key>,
   }
   Signs it with her key.

2. Alice sends the SignedDelegateAction to relayer.near off-chain.

3. Relayer submits:
   Transaction {
     signer_id: "relayer.near",
     receiver_id: "alice.near",   // delegate action target
     actions: [Delegate(signed_delegate_action)],
   }
   Relayer's account is charged: gas cost + 100 NEAR deposit.

4. On alice.near's shard: apply_delegate_action succeeds.
   Inner receipt created: predecessor="alice.near", receiver="bob.near", deposit=100 NEAR.

5. On bob.near's shard: FunctionCall("steal") fails (method not found).
   refund_unspent_gas_and_deposits:
     deposit_refund = 100 NEAR
     balance_refund_receiver() = predecessor_id = "alice.near"
   → Receipt::new_balance_refund("alice.near", 100 NEAR) is emitted.

6. alice.near receives 100 NEAR.
   relayer.near net loss: 100 NEAR + gas.
```

The attack is repeatable with different nonces on Alice's key. Each iteration transfers up to the deposit amount from the relayer to Alice at zero cost to Alice.
