### Title
Direct TRX Transfers to Smart Contracts via `TransferContract` Bypass Contract Code Execution, Making Deposits Untraceable - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`)

### Summary
The reported ink!/OpenBrush issue is a bug class: a "raw" native-value transfer path exists that moves balance into a contract without invoking any of the receiving contract's code (fallback/receive), so the contract has no way to observe, log, or react to the deposit. java-tron has a directly analogous path: the system-level `TransferContract` actuator can move TRX straight into a contract account's balance without ever entering the TVM, meaning no fallback function runs and no event can be emitted.

### Finding Description
`TransferActuator.execute()` adjusts account balances directly via `adjustBalance` and never invokes the TVM or any contract bytecode [1](#0-0) . The only guard that would prevent sending TRX to a contract this way is the `FORBID_TRANSFER_TO_CONTRACT` governance flag, checked in `validate()`: [2](#0-1) 

This flag defaults to `0` (disabled) both in `CommitteeConfig` and `reference.conf`, and is only enabled if community governance separately approves proposal #35: [3](#0-2) [4](#0-3) 

`DynamicPropertiesStore` also seeds the on-chain value from this same default-`0` config at genesis/startup: [5](#0-4) 

So, on any deployment where this proposal has not been passed by the committee, any unprivileged account can call `TransferContract` to send TRX directly to a smart contract's balance. Unlike a TVM-level `CALL` (which is what Solidity's `.transfer()`/`.send()` compiles to and which does invoke the target's fallback/receive, allowing it to emit a `Deposit`-style event as in the OpenBrush `PaymentSplitter::receive`), this system actuator path never executes the contract's bytecode at all — it is closer to ink!'s raw `transfer` primitive than to a `call`. Contracts that rely on fallback-triggered logic/events to track incoming TRX (e.g., a PaymentSplitter-style accounting contract, or any contract maintaining an on-chain ledger of "known" deposits) will have their real TRX balance silently diverge from their internally tracked accounting, exactly the same root cause described in the report: the underlying platform provides a native value-transfer channel that bypasses the receiving contract's notification/tracking mechanism.

### Impact Explanation
This causes a genuine accounting/state divergence: a contract's actual balance (`getAccount(contractAddress).getBalance()`) can be increased by any third party without the contract's own accounting state (e.g., "total received", per-payee shares in a splitter-like design) ever being updated, because no fallback/receive code runs and no event is emitted. Downstream systems, indexers, or contracts that only trust events/fallback execution to track deposits will silently miss funds, and reconciliation between the ledger state and the actual TRX balance will fail. This mirrors the accepted impact class in the original report (untraceable, unaccounted native transfers to a payment-tracking contract).

### Likelihood Explanation
High: `FORBID_TRANSFER_TO_CONTRACT` is disabled (`0`) by default and requires an explicit, separate governance proposal to enable, per `CommitteeConfig`/`reference.conf` defaults [6](#0-5) . Any unprivileged account can trigger this by simply issuing a normal TRX transfer (`TransferContract`) to a contract address — no special permission, no TVM interaction required.

### Recommendation
Consider enabling `FORBID_TRANSFER_TO_CONTRACT` by default (or hard-coding the restriction) so that all TRX transfers into contracts must go through `TriggerSmartContract`, guaranteeing fallback/receive execution and giving contracts the opportunity to emit tracking events, consistent with how `AllowTvmCompatibleEvm` already forbids this for version-1 contracts [7](#0-6) . Document this attack surface clearly for contract developers who build accounting logic dependent on notification of incoming value.

### Proof of Concept
1. Deploy a Solidity/TVM contract implementing PaymentSplitter-like accounting that only updates its internal ledger inside a `receive()`/fallback function (analogous to OpenBrush's `PaymentSplitter::receive`).
2. On a network where `FORBID_TRANSFER_TO_CONTRACT` has not been enabled (default `0`), submit a standard `TransferContract` transaction with `to_address` set to the contract's address and a nonzero `amount`.
3. Observe: `TransferActuator.execute()` credits the contract's balance directly via `adjustBalance(accountStore, toAddress, amount)` [8](#0-7)  without ever constructing a `Program`/invoking the TVM, so the contract's fallback never runs and no event is logged.
4. Query the contract's actual TRX balance vs. its internal accounting variables — they diverge, reproducing the same "untraceable native transfer" condition described in the original ink! report.
