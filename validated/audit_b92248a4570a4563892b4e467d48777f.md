### Title
Single global byte-size cap and fixed random-eviction sample size in the read-only accounts cache indiscriminately evict all accounts regardless of size or access frequency - (File: `accounts-db/src/read_only_accounts_cache.rs`)

### Summary
The `ReadOnlyAccountsCache` uses one hardcoded pair of global byte-size watermarks (`max_data_size_lo`/`max_data_size_hi`) and a single `evict_sample_size` to decide when and what to evict, applied identically to every cached account regardless of the account's individual size or access frequency. Just as the reported `MultiFlowPump` bug applies one universal percentage cap (`LOG_MAX_INCREASE`/`LOG_MAX_DECREASE`) across tokens with very different natural volatility, causing some to be unfairly capped while others see no effect at all, this cache applies one universal byte budget across accounts with very different sizes and hotness, causing hot small accounts to be evicted far more aggressively than their access pattern warrants while a few large, rarely-accessed accounts can dominate the shared byte budget with no corresponding "cost" signal.

### Finding Description
`ReadOnlyAccountsCache::new` takes a single `max_data_size_lo`/`max_data_size_hi` pair and `evict_sample_size` that apply uniformly to the entire cache, independent of each entry's data length or update frequency. [1](#0-0) 

The background evictor only checks the aggregate byte total against the fixed high watermark, and once triggered, evicts using a fixed-size random sample compared purely by `last_update_time`, with no normalization for the entry's own size relative to the total budget. [2](#0-1) 

`account_size` mixes the fixed `CACHE_ENTRY_SIZE` with the variable account data length, so a handful of large accounts (e.g., large program/executable accounts, which this cache is explicitly designed to hold per its module doc) can consume a disproportionate share of the shared `max_data_size_hi` budget. [3](#0-2) [4](#0-3) 

Because the watermarks and sample size are single global constants (configured once via `AccountsDbConfig::read_cache_limit_bytes` / `read_cache_evict_sample_size`) rather than being scaled per-entry-size or per-access-rate, the eviction policy behaves exactly like the reported bug class: a one-size-fits-all cap indiscriminately applied to heterogeneous "assets" (here, accounts of widely varying size and hotness) rather than a per-asset (per-account) calibrated limit. [5](#0-4) 

### Impact Explanation
When the aggregate cache size exceeds `max_data_size_hi` (driven mainly by a few large accounts consuming most of the shared budget), the evictor must repeatedly evict entries down to `max_data_size_lo` using only a small random sample compared by recency. Small, frequently accessed accounts get swept up in this global churn purely because the byte budget is shared with unrelated large accounts, forcing repeated evictions and subsequent expensive disk reads (`AppendVec`/storage lookups) for hot accounts that would otherwise stay resident. This produces disproportionate CPU and I/O cost under normal transaction load whenever the working set mixes a few large accounts with many small hot accounts — a direct analog of the pump bug's "some assets become more stale than normal activity warrants."

### Likelihood Explanation
This is triggered by ordinary, unprivileged transaction activity: any workload that reads a mix of large accounts (e.g., large program data) and small frequently-touched accounts (e.g., token/program state accounts) will exercise this shared, unscaled byte budget. No special permissions or crafted snapshots are required — it is a property of the read-only cache's default eviction policy used on every validator during normal replay.

### Recommendation
Avoid a single global byte-size/eviction-sample policy indiscriminately applied to all cached accounts. Consider scaling eviction decisions (or the sample composition) by each entry's own size relative to its access frequency, or partitioning/weighting the byte budget so a small number of large, cold accounts cannot dominate the shared watermark and force disproportionate eviction of small, hot accounts.

### Proof of Concept
Not applicable as an on-chain PoC; the report is a code-analysis analog. Root cause is demonstrable by inspection of `ReadOnlyAccountsCache::evict` and `account_size`, where the eviction trigger (`data_size > max_data_size_hi`) and the eviction sample selection ignore each entry's individual size and hotness relative to the shared, globally fixed budget. [6](#0-5)

    /// following the sampled LRU eviction method, where a sample of size
    /// `evict_sample_size` is randomly selected from the cache, using the
    /// provided `rng`.
    ///
    /// Returns the number of entries evicted.
    fn evict<R>(
        target_data_size: usize,
        data_size: &AtomicUsize,
        cache_len: &AtomicUsize,
        evict_sample_size: usize,
        cache: &DashMap<ReadOnlyCacheKey, ReadOnlyAccountCacheEntry, AHashRandomState>,
        rng: &mut R,
        #[cfg(feature = "dev-context-only-utils")] mut callback: impl FnMut(
            &Pubkey,
            Option<ReadOnlyAccountCacheEntry>,
        ),
    ) -> u64
    where
        R: Rng,
    {
        let mut num_evicts: u64 = 0;
        while data_size.load(Ordering::Relaxed) > target_data_size {
            let mut key_to_evict = None;
            let mut min_update_time = u64::MAX;
            let mut remaining_samples = evict_sample_size;
            // NOTE: This can loop indefinitely if the cache is misconfigured
            // and when we get here there aren't at least `evict_sample_size`
            // elements. We could break the loop on `cache.is_empty()` but
            // calling `is_empty()` and `len()` on a dashmap is very expensive
            // as it requires iterating and locking all the shards. So, avoid
            // paying that cost and assume that when eviction triggers the
            // cache contains enough items.
            while remaining_samples > 0 {
                let shard = cache
                    .shards()
                    .choose(rng)
                    .expect("number of shards should be greater than zero");
                let shard = shard.read();
                for (key, entry) in shard.iter().choose_multiple(rng, remaining_samples) {
                    let last_update_time = entry.get().last_update_time.load(Ordering::Relaxed);
                    if last_update_time < min_update_time {
                        min_update_time = last_update_time;
                        key_to_evict = Some(key.to_owned());
                    }

                    remaining_samples = remaining_samples.saturating_sub(1);
                }
            }
