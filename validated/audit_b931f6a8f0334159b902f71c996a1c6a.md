### Title
Gas-to-credit rounding truncation allows zero-cost capability spend in workflow metering - (File: core/services/workflows/metering/balance_store.go)

### Summary
The `balanceStore.convertToBalance` function in the Chainlink workflow metering subsystem converts a node's reported gas/resource spend into billing credits using decimal division followed by a fixed, hard-coded rounding precision. Just as Popcorn's `AdapterBase._convertToShares` could round a legitimate deposit down to `0` shares, `convertToBalance` can round a legitimate non-zero gas spend down to `0` credits, meaning a workflow can consume real capability/gas resources while being billed nothing.

### Finding Description
`convertToBalance` computes credits for gas-type spends as `amount.Div(rate).Round(defaultDecimalPrecision)`, where `defaultDecimalPrecision` is fixed at `10`: [1](#0-0) 

`defaultDecimalPrecision` is declared as a magic constant intended to mirror a value in an external billing service: [2](#0-1) 

Because `amount.Div(rate)` is rounded to only 10 decimal places, any genuine, non-zero `amount/rate` value smaller than `5e-11` is truncated to exactly `0`. This value flows directly into `Settle`, which aggregates per-node spend and converts it to credits via `r.balance.ConvertToBalance`, then adds the result to `spentCredits`, which is what ultimately gets reported/billed via `SubmitWorkflowReceipt`: [3](#0-2) 

If the converted balance is `0`, `spentCredits` is not incremented for that step even though the node genuinely expended gas/resources to execute the capability. The existing test suite already demonstrates a related scenario where a small gas spend value converts to `"0"` credits and is submitted to the billing service without error: [4](#0-3) 

This is the same bug class as the Popcorn vault finding: a division-then-truncate calculation silently collapses a real, non-zero quantity to zero, and the caller proceeds as if the operation succeeded normally with no revert/guard against the zero result.

### Impact Explanation
Instead of a user losing funds (as in the original Popcorn finding), the beneficiary here is the party whose spend is being metered: a workflow owner can have real capability/gas usage recorded and billed as `0` credits, meaning the billing/metering system fails to capture true resource consumption. Because rate cards and gas-token conversion rates are configuration retrieved per workflow execution via `GetWorkflowExecutionRates`, and because per-step spend values are reported from potentially many nodes/capabilities, an attacker-controlled workflow could structure many capability calls whose individual gas spend values fall under the rounding threshold, executing real work while accruing effectively zero billed credits across all of them. This is a misreporting/billing-data-tampering-adjacent issue that directly undermines the integrity of the CRE workflow billing and metering pipeline (`ErrInsufficientFunding` and `ReserveCredits` checks can be bypassed in aggregate because Deduct/Settle never see the true non-zero cost).

### Likelihood Explanation
Likelihood is moderate: it requires a workflow author to control or influence step granularity/spend magnitude relative to the gas-token conversion rate (`GasTokensPerCredit`) such that `amount/rate < 5e-11`, which is plausible given gas values are shifted by `18` decimals before conversion: [5](#0-4) 

No privileged access is required — only the ability to design/run a workflow with capability calls whose gas usage is small relative to configured rates, which is within reach of any unprivileged workflow author using CRE.

### Recommendation
Do not silently round non-zero conversions down to zero. Either:
1. Track a running remainder/fractional credit balance instead of rounding per-call, so small spends accumulate correctly across steps, or
2. Explicitly detect when a non-zero `amount` converts to `0` credits and treat it as an error/warning that forces a minimum charge, rather than proceeding as though `0` cost was accurately measured.

### Proof of Concept
1. Configure a workflow execution rate such that `GasTokensPerCredit` for a chain results in a conversion rate `rate` (post `.Div`) where a plausible per-call gas spend `amount` satisfies `amount/rate < 5e-11`.
2. Have a capability report a `MeteringNodeDetail` with that small non-zero `SpendValue` for a gas spend unit, following the same flow exercised in the existing test: [6](#0-5) 
3. Call `report.Settle` and observe that `convertToBalance` returns `decimal.Zero` for the real, non-zero gas amount, and that `SubmitWorkflowReceipt` reports `CreditsConsumed == "0"` even though genuine gas was consumed.
4. Repeat across many steps/executions to accumulate real resource usage while the aggregate billed credits remain `0`.

// convertToBalance converts a resource dimension amount to a credit amount.
// This method should only be used under a read lock.
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}
