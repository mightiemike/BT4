## Title
Missing joint `TRADING_NATIVE` + per-store flag enforcement allows native-position writes with only `NATIVE_POSITION` enabled - ([File: aptos-move/framework/position-natives/src/natives.rs])

### Summary
The comment in `features.move` at lines 904-906 states that `TRADING_NATIVE` is an "umbrella auth flag" and that the per-store flags (`NATIVE_POSITION`, `NATIVE_ORDERBOOK`, `NATIVE_COLLATERAL`) only gate writes when `TRADING_NATIVE` is also on ("Both must be on to write") [1](#0-0) . However, the actual native-write enforcement point, `check_feature_enabled` in `aptos-move/framework/position-natives/src/natives.rs`, only checks `FeatureFlag::NATIVE_POSITION` and never checks `TRADING_NATIVE` at all [2](#0-1) .

### Finding Description
`check_feature_enabled` is the sole gate used by `native_set_position` and `native_delete_position`, the two native functions registered for the `native_position` module [3](#0-2) . Its implementation is:

```rust
fn check_feature_enabled(context: &SafeNativeContext) -> SafeNativeResult<()> {
    if context.get_feature_flags().is_enabled(FeatureFlag::NATIVE_POSITION) {
        Ok(())
    } else {
        Err(SafeNativeError::Abort { ... })
    }
}
``` [2](#0-1) 

This checks only `NATIVE_POSITION`; there is no corresponding check for `TRADING_NATIVE`. Meanwhile `features.move` documents `TRADING_NATIVE` as the umbrella flag that, together with the per-store flag, is required for a write to be permitted [4](#0-3) . The only place in the Move framework that actually checks `TRADING_NATIVE` is `trading_native_capability.move`'s capability-minting path (`get_capability`/`assert_valid`), which gates *capability issuance*, not the native storage writes themselves [5](#0-4) . Nothing in `natives.rs` requires or consumes that capability before performing the native write.

Because the two flags are independently settable feature flags (each one is a plain `is_enabled(FLAG)` check), it is possible for on-chain feature configuration to have `NATIVE_POSITION = true` while `TRADING_NATIVE = false`. In that state, any transaction invoking the native-position write entry point will pass `check_feature_enabled` and commit a native write, contradicting the documented invariant that both flags gate the write.

### Impact Explanation
If `TRADING_NATIVE` is disabled (e.g., because the umbrella subsystem was killed/paused) but `NATIVE_POSITION` remains enabled, unprivileged transactions can still produce native-position write set entries. This is a state-commitment integrity issue: the honestly-computed VM output under the intended two-flag gate should contain no such write, yet the actual code path commits one. This is exactly the class of "committed state differs from correct VM result" issue in scope, since the enforcement code (`natives.rs`) diverges from the documented/intended two-flag invariant declared in `features.move`.

### Likelihood Explanation
This depends on the flag configuration reachable on-chain: it requires `NATIVE_POSITION` enabled and `TRADING_NATIVE` disabled simultaneously. Whether this specific combination is reachable via governance/feature-flag operations independent of each other determines real-world likelihood, but nothing in the reviewed code prevents such a configuration, and no code enforces the joint condition — the gate simply does not exist in the write path.

### Recommendation
Update `check_feature_enabled` in `aptos-move/framework/position-natives/src/natives.rs` to require both `FeatureFlag::TRADING_NATIVE` and `FeatureFlag::NATIVE_POSITION` (and analogously for future `NATIVE_ORDERBOOK`/`NATIVE_COLLATERAL` natives) before permitting the write, matching the documented invariant in `features.move`.

### Proof of Concept
1. Enable only `NATIVE_POSITION` via `features::change_feature_flags_for_testing`, leaving `TRADING_NATIVE` disabled.
2. Invoke the Move entry point that calls the `native_set_position` native.
3. Observe that `check_feature_enabled` (natives.rs:34-46) returns `Ok(())` because it only checks `FeatureFlag::NATIVE_POSITION`, and the native write is executed and committed, producing a write set entry for the native-position store — contrary to the documented "both must be on to write" requirement.

Note: I was unable to locate the Move-level `native_position.move` module (which would show whether a Move-side call wraps the native with an additional `TRADING_NATIVE` check before invoking it) — the index does not contain this file's full contents, so I could not fully confirm whether Move-level code adds any additional gating. This should be verified in a full checkout; if no Move-level check exists either, this finding stands as-is.
