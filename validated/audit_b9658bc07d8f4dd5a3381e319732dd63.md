### Title
Integer overflow via `Long.MIN_VALUE` bypasses insufficient-balance guard in `RepositoryImpl.addTokenBalance` - (File: `RepositoryImpl.java`)

### Summary
`RepositoryImpl.addTokenBalance` uses unary negation `-value` to validate a reduction request, but when `value == Long.MIN_VALUE`, `-value` overflows back to `Long.MIN_VALUE` itself (two's-complement negation identity), which defeats the intended `balance < -value` insufficient-balance check and lets execution fall through into `reduceAssetAmountV2` with a negative "amount to reduce" argument instead of the intended positive magnitude.

### Finding Description
`addTokenBalance` is reachable from TVM precompiles/opcodes (e.g. TRC10 transfer/withdraw precompiles invoked by attacker-controlled contract bytecode) which forward a signed `value` parameter directly into this method: [1](#0-0) 

The guard at line 858 is:
```
if (value < 0 && balance < -value) { throw ... }
```
For `value == Long.MIN_VALUE` (-9223372036854775808), `-value` overflows and evaluates to `Long.MIN_VALUE` again (a negative number). Since `balance` is a non-negative token amount, `balance < -value` becomes `balance < Long.MIN_VALUE`, which is always `false`. The intended "insufficient balance" exception is therefore never thrown, and the code proceeds to the `else` branch, calling:
```
accountCapsule.reduceAssetAmountV2(tokenIdWithoutLeadingZero, -value, ...)
```
with `-value` still equal to `Long.MIN_VALUE` — a negative "reduce amount" being passed to a method whose contract expects a non-negative magnitude to subtract. This is exactly the "inconsistent sign" call path described in the question: the outer sign-based dispatch (`value >= 0` → add, `value < 0` → reduce with `-value`) is invalidated by the one input value for which negation is not the true additive inverse.

No upstream check in `Program.java`/`ContractState.java`/`MUtil.java` (the TVM-side callers of `addTokenBalance`) was confirmed in this session to reject `Long.MIN_VALUE` specifically, and the standard TVM validation path (signature checks, permission weights, `ForkController` gates, energy/bandwidth accounting) governs whether a transaction is admitted and executed, not the internal arithmetic correctness of `value` once inside a precompile call — those checks do not protect against this specific overflow.

The ultimate downstream effect depends on the implementation of `AccountCapsule.reduceAssetAmountV2`, which was not fully inspected in this session; if that method independently rejects negative arguments the corruption is limited to a no-op, but if it only compares `currentAmount < value` (without an explicit `value >= 0` guard), passing `Long.MIN_VALUE` causes `currentAmount - value` to overflow again (e.g., `100 - Long.MIN_VALUE` wraps around a 64-bit signed long), producing a corrupted/overflowed stored balance. This downstream behavior could not be fully verified with the tools available in this session, so the exact resulting balance/supply state is uncertain, but the bypass of the intended sanity check at line 858 itself is confirmed and reproducible.

### Impact Explanation
At minimum this is a confirmed logic/overflow defect that defeats an intended balance-sufficiency invariant check, allowing a caller to force `reduceAssetAmountV2` to execute with an internally-inconsistent (negative) "amount to reduce" instead of failing safely. Depending on `AccountCapsule.reduceAssetAmountV2`'s own validation (not fully verified here), this can propagate into TRC10 balance/asset-accounting corruption — matching the "asset/accounting corruption" bounty class — up to and including corrupted account balances via secondary long overflow.

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: own or control any account holding (or not holding) the target TRC10 token, deploy/call a contract that exercises the TRC10 transfer/withdraw precompile path with a crafted `value = Long.MIN_VALUE`, paying normal transaction fees/energy. No privileged role, signature bypass, or non-default configuration is required, making the trigger step trivially repeatable. The uncertain part is solely the magnitude of downstream impact, not the reachability of the flawed check.

### Recommendation
Replace the unary-negation-based check with overflow-safe logic, e.g. reject `value == Long.MIN_VALUE` explicitly or use `Math.negateExact(value)` (catching `ArithmeticException`) before comparing against `balance`, and add an explicit non-negative-argument guard inside `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` as defense in depth.

  @Override
  public long addTokenBalance(byte[] address, byte[] tokenId, long value) {
    byte[] tokenIdWithoutLeadingZero = ByteUtil.stripLeadingZeroes(tokenId);
    AccountCapsule accountCapsule = getAccount(address);
    if (accountCapsule == null) {
      accountCapsule = createAccount(address, Protocol.AccountType.Normal);
    }
    long balance = accountCapsule.getAssetV2(new String(tokenIdWithoutLeadingZero));
    if (value == 0) {
      return balance;
    }

    if (value < 0 && balance < -value) {
      throw new RuntimeException(
          StringUtil.createReadableString(accountCapsule.createDbKey())
              + " insufficient balance");
    }
    if (value >= 0) {
      accountCapsule.addAssetAmountV2(tokenIdWithoutLeadingZero, value, getDynamicPropertiesStore(),
          getAssetIssueStore());
    } else {
      accountCapsule
          .reduceAssetAmountV2(tokenIdWithoutLeadingZero, -value, getDynamicPropertiesStore(),
              getAssetIssueStore());
    }
    Key key = Key.create(address);
    accountCache.put(key, Value.create(accountCapsule,
         accountCache.get(key).getType().addType(Type.DIRTY)));
    return accountCapsule.getAssetV2(new String(tokenIdWithoutLeadingZero));
  }
