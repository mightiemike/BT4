### Title
`InitializeNonceAccount` performs no signer check, letting an attacker front-run initialization of a durable-nonce account and steal control of it - ([File: programs/system/src/system_instruction.rs])

### Summary
`SystemInstruction::InitializeNonceAccount` is dispatched in `system_processor.rs` and handled by `initialize_nonce_account` in `system_instruction.rs`. Neither the dispatch code nor the handler function requires any signature check on the target nonce account or on the `authorized` pubkey supplied in the instruction data. Anyone can submit a transaction calling `InitializeNonceAccount` against any writable, uninitialized, rent-exempt, system-owned account and set themselves as the `authority`, exactly the "front-run an unprotected initializer" bug class described in the Mento `__Locking_init` report.

### Finding Description
`SystemInstruction::CreateAccount` and `SystemInstruction::InitializeNonceAccount` are normally bundled together in one atomic client-side transaction via `system_instruction::create_nonce_account` [1](#0-0) . However, nothing in the protocol enforces that atomicity — a nonce account can legitimately be created via `CreateAccount` in one transaction (funded and owned by the system program, with `State::Uninitialized` nonce data) and initialized in a later, separate transaction.

The dispatch arm for `InitializeNonceAccount` only checks the number of accounts and reads sysvars; it never checks that any signer is present for account index 0 (the nonce account) or for the `authorized` pubkey passed as instruction data: [2](#0-1) 

The actual handler, `initialize_nonce_account`, only validates writability, sufficient rent-exempt balance, and that the account is currently `State::Uninitialized` — it performs **no** signer verification at all: [3](#0-2) 

This is in sharp contrast to the vote program's analogous initializer, `initialize_account`/`initialize_account_v2`, which explicitly calls `verify_authorized_signer(&vote_init.node_pubkey, signers)` before initializing the account state [4](#0-3) . The nonce-account initializer has no equivalent authorization check, so any writable, uninitialized nonce account is initializable by literally anyone, with any authority the attacker chooses.

Because pending/unconfirmed transactions and pool state are visible to other network participants, an attacker who observes a `CreateAccount` transaction for a not-yet-initialized nonce account (or simply scans the ledger for freshly created, system-owned, correctly-sized nonce accounts that are still `Uninitialized`) can race the legitimate owner and submit their own `InitializeNonceAccount` instruction naming themselves as `nonce_authority` before the legitimate initialize transaction lands.

### Impact Explanation
Once the attacker's `InitializeNonceAccount` instruction wins the race, the account's `Data::authority` field is permanently set to the attacker's pubkey (the legitimate owner's later `InitializeNonceAccount` call will then fail with `InstructionError::InvalidAccountData` because the account is no longer `Uninitialized` — see the `State::Initialized(_) => ... Err(InstructionError::InvalidAccountData)` branch). The attacker, as the recorded `authority`, can then:
- Call `AdvanceNonceAccount`, since it only requires `signers.contains(&data.authority)` [5](#0-4) .
- Call `WithdrawNonceAccount` and drain the account's entire lamport balance (including the funds the legitimate party deposited to make the account rent-exempt) down to zero, since withdrawal in the `Initialized` branch only checks `check_signer(&data.authority)` [6](#0-5) .

This results in concrete theft of funds (the lamports pre-funded into the nonce account) and permanent loss of control over a durable nonce that the legitimate user intended to own — satisfying the "concrete theft of funds" acceptance bar.

### Likelihood Explanation
Likelihood is moderate: the attack requires that a legitimate actor split account creation and nonce initialization into separate transactions (rather than using the standard atomic `create_nonce_account` helper, which bundles both in one signed transaction). Any tooling, wallet, or custom program flow that creates the account first and initializes it as a follow-up transaction (e.g., staggered multi-step provisioning, PDA-based nonce accounts created by a program then initialized separately, or manual CLI/RPC scripting) is exposed. An attacker monitoring the mempool/recent transactions for `CreateAccount` calls targeting system-program-owned accounts sized for nonce state can trivially front-run the initialize step with a higher-priority-fee transaction.

### Recommendation
Add a signer requirement to `initialize_nonce_account` (or to the `InitializeNonceAccount` dispatch arm in `system_processor.rs`) that the nonce account itself (or an authority pubkey established at `CreateAccount` time) must be a signer of the initializing transaction, mirroring the vote program's `verify_authorized_signer` pattern used in `initialize_account`/`initialize_account_v2`. Alternatively, document/enforce that `InitializeNonceAccount` must always be composed atomically with `CreateAccount` in the same transaction and add a runtime check rejecting initialize calls on accounts not created within the same transaction.

### Proof of Concept
1. Legitimate user submits transaction A: `SystemInstruction::CreateAccount` funding pubkey `N` (nonce account keypair) with `NonceState`-sized space, owned by the system program, sufficient lamports for rent exemption. This transaction is signed and confirmed.
2. Before the user submits their follow-up `InitializeNonceAccount` transaction, an attacker observes account `N` is `Uninitialized`, system-owned, and rent-exempt.
3. Attacker submits transaction B: `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` with account `N` as the sole non-sysvar account — no signature from `N` or from `attacker_pubkey` is required by `initialize_nonce_account` [7](#0-6) . This transaction succeeds and sets `authority = attacker_pubkey`.
4. The legitimate user's follow-up `InitializeNonceAccount(legit_authority)` transaction now fails with `InstructionError::InvalidAccountData` since the account is already `Initialized`.
5. Attacker submits `SystemInstruction::WithdrawNonceAccount(all_lamports)` signed only by `attacker_pubkey`, draining the account's full balance to an attacker-controlled destination, per the `check_signer(&data.authority)` path in `withdraw_nonce_account` [6](#0-5) .

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

pub fn initialize_account<S: std::hash::BuildHasher>(
