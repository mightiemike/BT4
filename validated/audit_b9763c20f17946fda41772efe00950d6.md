### Title
Unbounded per-cycle reward loop in `MortgageService.withdrawReward` can cause excessive on-chain computation - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The pSTAKE report describes an unbounded `for` loop over historical reward-rate change records that can exhaust gas when a user has not claimed rewards for a long time. The `MortgageService` reward-withdrawal path in java-tron contains an analogous unbounded loop: `getOldReward` iterates once per maintenance cycle between a user's last-claimed cycle and the current cycle, invoking a further per-vote loop for each cycle, with no cap on how many cycles can accumulate.

### Finding Description
`MortgageService.withdrawReward` (called by any unprivileged account via `WithdrawBalanceActuator`, and by the TVM `withdrawReward` opcode via `WithdrawRewardProcessor`/`VoteRewardUtil`) computes the reward owed since the account's last withdrawal by calling `computeReward(beginCycle, endCycle, accountCapsule)`: [1](#0-0) 

When `beginCycle` predates `newAlgorithmCycle` (the cycle at which the O(1) VI-based algorithm became effective), the code falls back to `getOldReward`, which loops over every maintenance cycle between `begin` and `end`, and for each cycle re-scans the account's full vote list via `computeReward(cycle, votes)`: [2](#0-1) [3](#0-2) 

This is structurally identical to the reported bug: a per-user reward computation whose cost scales with `(number of elapsed cycles) × (number of votes)`, with no upper bound enforced on `endCycle - beginCycle`, and each iteration performing a store lookup (`delegationStore.getReward`, `getWitnessVote`). Maintenance cycles occur roughly every 6 hours, so an account that never withdraws accumulates cycles indefinitely as long as `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()` (i.e. `allowOldRewardOpt`/new-algorithm activation) has not moved past that account's `beginCycle`.

This code path is reachable by any unprivileged account: `WithdrawBalanceActuator.execute` calls `mortgageService.withdrawReward(...)` unconditionally for the transaction's owner address, and the equivalent `VoteRewardUtil.withdrawReward` is reachable from TVM contract execution (`Program.withdrawReward`) through `WithdrawRewardProcessor`. [4](#0-3) [5](#0-4) 

### Impact Explanation
Unlike Ethereum-style gas metering per opcode, TRON actuators for non-TVM contract types (like `WithdrawBalanceContract`) are charged a fixed bandwidth/energy fee regardless of the actual CPU work performed inside `execute()`. If the old-reward loop path is still reachable in production (i.e., accounts with `beginCycle` older than `newRewardAlgorithmEffectiveCycle`, or in networks/scenarios where the new algorithm hasn't been enabled long enough to cover all historical cycles), a single fixed-fee transaction can force the node to execute a loop whose iteration count grows with wall-clock time since the account's last withdrawal (or last SR vote change), consuming disproportionate CPU/time during block processing relative to the fee paid. This is an underpriced-computation / potential block-processing-delay risk analogous to the reported "run out of gas" issue, though it manifests as CPU exhaustion/timing risk rather than an explicit VM revert, because java-tron's non-TVM actuators don't meter internal loop cost the way TVM opcodes do.

### Likelihood Explanation
The vulnerable branch is only reached when `beginCycle < newRewardCalStartCycle` (the effective cycle of the new O(1) VI algorithm) as computed by `RewardViCalService`/`DynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`. On networks where this migration has been active for a long time and all accounts have since withdrawn at least once, the old loop is cold code. I was not able to confirm from the indexed code whether `allowOldRewardOpt`/the new-algorithm effective cycle is unconditionally in the past on mainnet, or whether there remain any accounts/paths that can still trigger cycle counts large enough to matter (this requires runtime/on-chain state inspection outside the scope of static code search). This uncertainty limits confidence in current-day exploitability, though the code pattern itself is a genuine unbounded-loop-over-history construct matching the reported bug class.

### Recommendation
- Cap the number of cycles processed per `withdrawReward` call (e.g., process at most N cycles per transaction) and allow multiple partial-withdrawal transactions to fully catch up, mirroring the pSTAKE-recommended "partial update" mitigation.
- Ensure the VI-based (`RewardViCalService`) algorithm fully covers all historical cycles once activated so `getOldReward`'s cycle-by-cycle loop becomes fully dead code, and add a defensive cap even if unreachable, since the code depends on external activation-cycle state.

### Proof of Concept
Not applicable — this is a structural code-pattern analog, not a directly exploitable PoC confirmed against current mainnet state, because it depends on whether any account's `beginCycle` is still below `newRewardAlgorithmEffectiveCycle`. Conceptually: an account votes for many SRs, refrains from calling `WithdrawBalanceContract`/`withdrawReward` across many maintenance cycles while `beginCycle` remains below the new-algorithm cutoff, then submits a single withdraw transaction; `MortgageService.computeReward` → `getOldReward` iterates `endCycle - beginCycle` times, each doing a `computeReward(cycle, votes)` scan over all votes, for a fixed transaction fee.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
