### Title
Unfreezing BANDWIDTH/ENERGY stake under the new resource model leaves VotesStore entries backed by stale, higher `tronPower` than the account currently holds - (File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java)

### Summary
`UnfreezeBalanceV2Actuator.updateVote` only recomputes/shrinks an account's votes when the unfrozen resource is `TRON_POWER`, or on the one-time "clear all votes" migration step. For accounts that were created and staked purely through Stake-2.0 (`FreezeBalanceV2Contract`), that one-time migration step never fires because `initializeOldTronPower()` immediately sets `oldTronPower` to `-1` (since legacy `getTronPower()` is `0`), permanently placing them in the "already migrated" branch. From then on, unfreezing `BANDWIDTH`/`ENERGY` returns early without touching `VotesStore`, even though `getAllTronPower()` (used both to cap votes in `VoteWitnessActuator.validate()` and to compute vote weight) sums BANDWIDTH+ENERGY+TRON_POWER V2 frozen balances together as the voting-power base.

### Finding Description
`updateVote` in `UnfreezeBalanceV2Actuator`: [1](#0-0) 

only reaches the proportional vote-shrink block (which recomputes `newVoteCount` from `ownedTronPower = accountCapsule.getAllTronPower()`) when the unfreeze resource is `TRON_POWER` or when `supportAllowNewResourceModel()` is false: [2](#0-1) 

For `BANDWIDTH`/`ENERGY` while `oldTronPowerIsInvalid()` is already true, the function returns immediately with the comment "there is no need to change votes": [3](#0-2) 

The one-time "clear all votes" branch, intended to force a fresh vote after the Stake-2.0 migration, only runs while `oldTronPower != -1`: [4](#0-3) 

But `oldTronPower` is set to `-1` immediately for any account that never used legacy (Stake-1.0) `TRON_POWER` freezing, since `initializeOldTronPower()` falls back to `-1` when `getTronPower()==0`: [5](#0-4) [6](#0-5) 

This means every pure Stake-2.0 account (i.e., one that only ever used `FreezeBalanceV2Contract`) enters the "already migrated" (`oldTronPower == -1`) state from its very first `UnfreezeBalanceV2Contract` call, skipping the one-time full-vote clear entirely. `VoteWitnessActuator.validate()` accepts votes up to the combined `getAllTronPower()` (BANDWIDTH+ENERGY+TRON_POWER V2), i.e., BANDWIDTH/ENERGY frozen stake does back voting power under the new model: [7](#0-6) 

Attack flow:
1. Attacker freezes stake across BANDWIDTH, ENERGY and TRON_POWER via `FreezeBalanceV2Contract`.
2. Attacker casts a vote via `VoteWitnessContract`, validated against the combined `getAllTronPower()`.
3. Attacker's first `UnfreezeBalanceV2Contract` call (of any resource type) sets `oldTronPower` to `-1` directly (bypassing the vote-clear branch) since legacy `getTronPower()` is 0.
4. Attacker repeatedly issues `UnfreezeBalanceV2Contract(BANDWIDTH)`/`(ENERGY)`, each of which hits the early-return branch and never recomputes/shrinks `VotesStore`/`accountCapsule` votes.
5. The account's real `getAllTronPower()` shrinks, but its recorded votes (both in `AccountCapsule.votesList` and `VotesStore`) remain at the original, now-unbacked, higher value.

### Impact Explanation
Votes tallied at maintenance time from `VotesStore` remain inflated relative to the attacker's real remaining stake, corrupting witness ranking and reward distribution accounting - an unprivileged user can retain outsized voting influence while withdrawing most of their economic stake (only the TRON_POWER-designated portion needs to stay frozen to avoid triggering a TRON_POWER-driven recompute).

### Likelihood Explanation
Fully reachable through ordinary, unprivileged transactions (`FreezeBalanceV2Contract`, `VoteWitnessContract`, `UnfreezeBalanceV2Contract`) requiring `supportAllowNewResourceModel()` to be enabled (a chain parameter already assumed active in the current test suite) and no legacy Stake-1.0 TRON_POWER history — which is the default/likely state for any account onboarded purely under Stake 2.0. It is deterministic and repeatable for any number of BANDWIDTH/ENERGY unfreeze operations, as confirmed by the existing test `testUnfreezeBalanceForEnergyWithoutOldTronPowerAfterNewResourceModel`, which explicitly asserts the votes list is unchanged after an ENERGY-only unfreeze once `oldTronPower == -1`: [8](#0-7) 

### Recommendation
When `supportAllowNewResourceModel()` is true and `oldTronPowerIsInvalid()`, do not unconditionally skip vote recompute for `BANDWIDTH`/`ENERGY` unfreezes. Instead, always recompute/shrink votes proportionally against the current `getAllTronPower()` (the same logic already used for `TRON_POWER`), regardless of which resource type was unfrozen, since all three resource types contribute to voting power under the new model.

### Proof of Concept
```java
@Test
public void testBandwidthUnfreezeLeavesStaleVotes() throws Exception {
  dbManager.getDynamicPropertiesStore().saveAllowNewResourceModel(1L);
  long now = System.currentTimeMillis();
  dbManager.getDynamicPropertiesStore().saveLatestBlockHeaderTimestamp(now);

  byte[] owner = ByteArray.fromHexString(OWNER_ADDRESS);
  AccountCapsule account = dbManager.getAccountStore().get(owner);
  // Stake spread across all three resource types via V2 freeze only (no legacy TronPower)
  account.addFrozenBalanceForBandwidthV2(600_000_000L);
  account.addFrozenBalanceForEnergyV2(300_000_000L);
  account.addFrozenForTronPowerV2(100_000_000L);
  dbManager.getAccountStore().put(owner, account);

  // Vote using combined getAllTronPower() (1000 TRX worth => 1000 votes)
  VoteWitnessActuator voteActuator = new VoteWitnessActuator();
  voteActuator.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getVoteContract(OWNER_ADDRESS, WITNESS_ADDRESS, 1000L));
  voteActuator.validate();
  voteActuator.execute(new TransactionResultCapsule());

  // Drain BANDWIDTH stake entirely (900/1000 of total tronPower)
  UnfreezeBalanceV2Actuator unfreezeActuator = new UnfreezeBalanceV2Actuator();
  unfreezeActuator.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getContractForBandwidthV2(OWNER_ADDRESS, 600_000_000L));
  unfreezeActuator.validate();
  unfreezeActuator.execute(new TransactionResultCapsule());

  unfreezeActuator.setAny(getContractForCpuV2(OWNER_ADDRESS, 300_000_000L)); // ENERGY
  unfreezeActuator.validate();
  unfreezeActuator.execute(new TransactionResultCapsule());

  AccountCapsule after = dbManager.getAccountStore().get(owner);
  // BUG: votes remain at 1000 though only 100 TRX worth of TRON_POWER-backing stake remains
  Assert.assertEquals(1000L, after.getVotesList().get(0).getVoteCount());
  Assert.assertEquals(100_000_000L, after.getAllTronPower());
  // Expected (fixed) behavior: votes should shrink to <= 100 to match remaining tronPower
}
```
Expected assertion under a fix: `after.getVotesList()` vote counts should be proportionally reduced (or capped) to match `after.getAllTronPower()`, not remain at the original 1000-vote level.
