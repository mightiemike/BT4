### Title
Uncharged, attacker-controlled account loads via `unpack_token_account`'s mint lookup - ([File: svm/src/transaction_balances.rs])

### Summary
`BalanceCollector::collect_balances` calls `SvmTokenInfo::unpack_token_account`, which performs an unconditional second `account_loader.load_account(&mint)` call for every non-invoked account in a transaction whose owner matches a known SPL token program id. The `mint` pubkey is read directly out of attacker-controlled account data and is never validated against, or counted toward, the transaction's `loaded_accounts_data_size` limit or CU/fee accounting, so an attacker can force the validator to perform extra accounts-db loads of arbitrarily large accounts essentially for free.

### Finding Description
In `collect_balances`, for every account key in a transaction that is writable/non-invoked and whose owner is a known SPL token id, the code calls `SvmTokenInfo::unpack_token_account`: [1](#0-0) 

That function does: [2](#0-1) 

The `mint` value is parsed straight from `account.data()` — bytes the attacker fully controls, since the "token account" only needs its `owner` field set to a known SPL token program id and its data shaped so `generic_token::Account::unpack` succeeds (this unpack logic itself lives in the external `spl_generic_token` dependency crate, so its exact validation strictness could not be fully confirmed here). There is no requirement that `mint` correspond to a real, previously-associated mint, nor that the pointed-to account be small. `account_loader.load_account(&mint)` then performs a full `AccountLoader::do_load` → `AccountsDb::do_load` lookup: [3](#0-2) [4](#0-3) 

Crucially, the `mint` pubkey referenced here is not part of the transaction's account key list, so its size is never counted against the transaction's `loaded_accounts_data_size` limit or its CU cost, both of which are enforced earlier, during normal transaction loading (`load_transaction_account`), not during post-execution balance collection. This load also happens twice per relevant account (`collect_pre_balances` and `collect_post_balances`): [5](#0-4) 

Existing guards (slot/ancestor checks, zero-lamport filtering, `AccountLoader`'s per-batch `loaded_accounts` cache) do not prevent this: the per-batch cache only deduplicates repeated loads of the *same* pubkey within one batch, and an attacker deliberately using a unique `mint` pointer per transaction defeats that cache entirely.

### Impact Explanation
This is a resource-cost asymmetry / disproportionate-CPU-and-storage-I/O issue (per-account work not proportional to fees paid), matching the "resource exhaustion during normal (non-privileged) block processing" bounty category. It only manifests on nodes that enable transaction balance recording (i.e., have a `TransactionStatusSender` configured — a standard, non-privileged deployment mode for RPC/full-history nodes), not on every validator by default.

### Likelihood Explanation
Preconditions: only requires a normal user able to create/own accounts with `owner` set to a known SPL token program id and craft their data to pass `generic_token::Account::unpack`, then reference an arbitrary large existing account's pubkey as `mint`. No privileged access is needed; the attacker only pays ordinary per-signature fees plus minor CU cost for the small dummy token account itself. The extra `mint` load cost scales with the size of whatever account the attacker points to and with the number of such dummy accounts included per transaction, entirely decoupled from fees paid. This is repeatable across arbitrarily many transactions.

### Recommendation
Bound or charge the extra mint lookup: either (a) require the `mint` account to already be present in the transaction's account key list (so its size is already accounted for under `loaded_accounts_data_size`), or (b) cap the size of accounts eligible for this secondary lookup, or (c) explicitly charge/limit the aggregate bytes loaded by `collect_balances` per transaction and reject/skip token-balance collection beyond that budget.

### Proof of Concept
Integration test plan in `svm` crate:
1. Create N transactions, each including one dummy account with `owner = spl_token::id()` and data shaped as a minimal valid `generic_token::Account` whose `mint` field points to a distinct, pre-existing large account (e.g., a maximally-sized `10 MiB` account owned by the attacker, created ahead of time).
2. Enable `enable_transaction_balance_recording` in `SvmTestEnvironment`/`env.processing_config.recording_config` as done in existing tests: [6](#0-5) 
3. Measure wall-time / accounts-db bytes-read for `collect_pre_balances`/`collect_post_balances` (via `ExecuteTimingType::CollectBalancesUs`) as N and the referenced mint account size grow, and compare against a baseline where the "mint" is a tiny/nonexistent account.
4. Assert that measured I/O/time scales with attacker-chosen mint size × N while transaction fees remain constant per transaction, demonstrating the fee/cost mismatch.

impl SvmTokenInfo {
    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        account: &AccountSharedData,
        index: usize,
    ) -> Option<Self> {
        let program_id = *account.owner();
        let generic_token::Account {
            mint,
            owner,
            amount,
        } = generic_token::Account::unpack(account.data(), &program_id)?;

        let mint_account = account_loader.load_account(&mint)?;
        if *mint_account.owner() != program_id {
            return None;
        }

        let generic_token::Mint { decimals, .. } =
            generic_token::Mint::unpack(mint_account.data(), &program_id)?;

        Some(Self {
            account_index: index.try_into().ok()?,
            mint,
            amount,
            owner,
            program_id,
            decimals,
        })
    }

    pub(crate) fn load_account(&mut self, account_key: &Pubkey) -> Option<AccountSharedData> {
        match self.do_load(account_key) {
            // Exists, from AccountLoader.
            (Some((account, _last_modification_slot)), false) => Some(account),
            // Not allocated, but has an AccountLoader placeholder already.
            (None, false) => None,
            // Exists in accounts-db. Store it in AccountLoader for future loads.
            (Some((account, last_modification_slot)), true) => {
                self.loaded_accounts
                    .insert(*account_key, (account.clone(), last_modification_slot));
                Some(account)
            }
            // Does not exist and has never been seen.
            (None, true) => {
                self.loaded_accounts
                    .insert(*account_key, (AccountSharedData::default(), 0));
                None
            }
        }
    }
