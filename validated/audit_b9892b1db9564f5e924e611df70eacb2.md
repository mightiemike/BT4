### Title
Ancient-squash silently discards carry-forward tombstones on a release build (`debug_assert!`-only guard) — ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
The reported ALCX bug is a "merge/combine operation forgets to carry forward accrued state, permanently losing it." The closest reachable analog in `agave` is in the ancient-append-vec "squash" (combine) path: when combining ancient slot storages, `finish_combine_ancient_slots_packed_internal` assumes that any zero-lamport tombstone that must be carried forward for incremental-snapshot correctness can never appear at this point, and only checks that assumption with a `debug_assert!`, which is compiled out in release/production validator builds. If the invariant is ever violated, the tombstone data is silently dropped rather than an explicit runtime check preventing data loss.

### Finding Description
`shrink_collect` (accounts-db/src/accounts_db.rs, ~L2568-2599) computes `tombstones_to_carry_forward`: zero-lamport, single-ref accounts that are *not yet* purgeable because the latest full snapshot has not advanced past their slot (`can_purge_zero_lamport_single_ref_after_shrink`). These bytes must be rewritten to the new storage so an incremental snapshot can still propagate the deletion (see the dedicated regression test `test_incremental_snapshots_handle_tombstones` in `runtime/src/snapshot_bank_utils.rs`, L1450-1607, which explicitly documents that dropping such a tombstone during shrink would "resurrect" a deleted account).

For ordinary `shrink_storage` (accounts-db/src/accounts_db.rs, L2781-2874) this is handled correctly: `tombstones_to_carry_forward` is rewritten via `store_tombstones` after `store_accounts_for_shrink`.

But for the *ancient squash* path (`combine_ancient_slots_packed` → `calc_accounts_to_combine` → `finish_combine_ancient_slots_packed_internal`, accounts-db/src/ancient_append_vecs.rs, L722-774), there is **no code path that rewrites `tombstones_to_carry_forward`** into the newly packed ancient storage at all. The implementation instead relies purely on the reasoning that "ancient squash only runs on slots far older than the latest full snapshot," so tombstones there should always already be purgeable and the list should always be empty: [1](#0-0) 

This invariant is enforced only by:
```
debug_assert!(
    shrink_collect.tombstones_to_carry_forward.is_empty(),
    "ancient squash reached a carry-forward tombstone at slot {slot}",
);
``` [2](#0-1) 

`debug_assert!` compiles to a no-op in release builds (Solana/Agave validators run release builds in production). If the "ancient squash only runs far older than the latest full snapshot" assumption is ever wrong — e.g., because `latest_full_snapshot_slot` starts at `None`/very low before the node's first full snapshot completes, or advances more slowly than the epoch-based ancient boundary in some deployment/timing scenario — `shrink_collect` will populate a non-empty `tombstones_to_carry_forward` for a slot being ancient-squashed. In that case:
1. In a debug build, the process panics (a node crash/DoS on any validator running a debug build, or in test/CI environments).
2. In a release build (the production configuration), the assertion is entirely skipped, and the tombstone bytes are simply never written to the packed ancient storage — they are captured in `shrink_collect.tombstones_to_carry_forward` (accounts-db/src/accounts_db.rs, L253-268) but that `Vec` is never consumed by the ancient-squash write path (`write_packed_storages`/`write_one_packed_storage`, accounts-db/src/ancient_append_vecs.rs, L928-950, only handles `alive_accounts`/`many_refs_newest`).

This is structurally identical to the ALCX bug class: a combine/merge operation correctly handles the "primary" state (alive accounts) but omits carrying forward a secondary piece of pending state (the tombstone) that a sibling operation (`shrink_storage`) does carry forward, and the omission is silent rather than hard-failing in production.

### Impact Explanation
If triggered, this results in silently losing tombstone records that are required for an incremental snapshot to correctly propagate a zero-lamport-account deletion. As documented by the project's own regression test (`test_incremental_snapshots_handle_tombstones`), losing such a tombstone causes a full+incremental snapshot rebuild to resurrect a previously-deleted, zero-lamport account with its old (positive) balance from the full snapshot — i.e., a **silent balance/state divergence** between the live, correctly-replayed bank and a bank rebuilt from snapshot. This is exactly the class of "honest-node snapshot-vs-replay mismatch" / "silent balance change" impact called out as in-scope.

### Likelihood Explanation
Likelihood is constrained by how strong the "ancient squash only runs far older than latest full snapshot" invariant actually is in practice — I was not able to fully confirm from the available code whether there exists a concrete scheduling path (e.g., cold start before the first full snapshot, or a slow/aborted full-snapshot cadence relative to `get_oldest_non_ancient_slot`) that lets `shrink_ancient_slots`/`combine_ancient_slots_packed` run against a slot that is *not* yet snapshot-covered while it still holds a non-purgeable zero-lamport single-ref account. `sweep_slots_after_snapshot` and `set_latest_full_snapshot_slot` calls are both driven from the same `AccountsBackgroundService` thread sequentially, which reduces (but given only the code I reviewed, doesn't conclusively rule out) the chance of the invariant being violated in the mainline validator flow. Because the enforcement mechanism is a `debug_assert!` rather than an unconditional check, any latent violation of the invariant is currently undetectable in production (release) builds — the code would need to be exercised specifically to know for certain whether the assumption always holds.

### Recommendation
1. Replace the `debug_assert!` in `finish_combine_ancient_slots_packed_internal` with an unconditional assertion (or, better, an explicit runtime handling path) so a production/release build cannot silently proceed if `tombstones_to_carry_forward` is non-empty.
2. Implement an actual carry-forward path for tombstones in the ancient-squash/pack pipeline (mirroring `shrink_storage`'s `store_tombstones` call) so that, even if the invariant is occasionally violated, correctness is preserved rather than merely detected.
3. Add a targeted test that forces `combine_ancient_slots_packed`/`calc_accounts_to_combine` to run against a slot with a non-purgeable zero-lamport single-ref tombstone (i.e., with `latest_full_snapshot_slot` set below that slot) to verify the tombstone survives the ancient squash and an incremental snapshot taken afterward still reflects the deletion.

### Proof of Concept
Not independently reproduced against a running validator; this is derived from static analysis of the code paths cited above (`shrink_collect`, `finish_combine_ancient_slots_packed_internal`, and the existing `test_incremental_snapshots_handle_tombstones` test, which demonstrates the general consequence of a dropped tombstone via the `shrink_storage` path). A concrete PoC would need to construct a scenario where `combine_ancient_slots_packed` is invoked on a slot holding a zero-lamport single-ref account while `latest_full_snapshot_slot` is still below that slot (e.g., by manually calling `set_latest_full_snapshot_slot` to a low value and then invoking `shrink_ancient_slots`/`combine_ancient_slots_packed` on such a slot in a `cfg(not(debug_assertions))` test build), then verifying the resulting packed storage no longer contains the tombstone and that a subsequent incremental-snapshot round-trip resurrects the deleted account, analogous to `test_incremental_snapshots_handle_tombstones` (runtime/src/snapshot_bank_utils.rs, L1450-1607) but exercising the ancient-squash path instead of `shrink_storage`.
