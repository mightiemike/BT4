Based on my investigation, I found a concrete indexing bug in the sharded-execution total-supply reconciliation logic that corrupts the committed `total_supply` write-set value whenever more than one shard mutates total supply within the same round.

### Title
Off-by-`shard_id` indexing corrupts aggregated `total_supply` write set in sharded block execution - (File: `aptos-move/aptos-vm/src/sharded_block_executor/sharded_aggregator_service.rs`)

### Summary
`aggregate_and_update_total_supply` reconstructs the true, ledger-wide `total_supply` value for every transaction output after sharded parallel execution, because during execution every shard/round observes a shared sentinel (`TOTAL_SUPPLY_AGGR_BASE_VAL`) instead of the real value [1](#0-0) . The delta lookup used when patching each shard's transactions reads the wrong array index, mixing in delta contributions from *other shards of the same round*, which by design never observed each other's writes during execution.

### Finding Description
`AggregatorOverriddenStateView::get_state_value` always returns the constant `TOTAL_SUPPLY_AGGR_BASE_VAL` for the `TOTAL_SUPPLY_STATE_KEY`, unconditionally, regardless of round or shard [2](#0-1) . Shards within the same round execute independently/in parallel with no visibility into each other's `total_supply` writes (only cross-round dependencies are resolved via the normal state view for non-total-supply keys) [3](#0-2) .

Because of this, the true reconstruction rule must be: for a transaction in `(round r, shard s)`, the correction delta should be the cumulative sum of every shard's delta from **all fully preceding rounds** `0..r-1` only — never from other shards of the *same* round `r`, since those never fed into this shard's local computation.

The deltas are recorded in round-major flattened order, one entry per `(round, shard)` pair, with the fill loop populating index `round*num_shards + shard_id + 1` (comment confirms this): [4](#0-3) 

However, when patching the actual transaction outputs, the code reads back:
```rust
let delta_for_round =
    aggr_total_supply_delta_ref[round * num_shards + shard_id] + base_val_delta;
``` [5](#0-4) 

This index is off by exactly `1` relative to how the array was populated for the `(round, shard_id)` pair itself, but — critically — it is **not** simply "off by one" in a way that cancels out. Because the array holds a *cumulative* sum across the round-major flattened sequence, `aggr_total_supply_delta[round*num_shards + shard_id]` equals the cumulative sum of all `(round', shard')` pairs whose flattened index is strictly less than `round*num_shards + shard_id`. This set includes:
- all shards of every fully preceding round (`round' < round`) — **correct and intended**, **and also**
- shards `0..shard_id-1` of the **current** round `round` — **incorrect**, since those sibling shards' `total_supply` deltas were never visible to shard `shard_id` during actual execution (per the sentinel-override design above).

The correct index should have been `round * num_shards` (independent of `shard_id`), so that every shard within the same round receives the identical "delta contributed by prior rounds only" correction. Instead, shards with a higher `shard_id` erroneously accumulate extra delta from lower-numbered sibling shards in the same round, while never being credited to those siblings themselves (siblings with lower `shard_id` don't get this extra delta applied to their own outputs).

### Impact Explanation
This bug directly corrupts the committed `TOTAL_SUPPLY_STATE_KEY` write set entries persisted to the ledger for every affected transaction whenever `num_shards > 1` and more than one shard mutates total supply (mints/burns APT, e.g., via `coin::mint`/`coin::burn`, gas fee minting/burning, staking rewards) within the same round. Because different shards would end up with a different (and each individually wrong) `total_supply` value baked into their write sets for the same logical global counter, the final on-chain `total_supply` resource diverges from the true VM-computed aggregate. This is durable ledger corruption of a system state value that all validators executing the same sharded-execution path must reproduce identically to remain in consensus — this only manifests when sharded/remote execution (`aptos-move/aptos-vm/src/sharded_block_executor`) is actually used, which is a non-default execution mode, but when triggered, it corrupts a fundamental global invariant (`total_supply`) rather than user-controlled data.

### Likelihood Explanation
Triggering requires: (1) sharded block execution enabled (multiple shards, `num_shards > 1`), and (2) more than one shard within the same round producing transactions that mutate `total_supply` (mint/burn), which is common for ordinary blocks containing gas-fee burns/mints or staking-reward distributions spread across shards. No malicious or privileged actor is needed — this is a deterministic logic bug that fires under normal sharded-execution usage, not an adversarial input.

### Recommendation
Change the read-back index to not depend on `shard_id`:
```rust
let delta_for_round =
    aggr_total_supply_delta_ref[round * num_shards] + base_val_delta;
```
so every shard in a given round is corrected using only the cumulative delta contributed by fully preceding rounds, consistent with how the sentinel-override execution model actually isolates same-round shards from one another. Add a regression test with `num_shards >= 2` and multiple shards mutating total supply in the same round, asserting the final aggregated `total_supply` write matches the sum of all individual deltas plus the real base value.

### Proof of Concept
Conceptual trace with `num_shards = 2`, `num_rounds = 1`:
- Shard 0 in round 0 mints `+100` (relative to `TOTAL_SUPPLY_AGGR_BASE_VAL`).
- Shard 1 in round 0 mints `+50` (relative to `TOTAL_SUPPLY_AGGR_BASE_VAL`).
- Fill loop: `aggr_total_supply_delta[1] = +100` (shard 0), `aggr_total_supply_delta[2] = +150` (shard 0 + shard 1, cumulative).
- Patch loop for shard 0 (`shard_id=0`): reads `aggr_total_supply_delta_ref[0*2+0] = aggr_total_supply_delta[0] = 0` → correct (no prior rounds).
- Patch loop for shard 1 (`shard_id=1`): reads `aggr_total_supply_delta_ref[0*2+1] = aggr_total_supply_delta[1] = +100` → **incorrectly adds shard 0's same-round delta**, even though shard 1's transactions never observed shard 0's mint during execution. Shard 1's committed `total_supply` write becomes `real_base + 50 (its own delta) + 100 (erroneously borrowed from shard 0) = real_base + 150`, double counting shard 0's contribution, while shard 0's own committed write only reflects `real_base + 100`. The two shards disagree on the final `total_supply`, and the erroneously-inflated value (`real_base + 150` instead of the correct `real_base + 150` only in the *global*/last output, not per-shard outputs) gets persisted inconsistently across transaction outputs within the block, corrupting the ledger's `total_supply` resource history.
