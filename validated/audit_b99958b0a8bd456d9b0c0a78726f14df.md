## Finding: Stale/reverted Cairo 0 (deprecated) class definitions are served from the sequencer's shared class cache without re-validation against committed state

### Title
Undeclared/Reverted Cairo 0 Class Remains Usable via Stale Global Class Cache, Bypassing Declaration Check - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` re-validates a cache hit against the committed state only for Cairo 1 classes. For Cairo 0 (`RunnableCompiledClass::V0`) cache hits, no re-validation happens at all, even though the same `ContractClassManager` cache is shared across all block-building proposals and view calls for the lifetime of the process. A Cairo 0 class that was executed (and thus cached) during a proposal that is later aborted/discarded (never committed) remains servable forever afterward as if it were declared.

### Finding Description
In `get_compiled_from_class_manager`, a cache hit is handled as: [1](#0-0) 

For non-V0 (Cairo 1) classes, the code explicitly re-checks `self.state_reader.is_declared(class_hash)` because "the cache does not guarantee [declaration], it might contain a declared class from a reverted block." For `RunnableCompiledClass::V0(_)`, the match arm is a no-op — no equivalent check exists. This is not an oversight in a helper: `FetchCompiledClasses::is_declared` is documented to always return `false` for Cairo 0 classes: [2](#0-1) 

and the concrete implementation used by the sequencer's batcher/full-node reader (`ApolloReader::is_declared`) only checks the Cairo-1 declared-classes table, never the deprecated table: [3](#0-2) 

Critically, this `ContractClassManager` cache is not scoped to a single block or proposal — it is a single, long-lived, process-wide cache explicitly shared by block production and by view calls: [4](#0-3) [5](#0-4) 

Proposals can be aborted/discarded without ever being committed (e.g. `abort_proposal`/`BlockBuilderError::Aborted`): [6](#0-5) [7](#0-6) 

If a Declare (V0) transaction is executed during such a proposal, `set_and_compile` inserts the compiled Cairo 0 class into the shared global cache regardless of whether the proposal is ultimately committed: [8](#0-7) 

Because Cairo 0 cache hits skip the `is_declared` re-check, a subsequent, unrelated transaction that references this class hash (e.g. `deploy` or `library_call`) will be served the cached compiled class as if it were validly declared on the canonical, committed chain — even though the actual persisted state never contains that declaration.

### Impact Explanation
A node whose cache happened to retain the stale (never-committed) Cairo 0 class will execute a transaction that references an undeclared class hash successfully, while a node with a cold cache (or one that never ran the aborted proposal) will correctly return `StateError::UndeclaredClassHash` per its committed storage. This produces divergent execution results/state diffs for the same transaction across otherwise-honest sequencer nodes, i.e., honest-node divergence and a wrong committed state root/state-diff for that block — the same "trusted-but-not-actually-authorized artifact accepted" bug class as the referenced Keystone advisory (a revoked/invalid credential being treated as valid because the revocation/validity check was skipped).

### Likelihood Explanation
Triggering the precondition (a Declare V0 transaction executed in a proposal that gets aborted, e.g., due to deadline/timeout/full block during `propose_block`, or because a competing proposal wins the round) is a normal, frequent occurrence in block building and does not require any privileged access — any account able to submit a Declare transaction can populate this global cache. The follow-up transaction referencing the class hash can be submitted by anyone, including the same attacker.

### Recommendation
Apply the same `is_declared`-style re-validation to `RunnableCompiledClass::V0` cache hits as is done for Cairo 1, using a state-reader check that actually queries the deprecated-declared-classes table (unlike the current `is_declared`, which is documented to always return `false` for Cairo 0 and therefore cannot be reused as-is). Alternatively, invalidate/evict cache entries for classes executed in proposals that are aborted or not committed, so the shared `ContractClassManager` cache can never retain state from a block that never became canonical.

### Proof of Concept
1. Sequencer node begins building/validating a proposal for height `N` that includes a `Declare` (Cairo 0) transaction for class hash `C`.
2. During execution, `get_compiled_from_class_manager` misses the cache, fetches `C` from the state reader, and calls `contract_class_manager.set_and_compile(C, CompiledClasses::V0(...))`, populating the shared global cache.
3. The proposal is aborted (deadline reached, superseded by another proposer's block, or otherwise discarded) — `C` is never written to committed storage as declared.
4. A later transaction at height `N+1` (submitted by anyone) deploys a contract with class hash `C` or performs a `library_call` to `C`.
5. On this node, `get_compiled_from_class_manager` hits the cache for `C`; because it matches `RunnableCompiledClass::V0(_)`, no `is_declared` check runs, and the (never-committed) class is returned and executed successfully.
6. A different honest node that did not retain that stale cache entry queries its committed storage and correctly returns `StateError::UndeclaredClassHash(C)` for the same transaction, producing a differing execution result/state diff between honest nodes for the same block.
