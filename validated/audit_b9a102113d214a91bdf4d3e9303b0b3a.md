### Title
Hardcoded 0.01% precision-loss tolerance in `ExchangeWithdrawActuator` can permanently block liquidity withdrawal from a TRC10/TRX exchange pool - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator.doValidate()` enforces a hardcoded, non-configurable 0.01% ("0.0001") rounding/precision tolerance when computing the paired-token amount to return on an exchange withdrawal. Exactly like the Yearn `maxLoss` default of 0.01% that cannot be overridden by the caller, this fixed threshold is baked into the actuator with no way for the exchange creator to specify an acceptable tolerance, so any withdrawal whose integer-division remainder exceeds that fixed bound is rejected with `ContractValidateException("Not precise enough")`.

### Finding Description
When an exchange creator calls `ExchangeWithdrawContract`, `doValidate()` computes `anotherTokenQuant` via integer division of the pool balances, then re-derives the "true" ratio with `BigDecimal` division to 4-decimal precision and compares the remainder against a hardcoded `0.0001` (0.01%) fraction of `anotherTokenQuant`: [1](#0-0) 
The non-hardened branch performs the equivalent check using `double` arithmetic with the same fixed `0.0001` bound: [2](#0-1) 
The same fixed-bound pattern is duplicated for the reverse-token branch: [3](#0-2) 
There is no field on `ExchangeWithdrawContract`, nor any actuator logic, that lets the caller supply an acceptable tolerance or bypass the check — the 0.01% bound is a compile-time constant identical in spirit to the Yearn vault's hardcoded `maxLoss = 1` (0.01% BPS) that the external report flags as the root cause. Because the pool ratio (`firstTokenBalance` / `secondTokenBalance`) continuously drifts through ordinary trading via `ExchangeTransactionActuator`, an exchange creator who wants to withdraw a specific `tokenQuant` of one side has no guaranteed way to satisfy the fixed-precision constraint for that side once the pool ratio has moved into an "imprecise" region relative to the requested amount, and no protocol-level mechanism exists to relax the check.

### Impact Explanation
Any exchange creator can be denied a specific withdrawal (`ContractValidateException("Not precise enough")`) even though they own a economically valid claim on the pool, purely because the actuator enforces an immovable 0.01% precision bound rather than exposing it as a validated caller-supplied parameter. This is a state-transition validation defect in the `ExchangeWithdrawActuator`, directly reachable from a broadcast transaction (`ExchangeWithdrawContract`) by any unprivileged account that created an exchange, and it can force the creator to iteratively probe different `tokenQuant` values to find one that clears the hardcoded tolerance, or in adverse pool-ratio configurations be effectively unable to withdraw the exact quantities they need — mirroring the Medium-severity "assets become undrawable due to unconfigurable loss/tolerance parameter" bug class from the report.

### Likelihood Explanation
The check triggers deterministically whenever `bigSecondTokenBalance * bigTokenQuant / bigFirstTokenBalance` (or the mirrored ratio) does not divide evenly enough to stay within 0.01% of the truncated integer result — a condition that arises naturally as pool balances change through normal `ExchangeTransactionActuator` trading, and worsens as pool balances grow larger (fixed relative tolerance on larger absolute numbers). No special privileges or malicious peers are required; a legitimate exchange creator hits this simply by choosing an "unlucky" `tokenQuant` relative to the current pool state.

### Recommendation
Do not enforce an immovable, hardcoded precision/loss tolerance in `ExchangeWithdrawActuator`. Either remove the precision check entirely in favor of exact (non-lossy) computation, or, if a tolerance is required, make it an explicit, validated field on `ExchangeWithdrawContract` supplied by the caller (bounded to a sane maximum), analogous to exposing Yearn's `maxLoss` parameter, so users can control how much rounding they accept rather than being subject to a silent constant baked into the actuator.

### Proof of Concept
1. Create an exchange pool with `firstTokenBalance = 100_000_000`, `secondTokenBalance = 200_000_000` (as in the existing test fixtures).
2. As the creator, call `ExchangeWithdrawContract` requesting `secondTokenId` with `quant = 9991`.
3. `doValidate()` computes `anotherTokenQuant = firstTokenBalance * quant / secondTokenBalance` via integer division, then compares the BigDecimal-rounded ratio's remainder against `anotherTokenQuant * 0.0001`; because the remainder exceeds this hardcoded bound, the call reverts with `"Not precise enough"`, as reproduced by the existing test `SameTokenNameOpenNotPreciseEnough`: [4](#0-3) 
4. The creator cannot supply any parameter to relax this check; they must guess a different `quant` (e.g. `10001`) to succeed, demonstrating that withdrawal of the specific amount they intended is unconditionally blocked by the fixed 0.01% constant embedded in the actuator.
