### Title
Cached signature/permission verification allows stale-permission authorization bypass in `Manager.pushTransaction` - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The reported Uniswap bug is a TOCTOU: an identifier (tab ID) is checked once and the underlying data it refers to (dapp URL/tab info) is fetched again later without re-validating that nothing changed in between, letting a malicious actor exploit the gap. `Manager.pushTransaction` has an analogous pattern: it validates a transaction's signature/permission against `AccountStore` *before* acquiring `transactionLock`, caches the result via `TransactionCapsule.isVerified`, and then reuses that cached "verified" result inside `processTransaction` without re-checking against the account state that may have changed while the transaction was waiting for the lock.

### Finding Description
`Manager.pushTransaction` performs the signature/permission check outside the block-processing critical section: [1](#0-0) 

It calls `trx.validateSignature(chainBaseManager.getAccountStore(), ...)` against the *current* `AccountStore` snapshot, then only afterward enters `synchronized (transactionLock)` and waits (potentially sleeping in a loop) via `isBlockWaitingLock()` for block generation to finish before it can proceed to `processTransaction`.

`TransactionCapsule.validateSignature` memoizes its result in the `isVerified` flag: [2](#0-1) 

Once `isVerified` is `true`, all subsequent calls to `validateSignature`/`validatePubSignature` short-circuit and return `true` without re-consulting `AccountStore`: [3](#0-2) 

Inside `processTransaction` (which runs later, under the lock, potentially after a real state-changing block has been applied), the same cached check is invoked again and trivially passes: [4](#0-3) 

This is the same "check performed on a snapshot of mutable state, use happens later against a different/updated state, but the check is trusted rather than repeated" root cause described in the Uniswap report (URL/tab-info fetched at check time vs. reused at use time). Here the mutable state is the account's `Permission` set (weights/thresholds) in `AccountStore`, and the identifier trusted across the gap is the boolean `isVerified` flag rather than a tab ID, but the mechanism (TOCTOU via caching a check result made against state that can legitimately change between check and use) is structurally identical.

### Impact Explanation
If an account owner revokes or lowers the weight/threshold of a signer's `Permission` via an `AccountPermissionUpdateContract` transaction, and that update is applied (committed under `transactionLock`) while a previously-broadcast transaction signed by the now-revoked/insufficient key is sitting in `pushTransactionQueue` waiting on `isBlockWaitingLock()`/`transactionLock`, the earlier transaction's signature was validated once against the *pre-revocation* permission and is never re-checked against the *post-revocation* permission before `processTransaction` executes it. This lets a transaction signed under an authority that has since been withdrawn still be executed and change the account's state (e.g., transfers, resource operations) — an authorization/accounting integrity violation, not merely a data-exposure issue as in the original report, but the same class of stale-check-vs-actual-state divergence.

### Likelihood Explanation
The precondition (revoke/adjust an account's active permission shortly after a transaction signed under the old permission was broadcast) is a normal, unprivileged, reachable action — any account owner can submit a permission update, and any holder of a since-revoked key can pre-broadcast a transaction timed to land in the queue just before the revocation commits. The window is widened by `isBlockWaitingLock()`'s sleep-retry loop, which can hold a transaction in queue across a full block-production cycle, making the race practically triggerable rather than a tight nanosecond race. I was unable to fully confirm from the index the exact duration/behavior of `isBlockWaitingLock()` and `SLEEP_FOR_WAIT_LOCK` (their definitions were not returned by search), so the precise timing window size is not fully verified here.

### Recommendation
Do not cache the signature/permission verification result across the wait for `transactionLock`. Either (a) move the authoritative `validateSignature` call to occur atomically with permission consumption inside the locked section immediately before `processTransaction`'s state mutations, using a fresh `AccountStore` read, or (b) invalidate/reset `TransactionCapsule.isVerified` (similar to the existing `tx.setVerified(false)` pattern already used during fork switches, per `Manager.switchFork`) whenever the account's permission for the relevant address has been modified since the transaction entered the queue, forcing re-validation against current state before execution.

### Proof of Concept
Not independently reproducible with available tooling (index access only, no runtime/test execution). Conceptual PoC:
1. Attacker/holder of key `K` is an authorized signer (weight ≥ threshold) under account `A`'s active permission.
2. Attacker broadcasts transaction `T1` (e.g., a `TransferContract`) from `A`, signed with `K`. `Manager.pushTransaction` calls `trx.validateSignature(...)` which succeeds and sets `isVerified = true`, then `T1` blocks on `isBlockWaitingLock()`/`transactionLock`.
3. Before `T1` acquires the lock, account `A`'s owner submits and it gets committed an `AccountPermissionUpdateContract` transaction removing `K`'s authority (processed inside the lock, updating `AccountStore`).
4. `T1` acquires the lock; `processTransaction` calls `trxCap.validateSignature(...)` again, which returns `true` immediately due to cached `isVerified`, bypassing re-evaluation against the now-updated permission, and `T1` executes.

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }
