### Title
`LiquidityCap` on `TokenConfig` is defined but never enforced, allowing unbounded PRC20 minting on repeated inbounds - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`TokenConfig.LiquidityCap` is documented as "max supply cap for this token" [1](#0-0)  and is required to be non-empty by `ValidateBasic` [2](#0-1) , but the actual mint path in `x/uexecutor` (`depositPRC20` / `CallPRC20Deposit`) never reads or checks it against any cumulative minted amount. Every quorum-passed inbound just mints the requested `amount` unconditionally.

### Finding Description
`depositPRC20` fetches the `TokenConfig` only to resolve `NativeRepresentation.ContractAddress`, then calls `CallPRC20Deposit` with the raw inbound `amount` — no supply/cap check is performed anywhere in this call chain: [3](#0-2) 

`CallPRC20Deposit` mints PRC20 tokens directly via `DerivedEVMCall("depositPRC20Token", ...)` with no cap parameter or precondition: [4](#0-3) 

Every path that credits PRC20 supply from an inbound (`ExecuteInboundFunds`, the funds-and-payload path, the gas-and-payload auto-swap path) calls `depositPRC20`/`CallPRC20Deposit`/`CallPRC20DepositAutoSwap` without ever consulting `tokenConfig.LiquidityCap`: [5](#0-4) [6](#0-5) 

This is analogous to the `accruedYieldBps` bug class: a field (`accruedYieldBps` in the report, `LiquidityCap` here) is explicitly modeled as a bound on accumulated state, but the code path that increases the cumulative value (vesting into `accruedYieldBps` / minting PRC20 on each inbound) never checks the field against the running total. Integration tests confirm repeated inbounds simply keep accumulating PRC20 balance with no ceiling: [7](#0-6) 

### Impact Explanation
Any unprivileged attacker who can get an inbound observed and voted to quorum by honest Universal Validators (i.e., a legitimate deposit event on the external gateway, since UVs vote only real observations) can repeat deposits indefinitely and mint unbounded PRC20 supply for a token whose real backing on the external chain may be far smaller than the configured (or intended) `liquidity_cap`. Since `NativeRepresentation` maps PRC20 1:1 to an external asset, unbounded minting decouples PRC20 supply from actual locked/bridged collateral, corrupting PRC20 accounting and enabling redemption/outbound draining beyond what was ever legitimately deposited — a direct violation of the "corruption of PRC20 ... accounting" and "unauthorized mint" impact categories in scope.

### Likelihood Explanation
High from a mechanical standpoint: no code changes or validator collusion are needed, since the cap is simply never read in the mint path — it is dead configuration data. The practical trigger only requires normal, honestly-relayed inbound activity (repeated legitimate deposits), so this is reachable by an ordinary unprivileged user without any privileged or malicious-validator assumption.

### Recommendation
Track cumulative minted supply per PRC20/token (e.g., a running total keyed by `chain:address` in `x/uregistry` or `x/uexecutor` state) and enforce `amount + currentSupply <= LiquidityCap` before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` in `depositPRC20`, `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload`. Reject or queue inbounds that would exceed the cap, and surface the cap value from `TokenConfig` into the mint decision path instead of only validating its presence at config-write time.

### Proof of Concept
1. Admin registers a `TokenConfig` for `USDC.eth` with `liquidity_cap = "1000000000000000000000000"` (1e24 units) as in `config/testnet-donut/eth_sepolia/tokens/usdc.json`.
2. An attacker (or any user) repeatedly deposits into the external gateway (legitimate, honestly observed) and gets each inbound voted to quorum by honest UVs — exactly as exercised in `TestSolanaInboundFunds`'s "multiple ... inbounds accumulate balance" subtest [8](#0-7)  and `TestInboundSyntheticBridge`'s "multiple inbounds accumulate balances" subtest [7](#0-6) .
3. Each inbound calls `depositPRC20` → `CallPRC20Deposit`, minting the full `inbound.Amount` with no check against `LiquidityCap` or any running total.
4. Repeating step 2 enough times mints PRC20 balance that exceeds `liquidity_cap` (1e24) with no code path ever rejecting it, since `LiquidityCap` is never read outside of `ValidateBasic`'s non-empty check.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
