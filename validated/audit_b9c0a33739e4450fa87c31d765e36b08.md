### Title
Webhook HMAC validation does not bind the signature to the `X-Shopify-Shop-Domain` header, allowing cross-tenant session deletion via `APP_UNINSTALLED` replay - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`shopify.webhooks.validate`/`process` verifies a webhook's HMAC over the raw body only, and separately trusts the `X-Shopify-Shop-Domain` header without cryptographically tying it to the signed payload. A single unprivileged actor who has access to a legitimately-signed webhook body (e.g. one delivered for a shop they control) can resend that exact `(body, hmac)` pair to the app's webhook endpoint while swapping only the domain header to target another shop, causing the app-uninstall handler to delete that victim shop's session — permanently bricking the app for that merchant, analogous to `RootValidator::onUninstall` accepting any caller and deleting state for whichever identity happened to be `msg.sender`.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC using only `rawBody` and the app secret, and compares it against the `X-Shopify-Hmac-Sha256` header value: [1](#0-0) 

The shop identity used downstream, `domain`, is read from a separate header (`X-Shopify-Shop-Domain`) that is *not* part of the signed material, in `checkWebhooksHeaders`: [2](#0-1) 

`process()` then invokes the registered handler with this unauthenticated `domain` value directly: [3](#0-2) 

In `shopify-app-express`, the built-in `APP_UNINSTALLED` handler uses that `shop`/`domain` value verbatim to wipe all of that shop's sessions: [4](#0-3) [5](#0-4) 

Because the HMAC never covers `domain`/`topic`/`webhook-id` headers, a `(rawBody, hmac)` pair that Shopify legitimately generated for shop A's `APP_UNINSTALLED` webhook remains valid when replayed with the `X-Shopify-Shop-Domain` header changed to shop B — the signature check in `validateHmac`/`validateHmacString` still passes because it only re-hashes the body. This breaks the intended invariant that a validated webhook's `domain` field can be trusted to reflect the shop that actually triggered it, the same class of bug as `RootValidator::onUninstall`'s check validating only `_isInitialized(msg.sender)` without confirming `msg.sender` was authorized to act on behalf of the state being cleared.

### Impact Explanation
An attacker who has installed and then uninstalled the app on a shop they control (trivial for anyone, including via a free development store) obtains a valid `(APP_UNINSTALLED body, hmac)` pair. They can replay this to the app's public `/webhooks` endpoint against any other shop by only changing the `X-Shopify-Shop-Domain` header, causing:
- `AppInstallations.delete(victimShop)` to run, deleting every session (offline and online) for the victim shop.
- The victim's app instance becomes uninstalled from the app's perspective; any subsequent authenticated request (`ensureInstalledOnShop`, `validateAuthenticatedSession`, embedded requests) redirects to OAuth/re-auth, denying legitimate use of the app until the merchant re-authorizes it.

This is a denial-of-service against a specific victim tenant triggered entirely by an unprivileged remote actor, with no secret leakage or privileged access required, directly analogous to the reported "permanently bricking via attested modules" DoS pattern (unauthenticated identity used for a destructive administrative action).

### Likelihood Explanation
Likelihood is moderate-to-high for any app builder using the default `shopify-app-express` (or similarly-structured custom handlers that trust the callback's `shop` argument for destructive actions): the webhook endpoint is public and unauthenticated by design (Shopify calls it), the attacker only needs one shop they control to harvest a valid `(body, hmac)` pair, and no rate-limiting/anti-replay/domain-binding exists in `validateHmac`/`validateHmacFromRequestFactory` to prevent reuse against an arbitrary target domain.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the `X-Shopify-Shop-Domain` header to the signed payload before trusting it in `validateFactory`/`checkWebhooksHeaders`. At minimum, webhook handlers that perform destructive/global actions (like deleting all sessions for a shop) should not rely solely on the unauthenticated domain header; verify the request is plausible for that shop (e.g., cross-check against an existing session, or require single-use webhook-id tracking to reject replays) before running `AppInstallations.delete`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; then uninstall it. Shopify sends an `APP_UNINSTALLED` webhook: capture `rawBody` and the `X-Shopify-Hmac-Sha256` header value from the delivery log (or via a proxy/ngrok endpoint under attacker's control).
2. Craft a new POST to the victim app's webhook endpoint (`config.webhooks.path`) using the exact same `rawBody` and `X-Shopify-Hmac-Sha256` value captured in step 1, but set `X-Shopify-Shop-Domain: victim.myshopify.com`, `X-Shopify-Topic: app/uninstalled`, and a fresh/duplicate `X-Shopify-Webhook-Id`.
3. `validateHmacFromRequestFactory` recomputes the HMAC over the (unchanged) `rawBody` and it matches, so `webhookCheck.valid` is `true`, with `webhookCheck.domain === 'victim.myshopify.com'` per `checkWebhooksHeaders`. [6](#0-5) 
4. `callWebhookHandlers` invokes `deleteAppInstallationHandler`'s callback with `shop = 'victim.myshopify.com'`, which calls `appInstallations.delete('victim.myshopify.com')`, deleting all of the victim's sessions. [4](#0-3) 
5. The victim's next authenticated app load is redirected to OAuth (`ensureInstalledOnShop` sees no session and calls `redirectToAuth`), effectively denying access until the merchant re-installs/re-authenticates. [7](#0-6)
