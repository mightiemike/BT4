## Finding

### Title
Unbounded native recursion in compiled-class hash computation causes sequencer process crash via a malicious Declare transaction - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The upstream `akka-http` advisory describes a DoS where a `StackOverflowError` is triggered by feeding attacker-controlled, arbitrarily-nested input into a recursive parser with no depth bound, crashing the process. The sequencer has an analogous pattern in the compiled-class-hash computation: `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132` recursively walks a `NestedIntList` (`bytecode_segment_lengths`) tree with no depth limit, and this function runs directly on the sequencer's main thread (not inside the resource-limited/sandboxed compiler subprocess).

### Finding Description
When a `DeclareTransaction` reaches the gateway, `SierraCompiler::compile` in `crates/apollo_compile_to_casm/src/lib.rs:60-74` performs two logically separate steps:
1. It shells out to a resource-limited (CPU/memory bounded) subprocess to compile Sierra → CASM (`self.compiler.compile(class)`), which enforces `max_bytecode_size` via `--max-bytecode-size`.
2. Immediately afterward, in the *same, unsandboxed process*, it computes the class hash: `executable_class.hash(&HashVersion::V2)` (line 69), which calls into `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash` → `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:96-132`).

`bytecode_hash_node` recurses once per `Node` level of the `NestedIntList` bytecode-segment tree:
```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt) {
    if node.is_leaf() { ... }
    else {
        let inner_nodes = node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child)).collect_vec();
        ...
    }
}
```
There is no depth cap on this recursion. The `bytecode_segment_lengths` tree structure is produced by the Sierra→CASM compiler based on the *attacker-supplied* Sierra program's function/branch layout (e.g., many small functions or deeply nested control flow), and the `--max-bytecode-size` flag only bounds total leaf-data size, not tree depth. A Sierra program engineered to produce a deeply, linearly nested segment tree (e.g. thousands of singleton segments chained as nested `Node`s) can drive `bytecode_hash_node`'s native call-stack depth into the thousands, while the size stays under `DEFAULT_MAX_BYTECODE_SIZE` (81920 felts, see `crates/apollo_node/resources/config_schema.json:3737-3741`).

Unlike Cairo Sierra/Native execution, where the codebase explicitly documents and mitigates this exact risk by pre-allocating a large worker-thread stack (see comments in `crates/blockifier/src/concurrency/worker_pool.rs:47-59` and `crates/blockifier/src/blockifier/transaction_executor.rs:325-336`: "when running Cairo natively, the real stack is used and could get overflowed... We pre-allocate the stack here"), the compiled-class-hash computation in `SierraCompiler::compile` has no such stack-size mitigation and runs on whatever default OS thread services the gateway request.

### Impact Explanation
A native stack overflow in Rust aborts the process (it cannot be caught with `panic!`/`Result`), so a successfully-compiled but adversarially-shaped Sierra program can crash the `SierraCompiler`/gateway component process handling the Declare transaction. Because this hashing step is on the mandatory path for every accepted declare (both in the gateway compiler component and again when the class is loaded/executed elsewhere via `CasmContractClass::hash`, e.g. `crates/blockifier_test_utils/src/compile_cache.rs:61`), this can be used to repeatedly crash sequencer components processing declare transactions, producing a liveness/DoS impact on the network's ability to process new declarations — a network availability impact reachable from a single unprivileged declare submission.

### Likelihood Explanation
Likelihood is High-effort-but-feasible: an attacker fully controls the Sierra program submitted in a `DECLARE` transaction and can shape its function/branch structure to produce deeply nested bytecode segments while staying within the `max_bytecode_size` limit, since depth and size are not the same axis. No special privileges are required; this is reachable by any contract declarer.

### Recommendation
- Convert `bytecode_hash_node` (and its Starknet OS Cairo counterparts) to an iterative, explicit-stack algorithm, or enforce a maximum recursion/tree-depth bound on `NestedIntList`/`bytecode_segment_lengths` before hashing.
- Alternatively, perform the hash computation in the same resource/stack-limited environment as compilation (or explicitly spawn it on a thread with a bounded, sufficiently large stack, mirroring the mitigation already used for Cairo Native execution).
- Add a depth-limit validation step directly on `bytecode_segment_lengths` right after Sierra→CASM compilation, rejecting classes whose segment tree exceeds a safe depth.

### Proof of Concept
Conceptually: craft a Sierra program compiling into CASM whose `bytecode_segment_lengths` is a long, linear chain of nested `Node(vec![Leaf(1), Node(vec![Leaf(1), Node(...)])])` (e.g., via many nested/chained small functions), with total leaf-length under `DEFAULT_MAX_BYTECODE_SIZE` but nesting depth in the thousands. Submitting this as a `DECLARE` transaction causes `SierraCompiler::compile` to call `.hash(&HashVersion::V2)` on the resulting `CasmContractClass`, driving `bytecode_hash_node` recursion depth-first through the entire chain and exhausting the calling thread's native stack. /// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
```rust
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```
