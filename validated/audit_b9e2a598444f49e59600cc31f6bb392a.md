### Title
DeleteAccount with `beneficiary_id` equal to the account being deleted burns the account's balance instead of refunding it - (File: runtime/runtime/src/actions.rs)

### Summary
The `DeleteAccountAction`, reachable directly from a signed transaction, lets the account owner (or any actor with delete permission) specify an arbitrary `beneficiary_id` to receive the account's remaining balance. Validation only checks that `beneficiary_id` is a syntactically valid account id, never that it differs from the account being deleted. If a user sets `beneficiary_id` to the very account being deleted, the pool/account balance accounting is computed and the refund receipt is generated *before* the account is actually removed, but by the time that refund receipt executes, the account no longer exists, causing the transferred balance to be irrecoverably burnt — the same "receiver == self, accounted-for-but-not-actually-transferred" bug class as the reported Ajna `ERC721Pool.repayDebt` issue where `collateralReceiver == address(this)` desynchronizes internal accounting from the real asset movement.

### Finding Description
`action_delete_account` in `runtime/runtime/src/actions.rs` reads the account's current balance and unconditionally queues a `Receipt::new_balance_refund` to `delete_account.beneficiary_id`, then immediately deletes the account (`remove_account`, `*account = None`) in the same state transition: [1](#0-0) [2](#0-1) 

The only validation performed on `beneficiary_id` is a well-formedness check; there is no check that it is different from the account being deleted: [3](#0-2) 

Because refund receipts (`predecessor_id == "system"`) can never implicitly create an account, and a named account that has just been deleted no longer exists, when the queued balance-refund receipt is later executed against `beneficiary_id == account_id`, `check_account_existence`/`implicit_creation_allowed` rejects it (`is_refund` path returns `false`), so the receipt fails: [4](#0-3) 

A failing refund receipt does not retry or bounce back — the runtime treats system-predecessor receipt failures as a straight burn of the deposit into `other_burnt_amount`: [5](#0-4) 

This exact code path is exercised by the existing test `refund_may_not_create_universal_account`, which shows that a `Receipt::new_balance_refund` sent to a nonexistent account fails with `AccountDoesNotExist` and does not create the account nor deliver the funds: [6](#0-5) 

This mirrors the Ajna report's root cause: the state update ("pool.collateral is decremented" / "account balance is snapshotted and queued for transfer") happens before the actual value movement, and the movement targets an address that will not actually receive value (contract-self / just-deleted account), silently destroying value instead of transferring it.

### Impact Explanation
Any account owner (a single unprivileged transaction signer) can permanently burn their own remaining NEAR balance by submitting a `DeleteAccount` action with `beneficiary_id` equal to the account being deleted. While this is "self-inflicted," it still represents a concrete, transaction-triggered supply-destroying bug: funds that should have moved to a valid beneficiary are permanently and unrecoverably burnt due to a logic defect in balance accounting versus refund reachability, not user error. This is not caught anywhere in tx admission, action validation, or execution — the transaction succeeds and the funds vanish. Because this is a supply-affecting invariant break (a `DeleteAccount` should relocate the account's tokens, not destroy them) triggered by a single ordinary transaction, it qualifies as a concrete unauthorized value-destruction bug.

### Likelihood Explanation
The scenario requires no special privileges, no relayer collusion, and no race conditions: any account holder can trivially construct `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: <own_account_id> })` and sign it via `SignedTransaction::delete_account`. Existing test helpers such as `delete_account_with_beneficiary_set` and `tx_delete_account` show the API path is fully reachable and unguarded: [7](#0-6) [8](#0-7) 

The only mitigating factor is that the impact is self-directed (loses only the signer's own funds), which likely explains why it has not been flagged as a cross-account issue previously; however, it is still a violation of expected DeleteAccount semantics ("the remaining account balance will be transferred to the AccountId below") documented in `docs/RuntimeSpec/Actions.md`.

### Recommendation
Add a check in `validate_delete_action` (or in `action_delete_account`) rejecting `DeleteAccountAction` when `beneficiary_id == account_id` (the account being deleted), returning a clear `ActionsValidationError`/`ActionErrorKind` (e.g., `DeleteAccountBeneficiaryEqualsAccountId`), consistent with how `validate_delete_action` already validates other invariants on `beneficiary_id`: [3](#0-2) 

### Proof of Concept
1. Create/own account `alice.near` with balance `B > 0`.
2. Submit `SignedTransaction::delete_account(nonce, "alice.near", "alice.near", "alice.near", &signer, block_hash)` (i.e. `account_id == receiver_id == beneficiary_id == "alice.near"`), using the same construction as `tx_delete_account`: [8](#0-7) 
3. `action_delete_account` executes: it pushes `Receipt::new_balance_refund(&"alice.near", B)` and then deletes `alice.near`'s account record via `remove_account`: [1](#0-0) 
4. In a subsequent apply step, the refund receipt targeting the now-nonexistent `alice.near` is processed; `implicit_creation_allowed` returns `false` for the refund case, so the receipt fails with `AccountDoesNotExist` (as demonstrated by the analogous existing test `refund_may_not_create_universal_account`): [9](#0-8) 
5. Because it is a system-predecessor (refund) receipt, the failure burns the deposit `B` into `other_burnt_amount` rather than crediting any account: [5](#0-4) 
6. Net effect: balance `B`, which existed on `alice.near` prior to the transaction, is permanently destroyed instead of being transferred to a beneficiary, in direct contradiction of the documented `DeleteAccountAction` semantics.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {
            panic!("the refund receipt must produce exactly one outcome, got {:?}", result.outcomes)
        };
        assert_matches!(

            ExecutionStatus::Failure(TxExecutionError::ActionError(err))
                if matches!(err.kind, ActionErrorKind::AccountDoesNotExist { .. }),
            "a refund to a missing `0u` id must fail with AccountDoesNotExist",
        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
