### Title
`last-update` timestamp is only advanced when the index changes, allowing a later accrual to apply an inflated time-delta and over-accrue interest — (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and all sibling vaults: `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`)

### Summary
`accrue()` only calls `(var-set last-update stacks-block-time)` when the borrow index `idx` or liquidity index `lidx` actually changed. When the interest rate is zero (e.g., utilization is `u0` because there is no outstanding debt), the index does not change even though real time has elapsed, so `last-update` is left stale. A subsequent `accrue()` call — after debt becomes non-zero and the rate becomes positive — will then compute `time-delta` against the old, stale `last-update`, causing interest to be accrued as if debt had existed for the entire idle period, not just the time since the debt was created.

### Finding Description
`accrue()` computes the next indexes and conditionally persists them: [1](#0-0) 

The relevant private helpers that feed `next` are: [2](#0-1) 

`next-index` derives `multiplier` from `interest-rate` and `time-delta = stacks-block-time - last-update`. When `interest-rate` is `0` (which happens whenever `utilization` is `0`, i.e., `total-debt` is `0`), `calc-multiplier-delta` returns the identity multiplier and `next` equals `idx` regardless of how large `time-delta` is. The same applies to `next-liquidity-index` for `lidx`/`nliq`.

Because `idx == next` and `lidx == nliq` in that state, the guard at line 858 evaluates false and `last-update` is **not** advanced, even though `stacks-block-time` has moved forward. `last-update` therefore continues to reflect a much older timestamp.

Sequence to trigger the bug:
1. Vault has zero outstanding debt (`total-debt = u0`), so `utilization = u0` and `interest-rate = u0`. `last-update` is fixed at some early block/time `T0`.
2. Time passes (multiple blocks) with no borrow activity. Any `accrue()` calls in this window compute `next = idx`, `nliq = lidx` (rate still 0), so `last-update` remains `T0`.
3. A user calls `system-borrow`, which itself calls `(try! (accrue))` first — still before the borrow is applied, `total-debt` is still `u0`, so accrue again leaves `last-update = T0`. The borrow then sets `principal-scaled > 0` and `total-borrowed > 0`, at real time `T1 (T1 >> T0)`.
4. Later, at time `T2`, any operation that triggers `accrue()` (deposit, redeem, transfer, borrow, repay) now has `scaled-principal > 0`, so `utilization > 0` and `interest-rate > 0`. `next-index` computes `time-delta = T2 - last-update = T2 - T0` instead of the correct `T2 - T1`, drastically inflating the multiplier and thus `next`.
5. `debt-delta = new-debt - old-debt` in `accrue()` is computed off this inflated index jump, inflating `total-debt` for every borrower (their debt suddenly reflects interest for a period during which no debt existed) and inflating `reserve-inc`/`treasury-lp` minted to `.dao-treasury` (line 848, 855-856), diluting all other shareholders based on a fictitious accrual period.

This is a clock/cache value ("last-update") that is not advanced/invalidated on every real-time step, only on a derived condition ("index changed"), and a later, unrelated call resumes using it as if it were current — matching the "clock advanced only on change" analog class.

### Impact Explanation
The inflated `time-delta` causes the borrow index to jump far more than the actual elapsed borrowing period warrants, which:
- Artificially inflates every borrower's debt (`total-debt`/`debt-preview`), forcing borrowers to repay interest that never should have accrued — a form of protocol insolvency / incorrect accounting that can also trigger unwarranted liquidations.
- Mints inflated `treasury-lp` shares to `.dao-treasury` based on a fabricated `debt-delta`, diluting existing zToken holders' shares (theft of yield from depositors).

This lands in the in-scope Critical impact category (protocol insolvency / incorrect debt/interest accounting) and also constitutes theft/dilution of unclaimed yield for existing LPs (High).

### Likelihood Explanation
The precondition — a vault reaching `total-debt = u0` and remaining there for some time before a borrow occurs — is a normal, expected operational state (e.g., a newly deployed vault before its first borrow, or a vault that is fully repaid and idle for a period). No privileged access, oracle manipulation, or governance action is required; any user calling `system-borrow`, `deposit`, or any function that funnels through `accrue()` can trigger the stale-clock condition and the subsequent inflated accrual. This is reachable under normal single/multi-transaction flow and Clarity's deterministic execution order.

### Recommendation
Decouple the timestamp update from whether the index numerically changed. `last-update` should be advanced to `stacks-block-time` on every non-paused `accrue()` invocation (whenever `time-delta > u0`), regardless of whether `interest-rate` happened to be `0`, e.g.:
```clarity
(if (> (- stacks-block-time (var-get last-update)) u0)
    (var-set last-update stacks-block-time)
    false)
```
instead of gating on `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))`.

### Proof of Concept
Conceptual reproduction (values illustrative):
1. Deploy vault; no deposits/borrows. `last-update = T0`, `index = lindex = INDEX-PRECISION`.
2. Wait a long idle period with `total-debt = u0` (utilization 0 ⇒ rate 0). Any calls to `accrue()` in between leave `last-update = T0` because `idx == next`.
3. At time `T1`, user deposits and then borrows: `system-borrow` calls `accrue()` first (still `total-debt = u0` pre-borrow, so `last-update` stays `T0`), then sets `principal-scaled > 0`.
4. At time `T2` (much later), any call that invokes `accrue()` now computes `time-delta = T2 - T0` (not `T2 - T1`) with `interest-rate > 0`, producing a `next` index far larger than warranted for the actual `T2 - T1` borrowing duration, inflating `total-debt` for the borrower and `treasury-lp` minted to `.dao-treasury`.
