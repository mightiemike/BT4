### Title
Legacy `FreezeBalanceContract` overwrites the frozen-balance timelock instead of extending it, letting a later smaller-duration freeze shorten the unlock time of previously frozen/delegated balance - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
`FreezeBalanceActuator.execute` aggregates the newly frozen amount with the account's (or delegatee's) existing frozen balance, but it always **overwrites** the stored `expireTime` with `now + newDuration` rather than taking the maximum of the old and new expire times. Because `frozenDuration` is only bounded by `minFrozenTime`/`maxFrozenTime` (not by the remaining time of an existing lock), a second `FreezeBalanceContract` submitted with a shorter duration than an earlier one can pull the effective unlock time for the *entire* aggregated balance earlier than what was originally committed — the same root cause as the GNTDeposit report: depositing/locking more funds does not re-derive a timelock that is at least as strict as the existing one.

### Finding Description
In `FreezeBalanceActuator.execute`, for both self-freeze and delegated-freeze paths, `expireTime` is computed fresh from the current block time and the contract's requested duration, then stored unconditionally: [1](#0-0) 

For the non-delegated case, the *new* balance is added to the *existing* frozen balance, but the *existing* balance's original commitment is discarded and replaced with the newly computed `expireTime`: [2](#0-1) 

For the delegated case, `delegateResource` calls `DelegatedResourceCapsule.addFrozenBalanceForBandwidth/Energy(balance, expireTime)`, which likewise unconditionally overwrites `ExpireTimeFor*` with the new value: [3](#0-2) 

`validate()` bounds `frozenDuration` only against the global `minFrozenTime`/`maxFrozenTime` window — it never compares the requested duration against the *remaining* time of the account's (or delegatee's) currently active lock: [4](#0-3) 

This is structurally identical to the described bug class: `onTokenReceived` in GNTDeposit blindly increments `balances[_from]` without re-checking/extending the timelock. Here, `setFrozenForBandwidth`/`setFrozenForEnergy`/`setFrozenForTronPower` blindly increment the frozen balance while resetting the shared `expireTime` field to whatever the *latest* freeze call computes — with no guarantee it is later than the prior lock.

Notably, TRON's own developers recognized and fixed this exact bug class in the newer, still-supported `DelegateResourceActuator` (the V2 "lock" delegate path), which explicitly enforces that a new lock period cannot be shorter than the remaining time of an existing lock via `validRemainTime`: [5](#0-4) 

The legacy `FreezeBalanceContract` path (and its `delegateResource` helper) has no equivalent check.

### Impact Explanation
If exploitable (see Likelihood), an account could:
1. Freeze balance B1 for the maximum allowed duration (longest network-imposed lock), receiving BANDWIDTH/ENERGY/TRON_POWER voting weight for B1 for that full period.
2. Shortly after, freeze a small additional balance B2 using the minimum allowed duration.
3. Because `expireTime` is fully overwritten rather than maxed, the aggregated (B1+B2) frozen balance's unlock time becomes the short expiry from step 2, letting the user unfreeze/withdraw the full B1+B2 much earlier than the commitment made in step 1.

This corrupts the intended resource/vote-weight accounting invariant (frozen balance's stake-time relationship) and could be used to prematurely reclaim TRX that was supposed to remain locked (e.g., to back TRON_POWER voting weight or bandwidth/energy delegation for a promised duration), undermining any downstream logic or counterparties (e.g., a resource-delegation recipient) that relies on the stated `expireTime`.

### Likelihood Explanation
Exploitability depends entirely on whether `minFrozenTime != maxFrozenTime` (i.e., whether the network currently allows a *range* of freeze durations) at the time of the attack. In current TRON mainnet configuration these parameters have historically been fixed to the same value (3 days), which would make `expireTime` deterministic and monotonically increasing across freeze calls, preventing exploitation in the default configuration. I could not confirm the current on-chain default value of `getMinFrozenTime()`/`getMaxFrozenTime()` within the available tool budget, so likelihood is uncertain and depends on network parameters that may be adjusted over time (e.g., historical/legacy configurations, testnets, or private deployments of this codebase). Additionally, `FreezeBalanceContract` is only usable while `dynamicStore.supportUnfreezeDelay()` (FreezeV2) is not yet enabled: [6](#0-5) 
which further narrows the exploit window on networks that have already migrated to FreezeV2.

### Recommendation
- In `FreezeBalanceActuator.execute` (and `FreezeBalanceProcessor.execute`), when aggregating an additional freeze into an existing frozen balance, set the resulting `expireTime` to `Math.max(existingExpireTime, newExpireTime)` instead of unconditionally overwriting it.
- In `DelegatedResourceCapsule.addFrozenBalanceForBandwidth/Energy`, apply the same max-of-old-and-new logic used in the newer V2 lock-delegate path (`DelegateResourceActuator.validRemainTime`), or reuse that validation in the legacy `FreezeBalanceActuator.validate()` path.
- Alternatively, forbid a new freeze operation from reducing the effective duration of an existing, still-locked balance, mirroring the fix already applied to `DelegateResourceActuator`.

### Proof of Concept
1. Ensure network parameters `minFrozenTime < maxFrozenTime` (a precondition outside attacker control) and FreezeV2 not yet enabled (`supportUnfreezeDelay()` false).
2. Broadcast `FreezeBalanceContract` with `frozenBalance = B1`, `frozenDuration = maxFrozenTime`. Actuator computes `expireTime1 = now1 + maxFrozenTime*FROZEN_PERIOD` and stores it via `setFrozenForBandwidth`. [2](#0-1) 
3. Shortly after (`now2` close to `now1`), broadcast a second `FreezeBalanceContract` with `frozenBalance = B2`, `frozenDuration = minFrozenTime`. The actuator computes `expireTime2 = now2 + minFrozenTime*FROZEN_PERIOD`, which can be earlier than `expireTime1` if `(maxFrozenTime - minFrozenTime)*FROZEN_PERIOD > (now2 - now1)`.
4. `setFrozenForBandwidth(B1+B2, expireTime2)` overwrites the stored expire time entirely with `expireTime2`.
5. Once `now >= expireTime2` (well before `expireTime1`), the account can submit `UnfreezeBalanceContract` and withdraw the entire `B1+B2`, even though `B1` was originally committed to remain locked until `expireTime1`.

  private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime,
      long now) throws ContractValidateException {
    long remainTime = expireTime - now;
    if (lockPeriod * BLOCK_PRODUCED_INTERVAL < remainTime) {
      throw new ContractValidateException(
          "The lock period for " + resourceCode.name() + " this time cannot be less than the "
              + "remaining time[" + remainTime + "ms] of the last lock period for "
              + resourceCode.name() + "!");
    }
  }
