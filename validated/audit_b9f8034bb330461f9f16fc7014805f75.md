## Finding: WriteSets in transaction-backup restore are persisted to the ledger without being covered by the accumulator/txn-info proof

### Title
Backup-restore path commits attacker-controllable `WriteSet` data that is never proof-verified against `TransactionInfo.state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
During transaction-backup restore, `LoadedChunk::load` reads `write_sets` straight from the raw backup file and keeps them completely outside the `TransactionListWithProofV2` structure that is verified against the ledger info. Only `transactions`, `events`, and `transaction_infos` are proof-checked. The unverified `write_sets` are later handed to `restore_handler.save_transactions()`, which persists them to `WriteSetDb` and, in the `kv_replay` path, feeds them directly into `state_store.calculate_state_and_put_updates()` to mutate the Jellyfish Merkle state tree. This lets a compromised or malicious backup-storage source substitute a different write set for a transaction whose hash/events/status/gas still validate, corrupting committed state during restore.

### Finding Description
In `LoadedChunk::load` [1](#0-0)  the raw chunk file is parsed into `txns`, `persisted_aux_info`, `txn_infos`, `event_vecs`, and `write_sets`. Immediately afterward, only `txns`, `event_vecs`, `manifest.first_version`, and `TransactionInfoListWithProof::new(range_proof, txn_infos)` are wrapped into a `TransactionListWithProofV2` and passed through `.verify(ledger_info.ledger_info(), ...)` [2](#0-1) . `write_sets` never enters this structure and is never touched by `.verify()`.

`TransactionOutputListWithProof::verify` (the analogous verification routine in the types crate) shows exactly what proof coverage looks like when write sets *are* included: it explicitly hashes `txn_output.write_set` and checks it against `txn_info.state_change_hash()` [3](#0-2) . The transaction-chunk restore path, however, uses the plain `TransactionListWithProof`/`TransactionListWithProofV2` type, which only carries transactions and events for verification — write sets are simply not part of what gets authenticated by the accumulator/ledger-info proof in this flow.

After `.verify()` succeeds, the code unpacks the *verified* txns/txn_infos/events but the original, unverified `write_sets` value from step one is carried forward untouched into the returned `LoadedChunk` [4](#0-3) .

These write sets subsequently flow into `restore_handler.save_transactions(...)` [5](#0-4)  → `restore_utils::save_transactions` → `save_transactions_impl`, which:
- Persists the write set directly to durable storage via `WriteSetDb::put_write_set` [6](#0-5) .
- When `kv_replay` is enabled, feeds the same unverified write sets into `state_store.calculate_state_and_put_updates(&StateUpdateRefs::index_write_sets(...))`, which actually computes and commits new Jellyfish Merkle Tree state and then calls `state_store.set_state_ignoring_summary(ledger_state)` [7](#0-6) .

The check that *should* guard this — comparing `CryptoHash::hash(write_set)` against `txn_info.state_change_hash()` — exists in the codebase (`TransactionOutput::ensure_match_transaction_info` [8](#0-7) ), but it is only invoked from the chunk-executor's re-execution `verify_execution` path [9](#0-8) , not from the direct-save (`save_before_replay_version`) restore path that most transaction-backup restores use before the replay-from-version cutoff.

This is analogous to the MagicSea bug: a code path (`addToPosition`, here "restore chunk save") that is supposed to be safe because *other* related paths enforce integrity checks (renewLock/extendLock, here `ensure_match_transaction_info`), but this specific path has no such guard, letting untrusted input flow straight into committed state.

### Impact Explanation
An attacker who can tamper with or supply a malicious backup archive (compromised backup bucket, MITM on the backup-storage fetch, or a poisoned/forked backup source) can replace the `WriteSet` bytes for any transaction in a chunk while leaving the transaction bytes, events, and `TransactionInfo` untouched, since those are the only fields actually checked against the ledger-info-anchored accumulator proof. A restoring node (fresh validator/fullnode bootstrap, or `kv_only_replay`) will:
- Persist the wrong write set as the transaction's committed `WriteSetDb` entry (a permanent divergence from the authenticated `state_change_hash`), and
- In the `kv_replay` branch, actually apply the malicious writes into its Jellyfish Merkle state store, producing a corrupted state root/JMT that differs from what honest execution and the accumulator/ledger-info proof attest to.

This is a hard-fork-class integrity break: a node restored this way will diverge from the rest of the network's state while believing it has a proof-verified, authentic history, and any subsequent API responses (`get_state_value_with_proof_by_version`, etc.) served from this corrupted store will be internally "consistent" but wrong relative to the real chain.

### Likelihood Explanation
Likelihood depends on an attacker's ability to control or corrupt the backup storage/transport that a restoring node fetches from. Aptos backup/restore explicitly assumes an adversarial/unauthenticated storage backend (that is precisely why `TransactionInfoListWithProof`/accumulator proofs exist for transactions and events) — so a storage-layer compromise is within the threat model the proof machinery was built to defend against, yet write sets are left outside that defense. This does not require any privileged on-chain actor; it only requires control of the artifact the restoring operator downloads from, which for many deployments (self-hosted or third-party mirrors) is a realistic supply-chain vector.

### Recommendation
Include `write_sets` in the data authenticated during transaction-chunk restore. Either:
1. Extend `TransactionListWithProof`/`TransactionListWithProofV2` (or a restore-specific wrapper) to carry write sets and verify each one's hash against the corresponding `TransactionInfo.state_change_hash()`, mirroring `TransactionOutputListWithProof::verify` and `ensure_match_transaction_info`; or
2. Explicitly call `ensure_match_transaction_info`-style hash checks for `write_sets` inside `LoadedChunk::load` right after `txn_list_with_proof.verify(...)`, before returning the chunk, and abort restore on mismatch.

### Proof of Concept
Conceptual (no test harness/tool access to execute):
1. Produce a legitimate transaction backup chunk file and record its `(txn, txn_info, events, write_set)` tuples along with the accumulator range proof and ledger info, as read in `LoadedChunk::load`.
2. Modify only the serialized `write_set` bytes for one record (e.g. change a resource value) while leaving `txn`, `txn_info`, and `events` untouched.
3. Feed the tampered chunk to `TransactionRestoreController`. `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)` at line 167 of `restore.rs` succeeds because it only checks transactions/events/txn_infos against the ledger info, not `write_sets`.
4. `save_before_replay_version` persists the tampered `write_sets` via `restore_handler.save_transactions`, and with `kv_only_replay` set, `state_store.calculate_state_and_put_updates` applies the tampered write set to the JMT, producing a state root that diverges from `txn_info.state_change_hash()`/the real chain state — confirmable by comparing `store.get_root_hash(version)` post-restore against the root that would result from the honest write set.

**Uncertainty note:** I was not able to fully re-confirm the exact field layout of `TransactionListWithProof`/`TransactionListWithProofV2::verify` in this iteration (tool budget exhausted before reading that definition directly), so the claim that write_sets are entirely absent from its verified payload is inferred from `LoadedChunk::load`'s construction call (which only passes `txns`, `event_vecs`, `first_version`, and the `TransactionInfoListWithProof`) and from the fact that `write_sets` is never re-derived from `txn_list_with_proof.into_parts()`. This inference is strong but should be double-checked directly against the `TransactionListWithProof` struct/verify implementation before treating this as fully confirmed.
