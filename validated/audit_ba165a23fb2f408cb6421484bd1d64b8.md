### Title
`many_ref_accounts_can_be_moved` underestimates required packed storages, letting `PackedAncientStorage::pack` place multi-ref accounts below their live slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Finding Description
`many_ref_accounts_can_be_moved` (accounts-db/src/ancient_append_vecs.rs:390-415) approves packing `many_refs_newest` accounts into `target_slots_sorted` using a purely byte-based estimate:
```
required_ideal_packed = alive_bytes / ideal_storage_size + 1
```
It then compares every account's original slot only against `target_slots_sorted[len - required_ideal_packed]` [1](#0-0) . This assumes that `PackedAncientStorage::pack` can pack `many_refs_newest` perfectly, using exactly `required_ideal_packed` storages of `ideal_storage_size`.

`PackedAncientStorage::pack` (accounts-db/src/ancient_append_vecs.rs:1012-1094) is a first-fit bin packer: it never splits/rearranges to minimize waste, it just closes a chunk as soon as the next whole account would exceed `ideal_storage_size` [2](#0-1) . When `many_refs_newest` is made of many separate `AliveAccounts` groups (one per source slot) whose account sizes are each moderately larger than half of `ideal_storage_size`, only one account fits per storage, so the real number of chunks needed can be far larger than `alive_bytes / ideal_storage_size + 1`.

Since `write_packed_storages` assigns `packed_contents[k]` to `target_slots_sorted.iter().rev()[k]` [3](#0-2) , an underestimated `required_ideal_packed` means the many-ref chunk that actually lands at index `k >= required_ideal_packed` gets assigned a *lower* target slot than `target_slots_sorted[len - required_ideal_packed]`, the slot value the safety check validated against. If an account's original slot lies between that lower slot and the checked `highest_slot`, the check wrongly approves the move, and the account ends up rewritten at a slot lower than its own prior slot. The overall-count guard `pack.len() > accounts_to_combine.target_slots_sorted.len()` (line 506) only catches gross overflow of total chunks vs. total target slots — it does not catch this internal per-chunk slot-assignment mismatch.

This directly violates the invariant documented in the code itself: "the highest slot # where an account exists defines the most recent account" (accounts-db/src/ancient_append_vecs.rs:884) [4](#0-3) . The subsequent index update (`InMemAccountsIndex::replace`, accounts-db/src/accounts_index/in_mem_accounts_index.rs:568-602) blindly replaces the slot-list entry at `old_slot` with the new `(new_slot, info)` pair without validating that `new_slot` is still the highest entry for that pubkey [5](#0-4) , so no panic or assertion catches the mis-ordering; a stale/lower-slot instance of the account can silently become — or another still-alive higher instance can silently outrank — the packed one, causing wrong value reads.

An unprivileged attacker fully controls this precondition: by repeatedly writing/closing/reopening many distinct accounts they own across old (soon-to-be-ancient) slots, sized deliberately (e.g., just over half of `ideal_storage_size`), they can create many separate `many_refs_this_is_newest_alive` groups with poor bin-packing efficiency, all without needing validator, leader, or staked privileges — only ordinary transaction fees and control over account keys/sizes/write frequency.

### Impact Explanation
This falls under "AccountsDB ... halt validators" / consensus-affecting divergence: a stale or wrong-version account value can be read, and different validators packing ancient storages at different wall-clock times (background maintenance is not deterministic across nodes) may compute different resulting account layouts and therefore different bank hashes for the same logical state, producing a cluster fork/consensus divergence. It also constitutes disproportionate CPU/storage cost misuse of the ancient-packing maintenance path.

### Likelihood Explanation
Feasible with only unprivileged transaction access: create N distinct accounts (attacker-controlled pubkeys), interleave writes so several slots each contain one instance with ref_count > 1 (older copy still alive elsewhere), and choose account sizes slightly over `ideal_storage_size / 2` so pack() can fit only one per chunk. Repeating this over many old (ancient-eligible) slots directly inflates the gap between `required_ideal_packed`'s naive byte estimate and the true chunk count needed by `PackedAncientStorage::pack`. No special timing or leader control is required, though it does require the background ancient-append-vec squashing path (`combine_ancient_slots_packed`) to run over the crafted slot range, which happens automatically as slots age.

### Recommendation
Compute `required_ideal_packed` (or validate the final assignment) using the *actual* bin-packing result rather than a byte-count approximation — e.g., run (or simulate) `PackedAncientStorage::pack` for `many_refs_newest` first, then check that each resulting chunk's assigned target slot (from the real `write_packed_storages` zip order) is `>= max` original slot of the accounts placed in it, before committing to write. Alternatively, add an explicit post-hoc assertion inside `write_packed_storages`/`write_one_packed_storage` that every account's `target_slot >= account's source slot`, failing safe (skip and log, not panic) rather than silently writing.

### Proof of Concept
Add a differential/invariant test in accounts-db/src/ancient_append_vecs.rs test module:
```rust
#[test]
fn test_many_ref_accounts_can_be_moved_underestimates_fragmentation() {
    // ideal_storage_size = 1000
    let ideal = 1000u64;
    let tuning = PackedAncientStorageTuning {
        ideal_storage_size: NonZeroU64::new(ideal).unwrap(),
        ..default_tuning()
    };

    // Build N separate AliveAccounts groups (simulating N distinct pubkeys each
    // resurrected then rewritten at N distinct slots), each holding one account of
    // size 600 bytes (> ideal/2), so only 1 fits per packed storage.
    let n = 5;
    let account_size = 600usize;
    let many_refs_newest: Vec<AliveAccounts> = (0..n)
        .map(|i| AliveAccounts {
            bytes: account_size,
            slot: (i as u64) * 10, // distinct ascending original slots
            accounts: Vec::default(),
        })
        .collect();

    // naive estimate: total_bytes/ideal + 1 = (600*5)/1000 + 1 = 4
    // actual chunks needed by first-fit pack(): 5 (1 account per chunk)
    let target_slots_sorted: Vec<Slot> = (0..5).map(|i| i * 100).collect(); // ascending

    // The safety check approves based on the underestimated chunk count...
    assert!(AccountsDb::many_ref_accounts_can_be_moved(
        &many_refs_newest,
        &target_slots_sorted,
        &tuning,
    ));

    // ...but simulate the real per-chunk assignment that write_packed_storages would do
    // and show a many-ref account ends up assigned to a slot below its own original slot.
    let packed = PackedAncientStorage::pack(many_refs_newest.iter(), tuning.ideal_storage_size);
    assert!(packed.len() > target_slots_sorted.len() - 1 /* != naive estimate of 4 */);

    let assignments: Vec<(Slot, Slot)> = target_slots_sorted
        .iter()
        .rev()
        .zip(packed.iter())
        .flat_map(|(target_slot, p)| {
            p.accounts.iter().map(move |(src_slot, _)| (*src_slot, *target_slot))
        })
        .collect();

    // EXPECTED (bug): at least one (src_slot, target_slot) pair violates target_slot >= src_slot
    assert!(
        assignments.iter().any(|(src, target)| target < src),
        "expected invariant violation: an account was packed into a slot lower than its source slot"
    );
}
```
This test demonstrates that `many_ref_accounts_can_be_moved`'s naive byte-division estimate diverges from `PackedAncientStorage::pack`'s actual first-fit chunk count, and that the resulting slot assignment (as computed by `write_packed_storages`'s `target_slots_sorted.iter().rev().zip(packed_contents)`) can place a many-ref account at a target slot below its original slot — violating the "highest slot defines newest value" invariant that `many_ref_accounts_can_be_moved` exists to protect.
