### Title
`replay-on-archive` verification never checks state-checkpoint (SMT root) hashes, so a divergent Merkle state root is reported as a successful replay - (File: `types/src/transaction/mod.rs`)

### Summary
The `TransactionOutput::ensure_match_transaction_info` comparator, used by the `db-tool replay-on-archive` verification path, validates execution status, gas used, write-set hash, and event-root hash against the archived `TransactionInfo`, but it never compares the `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against a locally recomputed state root. This means that a divergence in the Sparse-Merkle-Tree state root at a checkpoint transaction — the exact quantity that anchors the authenticated Merkle proof for account/resource state on mainnet — is silently ignored by this auditing tool.

### Finding Description
`ensure_match_transaction_info` compares only a subset of the fields that constitute a `TransactionInfo`: [1](#0-0) [2](#0-1) 

It checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`, but the code's own comment admits the gap: [3](#0-2) 

This function is the sole correctness check used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which is the tool operators use to independently re-execute an archived transaction range and confirm the resulting ledger state matches what was authenticated by validator signatures in the backup: [4](#0-3) 

Because `state_checkpoint_hash` (the Sparse Merkle Tree root binding all account/resource state at a checkpoint) is never recomputed from the replayed state and compared to the archived value, a state-root divergence — e.g., a nondeterministic VM bug, a bad hard-fork migration, or storage corruption altering account resources — will not cause `execute_and_verify` to return an error as long as the write-set bytes, gas, events, and status still match. The write-set hash check only confirms individual transaction deltas are byte-identical; it does not confirm that the SMT reduction of those deltas onto the pre-existing state (the state_checkpoint_hash) reproduces the same root that validators originally signed off on.

### Impact Explanation
The state_checkpoint_hash inside `TransactionInfo` is the exact value that gets folded into the transaction accumulator and ultimately into the `LedgerInfo` that validators sign — it is the authenticated state root binding all authenticated API responses and Merkle state proofs served to light clients. A verification tool that structurally cannot detect its divergence provides false assurance of ledger integrity: an operator running `replay-on-archive` to confirm no state corruption occurred (e.g. after a chain upgrade, hard fork, or storage bug) could report success even though the archived/authenticated state root does not match what local re-execution actually produces. This directly undermines the "replay, restore, or proof verification" integrity guarantee this class of tooling is meant to provide.

### Likelihood Explanation
This isn't a rare edge-case: it is a structural gap present on every checkpoint transaction replayed through this tool, since `state_checkpoint_hash` is simply never included in the comparator's list of checked fields. The gap only manifests when an actual state-root divergence exists (which should be rare in healthy operation), but when it does occur, this tool is guaranteed to miss it. The bug is also explicitly self-documented in the code (`// TODO(trading-native): this comparator ignores the checkpoint hashes ...`), confirming both its existence and non-detection by existing tests.

### Recommendation
Extend `ensure_match_transaction_info` (or `execute_and_verify`'s call site) to recompute the Sparse Merkle Tree root from the replayed state updates at each checkpoint transaction and assert it equals `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` where applicable), returning an error on mismatch just as is done for `state_change_hash` and `event_root_hash`.

### Proof of Concept
Code-level proof (no external network needed): trace `replay_on_archive.rs::execute_and_verify` → calls `TransactionOutput::ensure_match_transaction_info` → function body only checks `status`, `gas_used`, `state_change_hash`, `event_root_hash`, and explicitly documents that `state_checkpoint_hash`/`hot_state_checkpoint_hash` are not validated: [5](#0-4) 
Any crafted or corrupted replay where the write-set bytes, events, gas, and status coincidentally match but the resulting SMT root differs (e.g., due to a state-store bug not reflected in the write-set bytes themselves, or divergent handling of deletions/defaults) will pass `execute_and_verify` without error.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
