### Title
Incomplete transaction-output verification silently accepts corrupted checkpoint state roots - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the local analog of the reported "checked one oracle but not the other" pattern: it validates several fields of a `TransactionInfo` against the locally-produced `TransactionOutput` (status, gas used, write-set hash, event root hash) but **explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`**, which are also part of the same `TransactionInfo`/`TransactionInfoV1` struct that gets committed to the ledger and covered by the transaction accumulator.

### Finding Description
`ensure_match_transaction_info` checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()` [1](#0-0) 

But it never checks `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against the actual computed state root(s). The code contains an explicit acknowledgment of this gap: [2](#0-1) 

`TransactionInfo`/`TransactionInfoV1` carries these checkpoint hash fields as first-class, hashed members of the struct that is stored in the transaction accumulator and authenticated by ledger-info signatures: [3](#0-2) 

This mirrors the external bug's core defect exactly: multiple independent commitments are supposed to be checked together to accept a value as valid, but the verification routine only checks a subset, leaving other commitment fields (here, the state/hot-state checkpoint roots) unauthenticated against the locally computed value.

### Impact Explanation
If a fetched `TransactionInfo` (e.g., during backup/restore replay-verify, or debugger/db-tool replay flows that call this function — confirmed callers include `aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `execution/executor/src/chunk_executor/mod.rs`, and `storage/db-tool/src/replay_on_archive.rs`) carries a `state_checkpoint_hash` that diverges from the actual locally-computed state root, this function will report success (`Ok(())`) even though the authenticated state root differs from the correct VM result. This is precisely the "authenticated ledger data bound to the wrong state" class of impact called out in the State-Integrity Gate: a wrong/corrupted state-checkpoint hash can be accepted as matching, undermining replay-verify tooling's ability to detect a divergent or forked state root.

I was not able to fully trace whether `execution/executor/src/chunk_executor/mod.rs` uses this exact function on the mainnet block-commit critical path (as opposed to only the read-only replay/verify tooling in `db-tool`/`aptos-debugger`); this remains unverified due to running out of tool budget. If it turns out to only guard offline replay-verify/debugger tooling and not the live consensus/state-sync commit path, the severity would be limited to "hard-fork-only divergence during replay/restore," which is still in-scope per the gate, but the concrete blast radius (whether it affects `chunk_executor`'s state-sync application path) is unconfirmed.

### Likelihood Explanation
The gap is not a hypothetical edge case — it's called out by name in a `TODO` comment in the code itself referencing `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, indicating the authors are aware the checkpoint-hash fields are unchecked and this is an existing, currently-shipped condition rather than a theoretical one. Any code path that trusts `ensure_match_transaction_info` as its sole state-root integrity check (rather than separately verifying `state_checkpoint_hash` via the accumulator proof against a signed `LedgerInfo`) would silently accept a mismatched checkpoint hash.

### Recommendation
Extend `ensure_match_transaction_info` to compute the actual state-checkpoint hash (and hot-state / position-state checkpoint hashes, when the relevant features are enabled) from the locally executed state and compare it against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, failing loudly on mismatch, exactly as is done for `state_change_hash` and `event_root_hash`. Any caller relying on this function for replay/restore verification should not consider verification complete until this is resolved.

### Proof of Concept
1. Construct a `TransactionOutput` with a correct write-set/events/status/gas, but supply (or intercept) a `TransactionInfo` whose `state_checkpoint_hash` does not match the actual post-execution state root (e.g., corrupted during backup fetch or during a hard-fork state-root divergence).
2. Call `ensure_match_transaction_info(version, txn_info, ...)`. [4](#0-3) 
3. Observe that the function returns `Ok(())` despite the checkpoint hash mismatch, because none of the four `ensure!` checks reference `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
