### Title
Wallet Contract's `has_in_flight_tx` lock can be stuck permanently `true` if a cross-contract callback panics, permanently freezing the ETH-implicit account - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (NEP-518) that is deployed on every ETH-implicit account uses a boolean flag `has_in_flight_tx` to serialize transaction processing: `rlp_execute` refuses new work whenever the flag is `true`, and the flag is only ever reset back to `false` at the top of the `#[private]` callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). [1](#0-0) [2](#0-1)  Since NEAR receipt execution atomically discards *all* state writes made by a function call when that call aborts (out of gas, deserialization panic, VM trap, etc.), any panic inside a callback — even after the `self.has_in_flight_tx = false;` line has logically executed in the function body — is rolled back along with everything else in that callback invocation, leaving the on-chain flag permanently `true`.

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` and schedules a promise chain that always ends in one of the `#[private]` callbacks, each of which begins by resetting the flag: e.g. `address_check_callback` [3](#0-2) , `nep_141_storage_balance_callback` [4](#0-3) , `rlp_execute_callback` [5](#0-4) , and `ban_relayer` [6](#0-5) .

The gas budget for these callbacks is a small, fixed constant computed at compile time (`ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `RLP_EXECUTE_CALLBACK_GAS`, each only a few TGas), independent of what the external contract being called (an arbitrary target, an arbitrary NEP-141 token contract, or the address registrar) actually returns: [7](#0-6) 

Because `target`, and for ERC-20 emulation the NEP-141 `token_id`, are attacker/relayer-controlled account IDs pointing at arbitrary contracts, an adversarial or buggy target/token contract can be crafted to return an oversized or deeply-nested response payload to `storage_balance_of`/registrar `lookup`. Deserializing (`serde_json::from_slice`) or otherwise processing that payload inside the fixed-gas callback can exceed the statically attached gas, causing the callback receipt to abort with an out-of-gas/host error. Any such abort rolls back the entire callback's state changes — including the reset of `has_in_flight_tx` — while the earlier `rlp_execute` call (which set the flag to `true`) had already committed successfully in a prior receipt.

Once `has_in_flight_tx` is stuck `true`, every future `rlp_execute` call is rejected up front: [8](#0-7) 
There is no other entry point capable of resetting the flag (it can only be set to `false` inside the very callbacks that are now unreachable), and ETH-implicit accounts cannot have a full-access key added or be deleted. [9](#0-8)  This is directly analogous to the reported Solidity issue: a fixed, unconditioned assumption baked into the contract (there, an internal-only getter used via `staticcall`; here, a fixed gas budget for a callback whose input size is attacker-influenced) causes an on-chain, unprivileged, protocol-critical code path to permanently and irrecoverably fail.

### Impact Explanation
Every future action originating from the affected ETH-implicit account (transfers, function calls, adding a relayer key) is permanently blocked because `rlp_execute` is the sole entry point into the account, and it always short-circuits while `has_in_flight_tx` is `true`. This matches "permanently frozen funds" — all NEAR and NEP-141 assets held by that ETH-implicit account become unspendable indefinitely, with no owner-controlled recovery path once the lock is set and the reset path is unreachable.

### Likelihood Explanation
The trigger requires only a single relayer-submitted transaction/receipt naming a `target` (or, for ERC-20 emulation, an NEP-141 `token_id`) that the caller controls or colludes with, arranged to return an oversized payload from `storage_balance_of`/registrar `lookup`. No validator or network compromise is needed — a normal user (or a malicious relayer acting on the user's signed but replay-protected transaction) reaching the wallet contract via ordinary `FunctionCall` receipts is sufficient to reach this code path.

### Recommendation
- Do not tie the correctness of the `has_in_flight_tx` unlock to successful completion of a bounded-gas callback whose workload size is influenced by an external, potentially adversarial contract.
- Bound/validate the size of cross-contract responses before deserializing them inside gas-constrained callbacks (e.g., reject overly large `PromiseResult::Successful` payloads early, or attach gas proportional to a conservative worst-case bound with an explicit cap check before parsing).
- Consider a watchdog/timeout or an explicit unprivileged "unlock" path (e.g., allow resetting `has_in_flight_tx` if no promise resolves within some number of blocks) so a stuck flag can be recovered without relying on the exact callback that failed.

### Proof of Concept
1. Deploy the Wallet Contract on an ETH-implicit account `A` (as done automatically on first transfer to an ETH-implicit address).
2. Deploy an attacker-controlled "token" contract `T` implementing NEP-141's `storage_balance_of` to return an intentionally huge/deeply nested JSON blob.
3. From account `A`, submit an RLP-encoded Ethereum transaction emulating an ERC-20 transfer with `target = T` via `rlp_execute`, per the flow in `inner_rlp_execute`/`action_to_promise` for `EthEmulationKind::ERC20Transfer`. [10](#0-9) 
4. `rlp_execute` sets `has_in_flight_tx = true` and schedules `Promise::new(T).function_call("storage_balance_of", ...)` followed by `.then(ext.nep_141_storage_balance_callback(...))` with gas capped at `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`.
5. `T` returns the oversized payload; `nep_141_storage_balance_callback` attempts `serde_json::from_slice` on it and exceeds its attached gas, aborting the receipt.
6. Because the receipt aborted, the `self.has_in_flight_tx = false;` write is rolled back; the flag remains `true` in committed state.
7. Any subsequent `rlp_execute` call on account `A` (with correctly incrementing nonce and valid signature) is now rejected with "transaction already in progress, please try again later" forever, since no receipt can ever reach the reset code inside the failing callback again — permanently freezing account `A`'s funds.
