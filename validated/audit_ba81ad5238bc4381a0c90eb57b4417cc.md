### Title
Frozen balance duration bound is not enforced unless a config flag is set, contradicting the freeze duration invariant - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.validate()` is supposed to enforce that a `FreezeBalanceContract`'s `frozenDuration` stays within `[minFrozenTime, maxFrozenTime]`, the on-chain equivalent of the Astaria "loan duration must not exceed spec bound" invariant. The enforcement is gated behind a boolean derived from a config value that is explicitly commented as test-only, meaning the bound can silently be skipped depending on deployment configuration.

### Finding Description
In `validate()`:
```java
long frozenDuration = freezeBalanceContract.getFrozenDuration();
long minFrozenTime = dynamicStore.getMinFrozenTime();
long maxFrozenTime = dynamicStore.getMaxFrozenTime();

boolean needCheckFrozeTime = CommonParameter.getInstance()
    .getCheckFrozenTime() == 1;//for test
if (needCheckFrozeTime && !(frozenDuration >= minFrozenTime
    && frozenDuration <= maxFrozenTime)) {
  throw new ContractValidateException(...);
}
``` [1](#0-0) 

The min/max duration bound check — the exact analog of the Astaria "duration must not exceed next epoch" rule — is only executed `if (needCheckFrozeTime)`. `needCheckFrozeTime` is computed from `CommonParameter.getInstance().getCheckFrozenTime()`, a field explicitly annotated `// clearParam: 1` and referenced in the actuator with the comment `//for test`: [2](#0-1) 

This means the actual enforcement of the duration invariant depends entirely on how `checkFrozenTime` is wired up at runtime/config, rather than being an unconditional protocol rule. This is structurally the same defect class as M-12: a documented duration constraint exists (min/max frozen days), but the code path that enforces it is conditionally bypassable, so the implementation does not unconditionally adhere to the spec.

By contrast, `AssetIssueActuator` enforces its analogous `frozenDays` bound unconditionally without any test-only gate: [3](#0-2) 

which highlights the inconsistency — one actuator enforces the duration bound unconditionally, the other only when a flag (intended for tests) happens to be enabled.

### Impact Explanation
If `checkFrozenTime` is not set to `1` in a given node's/network's configuration, `FreezeBalanceActuator` will accept any `frozenDuration` value (including durations far outside `[minFrozenTime, maxFrozenTime]`) for BANDWIDTH/ENERGY/TRON_POWER freezes. Frozen balance duration directly affects when funds become unfreezable and interacts with resource-weight accounting (`TotalNetWeight`/`TotalEnergyWeight`) and reward/vote calculations tied to `TRON_POWER`. An unbounded or mis-bounded freeze duration breaks the documented invariant and could distort resource/reward accounting in ways operators and downstream logic assume are bounded.

### Likelihood Explanation
Likelihood depends entirely on the deployment/config value of `checkFrozenTime`; I could not confirm from the indexed files what the production default is in `mainnet.conf`/`testnet.conf` (only the `reference.conf` had matches, which I was not able to fully inspect before the tool budget ran out). Because the flag is explicitly commented "for test" in the actuator and "clearParam: 1" (test-clear default) in `CommonParameter`, there is a real possibility that production configurations do not set it to `1`, in which case the bound is never enforced for every `FreezeBalanceContract` transaction (a widely reachable, unprivileged, broadcastable transaction type).

### Recommendation
Remove the conditional gating and enforce the `minFrozenTime`/`maxFrozenTime` duration bound unconditionally in `FreezeBalanceActuator.validate()`, consistent with how `AssetIssueActuator` enforces its analogous `frozenDays` bound. If a test-only bypass is required, it should be strictly confined to test build/config profiles (e.g., via a test-only subclass or explicit test harness), never via a general `CommonParameter` field that ships in the same binary as production nodes.

### Proof of Concept
Not applicable as a runnable PoC here — I could not confirm the actual default value of `checkFrozenTime` shipped in production configs (`mainnet.conf`) within the available tool budget, so I cannot definitively prove this is exploitable in the default mainnet deployment; this needs to be verified against the actual production config files (`framework/src/main/java/org/tron/core/config/args/Args.java` and the mainnet `.conf` resource) to confirm whether `checkFrozenTime` defaults to `0` (bypassing the check) or `1` (enforcing it) outside of tests.
