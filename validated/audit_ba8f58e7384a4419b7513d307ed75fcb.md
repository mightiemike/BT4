### Title
`WithdrawExpireUnfreezeProcessor.validate()` omits the `supportUnfreezeDelay()` committee feature-gate present in `WithdrawExpireUnfreezeActuator.validate()`, allowing the TVM native-contract path to withdraw expired-unfreeze balances even when the feature is disabled - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java])

### Summary
`WithdrawExpireUnfreezeActuator.validate()` explicitly rejects the transaction with `ContractValidateException` when `dynamicStore.supportUnfreezeDelay()` is false, gating the whole "expire-unfreeze withdraw" feature behind a committee-controlled dynamic property. `WithdrawExpireUnfreezeProcessor.validate()` (invoked from the TVM native-contract dispatch path in `Program.java`) contains no equivalent check, so a smart contract calling the native withdraw-expire-unfreeze opcode/precompile can execute the exact same balance-crediting logic (`getTotalWithdrawUnfreeze`/`getRemainWithdrawList`) while the feature is administratively disabled.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` performs this check before any accounting logic: [1](#0-0) 

`WithdrawExpireUnfreezeProcessor.validate()`, which is the entry point used by the TVM native-contract call path (referenced from `Program.java`), performs the address/account/amount checks but never calls or checks `dynamicStore.supportUnfreezeDelay()`: [2](#0-1) 

Both classes implement functionally identical `getTotalWithdrawUnfreeze`/`getRemainWithdrawList`/`execute()` logic that credits the owner's balance and clears/re-adds the `UnFreezeV2` list: [3](#0-2) [4](#0-3) 

This is a genuine code-level divergence: the committee-controlled feature flag `supportUnfreezeDelay()` is enforced only in the top-level actuator's `validate()`, not in the native-contract processor's `validate()`. I could not fully trace the TVM dispatcher (`Program.java`, which references `WithdrawExpireUnfreezeProcessor` 10 times) to confirm whether it independently re-checks `supportUnfreezeDelay()` before invoking `processor.validate()`/`execute()`; that call site was not retrievable within the available tool budget. If `Program.java` does not perform this same dynamic-property check itself, then a contract invoking the native withdraw-expire-unfreeze opcode would bypass the committee gate entirely, since `WithdrawExpireUnfreezeProcessor` has no such check of its own.

### Impact Explanation
If `Program.java` does not redundantly enforce `supportUnfreezeDelay()`, then disabling this dynamic property at the committee level (used to control rollout of the "unfreeze delay/expire withdrawal" feature) would not actually prevent users from withdrawing expired-unfreeze balances via a smart contract calling the TVM native contract, defeating the intended feature-gate/governance control and creating divergent behavior between the two entry points for the same underlying state transition.

### Likelihood Explanation
Exploitability depends entirely on whether `Program.java`'s native-contract dispatch independently checks `supportUnfreezeDelay()` before calling into `WithdrawExpireUnfreezeProcessor`. This could not be confirmed with the available search results (only match counts in `Program.java`, not the surrounding code, were retrieved). Without seeing that call site, I cannot conclusively state the missing check is unguarded end-to-end.

### Recommendation
Add an explicit `dynamicStore.supportUnfreezeDelay()` check at the start of `WithdrawExpireUnfreezeProcessor.validate()`, mirroring `WithdrawExpireUnfreezeActuator.validate()`, so the feature-gate is enforced identically regardless of entry point (actuator vs. TVM native contract), rather than relying on the caller (`Program.java`) to duplicate this business-logic check correctly.

### Proof of Concept
Java integration test plan (to be run against `WithdrawExpireUnfreezeProcessor` and `Program.java`'s native contract dispatch):
1. Set `dynamicPropertiesStore` such that `supportUnfreezeDelay()` returns `false`.
2. Create an account with a populated `UnFreezeV2` list whose `unfreezeExpireTime` is in the past relative to `latestBlockHeaderTimestamp`.
3. Call `WithdrawExpireUnfreezeActuator.validate()` directly and assert it throws `ContractValidateException("Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee")`.
4. Call `WithdrawExpireUnfreezeProcessor.validate(param, repo)` with the same repo/account state and assert whether it also throws (expected per the feature gate) or succeeds (confirming the divergence).
5. If step 4 succeeds, follow with `WithdrawExpireUnfreezeProcessor.execute(param, repo)` from a TVM-level test (invoking the corresponding opcode in `Program.java` from a deployed test contract) and assert the account balance increases and `UnFreezeV2` entries are cleared despite `supportUnfreezeDelay()` being disabled — confirming the bypass. If `Program.java` is found to independently gate the call, this PoC step will fail and the divergence is non-exploitable end-to-end, but the code-level inconsistency in `WithdrawExpireUnfreezeProcessor.validate()` still constitutes a maintenance/defense-in-depth defect.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
  }

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }

  private List<Protocol.Account.UnFreezeV2> getRemainWithdrawList(List<Protocol.Account.UnFreezeV2> unfrozenV2List, long now) {
    return unfrozenV2List.stream()
        .filter(unfrozenV2 -> unfrozenV2.getUnfreezeExpireTime() > now)
        .collect(Collectors.toList());
  }
