### Title
Deposit auto-swap `minPCOut` derived from the same-block Uniswap V3 spot quote allows sandwich extraction from every GAS/GAS_AND_PAYLOAD inbound - (File: x/uexecutor/keeper/evm.go)

### Summary
`GetSwapQuote` reads `QuoterV2.quoteExactInputSingle` with `SqrtPriceLimitX96 = 0` (no bound) immediately before `CallPRC20DepositAutoSwap` executes the real swap in the same keeper call sequence, using `minPCOut = quote * 95 / 100` as the only protection. [1](#0-0)  Because the "slippage bound" is computed from the pool's own instantaneous price rather than an independent, TWAP-based or attacker-uncontrollable reference, an attacker who moves the pool price immediately before the module's deposit-and-swap executes forces the quote itself to reflect the manipulated price — the 5% tolerance band moves with the manipulation and provides no real protection, exactly as in the Arrakis H-6 report where minimum-out/price bounds derived from the same instant being manipulated failed to protect the depositor.

### Finding Description
`ExecuteInboundGas` (triggered once a `MsgVoteInbound` finalizes a GAS-type inbound) and `gasAndPayloadDepositAutoSwap` (used for GAS_AND_PAYLOAD) both call `GetSwapQuote` and then `CallPRC20DepositAutoSwap` back-to-back with no independent price check in between. [2](#0-1) [3](#0-2)  The same pattern repeats for the gas refund path in `applyGasRefund`. [4](#0-3) 

Both `GetSwapQuote`'s underlying `quoteExactInputSingle` call and the real swap performed by `depositPRC20WithAutoSwap` read the live Uniswap V3 pool state at execution time in the same block. There is no independent oracle price, no observation-window/TWAP guard, and no external caller (the depositing user) can supply their own acceptable price bound — the protocol computes both the reference price and the tolerance from the same manipulable instant, which is the identical bug class as Arrakis H-6: relying on the pool's own spot state to derive "slippage protection" against manipulation of that same pool.

An unprivileged attacker who controls (or can influence) the Uniswap V3 pool for a PRC20/WPC pair (e.g., by holding both sides of the pair or by simply placing ordinary swaps around the block in which the UV threshold vote finalizes an inbound) can:
1. Swap to push the PRC20/WPC pool price to an unfavorable rate just before the finalizing `MsgVoteInbound` is included.
2. The module's `GetSwapQuote` reads this manipulated price and derives `minPCOut` from it (95% of the manipulated quote, not of fair value).
3. `CallPRC20DepositAutoSwap` executes the deposit swap at the manipulated price, still satisfying the (also-manipulated) `minPCOut` check, converting the user's bridged PRC20 into WPC/PC at a bad rate.
4. The attacker reverses their initial swap in a following transaction, extracting the value the depositor lost, symmetric to Alice's front-run/back-run in the Arrakis PoC.

### Impact Explanation
Each affected inbound execution (`GAS`, `GAS_AND_PAYLOAD`) and every successful outbound gas refund with a swap leg routes user or protocol-owned funds through this unprotected auto-swap. [5](#0-4)  Because this is module-originated value movement (mint/deposit/refund of user funds via `depositPRC20WithAutoSwap`/`refundUnusedGas`), value is siphoned from users bridging into Push Chain on every affected inbound, not merely a slippage inconvenience — this is unauthorized loss of user-controlled funds via manipulable accounting during universal execution, which is in the allowed impact set (corruption of PRC20/native asset accounting and gas/refund accounting reachable from ordinary user deposit paths).

### Likelihood Explanation
The trigger requires no privileged role: any external actor able to trade against the relevant Uniswap V3 pool can manipulate its instantaneous price around the block that finalizes a UV vote and executes the deposit swap. Nothing in `ExecuteInboundGas`/`ExecuteInboundGasAndPayload`/`applyGasRefund` bounds the deviation between the quote and any externally-verifiable fair price, and no user-supplied minimum-out parameter exists to opt into stricter protection. This is reachable purely through ordinary deposit flows plus ordinary DEX trading — an unprivileged, permissionless condition, matching the "permissionless to exploit" escalation accepted in the original Sherlock report.

### Recommendation
Do not derive the slippage bound from the same instantaneous quote used for execution. Use a TWAP (time-weighted average price) read from the Uniswap V3 pool's oracle observations (or an independent chain-meta/price-oracle source already tracked by `x/uexecutor`'s `ChainMeta`) to compute `minPCOut`, and/or enforce a maximum allowed deviation between the spot price and the TWAP before allowing `depositPRC20WithAutoSwap`/`refundUnusedGas` to proceed; abort/hold the deposit (falling back to the non-swap PRC20 deposit path, which already exists) rather than executing at a manipulated instantaneous price.

### Proof of Concept
1. Attacker holds inventory of PRC20(token) and WPC in the Uniswap V3 pool used for that token's default fee tier (`GetDefaultFeeTierForToken`). [6](#0-5) 
2. Attacker submits a large swap that pushes the PRC20/WPC pool price against WPC just before/within the block where a UV `MsgVoteInbound` finalizes a pending GAS or GAS_AND_PAYLOAD inbound for a victim user.
3. `ExecuteInboundGas` calls `GetSwapQuote(quoterAddr, prc20, wpc, fee, amount)`, which reads the now-manipulated spot price and returns a depressed `quote`. [7](#0-6) 
4. `minPCOut = quote * 95 / 100` is computed from this depressed quote, then `CallPRC20DepositAutoSwap` executes the deposit-and-swap for the victim's bridged amount at the manipulated rate. [8](#0-7) 
5. Attacker reverses the initial swap in a follow-up transaction, extracting the value difference — funded by the victim's deposit having been auto-swapped at an unfair rate — mirroring the Alice front-run/back-run sequence in the original Arrakis H-6 PoC.

func (k Keeper) CallPRC20DepositAutoSwap(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount, fee, minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: depositPRC20WithAutoSwap",
		"prc20", prc20Address.Hex(),
		"recipient", to.Hex(),
		"amount", amount.String(),
		"fee", fee.String(),
		"min_pc_out", minPCOut.String(),
	)
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // who is sending the transaction
		handlerAddr,        // destination: Handler contract
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20WithAutoSwap",
		prc20Address,
		amount,
		to,
		fee,
		minPCOut,
		big.NewInt(0), // deadline = 0 → contract uses its default
