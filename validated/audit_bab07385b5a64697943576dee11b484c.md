#No Vulnerability found for this question.

The comma-join collision in `stringifyQueryForAppProxy` ( [1](#0-0) ) does create a theoretical string collision between `a=['1,2']` and `a=['1','2']`, but this does not constitute an exploitable authenticity bypass for an unprivileged attacker:

1. **No secret-free forgery path exists.** The attacker cannot generate a valid `signature` for *any* representation without `apiSecretKey`. The only way a signature exists is because Shopify itself computed it over the exact query it forwarded to the app proxy endpoint, using the same "sort keys, join array values with commas" algorithm mirrored by `stringifyQueryForAppProxy` ( [1](#0-0) ). This is intentionally documented and tested Shopify behavior, not a library-introduced defect — see the explicit test case that signs `consentGiven=true,false` ( [2](#0-1) ).

2. **`normalizeQuery` collapses `URLSearchParams` repeats identically for signing and for downstream consumption.** When the library receives `a=1&a=2` via `URLSearchParams`, it folds this into the single string `"1,2"` *before* both HMAC verification and before the value is handed to the route/business logic ( [3](#0-2) ). So the verifier and any downstream code operating on `normalizedQuery` see the exact same collapsed value — there is no divergence between "what was signed" and "what is acted upon" inside this library's boundary.

3. **The `APP_PROXY_SINGLE_VALUE_PARAMS` guard already prevents the security-critical fields (`hmac`, `shop`, `signature`, `timestamp`) from being duplicated/array-ified**, which is the actual attack surface that would matter for authentication bypass ( [4](#0-3) ), and this is explicitly tested ( [5](#0-4) ).

4. Any residual ambiguity between "array of two items joined with a comma" vs. "single string value containing a literal comma" for *non-security* application parameters is a semantic interpretation question for the host app's own business logic (how it re-parses `a=1,2`), not a forgeable authenticity break in `validateHmac`/`safeCompare` — and the rules explicitly exclude bugs in the host app rather than this library.

Since the attacker cannot produce a signature for a semantically different payload without the secret, and the library's own verification and consumption of the query value are consistent (same collapsed string), there is no reproducible path to "sign one representation, submit a different one" that `validateHmac` would incorrectly accept.

```typescript
function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}
```

```typescript
function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
```
