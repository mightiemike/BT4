## Title
DeleteAccount refund to a non-existent/deleted `beneficiary_id` results in permanent, unrecoverable token burn — ([File: runtime/runtime/src/actions.rs])

### Summary
The Sherlock finding describes ERC20 `recoverERC20()` functions that unconditionally push tokens to a single hardcoded recipient (`recipient()`/`owner()`); if that recipient can't receive the asset (blacklisted), the transfer reverts and the funds become permanently stuck with no way to redirect them elsewhere. The same bug class — "value is sent to a single account chosen at submission time, and if that account can't receive it, the value is unrecoverably lost, with no redirection mechanism" — is reachable in nearcore's `DeleteAccount` action, where the account's remaining balance is unconditionally sent to `beneficiary_id` as a system refund receipt, and if that receipt fails to execute (e.g. because the beneficiary no longer exists), the balance is permanently burned rather than returned to the signer or redirected.

### Finding Description
When any account signer submits a `DeleteAccount` action, `action_delete_account` computes `account_balance = account_ref.amount()` and, if positive, unconditionally emits `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`: [1](#0-0) 

`Receipt::new_balance_refund` builds the receipt with `predecessor_id = "system"`, which the runtime treats as a "refund receipt": [2](#0-1) 

Refund receipts can never implicitly create the receiving account — `implicit_creation_allowed` explicitly returns `false` whenever `is_refund` is true: [3](#0-2) 

So if `beneficiary_id` does not exist at the time the refund receipt executes — e.g. it was mistyped, or (more importantly) it was a valid account when the `DeleteAccount` transaction was signed but got deleted (by its own owner, or by another `DeleteAccount`/protocol action) before this asynchronous refund receipt is processed — the `Transfer` action inside the refund receipt fails with `AccountDoesNotExist`.

Crucially, the runtime documents and implements that a failing refund is never retried, redirected, or returned to the original account (which no longer exists either, since it was just deleted) — the deposit is unconditionally burned: [4](#0-3) 

This exact behavior is asserted by an existing unit test, confirming the funds are gone for good (not "delayed" or held anywhere recoverable): [5](#0-4) 

And the design doc for refunds confirms this is expected/known behavior, not a corner case: "If the execution of a refund fails, the refund amount is burnt." [6](#0-5) 

There is no `onlyRecipient`/redirect equivalent for this action — `DeleteAccountAction` only carries a single `beneficiary_id` set at signing time, with no way for the network or the account owner to redirect the payout to a different address once the delete-account transaction/receipt is in flight and the beneficiary has since become unusable: [7](#0-6) 

### Impact Explanation
Unlike the ERC20 case (funds merely "locked" in the contract, technically recoverable if the blacklist is lifted), the NEAR analog is strictly worse: the balance is **burned/destroyed** — a concrete, permanent loss of value with no possibility of recovery under any future condition, and it reduces total NEAR supply (`other_burnt_amount`, later folded into `balance_burnt`). This is fully consistent with the "permanently frozen funds" (here even stronger: permanently destroyed funds) impact category called out for acceptance. Because a `DeleteAccount` is often the very last balance-bearing action for an account, and the beneficiary is chosen once at signing time with no revocation/redirect option, any race where the beneficiary account is removed (self-deleted, or purged for any other reason) between transaction submission and receipt execution destroys the deletor's entire remaining balance.

### Likelihood Explanation
Reachable directly by any unprivileged transaction signer issuing a normal `DeleteAccount` action — no special permissions, validator status, or malicious peer/network behavior required. The triggering condition (beneficiary account ceasing to exist between signing and asynchronous cross-shard receipt execution) is a realistic race in normal usage: e.g. sending the delete-account transaction to a friend/service account that itself gets deleted (or was deleted) around the same time, or a simple account-name/typo error that goes unnoticed until the receipt actually executes and the deletion has already destroyed the source account (so no fallback recipient exists). Given `DeleteAccount`'s beneficiary is a single point of failure with no override, the probability compounds with normal account churn.

### Recommendation
Consider adding a validation step at receipt-processing time (or a fallback/rescue path) so that when the balance-refund receipt from a `DeleteAccountAction` fails because the beneficiary no longer exists, the funds are not silently burned. Options include: requiring `beneficiary_id` existence to be (re-)verified as part of executing the `DeleteAccount` action rather than deferred to an unconditional refund receipt, or providing an explicit "rescue" transaction/receipt type analogous to `recoverERC20`'s suggested fix that lets a designated party redirect otherwise-unclaimable refunds before they are burned.

### Proof of Concept
1. Account `A` holds balance `X` and signs `DeleteAccountAction { beneficiary_id: B }`.
2. Before the resulting refund receipt (`Receipt::new_balance_refund(B, X)`, `runtime/runtime/src/actions.rs:385`) is processed in a later chunk/shard, account `B` is deleted (by its own valid `DeleteAccount` transaction, or any other means).
3. `action_delete_account` still deletes `A`, per its code path with no dependency on `B`'s existence at that time (`runtime/runtime/src/actions.rs:380-387`).
4. When the refund receipt for `X` executes against non-existent `B`, `check_account_existence`/`implicit_creation_allowed` reject account creation for a refund (`runtime/runtime/src/actions.rs:930-933`), producing `AccountDoesNotExist` and receipt failure.
5. Per `runtime/runtime/src/lib.rs:1047-1055`, because `predecessor_id().is_system()` is true and `result.result.is_err()`, the full deposit `X` is added to `other_burnt_amount` — permanently destroyed, exactly as reproduced by the existing `refund_may_not_create_universal_account` test at `runtime/runtime/src/tests/apply.rs:6880-6926`.

```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
