### Title
`liquidate-multi` absorbs mid-flight liquidation failures after an earlier atomic sub-call already committed, stranding liquidator funds and desyncing debt accounting - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` batches liquidations with `(map call-liquidate positions)`, where `call-liquidate` invokes `liquidate` as a plain in-contract function call rather than a `contract-call?`. `liquidate` executes several sequential state-mutating steps against other contracts (`vault-system-repay`, then `debt-remove-scaled`, `collateral-remove`, and a bad-debt socialization `fold`) via `try!`. Each of those is its own atomic `contract-call?` checkpoint, but `liquidate` itself is not, and its `err` return is never propagated past `map`, so the surrounding `liquidate-multi` transaction still returns `(ok ...)`. This is the batching analog of the ERC4626 report's theme of a component silently deviating from the invariant callers rely on: a "failed" liquidation in the report's terms is treated as fully undone, but on-chain only the last failing step is undone — earlier committed sub-calls are not.

### Finding Description
`liquidate` performs, in order:
1. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` — pulls tokens from the liquidator and credits the vault as repaid debt.
2. `(try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))`
3. `(try! (contract-call? .v0-market-vault collateral-remove borrower coll-final collateral-ft coll-aid actual-receiver))`
4. A `fold socialize-debt-asset` pass with `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [1](#0-0) 

Each of steps 1–3 is an independent `contract-call?`, which in Clarity is its own atomicity checkpoint: if step 1 succeeds, its state changes (moving the liquidator's tokens, crediting the vault) are committed to the transaction's working state regardless of what happens afterward, unless the *top-level* transaction itself ultimately returns `(err ...)`.

When `liquidate` is called directly by a user, `liquidate` **is** the top-level transaction, so any later `asserts!`/`try!` failure (e.g. in step 4's bad-debt socialization) causes the whole transaction — including step 1's already-executed repay — to roll back. That is the safe path.

`liquidate-multi` breaks this guarantee: [2](#0-1) 
`call-liquidate` calls `liquidate` as a bare function invocation: [3](#0-2) 
and `liquidate-multi` wraps the whole list of individual results in `ok`, so the *outer* transaction the user actually submitted always succeeds:
```
(define-public (liquidate-multi (positions ...))
  (ok (map call-liquidate positions)))
```
This is explicitly acknowledged in the code comment: "Failed liquidations return error codes but don't revert entire batch." [4](#0-3) 

Because `liquidate`'s own `err` return is absorbed as data inside the `map`/`fold`-style batch and never propagates to make `liquidate-multi` itself return `err`, the Clarity VM commits the whole transaction — including step 1's already-executed `vault-system-repay` for any position whose *later* step (2, 3, or 4) subsequently fails. This exactly matches the allowed "fold that absorbs failure" and "multi-step entry point that strands value on abort" mechanism classes: `vault-system-repay`'s mutation is evaluated and committed before the later guard (`debt-remove-scaled`/`collateral-remove`/socialization `asserts!`) can invalidate the whole operation, and because the entry point (`liquidate-multi`) is multi-step across positions, an abort partway through one position's flow strands the resources already moved in step 1.

### Impact Explanation
For any batched position where step 1 succeeds but a later step fails (e.g. `debt-remove-scaled` reverting due to a stale/insufficient scaled-debt read, or `ERR-BAD-DEBT-SOCIALIZATION-FAILED` in the socialization fold, or `collateral-remove` failing on that borrower's collateral state):
- The liquidator's `debt-to-repay` tokens are consumed by `vault-system-repay` and permanently committed to the vault (theft-adjacent: liquidator receives no collateral for capital spent, and the specific loan tranche is marked repaid at the vault level).
- The borrower's per-asset scaled debt in `market-vault` is **not** decremented (step 2 never committed), so the borrower's on-chain obligation and the vault's aggregate `total-borrowed`/`assets` bookkeeping fall out of sync.
- This directly produces protocol insolvency-class accounting desync (vault believes less is owed than the market-vault ledger says is owed) and unclaimed value loss to the liquidator, both in-scope Critical/High impact categories (direct fund loss and protocol insolvency via broken invariants).

### Likelihood Explanation
Any liquidator can trigger this by submitting `liquidate-multi` with at least one position engineered (or naturally arising from a race with another liquidator/borrower action in the same batch) to fail on `debt-remove-scaled`, `collateral-remove`, or the bad-debt socialization step after `vault-system-repay` has already succeeded. Since `price-feeds` updates are not supported per-position in the batch (per the code's own comment), stale price/state conditions across a multi-position batch make partial failures realistically likely, not merely theoretical.

### Recommendation
Do not let `liquidate-multi` treat a partially-executed, ultimately-failing `liquidate` as an isolated, cleanly-undone unit while still returning overall success. Either:
- Invoke each `liquidate` in the batch via `as-contract? (contract-call? .v0-4-market liquidate ...)` (i.e. force a genuine `contract-call?` boundary) so that if `liquidate` returns `err`, all of its internal sub-call effects (including `vault-system-repay`) are rolled back by the VM, or
- Reorder `liquidate`'s steps so that the token-moving `vault-system-repay` call happens only after all other validations/mutations that can fail have already succeeded (last, not first), or
- Have `liquidate-multi` propagate any per-position failure by asserting all positions succeeded (abandoning "partial batch success" semantics), matching the same all-or-nothing guarantee that a directly-invoked `liquidate` provides.

### Proof of Concept
1. Attacker (or any liquidator) submits `liquidate-multi` with two position entries for the same borrower/debt-asset, or one position where `scaled-to-remove`/`coll-final` computed off stale cached indexes will fail `debt-remove-scaled` or `collateral-remove` validation in `market-vault` (e.g. due to a race where the borrower's `debt`/`collateral` maps were already touched by a concurrent operation earlier in the same batch via `socialize-debt-asset` from a prior position in the list).
2. For the crafted position, `liquidate` executes `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` [5](#0-4)  successfully — liquidator's tokens are pulled and the vault-level repay is committed (independent `contract-call?` checkpoint).
3. The subsequent `(try! (contract-call? .v0-market-vault debt-remove-scaled ...))` or `collateral-remove` call fails validation and returns `err`. [6](#0-5) 
4. `liquidate` returns `(err ...)` for that position, but `call-liquidate`/`map`/`liquidate-multi` simply place that `err` into the results list and still return `(ok (list ...))` for the whole transaction. [7](#0-6) 
5. Because the top-level transaction (`liquidate-multi`) returns `ok`, the VM commits everything, including step 2's `vault-system-repay` mutation — the liquidator's funds are gone, no collateral was received, and the borrower's debt ledger in `market-vault` no longer matches the vault's `total-borrowed` accounting.
