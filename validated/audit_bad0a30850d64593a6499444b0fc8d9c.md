### Title
Naturally-expired inbound ballots route to `ExpiredInbounds` with no consuming refund path, permanently locking user-deposited funds - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
When an inbound's ballot naturally reaches a terminal failure state (`EXPIRED` via `ExpireBallotsBeforeHeight`, or `REJECTED` via failed vote quorum) without ever passing, `x/uexecutor`'s `BallotHooks.afterInboundBallotTerminal` moves the full audit trail into the `ExpiredInbounds` collection instead of the `UniversalTx`/outbound pipeline. No `UniversalTx` is ever created for that inbound, so no PRC20 mint happens and no refund/outbound is ever generated — yet the user has already deposited real funds on the source chain gateway expecting Push Chain to mint/settle them. `ExpiredInbounds` is documented and coded purely as an audit log: it is written (`ExpiredInbounds.Set`) and read only by a read-only query (`AllExpiredInbounds`); there is no message handler, keeper function, or automated hook that ever consumes an `ExpiredInboundEntry` to build a refund outbound. This is the direct analog of the `SpiceAuction` bug: an unprivileged user action (submitting a genuine cross-chain deposit whose vote ballot fails to reach quorum) results in funds becoming permanently stuck with the chain's own code acknowledging ("Consumed by the future escape-hatch refund flow") that the recovery mechanism does not yet exist.

### Finding Description
The lifecycle is described in `x/uexecutor/README.md:244-260`: `PendingInbounds` entries are created on the first validator vote, and when ALL ballot variants reach a terminal state, "If ALL variants ended `EXPIRED`/`REJECTED`, the full per-variant audit trail is moved to `ExpiredInbounds` for the **future** escape-hatch refund flow" [1](#0-0) .

The implementation in `BallotHooks.afterInboundBallotTerminal` confirms this: once all variants are terminal and none `PASSED`, it writes to `ExpiredInbounds` and does nothing else [2](#0-1) .

`ExpiredInboundEntry`'s own doc comment states it is "Consumed by the future escape-hatch refund flow" [3](#0-2)  — i.e. that consumer does not exist yet. A grep across the repo confirms `ExpiredInbounds` is only ever `Set`, `Get`, `Has`, `Walk`'d for the audit-trail and iterated by the read-only `AllExpiredInbounds` query [4](#0-3) ; no `Msg*` handler or keeper function reads `ExpiredInbounds` to build an `OutboundTx`/refund.

The chain *does* have an admin escape hatch, `MsgRevertStuckInbound` / `Keeper.RevertStuckInbound`, but it operates on a **different** scenario: a ballot stuck in `PENDING` (never reaching a terminal state), which the admin must first drive to `EXPIRED` via `MsgRecomputeBallotQuorum` and then revert [5](#0-4) . This path checks `ballot.Status == BALLOT_STATUS_EXPIRED` against the live `x/uvalidator` `Ballots` collection and then calls `CreateUniversalTx` + `attachOutboundsToUtx` to actually build the refund outbound [6](#0-5) .

Because `MarkBallotExpired`/`MarkBallotFinalized` persist the ballot record with its terminal status rather than deleting it (`DeleteBallot` is a separate, unused-here function) [7](#0-6) [8](#0-7) , it is *possible* an admin could invoke `MsgRevertStuckInbound` for a naturally-EXPIRED inbound ballot too (since `GetBallot` still resolves it). However:
1. `RevertStuckInbound` requires exact status `EXPIRED` — a naturally `REJECTED` ballot (failed-vote quorum, not timeout) is rejected outright with "requires EXPIRED" [9](#0-8) , so `REJECTED` inbounds have **no available recovery path at all**, privileged or not.
2. Even for `EXPIRED` ballots, this recovery is strictly a privileged admin-only action (`admin != msg.Signer` is rejected) — it is not a chain-driven, automatic, or user-triggerable mechanism, and the `ExpiredInbounds` audit trail that was purpose-built to support this flow is never actually referenced by it (the admin flow re-derives everything from the raw `Inbound` payload supplied off-chain, bypassing `ExpiredInbounds` entirely).

Net effect: for the `REJECTED` terminal case — reachable purely by ordinary validator voting behavior on a genuine unprivileged user deposit, no malicious node/validator required — there is no recovery mechanism whatsoever, matching the reported bug class precisely.

### Impact Explanation
A user who deposits real funds on a source chain (source-chain gateway lock/burn) triggering an `Inbound` vote can have that inbound's ballot resolve to `REJECTED` (e.g., due to conflicting/incompatible payload variants splitting the vote so no variant reaches the 2/3+1 threshold before expiry — this can happen with honest validators observing minor payload-encoding differences, which the README explicitly acknowledges as a designed possibility via "variant-aware" ballots). In that case, per `afterInboundBallotTerminal`, the audit entry lands in `ExpiredInbounds` with terminal status `REJECTED`, no `UniversalTx`/mint/outbound is ever created on Push Chain, and no code path — admin or automatic — can build a refund from a `REJECTED` entry (`RevertStuckInbound` only accepts `EXPIRED`). The user's source-chain funds are permanently unrecoverable through any on-chain Push Chain mechanism. This is a genuine permanent loss of user funds triggered by ordinary usage.

### Likelihood Explanation
Likelihood is moderate: it requires validator votes to split across multiple non-identical `Inbound` variants (e.g. differing decoded payload bytes for the same source event) such that no single variant reaches quorum before ballot expiry, or a ballot to be actively voted down to `REJECTED`. The `InboundVariant`/multi-variant design in `PendingInboundEntry` shows this is an anticipated, non-adversarial scenario in production (honest validators observing/marshaling slightly different bytes), not a contrived edge case.

### Recommendation
Implement the "escape-hatch refund flow" that the code already reserves storage for: add a keeper function/message that consumes `ExpiredInboundEntry` records (keyed by `utx_key`) and builds an `INBOUND_REVERT`-style `OutboundTx` refunding the original sender, mirroring `buildRevertOutbound`/`attachOutboundsToUtx` used by `RevertStuckInbound`. Ensure this covers both `EXPIRED` and `REJECTED` terminal variants (currently `RevertStuckInbound` only accepts `EXPIRED`), and decide whether this should be automatic (chain-driven from the `BallotHooks` terminal callback itself) or an explicit, ideally non-privileged/self-service message so affected users are not dependent on manual admin intervention for every stuck deposit.

### Proof of Concept
1. Two validators submit `MsgVoteInbound` for the same logical source-chain event but with slightly different `Inbound` payload bytes (different variants), splitting the eligible-voter set so neither variant's ballot reaches its 2/3+1 threshold (mirrors `TestBallotHook_MultiVariant_AllExpiredRoutesEntireEntry` / `TestBallotHook_SingleVariantRejectedRoutesToExpiredInbounds` in `test/integration/uexecutor/pending_inbound_audit_trail_test.go`).
2. Both ballots terminate (`EXPIRED` via timeout or `REJECTED` via vote), `afterInboundBallotTerminal` moves the entry to `ExpiredInbounds`, and no `UniversalTx` is created — confirmed by `TestBallotHook_MultiVariant_AllExpiredRoutesEntireEntry`.
3. Query `AllExpiredInbounds` — the entry is visible, but there is no message/keeper call anywhere in the codebase that turns this entry into a refund outbound.
4. For the `REJECTED` case specifically, attempt `MsgRevertStuckInbound` (even as admin) with the same `Inbound` payload — it is rejected with `"requires EXPIRED"` per `TestRevertStuckInbound_PassedBallot_Rejected`-style assertions in `x/uexecutor/keeper/msg_server.go:187-198`, leaving no recovery path at all.

**Note:** I was unable to fully trace the exact source-chain gateway contract semantics (whether/when the user's tokens are irrevocably locked/burned on the source chain before Push Chain quorum is reached) since that Solidity contract lives outside this repository's indexed scope; this assessment relies on the documented inbound lifecycle in `x/uexecutor/README.md` describing minting as occurring only after quorum. If the source-chain gateway does not commit/burn funds until Push Chain confirms, the severity would be lower.

// RevertStuckInbound creates an INBOUND_REVERT outbound for an inbound whose
// ballot has expired without finalizing. The revert outbound enters the normal
// PendingOutbounds flow; UVs sign it via TSS and broadcast it to the source
// chain, refunding the user.
//
// Strict precondition: the ballot for the supplied inbound must be in EXPIRED
// state. Admin must run MsgRecomputeBallotQuorum first to drive a stuck ballot
// to EXPIRED if it isn't already (recompute auto-expires when no eligible
// voters remain).
//
// Returns the new UTX ID and revert outbound ID for telemetry.
func (k Keeper) RevertStuckInbound(ctx context.Context, inbound types.Inbound) (utxId, outboundId string, err error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Same canonical form as the vote path, so the admin-supplied payload
	// derives the same ballot key / UTX key the votes did.
	inbound.Canonicalize()

	if vErr := inbound.ValidateBasic(); vErr != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, vErr.Error())
	}

	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, fmt.Sprintf("failed to derive ballot key: %s", err))
	}

	ballot, err := k.uvalidatorKeeper.GetBallot(ctx, ballotKey)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrNotFound, fmt.Sprintf("ballot for inbound not found (key=%s): %s", ballotKey, err))
	}

	if ballot.Status != uvalidatortypes.BallotStatus_BALLOT_STATUS_EXPIRED {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest,
			fmt.Sprintf("ballot %s status is %s; admin revert requires EXPIRED (use MsgRecomputeBallotQuorum to drive a stuck pending ballot to EXPIRED)",
				ballotKey, ballot.Status.String()))
	}

func (k Keeper) MarkBallotExpired(ctx context.Context, id string) error {
	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as expired",
		"ballot_id", id,
		"expiry_height", ballot.BlockHeightExpiry,
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.ExpiredBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = types.BallotStatus_BALLOT_STATUS_EXPIRED
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, types.BallotStatus_BALLOT_STATUS_EXPIRED)
	return nil
}

func (k Keeper) MarkBallotFinalized(ctx context.Context, id string, status types.BallotStatus) error {
	if status != types.BallotStatus_BALLOT_STATUS_PASSED && status != types.BallotStatus_BALLOT_STATUS_REJECTED {
		return fmt.Errorf("invalid finalization status: %v", status)
	}

	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as finalized",
		"ballot_id", id,
		"final_status", status.String(),
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.FinalizedBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = status
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, status)
	return nil
}

// RevertStuckInbound is the admin escape hatch — see Keeper.RevertStuckInbound.
func (ms msgServer) RevertStuckInbound(ctx context.Context, msg *types.MsgRevertStuckInbound) (*types.MsgRevertStuckInboundResponse, error) {
	ms.k.Logger().Info("msg: RevertStuckInbound", "signer", msg.Signer)

	admin, err := ms.k.uvalidatorKeeper.GetAdmin(ctx)
	if err != nil {
		return nil, errors.Wrap(err, "failed to read uvalidator admin")
	}
	if admin != msg.Signer {
		return nil, errors.Wrapf(govtypes.ErrInvalidSigner, "invalid admin; expected %s, got %s", admin, msg.Signer)
	}

	if msg.Inbound == nil {
		return nil, errors.Wrap(sdkErrors.ErrInvalidRequest, "inbound is required")
	}

	utxId, outboundId, err := ms.k.RevertStuckInbound(ctx, *msg.Inbound)
	if err != nil {
		return nil, err
	}
