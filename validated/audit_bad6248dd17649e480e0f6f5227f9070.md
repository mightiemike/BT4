## Analog Found: Replay-verification skips authenticated state-root checks

### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, letting replay-verify tools accept a corrupted state root as matching - (File: `types/src/transaction/mod.rs`)

### Summary
The external Streamr report is about a value derived from a config parameter (`minimumStakeWei`) silently becoming inconsistent with the actual committed state, breaking an invariant assumed later and causing wrong behavior to go unnoticed until it reverts. The Aptos-native analog is a comparator function used by every replay/verification tool that is supposed to prove "locally re-executed transaction output == authenticated on-chain `TransactionInfo`", but the function structurally omits the very fields that commit to the accumulated ledger state root, hot-state root, and native-position state root. This lets a real state-root divergence pass verification silently.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the shared comparator used to assert that a freshly-computed `TransactionOutput` matches the authenticated `TransactionInfo` (the object whose hash is what's actually stored in the transaction accumulator and covered by validator signatures). [1](#0-0) 

It checks status, gas used, `write_set_hash` (`state_change_hash`) and `event_root_hash`, but explicitly and admittedly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the code even contains a `TODO(trading-native)` comment stating this in plain terms: [2](#0-1) 

This function is the *sole* correctness check used by two independent replay/verify tools that bypass the normal `DoStateCheckpoint`/`DoLedgerUpdate` pipeline (which does perform the checkpoint-hash comparison via `get_state_checkpoint_hashes`):

- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which executes blocks directly via `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` on the resulting outputs against the backup's authenticated `TransactionInfo`s: [3](#0-2) 

- `execution/executor/src/chunk_executor/mod.rs::verify_execution` (used by `--verify-execution` / bootstrapping verification), which likewise calls `ensure_match_transaction_info` directly on the freshly-executed outputs: [4](#0-3) 

By contrast, `DoStateCheckpoint::get_state_checkpoint_hashes`, which *does* validate the accumulated state/hot-state/position-state root against `known_state_checkpoints` derived from committed `TransactionInfo`s, is only invoked from the normal chunk-execution `update_ledger` path — not from either of the above two "verify" utilities: [5](#0-4) 

The per-transaction `write_set_hash` check in `ensure_match_transaction_info` only covers that single transaction's write set; it cannot detect divergence in the *accumulated* Jellyfish-Merkle-Tree state root (or hot-state / native-position roots), because those roots depend on the merged effect of many transactions and prior state, and are only committed at checkpoint boundaries via `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`.

### Impact Explanation
Both `db-tool replay-on-archive` (the tool operators/auditors use to confirm that re-executing archived history against a candidate node/VM version reproduces the authenticated chain state) and `ChunkExecutor::verify_execution` (used in verify-execution bootstrapping/state-sync modes) can report a fully successful, matching replay even when the locally computed accumulated state root (JMT root), hot-state root, or the newly added native-position state root diverges from what was actually committed and signed by validators. This defeats the entire purpose of these state-integrity verification tools: a bug in execution/state-application logic, a resource-group merge error, or a bad write-set-to-storage conversion that doesn't happen to also change any single transaction's write-set hash but does change the aggregate JMT root would be invisible to both tools, giving false confidence that historical state is correct. Given `COMPUTE_TRADING_NATIVE_STATE_ROOTS` binds an authenticated position-state root into `TransactionInfoV1.position_state_checkpoint_hash`, this gap is explicitly called out by the developers as unsafe to ship without fixing first.

### Likelihood Explanation
This is not a hypothetical: the gap is present in the current comparator code path used by both tools today, requires no attacker privilege, and is triggered by any silent state-computation bug (e.g., in write-set materialization, resource-group flattening, or a future native-position bug) that doesn't happen to alter any individual transaction's `write_set_hash`/`event_root_hash` but does alter the accumulated root. Given `state_checkpoint_hash` is only emitted at specific checkpoint transactions (block boundaries), most transactions never get any state-root check at all through this comparator.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding root information is available/recomputable in the caller context (mirroring what `DoStateCheckpoint::get_state_checkpoint_hashes` already does for the normal execution path), and update both `replay_on_archive.rs` and `ChunkExecutor::verify_execution` to supply/derive the checkpoint hashes needed for this comparison, so that any divergence in the authenticated state, hot-state, or position-state root is surfaced as a verification failure rather than silently passing.

### Proof of Concept
1. Take a chain segment where a checkpoint transaction's authenticated `TransactionInfo.state_checkpoint_hash` (or, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, `position_state_checkpoint_hash`) commits to root `R`.
2. Introduce (or trigger via a latent bug) a local execution/state-application discrepancy that produces the same per-transaction `write_set_hash`/`event_root_hash`/`gas_used`/`status` for every transaction, but yields an accumulated state root `R' != R` (e.g., a bug affecting resource-group flattening order that changes the final SMT/JMT leaf set without changing any single transaction's raw write set hash, or a native-position write mis-accounted across the checkpoint boundary).
3. Run `db-tool replay-on-archive` (or `ChunkExecutor::verify_execution` via `--verify-execution`) over this segment.
4. Observe that `ensure_match_transaction_info` returns `Ok(())` for every transaction because it never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so the tool reports the replay as fully verified despite the true state root diverging from the authenticated one.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
