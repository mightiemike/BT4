### Title
ERC-20 `balanceOf` and `totalSupply` Emulation Returns JSON-Encoded `U128` Instead of ABI-Encoded `uint256`, Breaking Ethereum Client Compatibility — (`runtime/near-wallet-contract/implementation/wallet-contract/src/eth_emulation.rs`)

---

### Summary

The wallet contract's ERC-20 emulation layer maps `balanceOf(address)` (selector `0x70a08231`) to a NEP-141 `ft_balance_of` call and `totalSupply()` (selector `0x18160ddd`) to `ft_total_supply`. Both NEP-141 functions return a JSON-encoded `U128` string (e.g., `"100000000000000000000000000"`). The `rlp_execute_callback` passes these raw bytes through as `success_value` with no ABI-encoding step. The ERC-20 standard requires both functions to return an ABI-encoded `uint256` (32 bytes, big-endian). Any standard Ethereum client (MetaMask, ethers.js, web3.js) that calls `balanceOf` or `totalSupply` through the wallet contract will receive JSON bytes it cannot decode as `uint256`, making those read paths permanently broken for all eth-implicit accounts.

---

### Finding Description

**Root cause — `eth_emulation.rs`**

`try_emulation` dispatches on the 4-byte selector and, for `ERC20_BALANCE_OF_SELECTOR`, constructs a `FunctionCall` action targeting `ft_balance_of`:

```rust
ERC20_BALANCE_OF_SELECTOR => {
    ...
    Ok((
        Action::FunctionCall {
            receiver_id: target.to_string(),
            method_name: "ft_balance_of".into(),   // returns JSON U128
            ...
        },
        ParsableEthEmulationKind::ERC20Balance,
    ))
}
```

`ft_balance_of` on any standard NEP-141 contract returns a JSON string such as `"100000000000000000000000000"` (UTF-8 bytes). The ERC-20 ABI requires `uint256` encoded as 32 big-endian bytes.

**Pass-through in `lib.rs` — `rlp_execute_callback`**

```rust
PromiseResult::Successful(value) => {
    ExecuteResponse { success: true, success_value: Some(value), error: None }
}
```

There is no ABI-encoding step between the raw NEP-141 return bytes and the `success_value` field. The JSON bytes are returned verbatim.

**Test confirms the mismatch**

The existing test in `tests/emulation.rs` parses the result as JSON `U128`, not as ABI-encoded `uint256`:

```rust
let balance: U128 = serde_json::from_slice(result.success_value.as_ref().unwrap())?;
```

This confirms the wallet contract is returning JSON, not ABI-encoded data.

**Same issue for `totalSupply` and `transfer`**

- `ERC20_TOTAL_SUPPLY_SELECTOR` → `ft_total_supply` → JSON `U128` returned, but ERC-20 expects ABI `uint256`.
- `ERC20_TRANSFER_SELECTOR` → `ft_transfer` → NEP-141 `ft_transfer` returns nothing (void); ERC-20 `transfer` must return ABI-encoded `bool true`. The wallet contract returns empty bytes.

---

### Impact Explanation

Any Ethereum client that calls `balanceOf` or `totalSupply` through the wallet contract's `rlp_execute` entry point will receive a `success_value` containing raw JSON bytes. Attempting to ABI-decode those bytes as `uint256` will fail. This makes the ERC-20 read interface permanently non-functional for all eth-implicit accounts, breaking the contract execution flow for every user who relies on standard Ethereum tooling to query token balances. For `transfer`, the missing `bool` return causes clients to misinterpret a successful transfer as a failed one, potentially triggering double-spend retries or incorrect balance accounting.

---

### Likelihood Explanation

The trigger is a normal, unprivileged `rlp_execute` call with an ERC-20 `balanceOf` selector — exactly the operation any Ethereum user would perform to check a token balance. No special permissions, validator access, or privileged role is required. The issue is deterministic and reproducible on every call.

---

### Recommendation

After the NEP-141 call succeeds, ABI-encode the return value before placing it in `success_value`. For `balanceOf` and `totalSupply`, parse the JSON `U128` string and re-encode it as `ethabi::Token::Uint(U256::from(value))`. For `transfer`, always return `ethabi::encode(&[ethabi::Token::Bool(true)])` on success. The `EthEmulationKind` variants (`ERC20Balance`, `ERC20TotalSupply`, `ERC20Transfer`) already carry enough type information to select the correct encoding in `rlp_execute_callback`.

---

### Proof of Concept

1. Deploy a standard NEP-141 token contract and mint tokens to an eth-implicit wallet account.
2. Construct an Ethereum transaction with `data = ERC20_BALANCE_OF_SELECTOR ++ abi_encode(wallet_address)` and submit it via `rlp_execute`.
3. Observe that `success_value` in the returned `ExecuteResponse` contains the UTF-8 bytes of a JSON string (e.g., `0x22313030303030303030303030303030303030303030303030303022`) rather than 32 ABI-encoded bytes.
4. Attempt `ethabi::decode(&[ParamType::Uint(256)], &success_value)` — it returns a decode error because the input is not 32 bytes of big-endian integer.
