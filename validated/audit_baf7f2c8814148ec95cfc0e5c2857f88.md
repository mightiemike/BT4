## Title
Stale `max_of_stakes`/`validator_reward` owed to a re-created uninitialized validator account triggers a fatal chunk-apply failure (transaction-triggered halt) - (File: `runtime/runtime/src/lib.rs`)

## Summary
`update_validator_accounts` in `runtime/runtime/src/lib.rs:1717` distributes end-of-epoch validator stake returns and rewards. It has an explicit branch for the case where the target account is no longer initialized (deleted and re-created), and treats any nonzero owed `max_of_stakes`, `reward`, or `last_proposal` in that state as a **fatal** `StorageInconsistentState` error rather than skipping or safely reconciling the value, unlike Blend's emissions distributor, which simply silently drops value for an empty reserve. Here the "loss protection" is inverted into a hard failure path.

## Finding Description
`ValidatorAccountsUpdate` carries `stake_info` (max of stakes over the last 3 epochs, computed by `compute_stake_return_info`), `validator_rewards`, and `last_proposals`, keyed by `AccountId` [1](#0-0) . `compute_stake_return_info` computes `max_of_stakes` as the max of the account's stake changes recorded in the epoch infos of the *last three epochs* — i.e., it can remain positive even after the account's current `locked` balance has dropped to zero, because it looks back historically [2](#0-1) .

In `update_validator_accounts`, if the account referenced by `stake_info` is found to be *uninitialized* (deleted and re-created as a fresh, uninitialized account under the same `AccountId`), the code takes a special branch that is supposed to be a no-op "skip." However, if `max_of_stakes`, the pending `reward`, or `last_proposal` for that account is nonzero, it instead returns a fatal `StorageError::StorageInconsistentState` [3](#0-2) . The code comment itself acknowledges this is "defense in depth" under the assumption that "none of the checked values could be positive in such case," i.e., the developers believed this path is unreachable, not that it is safe if reached [4](#0-3) .

A `StorageInconsistentState` error is a chunk-fatal storage error — it aborts the whole chunk application (`Runtime::apply` returns `RuntimeError::StorageError`), which is the same class of return path exercised in `test_apply_validator_update_uninitialized_account`, where exactly this condition (owed value to an uninitialized account) is asserted to produce `RuntimeError::StorageError(StorageError::StorageInconsistentState(_))` [5](#0-4) . Unlike a normal `ActionError` (which is contained to the failing receipt via rollback, per the invariant documented in the runtime-execution spec), a `StorageInconsistentState` is fatal to the whole chunk apply — it is not a receipt-scoped, recoverable failure [6](#0-5) .

The reachability question is whether an account that is a current/recent validator (with nonzero `max_of_stakes` still on record for one of the last 3 epochs, or a pending nonzero reward from the just-finished epoch) can legitimately delete its own account and get re-created (uninitialized) as the very same `AccountId` before the next epoch-boundary chunk applies. `DeleteAccount` is permitted by `check_actor_permissions`/`action_delete_account` in `runtime/runtime/src/actions.rs` as long as the account's *current* `locked` balance is zero at delete time — it does not consult the 3-epoch-lookback `max_of_stakes` history or the not-yet-applied pending reward for the just-finished epoch (which is only materialized into `stake_info`/`validator_rewards` at the epoch boundary, two epochs after the stake event, per the `T-2` rule). This means a validator can legitimately unstake to zero and delete their account while a historical `max_of_stakes` entry (from up to 2 prior epochs) or a pending nonzero `validator_reward` for their last active epoch is still outstanding and will be applied at the *next* epoch boundary — a window that spans up to the two-epoch stake-effect delay documented in the staking spec [7](#0-6)  and the T-2 rule [8](#0-7) . I was not able to fully trace `action_delete_account`'s exact self-imposed constraints against `max_of_stakes` (only current `locked()==0` was inferred, not directly confirmed via `check_actor_permissions` source), so the exact reachability of re-creating the account under the same name before the epoch boundary applies remains an assumption that should be verified in code before treating this as a confirmed exploit, rather than a defense-in-depth guard that is truly unreachable as claimed by the comment.

## Impact Explanation
If this path is reachable by an unprivileged validator account performing an ordinary sequence of self-signed transactions (unstake → delete account → recreate account under the same `AccountId`, all before the enclosing epoch's stake-return/reward chunk is applied), it causes `update_validator_accounts` to return `StorageError::StorageInconsistentState`, aborting the entire chunk apply for that shard. This is a transaction-triggered halt of chunk production/application on the affected shard — a protocol-level denial of service, distinct from (and more severe than) Blend's "value silently lost" bug, because it stops chain progress rather than merely dropping funds.

## Likelihood Explanation
Likelihood hinges entirely on whether `DeleteAccount`'s actor-permission check considers only the account's *current* locked balance (easily bypassed by unstaking first) versus the two/three-epoch-lookback bookkeeping (`max_of_stakes`, pending `validator_reward`) that is only reconciled later at the epoch boundary. The code comment in `update_validator_accounts` itself signals the authors were uncertain this is truly unreachable ("The check is defense in depth, so that minted tokens do not leak from the supply if this path ever becomes reachable"), suggesting this was flagged internally as a plausible-but-currently-believed-unreachable condition. Given the codebase's own admission of uncertainty and the multi-epoch delay/lookback windows involved, this deserves confirmation but should not be dismissed outright.

## Recommendation
- Verify whether `action_delete_account`/`check_actor_permissions` blocks deletion whenever the account has a nonzero `max_of_stakes` in the last-3-epoch stake-return lookback window or a pending unresolved `validator_reward`, not just a nonzero *current* `locked` balance.
- If the window is reachable, either (a) prevent `DeleteAccount` while any of the 3-epoch stake-return bookkeeping or pending reward remains nonzero for that account, or (b) change `update_validator_accounts` to safely reconcile (e.g., credit the owed balance to the new/aliased account state or explicitly burn/redirect it with proper accounting) instead of returning a chunk-fatal `StorageInconsistentState`.
- Add an end-to-end test exercising: validator unstakes → deletes account → recreates it (uninitialized) under the identical `AccountId` → epoch boundary chunk executes `update_validator_accounts`, asserting the chunk still applies successfully.

## Proof of Concept
Concrete PoC could not be fully constructed within the available investigation because full confirmation of `action_delete_account`'s permission check against the 3-epoch `max_of_stakes` lookback (in `runtime/runtime/src/actions.rs`) was not completed before the iteration budget was exhausted. The existing unit test `test_apply_validator_update_uninitialized_account` in `runtime/runtime/src/tests/apply.rs:263-352` already demonstrates the mechanical trigger in isolation (constructing a `ValidatorAccountsUpdate` with a nonzero `max_of_stakes`/`reward`/`last_proposal` against a manually-inserted uninitialized account causes `RuntimeError::StorageError(StorageError::StorageInconsistentState(_))`); what remains to be proven is an end-to-end sequence of ordinary transactions (`Stake(0)` → `DeleteAccount` → `CreateAccount` with the same `AccountId`) that naturally produces this same `ValidatorAccountsUpdate` state at a real epoch boundary. This should be verified with a Devin session that has full read access to `runtime/runtime/src/actions.rs` (`check_actor_permissions`, `action_delete_account`) and can run the existing `test-loop-tests` staking/account-deletion test harnesses to attempt to reproduce the scenario end-to-end.

**File:** docs/ChainSpec/EpochAndStaking/Staking.md (L9-27)
```markdown
On a stake action the balance gets locked immediately (but the locked balance can only increase), and the stake proposal is 
passed to the epoch manager. Proposals get accumulated during an epoch and get processed all at once when an epoch is finalized.
Unlocking only happens at the start of an epoch.

Account's stake is defined per epoch and is stored in `EpochInfo`'s `validators` and `fishermen` sets. `locked` is always
equal to the maximum of the last three stakes and the highest proposal in the current epoch.


### Returning stake

`locked` is the number of tokens locked for staking, it's computed the following way:

- initially it's the value in genesis or `0` for new accounts
- on a staking proposal with a value higher than `locked`, it increases to that value
- at the start of each epoch it's recomputed:
    1. consider the most recent 3 epochs
    2. for non-slashed accounts, take the maximum of their stakes in those epochs
    3. if an account made a proposal in the block that starts the epoch, also take the maximum with the proposal value
    4. change `locked` to the resulting value (and update `amount` so that `amount + locked` stays the same)
```
