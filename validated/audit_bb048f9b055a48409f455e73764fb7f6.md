### Title
`create_account_charge` anti-spam fee for implicit account creation is silently zeroed whenever the receipt's purchase price is not strictly above the block's burn price - ([File: runtime/runtime/src/lib.rs])

### Summary
The `AccountCostIncrease` protocol feature introduces `account_creation_charge` (mainnet `0.007 N`) specifically to make implicit-account creation non‑free and prevent spam. This fee is funded out of `burned_gas_refund`, which in turn is derived from `price_surplus` — a value that is only non‑zero when the *purchase* gas price exceeds the *burn* gas price. In the ordinary case where the network gas price is flat or rising between the time a transaction purchases gas and the time its receipt executes (the common case, since price only drops under sub‑50% utilization), `gas_burn_price == gas_purchase_price`, `price_surplus == 0`, `burned_gas_refund == 0`, and therefore `create_account_charge` is forced to `0` — the fee is not charged at all, even though the account was created.

### Finding Description
`refund_unspent_gas_and_deposits` computes the account-creation fee as: [1](#0-0) 

Key mechanics:
1. `gas_burn_price = min(gas_purchase_price, apply_state.gas_price)` under `AccountCostIncrease` — i.e. burn price can never exceed purchase price by construction. [2](#0-1) 
2. `price_surplus` is only positive when `gas_purchase_price > gas_burn_price`; otherwise it is `Balance::ZERO`. [3](#0-2) 
3. `burned_gas_refund` (the *only* funding source for `create_account_charge`) is set to `price_surplus` under `AccountCostIncrease`. [4](#0-3) 
4. The actual charge is capped at `min(amount_to_charge, burned_gas_refund)` — so whenever `burned_gas_refund == 0`, the account-creation fee that is supposed to be `desired_cost = config.account_creation_charge` collapses to `0`, regardless of how large `desired_cost` is. [5](#0-4) 

The code even documents the intended invariant with a `debug_assert!` that "as long as the purchase price is high enough, there should always be enough refund balance to cover the cost of creating an account" — but this is only a debug-mode assertion, not an enforced production invariant, and more importantly the premise itself ("purchase price high enough") is not what actually gates `burned_gas_refund`; what gates it is whether `gas_burn_price < gas_purchase_price`, i.e. whether the network gas price *dropped* between receipt creation and receipt application: [6](#0-5) 

`gas_purchase_price` is fixed at transaction/receipt conversion time as `max(current_gas_price, min_gas_purchase_price)` (documented in the economics spec), and `apply_state.gas_price` is the gas price of the block the receipt is actually executed in. Whenever the chain's gas price is stable or rising (which is the default/steady-state behavior — `next_gas_price` only decreases when block utilization is below 50%, per `compute_next_gas_price_checked`), `apply_state.gas_price >= gas_purchase_price`, so `gas_burn_price = gas_purchase_price`, `price_surplus = 0`, and the entire `account_creation_charge` fee is bypassed with zero attacker effort — this is simply the steady-state behavior of the protocol, reachable by any unprivileged sender who submits a transfer/transaction that implicitly creates a new account (e.g. `Transfer` to a not-yet-existing implicit account), which is the normal, unprivileged transaction path described in `action_transfer_or_implicit_account_creation`.

### Impact Explanation
`account_creation_charge` is the protocol's designed fee/deterrent against cheap/free implicit account creation (state bloat, spam). Because its funding path (`burned_gas_refund`/`price_surplus`) is gated on a gas-price *decrease* between receipt purchase and execution — an event that does not happen in the common (flat or rising gas price) case — the fee is effectively never collected in normal network conditions. This is a systemic fee bypass: every ordinary user creating an implicit account pays `0` of the intended `0.007 N` charge instead of the designed amount, undermining the anti-spam/economic purpose of the fee across the whole network, not through any attacker action but as the default code path. This matches the report's bug class ("protocol fee can be bypassed entirely") — here the bypass isn't via front-running an event, but via the fee's funding source being tied to a condition (price *decrease*) that essentially never holds when accounts are actually being created under normal/rising load.

### Likelihood Explanation
High likelihood of occurring in practice: gas price on NEAR mainnet is largely at (or near) its floor and moves only via the `ADJ_FEE`-bounded per-block feedback controller; a decrease requires sub-50% chunk utilization at the exact block(s) between receipt creation and receipt application. In any period of average-or-higher network load (the case where fees matter most, i.e., when spam/state-bloat concerns are highest), gas price does not drop, so `create_account_charge` collapses to zero for every implicit account creation during that window. No special crafting by the sender is required — it happens for ordinary `Transfer` actions that implicitly create accounts.

### Recommendation
Decouple `create_account_charge` funding from `price_surplus`. The fee should be charged directly against the sender/receipt balance (e.g., deducted from the unused-gas refund pool as a whole, or billed as an explicit charge on the receipt regardless of price movement) rather than being capped by an unrelated, rarely-nonzero quantity. At minimum, replace the `debug_assert!` invariants with enforced (non-debug) guarantees, and add an explicit code path/test that verifies `create_account_charge` is fully collected when `gas_burn_price == gas_purchase_price` (the common case), not only when price drops.

### Proof of Concept
1. Observe/ensure the network gas price is flat or has been rising (default steady state; e.g., utilization ≥ 50% over recent blocks, per `compute_next_gas_price_checked`).
2. As any unprivileged signer, submit a `Transfer` action to a not-yet-existing NEAR-implicit (or ETH-implicit) account, causing implicit account creation via `action_transfer_or_implicit_account_creation`.
3. When the resulting receipt is applied, `gas_purchase_price` (fixed at receipt conversion) will be `<= apply_state.gas_price` (the block's current price), so `gas_burn_price = min(gas_purchase_price, apply_state.gas_price) = gas_purchase_price`.
4. `price_surplus = gas_purchase_price - gas_burn_price = 0` → `burned_gas_refund = 0` → `amount_actually_charged = min(desired_cost, 0) = 0` in `refund_unspent_gas_and_deposits`. [1](#0-0) 
5. Inspect the outcome's `tokens_burnt`/refund receipt: no portion of `config.account_creation_charge` (0.007 N on mainnet) is deducted, confirming the fee was bypassed even though a new account was created.

Note: I was unable to find (within this pass) an explicit integration test in `test-loop-tests/src/tests/account_cost_increase.rs`/`account_cost_increase_diff.rs` that specifically exercises the "flat/rising gas price" scenario for account creation to confirm whether this has already been caught and mitigated elsewhere (e.g., some compensating charge applied outside `refund_unspent_gas_and_deposits`); this should be verified in a full Devin session with test-execution access before treating this as fully confirmed.

            // We would like to charge as much as needed to reach desired_cost
