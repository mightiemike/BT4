### Title
Fund-migration signing amount derived from attacker-griefable live balance causes signing-hash mismatch and stalls TSS fund migration - (File: universalClient/chains/evm/tx_builder.go, universalClient/tss/coordinator/coordinator.go, universalClient/tss/sessionmanager/sessionmanager.go)

### Summary
`GetFundMigrationSigningRequest` computes the migration transfer amount (`maxTransfer = balance - gas - L1fee`) from a **live, freshly-queried** native-token balance of the old TSS address when no `Balance`/`claimedAmount` is supplied [1](#0-0) . The coordinator uses this path when first building the setup message [2](#0-1) , and — critically — each individual signing participant *independently re-queries the live balance again* in `verifyFundMigrationSigningRequest` to reconstruct and compare the signing hash [3](#0-2) . If the balance changes between these two independent RPC reads, the hashes diverge and the signing request is hard-rejected.

### Finding Description
The old TSS address is deterministically derivable from the public `OldTssPubkey` published in the `FundMigrationInitiated` event data [4](#0-3) . Sending native tokens to any address on an EVM chain requires no authorization or privileged access — it is the same class of unprivileged action as the original MAOR-1 report, where anyone could deposit into a validator's public key without re-activating it. Here, an attacker can send a trivial-value transaction to the (public) old TSS address at any time after a `FundMigration` is initiated. Because outbound is disabled and there is a delay between the coordinator's initial balance snapshot (used to build the DKLS setup message / signing hash) and each participant's independent balance re-query during verification, the attacker only needs to land one deposit inside that window to desynchronize the computed `maxTransfer`/signing hash across validators.

This mirrors the oracle bug's root cause exactly: a consensus-relevant, cumulative/committed value (`num validators withdrawn` there; `TSSFundMigrationAmount`/signing hash here) is derived from an externally-observable balance that any unprivileged party can mutate at will, rather than from an authenticated, chain-committed record insulated from attacker interference (e.g., a value fixed and voted on once, or bound to a specific block height agreed by all participants).

### Impact Explanation
Every honest participant computing a different signing hash means:
- The signing session for that fund migration event repeatedly fails verification (`"fund migration signing hash mismatch: our computed hash does not match coordinator's hash"`), preventing DKLS threshold signing from completing [5](#0-4) .
- Since the attacker can repeat this on every retry indefinitely and cheaply (dust-value transactions), fund migration for that (old key, chain) pair can be denied liveness — a persistent, unprivileged, non-network-level DoS of a core protocol function (migrating funds off a rotated/retiring TSS key).
- This falls squarely within the allowed "denial of service…reachable without privileged control" scope, since it requires only an ordinary unprivileged transaction/deposit, no malicious validator or node assumption.

### Likelihood Explanation
High likelihood: the old TSS address is public (embedded in on-chain event data), the attack costs only a dust-value native-token transfer, requires no special timing precision beyond "before verification completes," and can be repeated indefinitely to keep blocking migration completion for as long as the attacker wishes.

### Recommendation
Do not let each participant independently re-query a live, attacker-mutable balance for hash reconstruction. Instead:
- Snapshot the balance once (e.g., at a specific, block-height-pinned read agreed via the coordinator's setup message) and have all participants use that pinned value/height rather than re-querying "now," or
- Have the coordinator's initially-computed `TSSFundMigrationAmount` carried in the setup/ACK payload be treated as the single source of truth (already partially done via `claimedAmount` in the ACK-verify path), and apply this same pinned-amount approach consistently to the primary `verifyFundMigrationSigningRequest` path instead of a second live `GetBalance` call.

### Proof of Concept
1. Admin initiates a `FundMigration` for `oldKeyId` on chain X; `FundMigrationInitiatedEventData.OldTssPubkey` is emitted publicly.
2. Attacker derives `oldTSSAddr` (same derivation the protocol uses) and sends a minimal native-token transfer to it.
3. Coordinator calls `createFundMigrationSignSetup` → `buildFundMigrationTransaction` → `GetFundMigrationSigningRequest`, snapshotting balance B1, producing signing hash H1 and `TSSFundMigrationAmount` A1 [6](#0-5) .
4. Attacker sends another dust transfer to `oldTSSAddr` before the next verification round.
5. A participant's `verifyFundMigrationSigningRequest` re-queries the balance (now B2 ≠ B1), computes H2 ≠ H1, and rejects with "fund migration signing hash mismatch" [7](#0-6) .
6. Repeating step 4 on every retry keeps the migration from ever finalizing signing, denying the fund-migration function indefinitely at negligible attacker cost.
