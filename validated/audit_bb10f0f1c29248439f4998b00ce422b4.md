### Title
Unbounded per-cycle reward computation loop can DoS the reward-withdrawal transaction path - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.getOldReward()` iterates once per unclaimed cycle (`for (long cycle = begin; cycle < end; cycle++) { reward += computeReward(cycle, votes); }`), and each iteration internally loops over the caller's full vote list doing store lookups. This mirrors the Biconomy `LiquidityFarming.getUpdatedAccTokenPerShare()` bug class: a loop whose length is proportional to elapsed/unclaimed history rather than a bounded constant, invoked from an ordinary, unprivileged transaction (`WithdrawBalanceContract`, `UnfreezeBalanceContract`, or TVM `withdrawReward`/vote-precompile calls).

### Finding Description
`MortgageService.withdrawReward()`/`queryReward()` compute the reward owed to an account between `beginCycle` (last time the account's reward was settled) and `currentCycle` [1](#0-0) . This delegates to `computeReward(beginCycle, endCycle, accountCapsule)`, which for the portion of the range before `newRewardAlgorithmEffectiveCycle` calls `getOldReward()` [2](#0-1) .

`getOldReward()` either delegates to the precomputed `rewardViCalService` (O(1) per vote using an accumulator, analogous to the report's recommended fix) **or**, when `allowOldRewardOpt()` is not enabled, falls back to a manual per-cycle loop:
```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
  if (dynamicPropertiesStore.allowOldRewardOpt()) {
    return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
  }
  long reward = 0;
  for (long cycle = begin; cycle < end; cycle++) {
    reward += computeReward(cycle, votes);
  }
  return reward;
}
``` [3](#0-2) 

Each iteration of this loop calls `computeReward(cycle, votes)`, which itself loops over every vote the account has cast and performs two store reads (`getReward`, `getWitnessVote`) per vote [4](#0-3) . The total work is therefore `O((end - begin) * votes.size())`. `begin` is the account's stored `beginCycle`, which only advances when the account calls withdraw/unfreeze/vote-related actuators. An account that never triggers a settlement keeps `beginCycle` frozen while `currentCycle`/`newRewardAlgorithmEffectiveCycle` keep advancing every maintenance cycle (~every few hours) — exactly the "liquidityProviders are inactive" precondition in the original report, except here the growth driver is elapsed chain cycles rather than admin-driven rate updates.

This code path is reachable directly from unprivileged users:
- `WithdrawBalanceActuator.execute()` calls `mortgageService.withdrawReward(...)` [5](#0-4) .
- `UnfreezeBalanceActuator.execute()` also calls `mortgageService.withdrawReward(ownerAddress)` before unfreezing [6](#0-5) .
- The TVM-facing `VoteRewardUtil`/`WithdrawRewardProcessor` path exposes an analogous (though currently Vi-accumulator based, not per-cycle) reward settlement reachable from contract calls [7](#0-6) .

Whether this loop is actually exercised in production depends on the `allowOldRewardOpt` committee-controlled dynamic parameter; when disabled (its historical/default state before the migration was fully rolled out), any account whose `beginCycle` predates the current cycle by many cycles will trigger the unbounded loop the moment it calls a common, unprivileged operation like withdraw/unfreeze. I could not fully confirm the current on-chain default value of `allowOldRewardOpt` in this pass (index truncated before that line of `DynamicPropertiesStore.java` was retrieved), so likelihood of this specific code path currently executing on mainnet is uncertain and should be verified against the live parameter value/committee proposal history.

### Impact Explanation
If triggered, the loop performs a store read/computation whose cost scales with the number of never-settled cycles times the number of votes cast, which can run into tens of thousands of iterations for a long-idle voter (Tron cycles occur roughly every few hours; años of inactivity → thousands of cycles). This can exhaust the transaction's energy/time budget (`OutOfEnergyException`/`OutOfTimeException`, as demonstrated by the endless-loop energy test in the codebase) and cause the withdraw/unfreeze transaction to permanently fail, freezing the user's unclaimed rewards and blocking further account actions (e.g., unfreeze) that also invoke `withdrawReward` as a prerequisite step.

### Likelihood Explanation
Likelihood is moderate and conditional: it requires (a) the `allowOldRewardOpt` optimization to be disabled for the relevant cycle range, and (b) an account that voted long ago and never withdrew/unfroze since, letting `beginCycle` fall far behind `currentCycle`/`newRewardAlgorithmEffectiveCycle`. No attacker privilege is required — any long-term inactive voter can self-trigger this by simply calling withdraw/unfreeze once, and an attacker could also grief a victim indirectly by ensuring the victim's account accumulates a large unclaimed-cycle backlog (this happens naturally over time without any special action).

### Recommendation
- Ensure `allowOldRewardOpt` (the Vi-accumulator, O(1)-per-vote precomputation path) is permanently enabled and that the legacy per-cycle loop in `getOldReward()` cannot be reached, or remove the legacy branch entirely now that the migration is presumably complete.
- If the legacy path must remain for historical compatibility, cap the number of cycles processed per transaction (e.g., require multiple `withdrawReward` calls to catch up incrementally) rather than looping over the entire backlog in one transaction.
- Add a regression test asserting that `withdrawReward`/`queryReward` complete within bounded cost regardless of how many cycles have elapsed since `beginCycle`.

### Proof of Concept
1. Set `allowOldRewardOpt` to false (or find a network/cycle range where it is not yet enabled) and vote for one or more witnesses so `beginCycle` is recorded.
2. Advance the chain through many maintenance cycles (each cycle ~ a few hours in production, but arbitrarily fast in a test harness) without calling withdraw/unfreeze — analogous to the existing `VoteTest.testRewardAlgorithmBenchmark` benchmark test that iterates `payRewardAndDoMaintenance(72999)` cycles and measures the cost of the old vs. new reward query [8](#0-7) .
3. Call `WithdrawBalanceContract` (or `UnfreezeBalanceContract`) for that account; observe that `mortgageService.withdrawReward()` executes `getOldReward()`'s per-cycle loop, with cost proportional to the accumulated cycle backlog, and can exceed feasible energy/time budgets for large backlogs.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
