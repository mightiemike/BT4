### Title
Inconsistent uncaught NonUniqueObjectException in HTTP GetAssetIssueByNameServlet vs. caught-and-nulled in gRPC WalletApi/WalletSolidityApi produces divergent error responses for identical duplicate-name asset input - ([File: GetAssetIssueByNameServlet.java])

### Summary
When `AllowSameTokenName==1` and two assets share the same `name`, `Wallet.getAssetIssueByName` throws `NonUniqueObjectException` from its filter-based lookup. `GetAssetIssueByNameServlet.doGet/doPost` calls `wallet.getAssetIssueByName(...)` directly and only wraps it in a generic `catch (Exception e) { Util.processError(e, response); }`, while the gRPC `WalletApi.getAssetIssueByName` in `RpcApiService.java` explicitly catches `NonUniqueObjectException` and returns `null` to the client instead of propagating an error. This produces different observable behavior (HTTP error response vs. gRPC null/empty response) for the same underlying condition across the two API surfaces.

### Finding Description
`Wallet.getAssetIssueByName(ByteString assetName)` declares `throws NonUniqueObjectException` and throws it when more than one asset shares the queried `name` under `AllowSameTokenName==1`, via the `filter(assetIssueCapsule -> assetIssueCapsule.getName().equals(assetName))` count check [1](#0-0) .

`GetAssetIssueByNameServlet.doGet` and `.doPost` call `fillResponse`, which calls `wallet.getAssetIssueByName(address)` and only handle the resulting exception via the generic `catch (Exception e) { Util.processError(e, response); }` block, meaning the `NonUniqueObjectException` propagates as a generic processed error rather than being explicitly handled [2](#0-1) .

By contrast, `RpcApiService`'s `WalletApi.getAssetIssueByName` gRPC handler explicitly catches `NonUniqueObjectException` and calls `responseObserver.onNext(null)` instead of surfacing an error to the client [3](#0-2) .

This is a genuine input-driven behavioral difference: an unprivileged attacker/user can issue two assets with the same `name` (permitted once `AllowSameTokenName==1`, which is a chain-wide dynamic property, not attacker-controlled but reachable in practice on any chain running with that setting), then query `getAssetIssueByName` for that name via HTTP vs. gRPC and observe different responses (an HTTP error payload from `Util.processError` vs. an empty/null gRPC response).

### Impact Explanation
The impact is limited to **response/behavior inconsistency across API surfaces (HTTP vs gRPC vs Solidity-node)**, not fund loss, unauthorized execution, or consensus divergence — the underlying chain state is unaffected. It is an information/DoS-adjacent nuisance: HTTP clients see an error response for a legitimate query, while gRPC clients silently receive `null`, which can confuse downstream tooling and API consumers, and could be used to fingerprint/distinguish node API implementations or trigger unexpected error-handling paths in dependent client code.

### Likelihood Explanation
This requires `AllowSameTokenName==1` (a network-wide dynamic property enabled by chain governance, not by an individual attacker) and two assets already existing with an identical `name` field, which is a legitimate state achievable by any account issuing assets under that mode. Given those preconditions, triggering the divergence is trivial and fully repeatable via a simple read-only query — no privileged access needed once the precondition state exists.

### Recommendation
Make the HTTP servlet explicitly catch `NonUniqueObjectException` from `wallet.getAssetIssueByName` and return a well-defined error (or empty `{}`), consistent with the gRPC path's behavior of swallowing it and returning null/empty — or, conversely, propagate a structured error consistently in both the HTTP and gRPC/Solidity paths so behavior is uniform across surfaces.
