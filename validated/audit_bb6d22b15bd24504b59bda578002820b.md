Based on my investigation, I found a concrete analog of the report's bug class in the NEAR Wallet Contract.

### Title
Wallet Contract pays relayer fee for ERC-20/base-token transfer emulation unconditionally, regardless of whether the underlying transfer action actually succeeds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Sherlock finding describes a root cause pattern: a contract commits to a value-moving action based on a *declared/nominal* amount instead of the amount actually confirmed to have moved, decoupling the accounting from the real outcome. The closest reachable analog in nearcore is in the NEAR Wallet Contract's `inner_rlp_execute`, which fires the relayer-fee refund `Transfer` promise **before** the underlying user-requested action (base-token transfer or NEP-141 `ft_transfer`) has been attempted or resolved, and does so as an independent, unlinked promise.

### Finding Description
`inner_rlp_execute` parses an Ethereum-formatted transaction into a NEAR `Action`/`TransactionKind`. For `EOABaseTokenTransfer` and `ERC20Transfer` kinds carrying a non-zero relayer `fee`, the code immediately creates a standalone promise batch that transfers the fee to the predecessor (the relayer): [1](#0-0) 
This fee-payment promise is not chained to (`.then(...)`) the promise that actually performs the requested transfer/`ft_transfer`. The main action promise is built and returned separately afterward: [2](#0-1) 
Failure handling for the *main* action only refunds `caller_deposit` (the attached deposit for the underlying call), not the relayer fee, in `rlp_execute_callback`: [3](#0-2) 
This mirrors the audited pattern: the contract acts on the *declared* value (the `fee` field parsed from the signed transaction) rather than tying the payout to confirmation that the value-bearing action (e.g., the NEP-141 `ft_transfer`, which can fail for many reasons — insufficient balance, non-standard token behavior, `storage_deposit` insufficiency for tokens with higher-than-hardcoded `storage_balance_bounds`, see `NEP_141_STORAGE_DEPOSIT_AMOUNT`) actually completed.

### Impact Explanation
If the underlying `ft_transfer`/base transfer fails (e.g., the target NEP-141 contract requires more than the hardcoded `NEP_141_STORAGE_DEPOSIT_AMOUNT` for `storage_deposit`, or the token balance is insufficient, or the token contract's `ft_transfer` panics for other reasons), the relayer is still unconditionally paid its full quoted `fee` from the wallet contract's own NEAR balance, even though the user's intended transfer never happened. This is a concrete value-movement bug: NEAR tokens leave the wallet-contract account (paid to whichever address is `predecessor_account_id`, i.e., whoever calls `rlp_execute`) without a successful corresponding user action, which any third party relaying a doomed transaction to a target that reliably fails could exploit repeatedly to drain small amounts of NEAR from wallet-contract accounts. Because `has_in_flight_tx` only blocks one transaction at a time (not repeated submission over time by any relayer), and a faulty/malicious relayer is only banned when the *signer itself* submits and detects certain relayer errors (`Error::Relayer`) — not for general action failures — the fee-drain path is not gated by the ban mechanism.

### Likelihood Explanation
Reachable by any unprivileged account acting as a "relayer" for a Wallet Contract instance: it only needs to submit a validly signed (by the wallet owner or via access key) Ethereum-formatted transaction with `to` pointing at a NEP-141 contract or another wallet, encoding an ERC-20 `transfer` with a nonzero gas price (relayer fee), where the target action is engineered/known to fail (e.g., unregistered/rejecting receiver with a non-standard storage bound, or insufficient token balance). No special privilege beyond being the transaction's `predecessor_account_id` calling `rlp_execute` is required. This is directly reachable through the "NEAR wallet contract" scope explicitly listed as in-scope.

### Recommendation
Chain the relayer-fee transfer to occur only after the main action promise succeeds (e.g., attach it as part of the same promise chain via `.then()`, executed conditionally on `PromiseResult::Successful`), or refund/claw back the fee alongside the `caller_deposit` refund path in `rlp_execute_callback` when the underlying promise fails. This ties the relayer's payment to a confirmed, successful state transition rather than the nominal `fee` value parsed at the start of transaction handling.

### Proof of Concept
1. Deploy/observe an existing NEAR Wallet Contract instance owned by a victim (`wallet.near`) with a NEAR balance.
2. Victim signs an Ethereum-formatted ERC-20 `transfer` calldata (selector `ERC20_TRANSFER_SELECTOR`) targeting a NEP-141 token contract, with `to` = some receiver, `value` = some amount, and `gas_price` set such that the derived relayer `fee` is nonzero (per `ParsableEthEmulationKind::ERC20Transfer { fee, .. }` derivation in `eth_emulation.rs`).
3. An attacker acting as relayer calls `rlp_execute(target=<token_contract>, tx_bytes_b64=<signed tx>)` from their own account (`predecessor_account_id` = attacker), where the NEP-141 token contract is chosen/known to fail the subsequent `ft_transfer`/`storage_deposit` (e.g., a token with `storage_balance_bounds` far exceeding the hardcoded `NEP_141_STORAGE_DEPOSIT_AMOUNT`, causing insufficient attached deposit and a chained-call failure) — see `nep_141_storage_balance_callback` at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:239-269`.
4. `inner_rlp_execute` immediately executes `env::promise_batch_action_transfer(refund_promise, *fee)` to the attacker's account (lines 381-384), independent of the outcome of the later `ft_transfer` chain.
5. The later promise chain fails; `rlp_execute_callback` only refunds `caller_deposit`, not the fee already paid to the attacker.
6. Net effect: attacker collects `fee` in NEAR from the wallet contract with no successful token transfer having occurred, repeatable across multiple relayed transactions (bounded only by nonce increments and `has_in_flight_tx` serialization, not by success/failure of the requested action).
