### Title
Signer global-state agreement threshold uses floor rounding while block-approval threshold uses ceiling rounding, causing signer subsets to diverge on tx-replay-set / active-miner state - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
The codebase has two independently-implemented "70% weight threshold" calculations that are supposed to express the same Nakamoto signer-approval quorum: `NakamotoBlockHeader::compute_voting_weight_threshold` (the canonical, consensus-critical function used for actual block-signature quorum) and `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` (a reimplementation used by the signer's global state machine to agree on the active miner, protocol version, and transaction-replay set). Like the `BeamBalanceStore` reimplementation of `approve`/`allowance` instead of reusing the audited base implementation, this is an unnecessary duplicate implementation of the same weight-threshold arithmetic, and the two implementations round differently.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` computes the minimum weight needed for block approval by **rounding up**: [1](#0-0) 

`GlobalStateEvaluator::reached_agreement` (and its inverse `reached_disagreement`) reimplements the same 70%/30% threshold logic independently, but with plain integer division (floor), not the ceiling used by `compute_voting_weight_threshold`: [2](#0-1) 

For a `total_weight` where `total_weight * 7` is not a multiple of 10 (e.g. `total_weight = 13`), `compute_voting_weight_threshold` returns `ceil(13*7/10) = 10`, while `reached_agreement` accepts agreement at `vote_weight >= floor(13*7/10) = 9`. The two functions are meant to encode the identical Nakamoto signer super-majority rule (`NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`, i.e. 70%), but because the global-state evaluator was written as a separate reimplementation rather than delegating to the canonical function, it silently uses a *lower* effective threshold than the one enforced for actual block-signature verification in `NakamotoBlockHeader::verify_signer_signatures`: [3](#0-2) 

`GlobalStateEvaluator::determine_global_state`/`determine_latest_supported_signer_protocol_version`/`determine_global_burn_view` all gate on `reached_agreement`, and this evaluator is instantiated per-node from the reward set's signer weights inside `StackerDBListener::new`: [4](#0-3) 

Because `reached_agreement`'s floor-rounded threshold is off by up to one weight-unit relative to the ceiling-rounded canonical threshold, there exist total-weight values (any total weight where `total_weight*7 mod 10 != 0`) for which the exact minority weight bracket `[floor_threshold, ceil_threshold)` is enough to make the global-state evaluator declare "agreement reached" on a given active-miner/tx-replay-set view while the same weight would be insufficient to satisfy the canonical block-approval quorum used elsewhere in the same signer for actual block signature counting (`compute_voting_weight_threshold`, used directly in `handle_block_pre_commit` and `store_and_process_block_signature`): [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a minority-triggerable equality break between two supposedly-identical threshold definitions within the same signer binary/network. A signer set whose combined weight falls in the one-unit gap between the floor and ceiling of `total_weight*7/10` can cause the `GlobalStateEvaluator` to "lock in" a tx-replay-set / active-miner view or protocol version that a strict reading of the canonical Nakamoto quorum rule would not yet support. Since `get_global_tx_replay_set`/`determine_global_state` feed into which transactions signers believe must be replayed and which miner is considered active, this can cause one subset of signers (those whose local tally crosses the floor threshold first) to diverge from another subset still waiting for the ceiling threshold, producing a temporary block-validation/tip disagreement across signers — the "High" impact category of a minority-triggerable divergence in validation verdict bounded to a temporary tip disagreement.

### Likelihood Explanation
The discrepancy is deterministic arithmetic (floor vs. ceiling division) and triggers on the great majority of `total_weight` values not evenly divisible in the required way — it does not require an attacker at all, just an unprivileged/organic signer-weight distribution that lands in the rounding gap, and no majority collusion is needed since the divergence is purely a function of `total_weight`.

### Recommendation
Replace `GlobalStateEvaluator::reached_agreement`/`reached_disagreement`'s independent threshold arithmetic with a direct call to (or a shared helper matching) `NakamotoBlockHeader::compute_voting_weight_threshold`, so there is a single canonical, consistently-rounded definition of the 70% quorum used everywhere weight thresholds are evaluated (block signature quorum, global state agreement, blocking-minority rejection), eliminating the reimplementation and its rounding drift.

### Proof of Concept
1. Construct a reward set with a `total_weight` such that `total_weight * 7 % 10 != 0` and `total_weight * 3 % 10 != 0` (e.g. `total_weight = 13`).
   - `NakamotoBlockHeader::compute_voting_weight_threshold(13)` → `ceil(91/10) = 10`.
   - `GlobalStateEvaluator::reached_agreement` with `total_weight = 13` accepts `vote_weight = 9` as sufficient (`floor(91/10) = 9`).
2. Have signers whose aggregate weight for a particular `(burn_block, current_miner, protocol_version)` view sums to exactly `9` out of `13`.
3. `GlobalStateEvaluator::determine_global_state` (called via `get_global_tx_replay_set`/`determine_latest_supported_signer_protocol_version`) returns this view as "agreed," while the same 9/13 weight would be rejected by `NakamotoBlockHeader::compute_voting_weight_threshold`-gated logic (`min_weight > commit_weight` checks in `handle_block_pre_commit`/`store_and_process_block_signature`), producing inconsistent state resolution between the global-state subsystem and the block-approval subsystem within the same or across different signers.

Note: I was unable to fully trace every downstream consumer of `determine_global_state`/`get_global_tx_replay_set` (e.g., in `stacks-signer/src/v0/signer_state.rs` and `chainstate/v2.rs`) within the available iterations to confirm the complete propagation path into a concrete on-chain validation verdict; the analysis above is based on the confirmed divergent threshold arithmetic and its confirmed use sites in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` and `stacks-signer/src/v0/signer.rs`.

    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    /// Check if the supplied vote weight crosses the global agreement threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_agreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

    /// Check if the supplied vote weight crosses the blocking minority threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }
