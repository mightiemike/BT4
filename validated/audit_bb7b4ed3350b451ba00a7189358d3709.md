### Title
Silent (unchecked) balance underflow in `ExchangeCapsule.transaction()` legacy path corrupts pool accounting instead of reverting - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The Astaria `PublicVault.processEpoch()` bug is caused by subtracting a freshly-computed, potentially stale/rounding-affected value from a running balance (`yIntercept`) without validating that the subtrahend cannot exceed the minuend, leading to an underflow that reverts and bricks the epoch. java-tron's on-chain TRX/TRC10 bonding-curve Exchange (`ExchangeCapsule.transaction`) has the same root-cause pattern in its **default (legacy) execution path**: it computes a derived trade output via a floating-point Bancor-relay formula and then subtracts it from a stored pool balance using plain `long` arithmetic, with no check that the result stays non‑negative.

### Finding Description
`ExchangeCapsule.transaction()` supports two calculation modes selected by the governance-controlled flag `AllowHardenExchangeCalculation`: [1](#0-0) 

When `hardenedCalc` is `false` (the legacy/default behavior for any exchange still using `ExchangeProcessor`), `buyTokenQuant` is computed with double-precision `Math.pow` arithmetic in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`: [2](#0-1) 

and the resulting `newFirstTokenBalance`/`newSecondTokenBalance` are computed with unchecked `long` subtraction (`secondTokenBalance - buyTokenQuant` / `firstTokenBalance - buyTokenQuant`) — unlike Solidity, Java `long` subtraction does **not** revert on underflow, it silently wraps/produces a negative value. The negative-balance guard only exists in the hardened branch: [3](#0-2) 

This is reachable by any unprivileged account via `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(...)` and then persists the (possibly corrupted) `ExchangeCapsule` back to `ExchangeStore`/`ExchangeV2Store` without any post-condition check on the new balances: [4](#0-3) 

`doValidate()` only checks slippage (`tokenExpected`), account balance/asset sufficiency, and pool balance ceilings — it never re-verifies that the post-trade pool balances remain non-negative in the non-hardened path: [5](#0-4) 

The developers themselves have already acknowledged this exact bug class — the repository's own test suite explicitly documents and exercises "hardened mode" fixes for `subtractExact` overflow/underflow in the exchange code path (`ExchangeCapsuleTest.testHardenedTransactionNegativeBalanceThrows`, `ExchangeTransactionActuatorTest`/`ExchangeWithdrawActuatorTest` hardened-mode tests), confirming that unguarded subtraction of a computed trade amount from a stored balance is a known, real vulnerability class in this codebase: [6](#0-5) [7](#0-6) 

### Impact Explanation
Unlike the Astaria case where the underflow simply reverts (causing a temporary DoS on `processEpoch()`), in java-tron's legacy exchange path the underflow does **not** revert — it silently writes a negative `firstTokenBalance`/`secondTokenBalance` into the persisted `ExchangeCapsule`. This is a state-accounting corruption: subsequent trades against the same exchange pair operate on a corrupted invariant (negative reserve), which can produce economically nonsensical outputs (e.g., minting disproportionate `anotherTokenQuant` on later trades), enabling drainage of the counter-asset reserve or permanent divergence of the pool's on-chain accounting from its true value. This is a concrete accounting/invalid-state impact reachable by any unprivileged user issuing an `ExchangeTransactionContract` (or `ExchangeWithdrawContract`, which reuses the same `transaction()`/balance-subtraction pattern) — no privileged role is required.

### Likelihood Explanation
Triggering requires the legacy (non-hardened) calculation path, which is default unless the `AllowHardenExchangeCalculation` chain parameter has been activated via committee proposal. The Bancor-relay double-precision math (`Math.pow`) is known to accumulate rounding error especially near pool-balance extremes (very small `buyTokenBalance` relative to `sellTokenQuant`, or many successive trades), which is exactly the scenario that motivated the project's own "hardened" rewrite and negative-balance guard. Because on-chain TRC10 Exchange pairs are created and traded permissionlessly, and no additional caller privilege is needed, likelihood is non-trivial for any live exchange pair still relying on the legacy path — but exploitation depends on whether `AllowHardenExchangeCalculation` has been activated network-wide, which could not be confirmed from the indexed code (I could not locate the deployed on-chain proposal state / mainnet activation status).

### Recommendation
Apply the underflow/negative-balance guard unconditionally, not only when `hardenedCalc` is `true`: always compute new balances with checked arithmetic (`Math.subtractExact`/`addExact`) and reject the transaction (throw `ContractValidateException`) if either resulting balance would go negative, mirroring the existing hardened-mode check in `ExchangeCapsule.transaction()` lines 160–162. Equivalent to the Astaria fix recommendation ("call `accrue()` before subtracting"), ensure the pre-trade invariant (available reserve ≥ computed trade output) is validated in `doValidate()` before `execute()` mutates state, for both `ExchangeTransactionActuator` and `ExchangeWithdrawActuator`.

### Proof of Concept
1. Create a TRC10↔TRX (or TRC10↔TRC10) exchange pair with a very small `secondTokenBalance` relative to `firstTokenBalance` via `ExchangeCreateActuator`.
2. Ensure `AllowHardenExchangeCalculation == 0` (default/legacy path).
3. Submit an `ExchangeTransactionContract` selling a `sellTokenQuant` sized so that the double-precision Bancor formula in `ExchangeProcessor.exchangeFromSupply` (`chainbase/.../ExchangeProcessor.java:31-39`) returns a `buyTokenQuant` that rounds up to exceed the true available `buyTokenBalance` due to floating-point error.
4. `ExchangeCapsule.transaction()` computes `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (or `newFirstTokenBalance` for the reverse direction) using plain `long` subtraction — no exception is thrown, and a negative balance is persisted via `Commons.putExchangeCapsule(...)` in `ExchangeTransactionActuator.execute()`.
5. Subsequent trades against the same exchange pair now operate on a corrupted (negative) reserve, producing incorrect outputs and enabling extraction of value beyond the pool's actual holdings — an accounting/invalid-state impact directly analogous to, but more severe than, the referenced Astaria underflow (silent corruption instead of revert-based DoS).

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public void testHardenedTransactionNegativeBalanceThrows() throws Exception {
    // Construct a corrupt-state pool with a negative balance to drive the
    // < 0 invariant in the hardened branch via subtractExact wrapping.
    ExchangeCapsule capsule = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 99L, 0L,
        "abc".getBytes(), "def".getBytes());
    capsule.setBalance(Long.MAX_VALUE, 1L);

    // Selling abc adds to firstTokenBalance: addExact(MAX, q) overflows -> ArithmeticException
    Assert.assertThrows(ArithmeticException.class,
