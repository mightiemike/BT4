### Title
Signer weight "global agreement" threshold uses floor rounding while block-approval threshold uses ceiling, letting a sub-70% minority satisfy global state consensus - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The Stacks signer network computes the same 70% supermajority constant (`NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`) with two different rounding rules in two different places: `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs` uses integer-truncating (floor) division, while `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs` (used verbatim as the consensus-critical block-signature `weight_threshold` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) rounds the same fraction up (ceiling). This mirrors the Rubicon `mulDivUp`/`mulDivDown` inconsistency: the same nominal "70%" boundary is computed with two different rounding directions in two components that are supposed to agree.

### Finding Description
`GlobalStateEvaluator::reached_agreement` is: [1](#0-0) 

```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}

pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```

This computes `floor(total_weight * 7 / 10)` and requires `vote_weight >= floor`. It is the sole threshold check used by `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and `determine_global_state` [2](#0-1) , which are the functions signer nodes use to decide the network-wide agreed `current_miner`, `burn_block_view`, `tx_replay_set`, and protocol version (surfaced to the miner coordinator via `StackerDBListenerComms::get_signer_global_state`) [3](#0-2) .

By contrast, the consensus-critical threshold used to actually validate/approve a Nakamoto block's signer signatures is: [4](#0-3) 

```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil).map_err(...)
}
```

This computes `ceil(total_weight * 7 / 10)` and is the value assigned to `weight_threshold` that gates actual block signature approval in the node's coordinator loop: [5](#0-4) 

```rust
let total_weight = reward_set.total_signing_weight().map_err(...)?;
let weight_threshold = NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)?;
```

For any `total_weight` where `total_weight * 7` is not a multiple of 10 (e.g. `total_weight = 11` → `floor = 7`, `ceil = 8`), the two thresholds differ by exactly one unit of weight. A coalition holding exactly `floor(total_weight*7/10)` weight — genuinely *below* the intended 70% supermajority and below the weight required to get a block signed — is nonetheless sufficient to make `reached_agreement` return `true`. Because `determine_global_state`/`determine_global_burn_view` use only `reached_agreement`, such a minority can cause every signer's local `GlobalStateEvaluator` to conclude that a specific `current_miner`, `burn_block_view`, or `tx_replay_set` has reached "global agreement," even though that same weight cannot produce a validly-approved Nakamoto block header under `verify_signer_signatures`/`compute_voting_weight_threshold` [6](#0-5) .

### Impact Explanation
This breaks the equality that both mechanisms are meant to enforce the same 70% supermajority. A sub-70% (but ≥ floor(70%)) coalition can force `GlobalStateEvaluator::determine_global_state` to register agreement on a specific tenure/miner/burn-view/replay-set one weight-unit earlier than the true supermajority would allow, while `weight_threshold` (block-signature approval) still correctly demands the higher ceiling value. Signers driving miner failover, tenure-extension timestamp aggregation, and transaction-replay-set decisions off `determine_global_state`/`get_signer_global_state` can diverge from what block-level validation would actually accept, producing a temporary, minority-triggerable disagreement among honest signer nodes about the current global signer state — matching the "signer weight below threshold" / "temporary tip disagreement" High-impact category.

### Likelihood Explanation
The trigger condition (`total_weight * 7 mod 10 != 0`) is common — most `total_weight` values are not multiples of 10 — so the one-unit floor/ceiling gap exists in the overwhelming majority of reward cycles. Exploitation only requires a coalition to hold weight exactly equal to the floor value (a value strictly less than the "true" 70% supermajority), which is a modest, non-majority requirement, making this readily triggerable by a minority rather than requiring 51%+ control.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` use the identical ceiling-rounding formula as `NakamotoBlockHeader::compute_voting_weight_threshold` (or have one call the other), so that "global state agreement" and "block signature approval" always agree on the exact same weight boundary.

### Proof of Concept
1. Configure a reward set with `total_weight = 11` (e.g., signer weights `[7, 1, 1, 1, 1]`).
2. `compute_voting_weight_threshold(11)` → `ceil(11*7/10) = ceil(7.7) = 8`; a block needs `>= 8` weight of signatures to be accepted per `verify_signer_signatures`.
3. `GlobalStateEvaluator::reached_agreement(7)` → `7 >= floor(11*7/10) = 7` → `true`.
4. A signer holding weight `7` (63.6% of 11, below the true 70%/8-weight supermajority) broadcasts a `StateMachineUpdate` naming a particular `current_miner`/`burn_block_view`. Every listener's `determine_global_state` (via `reached_agreement`) reports this as the agreed global state, even though the same 7-weight signer cannot get any block signed/approved (needs 8) under `compute_voting_weight_threshold`.
5. This produces two disagreeing "views of consensus" among honest nodes for the same 11-unit reward set: one code path (global state machine) says "agreed" at 7/11, another (block approval) requires 8/11.

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
