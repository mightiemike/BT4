## Analog Found

### Title
Unbounded recursion in `bytecode_hash_node` over attacker-influenced `NestedIntList` segment tree causes native stack overflow / process crash during declared-class hash computation - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The graphql-php advisory describes unbounded recursive-descent parsing with no depth counter, letting a small attacker-crafted nested payload exhaust the C stack and SIGSEGV the process before any validation runs. The sequencer contains an structurally identical pattern in the compiled-class-hash computation path: `bytecode_hash_node` recurses over a `NestedIntList`/`HashableNestedIntList` tree with **no recursion-depth counter, no depth limit option, and no bound on the input tree's structure**, and it runs unsandboxed in the gateway/class-manager process on data whose shape is influenced by an unprivileged declarer's submitted Sierra program.

### Finding Description
`bytecode_hash_node` in [1](#0-0)  is a plain recursive function with no depth tracking:
```
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
```
It is invoked from `bytecode_hash` [2](#0-1) , which is invoked from `hash_inner`/`HashableCompiledClass::hash` [3](#0-2) , operating on `CasmContractClass.bytecode_segment_lengths` via `get_bytecode_segment_lengths` [4](#0-3) .

This is called by the gateway's `SierraCompiler::compile` directly after the Sierra→CASM compiler subprocess returns, and runs **in the main (unsandboxed) process**, not inside the resource-limited subprocess used for compilation itself:
```
let executable_class = self.compiler.compile(class)?;
let executable_class_hash = executable_class.hash(&HashVersion::V2);
``` [5](#0-4) 

`SierraCompiler::compile` is reached from `ClassManager::add_class`, which every DECLARE transaction submitted by an unprivileged declarer flows through: [6](#0-5) 

The `NestedIntList` tree (`bytecode_segment_lengths`) is produced by the external `cairo-lang-sierra-to-casm` compiler based on the shape of the attacker-supplied Sierra program (function/branch/segment structure). Only the compiler *subprocess* has CPU/memory/time limits via `ResourceLimits` [7](#0-6) ; no such protection covers the subsequent in-process recursive hash computation on the returned tree. Notably, elsewhere in the codebase the equivalent tree-walk explicitly hard-codes an assumption of depth ≤ 1 and panics otherwise (`assert!(segmentation_depth <= 1, ...)` in `NestedFeltCounts::new_inner`, [8](#0-7) ), confirming that the sequencer's own code does not actually guarantee the compiler always emits a depth-1 tree — yet `bytecode_hash_node` makes no such check and will happily recurse to whatever depth the compiler emits.

The gateway-side stateless validator only bounds the *raw* Sierra program size (`max_contract_bytecode_size` = 81920 felts, `max_contract_class_object_size` ≈ 4MB) [9](#0-8)  — it does not bound or reject the compiled CASM segment tree's structural depth before it is fed into the unbounded recursive hasher.

### Impact Explanation
Rust's native stack overflow is not a catchable panic — like the SIGSEGV in the graphql-php report, it aborts the whole process. A single DECLARE transaction from any unprivileged account, crafted so that the Sierra→CASM compiler emits a deeply nested `bytecode_segment_lengths` tree, can crash the gateway/class-manager process performing `hash()` on the returned `CasmContractClass`, dropping all in-flight requests on that process and requiring a restart — directly impacting "a network unable to confirm new transactions" for the affected sequencer instance, matching the required impact category.

### Likelihood Explanation
Reachable from a single, unprivileged, unauthenticated (network-side) DECLARE transaction — no special privileges, no operator/proposer/validator role needed. The only defenses in place (gateway size/version checks, subprocess resource limits) constrain the raw Sierra size and the compiler subprocess's CPU/memory/time, but do nothing to bound the *depth* of the segment tree the compiler emits nor to bound the recursive hashing pass that consumes it in the main process.

### Recommendation
Add an explicit recursion-depth counter/limit to `bytecode_hash_node` (and its sibling recursive consumers of `HashableNestedIntList`, e.g. `NestedFeltCounts::new_inner` and `create_bytecode_segment_structure_inner`), rejecting (with a normal `Result` error) any `NestedIntList` whose nesting exceeds a small, protocol-defined maximum (e.g. 1–2, consistent with the assumption already hard-coded in `NestedFeltCounts::new_inner`). Alternatively/additionally, validate the depth of `bytecode_segment_lengths` returned by the Sierra→CASM compiler immediately after compilation and before it is hashed or otherwise processed outside the sandboxed subprocess.

### Proof of Concept
Conceptually: craft a Sierra program (within the existing 81920-felt / ~4MB size limits) composed of many nested/chained function definitions such that `cairo-lang-sierra-to-casm`'s segmentation produces a deeply nested `NestedIntList::Node(vec![... NestedIntList::Node(...) ...])` chain (depth in the thousands). Submit it as the `contract_class` of a DECLARE V3 transaction. When the gateway's `SierraCompiler::compile` ( [5](#0-4) ) calls `.hash(&HashVersion::V2)`, `bytecode_hash_node` recurses once per tree level with no bound, exhausting the process stack and crashing the gateway/class-manager process — analogous to vectors A–D in the referenced graphql-php PoC.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash

    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,

        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());

        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

        &*hashable_class.get_bytecode_segment_lengths(),

        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}
