### Title
Unvalidated attacker-controlled `RevertInstructions.FundRecipient` allows funds to be permanently burned to `address(0)` on outbound revert / gas refund - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
The external report's bug class is "an attacker-influenced transfer target being `address(0)` is never validated/handled, causing funds to be silently misdirected/lost." The Push Chain analog is `RevertInstructions.FundRecipient`, a field supplied inside the inbound event observed from the *external* source chain (i.e., attacker-controlled data submitted by whoever calls the gateway on the source chain). This value is only lenient-canonicalized, never validated for non-emptiness or non-zero-ness, and is used directly as the destination for re-minted bridged funds and unused-gas refunds when an outbound fails.

### Finding Description
`Inbound.Canonicalize()` normalizes `RevertInstructions.FundRecipient` but never rejects malformed or zero values: [1](#0-0) 

`ValidateForExecution` validates `Recipient` for `FUNDS`/`GAS`/CEA payload paths, but never validates `RevertInstructions.FundRecipient` at all: [2](#0-1) 

That unchecked value is then used as the fallback/override recipient in three separate fund-moving paths:

1. Revert-outbound construction (used when an inbound execution needs a revert): [3](#0-2) 

2. Failed-outbound handling — re-mints bridged PRC20 funds directly to `recipient` derived from `FundRecipient` with no zero-address guard, then calls `CallPRC20Deposit`: [4](#0-3) 

3. Gas-refund handling — computes `refundRecipient` the same way and sends the excess gas fee there via `CallUniversalCoreRefundUnusedGas`: [5](#0-4) 

Because `FundRecipient` originates from attacker-controlled inbound event data (the caller of the source-chain gateway sets `RevertInstructions`) and is never checked against `address(0)` (or any other unrecoverable sentinel) before being converted with `common.HexToAddress(...)`, an attacker can set it to the zero address. When the corresponding outbound later fails (a scenario the attacker can often induce or that occurs naturally, e.g. destination-chain execution failure), the honest validators/honest node will faithfully re-mint the bridged PRC20 amount and/or the unused-gas refund to `address(0)`, permanently burning user/protocol funds that were meant to be returned to a valid owner.

### Impact Explanation
This is a permanent, unrecoverable loss of user or protocol-controlled funds (the bridged principal and/or the excess gas fee) reachable purely through unprivileged, ordinary inbound submission by any external-chain caller — matching the in-scope impact "permanent loss ... of user or protocol-controlled funds" and "corruption of ... refund accounting ... revert destination." No privileged actor is required; the honest validator set and honest core-validator execution path faithfully process the malformed but well-formed-looking `FundRecipient` value.

### Likelihood Explanation
Medium: the attacker must construct a source-chain inbound event whose `revert_instructions.fund_recipient` is `address(0)` (or any address they cannot practically recover, though `address(0)` is the clearest case) and then get, or wait for, that inbound's spawned outbound to fail on the destination chain (a failure that is either attacker-inducible in many cross-chain flows or naturally occurring). Because the field is fully attacker-controlled and completely unvalidated in `ValidateForExecution`, the trigger condition itself requires no special privilege.

### Recommendation
Add validation of `RevertInstructions.FundRecipient` in `Inbound.ValidateForExecution` (and/or at vote-ingress in `Canonicalize`) rejecting empty and `address(0)` (`EvmZeroAddress`) values, similar to the existing check already performed on `Recipient`. Additionally, add a defensive zero-address guard immediately before the fund-moving calls in `handleFailedOutbound` and `applyGasRefund` (`x/uexecutor/keeper/outbound.go`), falling back to `outbound.Sender` (or aborting the outbound for manual intervention) whenever the resolved recipient is the zero address.

### Proof of Concept
1. Attacker calls the gateway contract on an external chain (e.g. EVM or Solana) to initiate a bridge transfer, supplying `revertInstructions.fundRecipient = 0x0000000000000000000000000000000000000000` in the emitted gateway event.
2. Universal Validators observe and vote the inbound via `MsgVoteInbound`; `Canonicalize()` accepts the zero address unchanged, and `ValidateForExecution()` performs no check on `FundRecipient`, so the UTX is created and processed normally.
3. The resulting outbound to the destination chain later fails (destination revert/insufficient gas/etc.), triggering `handleFailedOutbound`.
4. `recipient := outbound.Sender` is overridden by the non-empty `RevertInstructions.FundRecipient == address(0)` at `x/uexecutor/keeper/outbound.go:108-112`, and `k.CallPRC20Deposit` mints the bridged token amount to `address(0)`, permanently destroying the funds instead of returning them to the sender.
5. Similarly, `applyGasRefund` sends the excess gas-fee refund to the same zero address (`x/uexecutor/keeper/outbound.go:201-253`).
