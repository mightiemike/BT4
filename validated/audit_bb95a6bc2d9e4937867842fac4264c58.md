**Analysis:** The claim conflates two distinct fork-resolution calls that are correctly kept separate by design. The `tx_validator.rs` docstring itself states the admission-time L1-fee simulation is "best-effort... not a guarantee" [1](#0-0) , and that simulation only affects whether a tx is *admitted to the mempool*—it never influences what SpecId is actually used to *execute* the block.

The binding that matters—native execution vs. circuit execution for the *same* L2 block height—holds exactly. Both paths resolve `SpecId` from the identical global, deterministic `FORKS` table via `fork_from_block_number`/`ForkManager::active_fork()`, keyed only by `l2_height`:

- Sequencer sealing uses `self.fork_manager.active_fork().spec_id` for the L2 block being sealed [2](#0-1) .
- Batch prover native re-execution uses `fork_from_block_number(l2_height).spec_id` for that same height [3](#0-2) .
- The batch proof circuit (guest) uses `fork_manager.active_fork().spec_id` after `fork_manager.register_block(l2_height)` for that same height [4](#0-3) .

All three resolve to the same `SpecId` for a given `l2_height`, since `FORKS` is a compiled-in constant table shared by sequencer, prover, and guest binaries [5](#0-4) . Even if a divergence somehow occurred, both the batch-prover's witness-regeneration step and the guest circuit itself hard-assert that the computed state root matches the sequencer-claimed root, aborting proving/proof-generation on mismatch rather than silently producing an unprovable or false proof [6](#0-5) [7](#0-6) .

The attacker-controlled admission-time vs. execution-time divergence in `simulate_tx_l1_fee` (using `fork_from_block_number(H-1)` at mempool-admit time vs. `fork_from_block_number(H)` at sealing time) can at most cause a transaction to be admitted or rejected slightly inaccurately with respect to the true L1 fee—an accepted best-effort limitation, not a state-root or proof-soundness issue, and out of scope per the rules (no bridge value movement, no false proof, no honest-node split).
