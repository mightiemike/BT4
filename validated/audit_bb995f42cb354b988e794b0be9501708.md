### Title
Meta-transaction (`DelegateAction` / NEP-366) signature scheme omits a chain/network identifier, enabling cross-network replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The NEP-461/NEP-366 signature scheme used to authorize `DelegateAction`/`DelegateActionV2` meta-transactions binds the signature only to a NEP-number+on/off-chain discriminant, the sender/receiver, actions, nonce and `max_block_height`. Unlike ordinary `Transaction`s, which are bound to a specific chain by including a recent `block_hash` (a value that is chain-specific and cannot be replayed on a network with a different history), `DelegateAction`/`DelegateActionV2` contains no chain-identifying value at all (no genesis hash, no `chain_id`, no recent block hash).

### Finding Description
`SignedDelegateAction::verify` and `VersionedSignedDelegateAction::verify` compute the signed hash purely from the NEP-461 `SignableMessage` (a 4-byte NEP/on-off-chain discriminant) plus the Borsh-serialized `DelegateAction`/`DelegateActionV2` payload: [1](#0-0) [2](#0-1) 

The discriminant construction itself carries only a NEP number and an on-chain/off-chain flag - nothing that identifies which NEAR network (mainnet, testnet, or any other deployment sharing the same NEP number scheme) the signature was intended for: [3](#0-2) [4](#0-3) 

By contrast, an ordinary `SignedTransaction` includes a recent `block_hash`, and the runtime/routing layer explicitly rejects a transaction whose `block_hash` does not correspond to a recent block on the receiving chain - this is documented as an explicit replay-protection mechanism unique to a chain's own recent history: [5](#0-4) [6](#0-5) 

`DelegateAction` has no equivalent field: replay protection for meta-transactions relies solely on the access-key `nonce` and an absolute `max_block_height` (a plain integer, not a chain-specific hash), both of which are meaningful only relative to on-chain state and say nothing about *which* chain that state belongs to: [7](#0-6) [8](#0-7) 

NEAR explicitly supports multiple networks (mainnet/testnet/localnet) that are otherwise built from divergent genesis/state but can and do provision accounts with the *same* `AccountId` and the *same* key material - this exact correspondence is what the mirror tooling in the repo relies on to replicate transactions between networks (mapping keys 1:1 between environments), demonstrating that identical account/key pairs across independent NEAR networks is an anticipated, supported scenario rather than a theoretical edge case: [9](#0-8) 

Because the `DelegateAction` signing payload contains no chain-binding value, a `SignedDelegateAction` produced for use as a meta-transaction on one NEAR network is byte-for-byte valid on any other NEAR network where the same `sender_id`/`public_key` pair exists with the same access-key nonce (e.g., an account whose keys were provisioned identically on mainnet and testnet, or on a forked/companion network). A relayer on that other network can wrap the identical signed payload in its own `Transaction`, submit it, and `apply_delegate_action`'s signature check (`DelegateActionInvalidSignature`) and nonce check (`DelegateActionInvalidNonce`) will both pass because they only compare against local per-network state, not against any chain identifier baked into the signature itself.

Notably, nearcore's own EVM-compatible `near-wallet-contract` recognizes exactly this class of risk and defends against it by hard-coding a `CHAIN_ID` into every Ethereum-style transaction it accepts, rejecting (and penalizing) any relayer that submits a transaction signed for the wrong chain id: [10](#0-9) [11](#0-10) 

The core NEP-366/NEP-461 meta-transaction signature scheme has no analogous protection.

### Impact Explanation
A user who signs a `DelegateAction` off-chain (as required by the meta-transaction/relayer flow) for execution on one NEAR network has that signature accepted as valid on any other NEAR network that happens to have provisioned the same account/key/nonce state. If the user (or a wallet product) reuses the same seed/key across multiple NEAR-based networks - a supported and expected configuration per the mirror tooling - an out-of-scope or malicious relayer on the "wrong" network could submit the identical `SignedDelegateAction`, causing the user's actions (transfers, key additions, function calls, etc.) to execute on a network the user never intended, resulting in unauthorized value movement or unintended state changes attributable to the user's account on that network.

### Likelihood Explanation
Exploitability depends on the same account/key pair (and matching nonce) existing on two live NEAR networks, which is not the default case for independent mainnet/testnet deployments but is an explicitly anticipated and tooled-for scenario in this codebase (account/key mirroring). Any relayer or intermediary that has access to a user's off-chain-transmitted `SignedDelegateAction` (which by design passes through an untrusted relayer before being submitted) could attempt replay on any network where matching account state exists.

### Recommendation
Include a chain/network-binding value (e.g., the genesis hash or a `chain_id` string equivalent to `GenesisId::chain_id`) in the NEP-461 `SignableMessage`/`MessageDiscriminant` construction used for `DelegateAction` and `DelegateActionV2`, so that a delegate-action signature is cryptographically bound to a specific NEAR network and cannot be replayed against a different network's runtime, mirroring the `CHAIN_ID` binding already used in `near-wallet-contract`.

### Proof of Concept
1. Provision `alice.near`/`bob.near`-equivalent accounts with identical `AccountId`s and identical access-key `public_key`/`nonce` state on two independent NEAR networks (Network A and Network B) - the same correspondence the mirror tool sets up in `tools/mirror/src/genesis.rs`.
2. Alice signs a `DelegateAction` (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`) intending it for use as a meta-transaction on Network A, per `SignedDelegateAction::sign` in `core/primitives/src/action/delegate.rs:92-95`.
3. A relayer that has access to this `SignedDelegateAction` (as required by the meta-tx flow, see `docs/architecture/how/meta-tx.md:47-52`) instead wraps it into a `Transaction` on Network B and submits it.
4. Network B's runtime executes `apply_delegate_action`, which only checks the NEP-461 signature (`DelegateActionInvalidSignature`) and the local access-key nonce (`DelegateActionInvalidNonce`) - both of which succeed because Network B has matching account/key/nonce state and the signed payload contains no value identifying it as belonging to Network A. The delegate action's inner actions execute on Network B against Alice's account there, despite her never intending or authorizing that.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

/// The struct a user creates and signs to create a meta transaction.
struct DelegateAction {
    /// Signer of the delegated actions
    pub sender_id: AccountId,
    /// Receiver of the delegated actions.
    pub receiver_id: AccountId,
    /// List of actions to be executed.
    ///
    /// With the meta transactions MVP defined in NEP-366, nested
    /// DelegateActions are not allowed. A separate type is used to enforce it.
    pub actions: Vec<NonDelegateAction>,
    /// Nonce to ensure that the same delegate action is not sent twice by a
    /// relayer and should match for given account's `public_key`.
    /// After this action is processed it will increment.
    pub nonce: Nonce,
    /// The maximal height of the block in the blockchain below which the given DelegateAction is valid.
    pub max_block_height: BlockHeight,
    /// Public key used to sign this delegated action.
    pub public_key: PublicKey,
}

// A relayer sending a transaction signed with the wrong chain id is a ban-worthy offense.
#[tokio::test]
async fn test_relayer_wrong_chain_id() -> anyhow::Result<()> {
    let TestContext { worker, mut wallet_contract, wallet_sk, wallet_address, .. } =
        TestContext::new().await?;

    let relayer_pk = wallet_contract.register_relayer(&worker).await?;

    let transaction = aurora_engine_transactions::eip_2930::Transaction2930 {
        nonce: 0.into(),
        gas_price: 0.into(),
        gas_limit: 0.into(),
        to: Some(Address::new(wallet_address)),
        value: Wei::zero(),
        data: [
            crate::eth_emulation::ERC20_BALANCE_OF_SELECTOR.to_vec(),
            ethabi::encode(&[ethabi::Token::Address(wallet_address)]),
        ]
        .concat(),
        chain_id: CHAIN_ID + 1,
        access_list: Vec::new(),
    };
    let signed_transaction = crypto::sign_transaction(transaction, &wallet_sk);

    let result = wallet_contract
        .rlp_execute(wallet_contract.inner.id().as_str(), &signed_transaction)
        .await?;

    assert!(!result.success);
    assert_eq!(result.error.as_deref(), Some("Error: faulty relayer"));

    Ok(())
}
