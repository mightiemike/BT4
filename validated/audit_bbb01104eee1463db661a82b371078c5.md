### Title
Non-deterministic L1-handler cancellation-timelock check uses each validator's local wall clock instead of a consensus-agreed timestamp - ([File: crates/apollo_l1_events/src/l1_events_provider.rs])

### Summary
`L1EventsProvider::validate` determines whether a pending `L1HandlerTransaction` is still valid (not yet `CancelledOnL2`) by calling `self.clock.unix_now()` — each node's own live wall clock — rather than a timestamp that is fixed and agreed upon for the block/proposal being validated. [1](#0-0) 

### Finding Description
`validate()` forwards `self.clock.unix_now()` into `TransactionManager::validate_tx`, which uses it to lazily transition a record from `CancellationStartedOnL2` to `CancelledOnL2` via `update_time_based_state`: [2](#0-1) [3](#0-2) [4](#0-3) 

The comparison `unix_now >= requested_at.saturating_add(cancellation_timelock)` decides whether the transaction is still `is_validatable()` (usable in the block) or must be rejected as `CancelledOnL2`. Because `unix_now` comes from each node's independent `Clock::unix_now()` (the `DefaultClock`, i.e. real system time) rather than from a value embedded in the proposal (e.g. the block/proposal timestamp that all validators agree to validate against), two honest validators processing the *same* proposal, for a tx whose cancellation timelock boundary falls within the validation window, can observe different results purely due to clock skew or processing-time differences between nodes. One validator sees `unix_now` still below the timelock boundary → `Validated`; another, slightly later or with a skewed clock, sees `unix_now` past the boundary → `Invalid(CancelledOnL2)`.

This is structurally the same class of bug as CVE-2024-27397: a time-based validity check inside a stateful control-plane operation samples "now" independently at each evaluation point instead of using one consistent timestamp fixed for the whole operation/transaction, letting the same logical item (nftables set element / here, an L1-handler tx nearing its cancellation timelock) be judged valid by one path and expired by another concurrently-running path.

### Impact Explanation
Since block validation must be deterministic across all honest validators for consensus to make progress, this discrepancy can cause honest-node divergence: some validators vote to accept a proposal (all txs `Validated`) while others reject the same proposal (a tx is `CancelledOnL2`), for a tx right at its cancellation-timelock boundary. In the worst case this repeatedly stalls consensus on proposals containing such L1-handler transactions, i.e. "a network unable to confirm new transactions" for as long as reproposals keep hitting the same boundary condition, which is an explicitly in-scope impact bucket.

### Likelihood Explanation
Triggering requires an L1 handler transaction whose cancellation was requested, with cancellation timelock (`l1_handler_cancellation_timelock_seconds`) about to expire at the moment a proposal containing/referencing it is being validated network-wide. Given normal network propagation delay and validator clock drift (NTP skew is typically bounded but nonzero, and per-node processing latency adds further variance), it is plausible — though narrow in timing window — for different validators to be on opposite sides of the boundary during the same round, especially since `unix_now` is sampled per call to `validate` (once per transaction in the proposal) rather than once per height/round.

### Recommendation
Do not use each node's live wall clock to decide cancellation-timeout expiry for control-plane/consensus-relevant validity of a proposal's transactions. Use a timestamp that is part of the proposal/round context and identical for all validators evaluating it (e.g., the `ProposalInit.timestamp`/block timestamp, similar to how `is_proposal_init_valid` in `crates/apollo_consensus_orchestrator/src/validate_proposal.rs` bounds proposal timestamps against a shared reference), and thread that fixed timestamp into `TransactionManager::validate_tx` / `update_time_based_state` instead of `self.clock.unix_now()`. Reserve live wall-clock reads for genuinely node-local/async paths (e.g. the scraper, async GC-equivalent housekeeping such as `clear_old_tx_from_consumed_queue`), matching the upstream fix's split between transaction-timestamp based control-plane checks and current-time based async/lockless checks.

### Proof of Concept
1. Two honest validators, V1 and V2, are validating the same consensus round/proposal at height H, which includes L1-handler tx `t` whose cancellation was requested at `requested_at`, with `cancellation_timelock` seconds configured.
2. Suppose real time `T = requested_at + cancellation_timelock` falls inside the round's validation window.
3. V1 calls `provider.validate(t.tx_hash, H)` slightly before `T` (its local `clock.unix_now()` still `< requested_at + cancellation_timelock`): `update_time_based_state` does not transition the record, `is_validatable()` is true → `ValidationStatus::Validated`.
4. V2, due to a few hundred ms of clock skew or later message arrival, calls `validate` after `T`: `is_cancellation_timelock_passed` is true, record transitions to `CancelledOnL2`, `is_validatable()` is false → `Invalid(CancelledOnL2)`.
5. V1 votes to accept the proposal; V2 votes to reject it — the two honest nodes diverge on the validity of the same proposal, matching the test-visible behavior already exercised in `validate_tx_cancellation_requested_validated_then_expired_returns_cancelled` (which demonstrates the same tx transitioning from `Validated` to `CancelledOnL2` purely due to a clock advance, but here across two different nodes' independent clocks rather than one node's clock advancing over time).     pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
```rust
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }
```

```rust
    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
```

```rust
#[test]
fn validate_tx_cancellation_requested_validated_then_expired_returns_cancelled() {
    // Setup.
    let tx_1 = l1_handler(1);
    let clock = Arc::new(FakeClock::new(5));
    let mut l1_events_provider = L1EventsProviderContentBuilder::new()
        .with_clock(clock.clone())
        .with_nonzero_timelock_setup()
        .with_cancel_requested_txs([tx_1.clone()])
        .with_state(ProviderState::Validate)
        .build_into_l1_provider();

    // Test.

    // Should be validatable before expiry,
    let status =
        l1_events_provider.validate(tx_1.tx_hash, l1_events_provider.current_height).unwrap();
    assert_eq!(status, ValidationStatus::Validated);
    // Now, advance time past expiry and validate again,
    // This tests the edge case: a tx can be validatable before expiry, but if validated again after
    // expiry, it should return the cancellation error.
    clock.advance(Duration::from_secs(
        l1_events_provider.config.l1_handler_cancellation_timelock_seconds.as_secs(),
    ));
    let status2 =
        l1_events_provider.validate(tx_1.tx_hash, l1_events_provider.current_height).unwrap();
    assert_eq!(status2, InvalidValidationStatus::CancelledOnL2.into());
}
```
