### Title
Unhandled exception from malformed `host` query parameter causes DoS in `sanitizeHost`/`decodeHost` (Node's `atob`) - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` validates the untrusted `host` query parameter using a permissive regex before decoding it with `atob()`, and the resulting exception type is not normalized into a `ShopifyError`. This mirrors the reported bug class: input from an anonymous, attacker-controlled request field is passed into a decode path whose validation is insufficient to guarantee the decode step succeeds, so malformed input can throw an unhandled/unexpected exception instead of a handled validation error.

### Finding Description
`sanitizeHost` only checks the `host` value against a permissive base64 character-set regex, then immediately calls `decodeHost`, which just delegates to the platform `atob()`: [1](#0-0) [2](#0-1) 

The regex `^[0-9a-zA-Z+/]+={0,2}$` accepts strings that are not valid base64 (e.g., strings whose length is not a multiple of 4, or with padding `=` in the wrong position), which `atob()` can reject by throwing a `DOMException`/`InvalidCharacterError` rather than returning normally. Unlike the other validation errors in this function (`InvalidHostError`), an exception thrown by `atob()` here is a generic platform exception, not a `ShopifyErrors.InvalidHostError`, so any code that specifically catches `ShopifyErrors` (as is the pattern throughout this codebase, e.g. `handleCallbackError` switches on `error instanceof InvalidOAuthError`, etc.) would not catch it, and it can propagate as an unhandled error.

This function is reached directly from anonymous, unauthenticated request paths that read the `host` query parameter without wrapping the call in a broad try/catch, for example: [3](#0-2) [4](#0-3) [5](#0-4) 

This is the same bug class as the report: a deserialization/decoding routine on untrusted, network-supplied data (`GossipMessage`'s `TryFrom` in the dfinity report; here, `host`'s base64 decode) has a validation gate that is insufficient to prevent the underlying decode primitive from throwing, and the thrown exception is not the expected/handled error type.

### Impact Explanation
An unhandled exception in a request-handling code path can result in a 500/unhandled rejection for that request. In server frameworks (Express) an uncaught synchronous throw inside a non-async handler, or an unhandled promise rejection, can in some configurations crash the Node process (Denial of Service) rather than being cleanly converted into an HTTP error response, especially since the exception type doesn't match any of the `ShopifyErrors` classes the surrounding code branches on.

### Likelihood Explanation
The `host` parameter is fully attacker-controlled and reachable by any anonymous request to embedded-app document routes (no authentication required, no signature check on `host`). Constructing a base64-charset string whose length/padding is invalid for `atob()` is trivial for an unauthenticated attacker.

### Recommendation
Wrap the `atob()` call in `decodeHost`/`sanitizeHost` in a try/catch and translate any decoding failure into `ShopifyErrors.InvalidHostError`, consistent with the rest of the validation flow, so all callers can rely on catching a single well-known error type instead of a low-level platform exception. Long term, avoid relying on regex pre-checks as the sole guard for a decode call that can itself throw; validate structurally (e.g., check length is a multiple of 4) or use a decode function with its own well-defined error contract, per the same recommendation as the original report (avoid unguarded calls that can panic/throw on attacker input).

### Proof of Concept
1. Send `GET /?shop=<TEST_SHOP>&host=A` (a single-character string, which matches `base64regex` but is not valid base64 padding) to an embedded app route that calls `validateShopAndHostParams` / `sanitizeHost` / `getEmbeddedAppUrl` (e.g., the `authenticate.admin` document-request path).
2. `sanitizeHost` passes the regex check, then calls `decodeHost('A')`, which calls `atob('A')`.
3. `atob()` throws (invalid base64 length) instead of returning a decoded string.
4. Because this exception is not a `ShopifyErrors.InvalidHostError`, it is not handled by the `instanceof` error-branch logic used elsewhere in the codebase (e.g. `handleCallbackError`), potentially surfacing as an unhandled error/500 rather than the intended graceful "invalid host" response, for every occurrence of this malformed input.

Note: I was not able to execute code in this environment to confirm the exact current Node `atob()` throwing behavior for all malformed-length inputs, and I did not find an existing repo-level test that feeds a malformed (non-multiple-of-4, non-empty) base64-charset string into `sanitizeHost`/`decodeHost` — the existing `INVALID_HOSTS` test fixtures use non-base64-charset examples that fail the regex check before reaching `atob`, not malformed-but-charset-valid ones. This should be verified with a live Devin session to confirm the crash and its blast radius before treating this as fully confirmed.

  return (host: string): string => {
