### Title
`withdrawReward`/`queryReward` cost grows unboundedly with unresolved maintenance cycles, risking DoS on vote/withdraw operations - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.withdrawReward`/`queryReward` (and its TVM analog `VoteRewardUtil.withdrawReward`/`queryReward`) compute reward by delegating to `computeReward(beginCycle, endCycle, accountCapsule)`, which for cycles prior to `getNewRewardAlgorithmEffectiveCycle()` falls back to `getOldReward`, a `for (long cycle = begin; cycle < end; cycle++) { reward += computeReward(cycle, votes); }` loop — an O(number-of-unwithdrawn-cycles × votes) computation, structurally analogous to Hubble's `settleFunding`/`_calcTwap` pattern where cost scales with an unbounded, time-growing quantity rather than a fixed bound.

### Finding Description
`withdrawReward` is reached from ordinary, unprivileged user actions: casting a vote (`VoteWitnessActuator.countVoteAccount` → `mortgageService.withdrawReward`) [1](#0-0) , withdrawing balance (`WithdrawBalanceActuator`), unfreezing (`UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`), and via a smart-contract call through the TVM vote/withdraw-reward native contracts (`VoteWitnessProcessor.execute` → `VoteRewardUtil.withdrawReward`) [2](#0-1) .

Inside `MortgageService`, when `beginCycle` predates `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`, the reward for the old-algorithm range is computed by iterating cycle-by-cycle: [3](#0-2) 
and each cycle iteration re-scans the account's full vote list with `computeReward(cycle, votes)` [4](#0-3) . The overall `computeReward(beginCycle, endCycle, accountCapsule)` dispatches to this old path or the newer O(1)-per-vote Vi-delta path depending on `newAlgorithmCycle` [5](#0-4) . The identical pattern exists in the TVM-reachable `VoteRewardUtil` [6](#0-5) .

This mirrors the reported bug class: a per-call cost that is a function of an ever-growing counter (maintenance cycles elapsed since the account's `beginCycle`, analogous to Hubble's growing market count / TWAP snapshot count) rather than a bounded input size. Any account (or delegate/relayer paying energy for a contract calling the vote/withdraw precompile) that has not interacted for a long stretch, combined with `allowOldRewardOpt` disabled, can trigger an execution path whose cost scales with the full backlog of un-migrated cycles times the number of votes cast (bounded by `MAX_VOTE_NUMBER`), rather than a constant.

### Impact Explanation
If the old-algorithm cycle range grows large for a given account (long-dormant voter, or if `allowOldRewardOpt`/the Vi-based algorithm migration point is far enough in the past relative to that account's `beginCycle`), a single `VoteWitnessContract`, `WithdrawBalanceContract`, `UnfreezeBalanceContract` transaction, or TVM contract call that reaches this code path can consume disproportionate CPU/energy relative to its declared cost, potentially causing the transaction to fail from energy exhaustion, or — for the FullNode/produced-block path outside TVM metering — consuming excessive wall-clock processing time on the node executing the actuator, degrading block production/propagation. This is a self-inflicted, per-account DoS (an account can lock itself out of withdrawing/voting) rather than a global cross-account DoS like `settleFunding`, which materially limits severity versus the original finding.

### Likelihood Explanation
Likelihood is low-to-moderate and highly dependent on network configuration: the cost only materializes for accounts whose unresolved cycle range predates `getNewRewardAlgorithmEffectiveCycle()`/lacks `allowOldRewardOpt`, and `RewardViCalService.getNewRewardAlgorithmReward` appears intended to make the migrated path O(1) per vote, capping the unbounded portion to a fixed historical window rather than a permanently growing one. I was not able to fully confirm from the available index whether `allowOldRewardOpt`/`NewRewardAlgorithmEffectiveCycle` are already enabled network-wide on current java-tron mainnet parameters (this requires checking `DynamicPropertiesStore` default/migrated values and `ProposalService`, which I could not fully trace within the remaining budget) — this materially affects whether the unbounded-loop window is closed or still open going forward.

### Recommendation
- Ensure `allowOldRewardOpt` (Vi-delta based `RewardViCalService.getNewRewardAlgorithmReward`) is enabled and that `NewRewardAlgorithmEffectiveCycle` bounds the legacy per-cycle loop to a small, fixed, already-elapsed range so no growing backlog can accumulate going forward.
- Cap/guard the legacy per-cycle loop in `MortgageService.getOldReward` (and mirror in `VoteRewardUtil` if a similar legacy path exists there) with a maximum number of cycles processed per call, requiring multiple calls to fully settle very old backlogs, analogous to allowing `settleFundingForMarkets` in batches rather than all-at-once.
- Add monitoring/alerting for accounts whose `endCycle - beginCycle` (or cycle backlog) exceeds a safety threshold before they call vote/withdraw, and consider proactively migrating/settling such backlogs administratively.

### Proof of Concept
Conceptual reproduction (not executed against live state, since this requires long time elapsed / many un-migrated cycles which cannot be fabricated from static review alone):
1. An account votes for the maximum allowed number of witnesses (`MAX_VOTE_NUMBER`) and then never calls vote/withdraw/unfreeze again while many maintenance cycles elapse under the old reward algorithm (i.e., `beginCycle` remains far below `newAlgorithmCycle`, or the new algorithm/`allowOldRewardOpt` was never enabled).
2. The account later calls `VoteWitnessContract` (or a TVM contract invoking the vote precompile) to vote again.
3. `VoteWitnessActuator.countVoteAccount` invokes `mortgageService.withdrawReward(ownerAddress)` [1](#0-0) , which calls `computeReward(beginCycle, endCycle, accountCapsule)` → `getOldReward(begin, oldEndCycle, srAddresses)` [7](#0-6) , iterating `cycle = begin` to `oldEndCycle`, each iteration scanning up to `MAX_VOTE_NUMBER` votes with store reads [3](#0-2) .
4. As the cycle backlog grows (measured in elapsed maintenance periods), the transaction's execution time/energy consumption grows linearly, eventually risking failure due to energy limits or excessive processing time for that single call — the same class of unbounded, activity/time-scaling cost identified in the Hubble `settleFunding` report.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
