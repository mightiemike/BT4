### Title
Capability Execution Metadata Spoofing via `/v2/execute_capability` Allows Workflow Owner Impersonation - ([File: core/web/capability_controller.go])

### Summary
The dev-only `CapabilityController.ExecuteCapability` handler accepts an attacker-supplied, raw protobuf-encoded `CapabilityRequest` and passes it directly to `capability.Execute` without validating that the embedded `Metadata` (WorkflowID/WorkflowOwner/DON info) matches the authenticated caller's own identity. Any authenticated 'run'-role user can therefore forge a `CapabilityRequest` claiming to belong to another workflow/owner and have it executed by the target capability (e.g. chain-write, gateway, or other side-effecting capabilities).

### Finding Description
`ExecuteCapability` in `core/web/capability_controller.go` binds the JSON body into `CapabilityRequestOuter{CapabilityName, CapabilityRequest []byte}`, both attacker-controlled fields: [1](#0-0) 

It then looks up the executable purely by the attacker-supplied `CapabilityName`, unmarshals the raw bytes into a `pb.CapabilityRequest` (which contains `Metadata` fields like WorkflowID/WorkflowOwner/DON), and executes it directly: [2](#0-1) 

At no point does the handler cross-check `capabilityRequest.Metadata.WorkflowOwner`/`WorkflowID` against the identity of the authenticated session/token used to reach the endpoint. There is no code path in this function establishing or enforcing such a binding — the only gating is the router-level middleware (`auth.RequiresRunRole`, wired under `build.IsDev()`), which authenticates/authorizes the caller for *access to the endpoint*, not for the *content of the pb-encoded payload*. Because the capability registry's `Execute` trusts the metadata verbatim, any capability implementation that branches on `WorkflowOwner`/`WorkflowID` (e.g., to authorize a chain-write, a gateway call, or to attribute cross-chain execution) will act as if the request came from the impersonated workflow/owner.

### Impact Explanation
A minimally-privileged, non-owner 'run'-role user can forge capability metadata to impersonate another workflow's owner and trigger unauthorized capability execution — e.g., an unauthorized chain-write, gateway message, or other externally-observable side effect attributed to a different workflow/owner. This is a capability-routing/authorization hijack with real transaction/execution impact, matching a "unauthorized workflow execution" bounty category.

### Likelihood Explanation
Exploitability requires: (1) `build.IsDev()==true` at build/runtime (dev builds only), and (2) attacker holds a valid 'run'-role token. Given those two preconditions — which do not require node-operator/admin privilege or key leakage, only a legitimately issued run-role credential — the attack is trivial and fully repeatable: craft any pb `CapabilityRequest` with arbitrary `Metadata`, POST it to `/v2/execute_capability`, and the handler executes it without further checks.

### Recommendation
In `ExecuteCapability`, after unmarshaling the `CapabilityRequest`, validate/overwrite `capabilityRequest.Metadata.WorkflowOwner` (and any other owner/DON-identifying fields) using the authenticated session/token identity rather than trusting attacker-supplied protobuf metadata. Reject the request if the caller cannot be resolved to a workflow owner, or if the endpoint is intended for arbitrary manual invocation, explicitly document/restrict it to capabilities that do not use metadata for authorization, and enforce that in code (e.g., an allowlist of safe capability types), rather than relying solely on the `build.IsDev()` gate.

### Proof of Concept
Unit test in `core/web/capability_controller_test.go` style:
1. Register a mock capability whose `Execute` implementation asserts/records `req.Metadata.WorkflowOwner`.
2. Authenticate as a 'run'-role (non-owner) user for workflow A.
3. Build a `pb.CapabilityRequest` with `Metadata.WorkflowOwner = "victim-owner-B"`, `WorkflowID = "victim-workflow"`, marshal via `pb.MarshalCapabilityRequest`.
4. POST to `/v2/execute_capability` with `{capabilityName, capabilityRequest: <bytes>}`.
5. Assert current behavior: request succeeds (200) and mock capability received `WorkflowOwner == "victim-owner-B"` — i.e., metadata was not rebound to the authenticated caller.
6. Expected secure behavior: the handler should either reject the mismatched metadata (403/400) or overwrite it with the authenticated caller's own identity before calling `Execute`.
