### Title
`LiquidityCap` (max-supply cap) recorded in `TokenConfig` is never enforced when PRC20 tokens are minted on inbound deposit - ([File: x/uexecutor/keeper/handler.go])

### Summary
`uregistry`'s `TokenConfig.LiquidityCap` is documented as "max supply cap for this token" and is required to be non-empty at registration time, but no code path in `x/uexecutor` (or elsewhere in the scoped Go modules) ever reads this field before minting PRC20 tokens for an inbound deposit. This is the direct analog of the reported "no cap for Minter" bug: a value that is supposed to bound minted supply exists in configuration but is not enforced at the mint call site.

### Finding Description
`TokenConfig` in `x/uregistry` carries a `LiquidityCap` field explicitly commented as the "max supply cap for this token": [1](#0-0) 

`ValidateBasic` for `TokenConfig` only checks that `LiquidityCap` is a non-empty string — it performs no numeric validation and, more importantly, the value is never consulted anywhere else in the codebase outside of this presence check: [2](#0-1) 

The actual PRC20 minting path for inbound deposits is `depositPRC20` (called from both the funds+payload and gas+payload inbound execution flows), which fetches the `TokenConfig`, resolves the PRC20 contract address, converts the raw amount string to a `big.Int`, and calls `CallPRC20Deposit` — with no reference to `LiquidityCap` or any supply check at all: [3](#0-2) 

`CallPRC20Deposit` then issues a module-originated `DerivedEVMCall` to `depositPRC20Token` on the `UniversalCore`/PRC20 handler contract, minting the exact requested amount with no supply-cap gate in the Go keeper: [4](#0-3) 

I was unable to locate the PRC20 Solidity contract source in this repository (it lives in the separate `push-chain-core-contracts` repo referenced by the README), so I cannot confirm whether the on-chain PRC20 contract itself enforces a max-supply check independent of `LiquidityCap`. A `maxSupply`/`MaxSupply` search across this repository returned no matches, and `LiquidityCap` is never referenced anywhere in `x/uexecutor`.

### Impact Explanation
Every ordinary user deposit into a registered source-chain token that the chain observes and votes to quorum (`MsgVoteInbound` → honest-UV finalization → `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` → `depositPRC20` → `CallPRC20Deposit`) mints the corresponding PRC20 amount with no check against the `LiquidityCap` recorded for that token in `x/uregistry`. Since `LiquidityCap` exists specifically to bound total minted PRC20 supply/protocol exposure per token, its complete non-enforcement means an unprivileged user can, purely through their own repeated deposits, cause total PRC20 supply for that asset to grow past the operator-configured cap — corrupting the PRC20 accounting invariant the registry field is meant to protect (`Required Impacts`: "corruption of PRC20 or native asset accounting"). This does not by itself let an attacker mint unbacked tokens (each mint still corresponds to a real observed source-chain inbound), but it defeats the intended risk-limiting control entirely, silently, and permanently for every token in the registry.

### Likelihood Explanation
High likelihood of occurrence given normal usage: any user (or set of users) can trigger this simply by depositing on a supported source chain repeatedly — no validator misbehavior, admin action, or privileged access is required. The gap is structural (the field is written but never read anywhere in the mint path), so it will trigger on every token for which the aggregate minted amount would otherwise need bounding.

### Recommendation
Enforce `TokenConfig.LiquidityCap` at the point of mint. Before calling `CallPRC20Deposit` in `depositPRC20` (`x/uexecutor/keeper/handler.go`), query the PRC20 contract's current `totalSupply` (or maintain a running minted-supply counter in `x/uregistry`/`x/uexecutor` state) and reject/cap deposits that would push total minted supply above `tokenConfig.LiquidityCap`. Parse `LiquidityCap` as a `big.Int` in `ValidateBasic` to guarantee it is numeric, and add an explicit unit/integration test asserting that a deposit exceeding the configured cap is rejected rather than silently minted.

### Proof of Concept
1. Register a `TokenConfig` via `MsgAddTokenConfig` with `LiquidityCap = "1000"` for a given source-chain asset.
2. Have an unprivileged user deposit source-chain funds worth more than `1000` units of that asset (or repeat smaller deposits that sum past the cap) and let honest validators vote the inbound to quorum via `MsgVoteInbound`.
3. Observe that `depositPRC20` → `CallPRC20Deposit` mints the full deposited amount with no rejection, and that the PRC20 contract's `totalSupply()` now exceeds the registered `LiquidityCap` — confirmable via `balanceOf`/`totalSupply` calls as used in existing tests such as: [5](#0-4)

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

func TestSolanaInboundFunds(t *testing.T) {
	prc20Address := utils.GetDefaultAddresses().PRC20USDCAddr
	prc20ABI, err := uexecutortypes.ParsePRC20ABI()
	require.NoError(t, err)

	t.Run("quorum reached executes solana FUNDS inbound and mints PRC20", func(t *testing.T) {
		app, ctx, vals, inbound, coreVals := setupSolanaInboundTest(t, 4, uexecutortypes.TxType_FUNDS)

		ueModuleAccAddress, _ := app.UexecutorKeeper.GetUeModuleAddress(ctx)
		recipient := common.HexToAddress(inbound.Recipient)

		// Check initial balance is 0
		res, err := app.EVMKeeper.CallEVM(ctx, prc20ABI, ueModuleAccAddress, prc20Address, false, nil, "balanceOf", recipient)
		require.NoError(t, err)
		balances, _ := prc20ABI.Unpack("balanceOf", res.Ret)
		require.Equal(t, int64(0), balances[0].(*big.Int).Int64())

		// Vote to quorum
		voteToQuorum(t, ctx, app, vals, coreVals, inbound)

		// Inbound should no longer be pending
		isPending, err := app.UexecutorKeeper.IsPendingInbound(ctx, *inbound)
		require.NoError(t, err)
		require.False(t, isPending)

		// PRC20 balance should equal inbound amount
		res, err = app.EVMKeeper.CallEVM(ctx, prc20ABI, ueModuleAccAddress, prc20Address, false, nil, "balanceOf", recipient)
		require.NoError(t, err)
		balances, _ = prc20ABI.Unpack("balanceOf", res.Ret)
		expected := new(big.Int)
		expected.SetString(inbound.Amount, 10)
		require.Equal(t, 0, balances[0].(*big.Int).Cmp(expected))
	})
