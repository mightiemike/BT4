## Finding: `ensure_match_transaction_info` never validates the state-checkpoint root hash, allowing state-corruption to pass replay-verification

### Title
Replay-verify integrity check silently skips state-checkpoint (Merkle) root comparison, letting corrupted committed state pass as valid — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole function used by every replay/verification tool in the codebase (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`) to assert that a freshly re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain/in a backup. The function checks status, gas used, write-set hash, and event-root hash, but by the code's own admission it never checks `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), the Sparse-Merkle/Jellyfish-Merkle root that commits the *entire resulting account state* at a checkpoint boundary. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` builds `expected_txn_status`, compares `gas_used`, recomputes `write_set_hash = CryptoHash::hash(self.write_set())` against `txn_info.state_change_hash()`, and recomputes the event-root hash — but the function returns `Ok(())` right after a comment that explicitly states the state-checkpoint hashes are ignored: [2](#0-1) 

The `state_checkpoint_hash` carried in `TransactionInfo` is the authenticated commitment to the post-transaction account-state tree (the Jellyfish Merkle root), separate from the per-transaction write-set hash. A transaction's `write_set` can be individually correct (same write-set hash, same events, same gas) while the *aggregate* state tree that the checkpoint hash commits to is wrong — e.g., due to a bug in JMT construction/merklization, a storage-layer corruption, hot-state/position-state divergence, or a backup archive that was tampered with or produced by a buggy prior version. None of the call sites that use `ensure_match_transaction_info` as their integrity oracle perform any supplementary state-root check:

- `execution/executor/src/chunk_executor/mod.rs::verify_execution` uses only this function to validate chunk-executor replay against expected `TransactionInfo`s. [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the core of the mainnet/testnet "replay-verify" archive-integrity pipeline referenced by `testsuite/replay-verify/README.md`, also relies solely on this function. [4](#0-3) 

So the one dedicated safety net whose entire purpose is to catch "committed state differs from the correct VM result" (exactly the State-Integrity Gate's first listed impact) structurally cannot detect that class of bug, because it never re-derives/compares the state-checkpoint root.

### Impact Explanation
Replay-verify tooling (`replay_on_archive`, `chunk_executor::verify_execution`, `aptos-debugger`) is the primary mechanism operators and the Aptos Foundation use to confirm that backed-up/archived ledger data is consistent with correct VM execution before it is trusted for restore, fast-sync bootstrapping, or auditing. Since `ensure_match_transaction_info` never compares `state_checkpoint_hash`, a corrupted or incorrect account-state snapshot (wrong JMT root) bundled with an otherwise-correct write set/events/gas/status can pass every "verify" pass silently. This means state divergence — the highest-severity class explicitly called out in the gate ("Committed state that differs from the correct VM result or corrupts durable ledger data" and "Wrong accumulator root ... accepted as valid") — is exactly the failure mode this comparator is blind to. Any restore or replay-verify workflow built on top of `ensure_match_transaction_info` provides false assurance of state correctness.

### Likelihood Explanation
This is not a hypothetical: the gap is self-documented by the authors in the surrounding `// TODO(trading-native):` comment, confirming the maintainers are aware the comparator "ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." The comment scopes the acknowledged risk to `position_state_checkpoint_hash` (guarded behind the unreleased `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature), but the code omits validation of `state_checkpoint_hash` and `hot_state_checkpoint_hash` unconditionally — these are already live/committed today for every state-checkpoint transaction, independent of that feature flag. No caller of `ensure_match_transaction_info` adds any compensating state-root check, so the gap is live in current replay-verify usage, not merely in an unreleased trading-native path.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the state-checkpoint root (and hot-state/position-state roots when applicable) from the resulting state and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, mirroring the pattern already used for `write_set_hash` and `event_root_hash`. Until this is implemented, replay-verify and chunk-executor verification cannot be relied upon to catch state-root corruption, and should not be treated as a full state-integrity guarantee in operational runbooks.

### Proof of Concept
1. Take any backed-up chunk of `(Transaction, TransactionInfo, WriteSet, Vec<ContractEvent>)` consumed by `storage/db-tool/src/replay_on_archive.rs`.
2. Craft (or let a real storage bug produce) a `TransactionInfo` whose `state_checkpoint_hash` does not match the JMT root that would actually result from applying the given, correct `write_set` on top of the correct prior state (i.e., the write set/events/gas/status are all genuinely correct, but the checkpoint root field has been altered/corrupted).
3. Run `replay_on_archive`'s `execute_and_verify` (`storage/db-tool/src/replay_on_archive.rs:349-416`) against this data: the VM re-executes the transaction, produces a matching write-set hash, event-root hash, gas, and status, so `ensure_match_transaction_info` returns `Ok(())` and the chunk is reported as verified — despite the checkpoint root being wrong.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
