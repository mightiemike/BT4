### Title
Stale market-level liquidity-index cache is not invalidated by vault-level `socialize-debt` write-downs, causing misleading collateral valuation for subsequent liquidations in the same batch/block - ([File: local-testing/contracts/market/market.clar])

### Summary
`market.clar` caches each vault's borrow/liquidity index (`index`, `lindex`) per `(stacks-block-time, aid)` in `index-cache-` so that repeated price resolutions for zTokens within the same block avoid extra cross-contract calls [1](#0-0) . The cache is populated via `accrue-and-cache`, which calls the vault's public `accrue` and stores the resulting `{index, lindex}` [2](#0-1) . However, when a liquidation leaves a borrower with no collateral, `market.clar` triggers bad-debt socialization by directly calling the vault's `socialize-debt`, which mutates the vault's `lindex` var in place, bypassing `accrue-and-cache`/`index-cache-` entirely [3](#0-2) . Because `index-cache-` is keyed only by block timestamp and asset id, any zToken price resolution for that same asset later in the same transaction (e.g., a subsequent position processed by `liquidate-multi`) still reads the old, pre-write-down `lindex` from the map, not the vault's real, reduced value.

### Finding Description
`resolve-ztoken` values zTokens purely from the market's cached copy of the vault's liquidity index: `(get lindex cached)` where `cached = (get-cached-indexes aid)` — a plain `map-get?` on `index-cache-`, with no re-accrual [1](#0-0) . This cache is only ever refreshed by `accrue-and-cache`, and only when the cache key `{timestamp: stacks-block-time, aid}` is missing [2](#0-1) .

Bad-debt socialization during liquidation does not go through this path. In `liquidate`, once a borrower's collateral is exhausted, `market.clar` folds over the borrower's remaining debt list and calls a per-asset socialization helper, which invokes the vault's `socialize-debt` [4](#0-3) . The vault's `socialize-debt` writes the new, reduced `lindex` directly with `var-set`, based on the proportional loss to `total-assets` [3](#0-2) . This state mutation happens purely inside the vault contract; nothing updates or invalidates `index-cache-` in `market.clar` for that `(timestamp, aid)` entry.

`liquidate-multi` processes many borrower liquidations within a single transaction/block via `map call-liquidate positions`, explicitly noting that failed items don't abort the batch [5](#0-4) . If an earlier position in the batch has already caused `accrue-and-cache` to populate `index-cache-` for asset X's `lindex` (e.g., during health/LTV evaluation), and that same position then triggers `socialize-debt` on vault X (write-down), the market-level cache for X still holds the old, higher `lindex`. Any later position in the same batch/block whose collateral or debt valuation calls `resolve-ztoken` for asset X will use this stale, inflated `lindex`, overstating that zToken's USD value — exactly the "value bound before an invalidating event, then reused after that event" pattern.

This mirrors the H-12 analog: entry price (bound at open, not decreased on close) stays stale and misleads pool valuation until later use. Here the market's cached `lindex` (bound at first accrual in the block, not decreased on socialization) stays stale and misleads collateral/health valuation for later same-block operations.

### Impact Explanation
Health checks, LTV evaluation, and liquidation seizure amounts throughout `market.clar` all depend on `resolve-ztoken`/`get-cached-indexes` for zToken pricing. Using a stale, inflated `lindex` after a real loss write-down means:
- A borrower whose zToken-X collateral value is overstated may incorrectly pass a health check that should fail, or a liquidator may seize less collateral than the borrower's true post-write-down debt warrants.
- Because socialization exists specifically to spread realized bad debt losses across LP suppliers, mispricing zToken-X immediately afterward in the same block undermines the very LTV/liquidation math meant to protect protocol solvency — creating additional uncompensated bad debt and risking protocol insolvency.

This lands in the in-scope **protocol insolvency / temporary freezing of funds** impact category, since it directly corrupts collateral valuation used to gate borrow, withdraw, and liquidation decisions.

### Likelihood Explanation
This requires: (a) multiple borrowers holding or being collateralized/debited in the same asset X being liquidated within the same `liquidate-multi` transaction (same `stacks-block-time`), and (b) at least one of them triggering bad-debt socialization for X before a later position's valuation reads the market's cached index for X. Liquidation cascades where several undercollateralized borrowers share the same debt/collateral asset are a realistic scenario during sharp price moves, making the ordering achievable by any liquidator constructing the `liquidate-multi` batch, or by chance when multiple liquidators/liquidations land in the same block.

### Recommendation
When `socialize-debt` write-downs occur on a vault, the market contract should invalidate or immediately refresh the corresponding `index-cache-` entry for that `(stacks-block-time, aid)` (e.g., by re-calling `accrue-and-cache`/re-querying the vault's post-socialization index right after the socialization call, or by having socialization flow through the same cache-write path used by `accrue-and-cache`) so that all subsequent price resolutions within the same block use the updated `lindex`.

### Proof of Concept
1. Attacker/liquidator submits a single `liquidate-multi` call containing two independent unhealthy positions, Borrower A and Borrower B, both of which hold zToken-X (e.g., zUSDC) either as collateral or reference the same vault X for debt.
2. During processing of Borrower A (first in the list), `market.clar`'s health/LTV evaluation path calls `accrue-and-cache` for asset X, populating `index-cache-{timestamp: T, aid: X}` with the current `lindex` (e.g., 1.10).
3. Borrower A ends up with no remaining collateral after seizure, triggering bad-debt socialization: the vault's `socialize-debt` is called and writes `lindex` down to a lower true value (e.g., 1.05) via `var-set` [6](#0-5) .
4. `map` continues to Borrower B within the same transaction/timestamp `T`. Borrower B's zToken-X collateral is priced via `resolve-ztoken` → `get-cached-indexes X`, which still returns the cached `lindex = 1.10` from step 2, not the corrected `1.05`.
5. Borrower B's collateral value is overstated by ~5%, potentially allowing an unhealthy Borrower B position to pass the health check and avoid or reduce liquidation, or causing the liquidator to under-seize relative to Borrower B's true risk.
