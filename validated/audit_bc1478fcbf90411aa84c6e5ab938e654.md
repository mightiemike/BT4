Based on my research, I found a strong analog in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`, in `build_updated_stake_reward` and `test_delegation_adjustment_at_distribution`, which directly mirrors the "unfavorable exchange" bug class: computing a result from an absolute post-transfer balance rather than tracking the delta between a pre-recorded/expected amount and what's actually present.

### Title
Stake reward crediting relies on absolute stake-account balance rather than the pre/post delta, allowing an externally inflated balance to silently alter delegation math - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
`Bank::build_updated_stake_reward` credits `partitioned_stake_reward.inflation.stake_reward` and `block_reward` onto the stake account via `checked_add_lamports`, then derives/asserts the new delegation amount using `account.lamports()` and reward fields computed earlier (in the calculation phase) from the account's balance *at that time*. Between the calculation phase and the distribution phase, arbitrary lamports can be transferred into the stake account (a stake account remains owned by the stake program but is still a normal `AccountSharedData` that can receive a `system_instruction::transfer`, as demonstrated in the existing test). Because the reward/delegation math is derived from the account's absolute balance rather than a tracked pre/post-transfer delta (analogous to the reported "unfavorable exchange" pattern of using `self.balance()` instead of `after - before`), a balance injected between calculation and distribution changes the effective outcome of the distribution logic (e.g. `adjust_delegation_for_rent`, delegation capping/floor decisions) using stale-vs-actual balance assumptions.

### Finding Description [1](#0-0) 
computes `new_stake`/delegation state from `partitioned_stake_reward.inflation.stake` (computed during the earlier calculation phase) and, when `adjust_delegations_for_rent` is set, calls `adjust_delegation_for_rent` using `account.lamports()` — the *current, absolute* balance at distribution time — as an input, rather than strictly using the previously-computed pre-balance plus the known reward delta: [2](#0-1) 

The existing test `test_delegation_adjustment_at_distribution` explicitly demonstrates and accepts this behavior: extra lamports (`1_000_000_000`) are transferred into the stake account *after* reward calculation but *before* distribution, and the resulting delegation reflects only the reward amount while the account balance itself silently absorbs the injected lamports: [3](#0-2) 

This mirrors the reported bug class precisely: the code computes an outcome (delegation/rent-adjustment amount) using a snapshot of "current absolute balance" taken at a different point in time than when the effect is applied, instead of computing strictly from the recorded before/after delta of the operation being processed. If `adjust_delegations_for_rent` is active and any lamports are added to a stake account between the calculation and distribution phases of partitioned epoch rewards (e.g., via a normal transfer instruction targeting the stake account, which is permitted because stake accounts are just regular accounts with system-transferable lamports), `adjust_delegation_for_rent`'s inputs no longer correspond to the value that was used to compute rewards, potentially causing delegation stake to be adjusted using a balance that does not solely reflect the tracked reward being distributed.

### Impact Explanation
This falls under "silent balance change" divergence: the stake account's final lamports and its internal delegation-stake field can diverge from what the reward-calculation phase computed, because the code path uses the account's absolute balance at store time (`account.lamports()`) rather than deriving amounts purely from the tracked pre-reward balance plus the known reward. In practice this can affect stake activation/warmup accounting (`delegation.stake`) inconsistently with actual funds, which could propagate into stake-weighted consensus calculations over subsequent epochs.

### Likelihood Explanation
Requires that `relax_post_exec_min_balance_check` (the feature gating `adjust_delegations_for_rent`) is active, and that a transfer lands on a specific stake account between the reward-calculation and reward-distribution phases of the same epoch boundary — both of which are attacker/user-controllable (any account holder can send lamports to any stake account pubkey they know), and the "vulnerable window" spans multiple blocks (`REWARD_CALCULATION_NUM_BLOCKS`) during epoch-boundary reward distribution, giving a realistic opportunity.

### Recommendation
Compute reward-driven delegation adjustments from the pre-recorded balance/stake at the time of the calculation phase plus the known reward delta, rather than reading `account.lamports()` (the current absolute balance) at distribution time in `adjust_delegation_for_rent`'s call site. This mirrors the report's own recommendation: derive amounts from the difference between the value captured at calculation time and the value at application time, rather than trusting an absolute balance snapshot that could have changed for unrelated reasons.

### Proof of Concept
1. Set up a stake account and trigger the epoch-boundary calculation phase for partitioned rewards (`relax_post_exec_min_balance_check` feature active), producing a `PartitionedStakeReward` for the account with a known `stake_reward`.
2. Before the distribution phase runs (within the `REWARD_CALCULATION_NUM_BLOCKS` window), submit a normal `system_instruction::transfer` that adds lamports directly to the stake account's pubkey.
3. Allow `distribute_epoch_rewards_in_partition` / `store_stake_accounts_in_partition` to run; observe (as in `test_delegation_adjustment_at_distribution`, lines 1263-1292 above) that `adjust_delegation_for_rent` and the final stored account state are computed using `account.lamports()`, which now includes the externally injected balance, rather than solely the pre-transfer balance the reward calculation was based on.
