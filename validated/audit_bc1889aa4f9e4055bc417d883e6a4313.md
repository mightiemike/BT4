### Title
Uncontrolled Resource Consumption via Unbounded Webhook Body Buffering Before HMAC Validation - (File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts)

### Summary
The Tendermint advisory describes a client consuming unbounded response/request body content without size limits, allowing resource exhaustion. In `shopify-app-js`, the webhook authentication entrypoint reads the *entire* raw HTTP request body into memory via `await request.text()` before any HMAC/signature verification is performed, and does so with no size cap, for a fully anonymous, unauthenticated POST request.

### Finding Description
`authenticateWebhookFactory` in [1](#0-0)  only checks that the HTTP method is `POST` before calling `const rawBody = await request.text();` — this buffers the complete request body into memory *before* `api.webhooks.validate({rawBody, rawRequest: request})` performs any HMAC check. The same unauthenticated-buffer-before-verify pattern exists in the React Router equivalent (`packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts`).

The library-level `validateFactory`/`validateHmacFromRequestFactory` path in [2](#0-1)  also assumes `rawBody` is already a fully materialized string passed in by the caller — there is no streaming validation, no `Content-Length` pre-check, and no maximum body size enforced anywhere in the webhook processing pipeline (`packages/apps/shopify-api/lib/webhooks/process.ts`). Nothing in the library or the framework adapters imposes an upper bound on the size of the body that gets buffered from an anonymous request before its authenticity is established.

### Impact Explanation
Because the webhook callback URL is a public, unauthenticated HTTP endpoint (any external actor can POST to it, not just Shopify), an attacker can send arbitrarily large request bodies. Each request causes the app server to fully buffer that body into memory via `request.text()` prior to rejecting it for a bad HMAC. Repeated or concurrent requests with large bodies can exhaust server memory/CPU, resulting in denial of service of the app's webhook (and by extension, auth-adjacent) handler — directly analogous to the CWE-400 pattern in the reported CVE.

### Likelihood Explanation
The webhook endpoint is deliberately exposed as public/unauthenticated by design (Shopify needs to be able to call it without prior session), so no privileged access or secret knowledge is required to reach this code path — a plain anonymous HTTP POST suffices. This raises likelihood, though actual exploitability depends on the surrounding HTTP server/framework (e.g., Remix/Node/React Router) not already enforcing a global body-size limit; the shopify-app-js library itself provides no such guard.

### Recommendation
Enforce a maximum allowed request body size (checking `Content-Length` and/or capping bytes read via a bounded stream reader) before or while buffering the webhook body, both in the framework-specific `authenticate.ts` handlers (`packages/apps/shopify-app-remix`, `packages/apps/shopify-app-react-router`) and as a documented requirement/helper in `packages/apps/shopify-api/lib/webhooks/validate.ts` and `process.ts`, rejecting oversized requests with a `413 Payload Too Large` before HMAC verification.

### Proof of Concept
1. Identify an app's public webhook callback URL (e.g., `/webhooks`).
2. Send an anonymous `POST` request with a very large body (e.g., several hundred MB) and an invalid/absent HMAC header, repeated concurrently.
3. Observe that `authenticateWebhookFactory` buffers each full body into memory via `request.text()` prior to the HMAC check in `validate()` failing, causing elevated memory/CPU consumption on the app server proportional to attacker-controlled payload size, with no library-enforced cap.
