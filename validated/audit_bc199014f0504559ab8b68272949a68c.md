### Title
Unbounded delegated-resource index growth enables memory/CPU DoS via anonymous RPC query - (chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix()` performs an unbounded `prefixQuery` over the `FROM_PREFIX`/`TO_PREFIX` (and V2 equivalents) key space for a single address and loads *every* matching entry into memory before sorting, with no cap on the number of delegate relationships an account can accumulate. [1](#0-0) 

### Finding Description
The store keys resource-delegation index entries as `PREFIX + fromAddress + toAddress` and `PREFIX + toAddress + fromAddress`. [2](#0-1) 
Every call to `FreezeBalanceV2`/delegate-resource transactions (a normal, cheaply broadcastable transaction) adds two new entries via `delegate`/`delegateV2`, with no limit on how many distinct counterparties (or repeated timestamps) a single address can accumulate. `getIndex`/`getV2Index` then call `getWithPrefix`, which does `this.prefixQuery(key).values()` — collecting *all* matching rows for that address into a `List`, sorting them, and materializing full account lists. [3](#0-2) 
`prefixQuery` in the base store performs an unbounded stream collection over the underlying LevelDB/RocksDB prefix scan with no size limit. [4](#0-3) 
This index is directly reachable from anonymous, unauthenticated gRPC calls `GetDelegatedResourceAccountIndex` / `GetDelegatedResourceAccountIndexV2`, exposed via `RpcApiService`. [5](#0-4) [6](#0-5) 

This is the same bug class as the Frax `removeValidator()`/`removeMinter()` finding: an attacker-growable, unbounded array/index is iterated in full on every access with no pagination or cap, so cost scales linearly (or worse, with sorting, O(n log n)) with attacker-controlled data size.

### Impact Explanation
An attacker who controls (or creates) an address can send a large number of cheap `UnfreezeBalanceV2`/`DelegateResource` transactions to many distinct counterparty addresses (or repeatedly to the same address at different timestamps, which still creates separate keyed rows), inflating the from/to index for that address. Any subsequent call to `GetDelegatedResourceAccountIndex(V2)` for that address — which any anonymous client can trigger — forces the full-node/solidity-node to scan, deserialize, collect, and sort the entire accumulated set in memory on every single query. Because the RPC handler directly forwards to `wallet.getDelegatedResourceAccountIndex(V2)` without applying any limit or pagination, this results in a per-query CPU/memory spike, and if scaled up sufficiently, node slowdown or OOM — a denial-of-service against the queried node's RPC service, and since this can be repeated against multiple full nodes, it degrades service availability network-wide.

### Likelihood Explanation
Medium. Unlike the original Solidity finding, gas cost does not bound this loop (there is no "gas limit" concept for handling a gRPC query on a full node); the cost is instead CPU time and memory on the responding node, so the impact is a query-time DoS rather than a failed on-chain state transition. The attack requires the attacker to actually perform many delegate transactions (each incurs real TRX freeze costs and transaction fees), which raises the cost of the attack somewhat, but delegation of small resource amounts to many distinct addresses is a cheap, repeatable, permissionless operation available to any account, and no protocol-level cap exists on the number of delegation relationships per account.

### Recommendation
- Introduce a maximum number of delegation relationships (from/to) tracked per address, enforced in `delegate`/`delegateV2`, and reject/limit further delegations once the cap is reached.
- Add pagination/limit parameters to `getWithPrefix`/`prefixQuery` (similar to `getPriceKeysList`'s `count`/`totalCount` pattern used elsewhere in the codebase) so `GetDelegatedResourceAccountIndex(V2)` cannot force an unbounded full scan in a single RPC call.
- Consider bounding `prefixQuery` itself in `TronStoreWithRevoking` with an optional max-results parameter to protect all current and future callers.

### Proof of Concept
1. From an attacker-controlled account `A`, repeatedly broadcast `FreezeBalanceV2`+delegate-resource transactions delegating a minimal amount of bandwidth/energy to N distinct freshly generated addresses `B1..BN` (each transaction is a normal, permissionless, low-cost broadcast transaction).
2. Each such delegation inserts two rows into `DelegatedResourceAccountIndexStore` under `V2_FROM_PREFIX + A + Bi` and `V2_TO_PREFIX + Bi + A`. [7](#0-6) 
3. Once N is large (e.g., tens of thousands), call the anonymous gRPC `GetDelegatedResourceAccountIndexV2` with `A`'s address. [8](#0-7) 
4. The node performs an unbounded `prefixQuery` collecting and sorting all N entries for `A` in `getWithPrefix`, consuming CPU/memory proportional to N on every repeated call, which can be issued at high frequency by the same anonymous caller to sustain load on the target node. [1](#0-0)

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
