### Title
Post-validation mutation of `output_data_receivers` lets a single transaction produce and forward a receipt exceeding `max_receipt_size`, bypassing the state-witness size budget - ([File: test-loop-tests/src/tests/max_receipt_size.rs])

### Summary
The TensorFlow advisory describes a `CHECK`-fail class of bug: an operation validates one shape/size, then a subsequent, unvalidated step is performed with attacker-controlled dimensions that were never re-checked, producing an out-of-bounds state that the guard rails don't catch. The nearcore analog is a receipt-size validation bypass, already flagged in the codebase as a known, currently-unfixed bug (near/nearcore#12606): a `FunctionCall` receipt is validated against `max_receipt_size` when it is created, but `output_data_receivers` is appended to it *after* that validation, when the receipt is linked into a promise DAG (`promise_then`). This pushes the final serialized receipt above `max_receipt_size` without the increase ever being re-validated.

### Finding Description
Receipt-size validation is enforced in `runtime/runtime/src/verifier.rs::validate_receipt`, gated on `max_receipt_size` from `LimitConfig` [1](#0-0)  — but this check runs against the receipt as constructed by `ReceiptManager` at the time actions are appended in `runtime/runtime/src/receipt_manager.rs`, before `output_data_receivers` are added by a later `promise_then`/`promise_and` call in the same or a subsequent host-function call (`output_data_receivers` accumulate via `receipt_manager.rs`, `runtime/runtime/src/lib.rs`, and `runtime/runtime/src/actions.rs`) [2](#0-1) .

The exact reachable path is documented in the test comment: a contract creates promise `C` sized to exactly `max_receipt_size` (computed via `borsh::object_length`), which passes the size check; a subsequent `promise_then` links a callback `B` to `C`, which appends an `output_data_receivers` entry to `C`'s receipt — pushing its serialized size above the limit without a second validation pass: [3](#0-2) 

The test explicitly documents this as a known, unfixed defect (`See https://github.com/near/nearcore/issues/12606`) rather than a hypothetical: [4](#0-3) 

An analogous case exists for oversized data receipts produced by `value_return`, where the returned value is wrapped in a `DataReceipt` whose size is likewise not re-validated after the fact: [5](#0-4) 

Both are single-transaction/single-contract-call reachable: the attacker is simply a contract deployer/caller crafting promise DAGs with `promise_create`, `promise_then`, and `value_return` — no validator or peer privilege required. This is exactly the "validate one shape, mutate afterward without re-validating" pattern behind the TensorFlow `RandomPoissonV2` `CHECK`-fail (shape/rate validated, then large derived tensor allocated without a bound).

### Impact Explanation
`max_receipt_size` (4 MiB) exists specifically to bound the `ChunkStateWitness` size, which the project targets at ~21 MiB total (`docs/misc/state_witness_size_limits.md`) [6](#0-5) . A receipt that silently exceeds this bound after validation defeats that budget enforcement: it can inflate outgoing/incoming receipt proofs and state witnesses beyond the sizes chunk producers and validators are supposed to guarantee, which the size-limit doc states is required for correctness of stateless validation (chunk validators re-derive and must match the producer's bounded work). Because this bypasses a hard limit that other protocol invariants (bandwidth scheduling caps, witness distribution assumptions) are built on top of, it functions as a limit/quota bypass reachable from a single unprivileged transaction, and repeated exploitation could be used to reliably inflate witness/proof sizes beyond intended bounds. The test suite confirms the runtime does not crash when this occurs (so it is not a direct halt), but the validation gap itself is a confirmed, open, transaction-triggered bypass of a security-relevant size limit.

### Likelihood Explanation
High: exploitation requires only a single account calling a deployed contract with a crafted argument size (`max_receipt_size_promise_return_method1`) and no elevated privileges; the DAG/promise pattern (`promise_create` → `promise_then`) is a normal contract capability. The bug is already reproduced and tracked upstream as near/nearcore#12606, and remains unfixed as of this codebase snapshot, per the test comments.

### Recommendation
Re-validate receipt size (against `max_receipt_size`) after any post-construction mutation, specifically after `output_data_receivers` are appended during `promise_then`/`promise_and` linking, and after wrapping return values into `DataReceipt` from `value_return`. The check should occur at the point the receipt is finalized for storage/dispatch (e.g., in `ReceiptManager`'s finalize path or in `runtime/runtime/src/lib.rs` right before receipts are queued as outgoing/local), not only at initial action-append time.

### Proof of Concept
The existing test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` (lines 129–208) is itself the PoC: it deploys `near_test_contracts::rs_contract()`, computes an `args_size` such that receipt `C` is exactly `max_receipt_size` bytes, calls `max_receipt_size_promise_return_method1` to build the DAG `A -then-> B`, have `A` spawn `C` and `promise_return` it (changing the DAG to `C -then-> B`), which appends `output_data_receivers` to `C` and pushes it over `max_receipt_size` without the size check firing — verified via `assert_oversized_receipt_occurred`, which scans committed blocks for a receipt whose `borsh::object_length` exceeds `max_receipt_size` [7](#0-6) .

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
