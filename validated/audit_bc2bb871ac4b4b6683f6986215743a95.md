### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` enables O(n) cost amplification and account-level DoS on freeze/delegate/unfreeze actuators - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
`FreezeBalanceActuator`, `DelegateResourceActuator`, `UnfreezeBalanceActuator`, and `UnDelegateResourceActuator` maintain a per-account `DelegatedResourceAccountIndexCapsule` whose `toAccounts`/`fromAccounts` repeated fields grow every time an account delegates resources to a new, distinct receiver address. There is no cap on the number of distinct receivers, and every subsequent freeze/delegate/unfreeze/undelegate transaction from (or to) that account performs linear-time operations (`contains`, `remove`, full re-serialization via `setAllToAccounts`/`setAllFromAccounts`) over this list. This mirrors the reported `pendingStakes` bug class: an attacker can cheaply and unboundedly grow a list that is later iterated/scanned by protocol logic, degrading performance and potentially causing failures for that account's future operations.

### Finding Description
In legacy (non-optimized) delegation mode, `FreezeBalanceActuator.delegateResource` appends to `DelegatedResourceAccountIndexCapsule` for both the owner and receiver without any bound: [1](#0-0) 

The append operation (`addToAccount`/`addFromAccount`) simply concatenates to the protobuf repeated field with no size check: [2](#0-1) 

When resources are later unfrozen, `UnfreezeBalanceActuator` performs a linear `remove` on a copy of the (potentially huge) list, followed by `setAllToAccounts`, which rebuilds the entire protobuf list: [3](#0-2) 

A test in the repo already demonstrates the pattern of growing this list to over 100 entries via repeated `FreezeBalanceContract` calls to distinct receivers, without any validation rejecting large lists: [4](#0-3) 

No check on `toAccountsList().size()` or `fromAccountsList().size()` exists anywhere in the validate() paths of `FreezeBalanceActuator`, `DelegateResourceActuator`, `UnfreezeBalanceActuator`, or `UnDelegateResourceActuator` (confirmed by search across the codebase — no `MAX_DELEGATE`/size-limit constants exist for these lists). `DelegateResourceActuator.calcFee()` returns 0, meaning growing this list costs nothing beyond the resource frozen (which can be the network minimum of 1 TRX), and delegation to many distinct receiver addresses (e.g. attacker-controlled throwaway accounts) is cheap.

### Impact Explanation
Each `DelegatedResourceAccountIndexCapsule` is stored as a single serialized value per account key in `DelegatedResourceAccountIndexStore`. As the `toAccounts`/`fromAccounts` lists grow unboundedly:
- Every subsequent freeze/delegate/unfreeze/undelegate operation involving that account must deserialize the full (growing) protobuf object, perform linear scans (`contains`, `remove`), and re-serialize/store the full list again — turning what should be O(1) per-transaction work into O(n).
- This increases per-block processing time for any actuator touching that account, and increases the on-disk/storage footprint tied to a single key, which can degrade node performance and slow down block validation for all nodes replaying the chain (not just the attacker's node), since this is deterministic state-transition logic executed by every full node.
- This does not directly halt block gas limit like TVM code (java-tron's account-level actuators aren't gas metered per-array-element the way EVM opcodes are), so the severity is a performance/DoS degradation via disk I/O and CPU rather than an outright unrecoverable freeze of funds. Funds themselves are not "frozen" the way the LiquidationPool's `pendingStakes` funds are, since TRX unfreezing for a specific delegation is keyed by `(owner, receiver)` pair in `DelegatedResourceStore`, not by iterating the whole index list to locate and release balance.

### Likelihood Explanation
The attack requires only that an attacker (or any account) issues many `FreezeBalanceContract`/`DelegateResourceContract` transactions to distinct receiver addresses. This is unprivileged, requires only paying to freeze the network minimum of 1 TRX (temporarily locked, not spent) per distinct receiver, and `calcFee()` for delegation actuators returns 0. Given TRX is refunded on unfreeze, the ongoing cost to the attacker is primarily opportunity cost of locked TRX for the freeze period, making this a plausible, low-cost griefing vector, though it primarily affects the attacker's own account state (and its counterparties') rather than the entire chain, limiting blast radius compared to the original `pendingStakes` report where a shared array is spammed and blocks *all* stakers.

### Recommendation
- Enforce a reasonable maximum number of distinct entries in `toAccountsList`/`fromAccountsList` (and reject `FreezeBalanceContract`/`DelegateResourceContract` transactions that would exceed it) similar to the `MAX_VOTE_NUMBER` cap already used for `VoteWitnessContract`.
- Consider migrating fully to the "optimized" delegate index model (`delegatedResourceAccountIndexStore.delegate`/`delegateV2`, which use per-`(from,to)` keys rather than a single growing list) as the default/mandatory model, and disable/deprecate the legacy unbounded-list mode.
- Where linear scans (`contains`, `remove`) are unavoidable, bound the list size at write time rather than relying only on downstream consumers to survive arbitrarily large lists.

### Proof of Concept
Not independently executed; based on static analysis of `FreezeBalanceActuator.delegateResource` (lines 319–345) and the existing test `testMultiFreezeDelegatedBalanceForBandwidth`, which already demonstrates growing `ownerIndexCapsule.toAccountsList()` to 101 entries by issuing 100 `FreezeBalanceContract` delegations to distinct freshly generated `ECKey` addresses followed by a 101st delegation — showing the list has no enforced upper bound and grows linearly with attacker-supplied distinct receiver addresses: [4](#0-3) 

Note: I could not fully verify the exact quantitative performance/storage impact (e.g., how large the list would need to grow to cause measurable node slowdown, or whether `TronStoreWithRevoking` imposes any implicit value-size limits) within the available static index; this would require running the code or reviewing storage engine limits (e.g., LevelDB/RocksDB value size handling) directly in a live environment.

  public void removeToAccount(ByteString toAccount) {
    if (getToAccountsList().contains(toAccount)) {
      List<ByteString> toList = new ArrayList<>(getToAccountsList());
      toList.remove(toAccount);
