### Title
Unauthenticated `/sessions` login endpoint leaks account existence and MFA-enrollment status via distinct error text - ([File: core/sessions/localauth/orm.go])

### Summary
`orm.CreateSession` returns three distinguishable error/response bodies — `"Invalid email"`, `"Invalid password"`, and (when the password is correct) a raw JSON WebAuthn challenge — all surfaced verbatim to the client by `SessionsController.Create` via `jsonAPIError`/`c.JSON`. While a constant-time comparison is used for the email check (to mitigate *timing* leaks), the response *content* itself still differs per case, so an unauthenticated caller can trivially distinguish "email doesn't exist" from "email exists, wrong password" from "email exists, correct guess, MFA required" purely by reading the response body, without any timing analysis.

### Finding Description
In `core/sessions/localauth/orm.go`, `CreateSession` (lines 144-199):
- If the submitted email doesn't match the looked-up user, it returns `pkgerrors.New("Invalid email")` [1](#0-0) .
- If the email matches but the password is wrong, it returns `pkgerrors.New("Invalid password")` [2](#0-1) .
- If email+password are correct and the account has WebAuthn tokens enrolled, it returns the serialized WebAuthn challenge JSON as the error string itself: `pkgerrors.New(string(j))` [3](#0-2) .

These three outcomes have completely distinct, easily distinguishable text/shape. The comment at lines 152-153 states the ordering ("email and password check first") is meant only to avoid an *extra DB lookup* that would leak MFA-enrollment via *timing* — it does not (and cannot) prevent the *content* leak, since the returned error string itself differs by case and is echoed straight to the HTTP client.

`core/web/sessions_controller.go`'s `Create` handler passes this error straight through as the HTTP body with `jsonAPIError(c, http.StatusUnauthorized, err)` [4](#0-3) , and `jsonAPIError` wraps `err.Error()` into the JSON:API error body verbatim [5](#0-4) . All three cases share the same HTTP status code (401), but the body text/shape trivially discloses account state — no timing side channel is even needed.

Additionally, `SessionsController.Create` independently calls `GetUserWebAuthn(ctx, sr.Email)` *before* any password check, purely to decide whether to populate `sr.SessionStore`/`sr.WebAuthnConfig` [6](#0-5)  — though this call itself doesn't directly leak to the response, it duplicates the same DB query `CreateSession` performs later, and confirms WebAuthn state is queried for arbitrary attacker-supplied emails without any password verification precondition.

### Impact Explanation
This allows an unauthenticated, unprivileged attacker to enumerate valid Chainlink node operator account emails at the login endpoint (`POST /sessions`), which is a classic precursor to targeted credential-stuffing and password-spraying attacks. Once a valid email/correct-password combination is found, the attacker also directly learns whether MFA/WebAuthn is enrolled (from the shape of the response — full session vs. WebAuthn challenge JSON), informing whether MFA-bypass techniques need to be attempted. This does not by itself grant unauthorized access, but it is a genuine confidentiality/information-disclosure weakness in the authentication flow that materially aids account takeover of the node's admin UI/API.

### Likelihood Explanation
Fully exploitable by any unauthenticated network client with access to `POST /sessions`: no privileges, no special access, and no race conditions are required. It's a deterministic, repeatable oracle — every request against a real vs. fake email returns a different, static string ("Invalid email" vs "Invalid password"), so likelihood is high and requires no timing measurement.

### Recommendation
Return a single generic error (e.g., `"Invalid email or password"`) with the same static text and status code for both the "no such user" and "wrong password" branches, and avoid ever returning the raw WebAuthn challenge JSON as an `error` value distinguishable from other failure text at the same call site — e.g., use a typed/sentinel result (or a dedicated success path with a `mfa_required` flag) instead of encoding challenge JSON inside `pkgerrors.New(string(j))`, so failure/challenge/success responses aren't trivially distinguishable to an attacker who hasn't yet supplied a correct password.

### Proof of Concept
Integration test plan (extending `core/sessions/localauth/orm_test.go`):
1. Seed one user with no MFA and one user with WebAuthn enrolled.
2. `POST /sessions` with a non-existent email + arbitrary password → capture response body/text.
3. `POST /sessions` with the real (non-MFA) user's email + wrong password → capture response body/text.
4. `POST /sessions` with the real (non-MFA) user's email + correct password → 200 with session.
5. `POST /sessions` with the MFA-enrolled user's email + correct password, no `WebAuthnData` → capture response, assert it differs in shape/content from steps 2/3 (i.e., contains WebAuthn challenge JSON).
6. Assert: text from step 2 ("Invalid email") differs from step 3 ("Invalid password") — proving email-existence oracle; assert step 5's body is JSON-shaped WebAuthn data, distinct from steps 2/3/4 — proving MFA-enrollment can be confirmed once credentials are correct. A fix should be validated by asserting steps 2 and 3 return byte-identical error bodies.
