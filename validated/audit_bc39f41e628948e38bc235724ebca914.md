### Title
Pausing vault interest accrual is a pass-through no-op instead of a revert, letting borrow/repay/deposit/redeem continue on a frozen index while other suppliers keep accruing risk - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Zest v2's vault contracts (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) implement an `accrue` pause flag inside the shared `pause-states` tuple. When `accrue` is set to `true`, the internal `accrue` routine does not revert - it silently passes through and returns the *stale* cached `index`/`lindex` without updating them or advancing `last-update`. Meanwhile the higher-level operations that call `accrue` as their first step (`deposit`, `system-borrow`, presumably `system-repay`/`redeem`) do not check the `accrue` pause flag themselves and continue executing normally against the frozen index. [1](#0-0) 

### Finding Description
The accrue logic branches on the `accrue` pause bit:

```
(if (get accrue states)
    ;; PAUSED: Pass-through without reverting
    (ok { index: idx, lindex: lidx })
    ;; NOT PAUSED: Normal accrual logic
    ... updates index/lindex/last-update, mints treasury shares ...)
``` [2](#0-1) 

`system-borrow` (and by the same pattern `deposit`, `redeem`, `system-repay`) calls `(try! (accrue))` first and then proceeds unconditionally with borrow/deposit/redeem logic, gated only by its *own* `borrow`/`deposit`/etc. pause bit - never by the `accrue` bit:

```
(define-public (system-borrow (amount uint) (receiver principal))
  (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      ...)
    (try! (check-caller-auth))
    (asserts! (not (get borrow states)) ERR-PAUSED)
    ...
    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed (+ (var-get total-borrowed) amount))
    (try! (send-underlying amount receiver))
    ...))
``` [3](#0-2) 

`set-pause-states` itself documents the intended invariant - "When pausing accrue, accrue first to capture pending interest" and "When unpausing accrue, jump last-update to now to skip paused period" - confirming the design assumes no vault state-mutating operation (borrow/repay/deposit/redeem) is meant to move `principal-scaled`/`total-borrowed`/shares while the index is frozen:

```
(if (and (not was-paused) now-paused)
    (begin (try! (accrue)) false)
    false)
(if (and was-paused (not now-paused))
    (var-set last-update stacks-block-time)
    false)
``` [4](#0-3) 

This is the "pause that passes through instead of reverting" pattern: rather than causing `accrue`-dependent callers to abort when accrual is paused, the pause silently returns cached, stale values, and downstream state-mutating logic (`system-borrow`, mint of `principal-scaled`, `total-borrowed`) proceeds as if a fresh accrual had occurred. During the paused window, new borrows are scaled against the frozen `index` captured at pause time (`idx (var-get index)`), while `last-update` is not advanced, so once unpaused the vault computes interest for a period during which extra principal was added at the stale index instead of the correct time-weighted rate. [5](#0-4) 

### Impact Explanation
Because interest continues to be modeled from `last-update` to the eventual un-pause timestamp as a single jump (`(var-set last-update stacks-block-time)` on unpause), any principal added or removed during the pause window is retroactively subjected to interest calculated as if it had existed for the entire paused duration (or none of it, depending on which branch executes first), depending on how `total-debt`/`principal-scaled` interacts with `next-index()`'s calculation once accrual resumes. This misallocates interest between suppliers and borrowers who transacted during the pause versus those who held positions the whole time - i.e., theft/freezing of unclaimed yield for one class of user, funded from state mutations that should not have been allowed to occur while the accrual clock was frozen. This lands in the "temporary freezing of funds" / "theft of unclaimed yield" impact category.

### Likelihood Explanation
This requires the DAO (via `check-dao-auth`) to actually set `accrue: true` in `pause-states` while leaving `borrow`/`deposit`/`redeem`/`repay` unpaused - a plausible operational scenario if an operator pauses accrual alone (e.g., during an interest-rate-model migration) without realizing the other operations are not blocked by the same flag. This is a single-transaction/single-flag design gap rather than a multi-party exploit, and is reachable purely through the documented pause-state configuration surface, which the DAO/operators use routinely per `docs/vaults.md` and the vault helper functions (`pauseVault`/`unpauseVault`).

### Recommendation
Either (a) make every state-mutating public function (`deposit`, `redeem`, `system-borrow`, `system-repay`) also assert `(not (get accrue states)) ERR-PAUSED` before proceeding, so a paused accrue clock cannot be silently bypassed while principal continues to move, or (b) make the `accrue` pause revert instead of pass through so that all downstream `(try! (accrue))` callers abort automatically while accrual is paused, matching the documented intent that pausing accrue should also halt principal-changing operations until either accrual is manually captured or the vault is unpaused.

### Proof of Concept
1. DAO calls `set-pause-states` on `v0-vault-stx.clar` with `accrue: true`, leaving `borrow: false`. This does one "capture pending interest" accrue call, then sets `pause-states` with `accrue = true`, leaving `index`/`lindex`/`last-update` frozen at that moment. [6](#0-5) 
2. A user calls `system-borrow`. `(try! (accrue))` hits the paused branch and returns the frozen `{ index: idx, lindex: lidx }` without reverting. `check-caller-auth` and `(not (get borrow states))` both pass since only `accrue` is paused. `principal-scaled` and `total-borrowed` are updated using the stale `idx`, and underlying funds are sent to the borrower. [1](#0-0) 
3. Time passes while `accrue` remains paused; more borrows/deposits/redemptions can occur, all against the same stale index, while `last-update` never advances.
4. DAO later calls `set-pause-states` with `accrue: false`. The unpause branch jumps `last-update` straight to `stacks-block-time`, skipping the entire paused period from the perspective of interest accounting - erasing any interest that should have accrued proportionally on the principal added mid-pause, and misallocating what accrual does eventually occur across suppliers/borrowers who entered positions at different points during the pause window. [7](#0-6)
