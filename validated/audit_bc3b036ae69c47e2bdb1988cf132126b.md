### Title
Missing CPU-time checkpoint in `BN128Pairing`/`PairingCheck.run()` allows unbounded precompile execution within a single opcode dispatch step - ([File: crypto/src/main/java/org/tron/common/crypto/zksnark/PairingCheck.java])

### Summary
`PairingCheck.run()` and its `millerLoop`/`calcEllCoeffs` helpers contain no CPU-time checkpoint call, unlike other expensive precompiles (`ValidateMultiSign` via `MUtil.checkCPUTime()`, `create2` via `MUtil.checkCPUTimeForCreate2()`, and `ModExp` via `MUtil.checkCPUTimeForModExp()`). Because the TVM only checks elapsed CPU time between opcode steps (`Program.checkCPUTimeLimit`, invoked from `VM.play`'s dispatch loop and once more at TX_LAST_OP), a single `CALL` to precompile `0x08` runs `PrecompiledContracts.BN128Pairing.execute()` → `PairingCheck.run()` to full completion before any timeout check can fire, even though its energy cost was pre-approved by `getEnergyForData`.

### Finding Description
`BN128Pairing.execute()` at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:972-1003` loops over all decoded pairs and calls `check.run()` once, with no intermediate calls back into `Program`/`MUtil` for time checking. `PairingCheck.run()` itself (`crypto/.../PairingCheck.java:231-245`) iterates `pairs`, invoking `millerLoop()` and `finalExponentiation()`, again with no checkpoint. `millerLoop`/`calcEllCoeffs` (lines 63-132) execute a `LOOP_COUNT.bitLength()`-driven loop (fixed ~254 iterations) of expensive `Fp12`/`Fp2` field operations per pair, entirely uninterruptible.

Contrast with the mitigated precompiles: `MUtil.checkCPUTime()` (`actuator/src/main/java/org/tron/core/vm/utils/MUtil.java:62-66`), `checkCPUTimeForCreate2()`, and `checkCPUTimeForModExp()` (lines 68-78) each throw `Program.Exception.notEnoughTime` gated behind a `ForkController` version check, and are invoked from inside those specific precompiles/opcodes. No equivalent `checkCPUTimeForPairing()` exists or is called from `BN128Pairing.execute()` or `PairingCheck.run()`.

The only fine-grained timing enforcement in the codebase is `Program.checkCPUTimeLimit(String opName)` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:1241-1259`), which compares `System.nanoTime()` against `vmShouldEndInUs` and throws `OutOfTimeException`. This is invoked from the VM's per-opcode dispatch loop and once at `TX_LAST_OP` in `VMActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java:195-199`) — i.e., checked *between* opcodes, not inside a precompile call that executes synchronously as part of a single `CALL` opcode's execution (`Program.java` calls `VM.play(program, ...)` for the sub-call, and precompile dispatch happens inside that single opcode's handling). Consequently, an attacker can size the `BN128Pairing` input (e.g. ~500 pairs / 96000 bytes) so that `getEnergyForData` declares an affordable cost while the actual wall-clock cost of `PairingCheck.run()` (500 Miller loops + one final exponentiation) exceeds `constantCallTimeoutMs` (used for constant/`triggerconstantcontract` calls, see `VMActuator.calculateCpuLimitInUs`, lines 704-710) before the next timeout check point is reached.

### Impact Explanation
This is a CPU-exhaustion DoS against the node process handling `triggerconstantcontract`/`triggersmartcontract` RPC calls (and potentially block-verification/tx-execution if energyLimit computed from feeLimit is large enough for a non-constant call). Because the timeout check is at opcode-dispatch granularity and the precompile itself is atomic and uninterruptible, one call whose declared energy is within the caller's affordable limit can occupy a full RPC handler thread (or a witness/fullnode's VM execution thread) for far longer than `constantCallTimeoutMs`/`longRunningTime` intends, degrading node responsiveness — matches the "DoS via RPC-API" / "DoS via the TRON protocol implementation" bounty class.

### Likelihood Explanation
Feasible for any unprivileged caller: deploy a trivial contract that forwards `data` to precompile address `0x08` via `CALL`, then invoke it through `triggerconstantcontract` (no fee cost, only RPC-level gating) or a normal transaction sized to stay within `getEnergyForData`'s declared cost and the caller's fee/energy budget. `getEnergyForDataIstanbul` charges 34000 energy per pair (or 80000 pre-Istanbul), which is comparatively cheap for the actual elliptic-curve pairing work involved (full Miller loop + final exponentiation per pair), so the ratio of declared-cost to real CPU time is exploitable and repeatable at will.

### Recommendation
Add a per-pair (or periodic) CPU-time checkpoint inside `PairingCheck.run()` (or inside `BN128Pairing.execute()`'s per-pair loop) that calls back into `Program.checkCPUTimeLimit` (or an equivalent `MUtil.checkCPUTimeForPairing()` gated by a new fork flag, mirroring `checkCPUTimeForModExp`), so that time is checked at fine granularity within the precompile rather than only at opcode-dispatch boundaries.

### Proof of Concept
```java
// JUnit-style PoC sketch (mirrors Create2ModExpForkTest.java pattern)
@Test
public void bn128Pairing_notInterruptedMidExecution() {
    // Force a very small CPU time budget
    CommonParameter.getInstance().setConstantCallTimeoutMs(1);

    // Build ~500 pairs (96000 bytes) of valid BN128 points
    byte[] data = buildPairingInput(500);

    long start = System.nanoTime();
    PrecompiledContract bn128 = PrecompiledContracts.getContractForAddress(BN128_PAIRING_ADDR);
    Pair<Boolean, byte[]> result = bn128.execute(data); // no Program.checkCPUTimeLimit call inside
    long elapsedUs = (System.nanoTime() - start) / 1000;

    // Expected (per invariant): OutOfTimeException should interrupt promptly.
    // Actual: execute() completes fully; no OutOfTimeException is thrown from
    // within PairingCheck.run(), demonstrating the missing checkpoint.
    Assert.assertTrue(result.getLeft());
    Assert.assertTrue(elapsedUs > CommonParameter.getInstance().getConstantCallTimeoutMs() * 1000L);
}
```
This demonstrates that `BN128Pairing.execute()`/`PairingCheck.run()` runs to completion regardless of `constantCallTimeoutMs`, confirming no fine-grained timeout enforcement exists inside the precompile, unlike `ModExp`/`create2`/`ValidateMultiSign` which call `MUtil.checkCPUTimeFor*()`.
