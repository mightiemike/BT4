### Title
Webhook HMAC does not bind the `X-Shopify-Shop-Domain`/topic headers, enabling cross-tenant forged webhook processing - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`shopify.webhooks.validate()` verifies only that the raw request body was HMAC-signed with the app's (global, shop-independent) `apiSecretKey`, but it never binds that signature to the `domain`, `topic`, or `webhookId` headers. These fields are read straight off the unauthenticated HTTP headers after the HMAC check passes. This mirrors the GnosisBase issue: the code verifies "the sender is legitimate" (`messageSender()==_expected` / valid HMAC) but omits verifying "the message actually originated from the claimed source" (`messageSourceChainId()==MIRROR_DOMAIN` / `domain` header actually matches the shop that produced the signed body).

### Finding Description
`validateHmacFromRequestFactory` computes `localHmac` from `rawBody` alone and compares it against the request's HMAC header: [1](#0-0) 
The HMAC key (`config.apiSecretKey`) is the app's single, shop-independent secret — every shop that installs the app produces webhook HMACs with the exact same key.

After the HMAC passes, `checkWebhookHeaders` pulls `domain`, `topic`, `apiVersion`, and `webhookId` directly from the request headers, none of which participate in the HMAC computation: [2](#0-1) 

The resulting `domain` and `topic` are then trusted downstream to select the session and handler to run. In `authenticateWebhookFactory`, `check.domain` is passed unmodified into `ensureValidOfflineSession`, which loads that shop's stored offline session (access token) and attaches an authenticated admin API client to the webhook context: [3](#0-2) 
`ensureValidOfflineSession` simply loads/creates the offline session keyed by the `shop` argument with no cross-check against the payload: [4](#0-3) 

Because `domain` and `topic` are unauthenticated, any party who can obtain one legitimately HMAC-signed `(rawBody, hmac)` pair — trivially achievable by installing the app on their own store/dev shop and triggering any webhook event whose body content they can influence — can replay that exact body+hmac while spoofing `X-Shopify-Shop-Domain` to any other shop that has installed the app, and spoofing `X-Shopify-Topic` to select any registered handler. Validation still succeeds because the signature only ever covers `rawBody`.

### Impact Explanation
This allows a merchant/single account with no special privileges to:
- Trigger webhook handlers to run against a victim shop's offline session/admin API client that they don't control, by supplying a spoofed `domain` header (cross-tenant access using another shop's access token).
- Select an arbitrary registered topic via the spoofed `topic` header (e.g. `app/uninstalled`, order or customer webhooks), causing the app to execute privileged handler logic (which may write to shop data, revoke access, delete sessions, issue refunds, etc.) attributed to the victim shop, using attacker-influenced JSON body content taken from their own webhook.
- Achieve a targeted denial-of-service by forcing `app/uninstalled`-style processing (session invalidation/cleanup) against a victim shop chosen by the attacker.

This satisfies "cross-tenant access" / "forged Shopify request accepted" categories: it is a concrete authentication-bypass primitive reachable from an unprivileged single-merchant account against any other tenant of the same app.

### Likelihood Explanation
Medium-to-high. The attacker needs only:
1. Their own Shopify store with the target app installed (freely obtainable — no special access), to legitimately generate at least one `(rawBody, hmac)` pair.
2. Knowledge of the victim's `*.myshopify.com` domain, which is often guessable/public and is exactly the value most apps expect in `X-Shopify-Shop-Domain`.
3. The ability to send raw HTTP POST requests to the app's public webhook endpoint (no authentication barrier beyond the HMAC check that is bypassed here).

No cryptographic secret leak, MITM, or privileged access is required — this is directly reachable from an anonymous/unprivileged HTTP request to the webhook endpoint, matching the required analog class exactly.

### Recommendation
Bind the `domain` (and ideally `topic`/`webhookId`) to the HMAC verification instead of trusting them as free-form headers after only the body's signature is checked:
- Include the shop domain (and topic) in the string that is HMAC'd, or
- After computing a valid HMAC, cross-check that the `domain` header corresponds to a value obtained from an independently-trusted source (e.g., verify the domain is embedded/committed inside the signed body payload where Shopify actually includes shop identifiers, or maintain a per-shop webhook secret if supported) rather than relying solely on the header value.
- At minimum, document and enforce that consumers must not treat `domain`/`topic` as authenticated facts derived from the HMAC check, and require an additional server-side check (e.g., confirm the resolved session's shop matches an independently obtained shop context) before granting the admin client to webhook handlers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) any webhook the app is subscribed to (e.g., `products/update`) with body content they control (their own product data), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — this HMAC is valid because it is computed with the app's shared `apiSecretKey`.
3. Attacker resends this exact `rawBody` + `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled` (or any other registered topic of the attacker's choosing)
   - fresh `X-Shopify-Webhook-Id`
4. `validateHmacFromRequestFactory` succeeds (HMAC only checks `rawBody`), `checkWebhookHeaders` returns `valid: true` with the forged `domain`/`topic`, `authenticate()` loads `victim-shop.myshopify.com`'s offline session via `ensureValidOfflineSession`, and the app's registered handler for the forged topic executes with `session`/`admin` bound to the victim shop — using attacker-controlled payload content. export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
