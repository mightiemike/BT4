### Title
Missing check that `DeleteAccountAction::beneficiary_id` is not the reserved `system` account permanently burns the deleted account's balance - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId`; it never rejects the reserved `system` account id, even though `system` is documented as unusable/non-existent and can never receive funds. This is the direct nearcore analog of the reported Solidity bug class (a caller-supplied destination address is never checked against the "null"/unusable address), and it produces a concrete, unrecoverable loss of the deleting account's remaining NEAR balance.

### Finding Description
`validate_delete_action` is the only validation applied to `DeleteAccountAction::beneficiary_id`, and it just calls `validate_action_account_id`, which in turn calls `AccountId::validate`, a purely syntactic check (length/character rules): [1](#0-0) [2](#0-1) 

`"system"` is a valid, well-formed lowercase account-id string, so it passes this check even though the protocol documentation explicitly states it is a reserved account that "does not exist as part of the state" and "Users cannot create or access": [3](#0-2) 

When `action_delete_account` runs, it unconditionally builds a balance-refund receipt addressed to the attacker/user-controlled `beneficiary_id`: [4](#0-3) 

`Receipt::new_balance_refund` sets both `predecessor_id` and (here) `receiver_id` to reflect a system-style refund receipt: [5](#0-4) 

When this receipt is later applied, `check_account_existence` classifies `system` as a `NamedAccount` (not implicit), and `implicit_creation_allowed` always returns `false` for named accounts, so the transfer cannot create/credit the `system` "account": [6](#0-5) [7](#0-6) 

The receipt therefore fails with `AccountDoesNotExist`. Because this is a `system`-predecessor (refund) receipt, the runtime treats the failure as final and irreversibly burns the whole deposit instead of retrying or bouncing it back to any account: [8](#0-7) 

This matches the documented refund semantics: "If the execution of a refund fails, the refund amount is burnt," with no further recovery path.

### Impact Explanation
Any signer who submits an ordinary, unprivileged `DeleteAccount` transaction with `beneficiary_id = "system"` causes their entire remaining account balance to be permanently and irrecoverably burned rather than refunded to any account. This is a direct instance of the "permanently frozen/lost funds" impact category: real, spendable NEAR balance is destroyed as a side effect of a missing sanity check on a caller-supplied "beneficiary" field — exactly the same bug class as the referenced report (unchecked "null-like" address parameter leading to unrecoverable value with no way to fix after the fact, since deleting the account is a one-way operation). It also silently shrinks total supply (an unintended burn) outside the normal fee/gas-burning accounting path.

### Likelihood Explanation
The path is trivially reachable by any account holder signing a standard `DeleteAccount` action (or a meta-transaction/delegate action whose inner action they control) — no special privileges, races, or malicious peers are required. The only "attacker" is the transaction's own signer (self-inflicted loss, similar to the original report's "wrong constructor argument" scenario), but because account deletion is irreversible and the beneficiary is fully attacker/user chosen, this can also be leveraged by tooling bugs, wallet bugs, or social-engineering to trick a user into signing a delete with `beneficiary_id: "system"`, permanently destroying their balance.

### Recommendation
Add an explicit check in `validate_delete_action` (and ideally in the shared `validate_action_account_id` helper used by other actions that take a destination `AccountId`, e.g. `refund_to`, global contract identifiers) that rejects `beneficiary_id == "system"` (i.e., `AccountId::is_system()` style check) with a clear `ActionsValidationError`, so that transactions attempting to delete an account with an unusable beneficiary are rejected at validation time instead of silently burning funds at execution time.

### Proof of Concept
1. Create/fund a regular account `alice.near` with balance `B`.
2. Sign and submit a transaction from `alice.near` to `alice.near` containing a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "system".parse().unwrap() })`.
3. `validate_delete_action` accepts the action because `"system"` passes `AccountId::validate`.
4. `action_delete_account` deletes `alice.near` and enqueues `Receipt::new_balance_refund(&"system", B)`.
5. When this receipt is processed, `check_account_existence`/`implicit_creation_allowed` reject it with `AccountDoesNotExist { account_id: "system" }` because `system` is a `NamedAccount` that can never be implicitly created.
6. Because the receipt's predecessor is `system` (a refund), the failure branch at `runtime/runtime/src/lib.rs:1047-1054` adds `B` to `stats.balance.other_burnt_amount`, permanently burning it — `alice.near`'s balance `B` is gone with no receiving account, and total supply decreases accordingly.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
