### Title
Unbounded linear scan over `PendingInbounds` on every ballot termination enables gas-griefing DoS - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
`x/uexecutor`'s `BallotHooks.afterInboundBallotTerminal` locates the `PendingInboundEntry` owning a terminating ballot by doing a full `Walk` over the entire `PendingInbounds` collection (and a nested scan of each entry's `Variants`) instead of using a direct key lookup. This is the same anti-pattern as the reported Move bug: an unprivileged, ordinary user can grow the `PendingInbounds` set by simply initiating many small cross-chain deposits, and once the set is large every subsequent ballot termination — including terminations of completely unrelated, honestly-processed inbounds — pays an O(n) cost. Because ballot expiry is driven automatically from `EndBlocker` via `ExpireBallotsBeforeHeight`/`MarkBallotExpired`, this asymptotic blowup is triggered without any privileged actor.

### Finding Description
`RecordInboundVote` [1](#0-0)  creates a new `PendingInboundEntry` keyed by `utx_key` on the first honest-validator vote for any inbound event a user initiates on a source chain — this happens naturally as part of ordinary user activity (e.g. depositing funds through the gateway), with no cap on how many distinct pending inbounds can exist concurrently.

When a ballot for any inbound reaches a terminal state (`PASSED`, `REJECTED`, or `EXPIRED`), `x/uvalidator` invokes `BallotHooks.AfterBallotTerminal`, which for `INBOUND_TX` ballots calls `afterInboundBallotTerminal`: [2](#0-1) 

This function does **not** look up the owning entry by its natural key; instead it performs a full `Walk` over every entry in `PendingInbounds`, and for each entry linearly scans all of its `Variants`, just to find the one variant whose `BallotId` matches the ballot that just finalized. This mirrors exactly the `vector::index_of` linear-search pattern from the external report, just implemented as a KV-store `Walk` instead of a Move vector.

Ballot expiry (one of the three terminal triggers) is not user-initiated per se, but it is driven deterministically by chain state that an ordinary user controls: submitting an inbound causes a ballot to be created, and if it never reaches quorum (e.g. because it references a chain/config edge case, or validators split votes across multiple payload "variants" as described in the variant-aware design in `pending.proto`), the ballot eventually expires via `ExpireBallotsBeforeHeight`, which is called from the module's block lifecycle and fires `MarkBallotExpired` → `AfterBallotTerminal` for each expiring ballot ID.

### Impact Explanation
An attacker who repeatedly initiates many low-value cross-chain deposits (or crafts inbound events likely to produce split/never-finalizing ballots) can grow `PendingInbounds` to a large size `n` in O(1) chain cost per entry (each entry is created/extended cheaply on a single validator vote). Once `n` is large, **every** subsequent terminal ballot transition for **any** inbound — including those of honest, unrelated users — must pay an O(n) `Walk` cost inside `afterInboundBallotTerminal`. Since `ExpireBallotsBeforeHeight` can expire multiple ballots within a single block, and each expiry re-triggers the full O(n) walk, the per-block cost can become O(n·m) for m expiries in that block. This degrades block processing for the entire chain and inflates the effective gas/processing cost imposed on honest inbound processing — a non-network-level denial-of-service condition reachable purely through ordinary, unprivileged user activity (initiating deposits), consistent with the "denial of service...reachable without privileged control" impact category.

### Likelihood Explanation
Likelihood is moderate: creating additional `PendingInbounds` entries requires legitimate inbound observation and voting by honest Universal Validators (no validator collusion needed — validators just vote normally on genuine, attacker-initiated deposit events). Getting individual ballots to linger long enough to accumulate a large `n` (rather than resolving quickly to `PASSED`) may need either many concurrently in-flight low-value inbounds, or triggering variant divergence/edge-case configs that delay finalization until expiry. This is more involved than the original Move report's single-call trigger, but still achievable purely with unprivileged, honest-validator-processed transactions, without any admin, governance, or malicious-node assumption.

### Recommendation
Replace the `PendingInbounds.Walk` scan in `afterInboundBallotTerminal` with a direct index lookup: maintain a secondary `ballotID -> utxKey` mapping (set alongside `RecordInboundVote` when a new variant/ballot is created, and removed when the entry is removed) so the ballot-termination hook can resolve `utxKey` in O(1) instead of scanning the entire `PendingInbounds` collection and each entry's `Variants` slice.

### Proof of Concept
1. Attacker (unprivileged) submits N distinct small deposits from a source chain through the standard gateway flow, each producing a unique `Inbound` observed and voted by honest UVs, each creating its own `PendingInboundEntry` via `RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-46`).
2. Craft a subset of these inbounds so that validators observe slightly different byte-level variants (or otherwise fail to hit quorum quickly), keeping their ballots `PENDING` in `x/uvalidator` for many blocks, causing `PendingInbounds` to grow to size N without being pruned.
3. Once `PendingInbounds` holds N entries, any subsequent ballot termination — including one for a legitimate, unrelated user's routine deposit, or one of the attacker's own ballots naturally expiring via `ExpireBallotsBeforeHeight` — invokes `afterInboundBallotTerminal`, which performs a full `Walk` over all N entries (`x/uexecutor/keeper/ballot_hooks.go:86-94`) plus a per-entry scan of `Variants`, imposing O(N) cost on that unrelated operation.
4. Repeating this across many terminal events within the same or successive blocks compounds the cost, degrading processing for the entire chain, purely from unprivileged attacker-initiated deposits and honest validator/user activity.

```go
func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
```
