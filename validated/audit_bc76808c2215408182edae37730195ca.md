### Title
Starknet OS `execute_replace_class` accepts an undeclared class hash, causing OS/blockifier state divergence - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The `replace_class` syscall lets a contract change its own `class_hash` in storage. In the blockifier's native/Rust implementation (`syscall_base.rs::replace_class`) the class hash is validated: it must correspond to an actually declared, Cairo1 compiled class, obtained via `self.state.get_compiled_class(class_hash)?`, and the replacement is rejected otherwise (`ForbiddenClassReplacement`). The Starknet OS Cairo implementation of the same syscall, `execute_replace_class` in `syscall_impls.cairo`, performs no such check — it blindly writes the caller-supplied `class_hash` into the contract's `StateEntry` and appends a revert-log entry, with an explicit `TODO` acknowledging the missing validation.

### Finding Description
`execute_replace_class` (and its deprecated-syscall twin `execute_replace_class` in `deprecated_execute_syscalls.cairo`) reads `class_hash = request.class_hash` directly from syscall input controlled by the executing contract (reachable from any user transaction that triggers a `replace_class_syscall`), and unconditionally updates the contract's `StateEntry`: [1](#0-0) 

The comment on line 902 explicitly states the missing whitelist/existence check: `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` [2](#0-1) 

In contrast, the blockifier (the component that actually executes transactions in the sequencer and produces the `StateDiff` that the OS is meant to re-execute and verify) explicitly checks class declaration/type before accepting the replacement: [3](#0-2) 

This is directly analogous to the reported Holdefi bug class: a caller-supplied "address"/identifier (there, an ERC20 market address; here, a `class_hash`) is accepted and written into protocol state without validating it against the authoritative registry (there, `isActive`; here, the set of declared classes). The blockifier is the "whitelist check" implementation that the OS's Cairo re-execution path is missing.

### Impact Explanation
The Starknet OS re-executes the same block that the blockifier produced and is expected to derive an identical state diff / commitment, which is checked by Cairo proof verification (i.e., this code runs as part of the proven re-execution used to attest to block validity). If the blockifier rejects a `replace_class_syscall` call with an undeclared/undesired class hash (returning a revert due to `ForbiddenClassReplacement` or `UndeclaredClassHash`) while the OS accepts it unconditionally and commits the new (bogus) class hash into `contract_state_changes`, the OS-computed state diff/commitment for that contract diverges from the blockifier's actual state diff. This can produce an incorrect committed root/state entry for that contract address, an honest-node/OS divergence, and — in a system relying on this trace for proof generation — either a rejected/incorrect proof or (if unnoticed) an incorrect global state commitment being finalized, satisfying the "wrong committed root" / "honest-node divergence" impact bar.

### Likelihood Explanation
Reachable by any account/contract that can call `replace_class_syscall` (or the deprecated equivalent) with an arbitrary, non-existent `class_hash` — no special privileges required, just a single contract call in an ordinary transaction. No proof-of-nonexistence gadget for class hashes currently exists in the OS (per the TODO), so the bug is trivially triggerable whenever this code path executes without the missing validation being backfilled elsewhere in the surrounding hint/logic (which I could not fully verify — see caveat below).

### Recommendation
Add the same declared-class check to `execute_replace_class` (both `syscall_impls.cairo` and the deprecated `deprecated_execute_syscalls.cairo` variant) that the blockifier performs in `syscall_base.rs::replace_class`: verify the target `class_hash` corresponds to a declared class (and Cairo1 type, consistent with `ForbiddenClassReplacement`) before writing the new `StateEntry`, aborting/reverting otherwise so OS execution semantics match blockifier execution semantics exactly.

### Proof of Concept
Not independently executed; based on static comparison of the two execution paths:
1. Deploy/invoke a contract that calls `replace_class_syscall(some_undeclared_class_hash)`.
2. In blockifier execution, this reverts via `ForbiddenClassReplacement`/`UndeclaredClassHash` since `get_compiled_class` fails for an undeclared hash.
3. In the Starknet OS Cairo re-execution of the same transaction, `execute_replace_class` performs no such check and commits `class_hash=some_undeclared_class_hash` into `contract_state_changes`, producing a state diff/commitment that disagrees with the blockifier's.

**Caveat**: I could not fully confirm from the indexed code whether some earlier hint (e.g., inside `%{ GetContractAddressStateEntry %}` or elsewhere in the OS pipeline) independently enforces class declaration before this point, which would mitigate or negate the issue; the explicit `TODO` comment strongly suggests it does not, but a background agent with full repo access should verify this before treating the finding as conclusively unmitigated.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
