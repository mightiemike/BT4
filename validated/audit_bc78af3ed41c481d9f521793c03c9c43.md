Confirmed: in both `shopify-app-remix` and `shopify-app-react-router`, the token-exchange strategy's `authenticate()` reuses the cached/stored session by calling `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` — passing `undefined` for scopes instead of the app's configured scopes.

Since `Session.isScopeChanged()` short-circuits to `false` whenever `scopes === undefined` [1](#0-0) , and `isActive()` only checks token presence, expiry, and `isScopeChanged` [2](#0-1) , the token-exchange strategy treats a stored session as valid and reuses it **without ever verifying its stored `scope` matches the app's currently configured `scopes`**.

### Title
Stale/narrower-scoped session reuse in token-exchange auth strategy bypasses scope re-authorization - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts)

### Summary
The `TokenExchangeStrategy.authenticate()` (and its react-router twin `createTokenExchangeStrategy`) decides whether to reuse an existing stored `Session` or force a fresh OAuth token exchange by calling `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` [3](#0-2) [4](#0-3) . Passing `undefined` for the `scopes` argument disables the scope-comparison logic in `Session.isActive`/`isScopeChanged` [5](#0-4) , so a previously stored session is reused purely based on expiry, regardless of whether its `scope` field still matches the app's currently configured `scopes` in `AppConfig`.

This is the direct analog of CVE-2022-27782: a security-relevant option (authorized OAuth scopes, analogous to curl's TLS/CRL options) is silently ignored when deciding whether to reuse a previously-established credential/connection (the stored Shopify session/access token).

### Finding Description
Other admin auth code paths in this same codebase correctly pass the configured scopes into `isActive`, e.g. `shopify-app-express`'s `validateWithAuthCodeFlow` calls `session.isActive(api.config.scopes)` [6](#0-5) . However, the token-exchange strategy (used by `shopify-app-remix` and `shopify-app-react-router`, the modern recommended integration path) never supplies scopes to `isActive`, effectively disabling the "scope changed" re-authorization guard that the rest of the library relies on for detecting stale sessions after a scope change deploy.

The `isScopeChanged` implementation makes this explicit: `if (typeof scopes === 'undefined') { return false; }` [1](#0-0) .

### Impact Explanation
If a merchant granted an app narrower scopes historically (or the app's scopes were reduced/changed via a deploy of `scopes` config, or via managed installation flows), a stored offline/online session with the old `scope` value will still be treated as "active" and reused by `shopify.authenticate.admin()` indefinitely (until token expiry), instead of triggering a fresh `tokenExchange` call that would re-derive/re-validate scopes against the shop's current grant. This can let request handling proceed using an access token whose actual granted scopes no longer align with what the app now expects/requires, which is a security-relevant confused-authorization condition analogous to the curl bug's stale/mismatched security-option reuse.

### Likelihood Explanation
This triggers on every authenticated admin request that already has a stored session in `config.sessionStorage`, which is the common/majority path for embedded apps using the token-exchange strategy — no attacker action or privilege is needed to reach this code; it's exercised by ordinary merchant/session-token requests through `authStrategyFactory` → `getSessionTokenContext` → `strategy.authenticate` [7](#0-6) .

### Recommendation
Pass the app's configured scopes (e.g. `config.scopes` / `api.config.scopes`) into the `isActive` call in both `TokenExchangeStrategy.authenticate` implementations, mirroring `validate-authenticated-session.ts`'s `session.isActive(api.config.scopes)` pattern, so scope drift correctly forces re-exchange of the token.

### Proof of Concept
1. Configure an app with `scopes: ['read_orders']`, install it on a shop (offline session with `scope: 'read_orders'` gets stored).
2. Redeploy the app with `scopes: ['read_orders', 'write_orders']` (or the shop's actual grant is reduced independently).
3. A subsequent embedded request with a valid session token reaches `TokenExchangeStrategy.authenticate`; the stored session is loaded and `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` returns `true` purely because the token isn't expired [3](#0-2) .
4. The stale-scoped session is reused and returned to the app's route handler as `session`/`admin` context, without a token-exchange re-authorization ever being triggered, unlike the express-based flow which would catch this via `session.isActive(api.config.scopes)`.

  public isActive(
    scopes: AuthScopes | string | string[] | undefined,
    withinMillisecondsOfExpiry = 500,
  ): boolean {
    const hasAccessToken = Boolean(this.accessToken);
    const isTokenNotExpired = !this.isExpired(withinMillisecondsOfExpiry);
    const isScopeChanged = this.isScopeChanged(scopes);
    return !isScopeChanged && hasAccessToken && isTokenNotExpired;
  }

  /**
   * Whether the access token includes the given scopes if they are provided.
   */
  public isScopeChanged(
    scopes: AuthScopes | string | string[] | undefined,
  ): boolean {
    if (typeof scopes === 'undefined') {
      return false;
    }

    return !this.isScopeIncluded(scopes);
  }
