Confirmed: `action_delete_key` in `runtime/runtime/src/access_keys.rs:52` performs no check on whether the key being deleted is the account's last remaining `FullAccess` key. `delete_regular_key` (`access_keys.rs:136`) simply removes the key and adjusts storage usage — there is no guard against leaving the account with zero access keys, and the test `test_delete_key_last` at `integration-tests/src/tests/standard_cases/mod.rs:1163` explicitly exercises and accepts this outcome as successful.

### Title
Self-inflicted permanent fund lockout via unrestricted deletion of an account's last full-access key - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
A NEAR account holder can submit a single `DeleteKey` transaction that removes their own last remaining `FullAccess` access key. Once this succeeds, the account has zero access keys and (absent a deployed contract exposing its own authorization logic) no path exists to ever sign another transaction from that account, permanently freezing any NEAR balance and locked/staked balance held by it. This mirrors the reported `renounceOwnership()` bug class: a privileged actor voluntarily destroys the only credential that authorizes further privileged action on their own account, with no recovery path.

### Finding Description
`action_delete_key` (`runtime/runtime/src/access_keys.rs:52-91`) looks up the target key via `get_access_key` and, if found, unconditionally removes it through `delete_regular_key` (`:136-147`) for non-gas keys or `delete_gas_key` (`:93+`) for gas keys. Neither path counts the account's remaining `FullAccess` keys nor rejects deletion when it is the last one. The transaction-level verifier (`runtime/runtime/src/verifier.rs`) authorizes the `DeleteKey` action purely based on nonce/balance/permission checks on the *signing* key, not on the resulting state of the account's key set. The integration test suite documents and accepts this exact scenario as a "success" outcome: [3](#0-2) 

The protocol documentation itself acknowledges the resulting state — "If account has no access keys attached it means that it has no owner who can run transactions from its behalf" — but frames it purely as a documentation note rather than a protected invariant: [4](#0-3) 

For a plain named account (no deployed contract, or a contract without a recovery/withdrawal method reachable without a signing key), deleting the last `FullAccess` key permanently removes the only mechanism (a valid signed transaction) capable of moving the account's `amount`/`locked` balance, adding a new key, or invoking privileged `Stake`/`Transfer`/`DeployContract` actions on that account ever again.

### Impact Explanation
This results in permanently frozen funds for the affected account: the on-chain balance, staking rewards, and any locked stake become unreachable by any future transaction, with no protocol-level recovery mechanism. This is the direct NEAR analog of the reported Solidity bug class — an owner/administrator voluntarily renouncing their only privileged credential and thereby permanently disabling privileged operations, except here the "privilege" is the ability to transact at all from the account, so the impact is broader (total fund freeze rather than loss of specific admin functions).

### Likelihood Explanation
Likelihood is low, matching the original report's rating: it requires the account's own key holder to intentionally (or by tooling error) submit a `DeleteKey` transaction targeting their last `FullAccess` key. No third party can trigger this against another account; it is purely self-inflicted, exactly as `renounceOwnership()` in the original report is only callable by the current owner.

### Recommendation
Consider adding a guard in `action_delete_key` (or in `delete_regular_key`) that rejects deletion of the last `FullAccess` key on a contract-less account (or surfaces a distinct warning/error such as `DeleteLastFullAccessKey`), unless the account has a deployed contract capable of independently authorizing future actions. At minimum, wallet/CLI tooling should refuse to submit such a transaction without explicit confirmation, and RPC/view-layer tooling could expose a warning when an account is about to reach zero access keys.

### Proof of Concept
1. Create/fund a named NEAR account with a single `FullAccess` key (the signer's own key).
2. Submit a `SignedTransaction` containing a single `Action::DeleteKey(DeleteKeyAction { public_key: <signer's own public key> })`, signed by that same key, as exercised in `test_delete_key_last` (`integration-tests/src/tests/standard_cases/mod.rs:1163-1199`).
3. Observe the transaction succeeds (`FinalExecutionStatus::SuccessValue`), and `get_access_key` for the deleted public key now returns an error — the account has zero access keys.
4. Any subsequent attempt to sign a transaction from this account (e.g., to withdraw its NEAR balance or unstake locked funds) fails at verification with `AccessKeyNotFound`/`SignerDoesNotExist`-style errors, since no valid access key exists — the balance is now permanently unreachable.

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}

pub fn test_delete_key_last(node: impl Node) {
    let account_id = &node.account_id().unwrap();
    let node_user = node.user();
    let root = node_user.get_state_root();

    assert!(node_user.get_access_key(account_id, &node.signer().public_key()).is_ok());
    let transaction_result = node_user.delete_key(account_id.clone(), node.signer().public_key());

    match transaction_result {
        Ok(transaction_result) => {
            assert_eq!(transaction_result.status, FinalExecutionStatus::SuccessValue(Vec::new()));
            assert_eq!(transaction_result.receipts_outcome.len(), 1 + extra_refund_outcomes());
        }
        Err(err) => {
            // TODO(#6724): This is a wrong error, the transaction actually
            // succeeds. We get an error here when we retry the tx and the second
            // time around it fails. Normally, retries are handled by nonces, but we
            // forget the nonce when we delete a key!
            assert_eq!(
                err,
                CommitError::Server(ServerError::TxExecutionError(
                    TxExecutionError::InvalidTxError(InvalidTxError::InvalidAccessKeyError(
                        InvalidAccessKeyError::AccessKeyNotFound {
                            account_id: account_id.clone(),
                            public_key: node.signer().public_key().into(),
                        },
                    ))
                ))
            )
        }
    }

    let new_root = node_user.get_state_root();
    assert_ne!(new_root, root);

    assert!(node_user.get_access_key(account_id, &node.signer().public_key()).is_err());
