### Title
Hard-coded ECDSA Signing Key in Production `SignatureManager` Used for Peer Identity and Precommit Vote Authentication - ([File: crates/apollo_signature_manager/src/lib.rs])

### Summary
The production `create_signature_manager()` entry point unconditionally constructs a `SignatureManager` backed by `LocalKeyStore::new_for_testing()`, which embeds a fixed, publicly-known private key constant directly in source. This key is used to sign peer-identification challenges and consensus precommit votes.

### Finding Description
`LocalKeyStore::new_for_testing()` hard-codes a constant private key (`PRIVATE_KEY = Felt::from_hex_unchecked("0x608bf2cdb1ad4138e72d2f82b8c5db9fa182d1883868ae582ed373429b7a133")`) and its derived public key, despite the "for_testing" naming. [1](#0-0) 

This `LocalKeyStore` is the sole `KeyStore` implementation wired into the crate's public, non-test API: `LocalKeyStoreSignatureManager::new()` calls `GenericSignatureManager::new(LocalKeyStore::new_for_testing())` with no feature-gate or environment check, and `create_signature_manager()` — the crate's documented "production" constructor (see the accompanying TODO: "understand how key store would look in production") — calls this same path unconditionally. [2](#0-1) 

The `SignatureManager` produced from this key store is used for two security-sensitive signing operations reachable/verifiable by other network participants:
- `sign_identification`, which signs a peer-identity challenge (`INIT_PEER_ID` domain) used to authenticate a peer's identity/PeerId binding.
- `sign_precommit_vote`, which signs consensus precommit votes over a `BlockHash` (`PRECOMMIT_VOTE` domain), feeding into block finalization/consensus signature aggregation. [3](#0-2) [4](#0-3) 

Because the private key is a compile-time constant visible in the open-source repository, any party can independently compute the exact same ECDSA signature for `sign_identification` or `sign_precommit_vote` given the same public inputs (peer_id/challenge or block_hash), since ECDSA over a known private key is fully deterministic given (private key, message). This means the "identity" and "precommit vote" signatures produced by this component carry no real authentication value if this constant key is what backs a real, publicly-connected node's signature manager.

### Impact Explanation
If this key store is actually the one instantiated for live/non-test nodes (as the unconditional call chain from `create_signature_manager()` suggests, and as the crate's own TODO comment implies — "understand how key store would look in production" — meaning no distinct production key path currently exists), then any external actor knowing this hard-coded key can forge:
1. Peer-identity signatures for `INIT_PEER_ID` challenges, enabling identity spoofing of a node during peer authentication in the Propeller/consensus signature-manager identification flow, and
2. Precommit-vote signatures over arbitrary block hashes, enabling forged validator precommit votes that could be injected into the consensus signature-collection process.

Depending on how these signatures are consumed downstream (validator set membership checks, quorum signature aggregation for block finality), a forged precommit could contribute to a wrong committed block/finality result or allow an attacker to impersonate a node's identity, causing consensus/authentication mismatches between honest nodes — i.e., honest-node divergence or unauthorized "validator action" forgery. This matches CVE-2026-45336's bug class: a hard-coded signing/session key that lets an unauthenticated party forge protected identity/action tokens.

### Likelihood Explanation
High, assuming this code path is what actually backs live nodes: the constant is public (checked into the repo), requires no privileged access, and the only gating comment is a TODO acknowledging production key management is unresolved. No feature flag or `cfg(test)` currently distinguishes "testing" from "production" use in `create_signature_manager()`. This is directly reachable by any external actor who can present a peer-identification challenge or observe a block hash — no proposer/operator privilege required to exploit the forgeability, only knowledge of the well-known constant.

### Recommendation
- Replace `create_signature_manager()`'s unconditional `LocalKeyStore::new_for_testing()` with a real `KeyStore` implementation that loads a per-node private key from a genuinely private/generated source (e.g., wallet/KMS/secure config), never compiled into source.
- Gate `LocalKeyStore::new_for_testing()` behind `#[cfg(any(test, feature = "testing"))]` so it cannot be linked into the production binary at all.
- Resolve the outstanding TODO in `apollo_signature_manager/src/lib.rs` regarding "how key store would look in production" before relying on this component in any deployed node.

### Proof of Concept
1. Obtain the constant `PRIVATE_KEY = 0x608bf2cdb1ad4138e72d2f82b8c5db9fa182d1883868ae582ed373429b7a133` from `crates/apollo_signature_manager/src/signature_manager.rs`.
2. For a target node using `create_signature_manager()`, construct the same message digest as `build_peer_identity_message_digest(peer_id, challenge)` or `build_precommit_vote_message_digest(block_hash)` using publicly observable `peer_id`/`challenge`/`block_hash` values.
3. Compute `ecdsa_sign(&PRIVATE_KEY, &message_digest)` locally — this reproduces the exact signature the node would produce, allowing forgery of identity attestations or precommit votes without needing the actual node’s runtime secret (because there is none distinct from this hard-coded value).

**Caveat:** I could not fully verify from the indexed code whether `create_signature_manager()` is actually invoked in the live node's component wiring (vs. exclusively in test/integration harnesses) — the crate's own TODO strongly suggests no alternative production key store currently exists, but confirming the exact call sites in the node's startup/component-registration code would require deeper inspection than the current index coverage allowed. I recommend verifying this wiring in a full checkout before treating this as confirmed-exploitable in a running deployment.

fn build_peer_identity_message_digest(peer_id: PeerId, challenge: Challenge) -> MessageDigest {
    let challenge = &challenge.0;
    let peer_id = peer_id.to_bytes();
    let mut message = Vec::with_capacity(INIT_PEER_ID.len() + peer_id.len() + challenge.len());
    message.extend_from_slice(INIT_PEER_ID);
    message.extend_from_slice(&peer_id);
    message.extend_from_slice(challenge);

    MessageDigest(blake2s_to_felt(&message))
}

fn build_precommit_vote_message_digest(block_hash: BlockHash) -> MessageDigest {
    let block_hash = block_hash.to_bytes_be();
    let mut message = Vec::with_capacity(PRECOMMIT_VOTE.len() + block_hash.len());
    message.extend_from_slice(PRECOMMIT_VOTE);
    message.extend_from_slice(&block_hash);

    MessageDigest(blake2s_to_felt(&message))
}
