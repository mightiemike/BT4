### Title
Outgoing-receipt gas admission check can permanently starve legitimate receipts once a single receipt's attached gas exceeds the shard's entire per-round outgoing-gas budget - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`ReceiptSinkV2::try_forward` decides whether an outgoing receipt is sent this chunk or buffered for a later chunk. Pre-`ClampOutgoingGasAdmission` (protocol version 85), the admission check requires the *entire receiver's remaining outgoing-gas budget* (`forward_limit.gas`) to be `>=` the full attached gas of the receipt being forwarded. Because `forward_limit.gas` for a receiver shard is capped every chunk at `outgoing_gas_limit`, which is itself bounded above by `max_outgoing_gas` [1](#0-0) , any single receipt whose attached/prepaid gas exceeds `max_outgoing_gas` can never satisfy `forward_limit.gas >= gas`, no matter how many chunks pass. This exactly mirrors the Augur `DisputeCrowdsourcer` bug: a check of the form "cap minus already-accumulated must be enough for the new contribution" that can never succeed once the new contribution alone is larger than the cap, permanently blocking further progress for that item.

### Finding Description
`try_forward` computes an `admission_gas` value and only forwards the receipt if the receiver's remaining budget covers it: [2](#0-1) 

Under the pre-PV85 (`ClampOutgoingGasAdmission`) code path, `admission_gas` equals the receipt's full `gas` value (unclamped), and the receiver's `forward_limit.gas` for any shard is derived every chunk from `CongestionControl::outgoing_gas_limit`, which never exceeds `config.max_outgoing_gas` for a non-fully-congested shard (or `allowed_shard_outgoing_gas` when fully congested) [3](#0-2) . If a receipt's attached gas is larger than `max_outgoing_gas`, the condition `forward_limit.gas >= admission_gas` is false in every single chunk forever, since `forward_limit.gas` is re-derived each chunk from the same bounded config and can never reach the receipt's gas value. The receipt is therefore always routed to `buffer_receipt` instead of `try_forward`'s success branch, and stays in the outgoing buffer indefinitely — a permanent stall, exactly analogous to `size.sub(_curStake)` reverting forever once `_curStake > size` in the Augur contract.

The fix, `ClampOutgoingGasAdmission`, clamps the admission check to `allowed_shard_outgoing_gas` instead of the full receipt gas [4](#0-3) , which is the runtime's own acknowledgement of this exact bug class — it is gated behind protocol version 85 [5](#0-4) , meaning any protocol version prior to PV85 (or a hypothetical rollback / older running binary still voting sub-85 versions) executes the pre-fix, permanently-stuck logic.

### Impact Explanation
A receipt (triggered by an ordinary user function call that attaches a large amount of gas to a cross-shard promise) can become permanently stuck in a shard's outgoing buffer, never executing on the destination shard. This is receipt loss/permanent freezing of the corresponding state transition (e.g. a cross-contract call and its associated locked balance/callback never resolve), matching the "permanently frozen funds" / "receipt loss" acceptance criteria.

### Likelihood Explanation
This requires only a single ordinary transaction/contract call that produces an outgoing cross-shard receipt with attached gas exceeding `max_outgoing_gas` (a config-controlled but attacker-influenceable value via `promise_batch_action_function_call`), reachable by any unprivileged signer — no validator or network-level assumptions needed. The condition depends on the code path being active without the `ClampOutgoingGasAdmission` fix, i.e., on protocol versions prior to PV85; whether the currently examined codebase's default/mainnet-voted protocol version has already activated PV85 could not be conclusively determined from the available `version.rs` excerpt within the exploration budget.

### Recommendation
Ensure the `ClampOutgoingGasAdmission` behavior (clamping the admission-gas comparison to `allowed_shard_outgoing_gas` rather than the full receipt gas) is unconditionally active for all currently supported protocol versions, and add an explicit invariant/test asserting that a receipt with attached gas above `max_outgoing_gas` is still eventually forwarded (not perpetually buffered) under every configuration.

### Proof of Concept
1. Submit a transaction that creates a cross-shard promise/receipt (e.g., via `promise_batch_action_function_call`) with attached gas greater than `congestion_control_config.max_outgoing_gas` (300 Tgas per the shipped config snapshot) [6](#0-5) .
2. On the sending shard, `ReceiptSink::new` builds `forward_limit.gas` for the receiver shard from `outgoing_gas_limit`, bounded by `max_outgoing_gas`/`allowed_shard_outgoing_gas` [3](#0-2) .
3. Each chunk, `try_forward` computes `admission_gas = gas` (pre-PV85) and checks `forward_limit.gas >= admission_gas`; since `forward_limit.gas` can never reach the receipt's gas value, the branch always falls through to `NotForwarded`, and `buffer_receipt` re-queues it [2](#0-1) .
4. The receipt remains buffered indefinitely across all subsequent chunks, never reaching the destination shard.

    /// How much gas another shard can send to us in the next block.
    pub fn outgoing_gas_limit(&self, sender_shard: ShardId) -> Gas {
        let congestion = self.congestion_level();

        if Self::is_fully_congested(congestion) {
            // Red traffic light: reduce to minimum speed
            if sender_shard == ShardId::from(self.info.allowed_shard()) {
                self.config.allowed_shard_outgoing_gas
            } else {
                Gas::ZERO
            }
        } else {
            mix_gas(self.config.max_outgoing_gas, self.config.min_outgoing_gas, congestion)
        }
    }
