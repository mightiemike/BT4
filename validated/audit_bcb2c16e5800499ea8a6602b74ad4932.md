### Title
Panic (index-out-of-bounds) in `create_bytecode_segment_structure_inner` from unvalidated bytecode segment lengths - (File: crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs)

### Summary
`create_bytecode_segment_structure_inner` slices the CASM `bytecode` array using offsets and lengths derived directly from the (attacker-influenced) `bytecode_segment_lengths` field of a declared class's `CasmContractClass`, without first validating that the offsets/lengths are within bounds. The bounds check (`total_len != bytecode.len()`) is only performed by the wrapping function after the recursive traversal completes, so a segment length that overruns the bytecode buffer causes a Rust slice-index panic before the check can run.

### Finding Description
`create_bytecode_segment_structure` (lines 254-273) delegates to `create_bytecode_segment_structure_inner` and only afterwards compares the returned `total_len` against `bytecode.len()`. Inside `create_bytecode_segment_structure_inner` (lines 277-306), for a `NestedIntList::Leaf(length)` the code computes `segment_end = bytecode_offset + length` and immediately executes `bytecode[bytecode_offset..segment_end].to_vec()` (line 285) with no bounds check. If any leaf length (or an accumulation of leaf lengths through nested `Node` entries) causes `segment_end` to exceed `bytecode.len()`, this slicing operation panics with an out-of-range index — the Rust equivalent of the CVE's NULL-pointer/invalid-memory dereference during untrusted structured-data decoding. This function is invoked by the Starknet OS hint implementation while computing a compiled class's bytecode hash (`bytecode_segment_structure` hint) — a step exercised during Starknet OS re-execution/proving of blocks containing a `DECLARE` transaction for a Cairo 1 (Sierra→CASM) class. The `bytecode_segment_lengths` field of the `CasmContractClass` ultimately traces back to Sierra→CASM compilation output, which is invoked by the sequencer's gateway (`SierraToCasmCompiler::compile` in `crates/apollo_compile_to_casm/src/compiler.rs:30-55`) in a subprocess, and the JSON result is deserialized with `serde_json::from_slice::<CasmContractClass>` without independently validating that segment lengths sum consistently to `bytecode.len()` before it flows onward into the OS hash computation path. ### Impact Explanation
A panic inside a Starknet OS hint during block re-execution/proving on all honest nodes running that logic constitutes a denial-of-service: the affected node process crashes or the OS run aborts for a block containing the malformed declared class, preventing the network from confirming/proving that block. This matches the "network unable to confirm new transactions" acceptance criterion.

### Likelihood Explanation
Likelihood depends on whether the compiler subprocess used by the gateway (`apollo_compile_to_casm`) can ever be coerced into emitting a `bytecode_segment_lengths` value inconsistent with the true bytecode length, or whether any other path (e.g., a directly-supplied/pre-compiled `CasmContractClass`, or a legacy/alternate declare route) allows an attacker-controlled `CasmContractClass` with mismatched segment lengths to reach this OS hint without first invoking the trusted compiler. I was not able to fully verify within the available context whether the gateway strictly requires compilation through `SierraToCasmCompiler` for every declare path, or whether some code path allows a `CasmContractClass` to be supplied/reconstructed with attacker-chosen `bytecode_segment_lengths` that bypass the compiler's internal consistency guarantees before reaching `create_bytecode_segment_structure`. This uncertainty should be resolved by tracing all callers of `create_bytecode_segment_structure`/`create_bytecode_segment_structure_inner` and confirming whether `bytecode_segment_lengths` is ever taken from a source other than the trusted compiler's own output.

### Recommendation
Add an explicit bounds check inside `create_bytecode_segment_structure_inner` (or before calling it) that validates every computed `segment_end` does not exceed `bytecode.len()` at each recursion step, returning an `OsHintError` instead of panicking, mirroring the existing post-hoc check in `create_bytecode_segment_structure` but performed proactively before any slicing occurs.

### Proof of Concept

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
