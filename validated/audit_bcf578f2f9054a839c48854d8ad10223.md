## Local Analog Found: Replay-Verification Accepts Divergent Position-State Root as Valid

### Title
`TransactionOutput::ensure_match_transaction_info` never checks `position_state_checkpoint_hash`/`hot_state_checkpoint_hash`, so authenticated replay/DB-tool verification returns success on a corrupted native-position ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk-replay and `db-tool`'s `replay_on_archive` path to authenticate a locally-recomputed `TransactionOutput` against the trusted `TransactionInfo` fetched from an archive/peer. It checks status, gas, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are supposed to authenticate the state/hot-state/native-position Merkle roots.

### Finding Description
`TransactionInfo`/`TransactionInfoV1` carries multiple checkpoint-hash fields alongside `state_change_hash` and `event_root_hash`: [1](#0-0) 

The verification routine that binds a locally-produced `TransactionOutput` to an authenticated `TransactionInfo` (used by replay/verification tooling) checks write-set hash, gas, status, and event root, but the comment explicitly documents that it deliberately ignores the checkpoint hashes: [2](#0-1) 

This is called from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs` — all authenticated-verification consumers relying on this function's `Ok(())` to mean "the recomputed output matches the trusted commitment."

Meanwhile the actual root computation for the native-position tree is done in `DoStateCheckpoint::compute_position_checkpoint`, which folds native-position write-set entries into a separate sharded Jellyfish-Merkle-style summary and emits per-transaction `position_state_checkpoint_hash` values gated by `execution_output.compute_trading_native_state_roots`: [3](#0-2) [4](#0-3) 

Those hashes are embedded into `TransactionInfoV1` at commit time in `assemble_transaction_infos`: [5](#0-4) 

Because `ensure_match_transaction_info` never re-derives and compares this field, any divergence between a replaying node's locally computed native-position (or hot-state) root and the authenticated `TransactionInfo`'s corresponding field is silently accepted as a match. The root-cause is purely local: the comparator is incomplete relative to the fields it is supposed to authenticate, independent of any privileged actor or malicious peer — it is a structural gap in the verification function itself.

### Impact Explanation
This breaks the "authenticated API/replay output must stay bound to the correct proof/root" invariant required for state-integrity: a node (or `db-tool replay_on_archive`, or `aptos-debugger`) can execute transactions whose native-position ledger state or hot-state diverges from the canonical chain, yet `ensure_match_transaction_info` reports success. This can mask a bug in the position-state (or hot-state) accumulation logic, silently propagate an incorrect ledger state through replay-verification tooling used to validate archives/backups, and produce false confidence that a node's replayed history matches the authenticated chain when in fact its committed position/hot-state Merkle root has diverged. Since this tooling is explicitly used to validate replayed/archived data for correctness (the reason it exists), a corrupted or buggy state root can go undetected, which is exactly the class of "wrong accumulator/Merkle root accepted as valid" harm called out by the state-integrity gate.

### Likelihood Explanation
This is not a triggerable attacker exploit in the sense of forging state on mainnet in real time by an external unprivileged party; it requires either (a) a bug/regression in the native-position or hot-state computation path (`DoStateCheckpoint::compute_position_checkpoint`, hot-state updates) actually producing incorrect roots, or (b) a byzantine/faulty state-sync/backup source serving replay data whose committed native-position state has been tampered with while other fields (write-set hash, event hash, gas, status) remain correct. Given the code's own inline comment flags this precisely as a known gap ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"), the likelihood that this gap is hit in practice (masking a real regression during a native-position feature rollout) is credible, but it does not on its own let an unprivileged party corrupt consensus-committed state; it is a proof-integrity/verification-completeness bug rather than a live state-corruption exploit.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding value is present in the trusted `TransactionInfo`, mirroring the recomputation done in `DoStateCheckpoint`. At minimum, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or the hot-state feature) is enabled, callers of this function should be required to pass in the locally computed checkpoint hashes and assert equality before treating replay as successful.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-completeness gap in `ensure_match_transaction_info`, confirmed by direct code reading of `types/src/transaction/mod.rs:2139-2204`, which only calls `ensure!` on status, gas, `write_set_hash`, and `event_root_hash`, and never reads `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`, despite those fields existing on `TransactionInfoV1` (lines 2261-2283) and being populated from real computed roots in `do_state_checkpoint.rs`/`do_ledger_update.rs`. A concrete PoC would require constructing a `TransactionInfoV1` whose `position_state_checkpoint_hash` differs from the locally-recomputed root while write-set/event/gas/status match, and observing `ensure_match_transaction_info` return `Ok(())`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

                        value_hash,
                        value: None,

                }

        };

        let (new_latest, new_last_checkpoint) = if let Some(ci) = last_checkpoint_index {

                collect(0..ci + 1),
                base_summary,
                persisted,
            )?;
            if ci + 1 == num_txns {
                (new_ckpt.clone(), new_ckpt)

                let last_version = first_version + num_txns as u64 - 1;
