### Title
Webhook shop-domain spoofing via unsigned `X-Shopify-Shop-Domain` header — cross-tenant webhook processing - ([File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts])

### Summary
`authenticateWebhookFactory` derives the trusted shop identity (`check.domain`) from the `X-Shopify-Shop-Domain` request header, but the HMAC signature that gates webhook acceptance is computed only over the raw request body, never over that header. An attacker who can obtain any single body+HMAC pair signed with the app's shared secret (e.g. by installing the target app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop, and the library will accept it as valid and process it under the victim shop's offline session.

### Finding Description
`validateFactory` in [1](#0-0)  validates the request by calling `validateHmacFromRequestFactory`, which computes `HMAC-SHA256(apiSecretKey, rawBody)` and compares it (base64) against the `X-Shopify-Hmac-Sha256` header via `validateHmacString`/`safeCompare`: [2](#0-1) . Crucially, no other header — including `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` — is included in the HMAC input.

After the HMAC check passes, `checkWebhooksHeaders`/`checkEventsHeaders` simply read those headers verbatim off the request and return them as trusted fields, with no cryptographic binding to the signed body: [3](#0-2) .

Back in `authenticateWebhookFactory`, `check.domain` (the unsigned header value) is used directly to look up and authenticate the offline session for that shop: [4](#0-3) . If a session exists for that shop, an admin API client bound to that victim session is constructed and returned to the webhook handler: [5](#0-4) .

Exploit flow:
1. Attacker installs the target app on their own store (unprivileged — normal OAuth install), and Shopify sends the attacker's store a legitimately-signed webhook (`rawBody`, `X-Shopify-Hmac-Sha256`) using the app's shared secret.
2. Attacker replays that exact `rawBody` + HMAC header to the app's webhook endpoint, but substitutes `X-Shopify-Shop-Domain` with a victim shop domain (any shop that has an offline session stored for the app, e.g., a public app's other real installs).
3. `validateHmacString` still succeeds because the HMAC only checks the (unmodified) body, so `check.valid === true` and `check.domain` equals the attacker-supplied victim domain.
4. `ensureValidOfflineSession(params, check.domain)` retrieves the victim's real offline session/access token, and the webhook handler executes with `webhookContext.shop === victim`, `admin` bound to the victim's token, and the attacker-controlled payload from their own store's webhook.

This breaks the intended invariant that shop identity is bound to the verified signature — the signature only proves the body came from Shopify for *some* shop, not which shop.

### Impact Explanation
This allows a single (attacker-controlled) shop's genuine webhook to be misattributed to another (victim) tenant of the same app, once replayed with a modified domain header. Depending on the app's webhook handler logic, this can cause cross-tenant state changes or actions performed using the victim's real admin API session/access token in response to attacker-supplied payload data, and can spoof events like `APP_UNINSTALLED` against the victim shop even though it was never triggered by that shop. This matches the "cross-tenant webhook action" impact class referenced in the question.

### Likelihood Explanation
Practical exploitation requires: (1) attacker can install the target app on a shop they control (feasible for any public app, and many apps are freely installable), (2) attacker knows or can guess a victim shop domain that has an active offline session with the app (often discoverable, e.g. via app listings, public store fronts, or by targeting apps with predictable/enumerable customer bases), and (3) the app's webhook route uses `authenticate.webhook` without any additional out-of-band binding of the webhook payload to the claimed shop. No secret theft, MITM, or privileged role is required — only normal app installation and the ability to POST an HTTP request with custom headers to the app's public webhook endpoint. This is a repeatable, request-level replay, not a probabilistic race.

### Recommendation
Bind the shop-domain claim to the signed material rather than trusting the raw header. Concrete options:
- Cross-check `check.domain` against the shop that Shopify's webhook subscription registry expects for the given `webhookId`/subscription, if tracked, before honoring it.
- Where using the newer Shopify "Events" delivery format, verify against any cryptographically-bound shop identifier that Shopify includes as part of the signed payload/claims, instead of a bare header field.
- At minimum, document that host apps must not treat webhook shop-domain headers as trusted without additional verification, and add a defense-in-depth check that rejects webhooks whose `check.domain` was never associated with a webhook registration recorded by the app for that specific `webhookId`.

### Proof of Concept
```ts
// packages/apps/shopify-app-remix/src/server/authenticate/webhooks/__tests__/authenticate.spoof.test.ts
import {shopifyApp} from '../../..';
import {APP_URL, TEST_SHOP, getHmac, testConfig} from '../../../__test-helpers';

const VICTIM_SHOP = 'victim-shop.myshopify.com';

it('accepts a webhook whose domain header does not match the HMAC-signing shop', async () => {
  const shopify = shopifyApp(testConfig()); // assume both TEST_SHOP and VICTIM_SHOP have offline sessions stored
  const body = {some: 'attacker-controlled-data'};
  const rawBody = JSON.stringify(body);

  // HMAC is computed over rawBody with the SAME shared secret for all shops;
  // it does NOT include X-Shopify-Shop-Domain.
  const validHmac = getHmac(rawBody);

  const request = new Request(`${APP_URL}/webhooks`, {
    method: 'POST',
    body: rawBody,
    headers: {
      'X-Shopify-Shop-Domain': VICTIM_SHOP, // attacker-forged, not the shop that produced this body
      'X-Shopify-Topic': 'app/uninstalled',
      'X-Shopify-API-Version': '2023-01',
      'X-Shopify-Webhook-Id': '1234567890',
      'X-Shopify-Hmac-Sha256': validHmac,
    },
  });

  const context = await shopify.authenticate.webhook(request);

  // FAIL: library trusts the header instead of rejecting mismatched shop identity
  expect(context.shop).toBe(VICTIM_SHOP);
  expect(context.session?.shop).toBe(VICTIM_SHOP);
});
```
Expected (vulnerable) result: the request passes HMAC validation and returns a `WebhookContext` bound to `VICTIM_SHOP`'s offline session/admin client, even though the HMAC was never computed with any binding to that shop.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
