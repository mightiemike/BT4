## Analog Found

The bug class from the Sherlock report — an upgradeable dependency contract (`PoolOracle`) that a privileged party can point to broken code, causing critical account logic (`_tweakPosition`, `burn`, `mint`) to permanently revert and lock user funds — maps directly onto nearcore's **AccountId-mode global contracts** used by **deterministic accounts**.

### Title
Deterministic accounts referencing an `AccountId`-mode global contract can be permanently bricked when the contract owner redeploys broken code, freezing account funds - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
A `GlobalContractDeployMode::AccountId` global contract is mutable: whoever owns the deploying account can redeploy new code under the same `AccountId` identifier at any time, and every account referencing it via `GlobalContractIdentifier::AccountId` (through `UseGlobalContractByAccountId` or `DeterministicStateInitAction`) immediately runs the new code. Deterministic accounts (`0s…` accounts) are explicitly designed to never hold a full access key, so the only way to change their `code` reference is by calling `UseGlobalContract`/`UseGlobalContractByAccountId` from inside a transaction that the account itself signs, or from within its own currently-running contract logic. If the referenced global contract is redeployed with code that lacks the exposed methods (e.g. no methods at all, or a contract missing the function used to reassign/withdraw), the deterministic account can never again execute a state-changing call, including one that would let it switch to different code, and any funds credited to it become permanently unreachable.

### Finding Description
- Global contracts deployed with `GlobalContractDeployMode::AccountId` are explicitly documented as mutable and re-deployable by their owning account: "This allows the owner to update the contract for all its users." [1](#0-0) 
- `action_deploy_global_contract` allows redeploying under the same `AccountId` identifier at any time, with no protection for existing referencing accounts. [2](#0-1) 
- The test `test_global_contract_update` demonstrates the exact failure mode: after redeploying an `AccountId`-mode global contract with a "trivial" contract lacking any methods, every account referencing it by `AccountId` starts failing all function calls with `MethodResolveError::MethodNotFound`. [3](#0-2) 
- Deterministic accounts (created via `DeterministicStateInitAction`, referencing `GlobalContractIdentifier` in their `DeterministicAccountStateInitV1.code`) are architected to have **no full access key at all** — the docs describe implicit accounts as having "a fixed access key," but deterministic accounts instead have "fixed code and fixed initial state," with no equivalent key mechanism described. [4](#0-3) 
- This is reinforced by `test_transfer_and_add_key_to_deterministic_account` and `test_contract_transfer_and_add_key_to_deterministic_account`, both of which assert it must be impossible to add an access key to a deterministic account, even from within its own contract via `call_promise`. [5](#0-4) [6](#0-5) 
- `use_global_contract`/`action_use_global_contract`, which switch an account's `AccountContract` to a different global contract, perform no special authorization beyond standard action execution against the receiver account — meaning switching away from a broken global contract requires either a signed transaction from an access key of that account (which deterministic accounts never have) or a self-initiated call from the account's own currently-executing contract code. [7](#0-6) 

Putting this together: any account can deploy a global contract in `AccountId` mode and any number of deterministic accounts (each potentially holding a NEAR balance for storage or transferred funds) can reference it via `DeterministicStateInitAction`. If the deploying account later redeploys broken/incompatible code under that same `AccountId` (maliciously, by mistake, or after key compromise), all deterministic accounts pointing to it immediately lose the ability to execute any meaningful method — including whatever method would let them call `UseGlobalContractByAccountId` to escape to different code — because they have no access key to independently authorize an escape transaction.

### Impact Explanation
Funds held in any deterministic account that referenced the now-broken `AccountId`-mode global contract become permanently frozen: there is no access key to sign an escape transaction, and the currently-running (broken) contract code cannot expose the needed self-repair logic. This satisfies "permanently frozen funds" from a single external action (the global contract owner's redeploy transaction) with no operator/validator privilege required — the global contract owner is just an ordinary account.

### Likelihood Explanation
The `AccountId` deploy mode is a documented, always-available feature of global contracts, and `DeterministicStateInitAction` allowing `GlobalContractIdentifier::AccountId` references is likewise a standard, unprivileged capability. No special permission is needed by the global contract owner to redeploy; this can happen due to a buggy upgrade, a compromised deployer key, or malicious intent, and nothing in the runtime prevents it from bricking dependent deterministic accounts.

### Recommendation
Consider preventing deterministic accounts from referencing mutable (`AccountId`-mode) global contracts, or require an escape hatch (e.g., a runtime-level fallback / minimal always-present function such as `UseGlobalContract` self-repair callable independent of currently deployed code) so dependent accounts cannot be permanently bricked by a third party's contract redeploy. Alternatively, restrict `AccountId`-mode global contract redeployment to be additive/versioned, or require deterministic accounts to pin a specific `CodeHash` rather than a mutable `AccountId` reference.

### Proof of Concept
1. Account `D` deploys a global contract in `AccountId` mode with a full-featured contract (e.g. supporting withdrawal/transfer methods).
2. Any user submits `DeterministicStateInitAction` creating deterministic account `0s...` with `code = GlobalContractIdentifier::AccountId(D)` and deposits funds into it (test harness: `env.new_deterministic_account_with_data(...)`, mirroring `test-loop-tests/src/tests/deterministic_account_id.rs`).
3. Account `D` redeploys the global contract under `AccountId` mode with a trivial/broken contract exposing no usable methods, exactly as done in `test_global_contract_update` (`test-loop-tests/src/tests/global_contracts.rs:71-106`).
4. Any function call against the deterministic account now fails with `MethodResolveError::MethodNotFound` (or equivalent), and because the deterministic account has no access key (enforced by `test_transfer_and_add_key_to_deterministic_account`), no transaction can ever be signed on its behalf to call `UseGlobalContractByAccountId` and escape to different code — the account and any funds within it are permanently inaccessible.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

## Deterministic accounts

Deterministic accounts are an advanced kind of implicit account.
A normal implicit account has a fixed access key that is implicitly associated with it.
Deterministic accounts have a fixed code and fixed initial state associated with it.

### State-initializing data of deterministic accounts

The initial state of a deterministic account is fully defined by an instance of `DeterministicAccountStateInit`.

Key-value pairs in `data` must be at most `max_length_storage_key` and `max_length_storage_value` bytes long,

/// Try to do Transfer and AddKey in a single transaction targeting a
/// deterministic account. A single Transfer can create a deterministic
/// account, but multiple actions are disallowed.
/// It should not be possible to add an access key to a deterministic account this way, as it would
/// give the creator control over the account before StateInit.
#[test]
fn test_transfer_and_add_key_to_deterministic_account() {
    let mut env = TestEnv::setup(Balance::from_near(100));
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let data = empty();
    let (_state_init, det_account) = env.new_deterministic_account_with_data(data);

    let user_signer = create_user_test_signer(&env.user_account());
    let public_key = PublicKey::from_seed(KeyType::ED25519, "test");

    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        env.user_account(),
        det_account,
        &user_signer,
        vec![
            Action::Transfer(TransferAction { deposit: Balance::from_near(1) }),
            Action::AddKey(Box::new(AddKeyAction {
                public_key,
                access_key: AccessKey::full_access(),
            })),
        ],
        env.get_tx_block_hash(),
    );

    let outcome = env.try_execute_tx(tx).expect("should be able to send transaction");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::AccountDoesNotExist { .. },
            index: Some(0)
        }))
    );
}
