### Title
Unchecked `reduceAssetAmountV2`/`addAssetAmountV2` return value in `ExchangeTransactionActuator`/`ExchangeInjectActuator` allows asset-balance state divergence - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`AccountCapsule.reduceAssetAmountV2` / `addAssetAmountV2` return a `boolean` indicating whether the asset-balance mutation actually succeeded (e.g. `false` when the account lacks the asset key or the amount exceeds the current balance) [1](#0-0) . Several call sites correctly check this return value and abort on failure — `TransferAssetActuator.execute` [2](#0-1) , `ParticipateAssetIssueActuator.execute` [3](#0-2) , and `Commons.adjustAssetBalanceV2` [4](#0-3)  — but `ExchangeTransactionActuator.execute` and `ExchangeInjectActuator.execute` call the same mutators and silently discard the boolean result.

### Finding Description
In `ExchangeTransactionActuator.execute`, the owner's asset balance is decremented and the counter-asset balance is incremented without checking the returned success flag: [5](#0-4) 

The same unchecked pattern appears twice in `ExchangeInjectActuator.execute`: [6](#0-5) 

This mirrors exactly the reported bug class: a function whose boolean return communicates "operation not permitted / not applied" is called for its side effect only, and the caller proceeds as if the operation succeeded regardless of the actual outcome. Just as `RemoraToken::adminTransferFrom` ignored `Allowlist::exchangeAllowed`'s `false` return and let the transfer proceed, here the actuator ignores `reduceAssetAmountV2`/`addAssetAmountV2`'s `false` return and continues committing the exchange: it updates `exchangeCapsule` pool balances via `Commons.putExchangeCapsule` and persists `accountCapsule` to `accountStore.put(...)`, and marks the transaction `code.SUCESS`, even when the underlying per-account asset ledger update silently failed to apply.

By contrast, sibling actuators (`TransferAssetActuator`, `ParticipateAssetIssueActuator`) treat a `false` return as a hard failure and throw `ContractExeException`, preventing the transaction from committing a state where TRC10 accounting is inconsistent.

### Impact Explanation
If `reduceAssetAmountV2`/`addAssetAmountV2` returns `false` inside `ExchangeTransactionActuator`/`ExchangeInjectActuator`.execute (e.g., due to `importAsset` lazily materializing/removing map entries, precision/rounding divergence between the `validate()`-time check and the actual balance at execute time, or any state change to the account's asset map between validation and execution within the same actuator run), the actuator will still:
- update the on-chain `ExchangeCapsule` pool balances (`firstTokenBalance`/`secondTokenBalance`) as if the trade completed,
- persist the account without the intended debit (or credit),
- report the transaction as `SUCESS`.

This produces an accounting divergence between the exchange pool's recorded liquidity and the actual TRC10 asset supply held by accounts — funds can be effectively created or destroyed relative to the exchange's internal bookkeeping, without any exception or rollback. This is a concrete accounting/invalid-state impact matching the "settlement / invalid-state divergence" class called out in the validation rubric.

### Likelihood Explanation
Exploitability depends on being able to trigger a `false` return from `reduceAssetAmountV2`/`addAssetAmountV2` after `validate()` has already passed (both are unprivileged, user-callable contracts — `ExchangeTransactionContract` and `ExchangeInjectContract` — reachable by any account holding TRC10 assets and an active exchange pair). I could not fully confirm within this investigation whether `validate()`'s pre-checks (`assetBalanceEnoughV2`) and `execute()`'s actual mutation are guaranteed to observe identical account/asset state in all code paths (e.g., `importAsset` behavior, concurrent modifications across the block, or `AllowSameTokenName` transition edge cases straddling the two calls) — this would require deeper tracing of `importAsset` and the block-processing pipeline to fully confirm a reliable trigger. Regardless of the practical trigger difficulty, the code pattern itself is a genuine defensive-coding gap identical in shape to the reported vulnerability class, and the sibling actuators demonstrate that the correct practice (checking the return and reverting) was known and applied elsewhere but omitted here.

### Recommendation
Check the boolean return of `reduceAssetAmountV2`/`addAssetAmountV2` in both `ExchangeTransactionActuator.execute` and `ExchangeInjectActuator.execute`, and throw `ContractExeException` (as done in `TransferAssetActuator`/`ParticipateAssetIssueActuator`) whenever the mutation fails, rather than silently continuing to commit the exchange pool state and marking the transaction successful.

### Proof of Concept
Not independently reproduced against a live node; the analysis is based on static code review of the four cited files. To construct a concrete PoC, a background engineer would need to:
1. Identify a state transition where `assetBalanceEnoughV2` (checked in `doValidate()`) and the subsequent `reduceAssetAmountV2` (called in `execute()`) can observe different account asset balances — e.g. via `importAsset`'s lazy map population/removal semantics in `AccountCapsule` — or a case where `anotherTokenQuant`'s `addAssetAmountV2`/`reduceAssetAmountV2` in `ExchangeInjectActuator` is not covered by any pre-validation of the *account's* balance for the second leg.
2. Trigger `ExchangeTransactionContract`/`ExchangeInjectContract` execution under that condition and observe that the transaction succeeds (`code.SUCESS`) while the account's TRC10 asset map does not reflect the expected debit/credit, yet the `ExchangeCapsule` pool balances are updated — confirming the divergence.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
