### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` can throw `ArithmeticException` and abort TVM contract calls - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, which is the energy-limit calculation used by the TVM execution path (`VMActuator`) for every smart-contract call from an account that has frozen TRX for energy, divides by `totalEnergyWeight` while only guarding the divisor with a Java `assert` statement. Assertions are disabled by default in production JVMs, so the guard is a no-op at runtime. The sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit()`, used for non-TVM bandwidth/energy accounting, contains an explicit runtime check (`if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) return 0;`) that is missing from the `RepositoryImpl` copy. This mirrors the reported DEX bug class: a divisor that is only protected in one code path (or only protected in a state that can become stale/absent), while the parallel path performing the same calculation lacks the guard and can divide by zero.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit`:
```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
``` [1](#0-0) 

Compare this to `EnergyProcessor.calculateGlobalEnergyLimit`, which is the analogous (legacy, non-TVM) implementation:
```java
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
``` [2](#0-1) 

`EnergyProcessor` has a real, executable guard (`totalEnergyWeight <= 0 → return 0`) in addition to the no-op `assert`. `RepositoryImpl`'s copy of this logic — reachable from `VMActuator` on every TVM contract invocation where the caller/creator has frozen balance for energy — only has the `assert`, which does nothing unless the JVM is started with `-ea`. If `totalEnergyWeight` is 0 (or negative) when this code executes, and `hardenResourceCalculation()`/`VMConfig.allowHardenResourceCalculation()` is enabled, `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException` directly in a code path invoked from ordinary `TriggerSmartContract` transactions:
```java
long leftFrozenEnergy = rootRepository.getAccountLeftEnergyFromFreeze(account);
...
long energyFromBalance = max(account.getBalance() - callValue, 0, ...) / sunPerEnergy;
``` [3](#0-2) 
`getAccountLeftEnergyFromFreeze` calls `calculateGlobalEnergyLimit` directly:
```java
public Pair<Long, Long> getAccountLeftEnergyFromFreeze... {
  ...
  long energyLimit = calculateGlobalEnergyLimit(accountCapsule);
``` [4](#0-3) 

I found tests that explicitly document the divide-by-zero/overflow behavior of the hardened path (`testGlobalEnergyLimitOverflowDetectedWithHardening`, `testCalculateGlobalEnergyLimitHardenedOverflowDetected`), confirming `ArithmeticException` is a real, reachable outcome of this calculation under the hardened flag, though those tests target overflow rather than the zero-weight scenario specifically. ### Impact Explanation
If `totalEnergyWeight` reaches zero while an account still has a frozen-for-energy balance under the legacy (non-`supportUnfreezeDelay`) freeze model, every TVM call ( `TriggerSmartContract`, contract creation, or any transaction where `getAccountEnergyLimitWithFixRatio`/`getAccountLeftEnergyFromFreeze` is evaluated for that account) throws an uncaught `ArithmeticException` inside `RepositoryImpl`. This is a DoS vector against transaction execution for the affected account(s) (and, because this is deterministic block-execution logic, it would fail identically on every node, i.e., it is a chain-wide execution failure for those transactions rather than a consensus split). I was not able to fully trace, within the available time, whether `VMActuator`/`TransactionTrace` wrap this exception in a try/catch that safely reverts the single transaction, or whether it propagates and disrupts block processing — this is an area needing further investigation.

### Likelihood Explanation
Likelihood is low-to-medium and conditional: it requires (1) the legacy V1 freeze-for-energy model to still apply to an account (`!dynamicPropertiesStore.supportUnfreezeDelay()`), (2) `totalEnergyWeight` to be exactly `0` (which is guarded against in the parallel `EnergyProcessor` path but not in `RepositoryImpl`), and (3) `VMConfig.allowHardenResourceCalculation()` to be enabled (the non-hardened double-arithmetic branch would instead silently produce `NaN`/`0` rather than throwing). I could not confirm from the code review alone whether `totalEnergyWeight` can practically reach `0` on a live chain with legacy frozen accounts still present, so likelihood is uncertain without further chain-state/config analysis.

### Recommendation
Add the same explicit, non-assert guard used in `EnergyProcessor.calculateGlobalEnergyLimit` to `RepositoryImpl.calculateGlobalEnergyLimit`:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```
placed before the `hardenResourceCalculation()`/division branch, so behavior is safe regardless of whether Java assertions are enabled (`-ea`) at runtime.

### Proof of Concept
Not independently reproduced against a running node in this analysis; the reasoning is based on static code comparison between `RepositoryImpl.calculateGlobalEnergyLimit` (unguarded except by a no-op `assert`) and `EnergyProcessor.calculateGlobalEnergyLimit` (guarded by a real `if` check), plus existing project tests (`testGlobalEnergyLimitOverflowDetectedWithHardening`, `testCalculateGlobalEnergyLimitHardenedOverflowDetected`) that confirm the hardened BigInteger division path throws `ArithmeticException` under adverse divisor conditions. A full PoC would require: (1) constructing a legacy (non-`supportUnfreezeDelay`) account with `frozenBalance >= TRX_PRECISION` for energy, (2) driving `dynamicPropertiesStore.saveTotalEnergyWeight(0)` (or finding a legitimate state transition that reaches this), (3) enabling `allowHardenResourceCalculation`, and (4) issuing a `TriggerSmartContract` transaction from that account and observing the `ArithmeticException`. This last verification step (whether `totalEnergyWeight` can organically reach `0` while such a legacy account exists, and how the exception propagates through `VMActuator`) was not completed within the scope of this review.
