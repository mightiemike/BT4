## Finding

### Title
`ensure_match_transaction_info` skips state-checkpoint hash validation, allowing divergent state roots to pass replay/execution verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to confirm that a locally-computed transaction output (write set, events, status, gas) matches the trusted, proof-authenticated `TransactionInfo` for that version [1](#0-0) . It checks status, gas, write-set hash, and event root hash, but explicitly and knowingly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values baked into the authenticated `TransactionInfo` [2](#0-1) .

### Finding Description
`TransactionInfo` (V0/V1) carries `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, which are the Merkle roots of the world state after execution, committed into the transaction accumulator and thus authenticated by ledger-info signatures [3](#0-2) . `ensure_match_transaction_info` is the consistency gate meant to catch any divergence between a node's own re-execution and this authenticated record — it is used in `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs`.

The maintainers' own TODO on this function states the gap directly: replay-verify tooling (e.g. `db-tool`'s `replay_on_archive`) "can report a successful replay even when the authenticated position state root diverges from local execution," and instructs that checkpoint hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [4](#0-3) . `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a real, wired-in on-chain feature flag (referenced in `types/src/on_chain_config/aptos_features.rs`, `storage/aptosdb/src/db/aptosdb_reader.rs`, and the framework `features.move`), i.e. this is not a hypothetical future feature — it exists in the codebase and gates real state-root computation logic, but the verifier that is supposed to detect a mismatch does not check the very hashes this feature introduces/repurposes.

### Impact Explanation
If local re-execution during chunk replay, verified state sync, or `replay-verify`/`db-tool` produces write sets and events that hash-match but computes an incorrect state-checkpoint (i.e., diverges in the Merkle root of the resulting state — e.g. due to a bug in state-checkpoint hash computation, hot-state handling, or the position-state summary path), `ensure_match_transaction_info` will report success. This breaks the intended invariant that locally-committed/replayed state matches the authenticated ledger state exactly, which is precisely the "hard-fork-only divergence during commit/replay/restore/proof verification" class of impact: a node could silently persist or accept a state root that differs from the true committed state without any consistency check catching it.

### Likelihood Explanation
This is a self-acknowledged gap (not speculative) documented directly in the source by the Aptos team, tied to a live, wired feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) already present in `aptos_features.rs`, `aptosdb_reader.rs`, and `features.move`. It requires no privileged actor — it triggers on ordinary replay/verification paths whenever a divergence exists in state-checkpoint hash computation logic; the bug is that the safety-net meant to catch such divergence is incomplete.

### Recommendation
Extend `ensure_match_transaction_info` to also compare locally-derived `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/derivable) against `txn_info`'s corresponding fields, and fail loudly on mismatch, before any callers (chunk executor, debugger, db-tool replay) rely on it as a correctness gate, especially ahead of enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not independently reproducible as a runnable PoC from static analysis alone — the finding is a code-level proof of a missing invariant check, confirmed by the maintainers' own TODO comment at [5](#0-4) , combined with tracing all real call sites of `ensure_match_transaction_info` that rely on it as a correctness gate.

**Caveat:** I could not fully confirm within this investigation whether `chunk_executor/mod.rs`'s call to `ensure_match_transaction_info` occurs in the mandatory, always-on state-sync commit path versus only under `VerifyExecutionMode`/`ReplayChunkVerifier` (an opt-in verification mode); this affects whether the impact is "always-on ledger integrity" or "verification-tooling-only." Given tool-call limits, I was unable to read the exact call site in `execution/executor/src/chunk_executor/mod.rs` to pin this down further.
