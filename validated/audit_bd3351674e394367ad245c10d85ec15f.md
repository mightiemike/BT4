I have sufficient information to answer now.

The `ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap` implementation lacks a length check that every other chain-family implementation has (`ccipevm`, `ccipaptos`), confirming the vulnerability is real, and there is no generic `recover()` wrapper in the CCIP OCR plugin call chain (`MessageHasherV1.Hash`, `ExecutePluginCodecV1.Encode`) that would catch such a panic.

### Title
Unrecovered panic in `DecodeDestExecDataToMap` via undersized `destExecData` crashes the CCIP oracle process - ([File: core/capabilities/ccip/ccipsolana/extradatacodec.go])

### Summary
`ExtraDataDecoder.DecodeDestExecDataToMap` in `ccipsolana/extradatacodec.go` calls `binary.BigEndian.Uint32(destExecData)` with no length validation, unlike its sibling implementations (`ccipevm.ExtraDataDecoder.DecodeDestExecDataToMap` and `ccipaptos.ExtraDataDecoder.DecodeDestExecDataToMap`), which either use ABI/BCS decoders that return errors or explicitly check `len(destExecData) != 4`. Any message with `TokenAmounts[i].DestExecData` shorter than 4 bytes reaching a Solana-destination oracle causes an unrecovered `panic: runtime error: slice bounds out of range` inside privileged OCR report-generation code.

### Finding Description
`DecodeDestExecDataToMap` is:
```go
func (d ExtraDataDecoder) DecodeDestExecDataToMap(destExecData cciptypes.Bytes) (map[string]any, error) {
	return map[string]any{
		svmDestExecDataKey: binary.BigEndian.Uint32(destExecData),
	}, nil
}
``` [1](#0-0) 

`binary.BigEndian.Uint32` indexes `b[3]` unconditionally; for any slice shorter than 4 bytes this panics with an unrecovered slice-bounds-out-of-range error, unlike its EVM (`abiDecodeUint32`, which returns an error on malformed input) and Aptos (`if des.Remaining() != 4 { return nil, fmt.Errorf(...) }`) counterparts: [2](#0-1) [3](#0-2) 

This method is reached via the `ExtraDataCodecRegistry`/`ExtraDataCodecMap.DecodeTokenAmountDestExecData` dispatch (keyed by source-chain family) from multiple privileged call sites that process every `RampTokenAmount.DestExecData` field of a CCIP message with no upstream length validation:
- `ccipsolana.MessageHasherV1.Hash`, called during OCR observation/report hashing for Solana-destination lanes: [4](#0-3) 
- `ccipsolana.ExecutePluginCodecV1.Encode`, used when building the execute report during `Reports()`: [5](#0-4) 
- `ccipsolana.EstimateProvider.CalculateMessageMaxGas`, which explicitly `panic(err)`s on any error from `CalculateMessageMaxGasWithError` — meaning even a returned error (were one added) would still panic here today: [6](#0-5) 

`DestExecData` originates from the source-chain onramp/token-pool logic that is populated at `ccipSend` time based on token-pool configuration (e.g., dest gas overhead), and cross-chain relayers copy these bytes verbatim into the `cciptypes.RampTokenAmount.DestExecData` field without re-validating length before codec decoding — the check that exists in the EVM/Aptos codecs is simply missing for Solana. No existing authz, signature, or codec-level length check intercepts an under-length `destExecData` before it reaches `binary.BigEndian.Uint32`.

Searching the CCIP-relevant code, there is no generic `recover()` around `Hash`/`Encode`/`Reports` in the OCR3/OCR3.1 plugin wrapper chains (`promwrapper`, `beholderwrapper`) — these wrappers only instrument timing/metrics and propagate errors, they do not recover panics: [7](#0-6) [8](#0-7) . A panic in `Observation`/`Reports` will propagate up and crash the OCR3 plugin goroutine/process for that job.

### Impact Explanation
An unrecovered panic inside `Hash`/`Encode`/gas estimation during OCR observation or report generation for a Solana destination lane crashes the running plugin/oracle process for that job, causing node/oracle liveness loss for the affected CCIP lane (denial-of-service). This matches "node crash / liveness loss triggered by unauthenticated on-chain input" bounty impact category — it does not disclose secrets or allow unauthorized transactions, but does degrade CCIP oracle availability.

### Likelihood Explanation
Feasibility is high and repeatable: any unprivileged account that can call `ccipSend` (or otherwise get a message with a short `DestExecData` accepted by a source-chain onramp/token pool) targeting a Solana destination lane can trigger this. No node-operator privilege, leaked keys, or malicious peer collusion is required — a single malformed/short `destExecData` value processed once by any oracle node running the Solana destination plugin config is sufficient to crash the plugin.

### Recommendation
Add an explicit length check in `ExtraDataDecoder.DecodeDestExecDataToMap` in `core/capabilities/ccip/ccipsolana/extradatacodec.go`, mirroring the Aptos/EVM implementations, e.g.:
```go
func (d ExtraDataDecoder) DecodeDestExecDataToMap(destExecData cciptypes.Bytes) (map[string]any, error) {
	if len(destExecData) != 4 {
		return nil, fmt.Errorf("dest exec data invalid length: %d, should be 4 bytes", len(destExecData))
	}
	return map[string]any{
		svmDestExecDataKey: binary.BigEndian.Uint32(destExecData),
	}, nil
}
```
Additionally, replace the `panic(err)` in `ccipsolana.EstimateProvider.CalculateMessageMaxGas` with proper error propagation so a future returned decode error cannot itself become an unrecovered panic.

}
