## Finding

Replay-verification tooling in this repo authenticates re-executed transactions against archived `TransactionInfo` via `TransactionOutput::ensure_match_transaction_info()`, but that comparator never checks the state-checkpoint hash fields carried in `TransactionInfo` — meaning a divergent state root can pass "verification" silently.

### Title
Replay-verify comparator omits state/hot-state/position checkpoint hash checks, allowing undetected state-root divergence - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, `aptos-move/cli`) to confirm that a locally re-executed transaction output matches the transaction info that was actually committed and accumulator-authenticated on chain. It checks status, gas used, write-set hash, and event-root hash, but it explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that bind a transaction to the authoritative JMT/state-summary root.

### Finding Description
The function is defined at [1](#0-0)  and performs status/gas/write-set/event checks, but ends with a bare `Ok(())` accompanied by a self-documented gap: [2](#0-1) 

This means none of `TransactionInfo`'s checkpoint-hash fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are ever compared against the value actually produced by local re-execution.

This comparator is the sole state-divergence check used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` on each output to decide pass/fail: [3](#0-2) 

Because `state_checkpoint_hash` (the root of the account/global state Merkle tree at a checkpoint boundary) is excluded from this check, if local re-execution produces a different state root than what was actually committed and accumulator-signed on-chain — due to a bug in a state-computation path, a non-deterministic native, or an unintended difference between execution environments — `execute_and_verify` will report success as long as status/gas/write-set-hash/event-root happen to match. The write-set hash check alone does not protect against this, since `state_checkpoint_hash` is derived from the full state tree summary (including all prior accumulated writes), not solely the write set of the checkpoint transaction itself; a state root can diverge from causes external to the immediate write set (e.g., wrong hot-state application, wrong prior-state carry-forward, or, per the code's own TODO, `position_state_checkpoint_hash` divergence gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature).

The same callers (`aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) that use this comparator to validate replayed/debugged transactions against on-chain committed data inherit the same blind spot.

### Impact Explanation
Replay-verify is one of the primary integrity backstops used to detect consensus/execution divergence between archived (accumulator-proven) transaction results and independently re-executed results (e.g., during incident response, hard-fork audits, or state-sync/backup verification workflows). By omitting checkpoint-hash comparison, this tool can report a clean/successful replay even though the state root it recomputed differs from the authenticated root committed on-chain — exactly the "wrong accumulator/state root accepted as valid" class of impact called out as in-scope. This weakens detection of ledger-state corruption or divergence bugs across the executor→storage handoff, undermining confidence in replay-verify's guarantee that "the local state matches the correct VM/chain result."

### Likelihood Explanation
The gap is unconditional (not behind a flag) for `state_checkpoint_hash` and `hot_state_checkpoint_hash` — every call to `ensure_match_transaction_info` skips them regardless of feature flags, per the code as written today. It requires no privileged access to trigger: any state-computation bug elsewhere in the codebase (which this tool is specifically meant to catch) would go undetected here. The `position_state_checkpoint_hash` piece is explicitly staged behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS` per the TODO, so that consequence is latent until that feature is enabled, but the state/hot-state checkpoint omission is present unconditionally in the shipped comparator.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`-derived checkpoint hashes (computed from the replaying executor's resulting state view) against `txn_info.state_checkpoint_hash()` and `txn_info.hot_state_checkpoint_hash()` whenever the transaction is a checkpoint boundary (i.e., `has_state_checkpoint_hash()` is true), returning an error on mismatch just as is done for write-set and event-root hashes. Gate the `position_state_checkpoint_hash` check behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as the existing comment suggests, but do not leave the mandatory state/hot-state checks disabled unconditionally.

### Proof of Concept
Conceptual repro (no local execution tooling available to confirm at runtime, but the code path is deterministic and directly readable):
1. Run `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::verify` against a version range containing a state-checkpoint transaction.
2. Have the re-executing VM (or the state view backing it) produce a different final state root at that checkpoint than the archived `TransactionInfo::state_checkpoint_hash()` (e.g., due to any hypothetical determinism or state-carry-forward bug), while keeping status, gas_used, write-set hash, and event root the same for that specific transaction.
3. `execute_and_verify` at [3](#0-2)  calls `ensure_match_transaction_info`, which — per [4](#0-3)  — never inspects `state_checkpoint_hash`, so `Ok(())` is returned and the divergence is never flagged as a mismatch.
