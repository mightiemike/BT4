### Title
Attacker-controlled `UniversalPayload.GasLimit` lets a single inbound spawn an unbounded `OutboundTx` array, blocking outbound finalization for that UniversalTx — ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
`BuildOutboundsFromReceipt` iterates every log in the EVM receipt produced by executing a user's `UniversalPayload` and appends one `OutboundTx` entry per matching gateway event, with no cap on the number of outbounds attached to a single `UniversalTx`. [1](#0-0)  Because `UniversalPayload.GasLimit` is only validated as a syntactically well-formed uint256 (`ValidateBasic`), and I could not find any additional cap applied before it's forwarded to `DerivedEVMCall`, an attacker can submit an inbound/payload with a very large gas limit whose EVM execution emits many `UniversalTxOutboundEventSig` logs in one call, producing a `UniversalTx` with a very large `OutboundTx` slice — this is the direct analog of the reported `PayoutManager.record()` issue where an unbounded list is written/read in a single transaction.

### Finding Description
The vulnerable pattern is structurally identical to the reported bug: a loop appends attacker-influenced-count elements to a slice that is later always read and rewritten in full.

- `UniversalPayload.ValidateBasic` only checks that `GasLimit` parses as a non-negative uint256 string; it does not bound its magnitude. [2](#0-1) 
- That `GasLimit` is passed straight into `CallUEAExecutePayload`, which forwards it as the gas limit for `DerivedEVMCall`. [3](#0-2) 
- After execution, `BuildOutboundsFromReceipt` walks `receipt.Logs` and appends an `OutboundTx` for every matching gateway log with no upper bound on count. [4](#0-3) 
- These outbounds are then attached to the `UniversalTx.OutboundTx` slice via `attachOutboundsToUtx`/`AttachOutboundsToExistingUniversalTx`. [5](#0-4) 
- Every subsequent interaction with that UTX — most importantly `VoteOutbound`, which is called once per outbound per Universal Validator — loads the **entire** `UniversalTx` (including the whole `OutboundTx` array), does a linear scan to find the target outbound, and on finalization calls `UpdateUniversalTx`, which fetches, mutates, and re-serializes/re-writes the **whole** `UniversalTx` object back to the store. [6](#0-5) [7](#0-6) 

If the attacker inflates the number of outbounds in a single `UniversalTx` far enough, every vote on any of that batch's outbounds requires reading/writing a proportionally larger `UniversalTx` blob, and the linear `for _, ob := range utx.OutboundTx` scan in `VoteOutbound`/`UpdateOutbound` becomes O(n) per vote. [8](#0-7)  Pushed far enough, this can make individual `MsgVoteOutbound` transactions unable to complete within a block's gas budget, permanently stalling finalization/observation of every outbound in that batch — the same "cannot be handled in one transaction" failure mode as the `PayoutManager.record()` report, but here reached via ordinary payload execution rather than an admin call.

### Impact Explanation
If confirmed exploitable (see Likelihood), this would let an unprivileged inbound payload permanently starve the outbound-voting flow for the affected `UniversalTx`, since Universal Validators can never successfully cast/tally votes on outbounds inside an over-sized batch. That is a denial-of-service on a core universal-execution invariant (outbound finalization) reachable from a default user payload, which the scope explicitly treats as in-scope when "reachable without privileged control" and "not network-level." It does not, on its own, directly show fund theft, but it can permanently strand outbound processing (funds/messages destined to an external chain) for that UTX, which is a partial "permanent loss/freezing" impact on protocol-controlled flow.

### Likelihood Explanation
Likelihood is **uncertain and only partially confirmed** with the tools available. The exploit path requires:
1. `UniversalPayload.GasLimit` to be unbounded in practice — confirmed only that `ValidateBasic` doesn't cap it; I could not find (nor rule out) an additional cap enforced elsewhere (e.g., inside `DerivedEVMCall`, EVM params, ante handlers, or the block's consensus `MaxGas`) before this reaches EVM execution. My searches for `MaxGasWanted`/`MaxGas`/block gas-limit enforcement around this path did not surface a relevant guard, but the index may not cover the full `x/vm`/`DerivedEVMCall` implementation.
2. A single EVM call must be able to emit enough `UniversalTxOutboundEventSig` logs within one block's gas budget to make the resulting `OutboundTx` array large enough to break subsequent vote transactions — this is fundamentally bounded by the chain's per-block/per-tx gas limit, which likely caps the achievable outbound count to something far short of what would actually break a `MsgVoteOutbound` transaction's own gas budget (since writing back a few hundred/thousand serialized `OutboundTx` structs is unlikely by itself to exceed a normal tx gas limit).

Given this, the severity is likely lower than a guaranteed DoS unless the actual `DerivedEVMCall`/EVM gas limit configuration allows execution well beyond a single block's user-tx gas allowance (e.g., if module-originated calls are exempt from normal block gas accounting). I could not verify this boundary with the available search tools.

### Recommendation
- Enforce an explicit maximum on `UniversalPayload.GasLimit` in `ValidateBasic` (or in `ExecutePayloadV2`/`CallUEAExecutePayload`) tied to a sane fraction of the block gas limit, independent of whatever the underlying EVM module already enforces.
- Cap the number of outbound events processed per receipt in `BuildOutboundsFromReceipt` (e.g., reject or truncate with an error if `len(outbounds)` exceeds a configured `MaxOutboundsPerUTX` param), forcing large batches to be rejected/reverted rather than silently accepted onto a single `UniversalTx`.
- Consider moving `OutboundTx` per-outbound votes/state to a keyed collection (already partially done via `PendingOutbounds`) rather than requiring full-array read/mutate/write of `UniversalTx` on every single-outbound vote, decoupling the cost of any one vote from the total number of outbounds ever attached to that UTX.

### Proof of Concept
Not independently reproduced — this requires confirming (a) the actual max attacker-controllable `GasLimit`/EVM execution budget for `DerivedEVMCall`, and (b) how many `UniversalTxOutboundEventSig` logs can be emitted by the `UniversalGatewayPC` contract per unit of gas, both of which are outside what I could verify from the indexed code alone. A Devin session with full repo/contract access would be needed to determine the real achievable outbound-count ceiling and confirm whether it can push `MsgVoteOutbound` transactions past their own gas limits.

func (k Keeper) UpdateUniversalTx(
	ctx context.Context,
	key string,
	updateFn func(*types.UniversalTx) error,
) error {
	// fetch
	utx, found, err := k.GetUniversalTx(ctx, key)
	if err != nil {
		return err
	}
	if !found {
		return fmt.Errorf("universal tx with key %s not found", key)
	}

	// apply user-defined mutation
	if err := updateFn(&utx); err != nil {
		return err
	}

	// save back
	return k.UniversalTx.Set(ctx, key, utx)
}

func (k Keeper) UpdateOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	k.Logger().Debug("updating outbound state",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"status", outbound.OutboundStatus.String(),
	)
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {
		if utx.OutboundTx == nil {
			return fmt.Errorf("outbound tx list is not initialized for utx %s", utxId)
		}

		updated := false
		for i, ob := range utx.OutboundTx {
			if ob.Id == outbound.Id {
				utx.OutboundTx[i] = &outbound
				updated = true
				break
			}
		}

		if !updated {
			return fmt.Errorf(
				"outbound with id %s not found in utx %s",
				outbound.Id,
				utxId,
			)
		}

		return nil
	})
