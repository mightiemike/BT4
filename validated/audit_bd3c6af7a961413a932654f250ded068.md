The report describes a C-language integer overflow in ImageMagick's PSD/PSB RLE decoder (`ReadPSDChannelRLE` in `coders/psd.c`) causing a heap out-of-bounds read on 32-bit builds — a memory-safety bug class specific to unchecked pointer arithmetic in C. Searching the protobuf-go codebase for analogous length/overflow handling in the wire-format decode paths shows consistent bounds validation:

- `protowire.ConsumeBytes` explicitly checks the decoded length against the remaining buffer size before slicing (`m > uint64(len(b[n:]))`) rather than trusting an attacker-controlled length. [1](#0-0) 
- `protowire.ConsumeVarint`/`ConsumeFixed32`/`ConsumeFixed64` return explicit truncation/overflow error codes rather than reading past bounds. [2](#0-1) 
- The lazy-decode `BufferReader` used in `internal/protolazy` bounds-checks every varint/skip/fixed read against `len(b.Buf)` and returns `io.ErrUnexpectedEOF`/`errOverflow` instead of performing unchecked pointer arithmetic. [3](#0-2) [4](#0-3) 
- `protodelim.UnmarshalOptions.UnmarshalFrom` guards against a length that would overflow `int` before allocating (`size > math.MaxInt`), avoiding the unsafe cast/allocation pattern implicated in the ImageMagick bug. [5](#0-4) 

Because Go slices are bounds-checked by the runtime (any read past a slice's length panics rather than reading adjacent heap memory), the specific "integer overflow → heap out-of-bounds read → information disclosure" bug class from the C ImageMagick report has no direct analog in this codebase's decode paths; overflow conditions here are explicitly checked and produce Go errors, not raw pointer/memory reads. There is no reachable path where this bug class manifests as an OOB memory read in protobuf-go.

func ConsumeBytes(b []byte) (v []byte, n int) {
	m, n := ConsumeVarint(b)
	if n < 0 {
		return nil, n // forward error code
	}
	if m > uint64(len(b[n:])) {
		return nil, errCodeTruncated
	}
	return b[n:][:m], n + int(m)
}
