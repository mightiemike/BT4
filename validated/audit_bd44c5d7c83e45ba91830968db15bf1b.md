## Analog Vulnerability Found

### Title
`SystemInstruction::InitializeNonceAccount` can be front-run to steal control of a nonce account and drain its funds - (File: `programs/system/src/system_processor.rs`, `programs/system/src/system_instruction.rs`)

### Summary
The `BalancerLBPSwapper.init()` bug class — an initializer that sets critical, security-relevant state (the pool/owner) without verifying the caller is the legitimate deployer, and thus can be front-run before the intended initialization transaction lands — has a direct analog in the System Program's nonce-account initialization path. `SystemInstruction::InitializeNonceAccount` sets the nonce `authority` from a caller-supplied `Pubkey` parameter and never requires the target nonce account (or any other authorized party) to sign the instruction, nor checks who created the account.

### Finding Description
`InitializeNonceAccount` is dispatched in [1](#0-0)  and calls `initialize_nonce_account`, which is implemented as: [2](#0-1) 

The function only validates that:
- the account is writable,
- the account state is `Uninitialized`,
- the account has enough lamports to be rent-exempt.

It never checks that the transaction includes a signature from the account itself, from the account's creator, or from any pre-established owner/authority. The `nonce_authority` value written into the account's state is taken verbatim from the instruction's `authorized` parameter, which any transaction signer can supply.

Normal client tooling (e.g. `create_nonce_account` in `system_instruction`, used by `cli/src/nonce.rs`) issues `CreateAccount` and `InitializeNonceAccount` atomically in a single transaction. However, nothing in the protocol enforces this atomicity — a wallet, program, or user can legitimately submit `CreateAccount` for a nonce account in one transaction and `InitializeNonceAccount` in a later, separate transaction, exactly like the two-step "create pool" / "init swapper" pattern described in the report. During the window between these two transactions, the account exists, is owned by the System Program, holds lamports, and is in `Uninitialized` state — indistinguishable to an outside observer from an account ready to be raced.

An ordinary, unprivileged client who observes the pending `CreateAccount` transaction (or otherwise learns the nonce account address before the legitimate `InitializeNonceAccount` transaction confirms) can submit their own `InitializeNonceAccount` instruction naming themselves as `authorized`. Because there is no signer or ownership check on the initializer, if the attacker's transaction lands first, they become the nonce authority of an account they never funded or created.

### Impact Explanation
Once an attacker controls the `authority` field, they gain full control of the victim's nonce account:
- `withdraw_nonce_account` allows the holder of `data.authority` to withdraw lamports from the account, down to the rent-exempt minimum or entirely (closing the account) — see the authority-signature check in [3](#0-2) .
- `advance_nonce_account` and `AuthorizeNonceAccount` also gate on `signers.contains(&data.authority)` ( [4](#0-3) ), letting the attacker fully hijack durable-nonce usage for that account.

This is a concrete theft-of-funds primitive: the victim funds a nonce account (paying the rent-exempt balance, often used to store additional lamports for durable-nonce transactions), and the attacker can extract those lamports by winning the initialization race.

### Likelihood Explanation
Exploitation requires only that `CreateAccount` and `InitializeNonceAccount` be submitted as separate transactions (a supported, non-exotic usage pattern; the SDK convenience function bundles them, but the protocol itself does not enforce bundling) and that the attacker observe/front-run the pending initialization transaction — a standard MEV/mempool-racing capability available to any unprivileged network participant. No special privileges, validator cooperation, or protocol bypass is needed.

### Recommendation
`initialize_nonce_account` should require that the nonce account itself (or a previously-recorded creator/expected-authority) is a transaction signer, analogous to the signer checks already used elsewhere in `system_instruction.rs` (e.g., `allocate`/`assign`/`transfer` all require `address.is_signer(signers)` or `is_instruction_account_signer`). At minimum, require `signers.contains(account.get_key())` before transitioning from `Uninitialized` to `Initialized`, closing the front-running window regardless of how `CreateAccount` and `InitializeNonceAccount` are batched by client tooling.

### Proof of Concept
1. Victim submits Tx A: `SystemProgram.CreateAccount` funding new pubkey `N` with rent-exempt lamports, owned by the System Program.
2. Victim intends to submit Tx B: `SystemInstruction::InitializeNonceAccount(victim_authority)` targeting `N`.
3. Attacker observes Tx A (or predicts `N`) before Tx B confirms, and submits Tx C: `SystemInstruction::InitializeNonceAccount(attacker_authority)` targeting `N`, paying only the standard transaction fee — no signature from `N` or the victim is required per [5](#0-4) .
4. If Tx C lands before Tx B, `N`'s state becomes `Initialized { authority: attacker_authority, ... }`; Tx B then fails with `AccountAlreadyInitialized`-equivalent (`InstructionError::InvalidAccountData`) per lines 202-209.
5. Attacker submits `SystemInstruction::WithdrawNonceAccount` signed by `attacker_authority`, draining `N`'s lamports per [3](#0-2) .
