### Title
Fee-transfer (and OS `charge_fee`) execution does not verify the ERC20 `success` return value, only that the call did not revert - ([File: crates/blockifier/src/transaction/account_transaction.rs], [File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo])

### Summary
Both the Rust blockifier and the Cairo Starknet OS charge transaction fees by invoking the fee token's `transfer` entry point and only check that the call did **not revert**; neither path inspects the boolean `success` value that an ERC20-style `transfer`/`transferFrom` is expected to return. This mirrors the reported pattern ("use safeTransferFrom always" / always validate ERC20 return values) applied to the sequencer's fee-charging flow, which every unprivileged transaction sender reaches on every transaction.

### Finding Description
In the blockifier, `AccountTransaction::execute_fee_transfer` builds a `CallEntryPoint` for `TRANSFER_ENTRY_POINT_NAME` against the configured fee token and only propagates an error if `.execute(...)` itself errors/reverts; the `retdata` (the ERC20 `success` felt) is never asserted to be `TRUE`: [1](#0-0) 

Symmetrically, the Starknet OS's `charge_fee` builds the same `transfer` call and executes it via `non_reverting_select_execute_entry_point_func`, which only asserts `is_reverted = 0` — it never reads/validates the `retdata` (the `success` boolean) of the transfer call: [2](#0-1) [3](#0-2) 

By contrast, `run_validate` in the same file *does* check the retdata against the expected `VALIDATED` magic value, showing that the codebase pattern elsewhere is to validate return data, but `charge_fee` does not apply the same discipline to the `success` return of the `transfer` call: [4](#0-3) 

If the fee token contract behind `fee_token_address` ever returns `success = FALSE` on a failed transfer instead of reverting (a legitimate ERC20 implementation choice, and explicitly the return-value convention used by the token interface itself, as seen in the ERC20 fixture's `transfer`/`transferFrom` returning `(success: felt)`), both the blockifier and the OS would treat the fee as successfully charged even though no value moved: [5](#0-4) 

### Impact Explanation
If the deployed fee token ever returns `false` rather than reverting on a failed transfer (e.g., insufficient balance or a future/alternate fee-token implementation with non-reverting semantics), the sequencer would record `fee_transfer_call_info` as a successful, non-reverted call and commit a state diff crediting the sequencer's balance and debiting the account's balance bookkeeping accordingly, while the actual token balances were never moved by the contract. This is a fee/accounting-integrity issue: the sequencer's view of "fee collected" diverges from the real token movement performed by the (silently failing) contract, which is exactly the failure mode this bug class targets (accounting corruption from unchecked transfer return values) surfaces through `execute_fee_transfer`/`charge_fee`, and any code path (blockifier or Starknet OS re-execution) that assumes "not reverted implies transferred" would silently diverge from the true on-chain token state.

### Likelihood Explanation
Likelihood is constrained because the fee token contracts used in production (`ETH`/`STRK`) are fixed, well-known, audited ERC20 implementations that revert on insufficient balance rather than returning `false`; the fee token address itself is not attacker-controlled (`block_context.os_global_context.starknet_os_config.fee_token_address`) and cannot be substituted by a transaction sender per-transaction. Therefore, exploitation would require the actual protocol-configured fee token to deviate from "revert on failure" semantics, which is not demonstrated to be the case in the current production fee token contracts referenced in this codebase.

### Recommendation
Add an explicit check of the `success`/retdata value returned by the fee-token `transfer` call in both `AccountTransaction::execute_fee_transfer` (Rust, via inspecting `call_info.execution.retdata`) and `charge_fee` in the Starknet OS Cairo code (asserting `retdata[0] == TRUE`, similar to how `run_validate` checks `retdata[0] == VALIDATED`), so that a non-reverting but unsuccessful transfer cannot be silently treated as a completed fee payment.

### Proof of Concept
Not applicable as a concrete exploit against the current production fee token, since the current fee-token implementation reverts on failed transfers rather than returning `false` — the finding is a defense-in-depth/robustness gap rather than a demonstrated, exploitable divergence under the currently deployed fee token contracts.

    fn execute_fee_transfer(
        state: &mut dyn State,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
    ) -> TransactionExecutionResult<CallInfo> {
        // The least significant 128 bits of the amount transferred.
        let lsb_amount = Felt::from(actual_fee.0);
        // The most significant 128 bits of the amount transferred.
        let msb_amount = Felt::ZERO;

        let TransactionContext { block_context, tx_info } = tx_context.as_ref();
        let storage_address = tx_context.fee_token_address();
        // The fee contains the cost of running this transfer, and the token contract is
        // well known to the sequencer, so there is no need to limit its run.
        let mut remaining_gas_for_fee_transfer =
            block_context.versioned_constants.os_constants.gas_costs.base.default_initial_gas_cost;
        let fee_transfer_call = CallEntryPoint {
            class_hash: None,
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector_from_name(constants::TRANSFER_ENTRY_POINT_NAME),
            calldata: calldata![
                *block_context.block_info.sequencer_address.0.key(), // Recipient.
                lsb_amount,
                msb_amount
            ],
            storage_address,
            caller_address: tx_info.sender_address(),
            call_type: CallType::Call,

            initial_gas: remaining_gas_for_fee_transfer,
        };
        let mut context = EntryPointExecutionContext::new_invoke(
            tx_context,
            true,
            SierraGasRevertTracker::new(GasAmount(remaining_gas_for_fee_transfer)),
        );

        Ok(fee_transfer_call
            .execute(state, &mut context, &mut remaining_gas_for_fee_transfer)
            .map_err(|error| Box::new(TransactionFeeError::ExecuteFeeTransferError(error)))?)
    }

// Charges a fee from the user.
// If max_fee is not 0, validates that the selector matches the entry point of an account contract
// and executes an ERC20 transfer on the behalf of that account contract.
//
// Arguments:
// block_context - a global context that is fixed throughout the block.
// tx_execution_context - The execution context of the transaction that pays the fee.
func charge_fee{
    range_check_ptr,
    builtin_ptrs: BuiltinPointers*,
    contract_state_changes: DictAccess*,
    contract_class_changes: DictAccess*,
    outputs: OsCarriedOutputs*,

    alloc_locals;

    local tx_info: TxInfo* = tx_execution_context.execution_info.tx_info;
    let max_fee = compute_max_possible_fee(tx_info=tx_info);

    if (max_fee == 0) {
        return ();
    }

    local low_actual_fee;
    %{ LoadActualFee %}
    local calldata: TransferCallData = TransferCallData(
        recipient=block_context.block_info_for_execute.sequencer_address,

    // Verify that the charged amount is not larger than the transaction's max_fee field.
    assert_nn_le(calldata.amount.low, max_fee);

    let (__fp__, _) = get_fp_and_pc();
    // Use block_info directly from block_context, so that charge_fee will always run in
    // execute-mode rather than validate-mode.
    local execution_context: ExecutionContext = ExecutionContext(
        entry_point_type=ENTRY_POINT_TYPE_EXTERNAL,

        deprecated_tx_info=tx_execution_context.deprecated_tx_info,

    let remaining_gas = DEFAULT_INITIAL_GAS_COST;
    non_reverting_select_execute_entry_point_func{remaining_gas=remaining_gas}(
        block_context=block_context, execution_context=&execution_context
    );
    return ();
}

// Same as `select_execute_entry_point_func`, but does not support reverts and does
// not have an implicit 'revert_log' argument.
func non_reverting_select_execute_entry_point_func{
    range_check_ptr,

    builtin_ptrs: BuiltinPointers*,

@external
func transfer{syscall_ptr: felt*, pedersen_ptr: HashBuiltin*, range_check_ptr}(
    recipient: felt, amount: Uint256

    let (sender) = get_caller_address();
    ERC20_transfer(sender, recipient, amount);

    return (TRUE,);
}

@external
func transferFrom{syscall_ptr: felt*, pedersen_ptr: HashBuiltin*, range_check_ptr}(
    sender: felt, recipient: felt, amount: Uint256
) -> (success: felt) {
    alloc_locals;
    let (local caller) = get_caller_address();
    let (local caller_allowance: Uint256) = ERC20_allowances.read(owner=sender, spender=caller);

    // Validates amount <= caller_allowance and returns TRUE if true.
    let (enough_allowance) = uint256_le(amount, caller_allowance);
    assert_not_zero(enough_allowance);

    ERC20_transfer(sender, recipient, amount);

    // Subtract allowance.
    let (new_allowance: Uint256) = uint256_sub(caller_allowance, amount);
    ERC20_allowances.write(sender, caller, new_allowance);

    return (TRUE,);
}
