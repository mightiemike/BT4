### Title
Anyone can call the unchecked `ExtendProgram` instruction to grow any upgradeable program's `ProgramData` account without the upgrade authority's consent, permanently exhausting its growth headroom (SIMD-0431 minimum-extend griefing DoS) - (File: programs/bpf_loader/src/lib.rs)

### Summary
The legacy `UpgradeableLoaderInstruction::ExtendProgram` instruction calls `common_extend_program(invoke_context, additional_bytes, false)` with `check_authority = false`, meaning any unprivileged party — supplying only their own payer signature to cover the rent difference — can extend the size of *any* other program's `ProgramData` account, exactly as the Ajna `memorializePositions` bug allowed anyone to attach unwanted entries to someone else's position NFT without consent.

### Finding Description
`common_extend_program` in [1](#0-0)  is invoked from the `ExtendProgram` match arm with `check_authority = false`, while the authority check block itself is gated behind that same flag: [2](#0-1) [3](#0-2) 

Because `check_authority` is `false` for the plain `ExtendProgram` instruction, the code never verifies that the caller controls `AUTHORITY_ACCOUNT_INDEX`, nor even requires an authority account to be present at all (`optional_payer_account_index` is computed as index 3, skipping the authority slot entirely) — it only needs a payer to cover any lamport shortfall via a `system_instruction::transfer` CPI: [4](#0-3) 

The only real limits are:
- A hard cap of `MAX_PERMITTED_DATA_LENGTH` bytes total: [5](#0-4) 
- A once-per-slot restriction and a SIMD-0431 minimum extension size of `MINIMUM_EXTEND_PROGRAM_BYTES` (10 KiB) per call (unless finishing to the cap): [6](#0-5) 

Neither of these limits requires being the program's upgrade authority. Any ordinary client can submit a transaction invoking `ExtendProgram` against a target program they do not own, paying the rent difference themselves, and repeatedly (once per slot) grow the victim's `ProgramData` account toward the 10 MiB ceiling.

### Impact Explanation
This is directly analogous to the referenced Ajna finding: an unprivileged actor can attach unwanted state to a resource they don't own/control, with no authorization check, degrading that resource for its legitimate owner:
- Once an attacker drives a target `ProgramData` account's length to (or near) `MAX_PERMITTED_DATA_LENGTH`, the legitimate upgrade authority permanently loses the ability to further extend the account (`InvalidRealloc`/`InvalidArgument` on subsequent extends), which can block genuine future program upgrades that need more program data space — a persistent, irreversible denial-of-service against the program's evolvability, imposed by a third party without the authority's consent.
- Each successful call also forces `deploy_program!` verification over the enlarged program data, and permanently inflates on-chain account storage tied to a program the attacker does not control, at cluster-wide cost, though the attacker (not the victim) pays the direct rent lamports.
- The unbounded ability for arbitrary unprivileged accounts to mutate account size/state that should be authority-gated is itself a privilege/authorization defect in a builtin program instruction, matching the report's "attach without consent → resource exhaustion/DoS on legitimate operation" bug class.

### Likelihood Explanation
High likelihood: `ExtendProgram` is a standard, always-available instruction of the widely-used BPF Loader Upgradeable (loader v3) builtin program. No special privileges, feature flags, or governance are required by the attacker — only knowledge of the target program's `ProgramData` address (public) and enough SOL to cover the minimum 10 KiB rent increments once per slot. The instruction has been in production and the `check_authority` bypass is exercised in-repo by tests such as `test_extend_program` and `test_extend_program_without_payer`, confirming the unchecked path is live and reachable: [7](#0-6) [8](#0-7) 

### Recommendation
Require that the (unchecked) `ExtendProgram` instruction either be deprecated/disabled in favor of the authority-checked `ExtendProgramChecked` variant, or have `common_extend_program` invoked with `check_authority = true` unconditionally, so that only the program's actual upgrade authority (a required signer) can grow its `ProgramData` account. If backward compatibility must be preserved, gate the unchecked path behind a feature that restricts callers to the recorded `upgrade_authority_address`, mirroring the same signer/authority check already implemented for the checked variant at [3](#0-2) .

### Proof of Concept
1. Deploy an upgradeable program `P` with authority `A`; its `ProgramData` account starts below `MAX_PERMITTED_DATA_LENGTH`.
2. As an unrelated attacker account `B` (not `A`), submit a transaction each slot invoking `extend_program(&P, Some(&B_payer), MINIMUM_EXTEND_PROGRAM_BYTES)` per the client helper used in tests: [9](#0-8) 
3. Each transaction succeeds without any signature or account from `A`, since `check_authority` is `false` for this instruction path ( [1](#0-0) ), and `B` pays the incremental rent via the internal system transfer ( [10](#0-9) ).
4. Repeating this once per slot (respecting the "already extended this block" guard at [11](#0-10) ) drives the `ProgramData` account length to `MAX_PERMITTED_DATA_LENGTH`, after which `A`'s own future `ExtendProgram`/`ExtendProgramChecked` calls fail with `InstructionError::InvalidRealloc`, permanently denying `A` the ability to grow their program's data account for a legitimate upgrade — without `A`'s consent or involvement.

#[tokio::test]
async fn test_extend_program() {
    let mut context = setup_test_context(LoaderV3Features {
        minimum_extend_program_size: false,
    })
    .await;
    let program_file = find_file("noop.so").expect("Failed to find the file");
    let data = read_file(program_file);
    let upgrade_authority = Keypair::new();

    let program_address = Pubkey::new_unique();
    let (programdata_address, _) = Pubkey::find_program_address(&[program_address.as_ref()], &id());
    add_upgradeable_loader_account(
        &mut context,
        &program_address,
        &UpgradeableLoaderState::Program {
            programdata_address,
        },
        UpgradeableLoaderState::size_of_program(),
        |_| {},
    )
    .await;
    let programdata_data_offset = UpgradeableLoaderState::size_of_programdata_metadata();
    let program_data_len = data.len() + programdata_data_offset;
    add_upgradeable_loader_account(
        &mut context,
        &programdata_address,
        &UpgradeableLoaderState::ProgramData {
            slot: 0,
            upgrade_authority_address: Some(upgrade_authority.pubkey()),
        },
        program_data_len,
        |account| account.data_as_mut_slice()[programdata_data_offset..].copy_from_slice(&data),
    )
    .await;

    let client = &mut context.banks_client;
    let payer = &context.payer;
    let recent_blockhash = context.last_blockhash;
    const ADDITIONAL_BYTES: u32 = 42;
    let transaction = Transaction::new_signed_with_payer(
        &[extend_program(
            &program_address,
            Some(&payer.pubkey()),
            ADDITIONAL_BYTES,
        )],
        Some(&payer.pubkey()),
        &[payer],
        recent_blockhash,
    );

    assert_matches!(client.process_transaction(transaction).await, Ok(()));
    let updated_program_data_account = client
        .get_account(programdata_address)
        .await
        .unwrap()
        .unwrap();
    assert_eq!(
        updated_program_data_account.data().len(),
        program_data_len + ADDITIONAL_BYTES as usize
    );
}
