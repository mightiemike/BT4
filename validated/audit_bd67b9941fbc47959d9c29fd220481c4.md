The `PublicNetLimit` mechanism in `BandwidthProcessor.useFreeNet` is a shared, network-wide free-bandwidth quota (a leaky-bucket-style limiter, replenished only via the `increase()`/decay logic over a fixed `windowSize`) that any unprivileged account can exhaust just by sending free (non-fee-paying) transactions, denying the shared free-tier bandwidth to every other account on the network — structurally the same "shared limiter can be griefed by a single well-resourced actor since consumption is not fairly rate-limited per account" issue as the AlchemistV2 mint-limit report.

### Title
Global `PublicNetLimit` free-bandwidth pool can be exhausted by a single account, denying free transactions to all other users - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
`BandwidthProcessor.useFreeNet` checks and decrements a single, chain-wide counter (`PublicNetUsage`/`PublicNetLimit`) that is shared by every account attempting to use free bandwidth for a transaction. [1](#0-0)  There is no per-account share or fair-queuing of this global pool: consumption is first-come-first-served against one linear-decay counter that recovers only through the passage of time (`windowSize`), exactly like the `LinearGrowthLimiter` in the referenced Alchemix report.

### Finding Description
`useFreeNet` reads `publicNetLimit`/`publicNetUsage`/`publicNetTime` from `DynamicPropertiesStore`, computes the decayed usage via the shared `increase()` helper, and — if the requested transaction's byte cost fits under the remaining public quota — updates and persists the single global counter: [2](#0-1)  Any account without sufficient frozen bandwidth (`useAccountNet` fails) and with unused per-account `freeNetLimit` falls into this shared pool. Because `publicNetUsage` decays continuously with time and windowSize (the same "leaky bucket" pattern as `Limiters.sol`'s `LinearGrowthLimiter`), an attacker can continuously broadcast minimal-cost, zero-value transactions (e.g., simple transfers of 0 TRX to themselves) from any number of addresses that individually stay within their own per-account `freeNetLimit`, but collectively keep `publicNetUsage` pinned near `publicNetLimit`. The default `PublicNetLimit` is a fixed constant (`14_400_000_000L`) [3](#0-2)  that is not scaled to network size, so a moderately resourced attacker (needs no frozen TRX, only cheap free transactions) can keep this shared quota saturated indefinitely at negligible cost (transaction fees would apply only when free bandwidth is unavailable — while it's exhausted, other honest accounts are denied the free path and forced to pay bandwidth fees or fail).

### Impact Explanation
This is a DoS against the free-tier bandwidth mechanism available to every account on the network. Honest low-balance accounts relying on `freeNetLimit`/`publicNetLimit` to submit transactions without frozen TRX or fees would repeatedly fail `useFreeNet` and fall through to `useTransactionFee` (requiring TRX balance) or ultimately throw `AccountResourceInsufficientException`, blocking transaction submission for accounts without spare balance. [4](#0-3)  No funds are directly stolen, matching the "no loss of user funds" characterization in the original report, but it constitutes a protocol-level DoS reachable from any broadcast transaction.

### Likelihood Explanation
The attack requires only the ability to broadcast many low-cost transactions (e.g., zero-amount `TransferContract`s) that individually stay within each sender account's own `freeNetLimit`, and does not require large frozen TRX balances, governance/privileged roles, or precise timing beyond keeping the shared counter saturated. This is straightforward for a moderately resourced attacker to sustain continuously, similar to the flash-loan-driven griefing pattern described in the source report, though tron's per-block-timestamp granularity (`windowSize`/slot-based) makes exact sizing dependent on network throughput rather than instant flash-loan reset.

### Recommendation
Consider per-account or per-IP rate limiting on top of the shared `PublicNetLimit`, or scaling `PublicNetLimit` recovery based on network activity/adaptive limits (similar to `EnergyProcessor.updateAdaptiveTotalEnergyLimit`) so a single actor's sustained usage cannot pin the shared pool. Alternatively, introduce a minimum fee/weight cost per free-tier transaction that scales with how saturated the public pool currently is, discouraging sustained exhaustion.

### Proof of Concept
1. Identify that `PublicNetLimit` defaults to `14_400_000_000L` bytes-equivalent capacity, decaying over `windowSize` slots [5](#0-4) .
2. From many low-balance addresses (no frozen TRX required), continuously broadcast minimal `TransferContract` transactions costing only a few hundred bytes each, staying under each account's individual `freeNetLimit` (default 5000) [6](#0-5) .
3. Each accepted transaction increments the shared `publicNetUsage` via `useFreeNet` [2](#0-1) ; sustaining a submission rate at or above the decay rate keeps `publicNetUsage` near `publicNetLimit`.
4. Other honest accounts calling `useFreeNet` for their own free transactions now fail the `bytes > (publicNetLimit - newPublicNetUsage)` check and fall back to fee-based or fail entirely.

  private boolean useFreeNet(AccountCapsule accountCapsule, long bytes, long now) {

    long freeNetLimit = chainBaseManager.getDynamicPropertiesStore().getFreeNetLimit();
    long freeNetUsage = accountCapsule.getFreeNetUsage();
    long latestConsumeFreeTime = accountCapsule.getLatestConsumeFreeTime();
    long newFreeNetUsage = increase(freeNetUsage, 0, latestConsumeFreeTime, now);

    if (bytes > (freeNetLimit - newFreeNetUsage)) {
      logger.debug("Free net usage is running out."
              + " Bytes: {}, freeNetLimit: {}, newFreeNetUsage: {}.",
          bytes, freeNetLimit, newFreeNetUsage);
      return false;
    }

    long publicNetLimit = chainBaseManager.getDynamicPropertiesStore().getPublicNetLimit();
    long publicNetUsage = chainBaseManager.getDynamicPropertiesStore().getPublicNetUsage();
    long publicNetTime = chainBaseManager.getDynamicPropertiesStore().getPublicNetTime();

    long newPublicNetUsage = increase(publicNetUsage, 0, publicNetTime, now);

    if (bytes > (publicNetLimit - newPublicNetUsage)) {
      logger.debug("Free public net usage is running out."
              + " Bytes: {}, publicNetLimit: {}, newPublicNetUsage: {}.",
          bytes, publicNetLimit, newPublicNetUsage);
      return false;
    }

    latestConsumeFreeTime = now;
    long latestOperationTime = chainBaseManager.getHeadBlockTimeStamp();
    publicNetTime = now;
    newFreeNetUsage = increase(newFreeNetUsage, bytes, latestConsumeFreeTime, now);
    newPublicNetUsage = increase(newPublicNetUsage, bytes, publicNetTime, now);
    accountCapsule.setFreeNetUsage(newFreeNetUsage);
    accountCapsule.setLatestConsumeFreeTime(latestConsumeFreeTime);
    accountCapsule.setLatestOperationTime(latestOperationTime);

    chainBaseManager.getDynamicPropertiesStore().savePublicNetUsage(newPublicNetUsage);
    chainBaseManager.getDynamicPropertiesStore().savePublicNetTime(publicNetTime);
    chainBaseManager.getAccountStore().put(accountCapsule.createDbKey(), accountCapsule);
    return true;
