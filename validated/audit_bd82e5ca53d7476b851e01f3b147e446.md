### Title
Unbounded Gzip Decompression Bomb in RPC-Submitted Declare-v1 Contract Class Leads to Node DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
`decompress_program()` in `crates/apollo_rpc/src/v0_8/api/mod.rs` decompresses the base64+gzip `compressed_program` field of a Cairo-0 (`BroadcastedDeclareV1Transaction`) contract class with **no size limit, no member count limit, and no time-out**, unlike the equivalent decompression utility used elsewhere in the same codebase (`starknet_api::compression_utils::decode_and_decompress_with_size_limit`). An unprivileged caller can submit a tiny, highly-compressible gzip payload (analogous to the PraisonAI `_safe_extractall()` bug, which also lacked a decompressed-size check before extraction) that inflates to gigabytes in memory, exhausting the node's RAM/disk and crashing the process handling declare-class submissions.

### Finding Description
`decompress_program` is defined at [1](#0-0) :
```rust
pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}
```
The `// TODO(dan): add time and size limits.` comment confirms the maintainers are aware no bound exists. `decoder.read_to_end(&mut decompressed, ...)` will happily allocate as much memory as the compression ratio demands (classic zip/gzip-bomb pattern — the exact bug class in the external report, which flagged `tar.extractall()` performing no size check on `TarInfo.size` before extraction).

This function is reached directly from the `TryFrom<BroadcastedDeclareTransaction> for ExecutableTransactionInput` conversion path used by JSON-RPC execution/simulation endpoints (e.g. `estimateFee`, `simulateTransactions`, `traceTransaction`-adjacent flows) for Declare V1 transactions: [2](#0-1) 

`user_deprecated_contract_class_to_sn_api` calls `decompress_program(&value.compressed_program)` unconditionally on attacker-controlled input, with no upstream size validation of the decompressed program before it is passed into `serde_json::from_reader`.

For contrast, the codebase itself demonstrates the correct, bounded pattern elsewhere: `starknet_api::compression_utils::decompress_with_size_limit` caps decompressed output using `.take(max_size + 1)` before reading, and is used for the Sierra program pathway in `crates/apollo_http_server/src/deprecated_gateway_transaction.rs::convert_to_sierra_contract_class`: [3](#0-2) [4](#0-3) 

The deprecated Cairo-0 `program` decompression path in `apollo_rpc` was not updated to use this bounded helper, leaving an inconsistent, unguarded decompression sink.

### Impact Explanation
An attacker submitting an unauthenticated `estimateFee`/`simulateTransactions` request containing a `BroadcastedDeclareV1Transaction` with a small (few-KB) but maximally-compressible `compressed_program` (e.g., gigabytes of zeros) forces the node to allocate unbounded memory during `GzDecoder::read_to_end`. This can exhaust the node's memory/swap and crash or hang the RPC/execution service, denying legitimate fee-estimation/simulation requests — a prerequisite most wallets/SDKs perform before submitting real transactions. Repeated requests amplify the effect into a persistent denial of service against the node offering these RPC methods.

### Likelihood Explanation
High: the endpoint requires no authentication or fees (fee estimation/simulation calls, and V1 declare transactions are still accepted structurally by the RPC layer), the malicious payload is trivial to construct (a gzip bomb), and the vulnerable code path is directly reachable from a single externally-submitted broadcasted transaction object.

### Recommendation
Replace the manual `GzDecoder`/`read_to_end` loop in `decompress_program` with the existing bounded helper (`starknet_api::compression_utils::decode_and_decompress_with_size_limit` or an equivalent using `.take(max_size)`), enforcing the same maximum decompressed size (and, ideally, a CPU/time bound) already applied to Sierra program decompression elsewhere in the codebase. Reject the request if the decompressed size exceeds the limit instead of buffering to completion.

### Proof of Concept
1. Craft a `Program` JSON payload consisting of a large, highly repetitive/compressible byte sequence (e.g., a huge array of identical constant values) sufficient to produce, after JSON+gzip, only a few hundred KB compressed but multiple GB decompressed.
2. Base64-encode the gzip-compressed bytes and place them into `BroadcastedDeclareV1Transaction.contract_class.compressed_program`.
3. Submit this transaction object via any RPC method that triggers `TryFrom<BroadcastedTransaction> for ExecutableTransactionInput` (e.g. `starknet_estimateFee`, `starknet_simulateTransactions`) — no signature/fee validity check occurs before `decompress_program` is invoked.
4. Observe `decompress_program`'s `decoder.read_to_end(&mut decompressed, ...)` at [5](#0-4)  allocate unbounded memory, driving the serving node toward OOM/crash.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
