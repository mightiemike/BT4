### Title
Contract-controlled `refund_to` on a delegated/batched receipt can cause a relayer's or predecessor's gas/deposit refund to be permanently burnt instead of returned - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
NEAR's system-generated refund receipts (unused-gas refunds, deposit refunds on failed actions, delete-account beneficiary refunds) are created with `predecessor_id = "system"` and are treated as "free" (no gas charged, and critically, no further refund is ever generated if *they* fail). A receipt can carry a caller-settable `refund_to` field (`ActionReceiptV2::refund_to`, exposed to contracts via `refund_to_account_id`/`promise_batch_action_*` on `VMLogic`, see `runtime/near-vm-runner/src/logic/context.rs` and `core/primitives/src/receipt.rs:416-430`) that redirects where the refund for that receipt is sent, instead of defaulting to the receipt's predecessor.

### Finding Description
`Receipt::balance_refund_receiver` (`core/primitives/src/receipt.rs:428-430`) returns `refund_to` if set, otherwise falls back to `predecessor_id()`. This field is meant for meta-transaction relayers (NEP-366) so that unused gas/deposit is returned to whoever actually paid for the receipt rather than the inner-transaction signer. `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1166`) builds `Receipt::new_balance_refund` / `Receipt::new_gas_refund` addressed to that `balance_refund_receiver`.

When such a refund receipt is itself processed, `check_account_existence`/`implicit_creation_allowed` (`runtime/runtime/src/actions.rs:814-846`, `928-947`) explicitly forbid a refund from creating *any* account kind (`is_refund => return false`), even universal/implicit accounts that a normal transfer could create. If the target account does not exist at the time the refund is delivered, the refund receipt fails with `AccountDoesNotExist`, and, per the documented behavior (`runtime/runtime/src/lib.rs:929` and `protocol-model/spec/runtime-execution.md:69`), "a failed refund burns its deposit into `other_burnt_amount`" — the deposit is destroyed, not re-refunded (refunds of refunds are intentionally not generated, to avoid infinite loops). This is verified directly by the test `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6870-6927`), which shows a refund to a not-yet-existing account fails with `AccountDoesNotExist` and the account is never created — the funds are simply gone.

Because `refund_to` is attacker/contract-controllable at receipt-creation time (it is set on the *outer* receipt sent by a relayer/contract, independent of who ends up paying), a contract or meta-transaction relayer flow can point the refund destination at an account that is guaranteed to not exist by the time the refund is processed (e.g., an implicit/universal account id that was never funded, or a named account that gets deleted via a batched `DeleteAccount` in the same or a preceding receipt). The unused prepaid gas/deposit that should have been returned to the paying party is instead irrecoverably burnt.

This mirrors the reported ERC20 bug class ("transfer to a certain target may revert/fail depending on account state, causing funds that should be returned to the payer to instead be lost") — except in nearcore the "revert" manifests as `AccountDoesNotExist` and the outcome is not a revert-and-retry but a silent, permanent burn of the refund amount.

### Impact Explanation
Funds that were prepaid by an honest party (typically a meta-transaction relayer covering gas/deposit for a user's delegated action, or any predecessor of a receipt with unused gas) can be permanently destroyed rather than returned, if the receiver of the refund receipt does not exist at settlement time. This is an unauthorized, protocol-enforced value destruction (burnt supply) triggered purely by receipt construction choices reachable from a single submitted transaction/delegate action — a "permanently frozen/lost funds" condition for the paying party, matching the required impact class (frozen funds / fee bypass via destruction rather than misdirection).

### Likelihood Explanation
Reaching this path requires only: (1) crafting or relaying a delegate/meta-transaction (or any promise batch) whose refund target (`refund_to`) is an account that will not exist when the refund settles, and (2) the receipt's execution consuming less than the full prepaid gas/deposit (the common case for any successful or gracefully-failing call). Both conditions are fully controllable by an unprivileged transaction signer or contract without needing validator/operator privilege, making this readily reachable, though it primarily harms the party who set (or was tricked into accepting) the bad `refund_to`, which affects the likelihood/severity split between self-inflicted loss and third-party (relayer) loss scenarios.

### Recommendation
When a balance/gas-refund receipt's target account does not exist, do not simply burn the deposit — fall back to refunding to the receipt's original `predecessor_id` (or the ultimate transaction signer) instead of the (possibly bogus) `refund_to`, or validate that `refund_to` resolves to an account that is guaranteed to exist for the lifetime of the receipt before honoring it. At minimum, document/enforce that `refund_to` cannot target accounts that can be deleted or that were never created, and consider re-attempting delivery to the receipt's `predecessor_id` as a second-chance destination before burning.

### Proof of Concept
1. A relayer submits a `Delegate`/`DelegateV2` action (or any promise-batch receipt) with `refund_to` set to an implicit/universal account id that has never been funded (or a named account slated for deletion via a batched `DeleteAccount`).
2. The inner action executes and consumes less than its prepaid gas/deposit, so `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1166`) creates a `Receipt::new_balance_refund`/`new_gas_refund` addressed to `refund_to` via `Receipt::balance_refund_receiver` (`core/primitives/src/receipt.rs:428`).
3. When that refund receipt is processed, `check_account_existence`/`implicit_creation_allowed` reject account creation because `is_refund == true` (`runtime/runtime/src/actions.rs:929-933`), producing `ActionErrorKind::AccountDoesNotExist` — exactly the behavior asserted by `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6883-6926`).
4. Per the documented `other_burnt_amount` handling (`runtime/runtime/src/lib.rs:929`, `protocol-model/spec/runtime-execution.md:69`), the refund's deposit is burnt rather than returned to the relayer, permanently destroying the value that was supposed to come back to the party who prepaid the gas/deposit. /// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

    fn refund_may_not_create_universal_account() {
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {
            panic!("the refund receipt must produce exactly one outcome, got {:?}", result.outcomes)
        };
        assert_matches!(
            &outcome.outcome.status,
            ExecutionStatus::Failure(TxExecutionError::ActionError(err))
                if matches!(err.kind, ActionErrorKind::AccountDoesNotExist { .. }),
            "a refund to a missing `0u` id must fail with AccountDoesNotExist",
        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
