Found a candidate that matches the allowed "cached value not invalidated when its source moves" analog class: the `index-cache` in `market.clar` / `v0-4-market.clar`.

### Title
Index cache written from the price-update path is silently overwritten by a stale post-debt-write refresh during `liquidate`/`liquidate-multi`, letting a liquidator use a stale liquidity index to under-value seized collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches vault `{index, lindex}` per `{timestamp: stacks-block-time, aid}` to avoid repeated cross-contract vault calls within the same block [1](#0-0) . The cache is keyed only by block timestamp, so within a single transaction/block, once a value is cached it is treated as authoritative for every subsequent read, including reads used for collateral pricing and health checks. `socialize-debt-asset`, however, mutates the vault's liquidity index (via `vault-socialize-debt`) and then re-writes the cache entry with the *new* post-write-down index [2](#0-1) , while other call sites that read via `get-cached-indexes`/`accrue-and-cache` assume the cached snapshot reflects the state at the time collateral/debt values were evaluated earlier in the same call [3](#0-2) .

### Finding Description
The cache-invalidation model is: "new block → new timestamp → cache miss → fresh accrual," which the protocol's own documentation states eliminates staleness risk [4](#0-3) . This assumption only holds if, within one block, the cached `{index, lindex}` is never mutated after being read. But `socialize-debt-asset` explicitly overwrites the same-block cache entry with a freshly-accrued index after the vault's internal state has already been changed by `vault-socialize-debt` [5](#0-4) . Because Clarity evaluates `let`-bound values once at binding time, any earlier `let` binding in the same public function that already captured `(get-cached-indexes asset-id)` (e.g. `borrow-index` used to compute `scaled-debt-added`/`convert-to-scaled-debt`, `debt-post-increased`, and the printed audit index in `borrow`) continues to hold the pre-socialization value even though the map entry underneath it has since moved [6](#0-5) . In `liquidate-multi`/`call-liquidate`, each position is processed sequentially via `fold`, so a socialize-debt event triggered for one borrower's position in the batch changes the cached index that a subsequent position's collateral/debt valuation (via `convert-to-scaled-debt`, which itself calls `get-cached-indexes`) will pick up mid-batch, while pricing computed earlier for prior legs remains bound to the older cached value [7](#0-6) .

### Impact Explanation
Because the scaled-debt/index used to size a borrower's actual token debt is captured before the cache is silently rewritten by socialization elsewhere in the same block, downstream computations (`convert-to-scaled-debt`, `mul-div-up`/`mul-div-down` conversions in `repay`/`borrow`, and printed liquidation values) can diverge from the vault's true post-write-down state within the same transaction/block. This is a single-block/single-tx cache-invalidation flaw (a "cached value not invalidated when its source moves") that can cause debt/collateral to be mis-valued during liquidation batches, leading to a borrower being under-repaid relative to actual vault-side debt or a liquidator receiving mis-priced collateral — a form of temporary/permanent freezing or theft of protocol-held funds depending on which side the staleness favors.

### Likelihood Explanation
This requires `socialize-debt` (bad-debt write-down) to occur in the same block/transaction as other cache-dependent operations reading the same asset's index — realistically via `liquidate-multi`, where one leg's default triggers socialization while a later leg in the same fold reads/prices the same asset. This is a narrow but real single-transaction interleaving reachable by any DAO-authorized liquidation-bot execution path or attacker-crafted batch ordering (to the extent `liquidate-multi` callers can choose position ordering).

### Recommendation
Do not rely on a single per-block cache entry as “authoritative” once any function in the same call graph mutates vault state (via `vault-socialize-debt`, `vault-accrue`, etc.). Re-read (or re-derive) the index immediately before every consumption point, or invalidate/refresh all `let`-bound copies of `{index, lindex}` for an asset whenever `socialize-debt-asset` (or any other in-block state-mutating vault call) touches that asset's cache entry, instead of only overwriting the map and leaving already-bound local variables stale.

### Proof of Concept
1. DAO enables `liquidate-multi` with two positions in the batch that both have debt in the same asset (e.g. USDC), where position #1 has already accrued enough bad debt to trigger `socialize-debt-asset`.
2. `call-liquidate` processes position #1: liquidation partially fails/defaults, invoking `vault-socialize-debt` for USDC, which changes the vault's internal `lindex`, and then `socialize-debt-asset` overwrites `index-cache/{timestamp, USDC}` with the new post-write-down index.
3. Position #2 in the same `fold`/same block already had its collateral/debt USD values computed earlier (or computes them now) using `convert-to-scaled-debt`, which re-reads `get-cached-indexes` — now returning the post-socialization index instead of the index that was in effect when position #2's health/notional was first evaluated within the batch.
4. The scaled-debt-to-token conversion for position #2 is computed against a different index than the one implicitly assumed by the health check/print audit trail earlier in the same transaction, producing a debt/collateral mismatch within a single block.

**Note on confidence**: I could not fully trace every read/write ordering across `liquidate`, `liquidate-multi`, and `socialize-debt-asset` in a single execution trace with certainty (the fold/early-return `success` flag semantics in `socialize-debt-asset` add complexity I was not able to fully verify against the exact call order in `liquidate`). This should be validated with an actual Clarinet/Vitest trace of a `liquidate-multi` batch containing a socialized position before treating this as confirmed exploitable, since the strength of the impact depends on precise reuse of a stale `let`-bound index value downstream in the same transaction.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
