### Title
Declared PRC20 `liquidity_cap` is never enforced at mint time, allowing unbounded minting past the registered cap - (File: x/uregistry/types/token_config.go, x/uexecutor/keeper/evm.go)

### Summary
The external report's root cause is that a protocol-declared capacity limit (borrow capacity vs. collateral factor) is silently reused/accumulated across operations without the code re-validating the limit at the point of the new action, letting the user exceed the intended risk threshold. The Push Chain analog is `TokenConfig.LiquidityCap`, a per-token "max supply cap" [2](#0-1) , which is validated only for being a non-empty string on registration [3](#0-2)  but is never read, parsed, or compared against cumulative minted supply anywhere in the inbound execution / PRC20 deposit path.

### Finding Description
Every inbound `FUNDS`/`FUNDS_AND_PAYLOAD` tx type mints PRC20 tokens to the recipient's UEA via `CallPRC20Deposit` / `CallPRC20DepositAutoSwap` in `x/uexecutor/keeper/evm.go`, driven purely by the attacker/user-controlled `Inbound.Amount` field once a ballot passes with 2/3 UV votes. Nowhere in this flow — `msg_vote_inbound.go`, `execute_inbound_gas_and_payload.go`, or `evm.go` — is `TokenConfig.LiquidityCap` fetched from `uregistryKeeper` and compared to total supply or cumulative minted amount before minting. As a result, a token's registered liquidity cap (e.g. `"1000000000000000000000000"` in every seeded `TokenConfig` [4](#0-3) ) is purely cosmetic. This mirrors the reported bug class: a per-position/per-token capacity invariant that the protocol advertises as enforced is not actually checked against the running total at the moment new value is created, so ordinary users submitting normal inbound deposits (a fully unprivileged, user-reachable path once UVs honestly observe and vote a real gateway event) can drive total PRC20 supply for a token arbitrarily past its intended cap.

### Impact Explanation
This falls under "corruption of PRC20 ... accounting ... token mapping" and "unauthorized mint" in the allowed impact gate. Exceeding a configured liquidity cap defeats a risk-management control that likely exists to bound protocol exposure per external asset (e.g., limiting how much of an external chain's token Push Chain will represent/back). Uncontrolled over-minting of a PRC20 beyond its intended backing ratio can lead to insolvency of that token's synthetic representation relative to the real locked/bridged collateral on the source chain — a direct value-corruption/accounting invariant break, not merely informational.

### Likelihood Explanation
High. No privileged action or malicious validator/relayer collusion is required — any user can submit repeated, valid gateway deposit events on a source chain (paying only real transfer costs), and honest UVs will vote them through normally since ballot finalization logic never consults `LiquidityCap`. The only friction is the cost of the underlying source-chain deposits, and caps in shipped configs are quite large but finite — the invariant break is guaranteed to be reachable once cumulative deposits approach the cap, which is exactly the kind of "should be checked but isn't" condition the original report criticizes.

### Recommendation
Before minting in `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` (or earlier, during inbound validation in `x/uexecutor`), fetch the token's `TokenConfig.LiquidityCap` from `uregistryKeeper`, query/track the token's current total minted supply (e.g. via a running supply counter in `x/uexecutor` or `x/uregistry` state), and reject or clamp inbound execution once the new mint would exceed the cap — mirroring the "recompute from current state, don't rely on stale/unchecked accumulation" fix pattern recommended in the original report.

### Proof of Concept
Not independently runnable from this analysis (no local test harness executed). The static trace supporting this finding: `TokenConfig.LiquidityCap` is defined in proto [2](#0-1) , validated only for non-emptiness [1](#0-0) , and a repo-wide search confirms zero references to `LiquidityCap`/`liquidity_cap` anywhere under `x/uexecutor/` (the module that performs the actual PRC20 minting via `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` in `x/uexecutor/keeper/evm.go`), meaning the cap is stored but never consulted during mint execution.

**Uncertainty note:** I was not able to fully inspect the entire `x/uexecutor/keeper/evm.go` file contents (only partial snippets were indexed) to rule out a cap check being enforced through some other indirect mechanism (e.g., inside the PRC20 EVM contract itself rather than in the Cosmos keeper layer). If the cap is instead enforced on-chain inside the PRC20 smart contract's `deposit`/`mint` function (not visible in the indexed Go keeper code), this finding would be invalidated or reduced to informational. I recommend a Devin session with full repository/contract access to confirm whether the PRC20 EVM contract bytecode enforces `liquidity_cap` itself before treating this as confirmed-high.

// ValidateBasic performs sanity checks on the TokenConfig
func (p TokenConfig) ValidateBasic() error {
	if strings.TrimSpace(p.Chain) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "chain cannot be empty")
	}

	if strings.TrimSpace(p.Address) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token contract address cannot be empty")
	}

	// Enforce a parseable address for the chain's namespace (e.g. 20-byte hex
	// for eip155, base58 for solana) so every registration lands on the
	// canonical storage key.
	if _, err := utils.CanonicalizeAddressByNamespace(p.Chain, p.Address); err != nil {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token address for chain %s: %s", p.Chain, err)
	}

	if strings.TrimSpace(p.Name) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token name cannot be empty")
	}

	if strings.TrimSpace(p.Symbol) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token symbol cannot be empty")
	}

	if p.Decimals == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "decimals must be greater than zero")
	}

	// Validate token_type is within known enum range
	if _, ok := TokenType_name[int32(p.TokenType)]; !ok {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token_type: %v", p.TokenType)
	}

	if strings.TrimSpace(p.LiquidityCap) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "liquidity_cap cannot be empty")
	}
