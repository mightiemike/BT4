### Title
Missing value validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` proposal parameters allows setting to zero or negative - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator()` validates the value of nearly every committee/witness proposal parameter before it is allowed to be written to `DynamicPropertiesStore`, but the `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` cases fall straight through to `break` with no bound check whatsoever, unlike almost every sibling case which enforces a `[0, LONG_VALUE]` or similar range.

### Finding Description
`ProposalUtil.validator()` is the central gate that every `ProposalCreateContract` proposal value passes through before a witness/committee-approved proposal can mutate a chain parameter. Nearly all cases enforce explicit bounds, e.g. `ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, `WITNESS_PAY_PER_BLOCK`, etc. are checked against `[0, LONG_VALUE]`: [1](#0-0) 

However `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` are grouped together with no validation logic at all: [2](#0-1) 

Once a proposal with these codes is approved, `ProposalService.process()` writes the raw value directly into the dynamic-properties store with no re-check: [3](#0-2) 

This is the same bug class as the reported Audius `Governance` issue: a governance-gated setter mutates a consensus-critical parameter (there: `votingPeriod`/`votingQuorum`; here: `energyFee`/`exchangeCreateFee`) with no lower-bound/range enforcement, even though every comparable sibling parameter in the same code path is validated. `energyFee` in particular is the network-wide price (in SUN per unit of energy) that every smart-contract call transaction is billed at, and `exchangeCreateFee` gates creation of TRC10 bancor-style exchanges.

### Impact Explanation
If `ENERGY_FEE` is approved with a value of `0` (or a negative long, since the protobuf field is a signed `int64` and nothing here rejects negative values), the network-wide energy price becomes `0`. This means any contract call transaction — reachable from any anonymous broadcast transaction — would no longer burn TRX for energy consumption, letting anyone drive unlimited TVM execution/state growth for free, which is a direct resource-accounting/DoS impact on the network (analogous to "proposals with 0 votes can be executed" in the source bug — here "contract execution effectively becomes free"). Setting `EXCHANGE_CREATE_FEE` to `0` similarly removes a network-imposed cost, allowing unlimited free exchange creation and associated state bloat.

### Likelihood Explanation
This requires a proposal to be created and approved by the witness/committee governance process, which is the same governance-gated actor model as the original Audius report (where `setVotingPeriod`/`setVotingQuorum` could only be called through a passed governance proposal, not by an arbitrary EOA). Given the missing validation is purely a code-path gap (unlike all sibling cases that do validate), any single proposal that reaches quorum with this parameter set to `0` would silently corrupt the fee accounting with no compile-time or runtime safeguard, which is a realistic and reachable path through the standard `ProposalCreateContract`/`ProposalApproveContract` transactions.

### Recommendation
Add explicit range validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator()`, mirroring the pattern used for the other fee-type parameters (e.g., `value < 0 || value > LONG_VALUE` throwing `ContractValidateException`), so these parameters cannot be reset to zero or negative values.

### Proof of Concept
1. A witness proposes `ProposalCreateContract` with parameter key `ENERGY_FEE` (code 11) and value `0`.
2. `ProposalUtil.validator()` reaches `case ENERGY_FEE: case EXCHANGE_CREATE_FEE: break;` at [2](#0-1) , performing no check, so the proposal passes validation.
3. Once witnesses approve the proposal, `ProposalService.process()` calls `manager.getDynamicPropertiesStore().saveEnergyFee(0)` unconditionally at [4](#0-3) .
4. All subsequent smart-contract call transactions are billed energy at a price of `0`, effectively making contract execution free for every future broadcast transaction.
