I'll analyze the external bug (unclaimed rewards lost + continued allocation to drained pool during emergency) and search for a nearcore analog. The key invariant: when an account/pool is "drained" or removed, pending rewards/receipts/balances should not be silently lost while the system continues allocating to the now-empty entity.

Let me look at the exact `remove_account` function and the PromiseYield processing path to confirm the full trace.

### Title
PromiseYield Deposit Permanently Burned on Account Self-Deletion Due to Missing Cleanup in `remove_account` — (`core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

---

### Summary

When a contract creates a `PromiseYield` receipt with an attached deposit and then deletes itself in the same execution, `action_delete_account` transfers only the current `account.amount()` to the beneficiary. Because `deduct_balance` already subtracted the yield deposit from `amount()` at yield-creation time, that deposit is silently excluded from the beneficiary transfer. `remove_account` does not remove the orphaned `TrieKey::PromiseYieldReceipt` trie key. The global `PromiseYieldTimeout` queue entry is also left intact. When the timeout fires, `resolve_promise_yield_timeouts` finds the receipt key still present, emits a `PromiseResume` receipt to the now-deleted account, the callback fails with `AccountDoesNotExist`, the deposit refund is sent back to the deleted account (the predecessor), that refund receipt also fails, and the deposit is permanently burned. No guard in the deletion path prevents or compensates for this.

---

### Finding Description

**Step 1 – Deposit deducted at yield creation.**
`promise_yield_create` (or `promise_yield_create_with_id`) calls `self.result_state.deduct_balance(amount)` and then `append_action_function_call_weight(..., amount, ...)`, embedding the deposit inside the `PromiseYield` receipt's `FunctionCall` action. After this call, `account.amount()` is already reduced by `amount`. [1](#0-0) 

**Step 2 – Account deleted; beneficiary receives only the residual balance.**
`action_delete_account` reads `account_ref.amount()` — which no longer includes the yield deposit — and pushes a balance-refund receipt to the beneficiary. It then calls `remove_account`. [2](#0-1) 

**Step 3 – `remove_account` does not touch PromiseYield trie keys.**
`remove_account` removes `TrieKey::Account`, `TrieKey::ContractCode`, all access-key entries, and all contract-data entries. It does **not** remove `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId`. The orphaned receipt — carrying the deposit — remains in the trie. [3](#0-2) 

**Step 4 – Timeout queue entry also survives.**
The `TrieKey::PromiseYieldTimeout` entry is stored in a global ordered queue, not under the account prefix, so it is never touched by `remove_account`.

**Step 5 – Timeout fires; `resolve_promise_yield_timeouts` finds the orphaned receipt.**
At the configured timeout block height, `resolve_promise_yield_timeouts` checks `state_update.contains_key(&promise_yield_key, ...)`. Because the `PromiseYieldReceipt` key was never removed, the check succeeds and a `PromiseResume` receipt is emitted targeting the deleted account. [4](#0-3) 

**Step 6 – PromiseResume processing executes the orphaned yield receipt on the deleted account.**
`process_receipt` finds the `PromiseYieldReceipt` in the trie, removes it, and calls `apply_action_receipt` on it. The yield receipt's `FunctionCall` action fails with `ActionErrorKind::AccountDoesNotExist` because the account no longer exists. [5](#0-4) 

**Step 7 – Deposit refund sent to the deleted account; burned.**
On failure, `apply_action_receipt` emits a deposit-refund receipt to `receipt.balance_refund_receiver()` = `receipt.predecessor_id()`, which for a self-targeted PromiseYield is the deleted account itself. That refund receipt arrives at the deleted account, fails with `AccountDoesNotExist` (non-implicit account, no implicit-creation path), and per the refund spec the amount is burned. [6](#0-5) 

---

### Impact Explanation

The deposit attached to the `PromiseYield` receipt is permanently burned. It is neither transferred to the `DeleteAccount` beneficiary nor returned to any other party. The beneficiary receives `original_balance − yield_deposit` instead of `original_balance`. The burned amount equals whatever deposit the contract attached to the yield callback, which can be any value up to the account's full balance. This is a direct, irreversible loss of user funds reachable through ordinary contract execution with no privileged role required.

---

### Likelihood Explanation

The trigger requires a contract to (a) call `promise_yield_create` with a non-zero deposit and (b) schedule a `DeleteAccount` on itself in the same or a subsequent execution before the yield is resolved. Both are standard host-function calls available to any deployed contract. A contract implementing an async pattern (e.g., waiting for an oracle callback) that also supports self-destruction is a realistic scenario. The user may not realize the deposit is excluded from the beneficiary payout. Likelihood is low-to-medium: the combination is uncommon but entirely reachable by an unprivileged user without any admin or validator assumption.

---

### Recommendation

1. **Block deletion when pending yields exist.** In `action_delete_account`, iterate the `PromiseYieldReceipt` prefix for the account (analogous to how `compute_gas_key_balance_sum` iterates access keys) and return `ActionErrorKind::DeleteAccountWithPendingYield` if any are found. This mirrors the existing guard for staked balance (`DeleteAccountStaking`).

2. **Alternatively, sweep yield deposits to the beneficiary.** If deletion with pending yields must be allowed, `action_delete_account` should enumerate all `TrieKey::PromiseYieldReceipt` entries, sum their embedded `FunctionCall` deposits, add that sum to the beneficiary transfer, and remove the receipt and status keys. The corresponding `PromiseYieldTimeout` entries must also be invalidated (e.g., by removing the `PromiseYieldReceipt` key so `resolve_promise_yield_timeouts` skips them).

3. **Update `remove_account` documentation** to explicitly list which trie-key namespaces it does and does not clean up, so future features do not repeat this omission.

---

### Proof of Concept

```
1. Deploy contract C on account "mycontract.near".
2. Call C::run():
     a. promise_yield_create("callback", args=[], deposit=10_NEAR, gas=50TGas)
        → deposit deducted: account.amount() reduced by 10 NEAR
        → PromiseYieldReceipt stored in trie under (receiver="mycontract.near", data_id=X)
        → PromiseYieldTimeout enqueued at block H + timeout_length
     b. promise_batch_action_delete_account(self, beneficiary="alice.near")
        → DeleteAccount instant receipt queued

3. Same chunk: DeleteAccount instant receipt executes.
     action_delete_account reads account.amount() = original_balance - 10 NEAR
     → emits balance_refund("alice.near", original_balance - 10 NEAR)
     → calls remove_account("mycontract.near")
        removes: Account, ContractCode, access keys, contract data
        does NOT remove: TrieKey::PromiseYieldReceipt{receiver="mycontract.near", data_id=X}

4. At block H + timeout_length:
     resolve_promise_yield_timeouts checks contains_key(PromiseYieldReceipt{..., X}) → true
     → emits PromiseResume receipt to "mycontract.near"

5. Next chunk: PromiseResume processed.
     get_promise_yield_receipt → found (orphaned)
     remove_promise_yield_receipt, remove_promise_yield_status
     apply_action_receipt(yield_receipt) on deleted account
     → FunctionCall fails: AccountDoesNotExist
     → deposit_refund(10 NEAR) sent to predecessor = "mycontract.near" (deleted)

6. Next chunk: balance_refund receipt to "mycontract.near" processed.
     check_transfer_to_nonexisting_account → AccountDoesNotExist (non-implicit)
     → receipt fails → 10 NEAR burned per refund-failure rule

Result: alice.near receives original_balance - 10 NEAR; 10 NEAR is permanently burned.
```

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
