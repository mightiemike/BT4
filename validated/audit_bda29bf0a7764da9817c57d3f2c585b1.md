### Title
Witness vote-reward accounting lets a voter harvest a full cycle's `Vi`-based reward without their vote being counted in that cycle's reward denominator - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
java-tron's SR (witness) voting reward system distributes rewards using a per-witness cumulative "value-per-vote" index (`Vi`), analogous to the lsETH share-price mechanism in the reported bug. Because the vote-count used to compute each cycle's `Vi` delta is snapshotted **before** newly-cast votes for that cycle are folded into the witness's vote total, but a voter's *own* reward is later computed by multiplying that cycle's `Vi` delta by their *current* vote amount, a voter who casts a vote just before a maintenance/cycle boundary can be credited with a full cycle's reward despite not having contributed to (or being counted in) the pool that produced that `Vi` value — the same "time the deposit to harvest profits others earned" pattern described in the external report.

### Finding Description
Rewards accrue per witness as an accumulated index `Vi`, updated once per cycle in `MaintenanceManager.doMaintenance()`: [1](#0-0) 

This call to `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` happens **before** the current cycle's newly cast votes (`countWitness`, aggregated from `VotesStore`) are added to `witnessCapsule`'s vote count: [2](#0-1) 

and only after all this does the vote count get persisted for the *next* cycle: [3](#0-2) 

So the denominator used to compute `Vi` for cycle N is the vote total *as it stood before cycle N's votes were added* — i.e., votes cast during cycle N are deliberately excluded from that cycle's `Vi` computation and only affect cycle N+1.

However, when an individual account's reward is computed, `MortgageService.computeReward` (and its TVM-native duplicate `VoteRewardUtil.computeReward`) multiplies the delta `Vi` for a cycle range by the account's **current** vote amount taken from `accountCapsule.getVotesList()`, not a per-cycle historical snapshot of how much was voted during each cycle: [4](#0-3) 

The per-account cycle range (`beginCycle`) is set to the *current* cycle number whenever the user calls vote (via `VoteWitnessActuator.countVoteAccount`, which calls `mortgageService.withdrawReward(ownerAddress)` on the **old** vote amount before overwriting with the new vote and only then commits new votes): [5](#0-4) 

Because `beginCycle` is set to `currentCycle` (the in-progress cycle, not `currentCycle + 1`), the new vote amount ends up being treated as having earned reward starting from cycle N even though: (a) it was cast partway through cycle N, and (b) it was explicitly excluded from the vote-count denominator used to compute cycle N's `Vi` (per the `MaintenanceManager` ordering above). The result is that the late voter's payout for cycle N is calculated using a `Vi` rate that was derived from a smaller vote-count base that did not include them — over-crediting their reward relative to what the actual pool for that cycle can support, since the pool's per-vote rate assumed a smaller number of "shares" than actually got paid out once the late-arriving vote is included in `computeReward`'s numerator.

### Impact Explanation
This produces the same "deposit-timing to harvest disproportionate rewards" primitive described in the report: a voter can wait until just before a maintenance/cycle boundary, vote a large amount of TRON Power for a witness receiving a large block/transaction-fee reward for the closing cycle, and immediately withdraw a reward computed as if they held that vote for the entire cycle — while other, earlier voters effectively see their share of the pool diluted because the payout math does not scale down to conserve the total reward collected for that witness in that cycle. Since `MortgageService.adjustAllowance` credits `AccountCapsule.allowance`, which is later paid out as real TRX via `WithdrawBalanceActuator`/`WithdrawRewardProcessor`, this is a concrete accounting/economic issue rather than a purely theoretical one.

### Likelihood Explanation
Exploitation requires only an ordinary `VoteWitnessContract` (or the TVM native vote equivalent) sent in the last block(s) of a maintenance cycle, with no privileged role, and votes/maintenance cycles occur routinely (each maintenance interval, by default every 6 hours) — making the timing window predictable and repeatable, similar to how the report notes daily oracle updates limit but do not eliminate the analogous River issue.

### Recommendation
Track each account's vote weight per cycle explicitly (e.g. record the vote amount that was in effect at the start of each cycle in `DelegationStore`/`VotesStore`, rather than re-reading the account's *current* vote list in `computeReward`), or delay the effective start cycle for newly-cast votes to `currentCycle + 1` so a vote's `beginCycle` never precedes the cycle number used as the denominator basis for `Vi`. This aligns per-account reward accrual with the actual vote-count snapshot used to compute the witness's `Vi` for that cycle, closing the gap that allows late voters to be paid from a `Vi` rate computed without them.

### Proof of Concept
Conceptual sequence (based on the code paths above, not independently executed):
1. Witness W accrues a large block/fee reward during cycle N via `MortgageService.payReward` (`delegationStore.addReward(cycle, witnessAddress, value)`).
2. Near the very end of cycle N (just before `doMaintenance()` runs), attacker calls `VoteWitnessContract` to vote a large amount for W. `VoteWitnessActuator.countVoteAccount` withdraws attacker's prior (zero) reward and sets `beginCycle = N`, then registers the new vote in `AccountCapsule`/`VotesStore`.
3. `MaintenanceManager.doMaintenance()` runs: `accumulateWitnessVi(N, W, oldVoteCount)` computes `Vi(N)` using W's vote count *before* attacker's new vote is added; attacker's vote is only merged into W's vote count for cycle `N+1`.
4. Cycle advances to `N+1`. Attacker calls `queryReward`/`withdrawReward`; `computeReward(N, N+1, accountCapsule)` computes `deltaVi = Vi(N) - Vi(N-1)` and multiplies it by attacker's *current* vote amount (the large vote just cast), crediting the attacker a full cycle-N reward share despite having 0% actual participation in cycle N's vote-count denominator.

Because I could not execute this in a live node/test environment, this is presented as a structural/code-path analysis rather than an empirically confirmed exploit; the `VoteTest.java` reward-algorithm tests exercise adjacent vote/withdraw timing scenarios but do not appear to specifically test a vote cast in the final block before `doMaintenance()`.

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
