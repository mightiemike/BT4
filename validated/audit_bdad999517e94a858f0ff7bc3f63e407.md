### Title
Unchecked long overflow in `FreezeBalanceProcessor.execute()` expire-time calculation reachable from TVM contract calls, missing the duration bounds check present in the legacy actuator - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
`FreezeBalanceProcessor`, the native-contract handler invoked from TVM smart-contract execution (via `Program.java`), computes the freeze `expireTime` with plain, unchecked `long` arithmetic and never validates the `frozenDuration` value against the `minFrozenTime`/`maxFrozenTime` bounds that the equivalent legacy `FreezeBalanceActuator` enforces. This mirrors the reported Convexity-Protocol bug class: an attacker-influenced time-window value participates in unchecked arithmetic, letting the resulting checkpoint be pushed outside its intended range and corrupting the accounting/lock invariant that resource-freezing depends on.

### Finding Description
`FreezeBalanceProcessor.validate()` only checks that `frozenBalance` is positive, ≥ 1 TRX, ≤ balance, that `frozenCount` is 0/1, and that the resource code is BANDWIDTH/ENERGY: [1](#0-0) 

Unlike its sibling `FreezeBalanceActuator.validate()`, which explicitly bounds `frozenDuration` against `minFrozenTime`/`maxFrozenTime` before it is ever used to compute an expiry: [2](#0-1) 

`FreezeBalanceProcessor.execute()` uses `frozenDuration` directly in unchecked multiplication/addition to derive the resource-lock expiry: [3](#0-2) 

Because `nowInMs + param.getFrozenDuration() * FROZEN_PERIOD` is ordinary `long` arithmetic (no `Maths.addExact`/`multiplyExact`, no `StrictMathWrapper`, no `hardenCalculation()` gate as used elsewhere in the codebase, e.g. in `AssetIssueActuator` where the same class of overflow is explicitly guarded), a sufficiently large `frozenDuration` silently wraps the 64-bit `long`, producing an `expireTime` that can land in the past or at an unintended small/negative value — exactly the same “dynamic time-window subtraction/addition without SafeMath” defect the external report flags (`expiry - windowSize` wrapping to `2**256-1`). Compare with the hardened pattern already used for the same underlying invariant in `AssetIssueActuator`, which wraps the identical `frozenDays * FROZEN_PERIOD` addition in `StrictMathWrapper.addExact` specifically to reject overflow: [4](#0-3) 

`FreezeBalanceProcessor` implements no equivalent guard, and no `frozenDuration` range check exists at all in this native-contract code path, so the analogous protection that exists for the legacy contract-issued transaction path (`FreezeBalanceActuator`) is absent for the TVM-triggered path.

`FreezeBalanceParam.frozenDuration` is a plain mutable `long` field populated by the VM/Program layer when a contract invokes the corresponding native (precompiled) freeze operation: [5](#0-4) 
`Program.java` is the integration point that constructs/dispatches this native call from contract execution (confirmed by 10 references to `FreezeBalanceProcessor`/`FreezeBalanceParam` in that file), meaning the duration value ultimately originates from smart-contract-controlled call data reachable by any address that can invoke the corresponding TVM opcode/precompile. I was not able to fully trace, within the remaining tool budget, the exact bytes-to-`frozenDuration` decoding logic inside `Program.java` to confirm whether any additional clamping happens there before `setFrozenDuration` is called; this should be verified directly in that file.

### Impact Explanation
If `frozenDuration` is not bounded before entering this multiplication/addition, an attacker-controlled contract can drive `expireTime` to an unintended value (e.g., a value in the past, or a small positive value) via integer overflow. Because `expireTime` is the sole checkpoint used to gate resource release/unfreeze semantics, this could let an attacker acquire bandwidth/energy resource-freeze bookkeeping that appears expired immediately (bypassing the intended lock period) or otherwise desynchronize the on-chain resource/weight accounting (`repo.addTotalNetWeight`/`addTotalEnergyWeight`) from the account's actual locked balance — an accounting-corruption class impact consistent with the “No SafeMath validation of a subtracted/added time window” bug class described in the report.

### Likelihood Explanation
The path is reachable by any account able to submit a contract call that triggers the native freeze-balance operation (no privileged role required), and the missing bound is a straightforward, deterministic effect of supplying an out-of-range `frozenDuration`. Exploitability depends on confirming that `Program.java` does not itself clamp the decoded duration before calling `setFrozenDuration`; this is the one piece I could not fully verify.

### Recommendation
- Add the same `frozenDuration` bounds validation (`minFrozenTime`/`maxFrozenTime`) to `FreezeBalanceProcessor.validate()` that already exists in `FreezeBalanceActuator.validate()`.
- Replace the unchecked `nowInMs + param.getFrozenDuration() * FROZEN_PERIOD` computation with the project's existing hardened arithmetic helpers (`Maths.addExact`/`multiplyExact` or `StrictMathWrapper.addExact`, as already used in `AssetIssueActuator`) and reject the transaction/call on overflow.

### Proof of Concept
1. Deploy or use a contract that can trigger the native freeze-balance operation handled by `FreezeBalanceProcessor` (via the TVM path wired through `Program.java`).
2. Supply a `frozenDuration` value large enough that `frozenDuration * FROZEN_PERIOD` (or the subsequent `+ nowInMs`) overflows a signed 64-bit `long` (`FROZEN_PERIOD` is a fixed millisecond constant, so any duration greater than `Long.MAX_VALUE / FROZEN_PERIOD` triggers overflow).
3. Observe that `FreezeBalanceProcessor.validate()` does not reject this value (no min/max duration check), and `execute()` stores the wrapped `expireTime` via `accountCapsule.setFrozenForBandwidth`/`setFrozenForEnergy`, corrupting the freeze/expiry invariant relative to the actual balance locked.

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }
