### Title
Governance-driven change of `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` / `TOTAL_ENERGY_LIMIT` does not rebalance `TOTAL_ENERGY_CURRENT_LIMIT`, leaving every account's energy allocation stale for many adjustment cycles - (File: framework/src/main/java/org/tron/core/consensus/ProposalService.java, chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
Java-tron's adaptive energy mechanism splits the network's total energy budget into a "target" limit (`TOTAL_ENERGY_TARGET_LIMIT`, derived from `TOTAL_ENERGY_LIMIT / ratio`) and a "current" limit (`TOTAL_ENERGY_CURRENT_LIMIT`), the latter being the value actually used to compute every account's available energy. When the committee changes the ratio (or the base limit) through a governance proposal, only the target value is updated instantly; the current limit is left untouched and can only "catch up" through the existing ±0.1%-per-minute adaptive adjustment mechanism. This mirrors the AfEth finding: a configurable ratio parameter is changed, but there is no mechanism to rebalance the already-established state to the new ratio — the system instead relies on slow, incremental convergence, which can leave the actual allocation diverged from the intended one for a long time.

### Finding Description
`ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` is a chain parameter, analogous to AfEth's `ratio`, that determines how the total energy budget (`TOTAL_ENERGY_LIMIT`) is split into a target value used to decide whether the network should contract or expand `TOTAL_ENERGY_CURRENT_LIMIT`: [1](#0-0) 

```
case ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO: {
  long ratio = 24 * 60 * entry.getValue();
  manager.getDynamicPropertiesStore().saveAdaptiveResourceLimitTargetRatio(ratio);
  manager.getDynamicPropertiesStore().saveTotalEnergyTargetLimit(
      manager.getDynamicPropertiesStore().getTotalEnergyLimit() / ratio);
  break;
}
```

This proposal handler only updates `TOTAL_ENERGY_TARGET_LIMIT`; it never touches `TOTAL_ENERGY_CURRENT_LIMIT`, which is the value that is actually used to compute every account's real, usable energy: [2](#0-1) 

The only place `TOTAL_ENERGY_CURRENT_LIMIT` is adjusted is `updateAdaptiveTotalEnergyLimit()`, which nudges it toward the target by a fixed contraction/expansion rate (bounded by `totalEnergyLimit` and `totalEnergyLimit * multiplier`), executed once per adaptive period (on the order of one minute): [3](#0-2) 

The same pattern occurs for `TOTAL_ENERGY_LIMIT` itself: the deprecated `TOTAL_ENERGY_LIMIT` proposal path only recomputes `TOTAL_ENERGY_TARGET_LIMIT`, and even the newer `TOTAL_CURRENT_ENERGY_LIMIT` path only resets `TOTAL_ENERGY_CURRENT_LIMIT` when `AllowAdaptiveEnergy == 0` (i.e. on mainnet, where adaptive energy is enabled, changing the base limit does not rebalance the current limit either): [4](#0-3) 

This is the same root cause as the AfEth report: a governance-adjustable ratio/limit is changed, but the state that determines the *actual* real-time allocation is not rebalanced to reflect the new configuration — it can only converge slowly through the ordinary per-cycle adjustment mechanism, exactly as AfEth relies on "new deposits and reward compounding to slowly correct the offset."

### Impact Explanation
`TOTAL_ENERGY_CURRENT_LIMIT` directly determines the amount of energy every unprivileged account can obtain from frozen TRX (`calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`), which governs how much smart-contract execution every user can perform for free before paying in TRX. If governance lowers the ratio/base limit intending to shrink the network-wide energy budget (e.g., to react to abuse or congestion), the stale, higher `TOTAL_ENERGY_CURRENT_LIMIT` continues to grant all accounts inflated energy allocations for an extended period — an accounting/state divergence between the intended (target) resource budget and the actually enforced one. Conversely, if governance intends to raise the budget, users are under-served relative to the new configuration until the slow ±0.1%-per-minute steps catch up. Because this value is read on every energy computation across the entire network, the divergence is a systemic, network-wide state/accounting mismatch, not a localized issue.

### Likelihood Explanation
Triggering the divergence requires a passed committee/witness proposal changing `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` or `TOTAL_ENERGY_LIMIT`/`TOTAL_CURRENT_ENERGY_LIMIT` — a governance action, not an arbitrary unprivileged transaction. However, unlike a purely internal/no-impact governance quirk, the resulting mismatch is silently exploited by every ordinary, unprivileged account interacting with the TVM during the (potentially long) convergence window, since their actual energy allocation is computed straight from the stale `TOTAL_ENERGY_CURRENT_LIMIT`. This is the same likelihood profile the original judges accepted for AfEth (admin-triggered ratio change, but affecting all depositors going forward) and was still ranked Medium severity.

### Recommendation
When a proposal updates `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO`, `TOTAL_ENERGY_LIMIT`, or `TOTAL_CURRENT_ENERGY_LIMIT`, immediately recompute and persist a consistent `TOTAL_ENERGY_CURRENT_LIMIT` (e.g., clamp it into the new `[totalEnergyLimit, totalEnergyLimit * multiplier]` bounds, or reset it to the new target) rather than leaving it to converge only through the incremental `updateAdaptiveTotalEnergyLimit()` steps. This removes the window during which the enforced resource limit diverges from the governance-intended configuration.

### Proof of Concept
1. Assume `AllowAdaptiveEnergy == 1` (mainnet default) and `TOTAL_ENERGY_CURRENT_LIMIT` has drifted up to `totalEnergyLimit * multiplier` (its upper bound) due to sustained high usage.
2. The committee passes a proposal lowering `TOTAL_ENERGY_LIMIT` (case `TOTAL_ENERGY_LIMIT`/`TOTAL_CURRENT_ENERGY_LIMIT` in `ProposalService.process`). Only `TOTAL_ENERGY_TARGET_LIMIT` is recomputed from the new, lower `totalEnergyLimit`; `TOTAL_ENERGY_CURRENT_LIMIT` keeps its old, much larger value because `getAllowAdaptiveEnergy() == 1` skips the reset branch in `saveTotalEnergyLimit2`.
3. Every subsequent block, `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` still divides by the stale, oversized `TOTAL_ENERGY_CURRENT_LIMIT`, granting all frozen-TRX accounts far more free energy than the newly configured budget intends.
4. `updateAdaptiveTotalEnergyLimit()` only contracts the current limit by `CONTRACT_RATE_NUMERATOR/DENOMINATOR` (≈0.1%) per adaptive period, so it can take a large number of periods for the enforced limit to converge to the governance-intended value — during which every ordinary user's actual energy allocation is inconsistent with the on-chain configured parameters.

  public void updateAdaptiveTotalEnergyLimit() {
    long totalEnergyAverageUsage = dynamicPropertiesStore
        .getTotalEnergyAverageUsage();
    long targetTotalEnergyLimit = dynamicPropertiesStore.getTotalEnergyTargetLimit();
    long totalEnergyCurrentLimit = dynamicPropertiesStore
        .getTotalEnergyCurrentLimit();
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyLimit();

    long result;
    if (totalEnergyAverageUsage > targetTotalEnergyLimit) {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_DENOMINATOR);
    } else {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.EXPAND_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.EXPAND_RATE_DENOMINATOR);
    }
    long upperBound = hardenCalculation()
        ? BigInteger.valueOf(totalEnergyLimit).multiply(BigInteger.valueOf(
            dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier())).longValueExact()
        : totalEnergyLimit * dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier();
    result = min(max(result, totalEnergyLimit, this.disableJavaLangMath()),
        upperBound, this.disableJavaLangMath());

    dynamicPropertiesStore.saveTotalEnergyCurrentLimit(result);
    logger.debug("Adjust totalEnergyCurrentLimit, old: {}, new: {}.",
        totalEnergyCurrentLimit, result);
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimitV2(long frozeBalance) {
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (totalEnergyWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV2(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    double energyWeight = (double) frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
