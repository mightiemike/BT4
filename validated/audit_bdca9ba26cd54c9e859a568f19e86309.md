### Title
Staker-controlled `StakeInstruction::Split` between reward calculation and distribution triggers deterministic `assert_eq!` panic in `Bank::build_updated_stake_reward`, halting replay - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`Bank::build_updated_stake_reward` in the non-rent-adjusted path recomputes `expected_delegation` from the **live** stake delegation fetched from `self.stakes_cache` at distribution time, while `new_stake.delegation.stake` comes from the **calculation-time** snapshot stored in `PartitionedStakeReward`. Between the calculation block and the (potentially many blocks later) distribution block for a given partition, an ordinary staker can submit a `StakeInstruction::Split` to change the live `delegation.stake` of their own stake account, causing the `assert_eq!` to fail deterministically for every validator replaying that block.

### Finding Description
In `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`:

- `store_stake_accounts_in_partition` fetches `stakes_cache_accounts` from the **current** `self.stakes_cache.stakes()` at distribution time (line 363-364), which reflects all transactions executed up to that slot, including any `Split` on the reward-pending stake account. [1](#0-0) 

- `build_updated_stake_reward` looks up the live account/state (`stake`) for `partitioned_stake_reward.stake_pubkey` from this live map: [2](#0-1) 

- When `adjust_delegations_for_rent` (i.e. `relax_post_exec_min_balance_check`) is inactive (default), the code asserts that the live `stake.delegation.stake` plus the calculation-time `inflation.stake_reward` equals the calculation-time `new_stake.delegation.stake` (also frozen in `partitioned_stake_reward.inflation.stake`, computed during the once-per-epoch reward calculation phase): [3](#0-2) 

The reward calculation happens once at the epoch boundary and is partitioned across up to 10% of the epoch's slots (`get_reward_distribution_num_blocks`), so there can be a substantial window between calculation and a given account's distribution slot: [4](#0-3) 

During this window, the stake account is a normal, owner-controlled account, and nothing in the reviewed code (distribution.rs, mod.rs) re-derives `new_stake` from live state on the non-rent-adjusted path — it blindly reuses the calculation-time frozen value. I was unable to locate any check in the stake program (`programs/stake*`) that references `EpochRewards`/`epoch_rewards_sysvar` to block mutating instructions like `Split` while a reward is pending; no such references were found via search of that directory. If an attacker splits part of the stake off the account between calculation and that partition's distribution block, the live `stake.delegation.stake` (post-split, reduced) no longer matches the calculation-time `new_stake.delegation.stake` (pre-split, full), and `expected_delegation != new_stake.delegation.stake`, tripping the `assert_eq!` and panicking every validator replaying that slot deterministically (since the partition assignment and stake pubkeys are fixed by `hash_rewards_into_partitions` and identical across all nodes).

Note: a separate mechanism, `recalculate_partitioned_rewards_if_active`, does re-derive stake rewards from live state, but it is only invoked from `initialize_after_snapshot_restore`, not on every distribution block during normal replay: [5](#0-4) 

### Impact Explanation
If reachable, this is a cluster-halting consensus-liveness panic (PANIC_FREEDOM violation) triggerable by an unprivileged staker via ordinary `Split` instruction timing, with no special privileges required — matching the "consensus divergence / cluster-halting panic" bounty category.

### Likelihood Explanation
Preconditions are minimal and staker-controlled: an ordinary delegated stake account with a pending calculated inflation reward, and `relax_post_exec_min_balance_check` inactive (the stated default assert path). The attacker only needs to submit a normal `Split` instruction affecting `delegation.stake` on their own stake account at some point between the once-per-epoch calculation block and their account's assigned partition distribution block (a window that can span many slots per `get_reward_distribution_num_blocks`). This requires no elevated access, no exploit of loader/geyser/snapshot paths, and is fully repeatable each epoch, though it does deterministically crash the validator, so it is a one-shot, high-impact action per attempt. I could not confirm whether an additional safeguard elsewhere in the transaction-processing pipeline (outside `programs/stake*` and the files reviewed) blocks stake mutations while rewards are pending; this is the primary residual uncertainty.

### Recommendation
On the non-rent-adjusted path, do not compare against the frozen calculation-time `new_stake.delegation.stake`. Instead, re-derive the updated delegation from the **live** `stake.delegation.stake` plus `partitioned_stake_reward.inflation.stake_reward` (i.e., trust live state and add the addition amount to it), mirroring the rent-adjusted branch's model of applying rewards at distribution time rather than asserting equality with a stale precomputed value. Alternatively, invalidate/re-run reward calculation for any stake account whose delegation changed between calculation and distribution (similar in spirit to `recalculate_partitioned_rewards_if_active`), or reject/burn (not panic) the reward for such accounts.

### Proof of Concept
Bank integration test plan:
1. Create a bank, fund a keypair, and create a delegated stake account with a known `delegation.stake`.
2. Advance to the epoch boundary so `distribute_partitioned_epoch_rewards` computes and caches a `PartitionedStakeReward` for this stake account (feature `relax_post_exec_min_balance_check` inactive).
3. Before advancing to the block height corresponding to this account's assigned partition, submit a `StakeInstruction::Split` transaction that moves part of the stake to a new stake account, reducing the source account's live `delegation.stake`.
4. Advance the bank to the distribution slot for that partition and call `distribute_partitioned_epoch_rewards`.
5. Assert that `Bank::build_updated_stake_reward`'s `assert_eq!("stake reward delegation must be consistent...")` panics (reproducing the crash), confirming the code does not re-derive `expected_delegation`/`new_stake` from live post-Split state.
6. After applying the recommended fix (recompute delegation from live state), re-run the same scenario and assert no panic occurs and rewards are consistently applied to the post-split live stake.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }
