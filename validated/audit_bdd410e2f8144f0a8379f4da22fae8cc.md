### Title
Missing existence check on `DeleteAccountAction.beneficiary_id` causes irrecoverable loss of the deleted account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
The reported bug class is a missing validation of a recipient/owner address parameter (`_to`), which — if the value is invalid/"zero" — permanently blocks fund recovery. The nearcore analog is `DeleteAccountAction.beneficiary_id`: a transaction signer supplies this account id and it is never checked for actually existing (only its syntactic validity is checked). If the account named as beneficiary does not exist, the balance transfer generated by the delete bounces back as a failed system refund receipt, whose deposit is then **burned** rather than returned to anyone.

### Finding Description
`validate_delete_action` only validates that `beneficiary_id` is a *syntactically* valid account id, with no existence check: [1](#0-0) 

When the `DeleteAccount` action executes, the account's entire remaining balance is unconditionally wrapped into a `Receipt::new_balance_refund(beneficiary_id, account_balance)` and the source account is deleted immediately, with no check that `beneficiary_id` is a live account: [2](#0-1) 

The generated receipt is a system-predecessor "refund" receipt: [3](#0-2) 

When this refund receipt is later processed against `beneficiary_id`, if that account is a non-existent *named* account, `check_account_existence` rejects the implicit `Transfer` action with `AccountDoesNotExist` (implicit account creation is only allowed for implicit-style ids, not for named ids that were never created): [4](#0-3) 

Because the receipt's `predecessor_id` is `"system"`, a failure at this point does **not** generate a further refund — the deposit is unconditionally burned: [5](#0-4) 

The project's own tests document this exact behavior as expected/known: they deliberately pre-create the beneficiary account and note "the beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" (which, per the code above, is then burned): [6](#0-5) 

This is the direct analog of the reported `RewardsManager.vy` bug: an address parameter (`beneficiary_id`, playing the role of `_to`) is accepted from an unprivileged caller and used to move value without checking that the destination is actually usable/existing, leading to loss of funds instead of a safe rejection or fallback.

### Impact Explanation
A transaction signer who submits a `DeleteAccountAction` (directly, or via `promise_batch_action_delete_account` from a contract acting on their behalf) with a `beneficiary_id` that is syntactically valid but does not exist as an account (a typo, a since-deleted account, or any account the signer mistakenly believes exists) causes:
1. Their own account to be irrevocably deleted.
2. The account's entire remaining NEAR balance to be sent in a refund receipt that fails and is then **permanently burned** — not returned to the signer, not credited to anyone.

This is a concrete, transaction-triggered, permanent loss of user funds (frozen/destroyed funds), which is one of the accepted impact categories (permanently frozen funds / unauthorized value destruction). It does not require any privileged role, malicious peer, or validator — a single ordinary transaction signer reaches it.

### Likelihood Explanation
Likelihood is high for accidental triggering: `beneficiary_id` is a free-form, syntactically-validated-only `AccountId` supplied by the caller (transaction sender or a contract via the promise batch API), with zero requirement that it currently exists. Given how common minor typos or stale references to previously-existing accounts are, and that this action is final/irreversible (`DeleteAccountAction` deletes the source account synchronously in the same action, before the beneficiary receipt is even attempted), a mistake here cannot be corrected — the source account is already gone by the time the refund fails.

### Recommendation
Before executing `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or an account type where implicit creation on transfer is guaranteed to succeed, e.g. a `NearImplicit`/`EthImplicit`/deterministic id). If the beneficiary account does not exist, fail the `DeleteAccount` action itself (returning a clear error such as `BeneficiaryDoesNotExist`) rather than deleting the source account and only discovering the problem after the funds are already unrecoverably in flight to a system refund that burns on failure.

### Proof of Concept
1. Create account `alice.near` with balance `B`, and never create an account named `nonexistent123.near`.
2. As `alice.near`, submit a transaction whose only/final action is `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent123.near".parse().unwrap() })`, following the pattern used in existing tests: [7](#0-6) 
3. `action_delete_account` deletes `alice.near` and enqueues `Receipt::new_balance_refund("nonexistent123.near", B)` with `predecessor_id == "system"`.
4. When this receipt is processed, `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist` because `nonexistent123.near` is a named (non-implicit) account that was never created.
5. Because the receipt's predecessor is `"system"`, the failure path burns the deposit instead of refunding it (`runtime/runtime/src/lib.rs:1047-1054`), and `alice.near`'s balance `B` is permanently destroyed with no recovery path.

```rust
pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    receipt_shape: ReceiptShape,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            }
            if get_account_type(account_id, config).is_implicit() {
                // Implicit accounts can only be created implicitly.
                // `CreateAccount` claims `actor_id` for the new account, which
                // would let the rest of the receipt add an access key to an id
                // whose private key the sender does not hold. Rejecting the action
                // is the simplest way to close that.
                // See https://github.com/nearprotocol/NEPs/pull/71
                return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::Transfer(_) => {
            let account_type = get_account_type(account_id, config);
            if account.is_none() && !implicit_creation_allowed(account_type, receipt_shape) {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
```
