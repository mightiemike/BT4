### Title
`sanitizeHost()` fails to validate base64 length, causing unhandled `atob()` exceptions instead of the intended `InvalidHostError` — DoS of auth/redirect handlers - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
This is the same bug class as the Rocket Pool report: a boundary/length check is incomplete, so an input that should be rejected up front instead slips past validation and reaches logic that assumes well-formed data, producing incorrect/unsafe behavior instead of a clean revert (here, a clean `InvalidHostError`).

### Finding Description
`sanitizeHost()` validates the `host` query parameter with a regex that accepts *any* string composed of base64 characters, regardless of length: [1](#0-0) 

```
const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
```

This regex does not enforce that the base64 payload length is a multiple of 4 (nor forbid a length that decodes to a fractional byte). Per the WHATWG "forgiving-base64" decode algorithm implemented by `atob()` (used in Node/browsers), a string whose length modulo 4 equals 1 (e.g. a single character like `"A"`) causes `atob()` to throw `InvalidCharacterError`, since it cannot represent a whole number of bytes.

`decodeHost()` is a thin wrapper with no error handling: [2](#0-1) 

Because `sanitizeHost()` calls `decodeHost()` directly inside its validation logic (not inside a try/catch), a `host` value such as `A`, `AB CDE` truncated to 1/5/9… chars, etc. causes `sanitizeHost()` itself to throw a raw `DOMException`/`TypeError` instead of returning `null` or the intended `InvalidHostError`. Every caller of `sanitizeHost()` is written expecting either a string or `null` (or a `ShopifyErrors.InvalidHostError` when `throwOnInvalid` is used) — none of them anticipate an arbitrary uncaught exception type from `atob()`.

### Impact Explanation
Several request-handling paths call `sanitizeHost()` on an attacker-controlled `host` query parameter without wrapping the call in a try/catch:
- `redirectToShopifyOrAppRoot` in shopify-app-express: [3](#0-2) 
- `redirectToShopifyOrAppRoot` in shopify-app-remix/react-router: [4](#0-3) 
- `validateShopAndHostParams` in shopify-app-remix/react-router (used in the `authenticate.admin` flow): [5](#0-4) 
- `redirectWithExitIframe`: [6](#0-5) 
- `redirectToAuth` (client-side redirect branch) in shopify-app-express: [7](#0-6) 

For the Express integration in particular, these are `async` route/middleware functions registered directly with Express. Express 4.x (the version this repo's middleware style targets) does not automatically catch rejected promises thrown from async handlers; an uncaught exception thrown synchronously inside an `async` function becomes an unhandled promise rejection. Depending on the Node.js runtime configuration (`--unhandled-rejections` default is `throw` since Node 15), this can terminate the Node process, resulting in a denial of service against the app's auth/embedding flow from a single unauthenticated HTTP request.

Even where the framework does catch the exception (e.g. remix/react-router loaders that wrap thrown errors into 500 responses), the intended, typed `InvalidHostError` handling and user-facing behavior (redirect to login/App Bridge, embedded-app redirect, etc.) is bypassed in favor of an unstructured, unhandled error path — a change in behavior from the intended "revert cleanly" design of `sanitizeHost`.

### Likelihood Explanation
The trigger is trivial: an anonymous HTTP request to any embedded-app entrypoint (auth begin, callback redirect, admin authenticate loader) with a `host` query parameter of an invalid base64 length (e.g. `host=A`) is sufficient — no authentication, secrets, or session state is required. This mirrors the report's "challenger can supply a value that bypasses the depth/length check" pattern, but the concrete Shopify analog is a length check missing from the `base64regex`, which is meant to gate all subsequent parsing.

### Recommendation
Harden `sanitizeHost()`:
1. Enforce base64 length validity in the regex (length must be a non-zero multiple of 4 after accounting for padding), rejecting any string whose un-padded length mod 4 equals 1.
2. Wrap the `decodeHost()`/`new URL()` call inside `sanitizeHost()` in a try/catch, and treat any decoding failure the same as an invalid host (return `null` or throw `InvalidHostError` when `throwOnInvalid` is set), consistent with the function's documented contract.
3. Audit callers (`redirectToShopifyOrAppRoot`, `validateShopAndHostParams`, `redirectWithExitIframe`, `redirectToAuth`) to confirm none rely on `sanitizeHost()` never throwing unexpected exception types.

### Proof of Concept
1. Send `GET /?shop=test.myshopify.com&host=A` (or any base64-charset string whose length mod 4 is 1) to an embedded app route that calls `sanitizeHost` unprotected, e.g. the `authenticate.admin` loader (remix) or the `exitiframe`/auth-begin route (express).
2. `base64regex.test("A")` returns `true` (single alphanumeric char, no padding required by the regex).
3. `decodeHost("A")` → `atob("A")` throws `InvalidCharacterError` because a length-1 base64 string cannot decode to whole bytes.
4. The exception propagates out of `sanitizeHost()` uncaught by any of the calling middlewares/loaders listed above, producing either an unhandled promise rejection (Express) or an unstructured 500 (remix/react-router) instead of the intended `InvalidHostError`/login redirect flow.
