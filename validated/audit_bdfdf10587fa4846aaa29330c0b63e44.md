## Analog Found

### Title
Unbounded secondary-index (`SplTokenMint`/`SplTokenOwner`/`ProgramId`) growth enables disproportionate CPU cost per indexed scan - ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
The Bribe/Gauge finding shows that a permissionless function (`notifyRewardAmount`) can append attacker-controlled entries to an unbounded list (`rewards`) that a shared, critical function (`deliverBribes`) must fully and unconditionally iterate, so a single malicious/adversarial entry degrades service for everyone. Agave's accounts-index secondary indexes (`SplTokenMint`, `SplTokenOwner`, `ProgramId`) have the same shape: any unprivileged user can permissionlessly grow the reverse mapping for an arbitrary key without bound, and every subsequent index-based scan for that key must serially walk the entire (now attacker-inflated) list.

### Finding Description
`SecondaryIndex::insert` [1](#0-0)  adds an entry to `self.index[key]` (a `RwLockSecondaryIndexEntry` backed by an unbounded `HashSet<Pubkey>`) for every account whose owner/data matches an indexed token mint, token owner, or program id. There is no analog to Bribe's `MAX_REWARD_TOKENS` cap — any account creator can add unboundedly many pubkeys under one `SplTokenMint`/`SplTokenOwner`/`ProgramId` key simply by creating ordinary SPL token accounts (or program-owned accounts) referencing that key, which is a fully permissionless, cheap (rent-only) operation.

`AccountsIndex::get_index_key_pubkeys` [2](#0-1)  returns the *entire* list for a key with no size limit, and `AccountsDb::index_scan_accounts` then serially calls `self.do_load(...)` once per returned pubkey [3](#0-2) . Each `do_load` is a real accounts-index + storage/cache lookup (potentially disk I/O for the disk-backed index/append-vec), so the cost of a single indexed scan is O(n) in the number of pubkeys mapped to that key, entirely under attacker control and with no natural cap analogous to `MAX_REWARD_TOKENS`.

This scan path (`index_scan_accounts` / `get_filtered_indexed_accounts`) is reachable both from validator-internal bank calls, `Bank::get_filtered_indexed_accounts` [4](#0-3) , and from RPC methods that intentionally use the secondary index to avoid a full unfiltered `getProgramAccounts` scan, e.g. `get_filtered_spl_token_accounts_by_mint` [5](#0-4) , used by `get_token_accounts_by_delegate`/`get_token_largest_accounts`. Because the index itself was designed to make these operations cheaper than the excluded "unfiltered `getProgramAccounts`" case, the missing per-key cap effectively defeats that mitigation: a single legitimate call routed through the secondary index can be forced into the same O(n) serial-load cost the index was meant to avoid, once an attacker has inflated the target key's mapping.

### Impact Explanation
An unprivileged actor can, at near-zero marginal cost (creating standard SPL token accounts under one mint, or accounts owned by one program id), inflate a single secondary-index key's mapping to an arbitrarily large size. Any subsequent single call that resolves via that index key (validator-internal `get_filtered_indexed_accounts` or RPC methods built on `get_filtered_spl_token_accounts_by_mint`) then incurs O(n) serial `do_load` calls, producing disproportionate CPU/latency cost concentrated on a single request/thread, directly mirroring the reward-token DOS pattern where one attacker-controlled unbounded list is walked in full by a shared consumer.

### Likelihood Explanation
Reaching this requires only ordinary, permissionless account creation (e.g., SPL token account initialization under a chosen mint) — no special privileges, no crafted snapshot, and no more effort than paying rent for many small accounts, which is materially cheaper than the resulting per-scan cost multiplier. It is fully within the "unprivileged-user analog in AccountsDB storage and index" scope and does not depend on validator/peer role, mocking, or multi-client coordination.

### Recommendation
Bound the number of inner keys tracked per outer key in `SecondaryIndex` (analogous to `MAX_REWARD_TOKENS`), or cap/paginate `get_index_key_pubkeys`/`index_scan_accounts` iteration per call with an enforced maximum (not merely the optional, caller-supplied `byte_limit_for_scan`), so that a single index-based scan cannot be forced into unbounded serial work by an attacker-inflated key.

### Proof of Concept
1. Repeatedly submit ordinary `SPL Token` `InitializeAccount` transactions creating N token accounts all referencing the same mint `M` (permissionless, cost ~N × rent-exempt-minimum).
2. Each insertion calls `SecondaryIndex::insert` [1](#0-0) , growing `index[M]`'s inner-key set to size N with no cap.
3. Invoke any call path resolving through `IndexKey::SplTokenMint(M)`, e.g. `get_filtered_spl_token_accounts_by_mint` [6](#0-5)  or `Bank::get_filtered_indexed_accounts` [4](#0-3) .
4. `index_scan_accounts` iterates all N pubkeys from `get_index_key_pubkeys` and performs N serial `do_load` calls [3](#0-2) , producing CPU/latency cost proportional to the attacker-chosen N for a single caller request.

    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }
