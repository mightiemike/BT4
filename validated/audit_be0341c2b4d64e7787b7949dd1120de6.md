This confirms yield/resume: a `promise_yield_create` receipt records a data dependency in state and can be resumed by a **separate, later transaction** submitted by any signer with fresh gas [1](#0-0) . That decouples the depth of a receipt's completion chain from the gas of the originating transaction: a contract can chain many `yield → resume → yield → resume` cycles across transactions/blocks, each contributing new nodes to the receipt DAG rooted at one original transaction, without being capped by that transaction's `max_total_prepaid_gas`. The `AGENTS.md` doc confirms yield/resume literally works this way [2](#0-1) .

### Title
Unbounded native recursion in `get_recursive_transaction_results` allows stack-overflow crash of nodes answering `tx`/`EXPERIMENTAL_tx_status` for attacker-crafted deep receipt chains - (File: chain/chain/src/chain.rs)

### Summary
`Chain::get_final_transaction_result`, which backs the `tx` / `EXPERIMENTAL_tx_status` JSON-RPC methods, walks the entire receipt DAG spawned by a transaction using genuine (non-tail) Rust recursion with no depth bound, via `get_recursive_transaction_results` [3](#0-2) . A caller can query the status of *any* transaction hash, including ones they didn't submit. If a contract-controlled receipt chain for some transaction is made very deep — achievable via chained `yield_create`/`promise_yield_resume` cycles funded by successive independent transactions, which decouples chain depth from any single transaction's gas budget [1](#0-0) [2](#0-1)  — this recursive walk can exhaust the native call stack of the process answering the RPC query.

Notably, the codebase already recognizes this exact bug class: the newer `receipt_to_tx` RPC feature that performs an analogous recursive/iterative walk over a receipt ancestry chain was explicitly hardened with a `RECEIPT_TO_TX_MAX_DEPTH = 1000` bound, returning `DepthExceeded` instead of recursing unboundedly [4](#0-3) , with a dedicated regression test proving the bound is enforced [5](#0-4) . `get_recursive_transaction_results`, the older/parallel code path serving the primary transaction-status RPC, received no equivalent depth guard.

### Finding Description
`get_recursive_transaction_results` recurses once per receipt in the DAG rooted at the queried id, pushing an outcome and then recursively visiting every `receipt_id` referenced by that outcome, with no maximum-depth check [6](#0-5) . This is exactly analogous to the CVE's described flaw: a handler that can be invoked recursively based on externally influenced input, without a depth/stack guard, permitting a stack overflow.

The receipt chain depth for a *single* transaction's own gas is naturally capped (integration tests show `max_self_recursion_delay` capping self-recursive promise chains to roughly 56–221 hops before gas exhaustion) [7](#0-6) . However, `yield`/`resume` breaks this natural cap: a `promise_yield_create` receipt is stored in state and waits (up to `yield_timeout_length_in_blocks`, e.g. 200 blocks) for a `promise_yield_resume` call, which can come from a **separate transaction with its own independent gas budget** [1](#0-0) . By chaining many yield/resume cycles across many transactions/blocks, an attacker (or a normal but complex application, e.g. a long-running oracle-driven workflow) can grow the receipt DAG under one original transaction hash arbitrarily deep, well beyond what a single transaction's `max_total_prepaid_gas` could otherwise fund.

Any JSON-RPC caller (unprivileged, unauthenticated) can then request `tx`/`EXPERIMENTAL_tx_status` for that transaction hash, causing the serving node (RPC node or validator, since view calls are routed to `ViewClientActor`/`Chain`) to walk the full DAG with unbounded native recursion, risking a stack overflow and process crash — a transaction-triggered halt of the node servicing the query.

### Impact Explanation
A stack overflow in this code path crashes the node process handling the RPC/view request (denial of service). Because this is reachable by any RPC caller querying a transaction hash that anyone can learn (e.g., their own transaction, or one observed on-chain), and the deep-DAG precondition is achievable by an ordinary contract deployer without needing any privileged role, this can result in a transaction-triggered halt of nodes serving RPC/view traffic — matching the accepted impact category "a transaction-triggered halt."

### Likelihood Explanation
Constructing the deep yield/resume chain requires only ordinary account/contract-deployment capability and patience across many transactions/blocks (bounded by `yield_timeout_length_in_blocks` per hop, but that only bounds per-hop wait time, not total chain depth achievable over time). The `receipt_to_tx` feature's explicit `MAX_DEPTH` guard for a structurally similar recursive walk is direct evidence that the nearcore team is aware such receipt chains can grow large enough to be a concern, yet the older/primary `get_final_transaction_result` path was left unguarded.

### Recommendation
Add an explicit depth/node-count bound to `get_recursive_transaction_results` (mirroring `RECEIPT_TO_TX_MAX_DEPTH`), and/or convert it to an iterative (worklist/queue-based) traversal instead of native recursion so that stack usage is independent of DAG depth. Return a bounded error (e.g., `Started`/partial result or an explicit "too deep" error) instead of recursing unboundedly when the traversal exceeds the configured limit.

### Proof of Concept
Not directly executable from the indexed context (no test harness snippet demonstrating an actual crash was found), but the precondition is corroborated by:
1. `promise_yield_create`/`promise_yield_resume` semantics allowing resumption from an independent, later transaction [1](#0-0) .
2. Existing tests demonstrating multi-transaction, multi-block yield/resume chains [8](#0-7) .
3. The unbounded recursive walk itself [3](#0-2) .
4. The analogous feature's explicit depth cap, confirming the design concern exists elsewhere in the codebase but not here [4](#0-3) .

A full proof-of-concept would require driving a chain of hundreds/thousands of yield/resume cycles over many blocks and then issuing a `tx` status query against a node with a constrained stack — this would need to be validated end-to-end in a running environment (e.g., via a Devin session) to confirm actual crash thresholds, since exact stack-frame size per recursion level was not measurable from static review alone.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Returns FinalExecutionOutcomeView for the given transaction.
    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }
