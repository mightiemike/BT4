### Title
Unbounded `strings.Split` in `protojson` FieldMask unmarshaling allows CPU/memory exhaustion from a single JSON string - (File: encoding/protojson/well_known_types.go)

### Summary
`protojson.Unmarshal` decodes `google.protobuf.FieldMask` well-known-type fields by calling `strings.Split(str, ",")` on the attacker-controlled JSON string value with no bound on the number of resulting substrings, mirroring the "unbounded `explode()`" resource-exhaustion pattern described in the report.

### Finding Description
Any protobuf message containing a `google.protobuf.FieldMask` field (an extremely common pattern for `update_mask` fields in gRPC/REST APIs) is decoded via `unmarshalFieldMask`: [1](#0-0) 

The function reads the JSON string token, trims it, and unconditionally calls `strings.Split(str, ",")`, producing a slice with one element per comma found in the input. There is no cap on the number of parts, on the number of "paths" appended to the mask's `Paths` list, nor on the total input length beyond whatever the caller's own JSON size limit is. Each element then goes through `strs.JSONSnakeCase` and `protoreflect.FullName(s).IsValid()` and is appended to the message's repeated field via `list.Append`, so a huge number of tiny substrings all get materialized into Go strings, validated, and stored, before any error is surfaced.

This directly mirrors the report's bug class: an untrusted string is split on a delimiter with no `limit` parameter, letting the caller control the size of the resulting collection. Unlike some `protojson` list-decoding paths that grow a `protoreflect.List` incrementally (which still has this same problem, just via `List.Append` in a loop rather than a bulk `strings.Split`), this code performs one large allocation via `strings.Split` up front, then iterates the entire slice, so both memory and CPU scale with the number of commas in the input string, not with any legitimate/schema-bound field count.

### Impact Explanation
An attacker who can submit a modest-sized JSON payload (e.g., a few MB, well within typical default gRPC/HTTP message size limits) that contains a single string field with millions of commas (e.g., `"paths": ",,,,,,,,,,...,"`) causes the server to allocate a slice with millions of string elements, run per-element validation (`JSONSnakeCase`, `FullName.IsValid`), and grow a repeated field to millions of entries — all before the request is otherwise rejected. This wastes CPU and memory disproportionately to the request size, which is a classic CWE-770 uncontrolled resource consumption issue on an unprivileged/unauthenticated request path (any service accepting `FieldMask` from a client, e.g., an `UpdateFooRequest.update_mask`).

### Likelihood Explanation
Likelihood is high for any service that: (1) exposes an RPC/API accepting a message with a `google.protobuf.FieldMask` field, and (2) parses request bodies with `protojson.Unmarshal` (the default JSON codec for gRPC-Gateway/Connect and many REST-over-protobuf services). No authentication bypass, custom resolver, or attacker-controlled schema is required — this is a stock well-known-type decode path reachable with a trusted, generated schema and a plain string value.

### Recommendation
Bound the number of paths produced when decoding a `FieldMask` from JSON, e.g., by counting commas / capping the number of `strings.Split` results (or switching to an incremental split with an explicit maximum count) and returning a decode error once a reasonable limit (e.g., matching the schema's expected field count or a fixed sane maximum) is exceeded, consistent with how the referenced PocketMine-MP fix mandated explicit limits on all `explode()`-equivalent calls that process untrusted input.

### Proof of Concept
```go
package main

import (
	"fmt"
	"strings"

	"google.golang.org/protobuf/encoding/protojson"
	"google.golang.org/protobuf/types/known/fieldmaskpb"
)

func main() {
	// Simulate an attacker-controlled request body containing a FieldMask
	// with an enormous number of comma-separated (empty) paths.
	n := 5_000_000 // ~5M commas, only a few MB of JSON
	huge := strings.Repeat(",", n)
	payload := fmt.Sprintf(`{"paths":%q}`, "a"+huge+"a") // wrap to keep first/last non-empty if needed

	fm := &fieldmaskpb.FieldMask{}
	err := protojson.Unmarshal([]byte(payload), fm)
	// Regardless of whether validation ultimately errors on some path,
	// strings.Split(str, ",") already allocated a ~5M-element slice and
	// iterated it before returning, wasting CPU/memory per request.
	fmt.Println(err)
}
```
Sending repeated requests like this (or a slightly larger comma count within typical gRPC message-size limits) lets a single unauthenticated/unprivileged client force expensive, disproportionate allocation and iteration work inside `unmarshalFieldMask` for every request.

func (d decoder) unmarshalFieldMask(m protoreflect.Message) error {
	tok, err := d.Read()
	if err != nil {
		return err
	}
	if tok.Kind() != json.String {
		return d.unexpectedTokenError(tok)
	}
	str := strings.TrimSpace(tok.ParsedString())
	if str == "" {
		return nil
	}
	paths := strings.Split(str, ",")

	fd := m.Descriptor().Fields().ByNumber(genid.FieldMask_Paths_field_number)
	list := m.Mutable(fd).List()

	for _, s0 := range paths {
		s := strs.JSONSnakeCase(s0)
		if strings.Contains(s0, "_") || !protoreflect.FullName(s).IsValid() {
			return d.newError(tok.Pos(), "%v contains invalid path: %q", genid.FieldMask_Paths_field_fullname, s0)
		}
		list.Append(protoreflect.ValueOfString(s))
	}
	return nil
