## Analysis

The Astaria bug is: a post-hoc "reconciliation" subtraction over aggregated values relies on an implicit invariant (minuend ≥ subtrahend) that isn't guaranteed once many participants act, and the subtraction is unchecked, so it underflows and permanently breaks the commit path.

I looked for an Aptos-native analog in write-set/state-commit code that performs a similar "reconcile aggregated shard results back into a single committed value" subtraction. The closest and most concrete match is the sharded-execution total-supply reconciliation.

### Title
Unchecked `u128` subtraction in sharded-executor total-supply reconciliation can corrupt the committed `0x1::coin` total-supply write set - (File: `aptos-move/aptos-vm/src/sharded_block_executor/sharded_aggregator_service.rs`)

### Summary
Aptos' remote/local sharded block executor runs each shard against an `AggregatorOverriddenStateView` that substitutes the real total-supply value with a fixed constant `TOTAL_SUPPLY_AGGR_BASE_VAL = u128::MAX >> 1` [1](#0-0) , so each shard can independently execute total-supply mutations without cross-shard coordination. After all shards finish, `aggregate_and_update_total_supply` reconstructs the true total supply by computing signed deltas relative to that constant and relative to the real base value read from the state view, then patches each transaction's write set with `txn_output.update_total_supply(...)` [2](#0-1) .

### Finding Description
The reconciliation math is implemented with a hand-rolled signed-magnitude type, `DeltaU128`, whose core operation performs raw, unchecked `u128` arithmetic instead of the `checked_sub`/`BoundedMath::unsigned_subtract`/`try_sub` patterns used everywhere else in the aggregator stack (compare `aptos-move/aptos-aggregator/src/bounded_math.rs` lines 58-64 and the natives in `aggregator_natives/aggregator_v2.rs` lines 217-262, both of which return errors on underflow): [3](#0-2) 

`add_delta` computes `other - self.delta` with no bounds check when the accumulated delta is negative. The code comment itself acknowledges the intermediate arithmetic can go negative ("While `txn_total_supply` is u128, the intermediate computation can be negative...") [4](#0-3) , i.e. the author knew this invariant is fragile, yet the final application step that writes the patched value back into the committed `TransactionOutput` write set has no error path or invariant check — unlike the Move-level aggregator subtract natives, which explicitly abort/return `false` on underflow.

This mirrors the Astaria pattern exactly: a value that is supposed to reconcile per-shard/per-round partial results into one committed number, computed via an unchecked subtraction, with a comment admitting the intermediate value "can be negative" but no guard on the final result before it is written into durable, authenticated transaction output.

### Impact Explanation
`update_total_supply` directly patches the write set of the `0x1::coin::CoinInfo`/aggregator resource that is committed to the ledger for every sharded block [5](#0-4) . If `delta_for_round.add_delta(txn_total_supply)` underflows:
- In a debug/overflow-checked build, this panics, aborting sharded block execution/commit — a liveness break of the state-commit path, directly analogous to `processEpoch()` reverting and stalling all future epochs.
- In a standard release build (overflow checks disabled by default), the subtraction silently wraps to a huge, incorrect `u128`, which is then written as the authoritative total-supply value into the transaction's committed write set — a piece of committed state that diverges from the correct VM result, a Ledger-integrity violation per the State-Integrity Gate.

### Likelihood Explanation
The invariant that `delta_for_round.add_delta(txn_total_supply)` never underflows depends on strict consistency between: (1) the "last transaction with a total-supply write, scanned in reverse per shard/round" heuristic [6](#0-5) , (2) every shard/round pairing being populated in lockstep, and (3) no shard/round silently defaulting to a zero delta when it in fact should carry forward a previous nonzero delta. This is a nontrivial, code-review-only-verifiable invariant across a distributed/sharded execution path, and I was not able to fully trace all call sites (e.g. the remote-sharded variant) within the available tool budget to prove or disprove that the invariant always holds; I flag this as unresolved. Given that this path only activates when sharded/remote block execution is enabled (not the default single-shard VM path), and I could not confirm current mainnet usage of this execution mode, likelihood is uncertain and should be validated with a live/functional-test build.

### Recommendation
Replace the raw arithmetic in `DeltaU128::add_delta`/`Add` with `checked_add`/`checked_sub` (or `BoundedMath`) and propagate an error/invariant-violation up through `aggregate_and_update_total_supply` instead of allowing a silent wraparound or an uncontrolled panic during commit. Add an explicit assertion that reconciled total supply is non-negative before calling `update_total_supply`, and add a targeted test that exercises unequal shard/round total-supply-write distributions.

### Proof of Concept
Concrete reproduction requires constructing a sharded block where at least one shard/round has zero total-supply-touching transactions while sibling shards accumulate large deltas, verifying whether the `aggr_total_supply_delta` carry-forward and `base_val_delta` computation produce a case where `other < self.delta` in `add_delta`. I was unable to complete this simulation within the current investigation; this should be validated with a dedicated Devin/test session that runs `sharded_aggregator_service` under fuzzed shard/round transaction distributions with overflow-checks enabled to confirm a real underflow trigger before treating this as fully proven.

impl DeltaU128 {
    pub fn get_delta(minuend: u128, subtrahend: u128) -> Self {
        if minuend >= subtrahend {
            Self {
                delta: minuend - subtrahend,
                is_positive: true,
            }
        } else {
            Self {
                delta: subtrahend - minuend,
                is_positive: false,
            }
        }
    }

    fn add_delta(self, other: u128) -> u128 {
        if self.is_positive {
            self.delta + other
        } else {
            other - self.delta
        }
    }
}
