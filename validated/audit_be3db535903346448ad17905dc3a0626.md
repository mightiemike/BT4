### Title
`citrea_network_to_chain_id` collision lets a `Network::Nightly`-signed `BatchProofMethodId` upgrade replay unmodified on `Network::TestNetworkWithForks` - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same numeric chain id (`5665`). Since `run_l1_block` only checks `citrea_network_to_chain_id(network) == batch_proof_method_id.body.chain_id`, a `BatchProofMethodId` blob signed by the security council for one of these two networks is byte-for-byte valid on the other.

### Finding Description
The binding the code relies on is: `citrea_network_to_chain_id(network_A) == citrea_network_to_chain_id(network_B)` must be `false` for all `network_A != network_B`, so that a signed method-id body cannot cross networks.

In `crates/light-client-prover/src/circuit/mod.rs`: [1](#0-0) 
`Network::Nightly` and `Network::TestNetworkWithForks` both map to `5665`. This breaks the binding: it is false that all distinct networks get distinct chain ids.

The check that is supposed to prevent cross-network replay is in `run_l1_block`'s `DataOnDa::BatchProofMethodId` branch: [2](#0-1) 
This only compares the numeric chain id derived from the runtime `network` argument against `batch_proof_method_id.body.chain_id`. It never checks which specific `Network` variant produced that chain id. `verify_method_id_security_council` (in `method_id_verifier.rs`) verifies the council signatures over `body.serialize()`, which only encodes `method_id`, `activation_l2_height`, and `chain_id` — not the `Network` enum variant itself. Therefore, a `BatchProofMethodId` inscription with `body.chain_id = 5665`, signed by 3-of-5 council members for a `Nightly` deployment, is a fully valid, identically-signed blob for any light client prover run with `network = Network::TestNetworkWithForks` (and vice versa), because `citrea_network_to_chain_id` produces `5665` for both.

Exploit flow: an attacker observes/obtains a legitimately published, correctly-signed `BatchProofMethodId` DataOnDa blob issued for the Nightly network (e.g., from a public Nightly method-id upgrade), then inscribes the identical bytes into the Bitcoin DA chain that a `TestNetworkWithForks` light client prover is monitoring. Since the light client prover only checks the numeric chain id (5665 == 5665) and the signatures verify (same message bytes, same council pubkeys array assumed shared/reused for these test networks), the method id is accepted and installed via `BatchProofMethodIdAccessor::insert`, changing which batch-proof verification key the `TestNetworkWithForks` light client circuit trusts going forward.

### Impact Explanation
If the security council key set is shared (or the attacker manages to get the same `initial_da_pubkeys` used on both `Nightly` and `TestNetworkWithForks`), this allows an unauthorized method-id upgrade to be accepted on one network using signatures obtained for the other, corrupting the accepted verification key set for future batch proofs on that network. This is a method-id upgrade accepted that was never independently authorised for that specific network, matching the Critical impact category. However, both `Nightly` and `TestNetworkWithForks` appear to be non-production/test network variants (based on naming and usage in test files like `bin/citrea/tests/bitcoin/fork.rs`), not `Mainnet` or `Testnet`. I could not fully verify within the available tool budget whether `TestNetworkWithForks` is ever deployed with the same DA public keys as `Nightly` in any real (non-test/non-mock) configuration — the file `crates/primitives/src/forks.rs` and `bin/citrea/src/rollup/bitcoin.rs` reference `TestNetworkWithForks` but I was unable to confirm whether it's reachable in production deployment paths versus being confined to integration-test harnesses (which are out of scope per the rules).

### Likelihood Explanation
No mainnet/testnet collision exists — the only collision found is `Nightly` (5665) vs `TestNetworkWithForks` (5665), both of which are non-mainnet/non-primary networks. Given the audit scope explicitly excludes test/mock configurations and requires demonstration without mainnet, and `TestNetworkWithForks` by its name and typical usage appears tied to fork-testing scenarios, the practical blast radius is likely confined to test/dev environments rather than a genuine production network split. This weakens confidence that this is exploitable against a real, separately-keyed production deployment.

### Recommendation
Include the actual `Network` discriminant (not just the derived numeric chain id) in `BatchProofMethodIdBody`, or ensure `citrea_network_to_chain_id` produces pairwise-distinct values for every `Network` variant (e.g., assign `TestNetworkWithForks` its own unique id instead of reusing `5665`).

### Proof of Concept
```rust
// crates/light-client-prover/src/circuit/initial_values.rs (or method_id_verifier.rs tests)
#[test]
fn test_chain_ids_are_pairwise_distinct() {
    use sov_rollup_interface::Network;
    use crate::circuit::citrea_network_to_chain_id;

    let networks = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];

    for i in 0..networks.len() {
        for j in (i + 1)..networks.len() {
            let id_a = citrea_network_to_chain_id(networks[i]);
            let id_b = citrea_network_to_chain_id(networks[j]);
            assert_ne!(
                id_a, id_b,
                "chain id collision between {:?} and {:?}: both map to {}",
                networks[i], networks[j], id_a
            );
        }
    }
}
```
