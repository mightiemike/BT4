## Finding

### Title
Missing `accept_new_txs` (pause) check on the P2P transaction ingestion path allows bypassing the "pause new transactions" control - ([File: crates/apollo_gateway/src/gateway.rs])

### Summary
The sequencer exposes a "pause new transaction admission" control, `accept_new_txs`, that operators use to stop the node from accepting new transactions (e.g. during an incident, upgrade, or emergency mitigation). This control is enforced only in the HTTP server layer, via `check_new_transactions_are_allowed`, and is never checked inside the `Gateway` component itself. Transactions arriving through the Mempool P2P gossip path are forwarded directly to `Gateway::add_tx`/`add_tx_inner`, which contains no `accept_new_txs` (or equivalent) check, so a node that has "paused" transaction intake via `accept_new_txs = false` will still admit and forward transactions that arrive via P2P propagation.

### Finding Description
`check_new_transactions_are_allowed` is only invoked from the two HTTP handlers: [1](#0-0) 

and it gates access solely to `add_rpc_tx`/`add_tx` in the HTTP server crate: [2](#0-1) 

However, the actual admission logic that matters — pushing a transaction into the mempool — lives in `Gateway::add_tx_inner`, which performs stateless/stateful validation and calls `mempool_client.add_tx`, but has no notion of `accept_new_txs` at all: [3](#0-2) [4](#0-3) 

Transactions received over the mempool P2P gossip topic are delivered straight to this same `Gateway::add_tx` via the P2P runner, completely independent of the HTTP server and its `accept_new_txs` gate: [5](#0-4) 

The `HttpServerDynamicConfig.accept_new_txs` flag is declared and defaulted to `true`, and is the only mechanism referenced in the codebase to stop admitting transactions: [6](#0-5) 

This is structurally identical to the reported bug class: a "pause" gate (`whenNotPaused` in the report, `accept_new_txs`/`check_new_transactions_are_allowed` here) exists and is applied to one entry point (`createBid`/`createBidWithReferral` in the report; `add_rpc_tx`/`add_tx` HTTP handlers here) but is missing on the underlying/alternate code path that performs the same sensitive action (the auction's `_createBid`; here, `Gateway::add_tx_inner`, callable through the P2P runner without ever going through the HTTP layer).

### Impact Explanation
An operator who sets `accept_new_txs = false` — the node's only documented mechanism to stop accepting new transactions, presumably used during incident response, protocol upgrades, or to halt processing of a known-bad transaction class — has no actual guarantee that new transactions stop being admitted into their node's mempool and considered for block building. Transactions gossiped from other peers in the network will still flow into `Gateway::add_tx_inner` and be pushed into the local mempool, undermining the intended safety control. Since the mempool can supply these txs to the batcher for proposal, this allows continued transaction processing/inclusion during a period the operator explicitly intended to halt it, which is a meaningful confirmation/availability-control gap for the node.

### Likelihood Explanation
Likelihood is high: no privileged access or malicious behavior is required. Normal transaction gossip (any regular user transaction submitted to any peer in the network) will reach the affected node's `Gateway::add_tx` through the standard, expected P2P propagation flow shown in the transaction submission flow diagram, since the P2P ingestion path never consults `accept_new_txs`.

### Recommendation
Move (or duplicate) the `accept_new_txs` check into `Gateway::add_tx`/`add_tx_inner` (or into the shared component request handler in `crates/apollo_gateway/src/communication.rs`) so that it is enforced uniformly for both HTTP-submitted and P2P-received transactions, mirroring how `check_declare_permissions` is already correctly applied inside `add_tx_inner` for every ingestion path.

### Proof of Concept
1. Operator sets `http_server_config.dynamic_config.accept_new_txs = false` on Node A to pause new transaction intake; `is_ready` correctly reports `SERVICE_UNAVAILABLE`, and direct HTTP submissions to Node A are rejected by `check_new_transactions_are_allowed`.
2. A user submits a normal transaction to Node B (not paused).
3. Node B's mempool propagates the transaction over the `apollo_mempool_transaction_propagation` gossip topic.
4. Node A's `MempoolP2pRunner` receives the gossiped batch and calls `gateway_client.add_tx(GatewayInput { rpc_tx, message_metadata })` directly (`crates/apollo_mempool_p2p/src/runner/mod.rs:120-127`).
5. `Gateway::add_tx_inner` processes and validates the transaction and forwards it to Node A's mempool via `mempool_client.add_tx`, despite `accept_new_txs = false` — the pause control is silently bypassed.
