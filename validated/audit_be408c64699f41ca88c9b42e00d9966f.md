## Title
Wallet Contract pays the relayer's fee unconditionally, before the emulated transfer it is meant to compensate is confirmed to succeed - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In `inner_rlp_execute`, the NEAR Wallet Contract (an eth-implicit account's global contract used for meta-transactions) fires an independent `Transfer` promise that pays the relayer's fee as soon as the RLP transaction is *parsed* as an `EOABaseTokenTransfer`/`ERC20Transfer`, without waiting to see whether the actual emulated transfer promise it is compensating for succeeds. This is the same bug class as the GMX `claimForAccount()` report: a side-effect (crediting a party with value/state) is applied speculatively, based on an assumption that the follow-on action will succeed, instead of being conditioned on its actual outcome.

### Finding Description
`inner_rlp_execute` computes `tx_fee` from the relayer-supplied Ethereum transaction and, for `EOABaseTokenTransfer`/`ERC20Transfer` kinds with a non-zero fee, immediately schedules a transfer of that fee to the predecessor (the relayer): [1](#0-0) 

This `refund_promise` is created via `env::promise_batch_create`/`env::promise_batch_action_transfer` as a **separate, unchained** promise - it is not `.then()`-attached to the actual action promise (`action_to_promise(target, action)?.then(ext.rlp_execute_callback(...))`, built later in the same function): [2](#0-1) 

Both promises originate from the same predecessor account (the wallet) and draw from the same NEAR balance. Success/failure of the main transfer is only observed later in `rlp_execute_callback`, which triggers a refund path for an *external caller's attached deposit*, but has no mechanism to claw back the relayer fee that was already sent: [3](#0-2) 

Because the fee-payment receipt and the value-transfer receipt are independent outgoing receipts from the same account, whichever is applied first can drain enough of the account's balance that the second one fails for insufficient funds - yet the fee has already been irreversibly paid to the relayer with no corresponding value delivered to the intended recipient. This directly mirrors the GMX report's root cause: adding/crediting state (WETH in the asset list / a fee payment) based on the assumption that an action will complete successfully, rather than gating the side effect on confirmed successful execution, and executing it in the wrong order relative to the action itself.

### Impact Explanation
This allows unauthorized value movement out of a user's eth-implicit wallet account: the relayer fee is paid even when the corresponding base-token/ERC-20 transfer the fee was supposed to compensate ultimately fails (e.g., due to insufficient remaining balance after the fee is deducted, or any other failure of the decoupled transfer promise). The user's funds leave the account with no service rendered and no refund path, since `rlp_execute_callback`'s refund logic only covers the *external caller's* attached deposit, not the wallet's own balance spent on the relayer fee.

### Likelihood Explanation
Reachable by any relayer (an unprivileged meta-transaction sender) submitting an RLP-encoded Ethereum-style transaction to `rlp_execute` with a nonzero `gas_price`/`gas_limit`-derived fee for a base-token or ERC-20 transfer whose value exceeds the wallet's remaining balance after the fee is paid, or which otherwise fails independently of the fee promise's success. No special privileges, network position, or validator collusion is required - only a standard NEAR transaction invoking the deployed Wallet Contract.

### Recommendation
Chain the fee-refund promise after (or make it conditional on) confirmed success of the main transfer promise, e.g. by moving the `promise_batch_create`/`promise_batch_action_transfer` for the relayer fee into `rlp_execute_callback` (or a dedicated callback) gated on `PromiseResult::Successful`, analogous to the GMX fix of reordering `_updateTokensIn()` to occur only after the underlying action is confirmed to have succeeded.

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account and fund it with just enough NEAR to cover either the transfer amount or the relayer fee, but not both.
2. A relayer submits an RLP-encoded `EOABaseTokenTransfer` (or `ERC20Transfer`) with a nonzero `gas_price * gas_limit` fee and a `value` such that `wallet_balance - fee < value`.
3. `inner_rlp_execute` unconditionally schedules the `refund_promise` transfer of `fee` to the relayer (lines 381-384) before/independently of scheduling the main transfer promise (lines 412-471).
4. The fee-payment receipt executes and succeeds (relayer is paid). The main transfer receipt subsequently fails due to insufficient remaining balance.
5. Result: the relayer has extracted `fee` from the wallet with no corresponding transfer delivered to the intended recipient, and no refund mechanism recovers the fee for the wallet owner.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
