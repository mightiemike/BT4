### Title
Front-Runnable Signature-less DoS via Deploy-Account "Skip Validation" UX Feature - (File: crates/apollo_gateway/src/stateful_transaction_validator.rs)

### Summary
The gateway's `skip_stateful_validations` feature, intended to improve UX for `deploy_account` + `invoke` bundles, allows any unprivileged sender to submit a garbage/unsigned `invoke` transaction at nonce 1 for **any** undeployed account address that has a pending `deploy_account` transaction visible in the public mempool. Because `__validate__` is skipped entirely for this case, the attacker's transaction requires no valid signature to be admitted into the mempool, letting it occupy the victim's `(address, nonce=1)` slot ahead of the legitimate transaction — directly analogous to the reported Router.sol permit-front-running DoS, where an attacker observes public signed parameters and consumes state before the legitimate transaction lands.

### Finding Description
`skip_stateful_validations` in [1](#0-0)  returns `true` (i.e., skip `__validate__`) whenever an incoming `Invoke` transaction has `nonce == 1` and the sender account's on-chain nonce is `0`, provided `account_tx_in_pool_or_recent_block` returns true for that address (i.e., a `deploy_account` tx, or any tx, already exists for that address in the mempool).

This result feeds into `run_validate_entry_point`, which sets `execution_flags.validate = !skip_validate` [2](#0-1) . When `validate` is `false`, the CPU-heavy `__validate__` entry point (the account's own signature check) is never invoked before the transaction is admitted to the mempool.

Since `deploy_account` transactions (and their calldata, including the target account address) are visible in the public mempool/gateway before inclusion, any attacker can:
1. Observe a pending `deploy_account` tx for victim address `A`.
2. Submit their own `invoke` tx with `sender_address = A`, `nonce = 1`, and arbitrary/garbage calldata and signature.
3. Because `A`'s nonce is 0 and a tx for `A` already exists in the mempool, `skip_stateful_validations` returns `true`, and the gateway admits the attacker's tx into the mempool **without checking any signature**.
4. This occupies `(A, nonce=1)` in the mempool's `tx_pool`/`tx_queue` (`crates/apollo_mempool/src/mempool.rs`, `validate_fee_escalation` / `DuplicateNonce` logic, [3](#0-2) ), causing the legitimate user's real nonce-1 invoke to be rejected with `DuplicateNonce` (or forced into a fee-escalation bidding war it did not anticipate).

Eventually, when the attacker's garbage tx is picked up for actual block building, full execution flags apply (`ExecutionFlags::validate = true` in the ordinary execution path, confirmed via `AccountTransaction::execute_raw` and `perform_pre_validation_stage`/`run_validate` in the OS/blockifier — [4](#0-3) ), so its bogus `__validate__` will fail and it will be dropped/rejected from the block. But by then the legitimate transaction has already been denied admission for a window, and the attacker can repeat the attack indefinitely (cheaply, since no signing key or fee escalation is strictly required to block a same-fee duplicate-nonce submission) as long as a `deploy_account` tx for the target keeps appearing in the mempool.

This mirrors the report's root cause exactly: a state-consuming operation is gated on a **publicly observable** precondition (there, a `permit` signature; here, "a tx already exists in the mempool for this address") rather than on proof of authorization from the actual sender, letting any unprivileged party race and consume the slot ahead of the legitimate transaction.

### Impact Explanation
This is a mempool-admission-level denial-of-service against the `deploy_account` + `invoke` bundle UX flow: any unprivileged network participant can indefinitely block a targeted account's first post-deployment transaction from being included, without spending any real fee-escalation cost (a same-nonce duplicate is enough to force a `DuplicateNonce` rejection when fee escalation isn't strictly increasing, or otherwise it forces the victim to overpay in fee-escalation rounds). No state corruption or wrong-root risk exists (execution-time validation still catches the garbage signature), so the impact is confined to griefing/DoS on affected accounts' UX flow rather than fund loss or consensus divergence.

### Likelihood Explanation
Likelihood is high for any observer of the public mempool: the precondition (`account_tx_in_pool_or_recent_block`) is trivially satisfiable by watching for `deploy_account` transactions, and the attack requires no valid signature, private key, or special access — only submitting a standard `invoke` transaction through the gateway.

### Recommendation
Do not gate `__validate__` skipping purely on the existence of *any* transaction for the address in the mempool. Instead, require that the specific `deploy_account` transaction for that address has actually been observed and is itself validly signed and pending (already partially implied by the comment but not enforced against a specific tx), or tie the skip decision to a nonce-consistent chain of transactions that have each independently passed a lightweight validity check (e.g., verify the deploy_account signature itself before trusting the "already deployed intent" and admitting a nonce-1 tx without validation). Alternatively, require fee-escalation percentage > 0 strictly enforced for same-nonce competing submissions in this skip-validation window, and/or bound the number of unvalidated nonce-1 admissions per address to mitigate repeated griefing.

### Proof of Concept
1. Attacker monitors the public mempool/gateway for a `deploy_account` transaction targeting address `A` (nonce 0).
2. Attacker crafts an `Invoke` transaction with `sender_address = A`, `nonce = 1`, arbitrary calldata, and an invalid/empty signature, and submits it to the gateway.
3. In `skip_stateful_validations` ( [5](#0-4) ), `tx.nonce() == 1 && account_nonce == 0` is true, and `mempool_client.account_tx_in_pool_or_recent_block(A)` returns `true` (because the deploy_account tx for `A` is in the mempool), so `skip_validate = true`.
4. `run_validate_entry_point` sets `execution_flags.validate = false`, so the attacker's unsigned/garbage tx passes gateway admission and enters the mempool at `(A, nonce=1)`.
5. When the legitimate user's real nonce-1 invoke for `A` arrives, `validate_fee_escalation` in the mempool rejects it as `MempoolError::DuplicateNonce` (per [6](#0-5) ), denying the legitimate transaction.

    /// `(address, nonce)` via fee escalation, without mutating any state. Returns the existing
    /// transaction to be replaced when a valid replacement exists, `None` when there is nothing to
    /// replace, or an error when a replacement is present but not permitted.
    fn validate_fee_escalation(
        &self,
        incoming_tx_reference: TransactionReference,
    ) -> MempoolResult<Option<TransactionReference>> {
        let TransactionReference { address, nonce, .. } = incoming_tx_reference;

        self.validate_no_delayed_declare_front_run(incoming_tx_reference)?;

        if !self.config.static_config.enable_fee_escalation {
            if self.tx_pool.get_by_address_and_nonce(address, nonce).is_some() {
                return Err(MempoolError::DuplicateNonce { address, nonce });
            };

            return Ok(None);
        }

        let Some(existing_tx_reference) = self.tx_pool.get_by_address_and_nonce(address, nonce)
        else {
            // Replacement irrelevant: no existing transaction with the same nonce for address.
            return Ok(None);
        };

        if !self.should_replace_tx(&existing_tx_reference, &incoming_tx_reference) {
            info!(
                "{existing_tx_reference} was not replaced by {incoming_tx_reference} due to \
                 insufficient fee escalation."
            );
            // TODO(Elin): consider adding a more specific error type / message.
            return Err(MempoolError::DuplicateNonce { address, nonce });
        }

        Ok(Some(existing_tx_reference))
    }
