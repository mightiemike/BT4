Confirmed finding: `MsgVoteOutbound.ValidateBasic()` in `x/uexecutor/types/msg_vote_outbound.go` only checks that `obs.GasFeeUsed` is a non-empty string; it never validates that the string parses to a non-negative integer. That value flows into `applyGasRefund` in `x/uexecutor/keeper/outbound.go`, where `gasFeeUsed := new(big.Int); gasFeeUsed.SetString(obs.GasFeeUsed, 10)` will happily accept a negative decimal string (e.g. `"-1000000"`), and the only guard is `if gasFee.Cmp(gasFeeUsed) <= 0 { return }` [1](#0-0) . Because `gasFee` (always positive) is compared against a negative `gasFeeUsed`, the comparison passes and `refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)` computes `gasFee + |gasFeeUsed|` — an inflated, attacker-influenced refund amount that is then minted/swapped to the recipient via `CallUniversalCoreRefundUnusedGas` [2](#0-1) . This is the direct structural analog of the Lido `newStake` issue: a value that can be negative is fed into subtraction/refund-amount logic that assumes non-negative inputs, with the guard checking the wrong condition (`Cmp <= 0`) instead of validating sign.

However, I could not fully verify exploitability under the required unprivileged-attacker threat model. `obs.GasFeeUsed` is only set through `MsgVoteOutbound`, which per the ValidateBasic path requires a valid bech32 `Signer` [3](#0-2) , and the keeper's `VoteOutbound` treats the caller as a `universalValidator sdk.ValAddress` and requires ballot quorum via `VoteOnOutboundBallot` before `FinalizeOutbound`/`applyGasRefund` ever run [4](#0-3) . I was not able to confirm from the code inspected whether there is any ante-level or authorization check that restricts `MsgVoteOutbound` submission strictly to registered Universal Validators, or whether an unprivileged account could submit this message directly and have it accepted into a ballot (potentially requiring quorum from other, honest validators who each independently observe the real destination-chain gas usage). If submission is gated to bonded/registered UVs (as the field name and design intent strongly imply), then triggering a negative `GasFeeUsed` requires either a malicious validator or a bug in how honest validators derive this string from real chain data — both of which fall outside the "unprivileged external attacker" and "honest validators" scope constraints given.

Given this uncertainty, I can present this as a candidate structural analog but not confirm a fully unprivileged, honest-validator-reachable trigger:

### Title
Unvalidated negative `gas_fee_used` string causes gas-refund overflow/inflation - (File: x/uexecutor/keeper/outbound.go)

### Summary
`applyGasRefund` computes `refundAmount = gasFee - gasFeeUsed` where `gasFeeUsed` is a user/validator-supplied decimal string parsed via `big.Int.SetString` with no sign validation, either in `MsgVoteOutbound.ValidateBasic()` or in `applyGasRefund` itself.

### Finding Description
`MsgVoteOutbound.ValidateBasic()` requires `obs.GasFeeUsed` to be a non-empty string but does not parse it or reject negative values [5](#0-4) . In `applyGasRefund`, the string is parsed with `big.Int.SetString(obs.GasFeeUsed, 10)`, which accepts negative numbers, and the only sanity check is `gasFee.Cmp(gasFeeUsed) <= 0` (a "no excess" check), not a sign check on `gasFeeUsed` [1](#0-0) . If `gasFeeUsed` is negative, `refundAmount = gasFee - gasFeeUsed` becomes larger than `gasFee`, and this inflated amount is passed to `CallUniversalCoreRefundUnusedGas`, which mints/swaps PRC20/native value to the refund recipient [6](#0-5) .

### Impact Explanation
If reachable, this would allow minting of PC/PRC20 value far in excess of the legitimate gas-fee delta, directly corrupting gas-fee-refund accounting and potentially draining protocol-controlled swap liquidity or over-minting native tokens to a chosen recipient (`refundRecipient`, attacker-controllable via `RevertInstructions.FundRecipient` or `outbound.Sender`).

### Likelihood Explanation
Low-to-uncertain: reaching this path requires `MsgVoteOutbound` ballot finalization, which in the observed keeper code is modeled as validator voting with quorum (`VoteOnOutboundBallot`). I could not confirm in the available code whether message submission is restricted to registered Universal Validators at the ante/msg-server layer, nor whether quorum-based convergence could occur on a maliciously-crafted negative string without validator collusion. This is a candidate finding pending that verification, not a confirmed unprivileged-attacker-reachable bug.

### Recommendation
In `MsgVoteOutbound.ValidateBasic()` (and/or as defense-in-depth in `applyGasRefund`), parse `obs.GasFeeUsed` as a `big.Int` and explicitly reject if `Sign() < 0`, mirroring the non-negative validation already done for `Inbound.Amount` in `ValidateForExecution` [7](#0-6) .

### Proof of Concept
1. Submit (or have a validator submit) `MsgVoteOutbound` with `ObservedTx.GasFeeUsed = "-1000000000000000000"` and a valid `GasFee` on the outbound (e.g. `"111"`).
2. `ValidateBasic` passes (non-empty string check only).
3. On ballot finalization, `applyGasRefund` computes `gasFee.Cmp(gasFeeUsed) <= 0` → false (111 > -1e18) → proceeds.
4. `refundAmount = 111 - (-1e18) = 1e18 + 111`, an attacker-inflated refund minted to `refundRecipient`.
