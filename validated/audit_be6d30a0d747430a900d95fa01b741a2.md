### Title
Relayer fee is paid out unconditionally before the emulated transfer's success is known - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract's ERC-20/base-token emulation pays the relayer's `fee` refund via an independent, unconditional promise created immediately at parse time, without checking whether the corresponding user transfer (base token transfer or NEP-141 `ft_transfer`) actually succeeds. This mirrors the "unsafe ERC20" bug class in the referenced report: an operation's outcome (success/failure of a value transfer) is not checked before dependent state changes/fund movements are made final.

### Finding Description
In `inner_rlp_execute`, after parsing the Ethereum transaction into a `TransactionKind`, the code unconditionally creates a top-level, independent promise to pay the relayer's fee for `EOABaseTokenTransfer` and `ERC20Transfer` kinds: [1](#0-0) 

This fee-refund promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) is a separate, sibling promise batch, not chained (`.then(...)`) to the promise that actually performs the requested transfer or the NEP-141 `ft_transfer`/`storage_deposit` flow built later in the same function: [2](#0-1) 

Because the fee promise is created and dispatched before (and independently of) the actual transfer promise, it is not conditioned on `PromiseResult::Successful` in `rlp_execute_callback`. That callback only reports the success/failure of the *main* action promise, and on failure it refunds only the `caller_deposit` (the attached deposit from the external caller), never the relayer fee that was already sent out separately: [3](#0-2) 

For `ERC20Transfer`, the actual transfer requires an additional asynchronous NEP-141 flow (`storage_balance_of` → optionally `storage_deposit` → `ft_transfer`) which can fail for reasons entirely outside the relayer's/fee's control (insufficient token balance causing `ft_transfer` to panic, a paused/blacklisting token contract, `storage_deposit` failing, etc.), as seen in `nep_141_storage_balance_callback`: [4](#0-3) 

None of these downstream failure paths retroactively cancel or claw back the relayer fee that was already transferred at the top of `inner_rlp_execute`. This is analogous to the reported ERC-20 issue: the code assumes/relies on a value-moving action succeeding (here: "the fee is earned because the transfer will succeed") without validating the actual result before/along with disbursing funds, letting a relayer be paid even when the user's intended transfer fails.

### Impact Explanation
The wallet-owner (an unprivileged eth-implicit account holder) pays a NEAR fee to the relayer for every `EOABaseTokenTransfer`/`ERC20Transfer` attempt, even when the corresponding token/base-token transfer ultimately fails (e.g., insufficient token balance, the token contract panicking on `ft_transfer`, or `storage_deposit` failing). This results in unauthorized value movement from the user to the relayer without the corresponding service being rendered — actual funds leave the user's wallet with no compensating transfer to the intended recipient and no refund mechanism for the fee. A relayer (or a user acting as their own relayer under adverse conditions) can systematically drain fees from a wallet by submitting transactions it knows (or suspects) will fail on the token side, since the fee payment is dispatched before the outcome of the main action is known and is never reversed.

### Likelihood Explanation
This is reachable by any relayer (a permissionless, unprivileged role — anyone holding the appropriate function-call access key or acting as caller) simply by causing `rlp_execute` to be invoked with a transaction whose `tx.max_fee_per_gas * tx.gas_limit` (hence `tx_fee`) is non-zero and whose emulated action is later doomed to fail at the NEP-141/token layer (a condition fully within an adversarial relayer's/attacker's control, e.g. front-running the user's balance or simply choosing a moment when the wallet's token balance is insufficient). No validator or protocol-level privilege is required — a single submitted NEAR transaction containing the RLP-encoded Ethereum transaction is sufficient to trigger the unconditional fee payment.

### Recommendation
Chain the relayer-fee transfer to occur only after the main transfer/NEP-141 promise resolves successfully (e.g., include it as part of `rlp_execute_callback`, or as a `.then()` continuation gated on `PromiseResult::Successful`), or refund the fee back to the wallet if the main promise chain fails, mirroring the existing `caller_deposit` refund logic in `rlp_execute_callback`.

### Proof of Concept
1. Deploy a Wallet Contract for an eth-implicit account and fund it with $NEAR and a NEP-141 token balance.
2. Have the user sign (via `rlp_execute`) an Ethereum transaction representing an `ERC20Transfer` with `max_fee_per_gas * gas_limit > 0` (non-zero `tx_fee`), targeting a NEP-141 token contract, transferring an amount greater than the wallet's actual token balance (so the eventual `ft_transfer` cross-contract call will panic/fail).
3. Observe in `inner_rlp_execute` that the fee-refund promise to the relayer/predecessor is created and dispatched immediately: [5](#0-4) 
4. The subsequent `storage_balance_of`/`ft_transfer` chain fails (insufficient balance), and `rlp_execute_callback` returns `success: false` with only the `caller_deposit` (if any) refunded — the relayer fee already paid out is not reclaimed: [6](#0-5) 
5. Verify on-chain that the relayer's balance increased by `tx_fee` while the intended ERC-20 transfer never took effect and no compensating refund of the fee occurred.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
