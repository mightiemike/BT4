### Title
Environment hash omits `StorageGasSchedule` resource, allowing stale `IoPricing`/gas-charging state to be reused across state changes - (File: aptos-move/aptos-vm-environment/src/environment.rs / aptos-move/aptos-vm-environment/src/gas.rs)

### Summary
`Environment::new` computes a `sha3_256` hash meant to uniquely identify the effective on-chain configuration for VM/gas purposes, and `AptosEnvironment` equality (used to decide whether a cached `AptosEnvironment` can be reused instead of rebuilt) relies solely on this hash. `StorageGasParameters::new` reads the `StorageGasSchedule` on-chain resource from the same `state_view` to build `IoPricingV2`, but this resource's bytes are never fed into the hash.

### Finding Description
`StorageGasSchedule` is a governance-updatable resource independent of `GasScheduleV2`/`GasSchedule` (it has its own struct/address and can be changed by a separate governance proposal). If `StorageGasSchedule` is updated on-chain while `Features`, `ChainId`, `ConfigurationResource`, `GasScheduleV2`/`GasSchedule` bytes, and keyless config bytes remain unchanged, `Environment::new` will compute an identical `hash` for the pre- and post-update states, even though the actual `IoPricingV2` curves (and thus per-byte/per-item read/write gas charges) differ. Any caller relying on `AptosEnvironment::eq` (hash comparison) to decide "environment unchanged, keep using cached instance" will incorrectly keep the stale `IoPricing`, which drives read/write gas costs used in `calculate_read_gas` and `io_gas_per_write`.

### Impact Explanation
Gas charged for storage I/O directly affects `gas_used` in committed `TransactionInfo` and can affect whether a transaction runs out of gas (changing the committed write set/status). Because the hash fails to capture a state input (`StorageGasSchedule`) that changes the deterministic VM gas-charging outcome, two different ledger states can collide on the same `Environment.hash`. If any node path uses this hash as an "environment unchanged" shortcut (rather than always rebuilding `Environment` fresh per version), that node can execute transactions with stale `IoPricing` after a `StorageGasSchedule` governance update, producing a different `gas_used`/outcome than a node that rebuilt the environment fresh — a state/consensus divergence (hard-fork-only class) rather than merely a performance bug.

### Likelihood Explanation
Requires: (1) a governance-approved update to `StorageGasSchedule` without a corresponding hash-changing update to `Features`/`ChainId`/`ConfigurationResource`/`GasScheduleV2`, and (2) an environment-caching code path elsewhere in the VM that trusts `AptosEnvironment::eq`/hash to skip rebuilding. I was not able to fully trace, within the remaining tool budget, every call site that uses this hash for caching decisions (in particular I could not confirm the exact scope/lifetime of any `AptosEnvironment` cache in `aptos-vm` that would exhibit stale reuse across a live `StorageGasSchedule` governance update within the same process). This is a real gap in the hash's coverage of state inputs, but the concrete exploitability depends on caching behavior I could not fully verify with the tools available in this session.

### Recommendation
Include the raw `StorageGasSchedule` config bytes in the `sha3_256` hash computed in `Environment::new` (mirroring `fetch_config_and_update_hash` for `Features`/`ChainId`/etc.), so that any change to inputs of `StorageGasParameters::new`/`IoPricing::new` is reflected in `Environment.hash`, and any code relying on hash-based environment reuse is forced to rebuild when this resource changes.

### Proof of Concept
1. Build a `MockStateView` with `GasScheduleV2` bytes X and `StorageGasSchedule` bytes A; construct `Environment::new(&view1, ...)` → hash H1, `IoPricing` derived from A.
2. Build a second `MockStateView` with the same `GasScheduleV2` bytes X but different `StorageGasSchedule` bytes B; construct `Environment::new(&view2, ...)` → hash H2.
3. Assert H1 == H2 (since `StorageGasSchedule` bytes are never hashed) while `env1.storage_gas_params().io_pricing` differs from `env2.storage_gas_params().io_pricing` (different read/write cost curves), demonstrating the hash collision despite differing gas-charging behavior. [7](#0-6)

/// Fetches config from storage and updates the hash if it exists. Returns the fetched config.
fn fetch_config_and_update_hash<T: OnChainConfig>(
    sha3_256: &mut Sha3_256,
    state_view: &impl StateView,
) -> Option<T> {
    let (config, bytes) = T::fetch_config_and_bytes(state_view).ok().flatten()?;
    sha3_256.update(&bytes);
    Some(config)
}
