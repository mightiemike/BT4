### Title
Unbounded growth of `DelegatedResourceAccountIndex` FROM-list enables anonymous-transaction DoS on victim account queries - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
The Radiant Capital report describes a DoS where an unbounded per-user array (`userEarnings`) grows without a cap or access control, because any address can trigger an append to another account's array by calling a permissionless "claim" function repeatedly, eventually making reads/writes on that array too expensive/large to process. The closest reachable analog in java-tron is the `DelegatedResourceAccountIndex` FROM/TO account-index list, which is appended to on every `FreezeBalanceContract`/`DelegateResourceContract` delegation and is queryable by anyone through the RPC/HTTP API without any cap on the number of stored entries per address.

### Finding Description
When a resource owner delegates bandwidth/energy to a `receiverAddress` (via `FreezeBalanceContract` with a receiver, or `DelegateResourceContract`), the actuator updates a `DelegatedResourceAccountIndexCapsule` for both the sender and the receiver: [1](#0-0) 

For the legacy (non-optimized) index path, entries are only deduplicated per unique `(owner, receiver)` pair via a `List.contains()` check before `addToAccount`/`addFromAccount`: [2](#0-1) 

For the "optimized" V2 path (used once `supportAllowDelegateOptimization`/`DelegateResourceContract` is active), every delegation is stored as a *separate* keyed entry under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` namespace, with no limit on the number of distinct counterpart addresses: [3](#0-2) 

Because a `DelegateResourceContract`/`FreezeBalanceV2Contract` requires only a minimum of 1 TRX frozen balance to delegate, and `calcFee()` for delegation is `0`: [4](#0-3) 

an attacker can generate an arbitrary number of throwaway sender accounts, freeze the 1-TRX minimum in each, and delegate resources to a single victim address. Each such delegation appends a new distinct entry keyed by `(V2_TO_PREFIX, victim, sender_i)` to the victim's FROM-index, with **no upper bound**, and **no access control preventing an unrelated address from delegating (and thus indexing) against the victim**.

When any client subsequently queries the victim's delegated-resource index via the public RPC/HTTP API, the node performs an unbounded LevelDB/RocksDB prefix scan, materializes and sorts the full result set, and serializes it into the response: [5](#0-4) 

This is directly reachable from anonymous gRPC/HTTP requests: [6](#0-5) [7](#0-6) 

This is structurally identical to the Radiant Capital bug class: an unprivileged, permissionless action (claim / delegate) appends an entry to another account's tracked list with no size cap and no access control, and later reads of that list (withdraw / earnedBalances vs. getDelegatedResourceAccountIndex) become unbounded work that can exhaust resources (gas in Radiant's case; CPU/memory/DB I/O and gRPC message size in java-tron's case).

### Impact Explanation
An attacker can inflate a victim's delegated-resource index to an arbitrary size using cheap, repeatable, permissionless transactions (each only requiring 1 TRX temporarily locked, recoverable after the unfreeze delay). Once inflated:
- Calls to `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` (exposed over gRPC and HTTP, `framework/src/main/java/org/tron/core/services/RpcApiService.java`) against the victim address force the node to perform a full LevelDB/RocksDB prefix scan, in-memory sort, and full-list serialization, which scales linearly (or worse) with the number of entries.
- This degrades node responsiveness for that query and can be repeated against many victims to amplify load on public full nodes / API providers, a form of resource-exhaustion DoS on the RPC-API layer that also degrades the victim's ability to have their resource-delegation state read reliably.

This does not directly corrupt consensus state or steal funds, but is a concrete availability/DoS impact via the RPC-API surface, consistent with the "DoS via RPC-API" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: triggering the growth requires the attacker to spend TRX (1 TRX minimum per distinct index entry, only temporarily locked), and modern java-tron versions already introduced some guardrails elsewhere (e.g., `UNFREEZE_MAX_TIMES` capping the unfreeze list, `MAX_VOTE_NUMBER` capping votes-per-transaction) showing the team is aware of this bug class and has patched several similar lists — but no equivalent cap was found for the number of distinct delegation index entries per address in `DelegatedResourceAccountIndexStore`. Exploitation is inexpensive relative to the disruption caused, since the attacker's TRX is not spent/burned, only temporarily locked, and can be reused.

### Recommendation
- Enforce a maximum number of distinct FROM/TO index entries per account (analogous to `MAX_VOTE_NUMBER`/`UNFREEZE_MAX_TIMES`), rejecting new delegations to/from an address once the cap is reached, or evicting/merging low-value entries.
- Add pagination to `getDelegatedResourceAccountIndex(V2)` RPC/HTTP handlers instead of returning the full list in one response.
- Consider requiring a minimum lock value proportional to index growth, or rate-limiting delegation transactions targeting a single receiver from many distinct senders within a short window.

### Proof of Concept
1. Attacker generates N fresh keypairs `S_1..S_N` (no on-chain footprint required beyond receiving a small TRX funding to freeze).
2. For each `S_i`, attacker submits `FreezeBalanceV2Contract` with `frozenBalance = 1 TRX` (minimum allowed) then `DelegateResourceContract` from `S_i` to fixed `victimAddress`, `resource = BANDWIDTH`.
   - This is permitted purely because `frozenBalance >= TRX_PRECISION` (1 TRX) and delegation `calcFee() == 0`, with no check limiting how many distinct senders can delegate to the same receiver — see `actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java:117-192` and `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:77-89`.
3. Repeat for large N (e.g., tens of thousands), each transaction appending a new `(V2_TO_PREFIX, victimAddress, S_i)` entry.
4. Any client calls `getDelegatedResourceAccountIndexV2(victimAddress)` via gRPC (`RpcApiService.java:1929-1939`) or the equivalent HTTP endpoint; the node executes `getWithPrefix` (`DelegatedResourceAccountIndexStore.java:118-138`), performing an O(N) prefix scan, sort, and full serialization of N entries, degrading response time/resources proportionally to N with no cap in place.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
