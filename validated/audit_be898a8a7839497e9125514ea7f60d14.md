### Title
`ensure_match_transaction_info` accepts a diverged state root during replay verification - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole validator used by the `db-tool replay-on-archive` verifier to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` pulled from a backup/archive. Structurally, this mirrors the `_isValidNodeDefinition`/`_hasValidParentNodeDefinitions` bug pattern in the external report: a validation routine that is supposed to fully authenticate an object but silently omits part of the check, so the caller treats the object as valid when it is not.

### Finding Description
`ensure_match_transaction_info` checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash against the given `TransactionInfo`, but it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the post-execution state (Merkle/JMT) root: [1](#0-0) 

The function's own comment documents the gap directly:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [2](#0-1) 

This function is the only correctness check performed in `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which re-executes each transaction with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` against the archived `expected_txn_infos[idx]`. If it returns `Ok(())`, the tool records the transaction as successfully replayed: [3](#0-2) 

Because `state_checkpoint_hash` (the JMT state root committed on-chain) is never compared, a re-executed transaction whose write set hash, events, gas, and status all match but whose *resulting state tree root* diverges from what was actually committed will be reported as a verified match. This is exactly the DivReducer pattern: the validator is invoked, appears to do a complete check, but a necessary sub-check (parent validity / checkpoint hash) is skipped, so an "invalid" object (a divergent replay) is accepted as valid.

### Impact Explanation
`replay-on-archive`/`replay-verify` is one of the primary tools used to confirm that a given VM/execution-layer change does not silently change state-commitment behavior (hard-fork detection) before it reaches mainnet validators. If the comparator used by this tool cannot detect a divergence in the state checkpoint hash, a change that alters state-tree construction (but preserves per-transaction write-set/event/gas/status equivalence) could pass replay-verify undetected. That is a direct violation of the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category, and it means an authenticated proof-bearing field (`state_checkpoint_hash`) is not actually bound/verified by the tool meant to guarantee it.

### Likelihood Explanation
Medium. Exploiting this does not require an attacker in the traditional sense; it is a latent gap in an internal integrity tool that engineers rely on to catch state-root divergence bugs before they ship. The likelihood that a future or land-raced state-checkpoint-affecting code change slips through replay-verify undetected is realistic given the check is provably absent (not merely untested) and is explicitly acknowledged as pending in the source comment.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) between the locally computed checkpoint and `txn_info`, returning an error on mismatch, mirroring the pattern used for `state_change_hash` and `event_root_hash`:
```diff
     ensure!(
         event_root_hash == txn_info.event_root_hash(),
         ...
     );
+
+    if let Some(expected_state_checkpoint_hash) = txn_info.state_checkpoint_hash() {
+        ensure!(
+            self.computed_state_checkpoint_hash() == Some(expected_state_checkpoint_hash),
+            "{}: version:{}, state_checkpoint_hash mismatch",
+            ERR_MSG, version,
+        );
+    }
```
This requires plumbing the locally-computed checkpoint hash into `TransactionOutput` (or passing it as an extra parameter) since `TransactionOutput` currently only carries write set/events/gas/status.

### Proof of Concept
Not independently reproducible as a live exploit — this is a tooling/verification-gap finding, not an on-chain state-corruption bug. The concrete defect is demonstrable by inspection: any two executions that produce identical `write_set`/`events`/`gas_used`/`status` but different final JMT root (e.g. due to a bug in state-checkpoint construction in `execution/executor/src/workflow/do_state_checkpoint.rs`) will pass `ensure_match_transaction_info` and thus be reported as a successful replay by `storage/db-tool/src/replay_on_archive.rs`, even though the state root recorded in the archived `TransactionInfo.state_checkpoint_hash` does not match what was actually computed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,

        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(

            expected_events,

        // local execution. Validate the checkpoint hashes here before enabling
