### Title
Gas-key balance griefing permanently blocks `DeleteAccountAction`/`DeleteKeyAction` via `TransferToGasKeyAction` - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/access_keys.rs`)

### Summary
The reported Locke.sol bug is a griefing pattern: an unprivileged caller feeds state into a target (`incentives[who]`) that a required precondition (`== 0`) checks before a privileged/legitimate action (`arbitraryCall`) can succeed, and the only reset path is gated behind conditions the legitimate flow doesn't naturally reach in time — so an attacker can perpetually re-poison the precondition and block the action, at the mere cost of the tokens they send.

Nearcore has a structurally analogous precondition-poisoning gate on account/key deletion: gas-key balances must stay below `GasKeyInfo::MAX_BALANCE_TO_BURN` or `DeleteAccountAction`/`DeleteKeyAction` fails outright.

### Finding Description
`action_delete_account` sums all gas-key balances on the account and rejects deletion if the sum exceeds the burn cap: [1](#0-0) 

The single-key deletion path (`action_delete_key` → `delete_gas_key`) enforces the identical per-key cap: [2](#0-1) 

The only way to reduce a gas key's balance below the threshold is `action_withdraw_from_gas_key` (`WithdrawFromGasKeyAction`), which moves the balance back into the account: [3](#0-2) 

Balance is added to a gas key by `action_transfer_to_gas_key` (`TransferToGasKeyAction`). This function only checks that the target `public_key` resolves to an existing gas key on `account_id` — it performs no check that the predecessor/signer is the account owner, i.e. it behaves like a permissionless deposit (structurally the same role `createIncentive()` plays in the Locke.sol report: any address can push state that later blocks a privileged action): [4](#0-3) 

This mirrors the reported bug class exactly: `incentives[who] == 0` in Locke.sol vs. `gas_key_balance_to_burn <= MAX_BALANCE_TO_BURN` here; `claimIncentive()` (gated by stream end) vs. `WithdrawFromGasKeyAction` (available anytime, but must be re-applied after every attacker deposit); `arbitraryCall()` vs. `DeleteAccountAction`/`DeleteKeyAction`.

### Impact Explanation
An account owner who wants to delete their account (or a specific gas key) to reclaim storage rent can be perpetually blocked: any other account can call `TransferToGasKeyAction` against the victim's known gas-key public key (public keys are visible on-chain via `view_access_key`/state) to push the aggregate gas-key balance above `MAX_BALANCE_TO_BURN` right before or immediately after the victim withdraws. Because withdrawal and deletion are two separate transactions/receipts (not atomic), the attacker can always win the race by resubmitting a deposit, exactly as acknowledged in the original report ("it does cost the user" but the grief is repeatable indefinitely). This is a state-blocking / permanently-frozen-action condition reachable by any unprivileged transaction sender against any account whose gas-key public keys are known, satisfying the "permanently frozen funds/action" acceptance criterion (the account cannot complete its intended `DeleteAccount`/`DeleteKey` action, and its storage-rent balance stays locked in place indefinitely).

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker needs only (a) the target's account ID and the specific gas-key public key (both readable via RPC `view_access_key`/`view_access_key_list`), and (b) enough NEAR to exceed `MAX_BALANCE_TO_BURN` (1 NEAR per the protocol spec) minus whatever the victim currently holds in that key. The attack can be scripted to watch the mempool/chain for a `WithdrawFromGasKeyAction` or `DeleteAccountAction`/`DeleteKeyAction` from the victim and immediately front-run/back-run with a `TransferToGasKeyAction`, since these are ordinary, permissionless actions requiring no special privilege.

### Recommendation
Given the protocol team's own acknowledged trade-off in the referenced report ("accept the risk but clearly communicate"), the mitigations to consider are: (1) make the withdraw-then-delete sequence atomic within one receipt/transaction so an attacker cannot interleave a deposit between them, (2) allow `DeleteAccountAction`/`DeleteKeyAction` to auto-burn/refund excess gas-key balance above the threshold instead of hard-failing, removing the permanent block, or (3) restrict `TransferToGasKeyAction` to require actor permission matching the account (i.e., disallow third-party top-ups of another account's gas key), closing the permissionless-griefing vector entirely.

### Proof of Concept
1. Victim account `alice` holds a gas key `pk_A` with balance `0.5 NEAR` and wants to delete it (or delete the whole account).
2. Attacker submits `TransferToGasKeyAction{ public_key: pk_A, deposit: 0.6 NEAR }` against `alice`, calling `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257`) — succeeds with no ownership check, bringing the key's balance to `1.1 NEAR`, above `MAX_BALANCE_TO_BURN`.
3. Alice submits `DeleteKeyAction{ public_key: pk_A }` (or `DeleteAccountAction`); `delete_gas_key`/`action_delete_account` (`access_keys.rs:103`, `actions.rs:371`) rejects it with `GasKeyBalanceTooHigh`.
4. Alice calls `WithdrawFromGasKeyAction` to bring the balance back under the cap, then immediately retries deletion. The attacker resubmits `TransferToGasKeyAction` between Alice's withdraw and delete transactions (different receipts/blocks), re-triggering the `GasKeyBalanceTooHigh` failure indefinitely.

    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
