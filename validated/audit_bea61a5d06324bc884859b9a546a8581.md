### Title
Unbounded Gzip Decompression in RPC `decompress_program` Enables Memory-Exhaustion DoS via `add_declare_transaction` (Cairo0) - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The JSON-RPC `decompress_program` helper decompresses a user-supplied, base64-encoded gzip blob (the deprecated/Cairo0 `program` field of a `BroadcastedDeclareV1Transaction`) with no size limit or output cap, unlike the equivalent gateway path which enforces `decode_and_decompress_with_size_limit`.

### Finding Description
`decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs:671-682` base64-decodes and gzip-decompresses attacker-controlled bytes directly into an unbounded `Vec<u8>`: [1](#0-0) 
It is explicitly marked `// TODO(dan): add time and size limits.` and is invoked from `user_deprecated_contract_class_to_sn_api`, which converts a `BroadcastedDeclareV1Transaction`'s `compressed_program` field when constructing an `ExecutableTransactionInput::DeclareV1` for the RPC execution/simulation path: [2](#0-1) 
This contrasts with the gateway's own declare handling and the P2P class conversion path, which both call `decode_and_decompress_with_size_limit`, a hardened variant that caps decompressed output using `.take(max_size + 1)` and rejects oversized results: [3](#0-2) [4](#0-3) 
A small, highly-compressible gzip payload (a "zip bomb" of zeroes, exactly matching the external report's bug class) can therefore expand to gigabytes in memory when decompressed via `decoder.read_to_end(&mut decompressed, ...)` with no bound.

### Impact Explanation
An unprivileged RPC caller invoking declare-related simulation/estimation endpoints (e.g. `starknet_estimateFee`, `starknet_simulateTransactions`, `starknet_traceTransaction`-style execution paths that accept a `BroadcastedDeclareTransaction` V1) can submit a crafted small gzip blob that decompresses to an arbitrarily large buffer, exhausting node memory and causing the RPC server process to OOM or become unresponsive — a resource-consumption DoS matching CWE-400, directly analogous to CVE-2016-5004. Because `apollo_rpc` typically shares a process/host with sequencer/full-node components in various deployment topologies, this can degrade or crash the RPC-serving node, potentially disrupting transaction submission/confirmation for that node.

### Likelihood Explanation
Likelihood is significant: the vulnerable function is reachable directly from RPC input with no authentication, no size pre-check on the compressed input, and no decompression-output cap — the exact structural gap flagged by the code's own TODO comment. The bound severity is limited to Declare V1 (Cairo0) programs, since V2/V3 declare execution simulation is explicitly unimplemented at this call site (`Err(internal_server_error("Declare V2/V3 is not supported yet in execution."))`), which somewhat narrows exposure but does not eliminate it, since V1 declare simulation is fully wired through this exact function.

### Recommendation
Replace the manual `base64::decode` + `GzDecoder::read_to_end` logic in `decompress_program` with `starknet_api::compression_utils::decode_and_decompress_with_size_limit`, enforcing a configurable maximum decompressed size (consistent with `max_contract_bytecode_size` / `max_contract_class_object_size` used elsewhere in the gateway), and reject any request whose decompressed program exceeds that bound before further parsing.

### Proof of Concept
1. Craft a small gzip stream consisting of a long run of zero bytes (a classic decompression bomb), producing e.g. a 1 KB compressed payload that expands to several GB.
2. Base64-encode it and place it in the `program` field of a `BroadcastedDeclareV1Transaction` contract_class.
3. Submit it via an RPC method that routes through `TryFrom<BroadcastedDeclareTransaction>` for `ExecutableTransactionInput` (e.g. simulate/estimate-fee style execution endpoints accepting V1 declare), triggering `user_deprecated_contract_class_to_sn_api` → `decompress_program`.
4. Observe the node allocate memory proportional to the decompressed size with no cap, causing excessive memory consumption / OOM, as reproduced by the unit test harness at `crates/apollo_rpc/src/v0_8/execution_test.rs:1340-1345` which calls `decompress_program` directly on attacker-controlled input. /// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
