## Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint roots, letting `replay-verify` (db-tool) and the debugger accept a `TransactionInfo` whose checkpoint-hash fields diverge from local re-execution - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-response/replay integrity check used by `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` to confirm that locally re-executed VM outputs match the `TransactionInfo` that was actually committed to the accumulator/ledger. The function checks status, gas, write-set hash (`state_change_hash`), and event root hash, but it explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and the newer `position_state_checkpoint_hash` fields carried in `TransactionInfoV1`.

### Finding Description
`ensure_match_transaction_info` is documented in the source itself as incomplete: [1](#0-0) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```

It only validates status, gas, `state_change_hash` (write-set hash) and `event_root_hash`, never `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`: [2](#0-1) 

These checkpoint hashes are exactly the fields whose correctness is central to state-commitment integrity — they are what `DoStateCheckpoint::run` computes from local execution of the JMT/hot-state/native-position sparse Merkle trees, and what gets bound into the `TransactionAccumulator` leaf via `TransactionInfo::hash()`: [3](#0-2) 

The comparator is invoked directly by the `replay_on_archive` tool as the sole correctness gate after re-executing archived transactions against a freshly built `AptosVMBlockExecutor`: [4](#0-3) 

Because the comparator silently passes even when the recomputed `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` differ from the persisted `TransactionInfo`'s corresponding fields, a state-root divergence introduced by a storage bug, a bad JMT/hot-state/native-position merklization path, or a malicious/corrupted archive can pass `replay-verify` and the debugger's replay-and-check flow undetected. The in-code TODO explicitly calls out that this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — i.e., the authors know the native-position state root (a genuinely new proof/commitment surface, `PositionStateWithSummary`/`ProvablePositionStateSummary`) is not actually cross-checked by the tooling meant to detect commit-time divergence.

### Impact Explanation
This breaks the "committed state must survive verification unchanged" and "replay paths must not accept a different ledger state as correct" invariants from the state-integrity gate. Concretely:
- `replay-verify`, which is the primary tool operators/auditors use to confirm that a synced/backed-up node's ledger state matches independent re-execution, will report success even when the state-checkpoint root (main state, hot state, or native-position state) it recomputes does not match the root actually bound into the accumulator/ledger info.
- This masks state-commitment corruption (e.g., from a storage/restore bug elsewhere, or from an malicious archive/backup source) that would otherwise be caught by exactly this check, undermining audit/replay confidence in mainnet ledger correctness, especially once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native-position state root) is turned on.
- It does not by itself let an attacker forge a validator-signed root (BFT consensus still binds `state_checkpoint_hash` via `TransactionInfo::hash()` into the signed `LedgerInfo`), so it's not an immediate live-consensus fork; the impact is specifically that the authenticated verification/replay tooling built to detect proof/commit divergence fails to do so.

### Likelihood Explanation
The code path is reached on every invocation of `replay_on_archive` (and the debugger's replay-and-check API), which are the standard tools used to verify committed ledger state; no attacker action is required to trigger the gap — it's a permanent, unconditional omission that the maintainers themselves flagged via the TODO. The feature it explicitly warns about (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) already has wiring in `DoStateCheckpoint`, `aptosdb_writer.rs`, and `aptosdb_reader.rs`, so its checkpoint hash is already produced and stored in `TransactionInfoV1` today.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding execution feature is enabled/the recomputed hash is `Some`, matching them against the `txn_info` values before returning `Ok(())`. This should be resolved before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network, as the maintainers' own TODO states.

### Proof of Concept
No exploit code is required beyond reading the check itself: given any two `TransactionInfoV1` instances that agree on `transaction_hash`, `state_change_hash`, `event_root_hash`, `gas_used`, and `status`, but differ in `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, `ensure_match_transaction_info` returns `Ok(())` for both — i.e. `replay_on_archive::execute_and_verify` (storage/db-tool/src/replay_on_archive.rs:392-397) will treat re-execution as successfully verified regardless of which checkpoint-hash variant is supplied as `expected_txn_infos[idx]`, since none of those fields are read in the comparator (types/src/transaction/mod.rs:2139-2204).

Note: I was not able to independently confirm at what block height / feature-flag state `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently active on mainnet, so the practical exposure of the native-position-root gap specifically (versus the state/hot-state gap, which has existed longer) is uncertain without further investigation of on-chain feature flag status.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
