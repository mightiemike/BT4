### Title
`TransactionOutput::ensure_match_transaction_info` omits checkpoint-hash validation, allowing replay-verify to accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-response invariant checker used by replay/verification tooling to confirm that a locally re-executed `TransactionOutput` matches an archived, ledger-committed `TransactionInfo`. It validates status, gas, write-set hash, and event-root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newly introduced `position_state_checkpoint_hash` fields carried by `TransactionInfoV1`. The code itself documents this gap with a `TODO(trading-native)` comment stating that replay-verify can "report a successful replay even when the authenticated position state root diverges from local execution."

### Finding Description
`assemble_transaction_infos` in `execution/executor/src/workflow/do_ledger_update.rs` builds `TransactionInfoV1` including `maybe_state_checkpoint_hash`, `maybe_hot_state_checkpoint_hash`, and `maybe_position_state_checkpoint_hash` [1](#0-0) . These checkpoint hashes are computed separately from the write-set/event hashes, in `DoStateCheckpoint::run`, including the position-state root produced by `compute_position_checkpoint` when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled [2](#0-1) .

However, `ensure_match_transaction_info`, which is the function relied upon by replay/verify tools (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to assert that a locally computed `TransactionOutput` matches the trusted, accumulator-proven `TransactionInfo` from an archive/backup, only checks status, gas_used, the write-set hash against `state_change_hash`, and the event root hash [3](#0-2) . It never compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against anything computed locally, and the function itself contains a self-acknowledged TODO documenting this gap [4](#0-3) .

Because the checkpoint hash fields are part of `TransactionInfo` — the object bound into the transaction accumulator and thus into the authenticated ledger proof — omitting them from the comparator breaks the invariant that "VM outputs, transaction infos, ... must survive executor-to-storage handoff unchanged" and that replay must independently re-derive and check every committed root, not just a subset. A node whose position-state (or plain state/hot-state) Jellyfish Merkle root diverges from the canonical chain (due to a local bug, a bad DB migration, a sharded-executor bug in aggregating `native_position_iter` writes, etc.) will still pass `ensure_match_transaction_info` because the divergent root is simply never inspected, even though the accumulator-proof-bound `TransactionInfo` on the canonical chain encodes the correct root.

### Impact Explanation
This defeats the entire purpose of replay-verify: replay/verify tooling is the last line of defense used to confirm that a fast-sync/restored/replayed node's storage matches the canonical, proof-bound ledger state. If the checkpoint-hash comparison is skipped, a state root divergence (state trie, hot-state trie, or position-state trie) is silently accepted as "verified," meaning a corrupted or diverging committed state root can pass authenticated verification. Any downstream consumer (auditors, bootstrapping nodes using `replay_on_archive`, or the debugger tooling) that relies on `ensure_match_transaction_info`'s success as proof of ledger-state correctness could be misled, masking a class of committed-state corruption that state-integrity checks are specifically meant to catch. The impact is bounded today because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a new feature flag [5](#0-4)  and the state/hot-state checkpoint hash checks were seemingly never added either, but once the position-state root is authenticated on-chain via `TransactionInfoV1`, silently skipping its verification in the standard verification helper is a genuine gap in proof-integrity enforcement.

### Likelihood Explanation
Medium: the gap is always present for anyone calling `ensure_match_transaction_info` (replay-verify tooling, `aptos-debugger`, CLI replay commands), and does not require any privileged access to trigger — it simply means these tools fail to catch a class of bugs they are designed to catch. It requires an underlying, separate divergence in state/hot-state/position-state computation to actually manifest as a missed detection, so it is not directly exploitable by itself, but it removes the safety net that would otherwise catch such divergences on mainnet-adjacent tooling.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding feature is enabled/the hash is present in the `TransactionInfo`, comparing them to the locally computed checkpoint roots (as already computed in `DoStateCheckpoint`). At minimum, gate enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production on this validation being implemented, per the TODO already present in the code.

### Proof of Concept
Not applicable as an exploit script — this is a verification-logic omission rather than an actively triggerable exploit. The proof is the code path itself: `assemble_transaction_infos` commits `position_state_checkpoint_hash` into the authenticated `TransactionInfo` [6](#0-5) , while `ensure_match_transaction_info`, the function tools use to confirm replayed output matches that authenticated info, never reads or compares that field [7](#0-6) , so any local divergence in the position-state root is undetectable through this API.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
```
