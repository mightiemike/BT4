## Title
`DeleteAccount` does not purge pending `PromiseYield`/postponed-receipt state, allowing a stale receipt to execute against a re-created account of the same name - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` is used by `action_delete_account` (`runtime/runtime/src/actions.rs`) to wipe an account when `DeleteAccount` is executed. It only removes the `Account`, `ContractCode`, access keys/gas-key nonces, and contract data - it never removes `PromiseYieldReceipt`, `PromiseYieldTimeout` queue entries, `PostponedReceiptId`, `PendingDataCount`, or `ReceivedData` entries keyed to that account. This mirrors the reported `GuardianRecoveryValidator.onUninstall` bug: a "removal" operation drops the top-level entity but leaves pending/derived state behind, which can later resurface and act on behalf of an entity that no longer represents the same owner.

### Finding Description
`remove_account` is the sole state-cleanup routine invoked on `DeleteAccount`: [1](#0-0) 

It removes the account, code, access keys, gas-key nonces, and contract data, but never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldTimeout`, `TrieKey::PromiseYieldIndices`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` scoped to `account_id`. `action_delete_account` calls `remove_account` and unconditionally proceeds to null out the account, without checking for outstanding yields or postponed receipts: [2](#0-1) 

A `PromiseYield` receipt created by a contract on itself (via `promise_yield_create`) is stored keyed by `(receiver_id, data_id)` together with a FIFO timeout entry: [3](#0-2) 

If the owning account self-deletes (`DeleteAccount`) while a yield is outstanding, the `PromiseYieldReceipt` and its `PromiseYieldTimeout` entry survive in state, orphaned. Later, `resolve_promise_yield_timeouts` walks the timeout queue purely by index/expiry and, when it finds a live `PromiseYieldReceipt` key for the (deleted) `account_id`, synthesizes a new `PromiseResume` receipt targeting that same `account_id` - with no check that the account still exists: [4](#0-3) 

When that `PromiseResume` (or an in-flight real resume) is processed, the runtime looks up the account fresh from state via `get_account`, retrieves the still-stored (stale) `yield_receipt`, and executes its original actions with the resolved account: [5](#0-4) [6](#0-5) 

Since NEAR explicitly allows an account name to be deleted and later re-created (`update_validator_accounts` comments on this: "the only way it could appear...is when a validator deletes their account and re-creates"), and `check_account_existence`/`apply_action_receipt` only check whether *an* account currently exists at that id - not whether it is the *same* account - a stale yielded receipt whose actions were authored under the old account's context can execute against the newly created account transparently, because `get_account` simply reads current state: [7](#0-6) 

This is the direct analog of the reported bug: the "uninstall" (`DeleteAccount`) leaves pending guardian-like state (`PromiseYieldReceipt`/`PromiseYieldTimeout`) unpurged, and that state later reactivates and acts on an account the new owner did not authorize, without any check equivalent to `isReady`/existence-and-identity verification before consuming the parked state.

### Impact Explanation
The stale yielded action receipt was constructed by the pre-deletion contract execution and can contain arbitrary actions (e.g., `FunctionCall`, `Transfer`, `AddKey`, `DeleteKey`) targeting `account_id` with `predecessor_id` set to whatever the original yield-creating call specified. If a new account with the same `account_id` is created (funded and initialized) before the timeout/resume fires, this stale receipt executes against it without the new owner's action or consent - a state transition the new account owner never authorized. Depending on the yielded receipt's payload this can move balance, install/replace access keys, or invoke a function call on the new account's contract, i.e., unauthorized value movement / invalid state transition acceptance under the "reachable via ordinary transactions" threat model in scope.

### Likelihood Explanation
Reaching this requires: (1) a contract account calling `promise_yield_create` (a standard host function reachable from any `FunctionCall` action), (2) that same account executing `DeleteAccount` before the yield resolves, and (3) someone (anyone) re-creating an account with the identical name before the yield's timeout (a bounded, configurable number of blocks) expires or before a genuine resume arrives. All three steps are achievable by an unprivileged transaction signer/contract deployer using only standard, permitted actions - no validator or node compromise is required. The main constraint is timing (re-creation must occur before the yield timeout fires), which reduces but does not eliminate likelihood, especially since malicious contracts can be crafted to lengthen the exploitation window intentionally (e.g., a contract calls yield with a large custom timeout window, then self-deletes, expecting a victim to later claim the vacated account name).

### Recommendation
Before allowing `DeleteAccount` to proceed (or as part of `remove_account`), scan and purge any `PromiseYieldReceipt`, `PromiseYieldTimeout`, `PostponedReceiptId`, `PendingDataCount`, and `ReceivedData` entries scoped to the account being deleted, analogous to how the referenced fix verifies `isReady` before mutating guardian state. At minimum, `resolve_promise_yield_timeouts`/`PromiseResume` handling should verify the receiver account still exists (and ideally that it is the same account instance, e.g. via a generation counter) before executing a parked yield receipt, dropping/refunding it instead of executing against an unrelated re-created account.

### Proof of Concept
1. Deploy a contract to account `victim.near` and call a method that performs `promise_yield_create(callback, data, timeout=N, gas)` — this stores `PromiseYieldReceipt{receiver_id: victim.near, data_id}` and enqueues a `PromiseYieldTimeout` entry.
2. In the same or a following chunk, from `victim.near`, submit `DeleteAccount { beneficiary_id: attacker.near }`. `action_delete_account` calls `remove_account`, which deletes the `Account`/keys/code/data but leaves the `PromiseYieldReceipt` and `PromiseYieldTimeout` entries untouched.
3. Before the timeout elapses, have any party (e.g., the original creator's registrar or the attacker) execute `CreateAccount` for `victim.near` again, funding and initializing it (e.g. deploying a new contract or adding new keys).
4. Wait for `resolve_promise_yield_timeouts` to reach the queue entry (or send a legitimate `PromiseResume`): it finds the still-present `PromiseYieldReceipt` for `victim.near`, forwards a `PromiseResume`, and `apply_action_receipt` executes the original (pre-deletion) yielded receipt's actions against the freshly created `victim.near` account — actions the new owner of `victim.near` never authorized.
