### Title
Interest index and liquidity index desynchronize when `last-update` is advanced on any-change instead of per-index — permanent freezing of supplier yield - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent per-asset vaults)

### Summary
### Finding Description
Each lending vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts) tracks two independent accrual clocks derived from a single shared timestamp variable, `last-update`: [1](#0-0) 

```clarity
(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta rate time-delta true))))
          (calc-index-next idx multiplier)))))

(define-private (next-liquidity-index)
  (let ((states (var-get pause-states))
        (lidx (var-get lindex)))
    (if (get accrue states)
        lidx
        (let (
            (rate (interest-rate))
            (liquidity-rate (calc-liquidity-rate rate (utilization) (var-get fee-reserve)))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta liquidity-rate time-delta false))))
          (calc-index-next lidx multiplier)))))
```

Both `next-index` (debt/borrow index) and `next-liquidity-index` (supplier/liquidity index) compute their own multiplier from the *same* `time-delta` (`stacks-block-time - last-update`), but they use two different rates (`rate` — the borrow rate — vs `liquidity-rate` — a smaller, utilization/reserve-adjusted rate). Because Clarity uses truncating integer math, for short enough `time-delta` and small enough `liquidity-rate`, `calc-multiplier-delta` can round down to exactly `INDEX-PRECISION` (i.e., "no change") for the liquidity index while the higher borrow rate still produces a multiplier `> INDEX-PRECISION` for the debt index (or vice versa for very low-utilization periods).

The `accrue` public function then decides whether to persist `last-update` based on an `or` over *both* indices changing, not each index independently: [2](#0-1) 

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                ...)
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            ...
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
```

Because `last-update` is a single shared clock, if the debt index (`idx`) changes but the liquidity index (`lidx`) does not (due to rounding on a short interval), the `or` condition is still true, so `last-update` is advanced to the current `stacks-block-time`. On the next `accrue` call, `time-delta` is measured from this new, advanced timestamp — the time window during which the liquidity index should have accrued (but didn't, due to truncation) is permanently lost; it can never be recovered because the clock has already moved past it. Meanwhile the debt index continues to compound correctly. The result is a durable, non-recoverable divergence: borrowers keep paying interest that grows the debt index at the correct rate, while the amount attributable to suppliers (the liquidity index used for `zToken`/share pricing) permanently under-accrues for the skipped windows.

### Impact Explanation
This is not a per-user race — it is a protocol-level accounting invariant violation that occurs whenever `accrue()` (called on essentially every `deposit`, `redeem`, `system-borrow`, `system-repay`, and `market.clar`'s `accrue-and-cache`) is invoked frequently with short inter-call time deltas, which is common in practice (every deposit/borrow/repay call triggers `accrue`). Any caller can trigger `accrue()` indirectly through ordinary vault operations at will, with no special privilege, DAO action, or oracle manipulation required. The systematic effect is a permanent loss of yield that should have accrued to suppliers (`lindex`), since the clock used to compute it is stolen by the coincident, unrelated advance of the debt index clock. This falls under the in-scope High-severity class: permanent freezing of unclaimed yield, since supplier-side interest for the skipped windows is neither collected nor recoverable — the underlying assets tracked by `total-assets`/`total-assets-preview` never reflect that missed accrual once `last-update` has moved past it.

### Likelihood Explanation
The precondition (rounding difference between two multipliers computed from the same short `time-delta` but different rates) is a routine, low-probability-but-frequent occurrence given how often `accrue()` fires in normal usage (deposits/borrows/repays every block on active vaults) and how liquidity-rate is always ≤ borrow-rate (scaled by utilization and net of reserve factor), making it systematically more likely for the liquidity-index multiplier to truncate to `INDEX-PRECISION` while the borrow-index multiplier does not, for short block-to-block intervals. No attacker coordination, flashloan, or DAO compromise is required — it is a passive drift that compounds over time, and can be amplified by anyone repeatedly triggering `accrue` (e.g., by looping small `deposit`/`redeem` calls) during low-utilization, low-rate periods.

### Recommendation
Track a separate `last-update` timestamp per index (one for `index`/borrow accrual, one for `lindex`/liquidity accrual), and advance each timestamp independently based on whether that specific index actually changed — do not gate the persistence of either clock on the other index's change. Alternatively, always advance `last-update` on every non-zero `time-delta` accrue call regardless of whether either index numerically changed, so that no time window is ever silently dropped from either clock's future calculation.

### Proof of Concept
1. Deploy/observe a vault (e.g., `v0-vault-stx.clar`) with low utilization so `liquidity-rate` computed via `calc-liquidity-rate` is small relative to `interest-rate`.
2. At `last-update = T0`, call `accrue()` (indirectly via `deposit`/`system-borrow`) at `stacks-block-time = T0 + Δ` for a small `Δ` chosen such that `calc-multiplier-delta(liquidity-rate, Δ, false)` truncates to exactly `INDEX-PRECISION` (no change to `lindex`) while `calc-multiplier-delta(rate, Δ, true)` still yields `> INDEX-PRECISION` (i.e., `index` does change).
3. Observe that `accrue`'s final check `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` evaluates true (because `idx` changed), so `last-update` is set to `T0 + Δ`, even though `lindex` was never updated for interval `Δ`.
4. On the next `accrue()` call at `T0 + Δ + Δ2`, `time-delta` is computed as `Δ2` (measured from `T0 + Δ`), not `Δ + Δ2`; the interest that should have accrued to `lindex` over the original `Δ` window is permanently unrecoverable.
5. Repeating this pattern (e.g., via repeated small deposit/withdraw calls during low-utilization windows) accumulates a growing, permanent gap between debt accrued (`index`) and supplier yield credited (`lindex`), representing frozen/lost yield for suppliers.
