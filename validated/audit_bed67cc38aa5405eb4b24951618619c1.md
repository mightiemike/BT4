### Title
DoS of `ExchangeWithdrawContract` liquidity withdrawals via front-running `ExchangeTransactionContract` trades - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` lets an exchange's creator withdraw its Bancor-style liquidity pool by supplying an exact `tokenQuant`, from which the actuator computes the counter-asset amount (`anotherTokenQuant`) using the *current* on-chain pool ratio (`firstTokenBalance`/`secondTokenBalance`). Because the pool ratio is shared, mutable state that **any unprivileged account** can alter by submitting a normal `ExchangeTransactionContract` trade, an attacker can front-run a pending `ExchangeWithdrawContract` transaction with a minimal trade to shift the ratio just enough to make the withdraw fail its strict precision/sufficiency checks — the same "frontrun with a tiny state-mutating tx to break an exact-amount computation" pattern described in the reference report for `DSCEngine.liquidate`.

### Finding Description

The pool balances (`firstTokenBalance`, `secondTokenBalance`) are updated by `ExchangeTransactionActuator`, which is callable by **any** unprivileged account trading against the exchange: [2](#0-1) 

Because the withdraw transaction hard-codes `tokenQuant` (chosen off-chain against the pool state at broadcast time) and re-derives `anotherTokenQuant` from the pool ratio at execution time, an attacker observing the pending `ExchangeWithdrawContract` in the mempool can broadcast a trivially small `ExchangeTransactionContract` trade against the same exchange to shift `firstTokenBalance`/`secondTokenBalance` just enough that:
1. the recomputed `anotherTokenQuant` no longer satisfies the `< 0.0001` relative-precision tolerance (`"Not precise enough"`), or
2. the ratio shift exceeds pool balances (`"exchange balance is not enough"`).

This mirrors the reported DSCEngine bug class exactly: an unrelated, cheap, unprivileged transaction manipulates shared state that a separate exact-amount transaction depends on, causing that legitimate transaction to revert. The attack can be repeated on every re-submission attempt by the withdrawer, indefinitely denying the exchange creator's ability to withdraw liquidity in one operation.

### Impact Explanation
The exchange creator's withdrawal repeatedly reverts (`ContractValidateException`), consuming their bandwidth/energy fee each attempt with no state change, while the attacker's front-running trades are arbitrarily cheap (minimal `tokenQuant`). This is a functional Denial-of-Service against a specific unprivileged accounting operation (`ExchangeWithdrawContract`) that depends on shared AMM pool state (`ExchangeCapsule` balances), matching the "exchange/market math" scope. It does not directly corrupt funds but blocks legitimate liquidity withdrawal indefinitely, which can also be leveraged to keep an exchange creator's assets locked in a manipulated pool.

### Likelihood Explanation
The `Exchange`/`ExchangeV2` (Bancor-style) contract type is a legacy but still-supported TRON feature reachable via any broadcast transaction; `ExchangeTransactionContract` requires no special permission and can be sent by anyone holding a negligible amount of either pool asset. Front-running via mempool observation is a well-established technique on TRON given its public P2P transaction propagation before block inclusion. The attack cost is minimal (dust-level trade), making repeated exploitation highly likely once a withdraw transaction is observed pending.

### Recommendation
- Allow the withdrawer to specify acceptable slippage/tolerance bounds explicitly (e.g., a `minAnotherTokenQuant`) instead of relying purely on a fixed relative-precision check computed from live state, and fail gracefully with a clear "slippage exceeded" rather than a brittle precision assertion.
- Alternatively, allow `ExchangeWithdrawActuator` to accept a sentinel value (analogous to `type(uint256).max` in the reference recommendation) meaning "withdraw entire creator share regardless of exact ratio drift," recomputing amounts atomically at execution time rather than requiring the caller to pre-compute an exact ratio-matching ratio quant off-chain.
- Consider rate-limiting or requiring a cooldown/commit-reveal for trades immediately preceding a pending withdraw by the same exchange's creator, or restrict `ExchangeWithdrawActuator` to a proportional-share model unaffected by short-term ratio shifts.

### Proof of Concept
1. Exchange pool `E` has `firstTokenBalance = A`, `secondTokenBalance = B` (ratio `B/A`), and creator `C` is its `creatorAddress`.
2. `C` broadcasts `ExchangeWithdrawContract(exchangeId=E, tokenId=first, quant=A)` intending to fully withdraw, with `anotherTokenQuant` computed off-chain as `B*A/A = B` (or a proportional share).
3. Attacker observes this transaction in the mempool and immediately broadcasts a small `ExchangeTransactionContract(exchangeId=E, tokenId=first, quant=ε)` trade, shifting `firstTokenBalance`/`secondTokenBalance` slightly.
4. The attacker's transaction is included first (attacker sets a marginally higher fee/priority or simply wins the race).
5. When `C`'s `ExchangeWithdrawActuator.doValidate()` executes, it recomputes `anotherTokenQuant` from the now-shifted `firstTokenBalance`/`secondTokenBalance`, and the pre-recorded `tokenQuant`/expected ratio no longer satisfies the `< 0.0001` relative tolerance in [3](#0-2) , throwing `ContractValidateException("Not precise enough")` and reverting the withdrawal while consuming `C`'s fee.
6. The attacker repeats step 3 for every subsequent withdrawal attempt by `C`, indefinitely blocking the withdrawal.
