### Title
Webhook/fulfillment-service `Shop-Domain` header is not bound to the HMAC signature, allowing session/tenant spoofing - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
The webhook and fulfillment-service authentication paths validate the HMAC signature over the raw request body only. The shop-identifying header (`X-Shopify-Shop-Domain` / `shopify-shop-domain`) that determines *which* merchant's offline session and access token get attached to the authenticated context is read out-of-band and is never covered by that signature. Because the HMAC secret (`apiSecretKey`) is shared across every shop that has the same app installed, any party who can obtain one valid `(rawBody, hmac)` pair for their own shop can replay it with a different `Shop-Domain` header and have the library treat the request as authentic for an arbitrary other shop.

### Finding Description
`validateHmacFromRequestFactory` computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it against the `X-Shopify-Hmac-Sha256` header — nothing else is included in the signed data: [1](#0-0) 

The separate function that extracts the routing/tenant identity from the request headers (`domain`) does so independently of the HMAC check, and there is no cross-check binding `domain` to the signed payload: [2](#0-1) 

`authenticateWebhookFactory` then uses this unauthenticated `domain`/`shop` value directly to look up and attach the target shop's offline session (and thus its Admin API access token) to the webhook context: [3](#0-2) 

The fulfillment-service handler follows the identical pattern — HMAC validated over `rawBody` only, then `ShopifyHeader.Domain` trusted as-is to fetch the session: [4](#0-3) 

This is structurally the same class of bug as the reference report: a security-relevant identity parameter (`wallet`/`sender` there, `shop`/`domain` here) is taken from attacker-influenced input and used to select which tenant's privileged context to operate under, without verifying it against the value that was actually authenticated (the HMAC signer's identity).

### Impact Explanation
Any actor who legitimately installs the app on a shop they control (or otherwise obtains one valid signed webhook body, e.g. by triggering an event on their own store) can capture a valid `(rawBody, X-Shopify-Hmac-Sha256)` pair and resend it to the app's webhook/fulfillment endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop where the same app is also installed. Because the signature check never inspects the domain header, the request passes validation, and `authenticateWebhookFactory`/`authenticateFulfillmentServiceFactory` will load the **victim's** offline session and Admin API client and hand it to the app's webhook handler together with the **attacker-controlled** payload. Any app logic that trusts the payload to drive writes/mutations against the resolved session's shop (a common pattern, e.g. `ORDERS_CREATE`, `APP_UNINSTALLED`, `PRODUCTS_UPDATE` handlers) can be tricked into acting on a different merchant's store using attacker-chosen content — a cross-tenant authentication/authorization bypass.

### Likelihood Explanation
Exploitation only requires the ability to install the target app (a public, unprivileged, "single merchant" action) and to send an HTTP POST with a forged header — no secret disclosure, MITM, or dependency compromise is needed. Any Shopify app built on `shopify-app-js` that registers webhooks and both allows install by arbitrary shops is potentially affected, since this behavior lives in the shared library code (`shopify-api`, `shopify-app-remix`, `shopify-app-react-router`) rather than in individual app implementations.

### Recommendation
Bind the `shop`/`domain` value into the data that is cryptographically verified, or otherwise cross-check it against a value obtained from a channel Shopify actually authenticates (e.g., verify the resolved session's shop matches an independently-verified value, or include the domain/topic/webhook-id headers in the HMAC input as canonicalized data, similar to how `stringifyQueryForAdmin`/`stringifyQueryForAppProxy` bind `shop` into the OAuth/app-proxy HMAC in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 51-82). At minimum, document/require handler code to never trust webhook payload content to identify the acted-upon shop, and add an integrity check between the `domain` header and body-derived identifiers where the topic payload includes one (e.g. `shop_id`/`myshopify_domain` fields typically present in Shopify webhook payloads).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `PRODUCTS_CREATE`) to capture a legitimate `(rawBody, X-Shopify-Hmac-Sha256)` pair — since the app secret is shared for all installs of the same app, this HMAC is valid against `config.apiSecretKey`.
2. Send the following forged request to the app's webhook endpoint, keeping `rawBody`/`X-Shopify-Hmac-Sha256` identical but replacing the domain header with a victim shop that has the same app installed:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: products/create
X-Shopify-Hmac-Sha256: <captured-from-attacker-shop>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-API-Version: 2025-01
X-Shopify-Webhook-Id: 1

<captured-rawBody-from-attacker-shop>
```
3. `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-201`) validates successfully because it only checks `rawBody` against the secret. `authenticateWebhookFactory` (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:52-96`) then loads `victim-shop.myshopify.com`'s offline session/admin client and passes it, together with the attacker's forged payload, to the app's webhook handler.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}
