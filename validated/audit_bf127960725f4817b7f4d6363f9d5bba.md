### Title
Unbounded block range in `scanShieldedTRC20NotesByIvk`/`scanShieldedTRC20NotesByOvk` gRPC handlers enables synchronous CPU DoS on the gRPC executor - (File: framework/src/main/java/org/tron/core/services/RpcApiService.java)

### Finding Description
The gRPC handlers `scanShieldedTRC20NotesByIvk` and `scanShieldedTRC20NotesByOvk` extract `startNum`/`endNum` directly from the client-supplied `IvkDecryptTRC20Parameters`/`OvkDecryptTRC20Parameters` request and pass them straight into `wallet.scanShieldedTRC20NotesByIvk(...)` / `wallet.scanShieldedTRC20NotesByOvk(...)` with no server-side validation of the range width. [1](#0-0) [2](#0-1) 

The only guard present is `rejectIfEventsPresent`, which checks the `eventsList` field, not the block-range size. This contrasts with other block-range RPCs in the same file such as `getBlockByLimitNext`, which explicitly bounds the requested span using a `BLOCK_LIMIT_NUM` constant before executing the query. Because the shielded scan performs per-block ZK note decryption work proportional to `endNum - startNum`, an attacker-controlled unbounded range (e.g., `startBlockIndex=0`, `endBlockIndex=<current head>`) causes the handler to iterate and cryptographically process the entire chain history synchronously inside the RPC call, on a thread from the shared gRPC executor pool.

### Impact Explanation
This falls into the "DoS via RPC-API" bounty class. A small number of such requests (or a few concurrent ones) can occupy gRPC executor threads for a duration proportional to chain height, starving the thread pool and degrading or blocking other RPC traffic on the node.

### Likelihood Explanation
No authentication is required, only that the shielded TRC20 feature is enabled (a pre-existing/default-adjacent node capability, not a privileged action). The attacker cost is a single unauthenticated gRPC call; it can be trivially repeated/parallelized to multiply cost with no rate limiting or backpressure visible in the reviewed handler code.

### Recommendation
Add an explicit maximum range check (analogous to `BLOCK_LIMIT_NUM` used by `getBlockByLimitNext`) in `scanShieldedTRC20NotesByIvk`/`scanShieldedTRC20NotesByOvk` (and their HTTP counterparts `ScanShieldedTRC20NotesByIvkServlet`/`ScanShieldedTRC20NotesByOvkServlet`) that rejects requests where `endBlockIndex - startBlockIndex` exceeds a bounded constant, returning an error to the caller instead of performing unbounded synchronous work.

```java
// JUnit-style PoC (conceptual, requires a chain with N blocks populated)

long endNum = currentHeadBlockNum; // e.g., 1_000_000+

wallet.scanShieldedTRC20NotesByIvk(startNum, endNum, contractAddress, ivk, ak, nk);
long elapsed = System.currentTimeMillis() - start;
// Assert elapsed grows linearly with (endNum - startNum), with no rejection/error
// even though no BLOCK_LIMIT_NUM-style cap exists in the handler.
assertTrue(elapsed > EXPECTED_THRESHOLD_FOR_LARGE_RANGE);
```
Raw gRPC request:
```
IvkDecryptTRC20Parameters {
  startBlockIndex: 0
  endBlockIndex: <currentHead>
  ivk, ak, nk, shieldedTRC20ContractAddress: <valid values>
}
```
Sent repeatedly/concurrently to `WalletSolidityApi` (or `Wallet`) service without authentication; expected (vulnerable) behavior: the call blocks the gRPC thread for a duration proportional to `endBlockIndex - startBlockIndex` with no error returned for the wide range, unlike `getBlockByLimitNext`, which enforces `BLOCK_LIMIT_NUM`.

Note: I was unable to directly inspect the body of `Wallet.scanShieldedTRC20NotesByIvk`/`scanShieldedTRC20NotesByOvk` in `Wallet.java` within the available tool budget to confirm there is no internal range cap; however, a search for `BLOCK_LIMIT_NUM` (the constant used for range-capping elsewhere) returned no matches in `Wallet.java`, and the RPC handler itself performs no range validation, which is consistent with the described vulnerability.

    public void scanShieldedTRC20NotesByIvk(IvkDecryptTRC20Parameters request,

        return;

      byte[] ivk = request.getIvk().toByteArray();
      byte[] ak = request.getAk().toByteArray();
      byte[] nk = request.getNk().toByteArray();

        responseObserver.onNext(

        responseObserver.onError(getRunTimeException(e));
      }
      responseObserver.onCompleted();
    }
