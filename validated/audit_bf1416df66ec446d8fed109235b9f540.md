### Title
Transaction pool `ForkTracker` fork-activation flags are monotonic and never cleared on backward reorg, causing pool admission to diverge from block validity - (File: `crates/transaction-pool/src/validate/eth.rs`)

### Summary
`EthTransactionValidator::on_new_head_block` updates `ForkTracker`'s `AtomicBool` fork-activation flags (`shanghai`, `cancun`, `prague`, `osaka`, `amsterdam`) only in the "activate" direction: each flag is `store(true, ...)` when the new tip's timestamp satisfies the fork condition, but there is no corresponding `else { store(false, ...) }` branch. This mirrors the `traceEnd`-style bug class in the reference report: a state variable meant to track "are we currently past point X" is updated correctly when moving forward but never corrected when the tracked reference point moves backward (a reorg), leaving the pool's notion of "current fork" stale and wrong relative to the actual chain head.

### Finding Description
`on_new_head_block` is invoked whenever the canonical head changes (including on reorgs, see `crates/transaction-pool/src/validate/mod.rs` `TransactionValidator::on_new_head_block`): [1](#0-0) 

Every one of the five hardfork flags is only ever set to `true`; none of them are ever reset to `false`. `tip_timestamp` and `max_initcode_size`/`tx_gas_limit_cap` are unconditionally overwritten with the new tip's values every call, but `max_blob_count` is only updated `if let Some(blob_params) = chain_spec.blob_params_at_timestamp(...)` — i.e., also sticky in the "activated" direction, never lowered.

The flags are read via `ForkTracker::is_*_activated()`: [2](#0-1) 

and consumed inside `EthTransactionValidator`'s transaction-acceptance logic (`validate_one`/`validate_batch`, which check `fork_tracker.is_cancun_activated()`, `is_prague_activated()`, etc. to decide whether EIP-4844 blob transactions, EIP-7702 transactions, and related fields are permitted, and to pick `max_blob_count`).

Because the chain can legitimately reorg backward across a fork boundary (e.g. reorging out several blocks that were built after the Cancun/Prague/Osaka/Amsterdam activation timestamp, back to an ancestor whose timestamp precedes activation — this requires no malicious actor, just normal chain reorg activity near a fork boundary), `on_new_head_block` will be called with a `new_tip_block` whose timestamp is now *before* the fork activation timestamp. `is_cancun_active_at_timestamp(new_tip_block.timestamp())` (and the other fork checks) will now evaluate `false`, but since there is no `else` branch, the `AtomicBool` keeps its previously stored `true` value. The transaction pool therefore continues to believe the (now reorged-away) fork is active on the current chain tip.

### Impact Explanation
This breaks the intended equality between "the pool's admission rules" and "what the current chain head's block-validity rules actually are" — one of the explicitly allowed impact categories ("pool admission diverging from block validity"). Concretely, after a backward reorg across, say, the Prague (EIP-7702) or Cancun (EIP-4844) boundary:
- The pool keeps accepting EIP-7702 or EIP-4844 transactions (and permits the post-fork `max_blob_count`) into the mempool as valid, even though the current canonical tip is pre-fork and a block execution/validator (e.g. `crates/ethereum/consensus/src/lib.rs` `validate_header`, which checks `is_cancun_active_at_timestamp`/`is_prague_active_at_timestamp` against the header timestamp) would reject a block containing such a transaction/type for a block built on top of the reorged (pre-fork) tip.
- This produces pool contents that are inconsistent with what block builders can actually validly include, and can cause transactions to be broadcast/held as "valid" in the pool that would be rejected by consensus-level validation once actually included in a block, and vice versa the pool may retain oversized blob counts that a builder would reject.

### Likelihood Explanation
Requires only an ordinary chain reorg that crosses a hardfork activation timestamp boundary — a scenario that is not attacker-controlled and can occur during normal chain-tip instability around a network upgrade (e.g. validators/proposers momentarily building on both sides of the fork boundary before finality). No malicious peer, RPC caller, or flag is needed; it is a straightforward consequence of `on_new_head_block`'s asymmetric update logic.

### Recommendation
Make every `ForkTracker` update in `on_new_head_block` symmetric: always `store(is_fork_active_at_timestamp(...), ...)` (both `true` and `false` branches) instead of only storing `true`, and likewise recompute (and potentially lower) `max_blob_count` unconditionally from `chain_spec.blob_params_at_timestamp(new_tip_block.timestamp())` rather than only updating it when `Some`.

### Proof of Concept
1. Chain head advances past the Prague activation timestamp; `on_new_head_block` is called with a post-Prague tip, setting `fork_tracker.prague = true`.
2. A deep reorg occurs, replacing the canonical chain with a fork whose new tip's timestamp is before the Prague activation timestamp; `on_new_head_block` is called again with this pre-Prague tip.
3. `chain_spec.is_prague_active_at_timestamp(new_tip_block.timestamp())` now evaluates to `false`, but `fork_tracker.prague` is left as `true` because no `else` branch resets it (`crates/transaction-pool/src/validate/eth.rs` lines 900-924).
4. Subsequent calls to `validate_transaction`/`validate_one` consult `fork_tracker.is_prague_activated()` and continue to accept EIP-7702 transactions (or other Prague-gated transaction properties) into the pool as if Prague were still active on the current (now pre-Prague) chain tip, even though a block built on top of the actual current head would fail header/body validation in `crates/ethereum/consensus/src/lib.rs::validate_header` for containing such fields/types.

    fn on_new_head_block(&self, new_tip_block: &HeaderTy<Evm::Primitives>) {
        // update all forks
        if self.chain_spec().is_shanghai_active_at_timestamp(new_tip_block.timestamp()) {
            self.fork_tracker.shanghai.store(true, std::sync::atomic::Ordering::Relaxed);
        }

        if self.chain_spec().is_cancun_active_at_timestamp(new_tip_block.timestamp()) {
            self.fork_tracker.cancun.store(true, std::sync::atomic::Ordering::Relaxed);
        }

        if self.chain_spec().is_prague_active_at_timestamp(new_tip_block.timestamp()) {
            self.fork_tracker.prague.store(true, std::sync::atomic::Ordering::Relaxed);
