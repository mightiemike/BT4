### Title
Relayer fee for emulated EVM transactions is paid unconditionally, before the underlying action's success/failure is known - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In the Yearn report, a withdrawal that only partially completes still burns the caller's LP-token shares in full while the un-returned underlying tokens are stranded in the provider contract because the code doesn't correlate the state change (share burn) with the actual outcome (amount received). The NEAR Wallet Contract's `inner_rlp_execute` has the same class of flaw: it fires a relayer-fee `Transfer` as an independent, un-chained promise *before* the outcome of the emulated action is known, and never reconciles or reverses that fee if the action later fails.

### Finding Description
`inner_rlp_execute` parses an RLP-encoded Ethereum transaction into a NEAR `Action` plus a `TransactionKind`. For `EOABaseTokenTransfer` and `ERC20Transfer` kinds carrying a non-zero `fee`, it immediately schedules a standalone promise batch to pay the relayer that fee: [1](#0-0) 

This `refund_promise` is created with `env::promise_batch_create` and is **not** `.then()`-chained to (or otherwise made conditional on) the promise that actually performs the emulated transfer/ERC-20 call, which is built and returned separately further down: [2](#0-1) 

The eventual outcome of that main action is only inspected later, in `rlp_execute_callback`. On failure it refunds only the `caller_deposit` (the amount intended for the transfer itself), it does not touch or claw back the relayer fee that was already unconditionally sent out at the start of `inner_rlp_execute`: [3](#0-2) 

So the wallet contract's internal accounting (nonce increment + a single `caller_deposit` refund path) never reconciles against whether the paid-for action actually completed — exactly the "partial completion, no reconciliation" root cause identified in the Yearn report, just expressed as: fee paid out regardless of whether the service (the emulated transfer) was delivered.

### Impact Explanation
Any relayer sending a signed Ethereum-emulation transaction to a NEAR eth-implicit account's Wallet Contract collects the specified fee even when the underlying `EOABaseTokenTransfer`/`ERC20Transfer` action it was paid to execute fails on-chain (e.g., insufficient token balance, receiver storage registration issues, target contract rejecting the call, etc.). This is value leaving the user's (wallet contract) account with no corresponding service rendered and no refund path — a concrete unauthorized value movement out of the wallet-contract account, reachable by any account (including the relayer itself) that can submit an `rlp_execute` call with a non-zero fee and an action designed to fail after the fee promise fires.

### Likelihood Explanation
High reachability: this is triggered by a single `rlp_execute` call by a relayer/meta-transaction sender against any deployed Wallet Contract instance — no special privileges are required. A malicious or merely unlucky relayer relationship (e.g., a transaction that predictably fails, such as an ERC-20 transfer to an unregistered/rejecting receiver, or one racing against insufficient balance) reliably reproduces fee collection without delivering the transfer.

### Recommendation
Chain the fee-payment promise to the main action promise (e.g., attach it via `.then()`/batch it into the same promise, or move the fee transfer into `rlp_execute_callback` and pay it only when `PromiseResult::Successful` is observed for the main action). Alternatively, include the fee in the amount refunded on the `PromiseResult::Failed` branch of `rlp_execute_callback` so the relayer is never paid for an action that did not succeed.

### Proof of Concept
1. A relayer submits `rlp_execute` for an eth-implicit account's Wallet Contract with `tx_bytes_b64` representing an `ERC20Transfer` (or `EOABaseTokenTransfer`) carrying `fee > 0`.
2. `inner_rlp_execute` immediately issues `promise_batch_action_transfer(refund_promise, *fee)` to the relayer (`lib.rs:382-383`), independent of the main promise.
3. The main action promise (e.g., `ft_transfer`/`storage_deposit` chain from `nep_141_storage_balance_callback`, or the direct transfer) subsequently fails — for example, because the token contract rejects the transfer or the receiver cannot be registered.
4. `rlp_execute_callback` observes `PromiseResult::Failed` and refunds only `caller_deposit` (`lib.rs:298-305`); the relayer fee already sent at step 2 is not reclaimed.
5. Net effect: the wallet contract's balance is permanently reduced by `fee` even though the requested action never executed.
