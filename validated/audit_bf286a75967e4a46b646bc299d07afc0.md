### Title
Division-before-multiplication in witness reward/brokerage distribution causes systematic reward accounting loss - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService` computes witness rewards and brokerage splits using floating-point division performed *before* multiplication, mirroring exactly the bug class in the external report (`amount.div(x).mul(y)` instead of `amount.mul(y).div(x)`). This occurs in the core consensus reward-accounting path executed on every produced block.

### Finding Description
In `payReward`, the brokerage cut taken from a witness's block/fee reward is computed as:
```java
double brokerageRate = (double) brokerage / 100;
long brokerageAmount = (long) (brokerageRate * value);
``` [1](#0-0) 

This divides first (`brokerage / 100`) and multiplies afterward, using `double` arithmetic, exactly the "divide-then-multiply" anti-pattern flagged in the report instead of the correct `amount.mul(share).div(totalShare)` order. The same anti-pattern appears in `payStandbyWitness`, where each standby witness's pay-per-vote share is computed via `double eachVotePay = (double) totalPay / voteSum;` then multiplied by `w.getVoteCount()`: [2](#0-1) 

It also appears in the legacy per-cycle reward split, `computeReward(long cycle, List<Pair<byte[], Long>> votes)`, which divides `userVote / totalVote` into a `double voteRate` before multiplying by `totalReward`: [3](#0-2) 

This is notably inconsistent with the rest of the codebase, which elsewhere deliberately uses `BigInteger` `multiply().divide()` ordering to avoid exactly this precision loss (e.g. `RepositoryImpl.calculateGlobalEnergyLimit`, `ResourceProcessor.calculateGlobalLimitV1/V2`, `RewardViCalService`/`VoteRewardUtil` reward-per-vote computations): [4](#0-3) [5](#0-4) 

The `payReward`/`payStandbyWitness` paths are invoked from `payBlockReward` and `payTransactionFeeReward` on every block produced by the network: [6](#0-5) 

### Impact Explanation
Because `brokerage / 100` truncates/rounds in `double` space before being multiplied by the reward `value`, and because `totalPay / voteSum` similarly loses precision before multiplication by each witness's vote count, the split between witness brokerage, voter allowance, and standby-witness pay does not sum exactly to the intended total. This is a systemic, per-block accounting divergence affecting every witness/voter's reward balance (`delegationStore.addReward` / `adjustAllowance`), executed automatically by consensus logic — an asset/accounting-corruption class issue in resource and reward accounting rather than a contract-specific bug, but it is the direct java-tron analog of the reported pattern.

### Likelihood Explanation
This code path executes unconditionally on every block (`payBlockReward`, `payTransactionFeeReward`) and every maintenance cycle (`payStandbyWitness`), so the precision-loss/rounding-order defect is triggered continuously by normal chain operation, not by any privileged or malicious actor action — it requires no special trigger.

### Recommendation
Replace the `double`-based divide-then-multiply computations in `payReward`, `payStandbyWitness`, and the legacy `computeReward(cycle, votes)` with integer/`BigInteger` `multiply().divide()` ordering (multiply first, then divide by the total/denominator), consistent with the pattern already used in `RepositoryImpl`, `ResourceProcessor`, and `RewardViCalService`. Compute the deducted fee via `mul().div()` and derive the remainder by subtraction, rather than performing two independent divide-first calculations.

### Proof of Concept
Given `brokerage = 33` (33%) and `value = 100` sun:
- Correct: `brokerageAmount = value * brokerage / 100 = 100 * 33 / 100 = 33`.
- Current code: `brokerageRate = 33.0/100 = 0.33` (exact here, but for `brokerage` values that are not multiples that divide cleanly, e.g. `brokerage = 1`, `value = 3`) → `brokerageRate = 0.01`, `brokerageAmount = (long)(0.01 * 3) = (long)0.03 = 0`, while `mul-then-div` gives `3*1/100 = 0`. Larger-scale/adversarial `value`/`brokerage` combinations (values near `Long.MAX_VALUE` or fractional-cent-level rounding across millions of blocks) will accumulate divergence between the double-computed brokerage and the exact integer result, causing systematic under/over-payment relative to `value - brokerageAmount` remaining balance in `delegationStore`/`accountCapsule` allowance over time.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
