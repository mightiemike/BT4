### Title
`validateHmac` (admin signator) fails to reject array-valued `hmac`, causing `safeCompare` to throw an uncaught `SafeCompareError` - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`normalizeQuery` in `hmac-validator.ts` only rejects array-valued query parameters when `signator === 'appProxy'`; for the default `'admin'` signator it returns the raw query object unchanged. If `normalizedQuery.hmac` is an array (e.g. `{hmac: ['a','b']}`), the `!normalizedQuery.hmac` guard is bypassed (a non-empty array is truthy), and the array is passed to `safeCompare(hmac as string, localHmac)`, where `typeof hmac === 'object'` versus `typeof localHmac === 'string'`, triggering an uncaught `SafeCompareError` instead of the expected `InvalidHmacError`.

### Finding Description
In `lib/utils/hmac-validator.ts`:
- `normalizeQuery` (lines 118-151) only performs the `Array.isArray` rejection check for `signator === 'appProxy'` [1](#0-0) . For the default `'admin'` signator with a plain (non-`URLSearchParams`) query object, the function just returns the query as-is with no array validation.
- `validateHmac` then checks `!normalizedQuery.hmac` to detect a missing HMAC [2](#0-1) , but a non-empty array like `['a','b']` is truthy, so this check does not catch it.
- The array value is then passed to `safeCompare(hmac as string, localHmac)` [3](#0-2) .
- `safeCompare` explicitly throws `ShopifyErrors.SafeCompareError` when `typeof strA !== typeof strB` [4](#0-3) , which is exactly what happens here (`object` vs `string`).

This is a real inconsistency in the library: it explicitly guards against array-valued params for `appProxy` but omits the equivalent protection for `admin`, so the exported `shopify.utils.validateHmac` function can throw an unhandled internal error type (`SafeCompareError`) instead of the documented/expected `InvalidHmacError` when fed a crafted array value for `hmac`.

However, tracing the actual built-in OAuth callback handler (`lib/auth/oauth/oauth.ts`), the query passed to `validateHmac` is always built via `Object.fromEntries(new URL(request.url, ...).searchParams.entries())` [5](#0-4) . `URLSearchParams` never produces array values for `?hmac[]=a&hmac[]=b` (that key is parsed as literal `hmac[]`, not merged into `hmac`), and `Object.fromEntries` on `.entries()` never nests duplicate keys into arrays — it just keeps the last string value. Therefore the specific attack path through the library's own `oauth.callback()` handler as described in the question (framework `qs`-based array parsing reaching this code) is **not reachable**, since the library does its own URL/query parsing internally rather than relying on the host framework's `req.query`.

The only way to actually reach the vulnerable branch is if an app developer calls `shopify.utils.validateHmac()` directly with a framework-parsed query object (e.g. Express + `qs` producing `req.query.hmac = ['a','b']`) instead of going through the built-in `oauth.callback()`. That is a legitimate call pattern of a public exported API (`shopify.utils.validateHmac`), not solely a "host app bug," since the missing array-check asymmetry is a defect in the library itself.

### Impact Explanation
If reached, the effect is an unhandled `SafeCompareError` thrown instead of a handled `InvalidHmacError`, which could crash the request handler/process for apps that don't explicitly catch `SafeCompareError` (as opposed to catching `ShopifyErrors.InvalidHmacError`), causing a denial-of-service in an authentication-adjacent code path. This matches a low-severity "DoS in auth handler" impact class — it does not enable HMAC/session forgery, since the comparison still fails safe (throws rather than returning `true`); no authentication bypass occurs.

### Likelihood Explanation
Requires an app developer to invoke `shopify.utils.validateHmac()` directly with a raw framework-parsed query object under default `'admin'` signator (not the library's own `oauth.callback()`, which is unaffected because it does its own URL parsing). This is a plausible integration pattern but is not the primary/default code path exercised by `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` (need to confirm how their callback wrappers build the query, which was not fully verified within the available tool budget). No secrets or privileged access are required by the attacker — only crafting a bracketed query parameter, assuming the host framework's query parser produces arrays for that syntax (e.g., Express + `qs`, not the default `querystring` parser).

### Recommendation
In `normalizeQuery` (`lib/utils/hmac-validator.ts`), apply the same array-rejection guard used for `appProxy` uniformly to `hmac`/`signature`/`shop`/`timestamp` regardless of `signator`, throwing `InvalidHmacError` for any array-valued single-value parameter before it reaches `safeCompare`. Additionally, consider having `safeCompare` (or its caller) treat non-string inputs as an automatic `false` result rather than throwing, so that type-confusion inputs fail closed as `InvalidHmacError`/`false` instead of raising an uncaught internal error type.

```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('array-valued hmac causes uncaught SafeCompareError instead of InvalidHmacError', async () => {
  const shopify = shopifyApi(testConfig({apiSecretKey: 'my super secret key'}));

  const query = {
    code: 'some code',
    shop: 'the-shop.myshopify.com',
    state: 'nonce',
    timestamp: String(Math.trunc(Date.now() / 1000) - 60),
    hmac: ['a', 'b'], // simulates req.query.hmac from Express + qs for ?hmac[]=a&hmac[]=b
  };

  // Expected (secure) behavior: rejects with InvalidHmacError
  // Actual behavior: rejects with SafeCompareError (uncaught by callers expecting InvalidHmacError only)
  await expect(shopify.utils.validateHmac(query as any)).rejects.toBeInstanceOf(
    Object, // currently throws ShopifyErrors.SafeCompareError, not InvalidHmacError
  );
});
```
Expected assertion after fix: `rejects.toBeInstanceOf(ShopifyErrors.InvalidHmacError)`.

Note: this PoC targets the public `shopify.utils.validateHmac` API directly; I could not fully verify within the available tool budget whether any of the higher-level authenticate handlers in `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` pass raw framework query objects (rather than re-parsed `URLSearchParams`) into this function, which would be needed to confirm end-to-end reachability from an HTTP request through those packages' auth callback routes.

```typescript
function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }
```

```typescript
  if (typeof strA === typeof strB) {
    const enc = new TextEncoder();
    const buffA = enc.encode(JSON.stringify(strA));

    if (buffA.length === buffB.length) {
```
