## Title
`verify_snapshot_bank` validates the accounts lattice hash *before* `clean_accounts`/`shrink_all_slots` run, then re-checks only the cached (unchanged) hash afterward — corruption introduced by clean/shrink is never detected - (File: `runtime/src/bank.rs`)

### Summary
This is the closest in-scope analog to the H-2 report. The rollup bug is: a value (`prevStateRoot`) is validated at the wrong point in the pipeline (only at `finalizeBatch()`, not at `commitBatch()`), so a batch can be accepted/used for a period during which its true correctness has not actually been checked, enabling exploitation before the mismatch is discovered. In agave's snapshot-load path, `Bank::verify_snapshot_bank` has the same "check the wrong artifact" structure: it verifies the accounts lattice hash against the *pre-clean/pre-shrink* index state, then runs `clean_accounts()` and `shrink_all_slots()` (both of which mutate/reclaim account storage), and only afterward calls `verify_hash()` — but `verify_hash()` recomputes the bank hash from the bank's already-cached `accounts_lt_hash` value (set once during index generation/freeze), not by rescanning the storages as they exist *after* cleaning and shrinking.

### Finding Description
`verify_snapshot_bank()` performs, in order:
1. `verify_accounts()` — compares the bank's stored `accounts_lt_hash` against a hash computed from `calculate_accounts_lt_hash_at_startup_from_index()`, i.e. **before** any cleaning/shrinking of the just-loaded snapshot storages. [1](#0-0) 
2. `clean_accounts(Some(latest_full_snapshot_slot), true)` — purges old/zero-lamport account versions and reclaims storage. [2](#0-1) 
3. `shrink_all_slots(true, Some(self.slot()))` — compacts storages, physically rewriting/removing dead account bytes. [3](#0-2) 
4. `verify_hash()` — the *only* check performed after clean/shrink — but this does not rescan storages; it recomputes `hash_internal_state()` using the bank's already-frozen `accounts_lt_hash` field, which was fixed at freeze time via `finish_accounts_lt_hash_updates()` and is explicitly documented as not to be mutated again (`rehash()` comment: "Note that the account state is *not* allowed to change by rehashing"). [4](#0-3) [5](#0-4) 

The design intent (per the comment at line 5647-5650) is that clean/shrink must not be allowed to alter the accounts hash, and the ordering exists specifically "because we are about to perform an accounts hash calculation *up to that slot*" — i.e., the authors assume clean/shrink are pure no-ops with respect to the lattice hash and therefore do not need to be re-verified. This is structurally identical to the rollup bug's flawed assumption ("a sequencer can only win challenges if the batch is valid") — a correctness invariant is assumed to always hold post-mutation instead of being re-checked against the actual resulting state. If `clean_accounts` or `shrink_all_slots` contains a bug (e.g., in `collect_reclaims`, `update_candidate_after_reclaims`, `select_pubkeys_to_store`, or the zero-lamport single-ref/tombstone gating logic seen in `test_clean_purges_zero_lamport_single_ref_at_reclaim` and `test_accounts_clean_after_snapshot_restore_then_old_revives`) that incorrectly reclaims a live account or fails to purge/resurrects a stale one, `verify_snapshot_bank()` returns `true` regardless, because the only post-mutation check (`verify_hash`) never re-derives the hash from the mutated storages — it compares the cached value to itself. [6](#0-5) [7](#0-6) 

The two call sites (`bank_from_snapshot_archives` and `bank_from_snapshot_dir`) treat `verify_snapshot_bank()`'s boolean result as the definitive correctness gate before the bank is handed back to `bank_forks_utils::try_load_bank_forks_from_snapshot` and ultimately installed as `BankForks`'s root bank used for RPC and further replay. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
If clean/shrink silently corrupts account state during snapshot load (a bug class explicitly guarded against elsewhere in the codebase via test coverage of tombstones and zero-lamport single-ref accounts, indicating this is a recognized area of fragility), the validator would boot with a bank whose in-memory/on-disk account state diverges from the value it believes is verified, yet `verify_snapshot_bank()` reports success. This is a silent honest-node snapshot-vs-replay/hash divergence: the node proceeds to serve RPC reads and replay subsequent slots from storage that was never actually re-validated post-clean/shrink, risking either (a) stale/wrong account data being served or used in transaction execution, or (b) a subsequent bank-hash mismatch/panic much later (when the corrupted account is next touched and hashed), long after the root cause (clean/shrink) has executed and any diagnostic context is gone.

### Likelihood Explanation
This requires a latent defect in `clean_accounts`/`shrink_all_slots` reclaim logic to actually trigger; it is not exploitable by an unprivileged network actor directly, but the surrounding verification code gives **no defense-in-depth** if such a defect exists — the entire class of clean/shrink correctness is unguarded by the "verify" step whose name and placement (after clean/shrink) implies it does verify the effect of those operations. This is a genuine design/ordering weakness in the AccountsDb snapshot-verification path rather than a theoretical concern, since clean and shrink are exactly the accounts-lattice-hash-affecting operations the surrounding comment worries about, yet only the pre-mutation state is what gets hashed and compared.

### Recommendation
After `clean_accounts()` and `shrink_all_slots()` run in `verify_snapshot_bank()`, recompute the accounts lattice hash from the (mutated) accounts index/storages and compare it against the previously-verified value, rather than relying solely on `verify_hash()`'s reuse of the pre-mutation cached `accounts_lt_hash`. Equivalently, move the `verify_accounts()` call to occur *after* clean and shrink so it actually validates the state that will be used going forward, mirroring the fix recommended for the rollup bug ("check `prevStateRoot` where the state is actually used/finalized, not only earlier").

### Proof of Concept
No concrete PoC was constructed; this analysis relies on static review of `runtime/src/bank.rs::verify_snapshot_bank` and `runtime/src/bank.rs::verify_hash`/`rehash` and the ordering of clean/shrink/verify calls, plus the existing test suite (e.g. `runtime/src/serde_snapshot/tests.rs::test_accounts_clean_after_snapshot_restore_then_old_revives`, `accounts-db/src/accounts_db/tests/impl.rs::test_clean_purges_zero_lamport_single_ref_at_reclaim`) which demonstrate how fragile/edge-case-heavy the clean/tombstone/zero-lamport reclaim logic already is — precisely the logic whose correctness is never re-validated by `verify_snapshot_bank()`. I was unable to locate an actual triggerable bug inside `clean_accounts`/`shrink_all_slots` within the indexed portion of the codebase to build a full end-to-end PoC (some file contents may be excluded from the index); a Devin session with full repository access would be needed to attempt to construct or rule out a concrete reclaim-logic defect that this verification gap would fail to catch.
