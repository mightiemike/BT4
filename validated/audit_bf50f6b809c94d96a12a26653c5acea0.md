### Title
Sensitive state-mutating admin JSON-RPC methods (`batchProver_setCommitments`, `sequencer_haltCommitments`, `sequencer_resumeCommitments`, `batchProver_pauseProving`) bypass the `Auth` middleware entirely - (File: crates/common/src/rpc/auth.rs)

### Summary
The Sherlock report's root cause pattern is "a critical value-affecting operation with no protective check before it executes." The equivalent pattern in this codebase is the `Auth` RPC middleware, which is supposed to gate privileged, state-mutating RPC calls but only actually checks an allowlist of three backup-related methods. Every other RPC method — including several that directly mutate consensus-critical ledger state such as sequencer commitments and proving control — is let through with zero authentication, regardless of whether an `api_key` is configured.

### Finding Description
`Auth::call` in [1](#0-0)  only requires an API key for methods present in `PROTECTED_METHODS`, which is hard-coded to `["backup_create", "backup_validate", "backup_info"]`. Any other method name falls through the `if !PROTECTED_METHODS.contains(&method)` branch and is dispatched to the inner service without ever checking `api_key`.

Meanwhile, the batch-prover exposes `batchProver_setCommitments`, which directly overwrites the ledger's canonical sequencer-commitment records (`put_commitment_by_index`, `put_commitment_index_by_l1`, `put_prover_pending_commitment`) with attacker-supplied merkle roots, indices and L2 end-heights, with the docstring itself warning "It overrides the commitment already if exists, so use with caution": [2](#0-1) 

The sequencer likewise exposes `sequencer_haltCommitments` / `sequencer_resumeCommitments`, which can stop or resume the sequencer's commitment-posting pipeline via a plain RPC call: [3](#0-2) 

None of these methods are in `PROTECTED_METHODS`, so they are reachable by anyone who can open a connection to the node's JSON-RPC port, with no `api_key` and no other authorization check performed anywhere in the call path (`create_rpc_module` / `register_rpc_methods` do not add per-method guards).

### Impact Explanation
This matches the specified High-impact class directly: "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`." Concretely:
- `batchProver_setCommitments` lets an unauthenticated caller inject or override the batch prover's local view of sequencer commitments (arbitrary merkle root / index / l2_end_block_number), which feeds directly into what gets proven and submitted to L1 as a batch proof, corrupting the prover's local state and its subsequent proof outputs.
- `sequencer_haltCommitments` / `sequencer_resumeCommitments` let an unauthenticated caller stop the sequencer from posting commitments to L1, stalling L2 finality (nothing gets marked "committed"/"proven" per [4](#0-3) ) or resume it at will, i.e. remote control of consensus-critical liveness with no credentials.

### Likelihood Explanation
The `Auth` middleware is applied uniformly to the JSON-RPC server via `layer_fn` in `start_rpc_server` [5](#0-4) , giving the appearance that all sensitive endpoints are protected by the configured `api_key`. In reality only the three `backup_*` methods are covered — this is a straightforward allowlist gap, not something requiring special access beyond network connectivity to the RPC port. Exploitability further depends on whether the RPC port is reachable (mainnet full-node config binds `0.0.0.0:8080` by default per [6](#0-5) , though I could not fully confirm the default `bind_host` for the sequencer/batch-prover binaries specifically within the available iterations — this should be verified before treating the finding as remotely exploitable in every deployment topology).

### Recommendation
Change `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs` to a denylist-by-default or explicit inclusion of all state-mutating/administrative methods (`batchProver_setCommitments`, `batchProver_prove`, `batchProver_submitFakeProof`, `batchProver_pauseProving`, `batchProver_retryProvingJob`, `sequencer_haltCommitments`, `sequencer_resumeCommitments`, and any other write RPCs), or invert the logic so any method not explicitly marked "public" requires the API key.

### Proof of Concept
1. Start a batch-prover node with `rpc.api_key` configured (or unset).
2. Without supplying any API key parameter, call `batchProver_setCommitments` with an attacker-chosen `SequencerCommitmentRpcParam` (arbitrary `merkle_root`/`index`/`l2_end_block_number`), as exercised functionally (with legitimate intent) in the test helper: [7](#0-6) .
3. Observe the call succeeds and overwrites `ledger_db` commitment state per [2](#0-1) , confirming no authentication was required, unlike the intended behavior implied by the presence of the `Auth` middleware.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }

        let Some(api_key) = api_key else {
            return Box::pin(async move {
                MethodResponse::error(
                    req.id().clone(),
                    ErrorObjectOwned::owned(401, "Cannot access protected method", None::<String>),
                )
            });

A sequence of continuous sequencer commitments up to an L2 block height marks that height as "committed". If there are valid batch proofs covering every sequencer commitment in that chain, the final L2 block in that sequence is marked as "proven".

L2 block finality is defined relative to each L1 block height: at the end of an L1 block, a specific L2 block is marked as committed and another as proven. The committed height is always less than or equal to the proven height.
