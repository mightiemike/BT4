### Title
Unauthenticated "bootstrap declare" bypass skips `__validate_declare__`, fee enforcement, and declarer whitelist for any declare transaction - (File: crates/starknet_api/src/executable_transaction.rs)

### Summary
`DeclareTransaction::is_bootstrap_declare` and its use in `AccountTransaction::execute_raw` (blockifier) and in the Starknet OS Cairo re-execution (`execute_declare_transaction`) grant a complete bypass of account validation, fee charging, and nonce enforcement for any declare transaction whose `sender_address` equals the fixed magic constant `bootstrap_address()`, `nonce == 0`, and the transaction's fee is not charged. The check is evaluated purely from transaction fields — it is not gated on the chain being at genesis / block 0, nor tied to any authenticated "is this really the bootstrap flow" signal. This mirrors the vantage6 bug class: a special, attacker-controllable field (`parent_id` there, `sender_address`/fee-zero here) is trusted to skip a security-critical check (image whitelist there, account validation + declarer whitelist here) instead of the check being derived from a value the node itself computed/verified.

### Finding Description
`is_bootstrap_declare` is defined as a pure predicate over transaction fields, with no state lookup at all: [1](#0-0) 

It is consumed in the blockifier's execution path unconditionally, before any pre-validation (nonce/fee) or `__validate_declare__` call is performed: [2](#0-1) 

The same bypass is mirrored in the Starknet OS Cairo re-execution logic, again gated only on `sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, and `max_possible_fee == 0` — with no genesis/block-height precondition: [3](#0-2) 

Because `charge_fee` is derived from `enforce_fee(tx, only_query)`, which is `true` only if `resource_bounds.max_possible_fee(tip) > Fee(0)`: [4](#0-3) 

an attacker who can get a declare transaction executed with `sender_address = bootstrap_address()`, `nonce = 0`, and resource bounds whose max possible fee is `0` triggers the bypass at **any** point in the chain's life, not just genesis. In this branch:
- `__validate_declare__` is never invoked (no signature/authorization check of any kind for the `sender_address`, which is a non-existent/uncontrolled address — there is no account contract deployed there).
- `check_and_increment_nonce` is never called, so the same tx can be resubmitted from the mempool if it fails.
- The gateway's `authorized_declarer_accounts` whitelist (the actual "declarer whitelist" analog to vantage6's algorithm whitelist) is a config-level allow-list: [5](#0-4) 
but nothing in the bootstrap-declare code path re-derives or re-checks this whitelist against the class being declared; the bypass happens purely in the blockifier/OS execution layer based on attacker-supplied transaction fields.

The project's own test/integration fixtures show that this "bootstrap declare" is meant to be sent through the exact same `RpcTransaction::Declare` path as ordinary user declares — there is no separate privileged submission channel: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a declare transaction with `sender_address = bootstrap_address()`, `nonce = 0` and a max-possible-fee of `0` can be admitted by the gateway/mempool and picked up for block building at any height (not just genesis), then:
- Any external transaction sender can declare arbitrary Sierra/CASM classes for free, repeatedly (differing only by `class_hash`), with zero signature/account verification and without paying gas — a direct fee-bypass / resource-accounting violation.
- The `authorized_declarer_accounts` whitelist restriction configured by an operator can be circumvented entirely for this special address, since the whitelist check (wherever enforced in the gateway) is not part of the bootstrap-skip code path in the blockifier/OS execution, i.e., a non-whitelisted "declarer" gets an unauthorized declare admitted through a trusted special-case path — the precise bug-class analog to vantage6's `parent_id`-based whitelist bypass.
- Because the state changes made in this path (`dict_update` on `contract_class_changes`) are still committed to state and reflected by the Starknet OS re-execution, this could cause the sequencer to commit a wrong state root / diverge from honest re-execution assumptions if the check is exploitable outside the intended genesis-only usage.

### Likelihood Explanation
The predicate is evaluated unconditionally from transaction fields with no state-based gating (no check that the current block/state is still pre-genesis, no check that no bootstrap declare has already run). The only gating mechanisms that could prevent exploitation outside genesis are: (1) gateway-level resource-bounds validation (`validate_resource_bounds` in `StatelessTransactionValidator`, which by default rejects zero resource bounds) and (2) whatever additional runtime code (not identified in the available index) restricts admission of `sender_address == bootstrap_address()` transactions to genesis only. I was not able to fully confirm, within the indexed code, whether such a gate exists elsewhere in the gateway/mempool/batcher pipeline that prevents this transaction from being admitted at non-zero block heights. This is a genuine gap in my verification — a background Devin session with full repository access would be needed to trace every call site that constructs `AccountTransaction`/`ExecutionFlags::charge_fee` for regular mempool-sourced transactions (as opposed to test-only helpers like `AccountTransaction::new_for_sequencing` used in `test_bootstrap_declare`) to determine definitively whether `charge_fee=false` combined with `sender_address=bootstrap_address()` and `nonce=0` is reachable from an ordinary externally-submitted RPC transaction post-genesis.

### Recommendation
Restrict the bootstrap-declare bypass so it can only trigger when the chain state is unambiguously at genesis (e.g., require `latest_block_number` to be `None`/0 as tracked by `SyncStateReaderFactory`, not merely by inspecting transaction fields), and enforce this restriction in both the blockifier (`account_transaction.rs`) and the Starknet OS Cairo hints so that re-execution and live execution cannot diverge. Additionally, ensure `authorized_declarer_accounts` (and any per-class whitelist) is checked before the bootstrap short-circuit, not only in a code path that this special case skips.

### Proof of Concept
Conceptual PoC (pending confirmation of gateway-level admission, see Likelihood section):
1. Craft an `RpcTransaction::Declare` (V3) with `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`), `nonce = 0`, and `resource_bounds` such that `max_possible_fee(tip) == 0` (as used by `ValidResourceBounds::create_for_testing_no_fee_enforcement()` in test utilities): [6](#0-5) 
2. Submit through the ordinary gateway `add_tx` RPC path used for user declares.
3. If admitted and scheduled for execution, `AccountTransaction::execute_raw` detects `is_bootstrap_declare` and declares the class without ever invoking `__validate_declare__`, without charging fee, and without incrementing the sender's nonce: [8](#0-7) 
4. Repeat with a different `class_hash` to declare arbitrary classes for free at will, independent of `authorized_declarer_accounts` configuration.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
