### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a divergent authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling to confirm that a locally re-executed transaction output matches the trusted, previously-committed `TransactionInfo` for that version. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried by `TransactionInfoV1`. This is acknowledged in-code as a `TODO`, but the gap is real today and affects any caller of this function, not just the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event-root hash, then returns `Ok(())` without ever reading `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`. These three fields are exactly the fields that bind a `TransactionInfo` to the durable Merkle state root(s) computed by `DoStateCheckpoint` (main state, hot state, and native-position state) — see how they are produced in [2](#0-1)  and threaded into the committed `TransactionInfoV1` via [3](#0-2) , and are exposed on `TransactionInfo` at [4](#0-3) .

Every consumer of this comparator treats a returned `Ok(())` as proof that local execution reproduced the authenticated ledger state for that version:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` calls it per transaction to decide pass/fail for `replay-verify` [5](#0-4) .
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`'s `print_mismatches` relies on it to report execution mismatches [6](#0-5) .
- `aptos-move/cli/src/commands.rs` uses it to confirm a replayed system transaction matches the on-chain record before reporting success to a CLI operator [7](#0-6) .

Because the checkpoint hashes are skipped, a discrepancy between the locally-computed state/hot-state/position-state root and the value actually committed on-chain in `TransactionInfoV1` is silently accepted as a match. The code comment itself states the exact consequence: [8](#0-7) .

Note the comment frames this as needing to be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" for the `position_state_checkpoint_hash` case, but `state_checkpoint_hash` and `hot_state_checkpoint_hash` are unconditionally skipped as well — these are not gated behind an unreleased feature; `state_checkpoint_hash` is present on `TransactionInfoV0`/`V1` today and `hot_state_checkpoint_hash` is gated only by `HOT_STATE_ROOT_IN_TXN_INFO`.

### Impact Explanation
This function is a proof/verification-integrity gate, not part of consensus itself: it does not corrupt state during normal commit, since the executor's own `DoStateCheckpoint`/`DoLedgerUpdate` pipeline computes and commits the checkpoint hashes independently of this comparator. The impact is confined to tooling that is explicitly relied on to detect divergence after the fact — `replay-verify`, the debugger, and the CLI's transaction-replay comparison. If a bug elsewhere causes locally re-executed state (main state root, hot-state root, or native-position root) to diverge from what was actually committed to the chain, these tools would report a false "match"/success, masking a real state-integrity divergence instead of surfacing it. This weakens the primary safety net used to catch hard-fork-class state divergence, which is a legitimate but secondary-order impact (it doesn't itself write wrong state, it hides detection of wrong state).

### Likelihood Explanation
The gap is unconditionally present in code today (not hidden behind a disabled flag) for `state_checkpoint_hash` and `hot_state_checkpoint_hash`, and the `position_state_checkpoint_hash` gap is explicitly called out by the developers as a pre-condition to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. Triggering the missed-detection scenario requires an independent root-hash-computation bug elsewhere to exist first — this finding does not itself corrupt any committed data, it only removes a verification cross-check. That reduces standalone severity: it is a proof/detection gap rather than a primary state-corruption bug.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally-recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/`Some`) against `txn_info`'s corresponding fields, mirroring the existing `ensure!` pattern used for `state_change_hash` and `event_root_hash`.

### Proof of Concept
1. Enable (or simulate) `HOT_STATE_ROOT_IN_TXN_INFO`/`TRANSACTION_INFO_V1` such that committed `TransactionInfo` is `V1` with a non-`None` `hot_state_checkpoint_hash`.
2. Introduce (or have present) a bug in hot-state-root computation on the replay/verification node so the locally recomputed `hot_state_checkpoint_hash` differs from the one embedded in the on-chain `TransactionInfoV1`.
3. Run `storage/db-tool/src/replay_on_archive.rs`'s verifier (or the CLI's transaction-replay comparison) over that version range.
4. Observe `ensure_match_transaction_info` returns `Ok(())` because it never inspects `hot_state_checkpoint_hash`/`state_checkpoint_hash`/`position_state_checkpoint_hash`, so `replay-verify`/debugger reports success despite the divergent, authenticated state root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
