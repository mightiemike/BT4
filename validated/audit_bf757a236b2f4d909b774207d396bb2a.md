### Title
Client-side `proof_facts` become permanently invalid on protocol upgrade, causing fee loss / stuck mempool transactions - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
The virtual-OS "proof_facts" mechanism lets an Invoke V3 sender attach an off-chain-generated proof binding a transaction to a specific `base_block_number`/`base_block_hash`, `virtual_os_config_hash`, `program_hash`, and `proof_version`. This proof is expensive to compute off-chain and is validated both in `AccountTransaction::validate_proof_facts` (mempool/gateway pre-validation) and again in the Starknet OS's `check_proof_facts` (block-building re-validation). Because the acceptance criteria (`allowed_virtual_os_program_hashes`, `allowed_proof_versions`, and `virtual_os_config_hash`) are versioned constants that change across protocol upgrades, a transaction admitted to the mempool with a valid proof can become permanently invalid if the sequencer upgrades `VersionedConstants` before the transaction is sequenced — an exact structural analog of the reported "merkle root changes invalidate pending proofs" bug class.

### Finding Description
`AccountTransaction::validate_proof_facts` [1](#0-0)  checks that:
1. `snos_proof_facts.proof_version` is in `os_constants.allowed_proof_versions`,
2. `snos_proof_facts.program_hash` is in `os_constants.allowed_virtual_os_program_hashes`,
3. the referenced `proof_block_hash`/`proof_block_number` match on-chain stored state via `validate_proof_block_hash`/`validate_proof_block_number` [2](#0-1) ,
4. the computed `virtual_os_config_hash` from the current `BlockContext` equals the proof's embedded `config_hash` [3](#0-2) .

The same set of checks is re-executed at actual block-sequencing time inside the Starknet OS Cairo program, `check_proof_facts`, which validates `program_hash`, `proof_version`, and `virtual_os_config_hash` against the current protocol constants [4](#0-3) .

`allowed_virtual_os_program_hashes`, `allowed_proof_versions`, and the parameters feeding `virtual_os_config_hash` are part of `OsConstants`, which are versioned and change from one protocol version to another (evidenced by the diff regressions showing these fields changing value at every version bump, e.g. `0.14.1`→`0.14.2` and `0.14.2`→`0.14.3`) [5](#0-4) [6](#0-5) . A dedicated regression test even exists to guard against exactly this drift for fixtures: `proof_flow_program_hash_is_allowed`, whose comment explicitly states "Guards against drift between the virtual-OS program hash baked into the proof-flow fixtures and the `allowed_virtual_os_program_hashes` list in the latest versioned constants. If the hash is no longer allowed, the proof fixtures must be regenerated." [7](#0-6) 

This mirrors the reported bug class precisely: a client generates an expensive off-chain artifact (relayer-fee-funded `xcall`/merkle proof in the original report; here a client-side virtual-SNOS proof) bound to a specific on-chain "root" (merkle root there; `program_hash`/`proof_version`/`virtual_os_config_hash` here). If that binding value changes while the transaction is in flight (admitted to the mempool, awaiting sequencing), the previously-valid proof is rejected with `InvalidProofFacts`, and the transaction — and the resources/fees the user already committed to generate the proof and pay for gas/tip — are lost.

### Impact Explanation
Since `allowed_virtual_os_program_hashes`/`allowed_proof_versions`/config-hash-affecting fields can change between blocks when the sequencer activates a new protocol version (this is a normal, expected sequencer-controlled event, not a malicious action), any Invoke V3 transaction sitting in the mempool with an already-computed, previously-accepted client-side proof becomes permanently unexecutable the moment the new version activates. The client has already paid the (often significant, given the `stwo_proving`/recursive-proof machinery referenced in `starknet_transaction_prover`) cost of generating the virtual-SNOS proof, and the transaction will now deterministically fail `validate_proof_facts` pre-validation (or the equivalent OS check) forever, since a resubmission would require regenerating the entire proof against a now-current config hash and allowed program hash. This is a concrete loss of funds/resources for an unprivileged transaction sender reachable purely by submitting a normal Invoke V3 transaction with `proof_facts` and having the sequencer's protocol version legitimately change while the tx is pending — no privileged/malicious actor required.

### Likelihood Explanation
Protocol version upgrades (which bump `allowed_virtual_os_program_hashes`/`allowed_proof_versions` and other os_constants affecting `virtual_os_config_hash`) are a routine, expected sequencer operational event that has occurred at essentially every listed version bump in the resource fixtures. Any client using the "client-side proof" feature (`has_client_side_proof`) whose transaction remains in the mempool across such an upgrade boundary will hit this deterministically. Likelihood is Medium: it requires the sender to use the proof_facts feature and for their transaction to still be pending when the protocol version transitions, but given real deployments actively track/rotate these constants across versions, the window is real and not contrived.

### Recommendation
- Allow a grace/compatibility window during which both the previous and newly-activated `allowed_virtual_os_program_hashes`/`allowed_proof_versions`/config hash are accepted for already-mempool-admitted transactions, similar to how `STORED_BLOCK_HASH_BUFFER` is already used to guarantee block-hash immutability for `proof_block_hash`.
- Alternatively, have the gateway/mempool proactively evict and clearly report (rather than silently invalidate at inclusion time) transactions whose proof_facts reference constants that are about to be retired, so users can be informed before wasting further proving resources.
- Consider decoupling `virtual_os_config_hash` from fields that change on every routine version bump, so that only backward-incompatible protocol semantics actually invalidate previously-generated client proofs.

### Proof of Concept
1. A user calls `starknet_transaction_prover`'s `VirtualSnosProver` to generate an off-chain virtual-SNOS proof/`proof_facts` for their Invoke V3 transaction, bound to the currently active `os_constants.allowed_virtual_os_program_hashes[0]` and `virtual_os_config_hash` (see `virtual_snos_prover.rs::prove_transaction`) [8](#0-7) .
2. The user submits the Invoke V3 transaction with these `proof_facts` to the gateway; `AccountTransaction::validate_proof_facts` passes because the currently active `BlockContext.versioned_constants.os_constants` matches the proof (`allowed_virtual_os_program_hashes`, `allowed_proof_versions`, `virtual_os_config_hash`) [9](#0-8) .
3. The transaction sits in the mempool. Before it is sequenced, the sequencer activates a new protocol version, updating `allowed_virtual_os_program_hashes`/`allowed_proof_versions`/config-hash-affecting constants (as demonstrated by the version-to-version diffs `0.14.1_0.14.2.txt`/`0.14.2_0.14.3.txt` changing exactly these fields) [10](#0-9) .
4. When the transaction is finally picked for sequencing/validated again, `validate_proof_facts` (or the OS's `check_proof_facts`) now runs against the new `BlockContext`; `program_hash`/`proof_version` is no longer in the allowed lists or `virtual_os_config_hash` mismatches, causing `TransactionPreValidationError::InvalidProofFacts` [11](#0-10) ; the transaction is rejected and the previously generated (expensive) client-side proof is now permanently unusable.

    fn validate_proof_block_number(
        proof_block_number: u64,
        current_block_number: BlockNumber,
    ) -> TransactionPreValidationResult<()> {
        // Proof block must be old enough to have a stored block hash.
        // Stored block hashes are guaranteed only up to: current - STORED_BLOCK_HASH_BUFFER.
        let max_allowed =
            current_block_number.0.checked_sub(STORED_BLOCK_HASH_BUFFER).ok_or_else(|| {
                TransactionPreValidationError::InvalidProofFacts(format!(
                    "The current block number {current_block_number} is below the required \
                     block-hash retention buffer: {STORED_BLOCK_HASH_BUFFER}."
                ))
            })?;

        if proof_block_number > max_allowed {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "The proof block number {proof_block_number} is too recent. The maximum allowed \
                 block number is {max_allowed}."
            )));
        }

        Ok(())
    }

    fn validate_proof_block_hash(
        proof_block_hash: Felt,
        proof_block_number: u64,
        os_constants: &OsConstants,
        state: &mut dyn State,
    ) -> TransactionPreValidationResult<()> {
        if proof_block_hash == Felt::ZERO {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Proof block hash is zero for block {proof_block_number}."
            )));
        }

        // Compare the proof's block hash with the stored block hash.
        let block_hash_contract_address =
            os_constants.os_contract_addresses.block_hash_contract_address();

        let stored_block_hash = state
            .get_storage_at(block_hash_contract_address, StorageKey::from(proof_block_number))?;

        if stored_block_hash != proof_block_hash {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Block hash mismatch for block {proof_block_number}. Proof block hash: \
                 {proof_block_hash}, stored block hash: {stored_block_hash}."
            )));
        }

        Ok(())
    }

    fn validate_proof_facts(
        &self,
        block_context: &BlockContext,
        state: &mut dyn State,
    ) -> TransactionPreValidationResult<()> {
        // Only Invoke V3 transactions can carry proof facts.
        let Transaction::Invoke(invoke_tx) = &self.tx else {
            return Ok(());
        };
        if invoke_tx.version() < TransactionVersion::THREE {
            return Ok(());
        }

        // Parse proof facts.
        let proof_facts = invoke_tx.proof_facts();
        let snos_proof_facts = match ProofFactsVariant::try_from(&proof_facts)
            .map_err(|e| TransactionPreValidationError::InvalidProofFacts(e.to_string()))?
        {
            ProofFactsVariant::Empty => return Ok(()),
            ProofFactsVariant::Snos(snos_proof_facts) => snos_proof_facts,
        };
        let os_constants = &block_context.versioned_constants.os_constants;

        if !os_constants.allowed_proof_versions.contains(&snos_proof_facts.proof_version.as_felt())
        {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Proof version {} is not allowed under this protocol version.",
                snos_proof_facts.proof_version
            )));
        }

        // Validate the program hash.
        let allowed = &os_constants.allowed_virtual_os_program_hashes;
        if !allowed.contains(&snos_proof_facts.program_hash) {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS program hash {} is not allowed",
                snos_proof_facts.program_hash
            )));
        }

// Validates that the proof facts of an invoke transaction are of a valid virtual OS run.
func check_proof_facts{range_check_ptr, contract_state_changes: DictAccess*}(
    proof_facts_size: felt,
    proof_facts: felt*,
    current_block_number: felt,
    virtual_os_config_hash: felt,
) {
    if (proof_facts_size == 0) {
        return ();
    }

    assert_le(ProofHeader.SIZE + VirtualOsOutputHeader.SIZE, proof_facts_size);

    // Validate the proof header.
    static_assert ProofHeader.SIZE == 3;
    let proof_header = cast(proof_facts, ProofHeader*);
    assert proof_header.proof_variant = VIRTUAL_SNOS;
    assert is_program_hash_allowed(proof_header.program_hash) = TRUE;
    // Only proof version V1 is accepted.
    with_attr error_message("Unsupported proof version") {
        assert proof_header.proof_version = PROOF_VERSION_V1;
    }

    // Validate the virtual OS output header.
    let os_output_header = cast(&proof_facts[ProofHeader.SIZE], VirtualOsOutputHeader*);

    with_attr error_message("Virtual OS output version is not supported") {
        assert os_output_header.output_version = VIRTUAL_OS_OUTPUT_VERSION;
    }

    // Validate that the proof facts block number is not too recent.
    // (This is a sanity check - the following non-zero check ensures that the block hash is
    // not trivial).
    assert_nn_le(
        os_output_header.base_block_number, current_block_number - STORED_BLOCK_HASH_BUFFER
    );
    // Not all block hashes are stored in the contract; Make sure the requested one is not trivial.
    assert_not_zero(os_output_header.base_block_hash);

    // validate that the proof facts block hash is the true hash of the proof facts block number.
    read_block_hash_from_storage(
        block_number=os_output_header.base_block_number,
        expected_block_hash=os_output_header.base_block_hash,
    );

    // validate that the proof facts config hash is the true hash of the OS config.
    assert os_output_header.starknet_os_config_hash = virtual_os_config_hash;

    return ();
}

    /// Proves a transaction on top of the specified block.
    ///
    /// This method:
    /// 1. Validates and extracts the invoke transaction.
    /// 2. Optionally awaits an external blocking check (with timeout) before proving.
    /// 3. Runs the Starknet OS and generates a proof via `prove_virtual_snos_run`.
    #[instrument(skip(self, transaction), fields(block_id = ?block_id, tx_hash))]
    pub async fn prove_transaction(
        &self,
        block_id: BlockId,
        transaction: RpcTransaction,
    ) -> Result<ProveTransactionResult, VirtualSnosProverError> {
        let start_time = Instant::now();

        // Validate block_id is not pending.
        if matches!(block_id, BlockId::Pending) {
            return Err(VirtualSnosProverError::ValidationError(
                "Pending blocks are not supported; only finalized blocks can be proven."
                    .to_string(),
            ));
        }

        let invoke_v3 = extract_rpc_invoke_tx(transaction.clone())?;
        validate_transaction_input(&invoke_v3, self.validate_zero_fee_fields)?;
        let invoke_tx = InvokeTransaction::V3(invoke_v3.into());

        let result = match &self.blocking_check_client {
            None => self.run_and_prove(block_id, vec![invoke_tx]).await?,
            Some(client) => {
                self.prove_with_blocking_check(client, block_id, transaction, invoke_tx).await?
            }
        };

        info!(total_duration_ms = %start_time.elapsed().as_millis(), "prove_transaction completed");
        Ok(result)
    }
