### Title
Delayed-receipt validation failure permanently halts chunk application (chain-wide DoS via a single unprocessable receipt) - ([File: runtime/runtime/src/lib.rs])

### Summary
`process_delayed_receipts` treats a `validate_receipt` failure on a popped delayed receipt as a hard `RuntimeError::StorageError(StorageError::StorageInconsistentState)`, which propagates out of `Runtime::apply` without committing any of the current chunk's work, and which the node then turns into a `panic!` in `chain/chain/src/runtime/mod.rs`. Because the failing receipt is never actually removed from persistent state (nothing is committed), every subsequent attempt to apply this shard's chunk re-encounters the same receipt and panics again — an unrecoverable, chunk-triggered chain halt. This mirrors the `BulkCreateUnstakes` bug class: a conflict/validation error on one queued item hard-aborts the whole batch instead of being skipped/logged, and the offending item keeps coming back forever.

### Finding Description
`Runtime::process_delayed_receipts` pops receipts from the persistent delayed-receipt queue and re-validates them before execution: [1](#0-0) 

If `validate_receipt` fails, the error is converted into `StorageError::StorageInconsistentState` and returned via `?`, aborting `process_delayed_receipts`, `process_receipts`, and ultimately `Runtime::apply` for the whole chunk — no state is committed for this chunk at all.

The caller, `chain/chain/src/runtime/mod.rs`, maps `RuntimeError::StorageError` to `Error::StorageError`: [2](#0-1) 

That `Error::StorageError` then reaches `apply_chunk`, which explicitly panics for any `StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue`: [3](#0-2) 

Because the offending receipt was popped from the in-memory `state_update` but that update is never committed (the error is raised before `validate_apply_state_update`/`state_update.commit()`), the receipt remains at the head of the shard's delayed-receipt queue in the persisted trie. Every node that attempts to apply this chunk — and every retry after a crash/restart — will pop the same receipt, fail the same validation, and panic again. This is a permanent, receipt-triggered halt of that shard (and, transitively, of block/chunk production for the chain), exactly analogous to the reported `BulkCreateUnstakes` DoS where a conflicting record that is never deleted keeps re-triggering the hard failure on every processing pass.

The reachability path from an ordinary transaction/contract call is: any receipt whose gas/compute usage causes it to overflow the current chunk's `compute_limit` or proof-size limit is pushed onto the persistent delayed queue for later processing (`process_local_receipts`/`process_incoming_receipts`). `ValidateReceiptMode::ExistingReceipt` is intentionally "less strict" than `ValidateReceiptMode::NewReceipt` specifically to tolerate legacy/oversized receipts, precisely because there has historically been at least one bug (referenced in the code itself, issue #12606) allowing receipts above the size limit to be created and subsequently delayed: [4](#0-3) 

Thus a receipt that is valid at creation time but fails `ExistingReceipt` validation once it reaches the front of the delayed queue (e.g., due to size/limit-related edge cases, a future protocol-version tightening of `LimitConfig`, or a latent bug producing a pathological receipt that still passes `NewReceipt` checks) will deterministically and repeatedly crash chunk application for that shard, forever, since the receipt is never removed from the queue.

### Impact Explanation
This causes a **transaction-triggered halt**: once such a receipt is delayed, the shard can never again successfully apply a chunk, because the same panic recurs on every attempt (fresh node sync, restart, or retry). This blocks all further transaction/receipt processing on the shard (and, since NEAR chunks must all apply for the block to be valid, effectively stalls block production chain-wide), which is a Critical-severity denial of service — directly analogous to how `BulkCreateUnstakes`'s hard-stop on a conflicting-but-undeleted record DoS'd all future notary processing.

### Likelihood Explanation
Reaching `process_delayed_receipts`'s validation failure requires a receipt to (a) get admitted into the delayed queue as valid, and (b) later fail `validate_receipt` under `ExistingReceipt` mode. The code's own comments acknowledge this has previously happened via a receipt-size-limit bug (#12606), and `ExistingReceipt` mode exists specifically to be more permissive than `NewReceipt` to cope with that class of issue — indicating the underlying validation-drift scenario is a recognized, real possibility rather than a purely theoretical one. The exact trigger condition (a specific malformed/oversized receipt reaching this exact check) was not confirmed further within available context/time, so likelihood should be treated as plausible-but-not-fully-proven without a concrete PoC receipt construction.

### Recommendation
Do not treat a `validate_receipt` failure on a delayed (or incoming) receipt pop as an unconditional hard panic that also fails to make forward progress. At minimum:
- Ensure the queue index/removal for an unprocessable delayed receipt is durably committed (so it is *not* replayed) before or independent of raising the error, so the same node doesn't loop on the same receipt forever.
- Consider treating unprocessable delayed receipts analogous to other tolerated invalid-input cases in this codebase (e.g., invalid transactions are skipped rather than aborting the whole chunk, per the `process_transactions` code path) — log/trace the error and safely skip/quarantine the receipt rather than aborting the entire chunk apply and panicking the node.
- Audit all `?`-propagated errors inside `process_local_receipts`/`process_delayed_receipts`/`process_incoming_receipts` for the same non-committing-hard-abort pattern.

### Proof of Concept
Not independently constructed within the scope of this analysis — a concrete PoC would require crafting/admitting a receipt that passes `ValidateReceiptMode::NewReceipt` validation (allowing it into the delayed queue) but fails `ValidateReceiptMode::ExistingReceipt` validation when later popped (e.g., via the size-limit discrepancy referenced in issue #12606, or a protocol-version boundary that changes `LimitConfig`). The control-flow analysis above (lib.rs `process_delayed_receipts` → `chain/runtime/mod.rs::apply` error mapping → `apply_chunk` panic branch) is directly supported by the cited code.

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ValidateReceiptMode {
    /// Used for validating new receipts that were just created.
    /// More strict than `OldReceipt` mode, which has to handle older receipts.
    NewReceipt,
    /// Used for validating older receipts that were saved in the state/received. Less strict than
    /// NewReceipt validation. Tolerates some receipts that wouldn't pass new validation. It has to
    /// be less strict because:
    /// 1) Older receipts might have been created before new validation rules.
    /// 2) There is a bug which allows to create receipts that are above the size limit. Runtime has
    ///    to handle them gracefully until the receipt size limit bug is fixed.
    ///    See https://github.com/near/nearcore/issues/12606 for details.
    ExistingReceipt,
}
