Based on my research, I found a confirmed analog in nearcore. The external bug's invariant is: **a limit check is performed on value X, but execution proceeds with X+Y (where Y is added after the check), allowing the combined value to exceed the limit and cause failure/loss.**

In nearcore, the exact same pattern exists in the receipt size validation path.

---

### Title
Receipt `max_receipt_size` Limit Bypassed via `output_data_receivers` Appended After Validation — (`runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`)

### Summary

When a contract uses `promise_return`, the runtime validates a newly-created receipt's size against `max_receipt_size` **before** appending `output_data_receivers` from the parent receipt. After the size check passes, the runtime mutates the receipt by extending its `output_data_receivers` field, making the receipt's serialized size exceed `max_receipt_size`. No re-validation occurs after the mutation. The oversized receipt is then forwarded cross-shard. This is a confirmed bug (nearcore issue #12606) with a concrete unprivileged trigger.

### Finding Description

**Step 1 — Size check at receipt creation (passes):**

In `validate_receipt` (`runtime/runtime/src/verifier.rs`), when mode is `NewReceipt`, the receipt's borsh-serialized size is checked:

```rust
if receipt_size > limit_config.max_receipt_size {
    return Err(ReceiptValidationError::ReceiptSizeExceeded { ... });
}
```

A contract can craft a receipt whose size is exactly `max_receipt_size`. This check passes. [1](#0-0) 

**Step 2 — `output_data_receivers` appended after the check (size now exceeds limit):**

In `apply_action_receipt` (`runtime/runtime/src/lib.rs`), when the executed receipt returns a `ReceiptIndex` (i.e., `promise_return`), the runtime appends the parent receipt's `output_data_receivers` to the newly-created receipt **after** it has already passed validation:

```rust
ReceiptEnum::Action(new_action_receipt)
| ReceiptEnum::PromiseYield(new_action_receipt) => new_action_receipt
    .output_data_receivers
    .extend_from_slice(&action_receipt.output_data_receivers()),
```

Each `DataReceiver` entry in `output_data_receivers` adds bytes to the serialized receipt. If the receipt was already at `max_receipt_size`, appending even one `DataReceiver` pushes it over the limit. [2](#0-1) 

**Step 3 — No re-validation; oversized receipt forwarded:**

After the mutation, the receipt is passed directly to `receipt_sink.forward_or_buffer_receipt` without re-running `validate_receipt`. The `try_forward` function in `congestion_control.rs` contains an explicit workaround that **clamps** the oversized receipt's size to `max_receipt_size` for admission purposes to prevent it from getting permanently stuck:

```rust
// There is a bug which allows to create receipts that are above the size limit.
// Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
if size > max_receipt_size {
    size = max_receipt_size;
}
``` [3](#0-2) 

**Step 4 — Destination shard processes the oversized receipt:**

When the oversized receipt arrives at the destination shard, `validate_receipt` is called with `ValidateReceiptMode::ExistingReceipt`, which **skips the size check** by design (to handle pre-existing oversized receipts in state). The receipt is executed normally. [4](#0-3) 

**Confirmed by test:**

The test `test_max_receipt_size_promise_return` explicitly documents and demonstrates this bug. It constructs a receipt of exactly `max_receipt_size`, triggers `promise_return`, and then asserts that an oversized receipt was observed in the chain: [5](#0-4) [6](#0-5) 

### Impact Explanation

The `max_receipt_size` invariant is broken: a receipt that should be rejected at creation time is instead forwarded and executed. Without the `try_forward` size-clamping workaround, the oversized receipt would fail the outgoing bandwidth size check (`forward_limit.size >= size`) and be buffered indefinitely — permanently locking any funds or state changes attached to that receipt. With the workaround in place, the receipt is forwarded but the size limit is silently bypassed, allowing state witnesses to grow beyond the `per_receipt_storage_proof_size_limit` (PV 86), which can cause the receipt to be pushed to the delayed queue and delay execution of dependent receipts (including deposit refunds).

The impact matches **contract execution flow breakage**: the receipt lifecycle invariant (`max_receipt_size` is enforced end-to-end) is violated by an ordinary unprivileged user action.

### Likelihood Explanation

Any user who can deploy a contract can trigger this. The contract must:
1. Create a receipt whose action payload fills the receipt to exactly `max_receipt_size` (feasible by controlling `args` size in a `FunctionCall` action).
2. Use `promise_return` to redirect a promise chain through that receipt, causing the runtime to append `output_data_receivers` post-validation.

This is a reachable, deterministic code path requiring no privileged access.

### Recommendation

Re-validate the receipt size **after** `output_data_receivers` are appended in `apply_action_receipt`. Specifically, after the `extend_from_slice` at `lib.rs:1042–1047`, call `validate_receipt` (or an inline size check) on the mutated receipt and set `result.result = Err(...)` if the new size exceeds `max_receipt_size`. This mirrors the fix pattern from the external report: both the pre-mutation and post-mutation sizes must be checked against the same limit.

### Proof of Concept

1. Deploy a contract with a method `method1` that:
   - Creates promise A targeting itself with `args` sized so the resulting receipt serializes to exactly `max_receipt_size` (4,194,304 bytes).
   - Creates promise B (a `.then` continuation).
   - Returns promise A via `promise_return(A)`, causing the runtime to append B's `output_data_receivers` to A's receipt.
2. Call `method1` from an ordinary user account.
3. Observe (via `get_incoming_receipts_for_shard`) that a receipt with `borsh::object_length > max_receipt_size` appears in the chain.

This is exactly what `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` demonstrates end-to-end. [7](#0-6)

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let mut env = TestLoopBuilder::new()

    // User calls a contract method

    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]

            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();

    let args_size = max_receipt_size - base_receipt_size;

        102,

        &account_signer,
