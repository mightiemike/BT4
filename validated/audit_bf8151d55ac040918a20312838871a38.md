### Title
Witness HelloMessage Signature Has No Freshness Check, Enabling Replay to Forge Trust-Node Status - (File: `framework/src/main/java/org/tron/core/net/service/relay/RelayService.java`)

### Summary
`RelayService.checkHelloMessage` verifies a witness's signature over a bare `timestamp` field to authorize a peer as a fast-forward relay "trust node," but it never validates that the signed `timestamp` is recent or within any acceptable window. This is the same root cause as the referenced report: a signed payload with no deadline/expiry field, so a captured valid signature can be replayed indefinitely.

### Finding Description
`fillHelloMessage` (lines 107-124) has a witness sign only `Sha256Hash.of(ByteArray.fromLong(message.getTimestamp()))` — the signed digest contains no nonce, no expiry, and no binding to the specific peer/channel/session. [1](#0-0) 

`checkHelloMessage` (lines 126-184) recomputes the same hash from `msg.getTimestamp()`, recovers the signer address, and — if it matches an active witness (or its permission address) — adds `channel.getInetAddress()` to `TronNetService.getP2pConfig().getTrustNodes()`. There is no check that `msg.getTimestamp()` is close to `System.currentTimeMillis()`, no nonce store, and no session-binding of the signature to the specific channel/connection. [2](#0-1) 

Because the signature covers only a timestamp value (not the peer address, channel, or any single-use nonce), any peer that observes/captures a valid `(timestamp, signature)` pair sent by a legitimate witness to a legitimate fast-forward node can replay that exact `HelloMessage` to a *different* connection and be treated as a trusted node, since the check only re-derives the address from the signature and never rejects on staleness or reuse.

### Impact Explanation
Successful replay causes `checkHelloMessage` to return `true` and add the attacker-controlled `channel.getInetAddress()` to the process-wide `trustNodes` set maintained by the P2P layer. This is a real state/authorization outcome (an unprivileged network peer forging "trust node" status without possessing the witness's private key), directly matching the report's bug class: "signature does not contain a deadline, making it reusable," causing an unintended-but-valid re-use of an authorization credential.

The severity is bounded by the practical difficulty of capturing the signed HelloMessage in the first place (network position needed) and requires `fastForward`-mode to be enabled and the target node to be participating in fast-forward relay peering, so it is a real but conditionally-reachable protocol/session-security issue rather than a direct asset-theft path.

### Likelihood Explanation
Exploitation requires: (1) fast-forward mode enabled on the target node (`parameter.isFastForward()`), (2) the attacker being able to observe or intercept a legitimate witness's HelloMessage handshake (e.g., as a peer on the network or via a man-in-the-middle position between the witness and a fast-forward node), and (3) no other layer (TLS/session binding) preventing simple replay to a new connection. Given `HelloMessage` is sent as part of the standard unencrypted p2p handshake and the signed payload has no session/channel binding, an attacker capable of observing handshake traffic can replay it. This is a real but network-position-dependent finding.

### Recommendation
Bind the signed payload to session-specific and time-bounded data, e.g., include an expiry/deadline field or a fresh per-connection nonce/challenge (such as one derived from the specific channel's ephemeral handshake data) in the hash that is signed, and reject in `checkHelloMessage` any message whose timestamp is outside a small tolerance window (e.g., a few seconds) of the receiving node's current time, similar to the deadline check recommended in the original report for `PhiDaily.sol`.

### Proof of Concept
Conceptual replay sequence (not independently executed against a live network in this analysis):
1. Witness `W` sends a `HelloMessage` to fast-forward node `A`, containing `timestamp = T` and `signature = Sign_W(Sha256(T))`, per `fillHelloMessage`. [1](#0-0) 
2. Attacker `M`, positioned to observe this handshake, records `(T, signature)`.
3. `M` opens a new connection to any node `B` running with `fastForward=true` and sends a `HelloMessage` reusing the same `(address=W, timestamp=T, signature)`.
4. `checkHelloMessage` on `B` recomputes `Sha256(T)`, recovers `W`'s address from `signature`, confirms `W` is an active witness, and — since there is no timestamp-freshness or one-time-use check — accepts the message and adds `M`'s channel address to `B`'s `trustNodes` set. [2](#0-1) 

I was not able to fully verify downstream consumers of `trustNodes` within the p2p library (`org.tron.p2p.P2pConfig`), since that code is outside the indexed portion of this repository; its exact operational effect (e.g., whether trust nodes bypass connection limits or scoring) could not be confirmed from available files.
