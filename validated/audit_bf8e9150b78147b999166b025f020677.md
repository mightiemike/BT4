## Title
Unbounded allocation from attacker-controlled Cairo0 syscall array size before validation — Denial of Service - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo0 (deprecated) syscall request parser `read_felt_array` in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs` reads an array-size felt directly from Cairo VM memory and converts it to a `usize` with no upper-bound check before passing it to `felt_range_from_ptr`, which calls `vm.get_integer_range` (allocating a `Vec<Felt>` of that size) [1](#0-0) . This mirrors the CVE-2017-12602 pattern: a declared "length" field is trusted for allocation before any correlation with real available data or gas/step cost, letting a tiny, O(1) malicious payload trigger a disproportionately large allocation attempt.

### Finding Description
`read_felt_array` (deprecated syscalls) computes:
```
let array_size = felt_from_ptr(vm, ptr)?;
...
Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
``` [1](#0-0) 

`felt_range_from_ptr` in turn calls `vm.get_integer_range(ptr, size)` and collects the result into a `Vec<Felt>` [2](#0-1) . Because `array_size` is taken verbatim from a felt value that a Cairo0 contract's bytecode places into its own syscall request segment (e.g. as part of a `CallContractRequest`/`LibraryCallRequest`/`SendMessageToL1Request` calldata length field), the contract deployer fully controls this value at effectively zero cost: the size field and pointer field are simple immediate values written into the request struct — there is no requirement that the calling code first spend O(size) VM steps to populate that many real felts at the target address, unlike an ordinary memcpy loop. A contract can therefore emit a syscall request declaring an astronomically large `calldata_size` (bounded only by `usize` conversion, e.g. close to `usize::MAX` on 64-bit) pointing at a small or unrelated memory region.

This is analogous to the corresponding *non-deprecated* Cairo1 syscall path (`read_felt_array` in `crates/blockifier/src/execution/syscalls/hint_processor.rs`), where array size is derived from the *difference of two pointers* in the same segment rather than an arbitrary felt value — a materially safer construction, since real segment-backed data had to be written to produce a large offset [3](#0-2) . The deprecated Cairo0 path uses a `(size, data_ptr)` header layout instead, and the size felt is not checked against the caller's remaining gas, remaining VM steps, or the actual size of the referenced segment before conversion and allocation.

Notably, the codebase already recognizes and has explicitly patched this exact bug class elsewhere: `CairoArray::try_from` in `crates/apollo_cairo_utils/src/lib.rs` validates a declared array length against the number of remaining felts *before* calling `Vec::with_capacity`, with an explicit comment: "Validate before allocating to prevent a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`" [4](#0-3) . This same defensive pattern is missing from the deprecated syscall's `read_felt_array`.

### Impact Explanation
If `usize::try_from(array_size.to_biguint())` succeeds for a very large value (any value up to `usize::MAX`, e.g. up to ~1.8×10^19 on 64-bit), `vm.get_integer_range`/`Vec::with_capacity` will attempt to reserve capacity for that many `Felt` elements. Given `Felt` occupies 32 bytes, a modestly large declared size (e.g. a few hundred million) is enough to exceed available memory or trigger Rust's allocator to abort the process (`handle_alloc_error`) or panic on capacity overflow (`size * mem::size_of::<Felt>() > isize::MAX`). Because Starknet execution is deterministic and re-executed by every sequencer/full node processing the block, a single malicious transaction invoking such a Cairo0 contract entry point would crash every honest node attempting to execute or re-execute it — a network-wide denial of service (nodes unable to confirm new transactions / stalled processing) rather than a localized failure.

### Likelihood Explanation
Exploitability depends on whether Cairo0 (deprecated) contract declaration/invocation remains reachable in the current network configuration. Existing already-declared Cairo0 classes can still be invoked via ordinary `Invoke` transactions (the deprecated syscall executor is compiled into the current blockifier and actively used for backward compatibility), so any attacker controlling (or able to interact with) a Cairo0 contract that constructs such a malformed syscall request can trigger this without any special privilege — a single unprivileged transaction sender suffices. The construction of the malicious request requires knowledge of Cairo0 bytecode/hint semantics for building syscall segments directly, which raises the bar somewhat, but not out of reach for a sophisticated attacker with an already-deployed (or deployable, if Cairo0 declares are still permitted for existing classes) Cairo0 contract.

### Recommendation
In `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`), validate `array_size` before allocating: bound it against the actual remaining felts in the segment starting at `array_data_start_ptr` (similar to the check already implemented in `CairoArray::try_from` in `apollo_cairo_utils`), or against a hard configured maximum consistent with `max_calldata_length`/gas-derived limits, before calling `felt_range_from_ptr`. Apply the same length-vs-available-data validation pattern used in `apollo_cairo_utils/src/lib.rs` to this and any other unguarded `Vec`/`get_integer_range` allocation sites driven by attacker/contract-controlled size fields taken directly from VM memory rather than pointer-difference within an already-populated segment.

### Proof of Concept
1. Deploy (or use an existing) Cairo0 class whose entry point, when invoked, constructs a `CallContractRequest` (or `LibraryCallRequest`/`SendMessageToL1Request`) syscall segment where the calldata-length field is set to a large constant (e.g. `2^40`) and the calldata pointer refers to a small, real segment (e.g. length 1).
2. Submit a single `Invoke` transaction that calls this Cairo0 entry point.
3. During execution, the deprecated syscall handler calls `read_felt_array`, which converts the felt `2^40` to `usize` and calls `felt_range_from_ptr(vm, ptr, 2^40)` → `vm.get_integer_range` → attempts to allocate/collect ~2^40 `Felt` values (~35 TB at 32 bytes/felt), causing an allocation failure/panic or excessive memory consumption in the executing node's process. (Exact allocator behavior — panic vs. slow OOM — is implementation-dependent on the vendored `cairo-vm` crate, which was not directly inspectable in this analysis; the root-cause defect — missing bound validation in the sequencer's own wrapper before invoking that allocation — is confirmed in-repo.)

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
