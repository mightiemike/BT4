### Title
`TokenConfig.LiquidityCap` is never enforced during PRC20 minting, letting an unprivileged bridger mint unbounded synthetic supply on Push Chain - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/evm.go`)

### Summary
The external report's bug class is a *declared-but-unverified accounting cap*: a field meant to bound a mintable quantity (`plotSize` encoded in the tokenId) is never cross-checked, letting the caller mint beyond the intended limit. The Push Chain analog is `uregistry.TokenConfig.LiquidityCap`, which is documented and validated as "max supply cap for this token" ` [1](#0-0) ` but is only checked for non-emptiness at admin config time ` [2](#0-1) `. It is never read on the mint path.

### Finding Description
`ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload`/`ExecuteInboundGas` call `depositPRC20`, which loads the `TokenConfig`, resolves the PRC20 contract address, and mints the full `Inbound.Amount` with no comparison against `LiquidityCap` or the token's already-minted/circulating supply: [3](#0-2) 

`CallPRC20Deposit` then issues the `depositPRC20Token` mint call via `DerivedEVMCall` with the raw amount, again with no cap check: [4](#0-3) 

`TokenConfig.ValidateBasic` only requires `LiquidityCap` to be a non-empty string; it never validates the mint amount against it, and no other file in `x/uexecutor` references `LiquidityCap` at all (confirmed by grep across `x/uexecutor/**`): ` [5](#0-4) `

`Inbound.Amount` is attacker-controlled: it is whatever value the external gateway deposit event reports, subject only to `ValidateForExecution`'s basic uint256-format check, not any economic ceiling: ` [6](#0-5) `

### Impact Explanation
Because `LiquidityCap` is advertised as the enforced ceiling on a token's synthetic representation but is architecturally dead code, an ordinary unprivileged user who deposits on the source-chain gateway can cause honest Universal Validators to reach quorum on an inbound of arbitrary size and honest core validators to mint PRC20 supply on Push Chain that exceeds the registry's declared cap. This corrupts PRC20 accounting invariants (actual minted supply vs. the intended supply ceiling used for risk/collateralization assumptions), which falls squarely under "corruption of PRC20 or native asset accounting" in the allowed impact gate. If liquidity caps are relied upon elsewhere (e.g., collateral backing assumptions for vault/rescue paths), unbounded minting can also contribute to insolvency of the PRC20 representation relative to backing funds.

### Likelihood Explanation
High reachability: no privileged action is required — a normal user only needs to deposit on the external gateway with an amount above the intended cap, and honest Universal Validators will vote and finalize the inbound exactly as designed (`VoteInbound` → ballot finalize → `ExecuteInbound` → `depositPRC20`). There is no code path, guard, or state lookup that references `LiquidityCap` anywhere in the mint/execution flow, so the omission is unconditional, not dependent on a race or edge case.

### Recommendation
In `depositPRC20` (and the `CallPRC20DepositAutoSwap` variant), before minting, look up the token's current circulating/minted PRC20 supply (or track cumulative minted amount per token in `x/uregistry`/`x/uexecutor` state) and reject or partially execute (with a revert of the excess) any inbound that would push total minted supply above `TokenConfig.LiquidityCap`. Treat a cap violation the same way other execution failures are treated: record a FAILED PCTx and, if `!IsCEA`, create an `INBOUND_REVERT` outbound, consistent with the existing failure-handling pattern in `ExecuteInboundFundsAndPayload`.

### Proof of Concept
Not independently reproduced in this session (no test/terminal access); this is derived from static analysis of the mint path and confirmed by the absence of any `LiquidityCap` reference in `x/uexecutor` via repository-wide grep. A concrete PoC would: (1) register a `TokenConfig` with a small `LiquidityCap`, (2) submit `MsgVoteInbound` from a quorum of Universal Validators with `TxType_FUNDS` and `Amount` far exceeding that cap, (3) observe the PRC20 balance minted to the recipient's UEA equals the full `Amount`, unconstrained by `LiquidityCap` — analogous to the existing test pattern in `test/integration/uexecutor/inbound_solana_test.go` (`TestSolanaInboundFunds`), which already demonstrates that arbitrary inbound `Amount` values are minted 1:1 with no cap check present in that flow: [7](#0-6)

// ValidateBasic performs sanity checks on the TokenConfig
func (p TokenConfig) ValidateBasic() error {
	if strings.TrimSpace(p.Chain) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "chain cannot be empty")
	}

	if strings.TrimSpace(p.Address) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token contract address cannot be empty")
	}

	// Enforce a parseable address for the chain's namespace (e.g. 20-byte hex
	// for eip155, base58 for solana) so every registration lands on the
	// canonical storage key.
	if _, err := utils.CanonicalizeAddressByNamespace(p.Chain, p.Address); err != nil {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token address for chain %s: %s", p.Chain, err)
	}

	if strings.TrimSpace(p.Name) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token name cannot be empty")
	}

	if strings.TrimSpace(p.Symbol) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token symbol cannot be empty")
	}

	if p.Decimals == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "decimals must be greater than zero")
	}

	// Validate token_type is within known enum range
	if _, ok := TokenType_name[int32(p.TokenType)]; !ok {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token_type: %v", p.TokenType)
	}

	if strings.TrimSpace(p.LiquidityCap) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "liquidity_cap cannot be empty")
	}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
