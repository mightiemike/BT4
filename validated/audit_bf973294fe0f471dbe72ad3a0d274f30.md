### Title
Front-running `consume-signer-key-authorization` lets any user DoS a stacker's `stack-stx`/`stack-extend`/`stack-aggregation-*` transaction by burning their signature-authorized `auth-id` first - ([File: stackslib/src/chainstate/stacks/boot/pox-4.clar])

### Summary
`stack-stx` (and the other topics: `stack-extend`, `stack-increase`, `stack-aggregation-commit(-indexed)`, `stack-aggregation-increase`) validate a signer's authorization via `consume-signer-key-authorization`, which wraps `verify-signer-key-sig`. The authorization/signature is not bound to `tx-sender` — the `used-signer-key-authorizations` map key is only `{signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount}`, with no `sender`/`caller` field. Any address (a mempool observer) can replay the exact same public parameters and the same (public, mempool-visible) `signer-sig` in their own transaction with `amount-ustx <= max-amount`, front-run the intended stacker, and consume the authorization before the legitimate transaction lands — exactly the pattern in the referenced report where `permit`'s missing "spender == msg.sender" check let a front-runner burn someone else's authorization.

### Finding Description
`verify-signer-key-sig`/`consume-signer-key-authorization` in `pox-4.clar` check the secp256k1 signature against `signer-key`, and mark the authorization tuple used, but never assert anything about `tx-sender`: [1](#0-0) [2](#0-1) 

`stack-stx` calls `consume-signer-key-authorization` with parameters that are entirely public (`pox-addr`, `reward-cycle`, `"stack-stx"`, `lock-period`, `signer-sig`, `signer-key`, `amount-ustx`, `max-amount`, `auth-id`) and locks funds from `tx-sender`, not from any address embedded in the signed payload: [3](#0-2) 

Because Alice's `signer-sig` (produced off-chain and included in her pending transaction) authorizes any caller supplying the same `pox-addr`/`reward-cycle`/`topic`/`period`/`max-amount`/`auth-id` with `amount-ustx <= max-amount`, an attacker Bob who observes Alice's pending transaction in the mempool can submit his own `stack-stx` call reusing that exact signature and `auth-id` with a smaller `amount-ustx`. His transaction confirms first, `map-insert used-signer-key-authorizations` succeeds and marks the tuple used. When Alice's original transaction then executes, `verify-signer-key-sig` hits `(asserts! (is-none (map-get? used-signer-key-authorizations ...)) (err ERR_SIGNER_AUTH_USED))` and fails with `ERR_SIGNER_AUTH_USED` (39): [4](#0-3) 

Alice's intended lock-up never happens (or happens in the wrong reward cycle after she reissues a new signature), while Bob has consumed the one-time `auth-id` grant she obtained from her signer. This is the on-chain analog of the report's `MarketERC20::permit` issue: the authorization primitive lacks a `caller == expected-caller` binding, so anyone can consume/burn it on behalf of the intended party purely by observing the mempool.

### Impact Explanation
This is a minority-triggerable griefing/DoS vector bounded to a single stacker's/delegate's PoX participation for a given `auth_id`: it can cause a stacker to miss a reward cycle (lost potential rewards / wasted signer coordination), forcing them to obtain a brand-new signer signature and auth-id and resubmit, and it can be repeated by any unprivileged address that simply watches the mempool. It does not directly cause a chain split, a non-reproducible state root, or fund theft, but it is a reproducible, minority-triggerable divergence between the stacker's intended and actual on-chain state (their `stacking-state` entry never gets created for the intended cycle) — a High-severity temporary-tip/availability disagreement consistent with "minority-triggerable ... divergence, ... reward mis-payment bounded to fees" category, here bounded to a missed reward-cycle opportunity rather than reward mis-payment.

### Likelihood Explanation
High — no special privilege, key, or majority stake is required. The attacker only needs to observe Alice's pending, unconfirmed `stack-stx`/`stack-extend`/`stack-aggregation-commit` transaction (which necessarily contains the plaintext `signer-sig`, `pox-addr`, `reward-cycle`, `period`, `max-amount`, `auth-id`) in the mempool and submit a copy with the same parameters and any `amount-ustx <= max-amount`, paying only the transaction fee to front-run it into an earlier block/microblock.

### Recommendation
Bind the signer-key authorization to the intended caller/stacker so it cannot be consumed by an unrelated party:
- Add a `stacker`/`sender` (or `tx-sender`) field to the signed message hash (`get-signer-key-message-hash`) and to the `used-signer-key-authorizations`/`signer-key-authorizations` map keys, and assert `tx-sender == stacker` inside `verify-signer-key-sig`/`consume-signer-key-authorization`, analogous to adding `require(msg.sender == spender)` in the referenced fix.
- Alternatively, require that the authorization also commit to a specific `tx-sender`, so only the intended stacker/delegate can present that `signer-sig` successfully.

### Proof of Concept
1. Alice's signer produces `signer-sig` for `(pox-addr=P, reward-cycle=R, topic="stack-stx", period=L, max-amount=M, auth-id=A)` and Alice broadcasts `stack-stx(amount-ustx=M, pox-addr=P, start-burn-ht=H, lock-period=L, signer-sig=Some(sig), signer-key=K, max-amount=M, auth-id=A)`.
2. Bob observes this pending transaction, extracts `sig`, `K`, `P`, `R`, `L`, `M`, `A` (all public fields of Alice's tx), and submits his own `stack-stx(amount-ustx=m<=M, pox-addr=P, start-burn-ht=H, lock-period=L, signer-sig=Some(sig), signer-key=K, max-amount=M, auth-id=A)` from his own account with a higher fee/earlier nonce so it mines first.
3. Bob's call passes `verify-signer-key-sig` (signature matches `K`, tuple not yet used) via `consume-signer-key-authorization` at [5](#0-4) , inserting the `used-signer-key-authorizations` entry for `{K,R,"stack-stx",L,P,A,M}`.
4. Alice's original transaction is then processed; `verify-signer-key-sig`'s `(asserts! (is-none (map-get? used-signer-key-authorizations ...)))` at [6](#0-5)  now fails, returning `(err u39)` (`ERR_SIGNER_AUTH_USED`), and Alice's `stack-stx` call aborts — she is locked out of stacking for that authorization/cycle even though she never authorized Bob to use her signature.

(define-public (stack-stx (amount-ustx uint)
                          (pox-addr (tuple (version (buff 1)) (hashbytes (buff 32))))
                          (start-burn-ht uint)
                          (lock-period uint)
                          (signer-sig (optional (buff 65)))
                          (signer-key (buff 33))
                          (max-amount uint)
                          (auth-id uint))
    ;; this stacker's first reward cycle is the _next_ reward cycle
    (let ((first-reward-cycle (+ u1 (current-pox-reward-cycle)))
          (specified-reward-cycle (+ u1 (burn-height-to-reward-cycle start-burn-ht))))
      ;; the start-burn-ht must result in the next reward cycle, do not allow stackers
      ;;  to "post-date" their `stack-stx` transaction
      (asserts! (is-eq first-reward-cycle specified-reward-cycle)
                (err ERR_INVALID_START_BURN_HEIGHT))

      ;; must be called directly by the tx-sender or by an allowed contract-caller
      (asserts! (check-caller-allowed)
                (err ERR_STACKING_PERMISSION_DENIED))

      ;; tx-sender principal must not be stacking
      (asserts! (is-none (get-stacker-info tx-sender))
        (err ERR_STACKING_ALREADY_STACKED))

      ;; tx-sender must not be delegating
      (asserts! (is-none (get-check-delegation tx-sender))
        (err ERR_STACKING_ALREADY_DELEGATED))

      ;; the Stacker must have sufficient unlocked funds
      (asserts! (>= (stx-get-balance tx-sender) amount-ustx)
        (err ERR_STACKING_INSUFFICIENT_FUNDS))

      ;; Validate ownership of the given signer key
      (try! (consume-signer-key-authorization pox-addr (- first-reward-cycle u1) "stack-stx" lock-period signer-sig signer-key amount-ustx max-amount auth-id))

      ;; ensure that stacking can be performed
      (try! (can-stack-stx pox-addr amount-ustx first-reward-cycle lock-period))

      ;; register the PoX address with the amount stacked
      (let ((reward-set-indexes (try! (add-pox-addr-to-reward-cycles pox-addr first-reward-cycle lock-period amount-ustx tx-sender signer-key))))
          ;; add stacker record
         (map-set stacking-state
           { stacker: tx-sender }
           { pox-addr: pox-addr,
             reward-set-indexes: reward-set-indexes,
             first-reward-cycle: first-reward-cycle,
             lock-period: lock-period,
             delegated-to: none })

          ;; return the lock-up information, so the node can actually carry out the lock.
          (ok { stacker: tx-sender, lock-amount: amount-ustx, signer-key: signer-key, unlock-burn-height: (reward-cycle-to-burn-height (+ first-reward-cycle lock-period)) }))))

(define-read-only (verify-signer-key-sig (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                         (reward-cycle uint)
                                         (topic (string-ascii 14))
                                         (period uint)
                                         (signer-sig-opt (optional (buff 65)))
                                         (signer-key (buff 33))
                                         (amount uint)
                                         (max-amount uint)
                                         (auth-id uint))
  (begin
    ;; Validate that amount is less than or equal to `max-amount`
    (asserts! (>= max-amount amount) (err ERR_SIGNER_AUTH_AMOUNT_TOO_HIGH))
    (asserts! (is-none (map-get? used-signer-key-authorizations { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
              (err ERR_SIGNER_AUTH_USED))
    (match signer-sig-opt
      ;; `signer-sig` is present, verify the signature
      signer-sig (ok (asserts!
        (is-eq
          (unwrap! (secp256k1-recover?
            (get-signer-key-message-hash pox-addr reward-cycle topic period max-amount auth-id)
            signer-sig) (err ERR_INVALID_SIGNATURE_RECOVER))
          signer-key)
        (err ERR_INVALID_SIGNATURE_PUBKEY)))
      ;; `signer-sig` is not present, verify that an authorization was previously added for this key
      (ok (asserts! (default-to false (map-get? signer-key-authorizations
            { signer-key: signer-key, reward-cycle: reward-cycle, period: period, topic: topic, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
          (err ERR_NOT_ALLOWED)))

(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))
