## Title
Ethereum-style function-selector dispatch in the NEAR Wallet Contract lets attackers disguise `AddKey`/`DeleteKey`/`Transfer` actions as benign calls, enabling account takeover - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The NEAR Wallet Contract (`near-wallet-contract`, used to give eth-implicit accounts an Ethereum-style transaction interface) decides which privileged NEAR action to execute — including `AddKey` with `is_full_access = true` — purely by matching the first 4 bytes of the RLP-decoded Ethereum transaction's `data` field against a fixed set of hard-coded selectors. This is architecturally identical to the Ambire finding: dispatch is done via a narrow, attacker-controllable 4-byte selector rather than by verifying that what the signer believes they are authorizing matches what actually executes, so a party who can influence what the user signs (a malicious relayer front-end, dApp, or wallet-connect flow) can disguise an `AddKey`/full-access grant as an innocuous-looking Ethereum call.

### Finding Description
`parse_tx_data` in `internal.rs` dispatches solely on `tx.data[0..4]`: [1](#0-0) 

The selectors themselves are just `keccak256("addKey(uint8,bytes,uint64,bool,bool,uint128,string,string[])")[0..4]` etc., i.e. plain 4-byte values with only 2^32 possible outcomes: [2](#0-1) [3](#0-2) 

Critically, when the selector is `ADD_KEY_SELECTOR` (`0x753ce5ab`), the contract decodes attacker-supplied ABI parameters directly into an `AddKeyAction`, including a `is_full_access` boolean, with **no additional confirmation, no cross-check against a "declared" method name, and no restriction on the parameters**: [4](#0-3) 

This is functionally the fallback-handler selector-clashing scenario from the Ambire report: `AmbireAccount.setAddrPrivilege()` there corresponds to `AddKey{ is_full_access: true }` here, and the Ambire "fallback handler with a colliding selector" corresponds here to the fact that any Ethereum calldata whose first four bytes happen to equal `0x753ce5ab` (whether by brute-force collision search against a benign public 4-byte-signature or crafted directly by a malicious relayer/dApp presenting a deceptive UI) is treated by the wallet as an `AddKey` grant. Since `rlp_execute` is the sole entry point and it accepts arbitrary base64-encoded RLP bytes from any caller/relayer (`lib.rs`): [5](#0-4) 

the only barrier to executing `AddKey` is obtaining the account owner's ECDSA signature over the crafted transaction bytes — i.e., getting the user to sign something that *looks* benign (e.g. a "self-call" transaction with a deceptively labeled function, similar to how a fallback handler misleads a user in the Ambire scenario) but whose raw calldata prefix is `0x753ce5ab` followed by attacker-chosen `(public_key_kind, public_key, nonce, is_full_access=true, ...)`.

### Impact Explanation
If a user is induced to sign such a transaction (e.g., via a malicious/compromised relayer UI, a phishing dApp requesting an Ethereum "self-call" signature, or a wallet-connect flow that displays a misleading decoded method name for the selector), the wallet contract will add an attacker-controlled full-access key to the victim's NEAR account, granting the attacker complete control of the account and its funds — a concrete unauthorized value-movement / account-takeover primitive, directly analogous to and as severe as the Ambire `setAddrPrivilege()` case.

### Likelihood Explanation
Exploitation requires social engineering to obtain the user's signature over deceptive calldata rather than a pure protocol-level break, which is why the analogous Ambire issue was rated Medium rather than Critical/High. The same caveat applies here: the wallet-contract design deliberately relies on the user trusting whatever their signing tool displays for the raw calldata, and there is no on-chain safeguard (e.g., requiring `is_full_access` grants to go through a distinctly-labeled, harder-to-spoof code path, or requiring a secondary confirmation) to prevent a colliding/deceptive selector from being interpreted as a privileged `AddKey`.

### Recommendation
Do not let a bare 4-byte prefix alone gate a privileged action such as full-access `AddKey`. Options include: requiring an explicit, distinguishable "intent" tag (e.g., a larger, structured discriminator, or requiring `is_full_access` grants to use a selector/signature that cannot be produced by any plausible "normal" Ethereum ABI signature), enforcing a mandatory time-delay or secondary confirmation before a self-directed `AddKey` with `is_full_access = true` takes effect, or restricting the wallet contract's automatic action-inference to non-privileged actions and requiring privileged actions to be submitted through a separate, explicitly-labeled method rather than generic `rlp_execute` calldata sniffing.

### Proof of Concept
1. Attacker (a malicious relayer, dApp, or phishing site) presents the victim, who owns an eth-implicit NEAR account, with an Ethereum-style transaction to sign where `to == victim's own address` (satisfying `validate_tx_relayer_data`'s `CurrentAccount` check) and the UI relabels/obscures the true effect of the calldata.
2. The calldata is crafted as: `0x753ce5ab` (`ADD_KEY_SELECTOR`) followed by ABI-encoded `(public_key_kind=1, public_key=<attacker's secp256k1 key>, nonce=0, is_full_access=true, is_limited_allowance=false, allowance=0, receiver_id="", method_names=[])`, matching `ADD_KEY_SIGNATURE` in `types.rs` lines 30-41.
3. Victim signs the RLP transaction with their private key (the only real requirement for `rlp_execute` to accept it, per `validate_tx_relayer_data`, `internal.rs` lines 318-368) and it is submitted to `rlp_execute`.
4. `parse_tx_data` (`internal.rs` lines 272-296) decodes this as `Action::AddKey{ is_full_access: true, .. }`, which is converted into a real NEAR `AddKeyAction` in `try_into_near_action` (`types.rs` lines 262-290) and dispatched as a promise from the account itself, granting the attacker's key full access to the victim's account.
