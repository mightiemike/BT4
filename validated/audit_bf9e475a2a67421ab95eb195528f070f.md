### Title
Maker Order State Not Persisted To `MarketOrderStore` On The "Quantity Too Small" Return Path In `MarketSellAssetActuator.matchSingleOrder()`, Leaving A Permanently Stuck "Ghost" Active Order - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder()` mutates the maker's in-memory `MarketOrderCapsule` (marks it `INACTIVE`, zeroes `sellTokenQuantityRemain`, returns the residual sell-token to the maker) and then returns early from the "taker > maker, remainder too small" branch **without** persisting these mutations back to `MarketOrderStore` via `orderStore.put(...)`. The persistent `orderStore` copy of that order keeps its stale `State.ACTIVE` and stale non-zero `sellTokenQuantityRemain` forever, while the order has already been unlinked from the order-book (`MarketPairPriceToOrderStore`) and from the owner's active-order list (`MarketAccountStore`). This is the same bug class as the CSX report: a trade-terminating code path skips the cleanup call that its sibling branches perform, leaving a resource in a permanently inconsistent, unusable/exploitable state.

### Finding Description
In `matchSingleOrder()`, three outcome branches update `makerOrderCapsule`/`takerOrderCapsule` and then, unconditionally, fall through to: [1](#0-0) 
which persists the maker order to `orderStore`. However the "taker > maker" branch has an early `return` before that line is ever reached when the maker's computed proceeds are 0 (quantity-too-small edge case): [2](#0-1) 

In this early-return path:
1. `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` is called at line 465, which *does* correctly remove the order from the owner's active list in `MarketAccountStore`: [3](#0-2) 
2. `makerOrderCapsule.setSellTokenQuantityReturn()` and `returnSellTokenRemain(makerOrderCapsule)` mutate the in-memory capsule (setting `sellTokenQuantityRemain` to 0 via `MarketUtils.returnSellTokenRemain`) and refund the residual sell-token to the maker's account, persisting the **account** balance change: [4](#0-3) [5](#0-4) 
3. The function then `return`s at line 477, **skipping** `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule)` (line 486). The order's on-disk record in `MarketOrderStore` is never updated: it still shows `State.ACTIVE` and the original, non-zero `sellTokenQuantityRemain`.

Meanwhile, in the caller `matchOrder()`, the maker order is removed from the price-level linked list based on the in-memory object reference (which does show `sellTokenQuantityRemain == 0`, since Java objects are mutated by reference), so it is correctly unlinked from `MarketPairPriceToOrderStore`/`MarketPairToPriceStore`: [6](#0-5) 

The net result is a "ghost" order: removed from the account's active-order list and from the order book, but still recorded as `State.ACTIVE` with its original (already-refunded) `sellTokenQuantityRemain` in `MarketOrderStore` — an unbounded, permanent state inconsistency, exactly analogous to the CSX report's stuck asset-ID.

### Impact Explanation
Because `MarketCancelOrderActuator.validate()` only checks `marketOrderCapsule.isActive()` from the stale, unpersisted `orderStore` record: [7](#0-6) 
the owner can submit `MarketCancelOrderContract` against this ghost order. `execute()` will then re-run `MarketUtils.returnSellTokenRemain` using the stale non-zero remain, adding tokens to the account balance again, and later call `pairPriceToOrderStore.get(pairPriceKey)`: [8](#0-7) 
Since that price-level list entry has already been deleted from `MarketPairPriceToOrderStore` (fully consumed and removed by `matchOrder()`), this call throws `ItemNotFoundException`, which is caught and causes the whole transaction (including the fee deduction and the interim double credit made earlier in the same execution) to fail with `ContractExeException`. Whether the double-credit itself becomes permanently observable depends on whether the enclosing revoking-DB session for that transaction is rolled back on this failure; regardless of that, the practical, provable impact is:
- A specific, deterministically reachable maker order becomes permanently un-cancelable/un-queryable-correctly — the on-chain `MarketOrderStore` record for that `orderId` is stuck showing `State.ACTIVE` with stale quantity data forever, a persistent data/state-integrity corruption for market order accounting reachable purely from a broadcast `MarketSellAssetContract` transaction.
- Any account/tooling relying on `MarketOrderStore` (e.g., wallet/API queries of a user's orders) will report an incorrect "still open" order that can never be resolved through the normal order lifecycle (cancel fails, and it will never re-enter matching since it is absent from the order book).

### Likelihood Explanation
This is triggered purely by ordinary, unprivileged `MarketSellAssetContract` transactions (a public RPC/broadcast transaction path — `MarketSellAssetActuator` is a standard actuator invoked for any user's sell-asset transaction). It requires the specific "taker > maker, `makerBuyTokenQuantityReceive == 0`" arithmetic condition on `MarketUtils.multiplyAndDivide`, which the surrounding code comment itself claims "would not happen here" for a taker fully consuming a smaller maker order — but the divide-based computation can still legitimately reach zero for adversarially chosen sell/buy quantity ratios (the code retains the dead branch specifically because it is reachable), so any user can construct maker/taker order quantities to hit it deterministically.

### Recommendation
Persist the maker order to `orderStore` before returning in the early-return branch, mirroring the successful branches' behavior — i.e., add `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule);` immediately before the `return;` on line 477 in `MarketSellAssetActuator.matchSingleOrder()`. More robustly, refactor so that `orderStore.put()` for the maker/taker capsule is called unconditionally at the top of every exit path of `matchSingleOrder()` (e.g., via a `finally` block or a single terminal write) rather than being contingent on falling through to line 486, to prevent any future branch from re-introducing this class of bug.

### Proof of Concept
1. Owner A creates a maker sell order O with `sellTokenQuantity = S_m`, `buyTokenQuantity = B_m` such that later `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` truncates to 0 for the specific taker fill (achievable via `MarketUtils.multiplyAndDivide` integer division when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`).
2. Owner B submits a `MarketSellAssetContract` with taker quantities chosen so `takerBuyTokenQuantityRemain > makerOrderCapsule.getSellTokenQuantityRemain()` (the "taker > maker" branch in `matchSingleOrder`) and so that `makerBuyTokenQuantityReceive` computes to `0`.
3. `matchSingleOrder()` executes lines 461–477: sets maker `INACTIVE` in `MarketAccountStore`, refunds maker's remaining sell-token to their balance, and returns before `orderStore.put()`.
4. Query `MarketOrderStore` for order O: it still reports `State.ACTIVE` and the pre-match `sellTokenQuantityRemain`, even though O has been removed from `MarketPairPriceToOrderStore`/`MarketPairToPriceStore` and from Owner A's active order list in `MarketAccountStore`.
5. Owner A submits `MarketCancelOrderContract` for order O; `validate()` passes (`isActive()` reads the stale `ACTIVE` state), but `execute()` fails with `ItemNotFoundException` when looking up the already-deleted `pairPriceKey` entry, permanently preventing the order from ever being resolved while its `MarketOrderStore` record remains corrupted/stuck.
