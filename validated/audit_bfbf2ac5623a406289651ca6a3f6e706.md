### Title
Runtime `apply` maps `RuntimeError::UnexpectedIntegerOverflow` and `RuntimeError::ReceiptValidationError` to a hard `panic!()` instead of a graceful error, allowing a transaction-triggered node halt - (File: `chain/chain/src/runtime/mod.rs`)

### Summary
The Compound-style bug in the report ("a function that is expected to return a benign error/zero value instead reverts/throws, so its caller receives an unexpected hard failure") maps onto `chain/chain/src/runtime/mod.rs`, where the error produced by `Runtime::apply` (`runtime/runtime/src/lib.rs:1860`) is translated into a `near_chain::Error` for the rest of the node. Two of the four `RuntimeError` variants are not converted into a recoverable `Error` value; they are turned into a Rust `panic!()`.

### Finding Description
`NightshadeRuntime`'s chunk-application wrapper calls `self.runtime.apply(...)` and immediately `map_err`s the result: [1](#0-0) 

```rust
.map_err(|e| match e {
    RuntimeError::InvalidTxError(err) => {
        tracing::warn!(?err, "invalid tx");
        Error::InvalidTransactions
    }
    // TODO(#2152): process gracefully
    RuntimeError::UnexpectedIntegerOverflow(reason) => {
        panic!("RuntimeError::UnexpectedIntegerOverflow {reason}")
    }
    RuntimeError::StorageError(e) => Error::StorageError(e),
    // TODO(#2152): process gracefully
    RuntimeError::ReceiptValidationError(e) => panic!("{}", e),
    RuntimeError::ValidatorError(e) => e.into(),
})?;
```

Instead of surfacing `UnexpectedIntegerOverflow` and `ReceiptValidationError` as an `Error` variant that the block/chunk-production pipeline can reject gracefully (as is done for `InvalidTxError`, `StorageError`, and `ValidatorError`), the code deliberately calls `panic!`, annotated with an explicit `// TODO(#2152): process gracefully` comment acknowledging the shortcut is unfinished. This is functionally the same anti-pattern described in the report: a function that a caller relies on to return an error value ends up throwing/aborting instead, and the caller (here, the chunk-apply/runtime pipeline invoked for every chunk containing a transaction or receipt) is not equipped to handle that abrupt failure — it crashes the process rather than rejecting the offending input.

`Runtime::apply` (`runtime/runtime/src/lib.rs:1860`) is exactly the function that is invoked once per chunk for every transaction and receipt submitted by any transaction signer or produced as a receipt from any account, i.e., it is on the path reachable by an ordinary, unprivileged transaction/RPC submitter. If a crafted transaction or a chain of actions can cause `Runtime::apply` (or any function it calls, e.g., balance/gas arithmetic that returns `RuntimeError::UnexpectedIntegerOverflow`, or receipt construction/validation that returns `RuntimeError::ReceiptValidationError`) to surface either of those two error variants, the validator process that applies that chunk will panic.

### Impact Explanation
A `panic!()` inside the chunk-apply path is not a benign in-process error — it aborts the calling thread/task of the node applying the chunk. Because chunk application is deterministic and every honest validator/RPC node applying the same chunk will hit the identical code path with the identical inputs, this is a transaction-triggered halt: a single malicious transaction or receipt that reaches either error branch can crash all nodes that attempt to apply the chunk containing it, rather than being rejected as an invalid transaction (as `InvalidTxError` is). This matches the class of "transaction-triggered halt" that is explicitly in-scope, and is a direct parallel to the oracle bug reverting instead of returning `0` to its caller.

### Likelihood Explanation
Likelihood depends on whether an attacker can actually drive execution into the `UnexpectedIntegerOverflow` or `ReceiptValidationError` branches using only externally-controlled transaction/receipt content. The task did not confirm a concrete reachable trigger for either variant from a single unprivileged transaction within the current tool-call budget — `RuntimeError::UnexpectedIntegerOverflow` is produced from balance/gas-arithmetic helpers (`runtime/runtime/src/lib.rs`, `core/primitives/src/congestion_info.rs`) and `RuntimeError::ReceiptValidationError` from `validate_receipt`/receipt-construction logic (`runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`), both of which are intended to be defensive/invariant checks that should not fire on well-formed input. The explicit `// TODO(#2152): process gracefully` comments indicate the nearcore team is aware these paths currently panic and considers this only a resilience gap to be hardened, not necessarily a known-exploitable path from ordinary transactions today. This should be treated as Medium likelihood/impact pending confirmation of a concrete external trigger for either error variant.

### Recommendation
Convert `RuntimeError::UnexpectedIntegerOverflow` and `RuntimeError::ReceiptValidationError` into dedicated `near_chain::Error` variants (analogous to `Error::InvalidTransactions` / `Error::StorageError`) so the chunk containing the offending transaction/receipt is rejected/invalidated instead of panicking the node, closing out the outstanding `TODO(#2152)` and eliminating the transaction-triggered halt surface.

### Proof of Concept
Not independently reproduced in this review; a full PoC requires constructing a transaction or a receipt chain whose actions drive the arithmetic helpers backing `RuntimeError::UnexpectedIntegerOverflow` (e.g., balance/gas overflow paths in `runtime/runtime/src/lib.rs`, `core/primitives/src/congestion_info.rs`) or the `validate_receipt`/receipt-construction checks backing `RuntimeError::ReceiptValidationError` (`runtime/runtime/src/verifier.rs`) into their error branch, then applying the resulting chunk via `chain/chain/src/runtime/mod.rs:349-374` to observe the `panic!` fire. This step was not completed due to tool-call budget exhaustion; a follow-up session with terminal/code access should attempt to trigger these branches (e.g., via extreme deposit/gas values or maximal receipt sizes/action counts) to confirm exploitability from a single unprivileged transaction.
