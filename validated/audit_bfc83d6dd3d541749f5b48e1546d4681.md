## Title
`StateSnapshotRestoreMode::KvOnly` writes untrusted state-value chunks to `state_kv_db` without any Sparse Merkle range-proof verification - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
During backup/restore (the "phase 1.a" KV-only snapshot restore used by `RestoreCoordinator`), raw state-value chunks are written directly to the state KV DB while the `SparseMerkleRangeProof` that accompanies each chunk is silently discarded, unlike every other restore mode.

### Finding Description
`StateSnapshotRestore::add_chunk` branches on `restore_mode`: [1](#0-0) 

For `StateSnapshotRestoreMode::Default` and `TreeOnly`, the incoming `proof: SparseMerkleRangeProof` is passed into `JellyfishMerkleRestore::verify_chunk` / `add_chunk_impl`, which checks the chunk against the tree's frozen-node state and the expected root hash before anything is committed (see `storage/jellyfish-merkle/src/restore/mod.rs`, `verify_chunk`/`add_chunk_impl`). For `KvOnly`, however, the code path is:

```rust
StateSnapshotRestoreMode::KvOnly => {
    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
},
```

The `proof` parameter is never touched — `kv_restore.add_chunk` only takes `chunk` (the raw `(K, V)` pairs) and writes them to the state-value store; there is no call into any Merkle/range-proof verification routine for this branch. This mode is exactly what `RestoreCoordinator::run_impl`'s phase 1.a uses to restore the KV snapshot from an untrusted backup store: [2](#0-1) 

The only verification performed before this phase is a single, chunk-independent check that the backup **manifest's declared `root_hash`** matches a `TransactionInfoWithProof`-verified state-checkpoint hash for that version: [3](#0-2) 

That check only binds the *manifest's claimed* `root_hash` to the ledger; it does **not** verify that any individual chunk of `(key, value)` pairs pulled from the backup storage actually belongs to a tree with that root. Per-chunk binding is exactly what `SparseMerkleRangeProof` verification (`verify_chunk`) exists to provide — and it is skipped in `KvOnly` mode. A backup storage provider (or a corrupted/tampered backup archive) can therefore substitute arbitrary `(key, value)` pairs for the actual snapshot content in any chunk after the first, or entirely, without failing verification, as long as the manifest header (root hash + `TransactionInfoWithProof`) is otherwise consistent with something previously observed. Once committed, phase 1.b (`TransactionRestoreBatchController`, "only replay KV") replays subsequent transactions on top of this base state without recomputing/validating that base against the ledger's actual state root — the tree side of the same version is only reconstructed later (phase 2, `TreeOnly`) from a different, later snapshot; nothing in the flow re-derives or checks the `kv_snapshot.version` root hash against the raw KV rows that were written in phase 1.a.

### Impact Explanation
This breaks the state-integrity invariant that "Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding" and that "restore paths must not reinterpret committed data into a different ledger state." A node restoring from a backup (disaster recovery, new-node bootstrap via restore-cli, or any workflow using `RestoreCoordinator`) can be made to commit a state KV database that does not correspond to the real, consensus-agreed ledger state at that version, while the restore tool reports success. Because subsequent transaction replay (phase 1.b) is built on top of these unverified values, the resulting execution and any later exposed API/proof responses for that DB would be bound to a corrupted state rather than the correct VM/ledger result — this is a hard-fork-class divergence between the restoring node and the honest network, and a durable-ledger-corruption issue, not merely an availability/DoS concern.

### Likelihood Explanation
Exploitability requires control over, or tampering with, the backup storage source (e.g., a compromised or malicious S3/GCS backend, or a corrupted archive) supplying chunks to `StateSnapshotRestoreController` in `KvOnly` mode — this is a real, non-privileged trust boundary since backup storage is typically separate infrastructure from the consensus/validator trust domain, and restore is a standard operational procedure (this is exactly the "restore flows" surface the task calls out). No signature or on-chain privilege is needed; only control of the bytes served for chunks after manifest validation.

### Recommendation
In `StateSnapshotRestore::add_chunk`'s `KvOnly` branch, verify each chunk's `SparseMerkleRangeProof` against the target root hash (e.g., via a stateless/tree-free proof verification against `expected_root_hash`, or by still routing through `JellyfishMerkleRestore::verify_chunk` without persisting tree nodes) before writing to `kv_restore`. At minimum, `KvOnly` restore should not accept a `proof` argument and silently ignore it if it cannot be checked — that shape currently gives a false impression that this mode is proof-checked.

### Proof of Concept
1. Configure `RestoreCoordinator` against a backup storage implementation the attacker controls (or a tampered copy of legitimate backup archives).
2. Ensure the served manifest's `root_hash` and the accompanying `TransactionInfoWithProof`/`LedgerInfoWithSignatures` pass `txn_info_with_proof.verify(...)` and `root_hash == manifest.root_hash` (this only needs to be internally consistent with a genuinely-signed `LedgerInfo`/`TransactionInfo` at that version — attacker fully controls what bytes are served for the chunk files themselves).
3. Serve a `state_kv_db` chunk (`state_value_chunk_with_proof` / raw `(K, V)` pairs) containing tampered values (e.g., altered account balances) together with any `SparseMerkleRangeProof` bytes (they are never checked in the `KvOnly` path).
4. Observe: `StateSnapshotRestoreController::run_impl` → `StateSnapshotRestore::add_chunk` (`KvOnly` branch) commits the tampered `(K, V)` pairs to `state_kv_db` with no error, because `kv_restore.add_chunk(chunk)` never calls into proof verification, unlike `Default`/`TreeOnly`.
5. Phase 1.b replays real transactions on top of the tampered base state; the resulting restored node's state and API responses diverge from the honest network's ledger state at that version.

Note: I was not able to fully inspect `StateValueRestore::add_chunk`'s implementation itself (the type is referenced/imported into `storage/aptosdb/src/state_restore/mod.rs` but its defining module was not located within the indexed content), so I could not rule out a proof check being performed internally inside that type rather than at the call site. This is the one point of uncertainty in this finding, and I recommend it be verified directly against the full `storage/aptosdb/src/state_restore/` module contents (index size limits may have excluded that file) before treating this as fully confirmed — starting a full Devin session with file-system access would allow verifying `StateValueRestore::add_chunk`'s definition directly.

    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())
    }
