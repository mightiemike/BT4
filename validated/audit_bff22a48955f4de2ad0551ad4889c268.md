Good — `stringifyQueryForAdmin` uses `URLSearchParams.toString()` which properly delimits pairs with `&` and `=` (with percent-encoding), so the admin/OAuth/webhook HMAC path is not affected by this collision class. The vulnerability is isolated to the **App Proxy** signature canonicalization path, `stringifyQueryForAppProxy`, which joins `key=value` pairs with no delimiter at all.

### Title
Query-Parameter Boundary Collision in App Proxy HMAC Canonicalization Allows Forged/Replayed Requests to Pass Signature Verification - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The App Proxy signature verification builds its canonical string by concatenating `key=value` pairs with **no separator** between pairs, unlike the admin/OAuth path which uses `URLSearchParams` (delimited by `&`). Because arbitrary custom query parameter names/values in an App Proxy request are attacker-controlled (any anonymous visitor to the app's proxy URL), two semantically different parameter sets can produce an identical canonical string and therefore an identical valid `signature`, letting a previously-observed valid request be reinterpreted with different parameter boundaries while still passing `validateHmac`.

### Finding Description
`stringifyQueryForAppProxy` builds the string to be HMAC'd like this: [1](#0-0) 

Sorted keys are joined directly, `key=value`, back-to-back, with no `&` or other delimiter between pairs — the same class of ambiguity described in the report's `abi.encodePacked` finding (adjacent same-type/format fields concatenated without a boundary marker). This is confirmed by the project's own tests, which construct the exact same unseparated canonical strings, e.g. `` `logged_in_customer_id=1path_prefix=/apps/my_appshop=the shop URLtimestamp=${...}` ``: [2](#0-1) 

Because character boundaries between `key=value` pairs are not fixed, two different `(key, value)` sets can serialize to the identical byte string — e.g. `{a: "1b", c: "2"}` → `"a=1bc=2"` is indistinguishable from `{a: "1", bc: "2"}` → `"a=1bc=2"`. Since App Proxy requests are made by anonymous storefront visitors and can include arbitrary extra query parameters that Shopify forwards and signs as part of the request, an attacker who has observed one legitimately signed App Proxy URL (signatures are not secret; they appear directly in the forwarded request URL/logs/referrer) can re-partition the query string — moving characters across a key/value boundary into a differently-named parameter — and produce a new request whose canonical string, and therefore whose HMAC, is identical to the original, even though the parsed `(key, value)` pairs delivered to the app's business logic differ.

This contrasts with the admin/OAuth/webhook canonicalization path, which relies on `URLSearchParams`/percent-encoded, `&`-delimited serialization and is not subject to this ambiguity: [3](#0-2) 

The `APP_PROXY_SINGLE_VALUE_PARAMS` hardening only prevents *duplicate* reserved keys (`hmac`, `shop`, `signature`, `timestamp`) from appearing twice; it does nothing to prevent boundary-shifting collisions between a reserved key and an attacker-supplied custom key: [4](#0-3) 

### Impact Explanation
An App Proxy is reachable by any anonymous customer/browser (unprivileged actor). If exploited, this could allow acceptance of a request whose actual parsed parameters differ from what Shopify originally signed — e.g., smuggling/renaming a parameter such as `logged_in_customer_id` or `path_prefix` across the ambiguous boundary while keeping a previously valid `signature`, undermining the app's trust in `validateHmac`'s guarantee that the exact parameter set was signed by Shopify. This falls into the "accepted forged Shopify request" category.

### Likelihood Explanation
Exploitation requires: (1) the app to expose custom/attacker-influenced query parameters through its App Proxy route (common, since App Proxy passes through arbitrary storefront query strings), and (2) the attacker to obtain one legitimately-signed request/signature to reuse against a re-partitioned parameter set (signatures are visible, not secret, and appear in plain URLs). This is a non-trivial but realistic scenario for apps that trust additional query parameters beyond the reserved Shopify-set ones (`shop`, `timestamp`, `logged_in_customer_id`, `path_prefix`).

### Recommendation
Change `stringifyQueryForAppProxy` to join pairs with an explicit delimiter (e.g., `&`) between `key=value` entries, matching Shopify's actual App Proxy signing algorithm while still preventing boundary ambiguity, for example:
```ts
function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .map(([key, value]) => `${key}=${Array.isArray(value) ? value.join(',') : value}`)
    .join('&');
}
```
Note: any change here must exactly match Shopify's server-side App Proxy signing algorithm, since altering the delimiter changes the resulting hash for all existing valid requests — this must be verified against Shopify's official specification before deploying, since the current implementation may intentionally mirror Shopify's real (delimiter-less) format.

### Proof of Concept
1. Legitimate App Proxy GET request forwarded by Shopify to the app: `?a=1b&c=2&shop=store.myshopify.com&timestamp=T&signature=S`, where `S = HMAC(secret, "a=1bc=2shop=store.myshopify.com...")` (using `stringifyQueryForAppProxy`'s sorted, unseparated concatenation as shown in `stringifyQueryForAppProxy`, `packages/apps/shopify-api/lib/utils/hmac-validator.ts:60-66`).
2. Attacker observes `signature=S` in the URL (visible, non-secret) and crafts a new request: `?a=1&bc=2&shop=store.myshopify.com&timestamp=T&signature=S`.
3. `stringifyQueryForAppProxy` on the forged request sorts keys as `a, bc, shop, timestamp` and produces the identical concatenated string `"a=1bc=2shop=store.myshopify.com..."`.
4. `validateHmac` computes the same local HMAC and `safeCompare(hmac, localHmac)` returns `true`, accepting the forged request even though the actual `(key, value)` pairs (`{a: "1", bc: "2"}` instead of `{a: "1b", c: "2"}`) were never signed by Shopify as such.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
