Unbounded witness registration allows unbounded growth of `WitnessStore`, causing DoS of maintenance-cycle consensus processing and unpaginated witness-list RPC/HTTP endpoints - (File: `actuator/src/main/java/org/tron/core/actuator/WitnessCreateActuator.java`)

### Summary
`WitnessCreateActuator.validate()`/`execute()` allows any funded account, via an ordinary broadcast transaction (`WitnessCreateContract`), to add an unbounded number of entries to `WitnessStore` — the only gate is a balance check (`getAccountUpgradeCost()`, a fixed 9999 TRX fee) and an "address not already a witness" check. There is no limit on the total number of witnesses that can exist. This is directly analogous to the `addPool` bug class: an actor-controlled, unbounded-growth list that is later iterated in full by core protocol/consensus logic and by RPC/HTTP handlers, creating a DoS vector as the list grows.

### Finding Description
`WitnessCreateActuator.validate()` only checks address validity, URL validity, account existence, "not already a witness", and sufficient balance for `dynamicStore.getAccountUpgradeCost()`: [1](#0-0) 

`createWitness()` then unconditionally inserts a new `WitnessCapsule` into `WitnessStore` with no cap on the total witness count: [2](#0-1) 

`WitnessStore.getAllWitnesses()` iterates the entire underlying DB to materialize the full witness list, with no bound: [3](#0-2) 

This unbounded list is fully iterated in several core-path locations, exactly like `GLPbackingNeeded` iterating `poolInfo` in the referenced report:

1. **Consensus maintenance (every maintenance cycle, run by every node)** — `MaintenanceManager.doMaintenance()` calls `consensusDelegate.getAllWitnesses()` multiple times and iterates the full list to accumulate rewards/vote counts and to build `newWitnessAddressList`: [4](#0-3) [5](#0-4) 

2. **`WitnessStore.getWitnessStandby()`** sorts the entire witness list (an O(n log n) sort over all witnesses) on every call: [6](#0-5) 

3. **Unpaginated RPC/HTTP endpoints** — `Wallet.getWitnessList()` returns the entire, unbounded witness set with no offset/limit, unlike the paginated variant: [7](#0-6) 
This is exposed via `ListWitnessesServlet` and the corresponding gRPC `ListWitnesses` RPC, both callable by anonymous clients.

4. **`Wallet.getPaginatedNowWitnessList()`** also loads and sorts the *entire* witness list before applying the requested offset/limit — pagination is applied only after the full-list materialization/sort, so it does not protect against the underlying store size: [8](#0-7) 

Because witness creation is a normal, unprivileged actuator (any account with a sufficient balance can call it repeatedly with different funded accounts), and because no ceiling exists on the number of witnesses that `WitnessStore` can hold, an attacker with sufficient TRX can inflate the witness set arbitrarily. This directly parallels the reported `addPool` issue: an append-only, actor-triggerable list with no size cap, later fully iterated by core protocol logic (`doMaintenance`, called every maintenance interval by every full node/witness) and by anonymous-facing API handlers (`ListWitnesses`, `GetPaginatedNowWitnessList`), all of which scale linearly (or worse, due to sorting) with the number of witnesses.

### Impact Explanation
As the witness set grows large:
- Every node's periodic `doMaintenance()` call becomes slower (multiple full iterations, and `getWitnessStandby`/`sortWitnesses` performs full sorts), potentially causing block-production delays or missed maintenance windows if the cost grows large enough — a consensus-availability risk shared by all nodes running the chain, not just the attacker.
- `ListWitnesses`/`GetWitnessList` and `GetPaginatedNowWitnessList` RPC/HTTP handlers become increasingly expensive per call (unbounded list construction + sort), enabling a resource-exhaustion DoS against public API nodes reachable by anonymous clients.
- Unlike the `addPool` report where impact is "bricking" core protocol functionality outright via gas-limit exhaustion, java-tron's maintenance loop and API handlers are Java in-process CPU work rather than metered EVM gas, so the practical effect is degraded performance/availability rather than an outright halt — but the underlying "unbounded array growth iterated by core logic" defect is the same class of bug.

### Likelihood Explanation
Low-to-moderate. Unlike the report's "malicious/erring privileged admin" precondition, this analog requires no privileged role — any account can call `WitnessCreateContract`. However, each witness registration costs `getAccountUpgradeCost()` (9999 TRX per witness), so scaling to a magnitude sufficient to meaningfully degrade performance requires substantial capital, making it an economically costly but not privilege-gated attack.

### Recommendation
Introduce an explicit cap on the number of witnesses `WitnessCreateActuator.validate()` will allow (e.g., check `witnessStore.getAllWitnesses().size()` or maintain a counter in `DynamicPropertiesStore` and reject creation once a maximum is reached). Additionally, avoid materializing/sorting the entire `WitnessStore` in unpaginated API paths (`Wallet.getWitnessList()`, `getWitnessStandby()`), and ensure `getPaginatedNowWitnessList()` avoids doing a full-list sort before applying pagination.

### Proof of Concept
1. Fund N distinct accounts with at least `getAccountUpgradeCost()` (9999 TRX) each.
2. Broadcast N `WitnessCreateContract` transactions, one per funded account, via the public gRPC/HTTP `createwitness` endpoint. `WitnessCreateActuator.validate()` imposes no ceiling on total witness count, so all N succeed as long as each account is individually funded and not already a witness: [9](#0-8) 
3. After N registrations, `WitnessStore` contains the original set plus N new entries.
4. Observe: (a) `doMaintenance()` executes longer per call as witness count grows, since it fully iterates `consensusDelegate.getAllWitnesses()` several times per cycle; (b) calling the public `ListWitnesses` RPC/HTTP endpoint (`Wallet.getWitnessList()`) returns and serializes the entire, unbounded witness set on every call, with response cost scaling linearly with N.
