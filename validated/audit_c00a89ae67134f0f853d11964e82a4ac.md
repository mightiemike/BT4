### Title
Stale rejection weight surviving a signer's flip from reject to accept lets `SignCoordinator` wrongfully abort an already-approved block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::handle_signer_message` (in `stackerdb_listener.rs`) tallies per-signer approval and rejection weight for a block into a single shared `BlockStatus`. The rejection branch is guarded against double-counting by checking the *same* set (`responded_signers`) that the approval branch also writes into, but the approval branch itself never checks whether that signer's weight was already counted on the rejection side, nor does it clear the stale rejection weight when a signer later flips to approve. This lets one signer's weight be counted in `total_weight_rejected` and `total_weight_approved` at the same time, which the `SignCoordinator::wait_for_signer_signatures_from_stackerdb` consumer (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) uses to decide, respectively, whether to abort the block as globally rejected or accept it as signed.

### Finding Description
`BlockStatus` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82`) holds one `responded_signers: HashSet<u32>` and separately accumulates `total_weight_approved` / `total_weight_rejected`.

On an `Accepted` response the code does:
```rust
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [1](#0-0) 

On a `Rejected` response the code does:
```rust
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [2](#0-1) 

The reject path's guard (`responded_signers.insert`) correctly prevents double counting when a signer accepts and *then* rejects (their slot is already in `responded_signers`, so the second `insert` returns `false` and the reject weight is skipped). But the reverse order is unguarded: if a signer rejects first (adding their slot to `responded_signers` and their weight to `total_weight_rejected`) and later sends an `Accepted` response for the same block, the accept branch only checks `gathered_signatures.contains_key(&slot_id)` — which is still `false` because this signer never accepted before — so `total_weight_approved` is incremented by the same signer's weight, while `total_weight_rejected` is never decremented. The signer's weight is now counted on both sides simultaneously.

This differs from the equivalent, correctly-guarded logic in `stacks-signer/src/signerdb.rs::add_block_rejection_signer_addr`, which explicitly checks for an existing signature before storing a rejection and is exercised by the `reject_then_accept`/`accept_then_reject` regression tests [3](#0-2) [4](#0-3) . The miner-side `stackerdb_listener.rs` tally has no analogous symmetric protection.

`SignCoordinator::wait_for_signer_signatures_from_stackerdb` consumes these two counters to make a binary decision, checking rejection first:
```rust
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...);
}
``` [5](#0-4) 

Because rejection is checked first, a stale rejection weight that lingers after the rejecting signer(s) actually flipped to approve can make `total_weight_rejected` cross the "rejection makes 70% impossible" threshold even though the *current* set of signer opinions (including the flip) has genuinely reached the 70% approval threshold. The miner then takes the `SignersRejected` branch and gives up on a block that a correctly-implemented tally would have accepted.

### Impact Explanation
This breaks the equality the coordinator is meant to enforce: "reject-tally and accept-tally are mutually exclusive per signer, and the decision reflects each signer's *current* vote." A minority of signers (as few as one, at a near-70/30 boundary) can, purely as an artifact of message ordering (reject, then accept — a legitimate, permitted state-machine transition per `docs/signer-flows.md`'s own model, where "a rejection is a revocable opinion"), cause the miner's local coordinator to wrongfully treat a validly, currently-approved block as rejected. This is a minority-triggerable divergence between the miner's local verdict and the true, current signer-set opinion — i.e. a wrongful reject / temporary tip disagreement at the block-production layer, distinct from and not caught by the (correctly-guarded) authoritative on-chain `verify_signer_signatures` check.

### Likelihood Explanation
No majority collusion is required: any single signer that first rejects a proposal (a routine, expected event, e.g. due to transient chainstate mismatch) and later legitimately reconsiders and accepts triggers the stale-counter condition. Because the rejection-threshold check runs before the approval-threshold check in `wait_for_signer_signatures_from_stackerdb`, the corrupted state directly produces the wrong outcome whenever both counters happen to straddle their respective thresholds — a state reachable in ordinary operation, not requiring any privileged access beyond being one of the ordinary registered signers.

### Recommendation
Make the accept and reject branches mutually exclusive over the same underlying per-signer state, mirroring the fix already applied in `stacks-signer/src/signerdb.rs`:
- Before incrementing `total_weight_approved` on an `Accepted` message, check whether this `slot_id` previously contributed to `total_weight_rejected` and, if so, subtract that weight back out (or otherwise migrate the previously-recorded vote instead of leaving both counters populated).
- Symmetrically ensure the reject branch retracts any previously-recorded approval weight, not just skip re-adding via `responded_signers`.
- Track vote membership (approved vs rejected) per `slot_id` as an enum/lookup rather than two independent weight counters plus a shared "has responded" set, so a flip always transfers weight rather than accumulating it in both buckets.

### Proof of Concept
1. Configure a reward-cycle signer set with a signer S whose weight, combined with others' rejections, is exactly at the 30%+ε "block rejection" boundary and also exactly at the 70%-ε "approval" boundary when S's vote is excluded.
2. During block signing, have S broadcast a `BlockResponse::Rejected` for the proposal (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:486-573`) — `total_weight_rejected` now includes S's weight and crosses (or nearly crosses) `total_weight - weight_threshold`.
3. Have S then legitimately reconsider (e.g. after `check_block_against_signer_db_state` re-evaluation on the signer side) and broadcast `BlockResponse::Accepted` for the same `block_sighash` — the accept branch (`stackerdb_listener.rs:443-465`) adds S's weight to `total_weight_approved` as well, since `gathered_signatures` never contained S's slot.
4. Both `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and `total_weight_approved >= weight_threshold` can now be simultaneously true; `SignCoordinator::wait_for_signer_signatures_from_stackerdb` evaluates the rejection branch first and returns `NakamotoNodeError::SignersRejected`, discarding a block that in reality has legitimate 70% current support.
