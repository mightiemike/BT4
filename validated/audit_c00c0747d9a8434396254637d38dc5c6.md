### Title
Replay-verify accepts execution results with a divergent state root — `state_checkpoint_hash` is never checked in `TransactionOutput::ensure_match_transaction_info` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by `db-tool`'s `replay-on-archive` (and other replay/debug tooling) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain for that version. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but it explicitly does **not** check `state_checkpoint_hash` (nor the newer hot-state/position-state checkpoint hashes carried by `TransactionInfoV1`).

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . Its body validates status, gas, write-set hash, and event root hash [2](#0-1) , but then explicitly stops with a comment acknowledging that checkpoint hashes are skipped: [3](#0-2) 

This function is the sole correctness gate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes historical transactions with `AptosVMBlockExecutor` and calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` to decide pass/fail for each replayed transaction [4](#0-3) .

Because `state_checkpoint_hash` (the authenticated post-state Merkle root committed to the ledger at that version) is never compared against the state root that would result from applying the locally re-executed write set to the committed state tree, this tooling can report "successful replay" even when the actual state root produced by re-execution diverges from the state root that was originally committed and voted on by validators. A write-set can hash identically (matching `state_change_hash`) while `state_checkpoint_hash` differs due to divergent existing state under the applied deltas — i.e., a fork-inducing implementation bug (e.g., a hard-fork or non-deterministic VM bug affecting derived resources not directly captured by the write op values used to compute `state_change_hash`, or a bug in the merkle/state-checkpoint hashing logic itself) would not be detected by this specific integrity gate.

This matches the state-integrity gate criterion "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Committed state that differs from the correct VM result... accepted as valid," because the verification path whose job is to catch exactly this class of divergence silently omits the check.

### Impact Explanation
Replay-verify / replay-on-archive is one of Aptos's primary safety nets for catching consensus-breaking bugs before or after they reach mainnet (used in CI-based replay-verify pipelines per `testsuite/replay-verify/`). If this tool cannot detect a state-root divergence for a given historical transaction because `state_checkpoint_hash` (and the V1 hot-state/position-state checkpoint hashes) are never compared, a genuine hard-fork bug in execution or in state-checkpoint hash computation could pass replay-verify undetected. This weakens confidence in a critical detection mechanism for state-commitment correctness, which is exactly the class of "silently accepted wrong state" impact the scope calls Critical/High — even though the bug is in tooling rather than in the online consensus/commit path itself, it directly undermines the mechanism relied upon to catch and prevent state divergence from being missed until after other nodes have already diverged.

### Likelihood Explanation
Likelihood of the gap being exercised is Medium: it only manifests when write-set-hash-preserving executions produce a different derived state (e.g., subtle non-determinism, floating logic in state-checkpoint/hot-state hash computation, or a bug only visible in the state tree rather than in the write set values themselves). This is a narrow class of bugs, but it is precisely the class replay-verify exists to catch, and the omission is committed in code with an explicit TODO acknowledging the gap rather than a silent oversight, indicating it is a known, currently-unmitigated blind spot in the mainnet safety-net tooling.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` for `TransactionInfoV1`) against a state root computed from applying the re-executed write set to the appropriate state view, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state-root features are enabled by default. At minimum, `replay_on_archive.rs` should independently recompute and check the state checkpoint hash after each transaction batch rather than relying solely on this comparator.

### Proof of Concept
No executable PoC is provided; this is a static-analysis code-review finding based on:
1. The explicit `ensure!` checks omit `state_checkpoint_hash` comparison in `ensure_match_transaction_info` [5](#0-4) .
2. `replay_on_archive.rs::execute_and_verify` uses only this function as its correctness oracle per replayed transaction [4](#0-3) .

Note: I was unable to fully trace whether other call sites of `ensure_match_transaction_info` (e.g., `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) perform an additional independent state-root check that would compensate for this gap; I could not retrieve those file contents within the available tool budget, so it remains possible that one of those callers separately validates the state checkpoint hash, which would reduce the impact to be scoped only to `replay_on_archive.rs`'s path.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
