### Title
L1Handler transactions are capped by a hardcoded global gas bound instead of the fee actually paid on L1, causing legitimate cross-chain messages to revert and be permanently consumed - (File: `crates/blockifier/src/transaction/l1_handler_transaction.rs`)

### Summary
When an L1→L2 message is executed as an `L1HandlerTransaction`, the sequencer does not size the execution's gas budget according to the fee the L1 sender actually paid for the message. Instead it always uses a fixed, protocol-wide constant, `l1_handler_max_amount_bounds`, and only checks that `paid_fee_on_l1` is non-zero. This mirrors the ZetaChain finding's root cause: a resource limit that should reflect what the sender specified/paid for is replaced by a hardcoded value, so transactions that legitimately need more gas revert with an out-of-gas-style failure, while the underlying cross-chain message is still consumed and cannot be resubmitted, permanently losing the L1 sender's deposit/intent.

### Finding Description
`L1HandlerTransaction::execute_raw` sizes the Sierra gas budget solely from the global versioned constant `l1_handler_max_amount_bounds`, ignoring `self.paid_fee_on_l1` entirely for gas sizing purposes: [1](#0-0) 

After execution, the same fixed bound is used as the enforced resource cap via `FeeCheckReport::check_all_gas_amounts_within_bounds`, and if exceeded, the whole execution is reverted: [2](#0-1) 

The only check tied to what the L1 sender actually paid is a check that the paid fee is non-zero — explicitly acknowledged in the code as insufficient and left as a TODO: [3](#0-2) 

The default protocol constant is: [4](#0-3) 

Critically, per the L1 handler transaction lifecycle, once an `L1HandlerTransaction` is included/committed in a block — reverted or not — it transitions from `Pending` to `Committed` in the L1 Provider's transaction manager, meaning the corresponding L1→L2 message nonce is treated as consumed and cannot be resubmitted: [5](#0-4) 

This is structurally identical to the ZetaChain root cause: a resource/gas limit that is supposed to reflect the sender's payment/specification is instead a hardcoded, protocol-fixed value. Any contract logic invoked by the L1 message that legitimately requires more than the fixed `l1_handler_max_amount_bounds.l2_gas` (or `l1_gas`/`l1_data_gas`) will revert post-execution regardless of how much the L1 sender actually paid, and — unlike an ordinary V3 transaction where the sender chooses (and pays for) their own resource bounds — the L1 sender of a bridging/messaging call has no ability to raise this bound, since it is a global protocol constant, not a per-message field.

### Impact Explanation
Because a committed `L1HandlerTransaction` consumes the L1→L2 message regardless of whether execution reverted, an under-provisioned but otherwise valid message (e.g., a bridge deposit `handle_deposit` call whose logic needs slightly more Sierra gas than the fixed cap allows) will revert on L2, discard all state changes (`execution_state.abort()`), yet the message can never be resent from L1. Funds or state updates intended by the L1 sender are permanently unrecoverable on L2 even though the L1 side already considers the message sent/paid-for. This matches the "concrete loss or permanent freezing of funds" impact bar via a single L1 sender action reaching blockifier execution/fee accounting.

### Likelihood Explanation
This requires no privileged actor — it is triggered purely by a normal L1→L2 message whose L2-side execution (calldata-dependent control flow, loops, or contract complexity) happens to exceed the fixed `l1_handler_max_amount_bounds`. Because the bound is a governance-set global constant and not something the L1 sender can adjust or query in advance to guarantee sufficiency for their specific call, any contract/message combination near or above the bound is naturally exposed, especially as calldata size or contract logic complexity grows.

### Recommendation
Tie the enforced gas bound for an `L1HandlerTransaction` to the fee actually paid on L1 (`paid_fee_on_l1`), converting it into an equivalent gas amount using the current gas prices, rather than solely relying on the fixed `l1_handler_max_amount_bounds`. Alternatively, ensure the on-L1 message-sending flow (and its gas/fee estimation) is guaranteed to always satisfy the L2 protocol bound, and add a pre-execution accounting check (not just a "fee != 0" check) that ties `paid_fee_on_l1` to the resource bound being enforced, so that a message failing due to insufficient provisioned gas doesn't result in an unrecoverable consumed-but-reverted message.

### Proof of Concept
1. An L1 contract calls `sendMessageToL2` targeting an L2 contract whose `l1_handler` entry point performs more computation/calldata processing than what `l1_handler_max_amount_bounds.l2_gas` (or `l1_gas`/`l1_data_gas`) allows for the given payload, while still paying a valid non-zero fee.
2. The sequencer's L1 events scraper picks up the `LogMessageToL2` event and constructs an `ExecutableL1HandlerTransaction` as shown in [6](#0-5) .
3. During block building/validation, `L1HandlerTransaction::execute_raw` bounds gas execution strictly to `l1_handler_max_amount_bounds.l2_gas.0` [7](#0-6) , and the post-execution check in `FeeCheckReport::check_all_gas_amounts_within_bounds` fails once actual gas usage exceeds this fixed bound, exactly as exercised in [8](#0-7) .
4. The transaction is still included in the block (`Ok(l1_handler_tx_execution_info(None, receipt, Some(fee_check_error.into())))`), the L1 provider marks the corresponding L1 message as `Committed`/consumed per the flow in [5](#0-4) , and the message can never be resent, leaving any L1-side funds/intent tied to that message stuck.

fn test_l1_handler_resource_bounds(#[case] resource: Resource, #[case] new_bound: GasAmount) {
    let test_contract = FeatureContract::TestContract(CairoVersion::Cairo1(RunnableCairo1::Casm));

    // Set to true to ensure L1 data gas is non-zero.
    let use_kzg_da = true;

    let mut block_context = BlockContext::create_for_account_testing_with_kzg(use_kzg_da);
    let chain_info = block_context.chain_info.clone();
    let mut state = test_state(&chain_info, BALANCE, &[(test_contract, 1)]);
    let contract_address = test_contract.get_instance_address(0);

    // Modify the resource bound for the tested resource.
    let os_constants = Arc::make_mut(&mut block_context.versioned_constants.os_constants);
    match resource {
        L1Gas => os_constants.l1_handler_max_amount_bounds.l1_gas = new_bound,
        L2Gas => os_constants.l1_handler_max_amount_bounds.l2_gas = new_bound,
        L1DataGas => os_constants.l1_handler_max_amount_bounds.l1_data_gas = new_bound,
    }

    let tx = l1handler_tx(Fee(1), contract_address);

    let execution_info = tx.execute(&mut state, &block_context).unwrap();

    assert_matches!(
        execution_info,
        TransactionExecutionInfo {
            validate_call_info: None,
            execute_call_info: None,
            fee_transfer_call_info: None,
            revert_error: Some(RevertError::PostExecution(FeeCheckError::MaxGasAmountExceeded {
                resource: r,
                max_amount,
                actual_amount
            })),
            // TODO(Arni): consider checking other fields of the receipt.
            receipt: TransactionReceipt { fee, .. },
        } if r == resource && new_bound == max_amount && actual_amount > max_amount && fee == Fee(0)
    );
