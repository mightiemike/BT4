### Title
Protocol-relative URL bypasses `isSafe`/`sanitizeRedirectUrl` origin allowlist, enabling open redirect via `renderAppBridge` - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts)

### Summary
`sanitizeRedirectUrl`'s internal `isSafe` check is meant to guarantee that any URL passed to `renderAppBridge` (and ultimately opened via `window.open()` in an authenticated admin/embedded context) resolves to the app's own origin. A protocol-relative input such as `//attacker.com` bypasses both of `isSafe`'s structural checks because `FILE_URI_MATCH` only rejects three-or-more consecutive slashes and `INVALID_RELATIVE_URL` is evaluated against `url.pathname` of the *already-resolved* `URL` object, not the raw input string — so once WHATWG `URL` parsing absorbs `attacker.com` into the host component, the pathname check no longer sees anything unsafe.

### Finding Description
`isSafe` in `validate-redirect-url.ts` performs these checks, in order: [1](#0-0) 

1. `FILE_URI_MATCH = /\/\/\//` and `WHITESPACE_CHARACTER` are tested against the raw `redirectUrl` string.
2. `url = new URL(redirectUrl, domain)` is parsed.
3. `INVALID_RELATIVE_URL = /[/\\][/\\]/` is tested against `url.pathname` (the parsed pathname, **not** the raw string).
4. `url.protocol` must be `http:`/`https:`.

For input `redirectUrl = "//attacker.com"` and `domain = config.appUrl` (e.g. `https://myapp.com`):
- `FILE_URI_MATCH` requires **three** slashes; `//attacker.com` has only two, so it does not match.
- `new URL("//attacker.com", "https://myapp.com")` is standard WHATWG protocol-relative resolution and evaluates to `https://attacker.com/` — a completely different origin than `domain`.
- `url.pathname` for that resolved URL is `"/"`, so `INVALID_RELATIVE_URL` (which only inspects the pathname, and only after the host has already been hijacked) does not fire.
- `url.protocol` is `https:`, which passes the allow-list.

The function therefore returns `true` and `sanitizeRedirectUrl` returns `new URL("//attacker.com", domain)` = `https://attacker.com/`, despite the intended invariant that the resulting URL must stay within `config.appUrl`'s origin.

This value flows directly into `renderAppBridge`, which serializes it into an injected `<script>window.open(destination, target)</script>` in the HTML response: [2](#0-1) 

`renderAppBridge` is invoked by the `redirect()` helper (`redirect.ts`) whenever a bounce/embedded request needs to redirect, passing `redirectTo.url` built from the URL an app route supplies to `redirect(url)`: [3](#0-2)  Note that `redirect.ts` itself only uses the origin check (`isSameOrigin`) to decide whether to merge search params — it does not block cross-origin redirects — leaving `sanitizeRedirectUrl`/`isSafe` as the sole intended origin-allowlist gate: [4](#0-3) 

If any app route built on this library forwards attacker-controlled input (e.g., a query parameter) into `redirect(url)`/`redirectTo.url`, this single-layer gate is defeated by a protocol-relative string.

### Impact Explanation
Successful exploitation causes the embedded/authenticated admin browser context to execute `window.open("https://attacker.com/", target)`, redirecting (or opening a new window pointed at) an attacker-controlled origin from within a trusted, authenticated Shopify Admin embedded frame. This matches an open-redirect class impact in an authentication-adjacent flow, and depending on `target` (`_top`/`_parent`) can fully navigate the authenticated admin tab to the attacker's site, enabling phishing that impersonates the merchant's session context.

### Likelihood Explanation
Exploitability depends on a host app forwarding attacker-influenced input into the `redirect()`/`renderAppBridge` `url`, which is an app-specific precondition, not a default library behavior on its own. However, the library-level check that is supposed to be a defense-in-depth backstop (`DESTINATION_ALLOWLIST`/`isSafe`) is bypassable with a trivial, well-known payload (`//attacker.com`), so any app that does pass user-influenced data into this path is not protected by the library as expected.

### Recommendation
Fix `isSafe` to validate the **origin** of the resolved URL against `domain`'s origin explicitly, rather than relying on regexes over the raw string and the resolved pathname. E.g., after parsing, compare `url.origin === new URL(domain).origin` (or use `URL.canParse`/`new URL(redirectUrl)` first to detect absolute/protocol-relative inputs before merging with `domain`), and reject any case where the origin does not match.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from 'packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url';

const APP_URL = 'https://myapp.com';

test('protocol-relative URL bypasses isSafe and escapes app origin', () => {
  const result = sanitizeRedirectUrl(APP_URL, '//attacker.com');
  // BUG: current code returns https://attacker.com/ instead of throwing
  expect(result.origin).not.toEqual(new URL(APP_URL).origin);
  expect(result.toString()).toEqual('https://attacker.com/');
});
```
Expected (fixed) behavior: `sanitizeRedirectUrl(APP_URL, '//attacker.com')` should throw `ShopifyError` because `result.origin !== new URL(APP_URL).origin`.

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
