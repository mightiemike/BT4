### Title
Global signer state agreement threshold uses floor division while block-approval threshold uses ceiling division, causing consensus divergence - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs` compute the `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` quorum with a plain floor division (`total_weight * threshold / 10`), while the canonical Nakamoto block-approval threshold computed by `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs` uses ceiling division (adds 1 unless evenly divisible). For any `total_weight` where `total_weight * threshold` is not a multiple of 10, the two functions disagree on the minimum weight required to "reach agreement," exactly analogous to the reported ULTI bug where two logically-equivalent scaling computations used different rounding/scale conventions and broke the intended threshold guarantee.

### Finding Description
`compute_voting_weight_threshold` (the value actually used to gate Nakamoto block signature acceptance in `stackslib/src/chainstate/nakamoto/mod.rs:1180-1187`, and consumed by `stackerdb_listener.rs` and `stacks-signer/src/v0/signer.rs` to decide `weight_threshold`/`min_weight` for broadcasting/accepting a block) computes: [1](#0-0) 

```
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
(total_weight * threshold) / 10 + ceil
```

This is a strict *ceiling* division — it always rounds the required weight up.

In contrast, `GlobalStateEvaluator::reached_agreement` in `libsigner/src/v0/signer_state.rs` computes the same conceptual threshold with a plain *floor* division and no rounding adjustment: [2](#0-1) 

```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```

Both functions consume the same constant, `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD`, defined in `stackslib/src/core/mod.rs` and re-used across `stackslib`, `libsigner`, and `stacks-signer`. For any `total_weight` such that `total_weight * threshold` is not evenly divisible by 10, `compute_voting_weight_threshold` requires one more unit of weight than `reached_agreement` does. Example: with `threshold = 7` and `total_weight = 13`, `compute_voting_weight_threshold` yields `ceil(91/10) = 10`, while `reached_agreement` accepts a vote weight of `floor(91/10) = 9`.

`GlobalStateEvaluator` is used by `StackerDBListener::new` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:249`) to build the state used to determine the currently agreed-upon active miner, burn view, replay-transaction set, and protocol version among signers — i.e., which tenure is considered valid and which miner state the network is converging on. `compute_voting_weight_threshold`, on the other hand, is the actual on-chain-consensus-relevant gate for whether a Nakamoto block has enough signer weight to be considered signed (`stackslib/src/chainstate/nakamoto/mod.rs:1180-1187`), and is duplicated again in `stacks-signer/src/v0/signer.rs` (`handle_block_pre_commit`, `store_and_process_block_signature`) for the same purpose. [3](#0-2) [4](#0-3) 

Because these two independently-implemented threshold formulas can disagree by exactly one unit of weight, a set of signers whose combined weight equals the floor-rounded (weaker) threshold can force `GlobalStateEvaluator` to declare "global agreement" on a current miner / burn view / tx replay set even though that same weight would be insufficient to actually sign a Nakamoto block under `compute_voting_weight_threshold`. This breaks the intended equality that "global signer-state agreement" and "block-signing quorum" represent the same 70%-style consensus threshold.

### Impact Explanation
This is a minority-triggerable divergence in state-machine agreement logic among the signer set (not requiring a majority of signers, an operator key, or admin action) — it only requires a total signer weight distribution such that `total_weight * threshold` is not a multiple of 10, which is the common case. The consequence is a subset of signers just below the true block-approval quorum can cause `GlobalStateEvaluator::reached_agreement` to register consensus on a `current_miner`/`tx_replay_set`/`burn_view` state that doesn't correspond to a state that could actually gather enough weight to sign a block. This can cause temporary tip/tenure-view disagreement across the signer network (nodes converge on a "global state" that isn't truly quorum-backed), which maps to the High-severity class of "minority-triggerable sortition/static-validation divergence, temporary tip disagreement."

### Likelihood Explanation
Likelihood is high in practice: because signer weights are integers (reward-slot based) and the threshold constant is a single-digit numerator over 10, most non-trivial `total_weight` values will not make `total_weight * threshold` divisible by 10, so the off-by-one divergence between floor and ceiling occurs routinely, not just in edge cases. No special conditions or privileged access are needed to trigger it — it happens purely as a function of the reward-cycle's signer weight distribution.

### Recommendation
Unify the threshold computation into a single shared function reused by both `NakamotoBlockHeader::compute_voting_weight_threshold` and `GlobalStateEvaluator::reached_agreement`/`reached_disagreement`, using the same ceiling-division semantics in both places so that "global state agreement" and "block-signing quorum" always refer to the identical weight threshold.

### Proof of Concept
1. Configure a reward cycle where the signer set has `total_weight = 13` and `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7` (70%).
2. `compute_voting_weight_threshold(13)` returns `ceil(13*7/10) = ceil(9.1) = 10` — a Nakamoto block needs signature weight ≥ 10 to be accepted per `stackslib/src/chainstate/nakamoto/mod.rs:1180-1187`.
3. A colluding subset of signers with combined weight 9 (below the real block-signing quorum of 10) sends `StateMachineUpdate`s agreeing on a specific `current_miner`/`burn_block`/`tx_replay_set`.
4. `GlobalStateEvaluator::reached_agreement(9)` computes `floor(13*7/10) = floor(9.1) = 9`, and `9 >= 9` is `true` — so `determine_global_state()` (and `determine_global_burn_view`, `find_majority_prefix_replay_set`) declares this the agreed global state, even though this weight is one unit short of what is actually needed to sign a block.
5. Downstream consumers of the (incorrectly agreed) global state (e.g. `StackerDBListener`, used to decide miner activity/tenure view) diverge from nodes/consumers that rely on the stricter `compute_voting_weight_threshold`, producing inconsistent views of the current tenure/miner across the signer set until a real quorum forms.

Note: I was unable to fully trace every downstream consumer of `GlobalStateEvaluator::determine_global_state` (e.g. how tenure-extend or miner activation logic ultimately acts on this state) within the available indexed context, so the exact operational blast radius of the resulting tip disagreement could not be fully confirmed and would benefit from deeper tracing in a full Devin session with complete file access.

    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {

            )
        })
    }
