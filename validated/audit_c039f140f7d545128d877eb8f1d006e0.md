## Finding

### Title
Replay-verify skips state/hot-state checkpoint root comparison, allowing corrupted state roots to pass as "verified" — (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the sole correctness check used by the chunk-replay path (`ChunkExecutorInner::verify_execution`, driven by `db-tool`'s `replay-verify` / `restore --verify` flows), never compares the recomputed state-checkpoint root, hot-state checkpoint root, or position-state checkpoint root against the authenticated `TransactionInfo` pulled from a signed backup/archive. It only checks transaction status, gas used, the write-set hash (`state_change_hash`), and the event-root hash. A local execution/state-tree bug that corrupts the resulting Merkle root — while still producing byte-identical write ops and events for each transaction — will silently pass `replay-verify` as a successful, byte-for-byte match, even though the two ledgers' committed state roots diverge.

### Finding Description
`ensure_match_transaction_info` is defined at: [1](#0-0) 

It validates only:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- event-root hash vs `txn_info.event_root_hash()`

It never touches `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`. The code itself documents the gap in a `TODO(trading-native)` comment right above the `Ok(())` return:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the only correctness gate used by `ChunkExecutorInner::verify_execution`, the replay path used for `db-tool replay-verify` / restore verification: [2](#0-1) 

Contrast this with the normal chunk-apply/commit path (`update_ledger`), which does feed the archived `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` into `DoStateCheckpoint::run()` as `known_state_checkpoints` so a locally recomputed mismatch is detected and rejected: [3](#0-2) 

But `verify_execution` (the replay-verify path) bypasses `DoStateCheckpoint` entirely — it calls `DoGetExecutionOutput::by_transaction_execution` and then only calls `ensure_match_transaction_info` on each output, so the state/hot-state/position-state checkpoint roots recorded in the archive's proof-bound `TransactionInfo` are never re-derived and compared: [4](#0-3) 

Because a `TransactionInfo`'s hash (and thus its accumulator-proof binding) covers `state_change_hash`, `event_root_hash`, `state_checkpoint_hash`, etc., but `ensure_match_transaction_info` only re-derives two of those fields, this comparator is not a sufficient proxy for "the state root this transaction produced is correct." A defect anywhere in state-tree materialization (Jellyfish Merkle updates, hot-state promotion/eviction, or the "trading-native" position-state tree) that leaves per-transaction write ops/events unchanged but corrupts the cumulative checkpoint root will not be caught by replay-verify.

### Impact Explanation
`replay-verify`/restore-verify is the primary tool node operators and the Aptos Labs release process use to confirm that a given VM/storage build reproduces history correctly (an essential pre-hard-fork and pre-upgrade sanity check, and the mechanism operators use to validate restored archives). Since the checkpoint-root comparison is skipped, this tool can report a "clean" replay over a range of history even though the locally computed ledger state (state tree root, hot-state root, or position-state root) has silently diverged from the authenticated value bound into the accumulator/ledger-info signature chain. This is exactly the "Hard-fork-only divergence during commit, replay, or proof verification" and "authenticated ... proof-bearing responses must stay bound to the right ... root" class of impact: a wrong root can be accepted as verified.

### Likelihood Explanation
This is not remotely triggerable by an unprivileged attacker directly, but it removes a critical safety net for detecting state-root divergence bugs (e.g., regressions in JMT batch-update code, hot-state promotion logic, or the new position-state tree) during the very process meant to catch such regressions before they cause a chain split or corrupt an operator's restored database. Given that the gap is self-acknowledged in the code as a known TODO tied to the not-yet-fully-enabled "trading-native"/position-state feature, but the same comparator function is unconditionally used for the mainnet-critical `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields too, the exposure already exists today for any state-root-affecting bug, independent of whether position-state verification is enabled.

### Recommendation
Extend `ensure_match_transaction_info` (or the call sites in `verify_execution`) to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields of the trusted, proof-verified `TransactionInfo`, mirroring the `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` verification already performed in `ChunkExecutorInner::update_ledger` via `DoStateCheckpoint`. At minimum, route the replay-verify path through the same `DoStateCheckpoint` root-comparison logic used by the normal chunk-apply path before declaring a replayed chunk "verified."

### Proof of Concept
Code-level proof (no external harness required, since this is a logic-omission bug provable by inspection/trace):
1. `db-tool replay-verify` (or `restore --verify`) reads a signed backup, whose `TransactionInfo`s are already proof-bound to a `LedgerInfoWithSignatures` (see `StateSnapshotRestoreController::run_impl`'s use of `txn_info_with_proof.verify(...)`, `storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs:127`).
2. It then re-executes the same transactions locally and calls `ChunkExecutorInner::verify_execution`, which for each transaction calls `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`).
3. Construct (or imagine) a local execution/state-tree defect that leaves `write_set` and `events` byte-identical to the archived transaction but computes a different resulting Merkle root for `state_checkpoint_hash` (e.g., an off-by-one nibble bug in JMT batch update, or a hot-state promotion bug that changes `hot_state_checkpoint_hash` without touching the transaction's own write set/events).
4. `ensure_match_transaction_info` will return `Ok(())` because it never inspects `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`.
5. `replay-verify` reports success for the entire chunk despite the local ledger state actually diverging from the authenticated one — demonstrating that a wrong state root is accepted as "verified."

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

        &self,

        persisted_aux_info: &[PersistedAuxiliaryInfo],

        event_vecs: &[Vec<ContractEvent>],
        begin_version: Version,
        end_version: Version,
        verify_execution_mode: &VerifyExecutionMode,
    ) -> Result<Version> {
        // Execute transactions.
        let parent_state = self.commit_queue.lock().latest_state().clone();
        let state_view = self.state_view(parent_state.latest())?;
        let txns = transactions
            .iter()
            .take((end_version - begin_version) as usize)
            .cloned()
            .map(|t| t.into())
            .collect::<Vec<SignatureVerifiedTransaction>>();

            .iter()
            .take((end_version - begin_version) as usize)
            .map(|persisted_aux_info| AuxiliaryInfo::new(*persisted_aux_info, None))
            .collect::<Vec<_>>();
        let onchain_config = chunk_onchain_config(&state_view)?;
        let execution_output = DoGetExecutionOutput::by_transaction_execution::<V>(
            &V::new(),
            txns.into(),

            &parent_state,
            state_view,

        )?;
        // not `zip_eq`, deliberately
        for (version, txn_out, txn_info, write_set, events) in multizip((

            write_sets.iter(),

                Some(write_set),

                    verify_execution_mode.mark_seen_error();
                    Ok(version + 1)
                } else {
                    Err(err)
                };
            }
        }
