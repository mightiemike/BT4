### Title
`handle_poison_microblock` confiscates an honest miner's coinbase from two same-signer headers with different sequence numbers - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` derives the punished public-key hash via `check_microblock_header_signer`, whose only documented job is to confirm the two headers were "signed by the same key" — it does not require `mblock_header_1.sequence == mblock_header_2.sequence`. Combined with the codec-level deserializer for `TransactionPayload::PoisonMicroblock`, which only rejects a header pair when sequence *and* `prev_block` **both** differ, a pair of headers sharing the same `prev_block` but different sequence numbers passes both layers and is treated as valid double-signing proof.

### Finding Description
The claimed equality is: **reward paid == exactly one valid double-signature AT THE SAME SEQUENCE NUMBER**. In practice, the code only enforces **same-signer**, not **same-sequence**.

- `handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs, lines 722-856) calls `StacksChainState::check_microblock_header_signer(mblock_header_1, mblock_header_2)` to obtain `pubkh` [1](#0-0) . Nowhere in this function is `mblock_header_1.sequence` compared against `mblock_header_2.sequence`, nor is `prev_block` equality asserted; the code proceeds straight to looking up `mblock_pubk_height` and then records `mblock_header_1.sequence` as the `reported_seq` used for commission bookkeeping [2](#0-1) .
- At the codec layer, the `stacks-codec` test for `TransactionPayload::PoisonMicroblock` deserialization documents the actual accepted condition: two equal headers are rejected ("microblock headers match"), and a pair with **different sequence AND different `prev_block`** is rejected ("do not identify a fork") [3](#0-2) . This wording ("different sequence **AND** different prev_block") implies headers that share the same `prev_block` but differ in sequence are *not* rejected by this rule, i.e., they are accepted as a well-formed poison payload for deserialization purposes.
- Every place that legitimately *constructs* a `PoisonMicroblock` payload internally (e.g., `validate_parent_microblock_stream` in blocks.rs) only builds one when `prior_microblock.header.sequence == cur_microblock.header.sequence` [4](#0-3) , and `load_descendant_staging_microblock_stream_with_poison` does the same [5](#0-4) . This shows the *intended* invariant is same-sequence equivocation, but that invariant is not re-verified by `handle_poison_microblock` itself when an arbitrary user-submitted `PoisonMicroblock` transaction is processed (as exercised by tests like `process_poison_microblock_same_block`, which happen to use same-sequence headers but never assert same-sequence is *required*) [6](#0-5) .

Exploit flow: an unprivileged reporter obtains two headers signed by the same honest miner key, sharing `prev_block = P`, but with sequence 5 and sequence 9 respectively (e.g., from two locally-built but never-both-broadcast candidate microblock chains that the miner produced while reorganizing before choosing which to publish — legitimate miner behavior, not equivocation at any single position). The reporter packages these as `TransactionPayload::PoisonMicroblock(header_seq5, header_seq9)`, signs and broadcasts it. Because the codec's fork-identity check only fires when *both* sequence and `prev_block` differ, and because `handle_poison_microblock`/`check_microblock_header_signer` never independently checks sequence equality, the transaction is accepted, the miner's key is flagged as poisoned, and the reporter collects the `poison_microblock_commission`, with the honest miner's mature coinbase confiscated.

### Impact Explanation
This results in block-reward theft from an honest miner who never actually double-signed at a shared sequence position — the miner's coinbase reward is confiscated and paid out to an unrelated reporter based on data that does not prove equivocation. This matches the Critical category "block-reward theft/double-payment/loss." The loss is deterministic and reproducible against any miner for whom the attacker can obtain two same-signer, same-`prev_block`, different-sequence headers.

### Likelihood Explanation
The attacker needs no stake, no majority position, and no privileged role — only (a) the ability to submit a standard Stacks transaction (as any account holder can), and (b) possession of two headers signed by the target miner's microblock key sharing a `prev_block` but differing in sequence. Such headers are plausible byproducts of ordinary miner behavior (building/discarding alternate local microblock continuations from the same tip before broadcasting one), or could be observed via the P2P network if a miner ever leaked or partially broadcast an abandoned build. No BTC spend or sortition win is required by the attacker — they only file a report transaction referencing the microblock public key hash previously registered on-chain by the victim miner.

### Recommendation
In `check_microblock_header_signer` (or immediately in `handle_poison_microblock` before computing `pubkh`), enforce `mblock_header_1.sequence == mblock_header_2.sequence` and `mblock_header_1.prev_block == mblock_header_2.prev_block` in addition to the same-signer and header-inequality checks already performed, mirroring the invariant already enforced when the payload is legitimately constructed in `validate_parent_microblock_stream`/`load_descendant_staging_microblock_stream_with_poison`. Additionally, tighten the `stacks-codec` deserializer for `TransactionPayload::PoisonMicroblock` so that a same-`prev_block`-different-sequence pair is rejected exactly like the same-sequence-different-`prev_block` case, since neither constitutes valid double-signing proof.
