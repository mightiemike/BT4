Based on the reachable fee-charging logic in `refund_unspent_gas_and_deposits`, there's a legitimate analog to the reported bug class: a protocol fee that is not charged unconditionally but is instead siphoned out of a side-channel refund pool that can be empty, letting the fee be silently skipped under normal, attacker-reachable conditions.

### Title
Account creation fee (`account_creation_charge`) can be fully avoided when the gas price does not decrease between purchase and burn - ([File: runtime/runtime/src/lib.rs])

### Summary
The `AccountCostIncrease` feature is supposed to unconditionally levy `config.account_creation_charge` on every account-creating receipt. In practice this charge is not debited directly from the payer; instead it is carved out of `burned_gas_refund`, a "price surplus" refund that only exists when the gas price *decreased* between the moment gas was purchased and the moment it was burnt. When the surplus is zero (or smaller than the desired charge), the runtime silently charges less than intended - and can charge exactly zero - with only a `debug_assert!` (a no-op in release builds) standing between the intended invariant and reality.

### Finding Description
In `refund_unspent_gas_and_deposits` [1](#0-0) , the surplus refund is computed as:

```
price_surplus = (gas_purchase_price - gas_burn_price) * result.gas_burnt   // only if gas_burn_price < gas_purchase_price
burned_gas_refund = price_surplus   // (AccountCostIncrease only)
amount_to_charge = account_creation_charge - burned_cost(create_account exec fee at gas_burn_price)
amount_actually_charged = min(amount_to_charge, burned_gas_refund)
``` [2](#0-1) 

`gas_burn_price` is `min(gas_purchase_price, apply_state.gas_price)` per the economics spec [3](#0-2) , and `gas_purchase_price = max(current_gas_price, min_gas_purchase_price)` at tx-conversion time [4](#0-3) .

The code contains a comment and `debug_assert!` explicitly acknowledging the assumption this relies on: "as long as the purchase price is high enough, there should always be enough refund balance to cover the cost of creating an account" [5](#0-4) . That assumption only holds while the live chain gas price stays below `min_gas_purchase_price` between the block that converts the transaction and the block that executes the resulting receipt. If the live gas price is at or above `gas_purchase_price` at burn time (i.e. it did not drop), `gas_burn_price == gas_purchase_price`, so `price_surplus == 0`, so `burned_gas_refund == 0`, so `amount_actually_charged == 0` - the entire `account_creation_charge` is skipped, and the `debug_assert!` (compiled out in release) does not stop it.

The gas-price feedback controller can push the live price up to `max_gas_price = min(genesis_max_gas_price, min_gas_price * 20)` under sustained >50% block utilization [6](#0-5) , which the test suite's own comments show can exceed `min_gas_purchase_price` by design margin (the test's `GAS_PRICE` constant is deliberately pinned 10x below `min_gas_purchase_price` specifically to keep the invariant true for the test) [7](#0-6) . Nothing in the runtime otherwise clamps or guarantees `gas_purchase_price < min_gas_purchase_price` relative to the live chain price under real congestion.

The runtime's own protocol-upgrade test already demonstrates the exact code path producing a charge below `account_creation_charge` when the surplus is insufficient, and explicitly documents that the account is still created for free in that case: "the receipt crossed the upgrade boundary... there is no price surplus to take the account creation charge from... the account is created anyway and only the available surplus (nothing) is charged" [8](#0-7) . That test frames the shortfall as a one-time migration artifact, but the same code executes identically any time `gas_burn_price >= gas_purchase_price`, which is a normal (not migration-only) network state reachable by ordinary sustained load.

### Impact Explanation
`account_creation_charge` exists specifically to recover the cost/storage burden new accounts impose and to prevent cheap account-creation spam under `AccountCostIncrease`. Any account-creating transaction (explicit `CreateAccount`, or implicit creation via `Transfer` to a NEAR/ETH-implicit or universal account, or `DeterministicStateInit`) submitted while chain gas price is flat/rising bypasses this fee entirely, at zero extra cost or complexity to the submitter - this is a fee/gas-bypass with concrete, unauthorized value effect: the payer pays strictly less than the protocol-mandated cost for creating state, systematically under-collecting the anti-spam/storage-recovery charge network-wide during the (fairly common) periods of sustained chunk utilization.

### Likelihood Explanation
This requires no validator collusion, no malicious peer, and no special privileges - any ordinary account-creation transaction submitted while the network gas price is not decreasing (a routine market condition, especially during sustained congestion when the load-feedback controller raises price) triggers the bypass. The condition is a natural side effect of the gas-price feedback loop rather than an edge case; the codebase's own test comments acknowledge the underlying assumption can be violated. The only mitigation currently present (`debug_assert!`) is inert in production release builds.

### Recommendation
Charge `account_creation_charge` unconditionally as a direct debit against the payer/receipt (or against `unused_gas_balance_refund` broadly, not solely the price-surplus component), instead of capping it at `burned_gas_refund`. If it must be drawn from a refund pool, fall back to burning it from the account's own balance (analogous to a `LackBalanceForState` check) rather than silently reducing the charge to whatever surplus happens to exist, and replace the `debug_assert!` with an actual runtime invariant/error path so any shortfall is visible rather than silently absorbed.

### Proof of Concept
1. Let chain gas price rise (via ordinary >50% chunk utilization over several blocks) until `apply_state.gas_price >= min_gas_purchase_price`.
2. Submit an ordinary `CreateAccount` transaction (or a `Transfer` to a non-existent implicit/universal account) at that block height; `gas_purchase_price = max(current_gas_price, min_gas_purchase_price) = current_gas_price`.
3. If the gas price at receipt-execution time (one block later, or same shard's next block) has not dropped below `gas_purchase_price`, `gas_burn_price = min(gas_purchase_price, apply_state.gas_price) = gas_purchase_price`.
4. In `refund_unspent_gas_and_deposits`, `price_surplus = 0` ⇒ `burned_gas_refund = 0` ⇒ `amount_actually_charged = min(amount_to_charge, 0) = 0`.
5. The account is created successfully but `tokens_burnt` for the receipt excludes any `account_creation_charge`, confirmable by comparing `total_tokens_burnt` against `account_creation_charge` as the existing test `test_create_account_cost_protocol_upgrade` does for the analogous "no surplus" case [9](#0-8) .

### 4. Gas-price adjustment
The next block's gas price is a load-feedback controller (`core/primitives/src/block.rs:440` — `compute_next_gas_price_checked`):
- Formula (`block.rs:417`): `next_gas_price = gas_price * (1 + (gas_used/gas_limit − 1/2) * adjustment_rate)`. Implemented as the exact integer ratio `numerator/denominator` at `block.rs:460`. When utilization is exactly 50% the price is unchanged; above 50% it rises, below it falls.

### 6. Gas burning, rewards, and refunds during receipt execution
In `Runtime::apply_action_receipt` (`runtime/runtime/src/lib.rs`), after actions run:
1. **Gas burn price** — with `AccountCostIncrease` enabled, gas is burnt at `min(gas_purchase_price, apply_state.gas_price)`; before it, at `apply_state.gas_price` (`lib.rs:920`).
2. **Refunds** — `refund_unspent_gas_and_deposits` (`lib.rs:1166`) refunds unspent gas and, on failure, the full deposit. `gross_gas_refund` = prepaid gas + prepaid exec gas − gas actually used/burnt (`lib.rs:1186`). It then:
   - Computes the NEP-536 penalty `gas_penalty_for_gas_refund(gross)` = `min(gross, max(gross * gas_refund_penalty, min_gas_refund_penalty))` (`core/parameters/src/cost.rs:683`) at `gas_burn_price` (post-`AccountCostIncrease`) or `gas_purchase_price` (before) (`lib.rs:1201`). The unused-gas refund is issued at `gas_purchase_price` minus this penalty (`lib.rs:1210`).
   - Records `price_deficit` if the burn price rose above purchase price, else `price_surplus` (`lib.rs:1220`). With `AccountCostIncrease`, the surplus is refunded to the signer (`burned_gas_refund`, `lib.rs:1235`); before, it was retained as burnt.
   - If a new account was created (post-`AccountCostIncrease`), an extra `create_account_charge` = `min(desired = account_creation_charge − already-burned, burned_gas_refund)` is subtracted from the refund (`lib.rs:1243`).
3. **tx_burnt_amount** — burnt tokens for the receipt = `gas_burn_price * gas_burnt − price_deficit` (`lib.rs:975`), plus `refund_penalty`, `create_account_charge`, and `result.tokens_burnt`; pre-`AccountCostIncrease` also plus `price_surplus` (`lib.rs:978`). System/refund receipts burn 0 gas (`lib.rs:972`).
4. **Contract reward** — of the gas burnt *for function calls*, a `burnt_gas_reward` fraction (mainnet `3/10`) is paid to the receiver account and *subtracted* from `tx_burnt_amount` (`lib.rs:990`). Reward is priced at `gas_burn_price` post-`AccountCostIncrease`, else `gas_purchase_price` (`lib.rs:998`). If the receiver account no longer exists, the whole amount stays burnt (goes to validators via §3). The remaining `tx_burnt_amount` accumulates into `stats.balance.tx_burnt_amount` (`lib.rs:1023`) and ultimately reduces total supply as `balance_burnt`.

/// The interesting case is a receipt that crosses the boundary: its gas was purchased before
/// the upgrade at the old (10x lower) price, but it executes after the upgrade, where a created
/// account should burn `account_creation_charge` out of the gas price surplus refund. Such a
/// receipt has no surplus to take the charge from, so the runtime charges only what's available
/// (nothing) and the account is still created successfully.
///
/// The signer and the created accounts are placed on different shards so that the
/// account-creating receipt executes one block after the transaction is converted - a
/// same-shard receipt would execute in the same block as the conversion and could never cross
/// the upgrade boundary.
// TODO(spice-test): This test can be removed once the AccountCostIncrease feature is stabilized.
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
#[test]
fn test_create_account_cost_protocol_upgrade() {
    init_test_logger();

    // The test upgrades to PROTOCOL_VERSION, which must have the feature enabled.
    if !ProtocolFeature::AccountCostIncrease.enabled(PROTOCOL_VERSION) {
        return;
    }

    let signer = create_account_id("alice");
    // Boundary "mm": "alice" goes to the first shard, "subN.alice" to the second.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);
    let epoch_length = 10;

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(ProtocolFeature::AccountCostIncrease.protocol_version() - 1)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(PROTOCOL_VERSION))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .gas_prices(GAS_PRICE, GAS_PRICE)
        .add_user_account(&signer, Balance::from_near(1_000))
        .build();

    let account_creation_charge = env
        .rpc_node()
        .client()
        .runtime_adapter
        .get_runtime_config(PROTOCOL_VERSION)
        .account_creation_charge;

    // Send a CreateAccount transaction at every height until the network upgrades, then keep
    // sending for a few more blocks under the new version.
    let mut tx_hashes = Vec::new();
    let mut blocks_after_upgrade = 0;
    while blocks_after_upgrade < 5 {
        assert!(tx_hashes.len() < 10 * epoch_length as usize, "the upgrade never happened");
        let new_account = create_account_id(&format!("sub{}.alice", tx_hashes.len()));
        let tx = env.rpc_node().tx_from_actions(
            &signer,
            &new_account,
            vec![Action::CreateAccount(CreateAccountAction {})],
        );
        tx_hashes.push(env.rpc_node().submit_tx(tx));
        env.rpc_runner().run_for_number_of_blocks(1);
        if env.rpc_node().protocol_version_at_head() == PROTOCOL_VERSION {
            blocks_after_upgrade += 1;
        }
    }
    // Let the last transactions and all of their receipts finish executing.
    env.rpc_runner().run_for_number_of_blocks(5);

    let (mut before, mut crossing, mut after) = (0, 0, 0);
    for tx_hash in tx_hashes {
        let outcome = env.rpc_node().client().chain.get_final_transaction_result(&tx_hash).unwrap();
        // Every transaction must succeed: before, across, and after the upgrade.
        assert_outcome_success(&outcome, true);
        let cost = total_tokens_burnt(&outcome);

        // The transaction is converted to a receipt in one block, and the receipt may execute
        // in another. `receipts_outcome[0]` is the account-creating receipt, the rest are
        // refunds.
        let tx_with_feature = block_has_feature(&env, &outcome.transaction_outcome.block_hash);
        let receipt_with_feature = block_has_feature(&env, &outcome.receipts_outcome[0].block_hash);
        match (tx_with_feature, receipt_with_feature) {
            // Fully before the upgrade: the old, cheap account creation.
            (false, false) => {
                assert!(cost < account_creation_charge);
                before += 1;
            }
            // The receipt crossed the upgrade boundary: its gas was purchased at the old price,
            // so there is no price surplus to take the account creation charge from. The
            // account is created anyway and only the available surplus (nothing) is charged.
            (false, true) => {
                assert!(cost < account_creation_charge);
                crossing += 1;
            }
            (true, false) => panic!("receipt executed at an older version than its transaction"),
            // Fully after the upgrade: the account creation charge applies.
            (true, true) => {
                assert!(cost > account_creation_charge);
                after += 1;
            }
        }
