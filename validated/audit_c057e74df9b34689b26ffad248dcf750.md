### Title
Unprotected `initialize()` in vault contracts allows front-running DoS of DAO protocol-launch proposal - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`)

### Summary
The vault contracts (`v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-ststxbtc.clar`) expose a public `initialize()` function that is guarded only by a one-way `initialized` flag and has no caller/DAO authorization check, unlike every other administrative setter in the same contract. This mirrors exactly the `AdminStrategy.connect()` bug class in the report: an unauthenticated setup function that can be invoked by anyone, permanently locking a piece of state before the legitimate initializer runs, causing the official initialization transaction to abort.

### Finding Description
`initialize()` is defined with only a "not already initialized" guard: [1](#0-0) 

Compare this to every other state-mutating admin function in the same file, which requires `check-dao-auth`: [2](#0-1) 

`initialize()` sets `initialized` to `true` *before* calling `deposit`, and `deposit` itself only requires `initialized` to already be `true` and enforces a supply-cap check: [3](#0-2) 

Because `cap-supply` defaults to `u0` at deployment, `deposit`'s `ERR-SUPPLY-CAP-EXCEEDED` check (`current-assets + amount <= CAP-SUPPLY`) fails while the cap is still zero, atomically reverting the whole `initialize()` call (including the `var-set initialized true`) — so the attack is not exploitable immediately after deployment.

However, the DAO's protocol-init proposal sets non-zero caps on all vaults in one step, and only *later* (in a separate, non-atomic proposal transaction) calls `initialize()` on the vaults: [4](#0-3) 

This creates a real window between "caps set" and "vaults initialized" during which `cap-supply` is non-zero but `initialized` is still `false`. Any address holding at least `MINIMUM-LIQUIDITY` (u1000) of the vault's underlying asset can call `initialize()` directly during this window, successfully depositing the minimum liquidity themselves (shares are minted to `NULL-ADDRESS`, so the attacker gains nothing) and permanently flipping `initialized` to `true`.

When the DAO's later proposal transaction executes its own `initialize()` call on that same vault, it will hit `(asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)` and fail. Because the proposal script chains multiple `try!` calls inside one `begin` block executed atomically inside `dao-executor.execute-proposal`, a single failing `initialize()` call reverts the *entire* proposal transaction — including cap-setting and market-authorization calls for every other vault bundled in that same proposal. [5](#0-4) 

### Impact Explanation
This is a launch-blocking, single-transaction griefing vector: a single unprivileged actor, after the DAO's cap-setting step but before the DAO's vault-initialization step, can permanently strand the vault in a state where the official initialization proposal can never succeed as written, requiring the DAO to redeploy or hand-craft a bespoke recovery proposal. Since the same proposal transaction bundles multiple vaults' cap/authorization/initialization steps atomically, this griefing on a single vault causes the whole batch to revert, freezing the intended rollout of all bundled vaults (temporary/permanent freezing of protocol launch functionality) until the DAO manually works around it.

### Likelihood Explanation
Medium: it requires (1) the attacker to hold a small amount of the vault's underlying asset (as little as 0.00001 BTC-equivalent for sBTC's `MINIMUM-LIQUIDITY`), (2) awareness of the DAO's two-step (cap-then-initialize) rollout sequence, and (3) racing to submit the `initialize()` call in the window between the two DAO proposal transactions — all realistically achievable by any on-chain observer monitoring DAO proposal execution.

### Recommendation
Restrict `initialize()` to the DAO/executor, consistent with every other administrative function in the vault (e.g., require `check-dao-auth` or check `contract-caller`/`tx-sender` against `.dao-executor`), so it cannot be invoked by an arbitrary principal before the DAO's intended initialization step.

### Proof of Concept
1. DAO executes `v0-init.clar` (or equivalent protocol-init proposal), which sets `cap-supply`/`cap-debt` to non-zero values on `v0-vault-sbtc` but does not yet call `initialize()`.
2. Attacker, holding ≥1000 units of `sbtc-token`, directly calls `(contract-call? .v0-vault-sbtc initialize)`. Since `cap-supply > 0`, `deposit` succeeds; `initialized` is permanently set to `true`, minting minimum-liquidity shares to `NULL-ADDRESS` using the attacker's own funds.
3. DAO later executes the proposal that calls `(contract-call? .v0-vault-sbtc initialize)` as part of a batch (e.g., alongside cap-setting/authorization calls for other vaults). This call hits `ERR-ALREADY-INITIALIZED` and `try!` propagates the failure, aborting the entire proposal transaction.
4. None of the bundled vaults in that proposal get their caps/authorizations/initialization applied, and the DAO must issue a new, reworked proposal to recover — demonstrating the DoS on the protocol launch flow.
