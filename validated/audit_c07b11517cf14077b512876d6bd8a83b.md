## Analog Analysis

### Title
Unbounded recursive-descent JSON parsing of attacker-controlled `program` fields causes stack-exhaustion DoS before size/depth validation — ([File: crates/starknet_api/src/deprecated_contract_class.rs])

### Summary
The CVE describes a stack-consumption bug in `QPDFTokenizer` where two consecutive recursive-descent parsing calls on crafted input drive unbounded recursion and crash the process. The sequencer has an analogous unbounded-recursion parsing pattern: the deprecated-gateway Declare (Cairo0) path deserializes the entire contract-class `program` object as raw, arbitrarily-nested `serde_json::Value` trees, with no recursion-depth guard, before any structural validation runs.

### Finding Description
`starknet_api::deprecated_contract_class::Program` declares `attributes`, `builtins`, `compiler_version`, `data`, `debug_info`, `hints`, `identifiers`, `main_scope`, `prime`, and `reference_manager` all as raw `serde_json::Value`: [1](#0-0) 

`serde_json::Value`'s deserializer is a classic recursive-descent parser: for every nested array/object it recurses one stack frame deeper, with no built-in depth limit (unlike some JSON libraries which cap `recursion_limit`). This `Program` is embedded in `ContractClass` (Cairo0), which is embedded in the deprecated gateway's `DeclareV1Transaction`: [2](#0-1) [3](#0-2) 

This same `Program` value is later passed straight into `sn_api_to_cairo_vm_program`, which calls `serde_json::from_value` on each of `identifiers`, `builtins`, `hints`, `attributes`, `reference_manager`, i.e. these `Value` trees are built by recursive parsing at deserialization time and then walked recursively again in downstream conversions: [4](#0-3) 
Similarly, `compute_cairo_hinted_class_hash` re-serializes/re-parses and recursively sorts these JSON values (`sort_json_value`), another unbounded recursive walk over attacker-controlled structure: [5](#0-4) 

Crucially, the only guardrails found in the codebase for declared classes are **byte-size** limits (`max_contract_class_object_size`, `max_contract_bytecode_size`), not **nesting-depth** limits:
- `gateway_config.static_config.stateless_tx_validator_config.max_contract_class_object_size` = 4,089,446 bytes
- `gateway_config.static_config.stateless_tx_validator_config.max_contract_bytecode_size` = 81,920 bytes

A deeply nested JSON array/object (e.g. `[[[[[...]]]]]` repeated hundreds of thousands of times) is extremely small in byte count yet drives extremely deep recursion — well under any byte-size cap, so the size checks do not prevent the attack, and the stack overflow happens *during* the initial `serde_json` deserialization of the incoming request body, before stateless/stateful validators or bytecode-size checks even execute.

### Impact Explanation
A crafted Declare (Cairo0) transaction submitted through the deprecated gateway HTTP endpoint, with a `program.identifiers` (or `hints`/`reference_manager`/`attributes`) field containing extremely deep JSON array/object nesting, can exhaust the call stack of the gateway process during `serde_json` deserialization. This crashes (SIGSEGV/abort) the gateway/HTTP-server component handling the request — a process-level denial of service reachable from a single, unprivileged, unauthenticated transaction sender, with no fee paid and no signature validity required (the crash occurs before signature/fee checks). Repeated submission can be used to persistently disrupt transaction intake for the sequencer, matching the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
High likelihood of reachability: the deprecated gateway `add_transaction` HTTP endpoint accepts arbitrary JSON bodies from any external sender and deserializes the Declare(Cairo0) `contract_class.program` directly into `serde_json::Value` fields with no pre-validation of structural depth. Constructing a small payload (a few hundred KB or less) with hundreds of thousands of nested array brackets is trivial and requires no cryptographic material, valid signature, or account balance, since the crash happens in the deserialization step that precedes those checks.

### Recommendation
- Configure or wrap `serde_json` deserialization of all externally-supplied payloads (especially `Program`'s `Value` fields, and any `RpcTransaction`/`DeprecatedGatewayDeclareTransaction` body) with an explicit recursion/nesting-depth limit before attempting a full parse (e.g., pre-scan bracket/brace depth, or use a bounded-depth deserializer).
- Reject transactions whose JSON body exceeds a configured maximum nesting depth as part of stateless validation, applied prior to or concurrently with the existing byte-size checks.
- Consider replacing free-form `serde_json::Value` fields in `Program` with strongly-typed structures where feasible, limiting attacker-controlled recursive structure.
- Run the HTTP-server / gateway deserialization step under a size-and-depth-bounded parser, or increase/guard the thread stack and treat stack overflow as a recoverable per-request error rather than a process abort.

### Proof of Concept
1. Construct a Declare V1 (Cairo0) transaction JSON body targeting the deprecated gateway `add_transaction` endpoint.
2. Set `contract_class.program.identifiers` (or `hints`, `reference_manager`, `attributes`) to a deeply nested JSON value, e.g. `"[".repeat(500_000) + "]".repeat(500_000)` — a payload of roughly 1MB, well under `max_contract_class_object_size` (4,089,446 bytes).
3. Submit the request to the gateway's declare endpoint.
4. Observe that `serde_json`'s recursive-descent parsing of the nested array during `Program` deserialization exhausts the thread stack, crashing the handling thread/process before any stateless validator (bytecode size, calldata length, etc.) or signature check executes — a process crash triggered purely by transaction submission.

/// Recursively sorts all JSON objects by their keys.
/// This ensures deterministic serialization regardless of the `preserve_order` feature in
/// serde_json.
fn sort_json_value(value: serde_json::Value) -> serde_json::Value {
    match value {
        serde_json::Value::Object(map) => {
            let sorted: BTreeMap<String, serde_json::Value> =
                map.into_iter().map(|(k, v)| (k, sort_json_value(v))).collect();
            serde_json::Value::Object(sorted.into_iter().collect())
        }
        serde_json::Value::Array(arr) => {
            serde_json::Value::Array(arr.into_iter().map(sort_json_value).collect())
        }
        other => other,
    }
}
