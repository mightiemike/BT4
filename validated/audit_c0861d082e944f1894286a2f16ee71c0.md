### Title
ValidateMultiSign dedups on raw signature bytes instead of recovered address, allowing a single key's weight to be counted multiple times via distinct valid ECDSA signatures - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.ValidateMultiSign.execute` deduplicates submitted signatures with `ByteArray.matrixContains(executedSignList, sign)`, which performs raw `byte[]` equality on the signature blob itself rather than on the address recovered from it. Because ECDSA signing normally uses a randomized (or otherwise varying) nonce `k`, the same private key can produce many distinct, fully valid `(r,s,v)` signatures over the identical message hash — each a different byte sequence that nonetheless recovers to the same address — none of which are caught by this byte-level dedup.

### Finding Description
`ByteArray.matrixContains` is implemented as a straightforward `Arrays.equals` scan over a `List<byte[]>`: [1](#0-0) . In `ValidateMultiSign.execute`, this helper is used to detect whether a submitted signature has already been processed by comparing the raw signature bytes (`sign`), not the address recovered from it via `ECKey.recoverPubBytesFromSignature`/`recoverAddressFromSignature`. Weight for a given recovered address is then looked up in the target `Permission` and accumulated into `totalWeight`, which is compared against `permission.getThreshold()`.

The root cause is that signature identity (raw bytes) is used as the dedup key instead of key identity (recovered address). ECDSA does not bind a message hash to a single canonical signature: signing the same hash with a different nonce `k` yields a completely different, independently valid `(r,s)` pair (and the classical `s → N-s` malleability trick yields a second valid encoding from any given signature without even re-signing). `ECKey`'s `validateComponents()`-style checks only bound `r`/`s` within `[1, N-1]`; they do not enforce canonical low-`s` form nor prevent an attacker who holds the real private key from producing many distinct valid signatures over the same hash. Since each such signature is a distinct byte array, `matrixContains` never flags them as duplicates, and each one independently passes recovery, address weight lookup, and gets added to `totalWeight`.

An attacker who controls exactly one key that is insufficient alone to reach the multisig `threshold` can therefore submit `MAX_SIZE` (5) differently-encoded, individually valid signatures produced from that single key over the same hash, and have that key's weight counted up to 5 times, at the fixed energy cost of `5 * ENERGY_PER_SIGN` (1500), potentially reaching or exceeding the threshold that should require multiple distinct keys.

Note: the question frames the differing bytes as "trailing padding beyond byte 65." Signature slots are extracted as fixed 65-byte blocks, so trailing-padding-only variation of an otherwise identical `(r,s,v)` is unlikely to be the actual vector; the concretely supported mechanism is that any two independently-produced (or malleability-derived) valid `(r,s,v)` encodings from the same key differ in their 65 meaningful bytes, which is sufficient to defeat the raw-byte dedup — the exploitability conclusion is the same.

### Impact Explanation
This is an authorization-enforcement bypass (AUTHORIZATION_ENFORCED / weight double counting) for TRON's multi-signature account permission model exposed to Solidity contracts via the `ValidateMultiSign` precompile. An attacker holding a single insufficiently-weighted key can cause the precompile to report `DATA_TRUE` for a threshold that is supposed to require multiple independent authorized keys, enabling unauthorized approval of a contract-gated action guarded by multisig weight checks (e.g., funds release, permission changes gated by contract logic relying on this precompile).

### Likelihood Explanation
Preconditions are modest and fully attacker-controlled: a multi-sig account/permission configured with a threshold reachable by multiplying one key's weight (e.g., weight × up to `MAX_SIZE`=5 ≥ threshold), and the attacker possessing that one real private key. No privileged role, no other party's key, and no non-default node configuration are required — the attacker only needs to deploy or call a contract that invokes `ValidateMultiSign` with 5 crafted signature blobs, at a fixed, cheap energy cost (`5*1500`). The attack is fully repeatable and deterministic given the attacker's key.

### Recommendation
Change the dedup key in `ValidateMultiSign.execute` from the raw signature bytes to the recovered address (i.e., call `ByteArray.matrixContains(executedAddrList, recoveredAddr)` and add `recoveredAddr` to that list), so each distinct key can only contribute its weight once regardless of how many valid signature encodings exist for it. Additionally, enforce canonical low-`s` signatures in the ECDSA validation path to reduce malleability-based signature multiplicity in general.

```java
// Pseudocode PoC for actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java ValidateMultiSign
// Setup: account with Permission{ threshold = 2*W, keys = [ {addr=A, weight=W}, {addr=B, weight=W} ] }
// Attacker controls only key A (weight W < threshold alone).

ECKey keyA = attackerKey; // recovers to address A
byte[] hash = someMessageHash;

// Produce 5 independently-signed, distinct-byte, individually valid signatures
// over the SAME hash using the SAME key (different nonce k each time, or via
// standard s-negation malleability):
byte[] sig1 = keyA.sign(hash).toByteArray(); // (r1, s1, v1)
byte[] sig2 = keyA.sign(hash).toByteArray(); // (r2, s2, v2) - different nonce -> different bytes
byte[] sig3 = malleate(sig1);                // (r1, N-s1, v1^1) - same key, distinct bytes
byte[] sig4 = keyA.sign(hash).toByteArray();
byte[] sig5 = malleate(sig2);

byte[] data = encodeValidateMultiSignInput(accountAddr, permissionId, hash,
    new byte[][]{sig1, sig2, sig3, sig4, sig5});

Pair<Boolean, byte[]> result = new PrecompiledContracts.ValidateMultiSign().execute(data);

// EXPECTED (secure) behavior: result should equal DATA_FALSE because only
// key A (one distinct key) participated, and its weight alone (W) does not
// meet the threshold (2*W).
//
// ACTUAL vulnerable behavior: because ByteArray.matrixContains(executedSignList, sign)
// compares raw signature bytes, sig1..sig5 are all treated as distinct entries,
// key A's weight W is added 5 times, totalWeight = 5*W >= threshold, and the
// precompile returns DATA_TRUE.
assertArrayEquals(DATA_FALSE, result.getRight()); // fails on vulnerable code, proving the bug
```
