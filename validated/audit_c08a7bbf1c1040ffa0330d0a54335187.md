### Title
QPS-based rate limiting on `scannotebyivk` does not account for actual native-crypto decrypt cost, enabling underpriced CPU amplification - ([File: framework/src/main/java/org/tron/core/services/http/ScanNoteByIvkServlet.java])

### Summary
`ScanNoteByIvkServlet` (and its gRPC/PBFT/Solidity equivalents) is throttled only by `RateLimiterServlet.service`'s request-count-based `GlobalRateLimiter`/`DefaultBaseQqsAdapter`, while the actual work performed by `Wallet.queryNoteByIvk` scales with the number of `ReceiveDescription`s across the requested 1000-block window, each requiring a native `JLibrustzcash`/`Note.decrypt` trial-decryption call. An attacker who has previously paid to fill a 1000-block range with shielded transactions containing the maximum allowed outputs can then issue cheap, repeated HTTP requests against that dense range, causing the node to perform substantially more native-crypto work per request than the flat per-request quota accounts for.

### Finding Description
`Wallet.queryNoteByIvk` enforces only a block-count bound (`endNum - startNum <= 1000`), not a bound on the amount of cryptographic work performed: [1](#0-0) 

For every transaction in every block in the range, if it is a `ShieldedTransferContract`, the code iterates all `ReceiveDescription`s and calls the native `Note.decrypt` (JLibrustzcash-backed trial decryption) on each one: [2](#0-1) 

`ShieldedTransferContract` validation caps each individual transaction to at most 1 `SpendDescription` and 2 `ReceiveDescription`s: [3](#0-2) 

but there is no limit on how many such shielded transactions can exist across a 1000-block window — that is bounded only by block bandwidth/size limits and the fees the attacker is willing to pay to broadcast many shielded transfers over time. Once such a range is populated, every subsequent `scannotebyivk` call against it (from any caller, including the attacker) forces the server to perform native decrypt attempts proportional to the total `ReceiveDescription` count in that range.

The HTTP entrypoint enforces no cost-aware limiting — only a flat QPS-style throttle: [4](#0-3) 

`GlobalRateLimiter` is a simple token-bucket keyed by global QPS and per-IP QPS, with no knowledge of the requested block range or content: [5](#0-4) 

Because the per-endpoint adapter defaults to `DefaultBaseQqsAdapter`/`QpsStrategy` (also request-count based) unless explicitly overridden per servlet name, a request scanning 1000 empty blocks and a request scanning 1000 blocks packed with maximum-output shielded transactions consume the identical rate-limiter budget, despite the latter costing orders of magnitude more native CPU work.

### Impact Explanation
Once dense blocks exist, any unprivileged caller (including the attacker) can repeatedly call `scannotebyivk`/`scanandmarknotebyivk` (and the PBFT/Solidity mirrors) at the rate allowed by the QPS limiter, each call driving the node to perform hundreds/thousands of native Sapling decrypt operations. Sustained requests at the permitted QPS can consume disproportionate CPU relative to the "cost" the rate limiter accounts for, degrading responsiveness of the HTTP/gRPC service threads and shared node resources for other legitimate users of shielded settlement/spend endpoints (scope: node-wide availability degradation of shielded-related public APIs).

### Likelihood Explanation
- Requires `node.allowShieldedTransactionApi=true` to be enabled for the shielded scan endpoints to be reachable at all; this is a node operator configuration choice, not an attacker precondition, and is commonly enabled on nodes that support the shielded pool feature.
- Requires the attacker to have previously broadcast many shielded transactions with maximum (2) receive outputs to densely populate a contiguous 1000-block window — this is real, unprivileged, paid activity (transaction fees + bandwidth) that any user can perform over time; it need only be done once, then reused indefinitely via cheap queries.
- After that one-time cost, exploitation is simply repeated unauthenticated HTTP/gRPC calls at the permitted QPS rate — highly repeatable with no additional per-call cost or fee.

### Recommendation
Make the per-request cost accounting proportional to actual decrypt work rather than purely request count:
- Compute (or cap) the total number of `ReceiveDescription`s that will be scanned before/while processing a `scannotebyivk`/`scanandmarknotebyivk`/`scanShieldedTRC20NotesByIvk` request, and apply a cost-weighted token deduction (e.g., a leaky-bucket keyed on decrypt-op count, not just request count) in `RateLimiterServlet`/`GlobalRateLimiter`.
- Alternatively, reduce `SHIELDED_TRANSACTION_SCAN_RANGE`'s allowed span dynamically based on historical shielded-tx density, or expose/require a smaller max range for high-density segments.
- Consider bounding total `ReceiveDescription` decrypt attempts per request server-side (e.g., a hard cap independent of block count) and returning a partial-result/pagination response when exceeded, so worst-case per-request CPU is capped regardless of how densely populated attacker-chosen ranges are.

  public static boolean tryAcquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null || !r.tryAcquire()) {
        return false;
      }
    }
    return rateLimiter.tryAcquire();
  }

  public static boolean acquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null) {
        return false;
      }
      r.acquire();
    }
    rateLimiter.acquire();
    return true;
  }

  public static boolean acquirePermit(RuntimeData runtimeData) {
    return Args.getInstance().isRateLimiterApiNonBlocking()
        ? tryAcquire(runtimeData)
        : acquire(runtimeData);
  }
