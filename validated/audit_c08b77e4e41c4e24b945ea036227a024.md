### Title
Caller deposit permanently locked in NEAR Wallet Contract when address-check or NEP-141 storage lookup callback returns an error before reaching the refund logic - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (`WalletContract`) is a `#[payable]` NEAR contract that any external, unprivileged account can call via `rlp_execute` while attaching a NEAR deposit (`CallerDeposit`). That deposit is only ever refunded inside `rlp_execute_callback`'s `PromiseResult::Failed` branch. Two intermediate callbacks that also receive and are supposed to eventually forward `caller_deposit` — `address_check_callback` and `nep_141_storage_balance_callback` — contain early-return error paths that produce an `ExecuteResponse` directly, without spawning the refund promise or forwarding `caller_deposit` onward to `rlp_execute_callback`. In those paths the caller's attached deposit remains as part of the wallet contract's account balance permanently, with no method in the contract to withdraw or reclaim it.

### Finding Description
`rlp_execute` is a public `#[payable]` entry point reachable by any unprivileged transaction signer/relayer [1](#0-0) . When the predecessor differs from the wallet's own account id, `CallerDeposit::new` records the attached deposit to be tracked for a refund if the downstream cross-contract call fails [2](#0-1) .

For an `EOABaseTokenTransfer` with `address_check: Some(address)` (a transfer to another eth-implicit account), execution is routed through `address_check_callback`, passing `caller_deposit` along [3](#0-2) . Inside `address_check_callback`:
- If the registrar lookup promise fails, the function returns an error `ExecuteResponse` immediately, never using `caller_deposit` to issue a refund [4](#0-3) .
- If the registrar returns a matching account id but the caller is not itself the current account (the "faulty relayer" detection branch), the function again returns an error `ExecuteResponse` directly without refunding `caller_deposit` [5](#0-4) .

Similarly, in `nep_141_storage_balance_callback` (used for ERC-20-emulated transfers requiring a NEP-141 `storage_balance_of` check), if that lookup promise fails, the function returns an error response immediately, again bypassing any refund of `caller_deposit` [6](#0-5) .

The only place `caller_deposit` is actually redeemed for a refund is the final `rlp_execute_callback`, reached solely through the success paths of the two callbacks above [7](#0-6) . Since the error branches short-circuit before ever chaining into `rlp_execute_callback`, the attached deposit is never returned to the caller and remains part of the wallet contract's account balance. The `WalletContract` struct itself exposes no withdrawal method for such stranded balances beyond the actions parsed from a valid RLP-encoded Ethereum transaction, so this balance is effectively permanently locked from the caller's perspective — directly analogous to the reported `InfiltrationPeriphery` issue of a payable contract accepting funds with no corresponding withdraw path.

### Impact Explanation
Any external account (e.g., a relayer paying storage/registration costs on behalf of a user, as exercised in `test_caller_refunds`) that attaches a NEAR deposit to an `rlp_execute` call which happens to route through `address_check_callback` or `nep_141_storage_balance_callback` can permanently lose that deposit if the downstream cross-contract call (registrar lookup or NEP-141 `storage_balance_of`) fails, or if the relayer/target mismatch branch is hit. This is a genuine, unauthorized-permanent loss of funds for an unprivileged caller — not a user's deliberate misuse — since the deposit is silently absorbed into the target wallet contract's balance instead of triggering the standard refund pathway that exists for the exact same purpose elsewhere in the same contract.

### Likelihood Explanation
This is reachable by any account that calls `rlp_execute` (or has a relayer do so on its behalf) targeting an eth-implicit account (triggering the address-check flow) or performing an emulated ERC-20 transfer to an unregistered NEP-141 receiver (triggering the storage-balance check flow), while attaching a nonzero deposit as an external (non-self) caller. Registrar or NEP-141 lookup failures are plausible in practice (e.g., the registrar/token contract running out of allotted gas, being paused, or otherwise erroring), and the "faulty relayer" branch is a normal detection path reachable by legitimate relayer misconfiguration, not just malicious behavior. No special/privileged access is required to trigger the bug.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, ensure every early-return error branch also issues the same deposit-refund promise used in `rlp_execute_callback` (i.e., spawn `env::promise_batch_create(&account_id)` + `env::promise_batch_action_transfer(...)` for the tracked `CallerDeposit` before returning the error `ExecuteResponse`), so that a failed intermediate step always returns the caller's deposit rather than silently discarding it.

### Proof of Concept
1. An external account `caller` (distinct from the wallet's account id) calls `wallet_contract.rlp_execute(target, tx_bytes_b64)` with an attached deposit, where the decoded action is an `EOABaseTokenTransfer` to another eth-implicit `target` requiring `address_check` [8](#0-7) .
2. `CallerDeposit::new` captures the deposit since `predecessor_account_id != current_account_id` [2](#0-1) .
3. The registrar lookup promise resolves to `PromiseResult::Failed` (e.g., registrar contract panics or runs out of gas), causing `address_check_callback` to hit its early-return branch and return an error `ExecuteResponse` without ever using `caller_deposit` [4](#0-3) .
4. The caller's deposit is now permanently part of the wallet contract's balance; there is no exposed method to reclaim it, matching the reported bug class of funds becoming irrecoverably locked in a payable contract lacking a withdrawal mechanism.
