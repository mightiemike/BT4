### Title
`LiquidityCap` field on `TokenConfig` is never enforced during PRC20 minting, allowing per-token supply to grow unbounded across chains - ([File: x/uexecutor/keeper/handler.go])

### Summary
The external report describes a check (`Staking` balance) that fails to account for the aggregate liquidity consumed by *other* callers of the same shared resource. The Push Chain analog is the `TokenConfig.LiquidityCap` field [1](#0-0) , which is documented as "max supply cap for this token" and validated as non-empty at config-creation time [2](#0-1) , but is never read or compared against anything in the actual mint path. Multiple `TokenConfig` entries (one per source chain) can point to the same PRC20 contract address via `NativeRepresentation.ContractAddress` [3](#0-2) , exactly mirroring the "shared pool, multiple independent callers" structure of the original bug — except here there is no accounting for *any* caller at all, not even a single one.

### Finding Description
The inbound deposit flow calls `depositPRC20`, which loads the `TokenConfig` for `(sourceChain, assetAddr)`, resolves the target PRC20 contract from `tokenConfig.NativeRepresentation.ContractAddress`, and mints/deposits the full inbound `amount` with no reference to `tokenConfig.LiquidityCap` whatsoever: [4](#0-3) .

The only place `LiquidityCap` is referenced in the Go codebase is `ValidateBasic`, which merely checks the string is non-empty when an admin registers/updates a token — it never parses the value into a big.Int or uses it to bound any accounting: [5](#0-4) . There is no keeper-side tracking of cumulative minted supply per PRC20, and the mint call itself (`CallPRC20Deposit` → `depositPRC20Token` on the `UNIVERSAL_CORE` handler contract) is issued unconditionally for whatever amount an honest-validator-approved inbound reports: [6](#0-5) .

Because a single PRC20 contract address can legitimately be the `NativeRepresentation` target for several distinct `(chain, address)` `TokenConfig` entries (e.g. USDC bridged in from Ethereum, Arbitrum, Base, and Solana all mapping to the same PRC20, as seen in the config fixtures) [7](#0-6) [8](#0-7) , the situation is structurally identical to the "multiple game contracts share one Staking pool" scenario: several independent inbound streams mint into one shared PRC20 balance, and nothing sums or caps the total across them (nor even within a single one).

### Impact Explanation
Because there is no supply-cap enforcement at all, any ordinary unprivileged user submitting a legitimate inbound deposit (which honest validators will vote to approve as long as it matches the real source-chain event) can cause unbounded minting of the corresponding PRC20 token on Push Chain, independent of any configured cap. This directly corrupts PRC20 accounting invariants (the `LiquidityCap` is supposed to bound cross-chain-backed supply) and can be used to mint PRC20 balances disproportionate to what is actually locked/bridged on the source chain, undermining the 1:1 backing assumption of the wrapped asset and enabling economic drain once the token is used in swaps (`depositPRC20WithAutoSwap`) or transferred elsewhere.

### Likelihood Explanation
High. This requires no privileged access — any user can trigger it via a normal inbound deposit through the standard, honest-validator-approved inbound-voting path. The `LiquidityCap` field exists in config and documentation, signaling an intended protection that silently does not function, making this straightforward to hit even unintentionally.

### Recommendation
Track cumulative minted supply per PRC20 (or per canonical token) in keeper state, and before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` in `depositPRC20` (`x/uexecutor/keeper/handler.go`), parse `tokenConfig.LiquidityCap` and verify `currentMintedSupply + amount <= LiquidityCap`, aggregating across all `TokenConfig` entries that share the same PRC20 `NativeRepresentation.ContractAddress`. Reject or queue-for-revert any inbound that would exceed the cap, consistent with how other inbound failures already trigger `buildRevertOutbound`.

### Proof of Concept
Not executable from static review alone; the code path evidence is:
1. Register two `TokenConfig`s on different source chains (e.g. `eip155:1` and `eip155:97`) with the same `NativeRepresentation.ContractAddress` PRC20 and a `LiquidityCap` of `"1000000000000000000000000"`, as done in the test fixtures [9](#0-8) .
2. Submit honest, validator-approved inbounds from both chains, each with `Amount` far exceeding the configured `LiquidityCap`.
3. Observe `depositPRC20` mints the full amount for both inbounds with no rejection, since `LiquidityCap` is never read: [4](#0-3) .
4. Total minted supply for that PRC20 across both chains exceeds `LiquidityCap` with no error surfaced anywhere in the flow.

// ValidateBasic performs sanity checks on the TokenConfig
func (p TokenConfig) ValidateBasic() error {
	if strings.TrimSpace(p.Chain) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "chain cannot be empty")
	}

	if strings.TrimSpace(p.Address) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token contract address cannot be empty")
	}

	// Enforce a parseable address for the chain's namespace (e.g. 20-byte hex
	// for eip155, base58 for solana) so every registration lands on the
	// canonical storage key.
	if _, err := utils.CanonicalizeAddressByNamespace(p.Chain, p.Address); err != nil {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token address for chain %s: %s", p.Chain, err)
	}

	if strings.TrimSpace(p.Name) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token name cannot be empty")
	}

	if strings.TrimSpace(p.Symbol) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token symbol cannot be empty")
	}

	if p.Decimals == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "decimals must be greater than zero")
	}

	// Validate token_type is within known enum range
	if _, ok := TokenType_name[int32(p.TokenType)]; !ok {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token_type: %v", p.TokenType)
	}

	if strings.TrimSpace(p.LiquidityCap) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "liquidity_cap cannot be empty")
	}

	if p.NativeRepresentation == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "native_representation is required")
	}
	if err := p.NativeRepresentation.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid native representation")
	}

	return nil
}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
