### Title
Divergent signer-weight consensus thresholds between `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` and `NakamotoBlockHeader::compute_voting_weight_threshold` - (File: `libsigner/src/v0/signer_state.rs`, `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
Stacks-core, like IdleCDO, computes the same conceptual value — "has the 70% signer-weight approval threshold been reached" — with two independently-implemented formulas that are not guaranteed to agree for every `total_weight`. `NakamotoBlockHeader::compute_voting_weight_threshold` rounds the threshold *up* (ceiling division), while `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` compare directly against a *floored* fraction of `total_weight` using plain integer division. This is the same bug class as the reported issue: two "same meaning" computations that can diverge for the same inputs, breaking an equality that downstream logic assumes always holds.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` computes the minimum weight required to approve a Nakamoto block by taking `total_weight * 7 / 10` and rounding up whenever there's a remainder: [1](#0-0) 
This function is the authority used both when a node validates block signatures in `verify_signer_signatures` and when a signer decides whether it has collected enough pre-commits/signatures to broadcast/accept a block in `stacks-signer/src/v0/signer.rs` (`handle_block_pre_commit`, `store_and_process_block_signature`), which both call `NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)` for their `min_weight`: [2](#0-1) [3](#0-2) 

Separately, `libsigner`'s `GlobalStateEvaluator` computes an equivalent "have we reached agreement/disagreement" verdict using a *different* formula that does not apply a ceiling: [4](#0-3) 
`reached_agreement` checks `vote_weight >= total_weight * THRESHOLD / 10` — plain floored integer division, no ceiling adjustment — whereas `compute_voting_weight_threshold` computes `ceil(total_weight * THRESHOLD / 10)`.

For any `total_weight` where `total_weight * 7` is not evenly divisible by `10`, these two formulas produce different minimum-weight requirements. Example: `total_weight = 11`. `compute_voting_weight_threshold(11)` = `ceil(77/10)` = `8`. `reached_agreement` with `vote_weight = 7` evaluates `7 >= 77/10` = `7 >= 7` = `true` — agreement is declared reached at weight `7`, one full unit short of the `8` that `compute_voting_weight_threshold` (and hence `verify_signer_signatures`, `handle_block_pre_commit`, `store_and_process_block_signature`) would require. The `compute_voting_weight_threshold` rounding behavior is directly confirmed by the existing unit test asserting `compute_voting_weight_threshold(511) == 358` (ceiling of `511*7/10=357.7`): [5](#0-4) 

`GlobalStateEvaluator` is the global-state-machine consensus tracker used by `StackerDBListener`/miner coordination logic to decide whether a majority of signers agree on state (e.g., mining/tenure state), and its `reached_agreement`/`reached_disagreement` results feed into miner/coordinator decisions: [6](#0-5) 

### Impact Explanation
Because the two threshold formulas can disagree by exactly the boundary weight unit (e.g., weight `7` vs required `8` in the example above), a set of signers whose combined weight lands in the "gap" region between the floored and ceiled threshold can be treated as having reached global-state agreement by the `GlobalStateEvaluator` path while the same weight would be rejected as insufficient by `compute_voting_weight_threshold`-gated logic (block acceptance/pre-commit broadcasting, and `verify_signer_signatures` block validation). This is a minority-triggerable divergence: a subset of signers below the "true" 70% ceiling threshold but at/above the floored threshold can cause the global-state evaluator to declare consensus reached (driving miner/coordinator behavior) even though a node validating an actual block would reject it for insufficient signing weight under `verify_signer_signatures`. This matches the High-severity category of "a minority-triggerable sortition/signer-weight divergence causing temporary tip disagreement" between differently-implemented equivalent computations.

### Likelihood Explanation
The divergence is deterministic and depends only on `total_weight` not being a multiple of `10/gcd(7,10)`; such values are common (signer weights are typically not multiples of 10 evenly divisible against the 70% numerator). No majority collusion or privileged access is needed — this triggers purely from the total signer-weight distribution of a given reward cycle for values that fall in the identified boundary range, so it is a naturally-occurring rather than contrived condition.

### Recommendation
Replace `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs` with calls to the single canonical threshold function `NakamotoBlockHeader::compute_voting_weight_threshold` (or extract/share that ceiling-based computation into a common utility used by both `libsigner` and `stackslib`), so that every place in the codebase that needs to know whether a given weight meets/exceeds the 70% approval threshold uses one authoritative, consistently-rounded implementation, per the "single method used everywhere" recommendation from the referenced report.

### Proof of Concept
1. Consider a reward cycle where the sum of all registered signer weights is `total_weight = 11`.
2. `NakamotoBlockHeader::compute_voting_weight_threshold(11)` returns `ceil(11*7/10) = 8` — this is the threshold enforced during actual block validation (`verify_signer_signatures`) and used by signer nodes to gate pre-commit/broadcast decisions (`handle_block_pre_commit`, `store_and_process_block_signature`).
3. `GlobalStateEvaluator::reached_agreement(vote_weight = 7)` evaluates `7 >= (11 * 7) / 10 = 7` → `true`: the evaluator/tracking logic used by `StackerDBListener` and miner-coordinator code declares that state-machine consensus has been reached with only weight `7`.
4. A node/miner relying on `GlobalStateEvaluator`'s verdict proceeds as if the signer set had reached the 70% threshold, while a node validating the actual block signature set with `verify_signer_signatures`/`compute_voting_weight_threshold` at the same weight (`7 < 8`) rejects it as insufficiently signed — producing disagreement between the two subsystems about whether consensus/approval was reached for the same weight value.

```rust
    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
```

```rust
    /// Check if the supplied vote weight crosses the global agreement threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_agreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

    /// Check if the supplied vote weight crosses the blocking minority threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }
```
