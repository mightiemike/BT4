Based on this evidence, I found a valid, concrete analog.

### Title
`DeleteAccount` beneficiary is only syntax-validated, not existence-validated, causing permanent burning of the deleted account's balance when the beneficiary does not exist - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
The 1inch report flags a constructor that accepts an unchecked token address, so funds routed to a bad/zero address are permanently lost. The reachable nearcore analog is the `DeleteAccountAction.beneficiary_id` field: it is validated only for account-id *syntax*, never for whether the account actually exists. Any unprivileged signer can submit a `DeleteAccount` action with a syntactically valid but non-existent (or otherwise unreachable) `beneficiary_id`, causing their own account's entire remaining NEAR balance to be silently burned instead of delivered.

### Finding Description
`validate_delete_action` only checks the syntactic validity of the account id, not its existence: [1](#0-0) 

When the delete executes, `action_delete_account` unconditionally creates a balance-refund receipt addressed to `beneficiary_id`, with no existence check: [2](#0-1) 

That refund receipt is built via `Receipt::new_balance_refund`, which sets `predecessor_id = "system"`, marking it as a refund receipt: [3](#0-2) 

Refund receipts are explicitly forbidden from implicitly creating an account, even for implicit/eth-implicit/universal ids (only allowed when the transfer is not a refund): [4](#0-3) 

If the `beneficiary_id` account does not exist when the refund is delivered, the receipt fails with `AccountDoesNotExist`, and the runtime's refund-handling path burns the deposit outright because it is a system/refund receipt: [5](#0-4) 

This exact failure mode — a refund to a nonexistent target burning the deposit — is directly demonstrated for the analogous universal-account refund case in the test suite: [6](#0-5) 

The documentation confirms this is the intended (if hazardous) design: `DeleteAccountAction` "Validation Error" only covers `InvalidAccountId`, and there is no existence check documented or implemented: [7](#0-6) 

### Impact Explanation
Just like the 1inch bug (funds sent to an unchecked/zero address are irrecoverably lost), a NEAR account owner (or a contract issuing `promise_batch_action_delete_account` on a user's behalf, or a relayer executing a meta-transaction `DeleteAccount` action) can cause the deleting account's entire remaining balance to be burned permanently if `beneficiary_id` is any syntactically-valid-but-nonexistent account id (e.g., a typo, a not-yet-created account, or a subtly wrong id). This is a real "permanently frozen/lost funds" impact reachable from a single unprivileged transaction or meta-transaction, matching the report's core concern (loss of funds due to missing address/existence validation).

### Likelihood Explanation
This requires no special privileges — any signer holding a full-access key, or any relayer executing a `DelegateAction` on the user's behalf (as shown by `meta_tx_delete_account`), or any contract batching `promise_batch_action_delete_account` with an attacker/wrong-controlled beneficiary, can trigger it: [8](#0-7)  Because there is no runtime existence check nor warning, a simple typo or race (beneficiary account not yet created, or deleted between construction and execution) silently burns funds instead of erroring at submission time, making accidental as well as adversarial (e.g. malicious dApp/relayer front-end) triggering plausible.

### Recommendation
Add an existence check for `beneficiary_id` at action-application time (or at minimum surface a strong warning/simulation check), and/or make the refund path for `DeleteAccount` behave the same as an ordinary transfer with implicit-account-creation semantics rather than the stricter no-create refund path, so a well-formed but not-yet-existing beneficiary does not result in silent token burning. At minimum, treat delete-triggered refunds to nonexistent accounts as a hard failure of the `DeleteAccount` action (rolling back the deletion) rather than allowing the deletion to succeed while burning the payout.

### Proof of Concept
1. Create account `victim.near` with balance `B`.
2. From `victim.near` (or via a relayer using `DelegateAction`), submit a `DeleteAccount` action with `beneficiary_id = "doesnotexist.near"` (syntactically valid, never created).
3. `validate_delete_action` passes (syntax only) — see `runtime/runtime/src/action_validation.rs:447-451`.
4. `action_delete_account` deletes `victim.near` and enqueues `Receipt::new_balance_refund("doesnotexist.near", B)` — see `runtime/runtime/src/actions.rs:380-386`.
5. When that refund receipt executes, `check_account_existence`/`implicit_creation_allowed` rejects account creation because it is a refund (`is_refund = true`) — `runtime/runtime/src/actions.rs:928-947`.
6. The refund fails with `AccountDoesNotExist`, and because `predecessor_id == "system"`, the deposit `B` is added to `other_burnt_amount` and permanently destroyed — `runtime/runtime/src/lib.rs:1047-1054`, mirrored by the existing test `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6880-6926`).
7. `victim.near`'s full balance `B` is unrecoverable — never delivered to a beneficiary and never returned to the original owner.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

fn meta_tx_delete_account() {
