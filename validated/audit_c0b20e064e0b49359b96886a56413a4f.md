## Verdict: Valid finding (in-scope, non-network-level DoS)

### Title
Unbounded growth of permanently stuck CONFIRMED events starves the fixed-size processing queue - (File: `universalClient/chains/common/event_processor.go`, `universalClient/chains/common/chain_store.go`)

### Summary
`EventProcessor` has no mechanism to move a `CONFIRMED` event to any terminal failure state when voting repeatedly fails, and `GetConfirmedEvents` always returns the oldest 1000 `CONFIRMED` rows. An unprivileged attacker who can get arbitrarily many source-chain deposits recorded as `CONFIRMED` events that permanently fail `VoteInbound`/`VoteOutbound` can grow the stuck-event backlog past 1000 and permanently starve processing of legitimate, later-arriving events on every affected node.

### Finding Description
The event status model for external chains only defines `PENDING`, `CONFIRMED`, and the terminal states `REORGED`/`COMPLETED`: [1](#0-0) 

There is no `FAILED`/`EXPIRED` terminal status for external-chain events, and no code anywhere in `event_processor.go` transitions a `CONFIRMED` event out of `CONFIRMED` except on a *successful* vote: [2](#0-1) [3](#0-2) 

When `VoteInbound`/`VoteOutbound` (or parsing) fails, the function just logs and returns, leaving the event in `CONFIRMED` status to be retried indefinitely on the next 5-second tick: [4](#0-3) 

`GetConfirmedEvents` fetches a fixed-size window ordered by `created_at ASC`: [5](#0-4) 

`DeleteTerminalEvents` only prunes `COMPLETED`, `REORGED`, `REVERTED` — a permanently-failing `CONFIRMED` event is never eligible for cleanup: [6](#0-5) 

Combining these facts: if an attacker (via ordinary, permissionless deposits/log-emitting transactions on a watched source chain) can cause more than 1000 events to reach `CONFIRMED` status while permanently failing to vote, the oldest-first `LIMIT 1000` query will be entirely consumed by attacker-created stuck events on every tick, forever. Any legitimate event created afterward sorts after the stuck backlog and is never included in the query window, so it is never processed — regardless of how long the node runs.

### Impact Explanation
This is a liveness/DoS bug in the Universal Validator's inbound/outbound processing pipeline, not a network-level (bandwidth/connection) attack — it is an application-level unbounded-queue starvation bug reachable purely through ordinary user-facing deposit/withdrawal flows, which qualifies under the "denial of service ... not network-level ... reachable without privileged control" allowed-impact category. Because every honest UV independently runs the same `EventProcessor` logic against the same source-chain events, the effect is not confined to a single node: all UVs watching the affected chain would experience the same starvation, meaning legitimate deposits/withdrawals could be indefinitely delayed from ever reaching a vote, which can materially impair users' ability to have their inbound/outbound transactions finalized.

### Likelihood Explanation
The precondition is that the attacker can cheaply and repeatedly produce source-chain events that (a) pass the chain watcher/confirmer's promotion to `CONFIRMED` (block-depth-based, not data-integrity-based) and (b) permanently fail downstream vote/message construction or on-chain message validation (the "malformed-field techniques" referenced by the question). I could not fully verify the exact cost/mechanics of producing such permanently-unvotable events from this file alone (that depends on `signer.VoteInbound`/`VoteOutbound` and the `x/uexecutor` message validation, which are outside the file reviewed here), so the practical cost-per-stuck-event and the 1000-event threshold's real-world attainability should be confirmed by re-checking those referenced malformed-field techniques. Assuming such techniques exist (as implied by the question), the vulnerability itself — the missing terminal-failure transition plus fixed-size FIFO query — is confirmed present in code.

### Recommendation
- Introduce a bounded retry/backoff counter (and a terminal `FAILED`/`EXPIRED`-equivalent status, e.g. reusing `REVERTED`) for `CONFIRMED` events that repeatedly fail to vote, so they are moved out of the active processing set after N attempts or after `ExpiryBlockHeight` is passed.
- Change `GetConfirmedEvents` to skip/deprioritize events that have exceeded a failure threshold, or exclude them from the LIMIT window entirely once marked terminal, so legitimate newer events are not starved behind a permanently-stuck backlog.
- Extend `DeleteTerminalEvents` (or an equivalent sweep) to reclaim/quarantine long-stuck `CONFIRMED` events regardless of the specific failure mode.

### Proof of Concept
1. An attacker submits (or triggers) > 1000 distinct source-chain transactions/logs whose fields are malformed in a way that passes the chain confirmer's promotion to `CONFIRMED` but causes `VoteInbound`/`VoteOutbound` (or the pre-vote parsing/message-construction step) to fail deterministically every time.
2. Each tick, `processConfirmedEvents` calls `GetConfirmedEvents(1000)` [7](#0-6) , which — ordered `created_at ASC` — returns only the oldest 1000 rows, i.e., entirely attacker-created stuck events once their count exceeds 1000.
3. Each attempted `processInboundEvent`/`processOutboundEvent` call fails and simply `continue`s without altering status [8](#0-7) , so the same 1000 stuck rows are returned on every subsequent tick.
4. A legitimate user's deposit event, created after the attacker's flood, is confirmed normally but never appears in any `GetConfirmedEvents(1000)` result because it always sorts after the un-removable attacker backlog — it is never voted on, for as long as the attacker maintains > 1000 stuck `CONFIRMED` events.

// processConfirmedEvents processes confirmed events (both inbound and outbound)
func (ep *EventProcessor) processConfirmedEvents(ctx context.Context) error {
	events, err := ep.chainStore.GetConfirmedEvents(1000)
	if err != nil {
		return fmt.Errorf("failed to get confirmed events: %w", err)
	}

	for _, event := range events {
		if event.Type == store.EventTypeInbound {
			if !ep.inboundEnabled {
				ep.logger.Warn().Str("event_id", event.EventID).Msg("inbound disabled, skipping inbound event processing")
				continue
			}
			if err := ep.processInboundEvent(ctx, &event); err != nil {
				ep.logger.Error().
					Err(err).
					Str("event_id", event.EventID).
					Msg("failed to vote on inbound event")
				continue
			}
		} else if event.Type == store.EventTypeOutbound {
			if !ep.outboundEnabled {
				ep.logger.Warn().Str("event_id", event.EventID).Msg("outbound disabled, skipping outbound event processing")
				continue
			}
			if err := ep.processOutboundEvent(ctx, &event); err != nil {
				ep.logger.Error().
					Err(err).
					Str("event_id", event.EventID).
					Msg("failed to vote on outbound event")
				continue
			}
		}
	}

	return nil
}

// GetConfirmedEvents fetches confirmed events ordered by creation time
func (cs *ChainStore) GetConfirmedEvents(limit int) ([]store.Event, error) {
	if cs.database == nil {
		return nil, fmt.Errorf("database is nil")
	}

	var events []store.Event
	if err := cs.database.Client().
		Where("status = ?", store.StatusConfirmed).
		Order("created_at ASC").
		Limit(limit).
		Find(&events).Error; err != nil {
		return nil, fmt.Errorf("failed to query confirmed events: %w", err)
	}

	return events, nil
}

// DeleteTerminalEvents deletes events in terminal states (COMPLETED, REVERTED, EXPIRED)
// that were updated before the given time
func (cs *ChainStore) DeleteTerminalEvents(updatedBefore any) (int64, error) {
	if cs.database == nil {
		return 0, fmt.Errorf("database is nil")
	}

	// Unscoped() = hard delete (free disk). Without it, GORM does a soft
	// delete (just sets deleted_at), which defeats the cleaner's purpose.
	res := cs.database.Client().Unscoped().
		Where("status IN ? AND updated_at < ?",
			[]string{store.StatusCompleted, store.StatusReorged, store.StatusReverted}, updatedBefore).
		Delete(&store.Event{})

	if res.Error != nil {
		return 0, fmt.Errorf("failed to delete terminal events: %w", res.Error)
	}

	return res.RowsAffected, nil
}
