### Title
`FORBID_TRANSFER_TO_CONTRACT` safety switch is bypassable via internal TVM value-transfers — ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The committee-controlled `FORBID_TRANSFER_TO_CONTRACT` proposal is java-tron's closest analog to a global "pause" switch for TRX/TRC10 flowing into smart contracts. It is enforced in the top-level `TransferActuator` and `TransferAssetActuator`, but it is never checked on the internal-call value-transfer path executed inside the TVM (`Program.callToAddress`, `Program.createContractImpl`, and `VMUtils.validateForSmartContract`). Any unprivileged user can therefore keep moving TRX/TRC10 into contract addresses through a `TriggerSmartContract` call (or contract-to-contract `CALL`/`CREATE`) even after governance has switched the flag on to halt exactly that activity — the same missing-pause-enforcement bug class as the LensHub `_beforeTokenTransfer` finding.

### Finding Description
`DynamicPropertiesStore.getForbidTransferToContract()` is the on/off switch governance uses to stop transfers into contract accounts: [1](#0-0) 

It is checked in the two system actuators that move value between accounts as top-level contracts: [2](#0-1) [3](#0-2) 

However, when a value transfer happens *inside* TVM execution — e.g. a user calling `TriggerSmartContract` with `call_value`/`call_token_value`, or a contract doing an internal `CALL`/`CREATE` with an endowment — the value movement goes through `Program.callToAddress()` and `Program.createContractImpl()`, both of which validate only balance sufficiency via `VMUtils.validateForSmartContract`, with no reference to `getForbidTransferToContract()`: [4](#0-3) [5](#0-4) 

This is the identical vulnerability class described in the LensHub report: an emergency/governance-controlled halt mechanism is enforced on one public entry point (the "external functions"/`TransferActuator`) but not on another functionally equivalent entry point (`_beforeTokenTransfer`/the TVM internal transfer path), letting the guarded action continue unabated through the unguarded path.

### Impact Explanation
`FORBID_TRANSFER_TO_CONTRACT` exists specifically to let the committee stop TRX/TRC10 from accumulating in contract accounts (e.g. during an incident affecting a vulnerable contract, similar to the cited real-world example of halting token transfers). Because the TVM-internal transfer path ignores this flag, any account can still fund a contract with TRX or TRC10 by simply calling it (`TriggerSmartContract` with value, or contract-to-contract calls), completely defeating the governance intent. This is a concrete divergence between the intended halt state and the actual reachable behavior of the chain — the state/accounting invariant "no value enters contracts once forbidden" is violated by an ordinary unprivileged transaction.

### Likelihood Explanation
High: triggering the bypass requires nothing more than an ordinary `TriggerSmartContract` transaction carrying `call_value`/`call_token_value` to any contract address, which is a completely unprivileged, everyday operation. No special permissions, timing, or race conditions are needed.

### Recommendation
Enforce `dynamicStore.getForbidTransferToContract() == 1` inside the TVM internal-transfer path as well — specifically before performing the endowment transfer in `Program.callToAddress()` (and `createContractImpl()`/`callToPrecompiledAddress()` where endowments are also moved), mirroring the check already present in `TransferActuator`/`TransferAssetActuator`. Alternatively, centralize the check inside `VMUtils.validateForSmartContract` so all internal transfer call sites inherit it uniformly.

### Proof of Concept
1. Committee passes `FORBID_TRANSFER_TO_CONTRACT = 1` via a proposal (processed in `ProposalService`, persisted via `DynamicPropertiesStore.saveForbidTransferToContract`).
2. Confirm that a direct `TransferContract`/`TransferAssetContract` to a contract address is now rejected with `"Cannot transfer TRX/asset to a smartContract."` (as asserted by `TransferAssetActuatorTest.transferToContractAddress`).
3. Instead, submit a `TriggerSmartContract` transaction with a non-zero `call_value` (or `call_token_value`) targeting the same contract address.
4. Observe that `Program.callToAddress()` only calls `VMUtils.validateForSmartContract`, which checks balances only — the transfer succeeds and the contract's TRX/TRC10 balance increases, despite the governance-level halt being active.

  public static boolean validateForSmartContract(Repository deposit, byte[] ownerAddress,
      byte[] toAddress, long amount) throws ContractValidateException {
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid ownerAddress!");
    }
    if (!DecodeUtil.addressValid(toAddress)) {
      throw new ContractValidateException("Invalid toAddress!");
    }

    if (Arrays.equals(toAddress, ownerAddress)) {
      throw new ContractValidateException("Cannot transfer TRX to yourself.");
    }

    AccountCapsule ownerAccount = deposit.getAccount(ownerAddress);
    if (ownerAccount == null) {
      throw new ContractValidateException("Validate InternalTransfer error, no OwnerAccount.");
    }

    AccountCapsule toAccount = deposit.getAccount(toAddress);
    if (toAccount == null) {
      throw new ContractValidateException(
          "Validate InternalTransfer error, no ToAccount. And not allowed to create an account in a smartContract.");
    }

    long balance = ownerAccount.getBalance();

    if (amount < 0) {
      throw new ContractValidateException("Amount must be greater than or equals 0.");
    }

    try {
      if (balance < amount) {
        throw new ContractValidateException(
            "Validate InternalTransfer error, balance is not sufficient.");
      }

      addExact(toAccount.getBalance(), amount, VMConfig.disableJavaLangMath());
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }

    return true;
  }
