### Title
Unbounded per-address prefix scan in `DelegatedResourceAccountIndexStore` allows Sybil griefing that makes a victim's delegation-index query unboundedly expensive - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceActuator`/`FreezeBalanceActuator` let *any* unprivileged account delegate as little as 1 TRX of frozen resource to *any other* address without that receiver's consent, and every such delegation writes a new, individually-keyed entry into `DelegatedResourceAccountIndexStore` under both a `from`-prefixed and `to`-prefixed key. There is no cap on how many distinct delegator addresses can point at one receiver. When that receiver's index is later reconstructed (`getIndex`/`getV2Index` → `getWithPrefix`), the store performs an unbounded `prefixQuery` scan, loads every matching entry, and sorts them in memory — an attacker can inflate this to be arbitrarily large using low-cost Sybil transactions, analogous to the Vesting.sol `vest()`/`_claimableAmount()` unbounded-timelock-array bug.

### Finding Description
`DelegateResourceActuator.execute()` calls the private `delegateResource()` helper, which unconditionally records the delegation in the index store: [1](#0-0) 

For the "new" indexing model this results in a call to `DelegatedResourceAccountIndexStore.delegateV2`, which stores **one separate DB key per (owner, receiver) pair** rather than appending to a bounded array: [2](#0-1) 

`validate()` only requires `delegateBalance >= 1 TRX` and that owner/receiver are distinct existing accounts — it does not require the receiver to consent, and does not limit how many *different* owner addresses may delegate to the same receiver: [3](#0-2) [4](#0-3) 

This means an attacker can generate an unbounded number of Sybil accounts, freeze the 1-TRX minimum on each, and delegate to a single victim receiver address, creating one `V2_TO_PREFIX + receiver + attacker_i` key per Sybil.

Later, whenever the index for that receiver is read (e.g. via the `getDelegatedResourceAccountIndexV2` wallet/API query), `getV2Index` → `getWithPrefix` performs an **unbounded RocksDB prefix scan**, materializes every matching capsule into an `ArrayList`, and sorts the whole list by timestamp before returning it: [5](#0-4) 

This mirrors the Vesting.sol root cause exactly: an unprivileged actor can push unbounded entries associated with a *victim* account (no `require(beneficiary == msg.sender)`-style restriction exists here either), and a later read/settlement-style operation over that unbounded collection has no cap, causing cost to grow linearly (or worse, with the sort) with attacker-controlled input.

Additionally, the legacy (`!supportAllowDelegateOptimization`) code path stores the index as protobuf repeated fields (`toAccountsList`/`fromAccountsList`) inside a single `DelegatedResourceAccountIndexCapsule`, and only migrates/converts them via `DelegatedResourceAccountIndexStore.convert()`, which iterates the *entire* legacy list and performs `O(n)` additional writes the first time any delegate/undelegate touches that address: [6](#0-5) 
That conversion is not metered by TVM energy (this actuator's `calcFee()` returns 0 and it is not a TVM-charged native contract call in the legacy contract-actuator path), meaning the attacker-inflated list's migration cost is not priced proportionally to the resources it consumes.

### Impact Explanation
An unprivileged attacker can, at negligible ongoing cost (each delegation only requires owning/creating an account and freezing the 1 TRX minimum, which is later un-freezable/refundable), inflate the on-chain index data structure tied to an arbitrary victim address to an arbitrary size. Any subsequent read of that victim's delegated-resource index (via the public wallet/gRPC query API, or the one-time legacy-to-V2 `convert()` migration triggered by a state-changing transaction touching that address) then performs unbounded work — an unpriced/underpriced full prefix scan, in-memory list construction, and sort, or an unbounded batch of writes during conversion. This can degrade node responsiveness for that query, or (in the legacy-conversion case) cause the triggering transaction to consume disproportionate, unmetered resources. This is a resource-exhaustion / underpriced-public-work class issue, directly analogous to the referenced Vesting.sol finding where a malicious actor griefs a victim's account state to make their own future operation (claim/withdraw here: query/convert) infeasible or excessively costly.

The impact is bounded relative to the Solidity original (java-tron reads are not gas-metered on-chain per query, and the migration only triggers once per address), which lowers severity versus a full fund-lock, but the underlying pattern — unrestricted third-party writes into another account's unbounded index, later consumed by an unbounded loop/scan — is the same root cause.

### Likelihood Explanation
Reachable by any unprivileged account with no special permissions: only requires the ability to create accounts and freeze the protocol minimum (1 TRX) resource balance repeatedly, both of which are standard, permissionless operations. Sybil account creation on java-tron is cheap. The only limiting factor is the attacker's willingness to pay bandwidth/creation costs per Sybil delegation, which does not scale with the resulting victim-side query/processing cost (an asymmetry that is the core of the underpriced-work class).

### Recommendation
- Require the delegation actuators (`DelegateResourceActuator`, `FreezeBalanceActuator`) to cap or rate-limit the number of distinct delegator (`from`) entries that can accumulate against a single receiver's index, or store/aggregate them differently so reads are O(1)/O(log n) instead of O(n) prefix scans.
- Make `getWithPrefix` bound the number of entries scanned/returned (pagination) rather than an unconditional full scan + sort.
- If the legacy-to-V2 `convert()` migration work is unavoidable, ensure it cannot be forced by a third party against an inflated legacy index without appropriate resource accounting/fee, or lazily migrate incrementally rather than all-at-once.
- Consider requiring a minimum economically meaningful delegate amount (already 1 TRX) combined with a maximum number of concurrent delegations per receiver, similar to protections applied elsewhere (e.g., bounded unfreeze lists capped at 32 entries) to prevent unbounded per-account collections.

### Proof of Concept
1. Attacker creates `N` new accounts (Sybils), funds each with minimal TRX.
2. For each Sybil `S_i`, attacker: freezes 1 TRX for BANDWIDTH/ENERGY (`FreezeBalanceV2`), then issues `DelegateResourceContract` with `balance = 1 TRX`, `receiverAddress = victim`, from `S_i` — this is accepted per the validation logic shown in `DelegateResourceActuator.validate()` (lines 147-150, 191-209 above), with no check limiting how many distinct senders can target the same receiver.
3. Each such call causes `delegatedResourceAccountIndexStore.delegateV2(S_i, victim, timestamp)` to write a new key `V2_TO_PREFIX + victim + S_i` (`DelegatedResourceAccountIndexStore.java` lines 77-89).
4. Repeat for large `N` (e.g., tens of thousands) — cheap and fully permissionless.
5. Any subsequent call to `getDelegatedResourceAccountIndexV2(victim)` (Wallet API) invokes `getV2Index` → `getWithPrefix`, which now must prefix-scan, deserialize, and sort `N` entries (`DelegatedResourceAccountIndexStore.java` lines 114-138) — an unbounded-cost operation directly proportional to attacker-supplied `N`, with no corresponding fee paid by the querying party or the original attacker at read time.

Note: I was not able to fully verify, within available tool budget, whether any other *consensus-critical* (fee/energy-metered) code path besides the one-time legacy `convert()` iterates this index at write time for every subsequent transaction touching the victim address; this would materially increase severity if confirmed (e.g., turning it into a fully repeatable per-transaction DoS instead of a one-shot/query-time cost). This should be verified with deeper tracing of all callers of `DelegatedResourceAccountIndexStore.get/getIndex/getV2Index/convert` in a live Devin session before finalizing severity.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
