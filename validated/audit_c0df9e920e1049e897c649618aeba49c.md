### Title
`pox_4_compute_and_update_signers` can produce a `RewardSet` with `signers = Some(vec![])`, letting `verify_signer_signatures` accept a zero-signature block - ([File: stackslib/src/chainstate/nakamoto/mod.rs], [File: stackslib/src/chainstate/stacks/boot/mod.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` only rejects a reward set when `reward_set.signers()` is `None`; it never checks for an explicitly-empty-but-`Some` signer list. `StacksChainState::make_signer_set` (used by the PoX-4 signer-set computation path) can legitimately return `Some(vec![])` when every distinct signing key's aggregated stacked amount falls below the per-slot threshold, even though the (differently-aggregated) reward-address list is non-empty. Unlike the PoX-5 path, the PoX-4 path never checks for this degenerate empty-but-`Some` case, so a block with zero `signer_signature` entries can pass `0 < 0` and be accepted network-wide.

### Finding Description
The broken equality: SIGNING requires `total_weight_signed >= threshold` derived from a *non-trivial* reward set; here both sides degenerate to 0 so the inequality is vacuously satisfied.

`verify_signer_signatures` only guards the `None` case: [1](#0-0) 
and then computes `total_weight` via `reward_set.total_signing_weight()`, which sums an empty `Vec` to `0` without error when `signers = Some(vec![])`: [2](#0-1) 
`compute_voting_weight_threshold(0)` returns `0`: [3](#0-2) 
The signature loop over an empty `self.signer_signature` never executes, so `total_weight_signed` stays `0`, and `0 < 0` is `false`, so `Ok(0)` is returned: [4](#0-3) 

Root cause: `StacksChainState::make_signer_set` filters out any signing key whose aggregated `stacked_amt / threshold == 0`, but only returns `None` when the *input entries slice* is empty — not when the *filtered output* is empty: [5](#0-4) 
Because `make_reward_set`'s address-slot aggregation groups by `reward_address` while `make_signer_set`'s weight aggregation groups by `signing_key`, it is possible for several distinct stackers sharing one pooled reward address (each individually below the per-slot threshold, but collectively above it) to produce non-empty `rewarded_addresses` while every one of their distinct signing keys is individually filtered to weight 0 — yielding `signers: Some(vec![])`: [6](#0-5) 

Critically, `pox_4_compute_and_update_signers` never checks for this empty-signer-set condition before returning the `RewardSet`: [7](#0-6) 
This is in contrast to the PoX-5 path, which explicitly guards against `signer_set.is_empty()` and errors out with `ChainstateError::PoxNoRewardCycle`: [8](#0-7) 
and `get_signers_weights` similarly guards against the empty case with `NoRegisteredSigners`: [9](#0-8) 
No equivalent guard exists on the PoX-4 code path or inside `verify_signer_signatures` itself.

### Impact Explanation
If this reward set is used to validate a Nakamoto block (via `NakamotoChainState::accept_block` / `store_block_if_better` calling `verify_signer_signatures`, per `stackslib/src/chainstate/nakamoto/mod.rs:2917-2925`), a block with an empty `signer_signature` vector is accepted as fully valid with zero signer consent. This is a Critical-severity "invalid block accepted network-wide" case: every honest node computing the same deterministic reward set for that reward cycle would independently accept the unsigned block, since the check is purely a function of on-chain PoX state, not attacker-supplied data. This breaks the core Nakamoto consensus invariant that blocks require signer approval.

### Likelihood Explanation
This requires a specific PoX-4 stacking configuration: multiple distinct signing keys pooling stake behind a shared reward (BTC payout) address, where each individual signer's aggregated stacked amount is below the per-slot USTX threshold for that cycle, but the combined amount under the shared reward address exceeds it. This is a plausible configuration for a stacking pool operator who assigns a common payout address to many small delegators, each with their own signer key — well within reach of unprivileged, minority-stake participants (no majority stake needed, just careful reward/signer-key partitioning). It requires PoX-4 to be the active PoX contract for the cycle in question (i.e., before/during the PoX-5 transition), and does not require any privileged role.

### Recommendation
In `pox_4_compute_and_update_signers`, add the same guard used in the PoX-5 path: check whether the computed signer set (post-filter) is empty and, if so, return an error (e.g. `ChainstateError::PoxNoRewardCycle` or `NoRegisteredSigners`) instead of producing a `RewardSet` with `signers: Some(vec![])`. Additionally, as defense-in-depth, `verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs` should explicitly reject an empty-but-`Some` signer list (`signers.is_empty()`) rather than relying solely on the `None` check.

### Proof of Concept
Rust integration test plan:
1. Construct a `RewardSet::V0` via `RewardSet::empty()` and set `.signers = Some(vec![])` directly (bypassing `pox_5_make_signer_set`/`make_signer_set` guards, simulating the degenerate PoX-4 output).
2. Build a `NakamotoBlockHeader::empty()` with `signer_signature = vec![]`.
3. Assert both sides of the equality: `reward_set.total_signing_weight().unwrap() == 0` and `NakamotoBlockHeader::compute_voting_weight_threshold(0).unwrap() == 0`.
4. Call `header.verify_signer_signatures(&reward_set, StacksEpochId::latest())` and assert it currently returns `Ok(0)` — demonstrating the block is accepted with zero signatures.
5. After applying the fix (guard against empty `signers` list), assert the same call now returns `Err(ChainstateError::InvalidStacksBlock(_))` or equivalent, and add a companion property test on `StacksChainState::make_signer_set` / `pox_4_compute_and_update_signers` asserting it never returns a non-`None` but empty signer set when the input `entries` slice is non-empty.

    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    pub fn make_signer_set(
        threshold: u128,
        entries: &[RawRewardSetEntry],
    ) -> Option<Vec<NakamotoSignerEntry>> {
        let Some(first_entry) = entries.first() else {
            // entries is empty: there's no signer set
            return None;
        };
        // signing keys must be all-or-nothing in the reward set
        let expects_signing_keys = first_entry.signer.is_some();
        for entry in entries.iter() {
            if entry.signer.is_some() != expects_signing_keys {
                panic!("FATAL: stacking-set contains mismatched entries with and without signing keys.");
            }
        }
        if !expects_signing_keys {
            return None;
        }

        let mut signer_set = BTreeMap::new();
        for entry in entries.iter() {
            let signing_key = entry
                .signer
                .expect("BUG: signing keys should all be set in reward-sets with any signing keys");
            if let Some(existing_entry) = signer_set.get_mut(&signing_key) {
                *existing_entry += entry.amount_stacked;
            } else {
                signer_set.insert(signing_key, entry.amount_stacked);
            };
        }

        let mut signer_set: Vec<_> = signer_set
            .into_iter()
            .filter_map(|(signing_key, stacked_amt)| {
                let weight = u32::try_from(stacked_amt / threshold)
                    .expect("CORRUPTION: Stacker claimed > u32::max() reward slots");
                if weight == 0 {
                    return None;
                }
                Some(NakamotoSignerEntry {
                    signing_key,
                    stacked_amt,
                    weight,
                })
            })
            .collect();

        // finally, we must sort the signer set: the signer participation bit vector depends
        //  on a consensus-critical ordering of the signer set.
        signer_set.sort_by_key(|entry| entry.signing_key);

        Some(signer_set)
