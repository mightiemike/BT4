### Title
Silent, Unrecoverable Loss of External Caller's Refund Deposit in NEAR Wallet Contract's Fire-and-Forget Refund Promise - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract tracks a relayer/external caller's attached deposit via `CallerDeposit` and attempts to refund it if the underlying Ethereum-emulated action fails, via `rlp_execute_callback`. This refund is issued as a bare `env::promise_batch_action_transfer` on a freshly created batch promise, without any `.then()` continuation to verify or retry on failure. If that outgoing `Transfer` receipt itself fails, NEAR's own runtime deposit-refund mechanism returns the deposit to the *predecessor* of that failed receipt — i.e., back into the Wallet Contract's own account balance, not to the external caller who is owed the refund. Because `CallerDeposit` state is not persisted for retry, the external caller has no code path to reclaim these funds: they are absorbed into the wallet-owner's account with no accounting trail. This mirrors the reported XVS bridge bug class — a designed "release/refund" step whose own failure path is unhandled, permanently stranding value that belongs to a different party than the one who ends up holding it.

### Finding Description
`rlp_execute_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:275-317`) is the terminal callback for every `rlp_execute` invocation. When the inner action promise fails, it fires a refund: [1](#0-0) 

This refund is a `promise_batch_create` + `promise_batch_action_transfer` combo that is *not* chained via `.then()` to any further callback. `CallerDeposit` is populated only for external (non-owner) callers who attach a deposit to `rlp_execute`: [2](#0-1) 

`test_caller_refunds` in the test suite demonstrates the intended happy path — an external caller gets its deposit back when the cross-contract call fails: [3](#0-2) 

However, nothing in `rlp_execute_callback` verifies that the refund `Transfer` receipt it just created actually succeeds. Per NEAR's own runtime refund semantics, if an action receipt fails, any deposit attached to it is refunded to the receipt's `predecessor_id`, not to its intended `receiver_id`: [4](#0-3) 

Since the predecessor of the wallet contract's outgoing refund-`Transfer` receipt is the Wallet Contract account itself, a failure of that specific Transfer (e.g. the `account_id` stored in `CallerDeposit` is a non-existent, non-implicit named account, or is later deleted between the original call and the callback resolving, or any other reason the destination Transfer fails) causes the yoctoNEAR to be silently returned into the Wallet Contract's *own* balance — owned by the Ethereum-address user who owns the wallet, not the external relayer/caller who is supposed to be refunded. Because `CallerDeposit` is not persisted anywhere for retry and `rlp_execute_callback` returns a plain value (not a promise), `has_in_flight_tx` is cleared and the transaction is considered finished; there is no subsequent mechanism, transaction, or method that can recover this amount on behalf of the original caller.

This is analogous to the reported XVS bridge issue: a bridge fix added a "refund/recovery" step (`fallbackWithdraw`), but that step's own failure mode (a failed `sendAndCall` callback) was not handled, permanently stranding minted tokens in the destination contract instead of returning them to the rightful owner. Here, the Wallet Contract's refund step has the same class of gap: the refund promise's own failure is unhandled and the funds land with the wrong party.

### Impact Explanation
Funds belonging to an external caller (a relayer or any account that pays the deposit portion of an `rlp_execute` transaction, e.g. `EOABaseTokenTransfer`/`ERC20Transfer` fee-refund flows or arbitrary attached deposits) can become permanently unrecoverable by that caller and effectively absorbed into a third party's (the wallet owner's) account balance with no on-chain trace connecting it back to the depositor. This is a frozen-funds condition for the depositor: value transferred by one account is silently captured by an unrelated account as a side effect of an unhandled refund-receipt failure, matching the "permanently frozen funds" / unauthorized value movement criteria.

### Likelihood Explanation
Triggering the underlying condition (refund `Transfer` to `CallerDeposit.account_id` failing) requires an external caller submitting `rlp_execute` with an attached deposit while relaying a transaction that ultimately fails on the destination (a normal, easily reachable path for any relayer), combined with any condition that makes the reflexive Transfer receipt itself fail — the most direct such condition being submission when the caller's account is deleted, or any transient runtime condition causing that specific `Transfer` receipt to error. Since relayers/callers are unprivileged parties who fully control when and how they call `rlp_execute` and can also control their own account's existence/deletion timing relative to the async callback, this is realistically reachable without any privileged access.

### Recommendation
Chain the refund `promise_batch_action_transfer` with a `.then()` callback that checks `PromiseResult` for the refund receipt, and on failure, persist the pending refund (e.g., a `CallerDeposit`-keyed pending-refund map in contract state) so it can be retried or claimed later, rather than allowing the deposit-refund fallback (predecessor refund) to silently merge the funds into the Wallet Contract's own balance. At minimum, emit an event/log when a caller refund's underlying transfer fails so off-chain monitoring can detect and manually intervene, and consider disallowing the refund destination for such a caller-owed refund from being deleted/inactive without a resolution path.

### Proof of Concept
1. External caller (not the wallet's own address) calls `rlp_execute` on a `WalletContract`, attaching a NEAR deposit `D` and specifying an RLP-encoded transaction whose emulated action is designed to fail at the destination (e.g., targeting a nonexistent method or account) — `CallerDeposit { account_id: caller, yocto_near: D }` is captured (`types.rs:180-191`).
2. The inner action promise fails; `rlp_execute_callback` executes the `PromiseResult::Failed` branch and issues `promise_batch_action_transfer(refund_promise, D)` targeting `caller` (`lib.rs:296-305`).
3. Before this refund receipt is processed, the `caller` account is deleted (a normal, permissionless operation any account holder can perform on themselves), or otherwise made unable to receive the transfer (e.g., insufficient storage balance edge cases for named accounts).
4. The refund `Transfer` receipt fails on the receiving shard; per NEAR's refund model (`docs/RuntimeSpec/Refunds.md:15-18`), the deposit `D` is refunded to the receipt's `predecessor_id` — the `WalletContract` account itself — increasing its own spendable balance.
5. `rlp_execute_callback` had already returned `ExecuteResponse{success:false}` as a plain value (not a promise chained to check the refund outcome), `has_in_flight_tx` is reset to `false`, and no state records that `D` is still owed to `caller`. The wallet owner (a different party) now effectively controls `D`, and `caller` has no method call available to reclaim it.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
