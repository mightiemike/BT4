### Title
Unrefunded Rounding Loss in `ParticipateAssetIssueActuator.execute()` Due to Integer Division - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
`ParticipateAssetIssueActuator`, which handles the broadcast `ParticipateAssetIssueContract` transaction (TRON's on-chain "buy tokens with TRX" crowdsale mechanism), computes the number of tokens a buyer receives using floor-division (`floorDiv`) of `cost * num / trxNum`, while deducting the *entire* `cost` in TRX from the buyer's balance. Any remainder lost to integer-division truncation is not refunded to the buyer, exactly mirroring the unrefunded-excess bug class described in the report for `purchaseNMTWithETH()`/`purchaseNMTWithToken()`.

### Finding Description
In `execute()`, the buyer's full payment (`cost`) is unconditionally subtracted from the owner's balance and credited in full to the asset issuer's (`toAccount`) balance: [1](#0-0) [2](#0-1) 

However, the amount of asset tokens actually granted to the buyer is computed with truncating integer math: [3](#0-2) 

The same truncating calculation is repeated in `validate()`, and the only safeguard is a check that the computed amount is strictly greater than zero — there is no check or refund for the *fractional remainder* of the payment that does not correspond to a whole token: [4](#0-3) 

Because `cost` is paid in full (moved TRX-for-TRX to the issuer's account) while `exchangeAmount = floor(cost * num / trxNum)`, any `cost` value that is not an exact multiple of `trxNum / gcd(trxNum, num)` results in the buyer paying for a fractional token that they never receive, and that value is never returned to them. This is functionally identical to the NetMind report's root cause: "integer division during the calculation of `_purchaseNMTQuantity` ... results in a value that does not use the full [payment], the remainder is not refunded to the user."

### Impact Explanation
Every `ParticipateAssetIssueContract` transaction whose `amount` is not an exact multiple of the token's `trxNum`/`num` ratio silently transfers TRX value to the asset issuer without granting the corresponding proportional token amount to the buyer. This is a systemic, protocol-level asset/accounting corruption reachable by any account via a normal broadcast transaction, and it can be exploited/triggered on every crowdsale-style `AssetIssueContract` on the network, causing repeated, unrefunded loss of funds for buyers in favor of asset issuers.

### Likelihood Explanation
This is trivially and deterministically triggerable: any user picking an `amount` value that isn't a clean multiple of `trxNum` (which is the common case for most `trxNum`/`num` ratios, e.g. `trxNum=3, num=1`) will lose the truncated remainder on every purchase. No special privileges, timing, or race conditions are required — it happens on essentially every real-world participation transaction whose ratio yields a non-integer result, as demonstrated by the project's own tests (e.g. `sameTokenNameCloseExchangeDevisibleTest`) that assert the truncated (non-refunded) outcome as expected behavior.

### Recommendation
Mirror the report's recommended fix: before finalizing the transfer, recompute the exact TRX amount needed for the truncated `exchangeAmount` (`neededCost = ceil(exchangeAmount * trxNum / num)` or equivalently derive `cost` from `exchangeAmount` rather than the reverse), and refund the difference between the originally requested `cost` and `neededCost` back to the buyer's balance instead of transferring it in full to the issuer. Alternatively, reject transactions whose `amount` does not divide evenly into whole tokens, requiring the buyer to submit an exact amount.

### Proof of Concept
1. Issue an asset with `trxNum = 3`, `num = 1` (i.e., 1 token per 3 TRX).
2. Buyer broadcasts `ParticipateAssetIssueContract` with `amount = 5` (5 TRX).
3. `exchangeAmount = floorDiv(5 * 1, 3) = 1` token.
4. `validate()` passes since `exchangeAmount (1) > 0`.
5. `execute()` deducts the full `5` TRX from the buyer and credits `5` TRX to the issuer, but the buyer only receives `1` token — the value of `2` TRX (2/3 of a token) is permanently lost with no refund, repeatable indefinitely across transactions.
