## Analog Identified

### Title
Token-mapping mismatch in rescue-outbound attachment allows PRC20→external-asset substitution independent of the original inbound's asset — (`File: x/uexecutor/keeper/create_outbound.go`)

### Summary
The DODO bug's root cause is a callback (`executeOperation`) that trusts *shape* (correct callback signature, correct calling pool) instead of *origin* (who actually initiated the flash loan), letting an attacker drive privileged post-conditions with attacker-chosen parameters. The same trust pattern exists in `EVMHooks.PostTxProcessing` → `AttachRescueOutboundFromReceipt`: it authenticates an event purely by `(log.Address == UniversalGatewayPC, log.Topics[0] == RescueFundsOnSourceChainEventSig)` and then uses one attacker/relayer-influenceable event field (`event.PRC20`) to resolve which *external* asset a TSS-signed outbound will release — without cross-checking that this PRC20 matches the token that was actually part of the original stuck inbound.

### Finding Description
`x/uexecutor/keeper/evm_hooks.go:PostTxProcessing` runs unconditionally after **every** EVM transaction on Push Chain [1](#0-0) . It calls `AttachRescueOutboundFromReceipt`, which scans logs for `RescueFundsOnSourceChainEventSig` emitted by the `UniversalGatewayPC` system contract address and decodes the event [2](#0-1) .

The only origin check is `log.Address == UniversalGatewayPC` plus the topic signature — there is no check that the underlying transaction was the module-driven "legitimate rescue" flow, no check of `msg.sender`/`isModuleSender`, and no cross-validation that `event.PRC20` corresponds to the same token used in `originalUtx.InboundTx` (the CEA deposit or reverted inbound that made the UTX rescue-eligible): [3](#0-2) 

Once eligibility (`FAILED` CEA deposit, or `REVERTED` `INBOUND_REVERT` outbound) is confirmed from *trusted state*, the code builds the actual TSS-signed outbound: `Amount` and `Recipient` are taken from stored state (`originalUtx.InboundTx.Amount`, revert-recipient), which is good — but `ExternalAssetAddr` is derived from `event.PRC20`, an event field sourced from the same log that only had its *address+topic* authenticated, not its full semantic correctness against the original inbound: [4](#0-3) 

If the `PRC20` value carried in the on-chain `RescueFundsOnSourceChain` event can differ from the token actually associated with the stuck inbound (e.g., because the emitting Solidity function does not itself enforce `PRC20 == originalInbound.asset`), Push Chain's node code will happily attach an outbound record where `Amount` is denominated for one token but `ExternalAssetAddr` points at a different, and possibly far more valuable, registered asset on the source chain. Universal Validators subsequently sign and broadcast this outbound via TSS based on `ExternalAssetAddr`/`Amount`, which is the same class of bug as the DODO report: the module treats an externally-observable signal as fully self-authenticating instead of validating it end-to-end against the state it's supposed to be consistent with.

### Impact Explanation
If exploitable, this could cause the TSS/UV set to sign and broadcast a legitimate-looking outbound that releases the wrong (and potentially higher-value) external asset from the source-chain vault relative to what was actually locked/failed for that UTX — an unauthorized release/misrouting of protocol-controlled funds, matching the in-scope "unauthorized release" and "corruption of token mapping" impact categories.

### Likelihood Explanation
**Low-to-uncertain**, and this is the key caveat: the actual gate on this is the Solidity `UniversalGatewayPC.rescueFunds`-style function, which lives in the external `push-chain-core-contracts` repository, not in the indexed Push Chain node repo. I could not verify from this repository whether that Solidity function:
- restricts the caller to a privileged relayer/admin (which would make this out of scope per the "no privileged actor" rule), and/or
- itself enforces `PRC20 == <the token originally associated with the stuck inbound>` before emitting the event.

If either of those guards exists on the Solidity side, this finding is not exploitable by an unprivileged attacker and should be rejected. Without visibility into that contract, this can only be reported as a **plausible node-side gap** (the Go code performs no independent cross-validation of `event.PRC20` against the original inbound's asset before wiring it into a TSS-signable outbound), not a confirmed, fully-reachable vulnerability.

### Recommendation
In `AttachRescueOutboundFromReceipt` (`x/uexecutor/keeper/create_outbound.go`), before building the rescue `OutboundTx`, explicitly validate that `event.PRC20` matches the PRC20/asset address recorded on `originalUtx.InboundTx` (or the token config resolved from it) rather than trusting the event's `PRC20` field independently. This closes the gap regardless of what access control exists on the Solidity side, mirroring the DODO fix's philosophy of not trusting a callback/event by shape alone — validate it against the expected origin state.

### Proof of Concept
Not constructible with confidence from this repository alone — a full PoC requires the `UniversalGatewayPC.sol` rescue-emitting function's source (external repo) to confirm whether `PRC20` is attacker/relayer-suppliable independent of the original stuck inbound's asset, and whether the function is unprivileged. I recommend a Devin session with access to `push-chain-core-contracts` to confirm the emitting function's access control and parameter validation before treating this as a confirmed finding.
