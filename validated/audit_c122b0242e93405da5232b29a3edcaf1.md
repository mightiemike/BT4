### Title
Owner of an AccountId-mode global contract can front-run pending calls of every dependent account by silently redeploying malicious logic that executes with the dependent account's own balance - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
NEAR's global-contract feature lets an account `O` publish WASM code under `GlobalContractDeployMode::AccountId`, and any other account `U` "install" it via `UseGlobalContractByAccountId` (`Action::UseGlobalContract` → `AccountContract::GlobalByAccount(O)`). Unlike `DeployContract` (code pinned by hash to the deployer's own account) or `GlobalContractDeployMode::CodeHash` (immutable), the `AccountId` mode resolves to whatever code `O` has *most recently* deployed, looked up dynamically at the moment each receipt executes. Because `O` can redeploy new code at any time and it takes effect for every account referencing `O` by account id — including receipts already signed and in flight against `U` — `O` can front-run `U`'s pending call by swapping in malicious logic that runs with `U`'s own account balance and permissions, functionally identical to the MetaSwap `DELEGATECALL` front-running bug (owner rewrites the "adapter" implementation that other parties are relying on, right before it executes).

### Finding Description
`action_use_global_contract` / `use_global_contract` records only a *pointer* to the publisher account, not a code hash, for `AccountId`-mode contracts: [1](#0-0) 

`RuntimeContractIdentifier::resolve` re-resolves this pointer to a code hash on every single execution by reading the live `TrieKey::GlobalContractCode` entry for the publisher's account id: [2](#0-1) [3](#0-2) 

`action_deploy_global_contract` lets `O` overwrite the code stored under that key at will, at any time, with no restriction and no interaction with — or consent from — any account that has already opted into using it via `AccountId` mode: [4](#0-3) [5](#0-4) 

Crucially, the distribution/nonce mechanism is designed to make a redeploy visible to callers as fast as possible, even within the same chunk (`GlobalContractSameChunkCallFix`): [6](#0-5) 

The protocol's own documentation for `GlobalContractDeployMode::AccountId` acknowledges the mutability but frames it purely as a convenience feature ("allows the owner to update the contract for all its users") without describing any consent, pinning, or timelock mechanism protecting dependent accounts from a malicious/compromised update landing exactly in between a dependent account signing a transaction and that transaction's receipt executing: [7](#0-6) 

The execution model means the swapped-in code runs *as* the dependent account `U` — with `U`'s balance, storage, and promise-issuing rights (`account_balance`, `account_contract` are taken directly from `U`'s account and the resolved global contract in `execute_function_call`): [8](#0-7) 

So this is the direct structural analog of the MetaSwap issue: because the "adapter" (global contract) is referenced by a mutable pointer (account id) instead of an immutable identifier (code hash), the publisher can rewrite the logic that a completely different account's pending, already-signed operations will execute, with no way for the victim to detect or prevent the swap between signing and execution.

### Impact Explanation
Any account `U` that opts into a shared/"library" global contract via `UseGlobalContractByAccountId` implicitly grants the publisher `O` a standing, unbounded, unauditable ability to rewrite the code that runs against `U`'s own balance on every future call, including calls `U` has already signed and broadcast. A malicious or compromised `O` can:
- Wait for `U` (or many dependent accounts) to have pending `FunctionCall` receipts en route.
- Submit `DeployGlobalContractAction` with `AccountId` mode containing code that, e.g., issues `Transfer`/promise actions draining the caller's balance to an attacker-controlled account, disguised as the expected legitimate method.
- Because the redeploy is visible immediately (even same-chunk), the still-pending receipts against `U` execute the malicious code instead of the code `U` believed was in place when it signed/queued its transaction.

This is unauthorized value movement/state-transition risk that is not the fault of `U`'s own transaction content, purely a consequence of the mutable-by-account-id resolution scheme, and is reachable by any two ordinary accounts (no validator/operator privilege required) — matching the "concrete unauthorized value movement" and "invalid state transition acceptance" bar (the transition is protocol-valid but violates the security expectations users are led to rely on when integrating a shared library contract).

### Likelihood Explanation
Exploitation only requires: (1) publishing a global contract in `AccountId` mode (any account can do this — no special permission), (2) getting one or more accounts to reference it via `UseGlobalContractByAccountId` (a natural pattern for shared library/factory contracts, similar to how MetaSwap's adapter registry was meant to be used by many independent traders), and (3) timing a redeploy transaction to land before pending calls against dependent accounts execute. Since redeploys are visible essentially immediately (further hastened by `GlobalContractSameChunkCallFix`), and no cool-down, hash-pinning, or explicit governance/consent gate exists in `action_deploy_global_contract`/`use_global_contract`, the attack is straightforward for the publisher account and requires no chain-level race beyond normal transaction submission timing.

### Recommendation
Apply the same remediation direction the MetaSwap fix used: disallow silent, retroactive changes to code an account already depends on.
- Require dependent accounts to pin to an explicit code hash (`GlobalContractIdentifier::CodeHash`) rather than a mutable account-id pointer for any security-sensitive use, or
- Change `AccountId`-mode semantics so existing consumers are not automatically upgraded: e.g. require consumers to explicitly re-`UseGlobalContract` (i.e., re-consent) after a publisher redeploy, or add a mandatory delay/epoch boundary between a `DeployGlobalContractAction` (AccountId mode) and the new code becoming effective for already-referencing accounts, giving dependents a window to detect and react to the pending change.
- At minimum, clearly gas-meter/expose a "pending redeploy" signal so wallets/RPC callers can warn signers when the contract logic backing an in-flight transaction has changed since it was signed.

### Proof of Concept
1. Account `O` deploys global contract "V1" in `AccountId` mode: `DeployGlobalContractAction { code: V1, deploy_mode: AccountId }` (`action_deploy_global_contract`, `runtime/runtime/src/global_contracts.rs:25-63`).
2. Account `U` runs `UseGlobalContractAction { contract_identifier: AccountId(O) }`, setting `U.contract = AccountContract::GlobalByAccount(O)` (`use_global_contract`, `runtime/runtime/src/global_contracts.rs:76-109`).
3. `U` signs and broadcasts `FunctionCallAction { method_name: "swap", .. }` intending to invoke V1's logic against its own balance.
4. Before that receipt is applied, `O` broadcasts `DeployGlobalContractAction { code: V2_malicious, deploy_mode: AccountId }`, overwriting `TrieKey::GlobalContractCode{AccountId(O)}` (`apply_distribution_current_shard`, `runtime/runtime/src/global_contracts.rs:191-234`).
5. When `U`'s previously-signed "swap" receipt is finally applied, `RuntimeContractIdentifier::resolve` (`runtime/runtime/src/contract_code.rs:36-50`) re-reads the (now-malicious) code hash for `AccountId(O)`, and `execute_function_call` runs V2 with `U`'s own account balance/storage (`runtime/runtime/src/function_call.rs:257-278`), letting V2 issue a `Transfer`/promise action that drains `U`'s balance to an account controlled by `O` — all without `U` having signed anything referencing V2.

Uncertainty note: I was not able to directly trace mempool/chunk-scheduling timing guarantees (i.e., exact worst-case window between `U`'s transaction being accepted into a chunk and `O`'s competing redeploy being applied in the same or an earlier chunk) within the indexed content; the `GlobalContractSameChunkCallFix` comment in `global_contracts.rs:214-225` indicates the redeploy can affect calls within the *same* chunk, which reinforces feasibility, but a full end-to-end timing proof would require running a local test-loop/test-cluster scenario mirroring `test-loop-tests/src/tests/global_contracts.rs`.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

fn apply_distribution_current_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
) -> Result<Compute, RuntimeError> {
    let identifier = match &global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => GlobalContractCodeIdentifier::CodeHash(*hash),
        GlobalContractIdentifier::AccountId(account_id) => {
            GlobalContractCodeIdentifier::AccountId(account_id.clone())
        }
    };

    let is_nonce_fresh = check_and_update_nonce(global_contract_data, &identifier, state_update)?;
    if !is_nonce_fresh {
        return Ok(0);
    }

    let config = apply_state.config.wasm_config.clone();
    let trie_key = TrieKey::GlobalContractCode { identifier };
    let code_len = global_contract_data.code().len() as u64;
    state_update.set(trie_key, global_contract_data.code().to_vec());

    // Record the deploy so a same-chunk call can find the code without a warm cache.
    let code_hash = match global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => Some(*hash),
        GlobalContractIdentifier::AccountId(_) => None,
    };
    if ProtocolFeature::GlobalContractSameChunkCallFix.enabled(apply_state.current_protocol_version)
    {
        state_update.record_global_contract_deploy(ContractCode::new(
            global_contract_data.code().to_vec(),
            code_hash,
        ));
    }

    state_update.commit(StateChangeCause::ReceiptProcessing { receipt_hash: receipt.get_hash() });

    precompile_contract_with_warming(
        &ContractCode::new(global_contract_data.code().to_vec(), code_hash),
        config,
        apply_state.next_wasm_config.clone(),
        apply_state.cache.as_deref(),
    );

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }
