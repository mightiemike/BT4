### Title
Deploy-account validation-skip relies on mempool residency instead of authoritative deployment state, enabling signature-check bypass - ([File: crates/apollo_gateway/src/stateful_transaction_validator.rs])

### Summary
The sudo CVE describes a class of bug where a security-relevant decision (host-based privilege check) is made using a value that is not reliably synchronized with the authoritative source, so a party that should have lost privileges retains them. The closest reachable analog in this codebase is the "skip stateful validation for deploy_account + invoke" UX feature, where the sequencer decides whether to skip running an account's `__validate__` entry point (the signature check) based on whether the mempool reports that a `deploy_account` transaction is "in pool or recent block" for the sender — not based on the account actually being deployed in committed state.

### Finding Description
`skip_stateful_validations` in `crates/apollo_gateway/src/stateful_transaction_validator.rs` decides to skip stateful validation of an `Invoke` transaction whenever the tx nonce is `1`, the account nonce read from state is `0`, and `mempool_client.account_tx_in_pool_or_recent_block(sender_address)` returns `true`: [1](#0-0) 

This value is then propagated as `skip_validate` back through `extract_state_nonce_and_run_validations` / `run_pre_validation_checks`: [2](#0-1) [3](#0-2) 

The equivalent decision exists in the native blockifier path (`PyValidator::should_run_stateful_validations`), where `execution_flags.validate` is set to `false` when a `deploy_account_tx_hash` was supplied and the account nonce is still zero: [4](#0-3) [5](#0-4) 

The mempool's own test `mempool_state_retains_address_across_api_calls` documents that `account_tx_in_pool_or_recent_block` continues to report `true` for an address even after the transaction has left the pool (sent to batcher) and even after a block is committed — i.e., this signal is a heuristic recency indicator, not a proof that the specific deploy_account transaction succeeded or even that it will ever be included: [6](#0-5) 

The bug-class parallel to CVE-2023-7090 is: a privilege/validation decision (whether to require signature validation) is keyed off a value from one subsystem (the mempool's pool/recent-block membership tracking) that does not stay strictly synchronized with the authoritative subsystem (committed account deployment state), which is exactly the "config/state propagation gap leads to privilege retention" pattern in the sudo advisory.

### Impact Explanation
If an attacker can get `account_tx_in_pool_or_recent_block` to return `true` for a sender address without that address's `deploy_account` transaction ever being validly committed (e.g., by submitting a `deploy_account` transaction that is accepted into the pool/recent-block tracking but is later dropped, replaced, or fails at execution/commit, while the tracking entry persists), a subsequent `Invoke` transaction with nonce `1` for that (still-undeployed, nonce-0) account could have its `__validate__` (signature) check skipped. This would let a transaction be admitted and executed without proof of key ownership for the target account — a signature/authorization bypass.

### Likelihood Explanation
I was not able to fully verify this within the available search iterations. Specifically I could not confirm/deny:
- Whether `account_tx_in_pool_or_recent_block`'s "recent block" tracking has any eviction/expiry path that could be triggered by an attacker while the corresponding deploy_account never actually committed for that address.
- Whether `run_validate_entry_point` (referenced in `stateful_transaction_validator.rs`) has additional guards beyond `skip_validate` that would still enforce nonce/fee correctness even when signature validation is skipped.
- Whether downstream execution in blockifier still enforces some other invariant that would prevent state corruption even if `__validate__` is skipped for a not-yet-deployed account (e.g., class-hash-at-address checks would fail during actual execution since the account contract doesn't exist yet).

Given these open questions, I cannot assert with confidence that this reaches the "concrete loss or freezing of funds / unauthorized account action" bar required. It is a plausible bug-class match to the sudo CVE (a security decision keyed off a non-authoritative, laggy signal) but requires further investigation (particularly of `run_validate_entry_point` and the mempool's `known_addresses`/recent-block retention/eviction logic) to confirm actual exploitability.

### Recommendation
If pursuing this further, a Devin session with full file access should:
1. Read the full implementation of `run_validate_entry_point` in `crates/apollo_gateway/src/stateful_transaction_validator.rs` to see exactly what is skipped when `skip_validate` is true.
2. Read `Mempool::account_tx_in_pool_or_recent_block` in `crates/apollo_mempool/src/mempool.rs` and its underlying tracking structure to determine whether it can report `true` for an account whose `deploy_account` transaction never actually gets committed to state.
3. Confirm whether blockifier execution still independently enforces that the account contract exists / class hash is set for the sender before executing the invoke call when validation is skipped.

async fn skip_stateful_validations(
    tx: &ExecutableTransaction,
    account_nonce: Nonce,
    mempool_client: SharedMempoolClient,
) -> StatefulTransactionValidatorResult<bool> {
    if let ExecutableTransaction::Invoke(ExecutableInvokeTransaction { tx, .. }) = tx {
        // check if the transaction nonce is 1, meaning it is post deploy_account, and the
        // account nonce is zero, meaning the account was not deployed yet.
        if tx.nonce() == Nonce(Felt::ONE) && account_nonce == Nonce(Felt::ZERO) {
            let account_address = tx.sender_address();
            debug!("Checking if deploy_account transaction exists for account {account_address}.");
            // We verify that a deploy_account transaction exists for this account. It is sufficient
            // to check if the account exists in the mempool since it means that either it has a
            // deploy_account transaction or transactions with future nonces that passed
            // validations.
            return mempool_client
                .account_tx_in_pool_or_recent_block(tx.sender_address())
                .await
                .map_err(|err| mempool_client_err_to_deprecated_gw_err(&tx.signature(), err))
                .inspect(|exists| {
                    if *exists {
                        debug!("Found deploy_account transaction for account {account_address}.");
                    } else {
                        debug!(
                            "No deploy_account transaction found for account {account_address}."
                        );
                    }
                });
        }
    }

    Ok(false)
}

impl PyValidator {
    // Returns whether the transaction should be statefully validated.
    // If the DeployAccount transaction of the account was submitted but not processed yet, it
    // should be skipped for subsequent transactions for a better user experience. (they will
    // otherwise fail solely because the deploy account hasn't been processed yet).
    #[allow(clippy::result_large_err)]
    pub fn should_run_stateful_validations(
        &mut self,
        account_tx: &AccountTransaction,
        deploy_account_tx_hash: Option<TransactionHash>,
    ) -> StatefulValidatorResult<bool> {
        if account_tx.tx_type() != TransactionType::InvokeFunction {
            return Ok(true);
        }
        let tx_info = account_tx.create_tx_info();
        let nonce = self.stateful_validator.get_nonce(tx_info.sender_address())?;

        let deploy_account_not_processed =
            deploy_account_tx_hash.is_some() && nonce == Nonce(Felt::ZERO);
        let tx_nonce = tx_info.nonce();
        let is_post_deploy_nonce = Nonce(Felt::ONE) <= tx_nonce;
        let nonce_small_enough_to_qualify_for_validation_skip =
            tx_nonce <= self.max_nonce_for_validation_skip;

        let skip_validate = deploy_account_not_processed
            && is_post_deploy_nonce
            && nonce_small_enough_to_qualify_for_validation_skip;

        Ok(!skip_validate)
    }

fn mempool_state_retains_address_across_api_calls(mut mempool: Mempool) {

    // Test.

    // Note that in the future, the Mempool's state may be periodically cleared from records of old
    // committed transactions. Mirroring this behavior may require a modification of this test.
    assert!(mempool.account_tx_in_pool_or_recent_block(account_address));
