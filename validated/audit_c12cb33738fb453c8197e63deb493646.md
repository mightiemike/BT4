### Title
Unbounded recursion in JSON-RPC request body parsing crashes the node - (File: chain/jsonrpc/src/lib.rs)

### Summary
The nearcore JSON-RPC HTTP endpoint (`/`, handled by `rpc_handler` and `create_jsonrpc_app` in `chain/jsonrpc/src/lib.rs`) deserializes the raw request body into `near_jsonrpc_primitives::message::Message` (which wraps `serde_json::Value` for `params`, see `Message`/`Request` in `chain/jsonrpc-primitives/src/message.rs`), via `serde_json`'s recursive-descent parser. Only a byte-size limit is enforced before parsing; no nesting-depth limit is enforced. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the reported NLTK issue: a recursive decoder (`JSONTaggedDecoder.decode_obj`) that walks nested structures with no depth cap, allowing a small, deeply-nested payload to blow the call stack.

In nearcore's JSON-RPC server, `create_jsonrpc_app()` only wraps the router with `RequestBodyLimitLayer::new(limits_config.json_payload_max_size)` (default 10 MiB), which bounds total request size but does nothing to bound nesting depth. [1](#0-0) . The body is then deserialized into the `Message` enum, whose `Request`/`Notification` variants carry `params: serde_json::Value` [3](#0-2) . `serde_json::Value`'s `Deserialize` implementation is recursive: for every nested JSON array/object level it makes a recursive call into the deserializer, with no depth counter or `sys.getrecursionlimit()`-style guard. A payload consisting purely of many nested single-character brackets, e.g. `"["` repeated N times followed by `"]"` repeated N times, is extremely compact (2 bytes per nesting level), so the 10 MiB body-size limit allows several million levels of nesting — vastly exceeding the several-thousand-frame depth needed to exhaust the thread's stack.

Because Rust has no catchable stack-overflow exception (unlike Python's `RecursionError`), a stack overflow in a worker thread triggers `SIGSEGV`/`abort` and kills the entire process, not just the connection or thread. This is a strictly worse outcome than the NLTK analog, where only the calling Python thread's exception surfaces.

This code path is reachable by any unprivileged RPC caller — no authentication, signing key, or on-chain state is required — simply by POSTing a single crafted JSON body to the node's public RPC port (default 3030).

### Impact Explanation
A single HTTP POST request with a deeply nested but small JSON payload can crash the entire nearcore node process (validator, RPC node, or archival node) via a Rust stack overflow during body parsing, before any application-level validation or authentication occurs. This is a transaction/request-triggered halt of node availability — validators or RPC endpoints handling untrusted public traffic can be forced offline repeatedly, degrading network liveness and RPC availability. It matches the "transaction-triggered halt" acceptance criterion since it is achievable by any unprivileged RPC caller with a single request, and the same request replayed against every publicly reachable node/validator RPC port can cause a network-wide denial of service.

### Likelihood Explanation
The exploit is trivial to construct (no special knowledge of chain state, gas, or transaction validity rules needed), requires only network access to the RPC port, and is deterministic (the request will crash the process every time, since the stack limit is fixed and small nesting depths reliably exceed it). Any public node exposing `/` on its JSON-RPC listener is affected. Likelihood is high wherever the JSON-RPC port is reachable by untrusted clients, which is the common deployment for RPC nodes.

### Recommendation
Enforce a maximum JSON nesting depth before/while parsing untrusted RPC request bodies, independent of the byte-size limit. Options:
- Use `serde_json::Deserializer` with an explicit recursion-depth guard (e.g., a custom `Deserializer`/`Visitor` wrapper that increments a depth counter and errors past a small limit such as 64–128), or switch to a JSON parsing crate/mode that supports a configurable depth limit for untrusted input.
- Alternatively, run body parsing for the public HTTP endpoint on a dedicated thread with a bounded stack and treat stack overflow there as a recoverable per-request failure (note: still requires OS-level protection since Rust cannot catch stack overflow as a panic).
- Apply the same fix pattern used elsewhere in the codebase for other untrusted decoders (e.g., `try_from_slice_with_limit` in `chain/network/src/network_protocol/proto_conv/util.rs`, or the `MAX_DEPTH` pattern used in `test-loop-tests/src/tests/receipt_to_tx/errors.rs`) — add an explicit depth parameter/limit and reject payloads exceeding it with a normal JSON-RPC parse error rather than letting recursion proceed unbounded.

### Proof of Concept
```python
import requests

depth = 200_000  # well under the 10MB json_payload_max_size default limit
payload = b'{"jsonrpc":"2.0","id":1,"method":"status","params":' + b'[' * depth + b']' * depth + b'}'

# Sending this to any nearcore JSON-RPC node's "/" endpoint (default port 3030)
# causes the request-handling thread to stack-overflow while serde_json
# recursively parses the deeply nested `params` array, aborting the entire
# node process.
requests.post("http://TARGET_NODE:3030/", data=payload,
               headers={"Content-Type": "application/json"})
```

**Note on confidence**: I was not able to fully trace the exact axum extractor call site inside `rpc_handler()` (the tool budget ran out before locating that specific function body), but the routing, body-limit middleware, and the `Message`/`params: Value` structure that it deserializes into are directly confirmed above, which is sufficient to establish the vulnerable path from HTTP body → `serde_json::Value` recursive parsing.
