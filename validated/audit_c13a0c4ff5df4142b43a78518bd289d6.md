### Title
Unit/decimal mismatch between `OutboundTx.GasFee` (gas-token PRC20 decimals) and `OutboundObservation.GasFeeUsed` (destination-chain wei) corrupts gas-refund accounting - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`applyGasRefund` in `x/uexecutor/keeper/outbound.go` computes the excess gas to refund by directly subtracting two `big.Int` values, `outbound.GasFee` and `obs.GasFeeUsed`, that are populated from two different sources with different unit/decimal conventions, without any scaling step. This mirrors the H-3 pattern from the external report: one value is scaled/denominated one way, the other is denominated another way, and both are combined as if they were in the same base unit.

### Finding Description
`outbound.GasFee` is set by `buildRevertOutbound` (`x/uexecutor/keeper/build_revert_outbound.go:50-53`) and by the standard outbound-creation path from `GetOutboundTxGasAndFees` (`x/uexecutor/keeper/gas_fee.go:26-64`), which calls `UniversalCore.getOutboundTxGasAndFees(prc20, gasLimit)`. Per the module README, `gas_fee` is documented as "amount paid to relayer" and `gas_token` as "PRC20 used to pay relayer" [1](#0-0) , i.e. `GasFee` is denominated in whatever PRC20 gas token was selected — a token whose decimals vary per configured asset (6 for USDC-class tokens, 9 for SOL-class tokens, 18 for ETH/BNB-class tokens) [2](#0-1) [3](#0-2) .

`obs.GasFeeUsed`, by contrast, is populated by the `universalClient` EVM confirmer as `gasUsed * gasPrice`, i.e. the destination chain's native gas cost in wei, with no conversion to the gas token's unit: [4](#0-3) . This is also explicitly documented on the wire type: `GasFeeUsed` is "gas fee used in wei (decimal string)" [5](#0-4) .

`applyGasRefund` then compares and subtracts these two values directly, with no decimal normalization between the gas-token's own decimals and the raw wei figure: [6](#0-5) 

This is structurally identical to the reported UErc20 bug: one operand (`amount`/`GasFee`) is denominated in a token-specific scale while the other operand (`interest`/`GasFeeUsed`) is left in a different scale (wei), and both are fed into the same arithmetic as if comparable.

### Impact Explanation
Because `GasFee` (gas-token decimals, e.g. 6) and `GasFeeUsed` (wei, effectively 18-decimal-scale native units) are combined without conversion:
- When the gas token has fewer decimals than wei, `GasFee` will numerically be far smaller than `GasFeeUsed`, so `gasFee.Cmp(gasFeeUsed) <= 0` triggers on essentially every outbound, permanently suppressing refunds — protocol/relayer keeps the entire pre-charged gas fee even though the destination-chain execution used far less, corrupting refund accounting (`x/uexecutor/keeper/outbound.go:194-196`).
- When the ordering happens to invert (e.g. large enough `GasLimit`/`GasPrice` snapshot vs a low actual `gasUsed*gasPrice` in wei terms relative to a high-decimal gas token), `refundAmount` computed via raw subtraction is a garbage value denominated in the wrong unit, and `CallUniversalCoreRefundUnusedGas` (`x/uexecutor/keeper/evm.go:597-644`) is invoked with that value — mis-crediting the refund recipient by orders of magnitude relative to the intended amount, i.e. overpayment/underpayment of protocol-controlled PRC20/native funds through the honest-validator outbound-voting flow.

This directly corrupts gas-fee/refund accounting reachable from ordinary outbound execution with honest validators — matching the "corruption of gas fee accounting, refund accounting" allowed impact.

### Likelihood Explanation
This triggers on every successful/failed outbound whose destination gas token is not the destination chain's native 18-decimal asset (e.g. any USDC/USDT/SOL-denominated gas token), which per the config files in this repo is a common, non-privileged, default configuration (`usdc.json`, `usdt.json`, `bnb.json` all reference varying decimals). No malicious actor input is required — honest UV votes with a correctly-observed `gas_fee_used` in wei are sufficient to reproduce the mismatch.

### Recommendation
Normalize both operands to a common base unit before comparing/subtracting in `applyGasRefund`: either convert `obs.GasFeeUsed` (wei) into the gas token's own decimal scale using the token's decimals/exchange rate before computing `refundAmount = gasFee - gasFeeUsed`, or ensure `GetOutboundTxGasAndFees`/`getOutboundTxGasAndFees` and the wei-based `gasFeeUsed` are documented and enforced to be in the same unit end-to-end, with an explicit scaling step (analogous to the recommended fix of scaling both `amount` and `interest` consistently in the original report).

### Proof of Concept
1. Configure an outbound destination-chain gas token as `USDC.arb` (`decimals: 6`) as seen in `config/testnet-donut/arb_sepolia/tokens/usdc.json`.
2. `UniversalCore.getOutboundTxGasAndFees` returns `GasFee` denominated in USDC's 6-decimal units, e.g. `GasFee = 500000` (0.5 USDC).
3. The relayer executes the outbound on Arbitrum Sepolia consuming real gas, e.g. `gasUsed = 100000`, `gasPrice = 100000000` wei/gas → `gasFeeUsed = 10^13` wei, reported verbatim by `event_confirmer.go` as `GasFeeUsed = "10000000000000"`.
4. Honest UVs vote this observation via `VoteOutbound` → `applyGasRefund` compares `gasFee (500000)` against `gasFeeUsed (10000000000000)`; since `gasFee.Cmp(gasFeeUsed) <= 0` is true, no refund is ever computed/issued, even though only a tiny fraction of the pre-charged gas fee (in USDC terms) was actually consumed — the excess is permanently stuck / never returned to the user, corrupting refund accounting on every such outbound.
