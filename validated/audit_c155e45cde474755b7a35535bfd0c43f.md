## Finding [1](#0-0) 

### Title
Unhandled exception in `sanitizeHost` from malformed `host` parameter causes uncaught crash of auth handler - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`sanitizeHost` decodes an attacker-controlled, base64-encoded `host` query parameter and feeds it directly into `new URL()` without any try/catch, mirroring the reported bug class: an untrusted, weakly-validated conversion (there, `U512`→`U256`; here, base64 bytes → `URL`) that can throw an unhandled exception and abort the request flow instead of failing gracefully.

### Finding Description
`sanitizeHost` validates the `host` parameter with a loose regex before decoding and parsing it: [2](#0-1) 

The regex `^[0-9a-zA-Z+/]+={0,2}$` only checks the character set, not that the string is well-formed base64 (e.g., it doesn't enforce a length that's a multiple of 4). `decodeHost` simply calls `atob(host)`: [3](#0-2) 

`atob()` throws `DOMException`/`InvalidCharacterError` on malformed base64 input, and even when it succeeds, the decoded bytes are attacker-controlled arbitrary text that is spliced directly into a URL string and passed to `new URL()`: [4](#0-3) 

Unlike `sanitizeShop`, which only uses regex tests and safely returns `null` for invalid input, `sanitizeHost` performs decoding and URL construction that can throw runtime exceptions rather than returning `null`. Neither call (`atob`, `new URL`) is wrapped in a try/catch inside this function, so any exception propagates up to the caller.

`sanitizeHost` (via `shopify.utils.sanitizeHost` / `getEmbeddedAppUrl`) is reachable from unauthenticated request-handling code paths that read the `host` query parameter supplied by the browser/merchant during embedded-app loading and OAuth flows, e.g. `get-embedded-app-url.ts`, `redirect-to-shopify-or-app-root.ts`, and `validate-shop-and-host-params.ts` across the Express/Remix/React-Router adapters.

### Impact Explanation
An anonymous request with a malformed `host` value (e.g., an odd-length base64-looking string, or a validly-decoding string whose bytes are not a legal URL/hostname) causes `atob()` or `new URL()` to throw synchronously and uncaught within `sanitizeHost`. If the calling route handler does not itself wrap the call in try/catch, this results in an unhandled exception in the request path used for admin embedding / OAuth redirect validation — a denial-of-service of the auth handler for that request (and, depending on the runtime, potentially an unhandled promise rejection or process-level error). This matches the "DoS of an auth handler" acceptance criterion.

### Likelihood Explanation
The `host` parameter is fully attacker-controlled on requests that reach embedded app URL construction and shop/host validation helpers used before authentication completes, so no privileged access is required to trigger this path — a single crafted HTTP GET to any embedded-app route is sufficient to attempt to trigger the exception.

### Recommendation
Wrap the `atob()`/`new URL()` calls inside `sanitizeHost` in a try/catch and return `null` (or throw `InvalidHostError` only when `throwOnInvalid` is set, consistent with `sanitizeShop`'s contract) instead of letting the underlying `DOMException`/`TypeError` propagate uncaught. Additionally, tighten the base64 regex validation (length % 4 check) to reduce reliance on `atob`'s own error behavior.

### Proof of Concept
Calling `shopify.utils.sanitizeHost(host)` with a `host` value such as an odd-length base64-looking string (e.g., `"abcde"`, which passes `/^[0-9a-zA-Z+/]+={0,2}$/` but is not valid base64 padding) will cause `atob()` to throw, propagating out of `sanitizeHost` uncaught. Similarly, a base64 string that decodes to bytes containing characters illegal in a URL authority component will cause `new URL()` to throw a `TypeError` uncaught inside `sanitizeHost` — this can be exercised via any embedded-app route (e.g., app root, auth redirect helpers) that passes the request's `host` query parameter into `sanitizeHost`/`getEmbeddedAppUrl` without its own try/catch.

**Note:** I could not fully confirm from the available index whether every calling site (e.g., `validate-shop-and-host-params.ts` in the Remix/React-Router/Express adapters) wraps its `sanitizeHost` call in a try/catch — I was only able to see file-level references, not their full bodies, before running out of tool iterations. If those callers do already catch exceptions, the impact would be reduced to a handled 4xx error rather than a full DoS; I'd recommend confirming this via a full read of those files in a Devin session.

```typescript
export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }

    return sanitizedHost;
  };
```
