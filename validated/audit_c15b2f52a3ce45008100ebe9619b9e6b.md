## Title
Protocol treasury reward silently overwritten (and lost) when the treasury account is also selected as an epoch validator - (File: `chain/epoch-manager/src/reward_calculator.rs`)

### Summary
`RewardCalculator::calculate_reward` builds a single `HashMap<AccountId, Balance>` (`res`) that is meant to hold, per account, the reward to credit for the epoch. It first inserts the protocol treasury's guaranteed share keyed by `protocol_treasury_account`, then iterates over all epoch validators and does a plain `res.insert(account_id, reward)` for each one. If the protocol treasury account is itself one of the epoch's selected validators, the second insert silently overwrites the first, dropping the treasury's `epoch_protocol_treasury` share instead of adding it to the validator reward, even though the "total minted" accumulator still counts both amounts.

### Finding Description
`calculate_reward` first computes and inserts the treasury cut: [1](#0-0) 

It then iterates the per-validator stats (`validator_block_chunk_stats`, one entry per validator account for the epoch) and unconditionally overwrites `res[account_id]` with the individual validator reward, while still adding that reward on top of the running `epoch_actual_reward` total: [2](#0-1) 

`validator_block_chunk_stats` is populated by `compute_validators_to_reward_and_kickout` from the actual epoch validator set, one entry per `account_id`: [3](#0-2) 

There is no code that excludes `protocol_treasury_account` from being a regular validator — it is a plain `AccountId` set in genesis config, and any account (including the one designated as treasury) can submit a `Stake` action and be selected into the validator set two epochs later, exactly like any other account. When that happens, `res.insert(account_id, reward)` at line 142 overwrites the treasury entry inserted at line 84, so the returned reward map contains only the (typically much smaller) per-validator reward for that account instead of `epoch_protocol_treasury + validator_reward`.

This is the same bug class as the reported Sherlock finding: a map is populated from two different sources keyed by the same identifier, and the second write clobbers the first instead of accumulating, causing part of the intended payout to be lost.

Downstream, `update_validator_accounts` in the runtime credits the treasury only if it isn't already present in `stake_info`, and otherwise looks up the (now already-clobbered) reward via a single `get(account_id)`: [4](#0-3) 

Meanwhile `epoch_actual_reward` (returned as the second tuple element and stored as `minted_amount` on the `EpochInfo`) still includes both the treasury share and the validator share that was added on top of it: [5](#0-4) [6](#0-5) 

so the network believes it minted `epoch_protocol_treasury + validator_reward`, while only `validator_reward` is ever actually credited to any account — the treasury's share vanishes without being credited or burned explicitly.

### Impact Explanation
Whenever the account configured as `protocol_treasury_account` also stakes and becomes a selected validator for an epoch, its guaranteed protocol-treasury reward for that epoch is permanently lost: it is neither credited to the treasury account nor to anyone else, yet `minted_amount`/`epoch_actual_reward` (used for total-supply accounting on `EpochInfo`) still counts it as minted. This is a genuine, deterministic loss of funds/inflation-accounting inconsistency (the recorded minted amount overstates the sum of amounts actually credited to accounts), matching the "Rewards may be lost … overwritten" bug class from the source report, reachable purely through a normal `Stake` transaction from the treasury-controlled account — no special/validator-only privilege beyond being a staking participant is required.

### Likelihood Explanation
This requires that the specific account configured in genesis as `protocol_treasury_account` submits a `Stake` action and gets selected into the epoch's validator set — a state that is entirely reachable through ordinary, unprivileged staking transactions from that account's key holder. It is not attacker-controlled in the adversarial sense (the treasury account's key is normally held by the protocol/foundation), so likelihood of intentional exploitation is low, but the bug is triggered by a completely legitimate, non-malicious use of the staking mechanism (the treasury account choosing to also validate), making it a real, reachable, unintentional loss-of-funds bug rather than a purely theoretical one.

### Recommendation
In `RewardCalculator::calculate_reward`, when inserting a validator's reward into `res`, accumulate rather than overwrite any existing entry for that account, e.g.:
```rust
res.entry(account_id)
    .and_modify(|r| *r = r.checked_add(reward).unwrap())
    .or_insert(reward);
```
This ensures that if `protocol_treasury_account` is also a validator, its treasury share and validator share are both credited, consistent with the `epoch_actual_reward` total that already assumes both are minted.

### Proof of Concept
1. Set genesis config so `protocol_treasury_account = "treasury.near"`.
2. Have `treasury.near` submit a `Stake` action with sufficient stake to be selected as a validator (an ordinary, unprivileged transaction).
3. Wait until `treasury.near` is included in the validator set for an epoch and produces/validates blocks/chunks online.
4. At epoch end, `calculate_reward` is invoked: `res.insert("treasury.near", epoch_protocol_treasury)` runs first (`reward_calculator.rs:84`), then the validator loop runs `res.insert("treasury.near", validator_reward)` (`reward_calculator.rs:142`), overwriting the treasury entry.
5. Inspect the resulting `res` map (or the state changes credited via `update_validator_accounts`): `treasury.near` receives only `validator_reward`, not `epoch_protocol_treasury + validator_reward`, while `epoch_actual_reward`/`minted_amount` on the `EpochInfo` reflects the sum of both — demonstrating the lost treasury reward.
