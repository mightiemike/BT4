### Title
Write-cache size accounting ignores per-account storage overhead, letting `write_cache_limit_bytes` be silently exceeded - ([File: accounts-db/src/accounts_cache.rs])

### Summary
The external report describes an EntryPoint gas-penalty mechanism that reserves capacity (`paymasterPostOpGasLimit`) but fails to charge for it when `postOp` isn't invoked, letting reserved-but-unaccounted space consume bundle capacity that should be available to other operations. The `AccountsCache`/`SlotCache` write-cache accounting has the same class of defect: the byte counter used to decide when the cache is "too big" and must be flushed only tracks account *data* length, not the actual per-account storage footprint, so the cache can grow well past its configured `write_cache_limit_bytes` budget without triggering the flush that is supposed to bound it.

### Finding Description
`SlotCache::insert` computes the cost of caching an account purely from `account.data().len()` and adds it to both the per-slot `size` counter and the cross-cache `total_size` counter: [1](#0-0) 

`AccountsCache::size()` simply returns this `total_size` accumulator, and it is the sole input to `AccountsDb::should_aggressively_flush_cache`, which gates whether the background service force-flushes the write cache once it exceeds `write_cache_limit_bytes`: [2](#0-1) 

This accounting ignores the fixed per-account overhead that every cached entry actually costs: a `DashMap<Pubkey, Arc<CachedAccount>>` entry (pubkey, hashmap bookkeeping, `Arc` control block, `CachedAccount` struct with its own `pubkey` field and `AccountSharedData` header/lamports/owner/executable metadata), plus the eventual `AppendVec::calculate_stored_size` overhead charged per account when it is actually flushed to storage. The same disk-oriented function is referenced when accounting the *stored* bytes at flush time, but is not used for the *in-memory cache* threshold check: [3](#0-2) 

Because the tracked cost per account is just its data length (often 0 for many system/vote/small accounts) rather than the real fixed overhead per entry, a workload that creates a very large number of zero- or small-data-length accounts can push the actual heap/DashMap/index footprint of the write cache far beyond `write_cache_limit_bytes` while `AccountsCache::size()` still reports a tiny number, so `should_aggressively_flush_cache` never returns `true` and the flush that is meant to bound memory use never fires early. This directly parallels the gas-limit bug: a reserved/consumed resource (memory occupied by a cached account entry) is not counted toward the metric that is supposed to penalize/bound it, so the safety threshold becomes ineffective for the class of usage that dodges the metric.

### Impact Explanation
An validator processing many accounts with little or no data (e.g., many freshly created zero-lamport/zero-data accounts, or accounts whose data shrinks to 0 as in `SlotCache::insert`'s shrink branch) will have its accounts write-cache grow proportionally to the *number* of cached accounts rather than to the configured byte budget. This causes disproportionate memory consumption relative to the configured `--accounts-db-write-cache-limit`, since the operator-configured safety valve is bypassed. This falls under the allowed "disproportionate storage and CPU cost" impact class for this scan, since the actual resident memory usage (DashMap entries, `Arc<CachedAccount>` allocations, per-account index bookkeeping) is not bounded by the value operators configure to control it.

### Likelihood Explanation
Any transaction stream containing a high volume of accounts with small/zero data payloads (which is common and cheap to construct, e.g. simple system-program allocate/assign patterns or votes) drives this discrepancy; no privileged access or malicious cluster is required, purely normal high-account-churn load. However, the actual per-entry overhead (tens to a couple hundred bytes) is much smaller in absolute terms than the multi-GB default `WRITE_CACHE_LIMIT_BYTES_DEFAULT`, so triggering unbounded/uncontrolled growth requires a correspondingly very large number of distinct small accounts to be cached before a root flush occurs, which limits how far the overshoot can practically be pushed under normal cluster throughput.

### Recommendation
Include a fixed per-entry overhead constant (covering `CachedAccount`, `Arc` control block, and the `DashMap` slot cost, similar to `CACHE_ENTRY_SIZE` already used by `ReadOnlyAccountsCache`) in `SlotCache::insert`'s size accounting instead of using `account.data().len()` alone, so `AccountsCache::size()` reflects the real memory cost of pinning an entry in the write cache and `should_aggressively_flush_cache` triggers correctly under high account-count, low-data-size workloads.

### Proof of Concept
1. Configure a validator/test harness with a small `write_cache_limit_bytes` (as in `run_test_flush_accounts_cache_if_needed`, using `db.write_cache_limit_bytes = Some(N)` [4](#0-3) ).
2. Repeatedly call `AccountsDb::store_for_tests` with a large number of unique pubkeys each holding zero-length account data (`space = 0`), across many unrooted/rooted slots, so the number of cached entries grows into the hundreds of thousands while `SlotCache::size`/`AccountsCache::total_size` stay at or near 0 (since `data_len == 0` contributes nothing to the counter, see `SlotCache::insert` at lines 101-135).
3. Observe that `should_aggressively_flush_cache` (accounts_db.rs:4219-4227) never returns `true` regardless of the number of cached accounts, because `self.accounts_cache.size()` remains near zero, while actual heap usage (DashMap buckets, `Arc<CachedAccount>` allocations, index entries) grows unbounded with account count — demonstrating the metric does not reflect real reserved memory, analogous to the unpenalized `paymasterPostOpGasLimit` reservation in the source report.

    fn insert(&self, pubkey: &Pubkey, account: AccountSharedData) -> (Arc<CachedAccount>, bool) {
        let data_len = account.data().len() as u64;
        let item = Arc::new(CachedAccount {
            account,
            pubkey: *pubkey,
        });
        let is_new_key = if let Some(old) = self.cache.insert(*pubkey, item.clone()) {
            self.same_account_writes.fetch_add(1, Ordering::Relaxed);
            self.same_account_writes_size
                .fetch_add(data_len, Ordering::Relaxed);

            let old_len = old.account.data().len() as u64;
            let grow = data_len.saturating_sub(old_len);
            if grow > 0 {
                self.size.fetch_add(grow, Ordering::Relaxed);
                self.total_size.fetch_add(grow, Ordering::Relaxed);
            } else {
                let shrink = old_len.saturating_sub(data_len);
                if shrink > 0 {
                    self.size.fetch_sub(shrink, Ordering::Relaxed);
                    self.total_size.fetch_sub(shrink, Ordering::Relaxed);
                }
            }
            false
        } else {
            self.size.fetch_add(data_len, Ordering::Relaxed);
            self.total_size.fetch_add(data_len, Ordering::Relaxed);
            self.unique_account_writes_size
                .fetch_add(data_len, Ordering::Relaxed);
            self.accounts_count.fetch_add(1, Ordering::Release);
            self.total_accounts_count.fetch_add(1, Ordering::Relaxed);
            true
        };
        (item, is_new_key)
    }
