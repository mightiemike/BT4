### Title
Unbounded MarketOrderStore growth via repeated create/cancel cycles bypassing MAX_ACTIVE_ORDER_NUM - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.validate()` limits only the number of *active* orders per account (`marketAccountOrderCapsule.getCount()`), while `createAndSaveOrder` derives the persisted order key from `getTotalCount()`, a counter that is incremented on every create and never decremented on cancel. An attacker can loop create+cancel indefinitely, permanently growing `MarketOrderStore` while only ever holding at most one active order, for the flat cost of `MarketSellFee` + `MarketCancelFee` per cycle.

### Finding Description
`validate()` rejects new orders only when `marketAccountOrderCapsule.getCount() >= MAX_ACTIVE_ORDER_NUM` [4](#0-3) . `execute()` then calls `createAndSaveOrder`, which computes the new order's DB key via `MarketUtils.calculateOrderId(..., marketAccountOrderCapsule.getTotalCount())`, increments both `count` and `totalCount`, and persists the new `MarketOrderCapsule` into `orderStore` (`MarketOrderStore`) [2](#0-1) .

When the attacker cancels that order via `MarketCancelOrderActuator.execute()`, the order is set to `State.CANCELED`, `MarketUtils.updateOrderState` calls `accountOrderCapsule.removeOrder(...)` (which decrements `count`, not `totalCount`), and the order is unlinked only from `pairPriceToOrderStore`'s order-id list — it is `put` back into `orderStore` in its canceled state, never deleted [5](#0-4) [1](#0-0) .

Because `count` returns to 0 after cancel but `totalCount` keeps rising, `validate()`'s `MAX_ACTIVE_ORDER_NUM` check never blocks the next create, letting the attacker repeat the cycle without limit. Each cycle leaves one permanent (canceled, never pruned) record in `MarketOrderStore`. No other check (signature, balance, fork gate, fee) limits the number of cycles beyond ordinary balance sufficiency for the flat fees.

### Impact Explanation
This is a DoS-via-protocol-implementation issue: an attacker can grow `MarketOrderStore`'s key count linearly with the number of create/cancel cycles executed, at a cost of only `MarketSellFee + MarketCancelFee` per cycle (both flat, size-independent fees), with no per-account or global cap on total orders ever created. Over time this inflates full-node on-disk state size, degrading iteration/backup/sync performance disproportionately to the fees actually paid — the fee is a small constant, not scaled to permanent storage consumption.

### Likelihood Explanation
Preconditions are minimal and match the unprivileged-attacker model: any funded account, with `AllowMarketTransaction` enabled (a normal committee-controlled feature flag, not attacker-controlled but assumed enabled per the question's precondition). The attack is trivially repeatable — a simple loop of `MarketSellAssetContract` + `MarketCancelOrderContract` pairs — and requires no special timing, race conditions, or privileged access. Cost per cycle is bounded and predictable (flat fees), while storage growth is unbounded, making the attack highly feasible for a well-funded but otherwise unprivileged actor.

### Recommendation
Either (a) delete canceled/inactive `MarketOrderCapsule` entries from `MarketOrderStore` once they are no longer referenced by any active list, or (b) enforce `MAX_ACTIVE_ORDER_NUM`-style limits against `totalCount` (i.e., a per-account lifetime order cap, not just concurrent-active cap), or (c) make `MarketSellFee`/`MarketCancelFee` scale with the number of lifetime orders created so storage cost is proportional to fee revenue. A combination of pruning old canceled orders after a retention window plus a lifetime cap is preferable to avoid unbounded growth while preserving order-id uniqueness guarantees.
