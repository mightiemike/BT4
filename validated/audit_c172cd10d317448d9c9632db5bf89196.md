### Title
Missing zero-address check in `TransferActuator`/`TransferAssetActuator` allows irrecoverable, unrecoverable loss of TRX/TRC10 sent to an all-zero address - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
The external report flags LibERC20's `mint` function for not rejecting `_to == address(0)`, which causes newly minted tokens to be irretrievably lost while `totalSupply` is still incremented — an accounting/asset-loss bug rooted in a missing zero-address check on a value-creating/moving code path. The closest reachable analog in java-tron is the address validation used by `TransferActuator` and `TransferAssetActuator`, which accept a `toAddress` from an anonymous, unprivileged, broadcast transaction and validate it solely with `DecodeUtil.addressValid()`. That function checks only the byte length and the network prefix byte, never that the 20-byte payload is non-zero.

### Finding Description
`TransferActuator.validate()` calls `DecodeUtil.addressValid(toAddress)` [2](#0-1)  and `execute()` auto-creates the destination account and moves TRX to it if it doesn't already exist [3](#0-2) . `TransferAssetActuator.execute()` follows the same pattern for TRC10 tokens, auto-creating the `toAddress` account and crediting the asset amount to it [4](#0-3) . In both cases the only address-format gate is `DecodeUtil.addressValid`, which accepts any 21-byte value whose first byte matches the network prefix (`0x41` on mainnet), including a payload of 20 zero bytes [1](#0-0) . Because that all-zero payload does not correspond to any hash160 of a known/derivable public key, any TRX or TRC10 balance moved there is permanently unspendable — functionally equivalent to the "mint to zero address" loss described in the report (value created/transferred is stranded), except here it is an existing balance rather than newly minted supply.

### Impact Explanation
Funds (TRX or TRC10 tokens) sent to the zero-payload address become permanently inaccessible, since no private key can produce that hash160. This is a genuine, if narrow, asset-loss condition reachable from an ordinary broadcast transaction signed by the sender — the loss falls on whoever sends there (typically by mistake, e.g., wallet bug, or a compromised UI), not an attacker draining someone else's funds. It does not by itself corrupt global accounting (no `totalSupply`-style invariant exists for TRX; TRC10 total supply is also unaffected since the tokens are still tracked as belonging to the zero-address account) and does not enable a broader attacker-controlled exploit against third parties.

### Likelihood Explanation
Likelihood is low: for the loss to occur, the sender itself must construct/sign a transaction with `toAddress` set to the specific zero-payload value, which normal wallet software would not generate. It's the same "footgun" class as Ethereum's classic mint/transfer-to-zero issue, but on java-tron it requires the sender to deliberately or accidentally target the degenerate address; it is not attacker-triggerable against other users' balances.

### Recommendation
Add an explicit check rejecting the zero-payload address (20 zero bytes after the prefix byte) in `DecodeUtil.addressValid`, or add a dedicated check in `TransferActuator.validate()` and `TransferAssetActuator.validate()` (and any other actuator accepting an arbitrary `toAddress`, e.g. `AccountCreateContract`, `ParticipateAssetIssueContract`) that rejects a destination address whose 20-byte body is all zero, mirroring `require(_to != address(0))` in the reported Solidity pattern.

### Proof of Concept
1. Craft a `TransferContract` (or `TransferAssetContract`) with `toAddress` = `0x41` followed by 20 `0x00` bytes.
2. `DecodeUtil.addressValid` returns `true` for this address since it only checks length and prefix byte [1](#0-0) .
3. Broadcast the signed transaction; `TransferActuator.execute()`/`TransferAssetActuator.execute()` creates the account and credits it with the transferred value [3](#0-2) .
4. The value is now held by an account whose address has no corresponding private key, making it permanently unrecoverable.

**Note on confidence**: This is the strongest structurally-analogous, unprivileged, RPC/broadcast-transaction-reachable pattern found in the indexed codebase; I did not find any code path where java-tron itself increments a `totalSupply`-like counter while sending newly created value to an unchecked destination address (the literal "mint" analog), so this finding substitutes the closest available bug-class match — a missing zero-address check on a value-transfer path — with the caveat that it is a self-inflicted loss rather than an attacker-triggered fund theft.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
