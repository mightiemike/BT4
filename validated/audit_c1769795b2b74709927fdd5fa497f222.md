### Title
Wallet Contract `has_in_flight_tx` lock can be permanently stuck `true`, causing a transaction-triggered halt of the account - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `near-wallet-contract` (deployed as the code behind ETH-implicit accounts) uses a boolean flag `has_in_flight_tx` as a re-entrancy/ordering lock: `rlp_execute` refuses to start a new Ethereum-emulated transaction while `has_in_flight_tx == true`, and the flag is only reset back to `false` as the *first statement* of the various promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). This is structurally the same pattern as the reported Arrakis `setManager` bug: a state update meant to "unlock" a privileged/exclusive operation is bundled into the same execution unit as an external, attacker-influenceable call, and if that unit fails/panics for any reason before it commits, the unlocking write never persists, leaving the resource permanently locked.

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` and returns a `Promise` chain [1](#0-0) . The invariant documented at the top of the struct says the flag must be reset to `false` by whichever callback resolves the chain [2](#0-1) .

Each callback resets the flag as its very first statement, e.g. `nep_141_storage_balance_callback`:
```
self.has_in_flight_tx = false;
let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) { ... };
``` [3](#0-2) 

On NEAR, a function-call receipt's state mutations are only committed if the receipt's execution completes without panicking (e.g. by running out of the gas that was statically attached via `.then()`); if it panics partway through, *all* state writes made during that execution — including the earlier `self.has_in_flight_tx = false` — are rolled back together with the rest of the receipt. The gas attached to these callbacks is a small, mostly-fixed budget (`RLP_EXECUTE_CALLBACK_GAS` = 5 Tgas, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` = 5+5 Tgas + `action.gas()`) [4](#0-3) . The callback then deserializes the untrusted response of an externally-controlled contract with `serde_json::from_slice` (e.g. the `storage_balance_of` response from an attacker-supplied `token_id`/`target`) [5](#0-4) . Because `token_id`/`target` is an ordinary NEAR account chosen for the emulated ERC-20 transfer (see `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => { let token_id = target; ... }` [6](#0-5) ), an attacker can deploy a malicious contract at that account whose `storage_balance_of` view returns an oversized/expensive-to-parse payload, causing the callback receipt to exceed its small statically attached gas and panic *after* the flag-reset line was executed in-memory but *before* the receipt commits.

Because the panic reverts the whole receipt (including the flag reset), `has_in_flight_tx` remains permanently `true` in committed state. From then on every call to `rlp_execute` returns early with `"Error: transaction already in progress, please try again later."` [7](#0-6) , and there is no other method in the contract that can flip the flag back — every path that touches it does so via the same lock-first/unlock-in-callback pattern. This permanently freezes the ETH-implicit wallet account: it can never again process any Ethereum-emulated transaction (transfers, ERC-20 transfers, function calls, add/delete key), a permanent, transaction-triggered halt of that account's usable state transitions.

### Impact Explanation
This satisfies the "transaction-triggered halt"/"permanently frozen funds" criteria: an unprivileged actor (the wallet owner or, more importantly, a malicious relayer/attacker who can get any account to sign an ERC-20-style call targeting an attacker-controlled `token_id`) can, with a single crafted call, permanently disable `rlp_execute` for a given ETH-implicit account. Since all normal fund movement and key management for that wallet flows exclusively through `rlp_execute`, the account's assets and access-key management become effectively frozen — there is no recovery method that resets `has_in_flight_tx` without going through the same vulnerable callback path.

### Likelihood Explanation
Reaching this requires: (1) a wallet owner or relayer submitting an RLP transaction that emulates an ERC-20 transfer whose `target`/`token_id` is an attacker-controlled account, and (2) that malicious contract returning a `storage_balance_of` payload sized to exceed the fixed gas budget of `nep_141_storage_balance_callback` (and/or similar overflow in `address_check_callback`'s registrar-response deserialization). Both are fully within the control of a party that can influence which `target` is used and what a "token" contract at that account returns; deploying a contract and choosing a large-enough response is straightforward and requires no privileged access. Because the wallet contract is a "temporary/placeholder implementation" per its own README [8](#0-7) , it is explicitly flagged as not production-ready, which somewhat tempers the severity classification, but the underlying flaw is a legitimate protocol/runtime-reachable state-lock DOS analogous to the reported bug class.

### Recommendation
- Do not rely on state written earlier in the same fallible execution to represent "operation complete." Reset `has_in_flight_tx` in a receipt that is guaranteed to commit regardless of any subsequent gas/parsing failure — e.g., split the untrusted-response handling into its own sub-call so a parse failure in that sub-call cannot roll back the flag reset, or reset the flag via a dedicated, minimal, panic-free final step scheduled after (not interleaved with) any parsing of attacker-controlled data.
- Bound/limit the size of external responses parsed (`storage_balance_of`, registrar `lookup`) before calling `serde_json::from_slice`, and attach sufficient/worst-case gas headroom for that deserialization independent of `action.gas()`.
- Add a recovery path (e.g., a time-locked or owner-only method) that can force-clear `has_in_flight_tx` if a chain of promises has definitively resolved but the flag was never reset, to bound the worst-case impact.

### Proof of Concept
1. Attacker deploys a NEAR contract at account `evil-token.near` implementing a `storage_balance_of` view method that returns an oversized JSON blob (e.g., several hundred KB of nested values) instead of the expected small `StorageBalance` object.
2. Attacker (as wallet owner, or via a relayer who is allowed to pick `target`) submits an RLP-encoded ERC-20-transfer-shaped Ethereum transaction through `rlp_execute` with `target = evil-token.near`.
3. `inner_rlp_execute` classifies it as `EthEmulationKind::ERC20Transfer`, sets `token_id = target`, sets `has_in_flight_tx = true`, and schedules `storage_balance_of` → `nep_141_storage_balance_callback` with a small static gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) [6](#0-5) .
4. `evil-token.near::storage_balance_of` returns its oversized payload; the callback receipt executes `self.has_in_flight_tx = false;` then attempts `serde_json::from_slice(&value)` on the oversized payload, exhausting the remaining prepaid gas and panicking.
5. Because the receipt panicked, the entire state diff for that receipt (including the flag reset in step 4) is discarded on commit; the persisted `has_in_flight_tx` remains `true`.
6. Any subsequent call to `rlp_execute` for this wallet immediately returns `"Error: transaction already in progress, please try again later."` [7](#0-6) , permanently, since no other method can reset the flag.

Note: I was unable to execute this scenario against a live/test runtime within this investigation (no sandbox access), so gas-budget exhaustion at exactly the right point and the exact commit/rollback semantics for a mid-function panic should be confirmed with a concrete integration test (e.g., in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/`) before treating this as fully proven.
