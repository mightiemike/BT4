### Title
Replay-verify accepts a divergent authenticated state/position checkpoint root as valid - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`, plus `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`) to check that a locally re-executed transaction output matches the `TransactionInfo` that was actually committed to the ledger accumulator. The function validates status, gas, write-set hash, and event-root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that authenticate the Merkle/JMT/native-position state roots bound into `TransactionInfoV1`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` computes and asserts equality only for `status`, `gas_used`, `write_set_hash` (vs `state_change_hash`), and `event_root_hash`: [2](#0-1) 

It never recomputes or compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against locally derived roots — these fields exist on `TransactionInfoV1` (and `state_checkpoint_hash` on `TransactionInfoV0`) as the actual authenticated commitments to global/hot/position state: [3](#0-2) 

The code's own comment acknowledges the gap and states it must be fixed before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled: [1](#0-0) 

`replay_on_archive.rs`'s `execute_and_verify` treats a clean return from `ensure_match_transaction_info` as proof that the chunk replayed correctly, and only rewinds/reports failure when it returns `Err`: [4](#0-3) 

Because the state/hot-state/position-state checkpoint hashes are the fields that bind a `TransactionInfo` (an accumulator leaf) to the actual JMT/hot-state/native-position Merkle roots (see `do_ledger_update.rs`'s `assemble_transaction_infos`, which populates exactly these fields from computed roots), a divergence there means the locally computed state root differs from what is durably committed and covered by consensus signatures — yet the verification tool reports success. [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the "authenticated API / proof-bearing responses must stay bound to the right ledger version, root, and object" invariant for the replay/verify path: a node or auditor running `replay-on-archive` (or `aptos-debugger`) can silently accept a chain segment whose *recomputed* state root, hot-state root, or native-position state root differs from the one actually anchored in the accumulator/`LedgerInfo`, as long as write-set bytes, event bytes, gas, and status happen to match. This can mask:
- Storage bugs where the committed JMT/hot-state/position-state root diverges from the true VM-derived state (a corrupted or non-canonical state tree persisted on some nodes),
- Hard-fork-only state divergence between execution and storage/restore paths that only manifests in the checkpoint-hash fields,
without being caught, defeating the primary safety purpose of replay-verify tooling used to detect exactly this class of consensus/state divergence bugs. This directly matches the state-integrity gate's "Wrong accumulator root ... or state proof accepted as valid" and "Hard-fork-only divergence during commit, replay ... verification" categories.

The severity is bounded by the fact that this is a verification-tooling gap rather than a live consensus/execution bug — it does not itself corrupt state, but it removes the safety net that would otherwise detect corrupted state or root divergence, which is high-impact given it undermines the state-integrity guarantee the tool is meant to provide for auditors and node operators relying on `replay_on_archive` before trusting archive data.

### Likelihood Explanation
The gap is unconditional whenever `ensure_match_transaction_info` is invoked (every `replay_on_archive` run, and other callers), and is explicitly acknowledged in-code as a known omission that only becomes acute once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`/`TRANSACTION_INFO_V1` are enabled on-chain — features already wired through `BlockExecutorConfigFromOnchain` and feature flags in this codebase. No attacker action is required to trigger the blind spot; it manifests automatically the moment any divergence occurs in checkpoint-hash computation between execution and what was persisted.

### Recommendation
In `ensure_match_transaction_info`, recompute the local state checkpoint hash (and, when applicable, hot-state and position-state checkpoint hashes) at checkpoint boundaries and compare them against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, failing loudly (as the other checks do) on mismatch. This should be wired in before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled in production, per the existing TODO.

### Proof of Concept
Conceptual PoC (cannot be executed without a live DB, but demonstrated purely from local code paths):
1. Persist a `TransactionInfoV1` (or `V0`) at some version whose `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) does not match the actual JMT/hot-state/native-position root that would be recomputed from the same write set (e.g., due to a bug/corruption in `DoStateCheckpoint::run`/`compute_position_checkpoint`, see `execution/executor/src/workflow/do_state_checkpoint.rs:36-84,90-190`), while keeping `write_set`, `events`, `gas_used`, and `status` unchanged.
2. Run `storage/db-tool/src/replay_on_archive.rs`'s replay-verify over that version range.
3. `execute_and_verify` calls `ensure_match_transaction_info` per transaction (`storage/db-tool/src/replay_on_archive.rs:392-405`); since only write-set hash/event-root/gas/status are checked, the call returns `Ok(())` despite the state/hot-state/position-state checkpoint hash mismatch, and the tool reports the chunk as successfully verified.     pub fn ensure_match_transaction_info(
```rust
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
```
