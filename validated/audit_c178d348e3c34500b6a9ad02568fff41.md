## Title
Legacy `ExchangeProcessor` uses unchecked `double` power arithmetic that can silently overflow/produce corrupted exchange results when `AllowHardenExchangeCalculation` is disabled - (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The reported PRBMath bug class is: an unchecked fixed-point math routine (`exp()`) silently overflows on extreme inputs, producing wrong results (or reverting) instead of safely saturating, corrupting the protocol's pricing/computation flow. Java-tron's on-chain bonding-curve/Bancor-relay `Exchange*` actuators (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) contain an analogous unchecked-math code path: the legacy `ExchangeProcessor` [1](#0-0)  performs the bonding-curve calculation using raw IEEE-754 `double` arithmetic and `Maths.pow`, with no bounds/NaN/Infinity checks before truncating to `long`.

### Finding Description
`ExchangeCapsule.transaction()` selects between the hardened `SafeExchangeProcessor` (BigDecimal-based, exact) and the legacy `ExchangeProcessor` (double-based) depending on the `hardenedCalc` flag, which is derived from the `allowHardenExchangeCalculation` dynamic property [2](#0-1)  and [3](#0-2) . When this chain parameter is not enabled (its default/legacy state), every `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` broadcast by any account routes through `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, computing `Maths.pow(1.0 + quant/newBalance, exponent, useStrictMath)` in `double` and casting the result to `long` with no overflow, NaN, or Infinity guard [1](#0-0) .

This mirrors the PRBMath issue structurally: a math primitive used for pricing that has an unchecked failure mode for extreme (but reachable) inputs, silently corrupting results rather than safely bounding them. In `ExchangeProcessor`, extreme ratios of `quant`/`newBalance` (e.g., very large `tokenQuant` relative to a small pool balance, which the validators only bound by a configurable `ExchangeBalanceLimit`, not by ratio) can drive `Maths.pow` toward `Infinity`/`NaN`. Casting `Infinity` to `long` in Java yields `Long.MAX_VALUE`, and casting `NaN` yields `0`; both are silent, non-reverting corruptions of the computed relay/output quantity that feed directly into `exchangeCapsule.setBalance(...)` and account asset/balance mutations in `ExchangeInjectActuator.execute` and `ExchangeWithdrawActuator.execute` and `ExchangeTransactionActuator.execute` [4](#0-3) .

The project itself acknowledges the double-arithmetic path is unsafe: `SafeExchangeProcessor` was introduced specifically to replace it with `BigDecimal`/`longValueExact()` arithmetic that throws `ArithmeticException` on overflow instead of silently wrapping [5](#0-4) , and dedicated tests confirm the legacy processor's divergence from the hardened one on the same inputs [6](#0-5) .

### Impact Explanation
If `allowHardenExchangeCalculation` is not active on a given chain/fork state, an attacker able to create or interact with an `Exchange` (TRX/TRC10 bonding curve pair) could attempt to drive the pow computation into an extreme regime (very small pool reserve combined with a large `quant`) to obtain a corrupted `anotherTokenQuant`/relay amount — potentially `Long.MAX_VALUE` from an `Infinity` truncation, or `0` from `NaN`, either of which can misallocate assets/TRX between the exchange pool and the user account, corrupting AMM accounting (asset or accounting corruption).

### Likelihood Explanation
Likelihood is moderate-to-low: `SafeExchangeProcessor`/the hardening flag exists specifically to close this failure mode, suggesting the maintainers are aware of it and intend it to be default-on eventually; whether it is active on the target deployment/chain determines exploitability. It also requires an exchange pool with an attacker-influenceable extreme reserve ratio (achievable since exchange pools are user-created via `ExchangeCreateContract` and reserves can be manipulated by legitimate inject/withdraw operations), analogous to the original finding's note that "liquidation pair creator" control over parameters makes the extreme-input precondition reachable.

### Recommendation
Ensure `allowHardenExchangeCalculation` is permanently enabled (make `SafeExchangeProcessor` the only code path) rather than an optional/legacy toggle, and add explicit bounds checks in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` to reject or safely saturate on `Double.isNaN`/`Double.isInfinite` results before casting to `long`, matching the recommended PRBMath mitigation of clamping unchecked math to a safe bound instead of allowing silent overflow.

### Proof of Concept
Conceptual (not executed): Create an `Exchange` with a very small `secondTokenBalance`/`firstTokenBalance` (e.g., near-zero reserve) via legitimate `ExchangeCreateContract`/`ExchangeWithdrawContract` calls until reserves are minimal, then submit `ExchangeTransactionContract` with a large `tokenQuant` while `allowHardenExchangeCalculation` is disabled. This routes to `ExchangeProcessor.exchange` → `exchangeToSupply`/`exchangeFromSupply` [7](#0-6) , where the extreme ratio can push `Maths.pow` results toward `Infinity`/`NaN`, and the `(long) issuedSupply`/`(long) exchangeBalance` casts silently truncate to `Long.MAX_VALUE`/`0` rather than throwing, unlike the hardened path in `SafeExchangeProcessor` which would throw `ArithmeticException` via `longValueExact()` [8](#0-7) . Full confirmation of an exploitable extreme-input case (exact reserve/quant values producing `Infinity`/`NaN`) would require running the arithmetic, which was not verified numerically in this analysis.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
