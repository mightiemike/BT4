Based on the investigation, java-tron's built-in Bancor-style TRX/TRC10 exchange (`Exchange*Actuator` family) is the closest on-chain analog to this bug class: it computes swap output entirely from mutable on-chain pool reserves at execution time, exposed to unprivileged users, and is susceptible to the same front-running/sandwich price-manipulation pattern described in the Curve report.

### Title
On-chain Bancor-relay pool price in `ExchangeTransactionActuator` is manipulable via front-running/sandwiching the swap - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The TRON built-in decentralized exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) computes swap output purely from the pool's current on-chain reserve balances (`firstTokenBalance`/`secondTokenBalance`), exactly like the Curve `calc_withdraw_one_coin` spot-price calculation flagged in the report. Because this price is derived on-chain from state that any account can shift immediately beforehand (via an `ExchangeTransactionContract` swap of their own), an attacker can front-run a pending victim swap, distort the reserve ratio, let the victim's transaction execute at the manipulated price, then reverse the position — a classic sandwich attack against a same-block, state-derived price, with no external price reference.

### Finding Description
`ExchangeTransactionActuator.execute()`/`doValidate()` compute the output amount by calling `exchangeCapsule.transaction(tokenID, tokenQuant, ...)`, which invokes `ExchangeProcessor.exchange()` (or `SafeExchangeProcessor.exchange()`), a Bancor relay-style bonding-curve formula operating solely on the pool's current `firstTokenBalance`/`secondTokenBalance` fields: [1](#0-0) 

The formula itself: [2](#0-1) 

`doValidate()` in `ExchangeTransactionActuator` re-derives the same on-chain price at the moment of validation/execution and only checks it against a caller-supplied minimum (`tokenExpected`), which protects the caller from getting *less* than their own quoted minimum, but does nothing to stop an attacker from profiting by shifting the pool ratio immediately before the victim's transaction is applied and reversing it immediately after (sandwiching): [3](#0-2) 

This mirrors the reported Curve issue precisely: the withdrawal/swap "price" is a spot-price-style function of manipulable on-chain reserves (`calc_withdraw_one_coin` vs `ExchangeCapsule.transaction`/`ExchangeProcessor.exchange`), computed at execution time with no off-chain computed amount, no TWAP, and no external oracle. Any account can call `ExchangeInjectContract`... wait, `ExchangeInjectContract`/`ExchangeWithdrawContract` are restricted to the exchange creator, but `ExchangeTransactionContract` swaps are open to any unprivileged account, so an attacker can shift `firstTokenBalance`/`secondTokenBalance` with their own ordinary swap transaction to sandwich a victim's swap, exactly as in the Curve report where an attacker submits a manipulating transaction to the same pool that the victim's price calculation depends on.

### Impact Explanation
An attacker observing a pending, sizeable `ExchangeTransactionContract` can:
1. Submit a swap in the same direction as the victim just before it is applied, pushing the reserve ratio (and thus the bonding-curve exchange rate) unfavorably for the victim.
2. Let the victim's swap execute at the now-worse rate (still passing their `tokenExpected` check if it is loose, which is common).
3. Submit a reverse swap immediately after to restore the ratio and capture the spread — extracting value from the victim and the pool's liquidity providers (the exchange creator), i.e., concrete underpriced/mispriced settlement impact on real TRX/TRC10 balances moved through `AccountCapsule` balance and asset updates.

### Likelihood Explanation
This requires only unprivileged, ordinary `ExchangeTransactionContract` calls — no special role, no contract bug beyond relying on manipulable on-chain reserves for pricing, and transaction ordering within a block (broadcast timing / SR packing order) is not guaranteed to be manipulation-resistant. The attack is limited to `Exchange` pools with practical liquidity and does not require the victim to make an error beyond using a slippage tolerance wider than the manipulation window, which is a common real-world configuration (as in most AMM sandwich attacks).

### Recommendation
- Do not rely purely on the instantaneous on-chain reserve ratio for swap pricing; consider adding a maximum allowed price-impact-per-transaction or a minimum block-delay/TWAP-based price check for large trades in `ExchangeCapsule.transaction()`.
- Encourage/require callers of `ExchangeTransactionContract` to set tight, mandatory slippage bounds (`tokenExpected`) rather than treating it as an optional check just above zero, and consider adding a maximum-price-impact validation in `ExchangeTransactionActuator.doValidate()`.
- Consider deprecating or clearly documenting the built-in Exchange as unsuitable for high-value swaps given this inherent, non-oracle, spot-price design, consistent with the auditor's recommendation to avoid on-chain-only manipulable pricing.

### Proof of Concept
1. Attacker monitors the mempool/pending pool for a large `ExchangeTransactionContract` swapping token A → B against exchange `X` with a loose `tokenExpected`.
2. Attacker submits `ExchangeTransactionContract` (A → B) that gets included immediately before the victim's transaction, shrinking `secondTokenBalance` relative to `firstTokenBalance` via `ExchangeCapsule.transaction()` at `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:124-169`.
3. Victim's transaction executes via `ExchangeTransactionActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:38-107`), receiving fewer tokens than they would have absent manipulation, but still passing the `tokenExpected` check at line 219 because the tolerance was set loosely.
4. Attacker submits a reverse `ExchangeTransactionContract` (B → A) immediately after, restoring the ratio and pocketing the price difference extracted from the victim/pool.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {

  }
