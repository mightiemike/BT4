### Title
`TokenConfig.Enabled` (registry token allowlist flag) is never checked during inbound execution / minting - ([File: x/uexecutor/keeper/execute_inbound_gas.go], [File: x/uexecutor/keeper/execute_inbound_gas_and_payload.go], [File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go], [File: x/uregistry/keeper/keeper.go])

### Summary
`x/uregistry.TokenConfig` defines an `enabled` field described as "Whether this token is enabled for minting/bridging" [1](#0-0) , mirroring HiFi's `Fintroller.isRedeemHTokenAllowed` gate. However, none of the inbound execution paths that call `uregistryKeeper.GetTokenConfig` (`ExecuteInboundGas`, `ExecuteInboundGasAndPayload`, `ExecuteInboundFundsAndPayload`) ever inspect `tokenConfig.Enabled` before minting/depositing the corresponding PRC20 into a user's UEA.

### Finding Description
`GetTokenConfig` in `x/uregistry/keeper/keeper.go` is a plain lookup that returns the stored `TokenConfig` without any gating on the `Enabled` field [2](#0-1) . All three inbound-execution keeper functions call this lookup and immediately proceed to use `tokenConfig.NativeRepresentation.ContractAddress` to mint/deposit PRC20 tokens, with no check of `tokenConfig.Enabled` anywhere in the flow:

- `ExecuteInboundGas` fetches the token config and, on success, proceeds straight to computing a swap quote and calling `CallPRC20DepositAutoSwap` [3](#0-2) .
- `ExecuteInboundGasAndPayload` fetches the token config and proceeds to `gasAndPayloadDepositAutoSwap` [4](#0-3) .
- `ExecuteInboundFundsAndPayload` calls `depositPRC20` directly using `utx.InboundTx.AssetAddr` without re-checking `Enabled` [5](#0-4) .

I could not find any check of `tokenConfig.Enabled` (or `.GetEnabled()`) anywhere in the repository outside of test fixtures and proto/pb generated getters — a grep for `tokenConfig.Enabled`, `TokenConfig.Enabled`, and `.GetEnabled()` returned zero matches in production code. Likewise, `Inbound.ValidateForExecution()` — the pre-execution validation gate called from `VoteInbound` — validates amount, asset address non-emptiness, payload shape, and recipient, but never consults the registry's `TokenConfig.Enabled` flag [6](#0-5) .

By contrast, the `ChainConfig.Enabled` (`IsInboundEnabled`/`IsOutboundEnabled`) analog IS properly enforced — `VoteInbound` and `ExecutePayload` both check `IsChainInboundEnabled` before proceeding [7](#0-6) , as confirmed by dedicated integration tests [8](#0-7) . This asymmetry — chain-level enable flag enforced, token-level enable flag silently ignored — is the direct structural analog of the HiFi bug, where one Fintroller-style boolean gate (`isRedeemHTokenAllowed`) existed in the registry contract but was never consulted by the execution function that it was meant to gate.

### Impact Explanation
If an admin disables a `TokenConfig` (sets `Enabled = false`) — e.g., to pause a compromised, depegged, or deprecated asset from being bridged — an unprivileged external attacker can still submit inbound observations (via honest Universal Validators voting on a real, attacker-triggered source-chain event) referencing that disabled `asset_addr`. Because `Enabled` is never checked, `GetTokenConfig` still succeeds (the row still exists), and the keeper proceeds to mint/deposit the disabled token's PRC20 representation into the recipient's UEA — a form of unauthorized mint / bypass of protocol-controlled asset admission, directly analogous to unauthorized redemption in the HiFi report. This could let a user route funds through a token the protocol operators explicitly disabled (e.g., because it was compromised or over its liquidity cap enforcement should have blocked further inflow), corrupting PRC20 accounting invariants that the registry is supposed to protect.

### Likelihood Explanation
High reachability: `Enabled` requires no special conditions — it is a boolean the admin toggles via `MsgUpdateTokenConfig`, and once toggled off, the config row is not removed (`RemoveTokenConfig` is a separate message). Any inbound event on an already-configured (but disabled) `(chain, asset_addr)` pair, submitted by an ordinary user and honestly relayed by the Universal Validators, will pass `GetTokenConfig` and get executed. No privileged action or malicious validator/relayer behavior is required on the attacker's part — only that an admin has disabled a previously-enabled token, a realistic operational scenario (asset deprecation/incident response).

### Recommendation
Add an explicit `tokenConfig.Enabled` check in each inbound execution path immediately after `GetTokenConfig` succeeds (in `ExecuteInboundGas`, `ExecuteInboundGasAndPayload`, and `ExecuteInboundFundsAndPayload`), and/or centralize this in `Inbound.ValidateForExecution` (or an earlier validation step) so that a disabled token config causes a FAILED PCTx + revert path identical to the missing-token-config case, rather than proceeding to mint/deposit.

### Proof of Concept
1. Admin adds `TokenConfig{Chain: "eip155:11155111", Address: <asset>, Enabled: true, NativeRepresentation: {ContractAddress: prc20Addr}}`.
2. Admin later disables it via `MsgUpdateTokenConfig` setting `Enabled: false` (e.g., in response to an incident) but does not remove the config row.
3. Attacker triggers a real deposit event on the source chain for `asset`. Universal Validators honestly observe and vote `MsgVoteInbound` for a `FUNDS`/`FUNDS_AND_PAYLOAD` inbound referencing that `asset_addr`.
4. `VoteInbound` → `ValidateForExecution` passes (no `Enabled` check exists) → `ExecuteInbound` → `ExecuteInboundFundsAndPayload`/`ExecuteInboundGas` calls `GetTokenConfig`, which returns the disabled config successfully → `depositPRC20`/`CallPRC20DepositAutoSwap` is invoked, minting/crediting the disabled asset's PRC20 into the recipient's UEA despite `Enabled == false`.

(Note: I verified via grep that no production code path checks `TokenConfig.Enabled`; this is based on static analysis of the indexed code and I was unable to execute the test suite to dynamically confirm the runtime behavior. If a check exists elsewhere not captured by the index due to size limits, that would need to be verified in a full checkout.)

func (k Keeper) GetChainConfig(ctx context.Context, chain string) (types.ChainConfig, error) {
	config, err := k.ChainConfigs.Get(ctx, chain)
	if err != nil {
		return types.ChainConfig{}, err
	}
	return config, nil
}

// IsChainInboundEnabled checks if inbound is enabled for a given chain
func (k Keeper) IsChainInboundEnabled(ctx context.Context, chain string) (bool, error) {
	config, err := k.GetChainConfig(ctx, chain)
	if err != nil {
		if errors.Is(err, collections.ErrNotFound) {
			// chain not found
			return false, nil
		}
		return false, err
	}
	if config.Enabled == nil {
		return false, nil
	}
	return config.Enabled.IsInboundEnabled, nil
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}
