### Title
Default (non-hardened) exchange math path allows silent negative-balance accounting corruption in the Bancor-style TRC10 exchange pool - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The java-tron TRC10 `Exchange` feature (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) is the closest on-chain analog to the 0x order-filling math described in the report: a Bancor-style relay-token calculation determines how much of `anotherTokenID` a user receives when trading `tokenID`. Exactly like the reported issue — where a caller cannot know in advance whether a "fillable" order will actually succeed because the underlying math can silently misbehave — java-tron's exchange math has two code paths with different guarantees, and the **default path silently accepts results that the hardened path explicitly rejects**, meaning the state-changing (`ExchangeTransactionContract`) transaction can corrupt exchange-pool accounting instead of reverting.

### Finding Description
`ExchangeCapsule.transaction()` dispatches to one of two processors depending on the `allowHarden` (i.e. `allowHardenExchangeCalculation()`) chain parameter: [1](#0-0) 

- When `hardenedCalc` is `false` (the default, unless committee/SR proposal 22-style parameter has been voted to enable it), it uses `new ExchangeProcessor(supply, useStrictMath)`, which performs the Bancor "issued supply" calculation using raw `double` arithmetic and truncating casts (`(long) issuedSupply`), with **no overflow or sanity check**: [2](#0-1) 

- When `hardenedCalc` is `true`, it uses `SafeExchangeProcessor`, which performs the same Bancor formula with `BigDecimal`/`StrictMathWrapper` and explicit `ArithmeticException` on overflow/div-by-zero: [3](#0-2) 

Critically, the resulting new pool balances are **only validated for negativity when `hardenedCalc` is true**: [4](#0-3) 

In the default (non-hardened) path, `newFirstTokenBalance`/`newSecondTokenBalance` can become negative or otherwise wrong due to floating-point rounding, yet the code proceeds to persist them via `Commons.putExchangeCapsule(...)` in `ExchangeTransactionActuator.execute()`: [5](#0-4) 

This mirrors the report's core complaint (unclear, undocumented failure boundary in order-fill math) but is more severe on java-tron: instead of reverting like 0x's `RoundingError`, the default computation path has **no failure signal at all** — it just returns a `long` that may not reflect a real, solvent state. The actuator then unconditionally credits `anotherTokenQuant` to the taker's real TRC10/TRX balance via `addAssetAmountV2`/`setBalance`, while the pool's virtual balances (`ExchangeCapsule.firstTokenBalance`/`secondTokenBalance`) are the *only* accounting record backing the pool — there is no separate escrow account whose real balance is checked against the virtual pool numbers.

`doValidate()` in `ExchangeTransactionActuator` also calls `exchangeCapsule.transaction(...)` purely to compute `anotherTokenQuant` for the `tokenExpected` check, duplicating the exact same unguarded calculation that `execute()` performs, so both entry points inherit the same unreverted-miscalculation risk: [6](#0-5) 

### Impact Explanation
If the non-hardened Bancor calculation (the default unless a chain governance parameter has explicitly turned on hardening) produces a result that makes one side of the pool's virtual balance negative or otherwise inconsistent with real backing, an attacker submitting an ordinary `ExchangeTransactionContract` transaction can withdraw more of a token than the pool's real economic backing, since the credited amount comes directly from `AccountCapsule.addAssetAmountV2`/`setBalance` calls that are independent of any actual escrowed balance check. This is an accounting-corruption / fund drainage risk in the exchange/market math category, reachable from any anonymous broadcast transaction (`ExchangeTransactionContract`), not from a privileged actor.

### Likelihood Explanation
Reachability is trivial — any account can create an exchange (`ExchangeCreateActuator`), inject liquidity, and then send crafted `ExchangeTransactionContract` transactions repeatedly with quantities chosen to maximize floating-point rounding drift near pool-balance boundaries (e.g., very small or very large relative quant vs. balance, as in the original report's 20-token partial-fill example). Because the non-hardened processor is the historical default and the hardened path is opt-in via a `allowHardenExchangeCalculation` chain parameter, most exchanges created before that parameter is enabled remain exposed. Exploitation requires no elevated privileges, only ordinary TRC10 token balances to interact with the exchange.

### Recommendation
- Apply the same non-negative-balance / overflow validation performed in the hardened (`SafeExchangeProcessor`) path unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, and reject the transaction (`ContractValidateException`/revert) rather than silently persisting a negative or overflowed balance.
- Document explicitly, in the protocol specification, the precise conditions (rounding, pool depletion, balance limits) under which `exchangeTransaction`/`exchangeInject`/`exchangeWithdraw` can fail, similar to the recommendation in the source report to formally define "fillable" and test exhaustively (e.g., via property-based/fuzz testing) that the default path can never produce a negative or overflowed pool balance for any valid, non-adversarial input.
- Consider deprecating/removing the non-hardened `ExchangeProcessor` double-based path entirely in favor of the `BigDecimal`-based hardened path as the sole implementation.

### Proof of Concept
Conceptual reproduction path (concrete numeric PoC would require running the actual double-precision `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` against pool sizes/quant ratios chosen to trigger floating-point rounding beyond the pool's real balance, analogous to the report's Alice scenario):
1. Create an exchange pool with `ExchangeCreateContract` (`firstTokenBalance`, `secondTokenBalance` near governance-configured `EXCHANGE_BALANCE_LIMIT`).
2. Ensure `allowHardenExchangeCalculation` is not enabled (default off) so `ExchangeCapsule.transaction()` uses the unguarded `ExchangeProcessor` double-math path.
3. Submit a sequence of `ExchangeTransactionContract` transactions with quantities selected (via off-chain simulation of `ExchangeProcessor.exchange`) to drive `newFirstTokenBalance`/`newSecondTokenBalance` negative through rounding, since the non-hardened path in `ExchangeCapsule.transaction()` performs no negativity check before calling `Commons.putExchangeCapsule(...)`.
4. Observe that the transaction succeeds (`code.SUCESS`) and the taker's real asset/TRX balance is credited via `addAssetAmountV2`/`setBalance`, while the exchange pool's persisted virtual balance is inconsistent (negative or unbacked), corrupting the exchange's on-chain accounting.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
