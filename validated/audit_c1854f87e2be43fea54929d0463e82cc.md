### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant session hijacking - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`shopify.webhooks.validate` (and the `authenticate.webhook` / `processWebhooks` handlers built on top of it in `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express`) authenticates a webhook request solely by checking that `X-Shopify-Hmac-Sha256` matches an HMAC of `rawBody`. The shop domain, topic, API version, and webhook ID are read straight from HTTP headers and returned as trusted output without being part of the signed data.

### Finding Description
`validateHmacFromRequestFactory` computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it against the `X-Shopify-Hmac-Sha256` header value: [1](#0-0) 

Only `rawBody` is protected. After the HMAC check succeeds, `checkWebhooksHeaders`/`checkEventsHeaders` pull `domain`, `topic`, `apiVersion`, and `webhookId` from headers and mark the whole payload `valid: true` without any cross-check that these headers were also signed: [2](#0-1) 

Downstream, `authenticateWebhookFactory` (in both `shopify-app-remix` and `shopify-app-react-router`) trusts `check.domain` unconditionally to load the shop's offline session and build an authenticated Admin/Storefront API client: [3](#0-2) 

Because `domain` is not covered by the signature, an attacker who is a legitimate merchant/installer of the app can capture one authentic `(rawBody, hmac)` pair generated by Shopify for a real event on their own store, then replay that exact `rawBody`/`hmac` to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. The HMAC still validates (it never inspected the domain), so the request is accepted as `valid: true` with `check.domain` set to the victim's shop. The webhook handler then loads the victim's offline `Session` via `ensureValidOfflineSession(params, check.domain)` and hands the attacker-triggered payload to app code running with the victim shop's admin/storefront credentials — an unprivileged actor (any installer of the app) can trigger app logic bound to another tenant's session using data they fully control by replaying their own legitimately-signed body.

This mirrors the audited bug class: an access-control check (`onlyAllowedModule` / HMAC validation) is satisfiable by data the attacker can freely manufacture (an arbitrary Oracle request / an unsigned header), letting them redirect the effect of the check onto a victim of their choosing.

### Impact Explanation
Any single installer of a vulnerable app can, through header manipulation on a raw HTTP POST to the app's webhook endpoint, cause the app to execute webhook-processing logic (which typically writes to the database, calls the Admin API, or triggers business logic) using another merchant's offline access token and session data. Depending on what the app's webhook handlers do with `session`/`admin` (e.g., updating billing, creating resources, reading/writing shop-configuration), this is a cross-tenant confidentiality/integrity break, and in apps that key security decisions off `shop`/`topic`/`webhookId` (e.g., idempotency, entitlement checks) it can also cause corrupted or duplicated app-side state for the victim tenant.

### Likelihood Explanation
Exploitation requires: (1) the attacker installs the target app on at least one shop they control (a standard, unprivileged action for any Shopify merchant/developer), (2) the attacker triggers any webhook topic that is subscribed by the target app on their own shop (e.g., `app/uninstalled`), capturing the real `rawBody` + `X-Shopify-Hmac-Sha256` pair, and (3) the attacker replays that exact body with a forged domain header pointed at a known victim shop that also has the app installed. No secret key or Shopify-side credential is needed — everything used to forge the header is visible to the attacker on their own webhook deliveries. This is a straightforward, repeatable, purely network-level attack against any app relying on this shared `webhooks.validate` implementation.

### Recommendation
- **Short term:** Include the shop domain (and ideally topic/webhook ID) in the HMAC-signed material, or independently verify `X-Shopify-Shop-Domain` against a value cryptographically bound to the request (e.g., compare it to the `dest`/`iss` claim of a session token when available, or require that the loaded session's `shop` match an out-of-band verified identifier). At minimum, document that `check.domain` from `shopify.webhooks.validate` must not be trusted as tenant-scoping input without additional verification.
- **Long term:** Redesign webhook authentication so that every field consumed by the caller (`domain`, `topic`, `apiVersion`, `webhookId`) is part of the signed payload, eliminating any header that can be independently manipulated after a valid signature has been obtained for different content.

### Proof of Concept
1. Install a target Shopify app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g., uninstall the app) so Shopify sends a POST to the app's webhook endpoint with a real `rawBody` and a correctly computed `X-Shopify-Hmac-Sha256` header.
3. Intercept/replay this exact `rawBody` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but change `X-Shopify-Shop-Domain` (and, for `events` webhooks, `shopify-shop-domain`) to `victim.myshopify.com`, a shop that also has the app installed.
4. `shopify.webhooks.validate` returns `{valid: true, domain: 'victim.myshopify.com', ...}` because `validateHmacFromRequestFactory` only checked `rawBody` against the HMAC (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:189-197`), and `checkWebhooksHeaders` echoes back the attacker-controlled `domain` header unchecked (`packages/apps/shopify-api/lib/webhooks/validate.ts:99-146`).
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim.myshopify.com')` and constructs an `admin` client using the victim's stored access token, then invokes the app's webhook handler with the attacker's payload as if it originated from the victim shop (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:35-96`).

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
