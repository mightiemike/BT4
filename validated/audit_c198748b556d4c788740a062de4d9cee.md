### Title
Legacy floating-point bonding-curve formula in `ExchangeProcessor` causes token-amount precision loss/divergence, gated behind an opt-in hardened flag - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator` (TRX/token bancor-style exchange) computes the amount of tokens a user receives via `ExchangeCapsule.transaction()`, which by default uses the legacy `ExchangeProcessor` implementing the swap with `double`/`Math.pow` floating-point arithmetic instead of exact integer/BigDecimal math. [1](#0-0) [2](#0-1) 

### Finding Description
`ExchangeProcessor.exchangeToSupply` / `exchangeFromSupply` compute the bancor-relay/token amounts using `double` arithmetic and `Math.pow`, then truncate with a plain `(long)` cast: [3](#0-2) 
This is precisely the bug class from the external report: an unnecessarily complex chained formula (division, `pow`, subtraction, multiplication) computed in floating point instead of exact arithmetic, causing loss of precision and result divergence depending on which math path is taken. The codebase itself acknowledges this: a `SafeExchangeProcessor` was added that redoes the same swap with `BigDecimal` at 18-digit scale to avoid precision loss, and is proven to produce different (and presumably "correct"/exact) results than the legacy processor: [4](#0-3) 
The regression test `testStrictMath` in `ExchangeProcessorTest.java` explicitly asserts `anotherTokenQuant` (legacy, `useStrictMath=false`) is `NOT` equal to the strict/hardened result, while the hardened `ExchangeProcessor` and `SafeExchangeProcessor` results are equal to each other: [5](#0-4) 
The choice between legacy and hardened math is controlled by a dynamic-property/committee-gated flag (`allowHardenExchangeCalculation` / `useStrictMath`), meaning the legacy imprecise path is the default unless a governance proposal enables the safer mode. `ExchangeCapsule.transaction()` selects `ExchangeProcessor` (legacy, double math) unless `hardenedCalc` is explicitly requested: [6](#0-5) 

### Impact Explanation
Any unprivileged user calling `ExchangeTransactionContract` on a TRX/TRC-10 bancor-exchange pool computes `buyTokenQuant` via this floating-point path, so the credited/debited token amount can diverge from the mathematically exact amount by rounding/precision error inherent to `double` and non-associative floating point operations (`pow`, division, subtraction chained together). This is a settlement/accounting-correctness issue affecting on-chain balances (`ExchangeCapsule` pool balances and `AccountCapsule` asset/TRX balances), not merely a theoretical rounding nit — the project's own test suite demonstrates the legacy and hardened calculations diverge for real inputs, confirming systematic non-exactness rather than negligible float noise.

### Likelihood Explanation
High reachability: any account can submit `ExchangeTransactionContract` transactions against any existing bancor-style Exchange without any privileged role, and the default configuration path uses the imprecise `ExchangeProcessor` unless the network has separately activated `allowHardenExchangeCalculation` via committee proposal. Because the imprecise legacy processor remains the default/fallback path, repeated small trades or crafted balance ratios can reliably trigger precision drift, and the divergence is deterministically reproducible per the project's own comparison tests.

### Recommendation
Make the `SafeExchangeProcessor` (BigDecimal-based, exact-scale) path the sole/default implementation for `ExchangeCapsule.transaction()` rather than gating it behind an opt-in dynamic property, removing the legacy `double`/`Math.pow` computation in `ExchangeProcessor` entirely, consistent with the external report's recommendation to replace chained floating-point/complex formulas with exact arithmetic.

### Proof of Concept
Run `ExchangeProcessorTest.testStrictMath` (already present in the repo) with `useStrictMath=false` and compare against `SafeExchangeProcessor.INSTANCE.exchange(...)` for the same `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` tuples — the assertion `Assert.assertNotEquals(anotherTokenQuant, result)` at [7](#0-6) 
demonstrates that the default (non-hardened) `ExchangeTransactionActuator` execution path yields a token amount different from the exact BigDecimal computation for real-world exchange balances/quantities, confirming the precision-loss vulnerability is live in the default configuration.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
