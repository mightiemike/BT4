## Finding: Race Between Async State-Merkle Commit and Ledger-Metadata Epoch-Boundary Write Can Cause Stale `previous_epoch_ending_version` Routing - (File: `storage/aptosdb/src/state_store/state_snapshot_committer.rs`)

### Summary
`merklize_main_state` derives `previous_epoch_ending_version` by reading `EpochByVersionSchema` from the ledger metadata DB at the moment the state snapshot is merklized [1](#0-0) . That value is then used by `populate_jmt_writes` to decide whether a stale JMT node index belongs in `StaleNodeIndexCrossEpochSchema` or `StaleNodeIndexSchema` [2](#0-1) . The `EpochByVersionSchema` entry for an epoch boundary is only persisted inside `commit_ledger()` (via `check_and_put_ledger_info`/`put_ledger_info`) [3](#0-2) [4](#0-3) , whereas the state-merklize path (which reads that schema) is triggered from `pre_commit_ledger()` [5](#0-4) . The code explicitly documents that pre-commit and commit are allowed to run concurrently: *"Pre-committing and committing in concurrency is allowed... Consensus and state sync must hand over to each other after all pending execution and committing complete."* [6](#0-5) [7](#0-6) 

The pipeline README also confirms that a block's `Pre-Commit` stage only depends on the *parent block's* `Pre-Commit` — not on the parent block's `Commit Ledger` [8](#0-7) . This means `Pre-Commit(N+1)` — and the asynchronous state-snapshot-merklize work it enqueues — can run concurrently with, or even complete before, `Commit Ledger(N)` finishes writing the `EpochByVersionSchema` row for the epoch that ended in block N.

### Finding Description
`get_previous_epoch_ending(version)` does a direct, uncached RocksDB scan of `EpochByVersionSchema` [9](#0-8) . For versions in the first block of a new epoch, the correct answer requires the just-ended epoch's boundary row to already be durable. That row is written only in `commit_ledger`, a separate, differently-locked call from `pre_commit_ledger` [10](#0-9) .

If the background state-snapshot committer thread (spawned via `spawn_commit_pipeline`/`AsyncCommitThread`, invoked from `buffered_state().lock().update(...)` inside `pre_commit_ledger`) processes a snapshot for the new epoch's first version before `commit_ledger` for the boundary block has completed its DB write, `get_previous_epoch_ending` returns the *older* (N-2 epoch) boundary instead of the true, just-committed one. `populate_jmt_writes` then compares `row.node_key.version() <= prev` against this stale (too-low) `prev`, so nodes with versions between the stale boundary and the true boundary are written to `StaleNodeIndexSchema` instead of `StaleNodeIndexCrossEpochSchema` [11](#0-10) .

Note the reconfiguration block itself is protected: `chunk.is_reconfig` forces `sync_commit`, so the epoch-ending chunk's own merklize runs synchronously inside `pre_commit_ledger` [12](#0-11) . The exposure is specifically for the block(s) immediately *following* the epoch boundary, whose async merklize can race the boundary block's `commit_ledger`.

### Impact Explanation
Nodes with versions that belong to the just-completed epoch but are misclassified into the plain `StaleNodeIndexSchema` will be eligible for regular (non-epoch-aware) pruning. The `epoch_snapshot_pruner`/cross-epoch pruning logic relies on `StaleNodeIndexCrossEpochSchema` to retain the last version of nodes needed to serve epoch-ending state/Merkle proofs [13](#0-12) . Misrouting these entries can cause premature pruning of nodes still required for old-epoch proof serving, corrupting proof availability for state-sync/epoch-boundary consumers — this affects durable committed storage state and proof material rather than the JMT root hash itself. This is a node-local storage-integrity defect (does not alter the merkle root or cause a hard fork), but it can degrade or corrupt the authenticated proof responses a node serves for epoch-boundary queries.

### Likelihood Explanation
The race window depends purely on thread-scheduling and channel-processing timing between the two independently-locked commit stages (`pre_commit_lock` vs `commit_lock`), both explicitly allowed to run concurrently by design comments in the code [14](#0-13) . No malicious input or privileged action is required — any normal epoch-changing transaction stream (validator-set-unaffected or not) can trigger it, since the effect only depends on where the epoch boundary falls relative to snapshot batching. I was not able to fully confirm the exact timing/queue-depth behavior of the `AsyncCommitThread`/`SnapshotCommitter` (e.g., whether channel back-pressure incidentally prevents the race in practice), so likelihood should be treated as plausible-but-unverified rather than confirmed exploitable in production; a targeted concurrency/integration test is needed to establish whether the race is actually reachable given real channel capacities and thread scheduling.

### Recommendation
Make `previous_epoch_ending_version` resolution independent of a racing `commit_ledger` DB write — e.g., compute/carry it forward from the same in-memory `ChunkToCommit`/execution output that determined the epoch boundary (which is already known deterministically from the `LedgerInfoWithSignatures`/reconfiguration event at execution time), rather than doing a fresh RocksDB lookup in the async merklize path. Alternatively, add an explicit dependency so that `pre_commit_ledger` for the block after an epoch-ending block cannot enqueue its async merklize before the epoch-ending block's `commit_ledger` has durably written `EpochByVersionSchema`.

### Proof of Concept
Integration-test sketch:
1. Drive `AptosDB` (or `FakeAptosDB`) through a chunk sequence that ends an epoch at version `V`, immediately followed by a chunk starting the new epoch.
2. Artificially delay/serialize `commit_ledger(V, ...)`'s `write_schemas` relative to the async state-snapshot-committer thread processing the next chunk's snapshot (e.g., via a test hook/sleep injected around `check_and_put_ledger_info`).
3. After both complete, iterate `StaleNodeIndexSchema` and `StaleNodeIndexCrossEpochSchema` for node versions in `(prev_prev_epoch_boundary, V]` and assert all such stale indices for nodes stale-since `<= V` land in `StaleNodeIndexCrossEpochSchema` as required by `get_previous_epoch_ending`'s contract [15](#0-14) ; demonstrate failure occurs when the race is forced.

```rust
/// Routes each `stale_node_index_batch` entry into the cross-epoch
/// schema when its node version is `<= previous_epoch_ending_version`,
/// otherwise the regular stale-index schema.
pub(crate) fn populate_jmt_writes<W: WriteBatch>(
    batch: &mut W,
    tree_update_batch: &TreeUpdateBatch<StateKey>,
    previous_epoch_ending_version: Option<Version>,
) -> Result<()> {
    for (node_key, node) in tree_update_batch.node_batch.iter().flatten() {
        batch.put::<JellyfishMerkleNodeSchema>(node_key, node)?;
    }
    for row in tree_update_batch.stale_node_index_batch.iter().flatten() {
        if previous_epoch_ending_version.is_some_and(|prev| row.node_key.version() <= prev) {
            batch.put::<StaleNodeIndexCrossEpochSchema>(row, &())?;
        } else {
            batch.put::<StaleNodeIndexSchema>(row, &())?;
        }
    }
    Ok(())
```

```rust
    /// Returns the latest ended epoch strictly before required version, i.e. if the passed in
    /// version ends an epoch, return one epoch early than that.
    pub(crate) fn get_previous_epoch_ending(
        &self,
        version: Version,
    ) -> Result<Option<(u64, Version)>> {
        if version == 0 {
            return Ok(None);
        }
        let prev_version = version - 1;

        let mut iter = self.db.iter::<EpochByVersionSchema>()?;
        // Search for the end of the previous epoch.
        iter.seek_for_prev(&prev_version)?;
        iter.next().transpose()
    }
```

```rust
    fn test_get_previous_epoch_ending(ledger_infos_with_sigs in arb_ledger_infos_with_sigs()) {
```
