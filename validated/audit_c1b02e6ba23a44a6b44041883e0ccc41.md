### Title
`FinalizeOutbound` never advances a successful outbound's status past `Status_OBSERVED`, leaving the gas-refund accounting re-triggerable - (File: x/uexecutor/keeper/outbound.go)

### Summary
`FinalizeOutbound` gates all refund/re-mint logic on a single check: `outbound.OutboundStatus != types.Status_OBSERVED` must be false to proceed. On the failure path the code explicitly advances the state to `Status_REVERTED` before persisting, permanently closing the re-entry window. On the success path, `handleSuccessfulOutbound` does **not** set any terminal status on `outbound` before calling `applyGasRefund` and persisting via `UpdateOutbound` — the record is written back to store still carrying `Status_OBSERVED`.

### Finding Description
This mirrors the root cause pattern in the H-1 report: an accounting/state field that is supposed to be mutated to reflect "rewards/refunds already paid" is not updated consistently across all code paths, so a value that should gate repeat payouts remains in its pre-payout state. [1](#0-0) 

`FinalizeOutbound` only refuses to run when `outbound.OutboundStatus != types.Status_OBSERVED`: [2](#0-1) 

`handleFailedOutbound` correctly transitions the outbound to a terminal state (`Status_REVERTED`) before calling `k.applyGasRefund` and persisting: [3](#0-2) 

`handleSuccessfulOutbound`, by contrast, calls `applyGasRefund` and `UpdateOutbound` **without ever assigning a new `OutboundStatus`** to the local `outbound` value, so the persisted record still reads `Status_OBSERVED`: [4](#0-3) 

`applyGasRefund` itself computes `gasFee - gasFeeUsed` and, if positive, calls `k.CallUniversalCoreRefundUnusedGas` to move real PRC20/native value out of `UniversalCore` to the recipient: [5](#0-4) 

Because the guard in `FinalizeOutbound` is purely based on `outbound.OutboundStatus`, and the success path never flips that field away from `Status_OBSERVED`, any code path that re-invokes `FinalizeOutbound` against the same (still-`OBSERVED`) `OutboundTx` record will re-enter `handleSuccessfulOutbound` → `applyGasRefund` and re-issue the `refundUnusedGas` EVM call for the same `refundAmount`, repeatedly draining the gas-fee/refund pool. This is structurally identical to the Sherlock issue: a debt/state field that should be advanced on every payout is left stale on one of the two code branches, so replays of the same finalize path pay out repeatedly instead of being blocked by the accounting field.

### Impact Explanation
If `FinalizeOutbound` can be invoked more than once for the same outbound (e.g., via any retry/resend path that re-reads the stored `OutboundTx` — still `Status_OBSERVED` — and re-drives finalization, or via non-idempotent handling of duplicate `MsgVoteOutbound`/observation replay at the keeper layer), each invocation re-executes `CallUniversalCoreRefundUnusedGas`, transferring the same excess-gas amount out of protocol-controlled funds again. This is an unauthorized repeated release of funds, matching the "unauthorized release" / "corruption of gas fee accounting / refund accounting" impact categories in scope.

### Likelihood Explanation
This is a **partial/unconfirmed** finding: I was not able to fully trace, within the available iterations, whether the ballot-voting layer (`x/uvalidator`'s generic ballot machine, `VoteOnBallot`) that drives `MsgVoteOutbound` strictly guarantees `FinalizeOutbound` is invoked exactly once per outbound under honest validators (which would neutralize this bug in the honest-validator model), or whether there exists a distinct, unprivileged re-trigger path (e.g., a retry/resend message, or duplicate-observation handling) that re-reads the persisted `OutboundTx` and re-calls `FinalizeOutbound` without a corresponding fresh ballot. The concrete code defect — `handleSuccessfulOutbound` failing to advance `OutboundStatus` while `handleFailedOutbound` does — is confirmed by direct code inspection and is asymmetric in a way that looks unintentional, since it undermines the exact single-check idempotency guard `FinalizeOutbound` relies on.

### Recommendation
Set a terminal `OutboundStatus` (e.g., `Status_SUCCESS`/`Status_COMPLETED`, analogous to `Status_REVERTED` on the failure branch) inside `handleSuccessfulOutbound` before calling `applyGasRefund`/`UpdateOutbound`, so the `FinalizeOutbound` guard (`outbound.OutboundStatus != types.Status_OBSERVED`) correctly blocks any subsequent re-invocation from re-issuing the gas refund. Additionally, consider making `applyGasRefund` itself idempotent (e.g., checking `outbound.PcRefundExecution == nil` before calling `CallUniversalCoreRefundUnusedGas`) as defense in depth, so that even if `FinalizeOutbound` is re-entered, the refund transfer itself cannot be repeated.

### Proof of Concept
Not executed — this requires confirming, via a running node/test harness, whether any reachable code path (retry logic, duplicate observation submission, or a resend RPC) causes `FinalizeOutbound` to be called a second time on an `OutboundTx` that is still stored with `Status_OBSERVED` after a successful finalization. The existing integration test `test/integration/uexecutor/gas_fee_refund_test.go` exercises the single-call refund path and would be the natural place to add a second `FinalizeOutbound` invocation against the same stored outbound to check whether `CallUniversalCoreRefundUnusedGas` fires twice. func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}

func (k Keeper) handleSuccessfulOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	k.Logger().Info("outbound completed successfully",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"dest_chain", outbound.DestinationChain,

}
