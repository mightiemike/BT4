### Title
Unbounded, zero-fee growth of `DelegatedResourceAccountIndexStore` entries creates an asymmetric read-amplification DoS via `GetDelegatedResourceAccountIndexV2Servlet` - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`FreezeBalanceActuator.delegateResource` and `DelegateResourceActuator.execute` both call `calcFee()` which returns `0`, and each delegation only requires minimal frozen TRX to add one `V2_FROM_PREFIX`/`V2_TO_PREFIX` key-value pair to `DelegatedResourceAccountIndexStore`. The read path `DelegatedResourceAccountIndexStore.getV2Index` (invoked by `GetDelegatedResourceAccountIndexV2Servlet`) performs a full RocksDB prefix scan plus an in-memory sort over *all* entries for the queried address on every single call, so write cost is O(1)/negligible while read cost is O(N) per query and grows unboundedly with N.

### Finding Description
`FreezeBalanceActuator.delegateResource` (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:289-370`) and `DelegateResourceActuator.delegateResource` (`actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java:282-325`) both terminate in a call to `DelegatedResourceAccountIndexStore.delegate`/`delegateV2`, which simply does two `put()` calls: [1](#0-0) 

Both actuators return `calcFee() == 0`: [2](#0-1) [3](#0-2) 

So the only cost of adding an index entry is the minimal frozen TRX amount and standard transaction bandwidth/energy, unrelated to the size of the resulting index. Meanwhile the read path `getV2Index`/`getWithPrefix` performs a `prefixQuery` (RocksDB range scan) over both the `V2_FROM_PREFIX` and `V2_TO_PREFIX` keyspace for the target address, materializes all matching values into an `ArrayList`, and sorts them by timestamp on **every** call: [4](#0-3) 

This is reachable by an unauthenticated caller through `GetDelegatedResourceAccountIndexV2Servlet.fillResponse` → `wallet.getDelegatedResourceAccountIndexV2(address)`, exposed at `/wallet/getdelegatedresourceaccountindexv2`, `/walletsolidity/...`, and PBFT/Solidity variants: [5](#0-4) 

There is no cap on the number of distinct receiver addresses an owner (or attacker acting as a receiver, since both `from` and `to` sides get entries) can accumulate, and no fee scaling with N. The servlet only extends `RateLimiterServlet`, which limits request *rate*, not the cost-per-request, so an attacker who pre-inflates one target address's index (by repeatedly delegating to it, or self-targeting) makes every subsequent query against that address (by anyone, including monitoring services or block explorers) permanently more expensive, without the attacker paying any fee proportional to that cost.

### Impact Explanation
Once an address accumulates a large number of delegation relationships, every call to `getdelegatedresourceaccountindexv2` for that address triggers a full prefix scan and sort of the accumulated set, consuming CPU/disk-IO on the querying node. Since creation is essentially free (bounded only by minimal frozen balance and normal transfer bandwidth cost — unrelated to N) and each entry permanently increases the cost of all future reads for that address, an attacker can cheaply inflate N to create an asymmetric, compounding CPU cost on any full/solidity node that serves this public API for that address, degrading node performance for legitimate callers (wallets, explorers) querying that account.

### Likelihood Explanation
Feasible and repeatable with only unprivileged transactions: `FreezeBalanceContract(delegated=true, minimal frozen balance, new receiver)` submitted N times (each with a small unique receiver or bandwidth/energy resource), followed by M `GET /wallet/getdelegatedresourceaccountindexv2` calls. No admin/governance action, no privileged keys, and no protocol-level cap on the number of delegation relationships per address is present in the reviewed code.

### Recommendation
Introduce a cap on the number of distinct delegation relationships tracked per address in `DelegatedResourceAccountIndexStore` (rejecting further `FreezeBalanceContract`/`DelegateResourceContract` delegations to new receivers past the limit, similar to `GetCanDelegatedMaxSizeServlet`'s "max delegated size" concept but enforced pre-write), and/or make `calcFee()` in `FreezeBalanceActuator`/`DelegateResourceActuator` scale with the current entry count for the target address so index growth is priced. Additionally, consider paginating or bounding `getWithPrefix`'s scan (e.g., limit + cursor) so a single query cannot be forced into unbounded work.

### Proof of Concept
```java
// Integration test sketch (framework/src/test/java/org/tron/core/actuator/DelegateResourceActuatorTest.java style)
@Test
public void testAsymmetricIndexGrowthCost() {
  // 1. Attacker freezes minimal balance, delegating to N distinct receiver addresses.
  int N = 5000;
  long minimalBalance = 1_000_000L; // 1 TRX
  for (int i = 0; i < N; i++) {
    ECKey receiverKey = new ECKey(Utils.getRandom());
    byte[] receiver = receiverKey.getAddress();
    // fund receiver account minimally so it exists
    AccountCapsule receiverCapsule = new AccountCapsule(
        ByteString.copyFromUtf8("r" + i), ByteString.copyFrom(receiver),
        AccountType.Normal, 0L);
    dbManager.getAccountStore().put(receiver, receiverCapsule);

    FreezeBalanceActuator actuator = new FreezeBalanceActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(
        getDelegatedContractForBandwidth(OWNER_ADDRESS,
            ByteArray.toHexString(receiver), minimalBalance, 3));
    TransactionResultCapsule ret = new TransactionResultCapsule();
    actuator.validate();
    actuator.execute(ret);
    // assert fee == 0 for every delegation
    assertEquals(0L, ret.getFee());
  }

  // 2. Measure read cost via getV2Index (equivalent to what
  //    GetDelegatedResourceAccountIndexV2Servlet triggers).
  byte[] owner = ByteArray.fromHexString(OWNER_ADDRESS);
  long start = System.nanoTime();
  DelegatedResourceAccountIndexCapsule index =
      dbManager.getDelegatedResourceAccountIndexStore().getV2Index(owner);
  long elapsed = System.nanoTime() - start;

  assertEquals(N, index.getToAccountsList().size());
  // Expect elapsed time to scale with N (demonstrate widening ratio vs.
  // near-constant write cost measured in step 1), showing read cost is not
  // bounded/priced relative to the (zero) creation fee.
  System.out.println("Read latency for N=" + N + " entries: " + elapsed + "ns");
}
```
Run this with increasing `N` (e.g., 100, 1000, 5000, 20000) and record: (a) total attacker fee paid (constant near-zero per entry), and (b) `getV2Index` latency/CPU time, to demonstrate the growing read/write cost ratio.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
