## Analysis

The scoped repository implements an on-chain slippage-protection pattern for the module-driven "bridged token → PC" swap that is structurally analogous to the LiquiStake bug: slippage is derived from a value the attacker can manipulate at the moment of the trade, so the protection doesn't actually stop the trade from executing at a bad price.

### Title
Slippage protection derived from manipulable spot-price Uniswap V3 quote allows sandwich extraction of bridged user value - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
For `GAS` and `GAS_AND_PAYLOAD` inbound execution, and for excess-gas refunds on outbound finalization, `uexecutor` computes `minPCOut` by calling `GetSwapQuote`, which reads the *current* spot price from `QuoterV2.quoteExactInputSingle` on the live Uniswap V3 pool, then applies a flat 5% haircut and immediately executes `depositPRC20WithAutoSwap` / `refundUnusedGas` at that `minPCOut`. [1](#0-0)  Because the reference price comes from the same pool that is about to be traded against, and is read from live reserves rather than a manipulation-resistant TWAP, an unprivileged party can shift the pool's spot price with an ordinary swap immediately before the module's deposit-and-swap executes, causing the module to accept a `minPCOut` that reflects the manipulated (bad) price rather than a fair one.

### Finding Description
`GetSwapQuote` performs a static call to `quoteExactInputSingle`, which returns the amount out for the *current* pool state (no TWAP, no multi-block averaging, no independent price reference): [2](#0-1) 

This quote is immediately turned into a "slippage-protected" bound with a fixed 5% discount and used to gate the real swap in the very next call: [3](#0-2) 

The same pattern is repeated for `GAS_AND_PAYLOAD` inbound deposits: [4](#0-3) 

and for excess-gas refunds on outbound vote finalization (reachable purely from an honest UV's vote submission after ordinary user activity, no privileged action required): [5](#0-4) 

The upgrade handler confirms this quote-then-95%-swap design was itself introduced as the *fix* for a prior 0-slippage call, but the fix only prevents the swap from reverting — it does not prevent the swap from executing at an attacker-manipulated price: [6](#0-5) 

Because the source-chain inbound and its accumulating validator votes are visible on-chain before quorum finalizes (`PendingInbounds`), and quorum finalization triggers `ExecuteInboundGas`/`ExecuteInboundGasAndPayload` inside ordinary `MsgVoteInbound`/`MsgVoteOutbound` processing, an attacker can:
1. Observe a pending inbound/outbound nearing quorum.
2. Submit an ordinary EVM swap in the same PRC20/WPC Uniswap V3 pool (ordered just before the finalizing vote tx, e.g. via gas-price priority) to push the pool's spot price away from fair value in the direction that shrinks `amountOut` for the module's upcoming trade.
3. Let the module's `GetSwapQuote` read this manipulated spot price and derive `minPCOut` as 95% of it — a bound that is trivially satisfied by the now-degraded trade.
4. Let `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas` execute at the bad price, transferring value from the bridging user (who receives less PC/WPC than fair value) to the attacker's position in the pool.
5. Reverse the price with a second swap, capturing the price-impact difference — a classic sandwich, fully enabled because "slippage protection" is computed from the same manipulable venue as the trade itself, with no independent/TWAP oracle and no maximum-price-impact cap.

This mirrors the audit finding's root cause precisely: slippage/minimum-output values that are computed from a source an attacker can influence immediately beforehand provide no real protection against value extraction, even though they nominally prevent outright revert.

### Impact Explanation
This directly produces "unauthorized...loss of user or protocol-controlled funds" per the allowed impact gate: bridging users receive less native PC (or less refunded gas-equivalent) than the fair-value swap would produce, with the difference captured by an unprivileged attacker via pool arbitrage. It is triggered purely by ordinary user bridging activity plus an ordinary attacker-submitted swap transaction — no validator, TSS, or admin compromise is required.

### Likelihood Explanation
Likelihood is moderate-to-high wherever the underlying PRC20/WPC pool has shallow liquidity relative to the bridged/refunded amount, since Uniswap V3 spot price is well known to be manipulable within a single block via flash-swaps, and the pending-inbound/outbound state needed to time the attack is readable on-chain (`PendingInbounds`/`PendingOutbounds` queries) before quorum finalizes.

### Recommendation
Do not derive `minPCOut` solely from an instantaneous `quoteExactInputSingle` spot read. Use a TWAP-based reference price (or an off-chain/oracle-sourced fair price, computed independently of the pool about to be traded) and/or enforce a maximum allowable price-impact/deviation between the spot quote and the TWAP before allowing the module-originated swap to proceed, similar to how the original audit recommended computing slippage off-chain/in advance from a trusted source rather than from data an attacker can influence just before execution.

### Proof of Concept
1. Bridge a `GAS` inbound of token `X` (PRC20) through a shallow `X/WPC` Uniswap V3 pool used by `UniversalCore`.
2. As quorum approaches (observable via `AllPendingInbounds`), submit a swap in the same pool sized to move `quoteExactInputSingle(X→WPC)` down significantly, timed to land in a block before the UV's finalizing `MsgVoteInbound`.
3. When `ExecuteInboundGas` runs, `GetSwapQuote` returns the manipulated low value; `minPCOut = quote*95/100` is correspondingly low and easily satisfied by `CallPRC20DepositAutoSwap`, which executes the deposit-and-swap at the manipulated price.
4. Reverse the manipulation with a follow-up swap, netting the price-impact loss extracted from the bridging user's swap.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
