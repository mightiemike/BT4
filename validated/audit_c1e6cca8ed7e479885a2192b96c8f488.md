### Title
Unbounded, gas/compute-unmetered PromiseYield-timeout resolution loop enables a transaction-triggered chunk-processing DoS - (File: `runtime/runtime/src/lib.rs`)

### Summary
`Runtime::resolve_promise_yield_timeouts` walks the on-chain `PromiseYieldTimeout` queue and, for every entry whose `expires_at` has passed, performs trie reads/writes and creates/forwards a `PromiseResume` receipt. The loop's only early-exit conditions are `total.compute >= compute_limit` and `state_update.trie.check_proof_size_limit_exceed()`, but the body of the loop never adds anything to `total.compute` (unlike every other receipt-processing loop in the same file, which calls `processing_state.total.add(gas_burnt, compute_usage)` after executing a receipt). This mirrors the reported bug class exactly: an external-facing per-entry operation performed inside a loop whose termination is not actually gated by the resource cost of the operation itself, so the number of iterations that occur "for free" (with respect to compute/gas accounting) can be driven arbitrarily high by attacker-controlled state that accumulated over many prior blocks.

### Finding Description
`resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3113-3220`) is invoked once per chunk as the last stage of `process_receipts` (`runtime/runtime/src/lib.rs:2778-2843`, call at `:2824-2825`), always after `process_local_receipts`, `process_delayed_receipts`, and `process_incoming_receipts` have already consumed part of `compute_limit`. [1](#0-0) 

The loop condition breaks only on:
- `total.compute >= compute_limit`, or
- `state_update.trie.check_proof_size_limit_exceed()` (the stateless-validation state-witness size guard). [2](#0-1) 

For every due entry, the function performs a `contains_key` lookup, optionally a `get_pure` read, builds and forwards a new `PromiseResume` receipt via `receipt_sink.forward_or_buffer_receipt`, then removes the queue entry — all real trie/CPU work — but nowhere in the function is `processing_state.total.add(...)` (or any other `total.compute`/`total.gas` mutation) called. [3](#0-2) 

Compare this to every sibling receipt-processing routine, which does account for the cost of what it just did: [4](#0-3) 

Because `total.compute` is a value shared across all four processing phases of the chunk (`ApplyProcessingReceiptState.total`, incremented only by `process_receipt_with_metrics`), if a chunk contains few or no local/delayed/incoming receipts to execute, `total.compute` can remain near zero when `resolve_promise_yield_timeouts` starts — meaning its own loop-termination check based on `total.compute >= compute_limit` will essentially never fire, regardless of how many timeout entries are due. The only real backstop is the storage-proof/state-witness size check, which is a size-of-recorded-proof heuristic, not a compute/time bound, and can be satisfied by many cheap, small trie touches.

`PromiseYieldTimeout` entries in the queue are created whenever any account calls the `promise_yield_create` host function; the `expires_at = block_height + timeout_length` field is attacker-controlled to the extent that `timeout_length` is a caller-supplied (config-bounded) parameter. This is documented in the protocol spec: [5](#0-4) 

Crucially, `PromiseYield` receipts are "instant receipts" confined to a single account and are explicitly exempted from congestion accounting (`compute_receipt_congestion_gas` counts them as zero congestion gas), so cross-shard congestion control provides no throttling on how many can be queued up: [6](#0-5) 

Because `timeout_length` is attacker-chosen (within the config's allowed range) and `expires_at` is computed relative to the block height at *creation* time, an attacker can spread the creation of many `promise_yield_create` calls across many separate chunks/blocks (each creation batch bounded only by the normal per-chunk gas limit for that chunk) while choosing each call's `timeout_length` so that all the resulting `PromiseYieldTimeout` entries share (or cluster around) the *same* future `expires_at` block height. At that target height, `resolve_promise_yield_timeouts` will attempt to drain the entire accumulated backlog in a single chunk application, and — per the above — its own per-entry cost is not fed back into the `compute_limit` check that is supposed to bound per-chunk work.

### Impact Explanation
This is a resource-exhaustion issue in the runtime's deterministic state-transition function, reachable purely from ordinary, unprivileged transactions (any account can call a contract exposing `promise_yield_create`, e.g. via `promise_yield_create`/`promise_yield_resume` host functions available to any WASM contract). Because chunk application is deterministic and run identically by every validator/chunk-producer for that shard, a maliciously engineered spike in due `PromiseYieldTimeout` entries at a single block height would cause **every** honest node applying that chunk to perform the same unexpectedly large amount of trie work in one chunk-production/validation cycle. If the resulting wall-clock cost exceeds the block-time budget, this can cause repeated missed chunks / degraded liveness at that height — a transaction-triggered denial-of-service against chunk production for the affected shard, without any compensating gas charge to the attacker for the *resolution* work (only the original `promise_yield_create` calls were paid for; the timeout-processing cost is externalized onto all validators for free).

### Likelihood Explanation
Building the attack requires no special privileges — only ordinary `FunctionCall` transactions from a contract using `promise_yield_create` with attacker-chosen `timeout_length`, executed over a number of blocks bounded by the configured maximum yield timeout length. The number of entries that can be amassed is limited by cumulative gas spent on `promise_yield_create` calls across that window (an ordinary cost to the attacker) and by the config's max timeout length, not by any special defense in this code path. The attack is straightforward to reason about statically from the code (no fuzzing/adversarial-node assumptions needed), placing likelihood at Medium: it requires deliberate multi-block setup and gas expenditure, but no protocol bypass or privileged access.

### Recommendation
- In `resolve_promise_yield_timeouts`, account for the cost of each processed timeout entry against `total.compute` (and/or `total.gas`), e.g. by charging a fixed per-entry compute cost (mirroring how `process_receipt_with_metrics` calls `total.add(gas_burnt, compute_usage)`), so the existing `total.compute >= compute_limit` check actually bounds the number of entries processed per chunk.
- Alternatively/additionally, introduce an explicit per-chunk cap on the number of `PromiseYieldTimeout` entries resolved (independent of the shared `total.compute`), so this phase cannot silently consume unmetered chunk time even when other phases used little compute.
- Audit other loops that only check `check_proof_size_limit_exceed()` without a `total.compute`/`total.gas` increment for the same class of unmetered-per-iteration cost.

### Proof of Concept
1. Deploy a contract that repeatedly calls the `promise_yield_create` host function with a configurable `timeout_length` argument.
2. Over `K` consecutive blocks (`K` ≤ the protocol's maximum allowed yield timeout length), submit batches of `FunctionCall` transactions from many signer accounts, each calling `promise_yield_create` with `timeout_length_i = TARGET_HEIGHT - block_height_i`, so every created `PromiseYieldTimeout` entry has `expires_at == TARGET_HEIGHT`. Each batch is only bounded by that block's normal gas limit, so across `K` blocks the attacker can accumulate roughly `K × (gas_limit / gas_cost_of_yield_create)` queued entries.
3. At `TARGET_HEIGHT`, on the shard holding these accounts, `process_receipts` invokes `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:2824-2825` → `:3113`). Since no other/only few receipts are queued for that chunk, `total.compute` starts near zero and is never incremented by this function's own work, so the loop processes the *entire* accumulated backlog of due entries in one chunk application, bounded in practice only by the storage-proof/state-witness size limit — a size heuristic that does not correspond to a fixed bound on wall-clock work per entry.
4. Observe elevated chunk-application latency for that shard at `TARGET_HEIGHT`, evidenced by the `yield_timeouts_done` metric's processed count and elapsed time (`runtime/runtime/src/lib.rs:3209-3214`), and, if scaled sufficiently, missed-chunk symptoms for that height.

*(Note: exact numeric bounds for `timeout_length`/`gas_cost_of_yield_create`, i.e. how large the achievable backlog actually is in production configuration, were not fully derived from the index in this pass — the `parameters.yaml` config entries for `yield_timeout_length` were located but not read in full; a background Devin session with full repository access would be needed to compute concrete worst-case entry counts and confirm proof-size vs. compute-time behavior empirically.)*

### 8. Promise yield / resume (parking and timeout)

A `PromiseYield` receipt, when processed, is simply stored keyed by
`(receiver_id, data_id)` and awaits resume (`process_receipt`, `lib.rs:1431-1434`,
`set_promise_yield_receipt`). Yields are **instant receipts** (`is_instant_receipt`,
`receipt.rs:474`) and confined to a single account, so they never cross shard
boundaries and count as zero congestion gas (`congestion_control.rs:696`).

A `PromiseResume` receipt (`lib.rs:1436`) delivers the awaited data. If it is a
*timeout* resume (`data: None`) and the yield status is `ResumeInitiated`, it is
dropped because a real resume already exists (`lib.rs:1441-1444`). Otherwise, if the
parked yield receipt is found, the runtime removes it and its status, stores the
`ReceivedData`, and executes the yield receipt immediately (`lib.rs:1450-1498`); a
second resume for the same `data_id` finds nothing and is ignored (`lib.rs:1499`).

**Timeouts** are the last step of `process_receipts`:
`resolve_promise_yield_timeouts` (`lib.rs:2986`) walks the `PromiseYieldTimeout` queue
in `expires_at` order, stopping at the first entry with `expires_at >
block_height` (`:3019`) or once the compute/proof-size budget is hit (`:3003`). For
each expired entry whose yield still exists, it synthesizes a `PromiseResume` with
`data: None` destined for the same (local) account and forwards/buffers it
(`:3037-3074`); the timeout is then dequeued (`:3078`). The timeout resume and any
real resume are ordered to the same shard, so a late timeout after a real resume is
simply discarded.
