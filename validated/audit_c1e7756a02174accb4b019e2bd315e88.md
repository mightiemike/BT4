### Title
Unchecked `SessionStorage.storeSession()` boolean return value during OAuth/token-exchange causes silent session-persistence failure while app proceeds as authenticated - (Files: `packages/apps/shopify-app-express/src/auth/auth-callback.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/auth-code-flow.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts`, `packages/apps/shopify-app-react-router/src/server/authenticate/admin/strategies/token-exchange.ts`)

### Summary
The `SessionStorage` interface explicitly documents `storeSession()` as returning `Promise<boolean>` — `true` if the session was successfully stored, `false` otherwise [1](#0-0) . Across all OAuth/token-exchange completion paths in this repo, the returned boolean is discarded with a bare `await`, and execution unconditionally continues as though the session was persisted — mirroring the reported ERC20 pattern of not checking a transfer's success/failure return value before proceeding with dependent logic.

### Finding Description
In the Express adapter, `authCallback()` calls `await config.sessionStorage.storeSession(callbackResponse.session);` without checking the result, then immediately proceeds to register webhooks, attach the session to `res.locals.shopify`, and invoke the `afterAuth` hook [2](#0-1) .

In the Remix (and equivalent React Router) `AuthCodeFlowStrategy.handleAuthCallbackRequest()`, the same pattern occurs: `await config.sessionStorage!.storeSession(session);` is not checked before triggering the after-auth hook and redirecting the merchant into the embedded app as if fully authenticated [3](#0-2) .

In `TokenExchangeStrategy.authenticate()`, both the offline and online `storeSession()` calls are unchecked before the new session is returned and used to authorize the request / trigger the after-auth hook [4](#0-3) .

If the configured `sessionStorage` backend returns `false` on failure (e.g. a custom or third-party `SessionStorage` implementation encountering a transient write failure, unique-key conflict, or connection issue that it surfaces as `false` rather than throwing — this is exactly the documented contract, and the bundled `CsvSessionStorage` example in the docs demonstrates returning `false` on write errors [5](#0-4) ), none of these call sites detect it. The library proceeds to: register webhooks, run `afterAuth` hooks (which commonly perform additional privileged setup), set authenticated cookies/session state, and redirect the merchant into the app as if OAuth fully succeeded — while the access token was never durably persisted.

### Impact Explanation
This is an authentication-state/session-storage integrity issue analogous to the ERC20 case: the code assumes a storage operation succeeded without checking its explicit success/failure signal, leading to inconsistency between what the app believes (session stored, merchant authenticated) and the actual backing store state (nothing persisted). Consequences include: subsequent requests failing to load the session (forcing repeated/broken OAuth loops), `afterAuth` hooks firing for a session that doesn't durably exist, webhooks being registered for a shop/token pair that isn't retrievable, and potential inconsistent state in multi-instance deployments where the failed write is silently dropped. It does not directly grant a forged session to an attacker, but it produces silent inconsistency in the auth/session lifecycle stemming from ignoring an explicit boolean success indicator — the same bug class described in the report.

### Likelihood Explanation
This code path executes on every OAuth callback and every token-exchange call, i.e., is reachable from a normal merchant install/re-auth flow (single merchant, not privileged). Triggering the failure condition requires the configured `SessionStorage` implementation to return `false` (per its documented contract) rather than throw, which depends on the specific storage backend/implementation in use; the bundled adapters largely `throw` on error rather than return `false`, so under default first-party adapters (Prisma, Redis, SQLite, Postgres, MySQL, DynamoDB, MongoDB, KV, Drizzle) the returned boolean is effectively always `true`, and only custom/third-party `SessionStorage` implementations following the documented contract's negative case would expose this gap in practice.

### Recommendation
At every OAuth callback and token-exchange call site (`shopify-app-express/src/auth/auth-callback.ts`, `shopify-app-remix`/`shopify-app-react-router` `auth-code-flow.ts` and `token-exchange.ts`), check the boolean returned by `storeSession()` and abort the authentication flow (return an error / trigger re-auth) instead of proceeding if it returns `false`, consistent with the interface's documented contract.

### Proof of Concept
Not applicable as a runnable exploit — this is a code-review-level defect in first-party code (missing check on a documented boolean return value), not an externally forgeable request. Concretely, implement/configure a `SessionStorage.storeSession()` that returns `false` on write failure (as the documented `CsvSessionStorage` example does) and complete OAuth: the callback/token-exchange handlers in the files above proceed to fire `afterAuth`, register webhooks, and redirect into the app despite `storeSession()` resolving to `false`.

  public async storeSession(session: Session): Promise<boolean> {
    try {
      const lines = this.readLines();

      let found = false;

      // process each line
      for (let i = 0; i < lines.length; i++) {
        // split the line by comma into columns
        const columns = lines[i].split(',');
        // check if the id column matches (second column is value of 'id')
        if (columns[1] === session.id) {
          // if the session id already exists, update the line
          lines[i] = session.toPropertyArray().join(',');
          found = true;
          break;
        }
      }

      if (!found) {
        // if the session id does not exist, add a new line
        lines.push(session.toPropertyArray().join(','));
      }

      try {
        this.writeLines(lines);
        return true;
      } catch (err) {
        // error on write
        return false;
      }
    } catch (err) {
      // error on read
      return false;
    }
  }
