### Title
Stale Global Contract-Class Cache Bypasses Declaration State After Block Revert for Cairo0 Classes - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` re-validates cache hits against the authoritative "is this class currently declared" state only for Cairo1/Native classes, not for Cairo0 (`RunnableCompiledClass::V0`) classes. When a block containing a `Declare` (Cairo0) transaction is reverted via `revert_block`, the storage layer correctly removes the class from `declared_classes`/`deprecated_declared_classes`, but the sequencer's in-memory `GlobalContractCache` retains the compiled class indefinitely and keeps serving it as executable code, causing the runtime's view of "is this class declared" to permanently diverge from the storage/committed view.

### Finding Description
`get_compiled_from_class_manager` checks the shared, long-lived `contract_class_manager` cache first: [1](#0-0) 

The `match` arm explicitly skips re-validation for `RunnableCompiledClass::V0(_)`, only re-checking `is_declared` for the `_` (Cairo1/Native) branch, with the comment acknowledging the exact hazard: cache entries "might contain a declared class from a reverted block." `is_declared` is documented to always return `false` for Cairo0 classes: [2](#0-1) 

This means there is *no* re-validation path at all for Cairo0 classes — once cached, a Cairo0 class hash is treated as forever-valid and executable, regardless of what the authoritative storage says. The cache itself (`GlobalContractCache`, `crates/starknet_api/src/class_cache.rs:14-37`) is a process-global LRU that is never cleared or invalidated by `revert_block`/`revert_state_diff`.

The revert path that creates this desync is a first-class, non-malicious sequencer operation: `Batcher::revert_block` calls `self.storage_writer.revert_block(height)` (`crates/apollo_batcher/src/batcher.rs:1428-1456`), which invokes `apollo_reverts::revert_block`, calling `revert_state_diff` (`crates/apollo_reverts/src/lib.rs:125-147`). `revert_state_diff` explicitly deletes declared/deprecated-declared class entries and their block markers: [3](#0-2) 
and the storage-level test suite confirms that after `revert_state_diff`, `get_class_definition_at`/`get_deprecated_class_definition_block_number` correctly report the class as gone: [4](#0-3) 

However, nothing in this revert flow touches the blockifier's `ContractClassManager`/`GlobalContractCache`, which was populated by prior block execution via `set_and_compile` on the original (soon-to-be-reverted) declare: [5](#0-4) 

This is a direct structural analog to the reported Rocq issue: a locally/temporarily valid piece of state (the declared class, analogous to the "local Unset Universe Checking" inside a module) is supposed to be undone when its enclosing scope (the block) is reverted, but a secondary cached "view" of that state (the global class cache, analogous to the universe graph's copy of the checking flag) is never resynchronized, so two internal state views permanently disagree — one (the authoritative persisted `declared_classes` table) says undeclared, the other (`GlobalContractCache`) says valid and returns executable code.

### Impact Explanation
- **Honest-node divergence / wrong committed state**: Any subsequent transaction from any unprivileged sender that calls into (or attempts to deploy against, or `replace_class` to) the reverted class hash will succeed on a sequencer node whose cache is warm (class hit → executed as if declared) while failing (`UndeclaredClassHash`) on a node whose cache is cold or was cleared/restarted. Two honest sequencer/validator nodes processing the identical block can therefore reach different execution results (accept vs. reject) for the same transaction, which is a consensus-relevant divergence.
- **Unauthorized contract execution against unregistered class**: A contract can effectively continue running bytecode for a class hash the network no longer considers declared (e.g. after a legitimate height-revert used to correct a bad block), letting execution proceed on code the current global state does not attest to — directly undermining Starknet's declare/undeclare invariant that class execution requires a currently valid, committed declaration.
- The bug is entirely triggerable through the standard revert-then-rebuild path any sequencer performs, and every subsequent invocation of the affected class hash by ordinary transactions exercises the desynchronized cache — no privileged/malicious actor needed to *trigger the disagreement itself*, only to submit ordinary transactions once the desync exists.

### Likelihood Explanation
Height reverts are a built-in, exercised production mechanism (`Batcher::revert_block`, `apollo_consensus_manager::revert_batcher_blocks`) used whenever the batcher/committer must roll back a height, not an exotic or attacker-only path. Because Cairo0 (`RunnableCompiledClass::V0`) classes still exist and can be declared/redeclared in current versions of Starknet, and the class cache is never scoped per-block or invalidated on revert, the desynchronization is reached anytime a Declare (Cairo0) transaction's block is reverted after the class has been read/cached at least once (which happens automatically the first time the class is invoked). This is a deterministic, code-path-level bug rather than a probabilistic race, making it highly likely to manifest whenever a revert of a block containing a Cairo0 declare occurs.

### Recommendation
Extend the `is_declared` re-validation performed for Cairo1/Native cache hits to Cairo0 (`RunnableCompiledClass::V0`) entries as well — i.e., have `FetchCompiledClasses::is_declared` (or an equivalent deprecated-class check) return a meaningful answer for Cairo0 classes and invoke it unconditionally in `get_compiled_from_class_manager`, removing the special-cased `V0(_) => {}` no-op branch. Alternatively, invalidate/evict the relevant `GlobalContractCache` entries as part of `revert_block`/`revert_state_diff` so no stale compiled classes can survive a state revert.

### Proof of Concept
1. Sequencer node executes block N containing `Declare` of Cairo0 class `C` (deprecated contract class); a subsequent transaction in the same or later block invokes class `C`, causing `get_compiled_from_class_manager` to fetch and cache `C` into the process-global `contract_class_manager` cache (`state_reader_and_contract_manager.rs:88-103`).
2. Consensus/batcher determines block N must be reverted (e.g., due to a builder/consensus rollback) and calls `Batcher::revert_block` → `apollo_reverts::revert_block` → `revert_state_diff`, which deletes `C` from `declared_classes`/markers in persistent storage (verified by `declare_revert_declare_scenario`, `apollo_storage/src/state/state_test.rs:754-836`).
3. The process's `GlobalContractCache` still holds `C` (nothing in the revert path clears it).
4. A new block is built without re-declaring `C`. Any transaction that invokes class `C` (e.g. calling a contract deployed with class hash `C`, or a `replace_class` targeting `C`) reaches `get_compiled_from_class_manager`; since `runnable_class` matches `RunnableCompiledClass::V0(_)`, the `is_declared` check is skipped entirely, and the stale cached class is returned as valid, executing code for a class hash the storage layer no longer recognizes as declared — while a node with a cold cache (or one that evicted the entry) would correctly return `StateError::UndeclaredClassHash` for the identical transaction, producing a fork in execution results between otherwise-honest nodes.
