## Title
Exchange pool inject/withdraw amounts computed from manipulable spot balance ratio, enabling value extraction via sandwich attacks - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the paired ("another") token amount for a liquidity injection or withdrawal purely from the *current* on-chain reserve ratio (`firstTokenBalance` / `secondTokenBalance`) of the TRC10 Bancor-style `Exchange` pool, taken at the instant the transaction executes. This is the direct java-tron analog of the reported `OmoOracle.getLiquidityAmounts()` bug: both derive economically significant amounts from an instantaneous ("spot") reserve ratio with no time-weighting or manipulation resistance, so a party who can also move that ratio in the same block can extract value from other liquidity providers.

### Finding Description
`ExchangeInjectActuator.execute()` reads the exchange's live reserves and computes the counter-token quantity proportionally to the current ratio, exactly as `getLiquidityAmounts()` uses the live `sqrtPriceX96` from `pool.slot0()`: [1](#0-0) 

`ExchangeWithdrawActuator.execute()` does the same for withdrawals — the amount of the "other" token returned to the withdrawer is derived directly from the live `firstTokenBalance`/`secondTokenBalance` ratio: [2](#0-1) 

The actual price-moving primitive, `ExchangeCapsule.transaction()` (the Bancor swap function used by `ExchangeTransactionActuator`), mutates `firstTokenBalance`/`secondTokenBalance` and therefore the spot ratio in a single call: [3](#0-2) 

Because all three actuators (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) operate on the same mutable `ExchangeCapsule` reserves and there is no TWAP, oracle, or slippage/ratio-bound check anywhere in the inject/withdraw path (validation only checks balance limits, not price deviation — see `ExchangeInjectActuator` validate logic), any account that controls the ordering of transactions within a block (e.g., by submitting several transactions itself, which execute sequentially in block order) can:
1. Execute a large `ExchangeTransactionContract` swap to skew the first/second token reserve ratio.
2. Execute an `ExchangeInjectContract` (or `ExchangeWithdrawContract`) that is priced using this now-skewed ratio, extracting more of one token relative to the other than the pre-manipulation fair value.
3. Execute a reverse swap to restore reserves to close to the original ratio, keeping the swap fee cost as the only expense.

This mirrors the reported bug exactly: a spot on-chain ratio, freely movable within one atomic sequence of transactions by the same actor, is used unguarded as the pricing "oracle" for a value-transferring operation (position/liquidity sizing).

### Impact Explanation
An attacker can extract value from other liquidity participants of a TRC10 Bancor exchange pool (or dilute their share) by manipulating the spot reserve ratio immediately before injecting or withdrawing liquidity, then reversing the manipulation. This directly harms other exchange participants' economic value and constitutes underpriced/overpriced settlement of liquidity operations — an accounting/settlement impact reachable by any unprivileged account holding TRX/TRC10 tokens and paying only transaction fees and swap slippage cost, similar in class to the High severity rated in the original report because it can transfer real economic value away from other pool participants.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control multiple sequential transactions that land in the same or nearby blocks (achievable since ordinary users can submit chained transactions), and profitability depends on pool depth and the current inject/withdraw activity of victims, similar to the medium likelihood rated in the source report for the Uniswap analog.

### Recommendation
Bound the allowable deviation between the price implicit in an inject/withdraw operation and a time-weighted or previously-checkpointed reference price for the pool (e.g., disallow injects/withdraws that would move reserves by more than a configured percentage in the same block as a swap on the same pool), or require injects/withdraws to specify and enforce a caller-supplied minimum/maximum ratio bound (slippage protection) analogous to `tokenExpected` already used in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker (or colluding transactions ordered together) submits `ExchangeTransactionContract` selling a large amount of `firstToken` into the pool via `ExchangeTransactionActuator`, shifting `firstTokenBalance`/`secondTokenBalance` significantly (see `ExchangeCapsule.transaction()`).
2. In the same block, attacker submits `ExchangeInjectContract` (via `ExchangeInjectActuator`) injecting `secondToken`; `anotherTokenQuant` is computed from the now-skewed ratio at [4](#0-3) , letting the attacker mint a disproportionately large ownership stake in the pool relative to fair value.
3. Attacker submits a reverse `ExchangeTransactionContract` swap restoring the reserve ratio close to the pre-attack level, paying only the Bancor formula's spread as cost.
4. Attacker's injected position is now overvalued relative to true reserves, extracting value from other pool participants on subsequent withdrawals — the same "spot-price-used-as-value-oracle without TWAP" flaw described in the original report.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
