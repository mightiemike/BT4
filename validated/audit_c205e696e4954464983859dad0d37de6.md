## Analog Analysis Result

### Title
Gateway spawns expensive recursive-circuit proof verification before any fee/stake/resource accounting, enabling a cheap compute-exhaustion DoS on every sequencer's gateway - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
The external report's bug class is: an expensive cryptographic verification (signature check) is performed on attacker-controlled, large input *before* the cost of that verification is charged to the submitter, so failing verification is nearly free for the attacker while being expensive for the node. This sequencer has a structurally identical flow for client-side-proving `Invoke` transactions: the gateway runs a recursive STARK proof verification (`starknet_proof_verifier::verify_proof` → `privacy_circuit_verify_v1::verify_recursive_circuit`) for every submitted transaction that carries `proof_facts`/`proof`, and this verification happens purely in the stateless/pre-mempool gateway path, before any per-transaction fee, resource-bound, or balance check is enforced on the submitter.

### Finding Description
`GenericGateway::add_tx_inner` runs `stateless_tx_validator.validate(&tx)` (which only bounds sizes: `max_calldata_length`, `max_signature_length`, `max_proof_size`) and then immediately calls `convert_rpc_tx_to_internal_and_executable_txs`, which invokes `TransactionConverterTrait::convert_rpc_tx_to_internal_rpc_tx` → `spawn_proof_verification`. This spawns `run_proof_verification`, which — if the proof isn't already cached — calls `starknet_proof_verifier::verify_proof` inside `tokio::task::spawn_blocking`, performing a full recursive-circuit STARK verification (`privacy_circuit_verify_v1::verify_recursive_circuit`) on the submitted proof bytes. [1](#0-0) [2](#0-1) [3](#0-2) 

Crucially, the only gating performed before this expensive verification is the `StatelessTransactionValidator`, which checks structural/size bounds (`validate_tx_size`, `validate_proof_size`, `validate_client_side_proving_allowed`) but performs **no fee, balance, resource-bound, or stateful account check** — those (`extract_state_nonce_and_run_validations`, i.e., stateful validation against account balance/nonce/resource bounds) happen *after* the proof verification completes. [4](#0-3) [5](#0-4) 

This is a nearly exact structural analog to the reported `EVM.Restore()` bug: an "honest server" (here, an honest client that legitimately proved something) is expected to only submit valid proofs, but nothing stops an attacker from submitting `max_proof_size`-bounded, syntactically-valid-looking but cryptographically invalid proof bytes on invoke transactions repeatedly. Each submission forces every gateway node in the network (both the originating sequencer and, via P2P propagation before mempool admission, every peer sequencer since "Same validation flow" runs on receipt — see `docs/diagrams/02-tx-submission-flow.md`) to run a full recursive circuit verification, which is computationally far more expensive than intrinsic/stateless checks, before the account is even confirmed to be able to pay for the transaction. Unlike normal EVM/Starknet transaction validation (where step/gas metering bounds worst-case cost), this proof verification cost is paid by the *node's CPU*, not by the submitter's resource bounds, and is not deducted from any fee since the transaction is rejected outright on verification failure (`StarknetErrorCode::KnownErrorCode(KnownStarknetErrorCode::InvalidProof)`), with no balance debit. [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged transaction sender can craft repeated `Invoke` transactions (no valid account state/funds strictly required at gateway ingestion time, since the account balance/nonce check occurs *after* proof verification) with `proof_facts`/`proof` fields filled with garbage bytes up to `max_proof_size`. Each submission forces the gateway (and, via P2P re-broadcast/re-validation, every peer sequencer) to run a full recursive STARK circuit verification on a background thread pool (`spawn_blocking`), which is orders of magnitude more CPU-expensive than the size/structural checks that gate it. At sufficient submission rate this can starve the gateway's blocking thread pool / CPU across the network, delaying or preventing legitimate transactions from being validated and admitted to the mempool — i.e., a network unable to confirm new transactions in a timely manner, matching the "concrete... network unable to confirm new transactions" bar in scope.

### Likelihood Explanation
Likelihood is high for reachability (any unprivileged sender can submit such a transaction via the standard `add_transaction` RPC endpoint used for normal invoke transactions with client-side proving enabled), but the actual severity depends on operational parameters not fully visible from static code alone: (1) whether `allow_client_side_proving` is enabled in production configs, (2) the concrete cost of `verify_recursive_circuit` relative to CPU/thread-pool capacity, and (3) whether there is out-of-band rate limiting (e.g., per-IP throttling at the HTTP layer, mempool duplicate/spam filters) that mitigates volume. These operational mitigations could not be confirmed from the indexed code; the `declare_compilation_semaphore` pattern shows the team is aware of exactly this class of gateway CPU-exhaustion risk for Sierra compilation but no equivalent semaphore/limit was found guarding proof verification. [8](#0-7) 

### Recommendation
Apply the same mitigation pattern already used for declare compilation: gate proof-verification with a concurrency semaphore/rate limiter sized to the CPU cost of `verify_recursive_circuit`, and/or require a minimal stake/fee-bond check (balance sufficiency for at least the proof-verification-related resource cost) before spawning verification, so failing verifications cannot be repeated for free at unbounded rate. Consider charging or blacklisting senders whose proofs repeatedly fail verification, analogous to consuming all gas on invalid restoration signatures in the original report.

### Proof of Concept
1. Enable `allow_client_side_proving` in gateway config.
2. Submit repeated `RpcInvokeTransaction::V3` transactions (from possibly unfunded/new accounts) with random `proof_facts` (satisfying only the structural/length checks in `validate_tx_size`/`validate_proof_facts_and_proof_consistency`) and `proof` bytes near `max_proof_size`.
3. Observe that each request reaches `spawn_proof_verification` → `verify_proof` → `verify_recursive_circuit` before nonce/balance/resource-bound checks in `extract_state_nonce_and_run_validations`, consuming gateway CPU/thread-pool capacity per request at negligible cost (network round-trip) to the attacker, with transactions ultimately rejected via `InvalidProof` with no fee charged.     async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }

pub fn verify_proof(proof_facts: ProofFacts, proof: Proof) -> Result<(), VerifyProofError> {
    // Reject empty proof payloads before running the verifier.
    if proof.is_empty() {
        return Err(VerifyProofError::EmptyProof);
    }

    let proof_version_felt = proof_facts.0.first().copied().unwrap_or_default();
    let proof_version = ProofVersion::try_from(proof_version_felt)
        .map_err(|()| VerifyProofError::InvalidProofVersion { actual: proof_version_felt })?;

    let output_preimage = reconstruct_output_preimage(&proof_facts)?;
    // TODO(Avi): Avoid cloning the proof.
    let proof_bytes = proof.0.to_vec();

    match proof_version {
        // V0 proofs are no longer verifiable: the v0 circuit was removed. V0 proof facts are only
        // tolerated by the blockifier (gated per protocol version) for replaying historical blocks.
        ProofVersion::V0 => {
            return Err(VerifyProofError::InvalidProofVersion { actual: proof_version_felt });
        }
        ProofVersion::V1 => {
            let proof_output = privacy_circuit_verify_v1::PrivacyProofOutput {
                proof: proof_bytes,
                output_preimage,
            };
            privacy_circuit_verify_v1::verify_recursive_circuit(&proof_output)
                .map_err(|e| VerifyProofError::Verification(e.to_string()))?;
        }
