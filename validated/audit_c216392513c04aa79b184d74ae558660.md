### Title
Stale PromiseYield / postponed-receipt state on a deleted account is inherited by a newly created account with the same `AccountId` - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (called from `action_delete_account`) only removes `Account`, `ContractCode`, `AccessKey`/gas-key rows, and `ContractData`. It does not remove `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, or `YieldIdToDataId`/`DataIdToYieldId` entries keyed by that account's `AccountId`. Because Xenstore-style per-`AccountId` trie rows are never purged, a new account created later under the exact same `AccountId` inherits leftover receipt-matching state from the deleted incarnation — the same bug class as CVE-2020-29481 (Xen access rights tied to a reused `domid` surviving domain destruction).

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs:504-575` is the sole cleanup routine invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:330-407`, specifically the call at line 387): [1](#0-0) [2](#0-1) 

It removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [3](#0-2) 

However, `core/primitives/src/trie_key.rs` shows that several other columns are also keyed by `account_id`/`receiver_id` and are never touched by `remove_account`: `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, `DATA_ID_TO_YIELD_ID`: [4](#0-3) [5](#0-4) 

`action_delete_account` performs only a storage-usage cap check (`DeleteAccountWithLargeState`) and a gas-key-balance check before wiping the account — there is no check that the account has no outstanding postponed receipts or parked `PromiseYield` entries: [6](#0-5) 

Separately, `action_create_account` (`runtime/runtime/src/actions.rs:166-200`) only validates naming/registrar rules and initializes a fresh `Account`; it performs no scan for or cleanup of leftover receipt-matching rows under the same `account_id`: [7](#0-6) 

The `PromiseYieldTimeout` queue is a *global per-shard FIFO*, independent of the account's lifecycle, and is processed automatically each chunk once `expires_at` height is reached, per the spec: [8](#0-7) 

Because the `PromiseYieldReceipt`/`PromiseYieldStatus` rows are addressed purely by `(receiver_id: AccountId, data_id)` and `remove_account` never clears them, if an account creates a `promise_yield_create` receipt (parked under its own `account_id`) and is then deleted (`DeleteAccount`) before the yield resumes/times out, the parked receipt entry silently survives account deletion in the trie. If a new account is later created under the identical `AccountId` (a named/sub-account can always be recreated once deleted, and the existing test suite explicitly exercises "delete then recreate the same id" scenarios), the dangling `PromiseYieldTimeout` entry will still fire at its recorded `expires_at` height. `resolve_promise_yield_timeouts` will find the still-present `PromiseYieldReceipt`/`PromiseYieldStatus` rows for that `account_id`, synthesize a `PromiseResume`, and the runtime will execute the parked receipt's actions against whatever account now occupies that `account_id` — a receipt the new account owner never created, authorized, or is even aware of.

### Impact Explanation
This produces a transaction-triggered, deterministic invalid state transition: actions embedded in a stale, pre-deletion receipt (potentially `FunctionCall`s with attached deposit/gas, `Transfer`s, etc., created by the previous incarnation of the account) execute unexpectedly against the new account's current code and state, without any authorization from the new account's access keys. Depending on what the resumed callback logic does (e.g., finalizing an escrow, minting/crediting balances, invoking a privileged "resume" callback method), this can cause unauthorized value movement or corruption of the new account's contract state — consistent with "invalid state transition acceptance" / "receipt loss or duplication" as scoped by the rules. All honest nodes process this deterministically from the leftover trie state, so it does not itself cause state-root divergence between honest nodes, but it does constitute execution of an action nobody currently controlling the account approved, which is a concrete unauthorized-execution/value-movement bug directly analogous to Xen's stale access-rights-on-reused-domid issue.

### Likelihood Explanation
Reachability requires only ordinary, permissionless operations available to any transaction signer/contract deployer: (1) deploy a contract that calls `promise_yield_create`, (2) delete the account via a normal `DeleteAccount` action before the yield resolves (there is no check preventing deletion while a yield/postponed receipt is outstanding), and (3) have (or wait for) the same sub-account name to be recreated by anyone (the parent account, or self after refunding) before the yield's timeout height is reached. All of these are standard, unprivileged actions reachable from a signed transaction; no validator/network/sync privileges are needed.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also purge, for the given `account_id`: all `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` rows, and remove or invalidate any corresponding `PromiseYieldTimeout` queue entries so they are dropped rather than executed once the account no longer exists (or once a different account occupies that id). Alternatively/additionally, disallow `DeleteAccount` while the account has any outstanding postponed receipts or parked promise-yield entries, mirroring the existing `DeleteAccountWithLargeState`/`GasKeyBalanceTooHigh` guards in `action_delete_account`.

### Proof of Concept
Not independently executable from the index (no test harness confirming end-to-end resume-after-recreate was found), but the mechanism is directly supported by code:
1. Contract on account `child.parent.near` calls `promise_yield_create`, producing a `PromiseYieldReceipt`/`PromiseYieldStatus` row keyed by `(receiver_id=child.parent.near, data_id)` and a `PromiseYieldTimeout` queue entry with some `expires_at` height (see `set_promise_yield_receipt`/timeout handling referenced in `runtime/runtime/src/lib.rs:1559-1618` and the congestion-control spec section 8).
2. Before the yield resolves, `child.parent.near` self-deletes via `Action::DeleteAccount` (as in `test_instant_delete_account`, `test-loop-tests/src/tests/create_delete_account.rs:23-86`). `remove_account` clears only Account/ContractCode/AccessKey/ContractData rows.
3. `parent.near` recreates `child.parent.near` (`Action::CreateAccount`) before `expires_at`, exactly as exercised by `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` (`runtime/runtime/src/tests/apply.rs:4978-5055`), which already demonstrates that receiver resolution after delete+recreate binds to the new account.
4. At block height `expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:2986` per spec citation) finds the still-present `PromiseYieldReceipt` for `child.parent.near` and executes it against the newly created account, running actions the current owner never authorized. /// Removes account, code and all access keys and gas keys associated to it.
```rust
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
```

```rust
pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
```

**File:** protocol-model/spec/cross-shard-congestion.md (L299-307)
```markdown
**Timeouts** are the last step of `process_receipts`:
`resolve_promise_yield_timeouts` (`lib.rs:2986`) walks the `PromiseYieldTimeout` queue
in `expires_at` order, stopping at the first entry with `expires_at >
block_height` (`:3019`) or once the compute/proof-size budget is hit (`:3003`). For
each expired entry whose yield still exists, it synthesizes a `PromiseResume` with
`data: None` destined for the same (local) account and forwards/buffers it
(`:3037-3074`); the timeout is then dequeued (`:3078`). The timeout resume and any
real resume are ordered to the same shard, so a late timeout after a real resume is
simply discarded.
```
