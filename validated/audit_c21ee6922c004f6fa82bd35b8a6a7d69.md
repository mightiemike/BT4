### Title
Zero-Weight Reward Set Sets Signer Approval Threshold to 0, Allowing Blocks to Be Accepted With No Signatures - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoBlockHeader::verify_signer_signatures` derives the required signature weight from `RewardSet::total_signing_weight()` and `NakamotoBlockHeader::compute_voting_weight_threshold`. If the reward set computed for a cycle ends up with signer entries whose weights all round down to zero (a known degenerate mode of the "floor-and-drop" weight-apportionment scheme still used by `StacksChainState::make_signer_set`/`make_reward_set` for PoX-4), `total_signing_weight()` returns `0`, and `compute_voting_weight_threshold(0)` also returns `0`. A Nakamoto block with **zero signer signatures** then satisfies `total_weight_signed (0) < threshold (0) == false`, so it is accepted as validly signed — bypassing the entire signer-approval mechanism.

### Finding Description
`StacksChainState::make_signer_set` (`stackslib/src/chainstate/stacks/boot/mod.rs:1020-1072`) apportions weight per signing key as `stacked_amt / threshold`, dropping (filtering out) any entry whose weight floors to 0: [1](#0-0) 

This is exactly the "floor-and-drop" scheme that the codebase's own regression test documents as broken when there are more distinct signers than reward slots with comparable stake — every signer's weight floors to 0 and the *entire* signer set is dropped: [2](#0-1) 

For PoX-5 this was fixed with a largest-remainder ("Hare") apportionment plus an explicit guard that aborts block production if the resulting signer set is empty: [3](#0-2) 

However, the PoX-4 path (`pox_4_compute_and_update_signers`) still calls the old, unguarded `make_reward_set`/`make_signer_set`, and performs **no equivalent empty/zero-weight check**: [4](#0-3) 

If this produces `RewardSet::V0` with `signers: Some(vec![])` (or, more generally, a signer set whose weights sum to 0), then `RewardSet::total_signing_weight()` returns `0`: [5](#0-4) 

That `0` flows into `verify_signer_signatures`: [6](#0-5) 

and into `compute_voting_weight_threshold`, which for `total_weight = 0` computes `threshold = 0`: [7](#0-6) 

The equality that is supposed to be enforced — "a block is validly signed only if signed weight ≥ threshold, where threshold is derived from a nonzero, meaningfully-populated signer set" — degenerates to `0 ≥ 0`, which is trivially true even for a block carrying an **empty** `signer_signature` vector. This is the direct structural analog of the reported ERC-4626 issue: a boundary condition (`total_signing_weight == 0`, analogous to `totalSupply == 0`) collapses the ratio/threshold check to a value that lets an attacker (here, a miner or the party controlling PoX-4 stacking spread) satisfy the "≥ threshold" comparison without contributing anything of substance (zero valid signer approvals, analogous to receiving shares essentially for free).

### Impact Explanation
If reached, this breaks the core Nakamoto consensus invariant that a block must be approved by signers holding at least 70% of signing weight before it is treated as valid. With `threshold == 0`, `verify_signer_signatures` returns `Ok(0)` for a block with no signatures at all, meaning the miner alone can produce a "signed" block that every node will accept as valid — a network-wide acceptance of an unauthorized/invalid block. Per the impact rubric this is Critical: an invalid block accepted network-wide, undermining the block-approval mechanism entirely (potential for chain splits versus honest signers who refuse to build on such a block, and effectively silent removal of the signer security layer for that cycle).

### Likelihood Explanation
This does not require compromising a signer key or node-operator/admin privileges — it is a pure consequence of the reward-set weight computation for a given PoX-4 cycle. It requires that the PoX-4 stacker/signer registration for a cycle be structured (many distinct signing keys, each below `stacked_amt/threshold`) such that every entry's floor-divided weight is 0 — precisely the scenario the codebase's own regression test (`equal_stakes_exceeding_reward_slots_are_not_all_zeroed`) demonstrates causes total collapse under the old scheme. Because `pox_4_compute_and_update_signers` (unlike its PoX-5 counterpart) has no guard against this, and because low/fragmented participation reward cycles are a realistic PoX-4 condition (especially in low-activity periods or as a deliberate registration strategy by a large stacker splitting funds across many signing keys), the precondition is plausible without needing majority hash power or Sybil control of the whole network.

### Recommendation
- Add the same non-empty/non-zero-weight guard used in `pox_5_compute_and_update_signers` to `pox_4_compute_and_update_signers` (and any other caller of `StacksChainState::make_signer_set`/`make_reward_set` that feeds into `RewardSet` used for signature verification): abort reward-cycle computation (or fall back to "no PoX/no signer" behavior with explicit chain-halt semantics rather than a silent zero-weight cycle) if the derived signer set is empty or `total_signing_weight() == 0`.
- In `NakamotoBlockHeader::verify_signer_signatures` / `compute_voting_weight_threshold`, explicitly reject (rather than silently compute a `0` threshold) when `total_weight == 0`, since a reward set with zero signing weight can never legitimately authorize a block.
- Port the largest-remainder (Hare) apportionment scheme used for PoX-5 signer sets to the PoX-4 code path, or otherwise ensure the floor-and-drop scheme cannot zero out an entire signer set for cycles still on PoX-4.

### Proof of Concept
1. Arrange a PoX-4 reward cycle where the total stacking participation is dominated by more distinct signing keys than `reward_slots`, each with roughly equal (small) stacked amounts, such that `threshold_precise = scale_by / reward_slots` exceeds every individual `stacked_amt` (mirrors the exact setup in `equal_stakes_exceeding_reward_slots_are_not_all_zeroed`, but exercised through `pox_4_compute_and_update_signers` → `StacksChainState::make_reward_set` → `make_signer_set` instead of the guarded `pox_5_make_signer_set`).
2. `make_signer_set` filters out every entry because `stacked_amt / threshold == 0` for all of them, yielding `signers: Some(vec![])` in the resulting `RewardSet`.
3. `RewardSet::total_signing_weight()` returns `0`; no empty-set guard exists in `pox_4_compute_and_update_signers` to reject this cycle.
4. A miner proposes (or self-signs) a Nakamoto block for this reward cycle with `signer_signature = vec![]`.
5. `verify_signer_signatures` computes `total_weight = 0` → `threshold = compute_voting_weight_threshold(0) = 0`; the loop over `self.signer_signature` never executes, leaving `total_weight_signed = 0`; the check `total_weight_signed (0) < threshold (0)` is `false`, so the function returns `Ok(0)` — the block is accepted as validly signed by every node evaluating it, despite carrying zero signer approvals.

            return Err("Unable to calculate total weight - No signers in reward set".to_string());

        Ok(signers.iter().map(|s| s.weight).fold(0, |s, acc| {

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
