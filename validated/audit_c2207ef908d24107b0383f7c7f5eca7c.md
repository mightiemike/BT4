This confirms the analog: in NEAR meta-transactions (NEP-366), the relayer prepays deposits for inner actions in a `DelegateAction`, but if the inner action fails, the deposit refund is issued to the delegate's `sender_id` (the predecessor of the inner receipt) rather than to the relayer who actually paid for it. ### Title
Relayer-funded deposit in meta-transactions is refunded to the delegate sender instead of the paying relayer on inner-action failure - (File: `runtime/runtime/src/actions.rs`)

### Summary
When a relayer submits a `DelegateAction`/`DelegateV2` meta-transaction (NEP-366) that includes an inner action with an attached deposit (e.g. `Transfer` or `FunctionCall` with `deposit`), the relayer is the one who actually pays that deposit out of its own account balance. If the inner action's receipt subsequently fails on the receiver's shard, the protocol issues a `deposit_refund` balance-refund receipt to the failed receipt's `predecessor_id`, which is the delegate's `sender_id` (the user who signed the `DelegateAction`), not the relayer who funded it.

### Finding Description
`apply_delegate_action` in [4](#0-3)  constructs the inner receipt with `predecessor_id: sender_id.clone()` (the delegate sender, e.g. "Alice"), while the relayer only appears as `signer_id`/`signer_public_key`. The code comment explicitly states: "Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit."

The deposit-refund path (`refund_unspent_gas_and_deposits`, [5](#0-4) ) computes `deposit_refund = total_deposit` when `result.result.is_err()`, and pushes `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)` ( [6](#0-5) ). Per the documented deposit-refund model in [7](#0-6) , "All attached deposit amounts are summed together and sent as a refund to a `predecessor_id`" — which for the inner delegated receipt is `sender_id`, not the relayer.

This is the same bug class as the original report: a party that fronts funds for an operation on behalf of a third party has the leftover/failed value routed to that third party's chosen address instead of back to the funder. `docs/architecture/how/meta-tx.md` explicitly documents this consequence: "what if the transaction fails execution on Bob's shard? At this point, the predecessor is Alice and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard" ( [8](#0-7) ).

### Impact Explanation
A malicious `sender_id` can craft a `DelegateAction` whose single receiver-shard action is guaranteed (or made likely, e.g., via a contract callback, insufficient gas, or a receiver-side condition the sender controls) to fail after the relayer has already fronted the deposit balance from its own account (deducted via `total_deposit`, [9](#0-8) , and burnt against the relayer's shard balance per NEP-366's cost model). Because the deposit-refund receipt's receiver is `sender_id` and not the relayer, the sender receives back tokens that were never actually theirs — resulting in unauthorized value movement from the relayer to the malicious sender. This directly matches the original report's "loss of funds" impact for the party who fronted the funds, with the attacker (sender) able to choose or influence the failure condition.

### Likelihood Explanation
Reachable purely by submitting a signed `DelegateAction`/`DelegateV2` off-chain to any relayer that accepts general meta-transactions and having the relayer wrap and submit it in a transaction — no validator or node compromise is required. The attacker (malicious "sender") only needs to design an inner action whose execution predictably fails at the receiver contract (e.g., targeting a receiver account/contract that will reject the call, or a call with insufficient/borderline attached gas that the attacker controls the parameters of within the delegate action they authored) while ensuring the relayer still funds the deposit. This is explicitly called out as a known risk in the docs, indicating it is a real, currently-present behavior rather than a hypothetical.

### Recommendation
Track the actual balance-refund receiver separately from `predecessor_id` for delegate-originated receipts — e.g., populate `refund_to` (already present in `ActionReceiptV2`, see [10](#0-9)  and the `set_refund_to`/`promise_refund_to` mechanism in [11](#0-10) ) with the relayer's account for the inner delegated receipt, so that on failure the deposit refund routes back to whichever account (relayer) actually supplied the attached deposit, consistent with how gas refunds already correctly go to the relayer as `signer_id`.

### Proof of Concept
1. Relayer R receives a `SignedDelegateAction` from sender S with `sender_id = S`, `receiver_id = C` (some contract), and a single inner action `FunctionCall { method_name, deposit: D, gas: G }` where S has crafted the call to a method/contract state that S knows will fail (e.g., a nonexistent method, or a method that reverts under conditions S controls).
2. R wraps this in a transaction as signer, submits it. R's account is debited D (attached deposit) plus gas costs, per `apply_delegate_action` and the cost accounting in [12](#0-11) .
3. The generated inner receipt has `predecessor_id: sender_id` (S) per [13](#0-12) .
4. Execution on C's shard fails as designed by S.
5. `refund_unspent_gas_and_deposits` computes `deposit_refund = total_deposit` and issues `Receipt::new_balance_refund` to `receipt.balance_refund_receiver()`, which resolves to the receipt's predecessor S, not relayer R ( [14](#0-13) ).
6. S's balance increases by D even though R paid for D; R has no recourse on-chain.

## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.

    fn refund_unspent_gas_and_deposits(
        &self,
        gas_burn_price: Balance,
        gas_purchase_price: Balance,
        receipt: &Receipt,
        action_receipt: &VersionedActionReceipt,
        result: &mut ActionReceiptResult,
        config: &RuntimeConfig,
        created_account: bool,
        protocol_version: ProtocolVersion,
    ) -> Result<GasRefundResult, RuntimeError> {
        let total_deposit = total_deposit(&action_receipt.actions())?;
        let prepaid_gas = total_prepaid_gas(&action_receipt.actions())?
            .checked_add(total_prepaid_send_fees(config, &action_receipt.actions())?.gas)
            .ok_or(IntegerOverflowError)?;
        let prepaid_exec_gas =
            total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
                .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee())
                .ok_or(IntegerOverflowError)?;
        let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
        let gross_gas_refund = if result.result.is_err() {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_burnt)
                .unwrap()
        } else {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_used)
                .unwrap()
        };

        // NEP-536 also adds a penalty to gas refund.
        let refund_penalty: Gas = config.fees.gas_penalty_for_gas_refund(gross_gas_refund);
        let penalty_gas_price = if ProtocolFeature::AccountCostIncrease.enabled(protocol_version) {
            gas_burn_price
        } else {
            gas_purchase_price
        };
        let refund_penalty_amount = safe_gas_to_balance(penalty_gas_price, refund_penalty)?;

        // Refund for the leftover gas that was not used by this receipt.
        let unused_gas_balance_refund = safe_gas_to_balance(gas_purchase_price, gross_gas_refund)?
            .saturating_sub(refund_penalty_amount);

        let mut gas_refund_result = GasRefundResult {
            price_deficit: Balance::ZERO,
            price_surplus: Balance::ZERO,
            refund_penalty: refund_penalty_amount,
            create_account_charge: Balance::ZERO,
        };

        if gas_burn_price > gas_purchase_price {
            // price increased, burning resulted in a deficit
            gas_refund_result.price_deficit = safe_gas_to_balance(
                gas_burn_price.checked_sub(gas_purchase_price).unwrap(),
                result.gas_burnt,
            )?;
        } else {
            // price decreased, burning resulted in a surplus
            gas_refund_result.price_surplus = safe_gas_to_balance(
                gas_purchase_price.checked_sub(gas_burn_price).unwrap(),
                result.gas_burnt,
            )?;
        };

        // Refund for the price difference between gas_purchase_price and gas_burn_price of the gas burned in this receipt.
        let mut burned_gas_refund =
            if ProtocolFeature::AccountCostIncrease.enabled(protocol_version) {
                gas_refund_result.price_surplus
            } else {
                Balance::ZERO
            };

        // If an account was created, charge more to cover its cost.
        if created_account && ProtocolFeature::AccountCostIncrease.enabled(protocol_version) {
            // This is how much creating an account should cost
            let desired_cost = config.account_creation_charge;

            let create_account_gas_cost =
                config.fees.fee(ActionCosts::create_account).exec_fee().gas;
            // The cost of the gas that was burned already
            let burned_cost = safe_gas_to_balance(gas_burn_price, create_account_gas_cost)?;

            // We would like to charge as much as needed to reach desired_cost
            let amount_to_charge = desired_cost.saturating_sub(burned_cost);

            // We can't charge more than `burned_gas_refund`.
            // `burned_gas_refund < amount_to_charge` could happen for receipts where the gas was
            // purchased in protocol versions before `ProtocolFeature::AccountCostIncrease`, at a lower
            // gas price that isn't enough to cover the cost of creating an account.
            let amount_actually_charged = std::cmp::min(amount_to_charge, burned_gas_refund);

            // sanity check: purchasing gas at `min_gas_purchase_price` should be enough to cover
            // the cost of creating an account.
            debug_assert!(
                safe_gas_to_balance(config.min_gas_purchase_price, create_account_gas_cost)
                    .unwrap()
                    >= desired_cost
            );

            // sanity check: as long as the purchase price is high enough, there should always be
            // enough refund balance to cover the cost of creating an account.
            if gas_purchase_price >= config.min_gas_purchase_price {
                debug_assert!(burned_gas_refund >= amount_to_charge);
            }

            // Subtract `amount_actually_charged` from the refund.
            gas_refund_result.create_account_charge = amount_actually_charged;
            burned_gas_refund = burned_gas_refund
                .checked_sub(amount_actually_charged)
                .expect("burned_gas_refund >= amount_actually_charged checked above");
        }

        let gas_balance_refund = safe_add_balance(unused_gas_balance_refund, burned_gas_refund)?;

        if deposit_refund > Balance::ZERO {
            result.new_receipts.push(Receipt::new_balance_refund(
                receipt.balance_refund_receiver(),
                deposit_refund,
            ));
        }
