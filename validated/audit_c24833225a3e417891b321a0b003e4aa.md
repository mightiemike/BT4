### Title
`ensure_match_transaction_info` skips state/hot-state checkpoint hash verification, letting replay-verify tooling accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole verification routine used by Aptos's replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that locally re-executed transactions match the transaction infos recorded in the authenticated, on-chain-committed transaction accumulator. The function checks status, gas used, write-set hash, and event-root hash, but never compares `state_checkpoint_hash` or `hot_state_checkpoint_hash` (both real, already-used `TransactionInfo` fields) against the locally computed values. A divergence in the state Merkle root produced by local re-execution is therefore silently accepted as a successful replay.

### Finding Description
`TransactionInfo` carries `state_checkpoint_hash` (and, for V1, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) as committed, authenticated fields that bind a version's state to the transaction accumulator root that consensus and every full/light node verify against a signed `LedgerInfo`. `types/src/transaction/mod.rs` lines 2139–2204 implements `ensure_match_transaction_info`, the exact function relied on to validate a locally re-executed `TransactionOutput` against the historical, tamper-evident `TransactionInfo` retrieved from backup/archive storage: [1](#0-0) 

It validates status, gas, `write_set_hash` against `state_change_hash`, and `event_root_hash`, but the function's own trailing comment admits the gap: [2](#0-1) 

This function is the only correctness check performed in `Verifier::execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs`, which re-executes historical transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` per transaction to decide pass/fail: [3](#0-2) 

Because `state_checkpoint_hash` and `hot_state_checkpoint_hash` are never compared, any bug in local execution or in the state-tree/hot-state materialization logic that corrupts the computed state root — without also altering the write-set bytes or event bytes for that specific transaction — will go completely undetected by this tool, even though the state root is precisely the value that binds a version's data to the authenticated ledger (accumulator root -> `LedgerInfo` -> validator signatures).

### Impact Explanation
Replay-verify (`replay_on_archive`) and the debugger's replay path are the primary tools operators, auditors, and incident responders use to confirm that an archived/backed-up ledger's execution matches the authenticated chain history and to detect state-root divergence bugs (including hard-fork-class VM bugs) after the fact. Because the checkpoint-hash fields are skipped, this tool can report "successful replay" while the actual state-commitment (state Merkle root) diverges from the canonical, consensus-verified value — defeating the purpose of the tool for exactly the class of bug (silent state corruption without a divergent write set for the checkpoint transaction) it exists to catch. This directly matches the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result" impact classes, since a mismatch here indicates the replayed chain no longer produces the authenticated state root but is reported as verified.

### Likelihood Explanation
This is not a hypothetical: `state_checkpoint_hash` is a real, currently-populated field on every checkpoint `TransactionInfo` (independent of the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature referenced in the comment for `position_state_checkpoint_hash`), and the omission is unconditional in `ensure_match_transaction_info` — it is not guarded by any feature flag for the `state_checkpoint_hash`/`hot_state_checkpoint_hash` case. Any execution or state-checkpoint-hash computation bug (e.g., in `do_state_checkpoint.rs`'s hashing of the resulting state tree, or a JMT/SMT computation error) that changes the resulting state root but not the specific write set of the checkpoint transaction will pass replay-verify silently.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally computed `state_checkpoint_hash` (and, where applicable, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against the corresponding fields on `txn_info`, using the version's actual checkpoint hash computed the same way `do_state_checkpoint.rs` does it, and fail replay verification on mismatch (removing the current TODO-gated bypass).

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap demonstrable by code inspection: construct a `TransactionOutput` whose write set/events match `expected_writeset`/`expected_events` but whose associated state-checkpoint transaction produces a different state root (e.g., by feeding `execute_and_verify` an `expected_txn_infos[idx].state_checkpoint_hash` that differs from the hash actually computed by `DoStateCheckpoint` for the locally executed state), and observe that `ensure_match_transaction_info` returns `Ok(())` because the comparison is never performed.
