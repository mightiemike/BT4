### Title
Sierra compiler subprocess temp-file path leaked to unprivileged declare senders via compilation error messages - (File: crates/apollo_compilation_utils/src/compiler_utils.rs)

### Summary
When a `declare` transaction's Sierra class fails to compile, the sequencer invokes an external compiler binary against a `NamedTempFile` and forwards the subprocess's raw `stderr` (after light filtering) back through `CompilationUtilError::CompilationError` → `SierraCompilerError::CompilationFailed` → `ClassManagerError::SierraCompiler` → `StarknetError` to the RPC/gateway client that submitted the declare. This is analogous to CVE-2013-7060 (Plone), where a filesystem path embedded in a server-side object/error was exposed to a remote, unprivileged caller, revealing installation/runtime path information (CWE-200).

### Finding Description
`compile_with_args` serializes the submitted Sierra class into a `NamedTempFile` and passes the file's absolute path as an argument to the external Cairo/Sierra compiler binary: [1](#0-0) 

If the compiler process exits with failure, the function captures the subprocess's `stderr`, passes it through `extract_error_from_stderr`/`format_compiler_error`, and returns it as the error string: [2](#0-1) 

`extract_error_from_stderr` only strips resource-limit setup lines and stack-backtrace headers/frames; it performs no filtering of absolute filesystem paths (e.g. `/tmp/.tmpXXXXXXXX`, `/data/...`, or container path fragments) that the compiler binary may echo back in its diagnostics (compilers commonly quote the input file path in error/panic output): [3](#0-2) 

This raw string is wrapped as `CompilationUtilError::CompilationError(String)`: [4](#0-3) 

...propagated into `SierraCompilerError::CompilationFailed`: [5](#0-4) 

...and ultimately converted into a client-facing `StarknetError` whose `message` is `err.to_string()` — i.e., the same unfiltered text, including any leaked path — for the `SierraCompiler`/`CompilationFailed` class-manager error variant: [6](#0-5) 

This path is directly reachable by any unprivileged account submitting a `Declare` transaction through the gateway's `add_tx_inner` flow, which invokes Sierra→CASM compilation as part of converting the RPC transaction: [7](#0-6)

### Impact Explanation
An attacker who submits a crafted (invalid) Sierra class in a `Declare` transaction can trigger compiler failures whose stderr output — potentially including the absolute path of the sequencer-side temporary file (revealing local filesystem layout, temp-directory naming conventions, container/user paths, or deployment specifics) — is returned verbatim in the API error response. This is a CWE-200 information disclosure: it does not directly cause fund loss or consensus divergence, but it discloses internal infrastructure details (matching the "Medium" classification and impact profile of the referenced CVE-2013-7060 analog) that can aid further targeted attacks (e.g., fingerprinting deployment environment, container escape reconnaissance, or resource-limit tuning bypass attempts).

### Likelihood Explanation
High likelihood of triggering compiler failures (declares with malformed Sierra are trivial and cheap to construct), and the code path performs no path-redaction/sanitization on subprocess stderr before returning it to the client — only backtrace/resource-log filtering is present, as shown in `extract_error_from_stderr`. Any external declare sender can reach this without special privileges, matching the "unprivileged transaction sender" reachability requirement.

### Recommendation
Sanitize `compile_with_args`'s stderr before surfacing it to clients: strip or redact absolute filesystem paths (e.g., regex-replace `/[^\s]*tmp[^\s]*` or any path matching the temp file's directory) and avoid echoing the full subprocess stderr for `CompilationError`/`UnexpectedError` variants that reach `StarknetError.message`. Consider returning a generic "Sierra compilation failed" message to callers while logging the full unredacted stderr server-side only (similar to how `StarknetError::internal_with_logging` already redacts internal errors from client responses).

### Proof of Concept
1. Submit a `Declare` (v2/v3) transaction with a syntactically-invalid or truncated Sierra program (e.g., as done in `get_faulty_test_contract` in the test suite, which truncates `sierra_program`).
2. The gateway routes the tx through `add_tx_inner` → class manager → `SierraCompiler::compile` → `SierraToCasmCompiler::compile` → `compile_with_args`, which writes the payload to a `NamedTempFile` and invokes the external `starknet-sierra-compile` binary against that path.
3. If the compiler binary's diagnostic output includes the input file path (a common compiler behavior for parse/panic errors referencing the source path), that path is preserved by `extract_error_from_stderr` (which only filters resource-setup/backtrace lines) and returned as `CompilationUtilError::CompilationError(stderr)`.
4. This string flows unmodified into the `StarknetError.message` returned to the RPC caller for `KnownStarknetErrorCode::CompilationFailed`, exposing the local file path to the transaction submitter.

Note: I could not execute the compiler binary to confirm which exact error strings it emits (e.g., whether it always includes the temp path on all failure modes), since I only have read access to the repository index, not a runtime environment. This should be verified with an actual compiler invocation in a Devin session to confirm the precise leaked substrings.

/// Extracts the meaningful error lines from compiler stderr, filtering out stack backtraces and
/// resource limit setup messages.
fn extract_error_from_stderr(stderr: &str) -> String {
    let meaningful_lines: Vec<&str> = stderr
        .lines()
        .filter(|line| {
            let trimmed = line.trim();
            // Skip resource limit setup lines (e.g., "Setting Resource::CPU limits: ...").
            if trimmed.starts_with("Setting Resource::") {
                return false;
            }
            // Skip stack backtrace header and frames (e.g., "0: module::path").
            if trimmed.eq_ignore_ascii_case("stack backtrace:")
                || trimmed.starts_with("Signal info:")
            {
                return false;
            }
            if let Some(rest) = trimmed.strip_prefix(|c: char| c.is_ascii_digit()) {
                let rest = rest.trim_start_matches(|c: char| c.is_ascii_digit());
                if rest.starts_with(':') {
                    return false;
                }
            }
            !trimmed.is_empty()
        })
        .collect();

    if meaningful_lines.is_empty() {
        return "Compilation failed with no meaningful error output".to_string();
    }

    meaningful_lines.join("\n")
}
