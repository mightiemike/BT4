## Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/archive tooling accept a divergent authenticated state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/cli/src/commands.rs` as the sole correctness gate for replay-verification against archived/authenticated `TransactionInfo`) checks transaction status, gas used, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is a self-acknowledged gap in the code itself.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates status, gas_used, write_set hash and event_root_hash against the authenticated `TransactionInfo`, but the function ends with:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [2](#0-1) 

This function is the exclusive verification step used by the replay-verify tool that recomputes execution against a real archive and checks it against the authenticated `TransactionInfo` fetched from backup storage: [3](#0-2) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class fields bound into the transaction-accumulator leaf hash (i.e., they are part of the authenticated, proof-bearing commitment): [4](#0-3) 

These same fields are computed independently during normal execution in `assemble_transaction_infos` (state checkpoint hash, hot state checkpoint hash, position state checkpoint hash are all folded into the committed `TransactionInfo`): [5](#0-4) 

Because `ensure_match_transaction_info` never re-derives or compares these checkpoint hashes against the locally-recomputed state during replay, a divergence between the archived/authenticated commitment and a node's local re-execution in exactly these fields — the state root, hot-state root, or (newly added) "trading-native" position-state root — will not be detected by replay-verify. The `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag (referenced in the TODO) gates a still-in-development "native position" state root subsystem (`execution/executor/src/workflow/do_state_checkpoint.rs`, `execution/executor-types/src/execution_output.rs`, `types/src/on_chain_config/aptos_features.rs`), meaning this checkpoint-hash blind spot is present precisely in the newest state-commitment surface being added to the ledger.

### Impact Explanation
Replay-verify / archive-based auditing (`db-tool replay-on-archive`) is a core state-integrity tool: it is meant to detect exactly the class of bug this task is scoped to catch — "committed state that differs from the correct VM result" and "hard-fork-only divergence during commit, replay ... verification." Because the comparator omits the checkpoint-hash fields, a bug in state-checkpoint/hot-state/position-state root computation (a genuine consensus/commit-path defect, a storage corruption, or a malicious archive provider serving transaction outputs with a tampered but internally-consistent write-set/event/status but wrong checkpoint root) would pass `ensure_match_transaction_info` and be reported as a successful, verified replay. This masks state-root corruption that the tool exists specifically to catch, undermining confidence in the ledger's authenticated root when this tool is relied on for validation/dispute-resolution/hard-fork-divergence detection. This is a proof-integrity gap: an authenticated, proof-bearing value (`state_checkpoint_hash` inside `TransactionInfo`, which feeds the accumulator root used for all Merkle/state proofs) is silently excluded from the verifier's decision.

### Likelihood Explanation
The gap is unconditional and always active today — it is not behind a flag; the flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS` only governs whether the position-state root is *computed and populated* at all, not whether `ensure_match_transaction_info` validates it. So even for the already-shipped `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields, the comparator has always ignored them, and the code's own comment says so directly. Any replay-verify run (used in production/backup validation and by developers/auditors) using this comparator today does not confirm state-checkpoint agreement, only write-set and event agreement, so this can trigger whenever an execution-path bug produces a wrong checkpoint hash while otherwise reproducing status/gas/write-set/events identically (e.g., an in-memory SMT/JMT update-order bug, a stale summary bug in `do_state_checkpoint.rs`, or corrupted archived bytes for the checkpoint field only).

### Recommendation
Extend `ensure_match_transaction_info` to recompute (or accept as a parameter) the locally-derived `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` and assert equality against `txn_info.state_checkpoint_hash()` / `.hot_state_checkpoint_hash()` / `.position_state_checkpoint_hash()` whenever these are present in `TransactionInfoV1`, mirroring the pattern already used for `state_change_hash` and `event_root_hash`. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, per the existing TODO, but the state/hot-state checkpoint validation gap should be closed immediately regardless of that flag.

### Proof of Concept
No executable PoC is available/verifiable from static code review alone — the flaw is demonstrated directly by the code path itself:
1. `replay_on_archive.rs::execute_and_verify` re-executes the transaction block and calls `TransactionOutput::ensure_match_transaction_info(version, expected_txn_info, ...)` as the only pass/fail gate (lines 392–405).
2. `ensure_match_transaction_info`'s implementation (types/src/transaction/mod.rs, lines 2139–2204) checks only `status`, `gas_used`, `write_set_hash`, and `event_root_hash`, then returns `Ok(())` unconditionally with respect to `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, as documented by the inline TODO.
3. Therefore, constructing (or reproducing via replay) any two `TransactionOutput`s with identical status/gas/write-set/events but different underlying state roots is sufficient to have replay-verify report success despite a real state-commitment divergence. I was not able to execute this scenario in the sandbox (no filesystem/test-runner access here), so this should be validated with an integration test that feeds `execute_and_verify` a crafted `TransactionInfo` with a mismatched `state_checkpoint_hash` and confirms no error is raised.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
