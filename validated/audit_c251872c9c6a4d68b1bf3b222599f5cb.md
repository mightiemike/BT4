## Analysis

The NMKT‑7 bug class is about an eligibility/permission gate that is keyed to a piece of *mutable* state (NFT ownership) rather than to the original grant of the right, so a state change unrelated to intent can permanently deny a legitimate action. The Push Chain analog I found is the **rescue-funds eligibility gate**, which is keyed to the exact enum value `Status_REVERTED` on the auto-generated `INBOUND_REVERT` outbound, while the outbound state machine also has an `ABORTED` terminal state that the rescue check does not recognize.

### Relevant code

`AttachRescueOutboundFromReceipt` only allows a rescue outbound to be created for a non-CEA inbound if it finds an `INBOUND_REVERT` outbound whose `OutboundStatus == types.Status_REVERTED`: [1](#0-0) 

The `INBOUND_REVERT` outbound's status is set inside `handleFailedOutbound`. When the PRC20 re-mint call back to the (attacker-influenced) revert recipient fails, the outbound is diverted to `AbortOutbound` instead of ever reaching `Status_REVERTED`: [2](#0-1) 

The recipient used for that re-mint call is derived from `RevertInstructions.FundRecipient`, which is attacker-supplied data on the original inbound: [3](#0-2) 

### Title
Rescue-fund eligibility permanently blocked when re-mint on revert fails and outbound is diverted to ABORTED instead of REVERTED - (File: x/uexecutor/keeper/create_outbound.go, x/uexecutor/keeper/outbound.go)

### Summary
The rescue-funds recovery path (`AttachRescueOutboundFromReceipt`) is the only way to recover bridged funds for a non-CEA inbound whose auto-generated `INBOUND_REVERT` outbound could not be delivered back to the source chain. Eligibility is hard-gated on the outbound reaching exactly `Status_REVERTED`. However, `handleFailedOutbound` can instead leave the outbound in `Status_ABORTED` (via `AbortOutbound`) if the PRC20 re-mint call to the revert recipient fails. Because the recipient of that re-mint call is attacker-controlled (`RevertInstructions.FundRecipient` from the original inbound), an unprivileged user can construct an inbound whose revert path is guaranteed to hit the re-mint failure branch, forcing the outbound into `ABORTED` and permanently locking themselves — or, more importantly, permanently locking the module's bridged/vault funds — out of the only recovery mechanism the protocol exposes.

### Finding Description
`handleFailedOutbound` mints bridged tokens back to a revert recipient before marking the outbound `REVERTED`: [4](#0-3) 
If `CallPRC20Deposit` errors, the function calls `k.AbortOutbound(...)` and returns early — the outbound never reaches `Status_REVERTED`, and the function comment/behavior indicates this requires "manual intervention" that isn't wired to any completion path shown in the reachable rescue logic.

Rescue for non-CEA inbounds strictly requires an `INBOUND_REVERT` outbound with `OutboundStatus == types.Status_REVERTED`: [1](#0-0) 
There is no equivalent branch accepting `Status_ABORTED`. Since the recipient of the PRC20 re-mint (`recipient := outbound.Sender` overridden by `outbound.RevertInstructions.FundRecipient`) is populated straight from the original inbound's user-supplied `RevertInstructions`, an attacker fully controls this address. By pointing it at, e.g., a PRC20-hook/receiver contract engineered to always revert on `deposit`, the attacker deterministically forces `CallPRC20Deposit` to fail on the revert outbound, driving it into `ABORTED` rather than `REVERTED`.

This mirrors the NMKT‑7 pattern precisely: the authorization gate for a fund-recovery action ("rescue") depends on a specific mutable state value (`REVERTED`) that can diverge from the true "the funds are stuck and should be recoverable" condition (which is equally true for `ABORTED`), and an ordinary, unprivileged user input (a crafted revert recipient) can steer the state machine into the ungated branch.

### Impact Explanation
This blocks the only documented recovery mechanism for bridged/protocol-controlled PRC20 funds that failed to revert back to the source chain, resulting in **permanent freezing of user or protocol-controlled funds** — squarely in the "Allowed Impact" list (permanent freezing). Because the recipient is attacker-controlled, this is reachable by any ordinary user submitting an inbound with a malicious `RevertInstructions.FundRecipient`, with no privileged actor involved.

### Likelihood Explanation
Reaching the `ABORTED` branch requires: (1) the primary inbound execution to fail so an `INBOUND_REVERT` outbound is created, and (2) the re-mint call during that revert to itself fail. Both conditions are attacker-triggerable purely through crafted inbound/revert-instruction fields and a malicious PRC20-adjacent contract as the fund recipient, with no reliance on malicious validators, TSS, or admin actions — only on ordinary honest-validator processing of a crafted inbound.

### Recommendation
- Extend the rescue eligibility check in `AttachRescueOutboundFromReceipt` to also accept `Status_ABORTED` (or otherwise unify the "stuck, recoverable" states), or
- Ensure `AbortOutbound` triggers/permits a subsequent transition to `REVERTED` (e.g., via a follow-up admin/automatic retry that doesn't route the re-mint through the same failing recipient), so an attacker-controlled recipient cannot permanently strand funds outside of any recovery path.
- More generally, decouple "is this outbound recoverable" from a single terminal-status literal comparison, and audit all other status-gated recovery/eligibility checks for the same terminal-state coverage gap.

### Proof of Concept
1. Attacker submits a `FUNDS` (non-CEA) inbound with `RevertInstructions.FundRecipient` set to the address of an attacker-deployed contract implementing a PRC20 receiver hook that unconditionally reverts.
2. Attacker crafts the inbound so that execution fails (e.g., using an unsupported token config or an execution error path), causing `buildRevertOutbound`/`attachOutboundsToUtx` to create a `PENDING` `INBOUND_REVERT` outbound, per [5](#0-4) .
3. Validators vote the outbound as failed on the source chain (or the TSS broadcast itself fails on-chain), causing `handleFailedOutbound` to run.
4. `CallPRC20Deposit(ctx, prc20, attackerRecipient, amount)` reverts because the attacker's contract rejects the deposit, so `k.AbortOutbound(...)` is invoked and the outbound is left `ABORTED` rather than `REVERTED`, per [6](#0-5) .
5. Any later attempt to call the rescue flow (`AttachRescueOutboundFromReceipt`) for this UTX fails with `"rescue: UTX %s has no reverted inbound-revert outbound"` because the loop only recognizes `Status_REVERTED`, per [1](#0-0) , permanently freezing the bridged funds.

**Note on uncertainty**: I could not fully inspect the implementation of `AbortOutbound` itself (its file/line location was not returned by the index, only its usage sites in `x/uexecutor/keeper/outbound.go` and `x/uexecutor/types/outbound_tx.go`), so I cannot confirm with certainty whether some other admin-only or automated recovery path exists for `ABORTED` outbounds elsewhere in the codebase. If such a path exists and is reachable without additional preconditions, the severity of this finding would be reduced from "permanent freezing" to "delayed/degraded recovery requiring admin action." A Devin session with full file access should verify the complete `AbortOutbound` implementation and any downstream handling of `Status_ABORTED` before treating this as fully confirmed.

```go
// handleFailedOutbound mints back the bridged tokens to the revert recipient,
// then attempts to refund any excess gas (gasFee - gasFeeUsed) just like a
// successful outbound would. Both operations are recorded on the outbound.
func (k Keeper) handleFailedOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	// Only revert bridged funds for funds-related tx types
	if outbound.TxType == types.TxType_FUNDS || outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
		outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD {

		// Decide revert recipient safely
		recipient := outbound.Sender
		if outbound.RevertInstructions != nil &&
			outbound.RevertInstructions.FundRecipient != "" {
			recipient = outbound.RevertInstructions.FundRecipient
		}

		amount := new(big.Int)
		amount, ok := amount.SetString(outbound.Amount, 10)
		if !ok {
			return fmt.Errorf("invalid amount: %s", outbound.Amount)
		}
		receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)

		pcTx := types.PCTx{
			Sender:      outbound.Sender,
			BlockHeight: uint64(ctx.BlockHeight()),
		}
		// Capture tx hash from receipt even on EVM revert for debugging.
		if receipt != nil {
			pcTx.TxHash = receipt.Hash
			pcTx.GasUsed = receipt.GasUsed
		}
		if err != nil {
			pcTx.Status = "FAILED"
			pcTx.ErrorMsg = err.Error()
			outbound.PcRevertExecution = &pcTx
			// Re-mint failed — mark as ABORTED for manual intervention
			return k.AbortOutbound(ctx, utxId, outbound,
				fmt.Sprintf("failed to re-mint tokens for revert: %s", err.Error()))
		}
```
