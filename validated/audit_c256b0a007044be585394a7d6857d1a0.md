### Title
Replay-verify's `ensure_match_transaction_info` skips checkpoint-hash validation, letting divergent state/hot-state/position roots pass as "verified" - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the authenticated cross-check used by replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that locally re-executed transaction outputs match the `TransactionInfo` fields committed to the ledger accumulator. The function validates status, gas, write-set hash, and event-root hash, but the code itself documents that it intentionally omits comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the exact fields that bind execution output to the committed Sparse-Merkle/JMT state roots.

### Finding Description
`ensure_match_transaction_info` ( [1](#0-0) ) checks `status`, `gas_used`, and `write_set_hash` against the `TransactionInfo`, and separately checks `event_root_hash` [2](#0-1) . It then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or the `position_state_checkpoint_hash` — a gap that is explicitly called out in the trailing comment: "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution" [3](#0-2) .

This function is the sole per-transaction integrity gate used by the replay-verify tool: `Verifier::execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` calls `executed_outputs[idx].ensure_match_transaction_info(...)` and only records a mismatch/error if this call fails [4](#0-3) . The `TransactionInfo` fields it should be checking are produced by `DoLedgerUpdate::assemble_transaction_infos`, which populates `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from `DoStateCheckpoint` outputs [5](#0-4) , and `DoStateCheckpoint::run` computes the position-state root only when the `compute_trading_native_state_roots` (i.e. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) on-chain feature is enabled [6](#0-5) .

Because `ensure_match_transaction_info` never compares these checkpoint hashes, a local executor whose state-checkpoint/hot-state/position-state roots diverge from what was actually committed on-chain (due to a bug in state-checkpoint computation, JMT update logic, or a hard-fork-only code path) will still pass the replay-verify check as long as the write set, events, gas, and status happen to match. Replay-verify's whole purpose is to be the safety net that catches exactly this class of divergence before it's trusted as validated history.

### Impact Explanation
This is a proof/commit-integrity blind spot in the tool that is supposed to authenticate that committed ledger state equals correct VM execution results across the accumulator-proven `TransactionInfo`. A wrong `state_checkpoint_hash` (i.e., a wrong SMT/JMT state root, or wrong hot-state/position-state root) is exactly the class of "committed state that differs from the correct VM result" the audit gate calls out — and today's `ensure_match_transaction_info` cannot detect it. This does not itself corrupt state, but it removes the only automated detector for hard-fork-only state divergence and root corruption when replay-verify is used as the correctness oracle over archived/replayed history, allowing a silent chain-state divergence to go unnoticed via this tool.

### Likelihood Explanation
Medium-to-high for a "silent-miss" class bug: any divergence limited to state-checkpoint-related roots (as opposed to write-set/event/gas/status) is invisible to this check today, and the feature it explicitly targets (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, position-state roots) is a newly-introduced code path (per the comment, gated behind an on-chain feature not yet safely covered). The gap is self-documented as a known-missing validation ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), confirming it is a real, currently-live limitation rather than a hypothetical.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present), and `position_state_checkpoint_hash` (when present) between the locally computed values and the `TransactionInfo` under verification, returning an error on any mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any feature relying on these fields) is enabled on mainnet.

### Proof of Concept
Not applicable as a runtime exploit — the issue is a coverage gap in an offline verification tool: construct a `TransactionOutput` whose write set/events/gas/status match a given `TransactionInfo` but whose implied state-checkpoint/hot-state/position-state root differs (e.g., by mutating `state_checkpoint_hash` in the `TransactionInfo` while keeping write-set/event data constant) and observe that `ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2203` returns `Ok(())`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
