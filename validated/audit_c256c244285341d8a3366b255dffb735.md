The `timestamp` field is protected against array collisions but the canonicalization concatenation ambiguity in `stringifyQueryForAppProxy` remains exploitable for non-critical/custom keys and even for `logged_in_customer_id`/`path_prefix`, which are not in `APP_PROXY_SINGLE_VALUE_PARAMS`.

### Title
App Proxy HMAC canonicalization allows key/value boundary forgery, enabling `logged_in_customer_id` smuggling - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`validateHmac`'s App Proxy signature check reconstructs a canonical string by sorting query keys and concatenating `key=value` pairs **with no separator** between pairs, exactly mirroring how a raw ABI-encoded byte blob is consumed by `AllowedCalldataEnforcer` at a fixed offset without regard for how the boundaries of dynamic-length fields were actually determined. Because no delimiter (e.g. `&`) separates one `key=value` pair from the next, two structurally different query dictionaries can produce byte-identical canonical strings, and therefore identical valid signatures.

### Finding Description
`stringifyQueryForAppProxy` builds the string that is HMAC-signed/verified by joining sorted entries with no inter-pair separator: [1](#0-0) 

`normalizeQuery` only hardens the four "security" keys (`hmac`, `shop`, `signature`, `timestamp`) against being supplied as duplicate/array values: [2](#0-1) [3](#0-2) 

Because the canonical string has no reserved separator character between `key=value` pairs, a dictionary `{bar: "1", foo: "2"}` (canonical `"bar=1foo=2"`) and a dictionary containing only `{bar: "1foo=2"}` (canonical also `"bar=1foo=2"`, achievable on the wire via `?bar=1foo%3D2`) hash to the exact same HMAC input, and therefore the exact same valid signature for a given secret. This is structurally identical to the `AllowedCalldataEnforcer` flaw: a security check reads a fixed/positional interpretation of a byte sequence built from dynamic-length fields, but the *boundary* between fields is not itself protected by the encoding, so two semantically different inputs collapse to one verified representation.

`logged_in_customer_id` and `path_prefix` (the two app-proxy-specific fields that downstream app code trusts to identify a logged-in storefront customer and the mounted proxy path) are not part of `APP_PROXY_SINGLE_VALUE_PARAMS`, so they are not protected from this boundary-shifting collision the way `hmac`/`shop`/`signature`/`timestamp` were explicitly hardened (per the dedicated "App Proxy HMAC hardening" test suite): [4](#0-3) 

An attacker who has observed one legitimately Shopify-signed App Proxy URL (these are not secret — they appear directly in storefront-rendered links/requests, e.g. `?custom=X&logged_in_customer_id=42&shop=...&timestamp=...&signature=S`) can replay the identical `signature` value with a restructured query string in which `custom` and `logged_in_customer_id` are merged into a single, differently-keyed parameter (or vice-versa) whose canonical concatenation is byte-for-byte identical to the original. `validateHmac` will still return `true` for the replayed/restructured request because it only recomputes the HMAC over whatever dictionary it is handed — it never verifies that the dictionary's key/value partition is the *unique* one that could have produced that canonical string.

### Impact Explanation
This allows forging the presence/value/absence of the `logged_in_customer_id` field (and any other non-hardened app-proxy field) in a request that will still pass `validateHmac`, letting an attacker impersonate a different logged-in customer context (or fabricate one where none existed) to an app that trusts `logged_in_customer_id` from an "HMAC-validated" App Proxy request — a cross-tenant/customer-impersonation vector reachable by any anonymous visitor to a storefront.

### Likelihood Explanation
Exploitation requires the attacker to first observe one genuinely Shopify-signed App Proxy request/signature that contains an adjacent, attacker-influenced custom parameter next to `logged_in_customer_id` in sort order, then re-encode it with a shifted key/value boundary (e.g. using `%3D` inside a value) while replaying the same `signature`. This is possible without any secret knowledge, but does require the app to (a) expose a custom app-proxy parameter whose value the requesting customer controls, and (b) trust `logged_in_customer_id` for authorization decisions — a common but not universal pattern. Likelihood is moderate: no privileged access or secret leak is required, only crafting of query strings and observation of the app's own proxy traffic pattern.

### Recommendation
Change `stringifyQueryForAppProxy` (and the equivalent signing routine used by any app) to use an unambiguous, delimiter-based canonicalization (e.g. joining pairs with `\n` or `&`, or length-prefixing keys/values) so that no two distinct query dictionaries can ever canonicalize to the same byte string. Additionally, extend the `APP_PROXY_SINGLE_VALUE_PARAMS`-style hardening (or an explicit re-parse-and-compare step) to cover `logged_in_customer_id` and `path_prefix`, and reject any query values containing a literal `=` that could be reinterpreted as a key/value boundary when concatenated with a neighboring key.

### Proof of Concept
```ts
import crypto from 'crypto';
const secret = 'shhh';
const sign = (s: string) => crypto.createHmac('sha256', secret).update(s).digest('hex');

// "Legit" two-field canonical string Shopify would sign:
const canonicalTwoFields = 'bar=1foo=2'; // sorted: bar, foo
const legitSig = sign(canonicalTwoFields);

// Attacker-controlled single-field query that canonicalizes identically:
// on the wire: ?bar=1foo%3D2&signature=<legitSig>
const canonicalOneField = 'bar=1foo=2'; // same bytes, only "bar" key exists
console.log(sign(canonicalOneField) === legitSig); // true — signature replays across different key structures
```
Applied to the real App Proxy fields, replacing `bar`/`foo` with a controllable custom parameter and `logged_in_customer_id` demonstrates that `shopify.utils.validateHmac(query, {signator: 'appProxy'})` in [5](#0-4)  will accept a query whose `logged_in_customer_id` key/value boundary was shifted from an adjacent parameter, as long as the concatenated canonical bytes match a previously signed request.

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

    {signator}: {signator: HMACSignator} = {signator: 'admin'},
  ): Promise<boolean> => {
    const normalizedQuery = normalizeQuery(query, signator);

    if (signator === 'admin' && !normalizedQuery.hmac) {

        'Query does not contain an HMAC value.',
      );

        'Query does not contain a signature value.',
      );

      normalizedQuery,
      signator,
    );

  };

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }
