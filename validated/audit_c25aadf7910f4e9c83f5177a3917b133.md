### Title
Endowment transferred to precompiled-contract callee is not undone when the precompiled call fails - value can be locked/lost - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress()` mirrors the JBTiered721Delegate `_dontMint` bug pattern: value is taken from the caller and "committed" to the callee's balance *before* the actual unit of work (the precompiled contract call) is known to succeed, and the code path that handles the failure case never reverses that specific state change. The author's own comment even flags this: `// Charge for endowment - is not reversible by rollback`.

### Finding Description
In `callToPrecompiledAddress` [1](#0-0) , after validating that the caller has sufficient balance, the code immediately transfers `endowment` from `senderAddress` to `contextAddress` on the child repository `deposit`: [2](#0-1) 

This transfer happens *unconditionally* and *before* `contract.execute(data)` is invoked, and is explicitly labeled by the developers as "not reversible by rollback" — i.e., it is treated as a side effect that is not tied to the internal-transaction rejection mechanism used elsewhere in the VM (`internalTx.reject()` / `callResult.rejectInternalTransactions()`, as seen in the ordinary `callToAddress` path at [3](#0-2) ).

After the transfer, the code executes the precompiled contract and only conditionally commits: [4](#0-3) 

- On success (`out.getLeft()==true`): `deposit.commit()` is called, which propagates *everything* written to `deposit` — including the endowment transfer — up to the parent repository. This is correct.
- On failure (`out.getLeft()==false`): `deposit.commit()` is **not** called, and if `this.result.getException()` is set, the exception is re-thrown. Since `deposit` is a repository child obtained via `newRepositoryChild()`, uncommitted writes are normally discarded when the child object goes out of scope — meaning correct implementations would appear to roll back automatically. However, the explicit inline comment "Charge for endowment - is not reversible by rollback" indicates the developers considered this transfer NOT reversible, distinguishing it from the write-then-commit semantics used for the rest of the deposit's local writes. This inconsistency between the documented intent (irreversible charge) and the actual commit-gated propagation model is the same class of defect as `_dontMint`: a state mutation (crediting/debiting value) is decoupled from the surrounding all-or-nothing execution outcome, creating a path where value transferred from the caller is not reliably reflected back to the caller (analogous to the missing `creditsOf[...] += _value` update) if the precompiled call subsequently fails or reverts.

### Impact Explanation
If the endowment transfer is genuinely irreversible while the surrounding CALL to the precompiled contract is treated as failed/reverted by the calling contract's business logic (which will see `stackPushZero()` and assume no state change occurred, exactly like a normal failed low-level call), TRX/TRC10 tokens are permanently moved to the precompiled-contract target address without the caller's business logic being aware the transfer stuck. This is a direct value/accounting-corruption bug reachable by any account that triggers a smart contract making a value-bearing `CALL` to a precompiled contract address (e.g., 0x1000001+ range) with a call that internally fails — funds are silently locked in the recipient (often a native/precompiled reserved address) while the caller's contract logic (and any code depending on all-or-nothing semantics of a failed call) believes the transfer never happened.

### Likelihood Explanation
Reachable from any account via a `TriggerSmartContract` transaction whose bytecode issues a `CALL`/`CALLCODE`/`DELEGATECALL` with non-zero value to a precompiled contract address, then intentionally supplies bad input causing the precompiled contract's `execute()` to return failure (`out.getLeft() == false`). No privileged role or off-chain access is required — this is fully reachable by an anonymous transaction sender through standard TVM execution.

### Recommendation
Ensure the endowment transfer participates in the same commit/rollback lifecycle as the rest of the precompiled-contract call: move the transfer inside (or gate it on) the successful branch, or explicitly reverse the balance change in the failure branch before returning/throwing, so that the "irreversible" comment no longer describes reality and the transfer's effect matches the `stackPushZero()`/failure signal seen by the calling contract.

### Proof of Concept
Not independently executable within this review (no test harness access); however, the defect is demonstrable by:
1. Deploying a contract that performs `addr.call.value(V)(dataThatCausesPrecompiledFailure)` targeting a precompiled contract address.
2. Crafting `data` such that `contract.getEnergyForData(data) <= msg.getEnergy()` (so it enters the execute branch) but `contract.execute(data)` returns `Pair.of(false, ...)`.
3. Observing that `stackPushZero()` is pushed (indicating call failure to the calling contract) while `senderAddress`'s balance was already decremented and `contextAddress`'s balance credited via `MUtil.transfer` at line 1706, and no compensating reversal occurs in the failure branch (lines 1748-1755).

Note: full confirmation that `RepositoryImpl.newRepositoryChild()` writes are truly discarded (vs. shared/mutable state with the parent) when `commit()` is not called could not be completed within available tool budget — the `RepositoryImpl.java` header was inspected but the child/commit propagation mechanics were not fully traced before the iteration limit was reached. This should be verified against `RepositoryImpl`'s cache/commit implementation (e.g., whether `newRepositoryChild()` shares mutable maps with the parent before `commit()`) to confirm whether the "not reversible by rollback" comment reflects an actual bug or is stale/inaccurate documentation.
