### Title
Unbounded recursion in `get_recursive_transaction_results` allows transaction-triggered stack-overflow/crash of RPC-serving nodes - (File: `chain/chain/src/chain.rs`)

### Summary
`get_recursive_transaction_results` in `chain/chain/src/chain.rs` walks the outcome→`receipt_ids` graph of a transaction via **unbounded native recursion**, with no depth counter and no cycle/size guard, unlike the analogous `handle_receipt_to_tx` walker which enforces `RECEIPT_TO_TX_MAX_DEPTH = 1000` [1](#0-0) . This is reachable by any unprivileged caller who submits a transaction and then queries its status over JSON-RPC (`tx_status`) or via `EXPERIMENTAL_tx_status`, i.e. the RPC surface hit by `ViewClientActor::get_tx_status` → `Chain::get_partial_transaction_result_option`/`get_final_transaction_result` → `get_recursive_transaction_results` [2](#0-1) .

### Finding Description
`get_recursive_transaction_results` recursively descends into every `receipt_ids` entry of every outcome it finds, pushing to a shared `outcomes` vector and recursing once per receipt id without any depth limit: [3](#0-2) 

This is invoked from both the "wait for all outcomes" path, `get_final_transaction_result` [4](#0-3) , and the "best effort" path, `get_partial_transaction_result_option` [5](#0-4) . Both are reachable from `ViewClientActor::get_tx_status`, which is the direct backend for the public `tx_status` / `EXPERIMENTAL_tx_status` JSON-RPC methods, and is triggered simply by any account submitting a transaction and then querying its status: [6](#0-5) .

A single transaction can legitimately create a long, deep chain of receipts through nested `promise_then`/`promise_batch_then` callbacks — NEAR's async-callback model explicitly supports a "promise DAG" where a `FunctionCall` action can spawn a chain of receipts, each depending on the previous via `input_data_ids`/`output_data_receivers` [7](#0-6) . Because gas cost per hop can be kept relatively small (each hop just consumes send/exec fees, not the entire gas budget), an attacker can construct a transaction whose resulting receipt chain has thousands of hops — well beyond typical native stack recursion limits — well within a single transaction's gas allowance. This is directly analogous to the QEMU `xhci_ring_fetch` bug: an attacker-controlled chain of "descriptors" (there: TRB links; here: `SuccessReceiptId`/`receipt_ids` links) is walked without any bound, causing either an unbounded loop (QEMU) or unbounded stack recursion (nearcore) that crashes the process.

Notably, the codebase already recognizes this exact bug class and has fixed it in a sibling code path: `handle_receipt_to_tx` in `chain/client/src/view_client_actor.rs` explicitly bounds its own receipt-chain walk to `RECEIPT_TO_TX_MAX_DEPTH = 1000` and returns `GetReceiptToTxError::DepthExceeded` beyond that limit [1](#0-0) [8](#0-7) , but the older `get_recursive_transaction_results` used by the primary `tx_status`/`get_final_transaction_result` code path has no equivalent bound.

### Impact Explanation
Every honest RPC/validator node that services `tx_status` for the attacker's transaction, or that internally calls `get_final_transaction_result`/`get_partial_transaction_result_option` (used broadly for finalizing/serving user tx results), will attempt the same unbounded recursive walk. A sufficiently deep receipt chain can exhaust the call stack and crash the serving process (an availability/DoS impact triggered purely by a transaction a user submitted and then queried). Because every RPC node that tracks the relevant shard and serves this query independently performs the same recursive walk, this can degrade or crash multiple/all RPC nodes servicing that shard — a transaction-triggered halt of RPC service, not merely a single-node bug.

### Likelihood Explanation
Likelihood is Medium: it requires no privileged access, only (1) submitting one transaction that fans out into a deep promise chain (an unprivileged FunctionCall pattern any signer can construct), and (2) any subsequent `tx_status` query for that transaction hash (which the attacker themselves, or normal indexer/explorer/wallet infrastructure, will typically make automatically). The main uncertainty is the exact recursion depth needed to trigger a real stack overflow (dependent on stack frame size and thread stack size in the RPC binary), which could not be fully confirmed from static analysis alone.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative (explicit-stack or queue-based) traversal, and add an explicit depth/size bound analogous to `RECEIPT_TO_TX_MAX_DEPTH` used in `handle_receipt_to_tx`, returning a bounded error (e.g. a new `Error` variant) instead of recursing indefinitely.

### Proof of Concept
1. Submit a `FunctionCall` transaction whose contract logic issues a long chain of `promise_then`/`promise_batch_then` calls (e.g. via `near-sdk`/raw promise API), each hop cheap enough in gas to allow thousands of chained receipts within the transaction's/account's gas allowance.
2. After the chunks execute (receipts drained across chunks as delayed/incoming receipts per the documented `local → delayed → incoming` processing order [9](#0-8) ), call `tx_status`/`EXPERIMENTAL_tx_status` for the original transaction hash against an RPC node tracking that shard.
3. `ViewClientActor::get_tx_status` invokes `Chain::get_partial_transaction_result_option` → `get_recursive_transaction_results`, which recurses once per receipt hop with no depth bound, consuming stack proportional to chain length until the process stack is exhausted and the RPC node process crashes/aborts.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    pub fn get_partial_transaction_result_option(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<Option<FinalExecutionOutcomeView>, Error> {
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));

        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, false)?;
        if outcomes.is_empty() {
            // The transaction is in the store (included in a chunk) but its execution outcome has
            // not been recorded yet, so there is no result to assemble.
            return Ok(None);
        }

        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(Some(FinalExecutionOutcomeView {
            status,
            transaction,
            transaction_outcome,
            receipts_outcome,
        }))
    }

NEAR allows to create a promise DAG. A FunctionCall action can generate multiple receipts and order them to execute in some specified order, expressed as a DAG (directed acyclic graph).
In smart contracts, creating a `promise` spawns a `receipt`, the naming is a bit different, but under the hood it's the same thing.
The ordering is achieved by specifying data dependencies between the receipts, by manipulating the input_data_ids and output_data_receivers.
After executing a receipt, the result is sent out as a Data receipt to all of the specified output_data_receivers. The other receipts have this data in their input_data_ids and wait for the Data receipts to be sent before being executed.

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }
