### Title
Unbounded, non-deduplicated growth of the per-shop session ID index causes permanent DoS of session storage / OAuth in `KVSessionStorage` - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession()` maintains a secondary index (`shop:<shop>`) listing every session id ever stored for a shop, via the private `addShopIds()` helper. Unlike the sibling `RedisSessionStorage.addKeyToShopList()`, which explicitly checks `if (!idKeysArray.includes(idKey))` before appending, the KV implementation appends the incoming id(s) unconditionally on every call, with no bound and no deduplication check.

### Finding Description
`storeSession()` calls `addShopIds(session.shop, [session.id])` on every invocation: [1](#0-0) 

`addShopIds()` reads the existing array for the shop key and blindly concatenates the new id(s) without checking whether the id is already present: [2](#0-1) 

Because `storeSession()` is re-invoked on every OAuth callback, offline-token refresh, or online-token re-issuance for the same shop/session id (e.g. a merchant or app user re-triggering `/auth` or re-authenticating an embedded session), the same session id is appended to the `shop:<shop>` array again and again. There is no upstream check (analogous to Hats' missing "owner count unchanged" check in `checkAfterExecution()`) verifying that the array doesn't already contain the id, or that its size stays within any bound, before persisting it back to the KV namespace. This mirrors the reported bug class exactly: a value that should be capped/deduped is instead allowed to grow without limit through a legitimate, attacker-reachable action path, and there is no compensating check anywhere else in the flow to catch or reverse it.

By contrast, the Redis adapter for the same abstraction correctly guards against this: [3](#0-2) 

### Impact Explanation
Cloudflare KV enforces a hard 25 MiB limit per value. Once the JSON-serialized `shop:<shop>` array exceeds that size, `this.namespace.put(key, ...)` will throw, and every subsequent `storeSession()` call for that shop will fail — silently breaking the OAuth callback flow and all future session persistence (both offline and online) for that shop. This is a durable denial of service against the app's authentication handler for the affected shop: no code path in this package removes duplicate/stale ids from the shop index except `deleteSession`, so recovery requires manual, out-of-band cleanup of the KV key by the app operator — the same "brick until manual intervention" outcome described in the reference report.

### Likelihood Explanation
This requires no privileged access: any single merchant/user of the app who can trigger repeated OAuth flows or token refreshes for their own shop (e.g. repeatedly hitting the app's `/auth` entry point, or normal token-expiry-driven re-auth over time) causes monotonic, unbounded growth of the shop's session-id index. No collusion or elevated privileges are needed, and the growth is entirely a side effect of standard, expected traffic patterns to the auth handler, making accidental triggering plausible and deliberate triggering trivial.

### Recommendation
Update `addShopIds()` in `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts` to deduplicate before persisting (mirroring `RedisSessionStorage.addKeyToShopList()`), e.g. store the ids as a `Set` or check `includes()`/filter for existing entries prior to the `put()` call, and consider capping/pruning the per-shop session id list.

### Proof of Concept
1. Configure `KVSessionStorage` with a Cloudflare KV namespace for an app.
2. As a single authenticated app user, repeatedly trigger the app's OAuth callback for the same shop/session id (e.g. repeated `/auth/callback` completions, or automated token refresh on each app load) — each of which calls `storeSession(session)` with the same `session.id`.
3. Observe that `addShopIds()` appends `session.id` to the `shop:<shop>` KV array on every call without checking for duplicates: [2](#0-1) 
4. Repeating this a sufficient number of times (fully scriptable, no rate limiting shown in this code path) grows the serialized array past the 25 MiB Cloudflare KV per-value limit.
5. All further `storeSession()` calls for that shop now throw on `namespace.put`, breaking OAuth completion and session persistence for every user of that shop until an operator manually clears/repairs the `shop:<shop>` KV entry.

    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
