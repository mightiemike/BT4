### Title
Transaction backup restore persists `WriteSet`s without verifying them against the accumulator-proven `state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
During transaction backup restore, `LoadedChunk::load` verifies transactions and events against the ledger-info-anchored accumulator proof, but the per-transaction `WriteSet`s read from the backup chunk file are never checked against `TransactionInfo::state_change_hash()` before being persisted to `WriteSetDb` and (when `kv_replay` is enabled) used to reconstruct state.

### Finding Description
`LoadedChunk::load` reads five parallel vectors from the backup chunk file: `txns`, `persisted_aux_info`, `txn_infos`, `event_vecs`, `write_sets` [1](#0-0) . It then builds a `TransactionListWithProofV2` — deliberately excluding `write_sets` — and calls `.verify(...)` to authenticate the chunk against the epoch ledger info: [2](#0-1) 

That `verify()` implementation only checks (1) transaction hash vs. `txn_info.transaction_hash()` and (2) event root hash vs. `txn_info.event_root_hash()`; it never touches `write_set` or `state_change_hash()`: [3](#0-2) [4](#0-3) 

Compare this with `TransactionOutputListWithProof::verify`, which explicitly does hash the write set and checks it against `txn_info.state_change_hash()` before accepting an output chunk — proving the codebase considers this the correct invariant elsewhere, but the transaction-restore path omits it: [5](#0-4) 

The unverified `write_sets` then flow straight into `restore_utils::save_transactions_impl`, which writes them to `WriteSetDb` via `WriteSetDb::put_write_set` and, when `kv_replay` is true, feeds them into `StateUpdateRefs::index_write_sets` / `state_store.calculate_state_and_put_updates` to actually reconstruct the ledger state: [6](#0-5) 

No later point in the restore pipeline (in `LoadedChunk::load`, the streaming/replay path in `restore.rs`, or `restore_utils.rs`) recomputes `CryptoHash::hash(&write_set)` and compares it to `txn_info.state_change_hash()`. A grep for `state_change_hash`/`write_set_hash` across `storage/backup/**` returns no matches, confirming the check is absent from the entire backup-cli restore module.

### Impact Explanation
The `TransactionInfo.state_change_hash` is precisely the commitment that binds a `WriteSet` to the accumulator-proven ledger history (per `types/src/transaction/mod.rs:2406-2407`, "hash of the output write set"). Because restore never checks this binding for the transaction-backup format, a corrupted or tampered chunk file (e.g., from a compromised/faulty backup storage backend, a partial/incorrectly-regenerated backup, or bit corruption that happens to preserve `txn`/`events`/`txn_info` bytes but not `write_set` bytes) will pass `verify()` yet install an arbitrary `WriteSet` into `WriteSetDb`, and — when KV replay is used to reconstruct state — into the live state tree itself. This directly violates the required invariant "write sets must survive executor-to-storage handoff unchanged" and "restore helpers must not reinterpret committed data into a different ledger state," and can cause a durably persisted node to have `get_write_set`/API responses and (in the KV-replay path) actual account/resource state that diverges from what is truly proven by the transaction accumulator/ledger info, without any error being raised.

### Likelihood Explanation
This requires a corrupted or malicious backup source (compromised/misconfigured `BackupStorage`, or accidental data corruption) supplying a chunk file whose `write_set` field diverges from `txn_info.state_change_hash` while other fields stay proof-consistent. This is not exploitable by a generic unprivileged network attacker without also controlling backup storage content, but node operators who restore from an unverified/mirrored/third-party backup source would be silently exposed — there is no defense-in-depth check that the write set matches what the chain actually agreed on, unlike the output-list path which does have that check.

### Recommendation
In `LoadedChunk::load` (or in `TransactionListWithProof::verify`/a new verification step used specifically for restore), add an explicit check `CryptoHash::hash(&write_set[i]) == txn_infos[i].state_change_hash()` for every transaction in the chunk before it is accepted and passed to `restore_handler.save_transactions` / `save_transactions_and_replay_kv`, mirroring the check already present in `TransactionOutputListWithProof::verify`.

### Proof of Concept
1. Produce (or tamper with) a `TransactionChunk` backup file where `txns`, `txn_infos`, and `event_vecs` are left intact (so the transaction hash and event-root checks pass) but the associated `write_set` bytes for one record are swapped for a different, well-formed `WriteSet`.
2. Run transaction restore (`aptos-db restore` transaction-backup path). `LoadedChunk::load` at `storage/backup/backup-cli/src/backup_types/transaction/restore.rs:99-186` builds `txn_list_with_proof` (which excludes `write_sets`) and calls `.verify(...)`, which succeeds because it only checks `txn.committed_hash()` and event root hash.
3. The tampered `write_sets` are returned unchanged by `load()` and eventually reach `restore_utils::save_transactions_impl` (`storage/aptosdb/src/backup/restore_utils.rs:192-291`), which persists them via `WriteSetDb::put_write_set` and, if `kv_replay` is enabled, feeds them into `calculate_state_and_put_updates`, corrupting the restored ledger/state without any verification failure.
