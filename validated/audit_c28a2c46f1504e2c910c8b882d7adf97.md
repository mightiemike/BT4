## Title
Insufficient/Bypassable Source-Chain Confirmation Depth Enables Reorg-Based Unauthorized Minting of Synthetic Funds - (File: `universalClient/chains/evm/event_confirmer.go`)

### Summary
Push Chain's `x/uexecutor` finalizes inbound cross-chain deposits irrevocably: once a `UniversalTx` is created for a given `(source_chain, tx_hash, log_index)` key, it is never deleted or rolled back, and any later attempt to re-process the same key is rejected (`found` check in `VoteInbound`). The decision of *when* an observed source-chain event is safe to vote on rests entirely on the Universal Validator client's `EventConfirmer`, which gates confirmation solely on a configurable block-confirmation count. That gate is both weakly enforced in code and configured to near-zero depth in production chain configs, allowing an event to be voted in and permanently minted/executed on Push Chain before the source-chain transaction is actually final — the same class of bug as the Boba `_updateDepositHash()` finding, where an insufficiently protected reorg window let an attacker extract value that was later shown never to have existed on the canonical chain.

### Finding Description
`EventConfirmer.getRequiredConfirmations` in `universalClient/chains/evm/event_confirmer.go` is supposed to fall back to safe defaults (5/12) when a configured confirmation count is unset, but the guard is a tautology on an unsigned type: [1](#0-0) 

`ec.fastConfirmations >= 0` is always true for a `uint64`, so the "use default" branches are dead code — whatever value is configured (including `0`) is used verbatim. Production chain configs for multiple live spokes explicitly set `fast_inbound: 0` and `standard_inbound: 1`: [2](#0-1) [3](#0-2) 

With `fastConfirmations = 0`, `confirmations := latestBlock - receipt.BlockNumber.Uint64() + 1` is always `>= 0`, so a transaction is marked `CONFIRMED` (and thus votable) the instant its receipt is observed — effectively zero confirmation depth for any inbound whose `TxType` maps to `FAST` (`GAS`/`GAS_AND_PAYLOAD`): [4](#0-3) 

Once confirmed, `EventProcessor.processInboundEvent` immediately submits `MsgVoteInbound`: [5](#0-4) 

On the chain side, `VoteInbound` finalizes the ballot and unconditionally creates a `UniversalTx` — the record is append-only and the key is permanently reserved, so no re-vote or correction is possible afterward: [6](#0-5) 

The store even defines a `StatusReorged` status intended for exactly this situation, but it is only referenced by the terminal-event cleaner/tests, not by any active reorg-detection routine that would revert a wrongly confirmed or already-voted event: [7](#0-6) 

There is no analog of Boba's `_updateDepositHash()` safety net — no mechanism re-validates that a confirmed and voted inbound is still present on the canonical source chain once minting/execution has occurred on Push Chain.

### Impact Explanation
If the source-chain transaction backing a `GAS`/`GAS_AND_PAYLOAD` (or, on chains with `standard_inbound: 1`, any) inbound is reorged out after Push Chain honest validators have already confirmed it (using the effectively 0–1 block window) and voted it to quorum, Push Chain will have already minted PRC20/gas top-ups or executed a payload against funds that never landed on the canonical source chain. Because `UniversalTx` creation is permanent and idempotent-blocking (`found` check), this is an unauthorized mint with no possible correction, retry, or refund path — a direct violation of the "unauthorized mint" / accounting-integrity invariant in scope. This requires no privileged validator or TSS compromise: it is triggered purely by ordinary chain reorg dynamics (common on testnets/L2s such as BSC and Arbitrum Sepolia) combined with an attacker submitting a normal `sendFunds`/gas-top-up transaction timed around a reorg.

### Likelihood Explanation
The vulnerable configuration (`fast_inbound: 0`, `standard_inbound: 1`) is present in the shipped configs for multiple production spoke chains, not a hypothetical parameter choice, and the code path that should apply a safe default in the absence of meaningful confirmation depth is unreachable due to the `>= 0` tautology on a `uint64`. An attacker does not need to control 51% of an external chain's hashpower for extended attacks (as in the Boba scenario) — an ordinary 1-block reorg on any of these fast-finality/short-confirmation chains suffices to trigger the unauthorized mint, making this substantially easier to trigger than the original Boba report's 8-vs-64-block scenario.

### Recommendation
- Fix `getRequiredConfirmations` so the fallback-to-default logic actually triggers on genuinely "unset" configuration (e.g., use a sentinel or a separate "configured" boolean) rather than an always-true `>= 0` check on an unsigned integer.
- Enforce a chain-registry-level minimum confirmation floor (e.g., reject/clamp `fast_inbound`/`standard_inbound` values below a safe minimum such as 1–2 for testnets and higher for mainnet chains with historical reorg depth).
- Implement an active reorg-detection/rollback path that actually uses `StatusReorged`: after a source-chain event is confirmed but before/at vote time, re-verify block hash/ancestry, and if a previously confirmed transaction is later found reorged out, provide an on-chain remediation (e.g., a governance/escape-hatch clawback or explicit "unbacked mint" quarantine) analogous to Boba's `_updateDepositHash()` fix.

### Proof of Concept
1. Target a configured spoke chain with `block_confirmation.fast_inbound = 0` (e.g., `bsc_testnet`, `eth_sepolia`, `arb_sepolia` per shipped configs).
2. Submit a `sendFunds` gateway call with `TxType = GAS` or `GAS_AND_PAYLOAD` so the parsed event gets `ConfirmationType = FAST` (`finalizeEvent`, `event_parser.go:235-239`).
3. As soon as the transaction is mined (receipt available), `EventConfirmer.processPendingEvents` computes `confirmations >= 0` (always true given `fastConfirmations = 0`) and marks it `CONFIRMED` within one poll cycle — no meaningful block depth is required (`event_confirmer.go:161-165`, `248-267`).
4. Honest Universal Validators immediately call `MsgVoteInbound`; once 2/3+ vote, `VoteInbound` finalizes the ballot and creates a permanent `UniversalTx`, minting the corresponding PC/PRC20 gas top-up (`msg_vote_inbound.go`).
5. If the source-chain block containing the original transaction is reorged out (a routine, non-51%-attack event on short-finality testnets), the mint on Push Chain remains permanent and unbacked — the `found` check in `VoteInbound` (`msg_vote_inbound.go:45-52`) prevents any correction, and no code path consults `StatusReorged` to reverse it.

```go
// getRequiredConfirmations returns the required number of confirmations based on confirmation type
func (ec *EventConfirmer) getRequiredConfirmations(confirmationType string) uint64 {
	switch confirmationType {
	case store.ConfirmationFast:
		if ec.fastConfirmations >= 0 {
			return ec.fastConfirmations
		}
		return 5
	case store.ConfirmationStandard:
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	default:
		// Default to standard if unknown
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	}
```

```go
// finalizeEvent marshals the payload and sets confirmation type on the event.
func finalizeEvent(event *store.Event, payload *common.UniversalTx, logger zerolog.Logger) {
	if b, err := json.Marshal(payload); err == nil {
		event.EventData = b
	} else {
		logger.Warn().Err(err).Msg("failed to marshal universal tx payload")
	}

	if payload.TxType == 0 || payload.TxType == 1 {
		event.ConfirmationType = store.ConfirmationFast
	} else {
		event.ConfirmationType = store.ConfirmationStandard
	}
```

```go
// processInboundEvent processes an inbound event by voting on it and confirming it
func (ep *EventProcessor) processInboundEvent(ctx context.Context, event *store.Event) error {
	ep.logger.Debug().
		Str("event_id", event.EventID).
		Msg("processing inbound event")

	// Extract inbound data from event
	inbound, err := ep.constructInbound(event)
	if err != nil {
		return fmt.Errorf("failed to construct inbound: %w", err)
	}

	// Execute vote on blockchain
	voteTxHash, err := ep.signer.VoteInbound(ctx, inbound)
	if err != nil {
		ep.logger.Error().
			Str("event_id", event.EventID).
			Err(err).
			Msg("failed to vote on event - keeping status for retry")
		return err
	}
```
