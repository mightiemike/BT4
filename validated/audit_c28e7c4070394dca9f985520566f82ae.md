### Title
Front-runnable CREATE2 address collision causes deterministic DoS of pending contract-deployment transactions - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary

### Finding Description
The reported bug's root cause is generic: a user picks a globally-unique identifier (`loanId`) for a not-yet-executed action, and because the identifier is public/predictable and there is a window between submission and on-chain execution, an attacker can consume that identifier first, causing the legitimate transaction to deterministically revert once it lands.

java-tron's TVM `CREATE2` opcode has the same structural property. `CREATE2` computes a fully deterministic contract address from `sender/factory address + salt + keccak256(init code)` [1](#0-0) . This address is the "identifier" a deployer commits to before the transaction is confirmed, exactly analogous to `loanId`. When the `CREATE`/`CREATE2` opcode actually executes in `Program.createContractImpl`, it checks whether an account/contract already exists at that address, and if so marks the operation as failed: [2](#0-1) [3](#0-2) 

Because the salt, init code, and deployer/factory address are all attacker-observable (they must be included in the pending transaction's calldata to be broadcast/relayed), an adversary who sees a pending `CREATE2` transaction (in the mempool, or via a delayed relay/queue analogous to the Wormhole relayer path in the report) can race a transaction that deploys *any* contract with the same `salt` + `init code` at the same predicted address first. When the victim's original transaction subsequently executes, `contractAlreadyExists` evaluates to `true` and the create operation fails deterministically with "Trying to create a contract with existing contract address" [4](#0-3) , exactly mirroring `UserLoanAlreadyCreated` in the report. There is no mechanism (e.g., incorporating `msg.sender`/nonce uniquely into the salt enforcement, or reserving the address for the original submitter) to prevent this race — the check is purely "does an account/contract already exist at this deterministic address," with no ownership binding to the original transaction's sender.

This is a long-known general CREATE2 front-running property of EVM-compatible VMs, but it is concretely reachable and unprivileged in java-tron via ordinary `TriggerSmartContract` calls that execute `CREATE2` bytecode — no special role is required.

### Impact Explanation
An attacker can grief any unprivileged user whose transaction (or contract-internal logic) performs a `CREATE2` deployment with a predictable/observable salt and init code, causing the victim's transaction to fail on-chain after consuming energy/bandwidth (their `feeLimit`-bounded energy is still spent up to the point of the reverted CREATE, and the transaction is included in a block as failed). This is griefing/DoS impact analogous to the reported bug — it does not directly steal funds, but it can be used to reliably block legitimate contract-factory deployments (e.g., deterministic wallet deployment factories, counterfactual instantiation patterns used by smart-contract wallets or state-channel/AA-style contracts) that rely on `CREATE2` to guarantee a fixed address for a specific user before deployment.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to observe the victim's pending transaction (mempool sniping) and win a race to get their own transaction confirmed first — a well-established, practically demonstrated technique in EVM ecosystems. java-tron's fast block times reduce (but do not eliminate) the front-running window compared to Ethereum. It also requires the target contract logic to expose a `CREATE2` call with an attacker-predictable salt/init-code combination (e.g. `msg.sender`-independent salts), which is a common but not universal pattern in factory contracts.

### Recommendation
- At the TVM level this is inherent EVM/CREATE2 semantics and not something java-tron should "fix" unilaterally (matching production Ethereum behavior); instead, document the risk for TVM developers.
- Recommend that factory/wallet contract authors on TVM incorporate `msg.sender` (or another caller-bound value) into the `CREATE2` salt so that address collisions cannot be front-run by third parties, mirroring the report's own recommendation to bind `loanId` to `msg.sender`.
- If java-tron wants to reduce griefing at the protocol layer, consider whether energy refund policy for reverted `CREATE`/`CREATE2` due to `contractAlreadyExists` should be adjusted, since currently the victim still pays for VM execution up to the failure point [5](#0-4) .

### Proof of Concept
Conceptual PoC (mirroring `framework/src/test/java/org/tron/common/runtime/vm/Create2Test.java`, whose commented-out `create2AddressTest` already demonstrates a second deployer being blocked from using the same salt/address [6](#0-5) ):
1. Deploy a `Factory` contract with a `deploy(bytes code, uint256 salt)` function that internally calls `CREATE2`.
2. Victim (Alice) broadcasts a transaction calling `deploy(initCode, salt=100)`, computing an expected address via `generateContractAddress2(factoryAddress, salt, initCode)`.
3. Attacker (Eve), observing Alice's pending transaction, submits their own `deploy(initCode, salt=100)` call (using the same salt/init code, which is visible in Alice's calldata) with higher priority/fee so it confirms first.
4. When Alice's transaction executes, `existingAccount != null` at the same computed address, so `contractAlreadyExists = true`, and her `CREATE2` fails with "Trying to create a contract with existing contract address," consistent with the exception path shown in `Program.createContractImpl` [3](#0-2) .
