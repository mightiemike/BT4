### Title
Concurrent bucket-map growth requests can panic the validator due to an un-reset "reallocation pending" flag - (File: bucket_map/src/bucket.rs)

### Summary
The reported CCTP bug is a "before-only" flag (`HAS_BEFORE_BEEN_CALLED_SLOT`) that is set on the first call but only ever cleared by a corresponding after-hook. Because the hook is not registered as an after-hook, a second legitimate call in the same batch sees the flag still set and is treated as an illegal repeat call. `Bucket`'s reallocation tracking in `bucket_map` has the same shape: a flag is set by one code path (`add_reallocation`, taken under only a read lock) and cleared only by a separate code path (`handle_delayed_grows`, taken under a write lock). If a second "before" event (a second bucket-growth request) arrives before the first is drained, it does not degrade gracefully — it panics.

### Finding Description
`Reallocated::add_reallocation()` asserts that only one reallocation can be pending at a time: [1](#0-0) 

This flag is set from `Bucket::grow_index`/`grow_data` (invoked via `Bucket::grow`), and is only cleared by `Reallocated::get_reallocated()`, which is called exclusively from `Bucket::handle_delayed_grows()`: [2](#0-1) 

Crucially, `BucketApi::grow()` — the entry point used by callers when a write into the bucket map fails with `BucketMapError` (index or data full) — intentionally takes only a **read** lock on the bucket, explicitly to avoid write-lock contention on the hot insert path: [3](#0-2) 

The comment even documents the asymmetry: "grows are special - they get a read lock and modify 'reallocated' the grown changes are applied the next time there is a write lock taken." That "next write lock" is `get_write_bucket()`, which always calls `handle_delayed_grows()` before performing an operation: [4](#0-3) 

This is structurally identical to the CCTP defect: the "set" side (`add_reallocation`, analogous to the before-hook) can be reached repeatedly under only a read lock (no exclusion between concurrent callers), while the "clear" side (`get_reallocated` via `handle_delayed_grows`) is gated behind an entirely different, less-frequently-taken lock path (the write lock). If two growth conditions occur for the same underlying `Bucket` before any write-locked operation drains the pending reallocation, the second call to `add_reallocation()` finds `active_reallocations` already at `1` and panics via `assert_eq!(0, self.active_reallocations.fetch_add(1, ...))`, instead of returning gracefully or being resolved by a proper "after" step, mirroring the CCTP hook's failure to reset state between the first and second calls within the same operation window.

### Impact Explanation
An assertion panic in `Bucket::grow_index`/`grow_data` (via `Reallocated::add_reallocation`) crashes the validator process, since accounts-index disk-bucket writes happen on every account update, and bucket growth is triggered organically as accounts data grows (a normal, unprivileged, honest-node condition — not adversarial input). A crash here is a node-panic-class impact per the validation criteria, i.e., a real availability issue reachable by ordinary transaction/account load.

### Likelihood Explanation
Likelihood depends on whether multiple growth-triggering `BucketMapError`s for the *same* bucket can be observed via the read-lock-only `BucketApi::grow()` path before an intervening write-locked operation (insert/update/try_write/set_anticipated_count) calls `handle_delayed_grows()` to drain the pending reallocation. The read/write lock split and the explicit design comment indicate this race window is intentional and narrow but not proven safe here; I was not able to fully trace, within available tool calls, whether callers of `BucketApi::grow()` in `bucket_map.rs`/`accounts_index` are serialized elsewhere (e.g., by a per-bin single-writer discipline) such that the race is actually unreachable in practice. This is a gap in verification — the structural asymmetry is confirmed, but concrete concurrent-call-site proof of the race is not.

### Recommendation
Either (a) make `add_reallocation()` idempotent/tolerant of an already-pending reallocation (e.g., coalesce or return a result instead of asserting), or (b) ensure `BucketApi::grow()` cannot be invoked concurrently for the same bucket without first draining any pending reallocation (mirroring the CCTP fix pattern: don't let a "set" operation be re-entered before the corresponding "clear" step has definitely occurred, or make the clear step mandatory/paired at every entry point that can set the flag).

### Proof of Concept
Conceptual PoC (not fully validated against calling code outside the reviewed files):
1. Two account-index writes destined for the same on-disk bucket bin each hit `BucketMapError::IndexNoSpace`/`DataNoSpace` roughly concurrently, going through `BucketApi::grow()`, which only takes a read lock.
2. The first call sets `active_reallocations` to `1` via `add_reallocation()`.
3. Before any write-locked bucket operation runs `handle_delayed_grows()` to clear it, the second concurrent caller also reaches `add_reallocation()`.
4. `assert_eq!(0, self.active_reallocations.fetch_add(1, Ordering::Relaxed), "Only 1 reallocation can occur at a time")` fails, panicking the thread/process. [1](#0-0) [3](#0-2)

    /// if a bucket was resized previously with a read lock, then apply that resize now
    pub fn handle_delayed_grows(&mut self) {
        if self.reallocated.get_reallocated() {
            // swap out the bucket that was resized previously with a read lock
            let mut items = std::mem::take(&mut *self.reallocated.items.lock().unwrap());

            if let Some(bucket) = items.index.take() {
                self.apply_grow_index(bucket);
            } else {
                // data bucket
                let (i, new_bucket) = items.data.take().unwrap();
                self.apply_grow_data(i as usize, new_bucket);
            }
        }
    }
