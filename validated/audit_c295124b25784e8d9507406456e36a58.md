### Title
Panic-on-overflow in `GasVector::cost` allows an attacker-controlled transaction to crash the sequencer (DoS) - (File: `crates/starknet_api/src/execution_resources.rs`)

### Summary
The external report describes a DoS caused by an unguarded arithmetic overflow that occurs when a user-influenceable value (share/asset conversion input set to `type(uint256).max`) is fed into a conversion routine that `panic`s/reverts on overflow instead of handling the boundary gracefully. The same bug class exists in the sequencer's fee-computation path: `GasVector::cost` and `to_discounted_l1_gas` multiply/add attacker-controlled resource-bound values (`max_amount`, `max_price_per_unit`, `tip`) and `panic!` on overflow rather than returning a `Result`/saturating value.

### Finding Description
`GasVector::cost` computes the fee for a transaction by multiplying each gas amount by its price and summing the results: [1](#0-0) 

Each of the three arithmetic steps — the tip/L2-gas-price addition, the `gas.checked_mul(price)` multiplication, and the running-sum addition — calls `.unwrap_or_else(|| panic!(...))` on overflow instead of returning an error that can be turned into a transaction rejection. The same pattern recurs in `to_discounted_l1_gas`, `TransactionResources::to_gas_vector`, `ComputationResources::to_gas_vector`, `StarknetResources::to_gas_vector`, `StateResources::to_gas_vector`, and `MessageResources::to_gas_vector`, all of which `panic!` on `checked_add`/`checked_mul`/`checked_scalar_mul` failure: [2](#0-1) [3](#0-2) 

`GasAmount` is a `u64` and `GasPrice`/`Fee` are `u128`, but the resource bounds (`max_amount`, `max_price_per_unit`) and `tip` on an `Invoke`/`Declare`/`DeployAccount` V3 transaction are fields fully controlled by the transaction sender. `get_fee_by_gas_vector` (used to compute `max_possible_fee`, called from `verify_can_pay_committed_bounds` in `crates/blockifier/src/fee/fee_utils.rs:139-146,173-203`) and `TransactionContext::max_possible_fee` (`crates/blockifier/src/context.rs`) route directly into `GasVector::cost`. If the stateless/stateful gateway validators do not tightly bound `max_amount * max_price_per_unit` (and `tip + l2_gas_price`) to stay under `u128::MAX`, a submitted transaction with extreme resource bounds will cause a `panic!` deep in fee computation during gateway validation or execution — analogous to the reported `maxMint` overflow revert, but here manifesting as a Rust panic in a sequencer process rather than a Solidity revert.

### Impact Explanation
A panic triggered from validation/execution of a single submitted transaction can unwind and potentially abort a sequencer worker thread/process depending on panic-handling configuration, halting further transaction admission or block building — a network-availability impact matching the report's "DoS of a specific function," escalated here to a sequencer component. This satisfies the "network unable to confirm new transactions" acceptance criterion if the panic is not caught at a `catch_unwind` boundary before it can crash the relevant service.

### Likelihood Explanation
Likelihood depends entirely on whether `apollo_gateway`'s stateless/stateful validators (`crates/apollo_gateway/src/stateless_transaction_validator.rs`, `stateful_transaction_validator.rs`) already clamp `max_amount`, `max_price_per_unit`, and `tip` tightly enough that `gas.checked_mul(price)` and the tip addition can never overflow `u128`/`u64`. I was not able to fully confirm the exact bound-checking logic in the gateway validators within the remaining investigation budget (the search only surfaced references to `max_possible_fee` and `validate_resource_bounds`-related config/tests, not the concrete numeric clamps). If such bounds exist and are provably tighter than `u128::MAX / u64::MAX` products, this reduces to a defense-in-depth issue rather than an exploitable DoS. Given this uncertainty, I flag this as a **potential** analog rather than a confirmed one.

### Recommendation
- Replace `panic!`-based overflow handling in `GasVector::cost`, `to_discounted_l1_gas`, and the various `to_gas_vector` methods with `Result`-returning APIs that propagate a `TransactionFeeError` (as already exists in `crates/blockifier/src/fee/resources.rs`'s `TransactionFeeResult`), so that pathologically large but validator-admitted resource bounds cause transaction rejection rather than a process panic.
- Independently verify (in `apollo_gateway/src/stateless_transaction_validator.rs`) that `max_amount * max_price_per_unit` for every resource and `tip + l2_gas_price` are bounded well below `u128::MAX`/`u64::MAX` at stateless-validation time, before any fee computation is attempted.

### Proof of Concept
Conceptual PoC (pending confirmation that gateway validation does not already reject such bounds):
1. Submit a V3 `Invoke` transaction with `AllResourceBounds` where `l2_gas.max_price_per_unit` is set near `u128::MAX` and `tip` is set to a large `u64` value such that `gas_prices.l2_gas_price.checked_add(tip.into())` overflows, or where `l1_gas.max_amount` (up to `u64::MAX`) multiplied by an attacker-chosen `max_price_per_unit` overflows `u128` in `GasAmount::checked_mul` inside `GasVector::cost`.
2. If gateway/stateful validation does not reject this combination before `verify_can_pay_committed_bounds` / `max_possible_fee` is computed, the sequencer panics inside `GasVector::cost` at [4](#0-3)  instead of returning a transaction-rejection error.

    /// Computes the cost (in fee token units) of the gas vector (panicking on overflow).
    pub fn cost(&self, gas_prices: &GasPriceVector, tip: Tip) -> Fee {
        let tipped_l2_gas_price =
            gas_prices.l2_gas_price.checked_add(tip.into()).unwrap_or_else(|| {
                panic!(
                    "Tip overflowed: addition of L2 gas price ({}) and tip ({}) resulted in \
                     overflow.",
                    gas_prices.l2_gas_price, tip
                )
            });

        let mut sum = Fee(0);
        for (gas, price, resource) in [
            (self.l1_gas, gas_prices.l1_gas_price, Resource::L1Gas),
            (self.l1_data_gas, gas_prices.l1_data_gas_price, Resource::L1DataGas),
            (self.l2_gas, tipped_l2_gas_price, Resource::L2Gas),
        ] {
            let cost = gas.checked_mul(price.get()).unwrap_or_else(|| {
                panic!(
                    "{resource} cost overflowed: multiplication of gas amount ({gas}) by price \
                     per unit ({price}) resulted in overflow."
                )
            });
            sum = sum.checked_add(cost).unwrap_or_else(|| {
                panic!(
                    "Total cost overflowed: addition of current sum ({sum}) and cost of \
                     {resource} ({cost}) resulted in overflow."
                )
            });
        }
        sum
    }

pub fn to_discounted_l1_gas(
    l1_gas_price: NonzeroGasPrice,
    l1_data_gas_price: GasPrice,
    l1_gas: GasAmount,
    l1_data_gas: GasAmount,
) -> GasAmount {
    let l1_data_gas_fee = l1_data_gas.checked_mul(l1_data_gas_price).unwrap_or_else(|| {
        panic!(
            "Discounted L1 gas cost overflowed: multiplication of L1 data gas ({l1_data_gas}) by \
             L1 data gas price ({l1_data_gas_price}) resulted in overflow."
        );
    });
    let l1_data_gas_in_l1_gas_units =
        l1_data_gas_fee.checked_div_ceil(l1_gas_price).unwrap_or_else(|| {
            panic!(
                "Discounted L1 gas cost overflowed: division of L1 data fee ({l1_data_gas_fee}) \
                 by regular L1 gas price ({l1_gas_price}) resulted in overflow."
            );
        });
    l1_gas.checked_add(l1_data_gas_in_l1_gas_units).unwrap_or_else(|| {
        panic!(
            "Overflow while computing discounted L1 gas: L1 gas ({l1_gas}) + L1 data gas in L1 \
             gas units ({l1_data_gas_in_l1_gas_units}) resulted in overflow."
        )
    })
}
