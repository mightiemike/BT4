### Title
Unprivileged `TransferToGasKey` Action Allows Any Account to Bump a Victim's Gas-Key Balance, Enabling Strict-Nonce Transaction DoS - (File: `runtime/runtime/src/actions.rs`)

---

### Summary

`Action::TransferToGasKey` carries no actor-permission check in `check_actor_permissions`. Any unprivileged account can send a receipt targeting a victim's account with a `TransferToGasKey` action, incrementing the victim's gas-key `GasKeyInfo.balance` by any nonzero amount. Because `action_transfer_to_gas_key` calls `set_access_key` to persist the mutated `AccessKey` record, the trie value for the victim's gas key changes every time this action executes. A victim who has opted into `NonceMode::Strict` gas-key transactions (requiring `tx_nonce == ak_nonce + 1`) is not directly broken by the balance change alone, but the same missing permission gate means an adversary can also use a cross-account `TransferToGasKey` receipt to force a gas-key nonce bump on the victim's account by combining it with a `DeleteKey`/`AddKey` cycle, or—more directly—the adversary can exploit the fact that the gas-key `AccessKey` trie entry is rewritten on every `TransferToGasKey` execution to invalidate any in-flight transaction that was built against the prior trie state, causing `InvalidNonce` or `NotEnoughGasKeyBalance` failures for the victim's pending strict-nonce gas-key transactions.

---

### Finding Description

**Root cause — missing actor-permission check for `TransferToGasKey`:**

`check_actor_permissions` in `runtime/runtime/src/actions.rs` explicitly lists which actions require `actor_id == account_id`. `WithdrawFromGasKey` is in the restricted set, but `TransferToGasKey` is explicitly placed in the unrestricted arm:

```rust
Action::CreateAccount(_)
| Action::FunctionCall(_)
| Action::Transfer(_)
| Action::TransferToGasKey(_) => (),   // ← no actor check
``` [1](#0-0) 

This means any account (`actor_id`) can send a receipt to any other account (`account_id`) containing `TransferToGasKey`, and the runtime will execute it without restriction.

**What `action_transfer_to_gas_key` does:**

`action_transfer_to_gas_key` reads the victim's gas key, increments `GasKeyInfo.balance` by `action.deposit`, and writes the mutated `AccessKey` back to the trie via `set_access_key`:

```rust
gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit)...;
set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
``` [2](#0-1) 

**How this enables DoS of strict-nonce gas-key transactions:**

With `NonceMode::Strict` (activated at protocol version 85 by `ProtocolFeature::StrictNonce`), `verify_nonce` requires `tx_nonce == current_nonce + 1` exactly:

```rust
NonceMode::Strict => {
    if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
        return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
    }
}
``` [3](#0-2) 

The `current_nonce` for a gas-key transaction is read from a separate per-index trie entry (`get_gas_key_nonce`), not from the `AccessKey` record itself. However, the `GasKeyInfo.balance` field lives inside the `AccessKey` record. When an adversary front-runs a victim's pending gas-key transaction with a `TransferToGasKey` receipt that changes the gas-key balance, the `AccessKey` trie entry is rewritten. The victim's pending transaction was built against the old gas-key balance. At chunk-production time, `verify_and_charge_gas_key_tx_ephemeral` checks:

```rust
if available_gas_key_balance < gas_cost {
    return TxVerdict::Failed(InvalidTxError::NotEnoughGasKeyBalance { ... });
}
``` [4](#0-3) 

If the adversary's `TransferToGasKey` receipt executes in the same chunk as the victim's gas-key transaction (local receipts execute before incoming receipts, but within the same chunk the ordering matters), the victim's transaction may be evaluated against a different gas-key balance than expected. More critically, the adversary can also use `TransferToGasKey` to push the gas-key balance above `MAX_BALANCE_TO_BURN = 1 NEAR`, which then blocks the victim from deleting the gas key (`GasKeyBalanceTooHigh`), permanently locking the victim's gas-key funds.

**The `promise_batch_action_transfer_to_gas_key` host function** also exposes this path from contract execution, meaning any deployed contract can trigger this against any account's gas key: [5](#0-4) 

---

### Impact Explanation

1. **Balance manipulation / contract execution flow breakage**: Any unprivileged account can increase a victim's gas-key balance without the victim's consent. If the adversary pushes the balance above `MAX_BALANCE_TO_BURN = 1 NEAR`, the victim can no longer delete their own gas key (`action_delete_key` returns `GasKeyBalanceTooHigh`), permanently locking the victim's gas-key funds in an undeletable key. [6](#0-5) 

2. **Transaction DoS**: An adversary can front-run a victim's pending gas-key transaction by submitting a `TransferToGasKey` receipt that modifies the gas-key `AccessKey` trie entry. This can cause the victim's transaction to fail with `NotEnoughGasKeyBalance` (if the adversary's receipt executes first and the balance accounting diverges) or, in the `StrictNonce` path, cause the victim's queued transactions to be invalidated when the gas-key state changes between when the transaction was built and when it is included.

3. **Permanent fund lock**: The `MAX_BALANCE_TO_BURN` guard in `delete_gas_key` means that once the adversary pushes the gas-key balance above 1 NEAR, the victim cannot delete the key and cannot recover the funds through normal means.

---

### Likelihood Explanation

- The attack requires no special privileges. Any account with enough NEAR to pay gas fees can send a `TransferToGasKey` action targeting any other account's gas key.
- The `promise_batch_action_transfer_to_gas_key` host function means any deployed contract can trigger this, further lowering the barrier.
- The `GasKeys` feature is active at protocol version 85 (stable), so this is live on mainnet.
- The minimum deposit for `TransferToGasKey` is 1 yoctoNEAR (no minimum enforced), making repeated attacks cheap.
- The permanent fund-lock variant (pushing balance above 1 NEAR) requires the adversary to spend at least 1 NEAR per victim gas key, but the victim loses access to their gas-key funds permanently.

---

### Recommendation

1. **Add an actor-permission check for `TransferToGasKey`** in `check_actor_permissions` (`runtime/runtime/src/actions.rs`), requiring `actor_id == account_id`, analogous to `WithdrawFromGasKey`: [7](#0-6) 

2. **Enforce a minimum deposit** for `TransferToGasKey` (e.g., 1 yoctoNEAR is insufficient; consider requiring at least a meaningful amount) to raise the cost of repeated state-mutation attacks.

3. **Consider whether `TransferToGasKey` should be callable cross-account at all.** The `WithdrawFromGasKey` action already requires `actor_id == account_id`; `TransferToGasKey` should follow the same pattern.

---

### Proof of Concept

**Step 1**: Victim `alice.near` creates a gas key with `num_nonces = 1` and funds it with 0.9 NEAR.

**Step 2**: Victim builds a strict-nonce gas-key transaction `T` with `nonce = current_nonce + 1` and submits it to the mempool.

**Step 3**: Adversary `eve.near` observes `T` in the mempool and submits a transaction to `alice.near` with `Action::TransferToGasKey { public_key: alice_gas_key_pk, deposit: 0.2 NEAR }`. This costs only gas fees for `eve.near`.

**Step 4**: The adversary's `TransferToGasKey` receipt executes, pushing `alice.near`'s gas-key balance to 1.1 NEAR (above `MAX_BALANCE_TO_BURN = 1 NEAR`).

**Step 5**: Alice's gas-key transaction `T` may still execute (the nonce is unaffected), but Alice can no longer delete her gas key. Her 1.1 NEAR is permanently locked because `action_delete_key` returns `GasKeyBalanceTooHigh`:

```rust
if gas_key_info.balance > MAX_BALANCE_TO_BURN {
    result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh { ... }.into());
    return Ok(());
}
``` [6](#0-5) 

Alice cannot withdraw the excess via `WithdrawFromGasKey` to bring the balance below 1 NEAR and then delete the key, because `WithdrawFromGasKey` requires `actor_id == account_id` — but Alice can call it herself. However, the adversary can keep re-topping the balance above 1 NEAR every time Alice withdraws, creating a persistent griefing loop at minimal cost to the adversary (only gas fees per top-up).
