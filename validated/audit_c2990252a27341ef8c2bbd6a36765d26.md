## Analysis Result

**No vulnerability found for this question.**

### Reasoning

The equality being tested is: *(message actually signed by the recovered/verified signature)* == *(message of the block ultimately accepted into chainstate)*.

**Chain-level guard (`verify_signer_signatures`)**: `message` is computed strictly from block A's own header fields via `self.signer_signature_hash()` [1](#0-0)  and every signature in `self.signer_signature` is recovered against that exact `message` [2](#0-1) . A signature made over block B's unrelated hash recovers to an unrelated public key under ECDSA, which then fails the `signers_by_pk.remove(&public_key_bytes)` lookup and returns `InvalidStacksBlock` [3](#0-2) . There is no caching of `(public_key, block_id)` pairs across blocks at this layer — the hash is recomputed fresh from block A's fields every time.

**Node/StackerDB-level guard (`stackerdb_listener.rs`)**: the `block_sighash` used as the map key in `blocks.get_mut(&block_sighash)` is not attacker-chosen arbitrarily and then trusted — it is validated by `signer_pubkey.verify(block_sighash.bits(), &signature)` [4](#0-3) , using the signer's *known* public key (looked up by `slot_id` from `signer_entries`, not recovered from the signature) [5](#0-4) . This means a signature is only ever stored keyed under the hash it was cryptographically produced for; it is infeasible to make an ECDSA signature over H(B) validate against a different claimed hash H(A) under the signer's fixed public key. Consequently, `gathered_signatures` (a `BTreeMap<u32, MessageSignature>`) inside each `BlockStatus` entry is scoped per-proposal by its own `signer_signature_hash` key in `self.blocks`, inserted once per proposal via `insert_block` [6](#0-5) , and looked up in `get_block_status`/`wait_for_block_status` by that same specific `block_signer_sighash` [7](#0-6) . There is no code path that reuses or cross-references a signature validated for one hash under a different block's hash.

Both layers independently bind the signature to the exact message it was created over — one via ECDSA public-key recovery (chain consensus), the other via ECDSA verification against a known key (node/off-chain gossip layer) — so the claimed splice-and-replay CALL_SEQUENCE fails at both the `signers_by_pk.remove` step (chain) and the `blocks.get_mut`/`verify` step (node), exactly as the question's own precondition analysis anticipated. No caching or loose keying exists that would let a signature verified for block B be credited toward block A.
