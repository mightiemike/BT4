### Title
Starknet OS `replace_class` syscall omits the "class is declared" check present in the Blockifier, allowing state root divergence - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Cairo `execute_replace_class` implementations in the Starknet OS program do not verify that the target `class_hash` corresponds to an actually declared contract class before writing it into `contract_state_changes`, unlike the equivalent Rust Blockifier syscall handler, which performs this check via `state.get_compiled_class(request.class_hash)?` and errors with "is not declared" if the class hash is unknown.

### Finding Description
The `replace_class` syscall lets a contract change its own class hash. In the Rust Blockifier (the component that executes transactions when building blocks), `replace_class` explicitly reads the compiled class for the given hash to confirm the class is declared before updating state: [1](#0-0) . This is validated by tests expecting failures such as "is not declared" for undeclared class hashes [2](#0-1)  and [3](#0-2) .

However, the Starknet OS's Cairo implementation of the same syscall (used to re-execute transactions for proof generation and for the OS-based state diff/consistency verification path) contains an explicit, unresolved TODO acknowledging the missing check:
```
let class_hash = request.class_hash;

// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
local state_entry: StateEntry*;
%{ GetContractAddressStateEntry %}

tempvar new_state_entry = new StateEntry(
    class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
);
``` [4](#0-3) 

The same unchecked pattern also exists in the deprecated syscalls path used for Cairo 0 execution semantics: [5](#0-4) . Neither Cairo function reads/validates against a declared-classes structure (unlike `get_compiled_class` in Rust, which errors with `StateError::UndeclaredClassHash` when the class is undeclared, as seen in `CachedState::get_compiled_class` [6](#0-5) ).

This mirrors the JOJO audit finding's bug class exactly: a piece of state (the class-hash-to-declared-class mapping, analogous to `perpRiskParams.isRegistered`) is validated in one code path (Blockifier) but not in a sibling code path (the Cairo OS) that consumes the same syscall request and produces state changes that are supposed to match.

### Impact Explanation
A transaction sender can invoke a contract that calls `replace_class` with a completely arbitrary/undeclared class hash. The Blockifier (used for actual sequencing/mempool inclusion decisions and state commitment during block building) will reject this transaction because the class is undeclared. But the Starknet OS Cairo program — which re-executes the block to produce/verify the proof and the committed state — has no such guard, so if this code path were ever exercised on a transaction that somehow reaches it (e.g., any divergence in class-declared bookkeeping between the two implementations, or future code paths that rely solely on the OS's permissiveness), the OS would happily accept an undeclared class hash and commit it into `contract_state_changes`, producing a state diff/state root that the Blockifier's independent execution would never produce. This is a root cause for honest-node/component divergence between the Blockifier-computed state and the OS-computed (proven) state, risking a wrong committed state root or an OS/Blockifier consistency failure for block proving.

### Likelihood Explanation
Likelihood is currently constrained by the fact that the Blockifier's own validation (`get_compiled_class` check before replace) prevents such a transaction from being accepted through the normal transaction execution flow, so under the current call graph this divergence is latent rather than immediately triggerable via a single externally-visible flow. However it is a genuine correctness gap flagged by the developers themselves via the TODO comment, and it is directly reachable by any contract that issues the `replace_class` syscall with attacker-chosen calldata — the missing check exists at exactly the point in the OS code that consumes untrusted, user-controlled `class_hash` input.

### Recommendation
Add a check in `execute_replace_class` (both `crates/apollo_starknet_os_program/.../syscall_impls.cairo` and the deprecated syscalls variant) that verifies the given `class_hash` exists in the OS's declared classes/contract class Merkle tree (mirroring the Blockifier's `get_compiled_class`/`is_declared` checks) before writing the new `StateEntry`, and revert/fail the syscall analogous to the Blockifier's `StateError::UndeclaredClassHash` behavior if it is not declared.

### Proof of Concept
1. Deploy a contract implementing `test_replace_class` (or any entry point invoking the `replace_class` syscall) with an attacker-chosen, undeclared `class_hash` argument (e.g., `0x1234`), analogous to the existing Blockifier test `undeclared_class_hash` in `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs` lines 17-29.
2. Under the Blockifier execution path, this call is rejected with "is not declared" as shown in `crates/blockifier/src/execution/deprecated_syscalls/deprecated_syscalls_test.rs` lines 375-391.
3. If the same syscall request were processed purely by the Starknet OS Cairo program's `execute_replace_class` (`syscall_impls.cairo` lines 882-921 or `deprecated_execute_syscalls.cairo` lines 307-329), no equivalent check exists, and the arbitrary `class_hash` would be written unconditionally into `contract_state_changes`, demonstrating the code-path inconsistency between the two independently-implemented state-transition logics that are required to compute the same result for block validity.

        let mut cache = self.cache.borrow_mut();

        if let std::collections::hash_map::Entry::Vacant(vacant_entry) =
