### Title
Unbounded attacker-controlled array-size drives unchecked large allocation in deprecated (Cairo0) syscall payload parsing — Denial of Service (`File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
The Cairo0 (“deprecated”) syscall payload/array parser reads a `size` value directly from a felt written into VM memory by the executing contract, converts it to `usize`, and immediately passes it into a memory-range read that allocates a `Vec` of that size — without ever bounding it against the actual amount of available/backing data. This mirrors CVE-2017-11613 (libTIFF `td_imagelength` driving `_TIFFCheckMalloc` with an attacker-controlled, unvalidated size), causing an out-of-memory/DoS condition instead of a bounds error.

### Finding Description
`read_felt_array` for deprecated (Cairo0) syscalls reads an unconstrained felt as the claimed array length and forwards it straight into an allocation-triggering read: [1](#0-0) 

This function is used, among others, by `SendMessageToL1Request::read`, where `payload_size` is a raw felt taken from the Cairo0 syscall struct written by the executing (attacker-authored) contract code — it is not derived from or checked against the real size of the `payload` data segment: [2](#0-1) 

The size (after `usize::try_from`) flows into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` — a call that must allocate a buffer of `size` elements before it can even attempt to validate that the corresponding memory cells exist: [3](#0-2) 

By contrast, the analogous Cairo1 (“new”) syscall parser derives its array length from the difference between two real segment pointers (`array_data_end_ptr - array_data_start_ptr`), which is tied to an actual allocated Cairo VM segment and is not an arbitrary attacker-supplied integer: [4](#0-3) 

The deprecated path has no such tie to real data — the Cairo0 program can freely set `payload_size` to any large value (up to what fits in `usize`) independent of the actual payload array length, exactly as `td_imagelength` in the CVE could be set independent of actual image data / available memory. The result is a call that immediately attempts to reserve capacity for a huge `Vec<Felt>`, well before any legitimate bounds or gas/resource check can reject the malformed input.

### Impact Explanation
Any deployer of a Cairo0 (legacy) contract can craft a contract that invokes `send_message_to_l1` (or any other deprecated syscall relying on `read_felt_array`, e.g. `Deploy`'s constructor calldata region) with a very large declared payload/array size and a much smaller actual data pointer. Every honest sequencer/full node executing that transaction (during block building, validation, or Starknet OS re-execution) will attempt the same huge allocation deterministically. This can crash the process (OOM killer) or exhaust memory, producing a liveness/DoS condition across the network — nodes reproducing the block cannot complete execution, i.e., "network unable to confirm new transactions," which matches the accepted-impact criteria for this scan.

### Likelihood Explanation
Likelihood is high for any deployer of a Cairo0 contract: this requires only a standard `deploy`/`invoke` transaction from an unprivileged sender, using a syscall attribute (`payload_size`) that is fully attacker-controlled at the Cairo0 bytecode level. No special privileges, timing, or network position are required — the same class of contract can be deployed and invoked by anyone. Cairo0 support remains part of production execution (`RunnableCompiledClass::V0`), so this path is reachable in current mainnet-compatible execution flows.

### Recommendation
Bound `array_size`/`payload_size` (and any other length read via `read_felt_array` in `deprecated_syscalls/hint_processor.rs`) to a sane maximum (e.g., a configured max calldata/payload length, consistent with resource/gas accounting) before performing the allocation-triggering range read, and/or validate the size against gas already charged for that many felts prior to allocating. Alternatively, switch to an allocation strategy that grows incrementally (bounded chunks) rather than reserving `size` capacity up front from an untrusted value.

### Proof of Concept
1. Deploy a Cairo0 contract whose entry point calls the `send_message_to_l1` syscall with `payload_size` set to a very large value (e.g., `usize::MAX / 2`) while providing a `payload` pointer to a tiny (or empty) real data segment.
2. Submit an `invoke` transaction (from any unprivileged account) calling that entry point.
3. During execution, `SendMessageToL1Request::read` → `read_felt_array` → `felt_range_from_ptr` → `vm.get_integer_range` attempts to allocate/collect a `Vec<Felt>` of the attacker-chosen size before any bounds violation is detected, exhausting memory and crashing/hanging the executing node — reproducible deterministically by every node that executes or re-executes the block/transaction. pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
