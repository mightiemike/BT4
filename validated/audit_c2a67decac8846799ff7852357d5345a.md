Key finding: `AccountTransaction::new_for_sequencing` sets `charge_fee: enforce_fee(&tx, false)`, which is the path used by the batcher/mempool when sequencing arbitrary user-submitted transactions. `enforce_fee` determines fee-enforcement based on the transaction's own fields (e.g., resource bounds), not on any operator-only gate. ### Title
Declare transactions can spoof the reserved `BOOTSTRAP` sender address to skip validation, fee, and nonce checks - (File: crates/starknet_api/src/executable_transaction.rs, crates/blockifier/src/transaction/account_transaction.rs)

### Summary
`DeclareTransaction::is_bootstrap_declare` treats any V3 declare transaction whose `sender_address` equals the hardcoded `bootstrap_address()` (`'BOOTSTRAP'` as felt) and whose `nonce == 0` and for which `charge_fee` is `false` as a special genesis-bootstrap transaction. In `AccountTransaction::execute_raw`, such transactions skip `perform_pre_validation_stage` (nonce increment, fee bound checks, balance verification) and skip running `__validate_declare__` entirely, going straight to declaring the class for free. `sender_address` and `nonce` are ordinary user-controlled transaction fields; nothing observed in the reachable declare-transaction validation path (`apollo_gateway/src/stateless_transaction_validator.rs`, `crates/starknet_api/src/executable_transaction.rs`) restricts who may set `sender_address` to this specific constant, analogous to how `divisionTier` was never range-checked in the original report, letting a caller reach a code path meant only for a privileged/one-time genesis flow.

### Finding Description
This mirrors the report's bug class: a value that should be validated/restricted (a "special" index/identifier — here the sender address used to gate a privileged, fee-free code path) is instead accepted from unauthenticated user input without an explicit check that the caller is actually the legitimate bootstrap process. `bootstrap_address()` is just `ContractAddress::from(0x424f4f545354524150_u128)` — a public, derivable constant, not a secret or protocol-enforced address ownership check (there is no signature verification against a real deployed account at that address for this special path, since `__validate_declare__` is explicitly skipped). Combined with `AccountTransaction::new_for_sequencing` computing `charge_fee` from `enforce_fee(&tx, false)` (a function of the transaction's own resource-bounds fields, which the attacker also controls), an attacker-supplied declare transaction can satisfy all three bootstrap conditions (`sender_address == bootstrap_address()`, `nonce == 0`, `!charge_fee`) purely through self-chosen transaction fields.

### Impact Explanation
If reachable outside the legitimate one-time genesis bootstrap flow, this allows: (1) declaring arbitrary classes with zero fee paid — a fee-bypass/free-resource-usage impact directly analogous to the reported "mint for free" bug, and (2) more critically, execution of `run_execute` for the "declare" without going through the normal validate/fee/nonce-increment pipeline, which — depending on how the batcher/mempool treats the resulting `TransactionExecutionInfo::default()` (no state diff for nonce, as noted in the code comments) — could be replayed repeatedly (since nonce is never incremented, the same transaction remains valid and can be resubmitted every block until rejected only after the class is already declared).

### Likelihood Explanation
Likelihood hinges entirely on whether any component upstream of `AccountTransaction::execute_raw` (the gateway's stateless/stateful validators, mempool admission) rejects a declare transaction using `bootstrap_address()` as its sender unless it is actually part of the node's own genesis bootstrapping sequence. I was not able to locate such a check in the code paths I reviewed within the available search budget; the tests found (`crates/blockifier/src/transaction/account_transactions_test.rs::test_bootstrap_declare`, `crates/apollo_integration_tests/tests/bootstrap_declare.rs`) construct these transactions directly via `AccountTransaction::new_for_sequencing`/`execute()` without going through gateway-level authorization gating, which is consistent with — but does not conclusively prove — the absence of an external guard.

### Recommendation
Explicitly gate the bootstrap-declare fast path so it can only trigger during actual genesis processing (e.g., only when the block/chain has no prior blocks, or only when invoked through a dedicated bootstrap API/internal transaction type that ordinary user-submitted RPC transactions cannot construct), rather than relying solely on the transaction's own `sender_address`/`nonce`/`charge_fee` fields, all of which are attacker-controlled inputs.

### Proof of Concept
1. Craft a `DeclareTransactionV3` with `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`), `nonce = Nonce(0)`, and resource bounds chosen such that `enforce_fee(&tx, false)` evaluates to `false` (see `crates/blockifier/src/transaction/transactions.rs::enforce_fee`).
2. Submit via the normal sequencing path (`AccountTransaction::new_for_sequencing`), matching `test_bootstrap_declare`'s non-genesis test setup in `crates/blockifier/src/transaction/account_transactions_test.rs:905-991`.
3. Observe `is_bootstrap_declare` returns `true` in `crates/starknet_api/src/executable_transaction.rs:248-255`, causing `execute_raw` in `crates/blockifier/src/transaction/account_transaction.rs:899-911` to declare the class while skipping `perform_pre_validation_stage`, `__validate_declare__`, fee charging, and nonce increment.

impl<U: UpdatableState> ExecutableTransaction<U> for AccountTransaction {
    fn execute_raw(
        &self,
        state: &mut TransactionalState<'_, U>,
        block_context: &BlockContext,
        concurrency_mode: bool,
    ) -> TransactionExecutionResult<TransactionExecutionInfo> {
        let tx_context = Arc::new(block_context.to_tx_context(self));
        self.verify_tx_version(tx_context.tx_info.version())?;

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
        }
