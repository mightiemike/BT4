### Title
Attached deposit permanently stuck in Wallet Contract when `rlp_execute` fails before a refund promise is scheduled - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `#[payable]` entrypoint `rlp_execute` on the NEAR Wallet Contract accepts an `attached_deposit` from an external caller. This is tracked via `CallerDeposit`, whose sole purpose is to refund the caller's deposit if the requested cross-contract action fails. However, that refund only happens inside `rlp_execute_callback` when the scheduled promise chain later returns `PromiseResult::Failed`. Several early-exit error paths inside `inner_rlp_execute` (and the `Err(e)` branch of `rlp_execute` itself) return a plain `ExecuteResponse`/`Err` without ever constructing a promise, so `CallerDeposit`/the refund transfer is never issued — while the attached NEAR deposit has already been credited to the wallet contract's balance as part of the `#[payable]` call.

### Finding Description
`rlp_execute` is `#[payable]`, meaning any attached deposit is unconditionally added to the wallet contract's account balance the moment the function call executes, before any of its logic runs [1](#0-0) .

Inside `rlp_execute`, `inner_rlp_execute` builds an `ExecutionContext` from `env::attached_deposit()` and immediately creates a `CallerDeposit` object specifically to remember "the deposit given by an external caller… allows us to refund the caller's deposit if the cross-contract call fails" [2](#0-1) [3](#0-2) .

That `caller_deposit` value is only ever consumed by being threaded through the various promise-callback chains (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`), and the actual refund transfer is issued in exactly one place — inside `rlp_execute_callback`, only on `PromiseResult::Failed` [4](#0-3) .

But `inner_rlp_execute` has multiple paths that return `Err(...)` (and therefore never build any promise/callback at all) after `CallerDeposit::new` has already been computed from the deposit that was credited to the contract balance:
- `Err(err @ Error::User(_)) => { *nonce = nonce.saturating_add(1); return Err(err); }` [5](#0-4) 
- The generic `Err(err) => { ... return Err(err); }` branch for Relayer/AccountId errors [6](#0-5) 

These `Err` results propagate up to `rlp_execute`, where the top level handler simply converts the error to a value and returns it without ever creating a `Promise`:
```
Err(e) => PromiseOrValue::Value(e.into()),
``` [7](#0-6) 

Since no promise/transfer is ever scheduled in this path, the `CallerDeposit` refund logic in `rlp_execute_callback` is never reached, and the attached deposit — already added to the wallet contract's balance by the payable call — is never returned to the caller. The funds are permanently absorbed by the wallet contract with no user-facing mechanism to reclaim them.

### Impact Explanation
Any external, unprivileged caller (a relayer's counterparty, a third-party dApp, or the user themselves acting through a different account) who calls `rlp_execute` with a non-zero attached NEAR deposit and whose embedded Ethereum transaction fails RLP/action parsing (bad signature format, unsupported action encoding, address/target mismatch classified as a `User` or other early error) permanently loses that attached deposit into the wallet contract's balance. This is a permanent, unauthorized-value-freeze condition reachable by a single transaction/contract call from an unprivileged signer, matching the "permanently frozen funds" impact category. The severity is Medium: the amount lost is bounded by what the caller chooses to attach, requires the caller to trigger a parsing failure while depositing funds, but no privileged access or coordination is needed to reach the vulnerable code path.

### Likelihood Explanation
Likelihood is moderate: it requires the caller to deliberately (or accidentally) attach a NEAR deposit while calling `rlp_execute` with an RLP transaction that fails early validation (bad target/address mismatch, bad decode, or a `User`/`Relayer`/`AccountId` classified error) rather than progressing into one of the promise-chain paths. Because `CallerDeposit` exists specifically to support external callers attaching a deposit (its constructor explicitly excludes the self-call case), this is an anticipated, reachable usage pattern, not a purely theoretical one.

### Recommendation
In every early-return `Err(...)` path of `inner_rlp_execute` (and any other path that returns without constructing a promise) where a non-zero deposit was attached by an external caller, issue an explicit `Promise::new(predecessor_account_id).transfer(...)` refund (mirroring the logic already present in `rlp_execute_callback`) before returning the error. Alternatively, centralize the refund logic so that any code path terminating with a synchronous `Value` result first checks the attached deposit/`CallerDeposit` and refunds it, guaranteeing that "attached deposit is refunded whenever the requested action does not consume it," consistent with the deposit-refund pattern used elsewhere in the runtime (e.g., `refund_unspent_gas_and_deposits`, `settle_state_init_deposit`).

### Proof of Concept
1. Deploy/derive an eth-implicit account backed by the Wallet Contract (as in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`).
2. As an external caller (a different `predecessor_account_id` than `current_account_id`, i.e. not a self-call), submit a NEAR `FunctionCall` to `rlp_execute` with:
   - `target`: a value that will trigger a `User`/`Relayer`/`AccountId` classified parsing error in `parse_rlp_tx_to_action` (e.g., malformed RLP bytes or mismatched target/address), and
   - a non-zero `deposit` attached to the call.
3. Observe: the call returns `ExecuteResponse { success: false, ... }` synchronously (no promise scheduled), and `env::promise_batch_action_transfer` is never invoked.
4. Check the wallet contract's account balance before/after: the attached deposit is retained by the contract permanently, and the caller's balance is decreased by the deposit amount with no compensating transfer back — contrasted with `test_caller_refunds` in `sanity.rs`, which only exercises the promise-chain-failure refund path (`PromiseResult::Failed`), not this early synchronous-error path, confirming the gap is untested and unhandled.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
