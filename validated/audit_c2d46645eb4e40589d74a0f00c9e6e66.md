## Title
Wallet Contract pays the relayer fee refund unconditionally, before the underlying transfer is known to succeed — ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Sherlock finding flags Solidity code that fires `transfer()`/native token sends without checking the outcome, letting side effects (like paying a fee) proceed even when the corresponding action silently fails. The NEAR analog lives in the `near-wallet-contract`'s `inner_rlp_execute`, where the relayer's fee refund is dispatched as an independent promise **before** the wallet knows whether the user's actual EOA base-token transfer or ERC-20 transfer will succeed.

### Finding Description
`inner_rlp_execute` computes a relayer `fee` from the signed Ethereum transaction and, for `EOABaseTokenTransfer`/`ERC20Transfer` kinds, immediately creates and dispatches a transfer receipt to the relayer via `env::promise_batch_create` / `env::promise_batch_action_transfer`, completely detached from the `.then()` chain that performs the real action: [1](#0-0) 

This refund is not chained to the subsequent action promise (the multi-hop `storage_balance_of` → `storage_deposit` → `ft_transfer` → `rlp_execute_callback` chain built in the same function): [2](#0-1) 

If that action chain later fails (e.g. a `PromiseResult::Failed` reaches `rlp_execute_callback`), the contract only refunds the caller's attached `caller_deposit`, never the fee already paid to the relayer: [3](#0-2) 

Additionally, the nonce is incremented unconditionally for these cases before the promise/result is known, so the "attempt" is consumed regardless of outcome: [4](#0-3) 

The only gas safeguard is that `validate_tx_relayer_data` requires the outer call's `env::prepaid_gas()` to be at least `gas_limit * GAS_MULTIPLIER` taken from the user-signed Ethereum transaction: [5](#0-4) 

This only checks total prepaid gas for the top-level call; it does not guarantee sufficient gas will remain for the deep NEP-141 storage-check/deposit/transfer/callback chain once static costs (registrar lookups, storage_balance_of, storage_deposit) are subtracted. A relayer — an unprivileged entity that need not hold any access key to the wallet, since `rlp_execute` is a public, `#[payable]` method reachable by any predecessor — fully controls how much NEAR gas it attaches to the outer `FunctionCall` invoking `rlp_execute`, and can pick a value that just satisfies the `validate_tx_relayer_data` check but is insufficient for the downstream multi-hop call chain (e.g. the receiver requires a `storage_deposit` hop it did not have when the tx was signed), causing the actual ERC-20/base-token transfer to fail with `PromiseResult::Failed` while the fee receipt has already been sent.

### Impact Explanation
An unprivileged transaction relayer can repeatedly submit otherwise-valid signed RLP transactions with an attached `fee`, deliberately under-provisioning gas for the downstream action chain so it fails, while unconditionally collecting the pre-committed fee payment because that transfer promise is created independently of, and prior to, resolution of the actual action. The wallet's balance is drained of the fee amount per attempted transaction without the user's requested value transfer ever completing, and the nonce is consumed so the same intended transfer cannot be retried without a brand-new user-signed transaction. This is unauthorized value extraction from the wallet contract's balance triggered purely by relayer behavior, reachable from a single submitted (relayed) transaction.

### Likelihood Explanation
Any account can act as a relayer for `rlp_execute` (it is a public payable method; no access key ownership is required for a permissionless relayer flow, only the RLP-transaction signature by the user's key is checked). Controlling the amount of NEAR gas attached to the outer function call is trivial and entirely under the relayer's control, and the fee amount is derived directly from the user-signed `gas_price`/`gas_limit`, so a malicious relayer processing routine ERC-20/base-token transfer traffic can systematically trigger this pattern.

### Recommendation
Chain the relayer fee-refund promise to the same promise as the underlying action (e.g. via `.then()`/callback) so it is only paid out after `rlp_execute_callback` confirms `PromiseResult::Successful`, or reserve/hold the fee and only release it to the relayer inside `rlp_execute_callback`'s success branch, refunding it back to the wallet (or not spending it) on the failure branch alongside the existing `caller_deposit` refund logic.

### Proof of Concept
1. User signs an RLP Ethereum transaction representing an `ERC20Transfer` with a non-zero `max_fee_per_gas * gas_limit` (i.e., non-zero `fee`), targeting a receiver not yet registered for storage on the NEP-141 token.
2. A relayer account (no special privileges) submits a NEAR `FunctionCall` to `rlp_execute` with just enough attached gas to pass `validate_tx_relayer_data`'s `prepaid_gas >= gas_limit * GAS_MULTIPLIER` check, but insufficient gas for the full `storage_balance_of → storage_deposit → ft_transfer → rlp_execute_callback` chain.
3. `inner_rlp_execute` creates and dispatches the fee-refund receipt to the relayer immediately (lines 381-384), then separately schedules the action chain.
4. The downstream chain fails with `PromiseResult::Failed` due to running out of gas at some hop; `rlp_execute_callback` refunds only `caller_deposit`, not the fee.
5. The relayer has collected the fee even though the user's transfer never occurred, and the nonce has advanced, so the specific requested transfer cannot be resubmitted as-is.
