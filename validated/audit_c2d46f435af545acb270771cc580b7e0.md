### Title
Missing Prepare-Phase Access Window Check in `vote-for-aggregate-public-key` Allows Stale/Out-of-Window Aggregate Key Approval - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
The `signers-voting.clar` boot contract defines a helper `is-in-voting-window` (which in turn calls `is-in-prepare-phase`) whose stated purpose, per the surrounding comments, is to ensure that signer votes for the aggregate public key are only accepted "after the list of signers has been set by the node, which occurs in the first block of the prepare phase." However, this check is never called from `vote-for-aggregate-public-key`, the only public entry point for casting a vote. [1](#0-0) [2](#0-1) 

### Finding Description
`vote-for-aggregate-public-key` is a `define-public` function callable by any principal that can produce a valid `signer-index`/`reward-cycle` pair recognized by `.signers`: [3](#0-2) 

Its only gating checks are:
- the aggregate key hasn't already been approved for that `reward-cycle` (`map-get? aggregate-public-keys reward-cycle`),
- the key is 33 bytes and globally novel,
- the caller (via `get-signer-weight`) is the actual registered signer at `signer-index` for that `reward-cycle`,
- the caller hasn't voted yet in that `(reward-cycle, round)`, and
- the round increases by at most 1.

Nowhere does it call `is-in-voting-window`/`is-in-prepare-phase`, even though these are defined specifically for this purpose: [4](#0-3) 

`get-signer-by-index`, called transitively through `get-signer-weight`, reads from `cycle-signer-set`, a map keyed by reward cycle that is never cleared once set: [5](#0-4) 

Because entries in `cycle-signer-set` persist indefinitely, a principal who was a legitimate signer for some past reward cycle `N` retains the ability to call `vote-for-aggregate-public-key` with `reward-cycle = N` at any later burn height, as long as `aggregate-public-keys` for `N` was never finalized (e.g., voting stalled or quorum was not reached during the intended prepare-phase window). This breaks the equality the protocol depends on: "the aggregate public key for reward cycle `N` is only decided during `N`'s prepare-phase voting window using the signer set as of that window." Any node or signer client that assumed no key would ever be set for `N` after the window closed can later observe `aggregate-public-keys` populated for that same cycle, creating a legitimate `get-approved-aggregate-key` divergence in time.

### Impact Explanation
This is a minority-triggerable (single stale signer, not requiring majority collusion beyond the normal 70% weight threshold already baked into the tally logic) validation-window divergence in a signer boot contract that directly feeds DKG/signing consensus for Nakamoto block signing. Late finalization of an aggregate key for an already-elapsed reward cycle can cause different nodes/signers to disagree about which aggregate key is authoritative for that cycle depending on when they query it, which maps to the "temporary tip disagreement" / signer-set validation divergence category described as High impact.

### Likelihood Explanation
Exploitation only requires: (1) being a real signer registered for some reward cycle whose vote never reached quorum in time, and (2) submitting further votes after the window has passed. No special privileges, admin keys, or majority collusion are needed beyond what is already required to accumulate 70% weight — the bug is purely the absence of the time-window enforcement that the code's own comments and unused helper function indicate was intended.

### Recommendation
Invoke `is-in-voting-window` (or equivalent burn-height/prepare-phase and `last-set-cycle` checks) inside `vote-for-aggregate-public-key` before accepting a vote, so that votes for a given `reward-cycle` are only accepted while that cycle's prepare phase is active and `last-set-cycle` equals `reward-cycle`, matching the documented intent.

### Proof of Concept
1. Reward cycle `N`'s prepare phase begins; `.signers` sets `cycle-signer-set` for `N` via `set-signers`.
2. Voting for cycle `N` fails to reach the 70% threshold before the prepare phase / window ends (e.g., due to slow signers), and burn-block-height moves well past `N`'s window into cycle `N+5`.
3. A signer that was part of `N`'s signer set (still resolvable via `get-signer-by-index` since `cycle-signer-set` is never pruned) calls `vote-for-aggregate-public-key` with `reward-cycle = N` at the current (much later) height.
4. Because `is-in-voting-window`/`is-in-prepare-phase` is never checked, the vote is accepted, and if it (combined with other still-valid votes from `N`'s signer set) reaches 70% weight, `aggregate-public-keys` for `N` becomes populated well after the cycle has ended, despite nodes/tools that already treated `N` as having no finalized key.

;; Signer vote for the aggregate public key of the next reward cycle
;;  Each signer votes for the aggregate public key for the next reward cycle.
;;  This vote must happen after the list of signers has been set by the node,
;;  which occurs in the first block of the prepare phase. The vote is concluded
;;  when the threshold of `threshold-consensus / 1000` is reached for a
;;  specific aggregate public key. The vote is weighted by the amount of
;;  reward slots that the signer controls in the next reward cycle. The vote
;;  may require multiple rounds to reach consensus, but once consensus is
;;  reached, later rounds will be ignored.
;;
;;  Arguments:
;;   * signer-index: the index of the calling signer in the signer set (from
;;     `get-signers` in the .signers contract)
;;   * key: the aggregate public key that this vote is in support of
;;   * round: the voting round for which this vote is intended
;;   * reward-cycle: the reward cycle for which this vote is intended
;;  Returns:
;;   * `(ok true)` if the vote was successful
;;   * `(err <code>)` if the vote was not successful (see errors above)
(define-public (vote-for-aggregate-public-key (signer-index uint) (key (buff 33)) (round uint) (reward-cycle uint))
    (let ((tally-key {reward-cycle: reward-cycle, round: round, aggregate-public-key: key})
            ;; vote by signer weight
            (signer-weight (try! (get-signer-weight signer-index reward-cycle)))
            (new-total (+ signer-weight (default-to u0 (map-get? tally tally-key))))
            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))
            (threshold-weight (get-threshold-weight reward-cycle))
            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))
        ;; Check that aggregate public key has not been used in a previous reward cycle
        (asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))
        ;; Check that signer hasn't voted in this reward-cycle & round
        (asserts! (map-insert votes {reward-cycle: reward-cycle, round: round, signer: tx-sender} {aggregate-public-key: key, signer-weight: signer-weight}) (err ERR_DUPLICATE_VOTE))
        ;; Check that the round is incremented by at most 1
        (try! (update-last-round reward-cycle round))
        ;; Update the tally for this aggregate public key candidate
        (map-set tally tally-key new-total)
        ;; Update the current round data
        (map-set round-data {reward-cycle: reward-cycle, round: round} {
            votes-count: (+ (get votes-count current-round) u1),
            votes-weight: (+ (get votes-weight current-round) signer-weight)})
        ;; Update used aggregate public keys
        (map-set used-aggregate-public-keys key reward-cycle)

(define-map cycle-signer-set uint (list 4000 { signer: principal, weight: uint }))

;; Called internally by the Stacks node.
;; Stores the stackerdb signer slots for a given reward cycle.
;; Since there is one stackerdb per signer message, the `num-slots` field will always be u1.
(define-private (stackerdb-set-signer-slots 
                   (signer-slots (list 4000 { signer: principal, num-slots: uint }))
                   (reward-cycle uint)
                   (set-at-height uint))
	(let ((cycle-mod (mod reward-cycle u2)))
        (map-set cycle-set-height reward-cycle set-at-height)
        (var-set last-set-cycle reward-cycle)
        (if (is-eq cycle-mod u0)
            (ok (var-set stackerdb-signer-slots-0 signer-slots))
            (ok (var-set stackerdb-signer-slots-1 signer-slots)))))

;; Called internally by the Stacks node.
;; Sets the list of signers and weights for a given reward cycle.
(define-private (set-signers
                 (reward-cycle uint)
                 (signers (list 4000 { signer: principal, weight: uint })))
     (begin
      (asserts! (is-eq (var-get last-set-cycle) reward-cycle) (err ERR_CYCLE_NOT_SET))
      (ok (map-set cycle-signer-set reward-cycle signers))))

;; Get the list of signers and weights for a given reward cycle.
(define-read-only (get-signers (cycle uint))
     (map-get? cycle-signer-set cycle))
