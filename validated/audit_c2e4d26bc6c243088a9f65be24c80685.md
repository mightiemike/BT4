## Title
Witness cycle rewards are permanently lost when a witness's vote count drops to zero before the reward VI is accumulated - (`File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
`java-tron`'s new vote-reward algorithm accrues block/transaction-fee rewards per witness per cycle in `DelegationStore` (via `addReward`), and periodically converts those rewards into a per-witness reward index (`Vi`) that voters later use to compute their claimable share. If, at the moment the index is updated, the witness's recorded vote count is `0`, the code silently skips incorporating that cycle's reward into the index — exactly the same "supply == 0 ⇒ emissions lost" pattern described in the referenced Blend report, except here the "supply" is a witness's vote count and the "emissions" are TRX block/fee rewards.

### Finding Description
Rewards for a witness are accrued every block through `MortgageService.payReward`, which calls `delegationStore.addReward(cycle, witnessAddress, value)`: [1](#0-0) 

At each maintenance cycle boundary, when the new reward algorithm is enabled, `MaintenanceManager.doMaintenance` accumulates that cycle's reward into the witness's Vi index using the witness's *current* stored vote count, and this call happens before the new cycle's vote tally (`countVote`) is applied: [2](#0-1) 

The core accumulation logic in `DelegationStore.accumulateWitnessVi` explicitly skips updating the reward index whenever the reward is `0` **or** the vote count is `0` — it just forwards the previous index unchanged: [3](#0-2) 

The equivalent path in `RewardViCalService` (used for historical/backfill Vi calculation) has the identical skip condition: [4](#0-3) 

Because the reward value was already durably written to `DelegationStore` for `(cycle, witnessAddress)` via `addReward`, but the Vi index — the only mechanism by which voters can later derive their claimable share via `computeReward`/`withdrawReward` — is never advanced for that cycle, the reward amount becomes permanently unclaimable. `withdrawReward`/`computeReward` only ever consult the Vi delta between `beginCycle` and `endCycle`, not the raw per-cycle reward store, so once a cycle is skipped in this way there is no future path to recover it: [5](#0-4) 

This is directly analogous to the reported Blend issue: `do_gulp_emissions` distributes/records emissions to a reserve irrespective of whether that reserve currently has any supply, and the corresponding claim path (`update_emission_data`) silently no-ops when `supply == 0`, causing that reserve's share of emissions to be lost forever. In java-tron, the "supply" is the witness's vote count and the reward store `addReward` plays the role of the unconditional gulp, while `accumulateWitnessVi`'s `voteCount == 0` guard plays the role of the claim-time no-op.

### Impact Explanation
Any TRX (block reward + transaction fee reward) accrued for a witness during a maintenance cycle in which that witness's tallied vote count is `0` at the time `doMaintenance` runs is permanently lost — it is neither credited to any voter's withdrawable allowance nor recoverable by the witness or protocol. This is a fund-loss/accounting-corruption bug in the consensus reward system, reachable purely through unprivileged voting/unvoting transactions plus normal block production, with no admin/privileged action required.

### Likelihood Explanation
This requires a witness to have all of its votes withdrawn (via ordinary `VoteWitnessContract`/unfreeze/withdraw flows available to any account) within the same maintenance cycle in which it is still producing blocks and earning fees, before `doMaintenance` processes the new vote tally. Because `accumulateWitnessVi` is invoked with the witness's vote count as it stood *before* the current cycle's `countVote` update is applied, a witness that loses all its voters during a cycle (e.g., large delegators unvote or withdraw stake) will hit `voteCount == 0` at accumulation time, silently dropping that cycle's reward. While this scenario is not the common case, it is plausible for lower-ranked active/standby witnesses with concentrated voting, and is entirely triggerable by unprivileged accounts without any special preconditions beyond normal vote/unvote activity.

### Recommendation
When `voteCount == 0` but `reward > 0` in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`, do not silently discard the reward. Options include: (1) carrying the un-distributed reward forward to be combined with the next cycle that has a non-zero vote count instead of dropping it, or (2) redirecting it to a well-defined destination (e.g., burn, treasury, or explicit "unclaimed rewards" account) rather than leaving it unaccounted for. At minimum, add an explicit accounting check so that reward tokens are never both recorded in `DelegationStore` (`addReward`) and simultaneously excluded from every Vi index update path, which currently causes silent, unrecoverable value loss.

### Proof of Concept
1. Witness `W` is in the active set and produces blocks in cycle `N`; each block triggers `MortgageService.payBlockReward`/`payTransactionFeeReward` → `payReward` → `delegationStore.addReward(N, W, value)`.
2. Before `doMaintenance()` runs for cycle `N`, all accounts holding votes for `W` submit unvote/withdraw transactions such that `WitnessCapsule(W).getVoteCount()` reads `0` (the vote count used is the pre-`countVote` value read at the top of `doMaintenance`).
3. `doMaintenance()` executes `delegationStore.accumulateWitnessVi(N, W, 0)`, which — because `voteCount == 0` — takes the "just forward pre `Vi`" branch and does not incorporate the reward accrued in step 1 into `W`'s Vi index.
4. Any voter who had previously voted for `W` and later withdraws via `MortgageService.withdrawReward`/`computeReward` computes their reward strictly from the Vi delta across cycles; since `Vi` for cycle `N` was never advanced, the reward accrued in step 1 is not reflected in any voter's payout and is permanently unclaimable, even though it was durably persisted via `addReward`.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
