Based on my investigation, I found the relevant analog: the `getAccountEnergyUsageBalanceAndRestoreSeconds` / `usageToBalance` and `calculateGlobalEnergyLimit` code paths in `RepositoryImpl.java` and `EnergyProcessor.java` divide by `totalEnergyWeight`/`totalNetWeight`, guarded in some call sites but not all.

### Title
Unguarded division by zero-able `TotalEnergyWeight`/`TotalNetWeight` can revert resource/energy accounting paths - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
Several resource-accounting computations divide a usage/weight value by the chain's aggregate `TotalEnergyWeight` (or `TotalNetWeight`), a store-derived value that can legitimately be zero (e.g., right after chain init, or after mass unfreezing under `supportUnfreezeDelay`). Some call sites guard against this (`if (totalEnergyWeight == 0) return 0;` in `EnergyProcessor.calculateGlobalEnergyLimitV2`/`BandwidthProcessor.calculateGlobalNetLimitV2`), but others do not.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` asserts `totalEnergyWeight > 0` but only inside an `assert` statement, which is disabled by default in production JVMs (`-ea` not typically set): [1](#0-0) 

If `totalEnergyWeight` is 0 and the JVM assertion is disabled, the subsequent BigInteger `.divide(...)` (when `hardenResourceCalculation()` is enabled) or the double division `((double) totalEnergyLimit / totalEnergyWeight)` will either throw `ArithmeticException` (BigInteger path) or produce `Infinity`/`NaN` (double path), silently corrupting a TVM-callable native contract's energy accounting (`calculateGlobalEnergyLimit` is invoked by `Repository`, which backs `DelegateResourceProcessor`/`UnDelegateResourceProcessor`/native contracts reachable from broadcast transactions).

Similarly, `RepositoryImpl.getAccountEnergyUsageBalanceAndRestoreSeconds` and `getAccountNetUsageBalanceAndRestoreSeconds` call `usageToBalance(newEnergyUsage, totalEnergyWeight, totalEnergyLimit)` with no zero-guard at all before entering the BigInteger division path: [2](#0-1) 

This mirrors the reported bug class: a derived accounting divisor (`coinsPerSecond` in the report; `totalEnergyWeight`/`totalNetWeight` here) that, when zero, causes reverts/exceptions in downstream withdrawal/accounting logic rather than being defensively guarded at every call site.

### Impact Explanation
If `TotalEnergyWeight` (or `TotalNetWeight`) reaches zero — which is a store value adjusted by freeze/unfreeze actuators and can transiently be zero on a fresh or fully-unfrozen network state, or via a witness/committee-controlled dynamic parameter path — any call into the unguarded `calculateGlobalEnergyLimit`/`getAccountEnergyUsageBalanceAndRestoreSeconds` paths from a TVM contract (native resource-delegation precompiles) or from RPC-facing `Wallet` energy-query APIs would throw an uncaught `ArithmeticException` (when hardened BigInteger division is enabled) or return `Infinity`/garbage (legacy double division), causing failed transaction execution or incorrect resource-limit reporting. This is a resource-accounting correctness/availability issue rather than a fund-theft issue.

### Likelihood Explanation
Low-to-Medium. `totalEnergyWeight`/`totalNetWeight` are normally kept positive under standard mainnet operation, and several sibling functions (`calculateGlobalEnergyLimitV2`, `calculateGlobalNetLimitV2`, `calculateGlobalNetLimit`) already explicitly guard against a zero value, indicating the maintainers are aware this can happen but did not apply the guard uniformly to every division site (notably `RepositoryImpl.calculateGlobalEnergyLimit` and the `usageToBalance` call sites). Reaching a zero weight requires specific network/freeze-state conditions, which reduces but does not eliminate likelihood; it is plausible on low-participation testnets or shortly after protocol upgrades that reset these dynamic parameters.

### Recommendation
Add an explicit, unconditional `if (totalEnergyWeight <= 0) return 0;` (or throw a well-defined `ContractValidateException`/`0` fallback rather than relying on `assert`, which is disabled by default) at the start of `RepositoryImpl.calculateGlobalEnergyLimit`, `getAccountEnergyUsageBalanceAndRestoreSeconds`, `getAccountNetUsageBalanceAndRestoreSeconds`, and any other production path that divides by `totalEnergyWeight`/`totalNetWeight`, matching the guards already present in `EnergyProcessor.calculateGlobalEnergyLimitV2` and `BandwidthProcessor.calculateGlobalNetLimitV2`.

### Proof of Concept
Not independently reproducible from static analysis alone — reproducing requires driving `TotalEnergyWeight`/`TotalNetWeight` to 0 in a running node's dynamic-properties store (e.g., via a test harness directly setting the property, as done in `CalculateGlobalLimitHardenTest`) and then invoking `RepositoryImpl.calculateGlobalEnergyLimit` (via a TVM native resource-delegation contract call) or `getAccountEnergyUsageBalanceAndRestoreSeconds` (via an RPC energy-query call) to observe the uncaught `ArithmeticException` or `Infinity` result. I could not verify from the index whether production configuration paths ever legitimately allow this value to be 0 in mainnet steady state, versus only being reachable through a chain that has never been bootstrapped with witnesses/freezes.

  public Pair<Long, Long> getAccountEnergyUsageBalanceAndRestoreSeconds(AccountCapsule accountCapsule) {
    long now = getHeadSlot();

    long energyUsage = accountCapsule.getEnergyUsage();
    long latestConsumeTime = accountCapsule.getAccountResource().getLatestConsumeTimeForEnergy();
    long accountWindowSize = accountCapsule.getWindowSize(Common.ResourceCode.ENERGY);

    if (now >= latestConsumeTime + accountWindowSize) {
      return Pair.of(0L, 0L);
    }

    long restoreSlots = latestConsumeTime + accountWindowSize - now;

    long newEnergyUsage = recover(energyUsage, latestConsumeTime, now, accountWindowSize);

    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getTotalEnergyWeight();

    long balance = usageToBalance(newEnergyUsage, totalEnergyWeight, totalEnergyLimit);

    return Pair.of(balance, restoreSlots * BLOCK_PRODUCED_INTERVAL / 1_000);
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
