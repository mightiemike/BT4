## Finding

### Title
Unbounded recursive JSON traversal in Cairo-0 hinted class hash computation causes stack-overflow DoS during declare-transaction processing - (File: crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs)

### Summary
When computing the "hinted class hash" for a deprecated (Cairo 0) contract class, the sequencer recursively walks the entire `serde_json::Value` tree built from attacker-controlled fields of the declared class (`identifiers`, `reference_manager`, `hints`, `attributes[].accessible_scopes`, `attributes[].flow_tracking_data`) with no depth limit, exactly the bug class described in CVE-2018-15671 (unbounded native-stack recursion while parsing/normalizing a crafted, deeply-nested input structure).

### Finding Description
`compute_cairo_hinted_class_hash` deserializes the declared Cairo 0 contract into a `CairoProgram`, which stores several fields as raw, unconstrained `serde_json::Value`/`Vec<serde_json::Value>` trees: [1](#0-0) 

Before hashing, it recursively sorts every nested object/array in this attacker-supplied JSON with a plain, non-tail recursive function that has no depth check: [2](#0-1) 

This is invoked directly from `compute_cairo_hinted_class_hash`: [3](#0-2) 

An attacker who declares a Cairo 0 class can put arbitrarily deep nesting (e.g., `[[[[[...]]]]]`) inside `identifiers`, `reference_manager`, `hints`, or `attributes[].accessible_scopes`/`flow_tracking_data`, since these fields accept arbitrary JSON with no schema/depth validation. `sort_json_value` will recurse once per nesting level, consuming native stack frames, exactly mirroring how `H5P__get_cb()` in the HDF5 CVE recursively parses a crafted file's nested structures without a depth bound.

Unlike Sierra→CASM compilation of untrusted Cairo-1 classes — which the codebase explicitly runs in a resource-limited *subprocess* to avoid exactly this class of issue (comment in `crates/blockifier_reexecution/src/compile.rs`: "the sequencer gateway ... compiles user-submitted classes in a resource-limited subprocess") — this Cairo 0 hinted-hash computation and the underlying `serde_json::Value` parsing run in-process, in the same call chain as the Starknet OS hint execution / class-hash validation, with no subprocess isolation, no configured stack-size guard, and no recursion-depth guard analogous to `RecursionDepthGuard` used elsewhere for entry-point call recursion: [4](#0-3) 

### Impact Explanation
A stack overflow in this path aborts the process (Rust `abort()` on stack overflow, unrecoverable), which would crash the Starknet OS component or the process re-executing the declare transaction. If this occurs during block building or OS re-execution, it can crash the sequencer/prover process handling the block, producing a denial of service against the block-production pipeline — a node unable to confirm new transactions, consistent with the "network unable to confirm new transactions" impact bar. If different node implementations tolerate the depth differently (e.g., differing default stack sizes across environments), this could also produce honest-node divergence for the same declare transaction.

### Likelihood Explanation
Reachability requires only an ordinary Declare transaction for a Cairo 0 (deprecated) class with crafted JSON metadata fields — no privileged access, no proposer/operator role, and it is a standard, still-supported transaction type in the codebase (Cairo 0 declare paths remain present: `DeprecatedContractClass`, `DeclareV0/V1`, `compute_deprecated_class_hash`, and OS hint `deprecated_compiled_class` handling). Whether an attacker can craft the nesting depth within existing declare-transaction size limits without being rejected by fee/size checks first, and the exact point in the pipeline where `compute_cairo_hinted_class_hash` is invoked relative to other validations, could not be fully confirmed in this pass — I was only able to identify its callers in `starknet_os/src/hints/hint_implementation/deprecated_compiled_class/` and test files, not trace the complete calling path back to gateway-level size/structure validation for the class JSON fields in question.

### Recommendation
Add an explicit recursion-depth (or iterative, work-list based) bound to `sort_json_value`, and/or validate maximum nesting depth of `identifiers`, `reference_manager`, `hints`, and `attributes` fields at declare-transaction stateless validation time (mirroring the existing `max_bytecode_size`/`max_sierra_version` checks in `stateless_transaction_validator.rs`), rejecting classes that exceed the bound before they reach hinted-hash computation.

### Proof of Concept
Submit a Declare V0/V1 transaction for a Cairo 0 contract class whose `program.identifiers` (or `reference_manager`/`hints`) field is a deeply nested JSON array, e.g. `{"identifiers": [[[[[[[[[[ ... ]]]]]]]]]], ...}` nested to a depth sufficient to exceed the default thread stack size. When this class is processed via `compute_cairo_hinted_class_hash` → `sort_json_value`, the recursive traversal will exhaust the stack and abort the process.

**Note on confidence**: I could not fully verify the exact call path from an untrusted network-submitted declare transaction through to `compute_cairo_hinted_class_hash` within the tool budget available (only test-file callers and the OS hint implementation module were located, not the full transaction-processing call graph), nor confirm whether any upstream size/structure limit already implicitly bounds nesting depth. This should be validated by tracing `deprecated_compiled_class/class_hash.rs` and `deprecated_compiled_class/utils.rs` callers back to the transaction validation/execution entrypoints before treating this as fully confirmed.

/// Recursively sorts all JSON objects by their keys.
/// This ensures deterministic serialization regardless of the `preserve_order` feature in
/// serde_json.
fn sort_json_value(value: serde_json::Value) -> serde_json::Value {
    match value {
        serde_json::Value::Object(map) => {
            let sorted: BTreeMap<String, serde_json::Value> =
                map.into_iter().map(|(k, v)| (k, sort_json_value(v))).collect();
            serde_json::Value::Object(sorted.into_iter().collect())
        }
        serde_json::Value::Array(arr) => {
            serde_json::Value::Array(arr.into_iter().map(sort_json_value).collect())
        }
        other => other,
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
