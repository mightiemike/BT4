## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash`, letting replay-verify accept a diverged state root as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the authenticated-equivalence check used by every offline "did local re-execution reproduce the committed ledger" tool (archive replay-verify, the Move CLI debugger, and `aptos-debugger`). It checks status, gas, write-set hash, and event-root hash against the persisted `TransactionInfo`, but it never compares the locally computed state-checkpoint root against `txn_info.state_checkpoint_hash()` (nor the hot-state/position checkpoint hashes). A version whose re-executed write set/events happen to match but whose resulting global state tree diverges will still be reported as a successful, verified replay.

### Finding Description
The function is defined at [1](#0-0)  and checks exactly four things: `status`, `gas_used`, `write_set` hash vs `txn_info.state_change_hash()`, and `event_root_hash` vs `txn_info.event_root_hash()`. It stops there, and the code itself documents the gap explicitly: [2](#0-1) 

`TransactionInfo` carries a distinct `state_checkpoint_hash` field — the Sparse-Merkle-Tree root summarizing the entire world state at a checkpoint — separate from `state_change_hash` (the write-set hash) [3](#0-2) . `state_change_hash` only proves the write set that was *applied*; `state_checkpoint_hash` proves the state that *resulted*. Skipping the latter means a bug in JMT/state materialization (e.g. in `commit_state_kv_and_ledger_metadata`, hot-state promotion, or state-summary computation) that corrupts the state root while leaving individual write ops and events unchanged would not be detected by this comparator.

This comparator is the sole authenticity gate used by the two tools whose entire purpose is proof/replay integrity:
- `storage/db-tool/src/replay_on_archive.rs`, which independently re-executes archived transactions and calls `ensure_match_transaction_info` to decide pass/fail [4](#0-3) .
- `aptos-move/cli/src/commands.rs`'s `Replay` command, used to verify on-chain transactions locally [5](#0-4) .
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`'s mismatch printer [6](#0-5) .

None of these call sites pass or check anything for the state-checkpoint hash — the field simply isn't part of the comparison contract.

### Impact Explanation
This breaks the "authenticated response bound to the right root" invariant for the replay/verify pathway: a checkpoint transaction whose recomputed global state root differs from the one recorded and Merkle-accumulator-committed on-chain would still be reported as "verified" by `replay_on_archive` and by CLI replay. Since these are the tools operators and auditors rely on to detect state divergence/hard-fork bugs after the fact, a real state-materialization bug (independent of write-set/event correctness) could pass undetected through the one mechanism designed to catch it, undermining confidence in "verified" replay results and delaying detection of ledger-state corruption.

### Likelihood Explanation
This is not a hypothetical: the check is unconditionally absent for `state_checkpoint_hash` regardless of feature flags (unlike the hot-state/position-state hashes, which are also skipped but are still being rolled out). Any discrepancy between local execution and the persisted `TransactionInfo` limited to the checkpoint state root — as opposed to the write set or events — will silently pass. The bug is exercised on essentially every checkpoint/block-epilogue transaction replayed by these tools.

### Recommendation
Extend `ensure_match_transaction_info` to also assert the locally computed state-checkpoint root (and, once fully enabled, hot-state/position-state checkpoint roots) against `txn_info.state_checkpoint_hash()` / the corresponding `TransactionInfoV1` fields, mirroring the way write-set and event hashes are already checked, before relying on this function to gate replay-verify success.

### Proof of Concept
Not applicable as an on-chain exploit (this does not affect consensus-committed state); the issue is demonstrable by inspection: construct any `TransactionOutput` whose write set/events serialize identically to a given `TransactionInfo` but originates from a different global state (e.g. corrupt just the state-checkpoint hash field in a fabricated `TransactionInfo`, or feed a `TransactionOutput` from execution against a state view with a subtly different pre-existing account state that still produces the same write ops). `ensure_match_transaction_info` at [7](#0-6)  returns `Ok(())`, and `replay_on_archive`'s `execute_and_verify` at [4](#0-3)  treats the version as successfully verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
