## Title
Missing zero-address (burn-address) validation allows unrecoverable loss of TRX/TRC10 tokens via `TransferActuator` and `TransferAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`, `common/src/main/java/org/tron/common/utils/DecodeUtil.java`)

### Summary
The external report describes an ERC20/BentoBox pattern where transfers to the zero address are not rejected, permanently burning tokens. The closest analog in java-tron is that `DecodeUtil.addressValid()` — the sole address-format check used by `TransferActuator` and `TransferAssetActuator` — only validates address length and the `0x41` Tron prefix byte. It never rejects the "zero" address (`0x41` followed by 20 zero bytes), so a user (via a normal broadcast transaction) can send TRX or TRC10 tokens to this all-zero address and they become permanently unrecoverable, since no private key exists for it and it isn't the chain's dedicated black-hole/burn account with any special handling logic in these actuators.

### Finding Description
`DecodeUtil.addressValid()` only checks that the address is non-empty, exactly 21 bytes, and starts with the mainnet prefix byte; it performs no check that the remaining 20 bytes are non-zero: [1](#0-0) 

`TransferActuator.execute()` uses `toAddress` directly from the unpacked `TransferContract` without any validate() step calling zero-address checks (it silently creates a new account and credits it) — TRX sent to the zero-format address is credited into that unspendable account: [2](#0-1) 

`TransferAssetActuator.validate()` similarly relies solely on `DecodeUtil.addressValid(toAddress)` for the destination and rejects only self-transfers (`Arrays.equals(ownerAddress, toAddress)`), not the zero address: [3](#0-2) 

`TransferAssetActuator.execute()` then creates the destination account (if absent) and credits the TRC10 asset amount to it unconditionally: [4](#0-3) 

The same missing-zero-check pattern also exists in the TVM-triggered TRC10 transfer validation path used for `transferToken`/internal transfers: [5](#0-4) 

This mirrors the reported bug class exactly: tokens/assets sent to an address with no controlling private key are permanently lost, because none of these code paths distinguish the "zero" address from any other syntactically-valid address.

### Impact Explanation
Funds (TRX and TRC10 tokens) sent to the zero-format address (`0x41` + 20 zero bytes) become permanently unspendable/unrecoverable, since no key material corresponds to it and none of these actuators treat it specially (unlike the dedicated `accountStore.getBlackhole()` address used deliberately for fee burning). This is a direct, irreversible asset-loss condition reachable by any ordinary broadcast transaction — no privileged role or compromised key required, satisfying the "unauthorized... asset or accounting corruption" impact bar. However, the loss only affects the sender's own funds/tokens (self-inflicted, typically via wallet/integration bugs or malformed input), it does not let an attacker steal others' assets, cause consensus divergence, or achieve RCE.

### Likelihood Explanation
Low-to-moderate. It requires a transaction (from a wallet, exchange integration, or smart contract) that constructs a `TransferContract`/`TransferAssetContract` with a destination address that decodes to the all-zero Tron address, which passes the existing `addressValid` check unmodified. This is analogous to well-documented ERC20 "burn to zero address" incidents that happen due to integration bugs, copy-paste errors, or uninitialized address variables, and has historically caused real losses on other chains.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid()` (or in each actuator's `validate()`) to reject the reserved zero address (`0x41` followed by 20 zero bytes) as a valid `toAddress` for `TransferActuator`, `TransferAssetActuator`, and the corresponding TVM TRC10 transfer validation in `VMUtils.validateForSmartContract`, consistent with the existing self-transfer rejection (`Cannot transfer asset to yourself.`).

### Proof of Concept
1. Construct a `TransferContract` (or `TransferAssetContract`) with `toAddress` set to `0x41` followed by 20 zero bytes (a syntactically valid Tron address per `DecodeUtil.addressValid`).
2. Broadcast the transaction; `TransferActuator.validate()`/`execute()` (or `TransferAssetActuator.validate()`/`execute()`) accepts it, creates the account if needed, and credits the TRX/asset balance to that address. [6](#0-5) 
3. The funds are now held by an address for which no private key exists, and are permanently unrecoverable.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
