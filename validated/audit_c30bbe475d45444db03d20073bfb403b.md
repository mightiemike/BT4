### Title
Congestion-based transaction-admission filter is enforced only at chunk-preparation time and never re-checked during chunk execution/state-witness validation - ([File: chain/chain/src/runtime/mod.rs])

### Summary
The scheduling-time filter that is supposed to keep new transactions out of a congested shard (`shard_accepts_transactions` / `congestion_control_accepts_transaction`) is applied only when a chunk producer is selecting transactions from the tx pool. Neither the runtime's actual transaction-processing path (`runtime/runtime/src/lib.rs`) nor chunk/state-witness validation re-enforces this filter, so once a transaction is placed inside a chunk it is unconditionally executed, exactly mirroring the Nova bug where a filter (e.g. `ImagePropertiesFilter`/`IsolatedHostsFilter`) is applied only at initial scheduling and is bypassed by any code path that doesn't go back through the Filter Scheduler (there, "rebuild"; here, chunk application/validation).

### Finding Description
`shard_accepts_transactions` on `CongestionControl` is the "filter" that is meant to reject new transactions targeting a congested receiving shard [1](#0-0) . It is invoked in exactly two places, both in `chain/chain/src/runtime/mod.rs`:

1. `validate_tx`, used when a transaction is first admitted into the mempool [2](#0-1) .
2. `congestion_control_accepts_transaction`, used inside `prepare_transactions`/`prepare_transactions_extra` while the chunk producer is pulling transactions out of the pool to build a chunk [3](#0-2) , called from the selection loop at [4](#0-3) .

`grep` across the repo confirms `shard_accepts_transactions`/`ShardAcceptsTransactions` and `congestion_control_accepts_transaction` are referenced nowhere else — not in `runtime/runtime/src/lib.rs::process_transactions` (the function that actually executes transactions already included in a chunk during `apply_chunk`), and not in the chunk/state-witness validation path (`chain/chain/src/stateless_validation/chunk_validation.rs`, `chain/chain/src/spice/chunk_validation.rs`). Those paths re-execute whatever transactions are present in the (received or witnessed) chunk via `apply_new_chunk` → `process_transactions` [5](#0-4) , checking cost, nonce, and access-key validity, but never re-derive congestion info for the *receiver* shard of each transaction to confirm it should have been admitted.

This is structurally identical to the Nova defect: `ImagePropertiesFilter`/`IsolatedHostsFilter` are consulted by the Filter Scheduler only at the initial placement decision; Nova's "rebuild" operation re-created the instance without going back through the scheduler, so the filter was silently skipped. Here, `shard_accepts_transactions` is consulted only by the "scheduler" (the transaction-selection/preparation code that a chunk producer runs locally), not by the "hypervisor" (the deterministic state-transition function that every validating/verifying node runs when applying or validating the chunk). Any code path that produces a chunk containing a transaction to a congested shard without going through `prepare_transactions`/`prepare_transactions_extra` — most importantly the deterministic re-execution performed by every other validator when validating the chunk state witness — will accept and execute that transaction unconditionally.

### Impact Explanation
A malicious or buggy chunk producer can include, inside a chunk it proposes, a transaction whose receiver shard is fully congested (congestion_level ≥ `reject_tx_congestion_threshold`, i.e. exactly the case that is supposed to be rejected as "ShardCongested"/"ShardStuck"). Because `process_transactions`/`apply_chunk`/state-witness validation contain no equivalent re-check, honest chunk validators executing the state witness will independently arrive at the *same* post-state (since they run the identical, filter-free `process_transactions` code), so this does not directly cause a state-root divergence between honest nodes. However, it does mean the congestion-control transaction-admission invariant ("no new transaction is accepted into an already-congested shard", NEP-539) is not actually a consensus rule — it is only a soft, producer-side heuristic that any producer can ignore, which directly bypasses a documented gas/resource-throttling protection and permits unbounded injection of new transactions into an already-overloaded shard, defeating the congestion-control safety mechanism designed to protect chain liveness/fairness under load.

### Likelihood Explanation
Reachable by any single chunk producer (a role rotated among ordinary validators, i.e., not requiring "malicious validator" collusion beyond the producer simply not calling the standard `prepare_transactions` selection code, or feeding it a modified filter). No special privileges beyond being the currently assigned chunk producer for a shard are needed, and the offending transaction can originate from any ordinary signer.

### Recommendation
Move the congestion-based transaction-admission check (`shard_accepts_transactions`) from being solely a `prepare_transactions`-time heuristic into a check enforced during chunk validation/state-witness verification (or into `process_transactions` itself), so it becomes a consensus-checked invariant rather than a producer-only optimization — mirroring the eventual OpenStack fix, which made the corresponding filter re-checked on `rebuild` rather than relying on the scheduler having been the only entry point.

### Proof of Concept
1. Drive a shard's `CongestionInfo` above `reject_tx_congestion_threshold` (e.g., via `buffered_receipts_gas` growth as in `core/primitives/src/congestion_info.rs` tests around line 723-767).
2. As the assigned chunk producer for the *sender* shard, construct a chunk directly (bypassing `ChunkProducer::prepare_transactions`, e.g. through a custom producer/test-harness path or any future code path that builds `PreparedTransactions`/`ShardChunk` without calling `prepare_transactions`/`prepare_transactions_extra`) containing a valid, well-formed transaction whose `receiver_id` maps to the congested shard.
3. Broadcast the chunk; other validators validate the chunk state witness by calling `apply_new_chunk` → `process_transactions`, which contains no call to `shard_accepts_transactions`/`congestion_control_accepts_transaction`, so the transaction is executed and produces receipts into the already-congested shard, despite `CongestionControl::shard_accepts_transactions()` returning `No(...)` for that shard at that congestion level (verifiable directly via unit test assertions such as `assert!(control.shard_accepts_transactions().is_no())` in `core/primitives/src/congestion_info.rs:736,753`).

    pub fn shard_accepts_transactions(&self) -> ShardAcceptsTransactions {
        let incoming_congestion = self.incoming_congestion();
        let outgoing_congestion = self.outgoing_congestion();
        let memory_congestion = self.memory_congestion();
        let missed_chunks_congestion = self.missed_chunks_congestion();

        let congestion_level = incoming_congestion
            .max(outgoing_congestion)
            .max(memory_congestion)
            .max(missed_chunks_congestion);

        // Convert to NotNan here, if not possible, the max above is already meaningless.
        let congestion_level =
            NotNan::new(congestion_level).unwrap_or_else(|_| NotNan::new(1.0).unwrap());
        if *congestion_level < self.config.reject_tx_congestion_threshold {
            return ShardAcceptsTransactions::Yes;
        }

        let reason = if missed_chunks_congestion >= *congestion_level {
            RejectTransactionReason::MissedChunks { missed_chunks: self.missed_chunks_count }
        } else if incoming_congestion >= *congestion_level {
            RejectTransactionReason::IncomingCongestion { congestion_level }
        } else if outgoing_congestion >= *congestion_level {
            RejectTransactionReason::OutgoingCongestion { congestion_level }
        } else {
            RejectTransactionReason::MemoryCongestion { congestion_level }
        };
        ShardAcceptsTransactions::No(reason)
    }

                    }
                };

            }
        }

/// Returns true if the transaction passes the congestion control checks. The
/// transaction will be accepted if the receiving shard is not congested or its
/// congestion level is below the threshold.
fn congestion_control_accepts_transaction(
    epoch_manager: &dyn EpochManagerAdapter,
    runtime_config: &RuntimeConfig,
    epoch_id: &EpochId,
    prev_block: &PrepareTransactionsBlockContext,
    validated_tx: &ValidatedTransaction,
) -> Result<bool, Error> {
    let receiver_id = validated_tx.receiver_id();
    let receiving_shard = account_id_to_shard_id(epoch_manager, receiver_id, &epoch_id)?;
    let congestion_info = prev_block.congestion_info.get(&receiving_shard);
    let Some(congestion_info) = congestion_info else {
        return Ok(true);
    };

    let congestion_control = CongestionControl::new(
        runtime_config.congestion_control_config,
        congestion_info.congestion_info,
        congestion_info.missed_chunks_count,
    );
    let shard_accepts_transactions = congestion_control.shard_accepts_transactions();
    Ok(shard_accepts_transactions.is_yes())
}
