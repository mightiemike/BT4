### Title
CPU time budget can be exceeded by the last opcode of a transaction before the overrun is detected - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
java-tron enforces a CPU time budget per transaction execution (`Program.checkCPUTimeLimit`), analogous in spirit to Optimism's "nuisance gas" budget: an upper bound on the resource (wall-clock CPU time) a transaction may consume during TVM execution. Like the nuisance-gas bug, the check in `VM.play` is performed *before* each opcode executes, meaning the currently-executing opcode's real cost is only detected against the budget *after* it has already run — the check only detects a breach, it does not preempt it. For the *last* opcode of a transaction, the overrun is only caught by a special post-hoc check in `VMActuator.execute`, guarded by the `allowEnergyAdjustment` (fair energy adjustment) feature switch.

### Finding Description
`VM.play` spends energy and checks the CPU time budget once per opcode, before calling `op.execute(program)`: [1](#0-0) 

Because `checkCPUTimeLimit` runs *before* the opcode executes rather than bounding the opcode's own execution time, a single expensive opcode (e.g., a call into a large/complex contract, an expensive precompiled contract, or a memory/computation-heavy instruction) can push the actual wall-clock time over the allotted budget; this is only detected on the *next* iteration of the loop, not prevented. `checkCPUTimeLimit` itself only compares "now" to `vmShouldEndInUs` and throws if already exceeded: [2](#0-1) 

For the transaction's very last operation, there is no subsequent loop iteration in which `checkCPUTimeLimit` would fire, so the overrun could go completely unnoticed. `VMActuator.execute` explicitly documents and patches this gap only when the `allowEnergyAdjustment` feature is enabled: [3](#0-2) 

This mirrors the nuisance-gas report precisely: the resource-limit mechanism is a *detection* mechanism, not a *prevention* mechanism, so an individual unit of work (an opcode, analogous to Optimism's "call frame") can push total consumption beyond the intended budget "by one operation" before the check reacts, and only a special-cased fix ("checked at the end of tx execution" — comparable to Optimism's PR #1366 "revert pre-emptively" fix) closes the gap, and only when the corresponding feature switch is enabled.

### Impact Explanation
If the CPU-time overrun by the last opcode is not detected (e.g., if `allowEnergyAdjustment` is not active, or the overrun occurs during a call frame that legitimately consumes disproportionate wall-clock time relative to its fixed energy cost), the actual CPU/wall-clock time a witness spends executing/validating a transaction can exceed the fraction of block time budgeted for it (`getVmShouldEndInUs`/block-produced-timeout accounting). A block producer packing many transactions, each engineered to end on a maximally CPU-heavy last opcode, could cause the cumulative real execution time for a block to exceed the intended `blockProducedTimeOut` budget, similar to how, in the nuisance-gas report, many minimal call frames could each exceed their budget by one operation to blow past the transaction-wide budget. This is a potential DoS vector against block production/validation timing (chain-level availability), reachable purely from a broadcast smart-contract-invoking transaction — no privileged access required.

### Likelihood Explanation
This requires the `allowEnergyAdjustment` fair-energy-adjustment proposal to be *disabled* (or a bypass of its intended semantics) for the "last-op" gap to matter, since when it is enabled the post-hoc check reverts (though after CPU time is already spent) the offending transaction. The exploit further depends on crafting an opcode/call sequence whose *actual* execution wall-time is disproportionate to its fixed energy cost — precompiled contracts and large `CALL`-family invocations are the most likely candidates, matching the "interacting with a large contract" theme from the analog bug. Verifying the exact conditions under which `allowEnergyAdjustment` is on/off in production, and quantifying how disproportionate real execution time can get relative to energy cost for specific opcodes, requires further investigation that exceeded the available search budget in this session.

### Recommendation
- Make the CPU-time check unconditional (not gated behind `allowEnergyAdjustment`) for the last opcode of every transaction, and consider bounding the maximum wall-clock cost any single opcode/precompile can incur regardless of energy pricing, rather than only detecting the breach afterward.
- Audit precompiled contracts and `CALL`-family opcodes for cases where energy cost significantly under-prices real CPU time, and align energy pricing with actual node-side execution cost so the budget check reliably bounds real resource consumption instead of merely detecting after the fact.
- Document explicitly, at `Program.checkCPUTimeLimit` and `VMActuator.execute`, that per-opcode checks are pre-emptive detection only and note the residual risk from the final opcode of the call trace.

### Proof of Concept
Not independently verified in this session — a concrete PoC would require constructing a transaction whose last executed opcode invokes a maximally expensive operation (e.g. a `CALL` to a very large/complex contract or an expensive precompile) while `allowEnergyAdjustment` is disabled, then measuring wall-clock execution time against `vmShouldEndInUs`/`blockProducedTimeOut` to demonstrate the overrun escapes detection. This would need to be validated in a running node/test harness, which was not available in this analysis.

  public void checkCPUTimeLimit(String opName) {

    if (CommonParameter.getInstance().isDebug()) {
      return;
    }
    if (CommonParameter.getInstance().isSolidityNode()) {
      return;
    }
    long vmNowInUs = System.nanoTime() / 1000;
    if (vmNowInUs > getVmShouldEndInUs()) {
      logger.info(
          "minTimeRatio: {}, maxTimeRatio: {}, vm should end time in us: {}, "
              + "vm now time in us: {}, vm start time in us: {}",
          CommonParameter.getInstance().getMinTimeRatio(),
          CommonParameter.getInstance().getMaxTimeRatio(),
          getVmShouldEndInUs(), vmNowInUs, getVmStartInUs());
      throw Exception.notEnoughTime(opName);
    }
