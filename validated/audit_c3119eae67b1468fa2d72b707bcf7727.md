### Title
Renderer-controlled frame token in `IndigoImageReplacementManager::ReplacementFrameAttached` allows hijacking an unrelated same-process iframe (confused-deputy iframe takeover) - (File: chrome/browser/indigo/indigo_image_replacement_manager.cc)

### Summary
`IndigoImageReplacementManager::ReplacementFrameAttached()` is a Mojo IPC handler (`blink::mojom::ImageReplacementHost`) that a renderer's content-script-driven `ImageReplacement` remote calls to tell the browser that a subframe used for AI-generated image replacement has attached. The handler resolves the caller-supplied `blink::LocalFrameToken` into a `RenderFrameHost` using the page's own process ID, checks that the resolved frame is *a* child of the page's main document, and then immediately navigates that frame to the trusted Indigo extension UI (`chrome-extension://<indigo id>/index.html`). Nowhere does it verify that the resolved frame token actually corresponds to the specific iframe created for *this* `ImageReplacementHost` receiver's context (i.e., the frame that the content script is supposed to control) - only that some frame in the page happens to be a child of the main document.

This is structurally the same bug class as the reported `V3Vault::transform()` finding: one identifier is validated for authorization purposes (here, "resolves to a frame in this page's own process, and is a child of this page's main document") while a second, attacker-controlled identifier embedded in the message (`replacement_frame_token`) is what is actually operated on, without checking that it belongs to the calling context/resource the caller is authorized to act on.

### Finding Description [1](#0-0) 

Walking through the logic:
- `RegisterImageReplacement()` binds a `mojo::ReceiverSet<blink::mojom::ImageReplacementHost, IndigoImageReplacement>` per page and hands the renderer a `PendingRemote<ImageReplacement>`/receives a `PendingReceiver<ImageReplacementHost>` [2](#0-1) . Multiple `ImageReplacement` instances (primary and non-primary) can be registered for the same page, each with its own receiver context (`IndigoImageReplacement`).
- When `ReplacementFrameAttached(replacement_frame_token, replacement_data)` is invoked over that receiver, the browser resolves the token via `content::RenderFrameHost::FromFrameToken(GlobalRenderFrameHostToken(page's process id, replacement_frame_token))` [3](#0-2) . The process ID half of the lookup is browser-trusted, but the `LocalFrameToken` half is 100% attacker-controlled data coming from the (potentially compromised or malicious-content-script-hosting) renderer.
- The only authorization checks performed are: (1) the resolved frame exists, (2) its parent is the current page's main document, and (3) this particular receiver hasn't already attached a frame [4](#0-3) . There is no check that `replacement_frame_token` refers to the frame *that this specific content script/`ImageReplacement` instance actually created or owns* — any child iframe of the page (e.g., an ad iframe, a cross-origin embed, or an iframe belonging to a *different* `ImageReplacement` registration) satisfies the "is a child of the main document" check.
- Having resolved to that arbitrary sibling frame, the code immediately takes ownership of it: it stores `frame_tree_node_id` in the receiver's context and issues `web_contents->GetController().LoadURLWithParams()` targeting that `frame_tree_node_id`, forcibly navigating the arbitrary child frame to the Indigo extension's own page and replacing the current entry [5](#0-4) .

This mirrors the smart-contract bug's root cause precisely: `V3Vault::transform()` validated ownership of `tokenId` but let a second, unchecked `tokenId` inside `data` be the actual target of the privileged operation. Here, the code validates process/parentage of the *lookup*, but the actual *target resource* (`replacement_frame_token` → `frame_tree_node_id`) is never tied back to the calling `ImageReplacement` instance/content-script context that is supposed to own it.

### Impact Explanation
A page hosting the Indigo image-replacement feature (or its content script running in that renderer process, if compromised via a separate memory-safety bug, or simply behaving maliciously if the "content script" surface is scriptable/attacker-influenced) can supply the `LocalFrameToken` of *any other same-process child frame of the page* — including a cross-origin iframe unrelated to the AI shopping/image-replacement flow — and force the browser to navigate that frame to a browser-privileged extension page, overwriting its contents and current history entry. This is a confused-deputy /iframe-hijack primitive: it lets script-level control over which of the page's iframes gets clobbered and repointed to trusted extension content, which can be leveraged for UI/security spoofing (making attacker content appear to originate from, or replace the display of, another origin's frame) and for corrupting the page's frame/navigation state in ways the embedding site did not authorize. It does not on its own leak cross-origin data, but it is a concrete SOP-adjacent frame-confusion / security-UI-spoofing primitive reachable purely from renderer-side script through a Mojo IPC message with no cross-checked ownership of the target resource — matching the "confused deputy" class explicitly called out as in-scope.

### Likelihood Explanation
Reaching this code requires only that the Indigo image-replacement feature be active for a page (feature-gated by `features::kIndigo`) and that the renderer-side `ImageReplacement`/content-script logic can be induced to call `ReplacementFrameAttached` with an arbitrary `LocalFrameToken` rather than the token of the frame it actually created. Because `LocalFrameToken` values are plain data passed over Mojo and are not renderer-process-enforced to be "the token of a frame I created," any renderer-side code path with access to the bound `ImageReplacementHost` receiver (including a compromised or buggy renderer, which is the standard Chromium sandbox threat model) can supply an arbitrary sibling frame's token. No special flags, extensions, or MITM access are needed — only the feature to be enabled and IPC access from the renderer, which is the intended reachable interface for this Mojo endpoint.

### Recommendation
Track, per `IndigoImageReplacement` receiver context, the specific `FrameTreeNodeId`/frame identity that the content script was instructed to create for that registration (e.g., pass an expected frame token/tracked-element id when `StartReplacement()` is issued, or record the frame that sent the registration IPC), and in `ReplacementFrameAttached()` verify that the resolved frame token matches that expected target rather than merely checking "is a child of the main document." If the token cannot be pre-committed, at minimum ensure the resolved frame is not already owned by a different `IndigoImageReplacement` receiver context and is created for this exact registration flow before navigating it.

### Proof of Concept
Conceptual reproduction (renderer-side, requires ability to drive the `blink::mojom::ImageReplacement`/`ImageReplacementHost` Mojo channel, e.g. via a compromised renderer):
1. Page enables Indigo image replacement; `RegisterImageReplacement()` is called, creating receiver A bound to content-script instance A and its intended subframe `iframeA`.
2. The page also contains an unrelated cross-origin `<iframe id="ads">` (`iframeB`), a normal child of the main document.
3. Over the Mojo pipe for receiver A, instead of sending `iframeA`'s `LocalFrameToken`, the renderer sends `iframeB`'s `LocalFrameToken` to `ReplacementFrameAttached()`.
4. `content::RenderFrameHost::FromFrameToken()` resolves to `iframeB` (same process, child of main document) — passing both checks.
5. The browser stores `iframeB`'s `frame_tree_node_id` in receiver A's context and calls `LoadURLWithParams()` targeting `iframeB`, forcibly navigating the unrelated ad/cross-origin iframe to `chrome-extension://<indigo_extension_id>/index.html`, replacing its content without the page's or that frame's consent.

void IndigoImageReplacementManager::RegisterImageReplacement(
    mojo::PendingRemote<blink::mojom::ImageReplacement> image_replacement,
    bool is_primary) {
  if (is_primary) {
    if (primary_receiver_id_.has_value()) {
      // Registering a new primary replacement (when one was previously
      // registered) triggers a reset of all existing replacements.
      // Note: We don't want to reset the content script here as we're reacting
      // to it registering a new primary replacement.
      Reset(ResetType::kResetReplacementsOnly);
    }
    active_invocation_id_ = g_invocation_id_generator.GenerateNextId();
  } else if (!primary_receiver_id_.has_value()) {
    // We ignore all non primary replacements until a primary replacement is
    // registered.
    return;
  }

  mojo::Remote<blink::mojom::ImageReplacement> remote(
      std::move(image_replacement));
  mojo::PendingRemote<blink::mojom::ImageReplacementHost> host_remote;
  auto host_receiver = host_remote.InitWithNewPipeAndPassReceiver();
  std::optional<int32_t> feature_id;
  if (is_primary) {
    feature_id =
        static_cast<int32_t>(page_content_annotations::TrackedElementFeature::
                                 kIndigoImageReplacement);
  }
  remote->StartReplacement(std::move(host_remote), feature_id);

  auto receiver_id = receivers_.Add(
      this, std::move(host_receiver),
      IndigoImageReplacement(this, std::move(remote), is_primary));
  if (is_primary) {
    primary_receiver_id_ = receiver_id;
  }
}

void IndigoImageReplacementManager::ReplacementFrameAttached(
    const blink::LocalFrameToken& replacement_frame_token,
    blink::mojom::ReplacementDataPtr replacement_data) {
  content::RenderFrameHost* image_replacement_subframe =
      content::RenderFrameHost::FromFrameToken(
          content::GlobalRenderFrameHostToken(
              page().GetMainDocument().GetProcess()->GetID().GetUnsafeValue(),
              replacement_frame_token));
  if (!image_replacement_subframe) {
    // TODO(b/489445294): We should wait for this subframe to be attached,
    // rather than returning early.
    return;
  }

  if (image_replacement_subframe->GetParent() != &page().GetMainDocument()) {
    receivers_.ReportBadMessage(
        "Frame is not a child of the current document!");
    return;
  }

  auto& image_replacement = receivers_.current_context();
  if (image_replacement.frame_tree_node_id()) {
    receivers_.ReportBadMessage("Replacement frame already attached!");
    return;
  }

  content::FrameTreeNodeId frame_tree_node_id =
      image_replacement_subframe->GetFrameTreeNodeId();
  std::vector<uint8_t> image_bytes_copy;
  if (replacement_data->original_image) {
    image_bytes_copy.assign_range(replacement_data->original_image->webp_bytes);
  }
  image_replacement.ReplacementFrameAttached(
      frame_tree_node_id, std::move(image_bytes_copy),
      replacement_data->tracked_element_id, replacement_data->object_fit);

  content::WebContents* web_contents =
      content::WebContents::FromRenderFrameHost(&page().GetMainDocument());

  Profile* profile =
      Profile::FromBrowserContext(web_contents->GetBrowserContext());
  IndigoService* service = IndigoServiceFactory::GetForProfile(profile);
  CHECK(service);
  service->EnsureComponentExtensionRegistered();

  content::NavigationController::LoadURLParams params{
      extensions::Extension::GetResourceURL(
          extensions::Extension::GetBaseURLFromExtensionId(
              extension_misc::kIndigoExtensionId),
          "index.html")};
  params.frame_tree_node_id = frame_tree_node_id;
  params.should_replace_current_entry = true;
  web_contents->GetController().LoadURLWithParams(std::move(params));
