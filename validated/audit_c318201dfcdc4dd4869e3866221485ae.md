### Title
Division-by-zero panic in `accrue`'s treasury-LP mint math can permanently freeze a vault - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Every Zest vault contract (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) computes a `treasury-lp` mint amount inside the public `accrue` function by dividing by `(- (total-assets-preview) reserve-inc)` without ever checking that this subtraction is non-zero, mirroring the Blend `backstop_token_to_base` division-by-zero pattern where an unguarded denominator derived from a shrinking pool value can round/reduce to zero and panic.

### Finding Description
`accrue` in each vault contract computes: [1](#0-0) 

```clarity
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```

`total-assets-preview` is `current-assets + interest`, where `current-assets` is the vault's idle underlying balance and `interest` is the freshly-accrued debt increment (`debt-preview - total-borrowed`, floored at zero): [2](#0-1) 

`reserve-inc` is a fraction of `debt-delta` (which itself tracks the interest increment) scaled by `fee-reserve/BPS`. If the vault is fully utilized (`current-assets = 0`, i.e. all liquidity has been borrowed out) and the fee-reserve parameter is at its maximum allowed value (`fee-reserve == BPS`, i.e. 100%), then:

```
ta-preview = 0 + interest = interest
reserve-inc = interest * BPS / BPS = interest
(- ta-preview reserve-inc) = interest - interest = 0
```

`mul-div-down reserve-inc (total-supply) 0` then divides by zero and panics, aborting the entire transaction. Because `accrue` is invoked at the top of essentially every state-mutating vault entrypoint (`system-borrow`, `system-repay`, deposit/redeem paths), this panic reproduces on every subsequent call as long as the same zero-denominator condition (fully-utilized vault + accrued interest + `fee-reserve = BPS`) persists, since no successful call can execute to change `current-assets` or accrued interest away from the triggering state.

### Impact Explanation
Once triggered, every operation that calls `accrue` (borrow, repay, deposit, redeem) on the affected vault reverts with a runtime panic, since the vault cannot process any transaction without first calling the now-perpetually-failing `accrue`. This is a temporary/potentially indefinite freezing of funds: depositors cannot withdraw, borrowers cannot repay to unwind their positions, and the vault is effectively bricked until the specific numeric condition (interest exactly equal to the reserve cut with a fully-depleted idle balance) no longer holds — which, given the call itself cannot succeed to change state, can require external/admin intervention (e.g., lowering `fee-reserve` via DAO config) to recover. This falls under "temporary freezing of funds."

### Likelihood Explanation
Reaching `current-assets = 0` (full utilization) is achievable through normal borrowing activity and is not itself a privileged action. However, triggering the exact zero-denominator condition additionally requires `fee-reserve` to be configured at its maximum value (`BPS`, 100%), which is a DAO/admin-controlled parameter; I was unable to conclusively verify the enforced upper bound on `fee-reserve` in the setter within the available context. If the protocol enforces `fee-reserve < BPS` strictly, the denominator can never reach exactly zero under this exact scenario, which would reduce/eliminate likelihood. Given this open question, likelihood should be treated as low-to-medium pending confirmation of the `fee-reserve` bound.

### Recommendation
Add an explicit guard around the treasury-lp calculation, e.g.:
```clarity
(treasury-lp (if (and (> reserve-inc u0) (> ta-preview reserve-inc))
                 (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
                 u0))
```
Additionally, cap `fee-reserve` strictly below `BPS` (e.g., `< BPS`) at the setter level to guarantee the denominator is always strictly positive whenever `reserve-inc > 0`.

### Proof of Concept
1. Vault reaches full utilization: all idle liquidity is borrowed out via repeated `system-borrow`, so `current-assets = 0` [3](#0-2) .
2. DAO/admin configuration sets `fee-reserve` to its maximum permitted value (verification of the exact cap was not completed in this session).
3. Time passes so `next-index` accrues interest, making `debt-delta > 0` and thus `reserve-inc > 0` and `ta-preview = interest` [4](#0-3) .
4. Any call that triggers `accrue` (e.g. `system-borrow`, `system-repay`) computes `(- ta-preview reserve-inc)` = 0 and panics on `mul-div-down` division, reverting the transaction.
5. Because every subsequent vault operation also calls `accrue` under the same unresolved state, the vault becomes stuck, freezing depositor/borrower funds until the triggering condition is externally remediated.

Note: I could not verify the exact upper bound enforced on `fee-reserve` in the setter function within the available indexed context; confirming this bound (whether it is capped strictly below `BPS`) is necessary to fully validate reachability of the exact zero-denominator edge case. If more certainty is needed, a Devin session with full repository access could inspect the `fee-reserve` setter and any associated cap validation directly.
