### Title
Voting-accrued TRX rewards for smart-contract accounts can become permanently unclaimable - ([File: actuator/src/main/java/org/tron/core/actuator/WithdrawBalanceActuator.java])

### Summary
The reported bug class is: a claim/withdraw function restricts the caller to a specific "receiver" address, but that address can be a smart contract with no built-in ability to originate the call itself, permanently locking the funds. The same structural pattern exists in java-tron's voting-reward flow: rewards ("allowance") accrue to a voter address, and the only ways to release that allowance require an action that must originate from that exact address — which is impossible for an ordinary smart-contract account.

### Finding Description
A TRON account can vote for witnesses either through the normal `VoteWitnessContract` actuator, or from inside a smart contract via the TVM `VOTEWITNESS`/`WITHDRAWREWARD` opcodes, which are implemented by `VoteWitnessProcessor.execute()` [1](#0-0)  and `WithdrawRewardProcessor` respectively [2](#0-1) . Voting rewards accumulate into the account's `allowance` field via `MortgageService.payReward()`/`adjustAllowance()` [3](#0-2) .

There are exactly two ways to move that `allowance` into spendable `balance`:
1. `WithdrawBalanceActuator`, an outer, top-level transaction whose `ownerAddress` must match the transaction's cryptographic signer [4](#0-3) .
2. The TVM `WITHDRAWREWARD` opcode (`Program.withdrawReward()`), which always uses `getContextAddress()` — i.e. the currently executing contract's own address — as the owner, and can only be triggered by that contract's own bytecode logic [5](#0-4) .

This mirrors the audited bug precisely: just as `claimRoyalties()` hard-codes `receiver == msg.sender`, java-tron hard-codes the reward owner to either (a) the outer transaction's signer, or (b) the calling contract's own execution context — there is no "claim on behalf of" path. If the voting/reward-accruing address is a smart-contract account (deployed via `CREATE`/`CREATE2`, which has no private key), path (1) is permanently impossible because no signature can ever be produced for that address, and path (2) only works if that exact contract's bytecode happens to contain logic that calls `WITHDRAWREWARD`/triggers `WithdrawRewardProcessor`. Contract accounts that only vote (e.g., via `VOTEWITNESS` from a delegate/proxy call, or a contract that received votes indirectly) but were never coded to also invoke the withdraw opcode have no way for anyone — owner, deployer, or third party — to ever release the accumulated TRX allowance.

### Impact Explanation
Voting rewards paid to a smart-contract voter address can become permanently stuck if the contract's bytecode does not itself implement a call to the reward-withdrawal opcode. Unlike a normal EOA, which always has some agent capable of producing a signature, a contract account has no owner able to force a top-level `WithdrawBalanceContract` transaction. This is an asset/accounting corruption issue (funds accounted as belonging to an address but structurally unclaimable), analogous to the disclosed royalties-stuck issue, though it requires that a smart-contract account be used as a voter/reward recipient without a matching withdrawal function in its logic.

### Likelihood Explanation
Likelihood is moderate: it requires a smart contract to accumulate voting rewards (e.g., contracts holding frozen TRX/voting for witnesses on behalf of users, common in staking-aggregator contracts) without including reward-withdrawal logic, or with logic that becomes unreachable (e.g., due to an upgrade, a bug, or restrictive access control in the calling contract). This is a design/no-escape-hatch issue rather than an actively exploitable attack by a third party, since no external caller can force the release either.

### Recommendation
Because I was unable to fully verify (in the remaining iteration budget) whether any alternate top-level path exists that lets a third party trigger `WithdrawBalanceActuator`/`WithdrawRewardProcessor` on behalf of a contract address (e.g., via `TriggerSmartContract` delegatecall patterns), this should be validated further. Assuming no such path exists, consider adding a permissionless "withdraw-for" mechanism analogous to the report's mitigation: allow any caller to trigger `WithdrawRewardProcessor`/`MortgageService.withdrawReward()` on behalf of a target address when that address is a deployed smart contract (verifiable via `AccountStore`/`ContractStore` lookup), crediting the reward directly to that contract's balance rather than requiring the contract's own signature or self-triggered opcode call.

### Proof of Concept
Conceptual PoC (not independently executed against a live node):
1. Deploy a smart contract `C` that only implements a `vote(witness, count)` function calling the `VOTEWITNESS` opcode, with no function that calls `WITHDRAWREWARD`.
2. Have `C` vote for an active witness; over multiple maintenance cycles, `MortgageService.payReward()`/`adjustAllowance()` credits `allowance` to `C`'s `AccountCapsule` [3](#0-2) .
3. Attempt to submit `WithdrawBalanceContract` with `ownerAddress = C` — this can never be signed because `C` has no private key, so `validate()`/signature verification will always fail [6](#0-5) .
4. Attempt to trigger `WITHDRAWREWARD` from any other contract/account targeting `C`'s allowance — impossible, since `Program.withdrawReward()` always uses the caller's own `getContextAddress()` as owner [7](#0-6) .
5. Result: `C`'s accrued `allowance` remains permanently locked in `AccountStore` with no code path to convert it to spendable `balance`.

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
