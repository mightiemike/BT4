### Title
Borrower can self-liquidate their own position via `liquidate()` to capture the liquidation bonus and offload bad debt to vault depositors - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` never checks whether `contract-caller` (the liquidator) is the same principal as `borrower`. This mirrors the reported `BountyV1.sol` class of bug where a single actor is allowed to occupy both sides of an economic mechanism (funder/submitter here becomes borrower/liquidator) without any restriction, letting that actor extract value that the mechanism was designed to pay to an independent third party.

### Finding Description
`liquidate()` computes `liquidator` as `contract-caller` and defaults the collateral `actual-receiver` to that same `liquidator` when `collateral-receiver` is not supplied: [1](#0-0) [2](#0-1) 

The only preconditions checked are that the position's current LTV is above `ltv-liq-partial`, the caller is `tx-sender`, amounts are non-zero, slippage is respected, and liquidation is not paused: [3](#0-2) 

At no point does the function assert `(not (is-eq contract-caller borrower))`. This is the same root cause pattern as the reported issue in `BountyV1.sol`, where `approveSubmission()`/`makeSubmission()` never checked `msg.sender != funder`. There, the funder role and the submitter role were allowed to be occupied by the same address; here, the borrower role and the liquidator role are allowed to be occupied by the same address.

This matters because unlike `collateral-remove`/`repay`, which enforce a **post-condition health check** (the resulting position must remain healthy) before releasing collateral: [4](#0-3) 

`liquidate()` has no such post-condition — it is designed to release *more* collateral value than the debt repaid (the liquidation penalty/bonus), on the assumption that this bonus compensates an *independent* liquidator for taking on risk on behalf of the protocol. If the borrower is also the liquidator, they simply route this bonus back to themselves while any resulting collateral shortfall is later socialized as bad debt against vault depositors: [5](#0-4) 

### Impact Explanation
By self-liquidating, a borrower captures the liquidation bonus (`liq-penalty`) that is meant to reward an independent third-party liquidator for repairing risk to the protocol. Because the collateral routed to `actual-receiver` goes back to the same person who owes the debt, the borrower extracts collateral value disproportionate to the debt actually repaid, without any post-action health check limiting the extraction (unlike normal `collateral-remove`). Repeating this while the position stays above `ltv-liq-partial` lets a borrower drain their own collateral position preferentially, and once collateral runs out, the remaining debt is socialized via `socialize-debt-asset`, spreading losses onto other vault depositors. This is a theft-of-user-funds / protocol-insolvency vector on the vault side (impact: Critical — theft of funds at rest belonging to other depositors / protocol insolvency).

### Likelihood Explanation
This requires no privileged access, no oracle manipulation, and no interference between two different users — it is purely a single-actor action. Any borrower whose position crosses `ltv-liq-partial` (which they can also engineer, e.g. via price movement or by deliberately borrowing near the threshold) can call `liquidate()` on themselves at will, using ordinary token approvals for the debt asset they already hold. This makes the likelihood high whenever a position is at or near the partial-liquidation threshold.

### Recommendation
Add an explicit check in `liquidate()` (and `liquidate-redeem` / `liquidate-multi` call paths) that `contract-caller` (or `tx-sender`) is not equal to `borrower`, e.g. `(asserts! (not (is-eq contract-caller borrower)) ERR-SELF-LIQUIDATION)`, mirroring the acknowledgment pattern the client used for the analogous bounty report: if self-liquidation is to be permitted at all, ensure the bonus/penalty economics cannot be captured back by the same address, or cap self-directed extraction to be equivalent to a normal health-checked `repay` + `collateral-remove`.

### Proof of Concept
1. Borrower deposits collateral and borrows near the max `LTV-BORROW` threshold using `borrow()`. [6](#0-5) 
2. Price moves (or time passes) such that current LTV crosses `ltv-liq-partial` but not yet `ltv-liq-full`.
3. The same borrower principal calls `liquidate(borrower=self, collateral-ft, debt-ft, debt-amount, min-collateral-expected, collateral-receiver=none, price-feeds)` as `contract-caller`. [7](#0-6) 
4. `health-check` passes because LTV ≥ `ltv-liq-partial`; no check blocks `contract-caller == borrower`. [8](#0-7) 
5. `coll-final` (computed with the liquidation bonus `liq-penalty`) is transferred to `actual-receiver`, which defaults to `liquidator` = the borrower themselves. [9](#0-8) 
6. The borrower has effectively withdrawn collateral at a bonus rate without the post-condition health check that a normal `collateral-remove` would require, and can repeat while still above `ltv-liq-partial`. Any resulting collateral shortfall is later socialized against the vault's other depositors via `socialize-debt-asset`. [5](#0-4)
