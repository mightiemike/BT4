### Title
Backup restore of a transaction chunk persists `WriteSet` data that is never authenticated against the accumulator-proven `TransactionInfo.state_change_hash` - (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`, `storage/aptosdb/src/backup/restore_utils.rs`)

### Summary
`LoadedChunk::load` verifies a downloaded transaction backup chunk using `TransactionListWithProof`/`TransactionListWithProofV2`, which authenticates transaction hashes and event root hashes against the accumulator-proven `TransactionInfo`, but this proof object does not carry or check `WriteSet` data at all. The `write_sets` vector is read from the same backup file and pushed alongside `txns`/`txn_infos`/`events` without ever being checked against `TransactionInfo::state_change_hash()`. These unauthenticated write sets are subsequently persisted straight into the ledger DB by `save_transactions`/`save_transactions_impl`.

### Finding Description
The transaction-output backup/restore path authenticates write sets: `TransactionOutputListWithProof::verify` (`types/src/transaction/mod.rs:2941-3022`) explicitly computes `CryptoHash::hash(&txn_output.write_set)` and checks it equals `txn_info.state_change_hash()`.

The plain transaction-backup path used by `TransactionRestoreController`/`LoadedChunk::load` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs:156-186`) instead builds a `TransactionListWithProofV2`/`TransactionListWithProof` (`types/src/transaction/mod.rs:2681-2753`), whose `verify()` only checks:
- first-transaction-version match,
- `txn_hash == txn_info.transaction_hash()`,
- the accumulator proof from ledger info to the `TransactionInfo`s,
- optional event-root-hash equality.

Nowhere in this `verify()` is `write_set` referenced, because `TransactionListWithProof` has no `write_set` field at all — write sets for this backup format are carried in a completely separate, parallel vector (`write_sets: Vec<WriteSet>` in `LoadedChunk`) that is populated purely positionally in the same read loop (`restore.rs:105-137`) and is never fed into, or checked by, the cryptographic verification call at `restore.rs:167` (`txn_list_with_proof.verify(...)`).

After `verify()` succeeds, the same unverified `write_sets` are handed to `restore_handler.save_transactions(...)` (`restore.rs:507-517`) which flows into `save_transactions` / `save_transactions_impl` (`storage/aptosdb/src/backup/restore_utils.rs:115-176`, `193-292`). That function writes `txn_infos` (whose `state_change_hash` is the *authenticated* one) into `transaction_info_db()`/`transaction_accumulator_db()` and independently writes the attacker/storage-controlled `write_sets` into `write_set_db_batches` and, when `kv_replay` is set, feeds them into `state_store.calculate_state_and_put_updates(...)` to materialize actual state values — all without ever checking `CryptoHash::hash(write_set) == txn_info.state_change_hash()`.

This breaks the "VM outputs / write sets must survive executor-to-storage handoff unchanged" and "proof-bearing data must stay bound to the correct root" invariants explicitly called out in the review scope: the `TransactionInfo` (and its accumulator-proven `state_change_hash`) is proven authentic, but the `WriteSet` actually committed to storage under that same version is not bound to that authenticated hash in this specific restore code path.

### Impact Explanation
A party that can influence the contents of a transaction backup archive (e.g., a compromised/malicious backup storage backend, or corrupted/tampered backup files restored by an operator) can substitute an arbitrary `WriteSet` for any transaction while keeping the transaction and its `TransactionInfo`/proof intact. Restoring from such a chunk would pass all of `LoadedChunk::load`'s cryptographic checks yet install state values into the restored `AptosDB` (via `write_set_db_batches` and, in `kv_replay` mode, into the actual state tree) that diverge from the correct, VM-produced/consensus-committed state — i.e., committed ledger state differing from the true result while still appearing "verified" by the backup/restore tooling. This is a state-commitment integrity break in the restore path, matching the "Committed state that differs from the correct VM result or corrupts durable ledger data" and "restore" bullets in the state-integrity gate.

### Likelihood Explanation
Exploitability depends entirely on control over the backup artifact content (backup storage compromise, MITM on backup transport, or a corrupted/adversarial backup source) — this is not exploitable by a purely passive network observer, but is squarely in-scope as a restore/proof-integrity gap rather than a privileged-admin assumption, since the whole point of accumulator proofs in backups is to make restore safe even from an untrusted backup store. I was not able to fully verify, within the available iterations, whether `verify_execution_mode`/subsequent chunk-executor replay (the "replay" path, as opposed to "save before replay" path) independently recomputes and cross-checks the write set against VM execution before commit — that would mitigate impact only for versions after `replay_from_version`, but versions saved via `save_before_replay_version` (the common default, no replay) are directly persisted with no such check.

### Recommendation
In `LoadedChunk::load` (or in `TransactionListWithProof`/a new verification helper), verify each `write_set` against `txn_info.state_change_hash()` (as already done in `TransactionOutputListWithProof::verify`) before the chunk is accepted, and reject/fail restoration if any mismatch is found — mirroring the length/hash cross-check pattern recommended for the original Solidity report, generalized to "no unauthenticated data may be committed alongside authenticated `TransactionInfo`s."

### Proof of Concept
Conceptual PoC (cannot be executed in this read-only review):
1. Take a valid transaction backup chunk file (`TransactionChunkFormat::V1`, BCS records of `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, Vec<ContractEvent>, WriteSet)`).
2. For one record, replace the `WriteSet` bytes with a different, structurally valid `WriteSet` (e.g., crediting an attacker's account) while leaving `Transaction`, `PersistedAuxiliaryInfo`, `TransactionInfo`, and `Vec<ContractEvent>` untouched (so `transaction_hash`/`event_root_hash`/accumulator proof still validate).
3. Point `aptos-db-restore` (or `TransactionRestoreController`) at this tampered chunk.
4. `LoadedChunk::load` → `txn_list_with_proof.verify(...)` succeeds (transaction hash, event hash, and accumulator proof all still match).
5. `save_before_replay_version` → `restore_handler.save_transactions(...)` → `save_transactions_impl` persists the tampered `WriteSet` into `write_set_db_batches`, and if `kv_replay` is enabled, `calculate_state_and_put_updates` materializes the forged state values into the state tree — with no error raised, despite `CryptoHash::hash(tampered_write_set) != txn_info.state_change_hash()`.     pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }

pub(crate) fn save_transactions_impl(
    state_store: Arc<StateStore>,
    ledger_db: Arc<LedgerDb>,
    first_version: Version,
    txns: &[Transaction],
    persisted_aux_info: &[PersistedAuxiliaryInfo],
    txn_infos: &[TransactionInfo],
    events: &[Vec<ContractEvent>],
    write_sets: &[WriteSet],
    ledger_db_batch: &mut LedgerDbSchemaBatches,
    state_kv_batches: &mut ShardedStateKvSchemaBatch,
    kv_replay: bool,
) -> Result<()> {
    for (idx, txn) in txns.iter().enumerate() {
        ledger_db.transaction_db().put_transaction(
            first_version + idx as Version,
            txn,
            /*skip_index=*/ false,
            &mut ledger_db_batch.transaction_db_batches,
        )?;
    }

    for (idx, aux_info) in persisted_aux_info.iter().enumerate() {
        PersistedAuxiliaryInfoDb::put_persisted_auxiliary_info(
            first_version + idx as Version,
            aux_info,
            &mut ledger_db_batch.persisted_auxiliary_info_db_batches,
        )?;
    }

    for (idx, txn_info) in txn_infos.iter().enumerate() {
        TransactionInfoDb::put_transaction_info(
            first_version + idx as Version,
            txn_info,
            &mut ledger_db_batch.transaction_info_db_batches,
        )?;
    }

    ledger_db
        .transaction_accumulator_db()
        .put_transaction_accumulator(
            first_version,
            txn_infos,
            &mut ledger_db_batch.transaction_accumulator_db_batches,
        )?;

    ledger_db.event_db().put_events_multiple_versions(
        first_version,
        events,
        &mut ledger_db_batch.event_db_batches,
    )?;

    for (idx, txn_events) in events.iter().enumerate() {
        for event in txn_events {
            if let Some(event_key) = event.event_key() {
                if *event_key == new_block_event_key() {
                    LedgerMetadataDb::put_block_info(
                        first_version + idx as Version,
                        event,
                        &mut ledger_db_batch.ledger_metadata_db_batches,
                    )?;
                }
            }
        }
    }
    // insert changes in write set schema batch
    for (idx, ws) in write_sets.iter().enumerate() {
        WriteSetDb::put_write_set(
            first_version + idx as Version,
            ws,
            &mut ledger_db_batch.write_set_db_batches,
        )?;
    }

    if kv_replay && first_version > 0 && state_store.get_usage(Some(first_version - 1)).is_ok() {
        let (ledger_state, _hot_state_updates) = state_store.calculate_state_and_put_updates(
            &StateUpdateRefs::index_write_sets(first_version, write_sets, write_sets.len(), vec![]),
            &mut ledger_db_batch.ledger_metadata_db_batches, // used for storing the storage usage
            state_kv_batches,
        )?;
        // n.b. ideally this is set after the batches are committed
        state_store.set_state_ignoring_summary(ledger_state);
    }
