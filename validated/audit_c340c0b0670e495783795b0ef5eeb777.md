### Title
Unbounded JSON-RPC batch size allows single-request DoS via serial sub-request dispatch - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java])

### Summary
`JsonRpcServlet.doPost` only rejects an oversized batch array when `jsonRpcMaxBatchSize > 0`; when this parameter is left disabled (its zero/default state), an attacker can submit a single POST containing an arbitrarily large JSON array, and `handleBatch` will serially re-serialize (`MAPPER.writeValueAsBytes`) and dispatch (`rpcServer.handleRequest`) every sub-request within one servlet thread. This lets one HTTP request consume disproportionate CPU/thread time relative to the single rate-limiter permit it costs.

### Finding Description
In `doPost`, the only batch-size guard is: [1](#0-0) 
If `jsonRpcMaxBatchSize` is `0` (disabled) or configured very high, this check never fires, and `rootNode.size()` is unbounded going into `handleBatch`.

`handleBatch` then iterates every element, re-serializing and independently dispatching each sub-request through `rpcServer.handleRequest`, all inside the same thread that handled the original HTTP request: [2](#0-1) 

`readBody` also imposes no cap on total input size before parsing: [3](#0-2) 

The servlet-level protection, `RateLimiterServlet.service`, only gates the QPS/permit for the *outer* HTTP request (one token consumed for the whole batch), not per-sub-request cost: [4](#0-3) 

This means the fee/rate-limit budget accounted for is "1 request," while the actual work performed is O(N) full JSON-RPC dispatches (each potentially invoking heavy `eth_call`/contract-simulation logic with attacker-supplied `params`), a mismatch that violates faithful metering: the attacker pays for one QPS slot but consumes N times the compute.

### Impact Explanation
This is a scoped DoS via RPC-API: a single crafted POST can occupy a Tomcat/servlet worker thread for a duration proportional to N (number of batch sub-requests) rather than proportional to the single rate-limited unit of work the throttling system assumes. With enough concurrent large batches, this can exhaust the servlet thread pool and stall other RPC clients, degrading node RPC availability without any privileged access, signed transaction, or on-chain fee payment.

### Likelihood Explanation
Preconditions: `jsonRpcMaxBatchSize` must be disabled (0) or set to a very large value — this is the parameter's zero-cost/default-permissive state defined in `CommonParameter`/`Args`. No signature, no funded account, no on-chain fee is required — this is a pure HTTP/JSON-RPC endpoint reachable by any anonymous client. The cost to the attacker is only the bandwidth to send one large batch array; repeatability is trivial (fuzz N upward). Whether this is reachable "out of the box" depends on the shipped default for `jsonRpcMaxBatchSize` in `config.conf`/`reference.conf`, which was not fully confirmed in this pass — if the default ships with a reasonable positive cap, this finding requires a non-default configuration and would fall outside the accepted attacker model.

### Recommendation
Enforce an always-on, non-zero default upper bound for JSON-RPC batch size (do not treat `0`/negative as "unlimited"); additionally cap cumulative processing cost per batch (e.g., total re-serialized bytes, or per-sub-request timeout) independent of the `jsonRpcMaxBatchSize > 0` gate, and consider charging the rate limiter proportionally to `rootNode.size()` rather than once per HTTP request.

### Proof of Concept
```
POST /jsonrpc HTTP/1.1
Content-Type: application/json

[
  {"jsonrpc":"2.0","id":1,"method":"eth_call","params":[{"to":"0x...","data":"0x<heavy calldata>"},"latest"]},
  {"jsonrpc":"2.0","id":2,"method":"eth_call","params":[{"to":"0x...","data":"0x<heavy calldata>"},"latest"]},
  ... (repeat N times, N = 50,000)
]
```
Expected observation (with `jsonRpcMaxBatchSize` unset/0): server response latency grows non-linearly with N (measured via repeated requests with increasing N), and concurrent smaller RPC requests from other clients experience increased latency/timeouts while the batch is being processed, demonstrating thread-pool starvation from a single request that consumed only one rate-limiter permit.
