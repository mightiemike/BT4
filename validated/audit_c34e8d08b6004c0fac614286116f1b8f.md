### Title
Witness brokerage fee truncates to zero for small reward values in `payReward` - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payReward` computes a witness's brokerage cut of a block/transaction-fee reward using floating point multiplication followed by a truncating cast to `long`. For small `value` amounts (or brokerage percentages that produce a fractional product below 1), `brokerageAmount` truncates to `0`, so the witness never receives the self-allocated brokerage share it configured, mirroring the `Fund.finalizeGrant` integer-division-to-zero bug class from the external report.

### Finding Description
The `payReward` method reads the witness's configured `brokerage` (0-100, set via `UpdateBrokerageActuator`, a broadcast `UpdateBrokerageContract` transaction) and computes: [1](#0-0) 

`brokerageRate = brokerage / 100.0`, and `brokerageAmount = (long)(brokerageRate * value)`. When `value` is small (e.g. tiny per-block transaction-fee rewards distributed to many standby witnesses, or small `pay` amounts from `payStandbyWitness`) and/or `brokerage` is not close to 100, `brokerageRate * value` can be `< 1`, and the truncating cast to `long` rounds it down to `0`. `value` itself is then unaffected (`value -= 0`), so the full `value` is credited to `delegationStore.addReward` while the witness's `adjustAllowance` brokerage cut is `0`, even though the witness explicitly configured a non-zero brokerage percentage.

This is structurally identical to the reported bug class: a percentage-based fee (`grant.value/100` in the report, `brokerageRate*value` here) truncates to zero for small base values, silently denying the intended fee/reward recipient (the admin in the report, the witness here) their due share.

Unlike the Endaoment case, the split here is internally consistent — the truncated amount is not lost from the system (it stays as `value` credited to the reward pool rather than the witness's own allowance) — but the witness is still systematically deprived of the brokerage percentage it configured whenever rewards are small, which repeats every block/transaction-fee distribution cycle. [2](#0-1) 

### Impact Explanation
This falls under resource/reward accounting corruption: witnesses can be underpaid their configured brokerage indefinitely for small per-block/per-standby-witness reward slices, which recur on every block across the network. While each individual truncation is small, over the network's operational lifetime this leads to a persistent, silent divergence between the brokerage rate a witness configured and the rate actually paid, corrupting the reward-accounting invariant that brokerage should always reflect the configured percentage.

### Likelihood Explanation
The condition (`brokerageRate * value < 1`) is readily reachable: `payStandbyWitness` distributes `totalPay` split by vote proportion across up to 127 standby witnesses, producing small `pay` values, and `payTransactionFeeReward` is invoked per-transaction with fee amounts that can be small relative to `brokerage` percentage. Any witness that sets a low-to-moderate brokerage (via the broadcastable `UpdateBrokerageContract`) is likely to periodically receive `brokerageAmount == 0` for legitimate reward payouts, making this a common, not just theoretical, occurrence.

### Recommendation
Compute the brokerage split using integer/BigInteger arithmetic consistent with the rest of the reward-processing code (which already uses `BigInteger`-based hardened calculations elsewhere, e.g. in `ResourceProcessor`/`EnergyProcessor`), e.g. `brokerageAmount = value * brokerage / 100` using `Math.multiplyExact`/`BigInteger` to avoid precision loss from `double`, and consider accumulating fractional remainders across payments so that, over time, the witness's total received brokerage converges to the configured percentage rather than being lost by repeated truncation.

### Proof of Concept
1. A witness calls `UpdateBrokerageContract` to set `brokerage = 50` (50%) — allowed by `UpdateBrokerageActuator.validate` since `0 <= 50 <= 100`. [3](#0-2) 
2. During block production, `MortgageService.payStandbyWitness` (or `payTransactionFeeReward`) calls `payReward(witnessAddress, value)` with a small `value`, e.g. `value = 1` sun.
3. `brokerageRate = 50/100.0 = 0.5`; `brokerageAmount = (long)(0.5 * 1) = 0`.
4. `adjustAllowance(witnessAddress, 0)` is called — the witness receives no brokerage despite configuring 50%, while `delegationStore.addReward` receives the full `value = 1`.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
