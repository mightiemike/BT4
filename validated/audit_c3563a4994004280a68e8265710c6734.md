`ensure_match_transaction_info` skips state/hot-state/position checkpoint-hash validation, letting a diverging state root pass replay-verify and backup-restore checks - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole per-transaction integrity gate used by chunk-executor's `verify_execution`, `db-tool`'s `replay_on_archive`, and the CLI/debugger replay paths to confirm that locally re-executed output matches an authenticated `TransactionInfo` (one that ultimately traces back, via a transaction-accumulator proof, to a validator-signed `LedgerInfo`). The function checks `status`, `gas_used`, `write_set_hash` (`state_change_hash`), and `event_root_hash`, but explicitly and admittedly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the resulting state Merkle root(s). This is called out in-code as a known, unresolved gap.

### Finding Description
`TransactionInfo` carries several distinct commitments: `state_change_hash` (hash of the write set), `event_root_hash`, and (optionally) `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` (roots of the JMT-based global/hot/position state trees at checkpoint boundaries). These checkpoint hashes are what actually bind a transaction's execution to the durable, authenticated ledger *state* (as opposed to just the write set it produced).

`ensure_match_transaction_info` at [1](#0-0)  validates status, gas, and `write_set_hash`, and separately validates `event_root_hash` at [2](#0-1) , but then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against anything computed locally. The in-code TODO makes this explicit: [3](#0-2) 

This function is the only per-transaction cross-check used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which re-executes a range of transactions and compares against externally supplied `transaction_infos`/`write_sets`/`events` during backup-verify/replay-verify flows: [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the standalone "replay-verify" tool operators run to confirm that an archived backup, when re-executed, reproduces exactly the historical outputs: [5](#0-4) 
- `aptos-move/cli/src/commands.rs` transaction-replay/simulation output comparison: [6](#0-5) 

Because the write set is compared only via its hash (`state_change_hash`), and never against the resulting Merkle root of the state tree it produces, any bug or divergence purely in *state-tree construction/application* (e.g. in `StateStore::put_state_updates`/state summary computation, JMT node hashing, hot-state promotion logic, or the newer position/"trading-native" state tree noted in the TODO) — as opposed to a bug in write-set *generation* — would leave `write_set_hash` and `event_root_hash` matching while the actual committed state root silently diverges. None of the callers above would detect or report this divergence.

### Impact Explanation
This breaks the intended integrity guarantee of replay-verification: `replay_on_archive` and `verify_execution` exist specifically so that a full node (or auditor) can prove that re-executing archived transaction history reproduces the exact same ledger state that validators originally committed and signed. Skipping checkpoint-hash comparison means these tools can report "replay verified successfully" even though the freshly computed state Merkle root (and thus every derived state proof, state value, or API response served from that restored/verified DB) differs from the authentic chain state. This is a genuine proof-integrity gap on the exact pivot called out in the task ("Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding") and directly enables committed/restored state to silently diverge from the correct result without any error surfaced by the standard verification tooling.

The severity is bounded by two factors I could not fully resolve given available context (see Likelihood/uncertainty below): (1) this gate only *detects* divergence — it does not itself corrupt a live, consensus-committed database (a live validator's committed root_hash is computed and gossiped independently, and BFT consensus over `LedgerInfo` is a separate check not gated by this function); (2) it primarily affects offline/backup verification and chunk-executor `verify_execution` (state-sync catch-up and backup-restore-verify), not the online execute→commit path, since normal block commit does not call `ensure_match_transaction_info`.

### Likelihood Explanation
This is a missing-check defect, not something requiring active exploitation by an unprivileged attacker to trigger — it triggers automatically whenever there is *any* divergence between locally computed state-tree roots and the authenticated ones (a latent implementation bug, an unintentional non-determinism in state-tree construction, or a compromised/buggy backup source feeding a technically-consistent write set with a differently-computed state root). The TODO comment indicates the aptos-core maintainers are aware this must be fixed before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (referenced in `types/src/on_chain_config/aptos_features.rs` and `types/src/block_executor/config.rs`), which suggests the feature/checkpoint fields in question may not yet be fully active in production, tempering immediate exploitability. I was not able to fully confirm within the available turns whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet or whether `state_checkpoint_hash`/`hot_state_checkpoint_hash` divergence (independent of the "trading-native" feature) is already exercised by mainline replay-verify today — this uncertainty affects whether the gap is already live for the base `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields versus only the newer position-state field.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/expected) between the locally computed output and the trusted `TransactionInfo`, and fail with the same `ERR_MSG` pattern on mismatch, mirroring the treatment already given to `write_set_hash` and `event_root_hash`. This should be resolved before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, and ideally is backported as a general hardening fix independent of that feature flag, so that `replay_on_archive` and `chunk_executor::verify_execution` genuinely prove state-tree consistency, not just write-set/event consistency.

### Proof of Concept
Conceptual (no live exploit possible from static review alone):
1. Introduce (or trigger via an existing latent bug) a divergence purely in state-tree application — e.g., a JMT/state-store code path that applies the same `WriteSet` but produces a different Merkle root (this is exactly the class of bug the in-code TODO anticipates for the "trading-native"/position state tree).
2. Run `db-tool replay-on-archive` (or `chunk_executor::verify_execution` via backup restore in verify mode) over the affected version range.

4. The tool reports the range as successfully verified/replayed, despite the locally materialized state Merkle root (and any state stored under it) diverging from the authentic, validator-attested state at that version. [7](#0-6)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
