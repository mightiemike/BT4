### Title
Signature malleability in `ValidateMultiSign` precompile allows a single private key to be counted twice toward the multisig weight threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract computes ECDSA signature validity via `recoverAddrBySign`, which accepts any `(r, s)` pair satisfying only `1 <= r,s < SECP256K1N` (no canonical low-`s` enforcement), and de-duplicates repeated signers by comparing the *exact signature bytes* rather than solely the recovered address. This allows one private key to produce two distinct, both-valid byte-level signatures over the same message (`(r, s)` and `(r, n-s)` with flipped recovery id), each of which is accepted by the weight-counting loop as a separate approval.

### Finding Description
`ECKey.ECDSASignature.validateComponents()` [1](#0-0)  only checks that `r` and `s` are within `[1, SECP256K1N)`. It does not enforce the canonical "low-s" rule (`s <= HALF_CURVE_ORDER`), even though `toCanonicalised()` exists in the same class [2](#0-1) . This means for any valid signature `(r, s, v)`, the malleated counterpart `(r, n-s, v')` is also a distinct, byte-different, cryptographically valid signature for the same private key and message — the classic signature malleability property.

`PrecompiledContracts.recoverAddrBySign` (used by `ValidateMultiSign`) parses signature components and recovers the address without any canonicalization/malleability check: [3](#0-2) .

In `ValidateMultiSign.execute`, the de-duplication logic is:
```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
``` [4](#0-3) 

When the same signer's address is seen a second time but the raw signature bytes differ (as happens with a malleated signature), the inner `continue` is *not* taken — the code only calls `MUtil.checkCPUTime()` (a CPU-exhaustion throttle for repeated identical signer submissions) and then falls through to add that signer's weight to `totalWeight` again. This means an attacker holding a single private key that is a member of a multisig `Permission` can submit two syntactically different but cryptographically valid signatures (the original and its malleated form) and have their weight counted twice.

By contrast, the consensus-level transaction signature check `TransactionCapsule.checkWeight` was hardened against this exact malleability class post-fork `VERSION_4_7_1`, switching the de-duplication key from the raw base64 signature to the recovered address: [5](#0-4) . The `ValidateMultiSign` TVM precompile does not have the equivalent fix — it still allows a second, different-byte signature from an already-counted address to add weight again.

### Impact Explanation
This is reachable from any smart contract that calls the `ValidateMultiSign` precompile (address `0x0000...09` family in TRON's TVM), which any account can trigger via a normal `TriggerSmartContract` transaction (broadcast transaction / contract call — no privileged actor needed). A contract that relies on `ValidateMultiSign` to gate a sensitive operation (e.g., withdrawal, permission change, multi-approver escrow) behind an on-chain `Permission` with `threshold >= 2` and multiple equally-weighted keys can be bypassed by a single key-holder who submits both the original and the malleated signature, doubling their counted weight and satisfying the threshold without the cooperation of the other required signers. This is an unauthorized-operation / accounting-corruption class impact executed purely through the TVM, matching the "resubmit approval to bypass intended multi-party control" pattern described in the source report.

### Likelihood Explanation
Exploitation requires only: (1) a smart contract using `ValidateMultiSign` with a `Permission` whose threshold can be met by doubling one signer's weight, and (2) the ability to compute `(r, n-s)` from any observed `(r, s)` signature — a trivial, well-known operation (`s' = CURVE.getN().subtract(s)`, flip `v`). No special privileges, leaked keys, or malicious peers are needed; this is purely a signature-format weakness reachable from ordinary contract calls.

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute`, de-duplicate strictly by `recoveredAddr` (not by exact signature bytes): once an address has contributed weight, skip it (or reject the whole set) regardless of whether the raw signature bytes differ, mirroring the `VERSION_4_7_1` fix already applied in `TransactionCapsule.checkWeight`. Additionally, consider enforcing canonical low-`s` signatures in `ECKey.ECDSASignature.validateComponents()` (using the existing `toCanonicalised()`/`HALF_CURVE_ORDER` logic) for all signature-validating entry points to eliminate malleable duplicates at the source.

### Proof of Concept
1. Deploy/point to an account address `A` with an Active `Permission` (id `P`) having threshold `2`, containing key `K1` with weight `1` and key `K2` with weight `1`.
2. Compute `hash = SHA256(A || permissionId || data)` per `ValidateMultiSign` semantics [6](#0-5) .
3. Using only `K1`'s private key, produce signature `sig1 = (r, s, v)` over `hash`.
4. Derive the malleated signature `sig2 = (r, n-s, v_flipped)` — mathematically valid for the same key and hash (this is exactly what `ECDSASignature.toCanonicalised()` exists to normalize away, confirming `s` and `n-s` are both accepted forms) [2](#0-1) .
5. Call `ValidateMultiSign(A, P, data, [sig1, sig2])` from a contract (only `K2`'s cooperation is absent). Trace the loop: for `sig1`, `recoveredAddr = K1`, not yet in `executedSignList`, weight `1` added. For `sig2`, `recoveredAddr = K1` again, `matrixContains(executedSignList, K1)` is true, but `matrixContains(executedSignList, merge(K1, sig2))` is false (different bytes), so it does **not** `continue`; it falls through and adds weight `1` again [7](#0-6) .
6. `totalWeight` reaches `2`, meeting the threshold with only `K1`'s single private key, and the precompile returns success (`dataOne()`) without `K2` ever signing.

**Uncertainty note:** I could not fully verify whether any TVM feature flag (e.g., `VMConfig.allowTvmSelfdestructRestriction()` / `allowTvmOsaka()`) that gates the `extractSigArray` vs `extractBytesArray` path also changes the dedup semantics beyond `MAX_SIZE` checks; the code shown does not indicate it does, but confirming this fully would require tracing `extractSigArray` and the exact activation history in a running/test environment, which was not accessible in this read-only review.

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }

      throw new PermissionException(

    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {

      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)

      }

    }
