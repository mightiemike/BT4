## Title
Relayer fee is paid out unconditionally before the underlying transfer/action is confirmed successful, allowing fee extraction without delivering the user's transaction - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's `inner_rlp_execute` function dispatches the relayer fee as an independent, unchained `Transfer` promise *before* the promise chain that actually performs the user's requested action (base-token transfer or emulated ERC-20 transfer) is created or resolved. Because the fee-payment promise is not `.then()`-chained on the outcome of the action promise, it is not conditioned on that action's success. This is structurally the same root cause as the reported DODO issue — a value-moving side effect is committed without verifying that the operation it is supposed to compensate for actually succeeded.

### Finding Description
In `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:374-385`), when parsing produces an `EOABaseTokenTransfer` or `ERC20Transfer` kind with a non-zero `fee`, the code immediately creates and dispatches a separate `Transfer` promise batch to `predecessor_account_id` (the relayer): [1](#0-0) 

This happens *before* the code below (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:412-471`) builds the promise that actually executes the requested transfer/`ft_transfer` call and chains a `rlp_execute_callback`: [2](#0-1) 

The fee-transfer promise batch is created via `env::promise_batch_create` + `env::promise_batch_action_transfer` and is never `.then()`-composed with, or made contingent upon, the promise that performs the actual base-token transfer or ERC-20 `ft_transfer`/`storage_deposit` sequence. Both promises are simply returned/executed as siblings scheduled from the same receipt; NEAR's runtime executes independent promises regardless of each other's success (`docs/RuntimeSpec/Components/BindingsSpec/PromisesAPI.md` describes `promise_batch_action_transfer` as an unconditional action append to a receipt, and `promise_and`/`.then()` are the only combinators that create dependency between promises).

By contrast, the contract's own `rlp_execute_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:275-317`) demonstrates that the code is aware promise results must be checked via `env::promise_result(0)` before deciding on further actions (e.g., refunding the caller's deposit only if the callback observes `PromiseResult::Failed`): [3](#0-2) 

The fee payment, however, bypasses this pattern entirely — it is fired unconditionally at dispatch time rather than being gated on the success of the underlying transfer, which is the exact analog of the DODO report's unchecked-transfer pattern: a value transfer is executed and the contract's accounting/behavior proceeds as if the paired operation succeeded, without verifying that it actually did.

### Impact Explanation
A relayer (the `predecessor_account_id`, an unprivileged transaction/meta-transaction sender who is reachable via a plain `FunctionCall` to `rlp_execute`) that submits a user's signed emulated transaction can collect the fee payment even if the corresponding base-token transfer or ERC-20 transfer subsequently fails (e.g., the ERC-20 token contract's `ft_transfer` reverts due to insufficient balance, the receiver's `storage_deposit`/registration step fails, gas is exhausted for the transfer, or `action_to_promise`/downstream calls error). Because the fee promise is dispatched unconditionally and independent of that outcome, the relayer receives compensation for work that was not actually completed for the user, and the user's tokens are not delivered to the intended receiver. This is an unauthorized value movement / fee-bypass condition triggered by a single transaction from an unprivileged relayer, matching the "fee or gas bypass" / "concrete unauthorized value movement" acceptance criteria.

### Likelihood Explanation
Likelihood is high given normal usage: any relayer relaying an `ERC20Transfer` (which is a multi-step promise chain: `storage_balance_of` → possibly `storage_deposit` → `ft_transfer` → callback) has multiple failure points downstream of where the fee is already dispatched. Relayers control gas allocation and can also intentionally under-provision gas for the downstream steps, or target ERC-20 tokens/contracts they know will reject the transfer, guaranteeing fee collection without delivering value. No special privileges beyond being any relaying account (or an access-key holder) are required — this is directly reachable via `rlp_execute`.

### Recommendation
Chain the fee-payment transfer onto the success path of the action promise (e.g., append it as part of the same promise batch that also performs the transfer, or move the `promise_batch_action_transfer` for the fee into `rlp_execute_callback`/the success branch of `PromiseResult::Successful`) so the relayer is only paid if `env::promise_result(0)` for the underlying action indicates success. Alternatively, use `Promise::and`/`.then()` composition to guarantee the fee transfer executes only after the main action's outcome is known, and refund/skip the fee if the main action failed.

### Proof of Concept
1. A user signs an RLP-encoded ERC-20 `transfer` emulation transaction with a non-zero relayer `fee`, targeting a NEP-141 token contract, intending funds to go to `receiver_id`.
2. A relayer (or the user itself, malicious or careless) submits this via `rlp_execute` with `target` = the token contract.
3. In `inner_rlp_execute`, because `fee != 0` and `predecessor_account_id != current_account_id`, the fee `Transfer` promise to the relayer is created and dispatched immediately (`lib.rs:381-384`).
4. Separately, the ERC-20 transfer promise chain (`storage_balance_of` → `nep_141_storage_balance_callback` → `ft_transfer`/`storage_deposit` → `rlp_execute_callback`) is built and returned (`lib.rs:433-458`).
5. If the token contract's `ft_transfer` call fails (e.g. insufficient token balance, blacklisted receiver, or insufficient attached gas caused deliberately by the relayer), `rlp_execute_callback` observes `PromiseResult::Failed` and reports `success: false` — but the fee transfer from step 3 has already been executed as an independent receipt and is not rolled back or gated by this failure.
6. Net effect: the relayer collects the fee NEAR tokens while the user's ERC-20 tokens were never transferred to the intended recipient.

Note: I was not able to fully trace whether any global cross-receipt rollback semantics in the runtime (outside this contract) could retroactively undo the already-executed fee transfer; based on `docs/RuntimeSpec/Refunds.md` and the receipt-execution model, independently-created receipts are not rolled back based on sibling receipt failure, so the described flow persists unless the contract logic itself is fixed.

            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;

                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }

            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =

            ext.rlp_execute_callback(caller_deposit)
