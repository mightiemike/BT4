### Title
Rounding error in standby witness reward distribution favors the reward pool over standby witnesses - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payStandbyWitness()` computes a single shared "pay-per-vote" quotient once, then multiplies it per witness and truncates the result — the exact division-before-multiplication pattern flagged in the external report (`rewardsPerActiveValidator = _reward / totalActiveValidators` computed once, then `validatorCounts[idx] * rewardsPerActiveValidator` per operator).

### Finding Description
`payStandbyWitness()` calculates `eachVotePay` **once** outside the loop over all standby witnesses, then multiplies it by each witness's individual vote count and truncates to a `long` inside the loop: [1](#0-0) 

```java
public void payStandbyWitness() {
  List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(...);
  long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
  if (voteSum < 1) { return; }
  long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
  double eachVotePay = (double) totalPay / voteSum;
  for (WitnessCapsule w : witnessStandbys) {
    long pay = (long) (w.getVoteCount() * eachVotePay);
    payReward(w.getAddress().toByteArray(), pay);
  }
}
```

This mirrors the reported anti-pattern precisely: a shared per-unit reward rate is derived from a single division (`totalPay / voteSum`), and then each recipient's share is obtained by multiplying that rate by their weight and truncating (via the `(long)` cast) independently, once per witness in the loop. Because the truncation happens per-witness rather than once at the aggregate level, the sum of all `pay` values paid out to standby witnesses is systematically less than or equal to `totalPay`, with the shortfall (dust) simply never being paid to any witness and remaining in the pool/undistributed balance — the same "rounding favors the pool/depositors, not the fee/reward recipients" effect described in the report. Unlike a straightforward integer division, this implementation additionally relies on `double` arithmetic for a financial calculation, which introduces its own IEEE-754 precision loss for large `totalPay`/`voteSum` values in addition to the structural truncation-before-multiplication issue.

The correct pattern (multiply first, then divide once per recipient using the recipient's own numerator) would look like:
```java
long pay = (long) ((BigInteger.valueOf(totalPay).multiply(BigInteger.valueOf(w.getVoteCount())))
    .divide(BigInteger.valueOf(voteSum)).longValue());
```
This is analogous to how `MortgageService.computeReward` and `RewardViCalService` already correctly multiply before dividing using `BigInteger` elsewhere in the same class: [2](#0-1) .

### Impact Explanation
Every block, standby witnesses (ranks 28-127 in the witness list) receive a portion of `WITNESS_127_PAY_PER_BLOCK` proportional to their votes via this function, invoked from block processing in `Manager.java`. The rounding-down-per-witness behavior causes real, continuously-accumulating loss of rewards actually owed to standby witnesses across every block over the life of the chain, i.e., real value is permanently withheld from legitimate unprivileged actors (witnesses/voters who rely on this payout) each time this function executes. This is an accounting/underpayment bug affecting protocol-level reward settlement, not a purely theoretical rounding nuance.

### Likelihood Explanation
This code path executes unconditionally on every maintenance/reward cycle for all standby witnesses as long as `voteSum >= 1`, which is virtually always true on a live network. No special privilege or attacker action is required to trigger it — it happens automatically as part of normal consensus reward accounting, making the likelihood of the rounding loss occurring effectively 100% per invocation.

### Recommendation
Replace the shared floating-point "pay-per-vote" quotient with a per-witness multiply-then-divide calculation (ideally using `BigInteger` or integer math to avoid `double` imprecision), computing `pay = totalPay * w.getVoteCount() / voteSum` for each witness individually so truncation only occurs once per witness against its own exact numerator rather than through a shared, pre-rounded rate.

### Proof of Concept
Given `totalPay = 10` and 3 standby witnesses each with `voteCount = 1` (`voteSum = 3`):
- `eachVotePay = 10.0 / 3 = 3.333...`
- Each witness's `pay = (long)(1 * 3.333...) = 3`
- Total distributed = `3 * 3 = 9`, while `totalPay = 10`

One unit of the reward pool is silently withheld from the standby witnesses every time this ratio doesn't divide evenly — repeating every block/maintenance cycle indefinitely.
