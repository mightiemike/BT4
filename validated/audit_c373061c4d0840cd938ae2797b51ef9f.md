### Title
Webhook authenticity check signs only the request body, not the shop-domain/topic headers used for authorization routing - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`shopify.webhooks.validate()` verifies webhook authenticity by computing an HMAC over `rawBody` alone and comparing it to the `X-Shopify-Hmac-Sha256` header. The `X-Shopify-Shop-Domain` and `X-Shopify-Topic` (and `webhookId`/`apiVersion`) headers, which the app frameworks then use to decide *which shop's offline session to load* and *which topic handler to run*, are only checked for presence — never cryptographically bound to the signed payload. This is structurally the same flaw as the Trail of Bits finding: an authorization/authenticity check validates one component (`fulfiller` in `BunniZone.validate`, `rawBody` here) while a second, independent set of decision-relevant fields (`preHooks`/`postHooks` contents there, `domain`/`topic` headers here) is left unauthenticated and swappable by whoever can produce a valid signed payload.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC exclusively from `rawBody` and compares it to the `hmac` header: [1](#0-0) 

`shopify.webhooks.validate` first runs this body-only HMAC check, and only afterwards separately checks that the routing headers (`domain`, `topic`, `webhookId`, `apiVersion`) are merely *present* — not that they are cryptographically tied to the verified body: [2](#0-1) [3](#0-2) 

`getRequiredHeader` only checks for a truthy value, adding it to `missingHeaders` if absent — no comparison against anything derived from the signed body: [4](#0-3) 

Downstream, `authenticateWebhookFactory` (shared by shopify-app-remix and shopify-app-react-router) takes the unauthenticated `check.domain` value and uses it directly to load an **offline session with an access token** for that shop, and uses `check.topic` to select which business logic to dispatch: [5](#0-4) [6](#0-5) 

Because the apiSecretKey is a single shared secret for the whole app (not per-shop), any shop that has the app installed — an unprivileged, single merchant — can obtain a legitimately-signed `(rawBody, hmac)` pair from a webhook delivered to their own store (many lifecycle webhooks such as `app/uninstalled`, `shop/redact`, etc. have small/predictable bodies). Since the `domain` and `topic` headers are never bound to that signature, the same merchant can resend that exact body+HMAC pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different (victim) shop and/or forging `X-Shopify-Topic` to a different, more sensitive topic. `validate()` will report `valid: true`, and the app framework will load the **victim shop's offline session/access token** and execute the handler as if the victim shop had sent that topic's payload.

### Impact Explanation
This is a genuine cross-tenant confused-deputy: the authenticity check (HMAC) protects the wrong scope. It binds "this body was produced with our app secret" but not "for this shop" or "for this event type." Any single, low-privileged merchant using the app can leverage this to make the app process arbitrary webhook topics under another installed shop's identity/session, exactly mirroring the report's pattern where the BunniZone's `validate()` authenticated the caller but not the content that gets executed against that caller's authority.

### Likelihood Explanation
Exploitability requires only: (1) installing the app on any shop (unprivileged, self-service), (2) capturing one legitimately delivered webhook body+HMAC (trivial via the app's own webhook logs or a locally reproducible minimal-body topic), and (3) POSTing it back with forged `domain`/`topic` headers — no secret knowledge, no privileged role, and no interaction with the victim required.

### Recommendation
Include the shop domain, topic, webhook ID, and API version in the data covered by the HMAC (or otherwise cryptographically bind the routing headers to the signed body), and reject any webhook whose headers cannot be tied to the signature. Short term, additionally cross-check `domain` against the shop that owns the currently-loaded offline session before using it, and treat `topic` as untrusted input requiring separate authorization before dispatch.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled, low privilege).
2. Capture a Shopify-delivered webhook to Shop A's endpoint with topic `app/uninstalled` (body typically `{}`), noting the `X-Shopify-Hmac-Sha256` value and raw body.
3. Replay the exact same raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and, if desired, a different `X-Shopify-Topic`.
4. `shopify.webhooks.validate()` returns `valid: true` (per `validate.ts:46-74`) because only `rawBody` is checked against the HMAC.
5. `authenticateWebhookFactory` loads the victim shop's offline session (`ensureValidOfflineSession(params, check.domain)`) and executes the handler for the forged topic using the victim's session/access token.

  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {

      await abstractConvertRequest(adapterArgs);

      }
      return validHmacResult;
    }

  };

function getRequiredHeader(
  headers: Headers,
  headerName: string,
  missingHeaders: string[],
): string | undefined {
  const value = getHeader(headers, headerName);
  if (!value) {
    missingHeaders.push(headerName);
  }
  return value;
}
