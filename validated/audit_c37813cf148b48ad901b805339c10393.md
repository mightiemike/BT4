### Title
Replay-verification skips checkpoint hash validation, allowing corrupted state/position roots to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used by replay/verify tooling to confirm that a locally re-executed transaction output matches an authenticated `TransactionInfo` pulled from backup/archive. The function validates status, gas, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap acknowledged in-code by a `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks execution status, gas used, and write-set hash against the authenticated `TransactionInfo`, and separately checks the event root hash. However, the function's trailing comment makes explicit that the checkpoint-related commitments are skipped: [2](#0-1) 

These checkpoint hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are the fields on `TransactionInfoV0`/`TransactionInfoV1` that bind a committed transaction to the Sparse-Merkle-Tree/JMT state root at that version [3](#0-2)  and, for the newer "position" (native trading) state, at [4](#0-3) . The position-state checkpoint root is computed during normal execution via `DoStateCheckpoint::compute_position_checkpoint`, which folds `native_position_iter()` write-ops into a Merkle-summarized tree only when `execution_output.compute_trading_native_state_roots` is enabled [5](#0-4) . This root is the sole authenticated commitment binding the "position" ledger sub-state to a version — but it is never compared during output-vs-info matching.

The comment itself states the consequence in explicit terms: "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

### Impact Explanation
Replay-verify (`ensure_match_transaction_info`) is the primary defense used by db-tool/backup verification to detect whether a re-executed history reproduces the exact ledger state committed on mainnet. If the write-set/events/status/gas all match but the state (or position/hot-state) checkpoint diverges — e.g. due to a state-computation bug, a hard-fork-only divergence, or corrupted restore data — that divergence is silently accepted as "verified." This directly undermines the state-commitment integrity guarantee: an authenticated proof artifact (`TransactionInfo.state_checkpoint_hash`/`position_state_checkpoint_hash`) is present specifically to catch such mismatches, but the comparator that is supposed to enforce it does not check it. This matches the "committed state that differs from the correct VM result... accepted as valid" and "hard-fork-only divergence during commit, replay ... verification" categories in scope.

### Likelihood Explanation
This is not a remotely-exploitable "attacker" bug — it requires an underlying state-computation divergence (bug, non-determinism, or storage/restore corruption) to exist first. However, given such a divergence, the omission is deterministic and 100% reproducible: `ensure_match_transaction_info` will unconditionally return `Ok(())` regardless of checkpoint-hash mismatch, because those fields are simply never read in the comparison. The code authors flagged this explicitly as a pending TODO gating the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature [6](#0-5) , confirming the gap is real and currently unaddressed rather than theoretical.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info` whenever those fields are `Some` on the expected `TransactionInfo`, mirroring the existing write-set/event-root checks, before enabling/relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` for mainnet replay-verify tooling.

### Proof of Concept
Not applicable as a live exploit — this is a static code-review finding based on the acknowledged gap in the comparator function itself: [7](#0-6) . A conceptual reproduction: construct a `TransactionOutput` whose write set/events/status/gas match a given `TransactionInfo`, but whose actual re-executed state or position-state root would differ (e.g., by using a `TransactionInfo` from one version's checkpoint against a `TransactionOutput` produced under a divergent state-computation path affecting only checkpoint-tree contents, not the write set). `ensure_match_transaction_info` returns `Ok(())` in this case even though the checkpoint commitments diverge, which local code review confirms is due to the fields being excluded from all `ensure!` checks in the function body.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
