## Finding

### Title
Unbounded recursive bytecode-segment hashing causes stack-overflow DoS in the Sierra-to-CASM declare pipeline - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
When a declare transaction is admitted, the sequencer's Sierra compiler component compiles the submitted Sierra program to CASM in a resource-limited subprocess, then computes the compiled class hash **in the parent process** by recursively walking the `bytecode_segment_lengths` tree with no depth bound. A crafted declare transaction whose Sierra program yields a deeply nested segment tree can drive this recursion far enough to overflow the native thread stack, aborting the process — the same bug class as the reported libsass `CompoundSelector::has_real_parent_ref` unbounded-recursion stack overflow (BIT-sass-2022-43357 / CVE-2022-43357).

### Finding Description
`SierraCompiler::compile` in [1](#0-0)  does two things for every declare transaction: it runs the external Sierra→CASM compiler binary under CPU/memory `rlimit`s (`ResourceLimits`, which only sets `RLIMIT_CPU`/`RLIMIT_FSIZE`/`RLIMIT_AS`, never a stack limit) via [2](#0-1) , and then, back in the (unsandboxed) calling process/thread, invokes `executable_class.hash(&HashVersion::V2)`.

That hash routine recursively descends `bytecode_segment_lengths` (a `NestedIntList`) with `bytecode_hash_node`: [3](#0-2) 

There is no recursion-depth check anywhere in this path — unlike entry-point execution, which is explicitly guarded by `RecursionDepthGuard`/`max_recursion_depth` ( [4](#0-3) ). `bytecode_segment_lengths` is derived by the (external) Sierra-to-CASM compiler from the control-flow structure of the attacker-supplied Sierra program (the `RpcDeclareTransaction` carries the raw Sierra program directly, not compiled Cairo source), so an attacker fully controls the nesting shape of this tree, up to the `max_bytecode_size` limit (default 80 KiB felts, [5](#0-4) ). By constructing a Sierra program whose branch/segment structure nests as deeply as possible (a chain of single-instruction segments rather than a flat/balanced tree), the resulting `NestedIntList` can be nested tens of thousands of levels deep, well beyond what a default thread stack can sustain for a generic recursive function carrying `HashableNestedIntList`/`StarkHash` type parameters and intermediate `Vec` allocations per frame.

Because the hashing happens after the sandboxed subprocess returns and inside the gateway/`apollo_compile_to_casm` service's own thread (per the flow documented in [6](#0-5) ), a stack overflow here aborts that process (Rust cannot catch a real stack overflow as a panic); it is not confined to the resource-limited child. Every honest sequencer that receives this declare transaction (directly or via mempool P2P gossip) independently repeats compilation and hashing and will independently crash the same way, since the vulnerable code is a general helper reached the same way on every node.

### Impact Explanation
A single malicious but syntactically valid declare transaction can crash the Sierra compiler/gateway component on every sequencer that processes it, since declare admission is a mandatory step for any node validating that transaction. This is a network-wide denial-of-service against transaction admission (declares, and indirectly the gateway process handling them), matching the "network unable to confirm new transactions" impact bar, not merely a resource-only nuisance, because process abort (not graceful error) removes the whole gateway instance from service until restarted.

### Likelihood Explanation
The attacker only needs to submit one declare transaction with a crafted Sierra program; no privileged position, staking, or race condition is required. The relevant CPU/memory subprocess sandbox does not constrain the parent-process hashing step, and there is no code path that validates or bounds the depth of `bytecode_segment_lengths` before recursively hashing it — the only bound is the flat instruction-count limit (`max_bytecode_size`), which does not limit nesting depth.

### Recommendation
- Convert `bytecode_hash_node` (and its Blake/Poseidon Cairo-side counterparts, if native-stack based) to an explicit-stack/iterative algorithm, or enforce and validate a maximum nesting depth for `NestedIntList`/`bytecode_segment_lengths` immediately after deserializing the compiler's output, rejecting classes whose segment tree exceeds a safe depth.
- Alternatively/also, perform the compiled-class-hash computation for untrusted, freshly-compiled classes inside the same resource-limited subprocess (or a dedicated bounded-stack worker thread) so a stack overflow there fails the single declare compilation instead of aborting the whole service.

### Proof of Concept
1. Construct a Sierra program (`sierra_program` field of `RpcDeclareTransaction::V3`) whose control-flow graph is a long, deep chain of nested branch points, close to `max_bytecode_size` (~80 K) total bytecode instructions, but structured so the compiler emits a `NestedIntList` composed of thousands of nested single-element `Node`s (e.g., one segment per instruction, chained rather than grouped).
2. Submit it as a declare transaction through the gateway; it passes `StatelessTransactionValidator::validate_declare_tx` (only checks sierra version, class size, and entry-point sort order — [7](#0-6) ).
3. `SierraCompiler::compile` runs the subprocess successfully (bytecode size within limits), then calls `executable_class.hash(&HashVersion::V2)` in-process, invoking `bytecode_hash_node` recursively to the depth of the crafted `NestedIntList`.
4. Observe the gateway/Sierra-compiler process crash with a stack overflow (SIGSEGV/abort) instead of returning a compilation error.

```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```

```rust
// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
```
