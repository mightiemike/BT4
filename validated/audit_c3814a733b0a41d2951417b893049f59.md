## Broken Equality

Before tracing code, the equality the question claims is broken:

**Claimed invariant** (accounts.rs comment, line 503-504): for a fixed `(parent_block_id, child_block_id)` key, `inner_insert_matured_miner_reward` assumes *any* two forks computing a matured reward for that same historical block pair must compute **byte-identical** `MinerReward` values — because the block being rewarded is a fixed, already-mined common ancestor.

**What actually holds**: the `MinerReward.recipient`/`address` fields depend on `poison_recipient_opt`, which is read via `get_poison_microblock_report` from the *current fork's* Clarity/MARF key-value store — mutable, fork-local state that two temporarily-competing forks can populate differently (different reporter principals) for the same punished microblock public-key hash, even while agreeing on every other fact about the rewarded block. So the equality `reward_fork_A == reward_fork_B` is **not guaranteed**, contradicting the code's assumption.

## Trace

- `handle_poison_microblock` [1](#0-0)  writes the poison report into the Clarity KV store via `insert_microblock_poison`, keyed only by `("microblock-poison::{height}")`, whichever principal submits the winning (lowest-sequence) report *in that block's own history*. This is standard Clarity/MARF state, i.e., fork-local.
- At maturation, `find_mature_miner_rewards` re-reads this fork-local state via `get_poison_microblock_report(clarity_tx, reward_height)` [2](#0-1)  and feeds the resulting reporter into `calculate_miner_reward`, which sets `child_recipient = reporter_address.to_account_principal()` [3](#0-2) . `MinerReward` derives `PartialEq` over all fields including `recipient` [4](#0-3) .
- The resulting reward is written via `insert_matured_child_miner_reward` → `inner_insert_matured_miner_reward`, which is keyed only by `(parent_block_id, child_block_id)` — the historical block being rewarded, not the fork's identity — in the node's single shared `matured_rewards` SQLite table [5](#0-4) .
- Nodes legitimately track multiple concurrently-valid Stacks forks/tips before signers resolve which is canonical — this is explicitly documented as expected "benign fork" behavior [6](#0-5) . Each fork's blocks are independently appended and their matured rewards independently computed and inserted into the same shared table.

If fork A processed a poison report from reporter R1 and fork B (sharing the punished tenure as common ancestor, diverging afterward) processed a *different* report from R2 for the same underlying double-signed microblock key, both forks compute the *same* `(parent_block_id, child_block_id)` key but *different* `MinerReward.recipient`, and the `assert_eq!` at line 515 panics.

No existing guard prevents this: `check_tenure_tx`, VRF/static validators, and `common_validate_against_burnchain` are unrelated to user-submitted `PoisonMicroblock` transactions, and nothing deduplicates poison reports across sibling forks — by design, poison-microblock reporting is permissionless and per-fork.

### Title
Fork-divergent PoisonMicroblock reporters cause `assert_eq!` panic in `inner_insert_matured_miner_reward` - (`stackslib/src/chainstate/stacks/db/accounts.rs`)

### Summary
Two temporarily-competing Stacks forks sharing a common punished tenure can each record a *different* reporter for the same underlying microblock-fork poison event, because poison reports are stored in fork-local Clarity/MARF state. When both forks' blocks mature that shared tenure's reward, they write conflicting `MinerReward` rows for the same `(parent_block_id, child_block_id)` key into the shared, fork-agnostic `matured_rewards` table, tripping the `assert_eq!` dedup check and panicking the node.

### Finding Description
`inner_insert_matured_miner_reward` assumes that re-insertion for a given `(parent_block_id, child_block_id)` pair is only ever a "two forks recomputing the same fact" scenario and therefore must be byte-identical [7](#0-6) . This assumption is false for poison-microblock-affected rewards: `calculate_miner_reward` sets the reward recipient to whichever principal's `PoisonMicroblock` report is currently visible in the *processing fork's own* Clarity KV state at `reward_height` [8](#0-7) , and that visibility is fork-local (`env.global_context.database.insert_microblock_poison` / `get_microblock_poison_report` in `handle_poison_microblock`) [9](#0-8) , [10](#0-9) .

Exploit flow: an unprivileged attacker (or independent, uncoordinated observers) submits two different `PoisonMicroblock` report transactions with two different sender addresses (R1, R2) targeting the same double-signed microblock public key hash, one into each of two temporarily-competing Stacks tenure branches (a scenario the codebase itself documents as a normal, expected occurrence when signers split votes across two miners' tenure-change blocks) [6](#0-5) . Any node that processes both forks' blocks (which it must, in order to determine which becomes canonical) will independently mature the shared punished-tenure reward once in each fork's context, computing `recipient = R1` in one and `recipient = R2` in the other. Both calls target the identical `(parent_block_id, child_block_id)` since that historical block predates the fork split. The second `insert_matured_child_miner_reward` call hits the existing row, finds a mismatched `MinerReward`, and `assert_eq!` panics [11](#0-10) .

### Impact Explanation
This is a chain-halting panic reachable by any node that legitimately processes two sibling forks under the documented "benign fork" pattern — not a majority-stake or privileged action. Because every fully-validating node that receives both forks (a normal occurrence, not an edge case requiring collusion) hits the same deterministic panic, this can crash a large fraction of the network simultaneously, matching the "Critical — chain-halting panic / chain split via node crash divergence" category.

### Likelihood Explanation
Preconditions: (1) a genuine microblock fork exists (a double-signed microblock public key), which can occur from any single miner slot without majority stake; (2) two temporarily-competing Stacks tenure branches exist before reconvergence — an occurrence the codebase explicitly anticipates as routine (`sortdb.rs` comment on "benign forks" from split signer votes); (3) two report transactions with distinct sender principals are broadcast, one into each branch — trivial for the attacker to arrange with two funded testnet/mainnet accounts and no special stake. No BTC cost beyond ordinary transaction fees is required, and the condition is repeatable each time a microblock fork and a tenure-branch race coincide.

### Recommendation
Do not use `assert_eq!`/panic as the reconciliation strategy for `matured_rewards`. Either (a) key the dedup check and stored row explicitly by which report (reporter, sequence) was used, allowing multiple valid rows per `(parent_block_id, child_block_id)` until the canonical fork is determined, and only pay out based on the reward computed on the winning fork's tip; or (b) make poison-microblock report resolution deterministic independent of processing fork (e.g., always resolve to the lowest-sequence report visible on the *canonical* burn view, computed lazily at final maturation only against the canonical chain, never inserted speculatively for non-canonical tips). At minimum, replace the `assert_eq!` with a non-panicking conflict-resolution path (log + keep the row from the eventually-canonical fork, deferring the insert until the fork is canonical) to remove the crash vector.

### Proof of Concept
Rust integration test plan (two-node/two-fork harness or single-node dual-fork chainstate harness):
1. Build a common tenure containing a miner that double-signs a microblock at sequence `S` with public key `K` (standard test helper `make_signed_microblock` already used in existing poison-microblock tests, e.g. `stackslib/src/chainstate/stacks/db/transactions.rs:5716-5814`).
2. From that common ancestor, construct fork A: a tenure branch whose block includes a `PoisonMicroblock` tx signed by reporter `R1` for `(mblock_1_1, mblock_1_2)`.
3. Construct fork B from the same ancestor: a different tenure branch whose block includes a `PoisonMicroblock` tx signed by reporter `R2` for the same `K` but a different valid conflicting pair.
4. Feed both forks' blocks through `NakamotoChainState::append_block` (or equivalent `advance_tip`) on the same `StacksChainState`, advancing each past `MINER_REWARD_MATURITY` so `insert_matured_child_miner_reward` fires for each fork against the same `(parent_block_id, child_block_id)`.
5. Assert equality-under-test *before* the second insert: `get_matured_miner_payment(conn, parent_block_id, child_block_id).recipient == R1_principal` (fork A's view).
6. Process fork B's maturing block and assert the crash: expect a panic from `assert_eq!` in `inner_insert_matured_miner_reward` (currently reproducible), or, after the fix, assert `get_matured_miner_payment` returns exactly one `MinerReward` with `punished == true` and a single, fork-resolved recipient, with no panic.
