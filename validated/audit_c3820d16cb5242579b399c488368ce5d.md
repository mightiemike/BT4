### Title
Unhandled `.unwrap()` panic on `receiver_shard_id` in the delayed-receipt filter can be triggered by an attacker-timed `GlobalContractDistribution` receipt, halting chunk application - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally unwraps the result of `Receipt::receiver_shard_id`, which is fallible specifically for `GlobalContractDistribution` receipts whose `target_shard` can no longer be resolved in the current shard layout. Any account can trigger the creation of such a receipt via a `DeployGlobalContract` action, and if the receipt lingers in the delayed-receipt queue across shard-layout transitions faster than the shard layout's split-history can track, every validator applying that shard's chunk hits the same `.unwrap()` panic deterministically — a transaction/deployment-triggered chain halt, analogous to the DNSdist DoH assertion-failure DoS (CVE-2024-25581), where a routed request whose shape the backend didn't expect crashed the process via an unhandled assertion.

### Finding Description
`Receipt::receiver_shard_id` returns `Result<ShardId, EpochError>` because, for `ReceiptEnum::GlobalContractDistribution`, the `target_shard` recorded on the receipt may belong to an old shard layout: [1](#0-0) 

If the target shard is not in the current layout, the code tries `shard_layout.resolve_to_current_shard(target_shard)` and returns `Err(EpochError::ShardingError(...))` if that also fails — i.e. the receipt's origin shard has been split/resharded away far enough that even the split-history chain can't map it forward.

The delayed-receipt processing path, however, does not propagate this error. `DelayedReceiptQueueWrapper::receipt_filter_fn`, used both by `pop()` (called every time a delayed receipt is dequeued for execution) and by `peek_iter()`, calls `.unwrap()` directly on the fallible result: [2](#0-1) 

This is a `Runtime::apply`-path function invoked on every chunk while processing the delayed queue (`process_receipts` → `pop`), which is on the critical, protocol-mandatory state-transition path — not test-only or sandbox code. If `receipt_filter_fn` panics, the entire `apply` call panics, and since every honest validator processes the same delayed queue deterministically, the panic reproduces on all of them, producing a chain-wide halt for that shard rather than a graceful per-receipt/per-transaction failure (contrast with how ordinary action failures are contained per-receipt, e.g. `ActionReceiptResult::merge`/`set_error`).

The repo's own regression test acknowledges this exact failure mode and demonstrates one scenario (two sequential shard splits while the distribution receipt is held in the delayed queue by compute saturation) where `receiver_shard_id` would previously fail to resolve the stale `target_shard`: [3](#0-2) 

That specific two-split case appears mitigated by `resolve_to_current_shard`'s split-history walk, but the underlying `.unwrap()` in `receipt_filter_fn` remains unguarded: any condition where `resolve_to_current_shard` cannot resolve the stale `target_shard` (e.g. more resharding generations than the walk covers, shard-layout transitions that are not simple splits, or any other divergence between the receipt's `target_shard` and the split-history graph) still results in an `EpochError` that is unconditionally unwrapped into a panic. I was not able to fully verify the exact depth/limits of the split-history walk in `resolve_to_current_shard` (`core/primitives/src/shard_layout/v3.rs`) within this investigation, so I cannot confirm precisely how many additional resharding generations, or which specific dynamic-resharding configuration, are needed to still trigger the unresolved case — this would need direct inspection of `resolve_to_current_shard`'s implementation and the `ShardLayoutV3`/split-history data structure to bound conclusively.

### Impact Explanation
A panic inside `Runtime::apply` (or any function it calls, such as `receipt_filter_fn` via `pop`/`peek_iter`) is not caught gracefully anywhere in the call chain shown by `chain/chain/src/runtime/mod.rs`, which only pattern-matches specific `RuntimeError` variants and otherwise lets a raw Rust panic propagate and crash the process. Because the delayed-receipt queue and shard layout are part of consensus-critical state, this panic is deterministic across all validators tracking the affected shard, causing a synchronized chain halt for that shard rather than node-specific corruption. This matches the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Triggering a `GlobalContractDistribution` receipt is available to any account (via `DeployGlobalContract`), and the delayed queue can be made to hold such a receipt across shard-layout transitions by saturating shard compute budgets (as the existing test does) so that the receipt is deferred rather than processed immediately. The exact conditions needed to make `resolve_to_current_shard` fail (as opposed to succeed, per the two-split regression test) require either more resharding generations, unusual dynamic-resharding sequences, or an edge case in the split-history representation not covered by the current test suite. Given this uncertainty, and that the currently-known two-split scenario appears mitigated, the likelihood is assessed as **contingent** — plausible under specific, not-yet-fully-characterized resharding sequences, but not confirmed as unconditionally reachable from a fresh state.

### Recommendation
- Replace the `.unwrap()` in `DelayedReceiptQueueWrapper::receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`) with proper error propagation (`Result`) up through `pop()` and `peek_iter()`, so a resolution failure becomes a handled `RuntimeError`/`StorageError` rather than a hard panic.
- Audit `resolve_to_current_shard` to guarantee it can resolve a `target_shard` across an arbitrary number of resharding generations (not just the two exercised by the existing regression test), or otherwise bound how long a `GlobalContractDistribution` receipt can remain queued relative to the shard split-history retention.
- Add fuzz/regression coverage for 3+ chained resharding events with a stalled `GlobalContractDistribution` receipt, and for any non-split shard-layout transition types, to close the gap the current test only partially covers.

### Proof of Concept
Conceptual reproduction (mirrors the existing test's structure, extended to look for the still-unguarded panic path):
1. Deploy a global contract from an account whose shard will be forced to split (as in `test_stale_global_contract_distribution_after_double_resharding`), creating a `GlobalContractDistributionReceipt` with `target_shard = S_A`. [4](#0-3) 
2. Saturate the shard's compute budget every block so the distribution receipt is pushed into, and stays in, the delayed-receipt queue across multiple forced dynamic-resharding splits. [5](#0-4) 
3. Configure a resharding sequence with more chained splits (or a shard-layout transition type not modeled by the split-history walk) than `resolve_to_current_shard` can resolve, then let the delayed queue drain.
4. Observe that `receipt.receiver_shard_id(&shard_layout)` returns `Err(EpochError::ShardingError(...))` and that `receipt_filter_fn`'s `.unwrap()` panics inside `Runtime::apply`, halting chunk production for that shard on all validators simultaneously — the same crash mode the existing test explicitly guards against for the two-split case.     pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
