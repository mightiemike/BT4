### Title
`isUnfreezableV2`/`UnfreezableBalanceV2` precompile overstates unfreezable balance by ignoring the 32-times pending-unfreeze limit - (File: actuator/src/main/java/org/tron/core/vm/utils/FreezeV2Util.java)

### Summary
The TVM precompiled contract `UnfreezableBalanceV2` (backed by `FreezeV2Util.queryUnfreezableBalanceV2`) is a read-only "max" query analogous to ERC4626's `maxWithdraw`/`maxRedeem`. Like the BakerFi finding where `maxWithdraw`/`maxRedeem` fail to factor in global/user-specific restrictions (e.g. a pause), this TRON precompile reports the entire frozen balance for a resource type as "unfreezable" without checking the account's current pending-unfreeze count, even though the real `unfreezeBalanceV2` operation enforces a hard cap of 32 concurrent pending unfreezes and will revert once that cap is reached.

### Finding Description
`FreezeV2Util.queryUnfreezableBalanceV2` simply returns the raw frozen-v2 balance for BANDWIDTH/ENERGY/POWER with no other checks: [1](#0-0) 

This is exposed on-chain via the `UnfreezableBalanceV2` precompiled contract (address `...0100000c`), callable by any contract/transaction: [2](#0-1) 

However, the actual unfreeze path (`UnfreezeBalanceV2Actuator.validate` and its TVM-native equivalent `UnfreezeBalanceV2Processor.validate`) enforces a separate, independent limit: no more than `UNFREEZE_MAX_TIMES` (32) concurrently pending unfreeze entries per account: [3](#0-2) [4](#0-3) [5](#0-4) 

Notably, TRON's own codebase already has the *correct* pattern for this exact restriction in a sibling precompile, `AvailableUnfreezeV2Size`, whose backing function `queryAvailableUnfreezeV2Size` does account for the pending-unfreeze count: [6](#0-5) 

This proves the omission in `queryUnfreezableBalanceV2` is a genuine inconsistency between the "preview" query and the "actual" execution path, exactly mirroring the ERC4626 `maxWithdraw`/`maxRedeem` defect: the max-query does not "factor in ... global and user-specific limits" that the real operation enforces.

### Impact Explanation
Any smart contract on TRON that calls `isUnfreezableBalanceV2`/`UnfreezableBalanceV2` to decide how much frozen balance it can safely unfreeze (a common integration pattern for staking/resource-management contracts, analogous to ERC4626 vault integrators relying on `maxWithdraw`) will receive an inflated value once the target account already has 32 pending unfreeze entries. Any subsequent `unfreezeBalanceV2` call built on that inflated value will revert with "unfreezing times is over limit," wasting the caller's energy/fee and breaking automated on-chain integrations that trust the precompile's reported maximum — a functional/DoS-style correctness bug in a reachable, unprivileged TVM precompiled contract.

### Likelihood Explanation
Reaching the pending-unfreeze cap of 32 is realistic for active accounts (e.g., automation contracts or high-frequency users unfreezing BANDWIDTH/ENERGY/TRON_POWER repeatedly before entries expire), and any contract/EOA can call the precompile directly via a `TriggerSmartContract` (constant or broadcast) — no privileged access required. The trigger condition (>=32 unexpired `UnFreezeV2` entries) is fully attacker/user controllable.

### Recommendation
Update `FreezeV2Util.queryUnfreezableBalanceV2` to also account for the account's current `getUnfreezingV2Count(now)` relative to `UnfreezeBalanceV2Actuator.getUNFREEZE_MAX_TIMES()`, returning 0 (or clamping) when the pending-unfreeze limit has already been reached, so the precompile's reported "unfreezable" amount can never exceed what a real `unfreezeBalanceV2` call would actually accept.

### Proof of Concept
1. Freeze BANDWIDTH/ENERGY/TRON_POWER on an account so it has non-zero `FrozenV2` balances.
2. Issue 32 separate `unfreezeBalanceV2` calls (small amounts) so the account accumulates 32 unexpired `UnFreezeV2` entries (`getUnfreezingV2Count(now) == 32`), as exercised in `UnfreezeBalanceV2ActuatorTest.testUnfreezeBalanceUnfreezeCount`. [7](#0-6) 
3. From a smart contract, call the `UnfreezableBalanceV2` precompile for that account/type — it still returns the full remaining `FrozenV2` balance (e.g. via `queryUnfreezableBalanceV2`), giving no indication the limit is reached.
4. Submit `unfreezeBalanceV2` for that reported amount — it reverts with `ContractValidateException("Invalid unfreeze operation, unfreezing times is over limit")`, confirming the precompile's advertised maximum did not match the actually accepted amount, in contrast to `AvailableUnfreezeV2Size`, which correctly reports 0 remaining slots in this state.

    if (!VMConfig.allowTvmFreezeV2()) {
      return 0;
    }

    AccountCapsule accountCapsule = repository.getAccount(address);
    if (accountCapsule == null) {
      return 0;
    }

    // BANDWIDTH
    if (type == 0) {
      return accountCapsule.getFrozenV2BalanceForBandwidth();
    }

    // ENERGY
    if (type == 1) {
      return accountCapsule.getFrozenV2BalanceForEnergy();
    }

    // POWER
    if (type == 2) {
      return accountCapsule.getTronPowerFrozenV2Balance();
    }

    return 0;
  }

  public static long queryAvailableUnfreezeV2Size(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmFreezeV2()) {
      return 0L;
    }

    AccountCapsule accountCapsule = repository.getAccount(address);
    if (accountCapsule == null) {
      return 0L;
    }

    long now = repository.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    int unfreezingV2Count = accountCapsule.getUnfreezingV2Count(now);
    return max(UnfreezeBalanceV2Actuator.getUNFREEZE_MAX_TIMES() - unfreezingV2Count, 0L,
        VMConfig.disableJavaLangMath());
  }
