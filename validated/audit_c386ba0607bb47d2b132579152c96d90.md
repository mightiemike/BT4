## Finding: `ensure_match_transaction_info` omits checkpoint-hash validation, letting replay/restore verification accept a diverged state root

### Title
Replay/restore verification (`ensure_match_transaction_info`) skips state/hot-state/position checkpoint hash checks, allowing committed state divergence to pass as verified — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by both the chunk executor's replay-verification path and the `db-tool replay-on-archive` tool to confirm that locally re-executed results match the authenticated `TransactionInfo` recorded on-chain/in backups. It validates status, gas, write-set hash, event root hash, and transaction hash — but it explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as flagged by its own TODO comment.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and its trailing comment admits the gap directly: [2](#0-1) 

This is the sole comparator used to detect divergence between a locally re-executed transaction and the authenticated `TransactionInfo` (which carries `state_checkpoint_hash` — the Sparse Merkle root of world state — and the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields on `TransactionInfoV1`, see [3](#0-2) ). Because none of these fields are compared:

- `execution/executor/src/chunk_executor/mod.rs::verify_execution` calls this function per-transaction to verify replayed chunks: [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` (the `replay-verify`/`replay-on-archive` tool used to independently confirm archived ledger history against fresh re-execution) calls the same function: [5](#0-4) 

In both call sites, a transaction whose write set, events, gas, and status match, but whose *Merkle state-checkpoint root* differs (due to a bug in checkpoint-hash computation such as in `DoStateCheckpoint`, `do_ledger_update.rs`'s `assemble_transaction_infos`, hot-state root logic, or the newer native-position checkpoint logic seen in `execution/executor/src/workflow/do_state_checkpoint.rs`), will be reported as "verified"/"successfully replayed" even though the actual Jellyfish-Merkle/SMT root the tool computed disagrees with the authenticated root bound to the ledger.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant required for replay and restore correctness: a verification tool whose entire purpose is to detect ledger-state corruption or executor bugs can silently pass even when the authenticated state root has diverged from correct re-execution. This directly undermines the guarantee that "committed state differs from the correct VM result" must be caught by verification, and it defeats the archival/backup consistency check that operators and auditors rely on to detect state divergence (e.g., from hard-fork-only bugs, checkpoint-hash regressions, or corrupted write-set-to-storage handoff). A corrupted or incorrectly-computed state root could propagate through restores/replays undetected, since the one function meant to catch such divergence structurally cannot.

### Likelihood Explanation
The condition is code-guaranteed, not probabilistic: any bug elsewhere in state-checkpoint-hash computation (a class of code the same PR/TODO calls out — `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, hot-state root, position-state checkpoint hash) will always be missed by this comparator, since it is unconditionally excluded from the check regardless of feature flags. The TODO explicitly documents this as a known-but-unfixed gap, confirming the local root cause without requiring speculation.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed values and `txn_info`, when those hashes are expected to be present (i.e., not `None` due to non-checkpoint transactions), mirroring the same defense-in-depth pattern applied to `state_change_hash`/`event_root_hash`.

### Proof of Concept
Not directly exploitable as a standalone PoC without triggering an actual checkpoint-hash-computation bug; the proof is structural/code-based: `ensure_match_transaction_info`'s body at [6](#0-5)  demonstrably never reads `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` from `txn_info`, so any test constructing a `TransactionOutput` whose recomputed checkpoint hash differs from a given `TransactionInfo`'s checkpoint hash (all other fields equal) will pass `ensure_match_transaction_info` with `Ok(())`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
