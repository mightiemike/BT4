### Title
GlobalRateLimiter caches QPS thresholds at class-load time and never re-reads config, so dynamic rate-limit tightening never takes effect - (File: framework/src/main/java/org/tron/core/services/ratelimiter/GlobalRateLimiter.java)

### Summary
`GlobalRateLimiter` reads the global and per-IP QPS limits once, at static-initializer time, from `Args.getInstance()`, and never refreshes them for the remainder of the process lifetime. This mirrors the root cause in the referenced report: a security-relevant limit (`minAnswer`/`maxAnswer` in the oracle case, QPS caps here) is snapshotted from a live, mutable configuration source at "construction" time and is subsequently treated as immutable, even though the underlying source can legitimately change while the node is running.

### Finding Description
`GlobalRateLimiter` declares: [1](#0-0) 

`QPS` and `IP_QPS` are `static` fields evaluated exactly once, at class-load time, from `Args.getInstance().getRateLimiterGlobalQps()` / `getRateLimiterGlobalIpQps()`. The shared `rateLimiter` instance is built from that one-time `QPS` value, and every per-IP `RateLimiter` later created in `loadIpLimiter` is built from the same static `IP_QPS` field: [2](#0-1) 

java-tron does support live configuration reload via `DynamicArgs`, which re-reads `config.conf` on a schedule and pushes updated values into `Args`/`CommonParameter` for a specific subset of settings (active/trust nodes): [3](#0-2) 

However, `DynamicArgs.reload()` does not touch `GlobalRateLimiter`'s QPS fields, and there is no other code path that re-derives `QPS`/`IP_QPS`/`rateLimiter` after JVM startup. This is the exact bug class from the report: a value copied out of a mutable authority (`priceFeed.aggregator()` there, `Args`/config here) into a field that is treated as a constant thereafter, so subsequent changes to the authoritative source are silently ignored by the consuming logic. The project's own configuration conventions document explicitly calls out this failure mode as a known anti-pattern ("If the value is captured in a `static final` field at class-load time... a config key is misleading — it appears tunable but changes are silently ignored"): [4](#0-3) 

The test suite for `GlobalRateLimiter` independently confirms this: it has to use reflection to force-reset the static `IP_QPS`/`rateLimiter`/`cache` fields between tests precisely because there is no supported runtime API to change them: [5](#0-4) 

### Impact Explanation
`GlobalRateLimiter` gates every unauthenticated RPC/HTTP/JSON-RPC request via `RateLimiterInterceptor` / `RateLimiterServlet` (`GlobalRateLimiter.acquirePermit` / `tryAcquire`), acting as the node's primary DoS mitigation for anonymous inbound traffic. If an operator lowers `rateLimiter.global.qps` or `rateLimiter.global.ipQps` in `config.conf` while the node is under an active flood/DoS attack — expecting the already-running `DynamicArgs` live-reload mechanism to apply it — the change is silently ignored. `GlobalRateLimiter`'s static fields keep the original, larger QPS values for the lifetime of the JVM, so the attacker continues to consume RPC resources at the old, higher rate. The only remedy is a full node restart, which itself causes an availability gap. This is a DoS-relevant defect in the RPC-API rate limiter, reachable purely via anonymous network requests, matching the report's core failure mode (a stale cached security bound that can no longer track its authoritative, mutable source).

### Likelihood Explanation
The defect triggers deterministically any time an operator relies on `node.dynamicConfig` hot-reload to adjust `rateLimiterGlobalQps`/`rateLimiterGlobalIpQps` without restarting — a realistic operational response during an ongoing flood. No attacker action is required to create the bug; the attacker only needs to be actively flooding the RPC endpoint at the moment the operator attempts to tighten limits, which is the exact scenario rate limiting exists for. Likelihood of the underlying stale-state condition existing is high (it is unconditional/always true after startup); likelihood of it being exploited to prolong a DoS window depends on operator behavior, making it moderate overall.

### Recommendation
Make `QPS`/`IP_QPS` (and the derived `rateLimiter`) re-readable at runtime instead of `static` snapshots:
- Read `Args.getInstance().getRateLimiterGlobalQps()` / `getRateLimiterGlobalIpQps()` on each use, or
- Register `GlobalRateLimiter` with `DynamicArgs.reload()` so a config change rebuilds `rateLimiter` and clears/rebuilds the per-IP `cache` with the new `IP_QPS`, mirroring how `updateActiveNodes`/`updateTrustNodes` are refreshed today.

### Proof of Concept
1. Start a fullnode with `rateLimiter.global.qps = 1000`, `node.dynamicConfig.enable = true`.
2. `GlobalRateLimiter`'s static initializer captures `QPS = 1000` at class load.
3. An attacker floods the gRPC/HTTP/JSON-RPC endpoint at ~1000 req/s, saturating node resources.
4. Operator edits `config.conf`, setting `rateLimiter.global.qps = 10`, expecting `DynamicArgs`'s scheduled reload (`node.dynamicConfig.checkInterval`) to apply it.
5. `DynamicArgs.reload()` only calls `updateActiveNodes`/`updateTrustNodes`; `GlobalRateLimiter.QPS`/`rateLimiter` are untouched.
6. The attacker's requests continue to be accepted at ~1000 req/s (verifiable by observing `GlobalRateLimiter.tryAcquire` continuing to succeed at the original rate), confirming the tightened limit never takes effect without a node restart.

```java
  private static RateLimiter loadIpLimiter(String ip) {
    try {
      // cache.get is atomic: only one loader executes per key under concurrent requests,
      // preventing multiple RateLimiter instances from being created for the same IP.
      return cache.get(ip, () -> RateLimiter.create(IP_QPS));
    } catch (Exception e) {
      logger.warn("Failed to load IP rate limiter for {}, denying request: {}",
          ip, e.getMessage());
      return null;
    }
  }
```
