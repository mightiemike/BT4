### Title
Reassigning a cached stake account's owner away from the stake program leaves a stale entry in `Stakes<StakeAccount>::stake_delegations` - (File: runtime/src/stakes.rs)

### Summary
`StakesCache::check_and_store` only evicts a cached stake/vote entry when the account's lamports drop to zero, or when the owner is (still) the stake/vote program but fails to parse. If an account that is cached as a stake delegation has its owner reassigned to a non-stake/non-vote program (e.g. `System Assign`) while lamports remain non-zero, none of the `if`/`else if` branches execute, and the stale `StakeAccount` entry is never removed from `Stakes::stake_delegations`. This is exactly the gap flagged by the `TODO` comment at lines 94-97.

### Finding Description
`check_and_store` branches on `account.owner()`: [1](#0-0) 
- If `lamports() == 0`, it removes the vote/stake entry appropriately.
- Otherwise, it only acts `if solana_vote_program::check_id(owner)` [2](#0-1)  or `else if stake_program::check_id(owner)` [3](#0-2) .
- There is **no final `else`** branch. If an account was previously cached as a stake delegation (owner == `stake::program::id()`) and its owner is later changed to something else (e.g., `system_program::id()`) via a `System Assign` instruction while lamports stay non-zero, `check_and_store` is called with the new account state, matches neither condition, and returns without touching the cache.

Attacker sequence (all reachable with a normal funded keypair, no privileged access required):
1. `CreateAccount` with `owner = stake::program::id()`.
2. Stake `Initialize`.
3. Stake `DelegateStake` with minimum delegation — this causes `check_and_store`/`upsert_stake_delegation` to insert the account into `Stakes::stake_delegations` (an `imbl::HashMap`).
4. `Assign` (System program instruction) changing the account's owner to `system_program::id()`, keeping lamports > 0.

After step 4, `Bank::update_stakes_cache`/`store_accounts` calls `StakesCache::check_and_store` with the account's new owner and non-zero lamports; the falls-through path is taken, and the previously inserted `StakeAccount` entry for `pubkey` remains in `stake_delegations` indefinitely, no longer reflecting the true on-chain owner.

### Impact Explanation
This produces a genuine and persistent divergence between the accounts-db/committed truth (account owner is now `system_program`) and the in-memory `Stakes<StakeAccount>` cache, which is authoritative for leader-schedule/stake-weight calculations elsewhere in the runtime. Each such account is cheap to create (minimum stake delegation, one `Assign` transaction) yet leaves a permanent stale entry in the cache, which is never cleaned up by any other code path shown, matching the "cheap accounts/writes forcing disproportionate storage/index work" bounty category (stale-cache growth / consistency divergence at negligible one-time cost).

### Likelihood Explanation
- Preconditions: only a funded keypair and standard System/Stake program instructions — no validator, leader, or privileged access needed.
- Feasibility: the instruction sequence (`CreateAccount` → `Initialize` → `DelegateStake` → `Assign`) uses only public, permissionless program instructions.
- Repeatability: this can be repeated per-account indefinitely and cheaply (bounded only by minimum delegation + rent + fees), so the stale-entry issue is exploitable at scale.

### Recommendation
Add a final `else` branch to `check_and_store` (or equivalent handling before the owner check) that unconditionally evicts any cached vote/stake entry for `pubkey` when the account's current owner is neither `vote_program` nor `stake_program`, regardless of lamports being non-zero — i.e., call `stakes.remove_vote_account(pubkey)` and `stakes.remove_stake_delegation(pubkey, ...)` (or check whichever cache currently holds the pubkey) whenever the owner no longer matches. This closes the exact gap noted by the `TODO` at lines 94-97.

### Proof of Concept
Rust unit test in `runtime/src/stakes.rs` (or a new test module) exercising `StakesCache::check_and_store` directly:
1. Build a valid stake `AccountSharedData` with `owner = stake::program::id()`, non-zero lamports, and a properly initialized+delegated `StakeStateV2`.
2. Call `stakes_cache.check_and_store(&pubkey, &stake_account, None, true)` and assert `stakes_cache.stakes().stake_delegations().contains_key(&pubkey)` is `true`.
3. Mutate the same `AccountSharedData`'s owner to `system_program::id()` (keep lamports > 0, e.g. via `set_owner`).
4. Call `stakes_cache.check_and_store(&pubkey, &account, None, true)` again.
5. Assert `stakes_cache.stakes().stake_delegations().contains_key(&pubkey)` is now `false` (this assertion currently **fails** against the existing code, demonstrating the bug, and should be added as a regression test enforcing the fix).
