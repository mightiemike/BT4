### Title
Attacker-inflated TRC10 asset count triggers unbounded `prefixQuery` scan on every `GetAccount` call - (chainbase/src/main/java/org/tron/core/capsule/utils/AssetUtil.java)

### Finding Description
When TRC10 "asset optimization" is enabled (`dynamicPropertiesStore.supportAllowAssetOptimization()` is true), asset balances are no longer stored inline in the `Account` protobuf; instead each `(address, assetId)` balance pair is stored as a separate key in `AccountAssetStore`, prefixed by the account address [1](#0-0) . Reading back the full set of an account's assets requires `AccountAssetStore.getAllAssets(Protocol.Account)`, which does an unbounded `prefixQuery(account.getAddress().toByteArray())` over the underlying store and rebuilds a map for every matching key [2](#0-1) .

`AssetUtil.importAllAsset(Account)` is the wrapper that performs this full scan whenever asset optimization is enabled, with no cap on the number of assets returned/scanned [3](#0-2) . This is invoked from `Wallet.java` (3 references found) as part of building the `Account` response for `GetAccount`/`wallet/getaccount`, which is a public, unauthenticated, zero-fee HTTP/gRPC read endpoint.

An unprivileged attacker can broadcast N `TransferAssetContract` transactions using N distinct TRC10 `assetName` values to a victim address, each transaction only paying the flat network fee for `TransferAssetContract` (no fee scaling with number of distinct assets held by the recipient). Each such transfer creates a new key under the victim's address prefix in `AccountAssetStore` via `putAccount`/`getAssets` [4](#0-3) . After N such transfers, every subsequent `GetAccount` call for the victim address triggers a full `prefixQuery` over N entries, work whose cost is not reflected in any fee paid by the querying caller (who pays nothing) or amortized against the cost the attacker incurred (a flat, asset-count-independent fee per transfer).

### Impact Explanation
This is a public-API denial-of-service / resource-exhaustion primitive: a single low-cost attacker action (many cheap TRC10 transfers) permanently inflates the read cost of a victim account for all future callers of a free, unauthenticated endpoint. Because `GetAccount`/`wallet/getaccount` is queried extremely frequently by wallets, exchanges, and explorers, this allows an attacker to degrade node performance or specifically target high-value/well-known addresses (e.g., exchange hot wallets) to slow down account balance queries against them, and more broadly to increase full-node CPU/disk I/O load for a cost far below the induced work — violating the intended public-cost invariant that read APIs must not expose materially underpriced state-iteration work.

### Likelihood Explanation
Feasible and fully attacker-controlled: requires only `supportAllowAssetOptimization()==true` (a chain-wide parameter set via committee proposal, not attacker-controlled but plausible on mainnet/testnet once enabled) and the target account having `getAssetOptimized()==true` (set once the account's assets are migrated to the optimized format). No authentication, special privilege, or victim cooperation is needed — any address can be targeted by simply sending it many distinct TRC10 assets. The attack is fully repeatable and scales linearly in attacker cost (N transactions) while producing scan cost that grows with N on every subsequent read, an asymmetric cost multiplier across the many callers who will query that address afterward.

### Recommendation
Bound the amount of work `getAllAssets`/`importAllAsset` can perform per call — e.g., cap the number of prefix-scanned keys returned per `GetAccount` request, paginate asset listing, or require callers to explicitly request full asset enumeration (with an associated cost) rather than doing it unconditionally inside the default `GetAccount` response path. Alternatively, consider charging or rate-limiting `GetAccount`/`wallet/getaccount` in proportion to the number of assets held by the queried account, or cap the number of distinct TRC10 asset types that can be sent to a single account without an explicit "accept new asset" registration step that carries a cost proportional to the number of distinct assets already held.

### Proof of Concept
Java integration test plan (using `AccountAssetStoreTest`-style harness):
1. Enable asset optimization: set `dynamicPropertiesStore.setAllowAssetOptimization(1)` and mark a test account's `assetOptimized` flag true.
2. For `N` in {10, 100, 1000, 10000}: populate `AccountAssetStore` with `N` distinct `(address, assetId)` keys via `putAccount` calls simulating `N` separate cheap `TransferAssetContract` transactions to the same address.
3. Measure wall-clock time of `AccountAssetStore.getAllAssets(account)` (equivalently `AssetUtil.importAllAsset(account)`) for each `N`.
4. Assert latency grows with `N` (ideally show super-linear growth relative to a baseline single-asset account), demonstrating that a `GetAccount` call against this address costs materially more CPU/disk work than the flat per-request cost assumed by the zero-fee, unauthenticated API, and that this cost was purchased by the attacker at a flat per-transfer price uncorrelated with N.

  public Map<String, Long> getAllAssets(Protocol.Account account) {
    Map<String, Long> assets = new HashMap<>();
    if (account.getAssetOptimized()) {
      Map<WrappedByteArray, byte[]> map = prefixQuery(account.getAddress().toByteArray());
      map.forEach((k, v) -> {
        byte[] assetID = ByteArray.subArray(k.getBytes(),
                account.getAddress().toByteArray().length, k.getBytes().length);
        assets.put(ByteArray.toStr(assetID), Longs.fromByteArray(v));
      });
    }
    account.getAssetV2Map().forEach((k, v) -> assets.put(k, v));
    return assets;
  }
