Found a concrete analog: an unreliable in-band sentinel heuristic used to decide where valid account data "ends" during an `AppendVec` scan, mirroring the Sherlock bug pattern (using an unreliable heuristic — `totalSupply()==0` — to classify data and silently mis-handling it).

### Title
Unreliable end-of-data heuristic (`lamports==0 && pubkey==Pubkey::default()`) in AppendVec scans can silently truncate accounts scans - ([File: accounts-db/src/append_vec.rs])

### Summary
`AppendVec::scan_accounts_stored_meta` and `AppendVec::scan_stored_accounts_no_data` both use the same heuristic to detect "the end of useful data" in an append-only storage file: if a decoded record's `lamports == 0` and `pubkey == Pubkey::default()`, the scan assumes it has walked off the end of real data (into zero-initialized/unwritten mmap space) and breaks the loop, silently ignoring everything after that offset. [1](#0-0) [2](#0-1) 

### Finding Description
Just as the Convex/Aura adapter used `totalSupply() == 0` as an unreliable proxy for "this is a stash token, skip it," these two scan functions use a data-based pattern match (`lamports == 0 && pubkey == Pubkey::default()`) as a proxy for "this is unwritten/garbage tail space, stop scanning." Both are heuristics inferred from observed data values rather than a definitive structural marker (e.g. an explicit end-of-data length/count field).

`Pubkey::default()` is the all-zero pubkey, which is also the well-known system-program address. `AppendVec` legitimately stores a `StoredMeta`/`AccountMeta` pair for *any* account that touched a slot, including tombstones written by `store_tombstones` for zero-lamport accounts carried forward across shrink [3](#0-2) . A tombstone record has `lamports == 0` by construction (it represents a zero-lamport account) [4](#0-3) . If any stored record — a tombstone, a legitimately-zeroed account, or (in principle) an account whose address happens to be the all-zero pubkey — is present at a lower offset than other alive/tombstone accounts in the same `AppendVec` and matches the `lamports==0 && pubkey==default` bit pattern, the scan stops there and all subsequent records in the file are silently dropped from the scan result, even though they physically exist and are valid.

This is structurally identical to the audited bug: a heuristic derived from account *content* (not an authoritative structural signal) is used to make a binary include/exclude decision, and the heuristic's assumption ("this pattern can only occur past the end of real data") is not actually guaranteed by the format.

### Impact Explanation
Both scan functions feed core `AccountsDb` invariants:
- `scan_accounts_without_data` / `scan_stored_accounts_no_data` back `get_unique_accounts_from_storage`, which is the input to `shrink_collect` and the ancient-append-vec packing pipeline [5](#0-4) . If a record after the false "end" sentinel is silently excluded, `shrink_collect`/`shrink_storage` would omit alive accounts from the rewritten storage, permanently losing them from the append vec being shrunk into (`store_accounts_for_shrink` only writes what `shrink_collect` returned) [6](#0-5) .
- `scan_accounts_stored_meta` (used via `scan_accounts`) feeds `generate_index_for_slot`, which builds the accounts index and the lattice hash (`lt_hash_account`) at startup from snapshot storages [7](#0-6) . Silently missing trailing records here would produce an index/hash that diverges from what the storage actually contains — i.e., an honest-node snapshot-vs-replay/hash mismatch, or a stale/missing account load, since the missed accounts would neither appear in the rebuilt index nor be reflected in `AccountsLtHash`.

Because the resulting corruption depends only on the content of a legitimately-writable record (a tombstone, or account data with `lamports=0`), this is reachable purely through normal on-disk data written by the node itself (shrink, flush) without any external adversarial input.

### Likelihood Explanation
Likelihood is difficult to establish concretely from the available code and is largely theoretical/low-confidence:
- Every account/tombstone record is preceded by a `StoredMeta.pubkey` set to the actual account's real address; for the false-positive to trigger mid-file, some record would need `pubkey == Pubkey::default()` (the literal all-zero address, i.e. the system program's own address) *and* `lamports == 0`, sitting before other real records in the same file.
- I could not find, within the available index, an explicit mechanism that writes a record with pubkey exactly `Pubkey::default()` and lamports 0 as ordinary data (as opposed to genuinely being past written length) — tombstones use the *original* account's real pubkey, not `Pubkey::default()`. Whether the system program's own account can ever be legitimately stored with 0 lamports mid-file, or whether any other code path constructs a record with this exact pattern, is unverified with the tools available.
- The tests in `test_scan_useless_accounts` / `test_scan_stored_accounts_no_data` explicitly rely on this exact sentinel (writing a `StoredMeta{pubkey: Pubkey::default(), ..}` + `AccountMeta{lamports:0,..}`) to simulate "hiding" trailing accounts [8](#0-7) , confirming the code path's behavior is intentional-by-design for that specific test scenario, but this does not by itself prove a naturally-reachable trigger in production.

Given the uncertainty about whether a naturally-occurring on-disk record can match this exact sentinel outside of deliberately crafted/corrupted data, and that "maliciously crafted snapshots" are explicitly out of scope per the SECURITY.md rules, I cannot confirm this rises to a concrete, reachable vulnerability under the stated validation bar (which requires proving concrete stale/wrong account loads or hash divergence, not merely a design pattern resembling the reported bug class).

### Recommendation
Replace the content-based heuristic with an authoritative structural signal for "end of valid data," such as relying solely on `self.len()`/the file's tracked write-cursor (which the code already checks via `offset + unaligned_stored_size > self_len`) rather than also breaking on the `lamports==0 && pubkey==default` pattern. If a sentinel is still desired for defensive parsing of unexpectedly short files, it should not double as a legitimate-content collision (e.g., use a dedicated marker that cannot arise from any valid stored account/tombstone, or only rely on the length bound check already present in both functions).

### Proof of Concept
Not established with the available tools: constructing a concrete PoC would require verifying whether any accounts-db code path can legitimately write a `StoredMeta{pubkey: Pubkey::default()}`/`AccountMeta{lamports: 0}` pair into an `AppendVec` at an offset preceding other real records (e.g., via tombstone writes, shrink packing order, or the system program's own account transitioning to 0 lamports). The existing unit tests `test_scan_useless_accounts` and `test_scan_stored_accounts_no_data_*` in `accounts-db/src/append_vec.rs` demonstrate the mechanism (manually crafted bytes) but do not demonstrate a production trigger. Given this gap, I present this as an analog worth further investigation rather than a confirmed exploitable vulnerability.
