## Title
`ensure_match_transaction_info` omits state-checkpoint / hot-state / position-state root comparison, letting replay-verify and db-tool report a corrupted ledger as valid — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness oracle used by both the executor's `verify_execution` (used during backup replay-verification in `execution/executor/src/chunk_executor/mod.rs`) and the standalone `storage/db-tool/src/replay_on_archive.rs` tool (and `aptos-move/cli`'s replay command) to confirm that re-executing historical transactions reproduces the authenticated on-chain result. The function checks status, gas, write-set hash, and event-root hash against the persisted `TransactionInfo`, but — per its own code comment — intentionally skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` validates only 4 of the fields that make up a `TransactionInfo` leaf hash: `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`. It never touches `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, which are the fields that authenticate the Sparse-Merkle/Jellyfish-Merkle *state* root (and hot-state/position-state roots) committed into the ledger's transaction accumulator. The comment directly acknowledges this:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
```

This function is the terminal integrity check in two independent code paths:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` as the pass/fail criterion for the whole replay job. [2](#0-1) 
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, used when validators/full nodes verify chunk execution during backup restore/replay verification. [3](#0-2) 

Because state-checkpoint hashes are never compared, a divergence in the recomputed Sparse Merkle Tree root (or hot-state root, or the newer native-trading position-state root) at a checkpoint transaction is invisible to this verification path. Only the write-set (the *diff* applied to state) and events are checked — not the resulting materialized state root that storage actually commits and that light clients/API responses rely on for state proofs.

### Impact Explanation
This breaks the "authenticated commitment must match the correct VM result" invariant for any tooling that relies on `ensure_match_transaction_info` as ground truth:
- `db-tool replay-on-archive`, used by operators/auditors to certify that an archived ledger correctly reproduces on-chain history, can report a clean pass even when the state root diverges — silently missing state-corruption bugs (e.g., a bug in JMT construction, hot-state promotion, or position-state root computation) that would otherwise be flagged.
- Because this is the same function invoked by the chunk executor's `verify_execution` used during fast-sync/backup-restore verification flows, a state-root divergence introduced by a storage/restore bug could pass verification undetected, and be treated as validated ledger data.

This does not directly let an attacker rewrite consensus-committed state (the accumulator/ledger-info verification elsewhere in the stack, e.g., `AccumulatorProof::verify` and `TransactionInfoListWithProof::verify`, still binds hashes correctly for consensus/sync). The impact is specifically that the *verification tooling* meant to catch state-commitment bugs has a documented blind spot on the checkpoint/state-root fields, undermining the primary defense against a "committed state differs from VM result" class of bug going unnoticed until it causes real corruption or a hard fork.

### Likelihood Explanation
This is not a theoretical edge case — the omission is explicit and acknowledged in-repo as a known gap gated behind the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature rollout, meaning the code already anticipates enabling the feature it fails to validate. Given `HOT_STATE_ROOT_IN_TXN_INFO` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are on-chain features intended for mainnet, any regression in the state/hot-state/position-state root computation logic (execution or storage side) would go completely undetected by both existing verification tools that depend on this comparator.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when the corresponding feature is enabled / the checkpoint is expected) against locally recomputed values before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` on mainnet, exactly as the existing TODO in the code states is required.

### Proof of Concept
1. Enable `HOT_STATE_ROOT_IN_TXN_INFO`/`TRANSACTION_INFO_V1` (or `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) on a test network.
2. Introduce (for test purposes) a deliberate divergence in hot-state/position-state root computation during replay (e.g., skip a hot-state promotion) so the locally recomputed state/hot-state/position-state root differs from the persisted `TransactionInfoV1` checkpoint hash, while write set and events remain identical.
3. Run `storage/db-tool/src/replay_on_archive.rs` (or the executor's `verify_execution` path) against the archived transactions.
4. Observe that `ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2204` returns `Ok(())` because it never reads `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, so the replay-verify job reports success despite the committed state root being wrong.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
