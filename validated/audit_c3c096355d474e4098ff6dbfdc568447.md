Based on my investigation, I found a directly relevant analog: a documented, already-patched vulnerability class in the `x/uexecutor` inbound-execution paths, and an un-mirrored code path that may still carry the same defect.

### Title
Missing CacheContext Protection in Direct `MsgExecutePayload` Handler Allows Fee-less UEA Execution - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
The reported Tadle bug is a class of "funds/obligations decoupled from settlement" — a party extracts value (withdraws funds) while a required subsequent obligation (settlement/gas payment) is skipped or fails, with no rollback tying the two together. Push Chain's `x/uexecutor` module has this exact bug class documented and fixed in two internal execution paths (`ExecutePayloadV2` and the CEA smart-contract path in `execute_inbound_funds_and_payload.go` / `execute_inbound_gas_and_payload.go`), where a `CacheContext` was added specifically to ensure that if gas-fee deduction fails after a UEA/contract payload executes, the payload's EVM state changes are rolled back together with the fee failure [1](#0-0) . However, the top-level, directly user-reachable `ExecutePayload` function (invoked by `MsgExecutePayload`) performs the same "execute payload, then deduct gas fee" sequence but does **not** wrap the two steps in a `CacheContext` [2](#0-1) .

### Finding Description
In `ExecutePayloadV2`, the fix comment explicitly states the invariant being protected: "If fee deduction fails, the EVM state changes from CallUEAExecutePayload are discarded — closes the free-execution gap when the UEA has no native UPC to cover gas" [1](#0-0) . The same fix (referenced as `F-2026-16738`) was applied to the CEA smart-contract inbound path, wrapping `CallExecuteUniversalTx` and `DeductGasFeesFromReceipt` in a `CacheContext` so a fee-deduction failure discards the payload's state mutation while the (unrelated) deposit remains committed [3](#0-2) .

`ExecutePayload` (the handler backing the user-facing, gasless `MsgExecutePayload` message) performs the identical sequence — `CallUEAExecutePayload` followed by `DeductGasFeesFromReceipt` — but executes both directly against `sdkCtx` with no `CacheContext`, only returning a Go error on fee failure: [2](#0-1) 

Whether this is safe depends entirely on whether returning this error unwinds *all* EVM state mutations already applied by `CallUEAExecutePayload` for this call. That guarantee holds only if `MsgExecutePayload` is executed inside the standard Cosmos SDK per-tx atomic cache-multistore with no special-case handling. Given that `MsgExecutePayload` is explicitly a **gasless** message type with dedicated allowlisting/relay infrastructure (`app/txpolicy/gasless.go`), and that the module's own engineers found it necessary to add explicit `CacheContext` protection in every other internal call site performing this exact "execute-then-charge" pattern, the absence of equivalent protection in the single directly user/relayer-reachable entry point is inconsistent with the rest of the codebase's defensive posture for this specific bug class.

### Impact Explanation
If the gasless dispatch path for `MsgExecutePayload` does not provide the same atomic-rollback guarantee as ordinary message execution (analogous to how the inbound-vote finalization flow swallows internal errors and requires manual `CacheContext` protection), an attacker-relayed payload could cause the UEA to execute a value-moving `executeUniversalTx` call (e.g., draining PRC20/native balances via the UEA) while the corresponding gas-fee obligation silently fails to be charged — the on-chain equivalent of "seller withdraws buyer's funds before completing settlement obligation," since state-changing execution is accepted without its enforced payment counterpart.

### Likelihood Explanation
Low-to-moderate confidence without being able to trace the full `msgServer.ExecutePayload` → baseapp dispatch chain in this session. If `MsgExecutePayload` runs through ordinary `runTx`/`runMsgs`, the SDK's own cache-multistore semantics already discard all state on message error, making this pattern safe by construction and the missing `CacheContext` cosmetic rather than exploitable. I was unable to fully confirm this in the given tool budget — the `x/uexecutor/keeper/msg_server.go` wiring for `MsgExecutePayload` and any gasless-specific post-handler logic (`app/txpolicy/gasless.go`) still need to be inspected to determine whether message failure here truly discards `CallUEAExecutePayload`'s state.

### Recommendation
Verify whether the gasless dispatch path for `MsgExecutePayload` provides full per-tx atomic rollback identical to standard message handling. If it does not (e.g., gasless/relayed txs use any soft-fail or partial-commit semantics), apply the same `CacheContext` pattern used in `ExecutePayloadV2` and the CEA inbound paths to `ExecutePayload` in `x/uexecutor/keeper/msg_execute_payload.go`, ensuring `CallUEAExecutePayload` and `DeductGasFeesFromReceipt` commit or roll back atomically together.

### Proof of Concept
Not constructed — this requires confirming the gasless/`MsgExecutePayload` dispatch semantics (`app/txpolicy/gasless.go` and `x/uexecutor/keeper/msg_server.go`) to determine whether a fee-deduction failure after successful `CallUEAExecutePayload` actually persists partial state, mirroring the exact reproduction pattern already validated for the CEA path in `test/integration/uexecutor/inbound_cea_smart_contract_test.go:360-479` [4](#0-3) .
