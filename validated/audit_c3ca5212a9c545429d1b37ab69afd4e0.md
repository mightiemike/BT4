### Title
Inconsistent enforcement of the 24-hour witness allowance withdrawal cooldown between `WithdrawBalanceActuator` and TVM `WithdrawRewardProcessor` - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java)

### Summary
The account field `latestWithdrawTime` is used as a rate-limiting timestamp to prevent a witness (super representative) from withdrawing its block-producing `allowance` more than once every 24 hours. This cooldown is enforced only in the classic `WithdrawBalanceContract` transaction path, but not in the TVM native-contract path (`WITHDRAWREWARD` opcode) that performs the exact same state mutation.

### Finding Description
`WithdrawBalanceActuator.validate()` reads `accountCapsule.getLatestWithdrawTime()` and rejects the transaction if less than `dynamicStore.getWitnessAllowanceFrozenTime() * FROZEN_PERIOD` (24 hours) has elapsed since the last withdrawal: [1](#0-0) 

Its `execute()` transfers `allowance` into `balance`, zeroes `allowance`, and stamps `latestWithdrawTime = now`: [2](#0-1) 

The TVM equivalent, `WithdrawRewardProcessor`, performs the identical mutation (move `allowance` into `balance`, zero `allowance`, set `latestWithdrawTime`) but its `validate()` only rejects genesis-block witnesses — it never checks `latestWithdrawTime` against the cooldown window: [3](#0-2) 

This processor is invoked from the `WITHDRAWREWARD` opcode, reachable by any deployed contract once `VMConfig.allowTvmVote()` is enabled: [4](#0-3) [5](#0-4) 

This is a direct analog of the reported bug class: the same "last-updated timestamp" gate is written in two different code paths that mutate the same state, but the min-time check is only re-derived/enforced in one of them, producing materially different behavior depending on which entry point is used.

### Impact Explanation
A non-genesis witness account can deploy (or use) a smart contract that calls `WITHDRAWREWARD` to withdraw its accumulated block-producing `allowance` at will, completely bypassing the intended 24-hour anti-spam/rate-limit rule that the protocol otherwise enforces via `WithdrawBalanceActuator`. This breaks a deliberately designed on-chain economic/security constraint and creates divergent behavior for the same logical operation depending on whether it is invoked as a top-level transaction or via a contract call, undermining consensus-level consistency of account state semantics.

### Likelihood Explanation
Any witness/SR account can trivially deploy a minimal contract that calls the `WITHDRAWREWARD` opcode; no privileged access or crafted timing/race condition is required, and the opcode is active by default under current chain parameters (`allowTvmVote`).

### Recommendation
Add the same `latestWithdrawTime` + `witnessAllowanceFrozenTime` cooldown check in `WithdrawRewardProcessor.validate()` that exists in `WithdrawBalanceActuator.validate()`, so both entry points enforce identical constraints on the same underlying account state.

### Proof of Concept
1. A witness account (not a genesis witness) accumulates `allowance` from block production.
2. It withdraws once via a normal `WithdrawBalanceContract` transaction, setting `latestWithdrawTime = now`.
3. Immediately afterward (well within the 24-hour window), it deploys/calls a contract executing the `WITHDRAWREWARD` opcode.
4. `WithdrawRewardProcessor.validate()` only checks `isGP` and passes; `execute()` withdraws the newly accrued `allowance` again and resets `latestWithdrawTime`, with no 24-hour restriction ever applied — repeatable indefinitely, unlike the transaction-based path.

  public void validate(WithdrawRewardParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();

    boolean isGP = CommonParameter.getInstance()
        .getGenesisBlock().getWitnesses().stream().anyMatch(witness ->
            Arrays.equals(ownerAddress, witness.getAddress()));
    if (isGP) {

          ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(ownerAddress)
              + "] is a guard representative and is not allowed to withdraw Balance");

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
