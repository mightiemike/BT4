Based on tracing the actual Bitcoin script construction for chunk/aggregate reveal transactions, this scenario is not exploitable by an unprivileged attacker.

**The binding to check:** the wtxid set referenced by `DataOnDa::Aggregate`'s second field == the wtxid set of the chunk reveal transactions that actually confirm on Bitcoin, keyed via `ChunkAccessor::get`/`insert` in `run_l1_block`. [1](#0-0) 

**Why the premise fails:** every reveal transaction type — including `Chunks` — begins its tapscript with `push_x_only_key(&public_key)` followed by `OP_CHECKSIGVERIFY`, using the batch prover's `da_private_key`, before any of the type-specific payload: [2](#0-1) 

The witness for this script-path spend is built by `build_witness`, which signs the sighash of the fixed reveal transaction with the prover's Schnorr key and pushes exactly `[signature, reveal_script, control_block]`:
