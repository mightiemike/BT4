## Analysis

Confirmed analog: NEAR's `DeleteAccount` action does not validate that the caller-supplied `beneficiary_id` corresponds to an existing account before deleting the source account and forwarding its balance there, mirroring the "unchecked recipient address" bug class from the EthBridge report.

### Title
Unchecked non-existent `beneficiary_id` in `DeleteAccount` action causes permanent burn of the deleted account's balance - (`runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` accepts any syntactically-valid `AccountId` as `beneficiary_id` without verifying the account actually exists, and unconditionally proceeds to delete the source account. The balance is forwarded via a system refund receipt, and per NEAR's refund semantics a failed refund (e.g., because the target does not exist) silently burns the funds instead of reverting the deletion.

### Finding Description
`action_delete_account` reads the current balance and, if positive, appends a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`, then unconditionally removes the account and clears its state [1](#0-0) . The only validation on `beneficiary_id` performed elsewhere in the codebase is that it is a syntactically valid `AccountId` (`InvalidAccountId` error), not that the account exists [2](#0-1) .

Refund receipts (`predecessor_id == "system"`) are special: `Receipt::new_balance_refund` builds a bare `Transfer` action addressed at `beneficiary_id` [3](#0-2) , and refunds are explicitly disallowed from creating new accounts — a refund to a non-existent receiver fails with `AccountDoesNotExist`, confirmed by the test `refund_may_not_create_universal_account`, which asserts a refund to a non-existent id fails rather than creating the account [4](#0-3) . Per the refunds specification, "If the execution of a refund fails, the refund amount is burnt" [5](#0-4) , and the runtime implements this by adding the failed refund's deposit to `other_burnt_amount` when the refund receipt's `result.result.is_err()` [6](#0-5) .

Because `action_delete_account` deletes the account and only afterward pushes the (potentially unfulfillable) refund receipt, there is no atomicity between "beneficiary can actually receive funds" and "source account is destroyed" — the deletion always succeeds even when the beneficiary cannot receive the balance.

### Impact Explanation
Any unprivileged transaction signer can submit `Action::DeleteAccount(DeleteAccountAction { beneficiary_id })` targeting their own (or another authorized) account with a `beneficiary_id` that is a valid-looking but non-existent `AccountId` (e.g., a mistyped, unregistered, or already-deleted account). The account's entire remaining NEAR balance is then irrecoverably burnt from total supply rather than transferred, with no revert of the deletion and no error surfaced that would let the user recover. This is a permanent, protocol-level loss of user funds triggered by a single ordinary transaction — meeting the "permanently frozen/burnt funds" impact bar.

### Likelihood Explanation
High reachability: `DeleteAccount` is a standard action available to any account owner via a normal signed transaction or meta-transaction (`meta_tx_delete_account` shows it is reachable via delegate/relayer flows too) [7](#0-6) . The only precondition is a `beneficiary_id` that parses as a valid `AccountId` but does not exist on-chain — trivial to construct (e.g., an account that was never created, or one deleted earlier in the same batch). This is far more likely to occur accidentally (typo, stale UI data, front-end bug) than as a deliberate attack, but is also trivially triggerable deliberately for griefing/self-harm testing of protocol invariants, and is unconditionally reachable by any signer with no special privilege.

### Recommendation
Before deleting the account (or before finalizing the delete), validate that `beneficiary_id` refers to an existing account, returning an `ActionErrorKind` (e.g., `BeneficiaryAccountDoesNotExist { account_id }`) instead of proceeding to delete and burn. Alternatively, make the refund and the deletion atomic so that a failed refund also rolls back the account deletion, ensuring users cannot lose funds to an unreachable beneficiary.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance and no locked stake.
2. `alice.near` signs `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent-xyz.near".parse().unwrap() })` as the final (and only) action of the receipt (satisfying `DeleteActionMustBeFinal`), where `nonexistent-xyz.near` has never been created.
3. Runtime executes `action_delete_account`: it removes `alice.near` and queues `Receipt::new_balance_refund("nonexistent-xyz.near", balance)` [8](#0-7) .
4. The refund receipt executes against `nonexistent-xyz.near`; since refunds cannot create accounts, it fails with `AccountDoesNotExist` (same mechanism verified in `refund_may_not_create_universal_account` [9](#0-8) ).
5. Per the refund-failure burn path, `alice.near`'s balance is added to `other_burnt_amount` and permanently removed from total supply [6](#0-5) , while `alice.near`'s account is already gone — funds are unrecoverable.

**Note:** I could not directly execute this scenario in a live/test harness (no code execution tool available in ask-only mode); the conclusion is derived by tracing the exact code paths and corroborating existing tests/spec documentation cited above, which together are consistent with this being a genuine, currently-unmitigated behavior in this tree.

#[test]
fn meta_tx_delete_account() {
    let relayer = alice_account();
    let sender = eve_dot_alice_account();
    let receiver = sender.clone();
    let node = RuntimeNode::new(&relayer);

    // setup: create new account because the standard accounts are validators (can't be deleted)
    let balance = Balance::from_near(1);
    node.user()
        .create_account(
            relayer.clone(),
            sender.clone(),
            PublicKey::from_seed(KeyType::ED25519, sender.as_ref()),
            balance,
        )
        .expect("account setup failed")
        .assert_success();

    let fee_helper = fee_helper(&node);

    let actions =
        vec![Action::DeleteAccount(DeleteAccountAction { beneficiary_id: relayer.clone() })];

    // special case balance check for deleting account
    let gas_cost = fee_helper
        .prepaid_delete_account_cost()
        .checked_add(fee_helper.meta_tx_overhead_cost(&actions, &receiver))
        .unwrap();
    let (_tx_result, sender_diff, relayer_diff, receiver_diff) =
        check_meta_tx_execution(&node, actions, sender, relayer, receiver.clone());

    assert_eq!(
        sender_diff,
        -(balance.as_yoctonear() as i128),
        "sender should be deleted and thus have zero balance"
    );
    assert_eq!(sender_diff, receiver_diff);
    assert_eq!(
        relayer_diff,
        balance.as_yoctonear() as i128 - (gas_cost.as_yoctonear() as i128),
        "unexpected relayer balance"
    );
    let err = node.view_account(&receiver).expect_err("account should have been deleted");
    assert_eq!(err, "Account ID #eve.alice.near does not exist");
}
