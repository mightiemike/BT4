### Title
Post-validation growth of an action receipt beyond `max_receipt_size` bypasses the receipt-size sanity check ([File: runtime/runtime/src/verifier.rs], [File: runtime/runtime/src/lib.rs])

### Summary
The reported bug class — a value that is validated once at "order creation" time but can independently drift afterward, defeating a downstream size/threshold check — has a direct, already-acknowledged analog in nearcore's receipt pipeline. A `FunctionCall` action's outgoing action receipt is checked against `max_receipt_size` once, but the receipt can still grow *after* that check (via added `output_data_receivers` or an oversized returned value converted into a `Data` receipt), so the final on-chain receipt can end up larger than the protocol's `max_receipt_size` invariant while still being accepted, exactly as the limit-order's position size could grow past `maxPositionSize` after the order was created and validated.

### Finding Description
`validate_receipt` performs the `max_receipt_size` check only in `ValidateReceiptMode::NewReceipt` mode, comparing the *current* borsh-serialized size at the time actions are validated: [1](#0-0) 

But `ValidateReceiptMode::ExistingReceipt` is explicitly documented as a deliberate carve-out to "tolerate" receipts already known to exceed this limit, because of a still-open bug (nearcore issue #12606) where receipts can be mutated (e.g., `output_data_receivers` appended, or a large return value wrapped as a `Data` receipt) **after** the size check has already passed for that receipt: [2](#0-1) 

This is reproduced directly in the test suite: a receipt is built to be exactly `max_receipt_size`, passes validation, then has `output_data_receivers` attached afterward, pushing it over the limit — and the receipt is *not* rejected, which the test comments flag as a known bug: [3](#0-2) [4](#0-3) 

The runtime does not treat this as a hard failure. Instead, downstream congestion-control code (`try_forward`, `generate_bandwidth_request`) explicitly works around it by *pretending* the receipt is at most `max_receipt_size` for forwarding/bandwidth-budget purposes — a mitigation for the symptom (receipts getting permanently stuck), not the root cause (the size invariant itself being violated): [5](#0-4) [6](#0-5) 

This is the same shape of bug as the limit-order report: a check performed at "creation time" (`max_receipt_size` validated when the receipt is first built) does not account for a later, independent state change (appended `output_data_receivers` / oversized returned values) that pushes the actual value past the limit that a later stage relies on. The nearcore team's own workaround comments ("There is a bug which allows to create receipts that are above the size limit... Runtime has to handle them gracefully until the receipt size limit bug is fixed") mirror the external report's own admission that a full on-chain sanity check is hard to guarantee and that a partial mitigation was chosen instead of a root-cause fix.

### Impact Explanation
An oversized receipt that slips past the `NewReceipt` check still carries its full, non-clamped size when persisted to the trie (delayed/outgoing-buffer queues) and when embedded in `source_receipt_proofs` for cross-shard forwarding; only the *admission/limit comparisons* are clamped to `max_receipt_size`, not the receipt's actual stored bytes. This inflates the real `ChunkStateWitness` size beyond the sizing model documented in `docs/misc/state_witness_size_limits.md` (which assumes every receipt is ≤ `max_receipt_size`), and inflates `own_congestion_info`'s memory/byte accounting with the true, larger size while the forwarding logic reasons about a clamped size — a discrepancy between the accounted and actual receipt footprint. In the worst case this degrades toward the same "un-executable/stuck" pattern the original report describes (the size-limit violation was severe enough that nearcore had to add an explicit "avoid receipts getting stuck" workaround, referenced by issue #12606), rather than a clean rejection at creation time.

### Likelihood Explanation
This is reachable by any unprivileged account that can submit a `FunctionCall` transaction: the size-inflating mutation (`output_data_receivers`, oversized `promise_return`/value-return payloads) is native contract behavior, not a privileged or adversarial-node action, exactly as demonstrated by the existing `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` tests in this tree. The bug is already tracked upstream (near/nearcore#12606) and only partially mitigated (forwarding/bandwidth clamped), while the underlying acceptance of over-limit receipts by `validate_receipt`'s `ExistingReceipt` path remains intentional and unresolved.

### Recommendation
Re-validate the final, fully-assembled receipt (including `output_data_receivers` and any appended return-value `Data` receipts) against `max_receipt_size` immediately before it is committed/queued, rather than only at initial construction, closing the same "sanity check at creation, not at final assembly" gap the external report calls out for the limit-order case. If a receipt is found to exceed the limit at that later point, fail the originating action deterministically instead of relying on downstream clamping in `try_forward`/`generate_bandwidth_request` to paper over the invariant violation.

### Proof of Concept
The existing repository test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` (lines 124–208) is a working PoC: it builds a receipt sized exactly at `max_receipt_size`, which passes the `NewReceipt` validation in `validate_receipt`, then triggers a promise chain where `output_data_receivers` is appended afterward, pushing the receipt's true size above `max_receipt_size`; the code comments and `assert_oversized_receipt_occurred` helper confirm the oversized receipt is observed on-chain rather than rejected. /// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
