## Analysis

The Velocimeter bug is a **"small input amount → derived value rounds to zero → downstream call with a hard non-zero requirement reverts"** pattern. Searching Push Chain's `x/uexecutor` module for the same class of bug in gas-abstraction / swap flows turns up a real analog in the deposit-with-autoswap path, and it's notably asymmetric with a fix the team already applied to the *refund* path for the same failure mode.

### Title
Gas-abstraction deposit-autoswap has no fallback for swap failure caused by rounding-to-zero minPCOut on low-value/low-decimal gas tokens, unlike the refund path — ([File: x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go])

### Summary
`ExecuteInboundGas` and `gasAndPayloadDepositAutoSwap` compute a swap quote and derive `minPCOut = quote * 95 / 100` before calling `CallPRC20DepositAutoSwap` (`depositPRC20WithAutoSwap` on `UniversalCore`). For low-decimal or low-unit-value gas tokens bridged in small (but validated, non-zero) amounts, the quoter's `quote` can legitimately round down toward zero, and any resulting swap failure (e.g. an AMM-side minimum-output/liquidity revert) is treated as an unconditional failure: `shouldRevert = true`, and the entire inbound is bounced back via `INBOUND_REVERT`. This is functionally the exact same "amount not large enough → derived fee/output rounds to zero → downstream revert" pattern as the Velocimeter M-2 report, just relocated from a bribe/fee contract to a Uniswap-style deposit swap.

### Finding Description
`ExecuteInboundGas` (`TxType_GAS`) requires `amount > 0` per `ValidateForExecution` ( [1](#0-0) ) but then unconditionally routes any positive amount through the swap pipeline: [2](#0-1) 

The same pattern repeats in `gasAndPayloadDepositAutoSwap`, used for `TxType_GAS_AND_PAYLOAD`: [3](#0-2) 

If `GetSwapQuote` returns a value that rounds to a very small number (or the resulting `minPCOut` is small/zero for low-decimal-token/low-priced gas assets), and the on-chain swap subsequently fails (insufficient liquidity, minimum-output revert, or any other AMM-side check tied to the tiny computed values), `CallPRC20DepositAutoSwap` returns an error. Both callers set `shouldRevert = true` unconditionally on this error: [4](#0-3) 

By contrast, the team already recognized this exact failure mode in the **outbound gas refund** path and built a two-step fallback: attempt the swap-refund first, and if it fails for any reason (fee-tier fetch, quote fetch, or the swap call itself), fall back to a no-swap direct PRC20 deposit instead of failing the whole operation: [5](#0-4) 

No equivalent no-swap fallback exists for the inbound gas-abstraction deposit path, even though it faces the identical rounding/liquidity edge case for low-decimal or low-unit-value external gas tokens.

### Impact Explanation
An ordinary, unprivileged user bridging a small (but valid, non-zero) amount of a low-decimal or low-unit-value gas token via the `TxType_GAS` / `TxType_GAS_AND_PAYLOAD` inbound flow can have their deposit unconditionally reverted back to the source chain whenever the derived swap quote/`minPCOut` is too small for the underlying swap to succeed — with no fallback path to still credit the user via a non-swap deposit. Because the failure is deterministic given the token's decimals/price and the transferred amount, the same amount will fail identically on every retry, effectively making legitimate small-value gas-abstraction deposits for such tokens permanently un-executable through ordinary, unprivileged use of the protocol. This is reachable purely through a normal external-chain deposit and default inbound voting/execution by honest validators — no privileged actor or malicious node/validator assumption is required.

### Likelihood Explanation
This is triggered by ordinary usage: any user bridging a small amount of a low-decimal gas token (e.g., a token with 2–6 decimals and low USD-equivalent unit price) through the standard gas-abstraction inbound path. It requires no cooperation from validators, TSS participants, or governance — only that the resulting swap quote/`minPCOut` be small enough to trip whatever minimum-output/liquidity constraint exists in the swap contract, which is inherent to the token's decimals and current pool pricing rather than attacker-crafted state.

### Recommendation
Mirror the refund path's design: in `ExecuteInboundGas` and `gasAndPayloadDepositAutoSwap`, if the auto-swap call fails, fall back to a direct (non-swap) `CallPRC20Deposit` of the raw amount into the recipient/UEA instead of unconditionally setting `shouldRevert = true`. At minimum, distinguish "swap failed due to rounding/liquidity on a small amount" from other hard failures so small legitimate deposits are not perpetually stuck in a revert loop.

### Proof of Concept
1. Register a low-decimal / low-unit-value external token as a `GAS`-eligible asset in `x/uregistry`.
2. Submit a `TxType_GAS` inbound with a small positive `Amount` (passes `ValidateForExecution`'s `amount > 0` check) for that token.
3. Once validator quorum is reached, `ExecuteInboundGas` computes `quote` via `GetSwapQuote` and `minPCOut = quote*95/100`; for a sufficiently small `amount`/low pool price, `quote` rounds to a value the swap contract cannot satisfy.
4. `CallPRC20DepositAutoSwap` returns an error; `execErr != nil` and `shouldRevert = true` unconditionally trigger `buildRevertOutbound`, bouncing the deposit back to the source chain (see `x/uexecutor/keeper/execute_inbound_gas.go:142-153,192-208`).
5. Resubmitting the identical inbound reproduces the same deterministic failure — the deposit can never be completed through the standard path, unlike the outbound refund path which would fall back to a non-swap deposit in the analogous situation (`x/uexecutor/keeper/outbound.go:213-253`).

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
