### Title
Stale cached `cycle-total-weight` lets aggregate-key voting cross the consensus threshold against the wrong (stale) signer-set weight - ([File: stackslib/src/chainstate/stacks/boot/signers-voting.clar])

### Summary
`signers-voting.clar` caches the total signer weight for a reward cycle the first time any signer votes, but the underlying `.signers` contract's `cycle-signer-set` for that same reward cycle can legitimately be rewritten (with different weights) later in the same prepare phase. The consensus-threshold check keeps using the stale cached total while individual vote weights are read live from the updated signer set, breaking the invariant that the aggregate-public-key vote reflects `threshold-consensus%` of the true, final signer weight for the cycle.

### Finding Description
`get-and-cache-total-weight` in `signers-voting.clar` computes and caches `cycle-total-weight[reward-cycle]` only once, on first access: [1](#0-0) 

This cache is consumed by `get-threshold-weight`, which derives the consensus threshold purely from the cached total: [2](#0-1) 

Meanwhile, each vote's weight is read live from `.signers` via `get-signer-weight` -> `get-signer-by-index`, i.e. from whatever `cycle-signer-set[reward-cycle]` currently holds: [3](#0-2) 

The `.signers` contract explicitly permits `cycle-signer-set` to be overwritten repeatedly for the *same* reward cycle - the only guard is that `last-set-cycle` still equals that cycle, which is satisfied every time the node recomputes the reward set for the still-open prepare phase of that cycle: [4](#0-3) 

The reward set/weights for a cycle are computed by `pox_5_compute_and_update_signers`, which apportions weight across signers proportionally to stacked amount via a largest-remainder method and then calls `update_signers` (which ultimately calls `set-signers`): [5](#0-4) [6](#0-5) 

Voting itself is only permitted during the prepare phase of the very cycle being decided: [7](#0-6) 

Since (a) the reward set for a cycle can be recomputed/rewritten multiple times across the blocks of that cycle's prepare phase (each time new PoX-5 stacking activity changes the largest-remainder apportionment), and (b) voting is allowed throughout that same prepare phase, an early vote can populate `cycle-total-weight` with a total that does not match the weight distribution in effect when later votes (and the threshold check) are evaluated. `get-and-cache-total-weight` never invalidates or recomputes the cache when `set-signers` rewrites `cycle-signer-set` for the cycle, so the equality "sum of weight of agreeing signers ≥ `threshold-consensus`% of the true (final) total weight of the cycle's signer set" is broken.

### Impact Explanation
This is directly analogous to the reported `vaultCount` bug class: a counter (`cycle-total-weight`) that is meant to track a live, mutable quantity (`cycle-signer-set` weights) is instead cached once and never refreshed when the underlying set is updated by a legitimate, non-privileged-triggerable code path (repeated `set-signers` calls within a cycle's prepare phase). The consequence is a signer-weight/threshold divergence: the aggregate-public-key vote (which selects the key used for block signature verification via the `.signers`/`.signers-voting` contracts) can be finalized using a wrong total, so a signer coalition can either (a) finalize a key despite holding less than the intended 70%(or configured `threshold-consensus`) share of the *actual, final* signer weight for the cycle, or (b) be unable to finalize a key that legitimately has ≥ threshold of the real final weight, because the stale cached total no longer matches reality. This falls under "signer weight below threshold or from the wrong set," causing at minimum a temporary tip/consensus disagreement among signers about which aggregate key is valid for the cycle - a High-impact minority-triggerable divergence.

### Likelihood Explanation
No majority collusion or privileged role is needed. Any single signer can trigger the caching simply by being the first to call `vote-for-aggregate-public-key` for a cycle early in its prepare phase, before the node's final reward-set recomputation for that cycle lands (which happens naturally as PoX-5 stacking activity continues through the prepare phase). This is a normal, unprivileged sequence of events rather than an adversarial majority attack, matching the "minority-triggerable" bar required.

### Recommendation
Invalidate (or recompute) `cycle-total-weight[reward-cycle]` in `signers-voting.clar` whenever `.signers`' `cycle-signer-set` is rewritten for that reward cycle (e.g., have `set-signers` clear/update the cached total transactionally, or have `signers-voting.clar` recompute the total from `cycle-signer-set` on every vote instead of caching it after the first read), so that the threshold check always reflects the currently stored signer set for the cycle.

### Proof of Concept
1. Reward cycle N enters its prepare phase. At prepare-phase block P0, the node computes an initial signer set/weights `W0` from PoX-5 stacking snapshot at P0 and calls `set-signers(N, W0)` (via `pox_5_compute_and_update_signers` -> `update_signers`).
2. Signer A immediately calls `vote-for-aggregate-public-key` for cycle N. This triggers `get-and-cache-total-weight(N)`, which sums `W0`'s weights and stores `cycle-total-weight[N] = sum(W0)`.
3. Between P0 and the end of the prepare phase, new PoX-5 stacking transactions land, changing the largest-remainder apportionment; the node recomputes the reward set at a later prepare-phase block and calls `set-signers(N, W1)` again (allowed because `last-set-cycle` is still `N`), overwriting `cycle-signer-set[N]` with a different weight distribution `sum(W1) ≠ sum(W0)`.
4. Later signers vote using `get-signer-weight`, which now reads weights from `W1`. Their combined recorded vote weight in `tally`/`round-data` is thus `W1`-denominated.
5. `get-threshold-weight(N)` still divides using the stale `cycle-total-weight[N] = sum(W0)`. If `sum(W1) > sum(W0)`, a coalition whose real share of `W1` is below the intended `threshold-consensus`% can still satisfy `new-total >= ceil(sum(W0) * threshold-consensus / 100)`, causing `vote-for-aggregate-public-key` to finalize an aggregate key with less than the intended proportion of the cycle's true final signer weight.

    pub(crate) fn pox_5_make_signer_set<I>(
        entries: &mut I,
        pox_constants: &PoxConstants,
    ) -> Result<Pox5SignerSetOutput, ChainstateError>
    where
        I: Iterator<Item = Result<RawPox5Entry, PoxEntryParsingError>>,
    {
        let mut signer_set = HashMap::new();
        let mut total_ustx_locked = 0u128;
        for entry_res in entries {
            let entry = match entry_res {
                Ok(x) => x,
                Err(PoxEntryParsingError::Skip(err_str)) => {
                    warn!(
                        "Error while iterating PoX-5 entries, impacting a single entry. Dropping entry from signer set";
                        "error" => err_str
                    );
                    continue;
                }
                Err(PoxEntryParsingError::Abort(err_str)) => {
                    error!(
                        "Abort-triggering error while iterating PoX-5 entries";
                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }
