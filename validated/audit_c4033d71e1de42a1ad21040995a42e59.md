## Finding: Gas fee is silently skipped for CEA smart-contract execution when `UniversalPayload` is omitted, reopening the "free-execution gap" the code claims to close

### Title
Fee-bypass on `executeUniversalTx` CEA calls via omitted `UniversalPayload` — attacker-triggered free EVM execution ([File: x/uexecutor/keeper/execute_inbound_gas_and_payload.go], [File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go], [File: x/uexecutor/keeper/fees.go])

### Summary
The `DynamicAfterFee`-class bug (fee logic that only fires on one code path, letting the user route around it by choosing the other path) has a direct analog in Push Chain's CEA (Cross-chain External Account) execution flow. `DeductGasFeesFromReceipt` no-ops with `nil, nil` whenever `universalPayload == nil`. Since `UniversalPayload` is an attacker-supplied, optional field of the inbound (constructed by the source-chain sender and never required for the isCEA smart-contract-recipient path), an attacker can trigger a real `executeUniversalTx` call on the recipient contract while making the surrounding gas-fee-deduction guard vacuously succeed, so the state changes always commit — with zero fee ever attempted.

### Finding Description
In the isCEA "smart contract recipient" branch of both `ExecuteInboundGasAndPayload` and `ExecuteInboundFundsAndPayload`, the intended safety design is: [1](#0-0) 

```go
cacheCtx, writeCache := sdkCtx.CacheContext()
contractReceipt, contractErr := k.CallExecuteUniversalTx(cacheCtx, ...)
var feeErr error
if contractErr == nil && contractReceipt != nil {
    feeErr = k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, contractReceipt, utx.InboundTx.UniversalPayload)
    if feeErr == nil {
        writeCache()
    }
}
```

The comment explicitly says this wrapping "closes the free-execution gap when the recipient contract has no native UPC to cover gas" — i.e., if the fee can't be paid, the `executeUniversalTx` state change must be rolled back.

However, `DeductGasFeesFromReceipt` treats a `nil` `UniversalPayload` as an automatic success, not a failure: [2](#0-1) 

```go
func (k Keeper) DeductGasFeesFromReceipt(...) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}
	...
```

`utx.InboundTx.UniversalPayload` is fully optional and attacker-controlled — it originates from the source-chain deposit event the attacker constructs, and its presence/absence gates whether `payload` bytes are even forwarded to `CallExecuteUniversalTx`: [3](#0-2) 

Because `feeErr` is `nil` when `UniversalPayload == nil`, `writeCache()` is always invoked, unconditionally committing the `executeUniversalTx` EVM state transition on the recipient contract — exactly the "free execution" the cache-wrap was designed to prevent. The PRC20 deposit into the recipient (via `gasAndPayloadDepositAutoSwap` / equivalent) is *also* already committed unconditionally, outside this cache, before this block runs. So an attacker who simply omits `UniversalPayload` on an isCEA deposit whose `Recipient` is a deployed (non-UEA) smart contract gets: (1) guaranteed asset delivery, and (2) a real, committed `executeUniversalTx(...)` call against that contract, entirely for free — no `DeductAndBurnFees` bank transfer ever attempted, unlike every other path where a non-nil payload with a too-low `MaxFeePerGas` correctly triggers `CalculateGasCost`'s validation error and a full rollback.

This mirrors the `DynamicAfterFee` root cause precisely: the fee-charging function only recognizes and prices one shape of input (`UniversalPayload != nil`) and silently treats the alternative shape (`UniversalPayload == nil`) as "nothing to charge," rather than as "fee is owed but cannot be computed." An unprivileged external depositor fully controls which shape is submitted.

### Impact Explanation
This breaks the "corruption of gas fee accounting" / "unauthorized module-originated EVM execution" invariant: computation that the protocol's own design intends to be paid for (or rolled back if unpaid) instead executes and commits for free, every time, for any CEA smart-contract recipient the attacker chooses, with no cost besides the deposit itself (which the attacker already owns/controls). Repeated at scale, this is a systematic griefing/resource-drain vector against validator computation with no corresponding fee revenue, and it defeats the module's own stated invariant ("closes the free-execution gap") for exactly the class of tx it was written to close.

### Likelihood Explanation
High. No privileged role, no validator collusion, no timing race is required — a single unprivileged external depositor chooses to omit `UniversalPayload` (or leaves `Data` empty, since the same nil-check gates both `ExecuteInboundGasAndPayload` and `ExecuteInboundFundsAndPayload`) when constructing their cross-chain deposit calldata targeting a deployed smart-contract recipient. This is reachable through the ordinary inbound-deposit → honest-UV-vote → `ExecuteInboundGasAndPayload`/`ExecuteInboundFundsAndPayload` path with no special conditions on validators.

### Recommendation
Change `DeductGasFeesFromReceipt` so that a real receipt with `GasUsed > 0` but a `nil`/missing `UniversalPayload` is treated as a fee-computation failure (return a non-nil error) rather than a silent success, forcing the surrounding `writeCache()` to be skipped and the `executeUniversalTx` state change to roll back, consistent with every other fee-failure path. Alternatively, require `UniversalPayload` to be non-nil (with sane defaults for `MaxFeePerGas`/`MaxPriorityFeePerGas`) as a structural precondition for reaching the isCEA smart-contract branch at all.

### Proof of Concept
1. Deploy an arbitrary contract implementing `executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)` on Push Chain (non-UEA, has code).
2. From a source chain, submit a bridge deposit with `IsCEA = true`, `Recipient = <that contract address>`, and omit `UniversalPayload` entirely (or send it with empty `Data`).
3. Once UVs vote the inbound through quorum, `ExecuteInboundGasAndPayload` (or `ExecuteInboundFundsAndPayload`) runs: the PRC20 deposit commits unconditionally, then `CallExecuteUniversalTx` executes inside a `CacheContext`, `DeductGasFeesFromReceipt` returns `nil` immediately because `UniversalPayload == nil`, and `writeCache()` commits the contract call's state changes.
4. Observe: `callPcTx.Status == "SUCCESS"`, the recipient contract's `executeUniversalTx` logic has run and persisted, and no `upc` balance was ever debited from the recipient/UEA for gas — confirmed by the existing test `inbound_cea_smart_contract_test.go` which already demonstrates the balance-unchanged / rollback behavior for the *non-nil, too-low-maxFeePerGas* case; supplying a `nil` payload instead skips the rollback branch altogether.
