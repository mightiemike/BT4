### Title
JSON-RPC deeply-nested `params`/`id` JSON causes unbounded recursive parsing and CPU/stack exhaustion - ([File: chain/jsonrpc/src/lib.rs])

### Summary
The NEAR JSON-RPC HTTP endpoint (`POST /`) deserializes every request body directly into `near_jsonrpc_primitives::message::Message` via Axum's `Json<Message>` extractor, using plain `serde_json` deserialization with no depth limit. `Message::Request` (and `Notification`) carry a `params: Value` field, and `id: Value`, both typed as untyped `serde_json::Value` [1](#0-0) . `serde_json::Value`'s deserialization is recursive with no built-in nesting-depth guard, so an attacker who submits a deeply nested JSON array/object as `params` (e.g. `[[[[[...]]]]]]`) forces the parser to recurse once per nesting level. This mirrors the Wazuh bug class: an API endpoint accepting attacker-controlled JSON with unbounded nesting, consumed by a generic JSON deserializer with no depth cap, leading to CPU exhaustion or stack overflow.

### Finding Description
`rpc_handler()` is the sole entry point for all JSON-RPC requests and extracts the body as `Json<Message>`, i.e., it relies on Axum's/serde_json's generic deserialization before any application-level validation occurs [2](#0-1) . The only protective control mentioned for this endpoint is a request body size limit (documented as 10MB) — that limits total bytes but not nesting depth: a payload consisting almost entirely of the single byte `[` repeated millions of times fits comfortably in 10MB and produces millions of nesting levels [3](#0-2) .

`Message`/`Request`/`Notification`/`Broken::Unmatched` all hold raw `serde_json::Value` fields that are deserialized with `serde_json::de::from_slice` with no `recursion_limit` set and no manual depth checks [4](#0-3) . Further down the pipeline, per-method parameter parsing (`Params::parse`, `unwrap_or_parse`, `try_singleton`, `try_pair`) again calls `serde_json::from_value`/`serde_json::from_slice` on the already-parsed `Value`, but by that point the expensive recursive parse of the raw bytes into `Value` has already occurred in the initial `Json<Message>` extraction step [5](#0-4) . A grep of the workspace found no `recursion_limit`, `max_depth`, or explicit nesting guard anywhere related to JSON parsing in `chain/jsonrpc*` or `core/primitives`, confirming no depth cap is enforced before or during this parse.

Because `serde_json::Value`'s `Deserialize` implementation is inherently recursive (one stack frame consumed per nested array/object level) and has no depth ceiling, sufficiently deep nesting exhausts the OS thread stack. In async Rust with Tokio, a stack overflow aborts the process (Rust's default abort-on-overflow behavior, further hardened here since the workspace release profile sets `panic = 'abort'` [6](#0-5) ), rather than being a recoverable panic — this can bring down the entire `neard` process handling that request, not just fail the one call.

### Impact Explanation
Any unauthenticated RPC caller (JSON-RPC is a public, unauthenticated endpoint by default — no `allow_run_as`-style permission gate is required, unlike the Wazuh case) can submit a single crafted HTTP POST to `/` with a deeply nested `params` or `id` value. This can:
- Pin a CPU core in tight recursive parsing for large-but-not-overflowing nesting depths, degrading RPC availability for all other callers, or
- Trigger a stack overflow that aborts the `neard` process (given `panic = 'abort'` in release), causing a full node outage — a transaction/RPC-triggered halt of node availability, which is more severe than the referenced Wazuh CPU-exhaustion DoS.

This is reachable by any RPC caller against a public JSON-RPC endpoint (port 3030 by default), one of the explicitly in-scope classes for this analysis.

### Likelihood Explanation
High. No authentication, staking, or special account state is required. The only precondition is the ability to send an HTTP POST to a node's public JSON-RPC port, which is the node's primary user-facing interface. The 10MB body size limit does not meaningfully mitigate the attack, since minimal-byte-per-depth-level payloads (single-character bracket nesting) allow attaining depths far beyond what's needed to overflow a typical thread stack well within that size budget.

### Recommendation
Enforce a maximum JSON nesting depth before/while parsing the RPC request body — e.g., use a depth-limited JSON parser configuration, pre-validate depth with a cheap streaming scan before handing the body to `serde_json`, or wrap `Message`/`Value` parsing with a bounded-recursion deserializer (such as `serde_json`'s `Deserializer::from_slice` combined with an explicit depth-tracking `Visitor`, or a crate offering depth-limited JSON value parsing). Apply the same guard to nested `params` payloads consumed later in `chain/jsonrpc/src/api/mod.rs`'s `Params::parse`, and consider running request body deserialization on a dedicated thread with a bounded/guarded stack, or increasing stack size and converting overflow into a catchable, per-request error rather than a process abort.

### Proof of Concept
Send to the node's JSON-RPC endpoint:
```
POST / HTTP/1.1
Content-Type: application/json

{"jsonrpc":"2.0","method":"status","id":<N nested arrays>,"params":<N nested arrays>}
```
where `<N nested arrays>` is constructed as `[[[[ ... ]]]]` repeated on the order of hundreds of thousands to millions of times (kept under the ~10MB body limit at 1 byte per nesting level). Repeated submission of such payloads by a single unauthenticated caller against `rpc_handler()` in `chain/jsonrpc/src/lib.rs` exhausts CPU/stack resources during the `Json<Message>` extraction step, before any method-specific validation runs.
