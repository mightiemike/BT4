### Title
VRF v2 LINK-payment fee estimation uses stale `LatestRoundData` without freshness check - ([File: core/services/vrf/v2/listener_v2_log_processor.go])

### Summary
The VRF v2 listener's `estimateFee` function calls the LINK/ETH price feed's `LatestRoundData` and consumes only the `Answer` field, without validating `UpdatedAt`, `RoundId`/`AnsweredInRound` freshness, or a non-zero/positive price, matching the bug class described in the external report (insufficient protection against stale `latestRoundData` results).

### Finding Description
In `estimateFee`, when a VRF request is paid for in LINK (i.e. `!req.NativePayment()`), the code queries the aggregator directly: [1](#0-0) 

```go
callCtx, cancel := context.WithTimeout(ctx, 1*time.Second)
defer cancel()
roundData, err := lsn.aggregator.LatestRoundData(&bind.CallOpts{Context: callCtx})
if err != nil {
    return nil, fmt.Errorf("get aggregator latestAnswer: %w", err)
}

return EstimateFeeJuels(
    req.CallbackGasLimit(),
    maxGasPriceWei.ToInt(),
    roundData.Answer,
)
```
The code only checks the `err` return value of `LatestRoundData` and unconditionally trusts `roundData.Answer`, discarding `roundData.UpdatedAt`, `roundData.RoundId`, and `roundData.AnsweredInRound`. If the LINK/ETH aggregator stalls (as can happen when an underlying Chainlink aggregator halts updates, per the report's referenced conditions), `LatestRoundData` will return no error but an outdated `Answer` and old `UpdatedAt`, and this function will silently use the stale price to estimate the LINK-denominated cost of fulfilling a VRF request.

### Impact Explanation
`estimateFee` feeds directly into subaccount balance and cost-simulation logic used when deciding whether/how to fulfill VRF randomness requests paid in LINK. A stale or drastically wrong LINK/ETH price can cause the node to systematically under- or over-estimate the LINK cost of servicing a request — leading to fulfillment transactions that are simulated against inaccurate costs (potential balance/spend miscalculation) or requests being wrongly treated as unprofitable/unfulfillable, causing missed/delayed VRF fulfillments. This is a misreporting/data-tampering-adjacent issue in a reachable node code path (not a mock), consistent with the report's "inaccurate price data can lead to functions not working as expected and/or lost funds" concern.

### Likelihood Explanation
Likelihood is Medium: it requires the underlying LINK/ETH price feed aggregator to actually stall or misbehave (an external dependency failure), which is an infrequent but realistic occurrence (as acknowledged by Chainlink's own docs on aggregator downtime scenarios referenced in the report). The code comment even acknowledges effort is limited "since it's not critical for operating VRF," suggesting the missing check was a conscious but risky trade-off.

### Recommendation
Validate the round data returned by `LatestRoundData` before use: reject the result if `roundData.Answer <= 0`, if `roundData.UpdatedAt` is older than an acceptable staleness threshold, or if `roundData.AnsweredInRound < roundData.RoundId` (indicating a carried-over stale round). On failing these checks, fall back to a configured default/fallback LINK price (as is already done elsewhere in the codebase, e.g. `FallbackLinkPrice` in Keeper/Automation registry settings) rather than silently trusting a potentially stale answer.

### Proof of Concept
Not independently reproducible from static analysis alone — reproduction would require deploying/mocking a LINK/ETH aggregator that stops updating (freezes `UpdatedAt`/`RoundId` while still returning success) and observing that `estimateFee` in `listener_v2_log_processor.go` accepts and uses the frozen `Answer` value without any staleness rejection, as shown in the cited code path.
