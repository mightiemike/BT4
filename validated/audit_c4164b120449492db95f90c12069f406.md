### Title
Replay-verify tooling accepts corrupted state roots because `TransactionOutput::ensure_match_transaction_info` never checks `state_checkpoint_hash` - ([File: types/src/transaction/mod.rs])

### Summary
`ensure_match_transaction_info`, the single routine used by both `db-tool`'s `replay_on_archive` and the chunk executor's `verify_execution` to authenticate a locally re-executed `TransactionOutput` against the archived/authenticated `TransactionInfo`, checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash - but it does not check the `state_checkpoint_hash` (the JMT/state-tree root) or `hot_state_checkpoint_hash` carried in `TransactionInfo`. A local execution that produces the correct write-set/events/gas/status but a divergent global state root (e.g. due to a state-merkle-tree bug, hot-state divergence, or an unrelated storage corruption) will still pass `ensure_match_transaction_info`, and thus pass `replay_on_archive` verification and (for non-lazy-quit) `verify_execution`, silently confirming a wrong state root as valid.

### Finding Description
`ensure_match_transaction_info` is defined in `types/src/transaction/mod.rs`: [1](#0-0) 

The function checks:
- `status()` vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed `event_root_hash` vs `txn_info.event_root_hash()`

It explicitly does **not** check `txn_info.state_checkpoint_hash()` or `hot_state_checkpoint_hash()`, and the code contains its own acknowledgment of this gap:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is consumed directly by the archive-replay verification tool: [3](#0-2) 

and by the chunk executor's own re-execution verification path used during state-sync/backup verification: [4](#0-3) 

`state_checkpoint_hash` is the authenticated field of `TransactionInfo` that is supposed to bind a version to its exact global state (via the Sparse/Jellyfish Merkle root), and it's what `TransactionInfoWithProof::verify` and downstream restore logic rely on to prove state integrity (e.g. `storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs` explicitly cross-checks `state_root_hash == manifest.root_hash` derived from `ensure_state_checkpoint_hash()`): [5](#0-4) 

However, that check only occurs for the *state-snapshot* restore path — it does not occur for the *transaction replay* path that calls `ensure_match_transaction_info`. This means that during `replay_on_archive`/`replay-verify`, a divergence in the state root produced by re-execution (state commitment corruption, hot-state schema mismatch, or a JMT computation bug) can go completely undetected as long as the write set, events, gas, and status happen to match.

### Impact Explanation
This breaks the state-proof/commitment invariant: "committed state that differs from the correct VM result... must be detected during replay/verify." Since `state_checkpoint_hash` is never validated, `replay_on_archive`/replay-verify (an authenticated verification tool relied on to confirm mainnet history integrity) can report success even when local re-execution disagrees with the archived, signature-authenticated state root. This is a hard-fork/verification-only divergence but directly affects state-commitment/proof-integrity guarantees that operators, auditors, and node bootstrappers rely on — a corrupted or subtly wrong state root would not be surfaced by this tool.

### Likelihood Explanation
Likelihood is low under normal operation (requires either a bug in state root computation, a hot-state/position-state divergence, or corrupted local storage) but the omission is unconditional and always present in the current comparator — the code's own TODO confirms the developers are aware the check is missing and gated behind enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, but the standard `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields already exist for non-trading-native transactions today and are still skipped.

### Recommendation
Add explicit verification of `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash()` where present) against the locally computed state/hot-state root inside `ensure_match_transaction_info`, or add a parallel check at each call site (`replay_on_archive.rs`, `chunk_executor::verify_execution`) before accepting a replay as verified.

### Proof of Concept
1. Take an archived transaction backup where `TransactionInfo::state_checkpoint_hash` is `H_expected` for a given version, but corrupt (or fail to update in sync with an execution bug) the local state so that after replay `H_actual != H_expected`, while gas/status/events/write-set bytes stay identical (e.g. a state-value or key-hash aliasing bug that doesn't change the write set but does change the tree structure/root).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs::execute_and_verify`) over that version range.
3. Observe `ensure_match_transaction_info` returns `Ok(())` because it never compares `state_checkpoint_hash`, so the tool reports the range as successfully verified despite the state root mismatch.

Note: I could not fully trace every downstream consumer of `TransactionOutput` state-checkpoint hashes (e.g., whether `DoStateCheckpoint`/`ensure_transaction_infos_match` in the chunk-executor commit path independently re-derives and compares `state_checkpoint_hash` before persisting, which would mitigate impact for the *commit* path specifically, as opposed to the *offline verify* tooling). Given index size limits, some related files (e.g. `chunk_result_verifier.rs`'s `ensure_transaction_infos_match`) were only partially inspected; a full Devin session with complete file access is recommended to confirm whether the commit-time path has an independent state-root check that the offline replay-verify tool lacks.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
