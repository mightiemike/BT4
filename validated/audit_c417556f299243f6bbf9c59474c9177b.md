## Title
Front-runnable, fee-free unique account-ID (`SetAccountIdContract`) registration enables account-ID squatting / griefing DoS - (File: `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
The reported bug class is a race condition in a cross-chain protocol: an attacker who observes a user's pending "create account with ID X" transaction on one chain can pre-emptively claim the same globally-unique ID on the destination chain, permanently blocking the legitimate user and wasting the fees they already paid. The reachable analog in java-tron is `SetAccountIdActuator`, which lets any account claim a globally unique, case-insensitive `account_id` on a strict first-come-first-served basis, with no cost and no binding of the ID to the caller's identity beforehand (e.g., via commit-reveal or derivation from the address).

### Finding Description
`SetAccountIdContract` allows any account with no ID yet to set an arbitrary `account_id` chosen freely by the sender, exactly as flagged in the report's root-cause description of user-chosen, unbound IDs: [1](#0-0) 

At validation time the actuator only checks that the account itself has no ID yet and that the ID string is not already present in `AccountIdIndexStore`; it does not verify any relationship between `account_id` and the calling account's address, nor does it use any commit-reveal or address-derivation scheme to prevent race capture: [2](#0-1) 

Because all pending transactions are broadcast and visible in the transaction pool/relay layer before block inclusion, an attacker can observe a victim's `SetAccountIdContract` transaction (submitted via the anonymous RPC/HTTP `wallet/setaccountid` or gRPC `SetAccountId` endpoint) and race to submit their own `SetAccountIdContract` with the identical `account_id` value: [3](#0-2) [4](#0-3) 

`AccountIdIndexStore` reserves the ID case-insensitively the moment the attacker's transaction executes, and any subsequently confirmed transaction with the same ID reverts with "This id has existed": [5](#0-4) [6](#0-5) 

Critically, `calcFee()` for this actuator returns `0`, meaning an attacker pays no fee premium (only ordinary bandwidth/energy) to squat any number of desired IDs, making bulk griefing essentially free: [7](#0-6) 

### Impact Explanation
A victim who submits a `SetAccountIdContract` transaction risks having it revert if an attacker races to claim the same `account_id` first after observing the pending transaction. Since account IDs are permanently unique once claimed and an account can only ever set its ID once (`account.getAccountId() != null && !isEmpty()` guard), the victim permanently loses the ability to ever use that ID, and the attack can be repeated at negligible cost against any target ID because of the zero-fee actuator cost. This matches the report's "Griefing" impact category: no direct profit for the attacker, but denial of a legitimate protocol feature (unique account naming) and loss of trust for affected users.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to observe a specific victim's pending transaction (via mempool/relay visibility or a public API) and race a competing transaction into the same or an earlier block, which is feasible for any node operator or well-connected observer but requires targeting a specific desired ID rather than being exploitable indiscriminately.

### Recommendation
Bind `account_id` claims to the caller in a way that prevents front-running, e.g., require a commit-reveal scheme (commit to `hash(account_id, salt)` first, reveal later) or otherwise ensure the ID cannot be observed and squatted from the mempool before the legitimate owner's transaction is finalized. Consider adding an explicit fee to `SetAccountIdActuator.calcFee()` to raise the cost of mass ID squatting.

### Proof of Concept
1. Victim broadcasts a `SetAccountIdContract` transaction with `account_id = "MyBrandName"` and `owner_address = V`.
2. Attacker observes this pending transaction (via public API/mempool) and broadcasts their own `SetAccountIdContract` with the same `account_id = "MyBrandName"` (case-insensitive match) and `owner_address = A`.
3. If the attacker's transaction is included first, `AccountIdIndexStore.put` records `"mybrandname" -> A`.
4. When the victim's transaction executes, `accountIdIndexStore.has(accountId)` returns `true`, and `validate()` throws `ContractValidateException("This id has existed")`, permanently blocking the victim from ever claiming that ID, as demonstrated by the existing unit test `nameAlreadyUsed`: [8](#0-7)
