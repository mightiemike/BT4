### Title
Genesis phantom witness vote count inflates the reward-per-vote denominator, permanently locking a portion of voter rewards - (File: `chainbase/src/main/java/org/tron/core/service/RewardViCalService.java`, `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
### Finding Description
This mirrors the reported `CreateSsl::process` bug class: an amount with no claiming authority is folded into the denominator used to divide accumulated rewards among share-holders, so the reward fraction attributable to that "phantom" amount can never be withdrawn.

In java-tron's DPoS reward system, each Super Representative's total vote count (`witness.getVoteCount()`) is used as the denominator when accumulating the reward-per-vote accumulator (`Vi`): [1](#0-0) 

and [2](#0-1) 

`witness.getVoteCount()` is seeded at genesis with a hard-coded initial value (e.g. `voteCount = 100000026` for `THKJYuUmMKKARNf7s2VT51g5uPY6KEqnat`) that is **not** backed by any real account freezing balance and voting: [3](#0-2) 

This genesis vote count is carried forward every maintenance cycle into `delegationStore.setWitnessVote(nextCycle, ...)`: [4](#0-3) 

and directly used as the divisor when computing `deltaVi = reward * DECIMAL_OF_VI_REWARD / voteCount`: [5](#0-4) 

Because this genesis vote count has no owning account, the fraction of the witness's block/vote reward that is proportionally attributed to it (`genesisVoteCount / totalVoteCount * totalReward`) is diluted out of `Vi` but is never claimed by any `userVote` in `computeReward`/`VoteRewardUtil.computeReward` — those only iterate over `accountCapsule.getVotesList()` of real voters: [6](#0-5) 

The codebase itself acknowledges this genesis-vote artifact via `tryRemoveThePowerOfTheGr()`, a governance-gated cleanup that subtracts the genesis witness vote count once a committee proposal sets `RemoveThePowerOfTheGr = 1`: [7](#0-6) 

Until that proposal is executed, the genesis vote count keeps inflating the denominator in every reward cycle, exactly analogous to the `initial_pool_deposit` in the SSL report being included in `total_liquidity_deposits` without an owner able to claim the corresponding fee share.

### Impact Explanation
The unclaimed reward fraction accumulates inside the witness's reward bucket (`delegationStore.addReward`) and is economically "locked" — no account can ever withdraw it because no address owns the genesis phantom votes. This causes real voters/stakeholders to receive systematically diluted rewards relative to their true share of votes, i.e. an accounting/reward-distribution corruption affecting all legitimate voters of the affected genesis witnesses, until governance manually removes the genesis vote power.

### Likelihood Explanation
This is not attacker-triggered; it is a structural property of genesis configuration and default reward accounting that applies automatically to every reward cycle for any witness with an initial genesis vote count, as long as `RemoveThePowerOfTheGr` has not been enacted. It requires no privileged action to manifest — it is reachable purely through normal voting and reward withdrawal flows (`VoteWitnessActuator`, `MortgageService.withdrawReward`, `VoteRewardUtil.withdrawReward`).

### Recommendation
Exclude genesis-seeded, unowned vote counts from the vote-count denominator used in `Vi`/reward-per-vote accumulation (`RewardViCalService.accumulateWitnessVi`, `DelegationStore.accumulateWitnessVi`, `MaintenanceManager.doMaintenance`), or ensure `tryRemoveThePowerOfTheGr()`-style cleanup runs unconditionally (not gated behind an optional governance proposal) so that only vote counts backed by real staking accounts contribute to the reward-sharing denominator.

### Proof of Concept
1. At genesis, witness `THKJYuUmMKKARNf7s2VT51g5uPY6KEqnat` starts with `voteCount = 100000026` with no corresponding account holding those votes (`common/src/main/resources/reference.conf`).
2. `RemoveThePowerOfTheGr` governance proposal is not (yet) enacted, so `tryRemoveThePowerOfTheGr()` is a no-op.
3. Real users vote for this witness with a much smaller total (e.g. 1,000,000 votes) via `VoteWitnessActuator`.
4. At maintenance, `MaintenanceManager.doMaintenance()` sets `delegationStore.setWitnessVote(cycle, witness, witness.getVoteCount())` = 100000026 + 1,000,000 (genesis + real).
5. Reward accrues for the witness (`payBlockReward`/`payTransactionFeeReward`), and `RewardViCalService.accumulateWitnessVi`/`DelegationStore.accumulateWitnessVi` divides that reward by the combined vote count including the 100000026 phantom votes.
6. Real voters withdraw rewards via `MortgageService.withdrawReward`/`VoteRewardUtil.withdrawReward`, computed only from their `userVote` share against the diluted `Vi`. The reward fraction proportional to the phantom 100000026 votes is never paid to anyone and stays locked in the witness's `delegationStore` reward accounting.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
