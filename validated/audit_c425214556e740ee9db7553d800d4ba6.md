### Title
Liquidity-cap-blocked PRC20 re-mint permanently freezes a legitimate user's bridged funds - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`BunniHub`'s bug was that a critical fund-moving path (vault deposit) never checked whether the external accepting party (the vault) could actually take the amount, so a full-capacity/paused vault caused the whole deposit transaction to revert. Push Chain's `x/uexecutor` module has the same shape of bug in the outbound-failure re-mint path: when a destination-chain outbound is voted as failed, the keeper unconditionally calls `CallPRC20Deposit` to mint the bridged amount back to the user without ever checking the token's configured `LiquidityCap` (`x/uregistry` `TokenConfig.LiquidityCap`). If the mint reverts because it would exceed the token's supply cap, the outbound is driven into a terminal `ABORTED` state that requires manual/governance intervention, permanently freezing the user's own funds from an ordinary, unprivileged flow.

### Finding Description
`handleFailedOutbound` in [1](#0-0)  is invoked from `FinalizeOutbound` whenever honest Universal Validators vote that a destination-chain outbound execution failed (`obs.Success == false`), for `TxType_FUNDS`, `GAS_AND_PAYLOAD`, or `FUNDS_AND_PAYLOAD` outbounds. To make the user whole, it calls: [2](#0-1) 

`CallPRC20Deposit` performs the mint on the `UniversalCore`/PRC20 handler contract via `depositPRC20Token` [3](#0-2) . Neither `handleFailedOutbound` nor `CallPRC20Deposit` nor `depositPRC20` [4](#0-3)  ever consults the token's `LiquidityCap` (a max-supply cap defined in `TokenConfig` [5](#0-4) ) or otherwise pre-checks whether the PRC20 contract has "room" to accept the mint — exactly the missing check the external `BunniHub` report calls out for vault deposits (`vault.maxDeposit`).

If the mint reverts for any capacity-related reason (liquidity cap enforced on-chain by the PRC20/handler contract, or any other transient EVM-side rejection), the failure path is: [6](#0-5) 

`AbortOutbound` moves the outbound into a terminal, non-retryable state that (per the module's documented design in `x/uexecutor/README.md`) is only resolvable by governance/operator intervention — there is no automatic retry or refund path, since retrying risks double-payment and the module explicitly avoids automatic resolution for stuck outbounds [7](#0-6) .

Reachability by an unprivileged, ordinary user: a user's own crosschain funds transfer can legitimately fail on the destination chain for reasons entirely outside the attacker's control (destination contract revert, external chain congestion, gas exhaustion, etc.) — this is the normal, documented failure path validators vote on (`Status_REVERTED`). The token supply approaching `LiquidityCap` is also reachable through ordinary bridging activity (many users depositing the same asset over time) with no privileged actor required. Once the aggregate minted PRC20 supply is at/near the configured cap, any subsequent outbound-failure re-mint for that token — for any user, not just an attacker — will revert and get stuck in `ABORTED`.

### Impact Explanation
This breaks the "no permanent freezing of user or protocol-controlled funds" invariant. A user whose outbound legitimately fails is supposed to get their bridged asset re-minted back on Push Chain per the module's own design (`PcRevertExecution`). If that re-mint fails due to a capacity constraint the code never checks for, the funds are neither on the destination chain nor returned to the user on Push Chain — they are stuck in `ABORTED` state pending governance/manual action, which is out-of-band and not guaranteed. This is a Medium-severity DoS/fund-freezing issue analogous to the M-10 BunniHub finding: no funds are stolen, but user funds become inaccessible through the protocol's normal, permissionless flow.

### Likelihood Explanation
Medium likelihood. It requires (a) an outbound of `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` type to be voted as failed by honest validators (a normal, expected occurrence for cross-chain transfers) and (b) the affected PRC20's minted supply to be at/near its configured `LiquidityCap` at that moment. Both conditions arise from ordinary, unprivileged usage (bridging activity growing supply toward the cap, and destination-chain execution failures that are common in cross-chain messaging) with no validator/relayer/admin misbehavior needed.

### Recommendation
Before attempting `CallPRC20Deposit` in `handleFailedOutbound` (and any other re-mint/refund site such as `execute_inbound_funds.go`, `execute_inbound_gas.go`, `applyGasRefund`), check the token's remaining capacity against `TokenConfig.LiquidityCap` (or query the PRC20 contract's own cap/`maxSupply`-style view function, analogous to `vault.maxDeposit`) and:
- If the mint would exceed the cap, do not silently `AbortOutbound`; instead retry later automatically (e.g., re-queue the refund/revert for a future block) or clamp/queue the excess amount so it is guaranteed to eventually be delivered instead of stuck.
- At minimum, distinguish "temporary capacity" failures from other EVM errors so temporarily-capped mints are retried rather than immediately moved to the manual-intervention `ABORTED` terminal state.

### Proof of Concept
1. Admin/registry configures a `TokenConfig` for asset `X` on chain `C` with `LiquidityCap = N` (ordinary, already-deployed config; not attacker-controlled).
2. Multiple ordinary users bridge `X` inbound over time until the PRC20's minted supply approaches `N` (normal usage, no privilege needed).
3. A user submits a crosschain payload that creates an outbound of type `FUNDS_AND_PAYLOAD` moving `X` off Push Chain; UVs later vote (honestly) that the destination execution failed (`MsgVoteOutbound` with `Success=false`) — a normal occurrence unrelated to any malicious behavior.
4. `FinalizeOutbound` → `handleFailedOutbound` attempts to re-mint the reverted amount of `X` back to the user via `CallPRC20Deposit` [2](#0-1) .
5. Because minted supply + refund amount exceeds `LiquidityCap`, the underlying EVM mint call reverts; `err != nil` causes `AbortOutbound` to be called, leaving the outbound permanently `ABORTED` and the user's funds neither on the destination chain nor restored on Push Chain, pending manual/governance resolution.

Note: I was unable to directly inspect the Solidity source of the PRC20/`UniversalCore` handler contract's `depositPRC20Token` implementation in this index to confirm it enforces `LiquidityCap` on-chain as a hard `require`/revert (the config field's existence and its documented purpose as "max supply cap for this token" strongly imply enforcement, and the Go-side `AbortOutbound` failure-handling code confirms the keeper treats *any* mint failure as terminal). Access to the full contract repository (`push-chain-core-contracts`) or a Devin session with file-system access would be needed to verify the exact on-chain enforcement mechanism and revert conditions of `depositPRC20Token`/`liquidityCap`.

// handleFailedOutbound mints back the bridged tokens to the revert recipient,
// then attempts to refund any excess gas (gasFee - gasFeeUsed) just like a
// successful outbound would. Both operations are recorded on the outbound.
func (k Keeper) handleFailedOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	// Only revert bridged funds for funds-related tx types
	if outbound.TxType == types.TxType_FUNDS || outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
		outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD {

		// Decide revert recipient safely
		recipient := outbound.Sender
		if outbound.RevertInstructions != nil &&
			outbound.RevertInstructions.FundRecipient != "" {
			recipient = outbound.RevertInstructions.FundRecipient
		}

		amount := new(big.Int)
		amount, ok := amount.SetString(outbound.Amount, 10)
		if !ok {
			return fmt.Errorf("invalid amount: %s", outbound.Amount)
		}
		receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)

		pcTx := types.PCTx{
			Sender:      outbound.Sender,
			BlockHeight: uint64(ctx.BlockHeight()),
		}
		// Capture tx hash from receipt even on EVM revert for debugging.
		if receipt != nil {
			pcTx.TxHash = receipt.Hash
			pcTx.GasUsed = receipt.GasUsed
		}
		if err != nil {
			pcTx.Status = "FAILED"
			pcTx.ErrorMsg = err.Error()
			outbound.PcRevertExecution = &pcTx
			// Re-mint failed — mark as ABORTED for manual intervention
			return k.AbortOutbound(ctx, utxId, outbound,
				fmt.Sprintf("failed to re-mint tokens for revert: %s", err.Error()))
		}
		pcTx.TxHash = receipt.Hash
		pcTx.GasUsed = receipt.GasUsed
		pcTx.Status = "SUCCESS"
		outbound.PcRevertExecution = &pcTx
		k.Logger().Info("outbound failed: funds re-minted for revert",
			"utx_id", utxId,
			"outbound_id", outbound.Id,
			"tx_hash", receipt.Hash,
		)
	}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
