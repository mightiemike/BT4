### Title
Unbounded growth of `SecondaryIndex` reverse-index Vec via repeated distinct account-data rewrites — ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
The `SecondaryIndex::insert` path (`accounts-db/src/accounts_index/secondary.rs`) maintains a `reverse_index: DashMap<Pubkey, RwLock<Vec<Pubkey>>>` that records, for each account (`inner_key`), every distinct "outer key" (e.g. an SPL-token mint or owner value embedded in the account's data) it has ever been associated with. Unlike the `AccountsIndex` slot list — which explicitly asserts against and merges duplicate per-slot entries (`update_slot_list`, `accounts-db/src/accounts_index/in_mem_accounts_index.rs:757-814`) — the reverse-index `Vec<Pubkey>` only dedups against outer keys *already present*, and nothing ever trims stale entries individually. An account owner fully controls the bytes at the indexed offset in their own account data, so they can force a new, never-seen "outer key" into this vector on essentially every write, which is exactly the fill-then-never-clean-individual-entry pattern described in the report (entries accumulate rather than being merged/removed), except here there is no explicit "kill" step at all — growth is one-directional until the whole account is destroyed.

### Finding Description
`SecondaryIndex::insert` (`accounts-db/src/accounts_index/secondary.rs:133-171`):
```rust
pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
    let reverse_index_entry = self.reverse_index.entry(*inner_key)
        .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
    let mut outer_keys = reverse_index_entry.write().unwrap();
    self.index.get(key).unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
        .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);
    if !outer_keys.contains(key) {
        outer_keys.push(*key);
    }
    ...
}
```
This is invoked from `AccountsIndex::update_secondary_indexes` (`accounts-db/src/accounts_index.rs:614-660`) on every account write when secondary indexes (`--account-index spl-token-mint` / `spl-token-owner` / `program-id`) are enabled, via `update_spl_token_secondary_indexes`, which extracts the "index key" (owner or mint pubkey) directly from the transaction-supplied account data at a fixed offset.

The comment at `secondary.rs:57-60` explicitly acknowledges the assumption this relies on:
> "The only cases where an inner key should map to a different outer key is if the key had different account data for the indexed key across different slots. As this is rare, it should be ok to use a Vec here over a HashSet..."

This assumption is not enforced anywhere — nothing prevents a user from writing to their own token-like account with a different arbitrary 32-byte value at the indexed offset in every transaction. Each such write is treated as a legitimately "different outer key across different slots" and unconditionally pushed onto the `Vec`, because the `contains()` check only rejects values already recorded for that account. There is no cap, no LRU eviction, and no per-slot coalescing (unlike `update_slot_list`, which replaces the existing entry for the same slot instead of appending).

The `Vec` is only ever fully drained, and only when the account is entirely removed from the primary index and `handle_dead_keys` triggers `purge_secondary_indexes_by_inner_key_if` → `remove_by_inner_key_if` (`secondary.rs:220-250`), which does:
```rust
let num_removed = reverse_index_entry.get().write().unwrap().drain(..)
    .map(|outer_key| self.remove_index_entries(&outer_key, inner_key) as u64)
    .sum();
```
This is an O(N) operation, where N is the number of distinct outer-key values the attacker injected, executed on the clean-thread's dead-key path (`accounts_db.rs` `handle_dead_keys`/`purge_secondary_indexes_for_dead_keys`) with a DashMap lock held on `reverse_index_entry` for the whole drain.

### Impact Explanation
- **Memory growth**: A single account can be made to hold an ever-growing `Vec<Pubkey>` (32 bytes/entry) in the validator's process memory, entirely under an unprivileged user's control, at the cost of ordinary transaction fees. There is no size limit tied to account size, rent, or lamports — this is memory external to accounts-db's account storage/space accounting and thus escapes normal capacity/rent-based mitigations.
- **Disproportionate CPU cost on clean/removal**: When the account is eventually removed from the primary index (e.g. drained to zero lamports and reclaimed by `clean_accounts`), the reverse-index cleanup does an O(N) drain+remove sequence while holding the per-inner-key `RwLock` and touching the corresponding forward-index `DashMap` entries; a large enough N (achievable with many cheap transactions) turns a single dead-key cleanup into disproportionately expensive work on the background clean thread relative to the cost paid by the attacker.
- Because this only matters when the operator has enabled secondary indexes for RPC (`--account-index`), the blast radius is scoped to validators/RPC nodes that opted into this feature — but the growth and cleanup-cost effect on such a node is real and unbounded, matching the reported bug class of "fill without corresponding cleanup causing disproportionate cost."

### Likelihood Explanation
Requires the target validator/RPC node to run with `--account-index spl-token-mint`/`spl-token-owner`/`program-id` enabled — a common RPC configuration. Given that, any unprivileged user can trigger the growth just by repeatedly rewriting an owned account's data with a new pseudo-random value at the indexed offset (no special permissions, no reliance on other validators/peers). This is a straightforward, deterministic sequence of ordinary transactions, not a race condition or timing-sensitive exploit, making likelihood high once the precondition (secondary index enabled) holds.

### Recommendation
- Cap the reverse-index `Vec<Pubkey>` length per `inner_key` (e.g., replace with a bounded structure, or convert to a `HashSet` sized/limited similarly to the forward index's `RwLockSecondaryIndexEntry`), and/or evict/replace the oldest outer-key mapping when a new one is observed rather than unconditionally appending.
- Alternatively, only track the current/most-recent outer-key value per account (single mapping) rather than accumulating history, since the multi-value case was called out as "rare" but is not actually bounded or verified.
- Add metrics/alerts on `SecondaryIndex` reverse-index entry sizes so operators can detect abuse of this vector before it causes a large O(N) cleanup stall.

### Proof of Concept
1. Run a validator/RPC node with `--account-index spl-token-owner` (or `spl-token-mint`) enabled.
2. As an unprivileged user, create and fund a token-like account (or any account satisfying the size/owner checks consulted by `update_spl_token_secondary_indexes`).
3. Repeatedly submit transactions that rewrite this account's data such that the bytes at the indexed "owner"/"mint" offset are a new, previously-unused 32-byte value each time (e.g., increment a counter into that field).
4. Observe (via `SecondaryIndex::log_contents`/`datapoint_info!` metrics in `secondary.rs:159-170`, or heap inspection) that `reverse_index.get(&account_pubkey)`'s `Vec<Pubkey>` length grows monotonically with the number of distinct values submitted, with no bound.
5. Eventually zero out the account's lamports and let it be reclaimed by `clean_accounts`; observe the `remove_by_inner_key_if` drain path taking time proportional to the accumulated vector length, executed under the per-key lock on the background clean thread.

*Note: I was unable to fully verify the exact byte layout/validation logic inside `update_spl_token_secondary_indexes` (only its call sites were inspected) due to search coverage limits; a Devin session with full repository access would be needed to confirm the precise account-data validation gates (size/program-owner checks) that bound which writes are actually indexed, though the core reverse-index growth/cleanup mechanism described above is confirmed directly from `accounts-db/src/accounts_index/secondary.rs`.*
