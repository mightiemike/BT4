### Title
Insufficient intermediate precision in `ExchangeInjectActuator.execute()` causes legitimate exchange injections validated by `doValidate()` to revert - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The `execute()` path of `ExchangeInjectActuator` recomputes the counter-token amount using plain 64-bit `long` arithmetic (`multiplyExact`/`floorDiv`), while `doValidate()` computes the exact same value using arbitrary-precision `BigInteger`. Because the `long`-based intermediate product in `execute()` can overflow even when the final (validated) quotient is small and well within bounds, transactions that pass validation can deterministically fail at execution — the same class of bug as the reported StableSwap issue, where a narrower intermediate integer type causes legitimate, validation-passing operations to revert.

### Finding Description
`doValidate()` computes `anotherTokenQuant` with `BigInteger`, which never overflows on the multiply step: [1](#0-0) 

`execute()` recomputes the *same* value, but using plain `long` multiplication before dividing: [2](#0-1) 

`multiplyExact(secondTokenBalance, tokenQuant)` throws `ArithmeticException` whenever the raw product exceeds `Long.MAX_VALUE` (~9.22e18) — even though the mathematically correct quotient `secondTokenBalance * tokenQuant / firstTokenBalance` (computed safely via `BigInteger` in `doValidate()`) is small and passes all balance-limit checks. Only the *sum* `firstTokenBalance + tokenQuant` (and the analogous second-token sum) is bounded by `dynamicStore.getExchangeBalanceLimit()`; nothing bounds the *product* of `secondTokenBalance` and `tokenQuant` used as an unreduced intermediate in `execute()`. Realistic TRC10 pool balances and inject quantities (e.g., on the order of 1e10–1e15, well within the allowed exchange-balance range) easily produce a product exceeding `Long.MAX_VALUE`, mirroring exactly the reported StableSwap defect: an intermediate calculation performed in a numeric type too narrow for the values involved, distinct from (and narrower than) the type used for validation.

### Impact Explanation
Any unprivileged account can construct a valid `ExchangeInjectContract` that passes `validate()` (since it uses `BigInteger` and only checks the final, correctly-sized result) but deterministically throws `ArithmeticException` in `execute()`, which is caught and converted to a `ContractExeException`, failing the transaction on-chain: [3](#0-2) . This blocks legitimate liquidity-injection operations on TRC10 Bancor-relay exchange pools exactly as the StableSwap report describes for swaps — a settlement/availability failure for otherwise valid, validated operations, reachable by any user without special privileges.

### Likelihood Explanation
High. No special conditions are required beyond having pool balances and an inject quantity whose pairwise product exceeds `Long.MAX_VALUE`, which is fully achievable within the token-balance ranges already permitted by `getExchangeBalanceLimit()` and TRC10 token precision/decimals design (total supply values up to `Long.MAX_VALUE` are supported). No governance/hardening flag is required to hit this code path — it exists in the default (`execute`) flow regardless of the `AllowHardenExchangeCalculation` proposal state.

### Recommendation
Make `execute()` use the same arbitrary-precision (`BigInteger`) computation as `doValidate()`, rather than re-deriving the value with `long`-based `multiplyExact`/`floorDiv`. This eliminates the intermediate-overflow mismatch between validation and execution, analogous to the recommended fix of widening intermediate precision (`Uint256` → `Uint512`) in the original report.

### Proof of Concept
1. Create an exchange pool where `firstTokenBalance` and `secondTokenBalance` are large TRC10 balances (e.g., `secondTokenBalance = 4_000_000_000L`).
2. Submit an `ExchangeInjectContract` with `tokenID = firstTokenID` and `tokenQuant = 3_000_000_000L`, chosen such that `secondTokenBalance * tokenQuant > Long.MAX_VALUE` (here `4e9 * 3e9 = 1.2e19 > 9.22e18`) but the resulting quotient `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` remains small and within `getExchangeBalanceLimit()`.
3. `doValidate()` succeeds because it computes the product/quotient with `BigInteger` (no overflow).
4. `execute()` calls `multiplyExact(secondTokenBalance, tokenQuant)`, which throws `ArithmeticException`, is caught, and the transaction fails with `code.FAILED` via `ContractExeException`, despite having passed validation — reproducing the "legitimate operation blocked by insufficient intermediate precision" impact described in the original report.
