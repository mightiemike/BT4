### Title
No slippage/minimum-output protection in `ExchangeWithdrawActuator` allows frontrunning losses on TRC10 exchange liquidity withdrawal - (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's built-in Bancor-style TRC10 token exchange (`Exchange`/`ExchangeV2` pools) allows the exchange creator to withdraw liquidity via `ExchangeWithdrawContract`. Unlike the swap operation (`ExchangeTransactionContract`), which carries an `expected` field enforcing a minimum-received-amount check, the withdraw contract has no equivalent parameter. The paired-token amount returned on withdrawal is computed live, at execution time, from the current pool ratio, so it can be manipulated by an intervening swap transaction that changes the ratio between submission and execution of the withdrawal.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum/expected amount for the paired token. This is defined in the protocol spec and used unmodified by the actuator: [2](#0-1) .

In `ExchangeWithdrawActuator.execute()`, the amount of the "another token" the withdrawer receives is computed strictly from the current pool balances (`firstTokenBalance`/`secondTokenBalance`) at execution time via cross-multiplication with the requested `tokenQuant`: [3](#0-2) . There is no field in the contract or check in `doValidate()`/`execute()` that lets the caller specify and enforce a minimum acceptable `anotherTokenQuant`, so any value computed at execution — however low — is accepted as long as it satisfies the (permissive) precision check: [4](#0-3) .

By contrast, the swap path (`ExchangeTransactionActuator`) explicitly reads an `expected` field from the contract and reverts if the computed `anotherTokenQuant` is less than that value: [5](#0-4) . This shows the codebase already recognizes the need for slippage protection for pool-ratio-dependent operations, but omitted it for the withdrawal path — the same root cause identified in the omnipool `remove_liquidity` report (a `swap`-equivalent function has slippage protection but the liquidity-removal function does not).

Because Tron's mempool/broadcast model allows other pending transactions (e.g., an `ExchangeTransactionContract` swap against the same `exchange_id`) to be ordered ahead of a withdrawal in the same block by validators/packing logic, a third party can shift the `firstTokenBalance`/`secondTokenBalance` ratio immediately before the withdrawal executes, changing the `anotherTokenQuant` the withdrawer receives — with no way for the withdrawer to bound this outcome.

### Impact Explanation
This is unprivileged, real DeFi-accounting-affecting behavior: any account that created a TRC10 exchange pool (the "LP"/creator role check is just `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`, an ordinary account, not a chain-privileged role) can have its withdrawal amount degraded by a frontrunning swap, resulting in the withdrawer receiving fewer of the paired asset than intended, with the delta effectively captured by other participants/arbitrageurs interacting with the pool. This is an accounting/value-extraction issue analogous to the referenced medium-severity omnipool finding: absence of a caller-specified minimum-output guard on a pool-ratio-dependent state-changing operation.

### Likelihood Explanation
Likelihood is realistic but bounded: exploitation requires the attacker to observe a pending `ExchangeWithdrawContract` transaction in the mempool and get their own `ExchangeTransactionContract` swap ordered before it within the same block (transaction ordering/MEV), which is feasible for network participants/block producers monitoring the mempool, similar to the frontrunning scenario in the original report. It is limited to the legacy TRC10 Bancor-exchange feature rather than a broader/newer DeFi surface.

### Recommendation
Add an `expected`-style minimum-amount parameter to `ExchangeWithdrawContract` (and ideally `ExchangeInjectContract`, which has the same computed-ratio exposure with no bound) analogous to the field already present in `ExchangeTransactionContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by reverting when the computed `anotherTokenQuant` falls below the caller-specified minimum.

### Proof of Concept
1. Alice creates/owns an exchange pool (or previously injected liquidity) with `firstTokenBalance` and `secondTokenBalance` at a known ratio.
2. Alice broadcasts `ExchangeWithdrawContract` for `tokenQuant` of `firstTokenId`, expecting a proportional `anotherTokenQuant` of `secondTokenId` based on the current ratio.
3. Before Alice's transaction is packed, an attacker broadcasts and gets included first an `ExchangeTransactionContract` that swaps a large amount of `secondTokenId` into `firstTokenId` (or vice versa), shifting `firstTokenBalance`/`secondTokenBalance` significantly, as computed in `exchangeCapsule.transaction(...)` (see `ExchangeTransactionActuator.java:68`).
4. Alice's withdrawal then executes against the new, worse ratio in `ExchangeWithdrawActuator.execute()` (lines 74-89), receiving a lower `anotherTokenQuant` than she anticipated, with no `expected`/minimum check to abort the transaction — unlike the protection present in `ExchangeTransactionActuator.doValidate()` (lines 217-221).
