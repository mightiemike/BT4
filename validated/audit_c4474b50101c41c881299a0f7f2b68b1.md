### Title
`IdempotentPromiseHandler` permanently "locks" a session-token identifier even when `afterAuth` fails, blocking legitimate retries for up to 60s - (File: `packages/apps/shopify-app-express/src/helpers/idempotent-promise-handler.ts`)

### Summary
This is the same bug class as the BendDAO report: a resource is marked "locked/used" the moment an operation is *attempted*, with no way for the legitimate owner to re-trigger the operation until an arbitrary timeout expires — even if the attempted operation failed. In `YieldStakingBase`, `tokenData.lockerAddr` was set to non-zero on first lock and blocked all further re-entry by the same actor. In shopify-app-js, `IdempotentPromiseHandler.isPromiseRunnable()` marks a session-token `identifier` as "used" the instant it is seen, regardless of whether `promiseFunction()` (the `afterAuth` hook, e.g. webhook registration) succeeds or throws.

### Finding Description
`performTokenExchange` calls the `afterAuth` hook through `callAfterAuthHook`, keyed by the raw session token: [1](#0-0) 

The dedupe logic lives in `IdempotentPromiseHandler`: [2](#0-1) 

`isPromiseRunnable()` inserts the identifier into the map and returns `true` on first sight — this happens *before* `promiseFunction()` (the `afterAuth` hook) is awaited and regardless of its outcome. If `afterAuth` throws (already handled by the caller's `try/catch`, which returns a `500`), the identifier stays marked as "already run" in the map. `clearStaleIdentifiers()` only removes it once `IDENTIFIER_TTL_MS` (60000 ms) has elapsed. Any subsequent request bearing the same (still valid) session token during that 60-second window will silently skip `afterAuth` entirely, because `isPromiseRunnable()` now returns `false` — with no error and no indication to the caller that the hook was skipped.

This mirrors the BendDAO root cause exactly: a single "already attempted" flag is treated identically to "already succeeded," and there is no path for the legitimate caller to force re-execution short of waiting out a fixed timeout.

### Impact Explanation
`afterAuth` is the documented mechanism for registering webhooks and performing other post-authentication setup outside the OAuth callback for token-exchange apps: [3](#0-2) 

If the hook throws once (e.g. transient webhook registration failure, DB blip), retries with the same still-valid session token within the TTL window are silently no-ops from the hook's perspective — the request itself still succeeds (`next()` is called), masking the fact that `afterAuth` never actually completed. This can leave an app installed without its webhooks registered for up to a minute, and — because failures are swallowed rather than surfaced — an operator has no signal that a retry didn't actually retry the hook. This is a functional/availability defect in the auth flow, not a session-forgery or cross-tenant issue.

### Likelihood Explanation
This requires no attacker action beyond normal operation: any transient failure of the `afterAuth` hook combined with App Bridge's normal retry behavior on the same session token (which is valid for a short window) triggers the silent skip. It is a "single merchant" scenario reachable through ordinary use of the token-exchange flow, not a privileged-actor or leaked-secret scenario.

### Recommendation
Only mark an identifier as "consumed" after `promiseFunction()` resolves successfully; on failure, remove the identifier immediately (or never add it) so the operation can be retried on the next request with the same token:
```ts
async handlePromise({promiseFunction, identifier}: IdempotentHandlePromiseParams) {
  if (!this.isPromiseRunnable(identifier)) return;
  this.identifiers.set(identifier, Date.now());
  try {
    await promiseFunction();
  } catch (err) {
    this.identifiers.delete(identifier); // allow retry
    throw err;
  } finally {
    this.clearStaleIdentifiers();
  }
}
```

### Proof of Concept
1. Configure an app with `future.tokenExchange: true` and an `afterAuth` hook that registers webhooks.
2. Trigger `validateAuthenticatedSession` with a fresh, valid session token while the webhook-registration endpoint is briefly failing (e.g., mock a 500 from Shopify or throw inside `afterAuth`). The middleware returns `500` per `perform-token-exchange.ts`'s catch block, but `identifiers.set(sessionToken, now)` has already executed.
3. Immediately retry the same request with the same (still valid, short-lived) session token before 60 seconds elapse. `isPromiseRunnable()` returns `false`, `afterAuth` is skipped entirely, and the request now returns `200` (`next()` is called) even though webhooks were never registered — confirmable by inspecting `packages/apps/shopify-app-express/src/middlewares/__tests__/perform-token-exchange.test.ts` expectations around `afterAuth` call counts and adapting the flow to inject a failure on the first call.

```typescript
  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
```

```markdown
## Handling revoked access tokens

Token exchange reuses a stored access token while it is unexpired. If a token is **revoked** by the merchant before it expires, it still looks valid locally, so the library will use it and the Admin API call will fail with a `401`. The library does not automatically re-authenticate in that case, so your app should handle a `401` from the Admin API by re-running the request (which triggers a fresh token exchange) or re-authenticating. Expired tokens are handled automatically.

## Webhooks

The Auth Code flow registers webhooks in its callback. Token exchange has no such callback, so register webhooks yourself with `shopify.registerWebhooks({session})`, typically from the `afterAuth` hook (see the example above).
```
