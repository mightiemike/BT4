The premise is based on a misunderstanding of how the Poseidon-BN254 hashing is structured, not on any actual code defect:

- `hash_public_inputs` builds a fixed-size vector of field elements (EPK scalars, idc, exp fields, `iss_field_hash`, `has_extra_field`, `extra_field_hash`, `jwt_header_hash`, `jwk_hash`, override-aud fields) and passes it to `hash_scalars`, which selects the Poseidon constant set purely based on the *number* of inputs (`POSEIDON_1`..`POSEIDON_16`), not their values. [1](#0-0) [2](#0-1) 
- Since both the `extra_field = None` and `extra_field = Some(...)` cases produce a vector of the *same length* (they always push exactly one `has_extra_field` scalar and one `extra_field_hash` scalar, just with different values — `Fr::zero()`/`EMPTY_EXTRA_FIELD_HASH` vs `Fr::one()`/the actual padded hash), the *same* `POSEIDON_N` constant set is correctly selected in both cases. [3](#0-2)  This is the intended, standard design — Poseidon's constants are fixed per input arity by construction (as in the reference implementation at arnaucube/poseidon-rs), and its cryptographic security (collision resistance / diffusion) comes from the permutation round structure operating on those constants, not from varying the constants based on the input values.
- There is no code path where a changed `has_extra_field`/`extra_field_hash` value fails to affect the permutation state; every input scalar feeds through `hasher.input(elem)` before `hash_in_mode`, so any change to any input element changes the entire permutation trace and thus the output hash. [4](#0-3) 
- Asserting that "shared constants fail to diffuse a value change" would require demonstrating an actual cryptanalytic collision in Poseidon-BN254 itself (i.e., breaking the underlying primitive), which is not something discoverable via source review — the round constants here match published reference test vectors, e.g. the unit test `test_poseidon_bn254_poseidon_ark_vectors` validates against the canonical `poseidon-ark` outputs. [5](#0-4) 

Since no concrete code defect causes a collision between differing `extra_field` presence states, and the hypothesis would require breaking Poseidon-BN254's underlying cryptographic security rather than exploiting an implementation bug, this does not meet the bar for a state-integrity finding.

macro_rules! neptune_hash {
    ($elems:expr, $constants:expr) => {{
        let mut hasher = Poseidon::new(&$constants);
        hasher.reset();
        for elem in $elems.into_iter() {
            hasher.input(elem.into()).expect("Too many inputs");
        }
        hasher.hash_in_mode(OptimizedStatic);
        hasher.elements[0]
    }};

pub fn hash_scalars(inputs: Vec<ark_bn254::Fr>) -> anyhow::Result<ark_bn254::Fr> {
