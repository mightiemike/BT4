### Title
Signer weight inflation via stake-splitting (Sybil signing keys) in the PoX-5 largest-remainder apportionment - (File: stackslib/src/chainstate/nakamoto/signer_set.rs)

### Summary
`pox_5_make_signer_set` (which replaced the older `floor-and-drop` scheme, per the regression test `equal_stakes_exceeding_reward_slots_are_not_all_zeroed`) assigns Nakamoto signer voting weight using a base weight `floor(stacked/threshold)` plus a "Hare"/largest-remainder round that hands out one extra weight unit per leftover slot to the signers with the largest fractional remainder, ties broken by ascending `signing_key`. This mirrors the Audius delegation bug class: a rule ("minimum stake earns 1 unit of standing") intended to apply per staking entity is instead evaluated per registered key, and an attacker who is unprivileged (any staker) can register many distinct signing keys instead of one, submitting many separate remainder "tickets" from the same pool of locked STX.

### Finding Description
In `pox_5_make_signer_set` [1](#0-0) , each `(signer_key, amount_ustx)` pair from the PoX-5 stake entries is aggregated by `signer_key` (not by underlying stacker/owner), and weight is computed as:
- `threshold = max(1, total_ustx_locked.div_ceil(reward_slots))`
- `base_weight = stacked_amt / threshold` (floor)
- `remainder = stacked_amt % threshold`
- Leftover slots (`reward_slots - sum(base_weight)`) are awarded one-per-signer to the top `min(leftover, N)` entries ranked by `remainder` (ties broken by `signing_key` ascending).

Nothing prevents the same underlying stacker/delegator from registering `k` different `signer_key`s and splitting a fixed total `amount_ustx` roughly evenly across them. Each split key independently competes in the leftover round with its own `remainder`. Because the number of "tickets" a party can submit into the leftover-round is unbounded (limited only by the number of distinct signing keys they generate, which is free), an attacker with less than `threshold` STX per key — and even less than `threshold` STX in total — can claim multiple `weight = 1` slots instead of the single slot (or zero slots) a consolidated, single-key stacker would receive. This breaks the invariant validated by the property test `check_make_signer_set` at `stackslib/src/chainstate/nakamoto/tests/signer_set.rs` — namely that `weight ∈ {floor(stacked/threshold), floor(stacked/threshold)+1}` per aggregated key — because the aggregation key is attacker-controlled and can be Sybil-fragmented, so the *per-stacker* weight-to-stake ratio is no longer bounded.

This is directly analogous to the Audius report: there, `minDelegationAmount` was enforced per-delegator-across-all-SPs instead of per-SP, letting an attacker split funds across many recipients to consume many slots cheaply. Here, the reward-slot apportionment computes weight per-`signer_key` instead of per underlying stake owner, letting an attacker split the same amount of locked STX across many keys to consume many "leftover" weight-1 slots that should have gone to the honest largest-remainder holders (or been left unassigned/consolidated), thereby directly inflating that stacker's control over the Nakamoto block-signing weight relative to the STX they actually locked.

### Impact Explanation
Signer weight directly participates in `NakamotoBlockHeader::verify_signer_signatures` / `compute_voting_weight_threshold` [2](#0-1) , which gate whether a block is accepted or rejected, and in the StackerDB listener's rejection/approval weight math [3](#0-2) . A staker who can inflate their apportioned weight beyond their true locked-STX share gains disproportionate influence over block acceptance/rejection — this is exactly the bug class called out in the rules ("signer weight below threshold or from the wrong set"), except here it's "signer weight above the stake-proportional amount," which lets a minority of real economic stake behave as if it were a larger fraction of the signer set. Given enough leftover slots are up for grabs in a given cycle (which happens whenever `total_ustx_locked` isn't an exact multiple of `threshold` for many participants — a routine occurrence), this can shift practical control of the ~70% weight-threshold needed to approve/reject Nakamoto blocks, producing temporary tip disagreement or biased block validation outcomes without requiring majority economic stake. This matches the "High" impact bucket (minority-triggerable signer-weight divergence, bounded reward/voting-power mis-allocation).

### Likelihood Explanation
The attack requires only the ability to generate multiple secp256k1 signing keys and split an existing stack (or several small stacks) across them when submitting PoX-5 stake entries — no special privilege, no majority stake, and no interaction with other in-scope subsystems is needed. The number of leftover slots available in any given cycle is a function of `total_ustx_locked mod threshold` across all participants, which is generically nonzero, so leftover slots are commonly available for capture. The cost is bounded by the number of extra keys registered (cheap) rather than by additional STX locked, making this materially cheaper than acquiring equivalent honest weight.

### Recommendation
Aggregate the leftover ("Hare") round by underlying stacker identity (or PoX reward address / delegation principal) rather than purely by `signer_key`, or cap the number of leftover-round tickets a single underlying stacker can submit to 1 regardless of how many `signer_key`s they register with sub-threshold remainders. Alternatively, disallow a stacker/delegate from splitting the same reward cycle's locked STX across more than one `signer_key`, mirroring the recommended Audius fix of enforcing the threshold/allocation rule per delegatee (here, per underlying staking entity) instead of per registered key.

### Proof of Concept
1. Attacker locks `X` STX where `X < threshold` (or `X` is deliberately fragmented) for a PoX-5 reward cycle.
2. Instead of stacking under one `signer_key`, the attacker submits `k` distinct stake entries, each with a different `signer_key`, splitting `X` into `k` sub-threshold chunks (e.g., `X/k` each), so each entry has `base_weight = 0` and `remainder = X/k`.
3. When `pox_5_make_signer_set` runs its Hare/largest-remainder round [4](#0-3) , if there are `leftover >= k` slots available (common when many participants produce nonzero remainders), all `k` of the attacker's split keys can be selected, each receiving `weight = 1` — i.e., the attacker obtains `k` units of signer weight from `X` STX, whereas a single consolidated key with the same `X` STX would receive at most `1` leftover unit (and only if it wins the remainder tie-break at all).
4. Repeated across cycles/attackers, this inflates the attacker's fraction of `total_weight` used in `compute_voting_weight_threshold`, giving them outsized influence on Nakamoto block sign-off relative to actual locked STX — the exact "signer weight not matching the burn/stake-weight function" divergence targeted by this scan's scope.

*(Note: I was unable to fully inspect `pox_5_stake_entries` to confirm whether any upstream Clarity-side check limits one `signer_key` per stacker per cycle, which would materially affect exploitability; if such a check exists, it should be verified before treating this as fully confirmed. This is a limitation of the available context — a deeper live-code review of `pox_5_stake_entries` and pox-5.clar's stack-stx/delegate-stack-stx entry points is recommended to fully confirm the absence of a one-signer-key-per-stacker constraint.)*

    pub(crate) fn pox_5_make_signer_set<I>(
        entries: &mut I,
        pox_constants: &PoxConstants,
    ) -> Result<Pox5SignerSetOutput, ChainstateError>
    where
        I: Iterator<Item = Result<RawPox5Entry, PoxEntryParsingError>>,
    {
        let mut signer_set = HashMap::new();
        let mut total_ustx_locked = 0u128;
        for entry_res in entries {
            let entry = match entry_res {
                Ok(x) => x,
                Err(PoxEntryParsingError::Skip(err_str)) => {
                    warn!(
                        "Error while iterating PoX-5 entries, impacting a single entry. Dropping entry from signer set";
                        "error" => err_str
                    );
                    continue;
                }
                Err(PoxEntryParsingError::Abort(err_str)) => {
                    error!(
                        "Abort-triggering error while iterating PoX-5 entries";
                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();
