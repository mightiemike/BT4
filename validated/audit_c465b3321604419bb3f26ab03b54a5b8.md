## Analog Found

### Title
Excess attached deposit not refunded to caller in `AddressRegistrar::register` - ([File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs])

### Summary
`AddressRegistrar::register` is a `#[payable]` method that only requires enough attached deposit to cover the storage cost of the new `address -> account_id` mapping, but on the success path it silently keeps the *entire* attached deposit, including any amount above the computed `required_deposit`. This mirrors the reported Allo.sol pattern where `msg.value` can exceed the actual cost (`baseFee + _amount`) and the surplus is never returned to the caller.

### Finding Description
In `register`, the contract computes the exact storage cost needed: [1](#0-0) 

It only validates that `given_deposit >= required_deposit` and panics if insufficient, but performs no check for `given_deposit > required_deposit`. On the success path (`Entry::Vacant`), the mapping is inserted and the full `given_deposit` (attached NEAR) is retained by the contract with no refund of the difference: [2](#0-1) 

By contrast, in the collision branch (`Entry::Occupied`), the contract explicitly refunds the entire deposit via a transfer promise back to the predecessor: [3](#0-2) 

showing the contract authors clearly understood the need to return deposits when appropriate, but omitted the excess-refund logic in the success path.

At the NEAR protocol level, an attached deposit is credited to the receiving contract's balance immediately when the function call begins, and it is refunded to the predecessor automatically by the runtime **only if the receipt execution fails** — the economics/refunds model does not know about "expected cost" vs. "attached amount"; that is purely up to contract logic: [4](#0-3) [5](#0-4) 

This is confirmed by the wallet-contract integration test, which explicitly documents that on a successful call routed through the registrar, the caller loses **at least** the full deposit amount, even though only a fraction of it is actually required for storage: [6](#0-5) 

Since `AddressRegistrar` exposes no withdraw/owner-recovery method, any excess yoctoNEAR sent by a caller (directly, or indirectly via the NEAR wallet contract's `register`/EVM-relay flow) is permanently absorbed into the registrar contract's balance with no mechanism for the depositor (or anyone) to reclaim it.

### Impact Explanation
Any unprivileged caller — including callers relayed through the NEAR wallet contract (`rlp_execute`/EVM-style transaction relay) — who attaches more NEAR than the exact storage cost to `register` permanently loses the difference. There is no owner/withdraw function in `AddressRegistrar`, so the surplus is frozen in the contract's account balance forever. This is a direct value-loss bug matching the external report's bug class: unrefunded excess payment permanently locked in the receiving contract.

### Likelihood Explanation
High likelihood of occurrence in practice: callers (especially indirect callers going through the wallet-contract's EVM-style relay, where the deposit amount is computed/rounded from Wei-to-yoctoNEAR conversions) have no strong guarantee of attaching the exact required amount, and the contract provides no incentive or requirement to compute it precisely. Any overpayment is silently absorbed.

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute `given_deposit.saturating_sub(required_deposit)` and, if non-zero, issue a transfer promise refunding the surplus back to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Entry::Occupied` branch.

### Proof of Concept
1. Caller invokes `AddressRegistrar::register("alice.near")` with `attached_deposit = required_deposit + X` yoctoNEAR (X > 0), where `required_deposit` is computed from `storage_byte_cost() * (20 + len(account_id))`.
2. Since `given_deposit >= required_deposit`, the deposit check at lines 54-61 passes.
3. The address is not already registered, so execution takes the `Entry::Vacant` branch (lines 66-72), which inserts the mapping and returns `Some(address)` without issuing any refund.
4. The full `given_deposit` (including the extra `X` yoctoNEAR) becomes part of `AddressRegistrar`'s account balance permanently; the caller has no way to recover `X`.
5. This is exactly what the `test_caller_refunds` integration test observes: on a successful registrar call, `pre_tx_account_balance - post_tx_account_balance >= deposit_amount`, i.e., the caller is charged the full attached amount regardless of the actual storage cost.
