### Title
Replay-verification comparator silently ignores state-checkpoint / hot-state / position-state root hashes, allowing corrupted checkpoint state to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-comparator used by state-sync's chunk executor and by db-tool's replay-verify/replay-on-archive tooling to confirm that a locally re-executed transaction's output matches the accumulator-committed `TransactionInfo`. The function checks status, gas used, write-set hash, and event-root hash, but explicitly skips comparing the state-checkpoint hash, hot-state checkpoint hash, and position-state checkpoint hash fields, as acknowledged by an in-code TODO. This means a local execution result whose checkpoint/state root diverges from the authenticated on-chain `TransactionInfo` is reported as "matching," defeating the purpose of the check.

### Finding Description
`ensure_match_transaction_info` ( [1](#0-0) ) validates a `TransactionOutput` against a `TransactionInfo` pulled from an accumulator-proven, peer- or archive-supplied source. It verifies:
- execution status [2](#0-1) 
- gas used [3](#0-2) 
- write-set hash [4](#0-3) 
- event root hash [5](#0-4) 

It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is explicitly called out: [6](#0-5) 

This comparator is invoked in the `ChunkExecutor::verify_execution` path, which is used for both live state-sync chunk verification and for replay-verify/replay-on-archive tooling to confirm re-execution against `TransactionInfo`s carried by an accumulator proof: [7](#0-6) 

Because the accumulator proof authenticates the whole `TransactionInfo` (hashed as a leaf, including its checkpoint-hash fields — see `TransactionInfoV0`/`V1` builders at [8](#0-7) ), the *authenticated* value is available, but the comparator throws it away for these three fields.

### Impact Explanation
The state/hot-state/position-state checkpoint hashes are the durable commitments to a node's Merkle state root at that version — exactly the "committed state that differs from the correct VM result" category this scan targets. If a node's local state-checkpoint computation diverges from the authenticated on-chain value (due to a VM/state-merkle bug, feature-flag skew such as the referenced `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, or an incompletely-rolled-out state feature), this divergence is the exact class of bug that `verify_execution`/replay-verify exists to catch. With the current comparator, such a divergence is **not detected**: the tool/executor reports the chunk as verified even though the locally committed database's Merkle roots do not match the authenticated ledger. This can let corrupted local state persist silently through state-sync execution-mode catch-up and through operator-run replay-verify audits, undermining the primary safety net that would otherwise catch a state-root divergence bug before it propagates into further commits or is discovered post-hoc during an incident.

### Likelihood Explanation
This does not require a malicious peer or governance/admin privilege — the gap is triggered purely by a legitimate but diverging local execution (e.g., new state feature not fully wired, an execution bug in the state-checkpoint computation path). The bypass is deterministic and always present since the code path unconditionally omits the comparison; it does not depend on an attacker at all, only on the existence of divergent local checkpoint output, which is precisely the scenario this comparator is meant to protect against.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present in the `TransactionOutput`/execution result) against the corresponding fields on the authenticated `TransactionInfo`, returning an error on mismatch, consistent with how write-set and event-root hashes are already validated. Gate the position-state comparison behind the same flag that gates the state's own inclusion (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) if the field isn't always populated, but do not silently skip validation once a checkpoint hash is present in both sides.

### Proof of Concept
Not directly exploitable by an external adversary (no untrusted input path other than legitimate divergent local execution); a concrete PoC would require constructing a `TransactionOutput` whose write-set/event hashes match the accumulator-proven `TransactionInfo` but whose state-checkpoint hash differs from the `TransactionInfo`'s checkpoint hash, then calling `ChunkExecutor::verify_execution` and observing that `Ok` is returned despite the checkpoint mismatch — this follows directly from the code at [1](#0-0)  where no assertion path touches the checkpoint-hash fields.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
