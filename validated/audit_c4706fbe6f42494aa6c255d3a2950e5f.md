This confirms the vulnerability pattern. The auto-swap mechanism uses `GetSwapQuote()` [1](#0-0)  which reads a live spot-price quote from an on-chain Uniswap V3 QuoterV2 pool, then computes a fixed 5% slippage bound (`minPCOut = quote * 95 / 100`) with no TWAP or oracle cross-check, used identically in `ExecuteInboundGas` [2](#0-1) , `gasAndPayloadDepositAutoSwap` [3](#0-2) , and `applyGasRefund` [4](#0-3) . ### Title
Unprotected spot-price swap quote in gas/fund auto-swap enables sandwich extraction of bridged value - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
The external report describes how an attacker can exploit an "unfair" fee/valuation mechanism that reads a manipulable, momentary market state (active-bin liquidity) right before a flashloan executes, letting the attacker extract most of the value that should have gone to passive liquidity providers. Push Chain's `x/uexecutor` auto-swap flow has the same root cause: it queries an on-chain Uniswap V3 `QuoterV2` for a live spot-price quote and immediately uses that quote (minus a flat 5% tolerance) as the execution-time price floor for swapping a user's bridged PRC20 into native PC, with no TWAP, no external oracle cross-check, and no protection against the quote being read at a manipulated price.

### Finding Description
Whenever an inbound crosschain deposit carries a `GAS` or `GAS_AND_PAYLOAD` tx type, the keeper auto-swaps the deposited PRC20 for native PC to fund the recipient's gas: it calls `GetDefaultFeeTierForToken`, then `GetSwapQuote` (a live `quoteExactInputSingle` call against the pool's current reserves), then derives `minPCOut = quote * 95 / 100` and immediately executes `CallPRC20DepositAutoSwap` against that same pool [6](#0-5) . The exact same pattern is used for the `GAS_AND_PAYLOAD` inbound path [3](#0-2)  and for the outbound gas-refund swap-back leg [4](#0-3) .

Because the quote is a raw spot price read from `quoteExactInputSingle` [1](#0-0) , any unprivileged external actor can push the pool's reserves temporarily in their favor (e.g. via a large swap against the same pool submitted with a higher gas price/priority so it lands in an earlier or the same block just before the finalizing `MsgVoteInbound`/`MsgVoteOutbound` transaction executes), causing the quoted `amountOut` to be depressed. The protocol then executes the real swap and accepts anything down to 95% of that already-depressed quote, so the recipient/protocol receives up to a full slippage-band's worth less PC than a fair, unmanipulated price would produce. The attacker reverses their price-moving trade afterward (or simply lets natural arbitrage restore price) and captures the difference. This mirrors the report's root cause: reading a manipulable, momentary on-chain state right before a value-transfer event and using it as the basis for how much value a passive party receives — the auto-swap "gives" the recipient/protocol reserves a worse price while an unprivileged attacker profits from the price they themselves distorted.

The pools used for this auto-swap are also intentionally thin (e.g., created with 1 token vs 4 WPC in local setup) [5](#0-4) , meaning even modest capital is sufficient to move the quoted price meaningfully within the fixed 5% band.

### Impact Explanation
This corrupts PRC20/native asset accounting for every gasless inbound deposit and every outbound gas refund that goes through the auto-swap path: the amount of native PC actually credited to the recipient (or refunded to the sender) can be systematically less than fair value, with the shortfall extractable by an unprivileged attacker sandwiching the swap. This falls squarely within "corruption of PRC20 or native asset accounting, gas fee accounting, refund accounting... token mapping" in the allowed impact list, and is reachable purely through ordinary user deposit/outbound-refund flows — no privileged validator or TSS behavior is required, only normal transaction submission with fee/priority control.

### Likelihood Explanation
Medium-to-High. It requires no validator collusion — an unprivileged actor only needs to submit a transaction against the same shallow Uniswap V3 pool with sufficient priority/gas to land before (or in the same block as) the auto-swap-triggering vote transaction. Given the pools are protocol-specific and thin by design, the capital and timing requirements are low relative to the value that can be diverted from every gas-bearing inbound/outbound.

### Recommendation
Do not derive `minPCOut` purely from an instantaneous `quoteExactInputSingle` spot read. Use a time-weighted average price (TWAP) over multiple blocks, or bound the acceptable quote against an independent oracle/registry-configured reference price, and/or make the slippage tolerance a function of the configured pool's liquidity depth rather than a flat 5%. Consider also capping the maximum single-block price deviation the quote is allowed to reflect before falling back to the no-swap PRC20-direct-deposit path.

### Proof of Concept
1. Attacker identifies the thin PRC20/WPC Uniswap V3 pool backing a given `defaultFeeTier` token used by `GetSwapQuote` [1](#0-0) .
2. Attacker submits a swap against that pool (in the mempool, with elevated fee/priority) that depresses the PRC20→WPC price just before observing (or predicting) that a `MsgVoteInbound`/`MsgVoteOutbound` transaction carrying a `GAS`/`GAS_AND_PAYLOAD` inbound, or an outbound gas-refund, is about to reach quorum and trigger `ExecuteInboundGas`/`applyGasRefund`.
3. When quorum is reached, `GetSwapQuote` returns the depressed price; `minPCOut` is set to 95% of that depressed value [7](#0-6) ; `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` executes the swap and accepts the reduced output.
4. Attacker reverses their price-distorting trade, pocketing the difference between the fair price and the depressed execution price, at the expense of the deposit recipient / refund recipient / protocol liquidity.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}

// gasAndPayloadDepositAutoSwap handles the swap quote + deposit autoswap for GAS_AND_PAYLOAD.
func (k Keeper) gasAndPayloadDepositAutoSwap(
	sdkCtx sdk.Context,

		return nil, err

		return nil, err

		return nil, err

	quote, err := k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)

		return nil, err

	minPCOut.Div(minPCOut, big.NewInt(100))
