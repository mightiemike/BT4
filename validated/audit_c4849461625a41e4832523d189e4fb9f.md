### Title
Inconsistent "current block number" used for proof-facts recency check between stateful validation and actual block execution - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
This mirrors the Ajna "Early vote cutoff" bug class: a boundary/window check for a time-bounded action (there: screening-period end computed from the wrong reference block; here: the "is the proof block too recent" check computed from the wrong reference block number) is evaluated against two different "current" reference points in two different code paths, so the same invariant is enforced inconsistently depending on which stage validates the transaction.

### Finding Description
`AccountTransaction::validate_proof_facts` enforces that a proof-carrying Invoke V3 transaction's referenced block number is not "too recent": it must satisfy `proof_block_number <= current_block_number - STORED_BLOCK_HASH_BUFFER`, using `block_context.block_info.block_number` as `current_block_number`: [1](#0-0) [2](#0-1) 

The Starknet OS re-execution enforces the identical invariant in Cairo via `check_proof_facts`, using the block's `current_block_number` at execution time: [3](#0-2) 

However, the gateway's stateful transaction validator, which runs the same `validate` path (and therefore the same pre-validation / proof-facts check) for transactions submitted for admission, builds its `BlockContext` using the *next* block number rather than the block number that will ultimately be used when the transaction is actually included and executed by the batcher/OS: [4](#0-3) 

Because `validate_proof_block_number`'s bound (`current_block_number - STORED_BLOCK_HASH_BUFFER`) is computed from whichever "current" block number happens to be passed in by the caller, a transaction whose proof-fact block number sits exactly at the boundary can be accepted by the gateway (using `unchecked_next()`s block number) while later being evaluated against a different block number during actual batch execution/OS re-execution — or vice versa, rejected at the gateway while it would have been acceptable at inclusion time. This is directly analogous to the reported Ajna issue, where `_getScreeningStageEndBlock` computed a period boundary from the wrong base value than the one implied by the surrounding comments/spec, causing the enforced window to diverge from the intended window.

### Impact Explanation
If the gateway's admission check and the batcher/OS's execution-time check of the same "recency" invariant disagree at the boundary, this can produce validator/proposer divergence: a proposer's gateway may admit and include a transaction into a proposed block that a validating node's execution — using a different `current_block_number` reference — deems invalid (`InvalidProofFacts`), or a transaction rejected by one node's gateway could still be constructed and force execution divergence between nodes re-validating the same block. Either outcome undermines the safety property that all honest nodes agree on transaction validity for a given block, which can cause block rejection/consensus stalls (a network unable to confirm new transactions) in the affected edge case.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an unprivileged transaction sender to craft an Invoke V3 transaction with `proof_facts` whose `block_number` sits exactly at the `STORED_BLOCK_HASH_BUFFER` boundary relative to the block number computed by `unchecked_next()` at gateway-validation time versus the actual block number at inclusion/OS-verification time. This is a narrow, single-block window, but it is fully reachable by any external caller who can submit a transaction with proof facts, without needing any privileged role.

### Recommendation
Ensure the "current block number" used for the proof-facts recency bound in `validate_proof_facts`/`validate_proof_block_number` is consistently derived the same way in every call path that can execute this check — i.e., either always use the block number of the block the transaction will actually be included in, or make the gateway's stateful pre-check intentionally more permissive around the boundary (rather than using `unchecked_next()`) so it can never diverge from the authoritative check performed by the batcher/OS at execution time. Add a unit/integration test that submits a proof-facts transaction at the exact boundary via the gateway and asserts it is accepted/rejected consistently with actual block inclusion.

### Proof of Concept
1. Compute `N = current chain height`.
2. Craft an Invoke V3 transaction whose `proof_facts.block_number = N - STORED_BLOCK_HASH_BUFFER + 1` (i.e., the first value considered "too recent" relative to height `N`, per `validate_proof_block_number` at `crates/blockifier/src/transaction/account_transaction.rs:238-260`).
3. Submit the transaction to the gateway when the chain's stored/fixed block info is still `N-1` (so the gateway's `run_validate_entry_point` computes `block_info.block_number.unchecked_next() = N`, per `crates/apollo_gateway/src/stateful_transaction_validator.rs:323-324`) — under this reference the tx is exactly at the rejection boundary and the gateway's stateful validation of the transaction's `__validate__` path proceeds as if `current_block_number = N`.
4. By the time the batcher actually builds/executes the block including this transaction, the true `block_context.block_info.block_number` used in `validate_proof_facts` (`crates/blockifier/src/transaction/account_transaction.rs:331-337`) may differ from the gateway's assumed `N`, producing a different pass/fail outcome for the identical proof-facts recency check between admission time and execution/re-execution time.

Note: I was not able to fully trace, within the available tool budget, the exact call site(s) that determine which block number is passed into `validate_proof_facts` during actual batcher block-building/proposal (only the gateway's stateful validator path and the Cairo OS check were confirmed as consistent with each other). This means the concrete divergence described above is a plausible analog based on the pattern found (a `current_block_number` reference computed differently in a validation-only code path vs. the execution path) rather than a fully confirmed end-to-end trace. A background Devin session with full read access to `crates/blockifier/src/blockifier/stateful_validator.rs` and the batcher's block-building call chain would be needed to conclusively confirm whether the two block-number references can actually diverge in practice.

    fn validate_proof_block_number(
        proof_block_number: u64,
        current_block_number: BlockNumber,
    ) -> TransactionPreValidationResult<()> {
        // Proof block must be old enough to have a stored block hash.
        // Stored block hashes are guaranteed only up to: current - STORED_BLOCK_HASH_BUFFER.
        let max_allowed =
            current_block_number.0.checked_sub(STORED_BLOCK_HASH_BUFFER).ok_or_else(|| {
                TransactionPreValidationError::InvalidProofFacts(format!(
                    "The current block number {current_block_number} is below the required \
                     block-hash retention buffer: {STORED_BLOCK_HASH_BUFFER}."
                ))
            })?;

        if proof_block_number > max_allowed {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "The proof block number {proof_block_number} is too recent. The maximum allowed \
                 block number is {max_allowed}."
            )));
        }

        Ok(())
    }
