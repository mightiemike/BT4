This is the critical finding: the VM's `process_dkg_result_inner` (the actual state-committing entry point, invoked as a validator transaction that writes the DKG transcript into on-chain state) calls **only** `DefaultDKG::verify_transcript`, not `verify_transcript_extra`. [1](#0-0) 

- `real_dkg::verify_transcript` only range-checks dealer ids (`dealers.iter().all(|id| *id < num_validators)`); it never checks for duplicate `Player` ids. [2](#0-1) 
- The duplicate-dealer detection (`ensure!(main_trx_dealers.len() == dealer_set.len())`) exists only in `verify_transcript_extra`, which is a *separate* function used by the off-chain peer-to-peer transcript-aggregation broadcast logic (`dkg/src/transcript_aggregation/mod.rs`), not by the VM commit path. [3](#0-2) [4](#0-3) 
- `aggregate_with` (the function in question) itself performs no deduplication of `soks`/`Player` ids: `for sok in &other.soks { self.soks.push(sok.clone()); }`. [5](#0-4) 
- `get_dealers()` simply maps `soks` to `Player`s with no dedup, so a duplicated `Player` id will appear twice. [6](#0-5) 

Because the off-chain `contributors: HashSet<AccountAddress>` bookkeeping (`dkg/src/transcript_aggregation/mod.rs` line 101 check before calling `aggregate_transcripts`) is purely local, honest-node convenience logic — not part of the state-committing consensus/VM check — a byzantine block proposer/validator submitting the final validator transaction can hand-craft a `DKGTranscript` whose `transcript_bytes` decode to an "aggregated" `Transcript` containing a duplicated dealer `Player` in `soks` (e.g., by directly assembling it rather than going through `TranscriptAggregationState::add`, or by patching a legitimately produced aggregate). Since `process_dkg_result_inner` only calls `verify_transcript` (no dedup, no `verify_transcript_extra`), this transcript would pass VM validation and be written into on-chain DKG state via `FINISH_WITH_DKG_RESULT`.

However, whether this actually breaks the security invariant of the underlying cryptographic scheme requires more care: `batch_verify_soks` inside `Transcript::verify` (called from `real_dkg::verify_transcript`) validates each SoK/BLS signature independently per entry in `soks`, and a duplicate valid signature from the same dealer is still a valid signature — it does not, by itself, fail the pairing checks in `verify`, because those checks bind `V`/`V_hat`/`R`/`C` (the actual share commitments) rather than `soks` count. The double-counted `Player` in `get_dealers()` would then propagate into `verify_transcript_extra`'s dealer-set/voting-power accounting used elsewhere (e.g., quorum checks in `dkg/src/transcript_aggregation/mod.rs` and randomness config consumers), and into any downstream logic in the `randomness_dkg`/DKG session code that assumes each dealer contributes exactly once toward the threshold weight — this could allow a single validator's weight to be double-counted toward the threshold in the final committed transcript, without a second distinct dealer actually contributing shares, and it corrupts `DKGState`, which is committed on-chain resource state.

I was not able to fully trace, within the given index limits, whether some other invariant elsewhere (e.g., in `real_dkg`'s decryption/reconstruction code, or in the aggregation of `V`/`R`/`C` polynomial commitments, which are summed independent of `soks`) actually depends on `soks.len()`/`get_dealers()` matching a unique dealer count in a way that would make the double count exploitable for threshold-weight bypass versus just corrupting metadata/logging. The `V`, `V_hat`, `R`, `R_hat`, `C` fields are aggregated by direct field-wise addition over fixed index ranges tied to `sc` (SecretSharingConfig) regardless of `soks`, so the actual polynomial-share cryptographic material is unaffected by `soks` duplication; the impact is confined to `get_dealers()`-based dealer/weight bookkeeping (used in `verify_transcript_extra`'s voting-power check and any consumer of `get_dealers()`), not to corrupting the dealt secret itself.

### Title
Missing dealer-deduplication in PVSS transcript aggregation allows double-counted dealer weight in committed DKG state - (File: crates/aptos-dkg/src/pvss/das/weighted_protocol.rs)

### Summary
`aggregate_with` in `weighted_protocol.rs` blindly appends `other.soks` into `self.soks` without checking for duplicate `Player` entries. `get_dealers()` derives dealer identity purely from `soks`, so a maliciously crafted or improperly aggregated transcript can list the same dealer twice. The on-chain VM commit path `process_dkg_result_inner` (`aptos-move/aptos-vm/src/validator_txns/dkg.rs`) only calls `verify_transcript` (which has no duplicate check), not `verify_transcript_extra` (which does), so a duplicated-dealer transcript can be accepted into committed `DKGState`.

### Finding Description
`Aggregated<Transcript>::aggregate_with` (lines 400-426) pushes every SoK from `other` into `self.soks` with no set/dedup logic. `get_dealers()` (lines 248-253) maps `self.soks` 1:1 to `Player` ids, so a duplicate `Player` in `soks` surfaces as a duplicate dealer in `get_dealers()`. This function is consumed by `verify_transcript_extra` (`types/src/dkg/real_dkg/mod.rs` lines 274-304), which detects duplicates via a `HashSet`, but the VM's actual state-committing entry point `process_dkg_result_inner` only invokes `verify_transcript` (line 115 of `aptos-move/aptos-vm/src/validator_txns/dkg.rs`), which has no such check (lines 307-322 of `real_dkg/mod.rs`).

### Impact Explanation
A double-counted dealer's `Player` in `get_dealers()` corrupts dealer/weight bookkeeping derived from the committed transcript — used by `verify_transcript_extra`'s voting-power accounting and any other consumer relying on `get_dealers()` returning a unique dealer set. This is a state-integrity concern because `DKGState`/the aggregated transcript is committed via `FINISH_WITH_DKG_RESULT`. The core secret-sharing arithmetic (`V`, `V_hat`, `R`, `R_hat`, `C`) is unaffected since it is aggregated independently of `soks`, so the dealt secret itself is not corrupted, limiting severity to metadata/weight-accounting corruption rather than secret compromise.

### Likelihood Explanation
Requires a byzantine block proposer/validator to submit a hand-crafted `DKGTranscript` bypassing the honest off-chain `TranscriptAggregationState` contributor-dedup logic, i.e., outside the excluded "malicious peer" scope in normal p2p flow, but the actual exploit path here is at the validator-transaction/VM-commit boundary, which fits the required scope (unprivileged/validator-transaction input to VM commit). It requires the attacker to control transcript construction directly (not just relay), which is plausible for a validator producing its own validator transaction with crafted `transcript_bytes`.

### Recommendation
Add duplicate-dealer detection to `aggregate_with` (reject or dedupe by `Player`), and/or call `verify_transcript_extra`'s dealer-uniqueness check (or an equivalent) inside `verify_transcript`/`process_dkg_result_inner` before committing the transcript on-chain.

### Proof of Concept
1. Deal two transcripts for the same `Player` (or reuse one dealer's `sok` twice) and call `aggregate_with` to merge them into an accumulator whose `self.soks` already contains that `Player`.
2. Observe `get_dealers()` returns a `Vec<Player>` with a duplicate entry.
3. Feed the resulting serialized transcript through `process_dkg_result_inner`; `DefaultDKG::verify_transcript` succeeds because it does not check `get_dealers()` for duplicates, while `verify_transcript_extra`'s `ensure!(main_trx_dealers.len() == dealer_set.len())` would have caught it had it been invoked on this path.

    fn verify_transcript_extra(
        trx: &Self::Transcript,
        verifier: &ValidatorVerifier,
        checks_voting_power: bool,
        ensures_single_dealer: Option<AccountAddress>,
    ) -> anyhow::Result<()> {

        let main_trx_dealers = trx.main.get_dealers();
        let mut dealer_set = HashSet::with_capacity(main_trx_dealers.len());
        for dealer in main_trx_dealers.iter() {

                dealer_set.insert(*dealer_addr);

            verifier
                .check_voting_power(dealer_set.iter(), true)

        }

        Ok(())
    }
