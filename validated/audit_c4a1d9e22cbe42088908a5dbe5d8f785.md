## Analysis Result [1](#0-0) 

The analog of the Fei `Roots` library bug exists in `Keeper.CalculateGasCost` in `x/uexecutor/keeper/fees.go`. Like `twoThirdsRoot`/`threeHalfsRoot`, which truncate *before* the scaling multiplication (causing large downward bias), this function divides the base fee by the 18-decimal scaling factor **before** multiplying by `gasUsed`, instead of multiplying first and truncating last.

### Title
Truncate-before-multiply order of operations in `CalculateGasCost` systematically underburns gas fees for universal execution - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` unwraps the `LegacyDec` base fee to a whole-upc integer via `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` (line 60) *before* multiplying by `gasUsed` (line 81). This is the truncate-then-scale anti-pattern flagged in the Fei report: any fractional-upc component of the base fee is discarded up front, and the discarded error is not scaled by `gasUsed` — it is simply lost — instead of being multiplied first so that only the final result is truncated to whole upc.

### Finding Description [2](#0-1) 
The function's own comment claims: "the base fee is always a whole number of upc -- no fractional upc exists," but this is an assumption about an EIP-1559-style dynamically-adjusted `feemarketKeeper.GetBaseFee` value (a `LegacyDec` with 18-decimal precision) that is not enforced anywhere in the scoped code — dynamic base-fee adjustment per block (increase/decrease based on gas-target utilization) naturally produces fractional-upc values over time, just as the Fei report's `cubeRoot`/`sqrt` truncation assumption did not hold across the full input range. [3](#0-2) 
Because the division by `1e18` happens first, any fractional-upc remainder of the base fee (e.g. `1.9` upc truncated to `1`) is dropped from `effectiveGasPrice` entirely, before it is ever multiplied by `gasUsed`. Multiplying first (`baseFee.BigInt() * gasUsed`, then dividing the product by `1e18`) would preserve nearly all of that value and only lose sub-upc dust in the final result — exactly the fix pattern the Fei report recommends ("truncating steps are performed last").

### Impact Explanation
`DeductGasFeesFromReceipt` → `CalculateGasCost` is invoked on every ordinary universal payload execution to burn the gas fee owed by the recipient account (`DeductAndBurnFees`, `x/uexecutor/keeper/fees.go:21-37`). Any unprivileged user submitting a universal payload triggers this path. When the network's dynamic base fee carries a fractional-upc component (the normal, expected state of an EIP-1559 fee market that isn't pinned to whole-upc increments), the protocol systematically under-burns the fee owed — proportionally to the discarded fraction, amplified by `gasUsed`. If the base fee is below `1` upc (`< 1e18` in the internal representation), `effectiveGasPrice` truncates to `0`, and the gas fee charged is `0` regardless of `gasUsed`, i.e. a full accounting corruption of "gas fee accounting" as called out in the allowed impact list.

### Likelihood Explanation
This requires no privileged action — it is triggered purely by the ordinary, default flow of any user calling universal execution when the feemarket's base fee is not an exact whole-upc value, which is the expected steady state of any live EIP-1559-style adjustment mechanism rather than a rare edge case.

### Recommendation
Reorder the arithmetic to multiply before truncating: compute `gasCost = baseFee.BigInt() * gasUsed`, then divide the final product by `1e18` once, mirroring the Fei fix of combining operations and truncating only at the last step to minimize/eliminate the rounding bias.

### Proof of Concept
Given `baseFee = 1.9` upc (`baseFee.BigInt() = 1_900_000_000_000_000_000`) and `gasUsed = 1_000_000`:
- Current code: `baseFeeBig.Div(1.9e18, 1e18) = 1`, then `gasCost = 1 * 1_000_000 = 1_000_000` upc burned.
- Correct order: `gasCost = (1_900_000_000_000_000_000 * 1_000_000) / 1e18 = 1_900_000` upc burned.
The protocol under-burns by `900_000` upc (~47%) on this single execution, and this discrepancy scales linearly with `gasUsed` for every ordinary universal-payload transaction executed while the base fee holds a fractional-upc value.

func (k Keeper) CalculateGasCost(
	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,

	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18

	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.

	}

	// @dev: Currently, since we are not using maxPriorityFeePerGas, effectiveGasPrice is just baseFee
