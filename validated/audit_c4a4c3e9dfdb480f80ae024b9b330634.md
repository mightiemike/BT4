### Title
`AccountStore.delete()` never calls `accountStateCallBackUtils.deleteAccount(key)`, leaving destroyed accounts in the account-state trie - ([File: chainbase/src/main/java/org/tron/core/store/AccountStore.java])

### Summary
`AccountStore.put()` unconditionally forwards every write to `accountStateCallBackUtils.accountCallBack(key, item)` [1](#0-0) , but the overridden `AccountStore.delete()` only performs balance-trace bookkeeping and calls `super.delete(key)` — it never calls the equivalent `accountStateCallBackUtils.deleteAccount(key)` [2](#0-1) . This asymmetry is real and confirmed in the code: `AccountStateCallBack.deleteAccount(byte[] key)` exists specifically to remove a leaf from the account-state trie (`trie.delete(...)`) but it is simply never invoked by the store layer [3](#0-2) .

### Finding Description
`accountCallBack`/`deleteAccount` are only active when the account-state-root feature is turned on (`allowAccountStateRoot`, gated by the `ALLOW_ACCOUNT_STATE_ROOT` proposal) and `preExecute` has set `execute = true` for the current block [4](#0-3) . When active, every `AccountStore.put()` call queues a `TrieEntry` that is later merged into the block's account-state trie in `exeTransFinish()` [5](#0-4) , and the resulting `trie.getRootHash()` is compared against the block header's `accountStateRoot` in `executePushFinish()`, throwing `BadBlockException` on mismatch [6](#0-5) . Because `AccountStore.delete()` skips the `deleteAccount` call entirely, any account removed from the underlying store (e.g. via contract self-destruct, which routes through `RepositoryImpl`'s delete path) is never removed from the account-state trie — the stale leaf persists in the trie forever.

However, since every full node executes the identical `AccountStore`/`AccountStateCallBack` code deterministically, this bug is reproduced identically on all nodes computing the trie: the "wrong" root (with stale leaves for deleted accounts) is the *same* wrong root everyone computes, given the same block execution. There is no source of non-determinism between honest nodes here — `BadBlockException` compares each node's independently recomputed root against the value baked into the block header by the producer, and all validators run the exact same (buggy) logic, so they converge to the same value and the check passes consistently. The bug does not, by itself, create a fork or inconsistent `BadBlockException` behavior across nodes; it is a state-model correctness bug in the optional account-state-root trie, not a consensus-divergence bug.

Additionally, the question's proposed trigger ("zero-balance account pruning during a transfer that empties an account") does not correspond to code in this repository: ordinary transfers that empty an account's balance do not call `AccountStore.delete()` — accounts remain in the store with balance `0`. The only reachable trigger for `AccountStore.delete()` found in this codebase is contract account destruction (`RepositoryImpl`'s delete path used for `SUICIDE`/self-destruct), which is unprivileged and attacker-reachable via a deployed smart contract.

### Impact Explanation
If the `ALLOW_ACCOUNT_STATE_ROOT` feature is activated, self-destructing a contract (or otherwise causing `AccountStore.delete()` to fire) leaves a stale leaf for that address in the account-state trie forever. This corrupts the semantic guarantee of the account-state-root feature (used for external Merkle proofs of account state) — proofs against `accountStateRoot` could show a destroyed account as still "existing." This does not cause consensus divergence/halt between honest nodes because the bug is deterministic and identical across all nodes, so it does not satisfy the "invalid state/divergence/halt" bar in the sense of breaking node agreement; the impact is confined to the correctness of the optional account-state trie used for external proof verification.

### Likelihood Explanation
The precondition (`ALLOW_ACCOUNT_STATE_ROOT` proposal activated) is a network-wide governance toggle, not something the unprivileged attacker controls, but once active the trigger (deploying and self-destructing a contract) is fully unprivileged and trivially repeatable. The specific "transfer emptying account" trigger described in the question does not exist in this codebase's transfer path, so that exact PoC would not reproduce the bug; the real reachable trigger is contract self-destruct.

### Recommendation
Add the missing callback in `AccountStore.delete(byte[] key)`, mirroring `put()`:
```java
super.delete(key);
accountStateCallBackUtils.deleteAccount(key);
```
so that trie deletions stay symmetric with trie insertions whenever the account-state-root feature is active.

### Proof of Concept
Integration test plan (JUnit, using existing `framework` test harness patterns as in `AccountStoreTest`):
1. Enable `allowAccountStateRoot` via `dynamicPropertiesStore.saveAllowAccountStateRoot(1)` in a test `Manager`/`ChainBaseManager` fixture.
2. Deploy a simple contract via `CreateSmartContract`, mine/apply the block, and assert that the deployer address's key is present as a leaf in `AccountStateCallBack`'s underlying trie (`AccountStateStoreTrie`) after `executeGenerateFinish()`.
3. Send a transaction that triggers `SUICIDE`/self-destruct on that contract account (through `Runtime`/`RepositoryImpl`, which calls `AccountStore.delete()` on commit), then mine/apply the following block.
4. After `executeGenerateFinish()`/`executePushFinish()` for the block containing the self-destruct, query the trie via `trie.get(Hash.encodeElement(contractAddress))` and assert it still returns non-empty data — demonstrating the stale leaf remains despite the account no longer existing in `AccountStore.get(contractAddress)` (which should return `null`).
5. Compare against an expected/reference trie built by manually calling `deleteAccount(contractAddress)` for the same execution, and show the root hashes differ, confirming the asymmetry's effect on trie content (not necessarily on cross-node consensus, since all nodes reproduce the same incorrect root deterministically).

    execute = false;

    byte[] newRoot = trie.getRootHash();
