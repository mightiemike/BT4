### Title
Unbounded decompression of user-supplied Cairo0 program in `decompress_program` allows memory-exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
`decompress_program` in `apollo_rpc` decodes a base64/gzip-compressed Cairo0 `program` field supplied by an RPC caller and decompresses it with no size limit, unlike every other decompression path in the sequencer (which use `decode_and_decompress_with_size_limit` with an explicit `max_size`). This mirrors the rdiffweb "Token name" bug class: an unbounded, attacker-controlled length field is decompressed/allocated without a cap, enabling denial of service via memory exhaustion (zip-bomb style amplification).

### Finding Description
Throughout the sequencer, every user-supplied compressed program/class field is decompressed under an explicit byte-size cap:
- `decode_and_decompress_with_size_limit` enforces `max_size` and returns `CompressionError::SizeLimitExceeded` if the decompressed payload is too large [1](#0-0) .
- The gateway/HTTP-server path enforces `max_sierra_program_size` at decompression time for declare transactions [2](#0-1) .
- The protobuf class-sync path caps Cairo0 program decompression at a hardcoded 4MB [3](#0-2) .

However, `decompress_program` in the JSON-RPC execution API decodes and gzip-decompresses a caller-supplied program string with **no size limit at all**, and the code explicitly flags this as an outstanding TODO:
```
// TODO(dan): add time and size limits.
let mut decoder = GzDecoder::new(compressed_data.as_slice());
let mut decompressed = Vec::new();
decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
``` [4](#0-3) 

This function is reached from `TryFrom<BroadcastedDeclareTransaction>` when converting an RPC-submitted `BroadcastedDeclareV1Transaction` (Cairo0 declare) into an `ExecutableTransactionInput` used for execution simulation (e.g., fee estimation / call simulation endpoints), via `user_deprecated_contract_class_to_sn_api` [5](#0-4) . A caller only needs to submit a `program` string that is a small, highly-compressed gzip blob (a "zip bomb") to force the node to allocate an arbitrarily large `Vec<u8>` in `decoder.read_to_end`, unconstrained by any of the calldata/signature/contract-size validators that protect the gateway's stateless transaction validation path (`StatelessTransactionValidator::validate_class_length`, `max_contract_bytecode_size`, `max_contract_class_object_size`) [6](#0-5) , because those checks apply only to Sierra (V3) declare transactions submitted through the gateway, not to the deprecated Cairo0 V1 declare path handled by this RPC execution-simulation code.

### Impact Explanation
An unprivileged RPC caller can submit a crafted, tiny compressed payload that decompresses to a very large buffer, causing unbounded memory allocation on the node process handling the RPC call. Repeated or concurrent requests can exhaust node memory, causing the node (or its RPC/execution service) to crash or become unresponsive — a denial of service consistent with CWE-770 and the referenced advisory's impact (memory corruption/DoS via unbounded token length). This affects node availability, not directly consensus state, so it is scoped as a High-severity resource/availability DoS analogous to the reference report.

### Likelihood Explanation
Likelihood is high for any deployment exposing this JSON-RPC execution API (fee estimation / simulate call for V1 declare) to untrusted callers, since the exploit requires only a single crafted request with a valid base64+gzip encoded `program` field — no special privileges, staking, or node control needed. The explicit `// TODO(dan): add time and size limits.` comment confirms the developers were aware limits were missing but had not yet added them.

### Recommendation
Replace the unbounded `GzDecoder::read_to_end` in `decompress_program` with the same bounded-decompression pattern used elsewhere in the codebase, e.g., call `decode_and_decompress_with_size_limit` (or wrap the `GzDecoder` with `.take(max_size)` as done in `decompress_with_size_limit`) using a configurable maximum decompressed program size, and reject/­error the request when the limit is exceeded, mirroring `CompressionError::SizeLimitExceeded` handling used by the gateway and protobuf conversion paths.

### Proof of Concept
1. Construct a Cairo0 `program` string that is valid base64 of a gzip stream compressing many gigabytes of repeated bytes (a "gzip bomb"), which compresses down to a tiny payload (kilobytes).
2. Submit a JSON-RPC call that triggers `BroadcastedDeclareV1Transaction` → `TryFrom<BroadcastedDeclareTransaction>` → `user_deprecated_contract_class_to_sn_api` → `decompress_program` (e.g., an `estimate_fee`/`simulate_transactions`/`call` style RPC endpoint accepting a V1 declare broadcast) with this `program` field.
3. Observe `decoder.read_to_end(&mut decompressed)` allocate an unbounded buffer proportional to the decompressed size, exhausting node memory and causing the RPC/execution service to crash or become unresponsive, with no size-limit error ever being returned (unlike the bounded paths that would raise `CompressionError::SizeLimitExceeded`).

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
