### Title
Exchange pool can be drained to near-zero liquidity via `ExchangeWithdrawContract`, bypassing the balance floor enforced at creation - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeCreateActuator` enforces a floor on pool liquidity at creation time (`firstTokenBalance <= 0 || secondTokenBalance <= 0` is rejected), but `ExchangeWithdrawActuator` only rejects a withdrawal if the pool balance is *already* exactly zero. There is no check that the *resulting* balances after a withdrawal remain above any meaningful floor, so the exchange creator can withdraw down to a balance of `1` for either token. This mirrors the AegisVault bug class: a minimum-liquidity invariant is checked once at "deposit" (create) time but is never re-validated on "withdraw", so it can be trivially bypassed.

### Finding Description
`ExchangeCreateActuator.doValidate()` requires `firstTokenBalance > 0 && secondTokenBalance > 0` at creation: [1](#0-0) 

`ExchangeWithdrawActuator.doValidate()` only guards against a pool that is *already* fully depleted (`firstTokenBalance == 0 || secondTokenBalance == 0`), not against a withdrawal that drives the remaining balance down to a trivially small, precision-unsafe value: [2](#0-1) 

The subsequent balance-adjustment math only checks that the requested withdrawal amount does not exceed the current balance (`exchange balance is not enough`), never that what remains satisfies any minimum liquidity requirement: [3](#0-2) 

As a result, only the exchange creator (withdraw is restricted to the creator: `account[...] is not creator`) is needed to reduce both token balances to `1` unit each, which is far below the `>0` floor implicitly intended to keep the Bancor-style pricing formula numerically stable. The pricing math in `ExchangeProcessor` divides supply-adjustments by the pool balance: [4](#0-3) 

Once the pool is driven to minimal balances, any subsequent unprivileged trader calling `ExchangeTransactionContract` against that pool interacts with an numerically-unstable/manipulable price curve, letting the creator (or a colluding party) extract disproportionate value from later traders — the same "first depositor"-style precision-griefing pattern described in the AegisVault report, just realized through TRON's Bancor-style `Exchange` rather than an ERC-4626 vault.

### Impact Explanation
This breaks the accounting invariant that an on-chain liquidity pool maintains a non-trivial minimum reserve, enabling a griefing/value-extraction primitive against any counterparty who trades against the pool after it has been drained to near-zero. While the operation is gated to the pool's creator (not a fully unprivileged third party), the victims of the resulting precision distortion are ordinary unprivileged users calling `ExchangeTransactionContract`, so the accounting/settlement impact reaches unprivileged actors, consistent with underpriced/mispriced public-work-style impact in the exchange settlement path.

### Likelihood Explanation
Likelihood is Low: it requires the pool creator (a role obtained simply by calling `ExchangeCreateContract`, so effectively any unprivileged account can occupy this role for a pool they create) to intentionally withdraw down to near-zero balances, then wait for other users to trade against the degraded pool. No collusion with privileged network roles is required.

### Recommendation
In `ExchangeWithdrawActuator.doValidate()` / `execute()`, after computing the post-withdrawal `firstTokenBalance`/`secondTokenBalance`, require that both remain either exactly `0` (pool fully closed) or above a defined minimum liquidity floor, mirroring the check already enforced in `ExchangeCreateActuator`:
```java
long newFirstTokenBalance = ...; // balance after withdraw
long newSecondTokenBalance = ...;
if ((newFirstTokenBalance != 0 && newFirstTokenBalance < MIN_TOKEN_BALANCE)
    || (newSecondTokenBalance != 0 && newSecondTokenBalance < MIN_TOKEN_BALANCE)) {
  throw new ContractValidateException("Exchange balance would fall below minimum liquidity");
}
```

### Proof of Concept
1. Creator calls `ExchangeCreateContract` with `firstTokenBalance = X`, `secondTokenBalance = Y` (passes the `>0` check in `ExchangeCreateActuator`).
2. Creator repeatedly calls `ExchangeWithdrawContract`, each time withdrawing amounts that keep both `firstTokenBalance` and `secondTokenBalance` strictly greater than `0` (e.g., leaving `1` unit of each) — `doValidate()` only rejects when a balance is already `== 0`, so these withdrawals succeed.
3. An unrelated unprivileged user calls `ExchangeTransactionContract` against this now near-empty pool; `ExchangeProcessor.exchange()` computes `buyTokenQuant` using ratios against the minimal balances, producing precision-distorted results that can be exploited by the creator/colluding party to extract value from the trader, analogous to the "first depositor" precision attack described in the report.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
