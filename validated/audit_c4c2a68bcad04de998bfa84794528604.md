### Title
`Storage.put()` stores `DataWord.getData()` by reference without a defensive copy, allowing storage-slot aliasing/mutation across opcodes - ([File: actuator/src/main/java/org/tron/core/vm/program/Storage.java])

### Summary
`Storage.put()` writes `value.getData()` directly into a `StorageRowCapsule` without cloning the backing `byte[]`, and `Storage.getValue()` similarly wraps `StorageRowCapsule.getValue()` in a `new DataWord(...)` without cloning. Because `DataWord(byte[] data)` skips copying for 32-byte inputs, a value loaded from storage (`SLOAD`) shares the exact same backing array as the cached `StorageRowCapsule.rowValue`. Standard EVM opcodes mutate `DataWord` contents in place, so a subsequent arithmetic/bitwise opcode on that loaded word silently corrupts the cached storage row's value without ever calling `setValue()`/marking it dirty for that mutation.

### Finding Description
`Storage.put()` stores the raw array reference: [1](#0-0) 

`Storage.getValue()` also returns a `DataWord` built directly from the cached row's array: [2](#0-1) 

`StorageRowCapsule.getValue()`/`setValue()` never clone the array either: [3](#0-2) 

`DataWord`'s constructor assigns the input array directly when it is already 32 bytes long, instead of cloning it: [4](#0-3) 

Many TVM opcodes mutate a popped `DataWord`'s internal array in place and push the *same* object back onto the stack, e.g. `ltAction`, `gtAction`, `andAction`, `isZeroAction`: [5](#0-4) [6](#0-5) 

Exploit chain reachable from ordinary contract bytecode (no privileged role needed):
1. `SSTORE key, v` -> `Storage.put` stores `v`'s backing array by reference in the (dirty) `StorageRowCapsule` for `key`.
2. `SLOAD key` -> `Storage.getValue` returns a new `DataWord` wrapping the *same* backing array (no clone), which is pushed to the stack.
3. A subsequent in-place-mutating opcode (`AND`, `ADD`, `ISZERO`, etc.) operating on that loaded word mutates the shared array directly.
4. Because the row was already marked `dirty=true` from step 1's real `SSTORE`, `commit()` will still persist the row — but it persists the *mutated* value, not the value that was actually passed to `SSTORE` at charge time: [7](#0-6) 

No existing check (energy accounting, `dirty` flag, actuator validation) prevents this because the mutation never goes through `setValue()`, so it's invisible to the dirty-tracking/gas-accounting model, yet still gets committed since the row was already dirty from the legitimate `SSTORE`.

### Impact Explanation
The final committed storage value can diverge from the value that was actually charged for and observed at `SSTORE` time, purely due to in-VM array aliasing. In token/accounting contracts this can silently corrupt balances or other accounting state without a corresponding `SSTORE` "event"/energy charge for the final value — an asset-accounting corruption / unauthorized state change, matching TRON's "asset/accounting corruption" bounty impact class.

### Likelihood Explanation
This is fully reachable by an unprivileged smart-contract deployer/caller using only standard opcodes (`SSTORE`, `SLOAD`, arithmetic/bitwise ops) — no special permissions, no fork gates, no signature bypass involved. The only cost is normal gas/energy for the opcodes used. It is deterministically repeatable given the same bytecode sequence.

### Recommendation
Defensively copy the byte array on every boundary crossing between the VM stack/memory and persistent storage:
- In `Storage.put()`, clone `value.getData()` before storing it in `StorageRowCapsule` / before calling `setValue()`.
- In `Storage.getValue()`, clone `row.getValue()` before wrapping it in a `DataWord`.
- Alternatively/additionally, make `DataWord(byte[] data)` always clone its input array rather than aliasing it when `data.length == WORD_SIZE`.

### Proof of Concept
```java
// Demonstrates lack of defensive copy in Storage.put()
byte[] arr = new byte[32];
arr[31] = 1;
DataWord key = new DataWord(new byte[32]);
DataWord value = new DataWord(arr); // no copy: value.getData() == arr

Storage storage = new Storage(address, store);
storage.put(key, value);

// External mutation of the original array via a "reused" opcode operation
arr[31] = 2;

byte[] stored = storage.getRowCache().get(key).getValue();
// FAILS defensive-copy expectation: stored value changes even though
// put()/setValue() was never called again.
assertArrayEquals(new byte[]{ /*...*/ 2 }, new byte[]{stored[31]});
```
This confirms `StorageRowCapsule.getValue()` aliases the caller's array; combined with in-place-mutating opcodes (`andAction`, `isZeroAction`, etc. in `OperationActions.java`) operating on a `DataWord` obtained via `Storage.getValue()`, the same aliasing lets bytecode corrupt an already-dirty, about-to-be-committed row's value without another `SSTORE`.

  public DataWord(byte[] data) {
    if (data == null) {
      this.data = ByteUtil.EMPTY_BYTE_ARRAY;
    } else if (data.length == WORD_SIZE) {
      this.data = data;
    } else if (data.length < WORD_SIZE) {
      System.arraycopy(data, 0, this.data, WORD_SIZE - data.length, data.length);
    } else {
      throw new RuntimeException("Data word can't exceed 32 bytes: " + ByteArray.toHexString(data));
    }
  }
