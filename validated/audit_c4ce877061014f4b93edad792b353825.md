### Title
Vote-only-bank admission check (`is_simple_vote_transaction`) is looser than replay-time consensus check (`is_valid_vote_only_transaction`), allowing a "vote-program-shaped but semantically invalid" transaction to pass leader admission and dead-fork the block at replay - (File: `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`, `ledger/src/blockstore_processor.rs`, `vote/src/vote_parser.rs`)

### Summary
`translate_to_runtime_view` gates non-vote transactions out of a `vote_only_bank()` using `RuntimeTransaction::is_simple_vote_transaction()`, which only checks transaction *shape* (legacy message, ≤2 signatures, single instruction, program id == vote program) and never inspects whether the instruction data actually decodes to a valid vote state update. Replay-side validation of vote-only banks in `ledger/src/blockstore_processor.rs` uses the stricter `is_valid_vote_only_transaction` (in `vote/src/vote_parser.rs`), which additionally requires the instruction to deserialize as a `VoteInstruction` and be `is_single_vote_state_update()`. A transaction that targets the vote program with garbage/invalid instruction data satisfies the loose admission check but fails the strict replay check.

### Finding Description
`translate_to_runtime_view` (banking-stage ingestion path) enforces: [1](#0-0) 
where `is_simple_vote_transaction()` is computed from `is_simple_vote_transaction_view`-equivalent shape checks: legacy message, ≤2 signatures, exactly one instruction, and `program_id == solana_sdk_ids::vote::id()` — with no inspection of instruction data content. [2](#0-1) [3](#0-2) 

By contrast, the authoritative, consensus-critical replay-time check used when processing entries belonging to a `vote_only_bank` slot is `is_valid_vote_only_transaction`, which additionally requires the instruction data to deserialize into a `VoteInstruction` and satisfy `is_single_vote_state_update()`: [4](#0-3) 

`blockstore_processor.rs` applies this strict check to every transaction in every entry of a slot where `bank.vote_only_bank()` is true, and any transaction that fails it causes the entire block to be rejected with `BlockstoreProcessorError::UserTransactionsInVoteOnlyBank`: [5](#0-4) 

**Attack flow**: An unprivileged, funded attacker crafts a legacy, single-signature, single-instruction transaction whose sole instruction targets the vote program id but carries instruction data that does not deserialize as a valid `VoteInstruction` (or deserializes but is not a single vote-state-update, e.g. `InitializeAccount`, `Authorize`, `WithdrawTail`, or malformed bytes). During a vote-only-bank window (leader/cluster restart), this transaction passes `translate_to_runtime_view`'s loose `is_simple_vote_transaction()` gate and is admitted into the leader's scheduling/consuming pipeline as if it were a real vote. When the resulting block is later replayed (by peers, or the same validator via ledger replay), `blockstore_processor.rs`'s `is_valid_vote_only_transaction` check rejects the transaction, causing the whole entry/block to error out with `UserTransactionsInVoteOnlyBank` — i.e., the leader's produced block becomes unreplayable/dead. The check exists specifically because these two code paths (admission-time shape check vs. replay-time semantic check) are not identical.

### Impact Explanation
This is a liveness-impacting mismatch: at exactly the moment vote-only-bank mode exists to protect cluster restart/liveness recovery, an unprivileged attacker can cause any leader that naively schedules such a transaction to produce a dead block, wasting a slot precisely during the liveness-critical recovery window. This does not cause direct fund loss or consensus divergence (all correct validators reject the block identically, satisfying determinism), but it degrades liveness during the most fragile period of cluster operation, and it is a genuine discrepancy between admission-time and replay-time vote classification that the SIMD-0387 style vote-only-bank invariant is supposed to prevent.

### Likelihood Explanation
Preconditions: bank must be in `vote_only_bank()` mode (restart/liveness-recovery scenario — attacker cannot trigger this state itself, it must already be active). Given that precondition, cost to the attacker is minimal — a single signed transaction with a normal transfer-sized fee targeting the real vote program id with malformed instruction data. It is trivially repeatable by any funded keypair with no special privileges. The main mitigating factor is that this requires the vote-only-bank window to already be active (not attacker-controlled), limiting exploitation to specific restart periods, and it requires that whichever component schedules transactions into blocks during vote-only-bank (banking stage) actually attempts to include such a transaction rather than filtering it via some additional layer not identified in the search (e.g. `consumer.rs`/`decision_maker.rs` vote-only handling) — this additional filtering layer could not be fully confirmed within the available tool budget.

### Recommendation
Make `is_simple_vote_transaction()` (used for admission gating in `translate_to_runtime_view` and related banking-stage paths) consistent with `is_valid_vote_only_transaction` by also validating that the vote-program instruction data deserializes to a `VoteInstruction` that is `is_single_vote_state_update()`, or alternatively relax/align the replay-time check so that admission-time classification and replay-time classification are provably identical for all transaction shapes.

### Proof of Concept
Unit test plan (in `runtime-transaction`/`core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs` test modules):
1. Construct a legacy, single-instruction, single-signature transaction whose instruction targets `solana_sdk_ids::vote::id()` with instruction data that is garbage bytes (fails `limited_deserialize::<VoteInstruction>`).
2. Assert `RuntimeTransaction::is_simple_vote_transaction()` returns `true` for this transaction (admission-time classification succeeds).
3. Assert `solana_vote::vote_parser::is_valid_vote_only_transaction()` returns `false` for the same transaction (replay-time classification fails).
4. Integration test: put a bank into `vote_only_bank()` mode, call `translate_to_runtime_view` with this transaction and assert it is accepted (not `PacketHandlingError::Sanitization`), then feed the resulting entry through `blockstore_processor`'s vote-only-bank replay path and assert `BlockstoreProcessorError::UserTransactionsInVoteOnlyBank` is returned — demonstrating the admission/replay classification gap.

```rust
fn is_simple_vote_transaction_view<D: TransactionData>(view: &SanitizedTransactionView<D>) -> bool {
    // vote could have 1 or 2 sigs; zero sig has already been excluded by sanitization.
    if view.num_signatures() > 2 {
        return false;
    }

    // simple vote should only be legacy message
    if !matches!(view.version(), TransactionVersion::Legacy) {
        return false;
    }

    // skip if has more than 1 instruction
    if view.num_instructions() != 1 {
        return false;
    }

    let mut instructions = view.instructions_iter();
    let Some(instruction) = instructions.next() else {
        return false;
    };
    if instructions.next().is_some() {
        return false;
    }

    let program_id_index = usize::from(instruction.program_id_index);
    let Some(program_id) = view.static_account_keys().get(program_id_index) else {
        return false;
    };

    *program_id == solana_sdk_ids::vote::id()
}
```

```rust
/// Check if a transaction is a valid vote-only transaction.
/// A valid vote-only transaction must:
/// 1. Have exactly one instruction
/// 2. That instruction must be to the vote program
/// 3. That instruction must be a single vote state update (UpdateVoteState, TowerSync, etc.)
pub fn is_valid_vote_only_transaction(tx: &impl SVMStaticMessage) -> bool {
    let mut instructions = tx.program_instructions_iter();

    let Some((program_id, instruction)) = instructions.next() else {
        return false;
    };

    if instructions.next().is_some() {
        return false;
    }

    if !solana_sdk_ids::vote::check_id(program_id) {
        return false;
    }

    limited_deserialize::<VoteInstruction>(instruction.data, solana_packet::PACKET_DATA_SIZE as u64)
        .map(|ix| ix.is_single_vote_state_update())
        .unwrap_or(false)
}
```
