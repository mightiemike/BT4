This is a real vulnerability: `Show` never scopes the run lookup to the `:ID` job path parameter, and Chainlink's user roles (`UserRoleView`, `UserRoleRun`, `UserRoleEdit`, `UserRoleAdmin`) are node-wide, not per-job — but that's precisely the point: `RequiresRunRole` only checks the user has at least "run" privilege *anywhere* on the node, not that they are entitled to the specific job in the URL. Since jobs have no per-job ACL in this codebase (any authenticated run/edit/admin user is expected to only see jobs presented via the `:ID`-scoped routes), the `:ID` path parameter is the only scoping mechanism for job-level data exposure, and `Show` silently discards it.

### Title
Pipeline Run `Show` endpoint discloses run data across jobs due to missing job-ID ownership check - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` (`GET /jobs/:ID/runs/:runID`) parses only `runID` from the path and calls `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)`, never validating that the returned run's owning job matches the `:ID` path parameter. Any authenticated user with at least `run` role can enumerate `runID` values through any job's URL and read pipeline run outputs/inputs belonging to unrelated jobs.

### Finding Description
`Show` is registered behind `auth.RequiresRunRole`, which only checks the caller's role is not `UserRoleView` [1](#0-0) , and is otherwise agnostic to which job the request targets. The handler itself:
```go
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	...
	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	...
}
``` [2](#0-1) 

`c.Param("ID")` (the job ID from the route) is read nowhere in `Show`, unlike its sibling `Index`, which correctly threads the job ID into `prc.App.JobORM().PipelineRuns(ctx, &jobSpec.ID, offset, size)` to scope results to the requested job [3](#0-2) . The underlying `pipeline.ORM.FindRun` implementation performs an unconditional lookup by run ID alone with no job filter: `SELECT * from pipeline_runs WHERE id = $1 LIMIT 1` [4](#0-3) . Consequently, requesting `/jobs/<jobA>/runs/<runID-of-jobB>` returns job B's run data even though the caller only presented job A's ID in the path, and the response includes `presenters.NewPipelineRunResource`, which serializes run inputs/outputs/task results (potential bridge responses, prices, or other sensitive pipeline data).

### Impact Explanation
An attacker holding valid run-role (or lower-tier, non-admin) API credentials/session can enumerate integer `runID` values across arbitrary job path prefixes and read execution data — inputs, outputs, task run results — for jobs they were not intended to access via that route. This matches Chainlink's "unauthorized information disclosure" bounty impact class: leakage of job pipeline data/secrets that should be scoped by job. It does not grant write/execution capability, so impact is limited to read-only data disclosure, not fund loss or transaction tampering.

### Likelihood Explanation
Requires only a valid authenticated session/API token with `run` role or higher — no special privilege escalation needed, and `runID` is a simple sequential integer that's trivially enumerable. This is fully reachable via ordinary REST API calls with no rate limiting or ownership checks blocking it, making it highly feasible and repeatable in any Chainlink Node deployment that hosts multiple jobs of differing sensitivity for different operator roles.

### Recommendation
In `Show`, parse the `:ID` job ID param the same way `Index` does, and verify the fetched `pipelineRun.PipelineSpec`'s associated job ID equals it (or introduce a combined `FindRunByJobAndID`/join-based query) before returning the resource; return 404 on mismatch.

### Proof of Concept
Integration test plan:
1. Create Job A and Job B (e.g., via `job.ORM.CreateJob`), each producing a pipeline run (`mustInsertPipelineRun`/`mustInsertAsyncRun` associated to distinct `job_pipeline_specs`).
2. Authenticate as a run-role user.
3. Issue `GET /v2/jobs/<JobA.ID>/runs/<JobB_run.ID>`.
4. Assert current behavior returns HTTP 200 with Job B's run data (vulnerability) — expected fix should return 404/403 since Job B's run does not belong to Job A.
