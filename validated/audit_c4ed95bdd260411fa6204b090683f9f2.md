Based on my research, I found a strong Chromium analog to the Grafana redirect-based allowlist bypass.

### Title
Connection-Allowlist `redirects=block` directive is not enforced for PaymentRequestEvent.openWindow() navigations, allowing an allowlisted-but-malicious payment handler to redirect to an out-of-allowlist origin - (File: chrome/browser/payments/payment_request_connection_allowlist_browsertest.cc)

### Summary
Chromium's network Connection-Allowlist feature lets a page (or, for Payment Handler service workers, the service worker script) restrict which origins/URLs the browser is permitted to contact, including an explicit `redirects=block` directive meant to stop a request that initially matches the allowlist from silently following an HTTP redirect to a non-allowlisted origin. This mirrors Grafana's "Request security allow list": a security boundary meant to prevent an allowed endpoint from redirecting traffic to a forbidden host. Test code demonstrates that this `redirects=block` enforcement is bypassed entirely for one specific code path: `PaymentRequestEvent.openWindow()`, invoked from `ServiceWorkerVersion::OpenPaymentHandlerWindow`.

### Finding Description
The connection allowlist mechanism is validated end-to-end for HEAD/GET manifest downloads performed by `PaymentManifestDownloader`, where `redirects=block` correctly fails the request with `net::ERR_UNSAFE_REDIRECT` once a redirect to a non-matching origin occurs [1](#0-0) .

However, for the `PaymentRequestEvent.openWindow()` API — which opens a top-level browsing context from within a Payment Handler service worker — the connection allowlist is checked only against the initial request URL, and the `redirects=block` directive attached to the service worker's `Connection-Allowlist` header has "no effect," per the test's own comment and title (`NoEffectOnOpenWindowRedirect`) [2](#0-1) . The test explicitly registers a service worker with `Connection-Allowlist: (response-origin "*://b.com:*/*/redirect.html"); redirects=block`, has `redirect.html` 302-redirect to a different resource on the same host, and asserts that `openWindow()` still succeeds and the redirected request is completed [3](#0-2) .

Contrast this with the blocked case: when the *initial* URL itself is outside the allowlist, `ServiceWorkerVersion::OpenPaymentHandlerWindow` correctly rejects the request before it reaches the URL loader with the message "is blocked by Connection Allowlist." [4](#0-3) . This proves the check exists and is enforced only against the pre-redirect URL, exactly matching the Grafana bug class: a resource that is allowed by the security policy can respond with an HTTP redirect and have the browser blindly follow it to an origin the policy was meant to exclude.

I was unable to locate the actual production implementation of `ServiceWorkerVersion::OpenPaymentHandlerWindow` in the indexed codebase (only its name and behavior are referenced from the browser test comments) [5](#0-4) ; the implementation file may not be covered by the current index. This limits verification of the exact mechanism (e.g., whether the check happens once at dispatch time vs. per-redirect in a throttle), but the test-observed behavior is conclusive that redirect enforcement is skipped for this specific path.

### Impact Explanation
A malicious or compromised Payment Handler service worker (installed by any site the user grants payment-app permission to, without special privilege) whose `Connection-Allowlist` header only allows a benign-looking URL can use that URL as an open redirector to navigate the user's top-level payment handler window to an arbitrary origin outside the declared allowlist. This defeats the security purpose of the Connection-Allowlist (analogous to Grafana Enterprise's Request security allow list), letting network restrictions meant to constrain a payment handler's outbound navigation be silently bypassed, potentially exposing the user to phishing/UI-spoofing content or leaking payment-flow state to disallowed origins.

### Likelihood Explanation
The attacker needs only to install a payment handler service worker with a Connection-Allowlist header (no additional privilege, flags, or enterprise policy required, since `network::features::kConnectionAllowlists` is a standard content feature under active test coverage) and to have `evt.openWindow()` follow a same-origin-appearing URL that server-side 302-redirects elsewhere. This is a straightforward, deterministic, and reproducible bypass, not reliant on timing races or MITM.

### Recommendation
Enforce the `redirects=block` (and general redirect matching) semantics of `Connection-Allowlist` uniformly across all consumers of the allowlist, including `ServiceWorkerVersion::OpenPaymentHandlerWindow`, not only the `PaymentManifestDownloader`/network-service URL-loader-factory paths. The redirect target of an `openWindow()` navigation should be re-validated against the declared allowlist and directive before the navigation is allowed to proceed, matching the behavior already implemented for HEAD/GET manifest fetches.

### Proof of Concept
1. Install a Payment Handler service worker whose script is served with header:
   `Connection-Allowlist: (response-origin "*://attacker.example:*/*/redirect.html"); redirects=block`
2. In the service worker's `paymentrequest` handler, call `evt.openWindow('https://attacker.example/redirect.html')`.
3. Serve `/redirect.html` with an HTTP 302 to `https://evil.example/window.html` (an origin outside the allowlist).
4. Observe that `openWindow()` succeeds and the browser navigates to `evil.example`, despite `redirects=block` being declared — as shown by the existing `NoEffectOnOpenWindowRedirect` test [6](#0-5) .

// Test that payment manifest download from "a.com", which is redirected to
// "sub.a.com" is blocked when Connection-Allowlist is set to (response-origin
// "*://sub.a.com:*/*") and `redirects=block`.
IN_PROC_BROWSER_TEST_P(PaymentRequestConnectionAllowlistBrowserTest,
                       HeadRequestRedirectBlocked) {
  GURL target_url = https_server()->GetURL("sub.a.com", "/nickpay.test/pay");
  GURL redirect_url =
      https_server()->GetURL("a.com", "/server-redirect?" + target_url.spec());

  RegisterResponse(
      "/payment_request_connection_allowlist_redirects_block.html",
      ResponseEntry(
          kDefaultPaymentPageContent,
          {{"Connection-Allowlist",
            R"((response-origin "*://sub.a.com:*/*"); redirects=block)"}}));
  RegisterResponse(
      "/nickpay.test/pay",
      ResponseEntry(
          R"({ "default_applications": ["app.json"] })",
          {{"Content-Type", "application/json"},
           {"Link", "</nickpay.test/pay>; rel=\"payment-method-manifest\""}}));
  RegisterResponse(
      redirect_url.PathForRequest(),
      ResponseEntry("", {{"Location", target_url.spec()}}, net::HTTP_FOUND));

// when the URL is not allowed by the connection allowlist.
IN_PROC_BROWSER_TEST_P(PaymentRequestConnectionAllowlistBrowserTest,

  // Merchant page on a.com.
  RegisterResponse(
      "/payment_request_connection_allowlist_open_window_blocked.html",
      ResponseEntry(kOpenWindowMerchantPage, {}));

  // Payment app service worker on b.com. The service worker has an empty
  // connection allowlist, which means no request is allowed.
  RegisterResponse("/connection_allowlist_open_window/sw.js",
                   ResponseEntry(kOpenWindowServiceWorkerScript,
                                 {{"Content-Type", "application/javascript"},
                                  {"Connection-Allowlist", "()"}}));

  // Target to be opened by the service worker via
  // PaymentRequestEvent.openWindow().
  std::string window_relative_url{
      "/connection_allowlist_open_window/window.html"};
  RegisterResponse(
      window_relative_url,
      ResponseEntry("<!DOCTYPE html><html><body>Window</body></html>",
                    {{"Content-Type", "text/html"}}));

  NavigateTo("a.com",
             "/payment_request_connection_allowlist_open_window_blocked.html");

  std::string payment_method;
  InstallPaymentApp("b.com", "/connection_allowlist_open_window/sw.js",
                    &payment_method);

  GURL window_url = https_server()->GetURL("b.com", window_relative_url);
  content::URLLoaderMonitor monitor({window_url});

  // Verify PaymentRequestEvent.openWindow() resolves to null and returns
  // the error message because window.html is not allowed by service worker's
  // allowlist.
  EXPECT_THAT(
      content::EvalJs(GetActiveWebContents(),

// Test that service worker's connection allowlist's redirect directive has no
// effect on Payment Request API PaymentRequestEvent: openWindow() when there is
// a redirect.
IN_PROC_BROWSER_TEST_P(PaymentRequestConnectionAllowlistBrowserTest,
                       NoEffectOnOpenWindowRedirect) {
  RegisterResponse("/", ResponseEntry("", {}, net::HTTP_OK));

  // Merchant page on a.com.
  RegisterResponse(
      "/payment_request_connection_allowlist_open_window_redirect_allowed.html",
      ResponseEntry(kOpenWindowMerchantPage, {}));

  // Payment app service worker on b.com. Attempts to open redirect.html via
  // PaymentRequestEvent: openWindow(), which is then redirected to window.html.
  // Resolves payment with 'success' if opened, otherwise the error message.
  // Note the service worker's connection allowlist specifies `redirects=block`.
  // However, it should not have effect on PaymentRequestEvent: openWindow().
  RegisterResponse("/connection_allowlist_open_window/sw.js",
                   ResponseEntry(kOpenWindowServiceWorkerScript,
                                 {{"Content-Type", "application/javascript"},
                                  {"Connection-Allowlist", R"(
                                    (
                                      response-origin
                                      "*://b.com:*/*/redirect.html"
                                    ); redirects=block
                                  )"}}));

  GURL target_window_url = https_server()->GetURL(
      "b.com", "/connection_allowlist_open_window/window.html");
  RegisterResponse("/connection_allowlist_open_window/redirect.html",
                   ResponseEntry("", {{"Location", target_window_url.spec()}},
                                 net::HTTP_FOUND));

  // Target window document on b.com.
  RegisterResponse(
      "/connection_allowlist_open_window/window.html",
      ResponseEntry("<!DOCTYPE html><html><body>Window</body></html>",
                    {{"Content-Type", "text/html"}}));

  NavigateTo("a.com",
             "/payment_request_connection_allowlist_open_window_redirect_"
             "allowed.html");

  std::string payment_method;
  InstallPaymentApp("b.com", "/connection_allowlist_open_window/sw.js",
                    &payment_method);

  GURL redirect_url = https_server()->GetURL(
      "b.com", "/connection_allowlist_open_window/redirect.html");
  content::URLLoaderMonitor monitor({redirect_url});

  // Verify PaymentRequestEvent: openWindow() succeeds because the initial
  // request URL redirect.html matches the service worker's connection
  // allowlist. And the connection allowlist's redirect directive has no effect
  // for PaymentRequestEvent: openWindow().
  EXPECT_EQ(
      "success",
      content::EvalJs(GetActiveWebContents(),
                      content::JsReplace("testOpenWindow($1, $2)",
                                         payment_method, redirect_url.spec())));
  // Verify `redirect_url` was requested. We check `GetRequestInfo()` instead
  // of `WaitForRequestCompletion()` because `testOpenWindow()` completes the
  // payment request right after `openWindow()` resolves, closing the payment
  // handler window. Closing the window destroys its `WebContents` and in-flight
  // URL loaders before `URLLoaderMonitor` may have received `OnComplete()` from
  // the network service.
  monitor.WaitForUrls({redirect_url});
  EXPECT_TRUE(monitor.GetRequestInfo(redirect_url).has_value());
}
