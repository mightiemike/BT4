## Finding: Unbounded re-scan cost in ancient append-vec shrink caused by accumulating unpackable multi-ref slots

The bug class in the report — a loop whose iteration count grows monotonically with historical accumulation (liquidations since deposit) and is re-walked on every invocation — has a concrete analog in the AccountsDB ancient-storage shrink path.

### Title
Unbounded per-cycle iteration cost in ancient append-vec shrink from persistently unpackable multi-ref slots - (File: accounts-db/src/ancient_append_vecs.rs, accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb::shrink_ancient_slots` is invoked periodically by the background service and, on every call, recomputes the *entire* set of ancient candidate slots via `get_sorted_potential_ancient_slots` → `self.storage.slots_less_than(oldest_non_ancient_slot)`, then walks that whole set again in `calc_ancient_slot_info`/`calc_accounts_to_combine`. Slots containing accounts with `ref_count > 1` whose highest-slot entry lies elsewhere (`many_refs_old_alive`) cannot be packed away and are explicitly left in place "to be re-evaluated" on the next pass. If such slots accumulate faster than clean/shrink can resolve their multi-ref condition, the ancient candidate set grows without bound, and every subsequent background-service cycle re-scans a linearly (or worse) growing slot set indefinitely. [1](#0-0) [2](#0-1) 

### Finding Description
`shrink_ancient_slots` selects candidates with `get_sorted_potential_ancient_slots`, which calls `slots_less_than(oldest_non_ancient_slot)` — an unfiltered iteration over the entire `self.map` of storage entries, returning every slot older than the ancient boundary: [3](#0-2) 

Those slots are then fully re-scanned each cycle in `calc_ancient_slot_info` (iterates every slot, fetches its storage, computes alive/dead byte stats) and again in `calc_accounts_to_combine` (calls `shrink_collect` on every slot's unique accounts): [4](#0-3) [5](#0-4) 

The code explicitly documents that a slot holding only `many_refs_old_alive` accounts (multi-ref accounts whose newest version lives in a different, non-target slot) is skipped from packing and left behind: "this account must remain IN this slot... It could be a clean error or a transient condition that will resolve if we encounter this situation": [6](#0-5) 

Because resolution of these multi-ref conditions depends on `clean_accounts` eventually reducing the ref count to 1 (which itself depends on other forks/roots being cleaned), there is no hard guarantee this always happens promptly. As long as such slots exist, they remain permanent members of the "potential ancient slots" set returned by `slots_less_than`, so every future `shrink_ancient_slots` call — which runs on a fixed cadence regardless of progress — must re-fetch, re-scan, and re-attempt to pack them, in addition to any newly-aged slots. This is structurally the same growth pattern as `CDSLib.withdrawUser`'s liquidation loop: a background process forced to re-walk an ever-growing historical set on every invocation because the set is never shrunk once an item becomes "stuck."

### Impact Explanation
This does not corrupt state or affect consensus (ancient shrink is a storage-layout optimization only), but it produces disproportionate and growing CPU/IO cost on the `AccountsBackgroundService` thread over the life of a long-running validator, as permitted under "disproportionate storage and CPU cost." A validator whose ancient slot set accumulates unpackable multi-ref slots faster than they resolve will see `shrink_ancient_slots` take progressively longer on each call, competing with clean/flush for the same background thread and potentially causing storage to grow unbounded since those ancient append vecs are never shrunk or dropped.

### Likelihood Explanation
Likelihood is moderate: it requires accounts with `ref_count > 1` (the same pubkey alive in multiple root forks/slots) to persist in ancient storage where the highest-slot version is not co-located with the older instance — a scenario the code itself acknowledges can occur from "clean bugs or low memory conditions," i.e., it is a known, reachable edge case in ordinary node operation rather than a contrived or privileged attack, and requires no special validator/operator role to trigger — any client activity that produces multi-ref accounts across old slots can seed it.

### Recommendation
Bound the per-cycle work independent of how many slots remain unpackable, e.g. by tracking and excluding slots already known to be stuck in `many_refs_old_alive` from the candidate set recomputed by `slots_less_than`/`get_sorted_potential_ancient_slots` until their ref-count condition changes (via a dirty/invalidation signal from clean), rather than re-including and re-scanning them on every cycle.

### Proof of Concept
Not applicable as a single reproducible transaction (this is a validator-internal background-service cost issue, not a user-triggered call); the growth mechanism is demonstrated by the code path cited above: `get_sorted_potential_ancient_slots` → `slots_less_than` returns the full un-pruned ancient slot set each call, and `calc_accounts_to_combine` explicitly retains slots with `many_refs_old_alive` for re-evaluation on subsequent calls without any cap on how many times or how large that retained set can grow.
