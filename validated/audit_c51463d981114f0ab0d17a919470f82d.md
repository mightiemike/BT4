### Title
Rejected L1-handler transactions permanently excluded from proposal with no retry path, freezing the corresponding L1-to-L2 message - (File: `crates/apollo_l1_events/src/transaction_record.rs`, `crates/apollo_l1_events/src/transaction_manager.rs`)

### Summary
The `TransactionManager`/`TransactionRecord` state machine that tracks L1-handler (L1→L2 message) transactions has a `Rejected` state that is entered when a transaction is rejected at block-commit time, but the state machine has no transition that ever moves a `Rejected` record back to `Pending`. Because only `Pending` records are proposable, once a valid L1 message is rejected once, it can never again be proposed by any honest sequencer, permanently stranding that L1→L2 message — directly analogous to the reported `processWithdrawals` bug where a failed item is skipped and never retried, permanently locking user funds.

### Finding Description
`TransactionRecord::mark_rejected` unconditionally transitions the record to `TransactionState::Rejected`: [1](#0-0) 

`is_proposable()` — the sole predicate used to decide whether a transaction is inserted into (or kept in) `proposable_index`, which is the only source `get_txs` (block proposal) reads from — is `true` only for the `Pending` state: [2](#0-1) 

`maintain_indices` removes a record from `proposable_index` whenever `is_proposable()` becomes false, and there is no code path anywhere in `transaction_manager.rs` or `transaction_record.rs` that sets `state` back to `Pending` from `Rejected`: [3](#0-2) 

`commit_txs`, invoked from `apply_commit_block` after every block commit, is the only writer of the `Rejected` state and simply calls `mark_rejected` with no compensating logic: [4](#0-3) 

The `TransactionState` enum confirms there is no reverse edge defined from `Rejected`: [5](#0-4) 

Unlike the `Consumed` state (cleaned up via a timelock queue) or `CancelledOnL2`/`Committed` (each reachable from well-defined external triggers), `Rejected` records are simply left in `records` forever, excluded from `proposable_index`, with no timelock, no retry, and no external signal (L1 event) that could resurrect them, since consumption/cancellation only come from the L1 contract, which has no knowledge that the sequencer rejected the message.

This precisely mirrors the reported bug class: a value-bearing item (`Withdrawal` in the report, an `L1HandlerTransaction`/L1→L2 message here) enters a processing loop; on failure it is marked failed/skipped (`WithdrawalFailed` event / `Rejected` state) and the loop advances past it with no mechanism to reprocess, and no privileged actor is expected to intervene.

### Impact Explanation
L1-handler transactions represent L1→L2 messages, most critically bridge deposits where an L1 contract has already locked/burned funds and expects a corresponding L2-side credit to occur when the L1-handler executes. If such a transaction is rejected during block building (e.g., it does not fit given `bouncer` capacity limits, is dropped from a proposal by an honest proposer for capacity reasons, or fails some other non-consensus-critical, non-malicious condition) and marked `Rejected`, it can never be proposed by any future honest node, since `proposable_index` will never contain it again. The corresponding L1-side funds/message are permanently unfulfillable on L2 — a concrete permanent freezing of funds reachable purely from a normal L1 message submission by an unprivileged user, requiring no malicious operator or attacker action.

### Likelihood Explanation
This is triggered by ordinary block-building dynamics (e.g., the L1-handler transaction not fitting within `max_l1_handler_txs_per_block`/bouncer resource limits for several consecutive block-building cycles, or a transient rejection reason at commit time) rather than by attacker-controlled or malicious-operator behavior. Any legitimately-submitted L1 message can eventually be marked `Rejected` under normal sequencer operation, making this reachable without any special privilege — the trigger is exactly a "single L1 message."

### Recommendation
Add a well-defined recovery path for `Rejected` L1-handler transactions: either (a) automatically re-transition `Rejected` records back to `Pending` (re-inserting them into `proposable_index`) so they are retried in future blocks, or (b) surface an explicit, monitorable "permanently rejected" state together with alerting/metrics and a defined protocol-level fallback (e.g., re-queue via a new L1 event, or explicit sequencer retry policy) so that no legitimately-submitted L1→L2 message can be silently and permanently dropped from proposal consideration.

### Proof of Concept
1. An L1 contract sends a `LogMessageToL2` event; the scraper picks it up and `TransactionManager::add_tx` creates a `Pending` record, inserted into `proposable_index` [6](#0-5) .
2. The transaction is proposed via `get_txs` and included by a block builder, but the block/commit process later marks it in `rejected_tx_hashes` (e.g., due to bouncer capacity or another benign rejection reason) at `commit_proposal_and_block`, which calls `L1EventsProviderClient::commit_block` with the tx hash in `rejected_l1_handler_tx_hashes` [7](#0-6) .
3. `apply_commit_block` → `TransactionManager::commit_txs` calls `mark_rejected`, setting `state = Rejected` [8](#0-7) .
4. `maintain_indices` removes the tx hash from `proposable_index` because `is_proposable()` now returns `false` for `Rejected` state.
5. No future call to `add_tx`, `commit_txs`, `request_cancellation`, `finalize_cancellation`, or `consume_tx` ever restores `state` to `Pending`; the record permanently remains outside `proposable_index`, so no honest proposer will ever include this L1 message again, while the L1 side has already sent (and possibly locked funds for) the message.

    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }

                return;

                // preserves arrival order.

                if !tx_hashes.contains(&tx_hash) {

                // This tx needs to be removed from the proposable index if it was on it.

                                entry.remove();
                            }
