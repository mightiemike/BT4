### Title
Global contracts deployed via `DeployGlobalContractAction` can never be removed, permanently locking the deployer's storage-cost payment - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
The `DeployGlobalContractAction` lets any account signer permanently register code as a "global contract" (by code hash or by account id) that is distributed to every shard, while burning NEAR proportional to code size as a storage deposit. There is no corresponding action to undeploy/remove a global contract and reclaim that deposit, and no other account can ever "unuse" a `CodeHash`-mode entry from the network since it is documented as immutable.

### Finding Description
`action_deploy_global_contract` computes `storage_cost` from `global_contract_storage_amount_per_byte * code.len()`, subtracts it from the caller's balance via `account.set_amount(updated_balance)`, and burns it (`result.tokens_burnt`), then calls `initiate_distribution` to push the code to all shards as a `GlobalContractDistributionReceipt`. [1](#0-0) 
Once distributed, `apply_distribution_current_shard` writes the code into the trie at `TrieKey::GlobalContractCode { identifier }` on every shard, permanently occupying that state slot. [2](#0-1) 

The `Action` enum only exposes `DeployGlobalContractAction` and `UseGlobalContractAction`; there is no `DeleteGlobalContract`/remove action anywhere in the codebase (confirmed by the absence of any such variant or handler across `core/primitives/src/action/mod.rs`, `runtime/runtime/src/actions.rs`, and `runtime/runtime/src/global_contracts.rs`). [3](#0-2) 
For `CodeHash` deploy mode, the docs explicitly state this "effectively makes the contract immutable," and for `AccountId` mode the owner can only overwrite the code (re-deploy), never delete the registry entry to reclaim the burnt storage fee. [4](#0-3) 

This is a structural analog of the reported Gearbox `ContractsRegister` bug: an append-only on-chain registry (pool/manager list there, global-contract-code slot here) that provides an "add" path reachable by an ordinary caller but no corresponding "remove" path, so entries — and here, the NEAR paid as a storage deposit for them — become permanently stuck.

### Impact Explanation
The NEAR burned as `storage_cost` when deploying a global contract (`result.tokens_burnt`) is unrecoverable: the deployer cannot delete the global contract code to free that reserved value, and no protocol-level action exists to reclaim it. For `CodeHash`-mode deployments this is permanent by design/documentation, but even `AccountId`-mode deployers who no longer want the contract published (e.g. it contains a bug, or they simply want to stop paying implicitly for occupying global state) have no way to remove it and recover the deposit — this is a permanently frozen-funds condition triggered entirely by a single unprivileged transaction signer's own deploy action.

### Likelihood Explanation
Any account holder can trigger this simply by submitting a `DeployGlobalContractAction` transaction — no special privilege, validator status, or network condition is required. This is a normal, encouraged, and tested code path (see `pytest/tests/contracts/deploy_call_global_smart_contract.py` and `test-loop-tests/src/tests/global_contracts.rs`), so the condition is reached on every global contract deployment. [5](#0-4) 

### Recommendation
Introduce a protocol action (e.g. `DeleteGlobalContractAction`) restricted to the original deploying account (for `AccountId` mode) that removes the `TrieKey::GlobalContractCode` entry, decrements/clears the associated nonce state, and refunds the proportional storage deposit back to the deployer's account balance, provided no account currently references it via `UseGlobalContractAction` (or accepting that existing users keep running the last-known code, similar to how regular contract deletion is handled). For `CodeHash` mode, since immutability is intentional, at minimum document this as a known permanent-cost trade-off and consider a garbage-collection/refund path once distribution guarantees allow safely proving no account references remain.

### Proof of Concept
1. Submit a `DeployGlobalContractAction(code, GlobalContractDeployMode::AccountId)` transaction signed by `alice`, as in `deploy_global_contract_tx`, paying `storage_cost = global_contract_storage_amount_per_byte * code.len()` burnt from `alice`'s balance. [6](#0-5) 
2. Observe the code is now stored at `TrieKey::GlobalContractCode { identifier: AccountId(alice) }` on every shard after the distribution receipt runs. [7](#0-6) 
3. Attempt to find any action in the `Action` enum or any runtime handler that removes this entry or refunds `alice`'s storage deposit — none exists; `alice` can only overwrite the code via another deploy, never delete/reclaim it, permanently locking the burnt NEAR and the global state slot.
