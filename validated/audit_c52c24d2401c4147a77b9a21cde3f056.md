### Title
Unbounded, unsynchronized `refreshToken` calls via replayable fulfillment-service requests - ([File: packages/apps/shopify-app-remix/src/server/helpers/ensure-offline-token-is-not-expired.ts])

### Summary
`ensureOfflineTokenIsNotExpired` performs a check-then-act on `session.isExpired()` and calls `refreshToken` with no locking/deduplication, so any burst of authenticated fulfillment-service requests for a shop whose offline token is within `WITHIN_MILLISECONDS_OF_EXPIRY` triggers one Shopify OAuth token-exchange call per request. Because the HMAC validation used for fulfillment-service/webhook/flow requests (`validateHmacFromRequestFactory`) only checks the request body signature and has no timestamp/nonce, a single captured valid request can be replayed indefinitely and concurrently by its own recipient (or anyone who obtains the payload), amplifying calls to Shopify's token endpoint.

### Finding Description
`authenticateFulfillmentServiceFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts` validates a POST body via `api.fulfillmentService.validate` and then calls `ensureValidOfflineSession(params, shop)` [1](#0-0) . That in turn calls `ensureOfflineTokenIsNotExpired`, which loads the current session, checks `session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY)`, and if true (and refresh token present) unconditionally calls `refreshToken(params, shop, session.refreshToken)` before persisting the new session [2](#0-1) . `refreshToken` calls `api.auth.refreshToken`, which performs an HTTP POST to Shopify's `/admin/oauth/access_token` endpoint [3](#0-2) .

There is no mutex, in-flight-request cache, or optimistic-lock check around this read-check-refresh-write sequence, so N concurrent invocations for the same shop each independently read the same near-expiry session and each independently issue a refresh call.

Separately, the HMAC check used for this path (`validateHmacFromRequestFactory` → `validateHmacString`, used for `HmacValidationType.FulfillmentService`) validates only the raw request body against the static `X-Shopify-Hmac-Sha256` header value using `safeCompare` [4](#0-3) . Unlike `validateHmac` (used for admin/app-proxy query-string signing), this body-based path has no `validateHmacTimestamp` call and no nonce, so a previously captured, legitimately-signed fulfillment-service payload remains valid forever and can be replayed verbatim any number of times, including concurrently.

### Impact Explanation
A shop owner (or anyone in possession of one valid, previously-issued fulfillment-service payload for a shop) can replay it concurrently in bulk while that shop's offline token is within the 5-minute expiry window. Each replay independently passes HMAC validation and triggers a full call to Shopify's OAuth token endpoint via `refreshToken`. This can: (1) exhaust the app's or shop's rate limit against Shopify's OAuth endpoint, (2) cause excessive refresh-token rotation/thrashing that can race with legitimate refreshes and potentially invalidate concurrently-issued tokens, and (3) waste app server/database resources on repeated `storeSession` writes. This matches a denial-of-service class impact scoped to the token-refresh/authentication path.

### Likelihood Explanation
Feasibility requires only: a shop owner/merchant sending fulfillment-order-notification traffic to their own app (entirely within normal privileges of running a fulfillment service integration), capturing one such legitimately-signed request, and replaying it concurrently while the stored offline token is near expiry (a window that recurs periodically, since expiring tokens are refreshed and will re-enter the 5-minute window later). No secret, no privileged role, and no host-app misconfiguration is required beyond the `expiringOfflineAccessTokens` future flag being enabled (a supported, documented configuration, not a "non-default" bug condition in the sense of introducing new risk—refresh support is the feature under test).

### Recommendation
- Add a per-shop mutex/in-flight promise cache (e.g., keyed by `shop` or offline session id) around the refresh sequence in `ensureOfflineTokenIsNotExpired`/`refreshToken` so concurrent callers await a single in-flight refresh rather than each triggering their own.
- Add timestamp/nonce-based replay protection to the body-HMAC validation path (`validateHmacFromRequestFactory`) used by fulfillment-service/flow, consistent with the timestamp check already present in `validateHmac` for admin/app-proxy.
- Consider rate-limiting refresh attempts per shop (e.g., minimum interval between refresh calls) independent of concurrency.

it('calls refreshToken once per concurrent request without de-dup', async () => {
  const sessionStorage = new MemorySessionStorage();
  const nearExpiry = new Date(Date.now() + 60 * 1000); // within 5-minute window
  const session = await setUpValidSession(sessionStorage, {
    expires: nearExpiry,
    refreshToken: 'test-refresh-token',
  });

  const refreshSpy = jest.fn(async () => ({ session: { ...session, accessToken: 'new' } }));
  // wire refreshSpy in place of api.auth.refreshToken

  const body = { kind: 'FULFILLMENT_REQUEST' };
  const bodyString = JSON.stringify(body);
  const makeRequest = () => new Request(FULFILLMENT_URL, {
    method: 'POST',
    body: bodyString,
    headers: {
      'X-Shopify-Hmac-Sha256': getHmac(bodyString), // same valid HMAC, replayed
      'X-Shopify-Shop-Domain': session.shop,
    },
  });

  await Promise.all(
    Array.from({ length: 20 }).map(() =>
      shopify.authenticate.fulfillmentService(makeRequest()),
    ),
  );

  // Expected (secure) behavior: refreshSpy called once (de-duplicated)
  // Actual behavior: refreshSpy called up to 20 times
  expect(refreshSpy).toHaveBeenCalledTimes(1);
});

export async function ensureOfflineTokenIsNotExpired(
  session: Session,
  params: BasicParams,
  shop: string,
) {
  const {config} = params;
  if (
    config.future?.expiringOfflineAccessTokens &&
    session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY) &&
    config.distribution !== AppDistribution.ShopifyAdmin &&
    session.refreshToken
  ) {
    const offlineSession = await refreshToken(
      params,
      shop,
      session.refreshToken,
    );

    await config.sessionStorage!.storeSession(offlineSession);
    return offlineSession;
  }

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}
