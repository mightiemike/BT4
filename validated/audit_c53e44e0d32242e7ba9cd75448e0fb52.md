### Title
Webhook shop-domain spoofing via unsigned `X-Shopify-Shop-Domain` header enables cross-tenant session/token access - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
Similar to the GitLab GraphQL `namespace` report — where a resource identifier (`fullPath`) was trusted to select which tenant's private data to return without an independent authorization check tying the identifier to the requester — `shopify-app-js`'s webhook pipeline trusts the `X-Shopify-Shop-Domain` header to select which shop's offline session/access token to attach to an inbound webhook request, while the accompanying HMAC signature covers only the raw body, not that header.

### Finding Description
`shopify.webhooks.validate` (and the `process`/`authenticate` wrappers built on top of it) verifies webhook authenticity purely by recomputing an HMAC over `rawBody` with the app's shared secret and comparing it to the `X-Shopify-Hmac-Sha256` header [1](#0-0) . The test helper that generates a "valid" webhook signature computes the HMAC from `secretKey` and `body` alone [2](#0-1) , and `X-Shopify-Shop-Domain` is supplied as a separate, unsigned header alongside it [3](#0-2) .

After `validate()` succeeds, the resulting `domain` value (taken directly from that unsigned header) is used, without any further cross-check, to load the shop's stored offline session and expose it — together with an authenticated Admin API client — to the webhook handler: [4](#0-3) 
```
const check = await api.webhooks.validate({ rawBody, rawRequest: request });
...
const session = await ensureValidOfflineSession(params, check.domain);
```
and then `admin = adminClientFactory({params, session, ...})` is returned to the app's handler code [5](#0-4) . The same pattern exists in `shopify-app-remix` and the Express `process`/`validate` helpers [6](#0-5) .

Because the shared app secret is identical for every shop that installs the app, and the domain header is not part of the signed material, a party that has legitimately installed the app on their own shop can capture one of their own real webhook deliveries (valid `rawBody` + matching `X-Shopify-Hmac-Sha256`), then resend that exact body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop the attacker does not control. `validate()` will report the request as valid, and the webhook pipeline will look up and hand the victim shop's offline session/access token to the handler, exactly as if Shopify itself had sent that event for the victim shop.

### Impact Explanation
This lets a single, unprivileged app-installing merchant impersonate any other shop that has the same app installed, from the app's own webhook endpoint's point of view. Depending on how the app's webhook handler uses `session`/`admin`, consequences range from cross-tenant data exposure (the handler processing the attacker's payload while believing it belongs to the victim's shop) to acting on the victim's store using the victim's offline access token retrieved from session storage — a direct parallel to the H1 report's outcome of retrieving another tenant's private data via an identifier that wasn't properly bound to the authenticated caller.

### Likelihood Explanation
Exploitation requires only: (1) attacker's own legitimate installation of the target app (to obtain one authentic body+HMAC webhook pair), and (2) knowledge of the victim shop's domain, which is typically public (`*.myshopify.com`). No secrets need to be leaked and no privileged access is required — this fits the "unprivileged merchant" analog required by the rules.

### Recommendation
- Bind the shop identity to the signed payload: derive the shop from a value that Shopify actually signs (or from the app's own webhook subscription record keyed by the resource/topic), rather than trusting `X-Shopify-Shop-Domain` unconditionally.
- Where available, prefer verifying the webhook against the shop's own registered subscription (e.g., match `webhookId`/topic against session storage records created during `webhooks.register`) instead of using the header value directly as a session-storage lookup key.
- At minimum, document/enforce that consuming apps must independently verify that `check.domain` corresponds to a shop that legitimately installed the app before trusting any session or Admin client derived from it, and consider adding this cross-check inside `shopify-app-js` itself so it is not left to app developers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and triggers a webhook (e.g., updates a product) that the app has subscribed to.
2. Attacker captures the resulting POST to the app's webhook endpoint, recording the raw body and the `X-Shopify-Hmac-Sha256` header value (both are signed using the app's single shared secret, valid for any shop with that app installed).
3. Attacker resends the identical body and HMAC header to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `shopify.webhooks.validate`/`authenticate` accepts the request as valid because the HMAC check only covers `rawBody` [7](#0-6) , then loads and exposes `victim.myshopify.com`'s offline session/access token to the handler based solely on the spoofed header [4](#0-3) .

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);

        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };

export function createTestHmac(secretKey: string, body: string): string {
  return crypto
    .createHmac('sha256', secretKey)
    .update(body, 'utf8')
    .digest('base64');
}
