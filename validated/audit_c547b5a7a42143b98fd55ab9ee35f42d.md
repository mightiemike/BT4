### Title
Global contract deployer can unilaterally break already-referencing accounts' redeem/withdraw logic, permanently locking their funds - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
NEAR's global-contract mechanism lets one account own a piece of code that many other accounts share by reference (`UseGlobalContract`). When deployed with `GlobalContractDeployMode::AccountId`, the code is addressed by the deployer's account, and the deployer can redeploy different code at any time, instantly changing the executable logic of **every** account that referenced it via `GlobalContractIdentifier::AccountId`. This is architecturally analogous to the UXD `whitelistAsset` bug: a single "owner" action can retroactively strip functionality (e.g. a withdraw/redeem method) that dependent parties relied on when they entered a position, with no way for those dependents to recover, exactly like removing collateral from the whitelist blocks redemption of assets deposited earlier.

### Finding Description
`GlobalContractDeployMode::AccountId` is explicitly documented as allowing "the owner to update the contract for all its users": [1](#0-0) 

Any account can point itself at that shared code via `UseGlobalContract`, which simply checks the code exists and rewrites the account's `AccountContract` to `GlobalByAccount(id)`: [2](#0-1) 

Redeployment is a normal, unprivileged `DeployGlobalContract` transaction that overwrites the shared code identified by the deployer's `AccountId`: [3](#0-2) 

There is no versioning, no opt-out, and no protection for accounts that already reference the code: every account whose `AccountContract` is `GlobalByAccount(deployer_id)` immediately runs whatever code the deployer publishes next. The test suite explicitly demonstrates this: after redeploying a "trivial" contract with no methods, all previously-working accounts lose the ability to call any method (`MethodNotFound`) until the deployer chooses to redeploy compatible code again: [4](#0-3) 

If a referencing account's only path to move its own balance out (a "withdraw"/"redeem" method analogous to UXD's `_redeem()`) lives in that shared code, the deployer redeploying incompatible code — or simply never redeploying compatible code again — permanently blocks that path. There is no fallback: the runtime's only recourse for a missing/incompatible global contract is `GlobalContractDoesNotExist`/`MethodNotFound` failures, and `UseGlobalContract` cannot be reversed by the affected account without cooperation from the same code (which may no longer expose a method to do so): [5](#0-4) 

### Impact Explanation
Any number of accounts that adopted a `GlobalByAccount` contract to manage token balances/positions can have their exit logic permanently disabled by a single transaction from the (unprivileged) deployer account, freezing user funds inside those accounts exactly as in the UXD report — deposits made under one code version cannot be withdrawn once the shared code changes underneath them. Because `AccountContract::GlobalByAccount` is a first-class, protocol-supported feature (not a bug in a specific contract), this is a systemic footgun: the runtime provides no mechanism to protect dependents' already-committed funds when the shared code they rely on is altered or withdrawn.

### Likelihood Explanation
Likelihood is moderate: it requires an application built on `GlobalContractDeployMode::AccountId` sharing, and a set of users who both deposit funds into referencing accounts and rely on the shared code path for withdrawal. Given NEAR promotes global contracts (including for ZBA-style patterns, as seen in `setup_zba_global_contract` tests) as a way to save storage costs, this pattern is realistic for any protocol that stores value in accounts running shared, updatable code.

### Recommendation
Provide a protocol-level safeguard so that value already committed to an account referencing a `GlobalByAccount` contract cannot be stranded by the deployer's later redeployments — e.g., pin a referencing account to a specific code hash/version at time of `UseGlobalContract` (opt-in immutability), require the account itself to explicitly ack an update, or add a protocol-guaranteed unconditional balance-exit path independent of the currently-deployed global contract code.

### Proof of Concept
1. Deployer account `D` publishes a global contract via `DeployGlobalContract { deploy_mode: AccountId }` exposing a `withdraw` method (`runtime/runtime/src/global_contracts.rs:25-63`).
2. User account `U` calls `UseGlobalContract { contract_identifier: AccountId(D) }`, then transfers/deposits funds into `U`, relying on `withdraw` to exit later (`runtime/runtime/src/global_contracts.rs:76-108`).
3. `D` redeploys a new `DeployGlobalContract { deploy_mode: AccountId }` with code that has no `withdraw` method (or different, incompatible logic) — exactly as exercised in `test_global_contract_update` (`test-loop-tests/src/tests/global_contracts.rs:71-106`), which confirms calls that used to succeed now fail with `MethodNotFound`.
4. `U` calls `withdraw`; the call now fails at method resolution, and there is no other in-protocol action available to `U` to retrieve funds tied to the old contract logic — funds are stuck until/unless `D` chooses to restore compatible code.

```rust
pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}
```

```rust
pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
```

```rust
#[test]
fn test_global_contract_update() {
    let mut env = GlobalContractsTestEnv::setup(Balance::from_near(1000));
    let use_accounts = [env.account_shard_0.clone(), env.account_shard_1.clone()];

    env.deploy_trivial_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        env.use_global_contract(
            account,
            GlobalContractIdentifier::AccountId(env.deploy_account.clone()),
        );

        // Currently deployed trivial contract doesn't have any methods,
        // so we expect any function call to fail with MethodNotFound error
        let call_tx = env.call_global_contract_tx(account.clone(), account.clone());
        let call_outcome = env.execute_tx(call_tx);
        assert_matches!(
            call_outcome.status,
            FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
                kind: ActionErrorKind::FunctionCallError(FunctionCallError::MethodResolveError(
                    MethodResolveError::MethodNotFound
                )),
                index: _
            }))
        );
    }

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        // Function call should be successful after deploying rs contract
        // containing the function we call here
        env.assert_call_global_contract_success(account.clone(), account.clone());
    }
}
```
