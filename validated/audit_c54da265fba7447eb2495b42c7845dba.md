### Title
Wallet Contract `has_in_flight_tx` flag can be permanently stuck `true` on callback panic/OOG, permanently bricking an ETH-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (deployed on ETH-implicit accounts, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`) uses a boolean flag `has_in_flight_tx` to serialize execution of `rlp_execute` calls. The invariant, as documented, is that the flag must be `true` while a promise chain is outstanding and reset to `false` once it resolves. Every callback in the chain (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) resets the flag to `false` as its very first statement. This is analogous to the era-contracts bug class where a state meant to be released (`unfreezeChain`) is not reliably released, leaving the resource stuck — except here the wallet contract has **no privileged recovery function at all**.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` immediately before returning any `PromiseOrValue::Promise(...)` [1](#0-0) . Every callback that is chained after that promise (`address_check_callback` [2](#0-1) , `nep_141_storage_balance_callback` [3](#0-2) , and `rlp_execute_callback` [4](#0-3) ) resets `has_in_flight_tx = false` as its first line, and only re-sets it to `true` if a further promise is scheduled [5](#0-4) [6](#0-5) .

The invariant comment itself acknowledges the design intent: `has_in_flight_tx` must be `true` exactly while a promise is outstanding and `false` otherwise [7](#0-6) .

The bug-class analog to `unfreezeChain` accidentally re-invoking `freezeDiamond`: in NEAR, if a scheduled callback receipt fails to complete successfully — e.g. it runs out of prepaid gas ("Exceeded the prepaid gas") or otherwise panics partway through — **all state changes made during that receipt's execution are discarded**, including the `self.has_in_flight_tx = false` reset that happened at the top of the function. Since the flag was already durably committed to `true` by the *previous* receipt (the one that scheduled this callback), a failed/panicking callback leaves `has_in_flight_tx` permanently stuck at `true`.

Once stuck, `rlp_execute` unconditionally rejects **every future call** with "transaction already in progress, please try again later" [8](#0-7) , and this is the **only** entry point into the contract (`rlp_execute` is the sole public mutating method besides the `#[private]` callbacks, which cannot be invoked by any external transaction). There is no admin/owner "unstick" method comparable to `unfreezeDiamond` in the era-contracts report — the account becomes permanently unusable for any further ETH-emulated action (transfers, function calls, key management), a strictly worse outcome than the original report where the chain admin could still recover.

This is reachable by an unprivileged actor: any relayer forwarding an RLP-encoded Ethereum transaction on behalf of the ETH-implicit account owner triggers the promise chain. If the relayer under-provisions gas for the outer transaction (intentionally or through misestimation) such that a downstream callback (e.g. `nep_141_storage_balance_callback` or `rlp_execute_callback`) runs out of gas, the account is permanently bricked. Because callback gas is a fixed function of static constants plus `action.gas()` [9](#0-8)  and the overall transaction's total attached gas is chosen by the relayer/caller, there is no code path that guarantees a callback receipt can never run short of gas.

### Impact Explanation
A stuck `has_in_flight_tx = true` permanently denies the ETH-implicit account owner (and any relayer) the ability to use `rlp_execute` ever again, since that check is unconditional and there is no recovery function. This is a transaction-triggered halt of that account's functionality and effectively permanently freezes the user's funds/actions on that account (any $NEAR, tokens, or contract calls that were intended to be reachable only via `rlp_execute` become inaccessible). This matches the accepted "permanently frozen funds" / "transaction-triggered halt" impact categories.

### Likelihood Explanation
Likelihood depends on a callback receipt failing partway (gas exhaustion or unexpected panic) after `has_in_flight_tx` has already been committed `true` by a prior receipt. This can happen from ordinary gas misestimation by a careless/malicious relayer, from a downstream cross-contract call (registrar lookup or NEP-141 `storage_balance_of`/`storage_deposit`) behaving unexpectedly, or from any other panic in the callback bodies. Because relayers are explicitly untrusted in this design (the contract already anticipates dishonest relayers and bans their access keys on `Error::Relayer` conditions [10](#0-9) ), a relayer who wants to grief a user only needs to submit a transaction with gas tuned to run out during one of the later chained callbacks — no special privilege is required, only control over how much gas is attached to the outer `rlp_execute` call.

### Recommendation
- Add an explicit recovery mechanism (e.g., a privileged/owner-only or time-based method) that can reset `has_in_flight_tx` to `false` if a promise chain is detected as terminated abnormally (e.g., via `PromiseResult::Failed` handling at every stage, or a timeout-based unlock).
- Ensure `has_in_flight_tx` is only durably set `true` together with a guaranteed, gas-bounded completion path, or restructure the state machine so a failed/panicking callback cannot leave the flag stuck (for instance, using `#[near_bindgen(state = ...)]` promises with `ignore_state_if_prepaid_gas_exceeded` patterns, or splitting the "in-flight" marker so that a failed downstream receipt can still reach a top-level callback that always executes with reserved gas sufficient only to flip the flag off).
- Add unit/integration tests that intentionally starve a chained callback of gas (or force a panic) and assert the contract can still process subsequent `rlp_execute` calls afterward.

### Proof of Concept
1. Deploy the Wallet Contract as an ETH-implicit account's global contract, as in `test_wallet_contract_interaction` [11](#0-10) .
2. As a relayer, submit an RLP-encoded transaction whose action requires the ERC20/NEP-141 path (`EthEmulationKind::ERC20Transfer`), which schedules `nep_141_storage_balance_callback` [12](#0-11) .
3. Attach exactly enough gas for `rlp_execute` and the `storage_balance_of` cross-call to succeed, but insufficient gas for `nep_141_storage_balance_callback` to finish constructing/dispatching its follow-up promise (e.g. the `storage_deposit` + transfer branch) — causing it to fail with "Exceeded the prepaid gas."
4. Because the receipt that set `has_in_flight_tx = true` (in `inner_rlp_execute`/`rlp_execute`) already committed before the failing callback executes, the failed callback's `self.has_in_flight_tx = false` (line 202) is rolled back along with the rest of its state changes.
5. Submit any subsequent `rlp_execute` call — it is now rejected forever with "transaction already in progress, please try again later" [8](#0-7) , confirming the account is permanently bricked.

Note: I was not able to execute this PoC in a live environment (no sandbox/terminal access in this mode); the analysis is based on static review of the contract's promise/state-rollback logic and the general NEAR execution semantics that failed/panicking function calls discard their own state changes. The exact gas thresholds needed to trigger the failure would need to be confirmed experimentally in a Devin session with sandbox access.
