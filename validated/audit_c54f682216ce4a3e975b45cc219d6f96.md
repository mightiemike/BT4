## Title
JSON-RPC batch requests bypass the per-endpoint rate limiter enforced by `RateLimiterServlet`, allowing a single HTTP request to amplify into an unbounded number of unthrottled RPC calls - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java`)

### Summary
The external report describes a case where a "batch" code path (`batchProcessTransaction`) is missing the access-control/throttling guard (`onlySequencer`) that is enforced on the equivalent single-item path (`processTransaction`), letting callers bypass the intended per-request control by wrapping a single operation in a batch call. The same structural pattern exists in `JsonRpcServlet`: the rate limiter is enforced once per inbound HTTP POST by `RateLimiterServlet.service()` [1](#0-0) , but a single POST containing a JSON-RPC batch array is expanded internally into N independent RPC invocations via `handleBatch()`, each dispatched to `rpcServer.handleRequest(...)` without going through `RateLimiterServlet.service()` again [2](#0-1) .

### Finding Description
`JsonRpcServlet extends RateLimiterServlet` [3](#0-2) . `RateLimiterServlet.service()` acquires a per-endpoint permit and a global IP/QPS permit exactly once per inbound HTTP request, then delegates to `super.service(req, resp)` which ultimately invokes `doPost` [1](#0-0) .

`JsonRpcServlet.doPost` distinguishes a single JSON-RPC object from a batch (JSON array) request. For the single case, `handleSingle` calls `rpcServer.handle(...)` once, consistent with the one permit already acquired [4](#0-3) . For the batch case, `handleBatch` iterates over every element of the array and calls `rpcServer.handleRequest(...)` for each sub-request independently, inside the same single `doPost` invocation that already consumed exactly one rate-limiter permit [2](#0-1) . This is functionally analogous to `batchProcessTransaction` invoking the same processing logic as `processTransaction` for each item without re-checking the guard that the single-item endpoint enforces per unit of work.

The only cap on this amplification is `jsonRpcMaxBatchSize`, and the code explicitly supports disabling that cap: when `jsonRpcMaxBatchSize <= 0`, the size check is skipped and the batch is processed with no upper bound, as validated by the test `batchLimitDisabled_largeBatchAllowed` which sends and successfully processes 500 sub-requests in a single call [5](#0-4) . Even when `jsonRpcMaxBatchSize` is set to a positive value, that cap is enforced per HTTP request, so a client can still send batches sized right at the limit rapid-fire and multiply the effective per-request-permit throughput by that batch size — precisely mirroring the reported bug class where the batched code path is not subjected to the same per-unit control as the singular path.

### Impact Explanation
Because the rate limiter (both the per-endpoint adapter and `GlobalRateLimiter`'s QPS/IP-QPS throttles) is only consulted once per HTTP POST regardless of how many JSON-RPC calls are packed into the batch array, an attacker can use the JSON-RPC batch feature to execute an arbitrary multiple (bounded only by `jsonRpcMaxBatchSize`, which can be configured to `0`/unbounded) of RPC method calls per rate-limiter permit. This directly undermines the node's DoS protections implemented via `RateLimiterServlet`/`GlobalRateLimiter`, which exist specifically to bound per-IP and per-endpoint request throughput [6](#0-5) . This can be leveraged for a denial-of-service against the full/solidity node's JSON-RPC interface, degrading availability for legitimate users.

### Likelihood Explanation
The batch endpoint is reachable by any anonymous client capable of sending an HTTP POST to the JSON-RPC endpoint — no authentication or special privilege is required, matching the "reachable from an anonymous RPC request" criterion. The behavior is deterministic and exercised by existing unit tests (e.g., `batchLimitDisabled_largeBatchAllowed`), confirming the code path is live and not merely theoretical [7](#0-6) . Exploitability depends on the operator's configuration of `jsonRpcMaxBatchSize`, but the code allows a fully unbounded configuration, and even a "safe" positive value only linearly reduces (not eliminates) the amplification per rate-limited request.

### Recommendation
Enforce the rate limiter per JSON-RPC sub-request when handling a batch, not just once per HTTP POST — e.g., have `handleBatch` consult `RateLimiterContainer`/`GlobalRateLimiter` (or a dedicated cost-weighted acquisition proportional to `rootNode.size()`) before dispatching each sub-request, or account for the batch size as N permits up front in `RateLimiterServlet.service()`. Additionally, consider disallowing `jsonRpcMaxBatchSize <= 0` (unbounded) as a valid configuration, or impose a hard ceiling regardless of configuration.

### Proof of Concept
1. Configure a node with `jsonRpcMaxBatchSize = 0` (or any permissive value) and default rate limiter settings.
2. Send a single HTTP POST to the JSON-RPC endpoint containing a JSON array with N (e.g., 10,000) valid JSON-RPC requests (e.g., repeated `eth_blockNumber` calls), as exercised by `batchLimitDisabled_largeBatchAllowed` [7](#0-6) .
3. Observe that `RateLimiterServlet.service()` only consumes one permit for the entire request, while `JsonRpcServlet.handleBatch` executes all N RPC calls internally via `rpcServer.handleRequest` in a loop [8](#0-7) , producing N times the RPC work per rate-limited request compared to sending N separate single requests, which would each be individually throttled.

  private void handleSingle(HttpServletRequest req, HttpServletResponse resp,
      JsonNode rootNode, byte[] body, int maxResponseSize) throws IOException {
    CachedBodyRequestWrapper cachedReq = new CachedBodyRequestWrapper(req, body);
    BufferedResponseWrapper bufferedResp = new BufferedResponseWrapper(
        resp, maxResponseSize);

    try {
      rpcServer.handle(cachedReq, bufferedResp);
    } catch (RuntimeException e) {
      logger.error("RPC execution failed", e);
      writeJsonRpcError(resp, JsonRpcError.INTERNAL_ERROR, "Internal error",
          rootNode.get("id"), false);
      return;
    }

    bufferedResp.commitToResponse();
    if (bufferedResp.isOverflow()) {
      writeJsonRpcError(resp, JsonRpcError.RESPONSE_TOO_LARGE,
          "Response exceeds the limit of " + maxResponseSize + " bytes",
          rootNode.get("id"), false);
    }
  }

  private void handleBatch(HttpServletResponse resp, JsonNode rootNode, int maxResponseSize)
      throws IOException {

    ArrayNode batchResult = MAPPER.createArrayNode();
    int accumulatedSize = 2; // "[]"
    boolean overflow = false;

    for (int i = 0; i < rootNode.size(); i++) {
      JsonNode subRequest = rootNode.get(i);

      if (overflow) {
        if (!subRequest.isObject()) {
          batchResult.add(buildErrorNode(JsonRpcError.INVALID_REQUEST, "Invalid Request", null));
        } else if (subRequest.has("id")) {
          // Notifications (no "id") do not get a response even on overflow.
          batchResult.add(buildErrorNode(JsonRpcError.RESPONSE_TOO_LARGE,
              "Response exceeds the limit of " + maxResponseSize + " bytes",
              subRequest.get("id")));
        }
        continue;
      }

      if (!subRequest.isObject()) {
        ObjectNode errNode = buildErrorNode(JsonRpcError.INVALID_REQUEST, "Invalid Request", null);
        byte[] errBytes = MAPPER.writeValueAsBytes(errNode);
        int addition = errBytes.length + (!batchResult.isEmpty() ? 1 : 0);
        if (maxResponseSize > 0 && accumulatedSize + addition > maxResponseSize) {
          overflow = true;
        } else {
          accumulatedSize += addition;
        }
        batchResult.add(errNode);
        continue;
      }

      byte[] subBody;
      try {
        subBody = MAPPER.writeValueAsBytes(subRequest);
      } catch (JsonProcessingException e) {
        writeJsonRpcError(resp, JsonRpcError.INTERNAL_ERROR, "Internal error", null, true);
        return;
      }

      ByteArrayOutputStream subOutput = new ByteArrayOutputStream();
      try {
        rpcServer.handleRequest(new ByteArrayInputStream(subBody), subOutput);
      } catch (RuntimeException e) {
        logger.error("RPC execution failed for batch sub-request {}", i, e);
        writeJsonRpcError(resp, JsonRpcError.INTERNAL_ERROR, "Internal error", null, true);
        return;
      }

  public static boolean tryAcquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null || !r.tryAcquire()) {
        return false;
      }
    }
    return rateLimiter.tryAcquire();
  }

  public static boolean acquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null) {
        return false;
      }
      r.acquire();
    }
    rateLimiter.acquire();
    return true;
  }

  public static boolean acquirePermit(RuntimeData runtimeData) {
    return Args.getInstance().isRateLimiterApiNonBlocking()
        ? tryAcquire(runtimeData)
        : acquire(runtimeData);
  }
