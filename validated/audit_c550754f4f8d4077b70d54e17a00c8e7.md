### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash` (main/hot/position), letting replay-verify accept a wrong committed state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function relied on by db-tool's replay/verify pipeline (`storage/db-tool/src/replay_on_archive.rs`) to prove that locally re-executing archived transactions reproduces the exact result that was originally committed and signed into the transaction accumulator. It checks status, gas, write-set hash and event-root hash, but — by the code's own admission — it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the expected `TransactionInfo`. This is the same class of bug as the `ETHOracle`/`PythOracle` report: two independently-derived values that are supposed to represent the same quantity (the authenticated state root vs. the locally recomputed state root) are silently allowed to diverge because one of the two is never actually compared.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates a re-executed `TransactionOutput` against the trusted, accumulator-committed `TransactionInfo` for a given version. It checks:
- `status` [2](#0-1) 
- `gas_used` [3](#0-2) 
- write-set hash vs `state_change_hash` [4](#0-3) 
- event root hash [5](#0-4) 

It never compares `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or `position_state_checkpoint_hash` to anything computed locally. The function itself documents this gap explicitly: [6](#0-5) 

This function is not test-only scaffolding — it is the actual verification primitive used by the archive replay-verification tool: [7](#0-6) 

`execute_and_verify` re-executes a chunk of archived transactions with `AptosVMBlockExecutor`, then calls `ensure_match_transaction_info` to decide whether the replay matches the expected (archived, ledger-info-authenticated) `TransactionInfo`. Because the checkpoint-hash fields are excluded from the comparison, a re-executed chunk whose *write set and events* happen to match, but whose *derived Sparse-Merkle/Jellyfish state root* differs from the one actually committed and covered by the accumulator/`LedgerInfo` signatures, is reported as a **verified success**.

This is a genuine analog of the oracle bug: the "precision" invariant here is "the locally recomputed state root must equal the authenticated `state_checkpoint_hash` baked into the signed `TransactionInfo`/accumulator." One code path (write-set/event verification) enforces consistency; the parallel path (state-tree root verification) is silently skipped, exactly as `_PRECISION` was inconsistent between `ETHOracle` and `PythOracle`.

### Impact Explanation
Replay-verify and the archive-based verification tooling exist specifically to catch state-commitment divergence — e.g., non-determinism bugs in the JMT/Sparse-Merkle state-tree construction, storage schema bugs, or hidden consensus-breaking VM/state changes across versions. Because `state_checkpoint_hash` (and hot/position variants) is skipped, this class of divergence is invisible to the tool: it will report "replay OK" even though the recomputed ledger state differs from the authenticated one. That undermines the primary state-commitment integrity guarantee replay-verify is meant to provide, and could mask a live commit-corruption or hard-fork-only divergence bug until it manifests elsewhere (e.g. state sync/fast-sync consistency failures), rather than being caught by the dedicated verification path.

### Likelihood Explanation
The gap is unconditional (not merely behind a feature flag for the main `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields — only the newer `position_state_checkpoint_hash` path is behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), and is exercised on every call from `replay_on_archive.rs`, which is a production db-tool subcommand used for auditing archived history. No attacker interaction or privilege is required to trigger the missing check — it is a correctness bug in the verifier itself, triggered whenever a real state-root divergence bug exists elsewhere in the stack.

### Recommendation
Extend `ensure_match_transaction_info` to also assert that the locally recomputed state/hot-state/position-state checkpoint root(s) equal `txn_info.state_checkpoint_hash()` / hot / position checkpoint hash whenever the transaction is a checkpoint boundary, as the existing TODO comment already prescribes, before treating a replay as verified.

### Proof of Concept
1. Take an archived transaction chunk whose `TransactionInfo` records `state_checkpoint_hash = H1`.
2. Re-execute the same transactions with `AptosVMBlockExecutor` such that the write set and events happen to serialize identically (e.g., due to a bug in JMT root computation that does not affect the write-set bytes/BCS hash but does affect the derived Merkle root), producing a different actual state root `H2 != H1`.
3. Call `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_info, ...)` as done in `execute_and_verify` [8](#0-7) .
4. Observe `Ok(())` is returned because none of the checkpoint-hash fields are compared, even though the ledger state actually diverges from the accumulator-committed one — confirming replay-verify would falsely report success for a corrupted/incorrect state commitment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
