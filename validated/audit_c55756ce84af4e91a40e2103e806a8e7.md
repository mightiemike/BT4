### Title
Unbounded allocation from attacker-controlled array-size felt in deprecated syscall array reads causes sequencer abort - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo0 (deprecated) syscall array-decoding path reads an array length directly as a raw felt from VM memory — memory that is populated by the executing contract's own bytecode — and converts it straight into a `usize` that is then used to size a vector allocation, with no upper bound check against the amount of actual remaining/available memory.

### Finding Description
`read_felt_array` in the deprecated syscalls hint processor reads the array size as an arbitrary felt and passes it, only converted via `usize::try_from`, into `felt_range_from_ptr`: [1](#0-0) 

`felt_range_from_ptr` forwards this attacker-supplied `size` straight to `vm.get_integer_range(ptr, size)`, a cairo-vm library call, prior to any validation that `size` is a sane/reachable value: [2](#0-1) 

The sibling retdata path has the exact same shape: `read_execution_retdata` converts a felt (`retdata_size`) to `usize` (only checking it fits in `usize`, via `RetdataSizeTooBig`) and forwards it unchecked into `felt_range_from_ptr`/`get_integer_range`: [3](#0-2) 

This is structurally the same bug class as the referenced TensorFlow advisory: a length/size value taken from untrusted input is used to size a vector allocation (`reserve`/`with_capacity`-style call inside `get_integer_range`) before the code verifies that the declared size is actually backed by real data. A deployed Cairo0 contract's bytecode fully controls the felt written at the "array size" memory slot for syscalls such as `send_message_to_l1`, `emit_event`, or entry-point retdata — it can write an arbitrary huge value (e.g., close to `usize::MAX`) with O(1) Cairo steps, since writing a felt to memory is cheap regardless of its numeric value.

By contrast, other array-reading code in the codebase (e.g., `apollo_cairo_utils`'s `CairoArray` deserialization) was hardened specifically against this pattern by validating the declared count against the number of remaining elements before allocating: [4](#0-3) 

No equivalent check exists in `read_felt_array` (deprecated syscalls) or in `read_execution_retdata` — they trust the felt-derived size as-is.

### Impact Explanation
If `vm.get_integer_range` (from the external `cairo-vm` crate) allocates its result buffer (e.g., via `Vec::with_capacity(size)`) before validating that `size` cells actually exist and are populated, then a malicious Cairo0 contract deployer/caller can trigger an allocation request for an enormous number of `Felt` elements (each 32 bytes) using a single cheap transaction. This can cause the sequencer process to abort (allocation failure / OOM kill) while executing a single submitted transaction — i.e., a network-wide denial of service reachable by any unprivileged transaction sender who deploys or calls into a crafted Cairo0 contract, matching the "network unable to confirm new transactions" impact category.

Note: I was not able to directly inspect the internals of `cairo-vm`'s `get_integer_range` (it is an external dependency, not vendored in this repo/index), so I cannot fully confirm whether that function performs its own size-vs-memory bound check before allocating. This is the key remaining uncertainty for this finding — if `get_integer_range` already validates the range against actual segment bounds before allocating, the practical impact would be reduced to an ordinary bounded error return rather than an oversized allocation attempt.

### Likelihood Explanation
High reachability: any contract deployer can trivially write Cairo0 bytecode that sets an oversized array-length felt before invoking `emit_event`, `send_message_to_l1`, or returning from `__execute__`/`__validate__` with an oversized `retdata_size`. No special privileges, large gas expenditure, or race conditions are required — writing a single felt is O(1) regardless of its magnitude. The main mitigating uncertainty is whether the external VM crate already guards the allocation, which could not be confirmed from the indexed sources.

### Recommendation
Add an explicit sanity bound in `read_felt_array` and `read_execution_retdata` (and any other call sites of `felt_range_from_ptr`) that rejects a declared `size` exceeding the number of felts actually available in the relevant memory segment (analogous to the `num_remaining_felts` check already used in `apollo_cairo_utils`), before any allocation is attempted. Alternatively/additionally, cap `size` against a protocol-defined maximum (e.g., max calldata/event data length already enforced elsewhere via `EventLimits`) prior to calling into `felt_range_from_ptr`.

### Proof of Concept
1. Deploy a Cairo0 class whose `__execute__` (or any external entry point invoking `emit_event`/`send_message_to_l1`) writes an array-size felt of a very large value (e.g., `2^63 - 1`) followed by a data pointer, then invokes the syscall.
2. Submit an ordinary invoke transaction calling this entry point.
3. During execution, `read_felt_array` reads the oversized felt, converts it to `usize`, and calls `felt_range_from_ptr(vm, array_data_start_ptr, huge_size)`, which calls `vm.get_integer_range(ptr, huge_size)` — if this allocates before bounds-checking, the sequencer attempts a multi-exabyte allocation and aborts. pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
}

pub fn read_execution_retdata(
    runner: &CairoRunner,
    retdata_size: MaybeRelocatable,
    retdata_ptr: &MaybeRelocatable,
) -> Result<Retdata, PostExecutionError> {
    let retdata_size = match retdata_size {
        MaybeRelocatable::Int(retdata_size) => usize::try_from(retdata_size.to_bigint())
            .map_err(PostExecutionError::RetdataSizeTooBig)?,
        relocatable => {
            return Err(VirtualMachineError::ExpectedIntAtRange(Box::new(Some(relocatable))).into());
        }
    };

    Ok(Retdata(felt_range_from_ptr(&runner.vm, Relocatable::try_from(retdata_ptr)?, retdata_size)?))
}

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
