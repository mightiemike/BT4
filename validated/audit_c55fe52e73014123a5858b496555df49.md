### Title
Order-Dependent Mis-Attribution of Transferred Bandwidth/Energy Usage in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The `transferUsage` calculation performed when un-delegating bandwidth/energy computes a proportional share of the receiver's total accumulated usage using the **current** total frozen balance as denominator, without accounting for the fact that usage was accrued while the composition of frozen balances (self-frozen + delegated-from-multiple-owners) differed from its state at un-delegation time. This mirrors the EigenPodManager `_reduceSlashingFactor()` bug: a proportional-reduction ratio is computed from present-day aggregate balances instead of the balance/scaling state that was actually in effect when the quantity being reduced (usage / withdrawable shares) accrued, producing an order-dependent, incorrect result.

### Finding Description
In `UnDelegateResourceActuator.execute()` (and the TVM-reachable twin `UnDelegateResourceProcessor.execute()`), when a delegator un-delegates frozen balance from a receiver, the actuator computes how much of the receiver's accumulated bandwidth/energy `netUsage`/`energyUsage` must be "clawed back" and transferred to the un-delegating owner: [1](#0-0) 

```java
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
```

and identically for energy: [2](#0-1) 

The same formula is duplicated in the TVM native-contract path used by contract-invoked `unDelegateResource`: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported bug: `_reduceSlashingFactor()` computed
```
newBeaconSlashingFactor = prevBeaconSlashingFactor * (newRestakedBalanceWei / prevRestakedBalanceWei)
```
using only the *current* balances, ignoring that the deposit-scaling-factor (i.e., the historical composition/weighting of balances) had already changed between events (validator #2 staked after validator #1 was slashed). Here, `receiverCapsule.getNetUsage()` is a single aggregate counter that accrues bandwidth/energy consumption attributable to **whatever** frozen balance existed at the time usage occurred (self-frozen TRX, V1 delegated, and V2 delegated balances from potentially multiple different owners). `getAllFrozenBalanceForBandwidth()` is evaluated **at un-delegation time**, reflecting the current total, not the total that was in effect while usage accrued.

Concretely:
1. Owner A delegates balance `X` to Receiver. Receiver's `netUsage` accrues to `U` while `getAllFrozenBalanceForBandwidth() == X` (all usage is attributable to A's delegation).
2. Owner B subsequently delegates additional balance `Y` to the same Receiver (analogous to staking the second validator *after* the checkpoint/slash event in the report). Now `getAllFrozenBalanceForBandwidth() == X + Y`, but the already-accrued `U` bandwidth usage was consumed entirely against `X`, not `X+Y`.
3. Owner A un-delegates `X`. `transferUsage = U * (X / (X+Y))` — only a **fraction** of the usage that Owner A's balance actually incurred is clawed back, because the denominator now silently includes Owner B's freshly-added balance `Y`, which had no bearing on how `U` was generated.
4. The remainder of `U` incorrectly stays attributed to the Receiver's shared usage pool even though Owner B's un-consumed balance `Y` should not be diluting Owner A's attributable usage.

This produces a result that depends purely on **transaction ordering** (whether the second delegation happens before or after the usage was consumed, and before or after the un-delegation), exactly as in the report where the final withdrawable shares differed depending on whether a validator was verified before or after a checkpoint.

### Impact Explanation
This causes resource/usage accounting corruption reachable via a normal, unprivileged broadcast `UnDelegateResourceContract` transaction or a TVM contract calling the native `unDelegateResource` precompiled/native contract — no privileged role or leaked key required. The practical effect is that bandwidth/energy usage is mis-transferred between the owner and receiver accounts: the un-delegating owner can regain usable bandwidth/energy capacity ("Free" resource window) disproportionate to what they actually consumed, while the receiver's usage bookkeeping becomes desynchronized from its remaining frozen balance. Depending on the direction of the miscalculation, this can let an attacker who orchestrates multiple delegators/timing sequences either avoid legitimate usage decay (obtaining more free transactions than backed by frozen TRX — a resource-accounting/DoS-adjacent issue) or cause a receiver to be wrongly starved of usage capacity it is entitled to. Because usage windows also drive network-wide adaptive resource limits, systemic mis-accounting could compound across many delegation/un-delegation cycles.

### Likelihood Explanation
Reaching this code path requires only ordinary `DelegateResourceContract`/`UnDelegateResourceContract` transactions (or their TVM-native counterparts triggered from a smart contract), which are available to any account with sufficient TRX to freeze and delegate — no special permissions. Achieving the specific inconsistency requires a specific but easily reproducible sequence: delegate → accrue usage → additional delegation from a second owner → partial un-delegation. This ordering is fully attacker-controllable since delegation/un-delegation and transaction submission timing are under user control, making the likelihood of triggering the miscalculation moderate-to-high for a motivated actor, though the report's own upstream disposition (EigenLayer marked it "acknowledged, doc-only, no code fix") suggests the magnitude of exploitable value per occurrence may be limited without further quantification specific to java-tron's usage-window mechanics.

### Recommendation
Rework the `transferUsage` computation so it does not naively re-scale the receiver's *aggregate* `netUsage`/`energyUsage` by the *current* total frozen balance ratio. Instead, track/attribute usage per delegation relationship (or use a monotonic scaling factor recorded at the time usage was consumed, analogous to fixing `_reduceSlashingFactor()` by incorporating the deposit-scaling-factor at the time of the balance change) so that a later, unrelated delegation from a different owner cannot dilute the usage properly attributable to an earlier delegator during un-delegation. At minimum, apply `min(...)` bound checks against per-relationship delegated balances captured in `DelegatedResourceCapsule`, and add regression tests analogous to `UnDelegateResourceActuatorTest` that specifically cover interleaved multi-owner delegate/accrue-usage/un-delegate sequences to confirm usage clawback is order-independent.

### Proof of Concept
Conceptual sequence (extending the existing `testUnDelegateForBandwidth`/`testLockedAndUnlockUnDelegateForBandwidth` tests in `framework/src/test/java/org/tron/core/actuator/UnDelegateResourceActuatorTest.java`):
1. Owner A delegates `X` bandwidth-TRX to Receiver R. R consumes bandwidth so `netUsage = U`, with `getAllFrozenBalanceForBandwidth() == X`.
2. Owner B delegates `Y` bandwidth-TRX to the same Receiver R (no usage yet from B's share). Now `getAllFrozenBalanceForBandwidth() == X + Y`.
3. Owner A submits `UnDelegateResourceContract` to reclaim `X`.
4. Observe `transferUsage = U * (X / (X + Y))` per [5](#0-4)  instead of the full `U` that Owner A's delegation actually incurred, demonstrating usage is under-clawed-back from Receiver purely because Owner B's later, unrelated delegation changed the denominator.

Full exploitation quantification (exact numeric bandwidth/energy gain per TRX and downstream consensus effects) could not be fully verified within the available indexed code/tests; a Devin session with full repository/test-execution access would be needed to run the above scenario end-to-end and confirm concrete numeric deltas.
