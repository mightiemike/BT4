## Confirmed key detail

`build_updated_stake_reward` in `distribution.rs` looks up each `stake_pubkey` from `partitioned_stake_reward` in the **current** `stakes_cache_accounts` snapshot, and treats a missing entry as `DistributionError::AccountNotFound` rather than crashing — meaning "closed-account" divergence during normal (non-restart) distribution is already tolerated as a per-account error, not a fatal desync. [1](#0-0) 

However, that safety net only covers the *distribution* step for entries still present in the frozen `all_stake_rewards` list. It does **not** address the case in the question: `recalculate_stake_rewards`, invoked only via `initialize_after_snapshot_restore` on snapshot restore, rebuilds the entire `stake_delegations` list from the **live** `StakesCache` rather than reusing the frozen `all_stake_rewards` computed at the epoch boundary. [2](#0-1) [3](#0-2) 

`StakesCache::check_and_store` removes an entry from `stake_delegations` entirely once its lamports reach zero (e.g., via a legitimate `Withdraw` on a fully-deactivated stake account the attacker owns): [4](#0-3) 

### Title
Snapshot-restore reward recalculation reads live `StakesCache` instead of the frozen epoch-boundary reward list, causing bank divergence when an attacker closes their own stake account mid-calculation - ([File: runtime/src/bank/partitioned_epoch_rewards/mod.rs])

### Summary
`Bank::recalculate_stake_rewards`, reachable only through `initialize_after_snapshot_restore` on snapshot restore, rebuilds `PartitionedStakeRewards` from `self.stakes_cache.stakes().stake_delegations_vec()` — i.e. the bank's *current* live stake-delegation set — rather than replaying the frozen `all_stake_rewards` list produced by `begin_partitioned_rewards` at the epoch boundary. An unprivileged attacker who withdraws all lamports from their own already-deactivated stake account in a block between the epoch boundary and the snapshot slot causes that account to be removed from `StakesCache` (`check_and_store`, lines 99-116 of `stakes.rs`), so a node that restarts from a snapshot taken after that withdrawal computes a different `all_stake_rewards`/`partition_indices` set than a node that stayed in memory (or restarted before the withdrawal).

### Finding Description
- At the epoch boundary, `begin_partitioned_rewards` computes the epoch's `all_stake_rewards` once and freezes it into `Bank::epoch_reward_status` (`Calculation`/`Distribution` phase), and that frozen list is used for every subsequent distribution block for the rest of the epoch when the bank stays in memory. [5](#0-4) 
- `distribute_partitioned_epoch_rewards`, called each block while active, only re-derives `partition_indices` from the already-frozen `status.all_stake_rewards`; it never re-reads `StakesCache`. [6](#0-5) 
- The only code path that re-derives `all_stake_rewards` from scratch is `recalculate_stake_rewards`, called exclusively from `initialize_after_snapshot_restore` (bank construction from a snapshot). It pulls `stake_delegations` straight from `self.stakes_cache.stakes()` — the bank's current, potentially-mutated delegation set at the snapshot slot — via `get_epoch_params_for_recalculation`. [7](#0-6) 
- `StakesCache::check_and_store` unconditionally removes a pubkey's entry from `stake_delegations` once the account's lamports hit zero, which happens on a legitimate `Withdraw` of a fully-deactivated stake account owned by the attacker. [4](#0-3) 
- Consequently, if the attacker's `Withdraw` transaction lands in a block after the epoch-boundary Calculation snapshot but before the node stops and restarts, the restored bank's recalculated `stake_delegations_vec()` omits that account, so `calculate_stake_rewards_and_commissions` produces a `stake_rewards` vector that is shorter/reordered relative to the original in-memory list, and `hash_rewards_into_partitions` (which hashes over the vector) produces different `partition_indices`. [8](#0-7) 
- This divergence is not merely cosmetic: `distribute_epoch_rewards_in_partition`/`build_updated_stake_reward` use `partition_rewards.all_stake_rewards` and `partition_indices` to decide which accounts get credited lamports in which future block; a node with a different recalculated list will store different account states (and skip crediting the withdrawn account, or shift which accounts land in which partition/block) compared to a node that kept the original frozen list, producing different bank hashes for the same slot.
- The existing regression tests (`test_initialize_after_snapshot_restore`, `test_initialize_after_snapshot_restore_preserves_vat_filtered_rewards`, `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`) only validate that recalculation matches the original list when the stakes/vote data is *unchanged* or when specific denominator caching (`RewardEpochDelegatedStakes`) neutralizes a vote-account mutation; none of them cover an attacker-driven removal of a stake delegation between the epoch boundary and the snapshot/restart point. [9](#0-8) 

### Impact Explanation
A restarted validator's `epoch_reward_status` (and eventually the `EpochRewards` sysvar contents, stake account balances, and capitalization) can diverge from validators that stayed in memory through the same slots, purely as a side effect of one unprivileged staker withdrawing their own already-deactivated stake in the narrow window between the epoch boundary and a node restart. This falls into the "honest node's own snapshot generation/rebuild produces a bank disagreeing with full ledger replay" category — a consensus-divergence / bank-hash-mismatch bug, the most severe class in the Agave bounty program.

### Likelihood Explanation
Preconditions are attacker-controllable and require no privileged access: own a stake account that has already fully deactivated (from a prior epoch), issue a `Withdraw` for its full balance in any block after the epoch-boundary reward calculation snapshot, and have any validator restart-from-snapshot at a slot after that withdrawal but before the reward has been distributed for that account. Given ordinary validator restart cadence (crash-restart, catch-up-from-snapshot after outage, etc.), this is readily and repeatably triggerable by any staker at will, at every epoch boundary, without needing any timing coordination beyond one legitimate transaction.

### Recommendation
`recalculate_stake_rewards` should not reconstruct `stake_delegations` from the live `StakesCache`. Instead, either (a) persist/reserialize the frozen `all_stake_rewards` (and its `stake_delegations` inputs) as part of the serializable epoch-reward status so restore is a pure deserialize with no recomputation, or (b) snapshot the exact stake-delegation set (pubkeys + `Stake`) used at the epoch boundary alongside `stake_history`/`cached_vote_accounts`, and have recalculation iterate only over that frozen set rather than `stakes.stake_delegations_vec()`. If recomputation from live state must remain for size reasons, at minimum reconcile any stake accounts present in the original `all_stake_rewards` but absent from the current `StakesCache` (treat as zero-lamport already-distributed or explicitly re-add with their original entitlement) so the resulting list and partitioning are guaranteed identical regardless of subsequent account closures.

### Proof of Concept
Extend the existing `test_initialize_after_snapshot_restore` style test in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`:
1. Build a reward bank with several stake delegations (`create_reward_bank_with_specific_stakes`), advance to the epoch boundary so `bank.epoch_reward_status` is `Active(Calculation(..))`, capture `calculation_status.all_stake_rewards` as `original_rewards`.
2. In the next block, have one staker fully deactivate-then-withdraw (or, for a stake already deactivated in a prior epoch, just `Withdraw` the full balance) so their stake account's lamports hit zero, driving `StakesCache::check_and_store` to remove that delegation.
3. Simulate a snapshot restore on this bank (reset `feature_set`, call `bank.initialize_after_snapshot_restore(...)`) and capture the resulting `Distribution(distribution_status).all_stake_rewards`/`partition_indices`.
4. Assert `distribution_status.all_stake_rewards.num_rewards() != original_rewards.num_rewards()` (or that the withdrawn account's `PartitionedStakeReward` entry present in `original_rewards` is absent from `distribution_status.all_stake_rewards`), and that `hash_rewards_into_partitions` over the two lists produces different `partition_indices` for at least one remaining account — demonstrating the recalculated distribution schedule differs from what an uninterrupted, non-restarted bank would have used for the same slot range (violating `StartBlockHeightAndPartitionedRewards` / `SNAPSHOT_FIDELITY` equality).
