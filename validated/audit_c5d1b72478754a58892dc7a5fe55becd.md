### Title
`liquidity_cap` declared per-token on `TokenConfig` is never enforced anywhere in the inbound deposit / PRC20 mint path - (File: x/uexecutor/keeper/handler.go, x/uexecutor/keeper/evm.go)

### Summary
`TokenConfig.LiquidityCap` is documented as "max supply cap for this token" and is required to be non-empty by `ValidateBasic`, but no keeper code path (deposit, mint, or auto-swap) ever reads this value to compare it against cumulative minted/deposited amounts before calling `CallPRC20Deposit`. This is the same class of bug as the JOJO M-10 finding: a per-asset cap that exists conceptually in configuration/state but is enforced on none of the value-creating code paths, so an attacker (or simply organic usage) can mint unbounded PRC20 supply for a token whose registry entry claims a bounded cap.

### Finding Description
`TokenConfig` carries a `LiquidityCap` field intended to bound the supply of a bridged asset: [1](#0-0) 

`ValidateBasic` only checks that the string is non-empty — it never parses it as a big.Int, and no comparison against actual/minted supply ever happens at registration time or at runtime: [2](#0-1) 

Every inbound funds flow that mints PRC20 into the recipient (UEA, EOA, or CEA smart-contract recipient) routes through `depositPRC20`, which loads the token config only to resolve the PRC20 contract address — it does not read or check `LiquidityCap`: [3](#0-2) 

That in turn calls `CallPRC20Deposit`, which performs the derived EVM mint call with no supply-cap gate at all: [4](#0-3) 

A repo-wide search for any code that reads `LiquidityCap` outside of proto/config/tests confirms it is not referenced anywhere in `x/uexecutor` keeper logic, and there is no `TotalSupply`/`ExceedsCap`-style guard anywhere in the codebase — the field is fully decorative in the current implementation.

### Impact Explanation
If `liquidity_cap` is intended (per its own field comment and config files, e.g. `config/testnet-donut/*/tokens/*.json`) to bound how much PRC20 supply can exist for a bridged token, its absence from the mint path means any number of honest inbound deposits (or votes on inbounds, which are attacker-triggerable in the sense that any user can generate a source-chain deposit event that gets voted in by honest validators) can mint PRC20 supply far beyond the configured cap. This corrupts PRC20 accounting invariants and creates the exact "systemic risk" impact called out in the source report — no protocol-level ceiling exists on synthetic asset issuance despite governance/registry believing one is enforced, which directly matches the "corruption of PRC20 accounting" and "unauthorized mint" impact categories in scope.

### Likelihood Explanation
Likelihood is high in the sense that the condition requires no privileged access or malicious validator collusion — every honest inbound vote flow calls `depositPRC20`/`CallPRC20Deposit` unconditionally once 2/3 of honest Universal Validators vote an inbound as valid. The only way this "attack" manifests is organic/large-volume deposit traffic (or a user submitting large inbound amounts) that exceeds the intended cap; there is no artificial constraint stopping it. However, I could not fully verify whether an off-chain, non-scoped enforcement point exists (e.g., a relayer/vault-side rate limiter external to this repo, like the SVM gateway's own `rate_limit_config`/`token_rate_limit` PDAs seen in `universalClient/chains/svm/tx_builder.go`) that might be the actual intended enforcement mechanism for EVM-side liquidity caps, making the impact partially uncertain without further confirmation of the overall design intent for `TokenConfig.LiquidityCap` specifically (as opposed to the separate on-chain SVM gateway rate limiting, which is a different mechanism).

### Recommendation
Enforce `TokenConfig.LiquidityCap` in `depositPRC20` (or `CallPRC20Deposit`) by tracking cumulative minted supply per token (e.g., a new keeper-side supply counter, or a query to the PRC20 contract's `totalSupply()`), and reject/queue the inbound (mirroring the existing revert-instruction path) when a deposit would push supply above the configured cap — analogous to how `_isAccountSafeAfterBorrow` was recommended to be the single source of truth in the original finding. Alternatively, if `LiquidityCap` is meant to be purely informational/off-chain, it should be removed from the proto schema and validation to avoid the misleading appearance of an enforced protocol invariant.

### Proof of Concept
Conceptual trace (not independently executed, based on static code reading):
1. Register a `TokenConfig` with `liquidity_cap = "1000000"` (intended max supply) for `eip155:11155111` / USDC, as done in `test/integration/uexecutor/inbound_zero_amount_test.go` setup.
2. Submit N inbound deposit events (each validly signed/observed and voted PASSED by honest UVs) totaling far more than `1000000` in `Amount`.
3. Each inbound flows through `ExecuteInboundFundsAndPayload` → `depositPRC20` → `CallPRC20Deposit`, minting PRC20 tokens to the recipient every time, with no check against `tokenConfig.LiquidityCap` anywhere in this path. [5](#0-4) 
4. Resulting PRC20 total supply exceeds the configured `liquidity_cap`, with no error, no revert, and no on-chain record that the cap was ever consulted.

// ValidateBasic performs sanity checks on the TokenConfig
func (p TokenConfig) ValidateBasic() error {
	if strings.TrimSpace(p.Chain) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "chain cannot be empty")
	}

	if strings.TrimSpace(p.Address) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token contract address cannot be empty")
	}

	// Enforce a parseable address for the chain's namespace (e.g. 20-byte hex
	// for eip155, base58 for solana) so every registration lands on the
	// canonical storage key.
	if _, err := utils.CanonicalizeAddressByNamespace(p.Chain, p.Address); err != nil {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token address for chain %s: %s", p.Chain, err)
	}

	if strings.TrimSpace(p.Name) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token name cannot be empty")
	}

	if strings.TrimSpace(p.Symbol) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token symbol cannot be empty")
	}

	if p.Decimals == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "decimals must be greater than zero")
	}

	// Validate token_type is within known enum range
	if _, ok := TokenType_name[int32(p.TokenType)]; !ok {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token_type: %v", p.TokenType)
	}

	if strings.TrimSpace(p.LiquidityCap) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "liquidity_cap cannot be empty")
	}

	if p.NativeRepresentation == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "native_representation is required")
	}
	if err := p.NativeRepresentation.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid native representation")
	}

	return nil
}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
