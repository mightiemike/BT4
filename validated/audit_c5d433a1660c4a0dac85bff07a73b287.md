### Title
Unvalidated capability spend-type ratios in workflow metering can cause credit misallocation - ([File: core/services/workflows/metering/metering.go])

### Summary
The workflow metering subsystem splits a workflow execution's credit balance across multiple `CapabilitySpendType`s using per-capability ratios pulled from registry config. Like the `VaultRewardDistributor.distribute()` bug (which assumed `supplyRewardPoolRatio + borrowRewardPoolRatio == 1000` without enforcing it), `ratiosFromConfig()` and `creditToSpendingLimits()` never verify that the collected ratios sum to `1` before using them to derive per-spend-type credit limits.

### Finding Description
`ratiosFromConfig()` reads one ratio per configured `SpendType` from the capability's registry config map (`RatiosKey`) and returns them as a `map[capabilities.CapabilitySpendType]decimal.Decimal`, with no check that `sum(ratios) == 1`: [1](#0-0) 

These ratios are then applied directly to the total credit `amount` in `creditToSpendingLimits()` to compute each spend type's individual limit, again with no normalization or sum check — only a check that the *count* of ratios matches the *count* of spend types: [2](#0-1) 

If the configured ratios sum to less than `1`, part of the workflow's earmarked credit balance for that invocation is never assigned to any spend type — analogous to reward funds becoming "locked" and undistributed in the reported bug. If the ratios sum to more than `1`, the derived spend limits collectively exceed the actual credited amount, allowing a workflow's capability calls to consume more resources per credit than intended — an accounting/metering integrity issue equivalent to "misreporting" of billed amounts.

### Impact Explanation
Since credit deduction and spend-limit enforcement across capability spend types (e.g., HTTP, compute, gas) drive the workflow platform's billing/metering accuracy, an unvalidated ratio set leads to either under-utilized (effectively "locked"/wasted) credit balance or over-allocated spend limits that bypass the intended per-invocation cap. This is a metering/data-integrity defect: it does not directly compromise node keys or execute arbitrary code, but it can result in inaccurate billing enforcement for workflow executions.

### Likelihood Explanation
The ratios originate from capability registry configuration (`RatiosKey` in `capConfig`), which is described in the code comments as configurable "without redeploying a capability" specifically "to change spending ratios" — i.e., editable independent of capability code changes: [3](#0-2) 
A misconfiguration (or a workflow/capability config that is not carefully validated at write time) is sufficient to trigger the issue; no privileged node compromise is needed, only an incorrect config value reaching `creditToSpendingLimits`.

### Recommendation
In `ratiosFromConfig()` (or immediately after it in `creditToSpendingLimits()`), sum all resolved ratios and either (a) reject/mark the report into metering-mode-fallback (as already done for other invalid-ratio cases via `switchToMeteringMode`) if the sum deviates from `1` beyond a small epsilon, or (b) normalize each ratio by dividing by the sum before applying it to `amount`, ensuring the derived spend limits always total exactly the input credit amount.

### Proof of Concept
Given `info.SpendTypes = [A, B]` and registry config `RatiosKey = {A: "0.9", B: "0.9"}` (sum = 1.8):
1. `ratiosFromConfig` returns `{A: 0.9, B: 0.9}` with no error, since it only checks that a ratio exists for each spend type.
2. `creditToSpendingLimits(info, capConfig, amount)` computes `spendLimit_A = amount * 0.9` and `spendLimit_B = amount * 0.9`, totaling `1.8 * amount` in derived spend limits — 80% more spend capacity than the actual `amount` of credit reserved for the invocation.
3. Conversely, ratios `{A: 0.4, B: 0.4}` (sum = 0.8) silently leave 20% of the invocation's credit allocation unassigned to any spend type, similar to "locked" unattributed funds in the reported issue.
