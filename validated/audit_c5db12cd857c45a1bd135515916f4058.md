**Analysis:**

The premise assumes `EventDb::get_events_by_version`'s inability to distinguish "no key stored" from "zero events" can feed a corrupted or hidden divergence into the event accumulator root. That's not the case, because the event accumulator root for each version is never recomputed *from* `get_events_by_version`'s output for consensus or proof-verification purposes — it is computed once at execution time directly from the VM's `TransactionOutput::events()` and stored as an immutable field, `TransactionInfo::event_root_hash`, which becomes part of the (validator-signed) transaction accumulator leaf. [1](#0-0) 

Any consumer that needs to authenticate returned events (API responses, replay, restore verification) recomputes the event root from the *returned* event list and compares it against this already-committed `event_root_hash`, e.g. `verify_events_against_root_hash` and `TransactionOutput::ensure_match_transaction_info`: [2](#0-1) [3](#0-2) 

So if `get_events_by_version` (or the storage layer generally) silently returned an empty vector for a version that actually had events — whether due to a missing key, pruning, or any other omission — the recomputed root over that empty list would not match the non-empty `event_root_hash` already bound into the signed transaction accumulator, and verification would fail loudly rather than accept a corrupted root. This is exercised explicitly in replay/backup-verification code paths such as `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` and `verify_execution` in `execution/executor/src/chunk_executor/mod.rs`, both of which call `ensure_match_transaction_info` against externally supplied `expected_events`/`transaction_infos` before accepting a chunk as valid. [4](#0-3) [5](#0-4) 

In the restore path, events for each version come straight from the downloaded backup manifest chunk (`event_vecs`), not from a round-trip through `get_events_by_version`, and are saved together with the corresponding `TransactionInfo` whose `event_root_hash` was computed at original execution time — restore does not "reconstruct" the event root from `EventDb` state at all. [6](#0-5) 

The genuine ambiguity in `get_events_by_version` (version had zero events vs. version's keys are absent because they were legitimately pruned) is real, but it is purely a local query/indexing behavior and does not participate in accumulator-root recomputation, proof verification, or consensus-critical state. It also depends on an operator-driven pruning decision, not unprivileged transaction/API input, so it falls outside the scope of committed-state or proof-integrity corruption that this review targets.

/// Verifies a list of events against an expected event root hash. This is done
/// by calculating the hash of the events using an event accumulator hasher.
fn verify_events_against_root_hash(
    events: &[ContractEvent],
    transaction_info: &TransactionInfo,
) -> Result<()> {
    let event_hashes: Vec<_> = events.iter().map(CryptoHash::hash).collect();
    let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash();
    ensure!(
        event_root_hash == transaction_info.event_root_hash(),
        "The event root hash calculated doesn't match that carried on the \
                         transaction info! Calculated hash {:?}, transaction info hash {:?}",
        event_root_hash,
        transaction_info.event_root_hash()
    );
    Ok(())
