### Title
Webhook HMAC does not bind the `X-Shopify-Shop-Domain` header, enabling cross-tenant webhook forgery/replay - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`validateHmacFromRequestFactory` computes the webhook HMAC only over `rawBody` using the app-level `apiSecretKey`, and `checkWebhooksHeaders` then trusts the `X-Shopify-Shop-Domain` header verbatim without any cryptographic binding to that HMAC. Because the signing secret is shared across all shops that install the app (it is not per-shop), any party who legitimately receives one valid `rawBody`+`hmac` webhook for their own shop can replay it with a forged `domain` header pointing at a different shop, and downstream code (`ensureValidOfflineSession`, `process.ts`) will execute the handler with the victim shop's session/access token while the message body is fully attacker-controlled.

### Finding Description
`validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` calls `validateHmacString(config, rawBody, hmac, HashFormat.Base64)`, which computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it with `safeCompare` [1](#0-0) . This only covers `rawBody`, never `topic`, `domain`, `webhookId`, or `apiVersion`.

After HMAC validation succeeds, `validateFactory` calls `checkWebhookHeaders`, which for standard webhooks calls `checkWebhooksHeaders` [2](#0-1) . That function simply reads the `domain` header and returns it as trusted output with no relation to the HMAC computation [3](#0-2) .

Downstream consumers (`shopify-app-remix`/`shopify-app-react-router` `authenticateWebhookFactory`) take `check.domain` directly and use it to look up/refresh the offline session and construct the Admin API client for the handler: `const session = await ensureValidOfflineSession(params, check.domain);` [4](#0-3) , and `packages/apps/shopify-app-express` similarly builds the offline session id from the shop string with an explicit warning that it performs **no validation** on the shop value [5](#0-4) .

Exploit flow: the app's `apiSecretKey` used to sign webhooks is the same for every shop that installs the app (it's an app-level, not shop-level, secret). A merchant who installs the app on shop A will legitimately receive real, Shopify-signed webhook deliveries (valid `rawBody`+`hmac`) for shop A. Because the HMAC never covers the `domain`/`topic`/`webhookId` headers, that merchant can resend the exact same `rawBody`+`hmac` pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to `victim-shop.myshopify.com`. `checkWebhooksHeaders` and `validateHmacFromRequestFactory` both pass (HMAC is still valid for the unchanged body), and the returned `domain` is the forged victim shop. The app's handler then executes with the victim's offline session/access token (if a session exists), processing attacker-controlled body content under the victim's tenant context. Note: the "Notifications test" premise in the prompt is not itself a valid path (the docs explicitly state admin-triggered test webhooks fail HMAC validation) [6](#0-5) , but the underlying header-forgery weakness is real and reachable via any shop that has genuinely installed the app.

### Impact Explanation
This is a cross-tenant impact: an unprivileged party controlling one installed shop can forge webhook deliveries "for" any other shop known/guessable to them (shop domains are not secret), causing the app to invoke shop-specific webhook handler callbacks with a victim shop's `domain`/session context while supplying arbitrary attacker-controlled `rawBody`. If handler logic uses body data to make Admin API calls or persist data keyed by the (attacker-supplied) domain, this can result in cross-tenant data corruption, spoofed events, or actions taken using a victim's access token in response to attacker-fabricated content — matching a "cross-tenant session/data access" bounty class. It does not grant token theft or session forgery directly, and impact severity depends on how the consuming application's webhook handlers use the `domain`/body values, since the library itself does not perform any privileged action based on `domain` beyond looking up a session.

### Likelihood Explanation
The attacker needs only to be a legitimate (even trial) merchant who installs the target app once, which is a very low bar and squarely within the "single merchant sending crafted requests" threat model. No secret leakage, no MITM, and no non-default configuration are required — this exists in the default `checkWebhooksHeaders`/`validateHmacFromRequestFactory` flow used by `shopify-api`, `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express`. It is fully repeatable (webhook deliveries recur regularly, e.g., `ORDERS_CREATE`), and forged replays can be resent indefinitely since there is no anti-replay/domain-binding check.

### Recommendation
Bind the shop domain (and ideally topic/webhookId) into the HMAC verification, or otherwise validate that the `X-Shopify-Shop-Domain` header matches a shop that this specific `webhookId`/subscription belongs to (e.g., cross-check against the registry created during `webhooks.register`, or require that a session already exists for the offline id derived from `domain` **before** trusting it, and additionally verify webhook uniqueness/replay via `webhookId` de-duplication per shop). At minimum, document/warn that `domain` is unauthenticated relative to the HMAC and that host apps must independently verify the shop is entitled to receive that specific webhook (e.g., confirm the shop has an active app installation and no replay of `webhookId`).

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/webhooks/test/domain-forgery.test.ts
import {validateFactory} from '../validate';
import {shopifyApi, LATEST_API_VERSION, LogSeverity} from '../../..';
import {createSHA256HMAC} from '../../../runtime/crypto';
import {HashFormat} from '../../../runtime/crypto/types';

test('forged domain header is accepted with a valid hmac for a different shop', async () => {
  const config = shopifyApi({
    apiKey: 'test',
    apiSecretKey: 'secret',
    scopes: ['read_products'],
    hostName: 'localhost',
    apiVersion: LATEST_API_VERSION,
    isEmbeddedApp: true,
    logger: {level: LogSeverity.Debug},
  });

  const rawBody = JSON.stringify({id: 1, malicious: true});
  const hmac = await createSHA256HMAC(
    config.config.apiSecretKey,
    rawBody,
    HashFormat.Base64,
  );

  // This is a legitimately delivered webhook for attacker-owned "shop-a.myshopify.com"
  const forgedRequest = {
    rawBody,
    rawRequest: {
      headers: {
        'X-Shopify-Hmac-Sha256': hmac,
        'X-Shopify-Topic': 'products/create',
        // Attacker rewrites the domain to the victim shop instead of their own
        'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com',
        'X-Shopify-API-Version': LATEST_API_VERSION,
        'X-Shopify-Webhook-Id': 'forged-id',
      },
    },
  };

  const result = await validateFactory(config.config)(forgedRequest as any);

  // Currently PASSES (valid: true, domain: 'victim-shop.myshopify.com'),
  // demonstrating the HMAC does not bind the shop domain claim.
  expect(result.valid).toBe(true);
  if (result.valid) {
    expect((result as any).domain).toBe('victim-shop.myshopify.com');
  }
});
```
Expected secure behavior: validation should fail, or `check.domain` should not be trustable for session lookup without additional binding, so `ensureValidOfflineSession`/handler execution does not proceed against `victim-shop.myshopify.com` using attacker-supplied content signed only for the attacker's own shop.
