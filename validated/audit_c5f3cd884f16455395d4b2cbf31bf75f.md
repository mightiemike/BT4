This confirms `storeSession` is invoked repeatedly over the lifetime of a session — every offline/online session token exchange in `token-exchange.ts` and every automatic offline-token refresh in `ensure-offline-token-is-not-expired.ts` (called near expiry, e.g. every ~5 minutes of app usage) calls `config.sessionStorage!.storeSession(...)`, which for the `shopify-app-session-storage-kv` package unconditionally appends the session id to the shop's id list without deduplication.

### Title
Unbounded, unde-duplicated growth of per-shop session-id list causes denial-of-service in KV session storage - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
### Finding Description
`KVSessionStorage.storeSession` calls `addShopIds(session.shop, [session.id])` on every store, and `addShopIds` blindly concatenates the new id(s) onto the existing array without checking for duplicates: [1](#0-0) 
This is unlike the sibling `shopify-app-session-storage-redis` adapter, whose equivalent `addKeyToShopList` explicitly checks `if (!idKeysArray.includes(idKey))` before pushing: [2](#0-1) 

`storeSession` is called repeatedly for the *same* deterministic offline session id (`offline_${shop}`) throughout the app's normal, unprivileged lifecycle:
- On every token-exchange authentication when the cached session is missing/expiring: [3](#0-2) 
- On every offline-token refresh near expiry (every request within `WITHIN_MILLISECONDS_OF_EXPIRY` of token expiry, i.e., roughly every 5 minutes while the app is actively used): [4](#0-3) 

Because the id is the same string each time, this is a direct analog of the reported bug class: an unbounded loop/array that grows without bound as legitimate requests accumulate over time, eventually causing failures — just as the Aura report describes a for-loop over `rewardEpochs` growing without bound as epochs pass with no claim. Here the `shop:<shop>` KV value (a JSON array of ids) grows by one entry per `storeSession` call forever, since nothing ever deduplicates entries (only `deleteSession`/`removeShopIds`, called far less often, filters the array).

### Impact Explanation
Every `findSessionsByShop` call (used by `AppInstallations.includes`/`delete` in the Express package, invoked from auth and app-uninstalled webhook handling) fetches this ever-growing id array and runs `Promise.all(sessionIds.map(loadSession))` over it: [5](#0-4) [6](#0-5) 
As the array size grows unbounded (duplicate entries for the same offline session accumulate every few minutes indefinitely for a long-lived install), this causes:
1. Increasing latency/compute cost on every `findSessionsByShop` call (duplicate `loadSession` fetches), degrading the auth/uninstall handling path over time.
2. Eventual failure once the underlying KV value size limit (e.g., Cloudflare KV's 25 MiB per-value limit) is exceeded, causing `namespace.put` in `addShopIds`/`storeSession` to fail — breaking the token-exchange/refresh authentication path entirely for that shop (DoS of the auth handler), consistent with the "transaction always fails" pattern described in the source report.

### Likelihood Explanation
This requires no privileged actor or leaked secret — it happens automatically for any shop with a long-running, actively-used installation using the KV session storage adapter, purely as a byproduct of the built-in offline-token refresh cadence (every ~5 minutes near expiry) and re-authentication flow. No malicious intent is even required, though a malicious/curious merchant could accelerate it by repeatedly forcing re-auth (e.g., clearing session storage cookies is not even needed—simply causing repeated token-exchange calls near token expiry accelerates the array's growth deterministically).

### Recommendation
In `addShopIds`, deduplicate before writing, mirroring the Redis adapter's pattern:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```
Additionally, consider bounding the size of `findSessionsByShop`'s fan-out (e.g., paginating or capping) so a corrupted/oversized list cannot exhaust compute on lookup.

### Proof of Concept
1. Install the app on a shop using `KVSessionStorage`.
2. Repeatedly trigger the app's authenticated admin route (e.g., load the embedded app) so that `ensureOfflineTokenIsNotExpired` / `TokenExchangeStrategy.authenticate` calls `storeSession(offlineSession)` with the same `offline_<shop>` id multiple times (each refresh cycle, ~every 5 minutes while token is near expiry, or by simulating many token-exchange calls in a test).
3. Inspect the KV value at key `shop:<shop>` — observe the array contains the same session id duplicated once per `storeSession` call, growing without bound over the app's lifetime.
4. Call `findSessionsByShop(shop)` — observe it performs one `loadSession` per duplicate entry, and confirm the KV value eventually approaches/exceeds the KV namespace's per-value size limit, causing subsequent `storeSession`/`addShopIds` writes (part of the OAuth/token-exchange authentication path) to fail.
