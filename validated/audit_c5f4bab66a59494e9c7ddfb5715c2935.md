### Title
Unbounded `crossbeam_channel` in `MultithreadRuntimeHandle` allows unprivileged OOM via `broadcast_tx_async` — (`core/async/src/multithread/runtime_handle.rs`)

### Summary

An unprivileged attacker can flood the `broadcast_tx_async` JSON-RPC endpoint faster than the `RpcHandlerActor` consumes messages. Because the backing channel is `crossbeam_channel::unbounded()` and the HTTP path has no rate limiting or backpressure, the actor's message queue grows without bound until the process OOMs or block processing stalls.

### Finding Description

`spawn_multithread_actor` creates an unbounded crossbeam channel: [1](#0-0) 

The `CanSend<M>` implementation for `MultithreadRuntimeHandle` enqueues into this channel with no capacity check and no backpressure: [2](#0-1) 

`send_tx_async` in the JSON-RPC handler calls `process_tx_sender.send()` — a fire-and-forget enqueue — and immediately returns the transaction hash to the caller: [3](#0-2) 

`RpcHandlerActor` is backed by exactly this `MultithreadRuntimeHandle`: [4](#0-3) 

Each enqueued `MultithreadRuntimeMessage` boxes a closure that captures the full `SignedTransaction`. The `RpcHandlerActor` threads perform signature verification, nonce lookup, and balance checks before consuming each message — work that is orders of magnitude slower than the HTTP layer can accept new requests.

The network-level rate limiting in `messages_limits.rs` applies only to P2P peer messages, not to HTTP JSON-RPC requests: [5](#0-4) 

The `StateRequestActor` has its own throttle, but no equivalent guard exists on the `broadcast_tx_async` → `RpcHandlerActor` path: [6](#0-5) 

The `limits_config` in the JSON-RPC server controls only the HTTP request body size (default 10 MB), not request rate or queue depth.

### Impact Explanation

An attacker who can reach the RPC port (standard public endpoint) can submit `broadcast_tx_async` requests in a tight loop. Each request enqueues one heap-allocated `Box<dyn FnOnce>` capturing a `SignedTransaction`. With no bound on the channel and no rate limit on the HTTP path, the queue grows until:

- The node process OOMs and crashes, or
- The OS kills the process, halting block production and consensus participation for that node.

This is a non-network-level DoS fixable without a hardfork.

### Likelihood Explanation

The `broadcast_tx_async` endpoint is publicly documented and intentionally unauthenticated. No valid signature or account balance is required to enqueue a message — validation happens inside the actor after enqueue. A single attacker with a fast HTTP client can saturate the queue before any worker thread drains it.

### Recommendation

1. Replace `crossbeam_channel::unbounded()` in `spawn_multithread_actor` with a bounded channel (e.g., `crossbeam_channel::bounded(N)`) and drop or back-pressure senders when the channel is full.
2. Alternatively, add an HTTP-layer rate limiter (e.g., Tower `RateLimitLayer` or `ConcurrencyLimitLayer`) specifically on the `broadcast_tx_async` / `send_tx` routes before the message reaches the actor.
3. Consider a per-IP or global request-rate limit at the Axum router level for all transaction submission endpoints.

### Proof of Concept

```rust
// Spawn a MultithreadRuntimeHandle with a slow handler (sleeps 100ms per message).
// Fire N=100_000 send() calls in a tight loop without consuming responses.
// Assert channel length >> 0 before any message is processed.

use crossbeam_channel::unbounded;
use std::thread;
use std::time::Duration;

let (tx, rx) = unbounded::<usize>();
// Simulate slow consumer
thread::spawn(move || {
    for msg in rx {
        thread::sleep(Duration::from_millis(100));
        let _ = msg;
    }
});
for i in 0..100_000 {
    tx.send(i).unwrap(); // never blocks, heap grows
}
assert!(tx.len() > 10_000); // queue far exceeds safe threshold
```

In the real nearcore path: replace the slow consumer with `RpcHandlerActor::process_tx`, replace `tx.send(i)` with repeated HTTP POST to `broadcast_tx_async`, and observe RSS growth until OOM.

    /// Returns true if this request needs to be **dropped** due to exceeding a
    /// rate limit of state sync requests.
    fn throttle_state_sync_request(&self) -> bool {
        let mut timestamps = self.state_request_timestamps.lock();
        let now = self.clock.now();
        while let Some(&instant) = timestamps.front() {
            // Assume that time is linear. While in different threads there might be some small differences,
            // it should not matter in practice.
            if now - instant > self.throttle_period {
                timestamps.pop_front();
            } else {
                break;
            }
        }
        if timestamps.len() >= self.num_state_requests_per_throttle_period {
            return true;
        }
        timestamps.push_back(now);
        false
    }
