### Title
Withdraw of a PRC20 with a chain ID that doesn't match its registered origin chain permanently strands the underlying value with no compensating outbound - (File: `x/uexecutor/keeper/create_outbound.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
The external report describes a bridge that burns/locks the token on the source side (via `sendERC721UsingNative`) and then fails to construct the corresponding outbound payload because it resolves metadata from the wrong (origin vs. wrapped) contract address, permanently losing the asset. The same failure class exists in Push Chain's outbound-creation path: `BuildOutboundsFromReceipt` resolves the external-chain token identity for a withdrawn PRC20 via `GetTokenConfigByPRC20(ctx, event.ChainId, event.Token)` [1](#0-0) , which only succeeds if the token config's registered `Chain` exactly equals the destination `event.ChainId` the user (or their payload) specified. Because a PRC20 is registered under exactly one origin chain ("PRC20 addresses are globally unique by construction") [2](#0-1) , any withdrawal that specifies a `ChainId` other than the token's exact registered chain causes this lookup to fail — after the PRC20 burn/transfer already executed successfully inside the EVM call that produced the receipt being parsed.

### Finding Description
`BuildOutboundsFromReceipt` decodes `UniversalTxOutboundEvent` from a successfully-executed EVM receipt and then requires a token-config match for `(event.ChainId, event.Token)`: [3](#0-2) 

If no config matches (wrong/unsupported destination chain for that PRC20), the function returns an error rather than a partial/aborting outbound. This error is surfaced through two different call paths, and in neither path is the already-committed burn undone:

1. **Module-driven path (payload-triggered outbound).** In `ExecuteInboundFundsAndPayload`, the UEA payload is executed via `ExecutePayloadV2`, which wraps the EVM call and fee deduction in its own `CacheContext` and commits it with `writeCache()` on success [4](#0-3) . Only *after* that commit does the keeper call `AttachOutboundsToExistingUniversalTx` (→ `BuildOutboundsFromReceipt`) to record the resulting outbound: [5](#0-4) 
If this fails, the only effect is `utx.RevertError = attachErr.Error()` — a string field with no consumer that triggers compensation, retry, or refund. The PRC20 burn/transfer performed by the payload's EVM call has already been committed to state; no `OutboundTx` is ever attached to the UTX, so the value is not routed to any destination and there is no protocol-level path to recover it.

2. **Direct EVM-transaction path.** `EVMHooks.PostTxProcessing` runs after *every* EVM transaction (not just module-derived calls) and calls `CreateUniversalTxFromReceiptIfOutbound` whenever a `UniversalTxOutbound` event is present in the receipt: [6](#0-5) 
`CreateUniversalTxFromReceiptIfOutbound` calls `BuildOutboundsFromReceipt` before any `UniversalTx` is created [7](#0-6) ; if the token-config lookup errors, the function returns the error immediately and **no UniversalTx record is created at all** — there isn't even a `RevertError` breadcrumb — despite the withdrawing EVM transaction (and its underlying PRC20 burn) having already succeeded and been included in the block.

This is directly analogous to the external report's root cause: a bridging/withdraw flow performs the destructive action on the source representation, then fails to construct the accompanying cross-chain payload/outbound because of an address/chain mismatch in the lookup used to build that payload — permanently orphaning the value.

### Impact Explanation
An ordinary, unprivileged user who withdraws a PRC20 (directly via a gateway call, or via a UEA/CEA-executed universal payload) with a destination chain ID that does not exactly match the token's single registered origin chain causes the PRC20 to be burned/transferred on Push Chain with no corresponding `OutboundTx` ever created. There is no automatic refund, retry, or rescue path triggered by this specific failure mode (the `RESCUE_FUNDS`/`AttachRescueOutboundFromReceipt` path requires a distinct `RescueFundsOnSourceChain` event that this failure never emits, and it also requires a pre-existing REVERTED `INBOUND_REVERT` outbound or a FAILED CEA deposit, neither of which applies here). This is a permanent loss/freezing of user funds, matching the in-scope impact category.

### Likelihood Explanation
Reachable by any unprivileged user via a normal withdraw/outbound flow — no validator, TSS, or admin misbehavior required. Triggering it plausibly requires the EVM-side gateway/UEA logic to accept a `chainId` parameter for the withdraw that is not strictly validated against the PRC20's registered origin chain (this validation boundary lives in the EVM contract, which is outside this Go repository but is called by scoped module code as the sole gate for the resulting outbound). Because the Go-side registry enforces a strict one-PRC20-to-one-chain mapping while the outbound-construction code only detects the mismatch *after* the burn has already committed, the failure mode is a straightforward mismatch/validation-ordering bug rather than a hypothetical edge case.

### Recommendation
- Validate the destination `ChainId` against the PRC20's registered origin chain (via `GetTokenConfigByPRC20` with a chain-agnostic lookup, or by exposing the token's canonical chain and comparing) **before** the EVM-side burn/transfer commits, so a mismatched withdrawal reverts atomically instead of the value being consumed with no outbound created.
- For paths where the burn has already committed by the time `BuildOutboundsFromReceipt` runs (e.g., `ExecutePayloadV2`'s inner cache-commit), wrap the whole withdraw-and-outbound-construction sequence in a single `CacheContext` that is only committed once both the EVM burn and outbound construction succeed, mirroring the existing "deposit vs. fee/payload" cache pattern already used elsewhere in this module (`ExecutePayloadV2`, `ExecuteInboundFundsAndPayload`'s CEA branch).
- For the direct-EVM-transaction path (`EVMHooks.PostTxProcessing`), ensure a token-config mismatch produces a discoverable, protocol-visible failure record (e.g., a UTX/audit entry) instead of silently returning an error with no created UTX.

### Proof of Concept
1. Admin registers PRC20 `P` with `TokenConfig{ Chain: "eip155:11155111" (Sepolia), Address: <sepolia token>, NativeRepresentation.ContractAddress: P }`.
2. A user acquires balance of `P` on Push Chain (via normal inbound flow).
3. The user withdraws `P` by calling the UniversalGatewayPC withdraw entry point (directly, or through a UEA/CEA payload) specifying `chainId = "eip155:137"` (Polygon) instead of Sepolia — a value not registered for `P`.
4. The EVM-side gateway call burns/transfers `P` from the user and emits `UniversalTxOutboundEvent{ ChainId: "eip155:137", Token: P, ... }`; the EVM transaction succeeds and commits.
5. `BuildOutboundsFromReceipt` calls `GetTokenConfigByPRC20(ctx, "eip155:137", P)`, which returns `collections.ErrNotFound` because `P`'s only registered chain is Sepolia [8](#0-7) .
6. Depending on call path:
   - If triggered by a normal EVM tx: `CreateUniversalTxFromReceiptIfOutbound` returns the error before creating any `UniversalTx`; no record of the withdrawal or its failure exists.
   - If triggered via a UEA payload: `AttachOutboundsToExistingUniversalTx` fails and only sets `utx.RevertError`; the burn performed inside `ExecutePayloadV2`'s already-committed cache stands, with no outbound ever attached.
7. The user's `P` balance is gone with no destination-chain delivery and no automated recovery mechanism.

func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")

// GetTokenConfigByPRC20 looks up a token config by PRC20 address via the
// PRC20Index (O(1)). Returns ErrNotFound if the registered chain doesn't match.
func (k Keeper) GetTokenConfigByPRC20(
	ctx context.Context,
	chain string,
	prc20Addr string,
) (types.TokenConfig, error) {

	if strings.TrimSpace(prc20Addr) == "" {
		return types.TokenConfig{}, fmt.Errorf("prc20 address is empty")
	}
	// Same canonical form as the index function, so any case variant hits the row.
	prc20Addr = canonicalPRC20(prc20Addr)

	// PRC20 addresses are globally unique by construction; MatchExact returns at most one.
	iter, err := k.TokenConfigs.Indexes.PRC20Index.MatchExact(ctx, prc20Addr)
	if err != nil {
		return types.TokenConfig{}, err
	}
	defer iter.Close()

	for ; iter.Valid(); iter.Next() {
		pk, err := iter.PrimaryKey()
		if err != nil {
			return types.TokenConfig{}, err
		}
		cfg, err := k.TokenConfigs.Get(ctx, pk)
		if err != nil {
			return types.TokenConfig{}, err
		}
		if cfg.Chain == chain {
			return cfg, nil
		}
	}

	return types.TokenConfig{}, collections.ErrNotFound
}
