## Finding Analysis

Tracing `MsgExecutePayload`: [1](#0-0)  shows any unprivileged account can submit `MsgExecutePayload` naming an arbitrary `UniversalAccountId` (the victim's owner+chain identifier) — there is no check in `ValidateBasic` that `msg.Signer` must equal the owner encoded in `msg.UniversalAccountId`. [2](#0-1) 

In `Keeper.ExecutePayload`, `ueaAddr` is resolved purely from the `universalAccountId` via the factory (`CallFactoryToGetUEAAddressForOrigin`), i.e., it targets the victim's Universal Executor Account regardless of who calls the message. [3](#0-2) 

The payload is then executed with attacker-supplied `verificationData`, and critically:

```go
receipt, execErr := k.CallUEAExecutePayload(sdkCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

// Step 4: Deduct gas fees regardless of success/failure.
if feeErr := k.DeductGasFeesFromReceipt(ctx, sdkCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
    return fmt.Errorf("gas fee deduction failed: %w", feeErr)
}

if execErr != nil {
    return execErr
}
``` [4](#0-3) 

`DeductGasFeesFromReceipt` burns funds from `ueaAddr` as long as `receipt != nil` and `receipt.GasUsed > 0` — it does not check `execErr` at all: [5](#0-4) 

So if `CallUEAExecutePayload` produces a non-nil EVM receipt with `GasUsed > 0` before reverting (e.g., the contract-level verification of `verificationData` consumes gas before it fails), the fee is unconditionally charged against `ueaAddr` — the victim's smart account — even though `execErr != nil` indicates the payload was never actually authorized/executed.

Notably, `ExecutePayloadV2` (`execute_payload.go`) wraps the same sequence in a `CacheContext`, explicitly stating its purpose is to avoid a "free-execution gap," but it still commits the fee deduction on `execErr` paths as long as gas was used — it does not roll back gas charged on authorization failure either; it only rolls back if fee deduction itself fails. [6](#0-5)  This confirms the fee-for-attempt design is intentional across both entrypoints, not an oversight isolated to one function.

### Key uncertainty
I could not fully verify inside this session (i) whether `CallUEAExecutePayload`'s signature/authorization check inside the UEA contract reverts before or after non-trivial gas is spent (i.e., how much gas a garbage `verificationData` submission actually costs), and (ii) whether `CallFactoryToGetUEAAddressForOrigin` binds `ueaAddr` strictly to `universalAccountId` independent of `evmFrom`, or partially incorporates `evmFrom` into the derivation (limiting the blast radius to self-targeting only). The `evm.go` file containing `CallUEAExecutePayload`'s implementation and the actual UEA/factory contract bytecode were not available for confirmation, and I couldn't retrieve `precompiles/usigverifier` logic invoked during verification to quantify the gas consumed on failure.

Given the naming (`CallFactoryToGetUEAAddressForOrigin` operating on `universalAccountId`, which is the whole point of the "Universal Executor Account" abstraction — allowing relaying of payloads by arbitrary submitters on behalf of an owner elsewhere) and the absence of a `Signer == owner` binding check, the code structurally allows any unprivileged caller to name any victim's `UniversalAccountId` and force gas-fee deduction from that victim's UEA balance on failed/garbage authorization attempts, which matches the "fee-for-attempt regardless of success" comment in the code itself — but this being an intended design tradeoff versus an unauthorized drain hinges on the two unresolved points above.

### Title
Unconditional gas-fee deduction from `ueaAddr` on authorization-failed payloads enables unauthorized fund drain — (File: `x/uexecutor/keeper/msg_execute_payload.go`, `x/uexecutor/keeper/fees.go`)

### Summary
`ExecutePayload` charges gas fees to the resolved UEA (`ueaAddr`) based solely on `receipt.GasUsed`, without checking whether `execErr` indicates the UEA-level authorization/verification of `verificationData` failed, and without requiring `msg.Signer` to be the owner of the targeted `UniversalAccountId`.

### Finding Description
Any account can submit `MsgExecutePayload` specifying a victim's `UniversalAccountId`; the message signer need not be the account owner. `ExecutePayload` resolves `ueaAddr` from that identifier and calls `CallUEAExecutePayload` with attacker-controlled `verificationData`. Regardless of the resulting `execErr` (e.g. a contract-level revert from invalid verification), `DeductGasFeesFromReceipt` unconditionally burns gas fees from `ueaAddr` as long as the EVM receipt shows nonzero gas usage. This can force fee deduction from a victim's smart account balance purely by submitting payloads that fail authorization, at repeatable, low cost to the attacker (their own tx fee only).

### Impact Explanation
If confirmed (i.e., failed verification burns non-trivial gas, and UEA targeting isn't restricted to self), this allows unauthorized, repeatable draining of a victim's native `upc` balance with no successful execution and no consent, corrupting fee/gas accounting invariants and causing direct fund loss to the victim.

### Likelihood Explanation
Requires only standard `MsgExecutePayload` submission with garbage `verificationData` targeting a known/discoverable `UniversalAccountId`; no privileged role needed. Materiality depends on how much gas the on-chain verification path consumes before reverting.

### Recommendation
- Bind `msg.Signer`/`evmFrom` to the `UniversalAccountId.Owner` (or otherwise verify authorization) before charging fees, or
- Skip/limit `DeductGasFeesFromReceipt` when `execErr` stems from authorization/verification failure (as opposed to a legitimate contract-logic revert after successful authorization), or
- Cap the gas billed for verification-only failures to a small fixed amount rather than actual `GasUsed`, to bound worst-case drain per attempt.

### Proof of Concept
1. Attacker identifies any deployed UEA (`universalAccountId`) with a nonzero `upc` balance.
2. Attacker submits `MsgExecutePayload` with that `universalAccountId`, an arbitrary `universalPayload`, and garbage `verificationData`.
3. `CallUEAExecutePayload` performs on-chain verification, consumes gas, and returns `execErr != nil` with a receipt showing `GasUsed > 0`.
4. `DeductGasFeesFromReceipt` burns `gasCost` from `ueaAddr` per [7](#0-6) , before `execErr` is returned.
5. Repeat to drain the victim UEA's balance over multiple transactions, each costing the attacker only their own base Cosmos tx fee.

func (msg *MsgExecutePayload) ValidateBasic() error {
	// Validate signer
	if _, err := sdk.AccAddressFromBech32(msg.Signer); err != nil {
		return errors.Wrap(err, "invalid signer address")
	}

	// Validate universalAccountId
	if msg.UniversalAccountId == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal account cannot be nil")
	}

	// Validate universal payload
	if msg.UniversalPayload == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal payload cannot be nil")
	}

	// Validate verificationData
	if len(msg.VerificationData) == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "verificationData cannot be empty")

	if err := msg.UniversalAccountId.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universalAccountId")
	}

	// Validate universal payload structure
	if err := msg.UniversalPayload.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universal payload")
	}

	return nil
}

func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}
