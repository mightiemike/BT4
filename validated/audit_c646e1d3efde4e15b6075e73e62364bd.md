Based on the investigation, the strongest analog to the seed report ("using a wrong/stale field instead of the correct authoritative one") is a checkpoint-hash validation gap in `ensure_match_transaction_info`, which is the authenticated-proof-comparison routine used by state-integrity verification tooling (`replay-verify`, chunk-executor `verify_execution`).

### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay-verify accept a divergent state root as valid - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to authenticate a locally re-executed `TransactionOutput` against the authoritative, previously-committed `TransactionInfo` (the accumulator leaf). It is invoked by the chunk-executor's execution-verification path and by the `db-tool replay-on-archive` tool, both of which exist specifically to detect state divergence/hard forks between stored ledger data and fresh VM re-execution. The function checks status, gas, write-set hash, and event-root hash, but explicitly and admittedly (via an in-code `TODO`) omits comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields.

### Finding Description
`ensure_match_transaction_info` builds `write_set_hash` and `event_root_hash` from the freshly computed `TransactionOutput` and asserts equality against the corresponding fields of the authoritative `TransactionInfo`, but never re-derives or compares the state-checkpoint hash family: [1](#0-0) 

The comment inline states the exact consequence: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution": [2](#0-1) 

This routine is the sole per-transaction correctness gate in two state-integrity verification call sites:
- Chunk executor's `verify_execution`, which re-executes historical transactions and is expected to catch any divergence from the stored `TransactionInfo`: [3](#0-2) 
- `db-tool`'s `replay_on_archive`, the tool operators run to validate that an archive node's re-execution matches on-chain history exactly: [4](#0-3) 

Both callers treat an `Ok(())` return as full authentication of the re-executed output against the committed `TransactionInfo`, including any state-root fields it carries. Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a re-execution that produces a different Sparse-Merkle/hot-state/position root than what was originally committed — e.g. due to a nondeterminism bug, a subtle state-machine bug, or unintentional consensus-breaking change — passes verification silently as long as write-set bytes, events, gas, and status happen to match.

### Impact Explanation
This breaks the "Hard-fork-only divergence during commit, replay, restore, or proof verification" invariant: the tool whose entire purpose is to catch mainnet history/state divergence (`replay-verify`, execution verification mode) can affirmatively report a clean pass while the state root it computed has silently forked from the authenticated chain history. This directly weakens detection of state-integrity incidents, including retroactive detection of hard forks, meaning genuine committed-state divergence bugs could go unnoticed in the exact place designed to catch them.

### Likelihood Explanation
The gap only manifests when a real state-root divergence exists (rare on its own), but the check for it is *unconditionally* absent regardless of feature flags for the legacy `state_checkpoint_hash` field, and explicitly absent for `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` used by newer features (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, hot-state root in txn info). Likelihood of the underlying divergence is low, but the detection gap is deterministic and always present whenever `ensure_match_transaction_info` is relied upon.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/enabled) against the values carried by the authoritative `TransactionInfo`, as the existing TODO already recommends, before any feature that relies on `position_state_checkpoint_hash`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet.

### Proof of Concept
Not independently reproducible as a state-corrupting exploit from local code alone — this is a verification-completeness gap, not a write-path bug. Conceptually: run `db-tool replay-on-archive` (or chunk-executor `verify_execution`) against a transaction whose freshly-computed `TransactionOutput` has correct events/write-set/gas/status but a divergent state-checkpoint root (e.g. crafted via a state-computation bug elsewhere); `ensure_match_transaction_info` returns `Ok(())` despite the divergent root, and the tool reports the replay/verification as successful.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
