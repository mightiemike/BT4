### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash comparison, letting replay-verify tooling accept locally-diverged ledger state - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by non-consensus, state-integrity-auditing paths (`db-tool replay_on_archive`, `chunk_executor::verify_execution` via `VerifyExecutionMode`, `aptos-debugger`, and `aptos-move/cli`) to confirm that a freshly re-executed `TransactionOutput` matches the historical, already-committed `TransactionInfo`. As written, it compares status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newly-added `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks execution status, gas used, write-set hash, and event root hash against the persisted `TransactionInfo`, but the function's own trailing comment documents that it intentionally omits the checkpoint hashes:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is the sole per-transaction correctness gate in two important non-consensus integrity paths:
1. `db-tool`'s `replay_on_archive::execute_and_verify`, which re-executes archived transactions and is expected to catch any divergence between local VM execution and the historical, consensus-committed ledger state: [3](#0-2) 

2. `ChunkExecutorInner::verify_execution`, invoked whenever `VerifyExecutionMode` requests extra self-verification of chunk replay (used by backup restore's `verify_execution_mode`): [4](#0-3) 

Both call sites rely exclusively on `ensure_match_transaction_info` per-transaction and never separately compare `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` to the values embedded in the historical `TransactionInfo`. Because state (and, on the new native-trading subsystem, position-state) roots are only materialized at checkpoint boundaries and stored in `TransactionInfoV1`'s `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields [5](#0-4) , a divergence in the locally recomputed Sparse-Merkle/Jellyfish-Merkle state root (or the new native-position state root computed in `DoStateCheckpoint::compute_position_checkpoint`, [6](#0-5) ) relative to the authenticated historical root is never detected by this comparator. `replay_on_archive` and `verify_execution` will both report success ("replay verified") even though the locally-computed durable ledger state (accounts, position/orderbook state trees under the trading-native subsystem) has silently diverged from the value that was actually committed and consensus-authenticated on-chain.

This is distinct from the normal state-sync/consensus-driven chunk path (`StateSyncChunkVerifier::verify_chunk_result`), which builds the transaction accumulator from freshly-assembled `TransactionInfo`s (which do include the checkpoint hash fields, per `DoLedgerUpdate::assemble_transaction_infos` [7](#0-6) ) and compares the resulting accumulator root against the externally-verified target ledger info — that path *is* protected. The gap is specific to the `ensure_match_transaction_info`-based verification tools, which are the exact tools operators and auditors use to detect state divergence, corrupted/malicious archives, or executor bugs affecting historical or newly-added state trees (e.g., the native-position state root gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`).

### Impact Explanation
This breaks the "authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object" and "restore/replay paths must not reinterpret committed data into a different ledger state" invariants required by the state-integrity gate. A silent divergence in `state_checkpoint_hash` or `position_state_checkpoint_hash` — caused by an executor bug, a corrupted/tampered backup archive, or a bug specifically in the new native-position checkpoint logic — would go completely undetected by `replay_on_archive` and `verify_execution`, the primary tools relied upon to catch exactly this class of bug before/after a hard fork or during incident response. Because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a new, permanent-lifetime feature flag intended to commit the position-state root into consensus-verified `TransactionInfoV1`, any bug in `DoStateCheckpoint::compute_position_checkpoint` would be undetectable by the standard replay-verify workflow, i.e., a real state-corrupting divergence could pass verification as "correct," directly matching the "Committed state that differs from the correct VM result...accepted as valid" high/critical impact category.

### Likelihood Explanation
The gap is triggered by no attacker action; it exists any time replay-verify tooling is used to audit backup archives or perform chunk-replay self-verification, and it is explicit and self-acknowledged in the source (the code's own comment states this is a known, unaddressed limitation gating enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). Given that the comment explicitly says this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," if that feature flag were switched on in the current state, replay-verify/backup-verify workflows would provide a false sense of security for the entire native-position state tree.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally-recomputed `state_checkpoint_hash` (and, when features are enabled, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the corresponding fields of the passed-in `TransactionInfo`, at least at checkpoint-boundary versions, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network relying on `replay_on_archive`/`verify_execution` for integrity assurance.

### Proof of Concept
Not applicable as an exploit PoC — this is a verification-logic gap, not something exploitable via crafted transactions. The proof of the gap is structural/code-level:
1. `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2203) never reads `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`.
2. Both consumers — `replay_on_archive::execute_and_verify` (storage/db-tool/src/replay_on_archive.rs:373-405) and `ChunkExecutorInner::verify_execution` (execution/executor/src/chunk_executor/mod.rs:684-706) — treat `Ok(())` from this call as full confirmation that "replay matches history," with no supplementary checkpoint-hash check anywhere in either function.
3. The state/position checkpoint roots are computed separately in `DoStateCheckpoint` and only surface in the assembled `TransactionInfoV1` (execution/executor/src/workflow/do_ledger_update.rs:95-121), which these two verification tools never re-derive or compare independently.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",

            expected_events,

        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.

    fn compute_position_checkpoint(
        execution_output: &ExecutionOutput,
        parent: Option<&LedgerWithSummary<PositionStateWithSummary>>,
        persisted: &ProvablePositionStateSummary,
        known_position_state_checkpoints: Option<Vec<Option<HashValue>>>,
    ) -> Result<(
        LedgerWithSummary<PositionStateWithSummary>,
        Vec<Option<HashValue>>,
    )> {
        let _timer = OTHER_TIMERS.timer_with(&["get_position_checkpoint_hashes"]);

        let num_txns = execution_output.to_commit.len();
        let first_version = execution_output.first_version;
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();
        let base_summary = persisted.summary();
        // No in-memory parent at genesis / first block after enabling: seed
        // from the pre-committed position tip (covers committed writes the
        // merklized snapshot may lag).
        let parent_latest =
            parent.map_or_else(|| persisted.base().latest().clone(), |p| p.latest().clone());
        let parent_last_checkpoint = parent.map_or_else(
            || persisted.base().last_checkpoint().clone(),
            |p| p.last_checkpoint().clone(),
        );

        // Empty chunk: nothing to extend (avoids the `num_txns - 1` underflow).
        if num_txns == 0 {
            let summary = LedgerWithSummary::from_latest_and_last_checkpoint(
                parent_latest,
                parent_last_checkpoint,
            );
            return Ok((summary, vec![]));
        }

        // Collapse position writes (latest-per-key) over a version range into
        // SMT leaf updates.
        let collect = |range: std::ops::Range<usize>| -> Vec<(HashValue, PositionSlot)> {
            let mut latest: HashMap<HashValue, PositionSlot> = HashMap::new();
            for i in range {
                for (key, op) in execution_output.to_commit.transaction_outputs[i]
                    .write_set()
                    .native_position_iter()
                {
                    let value_hash = op.as_write_op().as_state_value_opt().map(StateValue::hash);
                    latest.insert(key.hash(), PositionSlot {
                        state_key: key.clone(),
                        value_hash,
                        value: None,
                    });
                }
            }
            latest.into_iter().collect()
        };

        let (new_latest, new_last_checkpoint) = if let Some(ci) = last_checkpoint_index {
            let checkpoint_version = first_version + ci as u64;
            let new_ckpt = parent_latest.extend(
                checkpoint_version,
                collect(0..ci + 1),
                base_summary,
                persisted,
            )?;
            if ci + 1 == num_txns {
                (new_ckpt.clone(), new_ckpt)
            } else {
                let last_version = first_version + num_txns as u64 - 1;
                let new_latest = new_ckpt.extend(
                    last_version,
                    collect(ci + 1..num_txns),
                    base_summary,
                    persisted,
                )?;
                (new_latest, new_ckpt)
            }
        } else {
            // No checkpoint in this chunk: only the latest advances.
            let last_version = first_version + num_txns as u64 - 1;
            let new_latest = parent_latest.extend(
                last_version,
                collect(0..num_txns),
                base_summary,
                persisted,
            )?;
            (new_latest, parent_last_checkpoint)
        };

        // Per-tx hash vector + known-hash validation (shared with main/hot state).
        let hashes = Self::get_state_checkpoint_hashes(
            execution_output,
            known_position_state_checkpoints,
            new_last_checkpoint.root_hash(),
            "position_state",
        )?;

        let summary =
            LedgerWithSummary::from_latest_and_last_checkpoint(new_latest, new_last_checkpoint);
        Ok((summary, hashes))
