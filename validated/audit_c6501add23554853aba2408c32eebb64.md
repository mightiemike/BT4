## Analysis

The 0x report's core defect pattern is: **a shallow gate check passes, and everything downstream is then trusted with no further validation of format/compatibility, opening the door to silent divergence when the trusted component's internal layout changes.** The closest reachable analog inside the permitted AccountsDB/bucket-map/index domains is in the disk-backed accounts-index bucket map's restart-reuse path.

`Restart::get_restart_file` does validate a `HEADER_VERSION`, `buckets` count, and `max_search` before trusting the shared restart-config mmap. [1](#0-0) 

But the actual per-bucket index/data files — which hold the real `IndexEntry<T>` payload (pubkeys, slot lists, ref counts) — are reused via `BucketStorage::load_on_restart`, which performs **no format/version validation at all**. It only checks that the file's byte length divided by the caller-supplied `elem_size` is non-zero, then blindly mmaps the file and reinterprets its bytes as `O::new(Capacity::Actual(num_elems))` entries. [2](#0-1) 

`elem_size` is computed fresh from the *currently running binary's* `size_of::<IndexEntry<T>>()` in `Bucket::new`, not read from the file itself: [3](#0-2) 

Once the shallow length check passes, `find_index_entry`, `keys()`, and all subsequent reads (`IndexEntryPlaceInBucket::new(ii)`, `.key(index)`, `get_slot_count_enum`) fully trust the reinterpreted bytes as correctly-laid-out entries — analogous to the 0x controller: once `sig == 0x415565b0` (the coarse gate) passes, "all possible calls are allowed. There is no further validation."

### Title
Disk accounts-index bucket files are reused across restarts without validating `IndexEntry<T>` layout/version compatibility - ([File: bucket_map/src/bucket_storage.rs])

### Summary
`BucketStorage::load_on_restart` reuses on-disk accounts-index bucket files (index and data buckets used by `AccountsIndex`'s disk-backed storage) purely based on a byte-length-vs-`elem_size` sanity check, with no stored format/version tag for the entry layout itself. `elem_size` is recomputed from the currently running binary's `size_of::<IndexEntry<T>>()`, not taken from the file. If the compiled `IndexEntry<T>`/`AccountInfo` layout changes between the run that wrote the file and the run that reuses it (e.g. across a validator software upgrade that changes struct size or field layout while the outer `Restart` header (`buckets`, `max_search`) still matches), the file is accepted and its raw bytes are reinterpreted under the new layout without any structural check.

### Finding Description
`Restart::get_restart_file` only gates reuse of the small restart-config mmap using `HEADER_VERSION`, `buckets`, and `max_search` [4](#0-3) 
It never records or checks `elem_size`/the layout version of `IndexEntry<T>` for the actual per-bucket data files that are reused via `RestartableBucket::get()` and `load_on_restart`: [5](#0-4) 

`load_on_restart` itself:
```
let num_elems = std::fs::metadata(&path).ok()
    .map(|metadata| metadata.len().saturating_sub(offset) / elem_size)?;
if num_elems == 0 { return None; }
let mmap = Self::map_open_file(&path, false, 0, &stats)?;
Some(Self { ..., contents: O::new(Capacity::Actual(num_elems)), delete_file_on_drop: false })
``` [2](#0-1) 
This is the only gate: file exists and its length is at least one `elem_size` unit. Once this passes, the mmap is trusted completely — every byte is treated as a validly-occupied-or-free `IndexEntry<T>`/`DataBucket` cell, and `keys()`, `find_index_entry`, `read_value`, etc. all deserialize directly from these bytes with no checksum, magic number, or explicit layout-version tag.

If `elem_size` (derived at compile/run time from `size_of::<IndexEntry<T>>()`) differs between the process that wrote the file and the process that reuses it — for instance following a validator binary upgrade that changes the generic value type used for the accounts index or reorders/adds fields in `IndexEntry<T>` — `num_elems` is computed incorrectly and every subsequent field access (`is_free`, `.key`, slot/ref-count decode) reads from the wrong byte offsets. The file is still accepted because the outer `Restart` header's `buckets`/`max_search` values are independent of this per-entry layout.

### Impact Explanation
Because this occurs in the disk-backed `AccountsIndex` used by `AccountsDb` (via `InMemAccountsIndex`/`BucketApi`), a mismatched reuse would corrupt pubkey/slot-list/ref-count entries read back into the accounts index during startup. This can produce stale or wrong-version account loads and could propagate to incorrect capitalization/hash calculations if corrupted index entries point at wrong storage offsets or slots (`AccountInfo` decode divergence), since `generate_index`/`accounts_index` rely on these entries being byte-accurate. [6](#0-5) 

### Likelihood Explanation
This requires no privileged actor or malicious snapshot — it is triggered purely by an honest node restarting the same on-disk bucket-map directory across a software upgrade that changes the index entry layout, while `restart_config_file`'s coarse header fields (`buckets`, `max_search`) happen to still match. Because `elem_size`/entry-layout compatibility is never persisted or checked, this can occur silently on any validator using the disk index feature across upgrades, without any explicit crash or error signal — the load simply "succeeds" per the existing check.

### Recommendation
Persist an explicit layout/format version (and ideally `elem_size`) for each bucket's index/data file, analogous to `Restart::Header.version`, and validate it against the current binary's expected layout in `BucketStorage::load_on_restart` before reusing the mmap. On mismatch, fail closed (delete/rebuild the file) rather than defaulting to blind reuse — mirroring the report's recommendation to allowlist/validate known-safe formats instead of accepting anything that passes a coarse check.

### Proof of Concept
1. Run a validator with disk-index enabled and a `restart_config_file` configured, producing bucket index files sized against the current `size_of::<IndexEntry<T>>()`.
2. Upgrade the validator binary such that `IndexEntry<T>`'s layout/size changes (e.g. a struct field change in the accounts-index value type) while `BucketMapConfig.max_buckets`/`max_search` remain unchanged.
3. Restart the validator against the same bucket-map directories. `Restart::get_restart_file` accepts the outer header (unchanged `buckets`/`max_search`), and `Bucket::new` → `load_on_restart` computes `num_elems` from the file length using the *new* `elem_size`, then mmaps and reinterprets old-layout bytes as new-layout `IndexEntry<T>` cells without any check.
4. Observe corrupted/garbage pubkey, slot, or ref-count fields being read back into the accounts index (verifiable by comparing `Bucket::keys()`/`items()` contents against the pre-upgrade set of pubkeys actually stored).

    /// load and mmap the file that is this disk bucket if possible
    pub(crate) fn load_on_restart(
        path: PathBuf,
        elem_size: NonZeroU64,
        max_search: MaxSearch,
        stats: Arc<BucketStats>,
        count: Arc<AtomicU64>,
    ) -> Option<Self> {
        let offset = Self::get_offset_to_first_data();
        let num_elems = std::fs::metadata(&path)
            .ok()
            .map(|metadata| metadata.len().saturating_sub(offset) / elem_size)?;
        if num_elems == 0 {
            return None;
        }
        let mmap = Self::map_open_file(&path, false, 0, &stats)?;
        Some(Self {
            path,
            mmap,
            cell_size: elem_size.into(),
            count,
            stats,
            max_search,
            contents: O::new(Capacity::Actual(num_elems)),
            // since we loaded it, it persisted from last time, so we obviously want to keep it present disk.
            delete_file_on_drop: false,
        })
    }

    pub(crate) fn new(

        max_search: MaxSearch,
        stats: Arc<BucketMapStats>,
        count: Arc<AtomicU64>,
        mut restartable_bucket: RestartableBucket,
    ) -> Self {
        let reuse_path = std::mem::take(&mut restartable_bucket.path);
        let elem_size = NonZeroU64::new(std::mem::size_of::<IndexEntry<T>>() as u64).unwrap();
        let (index, random, reused_file_at_startup) = reuse_path
            .and_then(|path| {
                // try to reuse the file this bucket was using last time we were running

                        count.clone(),

                        // we couldn't reuse it, so delete it
