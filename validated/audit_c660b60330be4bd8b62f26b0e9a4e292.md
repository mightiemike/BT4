### Title
Unhandled exception in `sanitizeHost` when decoding attacker-controlled `host` query parameter causes DoS of unauthenticated auth/embedded-app request handlers - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
This is the analog of the reported bug class: a validation function that is supposed to reject out-of-range/malformed input gracefully instead throws an uncaught exception when fed a boundary-case value, causing the calling flow to fail hard (DoS) instead of returning a clean rejection. In the Angle report, `LibHelpers.piecewiseLinear` reverted instead of handling collateral ratios below the first curve point. In shopify-app-js, `sanitizeHost` is meant to validate an untrusted, base64-encoded `host` query parameter and return `null` for anything invalid, but it does not guard the `new URL()` call against decoded content that fails hostname parsing, allowing an anonymous request to trigger an uncaught `TypeError` inside an authentication/embedded-app request handler.

### Finding Description
`sanitizeHost` first checks that the raw `host` string matches a generic base64 character-set regex, then unconditionally decodes it and constructs a `URL` object from it: [1](#0-0) 

`decodeHost` is a thin wrapper around `atob`, which will happily decode arbitrary base64 payloads into raw Latin-1 byte strings, including bytes/character sequences that are not valid hostnames (e.g. sequences that WHATWG's IDNA/host parser rejects): [2](#0-1) 

Because `base64regex` (`/^[0-9a-zA-Z+/]+={0,2}$/`) only validates the *encoding* of the input, not the *decoded content*, an attacker can craft a `host` value whose base64 form is syntactically valid but whose decoded bytes form a string that causes `new URL(https://${decodedHost})` to throw (WHATWG's URL/host parser throws a `TypeError` for hostnames it cannot parse, e.g. due to invalid Unicode/IDNA sequences). There is no `try/catch` around this call in `sanitizeHost`, so the exception propagates uncaught out of the function.

This function is called directly, without any surrounding try/catch, from multiple unauthenticated, request-facing code paths that read the `host` query parameter straight from the incoming HTTP request: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

These handlers are entered by any anonymous browser/agent hitting the app's embedded-auth entry point (e.g. `/`, `/auth`, or the app's authenticate.admin route) with a crafted `host` query string parameter — no session, cookie, or prior authentication is required to reach `sanitizeHost`.

### Impact Explanation
If the decoded host content triggers a `TypeError` inside `new URL()`, and the calling framework does not have a global unhandled-exception/error boundary that maps this specific throw to a clean 4xx response, the request-authentication code path (`validateShopAndHostParams`, `redirectToShopifyOrAppRoot`, Express's `redirectToAuth`) fails with an unhandled server error rather than the intended "invalid host -> null -> redirect to login/App Bridge" behavior. This is a denial-of-service class issue affecting the app's authentication entry point for any anonymous requester who can control the `host` parameter, analogous to the confirmed Medium-severity finding in the external report (a boundary/edge case not handled by the validation routine, causing the operation to abort instead of degrading gracefully).

### Likelihood Explanation
Likelihood depends on whether the specific runtime's URL implementation actually throws for some byte sequence that also passes the `[0-9a-zA-Z+/]+={0,2}` base64 regex — this needs to be confirmed empirically (e.g., fuzzing `atob` output through `new URL()`), which I could not execute given the tools available. The `base64regex` check does not validate UTF-8 or hostname-safe characters, so it is very plausible that some payloads decode into control characters, unpaired surrogates, or byte sequences that are invalid for `new URL()`'s host-parsing step. This mirrors the original report's root cause exactly: an underlying helper function assumes well-formed/expected-range input and lacks a defensive edge-case handler, and the calling code doesn't validate before invoking it.

### Recommendation
Wrap the decode-and-parse logic in `sanitizeHost` in a `try/catch` and return `null` (or throw `InvalidHostError` consistently, mirroring the `throwOnInvalid` contract) on any decoding/parsing failure, rather than letting `new URL()` or `atob` exceptions propagate to callers:
```ts
export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;
    let sanitizedHost = base64regex.test(host) ? host : null;

    if (sanitizedHost) {
      try {
        const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
        // ... existing regex validation using hostname
      } catch (_err) {
        sanitizedHost = null;
      }
    }

    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }
    return sanitizedHost;
  };
}
```

function clientSideRedirect(
  api: Shopify,
  config: AppConfigInterface,
  req: Request,
  res: Response,
  shop: string,
): void {
  const host = api.utils.sanitizeHost(req.query.host as string);
  if (!host) {
    res.status(500);
    res.send('No host provided');
    return;
  }

  const redirectUriParams = new URLSearchParams({shop, host}).toString();
  const redirectUri = `${api.config.hostScheme}://${api.config.hostName}${config.auth.path}?${redirectUriParams}`;

  redirectOutOfApp({config, api})({req, res, redirectUri, shop});
}

import {redirect} from 'react-router';

import type {BasicParams} from '../../../types';
import {AppDistribution} from '../../../types';

export async function redirectToShopifyOrAppRoot(
  request: Request,
  params: BasicParams,
  responseHeaders?: Headers,
): Promise<never> {
  const {api, config} = params;
  const url = new URL(request.url);

  const host = api.utils.sanitizeHost(url.searchParams.get('host')!)!;
  const shop = api.utils.sanitizeShop(url.searchParams.get('shop')!)!;

  let redirectUrl;
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    redirectUrl = `/?shop=${shop}&host=${encodeURIComponent(host)}`;
  } else {
    redirectUrl = await api.auth.getEmbeddedAppUrl({rawRequest: request});
  }

  throw redirect(redirectUrl, {headers: responseHeaders});
}
