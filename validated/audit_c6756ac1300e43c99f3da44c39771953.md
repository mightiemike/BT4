### Title
`check_microblock_header_signer` fails to enforce equal `sequence` between the two poisoned headers, allowing coinbase-forfeiture reports for non-equivocating microblocks - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`check_microblock_header_signer` (stackslib/src/chainstate/stacks/db/transactions.rs:686-713) only verifies that `mblock_hdr_1` and `mblock_hdr_2` recover to the same public-key hash; it never asserts `mblock_hdr_1.sequence == mblock_hdr_2.sequence`. `handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs:722-883) relies solely on this check before calling `insert_microblock_poison`, so any attacker who observes two distinct, validly-signed microblocks from the same miner — even non-conflicting ones at different sequence numbers — can submit them as a `PoisonMicroblock` payload and have the miner slashed.

### Finding Description
The intended equality for a valid poison-microblock report is: *two headers at the SAME `sequence` slot, signed by the same key, with different content* (a true equivocation/fork). The code instead only checks:

```
pkh1 == pkh2   // stackslib/src/chainstate/stacks/db/transactions.rs:704
``` [1](#0-0) 

There is no comparison of `mblock_hdr_1.sequence` against `mblock_hdr_2.sequence`, and no check that the two headers actually diverge from a common predecessor. `handle_poison_microblock` then unconditionally uses `mblock_header_1.sequence` as "the sequence at which the fork occurred" and stores it via `insert_microblock_poison`: [2](#0-1) [3](#0-2) 

Because `check_recover_pubkey` only validates the ECDSA signature over each header independently, two headers taken from the same honest, non-conflicting microblock stream (e.g., sequence 5 and sequence 9, both legitimately signed by the miner) satisfy `pkh1 == pkh2` trivially, since they were both signed by the same miner key. This lets any unprivileged participant who has observed two microblocks from a miner's normal stream file a `PoisonMicroblock` transaction and successfully call `insert_microblock_poison`, without any actual equivocation having occurred.

No other guard in the traced path (`check_microblock_header_signer`, the maturity check against `MINER_REWARD_MATURITY`, or the microblock-pubkey-hash lookup) validates sequence equality or checks that the headers are for conflicting forks rather than sequential, non-overlapping blocks.

### Impact Explanation
This is a reward mis-payment vulnerability: an honest miner who produced a normal, non-equivocating microblock stream can have their coinbase forfeited and the punishment credited to an attacker-controlled reporter principal, purely because the attacker submitted two validly-signed but non-conflicting headers. This is bounded to a single miner's coinbase (block-reward-adjacent, not a chain split, MARF divergence, or invalid-block-acceptance issue), matching the "poison or reward mis-payment" category. It is repeatable against any miner whose microblock pubkey hash is still within the maturity window, requires no majority stake, and needs only observation of two microblocks from the target miner's stream, which are public via the P2P network.

### Likelihood Explanation
Preconditions: the target miner must have registered a microblock pubkey hash via `insert_microblock_pubkey_hash` at a height within `MINER_REWARD_MATURITY` of the current height. The attacker needs no stake, no signer role, and no privileged access — merely the ability to observe two broadcast microblocks from the miner and submit a standard `PoisonMicroblock` transaction, which any account can do. This is trivially and repeatably exploitable against every actively-mining miner during the maturity window.

### Recommendation
In `check_microblock_header_signer`, additionally require `mblock_hdr_1.sequence == mblock_hdr_2.sequence` and that the header hashes actually differ (`mblock_hdr_1 != mblock_hdr_2`), rejecting the transaction otherwise so that only genuine same-slot equivocations qualify for a poison-microblock report.

### Proof of Concept
Rust integration test plan:
1. Register a miner's microblock pubkey hash via `insert_microblock_pubkey_hash` at height H.
2. Construct two microblock headers signed by the same miner key: `header_1` with `sequence = 5` and `header_2` with `sequence = 9`, both being legitimate, sequential, non-conflicting headers from a single honest stream (no shared predecessor conflict).
3. Build a `TransactionPayload::PoisonMicroblock(header_1, header_2)` transaction and run it through `process_transaction` → `handle_poison_microblock`.
4. Assert equality-before: `header_1.sequence (5) != header_2.sequence (9)`, i.e., no equivocation exists at any single sequence slot.
5. Assert equality-after: the call succeeds (`Ok(Value::Tuple(..))`), `get_microblock_poison_report`/`get_poison_microblock_report` records a report at `mblock_pubk_height`, and the miner's coinbase becomes forfeit — despite the absence of true equivocation, demonstrating the broken equality `poison reward paid == exactly one valid double-signature at the SAME sequence`.
