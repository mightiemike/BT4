### Title
Attacker-created pending outbound can permanently block `InitiateFundMigration`, freezing TSS-vault funds on a chain — ([File: x/utss/keeper/msg_initiate_fund_migration.go])

### Summary
`InitiateFundMigration` in `x/utss` refuses to open a fund-migration record for a chain if `HasPendingOutboundsForChain` reports any outstanding entry in `PendingOutbounds` [1](#0-0) . `PendingOutbounds` entries, by explicit design, are **only** removed on validator-quorum finalization of the outbound ballot and are never cleared by expiry [2](#0-1) . Because `x/uexecutor` also refuses to sign/broadcast any outbound once the destination chain's outbound flag is disabled — a precondition `InitiateFundMigration` itself enforces — an outbound created just before outbound-disable can never reach quorum and never leave `PendingOutbounds`. This is a direct analog of the Badger `MyStrategy._withdrawAll` bug: a single unprivileged, low-cost action ("dust") permanently locks the strict "balance must be zero" gate that full-fund migration depends on.

### Finding Description
The relevant guard: [3](#0-2) 

`HasPendingOutboundsForChain` walks the entire `PendingOutbounds` collection looking for any outbound whose `DestinationChain` matches the target chain: [4](#0-3) 

By design, a `PendingOutbounds` entry is created the moment an `OutboundTx` is generated (before any UV vote) and is **removed only when validator consensus is reached** on the observed result; ballot expiry deliberately does not clear it, and the README states resolution is meant to be governance-driven, not automatic: [5](#0-4) 

Separately, the Universal Validator's session manager refuses to sign an outbound transaction once outbound is disabled for its destination chain: [6](#0-5) 

`InitiateFundMigration` itself requires that outbound be disabled for the chain before a migration can be opened: [7](#0-6) 

Putting these together: any unprivileged user can, at negligible cost, submit a normal cross-chain inbound (e.g. `FUNDS_AND_PAYLOAD`/`PAYLOAD`) whose payload triggers creation of an outbound targeting the chain the operator will eventually want to migrate away from. As soon as the operator disables outbound for that chain (a mandatory, ordinary step before `InitiateFundMigration`), the pending outbound created by the attacker can never be signed or broadcast, so it can never reach the quorum vote that would remove it from `PendingOutbounds`. `HasPendingOutboundsForChain` will return `true` forever, and `InitiateFundMigration` will be permanently rejected with "chain %s still has pending outbounds; wait for them to drain before migration" [8](#0-7) .

The existence of a dedicated `app/upgrades/purge-expired-outbounds` chain upgrade in the repository (a governance-triggered migration whose purpose, per its name and match count for outbound-expiry logic, is to sweep stuck outbound entries) is corroborating evidence that this exact class of "stuck pending outbound" state has occurred in production and required a manual, privileged remediation rather than being self-healing.

### Impact Explanation
This is a legitimate analog of the Badger finding: an unprivileged actor can permanently deny a core protocol maintenance operation (TSS key rotation / fund migration) for a specific chain by spending a small amount to create one un-resolvable outbound before the chain's outbound is disabled. Since `KEYGEN` fund migration exists specifically to move funds off an old TSS key during a scheduled security rotation, permanently blocking it for one chain means funds custodied under the old TSS key on that chain can never be swept to the new key through the intended on-chain flow — a form of permanent freezing of protocol-custodied funds on that external chain, requiring a privileged, out-of-band governance upgrade (as the `purge-expired-outbounds` upgrade demonstrates) to recover.

### Likelihood Explanation
Triggering the underlying pending-outbound creation requires only a normal, unprivileged cross-chain transaction — no validator or admin collusion is needed. The blocking effect requires the outbound-disable step to occur after the attacker's outbound is created but before it resolves, which is a normal part of every migration's admin workflow, so a well-timed (or simply persistent) attacker can reliably win this race, especially since disabling outbound is a prerequisite the operator must perform every time a migration is planned.

### Recommendation
- Do not gate `InitiateFundMigration` on a strict "zero pending outbounds" invariant that a normal user action can hold hostage indefinitely. Instead, provide a governance/admin path to explicitly resolve or force-expire specific stuck `PendingOutbounds` entries for a chain (independent of the general `purge-expired-outbounds` upgrade path) before/while allowing migration to proceed, mirroring the Badger fix of allowing forced/partial sweeps instead of an all-or-nothing balance check.
- Alternatively, make outbound-disable itself refuse to leave outbounds permanently unsignable: allow signing to continue for outbounds that were already `PENDING` before the disable timestamp, or automatically fail/refund them through the standard finalize path so `PendingOutbounds` naturally drains.
- Add a bounded expiry-driven cleanup for `PendingOutbounds` (with proper double-pay/double-delivery protection, e.g. only expiring entries after independently confirming no delivery occurred) rather than leaving indefinite manual/governance-only resolution as the sole recovery mechanism.

### Proof of Concept
1. Attacker submits a low-value `FUNDS_AND_PAYLOAD`/`PAYLOAD` inbound whose payload triggers a destination-chain call, causing `x/uexecutor` to create an `OutboundTx` (`Status_PENDING`) and a matching `PendingOutbounds` entry for chain `C` [9](#0-8) .
2. Operator, following the normal migration runbook, disables outbound for chain `C` in `x/uregistry` (a step `InitiateFundMigration` itself requires) [7](#0-6) .
3. Any subsequent attempt by a Universal Validator to sign the attacker's still-pending outbound is now rejected: `"outbound disabled for chain %s, refusing to sign"` [6](#0-5) . The outbound can never reach `OutboundStatus_OBSERVED`, so `PendingOutbounds.Remove` in `msg_vote_outbound.go` is never called [10](#0-9) .
4. Operator calls `InitiateFundMigration(oldKeyId, "C")`; `HasPendingOutboundsForChain(ctx, "C")` returns `true` forever, and the call fails with `"chain C still has pending outbounds; wait for them to drain before migration"` indefinitely [1](#0-0) .

Note: I was not able to fully confirm within the available tool budget whether any code path outside `MsgVoteOutbound`'s normal success flow (e.g. a manual admin-revert or an outbound-specific force-fail message) exists that could unblock this state without a full chain upgrade; `admin_revert.go` in `x/uexecutor/keeper` appeared in search results and may be relevant to partial mitigation but was not inspected in detail.

```markdown
### `PendingOutbounds`

- **Created** by chain code at outbound creation in `create_outbound.go` —
  BEFORE any validator vote. The chain knows the outbound exists because it
  generated the destination-chain transaction itself; validators are tasked
  with observing whether/how it landed.
- **Keyed** by deterministic chain-derived `outbound_id`.
- **Variant-aware:** validator votes append `OutboundObservationVariant`s as
  they arrive (`RecordOutboundVote` inside `VoteOutbound`). Multiple variants
  per outbound indicate validator divergence on the destination-chain
  observation (different `success`/`tx_hash`/`error_msg`/`gas_fee_used`).
- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.
```

```go
// HasPendingOutboundsForChain checks if there are any pending outbounds for a given chain.
// It walks PendingOutbounds and joins against UniversalTx to check destination_chain.
// Returns true on first match. This is O(n) but only called during admin-initiated migration.
func (k Keeper) HasPendingOutboundsForChain(ctx context.Context, chain string) (bool, error) {
	var found bool
	err := k.PendingOutbounds.Walk(ctx, nil, func(outboundId string, entry types.PendingOutboundEntry) (bool, error) {
		utx, exists, err := k.GetUniversalTx(ctx, entry.UniversalTxId)
		if err != nil {
			return true, err
		}
		if !exists {
			return false, nil
		}
		for _, ob := range utx.OutboundTx {
			if ob.DestinationChain == chain && ob.Id == outboundId {
				found = true
				return true, nil // stop walking
			}
		}
		return false, nil
	})
	if err != nil {
		return false, err
	}
	return found, nil
}
```
