After thorough investigation of the nearcore codebase, I found a valid analog. The bug class is: **a missing return/refund handler in intermediate callback paths causes funds to be permanently stuck**. The analog exists in the wallet contract's intermediate callbacks.### Title
Missing `caller_deposit` refund in intermediate callback early-return paths causes permanent loss of external caller's NEAR deposit — (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

---

### Summary

The `nep_141_storage_balance_callback` and `address_check_callback` functions in the ETH-implicit wallet contract each receive a `caller_deposit: Option<CallerDeposit>` parameter that tracks an external caller's attached NEAR deposit. When these intermediate callbacks return early due to a failed or malformed upstream promise result, they drop `caller_deposit` without issuing a refund. The deposit is permanently absorbed into the wallet contract's balance. The correct refund path exists only in `rlp_execute_callback`, which is never reached when the intermediate callback exits early.

---

### Finding Description

`CallerDeposit` is constructed in `inner_rlp_execute` and records the predecessor account and the yoctoNEAR amount whenever an external (non-self) caller attaches a non-zero deposit to `rlp_execute`. [1](#0-0) 

The deposit is forwarded through the promise chain into the intermediate callbacks. `rlp_execute_callback` correctly refunds it on failure: [2](#0-1) 

However, **both intermediate callbacks return early without touching `caller_deposit`** in multiple failure branches.

**`address_check_callback` — registrar call fails:** [3](#0-2) 

**`address_check_callback` — registrar returns unparseable data:** [4](#0-3) 

**`nep_141_storage_balance_callback` — `storage_balance_of` call fails:** [5](#0-4) 

**`nep_141_storage_balance_callback` — `storage_balance_of` returns unparseable data:** [6](#0-5) 

In every one of these branches the function returns `PromiseOrValue::Value(...)` directly. Because `rlp_execute_callback` is chained only after the intermediate promise succeeds, it is never scheduled when the intermediate callback exits early. The `caller_deposit` value is silently dropped and the NEAR tokens remain in the wallet contract's balance indefinitely.

---

### Impact Explanation

**Loss of funds.** Any external account that attaches a non-zero NEAR deposit to `rlp_execute` for an ERC-20 transfer (triggering the `storage_balance_of` path) or for an EOA base-token transfer to an eth-implicit account (triggering the registrar lookup path) will permanently lose that deposit if the intermediate cross-contract call fails or returns unexpected data. The wallet contract's balance silently increases by the lost amount; there is no recovery mechanism.

---

### Likelihood Explanation

**Medium–High.** The conditions are:

1. An external caller (relayer or any third party) attaches a non-zero NEAR deposit to `rlp_execute`. This is the normal flow for ERC-20 transfers where the Ethereum transaction encodes a `yocto_near` value, or for base-token transfers with a relayer fee.
2. The intermediate call fails. This happens whenever the target token contract does not exist, panics, runs out of gas, or the address registrar is temporarily unavailable.

Condition 2 is not exotic: a user can craft an ERC-20 transfer targeting a non-existent or malicious token contract, causing `storage_balance_of` to fail deterministically. The deposit loss is then guaranteed for every such call.

---

### Recommendation

Mirror the refund logic already present in `rlp_execute_callback` into every early-return branch of both intermediate callbacks. For example, in `nep_141_storage_balance_callback`:

```rust
PromiseResult::Failed => {
    // Refund the external caller's deposit before returning.
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(
            refund,
            NearToken::from_yoctonear(yocto_near.into()),
        );
    }
    return PromiseOrValue::Value(ExecuteResponse {
        success: false,
        success_value: None,
        error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
    });
}
```

Apply the same pattern to the `serde_json` failure branch in `nep_141_storage_balance_callback` and to both early-return branches in `address_check_callback`.

---

### Proof of Concept

1. Deploy the wallet contract as a global contract for an ETH-implicit account (standard mainnet setup).
2. As an external relayer, call `rlp_execute` on the wallet contract with:
   - An ERC-20 transfer Ethereum transaction whose `to` address maps to a non-existent NEAR account (so `storage_balance_of` will fail with `AccountDoesNotExist`).
   - A non-zero `attached_deposit` (e.g., 1 NEAR).
3. Execution flow:
   - `inner_rlp_execute` constructs `CallerDeposit { account_id: relayer, yocto_near: 1e24 }`.
   - A promise chain `storage_balance_of → nep_141_storage_balance_callback` is scheduled.
   - `storage_balance_of` fails because the account does not exist.
   - `nep_141_storage_balance_callback` is called with `PromiseResult::Failed`.
   - The function hits the early-return at line 204–209 and returns without refunding.
   - `rlp_execute_callback` is never scheduled.
4. **Result:** The relayer's 1 NEAR deposit is permanently absorbed into the wallet contract's balance. The relayer's account balance decreases by 1 NEAR with no recovery path. [7](#0-6) [8](#0-7) [1](#0-0)
