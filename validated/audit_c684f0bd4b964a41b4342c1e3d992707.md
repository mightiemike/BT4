### Title
`ensure_match_transaction_info` never validates the state-checkpoint (state-root) hash, so replay-verify tooling can accept a corrupted/divergent state root as a match - ([File: types/src/transaction/mod.rs])

### Summary
The bug report's core pattern is: a value that should gate acceptance of a result (quorum) is computed but never actually re-checked against the value that matters at accept time, so a wrong result can be accepted as valid. The Aptos-native analog is `TransactionOutput::ensure_match_transaction_info`, the function used by chunk-executor's `verify_execution` (and by `db-tool`'s `replay_on_archive`, i.e. the mainnet-facing replay-verify path) to determine whether a locally re-executed transaction matches the transaction info recorded/backed-up on chain. This function checks status, gas used, write-set hash (`state_change_hash`), and event root hash — but it never checks `state_checkpoint_hash` (the Sparse-Merkle-Tree/state root committed for that transaction), despite that field being the primary authenticated commitment to the resulting world state.

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` compares a freshly-computed `TransactionOutput` against an authoritative `TransactionInfo` supplied from a backup/archive/chunk proof: [1](#0-0) 

It verifies `status`, `gas_used`, `write_set_hash == txn_info.state_change_hash()`, and `event_root_hash == txn_info.event_root_hash()`. It ends with an explicit acknowledgment that checkpoint hashes are not validated: [2](#0-1) 

Critically, this comment (and the code) shows the state-checkpoint hash (the SMT root — `state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) is *never* compared for equality with a locally-recomputed root — not even the base `state_checkpoint_hash` that has existed since V0 and is unconditionally present for checkpoint transactions. The write-set hash check only proves the *raw list of writes* matches; it says nothing about whether applying those writes over the correct base state produces the correct resulting SMT root. A write-set can hash-match while the actual state root it produces (due to base-state divergence upstream, e.g. from a prior mismatch, pruning bug, or restore corruption) no longer matches the authenticated `state_checkpoint_hash` from the backup/ledger — and this function would still return `Ok(())`.

This function is consumed directly in the replay-verify path used to check that locally re-executed transactions match transaction infos taken from an archive/backup: [3](#0-2) 

and it is also invoked from the `db-tool`'s `replay_on_archive` binary, which is exactly the tool operators use on mainnet archives to verify historical state correctness (`storage/db-tool/src/replay_on_archive.rs`, which imports `TransactionInfo`/`WriteSet` and calls the same verification routine).

### Impact Explanation
The state-checkpoint hash is the authenticated binding between a transaction and the resulting global state (the Jellyfish Merkle Tree root). Skipping its verification means:
- Replay-verify tooling (used to detect state divergence/corruption between an executed node and an archived/backed-up ledger) can report a **successful match** even when the state root actually diverges — i.e. exactly the "authenticated response bound to the wrong... root" failure mode called out in the task's proof/storage pivots.
- Any bug elsewhere in the storage/restore/JMT pipeline that corrupts the state root while leaving the write-set bytes unchanged (or a base-state corruption from a previous divergence that isn't otherwise caught) would go undetected by this check, allowing operators/tools to believe an execution path or restored archive is correct when it is not.
- This directly undermines the "must survive executor-to-storage handoff unchanged" and "must preserve deterministic proof binding" invariants for the restore/replay path, since the one component that would objectively catch such a divergence — hash comparison of the recomputed state root — is absent.

Given this affects the primary tool relied on to attest ledger/state correctness (replay-verify against archives), and could mask corruption of committed state, this is a genuine state-integrity gap of significant severity.

### Likelihood Explanation
The check is unconditionally skipped for every call to `ensure_match_transaction_info` — it does not require any adversarial input, race, or privileged access to trigger; it's a structural gap present on every invocation of this function. The comment in the code itself flags it as a known limitation that needs to be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", but the gap for the **base** `state_checkpoint_hash` (unrelated to the new trading-native feature) has evidently existed independent of that upcoming feature flag, and is exercised on every replay-verify run today.

I was not able to fully trace, within the available tool budget, the precise call site inside `storage/db-tool/src/replay_on_archive.rs` that invokes `ensure_match_transaction_info` (only its import/usage count was confirmed, not the surrounding control flow), so I cannot state with full certainty whether that specific binary treats a "match" here as the sole gate for reporting a clean replay, or layers another root-hash check on top elsewhere (e.g. via `state_checkpoint_output` or the accumulator root check in `chunk_result_verifier.rs`, which does verify the *transaction-accumulator* root, not the *state* root, and only during actual chunk-execution enqueue, not during `verify_execution`/replay-only mode). This uncertainty affects only the precise severity classification (whether other layers happen to compensate in some call paths), not the core finding that `ensure_match_transaction_info` itself omits the state-checkpoint hash check.

### Recommendation
Add explicit checks in `ensure_match_transaction_info` comparing the locally-recomputed state checkpoint hash(es) — `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) — against `txn_info.state_checkpoint_hash()` etc., whenever the transaction is expected to produce a checkpoint (`self.has_state_checkpoint_hash()`), before returning `Ok(())`. This requires threading the recomputed SMT/root value into `TransactionOutput` (or the call site) so the comparison can be made without waiting for the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature. Until fixed, replay-verify tooling should not be treated as authoritative proof that the resulting state root matches the archive/backup.

### Proof of Concept
1. Take any `TransactionOutput` whose write-set exactly matches the bytes/hash recorded in a `TransactionInfo` from a backup/archive (i.e. `write_set_hash == txn_info.state_change_hash()` and events match), but where the write set is applied over a *different* (corrupted) base state than the one used to originally produce that `TransactionInfo` — for example following any bug upstream in state-store/restore that leaves stale/incorrect values for unrelated keys in the SMT.
2. Compute the resulting local `state_checkpoint_hash` for this execution; it will differ from `txn_info.state_checkpoint_hash()`.
3. Call `ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` as done in `execution/executor/src/chunk_executor/mod.rs::verify_execution` (lines 692-697) or via the `db-tool replay_on_archive` binary.
4. Observe it returns `Ok(())` because status, gas, write-set hash, and event root all still match — the function never reads or compares `state_checkpoint_hash`, so the actual state-root divergence is silently accepted as "verified."

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
