### Title
Global rate-limit budget for MethodWebAPITrigger can be depleted in a single request via multi-topic payload fanout - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`triggerConnectorHandler.processTrigger` calls `trigger.rateLimiter.Allow(body.Sender)` once per matching topic inside a nested loop over `payload.Topics`, rather than once per gateway message. A single `MethodWebAPITrigger` request whose `Topics` list contains K topics that are all present in a trigger's `allowedTopics` will consume K units from that trigger's shared `GlobalRPS`/`GlobalBurst` token budget in one HTTP/gateway round trip.

### Finding Description
In `processTrigger` [1](#0-0) , the handler iterates `for _, trigger := range h.registeredWorkflows { for _, topic := range topics { ... trigger.rateLimiter.Allow(body.Sender) ... } }`. Each registered trigger owns a single `*ratelimit.RateLimiter` with a shared `GlobalRPS`/`GlobalBurst` budget across all senders, configured at registration time in `RegisterTrigger` [2](#0-1) .

Because the topic loop is nested inside the trigger loop, and `Allow` is invoked for every topic in the incoming payload that matches `trigger.allowedTopics`, an attacker who is one of the `AllowedSenders` for that trigger (satisfying `trigger.allowedSenders[sender.String()]` at line 101) can submit a single gateway message with `payload.Topics` containing K distinct topics that are all in `allowedTopics`. This results in K sequential `Allow()` calls against the same trigger's global limiter within one HTTP/gateway round trip, consuming K tokens from `GlobalBurst` in one request instead of the intended 1 token per request. Neither the sender check nor a per-message rate check gates the loop before it depletes the shared budget — the rate limiting is applied per (trigger, topic) match, not per inbound message. This lets the attacker exhaust the trigger's shared rate-limit budget disproportionately fast relative to other legitimate senders sharing the same `GlobalRPS`/`GlobalBurst` pool.

### Impact Explanation
This is a rate-limit bypass / resource-starvation issue: a single authorized sender can consume a disproportionate share of a trigger's shared `GlobalRPS`/`GlobalBurst` capacity by widening the topic list in one request, denying capacity to other legitimate senders targeting the same trigger. This matches a "material rate-limit bypass / unfair resource consumption" impact — it does not itself grant unauthorized access, secret disclosure, or unauthorized transaction execution, but it can degrade trigger availability for other senders.

### Likelihood Explanation
Exploitation requires only that the attacker be one of the `AllowedSenders` for a trigger with a finite `GlobalBurst`/`GlobalRPS` and that the trigger's `allowedTopics` contains multiple topics — both are configuration choices under the workflow owner's control, not privileged attacker capabilities. Crafting `payload.Topics` with many entries is trivial and fully attacker-controlled, making this readily and repeatably exploitable by any sender already permitted to call the trigger at least once.

### Recommendation
Rate-limit at the message level rather than per (trigger, topic) match: call `trigger.rateLimiter.Allow(body.Sender)` at most once per trigger per incoming gateway message (e.g., track whether the limiter has already been charged for this `(trigger, body.MessageId)` pair before entering the topic loop, or move the `Allow` check outside the topic loop and gate on whether any topic matched at all).

### Proof of Concept
Unit test plan in `core/capabilities/webapi/trigger/trigger_test.go`:
1. Register a trigger with `AllowedTopics = {"t1","t2",...,"tK"}`, `AllowedSenders = {senderA}`, `GlobalBurst = K` (small, e.g. 5), `GlobalRPS` low.
2. Send one `HandleGatewayMessage` request from `senderA` with `payload.Topics = ["t1","t2","t3","t4","t5"]` (K=5 topics, all in `allowedTopics`).
3. Assert that after this single request, the trigger's rate limiter is exhausted (i.e., a subsequent request from a different legitimate sender `senderB`, also in `AllowedSenders`, with a single topic is rejected with "request rate-limited").
4. Compare against a control case: K separate single-topic requests from K different senders each consuming 1 token — showing the multi-topic single-request case depletes the same `GlobalBurst` budget in one call instead of spreading consumption, demonstrating the disproportionate fan-out consumption tied to `len(payload.Topics)` rather than request count.
