### Title
Unbounded market order list query causes RPC-API DoS via attacker-inflated order book - ([File: GetMarketOrderListByPairServlet.java])

### Summary
`GetMarketOrderListByPairServlet` and its underlying `Wallet.getMarketOrderListByPair` handler expose `/wallet/getmarketorderlistbypair` on full (non-lite) nodes with no pagination or result-size cap. Since the servlet's only parameters are `sell_token_id`/`buy_token_id` [1](#0-0) , any account can inflate the number of open orders for a pair via ordinary `MarketSellAssetContract` transactions and then repeatedly query that pair to force expensive full iteration/sorting of the order book on every request.

### Finding Description
The `LiteFnQueryHttpFilter` only blocks `/wallet/getmarketorderlistbypair` (and its `walletsolidity`/`walletpbft` variants) when the node `isLiteNode()` and `openHistoryQueryWhenLiteFN` is disabled [2](#0-1) , and does nothing on a full node, so the endpoint is fully reachable there [3](#0-2) .

`GetMarketOrderListByPairServlet.doGet`/`doPost` accept only `sell_token_id` and `buy_token_id` (no offset/limit) and pass them straight to `wallet.getMarketOrderListByPair(sellTokenId, buyTokenId)`, writing the full resulting `MarketOrderList` to the response [4](#0-3) . There is no size cap enforced by the servlet itself — the only generic protection is inherited from `RateLimiterServlet`, which throttles request rate, not per-query cost.

Order creation is done through ordinary, unprivileged `MarketSellAssetContract` transactions handled by `MarketSellAssetActuator`, which persist orders keyed by pair/price in `MarketPairToPriceStore`/`MarketPairPriceToOrderStore` and `MarketOrderStore` [5](#0-4) . Nothing in the reachable path caps how many orders a single pair can accumulate, nor does the query-side code limit how many orders are read, merged, and sorted per request — this matches the described quadratic-ish cost: unbounded order count × unbounded per-query iteration.

Because this behavior is gated only by the lite-node filter (which is a deployment-mode check, not a security boundary against query cost) and by a generic rate limiter (which limits requests/sec, not per-request cost), a full node has no server-side defense against a large, attacker-grown order book being repeatedly and fully materialized/sorted on each query.

### Impact Explanation
This is an RPC-API DoS: an unprivileged attacker can grow the cost of a single, publicly reachable read-only endpoint (`/wallet/getmarketorderlistbypair`, plus `walletsolidity`/`walletpbft` equivalents) without bound, and then repeatedly trigger that cost to consume full-node CPU/I/O, degrading service for legitimate users of the node's RPC API. It does not directly corrupt state, leak keys, or cause consensus divergence — it is scoped to node/API availability degradation.

### Likelihood Explanation
- Precondition: target is a full (non-lite) node, which is the common deployment mode, and no custom `rate.limiter.http` override for this servlet — both are default configurations, not privileged.
- Attacker cost: creating many market orders requires only self-funded, signed `MarketSellAssetContract` transactions (standard bandwidth/energy fees), which is inexpensive relative to the amplified read cost imposed on the node per query, and orders can be reused indefinitely for repeated queries (no need to re-create per request).
- Repeatability: once the order book for a pair is inflated, every subsequent query against that pair pays the same inflated cost, so the attack is durable and requires only one-time setup cost.
- The generic `RateLimiterServlet` throttles request frequency but does not scale limits with the discovered cost of a given pair's order book, so it does not close this gap by default.

### Recommendation
- Add a hard server-side cap (e.g., max N orders, or max total orders scanned) inside `Wallet.getMarketOrderListByPair` (and the analogous solidity/PBFT paths) regardless of how many orders actually exist for a pair, returning a truncated/paginated result instead of the full set.
- Add pagination parameters (`limit`/`offset` or cursor) to `GetMarketOrderListByPairServlet` (and PBFT/Solidity variants), enforced server-side rather than trusted from the client.
- Consider capping the maximum number of open orders allowed per token pair (or per account per pair) at the actuator level in `MarketSellAssetActuator`/`MarketCancelOrderActuator` to bound worst-case order-book size.
- Optionally apply a cost-aware or adaptive rate limit (e.g., limit by estimated response size/order count) specifically for this and similarly unbounded market-query endpoints.

```java
@Test
public void testMarketOrderListByPairScalesWithOrderCount() {
  byte[] sellTokenId = "sellToken".getBytes();
  byte[] buyTokenId = "buyToken".getBytes();

  // 1. Seed N market orders for the pair via MarketSellAssetActuator (ordinary signed txs)
  int[] sizes = {100, 1_000, 10_000, 100_000};
  for (int n : sizes) {
    createMarketOrders(sellTokenId, buyTokenId, n); // helper: builds+executes N MarketSellAssetContract txs

    long start = System.nanoTime();
    MarketOrderList reply = wallet.getMarketOrderListByPair(sellTokenId, buyTokenId);
    long elapsedMs = (System.nanoTime() - start) / 1_000_000;

    System.out.println("orders=" + n + " elapsedMs=" + elapsedMs
        + " resultSize=" + reply.getOrdersCount());

    // Expected: elapsedMs grows roughly linearly/super-linearly with n,
    // and reply.getOrdersCount() == n (no server-side cap applied),
    // demonstrating unbounded per-request cost.
  }
}
```
Expected result: response latency and payload size grow monotonically and without an enforced ceiling as `n` increases, confirming the endpoint has no pagination or result-size cap and is thus vulnerable to attacker-driven cost inflation on a full node.
