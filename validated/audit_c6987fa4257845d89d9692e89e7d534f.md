Market order fees are not locked at order-creation time, allowing a committee fee change to alter the cost of matching/canceling pre-existing orders - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
The `MARKET_SELL_FEE` and `MARKET_CANCEL_FEE` dynamic parameters can be changed by the committee via a proposal at any time, and this new value is applied retroactively to fee charges for orders that were already created (and possibly partially matched) under the old fee, mirroring the Putty `PuttyV2` bug where `fee` is applied at withdrawal time rather than at order-creation time.

### Finding Description
`MarketOrder` records created by `MarketSellAssetActuator` do not store the fee agreed to at creation time; they only persist trade terms (`sellTokenId`, `buyTokenId`, quantities, `createTime`) via `MarketOrderCapsule`'s constructor [1](#0-0) . Instead, every time a market order is created, matched (further sold), or canceled, the fee charged is recomputed from the current value of the `MARKET_SELL_FEE` / `MARKET_CANCEL_FEE` dynamic properties: `calcFee()` in `MarketSellAssetActuator` returns `dynamicStore.getMarketSellFee()` [2](#0-1) , and `calcFee()` in `MarketCancelOrderActuator` returns `dynamicStore.getMarketCancelFee()` [3](#0-2) . Both values are read fresh at `execute()`/`validate()` time [4](#0-3) [5](#0-4) .

These dynamic properties are mutable at any time through a committee proposal processed by `ProposalService.process`, which directly overwrites `MARKET_SELL_FEE` and `MARKET_CANCEL_FEE` in `DynamicPropertiesStore` with no restriction tied to outstanding orders [6](#0-5) . The validator in `ProposalUtil` only bounds the new value to `[0, 10_000_000_000]`, with no protection for existing orders [7](#0-6) .

Consequently, a user who places a sell order at time T (fee = F1) has no guarantee about the fee that will be charged when: (1) the order is later matched against an incoming taker order (fee charged in `MarketSellAssetActuator.execute` for the taker, while the maker side is unaffected on cancel-path but the taker's fee still floats), or (2) the user cancels the order later via `MarketCancelOrderActuator` (fee charged at cancel time, not creation time). If the committee raises the fee between order placement and order cancellation/settlement, the user pays a fee they never agreed to when placing the order — the exact analog to the Putty `withdraw`-time fee application bug.

### Impact Explanation
This is an underpriced/unexpected-cost impact on unprivileged users of the TRC10 on-chain order book (Market feature): a user's expected transaction cost for an already-submitted order can be unilaterally inflated after the fact, up to the maximum allowed value of `10_000_000_000` sun (10,000 TRX) for both `MARKET_SELL_FEE` and `MARKET_CANCEL_FEE` [8](#0-7) [9](#0-8) . Since orders can remain open indefinitely (bounded only by `MAX_ACTIVE_ORDER_NUM`, not by time) [10](#0-9) , the exposure window can be long, and a fee hike could even push a previously-affordable cancellation out of reach if the user's balance is insufficient for the new fee, effectively trapping funds/tokens in the order until balance is topped up (`validate()` requires `ownerAccount.getBalance() >= fee` to cancel) [11](#0-10) .

### Likelihood Explanation
The fee change requires a committee proposal to pass (privileged action), so the root trigger is privileged; however, the actual victims are ordinary unprivileged users with pre-existing open orders, and no user consent or order-level fee lock exists to protect them once such a proposal is approved — matching the disclosed class ("fee can change without the consent of users"). Given that `MARKET_SELL_FEE`/`MARKET_CANCEL_FEE` are explicitly designed to be adjustable on live governance parameters and market orders can be long-lived, this is a realistic, low-friction path once a fee-change proposal executes.

### Recommendation
Snapshot the applicable sell/cancel fee into the `MarketOrder` protobuf at order-creation time (similar to Putty's fix of storing fees in the `Order` struct), and use that stored fee for all subsequent partial-match and cancel operations on that order, rather than re-reading the live `DynamicPropertiesStore` value at execution time.

### Proof of Concept
1. Committee sets `MARKET_SELL_FEE = 0` and `MARKET_CANCEL_FEE = 0` via proposal (processed in `ProposalService.process`) [6](#0-5) .
2. Alice submits a sell order via `MarketSellAssetContract`; `MarketSellAssetActuator.execute` charges `fee = calcFee() = 0` and creates the order, recording only trade terms, no fee [12](#0-11) [1](#0-0) .
3. Committee later raises `MARKET_CANCEL_FEE` to `10_000_000_000` (max allowed) via a new proposal [13](#0-12) .
4. Alice submits `MarketCancelOrderContract` to cancel her still-open order; `MarketCancelOrderActuator.calcFee()` now returns the new, much higher fee and deducts it from Alice's balance — a cost she never agreed to when the order was placed [5](#0-4) [3](#0-2) .
