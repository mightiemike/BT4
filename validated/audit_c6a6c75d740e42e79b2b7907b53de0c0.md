### Title
`sanitizeHost` throws an uncaught `TypeError` on attacker-controlled base64 host input instead of returning `null` - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` accepts any string that matches the base64 character regex, decodes it with `atob`, and feeds the raw decoded bytes directly into `new URL(\`https://${decodeHost(sanitizedHost)}\`)` without a try/catch. An attacker can craft a base64 string that decodes to bytes that are invalid as a URL host (e.g. containing forbidden host code points), causing the WHATWG `URL` constructor to throw a `TypeError`, which propagates up through every caller of `sanitizeHost`/`sanitizeShop`-adjacent host validation.

### Finding Description
`sanitizeHost(config)` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` line 58 only validates that the raw `host` query parameter matches the base64 character class regex (`base64regex`), then unconditionally does:
```
const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
```
`decodeHost` (`packages/apps/shopify-api/lib/auth/decode-host.ts`) is a thin wrapper around `atob`, which will happily decode any well-formed base64 string into arbitrary bytes, including forbidden host code points (null bytes, control characters, whitespace, etc.). The WHATWG `URL` parser throws `TypeError: Invalid URL` when the resulting hostname contains such forbidden code points, and this call is not wrapped in a `try`/`catch` anywhere in `sanitizeHost`.

This function is reached pre-authentication in the embedded-app admin flow: `validateShopAndHostParams` in both `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-shop-and-host-params.ts` and the equivalent react-router helper call `api.utils.sanitizeHost(url.searchParams.get('host')!)` directly on the raw, attacker-supplied `host` query parameter before any session-token or HMAC validation occurs. Similarly, `redirectToShopifyOrAppRoot` in `packages/apps/shopify-app-express/src/middlewares/redirect-to-shopify-or-app-root.ts` line 22 and `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` in `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts` call `sanitizeHost` on attacker-controlled query data with no surrounding exception handling at this layer.

Whether this constitutes a "crash" depends on the host framework: Remix/React Router loaders and Express route handlers generally catch synchronous throws from request handlers and convert them into a 500 response (error boundary / Express error middleware) rather than terminating the process. So the exploitable behavior is best characterized as an unhandled exception that produces an ungraceful 500 error / stack trace disclosure rather than a full process crash — I could not find a code path in this repo where this throw escapes an async boundary in a way that would crash the Node process itself (e.g. inside a raw `async` handler with no `.catch`, it would become an unhandled promise rejection only if not awaited by a framework that catches it, which I did not find evidence of in this indexed code).

### Impact Explanation
Concrete impact is limited to unhandled exceptions/500 errors within the embedded-app host/shop validation path, reachable by any anonymous, unauthenticated caller since this check runs before session-token/HMAC verification. This does not lead to session forgery, token theft, cross-tenant access, or open redirect/SSRF — it is, at most, a minor denial-of-service against a single request (not the server process), and only if the surrounding framework does not already catch synchronous exceptions from route handlers/loaders (which Remix, React Router, and Express typically do by design).

### Likelihood Explanation
Trivial to trigger: an anonymous attacker can send a GET request to any embedded route with a crafted `host` query parameter such as `Buffer.from('\x00example.myshopify.com').toString('base64')`. No secrets or privileged access are required. However, the actual observable impact is bounded by each framework's built-in error handling, which in the reviewed call sites (Remix loaders, Express middleware) is expected to catch and convert this into a 500 response rather than a true service outage.

### Recommendation
Wrap the `new URL(...)` construction in `sanitizeHost` in a try/catch and return `null` (or throw `InvalidHostError` when `throwOnInvalid` is set) on failure, consistent with the function's documented contract that it "never throws, only returns null" for malformed input.

```typescript
export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }

    return sanitizedHost;
  };
```
