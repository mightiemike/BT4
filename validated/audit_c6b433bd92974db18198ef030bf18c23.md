### Title
`ExchangeTransactionContract`'s `expected` (minimum-received) field is never enforced against the actual swap output - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator` implements TRON's on-chain bancor-style AMM swap (`ExchangeTransactionContract`). The contract carries a `expected` field that is meant to act as the caller's minimum acceptable output amount (slippage protection), analogous to a DEX aggregator's "amountOutMin". The actuator validates that `expected > 0` but never compares the actually computed swap output against `expected`, either in `validate()` or `execute()`. This mirrors the LiFi finding where swap facets never verified that the tokens actually returned from a swap met the caller's expectations — here the on-chain AMM swap silently executes and settles at whatever price the current pool state yields, ignoring the caller-supplied minimum.

### Finding Description
`doValidate()` in `ExchangeTransactionActuator` reads the contract's `tokenExpected` and checks only that it is positive: [1](#0-0) 

No code path in `doValidate()` computes the actual `anotherTokenQuant` that the swap would yield and compares it to `tokenExpected`. Contrast this with `ExchangeWithdrawActuator`, which does calculate the counterparty amount during validation and enforces a precision/tolerance check: [2](#0-1) 

In `execute()`, the actual output (`anotherTokenQuant`) is computed via `exchangeCapsule.transaction(...)` and applied directly to account balances and the exchange pool, then reported in the receipt — with no comparison to the contract's `expected` value anywhere: [3](#0-2) 

The underlying pricing/accounting logic lives in `ExchangeCapsule.transaction()`, which computes `buyTokenQuant` via the bancor-formula `Processor` and mutates pool balances unconditionally (aside from a hardened-mode non-negative check), with no linkage back to any caller-specified minimum: [4](#0-3) 

A grep across the codebase confirms `tokenExpected`/`getExpected()` is referenced only inside this actuator (for the `>0` check) and in a servlet test — it is never used to gate or validate the swap output. This confirms the root cause: the "minimum received" parameter is present in the protocol/API but is dead data that provides no actual protection.

### Impact Explanation
Any unprivileged account submitting `ExchangeTransactionContract` (via `exchangetransaction` API/wallet call) can have their swap settle at an arbitrarily worse rate than the `expected` value they specified, with the transaction still reporting `SUCCESS`. Because TRON's exchange pools are on-chain AMMs, this exposes users to:
- Front-running/sandwich attacks by other network participants (block producers or bots observing the pending transaction) that shift the pool ratio before the victim's swap executes, since there is no on-chain enforcement of the minimum-received guarantee.
- Silent value loss for users relying on the `expected` field as intended slippage protection — the field is documented/used at the API level but structurally unenforced, creating a false sense of security and a concrete asset-accounting deviation between expected and actual settlement.

This is a concrete, unprivileged-user-reachable accounting/settlement issue directly analogous to the LiFi finding: a swap-like operation completes and mutates balances without verifying that the amount "returned" satisfies the caller's minimum-output requirement.

### Likelihood Explanation
High. This requires no special privileges — any account can create and submit an `ExchangeTransactionContract`. The only precondition is an actively traded on-chain exchange pool with sufficient other order flow (or an adversary capable of front-running), which is a normal operating condition for public AMM pools. No validator/witness collusion or contract deployment is required.

### Recommendation
In `ExchangeTransactionActuator.execute()` (or in `doValidate()` after computing the would-be output), enforce that the computed `anotherTokenQuant` is greater than or equal to `contract.getExpected()`, throwing a `ContractValidateException`/`ContractExeException` otherwise — mirroring the LiFi remediation of requiring a minimum-received check (`require(actualReceived >= expected)`), and consistent with the precision check already implemented in `ExchangeWithdrawActuator`.

### Proof of Concept
1. Attacker/other traders observe (or independently trigger via pending swaps) pool state such that the current bancor-formula rate is unfavorable to a pending `ExchangeTransactionContract`.
2. Victim submits `ExchangeTransactionContract` with `quant = X`, `expected = Y` (intending to receive at least `Y`).
3. `ExchangeTransactionActuator.doValidate()` only checks `tokenExpected > 0` (line 190-192) — it never computes or checks the real output against `Y`.
4. `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, ...)` (line 68), which returns `anotherTokenQuant` computed purely from current pool reserves at the time of execution — this value could be far less than `Y`.
5. The actuator applies the resulting balances and sets `ret.setExchangeReceivedAmount(anotherTokenQuant)` with `code.SUCESS` (lines 93-99), regardless of whether `anotherTokenQuant < tokenExpected`.
6. The victim's transaction is confirmed successful on-chain, having received less than their specified minimum, with no revert or error signaling the slippage violation.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
