## Confirmed analog: `action_delete_account` / `remove_account` do not clean up pending `PromiseYield` state, allowing a stale parked receipt to execute against a recreated account

### Title
Deleting an account with a pending `PromiseYield` leaves stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId` trie entries that can later be executed against a re-created account of the same name - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
This is the same bug class as the reported `transferERC721` finding: one code path (`timeUnlockERC721`) properly deletes an auxiliary mapping (`timelockERC721s`) when it consumes the resource, while a different, reachable path (`transferERC721`) moves/destroys the primary resource but forgets to clean the auxiliary mapping, leaving stale state that a later operation can pick up and misuse. In nearcore, the analogous pair is: `PromiseResume` processing in `runtime/runtime/src/lib.rs` (`process_receipt`) which *does* clean up `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` when a yield is resolved, versus `action_delete_account` → `remove_account`, which deletes the `Account`, its access/gas keys, contract code, and contract data — but never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, or the `YieldIdToDataId`/`DataIdToYieldId` mappings for that account.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) is the single cleanup routine invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`). It removes:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- all `AccessKey`/gas-key-nonce entries
- all `ContractData` entries [1](#0-0) [2](#0-1) 

It never removes `TrieKey::PromiseYieldReceipt { receiver_id, data_id }`, `TrieKey::PromiseYieldStatus { receiver_id, data_id }`, `TrieKey::PromiseYieldTimeout { index }`, or the `TrieKey::YieldIdToDataId` / `TrieKey::DataIdToYieldId` mapping for that `receiver_id`. [3](#0-2) 

Compare this with the "proper" cleanup path that the reporter's normal-vs-alternate-path analog is based on: when a `PromiseResume` receipt legitimately resolves a parked `PromiseYield`, the runtime removes the receipt, the status, and (since `YieldWithId`) the yield-id mapping, all together, right before re-executing the parked action receipt: [4](#0-3) 

Because `action_delete_account` bypasses this cleanup entirely (it just sets `*account = None` and calls `remove_account`, which has no knowledge of promise-yield bookkeeping), any `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout`/yield-id-mapping entries that existed for the account at the moment of deletion are left orphaned in the trie under the (still fixed, deterministic) key `receiver_id = account_id`.

An account name in NEAR can be reused: a sub-account (e.g. `child.alice.near`) can be deleted and then recreated by its parent within the same or a later chunk — nearcore's own test suite explicitly covers same-chunk delete+recreate for `FunctionCall` receivers, confirming this scenario is a supported, reachable state transition (not a corner case that is rejected): [5](#0-4) 

If a `PromiseYield` was pending on the account at deletion time (e.g., the account itself, or another local action within the same receipt, called `yield_create`) and either (a) a real `promise_yield_resume` call was already in flight (a `PromiseResume` receipt queued/delayed/buffered) or (b) the yield's timeout is still pending in the `PromiseYieldTimeout` FIFO queue, that resume/timeout receipt is *not* removed by account deletion. `resolve_promise_yield_timeouts` walks the timeout queue purely by `expires_at` index and is unaware that the target account was deleted and possibly recreated in the interim: [6](#0-5) 

When that late `PromiseResume` (real or timeout) is finally processed, `process_receipt` looks up `get_promise_yield_receipt(state_update, account_id, data_id)` purely by `(account_id, data_id)` — with no check that this is still the "same" logical account instance that created the yield: [7](#0-6) 

If the account has since been recreated (same `account_id`, fresh `Account` record, no relation to the deleted one), the stale `PromiseYieldReceipt` — an entire pre-built `ActionReceipt` with `actions` chosen by the *old* account/contract logic and a `predecessor_id` set at creation time — is fetched and executed via `apply_action_receipt` against the *new* account's live state. `apply_action_receipt` sets `actor_id = receipt.predecessor_id()`, so any actions in the stale receipt that don't require `actor_id == account_id` (notably `Transfer`) execute unconditionally against the new account, mixing execution state and mutating balance/storage that has nothing to do with the entity that authorized it: [8](#0-7) 

This exactly mirrors the ERC-721 bug class: the "cleanup on consumption" path (`PromiseResume` execution) is correct, but the alternate path that destroys/repurposes the underlying resource (`DeleteAccount`) skips the cleanup that the other path relies on, leaving an administratively stale record (`PromiseYieldReceipt`/`PromiseYieldStatus`/timeout entry/yield-id mapping) that a later, unprivileged transaction (a normal `yield_resume` call, or simply the timeout firing) can trigger to reuse.

### Impact Explanation
A stale parked action receipt executing against a freshly (re)created account can move balance (`Transfer` actions inside the receipt are unconditionally applied via `action_transfer`, independent of `actor_id`/`check_actor_permissions`) or trigger unintended `FunctionCall` execution/state mutation attributed to a predecessor that has no relationship with the new account owner. This is concrete unauthorized value movement / invalid state transition acceptance reachable purely from ordinary, unprivileged transaction submission (create yield → delete account → recreate account → resume/timeout fires), satisfying the required impact categories (unauthorized value movement, invalid state transition acceptance). It can also desynchronize administration state: `PromiseYieldStatus`/timeout-queue entries under an account_id that no longer corresponds to the same logical account represent exactly the kind of "administration doesn't correspond to the available resource" issue called out in the original report.

### Likelihood Explanation
Reaching this requires an unprivileged sequence of ordinary actions (yield_create → delete_account with a pending yield → recreate the same account name → resume/timeout delivery), all of which are individually supported, tested code paths in the codebase (the delete+recreate-in-same-chunk scenario is explicitly tested for `FunctionCall`, and delete-account/create-account/yield-create/yield-resume are all standard contract-callable actions). No special privileges, validator status, or network-level manipulation are required — only ordinary contract logic performing a `yield`, a self-delete (or being deleted by an authorized actor), and account recreation, which a contract author or attacker-controlled contract can freely orchestrate. However, I was not able to fully trace every intermediate check (e.g., whether any other invariant elsewhere silently prevents deleting an account that still has an unresolved `PromiseYieldReceipt`) within the given tool budget, so this should be validated with a live reproduction before treating it as fully confirmed.

### Recommendation
When `action_delete_account` (or its `remove_account` helper) removes an account, it should also enumerate and remove any `PromiseYieldReceipt`, `PromiseYieldStatus`, pending `PromiseYieldTimeout` entries, and `YieldIdToDataId`/`DataIdToYieldId` mappings keyed by that `receiver_id`, mirroring the cleanup already performed on the legitimate `PromiseResume` resolution path in `runtime/runtime/src/lib.rs`. Alternatively, `process_receipt`'s `PromiseResume`/timeout-resume handling should validate that the account instance which created the yield is still the one being resumed (e.g., by tying the yield record to something that changes on account recreation) before re-executing the parked receipt.

### Proof of Concept
1. Account `child.alice.near` (created by `alice.near`) deploys a contract and calls a method that performs `promise_yield_create`, producing a `PromiseYieldReceipt`/`PromiseYieldStatus` keyed at `receiver_id = child.alice.near`.
2. Before the yield is resumed, `child.alice.near` (or `alice.near` acting on it) submits a receipt with `Action::DeleteAccount { beneficiary_id: alice.near }`. `action_delete_account` → `remove_account` deletes the `Account`, keys, and contract data, but leaves the `PromiseYieldReceipt`/`PromiseYieldStatus`/timeout queue entry intact (`runtime/runtime/src/actions.rs:330-406`, `core/store/src/utils/mod.rs:505-575`).
3. `alice.near` recreates `child.alice.near` in the same or a later chunk (supported per the same-chunk delete/recreate test at `runtime/runtime/src/tests/apply.rs:4978-4983`), depositing a fresh, unrelated balance.
4. Either (a) an in-flight `PromiseResume` for the original `data_id` arrives, or (b) the yield's timeout (still queued in `PromiseYieldTimeout`) fires. `process_receipt`'s `PromiseResume` branch (`runtime/runtime/src/lib.rs:1554-1616`) finds the stale `PromiseYieldReceipt` under `(account_id=child.alice.near, data_id)` and executes it via `apply_action_receipt` against the newly created account, applying its `actions` (e.g., a `Transfer`) and mutating the new account's state despite having no relationship to the entity that authorized/funded it.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

**Timeouts** are the last step of `process_receipts`:
`resolve_promise_yield_timeouts` (`lib.rs:2986`) walks the `PromiseYieldTimeout` queue
in `expires_at` order, stopping at the first entry with `expires_at >
block_height` (`:3019`) or once the compute/proof-size budget is hit (`:3003`). For
each expired entry whose yield still exists, it synthesizes a `PromiseResume` with
`data: None` destined for the same (local) account and forwards/buffers it
(`:3037-3074`); the timeout is then dequeued (`:3078`). The timeout resume and any
real resume are ordered to the same shard, so a late timeout after a real resume is
simply discarded.
