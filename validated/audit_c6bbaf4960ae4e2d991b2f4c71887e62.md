I found a genuinely interesting comment in the code that documents a real gap, rather than a speculative one.### Title
`ensure_match_transaction_info` omits state/hot-state/position checkpoint hash validation, allowing replay-verify to accept a corrupted state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by replay/verification tooling (e.g. `storage/db-tool/src/replay_on_archive.rs`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` committed on-chain. The function checks status, gas used, write-set hash, and event root hash, but a code comment explicitly documents that it **does not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates:
- execution status
- gas used
- write-set hash (`state_change_hash`)
- event root hash

but never compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (on `TransactionInfoV1`), or `position_state_checkpoint_hash()` against the locally computed values. The comment in the same function acknowledges this gap directly: [2](#0-1) 

This function is the sole correctness gate used by `execute_and_verify` in the archive replay tool, which calls it per-transaction after local VM re-execution and treats a passing result as proof that local execution reproduced the authenticated on-chain state: [3](#0-2) 

Because the state/hot-state/position checkpoint hashes are never compared, a divergence between the locally computed state root (JMT root over applied write sets) and the authenticated on-chain `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` at a checkpoint transaction will not be detected by this check. The write-set hash check only proves the write *operations* match, not that applying them produces the same resulting Merkle root the chain committed to — so a bug in state-tree construction, hot-state promotion, or the trading-native/position state root computation (all newer, actively developed subsystems referenced elsewhere in the code, e.g. `execution/executor/src/workflow/do_state_checkpoint.rs`) could silently diverge from the authenticated ledger state without failing replay-verify.

### Impact Explanation
Replay-verify / archive-verification tooling is a mainnet-facing integrity tool used to confirm that historical execution reproduces the exact, authenticated ledger state (root hashes bound into `TransactionInfo` and ultimately into the `LedgerInfo`/accumulator signed by validators). If the state root diverges from the true committed value (e.g., due to a hot-state or position-state computation bug), this tool will report success even though the resulting state view is wrong — masking a hard-fork-class divergence rather than catching it. This falls squarely under the "Committed state that differs from correct VM result... not detected by the intended integrity check" and "authenticated output not bound to the correct root" categories in scope.

### Likelihood Explanation
This is not an attacker-triggered exploit against consensus (the actual on-chain commit path still uses full JMT/accumulator verification elsewhere, e.g. `AccumulatorProof::verify`, `SparseMerkleProof::verify`, `TransactionInfoListWithProof::verify`). The weakness is specifically in this one auxiliary verification helper used by db-tool replay/verify, and it is explicitly and knowingly incomplete per the inline `TODO(trading-native)` comment — i.e., the feature it must guard (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is stated to be unsafe to enable until this gap is fixed. It is a real, code-confirmed, unprivileged-verifiable gap in a state-commit-integrity checkpoint, but its blast radius is bounded to replay-verification tooling correctness rather than live consensus safety, and the code already gates the risky feature behind a flag that appears to still be off by default (`compute_trading_native_state_roots: false` in all `BlockExecutorConfigFromOnchain` constructors) [4](#0-3) .

### Recommendation
Add explicit `ensure!` checks in `ensure_match_transaction_info` comparing the locally-computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on `txn_info`) against the corresponding locally computed roots, before allowing `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any hot-state/position-state root feature) to be enabled in production. This closes the parallel to the external report's root cause: a security-critical equality/matching check that omits a value an attacker (or a divergent implementation) could control, causing an integrity guarantee to be silently bypassed.

### Proof of Concept
Not independently exploitable by an unprivileged network attacker to corrupt live consensus state (the gap is in a replay-verification helper, not the commit path itself), so no PoC transaction sequence is provided. The code-documented gap is directly demonstrable by inspection: [5](#0-4)  never references `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, while `TransactionInfoV1` carries all three fields as shown in its constructor [6](#0-5) , and `execute_and_verify` relies exclusively on this function to certify a match [7](#0-6) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
