### Title
`Wallet.getMarketOrderByAccount` throws unhandled `IllegalStateException` inside a per-order loop, causing a single stale/missing order to break the entire query - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getMarketOrderByAccount` iterates over every order id stored in a user's `MarketAccountOrderCapsule` and looks each one up in the `MarketOrderStore`. If any single order id in that list is not present in `MarketOrderStore` (e.g., due to store desync, pruning, or historical inconsistency), the lambda throws an `IllegalStateException`, which propagates out of the `forEach`, aborts the whole method, and turns a normal read-only query into an unhandled runtime exception at the RPC/HTTP layer — closely analogous to the reported `BondAggregator.findMarketFor` issue, where a single reverting `payoutFor` call inside a for-loop broke the entire aggregation query.

### Finding Description
`getMarketOrderByAccount` in `Wallet.java` fetches the list of order IDs owned by an account and, for each ID, calls `marketOrderStore.get(orderId.toByteArray())`. This call throws `ItemNotFoundException` when the store lacks that key. The catch block wraps it into `new IllegalStateException("order not found in store")` and re-throws it inside the `forEach` lambda: [1](#0-0) 

Because this is thrown inside a `List.forEach` lambda over `orderIdList`, one bad entry anywhere in the list aborts iteration for *all* other (valid) orders — the caller gets none of the results, exactly like the `BondAggregator.findMarketFor` for-loop breaking entirely because one market's `payoutFor` call reverted.

The sibling function `getMarketOrderById` has the identical pattern for a single lookup: [2](#0-1) 

This method is directly reachable from unauthenticated HTTP/JSON-RPC clients via `GetMarketOrderByAccountServlet.getResult`, which calls `wallet.getMarketOrderByAccount(...)` with a user-supplied address and has no try/catch around the specific `IllegalStateException` — it falls into the generic `Util.processError(e, response)` path: [3](#0-2) 

Note: `getMarketOrderListByPair` and `MarketOrderIdListCapsule.getAllOrder` use `getUnchecked`, which does not throw, so they are not affected — only the account-lookup path uses the throwing `get`.

### Impact Explanation
For a normal user this is limited to a self-DoS: if their own order list contains one stale/missing entry, they cannot retrieve *any* of their market orders through this API until the underlying inconsistency is fixed, since the exception discards results for the whole account rather than skipping the bad entry. This degrades the "find orders" query feature analogous to the original Bond Protocol impact (broken market discovery), though because it errors out (rather than mismatching state) and the store lookup for one's own valid orders should not normally fail, the practical blast radius is limited to edge cases where `MarketOrderStore` and `MarketAccountOrderCapsule` fall out of sync (e.g., partial deletion, reorg edge cases, or future actuator bugs that remove an order from the store without updating the account order list).

### Likelihood Explanation
Requires a store inconsistency to exist (an order id present in the account's order list but absent from `MarketOrderStore`); such inconsistency would itself be a bug elsewhere, so this specific throw is a secondary/defense-in-depth issue rather than a directly attacker-triggerable full outage. It is not remotely triggerable by an arbitrary unprivileged caller without such a precondition, and is caught by `Util.processError`/gRPC error handling rather than crashing the node, so this is a low-severity availability/robustness issue rather than a critical DoS.

### Recommendation
In `getMarketOrderByAccount` (and `getMarketOrderById`), do not let a missing order abort the entire result set: catch `ItemNotFoundException` inside the loop, log a warning, and skip that order id instead of throwing `IllegalStateException` that unwinds the whole `forEach`/method — mirroring the report's recommendation to gracefully continue past a single failing iteration instead of letting it break the entire query.

### Proof of Concept
1. Populate `MarketAccountOrderCapsule` for an address with order ids `[A, B, C]` where `B` is subsequently removed from `MarketOrderStore` (e.g., via a data inconsistency window) while remaining referenced in the account's order list.
2. Call `GET /wallet/getmarketorderbyaccount?value=<address>` (or the gRPC/JSON-RPC equivalent invoking `Wallet.getMarketOrderByAccount`).
3. Observe that the lookup for `B` throws `ItemNotFoundException`, caught and rethrown as `IllegalStateException`, propagating out of the `forEach` at [4](#0-3) , so the response contains an error instead of listing orders `A` and `C`.
