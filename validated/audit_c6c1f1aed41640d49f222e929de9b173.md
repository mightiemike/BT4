### Title
Unchecked `u64` subtraction on `accounts_data_len` during startup index generation can underflow/panic - ([File: accounts-db/src/accounts_db.rs])

### Summary
During `generate_index()` (the accounts-index rebuild that runs at validator startup when restoring from a snapshot), the accumulated `accounts_data_len` is decremented with a plain, unchecked `-=` operator, unlike the adjacent `capitalization` accumulator in the very same code path which is explicitly protected with `checked_sub(...).expect(...)`. This is the same bug class as the FertilizerPremint `remaining()` underflow: an unguarded subtraction whose safety depends entirely on an implicit invariant that isn't enforced or asserted in code.

### Finding Description
`generate_index()` walks all accounts across all storages to build the in-memory accounts index and simultaneously derives the total capitalization and accounts data length from `IndexGenerationAccumulator`. When scanning a storage, non-zero-lamport accounts contribute their data length to `total_accum.accounts_data_len` via `accounts_data_len += data_len as u64;`. [1](#0-0) 

Later, `visit_duplicate_pubkeys_during_startup` finds pubkeys that have entries in more than one slot (duplicates from replayed roots) and sums the data length of the non-max-slot entries (i.e., the stale duplicate copies) into `accounts_data_len_from_duplicates`, filtering by `lamports > 0`. [2](#0-1) 

Back in `generate_index()`, the duplicate contribution is then subtracted from the two running totals:
```
total_accum.capitalization = total_accum
    .capitalization
    .checked_sub(capitalization_from_duplicates)
    .expect("capitalization cannot underflow");
total_accum.accounts_data_len -= accounts_data_len_from_duplicates;
``` [3](#0-2) 

Note the asymmetry: `capitalization` uses `checked_sub` with an explicit `.expect("capitalization cannot underflow")` guard, but `accounts_data_len` uses a raw `-=`. Both values are computed from the same duplicate-detection logic and rely on the same invariant ("the sum of duplicate contributions can never exceed the running total"), yet only one of the two is defensively checked. This mirrors the reported pattern in `FertilizerPremint.remaining()`, where a subtraction's safety relied on an unstated invariant instead of an explicit runtime check.

### Impact Explanation
- In debug builds (or any build compiled with `overflow-checks = true`, which is common for validator debug/test builds and some CI configurations), this will panic the whole node during snapshot-based startup index generation if the invariant is ever violated (e.g., due to an edge case not yet covered — such as a stale duplicate entry whose data length was not counted the same way in `accounts_data_len`, for instance if it were somehow inserted directly into the index without passing through the same “accumulate len for slot” code path, or if `zero_lamport` accounting diverges between the two passes for some future code change). A panic here is a startup-time node crash — the process aborts before it can serve stake or replay, which is a direct availability impact.
- In release builds without overflow checks, the subtraction would silently wrap to a near-`u64::MAX` value instead of panicking. `accounts_data_len` feeds directly into `IndexGenerationInfo.accounts_data_len`, which is subsequently used to set the bank's on-chain accounts-data-size accounting. A silently corrupted (wrapped) `accounts_data_len` would desynchronize the node's local accounting of accounts-data usage from the rest of the cluster, which can affect rent/data-size limit enforcement and could, in principle, cause a consensus-relevant state divergence between honest nodes that hit the edge case and those that don't (e.g. differing hardware/build flags), or between a node's replayed state and its restored-from-snapshot state.
- Because this only fires when duplicate pubkeys across slots are visited during startup (a normal, common occurrence for any active validator whose ledger contains many slots for the same accounts), the code path itself is definitely reachable in production, unlike a purely theoretical or mocked-only scenario.

### Likelihood Explanation
This is a `Low`/`Medium`-likelihood issue in the same vein as the original report: no currently-known input drives `accounts_data_len_from_duplicates > total_accum.accounts_data_len` under the code as written today (the same accounting rule — non-zero-lamport accounts contribute their length — is used on both the "add" and "subtract" sides). However, the asymmetric handling (one path is defensively `checked_sub` + `expect`, the other is a raw `-=`) shows that the invariant is understood by the code's author to be non-trivial enough to warrant a guard for `capitalization`, yet it was omitted for `accounts_data_len`. Any future refactor, feature-gate change, or unhandled account state edge case (e.g., changes to how zero-lamport/obsolete accounts are counted in one path but not the other) can silently reintroduce the underflow without a corresponding compiler or test failure to catch it, exactly the "no native overflow protection assumed" class of bug from the report.

### Recommendation
Make the two accumulator updates consistent and defensive: replace the raw `-=` with `checked_sub(...).expect("accounts_data_len cannot underflow")` (mirroring the capitalization pattern immediately above it), so any invariant violation surfaces as a clear, actionable panic message rather than either (a) an unexplained panic message that doesn't point to `accounts_data_len`, or (b) silent wraparound in optimized builds. Additionally, add a unit test analogous to the existing `test_calculate_capitalization_overflow_intra_slot` / `_inter_slot` tests that exercises the duplicate-pubkey accounts-data-length reduction path, and add documentation of the invariant relied upon here (that "duplicate data length can never exceed total data length") directly in the code.
