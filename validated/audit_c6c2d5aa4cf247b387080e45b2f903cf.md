### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay/backup-verify tooling accept an executed output that diverges from the authenticated ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity gate used by replay/backup-verify code paths (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/chunk_result_verifier.rs`, `aptos-move/cli` debugger replay) to confirm that a freshly-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed on-chain and covered by the ledger accumulator/ledger-info signatures. The function checks status, `gas_used`, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check the state checkpoint hash (or the new `position_state_checkpoint_hash` field), which is otherwise a first-class field of the committed, signed `TransactionInfo`.

### Finding Description
`TransactionInfo` carries a `state_checkpoint_hash` (and, per the code comment, a newer `position_state_checkpoint_hash` for the "trading-native" feature) that is meant to bind the transaction's on-chain record to the resulting global/authenticated state root computed by the executor (`execution/executor/src/workflow/do_state_checkpoint.rs`, `do_ledger_update.rs`). This hash is part of `TransactionInfo`, which is the leaf hashed into the transaction accumulator and ultimately covered by the signed `LedgerInfo`.

`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  validates status, gas, write-set hash, and event root hash, but the trailing comment makes explicit that it intentionally omits checking the checkpoint hashes: [2](#0-1) 

This function is the sole correctness oracle used by:
- `storage/db-tool/src/replay_on_archive.rs` (`execute_and_verify`), which replays historical transactions from an archive and calls `ensure_match_transaction_info` to decide pass/fail for replay-verify tooling: [3](#0-2) 
- `aptos-move/cli/src/commands.rs` transaction-replay debugger, which uses the same call to decide whether a replayed transaction matches the on-chain record: [4](#0-3) 
- `ReplayChunkVerifier`/chunk executor verification path (`execution/executor/src/chunk_executor/chunk_result_verifier.rs`), which ultimately calls into `ensure_transaction_infos_match`, sharing the same comparison semantics for validating replayed/state-synced chunks against previously committed `TransactionInfo`s.

Because the checkpoint-hash fields are not compared, a locally re-executed transaction whose write set, gas, status, and events all match, but whose resulting authenticated state/position checkpoint root differs from what was actually committed and signed by validators, will be reported as "matching" by all of these tools. This means the state-integrity oracle used for archive replay-verification and for CLI-based transaction debugging/auditing cannot detect a class of divergence that is specifically bound to the checkpoint/root-hash commitment — the exact invariant category this bug class targets (VM output must survive executor-to-storage handoff unchanged, and authenticated proof/root fields must stay bound to the correct ledger state).

### Impact Explanation
Replay-verify and archive-verify (`storage/db-tool/src/replay_on_archive.rs`, `storage/db-tool/src/replay_verify.rs`) are the tools operators and the Aptos Foundation use to certify that historical/backup data reproduces the exact ledger state that was originally computed and cryptographically committed on mainnet. If a state-checkpoint-affecting divergence exists (e.g., a bug in state-checkpoint/root computation logic, a corrupted backup snapshot, or a future protocol change that mutates the checkpoint hash calculation) it would be silently accepted as "verified" by this tooling because the checkpoint hash is excluded from the equality check. This directly undermines the "committed state must match VM output" and "authenticated root binding" invariants required by the task's State-Integrity Gate, since the very tool responsible for asserting that invariant does not test the field that carries the authenticated root.

### Likelihood Explanation
This is not attacker-triggerable on its own (it requires some other bug or corruption to actually produce a wrong checkpoint hash), and the comment indicates the gap is a known, deliberate, and presumably temporary omission tied to gating a new feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) before enabling checkpoint-hash comparisons. However, the missing check is not itself feature-gated — it applies unconditionally to every replay/backup-verify invocation today, on mainnet or otherwise, regardless of whether the trading-native feature is enabled. Given the current effort level, I could not fully confirm within the available iterations whether the checkpoint hash is otherwise re-validated by a different, downstream mechanism (e.g., the accumulator-root comparison against a signed `LedgerInfo` in the online/backup restore flows), which would reduce practical exploitability of the gap for the online (non-CLI-replay) restore paths.

### Recommendation
Add the state-checkpoint hash (and `position_state_checkpoint_hash`, gated as needed by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) as a mandatory comparison field inside `ensure_match_transaction_info`, matching how `state_change_hash`, `event_root_hash`, and `gas_used` are already checked, so that replay-verify and CLI debugging tooling cannot mark a transaction as "verified" while its authenticated state root diverges from the committed `TransactionInfo`.

### Proof of Concept
Not applicable as a standalone PoC — this is a missing-check defect in a verification helper rather than a directly triggerable state-corruption bug. Demonstrating impact would require constructing (or already possessing) a `TransactionOutput` whose write set/gas/events/status match the recorded `TransactionInfo` but whose state checkpoint hash differs (e.g., via a bug in checkpoint computation, corrupted backup data, or a modified local execution environment), then showing `ensure_match_transaction_info` (and thus `replay_on_archive`/CLI replay) returns `Ok(())` despite the checkpoint-hash mismatch.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
