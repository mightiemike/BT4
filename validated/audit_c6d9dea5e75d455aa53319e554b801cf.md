### Title
Body-size check in `GetPaginatedProposalListServlet.doPost` bounds bytes but not JSON structural complexity, allowing disproportionately expensive parsing of a two-field message - (File: `framework/src/main/java/org/tron/core/services/http/GetPaginatedProposalListServlet.java`)

### Summary
`doPost` only guards the raw byte length of the request body via `Util.checkBodySize(input)` before handing the entire string to `JsonFormat.merge(input, build, visible)` for a `PaginatedMessage` that has just two scalar fields (`offset`, `limit`). Because deep JSON nesting is byte-cheap (e.g. repeating `{"a":` thousands of times consumes only a few bytes per level), an attacker can stay under the byte limit while forcing the parser to do work (recursive descent / stack depth) that is wildly out of proportion to the trivial two-field schema it is supposed to populate.

### Finding Description
The reachable path is: unauthenticated HTTP `POST /wallet/getpaginatedproposallist` → `GetPaginatedProposalListServlet.doPost` [1](#0-0)  → `Util.checkBodySize(input)` (byte-length check only) → `JsonFormat.merge(input, build, visible)`, which uses the hand-written (Orbitz-derived) JSON/text-format parser in `JsonFormat.java` [2](#0-1) .

`checkBodySize` only enforces a maximum number of bytes/characters in the raw string; it has no notion of JSON nesting depth, object/array count, or key repetition. `PaginatedMessage` has only two int fields, so any JSON object nesting/keys that don't map to `offset`/`limit` must still be *consumed* (skipped) by the parser so it can continue past them to find valid fields or detect the end of input. A hand-rolled recursive-descent JSON parser (as opposed to an iterative one with an explicit depth counter) typically implements this skip-logic recursively, meaning parse cost/stack depth scales with nesting depth of the payload rather than with the number of fields actually merged into the target message. An attacker can therefore construct a payload such as `{"offset":1,"limit":1,"x":{"x":{"x": ... }}}` with tens of thousands of nesting levels, using only a few bytes per level, staying safely under `checkBodySize`'s byte limit while making the parser do orders of magnitude more work (or exhaust the JVM call stack, throwing `StackOverflowError`) compared to a minimal valid `{"offset":1,"limit":1}` payload of similar byte size.

None of the existing guards address this:
- `Util.checkBodySize` only checks byte length, not structural complexity.
- `RateLimiterServlet.service` throttles request *rate* (QPS/IP) [3](#0-2) , not per-request CPU/stack cost — a single request within QPS limits can still consume disproportionate resources.
- The endpoint requires no authentication/authorization, so it is reachable by any unprivileged caller of the public HTTP API.

### Impact Explanation
Each such request can consume CPU time and/or stack depth far beyond what the byte-size limit is meant to bound, on a servlet thread shared with other public API traffic. Repeated or concurrent submission of such payloads (bounded only by the existing QPS/IP rate limiter, which limits request count, not cost-per-request) can degrade or stall the HTTP API service, i.e., a public-cost-control violation / denial-of-service against the FullNode HTTP API. This does not lead to unauthorized state change, fund theft, or consensus divergence — the impact is confined to service availability/performance of the HTTP API layer.

### Likelihood Explanation
No authentication or special privilege is required — any caller of the public HTTP API can send such a request. The payload is easy to construct (repeated nesting characters). The limiting factor for how damaging this is depends on the exact `checkBodySize` byte limit and whether `JsonFormat`'s parser has any existing depth guard — I was not able to directly inspect the innermost recursive-descent/skip logic of `JsonFormat.merge` or the exact numeric limit configured in `Util.checkBodySize` within the indexed context, so the precise magnitude of the disproportion (and whether a depth limit already exists further down in `JsonFormat.java`) could not be fully confirmed from the available code. This should be verified directly in the repository (or via a Devin session) before treating the severity as certain.

### Recommendation
- Add an explicit JSON nesting-depth limit (and ideally a token/field-count limit) enforced during parsing in `JsonFormat.merge`, independent of the raw byte-size check in `Util.checkBodySize`.
- Reject payloads whose object/array nesting exceeds a small fixed depth (e.g., matching the maximum nesting realistically needed by any `Message` type parsed via this servlet family) before or during parsing, rather than only after full parse.
- Consider converting the skip-unknown-field logic in `JsonFormat` to an iterative implementation with an explicit depth counter to avoid `StackOverflowError` regardless of size limits.

```java
@Test
public void testDeepNestingCostDisproportion() throws Exception {
    int depth = 50_000; // tune below checkBodySize's byte limit
    StringBuilder sb = new StringBuilder("{\"offset\":1,\"limit\":1,\"x\":");
    for (int i = 0; i < depth; i++) sb.append("{\"x\":");
    sb.append("1");
    for (int i = 0; i < depth; i++) sb.append("}");
    sb.append("}");
    String maliciousPayload = sb.toString();

    String minimalPayload = "{\"offset\":1,\"limit\":1}";

    // Confirm both pass the size check
    Util.checkBodySize(maliciousPayload);
    Util.checkBodySize(minimalPayload);

    long t0 = System.nanoTime();
    try {
        PaginatedMessage.Builder b1 = PaginatedMessage.newBuilder();
        JsonFormat.merge(maliciousPayload, b1, false);
    } catch (StackOverflowError | Exception e) {
        // record whether it throws StackOverflowError or takes disproportionate time
    }
    long malCost = System.nanoTime() - t0;

    long t1 = System.nanoTime();
    PaginatedMessage.Builder b2 = PaginatedMessage.newBuilder();
    JsonFormat.merge(minimalPayload, b2, false);
    long minCost = System.nanoTime() - t1;

    // Assert bounded overhead expectation is violated:
    assertTrue("Expected disproportionate cost or crash for deeply nested payload",
        malCost > minCost * 100 /* or catch StackOverflowError */);
}
```
Expected result if the vulnerability is present: the malicious payload either throws `StackOverflowError`/takes CPU time orders of magnitude greater than the minimal payload, despite both passing `Util.checkBodySize`, demonstrating the cost/size correlation bypass.
