This confirms the finding. The impact is real but bounded: `stateTransitionCreateSecretsRequest` rejects create for existing keys, and update/delete on non-existent secrets returns not-found — so create-replay is not directly destructive after successful creation (it fails "key already exists"), but a replayed **update** or **delete** on a still-existing secret would re-execute successfully, since the KV store `WriteSecret`/`DeleteSecret` are unconditional writes/removes with no per-request idempotency tracking beyond the replay guard itself [1](#0-0) . This confirms the replay guard is indeed the sole layer preventing exact-duplicate authorized JSON-RPC vault requests from being re-executed.

### Title
In-memory-only RequestReplayGuard allows replay of previously-authorized vault.secrets.* requests after node restart - (File: core/capabilities/vault/request_replay_guard.go)

### Summary
`RequestReplayGuard` stores seen request digests only in an in-process `map[string]int64` guarded by a `sync.Mutex`, with no persistence or shared backing store. Because `NewAuthorizer` constructs a fresh `RequestReplayGuard` via `NewRequestReplayGuard()` on every instantiation, any node restart, failover, or authorizer re-creation wipes all previously recorded digests, allowing a previously-authorized (but not-yet-expired) request to be replayed and re-authorized.

### Finding Description
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` as the sole mechanism preventing re-execution of an already-authorized digest [2](#0-1) . The guard itself is defined as an in-memory struct: `type RequestReplayGuard struct { mu sync.Mutex; seen map[string]int64; nowFunc func() time.Time }`, created via `NewRequestReplayGuard()` which just allocates a fresh map [3](#0-2) . `NewAuthorizer` always builds a brand-new guard: `replayGuard: NewRequestReplayGuard()` [4](#0-3) .

Both authorization paths rely on this same single-process guard for one-time-use enforcement:
- Allow-list based auth only checks the on-chain/syncer allowlist expiry timestamp, not whether the request was already consumed [5](#0-4) .
- JWT based auth only validates token signature, scopes, tenant ID, and that the digest matches the claim `request_digest`; it does not track single-use of the digest itself [6](#0-5) .

The replay guard is explicitly documented as this shared safety net: "Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure that a given request digest is only accepted once" [7](#0-6) . Since it holds no persistent state, a node restart (or any event that re-instantiates the `authorizer`, e.g. via `NewGatewayHandler` → `NewAuthorizer`) resets the `seen` map to empty [8](#0-7) . An attacker who already sent one valid request (allowlisted or with a valid, unexpired JWT) can resend the identical bytes after the restart; `GatewayVaultRequestProcessor.authorizeAndStamp` will call `p.authorizer.AuthorizeRequest` again, which succeeds because the digest is no longer in the reset map [9](#0-8) .

Downstream, the KV store performs unconditional writes for update and unconditional removal for delete (`WriteSecret`/`DeleteSecret`), so a successfully replayed `vault.secrets.update` or `vault.secrets.delete` request re-executes against live state without any additional idempotency check [1](#0-0) . (Create requests are additionally guarded by a "key already exists" check in the OCR state transition, limiting — but not eliminating — impact for that specific method.)

### Impact Explanation
A replayed update/delete request causes unauthorized re-execution of a state-mutating vault operation for the legitimate owner after node restart — data tampering / unintended secret mutation or deletion, without any new attacker credential or privilege. This matches "misreporting/data tampering" and unauthorized workflow/vault-state mutation categories in Chainlink's bounty impact classification. It does not grant privilege escalation or exfiltration by itself, since the attacker still needs a previously legitimately obtained, unexpired allowlist/JWT-authorized request — but it breaks the stated invariant "a given authorized request digest must never be executed twice."

### Likelihood Explanation
Feasibility depends on: (1) attacker possessing one valid request that has not yet expired (allowlist entry not expired, or JWT not expired plus `jwtValidationLeeway`), and (2) a node restart, failover, or authorizer re-instantiation occurring within that validity window. Node restarts/deploys/failovers are routine operational events, and JWT/allowlist expiry windows can be minutes long, making this readily reproducible in normal operational conditions rather than requiring rare or complex preconditions.

### Recommendation
Back `RequestReplayGuard` with persistent or externally-shared storage (e.g., a DB table or shared cache keyed by digest with TTL matching `expiresAt`) so that recorded digests survive process restarts and are consistent across replica/failover instances, rather than resetting to an empty in-memory map on every `NewAuthorizer` call.

### Proof of Concept
Add an integration test in `core/capabilities/vault/request_replay_guard_test.go` or `authorizer_test.go`:
1. Construct an `authorizer` via `NewAuthorizer` with a mock `Authorizer` that returns a fixed digest and a future `expiresAt`.
2. Call `AuthorizeRequest` once — assert `err == nil` (request accepted).
3. Simulate a restart by constructing a brand-new `authorizer` via `NewAuthorizer` (mirroring what `NewGatewayHandler` does on process start), using the same mock returning the same digest/expiry.
4. Call `AuthorizeRequest` again on the new authorizer with the identical request — assert `err == nil` (currently succeeds) instead of the expected `errors.Is(err, ErrRequestAlreadySeen)`, demonstrating that restart resets replay protection for an otherwise still-valid, not-yet-expired digest.

	}

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

func (v *jwtBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	isEnabled, err := v.authEnabledGate.Limit(ctx)
	if err != nil {
		v.lggr.Errorw("failed to resolve JWTBasedAuth gate", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to resolve JWTBasedAuth gate: %w", err)
	}
	if !isEnabled {
		v.lggr.Debugw("JWTBasedAuth rejected request because it is disabled", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("JWTBasedAuth is disabled")
	}

	claims, err := v.validateToken(ctx, req.Auth)
	if err != nil {
		v.lggr.Debugw("JWTBasedAuth token validation failed", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("invalid JWT auth token: %w", err)
	}

	if scopeErr := enforceVaultJWTOAuthScopes(req.Method, claims.OAuthScopes); scopeErr != nil {
		v.lggr.Debugw("JWTBasedAuth OAuth scope rejected request", "method", req.Method, "requestID", req.ID, "orgID", claims.OrgID, "scopes", claims.OAuthScopes, "error", scopeErr)
		return nil, fmt.Errorf("invalid JWT auth token: %w", scopeErr)
	}

	if claims.TenantID == 0 {
		return nil, ErrMissingTenantID
	}
	if claims.TenantID != v.expectedTenantID {
		v.lggr.Debugw("JWT tenant id does not match job spec auth0 tenantID", "method", req.Method, "requestID", req.ID, "orgID", claims.OrgID, "claimsTenantID", claims.TenantID, "expectedTenantID", v.expectedTenantID)
		return nil, fmt.Errorf("%w: jwt tenant id %d expected tenant id %d", ErrJWTTenantIDJobSpecMismatch, claims.TenantID, v.expectedTenantID)
	}

	requestDigest, err := req.Digest()
	if err != nil {
		v.lggr.Debugw("JWTBasedAuth failed to compute request digest", "method", req.Method, "requestID", req.ID, "orgID", claims.OrgID, "workflowOwner", claims.WorkflowOwner, "error", err)
		return nil, fmt.Errorf("failed to compute request digest: %w", err)
	}

	if !strings.EqualFold(requestDigest, claims.RequestDigest) {
		v.lggr.Debugw("JWTBasedAuth request digest mismatch", "method", req.Method, "requestID", req.ID, "orgID", claims.OrgID, "workflowOwner", claims.WorkflowOwner, "computedDigest", requestDigest, "claimedDigest", claims.RequestDigest)
		return nil, fmt.Errorf("request digest mismatch: computed=%s claimed=%s", requestDigest, claims.RequestDigest)
	}

	derivedWorkflowOwner, err := DeriveJWTAuthorizedVaultWorkflowOwner(claims.OrgID, claims.TenantID, claims.WorkflowOwner)
	if err != nil {
		v.lggr.Debugw("JWTBasedAuth failed to derive authorized workflow owner", "method", req.Method, "requestID", req.ID, "orgID", claims.OrgID, "error", err)
		return nil, fmt.Errorf("invalid JWT auth token: %w", err)
	}

	authExpiresAt := claims.ExpiresAt.UTC().Add(jwtValidationLeeway).Unix()
	v.lggr.Debugw("JWTBasedAuth authorization succeeded", "method", req.Method, "requestID", req.ID, "orgID", claims.OrgID, "workflowOwner", derivedWorkflowOwner, "digest", requestDigest, "expiresAt", authExpiresAt)
	return &AuthResult{
		orgID:         claims.OrgID,
		workflowOwner: derivedWorkflowOwner,
		digest:        requestDigest,
		expiresAt:     authExpiresAt,
	}, nil
}
