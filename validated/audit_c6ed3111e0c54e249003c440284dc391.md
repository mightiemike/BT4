### Title
Sharded block execution never appends `BlockEpilogue` transaction while unsharded execution does, causing divergent committed transaction/state output for the same block - (`File: execution/executor/src/workflow/do_get_execution_output.rs`)

### Summary
`DoGetExecutionOutput::by_transaction_execution_unsharded` invokes the VM through `VMBlockExecutor::execute_block`, passing the full `TransactionSliceMetadata`, which allows the VM to synthesize and append a `Transaction::BlockEpilogue` at the end of the block [1](#0-0) . The sharded counterpart, `by_transaction_execution_sharded`, only receives `append_state_checkpoint_to_block()` (an `Option<HashValue>`) and forwards it nowhere — `execute_block_sharded` is called without any transaction-slice-metadata argument at all [2](#0-1) , and the `VMBlockExecutor::execute_block_sharded` trait signature itself has no parameter for slice metadata or block hash [3](#0-2) . Consequently, the sharded path can never construct a `BlockEpilogue` transaction, regardless of `TransactionSliceMetadata::Block` being supplied by the caller.

### Finding Description
`by_transaction_execution` dispatches based on `ExecutableTransactions::Unsharded` vs `::Sharded` [4](#0-3) . For the unsharded branch, the complete `TransactionSliceMetadata` is passed into `execute_block`, and the underlying `BlockOutput` may contain a `block_epilogue_txn` that gets pushed onto the committed `transactions` vector along with its manufactured auxiliary info and hotness write set [5](#0-4) .

For the sharded branch, only `transaction_slice_metadata.append_state_checkpoint_to_block()` (an `Option<HashValue>`) is passed, and it is used *exclusively* to set the `is_block` flag on the `Parser` builder — it is never forwarded into `execute_block_sharded`, which has no way to receive it since the trait method for sharded execution takes no metadata parameter at all [6](#0-5) . The code even contains a self-acknowledged gap: `// TODO(Manu): Handle state checkpoint here.` immediately after the sharded execution call [7](#0-6) .

The downstream `Parser::parse` then sets `is_block = true` (because `append_state_checkpoint_to_block` was `Some`) but finds that `transactions.last()` is not a `Transaction::BlockEpilogue` (because sharded execution never produced one), so the `if let Some(Transaction::BlockEpilogue(payload)) = transactions.last()` branch silently fails to match and `block_end_info` remains `None` [8](#0-7) .

The net effect: for the identical block (same `TransactionSliceMetadata::Block { parent, child }`), the unsharded path commits one extra `Transaction::BlockEpilogue` entry with its own `TransactionInfo`, write set (hotness updates), and status, while the sharded path commits a strictly shorter transaction/output vector missing that entry and never recovers `block_end_info`. This yields different transaction counts, different accumulator roots, and different resulting `LedgerState` for what should be the same input block.

### Impact Explanation
This is a state-commitment-integrity defect, not a presentation-only bug. If sharded block execution and unsharded block execution are both live code paths that can be selected to execute the same certified block (e.g., across different validator configurations, or the sharded remote/local executor path used for performance in some deployments vs. the standard path used elsewhere, or in replay/verification tooling that re-executes a historical block through a different path than the one that originally produced it), the two paths derive materially different `TransactionInfo` sequences and ledger states for byte-identical input. This is exactly the class of hard-fork-only divergence the review scope calls out: honest nodes executing the same block via different — but both "valid" — code paths would disagree on the committed state root and transaction count, which is a consensus/state-integrity violation rather than a cosmetic one.

### Likelihood Explanation
Triggering this requires no privileged action or malicious input — it happens deterministically any time a block boundary (`TransactionSliceMetadata::Block`) is executed through the sharded execution path, since the mechanism that appends `BlockEpilogue` in the unsharded path is structurally absent from the sharded path (the trait method itself has no metadata parameter). It is a systemic, unconditional divergence whenever the sharded path is exercised on a real block, not a rare corner case.

### Recommendation
Extend `VMBlockExecutor::execute_block_sharded` (and its call sites, including `execute_block_sharded` in `do_get_execution_output.rs`) to accept and honor `TransactionSliceMetadata`/`append_state_checkpoint_to_block`, ensuring the sharded path synthesizes the identical `BlockEpilogue` transaction (with identical write sets, hotness data, and `block_end_info`) that the unsharded path produces for the same block boundary. Add a cross-path determinism test that executes the same block through both `by_transaction_execution_unsharded` and `by_transaction_execution_sharded` with identical `TransactionSliceMetadata::Block` and asserts the resulting `to_commit` transaction/output vectors (and `block_end_info`) are identical.

### Proof of Concept
1. Construct a block with `TransactionSliceMetadata::Block { parent, child }` where `child` is the block's own id, containing at least one user transaction.
2. Call `DoGetExecutionOutput::by_transaction_execution` twice on the identical input: once with `ExecutableTransactions::Unsharded(...)`, once with `ExecutableTransactions::Sharded(...)` (partition the same transactions into shards).
3. Observe that the unsharded result's `to_commit.transactions` ends with a `Transaction::BlockEpilogue(..)` entry and `maybe_block_end_info` is `Some(..)`, per [5](#0-4) .
4. Observe that the sharded result's `to_commit.transactions` has no `BlockEpilogue` entry and `maybe_block_end_info` is `None`, because `execute_block_sharded` never receives the block-boundary metadata, per [9](#0-8)  and [3](#0-2) .
5. Diff the two `ExecutionOutput.to_commit` vectors and `result_state` roots to demonstrate byte-level divergence for the identical input block.

    fn by_transaction_execution_unsharded<V: VMBlockExecutor>(
        executor: &V,
        transactions: Vec<SignatureVerifiedTransaction>,
        auxiliary_infos: Vec<AuxiliaryInfo>,
        parent_state: &LedgerState,
        state_view: CachedStateView,
        onchain_config: BlockExecutorConfigFromOnchain,
        transaction_slice_metadata: TransactionSliceMetadata,
    ) -> Result<ExecutionOutput> {
        let txn_provider = DefaultTxnProvider::new(transactions, auxiliary_infos.clone());
        let block_output = Self::execute_block::<V>(
            executor,
            &txn_provider,
            &state_view,
            onchain_config,
            transaction_slice_metadata,
        )?;
        let (mut transaction_outputs, block_epilogue_txn) = block_output.into_inner();
        let (transactions, mut auxiliary_infos) = txn_provider.into_inner();
        let mut transactions = transactions
            .into_iter()
            .map(|t| t.into_inner())
            .collect_vec();
        if let Some(block_epilogue_txn) = block_epilogue_txn {
            transactions.push(block_epilogue_txn.into_inner());

            // Check if all existing auxiliary infos are None to maintain consistency
            let all_auxiliary_infos_are_none = auxiliary_infos
                .iter()
                .all(|info| matches!(info.persisted_info(), PersistedAuxiliaryInfo::None));

            let block_epilogue_aux_info = if all_auxiliary_infos_are_none {
                // If all other auxiliary infos are None, use None for consistency (version 0 behavior)
                AuxiliaryInfo::new(PersistedAuxiliaryInfo::None, None)
            } else {
                // Otherwise, use the standard function (version 1 behavior)
                AuxiliaryInfo::auxiliary_info_at_txn_index(transactions.len() as u32 - 1)
            };

            auxiliary_infos.push(block_epilogue_aux_info);
        }
