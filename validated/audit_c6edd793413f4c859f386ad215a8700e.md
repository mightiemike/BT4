### Title
Legitimate PoX reward address colliding with the sentinel burn address causes stacker reward loss - ([File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs])

### Summary
The Crowdfund bug used `address(0)` both as "no initial contributor" sentinel and as a mintable/burnable NFT owner, so a real balance became indistinguishable from — and burnable via — the null-address slot. The Stacks analog is `PoxAddress::standard_burn_address()` / `StacksAddress::burn_address()` (a p2pkh address whose `hashbytes` are all zero), which is used **both** as the semantic "this slot is unclaimed, must be burned" sentinel **and** as an address that the PoX-4 contract will happily accept as a *real* stacker's payout address, because `check-pox-addr-hashbytes` only validates length, not that the hash is non-zero.

### Finding Description
`PoxAddress::standard_burn_address(mainnet)` is documented as "consensus critical" and is used to pad/backfill reward-set slots that have no real stacker: [1](#0-0) 

It is used as a placeholder in the consensus-critical block-commit validation path when only one real recipient exists for a two-slot reward cycle: [2](#0-1) 

and as a fold-based "is the whole recipient set burn-only" shortcut that skips the (expensive) PoX-descendant check entirely: [3](#0-2) 

However, nothing in the PoX-4 contract prevents a stacker (or, more importantly, a pool operator/delegate who chooses the `pox-addr` on behalf of delegators) from registering a reward address whose `hashbytes` are all zero — `check-pox-addr-hashbytes` only checks length, not that the hash is non-zero: [4](#0-3) 

If a real reward-set entry's PoxAddress equals the sentinel burn address (hash160 = 0x00...00, version p2pkh), then:
1. `recipient_set_all_burns` in `check_pox_pre_waterfall` will evaluate `addr.is_burn()` as `true` for that "real" recipient, exactly like the padded sentinel would. If this happens to be the only recipient in the set (e.g. a single pool aggregated a reward slot), `recipient_set_all_burns` becomes `true` even though a legitimate staker actually earned that slot, forcing `self.all_outputs_burn()` to be required — i.e. the protocol now **requires** the miner to burn instead of paying the legitimate PoX participant.
2. In the two-recipient case, the same real address is literally identical (via `to_burnchain_repr()`) to the padding entry pushed at line 986, so the "find and remove" matching logic in the post-waterfall path cannot distinguish "the real recipient happens to be zero-hash" from "there was no second recipient, so pad with burn."

Because `hashbytes = 0x00…00` is a value fully controlled by the party constructing the `stack-stx` / `delegate-stx` / `stack-aggregation-commit` transaction (frequently a stacking-pool operator acting on behalf of many delegators, not the delegators themselves), this party can unilaterally cause an entire pool's PoX reward slot for a cycle to be treated by every node identically to "no stacker, burn only" — with **no majority, no admin key, and no protocol violation from the PoX-4 contract's perspective** (the address passes all Clarity-level validation).

### Impact Explanation
This is a minority/unprivileged-triggerable equality break: "a reward slot with a legitimately stacked amount gets paid to the correct party." A single pool operator/delegate choosing `hashbytes = 0` as the pool's PoX reward address collapses that slot into the "burn" sentinel used purely for bookkeeping/padding, forcing the network-wide consensus rule to require burning rather than paying real STX-backed BTC rewards to the pool's delegators for that cycle. This matches the "High — reward mis-payment bounded to fees/rewards for a cycle" impact bucket: real, staked funds do not earn their expected BTC yield because the address they registered is indistinguishable from the internal null/placeholder value, mirroring the underlying Crowdfund root cause of conflating a sentinel value with a valid, funds-bearing identity.

### Likelihood Explanation
Low-to-moderate but fully unprivileged and reproducible: any party that controls the PoX reward-address field of a `stack-stx`/`delegate-stx`/`stack-aggregation-commit*` call (most commonly a stacking-pool operator, who is not the party whose STX is at risk) can set `hashbytes` to all zero. No majority of signers or miners is required, and no bug is triggered in the Clarity contract itself — only in the Rust-side consensus interpretation of `is_burn()` against real reward-set entries in `leader_block_commit.rs`.

### Recommendation
- Reject PoX reward addresses whose `hashbytes` are the canonical all-zero value at the Clarity layer (`check-pox-addr-hashbytes` / `stack-stx` / `delegate-stx` / aggregation-commit entry points), the same mitigation direction PartyDAO took ("do not allow… when the sentinel value is used").
- Alternatively, make the sentinel/placeholder `standard_burn_address` unrepresentable as a valid Bitcoin PoX payout address (e.g., use an address with no possible corresponding scriptPubKey, or tag placeholder entries out-of-band rather than relying on value equality) so `is_burn()` can never collide with a legitimately-registered reward address.

### Proof of Concept
Conceptual PoC (Rust-side, mirroring the Solidity PoC's structure):
1. Have a stacking-pool operator call `delegate-stx` / `stack-aggregation-commit-indexed` with `pox-addr = { version: 0x00, hashbytes: 0x00*20 }` for a reward cycle where this is the only registered PoX address for that slot (`v0.recipients = [(standard_burn_address, ix)]`).
2. Observe that `leader_block_commit.rs::check_pox_pre_waterfall`'s `recipient_set_all_burns` fold evaluates to `true` for this recipient set, forcing `self.all_outputs_burn()`—i.e. consensus now requires the miner to burn rather than pay the pool's legitimately-earned PoX reward for that cycle. [3](#0-2) 
3. Compare against `stackslib/src/chainstate/stacks/address.rs:346-355`, confirming the sentinel and the attacker-chosen address are byte-for-byte identical, and `contrib/boot-contracts-unit-tests/boot_contracts/pox-4.clar:477-483`, confirming the Clarity contract never rejects an all-zero hash.
