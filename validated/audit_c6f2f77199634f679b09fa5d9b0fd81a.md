### Title
Legacy `callToPrecompiledAddress` memory write bypasses caller-specified `outDataSize`, allowing a precompiled contract's output length to drive unmetered memory growth - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The Trail of Bits finding is about a low-level `.call()` whose return data size is attacker-controlled and unbounded, causing the caller to incur unmetered memory-expansion costs and an out-of-gas condition that leaves protocol state (`forwarded[id]`) inconsistent. The closest reachable analog in java-tron's TVM is in `Program.callToPrecompiledAddress`, where — unless `allowTvmSelfdestructRestriction` is active — the precompile's returned byte array is written to VM memory using the unbounded `memorySave(int addr, byte[] value)` overload instead of the caller-declared `outDataSize`-bounded write.

### Finding Description
When a contract executes `CALL`/`STATICCALL`/`DELEGATECALL` against a precompiled-contract address, `OperationActions.exeCall` pre-computes the memory cost using the caller-supplied `outDataOffs`/`outDataSize` via `program.memoryExpand(outDataOffs, outDataSize)` and `EnergyCost.getCalculateCallCost` (which charges energy based on `memNeeded(...)` from the stack-declared out-region only): [1](#0-0) 

The actual write of the precompile's result, however, happens in `Program.callToPrecompiledAddress`, which branches on the `allowTvmSelfdestructRestriction` flag: [2](#0-1) 

- When the flag is enabled, `memorySave(outDataOffs, outDataSize, out.getRight())` is used — this is the size-limited overload that clamps the write to the caller-declared `outDataSize`.
- When the flag is disabled (the legacy/pre-hardfork code path, still reachable on any deployment or historical block where `allowTvmSelfdestructRestriction` has not been activated), the code calls `memorySave(offset, out.getRight())` — the unbounded overload: [3](#0-2) 

This overload calls `memory.extendAndWrite(addr, allocSize, value)` (with `allocSize` derived from `value.length`, not from the energy-charged `outDataSize`), meaning the actual memory extension performed is sized by the precompile's own output length rather than by the caller-declared/energy-metered size. If a precompile's `execute(data)` can be made to return an output whose length is influenced by the contract-controlled input (e.g., extractable arrays such as `extractBytesArray`/`extractSigArray` in `PrecompiledContracts`, or `ModExp`'s modulus-length-derived output), the actual memory growth diverges from what was paid for at the `CALL` opcode's cost-calculation step, since `getCalculateCallCost` only charged for the stack-declared `out` region, not the precompile's real output size. [4](#0-3) 

This is analogous to the reported bug class: a downstream call's return-data size, rather than the caller's declared/metered bound, drives memory expansion — creating a metering/DoS gap rather than a bounded-cost operation.

### Impact Explanation
If the mismatch between energy-charged out-region and actually-written byte-array length can be triggered with a large enough delta, this allows a contract to force additional, unmetered memory expansion inside the TVM interpreter on every full node processing the transaction, with cost not reflected in the energy accounting performed at the `CALL` opcode. Because TVM execution happens on every validating/full node for every transaction, unmetered memory growth is a resource-consumption/DoS vector at the protocol-execution level (not merely a smart-contract-level bug), and it can also produce accounting mismatches between what a contract believed it received/paid for at the opcode level and what memory was actually mutated.

### Likelihood Explanation
Likelihood is Low/Medium and difficult to fully confirm without deeper review of every precompile's exact output-length semantics: most fixed/known precompiles (`ECRecover`, `Sha256`, `Ripempd160`, `Identity`) return either input-length or fixed-size output that is already implicitly bounded by their own energy cost calc, so the divergence, if any, would only be problematic for precompiles whose `execute` output length is not tightly coupled to their `getEnergyForData` energy charge, and only when `allowTvmSelfdestructRestriction` is not active. This flag is a chain-parameter that TRON's governance controls, so on live mainnet the vulnerable legacy path may already be disabled; this could not be conclusively verified from the indexed code alone.

### Recommendation
- Short term: Remove or route all precompiled-contract memory writes through the size-limited `memorySave(offset, allocSize, value)` overload (as already done under `allowTvmSelfdestructRestriction`), rather than keeping a legacy unbounded-write branch, so that written size is always clamped to the caller-declared/energy-metered `outDataSize` regardless of hard-fork flag state.
- Long term: Audit every `PrecompiledContract.execute()` implementation to ensure returned byte array lengths are always tightly bounded and consistent with `getEnergyForData()`, and add regression tests asserting that memory expansion inside `callToPrecompiledAddress` never exceeds the energy-charged `out` region computed in `EnergyCost.getCalculateCallCost`.

### Proof of Concept
Not independently reproducible from the indexed code alone: exploitation would require identifying a precompiled contract whose `execute(data)` output length can be made to exceed the caller-declared `outDataSize`/energy-charged out region while running with `allowTvmSelfdestructRestriction` disabled, then measuring the resulting memory-expansion cost against the energy actually deducted at the `CALL` opcode. This requires validating exact precompile output-length semantics and confirming the flag's activation state on a target network, both of which were not confirmed within the available index.
