Based on the java-tron production code, I found a concrete structural analog to the reported Aera Balancer front-running issue: the TRC10 Bancor-style `Exchange` liquidity system exposes a swap contract with slippage protection but a liquidity-withdrawal contract with none.

### Title
Missing minimum-received-amount check in `ExchangeWithdrawContract` enables front-running/sandwich manipulation of liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`/`ExchangeWithdrawActuator` lets an exchange pool creator withdraw `tokenQuant` of one token and a proportional `anotherTokenQuant` of the paired token, computed live from the pool's current balances at execution time. Unlike the sibling `ExchangeTransactionContract` (swap), which has an `expected` field enforcing a minimum output, the withdraw path has no analogous minimum for `anotherTokenQuant`. This mirrors exactly the reported `AeraVaultV1.returnFunds()` bug class: a withdrawal function that pulls out pool holdings at a ratio determined at execution time, with no caller-specified minimum protecting against pre-transaction manipulation of that ratio.

### Finding Description
In `ExchangeWithdrawActuator.doValidate()` and `execute()`, `anotherTokenQuant` is derived purely from the exchange's `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction executes: [1](#0-0) 
The only checks performed are that the balances are sufficient and that the Bancor-curve rounding is "precise enough" — there is no field in `ExchangeWithdrawContract` allowing the caller to specify/enforce a minimum acceptable `anotherTokenQuant`: [2](#0-1) 

Contrast this with `ExchangeTransactionContract`, which explicitly carries an `expected` field and enforces it before allowing the trade to execute — i.e., the exact mitigation the Aera report recommends is already implemented for the *swap* path, but not for the *withdraw* path: [3](#0-2) [4](#0-3) 

The `Exchange` (TRC10 bancor-relay AMM) can be created and controlled by any ordinary account — this is not a privileged/trusted-role feature; only the pool's creator address may withdraw, but that creator is a normal unprivileged user, not a witness/committee/superrepresentative: [5](#0-4) 

### Impact Explanation
Because withdrawal payout ratios are computed against the live, front-runnable pool balances with no minimum-output enforcement, an attacker can submit an `ExchangeTransactionContract` swap immediately before the victim's `ExchangeWithdrawContract` transaction (ordered by fee/priority within the same block) to shift `firstTokenBalance`/`secondTokenBalance`. The victim's withdrawal then executes against the manipulated ratio, causing them to receive a distribution of tokens (and, due to the Bancor curve's fee/slippage characteristics, potentially less aggregate value) than what they would have received absent the manipulation — the attacker can then reverse their swap afterward to lock in the extracted value. This is a classic sandwich-style accounting-divergence impact on a market/exchange primitive, directly matching the "underprotected withdrawal from an AMM-like pool" bug class in the report.

### Likelihood Explanation
Any account can create an `Exchange` pool via `ExchangeCreateContract` and any account (including bots) can submit `ExchangeTransactionContract` swaps against it, so the preconditions are fully attacker-controlled and require no special privilege. The attack only requires ordering a swap transaction before a known/predictable creator withdrawal in the same or an adjacent block, which is straightforward given transaction pools are public prior to block inclusion.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract`, analogous to `ExchangeTransactionContract.expected`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` so that the calculated `anotherTokenQuant` (and/or `tokenQuant` payout) cannot fall below a caller-specified minimum, reverting the transaction otherwise.

### Proof of Concept
1. Alice creates an `Exchange` pool P with TRX and TokenA (`ExchangeCreateContract`), balances e.g. 1000 TRX / 3000 TokenA.
2. Alice wants to withdraw her share and submits `ExchangeWithdrawContract{exchange_id: P, token_id: TRX, quant: 1000}` expecting to receive proportional TokenA back.
3. Bob observes Alice's pending withdrawal transaction and front-runs it with an `ExchangeTransactionContract` swap that sharply shifts the TRX/TokenA ratio in pool P (e.g., dumping a large amount of TokenA into P to reduce its TRX balance, pushing the exchange rate against TokenA holders).
4. Alice's withdrawal executes after Bob's swap; `ExchangeWithdrawActuator` computes `anotherTokenQuant` from the now-manipulated `firstTokenBalance`/`secondTokenBalance` (lines 77-89 above), so Alice receives a TokenA amount she never agreed to and cannot reject, since no `expected` minimum exists to revert the transaction.
5. Bob then reverses his swap in pool P (or elsewhere) to realize the extracted value, completing the sandwich.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
