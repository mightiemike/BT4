### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay-verify/chunk-replay accept a state root that diverges from the authenticated `TransactionInfo` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single choke point used by both the chunk-executor's replay path (`execution/executor/src/chunk_executor/mod.rs`, `verify_execution`) and the archive replay-verify tool (`storage/db-tool/src/replay_on_archive.rs`) to confirm that locally re-executed output matches the authenticated `TransactionInfo` pulled from a backup/chunk before it is treated as valid. It checks status, gas, `state_change_hash` (write-set hash) and `event_root_hash`, but — per its own comment — deliberately omits `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only status/gas/write-set-hash/event-root-hash and explicitly documents that it "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." This function is the sole state-integrity gate used by:
- `ChunkExecutorInner::verify_execution`, which calls it per-transaction during chunk replay to accept re-executed `TransactionOutput`s against the trusted `transaction_infos` decoded from a backup manifest: [2](#0-1) .
- `ReplayVerifyController::execute_and_verify` in the archive replay-verify db-tool, the tool whose entire purpose is to catch consensus/state divergence against historical backups: [3](#0-2) .

Because the state (Sparse-Merkle / Jellyfish-Merkle) checkpoint root, hot-state checkpoint root, and position-state checkpoint root are not compared, a local execution that produces the *same write set and events* but a *different resulting state tree root* (e.g., due to a JMT/hot-state computation bug, a storage schema/versioning bug, or a divergent code path gated behind the `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO` feature flags referenced in `execution/executor/src/workflow/do_ledger_update.rs`) will be reported as a **successful, matching replay**, even though the locally committed state-checkpoint root does not match the one authenticated by the backup's `TransactionAccumulatorRangeProof`/`LedgerInfoWithSignatures`. This is exactly the "authenticated proof context bound to the wrong root" class the review criteria call out: [4](#0-3) .

### Impact Explanation
Replay-verify is the tool operators/auditors rely on to detect silent state divergence from historical, signature-authenticated backups. If the state-checkpoint (JMT) root diverges from what validators actually committed — due to a bug elsewhere in state-checkpoint computation (hot state, position state, or plain SMT) — this comparator will not flag it because it never compares `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`. The same gap applies to `ChunkExecutorInner::verify_execution` used for normal state-sync/backup-restore-driven chunk replay, meaning a node could silently persist a state tree whose root differs from the one authenticated by the accumulator/ledger-info proof chain, without any error being raised. Since state-checkpoint hashes feed directly into `TransactionInfo::hash()` which is what the transaction accumulator commits to and what `LedgerInfo.transaction_accumulator_hash()` ultimately authenticates via `AccumulatorProof`/`AccumulatorRangeProof` (`types/src/proof/definition.rs`), this weakens the guarantee that "committed state differs from correct VM result" is caught — a High severity integrity gap on the exact proof/commit boundary the report is meant to probe. The comment itself flags this as a known, acknowledged gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), which somewhat limits current severity since that feature isn't enabled yet, but the check is already exercised unconditionally by both replay paths today.

### Likelihood Explanation
The comparator is invoked unconditionally on every replay/backup-verify path today; the gap becomes latent when the write set and events happen to match but the state root does not (e.g. subtle bugs in `DoStateCheckpoint`/hot-state/position-state root computation, or divergent handling of `TransactionInfoV1` fields). This requires an independent bug in checkpoint-hash computation to actually manifest, so it's not directly triggerable by an unprivileged attacker on its own — it's a missing detection mechanism (a "gap in the safety net") rather than a directly exploitable state-corruption primitive by itself. It matters primarily as: (1) a real gap that a hard-fork/replay divergence would sail through undetected, and (2) it is authored as a deliberate, TODO-tagged trade-off rather than an oversight, which the code itself acknowledges needs to be closed before feature-gating on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present on the locally computed side) against the corresponding fields of the trusted `txn_info`, exactly as is already done for `state_change_hash` and `event_root_hash`, so that replay-verify and chunk-replay cannot report success when the authenticated state-checkpoint root diverges from local execution.

### Proof of Concept
Not independently exploitable without a companion bug in state-checkpoint-root computation; the concrete PoC would be: construct/replay a chunk whose `TransactionOutput` write set and events match the trusted `TransactionInfo` bit-for-bit, but whose independently-computed `state_checkpoint_hash` (or hot/position state root) differs (e.g. by feeding a state view at a stale/incorrect version while keeping the write set identical). Feed this into `ChunkExecutorInner::verify_execution` or `ReplayVerifyController::execute_and_verify`; both will return `Ok(())`/no error despite the state root mismatch, because `ensure_match_transaction_info` never inspects the checkpoint-hash fields (`types/src/transaction/mod.rs:2139-2204`).

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
