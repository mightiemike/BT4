### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash`, letting a diverged state root pass replay/backup verification - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function used by the chunk-executor's `verify_execution` path and by `aptos-debugger` to confirm that a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` before it is accepted and applied to storage during replay/state-sync/backup-replay flows. The function checks status, gas, write-set hash (`state_change_hash`) and event root hash, but it never compares the locally computed state-checkpoint root against `txn_info.state_checkpoint_hash()`. This is explicitly acknowledged in the code's own comment as a gap.

### Finding Description
`ensure_match_transaction_info` is documented as the authority for confirming a `TransactionOutput` matches an authenticated `TransactionInfo`: [1](#0-0) 

It validates status, gas, write-set hash, and event root hash: [2](#0-1) 

But it stops there — the trailing comment admits the state/hot-state checkpoint hash and `position_state_checkpoint_hash` are never checked: [3](#0-2) 

This function is the sole per-transaction correctness gate used by the chunk executor's replay-verification path, `verify_execution`, which calls it on locally re-executed `TransactionOutput`s against the trusted `transaction_infos` read from an archive/backup: [4](#0-3) 

and by `db-tool`'s `replay_on_archive` verify workflow, and by `aptos-debugger`'s mismatch printer, both of which rely on it to detect divergence between local VM execution and the authenticated (backed-up) ledger.

By contrast, `TransactionOutputListWithProof::verify` (used to validate output lists coming over the wire, e.g. for state sync) has the identical gap — it validates events, write-set hash, gas, status and transaction hash, but never the state-checkpoint hash either: [5](#0-4) 

The state-checkpoint hash is the Sparse-Merkle-Tree root summarizing the entire world state after a checkpoint transaction — it is the strongest state-commitment invariant a `TransactionInfo` carries, and it is precisely the value that both `db-tool replay-verify` and `aptos-debugger` are meant to use to catch consensus-vs-storage or hard-fork-style state divergence. Because it is silently skipped, a transaction whose write set superficially hashes correctly (`state_change_hash` match) but whose resulting Sparse-Merkle-Tree root differs from what was actually committed on-chain (e.g., due to a state-application bug, an incorrectly materialized delayed-field/resource-group write, or a local storage divergence) will still pass `ensure_match_transaction_info` / `verify_execution`, `db-tool replay_on_archive::verify`, and `aptos-debugger`'s mismatch detection.

### Impact Explanation
This breaks the state-proof-integrity invariant that authenticated/proof-bearing outputs must stay bound to the correct ledger state root. A wrong or corrupted state-checkpoint root — the on-chain summary of world state at a checkpoint — is exactly the class of divergence these tools are supposed to detect (as the TODO comment itself states: "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"). Silently accepting a divergent state root in `replay_on_archive` or `aptos-debugger` verification defeats the operator/incident-response tooling used to detect state corruption or hard-fork divergence in an already-committed chain, undermining confidence in the audited/committed ledger state without any observable failure. It is, however, a detection/verification-tooling gap rather than a live consensus-time acceptance path — it does not by itself let bad blocks be committed by validators (BlockSTM/consensus verification paths are separate), but it removes the safety net meant to catch such divergence during replay and archive verification.

### Likelihood Explanation
The gap is unconditional (not behind a feature flag check at the call site) and is hit on every call to `ensure_match_transaction_info`, i.e., every time `db-tool replay_on_archive::verify`, `aptos-debugger`'s mismatch printer, or the chunk-executor's `verify_execution` (invoked from state-sync/backup replay with `VerifyExecutionMode::should_verify()`) runs. It requires an underlying root-cause divergence (e.g. a bug in state materialization/write-set application) to actually manifest, so this finding by itself is a missing detection/invariant, not an exploitable state-corruption primitive on its own — I could not find, within the scope of this scan, a concrete local root cause that produces a wrong `state_checkpoint_hash` while keeping `state_change_hash` correct; the comment in the code implies this is a known, intentionally deferred TODO tied to the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature.

### Recommendation
Add validation of `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` where applicable) against the locally computed Sparse-Merkle-Tree root inside `ensure_match_transaction_info` and `TransactionOutputListWithProof::verify`, gated appropriately behind whatever on-chain config controls availability of the local state-checkpoint hash, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, as the code comment recommends.

### Proof of Concept
Not applicable — this is a missing-check finding identified via static code review of `types/src/transaction/mod.rs` lines 2139–2203 and its callers; no concrete triggering root cause producing a mismatched `state_checkpoint_hash` (while other fields match) was independently established within this investigation, so I cannot provide an end-to-end PoC. Given this uncertainty and that the gap is an explicitly acknowledged TODO deferred behind an unlaunched feature flag rather than a proven exploitable state-commitment break, I flag this with reduced confidence rather than as a fully proven critical vulnerability.
