### Title
Unchecked `Option::unwrap()` on Cairo-Native compiler output causes a reachable panic during declared-class compilation - (File: `crates/apollo_compile_to_native/src/compiler.rs`)

### Summary
The Sierra-to-Native compilation path unwraps an `Option` returned by `cairo_native::executor::AotContractExecutor::from_path` without checking for `None`. A declarer can submit a class whose Sierra program compiles "successfully" (subprocess exit code 0) yet produces output that `AotContractExecutor::from_path` cannot fully load, causing this code to hit `.unwrap()` on `None` and panic — the same bug class as the referenced LibSass `Selector_List::populate_extends` NULL-pointer-dereference DoS: a crafted, attacker-supplied input causes trusted post-processing code to dereference/unwrap an empty value instead of erroring gracefully.

### Finding Description
`SierraToNativeCompiler::compile` runs the native compiler binary out-of-process with resource limits, then loads the resulting artifact: [1](#0-0) 

Unlike the subprocess crash/signal paths in `compile_with_args`, which are converted into `CompilationUtilError::CompilationError` (see `crates/apollo_compilation_utils/src/compiler_utils.rs`), the final line here `.unwrap()`s the `Option<AotContractExecutor>` returned by `from_path` after the `?` has already handled the `Err` case. If the subprocess exits successfully but writes an artifact that `from_path` cannot resolve into `Some(_)` (e.g., a truncated/partial or unexpected library layout resulting from an adversarially crafted Sierra program near a size/format boundary), this `unwrap()` panics instead of returning a `CompilationUtilError`.

This function is reachable from a normal declared-class flow via `NativeClassManager`: [2](#0-1) [3](#0-2) 

When `CairoNativeMode::WaitOnCompilation` is configured, `process_compilation_request` (and therefore the panicking `compile()` call) executes synchronously on the caller's thread as part of handling a `Declare` transaction (`set_and_compile`), rather than on an isolated background worker thread as in `LazyCompilation` mode: [4](#0-3) [5](#0-4) 

### Impact Explanation
A panic on the transaction-processing call path is not caught anywhere in this flow — `set_and_compile` and `process_compilation_request` only convert declared `Err` results into no-ops via `.unwrap_or(())`; an actual Rust panic still unwinds/aborts. If this occurs on the thread driving block building/validation (`WaitOnCompilation` mode), it can crash that worker/process. Because every honest node performing native compilation runs the identical deterministic compiler on the identical attacker-supplied Sierra bytes, the same crafted class would panic on all nodes simultaneously that have native compilation enabled in `WaitOnCompilation` mode, causing a synchronized denial-of-service — matching the "network unable to confirm new transactions" impact criterion.

### Likelihood Explanation
This requires: (1) the deployment to have Cairo-Native compilation enabled (`cairo_native_mode` != `Off`, which is a supported, documented production configuration per `config_schema.json`), and (2) crafting a Sierra program that compiles successfully at the subprocess level yet defeats `AotContractExecutor::from_path`'s expectations. The exact trigger condition for `from_path` returning `None` lives in the external `cairo_native` crate and could not be further verified from this repository's index; this materially limits confidence that a concrete crafted-input trigger currently exists, versus the code merely lacking defensive error handling for a case the underlying library may never actually produce in practice.

### Recommendation
Replace the unchecked `.unwrap()` in `crates/apollo_compile_to_native/src/compiler.rs` with proper `Option` handling that returns a `CompilationUtilError::CompilationError` (or similar) instead of panicking, consistent with how signal/crash failures from `compile_with_args` are already handled. Additionally, ensure `process_compilation_request` / `set_and_compile` wrap compiler invocation in `std::panic::catch_unwind` (or otherwise isolate it) so that any unexpected panic from third-party compiler/library code cannot propagate into and terminate a transaction-processing thread.

### Proof of Concept
Not fully constructible from available context: reproducing the exact byte-level Sierra input that makes `AotContractExecutor::from_path` return `Ok(None)` after a successful subprocess exit depends on internals of the external `cairo_native` crate, which is outside this repository's index. The reachability chain (Declare tx → `set_and_compile` → `process_compilation_request` → `SierraToNativeCompiler::compile` → unchecked `.unwrap()`) is confirmed in-repo as cited above.
