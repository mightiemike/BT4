### Title
Unfreeze (v1/v2) can skip vote-clearing, letting an account withdraw its frozen TRX principal while continuing to earn witness voting rewards on stale, unbacked votes - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`)

### Summary
The Rocket Pool report describes a Node Operator who withdraws their staked ETH principal (via `refund()`) while deliberately skipping `finalise()`, so the accounting state that would exclude them from future rewards is never updated — they keep collecting RPL rewards on capital that has already been returned to them. The reachable analog in java-tron is the `needToClearVote` / `updateVote` logic in `UnfreezeBalanceActuator` and `UnfreezeBalanceV2Actuator`: under specific, attacker-controllable account states, unfreezing BANDWIDTH/ENERGY returns the principal TRX to the account's spendable balance but does **not** clear the account's `votesList`, so witness/voting rewards continue to accrue on votes that are no longer backed by frozen stake.

### Finding Description
`UnfreezeBalanceActuator.execute()` immediately credits the unfrozen TRX back to the owner's balance [1](#0-0) , then decides whether to clear the account's votes via a `needToClearVote` flag:

```
boolean needToClearVote = true;
if (dynamicStore.supportAllowNewResourceModel()
    && accountCapsule.oldTronPowerIsInvalid()) {
  switch (unfreezeBalanceContract.getResource()) {
    case BANDWIDTH:
    case ENERGY:
      needToClearVote = false;
      break;
``` [2](#0-1) 

When `needToClearVote` is `false`, the account keeps its existing `votesList` untouched even though the frozen balance backing BANDWIDTH/ENERGY has been fully withdrawn to the spendable balance [3](#0-2) . The same pattern exists in the newer path, `UnfreezeBalanceV2Actuator.updateVote()`, which explicitly returns without modifying votes for BANDWIDTH/ENERGY when `oldTronPowerIsInvalid()` is true: `"// there is no need to change votes"` [4](#0-3) .

Rewards for those retained votes are computed purely from `accountCapsule.getVotesList()` in `MortgageService.withdrawReward()`/`queryReward()` (legacy path) and `VoteRewardUtil.withdrawReward()`/`queryReward()` (TVM native path) — both walk the recorded vote list and multiply vote counts by the accumulated per-vote reward delta (Vi), with **no cross-check against the account's current frozen balance or `TronPower`** at reward-computation time [5](#0-4) [6](#0-5) .

Unit tests in `FreezeV2Test` confirm this is a real, reachable code path and not merely theoretical: when the account's old TronPower has already been invalidated, unfreezing ENERGY leaves the vote list untouched (`testUnfreezeWithoutOldTronPower`), whereas when old TronPower is still "valid," the same unfreeze operation clears the votes (`testUnfreezeWithOldTronPower`) [7](#0-6) [8](#0-7) .

This mirrors the Rocket Pool root cause exactly: the actuator returns the frozen principal to the account (`refund()`-equivalent) but the counter/step that should invalidate reward eligibility (clearing votes, equivalent to `finalise()`) is conditionally skipped, leaving stale accounting state (`votesList`) that the reward engine still honors.

### Impact Explanation
An account can freeze TRX for BANDWIDTH/ENERGY, vote with the resulting TronPower, then unfreeze that TRX (reclaiming spendable balance) while retaining the vote entries because `needToClearVote`/`updateVote` skips clearing votes in the described state. The account continues to receive SR voting rewards (`allowance`, ultimately withdrawable TRX) for votes that are no longer backed by any locked stake — a direct accounting/asset corruption: rewards are paid out disproportionately to unstaked accounts, diluting rewards for legitimate stakers and allowing free/duplicated yield extraction (unfreeze principal + keep earning). This is a resource/reward accounting bug rather than a memory-safety or RCE bug, but it directly corrupts on-chain economic incentives at network scale (affects the SR reward pool that all voters draw from).

### Likelihood Explanation
The trigger conditions (`supportAllowNewResourceModel()` on, `oldTronPowerIsInvalid()` true, resource type BANDWIDTH or ENERGY) are all reachable through ordinary, unprivileged transactions — freeze v2 flows, unfreeze v1/v2 contracts, and vote-casting are all standard broadcastable transaction types available to any account. No privileged actor or leaked key is required. The main uncertainty is precisely which state transitions cause `oldTronPowerIsInvalid()` to become `true` for a given account and whether, in that state, the account's `TronPower`/`AllTronPower` (used at vote-cast time and by `VoteWitnessActuator`) is fully decoupled from BANDWIDTH/ENERGY frozen amounts, guaranteeing the votes are genuinely stake-unbacked after the unfreeze. This requires deeper analysis of `AccountCapsule.getAllTronPower()`/`getTronPower()` and `VoteWitnessActuator`'s freezing-power validation, which could not be located/confirmed in the available index (the `AccountCapsule.java` methods `getAllTronPower`, `oldTronPowerIsInvalid`, etc. were not returned by search, likely due to index size limits). A Devin session with full file access would be needed to trace these methods precisely and confirm whether the "no need to change votes" comment is a documented, safe design invariant (e.g., because TronPower for voting is computed independently from the specific BANDWIDTH/ENERGY unfreeze) or an exploitable gap.

### Recommendation
- In `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`, verify — for every case where `needToClearVote`/vote-adjustment is skipped — that the account's remaining stake (across all frozen types, including TRON_POWER) is still sufficient to back every existing vote count; if not, force-clear or proportionally reduce votes before crediting the unfrozen balance.
- Add an explicit reward-time consistency check (in `MortgageService`/`VoteRewardUtil`) that caps reward accrual to the minimum of recorded vote count and currently-backed `TronPower`, rather than trusting the stored `votesList` unconditionally.
- Add regression tests that freeze BANDWIDTH/ENERGY, vote, unfreeze under the `oldTronPowerIsInvalid()`-true condition, and then assert that voting rewards stop accruing for the withdrawn stake.

### Proof of Concept
Conceptual reproduction based on existing test scaffolding in `FreezeV2Test`/`UnfreezeBalanceV2ActuatorTest`:
1. Freeze TRX for ENERGY via `FreezeBalanceV2Contract`/`freezeV2`, then cast votes for a witness using the resulting TronPower.
2. Drive the account into the `oldTronPowerIsInvalid()`-true state (as done in `testUnfreezeWithoutOldTronPower`, e.g. by setting `oldTronPower(-1L)`), reachable through the normal freeze v2 migration flow.
3. Submit `UnfreezeBalanceContract`/`UnfreezeBalanceV2Contract` for ENERGY — the frozen TRX is credited back to `balance` immediately, but `votesList` is left non-empty as shown in `testUnfreezeWithoutOldTronPower` [7](#0-6) .
4. Trigger `payRewardAndDoMaintenance`/`withdrawReward` in subsequent cycles (as in `VoteTest.checkRewardAndWithdraw`) and observe `mortgageService.queryReward`/`VoteRewardUtil.queryReward` returning non-zero rewards for the account despite it holding zero frozen ENERGY/BANDWIDTH balance backing those votes [9](#0-8) .

Note: full confirmation that this yields *unbacked* reward accrual (rather than being safely covered by remaining TRON_POWER-type stake) requires tracing `AccountCapsule.getAllTronPower()`/`getTronPower()` and `VoteWitnessActuator`'s stake-sufficiency checks, which were not fully retrievable from the current index. A Devin session with full repository access is recommended to complete this trace before treating this as a confirmed, exploitable vulnerability.

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private void checkRewardAndWithdraw(byte[] contract, boolean isZero) throws Exception {
    long rewardBySystem = mortgageService.queryReward(contract);
    long beginCycle = dbManager.getDelegationStore().getBeginCycle(contract);
    long currentCycle = dbManager.getDynamicPropertiesStore().getCurrentCycleNumber();
    long passedCycle = max(0, currentCycle - beginCycle,

        getConsumer(">=", rewardBySystem)
            .andThen(getConsumer("<=", rewardBySystem + passedCycle)),
        queryRewardBalanceMethod);

    long oldBalance = dbManager.getAccountStore().get(contract).getBalance();

        getConsumer(">=", rewardBySystem)

        withdrawRewardMethod).getRuntime().getResult().getHReturn()).longValue();
