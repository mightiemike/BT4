### Title
Positional (height, vtxindex) binding of a `LeaderBlockCommitOp` to its VRF `LeaderKeyRegisterOp` lets a Bitcoin reorg silently rebind a miner's commit to a different, attacker-controlled VRF key - ([File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs])

### Summary
A `LeaderBlockCommitOp` does not reference the `LeaderKeyRegisterOp` it intends to consume by content (the registered VRF public key itself); it references it purely by position, `(key_block_ptr, key_vtxindex)`. `check_common` only verifies that *some* key exists at that position in the current fork, with no requirement that it be the same key (or even the same sender) the committing miner originally registered. If a Bitcoin reorg reorders or replaces the operation that lands at that exact `(height, vtxindex)` slot, an already-broadcast or resubmitted block-commit will, upon reprocessing, silently bind to whatever `LeaderKeyRegisterOp` now occupies that position - which the committing miner may not hold the private key for. This mirrors the reported bug class: an address/identity is derived from a purely positional/ordering-dependent value (nonce / vtxindex) rather than from content the legitimate party controls, so a reorg lets an unrelated actor's data occupy the slot a pending transaction implicitly depends on.

### Finding Description
`LeaderBlockCommitOp::check_common` resolves the consumed key strictly by position: [1](#0-0) 

It calls `tx.get_leader_key_at(leader_key_block_height, self.key_vtxindex.into(), &tx_tip)` and only checks that a key exists at that slot in the current fork's tip - it never checks that the returned key's `public_key` matches the value the miner actually registered, nor that the key's registrant is the same `apparent_sender` as the commit. The test suite explicitly documents that a different burn-chain signer is accepted at this stage: [2](#0-1) 

The same positional lookup, `get_leader_key_at(key_block_ptr, key_vtxindex)`, is later used to fetch the "winning leader" key that is checked against the actual VRF proof in the mined Stacks block: [3](#0-2) 

and to compute the set of consumed leader keys for the burn distribution: [4](#0-3) 

By contrast, uniqueness of key *registration* is enforced by content, and is fork-aware: [5](#0-4) 

That fork-awareness is even validated by an existing unit test that explicitly reorders a key registration relative to a block commit and shows the "consumed" status changes with the fork: [6](#0-5) 

The inconsistency is the bug: `LeaderKeyRegisterOp` uniqueness is content-bound and reorg-safe, but the `LeaderBlockCommitOp`'s *reference* to that key is purely positional and reorg-*unsafe*. If a short Bitcoin reorg changes which operation lands at burn height `H`, vtxindex `V` (e.g., the victim's own registration is displaced by one vtxindex because of transaction reordering within the replacement block, or another party's `LeaderKeyRegisterOp` is confirmed at exactly that slot), a block-commit that still encodes `(key_block_ptr=H, key_vtxindex=V)` will now be checked against - and bound to - a VRF public key the original committing miner never registered and does not hold the private key for.

### Impact Explanation
This is directly analogous to the reported bug class: a value that should uniquely and immutably identify a resource controlled by a specific party (the CREATE'd Vault address / here, the VRF key a miner's commit consumes) is instead derived from transaction ordering that a short reorg can perturb. The consequences:
- A miner who paid real BTC to submit a block-commit can have that commit accepted by consensus (`check_common` passes) while being bound to a VRF public key they cannot produce a valid VRF proof for, since some other party's key now occupies the referenced slot. If that commit subsequently wins the sortition via the burn-weight sampling in `distribution.rs`/`sortition.rs`, the true miner can never produce a block satisfying `validate_burnchain`'s VRF check against `leader_key.public_key`, causing loss of the committed burn fee with no chance of a valid block - a reward/fee loss triggered without requiring majority Stacks stake or majority Bitcoin hash power, only a minority-capable short reorg (the same threat model the original report used for Ethereum/Polygon/Optimism reorgs).
- This breaks the intended equality "the VRF key consumed by a block-commit is the key its own sender registered," which underlies the sortition/VRF security model.

This maps to the High-severity category: a minority-triggerable VRF/static-validation divergence bounded to the fee lost by the affected miner.

### Likelihood Explanation
Low-to-medium likelihood, matching the referenced report's own assessment: it requires a short Bitcoin reorg (1+ blocks) that changes the transaction ordering or content at the exact `(block_height, vtxindex)` a pending/rebroadcast commit references. Such reorgs are rare but documented as occurring on Bitcoin and are explicitly the risk model the original report relies on for its host chains.

### Recommendation
Bind `LeaderBlockCommitOp`'s reference to its `LeaderKeyRegisterOp` by content, not only by position: include (or additionally verify) the registered VRF public key value itself, and verify the resolved key's registering identity (or its committed content hash) matches what the block-commit intends to consume, analogous to using `create2` with a content-derived salt instead of relying on transaction ordering for CREATE address derivation. At minimum, `check_common` should re-derive the key strictly by matching the specific `LeaderKeyRegisterOp` fields the sender originally observed, and re-abort/re-submit the commit if the fork's operation at that slot has changed since the commit was constructed.

### Proof of Concept
1. Miner M submits `LeaderKeyRegisterOp` with VRF public key `K_M`; it confirms at burn height `H`, vtxindex `V` on the canonical chain.
2. M constructs and submits `LeaderBlockCommitOp` with `key_block_ptr = H`, `key_vtxindex = V`, intending to consume `K_M` (`stacks-node/src/nakamoto_node/relayer.rs:rotate_vrf_and_register`, `stackslib/src/chainstate/burn/operations/leader_block_commit.rs:check_common`).
3. A short Bitcoin reorg replaces the block at height `H` such that a different `LeaderKeyRegisterOp` (registered by attacker A with public key `K_A`, or simply reordered so a different tx occupies vtxindex `V`) now sits at `(H, V)`.
4. M's block-commit (already broadcast, or resubmitted verbatim by M's node before it notices the reorg) is reprocessed by `check_common`, which only checks that *a* key exists at `(H, V)` (`leader_block_commit.rs:1223-1232`) - it is accepted, now bound to `K_A` instead of `K_M`.
5. `get_leader_key_at` / `get_consumed_leader_keys` (`sortdb.rs:1318-1348`) and `validate_burnchain` (`stacks/db/blocks.rs:3147-3168`) subsequently resolve this commit's leader key as `K_A`.
6. If M's commit wins the sortition, M cannot produce a VRF proof matching `K_A` and forfeits the committed BTC fee with no valid block ever produced for that tenure.

    /// Find the VRF public keys consumed by each block candidate in the given list.
    /// The burn DB should have a key for each candidate; otherwise the candidate would not have
    /// been accepted.
    pub fn get_consumed_leader_keys(
        &mut self,
        parent_tip: &BlockSnapshot,
        block_candidates: &[LeaderBlockCommitOp],
    ) -> Result<Vec<LeaderKeyRegisterOp>, db_error> {
        // get the set of VRF keys consumed by these commits
        let mut leader_keys = vec![];
        for candidate in block_candidates.iter() {
            let leader_key_block_height = candidate.key_block_ptr as u64;
            let leader_key_vtxindex = candidate.key_vtxindex as u32;
            let leader_key = self
                .get_leader_key_at(
                    leader_key_block_height,
                    leader_key_vtxindex,
                    &parent_tip.sortition_id,
                )?
                .unwrap_or_else(|| {
                    panic!(
                        "FATAL: no leader key for accepted block commit {} (at {},{})",
                        &candidate.txid, leader_key_block_height, leader_key_vtxindex
                    )
                });

            leader_keys.push(leader_key);
        }

        Ok(leader_keys)
    }
