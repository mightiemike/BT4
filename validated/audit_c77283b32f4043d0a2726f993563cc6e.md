## Analysis

The Sherlock bug class is: a stale "before" value that should have been zeroed/reset is instead combined with an accrual (interest), producing outcome different from what the protocol design intends (extra debt forced on the user). The closest reachable analog in nearcore is in the validator-proposal reward application logic used every epoch to compute stake for T+2.

### Title
Validator's explicit full-unstake (0-stake) proposal gets its epoch reward added back into `stake_change`, delaying return of funds - (File: `chain/epoch-manager/src/validator_selection.rs`)

### Summary
`apply_epoch_update_to_proposals` is supposed to honor a validator's explicit unstake request (a `Stake` action proposing `stake == 0`) by keeping their post-epoch stake at zero, per the documented algorithm ("considered stake of the proposal is `0 if proposal.stake == 0 else proposal.stake + reward[...]`" — [1](#0-0) ). The implementation does not check for the zero-stake case before adding the reward.

### Finding Description
In the first loop over `proposals`, an unstaking validator's zero-stake proposal `p` is stored unconditionally into `proposals_by_account` and `stake_change` [2](#0-1) . In the second loop, that same zero-stake `p` is retrieved via `proposals_by_account.entry(account_id).or_insert(r)`, and if the account earned a reward this epoch (which it will, since it was a validator throughout the epoch before unstaking), the reward is unconditionally added to `p.stake_mut()` — without ever checking whether the proposal's stake was `0` [3](#0-2) . This is the exact analog of the Synth-vault bug: an accrued increment (reward / interest) is applied on top of a value that should have first been reset to reflect the user's explicit request (full withdrawal / correct principal), producing an inflated resulting value (`stake_change` non-zero instead of `0`).

### Impact Explanation
An account that submits a `Stake` action with `stake == 0` intending to fully unstake and reclaim all locked funds ends up with a nonzero `stake_change` entry (equal to their just-earned reward) for the transitioning epoch. Because `max_of_stakes` — computed from `stake_change` across the trailing epochs and used by `update_validator_accounts` to decide how much of `account.locked()` is returned — is derived from this incorrect value, the validator's requested full withdrawal is not honored immediately: reward funds that should be freed remain classified as locked stake instead of returned balance [4](#0-3) . The user is thus forced to keep more value locked/staked than they explicitly requested, directly analogous to the Synth vault forcing borrowers to post more collateral than intended.

### Likelihood Explanation
This is reachable by any single permissionless staker: submitting a normal `Stake` action with amount `0` (a common, documented way to fully unstake) is enough to trigger the discrepancy every time the account earned a nonzero reward in the epoch it unstakes from — no privileged role or adversarial coordination required.

### Recommendation
Match the documented spec: in the second loop of `apply_epoch_update_to_proposals`, only add the reward to `p.stake_mut()` when `p.stake() != 0` (i.e., skip reward addition for proposals that explicitly requested zero stake), consistent with `docs/Economics/Economics.md`'s "0 if proposal.stake == 0" rule.

### Proof of Concept
1. Validator `V` is an active validator in epoch `T` with stake `S` and earns reward `R` for the epoch (any online validator).
2. `V` submits a `Stake` action with `amount = 0` during epoch `T` to fully unstake.
3. At the `T -> T+1` epoch boundary, `proposals_to_epoch_info` calls `apply_epoch_update_to_proposals`: the first loop inserts `V`'s zero-stake proposal into `proposals_by_account`/`stake_change` [5](#0-4) ; the second loop finds `V` in `prev_epoch_info.validators_iter()`, retrieves the same zero-stake entry, and unconditionally adds `R` to it, setting `stake_change[V] = R` instead of `0` [6](#0-5) .
4. This inflated `stake_change` feeds `max_of_stakes` for `V`, so `update_validator_accounts` withholds `R` from being returned to `V`'s spendable balance at this boundary, contrary to `V`'s explicit unstake request [7](#0-6) .
