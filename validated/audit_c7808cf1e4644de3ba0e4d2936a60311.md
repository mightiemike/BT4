## Analog Vulnerability Found

### Title
Permanent loss of account funds when `DeleteAccountAction.beneficiary_id` does not resolve to an existing account - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId`; it never checks that the account actually exists. When the beneficiary account does not exist, the balance-refund receipt generated by account deletion fails to execute, and instead of the transaction reverting or the funds being returned to anyone, the entire remaining balance is permanently burned. This is the direct analog of the reported "missing zero-address check" bug class: an unvalidated destination parameter for a fund-transferring action leads to unrecoverable loss of value.

### Finding Description
`action_delete_account` unconditionally emits a balance-refund receipt addressed to `beneficiary_id` for the account's full remaining balance: [1](#0-0) 

The only validation ever performed on `beneficiary_id` is that it is a syntactically valid account id string (`InvalidAccountId`), documented here: [2](#0-1) 

The generated receipt is built with `Receipt::new_balance_refund`, which sets `predecessor_id = "system"`, marking it as a refund receipt: [3](#0-2) 

When this refund receipt is later executed against `beneficiary_id`, `check_account_existence` is invoked with `receipt_shape.is_refund == true`. Because `implicit_creation_allowed` unconditionally returns `false` for refunds — "Refund can never create an account" — the transfer fails with `AccountDoesNotExist` if the beneficiary account is missing: [4](#0-3) [5](#0-4) 

Critically, when a refund receipt (`predecessor_id().is_system()`) fails execution, the runtime does not roll the funds back to anyone or retry — it permanently destroys them by adding the deposit to `other_burnt_amount`: [6](#0-5) 

This exact behavior is confirmed by an existing test showing a refund to a nonexistent account fails with `AccountDoesNotExist` and the funds are not delivered anywhere: [7](#0-6) 

The comment attached to a related test explicitly acknowledges the danger of this design: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund," but nothing in validation actually enforces beneficiary existence: [8](#0-7) 

### Impact Explanation
Any account owner (or contract acting via `promise_batch_action_delete_account`) who submits a `DeleteAccount` action with a `beneficiary_id` that is syntactically valid but does not currently exist on-chain — due to a typo, a copy-paste error, a beneficiary account that was itself deleted/never created, or a stale reference in a script/tool — will have their entire account balance permanently and irrecoverably burned. This is concrete, unauthorized (accidental, but protocol-permitted) destruction of user funds with no recovery path, matching the "permanently frozen/lost funds" impact category. The reachable surface includes both a direct `SignedTransaction` with a `DeleteAccountAction`, and the `promise_batch_action_delete_account` host function callable from any contract: [9](#0-8) 

### Likelihood Explanation
This is directly analogous to the reported exploit scenario (an uninitialized/incorrect `to` argument in an automated withdrawal script). Any wallet, SDK, CLI, or contract-integration bug that supplies an incorrect-but-well-formed `beneficiary_id` (e.g., an account that was deleted between construction and execution of the transaction, or a mistyped subaccount) triggers the loss with a single, ordinary, unprivileged transaction. No special privileges, timing races, or validator collusion are required — the action is a standard user-facing capability (self-deletion of one's own account).

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` refers to an existing account (or restrict deletion to well-known/verified beneficiaries), or alternatively change the refund/failure path so that a failed system refund to a nonexistent account does not silently burn the deposit but instead fails the entire `DeleteAccount` action atomically (i.e., check beneficiary existence as part of action validation, symmetric to how `CreateAccount`/other actions already check account existence in `check_account_existence`).

### Proof of Concept
1. Create account `alice.near` with a non-trivial balance.
2. Submit `SignedTransaction` from `alice.near` to itself containing a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "does-not-exist.near" })`, where `does-not-exist.near` is a syntactically valid but never-created (or previously deleted) account id.
3. `action_delete_account` succeeds, deletes `alice.near`, and enqueues a `Receipt::new_balance_refund("does-not-exist.near", alice_balance)`.
4. When that refund receipt executes, `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist` because `is_refund == true` forbids implicit creation.
5. Because the failing receipt's `predecessor_id` is `"system"`, the runtime does not produce any further refund — the deposit amount is added to `other_burnt_amount` in `runtime/runtime/src/lib.rs` and is gone permanently.
6. Verified by the existing test `refund_may_not_create_universal_account` in `runtime/runtime/src/tests/apply.rs:6883-6926`, which demonstrates the same failure mode (refund to nonexistent account fails and funds are not delivered), generalizable to any account type since `implicit_creation_allowed` rejects all account types when `is_refund` is true.

pub fn promise_batch_action_delete_account(

    memory: &mut [u8],

    ctx.result_state.gas_counter.pay_base(base)?;

        ActionCosts::delete_account,
        sir,
    )?;
