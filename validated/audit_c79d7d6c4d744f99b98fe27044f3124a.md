### Title
Starknet OS `deploy_contract` unconditionally asserts constructor success, causing OS re-execution failure for blockifier-accepted reverted deploy transactions - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/deploy_contract.cairo`)

### Summary
The Starknet OS Cairo function `deploy_contract` hard-asserts that a deployed contract's constructor never reverts (`assert is_reverted = 0;`). However, `blockifier` (the sequencer's real execution engine) permits an `Invoke` transaction whose inner logic calls the `deploy` syscall with a constructor that fails: blockifier gracefully marks the *transaction* as reverted (fee charged, included in the block) rather than rejecting it outright. This produces a block that blockifier considers valid but that the Starknet OS re-execution/proving path cannot process, because it will hit an unsatisfiable Cairo assertion.

This mirrors the analog report's core defect: the deployment path assumes success and does not gracefully handle/propagate a failed deployment; instead of reverting the caller's own state (as the `revert_log` machinery is clearly designed to support, see `RevertLogEntry`/`handle_revert` in the same subsystem), it forces a Cairo assertion failure whenever the constructor call fails, marked explicitly as an outstanding TODO: [2](#0-1) 

This function is reachable both from the new `execute_deploy` syscall handler for ordinary `Invoke`/`L1Handler` calls: [3](#0-2) 

and from the `DeployAccount` transaction constructor flow: [4](#0-3) 

Crucially, blockifier — the code path that actually determines whether a transaction is *included* in a block and whether it is *reverted* vs *rejected* — does **not** require the constructor to succeed for the containing transaction to be block-worthy. `blockifier`'s test suite demonstrates that an `Invoke` transaction whose `__execute__` deploys a contract whose constructor fails is executed successfully at the transaction level, is included in the block, and is only marked with a non-fatal `revert_error` (fee charged, no rejection): [5](#0-4) [6](#0-5) 

This is fundamentally different from the `DeployAccount` case, where a failing constructor causes the whole transaction execution call to return an `Err` (i.e., the transaction is rejected before ever entering a block): [7](#0-6) 

So specifically for `Invoke`/`L1Handler` transactions that internally call the `deploy` syscall with a failing constructor, blockifier commits such a transaction into a block as a legitimate REVERTED transaction, while the OS's `deploy_contract` will unconditionally fail the Cairo assertion `is_reverted = 0` when attempting to re-execute/prove that same block.

### Impact Explanation
Any account contract (deployed by any unprivileged user) can, inside its `__execute__` (or any invoked entry point / L1 handler), call the `deploy` syscall targeting a class whose constructor is designed to fail (or fails naturally, e.g. insufficient calldata, business-logic checks, or deploying to an address that becomes unavailable due to a race in the same block). Blockifier will accept and include this transaction in a block as REVERTED. When the sequencer/prover attempts to generate the Starknet OS execution trace/proof for that block, the `assert is_reverted = 0` in `deploy_contract` will fail, making the block unprovable. This constitutes a real halt in progress: the block built and considered final by the sequencer cannot be proven and thus cannot be settled/finalized via the OS, causing an honest-node divergence between the execution layer (blockifier) and the proving layer (Starknet OS), and ultimately preventing the network from confirming new transactions in that block.

### Likelihood Explanation
High likelihood: any ordinary invoke transaction can trigger this by deploying a contract with a constructor that reverts from inside a Cairo1 contract's own logic — no special privileges, race conditions, or malicious-operator behavior required. Constructor failures during a `deploy` syscall inside an `Invoke` are an explicit, tested, and expected blockifier behavior (not an edge case), making the divergence trivially and repeatably reachable by any transaction sender.

### Recommendation
Update `deploy_contract` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/deploy_contract.cairo` to mirror blockifier's semantics: when `is_reverted == 1` for a `deploy` syscall invoked from a general `Invoke`/`L1Handler` context (as opposed to the `DeployAccount` constructor path, which must reject the whole transaction), roll back the just-created state entry for `contract_address` (undoing the `dict_update` at lines 62-66) and propagate the failure to the caller as a syscall failure response, consistent with how other reverting inner calls are represented via `is_reverted`/`RevertLogEntry`, rather than asserting `is_reverted = 0` unconditionally.

### Proof of Concept
1. Declare and fund an account contract `A` whose `__execute__` calls `deploy_syscall(class_hash=B, ...)` where class `B`'s constructor unconditionally panics/fails (analogous to `FaultyAccount`/`deploy_and_fail` feature contracts already present in the test suite, see `crates/blockifier_test_utils/resources/feature_contracts/cairo1/test_contract.cairo:584-596`).
2. Submit an `Invoke` transaction from `A` calling this entry point.
3. Observe (as in `crates/blockifier/src/execution/stack_trace_test.rs:845-852`) that blockifier executes the transaction, returns `Ok`, and sets `revert_error`, meaning the transaction is included in the block as REVERTED (fees charged).
4. Feed that block/transaction trace into the Starknet OS re-execution (`deploy_contract` in the OS program): the constructor's `is_reverted` will be `1`, causing `assert is_reverted = 0;` in `deploy_contract.cairo:91` to fail, aborting OS execution/proof generation for that block, even though blockifier deemed the block valid.
