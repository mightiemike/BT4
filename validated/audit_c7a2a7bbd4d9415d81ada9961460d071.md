### Title
Transaction Pool `ForkTracker` Fork-Activation Flags Are Never Reset on Reorg, Causing Pool Admission to Diverge from Block Validity - (File: `crates/transaction-pool/src/validate/eth.rs`)

### Summary
`EthTransactionValidator::on_new_head_block` (`crates/transaction-pool/src/validate/eth.rs:900-956`) updates the pool's `ForkTracker` (`shanghai`, `cancun`, `prague`, `osaka`, `amsterdam` `AtomicBool`s) monotonically: it sets a flag to `true` when the new tip's timestamp indicates the fork is active, but it never clears the flag back to `false` when the new tip's timestamp indicates the fork is *not* active. This function is invoked on every canonical state update, including reorgs (`crates/transaction-pool/src/pool/mod.rs:539`, driven from `crates/transaction-pool/src/maintain.rs`'s `CanonStateNotification::Reorg` handling, which calls `on_canonical_state_change` with the new tip after a reorg).

### Finding Description
The root cause is the update logic itself: [1](#0-0) 
Each fork flag is only ever stored as `true`; there is no corresponding `else { store(false) }` branch. Contrast this with the analogous Solana bug where `update_tss()` updated the signing authority but never reset the nonce counter that depended on it — here, `on_new_head_block` updates the "current chain tip" but never resets the derived fork-activation state that depended on the old tip when the chain moves backward across a fork boundary (a deep reorg).

If the canonical chain reorgs from a tip past a fork's activation timestamp (e.g., past Prague) back to a tip before that timestamp — which is exactly the scenario `maintain_transaction_pool`'s `CanonStateNotification::Reorg` branch is built to handle via `pool.on_canonical_state_change(update)` — the validator's `fork_tracker.prague` (or any other fork's flag) remains `true` even though the chain's *actual* new tip is pre-Prague. All statelesss checks gated on `self.fork_tracker.is_prague_activated()` (e.g., EIP-7702 transaction type acceptance in `validate_stateless`, sender-bytecode/EIP-7702-delegation checks in `validate_sender_bytecode`, EIP-4844 in `validate_stateful` via `is_cancun_activated()`, blob count via `max_blob_count`, init-code-size checks via `is_shanghai_activated()`) will continue to admit transactions into the pool as if the fork were active, even though a block built on the new (pre-fork) tip would reject those same transactions during actual EVM/consensus execution, since block execution and validation always consult `chain_spec.is_*_active_at_timestamp` directly against the real header timestamp rather than through this monotonic tracker. ### Impact Explanation
This breaks the equality between "transaction pool admission criteria" and "actual block validity criteria" required by the block validator/consensus layer for the current canonical tip, matching the explicitly listed High-impact category: *"pool admission diverging from block validity."* Concretely, after a reorg backward across a hardfork boundary, the pool will keep accepting and propagating transactions (e.g. EIP-7702 authorization-list transactions, or blob transactions with post-fork blob counts) that cannot legally be included in a block built on the current (pre-fork) canonical head, since `payload_validator`/EVM configuration derive fork activation strictly from the chain spec and the block's own timestamp, not from `ForkTracker`. This can cause block builders to construct blocks with pool-sourced transactions that other clients (and reth's own execution engine) reject as invalid for the header timestamp, or waste block space/propagation bandwidth on to-be-discarded transactions.

### Likelihood Explanation
This requires a deep reorg that crosses backward over a hardfork's activation boundary (block-number or, more commonly for post-merge forks, timestamp-based). Such reorgs are not attacker-controlled in the sense of a malicious peer forging state, but they are a legitimate scenario handled explicitly by `maintain_transaction_pool`'s reorg branch — the code path exists specifically to react to `CanonStateNotification::Reorg`, so the trigger (a reorg spanning a fork boundary) is within the range of protocol-level events reth is expected to correctly handle, even if it is relatively rare in mature networks (more likely on testnets/devnets around fork-activation windows, or in engines that allow proposers to reorg their own chain such as OP-stack, given `always_process_payload_attributes_on_canonical_head`).

### Recommendation
In `on_new_head_block`, replace the one-directional `if active { store(true) }` pattern with a bidirectional update that always reflects the fork status at the new tip's timestamp:
```rust
self.fork_tracker.shanghai.store(
    self.chain_spec().is_shanghai_active_at_timestamp(new_tip_block.timestamp()),
    Ordering::Relaxed,
);
```
and similarly for `cancun`, `prague`, `osaka`, and `amsterdam`, so a backward reorg across a fork boundary correctly clears the flag, restoring the invariant that pool admission always matches the fork rules of the current canonical tip.

### Proof of Concept
1. Configure a chain spec where Prague activates at timestamp `T`.
2. Advance the canonical chain to a tip with timestamp `>= T` (Prague active); the pool's `EthTransactionValidator::on_new_head_block` sets `fork_tracker.prague = true`.
3. Submit and admit an EIP-7702 transaction with an authorization list into the pool (accepted per `crates/transaction-pool/src/validate/eth.rs:595-604`).
4. Trigger a `CanonStateNotification::Reorg` (via `maintain_transaction_pool`) that moves the canonical tip back to a block with timestamp `< T` (pre-Prague), e.g., reorging out the fork-activation block.
5. Observe that `fork_tracker.prague` remains `true` (never reset), so the pool still accepts/retains the EIP-7702 transaction as valid, while a new block built on the reorged (pre-Prague) tip would reject that same transaction during EVM execution/consensus validation (`is_eip7702()` gated on chain-spec timestamp check), demonstrating pool admission diverging from actual block validity for the current canonical head.
