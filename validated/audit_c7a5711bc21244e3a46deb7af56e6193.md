### Title
Dust/malformed-inbound spam permanently blocks TSS fund migration via unbounded `PendingOutbounds` growth - (File: x/utss/keeper/msg_initiate_fund_migration.go)

### Summary
`InitiateFundMigration` requires `HasPendingOutboundsForChain` to be false before an admin can move funds from an old, retiring TSS key to the current key for a given chain. An unprivileged attacker can keep this precondition permanently true by repeatedly submitting cheap, deliberately-invalid inbound transactions for that chain (e.g., unsupported/zero amount, invalid recipient, or a missing token config), each of which is honestly voted on by validators and produces a new `INBOUND_REVERT` outbound entered into `PendingOutbounds` — with no dependency on whether the chain's outbound flag is enabled or how large the original amount was.

### Finding Description
`InitiateFundMigration` gates migration on two independent flags for the target chain: outbound must be disabled (`IsChainOutboundEnabled` must return false) and there must be no pending outbounds (`HasPendingOutboundsForChain` must return false) [2](#0-1) .

Crucially, only `IsChainOutboundEnabled` is checked for genuine (successful) outbound creation via `BuildOutboundsFromReceipt`, which rejects new outbounds when outbound is disabled for the destination chain [3](#0-2) . However, the separate `INBOUND_REVERT` outbound path used for failed inbound validation (`buildRevertOutbound`, invoked from `handleFailedInboundValidation`) performs no such check — it is created purely from the (still enabled) inbound flag path [4](#0-3) [5](#0-4) .

`VoteInbound` only requires `IsChainInboundEnabled` to be true — not outbound — before honest validators process and finalize the vote [6](#0-5) . Since the admin migration workflow disables only *outbound* for the chain (per the precondition check) while inbound observation remains active, an attacker can continue sending malformed/failing inbounds (e.g., zero amount, bad recipient, missing token config — all shown to reliably produce `INBOUND_REVERT` outbounds in the test suite) [7](#0-6) . Each such inbound, once it reaches quorum, adds a fresh entry to `PendingOutbounds`, which `HasPendingOutboundsForChain` walks to gate migration [8](#0-7) .

The attacker does not need real funds or a meaningful deposit — the "dust" here is a cheap/malformed inbound observation (analogous to sending a trivial ETH/token amount to the NDC in the original bug) that is nonetheless honestly voted through by validators and results in a durable queue entry that blocks a security-critical admin operation.

### Impact Explanation
This blocks `InitiateFundMigration`, the mechanism used to move TSS-custodied chain funds off a retiring/compromised key to the new key after a key-rotation event. If an attacker can perpetually keep `PendingOutbounds` non-empty for the affected chain, the protocol cannot complete migration of funds away from an old TSS key, which can prolong exposure of funds under a key intended to be retired, and generally denies the admin's ability to manage TSS/chain state — a denial-of-service on a privileged-but-legitimate protocol operation, triggered entirely by unprivileged inputs, fitting the "unauthorized/blocked state transition in TSS/migration flows" and "DoS reachable without privileged control" impact categories.

### Likelihood Explanation
Likelihood is high for sustaining the block, though the severity depends on how quickly UVs can process/clear each new dust revert outbound versus how cheaply/quickly the attacker can generate new ones. Since inbound observation remains open even while outbound is disabled for a chain undergoing migration, and generating a failing inbound (e.g., a zero-amount or bad-recipient submission) is inexpensive and requires no real deposit, an attacker with modest resources/relayer access could realistically keep re-seeding `PendingOutbounds` faster than migration can be initiated.

### Recommendation
- Gate `INBOUND_REVERT` (and any other outbound-type) creation on the same `IsChainOutboundEnabled` check used for regular outbounds, or introduce an explicit "chain frozen for migration" state that also rejects new inbound votes for the chain, not just new outbound creation.
- Alternatively/additionally, apply a `maxNegligibleAmount`-style threshold or per-source rate limiting so trivial/malformed inbound spam cannot indefinitely populate `PendingOutbounds` and block admin-only fund-migration paths.
- Consider allowing `InitiateFundMigration` to only require that outbounds existing *prior to migration initiation* have drained (a snapshot check) rather than a live, attacker-extendable "no pending outbounds at all" condition.

### Proof of Concept
1. Admin disables outbound for chain `eip155:X` (a required precondition for migration) but inbound remains enabled.
2. Attacker repeatedly submits `MsgVoteInbound`-eligible inbound observations for `eip155:X` that intentionally fail `ValidateForExecution` (e.g., `Amount: "0"`, or `Recipient` set to an unsupported/invalid value, or referencing an asset with no token config) — as demonstrated to succeed and create `INBOUND_REVERT` outbounds in `test/integration/uexecutor/inbound_zero_amount_test.go:464-500` and `test/integration/uexecutor/vote_inbound_validation_test.go:312-364`.
3. Each such vote reaching quorum invokes `handleFailedInboundValidation`, which calls `buildRevertOutbound`/`attachOutboundsToUtx` unconditionally, adding a new entry to `PendingOutbounds` for `eip155:X` [9](#0-8) .
4. Admin calls `MsgInitiateFundMigration` for `eip155:X`; `HasPendingOutboundsForChain` finds the attacker-seeded entry and the call fails with `"chain %s still has pending outbounds; wait for them to drain before migration"` [10](#0-9) .
5. Attacker repeats step 2 continuously (each new dust/malformed inbound is cheap and does not require outbound to be enabled), keeping the migration blocked indefinitely.

// handleFailedInboundValidation records a failed PCTx on the UTX and, for non-isCEA
// inbounds, schedules an INBOUND_REVERT outbound so the user's funds can be returned
// on the source chain. This is called when ValidateForExecution fails after the ballot
// has already been finalized and the UTX created.
func (k Keeper) handleFailedInboundValidation(sdkCtx sdk.Context, utx types.UniversalTx, validationErr error) error {
	inbound := utx.InboundTx
	_, ueModuleAddressStr := k.GetUeModuleAddress(sdkCtx)
	universalTxKey := utx.Id

	k.Logger().Warn("inbound validation failed",
		"utx_key", universalTxKey,
		"source_chain", inbound.SourceChain,
		"is_cea", inbound.IsCEA,
		"error", validationErr.Error(),
	)

	// Record the failed PCTx
	failedPcTx := types.PCTx{
		Sender:      ueModuleAddressStr,
		BlockHeight: uint64(sdkCtx.BlockHeight()),
		Status:      "FAILED",
		ErrorMsg:    validationErr.Error(),
	}

	if err := k.UpdateUniversalTx(sdkCtx, universalTxKey, func(utx *types.UniversalTx) error {
		utx.PcTx = append(utx.PcTx, &failedPcTx)
		return nil
	}); err != nil {
		return err
	}

	// For non-isCEA inbounds, schedule a revert outbound to return funds on source chain.
	// isCEA failures never create an INBOUND_REVERT outbound (consistent with execute_inbound_funds_and_payload.go).
	if !inbound.IsCEA {
		k.Logger().Info("scheduling inbound revert outbound",
			"utx_key", universalTxKey,
			"source_chain", inbound.SourceChain,
			"amount", inbound.Amount,
		)
		revertOutbound := k.buildRevertOutbound(sdkCtx, inbound)

		if attachErr := k.attachOutboundsToUtx(
			sdkCtx,
			universalTxKey,
			[]*types.OutboundTx{revertOutbound},
			validationErr.Error(),
		); attachErr != nil {
			// Store the revert failure reason on the UTX so it's queryable on-chain.
			// The FAILED PCTx is already recorded above — this adds why the revert wasn't attached.
			if storeErr := k.UpdateUniversalTx(sdkCtx, universalTxKey, func(utx *types.UniversalTx) error {
				utx.RevertError = attachErr.Error()
				return nil
			}); storeErr != nil {
				// UpdateUniversalTx only fails on infra issues — return to roll back and retry
				return storeErr
			}
		}
	}

func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {

		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}

// HasPendingOutboundsForChain checks if there are any pending outbounds for a given chain.
// It walks PendingOutbounds and joins against UniversalTx to check destination_chain.
// Returns true on first match. This is O(n) but only called during admin-initiated migration.
func (k Keeper) HasPendingOutboundsForChain(ctx context.Context, chain string) (bool, error) {
	var found bool
	err := k.PendingOutbounds.Walk(ctx, nil, func(outboundId string, entry types.PendingOutboundEntry) (bool, error) {
		utx, exists, err := k.GetUniversalTx(ctx, entry.UniversalTxId)
		if err != nil {
			return true, err
		}
		if !exists {
			return false, nil
		}
		for _, ob := range utx.OutboundTx {
			if ob.DestinationChain == chain && ob.Id == outboundId {
				found = true
				return true, nil // stop walking
			}
		}
		return false, nil
	})
	if err != nil {
		return false, err
	}
	return found, nil
}
