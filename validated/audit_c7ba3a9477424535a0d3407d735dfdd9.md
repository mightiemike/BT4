### Title
Stale compiled Wallet Contract WASM can silently diverge from its Rust source, shipping a version with omitted security checks - (File: `runtime/near-wallet-contract/build.rs`)

### Summary
`near-wallet-contract`'s deployed WASM binaries (`res/wallet_contract_mainnet.wasm`, `res/wallet_contract_testnet.wasm`, `res/wallet_contract_localnet.wasm`) are the *only* code nearcore actually executes for every ETH-implicit account via `rlp_execute`. These binaries are supposed to be a 1:1 compiled artifact of the Rust source under `./implementation`, but `build.rs` explicitly skips rebuilding whenever the target artifact already exists on disk, exactly the same "two copies of the logic that must be kept in sync manually" failure mode described in the report (`vault.js` string vs. `vault.teal.tmpl`).

### Finding Description
`build_contract` in `runtime/near-wallet-contract/build.rs` returns immediately without compiling if the output file is already present: [1](#0-0) 

This means that after a developer fixes a bug in the Rust "source of truth" under `./implementation` (e.g. a missing/incorrect check in `validate_tx_relayer_data`), the checked-in `res/*.wasm` file will **not** be regenerated unless someone manually deletes it first. The README for the crate confirms this is a manual, easy-to-miss step: [2](#0-1) 

The static WASM bytes are `include_bytes!`'d directly into nearcore and are what gets executed for every eth-implicit account's `rlp_execute` call, matched purely by hash: [3](#0-2) [4](#0-3) 

The security-critical checks that gate every relayed Ethereum-style transaction (sender address, chain id, target, nonce, gas) live only in the Rust source, e.g. `validate_tx_relayer_data`: [5](#0-4) 

If any of these checks is fixed/strengthened in source but the corresponding `res/*.wasm` is not regenerated (because it already exists on disk and `build_contract` skips it), the binary nearcore actually ships and treats as canonical continues running the old, unpatched logic — a silent divergence between "reviewed source" and "deployed bytecode," identical in nature to the vault's `vault.js`/`vault.teal.tmpl` mismatch.

This is not a purely hypothetical risk in this codebase: nearcore already had to special-case a previously-shipped, buggy version of the wallet contract on testnet, permanently trusting its old (flawed) bytecode for already-created accounts: [6](#0-5) [7](#0-6) 

This confirms the exact failure class described in the report has already manifested in production once (`OLD_TESTNET`), and the current build process still contains the same structural weakness (skip-if-exists) that allows it to recur silently for mainnet/testnet/localnet artifacts.

### Impact Explanation
Every ETH-implicit account on NEAR runs whatever code is embedded in `res/*.wasm`. If a security-relevant check (sender/target/chain-id/nonce validation, fee accounting, etc.) is fixed in the Rust source but the corresponding compiled artifact is stale due to the skip-if-exists build logic, any transaction signer/relayer reachable through ordinary `FunctionCall` transactions to `rlp_execute` could exploit the un-patched check to move funds out of eth-implicit accounts without proper authorization — a concrete unauthorized value-movement path, reachable by an unprivileged transaction sender, matching the "Eve drains the funds" scenario in the original report.

### Likelihood Explanation
Likelihood is tied to human process error rather than an active exploit primitive today: it requires a developer to fix a bug in `./implementation`, forget (or not know) to delete the pre-existing `res/*.wasm` before running `cargo build`, and have that stale artifact reviewed/merged/shipped. Given the wallet-contract crate's own README documents this as a manual, easy-to-forget step, and nearcore has already needed to hard-code a workaround (`OLD_TESTNET`) for exactly this kind of divergence occurring once in the past, the likelihood of recurrence is non-trivial, matching the report's "High difficulty to notice, but concretely exploitable once it happens" framing.

### Recommendation
- Make the build deterministic and remove the skip-if-artifact-exists shortcut in `build_contract` (`runtime/near-wallet-contract/build.rs`) so the WASM is always rebuilt from `./implementation` when included in a release build, or add a CI check that recompiles the contract and diffs/hashes it against the checked-in `res/*.wasm` to fail the build on mismatch (mirroring the report's "maintain a single source of truth" recommendation).
- Extend the existing `check_wallet_contract` / `check_wallet_contract_magic_bytes` tests referenced in the README to run automatically in CI (not just as an ad hoc manual step) so any drift between source and shipped bytecode is caught before merge.

### Proof of Concept
Conceptual reproduction (build-process level, not a live-chain exploit):
1. Checkout `runtime/near-wallet-contract` with `res/wallet_contract_testnet.wasm` already present (as committed in the repo).
2. Modify a security check in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs::validate_tx_relayer_data` (e.g., weaken/remove the `tx.chain_id != Some(CHAIN_ID)` check) to simulate a "fix that should have been shipped" being introduced.
3. Run `cargo build` on `near-wallet-contract`; observe in `build_contract` (`runtime/near-wallet-contract/build.rs:56-61`) that because `./res/wallet_contract_testnet.wasm` already exists, the Docker rebuild is skipped and the old binary is retained.
4. `near_wallet_contract::wallet_contract()` (`runtime/near-wallet-contract/src/lib.rs:69-71`) still returns the stale bytecode, which is what any submitted `rlp_execute` transaction against an eth-implicit account will execute — demonstrating that source changes do not guarantee the deployed/executed bytecode is updated.

```rust
pub fn code_hash_matches_wallet_contract(chain_id: &str, code_hash: &CryptoHash) -> bool {
    let magic_bytes = wallet_contract_magic_bytes(&chain_id);

    if code_hash == magic_bytes.hash() {
        return true;
    }

    // Extra check needed for an old version of the wallet contract
    // that was on testnet. Accounts with that hash are still intentionally
    // made to run the current version of the wallet contract because
    // the previous version had a bug in its implementation.
    if chain_id == chains::TESTNET {
        let alt_testnet_code = OLD_TESTNET.magic_bytes();
        return code_hash == alt_testnet_code.hash();
    }

    false
}
```

```rust
fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

    let nonce = if tx.nonce <= U64_MAX {
        tx.nonce.low_u64()
    } else {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    };
    if nonce != expected_nonce {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    }
```
