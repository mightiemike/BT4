No vulnerability found for this question.

**Reasoning:**

The premise conflates two unrelated concepts. The doc comment in `ValidatorInfo` — "AccountAddresses are initially derived from the account auth pubkey; however, the auth key can be rotated, so one should not rely on this initial property" — refers to the Aptos account model where an address is originally computed from a transaction *authentication key* at account creation, but the auth key can later be rotated independently of the address. This has nothing to do with the binding between `account_address` and `consensus_public_key` inside `ValidatorInfo`/`ValidatorConsensusInfo`. [1](#0-0) 

That binding is enforced entirely on-chain in the `stake` module and cannot be forged by unprivileged input:

- `ValidatorInfo.addr` in the Move `ValidatorSet` is always the `pool_address` (the `StakePool` resource's own account address), set when the pool is created/joins the set. [2](#0-1) 

- `config.consensus_pubkey` can only be changed via `rotate_consensus_key`, which asserts the caller is the registered `operator_address` for that exact `pool_address`, and requires a valid proof-of-possession for the new key. [3](#0-2) 

Because `addr` and `config.consensus_pubkey` always originate from the same `StakePool`/`ValidatorConfig` resource pair, and only that pool's authorized operator can mutate the pubkey, there is no way for an unprivileged actor to produce a `ValidatorInfo`/`ValidatorConsensusInfo` where `account_address` is bound to a `consensus_public_key` belonging to a different logical validator.

On the Rust side, `ValidatorVerifier::from(&ValidatorSet)` and `build_index` simply copy the `(address, public_key)` pairs as they arrive from the already-consistent on-chain struct — they do not independently derive or validate the address from the key, so there's no additional attack surface introduced there. [4](#0-3) [5](#0-4) 

The scenario described (attacker supplying `account_address` "unrelated to `config().consensus_public_key`") would require either a bug in `rotate_consensus_key`'s authorization check (none found) or a way to write directly into another account's `ValidatorConfig`/`StakePool` resources (not possible for unprivileged callers, since these are `acquires`/`borrow_global_mut` on the caller-supplied `pool_address` gated by the `operator_address` check). This is a trusted-invariant misreading of the doc comment, not an exploitable state-integrity issue.

        // Checks the public key has a valid proof-of-possession to prevent rogue-key attacks.

            &bls12381::public_key_from_bytes_with_pop(
                new_consensus_pubkey,
                &proof_of_possession_from_bytes(proof_of_possession)
            );
        assert!(
            pubkey_from_pop.is_some(), error::invalid_argument(EINVALID_PUBLIC_KEY)
        );
        validator_info.consensus_pubkey = new_consensus_pubkey;

impl From<&ValidatorSet> for ValidatorVerifier {
    fn from(validator_set: &ValidatorSet) -> Self {
        let sorted_validator_infos: BTreeMap<u64, ValidatorConsensusInfo> = validator_set
            .payload()
            .map(|info| {
                (
                    info.config().validator_index,
                    ValidatorConsensusInfo::new(
                        info.account_address,
                        info.consensus_public_key().clone(),
                        info.consensus_voting_power(),
                    ),
                )
            })
            .collect();
        let validator_infos: Vec<_> = sorted_validator_infos.values().cloned().collect();
        for info in validator_set.payload() {
            assert_eq!(
                validator_infos[info.config().validator_index as usize].address,
                info.account_address
            );
        }
        ValidatorVerifier::new(validator_infos)
    }
