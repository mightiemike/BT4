### Title
Unbounded `domains` list from Functions source-code execution can inflate telemetry payload via `reportSourceCodeDomains` - ([File: core/services/functions/listener.go])

### Finding Description
`functionsListener.reportSourceCodeDomains` builds a `telem.FunctionsRequest` directly from the `domains []string` value returned by the external adapter's `RunComputation` call and marshals/sends it without any size or count validation: [1](#0-0) 

The `domains` slice originates from the external adapter's JSON response field `responseData.Domains []string`, which is populated by the sandboxed JS execution environment (e.g., every hostname the requester's script attempted to `fetch()`): [2](#0-1) 

Since the Functions product's entire premise is executing user-supplied JavaScript source code from a subscription owner's request, the number and content of `fetch()` calls (and thus the number/length of domain strings returned) is attacker-influenced. There is no cap in `reportSourceCodeDomains` on the number of domains, the length of each domain string, or the total serialized size before `proto.Marshal` and `l.urlsMonEndpoint.SendLog(bytes)` are invoked. Unlike the request-data path, which uses tiered size limits (`packFlags(1, 0) // tier no 1 of request size, allows up to 100 bytes` as seen in tests), no equivalent tier/size enforcement exists for the domains array on the output side.

### Impact Explanation
A malicious (but otherwise permitted) Functions requester could craft JS source containing many/large `fetch()` targets, causing `RunComputation` to return an oversized `domains` slice. This inflates the `telem.FunctionsRequest` protobuf payload sent to the telemetry/monitoring ingress on every request, which can increase telemetry pipeline load, `SendLog` invocation cost, and outbound bandwidth to the monitoring endpoint. This is a resource-consumption / telemetry data-quality issue local to the monitoring pipeline, not a node compromise or fund-loss vector — impact is bounded to telemetry/monitoring degradation rather than exploit of core Functions logic (secrets, transmission signing, OCR consensus are unaffected).

### Likelihood Explanation
Feasibility depends entirely on whether the actual external adapter (EA) that executes the JS sandbox and returns `responseData.Domains` itself enforces any cap on the number/length of returned domains before returning its HTTP response to the node — this enforcement point lives outside of `core/services/functions/listener.go` (in the EA implementation, which is not part of this repo/index) and could not be confirmed in this codebase. If the EA does not bound its own output, the path is straightforwardly reachable by any account permitted to submit a Functions request (an existing, intended user of the product, not a node operator or key holder), making this readily reproducible. If the EA already caps `domains`, this issue is largely mitigated at a layer outside the listener.

### Recommendation
Add an explicit bound in `reportSourceCodeDomains` (defense in depth, independent of any EA-side limit) before marshaling/sending: cap the number of domains (e.g., truncate/dedupe to N entries) and cap/truncate each domain string length, logging a warning when truncation occurs, similar to how request payload sizes are tiered elsewhere in the Functions plugin.

### Proof of Concept
Unit test plan (extend `core/services/functions/listener_test.go`):
1. Mock `eaClient.RunComputation` to return a `Domains` slice with, e.g., 100,000 entries or entries of extreme length (e.g., 64KB strings).
2. Trigger request handling as in `TestFunctionsListener_ReportSourceCodeDomains` (`core/services/functions/listener_test.go:354-393`), capturing the bytes sent to `ingressClient.Send`/`urlsMonEndpoint.SendLog`.
3. Assert whether `reportSourceCodeDomains` truncates/caps the payload (expected: it currently does not — the marshaled byte size grows proportionally to input size with no upper bound), demonstrating the missing invariant.

```go
func (l *functionsListener) reportSourceCodeDomains(requestId RequestID, domains []string) {
	r := &telem.FunctionsRequest{
		RequestId:   formatRequestId(requestId),
		NodeAddress: l.job.OCR2OracleSpec.TransmitterID.ValueOrZero(),
		Domains:     domains,
	}

	bytes, err := proto.Marshal(r)
	if err != nil {
		l.logger.Warnw("telem.FunctionsRequest marshal error", "err", err)
	} else {
		l.urlsMonEndpoint.SendLog(bytes)
	}
}
```
