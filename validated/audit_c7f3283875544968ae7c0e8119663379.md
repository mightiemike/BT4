### Title
Unbounded, non-deduplicated growth of the per-shop session-id index in `KVSessionStorage` causes DoS of session storage/auth flow - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` unconditionally appends the session id to the shop's session-id index list on every call, without checking whether the id is already present. Because `storeSession` is invoked on every OAuth callback/token exchange (including repeated logins/re-auths that reuse the same deterministic session id), the list grows without bound and without deduplication until the underlying KV value exceeds size limits, causing subsequent `findSessionsByShop`, `storeSession`, and `deleteSession`/`removeShopIds` calls for that shop to fail. This mirrors the analog-report bug class: an ever-growing, never-pruned collection whose read/write eventually fails/DoSes.

### Finding Description
`addShopIds` reads the existing id array for a shop key and blindly concatenates the new id(s), with no `includes()`/dedup check: [1](#0-0) 

This is called from `storeSession` on **every** session store, not just new sessions: [2](#0-1) 

Compare this to the Redis adapter's equivalent, which explicitly guards against duplicates before pushing: [3](#0-2) 

`storeSession` is invoked directly from the unauthenticated OAuth callback path used by app frameworks built on this library, e.g. `authCallback` in `shopify-app-express`: [4](#0-3) 

and `handleAuthCallbackRequest` in `shopify-app-remix`'s auth-code-flow strategy: [5](#0-4) 

Session ids for a given shop/user are deterministic and reused across re-authentications: offline session ids are `offline_${shop}` and embedded online session ids are `${shop}_${userId}`: [6](#0-5) [7](#0-6) 

Because the OAuth flow (begin → callback) can be re-triggered repeatedly by any actor who can reach the app's auth endpoints for a shop (e.g., re-login after logout, session expiry forcing re-auth, or an attacker/scriptable client hitting the callback URL repeatedly with a valid HMAC-signed query from a real OAuth grant), every completed OAuth round trip appends another copy of the *same* session id to the `shop:${shop}` KV value, since `addShopIds` never checks for existing entries.

### Impact Explanation
Over time, the `shop:${shop}` KV entry grows with duplicate ids without limit, since there is no dedup or pruning logic akin to the `deleteSessions`/`removeShopIds` filter path (which only runs on explicit deletion, not on store). Cloudflare KV enforces a maximum value size; once the JSON-serialized array exceeds that limit, `namespace.put` in `addShopIds`/`storeSession` will throw, breaking the OAuth callback flow for that shop going forward (new sessions cannot be stored), and `findSessionsByShop` will also degrade, having to fetch and attempt to load an ever-larger, duplicate-laden list including a growing volume of failed session lookups (`(await this.loadSession(id))!` — note the non-null assertion, which would even throw/return incorrect data if the referenced session was independently deleted). This is a Denial of Service against the app's authentication/session-storage subsystem for the affected shop, achievable purely by an unprivileged actor (a merchant or customer) driving the app through its normal, repeated OAuth re-authentication cycles.

### Likelihood Explanation
Likelihood depends on how often OAuth is re-triggered for the same shop/user without an intervening `deleteSession`. Apps using `KVSessionStorage` (Cloudflare Workers deployments) that experience frequent re-auth (e.g., short-lived online tokens, users re-installing/re-authorizing, or session expiry forcing repeated OAuth) will accumulate duplicates continuously. No special privilege is needed beyond completing OAuth, which any user with access to install/open the app can do repeatedly.

### Recommendation
In `addShopIds`, deduplicate before writing back to KV, mirroring the Redis implementation's `includes()` check:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```
Additionally, consider pruning stale/expired session ids periodically or capping the tracked list size, and avoid the non-null assertion in `findSessionsByShop` so a missing/expired session doesn't produce `undefined` entries silently or crash callers.

### Proof of Concept
1. Configure a Cloudflare Workers app using `KVSessionStorage` for `sessionStorage` (per `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`).
2. As a merchant/customer, complete OAuth once for `shop.myshopify.com` (offline or embedded online flow) — a session with a deterministic id (e.g., `offline_shop.myshopify.com`) is stored, and `shop:shop.myshopify.com` in KV becomes `["offline_shop.myshopify.com"]`.
3. Trigger OAuth again for the same shop/user (e.g., re-authorize the app, or let the online token expire and re-authenticate) any number of times.
4. After each cycle, `storeSession` → `addShopIds` appends the same id again: `["offline_shop.myshopify.com","offline_shop.myshopify.com", ...]`, growing linearly with each re-auth and never shrinking.
5. Repeating this a sufficient number of times (scriptable since OAuth begin/callback are just HTTP calls that can be automated by a user with legitimate install/re-install access) grows the KV value until it exceeds Cloudflare KV's per-value size limit, causing subsequent `namespace.put` calls in `storeSession`/`addShopIds` to fail and `findSessionsByShop` to return errors or corrupted results — denying session storage service for that shop.
