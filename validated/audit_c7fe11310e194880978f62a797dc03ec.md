### Title
Sandwichable on-chain price for TRC10 Bancor-relay `Exchange` swaps — slippage floor computed from manipulable in-block reserve state (`File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
java-tron's built-in TRC10 "Exchange" feature (a Bancor-formula relay market) computes the amount a user receives from an `ExchangeTransactionContract` swap entirely from the exchange pair's current on-chain reserve balances (`firstTokenBalance`/`secondTokenBalance`). This is the direct analog of Portico's use of `pool.slot0`: the "spot price" used to satisfy the user-supplied slippage floor is itself mutable, in-block state that any other account can shift by submitting `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transactions immediately before/after the victim's transaction in the same block, enabling classic sandwich-attack value extraction even when the victim's `expected` (minimum-received) check passes.

### Finding Description
The relay pool state lives in `ExchangeCapsule` and is read/mutated directly by `transaction()`: [1](#0-0) 

`ExchangeProcessor.exchange()` derives the output purely as a function of the current `firstTokenBalance`/`secondTokenBalance` at execution time: [2](#0-1) 

`ExchangeTransactionActuator.doValidate()` re-derives the swap output from this same manipulable pool state and only checks it against the user-supplied `expected` floor before allowing execution: [3](#0-2) 

`execute()` then performs the swap again against whatever the reserve balances are at that moment: [4](#0-3) 

Because reserves can be pushed arbitrarily far by any other account's `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction ordered immediately before the victim's transaction in the same block (and reversed immediately after), the price at execution time is not resistant to manipulation — structurally identical to reading `pool.slot0` for a swap's slippage check in the reported Uniswap-based bug class. There is no TWAP-like or externally-committed reference price; the only protection is the user-chosen `expected` value, and unlike Portico's vulnerable `maxSlippage`-based on-chain calculation, this system does let the user hardcode a minimum, but that minimum only bounds the worst case the victim is willing to accept — it does not prevent an attacker from capturing the price-impact spread via a front-run/back-run pair (sandwich), since the victim will still often set `expected` loosely (as most callers do) and the price the victim actually receives is set by whatever reserve state exists at the moment their transaction executes.

### Impact Explanation
An attacker (any ordinary, unprivileged account, or a block producer choosing tx order) can:
1. Observe a pending `ExchangeTransactionContract` in the mempool.
2. Submit a large opposing trade ordered just before it, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for the victim.
3. Let the victim's swap execute at the manipulated rate (still clearing their `expected` floor, since most callers don't set it to the exact theoretical output).
4. Submit a reversing trade immediately after to restore the pool and capture the price-impact spread as profit.

This directly transfers value from ordinary users of the TRC10 Exchange to the attacker/producer, i.e., unauthorized value extraction/asset accounting corruption for regular swap users — not merely a "worse rate" but real, sandwichable MEV extractable from the network's own AMM-like market feature.

### Likelihood Explanation
The `ExchangeTransactionContract` and Bancor relay logic are reachable by any broadcast transaction from an unprivileged account — no special permission is required to create exchange pairs, inject/withdraw liquidity, or execute trades. Any account (or especially any block-producing witness that controls transaction ordering within its own blocks) can trivially construct a front-run/back-run pair. This mirrors the "easily manipulable, exploited via sandwich attacks" characterization in the source report.

### Recommendation
- Do not rely purely on the pool's in-block reserve state as the "market price" reference for the `expected` check; consider adding a minimum-liquidity-fraction cap per trade (already partially bounded by `getExchangeBalanceLimit`), and/or a maximum permitted price-impact percentage per single swap, so a small trade cannot be pushed through a heavily-skewed pool in one block.
- Encourage/require callers to compute a tight `expected` value off-chain immediately before submission (short-lived, close to fair value) rather than a loose bound, and consider adding an expiration/deadline parameter to the contract to reduce the window during which mempool front-running is profitable.
- Evaluate rate-limiting or cooldown windows on `ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` targeting the same `exchange_id` within a single block to reduce the feasibility of same-block sandwich sequences.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from Victim on pair `(A, TRX)` with a loosely-set `expected`.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of `A` for `TRX` just before Victim's tx is packed, using `ExchangeCapsule.transaction()`'s Bancor formula to sharply reduce the `TRX` reserve balance relative to `A` (`chainbase/.../ExchangeCapsule.java:124-158`).
3. Victim's swap executes against `ExchangeTransactionActuator.execute()` at the now-skewed reserve ratio (`actuator/.../ExchangeTransactionActuator.java:61-69`), still passing the `tokenExpected` check in `doValidate()` (`actuator/.../ExchangeTransactionActuator.java:217-221`) because the floor was set loosely, but receiving far less than the pre-attack fair price.
4. Attacker submits a reversing `ExchangeTransactionContract` swapping back `TRX` for `A`, capturing the spread created by steps 2–3 as risk-free profit at Victim's expense.

    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

          firstTokenBalance,

          : firstTokenBalance - buyTokenQuant;

          : secondTokenBalance + sellTokenQuant;

    }
