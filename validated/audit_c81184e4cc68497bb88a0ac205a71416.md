This confirms the mechanism: `AccountContract::GlobalByAccount(id)` is resolved to concrete code dynamically at execution time via `RuntimeContractIdentifier::resolve` [1](#0-0) , and `GlobalContractDeployMode::AccountId` is explicitly designed so "the owner can update the contract for all its users" at any point after users have already pointed their accounts at it [2](#0-1) .

### Title
Value sent to a `FunctionCall` on an `AccountId`-mode global contract can be redirected by the contract owner redeploying malicious code between a caller's transaction submission and its execution - (File: `runtime/runtime/src/global_contracts.rs`, `runtime/runtime/src/contract_code.rs`)

### Summary
A caller inspects the code of a global contract referenced by `GlobalContractIdentifier::AccountId(owner)` (or an account that already points at it via `UseGlobalContractAction`), decides the logic is trustworthy, and sends a `FunctionCall` action with an attached deposit. Because the contract is not pinned by hash but resolved dynamically at execution time from whatever code currently sits at `TrieKey::GlobalContractCode { identifier: AccountId(owner) }`, the owner can redeploy different code to the same identifier between the caller's decision and the actual execution of the receipt, so the caller's deposit is spent against logic they never inspected or approved.

### Finding Description
`DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` is documented and implemented to let the owner "update the contract for all its users" [2](#0-1) . `use_global_contract` sets `AccountContract::GlobalByAccount(id)` on any account that opts in via `UseGlobalContractAction` [3](#0-2) . Crucially, this stored reference is only a pointer, not a commitment to specific code: at `FunctionCall` execution time, `RuntimeContractIdentifier::resolve` looks up the code hash currently associated with that `AccountId` identifier and this can differ from whatever code existed when the caller last inspected/decided to interact [1](#0-0) . The dispatch path for `Action::FunctionCall` performs this resolution fresh for every receipt, right before invoking the VM [4](#0-3) , so nothing in the transaction that carries the attached deposit references the specific code version the sender expected. `GlobalContractAccessExt::hash`/`code` similarly resolve the `AccountId` identifier to whatever is currently stored, not a version pinned at signing time [5](#0-4) . This exactly mirrors the reported bug class: a value-bearing action (attached deposit/`FunctionCall`) is executed against mutable state (the referenced contract logic) that a counterparty fully controls and can change after the victim commits to sending value but before the transaction lands on-chain, without any hash/commitment check tying execution to the inspected state.

### Impact Explanation
An owner of an `AccountId`-mode global contract (or any account that legitimately publishes such a contract, e.g. as a "vault", "swap", or "lending" front-end pattern) can advertise benign, audited code, wait for users to send `FunctionCall`s with attached NEAR deposits or to have `Transfer`/`FunctionCall` receipts in flight, then redeploy malicious code to the same `AccountId` identifier. Any receipt whose `FunctionCall` action executes after the redeploy runs the new, attacker-controlled logic against the caller's attached deposit, allowing the deposit to be diverted (e.g., to the attacker) instead of performing the expected logic — concrete unauthorized value movement with no compromise of consensus needed, reachable purely by an unprivileged account owner redeploying its own global contract and any unprivileged caller sending a normal transaction.

### Likelihood Explanation
This requires no validator collusion, no network-level attack, and no cross-shard timing tricks beyond ordinary same-chunk/next-chunk propagation delay between a caller signing/broadcasting a transaction and it being included and its receipt executed. Any account can deploy an `AccountId`-mode global contract, any account can point itself at it (or advertise itself as already using it), and redeployment is a single, always-available `DeployGlobalContractAction`. The main constraint is that a victim must be induced to send a deposit-bearing call without pinning a specific code hash (which the protocol does not offer as an alternative to the `AccountId` mode for this purpose — only `CodeHash` mode is immutable) — this is a realistic social-engineering/trust-abuse pattern rather than a rare edge case.

### Recommendation
Consider one of:
1. Require `FunctionCall` receipts carrying non-zero attached deposit to fail (or be explicitly opt-in) when the receiver resolves through `AccountContract::GlobalByAccount`, forcing value-bearing calls to either target immutable `CodeHash`-mode contracts or local code.
2. Allow callers to pin the expected code hash for an `AccountId`-mode global contract inside the transaction/receipt (analogous to a commitment hash), and have the runtime verify at execution time (in `RuntimeContractIdentifier::resolve` or in `action_function_call`) that the currently resolved `code_hash` matches the caller's expectation, failing the action otherwise.
3. Document and strongly discourage sending deposits to `AccountId`-mode global contracts without an explicit escrow/timelock, since this is architecturally equivalent to sending funds to logic that can change underneath the caller.

### Proof of Concept
Conceptual sequence (matches the `AccountId` global-contract flow already exercised by existing tests such as `test_global_contract_update` [6](#0-5) ):
1. Owner `O` deploys benign code `C1` under `GlobalContractDeployMode::AccountId` (`DeployGlobalContractAction`).
2. Victim `V` inspects `C1` (e.g., via `view_global_contract_code`), decides its logic is safe, and calls `UseGlobalContractAction { contract_identifier: AccountId(O) }` on an account, or directly targets an account already using it, then submits a `FunctionCall` with an attached deposit intended to be processed by `C1`.
3. Before `V`'s `FunctionCall` receipt executes (same or next chunk), `O` submits `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` and malicious code `C2` (e.g., a method with the same name that unconditionally transfers the attached deposit to `O`).
4. `RuntimeContractIdentifier::resolve` for `V`'s pending `FunctionCall` now resolves to `C2`'s code hash (`GlobalContractIdentifier::AccountId(O).hash(...)` returns the freshly stored hash) [1](#0-0) , so `V`'s deposit is spent under `C2`'s logic instead of the inspected `C1`, with no error and no commitment check anywhere in the execution path [4](#0-3) .

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }

    fn code(self, store: &TrieUpdate) -> Result<Option<ContractCode>, StorageError> {
        let key = TrieKey::GlobalContractCode { identifier: self.clone().into() };
        let code_hash = match self {
            GlobalContractIdentifier::AccountId(_) => None,
            GlobalContractIdentifier::CodeHash(hash) => Some(hash),
        };
        let code = store.get(&key, AccessOptions::DEFAULT)?;
        Ok(code.map(|code| ContractCode::new(code, code_hash)))
    }
