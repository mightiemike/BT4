### Title
Receipt size validation happens before `output_data_receivers`/return-value wrapping is finalized, allowing receipts to exceed `max_receipt_size` - ([File: test-loop-tests/src/tests/max_receipt_size.rs])

### Summary
The reported openbrush bug class is "a size/amount check is performed against an incomplete quantity, so a component added after the check causes the real value to exceed the intended cap." Nearcore has a directly analogous, already-documented defect: receipt-size validation against `max_receipt_size` is performed before `output_data_receivers` are attached to a promise-return receipt, and before a large returned value is wrapped into a `DataReceipt`. As a result, the final serialized receipt can exceed `max_receipt_size` even though it passed the size check.

### Finding Description
`max_receipt_size` is the protocol-level cap on receipt size used throughout congestion control and the bandwidth scheduler (e.g. `BandwidthSchedulerParams::calculate` asserts `max_single_grant >= max_receipt_size` because "it'll be impossible to send a max size receipt" otherwise) [1](#0-0) . The test suite explicitly documents that this cap can be silently violated in two code paths and links this to a still-open bug:

- Promise return: a function call generates a receipt whose size is validated at exactly `max_receipt_size`, but `output_data_receivers` are appended to that receipt *after* validation, pushing the final receipt above the limit. The test comment states plainly: "The receipt should be rejected, but currently isn't because of a bug (See near/nearcore#12606)" [2](#0-1) .
- Value return: a contract returns a value as large as `max_receipt_size`; that value gets wrapped into a `DataReceipt` whose total size (value + receipt overhead) exceeds `max_receipt_size`, again bypassing rejection, per the same referenced issue [3](#0-2) .

Both tests assert the oversized receipt does get produced and persisted (`assert_oversized_receipt_occurred`), confirming the cap-check is checked against an incomplete/insufficient quantity — the direct structural analog of `max_flashloan` computing an amount without accounting for the `PSP22Capped` cap, later discovered to be wrong when the real constrained operation runs. [4](#0-3) 

By contrast, the yield/resume path was fixed to check the *final* receipt size and correctly rejects an oversized yield receipt with `ReceiptSizeExceeded` [5](#0-4) , showing the intended enforcement point (post-assembly, pre-persistence) is missing from the promise-return and value-return paths.

### Impact Explanation
`max_receipt_size` is a hard protocol invariant relied on by: (1) the bandwidth scheduler's admission model, which assumes any single receipt fits within `max_single_grant` (`max_single_grant >= max_receipt_size` assertion) [6](#0-5) ; (2) congestion control's outgoing-buffer/bandwidth-request sizing, which clamps request sizes to `max_receipt_size` (`get_receipt_group_sizes_for_buffer_to_shard` clamped at `:561` per the congestion spec) [7](#0-6) ; and (3) chunk/state-witness size limits that size-gate cross-shard receipt transport. A receipt that silently exceeds `max_receipt_size` can be produced by any unprivileged contract call from a single transaction (no special privileges needed — just a promise chain that appends `output_data_receivers` after generating a max-size receipt, or a `value_return` at the size limit). This can violate downstream size assumptions in bandwidth-scheduler grants and congestion-control receipt-group sizing, both of which are consensus-critical, deterministic computations feeding into chunk headers; a discrepancy between what different code paths assume about receipt size vs. what is actually produced is the kind of invariant violation that can lead to state-witness/limit violations or receipt-transport inconsistency across chunk boundaries.

### Likelihood Explanation
High reachability: this is triggerable by any account submitting a normal transaction that calls a deployed contract with a promise chain (`generate_large_receipt`-style helper methods already exist in the test contract used for this exact test), no elevated privileges, staking, or validator status required. The bug is already confirmed present by test comments in the current tree ("currently isn't because of a bug"), i.e., it has not yet been fixed in this codebase snapshot.

### Recommendation
Move the `max_receipt_size` validation to occur after the receipt is fully assembled (including `output_data_receivers` and any wrapped return value in the resulting `DataReceipt`), mirroring the fix already applied to the yield/resume path (`ReceiptSizeExceeded` check against the final serialized receipt). Add a size check immediately before a receipt is queued for cross-shard delivery/persistence, not only when the "core" action receipt is first constructed.

### Proof of Concept
The existing test suite already reproduces both variants of the issue and asserts the resulting invariant violation:
- `test_max_receipt_size_promise_return` builds a promise DAG `[A -then-> B]` where `A` creates promise `C` (a maximum-size receipt) and calls `promise_return`; the runtime then appends `output_data_receivers` to `C`'s receipt, pushing it over `max_receipt_size`, and the test confirms via `assert_oversized_receipt_occurred` that the oversized receipt is accepted rather than rejected [8](#0-7) .
- `test_max_receipt_size_value_return` has a contract return a value of exactly `max_receipt_size` bytes, which is wrapped in a `DataReceipt` larger than the limit; `assert_oversized_receipt_occurred` again confirms the runtime persists the oversized receipt instead of rejecting it [9](#0-8) .

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
