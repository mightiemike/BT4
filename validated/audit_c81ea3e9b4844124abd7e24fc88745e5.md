### Title
Unvalidated `RevertInstructions.FundRecipient` / outbound `Sender` allows silent misroute of refunded/reverted PRC20 funds instead of a safe revert - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
The external report's root cause is that a cancel/refund path uses an address value that was never validated as a real, meaningful recipient before value is moved to it — instead of reverting cleanly, the mis-specified recipient silently absorbs (or loses) the funds. Push Chain's `x/uexecutor` outbound revert/refund flow has the same shape: `outbound.Sender` and `RevertInstructions.FundRecipient` are only *canonicalized* (`Canonicalize()` in `x/uexecutor/types/inbound.go`, applying `utils.LenientCanonicalizeAddress`) but never checked with `utils.IsValidAddress` before being passed straight into `common.HexToAddress(...)` and used as the destination of a PRC20 mint.

### Finding Description
When an outbound fails, `handleFailedOutbound` in `x/uexecutor/keeper/outbound.go` (lines 99-161) re-mints the bridged PRC20 back to a "revert recipient": [1](#0-0) 

The `recipient` is either `outbound.Sender` or `outbound.RevertInstructions.FundRecipient` — both plain strings taken from attacker/relayer-controlled inbound/outbound data — and is passed directly to `common.HexToAddress(recipient)` with no `utils.IsValidAddress`/hex-format check at this call site. `common.HexToAddress` (go-ethereum) never errors on malformed input: it decodes whatever hex bytes it can and left-pads/truncates the rest, so a malformed, empty, or non-hex `recipient` string silently resolves to some address (in the worst case, the zero address or an unowned address) rather than causing a revert.

The same unvalidated-string-to-address pattern recurs in `applyGasRefund` (same file), which computes `refundRecipient` from `outbound.Sender`/`RevertInstructions.FundRecipient` and calls `common.HexToAddress(refundRecipient)` before invoking `CallUniversalCoreRefundUnusedGas`: [2](#0-1) 

Upstream, `RevertInstructions.FundRecipient` is set from the original `Inbound.RevertInstructions` (an attacker-observable, relayer-supplied field per the CAIP-2 inbound event) and is only run through `Canonicalize()`: [3](#0-2) 

`ValidateForExecution` in the same file validates `Recipient` for `FUNDS`/`GAS`/`*_AND_PAYLOAD` types using `utils.IsValidAddress(p.Recipient, utils.HEX)`, but there is **no equivalent check anywhere for `RevertInstructions.FundRecipient`**: [4](#0-3) 

`OutboundTx.ValidateBasic` (`x/uexecutor/types/outbound_tx.go`) validates `Sender` with `utils.IsValidAddress`, but this validation is not invoked in the revert/refund code path (`handleFailedOutbound`/`applyGasRefund`), and there is no equivalent validation of `RevertInstructions.FundRecipient` on `OutboundTx` either.

### Impact Explanation
If a relayer/observer submits (or an honest-vote-quorum records) an `Inbound`/`OutboundTx` whose `RevertInstructions.FundRecipient` is not a syntactically valid EVM hex address (e.g., truncated, garbage, or non-hex characters — something `Canonicalize`'s `LenientCanonicalizeAddress` explicitly tolerates and passes through unrejected), the eventual revert/refund of bridged PRC20 funds or excess gas will mint value to whatever address `common.HexToAddress` happens to compute from that malformed string, rather than reverting the operation. This can result in **permanent loss of user/protocol funds** (funds minted to an unreachable/zero/unintended address) instead of a safe, observable failure — the same failure mode as the original report where a validation mismatch caused mis-delivery of value instead of a clean revert. This falls squarely within the "Registry and accounting path" and "corruption of ... refund accounting ... revert destination" allowed-impact categories.

### Likelihood Explanation
Reachability depends on whether `FundRecipient` (or `Sender`) can actually reach `handleFailedOutbound`/`applyGasRefund` in malformed form under honest-validator quorum. Because `Canonicalize()` is explicitly documented as "lenient (unparseable values are kept trimmed, never rejected)" and no downstream call in the revert/refund path enforces `utils.IsValidAddress` on `FundRecipient`, a malformed value that entered the system via a mis-parsed or attacker-influenced inbound observation (or via `MsgRevertStuckInbound`, which only calls `inbound.ValidateBasic()` — not necessarily a strict hex check on `FundRecipient`) could persist all the way to the fund-movement call. I was not able to fully confirm within available context whether `ValidateBasic()`/ballot-key derivation elsewhere blocks a non-hex `FundRecipient` before it reaches `buildRevertOutbound`/`handleFailedOutbound` in all code paths — this needs verification against the full `ValidateBasic` implementation and any outbound-message validators guarding `MsgVoteOutbound`/`MsgRevertStuckInbound`, which the available index did not fully expose.

### Recommendation
Add an explicit `utils.IsValidAddress(fundRecipient, utils.HEX)` (or equivalent EVM address-format) check on `RevertInstructions.FundRecipient` in `Inbound.ValidateForExecution` (mirroring the existing `Recipient` check) and add the same check in `handleFailedOutbound` / `applyGasRefund` immediately before calling `common.HexToAddress`, falling back to a safe default (or aborting the outbound via `AbortOutbound` for manual intervention) rather than silently minting to a derived address when the check fails.

### Proof of Concept
Conceptual PoC (not fully verified against every intermediate validation layer, per Likelihood note above):
1. An inbound/outbound event is submitted (via the relayer/observer path) with `RevertInstructions.FundRecipient` set to a malformed but non-empty string (not `0x`-prefixed valid hex, e.g. `"not-a-hex-address"` — a value already used in existing unit tests such as `test/integration/uexecutor/execute_inbound_gas_test.go:478` for *recipient* field validation, showing such strings are exercised in the codebase).
2. `Canonicalize()` passes this value through unchanged/lenient (`x/uexecutor/types/inbound.go:32-35`).
3. No validation function rejects `RevertInstructions.FundRecipient` specifically (confirmed absent from `ValidateForExecution`, `x/uexecutor/types/inbound.go:150-172`).
4. When the corresponding outbound later fails, `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go:107-119`) resolves `recipient` to this malformed string and calls `common.HexToAddress(recipient)`, which silently succeeds and yields an address derived from partial/garbage bytes instead of erroring.
5. `CallPRC20Deposit` mints the reverted PRC20 amount to that address — funds are misrouted/potentially permanently lost instead of the operation reverting or being flagged for manual intervention.

func (p *Inbound) Canonicalize() {
	p.SourceChain = strings.TrimSpace(p.SourceChain)
	p.TxHash = utils.LenientCanonicalizeTxHash(p.SourceChain, p.TxHash)
	p.Sender = utils.LenientCanonicalizeAddress(p.SourceChain, p.Sender)
	p.AssetAddr = utils.LenientCanonicalizeAddress(p.SourceChain, p.AssetAddr)
	// Recipient lives on Push Chain (EVM) regardless of source chain.
	p.Recipient = utils.LenientCanonicalizeEVMAddress(p.Recipient)
	p.LogIndex = strings.TrimSpace(p.LogIndex)
	p.Amount = strings.TrimSpace(p.Amount)
	p.RawPayload = utils.CanonicalizeHexBlob(p.RawPayload)
	p.VerificationData = utils.CanonicalizeHexBlob(p.VerificationData)
	if p.RevertInstructions != nil {
		// Refunds return to the source chain.
		p.RevertInstructions.FundRecipient = utils.LenientCanonicalizeAddress(p.SourceChain, p.RevertInstructions.FundRecipient)
	}
}
