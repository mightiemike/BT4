Based on my investigation, I found a genuine, code-documented integrity gap in the transaction-output verification routine used by replay/verification tooling.

### Title
`ensure_match_transaction_info` skips state-checkpoint / hot-state / position-state root comparison, letting replay-verify accept a corrupted authenticated state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator that decides whether a locally re-executed transaction output matches the persisted, ledger-committed `TransactionInfo`. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, even though `TransactionInfoV1` carries these fields as part of the authenticated, accumulator-committed record.

### Finding Description
The function's own comment documents the gap: [1](#0-0) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

`ensure_match_transaction_info` only asserts on `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash: [2](#0-1) . It never compares against `TransactionInfo::state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, which are part of `TransactionInfoV1` and are what gets committed into the transaction accumulator as the authenticated per-transaction record (verified elsewhere via `AccumulatorProof::verify` in `types/src/proof/definition.rs`, e.g. [3](#0-2) ).

This comparator is used as the sole correctness gate in two consumers:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which calls it to decide pass/fail for each replayed transaction against the archived `TransactionInfo` [4](#0-3) .
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, used during chunk-executor archive/backup verification [5](#0-4) .

Because the state-checkpoint hashes are excluded from the comparison, a divergence between the locally computed sparse-Merkle/JMT state root (main state, hot state, or the newer "position state" tree computed in `do_state_checkpoint.rs`, which independently derives `position_state_checkpoint_hash` via `get_state_checkpoint_hashes` [6](#0-5) ) and the value stored in the historical `TransactionInfoV1` on the accumulator will not be caught by replay verification, even though write set and events match.

### Impact Explanation
Replay-verify tooling (`db-tool replay-on-archive`) and the chunk-executor's execution-verification path are the primary mechanisms operators and auditors use to confirm that a node's local re-execution of history reproduces the exact, accumulator-committed ledger state, including the state root that clients trust via `TransactionAccumulatorRangeProof`/`AccumulatorProof` verification. Because the checkpoint-hash fields are silently excluded, a bug in state-checkpoint/hot-state/position-state root computation (JMT update logic, hot-state eviction, or the new position-state tree) could produce a wrong committed state root that would otherwise be flagged by `ensure_match_transaction_info`, but instead is accepted as a "successful" verified replay. This means an authenticated, proof-bearing field (`state_checkpoint_hash`) can diverge from the correct VM/storage result without detection by the tool whose entire purpose is to catch exactly that divergence — matching the "wrong … state proof accepted as valid" and "authenticated API … bound to the wrong … proof context" impact categories.

### Likelihood Explanation
The gap is deterministic and always present (not race- or environment-dependent): any run of `replay_on_archive` or chunk-executor `verify_execution` will never compare checkpoint hashes, by construction of the comparator. The trigger condition — an actual computation bug in the state-checkpoint/hot-state/position-state root logic — is a separate prerequisite, and the code comment itself indicates this is a known, currently-unmitigated blind spot tied to the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag (present in `types/src/on_chain_config/aptos_features.rs`). The confirmed, provable part is that the verification gate itself is incomplete; I could not determine (within this investigation's scope) whether a concrete state-root-computation bug already exists that this gap would currently be masking, so the practical current-mainnet severity depends on that separate, unconfirmed factor.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionOutput`/execution context) against the corresponding fields on `txn_info: &TransactionInfo`, returning an error on mismatch, consistent with how `write_set_hash` and `event_root_hash` are already validated, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not independently reproducible from static analysis alone: the vulnerable code path (missing comparison) is confirmed directly in `types/src/transaction/mod.rs`, but exercising it end-to-end requires an execution-side bug that produces a divergent state-checkpoint root while write set and events still match — verifying that requires triggering a real JMT/hot-state/position-state discrepancy, which requires runtime state manipulation not obtainable via static code review with the tools available here.

    /// Verifies an element whose hash is `element_hash` and version is `element_version` exists in
    /// the accumulator whose root hash is `expected_root_hash` using the provided proof.
    pub fn verify(
        &self,
        expected_root_hash: HashValue,
        element_hash: HashValue,
        element_index: u64,
    ) -> Result<()> {
        ensure!(
            self.siblings.len() <= MAX_ACCUMULATOR_PROOF_DEPTH,
            "Accumulator proof has more than {} ({}) siblings.",
            MAX_ACCUMULATOR_PROOF_DEPTH,
            self.siblings.len()
        );

        let actual_root_hash = self
            .siblings
            .iter()
            .fold(
                (element_hash, element_index),
                // `index` denotes the index of the ancestor of the element at the current level.
                |(hash, index), sibling_hash| {
                    (
                        if index % 2 == 0 {
                            // the current node is a left child.
                            MerkleTreeInternalNode::<H>::new(hash, *sibling_hash).hash()
                        } else {
                            // the current node is a right child.
                            MerkleTreeInternalNode::<H>::new(*sibling_hash, hash).hash()
                        },
                        // The index of the parent at its level.
                        index / 2,
                    )
                },
            )
            .0;
        ensure!(
            actual_root_hash == expected_root_hash,
            "{}: Root hashes do not match. Actual root hash: {:x}. Expected root hash: {:x}.",
            type_name::<Self>(),
            actual_root_hash,
            expected_root_hash
        );

        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
