### Title
Unbounded recursion in bytecode-segment hashing during compiled-class-hash computation - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The `bytecode_hash_node` function used to compute a declared class's compiled-class-hash (V2 hashing scheme) recurses once per nesting level of the CASM `bytecode_segment_lengths` structure (`NestedIntList`) with no depth bound. The equivalent structure-building recursion in the Starknet OS hint implementation (`create_bytecode_segment_structure_inner`) and the corresponding `BytecodeSegmentNode::hash` walker have the same property. None of these recursive routines run inside the sandboxed, resource-limited compiler subprocess used for Sierra→CASM compilation — they execute in-process inside the sequencer (blockifier) and inside Starknet OS re-execution, which is the sequencer's core state-transition path.

### Finding Description
When a class is declared, the Sierra→CASM compiler subprocess (`crates/apollo_compile_to_casm/src/compiler.rs`) is invoked with CPU-time, file-size and address-space `setrlimit` bounds via `ResourceLimits` [1](#0-0) . Critically, no `RLIMIT_STACK` is set, and — more importantly — the CASM bytecode segment structure (`CasmContractClass::bytecode_segment_lengths`, represented as `NestedIntList`) that the compiler emits is later re-consumed **outside** that sandbox, directly in-process, whenever the compiled-class-hash needs to be (re)computed:

- `bytecode_hash_node` in `starknet_api` recurses over `NL::iter_children()` with no depth limit, once per nested segment: [2](#0-1) 
- `create_bytecode_segment_structure_inner` in the Starknet OS hint code performs the same unbounded recursion while reconstructing the `BytecodeSegmentNode` tree used during OS re-execution: [3](#0-2) 
- `BytecodeSegmentNode::hash` walks the same tree recursively when hashing: [4](#0-3) 
- A near-identical, explicitly depth-unaware recursive builder (`NestedFeltCounts::new_inner`) exists in the blockifier as well, currently asserting depth ≤ 1 only for its specific caller, but demonstrating the same recursive-without-bound pattern used elsewhere: [5](#0-4) 

This is the same bug class as the reported xgrammar advisory (CWE-674, uncontrolled recursion on attacker-supplied nested structure causing stack exhaustion / SIGSEGV): a recursive-descent walk over a nested container whose depth is derived from untrusted, attacker-submitted input, with no explicit recursion-depth check.

The gateway's stateless validation only bounds total Sierra program length (`max_contract_bytecode_size` = 81920) and serialized class size (`max_contract_class_object_size` ≈ 4 MB); it does not bound the *nesting depth* of the CASM bytecode-segment tree that the compiler subsequently produces: [6](#0-5) . The Sierra→CASM compilation itself is sandboxed with CPU/memory rlimits and gracefully converts subprocess crashes/signals into a `CompilationUtilError`: [7](#0-6) . However, the segment-tree consumers listed above are not behind that subprocess boundary — they run directly in the sequencer/OS process whenever a compiled class's hash is computed (e.g., during block finalization/state-diff computation, and during Starknet OS re-execution).

### Impact Explanation
If a Sierra program can be crafted (within existing size limits) such that the compiler emits a `bytecode_segment_lengths`/`NestedIntList` tree with a sufficiently deep nesting chain (e.g., via deeply nested branch/function structure that the compiler's segmentation heuristic maps to nested segments), the unbounded recursive walk during compiled-class-hash (re)computation can exhaust the native thread stack and crash the process (SIGSEGV), independent of the CPU/memory-gas-based bounds that protect Cairo VM/Native execution recursion elsewhere in the codebase (e.g., `max_recursion_depth`, `RUST_MIN_STACK`, dedicated large-stack threads for cairo_native — see `crates/native_blockifier/.cargo/config.toml` and `execute_txs_sequentially`). A crash in this in-process path (unlike a crash inside the sandboxed compiler subprocess, which is caught and converted to an error) would abort block building or OS re-execution on the affected node — a denial-of-service that halts confirmation of new transactions, matching the "network unable to confirm new transactions" impact criterion.

### Likelihood Explanation
Likelihood is uncertain because it depends on whether the cairo-lang Sierra→CASM compiler's segmentation heuristic can be coerced, within the existing 81920-felt bytecode-size and ~4 MB class-size limits, to emit a segment tree deep enough (segment depth generally tracks call/branch structure, not an attacker-chosen literal like the xgrammar PoC's `(` repetition) to overflow a typical several-MB stack. This requires further investigation/fuzzing of the compiler's segmentation behavior on adversarially structured Sierra programs (e.g., deeply nested match/if-else chains or deeply nested function call trees) to confirm whether achievable depth is sufficient to overflow the stack before other resource limits (gas, size) are hit. No explicit recursion-depth guard exists in any of the cited functions, which is the concrete root-cause match to the reported bug class.

### Recommendation
- Add an explicit maximum-depth check when deserializing/traversing `NestedIntList`/`BytecodeSegmentNode` structures in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` and `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`, rejecting classes whose segment tree exceeds a safe bound.
- Convert these recursive traversals to iterative (explicit stack/work-queue) implementations to remove the native-stack dependency entirely.
- Verify the maximum possible segment-tree depth producible by the Sierra→CASM compiler under the current `max_contract_bytecode_size`/`max_contract_class_object_size` limits, and, if unbounded relative to input structure, add a depth cap enforced by the gateway at declare time (similar to `validate_class_length`/`validate_entry_points_sorted_and_unique` in `stateless_transaction_validator.rs`).

### Proof of Concept
Not independently verified end-to-end (would require constructing a Sierra program that, after compilation to CASM by the exact `SierraToCasmCompiler`, yields a `bytecode_segment_lengths` `NestedIntList` with extreme nesting depth, then invoking `bytecode_hash_node`/`create_bytecode_segment_structure_inner` on it to observe a stack overflow). The absence of any depth check in the cited recursive functions is confirmed directly from source; confirming the achievable nesting depth from the compiler's segmentation algorithm under current size limits requires additional experimentation that was not performed here.

```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```

```rust
impl BytecodeSegmentNode {
    pub(crate) fn hash<H: HashFunction>(&self) -> StarkHash {
        match self {
            BytecodeSegmentNode::Leaf(leaf) => H::hash_array(&leaf.data),
            BytecodeSegmentNode::InnerNode(inner_node) => {
                let flatten_input: Vec<_> = inner_node
                    .segments
                    .iter()
                    .flat_map(|segment| [Felt::from(segment.length), segment.node.hash::<H>()])
                    .collect();
                H::hash_array(&flatten_input) + Felt::ONE
            }
        }
    }
```

```rust
pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
```

```rust
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,

    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);

            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
```

```rust
pub fn compile_with_args(
    compiler_binary_path: &Path,
    contract_class: ContractClass,
    additional_args: &[&str],
    resource_limits: ResourceLimits,
) -> Result<Vec<u8>, CompilationUtilError> {
    // Create a temporary file to store the Sierra contract class.
    let serialized_contract_class = serde_json::to_string(&contract_class)?;

    let mut temp_file = NamedTempFile::new()?;
    temp_file.write_all(serialized_contract_class.as_bytes())?;
    let temp_file_path = temp_file.path().to_str().ok_or(CompilationUtilError::UnexpectedError(
        "Failed to get temporary file path".to_owned(),
    ))?;

    // Set the parameters for the compile process.
    let mut command = Command::new(compiler_binary_path.as_os_str());
    command.arg(temp_file_path).args(additional_args);

    // Apply the resource limits to the command.
    resource_limits.apply(&mut command);

    // Run the compile process.
    let compile_output = command.output()?;

    if !compile_output.status.success() {
        let stderr_output = String::from_utf8(compile_output.stderr)
            .unwrap_or_else(|_| "Failed to decode stderr output".to_string());

        let error_message = format_compiler_error(&stderr_output, &compile_output.status);
        return Err(CompilationUtilError::CompilationError(error_message));
    }
    Ok(compile_output.stdout)
}
```
