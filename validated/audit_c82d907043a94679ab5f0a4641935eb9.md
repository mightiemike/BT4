### Title
Replay-verify integrity check silently ignores state/hot-state/position checkpoint-root divergence - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` stored in (and proven against) the ledger's transaction accumulator. It checks status, gas, write-set hash, and event-root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually commit to the resulting state/JMT root. This mirrors the external report's bug class: a component whose entire job is to bind a computed result to a committed value silently fails to enforce the binding on the most important field, so a divergence goes undetected by exactly the tooling meant to catch it.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  verifies transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against a trusted `TransactionInfo`, but the function contains an explicit TODO acknowledging it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [2](#0-1) .

This function is called from `storage/db-tool/src/replay_on_archive.rs`, whose `Verifier::verify`/`execute_and_verify` re-executes archived transactions with `AptosVMBlockExecutor` and checks the output against `expected_txn_infos` pulled from backup/archive data [3](#0-2) , and from `aptos-move/aptos-debugger/src/aptos_debugger.rs`. `TransactionInfo` (V1) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class committed fields [4](#0-3) , and these are the values that bind the transaction accumulator leaf to the actual JMT/state root produced by execution. Because `ensure_match_transaction_info` never compares the locally-computed checkpoint hash to the one baked into the trusted `TransactionInfo`, a state-root divergence (e.g., a bug in state-merkle commit, hot-state, or the newer "trading-native"/position state feature) will not be flagged as a failed transaction by replay-verify — the tool will report success even though the resulting ledger state differs from the authenticated one.

By contrast, the separate accumulator/proof-consuming path `TransactionOutputListWithProof::verify` (used for real proof verification of output lists) only checks write-set hash, gas, status and event root as well — it does not need to check state checkpoint hash because it doesn't reconstruct state, whereas `ensure_match_transaction_info` specifically exists to certify that *local re-execution* reproduces the *committed* result, and skipping the checkpoint-hash comparison defeats that purpose for the state-root dimension.

### Impact Explanation
This breaks the state-commitment integrity guarantee for the class of consumers that rely on replay-verify to catch state divergence: `db-tool replay_on_archive` and `aptos-debugger`. These tools are the primary mechanism operators and auditors use to confirm that historical execution reproduces the exact same state, including as new state components (hot state, "trading-native"/position state) are rolled out behind feature flags like `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. If execution logic introduces a state-root-affecting bug (in state-merkle write, hot-state promotion, or position-state commit) that does not also change the write-set bytes or events, replay-verify will report success, masking a real divergence in committed ledger state. This is a hard-fork-relevant integrity gap: a node could believe replay verification passed while its computed durable state actually differs from the authenticated ledger.

### Likelihood Explanation
The gap is deterministic and unconditional whenever `ensure_match_transaction_info` is the verification path used (both call sites use it unconditionally) — it is not a rare edge case, but a structural omission that the code comment itself flags as needing to be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." Because the new position/trading-native state root feature is under active development, any bug introduced there (or in hot-state) prior to closing this check would go unnoticed specifically by the audit mechanism designed to detect it.

### Recommendation
Extend `ensure_match_transaction_info` to also compare locally computed `state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` when applicable) against the corresponding fields of the trusted `TransactionInfo`, consistent with how write-set and event-root hashes are already checked, before any feature depending on those additional checkpoint roots is enabled in production.

### Proof of Concept
Not independently reproducible as a live exploit from the code alone — the finding is a structural verification gap rather than a triggerable state-corruption bug: `ensure_match_transaction_info` at [1](#0-0)  can be shown to omit the checkpoint-hash comparisons that `TransactionInfoV1`/`TransactionInfoV0` carry [5](#0-4) ; a concrete PoC would require constructing a `TransactionOutput` whose write set/events hash match a given `TransactionInfo` but whose resulting state root (as separately computed by the executor) differs, then showing `replay_on_archive`'s `execute_and_verify` ( [3](#0-2) ) reports no failure — this would need running the actual executor pipeline, which is outside the scope of static code review here.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    // Execute the verify one valid range
    pub fn verify(&self, start: Version, limit: u64) -> Result<Vec<Error>> {
        let mut total_failed_txns = Vec::with_capacity(limit as usize);
        let txn_iter = self
            .backup_handler
            .get_transaction_iter(start, limit as usize)?;
        let mut cur_txns = Vec::with_capacity(limit as usize);
        let mut cur_persisted_aux_info = Vec::with_capacity(limit as usize);
        let mut expected_events = Vec::with_capacity(limit as usize);
        let mut expected_writesets = Vec::with_capacity(limit as usize);
        let mut expected_txn_infos = Vec::with_capacity(limit as usize);
        let mut chunk_start_version = start;
        let executor = AptosVMBlockExecutor::new();
        for item in txn_iter {
            // timeout check
            if let Some(duration) = self.timeout_secs {
                if self.replay_stat.get_elapsed_secs() >= duration {
                    bail!(
                        "Verify timeout: {}s elapsed. Deadline: {}s. Failed txns count: {}",
                        self.replay_stat.get_elapsed_secs(),
                        duration,
                        total_failed_txns.len(),
                    );
                }
            }

            let (
                input_txn,
                persisted_aux_info,
                expected_txn_info,
                expected_event,
                expected_writeset,
            ) = item?;
            let is_epoch_ending = expected_event.iter().any(ContractEvent::is_new_epoch_event);
            cur_txns.push(input_txn);
            cur_persisted_aux_info.push(persisted_aux_info);
            expected_txn_infos.push(expected_txn_info);
            expected_events.push(expected_event);
            expected_writesets.push(expected_writeset);
            if is_epoch_ending || cur_txns.len() >= self.chunk_size {
                let cnt = cur_txns.len();
                while !cur_txns.is_empty() {
                    // verify results
                    let failed_txn_opt = self.execute_and_verify(
                        &executor,
                        &mut chunk_start_version,
                        &mut cur_txns,
                        &mut cur_persisted_aux_info,
                        &mut expected_txn_infos,
                        &mut expected_events,
                        &mut expected_writesets,
                    )?;
                    // collect failed transactions
                    total_failed_txns.extend(failed_txn_opt);
                }
                self.replay_stat.update_cnt(cnt as u64);
                self.replay_stat.print_tps();
            }
        }
        // verify results
        let fail_txns = self.execute_and_verify(
            &executor,
            &mut chunk_start_version,
            &mut cur_txns,
            &mut cur_persisted_aux_info,
            &mut expected_txn_infos,
            &mut expected_events,
            &mut expected_writesets,
        )?;
        total_failed_txns.extend(fail_txns);
        Ok(total_failed_txns)
    }
