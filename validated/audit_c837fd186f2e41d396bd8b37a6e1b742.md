## Title
Permissionless `RescueFundsOnSourceChain` event lets any attacker hijack a victim's stuck-fund recovery, locking their `UniversalTx` into an attacker-controlled `RESCUE_FUNDS` outbound - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
The Folio bug is a state-manipulation DoS: anyone can front-run a legitimate operation with a call that locks internal filler state (`swapActive()`), and every subsequent `sync()`-gated function (mint/redeem/fees/param updates) reverts until the attacker's fake state is cleared. The Push Chain analog is in the "stuck fund rescue" pipeline of `x/uexecutor`: `AttachRescueOutboundFromReceipt` accepts a `RescueFundsOnSourceChain` EVM log from **any** Push Chain transaction and, without checking that the caller/`event.Sender` is the original inbound sender or recipient, attaches a `RESCUE_FUNDS` outbound populated with attacker-supplied `GasFee`/`GasPrice`/`GasLimit` to the victim's `UniversalTx`. Because a duplicate-rescue guard rejects any further rescue attempts while one is `PENDING`/`OBSERVED`, an unprivileged attacker can repeatedly seize this slot ahead of the legitimate owner, similar to how the Folio attacker seizes `swapActive()` ahead of legitimate `sync()` callers.

### Finding Description
`EVMHooks.PostTxProcessing` runs on **every** EVM transaction and unconditionally calls `AttachRescueOutboundFromReceipt` for any log emitted by the `UNIVERSAL_GATEWAY_PC` system contract matching the `RescueFundsOnSourceChain` signature [1](#0-0) .

Inside `AttachRescueOutboundFromReceipt`, the eligibility check only inspects the *target* `UniversalTx`'s own state (CEA deposit `FAILED`, or a `REVERTED` `INBOUND_REVERT` outbound) — it never checks that the transaction's sender or `event.Sender` corresponds to the original inbound's `Sender`/`RevertInstructions.FundRecipient` [2](#0-1) . Any address can therefore construct a Push Chain transaction that emits this event for an arbitrary victim's `universalTxId`, as long as that UTX is already in a rescuable state.

The resulting outbound is built directly from attacker-controlled event fields (`GasFee`, `GasPrice`, `GasLimit`, `Sender`), while `Recipient`/`Amount` are pulled from the original UTX [3](#0-2) .

A duplicate-rescue guard then blocks any further `AttachRescueOutboundFromReceipt` calls for that UTX while the attacker's outbound is `PENDING` or `OBSERVED`, only permitting a retry once it becomes `REVERTED` [4](#0-3) . This mirrors the Folio pattern: an unprivileged party seizes a single-slot "active operation" state via a permissionless entry point, blocking the legitimate flow until it is externally resolved — except here resolution requires an honest-validator TSS/outbound vote cycle rather than being permanently stuck.

### Impact Explanation
An attacker can:
1. Front-run the legitimate victim's own rescue attempt by submitting the `rescueFunds` call first with attacker-chosen `GasFee`/`GasPrice`/`GasLimit`, locking in the `RESCUE_FUNDS` outbound slot for that UTX.
2. Repeat this every time the outbound resolves to `REVERTED`, indefinitely delaying the rightful owner's ability to recover their own stuck funds (denial of service on the recovery path, reachable by an ordinary unprivileged user transaction).
3. Because `GasFee`/`GasPrice`/`GasLimit` are attacker-supplied and used to construct the actual signed outbound transaction to the source chain, a maliciously chosen value can cause the rescue transaction to be malformed or economically unfavorable for the fee-paying side, wasting a TSS/voting cycle and prolonging recovery of user funds each time.

This falls under "permanent freezing" / denial-of-service in the universal execution / outbound flow reachable by an ordinary unprivileged user, matching the allowed-impact gate.

### Likelihood Explanation
Medium: the attacker needs no special privilege — only the ability to identify a UTX with a `FAILED` CEA deposit or `REVERTED` auto-revert (both are on-chain, queryable states) and to submit an ordinary Push Chain transaction invoking the gateway's rescue path with that `universalTxId`. No validator collusion or key compromise is required.

### Recommendation
- Bind the rescue authorization to the original UTX: require `event.Sender` (or the transaction's `msg.sender`) to match `originalUtx.InboundTx.Sender` or `RevertInstructions.FundRecipient` before attaching a `RESCUE_FUNDS` outbound in `AttachRescueOutboundFromReceipt`.
- Alternatively/also, do not allow arbitrary third-party-controlled `GasFee`/`GasPrice`/`GasLimit` values to be used verbatim; validate/clamp them against protocol-computed values (e.g., via `getRescueFundsGasLimit`) instead of trusting the emitted event.
- Consider allowing the legitimate owner to override/cancel an unauthorized pending rescue outbound rather than only allowing progression via `PENDING → OBSERVED/REVERTED`.

### Proof of Concept
1. Victim's inbound UTX ends up with a `FAILED` CEA deposit (or a `REVERTED` `INBOUND_REVERT`), making it eligible for rescue per `create_outbound.go:239-262`.
2. Attacker (any account, no relationship to the victim) submits a Push Chain transaction calling the `UNIVERSAL_GATEWAY_PC` contract's rescue entry point with the victim's `universalTxId`, but with attacker-chosen `gasFee`/`gasPrice`/`gasLimit`.
3. `EVMHooks.PostTxProcessing` → `AttachRescueOutboundFromReceipt` decodes the log and attaches a `RESCUE_FUNDS` outbound (`OutboundStatus: PENDING`) to the victim's UTX, using the attacker's gas parameters, per `create_outbound.go:295-320`.
4. When the legitimate victim later submits their own correctly-parameterized rescue call, it is rejected with `"already has an active rescue outbound"` (`create_outbound.go:269-282`) until the attacker's outbound resolves through the honest validator vote cycle.
5. Attacker repeats step 2 immediately after each resolution to `REVERTED`, perpetuating the denial of the victim's legitimate, correctly-parameterized rescue.
