**Rationale:** `TokenOfferEvent` in `types/src/account_config/events/token_offer_event.rs` is a plain data struct with only `Debug, Deserialize, Serialize` derives and no `PartialEq`/`Eq` [1](#0-0) . However, the exploit hypothesis requires a downstream "caching or deduplication layer keyed by decoded struct rather than raw bytes/hash" feeding into "proof-verification" — no such component exists in this codebase for this event type.

Event proof binding in Aptos works by hashing raw `ContractEvent` bytes into the event accumulator, and the `event_root_hash` in `TransactionInfo` is verified against that raw-byte hash tree, not against any decoded/deserialized struct equality check [2](#0-1) . `TokenOfferEvent::try_from_bytes` simply performs `bcs::from_bytes` deserialization for use inside the `token_transfers` module's Move-event translation logic, and its only known caller path is `storage/indexer/src/event_v2_translator.rs`'s `OfferTranslator`, which re-serializes the decoded fields into a `TokenOfferEvent`-based `ContractEventV1` for the indexer, not for any proof-verification cache [3](#0-2) . There is no evidence in the codebase of a decoded-struct-keyed cache sitting between event decoding and `event_root_hash` proof verification — the only cache present in this file is `event_sequence_number_cache`, which is a `DashMap<EventKey, u64>` for sequence numbering, unrelated to struct equality or proof binding [4](#0-3) .

Since the described "downstream proof-verification cache keyed by decoded struct" does not exist in this codebase, the scenario is speculative and not traceable to any actual authenticated-response or proof-binding code path. Per the review rules, this must be rejected as it does not demonstrate that unprivileged input can corrupt committed state, corrupt proof material, or misbind an authenticated response through code that actually exists.
