## Analysis

Found a valid analog in `MarketSellAssetActuator`'s order-matching logic, where a rounding-to-zero calculation is explicitly checked in one code path but is missing on the symmetric path — mirroring the Primitive Finance bug where one `getAmounts` scaling was left unguarded.

### Title
Rounding-to-zero in market order matching lets a maker's residual sell quantity be silently destroyed without paying the taker - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes cross-order fill quantities using integer division via `MarketUtils.multiplyAndDivide`, which floors results to zero for small ratios [1](#0-0) . The "taker > maker" branch explicitly guards against a zero result by returning the maker's leftover tokens when `makerBuyTokenQuantityReceive == 0` [2](#0-1) , but the "taker == maker" branch performs the identical computation without any zero-check before consuming the maker's entire remaining balance [3](#0-2) .

### Finding Description
In `matchSingleOrder`, `makerBuyTokenQuantityReceive` is derived from `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which performs `floorDiv(a*b, c)` and can legitimately return 0 when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` [1](#0-0) .

- In the "taker > maker" branch (lines 453–483), the code checks `if (makerBuyTokenQuantityReceive == 0)` and, if so, returns the maker's sell remainder rather than silently zeroing it out, with an explicit comment acknowledging this is an intentional guard against the rounding edge case [2](#0-1) .
- In the "taker == maker" branch (lines 418–439), the exact same `multiplyAndDivide` computation is used for `makerBuyTokenQuantityReceive`, but there is **no check for a zero result**. The code unconditionally sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` and marks the maker order `INACTIVE`, then calls `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` with `makerBuyTokenQuantityReceive == 0` [3](#0-2) .

This means when the maker's remaining sell quantity, multiplied by the maker's buy/sell ratio, floors to zero (a scenario the comment at line 469-474 explicitly discusses as a known edge case for the "makerSellQuantity < makerBuyQuantity" ratio), the maker's entire remaining sell-side asset balance is wiped from the order book and closed out as `INACTIVE`, while the maker receives 0 of the buy-side token in return. The taker's counterpart credit (`takerBuyTokenQuantityReceive`) is set to the full `makerOrderCapsule.getSellTokenQuantityRemain()` and correctly credited, so the taker still profits, but the maker's assets are effectively destroyed/uncompensated — a direct violation of the balance/accounting invariant that closing an order at 0 received quantity should never happen (the exact invariant the sibling branch protects).

### Impact Explanation
Any user who places a maker sell order (`MarketSellAssetContract`) with parameters such that a taker's `sellTokenQuantityRemain` exactly equals the maker's outstanding `sellTokenQuantityRemain` (the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` condition, i.e., "taker == maker" branch) and where `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` can have their remaining maker order tokens consumed with zero payout. This is an on-chain asset/accounting corruption reachable by any account broadcasting ordinary `MarketSellAssetContract` transactions (a TRC-10 decentralized exchange feature), with no privileged role required.

### Likelihood Explanation
Reachability requires crafting two orders (a maker and a taker) with token quantities chosen so the ratio computation rounds to zero on the "taker == maker" equality path. This is entirely achievable by any unprivileged actor controlling both a maker and taker order (e.g., self-trading, or waiting for a victim maker order with matching remainder), since `MarketSellAssetContract` amounts and token pairs are fully attacker-controlled and the DEX-matching logic runs deterministically in `execute()` for every `MarketSellAssetContract` transaction once `supportAllowMarketTransaction` is enabled [4](#0-3) .

### Recommendation
Add the same zero-value guard used in the "taker > maker" branch to the "taker == maker" branch: check `makerBuyTokenQuantityReceive == 0` before closing out the maker order, and if zero, return the maker's remaining sell tokens (`MarketUtils.returnSellTokenRemain`) instead of discarding them, consistent with the existing mitigation pattern at lines 466-477.

### Proof of Concept
1. Create a maker sell order with `sellTokenQuantity` and `buyTokenQuantity` such that a later partial fill leaves `makerSellRemainQuantity` small relative to `makerSellQuantity`/`makerBuyQuantity` (e.g., `makerSellQuantity=200`, `makerBuyQuantity=100`, and after prior matches `makerSellRemainQuantity=1`, giving `multiplyAndDivide(1, 100, 200) = 0`).
2. Submit a taker `MarketSellAssetContract` order whose `sellTokenQuantityRemain` equals the maker's current `getSellTokenQuantityRemain()` (1), forcing the "taker == maker" branch (line 418) rather than "taker > maker" (line 453).
3. Observe: `makerBuyTokenQuantityReceive` computes to 0 via `MarketUtils.multiplyAndDivide`, but the code proceeds to zero out `makerOrderCapsule.setSellTokenQuantityRemain(0)`, mark it `INACTIVE`, and call `addTrxOrToken(makerOrderCapsule, 0)` — crediting the maker with 0 tokens while their remaining sell-side balance is permanently removed from the order book, unlike the explicitly-guarded "taker > maker" path.
