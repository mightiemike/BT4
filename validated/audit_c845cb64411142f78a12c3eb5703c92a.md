## Finding: Fund Migration Signing Verification Desyncs on Attacker-Sent Funds to the Old TSS Address — DoS on Migration Completion

### Title
Unprivileged native-token deposit to the old TSS address desynchronizes independently-computed fund-migration signing hashes, causing honest Universal Validators to reject the migration signing request (DoS) - ([File: universalClient/chains/evm/tx_builder.go], [File: universalClient/tss/sessionmanager/sessionmanager.go])

### Summary
The external report describes a class of bug where an attacker inflates a balance the protocol relies on for an exact-match/close-out check by sending tokens directly to an account the protocol doesn't fully control, causing a desync between the protocol's internally recorded amount and the actual on-chain balance, which then breaks an invariant check and results in denial of service. Push Chain's TSS fund migration flow contains a native analog: the transfer amount signed by the coordinator, and independently re-derived by each verifying Universal Validator, is computed from a **freshly queried on-chain balance** of the old TSS address rather than from a value fixed/pinned at protocol-level. An unprivileged external actor can send native tokens to the (publicly known) old TSS address between the coordinator's signing-hash computation and a validator's independent re-verification, causing the two computed values (and thus signing hashes) to diverge.

### Finding Description
Fund migration builds a native-token sweep transaction whose amount is `balance - gasCost - l1Fee`, where `balance` is queried live from the external chain when not explicitly supplied: [1](#0-0) 

The code's own comment states the load-bearing assumption: *"Fund migration only triggers when outbound is disabled and no pending outbounds remain, so the balance at signing time will equal the balance at broadcast time."* This assumption only covers protocol-driven balance changes (pending outbounds); it does not account for an **unprivileged external actor directly depositing funds to the old TSS address**, which is a public, known EVM address once a `KEYGEN` process has occurred.

The coordinator computes the signing request once (querying balance fresh, `claimedAmount=nil`) to build the DKLS setup message: [2](#0-1) 

Each participating Universal Validator then **independently re-derives** the same signing request to verify it before agreeing to sign, again with no pinned balance (so it re-queries the chain fresh): [3](#0-2) 

If the old TSS address's balance changes between the coordinator's query and a validator's independent query — trivially achievable by anyone sending even 1 wei/lamport-equivalent to that public address — the two independently recomputed `SigningHash` / `TSSFundMigrationAmount` values diverge, and the validator rejects the signing request: [4](#0-3) 

This mirrors the structure of the reported bug class precisely: an internally expected value (the amount baked into the coordinator's signing hash) is compared against a freshly-observed on-chain quantity (the validator's independently-queried balance), and an unprivileged party can desynchronize the two by directly interacting with an account the protocol depends on for an exact-match check.

### Impact Explanation
This is an unprivileged, no-cost-to-attacker DoS on the TSS fund-migration signing process (in scope per "TSS coordination" and the explicit allowance for "denial of service only when it is not network-level and is reachable without privileged control"). Because the nonce for a migration event is assigned once via `assignFundMigrateNonce` and the fund migration record stays `PENDING` until a `MsgVoteFundMigration` finalizes it, a validator's rejection of the signing request prevents that signing round from completing, blocking migration of externally-locked funds from the old TSS key to the new one after a `KEYGEN`. An attacker who repeats the deposit on every retry attempt can perpetually keep the migration from finalizing at negligible cost (a single dust-value native-token transfer per attempt), leaving protocol-controlled funds effectively stuck under the old (rotated-out) TSS key.

### Likelihood Explanation
Likelihood is high in terms of accessibility: the old TSS address is public once a keygen rotation is announced/observed, and depositing a small amount of native currency to it requires no special access, no validator/relayer compromise, and only ordinary external-chain interaction — squarely an "unprivileged external attacker" per the scope. The race window (between coordinator hash computation and validator verification) is bounded but repeatable indefinitely by the attacker for as long as fund migration is pending.

### Recommendation
Do not re-query "live" balance independently at verification time. Have the coordinator pin the balance (or the derived `maxTransfer`) that funds the signing hash into the on-chain `FundMigrationInitiatedEventData` (or an equivalent canonical, chain-tallied source), and have verifying validators use that pinned value (the `claimedAmount` reconstruction path already exists for the ACK-verify case and should be the default, not an exception) instead of independently re-querying a mutable external balance for the initial verification path.

### Proof of Concept
1. Admin initiates a `KEYGEN` TSS process; the old TSS address `oldTSSAddr` becomes publicly known via the `FundMigrationInitiatedEventData`.
2. `x/utss` creates a pending `FundMigration` for `oldTSSAddr` on some external chain; the coordinator queries `oldTSSAddr`'s balance `B0` and computes `maxTransfer0 = B0 - gasCost - l1Fee`, embedding it into the DKLS signing hash sent to session participants.
3. Before the other Universal Validators independently verify the request, an attacker (any unprivileged external account) sends a small amount of native currency to `oldTSSAddr`, changing its balance to `B1 = B0 + delta`.
4. A verifying validator calls `verifyFundMigrationSigningRequest`, which re-queries `oldTSSAddr`'s balance (now `B1`) and computes `maxTransfer1 = B1 - gasCost - l1Fee ≠ maxTransfer0`, producing a different `SigningHash`.
5. The comparison in `sessionmanager.go` fails ("fund migration signing hash mismatch"), the validator refuses to participate in the DKLS signing session, and the migration cannot reach the threshold of cooperating signers, blocking completion of the fund migration for as long as the attacker repeats the deposit on each retry.

```go
// GetFundMigrationSigningRequest builds a native token transfer for fund migration,
// transferring the maximum possible balance (balance minus gas cost minus L1 fee).
// Fund migration only triggers when outbound is disabled and no pending outbounds remain,
// so the balance at signing time will equal the balance at broadcast time.
// L1GasFee covers OP-stack sequencer data-availability charges; 0 for non-L2 chains.
func (tb *TxBuilder) GetFundMigrationSigningRequest(ctx context.Context, data *common.FundMigrationData, nonce uint64) (*common.UnsignedSigningReq, error) {
	fromAddr := ethcommon.HexToAddress(data.From)
	toAddr := ethcommon.HexToAddress(data.To)

	if data.GasPrice == nil || data.GasPrice.Sign() == 0 {
		return nil, fmt.Errorf("gas price must be provided for fund migration")
	}
	if data.GasLimit == 0 {
		return nil, fmt.Errorf("gas limit must be provided for fund migration")
	}

	var balance *big.Int
	if data.Balance != nil {
		balance = new(big.Int).Set(data.Balance)
	} else {
		queried, err := tb.rpcClient.GetBalance(ctx, fromAddr)
		if err != nil {
			return nil, fmt.Errorf("failed to get balance of %s: %w", data.From, err)
		}
		balance = queried
	}
```

```go
// buildFundMigrationTransaction parses event data and returns the signing
// request for sweeping old-TSS funds to the current TSS. If claimedAmount is
// non-nil, the balance is reconstructed as amount + gas + L1 instead of
// queried from chain — used by the ACK verify path to rebuild the hash
// deterministically without racing a successful sweep.
func (c *Coordinator) buildFundMigrationTransaction(ctx context.Context, eventData []byte, assignedNonce *uint64, claimedAmount *big.Int) (*common.UnsignedSigningReq, error) {
	if assignedNonce == nil {
		return nil, fmt.Errorf("assigned nonce is required for fund migration transaction")
	}
	var migrationData utsstypes.FundMigrationInitiatedEventData
	if err := json.Unmarshal(eventData, &migrationData); err != nil {
		return nil, fmt.Errorf("unmarshal fund migration event data: %w", err)
	}
	oldTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.OldTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive old TSS address: %w", err)
	}
	currentTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.CurrentTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive current TSS address: %w", err)
	}
	if c.chains == nil {
		return nil, fmt.Errorf("chains manager not configured")
	}
	client, err := c.chains.GetClient(migrationData.Chain)
	if err != nil {
		return nil, fmt.Errorf("get client for chain %s: %w", migrationData.Chain, err)
	}
	builder, err := client.GetTxBuilder()
	if err != nil {
		return nil, fmt.Errorf("get tx builder for chain %s: %w", migrationData.Chain, err)
	}

	gasPrice := new(big.Int)
	gasPrice.SetString(migrationData.GasPrice, 10)
	l1GasFee := new(big.Int)
	l1GasFee.SetString(migrationData.L1GasFee, 10)

	var balance *big.Int
	if claimedAmount != nil {
		// balance = amount + gas + L1; inverse of computeFundMigrationTransfer
		balance = new(big.Int).Set(claimedAmount)
		balance.Add(balance, new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(migrationData.GasLimit)))
		if l1GasFee.Sign() > 0 {
			balance.Add(balance, l1GasFee)
		}
	}

	return builder.GetFundMigrationSigningRequest(ctx, &common.FundMigrationData{
		From:     oldTSSAddr,
		To:       currentTSSAddr,
		GasPrice: gasPrice,
		GasLimit: migrationData.GasLimit,
		L1GasFee: l1GasFee,
		Balance:  balance,
	}, *assignedNonce)
```
