### Title
Stale/out-of-window signer votes can finalize a reward-cycle's aggregate public key with no time-bound check - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
The `.signers-voting` contract defines a helper `is-in-voting-window` that is meant to restrict aggregate-public-key voting to the current reward cycle's prepare phase, but this helper is never invoked by the public entry point `vote-for-aggregate-public-key`. This mirrors the AuraVestedEscrow class of bug: an action that is supposed to be bounded to a specific time window has no enforcement of that window, so it can be "vested"/finalized after the window's intended end.

### Finding Description
`is-in-voting-window` is defined at [1](#0-0)  and is intended to gate voting to the case where `(last-cycle == reward-cycle)` and the current burn height is within the prepare phase.

However, the public function `vote-for-aggregate-public-key` never calls this helper. Its full set of guards is limited to: the key not yet being approved for the target `reward-cycle`, key length, novelty of the key across cycles, no double-voting by the same signer/round, and monotonic round increments [2](#0-1) . None of these checks constrain *when* (relative to the reward cycle's prepare phase / `last-set-cycle`) the vote is cast.

`get-signer-weight` derives the caller's weight from `(contract-call? .signers get-signer-by-index reward-cycle signer-index)` [3](#0-2) , and the `.signers` contract's `get-signers`/`get-signer-by-index` return data for *any* previously-set reward cycle, not only the "current" one [4](#0-3) . Because `vote-for-aggregate-public-key` only checks `(is-none (map-get? aggregate-public-keys reward-cycle))` (i.e., that the cycle's key slot is still empty) and never checks that `reward-cycle` is still the currently-votable cycle, a signer who was part of an already-past reward cycle's signer set can still cast a valid, weighted vote for that reward cycle's aggregate key well after the intended voting window has closed — as long as no key has been finalized for it yet.

This breaks the intended equality: "the aggregate-public-key for reward-cycle N is fixed and known before N begins, by all nodes uniformly." Instead, the key for N can be set asynchronously and late, after nodes have already begun operating under the assumption that N has no (or a different) approved key.

### Impact Explanation
If the aggregate key for a reward cycle is finalized late via a stale vote, nodes that already treated `get-approved-aggregate-key` as `none` for that cycle (and proceeded with whatever fallback/consensus behavior applies) will diverge from nodes that observe the late finalization. This is a minority-triggerable (single or few signers with cumulative weight ≥ `threshold-consensus`, not necessarily a network majority) static-validation divergence over which key should be used to verify signer aggregate signatures for that reward cycle — i.e., a "validation verdict two nodes disagree on" per the accepted High-severity impact class, potentially causing a temporary tip disagreement among nodes/signers.

### Likelihood Explanation
No privileged access is required — any signer that was part of a signer set for a past reward cycle whose aggregate key slot is still empty can call `vote-for-aggregate-public-key` outside the prepare-phase window. The only barrier (`is-none` on the map slot) is trivially satisfiable whenever the legitimate voting round never reached consensus in-window. This is directly triggerable by an unprivileged signer without collusion of a majority.

### Recommendation
Add the missing guard in `vote-for-aggregate-public-key`, e.g.:
```clarity
(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))
```
using the already-defined `ERR_OUT_OF_VOTING_WINDOW` constant [5](#0-4) , so that votes (and thus aggregate-key finalization) are strictly bounded to the reward cycle's active voting window, matching the helper's evident original intent.

### Proof of Concept
1. Reward cycle `N`'s prepare phase begins; `.signers` sets the signer set for cycle `N` (`last-set-cycle = N`).
2. Voting proceeds but does not reach `threshold-consensus` before the prepare phase ends and `last-set-cycle` advances past `N` (e.g., to `N+1`).
3. `(map-get? aggregate-public-keys N)` is still `none`.
4. A signer who held weight in cycle `N`'s signer set calls `vote-for-aggregate-public-key` with `reward-cycle = N` at a much later burn height (well outside `is-in-voting-window`). Because `vote-for-aggregate-public-key` never checks `is-in-voting-window`, the call succeeds, tallies the vote, and — if their (cached) weight meets `threshold-consensus` for cycle `N` — finalizes `aggregate-public-keys[N]` long after cycle `N`'s window and possibly after cycle `N` itself have already passed, when other nodes/signers have already moved on assuming no key was set.
