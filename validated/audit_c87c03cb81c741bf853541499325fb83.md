### Title
Stale `WantedTenure.processed` flag survives Nakamoto-tip fork switches because reorg detection only checks the burnchain (sortition) tip, not the Stacks tip - ([File: stackslib/src/net/download/nakamoto/download_state_machine.rs])

### Summary
`inner_update_processed_wanted_tenures` sets `wt.processed = true` when `NakamotoChainState::has_processed_nakamoto_tenure(chainstate.index_conn(), stacks_tip, ...)` returns true for the node's *current* `self.nakamoto_tip`. Because the "processed" check is memoized (`if wt.processed { continue; }`) and the only invalidation path (`initialize_wanted_tenures`'s reorg check) is keyed off `PeerNetwork::is_reorg(self.last_sort_tip, sort_tip, sortdb)` — a **burnchain/sortition-tip** comparison — a Stacks-level (Nakamoto) fork switch that does not change the sortition tip never clears stale `processed=true` flags.

### Finding Description
The equality the download state machine relies on is: `wt.processed == true` should imply "this tenure's blocks are present on the eventual canonical Stacks chain." `inner_update_processed_wanted_tenures` (download_state_machine.rs:315-345) evaluates this using `chainstate.index_conn()` scoped by the *current* `stacks_tip` argument (`self.nakamoto_tip`, used at lines 362 and 370) [1](#0-0) . `has_processed_nakamoto_tenure` walks the MARF ancestor path from `stacks_tip`, so its answer is fork-relative: it can return `true` while the node's `nakamoto_tip` sits on a locally-adopted but non-canonical Nakamoto fork (e.g., during a transient period where two conflicting Stacks blocks/tenure-extensions exist for the same burn view, before signer/miner convergence settles on one).

Once `wt.processed` is set `true`, the loop short-circuits (`if wt.processed { continue; }`), so the flag is never re-evaluated against a later, different `stacks_tip` — unless the enclosing wanted-tenures list is entirely rebuilt. That rebuild only happens in `initialize_wanted_tenures` when `PeerNetwork::is_reorg(self.last_sort_tip.as_ref(), sort_tip, sortdb)` fires, which compares **sortition/burnchain tips**, not Nakamoto block tips [2](#0-1) . Therefore a Stacks-level fork switch within the same burn view (the losing branch abandoned in favor of a different, canonical Nakamoto fork) is invisible to this guard, and the stale `processed=true` persists.

### Impact Explanation
A node that briefly tracked a non-canonical Nakamoto tip can permanently mark a tenure as "processed" even though the blocks needed for the canonical fork of that tenure were never downloaded/applied. The download-scheduling logic will then skip re-fetching that tenure's data, so the node stalls and never converges to the canonical tip without an unrelated trigger (e.g., a later sortition-level reorg) to force a `wanted_tenures` reset. This matches the "temporary tip disagreement" / convergence-stall category (High), not a chain split, since the affected node's chainstate itself isn't corrupted — it just fails to catch up.

### Likelihood Explanation
This requires only a transient two-Stacks-fork condition within a single burn view (e.g., a miner/tenure equivocation, or normal contention between tenure-extend and next-tenure blocks), which is achievable by a single miner slot without majority stake or signer control, and can arise without any Bitcoin-level reorg. It requires no majority stake or admin access, matching the unprivileged-attacker model.

Note: I could not fully verify all code paths that update `self.nakamoto_tip` across a single burn view (i.e., how quickly/whether it flips before the "canonical" fork is picked), nor exhaustively confirm `PeerNetwork::is_reorg`'s full body, due to tool-call budget limits. The finding is grounded in the reorg check's parameters (`sort_tip`/`last_sort_tip`, sortition-level) versus the tip actually used for the processed check (`self.nakamoto_tip`, Stacks-level), which are clearly different values in the code I read.

### Recommendation
Invalidate/re-verify `wanted_tenure.processed` whenever `self.nakamoto_tip` changes to a tip that is not a descendant of the previously-used tip (i.e., detect Nakamoto-level forks, not just sortition-level reorgs), or simply never memoize `processed=true` as permanently un-reverifiable — instead re-check `has_processed_nakamoto_tenure` against the current tip each cycle for tenures near the tip, only skipping the check once the tenure is buried behind enough confirmations that a fork switch is no longer possible.

### Proof of Concept
Rust integration test plan (two-fork harness):
1. Set up two Nakamoto forks `fork_a` and `fork_b` sharing the same burn view/sortition, where `fork_a` fully includes tenure `T` and `fork_b` does not (or includes a different set of `T`'s blocks).
2. Set `self.nakamoto_tip = fork_a_tip` and call `inner_update_processed_wanted_tenures`; assert `wt.processed == true` for `T`.
3. Switch the node's canonical tip to `fork_b_tip` (simulating fork-b eventually winning, without a sortition-level reorg — same `sort_tip`).
4. Call `PeerNetwork::is_reorg` with the same `sort_tip`/`last_sort_tip` and assert it returns `false` (no rebuild triggered).
5. Assert `wt.processed` remains `true` even though `has_processed_nakamoto_tenure(chainstate.index_conn(), fork_b_tip, T)` would return `false` — this is the DETERMINISM assertion failing: `wt.processed != has_processed_nakamoto_tenure(..., fork_b_tip, ...)`.
6. Confirm the download state machine subsequently never schedules a re-download of `T`'s blocks needed for `fork_b`, stalling convergence.

    pub(crate) fn inner_update_processed_wanted_tenures(

        wanted_tenures: &mut [WantedTenure],

        stacks_tip: &StacksBlockId,
    ) -> Result<(), NetError> {
        for wt in wanted_tenures.iter_mut() {
            debug!(
                "update_processed_wanted_tenures: consider {:?} off of {}",
                &wt, stacks_tip
            );
            if wt.processed {
                continue;
            }
            if wt.burn_height < nakamoto_start {
                // not our problem
                wt.processed = true;
                continue;
            }
            if NakamotoChainState::has_processed_nakamoto_tenure(
                &mut chainstate.index_conn(),
                stacks_tip,
                &wt.tenure_id_consensus_hash,
            )? {
                debug!("Tenure {} is now processed", &wt.tenure_id_consensus_hash);
                wt.processed = true;
                continue;
            }
        }
        Ok(())
    }
