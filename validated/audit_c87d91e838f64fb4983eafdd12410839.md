Based on my investigation, I found a genuine, self-documented state-integrity gap in the transaction replay verification logic, distinct from the `ensure_transaction_infos_match` path (which does correctly compare full `TransactionInfo` objects including `state_checkpoint_hash`).

### Title
Chunk-replay verification skips state/hot-state/position checkpoint hash comparison, allowing divergent state roots to pass as "verified" - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by the chunk-executor's `verify_execution` path and by the `db-tool replay_on_archive` verification tool to confirm that locally re-executed transactions match the ground-truth (proof-authenticated) `TransactionInfo` — checks status, gas, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 
`ensure_match_transaction_info` verifies `status`, `gas_used`, write-set hash (`state_change_hash`), and `event_root_hash`, but the comment at line 2197-2202 explicitly states this comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", meaning replay-verify tooling can report success even when the authenticated state root diverges from local execution.

This function is used in two integrity-sensitive call sites:
1. `ChunkExecutorInner::verify_execution` in the chunk executor, invoked during transaction chunk replay verification (e.g., backup restore's `VerifyExecutionMode`). [2](#0-1) 
2. `execute_and_verify` in the `db-tool`'s `replay_on_archive`, used to audit archived transaction data against re-execution. [3](#0-2) 

By contrast, the separate `LedgerUpdateOutput::ensure_transaction_infos_match` path (used by `ChunkResultVerifier` for consensus/state-sync chunk verification) compares complete `TransactionInfo` structs, which do include the checkpoint-hash fields, and thus correctly binds committed state to the authenticated ledger. [4](#0-3) 

### Impact Explanation
`state_checkpoint_hash` is the root of the global JMT state after a transaction/checkpoint; the write-set hash alone does not guarantee that the entire derived state tree (including any state not directly captured in the emitted write set, e.g. native/position-tracked state referenced in the code comments) is identical. If local re-execution during replay/backup-verify diverges from the archived, ledger-committed state root — due to a bug, non-determinism, or ledger corruption — the checks performed via `ensure_match_transaction_info` would not catch it, and `replay_on_archive`/backup-restore-verify tooling would falsely report a clean replay. This undermines the fundamental trust guarantee of replay-verify tooling (which operators and auditors rely on to detect state divergence in archived history) and, per the code's own TODO, is explicitly called out as unsafe to leave unresolved before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Likelihood Explanation
This is not attacker-triggerable to produce direct fund loss on mainnet by itself, since the transaction infos consumed in these paths are already accumulator-proof-authenticated (`LoadedChunk::load` verifies `TransactionInfoListWithProof` against a trusted `LedgerInfoWithSignatures` before this comparator ever runs). [5](#0-4)  The gap only matters if local re-execution legitimately diverges (bug, hardware fault, or targeted manipulation of a node's own execution path) from the already-committed ledger — in which case the verification gate that is supposed to detect such divergence silently passes. The code comment itself flags this as a known, currently-open gap gated behind an unlaunched feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), so today's practical severity is limited mainly to the general `state_checkpoint_hash`/`hot_state_checkpoint_hash` omission for standard state, not just the position-tracking feature.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionInfo` variant) against the recomputed checkpoint hashes from the corresponding `StateCheckpointOutput`, before it is safe to treat replay-verify or `db-tool replay_on_archive` results as an authoritative attestation of state correctness — as the code's own TODO already recommends.

### Proof of Concept
Not applicable as a live exploit — this is a logic/verification-completeness gap identified directly in the source (see the explicit TODO comment at types/src/transaction/mod.rs:2197-2202), not a demonstrated live state corruption. I could not fully trace whether any currently-enabled mainnet code path relies solely on `ensure_match_transaction_info` (without the stronger `ensure_transaction_infos_match` check) as its only integrity gate for consensus-committed data; the two call sites found (`chunk_executor::verify_execution` and `db-tool::replay_on_archive`) both operate on backup/audit tooling rather than the live consensus-commit hot path, so I cannot claim confirmed high/critical mainnet impact — only a verified integrity gap in replay/audit verification.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
