## Title
Deleting an account leaves dangling `PromiseYield`/postponed-receipt state that is dereferenced (and can be resumed) after the account is later re-created — analogous to CVE-2026-39316's dangling-subscription UAF - (File: `core/store/src/utils/mod.rs`, function `remove_account`)

## Summary
`cupsdDeleteTemporaryPrinters` deletes a printer without first expiring the `cupsd_subscription_t` records that still reference it, leaving a dangling pointer that gets dereferenced later. NEAR's `DeleteAccount` action has the same structural flaw: it frees the "account" object but never expires the account-scoped auxiliary state that references it — specifically `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`, `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, and `ReceivedData` trie entries keyed by that same `account_id`.

## Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) computes storage usage, refunds the balance, and calls `remove_account`: [1](#0-0) 

`remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, all `AccessKey`/`GasKeyNonce` entries, and `ContractData`: [2](#0-1) [3](#0-2) 

It never touches the other account-scoped columns declared in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (`core/primitives/src/trie_key.rs:89-102`) — `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, `DATA_ID_TO_YIELD_ID`: [4](#0-3) 

A `PromiseYield` receipt is stored keyed purely by `(receiver_id, data_id)` with no per-incarnation nonce (`lib.rs:1549-1553`, `set_promise_yield_receipt`): [5](#0-4) 

and its corresponding `PromiseYieldTimeout` queue entry is only removed from the trie when the timeout fires or a real resume arrives (`lib.rs:1568-1616`, `lib.rs:3113-3208`, `resolve_promise_yield_timeouts`): [6](#0-5) [7](#0-6) 

None of this cleanup path is triggered by `DeleteAccount`. Since NEAR permits re-creating an account with the same `account_id` after it has been deleted (account creation only checks the `Account` trie entry, not these auxiliary columns), a deleted-then-recreated account inherits any stale `PromiseYieldReceipt`/`PromiseYieldStatus`/`PostponedReceipt`/`ReceivedData` rows left by the prior incarnation. A subsequent `PromiseResume` (real or timeout-triggered) for the same `data_id` will find `get_promise_yield_receipt` still returning the **old** parked receipt (`lib.rs:1568-1616`) and execute it via `apply_action_receipt` against the *new* incarnation's account/state — because the receiver_id and predecessor_id in the stale receipt are the account_id itself (self-call), the resumed actions run with self/full-access semantics against the new account's live balance.

## Impact Explanation
This is a state-consistency bug reachable purely from unprivileged transactions:
1. An attacker sets up a `promise_yield_create` on their own account (creating `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout`/`PromiseYieldIndices` entries) with a payload of self-directed actions of their choosing.
2. The attacker deletes the account (`DeleteAccount`), which — per the above — leaves those entries in the trie untouched.
3. Anyone (attacker or a new owner) re-creates an account with the same `account_id` and funds it.
4. The dangling `PromiseYield` either times out (`resolve_promise_yield_timeouts` still finds `contains_key(&promise_yield_key)` true and synthesizes a `PromiseResume`) or is resumed by a crafted `PromiseResume` with the matching `data_id`, causing the stale, attacker-controlled action receipt to execute against the new account's funds/state.

This can result in unauthorized value movement or unexpected state mutation on the re-created account, and produces state that is inconsistent with what an honest re-implementation of the spec would expect (permanently orphaned/duplicated trie entries persisting across account lifetimes) — matching the "concrete unauthorized value movement / invalid state transition acceptance" bar. It is also a self-inflicted storage-usage/state-bloat issue since these entries are never charged storage rent to anyone after the account is deleted, though the more serious concern is the cross-incarnation receipt execution described above.

## Likelihood Explanation
Medium. It requires no validator/network privilege — an ordinary contract-calling account can trigger `promise_yield_create` then `DeleteAccount` themselves, and account_id re-use after deletion is an explicitly supported NEAR feature. The harder part is getting a party to re-fund/reuse the exact same `account_id` (feasible for sub-accounts the attacker controls, e.g. `foo.attacker.near`, which the attacker can freely delete and recreate under their own control, or convincing/waiting for someone else to claim a vacated top-level name). The existence of dedicated resharding tests explicitly checking for "dangling trie value" bugs around `PromiseYieldIndices` (`test-loop-tests/src/tests/resharding_v3.rs:1917-1940`) shows the team is aware this class of dangling-reference bug exists in this subsystem, but that awareness is about resharding boundaries, not about `DeleteAccount` cleanup specifically: [8](#0-7) 

## Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), before/while deleting the account, also enumerate and remove all account-scoped auxiliary trie entries for that `account_id`: `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`. Additionally, any outstanding `PromiseYieldTimeout`/`PromiseYieldIndices` queue entries referencing the deleted account should be invalidated so `resolve_promise_yield_timeouts` cannot resurrect a resume receipt for an account that no longer exists (or existed as a different incarnation). This mirrors the CUPS fix of expiring dependent subscriptions before freeing the object they reference.

## Proof of Concept
Conceptual sequence (exact wasm-level driver would need to be written and validated in a test-loop environment, which was not runnable here):
1. Deploy a contract to account `A` with `call_yield_create_return_promise`-style method; call it so a `PromiseYield` receipt + `PromiseYieldTimeout` queue entry are stored for `A`/`data_id`, with a resume payload (actions) chosen by the attacker (e.g., a `Transfer` back to attacker or a privileged self action).
2. In the same or a following block, submit a `DeleteAccount` action from `A` to itself/beneficiary — confirm via state inspection that `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, and the `PromiseYieldTimeout` queue entry for `A` still exist in the trie after the account row is gone (this matches the existing test helper `assert_no_promise_yield_status_in_state` used elsewhere, which would need to be checked and shown to fail here).
3. Re-create account `A` (e.g., another `CreateAccount` action for the same `account_id`, or wait for someone else to claim it) and fund it.
4. Either let the timeout height pass (`resolve_promise_yield_timeouts` will still find the stale `PromiseYieldReceipt` and emit a `PromiseResume`) or directly send a `PromiseResume` receipt with the original `data_id` — observe that `apply_action_receipt` executes the original, attacker-chosen action set against the *new* account `A`'s balance/state.

Note: this PoC was reasoned from static code paths (`action_delete_account`, `remove_account`, `set_promise_yield_receipt`/`get_promise_yield_receipt`, `resolve_promise_yield_timeouts`) and the account-scoped `TrieKey` column list; it was not executed against a live test-loop node, so the exact recreate-account preconditions (e.g., whether the runtime permits immediate re-creation of a just-deleted account within the same epoch, or requires waiting) should be confirmed by a Devin session with test execution before treating this as a fully validated exploit.
