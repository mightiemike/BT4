### Title
Precision loss (divide-before-multiply) in bandwidth/energy resource-limit calculation can grant users inflated free resource limits - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`, `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

### Summary
The Numoen report identifies that `Pair.invariant()` divides before multiplying (`FullMath.mulDiv(amount, 1e18, liquidity) * scale`), causing rounding/precision loss that lets an attacker manipulate reserves without tripping the invariant check. The same *divide-before-multiply* pattern, using floating-point `double` arithmetic (which is strictly worse than integer division since it also introduces binary floating-point rounding), exists in java-tron's legacy resource-limit formulas that convert a user's frozen TRX balance into a bandwidth/energy quota.

### Finding Description
`EnergyProcessor.calculateGlobalEnergyLimit` and `calculateGlobalEnergyLimitV2`, and the structurally identical `BandwidthProcessor.calculateGlobalNetLimit` / `calculateGlobalNetLimitV2`, compute a user's resource limit from `frozeBalance`, `totalLimit`, and `totalWeight`. When the `hardenCalculation()` flag (`dynamicPropertiesStore.allowHardenResourceCalculation()`) is not enabled, the code takes the legacy path: [1](#0-0) [2](#0-1) 

This is exactly the flagged anti-pattern from the report: `totalEnergyLimit / totalEnergyWeight` is computed and truncated/rounded *first* (here even worse, in double-precision floating point), and only afterwards multiplied by `energyWeight`. The correct order (multiply first, then divide, as the report recommends and as the codebase's own hardened path does) is implemented in the same files behind the `hardenCalculation()` flag using `BigInteger` multiply-then-divide: [3](#0-2) 

The project's own test suite explicitly demonstrates the precision divergence between the legacy (buggy) and hardened formulas, confirming the root cause and its measurable impact: [4](#0-3) 

The identical mulDiv precision-loss pattern also appears in the read-only `RepositoryImpl.calculateGlobalEnergyLimit` / `usageToBalance` (TVM repository layer) with the same non-hardened legacy `double` fallback: [5](#0-4) [6](#0-5) 

### Impact Explanation
`calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` directly gate `useEnergy`/`useAccountNet`, i.e., how much free bandwidth/energy an unprivileged account can consume before being charged TRX: [7](#0-6) 

Because the legacy formula divides `totalLimit/totalWeight` before multiplying by the caller's own `energyWeight`, and does so in `double` (53-bit mantissa) rather than exact integer arithmetic, the computed limit can systematically round in the user's favor for certain combinations of frozen balance / network-wide totals (which are attacker-observable on-chain state). An account whose derived limit is inflated even by a small integer amount can execute additional free smart-contract calls (energy) or free transactions (bandwidth) beyond what its stake entitles it to — i.e., underpriced/free consumption of network computation and storage resources, a direct resource-accounting integrity issue, analogous to "anyone can call `swap()` to withdraw the excess value" in the original report. Every account performing a transaction is unprivileged and can trigger this path, since it is the default/legacy computation used whenever the hardening proposal has not been (or is not yet) activated on the network.

### Likelihood Explanation
This code executes on every single transaction that consumes bandwidth or energy (i.e., essentially all traffic on the network) whenever `allowHardenResourceCalculation` is `0`. The values `totalEnergyLimit`, `totalEnergyWeight`, `totalNetLimit`, `totalNetWeight` are public chain parameters, and `frozeBalance` is fully controlled by the account (via TRX freezing), so an attacker can iterate/select combinations that maximize the rounding benefit deterministically off-chain before submitting the freeze transaction — no privileged role or race condition is required. This is a systemic, reproducible determinism issue rather than a rare edge case, and the project's own hardening effort (feature-flagged fix with dedicated parity tests) confirms the team already recognizes the formula as defective; the risk persists for as long as the flag remains disabled on any given network deployment.

### Recommendation
- Ensure `allowHardenResourceCalculation` (and the equivalent VM/`RepositoryImpl` hardening flag) is enabled/activated by default going forward, and treat the legacy double-based formulas as deprecated, since they are provably lossy.
- Replace all remaining "divide-then-multiply" or floating-point resource-limit formulas with exact integer math using multiply-first-then-divide via `BigInteger` (matching `calculateGlobalLimitV1`/`V2` and `SafeExchangeProcessor`), across `EnergyProcessor`, `BandwidthProcessor`, and `RepositoryImpl`.
- Audit all other locations still guarded by `disableJavaLangMath()`/`hardenCalculation()`-style toggles for the same class of bug, and once validated, retire the legacy path entirely rather than keeping it reachable via governance toggle.

### Proof of Concept
Using the project's own parity test as the demonstrating PoC (it directly instantiates the vulnerable non-hardened formula and shows a different, favorable result versus the exact `BigInteger` computation):

```java
// framework/src/test/java/org/tron/core/vm/repository/RepositoryImplHardenTest.java:228-257
long totalEnergyLimit = 50_000_000_000L;
long totalEnergyWeight = 1_234_567L;
long frozeBalance = 10_000_000_000L; // energyWeight = 10000

VMConfig.initAllowHardenResourceCalculation(0);
long resultOld = repository.calculateGlobalEnergyLimit(account); // legacy divide-then-multiply (double)

long expected = BigInteger.valueOf(10000L)
    .multiply(BigInteger.valueOf(totalEnergyLimit))
    .divide(BigInteger.valueOf(totalEnergyWeight))
    .longValueExact(); // correct multiply-then-divide

long buggy = 10000L * (totalEnergyLimit / totalEnergyWeight); // divide-first, exact int form of the flaw
Assert.assertNotEquals(buggy, expected); // demonstrates divergence caused by dividing before multiplying
```
This confirms that for realistic on-chain parameter values, the legacy `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` formulas (used whenever hardening is not enabled) yield a resource limit that diverges from the mathematically correct value — the exact bug class described in the Numoen `invariant()` report, applied to java-tron's resource accounting instead of an AMM invariant.

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
