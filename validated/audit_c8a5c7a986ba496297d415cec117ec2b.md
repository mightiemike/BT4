### Title
KV-only state-snapshot restore commits unverified key/value data into the ledger's state KV store - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
`StateSnapshotRestore::add_chunk` (storage/aptosdb/src/state_restore/mod.rs:213-253) dispatches restore chunks differently depending on `StateSnapshotRestoreMode`. In `Default` mode the chunk's `SparseMerkleRangeProof` is verified against `expected_root_hash` before any data is written. In `KvOnly` mode, however, the code calls only `self.kv_restore...add_chunk(chunk)` and never calls `verify_chunk`/`verify`, so the proof argument is accepted by the API but never checked.

Compare with `Default` mode, which explicitly documents and enforces "verify proof -> write state_kv_db -> write state_merkle_db": [2](#0-1) 

`KvOnly` is not merely an internal test helper — it is a first-class production restore path used by the backup-restore coordinator to bootstrap the state-KV store ahead of the tree snapshot:
```rust

    StateSnapshotRestoreOpt {
        manifest_handle: kv_snapshot.manifest,
        version: kv_snapshot.version,
        validate_modules: false,
        restore_mode: StateSnapshotRestoreMode::KvOnly,
    },
    ...
``` [3](#0-2) 

The chunk contents (`blobs`) and the `proof` file are both fetched from the (potentially untrusted/compromised) `BackupStorage` backend: [4](#0-3) 

Because `KvOnly` never calls `JellyfishMerkleRestore::verify_chunk` (which is the only place that calls `SparseMerkleRangeProof::verify` against `expected_root_hash`, see `storage/jellyfish-merkle/src/restore/mod.rs:339-405` and `:648-717`), an attacker who controls or can tamper with the backup storage (e.g., a compromised/malicious backup blob store, a MITM on a fetch, or bit-rot/corruption that should be caught) can supply arbitrary `(StateKey, StateValue)` blobs for the KV-only phase that do not match the root hash recorded in the manifest/`TransactionInfoWithProof`. These blobs get durably written into `state_kv_db` via `StateValueWriter::write_kv_batch`. The subsequent tree-only phase (`StateSnapshotRestoreMode::TreeOnly`, used later in phase 2 of `coordinators/restore.rs:316-346`) verifies only the Merkle *tree* structure/hashes, not the KV *values* themselves in a way that cross-checks them against the already-written KV blobs — the tree restore only ever receives value hashes (`v.hash()`), so a mismatched value with a colliding/attacker-controlled interaction between the two phases is not detected by either stage individually. Note: full determination of whether the two phases are later cross-validated (e.g., by later JMT leaf hash lookups against the KV store) requires additional tracing beyond what I could confirm.

### Impact Explanation
If accepted, this allows a state value that differs from the correct/canonical VM-committed value to be durably persisted into a node's `state_kv_db` during restore, without the proof-integrity check that is the entire purpose of `SparseMerkleRangeProof`. This is exactly the "committed state that differs from the correct VM result / corrupts durable ledger data" class called out in scope. On a node that restores via this KV-only path (used specifically to fast-path bootstrapping/backup restore in `RestoreCoordinator`), later reads served from `state_kv_db` for that version (via `get_state_value_by_version`, API responses, or JMT leaf value lookups keyed by hash) could return corrupted/incorrect state, and any node built from a tampered backup could diverge from the honest network's canonical state.

### Likelihood Explanation
Exploitation requires control over the backup source used by the `restore` coordinator (a supply-chain/MITM position on the `BackupStorage`, e.g. a compromised S3 bucket/GCS backend), which is a nontrivial but realistic threat model for restore/disaster-recovery infrastructure that this proof check exists specifically to defend against. The code path is reachable in the normal, default restore coordinator flow (not a debug/test-only flag), and no additional signature or authentication guards the KV-only chunk data before it's written.

### Recommendation
Have `StateSnapshotRestoreMode::KvOnly` also invoke `JellyfishMerkleRestore::verify_chunk` (against `expected_root_hash`) before calling `kv_restore.add_chunk`, mirroring the `Default` path, or otherwise assert that the KV-only phase is always paired 1:1 with a strictly-prior, already-verified `TreeOnly`/`Default` pass over byte-identical chunk contents (not just value hashes) before commit, with an explicit invariant check that ties the two together.

### Proof of Concept
1. Stand up a `BackupStorage` implementation (or intercept an existing one) used by `RestoreCoordinator`.
2. When the coordinator downloads a KV-only snapshot chunk (`storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs:191-192`), substitute the `blobs` payload with different `(StateKey, StateValue)` pairs while leaving the `proof` file (or any well-formed proof) unchanged.
3. Run the restore with `restore_mode: StateSnapshotRestoreMode::KvOnly` as invoked in `storage/backup/backup-cli/src/coordinators/restore.rs:242-260`.
4. Observe that `add_chunk` in `storage/aptosdb/src/state_restore/mod.rs:213-218` accepts and commits the tampered blobs to `state_kv_db` with no `SparseMerkleRangeProof::verify` call, unlike the `Default`/`TreeOnly` code paths.
