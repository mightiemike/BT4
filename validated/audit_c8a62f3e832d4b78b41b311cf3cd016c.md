**Rationale:**

`SubBlock::start_index` is only consumed for two purposes in the codebase: (1) building local cross-shard dependency edges within the partitioner state machine, and (2) converting a local execution-thread index back to a "global" index inside `CrossShardCommitSender::on_transaction_committed` (`txn_idx + self.index_offset`) purely to route cross-shard write notifications during execution. [1](#0-0) 

The value that actually determines where a `TransactionInfo` gets committed in storage is not `start_index` at all. `assemble_transaction_infos` builds transaction infos by iterating `0..to_commit.len()` over the already-flattened, execution-ordered `TransactionsWithOutput`, and `commit_transaction_infos`/`commit_transaction_accumulator` write each info at `first_version + i`, where `i` is simply the positional index in that final ordered vector. [2](#0-1) [3](#0-2) 

That ordered vector is reconstructed by `SubBlocksForShard::flatten`/`PartitionedTransactions::flatten`, which determines canonical transaction order strictly from `(round_id, shard_id)` position in a matrix and `sub_block.into_txns()` vector order — it never reads or trusts the `start_index` field to place transactions. [4](#0-3) 

So even a hypothetical partitioner bug that produced an inconsistent `start_index` on a `SubBlock` would, at worst, corrupt cross-shard dependency routing during the (optional, currently non-mainnet-critical) sharded execution path, potentially causing wrong execution results detectable by every validator running identical deterministic partitioning code on the same consensus-ordered block. It would not cause the executor-to-storage handoff to record `TransactionInfo` at the wrong ledger `Version`, because that handoff is keyed off positional index in the flattened, execution-ordered array, not off the partitioner-supplied `start_index`. There is no unprivileged-input path (transaction, dependency structure, etc.) that can independently manipulate `start_index` without equally affecting the deterministic partitioning that all validators perform identically, so this does not meet the bar of unprivileged input corrupting authenticated state or proof binding.

    // Flattens a vector of `SubBlocksForShard` into a vector of transactions in the order they
    // appear in the block.
    pub fn flatten(block: Vec<SubBlocksForShard<T>>) -> Vec<T> {
        let num_shards = block.len();
        let mut flattened_txns = Vec::new();
        let num_rounds = block[0].num_sub_blocks();
        let mut ordered_blocks = vec![SubBlock::empty(); num_shards * num_rounds];
        for (shard_id, sub_blocks) in block.into_iter().enumerate() {
            for (round, sub_block) in sub_blocks.into_sub_blocks().into_iter().enumerate() {
                ordered_blocks[round * num_shards + shard_id] = sub_block;
            }
        }

        for sub_block in ordered_blocks.into_iter() {
            flattened_txns.extend(sub_block.into_txns());
        }

        flattened_txns
    }
