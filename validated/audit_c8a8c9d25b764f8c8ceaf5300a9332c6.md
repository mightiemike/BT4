### Title
Precision-loss from division-before-multiplication in resource-usage transfer calculation - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.execute()` computes the bandwidth/energy usage to be transferred back to the delegator using raw `double` arithmetic that divides first and multiplies second, instead of multiplying first and dividing last (or using the `BigInteger`-based "hardened" pattern that the rest of the resource-accounting code in this repo already adopted for the exact same ratio computation).

### Finding Description
In `execute()`, for both `BANDWIDTH` and `ENERGY` branches, the amount of usage to migrate from the receiver back to the owner is computed as: [1](#0-0) 

```
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
```

and analogously for `ENERGY`: [2](#0-1) 

Both expressions perform a `divide → divide → multiply` sequence (`unDelegateBalance / TRX_PRECISION`, then `totalNetLimit / totalNetWeight`, then the product) in floating point instead of computing the numerator products first and dividing once at the end. This is exactly the anti-pattern the codebase itself has already identified and fixed elsewhere via a "hardened" `BigInteger` path — e.g. `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` and `ResourceProcessor.calculateGlobalLimitV1`/`calculateGlobalLimitV2`, which explicitly multiply first with `BigInteger` and divide only once at the end to avoid the same class of precision loss: [3](#0-2) [4](#0-3) 

The repo's own regression tests demonstrate that at large frozen-balance magnitudes (close to `2^53`, i.e. TRX-supply scale), the double-based divide-then-multiply formula diverges from the exact rational (`BigInteger`) result: [5](#0-4) 

`UnDelegateResourceActuator` was not updated to reuse these hardened helpers; it re-implements the vulnerable divide-before-multiply formula inline for computing `unDelegateMaxUsage` and `transferUsage`.

### Impact Explanation
`UnDelegateResourceContract` is a public, unprivileged-user transaction (any account that delegated bandwidth/energy can call it). The miscalculated `transferUsage`/`unDelegateMaxUsage` directly changes how much bandwidth/energy usage bookkeeping is moved from the receiver's account to the owner's account on undelegation: [6](#0-5) [7](#0-6) 

Because these usage values feed into `receiverCapsule.setNetUsage(...)` / `setEnergyUsage(...)` and `processor.unDelegateIncrease(...)`, precision loss in the ratio computation causes divergent bandwidth/energy accounting between the exact/expected value and the actually persisted state — an invalid-state/accounting divergence affecting consensus-relevant account resource fields, at the scale where TRON's largest frozen balances (tens of billions of TRX in sun, i.e. up to ~1e17) approach or exceed the `2^53` double-precision integer limit that the project's own hardening tests target.

### Likelihood Explanation
Any account can trigger `UnDelegateResourceContract`; no privileged role is required. The precision-loss magnitude scales with `unDelegateBalance`, `getTotalNetLimit()`/`getTotalNetWeight()` (or the energy equivalents) and `getAllFrozenBalanceForBandwidth()/Energy()` — all of which are large, network-wide/global values that legitimately reach the multi-trillion-sun range in production, making triggering non-trivial precision error plausible without any adversarial setup, though the actual usage-unit deltas produced are generally small relative to total limits.

### Recommendation
Replace the two-step `divide, divide, multiply` double formula with a single-division `BigInteger` (or equivalent multiply-first) computation, consistent with the pattern already used in `BandwidthProcessor.calculateGlobalNetLimit`/`V2` and `ResourceProcessor.calculateGlobalLimitV1`/`V2`:
```java
long unDelegateMaxUsage = BigInteger.valueOf(unDelegateBalance)
    .multiply(BigInteger.valueOf(dynamicStore.getTotalNetLimit()))
    .divide(BigInteger.valueOf(TRX_PRECISION)
        .multiply(BigInteger.valueOf(dynamicStore.getTotalNetWeight())))
    .longValueExact();
```
and analogously for `transferUsage` and the `ENERGY` branch, gating the change behind the existing `hardenCalculation`/fork-activation mechanism used elsewhere for consistency with historical chain state.

### Proof of Concept
1. Freeze/delegate bandwidth such that `receiverCapsule.getAllFrozenBalanceForBandwidth()`, `dynamicStore.getTotalNetLimit()`, and `dynamicStore.getTotalNetWeight()` are set to large values (e.g. in the range used by `CalculateGlobalLimitHardenTest`, `~9.8e15`, close to `2^53`).
2. Submit an `UnDelegateResourceContract` for a `unDelegateBalance` chosen so that the exact rational result of `unDelegateBalance * totalNetLimit / (TRX_PRECISION * totalNetWeight)` differs from `(double) unDelegateBalance / TRX_PRECISION * ((double) totalNetLimit / totalNetWeight)` when both are cast to `long`.
3. Compare the persisted `receiverCapsule`/`ownerCapsule` net/energy usage after `execute()` against the value computed via `BigInteger` multiply-then-divide (as done in `CalculateGlobalLimitHardenTest.testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss`) — the values will diverge, confirming the round-off from the divide-before-multiply ordering.

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }

  public long calculateGlobalNetLimitV2(long frozeBalance) {
    long totalNetLimit = dynamicPropertiesStore.getTotalNetLimit();
    long totalNetWeight = dynamicPropertiesStore.getTotalNetWeight();
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV2(frozeBalance, totalNetLimit, totalNetWeight);
    }
    double netWeight = (double) frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
