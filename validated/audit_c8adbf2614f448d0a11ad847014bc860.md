### Title
Sender can front-run and invalidate a relayer's meta-transaction by racing the shared access-key nonce, causing `DelegateActionInvalidNonce` and irrecoverable relayer fee loss - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's meta-transaction (NEP-366) design lets a relayer pay gas/fees for a `SignedDelegateAction` authored and nonce-committed by another account ("the sender"). The sender can submit any other transaction that consumes the same access key before the relayer's transaction executes, advancing the on-chain nonce. When the relayer's transaction then executes, `validate_delegate_action_key` rejects it with `DelegateActionInvalidNonce`, but the relayer has already irrevocably burnt the transaction's send fees and part of the delegate action's exec fee, exactly mirroring the GMX report's pattern where the order owner front-runs the keeper's execution to invalidate a state precondition (`updatedAtBlock`) and cause the keeper to lose its fee.

### Finding Description
A `DelegateAction` embeds a `nonce` that must be strictly greater than the current access-key nonce stored on chain, and `validate_delegate_action_key` both checks and advances that nonce at execution time: [1](#0-0) [2](#0-1) 

This is the same "plain nonce" access key row used by ordinary transactions signed with the same key — i.e. `TransactionNonce::Nonce` shares state with regular transaction nonce verification, so *any* other transaction signed with that key (unrelated to the meta-transaction) advances the same counter: [3](#0-2) 

The relayer wraps the user's `SignedDelegateAction` in its own transaction and pays for it; the transaction's send fees and signature-verification cost are burnt on the relayer's shard at conversion time, unconditionally of whether the inner delegate action later succeeds: [4](#0-3)  The design doc explicitly acknowledges the shared-nonce race as a known but unmitigated risk in the MVP: "a meta transaction sent by Bob may invalidate a meta transaction signed by Alice... nothing along those lines has been approved" — but this framing only covers *another relayer-submitted meta-tx* colliding; it does not call out that the sender/owner of the access key itself can deliberately front-run and invalidate their own outstanding delegate action to grief a relayer, which is the direct structural analog of the GMX report (owner front-runs the pending action to flip a validity precondition and burn the executor's paid fee). [5](#0-4) 

Concretely:
1. Sender signs a `DelegateAction` with `nonce = N+1` and hands it to a relayer.
2. Relayer wraps it in a transaction and broadcasts it, paying send/signature fees.
3. Before the relayer's transaction is included, sender (front-running, e.g. seeing the pending tx in the mempool, or simply submitting concurrently) submits a normal transaction with any action using the same access key, causing on-chain nonce to become `N+1` already (or higher).
4. When the relayer's transaction executes, `delegate_nonce.nonce() <= current_nonce` is true, so `validate_delegate_action_key` returns `DelegateActionInvalidNonce` and the entire delegate/inner-action fails: [2](#0-1) 
5. Because the action failed, the relayer is only refunded *unused* prepaid gas/deposit; the already-burnt send fees, signature verification cost, and the exec fee consumed up to the point of failure are gone (burnt to validators), and the sender pays nothing for having invalidated the relayer's paid-for transaction. [6](#0-5) 

### Impact Explanation
A malicious sender can repeatedly grief any relayer offering a general-purpose meta-transaction service: sign a `DelegateAction`, hand it to the relayer, then immediately consume the same access key nonce via a self-transaction before the relayer's transaction lands, causing the relayer to pay gas/fees for a transaction that is guaranteed to fail. This is a reachable, unauthorized value loss for an unprivileged actor (the relayer) triggered purely by the sender's own transaction — no validator or network-level compromise required. Repeated abuse can drain a relayer's operating balance with no compensating benefit to the network.

### Likelihood Explanation
Medium-High: the sender only needs control of their own access key (which they inherently have) and the ability to submit a competing transaction before the relayer's transaction is applied — a normal front-running/race condition achievable by any sender against any relayer, requiring no special privileges. The docs already flag the shared-nonce collision as an open design gap, showing the underlying mechanism is real and currently unmitigated, though the doc doesn't call out this specific hostile-sender variant.

### Recommendation
Consider decoupling delegate-action nonce validation from the sender's regular transaction nonce (e.g. a dedicated meta-transaction nonce/sequence space, or gas-key-style per-purpose nonce rows as already partially exists for gas keys), so that ordinary sender activity cannot unilaterally invalidate an outstanding, relayer-funded `DelegateAction` without cost to the sender. Alternatively, require relayers to reserve/lock the nonce atomically with acceptance of the `SignedDelegateAction`, or charge the sender (not just the relayer) for invalidating a delegate action via a same-key race.

### Proof of Concept
Using the existing test harness pattern for delegate-action nonce validation, construct: (1) a `DelegateAction` with `nonce = current+1` handed to a relayer per `meta_tx` helper: [7](#0-6) ; (2) before executing the relayer's wrapping transaction, have the sender submit and apply an ordinary transaction using the same access key (any action) so the on-chain nonce advances to `current+1`; (3) apply the relayer's transaction and observe `ActionErrorKind::DelegateActionInvalidNonce` as demonstrated by the existing unit test for this exact failure mode: [8](#0-7) ; (4) confirm via `refund_unspent_gas_and_deposits` that only *unused* gas is refunded — the already-burnt send/verification fees are not recovered by the relayer: [6](#0-5) .

    fn refund_unspent_gas_and_deposits(
        &self,
        gas_burn_price: Balance,
        gas_purchase_price: Balance,
        receipt: &Receipt,
        action_receipt: &VersionedActionReceipt,
        result: &mut ActionReceiptResult,
        config: &RuntimeConfig,
        created_account: bool,
        protocol_version: ProtocolVersion,
    ) -> Result<GasRefundResult, RuntimeError> {
        let total_deposit = total_deposit(&action_receipt.actions())?;
        let prepaid_gas = total_prepaid_gas(&action_receipt.actions())?
            .checked_add(total_prepaid_send_fees(config, &action_receipt.actions())?.gas)
            .ok_or(IntegerOverflowError)?;
        let prepaid_exec_gas =
            total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
                .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee())
                .ok_or(IntegerOverflowError)?;
        let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
        let gross_gas_refund = if result.result.is_err() {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_burnt)
                .unwrap()
        } else {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_used)
                .unwrap()
        };

        // NEP-536 also adds a penalty to gas refund.
        let refund_penalty: Gas = config.fees.gas_penalty_for_gas_refund(gross_gas_refund);
        let penalty_gas_price = if ProtocolFeature::AccountCostIncrease.enabled(protocol_version) {
            gas_burn_price
        } else {
            gas_purchase_price
        };
        let refund_penalty_amount = safe_gas_to_balance(penalty_gas_price, refund_penalty)?;

        // Refund for the leftover gas that was not used by this receipt.
        let unused_gas_balance_refund = safe_gas_to_balance(gas_purchase_price, gross_gas_refund)?
            .saturating_sub(refund_penalty_amount);
