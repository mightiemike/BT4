Tracing the actual restore path: version binding for events is derived deterministically from the manifest's `first_version` plus the transaction's index within the restored chunk, not from any user-controlled or replayable event field [2](#0-1) . Events are written keyed by `(Version, index)` via `put_events_multiple_versions`, and later read back with `get_events_by_version` using that same version key [3](#0-2) .

Any authenticated consumer (e.g. `get_transaction_with_proof`) binds the returned events and the `TransactionInfoWithProof` to the same explicit `version` parameter, and `TransactionWithProof::verify` cryptographically checks that the event root hash computed from the returned events matches `event_root_hash()` in the transaction info covered by the accumulator proof at that exact version [4](#0-3) [5](#0-4) . There is no mechanism by which replaying an old transaction or supplying unprivileged input could cause the restore or read path to reassign these events to a different version — doing so would break the event-root-hash/accumulator-proof verification rather than silently succeed.

    /// Returns all of the events for a given transaction version.
    pub(crate) fn get_events_by_version(&self, version: Version) -> Result<Vec<ContractEvent>> {
        let mut events = vec![];

        let mut iter = self.db.iter::<EventSchema>()?;
        // Grab the first event and then iterate until we get all events for this version.
        iter.seek(&version)?;
        while let Some(((ver, _index), event)) = iter.next().transpose()? {
            if ver != version {
                break;
            }
            events.push(event);
        }

        Ok(events)
    }
