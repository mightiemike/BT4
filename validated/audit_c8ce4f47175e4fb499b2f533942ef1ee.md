### Title
Congestion control MVP does not account for gas or memory of PromiseYield/postponed receipts, allowing an unprivileged contract caller to bypass shard backpressure and grow unbounded, un-throttled per-account state - (`runtime/runtime/src/congestion_control.rs`)

### Summary
NEAR's congestion-control system (NEP-539) is the direct analog of the Linux netback RX-queue backpressure mechanism referenced in CVE-2021-28714/28715: it is supposed to bound the memory used by unprocessed/buffered receipts by tracking `delayed_receipts_gas`, `buffered_receipts_gas`, and `receipt_bytes` and reducing/rejecting further work once thresholds are hit. However, `compute_receipt_congestion_gas` explicitly assigns **zero** congestion gas to `Data`, `PromiseYield`, `PromiseResume`, and `GlobalContractDistribution` receipts, and the persisted `CongestionInfo.receipt_bytes`/gas accounting is only ever updated for the **delayed queue** and **outgoing buffers** — not for postponed action receipts (`TrieKey::PostponedReceipt`/`PendingDataCount`) or parked `PromiseYield` receipts sitting in state waiting for `promise_yield_resume`/timeout. This mirrors the CVE's root cause: a designed backpressure/timeout mechanism that can be systematically bypassed by a specific receipt/packet shape, letting an unprivileged caller accumulate large amounts of un-throttled state.

### Finding Description
`compute_receipt_congestion_gas` (`runtime/runtime/src/congestion_control.rs:678-714`) is the canonical cost function feeding `CongestionInfo`: [1](#0-0) 

For `PromiseYield` receipts it returns `Gas::ZERO` with the comment that the MVP "does not account for yielding a promise" because yields "never cross the shard boundaries" and are therefore "irrelevant for the congestion MVP, which only counts gas in the outgoing buffers and delayed receipts queue." The same is true for `Data` and `PromiseResume` receipts.

Crucially, `bootstrap_congestion_info` (`runtime/runtime/src/congestion_control.rs:743-789`) — the function that (re)builds `CongestionInfo.receipt_bytes` — only iterates the `DelayedReceiptQueue` and `ShardsOutgoingReceiptBuffer`: [2](#0-1) 

It never visits `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, the promise-yield receipt storage, or the `PromiseYieldTimeout` queue. Because a contract's own `FunctionCall` receipt is executed as a **local receipt** (not "incoming"/"delayed"), and the resulting `PromiseYield` receipt is processed and parked immediately (`ext.rs:356-372`, `set_promise_yield_status`), an attacker's yield receipts never pass through the delayed-queue/outgoing-buffer admission path that is protected by congestion control at all — they are simply written into state (`PostponedReceipt`/`PendingDataCount`-style entries plus a `PromiseYieldTimeout` queue entry) and wait for either an explicit `promise_yield_resume` or a timeout after `yield_timeout_length_in_blocks` blocks.

The only gate on creating a yield receipt is the ordinary per-transaction gas fee (`yield_create_base`, `yield_create_byte`, `pay_gas_for_new_receipt`) charged inside `promise_yield_create`/`promise_yield_create_with_id` (`runtime/near-vm-runner/src/wasmtime_runner/logic.rs:4113-4195`, `:4198-4303`). This bounds how many yields one *chunk* can create (bounded by the chunk gas limit), but nothing bounds the **cumulative** number of yields parked in state across many chunks over the `yield_timeout_length_in_blocks` window — and none of that accumulated state counts toward `CongestionInfo.receipt_bytes`/`delayed_receipts_gas`/`buffered_receipts_gas`, so `shard_accepts_transactions` / `reject_tx_congestion_threshold` never trips because of it.

This is the structural analog of CVE-2021-28714: Xen's netback driver had a stall-timeout meant to bound buffered guest traffic, but a guest could arrange the RX ring so the timeout's triggering condition (a full ring) never fires (e.g. one free slot when the next packet needs more), letting buffered data grow unbounded despite the "protection" being present. Here, congestion control's stated purpose is identical ("stops accepting new work when the queues get too large" — `runtime/runtime/AGENTS.md:56`), but the specific receipt kinds used for cross-contract "yield/resume" workflows are hard-coded to contribute zero cost to every congestion metric, so the mechanism structurally cannot see or throttle this kind of load. [3](#0-2) 

### Impact Explanation
An unprivileged contract deployer/caller can repeatedly invoke a contract method that calls `promise_yield_create` (or `promise_yield_create_with_id`) across many chunks, each call parking a receipt + timeout-queue entry in the receiver account's trie subtree for up to `yield_timeout_length_in_blocks` blocks without ever being resumed. Because this workload is invisible to `CongestionInfo`, it never triggers `shard_accepts_transactions`'s rejection threshold, never reduces `outgoing_gas_limit`, and is not reflected in the "red light" full-congestion protections that are supposed to cap validator memory/storage growth. The result is unthrottled growth of per-shard state (trie size, and when the timeout queue eventually drains, a burst of `PromiseResume` receipts and postponed-state cleanups that also don't count toward congestion), increasing validator resource consumption/storage-proof size independent of the congestion-control safety valve that all other receipt-producing workloads are subject to. This is a state-growth / congestion-bypass class issue rather than fund theft, but it defeats a security control explicitly designed to prevent validators being overwhelmed by attacker-controlled cross-shard/cross-account workload — directly analogous to the CVE's "guest can force host to hog large amounts of kernel memory" impact translated to "signer can force validators to hog large amounts of state/memory that the congestion-control accounting cannot see."

### Likelihood Explanation
Any unprivileged account holder that can deploy a contract (or call an existing contract using `promise_yield_create`) can trigger this at will, using only standard `FunctionCall` transactions and gas they pay for themselves — no special privileges, validator status, or network-level positioning required. The behavior (`Gas::ZERO` congestion cost for `PromiseYield`/`PromiseResume`/`Data`) is explicit and permanent in the code, not a race condition, so the exploit is fully deterministic and repeatable every block within the standard gas budget.

### Recommendation
Extend `CongestionInfo` accounting (or a parallel size/gas metric enforced during transaction/receipt admission) to include postponed action receipts and parked `PromiseYield` receipts, or otherwise impose a protocol-level cap on the number/aggregate size of outstanding yields per account/shard so that this workload contributes to `shard_accepts_transactions` and the other congestion signals the same way delayed/buffered receipts do.

### Proof of Concept
1. Deploy a contract exposing a method that calls `promise_yield_create` in a loop (as already exercised by the estimator contract's `yield_create_base`/`yield_create_with_id_base` functions, which create 1000 yields per call: `runtime/near-test-contracts/estimator-contract/src/lib.rs:2175-2205`). [4](#0-3) 
2. Submit repeated `FunctionCall` transactions invoking this method across many consecutive blocks, well within the per-chunk gas limit, and never call `promise_yield_resume` for any of them.
3. Observe that `CongestionInfo.delayed_receipts_gas`, `buffered_receipts_gas`, and `receipt_bytes` (as computed by `compute_receipt_congestion_gas`/`bootstrap_congestion_info`) remain unaffected by this workload, and `shard_accepts_transactions`/`reject_tx_congestion_threshold` never trigger due to it, while the shard's trie accumulates postponed/yield state that only unwinds after `yield_timeout_length_in_blocks` blocks — demonstrating the congestion-control backpressure is fully bypassed for this receipt class.

        VersionedReceiptEnum::Action(action_receipt) => {

            action_receipt_congestion_gas(receipt, config, action_receipt.into())

        VersionedReceiptEnum::Data(_data_receipt) => {
            // Data receipts themselves don't cost gas to execute, their cost is
            // burnt at creation. What we should count, is the gas of the
            // postponed action receipt. But looking that up would require
            // reading the postponed receipt from the trie.
            // Thus, the congestion control MVP does not account for data
            // receipts or postponed receipts.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseYield(_) => {
            // The congestion control MVP does not account for yielding a
            // promise. Yielded promises are confined to a single account, hence
            // they never cross the shard boundaries. This makes it irrelevant
            // for the congestion MVP, which only counts gas in the outgoing
            // buffers and delayed receipts queue.
            Ok(Gas::ZERO)
        }

            // The congestion control MVP does not account for resuming a promise.
            // Unlike `PromiseYield`, it is possible that a promise-resume ends
            // up in the delayed receipts queue.
            // But similar to a data receipt, it would be difficult to find the cost
            // of it without expensive state lookups.
            Ok(Gas::ZERO)
        }

Congestion control keeps track of the size of receipt queues on all shards and stops accepting new work when the queues get too large.

Yield/Resume is a feature which allows to `yield` and create a new receipt with an unsatisfied data dependency. Later another transaction can call `resume` with some payload to satisfy the data dependency, continuing execution of the yielded receipt. If the receipt is not resumed in time, it will time out and the yielded receipt will be executed with a timeout (None payload).
