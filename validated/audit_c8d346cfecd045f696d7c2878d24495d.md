### Title
Non-deterministic floating-point exchange calculation in `ExchangeProcessor` causes cross-platform (x86/ARM) consensus divergence when `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION` are disabled (default) - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeCapsule.transaction` selects `ExchangeProcessor` (legacy, non-deterministic double math) whenever `hardenedCalc` (`allowHardenExchangeCalculation()`) is `0`, which is the default/legacy value until a chain-wide proposal activates it. `ExchangeProcessor` further dispatches `Maths.pow` based on the separate `allowStrictMath()` dynamic parameter, and when that is also `0` it calls the platform-specific `MathWrapper.pow`, which is implemented differently on x86 (raw `Math.pow`, JIT/hardware-dependent) versus ARM (a hard-coded lookup table of historically-patched results, falling back to `StrictMath.pow` for anything not in the table).

### Finding Description
`ExchangeCapsule.transaction` at [1](#0-0)  picks `SafeExchangeProcessor.INSTANCE` (deterministic `BigDecimal` + `StrictMathWrapper`) only when `hardenedCalc` is true; otherwise it constructs `new ExchangeProcessor(supply, useStrictMath)`. `ExchangeTransactionActuator.execute`/`doValidate` invoke this with `dynamicStore.allowStrictMath()` and `allowHarden()` pulled straight from `DynamicPropertiesStore`, e.g. [2](#0-1) . Both `allowHardenExchangeCalculation()` and (by the same committee-proposal pattern) `allowStrictMath()` default to `0`/disabled until enabled by a network-wide proposal, per `getAllowHardenExchangeCalculation()`'s default fallback of `0L` [3](#0-2) .

Inside `ExchangeProcessor.exchangeFromSupply`, the result is computed with `Maths.pow(...)` and truncated via `(long) exchangeBalance` [4](#0-3) . `Maths.pow` dispatches to `MathWrapper.pow` when `useStrictMath` is false [5](#0-4) . Crucially, `MathWrapper` is platform-specific:
- x86: `MathWrapper.pow` calls `Math.pow` directly (JIT/hardware-dependent, non-strict) [6](#0-5) .
- ARM: `MathWrapper.pow` looks up a hard-coded table of exact bit patterns (`powData`) keyed to specific historical mainnet block computations, and falls back to `StrictMath.pow` for any unlisted input [7](#0-6) [8](#0-7) .

The existence of this `powData` correction table on ARM — hand-patched with dozens of specific `(a, b) -> result` triples tied to specific historical block numbers — is direct evidence that `Math.pow` (x86, non-strict) and `StrictMath.pow` (ARM fallback) have historically produced divergent results for identical inputs on this exact code path, and that these divergences had to be manually patched block-by-block after the fact to keep ARM nodes in consensus with x86 nodes. Any input not in the table remains exposed to divergence, and `ExchangeCapsule.transaction`/`ExchangeProcessor` is exactly the call site the table exists to patch.

The unit test `ExchangeProcessorTest.testStrictMath` explicitly documents that `Maths.pow`'s strict vs. non-strict results actually differ for typical exchange inputs (`Assert.assertNotEquals(anotherTokenQuant, result)` comparing `useStrictMath=false` vs `true`) [9](#0-8) , confirming the double-precision boundary sensitivity described in the audit question.

No existing check (`validateSignature`, `validate()`, fork gates) prevents this: `ExchangeTransactionActuator.doValidate`/`execute` only validate token balances/signatures/expected amounts, not floating-point determinism, and the divergence occurs purely from ordinary hardware/JIT differences on otherwise-honest validating nodes — no malicious peer or privileged role is required.

### Impact Explanation
Impact is consensus/state divergence (chain fork) between x86 and ARM validating nodes (or even between x86 nodes with different JIT compilation levels/CPU microarchitectures, though the ARM lookup-table's existence proves the x86/ARM split is the concretely observed instance) processing the identical `ExchangeTransactionContract`. Since `exchangeFromSupply`'s output feeds directly into account asset/TRX balances written to state (`ExchangeCapsule.transaction`, `ExchangeTransactionActuator.execute`), a differing `(long) exchangeBalance` produces a different post-state hash on different node subsets, causing a chain split without any malicious peer — matching the "consensus divergence" bounty class.

### Likelihood Explanation
Precondition is that `allowHardenExchangeCalculation()==0` and `allowStrictMath()==0`, i.e., the legacy/default path before these hardening proposals are activated network-wide — this is exactly the state the `powData` patch table in `MathWrapper` (ARM) was built to work around, evidencing this was a live, previously-encountered issue in production rather than a theoretical one. The attacker only needs to be an ordinary funded account able to broadcast a signed `ExchangeTransactionContract` with a `quant` chosen to land near an unstable `pow()` boundary — no special privilege, cost beyond ordinary transaction fees, and it is repeatable for any exchange pair.

### Recommendation
Route `ExchangeCapsule.transaction` unconditionally through the deterministic `SafeExchangeProcessor` (BigDecimal + `StrictMathWrapper`), independent of the `ALLOW_HARDEN_EXCHANGE_CALCULATION`/`ALLOW_STRICT_MATH` proposal state, or ensure `MathWrapper.pow` on all platforms is guaranteed bit-identical (e.g., always delegate to `StrictMath.pow` with no platform-specific non-strict fallback) rather than relying on a manually maintained historical patch table.

### Proof of Concept
```java
// Differential test demonstrating platform-dependent divergence for the identical
// exchange calculation used by ExchangeCapsule.transaction / ExchangeProcessor.
@Test
public void testNonStrictVsStrictPowDivergence() {
  long supply = 1_000_000_000_000_000_000L;
  // Same balances/quant as network-observed divergent inputs
  long sellBalance = 4732214L, buyBalance = 2202692725330L, sellQuant = 29218L;

  ExchangeProcessor nonStrict = new ExchangeProcessor(supply, false); // MathWrapper.pow (x86: Math.pow)
  ExchangeProcessor strict = new ExchangeProcessor(supply, true);     // StrictMathWrapper.pow (ARM fallback)

  long resultNonStrict = nonStrict.exchange(sellBalance, buyBalance, sellQuant);
  long resultStrict = strict.exchange(sellBalance, buyBalance, sellQuant);

  // On x86 vs ARM (for inputs not present in MathWrapper.powData), these can differ,
  // producing divergent ExchangeCapsule state / account balances for the identical
  // ExchangeTransactionContract broadcast on-chain.
  Assert.assertNotEquals(resultNonStrict, resultStrict); // demonstrates non-determinism
}
```
This mirrors `ExchangeProcessorTest.testStrictMath` [10](#0-9) , which already asserts `assertNotEquals(anotherTokenQuant, result)` between non-strict and strict paths for realistic exchange inputs, confirming the divergence is real and reachable via an ordinary `ExchangeTransactionContract`.
