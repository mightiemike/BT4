### Title
Permissionless `ExchangeWithdrawActuator` allows draining and permanently closing any Bancor-style exchange, denying market access to all future users - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Code4rena report describes a design flaw where an unprivileged, permissionless user action (buying then immediately selling all launchpad tokens) drives a shared counter to zero and permanently trips an irreversible "end rewards" flag (`_endRewards()` in `LaunchToken.sol`), denying future participants (post-graduation swappers) any reward accrual, for essentially only gas cost. The analogous root cause in java-tron is the `Exchange*` (Bancor-style TRC10/TRX pool) subsystem: any account can call `ExchangeWithdrawActuator` against an existing exchange pair with no requirement that the caller previously deposited into that pool, and the withdrawal amount can be chosen to bring the pool's balances to exactly zero. Once either side of the pool reaches zero, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` all permanently reject further operations with "the exchange has been closed," and there is no owner/committee mechanism to reopen it.

### Finding Description
`ExchangeCreateActuator.doValidate()`/`execute()` lets any account with sufficient balance permissionlessly create a TRC10/TRX exchange pool by depositing two initial token balances: [1](#0-0) 

Once created, `ExchangeWithdrawActuator.execute()` allows any account (not just the pool creator, and with no share/LP-token bookkeeping) to specify `tokenId` and `quant`, compute the proportional amount of the other token, and receive **both** amounts, while decrementing the pool's balances by the same amounts: [2](#0-1) 

If an attacker sets `tokenId = firstTokenID` and `quant = firstTokenBalance` (the entire current pool balance), the proportional computation `anotherTokenQuant = secondTokenBalance * quant / firstTokenBalance` resolves exactly to `secondTokenBalance`, so a single transaction can zero out both sides of the pool and credit the attacker with the pool's entire remaining liquidity: [3](#0-2) 

`doValidate()` for withdraw does not restrict the caller to the pool creator or to someone who has previously injected liquidity — it only checks fee balance, valid token IDs, and that computed amounts are sufficient/precise: [4](#0-3) 

Once the pool balance is zero, all three exchange actuators (`Inject`, `Withdraw`, `Transaction`) treat the market as permanently closed and reject every future operation, with no recovery path: [5](#0-4) 

This mirrors the reported bug class exactly: an unprivileged, permissionless action drives a shared accounting counter (pool balance / `totalFeeShare`) to zero, which permanently and irreversibly disables a mechanism (market trading / reward accrual) intended to serve future, unrelated participants, and the entire attack costs only the network fee.

### Impact Explanation
Any account can:
1. Wait for (or create) an exchange pair.
2. Submit a single `ExchangeWithdrawContract` withdrawing the full current balance of one token, receiving both the withdrawn token and the exactly-computed proportional amount of the other token.
3. Permanently zero out the pool, closing it for all future `Inject`/`Withdraw`/`Transaction` operations.

This is a denial-of-service against a core TRC10/TRX exchange (market/AMM) primitive and also results in unauthorized extraction of pooled assets belonging to whoever previously injected liquidity, since the withdraw path is not gated by prior contribution/shares. This corrupts exchange/market accounting and denies the market to all subsequent users, matching the "exchange/market math" and "resource and reward accounting" categories in scope.

### Likelihood Explanation
Likelihood is high: the attack requires only a single, correctly-crafted `ExchangeWithdrawContract` broadcast by any account (no special permissions, no leaked keys, no privileged role), and the exact-quotient case (`quant == firstTokenBalance`) is trivial to compute and cheap (only the standard exchange fee). It can be repeated against any newly created or actively used exchange pair.

### Recommendation
- Require the exchange to maintain proper liquidity-provider share accounting so that `ExchangeWithdrawActuator` only allows a caller to withdraw up to their own contributed share, not an arbitrary amount up to the full pool balance.
- Reject withdrawals that would drive either side of the pool balance to zero unless it is an intentional, fully-authorized pool closure (e.g., restricted to the original creator, or requiring all LPs to have withdrawn).
- Add a mechanism (or explicit governance-controlled path) to reopen/refund a pool if it is ever fully drained, rather than permanently bricking it via the `firstTokenBalance == 0 || secondTokenBalance == 0` check.

### Proof of Concept
1. Any account calls `ExchangeCreateActuator` (or reuses an existing pool) which deposits `firstTokenBalance = X`, `secondTokenBalance = Y` per `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java` lines 182–203.
2. Any account (not necessarily the creator) broadcasts an `ExchangeWithdrawContract` with `tokenId = firstTokenID`, `quant = X` (the full current first-token balance).
3. `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant = Y` exactly (per `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java` lines 77–89), sets the pool balances to `(0, 0)`, and credits the attacker with both `X` and `Y`.
4. All subsequent `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` calls against this exchange ID now fail with "Token balance in exchange is equal with 0, the exchange has been closed" (as verified by the existing test in `framework/src/test/java/org/tron/core/actuator/ExchangeWithdrawActuatorTest.java` lines 1044–1057), permanently denying the market to any future participant.
