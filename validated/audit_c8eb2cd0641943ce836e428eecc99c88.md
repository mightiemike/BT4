### Title
Missing minimum/maximum amount (slippage) protection in `ExchangeInjectContract` and `ExchangeWithdrawContract` allows unfavorable execution due to delayed transaction processing - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `protocol/src/main/protos/core/contract/exchange_contract.proto`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` only carry a `token_id` and a `quant` for one side of the trade; the counter-token amount (`anotherTokenQuant`) is derived at execution time from the exchange pool's *current* balances. Unlike `ExchangeTransactionContract`, which has an `expected` field enforced in `ExchangeTransactionActuator.doValidate()`, neither contract nor actuator provides any bound on how much of the other token can be taken from (inject) or given to (withdraw) the user. If the transaction sits in the mempool/queue and the pool ratio shifts before it is packed — exactly the "delayed execution changes economic parameters" scenario described in the report — the user's actual counter-token amount can diverge arbitrarily from what they expected when they signed the transaction, with no on-chain mechanism to reject the trade.

### Finding Description
`ExchangeTransactionContract` explicitly protects the caller from this class of issue: [1](#0-0) 
This check compares the pool-derived `anotherTokenQuant`, computed **at validate/execute time**, to the `tokenExpected` value the user embedded in the signed transaction, and reverts if the deal has become worse than the user accepted.

`ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent field: [2](#0-1) 

In `ExchangeInjectActuator.execute()`, `anotherTokenQuant` is computed purely from the pool balances present at execution time and is then deducted from the user's account together with `tokenQuant`, with no comparison to any user-supplied bound: [3](#0-2) 
Likewise, `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from live pool balances and credits it to the user with no bound check: [4](#0-3) 

Because the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be moved by any other `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` that is packed into an earlier block, a user's inject/withdraw transaction that waits in the pending-transaction queue (`Manager.generateBlock`, which pulls from `pendingTransactions`/`rePushTransactions` and can be delayed by block-size limits, `System.currentTimeMillis() > timeout`, or simple network propagation) will be executed against whatever the ratio is at that later point, not the ratio at submission time. There is no `deadline`-style or `expected`-style parameter to cause the transaction to revert if the ratio has drifted unfavorably.

### Impact Explanation
For `ExchangeInjectContract`, an unfavorable ratio shift means the user is forced to contribute more of the counter-token than intended to maintain the pool's constant ratio — effectively an uncapped, involuntary asset debit relative to their expectation. For `ExchangeWithdrawContract`, an unfavorable shift means the user receives less of the counter-token than expected for the same withdrawn `quant`. Both are direct, unprivileged-user-triggerable accounting/economic-loss issues reachable by any TRX/TRC10 holder interacting with a live TRC10 exchange pair, matching the report's root cause (execution-time state divergence from submission-time expectation, with no deadline/expected safeguard).

### Likelihood Explanation
Likelihood is medium: it requires (a) an active exchange pool with sufficient trading activity to move the ratio, and (b) the victim's transaction being delayed (mempool congestion, block-size postponement, or simple multi-block propagation) relative to other trades altering the pool. This is a naturally occurring condition on any moderately active TRC10 exchange, and does not require any privileged role — any account can submit competing `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions to shift the ratio before the victim's transaction lands.

### Recommendation
Add an `expected` (or `min_receive`/`max_another_quant`) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the pattern already used in `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `doValidate()` (and ideally re-checked in `execute()` for defense in depth), reverting the transaction if the computed `anotherTokenQuant` falls outside the user-specified bound.

### Proof of Concept
1. Exchange pool `firstToken`/`secondToken` has balances `A`/`B`.
2. User submits `ExchangeInjectContract` with `token_id = secondToken`, `quant = Q`, expecting `anotherTokenQuant ≈ A*Q/B` of `firstToken` to be additionally debited.
3. Before the user's transaction is packed, another account submits and gets included in an earlier block an `ExchangeTransactionContract` (or another Inject/Withdraw) that shifts the pool ratio to `A'`/`B'`.
4. When the user's transaction finally executes, `ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant` from `A'`/`B'` [5](#0-4) , debiting a different (potentially much larger) amount of `firstToken` from the user than they anticipated when signing, with no check or revert path available.
