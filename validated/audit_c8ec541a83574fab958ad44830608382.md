### Title
Malicious NEP-141 target permanently locks the Wallet Contract's transaction queue via callback gas exhaustion - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (`WalletContract`) enforces a single-in-flight-transaction invariant via `has_in_flight_tx`, which is only reset to `false` inside `#[private]` callback methods invoked at the end of a promise chain. For the ERC20-emulation path, one of those callbacks (`nep_141_storage_balance_callback`) is scheduled with a small, fixed static gas budget while it must read a `PromiseResult` whose byte size is entirely controlled by an attacker-chosen target contract (`token_id`). If the attacker's contract returns an oversized `storage_balance_of` value, the callback exhausts its gas before executing `self.has_in_flight_tx = false;`'s effects can be persisted, causing the whole receipt (including that reset) to be rolled back by NEAR's atomic per-receipt state semantics. This leaves `has_in_flight_tx` stuck at `true` forever, permanently blocking all future `rlp_execute` calls for that account — an analog of the Y2K "attacker blocks deposit/rollover queue via unfulfillable callback" bug class.

### Finding Description
`rlp_execute` refuses to run if `has_in_flight_tx` is `true`, and sets it back to `true` right before returning any promise: [1](#0-0) 

The invariant documented in the struct is that `has_in_flight_tx` is `true` while a receipt chain is pending and must return to `false` once resolved: [2](#0-1) 

For an ERC20 (NEP-141) style transfer, `inner_rlp_execute` schedules a call to the **attacker-controlled** `target` account's `storage_balance_of`, followed by a private callback `nep_141_storage_balance_callback`, with a fixed static gas budget: [3](#0-2) 

The callback gas is fixed by constants that do not scale with the size of the token contract's return value: [4](#0-3) 

Inside the callback, `self.has_in_flight_tx = false;` executes first, but the function then reads `env::promise_result(0)` and deserializes it — an operation whose gas cost scales with the byte length of the returned value (up to the protocol's maximum function-call return size): [5](#0-4) 

Because `token_id` (the `target` of the emulated ERC-20 transfer) is chosen by the transaction and can point to any account, an attacker can deploy a contract whose `storage_balance_of` method returns a maximally-sized blob. When such a call is routed through the Wallet Contract, the callback's fixed gas allotment (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, a handful of Tgas) is insufficient to copy/read that value, and the receipt fails with a gas-exceeded host error. NEAR's runtime rolls back *all* state changes made during a failed receipt — this is the same "all state changes of the receipt are undone on failure" semantics documented for action-receipt execution (`apply_action_receipt`, commit-or-rollback step): [6](#0-5) 

Consequently, the earlier `self.has_in_flight_tx = false;` write inside the failed callback is discarded along with everything else in that receipt, and the flag remains permanently `true`.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, every subsequent `rlp_execute` call for that account is rejected at the very first check with "transaction already in progress, please try again later" — there is no recovery path exposed in the contract (no admin reset, no timeout). This permanently freezes the eth-implicit account controlled by the Wallet Contract: the user can no longer relay any Ethereum-style transaction (transfers, function calls, ERC-20 transfers) through it. This matches the accepted impact class of "permanently frozen funds" (the account's assets become unusable through its only execution path) and is a transaction-triggered halt of that account's processing queue, directly analogous to the Y2K report's "attacker blocks deposit/rollover queue forever."

### Likelihood Explanation
The attack is reachable by any unprivileged party who can get an eth-implicit account's owner (or a relayer acting on their behalf) to submit an ETH-emulated ERC-20 transfer whose `target`/token contract is attacker-controlled — for instance, an attacker publishing a fake "token" and enticing a relayer/user to interact with it (a realistic scenario, since relayers process arbitrary user-signed RLP transactions and forward them without necessarily validating the token contract's behavior). No special privileges, validator collusion, or network-layer capability is required — a single crafted NEP-141-like contract and a single relayed transaction suffice.

### Recommendation
- Do not reset critical invariants (`has_in_flight_tx = false`) as a side effect that can be rolled back by a later panic/gas-exhaustion in the same receipt; perform the state write only after all potentially-failing operations (e.g., deserialize/read the promise result data) have completed successfully, or split the reset into its own guaranteed-to-succeed final step.
- Bound or reject unexpectedly large `PromiseResult` payloads before processing them (e.g., check `env::promise_result` length via a cheap raw byte-count check, if available, before attempting to read/deserialize), and allocate callback gas independent of dynamic, attacker-controlled response sizes — or use a fixed generous gas ceiling combined with an explicit size check that fails fast and cheaply rather than exhausting the whole budget mid-read.
- Add a fallback/unlock mechanism (e.g., a time-based expiry on `has_in_flight_tx`, or a privileged relayer/owner recovery action) so that gas-exhaustion or other unexpected callback failures cannot permanently deadlock the account.

### Proof of Concept
1. Attacker deploys a NEAR contract `evil_token.near` implementing a `storage_balance_of` method that ignores its arguments and returns the maximum-allowed function-call return payload (e.g., several hundred KB to a few MB of dummy bytes, `test_promise_input_size_limit_fails_callback` shows return payloads of 2.5 MB are accepted individually, `test-loop-tests/src/tests/promise_input_size_limit.rs:16-44`).
2. A relayer submits (via `rlp_execute`) a user's signed Ethereum-style transaction whose decoded action is an `EthEmulationKind::ERC20Transfer` with `target = evil_token.near`.
3. `inner_rlp_execute` builds: `Promise::new(evil_token.near).function_call("storage_balance_of", ..., NEP_141_STORAGE_BALANCE_OF_GAS).then(ext.nep_141_storage_balance_callback(...))` with `callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` — a small, fixed-plus-user-supplied-action-gas budget, not scaled to the attacker's response size (`lib.rs:433-458`).
4. `rlp_execute` sets `has_in_flight_tx = true` and returns the promise (`lib.rs:117-119`).
5. `evil_token.near::storage_balance_of` executes and returns its oversized blob.
6. `nep_141_storage_balance_callback` begins, sets `self.has_in_flight_tx = false;` in-memory (`lib.rs:202`), then calls `env::promise_result(0)` to read the oversized value — this exceeds the callback's fixed gas budget and the receipt fails with a gas-exceeded error.
7. Per NEAR's atomic receipt semantics, all state changes from this failed receipt (including the `has_in_flight_tx = false` write) are rolled back, leaving `has_in_flight_tx == true` in persisted state.
8. Every future `rlp_execute` call to this account now immediately returns `"Error: transaction already in progress, please try again later."` (`lib.rs:97-105`), permanently, with no way to reset it — freezing the account's ability to transact through the Wallet Contract.
