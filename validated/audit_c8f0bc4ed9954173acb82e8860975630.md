### Title
Address Registrar's `register()` Permanently Retains Excess Attached Deposit on Success, With No Refund Mechanism for Overpayment - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar::register` method is a `#[payable]` contract entry point that only validates `attached_deposit >= required_deposit` before writing a new address→account mapping. On the success path (a new, previously-vacant address slot), any excess deposit above the exact storage cost is never refunded — the caller's overpayment is silently absorbed into the contract balance forever. A refund is only issued on the failure/no-op path (address collision), which is the reverse of the pattern that actually needs protecting.

### Finding Description
`register()` computes `required_deposit` from the storage bytes needed to store the `Address -> AccountId` mapping, then only enforces a lower bound: [1](#0-0) 

If the entry is vacant (the success/storage-writing case), the code inserts the entry and returns the address **without ever computing or refunding `given_deposit - required_deposit`**: [2](#0-1) 

By contrast, in the `Entry::Occupied` branch (address collision, nothing written to storage) the *entire* `given_deposit` is refunded via a `Transfer` promise back to `predecessor_account_id`: [3](#0-2) 

This is structurally identical to the reported `buy()` bug class: the contract enforces `attached_deposit >= required_amount` (analogous to `msg.value >= totalRoseAmount`) but has no logic to return the difference when `attached_deposit > required_amount` on the success path. The existing test suite even encodes this behavior as expected rather than flagging it as a bug — `test_register_without_deposit` sends a deposit and only asserts the contract balance increases by **at least** the deposit amount, never checking that any excess is returned: [4](#0-3) 

This function is reachable by any unprivileged caller: directly via a normal `FunctionCall` action against the deployed `AddressRegistrar` contract, or indirectly through the ETH-implicit Wallet Contract's `rlp_execute` flow, which is explicitly documented as calling this registrar as part of eth-implicit account transaction processing: [5](#0-4) 

The Wallet Contract itself tracks and refunds `CallerDeposit` only when the downstream cross-contract call *fails* — when it succeeds (as in a successful `register` call), the caller's full attached amount (including any excess above the registrar's storage cost) is spent and not reconciled: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any user (or relayer acting on a user's behalf through the Wallet Contract) who attaches more NEAR than the exact storage cost when calling `register()` permanently loses the excess — there is no code path that returns it. Because the required deposit is a precise, hard-to-predict on-chain byte-cost calculation (`storage_byte_cost() * (20 + account_id.len())`), overpayment is a realistic and easy user error (e.g. rounding up, using a fixed "safe" deposit constant, or retrying with stale byte-cost assumptions). Funds sent this way become an unrecoverable donation to the `AddressRegistrar` contract's balance, meeting the "permanently frozen/lost user funds" criterion for a valid finding.

### Likelihood Explanation
High. The bug requires no adversarial conditions — it triggers on completely benign usage whenever a caller (end user or relayer via `rlp_execute`) attaches a deposit larger than the exact computed storage requirement, which is a normal, expected occurrence since callers typically don't compute the exact byte cost precisely and instead attach a rounded/conservative amount (as shown in the test using a fixed `NearToken::from_millinear(1)` deposit for `register`).

### Recommendation
In the `Entry::Vacant` success branch of `register()`, compute `given_deposit.checked_sub(required_deposit)` and, if positive, issue a `Transfer` promise refunding the excess to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Entry::Occupied` branch. This ensures the caller is charged exactly `required_deposit` regardless of how much they attach.

### Proof of Concept
1. Deploy/target `AddressRegistrar` on NEAR (as is done in the existing test harness).
2. Call `register({"account_id": "alice.near"})` attaching a deposit strictly greater than the exact required storage deposit (e.g. attach `1_000_000_000_000_000_000_000_000` yoctoNEAR when the exact required cost is `320000000000000000000` yoctoNEAR, as computed in `test_register_without_deposit`).
3. Observe the call succeeds (`Some(address)` returned, mapping stored).
4. Query the caller's account balance before/after: the full attached deposit was deducted, but only `required_deposit` was needed for storage — the excess is added to the contract's balance with no promise ever transferring it back.
5. Compare against `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:249-276`, whose assertions (`>=` rather than `==`) confirm the excess is retained rather than refunded.

/// Test asserting the address registrar requires a deposit.
#[tokio::test]
async fn test_register_without_deposit() -> anyhow::Result<()> {
    let TestContext { worker, address_registrar, .. } = TestContext::new().await?;

    let method = "register";
    let args = br#"{"account_id": "birchmd.near"}"#;
    let result = address_registrar.call(method).args(args.to_vec()).transact().await?;
    assert!(result.is_failure(), "Call without deposit must fail");

    let pre_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    let deposit_amount = NearToken::from_yoctonear(320000000000000000000);
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output.as_deref(), Some("0x4bfcff9a964925adf801c866f6ada98bd7ec40ca"));
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

### Wallet Contract

The Wallet Contract (see [NEP-518](https://github.com/near/NEPs/issues/518) for more details) functions as a user account and is designed to receive, validate, and execute Ethereum-compatible transactions on the NEAR blockchain.

Without going into details, an Ethereum-compatible wallet user sends a transaction to an RPC endpoint, which wraps it and passes it to the Wallet Contract (on the target account) as an `rlp_execute(target: AccountId, tx_bytes_b64: Vec<u8>)` contract call.
Then, the contract parses `tx_bytes_b64` and verifies it is signed with the private key matching the target [ETH-implicit account ID](#eth-implicit-account-id) on which the contract is hosted.

Under the hood, the transaction encodes a NEAR-native action. Currently supported actions are:

- Transfer (from ETH-implicit account).
- Function call (call another contract).
- Add `AccessKey` with `FunctionCallPermission`. This allows adding a relayer's public key to an ETH-implicit account, enabling the relayer to pay the gas fee for transactions from this account. Still, each transaction has to be signed by the owner of the account (corresponding Secp256K1 private key).
- Delete `AccessKey`.
