### Title
Missing `totalEnergyWeight == 0` guard causes `ArithmeticException` in `RepositoryImpl.calculateGlobalEnergyLimit` (used by TVM opcodes) - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` without the zero-guard that the equivalent chain-level function `EnergyProcessor.calculateGlobalEnergyLimit` has, mirroring the TribalChief `totalAllocPoint == 0` bug class: an unguarded divisor derived from a global accumulator can hit zero and cause a revert/exception in a code path relied upon by ordinary users.

### Finding Description
`EnergyProcessor.calculateGlobalEnergyLimit` (the resource accounting path used for bandwidth/energy consumption in normal transactions) explicitly guards against `totalEnergyWeight <= 0` by returning `0` early when the `allowNewReward` feature is active, and only falls back to an `assert` otherwise: [1](#0-0) 

However, `RepositoryImpl.calculateGlobalEnergyLimit` — the parallel implementation used by the TVM/actuator layer (`Repository` interface, delegated through `ContractState.calculateGlobalEnergyLimit`) — has no such `totalEnergyWeight <= 0` short-circuit at all; it only contains a bare `assert totalEnergyWeight > 0;` before unconditionally dividing by `totalEnergyWeight`: [2](#0-1) 

Java `assert` statements are disabled by default at runtime unless the JVM is started with `-ea`, so in a production deployment this assertion provides no protection. If `totalEnergyWeight` is `0` while an account nonetheless has `frozeBalance >= TRX_PRECISION` (e.g., very early chain state, a private/test network, or any transient state where the global energy-weight accounting can reach zero), the hardened path performs `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(totalEnergyWeight))`, which throws `ArithmeticException: / by zero`. This is delegated from `ContractState.calculateGlobalEnergyLimit`: [3](#0-2) 

This is the direct analog of the TribalChief bug: a globally-tracked accumulator (`totalAllocPoint` / `totalEnergyWeight`) is used unconditionally as a divisor in a public-facing accounting function, and reaching zero causes the function to revert/throw instead of degrading gracefully, unlike its sibling implementation (`EnergyProcessor`) which was hardened against exactly this case.

### Impact Explanation
If this code path throws during TVM execution (e.g., invoked while computing energy limits for a contract-related account), it manifests as an unexpected runtime exception in energy/resource accounting logic used by ordinary contract calls, rather than a controlled validation failure — potentially halting or reverting transaction processing unexpectedly instead of returning a sane fallback value (as `EnergyProcessor` does). This maps to the report's "invalid-state/halt" impact category since accounting logic that should degrade to `0` instead surfaces an uncaught arithmetic fault.

### Likelihood Explanation
Likelihood is limited by the fact that `totalEnergyWeight` reaching exactly `0` while a live account still has frozen balance for energy is not a normal mainnet condition (freezing for energy is what increments `totalEnergyWeight`), so on a mature mainnet this divisor is unlikely to be zero. However, the inconsistency between `RepositoryImpl` (unguarded) and `EnergyProcessor` (guarded) for the exact same computation is a genuine code defect, and the guard's absence is exploitable in any network state where `totalEnergyWeight` can transiently be `0` (private/consortium chains, early genesis states, or after mass unfreeze events combined with `allowNewReward` not yet active).

### Recommendation
Add the same `totalEnergyWeight <= 0` short-circuit used in `EnergyProcessor.calculateGlobalEnergyLimit` (lines 156–160) to `RepositoryImpl.calculateGlobalEnergyLimit`, returning `0` instead of relying on an assertion that is inert in production builds.

### Proof of Concept
1. Deploy/observe a chain state (e.g., private network at genesis, or right after a global reset of energy weight) where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0`.
2. Have an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (any nonzero frozen-for-energy balance) invoke a code path in the TVM that calls `Repository.calculateGlobalEnergyLimit` (via `ContractState`), with `VMConfig.allowHardenResourceCalculation()` enabled.
3. Execution reaches `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))`, throwing `ArithmeticException`, since the `assert totalEnergyWeight > 0` at line 976 does not fire in a standard (non `-ea`) JVM runtime: [4](#0-3)

```java
  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
```
