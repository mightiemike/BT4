### Title
Stale `TotalEnergyTargetLimit` after `TOTAL_ENERGY_LIMIT` proposal breaks Adaptive Energy Limit scaling decision - (File: framework/src/main/java/org/tron/core/consensus/ProposalService.java)

### Summary
When governance updates the `TOTAL_ENERGY_LIMIT` chain parameter via a passed proposal, `ProposalService.process()` only updates the raw `TotalEnergyLimit` value in the `DynamicPropertiesStore`. It never recomputes the derived `TotalEnergyTargetLimit` (`TotalEnergyLimit / adaptiveResourceLimitTargetRatio`), which is used every block by `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` to decide whether the network-wide adaptive energy budget should contract or expand. This mirrors the reported Anchor bug: a config value is updated by a privileged actor, but the dependent "epoch"-style derived calculation is not refreshed, so the system operates on stale data until an unrelated event happens to recompute it.

### Finding Description
`TotalEnergyTargetLimit` is only ever (re)written in two places inside `ProposalService.process()`:
- `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO`, which recomputes it from the *current* `TotalEnergyLimit`: [1](#0-0) 
- `ALLOW_ADAPTIVE_ENERGY` (one-time bootstrap when adaptive energy is first enabled): [2](#0-1) 

However, the `TOTAL_ENERGY_LIMIT` case only updates the raw limit and does **not** recompute the derived target: [3](#0-2) 

The stale `TotalEnergyTargetLimit` is then read every block (via the maintenance/adaptive-limit update path) in `EnergyProcessor.updateAdaptiveTotalEnergyLimit()`, where it is directly compared against the rolling `totalEnergyAverageUsage` to decide whether the current adaptive energy limit should be scaled up (`EXPAND_RATE`) or down (`CONTRACT_RATE`): [4](#0-3) 

Because `TotalEnergyTargetLimit` is not derived on-the-fly from the live `TotalEnergyLimit` at read time, but persisted as a snapshot that is only refreshed by an *unrelated* proposal type (`ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO`), any witness-governance decision to raise or lower `TOTAL_ENERGY_LIMIT` alone leaves the target used for the contract/expand decision pinned to the old limit divided by the old ratio — i.e., calculated against a value that no longer matches the newly configured total limit.

### Impact Explanation
`TotalEnergyCurrentLimit` (the actual global energy budget enforced for TVM/contract execution across the whole chain) is adjusted every maintenance cycle based on this comparison. If governance only proposes a `TOTAL_ENERGY_LIMIT` change (a very plausible governance action on its own, since `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` changes independently and much less frequently), the target used to gate expansion/contraction remains computed against the old total limit. This can cause the network to systematically over-contract or over-expand the adaptive current limit relative to what governance intended, producing an incorrect global resource ceiling that persists until a separate, unrelated `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` proposal happens to pass and incidentally refresh the target. This is a consensus-relevant, network-wide invalid-state condition (all full nodes derive the same wrong value deterministically, so it does not cause a fork by itself, but it silently diverges from the value governance intended to configure).

### Likelihood Explanation
This requires only a normal witness-approved chain-parameter proposal for `TOTAL_ENERGY_LIMIT` (`ProposalType` code 17), which is a routine governance action, with no attacker interaction needed — matching the "lack of validation / stale config-derived state" bug class from the reference report. No `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` proposal needs to be submitted at the same time, so this can realistically occur any time `TOTAL_ENERGY_LIMIT` is changed on its own.

### Recommendation
In the `TOTAL_ENERGY_LIMIT` case of `ProposalService.process()`, recompute and persist `TotalEnergyTargetLimit` from the newly-set `TotalEnergyLimit` and the currently configured `adaptiveResourceLimitTargetRatio`, mirroring the recomputation already performed in the `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` branch, e.g.:
```java
case TOTAL_ENERGY_LIMIT: {
  manager.getDynamicPropertiesStore().saveTotalEnergyLimit(entry.getValue());
  long ratio = manager.getDynamicPropertiesStore().getAdaptiveResourceLimitTargetRatio();
  manager.getDynamicPropertiesStore().saveTotalEnergyTargetLimit(entry.getValue() / ratio);
  break;
}
```
Alternatively, compute `TotalEnergyTargetLimit` on-the-fly inside `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` from the live `TotalEnergyLimit` and `AdaptiveResourceLimitTargetRatio` rather than persisting a separately-maintained snapshot, eliminating the possibility of the two values drifting apart.

### Proof of Concept
1. Governance submits and passes a proposal with `ProposalType.TOTAL_ENERGY_LIMIT` (code 17) raising `TotalEnergyLimit` from `50,000,000,000` to, say, `100,000,000,000`, without also submitting an `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` proposal.
2. `ProposalController.processProposal()` → `setDynamicParameters()` → `ProposalService.process()` executes the `TOTAL_ENERGY_LIMIT` case, calling only `saveTotalEnergyLimit(entry.getValue())`: [3](#0-2) 
3. `TotalEnergyTargetLimit` in the store still reflects the old `TotalEnergyLimit / oldRatio`, not the new limit.
4. On subsequent blocks, `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` reads this stale `targetTotalEnergyLimit` and compares it against `totalEnergyAverageUsage` to decide contraction/expansion of `TotalEnergyCurrentLimit`: [5](#0-4) 
5. The resulting `TotalEnergyCurrentLimit` no longer reflects the governance-intended scaling target based on the newly configured `TotalEnergyLimit`, until an unrelated `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` proposal happens to pass and recompute the target.

  public void updateAdaptiveTotalEnergyLimit() {
    long totalEnergyAverageUsage = dynamicPropertiesStore
        .getTotalEnergyAverageUsage();
    long targetTotalEnergyLimit = dynamicPropertiesStore.getTotalEnergyTargetLimit();
    long totalEnergyCurrentLimit = dynamicPropertiesStore
        .getTotalEnergyCurrentLimit();
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyLimit();

    long result;
    if (totalEnergyAverageUsage > targetTotalEnergyLimit) {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_DENOMINATOR);
    } else {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.EXPAND_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.EXPAND_RATE_DENOMINATOR);
    }
    long upperBound = hardenCalculation()
        ? BigInteger.valueOf(totalEnergyLimit).multiply(BigInteger.valueOf(
            dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier())).longValueExact()
        : totalEnergyLimit * dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier();
    result = min(max(result, totalEnergyLimit, this.disableJavaLangMath()),
        upperBound, this.disableJavaLangMath());

    dynamicPropertiesStore.saveTotalEnergyCurrentLimit(result);
    logger.debug("Adjust totalEnergyCurrentLimit, old: {}, new: {}.",
        totalEnergyCurrentLimit, result);
  }
