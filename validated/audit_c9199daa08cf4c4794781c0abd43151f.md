Based on my research, the closest native analog to the Permit2 `uint160(amount)` silent-truncation pattern is the unchecked `amount.Uint64()` narrowing conversion used when building the TSS-signed withdraw/execute message for Solana outbound transactions.

### Title
Unchecked `big.Int` → `uint64` narrowing of withdrawal amount in SVM TSS message construction - (File: universalClient/chains/svm/tx_builder.go)

### Summary
The Solana outbound tx builder converts the outbound `amount` (a `*big.Int`, PRC20-denominated) to `uint64` via `amount.Uint64()` when constructing the reference data that gets embedded into the TSS-signed message, mirroring the reported Permit2 pattern of casting a wide integer to a narrower type without a bounds check.

### Finding Description
`buildWithdrawAndExecuteRefData` is called with `amount.Uint64()` as one of its arguments when building the execute-mode gateway instruction: [1](#0-0) 

This value flows into `constructTSSMessage`, which encodes the amount as an 8-byte big-endian field that TSS validators sign and that the on-chain Solana gateway program uses to validate the message: [2](#0-1) 

Go's `(*big.Int).Uint64()` silently truncates to the low 64 bits when the value exceeds `2^64-1` — it does not return an error or overflow flag, so a `big.Int` amount larger than `math.MaxUint64` would be silently reduced to `amount mod 2^64`, exactly analogous to `uint160(amount)` truncating a `uint256` in the reported Permit2 bug.

### Impact Explanation
If the outbound/withdrawal amount that reaches this code path can exceed `2^64-1` (a very large PRC20-denominated amount, e.g., a token with 18 decimals and a large balance), the TSS-signed message would encode a truncated amount while the module's accounting/burn of the PRC20 token could be based on the full, untruncated amount. This mismatch could result in the TSS validators signing a withdrawal for far less than intended, causing user funds to be effectively stuck/lost relative to what was burned, or — depending on how the burn/accounting is reconciled elsewhere — a discrepancy between recorded UTX state and actual on-chain transfer amount.

### Likelihood Explanation
I could not fully verify, within available tool budget, whether an upstream validation step (e.g., in the `x/uexecutor` outbound-creation flow or PRC20 decimal/precision constraints) already bounds `amount` below `2^64-1` before this conversion is reached. If such a bound exists and is enforced on all code paths reaching `buildWithdrawAndExecuteRefData`, this finding would not be exploitable. This uncertainty should be resolved by tracing the full call chain from outbound creation/PRC20 burn accounting through to `BuildWithdrawAndExecuteTransaction` (the function enclosing this snippet) to confirm whether `amount` can ever legitimately exceed `math.MaxUint64` for any configured PRC20 token.

### Recommendation
Add an explicit bounds check before the narrowing conversion, e.g. `if amount.BitLen() > 64 { return error }` or `if !amount.IsUint64() { return error }`, and reject outbound/withdrawal construction rather than silently truncating.

### Proof of Concept

Due to index size limits, the full call chain from PRC20 accounting into this function was not completely traceable in this session; a Devin session with full codebase access would be needed to confirm reachability and finalize a concrete exploit trace.

	//   PREFIX || instruction_id || chain_id || deadline(i64 BE) || amount(u64 BE) || additional_data
	message := append([]byte(nil), tssMessagePrefix...)
	message = append(message, instructionID)
	message = append(message, []byte(chainID)...)
