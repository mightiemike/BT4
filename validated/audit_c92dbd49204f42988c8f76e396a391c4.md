### Title
Missing cross-validation between caller-supplied `shop` and the session token's `dest` claim in `shopify.auth.tokenExchange` - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
The bonding-curve report's root cause is a missing consistency check between two independently supplied values (`stepsize * numSteps` vs `curveSupply`) that are expected to match. The closest analogous pattern in shopify-app-js is `tokenExchange()`, which accepts a caller-supplied `shop` and a `sessionToken` as two independent parameters but never verifies that they refer to the same shop.

### Finding Description
`tokenExchange()` decodes and cryptographically validates the JWT `sessionToken` (signature, `exp`/`nbf`, and optionally `aud`), but it discards the decoded payload immediately without ever comparing `payload.dest` to the caller-supplied `shop` argument: [1](#0-0) 

The function then sanitizes `shop` (the caller-supplied value, not the value embedded in the token) and uses it verbatim to build the `/admin/oauth/access_token` request and to construct the resulting `Session`: [2](#0-1) 

By contrast, `decodeSessionToken` only checks `aud` (API key) and JWT time claims — it never asserts anything about `dest`: [3](#0-2) 

All first-party callers within this repo happen to avoid the problem by deriving `shop` directly from the validated token's `dest` claim rather than from an independent source:
- `shopify-app-express`'s `performTokenExchange` computes `shop` from `payload.dest` before calling `tokenExchange`: [4](#0-3) 
- `shopify-app-remix`/`shopify-app-react-router`'s `getSessionTokenContext` similarly derives `shop` from `payload.dest`: [5](#0-4) 

However, `tokenExchange` is a public, directly-callable API (`shopify.auth.tokenExchange`) documented for direct app use, and nothing in its implementation enforces that a caller must derive `shop` this way — it is architecturally analogous to the reported bug: two values (`shop` param and token `dest` claim) that are expected to be consistent are never cross-checked by the library itself, relying entirely on caller discipline.

### Impact Explanation
If a custom integration built directly on `@shopify/shopify-api` (bypassing the remix/react-router/express wrapper helpers) passes a `shop` value from an untrusted source (e.g., a query parameter) alongside a validly-signed session token for a *different* shop, `tokenExchange` will silently perform the OAuth token exchange against the attacker-chosen shop domain using the subject token from a different shop's session. Since Shopify's `/admin/oauth/access_token` token-exchange endpoint itself validates that the subject token matches the target shop, exploitability depends on Shopify's server-side enforcement, which this repository has no control over or test coverage for. Within the shopify-app-js codebase itself, there is no defense-in-depth check ensuring `shop === dest`, meaning the library trusts the remote token-exchange endpoint as the sole source of truth for shop consistency.

### Likelihood Explanation
Low-to-medium. All three first-party framework integrations (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) already derive `shop` correctly from the token payload, so default usage is unaffected. The exposure only exists for direct/custom consumers of the low-level `@shopify/shopify-api` `auth.tokenExchange` API who supply `shop` from a source other than the token's `dest` claim — a plausible but non-default integration pattern.

### Recommendation
Add a defense-in-depth check inside `tokenExchange()` (in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`) that compares the sanitized `shop` argument against the hostname derived from the decoded token's `dest` claim, throwing an `InvalidJwtError`/`InvalidOAuthError` on mismatch, similar to how `oauth.ts`'s `validQuery` cross-checks `state` against the cookie value with `safeCompare`. This removes reliance on every caller to independently re-derive `shop` from the token correctly.

### Proof of Concept
Not directly exploitable/demonstrable purely within this repository's test suite, since Shopify's remote OAuth endpoint is the actual enforcement point and is out of scope for a local PoC. The concrete code-level gap is shown by contrasting:
1. `decodeSessionToken` never validating `dest`: [6](#0-5) 
2. `tokenExchange` discarding the decoded payload and using only the caller-supplied `shop`: [7](#0-6) 

**Uncertainty**: I could not verify from the index whether any external/community consumer code in the wild calls `shopify.auth.tokenExchange` with a `shop` value not derived from the token's `dest` claim, nor could I confirm Shopify's remote token-exchange endpoint's exact server-side validation behavior for shop/subject-token mismatches — both are outside this repository. This finding is offered as the strongest structurally analogous "missing cross-field consistency check" pattern found in the codebase, but its exploitability is contingent on factors external to shopify-app-js.

    shop,

      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,

    const cleanShop = sanitizeShop(config)(shop, true)!;

        },
      },
    );

        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required

        config,
      }),
    };

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
}
