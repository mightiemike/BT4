### Title
Order-dependent `BatchProofMethodIdAccessor` activation-height check permanently drops earlier council-authorised method-id updates when a far-future update lands first - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`run_l1_block`'s handling of `DataOnDa::BatchProofMethodId` rejects any update whose `activation_l2_height` is `<=` the height of the *last-inserted* entry rather than the maximum known height, and the method-id body carries no DA-transaction-specific binding (no sender check, no nonce) so any already-published, validly-signed body can be re-inscribed by an unprivileged actor in a transaction whose Bitcoin inclusion order they control via fees. This lets an attacker force a genuinely council-authorised far-future method id (`H_far`) to be processed before a nearer one (`H_near`), permanently dropping `H_near` and making state transitions in `[H_near, H_far)` produced with the intended method id unprovable.

### Finding Description
The binding that must hold is: for every L2 height `h`, the method id selected by `process_complete_proof`'s binary search over `BatchProofMethodIdAccessor::get(...)` must equal the method id the security council most recently authorised for `h` — i.e. `selected_method_id(h) == council_intended_method_id(h)` for all council-authorised activation heights `<= h`.

In `run_l1_block`, for `DataOnDa::BatchProofMethodId(batch_proof_method_id)`: [1](#0-0) 

The guard only compares against `batch_proof_method_ids.last()....0`, i.e. the height of whatever was inserted *most recently*, not the maximum activation height ever seen. `BatchProofMethodIdAccessor::insert` simply appends to the vector without re-sorting: [2](#0-1) 
This is demonstrated by the accessor's own unit test, which inserts height `1` after heights `3,4` and gets it appended out of order rather than rejected — proving `insert` performs no ordering/monotonicity enforcement itself; that enforcement is only the fragile "vs last element" check in `run_l1_block`.

Verification of the body is purely a 3-of-5 signature check over `(method_id, activation_l2_height, chain_id)` with no per-transaction nonce, no `blob.sender()` check, and no binding to a specific DA txid/wtxid: [3](#0-2) 
This means once the security council has broadcast (or the message has otherwise become public, e.g. observed in mempool/on-chain) a validly-signed `BatchProofMethodIdBody` for `H_near` and another for `H_far` (`H_near < H_far`), an unprivileged attacker can copy the exact signed bytes of the `H_far` body into their own DA inscription and pay a higher fee / control timing so that it is mined in an L1 block that is processed by the light-client circuit before the block containing the original `H_near` update.

When `run_l1_block` processes the `H_far` blob first, `BatchProofMethodIdAccessor::insert` appends `(H_far, mid_far)`, making it `.last()`. When the block carrying the legitimate `H_near` update is processed afterward, `H_near <= H_far` triggers `continue`, and `(H_near, mid_near)` is **never inserted**. `process_complete_proof`'s binary search for any L2 height in `[H_near, H_far)` then falls back to the pre-`H_near` method id: [4](#0-3) 
A true batch proof honestly generated by the batch prover with the council-intended `mid_near` for that range will fail `Z::verify` against the wrong (stale) method id and be silently rejected (`Err("Failed to verify proof")`), permanently blocking progress for that L2 range until council intervention re-issues an update — and even a re-issued update for a height `<= H_far` would again be dropped by the same "vs last" comparison.

No existing guard prevents this: there is no check that `activation_l2_height` exceeds the maximum of *all* recorded activation heights, no ordering/replacement of out-of-order entries, and no sender/nonce restriction on `BatchProofMethodId` blobs to stop rebroadcast-by-others with different fee/timing.

### Impact Explanation
This makes a true, council-intended state transition permanently unprovable for the L2 range `[H_near, H_far)` because `process_complete_proof` rejects any correctly generated batch proof for that range as using an "unrecognized" (mismatched) method id. This matches the Critical category: "a light client proof... made unprovable." The effect persists across every subsequent L1 block and every future prover attempt for that height range until a further method-id update is issued and successfully lands with a height greater than `H_far`, and the blast radius covers all honest full nodes and provers relying on the light client's state (light client proof output, batch proof method id used for the range).

### Likelihood Explanation
Preconditions: two council-authorised `BatchProofMethodId` bodies must exist and become observable (mempool/on-chain) with `H_near < H_far`. The attacker needs no special key — only the ability to copy already-published signed bytes into their own Bitcoin transaction and to influence relative confirmation order via fee bidding, which is within the described unprivileged attacker capability set ("pay Bitcoin fees to inscribe or mine any Bitcoin transaction"). This does not require majority hashrate or reorg — only fee-based ordering within/across near-term blocks, which is realistic whenever the council publishes overlapping/staged upgrades. Repeatable each time the council issues two updates without immediate confirmation of the nearer one.

### Recommendation
Change the acceptance check in `run_l1_block` to compare `batch_proof_method_id.body.activation_l2_height` against the **maximum** activation height across all currently stored entries (not just `.last()`), and/or have `BatchProofMethodIdAccessor::insert` maintain the vector sorted and reject/no-op insertions that are not strictly greater than the current maximum. Additionally, consider binding each method-id upgrade message to a monotonically increasing sequence number or explicit "supersedes" reference so replays of an old-but-valid signed body cannot be reordered by third parties.

### Proof of Concept
In `crates/light-client-prover/src/tests/mod.rs`:
1. Construct two `create_new_method_id_tx`-style blobs, `blob_near` (`activation_l2_height = H_near`, `method_id = mid_near`) and `blob_far` (`activation_l2_height = H_far`, `method_id = mid_far`), both validly signed by the test security council.
2. Call `run_l1_block` (or process two sequential DA blocks) with `blob_far` included/processed before `blob_near`.
3. Assert `BatchProofMethodIdAccessor::get` afterward does **not** contain `(H_near, mid_near)` and that the binary-search lookup for an L2 height in `[H_near, H_far)` returns the pre-`H_near` method id instead of `mid_near`.
4. Build a `BatchProofCircuitOutput`/proof stub with `last_l2_height` in `[H_near, H_far)` verified under `mid_near`, call `process_complete_proof`, and assert it returns `Err("Failed to verify proof")` even though `mid_near` was the council-intended, validly authorised method id for that range — demonstrating the equality `selected_method_id(h) == council_intended_method_id(h)` is broken.
