### Title
CREATE2 address derivation in `WalletUtil.generateContractAddress2` omits the reference single-byte prefix, causing on-chain deployment address to diverge from externally/Solidity-computed predicted addresses - ([File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java])

### Summary
The TVM's CREATE2 implementation computes `keccak256(sender ++ salt ++ keccak256(init_code))[12:]` with **no leading prefix byte**, whereas the standard EVM reference formula prepends `0xff` and TRON's own Solidity compiler (`tron-solc`) hardcodes a `0x41`/`0xa0` prefix when contracts predict CREATE2 addresses via inline assembly. This creates a real, reproducible mismatch between the address the TVM actually deploys to and the address any external tool or on-chain Solidity prediction helper computes using the "reference" formula.

### Finding Description
`Program.createContract2` (invoked from the `CREATE2` opcode handler `OperationActions.create2Action`) computes the new contract address via: [1](#0-0) 

which calls: [2](#0-1) 

This merges `sender ++ salt ++ keccak256(code)` and hashes with `Hash.sha3omit12`, **without any prefix byte**. The standard/reference CREATE2 formula (used by Solidity, ethers.js, OpenZeppelin's `Create2.sol`, and explicitly documented as `tron-solc`'s own hardcoded on-chain prediction pattern) is `keccak256(prefix ++ sender ++ salt ++ keccak256(init_code))`, where `prefix` is `0xff` on Ethereum or `0x41`/`0xa0` as hardcoded by `tron-solc` for TRON, as shown in the reconstructed factory contract: [3](#0-2) 

This divergence is already flagged as a known inconsistency in the test suite itself: [4](#0-3) 

Because the TVM opcode-level formula omits the prefix entirely, any counterfactual-address-prediction pattern (a common Solidity idiom for computing a CREATE2 address before deployment, e.g. deposit-address factories, Uniswap-style pair prediction, state-channel counterparty addresses) that uses the reference formula (with a prefix byte) will predict an address that **does not equal** the address the TVM will actually assign on deployment. No authentication, accounting, or replay guard applies here since this is a pure address-derivation/formula bug reachable by any unprivileged account triggering `CREATE2` via `TriggerSmartContract`.

### Impact Explanation
An attacker who understands the true (no-prefix) TVM formula can:
- Deploy to the real CREATE2 address before a victim relying on standard/reference tooling realizes the actual deployment target differs from their off-chain prediction, enabling squatting on the address the victim's system believes is unowned/reserved.
- Cause dApps that verify user deposits/interactions against an externally-predicted CREATE2 address (computed with the standard `0xff`/`0x41` prefix) to never match the real, funded/controlled contract, leading to contract-identity confusion and potential misdirected fund flows for any protocol porting standard CREATE2-prediction patterns to TRON without adjustment.

### Likelihood Explanation
Fully feasible and deterministic: any unprivileged account can trigger `CREATE2` through a normal `TriggerSmartContract` call; the divergence occurs on every single CREATE2 invocation, not merely for the attacker's own crafted salts, and is 100% reproducible, since `WalletUtil.generateContractAddress2` unconditionally omits the prefix regardless of network-upgrade flags.

### Recommendation
Align `WalletUtil.generateContractAddress2` with a single, explicitly documented, versioned formula and prepend the same single prefix byte that `tron-solc`-generated Solidity code assumes when performing on-chain CREATE2 address prediction (or clearly document/enforce that TRON diverges from the EVM reference and update all official SDKs/tooling to match), so the TVM opcode's derivation and any on-chain/off-chain "predicted-address" computation are provably identical.

### Proof of Concept
Extend `Create2Test.java`'s pattern:
1. Deploy a factory contract containing a Solidity `get(bytes1 prefix, bytes code, uint256 salt)` function that computes `keccak256(abi.encodePacked(prefix, address(this), salt, keccak256(code)))` (as in the commented-out contract `A` in `Create2Test.java`).
2. Deploy a second contract via `CREATE2` from the same factory with identical `salt`/`code`.
3. Assert that the actual deployed address (`convertToTronAddress` of the `CREATE2` return value) differs from `get(0xff, code, salt)` (standard EVM reference) for all fuzzed `salt`/`code` pairs — proving the on-chain reference-style prediction never matches the real TVM-derived address.
4. Additionally assert it also differs from `get(0x41, code, salt)` unless `WalletUtil.generateContractAddress2` is patched to prepend `0x41`, confirming the current implementation matches neither the EVM standard nor TRON's own compiler-assumed prefix.

    //   address = keccak256(prefix ++ sender[20] ++ salt[32] ++ keccak256(code)[32])[12:]
    //
    // - Standard EVM uses 0xff as prefix (magic byte)
    // - TRON replaces it with the address prefix byte (0x41 for mainnet, 0xa0 for testnet)
    // - This value is hardcoded at compile time by tron-solc

    function getCreate2Addr(uint256 salt) public view returns (address) {
        bytes memory bytecode = type(FreezeContract).creationCode;
        bytes32 hash = keccak256(

                bytes1(0x41),       // TRON mainnet address prefix
                address(this),      // 20-byte factory address
                salt,               // 32-byte salt
                keccak256(bytecode) // 32-byte code hash
            )
        );
        return address(uint160(uint256(hash)));
    }
