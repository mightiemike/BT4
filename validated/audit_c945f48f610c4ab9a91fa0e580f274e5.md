### Title
Function-call access key `allowance` cap can be exceeded across pending (uncertified) SPICE chunks - ([File: runtime/runtime/src/verifier.rs])

### Summary
The SPICE pending-transaction-queue mechanism tracks a signer's committed *balance* and *gas-key* spend across chunks that have been included but not yet certified, and feeds that into the ephemeral transaction verifier via `PendingConstraints`. However it never tracks the *allowance* already consumed by other pending, uncertified transactions signed with the same `FunctionCallPermission` access key. Because the allowance check is computed purely from the on-chain `AccessKey.permission.allowance` value with no pending-consumption offset, several transactions signed by the same restricted access key can each independently pass the allowance check inside the same window of uncertified chunks, letting the holder of that key spend up to the full account balance even though the key was explicitly capped to a much smaller `allowance`.

### Finding Description
`PendingConstraints`, which is threaded through the ephemeral verification path, only carries balance- and gas-key-oriented fields: [1](#0-0) 

`verify_and_charge_tx_ephemeral` uses `pending.paid_from_balance` to correctly cap the account's *total* balance across pending chunks: [2](#0-1) 

but the `FunctionCallPermission.allowance` check that follows is computed with `check_and_compute_new_allowance`, which takes only the access key and the current transaction's cost — no pending-queue state at all: [3](#0-2) [4](#0-3) 

The `PendingTxSession` used by chunk production explicitly documents that it only tracks what the balance-based ephemeral state does *not* cover — P_MAX/deploy-exclusivity counts and `WithdrawFromGasKey` amounts — with no mention of `FunctionCallPermission.allowance`: [5](#0-4) [6](#0-5) 

This is the SPICE-only path (multiple already-included-but-not-yet-certified chunks can be outstanding at once) reached from `prepare_transactions` / `chunk_producer.rs`: [7](#0-6) 

Because `FunctionCallPermission.allowance` is documented as decreasing in lockstep with account balance ("both account balance and the allowance is decreased by the same value"): [8](#0-7) 

...the intended security property is that the *key* cannot ever move more than `allowance` regardless of how large the underlying account balance is. Since `paid_from_balance` bounds only the account's total balance and not the key's allowance ledger, an attacker holding a restricted function-call key (e.g., a leaked or intentionally-limited dapp/session key) can submit many transactions in parallel across the pending, uncertified-chunk window; each is validated against the *stale, not-yet-decremented* on-chain `allowance` value (because no earlier pending transaction's consumption has been written back to trie or reflected in `PendingConstraints`), so all of them pass the allowance check independently. The only real ceiling left is the account's total balance, not the restricted key's allowance — a direct bypass of an access-control boundary that results in unauthorized spend of funds beyond what the key's permission was designed to authorize.

### Impact Explanation
This breaks a core access-key security guarantee: a `FunctionCallPermission` key with a bounded `allowance` is meant to strictly cap the value that key can move/spend, independent of the account's actual balance (this is the whole purpose of `allowance` vs. relying on account balance). Under SPICE with multiple outstanding uncertified chunks, that cap can be bypassed up to the full account balance, i.e., unauthorized value movement by an under-privileged signer beyond its granted permission. This is a High severity access-control/fee-cap bypass, matching CVE-2016-10026's bug class (a permission check evaluated against state that does not reflect concurrently pending changes, allowing the restriction to be reverted/bypassed).

### Likelihood Explanation
Requires: (1) SPICE enabled (`ProtocolFeature::Spice`), (2) the pending transaction queue with multiple uncertified chunks outstanding for the same shard, and (3) an account holding a `FunctionCallPermission` access key with a set `allowance`. Any holder of such a restricted key — the intended threat model for these keys (e.g., a limited-scope dapp/session key) — can trigger this purely by submitting several ordinary transactions signed with that key in quick succession; no special validator, network, or node-compromise access is required.

### Recommendation
Add a `paid_from_allowance` (or per-key allowance-consumption) field to `PendingConstraints`/`ShardedPendingTransactionQueue`, populate it the same way `paid_from_balance`/`paid_from_gas_key` are populated for pending, uncertified chunks, and subtract it from `access_key.permission.allowance` inside `check_and_compute_new_allowance` (or an equivalent pending-aware call site) before accepting a `FunctionCall`-permissioned transaction.

### Proof of Concept
1. Enable SPICE and create an account with a `FunctionCallPermission` access key with `allowance = X` and large account balance `B >> X`.
2. Ensure multiple chunks referencing this shard are included but not yet certified (normal SPICE pipeline behavior under load).
3. Submit `k` transactions signed by that key, each with cost `~X`, spread across the pending/uncertified chunk window before certification catches up.
4. Because `PendingConstraints` carries no allowance-consumption tracking, `check_and_compute_new_allowance` in `runtime/runtime/src/verifier.rs` re-reads the same unconsumed `allowance = X` for each transaction and each one is admitted, letting the key spend up to `k*X` (bounded only by `B`), exceeding its intended `X` cap.

```rust
fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
```
