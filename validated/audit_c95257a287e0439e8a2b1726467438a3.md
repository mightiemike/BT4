### Title
Receipt `max_receipt_size` Invariant Bypass via Post-Validation `output_data_receivers` Mutation — (`runtime/runtime/src/lib.rs`)

### Summary

The nearcore runtime validates newly-created receipts against `max_receipt_size` immediately after each action executes, but then unconditionally appends `output_data_receivers` entries to a receipt returned via `promise_return` in a separate, post-action-loop step. This post-validation mutation can push the receipt's serialized size above `max_receipt_size`, bypassing the size invariant. The oversized receipt is stored in state, forwarded cross-shard, and the congestion-control layer silently clamps its reported size to `max_receipt_size` for accounting, causing the system to undercount actual bytes in flight.

### Finding Description

**Validation step (inside the action loop):**

In `runtime/runtime/src/lib.rs`, after each action executes, every new receipt it produced is checked against `max_receipt_size` using `ValidateReceiptMode::NewReceipt`: [1](#0-0) 

**Post-validation mutation (after the action loop):**

After the loop completes, if the executed receipt's result is `ReturnData::ReceiptIndex` (i.e., the contract called `promise_return`), the runtime extends the returned receipt's `output_data_receivers` with the parent receipt's own `output_data_receivers`: [2](#0-1) 

This mutation happens **after** the size check. A contract can craft a receipt whose serialized size equals exactly `max_receipt_size` (4,194,304 bytes), pass validation, and then have one or more `DataReceiver` entries appended, pushing the final size above the limit.

A second path exists in `ReceiptManager::create_action_receipt`, which pushes `DataReceiver` entries onto existing receipts when building promise DAGs: [3](#0-2) 

**Congestion-control workaround (masking the impact):**

The `try_forward` function in `congestion_control.rs` explicitly clamps any oversized receipt's reported size to `max_receipt_size` before deducting from outgoing limits: [4](#0-3) 

This means the congestion-control layer underestimates actual bytes in flight for every oversized receipt, allowing more data to cross shard boundaries than the configured limits permit.

**Existing acknowledgement:**

The `ValidateReceiptMode::ExistingReceipt` variant was added specifically because the bug allows receipts above the limit to reach state, and the runtime must tolerate them: [5](#0-4) 

The bug is tracked as [nearcore#12606](https://github.com/near/nearcore/issues/12606) and is confirmed by the test: [6](#0-5) 

### Impact Explanation

| Invariant broken | Effect |
|---|---|
| `max_receipt_size` (4,194,304 bytes) | Oversized receipts stored in trie state and forwarded cross-shard |
| Congestion-control byte accounting | Actual bytes in flight exceed the configured `max_outgoing_gas`/size limits because the clamping workaround under-reports receipt size |
| `ExistingReceipt` tolerance path | Runtime must permanently carry dead-code to handle receipts that should never have been created |

The congestion-control bypass is the material impact: an attacker who can repeatedly trigger oversized receipts can cause a target shard to receive more data per block than its configured bandwidth limit, degrading throughput for all users of that shard. This is a non-network-level DoS fixable without a hardfork (by re-validating after mutation).

### Likelihood Explanation

Any account holder can deploy a contract (normal NEAR user action, no special privilege). The exploit requires:
1. Deploy a contract that generates a receipt whose serialized size is exactly `max_receipt_size - sizeof(one DataReceiver entry)`.
2. Call the contract in a promise DAG so that `promise_return` causes `output_data_receivers` to be appended after validation.

The existing test `test_max_receipt_size_promise_return` demonstrates this path end-to-end and asserts that an oversized receipt does appear on-chain.

### Recommendation

Re-validate the receipt size **after** appending `output_data_receivers` in the post-action-loop block (`lib.rs` lines 1019–1037). Concretely:

```rust
// After extend_from_slice, re-check size:
if let Err(e) = validate_receipt(
    &apply_state.config.wasm_config.limit_config,
    &result.new_receipts[receipt_index as usize],
    apply_state.current_protocol_version,
    ValidateReceiptMode::NewReceipt,
) {
    result.result = Err(ActionErrorKind::NewReceiptValidationError(e).into());
}
```

Apply the same guard in `ReceiptManager::create_action_receipt` after pushing to `output_data_receivers`. Once the bug is fixed, the `ExistingReceipt` tolerance mode and the size-clamping workaround in `try_forward` can be removed.

### Proof of Concept

1. Compute `args_size = max_receipt_size - borsh_size(base_action_receipt_template)` (exactly as the existing test does at line 177).
2. Deploy a contract implementing `max_receipt_size_promise_return_method1` that creates a receipt of that size and calls `promise_return`.
3. Call the method inside a promise DAG `[A -then-> B]` so that when A executes, its `output_data_receivers` (pointing to B) are appended to the returned receipt C.
4. Observe that the outgoing receipt for C has `borsh_size > 4_194_304`.
5. Observe that `congestion_control::try_forward` logs `"try_forward observed a receipt with size exceeding the size limit"` and clamps the size, confirming the accounting bypass.

The test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` already reproduces this and asserts `assert_oversized_receipt_occurred`. [7](#0-6)

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
