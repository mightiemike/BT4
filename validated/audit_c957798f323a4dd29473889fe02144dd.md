This is a strong analog. The Gearbox bug is: a critical "master" resource/account is left in a default/uninitialized state, and anyone can perform an action that establishes control over it before the intended initialization path runs. The `HistoryBlockHashUtil.deploy()` code has exactly this pattern for a "system" address in java-tron: an EOA-owned account can pre-occupy the canonical TIP-2935 storage address before the proposal activates, and `deploy()` explicitly documents that it will "upgrade" that account in place rather than reject it — but it does not clear the pre-existing account's balance/asset state, and, more importantly, it does not clear the account's **permissions**. If an attacker sends TRX to `HISTORY_STORAGE_ADDRESS` before the TIP-2935 proposal activates, the account is created as a normal `AccountCapsule` with the attacker able to have previously set an `AccountPermissionUpdateContract` owner/active permission on it (since `CreateAccountActuator`/`TransferActuator` auto-create accounts with default owner permission equal to the address itself, and multisig permissions can be layered on any existing account address). When `deploy()` runs, it only calls `updateAccountType(Contract)` and `clearDelegatedResource()` — it does **not** reset `ownerPermission`/`activePermission`, so any permission structure the attacker set up beforehand survives the "contractification" of the address.

### Title
Pre-registered account permissions survive `HistoryBlockHashUtil.deploy()` account-type upgrade, letting an attacker retain control over the TIP-2935 system contract address - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` is the java-tron analog of Gearbox's uninitialized `masterCreditAccount`: a privileged, protocol-critical address (`HISTORY_STORAGE_ADDRESS`, the TIP-2935 `BlockHashHistory` system contract slot) can be "claimed" by an ordinary user transaction before the code that is supposed to establish it as a system contract ever runs, and that pre-existing state (including account permissions) is not cleared when the system finally installs itself there.

### Finding Description
`deploy()` is only invoked once, from `ProposalService` at proposal activation [1](#0-0) . Before that activation block, `HISTORY_STORAGE_ADDRESS` is a completely ordinary address that any unprivileged user can populate by simply sending it TRX or TRC10 via `TransferActuator`/`TransferAssetActuator`, which auto-creates a `Normal` `AccountCapsule` at that address with a default owner permission for the address itself when multisig is enabled [2](#0-1) . Once the account exists, `AccountPermissionUpdateActuator` lets its owner set arbitrary multisig owner/active permissions on it [3](#0-2) .

When `deploy()` eventually runs and finds a pre-existing account at the canonical address, it deliberately preserves that account's state rather than replacing it, only flipping its type to `Contract` and clearing delegated resources: [4](#0-3) . Nothing in this path resets `ownerPermission`/`activePermission`/`witnessPermission` on the capsule. This mirrors the Gearbox pattern precisely: a state variable/slot meant to be established exclusively by protocol logic is left reachable and "claimable" by any account/transaction beforehand, and the eventual initialization does not forcibly reset attacker-controlled state.

### Impact Explanation
If an attacker predicts (or copies from the reference implementation/EIP-2935 spec) the fixed `HISTORY_STORAGE_ADDRESS`, they can, prior to the TIP-2935 activation block, create an account there and set a self-controlled multisig owner permission on it. After `deploy()` runs, the account is marked `Contract` type and gets the `BlockHashHistory` bytecode/`ContractCapsule` installed, but the underlying `AccountCapsule`'s permission fields are untouched — the attacker's owner permission remains valid on what is now a system contract's account. This is a moderate integrity concern for the system-contract-account model (e.g., any TRX/TRC10 balance already at that address, and any semantics that key off account permissions rather than purely the `ContractStore`, remain attacker-influenced) though the VM code execution itself is fixed bytecode and not affected by account permissions.

### Likelihood Explanation
The precondition (attacker front-running the fixed, publicly-known deploy address before the corresponding proposal activates) is straightforward and requires no privileged access — anyone can send a `TransferContract` to that address and, if multisig is enabled network-wide, an `AccountPermissionUpdateContract` to set permissions on it, both being ordinary unprivileged broadcast transactions.

### Recommendation
In `HistoryBlockHashUtil.deploy()`, when a pre-existing account is found at `HISTORY_STORAGE_ADDRESS`, explicitly reset/clear its owner/active/witness permissions (and any other mutable account fields not intended to persist) in addition to `updateAccountType` and `clearDelegatedResource`, so no pre-registered attacker-controlled permission state can survive the transition to a system contract account.

### Proof of Concept
1. Before the TIP-2935 proposal is activated (`AllowTvmPrague`/related flag not yet set), broadcast a `TransferContract` sending any amount of TRX to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`). This auto-creates a `Normal` account there via `TransferActuator`.
2. If multisig (`AllowMultiSign`) is enabled, broadcast an `AccountPermissionUpdateContract` from that address setting an owner permission controlled by the attacker's own key(s) via `AccountPermissionUpdateActuator`.
3. Wait for the network to reach the maintenance block that activates the TIP-2935 proposal, triggering `ProposalService` → `HistoryBlockHashUtil.deploy(manager)`.
4. Observe that `deploy()` takes the "pre-existing account" branch [4](#0-3) , only updating `accountType` and clearing delegated resources — the attacker-set owner permission from step 2 remains stored on the account and is never reset.
