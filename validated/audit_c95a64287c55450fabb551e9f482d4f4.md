### Title
Lost-update on self-matched maker/taker orders causes silent loss of maker-side credit - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Finding Description
`execute()` loads the taker's account once into `accountCapsule` [1](#0-0)  and keeps mutating this single in-memory object throughout the call (fee deduction, sell-side transfer, and later the taker-side credit via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)`), and finally persists it with `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` [2](#0-1) .

However, the maker-side credit is applied by a *different* overload of `addTrxOrToken(MarketOrderCapsule, long)` [3](#0-2)  which independently does `accountStore.get(orderCapsule.getOwnerAddress()...)`, mutates that *separate* `AccountCapsule` instance, and immediately `accountStore.put()`s it — bypassing the in-memory `takerAccountCapsule`/`accountCapsule` object entirely.

If the resting maker order and the incoming taker order share the same `ownerAddress` (a self-match, trivially achievable since nothing in `matchOrder()`/`matchSingleOrder()`/`validate()` prevents an address from trading against its own resting order), both code paths operate on the *same physical account row* but on two different in-memory `AccountCapsule` objects:
1. `matchSingleOrder()` calls `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` at line 490, which fetches a fresh copy of the account, credits it, and persists it via `accountStore.put()` (lines 550-561).
2. Control returns to `execute()`, which later persists the *original* `accountCapsule` object (line 148) — an object that never received the maker-side credit applied in step 1 (only the taker-side credit from the other `addTrxOrToken` overload at line 489).
3. This final `accountStore.put()` at line 148 overwrites the DB row written in step 1, silently discarding the maker-side credit.

No code path re-reads the account or merges the two credit operations, so this is a genuine lost-update/stale-read issue rooted in inconsistent state management (two separate `AccountCapsule` instances backing the same DB key within one actuator execution).

### Impact Explanation
When an address places an order that matches against its own resting order, the maker-side buy-token/TRX credit computed and persisted at line 490/561 is overwritten and lost when `execute()` writes back its stale `accountCapsule` at line 148. The account's sell-side deduction (for both roles) and taker-side credit still apply, but the maker-side credit vanishes — the user's assets are effectively burned/lost from their own account, corrupting balance accounting for that account.

### Likelihood Explanation
The only precondition is that the same address has a resting maker order and later submits a taker order that matches it in the same pair/price — fully controllable by any unprivileged user via ordinary `MarketSellAssetContract` transactions and requires no special privileges, colluding party, or race condition; a single account can construct this deterministically and repeatably.

### Recommendation
Ensure a single consistent `AccountCapsule` instance is used for both maker and taker credit operations, or re-fetch the taker's account immediately before the final `accountStore.put()` in `execute()` after all matching side-effects have committed. Concretely, change `addTrxOrToken(MarketOrderCapsule, long)` to accept and reuse an already-loaded `AccountCapsule` when its owner address equals the taker's, or restructure `matchOrder`/`matchSingleOrder` to always look up accounts through a single per-transaction cache keyed by address, flushing all mutations to the store exactly once per account at the end of `execute()`.

### Proof of Concept
Java integration test outline for `MarketSellAssetActuatorTest`:
1. Create `OWNER_ADDRESS_FIRST` account with balance/assets for both `sellTokenID`/`buyTokenID`.
2. Submit a `MarketSellAssetContract` from `OWNER_ADDRESS_FIRST` (order A) that becomes a resting maker order (partially or fully unmatched), causing `saveRemainOrder` to store it in the order book.
3. Submit a second `MarketSellAssetContract`, also from `OWNER_ADDRESS_FIRST`, with sell/buy tokens/price such that it matches against order A as taker.
4. Execute the second actuator's `execute()`.
5. Assert: final `accountStore.get(OWNER_ADDRESS_FIRST).getBalance()` (or asset balance for `buyTokenID`) equals `initialBalance - fee - sellTokenQuantity(taker) + takerBuyTokenQuantityReceive + makerBuyTokenQuantityReceive`.
6. Expected (buggy) result: the assertion fails because the persisted balance is missing `makerBuyTokenQuantityReceive`, since it was overwritten by the stale taker-side `accountCapsule` write at execute() line 148.
