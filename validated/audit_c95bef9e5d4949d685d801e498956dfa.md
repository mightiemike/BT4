### Title
Non-atomic partial state commits during order matching allow `MarketSellAssetActuator` to persist maker-side balance/order mutations even when the taker transaction ultimately fails - (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The GMX finding centers on a fee/value transfer being attempted without first verifying sufficient funds are available, so a downstream failure reverts a transaction after the contract has already mutated its state, leaving that state incorrectly handled. The closest analog in java-tron is in `MarketSellAssetActuator`, where order-matching logic writes maker account and maker order state directly to the underlying stores **inside** the matching loop, before the taker-side transaction as a whole has fully succeeded. If a later step in the same `execute()` call throws (e.g. the `MAX_MATCH_NUM` guard), the transaction is marked `FAILED`, but the already-executed `accountStore.put()`/`orderStore.put()` calls for prior matched makers are not part of an in-memory, all-or-nothing capsule swap the way other actuators (e.g. `ExchangeInjectActuator`) are structured.

### Finding Description
In `MarketSellAssetActuator.execute()` [1](#0-0) , the flow is: deduct fee, transfer sell balance/token, create and save the taker order, then call `matchOrder()`, and only at the very end call `orderStore.put()`/`accountStore.put()` for the taker.

Inside `matchOrder()` → `matchSingleOrder()`, for every matched maker order the code calls `orderStore.put(makerOrderCapsule...)` [2](#0-1)  and `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)`, which itself calls `accountStore.put(orderCapsule.getOwnerAddress()...)` directly [3](#0-2) . These writes happen immediately for each matched maker, not deferred to the end of `execute()`.

The matching loop enforces a match-count cap and throws `ContractValidateException("Too many matches...")` once `matchOrderCount > MAX_MATCH_NUM` [4](#0-3) . This exception propagates up and is caught by the outer `try/catch` in `execute()`, which sets `ret.setStatus(fee, code.FAILED)` and re-throws `ContractExeException` [5](#0-4) .

By contrast, other actuators such as `ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator` mutate only in-memory capsule objects (`exchangeCapsule.setBalance(...)`, `accountCapsule.setBalance(...)`) and defer all `accountStore.put()`/`Commons.putExchangeCapsule()` calls to the very end of the method, after all fallible arithmetic (`subtractExact`, `addExact`) has succeeded [6](#0-5) . This "compute everything first, persist last" pattern is the safe design that avoids the GMX-style bug (a fallible step happening after state has already been partially externalized). `MarketSellAssetActuator`'s maker-side updates break that pattern by writing to the stores speculatively during a loop that can still fail.

Root cause: `matchOrder()`/`matchSingleOrder()` persist mutated maker `AccountCapsule` and `MarketOrderCapsule` objects to their respective stores mid-loop, before the overall taker transaction is known to succeed, mirroring the GMX pattern of performing a value-affecting action before confirming the operation as a whole can complete safely.

### Impact Explanation
If the whole `MarketSellAssetContract` transaction ultimately fails (via the `MAX_MATCH_NUM` guard, or any other exception raised after some makers have already been fully matched and persisted), the transaction result is reported as `FAILED` to callers/explorers, yet the maker accounts' balances/token amounts and the affected `MarketOrderCapsule`/`MarketOrderIdListCapsule` states have already been durably written to the account/order stores for that block. This produces a divergence between the reported transaction outcome and actual on-chain state: makers whose orders were consumed have had funds credited and their orders marked filled/removed, while the taker side (whose changes are only persisted at the end of `execute()`) is never updated, resulting in inconsistent bookkeeping between maker and taker sides of the same failed trade. This is analogous to the GMX issue where a mid-flow failure left protocol state incorrectly reconciled and value effectively unaccounted for.

### Likelihood Explanation
Reaching the `MAX_MATCH_NUM` throw path requires an attacker (or any regular trader) to construct a sell order that matches against more than `MAX_MATCH_NUM` (20) existing maker orders in the order book, which is achievable by any unprivileged user seeding many small maker orders and then submitting a matching taker order. This is a realistic, unprivileged, reachable path through the public `MarketSellAssetContract` trading flow, not a purely theoretical or trusted-role scenario.

### Recommendation
Refactor `matchOrder()`/`matchSingleOrder()` (and `addTrxOrToken(MarketOrderCapsule, long)` used for makers) to only mutate in-memory capsules during the matching loop, and defer all `accountStore.put()` and `orderStore.put()` calls for maker-side state until after the entire match/loop process (including the `MAX_MATCH_NUM` check) has completed successfully, mirroring the pattern already used in the `Exchange*Actuator` classes. Alternatively, perform the `MAX_MATCH_NUM` bound check before persisting any maker state changes, so a limit violation cannot occur after partial state has already been committed.

### Proof of Concept
1. Create more than `MAX_MATCH_NUM` (20) small maker sell orders (e.g., sell token A for token B) at prices such that they all can match a single incoming taker order.
2. Submit a `MarketSellAssetContract` (taker order) selling token B for token A, sized so it would match all of the above makers, exceeding `MAX_MATCH_NUM` in one execution of `matchOrder()`.
3. Observe that on the 21st match, `matchOrderCount > MAX_MATCH_NUM` triggers `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")` [4](#0-3) , which is caught in `execute()` and the transaction is marked `FAILED`.
4. Inspect the `MarketOrderStore`/`AccountStore` for the first 20 matched makers — their orders will show `sellTokenQuantityRemain == 0` (or reduced) and their accounts will show increased balances/token amounts from `addTrxOrToken`, even though the overall transaction result is `FAILED` and the taker's own order/account was never persisted.
