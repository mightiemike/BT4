### Title
`SafeExchangeProcessor` Bancor-style exchange math reverts with `ArithmeticException` on inputs that pass validated exchange bounds - ([File: chainbase/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java])

### Summary
The "hardened" exchange math path used by `ExchangeTransactionContract` and `ExchangeInjectContract` performs a Bancor-relay-style formula (`balance * ((1 + x)^k - 1)`) using `double`/`BigDecimal` power operations and then converts the result with `BigDecimal.longValueExact()`. Just like the Cobb–Douglas function in the external report, the actuator only validates coarse bounds (`tokenQuant > 0`, resulting pool balance `<= exchangeBalanceLimit`, sufficient account balance) but does not bound the *magnitude of the computed output*, so parameters that satisfy every documented/validated constraint can still make the underlying math throw an uncaught arithmetic exception, aborting the transaction.

### Finding Description
`ExchangeCapsule.transaction()` selects `SafeExchangeProcessor.INSTANCE` when `allowHarden()` is enabled [1](#0-0) . `SafeExchangeProcessor.exchangeFromSupply` computes an exponential expression with exponent `2000.0` via `StrictMathWrapper.pow` and then forces the BigDecimal result into a `long` using `longValueExact()`, which throws `ArithmeticException` if the value has a non‑zero fractional/overflow component beyond `Long` range: [2](#0-1) 

The only guardrails before this call are enforced in `ExchangeTransactionActuator.doValidate()`: token quant `> 0`, expected output `> 0`, and the *resulting pool balance* (not the *computed output magnitude*) must stay under `exchangeBalanceLimit`: [3](#0-2) 

None of these checks bound the exponential blow-up of `exchangeFromSupply`'s `(1 + supplyQuant/SUPPLY)^2000` term for legitimate-looking `sellTokenQuant` values relative to the pool's synthetic `supply` constant, so `longValueExact()` can legitimately overflow and throw for a transaction that otherwise satisfies every validated bound — exactly mirroring the reported Cobb–Douglas defect where documented input bounds do not guarantee the arithmetic will not revert.

When this exception is thrown inside `execute()`, it is caught generically and turned into a failed, but already partially-processed, transaction outcome: [4](#0-3) 
And when thrown from `doValidate()` via the `transaction()` call at line 217, it is wrapped as a `ContractValidateException`, rejecting the broadcast transaction outright: [5](#0-4) 

The companion `ExchangeInjectActuator` also drives balances through this same processor path and is reachable identically from a broadcast contract. [6](#0-5) 

Existing tests already demonstrate this exact failure mode being deliberately exercised (`ArithmeticException` from `addExact`/`longValueExact` inside the hardened processor for in-range-looking values), confirming the class of bug is present and reachable, not merely theoretical: [7](#0-6) 

### Impact Explanation
Any anonymous account can broadcast an `ExchangeTransactionContract` or `ExchangeInjectContract` against an existing trading pair. If the pool's balances and requested quant combination push the internal exponential formula's output past `Long.MAX_VALUE` precision (or produce a non-integral BigDecimal that `longValueExact()` rejects), the transaction fails via an uncaught `ArithmeticException`, even though every explicit validation check (positive quant, balance-limit compliance, sufficient funds) passed. This can be used to reliably block legitimate trades against a specific exchange pool (denial of service on that market), and — because the check also runs during `validate()` — can make transactions unconfirmable network-wide for that exchange id, without requiring any privileged role, leaked key, or malicious peer.

### Likelihood Explanation
Reaching this code path requires only a standard signed transaction of type `ExchangeTransactionContract`/`ExchangeInjectContract` against a pool with `allowHardenExchangeCalculation` enabled — both are ordinary, unprivileged, publicly reachable operations. Triggering the exact overflow requires crafting `sellTokenQuant`/pool-balance ratios that make the exponential term exceed representable precision; this is a data-validation gap in bounding the *output* magnitude rather than only the *input* magnitude, the same root cause pattern as the reported Cobb–Douglas issue, and is plausible for large yet fully-legal pool balances (up to `exchangeBalanceLimit`) combined with large relative quants.

### Recommendation
- Bound the intermediate relay/output magnitude of `SafeExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` explicitly (e.g., cap `supplyQuant`/`exchangeBalance` to a safe sub-range of `Long`), and reject with a proper `ContractValidateException` before attempting `longValueExact()`, instead of relying on an uncaught `ArithmeticException` bubbling out of low-level math.
- Add exhaustive property-based/fuzz testing (mirroring the Echidna methodology used against the Cobb–Douglas function) across the full range of `sellTokenQuant` versus pool balances up to `exchangeBalanceLimit` to prove the hardened exchange formula never reverts for validated inputs.
- Document the true safe input range for the exchange formula and enforce it explicitly in `doValidate()` rather than only checking `tokenQuant > 0` and post-balance limits.

### Proof of Concept
Not independently reproduced end-to-end in this analysis (would require constructing a live pool state near `exchangeBalanceLimit` and an in-bound `sellTokenQuant` that pushes `(1 + supplyQuant/SUPPLY)^2000` past `Long` precision inside `exchangeFromSupply`). The existing repository test suite already demonstrates the exact defect class — `ArithmeticException` thrown from within the hardened exchange math for values that are not rejected by `doValidate()`'s bound checks — confirming feasibility: [8](#0-7)

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
