### Title
Attacker-controlled MessageId collision in gateway capabilities handler allows cross-request response hijack - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores the caller's `handlers.Callback` in `h.savedCallbacks` keyed solely by the attacker/user-supplied `msg.Body.MessageId`, with no per-sender namespacing. Any unprivileged caller who can predict or brute-force a `MessageId` used by another in-flight `web_api_trigger` request can submit a second, independently-signed request with the same `MessageId`, overwriting the victim's saved callback so that the eventual node response (matched only by `MessageId` in `handleWebAPITriggerMessage`) is delivered to the attacker instead.

### Finding Description
`MessageId` is an entirely caller-chosen field of `api.MessageBody` [1](#0-0) . `Message.Validate()` only checks length/format constraints and derives `Sender` from the ECDSA signature — it never binds `MessageId` uniqueness to the sender [2](#0-1) . Any account holding a valid ECDSA key (no special privilege) can sign a `web_api_trigger` message with an arbitrary `MessageId`.

In `handler.HandleLegacyUserMessage`, after validation, the callback is stored unconditionally:
```
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [3](#0-2) 
There is no check for an existing entry at that key — a second request with the same `MessageId` silently overwrites the first caller's callback (map assignment, not `map[key]==nil` guarded insert).

When the DON node responds, `handler.HandleNodeMessage` routes solely by `msg.Body.Method` and `MethodWebAPITrigger` dispatches to `handleWebAPITriggerMessage`, which pops and delivers **whatever callback is currently stored** under that `MessageId`, with no verification that it corresponds to the original request's sender, DonId binding, or any nonce/session tie:
```
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [4](#0-3) 

The gateway entry point `gateway.ProcessRequest` also does not enforce cross-request uniqueness of `MessageId`; it validates the message and calls `HandleLegacyUserMessage` per request without any dedupe/anti-collision check [5](#0-4) . Thus if an attacker's `HandleLegacyUserMessage(msg2, cb2)` call with `msg2.Body.MessageId == msg1.Body.MessageId` lands after the victim's request has been saved but before the node responds, `cb1` is overwritten by `cb2`, and the eventual node response is delivered to the attacker's callback (`cb2`) instead of the victim's (`cb1`).

### Impact Explanation
This is a cross-request response hijack: an unprivileged attacker can obtain the plaintext response payload intended for another user's `web_api_trigger` request, and the legitimate requester's HTTP call to the gateway will time out (`RequestTimeoutError`) instead of receiving its own response. This corresponds to information disclosure and integrity breakage of the gateway's request/response contract for the workflow HTTP trigger capability — the impact depends on what data the `web_api_trigger` payload carries (which can include secrets/results relayed from DON node execution).

### Likelihood Explanation
Exploitability requires (a) the attacker to guess/brute-force the `MessageId` in use by another in-flight request, and (b) timing the attacker's request to land within the narrow window between the victim's request being saved and the node's response arriving (bounded by node/network latency, typically sub-second to a few seconds, and further bounded by `CallbackMaxAgeSec`, default 120s). If `MessageId`s are generated by legitimate clients using low-entropy or predictable schemes (e.g., sequential counters, timestamps), collision is trivial; if generated with high-entropy random values (e.g., UUIDv4), brute-forcing within the response window is infeasible. The code itself imposes no minimum entropy or uniqueness requirement on `MessageId`, so the practical likelihood depends entirely on caller-side ID generation practices, which are out of this handler's control — but the handler provides no defense-in-depth against this scenario despite being the last line of authorization before response delivery.

### Recommendation
Bind `savedCallbacks` entries to the requester's identity in addition to `MessageId` (e.g., key by `(Sender, MessageId)` or a value derived from the signed message, since `msg.Body.Sender` is set by `Validate()` from the ECDSA signature). Alternatively, reject `HandleLegacyUserMessage` calls when `msg.Body.MessageId` already exists in `savedCallbacks` (return a collision error) rather than silently overwriting. Additionally, verify on response delivery that the responding node's message matches the original request's `Sender`/`DonId` context stored alongside the callback, not just the raw `MessageId`.

### Proof of Concept
Integration test in `core/services/gateway/handlers/capabilities` package:
1. Create a `handler` with a `handlers.DON` mock.
2. Sign `msg1` (`MethodWebAPITrigger`, `MessageId = "X"`) with key A, and `msg2` (`MethodWebAPITrigger`, `MessageId = "X"`) with key B.
3. Call `h.HandleLegacyUserMessage(ctx, msg1, cb1)` then, before any node response arrives, call `h.HandleLegacyUserMessage(ctx, msg2, cb2)`.
4. Assert `h.savedCallbacks["X"].Callback == cb2` (overwritten), not `cb1`.
5. Simulate node response via `h.HandleNodeMessage` with `MessageId = "X"`; assert `cb2.Wait()` receives the response and `cb1.Wait()` times out — demonstrating the response intended for the first caller is delivered to the second (attacker) instead.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
