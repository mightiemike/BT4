### Title
Storage account-count underflow triggers unrecoverable panic in `AccountStorageEntry::remove_accounts` - (File: accounts-db/src/account_storage_entry.rs)

### Summary
`AccountStorageEntry::remove_accounts` mirrors the GaugeController pattern exactly: an atomic counter (`num_alive_accounts`/`num_alive_bytes`) is decremented via `fetch_sub` using a delta computed by a *caller-supplied* reclaim/removal batch, and only *after* the subtraction does the code assert that the delta did not exceed the previous value. Just like `pt.slope -= d_slope` in the GaugeController, if a caller ever supplies a removal delta larger than what is actually still tracked as alive in the storage entry (e.g., because the same account was already counted as removed through a different path), the `fetch_sub` silently wraps and the subsequent `assert!` panics, which is the exact "reset external state, then apply a stale delta computed against the old value" bug class described in the report.

### Finding Description
`remove_accounts` performs the subtraction unconditionally and only validates afterward: [1](#0-0) 

The invariant that callers must never double-count an account's removal is explicitly called out — and explicitly fragile — in `handle_reclaims`'s documentation: [2](#0-1) 

This is the same "it is anticipated that this may happen" signal that the original report used to argue High severity for GaugeController: the code comment states an account "must be unrefed and removed to avoid double counting or missed counting in shrink," which means the correctness of `remove_accounts`'s underflow-free operation depends entirely on every caller maintaining that ordering/uniqueness invariant across `clean_accounts`, `shrink`, and the zero-lamport-single-ref path.

The codebase even documents a concrete scenario where the same account can be independently marked "dead" through two different tracking mechanisms on the same `AccountStorageEntry` — `num_alive_bytes`/`num_alive_accounts` vs. the zero-lamport-single-ref offset set — and acknowledges the double-dead-accounting race directly in the struct's own doc comment: [3](#0-2) 

While the comment above asserts "this should be fine" for that specific double-count instance (since it only makes shrink more eager to visit the storage, it never re-invokes `remove_accounts` on the same offsets twice), the existence of the panic-guarded invariant and the explicit warning in `handle_reclaims` shows that `remove_accounts`'s underflow protection is a hard dependency on subtle cross-module bookkeeping (index unref ordering between `clean`, `shrink`'s zero-lamport-single-ref purge, and obsolete-account marking) rather than a self-contained invariant. The existing regression test demonstrates the exact underflow-then-panic mechanics when the invariant is violated: [4](#0-3) 

### Impact Explanation
If any code path (present or introduced by future changes to shrink/clean/obsolete-marking) ever submits a removal delta for a slot's storage that exceeds its currently tracked alive count/bytes — e.g., because the same offset was reclaimed both via `clean_accounts`'s normal dead-slot-list path and via `remove_zero_lamport_single_ref_accounts_after_shrink`'s `purge_keys_exact` reclaim path for the same underlying storage before the storage is dropped — the atomic `fetch_sub` in `remove_accounts` wraps, and the immediately following `assert!` panics the accounts-db background thread. This crashes the validator process (a genuine node panic), which is the same "gauge becomes permanently unusable" DoS outcome as the reported bug, except here it manifests as a full node crash rather than a locked contract state.

### Likelihood Explanation
This is lower likelihood than the original Solidity finding because Rust's `assert!` converts the underflow into an immediate, loud panic rather than a silently exploitable state, and the current call sites (`remove_dead_accounts`, `store_accounts_for_shrink`, `remove_zero_lamport_single_ref_accounts_after_shrink`) are carefully ordered so that a given account's removal from a specific storage's alive-count is only ever counted once per the current logic. However, the invariant is explicitly documented as caller-maintained rather than structurally enforced ("It must be unrefed and removed to avoid double counting or missed counting in shrink"), meaning any future change to the ordering of clean/shrink/obsolete-marking, or a currently-unrecognized interleaving among the concurrent clean/shrink/obsolete paths, can reintroduce the double-count and panic.

### Recommendation
Harden `remove_accounts` to use `checked_sub` (or `fetch_update`) instead of `fetch_sub` + after-the-fact assert, and, more importantly, make the "already removed/unrefed" invariant structurally enforced (e.g., track removed offsets in a set and reject/no-op duplicate removals) rather than relying purely on caller discipline across the clean/shrink/obsolete-marking code paths, mirroring the report's recommendation to defensively clamp the subtraction instead of assuming it can never underflow.

```rust
    /// Removes `num_bytes` and `num_accounts` from the storage,
    /// and returns the remaining number of accounts.
    pub(crate) fn remove_accounts(&self, num_bytes: usize, num_accounts: usize) -> usize {
        let prev_num_alive_bytes = self.num_alive_bytes.fetch_sub(num_bytes, Ordering::Release);
        let prev_num_alive_accounts = self
            .num_alive_accounts
            .fetch_sub(num_accounts, Ordering::Release);

        // enforce invariant that we're not removing too many bytes or accounts
        assert!(
            num_bytes <= prev_num_alive_bytes && num_accounts <= prev_num_alive_accounts,
            "Too many bytes or accounts removed from storage! slot: {}, id: {}, initial num alive \
             bytes: {prev_num_alive_bytes}, initial num alive accounts: \
             {prev_num_alive_accounts}, num bytes removed: {num_bytes}, num accounts removed: \
             {num_accounts}",
            self.slot,
            self.id,
        );

        // SAFETY: subtraction is safe since we just asserted num_accounts <= prev_num_accounts
        prev_num_alive_accounts - num_accounts
    }
```
