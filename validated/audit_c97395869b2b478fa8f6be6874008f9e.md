### Title
Unprivileged transaction sender can force eviction of another account's pending mempool transaction - (File: `crates/apollo_mempool/src/mempool.rs`)

### Summary
The mempool's capacity-management path lets any incoming transaction, submitted by an unrelated, unprivileged sender, trigger the forced removal ("eviction") of another account's already-admitted, pending transaction from the mempool, with no relationship or authorization check between the two accounts. This mirrors the `RCOrderbook.removeUserFromOrderbook` finding: a state-changing removal action that should be restricted to a legitimate trigger (capacity truly needed, victim actually foreclosable) is instead reachable and steerable by any third party, enabling griefing/censorship of a specific victim's transaction.

### Finding Description
When an incoming transaction would exceed configured mempool capacity, `add_tx_validations` calls `handle_capacity_overflow`, which calls `try_make_space`: [1](#0-0) 

`try_make_space` repeatedly calls `get_evictable_account`, which picks an account at random from `accounts_with_gap` — the set of accounts whose lowest pooled transaction nonce is greater than their known account nonce (i.e., accounts with a "nonce gap") — and evicts (removes) that account's pooled transactions to free space: [2](#0-1) 

Crucially, `get_evictable_account`/`try_make_space` have **no relationship to the incoming transaction's sender**: any account address can be evicted to make room for a completely unrelated transaction from a completely unrelated sender: [3](#0-2) 

This eviction path is reached purely through the ordinary, unprivileged `add_tx` entry point — i.e., any account can submit a transaction (even a cheap, minimal-fee one) to `Mempool::add_tx`, and if the mempool is at capacity, this can force the mempool to evict pooled transactions belonging to any account currently flagged in `accounts_with_gap`: [4](#0-3) [5](#0-4) 

A "gap" account is a normal and common state — it occurs whenever a user has multiple pending transactions and the lowest-nonce one hasn't yet been committed (e.g., it is still awaiting inclusion, was delayed, or is temporarily stuck behind congestion). Tests in the codebase confirm this is treated as an ordinary, frequently-occurring condition (`accounts_with_gap`, `n_stuck_txs`), not an edge case: [6](#0-5) 

Because `get_evictable_account` is a uniform random pick over the (typically small) `accounts_with_gap` set, and eviction removes the account's transactions entirely from the pool, an attacker who observes (via public mempool/API introspection or predictable network conditions) that a specific victim address currently has a nonce gap can flood the mempool with a stream of cheap, unrelated, capacity-overflowing transactions. Each overflowing submission re-triggers `try_make_space`, and — especially when few or only one account is in `accounts_with_gap` — this deterministically or with high probability re-selects and evicts the victim's transaction(s) again as soon as they are resubmitted, before the victim's low-nonce transaction can ever be committed.

### Impact Explanation
This allows an unprivileged attacker to repeatedly and specifically evict/censor a particular victim account's already-accepted mempool transaction(s) by paying only for cheap unrelated transactions of their own. Analogous to the referenced report (front-running a foreclosure-preventing deposit by triggering removal), an attacker here can front-run/outpace a victim's time-sensitive transaction (e.g., a transaction protecting the victim from an on-chain penalty, replay, deadline, or liquidation) by ensuring the victim's pending transaction is perpetually evicted from the mempool rather than reaching the sequencer for inclusion, causing denial of transaction confirmation for that specific account and potential loss tied to the missed transaction. This is reachable purely by an unprivileged transaction sender against the mempool admission logic, matching the required "unauthorized account action" / "network unable to confirm a targeted transaction" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high in a congested mempool: nonce-gapped pending states are common (multi-tx senders, wallets that pre-sign several nonces, or normal network reordering), `accounts_with_gap` is often small, and submitting cheap capacity-filling transactions is inexpensive for an attacker. No special privilege, staking, or protocol role is required — only the ability to submit ordinary transactions, which is the baseline unprivileged capability assumed in scope.

### Recommendation
Decouple eviction eligibility from unrelated third-party submissions: require that eviction targets be chosen based on protocol-level fairness/priority (e.g., lowest fee/tip, oldest inactivity, or self-inflicted overflow) rather than uniformly at random among all currently-gapped accounts regardless of the incoming transaction's origin. At minimum, rate-limit or increase the cost of triggering repeated eviction cycles against the same victim address (e.g., cooldown per evicted address, or requiring a minimum bond/priority delta before an incoming transaction is allowed to evict pooled transactions of an unrelated account), and expose fewer signals (e.g., don't allow easy enumeration of `accounts_with_gap`) that let an attacker target a specific victim.

### Proof of Concept
1. Victim `V` submits transactions at nonce `n+1` (and possibly higher) while nonce `n` is still pending elsewhere/delayed — `V` enters `accounts_with_gap` via `update_accounts_with_gap` (`crates/apollo_mempool/src/mempool.rs:958-990`).
2. Attacker `A` (no relation to `V`) repeatedly submits minimal-fee, unrelated transactions from many/one address(es), each just large enough that `exceeds_capacity` returns true (`crates/apollo_mempool/src/mempool.rs:948-956`).
3. Each such submission enters `handle_capacity_overflow` → `try_make_space` → `get_evictable_account`, which — since `V` is (one of few) entries in `accounts_with_gap` — evicts `V`'s pooled transaction(s) (`crates/apollo_mempool/src/mempool.rs:992-1040`).
4. `V`'s transaction is removed from `tx_pool` and `tx_queue` (`crates/apollo_mempool/src/mempool.rs:1013-1037`), preventing it from ever being selected by `get_txs` for inclusion, even though `V` never received an error and believes their transaction is pending.
5. Repeating step 2 whenever `V` resubmits denies `V`'s transaction inclusion indefinitely, at low, bounded cost to `A`.

    fn add_tx_validations(
        &mut self,
        tx_reference: TransactionReference,
        tx: &InternalRpcTransaction,
        account_nonce: Nonce,
    ) -> MempoolResult<()> {
        self.validate_incoming_tx(tx_reference, account_nonce)?;
        let replaced_tx_reference = self.validate_fee_escalation(tx_reference)?;

        // The replaced transaction is still pooled, so its bytes still count toward
        // `size_in_bytes()`. Credit what its removal will free: a same-size bump nets to zero (no
        // overflow handling), and a larger replacement only needs room for the delta, consistent
        // with how a fresh next-nonce transaction is treated. The removal happens only after
        // capacity is confirmed below, so a rejected incoming transaction never strands the
        // account.
        let freed_bytes = replaced_tx_reference.map_or(0, |reference| {
            self.tx_pool
                .get_by_tx_hash(reference.tx_hash)
                .expect("Replacement target from pool must exist.")
                .total_bytes()
        });

        if self.exceeds_capacity(tx, freed_bytes) {
            self.handle_capacity_overflow(tx, account_nonce, freed_bytes)?;
        }

        // Capacity is confirmed: this is the final, infallible mutation before the incoming
        // transaction is inserted by the caller.
        if let Some(existing_tx_reference) = replaced_tx_reference {
            self.remove_replaced_tx(existing_tx_reference);
        }

        Ok(())
    }

    pub fn add_tx(&mut self, args: AddTransactionArgs) -> MempoolResult<()> {
        // First remove old transactions from the pool.
        let mut account_nonce_updates = self.remove_expired_txs();
        if !self.is_fifo() {
            self.add_ready_declares();
        }

        let tx_reference = TransactionReference::new(&args.tx);
        self.add_tx_validations(tx_reference, &args.tx, args.account_state.nonce)
            .inspect_err(|err| self.log_add_tx_error(err, &args))?;

        MEMPOOL_TRANSACTIONS_RECEIVED.increment(
            1,
            &[(LABEL_NAME_TX_TYPE, InternalRpcTransactionLabelValue::from(&args.tx.tx).into())],
        );

        // May override a removed queued nonce with the received account nonce or the account's
        // state nonce.
        account_nonce_updates.insert(
            args.account_state.address,
            self.state.resolve_nonce(args.account_state.address, args.account_state.nonce),
        );

        let should_delay_declare =
            matches!(&args.tx.tx, InternalRpcTransactionWithoutTxHash::Declare(_))
                && !self.is_fifo();
        if should_delay_declare {
            self.delayed_declares.push_back(self.clock.now(), args);
        } else {
            self.add_tx_inner(args);
        }

        self.update_accounts_with_gap(account_nonce_updates);
        self.update_state_metrics();
        Ok(())
    }

    fn update_accounts_with_gap(&mut self, address_to_nonce: AddressToNonce) {
        for (address, account_nonce) in address_to_nonce {
            // If a delayed declare transaction exists at the account nonce, it is next to execute,
            // so no gap exists.
            if self.delayed_declares.contains(address, account_nonce) {
                self.remove_from_accounts_with_gap(address);
                continue;
            }

            // Gap exists when lowest transaction nonce is higher than account nonce.
            let gap_exists = match self.tx_pool.get_lowest_nonce(address) {
                Some(lowest_nonce) => account_nonce < lowest_nonce,
                None => false, // No transactions for the account, so no gap.
            };

            // Update the eviction tracking set accordingly.
            if gap_exists {
                if self.accounts_with_gap.insert(address) {
                    // Newly entered gap: all current pool txs for this account are now stuck.
                    let n_stuck = self.tx_pool.n_txs_for_address(address);
                    self.n_stuck_txs += n_stuck;
                    warn!(
                        "Account {address} has a nonce gap; {n_stuck} transaction(s) are now \
                         stuck."
                    );
                }
                // Stayed in gap: per-tx deltas were already applied at add/remove sites.
            } else {
                // Left gap: remaining pool txs for this account are no longer stuck.
                self.remove_from_accounts_with_gap(address);
            }
        }
    }

    pub fn get_evictable_account(&self) -> Option<ContractAddress> {
        let len = self.accounts_with_gap.len();
        if len == 0 {
            return None;
        }
        let random_index = thread_rng().gen_range(0..len);
        self.accounts_with_gap.get_index(random_index).copied()
    }

    // Attempts to make space for a new transaction by evicting existing transactions.
    // Returns true if enough space was freed, false otherwise.
    pub fn try_make_space(&mut self, required_space: u64) -> bool {
        let mut total_space_freed = 0;
        let mut evicted_txs = Vec::new();

        while total_space_freed < required_space {
            let Some(address) = self.get_evictable_account() else {
                break;
            };

            let txs: Vec<_> = self.tx_pool.account_txs_sorted_by_nonce(address).copied().collect();
            for tx_ref in txs.iter().rev() {
                let tx = self
                    .tx_pool
                    .remove(tx_ref.tx_hash)
                    .expect("Transaction must exist in the pool.");
                total_space_freed += tx.total_bytes();
                evicted_txs.push(*tx_ref);
                metric_count_evicted_txs(1);
                self.decrement_stuck_txs_if_gap_account(address, 1);
                if total_space_freed >= required_space {
                    break;
                }
            }

            // Clean up if account is now empty.
            if !self.tx_pool.contains_account(address) {
                self.accounts_with_gap.swap_remove(&address);
            }
        }

        // Keep the queue consistent with the pool: the evicted txs were removed from the pool, so
        // drop their (now-orphaned) queue references too. In fee mode gap accounts are never
        // queued, so this is a no-op there; in Echonet/FIFO mode they are, and skipping this leaves
        // a dangling reference that panics the next `get_txs`.
        self.tx_queue.remove_txs(&evicted_txs);

        total_space_freed >= required_space
    }

    fn handle_capacity_overflow(
        &mut self,
        tx: &InternalRpcTransaction,
        account_nonce: Nonce,
        freed_bytes: u64,
    ) -> Result<(), MempoolError> {
        let address = tx.contract_address();

        let account_has_gap = self.accounts_with_gap.contains(&address);
        let account_has_txs = self.tx_pool.contains_account(address);
        let closing_gap = tx.nonce() == account_nonce;
        let creating_gap = (account_has_gap || !account_has_txs) && !closing_gap;

        // Only the net growth must be evicted: an accompanying replacement removal frees
        // `freed_bytes` (0 when there is no replacement).
        let required_space = tx.total_bytes().saturating_sub(freed_bytes);
        if !creating_gap && self.try_make_space(required_space) {
            return Ok(());
        }

        Err(MempoolError::MempoolFull)
    }
