### Title
Reward double-payment via microblock-pubkeyhash reuse causing duplicate PoisonMicroblock report keys - (File: clarity/src/vm/database/clarity_db.rs)

### Summary
The poison-microblock report key used by `insert_microblock_poison` / `get_microblock_poison_report` is derived from `get_microblock_pubkey_hash_height`, a mutable `pubkey_hash -> height` mapping that is unconditionally overwritten by `insert_microblock_pubkey_hash_height` whenever any block (including a later block from the same miner) declares the same `microblock_pubkey_hash`. Because the report key is `height` (a value that can change for the same pubkey hash over time) rather than something intrinsic to the offending header pair (e.g. the pubkey hash itself or a hash of the conflicting headers), the same double-signed microblock fork can be "reported" twice at two different heights, allowing two independent, non-conflicting `insert_microblock_poison` entries and two separate reward payouts for a single offense.

### Finding Description
`insert_microblock_pubkey_hash_height` (clarity_db.rs:1561-1569) simply does `put_data(&key, &value)` keyed only on `pubkey_hash` — there is no existence check, no uniqueness enforcement, and no error if the same `pubkey_hash` is declared by a different block at a different height. Each time a new block declares a `microblock_pubkey_hash` (which happens on every block, whether or not the miner intentionally reuses an old key), the stored height for that hash is silently replaced.

`get_microblock_poison_report` / `insert_microblock_poison` (clarity_db.rs:1576-1607, 1627-1681) key the "already reported" check and the stored report entirely by `height`, which is obtained by resolving `pubkey_hash -> height` via `get_microblock_pubkey_hash_height` (clarity_db.rs:1609-1624) at the moment the PoisonMicroblock transaction is processed: [1](#0-0) [2](#0-1) [3](#0-2) 

The broken equality is: **"a poison report / reward payout is bound to the unique offending pubkey-hash+fork instance"** vs. what actually happens: **"a poison report / reward payout is bound to whatever height the mutable pubkeyhash→height map happens to resolve to at transaction-processing time."** Since the same `pubkey_hash` can legitimately resolve to `H1` at one point and `H2` after being overwritten, submitting the identical two conflicting microblock headers once while the mapping still points to `H1`, and again after a later block re-declares the same `microblock_pubkey_hash` (pointing the map to `H2`), produces two disjoint storage keys (`make_microblock_poison_key(H1)` and `make_microblock_poison_key(H2)`), each of which independently passes the "not yet reported" check and independently succeeds via `insert_microblock_poison`.

An unprivileged actor holding a single miner slot can trigger this deliberately: win a sortition/tenure at `H1`, sign two conflicting microblocks at the same sequence number with microblock key `K`, and report the fork (self- or third-party-reported) so it is recorded at `H1` and paid from `H1`'s coinbase once it matures. Later, win another tenure at `H2` and deliberately reuse the same microblock private key `K` for that block's declared `microblock_pubkey_hash` — nothing in the codebase prevents key reuse across unrelated tenures. This overwrites the map entry for `pubkey_hash(K)` to `H2`. Submitting the *same* two original microblock headers again now resolves to `H2`, which has never been reported, and the reward logic pays the reporter again once `H2`'s coinbase matures.

I was not able to fully trace, within the available tool budget, the exact reward-payment call path in `stackslib/src/chainstate/stacks/db/transactions.rs` and `accounts.rs` (both files reference these APIs per grep, but their contents were not retrieved before the iteration limit). The vulnerability's root cause — the mutable, overwritable, non-fork-intrinsic key used for de-duplicating poison reports — is confirmed directly in `clarity_db.rs`, but the precise reward-crediting code in `transactions.rs`/`accounts.rs` should be reviewed to confirm there is no additional guard (e.g., a check against the pubkey hash itself, or a "used microblock key" registry) that would prevent this from actually reaching payment. Based on the API surface examined, no such guard exists in `clarity_db.rs`.

### Impact Explanation
If confirmed end-to-end in the reward-payment path, this is a **Critical block-reward double-payment**: the same reported offense (one double-signing event by one microblock key) pays the reporter twice from two different coinbases, i.e., value is minted/paid to the reporter beyond the single intended commission. This directly matches the "block-reward theft/double-payment" Critical category.

### Likelihood Explanation
Preconditions: the attacker needs to win two separate tenures (any two heights `H1 < H2` within maturation distance considerations) and choose to reuse the same microblock private key in both — both are actions fully within a single miner slot's control and require no majority stake, no compromised keys, and no privileged role. Producing a microblock fork with a self-controlled key and reporting it is also unprivileged. The attack is repeatable each time the attacker wins another tenure with the same reused key.

### Recommendation
Key poison reports and the "already reported" de-duplication check on something intrinsic to the offending fork instance rather than a mutable, re-overwritable mapping — e.g., key by `pubkey_hash` directly (disallow re-declaring/overwriting an already-used `microblock_pubkey_hash` in `insert_microblock_pubkey_hash_height`, or version the key with a monotonic "first-seen height" that is never overwritten once set), and/or key the poison report by a hash of the two conflicting microblock headers so that resubmission after any subsequent height-mapping change cannot produce a new, distinct report entry for the same underlying offense.

### Proof of Concept
Rust integration test sketch (chainstate test harness):
1. Insert `pubkey_hash(K) -> H1` via `insert_microblock_pubkey_hash_height`.
2. Call `insert_microblock_poison(H1, reporter, seq)`; assert `get_microblock_poison_report(H1)` is `Some`.
3. Simulate coinbase maturation at `H1` and assert reporter STX balance increases by `commission(H1)`.
4. Overwrite mapping: call `insert_microblock_pubkey_hash_height` again for the same `pubkey_hash(K) -> H2`.
5. Submit/process the identical PoisonMicroblock transaction (same two header contents) again; assert `get_microblock_pubkey_hash_height(pubkey_hash(K))` now resolves to `H2`, `get_microblock_poison_report(H2)` was previously `None`, and `insert_microblock_poison(H2, reporter, seq)` succeeds.
6. Simulate coinbase maturation at `H2`; assert reporter balance increases again.
7. Assert equality violated: `total_paid_to_reporter == commission(H1) + commission(H2) > commission(H1)` (i.e., strictly more than one commission for one reported offense).
