### Title
Unbounded PRC20 minting on inbound deposits ignores `TokenConfig.LiquidityCap` - (File: x/uexecutor/keeper/handler.go)

### Summary
`x/uregistry` defines a `LiquidityCap` per token to bound how much of a given external asset can be represented on Push Chain as PRC20 [4](#0-3) . This field is enforced only as a non-empty string at `MsgAddTokenConfig`/`MsgUpdateTokenConfig` time [1](#0-0) , but the value is never read again anywhere in the codebase (no references in `x/uexecutor` or `x/uregistry/keeper`). Every inbound deposit path (`ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, gas-and-payload autoswap flows) calls `depositPRC20`, which mints the exact `inbound.Amount` reported by validator consensus with no comparison against the configured cap.

### Finding Description
`depositPRC20` in `x/uexecutor/keeper/handler.go` resolves the `TokenConfig` for `(sourceChain, assetAddr)` solely to obtain `NativeRepresentation.ContractAddress`, then parses `amountStr` and unconditionally forwards it to `CallPRC20Deposit` [2](#0-1) . `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` issue module-signed `DerivedEVMCall`s to `depositPRC20Token`/`depositPRC20WithAutoSwap` on the `UNIVERSAL_CORE` handler with no amount ceiling applied on the Cosmos side [3](#0-2) . This is the direct structural analog of the reported ERC20DAO issue: one code path (`x/uregistry` config validation) defines a `distributionAmount`-style limit (`LiquidityCap`), while the actual minting code path (`x/uexecutor` deposit execution) never checks it before minting.

Because `inbound.Amount` originates from honest-validator-observed source-chain events reaching quorum through `MsgVoteInbound`, an unprivileged attacker who can generate a large deposit event on a supported (even low-liquidity) external chain — or who exploits any decoding/parsing looseness in the amount field feeding an honestly-voted ballot — can cause the module to mint PRC20 in excess of the `LiquidityCap` the protocol configured for that token, with no on-chain circuit breaker in this repository's scope.

### Impact Explanation
`LiquidityCap` exists specifically to bound PRC20 issuance backed by external-chain liquidity/vault balances; unenforced minting beyond that cap can create PRC20 supply exceeding what is actually collateralized externally, corrupting PRC20 accounting invariants and enabling under-collateralized PRC20 balances that can later be redeemed/burned against real backing on the source chain — a form of unauthorized mint / accounting corruption in scope per the impact gate (corruption of PRC20 accounting, unauthorized mint).

### Likelihood Explanation
Medium: triggering requires only an ordinary large deposit on a registered external chain being honestly observed and voted through consensus (no privileged or malicious-validator assumption needed) — the vote path itself is standard and doesn't gate on the configured cap. Likelihood scales with how tightly `LiquidityCap` is meant to be enforced operationally versus relying on off-chain relayer/validator judgment.

### Recommendation
In `depositPRC20` (and its autoswap counterpart), track cumulative minted PRC20 supply against `tokenConfig.LiquidityCap` (parsed as `*big.Int`) before issuing `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`, returning an error (and triggering the existing revert/refund path) when a deposit would push total minted supply past the configured cap.

### Proof of Concept
1. Admin registers a `TokenConfig` for `eip155:X` / `TOKEN` with `LiquidityCap = "1000000"` (matching real external liquidity).
2. An inbound event for that token with `Amount = "999999999999999999"` (far exceeding the cap) is honestly observed and voted to quorum via `MsgVoteInbound`.
3. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full amount into the recipient's PRC20 balance [5](#0-4)  with no comparison to `LiquidityCap`, producing PRC20 supply with no corresponding external backing.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
