Based on my research, I found a genuine analog to the dompdf bug class in the deprecated (Cairo0) syscall parsing path of the sequencer's `blockifier` crate.

### Title
Uncontrolled resource allocation from an unvalidated declared array-size in deprecated Cairo0 syscall parsing - ([File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs])

### Summary
The dompdf bug trusts a declared BMP header dimension to size a native memory allocation before any check that enough backing pixel data actually exists. The sequencer has an analogous pattern in `read_felt_array` (deprecated/Cairo0 path): it reads a raw, attacker-controlled felt as `array_size` directly from Cairo VM memory and immediately uses it to size a range read/allocation, without validating it against any protocol-level bound before the read is attempted.

### Finding Description
`read_felt_array` in the deprecated syscall hint processor reads a size field straight out of VM memory (populated by the executing contract's own Cairo0 bytecode) and converts it to a `usize` with no upper-bound check: [1](#0-0) 

That size is then passed straight into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` — a call that builds a `Vec<Felt>` sized from the caller-declared `size` parameter: [2](#0-1) 

This is structurally the same root cause as the dompdf advisory: a declared length/dimension field taken from untrusted input is used to drive an allocation before the code confirms that the underlying backing store (in dompdf: pixel data; here: actual populated VM memory cells) is large enough to justify that allocation. `read_felt_array` (deprecated path) is used throughout `deprecated_syscalls/mod.rs` to parse request payloads for Cairo0 syscalls (e.g., `EmitEvent`'s `keys`/`data`, `SendMessageToL1`'s payload, `Deploy`'s constructor calldata, `CallContract`'s calldata) — all of which are populated by the executing (attacker-controlled) contract's own bytecode, not by the protocol layer. Contrast this with the modern Cairo1 `read_felt_array` in `crates/blockifier/src/execution/syscalls/hint_processor.rs:860-879`, which derives `array_size` from the difference between two already-materialized relocatable pointers — a value inherently bounded by real memory segment layout, not an arbitrary attacker-declared integer.

Importantly, protocol-level bounds such as `exceeds_event_size_limit` (`EventLimits::max_data_length`/`max_keys_length`) are only checked *after* `read_felt_array` has already executed and materialized the full-sized vector: [3](#0-2) 
— note this citation is for the modern (Cairo1) `EmitEventRequest::read`, which similarly performs no size check before calling `read_felt_array`, but is bounded by real memory. The deprecated path additionally lacks that pointer-based bound.

### Impact Explanation
If a contract deployed under a declared Cairo0 class supplies a syscall request with a very large declared `array_size` felt that does not correspond to actually-written memory, the sequencer will attempt to size/allocate a `Vec<Felt>` proportional to that attacker-chosen value before validating that the backing memory segment actually contains that much data. Depending on cairo-vm's internal implementation of `get_integer_range` (an external dependency not vendored in this repo, so I could not directly confirm whether it pre-reserves capacity before checking cell existence), this can translate into a large or failing allocation. In Rust, a failed large allocation from `Vec::with_capacity`/collection growth triggers `handle_alloc_error`, which aborts the process by default — not a recoverable `Result`. An abort in a block-building or block-validation worker while processing a single transaction is a liveness-affecting DoS: it can crash the sequencer process mid-execution of an otherwise ordinary transaction, potentially stalling block production or causing execution divergence between honest nodes if some abort and others don't (e.g. due to differing available memory), which affects the network's ability to confirm new transactions.

### Likelihood Explanation
I was not able to fully confirm from the available code (since `cairo-vm`'s `get_integer_range` implementation is external and not indexed in this repository) whether it pre-allocates a `Vec` sized to the full declared range before verifying the range is populated, or whether it performs a bounds/segment-size check first. This is the key uncertainty for exploitability: if `get_integer_range` checks the segment's used-size before allocating, the bug is not exploitable as an amplification primitive. Given this uncertainty, I flag this as a **plausible but unconfirmed** analog — it should be independently verified against the exact behavior of `get_integer_range` in the pinned `cairo-vm` version before treating it as an active, exploitable finding.

### Recommendation
Regardless of the exact allocation behavior of `get_integer_range`, defense-in-depth is warranted: bound the deprecated `array_size` felt in `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-950`) against a sane protocol maximum (e.g., segment length, remaining calldata budget, or a fixed max like `max_calldata_length`) before converting it to `usize` and passing it to `felt_range_from_ptr`, mirroring the Cairo1 path's implicit bound via realized pointer difference. Additionally, verify (and if necessary patch) that `vm.get_integer_range` in the vendored `cairo-vm` dependency validates the requested range against the actual segment's used size before allocating a same-sized `Vec`.

### Proof of Concept
Not independently reproduced against the compiled binary — reproduction would require running the sequencer's blockifier against a deployed Cairo0 contract whose bytecode issues a deprecated syscall (e.g. `emit_event`) with a memory layout where the `keys`/`data` size felt is set to a very large value (e.g., close to `usize::MAX` or another value chosen to trigger a large allocation) while the backing memory segment is left mostly unpopulated, then observing whether the worker OOMs/aborts before the subsequent `exceeds_event_size_limit`/similar bound check is reached. This step was not executed due to lack of a runtime/terminal environment in this ask-only session, and because `cairo-vm`'s exact `get_integer_range` allocation strategy could not be verified from the indexed code.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
}

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

pub type EmitEventResponse = EmptyResponse;

pub fn exceeds_event_size_limit(
    versioned_constants: &VersionedConstants,
    n_emitted_events: usize,
    event: &EventContent,
) -> Result<(), EmitEventError> {
    let EventLimits { max_data_length, max_keys_length, max_n_emitted_events } =
        versioned_constants.tx_event_limits;
    if n_emitted_events > max_n_emitted_events {
        return Err(EmitEventError::ExceedsMaxNumberOfEmittedEvents {
            n_emitted_events,
            max_n_emitted_events,
        });
    }
    let keys_length = event.keys.len();
    if keys_length > max_keys_length {
        return Err(EmitEventError::ExceedsMaxKeysLength { keys_length, max_keys_length });
    }
    let data_length = event.data.0.len();
    if data_length > max_data_length {
        return Err(EmitEventError::ExceedsMaxDataLength { data_length, max_data_length });
    }

    Ok(())
}
