### Title
Malicious relayer access key on the NEAR Wallet Contract escapes revocation via NEP-366 meta transactions, breaking the "relayer cannot maliciously burn user funds" invariant - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract's ban-relayer safety mechanism authorizes revocation of a misbehaving relayer's `FunctionCall` access key by comparing `env::signer_account_id()` to `env::current_account_id()` [1](#0-0) . This is the direct protocol analog of the reported `tx.origin`-style trust confusion: `signer_account_id()` is the outermost transaction signer (like `tx.origin`), while `predecessor_account_id()` is the immediate, cryptographically-verified caller. NEP-366 meta transactions explicitly make these two diverge — the relayer wrapping a `DelegateAction` becomes the receipt's `signer_id` while the delegate's `sender_id` becomes the `predecessor_id` [2](#0-1) . A relayer holding a valid, unlimited-allowance `FunctionCall` access key on the wallet (as created by the documented `register_relayer` flow) [3](#0-2)  can wrap its own faulty/garbage `rlp_execute` call inside a `SignedDelegateAction` with `sender_id = current_account_id` and have any throwaway outer account submit it as the meta-transaction relayer. This makes `signer_account_id()` return the throwaway outer account instead of `current_account_id`, causing the `env::signer_account_id() == current_account_id` check to evaluate `false` and skip `create_ban_relayer_promise` [4](#0-3) .

### Finding Description
The wallet contract's design explicitly relies on this identity check to detect "this faulty call was made via my own access key held by a relayer" and revoke that key immediately, as documented in the code's own safety comment: "if a relayer is using an access key for this wallet then that key will still be revoked... a relayer cannot maliciously burn a large portion of the user's tokens" [5](#0-4) . The check appears twice — once in `rlp_execute` and once in `address_check_callback` [6](#0-5) [7](#0-6) .

Both `RelayerError`s (invalid nonce, invalid target, wrong chain id, insufficient gas, etc., all documented and tested at `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs`) are intended to be un-repeatable because the offending access key gets deleted on the very first offense — this is what caps the attacker's blast radius. Routing the same access-key-signed call through a `DelegateAction` (any outer account can act as the relayer of the meta transaction, paying its own gas) preserves `predecessor_id == current_account_id` (so `inner_rlp_execute` still runs using the wallet's own access key permission) but changes `signer_id` to the outer account, defeating the revocation trigger while keeping the underlying vulnerable access key alive indefinitely, precisely mirroring how the referenced Connext report describes `xReceive`-adjacent code trusting `tx.origin` to distinguish "trusted, self-triggered" calls from third-party-triggered ones.

### Impact Explanation
This breaks a documented, load-bearing security invariant of the Wallet Contract (used for ETH-emulation / eth-implicit accounts): a bad-faith or compromised relayer key is supposed to be a one-shot liability, immediately banned after the first faulty call. If revocation can be bypassed, the same leaked/malicious `FunctionCall` access key — potentially with unlimited allowance and only restricted to `rlp_execute` — remains valid, letting the attacker repeatedly probe/replay/attempt fund-moving `rlp_execute` calls (transfers, NEP-141/ERC-20 transfers, `AddKey` grants) against the wallet owner's account instead of being cut off after one failure. This is a concrete violation of the protocol's own stated fund-safety guarantee for wallet-contract users.

### Likelihood Explanation
Exploitability requires only: (1) possession of a `FunctionCall` access key with `receiver_id = wallet_contract` and `method_names` including `rlp_execute` (obtainable by any relayer registered per the documented flow, or by a leaked key), and (2) the ability to submit a `SignedDelegateAction` wrapped by any account willing to pay the outer gas (trivially the attacker's own second account). No special node/validator privilege is needed — this is reachable purely via a standard NEP-366 meta transaction submitted through JSON-RPC.

### Recommendation
Do not rely on `env::signer_account_id()` to determine whether the call originated from the wallet's own access key. Instead, gate the ban-relayer path on `env::predecessor_account_id() == current_account_id()` (which is unaffected by delegate-action wrapping and reflects only who actually authorized the receipt), or explicitly reject/detect delegate-action-driven invocations of `rlp_execute`/`address_check_callback` before deciding whether to revoke the key.

### Proof of Concept
1. Relayer `R` registers a `FunctionCall` access key `K` on wallet contract `W` via the documented `register_relayer` flow (unlimited allowance, `receiver_id = W`, `method_names = ["rlp_execute"]`).
2. `R` crafts an intentionally invalid call to `W.rlp_execute` (e.g., garbage `tx_bytes_b64`, as in `test_relayer_invalid_tx_data`) but instead of submitting it directly, wraps it as `DelegateAction { sender_id: W, receiver_id: W, actions: [rlp_execute(...)], public_key: K, ... }`, signs it with `K`.
3. Any throwaway account `S` (could be `R` itself under a second identity) wraps this in an outer `SignedTransaction` naming `S` as signer/relayer of the meta transaction and submits it.
4. On-chain, the delegate action unpacks with `predecessor_id = W`, but `signer_id = S`.
5. Inside `rlp_execute`, `inner_rlp_execute` fails with `Error::Relayer(_)`; the guard `env::signer_account_id() == current_account_id` evaluates `S == W` → `false`, so `create_ban_relayer_promise` is skipped and `K` is never revoked, unlike the direct-call case tested in `test_relayer_invalid_tx_data`/`test_relayer_invalid_sender` where the key is always revoked.

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
    let pk = env::signer_account_pk();
    Promise::new(current_account_id).delete_key(pk).function_call_weight(
        "ban_relayer".into(),
        Vec::new(),
        NearToken::from_yoctonear(0),
        Gas::from_tgas(1),
        GasWeight(1),
    )
}

#[tokio::test]
async fn test_register_relayer() -> anyhow::Result<()> {
    let TestContext { worker, mut wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let relayer_pk = wallet_contract.register_relayer(&worker).await?;
    let key = wallet_contract.inner.as_account().view_access_key(&relayer_pk).await?;
    match &key.permission {
        AccessKeyPermission::FunctionCall(access) => {
            assert_eq!(access.allowance, None);
            assert_eq!(access.receiver_id.as_str(), wallet_contract.inner.id().as_str());
            assert_eq!(&access.method_names, &[RLP_EXECUTE]);
        }
        _ => panic!("Unexpected full access key"),
    }
