### Title
UEA FactoryV1 proxy owner is never initialized in `InitGenesis`, allowing an unprivileged attacker to front-run `initialize()` and seize control of UEA deployment - (File: x/uexecutor/keeper/genesis.go)

### Summary
`x/uexecutor`'s `InitGenesis` deploys the UEA Factory proxy/impl/admin trio via `deployFactoryEA` but never calls the factory's `initialize(address initialOwner)` function, unlike the sibling `ProxyAdmin` contract whose owner slot is written directly at genesis. Because `initialize()` on an OZ-style `Initializable` contract only guards against re-initialization (not caller identity), the very first account to call it after genesis becomes the permanent owner — and that account can be anyone, including an unprivileged attacker racing the legitimate genesis/operator transaction.

### Finding Description
`deployFactoryEA` (`x/uexecutor/keeper/genesis.go:100-109`) performs three steps at fresh genesis: [1](#0-0) 

It writes runtime bytecode for the factory implementation, proxy admin, and factory proxy, and even explicitly sets the `ProxyAdmin`'s owner storage slot: [2](#0-1) 

But it never touches the FactoryV1 proxy's own `Ownable` owner. The FactoryV1 ABI exposes a public `initialize(address initialOwner)` entry point: [3](#0-2) 

which per the codebase's own `README.md`/tests is expected to be called as a separate step to set the owner, exactly as shown in the test harness (never in production code): [4](#0-3) 

A grep across the entire repository shows `initialize` is invoked against the factory address only from this test helper — there is no production keeper, genesis, or upgrade-handler code path that calls it on a live chain. `registerNewChain`, `registerUEA`, and `setUEAProxyImplementation` — the three `onlyOwner`-gated admin functions that configure which per-chain UEA implementation contracts the factory will deploy — are likewise referenced only in the ABI and the test script, confirming they are only ever invoked once an owner exists.

Because `deployFactoryEA` runs inside `InitGenesis` at chain start with `Exported=false`, and `InitGenesis` itself contains no call to `initialize`: [5](#0-4) 

the FactoryV1 proxy sits at genesis with an unset (`address(0)`) owner. If FactoryV1 uses OpenZeppelin's `Initializable`/`Ownable` pattern (as its bytecode and the presence of an unrestricted `initialize(initialOwner)` entrypoint strongly indicate), any account — not just the deploying node — can submit a normal EVM transaction calling `initialize(attacker)` in the first block(s) after genesis, becoming the permanent `owner` of the on-chain UEA factory before the legitimate chain operator's own initialize transaction lands.

Once an attacker owns the factory, they control `setUEAProxyImplementation`, `registerNewChain`, and `registerUEA` — the exact functions that determine what bytecode every future `UEA` (Universal Executor Account) is deployed with. Every subsequent unprivileged inbound cross-chain deposit that needs a new UEA goes through this same factory via `DeployUEAV2`/`CallFactoryToDeployUEA`: [6](#0-5) 

and is triggered automatically and gaslessly for any first-time sender during ordinary inbound execution: [7](#0-6) 

With the factory owner compromised, an attacker can point `_UEA_PROXY_IMPLEMENTATION` (or per-chain-namespace registered implementations) at malicious bytecode so that every new user's UEA is deployed as an attacker-controlled contract instead of the genuine `UEA_EVM`/`UEA_SVM` logic — enabling theft of any funds or payload-execution rights subsequently routed to those UEAs.

### Impact Explanation
This is a critical, chain-wide compromise of the universal-execution trust root: control over which bytecode every future Universal Account is deployed with. It maps to "unauthorized UEA or CEA execution" and "unauthorized module-originated EVM execution" in the allowed-impact list, and can lead directly to draining or hijacking of funds/authority for every user whose UEA is deployed after the attacker seizes ownership.

### Likelihood Explanation
High. No privileged access, validator collusion, or race against consensus is required — only a plain EVM transaction submitted before the legitimate operator's own `initialize` call, in a narrow but realistic post-genesis window. This mirrors the exact bug class from the external report (front-runnable `initialize()`), except here the underlying `onlyOwner` protections are not merely broken (as in the report) but actively exploitable because they gate real, fund/authority-relevant admin functions.

### Recommendation
Set the FactoryV1 proxy's owner atomically inside `deployFactoryEA`/`InitGenesis`, using the same storage-slot-write technique already used for `deployProxyAdminContract`, instead of relying on a separate, later, unauthenticated `initialize()` call. Alternatively, invoke `initialize(owner)` synchronously within the same genesis code path (not as an out-of-band operator transaction), and add `_disableInitializers()`-equivalent protection or a genesis-only guard so the call cannot be front-run.

### Proof of Concept
1. Deploy chain from genesis; `InitGenesis` runs `deployFactoryEA`, installing FactoryV1 proxy/impl/admin bytecode with no owner set.
2. Before the operator submits their own `initialize(operatorAddr)` transaction, an attacker submits `eth_sendRawTransaction` calling `initialize(attackerAddr)` on the factory proxy address (`FACTORY_PROXY_ADDRESS_HEX`).
3. Attacker is now `owner()`; the operator's later `initialize` call reverts (already initialized).
4. Attacker calls `setUEAProxyImplementation(maliciousImpl)` / `registerUEA(chainHash, vmHash, maliciousImpl)`.
5. Any subsequent unprivileged user's first cross-chain deposit triggers `ExecuteInboundGas` → `DeployUEAV2` → `CallFactoryToDeployUEA`, deploying the user's UEA using the attacker-registered malicious implementation, giving the attacker control over that user's on-chain executor account.

func (k Keeper) CallFactoryToDeployUEA(
	ctx sdk.Context,
	from, factoryAddr common.Address,
	universalAccount *types.UniversalAccountId,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: deployUEA",
		"factory", factoryAddr.Hex(),
		"chain_namespace", universalAccount.ChainNamespace,
		"chain_id", universalAccount.ChainId,
		"owner", universalAccount.Owner,
	)

	abi, err := types.ParseFactoryABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse factory ABI")
	}

	abiUniversalAccount, err := types.NewAbiUniversalAccountId(universalAccount)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal account")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,        // who is sending the transaction
		factoryAddr, // destination: FactoryV1 contract
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"deployUEA",
		abiUniversalAccount,
	)
}
