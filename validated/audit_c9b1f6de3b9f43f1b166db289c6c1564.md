### Title
Unconditional order-count decrement on order removal without existence check leads to state divergence - (File: chainbase/src/main/java/org/tron/core/capsule/MarketAccountOrderCapsule.java)

### Summary
`MarketAccountOrderCapsule.removeOrder` mirrors the reported `aggregator::remove_job` pattern: it silently no-ops when the target item is not present in the tracked list, yet unconditionally decrements the associated counter regardless of whether an actual removal took place.

### Finding Description
`removeOrder` builds a copy of the order list, calls `orderList.remove(orderId)` (which silently returns `false` and does nothing if `orderId` is not present — Java `List.remove(Object)` never throws), and then unconditionally decrements `count` via `setCount(this.getCount() - 1)`: [1](#0-0) 

This is invoked from `MarketUtils.updateOrderState`, which is called whenever a market order transitions to `INACTIVE` or `CANCELED` (e.g., from `MarketCancelOrderActuator` and the order-matching logic in `MarketSellAssetActuator`): [2](#0-1) 

There is no assertion/verification that the order ID passed actually exists in `accountOrderCapsule`'s order list before decrementing `count`. If `updateOrderState`/`removeOrder` is ever invoked more than once for the same order ID (e.g., an order that is already `INACTIVE`/`CANCELED` being processed again during order-matching iteration, or any future code path re-entering this state transition), the second call will find nothing to remove from the list (silent no-op) but will still decrement `count`, causing `count` to diverge from the actual number of entries in `orders`. This is the same root cause as the reported `aggregator::remove_job` issue: absence-of-target should abort/skip the counter update, but here the counter update proceeds unconditionally regardless of whether removal succeeded.

### Impact Explanation
`count` (as distinct from `totalCount`) is the account-level bookkeeping value for active market orders, exercised directly in production order-cancellation flows (`MarketCancelOrderActuator`) and returned/used by market order actuators and tests. If `count` diverges from the true number of live entries in the `orders` list (e.g., drops below zero or below the real active-order count), any logic that relies on `count` for correctness (accounting checks, future features that trust `count` to reflect real list size) develops an invalid/inconsistent state. This falls into the "invalid-state/divergence" impact category — the actual per-account order list and its reported active count silently diverge on repeated/duplicate removal attempts, rather than aborting to signal the anomaly.

### Likelihood Explanation
Under the current, single actuator call path (`MarketCancelOrderActuator` validates that an order is `isActive()` before allowing cancellation, and order IDs removed are always freshly matched/created), a duplicate call for the same already-removed order is not obviously exercised by present code. The concrete reachability of a second `updateOrderState`/`removeOrder` invocation on the same already-processed order (e.g. via the order-matching loop in `MarketSellAssetActuator`) could not be fully confirmed within the scope of this review — this is the key precondition for triggering an observable divergence, and it remains unverified. The defect itself (missing existence check before decrementing the counter) is present and unconditionally reachable in code, matching the reported bug class, but whether an unprivileged user can currently force a double invocation was not conclusively established.

### Recommendation
Make `removeOrder` check whether `orderId` was actually present in the list (`List.remove(Object)` return value) before decrementing `count`, and only decrement when removal actually occurred; consider logging/aborting if the ID is unexpectedly absent, analogous to the suggested `assert!(is_in, E_JOB_NOT_FOUND)` fix in the report.

### Proof of Concept
Not independently reproduced — the exploitable precondition (a second/duplicate call into `MarketUtils.updateOrderState` → `MarketAccountOrderCapsule.removeOrder` for an order ID that has already been removed from the account's order list) was not confirmed against the order-matching code paths (e.g. `MarketSellAssetActuator`) within the available investigation. The structural defect (unconditional `count` decrement without checking removal success) is confirmed directly in the cited source.

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
