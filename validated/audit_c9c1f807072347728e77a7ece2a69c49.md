### Title
Stale `ProgramPrecompile` JUMPDEST cache keyed by contract address (not by code content) can diverge across nodes after code changes at a reused address, causing consensus-breaking execution divergence - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program` maintains a static, process-wide LRU cache `programPrecompileLRUMap` that stores the compiled `ProgramPrecompile` (essentially the set of valid `JUMPDEST` offsets) for a contract's bytecode [1](#0-0) . The `ProgramPrecompile.compile` routine simply scans the raw opcode bytes and records `JUMPDEST` positions [2](#0-1) . This is directly analogous to the reported bug class: a parsed/derived representation of executable code (ELF sections in the report; JUMPDEST table here) is cached by executors and is not guaranteed to be invalidated when the underlying "program data" (contract bytecode) at the same address changes.

### Finding Description
The precompile cache entry is looked up and stored per contract address (via the `Key` wrapper, whose `equals`/`hashCode` are based purely on the byte content of the key, i.e. the address) [3](#0-2) , not by a hash of the code itself. Contract bytecode, however, is mutable at a fixed address in java-tron: an account can be destroyed (`SELFDESTRUCT` → `Repository.deleteContract`, which removes the code/account/contract entries) [4](#0-3)  and later redeployed at the *same* address via `CREATE2`, whose target address only depends on `sender`, `salt`, and `keccak256(init_code)` — not on the runtime code produced. Using the well-known "metamorphic contract" technique (identical init-code bytes that branch on external/mutable state to select which runtime code to `RETURN`), an attacker can deploy materially different runtime bytecode at the same address across separate deployments.

If a witness node previously executed the old bytecode at that address, `programPrecompileLRUMap` may still hold the old JUMPDEST set for that address key when the new bytecode is executed, because nothing in the redeploy path (`createContractImpl`, `saveCode`, `deleteContract`) invalidates or evicts this static cache [5](#0-4) [6](#0-5) . Other nodes, whose cache entry was evicted (LRU) or never populated, will freshly recompile the JUMPDEST set from the actual (new) bytecode. This is exactly the "some executors use cached [stale] representation while others use the [correct] one" scenario described in the report, except the artifact here is the JUMPDEST validity table rather than a parsed ELF.

Note: a second, unrelated but structurally similar smell was found — `RepositoryImpl.removeLruCache` is a no-op stub `public static void removeLruCache(byte[] address) {}` that is called from `UpdateEnergyLimitContractActuator`, `UpdateSettingContractActuator`, and `VMActuator` as if it clears a cache, but does nothing [7](#0-6) [8](#0-7) . This is dead/no-op code today and doesn't independently create divergence since it isn't backed by any live cache, but it is worth flagging as evidence that cache-invalidation guarantees around contract mutation in this codebase are not consistently enforced.

### Impact Explanation
If JUMPDEST validity for a call disagrees between two honest witness nodes executing the identical transaction, one node may throw `Program.Exception` (invalid jump destination), reverting/erroring the call, while the other executes it successfully with different state changes and gas/energy consumption. Because TVM execution results (receipts, state root, energy usage) are part of block consensus, this divergence can cause block validation mismatches among witnesses — a consensus-affecting invalid-state/divergence bug, potentially leading to chain halt or fork, matching the report's stated impact category.

### Likelihood Explanation
This requires: (1) an attacker able to deploy a CREATE2 metamorphic contract with initcode that can be made to emit different runtime bytecode across deployments, (2) inducing a call to the contract so some nodes populate/warm the JUMPDEST cache with the old code, (3) redeploying different bytecode at the same address, and (4) triggering execution again before cache entries are naturally evicted on all nodes. This is a known, previously-demonstrated technique (metamorphic contracts) but requires deliberate contract engineering and specific timing relative to the LRU eviction window (`CommonParameter.getSafeLruCacheSize()`), so likelihood is moderate rather than trivial, but it is fully reachable by an unprivileged user with no special/trusted role.

### Recommendation
Key the `programPrecompileLRUMap` (and any other cached representation of a contract's parsed/compiled artifacts) by a hash of the actual bytecode (e.g. `codeHash`, as already tracked in `ContractCapsule.setCodeHash`/`getCodeHash`) rather than by the contract address alone, so a cache hit can only occur for byte-identical code regardless of which address it lives at. Alternatively, explicitly invalidate/evict the address's precompile cache entry whenever `saveCode`/`createContract`/`deleteContract` mutates the code at that address. Also remove or properly implement `RepositoryImpl.removeLruCache` so its call sites either genuinely invalidate a cache or are deleted, to avoid future confusion about invalidation guarantees.

### Proof of Concept
1. Deploy a factory contract whose `CREATE2` init-code is fixed in bytes but reads a mutable storage slot (or `block.number`) in the factory to decide, via a branch inside the init code, which of two different runtime-code blobs to `RETURN`. Because `keccak256(init_code)` is identical across deployments, the resulting `CREATE2` address is identical for both variants.
2. Deploy variant A (bytecode A) at address `X`. Trigger a `TriggerSmartContract` call to `X` on some witness nodes so that `Program` populates `programPrecompileLRUMap` for address `X` with variant A's JUMPDEST set (via `Program`'s precompile compile/cache path, backed by `ProgramPrecompile.compile` at [2](#0-1) ).
3. `SELFDESTRUCT` the contract at `X` (removes account/code/contract entries via `Repository.deleteContract` [4](#0-3) ), flip the factory's mutable state, and redeploy via the same `CREATE2` call — variant B (bytecode B, with `JUMPDEST` offsets that differ from A) lands at the same address `X`.
4. Trigger a call to `X` that exercises a `JUMP`/`JUMPI` at an offset that is a valid `JUMPDEST` in B but was not a `JUMPDEST` in A (or vice versa). Nodes with a still-warm `programPrecompileLRUMap` entry for address `X` (from step 2) validate the jump against A's stale JUMPDEST set and throw an invalid-jump exception, while nodes whose cache entry was evicted (or that never cached it) recompile from B's actual bytecode and execute successfully — producing different transaction results/receipts for the identical transaction across honest nodes.

  public static ProgramPrecompile compile(byte[] ops) {
    ProgramPrecompile ret = new ProgramPrecompile();
    for (int i = 0; i < ops.length; ++i) {
      int op = ops[i] & 0xff;

      if (op == Op.JUMPDEST) {
        ret.jumpDest.add(i);
      }

      if (op >= Op.PUSH1 && op <= Op.PUSH32) {
        i += op - Op.PUSH1 + 1;
      }
    }
    return ret;
  }
