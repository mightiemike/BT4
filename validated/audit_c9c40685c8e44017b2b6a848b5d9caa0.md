### Title
Stale per-block zToken index cache lets collateral be valued at a pre-loss price after `socialize-debt` in the same block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`accrue-and-cache` in the market contract caches each vault's `{index, lindex}` keyed only by `{timestamp: stacks-block-time, aid}`. Any operation in a block that populates this cache "locks in" the vault's index/lindex for the rest of that block. If a vault's authoritative state changes later in the *same block* via `socialize-debt` (which directly writes down `lindex` to reflect a bad-debt loss), later transactions in that block that resolve zToken collateral value still read the stale, higher `lindex` from the cache instead of the corrected value — exactly the class of bug in the report: a value is trusted after its source has moved without invalidating the cached copy.

### Finding Description
`accrue-and-cache` is a cache-or-compute helper: [1](#0-0) 

It is invoked from `accrue-collateral-asset`/`accrue-user-collateral` (used by `collateral-add`, `collateral-remove`, `borrow`, `liquidate`, etc.) and from `calculate-asset-notional-value` when pricing zToken collateral via `resolve-ztoken`: [2](#0-1) [3](#0-2) [4](#0-3) 

Once any transaction in a block calls `accrue-and-cache` for a given `aid`, the tuple `{index, lindex}` is written into `index-cache` keyed by `stacks-block-time`, and every subsequent call within the same block for that `aid` returns the cached value on a cache HIT without re-querying the vault.

Separately, `socialize-debt` in each vault directly mutates the vault's own `lindex` var-set to reflect a bad-debt write-down, bypassing the market's cache entirely: [5](#0-4) 

The vault has no mechanism to invalidate the market's `index-cache` when `socialize-debt` runs, and the market's cache key (`stacks-block-time`) has no dependency on the vault's actual state/version — it is a "cached value not invalidated when its source moves."

### Impact Explanation
Sequence within a single block:
1. Transaction 1 (any user) performs a `collateral-add`/`borrow`/`liquidate` call touching zUSDC, causing `accrue-and-cache(USDC)` to cache `{index: idx0, lindex: lindex0}` for `stacks-block-time = T`.
2. Transaction 2, later in the same block, triggers `vault-usdc.socialize-debt`, which writes down `lindex` to a lower value to reflect a realized loss (see `new-lindex` calc above), directly via `var-set lindex new-lindex` in the vault — the market's cache is unaware of this.
3. Transaction 3, still in block `T`, calls `borrow`/`collateral-add`/`liquidate` involving zUSDC collateral. `accrue-and-cache(USDC)` hits the cache from step 1 and returns the stale, higher `lindex0` instead of the corrected value.
4. `resolve-ztoken`/`calculate-asset-notional-value` price the user's zUSDC collateral using the stale higher `lindex0`, over-valuing collateral that has actually lost value. This lets a borrower extract more debt than their real (post-loss) collateral supports, or avoid liquidation that should otherwise be triggered — leading to protocol insolvency / theft of funds at the expense of other depositors, since debt is issued against collateral whose true backing has already been reduced.

This lands on **Critical** impact: protocol insolvency / theft of funds via over-valued collateral used to extract undercollateralized debt.

### Likelihood Explanation
This requires a `socialize-debt` call (a bad-debt write-down, an authorized-contract operation reachable during normal loss-recovery flows) to occur in the same block as other user-facing operations that already cached the pre-loss index for the same asset. An attacker who observes a pending `socialize-debt` transaction in the mempool can trigger a cache-populating call beforehand and a borrow/collateral-add afterward in the same block (or simply piggyback naturally occurring block co-location), making exploitation plausible without requiring privileged access, since `socialize-debt` is restricted to authorized contracts only via `check-caller-auth`, not to a leaked key or DAO compromise.

### Recommendation
Invalidate or bypass the `index-cache` entry for an asset whenever the underlying vault's index/lindex changes outside of the normal `accrue` path (e.g., have `socialize-debt` also update/clear the market's cached entry via a cross-contract call, or eliminate the cache-hit path for `lindex` specifically and always re-read after any loss-socializing event within the same block, or key the cache off a vault-side monotonically incrementing state version instead of purely `stacks-block-time`).

### Proof of Concept
Not independently executed; the sequence above is derived directly from reading `accrue-and-cache`, `resolve-ztoken`, `calculate-asset-notional-value` in `v0-4-market.clar` and `socialize-debt` in `v0-vault-usdc.clar` (same pattern present in all sibling vaults: `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`). Full multi-transaction, same-block simulation would require a test harness (Clarinet/local-testing) to confirm the exact numeric conditions under which the cache HIT masks the `socialize-debt` write-down; this is recommended as a follow-up verification step.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
