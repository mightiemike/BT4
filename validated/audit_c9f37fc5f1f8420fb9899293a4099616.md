### Title
Deposit Refund Misdirection in Meta-Transactions: Relayer's Deposit Stolen by Sender via Intentional Failure — (`runtime/runtime/src/actions.rs`)

### Summary

In nearcore's meta-transaction (NEP-366 `DelegateAction`) execution path, when a relayer pays a deposit for an inner action and that inner action fails on the receiver's shard, the deposit refund is sent to the `predecessor_id` of the spawned receipt — which is the **sender (Alice)**, not the **relayer** who actually paid. An unprivileged sender can exploit this by crafting a `DelegateAction` with a large attached deposit that is designed to fail on the receiver's shard, causing the relayer to permanently lose the deposit while Alice gains it.

### Finding Description

When `apply_delegate_action` processes a `DelegateAction`, it spawns a new receipt with `predecessor_id` set to `sender_id` (Alice):

```rust
// runtime/runtime/src/actions.rs:456-469
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice, not the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // ← Relayer
        ...
        actions: delegate_action.get_actions(),
    }),
});
```

The relayer is the `signer_id` (who paid all gas and deposits), but Alice is the `predecessor_id` of the spawned receipt.

When this inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` issues the deposit refund to `receipt.balance_refund_receiver()`:

```rust
// runtime/runtime/src/lib.rs:1281-1285
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),  // ← resolves to predecessor_id = Alice
        deposit_refund,
    ));
}
```

`balance_refund_receiver()` returns `refund_to` if set, otherwise `predecessor_id`:

```rust
// core/primitives/src/receipt.rs:428-430
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
```

Since the spawned receipt is `ReceiptEnum::Action` (not `ActionV2`), `refund_to()` always returns `&None`, so the refund unconditionally goes to `predecessor_id` = Alice. The relayer's deposit is transferred to Alice.

Gas refunds correctly go to `signer_id` (the relayer), but the deposit refund — which can be arbitrarily large — goes to Alice.

### Impact Explanation

An unprivileged sender (Alice) can steal an arbitrary amount of NEAR tokens from any relayer by:
1. Crafting a `DelegateAction` with a large `deposit` attached to an inner `FunctionCall` or `Transfer` action that will fail on the receiver's shard (e.g., calling a non-existent method, or targeting a receiver that will reject the call)
2. Submitting the signed `DelegateAction` to a relayer
3. The relayer pays the deposit and submits the meta-transaction
4. The inner action fails; Alice receives the full deposit refund; the relayer loses it permanently

The corrupted value is: `relayer.balance -= deposit_amount` and `alice.balance += deposit_amount`. This is a direct, protocol-enforced transfer of funds from the relayer to Alice with no recourse.

### Likelihood Explanation

The attack is reachable by any ordinary user who can interact with a relayer. The relayer cannot always predict whether an inner action will succeed — state can change between the relayer's pre-check and execution (race condition), or Alice can deliberately target a receiver that will fail. The nearcore documentation at `docs/architecture/how/meta-tx.md` lines 237–242 explicitly acknowledges: *"there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard."* This confirms the attack is known and reachable.

### Recommendation

The deposit refund for a meta-transaction's inner receipt should be directed to the relayer (the `signer_id` of the outer receipt), not to Alice (the `predecessor_id` of the inner receipt). One approach:

- When `apply_delegate_action` spawns the inner receipt, use `ReceiptEnum::ActionV2` and set `refund_to: Some(relayer_account_id)` so that on failure the deposit is returned to the relayer who paid it.
- Alternatively, record the relayer's identity in the spawned receipt's `refund_to` field so `balance_refund_receiver()` returns the relayer rather than Alice.

### Proof of Concept

**Actors**: Alice (sender), Relayer, Bob (receiver contract that always panics)

1. Alice creates and signs:
   ```
   DelegateAction {
     sender_id: "alice",
     receiver_id: "bob",  // contract that always panics
     actions: [FunctionCall { method: "always_fail", deposit: 100 NEAR, gas: 10 TGas }],
     nonce: ..., max_block_height: ..., public_key: alice_key
   }
   ```
2. Alice sends the `SignedDelegateAction` to the relayer.
3. Relayer wraps it in a transaction (relayer is signer, pays 100 NEAR deposit + gas).
4. On Alice's shard: `apply_delegate_action` spawns a receipt with `predecessor_id = alice`, `signer_id = relayer`.
5. On Bob's shard: `always_fail` panics → receipt fails → `refund_unspent_gas_and_deposits` runs → `deposit_refund = 100 NEAR` → `Receipt::new_balance_refund(alice, 100 NEAR)`.
6. Alice's balance increases by 100 NEAR. Relayer's balance decreases by 100 NEAR (net loss after gas refund).

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
