### Title
Front-runnable `BOOTSTRAP` declare transaction can permanently squat a system class hash, causing DOS to network bootstrap - (File: `crates/starknet_api/src/executable_transaction.rs`, `crates/blockifier/src/transaction/account_transaction.rs`, `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo`)

### Summary
The Allo report describes an unprivileged, unauthenticated `initialize()` entry point that any attacker can front-run right after deployment to permanently corrupt one-time setup state and cause DOS. The sequencer has a structurally identical pattern: a hardcoded, unauthenticated "bootstrap" declare path, reachable by anyone who can construct a `DECLARE` transaction with `sender_address == bootstrap_address()` and `nonce == 0`, that skips all account validation/signature checks and permanently commits a class-hash→compiled-class-hash mapping via a "declare-once" (`prev_value == 0`) guard.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` treats any V3 declare transaction as privileged "bootstrap" traffic purely based on well-known, public constants — `sender_address == bootstrap_address()` (the fixed felt for the ASCII string `'BOOTSTRAP'`) and `nonce == Nonce(Felt::ZERO)` and `charge_fee == false`: [1](#0-0) 

When this predicate is true, `AccountTransaction::execute_raw` completely skips validation and fee-related pre-checks, and directly runs the declare's execute logic: [2](#0-1) 

The matching Starknet OS logic in the Cairo program performs the same unauthenticated shortcut and commits the class declaration with a "declare-once" guard (`prev_value=0`), meaning whichever bootstrap-style declare for a given `class_hash` lands first wins permanently: [3](#0-2) 

There is no signature requirement (the account's `__validate_declare__` is never invoked), and `sender_address`/`nonce`/fee fields are all public, deterministic constants — anyone can craft this transaction. There is a gateway-level allowlist knob, `authorized_declarer_accounts` (`GatewayStaticConfig::is_authorized_declarer`), but it is an `Option<Vec<ContractAddress>>` — [4](#0-3)  — and its enforcement/default behavior for the bootstrap address specifically could not be fully verified within the scope of this investigation (see caveat below).

Test/integration code confirms the class hash can only be declared once via this path, and a second attempt (even a legitimate one for the same class hash) fails with "already declared": [5](#0-4) [6](#0-5) 

### Impact Explanation
If the gateway/mempool does not restrict who may submit a transaction with `sender_address = bootstrap_address()` (this is the open question — see caveat), any unprivileged party observing a legitimate bootstrap declare (e.g., of a core/system contract class during network genesis or an authorized upgrade window) in the mempool/p2p layer can front-run it with their own `BOOTSTRAP`/nonce-0/zero-fee declare for the exact same `class_hash` but a different (malicious or garbage) `compiled_class_hash`. Because the class/compiled-class mapping is committed with a strict "declare-once" (`prev_value == 0`) check both in the blockifier execution path and in the Starknet OS re-execution, the attacker's transaction wins the race, permanently squatting that class hash with the wrong compiled class. The legitimate bootstrap declare then fails forever (class already declared), and any dependent deployment/upgrade flow relying on that specific class hash is permanently blocked — a direct DOS of network bootstrap, matching the "impact HIGH / likelihood MEDIUM" characterization in the source report.

### Likelihood Explanation
The bootstrap sender address, nonce, and zero-fee/zero-max-fee conditions are all public constants (`0x424f4f545354524150` = ASCII `'BOOTSTRAP'`, nonce `0`), requiring no privileged key material to construct the transaction — exactly like the Allo `initialize()` case where the attacker needs no funds, only correct calldata and timing (mempool/mempool-ordering race). The main mitigating factor, and the one point of uncertainty, is whether `authorized_declarer_accounts` (or an equivalent gateway-side allowlist check applied specifically to the bootstrap address) is enforced by default; I could not fully confirm this from the available code within this session.

### Recommendation
- Restrict the bootstrap declare path so it is only accepted from a specific, pre-configured operator/genesis process (e.g., require gateway-side rejection of any `BOOTSTRAP`-sender declare unless the node is explicitly in a "genesis/bootstrap" mode, or require an out-of-band authorization signature even for the bootstrap sender).
- Ensure `authorized_declarer_accounts` (or a dedicated bootstrap-allowlist) is enforced unconditionally for `sender_address == bootstrap_address()`, not merely available as an opt-in config.
- Consider binding the "declare-once" guard to an explicit governance/ordering mechanism (e.g., only accept the first bootstrap declare from a designated sequencer/proposer identity) rather than purely first-committed-wins based on public constants.

### Proof of Concept
1. Attacker observes (or predicts) that a legitimate `BOOTSTRAP` declare transaction for class hash `C` (a critical system contract) is about to be/has been submitted.
2. Attacker crafts their own `DeclareTransactionV3` with `sender_address = bootstrap_address()` (`'BOOTSTRAP'`), `nonce = 0`, `class_hash = C`, `compiled_class_hash = <garbage>`, and zero resource bounds/fee, per `generate_bootstrap_declare` pattern: [7](#0-6) 
3. If the gateway does not block unauthorized bootstrap senders, this transaction is admitted to the mempool/gets included in a block before the legitimate one (front-run via gas/tip ordering or network propagation timing).
4. Execution hits `is_bootstrap_declare` → true, skips validation, commits `class_hash=C → compiled_class_hash=<garbage>` via the `prev_value=0` guard: [8](#0-7) 
5. The legitimate bootstrap declare for `C` subsequently fails execution because the class is already declared, permanently blocking the intended bootstrap/deployment flow for that class hash.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {

                    tx_context.clone(),
