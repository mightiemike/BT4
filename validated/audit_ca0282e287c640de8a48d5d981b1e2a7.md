### Title
Witness can arbitrarily raise its own brokerage rate at will and retroactively capture voter reward for a cycle already in progress via `UpdateBrokerageContract` - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
Any account registered as a witness (super representative candidate) can broadcast an unprivileged `UpdateBrokerageContract` transaction at any time to change its own brokerage (fee-cut) percentage, with no restriction on how often or when it can be changed. Because the reward-payment path reads the brokerage rate for the *current* cycle at the moment rewards are actually paid out, and that current-cycle rate is only snapshotted once at the *end* of the cycle from the live/mutable value, a witness can set a low or zero brokerage to attract votes, then raise it to the maximum (100%) immediately before the cycle's maintenance/reward-settlement point, capturing reward that economically belongs to the voters who delegated their votes earlier in that same cycle. This mirrors the Cally `feeRate` bug: an unrestricted, unilaterally-controlled rate parameter is applied against value/positions that were already committed under a different (lower) rate, letting the controlling party siphon funds intended for a counterparty.

### Finding Description
`UpdateBrokerageActuator.execute()` unconditionally accepts any `brokerage` value in `[0, 100]` from the witness owner and stores it via `delegationStore.setBrokerage(ownerAddress, brokerage)`, which writes to the "current" (`cycle = -1`) slot with no time-lock, cooldown, or restriction tied to the voting cycle: [1](#0-0) [2](#0-1) 

The only validation performed is a bound check `0 <= brokerage <= 100` and that the account is a registered witness — no check on cycle timing or on how recently the value was last changed: [3](#0-2) 

The per-cycle brokerage snapshot used for the *next* cycle is copied at maintenance time from whatever the live ("current") value happens to be at that instant: [4](#0-3) 

At reward-payout time, `MortgageService.payReward` reads the brokerage for the current cycle and computes the witness's cut against the *entire* reward that has accrued for that cycle (including the portion earned from votes that were cast while a different — potentially much lower — brokerage rate was advertised/in effect): [5](#0-4) 

Because votes accumulate value over an entire cycle (`countVote`/`doMaintenance` tally votes across the whole cycle) while the brokerage percentage applied to the resulting reward is only fixed for "the current cycle" at the single maintenance boundary, a witness can change its brokerage value multiple times within a cycle — including right up until the moment `doMaintenance()` runs and snapshots it forward — without ever being tied to the rate that was in effect when voters actually delegated their stake to that witness.

This is functionally the same defect pattern as the Cally `feeRate`: a single mutable rate value that applies retroactively/globally to already-accrued value with no lock-in at commitment time, controlled unilaterally by the party who benefits from raising it, and reachable via ordinary (non-privileged-governance) transactions — `UpdateBrokerageContract` does not require the super-majority committee proposal process that other fee-type parameters (e.g., `ENERGY_FEE`, `TRANSACTION_FEE`) go through via `ProposalService`/`ProposalUtil`.

### Impact Explanation
Voters who delegate their vote/stake to a witness expecting a given payout split (e.g., low brokerage) can have their share of block/standby rewards for the same cycle diverted to the witness if the witness raises `brokerage` toward 100 before the cycle's reward is finalized/paid. This is a real value-transfer griefing/theft vector against TRX holders who vote for witnesses, exploitable by any account that can become a witness — no elevated protocol privilege (e.g., committee/owner key) is required, only being a registered SR.

### Likelihood Explanation
Likelihood is moderate-to-high: becoming a witness only requires sufficient votes (not a privileged system role), `UpdateBrokerageContract` is a normal broadcastable transaction with no rate-limit/cooldown, and the incentive to snipe brokerage right before the maintenance cycle boundary is straightforward and repeatable every cycle. The main uncertainty is the precise timing granularity of how "current cycle" brokerage is captured relative to reward accrual per block versus at the single `doMaintenance()` boundary — this could not be fully traced to the exact block-level reward accrual formula (`accumulateWitnessVi`, `computeReward`) in the time available, so the exact magnitude of exploitable value per cycle is not fully quantified here.

### Recommendation
- Lock the brokerage rate that applies to a cycle's rewards to the value that was in effect when votes for that cycle were cast (i.e., snapshot brokerage per-voter or per-vote at vote time rather than reading a live "current" value at payout).
- Alternatively, enforce a minimum lock-in delay (e.g., changes to `brokerage` only take effect starting from the *next* cycle after the one in which the change was submitted, never affecting the cycle already in progress), analogous to fixing the fee rate at "vault creation" recommended for the Cally finding.
- Add a rate-of-change limit/cooldown on `UpdateBrokerageContract` (e.g., max one change per cycle, or a maximum delta per change) to prevent last-moment sniping.

### Proof of Concept
1. Witness W registers and advertises `brokerage = 0` via `UpdateBrokerageContract` at the start of cycle N, attracting voters who expect to keep 100% of their share of W's rewards. [1](#0-0) 
2. Voters cast votes for W throughout cycle N; `MaintenanceManager.countVote`/`doMaintenance` accumulate these votes for W's total `voteCount` over the whole cycle. [6](#0-5) 
3. Immediately before the maintenance boundary for cycle N (where `doMaintenance()` snapshots brokerage forward and increments the cycle number), W submits another `UpdateBrokerageContract` setting `brokerage = 100`. [7](#0-6) 
4. When `MortgageService.payReward` computes the split for the reward accrued during cycle N, it reads the current brokerage (now 100) and routes the entire reward to the witness's allowance instead of to `delegationStore.addReward` for voters. [5](#0-4)

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
