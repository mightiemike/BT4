### Title
`KVSessionStorage.storeSession()` never deduplicates the per-shop session-id index, causing unbounded growth and eventual write/read failure of session storage - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage` maintains a secondary index (`shop:<domain>` key holding a JSON array of session ids) so `findSessionsByShop` can work on top of Cloudflare KV, which has no native secondary-index support. `storeSession()` unconditionally appends the session id to that array on every call, including calls that simply re-persist (overwrite) an *already-existing* session id. Nothing ever checks whether the id is already present before appending, so the "accounting" array grows without bound every time the same session is re-stored, exactly mirroring the reported bug class where a state-mutating operation (`emergencyRevoke`) fails to update the companion accounting value (`categoryUsed`), leaving the tracked state permanently and incorrectly inflated.

### Finding Description
`storeSession` always calls `addShopIds`, which reads the current array, appends the new id(s), and writes it back with no existence check: [1](#0-0) [2](#0-1) 

`storeSession()` is not a one-time, admin-triggered operation — it is invoked automatically, per authenticated request, from multiple unprivileged, merchant/customer-reachable auth code paths whenever a session needs to be (re)persisted:

- Offline token refresh (`expiringOfflineAccessTokens` future flag) re-stores the same offline session id every time the token nears expiry, on ordinary authenticated requests: [3](#0-2) 
- Token-exchange authentication re-stores the (same) offline/online session id whenever the app determines the existing session is missing/inactive: [4](#0-3) 
- The equivalent Express and React Router middlewares have identical `storeSession` calls on the same trigger conditions: [5](#0-4) 

Because `deleteSession`'s companion `removeShopIds` correctly filters out an id, but `addShopIds` has no equivalent "already present" guard, the two operations are asymmetric: every re-store (overwrite) permanently and incorrectly grows the shop's id list, exactly like `categoryUsed` in the report was permanently and incorrectly inflated by a mutating operation that failed to reconcile the companion accounting state.

### Impact Explanation
An attacker who is a normal, unprivileged merchant/customer of the installed app can repeatedly trigger session-token exchange or force offline-token refresh cycles (both are normal, App-Bridge/Shopify-Admin-driven request flows that happen automatically and can be repeated at will by simply issuing many authenticated requests with stale/expiring session tokens). Each cycle appends a duplicate copy of the same session id to the `shop:<domain>` KV value. Over time:
- `findSessionsByShop()` returns an ever-growing, duplicated list, degrading in performance and correctness for any code that depends on this to enumerate sessions per shop.
- The KV value for the shop key grows unbounded and will eventually exceed Cloudflare KV per-value limits, causing `put()` to fail. At that point, `storeSession` (and thus authentication/token-refresh flows) start failing for that shop, effectively causing denial of service of the auth/session-persistence layer for the affected shop — a stuck/locked state that, like the reported bug, cannot be fixed except by manually clearing/repairing the underlying KV data out-of-band.

### Likelihood Explanation
Every authenticated request that lands on a stale or refreshed session (a routine, frequent occurrence in normal app usage, and one an attacker/merchant can force by repeatedly presenting near-expiry/invalid session tokens or by requesting an app page rapidly) triggers this code path. No privileged access is required — any merchant/customer of the app can drive this simply through normal browser/API usage patterns, making the growth condition highly likely to be reached in any long-lived, moderately active shop.

### Recommendation
Update `addShopIds` (and `storeSession`) to deduplicate before writing, e.g.:

```diff
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
- await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
+ const merged = Array.from(new Set([...shopIds, ...ids]));
+ await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
```ts
import {KVSessionStorage} from '@shopify/shopify-app-session-storage-kv';
import {Session} from '@shopify/shopify-api';

// namespace is a mock/in-memory KVNamespace implementation
const storage = new KVSessionStorage(namespace);

const session = new Session({
  id: 'offline_test-shop.myshopify.com',
  shop: 'test-shop.myshopify.com',
  state: '',
  isOnline: false,
  accessToken: 'token',
});

// Simulate repeated re-persistence of the SAME session id, as happens on
// every offline-token-refresh / token-exchange cycle triggered by normal
// authenticated traffic.
for (let i = 0; i < 1000; i++) {
  await storage.storeSession(session);
}

const sessions = await storage.findSessionsByShop('test-shop.myshopify.com');
// sessions.length === 1000 (all duplicates of the same session id),
// and the underlying `shop:test-shop.myshopify.com` KV value now contains
// 1000 duplicate id strings and keeps growing on every future call.
```
