## Title
Token exchange marks the offline session "active" before the `afterAuth` completion hook succeeds, permanently skipping that hook on retry — ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts])

### Summary
In the token-exchange authentication strategy (shared pattern across `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express`), the offline `Session` obtained from `tokenExchange` is persisted to `sessionStorage` and marked usable *before* the `afterAuth` hook has completed. If the `afterAuth` hook subsequently throws (any transient failure — DB write, outbound webhook registration call, etc.), the request fails with a 500, but the session is already stored as active. On the next request, the code takes the "session is already active" fast path and never re-attempts the exchange or the `afterAuth` hook, permanently skipping app completion logic for that shop/session lifetime.

### Finding Description
`authenticate()` in `token-exchange.ts` only performs the token exchange + `handleAfterAuthHook` call when there is no active session: [1](#0-0) 

The offline session is stored via `config.sessionStorage!.storeSession(offlineSession)` immediately after the token exchange succeeds, well before the `afterAuth` hook runs: [2](#0-1) 

If `handleAfterAuthHook` throws for any reason (transient error in a custom `afterAuth` hook, or in `triggerAfterAuthHook`), the strategy converts it into a `500 Internal Server Error` response, but by this point `storeSession` has already succeeded, so the session is durably marked active: [3](#0-2) 

On the *very next* request from the same shop, `authenticate()` loads the already-stored, active session and returns immediately at the bottom of the function — never re-entering the `if (!session || !session.isActive(...))` branch, and therefore never calling the token exchange or the `afterAuth` hook again: [4](#0-3) 

The identical structure exists in `packages/apps/shopify-app-react-router/src/server/authenticate/admin/strategies/token-exchange.ts` and in `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`, where the "session is active" short-circuit is at the top of the handler: [5](#0-4) [6](#0-5) 

This is the same class of bug as the reported issue: a state transition (Short Record → `PartiallyFilled` / Session → stored & active) is committed to durable storage without guaranteeing that a *required linked action* (adding the remaining Short Order to the market / running the `afterAuth` completion hook) actually happened, and subsequent code paths treat the "committed" flag alone as sufficient, permanently skipping the required linked action once the flag is set.

### Impact Explanation
The `afterAuth` hook is the documented extension point apps use to complete installation-critical work immediately after obtaining an access token (e.g., registering webhooks, writing shop records, initializing billing, other one-time setup). Because the session is persisted and marked "active" before this hook succeeds, a single transient failure in the hook (unprivileged flow — this fires for any real merchant install/reinstall/re-authentication, not a privileged actor) permanently prevents that hook from ever running again for the lifetime of that offline session (which by default has no expiry unless `expiringOfflineAccessTokens` is enabled, and even then only refreshes near expiry, not on failure). This can leave critical app-side webhook subscriptions or database provisioning permanently absent for a shop, degrading or entirely denying app functionality that depends on the hook running — a functional/DoS impact on the authentication completion handler itself, without any way for the shop to recover short of the app operator manually invalidating the stored access token.

### Likelihood Explanation
Any transient error inside a custom `afterAuth` hook (network blip calling the Admin API to register webhooks, momentary DB unavailability, etc.) triggers this every time, and it requires no privileged access or special conditions beyond a normal single-merchant OAuth/token-exchange flow completing once. Given that `afterAuth` hooks commonly make outbound network calls (e.g., `registerWebhooks`), which are inherently more failure-prone than in-memory operations, this is a realistically frequent occurrence in production.

### Recommendation
Only persist the session as "active"/complete after the `afterAuth` hook has succeeded, or track hook completion as a separate durable flag independent of session activity so that a session being "active" is not conflated with "post-auth setup completed." Concretely: store the session with a non-final/pending marker (or store it after the hook succeeds instead of before), and have the `isActive()` fast-path check also account for whether the required completion hook has run; otherwise, re-run `afterAuth` (idempotently) whenever it is known not to have completed successfully, rather than relying solely on session activity as the gate.

### Proof of Concept
1. Configure an app with `future.tokenExchange`/embedded token-exchange strategy and an `afterAuth` hook that occasionally throws (simulate with a hook that fails on the first call, e.g. due to a transient webhook-registration API error).
2. Trigger the flow: a request arrives with a valid session token, no existing active session found, `exchangeToken` succeeds, `config.sessionStorage!.storeSession(offlineSession)` succeeds — session is now active in storage.
3. `handleAfterAuthHook` throws → strategy returns/throws a `500 Internal Server Error`. Confirm the session is nonetheless present and `isActive()` in the configured `sessionStorage`.
4. Issue a subsequent request with a fresh session token for the same shop. Observe that `authenticate()` loads the stored session, finds `session.isActive(...)` true, and returns `session!` directly — verify (e.g. via a spy/mock on `afterAuth`) that the hook is never invoked again, even though it never succeeded on step 3.
