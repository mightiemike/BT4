### Title
Replay-verify accepts divergent state-checkpoint (SMT) roots because `ensure_match_transaction_info` never checks `state_checkpoint_hash` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity gate used by `db-tool replay-on-archive` (and `aptos-debugger`) to confirm that re-executing a transaction locally reproduces the same committed result recorded in a backup/archive `TransactionInfo`. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but does not check `state_checkpoint_hash` (the Sparse-Merkle-Tree / JMT state root at that checkpoint), nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. This is explicitly acknowledged by a `TODO` in the code itself.

### Finding Description [2](#0-1) 

The function walks through fields that must match between the freshly-computed `TransactionOutput` and the archived/expected `TransactionInfo`:
- `status` vs `expected_txn_status` [3](#0-2) 
- `gas_used` [4](#0-3) 
- `write_set_hash == txn_info.state_change_hash()` [5](#0-4) 
- `event_root_hash == txn_info.event_root_hash()` [6](#0-5) 

It then returns `Ok(())` without ever comparing the recomputed Jellyfish/Sparse Merkle state root (`state_checkpoint_hash`) or the newer `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields, as the comment states: *"this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."* [7](#0-6) 

This is the sole verification step in `Verifier::execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs`, which passes locally-executed `TransactionOutput`s and archived `expected_txn_infos`/`expected_writesets`/`expected_events` straight into `ensure_match_transaction_info` and treats `Ok(())` as proof the replay reproduced the exact committed ledger state [8](#0-7) . Because the write set (`state_change_hash`) is checked but the resulting state tree root (`state_checkpoint_hash`) is not, a state root computed incorrectly at commit time — e.g., from a wrong/incomplete write set that still hashes identically for `state_change_hash` purposes but is applied to the wrong SMT positions, or a bug in JMT/hot-state root computation itself — would silently pass replay verification.

### Impact Explanation
This tool is one of the primary mechanisms used to validate that historical/archived ledger data (backed up state, restored databases) reproduces byte-identical results from independent re-execution — the exact "replay, restore, or proof verification" integrity pivot called out in scope. A bug in state-checkpoint/hot-state root computation (or a corrupted archive) that alters `state_checkpoint_hash` while write-set/event hashes still match would go undetected, meaning replay-verify could falsely certify a divergent, corrupted, or hard-forked state root as consistent with the original chain. This directly undermines the guarantee that "committed state that differs from the correct VM result" is detected.

### Likelihood Explanation
This is not attacker-triggered on mainnet directly (it's an offline verification tool), but the missing check is unconditional and always reachable whenever `replay_on_archive` or the debugger's transaction-info verification path is used — there is no privileged assumption required to hit the gap; it is a deterministic logic omission that the code's own author flagged as a known deficiency ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`").

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute the state-checkpoint (and, once trading-native state roots are enabled, hot-state/position-state checkpoint) hash from the actual post-execution state view, and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, mirroring the existing `write_set_hash`/`event_root_hash` checks, before this comparator is relied upon as a correctness gate for replay/restore verification.

### Proof of Concept
Not applicable as an on-chain exploit — this is a verification-tooling gap. Conceptually: construct (or corrupt) an archived `TransactionInfo` whose `state_checkpoint_hash` does not match the true post-execution SMT root but whose `state_change_hash` (over the write set) and `event_root_hash` still match (e.g., through a state-tree-application bug that misplaces a write without changing the write-set's own hash, or a corrupted/malformed backup snapshot). Running `db-tool replay-on-archive` over that range would call `ensure_match_transaction_info`, which never inspects `state_checkpoint_hash`, and would report success despite the state root being wrong [7](#0-6) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
