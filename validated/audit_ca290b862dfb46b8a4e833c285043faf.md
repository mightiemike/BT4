### Title
Replay-verification tool never validates the state-checkpoint (state root) hash, silently accepting state-corrupting divergences - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole check used by `storage/db-tool/src/replay_on_archive.rs` (and `aptos-move/aptos-debugger`) to confirm that re-executing an archived transaction reproduces the historically committed result. It compares status, gas, write-set hash, and event-root hash against the trusted `TransactionInfo`, but never compares the `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) fields — the very fields that commit to the resulting Jellyfish Merkle state root. This is acknowledged in-code by a `TODO(trading-native)` comment but is a live gap today, not merely a future-feature caveat, since the function performs no state-root check for any code path currently exercising it.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) checks: [1](#0-0) 
only `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`. It never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` — fields present on both `TransactionInfoV0` and `TransactionInfoV1` and hashed into the `TransactionInfo` that is itself the leaf committed to the transaction accumulator (and thus authenticated by validator signatures on the `LedgerInfo`).

This comparator is invoked directly by the archive-replay auditing tool: `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` re-executes historical transactions against local `AptosVMBlockExecutor` output and calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` to decide pass/fail: [2](#0-1) 
Because the state-checkpoint hash is skipped, a re-executed transaction whose resulting state (post-write-set-application state root) diverges from the archived, ledger-info-authenticated value — e.g. due to nondeterministic execution, a storage/serialization bug, a hard-fork-only code path difference, or corrupted archive-side state metadata not reflected in the write set itself — will be reported as a successful, matching replay.

By contrast, the executor's *online* re-verification path (`execution/executor-types/src/ledger_update_output.rs:92-114`, used by `ReplayChunkVerifier` in `execution/executor/src/chunk_executor/chunk_result_verifier.rs`) compares full `TransactionInfo` structs with `==`, which does include the checkpoint hash fields. So the gap is specific to the offline/debugging comparator (`ensure_match_transaction_info` on `TransactionOutput`), not the in-process chunk-executor consensus/state-sync path.

### Impact Explanation
This weakens the primary tool operators use to detect state-commitment corruption or hard-fork divergence when auditing historical ledger data (`replay_on_archive`, and `aptos-debugger`'s diff printer). If a bug causes locally re-executed state to diverge from the archived, cryptographically-authenticated state root while write set, events, gas, and status still coincidentally match, the tool reports success — masking a real state-integrity break instead of flagging it. This falls in the "Hard-fork-only divergence during commit, replay ... verification" and "authenticated ... state-view output bound to the wrong version, object, or proof context" categories, since a corrupted/incorrect state root would go undetected by the intended verification mechanism.

### Likelihood Explanation
The gap is unconditional — it does not depend on any feature flag being enabled, and is exercised on every call to `ensure_match_transaction_info` today. Triggering an actual state-checkpoint-hash divergence still requires some underlying non-determinism or execution/storage bug, but once such a divergence exists, this checker cannot catch it, defeating its purpose. Likelihood of the *detection failure itself* is deterministic/always-on.

### Recommendation
Add comparisons for `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` in `TransactionOutput::ensure_match_transaction_info` (computing the actual post-write-set state root during replay and comparing it against `txn_info.state_checkpoint_hash()`), rather than deferring this to a future `COMPUTE_TRADING_NATIVE_STATE_ROOTS` gate. At minimum, replay-verify tooling should compute and check the state root explicitly so archive-replay auditing cannot silently pass over state-corrupting divergences.

### Proof of Concept
Not directly exploitable against mainnet consensus (this code path is off the hot commit/consensus path), but demonstrable by constructing a `TransactionOutput` whose write set/events/gas/status match a given `TransactionInfo` but whose actual resulting state root would differ (e.g., feed `ensure_match_transaction_info` a `TransactionInfo` with an arbitrary/incorrect `state_checkpoint_hash`) — the call returns `Ok(())` unconditionally regardless of the checkpoint-hash value, as seen at [3](#0-2) .
