Looking at the `apply_delegate_action` function in `runtime/runtime/src/actions.rs`, I found a direct off-by-one analog to the Infiltration bug.

---

### Title
DelegateAction Expiry Check Uses Strict `>` Instead of `>=`, Allowing Execution One Block Past `max_block_height` — (File: `runtime/runtime/src/actions.rs`)

### Summary

`apply_delegate_action` checks `apply_state.block_height > delegate_action.max_block_height()` to decide whether a `DelegateAction` has expired. The protocol specification and the field documentation both state the action should be invalid when `block_height >= max_block_height`, but the code uses strict `>`, granting one extra block of validity. A relayer can therefore execute a signed `DelegateAction` at the exact block the sender intended as the expiry, violating the sender's authorization boundary.

### Finding Description

In `runtime/runtime/src/actions.rs` at line 435:

```rust
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

The `DelegateAction` struct documents `max_block_height` as:

> "The maximal height of the block in the blockchain **below which** the given DelegateAction is valid."

"Below which" means valid for heights strictly less than `max_block_height`; the action should be invalid at height `== max_block_height`. The runtime spec in `docs/RuntimeSpec/Actions.md` line 402 is even more explicit:

> "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired`

The code contradicts both sources. With `>` instead of `>=`, the action is accepted at `block_height == max_block_height` and only rejected at `block_height == max_block_height + 1`. The existing unit test `test_delegate_action_max_height` only exercises `max_block_height + 1`, leaving the boundary case untested and the bug undetected.

### Impact Explanation

A user (sender) signs a `DelegateAction` and hands it to a relayer. The sender sets `max_block_height = N` to express "this authorization expires before block N." Following the documented semantics, the sender may take other actions at block N assuming the delegate is already expired (e.g., re-key, transfer funds, revoke). Because the runtime still accepts the `DelegateAction` at block N, the relayer can execute the delegated inner actions — transfers, function calls, key operations — at the exact block the sender believed was safe. This constitutes unauthorized transaction execution: the sender's intended authorization window is silently extended by one block.

### Likelihood Explanation

Any unprivileged user who creates a `DelegateAction` (meta-transaction) and relies on `max_block_height` for time-bounded authorization is affected. The relayer only needs to submit the action at the boundary block. No special privileges, validator access, or network-level capabilities are required.

### Recommendation

Change the strict greater-than to greater-than-or-equal in `apply_delegate_action`:

```rust
// Before
if apply_state.block_height > delegate_action.max_block_height() {

// After
if apply_state.block_height >= delegate_action.max_block_height() {
```

Add a test asserting `DelegateActionExpired` when `block_height == max_block_height`, mirroring the existing `test_delegate_action_max_height` which only covers `max_block_height + 1`.

### Proof of Concept

1. Sender creates and signs a `DelegateAction` with `max_block_height = 100` and hands it to a relayer.
2. Sender believes the action expires at block 100 (per the documented semantics "below which").
3. At block 100, the relayer submits the action.
4. `apply_delegate_action` evaluates `100 > 100` → `false` → no expiry error.
5. The inner actions (e.g., a `Transfer`) execute against the sender's account at block 100.
6. The sender's funds are moved without their current consent, one block after they believed the authorization had lapsed.
