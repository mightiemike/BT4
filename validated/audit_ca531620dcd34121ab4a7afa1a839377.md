### Title
Permanent DoS of the on-chain order-book queue via an unhandled `ArithmeticException` inside the maker-order matching loop - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator` maintains an on-chain analog of the "order queue" described in the report: a persistent, FIFO linked list of maker orders (`MarketOrderIdListCapsule`/`MarketOrderStore`) that is always processed starting at the list `head`. Every future `MarketSellAssetContract` transaction that targets the same trading pair is forced to match against this same head order first. If processing of that specific head order throws an exception type that is not caught by the actuator's `execute()` handler, the head order can never be consumed or removed, permanently freezing the trading-pair queue for all users — directly analogous to the reported "order queue becomes stuck" bug class.

### Finding Description
`matchOrder()` walks the maker-order linked list strictly from `orderIdListCapsule.getHead()` [1](#0-0) , and only removes the head maker order from the queue if `matchSingleOrder()` completes successfully and the remaining sell quantity hits `0` [2](#0-1) . There is no analog of a try/catch-and-skip mechanism around an individual order the way the report's keeper queues use — instead, the entire `execute()` call is wrapped by a narrow catch clause that only tolerates `ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, and `ContractValidateException` [3](#0-2) .

Inside `matchSingleOrder()` and its helpers (`addTrxOrToken`, `MarketUtils.multiplyAndDivide`, `subtractExact`), several arithmetic operations use `Math.addExact`/`subtractExact`-style exact arithmetic that throw `ArithmeticException` on overflow [4](#0-3) , [5](#0-4) . `ArithmeticException` is a `RuntimeException`, not any of the four types caught in `execute()`. If a matching attempt against the current head maker order deterministically triggers such an unhandled exception (e.g., because the maker order's stored `buyTokenId` account balance combined with the fill amount overflows a `long`, or any other unexpected runtime exception surfaces from the linked-list/store traversal), the exception propagates uncaught out of `execute()`, up through `RuntimeImpl.execute()` [6](#0-5)  and `TransactionTrace.exec()` [7](#0-6) .

Because the head order is never removed when this happens, every subsequent `MarketSellAssetContract` transaction attempting to trade against that pair/price level will re-enter `matchOrder()`, hit the exact same head order, and reproduce the same unhandled exception. This freezes the market order book for that trading pair indefinitely — the on-chain equivalent of the report's "queue becomes stuck," except here the impact is broader: an uncaught runtime exception during transaction processing (called from `Manager.processTransaction`/`generateBlock` and validated node-wide) risks destabilizing block validation/production for any node that attempts to include or validate such a transaction, not merely a single user's funds.

### Impact Explanation
This is reachable by an anonymous broadcast transaction (`MarketSellAssetContract`), requiring no privileged role. If triggered, the maker order at the head of a given trading-pair/price-level queue becomes permanently un-removable, blocking all future matching against that price level and denying order-book liquidity to legitimate users — an on-chain DoS. Depending on whether the uncaught exception surfaces during block *validation* (as opposed to only during the submitter's own transaction), it can also cause inconsistent transaction outcomes/exceptions across nodes validating the same block, which is a consensus-safety concern.

### Likelihood Explanation
Likelihood is moderate: the theoretical trigger requires crafting maker/taker order quantities whose product/sum in `multiplyAndDivide`/`addExact`/`subtractExact` overflows a `long`, or reaching some other runtime exception path in the linked-list traversal (e.g., transient store corruption after a partial write, similar to the "external report" scenario where blacklisting causes a revert outside the try/catch). Quantities are bounded by `dynamicStore.getMarketQuantityLimit()` in `validate()` [8](#0-7) , which likely constrains the overflow vector for `sellTokenQuantity`/`buyTokenQuantity` directly, but this bound is not verified to cover every downstream multiplication/accumulation path in `matchSingleOrder`, `addTrxOrToken`, and account balance accumulation, so the precise reachability of the overflow trigger could not be conclusively confirmed with the available code context.

### Recommendation
- Broaden the `execute()` catch clause in `MarketSellAssetActuator` to catch a generic `RuntimeException`/`Exception` boundary around the matching loop, converting any unexpected failure into a graceful `ContractExeException`/`ContractValidateException` without leaving the order-book state mutated.
- Alternatively (matching the report's preferred remedy), make the head-order removal path resilient: if a specific maker order cannot be matched safely (e.g., would overflow), automatically evict/skip that malformed order from the queue instead of aborting the whole transaction, so a single bad order can never block the queue.
- Add defensive overflow checks earlier in `validate()` covering the full computation chain (`multiplyAndDivide`, `addTrxOrToken` accumulation) rather than only the raw input quantities.
- Add regression tests that intentionally construct overflow-triggering quantities and confirm the transaction fails cleanly (with the head order remaining valid/tradable or safely evicted) rather than crashing block processing.

### Proof of Concept
Conceptual (not executed, given static analysis only):
1. Attacker submits `MarketSellAssetContract` A creating a maker order with `sellTokenQuantity`/`buyTokenQuantity` set near `Long.MAX_VALUE` bounds allowed by `getMarketQuantityLimit()`, placed at the head of a chosen pair/price queue via `saveRemainOrder()`.
2. Attacker (or any user) submits a second `MarketSellAssetContract` B on the opposite side that matches this order, causing `matchOrder()`→`matchSingleOrder()`→`addTrxOrToken`/`multiplyAndDivide` to overflow a `long` and throw `ArithmeticException`.
3. Because `execute()`'s catch block only handles four specific checked exceptions [3](#0-2) , the `ArithmeticException` propagates uncaught.
4. The maker order (still at `head`) is never removed from `MarketOrderIdListCapsule`, so every future transaction against that pair repeats step 2–3, permanently freezing the queue for that trading pair.

Confirmation of the exact overflow-reachable input values would require deeper testing/execution (e.g., a Devin session with test tooling) beyond what could be verified through static code reading alone.
