### Title
Missing enforcement of `TokenConfig.LiquidityCap` allows unbounded PRC20 minting via repeated inbound deposits - (File: x/uexecutor/keeper/handler.go)

### Summary
`TokenConfig.LiquidityCap` is a required, validated field (`ValidateBasic` rejects an empty value) intended to bound how much of a given external asset can be represented on Push Chain as PRC20. However, the deposit path that actually mints/credits PRC20 tokens never reads or checks this field, so the cap is entirely decorative.

### Finding Description
`TokenConfig.LiquidityCap` is defined in `proto/uregistry/v1/types.proto` and enforced only for non-emptiness in `x/uregistry/types/token_config.go` (`ValidateBasic`): [1](#0-0) 

The actual minting/crediting logic lives in `depositPRC20` (`x/uexecutor/keeper/handler.go`), which is invoked from every inbound execution path (`ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`). It fetches the `TokenConfig`, resolves the PRC20 contract address, and calls `CallPRC20Deposit` with the raw inbound amount — with no reference to `LiquidityCap` anywhere in the call chain: [2](#0-1) 

Grepping the entire `x/uexecutor` module and the `x/uregistry` keeper package for `LiquidityCap` returns zero matches outside of the type definition, validation, config JSON files, and tests — confirming no keeper logic ever reads or compares against it before minting PRC20 supply.

This is a stronger variant of the reported bug class (M-43's `maxTrainingDeposit`): where the original bug required an attacker to move balance to reset the per-account counter before exceeding the cap, here the cap check is entirely absent, so **no bypass trick is even required** — every single inbound deposit is unconditionally allowed regardless of cumulative liquidity, because the invariant "minted PRC20 supply must not exceed `LiquidityCap`" is never checked anywhere in the mint/deposit pipeline. Test evidence corroborates that repeated inbound deposits accumulate PRC20 balance without any bound: [3](#0-2) 

### Impact Explanation
An unprivileged external attacker who can produce valid inbound observations (i.e. relay/mirror real deposits on the source chain, which is the ordinary user flow) can mint PRC20 representation on Push Chain far beyond the intended `LiquidityCap` for that token/chain pair. Because `LiquidityCap` is meant to bound the native-asset backing that the Push Chain vault/gateway on the source chain actually holds, unbounded minting on the Push Chain side without a corresponding backing check breaks the PRC20 accounting invariant and can lead to under-collateralized PRC20 tokens circulating on Push Chain — i.e., an accounting corruption that maps to "corruption of PRC20 ... accounting" and effectively "unauthorized mint" of PRC20 supply beyond the registry-declared safe bound.

### Likelihood Explanation
High likelihood/always-reachable: this doesn't require any race condition, timing trick, or account manipulation — it triggers on the default, honest-validator inbound execution path for every single deposit, since the cap is simply never read. As soon as an external chain has more real depositor volume than the configured `liquidity_cap` (a per-token config value that is genesis/admin curated but not otherwise enforced at runtime), the invariant is silently exceeded with no on-chain signal.

### Recommendation
Enforce `TokenConfig.LiquidityCap` at deposit time: before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`, read the token's current outstanding minted supply (or track cumulative deposits per token config in `x/uexecutor`/`x/uregistry` state) and reject/queue the inbound if `currentSupply + amount > LiquidityCap`, mirroring the sherlock recommendation of validating against the true aggregate rather than trusting an unenforced field.

### Proof of Concept
1. Deploy a `TokenConfig` with `liquidity_cap = "1000000000000000000000000"` (1e24) as in `config/testnet-donut/*/tokens/*.json`. [4](#0-3) 
2. Submit N `MsgVoteInbound` batches (reaching quorum each time) for `TxType_FUNDS` with amounts that individually are below the cap but whose sum vastly exceeds `liquidity_cap`, as demonstrated in the "multiple solana FUNDS inbounds accumulate balance" test which shows balances accumulate unconditionally with no cap check: [3](#0-2) 
3. Observe that `depositPRC20` in `x/uexecutor/keeper/handler.go` never inspects `LiquidityCap`, so the PRC20 `balanceOf` for the recipient (or aggregate total supply) grows without bound past the configured cap, with no FAILED PCTx or rejection ever produced for exceeding it.

**Note on completeness:** I was unable to locate any PRC20 Solidity contract source in the index (searches for `mint`/`cap`/`_mint` inside PRC20-named files returned no matches), so I cannot fully rule out that supply-cap enforcement exists inside the PRC20 contract bytecode itself rather than in the Go keeper layer. Given the index size limits, some contract source files may not be indexed. I'd recommend confirming via a full Devin session with repository access whether `PRC20.sol` (or equivalent) enforces any supply cap independently of the `LiquidityCap` registry field, since that would materially affect the validity/severity of this finding.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
