## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state checkpoint hashes, letting replay-verify tooling accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the sole correctness gate used by Aptos's replay-verification tooling (`storage/db-tool/src/replay_on_archive.rs` and the transaction-debugger path in `aptos-move/cli/src/commands.rs`) to confirm that locally re-executed transactions match the archived/backed-up `TransactionInfo`. The function checks status, gas, write-set hash, and event-root hash, but explicitly skips `state_checkpoint_hash` and `hot_state_checkpoint_hash` (and `position_state_checkpoint_hash`), as acknowledged by its own TODO comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares four fields between a freshly-produced `TransactionOutput` and an externally supplied `TransactionInfo`: execution status, gas used, the write-set hash against `state_change_hash`, and the event root hash. It never compares `txn_info.state_checkpoint_hash()` or `txn_info.hot_state_checkpoint_hash()` against anything locally computed, as the trailing comment self-documents: [2](#0-1) .

These checkpoint hashes are not a future/inactive feature — `state_checkpoint_hash` and `hot_state_checkpoint_hash` are populated on every checkpoint transaction today, via `assemble_transaction_infos` in the executor: [3](#0-2) . They summarize the Sparse-Merkle-Tree world-state root (and hot-state root) at that version, computed in `DoStateCheckpoint::run`: [4](#0-3) .

This comparator is the acceptance criterion used by two real, unprivileged verification tools:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` to decide pass/fail for a chunk: [5](#0-4) .
- The CLI transaction debugger, which calls the same function to validate system-transaction replay: [6](#0-5) .

Because the state-root fields are excluded from the comparison, any divergence between the locally recomputed world-state root and the value recorded in the archived `TransactionInfo` — whether from a VM/state-checkpoint bug, a corrupted backup, or a hard-fork-only execution difference — produces a "match" verdict from `ensure_match_transaction_info`, even though the actual ledger state committed at that version is wrong.

### Impact Explanation
`replay-verify` and the archive-based debugger are the primary tools operators and auditors use to establish that a historical backup/archive faithfully reproduces on-chain execution, including the resulting state root. Since the state and hot-state checkpoint hashes are silently excluded from the check, this tooling can report a fully successful replay-verify run while the state root diverges from correct VM output — masking exactly the class of error (wrong accumulator/state root accepted as valid, hard-fork-only divergence not caught during replay/restore) that this verification path exists to catch. This directly undermines the integrity guarantee that backups/restores and replay-verify are meant to provide for authenticated state, without requiring any privileged access — a bug in state-checkpoint computation, or a tampered non-transaction-info-hash-covered archive path, would go undetected.

### Likelihood Explanation
This is not a hypothetical or speculative gap: the check is a normal Rust function called unconditionally by both production tools whenever they replay/verify transactions, and the code's own TODO acknowledges the missing checks are needed "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS" — but the `state_checkpoint_hash`/`hot_state_checkpoint_hash` gap applies today, independent of that unreleased feature flag, since those two fields are populated on every checkpoint transaction already.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the local state (and hot-state) checkpoint root at checkpoint boundaries and compare it against `txn_info.state_checkpoint_hash()` / `txn_info.hot_state_checkpoint_hash()` (and `position_state_checkpoint_hash()` once trading-native state roots are enabled), failing the check on any mismatch, consistent with how `write_set_hash` and `event_root_hash` are already validated.

### Proof of Concept
1. Take any archived `TransactionInfo` for a checkpoint transaction and mutate its `state_checkpoint_hash` (or corresponding `hot_state_checkpoint_hash`) to an arbitrary but well-formed `HashValue`, leaving `state_change_hash`, `event_root_hash`, `gas_used`, and `status` untouched.
2. Feed this mutated `TransactionInfo` alongside the correct transaction/output into `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` (or the CLI debugger's replay path) as the "expected" `TransactionInfo`.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` since the function never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`, at [7](#0-6) , causing the tool to report the chunk as successfully verified despite the checkpoint root diverging from what local execution actually produces.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
