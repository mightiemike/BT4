## Title
Merchant Custom App builds an authenticated Admin session from an unauthenticated `shop` query parameter, allowing privileged access-token requests to be redirected to an attacker-controlled shop domain - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`)

### Summary
For apps configured with `AppDistribution.ShopifyAdmin` ("merchant custom app" / custom store app), `authenticate.admin` skips OAuth and session-token verification entirely, and instead derives the `shop` used to build the authenticated `Session` directly from the request's raw, unauthenticated `shop` query string parameter. This value is only checked against a generic domain-suffix regex (`sanitizeShop`), not against any cryptographically verified source (JWT `dest`, HMAC-signed query, or signed cookie). The resulting `Session` — built via `customAppSession(shop)` — is subsequently used to make privileged Admin API calls with the app's statically configured access token, using the attacker-supplied `shop` as the API host. This mirrors the reported bug class: a variable, unauthenticated request parameter (`asset`/`receiver` in the P2P report, `shop` here) that determines a security-critical destination is never cross-validated against the actually authenticated identity, letting an attacker redirect a privileged operation.

### Finding Description
In `authStrategyFactory`, when `config.distribution === AppDistribution.ShopifyAdmin`, `getSessionTokenContext` takes the shortcut path that bypasses session-token/JWT validation: [1](#0-0) 

Here `shop` is read straight from `url.searchParams.get('shop')!` with no signature/HMAC/JWT covering it (contrast with the embedded-app branch just above, which derives `shop` from `payload.dest` of a cryptographically validated session token).

This `shop` value is passed into `strategy.authenticate(...)`, and for the `ShopifyAdmin` distribution the strategy is `MerchantCustomAuth`, whose `respondToOAuthRequests` is a no-op (no OAuth check at all for this distribution) and whose `authenticate` builds a session purely from the attacker-controllable `shop` string: [2](#0-1) 

`api.session.customAppSession(shop)` only re-validates the format of `shop` (must end in `myshopify.com`/`shopify.com`/`myshopify.io`/`shop.dev`), not that it is the shop the app was actually installed/configured for: [3](#0-2) 

The resulting `Session` (with `shop` fully attacker-controlled) is then handed to `createAdminApiContext` / `adminClientFactory`, which builds the outbound Admin GraphQL client URL from `session.shop`: [4](#0-3) 

Custom store apps use a single, statically configured `adminApiAccessToken` from `config` (per `packages/apps/shopify-api/lib/base-types.ts` and `docs/guides/custom-store-app.md`) rather than a per-request token tied to the verified identity of the caller. Because the `shop` field driving the destination host of the outbound Admin API request is never bound to a verified source, an app configured this way can be induced to send its privileged, statically configured access token to a hostname of the attacker's choosing (any domain matching the `myshopify.com`/`shopify.com`/`myshopify.io`/`shop.dev` suffix pattern, e.g. an attacker's own free development store), exactly as the report describes attackers manipulating unvalidated `asset`/`receiver` parameters to redirect where value flows.

I could not fully trace, within the remaining investigation budget, the exact line in `packages/apps/shopify-api/lib/clients/admin/graphql/client.ts` / `rest/client.ts` that substitutes `config.adminApiAccessToken` when `session.accessToken` is unset — this is inferred from the presence of `adminApiAccessToken` in `base-types.ts` and its heavy use across the custom-store-app tests/docs, but should be independently confirmed before relying on this analysis for a fix.

### Impact Explanation
If confirmed, any anonymous HTTP request to a merchant-custom-app's admin route with an attacker-chosen `?shop=` value causes the app's privileged, statically-configured Admin API access token to be used against a domain the attacker controls (any store on the `myshopify.com` family of domains). That results in the app's access token being sent (as an `X-Shopify-Access-Token` header or similar) to the attacker's shop, disclosing the app's live Admin API credential to the attacker — a direct secret-disclosure / SSRF-style vulnerability with high impact (full compromise of the app's Admin API privileges for the legitimate merchant).

### Likelihood Explanation
The `ShopifyAdmin` distribution path explicitly bypasses OAuth (`respondToOAuthRequests` is a no-op) and skips session-token/JWT validation (`getSessionTokenContext`'s early-return branch), so the vulnerable code path is reachable by any anonymous request that simply hits the app's document/admin route with a crafted `shop` query parameter — no authentication, secret, or privileged position is required to trigger it, only the ability to send an HTTP request to the app.

### Recommendation
For `AppDistribution.ShopifyAdmin` apps, do not derive `shop` from an unauthenticated query parameter. Bind the session's `shop` to the value the app was configured/installed for (e.g., a fixed value from app config, or a value cryptographically verified through a session token/JWT `dest` claim as is already done for embedded apps), and reject requests where the query-string `shop` does not match that verified value before constructing any `Session` or issuing any outbound Admin API request with the app's access token.

### Proof of Concept
1. Deploy/host a `shopify-app-remix` (or `shopify-app-react-router`) app configured with `distribution: AppDistribution.ShopifyAdmin` and a static `adminApiAccessToken` in its config (standard "custom store app" setup).
2. As an anonymous attacker, register a free Shopify development store, e.g. `attacker-dev.myshopify.com` (any subdomain satisfying the `sanitizeShop` regex works).
3. Send a request to the target app's admin-authenticated route with `?shop=attacker-dev.myshopify.com&...` (matching whatever other required non-signed params the doc-request path expects).
4. Because `getSessionTokenContext` takes the `ShopifyAdmin` branch, it builds `shop` purely from this query parameter (`packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts:220-221`), and `MerchantCustomAuth.authenticate` builds a `Session` for that shop without verifying it against the app's real configured shop (`packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts:35-48`, `packages/apps/shopify-api/lib/session/session-utils.ts:86-95`).
5. Any subsequent Admin GraphQL call made in that request context targets `attacker-dev.myshopify.com` using the app's real, privileged `adminApiAccessToken`, disclosing the token to the attacker's store's API logs/endpoint.

export function customAppSession(config: ConfigInterface) {
  return (shop: string): Session => {
    return new Session({
      id: '',
      shop: `${sanitizeShop(config)(shop, true)}`,
      state: '',
      isOnline: false,
    });
  };
}
