### Title
Uncontrolled Recursion in `get_recursive_transaction_results` Allows RPC-Triggered Stack Exhaustion - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` (`chain/chain/src/chain.rs:3052-3069`), used by `Chain::get_final_transaction_result` (`chain/chain/src/chain.rs:3073-3087`) to answer transaction-status JSON-RPC queries, recursively walks the receipt DAG produced by a transaction with **no depth limit**, unlike the analogous `get_receipt_to_tx` walk which explicitly enforces `MAX_DEPTH = 1000` (`test-loop-tests/src/tests/receipt_to_tx/errors.rs:158`, referenced from `chain/client/src/view_client_actor.rs`). This is directly analogous to the Avahi `lookup_handle_cname` bug: an externally reachable code path recurses once per hop in an attacker-influenced chain with no bound, risking native stack exhaustion.

### Finding Description [1](#0-0) 

`get_recursive_transaction_results` fetches the outcome for a receipt/tx id, pushes it onto the shared `outcomes` vector, and then, for every `receipt_id` produced by that outcome, calls itself again — this is genuine (non-tail, non-iterative) Rust recursion, one stack frame per hop of the receipt chain.

The depth of this recursion is controlled entirely by how many cross-contract "hops" (`promise_then`/`promise_batch_then` self-calls) a transaction's execution chain produces, e.g. via `max_self_recursion_delay` shown in the test contract: [2](#0-1) 

A single function call is bounded to roughly 56–221 hops by gas within one prepaid-gas budget (`slow_test_self_delay`, `integration-tests/src/tests/runtime/test_evil_contracts.rs:91-131`), but crucially each hop is a **separate receipt executed in a separate chunk/block with its own gas allotment**. Nothing prevents an attacker from chaining such promise callbacks across many blocks (each new promise refills the gas budget), producing a receipt chain thousands of hops deep over time, entirely from a single `SignedTransaction` submitted through normal RPC. This is unlike `EXPERIMENTAL_receipt_to_tx`, whose walker has an explicit, tested `MAX_DEPTH = 1000` guard (`test-loop-tests/src/tests/receipt_to_tx/errors.rs:157-228`) — showing the project is aware of this class of risk for chain-walking RPC handlers but did not apply the same protection to `get_recursive_transaction_results`.

When any RPC client subsequently queries the transaction's final status (the standard `tx`/`EXPERIMENTAL_tx_status` JSON-RPC method, served via `ViewClientActor`, `chain/client/src/view_client_actor.rs`), `get_final_transaction_result` → `get_recursive_transaction_results` recurses through the entire receipt tree with no cutoff, exactly mirroring the CNAME `lookup_handle_cname` pattern of "attacker constructs a chain reachable via a public-facing lookup path, walked with unbounded native recursion."

### Impact Explanation
An unbounded, attacker-controllable recursion depth in a function reachable by any RPC caller can exhaust the RPC/view-node's stack and crash the process (`SIGSEGV`/abort), producing a transaction-triggered halt of the RPC service for that node. Because `Chain`/`ChainStore` methods are shared infrastructure used by both RPC and full nodes' view-client actors, this is a concrete availability impact reachable from a single, unprivileged, self-funded transaction and a follow-up RPC query — no validator or peer collusion required.

### Likelihood Explanation
Constructing a very deep receipt chain purely via normal contract calls (repeated self cross-contract calls with `promise_batch_then`, resupplying gas on each new transaction/receipt) is straightforward and requires only paying for gas per hop; no special privileges, validator collusion, or protocol bugs are needed. The subsequent RPC status query that triggers the recursive walk is a completely standard, publicly exposed operation.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative, explicit-stack (e.g. `VecDeque`/worklist) traversal, and/or add a hard depth/size cap analogous to the `MAX_DEPTH = 1000` guard already used in `get_receipt_to_tx`, returning a bounded/partial result or an explicit error once the cap is exceeded instead of recursing indefinitely.

### Proof of Concept
1. Deploy a contract using a pattern like `max_self_recursion_delay`/`recurse` from `near-test-contracts` that repeatedly schedules a new self-directed `FunctionCall` promise on each receipt execution.
2. Rather than looping until gas in a single call runs out, have the contract issue a fresh promise callback in every receipt, chaining across many blocks (each new receipt gets its own gas allotment), building a receipt chain thousands of hops deep from one originating `SignedTransaction`.
3. After the chain completes, call the standard transaction-status RPC (`tx` / `EXPERIMENTAL_tx_status`) with the original transaction hash.
4. `ViewClientActor` → `Chain::get_final_transaction_result` → `get_recursive_transaction_results` recurses once per hop with no depth limit, exhausting the native stack of the RPC/view node.

Note: I could not fully trace the exact call site inside `view_client_actor.rs` that invokes `get_final_transaction_result` due to running out of tool iterations; the six matches found there for `tx_status`/`TxStatus` strongly indicate it is the backing implementation for the standard transaction-status RPC handler, but this final wiring should be double-checked in a full session before treating the PoC as validated end-to-end.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);

    let gas_fixed = 0;
    let gas_weight = 1;

        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}
