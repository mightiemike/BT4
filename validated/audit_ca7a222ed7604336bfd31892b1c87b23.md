### Title
Repeated fractional `unDelegateResource` calls cause additive rounding-error drift in bandwidth/energy usage accounting - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.execute` (and its TVM-native twin `UnDelegateResourceProcessor.execute`) compute the amount of consumption ("usage") to transfer from a resource receiver back to the delegating owner as a *change-based* ratio (`unDelegateBalance / totalFrozenBalance`) multiplied by the receiver's current usage, using truncating `double`→`long` arithmetic. Because this is recomputed from the *delta* being undelegated rather than derived directly from the post-operation totals, each call introduces an independent floor-rounding error. An account that splits a large un-delegation into many small `UnDelegateResourceContract` transactions (or repeated native-contract calls) accumulates these truncation errors, causing systematic usage-accounting drift between the owner and receiver — the same bug class described in the referenced report (additive rounding error from using deltas instead of recomputing from total notional/supply values).

### Finding Description
In `UnDelegateResourceActuator.execute`: [1](#0-0) 

and identically in the TVM native-contract path: [2](#0-1) 

`transferUsage` is derived as:
```
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
```
This is the exact analog of the reported anti-pattern: instead of recomputing the receiver's/owner's usage directly from post-state totals (e.g., `newTotalUsage * newFrozenBalance / oldFrozenBalance` computed once from final quantities), the code computes a proportional *change* using the amount being undelegated (`unDelegateBalance`, a delta) divided by the *current* total frozen balance, and multiplies against the current usage snapshot, truncating to `long` via `(long)` cast of a `double`. This mirrors `calculateDefaultEditPositionUnit`'s flaw of using `_componentPositionUnit... + notionalTransferred / setTokenSupply` deltas instead of `_postTotalNotional / _setTokenSupply`.

Every partial `unDelegateResource` operation re-executes this delta-based, double-precision, floor-truncating computation against the *current* (already-drifted) state (`receiverCapsule.getNetUsage()`, `getAllFrozenBalanceForBandwidth()`), so truncation errors from prior calls are baked into subsequent calculations rather than being corrected by recomputing from stable totals. This is functionally identical to the additive-rounding class described in the report: many small changes accumulate rounding loss instead of one exact computation from final totals.

Notably, the codebase already recognizes and hardened analogous rounding issues elsewhere with a `hardenCalculation()`/`allowHardenResourceCalculation` BigInteger path (see `ResourceProcessor.increase`, `increaseV2`, `calculateGlobalLimitV2`), but this hardening was **not** applied to the `transferUsage` computation in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor`: [3](#0-2) 

### Impact Explanation
The `transferUsage` value governs how consumption history (`NetUsage`/`EnergyUsage`) is shifted between the delegation receiver and the resource owner on `unDelegateResource` (reachable from any anonymous broadcast `UnDelegateResourceContract` transaction, or from a TVM contract calling the native `unDelegateResource` precompile). Because the transfer amount is systematically floor-truncated on the receiver's side and only that truncated amount is credited back onto the owner via `ResourceProcessor.unDelegateIncrease`, repeated partial un-delegations:
- leave the receiver's tracked usage higher than the mathematically correct value (residual usage never fully removed), and
- credit the owner with less usage than it should receive.

Over many repeated small `unDelegateResource` calls (which is fully within a single account's control against its own delegation and requires no privileged access), this produces an accounting drift in the bandwidth/energy usage ledger — a resource-accounting corruption that can be exploited to skew effective free-bandwidth/energy limits between two colluding or self-controlled accounts (owner and receiver), falling under the resource/reward accounting impact category.

### Likelihood Explanation
The path is reachable by any account: the actuator is a standard, unprivileged contract type (`UnDelegateResourceContract`) executed via ordinary broadcast transactions once `supportDR()`/`supportUnfreezeDelay()` are enabled (already active on mainnet), and via the equivalent TVM native contract call. No special permissions, keys, or trusted roles are required — only splitting an existing delegation un-delegation into many small `unDelegateBalance` amounts, which is trivially automatable.

### Recommendation
Recompute `transferUsage` from stable, exact quantities rather than an accumulating delta ratio, and use exact (BigInteger) arithmetic consistent with the existing `hardenCalculation()` path used elsewhere in `ResourceProcessor`, e.g.:
```
transferUsage = BigInteger.valueOf(receiverCapsule.getNetUsage())
    .multiply(BigInteger.valueOf(unDelegateBalance))
    .divide(BigInteger.valueOf(receiverCapsule.getAllFrozenBalanceForBandwidth()))
    .longValueExact();
```
and ensure this computation is gated behind the same hardening flag (`allowHardenResourceCalculation`) already used for the other resource-accounting formulas in `ResourceProcessor`, so usage transferred is derived deterministically from exact totals rather than compounding double-precision truncation across repeated partial operations.

### Proof of Concept
1. Delegate a large bandwidth/energy balance from account A (owner) to account B (receiver), causing B to accrue `NetUsage`/`EnergyUsage`.
2. From A, repeatedly broadcast `UnDelegateResourceContract` transactions with small `unDelegateBalance` values (instead of one large un-delegation).
3. After each call, `transferUsage` in `UnDelegateResourceActuator.execute` is computed via the truncating double formula at [4](#0-3) , floor-rounding down each time.
4. Compare final `B.getNetUsage()`/`A` usage after N small un-delegations vs. a single equivalent full un-delegation call — the sum of the small-step results diverges from the single-step result, demonstrating the additive rounding drift.
