Based on my investigation, I found a genuine, self-documented gap in the Aptos codebase, though I could not fully trace whether it's exploitable outside of tooling contexts before running out of iterations to verify further.

### Title
`TransactionOutput::ensure_match_transaction_info()` skips checkpoint-hash validation, allowing an authenticated output to be accepted despite a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the invariant check that binds a locally-computed `TransactionOutput` (write set, events, gas, status) to an authenticated `TransactionInfo` fetched from a peer/archive during replay and chunk-apply flows. The function explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash` against the supplied `TransactionInfo`, but the function itself carries a TODO acknowledging it does not validate the checkpoint-related fields: [1](#0-0) 
This function is invoked from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs`, all of which use it to confirm that recomputed execution output matches an authenticated `TransactionInfo`. Because the `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields carried inside `TransactionInfo` (which itself is committed into the transaction accumulator and thus covered by consensus signatures) are never compared against the locally-computed values in this check, a divergence in the Sparse-Merkle-Tree/JMT state root or the new native-position state root would not be caught by this specific comparator.

### Impact Explanation
If the state (or position-state) root diverges between the authenticated ledger and local re-execution — e.g., due to a bug in how state updates are applied at a checkpoint boundary — this comparator would still report success. The in-code comment for this exact function states the consequence directly: replay-verify tooling (`db-tool`'s `replay_on_archive`) "can report a successful replay even when the authenticated position state root diverges from local execution," and calls for validation to be added "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." [2](#0-1) 

### Likelihood Explanation
I was not able to fully confirm within the remaining investigation budget whether this same comparator, when used inside `execution/executor/src/chunk_executor/mod.rs` for state-sync chunk application, is the sole guard against a corrupted checkpoint hash, or whether an independent, stronger check (e.g. one comparing `state_checkpoint_hashes`/`position_state_checkpoint_hashes` computed by `StateCheckpointOutput` [3](#0-2)  against the accumulator-proof-backed `TransactionInfo`) is enforced elsewhere in that path (e.g. via `DoStateCheckpoint::get_state_checkpoint_hashes` which does compare known vs. computed checkpoint hashes when `known_state_checkpoints` is supplied [4](#0-3) ). Because the `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/native-position-root feature also appears currently gated (`hot_state_checkpoint_hashes` is `None` on mainnet per its own comment) [5](#0-4) , the practical blast radius today may be limited to the debugging/replay-verify tool paths rather than consensus-critical state-sync/commit, but this could not be conclusively ruled out for the chunk-executor path within available tool calls.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/enabled) against the corresponding fields of the authenticated `TransactionInfo`, exactly as already done for `state_change_hash` and `event_root_hash`, before enabling any feature (such as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on these roots for integrity.

### Proof of Concept
Not independently reproduced — this is based on the self-documented TODO in `types/src/transaction/mod.rs:2196-2203` and static call-site analysis; I could not verify within the remaining tool budget whether an independent checkpoint-hash check elsewhere in the chunk-executor commit path fully neutralizes this gap for consensus-critical (non-tooling) code paths. Confidence in this being a live, exploitable mainnet-impacting bug rather than an already-mitigated/tooling-only gap is **low-to-moderate**; further tracing of `execution/executor/src/chunk_executor/mod.rs`'s full call graph and the `apply_chunk`/`verify_execution` flow would be needed to confirm exploitability, ideally in a full Devin session with unrestricted tool access.
