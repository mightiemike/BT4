### Title
GraphQL MaxDepth(10) protection only bounds nesting depth, not alias/field breadth, and unauthenticated requests still reach the resolver - ([File: core/web/router.go])

### Summary
The `POST /query` endpoint is wired with `graphql.MaxDepth(10)` in `graphqlHandler` [1](#0-0) , but `graphql-go`'s `MaxDepth` option only limits how deeply a query can nest fields — it does not limit the number of aliased/root-level selections in a single request. Additionally, the `AuthenticateGQL` middleware placed in front of the handler does not reject unauthenticated requests; it silently proceeds without a session if none is present, deferring all authorization decisions to individual resolvers [2](#0-1) .

### Finding Description
`NewRouter` mounts `POST /query` behind `auth.AuthenticateGQL(...)`, `loader.Middleware(app)`, and `graphqlHandler(app)` [3](#0-2) . `AuthenticateGQL` only populates the request context with a `GQLSession` if a valid session cookie is found; if not, it simply `return`s and lets the request continue unauthenticated, per the comment "It is the responsibility of each resolver to validate whether it requires an authenticated user" [4](#0-3) . This means the GraphQL surface is reachable by any external caller without a valid session, subject only to the generic per-route rate limiter (`rl.AuthenticatedPeriod()/Authenticated()`) applied to the whole `api` group and the global body-size limiter `limits.RequestSizeLimiter(config.WebServer().HTTPMaxSize())` [5](#0-4)  — neither of which bounds per-request GraphQL query cost.

`graphqlHandler` only applies `graphql.MaxDepth(10)` when `!InfiniteDepthQueries()`, and it is the sole complexity-limiting schema option configured [6](#0-5) . There is no `graphql.MaxParallelism`, complexity-scoring, cost-limit, or alias-count limit configured anywhere in this handler. Since `MaxDepth` measures nesting depth of the AST, not the number of sibling/aliased selections, a single request containing hundreds of aliased copies of the same (shallow, depth ≤ 10) expensive query field will pass the depth check unmodified while causing the resolver to be invoked once per alias, and (depending on the target resolver) can multiply DB calls issued through `loader.Middleware(app)`'s dataloaders proportionally to the alias count.

### Impact Explanation
An external party (even one without valid credentials, since `AuthenticateGQL` does not block unauthenticated traffic) can submit a single crafted POST body with many aliased copies of an expensive query field to multiply resolver/DB work per HTTP request, bypassing the per-request rate limiter (which counts requests, not query cost) and the `MaxDepth(10)` guard (which counts nesting, not breadth). This can degrade node availability (CPU/goroutine/DB connection exhaustion) — a resource-exhaustion/DoS impact on the node's web/API surface.

### Likelihood Explanation
Feasibility depends on the request body size limit (`HTTPMaxSize`) allowing a sufficiently large payload with many aliases, and on whether the specific target resolver performs meaningful work (DB query) before any per-field authorization check runs. I was not able to fully verify, within the available tool budget, whether every `Query`/`Mutation` resolver checks authorization before touching the database (only `core/web/resolver/auth.go` and `query.go` were located but not fully inspected), so the exact magnitude of DB fan-out per alias for an *unauthenticated* caller is uncertain. What is confirmed structurally is that (1) `AuthenticateGQL` does not abort unauthenticated requests, and (2) `MaxDepth(10)` provides no protection against alias/breadth amplification. This makes the DoS vector plausible and repeatable, though its severity is bounded by `HTTPMaxSize` and the generic rate limiter, and possibly further mitigated if resolvers check auth cheaply before any DB access (unverified).

### Recommendation
Add width/complexity limiting to the GraphQL schema (e.g., `graphql.MaxParallelism`, a query-cost/complexity analyzer, or an explicit cap on the number of aliases/root selections per request) in `graphqlHandler` in `core/web/router.go`, independent of `InfiniteDepthQueries()`. Additionally, consider having `AuthenticateGQL` (or a wrapping check) apply a stricter, cost-aware rate limit for unauthenticated GraphQL requests, since currently unauthenticated callers are allowed to reach the resolver layer with the same rate limiting as authenticated ones.

### Proof of Concept
1. Unit/integration test in `core/web/router_test.go`-style harness: build an `httptest` GraphQL request to `POST /query` with no session cookie, containing a query with N (e.g., 200) aliases of a moderately expensive query field (depth ≤ 10, e.g., a paginated list field), and assert:
   - The request is *not* rejected for lack of auth (confirming `AuthenticateGQL` passthrough behavior in `core/web/auth/gql.go`).
   - The number of DB calls/dataloader invocations (instrumented via a counting mock `Authenticator`/ORM) scales linearly with N rather than being capped.
   - Wall-clock execution time for N=200 significantly exceeds execution time for N=1, demonstrating unbounded per-request cost despite `MaxDepth(10)`.
2. Fuzz test: vary N and alias nesting under `MaxDepth(10)` and assert that DB call count / execution time remains sublinear or bounded by a fixed ceiling — expected to fail against current code, confirming the gap.

```go
func graphqlHandler(app chainlink.Application) gin.HandlerFunc {
	rootSchema := schema.MustGetRootSchema()

	// Disable introspection and set a max query depth in production.
	var schemaOpts []graphql.SchemaOpt

	if !app.GetConfig().Insecure().InfiniteDepthQueries() {
		schemaOpts = append(schemaOpts,
			graphql.MaxDepth(10),
		)
	}

	schema := graphql.MustParseSchema(rootSchema,
		&resolver.Resolver{
			App: app,
		},
		schemaOpts...,
	)
```

```go
// AuthenticateGQL middleware checks the session cookie for a user and sets it
// on the request context if it exists. It is the responsibility of each resolver
// to validate whether it requires an authenticated user.
//
// We currently only support GQL authentication by session cookie.
func AuthenticateGQL(authenticator Authenticator, lggr logger.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		ctx := c.Request.Context()
		session := sessions.Default(c)
		sessionID, ok := session.Get(SessionIDKey).(string)
		if !ok {
			return
		}

		user, err := authenticator.AuthorizedUserWithSession(ctx, sessionID)
		if err != nil {
			if errors.Is(err, clsessions.ErrUserSessionExpired) {
				lggr.Warnw("Failed to authenticate session", "err", err)
			} else {
				lggr.Errorw("Failed call to AuthorizedUserWithSession, unable to get user", "err", err)
			}
			return
		}

		ctx = WithGQLAuthenticatedSession(c.Request.Context(), user, sessionID)

		c.Request = c.Request.WithContext(ctx)
	}
```
