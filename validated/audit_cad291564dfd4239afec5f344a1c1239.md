Looking at the `try_into_near_action` conversion path in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:162-163`, the `tx.value` from the raw Ethereum transaction is passed as `additional_value` into `Action::try_into_near_action`. [1](#0-0) 

For `Action::FunctionCall` and `Action::Transfer`, `additional_value` is added to `yocto_near` and forwarded as the actual NEAR `deposit` on the resulting action, so the ETH `value` is fully accounted for. However, for `Action::AddKey` and `Action::DeleteKey`, the `try_into_near_action` match arms construct the resulting `near_action::Action::AddKey` / `Action::DeleteKey` without using `additional_value` at all — it's silently discarded. [2](#0-1) 

This mirrors the Footium bug class exactly: a user (via a relayer-submitted Ethereum transaction) can attach a non-zero `msg.value`/`tx.value` to an `AddKey` or `DeleteKey` operation, and this value is silently dropped rather than either being rejected or refunded to the caller. Given `CallerDeposit` tracking is explicitly designed to refund a predecessor's deposit only when the *promise/cross-contract call* fails (`rlp_execute_callback`), and this deposit-loss occurs entirely within the synchronous, non-failing action construction step (before any promise is even created for `AddKey`/`DeleteKey`, since these are `SelfNearNativeAction`s dispatched locally), the value is never captured as a `CallerDeposit` and is never refunded on any path, success or failure.

Because I could not trace how the actual `NearToken::from_yoctonear`-converted deposit is attached to the `AddKey`/`DeleteKey` NEAR action receipt in the surrounding action-dispatch code (i.e., whether the wallet contract's outer `Promise` batch action wraps the discarded value elsewhere, such as via a top-level transfer using `context.attached_deposit`), I can't fully confirm whether the funds are burnt, sent to a wrong account, or actually reflected somewhere else in the flow (e.g. `rlp_execute` outer function directly consuming `env::attached_deposit()`). This uncertainty stems from not having visibility into `lib.rs`'s `rlp_execute`/`execute_from` top-level dispatch and how it composes the final `Promise` from `near_action::Action`, which is outside what I was able to inspect within the tool-call budget.

### Title
Ethereum-transaction `value` silently dropped for AddKey/DeleteKey actions in NEAR Wallet Contract - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs)

### Summary
The Wallet Contract's `Action::try_into_near_action` conversion discards the `additional_value` parameter (derived from the Ethereum transaction's `value` field) when constructing `AddKey` and `DeleteKey` NEAR actions, unlike `FunctionCall`/`Transfer` where it is correctly folded into the `deposit`.

### Finding Description
`parse_rlp_tx_to_action` in `internal.rs:162-163` computes `tx.value.raw().low_u128().saturating_mul(MAX_YOCTO_NEAR.into())` and passes it as `additional_value` to `action.try_into_near_action(...)`. In `types.rs`, the `FunctionCall` and `Transfer` arms add `additional_value` into the constructed action's `deposit` field (`types.rs:243-260`), but the `AddKey` and `DeleteKey` arms (`types.rs:262-296`) never reference `additional_value` — it is computed but has no effect on the resulting action.

### Impact Explanation
An externally-submitted, relayer-forwarded Ethereum transaction encoding an `AddKey`/`DeleteKey` call selector with a non-zero `value` field results in that value being unaccounted for in the produced NEAR action. Since `CallerDeposit`-based refunding is only wired up for the cross-contract-call failure path in `rlp_execute_callback`, and `AddKey`/`DeleteKey` are dispatched as `SelfNearNativeAction`s that bypass that promise/refund machinery, any NEAR value a user intends to attach via `tx.value` for these action kinds is lost rather than applied or refunded — a concrete loss of user funds analogous to the Footium overpayment bug.

### Likelihood Explanation
Reachable by any unprivileged relayer/RPC caller submitting an RLP-encoded Ethereum transaction with the `AddKey`/`DeleteKey` selector and a non-zero `value` field to the Wallet Contract via `rlp_execute`/`rlp_execute_from`. No special privileges are required — only the ability to submit or relay a transaction.

### Recommendation
Either (a) reject transactions with non-zero `value` targeting `AddKey`/`DeleteKey` selectors (mirroring the `ExcessYoctoNear` check already used for `yocto_near` overflow), or (b) route `additional_value` for these action kinds into an explicit transfer/refund back to the caller so it is never silently dropped.

### Proof of Concept
Construct and RLP-encode an Ethereum transaction whose `data` matches `ADD_KEY_SELECTOR` (or `DELETE_KEY_SELECTOR`) and whose `value` field is non-zero (e.g., 1 ETH-equivalent), then submit it via `rlp_execute`/`rlp_execute_from` to the Wallet Contract. Observe that the resulting NEAR `AddKey`/`DeleteKey` action carries no deposit reflecting `tx.value`, and the caller's account balance is debited by `tx.value` (as part of the overall attached deposit accounting) without any compensating transfer or refund, in contrast to `test_caller_refunds` (`sanity.rs:170-229`) which only covers the promise-failure refund path, not this silently-dropped-value path.
