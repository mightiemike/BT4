### Title
`ensure_match_transaction_info` skips validating state-checkpoint / hot-state / position-state root hashes, letting replay-verify accept a divergent committed state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-vs-locally-computed comparison used by replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`) to confirm that re-executing a backed-up transaction reproduces the exact same committed result as what is recorded (and cryptographically chained) in the archived `TransactionInfo`. The function only checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that exist on `TransactionInfo`/`TransactionInfoV1` and are part of the value that gets hashed into the transaction accumulator and ultimately the `LedgerInfo` root that light clients and other verifiers trust.

### Finding Description
`TransactionInfo` carries multiple root-hash fields beyond the write-set/event hashes: `state_checkpoint_hash` (Merkle root of global state after a checkpoint), and in `TransactionInfoV1`, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`. [1](#0-0) 

`ensure_match_transaction_info` is the function meant to independently verify that a locally re-executed `TransactionOutput` matches the authenticated on-chain `TransactionInfo` supplied from a backup/archive. It only asserts on status, gas, write-set hash, and event root hash, and its own code comment explicitly documents the gap: [2](#0-1) 

This function is invoked directly by `storage/db-tool`'s `replay-on-archive` verifier after re-executing transactions from a backup, to decide whether replay succeeded: [3](#0-2) 

Because the comparison omits the checkpoint-hash fields, any divergence between the locally-computed state/hot-state/position-state root and the authenticated root stored in the backup's `TransactionInfo` is silently ignored by this verification path. The write-set hash check alone does not substitute for the state-root check: `state_change_hash` only proves the write set bytes of that specific transaction match, it says nothing about whether the resulting global JMT/state-checkpoint root (which depends on how that write set is applied cumulatively across the whole tree, and on other authenticated roots such as hot-state and the new "trading native" position-state tree) is being computed correctly.

### Impact Explanation
Replay-verify (`replay-on-archive`) is one of the primary integrity tools used to detect state divergence between different execution/storage implementations (e.g., after a database/executor refactor, hot-state changes, or a new state-tree feature) and between a node's local computation and the network's committed history. Because `ensure_match_transaction_info` never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a bug in state-checkpoint computation, hot-state root computation, or the newly introduced position-state ("trading native") root computation would go completely undetected by this tool even when fed authenticated backup data — replay would be reported as fully successful while the locally materialized ledger state is actually wrong. This is exactly the kind of "committed state differs from correct VM result" / "wrong ... state proof accepted as valid" class of issue the review is meant to flag, since it removes an authenticated cross-check specifically over accumulator-bound state roots.

### Likelihood Explanation
This isn't a remotely triggerable exploit against a live validator — it requires a pre-existing state-root computation bug (e.g., in `DoStateCheckpoint`, hot-state materialization, or the new `compute_trading_native_state_roots` position-state code) to actually go unnoticed. But that is precisely the failure mode replay-verify exists to catch, and the code's own TODO comment confirms this was recognized but left unresolved ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"). Given `state_checkpoint_hash`/`hot_state_checkpoint_hash` are already active in mainnet `TransactionInfoV1`, the gap is live today, not merely a future concern tied to the unreleased position-state feature.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash` (when present in either output) against the locally computed state-checkpoint root, and similarly validate `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` when those features are active, failing the replay/verification if any authenticated root hash does not match the locally recomputed one, so `replay-on-archive` and any other future consumers of this comparator cannot report a false "success" while the state root has silently diverged.

### Proof of Concept
Conceptual PoC (cannot be executed here, but structurally sound from code inspection):
1. Take a backed-up chunk containing a `TransactionInfoV1` with a correct `state_change_hash`/`event_root_hash` but an intentionally/accidentally wrong `state_checkpoint_hash` (simulating a real state-tree computation bug in `DoStateCheckpoint`).
2. Run `db-tool replay-on-archive` over that range. [4](#0-3) 
3. `ensure_match_transaction_info` only compares status/gas/write-set-hash/event-root-hash, so it returns `Ok(())` and the tool reports the range as verified, despite `state_checkpoint_hash` (and by extension the accumulator root computed from `TransactionInfo::hash()`) diverging from what local execution would produce.

Note: I was not able to fully trace how deeply `compute_trading_native_state_roots`/position-state feature is wired into mainnet consensus (its gating flag) within the indexed code, so I cannot state with certainty whether the position-state portion of this gap is currently reachable on mainnet; the `state_checkpoint_hash`/`hot_state_checkpoint_hash` portion, however, is unconditionally skipped regardless of that feature's activation status.
