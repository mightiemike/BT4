### Title
Declare transactions bypass the L2 gas amount upper-bound check, allowing unbounded `__validate__`/execution gas limits - (File: `crates/apollo_gateway/src/stateless_transaction_validator.rs`)

### Summary
The gateway's `validate_resource_bounds` enforces `max_l2_gas_amount` (config-defined upper bound) on Invoke and DeployAccount transactions, but explicitly skips this check for Declare transactions, leaving the `l2_gas.max_amount` field unbounded above for Declare txs — directly analogous to the reported `_maxCollateralRatioMantissa` issue where a parameter had a lower bound but no upper bound.

### Finding Description
`StatelessTransactionValidator::validate_resource_bounds` enforces a lower bound on gas price (`min_gas_price`) for all transaction types and an upper bound on `l2_gas.max_amount` via `self.config.max_l2_gas_amount` — but only for non-Declare transactions: [1](#0-0) 

```
if resource_bounds.l2_gas.max_price_per_unit.0 < self.config.min_gas_price { ... }

// TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.
if let RpcTransaction::Declare(_) = tx {
} else if resource_bounds.l2_gas.max_amount.0 > self.config.max_l2_gas_amount {
    return Err(StatelessTransactionValidatorError::MaxGasAmountTooHigh { ... });
}
```

The code comment itself (`TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.`) confirms this is a known gap: the upper-bound gate that protects Invoke/DeployAccount transactions from carrying an arbitrarily large `l2_gas.max_amount` is not applied to Declare transactions. As a result, an unprivileged transaction sender (the class declarer) can submit a Declare transaction with `l2_gas.max_amount` set to any value up to `GasAmount::MAX` (u64::MAX), whereas for the same field on Invoke/DeployAccount the gateway strictly rejects anything above the configured cap (`max_l2_gas_amount`, default ~1.21e9 per `crates/apollo_gateway_config/src/config.rs:193`).

`l2_gas.max_amount` is the gas limit enforced by the OS/blockifier on the transaction's execution (this is stated explicitly in the client-facing documentation of the same limit for the prover: "l2_gas.max_amount: determines the gas limit the OS enforces on the transaction" — [2](#0-1) ). This bound is meant to cap the amount of computation (Cairo steps/builtins) a single transaction's `__validate__`/execution can consume before hitting an out-of-gas condition, which is precisely why the config exposes `max_l2_gas_amount` and why it is enforced for Invoke and DeployAccount transactions.

For Declare transactions, the account's `__validate__` entrypoint and other declare-specific processing still execute up to the gas limit supplied by the sender's resource bounds; blockifier's fee-bound checks only ensure resource bounds are *at least* the minimal required gas (`check_fee_bounds` / `estimate_minimal_gas_vector` in `crates/blockifier/src/transaction/account_transaction.rs:374-378`), not that they are capped at a sane maximum. With the gateway's upper-bound gate skipped for Declare, nothing in the stateless-validation path prevents a Declare transaction from carrying an L2 gas budget orders of magnitude larger than what any other admitted transaction type is allowed.

### Impact Explanation
Because the gateway is the mempool-admission gatekeeper (reachable directly by any unprivileged transaction sender via RPC submission), this gap lets a declarer submit transactions whose declared gas ceiling is unconstrained relative to every other transaction type in the system. This breaks the uniform resource-governance invariant the config was designed to enforce (the same invariant that Invoke/DeployAccount transactions are held to), and permits a sequencer/proposer to be forced into processing (executing/validating) a Declare transaction whose gas budget is far larger than the sanctioned maximum, undermining the predictability of per-transaction resource consumption that block-building and bouncer capacity accounting rely on. This is a resource-governance/config-invariant break reachable from a single submitted transaction, matching the class of bug in the reported issue (a bound present on similar/sibling parameters but missing on this one).

### Likelihood Explanation
High: any external, unprivileged actor can submit a Declare transaction (declare a class) with an arbitrarily large `l2_gas.max_amount` (up to `GasAmount::MAX`) through the standard gateway submission path — no special privileges, and the only limiting factor is the account's own STRK balance needing to cover `max_possible_fee`, which does not depend on this field's magnitude relative to the config limit that gates other transaction types.

### Recommendation
Remove the Declare-type exemption in `validate_resource_bounds` and apply the same `max_l2_gas_amount` upper-bound check to Declare transactions as is applied to Invoke and DeployAccount transactions (resolving the existing `TODO(Arni)` in `crates/apollo_gateway/src/stateless_transaction_validator.rs:78-85`), optionally with a distinct/appropriately-sized cap if Declare's legitimate gas needs differ from Invoke's.

### Proof of Concept
Not independently executed in this environment (index/tool access is read-only). Conceptually:
1. Craft an `RpcDeclareTransaction::V3` with `resource_bounds.l2_gas.max_amount` set to a value far exceeding `StatelessTransactionValidatorConfig::max_l2_gas_amount` (default `1_210_000_000`), e.g. `GasAmount(u64::MAX)`, while keeping `max_price_per_unit` at/above `min_gas_price` and other bounds valid so `max_possible_fee` isn't zero.
2. Submit via the gateway's RPC `validate` path (`StatelessTransactionValidator::validate` → `validate_resource_bounds`), per `crates/apollo_gateway/src/stateless_transaction_validator.rs:31-88`.
3. Observe that the transaction passes stateless validation (no `MaxGasAmountTooHigh` error), unlike an equivalent Invoke transaction with the same oversized `l2_gas.max_amount`, which is rejected as demonstrated in the test suite (`crates/apollo_gateway/src/stateless_transaction_validator_test.rs:160-241`, e.g. the `l2_gas_amount_out_of_limit`/`valid_l2_gas_amount_on_declare` cases confirming Declare is deliberately excluded from this check).
