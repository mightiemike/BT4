Based on the investigation, the sequencer already has a specific defense against unbounded recursion in transaction/contract call execution — the `RecursionDepthGuard` in `crates/blockifier/src/execution/entry_point.rs` increments and checks depth *before* each recursive `CallEntryPoint::execute` and correctly decrements it via `Drop`, so depth is never wrongly reset (unlike the libxml2 bug). That path is not a valid analog.

However, the compiled-class hashing code that a **contract declarer** reaches through a `Declare` transaction contains genuine uncontrolled, attacker-influenced recursion with no depth cap.

### Title
Uncontrolled recursion in compiled-class bytecode hashing enables stack-overflow DoS via a crafted Declare transaction - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node`, used to compute the CASM/compiled-class hash for every declared Cairo 1 class, recurses once per nested bytecode segment with no maximum-depth check. The segment tree shape is derived from the contract's own control-flow structure (branches/functions), which is attacker-controlled at declare time, allowing a crafted contract to force very deep, unbounded recursion in the sequencer's own process.

### Finding Description
`bytecode_hash_node` walks the `bytecode_segment_lengths` (`NestedIntList`) tree that accompanies a compiled class and calls itself once per non-leaf segment: [1](#0-0) 
This function is invoked from `bytecode_hash`, which is called from `hash_inner`/`HashableCompiledClass::hash`, the function used to compute the executable class hash right after Sierra→CASM compilation: [2](#0-1) 

This hashing call is made in-process by the Sierra compiler service, *after* the actual compilation subprocess (which is the only step protected by CPU/memory `ResourceLimits`): [3](#0-2) [4](#0-3) 

The subprocess isolation (`resource_limits::ResourceLimits`) bounds CPU time and memory of the compiler binary invocation, but it does not bound the recursion depth of `hash_inner`/`bytecode_hash_node`, which executes back in the calling (sierra-compiler / gateway-adjacent) process's own stack after `compile_with_args` returns. The only limit on bytecode itself is `max_bytecode_size` (81920 felts): [5](#0-4) 
but that bounds total bytecode length, not the *nesting depth* of the segment tree. A contract with sufficiently deep nested control flow (many nested branches/functions) can, after a legitimate compilation succeeds, produce a `bytecode_segment_lengths` structure whose tree depth approaches the bytecode size itself (worst case, a long chain of single-element segments), driving `bytecode_hash_node` into deep, unguarded recursion — directly analogous to the reported libxml2 issue where recursive evaluation functions lacked a preserved/enforced depth bound.

### Impact Explanation
If the recursion depth is large enough to exhaust the process's real stack, the compiling service process (`apollo_compile_to_casm` / Sierra compiler component, part of the gateway declare-transaction pipeline) crashes. Because this hashing step runs for every Declare transaction that reaches this stage, a single malicious declare submission can repeatedly crash or degrade the class-compilation service used by all sequencer nodes, hindering the network's ability to admit and confirm new (declare) transactions — a network-availability impact, not merely a resource-cost issue, since it happens post-compilation-limits and directly threatens process stability rather than gas/CPU accounting.

### Likelihood Explanation
Likelihood is Medium: constructing a Cairo1 contract whose CASM bytecode segment structure nests deeply enough to overflow a real stack is a non-trivial but achievable engineering task (deeply nested `if`/`match`/function-call chains within the `max_bytecode_size` bound), and only requires submitting one Declare transaction — no privileged access, no protocol changes.

### Recommendation
Bound the recursion depth of `bytecode_hash_node` (and its Cairo/OS counterparts `bytecode_hash_internal_node` in `blake_compiled_class_hash.cairo` / `poseidon_compiled_class_hash.cairo`) explicitly, or convert the traversal to an iterative (explicit stack) algorithm so recursion depth is not tied to the attacker-controlled bytecode segment structure. Additionally, run the post-compilation hashing step under the same resource-isolation guarantees (e.g., a bounded worker thread with a fixed, monitored stack size, similar to the `stack_size` protection already used for Cairo Native execution in `crates/blockifier/src/blockifier/transaction_executor.rs`) so a stack overflow there cannot take down the parent service.

### Proof of Concept
1. Author a Cairo1 contract whose compiled bytecode, after Sierra→CASM compilation, yields a deeply and narrowly nested `bytecode_segment_lengths` (e.g., many levels of nested `if`/`match` blocks or deeply nested function calls), close to the `max_bytecode_size` (81920) felt limit, such that segment nesting depth is in the tens of thousands.
2. Submit this class via a `Declare` transaction to the gateway/Sierra compiler service.
3. Compilation succeeds within CPU/memory resource limits (`ResourceLimits`), but the subsequent in-process call to `HashableCompiledClass::hash` → `bytecode_hash` → `bytecode_hash_node` recurses to the crafted depth, exhausting the calling process's stack and crashing the compiling service (verifiable by observing process termination/signal instead of a computed hash).

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}
