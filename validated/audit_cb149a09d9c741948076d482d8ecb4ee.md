### Title
Missing frozen-duration bounds check in TVM native freeze path bypasses the limit enforced by the regular `FreezeBalanceActuator` - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
This mirrors the reported bug class: a "combined"/alternate execution path duplicates the effect of a validated operation but omits one of its validation checks. In java-tron, `FreezeBalanceActuator` (the regular transaction path for freezing TRX for resources) enforces a bound on `frozenDuration`, but `FreezeBalanceProcessor` (the native-contract path invoked from within the TVM, i.e. reachable from a smart-contract call inside a broadcast transaction) performs the equivalent freeze operation without ever validating that bound.

### Finding Description
`FreezeBalanceActuator.validate()` explicitly bounds the freeze duration before allowing the freeze to proceed: [1](#0-0) 

`FreezeBalanceProcessor.validate()`, which is the validation routine for the TVM-native/precompiled freeze operation (used when a smart contract triggers a freeze via the VM), checks balance amount, frozen count, resource type, and delegation target — but never checks `param.getFrozenDuration()` against any minimum/maximum bound: [2](#0-1) 

`FreezeBalanceProcessor.execute()` then uses this unchecked `frozenDuration` directly to compute the resource `expireTime`: [3](#0-2) 

This is structurally the same class of bug as the reported issue: one code path (`FreezeBalanceActuator`, analogous to `borrow()`) enforces a duration limit, while a second code path performing the equivalent state transition (`FreezeBalanceProcessor`, analogous to `leverage()`) omits it.

### Impact Explanation
If `frozenDuration` reaching this native processor is attacker/contract-controlled, an attacker could set it to an extreme or degenerate value (e.g., very large, zero, or negative), causing `expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD` to overflow or produce an inconsistent expiry, corrupting resource accounting (`setFrozenForBandwidth`/`setFrozenForEnergy`, total network/energy weight adjustments) and potentially creating a permanent or inconsistent freeze state that diverges from the bounds intentionally enforced elsewhere in the protocol.

### Likelihood Explanation
I was not able to fully confirm, within the available context, whether the `frozenDuration` field of `FreezeBalanceParam` is actually attacker-controlled when invoked from Solidity/TVM (i.e., whether the VM opcode/native contract that populates `FreezeBalanceParam` exposes `frozenDuration` as a caller-supplied argument or sets it to a fixed constant). This is the key uncertain factor determining exploitability, and I could not complete verification of the call site in `actuator/src/main/java/org/tron/core/vm/program/Program.java` before this analysis had to conclude. Additionally, `FreezeBalanceActuator` itself refuses to operate once `dynamicStore.supportUnfreezeDelay()` (freeze v2) is enabled, so this legacy freeze-v1 native path may only be reachable on chains/forks that have not yet activated freeze v2.

### Recommendation
Add the same `minFrozenTime <= frozenDuration <= maxFrozenTime` validation in `FreezeBalanceProcessor.validate()` that exists in `FreezeBalanceActuator.validate()`, and confirm/lock down how `FreezeBalanceParam.frozenDuration` is populated from the TVM call site so it cannot carry an unbounded or attacker-supplied value.

### Proof of Concept
Not able to construct a concrete PoC without confirming the call site in `Program.java` that populates `FreezeBalanceParam.setFrozenDuration(...)` from TVM opcode arguments; this verification was not completed within the available investigation. A background Devin session with full read access to `actuator/src/main/java/org/tron/core/vm/program/Program.java` (and the associated `Repository`/native-contract dispatch code) could confirm whether the duration is caller-controlled, which would finalize the concrete exploit path.

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }

    // validate for delegating resource
    byte[] receiverAddress = param.getReceiverAddress();
    if (!FastByteComparisons.isEqual(ownerAddress, receiverAddress)) {
      param.setDelegating(true);

      // check if receiver account exists. if not, then create a new account
      AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
      if (receiverCapsule == null) {
        receiverCapsule = repo.createNormalAccount(receiverAddress);
      }

      // forbid delegating resource to contract account
      if (receiverCapsule.getType() == Protocol.AccountType.Contract) {
        throw new ContractValidateException(
            "Do not allow delegate resources to contract addresses");
      }
    }
  }
