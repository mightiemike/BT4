### Title
Stale destination-chain gas price locked at outbound commit can permanently strand bridged funds and freeze the reserved gas-fee reserve — (File: x/uexecutor/keeper/create_outbound.go, universalClient/chains/evm/tx_builder.go)

### Summary
This is the direct analog of the SkyWeaver `GoldCardsFactory` bug: a price is fixed at "commit" time but the corresponding value-moving action (burning weave / here, broadcasting the priced transaction and later refunding the unused gas reserve) happens after an unbounded delay, so a price move between commit and execution either breaks the transfer or leaves value permanently stuck.

### Finding Description
When an outbound withdraw is created, `GasPrice`/`GasFee`/`GasLimit` are captured once, at PC-commit time, from the `UniversalTxOutbound` event emitted by the `UniversalCore`/gateway contract, and stored immutably on the `OutboundTx` record: [1](#0-0) 

These exact stored values are re-emitted unchanged in the `OutboundCreatedEvent` used to drive TSS signing: [2](#0-1) 

The universalClient EVM `TxBuilder` then constructs and signs/broadcasts the actual destination-chain transaction using this stored `GasPrice` verbatim as the transaction's gas price, with no re-check against the current network gas price at the time of signing/broadcast: [3](#0-2) [4](#0-3) 

Broadcasting only happens after a full TSS signing ceremony completes for this outbound, which is not bounded in the code path itself (it is gated only by an optional per-chain `SigningDeadline` used for signature *validity*, not gas-price freshness): [5](#0-4) 

If the destination chain's real network gas price rises materially above the commit-time `GasPrice` before the TSS ceremony completes and the transaction is broadcast, the transaction is underpriced and will not be mined. There is no gas-price bump/replace-by-fee/resign mechanism in the traced code — the outbound simply stays in `PendingOutbounds` forever (the entry is only removed once validators reach quorum on an `OutboundObservation`, which never happens if the tx is never included): [6](#0-5) 

Meanwhile, the fixed `GasFee` (the gas-token/PRC20 amount reserved on the PC side to cover this exact outbound) is already deducted/held by `UniversalCore` at outbound-creation time (in the same commit transaction that produced the event), and is only released back via `applyGasRefund` after `FinalizeOutbound`/`handleSuccessfulOutbound`/`handleFailedOutbound` run — which require an `OutboundObservation` to exist: [7](#0-6) 

Since observation can never occur for a transaction that is never mined, `applyGasRefund` is never invoked and the reserved gas-fee amount is never returned to the user — this is the exact "weave tokens stuck in the contract forever" analog from the report, except here it's the outbound's reserved gas fee and, more importantly, the bridged principal amount itself that never reaches the destination-chain recipient.

Conversely, if the destination-chain gas price falls after commit, the transaction still pays the old, higher, commit-time price; `applyGasRefund` correctly refunds `gasFee - gasFeeUsed` for the *paid* amount, but only once the tx is actually observed — so the "excess reserved, stuck" case is bounded, while the "price rose, tx never confirms" case is not: it's an unrecoverable liveness/fund-freezing bug rather than merely an accounting rounding error.

### Impact Explanation
An ordinary unprivileged user's outbound withdrawal (bridging PRC20/native funds off Push Chain to an EVM destination chain) can become permanently stuck with no automated recovery path if destination-chain gas prices rise materially during the TSS signing window (which can be arbitrarily long under network congestion, TSS liveness issues, or high external-chain gas volatility — no code-level bound was found tying gas-price freshness to signing completion). This directly causes permanent loss/freezing of user funds (the withdrawal amount, held/burned/escrowed on the PC side pending finalization) and freezing of the reserved gas fee, matching the in-scope "permanent freezing ... of user or protocol-controlled funds" and "corruption of ... gas fee accounting, refund accounting" impact categories. It is reachable purely through ordinary user withdrawal submission with no privileged action required.

### Likelihood Explanation
Likelihood is moderate: it requires a real-world gas-price spike on the destination chain occurring within the window between outbound commit and TSS-signed broadcast. This is a realistic and externally-triggerable condition (attacker doesn't even need to act maliciously — normal market conditions on volatile L2/L1 gas markets suffice), and the code shows no re-pricing, retry-with-bumped-gas, or automatic recovery mechanism in the traced paths (`GetOutboundSigningRequest`, `BroadcastOutboundSigningRequest`, `attachOutboundsToUtx`, `FinalizeOutbound`). I could not locate (within index limits) any background job that monitors stuck `PendingOutbounds` entries and re-signs with fresh gas parameters; the only related maintenance code found (`purge-expired-outbounds` upgrade) only deletes stale *ballots* to allow re-voting, and does not address re-pricing an unmined transaction.

### Recommendation
Do not lock `GasPrice`/`GasFee` at outbound-commit time for use in the final broadcast. Instead:
1. Re-fetch current destination-chain gas price at the time the universalClient actually builds/signs the transaction (immediately before or during TSS signing), independently validating it does not exceed the reserved `GasFee` ceiling — reject/requeue rather than silently using stale data.
2. If the current price would exceed the reserved fee, trigger a top-up/re-quote flow (similar to `GetOutboundTxGasAndFees`) that adjusts the reserved amount and emits a corrected signing request, analogous to storing `goldPrice`/`goldRefund` at time-of-use rather than time-of-commit in the original report's recommendation.
3. Add a monitored, time-bounded escalation/retry path for outbounds that remain in `PendingOutbounds` past a reasonable threshold, including gas-price rebump and re-signing, so funds cannot become indefinitely stuck.

### Proof of Concept
Conceptual sequence (verified via code paths cited above; no test harness reproducing an actual stuck TSS ceremony was found in the index, so this is derived from tracing the production code rather than an executed exploit):
1. User submits a normal cross-chain withdrawal; `UniversalCore` computes `GasFee`/`GasPrice`/`GasLimit` based on the destination chain's gas price at that moment and reserves `GasFee` from the user's PRC20 balance.
2. `BuildOutboundsFromReceipt` stores these frozen values on the `OutboundTx` (`x/uexecutor/keeper/create_outbound.go:69-91`), and `attachOutboundsToUtx` emits an `OutboundCreatedEvent` carrying the same frozen `GasPrice` (`create_outbound.go:381-399`).
3. TSS signing ceremony begins but takes a non-trivial amount of time (network conditions, validator liveness). During this window, the destination chain's real gas price rises above the stored `GasPrice`.
4. `universalClient` builds and broadcasts the transaction using the stale `GasPrice` unmodified (`tx_builder.go:98-146`, `210-227`).
5. The transaction is rejected/never mined by the destination chain due to being underpriced; no OutboundObservation is ever produced, so `PendingOutbounds` entry persists indefinitely (`msg_vote_outbound.go:121-129`), the bridged funds never arrive at the recipient, and the reserved `GasFee` is never refunded because `applyGasRefund`/`FinalizeOutbound` require an observation that will never come (`outbound.go:71-96,163-172`).

// handleSuccessfulOutbound refunds unused gas fee when gasFee > gasFeeUsed.
func (k Keeper) handleSuccessfulOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	k.Logger().Info("outbound completed successfully",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"dest_chain", outbound.DestinationChain,
	)
	k.applyGasRefund(ctx, &outbound, obs)
	return k.UpdateOutbound(ctx, utxId, outbound)
}

// applyGasRefund computes the excess gas (gasFee - gasFeeUsed) and, if positive,
// calls UniversalCore refundUnusedGas. The result is recorded in outbound.PcRefundExecution.
// It is called for both successful and failed outbounds — gas is consumed on the
// external chain regardless of execution outcome.
func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}
