### Title
Replay verification silently ignores state/hot-state/position checkpoint hash mismatches - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used to prove that a re-executed (replayed) `TransactionOutput` matches the historically committed `TransactionInfo` for a given version. It checks status, gas used, write-set hash, and event root hash, but the function's own inline comment documents that it deliberately skips comparing the state-checkpoint hash, hot-state checkpoint hash, and `position_state_checkpoint_hash` fields of `TransactionInfo`.

### Finding Description [1](#0-0) 

The relevant code:
- `ensure_match_transaction_info` verifies `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`.
- It never touches `txn_info.state_checkpoint_hash()`, any hot-state checkpoint hash, or `position_state_checkpoint_hash()`.
- The trailing comment explicitly states: *"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."*

The state checkpoint hash is the root of the Jellyfish Merkle Tree / state summary that is authenticated by the transaction accumulator and, transitively, by the `LedgerInfo` signed by validators. This is precisely the proof-binding invariant called out in the "State-Integrity Gate": committed state must not silently diverge from the correct VM result, and proof/version binding fields must stay authenticated. Because this comparator is the single choke point used to assert "replayed output == authenticated on-chain result," omitting the checkpoint hash from that assertion breaks the guarantee that replay verification actually validates the full committed state — only the write-set/event/gas/status subset is validated, not the resulting Merkle root that downstream consumers (light clients, state proofs, hot-state reads) rely on.

### Impact Explanation
This directly weakens a state-commitment integrity control: any code path that relies on `ensure_match_transaction_info` (the CLI's `replay` command, and per the code comment, `db-tool`'s `replay_on_archive` verification flow) can report a transaction replay as "matching" while the state root (and therefore the full account/resource state at that version) has actually diverged from the authenticated ledger. This could mask a hard-fork-class execution divergence (e.g., changed VM semantics silently producing a different state tree) that would otherwise be caught by `replay-verify`/archive-node auditing tooling, since it only compares the write-set hash (a hash of a possibly different write set that could still combine into a different but coincidentally-consistent looking output) and not the resulting checkpoint/state root. Since replay-verify is the network's primary tool for catching consensus-breaking non-determinism in the VM/executor, a gap here has high potential impact (undetected mainnet state divergence) though it is only a detection/verification gap, not itself a state corruption.

### Likelihood Explanation
Low likelihood of being exploited directly (this is a passive verification tool, not an attacker-controlled write path), and the code’s own comment frames it as a known, intentionally-deferred TODO gated behind enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. However, it is a real, currently-shipped gap: nothing in the current code path enforces the state-checkpoint invariant, so any latent state-computation bug that changes only the state tree (not the write set contents/hash construction bug, VM upgrade, or executor refactor) would go undetected by this specific check today.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()` (and, when applicable/available, hot-state and `position_state_checkpoint_hash`) between the actual output and `txn_info`, rather than deferring this to a future feature flag. At minimum, gate usage of `ensure_match_transaction_info` in verification tooling behind an explicit warning/failure if checkpoint hashes are known but unchecked, so `replay_on_archive`/CLI replay cannot report false positives on state-root divergence.

### Proof of Concept
Not independently exploitable as a state-corruption PoC (this is a verification-completeness gap, not a write path). Conceptual repro:
1. Construct/replay a transaction where the resulting write set hash, event hash, gas, and status are unchanged but the resulting state checkpoint hash differs from the recorded `TransactionInfo.state_checkpoint_hash` (e.g., due to a hot-state or position-state computation bug in the executor).
2. Call `TransactionOutput::ensure_match_transaction_info` (as done in `aptos-move/cli/src/commands.rs` replay path, and referenced for `db-tool`'s `replay_on_archive`).
3. Observe the function returns `Ok(())` despite the state-checkpoint hash mismatch, because the comparator never inspects `state_checkpoint_hash()` at [2](#0-1) .

Note: I was unable to fully trace whether `db-tool/replay_on_archive.rs`'s `execute_and_verify` calls this exact comparator or a separate one due to tool/read limitations in the final iteration — this should be independently confirmed before treating the `replay_on_archive` claim as certain; the CLI usage in `aptos-move/cli/src/commands.rs` is confirmed directly.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
