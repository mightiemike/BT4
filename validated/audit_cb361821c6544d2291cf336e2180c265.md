### Title
Market order book can be spammed with minimal-quantity maker orders to force `MAX_MATCH_NUM` overflow, causing legitimate takers' `MarketSellAsset` transactions to fail while still consuming their trade fee - (`File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external report describes a griefing pattern where an attacker cheaply floods a sequentially-processed queue (deposits/withdrawals) so that legitimate users are forced to pay outsized costs to get their own request processed, since it can only be reached after all prior queue entries. `java-tron`'s on-chain exchange (`MarketSellAssetActuator`) contains an analogous unprivileged pattern: the maker order list at a given price is a FIFO linked list (`MarketOrderIdListCapsule`) that any account can populate with many minimal-quantity orders for a fixed, cheap fee, and any taker matching at that price must walk through it up to a hard cap (`MAX_MATCH_NUM = 20`), after which the whole taker transaction reverts.

### Finding Description
`MarketSellAssetActuator.matchOrder` walks the maker order linked list for the best price and matches against it one order at a time via `matchSingleOrder`, incrementing `matchOrderCount` for every order consumed: [1](#0-0) 

If more than `MAX_MATCH_NUM` (20) distinct maker orders are needed to satisfy the taker at that price level, the function throws: [2](#0-1) 

Order creation only requires `sellTokenQuantity > 0` and `buyTokenQuantity > 0`, with an upper bound (`getMarketQuantityLimit()`) but no meaningful lower bound, and the per-account order fee (`calcFee()` = `dynamicStore.getMarketSellFee()`) is a fixed, small constant, independent of order size: [3](#0-2) [4](#0-3) 

Each account can hold up to `MAX_ACTIVE_ORDER_NUM = 100` active orders, so an attacker only needs 21 orders (well under the 100 cap) at the best price to guarantee that any taker match at that price level exceeds `MAX_MATCH_NUM`: [5](#0-4) [6](#0-5) 

When `matchOrder` throws, `execute()` catches the `ContractValidateException`, marks the transaction result `FAILED`, and rethrows as `ContractExeException` — but only *after* the fee has already been deducted from the taker's in-memory account balance and the sell-side balance/asset transfer already performed earlier in `execute()`: [7](#0-6) 

This mirrors the report's root cause: a shared, sequentially-consumed, cheaply-populated data structure (linked list of orders at a price) that a legitimate participant must fully traverse (up to a hard limit) to get their own request serviced, where an unprivileged attacker can populate it far more cheaply than the cost imposed on victims.

### Impact Explanation
An attacker can place ~21+ minimal-quantity sell orders at the best price for a token pair, paying only the fixed `MarketSellFee` per order (no minimum quantity requirement enforced). Any legitimate trader attempting to sell/buy a larger quantity at that price is forced to match through the fragmented book; once more than `MAX_MATCH_NUM` (20) maker orders are required, their `MarketSellAssetContract` transaction fails with `ContractExeException` ("Too many matches"), despite having already deducted the trade fee and performed the sell-side transfer from the taker's account before the exception is raised. This is a Medium-severity griefing/DoS on the on-chain exchange: legitimate takers cannot execute their intended trade size against the best price and are charged for a failed attempt, similar in class to the referenced report's "forced exorbitant fees for legitimate users due to cheap queue/list flooding by an attacker."

### Likelihood Explanation
This requires no privileged role — any account (or set of Sybil accounts, since the 100-order cap is per-account) can place many small `MarketSellAssetContract` orders at negligible marginal cost. The market feature must be enabled (`supportAllowMarketTransaction()`), which is a network-wide committee-controlled flag, not a per-user restriction, so once the DEX is active this attack surface is reachable by any unprivileged user.

### Recommendation
- Enforce a minimum meaningful order quantity (in addition to the existing `> 0` check and `quantityLimit` ceiling) so that fragmenting a price level into many tiny orders is not cheap relative to their notional value.
- Consider charging the trade fee proportional to work actually completed, or refund/avoid double-charging the fee when a trade reverts due to exceeding `MAX_MATCH_NUM`.
- Increase `MAX_MATCH_NUM` dynamically or allow partial success (fill what is matchable and leave the remainder as a resting order) instead of reverting the whole transaction when the match count is exceeded, so a large taker order isn't entirely blocked by a spam-fragmented book.

### Proof of Concept
1. Attacker account A creates 21 `MarketSellAssetContract` orders selling `TOKEN_X` for `TOKEN_Y` at the lowest allowed non-trivial quantity (e.g., `sellTokenQuantity = 1`, `buyTokenQuantity = 1`), each paying only `dynamicStore.getMarketSellFee()`. All 21 orders land in the same price bucket's linked list (`MarketOrderIdListCapsule`) as verified by the existing test harness pattern in `addOrder` used throughout `MarketSellAssetActuatorTest`, e.g.: [8](#0-7) 
2. Victim submits a `MarketSellAssetContract` intending to buy a large quantity of `TOKEN_X` at that same best price.
3. `matchOrder` iterates the 21 orders; on the 21st match, `matchOrderCount (21) > MAX_MATCH_NUM (20)` triggers `throw new ContractValidateException("Too many matches...")`.
4. `execute()` catches this, sets the transaction result to `FAILED`, and re-throws `ContractExeException`, after the taker's balance/asset transfer and fee deduction logic earlier in `execute()` had already run in-memory for that call.

      // 1. transfer of balance
      transferBalanceOrToken(accountCapsule);

      // 2. create and save order
      MarketOrderCapsule orderCapsule = createAndSaveOrder(accountCapsule, contract);

      // 3. match order

      // 4. save remain order into order book
