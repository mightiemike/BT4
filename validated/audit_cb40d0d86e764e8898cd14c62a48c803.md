### Title
Unchecked u64 subtraction in `generate_index()` can underflow `accounts_data_len`, corrupting `Bank::accounts_data_size_initial` on snapshot load/rebuild - ([File: accounts-db/src/accounts_db.rs])

### Summary
During accounts index generation (used when rebuilding a `Bank` from storages/snapshots), `AccountsDb::generate_index()` computes `total_accum.accounts_data_len` by summing per-slot account data lengths, then subtracting out the contribution of duplicate (stale) account versions. Unlike the adjacent capitalization computation, which uses a checked subtraction with an explicit `.expect("capitalization cannot underflow")` guard, the `accounts_data_len` subtraction is a plain, unchecked `u64` operation. This is structurally the same bug class as the reported Uniswap V3 `getOwedFee`/`feeGrowthInside` issue: a delta is computed via subtraction without verifying the minuend is not less than the subtrahend, so if the invariant is ever violated, the result silently wraps (in release builds) instead of surfacing the error, corrupting a value that seeds bank-level accounting.

### Finding Description
In `AccountsDb::generate_index()`: [1](#0-0) 

```rust
total_accum.lt_hash.mix_out(&duplicates_lt_hash.0);
total_accum.capitalization = total_accum
    .capitalization
    .checked_sub(capitalization_from_duplicates)
    .expect("capitalization cannot underflow");
total_accum.accounts_data_len -= accounts_data_len_from_duplicates;
```

`accounts_data_len_from_duplicates` is accumulated in `visit_duplicate_pubkeys_during_startup` by summing `data_len` for every duplicate (non-max-slot) version of a pubkey that has `lamports > 0`: [2](#0-1) 

The developer explicitly hardened the analogous `capitalization` computation with `checked_sub().expect(...)` because "capitalization cannot underflow" is an invariant that must be actively enforced, not assumed. The `accounts_data_len` computation right next to it relies on the same invariant (that every duplicate's `data_len` counted here was already included in `total_accum.accounts_data_len` during `generate_index_for_slot`) but enforces it with plain `-=` instead of a checked/asserted subtraction. This means:
- In debug builds, an invariant violation would panic due to Rust's default debug overflow checks.
- In release builds (which is how validators actually run in production), the same violation silently wraps around to a value near `u64::MAX`, exactly mirroring the Solidity `< 0.8.0` unchecked-underflow behavior described in the report, where `getOwedFee`'s guard (`feeGrowthInside0X128 > feeGrowthInside0LastX128`) was missing and a legitimate subtraction underflowed unnoticed.

The resulting `calculated_accounts_lt_hash`-adjacent value, `total_accum.accounts_data_len`, becomes `IndexGenerationInfo::accounts_data_len`, which is subsequently used to seed the bank's on-chain accounts data size tracking (`accounts_data_size_initial`) when a `Bank` is rebuilt from index/snapshot at startup. Any accounting drift in the per-slot `accounts_data_len` bookkeeping upstream (e.g., an edge case in obsolete-account handling, zero-lamport transitions, or duplicate detection across multiple restart/rebuild cycles) that causes `accounts_data_len_from_duplicates` to exceed `total_accum.accounts_data_len` would silently produce a near-`u64::MAX` `accounts_data_len` in release, rather than failing loudly like the capitalization path does.

### Impact Explanation
If the underflow is triggered, the freshly rebuilt bank's accounts-data-size accounting becomes silently corrupted (wraps to an enormous value) instead of the process crashing with a clear diagnostic. Because `accounts_data_size_initial` gates the network-wide `MAX_ACCOUNTS_DATA_LEN` enforcement used during transaction processing (account resizing/creation checks), a corrupted, huge initial value would make the bank believe accounts data size is already exhausted, causing legitimate transactions that grow account data to be rejected — a denial-of-service against the specific validator that rebuilt state this way, and a state divergence between a node that rebuilt from index/snapshot vs. one that replayed normally (an "honest-node snapshot-vs-replay mismatch" per the accepted impact classes). This is asymmetric with the capitalization path, which is explicitly guarded and will `panic!` (a node panic, also an accepted impact) rather than silently corrupt data.

### Likelihood Explanation
This code only executes during `generate_index()`, i.e., at validator startup (loading from snapshot/index) — a lower-frequency, high-privilege internal path rather than something an unprivileged user can trigger per-transaction. Whether the upstream invariant (`accounts_data_len_from_duplicates <= total_accum.accounts_data_len`) can actually be violated by ordinary duplicate-account bookkeeping (e.g., accounts oscillating between zero and non-zero lamports across duplicate slot versions, or obsolete-account skip logic changing which offsets are summed) was not able to be fully traced/verified in this pass — this is a real gap in verification. The asymmetry with the neighboring, explicitly-guarded capitalization computation is the strongest evidence that the underflow is considered plausible enough by the codebase authors to warrant a checked operation for a directly analogous accumulator, but only for `capitalization`, not for `accounts_data_len`, which appears to be an oversight rather than a deliberate exemption.

### Recommendation
Change `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` to a checked subtraction with an explicit invariant-violation panic, mirroring the capitalization guard immediately above it:

```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```

This ensures that, exactly as with capitalization, any invariant violation is surfaced as a loud, diagnosable panic at startup rather than silently corrupting the bank's on-chain accounts-data-size accounting via integer wraparound in release builds.

### Proof of Concept
A concrete, minimal reproduction was not constructed in this pass because it requires demonstrating a real code path in which `visit_duplicate_pubkeys_during_startup`'s summed `data_len` for duplicate, non-zero-lamport account versions exceeds the `accounts_data_len` accumulated for those same accounts in `generate_index_for_slot` across the relevant slots — this would need controlled construction of storages with duplicate pubkeys/obsolete markings and tracing through `generate_index()` end-to-end, which was not completed here. This is flagged as an open verification item rather than a confirmed exploit; the finding is reported primarily on the basis of the clear code-level asymmetry (unchecked vs. checked subtraction for structurally identical accumulator patterns) rather than a demonstrated triggering sequence.
