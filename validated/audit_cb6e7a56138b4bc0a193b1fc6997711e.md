### Title
`ensure_match_transaction_info` never checks `state_checkpoint_hash`, letting replay-verify/chunk-executor accept a wrong state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by state-sync's chunk executor (`verify_execution`) and the backup `replay-verify` tooling to decide whether a locally re-executed transaction matches the authenticated `TransactionInfo` fetched (with proof) from a backup/peer. It checks status, gas_used, the write-set hash (`state_change_hash`), and the event root hash — but it never checks `state_checkpoint_hash`, the field that actually commits to the JellyfishMerkleTree root of the whole account/resource state after the transaction. The code even documents this gap in a `TODO(trading-native)` comment, but the gap is not limited to the trading-native feature: `state_checkpoint_hash` is unconditionally skipped for every checkpoint transaction, on every path that calls this function today.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  is documented as verifying a `TransactionOutput` against a `TransactionInfo`:

- status vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed event-accumulator root vs `txn_info.event_root_hash()`

It then returns `Ok(())` without ever reading `txn_info.state_checkpoint_hash()` (or the V1 `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), with an explicit note: "this comparator ignores the checkpoint hashes... so replay-verify tooling... can report a successful replay even when the authenticated position state root diverges from local execution." [2](#0-1) 

This function is the sole per-transaction correctness gate in the chunk-executor's replay/verify path:

- `ChunkExecutorInner::verify_execution` re-executes a batch of transactions locally and calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` for every transaction, treating any `Err` as a verification failure. [3](#0-2) 
- This is exercised by `storage/db-tool/src/replay_verify.rs`, which builds a `VerifyExecutionMode::verify_except(...)` and drives `TransactionReplayer::enqueue_chunks` → `remove_and_replay_epoch` → `verify_execution`, i.e. the exact tool operators run against mainnet backups to authenticate historical state. [4](#0-3) 

Separately, `DoStateCheckpoint`/`DoLedgerUpdate` do compute `state_checkpoint_hash` from the state tree during normal block execution/commit [5](#0-4) , and that hash is what's stored in the `TransactionInfo` accumulator and used for state proofs served to light clients/full nodes. But the *comparator used to validate replay against an already-trusted, proof-carrying `TransactionInfo`* never re-derives or compares this value against the locally recomputed state root. So a bug anywhere in the state-tree construction/commit path (JMT construction, hot-state root, or any future divergence introduced by a code change) that produces a wrong `state_checkpoint_hash` while still producing the *same write set and events* would go completely undetected by `verify_execution`/`replay-verify` and by `ensure_match_transaction_info` calls in the CLI replay tool. [6](#0-5) 

Note this is a real, provable gap in the local code's own comparator logic; it is *not* out-of-scope (it is not consensus-observer-only, not test/mock-only, and does not require malicious peers or privileged assumptions — it is a hole in an authenticated verification routine).

### Impact Explanation
The impact is on proof/replay integrity, matching the "Proof And Storage Pivots" criteria: an authenticated `TransactionInfo` (carrying `state_checkpoint_hash`, which anchors state proofs and light-client verification) can be "verified" as matching locally computed output even when the actual state root diverges. This means:
- `replay-verify` (used to audit historical mainnet backups for correctness) can silently pass even if the state root committed on-chain differs from what local execution computes — defeating its core purpose of independently re-proving on-chain state.
- Any latent bug in `DoStateCheckpoint`/JMT root computation, or an intentionally crafted transaction sequence that produces identical write-set/event hashes but a different tree structure/root (e.g. via divergent hot-state or resource-group merge paths), would not be caught by this gate.

This is High severity: it undermines the guarantee that a "verified replay" actually re-proves the committed ledger state, which is exactly the "authenticated ... state root context" class called out in the prompt's scope.

### Likelihood Explanation
The gap is unconditional and always present — it does not require a malicious actor, race condition, or feature flag; it is simply missing logic in the comparator that every replay-verify/state-sync-chunk-verification invocation depends on. It is currently latent (requires *some other* bug or divergence in the state-root-computation code to actually manifest), and the code's own comment confirms the authors are aware but have not yet closed it. Likelihood of the comparator being blind to a real divergence is Medium-to-High whenever such a divergence exists; the underlying trigger (a state-root-affecting bug) is speculative, but the defect in the verification logic itself is proven and 100% reproducible.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between the locally computed state root (from `DoStateCheckpoint`/state tree, where the transaction is a checkpoint) and `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` for V1), removing the current unconditional skip, before any tooling relies on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or general replay-verify to authenticate state correctness.

### Proof of Concept
1. Introduce (or trigger via a real bug) a divergence purely in state-root computation — e.g., a different but hash-collision-free ordering/merge in resource-group or hot-state application that yields the same final key/value set (hence same `write_set` bytes/hash and same events) but a different JMT root due to a code defect in `DoStateCheckpoint`.
2. Run `db-tool replay-verify` (or `ChunkExecutorInner::verify_execution` directly) against a backup containing the affected transaction.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` because it only compares `state_change_hash` (write-set hash) and `event_root_hash`, never `state_checkpoint_hash`, at [7](#0-6) , letting the tool report "ReplayVerify coordinator succeeded" while the recomputed state root is provably wrong. [8](#0-7) 

**Caveat / uncertainty:** I could not find, within the available index, an independent code path that also validates `state_checkpoint_hash` on the verify-execution/replay-verify route (e.g. inside `DoStateCheckpoint`'s "known hashes" check, which does validate *within* one execution session [9](#0-8)  — but that check only fires when `known_state_checkpoints` are threaded in from the *original* `TransactionInfo`s being replayed, i.e., for `ChunkExecutorInner::remove_and_apply`/replayer flows, not for the separately-invoked `verify_execution` re-execution-and-compare path). Given index size limits, I recommend a Devin session with full repository access to confirm whether `DoStateCheckpoint`'s known-hash check is actually wired into the `verify_execution` call path (which would mean the state-root mismatch is caught elsewhere and this finding is only a defense-in-depth gap rather than a standalone bypass) before treating this as fully confirmed high-severity.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn assemble_transaction_infos(
        to_commit: &TransactionsWithOutput,
        transaction_info_v1: bool,
        state_checkpoint_hashes: &[Option<HashValue>],
        hot_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
        position_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
    ) -> (Vec<TransactionInfo>, Vec<HashValue>) {
        let _timer = OTHER_TIMERS.timer_with(&["assemble_transaction_infos"]);

        (0..to_commit.len())
            .into_par_iter()
            .with_min_len(optimal_min_len(to_commit.len(), 64))
            .map(|i| {
                let txn = &to_commit.transactions[i];
                let txn_output = &to_commit.transaction_outputs[i];
                let persisted_auxiliary_info = &to_commit.persisted_auxiliary_infos[i];
                // Use the auxiliary info hash directly from the persisted info
                let auxiliary_info_hash = match persisted_auxiliary_info {
                    PersistedAuxiliaryInfo::None => None,
                    PersistedAuxiliaryInfo::V1 { .. } => {
                        Some(CryptoHash::hash(persisted_auxiliary_info))
                    },
                    PersistedAuxiliaryInfo::TimestampNotYetAssignedV1 { .. } => None,
                };
                let state_checkpoint_hash = state_checkpoint_hashes[i];
                let event_hashes = txn_output
                    .events()
                    .iter()
                    .map(CryptoHash::hash)
                    .collect::<Vec<_>>();
                let event_root_hash =
                    InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash();
                let write_set_hash = CryptoHash::hash(txn_output.write_set());
                let status = txn_output
                    .status()
                    .as_kept_status()
                    .expect("Already sorted.");
                let txn_info = if transaction_info_v1 {
                    TransactionInfo::builder_v1()
                        .transaction_hash(txn.committed_hash())
                        .state_change_hash(write_set_hash)
                        .event_root_hash(event_root_hash)
                        .maybe_state_checkpoint_hash(state_checkpoint_hash)
                        .maybe_hot_state_checkpoint_hash(
                            hot_state_checkpoint_hashes.and_then(|hot| hot[i]),
                        )
                        .gas_used(txn_output.gas_used())
                        .status(status)
                        .maybe_auxiliary_info_hash(auxiliary_info_hash)
                        .maybe_position_state_checkpoint_hash(
                            position_state_checkpoint_hashes.and_then(|p| p[i]),
                        )
                        .build()
                } else {
                    TransactionInfo::builder_v0()
                        .transaction_hash(txn.committed_hash())
                        .state_change_hash(write_set_hash)
                        .event_root_hash(event_root_hash)
                        .maybe_state_checkpoint_hash(state_checkpoint_hash)
                        .gas_used(txn_output.gas_used())
                        .status(status)
                        .maybe_auxiliary_info_hash(auxiliary_info_hash)
                        .build()
                };

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
