Based on my investigation, the strongest analog to the M-1 "hardcoded index causing overwritten requests" bug class is the previously-identified `cookiePath` default collision in the OAuth session cookie flow, which is functionally the same root cause pattern: a fixed/hardcoded key (path `'/'`) used to store per-request/per-tenant state, causing one request's state to silently overwrite another's.

### Title
Non-embedded OAuth session cookie uses a hardcoded `path: '/'` by default, causing cross-shop session cookie overwrite - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
In the OAuth `callback()` handler, the session cookie (`shopify_app_session`) written for non-embedded apps is scoped with a `cookiePath` that defaults to `'/'` unless the app developer explicitly opts in to a per-shop path. This mirrors the M-1 root cause: a value meant to disambiguate concurrent/parallel requests for different identities (there: request `index`; here: cookie `path`) is hardcoded/defaulted to a single fixed value, so a later write for one tenant (shop) silently overwrites the earlier write for another tenant in the same storage location (there: the request mapping; here: the browser's cookie jar).

### Finding Description
`begin()` starts OAuth and sets a signed `STATE_COOKIE_NAME` cookie scoped to `callbackPath` [1](#0-0) . On `callback()`, once the access token exchange succeeds, for non-embedded apps the library signs and stores the resulting `session.id` in a `SESSION_COOKIE_NAME` cookie, using `config.cookiePath ?? '/'` as the cookie path [2](#0-1) .

The `cookiePath` config field is optional and defaults to `'/'` [3](#0-2) . Because a single browser stores only one cookie per `(name, domain, path)` tuple, if a user authenticates App-shop-A and App-shop-B in separate tabs of the same non-embedded app (a very plausible pattern in local dev, multi-tenant admin proxies, or when a merchant manages multiple stores from one browser), the second OAuth callback's `Set-Cookie: shopify_app_session=...; path=/` overwrites the first shop's cookie value at the same path. Any subsequent request from the first tab will now authenticate using the session ID belonging to the second shop, because session lookup for non-embedded apps reads the current session id strictly from this cookie [4](#0-3) .

This is the exact class of bug described in the M-1 report: a value that should vary per logical "request"/tenant to prevent overwrite (there: an incrementing index; here: a per-shop cookie path) is fixed to a constant default, so the storage collides across tenants and the earlier session/request is lost/overwritten without any error being raised to the user.

The maintainers have already acknowledged this exact failure mode in the changelog for the `cookiePath` feature: *"all shops shared a single `shopify_app_session` cookie at `path=/`, so authenticating a new shop would silently overwrite the previous shop's session"* [5](#0-4) . However, the fix is opt-in only — the default behavior (`path: '/'`) remains exactly as vulnerable as before unless the app developer explicitly configures a per-shop `cookiePath`.

### Impact Explanation
When the collision occurs, one tab silently switches to operating as a different shop's authenticated session. A subsequent request made from the "overwritten" tab is authenticated using the wrong shop's session cookie — because `getCurrentSessionId()` (used by the non-embedded session-lookup path) simply trusts and returns whatever session ID is present in the cookie [4](#0-3) , without re-validating that the session actually corresponds to the shop the user believes they are operating on. Depending on how the consuming app wires this session ID into loading session data and authorizing API calls, this can result in cross-tenant confusion: actions/API calls intended for shop A being executed against/using shop B's stored offline/online token, or a merchant losing their in-progress OAuth session entirely (mirroring M-1's "lost request" impact, but for authentication state instead of a paid on-chain request).

### Likelihood Explanation
This requires no privileged access and no attacker interaction — it is triggered purely by the ordinary use pattern of a single unprivileged user (or two unrelated users sharing a browser/session, e.g., in local development or a shared kiosk) authenticating two different shops with the same non-embedded app in the same browser, which is a supported and expected use case for multi-shop non-embedded apps. The vulnerable default (`cookiePath: '/'`) applies unless developers explicitly discover and configure the newly-added `cookiePath` option, which is opt-in and not enforced.

### Recommendation
Make the per-shop cookie path scoping mandatory (or default it based on the shop) rather than optional, or require multi-shop non-embedded configurations to fail fast/warn at startup when `cookiePath` is left at its collision-prone default. At minimum, `getCurrentSessionId()`/session loading in consuming session-storage-based flows should validate that the loaded session's `shop` matches the shop present elsewhere in the request context (URL/query) before trusting it, so a cookie collision cannot silently authorize actions against the wrong shop.

### Proof of Concept
1. Configure a non-embedded app without setting `cookiePath` (default `'/'`).
2. In Tab 1, complete OAuth for `shop-a.myshopify.com`; the response sets `Set-Cookie: shopify_app_session=<session_id_for_shop_a>; path=/`.
3. In Tab 2 (or the same browser profile), complete OAuth for `shop-b.myshopify.com`; the response sets `Set-Cookie: shopify_app_session=<session_id_for_shop_b>; path=/`, overwriting the previous cookie value for the same `(name, domain, path)`.
4. Return to Tab 1 and make a request; `getCurrentSessionId()` reads the cookie and returns `<session_id_for_shop_b>` [6](#0-5) , even though the user in Tab 1 believes they are still working with `shop-a`.

  /**
   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use
   * the most-recently-authenticated shop.
   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
   *
   * @example
   * // Static path (single-shop apps or apps with no shop-specific routing)
   * cookiePath: '/'
   *
   * @example
   * // Factory function (multi-shop non-embedded apps)
   * cookiePath: (session) => `/shops/${session.shop}/`
   *
   * @defaultValue `'/'`
   */
  cookiePath?: string | ((session: Session) => string);

  Non-embedded apps that need to support multiple shops simultaneously in
