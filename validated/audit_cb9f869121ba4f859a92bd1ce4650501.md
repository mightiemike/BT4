### Title
`ValidateMultiSign`/`BatchValidateSign` precompiled contracts hardcode a signature-count cap that is smaller than the protocol's own configurable multi-sign limit, causing valid multi-signature verifications to permanently fail - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompile hardcodes `MAX_SIZE = 5` [1](#0-0)  and rejects any signature array larger than that (`signatures.length == 0 || signatures.length > MAX_SIZE` → returns `DATA_FALSE`) [2](#0-1) . However, the number of keys a permission is allowed to hold is controlled by the chain's own dynamic parameter `getTotalSignNum()`, enforced in `AccountPermissionUpdateActuator.checkPermission`: `permission.getKeysCount() > dynamicStore.getTotalSignNum()` is the only cap applied when an account configures its active permission [3](#0-2) . `TOTAL_SIGN_NUM` is a committee-adjustable dynamic property, not a fixed constant equal to 5 — it is stored/read via `DynamicPropertiesStore` and used identically in transaction-level checks (`checkWeight`, `getTransactionSignWeight`, `getTransactionApprovedList`) which reject only when signatures exceed `getTotalSignNum()` [4](#0-3) [5](#0-4) . This mirrors the Redstone bug class: a hardcoded byte/array size ceiling baked into one code path that is smaller than the size the protocol's own configuration legitimately allows elsewhere, so legitimate data/requests that the protocol says are valid are unconditionally rejected by the undersized path.

### Finding Description
Two independent signature-count ceilings exist in java-tron for multi-signature accounts:
1. The account-permission layer, which allows up to `dynamicStore.getTotalSignNum()` keys per permission (a governance-tunable dynamic property) [3](#0-2) .
2. The TVM precompiled contract `ValidateMultiSign`, reachable from any smart contract via `staticcall`/`call` to the precompile address, which hardcodes `MAX_SIZE = 5` as a `private static final int` and unconditionally returns `DATA_FALSE` for any legitimately constructed call with more than 5 signatures [6](#0-5) . The same pattern (a separate, smaller hardcoded `MAX_SIZE`) exists in `BatchValidateSign`, capped at 16 [7](#0-6) .

Since `getTotalSignNum()` is an on-chain configurable parameter (not fixed at 5) and account permissions are validated against it, the chain permits users/committee to configure permissions with a key/signature count above 5 (or above 16 for the batch precompile) as long as the parameter is raised via governance. Any contract on-chain that calls `ValidateMultiSign` to verify such an account's multi-signature approval will always receive `DATA_FALSE`, regardless of how many valid signatures are supplied, once the configured/legitimate signer count exceeds the hardcoded precompile ceiling. This is directly analogous to the reported issue: the Redstone Bytes[224] payload cap was smaller than what the protocol's own required signer count implied, causing every legitimate call to revert; here the precompile's static `MAX_SIZE` is smaller than what the protocol's own configurable/allowed signer count implies, causing every legitimate on-chain multi-sig verification for such accounts to fail.

### Impact Explanation
This breaks core contract functionality: any smart contract relying on `ValidateMultiSign` (or `BatchValidateSign`) to verify permissions with more signers than the hardcoded cap will never validate correctly, even with fully correct, sufficient signatures, rendering multi-sig-gated on-chain logic unusable for those accounts. There is no direct loss of funds from the precompile itself (it just returns false), consistent with a Medium-severity “breaks core functionality” classification as in the original finding, not a High-severity funds-loss issue.

### Likelihood Explanation
Reachable by any unprivileged contract call from any anonymous caller — no special privileges are required to invoke the `ValidateMultiSign`/`BatchValidateSign` precompiles from a contract, and any account that configures (or that the committee configures) a permission with more keys than the hardcoded `MAX_SIZE` will trigger this every time such verification is attempted. The trigger condition depends on `getTotalSignNum()` being set above 5 (or 16) and an account actually using that many keys, which is a normal, protocol-sanctioned configuration rather than an edge case.

### Recommendation
Align the precompile's `MAX_SIZE` constants with the dynamic property `getTotalSignNum()` (or otherwise make them consistently derived from the same governance-controlled source used in `AccountPermissionUpdateActuator` and `TransactionCapsule.checkWeight`), so that the maximum verifiable signature count in the TVM precompiles can never be smaller than what account-permission configuration allows.

### Proof of Concept
1. Committee/governance raises `TOTAL_SIGN_NUM` above 5 via the standard dynamic-parameter proposal mechanism.
2. An account owner calls `AccountPermissionUpdateContract` to set an `Active` permission with, e.g., 6 keys and a threshold reachable only by combining more than 5 signers; this passes `checkPermission` because `permission.getKeysCount() (6) <= dynamicStore.getTotalSignNum()` [3](#0-2) .
3. A deployed smart contract calls the `ValidateMultiSign` precompile, passing 6 valid signatures (65 bytes each, correctly recoverable to the 6 permission keys) for that account/permission.
4. In `ValidateMultiSign.execute`, `signatures.length` (6) `> MAX_SIZE` (5) causes an immediate `return Pair.of(true, DATA_FALSE)` [8](#0-7) , even though the permission itself, and the transaction-level `checkWeight` path, would accept these exact signatures as valid and sufficient [9](#0-8) .

    HashMap addMap = new HashMap();

      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");

        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
