### Title
Snapshot-restart reward recalculation re-reads live, mutable stake delegation state instead of the epoch-boundary snapshot, allowing an unprivileged staker to change their own distributed reward via `Merge`/`Split` during the distribution window - (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`Bank::recalculate_stake_rewards` (invoked only on the snapshot-restart path, via `recalculate_partitioned_rewards_if_active` -> `initialize_after_snapshot_restore`) recomputes `PartitionedStakeReward`s using `self.stakes_cache.stakes()` and `self.epoch_stakes()` as they exist at the *restart slot*, whereas a continuously-replaying node never recomputes rewards mid-distribution—it simply carries forward the `PartitionedStakeReward` list originally produced by `calculate_stake_rewards_and_commissions` at the epoch boundary, stored in `Bank::epoch_reward_status` and passed unchanged from parent to child bank. Because `Delegation::stake` (nominal stake) is a live, owner-mutable field (via `Split`/`Merge`), and per-account point/stake_reward math is recomputed from this live field rather than a frozen epoch-boundary value, a staker who mutates their own delegated stake account between the epoch boundary and a validator's snapshot-restart point can cause that validator to compute a different `stake_reward` for the same partition than validators that replayed continuously.

### Finding Description
`Bank::recalculate_stake_rewards` at [1](#0-0)  explicitly documents that it recalculates "from ... stake accounts from StakesCache," i.e. the *current* bank's `stakes_cache`, not a value fixed at the epoch boundary:

```
let stakes = self.stakes_cache.stakes();
let EpochRewardCalculateParamInfo { stake_history, stake_delegations, cached_vote_accounts } =
    self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
```

`get_epoch_params_for_recalculation` ( [2](#0-1) ) pulls `stake_delegations` straight from the live `Stakes<StakeAccount<Delegation>>` passed in, with no epoch-boundary snapshot to compare against. This is fed into `calculate_stake_rewards_and_commissions` -> `redeem_delegation_rewards`, where `let stake = *stake_account.stake();` ( [3](#0-2) ) uses the account's *current* `Stake` (containing `delegation.stake`, the nominal delegated lamport amount) to compute this delegator's share of the fixed `total_rewards`/`total_points` persisted in the `EpochRewards` sysvar.

Meanwhile, the continuously-replaying path never calls this recalculation function at all: `Bank::epoch_reward_status` (holding the original `all_stake_rewards` list computed once via `calculate_rewards_for_partitioning` at the epoch boundary) is simply threaded through unchanged from parent bank to child bank across the `REWARD_CALCULATION_NUM_BLOCKS` distribution window, and only `recalculate_partitioned_rewards_if_active` (called solely from `initialize_after_snapshot_restore`) rebuilds it from current state ( [4](#0-3) ).

`delegation.stake` is not immutable after delegation: an unprivileged owner of a stake account can invoke the Stake program's `Split` (reduce this account's `delegation.stake`) or `Merge` (increase it by combining with another already-delegated, fully-active account they control, same voter pubkey) at any point during the distribution window, i.e., strictly after the `rewarded_epoch` has ended. Because `redeem_delegation_rewards`/`calculate_stake_points_and_credits` compute the account's earned points/stake_reward for that already-elapsed `rewarded_epoch` using the *current* `delegation.stake` value (combined with historical `stake_history` activation ratios), a `Merge` performed after the epoch boundary but before a validator's snapshot-restart recalculation inflates the nominal stake used in that computation. A validator that restarts mid-distribution and calls `recalculate_stake_rewards` will therefore compute a different (larger) `stake_reward`/points share for that pubkey than a validator that never restarted and is still using the original, epoch-boundary-frozen `PartitionedStakeReward` for that same partition.

The repo's own regression test at [5](#0-4)  demonstrates that the developers are aware recalculation must match the original epoch-boundary result even after intervening state changes, but that test only exercises the case where the *AG total delegated-stake denominator* changes due to the reward-distribution payout itself (already-tested/fixed via `RewardEpochDelegatedStakes` capture). It does not cover an owner-initiated `Split`/`Merge` altering their own `delegation.stake` between the epoch boundary and recalculation, which is not guarded by any epoch-boundary snapshot of per-account `Delegation` state.

### Impact Explanation
This is a snapshot-vs-continuous-replay divergence in reward computation: validators that restart from a snapshot mid-`REWARD_CALCULATION_NUM_BLOCKS` distribution window can compute different `stake_reward` amounts (and thus different resulting account balances/hashes) for the same slot than validators that replayed continuously, purely as a result of an unprivileged staker's own `Split`/`Merge` transactions executed during the distribution window. This falls under the "honest-node snapshot-vs-replay mismatch" / bank-hash divergence category, which can fork the cluster if enough validators disagree on which path they took (some restarted mid-distribution, some didn't), and can also let a staker unfairly inflate their own reward relative to what they'd receive under continuous replay.

### Likelihood Explanation
Requires: (1) the attacker owns at least two stake accounts delegated to the same vote account, one of which is a reward recipient in the active distribution; (2) the attacker issues a normal `Merge` (or `Split`) instruction against their reward-pending account during the `REWARD_CALCULATION_NUM_BLOCKS` window, strictly after their reward partition was computed at the epoch boundary but before the specific block that would have distributed it; (3) at least one validator restarts from a snapshot taken after that mutation but before distribution of that partition completes. Precondition (3) depends on operational timing (snapshot cadence / restart occurring mid-distribution), which is plausible but not attacker-controlled, making this a real but conditional/probabilistic divergence rather than a deterministic one-shot exploit.

### Recommendation
Freeze the per-account `Delegation`/`Stake` values used for reward calculation at the epoch boundary (e.g., persist or reconstruct them from the same source used by `calculate_rewards_for_partitioning`, not from the live `stakes_cache`), or explicitly document/enforce that `recalculate_stake_rewards` must use a stakes snapshot taken at the `rewarded_epoch` boundary (analogous to how `RewardEpochDelegatedStakes` already freezes the AG total denominator) rather than the current `self.stakes_cache.stakes()`.

### Proof of Concept
Extend `test_recalculate_partitioned_rewards` (or the existing test at [5](#0-4) ) as follows:
1. Create two stake accounts (`stake_a`, `stake_b`) delegated to the same vote account, both fully activated, with `stake_a` smaller and being a reward recipient in the active distribution.
2. Capture the epoch-boundary `PartitionedStakeReward` for `stake_a` from `calculation_status.all_stake_rewards` (as in the existing test).
3. Before the partition containing `stake_a` is distributed, execute a `Merge` of `stake_b` into `stake_a` via the stake program processor (increasing `stake_a`'s `delegation.stake`).
4. Call `bank.recalculate_stake_rewards(&epoch_rewards_sysvar, &thread_pool)` (simulating a snapshot restart) and compare the recomputed `stake_reward` for `stake_a` against the original epoch-boundary value.
5. Assert they differ (`assert_ne!`), proving that snapshot-restart recalculation yields a different reward than continuous replay (which would still deliver the original, unchanged `PartitionedStakeReward`), for the same slot.

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }

    /// Returns a vector of partitioned stake rewards. StakeRewards are
    /// recalculated from an active EpochRewards sysvar, vote accounts from
    /// EpochStakes, and stake accounts from StakesCache.
    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,

            stake_history,
            stake_delegations,
