### Title
Hardcoded NEP-141 storage deposit amount in the Wallet Contract can permanently block ERC20-emulated token transfers to unregistered recipients - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit Wallet Contract emulates ERC-20 `transfer()` calls by translating them into NEP-141 `ft_transfer` calls. When the recipient is not yet registered with the token contract (per NEP-145 storage standard), the contract issues a `storage_deposit` call using a hardcoded constant `NEP_141_STORAGE_DEPOSIT_AMOUNT` instead of querying the target token's actual `storage_balance_bounds`, mirroring the reported bug class where a caller-supplied token address is assumed to conform to one specific implementation instead of using the token's own interface/state to determine required parameters.

### Finding Description
`NEP_141_STORAGE_DEPOSIT_AMOUNT` is defined as a fixed constant (`1_250 * MICRO_NEAR` yoctoNEAR) with an explicit comment stating it is "the one used by the standard NEP-141 implementation, which essentially all tokens use," and is hardcoded specifically "instead of doing the extra on-chain call to `storage_balance_bounds`": [1](#0-0) 

This constant is used unconditionally in `nep_141_storage_balance_callback`, which is reached whenever an ERC20Transfer emulation targets a `receiver_id` that has no existing NEP-141 storage balance. The callback batches a `storage_deposit` function call (with the fixed deposit) followed by the actual transfer function call as two actions in the same promise: [2](#0-1) 

The ERC-20 emulation path that leads here is triggered purely by matching a hardcoded 4-byte ABI selector (`0xa9059cbb`) against the call data, without any verification that the `target` account genuinely implements the NEP-141/NEP-145 standard with the assumed minimum storage bound: [3](#0-2) 

Any NEP-141 token contract whose actual minimum `storage_balance_bounds` exceeds `1,250 * 10^18` yoctoNEAR will reject the `storage_deposit` call for insufficient attached deposit. Because both actions are batched inside a single receipt, the failure of `storage_deposit` prevents the subsequent `ft_transfer` action from executing, and the whole promise resolves as `Failed`: [4](#0-3) 

This is the direct protocol-level analog to the [H01] report: a contract-level assumption that an externally specified, arbitrary token contract conforms exactly to one canonical implementation (here, a specific storage cost) rather than querying/using the target contract's real interface data, resulting in transactions that are structurally incapable of succeeding for non-conforming tokens.

### Impact Explanation
For any NEP-141 token whose registration cost exceeds the hardcoded value, the Wallet Contract can never register a not-yet-registered recipient on behalf of its ETH-implicit account owner via the ERC20-emulated transfer path. Because the emulation path is chosen deterministically from the ABI selector and there is no parameter allowing the signer to specify a larger deposit, tokens already held by the eth-implicit account can become effectively unmovable to any new (unregistered) recipient of that token through this contract — a functional, contract-enforced restriction on fund mobility rather than a one-off transaction failure. This matches the "permanently frozen funds" class of impact called out in the validation criteria, scoped to non-standard (but entirely valid, standard-compliant) NEP-141 tokens.

### Likelihood Explanation
Likelihood is moderate: it requires only a normal, unprivileged flow — an externally owned account holding NEP-141 tokens with an above-hardcoded storage cost, and an attempt to transfer to an unregistered address using the ERC20 emulation on the Wallet Contract. No malicious actor, validator, or special privilege is required; any NEP-141 token deployed with a different (and standard-compliant) storage cost triggers this deterministically.

### Recommendation
Query the target token contract's `storage_balance_bounds` on-chain before issuing `storage_deposit`, rather than relying on a hardcoded constant, and use the returned minimum value (capped to a sane maximum to retain the anti-griefing protection already noted in the code comments) when constructing the `storage_deposit` call.

### Proof of Concept
1. Deploy (or identify) a standard-compliant NEP-141/NEP-145 token contract whose `storage_balance_bounds().min` is greater than `1,250 * 10^18` yoctoNEAR (a value fully within the NEP-145 spec, e.g. tokens with larger per-account state).
2. Have an ETH-implicit account (Wallet Contract) hold a balance of this token.
3. Sign an Ethereum-style `transfer()` call (selector `0xa9059cbb`) via `rlp_execute`, targeting an account that has not yet called `storage_deposit` on that token.
4. Observe that `nep_141_storage_balance_callback` issues `storage_deposit` with the fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT`; the token contract rejects it for insufficient deposit, the batched `ft_transfer` never executes, and `rlp_execute_callback` reports failure — with no code path in the Wallet Contract able to supply a larger deposit for this token.
