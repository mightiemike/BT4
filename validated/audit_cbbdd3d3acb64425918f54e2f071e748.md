### Title
PoisonMicroblock reporting accepts two identical microblock headers as "proof" of equivocation, allowing theft of an honest miner's coinbase - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`check_microblock_header_signer` only verifies that `mblock_header_1` and `mblock_header_2` recover to the same public key hash; it never checks that the two headers actually differ (e.g. different `block_hash`/content at the same sequence number). `handle_poison_microblock`, which calls this function, also performs no such distinctness check before recording the poison report and slashing the miner's coinbase.

### Finding Description
The intended invariant of PoisonMicroblock is:
`poison_reward_paid == exactly_one_valid_double_signature`, i.e. a reward/commission should only be paid when the reporter proves a miner signed two *distinct* microblocks (same sequence, different content) with the same key — genuine equivocation.

`check_microblock_header_signer` (stackslib/src/chainstate/stacks/db/transactions.rs:686-713) only does: [1](#0-0) 
It recovers `pkh1` from `mblock_header_1` and `pkh2` from `mblock_header_2` and errors only if `pkh1 != pkh2`. It never compares `mblock_header_1.block_hash()` to `mblock_header_2.block_hash()`, and never enforces that the two headers even share the same `sequence`.

`handle_poison_microblock` (transactions.rs:722-883) then:
1. Calls `check_microblock_header_signer` and gets back `pubkh` [2](#0-1) .
2. Looks up when `pubkh` was inserted via `get_microblock_pubkey_hash_height` and checks the maturity window (`height + MINER_REWARD_MATURITY < current_height`) [3](#0-2) .
3. Records the report and pays commission to the reporting sender via `insert_microblock_poison`, using `mblock_header_1.sequence` as the "fork point" [4](#0-3) .

Since no code path checks `block_hash(mblock_header_1) != block_hash(mblock_header_2)`, an attacker can take any single, honestly-produced, canonical microblock header (publicly visible from gossip/chain data) that was signed with a pubkey hash `pubkh` inserted via `insert_microblock_pubkey_hash` at height `h` with `h < current_height - MINER_REWARD_MATURITY`, and submit a PoisonMicroblock transaction with `mblock_header_1 == mblock_header_2` (byte-identical). `check_recover_pubkey()` on identical headers trivially yields `pkh1 == pkh2`, so `check_microblock_header_signer` returns `Ok(pubkh)` even though there was never a second, conflicting microblock — i.e., no equivocation occurred at all.

### Impact Explanation
This breaks the reward-loss guarantee: the honest, non-equivocating miner who legitimately produced the microblock stream has their coinbase slashed, and the attacker collects the poison-microblock commission for a report that proves nothing. This is block-reward theft/misappropriation directed at a specific honest miner, matching the "poison or reward mis-payment" High-severity category (bounded to a single miner's coinbase per exploit, but repeatable against every miner whose pubkey-hash height is within the maturity window and whose microblock headers are public).

### Likelihood Explanation
The only precondition is that a legitimate `pubkh` was inserted at height `h` with `h` still inside the `MINER_REWARD_MATURITY` window relative to current height — a state that exists for essentially every actively-mining miner at any time, since microblock pubkey hashes are inserted routinely as part of normal block processing. The attacker needs no stake, no privileged role, and no majority position — merely the ability to read a public microblock header (broadcast via microblock gossip or embedded in the chain) and submit a standard transaction. This is trivially and repeatably exploitable by any unprivileged participant.

### Recommendation
In `check_microblock_header_signer` (or in `handle_poison_microblock` before calling it), require that the two headers represent a genuine fork: assert `mblock_header_1.sequence == mblock_header_2.sequence` and `mblock_header_1.block_hash() != mblock_header_2.block_hash()` (i.e., the serialized/signed content differs), returning `Error::InvalidStacksTransaction` otherwise, in addition to the existing pubkey-hash equality check.

### Proof of Concept
Integration test plan (extending the existing PoisonMicroblock tests in `stackslib/src/chainstate/stacks/tests/block_construction.rs`):
1. Set up a chainstate where an honest miner inserts a microblock pubkey hash `pubkh` at height `h` (via the normal block-commit/microblock-stream path using `insert_microblock_pubkey_hash`).
2. Advance the chain so `current_height < h + MINER_REWARD_MATURITY`.
3. Construct a single valid, honestly-signed `StacksMicroblockHeader` (`hdr`) for that miner's stream.
4. Build a `TransactionPayload::PoisonMicroblock(hdr.clone(), hdr.clone())` transaction from an arbitrary unprivileged sender account and submit it via `StacksChainState::process_transaction`.
5. Assert that `process_transaction` returns `Err(Error::InvalidStacksTransaction(..))` (equal-hash headers rejected) — currently it instead returns `Ok(receipt)` with a populated `StacksTransactionReceipt::from_poison_microblock` result, and the miner's coinbase account balance decreases / the reporter's account is credited a commission, which is the assertion that should fail and currently does not.
