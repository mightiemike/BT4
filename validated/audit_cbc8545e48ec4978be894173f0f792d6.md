### Title
Global contracts deployed in `AccountId` mode allow instant, timelock-free code takeover that can drain every account referencing them - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
NEAR's global contract feature (NEP-591/616) lets an account deploy WASM code that other accounts can reference indirectly via `GlobalContractIdentifier::AccountId(owner)` instead of embedding the code themselves. This is functionally the same "shared upgradeable logic" pattern that produced the original Blur/Non-Fungible finding: any account, including ordinary users' [deterministic accounts](https://github.com/near/NEPs/blob/master/neps/nep-0616.md), can point their contract execution at a global contract "owned" by another account, but that owner can redeploy new code to the same identifier at any time with no timelock, no version pinning, and no opt-out window, immediately changing the logic (and therefore the fund custody rules) that governs every account referencing it.

### Finding Description
The `GlobalContractDeployMode` enum explicitly documents this design: [1](#0-0) 

`CodeHash` mode is immutable (content-addressed), but `AccountId` mode is openly mutable: "This allows the owner to update the contract for all its users." The deploy path confirms there is no restriction preventing redeployment - `action_deploy_global_contract` simply charges storage and calls `initiate_distribution`, which derives the identifier from `account_id` again on every redeploy and bumps a monotonically increasing nonce so the new code always wins: [2](#0-1) 

The distribution/apply logic then unconditionally overwrites the stored code for that `AccountId` identifier as soon as the nonce is fresh, with no delay, no grace period, and no requirement that referencing accounts re-consent: [3](#0-2) 

Any account that referenced the contract "by account id" - either explicitly via `UseGlobalContract{contract_identifier: AccountId(...)}` or implicitly by being created as a NEP-616 deterministic account whose `DeterministicAccountStateInit.code` is a `GlobalContractIdentifier::AccountId(...)` - stores only the reference, not a snapshot of the code: [4](#0-3) [5](#0-4) 

Because only the identifier (not the code) is stored on the referencing account, every future `FunctionCall` resolves the *current* code for that identifier at call time. The runtime's own pipelining logic explicitly acknowledges that a global-contract redeploy changes "the account's executable-code identity" and must be tracked/blocked mid-chunk, confirming the swap is live and immediate: [6](#0-5) 

This is validated end-to-end by the project's own test, which deploys a trivial no-op contract under `AccountId` mode, has two other accounts reference it, then redeploys entirely different code (`rs_contract`) to the *same* identifier and shows the referencing accounts' behavior change instantly, without any additional consent action from those accounts: [7](#0-6) 

### Impact Explanation
Any protocol built on NEAR that uses the `AccountId` global-contract deployment mode to share logic across many accounts (e.g., a vault/AMM/lending pattern implemented via NEP-616 deterministic accounts pointing at a shared "logic" contract, or any account that opts into `UseGlobalContract` by `AccountId` for upgradeability convenience) is exposed to the exact centralization risk described in the source report: the deploying account's owner (or an attacker who compromises that owner's access key) can push new WASM that, e.g., adds a hidden `withdraw_all`/self-transfer method, and it takes effect for every account referencing that identifier with no warning and no time for users to exit. Since these referencing accounts can hold NEAR balances and FT/NFT allowances under the assumption of previously reviewed logic, this enables unauthorized value movement/drain across all accounts that rely on that shared contract, mirroring the "hacked or malicious owner can immediately steal all assets on the platform" impact of the original finding.

### Likelihood Explanation
Reachability requires nothing beyond an ordinary signed transaction: the attacker/owner submits a `DeployGlobalContractAction` with `deploy_mode: AccountId` to the same account id that other accounts already reference; no validator, operator, or node privilege is needed, and this is a first-class, documented, unrestricted protocol action available to any transaction signer.

### Recommendation
For `AccountId`-mode global contracts, add a mandatory delay/timelock between a redeploy submission and the moment the new code becomes callable (e.g., an epoch- or block-based activation height recorded alongside the nonce in `GlobalContractDistributionReceipt`/`TrieKey::GlobalContractNonce`), and/or require referencing accounts to explicitly re-`UseGlobalContract` (opt back in) after a redeploy rather than being silently upgraded, so that users of contracts/deterministic accounts relying on such shared code have a window to withdraw funds or migrate away before malicious logic can execute.

### Proof of Concept
1. Account `owner` deploys benign WASM `V1` via `DeployGlobalContractAction{ deploy_mode: AccountId }` (`runtime/runtime/src/global_contracts.rs:25-63`).
2. Multiple user accounts create NEP-616 deterministic accounts (or call `UseGlobalContract`) referencing `GlobalContractIdentifier::AccountId(owner)`, and deposit NEAR/FT balances managed by `V1`'s logic, as in `test_global_contract_update`/`test_global_contract_nonce_prevents_stale_overwrite` (`test-loop-tests/src/tests/global_contracts.rs:71-106`, `test-loop-tests/src/tests/global_contracts_distribution.rs:268-324`).
3. `owner` (or an attacker holding `owner`'s key) submits a second `DeployGlobalContractAction{ deploy_mode: AccountId }` with malicious WASM `V2` containing a backdoored transfer/withdraw method.
4. Once the distribution receipt with the higher nonce is applied on each shard (`apply_distribution_current_shard`, `runtime/runtime/src/global_contracts.rs:191-227`), every account still referencing `AccountId(owner)` is now executing `V2` on its next `FunctionCall`, with no separate confirmation step.
5. `owner`/attacker calls the malicious method against each user's deterministic account (using `actor_id` still equal to the deterministic account itself, so intra-account permissions in `V2`'s own code can move that account's funds) to drain balances, exactly as the original report's `_stealTokens` demonstrates for the Exchange proxy.

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

fn apply_distribution_current_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
) -> Result<Compute, RuntimeError> {
    let identifier = match &global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => GlobalContractCodeIdentifier::CodeHash(*hash),
        GlobalContractIdentifier::AccountId(account_id) => {
            GlobalContractCodeIdentifier::AccountId(account_id.clone())
        }
    };

    let is_nonce_fresh = check_and_update_nonce(global_contract_data, &identifier, state_update)?;
    if !is_nonce_fresh {
        return Ok(0);
    }

    let config = apply_state.config.wasm_config.clone();
    let trie_key = TrieKey::GlobalContractCode { identifier };
    let code_len = global_contract_data.code().len() as u64;
    state_update.set(trie_key, global_contract_data.code().to_vec());

    // Record the deploy so a same-chunk call can find the code without a warm cache.
    let code_hash = match global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => Some(*hash),
        GlobalContractIdentifier::AccountId(_) => None,
    };
    if ProtocolFeature::GlobalContractSameChunkCallFix.enabled(apply_state.current_protocol_version)
    {
        state_update.record_global_contract_deploy(ContractCode::new(
            global_contract_data.code().to_vec(),
            code_hash,
        ));
    }

    state_update.commit(StateChangeCause::ReceiptProcessing { receipt_hash: receipt.get_hash() });

#[test]
fn test_global_contract_update() {
    let mut env = GlobalContractsTestEnv::setup(Balance::from_near(1000));
    let use_accounts = [env.account_shard_0.clone(), env.account_shard_1.clone()];

    env.deploy_trivial_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        env.use_global_contract(
            account,
            GlobalContractIdentifier::AccountId(env.deploy_account.clone()),
        );

        // Currently deployed trivial contract doesn't have any methods,
        // so we expect any function call to fail with MethodNotFound error
        let call_tx = env.call_global_contract_tx(account.clone(), account.clone());
        let call_outcome = env.execute_tx(call_tx);
        assert_matches!(
            call_outcome.status,
            FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
                kind: ActionErrorKind::FunctionCallError(FunctionCallError::MethodResolveError(
                    MethodResolveError::MethodNotFound
                )),
                index: _
            }))
        );
    }

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        // Function call should be successful after deploying rs contract
        // containing the function we call here
        env.assert_call_global_contract_success(account.clone(), account.clone());
    }
}
