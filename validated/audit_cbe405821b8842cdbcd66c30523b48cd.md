## Title
Unauthenticated `batchProver_submitFakeProof` / `batchProver_setCommitments` RPC calls allow a false state transition to be proved and submitted to DA - ([File: crates/batch-prover/src/rpc.rs])

### Summary
The `Auth` JSON-RPC middleware only gates three methods (`backup_create`, `backup_validate`, `backup_info`) behind an API key. All other RPC methods registered on a batch-prover node — including `batchProver_setCommitments` and `batchProver_submitFakeProof` — are dispatched without any authentication or authorization check, mirroring the reported bug class of a state-mutating entry point missing an owner/authority check.

### Finding Description
The `Auth` middleware wraps every RPC call and only enforces the API key for a hard-coded allowlist: [1](#0-0) [2](#0-1) 

Any method not in `PROTECTED_METHODS` is passed straight through to the underlying service with no authentication. The batch-prover RPC module registers, among others: [3](#0-2) 

`set_commitments` explicitly documents that it "overrides the commitment already if exists, so use with caution," and `submit_fake_proof` "collect[s] output from the execution in native... and submit[s] the fake proof to DA" for an arbitrary commitment index range. Both directly mutate the sequencer-commitment/proof state that is later relied upon to build and submit proofs referencing L1, which is exactly the "false state transition proved" binding this scan is meant to catch: `(index_start, index_end)` chosen commitments → fake receipt built with `FakeReceipt`/`InnerReceipt` → submitted via `DaTxRequest::ZKProof` to the DA layer under the batch prover's own DA key, all without verifying that the caller is the legitimate batch-prover operator.

The RPC server itself does not bind these admin/test-only methods behind any additional network-layer restriction visible in-repo; the only control point (`Auth`) is scoped to backup methods, exactly as configured in `crates/common/src/rpc/server.rs`: [4](#0-3) 

The equality this breaks: `set of proofs a legitimate batch prover authorized` should equal `set of proofs the batch-prover node will submit/serve to DA and downstream consumers`. Because `submitFakeProof`/`setCommitments` are reachable by anyone who can reach the node's RPC port without any credential, this equality can be broken by an unauthenticated caller.

### Impact Explanation
If the batch prover's RPC port is reachable by anyone (no TLS interception, no key compromise required — merely no authentication is enforced by design for these methods), a caller can:
1. Call `batchProver_setCommitments` to overwrite the prover's local view of sequencer commitments with attacker-chosen values.
2. Call `batchProver_submitFakeProof` to build and submit a `FakeReceipt`-based ("fake"/non-cryptographic) batch proof for an arbitrary commitment range directly to the DA layer, tagged as coming from the batch prover's DA key.

This is a "false state transition proved" scenario: a non-genuine proof is injected into the DA-tracked batch-proof stream, which downstream light-client/rollup logic may treat as a legitimate proof submission from the batch prover, since `crates/light-client-prover/src/circuit/mod.rs` only checks batch-proof method IDs and DA sender pubkey/signature, not whether the proof content is "real" vs "fake."

### Likelihood Explanation
Reaching this requires only network access to the batch-prover's JSON-RPC endpoint — no sequencer, prover, or security-council key is needed, since these methods are excluded from the `Auth` allowlist entirely (they need no API key at all, unlike `backup_*`). This is a lower bar than most items excluded by the scan's rules (which exclude findings requiring a prover/sequencer/operator *role*); here the flaw is that the RPC layer treats these prover-administration methods as fully public rather than assigning them any role check, similar to `setTradingAccountToken` lacking `onlyOwner`.

I was not able to fully confirm from the indexed code whether these RPC methods are additionally restricted at deployment (e.g., bound to localhost only, or behind a reverse proxy) — that configuration detail is outside `crates/*/src/**` and not visible in the indexed source. If such external restriction is standard and mandatory, this reduces to a defense-in-depth gap rather than a directly exploitable vulnerability; if not, it is directly exploitable by any network-reachable client.

### Recommendation
Add `set_commitments`, `submit_fake_proof`, `pause_proving`, and `create_circuit_input` (and any other state-mutating batch-prover RPC methods) to the `Auth` middleware's protected-method list (or a broader allow/deny policy keyed to method sensitivity, not just backup methods), requiring the configured `api_key` for all of them by default.

### Proof of Concept
Not executable from the available read-only index (no terminal/RPC access). Conceptually:
1. Start a batch-prover node with RPC exposed (`rpc.bind_host`/`bind_port`), with `rpc_config.api_key` set (or unset).
2. From an unauthenticated JSON-RPC client, call:
```
{"jsonrpc":"2.0","id":1,"method":"batchProver_setCommitments","params":[[...attacker chosen commitments...]]}
```
followed by:
```
{"jsonrpc":"2.0","id":2,"method":"batchProver_submitFakeProof","params":[index_start, index_end]}
```
3. Observe that `Auth::call` in `crates/common/src/rpc/auth.rs` passes both requests straight through (since neither method name is in `PROTECTED_METHODS`), and the fake proof is submitted to DA via `DaTxRequest::ZKProof`, bypassing any batch-prover-operator authorization check.

**Confidence note:** I could not verify from the indexed files whether these RPC endpoints are gated by an external reverse-proxy or firewall in production deployments (that configuration lives outside `crates/*/src/**`/`bin/citrea/src/**`), so the practical exploitability depends on deployment topology not fully visible here.

pub trait BatchProverRpc {
    /// Manually set commitments. It overrides the commitment already if exists, so use with caution.
    ///
    /// # Arguments
    /// * `commitments` - A vector of sequencer commitments to be set.
    #[method(name = "setCommitments")]
    async fn set_commitments(&self, commitments: Vec<SequencerCommitmentRpcParam>)
        -> RpcResult<()>;

    /// Manually signal proving. This rpc triggers a proving signal with the difference that sampling will be ignored.
    ///
    /// # Arguments
    /// * `mode` - The partition mode to use for proving.
    #[method(name = "prove")]
    async fn prove(&self, mode: PartitionMode) -> RpcResult<Vec<Uuid>>;

    /// Simulate proving by collecting output from the execution in native, and submit the fake proof to DA.
    ///
    /// # Arguments
    /// * `index_start` - The starting index of the commitment range to submit a fake proof for.
    /// * `index_end` - The ending index of the commitment range to submit a fake proof for.
    /// Important caveats regarding the arguments:
    /// - `index_start` must be greater than 1, as the first commitment index requires special handling.
    /// - `index_end` must be greater than or equal to `index_start`.
    /// - The range is inclusive, meaning both `index_start` and `index_end` are included in the proof.
    /// - The previous index to `index_start` must exist in the ledger database if `index_start` is greater than 1.
    ///
    /// # Returns
    /// A `BatchProofResponse` containing the L1 transaction ID, proof, and proof output.
    #[method(name = "submitFakeProof")]
    async fn submit_fake_proof(
        &self,
        index_start: u32,
        index_end: u32,
    ) -> RpcResult<BatchProofResponse>;
