### Title
Replay-verify (`ensure_match_transaction_info`) does not validate the state/hot-state/position-state checkpoint hashes, allowing a divergent authenticated state root to pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by `db-tool`'s `replay_on_archive` verifier to confirm that locally re-executed transaction output matches the transaction info that was persisted/authenticated in the archive being replayed. It explicitly checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but — per its own embedded TODO — never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` is the sole gate used by `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` to decide whether a re-executed transaction "matches" the archived/authenticated `TransactionInfo`: [2](#0-1) 

The function itself contains an acknowledged gap, stated directly in the source:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

Meanwhile, `BlockExecutorConfigFromOnchain::with_features` already wires up an on-chain feature flag, `compute_trading_native_state_roots`, that is gated only behind `transaction_info_v1` and `hotness_in_epilogue` being enabled — it is not gated behind this validator being fixed: [4](#0-3) 

`TransactionInfoV1` includes the additional root fields (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) that this comparator is supposed to check: [5](#0-4) 

The `position_state` checkpoint root itself is computed via a separate Sparse-Merkle-style extend/hash path in `do_state_checkpoint.rs` that is independent of the write-set hash and event root hash already checked by `ensure_match_transaction_info`: [6](#0-5) 

Because `state_change_hash` (write-set hash) and `event_root_hash` are independent commitments from `state_checkpoint_hash`/`position_state_checkpoint_hash`, a node can produce a write set and events that hash-match the archived `TransactionInfo` while its locally computed position/state-checkpoint root differs from the one embedded (and blessed by validator signatures via `LedgerInfo`) in the archived `TransactionInfo`/`LedgerInfoWithSignatures`. `ensure_match_transaction_info` would still return `Ok(())`, and `replay_on_archive` would report a clean, successful replay.

### Impact Explanation
This breaks the guarantee that `replay-verify` tooling authenticates the full state produced by a block, not just the write set and events. If the `position_state`/hot-state Merklization logic (a newly introduced code path per the surrounding "HotState"/"trading-native" TODOs) has a bug that produces a wrong root hash while still producing a correct write set, `replay_on_archive` will silently certify a mismatch between the locally re-derived ledger state and the state that was actually committed and signed by validators. This directly matches the required "Committed state that differs from correct VM result" and "authenticated ... output bound to wrong ... proof context" impact class, since the very purpose of this tool is to catch such divergence and it is disabled for this specific root by design.

### Likelihood Explanation
The feature (`compute_trading_native_state_roots`) is currently off by default in all constructors (`new`, `new_no_block_limit`, `new_maybe_block_limit`, `on_but_large_for_test`), and is only enabled through `with_features` when the corresponding on-chain feature flags are turned on. This is an emerging/opt-in feature path (the "HotState"/"trading-native" work is explicitly still in progress, per the surrounding TODOs), so the likelihood of exploitation depends entirely on whether/when `compute_trading_native_state_roots` is activated on mainnet before this comparator is fixed. The code comment itself flags this as a pre-condition ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating the maintainers are aware this is an unresolved blocker for safely turning the feature on — I could not confirm from the index whether the feature is enabled on mainnet today.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the expected `TransactionInfo`) against the locally computed roots before this function is relied upon for any release enabling `compute_trading_native_state_roots`, consistent with the TODO already present in the code.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-tooling gap rather than a directly triggerable state-corruption bug. The relevant condition is structural: (1) `execute_and_verify` in `replay_on_archive.rs` relies solely on `ensure_match_transaction_info`; (2) that function does not compare `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`; (3) these fields are only produced/validated by a separate, independent code path in `do_state_checkpoint.rs`. Confirming actual exploitability requires knowing whether `compute_trading_native_state_roots` has been enabled in production and whether the underlying Merklization path has any independent bug — this was not verifiable from the indexed code alone, and I recommend a Devin session with full repo/checkout access to check the current feature-flag rollout status and any related unit tests before treating this as more than a documented-but-unaddressed gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
