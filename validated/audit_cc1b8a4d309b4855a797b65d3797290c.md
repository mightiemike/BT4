### Title
`handle_poison_microblock` never checks that `prev_block`/`sequence` match, so unrelated same-key microblocks are accepted as "poison" - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`StacksChainState::handle_poison_microblock` and its helper `check_microblock_header_signer` only verify that the two supplied `StacksMicroblockHeader`s recover to the same public key hash; they never check that `mblock_header_1.prev_block == mblock_header_2.prev_block` (or that `sequence` matches). The only place that enforces "these two headers actually conflict at the same fork point" is the mempool admission path (`MemPoolRejection::PoisonMicroblocksDoNotConflict` check), which is advisory and not part of the consensus-critical transaction-processing function that a miner invokes when building/accepting a block.

### Finding Description
The claimed equality is: *reward/commission is paid only for one verified double-signature at the same fork point (same `prev_block`/`sequence`, different microblock)*. Tracing the code:

- `check_microblock_header_signer` (stackslib/src/chainstate/stacks/db/transactions.rs, lines 686-713) recovers the pubkey hash from each header via `check_recover_pubkey` and only compares `pkh1 != pkh2`. It never touches `prev_block` or `sequence`. [1](#0-0) 
- `handle_poison_microblock` (same file, lines 722-870) calls only `check_microblock_header_signer`, then looks up `get_microblock_pubkey_hash_height`, checks the `MINER_REWARD_MATURITY` window, and unconditionally records/updates a poison report keyed only by `mblock_pubk_height` and `mblock_header_1.sequence` via `insert_microblock_poison`. [2](#0-1) [3](#0-2) 
- The equality check that the question refers to (`sequence` and `prev_block` and `version` must match, i.e., a genuine equivocation at one fork point) exists **only** in the mempool admission validator, `MemPoolRejection` handling for `TransactionPayload::PoisonMicroblock`, in `stackslib/src/chainstate/stacks/db/blocks.rs`. [4](#0-3) 

Because that check lives in the mempool admission path and not inside `handle_poison_microblock`/`process_transaction` (the actual state-transition function invoked when a block is processed, as exercised directly by the `process_poison_microblock_same_block` test which calls `StacksChainState::process_transaction` without going through mempool admission), a transaction built and injected directly into a block (something a miner — an unprivileged single-slot participant per the threat model — can do) bypasses the conflict check entirely. [5](#0-4) 

Exploit flow: attacker (a miner who legitimately reused the same microblock private key across two unrelated tenures — permitted by codec/consensus rules) takes `StacksMicroblockHeader`s from two different, unrelated microblock streams (different `prev_block`, not a fork of each other) signed by the same key, wraps them in `TransactionPayload::PoisonMicroblock(header_1, header_2)`, and includes this transaction directly in a block they mine (skipping mempool admission, or mining it themselves so mempool "rejection" is irrelevant). `process_transaction` → `handle_poison_microblock` → `check_microblock_header_signer` only checks pubkey equality, passes, and `insert_microblock_poison` records the "poison" and commissions the reporter.

### Impact Explanation
This is a false-slashing / reward-misdirection bug: an honest miner who reused a microblock signing key across two unrelated tenures can have their future coinbase commission diverted to a false "poison" reporter, even though no equivocation (fork) ever occurred. This is a reward mis-payment triggered by a minority participant (a single miner), matching the "poison or reward mis-payment bounded to fees/coinbase" category. It does not, by itself, cause two honest nodes to disagree on the canonical chain (both would apply the same faulty transaction identically), so it does not rise to a chain-split; the damage is confined to the reward accounting for the affected key/miner.

### Likelihood Explanation
Preconditions: the attacker must (a) hold a microblock private key that was legitimately reused across two tenures (permitted — the codec places no restriction preventing key reuse across tenures) and (b) be able to get a `PoisonMicroblock` transaction with the two forged headers into a processed block. The attacker only needs to be a single miner (their own sortition win, their own BTC) to embed the transaction directly into their own mined block, bypassing the mempool's advisory `PoisonMicroblocksDoNotConflict` check. This requires no majority stake and is repeatable against any key reused across tenures.

### Recommendation
Move the `sequence`/`prev_block`/`version` equality check (currently only present in the mempool `MemPoolRejection` validator at `stackslib/src/chainstate/stacks/db/blocks.rs` lines 6844-6850) into the consensus-critical path, i.e., add it to `check_microblock_header_signer` or at the top of `handle_poison_microblock` in `stackslib/src/chainstate/stacks/db/transactions.rs`, so that `process_transaction` itself rejects `PoisonMicroblock` transactions whose two headers do not share the same `prev_block` and `sequence` (a genuine equivocation), regardless of whether the transaction went through mempool admission.

### Proof of Concept
Rust integration test plan (extending the existing `process_poison_microblock_same_block`/`process_poison_microblock_invalid_transaction` tests in `stackslib/src/chainstate/stacks/db/transactions.rs`):
1. Generate a single microblock private key `block_privk` and register its pubkey hash at height 1 via `insert_microblock_pubkey_hash`.
2. Build `mblock_1` with `prev_block = BlockHeaderHash([0x11; 32])`, `sequence = 5` (simulating tenure A), signed with `block_privk`.
3. Build `mblock_2` with a *different* `prev_block = BlockHeaderHash([0x22; 32])`, `sequence = 9` (simulating unrelated tenure B), signed with the same `block_privk`.
4. Construct `TransactionPayload::PoisonMicroblock(mblock_1.header, mblock_2.header)`, sign it, and call `StacksChainState::process_transaction` directly (bypassing mempool admission, mirroring how a miner-built block would be processed).
5. Assert-before: no poison report exists for this pubkey/height.
6. Assert-after (bug confirmed if these pass): `process_transaction` returns `Ok(..)`, and `StacksChainState::get_poison_microblock_report` returns `Some((reporter_addr, sequence))`, i.e., a false slashing record was created despite `mblock_1.header.prev_block != mblock_2.header.prev_block` — proving the two headers never shared a fork point yet were accepted as valid poison.
7. Compare against expected correct behavior: the same call should instead return `Err(Error::InvalidStacksTransaction(..))` once the fix (equality check on `prev_block`/`sequence`) is added to `handle_poison_microblock`.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
