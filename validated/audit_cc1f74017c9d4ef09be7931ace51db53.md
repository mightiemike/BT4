### Title
Unauthorized `TransferToGasKey` lets any account grief a victim's gas-key deletion by pushing its balance over `MAX_BALANCE_TO_BURN` - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`action_transfer_to_gas_key` can be invoked by *any* predecessor against *any* account's gas key — it is not restricted to the account owner. An attacker can repeatedly top up a victim's gas key balance until it exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), after which the victim's own `DeleteKey`/`DeleteAccount` transactions targeting that key permanently fail with `GasKeyBalanceTooHigh`.

### Finding Description
`check_actor_permissions` (`runtime/runtime/src/actions.rs:755-801`) enforces `actor_id == account_id` for `AddKey`, `DeleteKey`, `WithdrawFromGasKey`, `DeployContract`, `Stake`, etc., but explicitly carves out `Action::TransferToGasKey(_)` alongside `CreateAccount`/`FunctionCall`/`Transfer` as actions requiring no actor-permission check (`actions.rs:793-796`). This means a receipt from any predecessor account can carry a `TransferToGasKey` action targeting a gas key on someone else's account, and `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`) will happily `checked_add` the deposit to `gas_key_info.balance` regardless of who sent it.

Separately, `delete_gas_key` (`runtime/runtime/src/access_keys.rs:93-111`) rejects deletion outright — via `ActionErrorKind::GasKeyBalanceTooHigh` — whenever `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`, because that balance would otherwise be silently burned (`result.tokens_burnt`) rather than refunded. There is no upper bound enforced when funds are added via `TransferToGasKey`; the cap is only checked at deletion time.

This is structurally the same bug class as the reported Blueberry issue: a value the contract/runtime relies on for admission/limit checks (here, `gas_key_info.balance`, analogous to `borrowToken.balanceOf(address(this))`) can be inflated by an unrelated, unprivileged party sending funds directly, and that inflated value then causes a legitimate operation by the rightful owner (deleting/burning the gas key) to revert, even though the owner never intended or authorized that balance level.

### Impact Explanation
An attacker with a trivial balance (just over `MAX_BALANCE_TO_BURN`, currently 1 NEAR, split across multiple `TransferToGasKey` receipts if desired) can force any of a victim's gas keys into a state where the victim can never delete that key or delete the account while the key is attached, because `DeleteKey`/`DeleteAccount` unconditionally hits `GasKeyBalanceTooHigh`. This is a transaction-triggered denial-of-service / permanent freeze of account/key lifecycle operations for the victim, reachable from a single unprivileged receipt sent by any account — no special privileges, validator status, or network position required.

### Likelihood Explanation
High likelihood: the attack requires only sending a standard `TransferToGasKey` action (available via `SignedTransaction`/`FunctionCall` promise batch, e.g. `promise_batch_action_transfer_to_gas_key`) to any account whose public key of a gas key is known (gas key public keys are visible on-chain via `AddKey` receipts/views). The griefing deposit needed is only slightly above `MAX_BALANCE_TO_BURN` (1 NEAR), a small, one-time cost to permanently lock the victim's ability to delete that key.

### Recommendation
Restrict `Action::TransferToGasKey` in `check_actor_permissions` (`runtime/runtime/src/actions.rs`) to require `actor_id == account_id`, matching `WithdrawFromGasKey`, so only the account owner (via full-access key or an already-authorized gas key) can fund its own gas keys. Alternatively, enforce the `MAX_BALANCE_TO_BURN` cap at `action_transfer_to_gas_key` time (reject or truncate deposits that would push the balance above the threshold) rather than only checking it at deletion time.

### Proof of Concept
1. Victim account `victim.near` adds a gas key `gk` via `AddKey` with `AccessKey::gas_key_full_access(n)`.
2. Attacker (any unrelated account) submits a transaction/receipt containing `Action::TransferToGasKey(TransferToGasKeyAction { public_key: gk, deposit: 2 NEAR })` targeting `victim.near`. Since `check_actor_permissions` does not check the actor for this action (`actions.rs:793-796`), the receipt succeeds and `gas_key_info.balance` becomes `2 NEAR > MAX_BALANCE_TO_BURN (1 NEAR)`.
3. Victim later submits `Action::DeleteKey(DeleteKeyAction { public_key: gk })` (self-signed, `actor_id == account_id`). This calls `delete_gas_key` (`access_keys.rs:93-111`), which checks `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN` and returns `ActionErrorKind::GasKeyBalanceTooHigh`, permanently blocking deletion of that key (and blocking `DeleteAccount` while the key remains attached) unless the victim first withdraws via `WithdrawFromGasKey`. Note: if the victim can still call `WithdrawFromGasKey` themselves, the true "unbounded freeze" only manifests when the attacker's funding races or exceeds what the victim can withdraw before deletion in the same block/receipt sequence, or when the added deposit is deliberately kept just above the threshold; the core issue — an unprivileged party unilaterally mutating a balance gating a privileged owner-only operation — is confirmed by the code paths cited above.
