### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting corrupted state/hot-state/position-state roots pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check that binds a locally-computed `TransactionOutput` (write set, events, status, gas) to the authenticated `TransactionInfo` that is hashed into the transaction accumulator. It verifies status, gas, write-set hash (`state_change_hash`) and event root hash, but the function's own comment documents that it does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against locally recomputed values [1](#0-0) . This function is exactly the kind of "authenticated response bound to the wrong ledger state" check the task asks about: it is the local oracle used by replay/restore tooling to assert that recomputed state matches the committed, consensus-signed `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` checks:
- `status` vs. `txn_info.status()` [2](#0-1) 
- `gas_used` vs. `txn_info.gas_used()` [3](#0-2) 
- write-set hash vs. `txn_info.state_change_hash()` [4](#0-3) 
- event root hash vs. `txn_info.event_root_hash()` [5](#0-4) 

It never touches `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which are fields carried on `TransactionInfoV0`/`TransactionInfoV1` and folded into the accumulator leaf hash that consensus signs [6](#0-5) . The code's own TODO states this plainly: the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and instructs that these hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [1](#0-0) .

This is analogous to the seed report's root cause: a downstream consumer (`WConvexPools`) assumed a fixed return/field shape from an evolving upstream struct (Convex `PoolInfo`) and broke silently when that shape changed. Here, `TransactionInfo` evolved from V0 to V1 by adding new authenticated hash fields (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) [6](#0-5) , but the shared integrity-check helper that consumers rely on for replay verification was not updated to cover the new fields — it silently continues to only check the subset of fields that existed for the original `TransactionInfoV0` shape (and even omits the pre-existing `state_checkpoint_hash`).

### Impact Explanation
If a node (or db-tool's `replay_on_archive`) uses `ensure_match_transaction_info` as its sole comparator when replaying archived transactions/outputs against committed `TransactionInfo`, it will report a clean replay even if the locally recomputed state root, hot-state root, or native-position state root diverges from the authenticated, consensus-committed root. This is a proof/commitment-integrity gap on the restore/replay-verification path: a corrupted or maliciously altered durable write set that still hashes to the correct write-set hash but whose materialized state tree/state root differs would not be caught. Since `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` verification is explicitly still gated behind not-yet-enabled feature flags (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) [7](#0-6) , current mainnet-observable impact is limited to whatever those features already gate, but the gap is real, self-acknowledged in-repo, and directly affects state-commitment verification integrity in replay/restore tooling — exactly the kind of hard-fork/replay divergence class called out in the task's scope.

### Likelihood Explanation
This isn't a hypothetical: the gap is called out by name in the source with an explicit TODO warning about the exact failure mode ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution") [1](#0-0) . The trigger condition is simply enabling the associated feature flags (which the code comments indicate is anticipated) or any other caller that reaches this comparator expecting it to fully validate checkpoint-bound state roots.

### Recommendation
Extend `ensure_match_transaction_info` to validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values whenever those fields are present on the `TransactionInfo` variant, gating each check on the feature flags that populate them, and block enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and any dependent feature) until this validation is in place, per the code's own TODO.

### Proof of Concept
Not applicable as an exploit PoC (no external attacker interaction is required); the "proof" is the code path itself: `ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2204` only asserts on `status`, `gas_used`, `state_change_hash`, and `event_root_hash`, and its own comment at lines 2197-2203 documents the missing checks and the exact tool (`replay_on_archive`) affected.

**Note on confidence**: I could not fully trace every call site of `ensure_match_transaction_info` (e.g., confirm whether db-tool's `replay_on_archive` or state-sync chunk-apply paths use it exclusively, or layer additional state-root checks elsewhere) within the available tool budget. If another code path independently verifies `state_checkpoint_hash` during normal chunk execution/commit (which is plausible, since it's a long-standing field), the practical severity would be reduced to the newer `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields only, consistent with the TODO's framing around `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. This should be verified against the actual replay-verify/db-tool call sites before treating this as fully independent of feature-flag gating.
