### Title
Duplicate-weight accumulation in `ValidateMultiSign` precompile via ECDSA signature malleability - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract, which lets on-chain contracts verify a weighted multi-signature quorum against an account's `Permission`, deduplicates signers by comparing raw signature bytes instead of by recovered address. Because ECDSA signatures are malleable (an `(r, s, v)` triple can be transformed into a distinct byte-different `(r, n-s, 1-v)` triple that recovers to the exact same address), a single signer's weight can be counted multiple times, letting one signer alone satisfy a quorum threshold meant to require independent approvals from several key holders. This mirrors the reported `submitCheckpoint` class of bug: "missing signature duplication check" that lets one signer inflate accumulated weight past the threshold.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`, the dedup logic is: [1](#0-0) 

```
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```

The inner `continue` only triggers when the *exact same signature bytes* (`sign`, merged with the address) are re-submitted. If the recovered address has already appeared but the raw signature bytes differ, execution falls through and adds the weight again for that same address, rather than rejecting the second entry as an already-counted signer. This is the same root cause as the `submitCheckpoint` finding: the array of signatories/signatures is not deduplicated by signer identity, only by exact signature bytes (analogous to not deduplicating the "signatories" array at all).

ECDSA signatures are malleable: given a valid `(r, s)` signature over a hash, `(r, n - s mod n)` (with the recovery id flipped) is also a valid signature that recovers to the identical public key/address. Anyone holding one valid signature from a real permission key holder can therefore mechanically derive a second, third, etc., distinct-byte signature for the same address without needing any additional private key material. Passing several such malleated variants in the `signatures` array bypasses the byte-exact dedup check and lets `totalWeight` be incremented multiple times for a single actual signer.

By contrast, the transaction-level multisig weight check (`TransactionCapsule.checkWeight`) correctly deduplicates by the *recovered address* itself: [2](#0-1) 
This confirms the precompile's approach (dedup by raw signature bytes via `executedSignList`) is inconsistent with the safer address-based pattern used elsewhere in the codebase, and is the defective analog.

### Impact Explanation
`ValidateMultiSign` is a TVM precompiled contract callable by any smart contract via a `TriggerSmartContract` transaction (reachable by any user broadcasting a contract call). DApps commonly use it to gate privileged on-chain actions (e.g., releasing funds, approving withdrawals, executing governance actions) behind an account's weighted `Permission` multisig. A single colluding or compromised key holder can supply several malleated variants of their own signature to make the precompile report the quorum threshold as met, even though only one real signer actually approved the action — directly undermining the security guarantee that a majority/threshold of independent key holders authorized the operation. This can lead to unauthorized execution of multisig-gated contract logic and asset/accounting corruption in any DApp relying on this precompile for authorization.

### Likelihood Explanation
The attack requires no privileged access and no more than one valid signature to bootstrap from: an attacker only needs to obtain (or already possess) one legitimate signature over the target hash for a key already present in the target `Permission`, then derive malleated variants deterministically (public math, no secret key needed) and submit them all in a single `TriggerSmartContract` call. This is a low-cost, purely computational operation reachable directly from an unprivileged RPC/broadcast transaction, making exploitation straightforward wherever a contract uses `ValidateMultiSign` for authorization with more than 1 required key/weight.

### Recommendation
Change the dedup key in `ValidateMultiSign.execute` from raw signature bytes to the recovered address, mirroring `TransactionCapsule.checkWeight`'s approach: track a set of addresses that have already contributed weight, and skip (or reject) any subsequent signature — regardless of its byte encoding — that recovers to an address already counted. Concretely, check `ByteArray.matrixContains(executedAddrList, recoveredAddr)` and `continue` before adding weight, and only add `recoveredAddr` (not the raw `sign`) to the executed list.

### Proof of Concept
1. Deploy/reference an account with an `Active` `Permission` containing key `K` with weight `W ≥ threshold`.
2. Obtain one valid signature `(r, s, v)` from `K` over the precompile's expected hash (`sha256(address || permissionId || data)`).
3. Compute a second, byte-different but still valid signature for the same address: `(r, n - s mod n, 1 - v)` where `n` is the secp256k1 curve order — this recovers to the same address as step 2 without needing the private key.
4. Call the `validateMultiSign` precompile (via a `TriggerSmartContract` transaction) with `signatures = [sig1, sig2]` for permission threshold `> W` (i.e., normally requiring at least 2 independent signers).
5. `ValidateMultiSign.execute` computes `recoveredAddr` for both entries as the same address; the first pass adds `W`; on the second pass `executedSignList` contains the address but not the exact byte-identical `sign`, so the `continue` is skipped and `W` is added a second time, producing `totalWeight = 2W ≥ threshold` and returning `DATA_TRUE` even though only one real signer participated.
