## Finding [1](#0-0) 

Looking at `truncate_ledger_db_single_batch`, the write order is:

1. Build an in-memory `LedgerDbSchemaBatches` containing the deletions for transaction index data, per-epoch data, per-version data (`TransactionAccumulatorRootHashSchema`, `TransactionInfoSchema`, `VersionDataSchema`, `WriteSetSchema`), event data, and the accumulator-truncation batch. [2](#0-1) 
2. **Before any of that batch is committed**, a separate `progress_batch` is written directly to `ledger_db.metadata_db()`, setting `DbMetadataKey::LedgerCommitProgress = start_version - 1` (i.e. `target_version`). [3](#0-2) 
3. Only afterward is the actual destructive batch committed via `ledger_db.write_schemas(batch)`, which internally writes to seven distinct physical RocksDB instances sequentially (write_set, transaction_info, transaction, persisted_auxiliary_info, event, transaction_accumulator, then ledger_metadata) with no cross-DB atomicity. [4](#0-3) 

This is the inverse of a crash-safe ordering. If the process crashes after step 2 completes but before step 3 finishes, `LedgerCommitProgress` on disk already reads `target_version`, while `TransactionAccumulatorRootHashSchema`, `TransactionInfoSchema`, the accumulator's internal merkle frontier, event data, transaction data, and write-set data are still left at their pre-truncation state (versions above `target_version`). Any restart logic that trusts `LedgerCommitProgress` as the authoritative "already truncated to here" marker (as is the pattern elsewhere in this file, e.g. the comment at `storage/aptosdb/src/utils/truncation_helper.rs:215-216` for `truncate_state_kv_db`) will skip re-running the truncation, permanently leaving the accumulator frontier, transaction-info table, and event/write-set data out of sync with the version recorded in `LedgerCommitProgress` and with `LedgerInfoSchema`.

I want to flag two things I could **not** fully verify given tool-call limits:
- The body of `truncate_transaction_accumulator` itself rendered as blank lines in the file view (lines 363-440), so I could not inspect exactly which schema keys/positions it deletes or in what internal order.
- I could not trace the DB-open/recovery code path that consumes `LedgerCommitProgress` to confirm it unconditionally trusts this value without an additional consistency check against the actual max version present in each sub-DB.

Given the index limitations here, if you need certainty on the recovery-time consistency check, a Devin session with full filesystem access would be needed to inspect `AptosDB::open`/`LedgerDb` recovery logic and to reproduce the crash-injection scenario end-to-end.

### Title
Progress marker (`LedgerCommitProgress`) is persisted before the destructive truncation batch, allowing a crash to leave the transaction accumulator and transaction-info tables inconsistent with the recorded ledger version - (File: `storage/aptosdb/src/utils/truncation_helper.rs`)

### Summary
`truncate_ledger_db_single_batch` writes `LedgerCommitProgress = target_version` to the ledger metadata DB *before* committing the batch that actually deletes/truncates `TransactionAccumulatorRootHashSchema`, `TransactionInfoSchema`, the accumulator's internal nodes, events, transactions, and write sets. A crash between these two writes leaves the on-disk progress marker claiming truncation to `target_version` while the accumulator/transaction-info data is still at the pre-truncation (higher) version.

### Finding Description [5](#0-4) 
The function assembles all deletions into `batch` (a `LedgerDbSchemaBatches`), including the accumulator truncation (`truncate_transaction_accumulator`) and the per-version deletions of `TransactionAccumulatorRootHashSchema`/`TransactionInfoSchema` via `delete_per_version_data`. It then writes a standalone `progress_batch` to the ledger metadata DB recording the new (lower) `LedgerCommitProgress`, and only afterward calls `ledger_db.write_schemas(batch)` to actually perform every deletion across the seven underlying RocksDB instances. Because these two writes are not atomic with each other (they are literally two separate `write_schemas` calls to different/overlapping physical DBs), a process crash between them commits the "truncation complete" marker without having truncated any of the real data.

### Impact Explanation
If restart/recovery logic treats `LedgerCommitProgress` as ground truth for "no more truncation needed" (the pattern used elsewhere in this same file), it will skip re-running `truncate_ledger_db_single_batch`. The transaction accumulator, `TransactionInfoSchema`, event, transaction, and write-set data then remain at a version above the one recorded in `LedgerCommitProgress` and above the retained `LedgerInfoSchema`/state data, breaking the invariant that the accumulator frontier, transaction-info table, and progress marker must agree. This can make transaction/event/state proofs served by the node bind to the wrong version or fail to match the certified `LedgerInfoSchema` root, since the proof-construction code paths read directly from `TransactionAccumulatorRootHashSchema`/`TransactionInfoSchema` rather than from `LedgerCommitProgress`.

### Likelihood Explanation
Triggering this requires only an ordinary process crash/restart (e.g., OOM-kill, power loss, `SIGKILL`) occurring during a routine ledger-DB truncation, which happens on every node restart after an unclean shutdown or during storage pruning/restore paths that call `truncate_ledger_db`. It does not require attacker-controlled input beyond normal chain activity generating transactions to be truncated; a crash at the right instant is operational/timing-dependent rather than trivially attacker-triggerable, but the code path is exercised on every affected node's restart.

### Recommendation
Reorder the writes so the destructive batch (`truncate_transaction_accumulator`, `delete_per_version_data`, `delete_per_epoch_data`, `delete_event_data`, `delete_transaction_index_data`) is committed **before** `LedgerCommitProgress` is updated, and ideally include the progress write inside the same `LedgerDbSchemaBatches`/`ledger_metadata_db_batches` so it is the last physical write performed by `LedgerDb::write_schemas`, matching the safe pattern already documented for `truncate_state_kv_db`.

### Proof of Concept
1. Commit a range of versions so accumulator/transaction-info data exists beyond `target_version`.
2. Invoke `truncate_ledger_db(ledger_db, target_version)`, injecting a crash immediately after `ledger_db.metadata_db().write_schemas(progress_batch)` returns but before `ledger_db.write_schemas(batch)` completes.
3. Restart the node/db handle and observe `get_progress(..., DbMetadataKey::LedgerCommitProgress) == target_version` while `TransactionInfoSchema`/`TransactionAccumulatorRootHashSchema` still contain entries above `target_version`.
4. Call `get_transaction_proof` for a version above `target_version` (that should have been pruned) or for `target_version` itself, and compare the reconstructed root against `LedgerInfoSchema` to demonstrate the mismatch.

```rust
fn truncate_ledger_db_single_batch(
    ledger_db: &LedgerDb,
    transaction_store: &TransactionStore,
    start_version: Version,
) -> Result<()> {
    let mut batch = LedgerDbSchemaBatches::new();

    delete_transaction_index_data(
        ledger_db,
        transaction_store,
        start_version,
        &mut batch.transaction_db_batches,
    )?;
    delete_per_epoch_data(
        &ledger_db.metadata_db_arc(),
        start_version,
        &mut batch.ledger_metadata_db_batches,
    )?;
    delete_per_version_data(ledger_db, start_version, &mut batch)?;

    delete_event_data(ledger_db, start_version, &mut batch.event_db_batches)?;

    truncate_transaction_accumulator(
        ledger_db.transaction_accumulator_db_raw(),
        start_version,
        &mut batch.transaction_accumulator_db_batches,
    )?;

    let mut progress_batch = SchemaBatch::new();
    progress_batch.put::<DbMetadataSchema>(
        &DbMetadataKey::LedgerCommitProgress,
        &DbMetadataValue::Version(start_version - 1),
    )?;
    ledger_db.metadata_db().write_schemas(progress_batch)?;

    ledger_db.write_schemas(batch)
}
```
