## Analysis

The reported CVE describes Grist's pyodide sandbox lacking a genuine process-isolation barrier, so a malicious document can run arbitrary processes on the host. The closest analog in this sequencer codebase is the Sierra→CASM/Native compilation subprocess used to compile **user-submitted, untrusted Sierra bytecode** during `DECLARE` transaction ingestion — protected only by POSIX `rlimit` values, not a real sandbox.

### Title
Untrusted Sierra compiler subprocess is isolated only by rlimits, not a real sandbox - ([File: crates/apollo_compilation_utils/src/resource_limits/resource_limits_unix.rs])

### Summary
Any unprivileged account can submit a `DECLARE` transaction carrying an attacker-controlled Sierra program. The gateway/class-manager pipeline compiles this untrusted class by spawning the external `cairo-lang`/`cairo-native` compiler binary as a child process, with the only isolation being CPU time, address-space size, and file-size `rlimit`s applied via `pre_exec`. There is no seccomp filtering, filesystem confinement, network namespace, capability drop, or process-count limit around this subprocess.

### Finding Description
`SierraCompiler::compile` (invoked by the `ClassManager::add_class` path shown in `crates/apollo_class_manager/src/class_manager.rs:71-113` and reachable directly from `GenericGateway::add_tx_inner` in `crates/apollo_gateway/src/gateway.rs:228-255` for every `DECLARE` transaction) calls `SierraToCasmCompiler::compile` / `SierraToNativeCompiler::compile`, both of which delegate to `compile_with_args` in `crates/apollo_compilation_utils/src/compiler_utils.rs:17-50`. That function spawns the compiler binary via `std::process::Command`, applying only `ResourceLimits` (`crates/apollo_compilation_utils/src/resource_limits/resource_limits_unix.rs:41-115`), which sets `Resource::CPU`, `Resource::FSIZE`, and `Resource::AS` via `setrlimit` in a `pre_exec` hook. No `seccomp`, `unshare`/namespaces, `chroot`/filesystem jail, capability dropping, or process/fork limits (`RLIMIT_NPROC`) are applied. The child process inherits the parent's environment and network access by default.

The compiler binaries process fully attacker-controlled input (arbitrary Sierra bytecode/libfuncs, `--allowed-libfuncs-list-name` notwithstanding — the Cairo-Native path in particular drives an LLVM/MLIR-based AOT toolchain, a large and complex native-code attack surface). This is directly analogous to the pyodide report: a "sandbox" boundary that only limits *resource consumption*, not *what the process is allowed to do* (filesystem access, network egress, process creation), such that any memory-safety or logic bug in the compiler toolchain reachable from crafted Sierra input becomes host-level code execution rather than a contained failure.

### Impact Explanation
If the compiler (particularly the LLVM/MLIR-backed Cairo-Native AOT compiler) can be driven to execute attacker-supplied logic through a compiler bug via a maliciously crafted Sierra program, the resulting process is unconstrained beyond CPU/memory/file-size caps: it can read local files (secrets, keys, other sequencer configuration) up to the file-size limit, open outbound network connections (SSRF to internal infrastructure), or exhaust process table (no `NPROC` cap) affecting node availability — all triggerable by a single, unprivileged `DECLARE` transaction. This weakens node integrity and availability guarantees for that sequencer instance.

### Likelihood Explanation
Reaching this code path requires nothing more than submitting a well-formed `DECLARE` transaction (`crates/apollo_gateway/src/gateway.rs:228` onward) — no special privileges, staking, or operator/proposer status are needed; `check_declare_permissions` only gates an optional allow-list, and by default declares are unrestricted. Exploitation still depends on the existence of an actual memory-safety/logic bug in the compiler binaries reachable from crafted Sierra/libfunc input, which is plausible given the size and complexity of the Cairo-Native/LLVM toolchain, but has not been independently proven here.

### Recommendation
Harden the compiler subprocess beyond rlimits: run it under a real sandbox (seccomp-bpf syscall allowlist, mount/network namespaces or a minimal chroot, dropped capabilities, `RLIMIT_NPROC`), and strip the inherited environment before `exec`. This mirrors the Grist fix (moving from a barrier-less runtime to one enforced via Deno/gVisor).

### Proof of Concept
Not applicable as a working exploit — the report is a structural/config gap (missing sandbox controls around `crates/apollo_compilation_utils/src/compiler_utils.rs:33-40` and `resource_limits_unix.rs:89-114`) rather than a demonstrated code-execution bug in the compiler binary itself. ```rust
    /// Apply the resource limits to a given command object. This moves the [`ResourceLimits`]
    /// struct into a closure that is held by the given command. The closure is executed in the
    /// child process spawned by the command, right before it invokes the `exec` system call.
    pub fn apply(self, command: &mut Command) -> &mut Command {
        if self.cpu_time.is_none() && self.file_size.is_none() && self.memory_size.is_none() {
            return command;
        }
        unsafe {
            // The `pre_exec` method runs a given closure after the parent process has been forked
            // but before the child process calls `exec`.
            //
            // This closure runs in the child process after a `fork`, which primarily means that any
            // modifications made to memory on behalf of this closure will **not** be visible to the
            // parent process. This environment is often very constrained. Normal operations--such
            // as using `malloc`, accessing environment variables through [`std::env`] or acquiring
            // a mutex--are not guaranteed to work, because after `fork`, only one thread exists in
            // the child process, while there may be multiple threads in the parent process.
            //
            // This closure is considered safe for the following reasons:
            // 1. The [`ResourceLimits`] struct is fully constructed and moved into the closure.
            // 2. No heap allocations occur in the `set` method.
            // 3. `setrlimit` is an async-signal-safe system call, which means it is safe to invoke
            //   after `fork`. This is established in the POSIX `fork` specification:
            //   > ... the child process may only execute async-signal-safe operations until such
            //    time as one of the `exec` functions is called.
            //   (See <https://pubs.opengroup.org/onlinepubs/9699919799/functions/fork.html>)
            command.pre_exec(move || self.set())
        }
    }
