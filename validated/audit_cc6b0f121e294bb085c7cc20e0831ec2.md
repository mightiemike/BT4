### Title
Silent per-account clamping in `AccountStorageEntry::get_obsolete_bytes` can under-report obsolete bytes, causing snapshot/replay content divergence - (File: accounts-db/src/account_storage_entry.rs)

### Summary
`AccountStorageEntry::get_obsolete_bytes()` computes the number of bytes to exclude from a storage when generating snapshots, by summing each obsolete account's stored size, but *clamps* each individual value with `.min(self.accounts.len() - offset)` instead of asserting/erroring on an inconsistency. This mirrors the Ajna `RewardsManager` pattern flagged in the external report: an amount owed/expected is silently capped to "whatever is available" and the shortfall is never tracked or surfaced, so downstream consumers permanently and silently see less than the correct amount.

### Finding Description
`get_obsolete_bytes` is the sole source of the "bytes to skip" total that both `AccountStorageReader::new` and the snapshot writer (`runtime/src/serde_snapshot/storage.rs`) rely on to compute `num_alive_bytes` for a storage being serialized into a snapshot: [1](#0-0) 

```
pub fn get_obsolete_bytes(&self, slot: Option<Slot>) -> usize {
    let obsolete_bytes: usize = self
        .obsolete_accounts_read_lock()
        .filter_obsolete_accounts(slot)
        .map(|(offset, data_len)| {
            self.accounts
                .calculate_stored_size(data_len)
                .min(self.accounts.len() - offset)
        })
        .sum();
    obsolete_bytes
}
```

and it feeds directly into: [2](#0-1) 

`num_alive_bytes = num_total_bytes - storage.get_obsolete_bytes(snapshot_slot)`.

Instead of failing loudly if a computed per-account stored size would overrun the file (which should never happen for a correctly-tracked obsolete entry, since `data_len` for a genuinely obsolete account is bounded by the file it was actually written into), the code silently clamps that one entry's contribution to `self.accounts.len() - offset`. This is structurally identical to the Ajna bug: a per-item amount is capped to "what's available" with no error, no logging, and — critically — **no compensating adjustment elsewhere**. Just like Ajna's `_claimRewards` capping the transferred lamports to the contract's balance while still emitting `ClaimRewards` for the full amount (leaving the shortfall permanently unaccounted for and unclaimable), here the true per-account "excluded size" silently becomes smaller than the account's actual on-disk footprint whenever the clamp fires, and the difference is dropped from the sum with no way to recover or detect it later.

The `min()` clamp can only actually change the result when `data_len` (and thus `calculate_stored_size(data_len)`) is inconsistent with the actual bytes available at `offset` in the *current* state of `self.accounts` — e.g., an obsolete-account record whose `data_len` was captured before the storage was later mutated/reused, or a race between marking an account obsolete and the storage being shrunk/rewritten. In that situation, the "true" number of bytes that should be excluded from the snapshot at that offset is ambiguous, and the code silently picks the smaller of the two rather than treating it as the invariant violation it is.

### Impact Explanation
If `get_obsolete_bytes` under-counts the true obsolete-byte total for one or more entries, `num_alive_bytes` in `AccountStorageReader` becomes *larger* than the amount of genuinely alive/valid data in the file. Since `AccountStorageReader::read` walks the file skipping only the `sorted_excluded_accounts` ranges (each also derived from the same clamped/underestimated sizes) and reports `len() == num_alive_bytes`, an over-counted `num_alive_bytes` can cause the reader to include a truncated/partial account record — or padding/garbage bytes belonging to a different account — in the serialized snapshot stream. This is exactly the "silent capitalization/hash divergence" class called out in the validation rubric: the snapshot writer and the live in-memory/replayed state can disagree about which bytes constitute valid account data, without any panic, error return, or stats counter firing to reveal the discrepancy. A node whose snapshot generation silently mis-sizes a storage entry produces a corrupted archive that other validators bootstrapping from that snapshot would load with wrong account data or a hash mismatch versus the node that produced it, and/or a self-consistency failure between the node's own snapshot and its subsequent replay.

### Likelihood Explanation
This is a defensive/edge-case code path — the clamp is designed to never fire under intended invariants (obsolete entries should always describe bytes fully contained within `self.accounts.len()`), and there is no accompanying test that exercises the clamp itself (only tests where offsets/lengths are already consistent, e.g. `accounts-db/src/account_storage_reader.rs` truncated-storage-simulation tests). Because the condition is silently absorbed rather than asserted, any future refactor of shrink/flush/obsolete-marking ordering that introduces a stale `data_len`/`offset` pair relative to the storage's current length would not be caught by CI or by a runtime panic — it would simply produce a slightly-wrong snapshot. This matches the Ajna report's core criticism: a previously-reported "silent short-fall" pattern that looks fixed (there is a safety `.min()` clamp) but is not actually reverted-on/tracked, so the bug class remains latent and undetectable until a snapshot/replay divergence is observed in production.

### Recommendation
Replace the silent `.min(...)` clamp in `get_obsolete_bytes` with an assertion (or a hard error) that `calculate_stored_size(data_len) <= self.accounts.len() - offset` for every obsolete entry, matching the pattern already used elsewhere in this file for `Stored size (...) is larger than the size of the accounts file` sanity checks (see the similar assertion in `accounts_db.rs` at the index-generation `stored_size` check). If an inconsistent obsolete-account record is ever observed, it should trip that assertion (or increment a dedicated stats counter and refuse to include that storage in the snapshot) rather than silently reporting a smaller total than reality. Additionally, add a unit test that deliberately marks an account obsolete with a `data_len` that would overrun `self.accounts.len() - offset`, and assert that this is now caught rather than silently clamped.

### Proof of Concept
1. Create an `AccountStorageEntry` with a small AppendVec file.
2. Call `storage.obsolete_accounts.write().unwrap().mark_accounts_obsolete([(offset, data_len)], slot)` with a `data_len` chosen so that `AppendVec::calculate_stored_size(data_len) > storage.accounts.len() - offset` (e.g., by marking obsolete an account whose recorded `data_len` predates a subsequent truncation/reuse of the storage, or by directly constructing the scenario in a unit test as described above).
3. Call `storage.get_obsolete_bytes(None)` and observe it silently returns the clamped (smaller) value instead of panicking or returning an error.
4. Construct an `AccountStorageReader::new(&storage, None, TombstonesFilter::Include, &mut reader)` and observe `reader.len()` (`num_alive_bytes`) is larger than the storage's genuinely valid byte range, demonstrating that a snapshot generated from this reader would include more bytes than are legitimately alive, with no diagnostic emitted anywhere in the process.
