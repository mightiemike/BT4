### Title
Webhook HMAC signs only the request body, letting an attacker forge the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers and trigger handlers against a victim shop's session - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
Shopify webhook authentication in `shopify-api` computes the HMAC only over `rawBody` and never binds the signature to the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers. Those unsigned headers are, however, exactly what downstream handlers (`shopify-app-remix`/`shopify-app-react-router` `authenticateWebhookFactory`, and `shopify-api`'s `process()`) trust to select the shop's offline session and which registered handler to invoke. This is the same root-cause pattern as SAML "signature wrapping": the cryptographic signature validates one part of the message (the body) while the application's authorization decision is driven by a different, unsigned part of the same message (the headers).

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` first calls `validateHmacFromRequestFactory`, which only hashes `rawBody`: [1](#0-0) 
After the HMAC on the body passes, `checkWebhookHeaders` simply reads `topic`, `domain`, `webhookId`, `apiVersion` straight from the (unsigned) HTTP headers and returns them as trusted fields: [2](#0-1) 

Those trusted-but-unsigned fields are then used directly for authorization-sensitive decisions:
- `authenticateWebhookFactory` uses `check.domain` to load/derive the *victim's* offline session and attach an authenticated Admin API client to the webhook context: [3](#0-2) 
- `process()` in `shopify-api` dispatches to app-registered handlers keyed purely by `webhookCheck.topic`, and calls the handler with `webhookCheck.domain` and the raw body: [4](#0-3) 

Because the webhook secret (`config.apiSecretKey`) is the app's single client secret shared across every shop that installs the app, any low-privilege actor can install the app on their own (e.g. free development) store and obtain a legitimately signed `(rawBody, hmac)` pair for any topic supported by the app (many webhook bodies contain attacker-influenced content, e.g. product/order fields). Since the HMAC never covers `domain` or `topic`, that same valid `(rawBody, hmac)` pair can be replayed with the `X-Shopify-Shop-Domain` header changed to a different, victim shop that has previously installed the app, and/or with `X-Shopify-Topic` changed to a different topic the attacker's body was never intended for. The webhook HMAC check still succeeds (it only checks the body), and the framework proceeds to run the shop's session/handler logic scoped to the *forged* domain and topic supplied by the attacker.

### Impact Explanation
This enables cross-tenant abuse of any app built on `shopify-app-remix`/`shopify-app-react-router`/`shopify-app-express`: an attacker who is merely a merchant/customer able to install the target app can forge webhook deliveries "from" any other shop that has the app installed, causing the app to execute topic handler logic bound to the victim's offline session/admin API client using attacker-chosen (but validly-HMAC'd) body content. Depending on the app's handler implementations (e.g. `app/uninstalled`, `customers/data_request`, `orders/*`, inventory or fulfillment webhooks), this can lead to unauthorized state changes, data exfiltration/deletion, or GDPR-handler abuse performed on behalf of a shop the attacker does not control — a concrete cross-tenant/forged-Shopify-request scenario matching the "accepted forged Shopify request" and "cross-tenant access" impact classes.

### Likelihood Explanation
Reachable from a single, unprivileged merchant/customer account (no leaked secrets, no MITM required): the attacker only needs to install the target app on their own store (or use a topic body they otherwise control) to obtain a valid `(rawBody, hmac)` pair, then POST it to the app's `/webhooks` endpoint with modified `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers. Successful exploitation additionally requires that the victim shop has an existing offline session in the app's session storage (i.e., previously installed the app), which is a realistic precondition for any multi-tenant Shopify app.

### Recommendation
- Do not trust `domain`/`topic`/`webhookId` headers as fully authenticated; bind them cryptographically to the signed payload, e.g. by including a canonical representation of `domain`+`topic`+`webhookId` in the HMAC input (where feasible per Shopify's webhook contract), or by validating that the JSON body's own shop/resource identifiers are consistent with the `domain` header before dispatching to handlers.
- Where the body cannot be extended, add a secondary integrity check: correlate `webhookId` against previously seen IDs per shop (replay/idempotency store) and reject any webhook whose `domain` was not the domain that most recently completed OAuth for that specific request's originating IP/registration record.
- Document and enforce, at the framework level, that webhook handler authors must not assume `domain`/`topic` supplied to the callback are inherently more trustworthy than the body — or better, make `process()`/`authenticateWebhookFactory` optionally verify against the shop's registered webhook subscription list (Shopify's Admin API) before dispatch.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers an event whose topic the app has registered a handler for (e.g. `orders/create`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` value from the delivered webhook.
2. Attacker (or any other single actor) confirms a victim shop `victim.myshopify.com` has the same app installed (has an offline session in the app's session storage — normal precondition for any multi-tenant app).
3. Attacker resends the exact same body and HMAC value to the app's `/webhooks` endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled` (or another topic within the same signed body's tolerance / or same topic if only domain needs forging)
4. `validateHmacFromRequestFactory` succeeds because it only re-computes the HMAC over the untouched `rawBody`: [5](#0-4) 
5. `checkWebhookHeaders` returns `domain: 'victim.myshopify.com'` and the attacker-chosen `topic` as "valid" fields: [6](#0-5) 
6. `authenticateWebhookFactory` loads the victim's offline session via `ensureValidOfflineSession(params, check.domain)` and hands the resulting `admin` client and forged `payload`/`topic` to the app's webhook handler, executing business logic against the victim's store: [7](#0-6) 

Note: I was not able to execute this against a live app instance in this environment; the analysis is based on static code review of the validation/dispatch pipeline. If further confirmation is desired (e.g., an end-to-end test harness reproducing cross-tenant handler invocation), a Devin session with runtime/test execution access would be needed.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
