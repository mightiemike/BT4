### Title
`ensure_match_transaction_info` omits checkpoint-hash validation, allowing replay-verify tooling to accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  is the sole correctness gate used by `db-tool`'s `replay-on-archive` and `ChunkExecutorInner::verify_execution` to compare locally re-executed VM output against the `TransactionInfo` recorded/authenticated in an archived/backup ledger. It validates status, gas, write-set hash, and event-root hash, but by its own documented admission it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
The function's own trailing comment states the gap explicitly: [2](#0-1) 

This is not a hypothetical: the function is called from real correctness-verification paths, not just tests:
- `db-tool`'s `replay_on_archive::Verifier::execute_and_verify` calls it to compare freshly executed transaction outputs against `expected_txn_infos` pulled from the archived database [3](#0-2) .
- `ChunkExecutorInner::verify_execution` (used by `TransactionReplayer`/backup restore verification) calls it the same way when `VerifyExecutionMode::should_verify()` is set [4](#0-3) .

Meanwhile, the state-checkpoint/position-state-checkpoint hash is a real, consensus-committed field of `TransactionInfoV1` — it is assembled into the accumulator leaf and hashed into the ledger's root in `DoLedgerUpdate::assemble_transaction_infos` [5](#0-4) , and its purpose is explicitly to make the native-trading position-state root "consensus-verified" once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (feature 122) is enabled, per the feature-flag documentation [6](#0-5) .

Because `ensure_match_transaction_info` skips these three hash fields, an archived/backup `TransactionInfo` whose `position_state_checkpoint_hash` (or `state_checkpoint_hash`/`hot_state_checkpoint_hash`) has been corrupted, tampered with, or diverges from what local re-execution actually produces will still pass `replay-verify` / `replay-on-archive` / restore-verification as a "successful match", even though the two other integrity checks that do exist elsewhere (`ChunkResultVerifier::verify_chunk_result`'s `ensure_transaction_infos_match`, which hashes the whole `TransactionInfo` against the accumulator) only detect divergence when compared against the accumulator/ledger-info signature chain — not when the tool's job is specifically to catch VM/local-execution divergence against an already-archived DB with a self-consistent (but wrong) `TransactionInfo`.

### Impact Explanation
This is a real gap in an audit/self-verification safety net (state-checkpoint and position-state-checkpoint integrity), but its live blast radius on mainnet today is limited by the fact that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `TRADING_NATIVE` are new, gated on-chain features whose default-enabled status on mainnet I could not confirm from the index. If disabled, `position_state_checkpoint_hash` is `None` for all transactions and this gap is inert. If/when the feature is enabled, an operator relying on `replay-verify`/`replay-on-archive` to detect ledger corruption for the native-trading subsystem would get a false "verified" result for a corrupted/incorrect position-state root, defeating the intended detection mechanism for hard-fork-only or storage-corruption divergence in that subsystem.

### Likelihood Explanation
Low-to-moderate today (feature likely not yet default-on), but the comment shows the Aptos team is aware and has explicitly gated further rollout of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on fixing this. I was not able to fully confirm the on-chain default/rollout status of `TRADING_NATIVE`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` in mainnet governance state within the scope of this session — that would require checking on-chain feature-flag configuration, which is outside what the code index can show.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between locally computed output and the trusted `TransactionInfo`, as the existing TODO already specifies, before (or as a prerequisite gate for) enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not independently reproducible as a mainnet exploit from static analysis alone, since it requires `COMPUTE_TRADING_NATIVE_STATE_ROOTS` to be active and a corrupted archived `TransactionInfo.position_state_checkpoint_hash`/`state_checkpoint_hash` to be fed into `replay_on_archive::Verifier::execute_and_verify` or `ChunkExecutorInner::verify_execution`; both call sites are cited above and the missing comparisons are directly visible in `ensure_match_transaction_info`.

**Caveat:** This finding is a self-documented gap (the code itself contains the TODO explaining the exact issue), and I was unable to determine the current on-chain/default activation status of `TRADING_NATIVE`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which materially affects real-world severity today.
