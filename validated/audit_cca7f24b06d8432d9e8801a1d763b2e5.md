### Title
L1 handler fee-paid check never validates the actual fee against required cost, and the consensus-received value is hardcoded — ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

### Summary
Analogous to the reported bug (bribe distribution amounts blindly accepted without validation against actual deposited bribes), the sequencer's L1-handler transaction path accepts an unverified `paid_fee_on_l1` value and only checks that it is non-zero, never that it actually covers the resources consumed. Worse, for L1-handler transactions received via consensus (i.e. proposed by another node and re-executed by a validator), this value isn't even taken from the real L1 event — it is hardcoded to `Fee(1)`.

### Finding Description
`L1HandlerTransaction::execute_raw` computes the receipt/gas actually consumed by the transaction, but the only fee-related check performed is: [1](#0-0) 

i.e. it only asserts `paid_fee != Fee(0)` — "For now, assert only that any amount of fee was paid." The comment above it even says "Consider removing this check. It is covered by the starknet core contract," acknowledging that the sequencer itself performs no real validation that the reported `paid_fee_on_l1` matches (or covers) the actual L2 resources consumed.

More critically, when an L1-handler transaction reaches a node through the consensus/proposal flow (not directly from the L1 events scraper), `paid_fee_on_l1` is not derived from the real `LogMessageToL2` event fee at all — it is hardcoded: [2](#0-1) 

This is the direct analog of the reported issue: a value that is supposed to reflect an actual on-chain deposit (`paid_fee_on_l1` should reflect the fee attached to the corresponding `sendMessageToL2` L1 event, just as `distributions[i]` should reflect the actual bribe amount) is instead accepted blindly / stubbed with a constant, with no cross-check against the real L1-side amount at execution/validation time on the consensus path.

### Impact Explanation
Because the only enforced invariant is "fee != 0", and because the value used during consensus re-execution is a constant `Fee(1)` regardless of the L1 event, the sequencer provides no actual guarantee that the resources consumed by an L1-handler transaction (bounded only by `l1_handler_max_amount_bounds`, see `crates/blockifier/src/blockifier_versioned_constants.rs`) are backed by a commensurate fee paid on L1. This weakens the fee/resource-accounting guarantees for L1-triggered execution: an L1 message sender can cause execution up to the per-tx `l1_handler_max_amount_bounds` gas cap on L2 while the sequencer-side check that is supposed to correlate cost with payment is a no-op, and the consensus-reconstructed field doesn't even reflect the true L1 payment.

### Likelihood Explanation
Any L1 message sender can trigger this path deterministically simply by sending a `sendMessageToL2` call with a minimal payload/fee; the flaw is in code that executes on every L1-handler transaction, not a rare edge case. The `TODO`/comment markers in the source (`crates/apollo_transaction_converter/src/transaction_converter.rs:480`, `crates/blockifier/src/transaction/l1_handler_transaction.rs:101`) confirm this is a known, currently-shipped gap rather than a hypothetical.

### Recommendation
- Validate `paid_fee_on_l1` against the actual L1 event data end-to-end, including in the consensus/transaction-converter path, instead of hardcoding `Fee(1)`.
- Replace the "any amount of fee was paid" check with a real comparison against the resources/fee actually consumed (as tracked in `TransactionReceipt`), consistent with how account transactions are checked via `FeeCheckReport`/`PostExecutionReport` in `crates/blockifier/src/fee/fee_checks.rs`.

### Proof of Concept
Not applicable as a standalone runnable PoC — the issue is demonstrated directly by the source: `crates/blockifier/src/transaction/l1_handler_transaction.rs:103-113` only checks `paid_fee == Fee(0)`, and `crates/apollo_transaction_converter/src/transaction_converter.rs:477-482` hardcodes `Fee(1)` for consensus-derived L1 handler transactions, decoupling the validated value entirely from the real L1 fee event captured in `crates/papyrus_base_layer/src/eth_events.rs:30-35`.
