### Title
Autofill brute-force-probing rate limiter is scoped per-`RenderFrame`, allowing attackers to multiply the token budget via multiple frames - (File: components/autofill/content/renderer/autofill_agent.cc)

### Summary
The BarnBridge report describes a fee-rounding bug where truncation of a per-transaction calculation to zero lets an attacker bypass an intended protection by splitting one large operation into many small ones. The closest analog in Chromium is the token-bucket rate limiter that `AutofillAgent::ShouldThrottleAskForValuesToFill` uses to mitigate CSS/timing-based, character-by-character brute-forcing of saved autofill/password data. Like the BarnBridge fee, the limiter's unit of enforcement (a single `AutofillAgent`, i.e. a single `RenderFrame`) is smaller than the unit an attacker actually controls (a page can create many same-origin frames), so the "cost" of probing can be split across frames to defeat the mitigation, in the same spirit as splitting a trade into many sub-threshold purchases to avoid fee rounding.

### Finding Description
`ShouldThrottleAskForValuesToFill` implements a token-bucket limiter intended to stop a malicious page from rapidly cycling input values and observing `:autofill` state changes to exfiltrate saved autofill/password data character by character: [1](#0-0) 

The state (`ask_for_values_to_fill_throttle_`, `last_ask_for_values_to_fill_`) is a member of `AutofillAgent`, and the comment explicitly documents the design as a **per-frame** throttle: [2](#0-1) 

Because `AutofillAgent` is instantiated once per `RenderFrame`, the burst budget (`kAutofillThrottleBruteForceProbingMaxTokens`, default 15) and refill rate (`kAutofillThrottleBruteForceProbingReplenishRate`, default one token/750 ms) are tracked independently for each frame: [3](#0-2) 

This mirrors the BarnBridge root cause: the security-relevant accounting (fee accrual there, probe-rate accrual here) is correctly computed for a single unit of work, but the protocol/attacker can decompose the "large" operation (one big purchase / one long brute-force session) into many small units (micro-purchases / many parallel frames), each of which is accounted for independently and never crosses the threshold that would trigger the defense.

### Impact Explanation
If a same-origin attacker context can create additional `RenderFrame`s that also host an autofillable/password-field form for the same origin (e.g. several same-origin iframes, or serially navigated/replaced frames), each frame gets its own fresh 15-token burst and its own 750 ms/token refill schedule. This multiplies the effective probing throughput proportionally to the number of frames, defeating the purpose of the mitigation described in the code comment (preventing brute-force extraction of saved autofill/password values via the `:autofill` CSS side channel). The result is a meaningfully faster path to disclosing saved form-fill and credential data than the mitigation was designed to allow — a cross-origin/user-data-disclosure-relevant weakening of a security control, not merely a performance quirk.

### Likelihood Explanation
Creating many same-origin iframes/frames from a single page is trivial JavaScript, requires no special permissions, flags, or extensions, and is reachable purely from web content. The only precondition is that autofill would actually offer to fill the field in each of these frames (i.e., the frame's effective origin matches a stored credential/autofill entry) — this is the same precondition that the existing rate limiter itself was built to defend against, so any attacker positioned to exploit the underlying side channel at all is also positioned to fan the probing out across frames.

### Recommendation
Scope the throttle state to a wider, harder-to-multiply unit than "one `AutofillAgent`/`RenderFrame`" — e.g., aggregate the token bucket at the `RenderFrame`'s top-level document/`AutofillDriver` in the browser process, or key it by origin across all frames in a `WebContents`, so that spawning additional same-origin frames cannot each obtain an independent burst allowance. This is the rate-limiter analog of "rounding fee calculations in the protocol's favor": make the enforcement unit at least as coarse as the unit an attacker can cheaply replicate.

### Proof of Concept
Conceptual (cannot be executed here, but follows directly from the code):
1. Attacker-controlled page (matching the target origin, e.g. via stored-credential-eligible context) creates N same-origin `<iframe>`s, each containing a copy of the vulnerable input field.
2. In each frame, script rapidly cycles the field's value and observes the `:autofill` pseudo-class / computed style to infer whether the current prefix matches a saved value, exactly as described in the code's own threat-model comment.
3. Each frame's `AutofillAgent::ShouldThrottleAskForValuesToFill` independently permits up to `kAutofillThrottleBruteForceProbingMaxTokens` (15) burst calls before throttling, per [4](#0-3) .
4. Running the probing loop concurrently across N frames yields N× the intended maximum probe rate, since each frame's token bucket, initialized/refilled independently, never observes the other frames' consumption.

// Mitigates side-channel brute-force probing of autofill data by rate-limiting
// AskForValuesToFill() invocations per RenderFrame via a token bucket.
BASE_FEATURE(kAutofillThrottleBruteForceProbing,
             base::FEATURE_ENABLED_BY_DEFAULT);

// The burst budget of AskForValuesToFill() calls permitted per RenderFrame.
BASE_FEATURE_PARAM(int,
                   kAutofillThrottleBruteForceProbingMaxTokens,
                   &kAutofillThrottleBruteForceProbing,
                   15);

// The rate at which AskForValuesToFill() token budget replenishes.
BASE_FEATURE_PARAM(base::TimeDelta,
                   kAutofillThrottleBruteForceProbingReplenishRate,
                   &kAutofillThrottleBruteForceProbing,
                   base::Milliseconds(750));
