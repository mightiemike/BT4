### Title
Missing Slippage Protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` Allows Front-Run of Liquidity Operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` compute the counterpart token amount (`anotherTokenQuant`) from the exchange pool's *current* ratio at execution time, with no user-supplied minimum/maximum bound. Unlike `ExchangeTransactionContract`, which includes an `expected` field checked against the computed output [1](#0-0) , neither the inject nor the withdraw contract exposes any such slippage-bound field, so the ratio-dependent value is trusted and used directly without validating it against the signer's expectations.

### Finding Description
`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from `firstTokenBalance`/`secondTokenBalance` read from the exchange pool at execution time and immediately debits the account and updates the pool with that value, with no check against any user-specified minimum: [2](#0-1) 

Its `validate()` recomputes the same ratio-derived value but only asserts it is `> 0` and that account balances are sufficient — never that it satisfies a caller-supplied floor: [3](#0-2) 

Likewise, `ExchangeWithdrawActuator` computes `anotherTokenQuant` from the pool ratio at execution time and transfers it out with only a "greater than zero" / precision-loss check, again with no user-controlled minimum bound: [4](#0-3) [5](#0-4) 

The protobuf definitions confirm this asymmetry: `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `token_id`/`quant`, whereas `ExchangeTransactionContract` explicitly adds an `expected` "minimum number of tokens" field that is validated in `ExchangeTransactionActuator`: [6](#0-5) 

This mirrors the reported bug class: a ratio/price-derived value (analogous to Yield's `sellBasePreview` output) is consumed for the actual state-changing transfer without any caller-enforced bound, making the check "equivalent to setting `returned = 0`" for inject/withdraw operations.

### Impact Explanation
Because the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be moved by any other account submitting `ExchangeTransactionContract` trades against the same pair between the time a user signs and broadcasts their inject/withdraw transaction and the time it is actually included/executed, an attacker can front-run/sandwich a pending inject or withdraw to force the victim to supply or receive tokens at a manipulated, unfavorable ratio. Since there is no `expected`-style floor for inject/withdraw, the victim has no on-chain mechanism to bound their loss, unlike with `ExchangeTransactionContract`. This is a direct accounting/value-extraction impact on exchange-pool liquidity providers.

### Likelihood Explanation
The exchange (TRC10 AMM) feature is user-reachable in production and pool ratios shift with every trade on the pair. Any account (not just a privileged role) can submit competing `ExchangeTransactionContract` transactions to shift the ratio before a targeted inject/withdraw is packed into a block, making this practically exploitable whenever exchange pairs have active trading volume.

### Recommendation
Add a caller-supplied slippage-bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to `expected` in `ExchangeTransactionContract`), and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.validate()`/`ExchangeWithdrawActuator.validate()` before executing, rejecting the transaction if the computed value falls outside the caller's acceptable bound.

### Proof of Concept
1. Exchange pool `P` holds `firstTokenBalance = 100_000_000`, `secondTokenBalance = 200_000_000`.
2. Pool creator broadcasts `ExchangeInjectContract{token_id=first, quant=1_000_000}` expecting `anotherTokenQuant ≈ 2_000_000` based on the ratio seen at broadcast time (per `ExchangeInjectActuator.execute` calculation) [7](#0-6) .
3. Before this transaction is packed, an attacker submits `ExchangeTransactionContract` trades on the same pair, shifting the ratio substantially (e.g., to 1:4).
4. The creator's inject transaction executes at the new, manipulated ratio, forcing them to inject a far larger `anotherTokenQuant` than anticipated with no on-chain floor/ceiling to reject the unfavorable execution, since neither `validate()` nor `execute()` checks against any caller-specified bound [8](#0-7) .
