### Title
Contract-address delegation restriction is conditionally bypassable in `FreezeBalanceActuator` while unconditionally enforced elsewhere - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
The reported Stakehouse bug is a class of "inconsistent validation between the initial creation path and a secondary path that mutates the same restricted field" - an EOA-only check enforced at creation time but missing when the field is later changed. java-tron has the same bug-class in its resource-delegation logic: the rule "a contract address may not be the receiver of delegated resources" is enforced unconditionally in the newer delegation path (`DelegateResourceActuator`/`DelegateResourceProcessor`), but in the older `FreezeBalanceActuator` delegation path the very same check is gated behind a mutable chain parameter (`AllowTvmConstantinople`), allowing it to be skipped.

### Finding Description
`DelegateResourceActuator.validate()` unconditionally rejects delegating resources to a contract account: [1](#0-0) 

The TVM-invoked equivalent `DelegateResourceProcessor.validate()` enforces the exact same rule unconditionally as well: [2](#0-1) 

However, the older delegation entry point, `FreezeBalanceActuator.validate()`, which lets an owner freeze balance and simultaneously delegate the resulting BANDWIDTH/ENERGY to a `receiverAddress`, only rejects a contract receiver when the dynamic property `AllowTvmConstantinople` equals `1`: [3](#0-2) 

If `AllowTvmConstantinople` is `0` (its state prior to the corresponding committee-controlled hard-fork proposal being passed, e.g., on a private network or a chain that has not yet enabled this proposal), the `receiverCapsule.getType() == AccountType.Contract` check is entirely skipped, so `FreezeBalanceActuator` will happily delegate BANDWIDTH/ENERGY to a smart-contract address - something the parallel, more modern `DelegateResourceActuator`/`DelegateResourceProcessor` code paths always disallow. `AllowTvmConstantinople` is a normal, mutable dynamic-store value driven by a committee proposal (see `ProposalUtil.java`/`DynamicPropertiesStore.java`), not a value that is guaranteed to already be `1` on every chain instance running this code, so the bypass window is a real, reachable configuration state, not merely historical.

### Impact Explanation
Delegating BANDWIDTH/ENERGY to a contract account breaks an invariant that the rest of the codebase (the DelegateResourceContract/TVM native `delegateResource` opcode path) treats as a hard rule ("Do not allow delegate resources to contract addresses"). Contract accounts are not supposed to hold acquired delegated resources; permitting this via the old freeze path can cause resource/energy accounting inconsistencies for that contract account (e.g., unexpected acquired delegated balances feeding into bandwidth/energy limit calculations), and creates divergent behavior between the two delegation mechanisms that are supposed to enforce identical account-type restrictions.

### Likelihood Explanation
The bypass requires only that `AllowTvmConstantinople` be `0` on the node/network processing the transaction, which is the default/pre-hardfork chain-parameter value and is a legitimate, reachable state for any private or newly bootstrapped network (or any deployment where this proposal has intentionally not been passed). Any unprivileged account holder can trigger this by simply broadcasting a `FreezeBalanceContract` transaction with a `receiverAddress` set to a contract account - no special privileges are required.

### Recommendation
Remove the `dynamicStore.getAllowTvmConstantinople() == 1 &&` gate in `FreezeBalanceActuator.validate()` so the "no delegation to contract addresses" check is enforced unconditionally, consistent with `DelegateResourceActuator` and `DelegateResourceProcessor`:
```java
if (receiverCapsule.getType() == AccountType.Contract) {
  throw new ContractValidateException(
      "Do not allow delegate resources to contract addresses");
}
```
The `AccountType.Contract`/receiver-existence check should not depend on an unrelated hard-fork toggle.

### Proof of Concept
1. Deploy/operate a java-tron node/network where the dynamic property `AllowTvmConstantinople` is `0` (default/pre-proposal state).
2. Create/own a contract account (`AccountType.Contract`) as `receiverAddress`.
3. Broadcast a `FreezeBalanceContract` transaction from any unprivileged owner account with `receiver_address` set to that contract account and `resource = BANDWIDTH` or `ENERGY`.
4. `FreezeBalanceActuator.validate()` at [4](#0-3)  skips the contract-address rejection because `getAllowTvmConstantinople() != 1`, and `execute()` proceeds to delegate resources to the contract address - despite `DelegateResourceActuator`/`DelegateResourceProcessor` unconditionally rejecting the identical operation.
