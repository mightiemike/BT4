### Title
Session tokens (JWT bearer tokens) are logged in plaintext at debug level during authentication - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts])

### Summary

### Finding Description
When authenticating an admin request, `getSessionTokenContext` extracts the raw JWT session token from the `Authorization` header or URL parameter and immediately logs it in full via `logger.debug`, before any validation takes place: [1](#0-0) 

Later in the same flow, once the token is decoded, the full decoded `payload` (which includes the token's subject, destination shop, expiry, and other JWT claims) is logged again: [2](#0-1) 

The same pattern is duplicated in `validateSessionToken`, which stringifies and logs the entire decoded JWT payload: [3](#0-2) 

Identical code exists in the parallel `shopify-app-react-router` package: [4](#0-3) [5](#0-4) 

This is a direct analog to the reported bug class: request/session data (here, the actual bearer session token string and its decoded contents) is written to logs without redaction. The token is attacker/merchant-supplied on every single request that hits `authenticate.admin`/`authenticate.public.*`, so this code path is reachable from any authenticated storefront/App Bridge request and is exercised on every request, not just error paths.

### Impact Explanation
The session token is a bearer credential — anyone possessing it can impersonate the merchant/user for the lifetime of the token (JWTs used here are short-lived, but the decoded `payload` also includes `dest` (shop) and `sub` (user) which combined with `sessionId` derivation logic (`getJwtSessionId`/`getOfflineId`) can be used to target session storage lookups). If application logs are aggregated to a third-party log service, stored insecurely, or accessible to support/ops staff, this exposes live bearer tokens and enables session hijacking without needing to compromise any other system. This matches the report's "excessive logging of sensitive data" bug class, mapped here onto session-token verification logic explicitly called out as in-scope.

### Likelihood Explanation
This code executes on every embedded-admin request that goes through `authenticate.admin` (or the extension/public authenticate helpers that call `validateSessionToken`), as long as the logger level is set to `Debug`. Since `logger.debug` is a documented/supported log level for these packages (not a temporary debug print), and the library's own docs encourage enabling `LogSeverity.Debug` for troubleshooting, this is a realistic production/staging configuration reachable by an anonymous request bearing a forged or intercepted session token, requiring no special privilege.

### Recommendation
Do not log the raw session token string or the fully decoded JWT payload. Log only non-sensitive identifiers already used elsewhere in the same functions (e.g. `shop`, `isOnline`), and drop the `sessionToken`/`payload` fields from the `logger.debug` calls in `getSessionTokenContext` (both `shopify-app-remix` and `shopify-app-react-router`) and in `validateSessionToken`. If claim-level debugging is needed, redact all fields except non-identifying ones (e.g., `exp`, `iat`) rather than serializing the entire payload/token.

### Proof of Concept
1. Configure the app with `logger: {level: LogSeverity.Debug}` (a supported, documented configuration).
2. Send any authenticated admin request with `Authorization: Bearer <session-token>`.
3. Observe the logs emit:
   - `Attempting to authenticate session token | {shop: ..., sessionToken: {"header":"<raw JWT>","search":null}}`
   - `Session token is valid - authenticated | {shop: ..., payload: {...full decoded JWT...}}`
   - `Session token is valid - validated | {shop: ..., payload: "<full decoded JWT JSON>"}`

These log lines expose the bearer token and its full claims to any consumer of the application logs.
