## Finding

### Title
ETH-implicit accounts are created pointing at an `AccountContract::Global` wallet contract without verifying it is deployed, permanently freezing transferred funds - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_implicit_account_creation_transfer` unconditionally assigns `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` to any newly created ETH-implicit account, without checking that this global contract actually exists in the trie. On a network where the wallet global contract has not yet been deployed (e.g., a freshly launched chain), any deposit sent to an ETH-implicit account permanently freezes those funds, because such accounts cannot be deleted or have a full-access key added, and can only be interacted with through the (missing) wallet contract's methods.

### Finding Description
When a `Transfer` action targets an account ID that classifies as `AccountType::EthImplicitAccount`, `action_implicit_account_creation_transfer` creates the account with: [1](#0-0) 

This sets `AccountContract::Global(global_contract_hash)` for every new ETH-implicit account, using a hash computed purely as a function of `chain_id`: [2](#0-1) 

For any chain that is not `MAINNET`/`TESTNET`/`MOCKNET` (i.e., any new custom or freshly-launched network), this hash is computed from the embedded `LOCALNET` code, but nothing guarantees that a `DeployGlobalContractAction` for that exact code has ever been submitted on that specific network — global contract deployment is a separate, explicit, permissionless action (`action_deploy_global_contract`) that must occur before any account can reference it: [3](#0-2) 

Critically, unlike `UseGlobalContractAction` and `DeterministicStateInitAction`, which explicitly verify the referenced global contract exists in the trie before proceeding (and fail cleanly with `GlobalContractDoesNotExist` if not): [4](#0-3) [5](#0-4) 

the implicit-account-creation path performs **no such check**. The account is created successfully, the deposit is committed to its balance, and the account is stamped with a global contract reference that may not exist anywhere in state. This is the direct analog of `OPERATOR_FILTER_REGISTRY` being assumed present on a new network without verification: a hard dependency on an external/global artifact is baked into a critical code path with no existence check, and the artifact is not guaranteed to be deployed on new networks.

An ETH-implicit account, per the account model, cannot be deleted nor have a full-access key added, and is documented to be "used... only by calling the methods of the Wallet Contract": [6](#0-5) 

If the wallet global contract is missing, every `FunctionCall` (including `rlp_execute`) against such an account resolves to no code (`contract_code.rs`'s `code()` returns `Ok(None)` for a missing `GlobalContractCode` trie entry), so the account can never be used to move its balance out: [7](#0-6) 

### Impact Explanation
Any `Transfer` (including a simple `send_money`) to an address that matches the ETH-implicit account format on a network where the wallet global contract has not been deployed yet causes an irrecoverable loss of the transferred balance: the account is created, funds are locked in it, and there is no action (no `DeleteAccount`, no `AddKey`, no usable `FunctionCall`) that can move the balance back out, since the only interaction surface (the wallet contract) does not exist. This is concrete, transaction-triggered "permanently frozen funds," and it can be repeated by any unprivileged sender simply by sending a transfer to any address of the ETH-implicit account form.

### Likelihood Explanation
This requires only two conditions, both realistic for a "new network" scenario mirrored in the original report: (1) the network is not yet mainnet/testnet/mocknet, or is a new deployment of any of those chain IDs before the wallet contract has been deployed as a global contract, and (2) any sender submits a `Transfer` action to an address of ETH-implicit account form (42-char `0x...` hex). No special privilege, validator status, or malicious peer/node cooperation is needed — a single ordinary transaction triggers it, and the resulting frozen state persists indefinitely.

### Recommendation
Mirror the check already used by `UseGlobalContractAction`/`DeterministicStateInitAction`: before assigning `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` in `action_implicit_account_creation_transfer`, verify the corresponding `TrieKey::GlobalContractCode` entry exists. If it does not exist, reject the implicit-account-creating transfer with an explicit error (e.g., extend/reuse `GlobalContractDoesNotExist`) rather than silently creating an unusable account and locking the deposit. Alternatively/additionally, require and validate at genesis/config load time that the wallet global contract corresponding to `eth_wallet_global_contract_hash(chain_id)` is deployed before the `EthImplicitGlobalContract` protocol feature is allowed to activate for that network.

### Proof of Concept
1. Launch a new network (custom `chain_id`, not mainnet/testnet/mocknet) with the `EthImplicitGlobalContract` protocol feature active, and do **not** submit any `DeployGlobalContractAction` for the wallet contract code matching `eth_wallet_global_contract_hash(chain_id)` (this is exactly the setup contrasted by the existing test `test_eth_implicit_accounts`, which explicitly deploys the wallet global contract first — showing this deployment is a manual prerequisite, not automatic): [8](#0-7) 
2. From any account, submit `SignedTransaction::send_money` (or any `Transfer` action) to a target account ID of ETH-implicit form (e.g., derived via `derive_eth_implicit_account_id`), with a non-zero deposit.
3. Observe the transaction succeeds and the account is created with `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` and the deposited balance, exactly as in `test_eth_implicit_account_creation`, but without the preceding wallet-contract deployment step: [9](#0-8) 
4. Attempt any `FunctionCall` (e.g., `rlp_execute`) or any other action against the account; it fails because the code (`GlobalContractCode` trie entry) does not exist. There is no `DeleteAccount` or `AddKey` path available for ETH-implicit accounts, so the deposited balance is permanently unreachable.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

/// Tests that ETH-implicit account is created correctly, with Wallet Contract hash.
#[test]
fn test_eth_implicit_account_creation() {
    let genesis = Genesis::test(vec!["test0".parse().unwrap(), "test1".parse().unwrap()], 1);
    let mut env = TestEnv::builder(&genesis.config).nightshade_runtimes(&genesis).build();
    let genesis_block = env.clients[0].chain.get_block_by_height(0).unwrap();
    let chain_id = &genesis.config.chain_id;

    let signer = InMemorySigner::test_signer(&"test0".parse().unwrap());
    let eth_implicit_account_id = eth_implicit_test_account();

    // Make zero-transfer to ETH-implicit account, invoking its creation.
    let transfer_tx = SignedTransaction::send_money(
        1,
        signer.get_account_id(),
        eth_implicit_account_id.clone(),
        &signer,
        Balance::ZERO,
        *genesis_block.hash(),
    );
    assert_eq!(
        env.rpc_handlers[0].process_tx(transfer_tx, false, false),
        ProcessTxResponse::ValidTx
    );
    for i in 1..5 {
        env.produce_block(0, i);
    }

    // Verify the ETH-implicit account has zero balance and appropriate code hash.
    // Check that the account storage fits within zero balance account limit.
    let request = QueryRequest::ViewAccount { account_id: eth_implicit_account_id };
    match view_request(&env, request).kind {
        QueryResponseKind::ViewAccount(view) => {
            assert!(view.amount.is_zero());
            assert_eq!(view.global_contract_hash, Some(eth_wallet_global_contract_hash(chain_id)));
            assert!(view.storage_usage <= ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT)
        }
        _ => panic!("wrong query response"),
    }
}
