### Title
Unvalidated offset pointers in `extractBytesArray`/`extractSigArray` allow out-of-bounds array access in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Solady report describes `decodeBatch()` trusting an offset/pointer value read from attacker-controlled calldata without verifying that the pointer's *own* storage location lies within the data before using it to index further into the buffer. The java-tron `ValidateMultiSign` and `BatchValidateSign` precompiled contracts contain the same root-cause pattern: an attacker-controlled offset word is used directly to index the parsed `DataWord[]` array (and the underlying `data` byte array) without first checking that the offset itself resolves to a location inside the array bounds.

### Finding Description
`ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()` parse the raw call data into `DataWord[] words = DataWord.parseArray(rawData)` and then compute a signature-array pointer directly from an attacker-controlled word: [1](#0-0) 

The same pattern exists in `BatchValidateSign`: [2](#0-1) 

The `sigArraySize`/`addrArraySize` computation (`words[words[3].intValueSafe() / WORD_SIZE]`, `words[words[1]...]`, `words[words[2]...]`) uses an attacker-controlled offset to directly index `words[]` with no bound check that `words[3].intValueSafe() / WORD_SIZE` (or `words[1]`, `words[2]`) is `< words.length`. This mirrors the Solady bug: the *pointer location itself* is unchecked before being dereferenced.

Downstream, `extractBytesArray` and `extractSigArray` only check the initial `offset` argument, not the per-item offsets computed from attacker data inside the loop: [3](#0-2) 

Here `len` (`words[offset].intValueSafe()`) is fully attacker controlled, and each loop iteration computes `bytesOffset` and dereferences `words[offset + i + 1]` / `words[offset + bytesOffset + 1]` with no bound check against `words.length`, and calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)`, which does an unchecked `Arrays.copyOfRange` on the raw `data` byte array: [4](#0-3) 

A structural ABI-shape guard (`isValidAbiEncoding`) was added, but it only checks total length divisibility by a fixed header/item word count, and is only enforced when the `allowTvmOsaka` (TIP-854) feature is active: [5](#0-4) [6](#0-5) 

This guard does not validate that individual dynamic-array offset fields point within bounds — it only constrains the *overall* data length shape, which is exactly the class of check the Solady report says is insufficient (offsets can still alias/overflow within a validly-shaped buffer).

### Impact Explanation
If a crafted offset causes `offset + i + 1` or `offset + bytesOffset + 1` to exceed `words.length`, the code throws an unchecked `ArrayIndexOutOfBoundsException` from within `extractBytesArray`/`extractSigArray`, called directly from `ValidateMultiSign.execute()`/`BatchValidateSign.doExecute()` *before* any surrounding try/catch is reached (the try/catch in `ValidateMultiSign` only wraps the later permission-weight logic, not the extraction call). Any smart contract can reach these precompiles (addresses gated by `VMConfig.allowTvmSolidity059()`) via a normal `CALL`/`STATICCALL` from any broadcast transaction, making this reachable by any anonymous transaction sender. Depending on how the TVM interpreter's precompile-invocation path handles arbitrary uncaught `RuntimeException`s (not confirmed in this pass), this can manifest as an inconsistent revert/exception path across nodes or an availability/DoS issue for the specific transaction/contract call, rather than a memory-corruption-class bug (Java has strict array bounds, unlike raw calldata in the Solidity/EVM case).

### Likelihood Explanation
Medium: constructing calldata with an out-of-range offset word for `ValidateMultiSign`/`BatchValidateSign` is straightforward and requires no privileged access — any account can deploy a contract that calls these precompile addresses with attacker-chosen calldata. The `isValidAbiEncoding` structural check (only active post-TIP-854/Osaka) reduces but does not eliminate the attack surface, since it validates the outer shape only, not per-element offset validity, matching the exact bypass technique described in the Solady report (multiple/invalid offsets can still satisfy a coarse length-based check).

### Recommendation
Add explicit bound checks in `extractBytesArray` and `extractSigArray` (and in the `sigArraySize`/`addrArraySize` pre-checks in `ValidateMultiSign`/`BatchValidateSign`) verifying that every computed index (`offset + i + 1`, `offset + bytesOffset + 1`, and the derived byte offset/length used in `extractBytes`) is strictly less than `words.length` / `data.length` before dereferencing, mirroring the fix applied to `LibERC7579.decodeBatch()` (validate the pointer's own location before following it).

### Proof of Concept
Not independently verified with a live execution trace in this pass (tool budget exhausted); root cause is established from static analysis of `extractBytesArray`/`extractSigArray`/`ValidateMultiSign.execute()`/`BatchValidateSign.doExecute()` shown above. A concrete PoC would construct raw calldata for `validatemultisign(...)`/`batchvalidatesign(...)` where the dynamic-array-length offset word (`words[3]`/`words[1]`/`words[2]`) resolves to an index at or beyond `rawData.length/32`, triggering `ArrayIndexOutOfBoundsException` inside `extractBytesArray`/`extractSigArray` before the existing `try { ... } catch (Throwable t)` block in `ValidateMultiSign.execute()` is reached.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
