### Title
`ValidateMultiSign` precompile fails to deduplicate by recovered signer address, allowing weight double-counting via ECDSA signature malleability - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract accumulates multi-sig `totalWeight` by iterating over a caller-supplied signature array and adding the corresponding key's weight for each signature. Its de-duplication check only rejects an exact repeated signature (same raw bytes), not a repeated *signer address* recovered from a different (malleable) signature. Because ECDSA/secp256k1 signatures are malleable, a holder of one valid signature can trivially derive a second, byte-distinct signature that recovers to the same address, causing that single key's weight to be counted twice (or more) toward the permission threshold — mirroring the reported bug class of "duplicate committee members not deduplicated," here manifesting as duplicate signer weight not deduplicated.

```
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);

  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {

  totalWeight += weight;

```

The `continue` (skip) branch is only taken when the *exact* `(recoveredAddr + sign)` combination has already been seen. If `recoveredAddr` was already seen but the current `sign` bytes differ (as happens with a malleable signature variant, e.g. flipping `s` to `n - s` and adjusting the recovery id `v`), the code falls through, recomputes `weight` for the same address, and adds it to `totalWeight` again. The correct fix (analogous to the reported committee-member fix) is to skip/reject as soon as `recoveredAddr` alone is a repeat, regardless of the exact signature bytes — i.e., deduplicate by *signer identity*, not by raw signature bytes.

This is directly analogous to the reported bug: an array (`committeeArray` / here `signatures[]`→weight accumulation) is processed without deduplicating by the semantically meaningful identity (committee member address / signer address), allowing the same identity to be counted multiple times and inflate a count that is compared against a threshold (`committeeArray.length` vs actual distinct members / `totalWeight` vs `permission.getThreshold()`).

### Impact Explanation
`ValidateMultiSign` is a TVM precompiled contract callable by any smart contract via `validatemultisign(address,uint256,bytes32,bytes[])`, and it is the on-chain primitive many contracts (exchanges, custodial wallets, multisig-gated contracts) rely on to verify that a threshold of *distinct* authorized keys approved an action. If a single key's weight can be counted twice by supplying two malleable variants of its own signature, a caller controlling fewer real distinct keys than the configured threshold can satisfy `totalWeight >= permission.getThreshold()`. This undermines the security guarantee multisig-based contracts depend on for authorizing sensitive operations (fund transfers, governance actions, etc.), constituting unauthorized-operation / accounting-corruption impact within contract execution.

### Likelihood Explanation
Exploitation requires only a single valid ECDSA signature over the fixed hash the contract computes (`sha256(address || permissionId || data)`) and standard secp256k1 malleability (negate `s`, flip `v`) to produce a second, byte-different signature recovering to the same address — a well-known, cheap, deterministic technique requiring no private-key knowledge beyond what the legitimate signer already used to produce the first signature. Any attacker who can obtain (or is themselves) one authorized signer with weight `w < threshold` can supply `[sig, malleable_variant_of_sig]` to double the counted weight. This is reachable from ordinary smart contract execution (any account can call a contract that invokes `validatemultisign`), with no privileged access needed.

### Recommendation
In `ValidateMultiSign.execute()`, change the de-duplication logic so that once `recoveredAddr` has been observed once, all subsequent signatures recovering to the same address are skipped (i.e., check `matrixContains(executedSignList_by_address, recoveredAddr)` first and always `continue`/reject in that case, never falling through to re-add weight), matching the pattern already correctly used in `TransactionCapsule.checkWeight()` (`addMap.containsKey(...)` → throws `"has signed twice!"`) and in `AccountPermissionUpdateActuator.checkPermission()` (`.distinct()` check on key addresses).

### Proof of Concept
Conceptual PoC (cannot be executed in this environment, but derivable from the code path):
1. Create an account with an Active permission containing one key `K` with `weight = 1` and `threshold = 2` (so `K` alone is insufficient).
2. Compute `hash = sha256(address || permissionId || data)` as done in `execute()`.
3. Sign `hash` once with `K`'s private key to get `sig1 = (r, s, v)`.
4. Derive the malleable variant `sig2 = (r, n - s, 1 - v)` (standard secp256k1 signature malleability transform) — `sig2` is a different byte sequence that still recovers to the same address as `sig1`.
5. Call `validatemultisign(address, permissionId, data, [sig1, sig2])`.
6. In `execute()`, iteration over `sig1` adds `weight=1`, `totalWeight=1`. Iteration over `sig2`: `recoveredAddr` matches (already in `executedSignList`), but the merged `sign` bytes differ from the stored one, so the exact-match check fails and the code does **not** `continue` — it recomputes weight and adds it again, yielding `totalWeight=2 >= threshold(2)`, returning `true` despite only one real distinct signer.

Note: The exact byte layout details of `merge()` / `recoverAddrBySign()` / `ByteArray.matrixContains()` were reviewed at a high level from the excerpts obtained; full confirmation of the malleability transform’s exact compatibility with this codebase's `SignUtils`/`ECDSASignature` verification (e.g., whether it also independently enforces low-s canonical form somewhere upstream) would benefit from a full read of `crypto/src/main/java/org/tron/common/crypto/SignUtils.java` and the ECDSA signature class, which was not fully retrieved in this session.
