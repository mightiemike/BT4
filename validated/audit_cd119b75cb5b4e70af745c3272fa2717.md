### Title
Unbounded, permanently-retained entries in `RequestReplayGuard.seen` via attacker-controlled far-future `ExpiryTimestamp` - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
`RequestReplayGuard.CheckAndRecord` stores `expiresAtUnix` exactly as supplied by the caller, and for the `AllowListBasedAuth` path this value is taken directly from the on-chain `WorkflowRegistryOwnerAllowlistedRequest.ExpiryTimestamp` (a `uint32`), which any linked workflow owner can set to values as large as `2^32-1` (~year 2106). Since `clearExpiredLocked` only removes entries whose expiry has already passed, entries created with a far-future expiry are never reclaimed, allowing unbounded growth of the in-memory `seen` map.

### Finding Description
`AllowListBasedAuth.AuthorizeRequest` reads `allowlistedRequest.ExpiryTimestamp` from the on-chain allowlist synced by `workflowRegistrySyncer` and forwards it unmodified into `AuthResult.expiresAt` [1](#0-0) . `authorizer.AuthorizeRequest` then calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` [2](#0-1) . `CheckAndRecord` stores the digest keyed to this caller-supplied unix timestamp with no upper bound validation, and `clearExpiredLocked` only deletes entries whose expiry is strictly in the past [3](#0-2) .

The `ExpiryTimestamp` originates from the `WorkflowRegistry.AllowlistRequest(requestDigest, expiryTimestamp)` on-chain call, which is exposed as a self-service, unprivileged user operation (`UserAllowlistRequest`/`UserAllowlistRequestOp`) requiring only that the caller has previously linked ownership via a self-signed ownership proof — no node-operator or admin privilege is required [4](#0-3) . The only client-side validation found is that the expiry cannot be zero; there is no maximum bound enforced [5](#0-4) . Since `ExpiryTimestamp` is a `uint32`, any linked owner can set it up to `4294967295` (Feb 2106).

An attacker who has linked a workflow owner address can therefore: (1) call `AllowlistRequest` on-chain for many distinct request digests with `ExpiryTimestamp = uint32 max`, and (2) submit the corresponding vault requests to the node so that `AuthorizeRequest` succeeds and `CheckAndRecord` inserts each digest into `RequestReplayGuard.seen` with an effectively permanent expiry. `clearExpiredLocked`, invoked on every `CheckAndRecord` call and via `ClearExpired`, will never remove these entries because `now > expiry` is never true for a ~2106 timestamp. There is no cap on the number of `seen` entries, no LRU eviction, and no independent bound imposed by the node on acceptable expiry windows — reclamation depends entirely on the attacker-influenced value.

### Impact Explanation
Each such entry persists in the Vault node's process memory for the lifetime of the process, growing linearly with the number of distinct digests the attacker registers and submits. Because entries are keyed by full request digest (32-byte hash as a string) and can be generated for arbitrarily many distinct requests, this constitutes unbounded, irreversible memory growth on any DON node running the Vault capability, consistent with an availability-impacting Denial-of-Service condition on Vault node functions.

### Likelihood Explanation
Exploitability is real but not free: it requires (1) a self-linked workflow-owner address (no special node/admin privilege, only a self-signed ownership proof), (2) one on-chain `AllowlistRequest` transaction per distinct digest (gas cost, size-bounded by chain throughput/allowlist retrieval pagination), and (3) delivering the corresponding request to the vault gateway to actually record it. This is more expensive than a pure off-chain flood, but it is fully within reach of an ordinary, unprivileged user/workflow owner — no leaked keys, admin role, or social engineering needed — and is repeatable indefinitely over time, making sustained memory bloat feasible.

### Recommendation
Do not trust caller-supplied `expiresAtUnix` as-is for replay-guard retention. Clamp it to a bounded maximum TTL from "now" (e.g., `min(expiresAtUnix, now + maxReplayWindow)`) inside `CheckAndRecord`/`authorizer.go` before storing, independent of what the on-chain allowlist or JWT claims report. Additionally, consider enforcing a hard cap on the number of entries in `seen` (e.g., LRU eviction) as defense in depth.

### Proof of Concept
Unit test in `core/capabilities/vault/request_replay_guard_test.go`:
1. Create `guard := NewRequestReplayGuard()`.
2. Loop N times (e.g., 100k), calling `guard.CheckAndRecord(fmt.Sprintf("digest-%d", i), math.MaxInt32*2)` (uint32-max-derived far future expiry).
3. Call `guard.ClearExpired()` after the loop.
4. Assert `len(guard.seen) == N` — i.e., the map never shrinks despite `ClearExpired` being invoked, demonstrating permanent, unbounded retention driven solely by attacker-suppliable expiry values.

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

// ClearExpired removes all entries whose expiry timestamp is in the past.
// Call this to eagerly reclaim memory even when CheckAndRecord is not invoked.
func (g *RequestReplayGuard) ClearExpired() {
	g.mu.Lock()
	defer g.mu.Unlock()
	g.clearExpiredLocked()
}

func (g *RequestReplayGuard) clearExpiredLocked() {
	now := g.nowFunc().UTC().Unix()
	for digest, expiry := range g.seen {
		if now > expiry {
			delete(g.seen, digest)
		}
	}
```
