### Title
`RepositoryImpl#calculateGlobalEnergyLimit` can divide by zero because the `totalEnergyWeight` guard present elsewhere is missing - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The Sherlock finding is a division-by-zero bug in `BalancerPairOracle#computeFairReserves`, where a raw integer division (`resA / resB`) is used as a denominator later, without guarding against the divisor becoming zero, causing the whole price/oracle call path to revert. The closest reachable analog in java-tron is `RepositoryImpl#calculateGlobalEnergyLimit`, a TVM-facing energy-limit computation that divides by `totalEnergyWeight` while relying only on a Java `assert` (disabled by default in production) instead of an explicit runtime check — unlike its sibling implementation in `EnergyProcessor`, which does perform the explicit check.

### Finding Description
`RepositoryImpl#calculateGlobalEnergyLimit` computes: [1](#0-0) 

It reads `totalEnergyWeight` from the dynamic properties store and only protects against it being zero with `assert totalEnergyWeight > 0;` (line 976), which is compiled out unless the JVM is started with `-ea`, so in a normal production deployment this assertion is a no-op. If `totalEnergyWeight` is 0 when `hardenResourceCalculation()` is enabled, `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` throws an unhandled `ArithmeticException`; if hardening is disabled, `(double) totalEnergyLimit / totalEnergyWeight` produces `Infinity`/`NaN`, which then gets silently truncated on cast to `long`, producing an incorrect (and effectively unbounded or zero, depending on sign) energy limit rather than a controlled error.

Contrast this with the parallel implementation in `EnergyProcessor#calculateGlobalEnergyLimit` / `calculateGlobalEnergyLimitV2`, which explicitly checks for a zero/negative `totalEnergyWeight` and returns `0` before doing any division: [2](#0-1) 

`RepositoryImpl#calculateGlobalEnergyLimit` has no equivalent guard, meaning the same division-by-zero root cause identified in the oracle bug (an unguarded division whose denominator can reach zero under some system states) is present here, but only in one of the two structurally similar implementations.

### Impact Explanation
`RepositoryImpl` implements the `Repository` interface used throughout TVM contract execution (`calculateGlobalEnergyLimit` is declared in `Repository` and consumed via `VMActuator`/`ContractState`), so this code path is reachable from ordinary (unprivileged) TVM/smart-contract execution whenever an account's energy limit needs to be computed during a transaction. If `totalEnergyWeight` reaches zero (e.g., all previously frozen-for-energy balances are unfrozen or migrated such that the chain-wide weight tally drops to zero) while an account still has `frozeBalance >= TRX_PRECISION`, any transaction that triggers this computation will throw an uncaught `ArithmeticException` (hardened path) causing an unexpected transaction/processing failure, or silently compute a wrong (Infinity/NaN-derived) energy limit (non-hardened path), which is an incorrect-state/accounting bug in a chain-wide, consensus-relevant resource-limit calculation.

### Likelihood Explanation
`totalEnergyWeight` is a chain-wide aggregate that should track the sum of all accounts' frozen-for-energy weight, and in ordinary operation it should stay consistent with any account that has nonzero frozen balance. However, the code that would guard against transient/edge-case inconsistencies (as done in `EnergyProcessor`) is missing here, so any discrepancy between an individual account's frozen balance and the global aggregate (e.g., from a bug elsewhere, migration edge cases, or the unfreeze-delay v2 pathway) has no fallback in this specific implementation and will directly hit the unguarded division.

### Recommendation
Add the same explicit zero/negative check that exists in `EnergyProcessor#calculateGlobalEnergyLimit` / `calculateGlobalEnergyLimitV2` to `RepositoryImpl#calculateGlobalEnergyLimit`, returning `0` (or otherwise safely handling the case) before performing the division, instead of relying on a Java `assert` that is disabled in production builds.

### Proof of Concept
Not independently exploitable to prove via code inspection alone: reaching `totalEnergyWeight == 0` while an account retains `frozeBalance >= TRX_PRECISION` requires a specific, currently-unconfirmed sequence of freeze/unfreeze/migration operations against `DynamicPropertiesStore#getTotalEnergyWeight` combined with a TVM execution path that calls `Repository#calculateGlobalEnergyLimit`. I was not able to trace the full call chain from `VMActuator`/`ContractState` down to this method within the available iterations to construct a concrete end-to-end transaction sequence; this should be validated with a live/test node (e.g., via a Devin session) by driving `totalEnergyWeight` to zero and then invoking a contract path that calls `calculateGlobalEnergyLimit` with `hardenResourceCalculation()` enabled.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimitV2(long frozeBalance) {
