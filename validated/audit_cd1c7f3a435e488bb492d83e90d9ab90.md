### Title
Double-Precision Arithmetic in TRC10 Bancor-Relay Exchange Math Causes Systematic Value Loss - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeCapsule.transaction()` selects between two exchange-rate calculators depending on the `ALLOW_HARDEN_EXCHANGE_CALCULATION` (proposal #98) flag: the legacy `ExchangeProcessor` (double/`Math.pow` based) or the newer `SafeExchangeProcessor` (`BigDecimal`-based) [1](#0-0) . Because this hardening flag defaults to `0` and must be turned on via an on-chain committee proposal [2](#0-1) , every ordinary, unprivileged `ExchangeTransactionContract` executed today runs through the double-precision Bancor relay formula in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which is directly analogous to the reported class of bug: fee/exchange-rate math relying on lossy floating-point/integer truncation in a financial accounting path.

### Finding Description
`ExchangeProcessor` computes the relay-token issuance and redemption using floating point `Math.pow`:

```java
double issuedSupply = -supply * (1.0
    - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
...
double exchangeBalance = balance
    * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
``` [3](#0-2) 

This is the same category of defect as the Sherlock report: a core financial-accounting function (rate/fee application) that discards precision through intermediate floating-point/integer operations rather than performing the full computation before truncating. In the original report, `DENOM`-based integer truncation and `interest/(reserves/100)` percent-truncation independently and jointly caused fee/rate underpayment of up to 100%. Here, `double` arithmetic for `Math.pow` with exponents `0.0005` / `2000.0` on ratios that can be very close to 1 (large pools, small trades) is well known to lose precision catastrophically (the classic "cube-near-one" floating point cancellation problem), and the truncation to `long` via `(long) issuedSupply` / `(long) exchangeBalance` discards any fractional/rounding-drift results.

The project's own author(s) recognized this exact problem: they introduced `SafeExchangeProcessor`, which redoes the same math with `BigDecimal` at 18-decimal scale and `RoundingMode.HALF_UP` specifically to eliminate this precision loss [4](#0-3) , and test code explicitly asserts that legacy vs. hardened results can diverge ("Allow ±1 difference due to BigDecimal vs double precision") [5](#0-4) . However, this hardened path is only used when `hardenedCalc` (driven by `ALLOW_HARDEN_EXCHANGE_CALCULATION`) is `1` [1](#0-0) , and this proposal is not enabled by default [2](#0-1) .

### Impact Explanation
Every `ExchangeTransactionContract` (a fully unprivileged, user-callable market action, validated in `ExchangeTransactionActuator.doValidate`) computes `anotherTokenQuant` via the vulnerable double-precision path by default [6](#0-5) . Precision loss here directly changes the amount of TRX/TRC10 tokens credited to the trader and debited from the pool's `firstTokenBalance`/`secondTokenBalance`, i.e., it is a direct on-chain settlement/accounting effect, not cosmetic. Repeated, deliberately-crafted trade sizes near ratio boundaries (small `quant` relative to `newBalance`, or repeated small trades) can consistently bias the result in one direction, draining value from the exchange pool (harming other TRC10/TRX liquidity participants) or systematically shortchanging traders — the same "loss of funds via consistent underpayment" impact class described in the source report.

### Likelihood Explanation
High: this is the default, currently active code path for TRC10 Bancor-relay exchanges (`ExchangeTransactionContract`) reachable by any account with a balance, no privileged role required. It requires no chain reconfiguration to trigger — the safer `BigDecimal` path is opt-in via governance and not enabled by default.

### Recommendation
Enable `ALLOW_HARDEN_EXCHANGE_CALCULATION` (or make `SafeExchangeProcessor` the unconditional default) so that all `ExchangeCapsule.transaction()` calls use the `BigDecimal`-based, precision-preserving computation regardless of committee proposal state, closing the floating-point precision-loss window in the default deployment.

### Proof of Concept
`ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection` demonstrates the divergence between the legacy (`hardenedCalc=false`) and hardened (`hardenedCalc=true`) processors on identical inputs, explicitly tolerating a discrepancy attributed to "BigDecimal vs double precision" [7](#0-6) . Since the legacy path is the default (flag off), this divergence is live in production unless the corresponding committee proposal has been passed on the target network.

Note: I was unable to execute code or fetch runtime governance state to confirm the current on-chain value of `ALLOW_HARDEN_EXCHANGE_CALCULATION` for a live deployment; the analysis relies on the observed default (`0`) in `reference.conf` and `ProposalType` definitions in this repository snapshot.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
