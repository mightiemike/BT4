### Title
Privilege escalation via case-insensitive email collision between local admin users table and upstream LDAP identity - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.FindUser` performs a case-insensitive lookup (`lower(email) = lower($1)`) against the local `users` (CLI admin) table *before* ever querying the upstream LDAP server, and returns that row's role unconditionally if any row matches. Note that the specific "local-fallback" branch cited in the question (`len(result.Entries) == 0` at line 177) is not actually vulnerable as described, because `email` is lowercased once at function entry (line 116) and that same normalized value is reused consistently in every subsequent query, including the fallback query — so no raw/non-lowercased mismatch exists there. However, the *earlier* check at lines 118-129 of the same function has the exact identity-conflation flaw the question is describing, just located one step earlier in the control flow.

### Finding Description
`FindUser` begins with:
```go
email = strings.ToLower(email)
var foundLocalAdminUser sessions.User
checkErr := l.ds.GetContext(ctx, &foundLocalAdminUser, "SELECT * FROM users WHERE lower(email) = lower($1)", email)
if checkErr == nil {
    return foundLocalAdminUser, nil
}
``` [1](#0-0) 

This check runs for *every* call to `FindUser`, regardless of whether the caller is an LDAP-bound identity or a local CLI login attempt, and returns immediately with the matched local user's full role if any case-insensitive email match exists in the `users` table — with no verification that the caller actually authenticated as that local admin (no password check is performed here; that already happened upstream via LDAP `Bind`, against a completely different identity).

In `CreateSession`, the flow is: bind against LDAP with attacker-supplied credentials, then call `FindUser(ctx, escapedEmail)` purely to resolve a role for the session:
```go
if err = conn.Bind(searchBaseDN, sr.Password); err != nil { ... }
foundUser, err := l.FindUser(ctx, escapedEmail)
``` [2](#0-1) 

If the attacker's own LDAP account has a `uid`/email string that collides case-insensitively with an existing local CLI admin row in `users` (e.g., local admin `Admin@Example.com` vs. attacker's real LDAP identity `admin@example.com`), the case-insensitive `lower(email) = lower($1)` match at line 120 fires and the function returns the local admin's role — even though the attacker only proved control of a distinct upstream LDAP identity via `Bind`. The later branch the question specifically names (lines 173-188, guarded by `len(result.Entries) == 0`) is unreachable for this exact scenario, since it can only be reached after the earlier case-insensitive check has already failed (`sql.ErrNoRows`), and that later query uses the same already-lowercased `email` variable (line 177), so it introduces no additional case-mismatch surface beyond what the first check already covers.

### Impact Explanation
An LDAP-authenticated user whose LDAP-bound email string case-insensitively collides with a local CLI admin's email in the `users` table is granted that local admin's role (including Admin) for their session and any API tokens derived from it, without ever proving control of the local admin credentials. This is a privilege escalation / identity-confusion issue between two supposedly separate authentication domains (local CLI-managed admin vs. upstream-managed LDAP identity), matching Chainlink's "privilege escalation via auth bypass" bounty category.

### Likelihood Explanation
Exploitability depends on the specific deployment: it requires (1) LDAP auth enabled, (2) at least one local CLI admin row in `users` (commonly the initial bootstrap admin), and (3) an upstream LDAP directory entry whose `uid`/email differs only by case (or is otherwise normalized-equal) from that local admin's email — either through directory naming conventions, migration artifacts, or case handling differences between the local CLI creation flow and the org's LDAP provisioning. This is a plausible but non-trivial precondition; it is not exploitable by a fully anonymous attacker with no LDAP account at all, since a valid LDAP bind is still required.

### Recommendation
Do not use a case-insensitive/loosely-normalized lookup to gate return of local admin identity. Segregate the local-admin lookup path (CLI/local auth) from the LDAP-identity path entirely, or require exact (not `lower()`-folded) match plus an explicit marker that the request originated from the local-auth flow rather than the LDAP flow, so an LDAP-bound identity can never silently inherit a `users` table row's role via string coincidence.

### Proof of Concept
Unit test in `core/sessions/ldapauth/ldap_test.go`:
1. Seed `users` table with a local admin: `email = "Admin@Example.com"`, `role = Admin`.
2. Mock the LDAP client/connection such that a `Search` for group membership of `admin@example.com` returns zero entries (simulating a distinct real LDAP identity with no assigned role groups, i.e., reaching what would be the "no entries" state).
3. Call `ldapAuthenticator.FindUser(ctx, "admin@example.com")`.
4. Assert the returned `sessions.User.Role` is **not** `sessions.UserRoleAdmin` and does not equal the seeded local admin row — currently this assertion fails because the function returns the local admin row's role at line 120-123 before the LDAP search is even attempted. [3](#0-2)

func (l *ldapAuthenticator) FindUser(ctx context.Context, email string) (sessions.User, error) {
	email = strings.ToLower(email)

	// First check for the supported local admin users table
	var foundLocalAdminUser sessions.User
	checkErr := l.ds.GetContext(ctx, &foundLocalAdminUser, "SELECT * FROM users WHERE lower(email) = lower($1)", email)
	if checkErr == nil {
		return foundLocalAdminUser, nil
	}
	// If error is not nil, there was either an issue or no local users found
	if !errors.Is(checkErr, sql.ErrNoRows) {
		// If the error is not that no local user was found, log and exit
		l.lggr.Errorf("error searching users table: %v", checkErr)
		return sessions.User{}, errors.New("error Finding user")
	}
