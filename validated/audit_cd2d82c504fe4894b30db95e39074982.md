### Title
Fee transfer's ERC20 execution failure is not checked, allowing a transaction to be accepted and its nonce/state committed without the fee actually being paid - (File: `crates/blockifier/src/transaction/account_transaction.rs`)

### Summary
This is the direct sequencer analog of the reported router bug: a call to an ERC20-like contract (`mToken.redeem()` vs. here the fee token's `transfer` entry point) can fail internally (Cairo panic/revert, represented by `CallInfo.execution.failed = true` and an `ENTRYPOINT_FAILED`-tagged retdata) without surfacing as a Rust `Err`. Just like the router's `redeem()` call ignoring the non-reverting failure code, `handle_fee`/`execute_fee_transfer` in the blockifier never inspects `fee_transfer_call_info.execution.failed` before treating the fee transfer as successful.

### Finding Description
`CallEntryPoint::execute` returns `Ok(CallInfo)` even when the called contract logically failed; a Cairo1 panic sets `CallInfo.execution.failed = true` but is not converted into an `Err` unless the caller explicitly checks it or uses `non_reverting_execute` [1](#0-0) . The dedicated helper `non_reverting_execute` exists precisely to convert a failed `CallInfo` into an `Err(EntryPointExecutionError::ExecutionFailed)` [2](#0-1) .

However, the fee-charging path uses the plain, non-reverting-aware `execute`, not `non_reverting_execute`:

```rust
fn execute_fee_transfer(...) -> TransactionExecutionResult<CallInfo> {
    ...
    Ok(fee_transfer_call
        .execute(state, &mut context, &mut remaining_gas_for_fee_transfer)
        .map_err(|error| Box::new(TransactionFeeError::ExecuteFeeTransferError(error)))?)
}
``` [3](#0-2) 

Its caller `handle_fee` propagates the resulting `CallInfo` unconditionally as `Some(fee_transfer_call_info)` — there is no check of `fee_transfer_call_info.execution.failed` anywhere in this function or in `handle_fee`'s caller:
```rust
let fee_transfer_call_info = if concurrency_mode && !tx_context.is_sequencer_the_sender() {
    Self::concurrency_execute_fee_transfer(state, tx_context, actual_fee)?
} else {
    Self::execute_fee_transfer(state, tx_context, actual_fee)?
};
Ok(Some(fee_transfer_call_info))
``` [4](#0-3) 

`handle_fee` is invoked from `execute_raw` after `run_or_revert` has already committed the transaction's state changes and nonce increment, and its result (`Some(fee_transfer_call_info)`) is stored directly into `TransactionExecutionInfo` regardless of whether the transfer actually succeeded: [5](#0-4) 

This mirrors the router bug precisely: the fee-token contract's `transfer` entry point (like `mToken.redeem()`) can "fail" via the Cairo revert mechanism (a non-`Err` return with a failure flag) rather than an unrecoverable Rust error, and the caller does not check that flag before finalizing the transaction as accepted with fee "paid."

Note: `execute_entry_point_call_wrapper`, which underlies `execute`, does convert a failed call into an `Err` only `if !context.versioned_constants().enable_reverts` (i.e. reverts disabled) [6](#0-5) . Since reverts are enabled in normal production configuration, a failing/reverting `transfer` call returns `Ok(CallInfo{ execution: { failed: true, ...} })`, and that failure is silently accepted by `execute_fee_transfer`/`handle_fee`.

### Impact Explanation
If the fee token's `transfer` entry point panics/reverts (e.g., due to a malicious or buggy custom fee-token class, insufficient allowance-equivalent logic, or a crafted proxy/upgrade scenario, or any state condition causing the ERC20 transfer logic itself to revert while the outer call still returns normally), the blockifier will:
- Commit the transaction's execution state and increment the sender's nonce (already done in `run_or_revert`/`execute_raw` before `handle_fee` runs).
- Record a `fee_transfer_call_info` in `TransactionExecutionInfo` that looks like a normal call, without flagging the transaction as reverted or failed, even though `execution.failed == true` and the token balances were never actually moved (the fee-token contract's `transfer` reverted, discarding its internal storage writes because the OS/blockifier revert mechanism rolls back only the inner call's storage effects, not the tx acceptance).
- The receipt still reports `final_fee` as paid, and the transaction is accepted into the block as a successful/valid transaction.

This causes a wrong committed state: the sequencer's local state (and ultimately the block's state root / state diff) will diverge from what should be recorded if fee collection had actually failed, and the sequencer balance won't reflect the fee that was supposedly charged — a discrepancy between actual and perceived token balances, exactly as in the original report. This can result in permanent loss of protocol/sequencer fee revenue and inconsistent block state commitments (potential honest-node divergence if not all nodes hit the exact same non-deterministic revert path, or a systemic under-charging vulnerability if an attacker can reliably force `transfer` to fail post-facto while still consuming resources for free).

### Likelihood Explanation
Reachable directly by any unprivileged transaction sender: any account transaction (Invoke/Declare/DeployAccount) with `charge_fee=true` triggers `handle_fee → execute_fee_transfer`, and the fee token contract executed is whatever class is deployed at the account's configured `fee_token_address` (in some deployments this could be a custom/user-influenced class or subject to upgrade). Because the failure is a *logical* revert of the fee-token's Cairo code rather than a VM/host error, the surface for triggering it depends on the deployed fee-token implementation, but the missing check itself is a deterministic code-path bug present on every transaction — it is not gated by any privileged actor.

### Recommendation
Explicitly check `fee_transfer_call_info.execution.failed` (or replace `.execute(...)` with `.non_reverting_execute(...)`, consistent with how validation calls (`non_reverting_execute`) and OS-level fee charging (`non_reverting_select_execute_entry_point_func`, seen in the Cairo OS program) are already handled) in `execute_fee_transfer`/`handle_fee`, and propagate a hard transaction-execution error (aborting/reverting the whole transaction, or rejecting it) if the fee transfer call itself reports failure, rather than silently accepting a "successful" `CallInfo` whose `execution.failed` flag is `true`.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the code paths cited):
1. Deploy/point the block's fee-token address at a Cairo1 ERC20-like class whose `transfer` entry point contains a conditional `panic!`/assert that can be triggered by the transaction's sender/recipient addresses or by a manipulable storage condition (e.g., a blocklist check, an overflow guard, or a custom hook) while leaving enough remaining resources for the outer call to return normally (this is exactly how Cairo1 "failed" `CallInfo`s are produced elsewhere in tests, e.g. `test_call_contract_and_than_revert` [7](#0-6) ).
2. Submit a normal Invoke transaction with `charge_fee = true` whose execution succeeds and passes `PostExecutionReport` (balance/resource checks, which only check balances/resources, not whether the fee-transfer call itself will succeed).
3. During `handle_fee → execute_fee_transfer`, the `transfer` call panics/reverts internally; `CallEntryPoint::execute` still returns `Ok(CallInfo{ execution: { failed: true, ...}, ... })` because reverts are enabled.
4. `execute_fee_transfer` returns `Ok(call_info)` (mapped only on `Err`, not on `failed`), `handle_fee` returns `Ok(Some(call_info))`, and `execute_raw` includes this as `fee_transfer_call_info` in the final `TransactionExecutionInfo`, which is treated as an accepted, non-reverted transaction with `final_fee` reported as collected — even though the fee-token contract's own logic reverted the transfer.

I was not able to fully trace how the OS/Starknet-side re-execution (`charge_fee` in `transaction_impls.cairo`, which uses `non_reverting_select_execute_entry_point_func`) would behave under this same scenario within the time available; that Cairo path appears to use a "non-reverting" wrapper, which could mean the OS enforces a stronger check than blockifier in this specific case — this discrepancy between blockifier and the OS's Cairo implementation should be verified as part of remediation, since a difference here could itself cause blockifier/OS divergence.

        context: &mut EntryPointExecutionContext,
        remaining_gas: &mut u64,

        let strip_vm_frames = context.versioned_constants().strip_vm_frames_in_sierra_gas;
        let mut decrement_when_dropped = RecursionDepthGuard::new(
            context.current_recursion_depth.clone(),
            context.versioned_constants().max_recursion_depth,
        );
        decrement_when_dropped
            .try_increment_and_check_depth()
            .map_err(|e| e.annotated(TrackedResource::CairoSteps, strip_vm_frames))?;

        // Validate contract is deployed.
        let storage_class_hash = state.get_class_hash_at(self.storage_address).map_err(|e| {
            EntryPointExecutionError::from(e)
                .annotated(TrackedResource::CairoSteps, strip_vm_frames)
        })?;
        if storage_class_hash == ClassHash::default() {
            return Err(EntryPointExecutionError::from(
                PreExecutionError::UninitializedStorageAddress(self.storage_address),
            )
            .annotated(TrackedResource::CairoSteps, strip_vm_frames));
        }

        let class_hash = match self.class_hash {
            Some(class_hash) => class_hash,
            None => storage_class_hash, // If not given, take the storage contract class hash.
        };
        // Hack to prevent version 0 attack on argent accounts.
        if tx_context.tx_info.version() == TransactionVersion::ZERO
            && class_hash
                == ClassHash(
                    Felt::from_hex(FAULTY_CLASS_HASH).expect("A class hash must be a felt."),
                )
        {
            return Err(EntryPointExecutionError::from(PreExecutionError::FraudAttempt)
                .annotated(TrackedResource::CairoSteps, strip_vm_frames));
        }
        // Add class hash to the call, that will appear in the output (call info).
        self.class_hash = Some(class_hash);
        let compiled_class = state.get_compiled_class(class_hash).map_err(|e| {
            EntryPointExecutionError::from(e)
                .annotated(TrackedResource::CairoSteps, strip_vm_frames)
        })?;

        context.revert_infos.0.push(EntryPointRevertInfo::new(
            self.storage_address,
            storage_class_hash,
            context.n_emitted_events,
            context.n_sent_messages_to_l1,
        ));

        // This is the last operation of this function.
        execute_entry_point_call_wrapper(
            self.into_executable(class_hash),
            compiled_class,
            state,
            context,
            remaining_gas,
        )
    }

    /// Similar to `execute`, but returns an error if the outer call is reverted.
    pub fn non_reverting_execute(
        self,
        state: &mut dyn State,
        context: &mut EntryPointExecutionContext,
        remaining_gas: &mut u64,
    ) -> EntryPointExecutionResult<CallInfo> {
        let execution_result = self.execute(state, context, remaining_gas);
        if let Ok(call_info) = &execution_result {
            // Update revert gas tracking (for completeness - value will not be used unless the tx
            // is reverted).
            context.sierra_gas_revert_tracker.update_with_next_remaining_gas(
                call_info.tracked_resource,
                GasAmount(*remaining_gas),
            );

            if call_info.execution.failed {
                return Err(EntryPointExecutionError::ExecutionFailed {
                    error_trace: extract_trailing_cairo1_revert_trace(
                        call_info,
                        Cairo1RevertHeader::Execution,
                    ),
                }
                .annotated(
                    call_info.tracked_resource,
                    context.versioned_constants().strip_vm_frames_in_sierra_gas,
                ));
            }
        }

        execution_result
    }

    fn execute_fee_transfer(
        state: &mut dyn State,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
    ) -> TransactionExecutionResult<CallInfo> {
        // The least significant 128 bits of the amount transferred.
        let lsb_amount = Felt::from(actual_fee.0);
        // The most significant 128 bits of the amount transferred.
        let msb_amount = Felt::ZERO;

        let TransactionContext { block_context, tx_info } = tx_context.as_ref();
        let storage_address = tx_context.fee_token_address();
        // The fee contains the cost of running this transfer, and the token contract is
        // well known to the sequencer, so there is no need to limit its run.
        let mut remaining_gas_for_fee_transfer =
            block_context.versioned_constants.os_constants.gas_costs.base.default_initial_gas_cost;
        let fee_transfer_call = CallEntryPoint {
            class_hash: None,
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector_from_name(constants::TRANSFER_ENTRY_POINT_NAME),
            calldata: calldata![
                *block_context.block_info.sequencer_address.0.key(), // Recipient.
                lsb_amount,
                msb_amount
            ],
            storage_address,
            caller_address: tx_info.sender_address(),
            call_type: CallType::Call,

            initial_gas: remaining_gas_for_fee_transfer,
        };
        let mut context = EntryPointExecutionContext::new_invoke(
            tx_context,
            true,
            SierraGasRevertTracker::new(GasAmount(remaining_gas_for_fee_transfer)),
        );

        Ok(fee_transfer_call
            .execute(state, &mut context, &mut remaining_gas_for_fee_transfer)
            .map_err(|error| Box::new(TransactionFeeError::ExecuteFeeTransferError(error)))?)
    }
