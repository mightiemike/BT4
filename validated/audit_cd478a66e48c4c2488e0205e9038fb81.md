### Title
Wallet Contract Relayer Can Repeatedly Drain NEAR by Replaying a Signed Transaction Whose Fee Is Paid Before Nonce Consumption or Action Success Is Verified - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract's `inner_rlp_execute` pays out the relayer "fee" (`tx_fee`, extracted from the user's Ethereum-emulated signed transaction) to the calling `predecessor_account_id` unconditionally and *before* the nonce is consumed, for the specific case where the transaction target is another eth-implicit account requiring an address-registrar check (`EOABaseTokenTransfer { address_check: Some(address), .. }`). Because the nonce is deliberately *not* incremented on this path until the registrar callback resolves favorably, the same signed transaction can be resubmitted to `rlp_execute` repeatedly whenever the registrar check resolves unfavorably (target turns out to be a registered named account), extracting the fee payment on every call while the underlying user action never executes.

### Finding Description
In `inner_rlp_execute`, when parsing succeeds and the transaction is `EOABaseTokenTransfer { address_check: Some(_), .. }`, the nonce increment is explicitly skipped: [1](#0-0) 

Regardless of that, if the transaction kind carries a non-zero `fee`, the fee is transferred immediately to `predecessor_account_id` via a standalone promise batch that is *not* chained (`.then()`) to the outcome of the address-check / actual transfer promise created later in the same function: [2](#0-1) 

The actual address-registrar verification and subsequent action only happen afterward, dispatched to `address_check_callback`: [3](#0-2) 

In `address_check_callback`, the nonce is only incremented in the branch where the registrar reports the address is *not* registered (`maybe_account_id` is `None`). If the address *is* registered (an "invalid target" for this transaction) and the caller is not using the wallet's own access key (`signer_account_id() != current_account_id`, i.e., the normal external-relayer path), the call simply returns a failure response with **no nonce increment and no ban**: [4](#0-3) 

Because the fee-payment promise (lines 374-385) was already dispatched during the *initial* call to `rlp_execute` — independent of, and prior to, this callback resolving — every resubmission of the exact same `(target, tx_bytes_b64)` pair produces another fee payout to the caller, even though the wrapped action can never succeed (the target will forever be reported as an existing named account by the registrar). Since the nonce check in `validate_tx_relayer_data` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:352-359`) continues to match on every retry, this is a genuine, indefinitely repeatable replay: an unprivileged caller (any account submitting `rlp_execute` transactions, i.e., an ordinary RPC/transaction sender) can call the wallet contract as many times as desired with the same arguments, each time siphoning `tx_fee` yoctoNEAR out of the wallet contract's balance with only gas cost as the "expense," while the wallet owner's intended action is never performed.

This is the direct structural analog of the reported ERC-20 issue: a payment (here, the relayer fee) is transferred out of the contract without any binding guarantee that the corresponding underlying transfer/action actually completed successfully — and, unlike a single-shot mistake, is unboundedly repeatable due to the missing nonce consumption on this specific failure path.

### Impact Explanation
This allows unauthorized, repeated value extraction (draining of NEAR) from any Wallet Contract account whose signed transaction ever falls into the `address_check: Some` branch with an eventually-registered target. Each replay produces a state-changing balance transfer that was not authorized by a *new* signature from the wallet owner (the same nonce/signature is reused indefinitely), which is a direct violation of the nonce-based replay protection this contract is meant to provide, and results in concrete unauthorized value movement out of user funds.

### Likelihood Explanation
Exploitation requires: (1) a legitimately signed transaction whose target resolves to `TargetKind::EthImplicit` requiring an address check (a supported/expected code path, not an edge case), and (2) the derived eth-implicit address is (or later becomes) registered with the address registrar as a named account. Any external caller who has observed such a transaction (which, by design, is meant to be broadcastable to arbitrary relayers) can trigger the exploit by simply calling `rlp_execute` again with the identical arguments — no special privileges, access keys, or validator/node compromise are required, only a standard NEAR RPC call.

### Recommendation
- Do not dispatch the relayer-fee transfer promise until nonce consumption (or the ultimate action outcome) is guaranteed/committed for the given path.
- Increment the nonce (or otherwise mark the transaction as consumed) immediately upon successfully validating `validate_tx_relayer_data`, *before* branching on `address_check`, so that no code path allows the same signed transaction to be resubmitted after a fee has already been paid.
- Alternatively, chain the fee-payment promise with `.then()` after the address-check/action promise so it only executes if the wrapped action actually succeeds, mirroring the "checks-effects" pattern recommended in the original report (pay only after confirmed success).

### Proof of Concept
1. Wallet owner signs an Ethereum-emulated transaction whose `to` corresponds to an eth-implicit address `A` (not yet a registered named account) with a non-zero `max_fee_per_gas * gas_limit` (`tx_fee`), intending a base-token transfer, and hands it to a relayer.
2. Before or shortly after submission, address `A` becomes/ is registered as a named NEAR account in the address registrar (attacker can arrange or wait for this, or intentionally target only such transactions).
3. Attacker (acting as "relayer") calls `rlp_execute(target="0x{A}", tx_bytes_b64=<the signed tx>)`.
   - `inner_rlp_execute` does not increment the nonce (line 358-365) and immediately transfers `tx_fee` to the attacker's account (`predecessor_account_id`), per lines 374-385.
   - The subsequent registrar lookup resolves `Some(named_account)`, and since `signer_account_id() != current_account_id`, `address_check_callback` returns an "Invalid target" failure with no nonce increment (lines 160-192).
4. Attacker repeats step 3 with the identical `target`/`tx_bytes_b64` any number of times; each call passes the nonce check (nonce was never advanced) and pays out `tx_fee` again, draining the wallet contract's NEAR balance with no bound other than available funds.
