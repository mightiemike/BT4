### Title
Panic-on-unwrap in `receipt_filter_fn` when a stale `GlobalContractDistribution` receipt's `target_shard` cannot be remapped after repeated resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The CVE describes a pointer/reference-dereference panic triggered when Asterisk's SDP handling encounters an *unexpected combination of fields* (a T.38 stream plus another disallowed media stream) that the code assumed could never co-occur, crashing the process. The structurally analogous condition in nearcore is `DelayedReceiptQueueWrapper::receipt_filter_fn`, which assumes `receiver_shard_id(&shard_layout)` can always be resolved for any delayed receipt sitting in the queue, and unconditionally `.unwrap()`s that `Result`/`Option`. A `GlobalContractDistribution` receipt whose `target_shard` predates two successive resharding generations is exactly the "field combination that should not occur but does" scenario, and the codebase itself contains a dedicated regression test (`test-loop-tests/src/tests/global_contracts_distribution.rs::test_stale_global_contract_distribution_after_double_resharding`) built to reproduce this exact crash.

### Finding Description
`receipt_filter_fn` is called from `DelayedReceiptQueueWrapper::pop` on every receipt popped from the state's delayed-receipt queue during normal chunk application: [1](#0-0) [2](#0-1) 

It does two unconditional `.unwrap()` calls: one on `shard_layout(&self.epoch_id)` and one on `receiver_shard_id(&shard_layout)`. The comment directly above the function acknowledges the hazard: *"With ReshardingV3, it's possible for a chunk to have delayed receipts that technically belong to the sibling shard before a resharding event."* If a `GlobalContractDistribution` receipt is deliberately kept in the delayed queue across **two** consecutive shard-layout transitions (by saturating the shard's compute budget so it never gets processed), its `target_shard` value can point to a shard id that no longer exists / cannot be remapped by the current `shard_layout`, so `receiver_shard_id` fails and the `.unwrap()` panics — crashing every honest validator/chunk-producer node that eventually tries to pop that receipt from the delayed queue.

This is directly acknowledged and reproduced by the existing test: [3](#0-2) 
which forces a shard containing an attacker-deployed global contract to be split twice while the resulting `GlobalContractDistribution` receipt is starved in the delayed queue via gas-saturating `burn_gas_raw` calls, then asserts the chain does not stall/panic when draining the queue: [4](#0-3) 

The trigger is fully reachable from an unprivileged actor: any account can submit a `DeployGlobalContract` action (creating the `GlobalContractDistribution` receipt with a `target_shard`) and can submit ordinary `FunctionCall` transactions that consume gas to keep that receipt delayed across epoch/resharding boundaries — no validator or network-layer privilege is required, only the ability to submit transactions to a shard undergoing dynamic resharding.

### Impact Explanation
If the safeguard implied by the test is not actually enforced everywhere `receiver_shard_id` is unwrapped (i.e., if the fix only patches one call site but `receipt_filter_fn`'s two unwraps remain unconditional), an attacker-triggerable state (stale `target_shard` surviving two resharding generations) causes an unrecoverable `.unwrap()` panic inside `Runtime::apply`'s receipt-processing path. Because this runs identically on every node applying the chunk, it manifests as a synchronized, transaction-triggered chain halt (denial of service) rather than divergence — matching the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Exploitation requires dynamic resharding (`DynamicResharding` / ReshardingV3) to be active and requires an attacker to time contract deployment and gas-saturating calls around two consecutive shard splits — a non-trivial but entirely permissionless sequence documented as reproducible by the test harness itself (`force_split_shards`, sustained `burn_gas_raw` saturation over ~12 epochs). This is a narrow, timing/config-dependent window (dynamic resharding must be configured and shard splits must occur while the receipt is delayed), so likelihood is moderate rather than high; the presence of an explicit regression test suggests the nearcore team is aware of and actively guarding against this class of bug, but the underlying `.unwrap()` calls in `receipt_filter_fn` are unconditional in the code as read.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and any other call site resolving `receiver_shard_id` for receipts that may have survived multiple resharding generations) with an explicit, protocol-safe fallback: e.g., look up the receipt's shard through the full split-history/ancestry chain instead of only the current `shard_layout`, or propagate a `RuntimeError`/`StorageInconsistentState` instead of panicking so the failure is handled the same way other storage-invariant violations are (returning `Result` instead of unwinding). Ensure the fix covers every consumer of `receiver_shard_id` for receipts that can be delayed across more than one resharding boundary, not just the primary processing path exercised by the existing test.

### Proof of Concept
1. Configure a network with `DynamicResharding` enabled and `force_split_shards` targeting the shard that will hold an attacker's account (mirrors `dynamic_config` in the referenced test).
2. As an unprivileged account, deploy a global contract (`DeployGlobalContract` action), producing a `GlobalContractDistribution` receipt with `target_shard = S_A`.
3. Flood the shard with `FunctionCall` transactions (e.g., `burn_gas_raw`) each block so the chunk's gas limit is saturated and the distribution receipt is pushed into, and kept in, the delayed-receipt queue.
4. Continue until two consecutive shard splits complete (`S_A` splits, then a second split occurs), so the stored `target_shard` no longer corresponds to any shard reachable from the current `shard_layout`.
5. Stop saturating gas and allow the delayed queue to drain; when the runtime calls `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`, `receiver_shard_id(&shard_layout).unwrap()` panics, crashing the chunk-producer/validator node(s) applying that chunk. [5](#0-4) [6](#0-5)

    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));

    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
