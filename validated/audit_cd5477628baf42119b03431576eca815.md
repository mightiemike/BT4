### Title
Chunk-executor replay verification ignores state/hot-state/position checkpoint-hash mismatches, allowing corrupted checkpoint state to be accepted as a valid replay — (File: `types/src/transaction/mod.rs`)

### Summary
The external Monetrix report's core pattern is: a value that should be part of a completeness/integrity check (borrow liabilities) is silently dropped from the check, so a state that should fail validation instead passes it and gets committed/distributed as if correct. The Aptos-native analog is in `TransactionOutput::ensure_match_transaction_info()`, which is the function chunk-executor replay/verification (state sync, backup restore-verify, replay-on-archive tooling) uses to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` fetched from a trusted source (peer/backup). This function explicitly checks status, gas, write-set hash, and event root hash, but — per its own inline `TODO(trading-native)` comment — never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally computed values.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only 4 fields between the locally produced `TransactionOutput` and the authenticated `TransactionInfo`: status, gas used, write-set hash (`state_change_hash`), and event root hash. The state checkpoint root (Sparse Merkle Tree root over all account/resource state), the hot-state checkpoint root, and the newly added `position_state_checkpoint_hash` (trading-native state root) are never compared here, as the code's own comment states:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

`TransactionInfo` itself carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class fields precisely because they are meant to be part of the authenticated commitment chain from `LedgerInfo` → accumulator → `TransactionInfo` → checkpoint roots [3](#0-2) . The whole point of these hashes is to let a verifier bind the resulting Sparse-Merkle/JMT state root to a version proven by the transaction accumulator (see `TransactionInfoWithProof::verify` / `verify_transaction_info`, which authenticate only the `TransactionInfo` hash itself against the ledger, not its constituent fields individually) [4](#0-3) [5](#0-4) . Because the accumulator proof only certifies the opaque `TransactionInfo` hash, the only place that ever cross-checks the *individual* fields of that `TransactionInfo` against locally-computed values is `ensure_match_transaction_info`. If that function omits a field, that field's integrity is effectively unchecked in that code path.

`ensure_match_transaction_info` is called from chunk-executor replay/state-sync code and CLI/debugger tooling: [6](#0-5)  (usage confirmed via grep), `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. This is used precisely in scenarios described in scope ("replay, restore, or proof verification") — e.g., `replay_on_archive`, chunk-executor's apply of remotely-fetched `TransactionOutputListWithProof` during fast/intelligent sync, where the local VM re-execution output is checked against an already-accumulator-verified `TransactionInfo` before being committed to local storage.

The `Inner` struct in `execution/executor-types/src/state_checkpoint_output.rs` confirms these checkpoint hashes are first-class execution outputs, computed separately from the write-set/event hashes already checked [7](#0-6) , reinforcing that they are meant to be validated but currently are not in this replay-comparison path.

### Impact Explanation
If a locally re-executed transaction produces the correct write set and events (which alone determine `state_change_hash`/`event_root_hash`) but the resulting state/hot-state/position Sparse-Merkle checkpoint root diverges from the authenticated value in `TransactionInfo` — due to a local storage bug, a JMT computation bug, a divergent hot-state or trading-native-state feature rollout mismatch, or non-determinism in checkpoint-root computation — `ensure_match_transaction_info` will not detect it and replay/verification will report success. This lets chunk-executor commit a corrupted/incorrect state checkpoint root into durable ledger storage as if it matched the trusted, proof-verified value, i.e., exactly the "committed state differs from correct result" / "wrong ... state proof accepted as valid" class in scope. Once committed, subsequent state proofs served from this node's storage would authenticate against the wrong (locally divergent) root while claiming to match the version's `TransactionInfo`. This is high impact because it silently breaks the fundamental invariant that a node's local storage state root always matches what its own execution independently proves, undermining trust in replay-verify tooling and any node that trusts this comparison as its correctness gate. As explicitly flagged by the maintainers' own comment, this is a known gap that must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," confirming the checkpoint-hash comparison is intended but currently missing, not merely an oversight.

### Likelihood Explanation
Medium. This requires a genuine local-execution/state-computation divergence to exist that affects only the checkpoint hash and not the write-set/event hash (since those are still checked) — e.g., a bug in JMT-root computation, a hot-state or native-position feature that's misconfigured between the executing node and its peers, or a storage corruption during checkpoint computation. The `hot_state_checkpoint_hashes` are noted as currently unused in production ("this is currently None in testnet and mainnet") [8](#0-7) , and `position_state_checkpoint_hash` is gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which the code comment states is not yet enabled — so this gap is latent rather than actively exploited today, but becomes a real hard-fork/replay-divergence risk once that feature is turned on, or in any regular `state_checkpoint_hash` divergence scenario during chunk-executor-based sync/replay.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally computed `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the corresponding fields of the passed-in `txn_info`, returning an error on mismatch just as is done for `write_set_hash` and `event_root_hash`. This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, per the existing TODO.

### Proof of Concept
Not independently runnable without a live divergence scenario; the vulnerability is proven by direct code inspection: `ensure_match_transaction_info` at [1](#0-0)  only asserts on `status`, `gas_used`, `write_set_hash`, and `event_root_hash`, and explicitly (per its own comment) does not assert on `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, even though `TransactionInfo` carries all of these as authenticated fields [3](#0-2)  and the accumulator proof authenticates only the opaque hash of the whole `TransactionInfo`, not its individual sub-fields [5](#0-4) . Any caller (chunk executor replay, `db-tool replay_on_archive`, debugger tooling) that relies solely on this function to validate re-executed output against a trusted `TransactionInfo` will not catch a checkpoint-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,

        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
