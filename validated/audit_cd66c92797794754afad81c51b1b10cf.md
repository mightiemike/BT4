### Title
`AddressRegistrar::register()` accepts over-payment and permanently locks the excess deposit with no refund or withdrawal path - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar` contract used by the NEAR Wallet Contract's Ethereum-emulation flow accepts an `attached_deposit` for its `register()` method but only performs a strict lower-bound check (`given_deposit < required_deposit`). Any amount attached above the actual storage cost is silently retained by the contract on the success path, with no logic to refund the excess and no function for anyone to withdraw it.

### Finding Description
In `register()`, the deposit sufficiency check is:
```rust
let given_deposit = env::attached_deposit();
if given_deposit < required_deposit {
    env::panic_str(...);
}
```
This is a strict `<` check, so any `given_deposit >= required_deposit` passes. On the success path (`Entry::Vacant`, i.e. a new address being registered), the code inserts the mapping and returns the address string — it never computes or refunds `given_deposit - required_deposit`. Only the collision path (`Entry::Occupied`) refunds the *entire* deposit back to the caller when no storage update happens; there is no logic anywhere that refunds a partial excess when storage *is* written. There is also no admin/owner-only withdrawal method defined anywhere in the contract (confirmed by the absence of any `withdraw`/`owner`/`admin` method in the crate). Consequently, any yoctoNEAR sent above `required_deposit` becomes permanently locked in the `AddressRegistrar` contract's balance with no code path to ever recover it.

This is directly analogous to the reported `UnikuraPhygitalCollection.mint()` bug: a payable entry point performs only a `>=`/`<` bound check on payment instead of strict equality, does not refund the excess on the success path, and provides no recovery mechanism, so overpayment is destroyed/locked forever.

### Impact Explanation
Because `register()` is reachable by any unprivileged NEAR account (an ordinary transaction signer or an RPC caller submitting a `FunctionCall` action with a deposit), any caller who overestimates or is tricked into overestimating the required deposit (e.g., a relayer helping a user register an address, or simple user error) will have the excess amount permanently frozen in the contract's balance, with no owner, upgrade, or withdrawal mechanism to recover it. This matches the "permanently frozen funds" impact category accepted by scope rules. The contract is part of the production Wallet Contract ecosystem (`ADDRESS_REGISTRAR_ACCOUNT_ID` is referenced from `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` and used to gate Ethereum-emulated base-token transfers to `EthImplicit` targets), so it is a live, reachable production contract rather than test-only scaffolding.

### Likelihood Explanation
Likelihood is moderate-to-high: any caller (user, wallet UI, or relayer) that attaches more than the exact byte-cost-derived `required_deposit` — which is easy to do since it depends on `account_id.len()` and the current `storage_byte_cost()`, both of which callers must compute exactly to avoid overpaying — will trigger this loss with no attacker action required beyond a normal `register` call. The project's own test suite (`test_register_without_deposit` in `sanity.rs`) explicitly asserts `post_tx_account_balance - pre_tx_account_balance >= deposit_amount`, i.e., the registrar's balance grows by at least the full deposit even though only the byte-cost-based `required_deposit` was actually needed, confirming this behavior is currently baked into and validated by the codebase rather than being a hypothetical edge case.

### Recommendation
Refund the excess deposit on the success path, mirroring the existing refund logic already present in the `Entry::Occupied` branch:
```rust
Entry::Vacant(entry) => {
    entry.insert(account_id);
    let refund = given_deposit.saturating_sub(required_deposit);
    if refund > NearToken::from_yoctonear(0) {
        let refund_promise = env::promise_batch_create(&env::predecessor_account_id());
        env::promise_batch_action_transfer(refund_promise, refund);
    }
    Some(address)
}
```
Alternatively, enforce strict equality (`given_deposit != required_deposit` → panic) so callers are forced to attach the exact amount, and/or add an owner-only withdrawal method for any residual balance.

### Proof of Concept
1. Compute `required_deposit` for a target `account_id` as `storage_byte_cost() * (20 + account_id.len())`.
2. Call `register(account_id)` on the deployed `AddressRegistrar` contract, attaching a deposit strictly greater than `required_deposit` (e.g., double the required amount), for an `account_id` not previously registered.
3. Observe the call succeeds (`Entry::Vacant` path), the mapping is stored, and the caller's account balance decreases by the full attached deposit while the registrar's balance increases by the full attached deposit — confirmed by the existing test `test_register_without_deposit` (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:249-276`), which asserts `post_tx_account_balance - pre_tx_account_balance >= deposit_amount` after a successful registration.
4. There is no subsequent call or admin function that can recover the excess `given_deposit - required_deposit`; it remains locked in the contract's balance indefinitely.

async fn test_register_without_deposit() -> anyhow::Result<()> {
