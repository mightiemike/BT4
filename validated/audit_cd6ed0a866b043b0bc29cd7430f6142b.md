### Title
Missing tenure-identity check in `check_nakamoto_tenure`'s `Extended` branch allows a tenure-extend block to graft onto a foreign tenure's chain tip - ([File: stackslib/src/chainstate/nakamoto/tenure.rs])

### Summary
`NakamotoChainState::check_nakamoto_tenure` validates tenure-change transactions before they are recorded via `advance_nakamoto_tenure`. For `TenureChangeCause::BlockFound`, it explicitly checks that the parent block's real tenure (`parent_tenure.tenure_id_consensus_hash`, obtained from `get_ongoing_tenure(parent_block_id)`) matches `tenure_payload.prev_tenure_consensus_hash`. For every `Extended*` cause, this equality is never checked - only the payload's own internal self-consistency (`tenure_consensus_hash == prev_tenure_consensus_hash`) is verified. This lets an attacker who once won any sortition (tenure `X`) craft a tenure-extend block that builds on the current canonical tip of an unrelated tenure `Y`, while declaring the stale tenure `X` as its identity.

### Finding Description
The broken equality is: `tenure_id_consensus_hash(parent_block)` (i.e. `NakamotoChainState::get_ongoing_tenure(&parent_block_id)?.tenure_id_consensus_hash`) must equal `tc_payload.tenure_consensus_hash` (== `self.header.consensus_hash`) for a tenure-extend block to be a legitimate continuation.

`NakamotoBlock::is_wellformed_tenure_extend_block` (stackslib/src/chainstate/nakamoto/mod.rs) only checks: [1](#0-0) 
i.e. `previous_tenure_end == parent_block_id` (block-ID equality) and `tenure_consensus_hash == prev_tenure_consensus_hash == self.header.consensus_hash` (internal self-consistency). None of these compare against the *actual* tenure that `parent_block_id` belongs to.

The DB-anchored check, `check_nakamoto_tenure`, resolves the parent's real tenure via `get_ongoing_tenure`: [2](#0-1) 
and then branches on `cause`: [3](#0-2) 
Only the `BlockFound` arm compares `parent_tenure.tenure_id_consensus_hash` against the payload's declared tenure lineage (line 779-787). The `Extended*` arm (lines 789-805) checks only `tenure_payload.tenure_consensus_hash == tenure_payload.prev_tenure_consensus_hash`, a self-referential check the attacker fully controls, and never re-validates it against `parent_tenure.tenure_id_consensus_hash`. The subsequent `tenure_len` check only reads `height_in_tenure` off the parent block's row and is independent of tenure identity: [4](#0-3) 
The returned `parent_tenure` is discarded by the caller `advance_nakamoto_tenure`, which only checks for `None`: [5](#0-4) 

**Attacker's exact input:** the attacker (any single miner slot who has won at least one past sortition, tenure `X`) builds a block `E` with:
- `E.header.parent_block_id = B`, a block belonging to a different, currently-canonical tenure `Y` (any block they did not mine and do not own the tenure of).
- `tc_payload.cause = Extended`, `tenure_consensus_hash = X`, `prev_tenure_consensus_hash = X`, `previous_tenure_end = B`.
- `previous_tenure_blocks` set to `B`'s known `height_in_tenure` (public data).
- `E.header.consensus_hash = X` (self-signed with the attacker's own valid leader/miner key for sortition `X`, since `X` is a real historical sortition win, so `check_valid_consensus_hash` and block-signature checks against `X`'s leader key both pass).

**Why existing guards fail:** `check_valid_consensus_hash` only verifies `X` is *some* canonical sortition, not that it is the sortition that produced `B`'s tenure. `check_tenure_continuity` is not invoked for tenure-change blocks (only for continuation blocks lacking any `TenureChange` tx). The `BlockFound` arm's identity check is skipped entirely for `Extended*` causes. As a result, `check_nakamoto_tenure` returns `Ok(Some(parent_tenure))` (tenure `Y`'s event record) even though the payload declares tenure `X`, and `advance_nakamoto_tenure` inserts a `nakamoto_tenure_events` row claiming tenure `X` extends onto a block that actually belongs to tenure `Y`, using `Y`'s current `coinbase_height`/tenure-length bookkeeping under `X`'s tenure id.

### Impact Explanation
This is an invalid block being accepted network-wide: a tenure-extend block that grafts a stale/foreign tenure identity onto the canonical tip of a different tenure passes deterministic validation on every honest node identically. Consequences include: (1) the attacker obtains a fresh execution budget for tenure `X` on top of the current chain tip without having won the current sortition, letting a minority/one-slot miner inject extra blocks under a mismatched tenure budget; (2) tenure/coinbase-height bookkeeping (`nakamoto_tenure_events`, `get_matured_miner_reward_schedules`, `calculate_scheduled_tenure_reward`) becomes associated with the wrong tenure lineage, risking miscomputed matured miner rewards. Because all honest nodes apply the same faulty deterministic logic, this does not directly split honest nodes from each other, but it does constitute acceptance of a block that should be rejected by `check_nakamoto_tenure`/`TENURE_REWARD` semantics, with downstream risk to reward accounting integrity.

### Likelihood Explanation
Preconditions: the attacker only needs to have won a single past sortition (holding a minority/one miner slot, entirely within the stated attacker capability) to obtain a valid `consensus_hash` `X` with a legitimate leader key, and be able to observe the current canonical tip `B` and its `height_in_tenure` (both public). No majority stake, no other party's key, and no privileged role are required. This is repeatable by any single miner who has ever won one sortition, at any point after their tenure has been superseded by a sibling fork.

### Recommendation
In `check_nakamoto_tenure`'s `Extended*` branch (stackslib/src/chainstate/nakamoto/tenure.rs, ~lines 789-805), add the same identity check used in the `BlockFound` branch: require `parent_tenure.tenure_id_consensus_hash == tenure_payload.tenure_consensus_hash` (equivalently `== prev_tenure_consensus_hash`) before accepting the tenure-extend, rejecting the transaction/block otherwise.

### Proof of Concept
Rust integration test plan (two-fork harness, e.g. extending `stackslib/src/chainstate/nakamoto/tests/mod.rs` fork-processing tests):
1. Build a chain with two sibling tenures `X` and `Y` off a common ancestor (`X` mined by attacker-controlled miner key, `Y` mined by a different miner), making `Y` the canonical tip at block `B`.
2. Construct a tenure-extend `NakamotoBlock` `E` with `header.parent_block_id = B`, `header.consensus_hash = X`, `tc_payload = TenureChangePayload { cause: Extended, tenure_consensus_hash: X, prev_tenure_consensus_hash: X, previous_tenure_end: B, previous_tenure_blocks: height_in_tenure(B), .. }`, signed with `X`'s miner key.
3. Assert before/after equality: `NakamotoChainState::get_ongoing_tenure(&mut conn, &B)?.unwrap().tenure_id_consensus_hash == E.header.consensus_hash` should be `false` (X ≠ Y).
4. Call `NakamotoChainState::check_nakamoto_tenure(&mut headers_conn, &mut sort_handle, &E.header, &tc_payload)` and assert it returns `Ok(None)` (current buggy behavior returns `Ok(Some(_))`), and/or call `advance_nakamoto_tenure`/full `append_block` and assert it returns `Err(ChainstateError::InvalidStacksTransaction(..))` instead of succeeding.
