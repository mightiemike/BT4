### Title
Cross-fork/cross-time state corruption via stale `partitioned_stake_reward.inflation.stake` merged with a live-but-mutated stake account in `build_updated_stake_reward` - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
`build_updated_stake_reward` merges a `PartitionedStakeReward` computed once at epoch-boundary calculation time with whatever `StakeAccount<Delegation>` is *currently* present in the live `stakes_cache` at the moment each distribution block executes, potentially many blocks later. Because a normal stake-account owner can deactivate an activating (not-yet-effective) delegation instantly and withdraw/reuse the same pubkey before their partition's distribution block runs, the function can either write a corrupted hybrid account (current `meta`/`flags` + stale calculated `delegation`) or deterministically panic every validator via its `assert_eq!` consistency check.

### Finding Description
The reward pipeline separates *calculation* and *distribution* into two different points in time/blocks:

- At calculation time, `calculate_stake_rewards_and_commissions` builds `PartitionedStakeReward` entries (including zero-value entries for “just activated” delegations that skip reward payout) from a `stakes_cache` snapshot taken at the epoch boundary: [1](#0-0) .
- These entries are hashed into partitions and distributed one partition per block over `distribution_starting_block_height..` blocks. Each such block calls `store_stake_accounts_in_partition`, which re-reads the **live, current-fork** `stakes_cache` at that later block, not the calculation-time snapshot: [2](#0-1) .
- `build_updated_stake_reward` then looks up the stake account solely by pubkey in this live cache, clones whatever it finds, and merges the **current** `meta`/`flags` with the **stale, pre-computed** `new_stake = partitioned_stake_reward.inflation.stake`: [3](#0-2) .
- The only consistency check is a hard `assert_eq!` comparing the *current* account's `stake.delegation.stake` plus the calculated `stake_reward` against the *stale* calculated `new_stake.delegation.stake`, and it only runs when `adjust_delegations_for_rent` is false; it never checks `voter_pubkey`, `activation_epoch`, or any generation/version identity: [4](#0-3) .

An unprivileged stake owner can change the live state of their own stake pubkey between calculation and their assigned distribution block without breaking any existing guard, because the Solana stake program allows instant deactivation/withdrawal of stake that is still "activating" (not yet effective) — demonstrated by CLI test flow: delegate → deactivate → withdraw all succeeding immediately: [5](#0-4) [6](#0-5) . Such a freshly-activated delegation is exactly the case that yields a zero-reward `PartitionedStakeReward` entry still queued for distribution (the `(_, None)` branch, "JustActivated"): [1](#0-0) .

The attacker can compute in advance which block/partition their pubkey lands in via `hash_rewards_into_partitions` and the (public) `parent_blockhash`, then, before that block, withdraw the stake (closing/rewriting the pubkey) and re-delegate a completely different `Stake` payload (different `voter_pubkey`, `activation_epoch`, `delegation.stake`) at the same pubkey. When the delayed distribution block runs `store_stake_accounts_in_partition`, `stakes_cache_accounts.get(&pubkey)` returns this new, unrelated delegation, and `build_updated_stake_reward` splices the old calculated `new_stake` (from the closed delegation) onto it — either failing the `assert_eq!` (deterministic validator panic across the whole cluster on that fork) or, in the `adjust_delegations_for_rent=true` path, silently producing an account whose on-chain `StakeStateV2::Stake` fields (voter, activation epoch, stake amount) are inconsistent with its real lamport balance and history, since `adjust_delegation_for_rent` only patches lamports/stake-amount math, not identity fields like `voter_pubkey`.

### Impact Explanation
Two concrete outcomes are reachable purely by an unprivileged user through ordinary stake instructions (`DelegateStake`, `DeactivateStake`, `Withdraw`, `DelegateStake` again) with no validator/leader control needed:
1. A deterministic `assert_eq!` panic in `build_updated_stake_reward`/`store_stake_accounts_in_partition`, hit identically by every node replaying the same fork — a consensus-halting crash.
2. Silent write of an inconsistent `StakeStateV2::Stake` (wrong `voter_pubkey`/`activation_epoch` merged with unrelated reward/lamport deltas) into `stakes_cache`/accounts DB, causing stale/wrong-version state to be treated as authoritative for subsequent epoch activation-stake accounting and hashing/capitalization.

This matches the "load returns wrong version" / stale-calculation-applied-to-diverged-account class in scope, escalating to a cluster-wide validator panic, which is a critical consensus/liveness impact caused by ordinary account operations, not a crafted snapshot or privileged action.

### Likelihood Explanation
Feasible with a single account owner acting alone: delegate stake (activating), wait for epoch-boundary calculation to run (queues a zero-value or later a real reward entry keyed by pubkey), compute the target distribution block via the public partitioning hash, then deactivate/withdraw/redelegate before that block executes. No cooldown blocks this specific window because "activating" (not-yet-effective) stake can be deactivated/withdrawn immediately, as shown by existing CLI integration tests. This is reproducible deterministically and repeatably by any user controlling their own keys/timing.

### Recommendation
`build_updated_stake_reward`/`store_stake_accounts_in_partition` must not merge stale calculation-time reward deltas into whatever account currently occupies the pubkey. Bind the calculated reward to an identity/version captured at calculation time (e.g., store and re-check `voter_pubkey`, `activation_epoch`, and/or a snapshot of the full pre-reward `Stake`/`Meta` at calculation time) and require it to match the live account before applying rewards; on mismatch, treat as `DistributionError` (burn reward, log) rather than merging fields or hitting a hard `assert_eq!`. Replace the `assert_eq!` with a recoverable `Result` error path so a legitimate account divergence cannot crash the validator.

### Proof of Concept
Integration test outline (adapt to existing `apply_epoch_operations`/`create_default_reward_bank` test harness used in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`):
1. Create bank, create stake account `S`, delegate to vote account `A` in epoch `N` (so it is "activating" and yields a zero-value `PartitionedStakeReward` for epoch `N`).
2. Advance to epoch `N+1` so calculation runs and queues the zero-value reward entry for `S`'s pubkey, capturing `distribution_starting_block_height` and partition index for `S`.
3. Before the block corresponding to `S`'s partition is processed, submit (in the same test bank/fork) `DeactivateStake` + `Withdraw` for `S`, then `CreateAccount`/`Initialize`/`DelegateStake` for the same pubkey to vote account `B` with a different `delegation.stake`.
4. Advance the bank to the distribution block for `S`'s partition and call `store_stake_accounts_in_partition`.
5. Assert either: (a) the process panics on the `assert_eq!` at `distribution.rs:289-293` (demonstrating the consensus-crash class), or with `adjust_delegations_for_rent=true`, (b) the stored `StakeStateV2::Stake` for pubkey `S` has `voter_pubkey == A` (stale) while `account.lamports()`/real history reflect delegation to `B`, proving a corrupted hybrid state rather than a clean error or consistent post-image.
