### Title
Stale global class cache serves undeclared Cairo 0 classes after a chain reorg/revert, with no re-validation against current state - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` explicitly re-validates Cairo 1 classes served from the process-global `RawClassCache` against the current declared-class state (to guard against exactly the scenario where "it might contain a declared class from a reverted block"), but performs **no such re-validation for Cairo 0 (`RunnableCompiledClass::V0`)** classes. This is the same bug class as CVE-2023-4046: a stale value in a long-lived, cross-execution global cache is trusted without re-checking it is still consistent with current program/chain state, leading to incorrect execution results.

### Finding Description
`get_compiled_from_class_manager` reads from `ContractClassManager`'s `RawClassCache`, which is a **process-global, cross-block** LRU cache (`starknet_api::class_cache::GlobalContractCache`, backed by a `Mutex<SizedCache<ClassHash, T>>`), shared across all blocks executed by the node process: [1](#0-0) 

When serving a cached class, the code branches on class version: [2](#0-1) 

For non-V0 (Cairo 1) classes it calls `self.state_reader.is_declared(class_hash)` and rejects the cached entry if the class is no longer declared in the *current* chain state — the comment states this exists precisely because "existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)". For `RunnableCompiledClass::V0(_)`, however, this branch is a no-op — the cached class is returned unconditionally, with no re-check against current declaration state.

This gap exists because `FetchCompiledClasses::is_declared` is documented to always return `false` for Cairo 0 classes: [3](#0-2) 

So the API used to guard V1 classes cannot be used to guard V0 classes at all — leaving V0 classes structurally unprotected against staleness once cached, for the lifetime of the process (or until LRU eviction).

Concretely: if a Cairo 0 class is declared, gets executed at least once (causing `set_and_compile` to populate the global cache), and the containing block is later reverted (e.g. via `apollo_reverts::revert_block`, which reverts headers, bodies, and state diffs including declared classes): [4](#0-3) 
the on-chain/state-reader view of that class hash reverts to "undeclared", but the in-memory `RawClassCache` entry for that class hash is untouched and keeps returning the fully executable compiled class on any subsequent `get_compiled_class` call — indefinitely, for any transaction that references that class hash (e.g., `deploy`/`library_call`/`invoke` referencing it), without a fresh declare.

### Impact Explanation
Two sequencer nodes that reached the same logical chain state through different histories (one that executed-then-reverted the class locally and thus retains a warm cache entry, vs. one that synced fresh state without ever populating the cache, e.g. after a restart or fresh sync) will diverge in behavior for a transaction referencing the "undeclared" class hash: one accepts and executes it (returning a stale-but-cached compiled class, producing state changes/fees/events), the other correctly rejects it with `UndeclaredClassHash`. This produces different transaction execution results, different state diffs, and ultimately different computed state roots/block hashes between otherwise-honest nodes for the same block — a consensus/re-execution divergence, matching the "honest-node divergence" and "wrong committed root" impact categories in scope. The same stale entry also lets a class that should be permanently gone remain executable, which is a form of unauthorized/incorrect account action.

### Likelihood Explanation
The trigger requires: (1) a block containing a Cairo 0 `Declare`(V0/V1 with V0 class) plus execution of that class, and (2) a subsequent revert of that block (a normal, non-malicious-operator operation performed by sequencer/consensus tooling in response to L1 reorgs or block-building faults), followed by (3) any ordinary, unprivileged transaction that references the now-undeclared class hash. None of these steps require special privilege beyond normal transaction submission; the revert itself is an existing operational code path, not attacker-controlled, but its consequence (permanently-stale V0 cache) is directly reachable and exploitable by any subsequent unprivileged transaction sender. Likelihood is Medium: it requires a revert event to occur, which is not attacker-triggerable on demand, but once it occurs the divergence is deterministic and exploitable by anyone.

### Recommendation
Extend the re-validation performed for Cairo 1 classes to Cairo 0 classes as well. Concretely:
- Change `FetchCompiledClasses::is_declared` (or add a parallel method) to support checking declaration status for Cairo 0 class hashes too (rather than being defined to always return `false` for them), and call it in the `RunnableCompiledClass::V0(_)` branch of `get_compiled_from_class_manager`, mirroring the existing Cairo 1 logic.
- Alternatively, invalidate/clear the relevant `RawClassCache` entries as part of `revert_block` (or any state-reverting code path) so that stale global cache entries cannot outlive the state they were derived from, for both Cairo 0 and Cairo 1 classes.

### Proof of Concept
1. Node A (long-running process) executes block N containing `Declare` of Cairo 0 class `C` and a transaction invoking `C`, causing `ContractClassManager::set_and_compile(C, CompiledClasses::V0(...))` to populate the global `RawClassCache`: [5](#0-4) 
2. Block N is reverted via `revert_block`, which reverts the state diff (including the declaration of `C`) in storage: [4](#0-3) 
3. Node A's `state_reader.is_declared(C)` would now report `false` for Cairo 1, but this check is never invoked for Cairo 0 classes.
4. A new transaction (from any unprivileged sender) that references class hash `C` (e.g., a deploy or library call) hits `get_compiled_from_class_manager`, matches the `RunnableCompiledClass::V0(_)` branch, skips validation entirely, and returns the stale cached compiled class as if it were still declared: [6](#0-5) 
5. Node B, which never cached `C` (fresh sync/restart after the revert), calls `state_reader.get_compiled_classes(C)` and correctly returns `UndeclaredClassHash` for the same transaction, diverging from Node A's accepted execution.

Note: I was unable to fully trace every caller of `revert_block` to confirm exactly which operational flows can trigger it in production (vs. purely CLI/administrative tooling), which affects the precise likelihood assessment; a Devin session with full-repo access could confirm this via `apollo_reverts` callers across the codebase.
