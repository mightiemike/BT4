### Title
Unbounded full-table scan of `AssetIssueStore` on every call to `getAssetIssueByAccount` allows QPS-bounded but size-unbounded CPU/IO amplification - (File: `framework/src/main/java/org/tron/core/services/http/GetAssetIssueByAccountServlet.java`)

### Summary
`GetAssetIssueByAccountServlet.doGet`/`doPost` calls `Wallet.getAssetIssueByAccount`, which loads the *entire* asset-issue table via `getAllAssetIssues()` and then filters in Java for every single request, with no pagination, cache, or secondary index by owner address. The endpoint has no per-servlet rate-limit override, so it falls back to the default `DefaultBaseQqsAdapter`/`QpsStrategy` at `qps=1000`, meaning per-request cost (an O(N) DB scan where N = total asset issues on-chain) is not accounted for by the rate limiter at all.

### Finding Description
`GetAssetIssueByAccountServlet.fillResponse` calls `wallet.getAssetIssueByAccount(address)` directly from `doGet`/`doPost`: [1](#0-0) 

`Wallet.getAssetIssueByAccount` unconditionally calls `getAllAssetIssues()` on the underlying store and then does an in-memory `filter` over the full list to find matches for the requested address: [2](#0-1) 

`AssetIssueStore.getAllAssetIssues()` performs a full iterator scan over the entire RocksDB/LevelDB column, with no pagination and no filtering pushed down to the DB layer: [3](#0-2) 

This is unlike `Wallet.getAssetIssueList(offset, limit)`, which uses `getAssetIssuesPaginated`, showing pagination support already exists in the store but is not used by this particular endpoint: [4](#0-3) 

On the rate-limiting side, since `GetAssetIssueByAccountServlet` has no entry in the `rate.limiter.http` config list, `RateLimiterServlet.addRateContainer` falls back to `DEFAULT_ADAPTER_NAME` (`DefaultBaseQqsAdapter`) with `QpsStrategy.DEFAULT_QPS_PARAM`: [5](#0-4) 

That default QPS comes from `Args.getInstance().getRateLimiterGlobalApiQps()`, which defaults to `1000` per `reference.conf`: [6](#0-5) [7](#0-6) 

Critically, this `QpsStrategy`/`DefaultBaseQqsAdapter` limiter is a token-bucket keyed purely on *request count*, with a flat token cost of 1 per call regardless of the size of the resulting DB scan: [8](#0-7)  There is no accounting mechanism that scales the "cost" of a request with the number of asset issues currently stored on-chain (`N`). As `N` grows (asset issues can be created by any account paying the asset-issue fee via `AssetIssueContract`), the per-request DB/CPU cost of `getAllAssetIssues()` grows linearly, while the rate limiter continues to permit up to 1000 such calls per second system-wide. Total node-wide cost is therefore `O(qps × N)`, unbounded in `N`, even though the attacker pays no incremental fee per HTTP call (HTTP APIs are free, unauthenticated, and not part of any on-chain fee/replay/settlement path).

### Impact Explanation
An unprivileged remote attacker can repeatedly call `/walletsolidity/getassetissuebyaccount` (or the fullnode/gRPC-backed HTTP equivalent) with any address, forcing the node to repeatedly deserialize and scan the entire `asset-issue` store (bounded by `ASSET_ISSUE_COUNT_LIMIT_MAX` only in the paginated variant, not here) on every call. At realistic mainnet-scale asset counts and up to 1000 qps (the unmodified default), this can saturate node CPU/IO, increasing HTTP service latency and potentially degrading block processing/sync latency on the affected FullNode/SolidityNode, which is a liveness-degradation risk for the node (not the whole network, since each node enforces this independently, but it affects any node an attacker targets, e.g. public API nodes relied upon by wallets/exchanges).

### Likelihood Explanation
The precondition is only that the node exposes the default HTTP API surface with no explicit `rate.limiter.http` override for `GetAssetIssueByAccountServlet` (the shipped default, per `reference.conf`'s commented-out example list) — a very common production condition. No authentication, fee payment, or special privilege is required; a single unprivileged HTTP client can trigger this repeatedly and cheaply. The attack is fully repeatable and scales with the number of asset issues already existing on the target chain (which an attacker could even inflate by issuing many low-cost `AssetIssueContract`s themselves, though this is not strictly required on a live network with many existing tokens).

### Recommendation
- Add owner-address-indexed lookup (secondary index keyed by owner address) instead of scanning all asset issues on every `getAssetIssueByAccount` call, mirroring the pagination pattern already used by `getAssetIssuesPaginated`.
- Alternatively/additionally, add a per-endpoint rate limit override for `GetAssetIssueByAccountServlet` in `reference.conf`'s `rate.limiter.http` list (e.g., a low `IPQPSRateLimiterAdapter` qps), and consider a `GlobalPreemptibleAdapter` concurrency cap for scan-heavy endpoints.
- Longer-term: make the rate limiter cost-aware for known O(N) endpoints (e.g., weight the token cost by store size or cap `N` scanned per call), consistent with the `ASSET_ISSUE_COUNT_LIMIT_MAX` pattern already applied to `getAssetIssuesPaginated`.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/services/http/GetAssetIssueByAccountScanCostTest.java
// Goal: demonstrate per-request DB scan cost grows linearly with total asset-issue
// count while the servlet's rate limiter cost stays flat (1 token per call).

@Test
public void perRequestScanCostGrowsWithStoreSizeRegardlessOfRateLimiterCost() {
  // 1. Seed AssetIssueStore with N=100_000 AssetIssueCapsule entries with distinct
  //    owner addresses (only 1 matches the queried address).
  seedAssetIssues(100_000);

  // 2. Measure wall-clock / DB-read count for wallet.getAssetIssueByAccount(address)
  long startReads = dbReadCounter.get();
  long t0 = System.nanoTime();
  wallet.getAssetIssueByAccount(ByteString.copyFromUtf8(targetAddress));
  long elapsedSmallN = System.nanoTime() - t0;
  long readsSmallN = dbReadCounter.get() - startReads;

  // 3. Re-seed to N=1_000_000 and repeat measurement.
  seedAssetIssues(1_000_000);
  startReads = dbReadCounter.get();
  t0 = System.nanoTime();
  wallet.getAssetIssueByAccount(ByteString.copyFromUtf8(targetAddress));
  long elapsedLargeN = System.nanoTime() - t0;
  long readsLargeN = dbReadCounter.get() - startReads;

  // Assert cost scales ~linearly with N (i.e., NOT bounded per request) —
  // this demonstrates the underpriced-work property, since the HTTP
  // rate limiter (QpsStrategy) always charges exactly 1 token per call
  // regardless of readsSmallN/readsLargeN.
  assertTrue("expected DB reads to scale with store size",
      readsLargeN > readsSmallN * 5);

  // 4. Confirm the rate limiter's per-call cost is constant (1 permit)
  //    irrespective of N, by asserting QpsStrategy.tryAcquire() consumes
  //    exactly one token per invocation regardless of scan size.
  QpsStrategy strategy = new QpsStrategy("qps=1000");
  for (int i = 0; i < 1000; i++) {
    assertTrue(strategy.tryAcquire());
  }
  assertFalse(strategy.tryAcquire()); // bucket exhausted at exactly 1000,
                                       // independent of N — proving cost
                                       // accounting is size-blind.
}
```
Expected result: DB read/scan cost per request increases proportionally with `N` while the rate-limiter token cost remains fixed at 1 per call, confirming that up to `qps` (default 1000) full O(N) scans per second can be forced by an unauthenticated caller, with total system cost unbounded in `N`.

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {

  }
