## Finding

### Title
`verify_snapshot_bank` continues expensive clean/shrink/hash-verify work after accounts lt-hash verification already failed - (File: `runtime/src/bank.rs`)

### Summary
`Bank::verify_snapshot_bank` runs four sequential, independently-costly verification/maintenance steps — accounts lt-hash verification, `clean_accounts`, `shrink_all_slots`, and `verify_hash` — and only combines their pass/fail results at the very end. If the very first step (`verify_accounts`) already fails, meaning the snapshot is already known to be invalid, the function still performs the full `clean_accounts` scan, the full `shrink_all_slots` pass over every storage, and a second full-index hash recomputation before returning `false`. This mirrors the reported bug class of not reverting/aborting on the first failed step, wasting significant CPU and I/O.

### Finding Description
`verify_snapshot_bank` is called once per snapshot load (from `bank_from_snapshot_archives` and `bank_from_snapshot_dir`) to validate a freshly reconstructed bank against the trusted snapshot metadata: [1](#0-0) 

```rust
pub fn verify_snapshot_bank(
    &self,
    skip_shrink: bool,
    force_clean: bool,
    latest_full_snapshot_slot: Slot,
    calculated_accounts_lt_hash: Option<&AccountsLtHash>,
) -> bool {
    let (verified_accounts, verify_accounts_time_us) = measure_us!({ ... self.verify_accounts(...) ... });
    let (_, clean_time_us) = measure_us!({ ... self.rc.accounts.accounts_db.clean_accounts(...) ... });
    let (_, shrink_time_us) = measure_us!({ ... self.rc.accounts.accounts_db.shrink_all_slots(...) ... });
    let (verified_bank, verify_bank_time_us) = measure_us!(self.verify_hash());
    ...
    verified_accounts && verified_bank
}
```

`verified_accounts` is computed first by `verify_accounts`, which (when no precomputed lt hash is supplied) walks the *entire* accounts index and recomputes the accounts lattice hash from scratch: [2](#0-1) 

That result is only combined with `verified_bank` (from `verify_hash`, itself another full `hash_internal_state` recomputation) in the final `verified_accounts && verified_bank` expression. There is no early return or short-circuit: even when `verified_accounts` is already `false`, the function unconditionally proceeds to call:
- `clean_accounts` — a full parallel scan/reclaim pass over all dirty stores and candidate pubkeys (`accounts-db/src/accounts_db.rs`, `clean_accounts`), and
- `shrink_all_slots` — a full pass compacting every storage slot in the account paths (`accounts-db/src/accounts_db.rs`, `shrink_all_slots`), and
- `verify_hash` — another expensive hash computation.

These three steps are independent of whether the accounts lt hash already mismatched; their outcome cannot change the already-determined `false` result of the boolean AND. This is analogous to the reported pattern of combining several verification steps via bitwise/boolean AND while allowing all of them to execute even after an earlier step is already known to make the overall verification fail.

### Impact Explanation
This is called on every validator/ledger-tool startup that loads from a snapshot (`bank_from_snapshot_archives`/`bank_from_snapshot_dir`), which is a routine, unprivileged, honest-node code path. Whenever the accounts lt hash fails to verify (e.g., after a code bug, disk corruption, or interrupted flush that leaves an inconsistent-but-loadable snapshot), the node needlessly performs:
- a full `clean_accounts` scan/reclaim across the whole accounts index and dirty stores, and
- a full `shrink_all_slots` compaction pass over every stored slot, and
- a second full accounts-hash / bank-hash recomputation,

all of which is disproportionate CPU and disk I/O cost for a run that is already guaranteed to fail and `panic!("Snapshot bank for slot {} failed to verify", ...)` immediately afterward at the call site. On large validators with terabytes of account state, `clean_accounts` and `shrink_all_slots` are among the most expensive operations in the codebase, so this wasted work can significantly delay detection of the failure and consume disproportionate resources before the node ultimately panics anyway.

### Likelihood Explanation
This code path executes on every snapshot load that reaches `verify_snapshot_bank` with `skip_shrink=false`/`force_clean=true` conditions satisfied, which is the default at startup from a downloaded/archived snapshot. Triggering the wasted work only requires the accounts lt-hash verification to fail first, which is a legitimate consistency-verification failure mode (not requiring a maliciously crafted snapshot) — e.g., due to bugs elsewhere in generate_index/index-consistency, or genuine data corruption caught by verification. No attacker action or elevated privileges are needed; it's purely a resource-wasting inefficiency on an honest node's own verification flow.

### Recommendation
Short-circuit `verify_snapshot_bank` on the first failure: check `verified_accounts` immediately after computing it and skip `clean_accounts`, `shrink_all_slots`, and `verify_hash` if it is already `false`, returning early with `false` (while still logging appropriately). This preserves correctness (the overall result would be `false` regardless) while avoiding unnecessary CPU/I/O expenditure before the eventual panic.

### Proof of Concept
1. Construct or corrupt a snapshot such that the stored `accounts_lt_hash` does not match the accounts actually present (e.g., by manually mutating account data post-serialization, or via a hypothetical index-generation bug).
2. Load the snapshot via `bank_from_snapshot_archives`/`bank_from_snapshot_dir`, which calls `bank.verify_snapshot_bank(...)`.
3. Observe that `verify_accounts` fails (logs "Verifying accounts failed: accounts lattice hashes do not match..."), yet the function still proceeds to execute `clean_accounts`, `shrink_all_slots`, and `verify_hash` (visible via the `clean_us`/`shrink_us`/`verify_bank_us` datapoints in `verify_snapshot_bank`) before the caller panics with "Snapshot bank for slot {} failed to verify".     pub fn verify_snapshot_bank(
        &self,
        skip_shrink: bool,
        force_clean: bool,
        latest_full_snapshot_slot: Slot,
        calculated_accounts_lt_hash: Option<&AccountsLtHash>,
    ) -> bool {
        let (verified_accounts, verify_accounts_time_us) = measure_us!({
            let should_verify_accounts = !self.rc.accounts.accounts_db.skip_initial_hash_calc;
            if should_verify_accounts {
                self.verify_accounts(calculated_accounts_lt_hash)
            } else {
                info!("Verifying accounts... Skipped.");
                true
            }
        });

        let (_, clean_time_us) = measure_us!({
            let should_clean = force_clean || (!skip_shrink && self.slot() > 0);
            if should_clean {
                info!("Cleaning...");
                // We cannot clean past the latest full snapshot's slot because we are about to
                // perform an accounts hash calculation *up to that slot*.  If we cleaned *past*
                // that slot, then accounts could be removed from older storages, which would
                // change the accounts hash.
                self.rc
                    .accounts
                    .accounts_db
                    .clean_accounts(Some(latest_full_snapshot_slot), true);
                info!("Cleaning... Done.");
            } else {
                info!("Cleaning... Skipped.");
            }
        });

        let (_, shrink_time_us) = measure_us!({
            let should_shrink = !skip_shrink && self.slot() > 0;
            if should_shrink {
                info!("Shrinking...");
                self.rc.accounts.accounts_db.shrink_all_slots(
                    true,
                    // we cannot allow the snapshot slot to be shrunk
                    Some(self.slot()),
                );
                info!("Shrinking... Done.");
            } else {
                info!("Shrinking... Skipped.");
            }
        });

        info!("Verifying bank...");
        let (verified_bank, verify_bank_time_us) = measure_us!(self.verify_hash());
        info!("Verifying bank... Done.");

        datapoint_info!(
            "verify_snapshot_bank",
            ("clean_us", clean_time_us, i64),
            ("shrink_us", shrink_time_us, i64),
            ("verify_accounts_us", verify_accounts_time_us, i64),
            ("verify_bank_us", verify_bank_time_us, i64),
        );

        verified_accounts && verified_bank
    }
