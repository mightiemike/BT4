## Finding: Unauthenticated `write_set` field in backup/restore transaction chunks lets a malicious backup source bind an arbitrary `WriteSet` to a cryptographically-verified `TransactionInfo`

### Summary
The backup/restore pipeline verifies transactions, events, and transaction-info hashes against an epoch-signed `LedgerInfo` via accumulator proofs, but never validates the `write_set` field that is read alongside them from the backup chunk file. This write set is passed unchecked into `restore_utils::save_transactions` → `WriteSetDb::put_write_set`, and is also fed into KV replay to build the persisted state tree, while the accumulator/ledger only ever commits to the state-change hash of the *original* (verified) write set carried in `TransactionInfo`.

### Finding Description
`LoadedChunk::load` in `storage/backup/backup-cli/src/backup_types/transaction/restore.rs` deserializes `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, Vec<ContractEvent>, WriteSet)` tuples straight from a backup file and pushes the `WriteSet` into a separate `write_sets` vector: [1](#0-0) 

It then builds a `TransactionListWithProofV2` from `txns`, `event_vecs`, `txn_infos`, and the range proof — deliberately **excluding** `write_sets` — and verifies that structure against the epoch-verified `ledger_info`: [2](#0-1) 

`TransactionListWithProof::verify` only checks transaction hashes against `txn_info.transaction_hash()`, event root hashes against `txn_info.event_root_hash()`, and the accumulator proof — it never touches `write_set`/`state_change_hash`: [3](#0-2) 

By contrast, `TransactionOutputListWithProof::verify` (used by the normal fullnode-to-fullnode sync path) explicitly checks `txn_info.state_change_hash() == CryptoHash::hash(&txn_output.write_set)`: [4](#0-3) 

That check is absent from the backup/restore path. The verified-but-write-set-blind chunk is then passed to `restore_handler.save_transactions` / `restore_utils::save_transactions_impl`, which independently commits `txn_infos` to the accumulator via `put_transaction_accumulator` and commits `write_sets` to `WriteSetDb::put_write_set` — with no cross-check that the two correspond: [5](#0-4) 

The accumulator leaf hash committed for that version is `txn_info.hash()`, which is derived from `state_change_hash` computed from the *original* correct write set: [6](#0-5) [7](#0-6) 

If `kv_replay` is enabled, the same unverified `write_sets` are also applied to build the persisted Jellyfish-Merkle state via `state_store.calculate_state_and_put_updates`, meaning the actual state tree/root can be corrupted, not just the `WriteSetDb` column family: [8](#0-7) 

### Impact Explanation
A backup manifest/chunk file is provided by `BackupStorage`, which the code base's own documentation states is intentionally treated as untrusted content whose authenticity should come entirely from cryptographic proofs (accumulator range proof + epoch-signed `LedgerInfo`), not from trust in the storage backend: [9](#0-8) 

Because the `write_set` bytes in the chunk file bypass that verification entirely, an attacker who controls (or can tamper with) the backup storage content can substitute an arbitrary `WriteSet` for any transaction while leaving `TransactionInfo`/`Transaction`/events genuine and provable. After restore:
- `WriteSetDb::get_write_set`/`get_write_sets` and any API/debugging path built on them return a `WriteSet` that the accumulator-bound `TransactionInfo.state_change_hash()` never actually authenticates — the write-set-to-transaction-info binding at that version is broken.
- With `kv_replay`, the bogus write set is applied to the state tree, producing a state root/state values that diverge from what honest validators computed, i.e., hard-fork-only divergence between the restored node and the rest of the network.
- Later, when a client fetches that version's output *with proof* (`TransactionOutputListWithProof::verify`), verification will correctly fail on the `state_change_hash` mismatch, but by then the corrupted `WriteSetDb`/state entry is already persisted and any code path that trusts local storage without re-verifying the proof (debug tools, indexer, direct `get_write_set` calls) is fed corrupted data.

### Likelihood Explanation
This requires the restoring node to pull transaction chunks from a backup store the attacker can tamper with (e.g., a compromised or malicious third-party backup bucket) — a scenario the accumulator-proof design in `manifest.rs` was explicitly built to defend against. No consensus/validator compromise is needed; only control over the bytes served by `BackupStorage::open_for_read`/`load_bcs_file` for the chunk's transaction record file.

### Recommendation
In `LoadedChunk::load`, after deserializing each `(txn, aux_info, txn_info, events, write_set)` record, verify `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` before accepting the chunk (mirroring the check already present in `TransactionOutputListWithProof::verify`), or include the write sets inside the object verified by `txn_list_with_proof.verify(...)`.

### Proof of Concept
1. Take a legitimate transaction backup chunk file containing valid `(Transaction, TransactionInfo, Events, WriteSet)` records and a valid `(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)`.
2. Replace the `WriteSet` bytes of one record with a different, structurally valid `WriteSet` (leave `Transaction`/`TransactionInfo`/events untouched).
3. Point `TransactionRestoreController`/`aptos-db-tool` backup restore at storage serving this tampered chunk.
4. Observe `LoadedChunk::load` succeeds (`txn_list_with_proof.verify(...)` only checks txn hash/events, not write_set), and `restore_handler.save_transactions` persists the tampered `WriteSet` via `WriteSetDb::put_write_set` at that version while `put_transaction_accumulator` commits the original `TransactionInfo` hash.
5. Confirm `db.ledger_db.write_set_db().get_write_set(version)` returns the tampered write set, while `CryptoHash::hash(&tampered_write_set) != txn_info.state_change_hash()` — reproducing the assertion used in `execution/executor/tests/db_bootstrapper_test.rs::assert_committed_write_set_version` (which would now fail) and demonstrating that a subsequent `TransactionOutputListWithProof::verify` on this version fails.

        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }

    /// Saves a batch of txn_info hashes starting from `first_version` in accumulator.
    pub fn put_transaction_accumulator(
        &self,
        first_version: Version,
        txn_infos: &[impl Borrow<TransactionInfo>],
        transaction_accumulator_batch: &mut SchemaBatch,
    ) -> Result<HashValue> {
        let txn_hashes: Vec<HashValue> = txn_infos.iter().map(|t| t.borrow().hash()).collect();

        let (root_hash, writes) = Accumulator::append(
            self,
            first_version, /* num_existing_leaves */
            &txn_hashes,
        )?;
        writes.iter().try_for_each(|(pos, hash)| {
            transaction_accumulator_batch.put::<TransactionAccumulatorSchema>(pos, hash)
        })?;

        Ok(root_hash)
    }
