### Title
Admin-disabled TokenConfig (`Enabled=false`) is never checked before minting PRC20 on inbound deposit, letting an unprivileged user keep depositing a blacklisted/frozen token - (File: `x/uexecutor/keeper/handler.go`)

### Summary
This is the closest native analog to the Sherlock M-1 pattern: a security-relevant registration/authorization flag (`isSharedVaultRegistered`/`isOperatorVaultRegistered` in the Symbiotic report, `TokenConfig.Enabled` here) is stored by the registry but the money-moving code path only checks that a config *exists* — never that it is *currently enabled* — allowing an attacker to keep exercising a resource the protocol operator explicitly disabled.

### Finding Description
`x/uregistry` stores a per-token `Enabled` boolean on `TokenConfig` (`x/uregistry/types/types.pb.go`, referenced throughout tests, e.g. [1](#0-0) ). This flag is clearly intended as an admin kill-switch for a specific token (e.g. to freeze a depegged, compromised, or otherwise unsafe asset without disabling the whole chain).

However, the only registry keeper method used on the money-moving inbound path is `GetTokenConfig`, which does a pure existence lookup and returns the config with no gating on `Enabled`: [2](#0-1) 

That config is consumed directly by `depositPRC20`, which mints/deposits PRC20 tokens for the resolved `NativeRepresentation.ContractAddress` without ever inspecting `tokenConfig.Enabled`: [3](#0-2) 

This helper is called from every inbound-deposit code path in `x/uexecutor`:
- `ExecuteInboundFundsAndPayload` (FUNDS / FUNDS_AND_PAYLOAD inbounds) [4](#0-3) 
- `ExecuteInboundGasAndPayload` (GAS_AND_PAYLOAD inbounds), which also fetches the token config purely to check existence, not enablement [5](#0-4) 
- `execute_inbound_gas.go` (GAS inbounds)

The only enable/disable gate actually enforced before execution is chain-level, in `VoteInbound`: [6](#0-5) 

That check calls `IsChainInboundEnabled`, which is a *chain*-scoped flag (`ChainConfig.Enabled.IsInboundEnabled`), not the *token*-scoped `TokenConfig.Enabled`. Nowhere in `x/uexecutor`'s vote/execute pipeline (`VoteInbound` → `ValidateForExecution` → `ExecuteInbound*`) is `TokenConfig.Enabled` consulted.

This is structurally identical to the Sherlock finding: a lookup function (`GetOperatorVotingPower`/`GetTokenConfig`) resolves an attacker-influenceable parameter (`vault`/`AssetAddr`) against a registry, validates only a shallow property (`isTokenRegistered(collateral)`/"config exists"), and skips the actual authorization bit that governs whether that resource should currently be usable (`vault registered`/`token enabled`).

### Impact Explanation
If a protocol admin disables a token via `MsgUpdateTokenConfig` (setting `Enabled = false`) — the documented mechanism for pulling a compromised or depegged asset out of circulation — an ordinary unprivileged user can still submit source-chain deposits for that exact `(chain, address)` pair. Universal Validators will observe and vote the inbound (chain-level check passes because the chain itself remains enabled), and `ExecuteInbound*` will happily call `depositPRC20`/`CallPRC20Deposit`, minting the PRC20 representation to the recipient's UEA. This defeats the entire purpose of the admin kill-switch, exposing users and the protocol to continued exposure of a token the operator explicitly tried to freeze (e.g., depegged stablecoin, exploited wrapped asset), i.e. it results in unauthorized PRC20 minting for an asset that governance/operations intended to be inert. This falls squarely within the in-scope "unauthorized mint" / "corruption of PRC20 accounting" / "token mapping" impact categories, triggered purely by an ordinary unprivileged user submitting a normal deposit — no privileged or malicious-validator assumption required.

### Likelihood Explanation
High reachability, low complexity: any user can trigger this simply by depositing the disabled token on the already-enabled source chain — no special conditions besides the token having previously been registered and later disabled (a supported, documented admin action per `x/uregistry/README.md`'s `MsgUpdateTokenConfig`). The disabled state can persist indefinitely as long as the chain stays enabled, so the window of exploitability is operator-defined and potentially long-lived.

### Recommendation
Add an explicit enablement check before minting/depositing in the inbound execution path — mirroring the chain-level `IsChainInboundEnabled` check already present in `VoteInbound`:
```go
tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
if err != nil {
    return nil, err
}
if !tokenConfig.Enabled {
    return nil, fmt.Errorf("token %s on chain %s is disabled", assetAddr, sourceChain)
}
```
Apply this consistently to every call site that resolves a `TokenConfig` for value-moving purposes (`handler.go:depositPRC20`, `execute_inbound_gas_and_payload.go`, `create_outbound.go`'s rescue path, `build_revert_outbound.go`), and treat a disabled-token deposit the same way a missing-token-config deposit is already handled today (FAILED PCTx + INBOUND_REVERT for non-CEA), so funds aren't stranded while still respecting the admin freeze.

### Proof of Concept
1. Admin registers token T on chain C with `Enabled = true`; users deposit T normally, minting PRC20(T) via `depositPRC20`.
2. Admin discovers T is compromised/depegged and calls `MsgUpdateTokenConfig` setting `Enabled = false` on T, expecting deposits to stop.
3. Attacker (any unprivileged user) sends a fresh deposit of T on source chain C to the gateway, exactly as before.
4. Universal Validators vote `MsgVoteInbound`; `VoteInbound` only checks `IsChainInboundEnabled(C)` (chain-level), which is still `true`.
5. `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` calls `depositPRC20(ctx, C, T, recipient, amount)` → `k.uregistryKeeper.GetTokenConfig(ctx, C, T)` returns the config with `Enabled: false`, but this field is never inspected.
6. `CallPRC20Deposit` mints PRC20(T) to the recipient as if the token were still active — the admin's disable action had no effect on the live minting path.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
