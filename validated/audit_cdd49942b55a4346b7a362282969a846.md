### Title
Receipt-size limit enforced only at creation time can be exceeded after `promise_return` / `output_data_receivers` mutation, admitting oversized receipts past the validated cap - ([File: runtime/runtime/src/verifier.rs])

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces `max_receipt_size` as a hard cap on a receipt's borsh-encoded size, analogous to `Fintroller`'s debt-ceiling check that is supposed to be the single source of truth for a bounded quantity. Just as `HToken.depositUnderlying()` could mint hTokens through a path that never consulted the debt-ceiling check performed in `BalanceSheetV2.borrow()`, nearcore has a code path where a receipt is validated against `max_receipt_size` at creation time, but is subsequently mutated (via `promise_return`, which rewrites `output_data_receivers`) *after* that check, so the final, actually-persisted/propagated receipt can exceed the configured limit without ever being re-validated.

### Finding Description
The size limit is defined and enforced in `runtime/runtime/src/verifier.rs::validate_receipt` (`ReceiptSizeExceeded`, checked against `wasm_config.limit_config.max_receipt_size`) [1](#0-0) . This check happens once, when the receipt is first created/validated as a `NewReceipt`.

However, `runtime/runtime/src/receipt_manager.rs` and `runtime/runtime/src/function_call.rs` implement `promise_return`, which mutates a receipt's `output_data_receivers` *after* the receipt object has already passed the size-validation gate — this is the same "check happens on one accounting path, mutation happens on another, uncoupled path" pattern as the debt-ceiling bug, where `BalanceSheetV2.borrow()` checks `bond.totalSupply()` against the ceiling but `HToken.depositUnderlying()` mints tokens through a path that never re-consults that ceiling.

This is not speculative: the nearcore test suite itself documents the bug as a known, currently-unfixed issue and directly references it:
```
// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
``` [2](#0-1) 

The two tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` construct exactly this scenario end-to-end: a contract creates a promise DAG where a later step (`promise_return`, or returning a large value that becomes a data receipt) grows a receipt past `max_receipt_size` after the size check already ran, and both tests assert that the runtime does not crash while confirming (via `assert_oversized_receipt_occurred`) that an oversized receipt is actually observed on-chain rather than being rejected [3](#0-2) , with the scanning helper walking incoming-receipt proofs / receipt proofs to find the oversized receipt that slipped through [4](#0-3) .

### Impact Explanation
`max_receipt_size` is one of the stateless-validation / state-witness size limits that bound how large a single receipt's borsh encoding — and therefore its contribution to the chunk's storage proof and state witness — can be [5](#0-4) . A receipt that bypasses this bound can inflate the state witness or storage proof beyond the size the protocol assumes is possible, which underlies chunk-validation resource bounds (this is the direct nearcore analog of a supply/ceiling invariant being silently exceeded: the invariant "no receipt exceeds `max_receipt_size`" that other consensus-critical code paths (congestion control, state-witness limits) rely upon is violated). Because this can be reached purely by an unprivileged contract caller crafting a promise chain (`generate_large_receipt` / `max_receipt_size_promise_return_method1` / `max_receipt_size_value_return_method` in the tests), it is reachable from a single submitted transaction, matching the "transaction/contract-call reachable" requirement.

### Likelihood Explanation
High likelihood of triggerability: it is already demonstrated by in-repo tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) that any account can deploy a contract and call methods that create a promise DAG whose resolved receipt (via `promise_return` or returned value becoming a data receipt) exceeds `max_receipt_size` after the one-time validation check. No privileged role, validator behavior, or network-layer assumption is required — a single account submitting ordinary `FunctionCall` transactions suffices.

### Recommendation
Re-validate (or bound) receipt size at every point a receipt's contents can still change after creation-time validation — specifically after `promise_return` mutates `output_data_receivers` in `runtime/runtime/src/receipt_manager.rs`/`function_call.rs`, and after data-receipt/value-return construction — rather than relying solely on the one-shot check in `validate_receipt` (`runtime/runtime/src/verifier.rs`). This mirrors the debt-ceiling fix recommendation of adding validation to the alternate mutation path (`HToken.depositUnderlying()`) instead of trusting that the single checked path (`BalanceSheetV2.borrow()`) is the only way the invariant can be affected.

### Proof of Concept
The existing repository tests are themselves a proof of concept and are unmodified reproductions of the bug:
- `test_max_receipt_size_promise_return`: deploys a contract, builds a promise DAG `[A -then-> B]` where `A` creates promise `C` and calls `promise_return`, causing `C`'s already-size-validated receipt to have `output_data_receivers` appended after validation, pushing it over `max_receipt_size`; the test asserts (via `assert_oversized_receipt_occurred`) that an oversized receipt is actually included rather than rejected [6](#0-5) .
- `test_max_receipt_size_value_return`: same pattern via a large returned value becoming an oversized data receipt [7](#0-6) .

Note: I was unable to fully trace the exact line-level mutation code in `receipt_manager.rs`/`function_call.rs` where `output_data_receivers` is appended post-validation before the tool budget ran out; the analysis above is corroborated directly by the in-repo test comments and the linked upstream issue (near/nearcore#12606) rather than by manually re-deriving the mutation site.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
