### Title
Unbounded-CPU gzip-bomb DoS in deprecated gateway Sierra program decompression - (File: crates/starknet_api/src/compression_utils.rs)

### Summary
The reported CVE (BIT-libpython-2022-48564 / CVE-2022-48564) describes a bug class where a parser reads an untrusted, attacker-controlled input format and expends unbounded CPU/RAM before any size or sanity checks take effect, enabling a DoS. The sequencer contains an analogous pattern in `decompress_with_size_limit` in `crates/starknet_api/src/compression_utils.rs`, used to decompress a `sierra_program` submitted by an unprivileged contract declarer through the deprecated HTTP gateway transaction format.

### Finding Description
`decompress_with_size_limit` gzip-decompresses base64-decoded, attacker-supplied bytes and only enforces a size limit on the *output*, not on the CPU time consumed while decompressing: [1](#0-0) 

The function's own TODO comment acknowledges this gap: `// TODO(dan): consider limiting the time it takes to decompress.` directly above `decode_and_decompress_with_size_limit`, which base64-decodes and calls the size-limited decompressor: [2](#0-1) 

This is reachable from an unprivileged transaction sender: `DeprecatedGatewaySierraContractClass::convert_to_sierra_contract_class` calls `decode_and_decompress_with_size_limit` on the `sierra_program` field of a submitted `DECLARE` transaction in the deprecated (Pythonic) gateway transaction format: [3](#0-2) 

Like `plistlib.read_ints`, which reads a count/size field and then loops/allocates based on attacker-controlled values before validating bounds, `GzDecoder::read_to_end` (wrapped with `.take(max_size+1)`) will still perform the full inflate computation for every byte up to the limit — an attacker can craft a small, deeply-compressed payload (a classic "gzip bomb", e.g. compression ratios of 1000:1+) that is cheap to transmit but expensive to inflate, consuming significant CPU per request before the size check ever rejects it.

### Impact Explanation
An attacker can submit DECLARE transactions via the deprecated gateway HTTP endpoint with a small but highly-compressed `sierra_program` payload. Each such submission forces the node to spend disproportionate CPU cycles in decompression during transaction validation/conversion, before the transaction is even added to the mempool. Repeated/concurrent submissions can degrade validation throughput for the sequencer's gateway component, potentially delaying honest transaction processing — this maps to the "network unable to confirm new transactions" impact category (resource-exhaustion-based liveness degradation of the gateway ingestion path), not a state-corruption issue.

### Likelihood Explanation
Likelihood is constrained by two factors I could not fully verify from available context: (1) whether this deprecated gateway HTTP endpoint is exposed/enabled in the production sequencer path, and (2) what `max_size` value is configured for declare transactions (which bounds the worst-case single-call cost, though it does not bound CPU-per-byte). The code path and gap are real and directly reachable by crafting a DECLARE transaction, but confirming exploitability at scale (e.g., whether there are additional request-level rate limits or timeouts at the HTTP server layer) requires further verification beyond what the indexed code shows.

### Recommendation
Bound the CPU time (not just output size) spent in `decompress_with_size_limit`, e.g., by decompressing in small chunks with a wall-clock or instruction-count budget, or by using a decompression library/setting that enforces a maximum compression-ratio check before inflating further. Apply the same treatment to the other size-limited decompression paths reachable from untrusted class/program data (e.g., `apollo_storage/src/compression_utils.rs`, `blockifier_reexecution/src/compile.rs`'s `decode_reader`) if those are also reachable pre-consensus from unprivileged input.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
