### Title
Truncated proportional `transferUsage` calculation in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` lets a third-party delegator dilute resource usage accounting - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.execute` (and its TVM counterpart `UnDelegateResourceProcessor.execute`) computes the amount of bandwidth/energy "usage" to move back from a resource receiver to the un-delegating owner as a proportional share: `receiverNetUsage * (unDelegateBalance / receiverAllFrozenBalance)`. This ratio is computed with `double` arithmetic and truncated to `long`, exactly the same class of rounding-truncation bug described in the external report, where a proportional value moved alongside a balance transfer is truncated to less than its true share whenever the denominator (the receiver's total delegated balance) is inflated right before the operation.

### Finding Description
In `UnDelegateResourceActuator.execute`:
```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
``` [1](#0-0) 
The identical pattern exists for `ENERGY`: [2](#0-1) 
and it is duplicated verbatim in the TVM native-contract path used by `UnDelegateResource` precompiled/native-contract calls: [3](#0-2) 

`receiverCapsule.getAllFrozenBalanceForBandwidth()` (the denominator) is the sum of the receiver's own frozen balance plus *all* delegated-in balances from any number of independent delegators — anyone can call `DelegateResourceContract`/`DelegateResourceActuator` to increase it for an arbitrary receiver without the receiver's consent: [4](#0-3) 

Because the divisor can be inflated by any unrelated account right before the original delegator calls `UnDelegateResource`, the computed `transferUsage` is truncated further down than the true proportional share. This is the exact rounding/truncation root cause pattern from the report ("`values[i] * contributions[from] / balanceOf(from)`" truncating to less than the fair share when the balance is inflated by a third party's transfer/donation immediately beforehand).

Notably, the codebase already recognizes this exact class of bug elsewhere and has hardened it with `BigInteger`-based, non-lossy math gated behind `hardenCalculation()` (e.g. `calculateGlobalLimitV1`/`V2`, `increase`, `increaseV2`, `unDelegateIncreaseV2` in `ResourceProcessor`): [5](#0-4) 
but the `transferUsage`/`unDelegateMaxUsage` computation inside `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` was never migrated to this hardened path and still uses raw `double` division and truncation unconditionally.

### Impact Explanation
When `transferUsage` is truncated down due to a third party inflating the receiver's `AllFrozenBalanceForBandwidth`/`AllFrozenBalanceForEnergy` just before an `UnDelegateResource` transaction, less usage is subtracted from the receiver and correspondingly less is credited back to the owner (`processor.unDelegateIncrease`). This permanently and silently corrupts the bandwidth/energy usage accounting split between owner and receiver: the receiver is left holding usage that should have moved back to the owner, distorting both accounts' available resource windows going forward. This matches the "resource and reward accounting" corruption category — impact is limited to resource-window state corruption (not fund loss), consistent with the "Low" impact rating in the original report.

### Likelihood Explanation
Both `DelegateResourceContract` and `UnDelegateResourceContract` are ordinary broadcastable transactions/native-contract calls available to any account (no privileged role required), and the `DelegateResource` step deliberately allows delegating to *any* receiver address without their consent. An attacker only needs to observe/anticipate a pending `UnDelegateResource` transaction (e.g., via mempool monitoring) and front-run it with a small `DelegateResource` to the same receiver to shift the rounding boundary, making this reliably triggerable, similar to the "High" likelihood in the original report.

### Recommendation
Replace the raw `double`-based ratio computation for `transferUsage`/`unDelegateMaxUsage` in `UnDelegateResourceActuator` and `UnDelegateResourceProcessor` with exact `BigInteger` arithmetic (as already done in `ResourceProcessor.calculateGlobalLimitV1/V2`), and/or validate that no rounding-favorable truncation to zero silently drops non-zero proportional shares when the source usage/contribution value is non-zero.

### Proof of Concept
1. Owner A delegates bandwidth `X` TRX to Receiver B via `DelegateResourceActuator`, increasing `B.acquiredDelegatedFrozenBalanceForBandwidth` and thus `B.getAllFrozenBalanceForBandwidth()`.
2. B consumes bandwidth, accumulating `B.getNetUsage() = U`.
3. Attacker M observes A's pending `UnDelegateResource(X)` transaction and front-runs it by delegating additional balance `Y` to B via `DelegateResourceActuator`, inflating `B.getAllFrozenBalanceForBandwidth()` to `X + Y + ...`.
4. When A's `UnDelegateResource(X)` executes, `transferUsage = (long)(U * (X / (X+Y+...)))` is computed with `double` arithmetic and truncated, yielding a value strictly smaller than the mathematically correct proportional share `U*X/(X+Y+...)` would be under exact integer math — usage that should move to A's account stays stuck on B's account, corrupting both parties' resource accounting.

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
