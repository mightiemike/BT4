No vulnerability found. Investigation confirms this is intentional design, not exploitable behavior.

**Analysis:**

The two-pass logic in `ComputeBudgetInstructionDetails::try_from` only runs the second builtin-counting pass when `requested_compute_unit_limit.is_none()`, because that pass exists solely to compute a *default* CU limit (`calculate_default_compute_unit_limit`) for transactions that didn't specify one explicitly. [1](#0-0) 

When an explicit `SetComputeUnitLimit` value is provided, that value is used directly as `compute_unit_limit` in `sanitize_and_convert_to_compute_budget_limits`, bypassing `calculate_default_compute_unit_limit` entirely — so the builtin/migrating counters are correctly unnecessary in that branch. [2](#0-1) 

Critically, `CostModel::get_estimated_execution_cost` (used for block-cost-limit / packing accounting) does **not** independently sum per-instruction builtin costs from `ComputeBudgetInstructionDetails` counters. It simply uses `config.compute_unit_limit` — i.e., whatever the transaction declares (explicit or default) — as the `programs_execution_cost` for cost-model purposes. [3](#0-2) 

This is confirmed by the existing test `test_transaction_cost_with_mix_instruction_with_cu_limit`, where the cost model uses the declared `cu_limit` directly regardless of instruction content. [4](#0-3) 

Since the cost model's execution-cost accounting is driven entirely by the *declared* `compute_unit_limit` (not a bottom-up sum of per-instruction/per-builtin costs), skipping `num_non_migratable_builtin_instructions`/`migrating_builtin_feature_counters` accumulation when an explicit limit is set introduces **no accounting gap**: block-packing already reserves exactly the declared 1 CU for that transaction, and real execution during the SVM aborts as soon as the declared budget (1 CU) is exhausted — meaning the "hundreds of migrating builtin instructions" past the first one are never actually executed, so no unaccounted-for work occurs. The scenario described (fee-only transaction with a minimal CU limit) is an already-recognized, intentional feature of Solana's fee/compute-budget model (transactions can legitimately pay a fee and fail fast on compute exhaustion), not a bypass of metering totality. Other resource costs relevant to block packing (signature cost, write-lock cost, instruction-data-bytes cost, loaded-accounts-data-size cost) are computed independently of the builtin counters and are unaffected. [5](#0-4)

    /// Return (programs_execution_cost, loaded_accounts_data_size_cost)
    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }
