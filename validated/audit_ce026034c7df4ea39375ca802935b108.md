### Title
Deleting an ETH key does not check for pending/unconfirmed transactions, orphaning in-flight txes and breaking TXM nonce/accounting guarantees - (File: core/services/keystore/eth.go)

### Summary
This is the closest reachable analog to the Renzo "remove collateral token while pending withdrawals exist" bug class. In the Renzo case, removing a tracked asset while unresolved obligations against it exist causes the accounting layer to silently lose track of value still owed. In Chainlink's EVM keystore, `eth.Delete()` permanently removes an ETH key's `evm.key_states` row via `safeRemoveKey` without checking whether that address still has `unstarted`/`in_progress`/`unconfirmed` transactions in `evm.txes`. The foreign key that used to CASCADE-delete `evm.txes` rows on key-state deletion was explicitly dropped (migration `0210_remove_evm_key_states_fk_constraint.sql`), and a regression test confirms the key can be deleted "even if evm.txes are present."

### Finding Description
`Delete` in `core/services/keystore/eth.go` looks up the key, then calls `ks.safeRemoveKey(...)` to delete the corresponding `evm.key_states` row and finally purges the key from the in-memory `keyStates`/`keyRing`: [1](#0-0) 

There is no check against `evm.txes` for the address being deleted (no lookup for `unstarted`, `in_progress`, or `unconfirmed` transactions) before the key state is removed.

Historically, `evm.txes` had a foreign key to `evm.key_states` with `ON DELETE CASCADE`, which at least kept the two tables consistent (deleting the key state would cascade-delete its transactions). That FK constraint was explicitly dropped: [2](#0-1) 

This means `evm.txes` rows referencing the deleted address are no longer cleaned up nor protected — they become orphaned in the database. This is confirmed by an existing test that explicitly asserts a key can be deleted while `evm.txes` rows still exist for it: [3](#0-2) 

The Transaction Manager's guarantees (documented in `docs/core/TX_MANAGER_ARCHITECTURE.md`) rely on a gapless, per-key nonce sequence and on `EthBroadcaster`/`EthConfirmer` continuously acting on `unstarted`/`unconfirmed` rows for each *enabled* key: [4](#0-3) 

Once the key state is deleted, `EnabledKeysForChain` (which TXM subsystems query to determine which addresses to service) no longer returns that address: [5](#0-4) 

Consequently, any transaction still `unstarted`/`in_progress`/`unconfirmed` for the deleted address is left in the `evm.txes` table but is no longer tracked/serviced by `EthBroadcaster`/`EthConfirmer`, breaking the documented "eventual confirmation" and "gapless nonce" guarantees — directly analogous to Renzo's `WithdrawQueue` balance surviving `removeCollateralToken()` while no longer being counted in TVL.

### Impact Explanation
An admin (via CLI `chainlink keys eth delete` or the `/keys/eth/:keyID` REST endpoint / GraphQL mutation) can delete an ETH key while it has pending/in-flight transactions. This can:
- Leave transactions permanently stuck in `unstarted`/`in_progress`/`unconfirmed` state with no service tracking or bumping their gas or checking for receipts, silently breaking job execution that depended on those transactions being confirmed (e.g. OCR transmissions, VRF fulfillments, Automation upkeeps).
- Create nonce-gap inconsistencies if the address is later re-added or reused, since the "gapless, monotonically increasing sequence of nonces... scoped to key" invariant documented for `EthBroadcaster` is defined against `key_states`, which was just wiped independent of the transaction history.
- Cause silent transaction/workflow misexecution (funds transactions dropped from tracking) — this matches the "misreporting/data tampering" / "unsafe transaction execution" impact class required by the validation rules, since the node's own accounting of its outstanding transaction obligations for that key becomes wrong the moment the key state is deleted.

This is a state-management/accounting gap directly reachable by an authorized node admin performing an ordinary key-management action, not a mocked-only or dependency-only issue — it is demonstrated by a passing core repo test.

### Likelihood Explanation
Requires an admin/API-key holder to actively call the "delete ETH key" action while transactions for that key are still pending — a deliberate, privileged operation, but one with no built-in warning, confirmation of pending-tx state, or blocking check (unlike bridge deletion, which does check `FindJobIDsWithBridge` and refuses deletion if jobs are using it, or job deletion, which enforces deleting the job before removing its bridge dependency — see the "must delete job before deleting bridge" guard). The keystore path has no equivalent guard for its own database of in-flight financial transactions, making accidental invocation plausible in operational key-rotation/decommissioning workflows.

### Recommendation
Before permanently deleting an ETH key (`eth.Delete`), check `evm.txes` for any rows in `unstarted`, `in_progress`, or `unconfirmed` state for that `(evm_chain_id, from_address)` pair and refuse deletion (or require an explicit `--force`/`abandon` flag, similar to the existing `--abandon` behavior in `keys eth chain`) until those transactions are confirmed, abandoned, or otherwise resolved. This mirrors Renzo's own recommended and accepted mitigation: block removal while there is an outstanding/pending balance, or explicitly force-resolve it first.

### Proof of Concept
The existing repository test itself is effectively a PoC demonstrating the gap (asserting current, apparently-intended-but-unsafe behavior): [3](#0-2) 
1. Create an ETH key (`ethKeyStore.Create`).
2. Insert a confirmed/pending `evm.txes` row for that key's address (`txmgrtest.MustInsertConfirmedEthTxWithLegacyAttempt`).
3. Call `ethKeyStore.Delete(ctx, key.ID())` — succeeds with no error and no check of transaction state.
4. `evm.key_states` row count drops to 0, while the `evm.txes` row for that address remains in the database, now untracked by any enabled-key query used by TXM.

```go
func (ks *eth) Delete(ctx context.Context, id string) (ethkey.KeyV2, error) {
	ks.lock.Lock()
	defer ks.lock.Unlock()
	if ks.isLocked() {
		return ethkey.KeyV2{}, ErrLocked
	}
	key, err := ks.getByID(id)
	if err != nil {
		return ethkey.KeyV2{}, err
	}
	err = ks.safeRemoveKey(ctx, key, func(ds sqlutil.DataSource) error {
		_, err2 := ds.ExecContext(ctx, `DELETE FROM evm.key_states WHERE address = $1`, key.Address)
		return err2
	})
	if err != nil {
		return ethkey.KeyV2{}, errors.Wrap(err, "unable to remove eth key")
	}
	ks.keyStates.Delete(key.Address)
	return key, nil
}
```

```go
func (ks *eth) EnabledKeysForChain(ctx context.Context, chainID *big.Int) (sendingKeys []ethkey.KeyV2, err error) {
	if chainID == nil {
		return nil, errors.New("chainID must be non-nil")
	}

	defer ks.lock.RUnlock()
	if ks.isLocked() {
		return nil, ErrLocked
	}

}
```

**File:** docs/core/TX_MANAGER_ARCHITECTURE.md (L92-98)
```markdown
**EthBroadcaster** makes the following guarantees:

- A gapless, monotonically increasing sequence of nonces for `evm.txes` (scoped to key).
- Transition of `evm.txes` from `unstarted` to either `fatal_error` or `unconfirmed`.
- If final state is `fatal_error` then the nonce is unassigned, and it is impossible that this transaction could ever be mined into a block.
- If final state is `unconfirmed` then a saved `eth_transaction_attempt` exists.
- If final state is `unconfirmed` then an eth node somewhere has accepted this transaction into its mempool at least once.
```
