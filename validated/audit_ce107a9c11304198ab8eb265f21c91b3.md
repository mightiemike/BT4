### Title
Out-of-bounds panic / heap over-read analog in stateless state-diff decompression - (File: `crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs`)

### Summary
The Rust `decompress` function that reconstructs the Starknet OS's DA-compressed state diff indexes into `unique_values`/`all_values` using indices (`repeating_value_pointers`, `bucket_index_per_elm`) taken directly from untrusted compressed input, without validating that these indices are in-bounds before use, analogous to CVE-2018-11725's `mobi_parse_index_entry`, which trusted an index/offset from a crafted file and read past the buffer.

### Finding Description
`decompress` (`crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs:543-618`) parses a header and several "buckets" from an iterator of `Felt`s (`compressed`). Two places use attacker/prover-controlled values as raw array indices with no bounds checks: [1](#0-0) 
- `repeating_value_pointers` are unpacked via `unpack_chunk_to_usize(..., unique_values.len().try_into().unwrap())` and then used as `unique_values[*ptr]` at line 594 with no explicit check that `ptr < unique_values.len()` beyond what `unpack_felts_to` may or may not enforce.
- `bucket_index_per_elm` values are used as `bucket_offset_trackers[bucket_index]` at line 611, indexing an array of size `TOTAL_N_BUCKETS`. If a crafted compressed blob supplies an out-of-range value for a bucket index (or the header specifies inconsistent bucket lengths versus the number of underlying compressed felts, e.g. via `unique_value_bucket_lengths`/`n_repeating_values`/`data_len` fields taken straight from `header` at lines 575-577), these vector indexing operations can panic with "index out of bounds" (Rust's memory-safe equivalent of the C heap-over-read in libmobi) instead of a validated, controlled error.

This function is invoked from `os_output_types.rs` (`use ...stateless_compression::utils::decompress;`) when parsing the Starknet OS program's output, which encodes the block's compressed state diff. That output is produced during OS execution/proving from data that a block's state diff (deployed contracts, storage diffs, declared classes, nonces) determines, and is subsequently consumed by nodes that decode/verify the OS output (e.g., re-execution or output verification flows), i.e., a party other than the code that packed the compression can supply malformed compressed data through unexpected state-diff content or through a divergent/malicious encoding, causing the decoder to read out-of-range indices.

### Impact Explanation
Where reachable, an out-of-bounds index causes a Rust panic (process abort in the decoding component) rather than a memory-disclosure like libmobi's heap over-read, since Rust's `Vec`/slice indexing is bounds-checked and panics on violation. In this sequencer, that means: a node that must decode the OS output (e.g., as part of re-execution/verification) could panic/crash on a malformed but "successfully proven" state diff, producing a denial-of-service on that decoding path, or divergence between whichever component tolerates the error and whichever panics — undermining a network's ability to consistently confirm/verify a block. This does not, by itself, produce the same information-disclosure impact as the CVE (no heap-over-read of adjacent memory across trust boundaries occurs, thanks to Rust's memory safety), which limits the direct applicability of the "information disclosure" impact from the original CVE.

### Likelihood Explanation
I was unable to fully trace, within available tool budget, the exact upstream call chain that feeds prover/state-diff-derived compressed bytes into `decompress` at `os_output_types.rs`, nor confirm whether an intermediate validation layer (e.g., cairo-VM proof verification, or a prior `unpack_felts_to` bounds check) already prevents out-of-range indices from ever reaching this Rust code in production before being consumed by nodes. The Cairo-side implementation (`compression.cairo`) explicitly documents that "a malicious prover might use a non-optimal compression" and adds STARK-level range checks (`assert_nn_le`, dict-based bound tracking) to prove indices are in range — see the dict-verification block in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/data_availability/compression.cairo:264-300`. It is unclear whether the standalone Rust `decompress` used by `os_output_types.rs` enforces equivalent guarantees, or relies on the STARK proof already having validated the OS execution (in which case out-of-range indices could never appear in a valid, accepted output, making this unreachable from a single unprivileged transaction/L1 message in practice).

### Recommendation
Given the uncertainty above, I cannot confidently assert this is an exploitable, high/critical-severity vulnerability reachable by "a single submitted transaction, contract call, declared class or L1 message" as required by the validation rules. A background engineering review should:
1. Trace whether `decompress` in `stateless_compression/utils.rs` is ever invoked on data that has not already passed the corresponding Cairo/STARK constraints (i.e., on non-proven, externally supplied bytes).
2. If so, add explicit bounds checks (returning `OsHintError`/`OsOutputError`) before indexing `unique_values`/`bucket_offset_trackers` with untrusted `ptr`/`bucket_index` values, mirroring the Cairo-side dictionary bound verification.
