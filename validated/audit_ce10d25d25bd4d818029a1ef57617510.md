### Title
Inconsistent resource-weight unit accounting in `FreezeBalanceActuator` corrupts `TotalNetWeight`/`TotalEnergyWeight` - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.addTotalWeight()` is fed two differently-derived quantities — a delegation-aware `increment` (the true change in weight units) and the raw `frozenBalance` (still in drops, not yet converted to weight units) — and silently picks one or the other based on a feature flag, without ensuring both represent the same unit/semantics in the delegated-resource code path. This mirrors the reported `aggregatedQueueAmount` bug class: a value computed in one unit/semantic context (delta of receiver's aggregated weight) is substituted for a differently-scoped value (frozen amount of this single transaction) when the legacy path is taken, corrupting the global aggregate used in resource-limit accounting.

### Finding Description
In `FreezeBalanceActuator.execute()`, for both `BANDWIDTH` and `ENERGY` resources, when the contract delegates resources to another account, `increment` is computed as the delta of the **receiver's** aggregated weight (`newWeight - oldWeight`, derived from `getAcquiredDelegatedFrozenBalanceForX() / TRX_PRECISION`) inside `delegateResource()`: [1](#0-0) 

That `increment` is then passed into `addTotalWeight`, which — depending on `dynamicStore.allowNewReward()` — either uses this delta (`increment`) or instead recomputes an entirely different quantity, `frozenBalance / TRX_PRECISION`, i.e. the *this-transaction* frozen amount, not the actual observed change in the aggregated weight state: [2](#0-1) 

These two quantities are only guaranteed to be equal when the receiver's pre-existing acquired-delegated balance is already exactly divisible by `TRX_PRECISION`. Because delegated/acquired balances accumulate over many independent transactions (freeze, unfreeze, TVM-triggered freeze/unfreeze, suicide-inherited transfers, etc.), the receiver's running total is not guaranteed to stay aligned to `TRX_PRECISION` multiples between calls; the `/ TRX_PRECISION` integer division on the *before* and *after* states can therefore diverge from a naive `frozenBalance / TRX_PRECISION` computed on the newly delegated amount alone. Using the wrong scalar in `addTotalWeight` mutates the network-wide `TotalNetWeight` / `TotalEnergyWeight` counters (`dynamicStore.addTotalNetWeight` / `addTotalEnergyWeight`) by an amount inconsistent with the actual sum of per-account weights.

This is directly analogous to the reported bug: a "pending/aggregated" quantity tracked in one semantic unit (delta of the receiver's actual state) is replaced by a raw, un-reconciled input quantity (the frozen amount of the current transaction) under certain conditions, corrupting a downstream global accounting value used to gate resource allocation for the entire network.

Notably, a very similar issue was previously found and explicitly flagged as fixed elsewhere in the same subsystem, evidenced by the comment `// adjust total resource, used to be a bug here` in `UnfreezeBalanceProcessor.execute()`, confirming this exact class of weight-accounting inconsistency is a known, real bug pattern in this codebase: [3](#0-2) 

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are consensus-critical global counters that determine every account's proportional share of network bandwidth/energy (`calculateGlobalNetLimit`, `calculateGlobalEnergyLimit`, and the analogous V2 methods). A silent drift in these aggregates — caused by using an unreconciled frozen-amount instead of the true observed weight delta on the delegation path — could over time misallocate free/paid resource limits network-wide, degrading a resource-accounting invariant, potentially permitting resource starvation or over-granting bandwidth/energy (a DoS-adjacent resource-accounting corruption) as this drift compounds across many `FreezeBalanceContract` delegating transactions from different accounts.

### Likelihood Explanation
`FreezeBalanceContract` is a normal broadcastable transaction type reachable by any account; the delegated-resource path (`receiverAddress` non-empty and `dynamicStore.supportDR()`) is a standard, frequently used feature (TRX delegation to power TVM contracts/other accounts). The divergence requires the receiver's aggregated acquired-delegated balance to not be an exact multiple of `TRX_PRECISION` at the time of a further delegation — a state that is easily reached through ordinary sequences of freeze/unfreeze/delegate/un-delegate operations, since none of these apparently guarantee alignment to `TRX_PRECISION` on every intermediate state.

### Recommendation
In `FreezeBalanceActuator.addTotalWeight`, always use the same unit-consistent value for accumulating `TotalNetWeight`/`TotalEnergyWeight`, regardless of the `allowNewReward()` flag: prefer the actually-observed weight delta (`increment`) that is computed consistently from before/after account state in both the delegated and non-delegated branches, instead of substituting a raw, unconverted `frozenBalance` figure. Add/restore invariant tests asserting `TotalNetWeight`/`TotalEnergyWeight` equal the sum of per-account weights after arbitrary freeze/delegate/unfreeze sequences that leave non-aligned balances.

### Proof of Concept
1. Freeze BANDWIDTH balance from account `R` to itself with an amount not a multiple of `TRX_PRECISION` is not directly possible since freeze amounts must be ≥ 1 TRX and drops; instead, have account `A` delegate a `frozenBalance` to `R` (`FreezeBalanceContract` with `receiverAddress = R`), so `R.getAcquiredDelegatedFrozenBalanceForBandwidth()` becomes non-zero.
2. Have a second account `B` delegate to the same `R` a `frozenBalance2` amount, chosen so that `R`'s pre-delegation acquired balance is not an exact multiple of `TRX_PRECISION` (achievable across several freeze/partial-unfreeze cycles because `TRX_PRECISION` alignment is not enforced on every state transition of `AcquiredDelegatedFrozenBalance`).
3. Observe that `increment` returned by `delegateResource()` (based on `newWeight - oldWeight` from `R`'s updated acquired balance) differs from `frozenBalance2 / TRX_PRECISION`.
4. With `allowNewReward()` disabled (legacy path), `addTotalWeight` adds `frozenBalance2 / TRX_PRECISION` to `TotalNetWeight` instead of the correct `increment`, causing `TotalNetWeight` to diverge from the true sum of all accounts' weights, as verifiable via `dynamicStore.getTotalNetWeight()` compared against a manually summed total across all accounts.   private void addTotalWeight(ResourceCode resourceCode, DynamicPropertiesStore dynamicStore,
                              long frozenBalance, long increment) {
    long weight = dynamicStore.allowNewReward() ? increment : frozenBalance / TRX_PRECISION;
    switch (resourceCode) {
      case BANDWIDTH:
        dynamicStore.addTotalNetWeight(weight);
        break;
      case ENERGY:
        dynamicStore.addTotalEnergyWeight(weight);
        break;
      case TRON_POWER:
        dynamicStore.addTotalTronPowerWeight(weight);
        break;

        logger.debug("Resource Code Error.");
