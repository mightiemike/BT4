The strongest local analog to the CF/LF mismatch — an unprivileged, provable gap where a "safety invariant" is silently not enforced — is in the transaction-output/transaction-info reconciliation check used by replay-verification tooling.

### Title
Replay-verification (`ensure_match_transaction_info`) never validates checkpoint hashes, so state divergence during replay is silently accepted - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to assert that a freshly re-executed `TransactionOutput` matches an archived, ledger-committed `TransactionInfo`. It checks status, gas, write-set hash, and event-root hash, but it explicitly skips the `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields of `TransactionInfo`, which are the fields that authenticate the resulting state (Merkle) root after a transaction/checkpoint boundary.

### Finding Description
`ensure_match_transaction_info` compares `status`, `gas_used`, the write-set hash against `txn_info.state_change_hash()`, and the event root hash, then returns `Ok(())` — the code comment itself documents that the checkpoint hashes are intentionally left unchecked: [1](#0-0) 

This function is the sole correctness gate in `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and validates the result against the recorded `TransactionInfo`, events, and write set pulled from backup: [2](#0-1) 

Because the state/hot-state/"position" checkpoint hashes are the values that bind a `TransactionInfo` to the actual post-execution state root (i.e., the JMT/SMT root produced at a checkpoint boundary), and they are never compared here, this tool can report "successful replay" even when the locally recomputed state root differs from the one authenticated in the original ledger's `TransactionInfo`/accumulator. The write-set hash check alone does not catch this, since checkpoint hashes are computed from the materialized state tree (including hot-state and the new "trading native" state roots), not directly from the write set of a single transaction.

### Impact Explanation
This breaks the "committed state must match VM/executor result, and replay must independently reproduce and validate it" invariant. `replay_on_archive` is one of the primary tools operators/auditors use to confirm that historical ledger state is reproducible and uncorrupted from backups; if the code that computes state/hot-state roots (e.g., new features gated by `hot_state_root_in_txn_info` / `compute_trading_native_state_roots`, per the same TODO comment) diverges from what was actually committed on mainnet, replay-verify will not detect it. This is exactly the class of "hard-fork-only divergence during commit/replay silently accepted" and "authenticated response bound to the wrong state root" the state-integrity gate calls out — a genuine ledger state discrepancy could go undetected by the verification tooling that is supposed to catch it.

### Likelihood Explanation
The gap is unconditionally present any time this verification path is used (there is no configuration to enable the checkpoint-hash checks), and it is explicitly reachable by anyone running `db-tool replay-on-archive` against archived data — no privileged access is required to trigger the code path, only to observe its failure to detect an underlying state divergence. The comment in the source acknowledges the gap directly, confirming it is a known, unaddressed condition rather than a coincidental oversight.

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check invoked alongside it in `chunk_executor` and `replay_on_archive`) to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from the recomputed state/checkpoint against the corresponding fields in the trusted `TransactionInfo`, at least whenever the transaction is a state-checkpoint boundary (`has_state_checkpoint_hash`), before treating replay as "verified."

### Proof of Concept
1. Take an archived chunk of transactions/`TransactionInfo`s from backup that include a state-checkpoint boundary.
2. Run `replay_on_archive` (`Verifier::execute_and_verify`) with an executor build in which the state/hot-state root computation (post-checkpoint SMT/JMT root) is wrong (e.g., a hypothetical regression in `hotness_in_epilogue`/`compute_trading_native_state_roots` logic) while write-set contents, gas, status, and events remain identical to the archive.
3. `ensure_match_transaction_info` at [3](#0-2)  passes because it never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
4. `execute_and_verify` returns `Ok(None)` (no failure), so `replay-on-archive` reports the chunk as successfully replayed even though the actual state root differs from what mainnet committed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
