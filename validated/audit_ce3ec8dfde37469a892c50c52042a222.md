Based on my investigation, the strongest analog to the `LibBytes.sol` unchecked-offset hashing bug is the unchecked byte-slicing logic used by the `BatchValidateSign` precompiled contract in java-tron's TVM.

### Title
Unchecked offset/length in `PrecompiledContracts.extractBytes`/`extractSigArray` allows attacker-controlled `Arrays.copyOfRange` calls with out-of-bounds indices - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Solidity report flags `LibBytes.sol#keccak` for computing a memory pointer (`add(data, add(32, offset))`) from an attacker-supplied `offset`/`length` pair without validating `offset + length <= data.length`. The java-tron TVM contains a structurally identical pattern in the code that decodes calldata for signature-validation precompiles: `extractSigArray`/`extractBytes` compute byte offsets from attacker-controlled `DataWord` values parsed out of the raw call data and pass them straight into `Arrays.copyOfRange` without first verifying the computed bounds fit inside the data buffer.

### Finding Description
`extractSigArray` parses an array length and per-item offsets directly from words contained in the precompile's input `data` [1](#0-0) . The computed `bytesOffset` (derived from `words[offset + i + 1].intValueSafe()`) is attacker-controlled and is used to build a byte index passed to `extractBytes`, which performs `Arrays.copyOfRange(data, offset, offset + len)` with no bounds validation against `data.length` [2](#0-1) . The only sanity check present, `isValidAbiEncoding`, validates that the overall `data.length` is a multiple of `WORD_SIZE` and that the "tail" region matches the expected item stride — it does not validate that every per-item `bytesOffset` value actually falls inside `data` [3](#0-2) . This mirrors the LibBytes.sol root cause: length/offset values taken from untrusted input are used to compute a memory/array access without checking `offset + length <= data.length` before the low-level copy/hash operation.

Because a malicious contract call can freely control every word of `data` (including the "offset" words), it can set `bytesOffset` to a value that makes `(bytesOffset + offset + 2) * WORD_SIZE` either far larger than `data.length` (triggering `ArrayIndexOutOfBoundsException` in `copyOfRange`) or, via integer overflow of the `int` multiplication, negative (triggering `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` for an invalid `from` index).

### Impact Explanation
Java's array bounds checking prevents true memory corruption (unlike the raw EVM/Solidity `keccak256(add(...), length)` case), so the practical impact is an unhandled runtime exception thrown deep inside precompiled-contract execution that is triggered purely by the content of a transaction's call data, reachable from any broadcast transaction that calls the `BatchValidateSign`/signature-validation precompile. If this exception type is not part of the set explicitly caught by the higher-level VM/`Program` execution wrapper (as opposed to `Program.Exception` subclasses that are turned into a normal REVERT), it could propagate as an unexpected `RuntimeException` during transaction/block processing — a deterministic DoS condition triggerable by any user submitting a single crafted contract call. I was not able to fully verify, within the remaining investigation budget, whether the top-level executor (`Runtime`/`Program`) wraps precompiled-contract `execute()` calls in a catch-all that converts arbitrary `RuntimeException`s into a transaction revert; if it does, the impact is limited to a failed/reverted transaction rather than node-level disruption.

### Likelihood Explanation
Likelihood is high for triggering the exception itself: the precompile's inputs are fully attacker-controlled calldata from an ordinary contract call/broadcast transaction, requiring no privileged access, and the offset arithmetic is straightforward to manipulate to exceed `data.length` or overflow. Likelihood of it causing node-level DoS (versus a harmless per-transaction revert) is uncertain and depends on exception-handling behavior I could not confirm.

### Recommendation
Add an explicit bounds check before every `Arrays.copyOfRange` call driven by attacker-controlled offsets in `extractBytes`/`extractSigArray`, e.g. verify `offset >= 0 && len >= 0 && offset + len <= data.length` (using overflow-safe arithmetic, e.g. `Math.addExact`) and reject/return an empty result or throw a well-defined `Program.Exception` (already caught and converted to REVERT by the VM) instead of letting the raw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` propagate.

### Proof of Concept
1. Craft a transaction that calls the `BatchValidateSign` precompiled contract (or any consumer of `extractSigArray`/`extractBytes`) with calldata that: (a) passes `isValidAbiEncoding`'s length/stride checks, but (b) encodes a per-item offset word such that `(bytesOffset + offset + 2) * WORD_SIZE` computed in `extractSigArray` [4](#0-3)  either exceeds `data.length` or overflows `int` to a negative value.
2. Broadcast the transaction; observe that `extractBytes` throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` from `Arrays.copyOfRange(data, offset, offset + len)` [2](#0-1) .
3. Determine whether this exception is caught and converted to a normal revert by the calling `Program`/`Runtime` machinery, or propagates further — the latter would confirm a reachable DoS.

Note: I was unable to trace the full call chain (`execute()` implementation of the `BatchValidateSign` contract and the surrounding `Program`/`Runtime` exception-handling wrapper) within the remaining tool budget, so the final severity (transaction-level revert vs. broader node impact) is not fully confirmed and should be validated with direct code/test execution.

  private static boolean isValidAbiEncoding(byte[] data, int headerWords, int itemWords) {
    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));
    return tail > 0 && tail % multiplyExact(itemWords, WORD_SIZE) == 0;
  }
