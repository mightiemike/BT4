## Title
Pending-transaction-queue balance reservation silently skips transactions whose `tx_cost` computation errors, bypassing the NEP-611 anti-double-spend guard across uncertified chunks - (File: `chain/client/src/pending_transaction_queue.rs`)

## Summary
`PendingTransactionQueue::add_chunk_transactions` is the guard that prevents an account from double-spending across multiple uncertified (included-but-not-yet-executed) chunks by reserving each transaction's cost against the account's balance. When `tx_cost(config, tx, gas_price)` returns an `Err` for a transaction that is nonetheless part of an already-produced block, the code silently `continue`s and never adds that transaction's cost to `pending_accounts`/`paid_from_balance`. This is structurally identical to the reported bug class: a per-item cost lookup/estimate that falls through to "$0 reserved" for an input that isn't cleanly priced, defeating the very fan-out/overspend guard the reservation exists to enforce.

## Finding Description
`add_chunk_transactions` iterates every transaction in a newly accepted block's chunk and computes its cost via `tx_cost`: [1](#0-0) 

If `tx_cost` returns `Err`, the transaction is skipped with only a warning log — it never contributes to `chunk_account.paid_from_balance` or `chunk_data.gas_key_costs`, even though the transaction was already included in the block and will still deduct real balance from the account once the chunk is certified/executed.

This reservation is exactly what protects concurrent/uncertified chunk production: `query_pending_state` exposes `paid_from_balance` (defaulting to `Balance::ZERO` when nothing was reserved) via `PendingConstraints`: [2](#0-1) 

and `check_pending` forwards it unchanged to the runtime verifier: [3](#0-2) 

The ephemeral verifier then computes the *only* line of defense against overspending an account across not-yet-certified chunks by subtracting this reserved amount from the trie-committed balance: [4](#0-3) 

If a transaction's cost was never reserved (because `tx_cost` errored for it), `available_balance` is computed as if that transaction's spend does not exist. A second, concurrently-produced transaction from the same signer — validated by a different/parallel chunk-production attempt against the same pre-execution trie state — can then pass the `NotEnoughBalance` check even though, once both transactions are actually executed, their combined cost exceeds the account's real balance. This mirrors the reported pattern precisely: a fan-out/parallel-admission guard relies on a per-item cost reservation, and any item whose cost computation takes the error branch reserves zero, silently defeating the guard for exactly the items most likely to be adversarially crafted to trigger that branch (e.g., overflow-inducing gas/deposit/size combinations, malformed `UniversalStateInit`/delegate payloads that decode differently between preparation time and this later config, etc.).

## Impact Explanation
If an attacker can craft a transaction that is accepted into a chunk (passes whatever checks ran at block-production time) but for which the *later* `tx_cost` recomputation in `add_chunk_transactions` returns an `IntegerOverflowError` (or any other `tx_cost` error path), that transaction's balance commitment is dropped from the pending-transaction-queue's per-account/per-gas-key reservation. Any other transaction from the same signer submitted before the first chunk is certified will then be admitted against an inflated `available_balance`/`paid_from_gas_key` budget, enabling the signer to spend more than their actual balance across the two uncertified chunks — a concrete double-spend / unauthorized value movement once both chunks execute.

## Likelihood Explanation
This requires (a) a signer submitting two conflicting/competing transactions timed to land in different uncertified chunks, and (b) at least one of them landing on the `tx_cost` `Err` branch in `add_chunk_transactions` despite having been accepted into a block. Reaching that error branch reliably (e.g., via overflow-inducing gas/deposit combinations, or a payload whose cost computation is version/feature-sensitive) needs further confirmation of a concrete overflow input that is accepted at block-production but errors again in `add_chunk_transactions`, so likelihood is not fully established from static review alone, but the code path is directly reachable by an ordinary transaction signer with no privileged access.

## Recommendation
- Never silently drop a transaction's cost reservation when `tx_cost` errors in `add_chunk_transactions`. If a transaction was accepted into a block, its cost must be reserved deterministically, or the block/transaction should be treated as invalid.
- As a safe fallback (mirroring the referenced fix of using a conservative fallback price instead of 0), reserve a conservative upper-bound cost (e.g., full account balance, or the maximum possible cost for the transaction's declared gas/deposit) instead of `continue`-ing past it.
- Add a regression test asserting that a transaction whose `tx_cost` fails still results in a nonzero `paid_from_balance`/`pending_gas_key_cost` reservation, and that a second concurrent transaction from the same signer is rejected when the combined cost would exceed the account balance.

## Proof of Concept
1. Identify (or construct) a `SignedTransaction` whose actions cause `tx_cost` to return `Err` (e.g., an `IntegerOverflowError` from an arithmetic overflow in fee/deposit computation) while still passing whatever validation gate is used to admit it into a produced chunk (`chain/client/src/pending_transaction_queue.rs:274-284`).
2. Have the block containing this transaction accepted, so `add_chunk_transactions` runs and skips reserving its cost (`chain/client/src/pending_transaction_queue.rs:274-284`).
3. Before this chunk is certified, submit a second transaction from the same signer that spends the account's full remaining balance.
4. Because `query_pending_state` reports `paid_from_balance = Balance::ZERO` (or less than the true committed spend) for the signer (`chain/client/src/pending_transaction_queue.rs:430-436`), `verify_and_charge_tx_ephemeral`'s `available_balance` check (`runtime/runtime/src/verifier.rs:353-360`) admits the second transaction.
5. Once both chunks are certified/applied, the account's real balance is overdrawn beyond what a single-chunk balance check would have permitted.
