### Title
`citrea_network_to_chain_id` is not injective — `Network::Nightly` and `Network::TestNetworkWithForks` both map to chain id `5665`, breaking the cross-network replay guard - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
The binding the check is supposed to enforce is `citrea_network_to_chain_id(network_of_node) == body.chain_id` implying a 1:1 mapping between `Network` and chain id so that a council-signed `BatchProofMethodId` for one network cannot be replayed on another. In the actual mapping, `Network::Nightly => 5665` and `Network::TestNetworkWithForks => 5665` collide, so a method-id upgrade body signed with `chain_id = 5665` for one of these two networks passes the chain-id gate unmodified when re-inscribed and processed by a node running the other network.

### Finding Description
The gate in `run_l1_block` is:

```
let circuit_chain_id = citrea_network_to_chain_id(network);
if circuit_chain_id != batch_proof_method_id.body.chain_id {
    log!("Method ID upgrade transactions chain ID does not match circuit chain ID");
    continue;
}
``` [1](#0-0) 

and the mapping function is:

```
pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}
``` [2](#0-1) 

`Network::Nightly` and `Network::TestNetworkWithForks` are distinct enum variants used to run distinct node/circuit configurations (e.g. `TestNetworkWithForks` is used in fork test tooling for `bin/citrea/tests/bitcoin/fork.rs`, `bin/citrea/src/rollup/bitcoin.rs`, `crates/primitives/src/forks.rs`), yet they collapse to the identical `chain_id = 5665`.

Attack flow as specified: a genuine security-council-signed `BatchProofMethodId` blob broadcast for one network with `chain_id = 5665` (say produced/tested on `Nightly`) is bit-for-bit re-inscribed on a Bitcoin DA feed consumed by a node/light-client-prover configured with `Network::TestNetworkWithForks` (or vice-versa). When that node's circuit runs `run_l1_block` with `network = TestNetworkWithForks`, `citrea_network_to_chain_id(network)` again yields `5665`, which equals `body.chain_id`, so the chain-id gate is satisfied even though the body was never authorized for that specific network context. The signature check `verify_method_id_security_council` only verifies against the pubkeys and does not re-derive or bind the network identity beyond the `chain_id` field inside `body`, which is exactly the value that collides.

Existing guards that were checked and do not stop this:
- `verify_method_id_security_council` verifies signatures over `body.serialize()`, but `body.chain_id` is the very field that collides between the two variants, so signature validity is preserved across the replay.
- The `activation_l2_height` monotonicity check (`batch_proof_method_id.body.activation_l2_height <= last_activation_height`) does not prevent this since the two networks maintain independent JMT state / independent last activation heights.

### Impact Explanation
If `Nightly` and `TestNetworkWithForks` are both live, non-mainnet node configurations that the codebase's own guard mechanism is meant to isolate from each other (and from mainnet/testnet), this collision means a council-authorized method-id upgrade for one of these environments is accepted verbatim by the other's light-client-prover circuit. This is a method-id upgrade accepted on a network it was never authorized for, matching the "batch or light client proof accepted for a state transition that did not happen" / "method-id upgrade accepted that was never authorised" Critical impact category — but only between `Nightly` and `TestNetworkWithForks`; `Mainnet` (4114), `Testnet` (5115), and `Devnet` (62298) remain pairwise distinct and are not affected by this specific collision.

### Likelihood Explanation
Given the rules explicitly exclude `Mainnet` as an entry point and require no live Clementine, and given that `TestNetworkWithForks` and `Nightly` both appear to be internal testing/fork-simulation network identifiers (heavily referenced from `tests.rs`/fork test harnesses such as `bin/citrea/tests/bitcoin/fork.rs`), it is uncertain from the available index whether `TestNetworkWithForks` is ever run as a real, independently-keyed, publicly-reachable node outside of test harnesses (which are explicitly out of scope per the rules: `**/tests/**`, `**/tests.rs`, `test_utils.rs`). I was not able to fully confirm from the indexed code whether `TestNetworkWithForks` is a production-deployable network variant or purely a test-only fork-simulation identifier that never has independent council key material in a real deployment — this would need to be verified by reading `crates/primitives/src/forks.rs`, `bin/citrea/src/rollup/bitcoin.rs`, and `bin/citrea/src/main.rs` in full, which was not completed before the iteration limit.

### Recommendation
Make `citrea_network_to_chain_id` injective by assigning `Network::TestNetworkWithForks` its own distinct chain id (e.g. a value different from `5665`), and add a compile-time or unit-test invariant asserting pairwise distinctness across all `Network` variants so future additions cannot silently reintroduce a collision.

### Proof of Concept
```rust
// crates/light-client-prover/src/circuit/mod.rs (test module)
use sov_rollup_interface::Network;

#[test]
fn chain_id_mapping_is_injective() {
    let variants = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];
    let ids: Vec<u64> = variants.iter().map(|n| citrea_network_to_chain_id(*n)).collect();
    for i in 0..ids.len() {
        for j in (i + 1)..ids.len() {
            assert_ne!(
                ids[i], ids[j],
                "Network::{:?} and Network::{:?} collide on chain_id {}",
                variants[i], variants[j], ids[i]
            );
        }
    }
}
```
This test fails today because `citrea_network_to_chain_id(Network::Nightly) == citrea_network_to_chain_id(Network::TestNetworkWithForks) == 5665` [2](#0-1) , demonstrating that the intended binding "`citrea_network_to_chain_id` is injective across `Network` variants" does not hold.
