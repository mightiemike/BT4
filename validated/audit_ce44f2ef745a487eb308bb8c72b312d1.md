### Title
`DelegateAction` Expiry Off-by-One Allows Execution at `max_block_height` — (`File: runtime/runtime/src/actions.rs`)

### Summary

`apply_delegate_action` uses a strict `>` comparison to check whether a `DelegateAction` has expired. The field specification and the runtime documentation both state the action is valid only for blocks with height **strictly below** `max_block_height`, meaning the action must be rejected when `block_height >= max_block_height`. The code rejects only when `block_height > max_block_height`, leaving the boundary block (`block_height == max_block_height`) as an unguarded execution window. A malicious relayer can exploit this one-block gap to execute a `DelegateAction` the sender believed had already expired, causing an unauthorized transfer or contract call.

### Finding Description

In `apply_delegate_action`, the expiry guard is:

```rust
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
``` [1](#0-0) 

The `DelegateAction` struct documents `max_block_height` as:

> "The maximal height of the block in the blockchain **below which** the given DelegateAction is valid." [2](#0-1) 

The runtime specification document reinforces this:

> "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired` [3](#0-2) 

The existing test suite confirms the off-by-one: `test_delegate_action` passes `apply_state.block_height == max_block_height` and asserts `result.result.is_ok()`, while `test_delegate_action_max_height` only tests `max_block_height + 1` for the expired path. [4](#0-3) [5](#0-4) 

The same off-by-one applies to `DelegateActionV2` because both `Action::Delegate` and `Action::DelegateV2` dispatch to the same `apply_delegate_action` function. [6](#0-5) 

### Impact Explanation

A `DelegateAction` is a user-signed meta-transaction submitted by an untrusted relayer. The user sets `max_block_height` as a hard deadline: "do not execute this action at or after block `N`." Because the code uses `>` instead of `>=`, the relayer can submit the action at exactly block `N` and it will execute. Any action the user placed inside the delegate — including `Transfer`, `FunctionCall`, `AddKey`, `DeleteKey`, or `DeleteAccount` — executes against the user's intent. This maps directly to **unauthorized transaction execution** and **balance manipulation / fund loss** within the allowed impact scope.

### Likelihood Explanation

The relayer is an ordinary, unprivileged network participant. Timing a submission to a specific block height is straightforward: the relayer monitors the chain, holds the signed `DelegateAction`, and broadcasts it the moment the head reaches `max_block_height`. No validator access, key compromise, or network-level capability is required. The attack is deterministic and requires no probabilistic timing.

### Recommendation

Change the strict greater-than to greater-than-or-equal in `apply_delegate_action`:

```rust
// Before (off-by-one: allows execution at block_height == max_block_height)
if apply_state.block_height > delegate_action.max_block_height() {

// After (correct: rejects at block_height >= max_block_height)
if apply_state.block_height >= delegate_action.max_block_height() {
``` [1](#0-0) 

Add a test asserting `DelegateActionExpired` when `block_height == max_block_height` to lock the boundary.

### Proof of Concept

1. Alice signs a `DelegateAction` containing `Transfer { deposit: 100 NEAR }` with `max_block_height = N`. She hands it to relayer Charlie.
2. Alice decides to cancel. She reasons: "At block `N` the action expires; I am safe."
3. Charlie (malicious) watches the chain. At the moment block `N` is produced, Charlie broadcasts the signed `DelegateAction`.
4. The runtime evaluates `apply_state.block_height (= N) > delegate_action.max_block_height() (= N)` → `false` → **not expired**.
5. The transfer executes: 100 NEAR leaves Alice's account.
6. Alice loses 100 NEAR despite believing the action had expired.

The root cause is the `>` vs `>=` boundary in `apply_delegate_action` at `runtime/runtime/src/actions.rs:435`, directly analogous to the `<` vs `<=` boundary in the GroupBuy `_verifySuccessfulState` finding. [7](#0-6)

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
