Confirmed root cause. The `tokenExchange()` function in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` calls `decodeSessionToken(config)(sessionToken)` purely for its cryptographic/expiry validation side effect but discards the returned `JwtPayload` (which contains the `dest` claim — the shop the token was actually issued for). It then uses the separately-supplied `shop` parameter (`sanitizeShop(config)(shop, true)`) to build the token-exchange request URL and to stamp the returned `Session.shop`, with no check that `shop` matches the token's `dest`.

### Title
Shop/Session-Token Identity Confusion in `tokenExchange()` Due to Discarded JWT `dest` Claim - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`tokenExchange()` decodes and verifies the session token's signature/expiry but throws away the decoded payload instead of using its `dest` (shop) claim. The caller-supplied `shop` parameter — which per the library's own documented example (`docs/reference/auth/tokenExchange.md`) is expected to be read straight from `req.query.shop`, i.e., attacker-controlled request input — is used unchecked to pick which shop's OAuth endpoint receives the `subject_token` and which shop the resulting `Session` is stamped for.

### Finding Description [1](#0-0) 

The function:
1. Calls `await decodeSessionToken(config)(sessionToken);` and discards the result (line 39), even though `decodeSessionToken` normally returns a `JwtPayload` whose `dest` field identifies the shop the token was minted for [2](#0-1) .
2. Sanitizes and uses the separate `shop` argument (not derived from the token) to build the outbound request URL `https://${cleanShop}/admin/oauth/access_token` and to construct the returned `Session` (`shop: cleanShop`) [3](#0-2) .

The library's own documented usage pattern instructs integrators to derive `shop` from the request query string rather than from the session token: [4](#0-3) 

By contrast, the safe pattern used internally by `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` derives `shop` from the verified payload's `dest` claim before calling `tokenExchange` (e.g. `const payload = await api.session.decodeSessionToken(sessionToken); const shop = new URL(payload.dest).hostname;`) [5](#0-4) . Nothing in `tokenExchange()` itself enforces this discipline — the exported public API silently accepts any `shop` regardless of what the `sessionToken` actually attests to, since the decoded `dest` is thrown away instead of being compared against `shop`.

This mirrors the reported bug class: a value proven/verified by one code path (the decoded, cryptographically-validated JWT payload, analogous to `msg.sender` in the Solidity report) is discarded, and a separate, less-trustworthy value (the `shop` argument, analogous to `address(this)` acting on behalf of the wrong party) is substituted for the privileged action (minting/labeling the access token/session for a shop).

### Impact Explanation
If an integrator follows the library's documented pattern (`shop` from `req.query.shop`), an attacker who possesses (or replays) a valid session token for Shop A but forges the `shop` query parameter as Shop B could cause the app to submit Shop A's `subject_token` to Shop B's `/admin/oauth/access_token` token-exchange endpoint. Depending on how Shopify's server-side token-exchange grant behaves when the `subject_token`'s embedded shop and the target domain in the URL disagree, this can result in: session storage being populated with a `Session` object that has an attacker-chosen `shop` value but credentials/context actually tied to a different token, i.e. session-storage key/shop confusion, potentially leading to acting on the wrong tenant's data or a stored session under a wrong shop key. At minimum, it is a broken invariant in a security-sensitive primitive: the shop identity used for privileged token issuance is never validated against the identity asserted by the verified token.

### Likelihood Explanation
Reachable by any actor who can influence the `shop` query parameter/argument passed into `tokenExchange()`, which per the documented integration is exactly the untrusted HTTP request. No privileged access needed beyond obtaining/replaying a session token (which App Bridge issues to any authenticated browser session, and which is itself bearer-like). Likelihood is elevated for any app author who followed the published doc example verbatim instead of the safer pattern used in the framework packages.

### Recommendation
Capture the decoded payload and enforce that `shop` matches (or is derived from) `payload.dest` before using it:
```diff
-    await decodeSessionToken(config)(sessionToken);
+    const payload = await decodeSessionToken(config)(sessionToken);
+    const tokenShop = sanitizeShop(config)(new URL(payload.dest).hostname, true)!;
+    const cleanShop = sanitizeShop(config)(shop, true)!;
+    if (cleanShop !== tokenShop) {
+      throw new ShopifyErrors.InvalidSession(
+        'Session token shop does not match the provided shop',
+      );
+    }
-    const cleanShop = sanitizeShop(config)(shop, true)!;
```
Additionally, update `docs/reference/auth/tokenExchange.md` to stop recommending deriving `shop` from `req.query.shop`, and instead recommend deriving it from the decoded token, consistent with `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router`.

### Proof of Concept
1. Attacker obtains a valid App Bridge session token for `victim-a.myshopify.com` (e.g., by using the embedded app normally on that store, or via a replayed/leaked token).
2. Attacker sends a request to the app's token-exchange endpoint (built per the documented pattern) with `?shop=victim-b.myshopify.com` while supplying the session token for `victim-a`.
3. `shopify.auth.tokenExchange({ shop: 'victim-b.myshopify.com', sessionToken: <token for victim-a>, requestedTokenType })` is invoked.
4. `decodeSessionToken` validates the token's signature/expiry/audience successfully (it doesn't check `shop` at all) but its `dest` (`victim-a.myshopify.com`) is discarded.
5. The library POSTs the `victim-a` `subject_token` to `https://victim-b.myshopify.com/admin/oauth/access_token` and, on success, returns/stores a `Session` labeled `shop: 'victim-b.myshopify.com'` — a shop/session identity mismatch never validated by the library.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
