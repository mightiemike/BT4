### Title
LDAP local-fallback authentication leaks account existence via distinguishable error messages and timing (bcrypt vs. fast-fail) - ([File: core/sessions/ldapauth/ldap.go])

### Summary
When LDAP bind fails for a supplied email, `CreateSession` falls back to `localLoginFallback`, which returns raw, distinguishable errors (`sql.ErrNoRows` for non-existent local accounts vs. `"invalid password"` after a bcrypt comparison for existing accounts) directly to the HTTP layer. `SessionsController.Create` propagates this error message verbatim in the JSON API response, and the code path for existing accounts always executes the expensive `utils.CheckPasswordHash` (bcrypt) call while non-existent accounts short-circuit immediately, creating both a message-based and a timing-based oracle for local admin account enumeration.

### Finding Description
In `ldapAuthenticator.CreateSession` (`core/sessions/ldapauth/ldap.go:396-457`), when `conn.Bind` fails for the supplied email, `localLoginFallback(ctx, sr)` is invoked at line 426. Inside `localLoginFallback` (lines 624-642):
- For an email with no matching row in the `users` table, `l.ds.GetContext` returns immediately with `sql.ErrNoRows` (line 627-629) — no bcrypt call is executed, and the raw SQL error is returned.
- For an email that does exist, the query succeeds, `constantTimeEmailCompare` is effectively always true here (the SQL predicate already filtered `lower(email) = lower($1)`, so the returned row's email always matches), and execution proceeds to `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))` (line 636), which performs a bcrypt hash comparison — an intentionally slow operation — before returning `"invalid password"`.

This `returnErr` is passed back up through `CreateSession` unmodified (`return "", returnErr` at line 432) and handed to `jsonAPIError(c, http.StatusUnauthorized, err)` in `SessionsController.Create` (`core/web/sessions_controller.go:56-60`), which serializes the underlying error text into the HTTP response body. Consequently:
1. Non-existent local emails produce a fast response with a generic SQL "no rows" error.
2. Existing local emails with wrong passwords produce a measurably slower response (bcrypt) with the distinct string `"invalid password"`.

No rate limiting, generic error normalization, or constant-time delay padding exists in this path to mask the difference. Any unauthenticated caller can hit `POST /sessions` with an arbitrary email and password, since LDAP bind failure is trivial to trigger with any non-existent LDAP username, deterministically reaching this fallback code every time.

### Impact Explanation
This allows an unprivileged attacker to enumerate valid local admin (CLI) account emails stored in the local `users` table by observing (a) different response latency (bcrypt cost factor, typically tens to hundreds of milliseconds) and (b) different error text between existing and non-existing accounts. This is a user-enumeration issue, which — while not full compromise — meaningfully reduces the attacker's search space for subsequent credential-stuffing or brute-force attacks against the local admin login, especially since local admin accounts are typically high-privilege in Chainlink node deployments.

### Likelihood Explanation
Feasibility is high and requires no preconditions beyond LDAP being enabled with local-admin fallback support (a documented, supported configuration per the package doc comment). Triggering LDAP bind failure is trivial (any nonexistent/garbage LDAP username fails bind). The oracle is deterministic and repeatable across requests, and timing differences from bcrypt are generally large enough to be reliably distinguished over a small number of samples, even over a network, especially combined with the message-content difference which is unambiguous and doesn't even require timing analysis.

### Recommendation
- Normalize all authentication failure responses at the `SessionsController.Create` boundary (and within `localLoginFallback`) to a single generic error (e.g., `"invalid credentials"`) regardless of whether the email exists, the LDAP bind failed, or the password check failed.
- Ensure a constant-time code path: when the local user lookup misses (`sql.ErrNoRows`), perform a dummy `utils.CheckPasswordHash` against a fixed/dummy hash before returning, so that the non-existent-user path takes comparable time to the existing-user path.
- Avoid returning raw internal errors (`err` from `sql.ErrNoRows`, or descriptive messages like `"invalid password"`/`"invalid email"`) to the HTTP layer; log detailed errors internally, and return only the generic message externally.

### Proof of Concept
Integration test in `core/sessions/ldapauth/ldap_test.go` (or a new test file):
1. Seed the `users` table with one known local admin account (`admin@example.com`, known bcrypt hash).
2. Call `ldapAuthenticator.CreateSession` (with an `LDAPClient` mock that always fails `Bind`) twice:
   - Case A: `sr.Email = "admin@example.com"`, `sr.Password = "wrongpassword"`.
   - Case B: `sr.Email = "doesnotexist@example.com"`, `sr.Password = "wrongpassword"`.
3. Assert that:
   - The returned error strings differ (`"invalid password"` vs. a `sql.ErrNoRows`-derived message) — demonstrating the message-based oracle.
   - Measure wall-clock duration of both calls (average over N runs); assert that Case A (bcrypt path) takes significantly longer (e.g., >5x) than Case B (fast-fail path) — demonstrating the timing oracle.
4. Expected (fixed) behavior: both cases return an identical generic error string and comparable execution time (within a small tolerance), regardless of account existence.
