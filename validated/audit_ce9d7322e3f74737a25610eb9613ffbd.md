## Title
Fixed Static Gas Stipend for Wallet Contract Callbacks Can Cause Permanent Denial-of-Service on `has_in_flight_tx` - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

## Summary
The external report describes WSHIDO's `withdraw()` using a fixed, non-scaling gas stipend (`transfer()`'s 2,300 gas) for a downstream operation, which can be insufficient and cause a revert that blocks fund delivery. The analogous pattern exists in nearcore's `near-wallet-contract`, where several internal callback promises are attached a **hardcoded, fixed** amount of static gas (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, each based on `Gas::from_tgas(5)`) rather than gas that scales with the size of data an external, attacker-influenced contract can return. If this fixed budget is exhausted before the callback can persist its state update, the whole receipt aborts and the previously-made state write is rolled back, leaving the contract's `has_in_flight_tx` flag permanently stuck at `true`.

## Finding Description
`WalletContract` guards against concurrent transactions with the invariant flag `has_in_flight_tx`, and `rlp_execute` refuses to process any new transaction while it is `true`: [1](#0-0) 

Every code path that returns a `Promise` sets `has_in_flight_tx = true` before yielding, and each corresponding callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) is expected to reset it back to `false` as its first action: [2](#0-1) [3](#0-2) 

These callbacks are scheduled with a **fixed** static gas constant rather than a value that scales with untrusted, externally-supplied response sizes: [4](#0-3) [5](#0-4) 

The only variable component added is `action.gas()`, which is gas attached to the *user's own action*, not gas reserved for processing an arbitrarily large `PromiseResult::Successful(value)` payload coming back from an external contract (e.g. the address registrar's `lookup` result, or a NEP-141-like token's `storage_balance_of` response). Both `address_check_callback` and `nep_141_storage_balance_callback` call `serde_json::from_slice(&value)` on that externally-controlled payload before ever writing `has_in_flight_tx = false` is durable — but since Near/WASM function execution is all-or-nothing, if the fixed 5 Tgas budget is exhausted (e.g. by a malicious or just unusually verbose registrar/token contract returning an oversized JSON blob, or by many nested/large fields), the entire callback receipt fails with `GasExceeded` and **none of its state writes are persisted**, including the reset of `has_in_flight_tx`.

Because the flag was already set to `true` before the promise chain was dispatched, and no other codepath can ever clear it once the resolving callback receipt itself perpetually fails, the wallet contract becomes permanently stuck in "transaction already in progress" state — exactly mirroring the WSHIDO analog where a fixed, too-small gas/stipend budget for a downstream, potentially attacker-influenced step causes an unrecoverable failure that blocks the intended fund/state operation forever.

## Impact Explanation
Once `has_in_flight_tx` is stuck `true`, `rlp_execute` unconditionally rejects all further transactions for that account: [6](#0-5) 
This is the sole entry point for interacting with the ETH-implicit account's wallet contract (used for ETH-emulated transfers/ERC-20 transfers as exercised by `test_wallet_contract_interaction`), so all $NEAR and NEP-141 balances controlled by that wallet become permanently inaccessible through the intended mechanism — a "permanently frozen funds" outcome triggered by a single crafted receipt/response from an external contract the relayer/attacker can choose as `target` (the address registrar or NEP-141 token contract in the ERC-20 emulation path).

## Likelihood Explanation
An attacker who can deploy or control a NEP-141-like token contract (or exploit any contract registered as the `ADDRESS_REGISTRAR_ACCOUNT_ID`) and get a wallet-contract-backed ETH-implicit account to interact with it (via the ERC-20 or EOA base-token-transfer emulation paths in `internal.rs`) can return an oversized `storage_balance_of` / `lookup` response designed to exhaust the fixed 5 Tgas callback budget during deserialization, deterministically triggering the stuck state. This requires only crafting a malicious/faulty contract response reachable through a normal relayer-submitted `rlp_execute` transaction — no privileged or network-level access is needed.

## Recommendation
Do not rely on a fixed constant gas budget for callbacks that must process externally-controlled response payloads (`address_check_callback`, `nep_141_storage_balance_callback`). Either bound/validate the size of `PromiseResult::Successful` payloads before deserializing, reserve gas proportional to the maximum expected/allowed payload size, or restructure the callback so that clearing `has_in_flight_tx` happens in a minimal, gas-cheap step that is guaranteed to complete (e.g., persist it eagerly via a low-gas dedicated call, or use `#[private]` panic-safe patterns) regardless of downstream deserialization cost.

## Proof of Concept
1. Deploy a NEP-141-token-lookalike contract at some `token_id`/registrar-equivalent account that implements `storage_balance_of` (or the registrar's `lookup`) but returns a very large/expensive-to-deserialize JSON value in its result.
2. Have a relayer submit an `rlp_execute` transaction on behalf of an eth-implicit wallet contract account targeting this contract via the ERC-20 emulation path (`EthEmulationKind::ERC20Transfer`), reaching: [7](#0-6) 
3. The wallet contract sets `has_in_flight_tx = true` and dispatches the promise with `callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`.
4. When the callback `nep_141_storage_balance_callback` runs, `serde_json::from_slice(&value)` on the oversized payload exhausts the fixed portion of gas before `self.has_in_flight_tx = false` is durably committed, causing the whole receipt to fail with `GasExceeded`.
5. All subsequent calls to `rlp_execute` on this wallet contract now return `"Error: transaction already in progress, please try again later."` permanently, as confirmed by the existing test demonstrating this exact rejection behavior when `has_in_flight_tx` is `true`: [8](#0-7)

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

/// Only one transaction can be in flight at a time.
#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
