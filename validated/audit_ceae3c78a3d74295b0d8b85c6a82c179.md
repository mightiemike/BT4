## Analysis

The exploit path described is real and verifiable in the ante-handler ordering.

`AccountInitDecorator.AnteHandle` gates purely on `txpolicy.IsGaslessTx(tx)`, which only checks the *message type URL* against the static allowlist in `app/txpolicy/gasless.go` — `/utss.v1.MsgVoteFundMigration` is on that list — with no check on whether the signer is a bonded (or even registered) Universal Validator. [1](#0-0) 

Given a gasless tx, if the signer has no existing account (`!aid.ak.HasAccount`), the decorator verifies the signature against `account_number=0, sequence=0` (which any freshly-generated keypair trivially satisfies for its own self-signed message), then calls `aid.ak.NewAccountWithAddress`, sets sequence to 1, persists it via `SetAccount`, and returns `ctx, nil` — short-circuiting the remainder of the ante chain (sig-count, sig-verification, fee deduction, gas consumption, increment-sequence decorators). [2](#0-1) 

This decorator runs *before* `SetPubKeyDecorator`/`SigVerificationDecorator`/`IncrementSequenceDecorator` in the chain, and — critically — entirely before message execution, where the actual authorization check (`IsBondedUniversalValidator`) lives inside `VoteFundMigration`'s `msgServer` implementation, not in the ante pipeline. [3](#0-2) [4](#0-3) 

In Cosmos SDK's `runTx`, the ante-handler's cache-multistore is written (`msCache.Write()`) immediately after the ante handler succeeds, *before* message execution runs in its own separate cache context. Since `AccountInitDecorator` returns `nil` error, the new account (`sequence=1`) is committed to state unconditionally — even though the subsequent `VoteFundMigration` message execution will fail downstream with "not bonded" and get rolled back. The account persists; only the message-level state changes are reverted.

Because `MinGasPriceDecorator` and `DeductFeeDecorator` also skip fee/balance checks for gasless txs, an attacker can generate an arbitrary number of fresh keypairs, sign one `MsgVoteFundMigration` each, and broadcast them — creating one spurious `BaseAccount` (sequence=1) per submission at literally zero token cost, regardless of the eventual downstream rejection.

### Title
Free/unauthenticated account creation via gasless `MsgVoteFundMigration` allowlisting - (File: `app/ante/account_init_decorator.go`, `app/txpolicy/gasless.go`)

### Summary
`AccountInitDecorator` creates and persists new on-chain accounts for any address that signs a gasless-whitelisted message, without checking whether the signer holds any authorization for that message type. Because `MsgVoteFundMigration` is unconditionally gasless and its `IsBondedUniversalValidator` check happens only in the message handler (after the ante chain and after account/state persistence), an unprivileged, never-bonded attacker can create unlimited spurious accounts for zero fee.

### Finding Description
The gasless allowlist check in `IsGaslessTx` is purely message-type based, with no signer authorization component. `AccountInitDecorator` uses this same check to decide whether to auto-provision an account for a first-time signer, verifying only that the signature is self-consistent (matches `account_number=0, sequence=0`) — not that the signer is entitled to submit that message. Since ante-handler state is committed before message execution, the account-creation side effect survives even when the message itself is later rejected for lacking bonded-UV status.

### Impact Explanation
This allows unbounded, cost-free growth of the `x/auth` account store (state bloat) by any unprivileged attacker, since each new keypair yields one new persisted account regardless of the eventual message-level rejection. This is a resource/storage-exhaustion concern rather than fund loss, reachable without any privileged role, gas payment, or bonded status.

### Likelihood Explanation
High — the only cost to the attacker is generating an ECDSA/Ed25519 keypair and signing a transaction; no tokens, gas, or validator bonding are required. The attack is trivially scriptable and repeatable.

### Recommendation
Gate `AccountInitDecorator`'s account-creation branch on an authorization check specific to the message content (e.g., only allow account auto-creation for `MsgVoteFundMigration`/`MsgVoteTssKeyProcess`/`MsgVoteOutbound`/`MsgVoteInbound`/`MsgVoteChainMeta` when the signer is already a registered/bonded Universal Validator, mirroring the check that currently lives only in the msg-server), or apply a minimal, non-refundable resource cost (e.g., mandatory minimal gas consumption tied to a bonded-check pre-flight) before persisting new accounts.

### Proof of Concept
1. Generate N fresh keypairs (no funding needed).
2. For each keypair, construct and self-sign a `MsgVoteFundMigration{Signer: addr, MigrationId: <any existing pending id>, TxHash: "...", Success: true}` transaction with zero fee (qualifies as gasless per `app/txpolicy/gasless.go`).
3. Broadcast each transaction. `AccountInitDecorator` verifies the self-signature (trivially valid), creates and persists a `BaseAccount` with `sequence=1`, and short-circuits the ante chain.
4. Message execution subsequently fails in `VoteFundMigration`/`IsBondedUniversalValidator` ("not bonded"), but query `auth` module state afterward and confirm the N new accounts exist despite every message having failed.

		return nil, fmt.Errorf("invalid signer address: %w", err)
