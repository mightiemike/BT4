This finding maps cleanly onto TRON's `ExchangeCapsule.transaction` logic in the token exchange (bonding-curve) actuators.

### Title
Missing non-negative balance check on legacy Exchange bonding-curve calculation allows exchange pool balances to go negative - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via a bancor-style bonding-curve formula and then derives `newFirstTokenBalance`/`newSecondTokenBalance` by simple addition/subtraction of `long`s. The resulting new pool balance is only checked for being non-negative when the `hardenedCalc` flag is `true` (i.e., when `allowHarden()` is active). When it is `false` — the legacy/default path using `ExchangeProcessor` with floating point math — the arithmetic proceeds unchecked and the new balances are written directly into the `Exchange` state, exactly mirroring the reported Vyper bug where `new_total_value` (derived from a computed delta) is trusted to be non-negative without validation.

### Finding Description
The core computation lives in `ExchangeCapsule.transaction()`: [1](#0-0) 

The `buyTokenQuant` is computed by `ExchangeProcessor.exchange()`, which uses double-precision floating point (`Maths.pow`) to model a Bancor-relay bonding curve: [2](#0-1) 

When `hardenedCalc` is `false` (the legacy path), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `long` arithmetic and there is **no check that they remain non-negative** before being persisted: [3](#0-2) 

The `SafeExchangeProcessor`/`hardenedCalc=true` path (guarded behind `StrictMathWrapper.subtractExact`/`addExact` and an explicit `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check) is precisely the fix the report recommends — but it is only exercised when `allowHarden()` returns true, which is a chain-parameter/hard-fork gated proposal, not the default behavior for all versions/paths. The unguarded floating-point path (`ExchangeProcessor`) can, due to double-precision rounding error near the edges of the bonding curve (e.g., very large `sellTokenQuant` relative to `buyTokenBalance`, or repeated small trades accumulating rounding drift), yield a `buyTokenQuant` that exceeds the actual pool reserve, driving `newSecondTokenBalance`/`newFirstTokenBalance` negative. Since these are persisted directly into the `Exchange` protobuf message without any post-condition check, the negative balance becomes part of on-chain state — an invalid-state condition analogous to the reported `new_total_value` going negative.

This is invoked from unprivileged, permissionless actuators reachable by any account: `ExchangeTransactionActuator.execute()`/`doValidate()` call `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`. [4](#0-3) [5](#0-4) 

`ExchangeInjectActuator`/`ExchangeWithdrawActuator` interact with the same balances through similar unchecked arithmetic (`addExact`/plain subtraction) for pool balance updates. [6](#0-5) 

### Impact Explanation
A negative token balance recorded for an `Exchange` breaks the fundamental invariant that pool reserves must be non-negative. Since subsequent trades use these balances as inputs to the bonding-curve formula (`exchangeToSupply`/`exchangeFromSupply`), a corrupted negative balance can cascade into further incorrect pricing, letting an attacker extract more of the other token than the pool actually holds — a fund-drain / accounting-divergence issue in the on-chain TRC10 exchange market feature. This is a state-corruption/accounting integrity issue reachable by any user, not requiring privileged access.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires either (a) interacting with the exchange on a chain/version where `allowHarden()` (the hardened-math proposal) has not been activated, so the unchecked floating-point path is used, or (b) crafting trade sizes that push the double-precision bonding curve calculation past the point where rounding causes `buyTokenQuant` to exceed the actual counter-balance. The `SafeExchangeProcessor` introduced in the codebase (with `addExact`/`subtractExact` and the explicit `< 0` checks) indicates the java-tron team already recognized and partially mitigated this exact class of issue, gated behind a governance-activated proposal.

### Recommendation
Make the negative-balance guard and safe (`Math.addExact`/`subtractExact`) arithmetic unconditional rather than gated behind `hardenedCalc`/`allowHarden()`, so that `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` always throws `ContractValidateException` regardless of the hard-fork flag, closing the gap for any deployment/version where the hardened path isn't yet active.

### Proof of Concept
1. Deploy/observe an Exchange (`ExchangeCreateActuator`) with small token reserves on a network state where `allowHarden()` is false (legacy default path).
2. Submit an `ExchangeTransactionContract` with a `sellTokenQuant` sized so that the double-precision Bancor-relay computation in `ExchangeProcessor.exchangeFromSupply` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:31-39`) rounds `buyTokenQuant` up to a value exceeding `secondTokenBalance` (or `firstTokenBalance`).
3. `ExchangeCapsule.transaction()` computes `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (line 145) without any non-negative check (the check at line 160 only applies when `hardenedCalc` is true), storing a negative balance into the `Exchange` capsule.
4. Subsequent trades against this exchange use the corrupted negative balance as an input to the bonding-curve math, producing further incorrect exchange rates and allowing extraction of tokens beyond the pool's actual holdings.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
