## Analysis

Reducing the external report's invariant: an operation returns a status/result that indicates whether committed data is authentic, but the caller doesn't check it before treating the operation as verified. The Aptos-native analog I found is in `TransactionOutput::ensure_match_transaction_info`, which is the function that validates a computed `TransactionOutput` against the authenticated `TransactionInfo` stored in the accumulator/proof during replay and restore.

### Title
`ensure_match_transaction_info` omits verification of state/hot-state/position-state checkpoint hashes, allowing replay-verify to accept a diverging authenticated state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk/replay verification (via `ChunkResultVerifier` and `ledger_update_output.ensure_transaction_infos_match`) to confirm a locally recomputed transaction output matches the authenticated `TransactionInfo` sourced from proofs. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of the authenticated `TransactionInfo`/`TransactionInfoV1` and are meant to bind the transaction to the state Merkle root at that version.

### Finding Description
The check performed is: [1](#0-0) 

It validates `status`, `gas_used`, `write_set_hash` (via `state_change_hash`), and `event_root_hash`, then returns `Ok(())` unconditionally afterward: [2](#0-1) 

The comment directly preceding the `Ok(())` acknowledges the gap: the comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), meaning replay-verify tooling (e.g., db-tool's `replay_on_archive`) can report success even when the authenticated position state root diverges from local execution.

This function's caller chain is used in the state-sync / chunk-executor replay-verification path: `ChunkResultVerifier::verify_chunk_result` and `ReplayChunkVerifier::verify_chunk_result` both call `ledger_update_output.ensure_transaction_infos_match`, which ultimately validates transaction-level state against the accumulator-proved `TransactionInfo`: [3](#0-2) [4](#0-3) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as fields that are meant to authenticate the resulting state tree(s): [5](#0-4) 

The `compute_trading_native_state_roots` feature (which gates `position_state_checkpoint_hash` production) is wired through the execution/chunk-executor pipeline, including `DoLedgerUpdate`/`DoStateCheckpoint` and `execution_output.rs`, indicating this is active machinery rather than dead code: [6](#0-5) 

### Impact Explanation
If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or in general, state/hot-state checkpoint hash validation) is enabled/relevant, a node performing chunk-based execution, replay, or backup/restore verification can compute a state tree that differs from the one committed on-chain/authenticated by consensus, yet `ensure_match_transaction_info` will still return `Ok(())` because only the write-set hash and event root are checked — not the checkpoint (state root) hashes themselves. This means the "authenticated" verification gate for replay/restore silently accepts a corrupted or diverging state summary, defeating the purpose of state-proof verification during restore/replay. This is a genuine proof-integrity gap matching the "Wrong ... state proof accepted as valid" class from the required impacts.

However, this impact is conditioned on how central these checkpoint hashes are to consensus-critical validation elsewhere (e.g., whether the accumulator's `TransactionInfo` hash — which does cover the whole struct including these fields via `CryptoHash`/`BCSCryptoHash` — is independently checked at a different point, such as accumulator proof verification itself). The accumulator proof binds the *hash of the whole* `TransactionInfo` (including checkpoint hash fields) to the ledger root; `ensure_match_transaction_info` is a *secondary* sanity check comparing computed output vs. the already-proven `TransactionInfo`. Since the `TransactionInfo` values themselves come from the untrusted/local recomputation being verified, and the proof only confirms the `TransactionInfo` blob hasn't been tampered with in transit (i.e., matches the ledger), it does NOT confirm that the locally-computed checkpoint hash matches the one in the authenticated `TransactionInfo`. That specific full-value comparison is exactly what `ensure_match_transaction_info` is supposed to do, and for checkpoint hashes it skips this comparison entirely.

### Likelihood Explanation
This is a self-acknowledged TODO in the code, explicitly gated behind not yet enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` for the position-state case, and it's unclear from the available code whether `state_checkpoint_hash`/`hot_state_checkpoint_hash` (the non-trading-native ones) are validated elsewhere in the normal (non-trading) execution path outside of this function. I was not able to fully confirm within the available tool budget whether `state_checkpoint_hash` mismatches are caught by another mechanism (e.g., `DoStateCheckpoint` comparing against `known_state_checkpoints` during chunk execution, seen at `chunk_executor/mod.rs:374-379`), which would reduce/negate the impact for the plain state root (as opposed to the position-state root gated by the still-disabled feature). This ambiguity, combined with the feature being explicitly called out as not-yet-enabled in the code comment itself, lowers confidence that this is currently exploitable on mainnet today rather than being a documented pre-existing gap for an unlaunched feature.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) between the locally computed value and `txn_info`, consistent with how `write_set_hash` and `event_root_hash` are already validated, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production and for any replay/restore verification tooling that relies on this function.

### Proof of Concept
Not independently constructible from static analysis alone — would require running `db-tool`'s `replay_on_archive` or the state-sync chunk executor with a maliciously/incorrectly-computed local state checkpoint hash (differing from the archived/authenticated `TransactionInfo`) and observing that `ensure_match_transaction_info` still returns success. I could not execute this in the current environment, so this remains a code-level finding backed by the explicit TODO comment rather than a verified runtime exploit.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
