## Title
`isExchangeTransaction()` bypass causes duplicate resource/fee consumption when `ALLOW_HARDEN_EXCHANGE_CALCULATION` is active - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

## Summary
### Finding Description
The reported Malt bug class is: a code path performs unchecked/wraparound arithmetic in one layer (Uniswap V2, Solidity 0.5.16) while a dependent consumer layer (`MaltDataLab`, Solidity 0.8) performs checked arithmetic on the same values, so a legitimate, unprivileged state transition (`stabilize()`) permanently reverts once the underlying counter wraps.

java-tron has introduced an almost identical structural pattern for its `Exchange*` actuators via the `ALLOW_HARDEN_EXCHANGE_CALCULATION` dynamic property. Two code paths compute the exact same pool-balance transition with different arithmetic semantics that are switched by a single flag:

- Default (flag = 0): `ExchangeCapsule.transaction()` and `AbstractExchangeActuator.addExact/subtractExact` use plain `+`/`-` (silent wraparound, mirrors Uniswap's "overflow is desired" semantics). [1](#0-0) [2](#0-1) 

- Hardened (flag = 1): the same balances are run through `StrictMathWrapper.addExact/subtractExact` and `SafeExchangeProcessor`, which throw `ArithmeticException` on overflow/underflow, exactly like Solidity 0.8's checked math in `MaltDataLab`. [3](#0-2) [4](#0-3) 

Once this proposal is activated on-chain (a normal governance/committee proposal path, not privileged-attacker abuse of a leaked key), `Manager.isExchangeTransaction()` — used to special-case fee/energy accounting for exchange contracts — flips behavior: [5](#0-4) 

```
// Default: hardened disabled (==0) -> contract is treated as exchange
// Hardened enabled -> bypass returns false
```

This means that as soon as `ALLOW_HARDEN_EXCHANGE_CALCULATION` is turned on, `ExchangeTransactionContract` transactions are no longer classified as exchange transactions by `Manager`, changing their resource-accounting treatment network-wide for every future exchange transaction, while simultaneously the actuator execution path becomes strict-checked and will throw `ArithmeticException` (wrapped into `ContractExeException`, i.e. a permanent transaction failure) for any exchange pool whose balances are already close to `Long.MAX_VALUE` from years of legitimate `ExchangeInject`/`ExchangeWithdraw` activity accumulated under the old unchecked semantics. [6](#0-5) [7](#0-6) 

### Impact Explanation
Any TRX/TRC10 exchange pool (`ExchangeCapsule`) whose `firstTokenBalance`/`secondTokenBalance` has grown, via ordinary unprivileged `ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` broadcasts, to a level where a subsequent `addExact` would overflow a `long`, will have every future `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` against that pool permanently fail once hardening is enabled — precisely the "stabilize() always reverts" DoS pattern from the report, applied to on-chain exchange pools rather than to a stability contract. This is a state-transition/accounting DoS reachable by any broadcast transaction against the affected pool, not by a privileged actor.

### Likelihood Explanation
Reaching an actual `long` overflow requires exchange balances to approach `Long.MAX_VALUE` (≈9.2×10^18), which is unlikely under realistic TRX/TRC10 supply constraints, and the underlying `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal must first be activated by committee vote (gated by `ProposalUtil`/fork checks per `ProposalUtilTest`). This substantially reduces likelihood versus the original Malt finding, where every `stabilize()` call was already exposed to Uniswap's routine, expected 256-bit wraparound. I could not fully verify from the index whether any exchange pool balances anywhere near this magnitude exist or are reachable in practice, nor could I confirm whether `ALLOW_HARDEN_EXCHANGE_CALCULATION` is currently active on mainnet — this would need to be checked in a live/full-repo session.

### Recommendation
- Ensure the hardened (`addExact`/`subtractExact`) path is only ever exercised transactionally per-pool with a pre-check that gracefully rejects (as a normal `ContractValidateException`, at `validate()` time) rather than surfacing raw `ArithmeticException` from `execute()`, so it cannot degrade into a permanent, retry-proof failure for a given pool.
- Add an explicit upper bound / cap on `ExchangeCapsule` balances enforced consistently regardless of the hardening flag, so pools can never approach the overflow boundary in the first place.
- Audit `Manager.isExchangeTransaction()`'s flag-dependent bypass logic separately, since it silently changes fee/resource accounting classification for all exchange transactions the moment the proposal activates — this should be validated against the intended semantics of energy/bandwidth billing for exchange contracts.

### Proof of Concept
1. Over time, via ordinary `ExchangeInjectContract` transactions, grow an exchange pool's `firstTokenBalance` to `Long.MAX_VALUE - 5` (as demonstrated feasible for the accounting logic in the existing test): [8](#0-7) 
2. A committee proposal activates `ALLOW_HARDEN_EXCHANGE_CALCULATION` (value 1) via `ProposalService`: [9](#0-8) 
3. Any subsequent unprivileged `ExchangeTransactionContract` against that pool calls `AbstractExchangeActuator.addExact`, which now routes to `StrictMathWrapper.addExact`, throws `ArithmeticException`, and the actuator wraps it into a `ContractExeException`, permanently failing every transaction against this pool going forward — the same "always reverts" outcome described in the Malt report.
