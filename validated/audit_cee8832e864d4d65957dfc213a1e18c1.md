## Analysis: UTX-key delimiter collision analog of the Ondo `txnHash` collision

### Title
Naive `":"`-delimited concatenation in `GetInboundUniversalTxKey` / `GetPcUniversalTxKey` allows two distinct inbound identities to collide on the same `UniversalTx` key - (File: `x/uexecutor/types/keys.go`)

### Summary
The Ondo bug arose because `txnHash = keccak256(payload)` was computed over `abi.encode`d fields (`version, srcSender, amt, nonce`) that omitted the true scoping fields (`srcChain`, `srcAddr`), so two logically distinct transactions could hash to the same key and overwrite each other's approval state. Push Chain's `x/uexecutor` module has the same *class* of defect in the UTX-identity derivation, and the codebase itself documents the fix pattern (per-field hashing) elsewhere but does not apply it here.

### Finding Description
`GetInboundUniversalTxKey` derives the canonical `UniversalTx` id used as the store key for `PendingInbounds`, `ExpiredInbounds`, and `UniversalTx` from a raw, delimiter-joined string rather than an injective per-field digest: [1](#0-0) 

Compare this to `GetInboundBallotKey`/`GetOutboundBallotKey`, which use `hashFields`, explicitly designed to avoid exactly this class of bug: [2](#0-1) 

The comment on `hashFields` states outright that per-field hashing "makes it injective — a sub-hash can't contain ':', so no field value can shift a boundary and collide with a different tuple" — i.e. the authors were aware of delimiter-collision risk and mitigated it for ballot keys, but `GetInboundUniversalTxKey` (and its sibling `GetPcUniversalTxKey`) still use the vulnerable raw-concatenation-then-hash construction: [3](#0-2) 

Two properties make the delimiter genuinely ambiguous rather than merely theoretical:
1. `source_chain` is itself a CAIP-2 id that already contains an embedded `:` (e.g. `"eip155:11155111"`), so the three logical fields are not each free of the join character even before considering the other two.
2. `LogIndex` is never namespace-canonicalized or charset-restricted anywhere in the derivation — it is only `strings.TrimSpace`'d — unlike `Sender`/`AssetAddr`/`TxHash`, which for `eip155`/`solana` are forced into a strict hex/base58 shape via `LenientCanonicalizeAddress`/`LenientCanonicalizeTxHash`: [4](#0-3) 

For any chain namespace that is *not* `eip155` or `solana`, `CanonicalizeTxHashByNamespace`/`CanonicalizeAddressByNamespace` fall through to the `default` branch, which returns the value **unchanged**, with no charset enforcement at all: [5](#0-4) 

This means that for such a chain (or for the `LogIndex` field on any chain, since it is never namespace-canonicalized regardless of namespace), two different `(chain, txHash, logIndex)` triples can be engineered to produce the identical joined string `"%s:%s:%s"`, and therefore the identical SHA-256 `UniversalTx`/`PendingInbounds` key, even though they represent two entirely different source-chain events.

### Impact Explanation
The UTX key is the canonical identity used to create the `UniversalTx` record via `CreateUniversalTx`, and the same key is used earlier to group ballot variants in `PendingInboundEntry`: [6](#0-5) [7](#0-6) 

If two distinct logical inbound events collide on this key:
- Their votes/variants get cross-linked in the same `PendingInboundEntry.utx_key` bucket rather than being tracked as separate logical events, and/or
- The second event's `CreateUniversalTx` call fails outright (`"universal tx with key %s already exists"`), because `CreateUniversalTx` errors rather than overwriting: [8](#0-7) 

Either outcome means the second, independently-valid inbound never gets its own canonical UTX record and therefore never gets its deposit minted / payload executed — a permanent-freezing/fund-loss outcome for that user, and a corruption of the "canonical UniversalTx state" invariant the module's own README asserts (`UniversalTx` is described as append-only and "lives forever" per event) [9](#0-8) .

### Likelihood Explanation
This is materially weaker than the Ondo M-03 finding as an *unprivileged-attacker-only* bug, and I could not fully verify exploitability within the tool budget available:
- For chains currently canonicalized strictly (`eip155`, `solana`), `TxHash`/`Sender`/`AssetAddr` are forced into fixed hex/base58 shapes that cannot contain `:`; the only unguarded field is `LogIndex`, whose value is derived from the real event's log index (normally a small integer assigned by the source chain itself, not free text an ordinary user can shape into an arbitrary colon-containing string).
- The `default` (no validation) canonicalization branch only becomes exploitable if `x/uregistry` registers a chain under a namespace other than `eip155`/`solana`; I was not able to confirm within the remaining budget whether such non-EVM/non-Solana chain configs are currently deployed.
- I was also unable to confirm whether `MsgVoteInbound.ValidateBasic` (or another guard) independently restricts `LogIndex` to a digit-only format across all code paths, which would foreclose this vector even for unvalidated namespaces.

Given these open questions, likelihood is **Low-to-Medium**: the code contains a real, self-acknowledged architectural inconsistency (naive delimiter join vs. the injective `hashFields` pattern used elsewhere), but a concrete unprivileged trigger depends on registry/namespace configuration and event-format details I could not fully verify.

### Recommendation
Replace `GetInboundUniversalTxKey` and `GetPcUniversalTxKey`'s raw `fmt.Sprintf("%s:%s:%s", ...)` + `sha256` construction with the same `hashFields`-style per-field hashing already used for ballot keys, so that no combination of field values can shift a delimiter boundary and collide with a different (chain, txHash, logIndex) tuple. Additionally, canonicalize/validate `LogIndex` (e.g., require it to be a non-negative integer string) regardless of chain namespace, consistent with the strict treatment already given to `TxHash`/`Sender` for `eip155`/`solana`.

### Proof of Concept
Conceptual (not independently verified against a live chain registry/config, due to tool-call limits):
1. Register or observe events from a source chain namespace that is not `eip155`/`solana` (or otherwise obtain an inbound whose `LogIndex` is attacker-influenceable to embed a colon character).
2. Craft/observe inbound A: `source_chain = "X:1"`, `tx_hash = "hashA"`, `log_index = "1"` → joined string `"X:1:hashA:1"`.
3. Craft/observe inbound B: `source_chain = "X:1:hashA"`, `tx_hash = "1"`, `log_index = ""` (or any other split of the same total string) → joined string also `"X:1:hashA:1"`.
4. Both produce identical `sha256("X:1:hashA:1")`, i.e. identical `UniversalTx`/`PendingInbounds` keys, despite being distinct logical events, causing the second event's `CreateUniversalTx` to fail (`already exists`) or its votes to be recorded against the wrong `PendingInboundEntry`.

// GetInboundUniversalTxKey: UTX identity from canonical (source_chain, tx_hash,
// log_index). Canonicalizes locals; caller's inbound is not mutated.
func GetInboundUniversalTxKey(inbound Inbound) string {
	chain := strings.TrimSpace(inbound.SourceChain)
	txHash := utils.LenientCanonicalizeTxHash(chain, inbound.TxHash)
	logIndex := strings.TrimSpace(inbound.LogIndex)
	data := fmt.Sprintf("%s:%s:%s", chain, txHash, logIndex)
	hash := sha256.Sum256([]byte(data))
	return hex.EncodeToString(hash[:]) // hash[:] converts [32]byte → []byte
}

// hashFields = sha256( hex(sha256(domain)) : hex(sha256(f0)) : ... ). Per-field
// hashing makes it injective — a sub-hash can't contain ':', so no field value
// can shift a boundary and collide with a different tuple.
func hashFields(domain collections.Prefix, parts ...string) string {
	hashed := make([]string, 0, len(parts)+1)
	d := sha256.Sum256(domain.Bytes())
	hashed = append(hashed, hex.EncodeToString(d[:]))
	for _, p := range parts {
		sum := sha256.Sum256([]byte(p))
		hashed = append(hashed, hex.EncodeToString(sum[:]))
	}
	final := sha256.Sum256([]byte(strings.Join(hashed, ":")))
	return hex.EncodeToString(final[:])
}

// CanonicalizeAddressByNamespace canonicalizes an address for the given
// CAIP-2 chain. Empty input passes through (optional fields).
func CanonicalizeAddressByNamespace(chain, addr string) (string, error) {
	addr = strings.TrimSpace(addr)
	if addr == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMAddress(addr)
	case namespaceSolana:
		return canonicalizeSolanaValue(addr)
	default:
		return addr, nil
	}
}

// CanonicalizeTxHashByNamespace canonicalizes a transaction hash/signature
// for the given CAIP-2 chain. Empty input passes through (e.g. failed
// outbound observations carry no hash).
func CanonicalizeTxHashByNamespace(chain, txHash string) (string, error) {
	txHash = strings.TrimSpace(txHash)
	if txHash == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMHash(txHash)
	case namespaceSolana:
		return canonicalizeSolanaTxHash(txHash)
	default:
		return txHash, nil
	}
}

// Lenient variants for the vote-ingress / key-derivation path: canonical form
// when the value parses, trimmed input otherwise (never an error). Used there
// because that path must never drop a vote — a malformed inbound still has to
// produce an on-chain UTX record (with a failed PCTx / revert), and
// execution-level validation, not key derivation, is what rejects it. Honest
// observers of the same value still converge (same trimmed string), and the
// injective hashFields digest keeps even malformed values collision-safe.
// Strict (error-returning) variants are for admin/config paths where bad input
// should be rejected before it is persisted.

// LenientCanonicalizeAddress canonicalizes addr for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeAddress(chain, addr string) string {
	canon, err := CanonicalizeAddressByNamespace(chain, addr)
	if err != nil {
		return strings.TrimSpace(addr)
	}
	return canon
}

// LenientCanonicalizeTxHash canonicalizes txHash for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeTxHash(chain, txHash string) string {
	canon, err := CanonicalizeTxHashByNamespace(chain, txHash)
	if err != nil {
		return strings.TrimSpace(txHash)
	}
	return canon
}

// CreateUniversalTx stores a new UniversalTx
func (k Keeper) CreateUniversalTx(ctx context.Context, key string, utx types.UniversalTx) error {
	exists, err := k.UniversalTx.Has(ctx, key)
	if err != nil {
		return err
	}
	if exists {
		return fmt.Errorf("universal tx with key %s already exists", key)
	}

	k.Logger().Debug("universal tx stored", "utx_key", key)
	return k.UniversalTx.Set(ctx, key, utx)
}

## The `UniversalTx` Record

`UniversalTx` (UTX) is the canonical, end-to-end record of a single crosschain transaction as it travels through Push Chain. One UTX is created per observed inbound and lives forever (it is never deleted, only mutated as new pieces of evidence arrive). It is the only object in the module that the rest of the protocol — Universal Validators, the JSON-RPC layer, indexers, the explorer — needs to read in order to know what's happening with a given crosschain action.
