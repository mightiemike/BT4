Based on my investigation, I found a concrete, self-documented integrity gap rather than needing to speculate.

### Title
`ensure_match_transaction_info` never verifies the state-checkpoint / hot-state / position-state root hashes, letting replay and chunk-apply flows accept a `TransactionOutput` whose committed state root diverges from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sanity-check comparator that ties a locally produced (or replayed) `TransactionOutput` to the trusted/proof-bearing `TransactionInfo` stored in the ledger. It checks status, gas used, write-set hash, and event-root hash, but the code itself documents that it skips the state-checkpoint hash, hot-state checkpoint hash, and position-state checkpoint hash fields entirely.

### Finding Description
The comparator is defined at [1](#0-0)  and only asserts equality of `status`, `gas_used`, and `write_set_hash` against `txn_info.state_change_hash()`, then event-root hash. Immediately after, the code contains an explicit TODO acknowledging the gap: [2](#0-1) 

`TransactionInfo` carries a `state_checkpoint_hash` (SMT root, V0 and V1) plus, for V1, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`: [3](#0-2) 

None of these are compared in `ensure_match_transaction_info`. This function is used as the core "did my execution/replay match the authenticated ledger record" check in several state-integrity-relevant call sites: `execution/executor/src/chunk_executor/mod.rs` (chunk apply / `TransactionReplayer` path used during state sync and replay), `storage/db-tool/src/replay_on_archive.rs` (replay-verify tooling), `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`.

### Impact Explanation
Because the world-state root (and, when `TRADING_NATIVE`/hot-state features are enabled, the hot-state and native-position roots) is never checked in this comparator, a node whose local execution or replay produces a state root that diverges from what is embedded in the trusted `TransactionInfo` (e.g., due to non-determinism, an execution bug, a corrupted local DB, or a maliciously altered `TransactionOutputListWithProof` payload whose write-set/event/gas fields were kept intact but the accompanying checkpoint-hash bookkeeping was not independently recomputed) will still pass this check as "matching." This is exactly the class of "authenticated state-view output bound to the wrong version/root" and "hard-fork-only divergence during commit, replay, restore" that the task's integrity gate targets: replay-verify and chunk-apply flows can report success while the locally committed state root has silently diverged from the network-agreed one.

### Likelihood Explanation
This is not a hypothetical construction — the omission is explicitly flagged in the source as a known limitation ("this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"). The gap is unconditionally present for every call to `ensure_match_transaction_info` regardless of feature flags, since the state-checkpoint-hash comparison is missing outright (not just the newer hot-state/position fields).

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()` against the locally computed checkpoint root whenever `self` represents a checkpoint transaction, and likewise validate `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` when `HOT_STATE_ROOT_IN_TXN_INFO` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled, before treating replay or chunk-apply as successful.

### Proof of Concept
Not independently verifiable from static code alone: reproducing the divergence requires driving a chunk-apply/replay-verify run where the locally recomputed state/hot-state/position roots differ from the persisted `TransactionInfo` and observing that `ensure_match_transaction_info` returns `Ok(())`. I could not execute the test suite in this environment, so this is based on static analysis of the comparator's logic and its self-documented gap, not a runtime-confirmed exploit.

**Uncertainty**: I was not able to fully trace, within the available iterations, whether `chunk_executor/mod.rs`'s call to `ensure_match_transaction_info` occurs on data whose checkpoint hash is *also* independently validated elsewhere in the same code path (e.g., via a separate SMT-root comparison against `ProvableStateSummary`/`ProvablePositionStateSummary`, which appeared in the imports at [4](#0-3) ). If such an independent check exists and is unconditionally enforced on the same path, the practical severity would be reduced to "replay-verify tooling only" rather than affecting the core chunk-apply/state-sync trust boundary. I recommend a background agent confirm this by tracing `DoStateCheckpoint` and the callers of `ensure_match_transaction_info` in `chunk_executor/mod.rs` end-to-end.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
