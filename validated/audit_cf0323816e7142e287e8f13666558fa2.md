### Title
Feature-boundary desync between cached `delegated_stakes` totals and freshly-recomputed effective stake causes underflow panic / phantom stake in `Stakes::sub_delegated_stake` - ([File: runtime/src/stakes.rs])

### Summary
`Stakes::upsert_stake_delegation` and `Stakes::remove_stake_delegation` never store *how much* stake was actually added to the `delegated_stakes` aggregate for a given account; instead, every time the account is touched again they recompute the "old"/"removed" contribution from scratch via `delegation_effective_stake(..., use_fixed_point_stake_math)` using whatever value of the flag is current at that moment. If the `use_fixed_point_stake_math` feature flag flips between the transaction that added a partially-activating/deactivating delegation to the cache and a later transaction that touches the same account, the freshly recomputed amount can differ from what was actually accumulated in `delegated_stakes`, causing `sub_delegated_stake`'s `checked_sub(...).expect(...)` to panic or leaving residual "phantom" stake in the map.

### Finding Description
`Stakes::add_delegated_stake` / `Stakes::sub_delegated_stake` treat `delegated_stakes` as a plain running total keyed by voter pubkey [1](#0-0) . Every write to a stake account goes through `StakesCache::check_and_store`, which calls `upsert_stake_delegation` or `remove_stake_delegation` with the `use_fixed_point_stake_math` boolean evaluated for the *current* bank/slot [2](#0-1) .

In `upsert_stake_delegation`, when the stake account already exists in the map, the code recomputes `old_stake` for the *previously stored* `StakeAccount` using the *current* `use_fixed_point_stake_math` value and then calls `sub_delegated_stake(&old_voter_pubkey, old_stake)`, which subtracts that freshly computed amount from whatever total is currently cached in `delegated_stakes` [3](#0-2) . The same recompute-on-touch pattern exists in `remove_stake_delegation`, where `removed_stake` is derived fresh from `delegation_effective_stake` at removal time and subtracted from the cache [4](#0-3) .

The cached total in `delegated_stakes`, however, was built up by a sequence of `add_delegated_stake`/`sub_delegated_stake` calls made at *earlier* points in time, each using whatever `use_fixed_point_stake_math` value was active then. Nothing ties the value that was actually added to the map to the value that will later be subtracted — the code assumes `delegation_effective_stake(delegation, epoch, ...)` is idempotent for the same `(delegation, epoch)` pair regardless of when it's called. That assumption breaks across the exact slot where `use_fixed_point_stake_math` flips from the floating-point formula to the fixed-point formula: for a delegation that is mid-warmup or mid-cooldown at that slot, the two formulas can produce different lamport-level effective-stake values for the identical `(delegation, epoch, stake_history)` input due to floating-point vs. fixed-point rounding differences in `delegation_effective_stake` (`runtime/src/stake_delegation.rs`).

Concretely:
1. Pre-activation slot: attacker submits `DelegateStake`. `upsert_stake_delegation` runs with `use_fixed_point_stake_math = false`, computing `stake = f(delegation)` (float formula) and calling `add_delegated_stake(voter, stake)` — the cache now holds `stake_old`.
2. Feature activates at the boundary slot.
3. Post-activation slot: attacker submits any transaction that rewrites the same stake account while it is still partially activating (e.g., a partial withdrawal, `Merge`, or `Deactivate`). `check_and_store` is invoked with `use_fixed_point_stake_math = true`. The code recomputes the "old" contribution as `g(delegation)` (fixed-point formula) instead of reusing `stake_old`, and calls `sub_delegated_stake(voter, g(delegation))`.
4. If `g(delegation) > stake_old` cached in the map, `current_stake.checked_sub(stake).expect("subtraction value exceeds delegated stake")` panics [5](#0-4) . If `g(delegation) < stake_old`, the subtraction under-removes, leaving residual/phantom stake permanently attributed to the voter in `delegated_stakes` (and correspondingly in `VoteAccounts` via `vote_accounts.sub_stake`/`add_stake`).

There is no signer/writable check, sanitization, or replay protection that guards against this — the flag is derived purely from bank slot/feature-activation state, so every validator processing the same transactions at the same slots will independently compute the identical mismatched values and panic identically (deterministic, cluster-wide liveness halt) or independently accumulate the identical phantom-stake drift (deterministic, but incorrect stake accounting feeding into reward/leader-schedule calculations).

### Impact Explanation
This falls into the "cluster-halting panic" / "lamport-accounting corruption" bounty categories: a `.expect()` panic inside `Stakes::sub_delegated_stake`, reached during ordinary transaction/bank replay processing, would cause every validator to panic identically at the exact same slot when a straddling stake account is next touched — a full network halt requiring a coordinated software fix, not just this validator. Alternatively, if the direction of the mismatch is the other way, `delegated_stakes` silently retains phantom stake that is never fully reconciled, corrupting stake-weighted leader schedule/reward calculations downstream (`runtime/src/inflation_rewards`, `bank/partitioned_epoch_rewards`).

### Likelihood Explanation
Preconditions are narrow but attacker-controllable at low cost: the attacker needs an ordinary funded keypair and a delegated stake account whose activation/deactivation is still "in flight" (partially warmed-up/cooled-down) exactly across the single slot boundary where the feature flag flips, plus one follow-up transaction touching that same stake account after the flip. Because feature activations are scheduled epoch boundaries known in advance from cluster state, an attacker can time delegation/deactivation to straddle the boundary deterministically and repeatably in a devnet/testnet fork or in a bank-level integration test. The magnitude of the discrepancy is bounded by whatever rounding difference exists between the float and fixed-point formulas in `delegation_effective_stake` (likely small, on the order of lamports, but sufficient to trigger the `.expect()` panic since even a 1-lamport mismatch is fatal to `checked_sub`). This is a one-time exploitation window per feature activation (it cannot be repeated once the flag has settled), which somewhat limits real-world exploitability but does not eliminate the correctness/liveness risk at the actual activation event.

Note: I was not able to confirm from available context whether the specific feature name in the question (`upgrade_bpf_stake_program_to_v5_1`) is actually the gate controlling `use_fixed_point_stake_math`, nor could I fully inspect `runtime/src/stake_delegation.rs` to confirm the exact magnitude/sign of divergence between the float and fixed-point formulas for partially-activating delegations — this should be verified directly in a Devin session with full repository access.

### Recommendation
Do not recompute the previously-added/removed stake contribution using the *current* value of `use_fixed_point_stake_math`. Instead, either (a) store the actual `u64` stake amount that was added to `delegated_stakes` alongside each `StakeAccount` in `stake_delegations` so it can be exactly reversed later, or (b) force a one-time full `refresh_delegated_stakes` recomputation of the entire `delegated_stakes` map atomically at the exact slot the feature activates (which `refresh_delegated_stakes` already supports) before allowing any further incremental `add_delegated_stake`/`sub_delegated_stake` calls to mix pre- and post-activation semantics.

### Proof of Concept
Bank/SVM integration test plan:
1. Construct a `Bank` with `use_fixed_point_stake_math` feature not yet activated; create and delegate a stake account so it enters partial warmup at epoch `E`.
2. Call `StakesCache::check_and_store` (or process the `DelegateStake` instruction through the bank) with `use_fixed_point_stake_math = false`, and record the resulting `delegated_stakes` value for the voter.
3. Activate the feature (simulate crossing the activation slot) so subsequent calls use `use_fixed_point_stake_math = true`.
4. Trigger another write to the same stake account while it is still partially activated (e.g., a `Merge`/partial `Withdraw` or re-store via `check_and_store`) causing `upsert_stake_delegation`/`remove_stake_delegation` to run with the new flag value.
5. Assert that either (a) the process panics inside `sub_delegated_stake`'s `.expect("subtraction value exceeds delegated stake")`, or (b) `delegated_stakes.get(&voter_pubkey)` after full removal of the delegation is not exactly `0` (proving phantom/residual stake), depending on the sign of the float-vs-fixed-point rounding difference for the chosen partial-activation epoch.

    fn add_delegated_stake(&mut self, voter_pubkey: Pubkey, stake: u64) {
        if stake == 0 {
            return;
        }
        *self.delegated_stakes.entry(voter_pubkey).or_default() += stake;
    }

    fn sub_delegated_stake(&mut self, voter_pubkey: &Pubkey, stake: u64) {
        if stake == 0 {
            return;
        }
        let current_stake = self
            .delegated_stakes
            .get_mut(voter_pubkey)
            .expect("subtraction from missing delegated stake");
        *current_stake = current_stake
            .checked_sub(stake)
            .expect("subtraction value exceeds delegated stake");
        if *current_stake == 0 {
            self.delegated_stakes.remove(voter_pubkey);
        }
    }
