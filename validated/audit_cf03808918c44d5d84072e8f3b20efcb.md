## Finding

The strongest reachable analog to the ERC‑4626 `maxDeposit()` misreport is `getCanDelegatedMaxSize()` in java-tron's resource-delegation API, which behaves like a "max query" that can overstate what the actual `DelegateResourceContract` actuator will accept.

### Title
`getCanDelegatedMaxSize` RPC/HTTP query can report a delegable amount higher than what `DelegateResourceActuator`/`DelegateResourceProcessor` will actually accept, causing broadcast reverts - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getCanDelegatedMaxSize()` [1](#0-0)  is exposed over gRPC and HTTP (`GetCanDelegatedMaxSizeServlet`) [2](#0-1)  as a preview API telling callers (wallets, exchanges, delegation-management tools) the maximum `balance` they can safely put into a `DelegateResourceContract`. This is architecturally the same role as ERC-4626's `maxDeposit()`: a read-only capacity hint that downstream integrators use to size a state-changing call before submitting it.

### Finding Description
The actual enforcement of the delegation limit happens in `DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()`, which computes the "available FreezeBandwidthV2/FreezeEnergyV2 balance" using account usage recovered at the time of *validation of the concrete transaction*, and — critically — adds an extra deduction only when the transaction is actually being created:

```
if (null != this.getTx() && this.getTx().isTransactionCreate()) {
  accountNetUsage += TransactionUtil.estimateConsumeBandWidthSize(dynamicStore,
          ownerCapsule.getFrozenV2BalanceForBandwidth());
}
``` [3](#0-2) 

This same “available balance” formula (bandwidth/energy usage projected against `TotalNetWeight`/`TotalNetLimit` or `TotalEnergyWeight`/`TotalEnergyCurrentLimit`) is duplicated in the native-contract path `DelegateResourceProcessor.validate()` [4](#0-3) , and if `delegateBalance` exceeds the computed available amount, the actuator throws `ContractValidateException("delegateBalance must be less than or equal to available FreezeBandwidthV2 balance")` (verified by `DelegateResourceActuatorTest.testDelegateBandwidthWithUsage`/`testDelegateCpuWithUsage`) [5](#0-4) .

The query API, `getCanDelegatedMaxSize`, has no transaction context (`this.getTx()` is not applicable since no `DelegateResourceContract` transaction exists yet) and can only call a standalone `calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize` estimator [1](#0-0) . By construction it therefore cannot include the actuator's transaction-creation-time bandwidth self-consumption adjustment (`estimateConsumeBandWidthSize`), which only exists inside `validate()` and is gated on `isTransactionCreate()`. This is the same class of bug as the ERC-4626 report: a capacity-preview function whose result is not guaranteed to match the value actually enforced at execution time, because the execution path applies additional, context-dependent deductions the preview path structurally cannot reproduce.

I was not able to read the full body of `calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize` within the available tool budget, so I cannot give a byte-for-byte diff of the two formulas — this is the one piece of the root-cause chain that remains unverified. What is verified is that the actuator path contains a usage adjustment term (`estimateConsumeBandWidthSize` under `isTransactionCreate()`) that has no counterpart callable from the query path, which is the structural reason a mismatch is possible.

### Impact Explanation
An integrator (exchange, wallet, delegation dashboard) that calls `getCanDelegatedMaxSize` and then submits a `DelegateResourceContract` for the returned amount can have that transaction rejected by `validate()` with a `ContractValidateException`, i.e. a failed/reverted broadcast. This is a functional/integration-correctness issue (denial of expected operation, wasted fee/bandwidth on a failed broadcast) rather than a fund-loss or consensus-divergence bug — consistent with the "Medium, integration failure" severity of the original ERC-4626 report.

### Likelihood Explanation
Any account with recent bandwidth/energy usage close to its frozen-v2 balance and that queries `getCanDelegatedMaxSize` immediately before constructing a delegation transaction is likely to hit this discrepancy, since usage recovery and the specific `isTransactionCreate()` adjustment are time- and state-dependent. This is reachable by any anonymous RPC/HTTP caller (`getCanDelegatedMaxSize` and `DelegateResource` broadcast are both public APIs), no privileged role required.

### Recommendation
Have `calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize` in `Wallet.java` reuse the exact same usage/availability formula (including the transaction-creation bandwidth-cost adjustment used in `DelegateResourceActuator.validate()`/`DelegateResourceProcessor.validate()`), or conservatively subtract a worst-case estimate of that adjustment, so the value returned by the "max" query is never higher than what the actuator will actually accept.

### Proof of Concept
Not independently reproduced against the exact `calcCanDelegatedBandWidthMaxSize` formula (unverified in this pass); the concrete revert path is demonstrated by `DelegateResourceActuatorTest.testDelegateBandwidthWithUsage` / `testDelegateCpuWithUsage`, which show `validate()` rejecting a delegation once actuator-side usage accounting reduces available balance below the requested amount [5](#0-4) . Confirming the analog end-to-end requires diffing this against the live output of `getCanDelegatedMaxSize` for the same account state, which needs a code read I could not complete.

  public GrpcAPI.CanDelegatedMaxSizeResponseMessage getCanDelegatedMaxSize(
          ByteString ownerAddress,
          int resourceType) {
    long canDelegatedMaxSize = 0L;
    GrpcAPI.CanDelegatedMaxSizeResponseMessage.Builder builder =
          GrpcAPI.CanDelegatedMaxSizeResponseMessage.newBuilder();
    if (Common.ResourceCode.BANDWIDTH.getNumber() == resourceType) {
      canDelegatedMaxSize = this.calcCanDelegatedBandWidthMaxSize(ownerAddress);
    } else if (Common.ResourceCode.ENERGY.getNumber() == resourceType) {
      canDelegatedMaxSize = this.calcCanDelegatedEnergyMaxSize(ownerAddress);
    }

    if (canDelegatedMaxSize < TRX_PRECISION) {
      canDelegatedMaxSize = 0L;
    }
    builder.setMaxSize(canDelegatedMaxSize);
    return builder.build();
  }
