## Finding [1](#0-0) 

The `EpochHistory::verify_ledger_info` function is the exact structural analog of the OmniPortal bug: instead of rejecting a signed statement whose signing authority cannot yet be checked (like `inXStreamValidatorSetId == 0` for an unregistered chain), it silently accepts it as trusted when the referenced epoch falls outside the known, already-verified epoch range.

### Title
Unverified `LedgerInfo` accepted during transaction backup restore when epoch exceeds known epoch history - (`storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` is supposed to check that a `LedgerInfoWithSignatures` presented during restore is signed by the validator set legitimately in power for its epoch. When the epoch of the supplied ledger info is greater than the number of already-restored epoch-ending records (`epoch > self.epoch_endings.len()`), the function skips signature verification entirely and returns `Ok(())` with only a warning log, instead of rejecting the input, checking a trusted waypoint, or deferring the decision safely.

### Finding Description
`verify_ledger_info` is called from `LoadedChunk::load` in [2](#0-1)  on a `LedgerInfoWithSignatures` that is deserialized directly from a backup-storage file (`manifest.proof`), i.e., attacker-influenced input if the backup storage/manifest source is not fully trusted or is tampered with in transit. This ledger info is then used as the trust anchor to verify the entire transaction chunk: [3](#0-2) 

If `verify_ledger_info` skips real verification (the `epoch > self.epoch_endings.len()` branch), `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)` only checks *internal consistency* between the supplied transaction infos/accumulator proof and the supplied (unauthenticated) `ledger_info` — it never checks that `ledger_info` was actually signed by the legitimate validator set for that epoch. The resulting transactions, transaction infos, and write sets are then persisted directly into durable storage via `restore_handler.save_transactions(...)` in [4](#0-3) .

This exact bypass condition is systematically reached for the newest (still-open, not-yet-epoch-ending) epoch at the tail of any restore/replay-verify run, because `epoch_endings` (built by `EpochHistoryRestoreController`) only contains epochs that have *already ended* with a recorded epoch-ending backup — the active epoch containing the most recent transactions being restored is, by construction, always one epoch ahead of what `epoch_endings` can cover. The code's own comment acknowledges the gap is unresolved: `// TODO(aldenhu): fix this from upper level`.

This is the direct analog to the OmniPortal issue: a zero/absent trust anchor (`inXStreamValidatorSetId == 0` there, `epoch_endings` too short here) is treated as "cannot verify, so allow" rather than "cannot verify, so reject or fall back to another proof of authenticity" (e.g., trusted waypoints).

### Impact Explanation
If the backup archive (manifest files, transaction chunk files, or the `ledger_info`/proof blob) is corrupted, MITM'd, or served by a compromised/malicious backup storage backend, a restoring node can be made to accept and durably commit a transaction chunk, write sets, and transaction infos that were never actually agreed upon by the real validator set. This directly corrupts durable ledger data and root/proof state for the restored node — its resulting local ledger state, transaction infos, and any proofs derived from it (accumulator root, transaction proofs) diverge from the actual canonical chain, while the restore path reports success as though everything was cryptographically verified.

### Likelihood Explanation
The bypass is not an edge case — it is hit deterministically on every restore/replay-verify run for the currently open epoch (the most recent unfinalized epoch) because no epoch-ending record for it can exist yet. Exploitation requires control or tampering of the backup storage/transport that a node operator points their restore tooling at (e.g., a shared/public backup service, or an unauthenticated transport), which is a plausible operational scenario, especially for full-node operators bootstrapping/restoring from third-party or self-hosted backup buckets rather than talking live to consensus.

### Recommendation
`EpochHistory::verify_ledger_info` must never return `Ok(())` without verification. When `epoch > self.epoch_endings.len()`, it should either: (1) return an error/require an explicit trusted waypoint at or after that version, or (2) defer verification safely to a subsequent state-sync/waypoint check before treating the corresponding transactions as durable and returning success, ensuring the caller path cannot commit transaction chunks whose backing `LedgerInfo` signatures were never checked against a known validator set.

### Proof of Concept
1. Take (or stand up) a backup storage location referenced by `TransactionRestoreController`/`TransactionRestoreBatchController`.
2. Craft a transaction chunk manifest whose `proof` file contains an attacker-fabricated `LedgerInfoWithSignatures` for an epoch `E` that has no corresponding epoch-ending backup yet (i.e., `E` is the "current"/open epoch at the tail of the restore range), with empty or bogus `AggregateSignature`.
3. Populate the accompanying transaction/write-set/transaction-info records so they are internally consistent with the forged `ledger_info`'s `transaction_accumulator_hash` (self-consistent, not validator-signed).
4. Run a restore (`TransactionRestoreController::run`) pointed at this backup with an `EpochHistory` that does not yet contain an epoch-ending record for `E`.
5. Observe that `EpochHistory::verify_ledger_info` takes the `epoch > self.epoch_endings.len()` branch, logs a warning, and returns `Ok(())`; `txn_list_with_proof.verify()` succeeds because it only checks internal consistency; `restore_handler.save_transactions` persists the forged data into the target `AptosDB`, completing successfully with no cryptographic authentication of validator signatures having occurred.
