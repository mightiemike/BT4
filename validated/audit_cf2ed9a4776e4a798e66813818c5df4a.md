### Title
Malformed PoX-4 signer key silently collapses to an all-zero key, corrupting signer-set weight aggregation - ([File: stackslib/src/chainstate/stacks/boot/mod.rs])

### Summary
`RawRewardSetEntry::from_pox_4_tuple` reads the `signer` field of a `.pox-4` reward-set-pox-address tuple and is documented to require it be exactly `SIGNERS_PK_LEN` (33) bytes, because Clarity's `(buff 33)` type only enforces a *maximum* length, not a minimum. When the length check fails, instead of rejecting the entry (as an error), the code silently substitutes an all-zero 33-byte array as the signing key. This mirrors the reported bug class: a value that should uniquely identify a distinct recipient/party is replaced by a degenerate placeholder that equals another entity's placeholder, which then gets treated as equal ("the same signer") by downstream aggregation logic — exactly the "vault(token0, token0) instead of vault(token0, token1)" pattern of an incorrect variable/value making two distinct things collide.

### Finding Description
In `get_reward_addresses_pox_4` → `RawRewardSetEntry::from_pox_4_tuple`: [1](#0-0) 
```
// (buff 33) only enforces max size, not min size, so we need to do a len check
let pk_bytes = if signer.len() == SIGNERS_PK_LEN {
    let mut bytes = [0; SIGNERS_PK_LEN];
    bytes.copy_from_slice(signer.as_slice());
    bytes
} else {
    [0; SIGNERS_PK_LEN]
};
``` [2](#0-1) 

Every parsed entry then always carries `signer: Some(pk_bytes)` — even the malformed one — and is fed into `StacksChainState::make_signer_set`: [3](#0-2) 
```
let mut signer_set = BTreeMap::new();
for entry in entries.iter() {
    let signing_key = entry.signer.expect(...);
    if let Some(existing_entry) = signer_set.get_mut(&signing_key) {
        *existing_entry += entry.amount_stacked;
    } else {
        signer_set.insert(signing_key, entry.amount_stacked);
    };
}
```
Because the substituted key is a fixed constant (`[0u8;33]`), any stacker whose `signer` buffer in `.pox-4`'s reward-cycle-pox-address-list has length ≠ 33 bytes collapses into the *same* bucket as every other malformed entry, and its `amount_stacked` is summed into that bucket instead of being attributed to (or rejected for) the actual stacker. The equality being broken is: "each `NakamotoSignerEntry.signing_key` corresponds to exactly one real secp256k1 public key controlled by one signer" — this invariant is violated by the zero-key collapse.

The resulting `NakamotoSignerEntry { signing_key: [0;33], weight, .. }` is a permanent member of the reward set with real ustx-backed weight, but `[0u8;33]` is not a valid compressed secp256k1 public key, so no signature can ever be recovered to it in `verify_signer_signatures`: [4](#0-3) 
That function computes `total_weight` (including the bogus entry) via `reward_set.total_signing_weight()` and requires `total_weight_signed >= threshold` where `threshold` is 70% of `total_weight`. Weight assigned to the unrecoverable zero-key entry can never be signed for, permanently shrinking the pool of *actually achievable* signing weight relative to the required threshold.

### Impact Explanation
This is minority-triggerable: a single stacker (or a small colluding set) can, via a crafted `stack-stx`/`stack-extend`/`stack-aggregation-commit` transaction that supplies a `signer` buffer shorter than 33 bytes, cause their stacked amount to be silently misattributed to a synthetic "signer" that can never produce a valid signature. If enough stacked STX accumulates on the zero-key bucket across a reward cycle, the total *achievable* signing weight can fall below the 70% threshold required by `NakamotoBlockHeader::compute_voting_weight_threshold`/`verify_signer_signatures`, making it impossible for signers to ever produce a validly-signed Nakamoto block for that cycle — a liveness failure (temporary-to-potentially-persistent chain halt for the cycle) rather than a fund-theft bug. This falls under "signer weight below threshold ... from the wrong set" and "temporary tip disagreement" in the accepted impact categories.

### Likelihood Explanation
Likelihood depends on whether `.pox-4`'s public entry points enforce an exact-33-byte `signer` argument before persisting it to `reward-cycle-pox-address-list`. The Rust-side comment and explicit length check strongly suggest the Clarity contract does **not** enforce a minimum length (only the `(buff 33)` max-size constraint), which is why this defensive length check exists in `from_pox_4_tuple` in the first place — but I was not able to fully trace every `.pox-4` public function (e.g. `stack-stx`, `stack-aggregation-commit(-indexed)`, `stack-signer-key` verification paths) within the tool budget available to confirm there is no additional, stricter length assertion earlier in the Clarity call chain that would make this unreachable. This uncertainty should be resolved by a follow-up review of `stackslib/src/chainstate/stacks/boot/pox-4.clar`'s signer-key handling functions.

### Recommendation
In `RawRewardSetEntry::from_pox_4_tuple`, treat a `signer` buffer whose length is not exactly `SIGNERS_PK_LEN` as a hard parsing error (`ChainstateError::Expects(...)`) rather than silently defaulting to an all-zero key, so malformed entries cannot collapse into and inflate a shared bogus identity. If backward compatibility requires tolerating such entries, they should be dropped/excluded from `amount_stacked` aggregation and from `total_signing_weight`, not merged together.

### Proof of Concept
Not independently executed against a live node in this analysis (no filesystem/terminal access here); the trace above is via static code reading, given:
1. `RawRewardSetEntry::from_pox_4_tuple` (`stackslib/src/chainstate/nakamoto/signer_set.rs:297-333`) accepting `signer.len() != 33` and substituting `[0;33]`.
2. `StacksChainState::make_signer_set` (`stackslib/src/chainstate/stacks/boot/mod.rs:1020-1072`) aggregating by `signing_key` without validating it is a recoverable public key.
3. `NakamotoBlockHeader::verify_signer_signatures` (`stackslib/src/chainstate/nakamoto/mod.rs:1097-1190`) computing the 70% threshold against `total_weight`, which includes the unattainable zero-key weight.

A concrete PoC would require: (a) confirming that a `.pox-4` transaction can be crafted/relayed with a non-33-byte `signer` buffer that the contract accepts, (b) stacking enough STX under such malformed entries across several stackers in one reward cycle to push `total_weight - unattainable_weight` below 70% of `total_weight`, and (c) observing that no combination of legitimate signer signatures can satisfy `verify_signer_signatures` for that cycle. This step requires running the boot contract unit tests (`contrib/boot-contracts-unit-tests`) and a local Nakamoto testnet, which was not available in this environment.
