### Title
Hardcoded `address-map.near` Registrar Account Causes Caller Deposit Loss on Failed Lookup — (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

---

### Summary

The ETH-implicit Wallet Contract bakes the address registrar account ID (`address-map.near`) into the WASM binary at compile time via `include_str!`. When a cross-contract call to that hardcoded account fails — because the account does not exist on the target network (testnet, localnet) or is temporarily unavailable — the `address_check_callback` returns an error without refunding the caller's attached deposit. The deposit is permanently stranded inside the wallet contract. This is the direct nearcore analog of the hardcoded Uniswap router address: a compile-time constant account ID that is only valid on one network, causing fund loss when the constant resolves to a non-existent or wrong account.

---

### Finding Description

**Hardcoded registrar account ID**

`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` line 27 reads the registrar account ID from a static file at compile time:

```rust
const ADDRESS_REGISTRAR_ACCOUNT_ID: &str = std::include_str!("ADDRESS_REGISTRAR_ACCOUNT_ID");
```

The file `runtime/near-wallet-contract/implementation/wallet-contract/src/ADDRESS_REGISTRAR_ACCOUNT_ID` contains exactly:

```
address-map.near
```

This value is baked into the WASM binary. The same binary is deployed on every ETH-implicit account on every network (mainnet, testnet, localnet). On testnet and localnet the account `address-map.near` does not exist.

**Where the hardcoded ID is used**

Inside `inner_rlp_execute` (lines 419–431), when an EOA base-token transfer targets another ETH-implicit account and the transaction payload is parseable as an Ethereum emulation (ERC-20 transfer, etc.), the contract schedules a cross-contract call to the hardcoded registrar:

```rust
let address_registrar = {
    let account_id = ADDRESS_REGISTRAR_ACCOUNT_ID
        .trim()
        .parse()
        .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
    ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
};
address_registrar.lookup(address).then(ext.address_check_callback(
    target,
    action,
    caller_deposit,   // ← caller's deposit is passed here
))
```

**Missing refund in the failure branch**

`address_check_callback` (lines 134–192) handles the result of that cross-contract call. When the call fails it returns immediately without touching `caller_deposit`:

```rust
PromiseResult::Failed => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false,
        success_value: None,
        error: Some("Call to Address Registrar contract failed".into()),
    });
    // caller_deposit is silently dropped — no refund issued
}
```

Compare with `rlp_execute_callback` (lines 296–312), which correctly refunds the caller on failure:

```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(
            refund_promise,
            NearToken::from_yoctonear(yocto_near.into()),
        );
    }
    ExecuteResponse { success: false, ... }
}
```

The two callbacks are structurally identical in purpose but only one refunds on failure. The inconsistency is the root cause; the hardcoded account ID is what makes the failure reachable from an ordinary user on any non-mainnet network.

**Nonce is not incremented before the registrar call**

The code explicitly skips nonce increment for the `address_check: Some(_)` path (lines 358–365):

```rust
if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
    address_check: Some(_), ..
}) = &transaction_kind
{
    // nonce NOT incremented here
} else {
    *nonce = nonce.saturating_add(1);
}
```

The nonce is only incremented inside `address_check_callback` when the registrar returns `None`. When the registrar call fails entirely, the nonce stays unchanged and the deposit is gone — the user can retry the transaction but the relayer's attached funds are already lost.

---

### Impact Explanation

A relayer that attaches a NEAR deposit to `rlp_execute` (to cover the transfer amount on behalf of the user) loses that deposit permanently when the address registrar call fails. The deposit is transferred into the wallet contract at call time and is never returned. The wallet contract owner (the ETH-implicit account holder) retains the funds inside their own contract, but the relayer — an unprivileged third party — has no mechanism to recover them. On testnet and localnet this failure is deterministic for every EOA-to-EOA transfer that triggers the address-check path, because `address-map.near` does not exist on those networks.

---

### Likelihood Explanation

- On **testnet and localnet**: every EOA base-token transfer that triggers `address_check: Some(_)` will fail with `PromiseResult::Failed` because `address-map.near` does not exist. Any relayer attaching a deposit on those networks loses it unconditionally.
- On **mainnet**: the failure is conditional on `address-map.near` being temporarily unavailable or returning a malformed response, which is a lower-probability event but still possible.
- The triggering transaction type (ERC-20 emulation targeting another ETH-implicit account) is a standard, documented use case of the wallet contract, so it is reachable by any ordinary user interacting with the ETH-compatibility layer.

---

### Recommendation

**Option 1 — Fix the missing refund (minimal change):**

In `address_check_callback`, add the same refund logic that `rlp_execute_callback` already uses:

```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(
            refund_promise,
            NearToken::from_yoctonear(yocto_near.into()),
        );
    }
    return PromiseOrValue::Value(ExecuteResponse {
        success: false,
        success_value: None,
        error: Some("Call to Address Registrar contract failed".into()),
    });
}
```

**Option 2 — Make the registrar account ID configurable at deploy time:**

Store the registrar account ID in the contract state and set it during initialization, analogous to passing the router address as a constructor argument. This also fixes the cross-network deployment problem:

```rust
pub struct WalletContract {
    pub nonce: u64,
    pub has_in_flight_tx: bool,
    pub address_registrar: AccountId,  // set at init, not compile time
}
```

Both options should be applied together: Option 1 closes the immediate fund-loss path; Option 2 closes the root cause.

### Proof of Concept

1. Deploy the nearcore wallet contract on **testnet** (where `address-map.near` does not exist). This happens automatically when any ETH-implicit account is created.
2. As a relayer, call `rlp_execute` on the wallet contract, attaching `N` yoctoNEAR as a deposit. The signed Ethereum transaction encodes an ERC-20 `transfer(address,uint256)` call targeting another ETH-implicit account (so `address_check: Some(address)` is set).
3. The wallet contract calls `address-map.near::lookup(...)`. Because `address-map.near` does not exist on testnet, the cross-contract call returns `PromiseResult::Failed`.
4. `address_check_callback` is invoked. It matches `PromiseResult::Failed`, returns an error `ExecuteResponse`, and exits — without issuing any refund promise for `caller_deposit`.
5. The relayer's `N` yoctoNEAR deposit remains in the wallet contract. The relayer has no access key on the wallet contract and no mechanism to retrieve the funds. The deposit is permanently lost to the relayer. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
