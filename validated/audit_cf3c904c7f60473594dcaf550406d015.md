### Title
Malicious miner can indefinitely refresh signer-side "activity" via repeated reorg-attempt proposals, bypassing the `reorg_attempts_activity_timeout`/`block_proposal_timeout` inactivity gate that permits tenure hand-off - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
The signer's block-proposal evaluation logic treats any proposal (even one that is *rejected* because it does not extend the chain, i.e. a reorg attempt) as valid "miner activity" as long as it arrives within `reorg_attempts_activity_timeout` of the last globally-accepted block [1](#0-0) . This is structurally the same bug class as the reported LP withdrawal-request timer gaming: a party can keep re-arming a "you're still active/legitimate" timer by repeatedly submitting cheap, ultimately-rejected requests just inside the allowed window, defeating the intended purpose of the timeout (to eventually treat the party as inactive/malicious and let the alternate path proceed).

### Finding Description
The signer only allows the *previous* tenure's miner to issue a `TenureExtend` once two independent gates are satisfied: (1) `block_proposal_timeout` has elapsed without the new sortition winner producing a valid block, and (2) `tenure_idle_timeout(+buffer)` has elapsed [2](#0-1) . Gate (1) is driven by the signer's notion of "last activity" for the current winning miner.

`SortitionData`'s reorg-check routine (`stacks-signer/src/chainstate/mod.rs`, function around lines 383-479) explicitly calls `signer_db.update_last_activity_time(...)` whenever a proposal fails to extend the known chain tip (i.e., is a reorg attempt / duplicate-height proposal), provided it arrived before `signed_time + reorg_attempts_activity_timeout` [1](#0-0) . The same "count as activity, but don't reject" logic is applied to pre-committed-block conflicts as well [3](#0-2) .

`reorg_attempts_activity_timeout_ms` defaults to 200 seconds [4](#0-3) , and is independent of, and much shorter than, `block_proposal_timeout_ms` (default 120,000 ms per the miner config docs, though the changelog notes it was raised to 4 hours in some deployments) [5](#0-4) . Because every rejected proposal that arrives inside this window resets `last_activity_time`, a miner who currently holds the tenure (the "current sortition winner") can trivially generate a fresh, cheap, invalid proposal (e.g., a stale-parent block or duplicate-height block that gets globally rejected) every `reorg_attempts_activity_timeout` interval. Each such proposal re-arms the activity timer just as the LP in the external report re-arms the withdrawal window by creating a new request every ~16 minutes, staying just inside the enforced cadence and defeating the timeout's purpose.

The intended equality here is: *"a miner is timed out as inactive/invalid if and only if `block_proposal_timeout` has genuinely elapsed since real (accepted) mining activity."* The bug breaks that equality: a miner can keep the "activity" clock ticking with proposals that produce **no accepted blocks at all**, so the signer's internal state ("this miner is still active") diverges from ground truth ("this miner is not actually producing valid blocks"). Because the reset depends on wall-clock arrival time at each signer independently (`get_epoch_time_secs()` compared against each signer's own `signed_time`), signers with slightly different message-arrival timing can disagree about whether a given proposal fell inside or outside the `reorg_attempts_activity_timeout` window, producing a genuine cross-signer verdict split: some signers keep resetting activity (and thus reject the honest previous miner's `TenureExtend`), while others do not (and accept it) — a minority-triggerable, unprivileged validation-verdict divergence.

### Impact Explanation
This matches the "High" bucket definition given in scope: a minority-triggerable, unprivileged mechanism produces a temporary tip disagreement among signers, because different signers' local clocks/message-arrival order can put the same reorg-attempt proposal on opposite sides of the `reorg_attempts_activity_timeout` boundary, causing some signers to treat the current miner as still "active" (rejecting the legitimate previous miner's tenure-extend) while others treat it as timed out (accepting the extend). This can stall block production or cause conflicting locally-accepted blocks/tenure paths until signers reconcile, without requiring any majority collusion — a single miner unilaterally controls when and how often it submits the resetting proposals.

### Likelihood Explanation
Likelihood is Medium: the attack requires no special privilege beyond being the current sortition-round's miner (which any miner can become by chance/normal participation), and it only requires crafting cheap, deterministically-rejected block proposals (e.g., re-proposing a stale/duplicate height) at a cadence just under `reorg_attempts_activity_timeout` (200s by default) — directly analogous to the reported LP repeatedly creating withdrawal requests every ~16 minutes to stay just inside the allowed cadence. The exact probability of observably differing arrival times across signers close enough to the timeout boundary to cause a real verdict split depends on network jitter and is not certain on every attempt, which is why this is Medium rather than High/Critical likelihood.

### Recommendation
- Do not let a locally-rejected (non-extending) proposal reset `last_activity_time` based on a per-signer wall-clock check alone; instead, derive "activity" from a canonical, network-agreed signal (e.g., the burn-view/consensus hash advancing or a globally-accepted block), removing the individual signer's local timing judgment as a source of divergence.
- Alternatively, bound the number of resets in a single tenure (a decaying "credit" for reorg-attempt tolerance, similar to the accepted "add penalty/cost" recommendation in the source report) so a miner cannot indefinitely refresh activity purely with rejected proposals.
- Ensure `reorg_attempts_activity_timeout` evaluation uses a value already agreed upon by the group (e.g., a majority-observed timestamp) rather than each signer's own `get_epoch_time_secs()`, to eliminate the boundary race that causes cross-signer disagreement.

### Proof of Concept
1. Miner A wins tenure N and its block is globally accepted at time T0.
2. At T0 + 190s (before the default 200s `reorg_attempts_activity_timeout`), Miner A submits a stale/duplicate-height block proposal (a "reorg attempt") that all signers reject as invalid (it does not extend the chain) [6](#0-5) .
3. Because this arrives inside the window, each signer independently calls `update_last_activity_time`, extending the "activity" deadline for Miner A to (its own) T_arrival + 200s [1](#0-0) .
4. Miner A repeats step 2 every ~190s indefinitely, always inside the 200s window as observed by most signers.
5. Due to normal network jitter, some signers receive a given resubmission slightly after their local 200s deadline while others receive it slightly before — producing a split verdict: some signers now consider Miner A inactive and are willing to accept a `TenureExtend` proposal from the previous miner (or the next sortition winner), others still consider Miner A active and reject it, producing a temporary, minority-triggerable tip/verdict disagreement among signers without any accepted block being produced by Miner A.
