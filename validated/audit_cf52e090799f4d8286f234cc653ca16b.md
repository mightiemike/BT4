### Title
Unmetered CPU Amplification via `estimateEnergy` Binary Search on Constant Contract Calls - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The reported bug class is "gas siphoning": a protocol-operated actor performs free, unpriced work on behalf of an unprivileged caller, where the caller fully controls the target contract, and the amplification/looping cost of that work is externalized onto the protocol rather than the caller. The closest reachable analog in java-tron is the `estimateEnergy` RPC/HTTP API, which repeatedly executes a fully attacker-chosen smart contract via `triggerConstantContract` in an unbounded-iteration binary search loop, at zero economic cost to the caller, with only a generic QPS rate limiter (default 1000 qps) as protection.

### Finding Description
`Wallet.estimateEnergy` implements a binary search over the fee-limit space to find the minimum energy required to execute a caller-supplied `TriggerSmartContract`. It first executes at `high = dps.getMaxFeeLimit()`, then narrows the range with repeated calls to `cleanContextAndTriggerConstantContract`, each of which invokes `callConstantContract` → `VMActuator` to run the TVM against the caller's contract and data. [1](#0-0) [2](#0-1) 

Each iteration is a full TVM execution capable of running up to `maxEnergyLimitForConstant` (default 100,000,000) worth of opcodes, bounded in time by `constantCallTimeoutMs` or, if unset, "the shared block-processing deadline" per the config comment — i.e., potentially the full per-block CPU budget. [3](#0-2) 

Because the contract address, bytecode/data, and call value are entirely attacker-supplied (constant calls do not require the target contract to have been deployed by the caller, only that it exists), an attacker can deploy a contract whose execution cost is deliberately tuned to consume close to the maximum energy/time on every invocation. A single external call to `/wallet/estimateenergy` (or the gRPC `EstimateEnergy` method) then forces the node to re-execute that expensive contract on every binary-search step (each step can itself retry up to `estimateEnergyMaxRetry`, default 3, on `OutOfTimeException`), multiplying the CPU cost of one request by the number of binary-search iterations plus retries — work the node performs "for free" since `triggerConstantContract`/constant calls do not debit any account's energy or bandwidth. [4](#0-3) [5](#0-4) 

The only mitigating control is a generic per-endpoint QPS limiter; if no custom entry is configured (the shipped `reference.conf` has all HTTP/RPC-specific `rate.limiter` entries commented out), the default is `QpsRateLimiterAdapter` with `qps=1000`. [6](#0-5) [7](#0-6) 

This mirrors the reported bug class precisely: an unprivileged caller supplies both the token/target contract logic and effectively controls the cost multiplier of a protocol-run, non-fee-charging worker (here, the binary-search "auto-estimator" instead of the "auto-collector"), and the QPS-based rate limiter (analogous to "monitoring gas usage") is a generic safeguard rather than a cost-aware one.

### Impact Explanation
This is an underpriced-public-work / resource-exhaustion vector: a normal user (no special role) can, at effectively zero cost (constant calls are not charged fees or consumed against any account's resources), force full nodes exposing `/wallet/estimateenergy` or the gRPC `EstimateEnergy`/`EstimateEnergyOnPBFT` endpoints to perform dozens of full-cost TVM executions per request. With enough concurrent requests (bounded only by the default 1000 qps global/per-endpoint limiter, which is far higher than the actual sustainable throughput of near-timeout TVM executions), this can degrade or stall node responsiveness for legitimate RPC/API consumers, a denial-of-service on public infrastructure paid for by the node operator rather than the caller.

### Likelihood Explanation
Likelihood depends on deployment configuration: `estimateEnergy` support (`vm.estimateEnergy`) and `vm.supportConstant` both default to `false` in `reference.conf`, so the vector only applies to nodes/API providers that have explicitly enabled these (a common configuration for RPC/DApp-facing full nodes and JSON-RPC `eth_estimateGas` support). Where enabled, no additional privilege is required — deploying and calling the target contract are standard operations. This is a realistic, medium-likelihood, config-gated amplification issue rather than a theoretical one.

### Recommendation
- Cap the number of binary-search iterations and/or the total wall-clock time budget for a single `estimateEnergy` request, independent of `constantCallTimeoutMs` per-iteration budget, so a single API call cannot re-run an expensive contract dozens of times.
- Charge or rate-limit `estimateEnergy`/`triggerConstantContract` calls based on measured energy usage of the underlying execution rather than solely on request-count QPS, e.g., a token-bucket keyed on estimated/actual TVM cycles consumed.
- Set explicit, restrictive default rate limits for `EstimateEnergyServlet`/gRPC `EstimateEnergy` in `reference.conf` (currently all specific rate-limit entries are commented out, so only the generic 1000-qps default applies), and document that operators enabling `vm.estimateEnergy` should tighten this.
- Consider bounding `dps.getMaxFeeLimit()`-derived `high` more conservatively for estimation purposes, since it directly determines the number of binary-search steps (`log2(high/TRX_PRECISION)`).

### Proof of Concept
1. Enable `vm.supportConstant = true` and `vm.estimateEnergy = true` on a target full node (a supported, documented configuration for RPC providers).
2. Deploy a contract whose fallback/target function contains a loop tuned to consume energy just under `maxEnergyLimitForConstant` (or to run close to `constantCallTimeoutMs`/the shared block-processing deadline) without reverting.
3. Call `/wallet/estimateenergy` (or gRPC `EstimateEnergy`) against this contract. `Wallet.estimateEnergy` will execute the contract at `high = getMaxFeeLimit()`, then perform the two-times/binary-search loop in `Wallet.estimateEnergy` — each iteration re-executing the same expensive contract, each with up to `estimateEnergyMaxRetry` retries on `Program.OutOfTimeException`.
4. Repeat the request from multiple threads/IPs up to the default 1000 qps allowance; observe cumulative CPU time on the node scale with (binary-search steps × retries × per-call cost) per request, well beyond the cost of a single `triggerconstantcontract` call, degrading node responsiveness for other API consumers.

  public Transaction callConstantContract(TransactionCapsule trxCap,
      Builder builder, Return.Builder retBuilder, boolean isEstimating)
      throws ContractValidateException, ContractExeException, HeaderNotFound, VMIllegalException {

    if (!Args.getInstance().isSupportConstant()) {
      throw new ContractValidateException("this node does not support constant");
    }

    Block headBlock;
    List<BlockCapsule> blockCapsuleList = chainBaseManager.getBlockStore()
        .getBlockByLatestNum(1);
    if (CollectionUtils.isEmpty(blockCapsuleList)) {
      throw new HeaderNotFound("latest block not found");
    } else {
      headBlock = blockCapsuleList.get(0).getInstance();
    }

    BlockCapsule headBlockCapsule = new BlockCapsule(headBlock);
    TransactionContext context = new TransactionContext(headBlockCapsule, trxCap,
        StoreFactory.getInstance(), true, false);
    VMActuator vmActuator = new VMActuator(true);

    try {
      vmActuator.validate(context);
      vmActuator.execute(context);
    } finally {
      // constant call runs on a pooled RPC worker; drop its thread-local VM config view so it
      // can never leak into a later (block/broadcast) execution on the same thread.
      VMConfig.clearLocalSnapshot();
    }

  protected void doPost(HttpServletRequest request, HttpServletResponse response)
      throws IOException {
    TriggerSmartContract.Builder build = TriggerSmartContract.newBuilder();
    TransactionExtention.Builder trxExtBuilder = TransactionExtention.newBuilder();
    EstimateEnergyMessage.Builder estimateEnergyBuilder = EstimateEnergyMessage.newBuilder();
    Return.Builder retBuilder = Return.newBuilder();
    boolean visible = false;
    try {
      String contract = request.getReader().lines()
          .collect(Collectors.joining(System.lineSeparator()));
      Util.checkBodySize(contract);
      visible = Util.getVisiblePost(contract);
      Util.validateParameter(contract);
      JsonFormat.merge(contract, build, visible);
      JSONObject jsonObject = JSONObject.parseObject(contract);

      boolean isFunctionSelectorSet =
          !StringUtil.isNullOrEmpty(jsonObject.getString(Util.FUNCTION_SELECTOR));
      if (isFunctionSelectorSet) {
        String selector = jsonObject.getString(Util.FUNCTION_SELECTOR);
        String parameter = jsonObject.getString(Util.FUNCTION_PARAMETER);
        String data = Util.parseMethod(selector, parameter);
        build.setData(ByteString.copyFrom(ByteArray.fromHexString(data)));
      }

      TransactionCapsule trxCap = wallet.createTransactionCapsule(build.build(),
          Protocol.Transaction.Contract.ContractType.TriggerSmartContract);

      wallet.estimateEnergy(build.build(), trxCap,
          trxExtBuilder, retBuilder, estimateEnergyBuilder);
    } catch (ContractValidateException e) {
      retBuilder.setResult(false).setCode(Return.response_code.CONTRACT_VALIDATE_ERROR)
          .setMessage(ByteString.copyFromUtf8(e.getMessage()));
    } catch (Exception e) {
      String errString = null;
      if (e.getMessage() != null) {
        errString = e.getMessage().replaceAll("[\"]", "\'");
      }
      retBuilder.setResult(false).setCode(Return.response_code.OTHER_ERROR)
          .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + errString));
    }
    estimateEnergyBuilder.setResult(retBuilder);
    response.getWriter().println(
        Util.printEstimateEnergyMessage(estimateEnergyBuilder.build(), visible));
  }
