I found a solid analog: a proof-integrity gap in the replay/verification comparator that is explicitly acknowledged in the code itself but has not been fixed. Let me confirm the surrounding context and callers before finalizing.### Title
Replay/execution-verification comparator silently skips state-checkpoint root hash, letting corrupted state roots pass as "verified" — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used to check that a *locally recomputed* transaction result matches the *authoritative* `TransactionInfo` (the leaf that is actually committed to the transaction accumulator and covered by validator signatures). It is invoked by every offline/replay verification path in the codebase — `aptos-move/cli` transaction replay, `aptos-debugger`, `storage/db-tool/replay_on_archive`, and the chunk executor's `verify_execution` (used when catching up/replaying chunks during state sync and backup verification). This function checks status, gas, write-set hash, and event-root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the actual world-state Merkle root. The gap is even called out in a code comment as a known limitation.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) validates a subset of fields: [1](#0-0) 

It never touches `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, and the code documents this explicitly: [2](#0-1) 

This is structural: `TransactionOutput` itself (`types/src/transaction/mod.rs:2060-2118`) carries only `write_set`, `events`, `gas_used`, `status`, and `auxiliary_data` — it has no field for the state-checkpoint root at all, so the comparator cannot verify it even in principle. [3](#0-2) 

`ensure_match_transaction_info` is the sole "did replay reproduce the correct ledger state" check used by:
- The chunk executor's `verify_execution`, which re-executes a batch of transactions through the VM and compares the result against the persisted/expected `TransactionInfo` before trusting the replayed state during chunk-based replay/sync: [4](#0-3) 
- `storage/db-tool/replay_on_archive.rs`, an operator/auditor tool whose entire purpose is to detect divergence between archived history and re-executed history: [5](#0-4) 
- `aptos-move/cli`'s transaction replay/debugging command, used to validate that a locally executed transaction matches on-chain history: [6](#0-5) 

In none of these call sites is `state_checkpoint_hash` (or the newer hot-state/position-state checkpoint hashes) independently re-verified after `ensure_match_transaction_info` returns `Ok(())`. The consumer only checks whether this function errors, and treats a successful return as "the replayed transaction reproduces the authenticated ledger state." That assumption is false for anything affecting the state-checkpoint/JMT root that does not also change the per-transaction write set or event hash — e.g., a bug in `DoStateCheckpoint`'s Sparse-Merkle/JMT update logic (`execution/executor/src/workflow/do_state_checkpoint.rs`), a bug in the new native-position state root computation, or externally corrupted/tampered checkpoint-hash data in a backup/archive being replayed.

### Impact Explanation
This breaks the proof-integrity guarantee that "replay of committed data reproduces the same authenticated state root." Concretely:
- `db-tool replay_on_archive` and `aptos-debugger`/CLI replay are the tools operators and auditors use to detect state divergence or archive corruption; they will report a transaction as verified/matching even when the underlying state-checkpoint (world-state) root differs from what is signed in the ledger.
- The chunk executor's `verify_execution` path (used during backup-restore / long-range replay verification) accepts a batch as correctly re-executed without checking that the recomputed world state root at checkpoints matches the expected root, so a subtly wrong state (e.g., from a JMT/state-checkpoint computation bug, or a maliciously altered archive/backup state-checkpoint hash that doesn't get independently re-derived elsewhere in that code path) can pass verification undetected.
- This is exactly the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated ... output bound to the wrong ... proof context" category called out as in-scope: the proof-bearing field (`state_checkpoint_hash`) is silently dropped from the authoritative-vs-recomputed comparison used by replay/verification tooling.

Note: on the live consensus/commit hot path, an actually wrong state root would still normally be caught because the final `LedgerInfo`'s accumulator root (which incorporates `TransactionInfo::hash()`, including `state_checkpoint_hash`) must match across 2f+1 validators, and `aptosdb_writer.rs::check_and_put_ledger_info` verifies `db_root_hash == li_root_hash` before committing a signed ledger info. The severity here is specifically about **offline replay/verification tooling and chunk-based replay/backup-restore verification**, which are the last line of defense for detecting divergence/corruption outside of live consensus (e.g., after backup restore, during long-range state-sync catch-up, or when auditing archived history) — and that line of defense is compromised for this specific class of state-root corruption.

### Likelihood Explanation
The gap is unconditional and always active — every call to `ensure_match_transaction_info` across all four call sites is affected, not gated behind a feature flag (the feature-flag comment refers only to enabling stricter *future* validation for the new hot-state/position-state fields; the omission of the already-live `state_checkpoint_hash` check is present today). No malicious input is even required to trigger it: any legitimate divergence in checkpoint-hash computation (bug, non-determinism, storage corruption, tampered backup blob) that doesn't also change the per-transaction write set/events will be missed by every consumer of this function.

### Recommendation
Extend `ensure_match_transaction_info` (or its callers) to independently verify `state_checkpoint_hash` (and, once enabled, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against the recomputed state-checkpoint root produced by `DoStateCheckpoint`, rather than relying solely on write-set/event-hash equality. Since `TransactionOutput` does not carry a checkpoint-hash field, the checkpoint root must be threaded through from the execution/checkpoint pipeline (`StateCheckpointOutput`) into the verification call sites (`chunk_executor::verify_execution`, `replay_on_archive`, `aptos-debugger`/CLI replay) and compared explicitly, as the existing TODO comment in the code itself already recommends.

### Proof of Concept
Not directly exploitable as a standalone PoC without triggering an actual state-checkpoint computation bug or archive corruption; the vulnerability is a missing-check (proof-integrity gap), demonstrable by static trace:
1. Corrupt or diverge only the persisted `state_checkpoint_hash` in a backup/archive chunk (or introduce a bug in `DoStateCheckpoint::run`, `execution/executor/src/workflow/do_state_checkpoint.rs:33-84`) while leaving per-transaction write sets/events/gas/status unchanged.
2. Run `storage/db-tool replay_on_archive` (`execute_and_verify`, `storage/db-tool/src/replay_on_archive.rs:349-416`) or the chunk executor's `verify_execution` (`execution/executor/src/chunk_executor/mod.rs:648-708`) against this data.
3. `ensure_match_transaction_info` returns `Ok(())` because it never inspects `state_checkpoint_hash`, so the tool reports a clean/verified replay despite the world-state root divergence.
