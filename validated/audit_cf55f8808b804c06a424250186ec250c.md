### Title
Unbounded CPU consumption via JSON-RPC batch notifications bypassing response-size DoS guard - (File: framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java)

### Summary
In `JsonRpcServlet.handleBatch`, every sub-request in a batch — including JSON-RPC "notifications" (objects with no `id` field) — is passed to `rpcServer.handleRequest()` and fully executed server-side before the result is discarded. Because notifications produce an empty `responseBytes` array, the `accumulatedSize`/`maxResponseSize` guard is never incremented for them, so an attacker can pack a batch with many CPU-heavy `eth_call` notifications and force the node to perform unbounded computation per HTTP request while completely evading the response-size-based throttle.

### Finding Description
The relevant code path is: [1](#0-0) 

For each element of the batch array, the servlet serializes the sub-request and calls `rpcServer.handleRequest(new ByteArrayInputStream(subBody), subOutput)` unconditionally — regardless of whether the request has an `id`. `handleRequest` fully invokes the underlying JSON-RPC method (e.g., `eth_call`, which executes EVM bytecode against a contract/state) before returning. Only after execution does the code check `responseBytes.length == 0` (true for notifications, since JSON-RPC servers by spec do not emit a response for id-less requests) and `continue` — discarding the result without ever adding to `accumulatedSize` or checking `maxResponseSize`.

The only two backend protections that exist are:
1. `jsonRpcMaxBatchSize` — a cap on the *number* of items in the batch array, checked at line 136-141 before `handleBatch` is invoked: [2](#0-1) . This bounds count, not per-item computational cost, and per the question's stated precondition can be configured large or disabled (`batchSize > 0` check — setting it to `0` or negative disables it entirely).
2. `maxResponseSize` (accumulatedSize tracking) — this only fires when `responseBytes.length > 0`, so it structurally cannot bound notification-based requests: [3](#0-2) 

Outside of `JsonRpcServlet`, the only other gate is `RateLimiterServlet.service()`, which enforces per-IP/global QPS limits on the number of HTTP requests, not on the computational cost of a single request's contents: [4](#0-3) . A single POST containing hundreds/thousands of heavy `eth_call` notifications counts as one request against this limiter, so it does not mitigate the per-request amplification.

There is no per-sub-request execution timeout, no CPU/energy accounting, and no distinction in cost calculation between notifications and regular calls before invoking `rpcServer.handleRequest`. This matches the exact mechanism described in the question: an attacker-controlled batch of notification-only `eth_call` requests forces full backend computation per element while the size-based guard never engages.

### Impact Explanation
This is a Denial-of-Service against the JSON-RPC API surface (DoS via RPC-API). By sending a single POST with many notification-style `eth_call` entries targeting a loop-heavy read-only contract, an attacker can consume disproportionate CPU/EVM execution time on the node relative to the request's size and the number of HTTP requests counted by the rate limiter, degrading service for legitimate JSON-RPC clients or the node's participation in block processing (if computation is heavy enough to starve threads). This does not lead to key leakage, state corruption, or consensus divergence — it is bounded to availability degradation of the JSON-RPC service.

### Likelihood Explanation
- Requires no authentication or privileged role — any anonymous client with network access to the JSON-RPC HTTP endpoint can send the batch.
- Requires `jsonRpcMaxBatchSize` to be large or disabled (0/negative), which is an operator configuration matter but plausible if not hardened; even with a moderate default nonzero cap, the attacker can still submit up to that cap's number of heavy `eth_call` notifications per request repeatedly, sidestepping the size guard within each request while incurring no per-item cost check.
- No fee, energy, or bandwidth cost is paid for `eth_call` (it's a query, not a broadcast transaction), so the attack is essentially free to execute repeatedly.
- Fully reproducible with a scripted HTTP client; no timing race or privileged setup needed.

### Recommendation
- Count computational/response cost for notifications too (e.g., measure `responseBytes` length even when discarding, or better, impose a hard cap on the number of "heavy" method invocations — such as `eth_call`/`eth_estimateGas` — per batch, independent of `id` presence).
- Add a wall-clock or gas/energy budget check inside `handleBatch` that aborts the loop once cumulative execution time/cost across all sub-requests (notifications included) exceeds a threshold, rather than only bounding output size.
- Consider rejecting or specially rate-limiting batches containing a majority of notifications, since they provide no protocol benefit to legitimate users of a request/response API but enable this amplification.

### Proof of Concept
```
POST /jsonrpc HTTP/1.1
Content-Type: application/json

[
  {"jsonrpc":"2.0","method":"eth_call","params":[{"to":"0x<loopHeavyContract>","data":"0x<expensiveSelector>"} ,"latest"]},
  {"jsonrpc":"2.0","method":"eth_call","params":[{"to":"0x<loopHeavyContract>","data":"0x<expensiveSelector>"} ,"latest"]},
  ... (repeated N times, each object omitting "id")
]
```
Expected behavior demonstrating the flaw:
1. Server responds with HTTP 200 and empty/near-empty body (per `batchResult.isEmpty()` branch at lines 252-258 or minimal content), since none of the items produced a response.
2. `accumulatedSize` never advances beyond `2` regardless of `N`, so `maxResponseSize`/overflow logic never triggers for these items — verifiable by instrumenting/logging `accumulatedSize` across the loop in a JUnit test that drives `handleBatch` directly with a batch of N no-`id` `eth_call` requests, asserting `accumulatedSize == 2` after the loop while measuring elapsed wall-clock time growing linearly with N (demonstrating real backend work was performed for each despite the discarded output).
