**Analysis:** The Move `sha3_512` function directly delegates to the native `sha3_512_internal` function, which is implemented in `native_sha3_512` in `aptos-move/framework/natives/src/hash.rs` using the standard `sha3::Sha3_512` crate. [1](#0-0) [2](#0-1) 

There is no separate "Move-level" hash implementation distinct from the native Rust implementation — the Move function is a thin wrapper that unconditionally calls the native function (after a feature-flag gate), so there is no possibility of divergence between "what Move computes" and "what the native Rust code computes." They are the same computation. The native implementation is deterministic, executed identically by every validator as part of the VM binary, and its output is verified against standard SHA3-512 test vectors in the Move test suite. [3](#0-2) 

Since every validator runs the same native code on the same input bytes, any Move struct that embeds a `sha3_512` output and is later BCS-serialized and hashed again (e.g., for an event key or object address) will be computed identically on all nodes. There is no code path in this repository where "the Move-level output" could differ from "the native Rust output" for the same input — they are one and the same call. This premise does not correspond to an actual divergence in the codebase, so there is no basis for accumulator root, event proof, or state proof corruption arising from this function.

fn native_sha3_512(
    context: &mut SafeNativeContext,
    mut _ty_args: &[Type],
    mut args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    debug_assert!(_ty_args.is_empty());
    debug_assert!(args.len() == 1);

    let bytes = safely_pop_arg!(args, Vec<u8>);

    let cost = HASH_SHA3_512_BASE + HASH_SHA3_512_PER_BYTE * NumBytes::new(bytes.len() as u64);
    context.charge(cost)?;

    let mut hasher = sha3::Sha3_512::new();
    hasher.update(&bytes);
    let output = hasher.finalize().to_vec();

    Ok(smallvec![Value::vector_u8(output)])
}
