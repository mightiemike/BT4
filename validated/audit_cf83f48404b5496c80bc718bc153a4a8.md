### Title
Unbounded `delayed_declares` queue causes per-transaction linear scan, degrading mempool ingestion under load - ([File: crates/apollo_mempool/src/mempool.rs])

### Summary
The mempool defers every incoming `Declare` transaction (in non-FIFO/priority mode) into a `delayed_declares` queue for `declare_delay` before admitting it to the pool [1](#0-0) . Every subsequent `add_tx` call — for *any* account, not just the one with pending declares — must check whether the incoming transaction conflicts with a still-delayed declare via `validate_no_delayed_declare_front_run`, which calls `self.delayed_declares.contains(tx_reference.address, tx_reference.nonce)` [2](#0-1) . This mirrors the reported bug class: an attacker-growable collection (`projectUsersInETH`/`projectUsersInUSDT` in the original report; here, `delayed_declares`) is scanned in full on a hot, frequently-invoked path (`refundFromAdmin*` there; `add_tx`/`get_txs` here), so cost grows with attacker-controlled queue size rather than being bounded.

### Finding Description
`delayed_declares` is a queue (accessed via `front()`/`pop_front()`/`push_back()`, i.e., FIFO/VecDeque-like) holding every declare transaction that has not yet passed its `declare_delay` window [3](#0-2) . Its size is controlled purely by how many distinct accounts submit valid `Declare` transactions and is only drained lazily, one delay-window at a time, by `add_ready_declares` [4](#0-3) .

Crucially, `add_tx_validations` (invoked for every incoming transaction from every account) calls `validate_no_delayed_declare_front_run`, which performs a `contains(address, nonce)` lookup against this same queue [2](#0-1) . Given the queue's exposed API is limited to `front`/`push_back`/`pop_front`/`contains` with no indexing structure evidenced in the surrounding code, `contains` is most consistent with a linear scan over all queued declares. If so, every single transaction admission — regardless of sender — pays a cost proportional to the total number of currently-delayed declare transactions from all accounts combined.

### Impact Explanation
If `contains` is indeed O(n), an attacker who repeatedly submits cheap, valid `Declare` transactions from many distinct addresses (paying only the declare fee, no need for them to ever be committed) can inflate `delayed_declares` to a large size within one `declare_delay` window. While inflated, *every* other user's `add_tx` (and the `get_txs`/`add_ready_declares` invocation from block building) pays an O(n) penalty, degrading mempool ingestion throughput for the entire network during that window. This is analogous to the reported bug's "admin refund becomes unavailable due to unbounded loop over attacker-grown array," except here the growable/scanned structure sits on the mempool's transaction-admission hot path, which can affect the network's ability to admit/confirm new transactions if the delay window is kept saturated by repeated cheap declare submissions.

### Likelihood Explanation
Medium-to-High, contingent on confirming that `AddTransactionQueue::contains` is a linear scan (not indexed by address/nonce) — this could not be fully verified from the available code snippets, since the struct's implementation file was not retrieved before the investigation budget was exhausted. The reachable trigger (submitting many `Declare` transactions from distinct addresses) is fully within reach of an unprivileged transaction sender and requires no special permissions, matching the rules' allowed reach ("mempool admission and ordering").

### Recommendation
- Confirm the concrete implementation of `AddTransactionQueue::contains`; if it is a linear scan, replace it with an indexed lookup (e.g., a `HashMap<(ContractAddress, Nonce), _>` or `HashSet<(ContractAddress, Nonce)>`) so membership checks are O(1) regardless of how many declares are currently delayed.
- Bound `delayed_declares` size independently of the general mempool byte-capacity check (which does not appear to gate delayed declares before `push_back`), e.g., cap total delayed declares per account or in aggregate, and reject/evict excess declare submissions.

### Proof of Concept
Conceptual (network-mempool-level, not confirmed against exact `contains` implementation):
1. Submit N valid `Declare` transactions from N distinct fresh addresses, each paying minimal required declare fee, while `behavior_mode` is `Starknet` (non-FIFO), so each is deferred into `delayed_declares` for `declare_delay` [1](#0-0) .
2. While these N entries remain in the delay window, submit an ordinary `Invoke` transaction from an unrelated account. Its `add_tx` triggers `validate_no_delayed_declare_front_run`, which scans the full `delayed_declares` queue of size N [2](#0-1) .
3. Repeat step 2 for many unrelated senders during the delay window; total ingestion cost across the network scales with N per transaction, rather than being O(1), degrading mempool throughput proportional to the attacker's spend on cheap declare transactions.

Because I could not directly inspect `AddTransactionQueue`'s internal data structure/`contains` method within the available tool budget, this should be verified by reading its definition (likely near the `Mempool` struct in `crates/apollo_mempool/src/mempool.rs`) before treating this as a confirmed vulnerability rather than a plausible analog.
