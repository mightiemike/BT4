### Title
Single transaction's class-manager conversion failure aborts the entire block-building batch, unlike per-transaction execution failures - (File: `crates/apollo_batcher/src/block_builder.rs`)

### Summary
`BlockBuilder::add_txs_to_executor` converts a whole chunk of consensus transactions to executable form concurrently via `futures::future::try_join_all`, calling into the external `ClassManagerClient` for every `Declare` transaction in the chunk. `try_join_all` fails fast: if the conversion of **any single transaction** in the chunk errors (e.g. `TransactionConverterError::ClassManagerClientError` or `ClassNotFound`), the whole call returns `Err`, which propagates via `?` up through `add_txs_to_executor` → `build_block_inner` → `build_block`, causing the entire block-building attempt (including all other, unrelated, valid transactions already accumulated in `self.block_txs`) to abort via `executor.abort_block()`.

This is the structural analog of the reported bug: exactly as a single failing external money-market call reverts an entire multi-market rebalance in Notional, here a single failing external dependency call (the class manager, an out-of-process/remote component reached over gRPC in distributed deployments) for a single transaction aborts an entire batch/block that otherwise contains many unrelated, valid transactions.

### Finding Description

Finally, `BlockBuilder::build_block` treats **any** error from `build_block_inner` as fatal for the whole block and calls `abort_block()`, discarding all execution progress made so far for that height/proposal: [5](#0-4) 

This is architecturally inconsistent with how the same code base handles per-transaction *execution* failures from the blockifier itself: those failures (`TransactionExecutorError` variants returned per index from `get_new_results`) are tolerated and simply excluded from the block without aborting the batch, as shown by the test harness that explicitly expects failed transactions to be dropped while the rest of the block still closes successfully: [6](#0-5) 

So there are two different fault-handling philosophies in the same pipeline: execution-level failures are isolated per transaction, but transaction-conversion failures (which route through the external class-manager dependency) are not isolated and instead take down the whole in-flight chunk/block.

### Impact Explanation
When a single transaction's conversion fails inside a chunk (`n_concurrent_txs` transactions batched together), the batcher aborts the entire block build (`abort_block()`), discarding execution results for every other, unrelated, valid transaction that had already been added to `self.block_txs`/executed in that build attempt. As proposer, this prevents the node from producing a proposal for that height at all; as validator, it forces `FailOnErrorCause`-style rejection of an otherwise valid proposal. Because chunk sizes (`n_concurrent_txs`) batch many transactions together, one bad transaction can repeatedly deny block production for that attempt, degrading liveness/throughput of the sequencer (a network unable to confirm new transactions for the affected height/round) rather than causing a fund-loss bug directly.

### Likelihood Explanation
The `ClassManagerClient` is reached over an in-process or remote (gRPC) call depending on deployment topology; any of `ClassManagerClientError` or `ClassNotFound` on a *single* `Declare` transaction present in the batch is sufficient to trigger this path. The code has explicit test coverage acknowledging the class manager can be slow/unresponsive ("stalled component" test), underscoring that error/latency conditions on this dependency are anticipated but the batch-wide fail-fast handling in `add_txs_to_executor` was not hardened against it. However, definitively proving how an *unprivileged transaction sender* can deterministically force a `ClassManagerClientError` (versus a purely infrastructure/availability issue on the class-manager side) requires additional investigation that could not be completed with the available read-only tools — the exact conditions under which a legitimately-included `Declare` transaction's class becomes unavailable to the class manager at block-building time (as opposed to purely operational/network failures, which are out of scope per the given rules) are not confirmed here.

### Recommendation
In `add_txs_to_executor`, avoid `try_join_all`'s fail-fast semantics for the conversion stage. Use `futures::future::join_all` and collect per-transaction results, dropping only the failing transaction(s) from the chunk (mirroring how execution failures are already handled), while still surfacing/logging the underlying class-manager error and metrics — but not calling `abort_block()` for the entire in-flight proposal because a single member of the chunk failed to convert.

### Proof of Concept
Not applicable as a runnable exploit given the read-only nature of this analysis; the control-flow proof is the code path traced above:
1. `add_txs_to_executor` batches `n_concurrent_txs` consensus transactions, at least one of which is a `Declare`. [7](#0-6) 
2. If the class manager returns an error or `None` for that Declare's class during `get_sierra`/`get_executable`, `try_join_all` returns `Err(TransactionConverterError)`. [8](#0-7) 
3. This `Err` propagates through `add_txs_to_executor().await?` in `build_block_inner`, and then `build_block` calls `executor.abort_block()`, discarding the whole block-building attempt including all other valid transactions in the chunk/block. [5](#0-4)
