### Title
Zero-payment token theft in `MarketSellAssetActuator.matchSingleOrder` exact-match branch — ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
The TRC10 on-chain order-matching engine (`MarketSellAssetActuator`) computes the counter-payment a maker receives via integer (floor) division through `MarketUtils.multiplyAndDivide`. In the "taker == maker" (exact-match) branch of `matchSingleOrder`, this computed value (`makerBuyTokenQuantityReceive`) is never checked for zero, unlike the structurally identical computation in the "taker > maker" branch, which explicitly guards against a zero result. An attacker who controls both the maker order (crafted ahead of time) and the matching taker order can force `makerBuyTokenQuantityReceive` to round down to 0 while still causing the full remaining quantity of the maker's already-escrowed tokens to be credited to the taker, closing the maker order with the maker receiving nothing back. This mirrors the reported `StarBaseDCA` bug class: an unvalidated/near-zero "payment" amount lets a taker receive assets while paying (effectively) zero.

### Finding Description
`MarketSellAssetActuator.matchSingleOrder` computes, for each match between a taker order and a maker order: [1](#0-0) 

then branches into three cases. In the exact-match branch: [2](#0-1) 

Here `makerBuyTokenQuantityReceive` is computed by floor division (`MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`), which can legitimately evaluate to `0` for small ratios, while `takerBuyTokenQuantityReceive` is unconditionally set to the *entire* `makerOrderCapsule.getSellTokenQuantityRemain()` — i.e., all of the maker's remaining escrowed tokens.

Contrast this with the "taker > maker" branch, which performs the exact same computation but explicitly guards against the zero case before crediting anyone: [3](#0-2) 

The comment at lines 466-474 explicitly acknowledges that a zero payment can occur mathematically and argues it "would not happen here" for that specific branch given order-construction constraints — but no equivalent reasoning or protection is applied to the "taker == maker" branch, even though it uses the identical rounding computation.

After all three branches, execution falls through to unconditionally persist the maker order and credit both parties: [4](#0-3) 

So in the exact-match branch with `makerBuyTokenQuantityReceive == 0`:
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` closes/consumes the maker's order (their tokens were already deducted from their balance at order-creation time via `transferBalanceOrToken`/`reduceAssetAmountV2`).
- `addTrxOrToken(makerOrderCapsule, 0)` credits the maker with nothing.
- `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` credits the taker with the maker's entire remaining sell quantity for free.
- The taker's own remaining sell quantity (`takerSellTokenLeft = taker remain - makerBuyTokenQuantityReceive`) is reduced by 0, so the taker's own order is left effectively untouched, i.e., the taker pays nothing for the tokens received.

This is directly analogous to the reported `StarBaseDCA.fillDCA` issue: an unvalidated/near-zero computed "payment" amount (`curTakerFillAmount` in the report, `makerBuyTokenQuantityReceive` here) allows the counterparty to receive assets (`order.inAmount` in the report, the maker's escrowed sell tokens here) while transferring effectively nothing in return, because the code lacks a `> 0` validation for that specific computed value in that specific code path.

### Impact Explanation
This is reachable by any account submitting an ordinary `MarketSellAssetContract` transaction (a `TriggerContract`-level, unprivileged, broadcast transaction) — no special permissions or admin role required. If exploitable, it allows direct theft of already-escrowed TRC10 tokens or TRX from a maker order: the maker's assets, deducted and held by the exchange/market engine at order-creation time, are transferred to the taker without any corresponding consideration, causing real asset/accounting corruption in on-chain balances (`AccountCapsule` TRX balance or TRC10 asset map). Since a single account can act as both maker and taker (the market has no restriction preventing self-trading), the attacker can engineer both orders to deliberately trigger the exact-match branch with the rounding-to-zero condition, making this exploitable rather than a purely theoretical edge case.

### Likelihood Explanation
Exploitability depends on being able to construct maker/taker order quantities and prices (`sellTokenQuantity`, `buyTokenQuantity`) such that: (1) `takerBuyTokenQuantityRemain` (`multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity)`) exactly equals `makerOrderCapsule.getSellTokenQuantityRemain()`, and (2) `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity)` floors to `0`. Both conditions are governed entirely by attacker-chosen integers (quantities and prices), and `MarketUtils.multiplyAndDivide` performs plain floor-division arithmetic with no automatic rejection of degenerate ratios, so constructing such values is a matter of arithmetic search rather than requiring any race condition, timing, or privileged access. This makes the likelihood MEDIUM-HIGH for a determined attacker able to freely create and match TRC10 market orders, though it requires careful arithmetic engineering to hit the exact-match branch, and I could not fully verify the achievability from the available code alone (e.g., interactions with `MAX_MATCH_NUM`, order price bucketing via `pairPriceToOrderStore`, and exact integer boundaries of `multiplyAndDivide`) within the scope of this review — these would need to be confirmed with concrete numeric test cases or a live/staging TVM run.

### Recommendation
In the "taker == maker" branch of `matchSingleOrder` (around actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:426-439), add an explicit `makerBuyTokenQuantityReceive == 0` check mirroring the one already present in the "taker > maker" branch (lines 466-477): if the computed value is zero, do not credit the taker with the maker's remaining sell quantity, and instead return the maker's remaining sell tokens to the maker (as done via `returnSellTokenRemain`) rather than crediting them to the taker for free. More broadly, unify the zero-payment guard so that every code path computing a "receive" quantity via `MarketUtils.multiplyAndDivide` validates the result is `> 0` before any token/balance transfer is performed, consistent with the recommendation in the referenced report to always validate the computed exchange/payment amount before executing a transfer.

### Proof of Concept
Not independently executed; a concrete PoC would require:
1. Account A creates a maker sell order with `sellTokenQuantity`/`buyTokenQuantity` chosen so that its residual `sellTokenQuantityRemain` (`makerSellRemainQuantity`) combined with `makerBuyQuantity/makerSellQuantity` yields `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity) == 0` via floor division.
2. Account A (or a colluding/attacker-controlled second account) then submits a taker sell order whose `takerSellRemainQuantity`, combined with the maker's price ratio, yields `takerBuyTokenQuantityRemain == makerSellRemainQuantity` exactly, forcing execution into the exact-match branch (lines 418-439 of `MarketSellAssetActuator.java`).
3. Observe that after `execute()`, the taker's account balance/asset map is credited with the maker's full remaining sell quantity (`addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)`), while the maker's order is closed (`sellTokenQuantityRemain = 0`) having been credited with `0` (`addTrxOrToken(makerOrderCapsule, 0)`), and the taker's own remaining sell quantity is unchanged, confirming a zero-cost transfer of the maker's escrowed assets to the taker.
