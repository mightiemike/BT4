### Title
Griefing via unscoped, user-controlled `requestID` collisions in HTTP trigger request registration - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The reported Folks Finance bug is a griefing pattern where a user-supplied identifier (`loanId`) is used as a global mapping key without any per-user namespace, letting a bad actor front-run and register the same ID first, causing the legitimate user's request to permanently fail. The chainlink CRE Gateway's HTTP trigger handler exhibits the same bug class: request identity is keyed purely by an attacker-controllable string (`req.ID`) in a single, gateway-instance-wide map, with no per-workflow or per-sender namespacing, so a colliding submission can block a legitimate request from being registered.

### Finding Description
`httpTriggerHandler.HandleUserTriggerRequest` validates and authorizes an incoming request, then calls `setupCallback`, which registers the callback keyed solely by the caller-supplied `req.ID`: [1](#0-0) 

```
func (h *httpTriggerHandler) setupCallback(...) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()
	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(..., "requestID: %s has already been used...")
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
	...
}
```

`h.callbacks` is a single map shared across the whole `httpTriggerHandler` instance (i.e., across *all* workflows served by that DON's gateway), not scoped by workflow ID or sender/owner. The only validation performed on the ID before this collision check is that it is non-empty and does not contain `/`: [2](#0-1) 

This mirrors the Folks Finance root cause precisely: an arbitrary, user-chosen identifier is used as the sole key into a shared, mutable global structure, and "already exists" is treated as a fatal, unrecoverable condition for the second submitter rather than being isolated per-tenant. Any sender who is an authorized signer for *any* registered workflow can pass the JWT-based `authorizeRequest` check for their own workflow, then deliberately choose (or, if IDs are predictable/observed, front-run) a `requestID` that a different, unrelated workflow's legitimate caller is about to use (or is using in-flight), and win the race to `setupCallback`, causing that other caller's genuinely distinct request to be rejected with `jsonrpc.ErrConflict` ("requestID ... has already been used").

This is confirmed by the existing test that demonstrates the same-ID collision rejecting a second, legitimate submission: [3](#0-2) 

### Impact Explanation
An attacker with valid credentials for one workflow can, without any profit motive, cause denial-of-service on request creation for other workflows/senders that happen to pick (or reuse, e.g. via client-side idempotency keys) the same `requestID` string, since the map is not namespaced. Because clients (workflow SDKs, HTTP trigger callers) frequently generate deterministic or low-entropy request IDs for idempotency/deduplication purposes, and the gateway's uniqueness check spans the *entire* handler rather than being scoped to `(workflowID, sender)`, this is a realistic griefing vector: legitimate requests are rejected with a conflict error and must be retried with a new ID, exactly analogous to the Folks Finance `UserLoanAlreadyCreated` revert griefing the victim's loan creation.

### Likelihood Explanation
Exploitability requires the attacker to hold a valid authorized key for at least one registered workflow on the gateway (i.e., be a legitimate but unprivileged "unprivileged-user" caller of the CRE HTTP trigger capability, not a node/operator), and to know or predict the victim's chosen `requestID` in advance. This is plausible where clients use predictable IDs (sequence numbers, hashes of static inputs, low-entropy identifiers) for idempotent retries — the same pattern that made the original Folks Finance bug practically exploitable (`keccak256(user, accountId)` was precomputable). The lack of namespacing by workflow/sender significantly increases the attack surface compared to a single-tenant contract, since one authorized-but-malicious workflow caller can grief requests belonging to a completely different, unrelated workflow.

### Recommendation
Scope the in-flight-request uniqueness key by `(workflowID, authorizedOwner/sender, requestID)` instead of by the raw user-supplied `requestID` alone, so that collisions can only occur within a single sender's own request stream, not across arbitrary tenants. Additionally, avoid making an ID collision a hard failure for the second caller when the callers are different authorized identities — treat cross-tenant collisions as a namespace error and internally allocate an execution identifier that is not directly attacker-controlled for internal bookkeeping (similar to the Folks Finance recommendation of switching to an internally managed identifier rather than an arbitrary caller-supplied value).

### Proof of Concept
Conceptual PoC (based on the existing `TestHttpTriggerHandler_HandleUserTriggerRequest` "duplicate request ID" test at lines 316-354):
1. Attacker holds a valid signing key authorized for Workflow A (or any registered workflow) and can pass `authorizeRequest`/JWT validation for their own request.
2. Attacker predicts or observes the `requestID` that a victim's client will use for Workflow B (e.g., a deterministic/idempotency-style ID), and submits a `workflows.execute` request with `req.ID = victimRequestID`, authorized under their own workflow/JWT.
3. Attacker's request reaches `setupCallback` first and inserts `h.callbacks[victimRequestID]`.
4. Victim's legitimate request for Workflow B with the same `req.ID` arrives at `setupCallback`, finds the key already present, and is rejected with `jsonrpc.ErrConflict` / "requestID ... has already been used", exactly as demonstrated by the existing unit test at [4](#0-3) , but here cross-tenant instead of same-tenant retry.

Note: I could not fully verify the cleanup/TTL behavior of `h.callbacks` (e.g., `cleanupCallback`, `CleanUpPeriodMs`) due to a tool access issue in this session, so the exact griefing window duration is unconfirmed; however, the root-cause collision logic at lines 397-404 is fully confirmed via direct file reads.

```go
func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}
```

```go
func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
```
