### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay-verify accept a corrupted state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to check that locally re-executed transaction outputs match the authenticated `TransactionInfo` recorded on an archived/backup ledger — only compares `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash`. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, a gap the code itself documents.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only the transaction status, gas used, write-set hash and event root hash against the given `TransactionInfo`. The trailing comment makes the gap explicit: [2](#0-1) 

This comment states that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the actual verification primitive used by `storage/db-tool/src/replay_on_archive.rs`, which re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` against the `expected_txn_infos` pulled from the backup/archive to decide success/failure of the replay: [3](#0-2) . The same method is also invoked from `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` for similar replay/verify purposes.

Meanwhile, the state-checkpoint hashes it fails to check are meaningful, deterministically-computed roots: `DoStateCheckpoint::run` computes `state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, and (when `compute_trading_native_state_roots` is on) `position_state_checkpoint_hashes` from the post-execution Jellyfish/position Merkle summaries [4](#0-3) , and `DoLedgerUpdate::run` folds these hashes into the `TransactionInfo`/`TransactionInfoV1` objects that get hashed into the transaction accumulator [5](#0-4) . `TransactionInfoV1` explicitly carries `position_state_checkpoint_hash` as a "repurposed reserved field" [6](#0-5) .

So the state root (or hot-state / native-position root) is a first-class, consensus-committed value baked into the accumulator via `TransactionInfo`, but the one code path whose entire purpose is to catch divergence between local re-execution and the authenticated historical record silently omits checking it.

### Impact Explanation
Replay-verify is the safety net intended to catch exactly the class of bug this task is scoped to: "committed state that differs from the correct VM result," and "hard-fork-only divergence during commit, replay, restore, or proof verification." If a state-computation bug (e.g., in JMT update logic, hot-state promotion, or the new native-position state summary) causes the locally recomputed state/hot-state/position checkpoint root to diverge from the historically committed one, `ensure_match_transaction_info` will still report success as long as the write-set hash, event root, status, and gas match — even though the state roots differ. This means a state-root-corrupting bug can pass `db-tool replay-verify` (used in CI/release validation, per `testsuite/replay-verify/main.py`) undetected, only to be discovered later as a genuine mainnet ledger divergence/hard-fork incident, since the verification gate that should have caught it was blind to exactly this invariant. The comment in the source explicitly flags this as a pre-condition that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," confirming this is a known, currently-live gap rather than a hypothetical.

### Likelihood Explanation
This is not a hypothetical exploit chain requiring an attacker — it's a verification-completeness bug in code that ships today, and it is self-acknowledged in-repo via the `TODO(trading-native)` comment. The `state_checkpoint_hash` and `hot_state_checkpoint_hash` fields are always populated in production (`transaction_info_v1`/`hot_state_root_in_txn_info` on-chain flags), so the missing-comparison gap is active for every replay-verify run today, not just once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on. The main uncertainty is that I could not confirm whether replay-verify is the *only* safety mechanism relying on this comparator, or whether independent state-root verification exists elsewhere (e.g., a separate JMT root re-computation check) that would compensate for this gap — I did not find one in the paths examined, but the search budget did not allow exhaustively ruling this out across the full storage/chunk-executor commit path.

### Recommendation
Extend `ensure_match_transaction_info` to also assert `self.write_set` state-checkpoint hash equality against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` when those fields are present (i.e., `TransactionInfo::V1`), following exactly the recommendation already left in the code comment. This should be done before any wider reliance on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, and ideally backported so that `replay_on_archive`/`aptos-debugger`/`cli` replay-verify tooling actually fails fast on state-root divergence rather than only on write-set/event mismatches.

### Proof of Concept
Not directly exploitable by an external attacker; this is a completeness gap in an internal verification tool. To demonstrate:
1. Run `db-tool replay-on-archive` against a range of historical transactions where `transaction_info_v1`/hot-state root is enabled.
2. Introduce (or find) a divergence purely in the JMT/hot-state root computation (e.g., corrupt a value in `LedgerStateSummary::update`'s hot-state path) that leaves the write-set/events/status/gas identical to the historical record but changes `state_checkpoint_hash`/`hot_state_checkpoint_hash`.
3. Observe that `execute_and_verify` in `replay_on_archive.rs` calls `ensure_match_transaction_info` [7](#0-6)  and reports no error, because the function never inspects the checkpoint-hash fields [8](#0-7) , despite the underlying state root having actually diverged.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
