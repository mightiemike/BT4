### Title
Non-deterministic, wall-clock-based L1 handler cancellation timelock causes honest-validator divergence and repeated block-validation failures - ([File: crates/apollo_l1_events/src/transaction_record.rs])

### Summary
`TransactionRecord::update_time_based_state` decides whether an L1→L2 message transitions from `CancellationStartedOnL2` to `CancelledOnL2` using each node's own local wall-clock time (`unix_now`), not a value derived deterministically from block/consensus data. Because both the proposer (`get_txs`) and every validator (`validate`) independently call `self.clock.unix_now()` [1](#0-0)  at the moment they process a block, a message whose cancellation timelock boundary falls close to block-processing time can be evaluated as `Validated` by some nodes and `Invalid(CancelledOnL2)` by others for the identical L1 handler transaction.

### Finding Description
`update_time_based_state` performs the state transition purely based on `unix_now` read from the caller's local clock and the (also locally supplied) `cancellation_timelock`: [2](#0-1) 

This function is invoked from `TransactionManager::validate_tx`, which is called by every validator during block validation via `L1EventsProvider::validate`: [3](#0-2) 

`self.clock.unix_now()` comes from `DefaultClock`, i.e. each node's own OS wall clock, with no consensus-level synchronization guarantee: [4](#0-3) 

The lifecycle diagram in the repo documents that any `Invalid` result for a proposed L1 handler tx (`AlreadyIncludedOnL2`, `CancelledOnL2`, `ConsumedOnL1`, `NotFound`, `AlreadyIncludedInProposedBlock`) causes the validating node to *fail the entire block validation*: [5](#0-4) 

This is directly analogous to the reported `CrossL2Inbox.validateMessage` bug class: a party that legitimately controls a limited piece of state (there, an arbitrary/invalid message hash passed to `validateMessage`; here, requesting cancellation of one's own L1→L2 message near the timelock boundary) can make the "is this message/transaction valid" decision diverge between the entity building a block and the entities validating it, causing legitimate transaction inclusion to be non-deterministically blocked. The `apollo_l1_events/tests/flow_test_cancellation.rs` tests explicitly demonstrate this state machine (`Validated` before the timelock, `Invalid(CancelledOnL2)` after it) [6](#0-5) , but rely on a single, artificially-frozen `FakeClock`; they never exercise the real multi-node scenario where each node's `DefaultClock` reading differs due to normal clock skew or processing-time jitter around consensus rounds.

### Impact Explanation
A proposer building a block at time `t_p` may find a given L1 handler transaction still `Pending`/`Validated` (its cancellation timelock has not yet expired w.r.t. `t_p`) and include it in the proposal. A validator processing that same proposal slightly later, at `t_v > t_p`, with the timelock boundary between `t_p` and `t_v`, will compute `is_cancellation_timelock_passed = true` and return `Invalid(CancelledOnL2)`. Per the documented flow, this causes that validator to fail validation of the whole block. If the block is repeatedly re-proposed (by the same or different proposers) with this L1 handler transaction still included, and different validators straddle the same wall-clock boundary at different relative times, the network can experience persistent split decisions on the same proposal — an honest-node divergence that prevents timely commitment of blocks containing that L1 handler transaction, i.e., the network becomes unable to confirm otherwise-valid transactions until the mechanism happens to align across nodes' clocks. This matches the acceptance criteria of "honest-node divergence" / "a network unable to confirm new transactions."

### Likelihood Explanation
Triggering this requires only actions any L1 message sender already performs as part of the standard messaging/cancellation flow: send an L1→L2 message, then call the L1 message-cancellation entry point at a moment engineered so the local cancellation timelock boundary lands inside a live consensus round for the block that would include the message. No special privileges are required beyond being the sender of one's own L1→L2 message (an "L1 message sender," an explicitly in-scope actor). Because block proposal/validation happens continuously and consensus rounds have bounded but non-trivial duration, an attacker with even modest control over timing (and knowledge of the configured `l1_handler_cancellation_timelock_seconds`) can reliably line up the request to straddle a proposal/validation window.

### Recommendation
Base the `CancellationStartedOnL2 -> CancelledOnL2` transition (and any other time-based validity decision consumed during block validation) on a deterministic, consensus-visible value — e.g., the block's own timestamp/height as agreed by the protocol — rather than each node's independently-read wall clock (`Clock::unix_now`). If wall-clock time must be used for UX reasons (e.g., cooldown for proposability), ensure the specific transition that participates in validate/reject decisions is pinned to a value that is identical for the proposer and all validators for a given height, so the validity of a given L1 handler transaction cannot differ between honest nodes evaluating the same proposal.

### Proof of Concept
1. User sends an L1→L2 message `M` via the L1 bridge; the scraper picks it up and it becomes `Pending` in every node's `TransactionManager` records.
2. User calls the L1 cancellation-request function for `M` at L1 block timestamp `T`. This is scraped and applied via `L1EventsProvider::add_events -> TransactionManager::request_cancellation`, moving `M` to `CancellationStartedOnL2` [7](#0-6) .
3. Proposer builds a block at local wall-clock time `t_p` such that `t_p < T + cancellation_timelock`; `validate_tx`/`get_txs` on the proposer's node still treats `M` as includable and proposes it.
4. A validator processes this proposal slightly later at local wall-clock time `t_v >= T + cancellation_timelock`; `TransactionManager::validate_tx` calls `update_time_based_state(t_v, policy)`, transitions `M` to `CancelledOnL2`, and returns `InvalidValidationStatus::CancelledOnL2` [8](#0-7) .
5. Per the documented validation flow, this validator fails validation of the entire block containing `M`, while the proposer (and any validator whose local clock read still falls under `t_p`) considered the block valid — an observable divergence between honest nodes over the validity of the same proposed block, driven entirely by uncoordinated local wall-clock reads rather than deterministic block data.

                    txs.len(),
                    n_txs

                    txs.iter()
                        .map(|tx| format!(
                            "L2 tx hash: {}, L1-L2 msg hash: {}",
                            tx.tx_hash,
                            tx.tx.calc_msg_hash()
                        ))
                        .collect::<Vec<_>>()
                );
                Ok(txs)
            }
            _ => Err(L1EventsProviderError::UnexpectedProviderState {
                expected: ProviderState::Propose,
                found: self.state,
            }),
        }
    }

            _ => Err(L1EventsProviderError::UnexpectedProviderState {
                expected: ProviderState::Validate,
                found: self.state,

        }

    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }
