### Title
Divergent PoX-contract selection between `active_pox_contract` (tip-scoped) and `active_pox_contract_for_cycle` (cycle-scoped) can desynchronize the RPC-served signer/reward set from the consensus-computed signer set - (File: stackslib/src/burnchains/mod.rs)

### Summary
`Burnchain`/`PoxConstants` expose two different functions to determine which PoX contract "governs" a given point in time: a tip-scoped `active_pox_contract(burn_height)` and a cycle-scoped `active_pox_contract_for_cycle(first_block_height, reward_cycle)` [1](#0-0) [2](#0-1) . The code's own comment states that "cycle-scoped callers (signer-set computation, reward-address resolution) must use" the cycle-scoped variant and "only tip-scoped callers (RPC, 'what's live now') use the burn-height variant" [3](#0-2) . This is structurally the same bug class as the reported `questionId` mismatch: two components independently derive an identifier (here, "which PoX contract/reward-set version applies to reward cycle N") that is assumed to be equal but is computed via different formulas, so at boundary conditions they diverge.

### Finding Description
`active_pox_contract_for_cycle`'s PoX-5 branch is derived from `first_pox_waterfall_block` combined with `nakamoto_first_block_of_cycle(reward_cycle)` [4](#0-3) , while `active_pox_contract` (and the reused `static_active_pox_contract` height cascade) makes its PoX-5/4/3/2 determination purely from a raw burn height compared against the corresponding `*_activation_height` fields [1](#0-0) . These are two independently defined boundary functions over the same conceptual axis (reward cycle → active PoX contract), and nothing in the code enforces that `nakamoto_first_block_of_cycle(reward_cycle) >= first_pox_waterfall_block` is equivalent to `reward_cycle_to_block_height(reward_cycle) > pox_5_activation_height` (or the analogous PoX-4/3/2 thresholds).

`stackslib/src/net/api/getstackers.rs::GetStackersResponse::load`, which serves the reward/signer set that external signers use to determine their cycle-N stacking weight, computes the contract version with the tip-scoped function: `burnchain.pox_constants.active_pox_contract(cycle_start_height)` [5](#0-4) . Meanwhile, `get_reward_addresses_in_cycle` in the boot module — the reward-address/reward-set resolution path referenced by the code comment as a "cycle-scoped caller" — explicitly switched to `active_pox_contract_for_cycle` to match "the boundary semantics ... and the signer-set dispatch" [6](#0-5) , and `chainstate/nakamoto/signer_set.rs` is also called out as a cycle-scoped consumer of the cycle-keyed function.

Because `GetStackersResponse::load` did not receive the same update, at any reward cycle straddling a PoX-contract transition boundary (most acutely the PoX-5 "waterfall" transition, whose activation condition is a Nakamoto-tenure-based predicate rather than a fixed burn height), the RPC path can select a different PoX contract version (and therefore a different signer/stacker set/weights) than the path actually used for cycle-scoped signer-set/reward-address computation in consensus-relevant chainstate code.

### Impact Explanation
If the externally-signer-facing stacker set (obtained via this RPC and used by signer software to know its authorized weight for a cycle) disagrees with the internally-computed signer set used to validate block signatures for that same cycle, this reproduces the "wrong questionId format → wrong lookup → false state" bug class as a "signer weight ... from the wrong set" condition explicitly called out as in-scope. This can cause honest signers to sign with a stale/incorrect view of their weight or to fail to recognize they are in the active set, leading to temporary tip disagreement between nodes/signers that trust the RPC-reported set versus nodes applying the correct cycle-scoped set — a High-severity, minority-triggerable divergence bounded to a boundary reward cycle.

### Likelihood Explanation
This requires no attacker privilege — it is a naturally occurring boundary condition at each PoX contract version transition (particularly the PoX-5 waterfall, which is defined by a Nakamoto-tenure predicate rather than a flat burn height, making a mismatch with the flat-height `active_pox_contract` check plausible). Any node/signer querying `getstackers` near such a boundary is minority-triggerable in the sense that only the querying party's local view is affected, but if this view is used to inform signing behavior it can produce real disagreement.

### Recommendation
Update `GetStackersResponse::load` in `stackslib/src/net/api/getstackers.rs` to compute the governing PoX contract using `active_pox_contract_for_cycle(first_block_height, cycle_number)` instead of `active_pox_contract(cycle_start_height)`, so that the RPC-served signer/reward set is guaranteed to agree with the cycle-scoped computation used elsewhere in consensus-critical signer-set and reward-address resolution code.

### Proof of Concept
Not independently executed (index-only review); the divergence is demonstrated structurally: construct `PoxConstants` such that `first_pox_waterfall_block(first_block_height)` for a given reward cycle yields a Nakamoto-tenure-based boundary that does not align with `reward_cycle_to_block_height(reward_cycle) > pox_5_activation_height`. For such a reward cycle, `active_pox_contract_for_cycle` and `active_pox_contract(cycle_start_height)` return different `PoxVersions`, causing `getstackers.rs::GetStackersResponse::load` [7](#0-6)  to fetch a reward set for a different contract version than the one used by `get_reward_addresses_in_cycle` [8](#0-7)  / signer-set computation for the same cycle number.

    /// Returns the PoX contract controlling the signer set and reward set
    /// for `reward_cycle`.
    ///
    /// Cycle-keyed counterpart to `active_pox_contract`.
    ///
    /// All cycle-scoped callers (signer-set computation, reward-address
    /// resolution) must use this; only tip-scoped callers (RPC, "what's
    /// live now") use the burn-height variant.
    ///
    /// The PoX-5 branch is derived from `first_pox_waterfall_block` so that
    /// `active_pox_contract_for_cycle` and the waterfall block-commit /
    /// nakamoto-cycle-start predicates agree on a single boundary.
    ///
    /// For pre-PoX-5 transitions the existing tip-keyed answer is preserved by
    /// evaluating at the cycle's mod-1 (classic reward-phase start) block.
    pub fn active_pox_contract_for_cycle(
        &self,
        first_block_height: u64,
        reward_cycle: u64,
    ) -> &'static str {
        if let Some(wf) = self.first_pox_waterfall_block(first_block_height) {
            if self.nakamoto_first_block_of_cycle(first_block_height, reward_cycle) >= wf {
                return POX_5_NAME;
            }
        }
        // PoX-5 already ruled out, now cascade through earlier
        // activations using a tip-height inside the cycle.
        let h = self.reward_cycle_to_block_height(first_block_height, reward_cycle);
        if h > u64::from(self.pox_4_activation_height) {
            POX_4_NAME
        } else if h > u64::from(self.pox_3_activation_height) {
            POX_3_NAME
        } else if h > u64::from(self.v1_unlock_height) {
            POX_2_NAME
        } else {
            POX_1_NAME
        }
    }
