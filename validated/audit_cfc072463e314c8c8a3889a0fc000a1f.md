## Analysis

The reported Uniswap issue is a missing-slippage-guard bug class: a liquidity-providing call accepts any resulting output ratio because minimum-amount parameters are hardcoded to `0`. The equivalent construct in `java-tron` is the legacy Bancor-style **Exchange** actuator family (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`), which implements an AMM-like `firstTokenBalance`/`secondTokenBalance` pool with `inject`, `withdraw`, and `transaction` (trade) operations reachable from any broadcast transaction.

`ExchangeTransactionContract`, the *trade* operation, explicitly carries an `expected` field that is checked in `ExchangeTransactionActuator.doValidate()`, rejecting the transaction if the computed `anotherTokenQuant` falls below the caller's specified minimum. [1](#0-0) 

However, the two liquidity-management operations, `ExchangeInjectContract` and `ExchangeWithdrawContract`, carry no equivalent slippage/minimum field at all — only `owner_address`, `exchange_id`, `token_id`, `quant`. [2](#0-1) 

`ExchangeInjectActuator.doValidate()`/`execute()` derives `anotherTokenQuant` purely from the exchange's *current* on-chain ratio at execution time (`secondTokenBalance * tokenQuant / firstTokenBalance`), with no bound on how much of the paired token the caller is willing to part with. [3](#0-2) 

`ExchangeWithdrawActuator.doValidate()`/`execute()` similarly derives the paired-token amount to be paid out purely from the current ratio, with no minimum-received guard for the withdrawing party. [4](#0-3) 

Both actuators do restrict the caller to `exchangeCapsule.getCreatorAddress()` (the account that originally created that specific token pair), so only that single account can inject/withdraw for a given exchange pool. [5](#0-4) [6](#0-5) 

This ownership check, however, is not a "privileged" node/admin/keyholder role in the excluded sense — any ordinary account can create an exchange pool (`ExchangeCreateContract`) and thereby become its sole liquidity manager, exactly analogous to being the LP owner in a Uniswap-style pool. The actor who suffers the loss is this ordinary account, and the attacker is any other anonymous account broadcasting `ExchangeTransactionContract` trades against the same pool — a fully unprivileged path.

### Title
Missing slippage/minimum-amount protection on `ExchangeInjectContract` and `ExchangeWithdrawContract` allows sandwich-style value extraction from Exchange liquidity operations - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The `Exchange` (Bancor-style AMM) subsystem in java-tron lets the pool creator inject or withdraw liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Unlike the trade operation (`ExchangeTransactionContract`), which carries an explicit `expected` minimum-output field enforced in `ExchangeTransactionActuator.doValidate()`, neither the inject nor the withdraw contract carries any minimum/maximum bound on the counter-token amount computed from the pool's live ratio. This is the direct analog of the reported Uniswap `addLiquidity()` issue where `amountAMin`/`amountBMin` are hardcoded to `0`.

### Finding Description
`ExchangeInjectActuator` computes the counter-token amount to pull from the creator's balance strictly from the exchange's current ratio at execution time:
```
anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)...
``` [7](#0-6) 

`ExchangeWithdrawActuator` computes the counter-token amount to pay out to the creator the same way: [4](#0-3) 

Neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` defines a caller-supplied bound field to compare against this computed value, unlike `ExchangeTransactionContract.expected`, which is validated against the trade output. [8](#0-7) 

Because Tron transactions are broadcast and sit in the pending pool before block inclusion, an attacker can observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction and submit `ExchangeTransactionContract` trades immediately before (and after) it to shift `firstTokenBalance`/`secondTokenBalance`, sandwiching the creator's inject/withdraw so that it executes against a manipulated ratio.

### Impact Explanation
For `Inject`: the creator can be forced to deposit more of the counter token than the fair-value ratio at signing time, transferring value to the attacker who reverses the price manipulation afterward.
For `Withdraw`: the creator can be forced to receive less of the counter token than fair value, again transferring value to the attacker.
This results in asset/accounting corruption for the exchange creator, reachable purely through normal broadcast transactions with no special privilege required by the attacker.

### Likelihood Explanation
Any account can create an `Exchange` and any other account can trade against it via `ExchangeTransactionContract`. Sandwiching a pending inject/withdraw transaction only requires observing it in the transaction pool and submitting ordinary trade transactions with the appropriate timestamp/fee/ordering — the classic MEV sandwich setup, with no need for elevated privileges, key compromise, or consensus-level access.

### Recommendation
Add explicit minimum/maximum bound fields to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and enforce them in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the ratio-derived counter-token amount falls outside the caller-specified bound.

### Proof of Concept
1. Creator C owns Exchange E with pool `(firstTokenBalance, secondTokenBalance)`.
2. C broadcasts `ExchangeInjectContract{exchange_id: E, token_id: first, quant: Q}` expecting to pay `secondTokenBalance*Q/firstTokenBalance` of the second token.
3. Attacker A observes C's pending transaction and broadcasts an `ExchangeTransactionContract` trade that shifts the pool ratio unfavorably for C, ordered to execute just before C's inject transaction (and reverses it just after).
4. C's inject executes against the manipulated ratio in `ExchangeInjectActuator.execute()`, causing C to deposit more second-token than intended, with no validation rejecting the unfavorable ratio, since no minimum/maximum field exists on `ExchangeInjectContract`. [9](#0-8)
