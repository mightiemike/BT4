### Title
Underflow-safe check but partial-deduction across split "unlock" and "lock" delegated-resource pools in `UnDelegateResourceActuator` can push a resource pool balance negative - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.validate()` validates an un-delegation request against the **sum** of two separate delegated-resource balance pools (`unlockResourceCapsule` and `lockResourceCapsule`), but `execute()` only ever deducts the requested amount from the "unlock" pool (`unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` / `addFrozenBalanceForEnergy(-unDelegateBalance, 0)`). This mirrors the reported bug class: a combined-balance check followed by a single-balance deduction.

### Finding Description
In `validate()`, the delegated balance available to satisfy an `UnDelegateResourceContract` is computed as the sum of two independent `DelegatedResourceCapsule` records — the "unlock" record and, if expired, the "lock" record: [1](#0-0) 

```java
case BANDWIDTH: {
  long delegateBalance = 0;
  if (unlockResourceCapsule != null) {
    delegateBalance += unlockResourceCapsule.getFrozenBalanceForBandwidth();
  }
  if (lockResourceCapsule != null
      && lockResourceCapsule.getExpireTimeForBandwidth() < now) {
    delegateBalance += lockResourceCapsule.getFrozenBalanceForBandwidth();
  }
  if (delegateBalance < unDelegateBalance) {
    throw new ContractValidateException(...);
  }
}
```

This is exactly the same structural pattern as the `withdrawInterest` bug: `require(amount <= (poolA + poolB))`. In `execute()`, however, only the "unlock" resource key (`key = createDbKeyV2(ownerAddress, receiverAddress, false)`) is fetched and decremented: [2](#0-1) 

Before that decrement, `delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, ...)` is called, which is presumably intended to migrate the expired "lock" pool's balance into the "unlock" pool so that the later single-pool subtraction is consistent with the combined check performed in `validate()`. I was not able to fully trace `DelegatedResourceStore.unLockExpireResource(...)` in this pass (tool budget exhausted before reading its body), so I cannot conclusively prove or disprove whether that migration step fully reconciles the two pools for every edge case (e.g., partial expiration timing differences between `validate()`'s `now` and `execute()`'s `dynamicStore.getLatestBlockHeaderTimestamp()`, or ordering/atomicity issues between the two calls within the same transaction).

### Impact Explanation
If `unLockExpireResource` does not fully merge the expired "lock" balance into "unlock" before the subtraction (e.g., due to timing skew between validate-time `now` and execute-time timestamp, or because it doesn't move the full amount), `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` could attempt to subtract more than the unlock pool holds. Depending on whether that setter enforces non-negativity, this either throws (unhandled exception mid-actuator-execution -> transaction/block processing exception, a DoS risk) or silently drives the delegated-resource balance negative, corrupting resource accounting (potential unauthorized resource/asset accounting corruption). This is reachable by any account via a standard `UnDelegateResourceContract` broadcast transaction — no privileged role required.

### Likelihood Explanation
Low-to-moderate confidence overall: the vulnerability class (combined-balance check, single-pool deduction) is structurally present and directly analogous to the reported issue, but I could not verify within the available searches whether `unLockExpireResource` neutralizes the discrepancy in all cases, nor whether `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` clamp at zero. Given this uncertainty, I cannot assert this as a confirmed, exploitable underflow with full root-cause proof — additional review of `DelegatedResourceStore.unLockExpireResource` and `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` (which I was unable to read before the iteration budget ran out) is required to confirm exploitability.

### Recommendation
Have a Devin session read `chainbase/src/main/java/org/tron/core/store/DelegatedResourceStore.java` (`unLockExpireResource`) and `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceCapsule.java` (`addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`) to confirm whether the lock→unlock migration is exact and atomic with the validate-time expiry check, and whether negative balances are prevented. If a gap exists, deduct sequentially from the unlock pool first and only then from the lock pool (mirroring the report's suggested fix), rather than relying on an implicit merge step.

### Proof of Concept
Not confirmed — requires verifying `unLockExpireResource`'s exact semantics, which I could not complete in this session. A concrete PoC would involve delegating both a locked and an unlocked resource amount, letting the lock expire, then submitting an `UnDelegateResourceContract` for an amount exceeding the unlock pool alone but within the combined total, observing whether the transaction throws or corrupts the resource balance.
