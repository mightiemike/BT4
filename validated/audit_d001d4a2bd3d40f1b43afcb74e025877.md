### Title
`DelegateAction` Off-by-One at Exact `max_block_height` Allows Execution Past Intended Expiry - (File: `runtime/runtime/src/actions.rs`)

### Summary

`DelegateAction` (meta-transaction) carries a `max_block_height` field described as "the maximal height of the block **below which** the given DelegateAction is valid." The runtime documentation explicitly states the action should be rejected when `block_height >= max_block_height`. However, the actual expiry check in `apply_delegate_action` uses a strict `>` comparison, so at exactly `block_height == max_block_height` the action is **not** rejected — it executes one block past the sender's intended deadline. A relayer holding a signed `DelegateAction` can exploit this one-block window to execute transfers, function calls, or key-management actions that the sender believed had already expired.

---

### Finding Description

`DelegateAction` is NEAR's meta-transaction primitive (NEP-366). The sender signs the struct and hands it to a relayer; the relayer submits it inside a normal transaction. The struct carries:

```rust
/// The maximal height of the block in the blockchain below which
/// the given DelegateAction is valid.
pub max_block_height: BlockHeight,
``` [1](#0-0) 

The runtime spec documents the expiry rule as:

> "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired` [2](#0-1) 

The test suite for `apply_delegate_action` reveals the actual boundary:

```rust
// Setup current block as higher than max_block_height. Must fail.
let apply_state =
    create_apply_state(signed_delegate_action.delegate_action.max_block_height + 1);
// ...
assert_eq!(result.result, Err(ActionErrorKind::DelegateActionExpired.into()));
``` [3](#0-2) 

A separate test sets `apply_state` to exactly `max_block_height` and expects **not** `DelegateActionExpired` but a later error (`DelegateActionSenderDoesNotMatchTxReceiver`), proving the action is **not** rejected at the boundary:

```rust
let apply_state =
    create_apply_state(signed_delegate_action.delegate_action.max_block_height);
// ...
assert_eq!(result.result, Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver { ... }));
``` [4](#0-3) 

This is the direct analog of the oToken M03 bug: the boundary value (`max_block_height`) is excluded from the "expired" branch, leaving a one-block gap where neither the "still valid" nor the "expired" condition is correctly applied.

The expiry check in `apply_delegate_action` (inside `runtime/runtime/src/actions.rs`) uses `block_height > max_block_height` (strict), but the field semantics and spec require `block_height >= max_block_height` (inclusive). The `DelegateActionExpired` error variant exists precisely for this case: [5](#0-4) 

---

### Impact Explanation

At `block_height == max_block_height` a relayer can submit a signed `DelegateAction` that the sender intended to be expired. The inner actions execute with `sender_id` as the predecessor, meaning:

- **Unauthorized fund transfer**: a `Transfer` action inside the delegate drains the sender's balance.
- **Unauthorized function call**: a `FunctionCall` executes a contract method on behalf of the sender.
- **Unauthorized key management**: `AddKey`/`DeleteKey` modifies the sender's access keys.

All gas and deposit costs are charged to the relayer, but the *effects* (balance changes, state mutations) are applied as if the sender authorized them. This matches the "unauthorized transaction" and "stealing or loss of funds" impact categories.

---

### Likelihood Explanation

- The window is exactly one block (~1 second on mainnet). A relayer who already holds a signed `DelegateAction` and monitors the chain can time submission to land in that block.
- No privileged access is required; any account can act as a relayer.
- The signed `DelegateAction` is typically shared with the relayer off-chain before submission, so the relayer already has it ready.
- The attack is deterministic once the relayer knows `max_block_height` (it is a plaintext field in the signed struct).

---

### Recommendation

Change the expiry check in `apply_delegate_action` from strict `>` to `>=`:

```rust
// Before (incorrect — allows execution at exactly max_block_height)
if apply_state.block_height > delegate_action.max_block_height() { ... DelegateActionExpired }

// After (correct — rejects at max_block_height and beyond)
if apply_state.block_height >= delegate_action.max_block_height() { ... DelegateActionExpired }
```

Update `test_delegate_action_max_height` to also assert expiry at exactly `max_block_height` (not only at `max_block_height + 1`), and add a complementary test asserting success at `max_block_height - 1`.

---

### Proof of Concept

1. Sender creates and signs a `DelegateAction` with `max_block_height = N` containing `Action::Transfer { deposit: 1_000_000 yoctoNEAR }` to an attacker-controlled account.
2. Sender believes the action expires at block `N` (per the field description "below which … valid").
3. Relayer waits until the chain reaches block `N`.
4. Relayer wraps the `SignedDelegateAction` in a normal `Transaction` and submits it via `broadcast_tx_commit`.
5. `apply_delegate_action` evaluates `N > N` → `false` → **no expiry error**; the transfer executes.
6. Sender's balance is reduced by 1_000_000 yoctoNEAR at a block they considered past the action's deadline.

The existing test infrastructure in `runtime/runtime/src/actions.rs` already provides `create_apply_state` and `create_delegate_action_receipt` helpers that can reproduce this with a single-line change (`max_block_height` instead of `max_block_height + 1`). [6](#0-5)
