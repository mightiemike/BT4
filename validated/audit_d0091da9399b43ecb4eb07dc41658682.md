## Title
Replay-verification skips checkpoint-hash validation, allowing a divergent state root to be accepted as a valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` recorded on-chain/in the archive. The function validates status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly and admittedly skips validating the state-checkpoint hash fields (state/hot-state checkpoint hash and `position_state_checkpoint_hash`) that are part of `TransactionInfo` and bind the transaction to a specific state root.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks four invariants between a locally computed `TransactionOutput` and the authenticated `txn_info: &TransactionInfo`: execution status, gas used, write-set hash vs `state_change_hash()`, and event root hash. It then contains a self-documenting `TODO` acknowledging the gap: [2](#0-1)  stating that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This is the exact structural analog of the reported bug class: a proof/commitment-binding check that is supposed to tie a locally-derived result to a specific committed context (here, the `TransactionInfo`'s state-checkpoint hash, which anchors the transaction to a specific state root/version) is missing, letting a caller present/accept a result that is only partially validated against the authoritative record. `TransactionInfo` carries separate hashes for `transaction_hash`, `event_root_hash`, `state_change_hash`, and the state-checkpoint hash(es); only the first three are checked here.

Both consumers of this function — `replay_on_archive.rs` and `aptos_debugger.rs` — rely on it as the pass/fail gate for whether locally replayed execution matches the authenticated ledger data. Because the state-checkpoint hash (and, per the TODO, the not-yet-enabled `position_state_checkpoint_hash` under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, referenced in `types/src/on_chain_config/aptos_features.rs`) is never compared, a divergence purely in the resulting state root (e.g., a resource/account state incorrectly computed, or a hot-state/position-state root that differs from the archived value) is invisible to this check even though the write-set hash and events match.

### Impact Explanation
This breaks the state-commitment/proof-integrity guarantee that "committed state that differs from the correct VM result... must be detectable," specifically for the replay/verification tooling relied upon to detect execution/state divergence (e.g., during hard-fork or upgrade validation, replay-verify pipelines, and debugging state-root mismatches). A bug that corrupts only the state-checkpoint/state-root computation (while leaving the per-transaction write-set hash and events intact — which is entirely possible since checkpoint hash is a separate, aggregate value computed from the whole state tree, not from the per-txn write set) would go undetected by `ensure_match_transaction_info`, giving false confidence that a replay is correct. This is directly relevant to the "trading-native"/position-state feature referenced in the TODO, where the authenticated position state root could silently diverge from local execution results without failing verification.

### Likelihood Explanation
This is not a hypothetical: the code comment is an explicit, current acknowledgment by the authors that this exact scenario ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution") is possible today. The gap is unconditional in current code (it applies regardless of feature flags) — the TODO says the checkpoint hashes should be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the check needs to be added even for the current state-checkpoint hash validation, not just the new position-state-checkpoint hash. Since `ensure_match_transaction_info` is the sole state-matching gate in the identified call sites, any state-root divergence bug elsewhere in execution would not be caught by these tools.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s computed state-checkpoint hash (and, once available, the position/hot-state checkpoint hash) against `txn_info.state_checkpoint_hash()` (and the corresponding `position_state_checkpoint_hash` accessor), erroring out on mismatch just as is done for `state_change_hash` and `event_root_hash`. This check must be wired in prior to/independently of enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, per the existing TODO's own guidance, since `TransactionInfo` already carries these fields on-chain, and the tooling in `replay_on_archive.rs`/`aptos_debugger.rs` should not certify a replay unless all authenticated commitment fields are checked.

### Proof of Concept
Direct exploitation requires triggering a real state-root-only divergence bug elsewhere in execution (e.g., in state summary/state checkpoint hash computation) and running `replay_on_archive` or the debugger's verification path over the affected version range; because `ensure_match_transaction_info` never compares the checkpoint hash fields, the tool will report success despite an actual state-root mismatch. I could not fully trace an independent local root-cause bug that produces a wrong checkpoint hash while producing an identical write-set hash (that would require a separate, unconfirmed defect in state summary computation), so this finding is reported strictly as the proven, admitted integrity gap in the verification comparator itself — the missing check is confirmed by direct code inspection, not by demonstrating a triggering state-root bug.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
```
