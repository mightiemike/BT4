## Analysis

The report's underlying bug class is: **a fee/gas cost model that charges based on the wrong metric (or doesn't charge for a metric at all), letting an attacker's transaction consume real resources far in excess of what it pays for.** In `nearcore`, the reachable analog is in **WASM contract preparation/instantiation gas metering**, not in the JSON-RPC/secrets part of the report (which is operator-only and out of scope).

`nearcore`'s gas-cost estimator explicitly documents that per-call WASM module instantiation cost for globals, active data segments, and active element segments scales with their count but is **not charged in the protocol's gas schedule**: [1](#0-0) 

These are measured via `measure_instantiation_overhead`, which shows the omitted cost is tied to *instantiation* (i.e., every `FunctionCall`, not just deployment): [2](#0-1) 

The only gas charged for loading/using a contract on each call is `contract_loading_base`/`contract_loading_bytes`, which scale with total code size — not with the number of globals, active data segments, or active element segments: [3](#0-2) 

Meanwhile, the protocol's own validation limits permit up to 1,000,000 globals, 100,000 data segments, and large element-segment counts in a deployed module: [4](#0-3) 

Test-contract generators for crafting such adversarial modules already exist in-repo: [5](#0-4) 

### Title
Gas metering does not charge for WASM module instantiation cost of globals/data-segments/element-segments, enabling a gas-underpricing (fee bypass) DoS on `FunctionCall` - (File: `runtime/runtime-params-estimator/src/vm_estimator.rs`, `core/parameters/src/cost.rs`)

### Summary
Analogous to the `FeeOracleV1.feeFor()` bug (charging for the wrong cost metric, causing a mismatch between the fee charged and the real resource consumed), NEAR's gas schedule for `FunctionCall` charges `contract_loading_base`/`contract_loading_bytes` proportional to total contract code size, but does not charge anything proportional to the number of globals, active data segments, or active element segments a WASM module declares. Instantiating a module re-initializes all of these on every call. A contract deployed once with a large number of globals/data-segments/element-segments (within the protocol's own stated limits of up to 1,000,000 globals / 100,000 data segments) can be invoked cheaply (paying only the flat `contract_loading_*` + trivial instruction gas) while making every chunk producer perform disproportionate real CPU work to instantiate it on each call.

### Finding Description
`nearcore`'s own runtime-params-estimator documents this gap explicitly: `AdversarialLoadManyGlobals`, `AdversarialLoadManyDataSegments`, and `AdversarialLoadManyElementSegments` are labeled as exposing "unbounded per-call ... re-initialization/initialization work not covered by gas" [1](#0-0) . The measurement harness `measure_instantiation_overhead` confirms the cost is incurred on every `prepare`+`run` (i.e., every `FunctionCall`), not just at deployment [2](#0-1) . The actual per-call gas cost model only accounts for `wasm_contract_loading_base`/`wasm_contract_loading_bytes` (scaling with total code size) and per-instruction `wasm_regular_op_cost` [6](#0-5) ; none of these scale with the number of globals, data segments, or element segments. Yet the protocol's own contract-validation rules allow modules with up to 1,000,000 globals and 100,000 data segments [4](#0-3) , and test-contract builders for such modules already exist in the codebase [5](#0-4) .

### Impact Explanation
Because instantiation cost of globals/data-segments/element-segments is not gas-metered, an attacker can deploy (once, paying deployment-time cost) a contract crafted with a very large number of these constructs, then submit ordinary, cheap `FunctionCall` transactions that repeatedly force every validator applying the chunk to re-initialize the oversized module. This is a gas/fee bypass: the signer pays gas commensurate with code size and instruction count, not with the real CPU cost imposed on the network. At scale this can push chunk application time above the block-time budget for all honest validators uniformly, i.e., a transaction-triggered slowdown/halt risk stemming directly from underpriced gas — the same root-cause pattern as the audited `FeeOracleV1.feeFor()` bug (a cost function that omits a real cost dimension, resulting in systematic underpricing/overpricing of a resource).

### Likelihood Explanation
Reachable by any unprivileged account: `DeployContractAction` (subject only to existing WASM validation limits which already permit large global/data-segment counts) followed by ordinary `FunctionCallAction`s. No validator, network, or operator privilege is required — only a single transaction/contract-call sequence from a standard signer.

### Recommendation
Introduce explicit `ExtCosts`/deployment-time charges proportional to the number of globals, active data segments, and active element segments declared by a module (charged either at deployment as an amortized "worst-case instantiation" fee, or per-call proportional to counts), calibrated via `runtime-params-estimator`'s existing `AdversarialLoadManyGlobals`/`AdversarialLoadManyDataSegments`/`AdversarialLoadManyElementSegments` measurements so the on-chain gas price for a `FunctionCall` reflects the true instantiation cost, closing the underpricing gap the estimator already flags as "not covered by gas."

### Proof of Concept
1. Deploy a contract generated via a helper equivalent to `many_data_segments_contract(100_000)` (or a similarly large `contract_with_num_globals`/`many_element_segments_contract`), staying within the documented protocol limits [4](#0-3) .
2. Repeatedly call its exported `main` function via ordinary `FunctionCall` transactions.
3. Compare gas charged per call (dominated by `contract_loading_base`/`contract_loading_bytes` and negligible instruction cost) against the measured real instantiation time via the estimator's `measure_instantiation_overhead` harness [7](#0-6)  to demonstrate the gap between paid gas and real CPU cost imposed on every applying node.

/// Warm the compile cache, then measure N invocations (instantiation + trivial execution).
/// The function body is a bare `end`, so execution cost is negligible.
fn measure_instantiation_overhead(
    metric: GasMetric,
    vm_kind: VMKind,
    contract_bytes: &[u8],
) -> GasCost {
    let config_store = RuntimeConfigStore::new(None);
    let mut config = config_store.get_config(PROTOCOL_VERSION).wasm_config.as_ref().clone();
    config.vm_kind = vm_kind;
    let config = Arc::new(config);
    let fees = Arc::new(RuntimeFeesConfig::test());
    let code = ContractCode::new(contract_bytes.to_vec(), None);
    let cache = MockContractRuntimeCache::default();
    let mut fake_external = near_vm_runner::logic::mocks::mock_external::MockedExternal::with_code(
        code.clone_for_tests(),
    );

    let mut run_once = || {
        let context = create_context(vec![]);
        let gas_counter = context.make_gas_counter(&config);
        vm_kind
            .runtime(config.clone())
            .unwrap()
            .prepare(&fake_external, Some(&cache), gas_counter, "main")
            .run(&mut fake_external, &context, Arc::clone(&fees))
            .expect("fatal_error")
    };

    // Warm: compiles and caches the module; subsequent calls only instantiate + execute.
    run_once();

    let n = 10_usize;
    let start = GasCost::measure(metric);
    for _ in 0..n {
        run_once();
    }
    start.elapsed() / n as u64
}

/// Many tiny active data segments, each writing 1 byte to memory offset 0.
pub fn many_data_segments_contract(num_segments: u32) -> Vec<u8> {
    let mut module = Module::new();
    let mut types = TypeSection::new();
    types.ty().function([], []);
    module.section(&types);
    let mut funcs = FunctionSection::new();
    funcs.function(0);
    module.section(&funcs);
    let mut memories = MemorySection::new();
    memories.memory(MemoryType {
        minimum: 1,
        maximum: None,
        memory64: false,
        shared: false,
        page_size_log2: None,
    });
    module.section(&memories);
    let mut exports = ExportSection::new();
    exports.export("main", ExportKind::Func, 0);
    module.section(&exports);
    let mut data = DataSection::new();
    for i in 0..num_segments {
        data.active(0, &ConstExpr::i32_const(0), [i as u8]);
    }
    module.section(&data);
    let mut code = CodeSection::new();
    let mut f = Function::new([]);
    f.instruction(&Instruction::End);
    code.function(&f);
    module.section(&code);
    module.finish()
}

/// Many active element segments, each writing function 0 into table slot 0.
pub fn many_element_segments_contract(num_segments: u32) -> Vec<u8> {
    let mut module = Module::new();
    let mut types = TypeSection::new();
    types.ty().function([], []);
    module.section(&types);
    let mut funcs = FunctionSection::new();
    funcs.function(0);
    module.section(&funcs);
    let mut tables = TableSection::new();
    tables.table(TableType {
        element_type: RefType::FUNCREF,
        minimum: 1,
        maximum: Some(1),
        table64: false,
        shared: false,
    });
    module.section(&tables);
    let mut exports = ExportSection::new();
    exports.export("main", ExportKind::Func, 0);
    module.section(&exports);
    let mut elements = ElementSection::new();
    for _ in 0..num_segments {
        elements.active(
            Some(0),
            &ConstExpr::i32_const(0),
            Elements::Functions(Cow::Borrowed(&[0u32])),
        );
    }
    module.section(&elements);
    let mut code = CodeSection::new();
    let mut f = Function::new([]);
    f.instruction(&Instruction::End);
    code.function(&f);
    module.section(&code);
    module.finish()
}
