### Title
Fixed 5% slippage on spot-quote-based auto-swaps allows sandwich extraction of user deposit/refund value - (File: x/uexecutor/keeper/execute_inbound_gas.go, execute_inbound_gas_and_payload.go, outbound.go)

### Summary
Push Chain's GAS-type inbound deposits, GAS_AND_PAYLOAD deposits, and outbound gas-fee refunds all convert a PRC20 gas token into PC native token via an atomic on-chain swap. The minimum output is derived from a single spot quote fetched from the UniversalCore/Uniswap V3 Quoter immediately before the swap, with a hardcoded ±5% slippage bound, rather than a TWAP or user/market-supplied bound. This is conceptually the same root cause flagged in the referenced report: the protocol executes a large, price-sensitive rebalancing action (the swap) using a naive/immediate pricing mechanism instead of a manipulation-resistant or bounded one, exposing depositors to avoidable value loss from adverse pricing around the execution.

### Finding Description
`ExecuteInboundGas` fetches `quote` via `GetSwapQuote` (a static, single-block Uniswap V3 QuoterV2 call) and computes `minPCOut = quote * 95 / 100`, then immediately calls `CallPRC20DepositAutoSwap` with that bound [5](#0-4) . The same pattern recurs verbatim in `gasAndPayloadDepositAutoSwap` [6](#0-5)  and in `applyGasRefund`'s swap-refund path [3](#0-2) . This whole flow — quote, compute bound, execute swap — runs inside a single Push Chain state transition triggered by `MsgVoteInbound`/`MsgVoteOutbound` finalization [1](#0-0) , i.e., inside one block, using the pool's current spot price.

Because the vote-finalizing transaction (the last validator vote that reaches quorum) is a normal, publicly-observable transaction sitting in the mempool before inclusion, and the swap it triggers uses only the spot price at execution time with a generous fixed 5% tolerance, an attacker with no privileged role can:
1. Watch the mempool/network for the validator vote transaction that will finalize a large GAS/GAS_AND_PAYLOAD inbound deposit or an outbound gas refund.
2. Front-run it with a large trade on the underlying UniswapV3 pool (gas token / WPC) to push the spot price against the pending swap direction.
3. Let the protocol's swap execute at the manipulated price, within the wide 5% band, extracting value from the depositor.
4. Back-run to restore the pool price, closing out with profit.

This mirrors the report's core issue: "immediately re-entering/exiting positions based on live price without protecting against short-term price movement causes avoidable slippage losses that are borne by the users, not the protocol." The report's proposed fix (marginal, TWAP-based, or delayed re-entry) applies directly here.

### Impact Explanation
Depositors making GAS or GAS_AND_PAYLOAD inbound transfers, and users receiving excess-gas refunds from outbounds, can have a meaningful percentage of their swapped value siphoned off by a sandwich attacker, up to the full 5% slippage tolerance per event (potentially compounded if the underlying pool has thin liquidity, since the spot price itself is easily moved). This is a fund-loss issue for ordinary users acting through the default transaction paths (deposit, outbound gas-fee refund), matching the in-scope impact category "corruption of ... gas fee accounting, refund accounting ... PRC20 or native asset accounting" and "unauthorized ... state transitions in universal execution flows" insofar as the executed swap price is not the fair/expected price. Severity is bounded by the pool's actual liquidity and the 5% cap, so it is not unbounded drain, but it is a systematic, repeatable value leak reachable by any unprivileged actor who can trade on the relevant DEX pool and observe the Push Chain mempool.

### Likelihood Explanation
High reachability: GAS-type inbounds and outbound gas refunds are part of the default/expected transaction flow, not requiring any privileged action. The attack does not require validator collusion, key compromise, or governance abuse — only participation in a public liquidity pool and observation of Push Chain's public mempool for the specific finalizing `MsgVoteInbound`/`MsgVoteOutbound` transaction, both classic and well-established MEV techniques. The main limiting factor is the liquidity depth of the specific gas-token/WPC pool and the attacker's capital, not any protocol-level defense, since the code has no TWAP, no per-call minimum-output override, and no cooldown/randomization protecting the spot quote.

### Recommendation
- Replace the single-block spot `GetSwapQuote` with a time-weighted average price (TWAP) over a meaningful window before computing `minPCOut`.
- Tighten the slippage tolerance from a flat 5% to a much smaller, configurable bound, or make it a function of pool depth/volatility.
- Consider decoupling execution from ballot finalization (similar to the report's "separate exit and re-entry" recommendation) — e.g., queue the swap and execute it in a subsequent block using an oracle-derived or TWAP price rather than executing atomically at spot price the moment quorum is reached.
- Add a circuit breaker that falls back to the no-swap PRC20 deposit path (already implemented for the failure case) whenever the spot price deviates significantly from the TWAP, protecting users from being force-swapped into a manipulated price.

### Proof of Concept
1. Attacker monitors Push Chain's mempool for the `MsgVoteInbound` transaction that will bring a large `TxType_GAS` inbound to quorum (the last of the required validator votes).
2. Immediately before it lands, attacker submits a transaction on the relevant Uniswap V3 pool (gas-token/WPC) that pushes the spot price down for the gas token.
3. The finalizing vote transaction executes `ExecuteInboundGas`, which calls `GetSwapQuote` and computes `minPCOut = quote*95/100` off the now-manipulated spot price [7](#0-6) , then calls `CallPRC20DepositAutoSwap`, executing the deposit's swap at the depressed price, within the 5% band.
4. Attacker immediately reverses their pool trade, restoring the price and realizing a profit equal to the price impact captured, extracted from the value that should have gone to the depositor's UEA.
5. The identical mechanic applies to `gasAndPayloadDepositAutoSwap` and to `applyGasRefund`'s swap-refund branch for outbound observations, multiplying the attack surface across all three call sites.
