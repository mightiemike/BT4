### Title
Unguarded `assert` on `totalEnergyWeight` allows divide-by-zero (`ArithmeticException`) in `RepositoryImpl#calculateGlobalEnergyLimit` when hardened resource calculation divides by a zero global energy weight - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The Cabal report describes a class of bug where a state variable used as a divisor (LST supply) can legitimately reach zero after a valid user action (burning the entire supply during `initiate_unstake`), and a downstream function performs `numerator / denominator` without checking for `denominator == 0`, causing every future call to permanently revert. The analogous condition in java-tron is `RepositoryImpl#calculateGlobalEnergyLimit`, which divides by the network-wide `totalEnergyWeight` counter and relies solely on a Java `assert` statement to protect against a zero divisor — `assert` statements are no-ops unless the JVM is started with `-ea`, which production nodes do not use.

### Finding Description
`totalEnergyWeight` is a dynamic property that is incremented on `FreezeBalanceV2`/`FreezeBalance` and decremented on `UnfreezeBalanceV2`/`UnfreezeBalance`, exactly mirroring how the Cabal LST supply is incremented/decremented on stake/unstake: [1](#0-0) 

The energy limit for any account interacting with the TVM is computed by `RepositoryImpl#calculateGlobalEnergyLimit`, used inside the actuator/VM execution path: [2](#0-1) 

This method guards `totalEnergyWeight` only with `assert totalEnergyWeight > 0;`, which is compiled out and inert in a normally-run production JVM (no `-ea` flag). If `hardenResourceCalculation()` is enabled (`VMConfig.allowHardenResourceCalculation()`), the method then executes:
```
BigInteger.valueOf(energyWeight)
    .multiply(BigInteger.valueOf(totalEnergyLimit))
    .divide(BigInteger.valueOf(totalEnergyWeight))
    .longValueExact();
```
`BigInteger.divide` throws `ArithmeticException: BigInteger divide by zero` when `totalEnergyWeight == 0`.

By contrast, the sibling implementation `EnergyProcessor#calculateGlobalEnergyLimit` explicitly checks for this condition before falling back on `assert`: [3](#0-2) 

and its V2 variant checks unconditionally: [4](#0-3) 

`RepositoryImpl#calculateGlobalEnergyLimit` has neither the `allowNewReward()`/`totalEnergyWeight <= 0` early-return present in `EnergyProcessor`, nor the unconditional `totalEnergyWeight == 0` check present in the V2 method — it only has the dead `assert`. This is the same root-cause pattern as the Cabal report: a divisor that is expected to “never” be zero by convention, guarded only by an assumption instead of an explicit check, in a path that is reachable through normal, unprivileged user operations (freeze/unfreeze energy).

### Impact Explanation
If `totalEnergyWeight` reaches zero — e.g., in a scenario where the accounts holding frozen-for-energy balance across the network fully unfreeze it (via `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceActuator`, both unprivileged, user-callable actuators) — then any subsequent smart-contract call that needs to compute an account's energy limit through `RepositoryImpl#calculateGlobalEnergyLimit` (i.e., essentially any TVM contract invocation, since this determines how much energy the caller can consume) will throw an uncaught `ArithmeticException` when `hardenResourceCalculation` is active. This differs from a graceful `ContractValidateException`/`ContractExeException`; it is a raw runtime exception originating deep in transaction/energy accounting used during deterministic TVM execution, i.e. during block application. An uncaught exception at this layer risks aborting transaction/block processing unpredictably across nodes (since every node independently re-executes the same transaction) — a potential denial-of-service / node-crash / consensus-relevant condition, analogous to the "last holder can't exit" DoS described in the report (permanent inability to execute a legitimate, previously-working operation once the divisor hits zero).

### Likelihood Explanation
Reaching a state where the entire network's `totalEnergyWeight` is exactly zero is unlikely on a live, populous mainnet (it requires essentially no account anywhere to have energy frozen), so the practical likelihood on Tron mainnet is low. However, on smaller/private/permissioned java-tron-based networks (a common deployment model), or in early-cycle situations, or if `totalEnergyWeight` accounting has any off-by-one/rounding edge cases that let it dip to zero even transiently, the condition is fully reachable via normal, unprivileged actuator calls (freeze/unfreeze), matching the "in-scope: resource and reward accounting" category. The bug is a structural, silent reliance on a disabled `assert`, which is a code-quality/security defect independent of how likely the network-wide zero state is.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl#calculateGlobalEnergyLimit` with an explicit runtime check (mirroring `EnergyProcessor`'s guard), e.g.:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```
before entering either the hardened `BigInteger` path or the legacy double-division path, so the method never attempts to divide by zero regardless of JVM assertion settings.

### Proof of Concept
Root cause can be demonstrated statically:
1. `getTotalEnergyWeight()` can be driven to `0` purely through unprivileged actuators `FreezeBalanceV2Actuator`/`UnfreezeBalanceV2Actuator` adjusting `dynamicStore.addTotalEnergyWeight(...)`.
2. With `VMConfig.allowHardenResourceCalculation()` enabled (production default in later versions) and JVM assertions disabled (default), call `RepositoryImpl#calculateGlobalEnergyLimit` for any account with `frozeBalance >= TRX_PRECISION` while `totalEnergyWeight == 0`:
```java
long totalEnergyWeight = 0; // reached via full network unfreeze
BigInteger.valueOf(energyWeight)
    .multiply(BigInteger.valueOf(totalEnergyLimit))
    .divide(BigInteger.valueOf(totalEnergyWeight)) // throws ArithmeticException
    .longValueExact();
```
This matches the exact `EDIVISION_BY_ZERO`-style failure mode in the report: a legitimate zero divisor state reached by ordinary user action, hitting an unguarded division in downstream accounting logic. A concrete end-to-end trigger requires a test harness that drives global `totalEnergyWeight` to zero and then invokes a TVM contract call with hardened resource calculation enabled — this was not runnable in this read-only analysis, so the finding is based on static code-path verification rather than an executed exploit.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
