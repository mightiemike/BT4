### Title
Reverted L1-handler transactions are permanently marked "Committed" by the sequencer even though the OS never consumes the corresponding L1→L2 message - (File: crates/apollo_batcher/src/block_builder.rs)

### Summary
When an L1-handler transaction (an L1→L2 message triggered by an unprivileged L1 sender) reverts due to contract-level logic (not a protocol-level executor error), the Starknet OS correctly refrains from including that message in `messages_to_l2`, meaning the message stays unconsumed on L1. However, the sequencer's batcher unconditionally records every executed L1-handler transaction hash as "consumed" and only reclassifies it as "rejected" (retryable) when the blockifier execution itself returns a hard `Err`. A Cairo-level revert returns `Ok(...)` with `revert_error: Some(...)`, so it is committed permanently, never to be retried by this node's mempool/L1-provider bookkeeping.

### Finding Description
`execute_raw` for `L1HandlerTransaction` ( [1](#0-0) ) executes the entry point and returns `Ok(l1_handler_tx_execution_info(...))` with a `revert_error` populated whenever the Cairo execution reverts (as demonstrated by `test_l1_handler_set_value_and_revert` producing `revert_error: Some(RevertError::Execution(...))` while still returning `Ok`) [2](#0-1) .

In the batcher, `collect_execution_results_and_stream_txs` unconditionally inserts the L1-handler's `tx_hash` into `execution_data.consumed_l1_handler_tx_hashes` before inspecting the execution `result`, and only inserts into `rejected_tx_hashes` inside the `Err(err)` branch: [3](#0-2) 

Because a Cairo-level revert reaches the `Ok((tx_execution_info, state_maps))` branch (not `Err`), its hash is never added to `rejected_tx_hashes`. When the block is committed, `apply_commit_block` partitions `consumed_txs` by whether they are in `rejected_txs`, and anything not rejected is passed to `tx_manager.commit_txs(committed_txs, ...)`, which calls `mark_committed()` on the transaction, permanently retiring it from the L1 provider's transaction manager [4](#0-3) [5](#0-4) .

Meanwhile, on the OS side, `is_reverted` (derived from `tx_execution_info.is_reverted()`, i.e. `revert_error.is_some()`) causes `execute_l1_handler_transaction` to `return()` **before** calling `consume_l1_to_l2_message`, so the message is never written to `outputs.messages_to_l2`: [6](#0-5)  and [7](#0-6) . This is confirmed by the flow test explicitly asserting `messages_to_l2.is_empty()` for a reverted L1 handler [8](#0-7) .

The result is a divergence: the L1 message backing this L1-handler transaction is never marked consumed on L1 (its nonce/hash is untouched in the Starknet core contract), yet the sequencer's local transaction-manager state permanently marks that exact `tx_hash` as `Committed`, which the transaction manager comment states can only be removed "via L1 cancellation/consumption" [9](#0-8) . Any unprivileged L1 sender whose bridged deposit/message happens to revert on L2 (e.g., due to a legitimate contract-side condition — insufficient state, a race with another entry-point call, or a bug in the target contract) will have their message silently frozen: the sequencer will never propose/execute it again, while L1 still shows the message unconsumed, so the associated on-L2 effect (e.g., minting bridged funds) can never happen through normal message processing.

### Impact Explanation
This is a "permanent freezing of funds" class issue analogous to the referenced report: legitimate L1→L2 messages (e.g., token bridge deposits implemented as L1-handler entry points) that revert once on L2 become permanently unprocessable by the sequencer, even though the L1 side still considers the message pending and unconsumed. Users relying on automatic retry semantics of L1-handler transactions lose access to the corresponding L2-side effect through the normal, expected pathway, and must rely entirely on out-of-band L1 message cancellation (a separate, manual mechanism on the L1 bridge/core contract) to recover, if such logic even anticipates this permanently-blacklisted-but-unconsumed state.

### Likelihood Explanation
Any unprivileged actor sending a message from L1 to L2 can trigger this by causing the target L1-handler entry point to revert (e.g., a call that depends on transient L2 state, insufficient balance in the target contract, or a race condition), which is a normal, unprivileged, and non-adversarial occurrence in production bridging usage — not requiring any privileged or malicious behavior.

### Recommendation
In `collect_execution_results_and_stream_txs` (crates/apollo_batcher/src/block_builder.rs), treat L1-handler transactions whose `tx_execution_info.revert_error.is_some()` the same as `rejected_tx_hashes` (not just hard `Err` results), so `apply_commit_block`/`commit_txs` unstage them and keep them `Pending` for retry (or otherwise align sequencer-side "consumed" bookkeeping exactly with the OS's `is_reverted` check that gates `consume_l1_to_l2_message`), guaranteeing the local commit state never diverges from whether the message was actually consumed by the OS.

### Proof of Concept
Not directly reproducible with a self-contained unit test snippet from indexed content alone; the divergence is demonstrated by combining two already-present tests: `test_reverted_l1_handler_tx` (crates/starknet_os_flow_tests/src/tests.rs:421-464), which proves the OS emits no `messages_to_l2` entry for a reverted L1-handler, and `failed_l1_handler_transaction_consumed`/the `Ok` branch behavior in `collect_execution_results_and_stream_txs` (crates/apollo_batcher/src/block_builder_test.rs:1064-1112 and crates/apollo_batcher/src/block_builder.rs:643-716), which proves the batcher marks any executed (non-`Err`) L1-handler transaction, including a reverted one, as `consumed_l1_handler_tx_hashes` without adding it to `rejected_tx_hashes`. A full end-to-end reproduction would require running `reverted_l1_handler_tx_flow` (crates/apollo_integration_tests/tests/reverted_l1_handler_tx_flow_test.rs) and then attempting to resubmit the same `tx_hash` via `validate`/`get_txs`, and separately checking that no `messages_to_l2` output was ever produced for it — confirming the tx is permanently `Committed` locally while unconsumed on L1.

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);

            );
