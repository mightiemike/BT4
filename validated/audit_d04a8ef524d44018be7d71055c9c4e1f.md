## Finding: `TransactionOutput::update_total_supply` silently downgrades write-op metadata during sharded execution total-supply patching

### Title
Sharded-execution total-supply patch replaces a possibly-metadata-carrying `WriteOp` with a bare `legacy_modification`, corrupting the committed write set - (File: `types/src/write_set.rs`, function `update_total_supply`)

### Summary
`WriteSetV0::update_total_supply` (invoked via `TransactionOutput::update_total_supply`, called from `aggregate_and_update_total_supply` in `aptos-move/aptos-vm/src/sharded_block_executor/sharded_aggregator_service.rs`) mutates the already-materialized write set for the `TOTAL_SUPPLY_STATE_KEY` in place, but unconditionally replaces the existing entry with `WriteOp::legacy_modification(...)`, discarding whatever `WriteOp` kind/metadata the VM originally produced for that key. [1](#0-0) 

### Finding Description
This is an in-place "hack" explicitly called out in the source comment: sharded execution cannot cheaply re-materialize the full write set after cross-shard aggregation of the total-supply delta, so instead of recomputing the `WriteOp` it simply overwrites the byte payload: [2](#0-1) 

The replacement always constructs `WriteOp::legacy_modification`, i.e. a write op with **no `StateValueMetadata`** (`PersistedStateValueMetadata`/slot metadata absent) and always classified as `WriteOpKind::Modification`. In modern Aptos storage, a real VM-produced write for this table item could instead be:
- `WriteOp::modification(data, metadata)` — carrying real slot metadata (deposit/refund bookkeeping) if the table item already exists with metadata (post storage-fee migration these are near-universal on mainnet), or
- `WriteOp::creation(data, metadata)` — if the underlying storage slot did not previously exist.

By construction, `update_total_supply` asserts the key already existed (`.is_some()`), so it never mis-classifies `Creation` vs `Modification`, but it still throws away any pre-existing `StateValueMetadata` that a correctly-materialized (non-sharded) execution of the identical transaction would have preserved, and forces the legacy (no-metadata) `WriteOp` variant. `TransactionInfo::state_change_hash` is the BCS-hash of the write set: [3](#0-2) 

and `WriteOp`/`StateValueMetadata` are part of the serialized/hashed representation, so a write set produced through this sharded path is byte-for-byte different from the write set the same transaction would produce via the ordinary (non-sharded) VM path whenever the total-supply slot carries `StateValueMetadata`. That means:
- The persisted `StateValue` for `TOTAL_SUPPLY_STATE_KEY` loses its metadata (e.g., storage-deposit/refund accounting fields), corrupting durable ledger data relative to the correct VM result.
- `state_change_hash` (part of `TransactionInfo`, which is what actually gets hashed into the transaction accumulator / ledger) diverges from the value the reference (non-sharded) executor would compute for the identical transaction, i.e. a wrong hash is placed into the accumulator/proof chain whenever the sharded path is the one that commits state.

This is the structural analog of the ERC4626 root cause: an intermediate accounting value (the deposited/`realNeeded` amount there; the aggregated total-supply delta here) is patched back into committed output through a shortcut path that doesn't preserve all the information the canonical path would have produced, silently dropping data (fees there, `StateValueMetadata` here) that is part of what should be durably committed/hashed.

### Impact Explanation
If the sharded block executor is ever used as the actual execution path that produces the `TransactionOutput`/`TransactionInfo` committed to the ledger (rather than purely for local benchmarking), this causes a genuine state-commitment divergence: the on-disk `StateValue` for the total-supply table item silently loses its `StateValueMetadata`, and the `state_change_hash`/`accumulator_root_hash` computed from that output no longer matches what regular (non-sharded, canonical) execution of the same block would compute. This is exactly the "hard-fork-only divergence during commit" and "committed state that differs from the correct VM result / corrupts durable ledger data" categories in scope.

### Likelihood Explanation
I could not, within the available tools, conclusively confirm that `ShardedBlockExecutor`/`aggregate_and_update_total_supply` is wired into the mainnet validator's actual block-commit path today (as opposed to being used only by `aptos-move/aptos-vm/tests/sharded_block_executor.rs`, `execution/executor-service` (remote executor benchmarking), and `aptos-move/aptos-transaction-benchmarks`). `execution/executor/src/workflow/do_get_execution_output.rs` does reference `ShardedBlockExecutor`, which suggests it is reachable from the executor workflow, but I was unable to trace, in the remaining budget, whether the current on-chain config actually routes production block execution through this code path on mainnet. This uncertainty is significant: if sharded remote execution is only used for the experimental `executor-service` (separate remote-execution binaries) and not for consensus-driven mainnet block commit, this bug's practical exploitability/likelihood is much lower (it would matter only for operators voluntarily running the experimental remote/sharded executor, which may fall under the "experimental" exclusion in scope).

### Recommendation
`update_total_supply` should not force `WriteOp::legacy_modification`. It should preserve the existing `WriteOp`'s kind and `StateValueMetadata`, updating only the byte payload (e.g., via `WriteOp::set_bytes`/a metadata-preserving mutator), so that the sharded-aggregation write-op is byte-identical to what canonical (non-sharded) execution would produce for the same input.

### Proof of Concept
Not independently verified with a runnable reproduction in this session, because I could not confirm the sharded executor is on the mainnet commit path within the tool budget. Conceptually:
1. Execute a block containing an APT-supply-mutating transaction (e.g., mint/transfer) once through the normal (non-sharded) VM path, capturing the `WriteOp` for `TOTAL_SUPPLY_STATE_KEY` (post storage-fee migration this will carry `StateValueMetadata`).
2. Execute the identical block through the sharded executor path so that `aggregate_and_update_total_supply` → `TransactionOutput::update_total_supply` is invoked.
3. Compare the two `WriteOp`s for `TOTAL_SUPPLY_STATE_KEY`: the sharded path's op will be `legacy_modification` (no metadata) even though the non-sharded op carries metadata, and the two `TransactionOutput`/`TransactionInfo::state_change_hash` values will differ.

Given the unresolved uncertainty about whether this path is reachable in mainnet block commit, I am reporting this candidate with reduced confidence rather than a fully confirmed finding — the strongest local integrity break I found (metadata loss in a post-hoc write-set patch) is real in the code, but its reachability from the production commit path is not something I could fully verify with the available search tools.
