The default OAuth session cookie path is `'/'` (domain-wide), documented explicitly in `packages/apps/shopify-api/lib/base-types.ts`:### Title
Domain-wide OAuth session cookie path collision causes cross-tenant session overwrite / DoS of auth handler for non-embedded, multi-shop apps - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The Compound Finance bug relies on a pattern where an unprivileged actor can trigger a state-changing claim on behalf of another party against a shared mutable resource (the contract's COMP balance), permanently corrupting that resource for the legitimate owner, who can only recover by an out-of-band remediation (an upgrade). The closest reachable analog in `shopify-app-js` is the OAuth `callback` handler's session cookie, which by default is written to a single, domain-wide path (`'/'`) shared across all shops for a given app installation in a merchant's browser, so completing OAuth for one shop silently clobbers the session cookie belonging to another shop in the same browser, forcing that other tab/shop into an invalid/DoS'd authenticated state until the developer explicitly opts into the newly added `cookiePath` mitigation.

### Finding Description
In `oauth.callback`, after a valid OAuth code exchange, the library sets the `shopify_app_session` cookie: [1](#0-0) 

```ts
if (!config.isEmbeddedApp) {
  const cookiePath =
    typeof config.cookiePath === 'function'
      ? config.cookiePath(session)
      : (config.cookiePath ?? '/');
  await cookies.setAndSign(SESSION_COOKIE_NAME, session.id, {
    expires: session.expires,
    sameSite: 'lax',
    secure: true,
    path: cookiePath,
  });
}
```

`config.cookiePath` defaults to `'/'` unless explicitly configured, as documented directly in the config type: [2](#0-1) 

The `SESSION_COOKIE_NAME` (`shopify_app_session`) is a single, fixed cookie name (`packages/apps/shopify-api/lib/auth/oauth/types.ts:3`) that is not otherwise namespaced by shop. Because both the `begin` and `callback` OAuth endpoints are public, unauthenticated HTTP endpoints reachable by simply visiting a URL (any actor — including the merchant themselves navigating to install/re-auth a second shop, or a link crafted by an attacker pointing at the app's own callback flow for a different shop) can trigger a full OAuth completion that rewrites this domain-wide cookie at path `/`. This is analogous to the CompFi bug's "anyone can trigger a claim which mutates shared state used to determine ownership": here, "claiming" a session (completing OAuth) for shop B silently overwrites the shared cookie previously pointing to shop A's session, and shop A's tab is left pointing to a session id that mismatches its actual shop context, or the cookie is entirely replaced. This exact defect and its blast radius are documented by the project itself: [3](#0-2) 

The fix (the `cookiePath` option) is opt-in and requires the developer to also restructure their app's URLs to match a shop-specific prefix — meaning any app that has not proactively adopted this new option remains vulnerable by default, similar to how CompFi's `TreasuryAction` bug required the protocol to proactively "upgrade to regain access."

### Impact Explanation
For non-embedded, multi-shop apps (the explicit target audience of this fix), a merchant or attacker-controlled flow that completes OAuth for shop B in one browser tab will overwrite the `shopify_app_session` cookie that shop A's tab depends on, since both share `path=/` and the same cookie name. This causes shop A's tab to silently begin acting on shop B's session (cross-tenant session confusion) or to lose its valid session (denial of service on the auth handler, forcing an unexpected re-authentication). This matches the accepted categories of "session storage injection" / "cross-tenant access" / "DoS of an auth handler." Unlike the CompFi case, there is no direct fund theft, but the confidentiality/integrity impact is that one tenant's authenticated context can be silently substituted with another's on the same device.

### Likelihood Explanation
This defect requires: (1) a non-embedded app, (2) the default `cookiePath` (i.e., the developer has not configured the new mitigation), and (3) two shops using the same app being authenticated in the same browser (e.g., a merchant operating multiple stores, or a QA/dev testing multiple shops). This is a realistic and commonly-encountered scenario for multi-store merchants, and requires no privileged access or secret knowledge — it is triggerable purely by completing the normal, public OAuth flow twice for different shops in one browser. The project's own CHANGELOG documents this as a real production issue for existing apps, though it is only exploitable/observable in the non-embedded, multi-shop deployment pattern, and does not affect embedded apps at all (`config.isEmbeddedApp` check at `oauth.ts:219`).

### Recommendation
Make `cookiePath` shop-aware by default (e.g., default to a shop-derived subpath or embed the shop into the cookie name) rather than defaulting to `'/'`, so apps are secure without requiring the developer to opt in and restructure URL routing. At minimum, strongly surface this as a required configuration for non-embedded apps rather than an optional, easy-to-miss setting, and consider warning at startup for `isEmbeddedApp: false` configs that leave `cookiePath` unset.

### Proof of Concept
1. Configure a non-embedded app with default settings (`cookiePath` unset).
2. In Browser Tab 1, complete OAuth for `shop-a.myshopify.com` via `/some-callback`; the response sets `shopify_app_session` at `path=/` bound to shop A's session id, as verified by the existing test: [4](#0-3) 
3. In Browser Tab 2 (same browser/cookie jar), complete OAuth for `shop-b.myshopify.com` via the same callback path; this again writes `shopify_app_session` at `path=/`, overwriting the cookie from step 2.
4. Return to Tab 1 and reload any app page: the browser now sends the cookie pointing at shop B's session id, causing Tab 1 to either fail its session-shop match check (DoS, forced re-auth) or, if the app's server-side logic does not strictly validate `session.shop` against the request's own shop parameter, to act on shop B's session while displaying shop A's context (cross-tenant confusion).

```typescript
  /**
   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use
   * the most-recently-authenticated shop.
   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
   *
   * @example
   * // Static path (single-shop apps or apps with no shop-specific routing)
   * cookiePath: '/'
   *
   * @example
   * // Factory function (multi-shop non-embedded apps)
   * cookiePath: (session) => `/shops/${session.shop}/`
   *
   * @defaultValue `'/'`
   */
  cookiePath?: string | ((session: Session) => string);
```

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```
