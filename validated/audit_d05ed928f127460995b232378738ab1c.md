### Title
`TransactionOutput::ensure_match_transaction_info` silently skips checkpoint-hash comparison, allowing locally computed state roots to diverge from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the integrity comparator that checks a locally produced `TransactionOutput` (status, gas, write-set hash, event root) against an authenticated `TransactionInfo` obtained from a trusted source (accumulator-proof-verified, e.g. during chunk execution / replay-verify / debugger replay). The function explicitly and knowingly omits comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that summarize the state-tree roots produced by execution.

### Finding Description [1](#0-0) 

The function verifies status, gas, write-set hash, and event root against `txn_info`: [2](#0-1) 

but then explicitly stops, with a code comment acknowledging the gap: [3](#0-2) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This is the same bug class as the external report: a check meant to bound/validate a committed value is computed from a partial/stale view (here, a subset of the fields that determine correctness) while the actual authoritative value (the full `TransactionInfo`, including all Merkle-root fields) includes more. Just as `assetsMax` in the Morpho contract ignored accrued interest and let the code take the wrong branch, `ensure_match_transaction_info` ignores the state/hot-state/position checkpoint roots and lets replay/verification logic conclude "match" when the underlying state tree has actually diverged.

This comparator is used in state-integrity-relevant call sites, not just debugging:
- `execution/executor/src/chunk_executor/mod.rs` — chunk execution path that verifies locally re-executed transactions against a peer/authenticated `TransactionInfo` before committing to local storage during (fast/state) sync.
- `storage/db-tool/src/replay_on_archive.rs` — replay verification tool used to certify that archived history reproduces the correct ledger state.
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs` — debugger/CLI replay checks.

### Impact Explanation
Because the comparator never checks `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, a chunk-executor/replay path that relies on `ensure_match_transaction_info` as its correctness oracle can declare a transaction "verified" and proceed to commit it even though the locally computed state tree (main state, hot state, or the native-position/trading state tree) differs from the value actually committed to the ledger accumulator and signed by validators. This directly maps to the in-scope impact "Committed state that differs from the correct VM result or corrupts durable ledger data" and to "Authenticated API or state-view output bound to the wrong version, object, or proof context," since durable local storage would end up holding a state root that is inconsistent with the authenticated ledger while being treated as validated.

### Likelihood Explanation
The gap is unconditional (it is not gated behind the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature check as the comment suggests it should be) — the missing comparisons apply to `state_checkpoint_hash` and `hot_state_checkpoint_hash` as well, which are core, always-relevant fields, not just the newer position/trading-native root. The bug is acknowledged by the code authors themselves via the TODO, which strongly corroborates that the root cause is real and unaddressed at the time of this snapshot. Exploitability/triggering conditions (e.g., whether other layers such as the accumulator-proof verification of the full `TransactionInfo` hash independently catch such divergence before commit) could not be fully traced within this pass — `execution/executor/src/chunk_executor/mod.rs` did not return readable content via the available tools, so the exact surrounding commit-guard logic at that call site (e.g., whether an independent accumulator-hash check would also have to be bypassed) could not be fully confirmed. This uncertainty should be resolved by a deeper review of `execution/executor/src/chunk_executor/mod.rs` before treating this as fully exploitable in isolation.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output and the authenticated `txn_info` whenever those fields are present, rather than skipping them, before any caller treats the transaction as verified/committable.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
