Based on my research, I found a valid analog to the CVE-2020-8620 bug class (attacker-triggerable assertion/panic that crashes the node process from network-supplied data).

### Title
Sequencer node crash via unreachable-`.expect()` panic on empty L1-handler calldata during message-hash computation - (File: `crates/starknet_api/src/hash.rs`)

### Summary
`l1_handler_message_hash` (called from `L1HandlerTransaction::calc_msg_hash`) unwraps `calldata.0.split_first()` with `.expect("Invalid calldata, expected at least from_address")`. `Calldata`/`L1HandlerTransaction` have no non-empty invariant and derive `Deserialize`, so an `L1HandlerTransaction` with zero-length calldata is constructible. When `calc_msg_hash()` is invoked on such a transaction, the `.expect()` panics, which — depending on call site — can abort the calling task/process (a sequencer component crash), analogous to BIND's reachable `assert()`-triggered process exit in CVE-2020-8620.

### Finding Description
`l1_handler_message_hash` in `crates/starknet_api/src/hash.rs` (lines 167-192) does:
```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
``` [1](#0-0) 

This is reached via `L1HandlerTransaction::calc_msg_hash()` [2](#0-1) , which is called by the L1 events scraper (`crates/apollo_l1_events/src/l1_scraper.rs`) when computing L1-L2 message hashes for every scraped `LogMessageToL2` event:
```rust
let l1_msg_hashes = events.iter().filter_map(|event| match event {
    Event::L1HandlerTransaction { l1_handler_tx, .. } => {
        Some(l1_handler_tx.tx.calc_msg_hash())
    }
    _ => None,
});
``` [3](#0-2) 

Normally, calldata is constructed by prepending the L1 sender address to the L1 event payload (`crates/papyrus_base_layer/src/lib.rs:158-173`, `crates/apollo_rpc/src/v0_8/transaction.rs:1220-1234`), guaranteeing at least one element. However, this invariant is not enforced as a type-level constraint on `Calldata`/`L1HandlerTransaction`: the struct derives `Deserialize` directly and there is no validation preventing empty calldata from entering the system through alternate construction paths (e.g., deserialized `L1HandlerTransaction` from stored/replayed data, malformed relayed event data, or any future code path that builds `L1HandlerTransaction` without going through the "prepend sender" helper). The codebase itself acknowledges this exact gap: a companion function, `L1HandlerTransaction::payload_size()` in `crates/starknet_api/src/executable_transaction.rs`, was explicitly patched to use `saturating_sub` specifically because "`Calldata` has no non-empty invariant... an empty calldata is constructible" [4](#0-3) , with a regression test proving the empty-calldata case is reachable and previously caused an underflow/panic risk [5](#0-4) . That fix, however, only covers `payload_size()` — `calc_msg_hash()`/`l1_handler_message_hash()` in `hash.rs` still uses an unguarded `.expect()` on the same unenforced invariant.

Test fixtures in the codebase also model calldata with just a single element (`from_address`, zero-length payload) as a "normal" case (`crates/apollo_l1_events/src/l1_scraper_tests.rs:347-358`), showing that the payload length is not assumed to be bounded away from zero; a calldata vector reduced to *zero* elements (missing even `from_address`) would panic identically.

### Impact Explanation
An `.expect()`-triggered Rust panic in the L1-events scraper's per-event processing (used to identify and deduplicate L1→L2 messages) would unwind and, depending on whether the surrounding task guards against panics, can terminate the scraper task/process. Because message-hash computation runs unconditionally for every `LogMessageToL2` event scraped from L1, a node that scrapes a maliciously/incorrectly encoded L1 message (empty calldata) would repeatedly panic on each scrape attempt of that block range, potentially preventing the node from making progress ingesting L1→L2 messages — a network-unable-to-confirm-new-transactions-class denial of service for L1 handler transaction processing, analogous to the reachable assertion-crash in CVE-2020-8620.

### Likelihood Explanation
Medium. The primary construction paths already guarantee non-empty calldata (sender address is always prepended), so triggering this via the standard Ethereum contract flow requires either a bug/inconsistency in log decoding, a future or alternate construction path that bypasses the "prepend" step, or replay/rehydration of stored/serialized `L1HandlerTransaction` data that was crafted with empty calldata (the type's `Deserialize` derive permits this and there is no validation gate). I could not conclusively identify a fully unprivileged, purely-remote path (i.e., control of the raw Ethereum contract call) that produces empty calldata through the current decoding pipeline in the time available — this is a real code defect (already recognized and partially patched for a sibling function) but full exploitability confirmation would require verifying that no upstream check rejects zero-length `payload` arrays before decoding, which I could not verify from the indexed code.

### Recommendation
Replace the `.expect()` in `l1_handler_message_hash` with a graceful error return (mirroring the `saturating_sub` fix already applied to `payload_size()`), or add a validation step at deserialization time for `L1HandlerTransaction`/`Calldata` construction ensuring calldata used for L1 handler transactions always contains at least the `from_address` element before any hash/size computation is performed.

### Proof of Concept
```rust
use starknet_api::transaction::{L1HandlerTransaction, fields::Calldata};
use std::sync::Arc;

let tx = L1HandlerTransaction {
    calldata: Calldata(Arc::new(vec![])), // empty calldata, permitted by type/deserialize
    ..Default::default()
};
tx.calc_msg_hash(); // panics: "Invalid calldata, expected at least from_address"
```
This mirrors the existing regression test `l1_handler_payload_size_empty_calldata_does_not_underflow` [6](#0-5) , which proves the same empty-calldata `L1HandlerTransaction` is constructible, but demonstrates that `calc_msg_hash()` (unlike `payload_size()`) still panics on it.

pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());
```
