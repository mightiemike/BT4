## Title
`ensure_match_transaction_info` skips validating checkpoint hashes, allowing replay-verify to silently accept a diverged ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by replay/backfill tooling to confirm that a locally-recomputed `TransactionOutput` matches the trusted, previously-committed `TransactionInfo` for a given version [1](#0-0) . It checks status, gas used, write-set hash, and event root hash, but by its own admission does not check the state checkpoint hash, hot-state checkpoint hash, or position-state checkpoint hash fields carried in `TransactionInfo` [2](#0-1) .

### Finding Description
The function's trailing comment explicitly documents the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is the sole verification gate in two consumer paths that compare recomputed execution results against archived/committed `TransactionInfo`s without going through the normal accumulator/ledger-info verification flow:
- `ChunkExecutorInner::verify_execution`, used by `TransactionReplayer` during backup/db-restore replay-verification, which calls it per-transaction after VM execution and treats any `Err` as a verification failure [3](#0-2) .
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, the standalone `replay-verify` CLI tool used to audit archived history against re-execution, which likewise treats an `Err` from this function as the sole failure signal [4](#0-3) .

Because `ensure_match_transaction_info` never compares `self`'s recomputed state checkpoint root (or hot-state/position roots) against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, a divergence in the state-checkpoint (Sparse Merkle Tree / Jellyfish Merkle) root — the field that authenticates the entire post-transaction world state, not just the write-set of a single transaction — will not be detected by either replay-verification tool. Both tools will report success even though the locally recomputed ledger state (the merklized state tree) differs from the state the network committed and signed off on.

### Impact Explanation
The state checkpoint hash is the field that binds a `TransactionInfo` (and therefore the ledger accumulator / signed `LedgerInfo`) to the actual Merkleized world state at that version. Skipping its comparison in the one function whose entire purpose is "does my re-executed output match the trusted committed record" defeats the core guarantee of replay-verification: that re-execution of archived history reproduces the exact same, authenticated ledger state. A state-divergence bug (e.g., in VM execution, in a native module, or from a partial hard-fork-only inconsistency) that changes the world state without altering write-set hash/event hash/gas/status for the affected transactions would go completely undetected by both the `replay-verify` CLI and `TransactionReplayer`-based backup restore, since these are exactly the tools relied upon to catch such regressions before/during mainnet upgrades. This is a proof-integrity gap that matters for hard-fork-only divergence during replay/restore, matching the report's proof-and-storage-pivot category.

### Likelihood Explanation
This is not an attacker-triggerable exploit in the traditional sense (no privileged input can flip a "payment amount" the way the Seaport analog described); it is a structural gap in an internal correctness oracle. It will only manifest as a security-relevant miss when there is an actual, independent execution-determinism bug that changes state without changing the checked fields — moderately likely given the scope of write-set/state changes that are possible outside the tracked resource write set (e.g., changes surfaced only via checkpoint hash such as hot-state promotion, or trading-native/position state changes referenced by the TODO). The comment indicates awareness that this must be fixed before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, implying the authors consider the risk real for that upcoming feature, but the same comparator function is unconditionally used today for the primary `state_checkpoint_hash` in existing replay-verify flows regardless of that feature flag.

### Recommendation
Extend `ensure_match_transaction_info` to also assert that the locally computed state checkpoint hash(es) match `txn_info.state_checkpoint_hash()`, and, when present, `hot_state_checkpoint_hash()` and `position_state_checkpoint_hash()`. Since `TransactionOutput` alone doesn't carry a computed checkpoint root, this requires plumbing the checkpoint-stage output (from `DoStateCheckpoint`) into the comparison at the call sites in `chunk_executor/mod.rs::verify_execution` and `db-tool/replay_on_archive.rs::execute_and_verify`, so that any divergence in the merklized state root also fails replay-verification, not just the per-transaction write-set/events/gas/status.

### Proof of Concept
Not independently exploitable via external input; the gap is demonstrated directly by the code: `ensure_match_transaction_info` never reads or compares `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` [5](#0-4) , while it is the only check performed in both replay-verification call sites [6](#0-5) [4](#0-3) . A minimal reproduction would be: construct a `TransactionOutput` whose write set produces the same write-set hash and event root as a reference `TransactionInfo`, but a different final state (e.g. an extra/side write that does not increase `state_change_hash` divergence, such as one whose effect is captured only in the checkpoint tree, e.g. a hot-state or position-state promotion) — `ensure_match_transaction_info` would return `Ok(())` despite the checkpoint root diverging.

**Confidence caveat:** I was not able to fully trace whether `DoStateCheckpoint`'s own hash computation (`get_state_checkpoint_hashes`, referenced but whose full body I could not resolve in the index) independently re-validates the checkpoint hash against a "known" value during the chunk-executor's `verify_execution`/`remove_and_apply` commit path, which could mean the checkpoint root is cross-checked elsewhere in the pipeline (e.g., at ledger commit time via `LedgerUpdateOutput`/accumulator append) even though `ensure_match_transaction_info` itself skips it. If such an independent check exists and fires unconditionally on this path, the practical severity would be lower than described (defense-in-depth gap rather than the sole check). Given the explicit developer TODO calling out `replay_on_archive` specifically as capable of reporting false success, I believe no such independent check currently exists in that CLI path.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
