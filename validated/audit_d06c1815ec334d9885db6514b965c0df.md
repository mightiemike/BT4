This is a genuine, documented gap in `TransactionOutput::ensure_match_transaction_info`, which is used by both the chunk executor's `verify_execution` replay-verification path and the `aptos move cli replay-transaction` debugger tool.### Title
Replay-verification of `TransactionOutput` never checks state, hot-state, or position-state checkpoint roots - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function that both `db-tool`'s `replay_on_archive` verifier and the chunk executor's `verify_execution` replay-verification path use to authenticate a locally re-executed transaction against the persisted/backed-up `TransactionInfo`, only compares status, gas used, write-set hash, and event root hash. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The gap is explicitly acknowledged by a `TODO(trading-native)` comment in the function itself.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks four fields of the `TransactionInfo`: execution status, gas used, write-set hash (`state_change_hash`), and event root hash. It does not compare the checkpoint-root fields carried by `TransactionInfoV1`: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, defined at [2](#0-1) . The comment directly above `Ok(())` states this is a known limitation: replay-verify tooling can report success even when the authenticated position/hot state root diverges from local execution, and recommends fixing it before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

This function is invoked from two production-facing consistency-check call sites that are supposed to be the last line of defense proving that re-executed results match the authenticated, previously committed ledger state:
- `execution/executor/src/chunk_executor/mod.rs` `verify_execution`, used during chunk-executor replay verification of state-sync/backup-restore chunks: [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs` `execute_and_verify`, the tool operators use to independently verify an execution replay against backup transaction infos: [4](#0-3) 

Because these checks never touch `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, if a bug in state-checkpoint root computation (state Merkle root, hot-state root, or the newly-added native-position state root computed in `do_state_checkpoint.rs`, see [5](#0-4) ) produces a wrong checkpoint hash, neither of these verification paths will catch it. Both tools will report "replay succeeded" while the locally recomputed checkpoint root silently diverges from the value that was actually authenticated/committed to the ledger accumulator.

### Impact Explanation
This is a proof-integrity gap, not a consensus-safety bug by itself: the state/hot-state/position-state checkpoint hash is still computed and stored in the committed `TransactionInfo`/ledger accumulator elsewhere in the normal execution path (`do_state_checkpoint.rs`), so a bug here does not corrupt what gets committed by validators during normal consensus. But it removes the only automated cross-check that replay-verify tooling and chunk-executor state-sync replay perform against those authenticated roots. A latent bug in checkpoint-root computation (state Merkle tree, hot-state tree, or the new native-position tree) could silently pass both `replay_on_archive` (used to audit historical mainnet data/backups) and executor chunk-replay verification (used during fast-sync/state-sync chunk application), meaning corrupted or diverged state roots would not be detected by the very mechanisms designed to catch them. Given `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a new, not-yet-enabled feature per the comments in `types/src/on_chain_config/aptos_features.rs`, the immediate mainnet blast radius is limited today, but the gap already applies to `state_checkpoint_hash`/`hot_state_checkpoint_hash` as well, both of which are live on `TransactionInfoV1`-enabled chains.

### Likelihood Explanation
The gap is deterministic and always present when `ensure_match_transaction_info` is called on a checkpoint transaction — there is no need for a race condition or crafted input; any real divergence between the locally computed and authenticated checkpoint hash is masked. However, exploiting it to cause actual damage requires an independent root-cause bug in one of the three checkpoint-root computations (state, hot-state, or position). Since I could not find such a root-cause miscalculation elsewhere in the reachable code within this scan, I can only confirm the detection gap itself, not a chain of full state corruption.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, and where present, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` against the values computed by re-execution, for both `TransactionInfoV0`/`V1` variants, before it is relied upon as a replay-verification gate — as the existing TODO comment already recommends. This should be done prior to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` broadly.

### Proof of Concept
Conceptual (no runnable exploit against a specific corrupting bug was found in this scan):
1. Enable/assume a scenario where `TransactionInfoV1.state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) as recomputed during replay differs from the value stored in the backup/persisted `TransactionInfo` (e.g., due to an independent bug in `LedgerStateSummary::update` or the position-tree computation in `do_state_checkpoint.rs`).
2. Run `db-tool replay-on-archive` over that version range, or trigger chunk-executor replay verification (`ChunkExecutor::verify_execution`) over the same range.
3. `ensure_match_transaction_info` at [1](#0-0)  returns `Ok(())` because it never inspects the checkpoint hash fields, so the tool reports a clean, successful replay despite the underlying state root mismatch.

Note: I was not able to locate, within the scanned code, an independent concrete bug that actually produces a wrong checkpoint hash value (i.e., I can prove the detection gap exists and is reachable in unprivileged tooling, but not a full end-to-end "wrong value silently committed" chain). This should be treated as a proof-integrity/detection weakness finding rather than a proven state-corruption exploit.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
