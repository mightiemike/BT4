### Title
Attached deposit permanently locked in the Near Wallet Contract when `address_check_callback` rejects an existing named target - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::rlp_execute` is `#[payable]`, and any external caller (relayer) attaching a deposit has that deposit tracked in a `CallerDeposit` so it can be refunded if the downstream cross-contract call fails. However, in `address_check_callback`, one of its early-return error branches drops `caller_deposit` on the floor without issuing any refund `Promise`, and the contract exposes no other function capable of moving out that stranded balance.

### Finding Description
`rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:88-128`) is `#[payable]`. `inner_rlp_execute` captures the deposit attached by an external (non-self) predecessor into `CallerDeposit::new` (`runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs:180-191`, `lib.rs:345`). For an `EOABaseTokenTransfer{ address_check: Some(address), .. }` this `caller_deposit` is threaded through the address-registrar lookup promise into `address_check_callback` (`lib.rs:412-431`).

Inside `address_check_callback` (`lib.rs:134-192`), when the registrar lookup succeeds and returns `Some(account_id)` (meaning the target eth-address collides with an existing named account) and the caller is *not* the contract itself (`env::signer_account_id() != current_account_id`, i.e. the normal external-relayer path), the function immediately returns:

```rust
return PromiseOrValue::Value(ExecuteResponse {
    success: false,
    success_value: None,
    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
});
``` [1](#0-0) 

This branch consumes `caller_deposit` (moved into the function's arguments) but never spawns a `Promise` to send it back, unlike the only two refund paths that exist in this contract:
- `rlp_execute_callback`'s `PromiseResult::Failed` arm, which explicitly creates a transfer promise back to the caller (`lib.rs:296-311`).
- The unrelated relayer-fee refund in `inner_rlp_execute` (`lib.rs:374-385`), which is a different, unconditional payment and not tied to `caller_deposit`.

Because the deposit attached to `rlp_execute` is credited to the wallet contract's own account balance at receipt-processing time (per NEAR's Economics API semantics, `attached_deposit` becomes part of `account_balance` immediately), and `address_check_callback`'s early return here neither spends it in a further action nor refunds it, those tokens remain stuck in the wallet contract's balance permanently. There is no rescue/withdraw method anywhere else in `WalletContract` (`get_nonce`, `rlp_execute`, `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer` are the entire public surface) that can move out an orphaned deposit balance.

This is directly analogous to the reported Solidity bug class: value can be deposited into the contract via a `#[payable]` entry point, but a specific control-flow branch swallows the deposit with no code path to later reclaim it.

### Impact Explanation
Any external caller/relayer submitting an `EOABaseTokenTransfer` with `address_check: Some(address)` and a nonzero attached deposit, targeting an address that happens to correspond to an existing named account, causes that deposit to become permanently frozen in the wallet contract's account. This is unauthorized, unrecoverable loss of value for the party that attached the deposit (the relayer/caller), reachable purely by submitting a single transaction to a deployed Wallet Contract instance — no privileged role required.

### Likelihood Explanation
The trigger requires: (1) a nonzero deposit attached to `rlp_execute` by a non-self predecessor, (2) an `EOABaseTokenTransfer` transaction kind whose target requires an `address_check` (i.e., the target looks like another eth-implicit account rather than the current account), and (3) the address-registrar returning `Some` for that address (the address actually corresponds to a registered named account) while the caller is not the contract itself. This is a specific but realistically reachable combination for a relayer that attaches a deposit (e.g., to cover fees/gas as seen elsewhere in this same code path) and targets an address that turns out to be a named account — plausible in practice given how flexible the relayer-driven eth-tx-emulation flow is.

### Recommendation
In `address_check_callback`, before returning the early error in the `maybe_account_id.is_some() && signer != current_account_id` branch, issue a refund `Promise` for `caller_deposit` (mirroring the logic already present in `rlp_execute_callback`'s `PromiseResult::Failed` arm) instead of silently dropping it. More generally, audit every early-return `PromiseOrValue::Value(...)` branch in this contract that has access to a `caller_deposit`/`Option<CallerDeposit>` parameter, and ensure the deposit is either spent or explicitly refunded on every code path, or centralize refund handling in a single terminal callback rather than duplicating it ad hoc.

### Proof of Concept
1. A relayer holds a valid Near account and submits `rlp_execute(target, tx_bytes_b64)` with an attached deposit `d > 0`, where the RLP-encoded transaction decodes to an `EOABaseTokenTransfer` whose destination Ethereum address does not match the target's own derived address, triggering `address_check: Some(address)` (`internal.rs`/`types.rs` parsing, not fully traced here — flagged as unverified given index limits).
2. `inner_rlp_execute` creates `caller_deposit = CallerDeposit { account_id: relayer, yocto_near: d }` and schedules `address_registrar.lookup(address).then(address_check_callback(target, action, Some(caller_deposit)))` (`lib.rs:412-431`).
3. The address registrar returns `Some(existing_account_id)` because `address` happens to correspond to a real named account.
4. Since `env::signer_account_id() != current_account_id` (a genuine external relayer, not a self-relay), `address_check_callback` hits the branch at `lib.rs:167-173` and returns `ExecuteResponse{success:false,...}` directly, without creating any promise to refund `caller_deposit`.
5. The `d` yoctoNEAR deposit remains part of the wallet contract's account balance indefinitely; no method in `WalletContract`'s public interface can transfer it back out. [2](#0-1) [3](#0-2) [4](#0-3) 

**Note on confidence:** I was not able to fully trace `internal::parse_rlp_tx_to_action` and the address-derivation logic that decides when `address_check: Some(...)` is set versus `None` (file `internal.rs` was not read in full due to iteration limits), so the exact conditions under which a nonzero deposit co-occurs with an `address_check` requirement could not be independently confirmed from the RLP-parsing code — this should be verified by reading `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs` in a Devin session before treating this as fully confirmed.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
