### Title
Vault interest index/liquidity-index update timestamp (`last-update`) is only advanced when the computed index actually changes, allowing accrual to silently stall while time and pending interest keep accumulating - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` / `v0-vault-sbtc.clar` / `v0-vault-stx.clar` / `v0-vault-ststx.clar` / `v0-vault-ststxbtc.clar` / `v0-vault-usdh.clar`, function `accrue`)

### Summary
Each vault's `accrue` public function recomputes `next-index`/`next-liquidity-index` from `last-update` and only writes the new values (and, crucially, only advances `last-update` itself) when the freshly computed index differs from the currently stored one:

```clarity
(if (not (is-eq idx next))
    (var-set index next)
    false)
(if (not (is-eq lidx nliq))
    (var-set lindex nliq)
    false)
...
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [1](#0-0) 

This is the "clock advanced only on change" pattern: the accrual clock (`last-update`) is treated as a proxy for "interest has been captured," but it is gated on the *result* of the calculation rather than being advanced unconditionally on every accrual pass.

### Finding Description
`accrue` is invoked as the very first step of nearly every state-changing vault entrypoint (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`, `set-pause-states`) via `(try! (accrue))`, e.g.: [2](#0-1) [3](#0-2) 

The design intent (per `next-index`/interest-rate-based accrual, and confirmed by the explicit "PAUSED: Pass-through without reverting" branch) is that every call to `accrue` should reconcile the stored index against elapsed time since `last-update`: [4](#0-3) 

However, the `var-set last-update stacks-block-time` mutation is wrapped in the *same* `is-eq` guard used to decide whether to persist the new index values. If `next-index`/`next-liquidity-index` compute to the same value as the currently stored `idx`/`lidx` (which can legitimately happen, e.g. when `total-borrowed`/utilization is `u0`, or when the elapsed time × rate rounds down to zero under integer/fixed-point math for small time deltas), then:
1. `last-update` is **not** advanced.
2. No error is raised - `accrue` returns `(ok { index: next, lindex: nliq })` successfully.
3. The calling function (deposit/borrow/repay/etc.) proceeds normally, oblivious that the clock did not move.

On a subsequent call, `next-index` is computed against the *same stale* `last-update`, so the elapsed-time window used for interest calculation extends from the old `last-update`, not from "now." As long as intervening calls to `accrue` keep landing on the same "no-change" branch (e.g., because utilization/rate stays at the boundary that rounds to zero delta), `last-update` can remain pinned indefinitely while real time passes, silently compounding a backlog of unaccrued interest that is measured all at once whenever the index finally does move.

### Impact Explanation
This is a single-function, single-block-evaluable defect in interest bookkeeping used by all six vault contracts (`v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-stx`, `v0-vault-usdc`, `v0-vault-usdh`). Because `treasury-lp` reserve minting to `.dao-treasury` is derived from `debt-delta` computed against the *stale* `old-debt`/`new-debt` pair (using the un-advanced `idx`), and suppliers'/borrowers' owed interest is likewise a function of `index`, a stalled `last-update` temporarily freezes protocol-reserve minting (`treasury-lp`) and skews the interest actually owed by borrowers/paid to suppliers relative to elapsed real time - i.e., a **temporary freezing of unclaimed yield** (interest/reserve accrual) until the index eventually ticks over. This lands on the in-scope High-impact category "theft of unclaimed yield or royalties, permanent freezing of unclaimed yield or royalties, or temporary freezing of funds."

### Likelihood Explanation
This requires no privileged access - it triggers purely from the normal flow of any user calling `deposit`/`borrow`/`repay`/`redeem`/`flashloan`, which all route through `accrue`, whenever the naturally-computed `next-index`/`next-liquidity-index` happens to equal the stored value (a state reachable at low utilization, very low elapsed time between transactions, or specific fixed-point rounding boundaries in `next-index`/`next-liquidity-index`, which I was not able to fully inspect due to index/tool-call limits - their exact bodies were not returned by search). The precise frequency/severity depends on the interest-rate curve's rounding behavior, which is unverified here.

### Recommendation
Decouple the "did the index change" check (used only to skip a redundant `var-set` write) from the clock advancement: always update `last-update` to `stacks-block-time` whenever `accrue` runs the non-paused branch, regardless of whether the computed index differs from the stored one:
```clarity
(var-set last-update stacks-block-time)
```
unconditionally, at the end of the non-paused branch, rather than gating it on `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))`.

### Proof of Concept
1. Ensure vault utilization/rate conditions are such that `next-index` (and `next-liquidity-index`) compute to the same value as the currently stored `index`/`lindex` (e.g., very low or zero utilization) - reachable via `mainnet/contracts/vault/v0-vault-usdc.clar` `accrue` at [5](#0-4) .
2. Call any state-changing entrypoint (e.g. `deposit`) which internally calls `(try! (accrue))` at [6](#0-5) . Observe the transaction succeeds and `last-update` is left unchanged because the branch at [7](#0-6)  evaluates false.
3. Repeat step 2 across multiple blocks while the no-change condition persists; `last-update` stays pinned to its original value even though real elapsed time (and, once utilization rises, actual owed interest) is growing.
4. When conditions change such that `next-index` finally differs, the accrual window used is `stacks-block-time - stale(last-update)`, i.e. the entire pinned period is settled in one lump calculation rather than being captured incrementally, temporarily distorting/freezing the treasury reserve mint (`treasury-lp`) timing relative to when it should have occurred.

Note: I was unable to retrieve the exact bodies of `next-index`/`next-liquidity-index`/`interest-rate`/`utilization` within the tool-call budget, so the precise numeric conditions under which the "no-change" branch triggers (and thus the exact likelihood) could not be fully confirmed from source and should be verified directly in the repository.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))

(define-public (system-borrow (amount uint) (receiver principal))
  (let (
