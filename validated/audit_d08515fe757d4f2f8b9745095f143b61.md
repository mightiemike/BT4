### Title
Unauthorized cancellation of finalized (APPROVED/DISAPPROVED) proposals via `ProposalDeleteActuator` corrupts price-history reconstruction - (File: `actuator/src/main/java/org/tron/core/actuator/ProposalDeleteActuator.java`)

### Summary
`ProposalDeleteActuator.validate()` only rejects proposals whose state is already `State.CANCELED` or that have expired; it never checks for `State.PENDING`. Because `ProposalController.processProposal` transitions a proposal to `State.APPROVED` or `State.DISAPPROVED` well before its `expirationTime` is reached (approval is decided at maintenance time, while `expirationTime` is a much later cutoff), the original proposer can still submit a `ProposalDeleteContract` after the proposal has already been approved and its dynamic parameters applied, unconditionally flipping the finalized state to `CANCELED`.

### Finding Description
`ProposalController.processProposal` sets the proposal to `State.APPROVED` (after already calling `setDynamicParameters` → `ProposalService.process`, which commits the parameter change) or `State.DISAPPROVED`, and persists it via `manager.getProposalStore().put(...)`. [1](#0-0) 

Separately, `ProposalDeleteActuator.validate()` checks ownership, expiration, and `State.CANCELED` only — it does not check `hasProcessed()` (i.e., `APPROVED`/`DISAPPROVED`): [2](#0-1) 

`ProposalDeleteActuator.execute()` then unconditionally overwrites the state to `CANCELED` regardless of the prior state: [3](#0-2) 

Because `expirationTime` (set at proposal creation, e.g. `createTime + cycles * maintenance period`) is generally far later than the maintenance cycle at which `processProposal` decides `APPROVED`/`DISAPPROVED`, there is a real window during which the original proposer (still holding the same address that created the proposal — an ordinary, unprivileged account/witness) can send a `ProposalDeleteContract` for their own already-`APPROVED` (or `DISAPPROVED`) proposal and successfully cancel it.

This corrupts `ProposalStore.getSpecifiedProposals(State.APPROVED, code)`, which filters purely on `state`: [4](#0-3) 

That method is the sole data source for `EnergyPriceHistoryLoader.getEnergyProposals()` and `BandwidthPriceHistoryLoader.getBandwidthProposals()`, which reconstruct historical energy/bandwidth fee prices used by `Wallet.getEnergyFee(long timestamp)` and equivalent bandwidth-fee lookups: [5](#0-4) [6](#0-5) 

If a proposer cancels their own already-approved fee-change proposal after the effect has already been applied to `DynamicPropertiesStore` (via `ProposalService.process`), the entry silently disappears from `getSpecifiedProposals(State.APPROVED, ...)`, so the historical price-history string built by these loaders will omit that price change entirely — even though the fee change was live on-chain for the interval it was in effect.

### Impact Explanation
This is a historical-data-integrity/state-corruption issue rather than direct fund theft: any account that created a fee/parameter-change proposal can erase the on-chain record of it being approved once approval has been finalized. Downstream consumers relying on `getSpecifiedProposals(State.APPROVED, code)` for reconstructing historical bandwidth/energy prices (used e.g. for fee/refund calculations keyed by timestamp via `Wallet.getEnergyFee(timestamp)`) will silently lose that entry, producing an incorrect (gapped) price history and potentially wrong fee computations for transactions in that time window.

### Likelihood Explanation
Preconditions: attacker only needs to be the original proposer address of a proposal (any witness/committee account able to create proposals, which is an ordinary permissioned-but-unprivileged action already reachable through `ProposalCreateContract`), and must act after the proposal is finalized (`APPROVED`/`DISAPPROVED`) but before its `expirationTime`. Since finalization typically happens at the next maintenance cycle while `expirationTime` is set multiples of maintenance cycles later, this window reliably exists for every proposal, making the issue deterministically reproducible, not a rare race.

### Recommendation
In `ProposalDeleteActuator.validate()`, reject deletion once the proposal has been processed, e.g. add a check using `ProposalCapsule.hasProcessed()` (which already exists and checks for `APPROVED`/`DISAPPROVED`) alongside the existing `State.CANCELED` check, throwing `ContractValidateException` if the proposal is no longer `PENDING`.

### Proof of Concept
Java unit test (extend `ProposalDeleteActuatorTest`/use `ProposalController` + `ProposalDeleteActuator`):
1. Create a proposal via `ProposalCreateActuator` as `OWNER_ADDRESS_FIRST` (as done in `initTest()`).
2. Drive the proposal to `State.APPROVED` by populating `activeWitnesses` in `WitnessScheduleStore` and adding sufficient approvals, then call `ProposalController.processProposal(proposalCapsule)` (mirroring `ProposalControllerTest.testProcessProposal`) — assert the dynamic parameter was applied (e.g., via `DynamicPropertiesStore` getter) and `proposalCapsule.getState() == State.APPROVED`.
3. Ensure `now < proposalCapsule.getExpirationTime()` still holds (it will, since expiration is much later than the maintenance cycle).
4. Construct `ProposalDeleteContract` with `OWNER_ADDRESS_FIRST` and the proposal id, run `ProposalDeleteActuator.validate()` — assert it does NOT throw (currently succeeds, which is the bug) — then `execute()` and assert `proposalStore.get(id).getState() == State.CANCELED`.
5. Call `EnergyPriceHistoryLoader.getEnergyProposals()` (or `BandwidthPriceHistoryLoader.getBandwidthProposals()`) and assert the previously-approved proposal is now absent from the returned list / resulting price-history string, demonstrating the historical record loss.
6. After applying the recommended fix (checking `hasProcessed()`), re-run step 4 and assert `validate()` throws `ContractValidateException` with a message indicating the proposal has already been processed.

  public List<ProposalCapsule> getSpecifiedProposals(State state, long code) {
    return Streams.stream(iterator())
        .map(Map.Entry::getValue)
        .filter(proposalCapsule -> proposalCapsule.getState().equals(state))
        .filter(proposalCapsule -> proposalCapsule.getParameters().containsKey(code))
        .sorted(
            (ProposalCapsule a, ProposalCapsule b) -> a.getExpirationTime() > b.getExpirationTime()
                ? 1 : -1)
        .collect(Collectors.toList());
  }
