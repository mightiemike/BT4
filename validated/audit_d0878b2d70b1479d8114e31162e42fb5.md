Based on my investigation, I found a legitimate analog in java-tron's DPoS voter reward mechanism (`MortgageService`/`DelegationStore`/`MaintenanceManager`), which mirrors the Synthetix-style "reward period starts before there are participants" bug class from `BathBuddy`.

### Title
Voter rewards for witnesses with zero votes in a cycle are permanently lost due to reward-index (`Vi`) not being incremented - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
In java-tron's new voting-reward algorithm, block/standby/transaction-fee rewards are credited to a witness's per-cycle reward bucket via `MortgageService.payReward()` regardless of whether that witness currently has any voters. At cycle boundary, `MaintenanceManager.doMaintenance()` converts this per-cycle reward into the accumulated reward-per-vote index (`Vi`) via `DelegationStore.accumulateWitnessVi()`. If the witness's vote count for that cycle is `0`, the accrued reward is silently discarded instead of being carried forward or refunded, exactly matching the `BathBuddy` root cause of rewards accruing "before there is at least one participant."

### Finding Description
`MortgageService.payReward()` unconditionally records a witness's net reward (after brokerage) into `delegationStore.addReward(cycle, witnessAddress, value)` for every block it produces and for standby-witness payouts: [1](#0-0) 

This reward pool is meant to be distributed to voters proportionally, through the `Vi` (value-index) mechanism computed at the end of each cycle in `MaintenanceManager.doMaintenance()`: [2](#0-1) 

The actual accumulation logic in `DelegationStore.accumulateWitnessVi()` explicitly discards the reward when `voteCount == 0` for that cycle, only forwarding the previous `Vi` unchanged: [3](#0-2) 

Because `Vi` never increases for that cycle, no voter's `computeReward()` (based on `deltaVi = endVi - beginVi`) will ever reflect that reward, even for voters who start voting for that witness in a later cycle — the specific cycle's reward is not baked into the cumulative index at all. This is structurally identical to `BathBuddy.notifyRewardAmount` accruing a `rewardRate` over a period with zero `totalSupply`: the funds are "spent" from an accounting perspective (deducted from `TransactionFeePool`, minted as block-pay) but never become claimable by anyone, since the crediting mechanism (`Vi`/`rewardPerToken`) requires nonzero participants to record the accrual.

A witness can have zero votes and still be actively producing blocks (and hence earning these rewards) because `WitnessCreateActuator.createWitness()` creates a new witness with an explicit vote count of `0` and no self-vote requirement: [4](#0-3) 

On networks with fewer registered witnesses than the active-witness slot count (e.g., private/test networks, or early after mainnet witness churn), a freshly created witness with 0 votes can be selected into the active set and produce blocks while `getWitnessVote(cycle, address)` for that cycle is `0`, triggering the loss path.

### Impact Explanation
This causes real economic value — freshly minted `WitnessPayPerBlock`/`Witness127PayPerBlock` rewards, and real funds debited from the shared `TransactionFeePool` via `payTransactionFeeReward` — to be computed, deducted/minted, and stored as a per-cycle reward entry, but never surface into any account's claimable allowance. It is not a theft vector, but it is a concrete state-accounting defect: funds are removed from `TransactionFeePool` (a real, shared, on-chain balance) with no destination account ever able to withdraw them, since `Vi` cannot represent per-cycle contributions when `voteCount == 0`, and unlike genuinely idle reward, the record in `DelegationStore` (`buildRewardKey`) is never revisited or refunded.

### Likelihood Explanation
Requires a witness that is in the active/standby producing set while having zero recorded votes for the corresponding cycle — an edge case most likely on chains with a witness count at or below the active/standby slot thresholds (private nets, early-stage networks, or after large witness churn), rather than on TRON mainnet where witness slots are typically fully saturated by voted candidates. Still, nothing in `WitnessCreateActuator` or `MaintenanceManager` prevents this state from occurring.

### Recommendation
When `voteCount == 0` for a cycle in `DelegationStore.accumulateWitnessVi`, carry the un-distributed reward forward to be merged into the next cycle's reward for that witness (rather than dropping it), similar to the "rollover" pattern recommended for `BathBuddy` — i.e., accumulate reward until the witness actually has voters, at which point it should be reflected in `Vi`.

### Proof of Concept
1. Enable `allowChangeDelegation` (new reward algorithm) on a network with witness slots exceeding the number of registered witnesses (or deliberately create a new witness via `WitnessCreateActuator`, which sets `voteCount = 0`).
2. Ensure this witness enters the active set with `voteCount == 0` for cycle `C` (`DelegationStore.setWitnessVote` will store `0` for cycle `C`, per `MaintenanceManager.doMaintenance` line 160).
3. Have the witness produce a block in cycle `C`; `MortgageService.payBlockReward`/`payTransactionFeeReward` call `payReward`, which calls `delegationStore.addReward(C, witnessAddress, value)` (`MortgageService.java` lines 79-87), decrementing `TransactionFeePool` for the transaction-fee portion.
4. At the next `doMaintenance()`, `accumulateWitnessVi(C, witnessAddress, 0)` is invoked; since `voteCount == 0`, `DelegationStore.accumulateWitnessVi` (lines 133-146) skips accumulating the reward into `Vi`.
5. Even if a voter later votes for this witness starting cycle `C+1`, `computeReward` only sees `Vi` deltas from `C+1` onward — the reward recorded for cycle `C` is unrecoverable by any account, despite already having been deducted from `TransactionFeePool`/minted as pay.

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
