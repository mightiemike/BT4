### Title
Webhook HMAC only signs the request body, letting a single merchant replay a legitimately-signed webhook against a victim shop's domain/topic and obtain that victim's authenticated `admin` client - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
The webhook signature verification used by `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express` authenticates only the raw HTTP body against `X-Shopify-Hmac-Sha256`. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id` and `X-Shopify-Api-Version` headers - which are used unauthenticated downstream to select which tenant's session/admin client to attach to the webhook context - are never included in the signed data. This mirrors the GiddyVaultV3 "incomplete signature coverage" bug class: a validly-signed artifact (the body+HMAC) is accepted in a context (domain/topic) it was never bound to.

### Finding Description
`validateHmacFromRequestFactory` computes the HMAC purely from `rawBody` and the app's single (per-app, shared-across-all-shops) `apiSecretKey`: [1](#0-0) 

`validateFactory` calls this HMAC check, and only after it succeeds does it separately *read* (never authenticate) the `domain`/`topic`/`webhookId`/`apiVersion` headers via `checkWebhookHeaders`: [2](#0-1) [3](#0-2) 

Downstream, `authenticateWebhookFactory` (identical in shopify-app-remix and shopify-app-react-router) trusts `check.domain` to look up and attach a real, previously-stored offline session/admin client, and trusts `check.topic`/payload for dispatch - none of which were part of the cryptographic signature: [4](#0-3) [5](#0-4) 

Because `apiSecretKey` is a single per-app secret shared by every shop that installs the app (not a per-shop signing key, and the signature never binds shop/topic), any actor who legitimately installs the app on their own store (an unprivileged, single-merchant actor) can capture one real Shopify-delivered webhook (`rawBody` + valid `X-Shopify-Hmac-Sha256`), then replay that exact `rawBody`/HMAC pair directly to the app's `/webhooks` endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain and `X-Shopify-Topic` with any topic of choice. The HMAC check still passes (it only checks the body), `checkWebhookHeaders` only checks that headers are *present*, and `ensureValidOfflineSession(params, check.domain)` will happily return the **victim's real, previously stored offline session/admin client** if the victim has installed the app.

### Impact Explanation
This produces a webhook context where `shop`/`admin` belong to the victim tenant, but `topic` and `payload` are entirely attacker-controlled (drawn from a webhook the attacker legitimately received for their own store). Any app webhook handler that uses `payload` to drive admin-API side effects (e.g., tagging orders, updating metafields, issuing refunds, writing draft orders) executes those side effects with the **victim's real admin credentials** in response to attacker-chosen data. This is a cross-tenant authentication/authorization bypass: a forged (header-substituted) Shopify request is accepted and routed to another merchant's authenticated session.

### Likelihood Explanation
Requires only: (1) the attacker installs the target app on their own development/trial store to receive at least one legitimately Shopify-signed webhook, (2) the attacker crafts a direct HTTP POST to the app's public `/webhooks` endpoint with the captured body/HMAC and swapped `domain`/`topic` headers, and (3) the victim shop has an existing stored offline session (true for any actively-installed app). No secrets are leaked and no MITM is needed - this is reachable by any single unprivileged merchant against any other shop that has the same app installed.

### Recommendation
Bind the trusted request metadata into the authenticated data used to establish the webhook context: e.g., validate that `check.domain` matches the shop that the HMAC was actually generated for (which requires Shopify to sign domain/topic, or alternatively deriving/caching a per-shop expectation at webhook-registration time), or at minimum cryptographically bind `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` into the value hashed for comparison rather than trusting them merely for presence. Failing a header-signing scheme change from Shopify itself, apps should treat `webhookId` as a single-use nonce (reject already-seen `webhookId`s) so a captured body/HMAC pair cannot be replayed with different header metadata.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real `ORDERS_CREATE` webhook delivery with valid `X-Shopify-Hmac-Sha256` header (per [6](#0-5) , the HMAC only covers `rawBody`).
2. Attacker resends the identical `rawBody` and `X-Shopify-Hmac-Sha256` value to the app's `/webhooks` endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: ORDERS_CREATE` (or any topic).
3. `validateFactory`/`validateHmacFromRequestFactory` accepts the request as valid because the body/HMAC pair matches (per [7](#0-6) ).
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, "victim-shop.myshopify.com")`, which loads the victim's real stored session and attaches a genuine `admin` client scoped to the victim (per [8](#0-7) ), while `payload`/`topic` remain attacker-controlled from step 1.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
