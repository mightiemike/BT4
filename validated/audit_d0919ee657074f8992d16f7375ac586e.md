### Title
Oversized-body rejection fails to close the connection, enabling keep-alive DoS amplification - ([File: core/services/gateway/network/httpserver.go])

### Summary
`httpServer.handleRequest` calls `http.MaxBytesReader(nil, r.Body, int64(maxRequestBytes))` with a `nil` `ResponseWriter` instead of the real `w`. Because of this, when a request body exceeds `maxRequestBytes`, net/http can never invoke the `requestTooLarger.requestTooLarge()` hook on the real response object, so the connection is never marked for forced closure and keep-alive is preserved, allowing repeated oversized-body submissions on the same TCP connection.

### Finding Description
In `httpServer.handleRequest` [1](#0-0)  the code obtains the configured byte limit and wraps the request body:

```go
source := http.MaxBytesReader(nil, r.Body, int64(maxRequestBytes))
rawMessage, err := io.ReadAll(source)
```

`http.MaxBytesReader`'s first parameter is meant to be the live `http.ResponseWriter` for the request. Internally, net/http's `maxBytesReader.Read` performs a type-assertion `l.w.(requestTooLarger)` and, if it succeeds, calls `requestTooLarge()` on the underlying `*http.response`. That method sets `closeAfterReply = true` and `requestBodyLimitHit = true` on the response, which forces the connection to be dropped after the reply instead of being kept alive, and skips net/http's own attempt to drain the remainder of an oversized body.

Because this handler passes a literal `nil` instead of `w`, the type assertion on the nil interface always fails, so `requestTooLarge()` is never invoked, `closeAfterReply`/`requestBodyLimitHit` are never set on the real response, and `w.WriteHeader(http.StatusBadRequest)` is issued without any signal to close the connection. net/http's `shouldReuseConnection()` therefore proceeds to try to reuse the connection for the next request as long as the small number of unread bytes left in the socket (bounded by net/http's own post-handler drain cap) can be discarded successfully — which is trivially achievable if the attacker sends a body only slightly larger than `maxRequestBytes`.

No other code path in `handleRequest` sets `Connection: close`, closes the connection, or otherwise penalizes/rate-limits a client for repeatedly exceeding the limit; `MaxRequestBytesLimiter` [2](#0-1)  only governs the per-request byte ceiling, not connection reuse or repeated-attempt cost.

### Impact Explanation
An unprivileged remote client can open a single persistent (keep-alive) HTTP connection to the gateway's request path and repeatedly send request bodies just over `maxRequestBytes`. Each attempt forces the server to allocate buffers and read up to the byte limit via `io.ReadAll` before erroring out, at effectively zero cost to the attacker (no new TCP/TLS handshake needed per attempt), amplifying CPU/memory consumption per attacker-controlled connection compared to the one-shot rejection the size-limiter is intended to enforce. This is a denial-of-service resource-amplification issue against the Gateway HTTP server, not a data-integrity or privilege-escalation compromise.

### Likelihood Explanation
Exploitability requires only default keep-alive HTTP behavior (enabled by default in Go's `net/http` client/server) and the ability to send POST requests to the gateway's configured `Path`, which is the normal, unauthenticated entry point before any JWT/auth check runs (the `Authorization` header is parsed only after the body read at line 212-216). Any external caller reaching the gateway's HTTP listener can trigger this repeatedly and deterministically, making it highly likely to be exploitable wherever this gateway HTTP endpoint is network-reachable.

### Recommendation
Pass the real `http.ResponseWriter` into `http.MaxBytesReader` instead of `nil`:
```go
source := http.MaxBytesReader(w, r.Body, int64(maxRequestBytes))
```
This allows net/http's built-in `requestTooLarge()` hook to fire, setting `Connection: close` and `closeAfterReply`, so the server terminates the abusive connection immediately after an oversized-body rejection rather than allowing indefinite reuse.

### Proof of Concept
Integration test plan (extends `core/services/gateway/network/httpserver_test.go`):
1. Start the server with a small `MaxRequestBytes` (e.g., 5 bytes) as in `TestHTTPServer_HandleRequest_RequestBodyTooBig` [3](#0-2) .
2. Open a raw `net.Conn` (not via `http.Client`, to control connection reuse) and send an HTTP/1.1 request with `Connection: keep-alive` and a body larger than the limit; read the `400` response.
3. Immediately send a second oversized-body request on the *same* connection without redialing.
   - Expected (fixed): the server closes the connection after the first response (`Connection: close` header present, or the socket read on step 3 returns EOF/connection reset), so the second request cannot be processed on the same connection.
   - Actual (vulnerable): the second (and further) oversized requests are accepted and processed on the same connection, each incurring a full `io.ReadAll` up to `maxRequestBytes`, demonstrating unmitigated connection-reuse amplification.
4. Optionally measure CPU/allocations for N oversized requests over one persistent connection versus N one-shot connections to quantify the amplification factor.
