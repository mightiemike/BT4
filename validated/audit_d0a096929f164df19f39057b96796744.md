Based on my investigation, I found a concrete analog in nearcore's `ShardLayout::resolve_to_current_shard`, which is the exact mechanism protecting `GlobalContractDistribution` receipts from becoming "stale" when the underlying shard configuration (shard layout) changes mid-flight — directly analogous to `distributableERC20s` being mutated mid-distribution in the original report.

### Title
Multi-generation resharding can strand `GlobalContractDistribution` receipts on legacy (V1/V2) shard layouts, causing a chunk-processing halt - (File: `core/primitives/src/shard_layout/mod.rs`)

### Summary
`GlobalContractDistribution` receipts carry a `target_shard` that is resolved against the *current* shard layout when the receipt is applied, exactly like the `distributableERC20s` array is read fresh at `distribute()` time in the original finding. If the "configuration" (shard layout) is mutated more than once while such a receipt is in flight (delayed queue / congestion buffered / forwarded shard-by-shard), the single-generation resolution used for legacy layouts cannot find a valid path and the runtime returns an unrecoverable `EpochError::ShardingError`.

### Finding Description
`Receipt::receiver_shard_id` resolves a `GlobalContractDistribution` receipt's shard using `shard_layout.resolve_to_current_shard(target_shard)` when the stored `target_shard` no longer exists in the current layout: [1](#0-0) 

`resolve_to_current_shard` explicitly documents that only `ShardLayoutV3` supports walking the **complete** split history; V0/V1/V2 layouts only support a **single generation**: [2](#0-1) 

This mirrors the root cause pattern of the reported bug: a value (`target_shard` / `distributableERC20s` index) that was captured under one version of a mutable, admin/protocol-controlled configuration (shard layout / distributable-token list) is later consumed under a newer version of that same configuration, and the reconciliation logic only accounts for a single step of drift.

The regression test added for this exact scenario (`test_stale_global_contract_distribution_after_double_resharding`) explicitly documents the residual gap for non-V3 (static resharding) shard layouts: [3](#0-2)  The test's own comment states the fix "only works with V3 shard layouts (dynamic resharding)" because "with static resharding, the shard layout doesn't maintain a full split history," and the test is a no-op unless `DynamicResharding` is enabled.

The full end-to-end path is `apply_global_contract_distribution_receipt` → `forward_distribution_next_shard`, which reads the shard layout for the *current* epoch each time the receipt hops to a new shard, and computes `already_delivered_shards` against that layout's `shard_ids()`: [4](#0-3)  If a receipt sits in the delayed-receipt queue (or is congestion-buffered) across two or more resharding transitions on a chain still running legacy (V1/V2) shard-layout bootstrapping/config (before/without `DynamicResharding`'s V3 split-history tracking), `resolve_to_current_shard` for V0/V1/V2 can only walk one generation (`self.get_children_shards_ids(shard_id).map(|c| c[0])`), and returns `None` once the shard id is two or more splits removed from the current layout — exactly the scenario the regression test exercises but explicitly does not cover for static resharding.

### Impact Explanation
`receiver_shard_id` returning `Err(EpochError::ShardingError(...))` for a receipt that must be processed (it's already committed to the delayed-receipt queue / trie) is not a recoverable, ignorable condition in `apply_state`/`congestion_control` receipt-forwarding code — the analogous scenario in the code-423n4 report was framed as "Index out of bounds" causing `distribute()` to permanently revert. Here the equivalent failure is a hard error surfaced while applying/forwarding a receipt that must be included in every block from that point on, which — per the report's `receipt_filter_fn`-referencing comment in the test itself ("processing the stale GlobalContractDistribution receipt will panic ... to remap the old target_shard after two resharding generations") — is characterized by the codebase's own authors as a chain-halting/panicking condition. This is reachable purely by any unprivileged account submitting a `DeployGlobalContractAction` transaction (any account can deploy a global contract) combined with the network undergoing shard splits, i.e. no operator/validator misbehavior is required — an ordinary transaction, submitted before two consecutive shard splits, can strand its own distribution receipt.

### Likelihood Explanation
Triggering this requires: (1) an ordinary account deploying a global contract so a `GlobalContractDistribution` receipt targets a soon-to-be-split shard, (2) that receipt getting delayed (naturally, via congestion, or via the delayed-receipts queue) across **two or more** resharding events, and (3) the shard layout of the network at the time not yet using `ShardLayoutV3`'s full split-history tracking (either the `DynamicResharding` protocol feature not yet active, or a chain that reshards using the legacy V1/V2 path). Given `DynamicResharding` is only enabled at protocol version 85 per the epoch-manager spec docs, any chain/testnet still on pre-85 layouts, or any resharding path that produces V1/V2 layouts, remains exposed. Likelihood is Medium: it needs a specific timing window (receipt survives two reshardings) that an attacker cannot force but that natural network congestion or an attacker deliberately saturating a shard's gas budget (as the regression test itself does, using ordinary `FunctionCall` transactions) can reliably create.

### Recommendation
Extend `resolve_to_current_shard` for V0/V1/V2 layouts to walk the full historical layout chain (via `get_shard_layout_history`, already used elsewhere for exactly this purpose, e.g. `check_if_descendant_of_tracked_shard_impl`) rather than a single `get_children_shards_ids` hop, so that a `GlobalContractDistribution` (or any other receipt relying on `receiver_shard_id`) can always be remapped forward regardless of how many resharding generations it has been delayed across, matching the guarantee already provided for V3. Alternatively, gate any protocol path that can leave a chain on non-V3 shard layouts capable of multi-generation resharding behind the same completeness guarantee, or make `receiver_shard_id`'s failure mode recoverable (e.g., re-buffer/re-delay rather than propagate a hard `RuntimeError`).

### Proof of Concept
The existing regression test in the repository already demonstrates the mechanism end-to-end (deploy a global contract on a shard, saturate that shard's chunk gas budget so the resulting `GlobalContractDistribution` receipt is pushed to the delayed queue, force two consecutive shard splits while the receipt is delayed, then drain the queue and observe whether chain processing halts): [5](#0-4)  The test's own guard clause shows the fix is scoped to V3/`DynamicResharding` layouts only, leaving the analogous legacy-layout code path (`ShardLayout::V0/V1/V2` branch of `resolve_to_current_shard`) unverified against the identical multi-generation-drift scenario: [6](#0-5)

    /// Resolve any historical shard ID to a current descendant shard ID.
    /// For V3 layouts this uses the complete `shards_split_map`.
    /// For older layouts it falls back to `get_children_shards_ids` (single generation only).
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        match self {
            Self::V0(_) | Self::V1(_) | Self::V2(_) => {
                self.get_children_shards_ids(shard_id).map(|c| c[0])
            }
            Self::V3(v3) => v3.resolve_to_current_shard(shard_id),
        }
    }

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,
    receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
