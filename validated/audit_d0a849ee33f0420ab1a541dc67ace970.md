## Title
Sharded execution's total-supply override leaks the fictitious `TOTAL_SUPPLY_AGGR_BASE_VAL` into arbitrary committed resources and events, producing non-deterministic/divergent ledger state vs. sequential execution — (File: `aptos-move/aptos-vm/src/sharded_block_executor/aggr_overridden_state_view.rs`)

### Summary
`AggregatorOverriddenStateView::get_state_value` intercepts every read of `TOTAL_SUPPLY_STATE_KEY` during sharded sub-block execution and substitutes a fake constant, `TOTAL_SUPPLY_AGGR_BASE_VAL = u128::MAX >> 1`, so that per-shard total-supply deltas can be tracked independently and reconciled later. [1](#0-0)  The reconciliation step, `aggregate_and_update_total_supply`, only patches the write-op that is literally keyed by `TOTAL_SUPPLY_STATE_KEY` inside each `TransactionOutput`'s write set — it looks for and rewrites only `txn_output.write_set().get_total_supply()` / `update_total_supply()`. [2](#0-1)  `update_total_supply` itself operates only on the `TOTAL_SUPPLY_STATE_KEY` entry and asserts it must already exist. [3](#0-2) 

Nothing corrects any other write or event whose value was computed from the fictitious read. `TOTAL_SUPPLY_STATE_KEY` is not an opaque internal key — it is precisely the table item backing the AptosCoin `OptionalAggregatorV1Resource` that `coin::coin_supply<AptosCoin>()` reads via `optional_aggregator::read`. [4](#0-3)  Any unprivileged Move code (an entry function or script) can call this `#[view]`-style public function and copy the returned value into a user-defined resource field or emit it in an event.

### Finding Description
During sharded execution, `ShardedExecutorService::execute_transactions_with_dependencies` wraps the state view with `AggregatorOverriddenStateView` before handing it to `AptosVMBlockExecutorWrapper::execute_block`. [5](#0-4)  Every transaction executed in that sub-block that reads `TOTAL_SUPPLY_STATE_KEY` — directly or through `coin::coin_supply<AptosCoin>()`/`coin::supply<AptosCoin>()` — observes `TOTAL_SUPPLY_AGGR_BASE_VAL` instead of the real aggregated supply.

If such a transaction also writes that observed value into a resource other than the coin-supply table item itself (e.g. logs it to a custom module's storage, or emits it in an event), that write op / event is baked into the `TransactionOutput` exactly as computed by the VM from the fabricated value. The subsequent correction pass, `aggregate_and_update_total_supply`, walks every shard's outputs and rewrites only the entry matching `TOTAL_SUPPLY_STATE_KEY` via `get_total_supply()`/`update_total_supply()`. [6](#0-5)  It has no knowledge of, and never touches, any other write-op or any event, so the fabricated value is committed to storage verbatim.

The known limitation is explicitly acknowledged only for the `TOTAL_SUPPLY_STATE_KEY` entry itself — the sharded/unsharded comparison test filters exactly that table item out of comparison ("Global supply tracking for coin is not supported in sharded execution yet, so we filter out the table item from the write set") and skips full write-set equality checks. [7](#0-6)  This filtering does not, and cannot, cover collateral writes/events derived from reading that key, because those land under unrelated `StateKey`s.

A sequential (non-sharded) execution of the identical block would use the real, unmodified `StateView`, so the transaction would read the true total supply and commit the correct value into the same resource/event. Sharded execution therefore produces a `TransactionOutput` (and ultimately a committed `write_set`/`events`) that is inconsistent with what honest sequential execution — and thus what the canonical VM semantics — would produce for the same input block.

### Impact Explanation
This breaks the invariant that "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and that different execution strategies (sharded vs. sequential) must derive identical ledger state for the same block. Since sharded execution is a production code path (not merely a benchmarking harness) used to compute committed state, any block containing such a transaction would cause validators/executors using sharded execution to commit a different resource/event value than validators using sequential execution — a deterministic-execution divergence rooted entirely in unprivileged transaction content. This is a hard-fork-class inconsistency: the corrupted data (a fabricated near-`u128::MAX/2` "observed supply") is permanently written to the JMT/state and to the event stream, and is bound into the block's computed state root and transaction accumulator once committed.

### Likelihood Explanation
Trivial to trigger: any unprivileged account can publish a Move module (or, where scripts are permitted, submit a script) whose entry function calls `coin::coin_supply<AptosCoin>()` (or the underlying aggregator read) and stores the result in one of its own resources or emits it as an event. No special privileges, capabilities, or trusted operator behavior is required — only that the transaction be scheduled into sharded execution, which is determined solely by the block partitioner, not by the attacker.

### Recommendation
Extend `aggregate_and_update_total_supply` (or an equivalent post-processing pass) to detect and correct *every* write/event that was derived from a read of `TOTAL_SUPPLY_STATE_KEY` during sub-block execution, or — more robustly — implement genuine aggregated/cross-shard total-supply tracking so `AggregatorOverriddenStateView` never returns a fabricated value to transaction logic in the first place. At minimum, sharded execution should be disallowed/flagged unsafe for blocks containing transactions that read `TOTAL_SUPPLY_STATE_KEY` outside of the coin module's own supply-update paths, or the executor should track provenance of any value derived from the override and reject/re-execute such transactions sequentially.

### Proof of Concept
1. Deploy a Move module with an entry function:
   ```move

   public entry fun log_supply(account: &signer) {
   ```

2. Submit a block containing this transaction such that the block partitioner assigns it to a sharded sub-block (see `ShardedExecutorService::execute_sub_block`). [8](#0-7)

```rust
pub struct AggregatorOverriddenStateView<'a, S> {
    base_view: &'a S,
    total_supply_aggr_base_val: u128,
}

impl<'a, S: StateView + Sync + Send> AggregatorOverriddenStateView<'a, S> {
    pub fn new(base_view: &'a S, total_supply_aggr_base_val: u128) -> Self {
        Self {
            base_view,
            total_supply_aggr_base_val,
        }
    }

    fn total_supply_base_view_override(&self) -> Result<Option<StateValue>> {
        Ok(Some(StateValue::new_legacy(
            bcs::to_bytes(&self.total_supply_aggr_base_val)
                .unwrap()
                .into(),
        )))
    }
}

impl<S: StateView + Sync + Send> TStateView for AggregatorOverriddenStateView<'_, S> {
    type Key = StateKey;

            return self.total_supply_base_view_override();
        }
        self.base_view.get_state_value(state_key)
```

```rust
pub fn aggregate_and_update_total_supply<S: StateView>(
    sharded_output: &mut Vec<Vec<Vec<TransactionOutput>>>,
    global_output: &mut [TransactionOutput],
    state_view: &S,
    executor_thread_pool: Arc<rayon::ThreadPool>,
) {
    let num_shards = sharded_output.len();
    let num_rounds = sharded_output[0].len();

    // The first element is 0, which is the delta for shard 0 in round 0. +1 element will contain
    // the delta for the global shard
    let mut aggr_total_supply_delta = vec![DeltaU128::default(); num_shards * num_rounds + 1];

    // No need to parallelize this as the runtime is O(num_shards * num_rounds)
    // TODO: Get this from the individual shards while getting 'sharded_output'
    let mut aggr_ts_idx = 1;
    for round in 0..num_rounds {
        sharded_output.iter().for_each(|shard_output| {
            let mut curr_delta = DeltaU128::default();
            // Though we expect all the txn_outputs to have total_supply, there can be
            // exceptions like 'block meta' (first txn in the block) and 'chkpt info' (last txn
            // in the block) which may not have total supply. Hence we iterate till we find the
            // last txn with total supply.
            for txn in shard_output[round].iter().rev() {
                if let Some(last_txn_total_supply) = txn.write_set().get_total_supply() {
                    curr_delta =
                        DeltaU128::get_delta(last_txn_total_supply, TOTAL_SUPPLY_AGGR_BASE_VAL);
                    break;
                }
            }
            aggr_total_supply_delta[aggr_ts_idx] =
                curr_delta + aggr_total_supply_delta[aggr_ts_idx - 1];
            aggr_ts_idx += 1;
        });
    }

    // The txn_outputs contain 'txn_total_supply' with
    // 'CrossShardStateViewAggrOverride::total_supply_aggr_base_val' as the base value.
    // The actual 'total_supply_base_val' is in the state_view.
    // The 'delta' for the shard/round is in aggr_total_supply_delta[round * num_shards + shard_id + 1]
    // For every txn_output, we have to compute
    //      txn_total_supply = txn_total_supply - CrossShardStateViewAggrOverride::total_supply_aggr_base_val + total_supply_base_val + delta
    // While 'txn_total_supply' is u128, the intermediate computation can be negative. So we use
    // DeltaU128 to handle any intermediate underflow of u128.
    let total_supply_base_val: u128 = get_state_value(&TOTAL_SUPPLY_STATE_KEY, state_view).unwrap();
    let base_val_delta = DeltaU128::get_delta(total_supply_base_val, TOTAL_SUPPLY_AGGR_BASE_VAL);

    let aggr_total_supply_delta_ref = &aggr_total_supply_delta;
    // Runtime is O(num_txns), hence parallelized at the shard level and at the txns level.
    executor_thread_pool.scope(|_| {
        sharded_output
            .par_iter_mut()
            .enumerate()
            .for_each(|(shard_id, shard_output)| {
                for (round, txn_outputs) in shard_output.iter_mut().enumerate() {
                    let delta_for_round =
                        aggr_total_supply_delta_ref[round * num_shards + shard_id] + base_val_delta;
                    let num_txn_outputs = txn_outputs.len();
                    txn_outputs
                        .par_iter_mut()
                        .with_min_len(optimal_min_len(num_txn_outputs, 32))
                        .for_each(|txn_output| {
                            if let Some(txn_total_supply) =
                                txn_output.write_set().get_total_supply()
                            {
                                txn_output.update_total_supply(
                                    delta_for_round.add_delta(txn_total_supply),
                                );
                            }
                        });
                }
            });
    });

    let delta_for_global_shard = aggr_total_supply_delta[num_shards * num_rounds] + base_val_delta;
    let delta_for_global_shard_ref = &delta_for_global_shard;
    executor_thread_pool.scope(|_| {
        let num_txn_outputs = global_output.len();
        global_output
            .par_iter_mut()
            .with_min_len(optimal_min_len(num_txn_outputs, 32))
            .for_each(|txn_output| {
                if let Some(txn_total_supply) = txn_output.write_set().get_total_supply() {
                    txn_output.update_total_supply(
                        delta_for_global_shard_ref.add_delta(txn_total_supply),
                    );
                }
            });
    });
```
