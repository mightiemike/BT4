### Title
Relayer Deposit Theft via Deliberately Failing Inner Receipt in Meta-Transactions (`apply_delegate_action`) - (File: `runtime/runtime/src/actions.rs`)

---

### Summary

In NEAR's meta-transaction (`DelegateAction`) system, the relayer pays the deposit for inner actions, but on failure the deposit refund is sent to the **sender** (Alice), not the relayer. An unprivileged user can craft a `DelegateAction` with a large deposit attached to a deliberately failing inner action, causing the relayer to permanently lose the deposit while the sender gains it. This is the direct nearcore analog of the PromiseRouter griefing bug: a third-party executor (relayer) pays upfront, a user-controlled execution path fails, and the executor suffers an uncompensated financial loss.

---

### Finding Description

In `apply_delegate_action` (`runtime/runtime/src/actions.rs:456–469`), when a `DelegateAction` is processed on Alice's shard, a new inner receipt is constructed with:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice
    receiver_id: delegate_action.receiver_id().clone(),
    ...
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // ← Relayer
        ...
        actions: delegate_action.get_actions(),
    }),
});
``` [1](#0-0) 

The relayer's balance is charged for the full deposit at transaction submission time. The code comment at line 471–475 explicitly acknowledges the asymmetry:

> "If something goes wrong, deposit is refunded to the predecessor, this is `sender_id`/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer." [2](#0-1) 

When the inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` computes:

```rust
let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
```

and pushes:

```rust
result.new_receipts.push(Receipt::new_balance_refund(
    receipt.balance_refund_receiver(),  // ← predecessor_id = Alice
    deposit_refund,
));
``` [3](#0-2) 

`Receipt::new_balance_refund` sends the full deposit to `receiver_id = predecessor_id = Alice`: [4](#0-3) 

The protocol specification confirms this in `docs/RuntimeSpec/Refunds.md`:

> "Deposit refunds are generated when an action receipt fails to execute. All attached deposit amounts are summed together and sent as a refund to a `predecessor_id`." [5](#0-4) 

The architecture documentation explicitly acknowledges the financial attack surface in `docs/architecture/how/meta-tx.md`:

> "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [6](#0-5) 

---

### Impact Explanation

**Stealing of funds / balance manipulation.** The relayer pays deposit `D` upfront (deducted from the relayer's balance when the outer transaction is converted to a receipt). When the inner receipt fails, Alice receives `D` as a deposit refund. Net result: Alice `+D`, Relayer `−D`. The deposit amount is bounded only by the relayer's balance and the gas attached to the inner function call. There is no protocol-level cap preventing Alice from attaching an arbitrarily large deposit to a deliberately failing inner action.

---

### Likelihood Explanation

**Medium.** Two concrete trigger paths exist for an unprivileged user:

1. **Direct griefing**: Alice crafts a `DelegateAction` with a large deposit attached to a call to a non-existent method (or a method guaranteed to panic). A relayer that does not deeply simulate the inner execution before submission will lose the deposit.

2. **Front-running**: Alice crafts a `DelegateAction` that appears valid during off-chain simulation (e.g., calls `ft_transfer` with sufficient balance). After the relayer submits the outer transaction but before the inner receipt executes on the receiver's shard, Alice front-runs with a direct transaction that drains her FT balance, causing the inner receipt to fail. The deposit is then refunded to Alice, not the relayer.

The second path is the direct nearcore analog of the PromiseRouter front-running scenario: the relayer simulates successfully, submits, and is griefed by a state change between submission and execution.

---

### Recommendation

The root cause is that `apply_delegate_action` sets `predecessor_id: sender_id` on the inner receipt, making Alice the deposit-refund recipient even though the relayer paid the deposit. Two mitigations are possible:

1. **Protocol fix**: Change the inner receipt's `predecessor_id` to the relayer (`action_receipt.signer_id()`) so that deposit refunds on failure return to the party who paid them. This requires a protocol version gate.

2. **Relayer-side mitigation** (already recommended in docs but insufficient against front-running): Relayers should simulate the full inner execution before submission and reject meta-transactions with deposits unless the inner action is guaranteed to succeed. However, this cannot prevent front-running attacks.

Option 1 is the correct protocol-level fix, analogous to the `try/catch` recommendation in the PromiseRouter report.

---

### Proof of Concept

1. Alice creates a `DelegateAction`:
   - `sender_id`: Alice
   - `receiver_id`: `some_contract.near`
   - `actions`: `[FunctionCall { method_name: "non_existent", deposit: 1000 NEAR, gas: 30 TGas }]`
   - Signs with her full-access key

2. Alice sends the signed `DelegateAction` to a relayer off-chain.

3. Relayer wraps it in a transaction (relayer is signer, Alice is receiver), submits to the network. The relayer's balance is charged 1000 NEAR for the deposit.

4. On Alice's shard, `apply_delegate_action` creates the inner receipt with `predecessor_id = Alice`, `signer_id = Relayer`.

5. Inner receipt is routed to `some_contract.near`'s shard. The function call fails (`MethodNotFound`).

6. `refund_unspent_gas_and_deposits` generates a deposit-refund receipt of 1000 NEAR to `predecessor_id = Alice`.

7. Alice's balance increases by 1000 NEAR. Relayer's balance is permanently reduced by 1000 NEAR (gas refund goes to the relayer, but the deposit does not).

The attack is repeatable with no cost to Alice beyond signing a message off-chain.
