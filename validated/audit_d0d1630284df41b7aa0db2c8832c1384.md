### Title
Deletion of the protocol treasury (or a slashed/kicked-out validator) account permanently halts chunk application at every epoch boundary - (File: `runtime/runtime/src/lib.rs`)

### Summary
`Runtime::update_validator_accounts` credits epoch rewards to the protocol treasury account and to validators by directly mutating account state via `get_account`/`set_account`, using a *push* pattern analogous to `FeeSplitter.distributeFees`. Unlike a Solidity `safeTransfer` reverting on a blacklisted recipient, here the equivalent failure mode is that the target account no longer exists in state. If it doesn't exist, the function returns a fatal `Err(StorageError::StorageInconsistentState(...))`, which propagates out of `apply()`. Because this runs unconditionally on the first block of every epoch, once the treasury account is gone the chain can no longer produce a valid state transition for that shard at any future epoch boundary.

### Finding Description
`update_validator_accounts` in `runtime/runtime/src/lib.rs` loops over `validator_accounts_update.stake_info` and, separately, handles the protocol treasury account: [1](#0-0) 

```
if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
    if !validator_accounts_update.stake_info.contains_key(account_id) {
        let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Protocol treasury account {} is not found",
                account_id
            ))
        })?;
        ...
    }
}
```

If the protocol treasury account is not present in state, `get_account` returns `Ok(None)`, and `ok_or_else` converts this into `Err(StorageError::StorageInconsistentState(...))`. This is the exact analog of the reported bug: a single unreachable/removed recipient in a "push" distribution loop causes the entire distribution operation to fail — except that in nearcore this failure is a hard `RuntimeError` returned from `apply()` rather than a reverted contract call, and it is triggered every epoch (not just once), because reward distribution to the treasury happens unconditionally at every epoch boundary as documented: [2](#0-1) 

The treasury account is an ordinary NEAR account (e.g. `near`) that is expected to hold funds/keys like any other account, meaning its owner can delete it via a normal `DeleteAccount` transaction (an ordinary, unprivileged action reachable by any account holder with access to their own keys) — this is not a "malicious validator" or "operator" action, it is normal account-lifecycle behavior available to any account owner.

The same non-existence class of failure exists for validators in the `stake_info` loop: if a validator account was deleted (uninitialized-account exception aside, a normal deleted account triggers a similar fatal path at line 1796-1804 when `max_of_stakes > 0`), producing: [3](#0-2) 

### Impact Explanation
Because `update_validator_accounts` is invoked deterministically by every node applying the same epoch-boundary chunk, this is not a state-root divergence between honest nodes — every honest node computes the same fatal error and fails identically. That is precisely the "transaction-triggered halt" acceptance criterion: a normal, permissionless transaction (self-deleting one's own account, when that account happens to be configured as the protocol treasury, or a validator account being removed under specific circumstances) causes `apply()` to return an unrecoverable error at every subsequent epoch boundary for the shard hosting that account, since the treasury-crediting code path runs unconditionally each epoch. This can render the network permanently unable to produce valid new blocks/chunks, a full protocol-wide denial of service triggered by a single transaction.

### Likelihood Explanation
Likelihood is low-to-moderate in practice because the protocol treasury account is normally a foundation-controlled account not expected to self-delete, and deleting an active validator account through normal means is constrained by the stake-info bookkeeping (an active validator's `locked` balance generally prevents full deletion while staked). However, the bug class matches the report precisely: a "push"-style, unconditional per-recipient state mutation in a recurring system operation with no defensive check for recipient absence beyond raising a fatal, unrecoverable error rather than gracefully skipping/logging and continuing. This differs from a benign design choice only in that here the "abort" is a chain-halting error rather than a single reverted user transaction, making the impact category qualitatively worse than the original finding despite lower likelihood of the triggering precondition (treasury/validator account deletion).

### Recommendation
Treat missing treasury/validator accounts at the epoch boundary as a recoverable condition rather than a fatal `StorageInconsistentState` error — e.g., skip crediting (and log/metric) if the account cannot be found, or (preferably) make the protocol treasury account non-deletable / re-creatable automatically by the protocol so this state can never occur. At minimum, add explicit invariant checks/documentation ensuring the treasury account can never be deleted through ordinary `DeleteAccount` transactions, and add a regression test that deletes the configured `protocol_treasury_account` and asserts that epoch-boundary `apply()` still succeeds (crediting to a freshly-created account, similar to how the code already re-creates zero-balance accounts elsewhere) instead of returning a fatal, unrecoverable error.

### Proof of Concept
1. Configure a test genesis where `protocol_treasury_account` is a normal account with a full-access key (as in `test_validator_reward` at `chain/chain/src/runtime/tests.rs:1325`).
2. From that account, submit a `DeleteAccount` action transferring remaining balance to a beneficiary, removing the account from state.
3. Advance blocks until the next epoch boundary. `EpochManager`/`Chain` will call `Runtime::apply` with `ValidatorAccountsUpdate::protocol_treasury_account_id` set.
4. `update_validator_accounts` calls `get_account(state_update, account_id)` for the (now-deleted) treasury account, receives `Ok(None)`, and returns `Err(StorageError::StorageInconsistentState("Protocol treasury account ... is not found"))` (`runtime/runtime/src/lib.rs:1810-1815`).
5. `apply()` propagates this error; every node processing this chunk hits the identical error, and the shard cannot advance past this epoch boundary, resulting in a chain halt for all subsequent epochs.
