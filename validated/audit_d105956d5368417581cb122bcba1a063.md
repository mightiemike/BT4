### Title
Registered `liquidity_cap` on `TokenConfig` is never enforced during PRC20 minting, allowing unbounded unauthorized mint via ordinary inbound deposits - (File: x/uexecutor/keeper/handler.go)

### Summary
Push Chain's `uregistry` module defines a `liquidity_cap` field on every `TokenConfig`, intended as a per-token exposure ceiling on the amount of PRC20 that can be minted against a bridged asset — directly analogous to the Aave v2 "exposure ceiling" concept described in the external report. The field is validated only for non-emptiness at config-creation time, but is never read, parsed, or checked anywhere in the inbound execution/minting path, so the cap has no runtime effect.

### Finding Description
`TokenConfig.LiquidityCap` is defined in the registry schema as "max supply cap for this token" [1](#0-0) , and `ValidateBasic` only requires the string to be non-empty, never validating it as a number or checking it against any running total [2](#0-1) .

The inbound minting path (`ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` → `DerivedEVMCall("depositPRC20Token", ...)`) looks up the `TokenConfig` only to resolve the PRC20 contract address, and never reads or checks `LiquidityCap`: [3](#0-2)  and [4](#0-3) . The same is true for the funds-and-payload deposit path [5](#0-4)  and the gas-swap deposit path [6](#0-5) . The Solidity PRC20/handler contract source is not present in this scoped repository, so there is no evidence the cap is enforced on-chain at the contract level either.

Consequently, any number of validated, honestly-voted, legitimate inbound bridge deposits (ordinary user transactions on the source chain, requiring no privileged actor) can mint PRC20 supply on Push Chain far beyond the configured `liquidity_cap`, since the value is purely informational metadata in this codebase.

### Impact Explanation
This corrupts PRC20/native asset accounting: the registry-declared supply ceiling for a bridged asset is not a real constraint, so aggregate minted PRC20 supply can exceed the backing/exposure limit that `liquidity_cap` was meant to enforce. This falls under "corruption of PRC20 or native asset accounting" and "unauthorized mint" in the allowed impact set, since PRC20 continues to be minted past the point the protocol declared as its safety ceiling, with no unprivileged-only conditions violated to reach it (ordinary inbound deposits alone reach the unenforced mint path).

### Likelihood Explanation
High reachability: every inbound deposit — the most common, fully user-triggered flow (`VoteInbound` → ballot finalization → `ExecuteInboundFunds`) — passes through the unguarded mint path. No privileged action, malicious validator, or race condition is required; an ordinary user (or many independent users) repeatedly bridging the same asset can accumulate minted PRC20 past `liquidity_cap` purely through honest majority-voted inbound processing.

### Recommendation
Track cumulative minted PRC20 supply per token config (e.g., a running total in `uregistry` or `uexecutor` state, or a supply cap enforced by the PRC20 contract itself) and compare against `LiquidityCap` before calling `depositPRC20`/`CallPRC20Deposit`; reject or revert deposits that would breach the cap, mirroring the "set LTV to zero and block further collateral use" approach in the referenced Aave resolution, but here it should be "reject or revert further mints once the cap is met."

### Proof of Concept
1. Register a `TokenConfig` with `liquidity_cap = "1000000"` for asset `USDC` on `eip155:11155111` via `MsgAddTokenConfig`.
2. Submit and get quorum-voted `VoteInbound` for an `Inbound` of `TxType_FUNDS` with `Amount = "1000000"` — deposit succeeds, PRC20 minted = 1,000,000, exactly at cap.
3. Submit and get quorum-voted a second `Inbound` (different `tx_hash`) with `Amount = "1000000"` for the same token/chain.
4. Observe `ExecuteInboundFunds` → `depositPRC20` succeeds again with `Status = "SUCCESS"` and PRC20 balance for the recipient increases further, exceeding `liquidity_cap` — because `depositPRC20` (`x/uexecutor/keeper/handler.go`) never reads or checks `LiquidityCap` from the resolved `TokenConfig`.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens with auto-swap.
// fee and minPCOut must be pre-computed by the caller (see GetDefaultFeeTierForToken / GetSwapQuote).
func (k Keeper) CallPRC20DepositAutoSwap(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount, fee, minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: depositPRC20WithAutoSwap",
		"prc20", prc20Address.Hex(),
		"recipient", to.Hex(),
		"amount", amount.String(),
		"fee", fee.String(),
		"min_pc_out", minPCOut.String(),
	)
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // who is sending the transaction
		handlerAddr,        // destination: Handler contract
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20WithAutoSwap",
		prc20Address,
		amount,
		to,
		fee,
		minPCOut,
		big.NewInt(0), // deadline = 0 → contract uses its default
	)
}
