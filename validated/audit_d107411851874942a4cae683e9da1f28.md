## Title
Replay/proof verification silently accepts a corrupted state-checkpoint root - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the check used to confirm that a re-executed `TransactionOutput` matches a persisted/authenticated `TransactionInfo`. It validates status, gas used, write-set hash, and event root hash, but it never checks `state_checkpoint_hash` (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`). This mirrors the GMX bug class: a value that is supposed to fully account for a committed quantity (here, the full set of fields binding output to committed ledger state) instead only covers a subset, silently dropping the most safety-critical portion — the state root itself.

## Finding Description
`ensure_match_transaction_info` is defined at `types/src/transaction/mod.rs` (lines 2139-2204). It checks:
- `status()` against `txn_info.status()` [1](#0-0) 
- `gas_used()` against `txn_info.gas_used()` [2](#0-1) 
- `write_set_hash` (`state_change_hash`) against `txn_info.state_change_hash()` [3](#0-2) 
- `event_root_hash` against `txn_info.event_root_hash()` [4](#0-3) 

It never compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against anything computed locally. The code even self-documents this gap:

"TODO(trading-native): this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [5](#0-4) 

This function is used as the ground-truth match check in at least three tooling call sites: `aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `execution/executor/src/chunk_executor/mod.rs`. The `state_checkpoint_hash` field is precisely the value that authenticates the Sparse-Merkle/Jellyfish state root for a version — the field a light client, replay tool, or state-proof consumer relies on to be sure the reconstructed state tree is the one actually committed to the ledger. Since `state_change_hash` (write-set hash) only proves the write set is byte-identical, and does not prove the resulting Merkle root over the *entire* state tree is correct (that requires successfully applying the write set to the correct base state and recomputing the tree), a divergence in the state Merkle root construction (e.g. from a base-state bug, a JMT/SMT construction bug, or a maliciously/erroneously altered snapshot in the underlying store used during replay) would not be caught by this comparator.

## Impact Explanation
Any code path (documented callers include CLI transaction execution/verification, the Aptos debugger's re-execution-comparison utility, and the chunk executor) that relies on `ensure_match_transaction_info` as its sole match check will treat a transaction whose committed state root has silently diverged as "matching," because state/hot-state/position state checkpoint hashes are excluded from the comparison. This directly violates the "Proof And Storage Pivots" requirement that "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and that authenticated output "must stay bound to the right ledger version, root, and object." A wrong state root accepted as valid during replay/verification is exactly the "committed state that differs from the correct VM result" class called out in the State-Integrity Gate, because such tooling is one of the mechanisms operators and auditors use to detect state divergence/corruption after the fact — and it will not fire even though the actual committed value in the row is wrong.

## Likelihood Explanation
This is a real, currently present code path (not test-only), and the comment in the code confirms the authors are aware the check is incomplete and that it can already mask divergence for `position_state_checkpoint_hash`. However, the same comparator's omission of the ordinary `state_checkpoint_hash` (not just the position-native one) is not gated behind an unreleased feature flag — it is unconditionally skipped for every call, in existing production code paths (`chunk_executor/mod.rs`, `aptos-debugger`, `cli/commands.rs`). This makes it a live, exploitable *silent-verification-gap* whenever a state-tree/root discrepancy independently arises upstream (e.g., data corruption in the replay source, a subtle JMT bug, or a bug in whichever component recomputes state during replay) — it just means such an independent divergence would go undetected rather than being reported.

## Recommendation
Extend `ensure_match_transaction_info` (or its callers) to additionally verify `state_checkpoint_hash` (and, once relevant, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against a locally recomputed state-tree root whenever that information is available to the caller, rather than only comparing the write-set hash and event root. At minimum, emit a hard error (not just a comment/TODO) if a caller attempts to rely on this function as a full state-integrity check while state checkpoint hashes are known but unchecked.

## Proof of Concept
Not independently exploitable as a standalone PoC without a companion bug that produces a wrong state-tree root during replay; this finding documents the missing bound/check rather than an actively wrong computed value. A concrete demonstration would require: (1) a transaction that is a state-checkpoint boundary, (2) a replay/verification run whose reconstructed state tree root differs from the persisted `state_checkpoint_hash` in `TransactionInfo` due to any independent divergence, and (3) confirming `ensure_match_transaction_info` returns `Ok(())` in that case because it never reads `state_checkpoint_hash()` at all — visible directly by inspection of the field list compared at [6](#0-5) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
