### Title
Unbounded growth of a victim's `DelegatedResourceAccountIndex` (from/toAccounts) list has no `maxVouchers`-style cap, enabling storage/DoS via `GetDelegatedResourceAccountIndex(V2)` RPC - ([File: chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java])

### Summary
This is the java-tron analog of the Union Finance `updateTrust()` bug: one side of a bidirectional relationship enforces no growth limit while the "voucher"-equivalent side does. When account A delegates bandwidth/energy resources to account B via `DelegateResourceContract`/legacy `FreezeBalanceContract`, the framework unconditionally appends an entry to the **receiver's** `DelegatedResourceAccountIndexCapsule` (`fromAccounts`/`toAccounts` list) with no bound check, symmetrical to how `vouchers[borrower]` was pushed to without checking `maxVouchers` while `vouchees[staker]` was checked.

### Finding Description
In `DelegateResourceActuator.delegateResource()` the code calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, ...)`, which in turn does: [1](#0-0) 
```
public void delegateV2(byte[] from, byte[] to, long time) {
  ...
  DelegatedResourceAccountIndexCapsule toIndexCapsule =
      new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
  toIndexCapsule.setTimestamp(time);
  this.put(fromKey, toIndexCapsule);
  ...
  DelegatedResourceAccountIndexCapsule fromIndexCapsule =
      new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
  fromIndexCapsule.setTimestamp(time);
  this.put(toKey, fromIndexCapsule);
}
```
For the legacy (`FreezeBalanceActuator`) path, the append is explicit and unconditional on the receiver's side: [2](#0-1) 
```
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(...)) { ownerIndexCapsule.addToAccount(...); }
...
List<ByteString> fromAccountsList = receiverIndexCapsule.getFromAccountsList();
if (!fromAccountsList.contains(ByteString.copyFrom(ownerAddress))) {
  receiverIndexCapsule.addFromAccount(ByteString.copyFrom(ownerAddress));
}
```
This is precisely the bug pattern in the report: the **sender's** own list append is naturally bounded by the sender's own transaction volume/fees (analogous to `vouchees` being checked), while the **receiver's** list (`fromAccounts` for the target of a delegation) grows purely at the discretion of anyone sending them a ≥1 TRX delegation, with **no `maxVouchers`-equivalent cap** anywhere in `DelegateResourceActuator.validate()` or `FreezeBalanceActuator.validate()`. I confirmed via `grep_search` that neither `DelegatedResourceAccountIndexStore`, `DelegatedResourceAccountIndexCapsule`, `DelegateResourceActuator`, nor `FreezeBalanceActuator` contains any `MAX`/size-limit check on `getFromAccountsList()`/`getToAccountsList()`.

The victim account cannot refuse or block a delegation being sent to it — `DelegateResourceContract.validate()` only checks the sender's own balance/lock-period constraints and that the receiver is not a contract address: [3](#0-2) [4](#0-3) 
— it does not check any size of the receiver's inbound index list.

This inflated per-account index is then read back in full (no pagination) by the anonymous RPC/HTTP/gRPC endpoint `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2`: [5](#0-4) 
which is exposed unauthenticated via `RpcApiService`, `RpcApiServiceOnSolidity`, and HTTP servlets such as `GetDelegatedResourceAccountIndexServlet`: [6](#0-5) [7](#0-6) 

Additionally, `getWithPrefix()` in `DelegatedResourceAccountIndexStore` performs a full prefix scan and sort over the unbounded list when serving the legacy (non-V2) index query: [8](#0-7) 

### Impact Explanation
An attacker with only trivial funds can repeatedly send `DelegateResourceContract` transactions of the minimum 1 TRX each (each transaction is individually cheap and fee-free per `calcFee() == 0`) targeting a single victim address as receiver, from many distinct sender addresses (or the same sender delegating to many receivers is symmetric — but crucially, the victim has no way to prevent being targeted). This grows the victim's `fromAccounts`/`toAccounts` protobuf list without bound. Any node serving `GetDelegatedResourceAccountIndex(V2)` for that address (an unauthenticated RPC/HTTP call) then has to deserialize, and for the legacy path, prefix-scan and sort, the entire unbounded list on every single query — leading to a CPU/DoS amplification and potentially large response payloads (bandwidth exhaustion) for full/solidity/PBFT nodes that expose this endpoint. This matches "DoS via RPC-API or protocol implementation" per validation criteria.

### Likelihood Explanation
Likelihood is moderate-to-high: `DelegateResourceContract` is a normal, permissionless broadcast transaction type (not privileged), costs no fee (`calcFee()` returns 0, only bandwidth/energy of the sender is consumed), and requires only 1 TRX of frozen balance per delegation. An attacker can create many throwaway accounts each freezing the minimum amount and delegating to the same victim, incrementally growing the victim's index across many blocks over time with low cost. The read side (`GetDelegatedResourceAccountIndex`) is available with no authentication and no pagination.

### Recommendation
Add an explicit maximum-size check analogous to `maxVouchers` for both `fromAccounts` and `toAccounts` growth in `DelegatedResourceAccountIndexCapsule`, enforced in the actuator/native-contract validate() paths (`DelegateResourceActuator.validate()`, `FreezeBalanceActuator.validate()`, and the corresponding `DelegateResourceProcessor`/native-contract validate for TVM-triggered delegation) before appending to the *receiver's* index, e.g.:
```java
if (receiverIndexCapsule.getFromAccountsList().size() >= MAX_DELEGATE_INDEX_SIZE) {
  throw new ContractValidateException("receiver's delegated resource index list is too long");
}
```
Additionally, consider paginating `GetDelegatedResourceAccountIndex`/`V2` responses and avoiding full prefix scans/sorts on every query.

### Proof of Concept
1. Attacker creates N throwaway accounts, each freezing the minimum required balance for `FreezeBalanceV2Contract`/enough to satisfy `DelegateResourceContract`'s `delegateBalance >= 1 TRX` check (`actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java:148-150`).
2. Each account broadcasts a `DelegateResourceContract` (BANDWIDTH or ENERGY) with the same `receiverAddress` = victim's address. `validate()` never inspects the victim's existing index size (`DelegateResourceActuator.java:101-249`), so all N transactions succeed.
3. Each execution calls `delegatedResourceAccountIndexStore.delegateV2(owner, receiver, ts)` (`DelegateResourceActuator.java:314-315` → `DelegatedResourceAccountIndexStore.java:77-89`), unconditionally growing the victim's `fromAccounts` list by one entry per transaction — with no upper bound.
4. After sufficiently many such transactions (e.g., tens of thousands, spread across blocks to respect bandwidth/energy limits per account), any client calls the public `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` RPC or HTTP endpoint against the victim's address (`framework/src/main/java/org/tron/core/services/http/GetDelegatedResourceAccountIndexServlet.java:58-67`, `framework/src/main/java/org/tron/core/services/RpcApiService.java:528-538`), causing the serving node to deserialize/scan/sort/return the massively bloated list on every request.

Note: I could not directly confirm from the index alone whether any global rate limiter or protobuf message-size cap on the node's gRPC/HTTP layer would truncate this before it becomes a severe DoS (e.g., default gRPC max message size settings) — that would require testing against a running node, which is outside what I can verify from static code search alone.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());

    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());

    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
