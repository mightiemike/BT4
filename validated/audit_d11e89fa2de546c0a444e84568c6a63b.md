The `Arbitrary` derive on `ValidatorConfig` is compile-time gated behind `cfg_attr(any(test, feature = "fuzzing"), derive(Arbitrary))` [1](#0-0) , and the `proptest_derive::Arbitrary` import is likewise gated by `#[cfg(any(test, feature = "fuzzing"))]` [2](#0-1) .

This does not constitute an exploitable state-integrity issue:

1. **No unprivileged input path exists.** The `Arbitrary` trait implementation is purely a compile-time-conditional trait impl used by property-based test frameworks (`proptest`) to generate randomized test instances. It is never invoked from any transaction execution, commit, or proof-verification code path — those paths only ever construct `ValidatorConfig` via `ValidatorConfig::new` [3](#0-2)  or by deserializing real Move resource data through `MoveResource`/`Deserialize` [4](#0-3) . Even if the trait were compiled in, nothing in production code calls `ValidatorConfig::arbitrary()`.

2. **Feature-unification concern is a build-configuration issue, not a code vulnerability.** Cargo feature unification could theoretically cause the `fuzzing` feature to be enabled in a workspace build if some other crate in the dependency graph enables it, but this depends entirely on the build/release process choices (a trusted operator/CI decision about which crates and features to compile), not on unprivileged transaction, package, API, view, bytecode, or proof input as required by the scope rules. There is no code path by which live transaction, state, or proof data would reach the `Arbitrary` implementation, so no committed state, proof, or authenticated response can be corrupted by it.

3. The review scope explicitly excludes findings that "depends on trusted operator mistakes alone" — accidental feature-flag leakage during a release build is exactly this category, not a code-level flaw with a real, exploitable input path.
