## Title
Vault accrual checkpoint (`last-update`) only advances when the index actually changes value, letting a rate spike be retroactively applied over an entire dormant period — ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

## Summary
Each vault (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`) tracks accrual progress with a `last-update` timestamp, but this "clock" is only advanced when the freshly computed borrow/liquidity index differs from the currently stored one, not unconditionally whenever `accrue()` runs. During periods of low utilization the multiplier computed from elapsed time rounds to exactly `INDEX-PRECISION`, so the index never changes and `last-update` freezes while real time keeps passing. When utilization is later spiked (even for a single block), the interest rate computed at that moment is applied over the *entire* frozen time-delta, inflating the index far beyond what actually accrued.

**Sequence:**
1. During a "drought" of vault activity (near-zero utilization, or a rate small enough that `mul-div-down(rate * time-delta * INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` floors to `0`), every call to `accrue()` computes `next == idx` and `nliq == lidx`. The `is-eq` check at `v0-vault-usdc.clar#L849-863` never fires, so `last-update` is never bumped, even though `accrue()` is being invoked repeatedly through routine `deposit`/`redeem`/`system-borrow` calls.
2. `stacks-block-time - last-update` (the value bound) keeps growing silently while the on-chain `index`/`lindex` stay flat — this is the event that later gets misused: the checkpoint (the "clock") has stopped advancing even though the real gap is growing.
3. In a single transaction, an actor spikes `utilization()` momentarily (e.g., large `system-borrow` or a liquidity withdrawal that reduces `get-available-assets`), which pushes `interest-rate()`/`calc-liquidity-rate` to a much higher value for that one block.
4. The same or an immediately following transaction triggers `accrue()`. `next-index`/`next-liquidity-index` now compute `time-delta = block.timestamp - last-update` — the entire stale drought period — and multiply it by the *momentary* elevated rate via `calc-multiplier-delta`, instead of the near-zero rate that actually prevailed for almost the whole gap.
5. `calc-index-next` applies this single-block rate compounded over the whole drought window, instantly and massively inflating both the borrow index (`idx`, used by `calc-cumulative-debt` for every open borrower) and the liquidity index (`lindex`, used for zToken redemption value in `convert-to-assets-preview`).
6. Anyone holding vault shares (including the attacker) can immediately `redeem` at the artificially inflated `lindex`, extracting yield that was never actually earned proportionally to the real time-weighted utilization/rate history — the value bound (`last-update`) was invalidated by an event (a rate spike) it was never reset for, and the later use (applying the current rate across the *whole* stale gap) is exactly the "clock advanced only on change" pattern called out as in-scope.

## Impact Explanation
This lets vault-share holders extract undeserved yield/interest by manufacturing (or opportunistically timing around) a rate spike after a period during which the checkpoint failed to advance, while simultaneously forcing all outstanding borrowers' debt to jump by the same manipulated multiplier — interest is realized and can be immediately redeemed that was never actually accrued over the elapsed calendar time. This matches "theft of unclaimed yield," a High severity impact.

## Likelihood Explanation
The precondition (a stretch of low/near-zero utilization long enough that the per-call multiplier rounds to no change) is a normal, expected market condition for any of the six vaults, not an artificial one. Timing a utilization spike into the accrual immediately after such a period is achievable within an attacker-controlled transaction (borrow/withdraw then trigger `accrue`), requiring no privileged access, oracle compromise, or DAO action.

## Recommendation
Decouple the checkpoint timestamp from whether the index value happened to change: update `last-update` to `stacks-block-time` unconditionally on every successful (non-paused) `accrue()` call, regardless of whether `idx`/`lindex` moved. This bounds the maximum "stale rate window" to the interval between actual `accrue()` invocations rather than to the interval between index-value changes, preventing a single momentary rate from being retroactively compounded across an arbitrarily long dormant period.

## Proof of Concept
1. Deposit into `v0-vault-usdc` and drive utilization to a level where the interpolated rate is low enough that `calc-multiplier-delta` rounds to `INDEX-PRECISION` for typical inter-block time deltas (`v0-vault-usdc.clar#L164-179`).
2. Let real time pass (e.g., days) while occasionally calling any vault-touching entry point (`deposit`, `redeem`, `system-borrow`) — each call recomputes `next-index`/`next-liquidity-index` equal to the stored values, so `last-update` never advances (`v0-vault-usdc.clar#L849-863`).
3. In one transaction, take a large `system-borrow` (or otherwise reduce `get-available-assets`) to spike `utilization()` and thus `interest-rate()`/`calc-liquidity-rate` for the current block.
4. Immediately trigger `accrue()` again (e.g., via `deposit` or `redeem`): `time-delta = stacks-block-time - last-update` now spans the entire multi-day drought, and `calc-multiplier-delta` applies the spiked rate over that whole span, jumping `index`/`lindex` far beyond the interest that actually accrued.
5. `redeem` existing zUSDC shares at the now-inflated `lindex` via `convert-to-assets-preview`, extracting underlying USDC in excess of the yield genuinely earned, while every existing borrower's debt (via `calc-cumulative-debt`) has simultaneously spiked by the same manipulated multiplier.
