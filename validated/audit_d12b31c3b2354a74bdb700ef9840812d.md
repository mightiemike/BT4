### Title
`load_accounts_index_for_shrink`'s per-account index scan cost scales with total historical rewrite count (ref_count/slot_list length) rather than final storage footprint, because shrink runs much more frequently than clean - (File: accounts-db/src/accounts_db.rs)

### Summary
`load_accounts_index_for_shrink` calls `self.accounts_index.scan(...)` for every candidate account in a shrinking storage, and for each pubkey the callback iterates the account's full `slot_list` to determine aliveness via `slot_list.iter().any(|(slot, _)| *slot == slot_to_shrink)` [2](#0-1) . If a pubkey has been rewritten across `K` distinct slots without an intervening `clean_accounts` pass, its `ref_count` and `slot_list.len()` are `O(K)`, making this per-account check `O(K)` rather than `O(1)`. Because `SHRINK_INTERVAL` (1s) is far shorter than `CLEAN_INTERVAL` (50s) in the background service loop [1](#0-0) , shrink passes can repeatedly touch the same inflated `slot_list` many times before clean ever prunes it.

### Finding Description
`load_accounts_index_for_shrink` is invoked from `shrink_collect` for every storage being shrunk, once per storage's stored accounts, via `stored_accounts.par_chunks(SHRINK_COLLECT_CHUNK_SIZE)` calling `self.load_accounts_index_for_shrink(stored_accounts, stats, slot)` [3](#0-2) . Inside, `accounts_index.scan` is called with the pubkeys of the storage's accounts, and for each pubkey with `Some((slot_list, ref_count))` returned, the code executes `slot_list.iter().any(...)` to verify aliveness at `slot_to_shrink`, an `O(slot_list.len())` operation [2](#0-1) . `AccountsIndex::scan` itself does no truncation of the slot list before invoking the callback — it hands the full `slot_list` reference straight through [4](#0-3) .

An attacker who repeatedly rewrites the same pubkey across `K` distinct rooted slots (`store_for_tests` + `add_root_and_flush_write_cache` per slot) inflates `ref_count` to `K` and `slot_list.len()` to `K`, since these are only reduced when `clean_accounts` runs and purges old rooted entries [5](#0-4) . Every one of the (up to `K`) storages containing this pubkey is independently eligible for `shrink_candidate_slots`, and each shrink pass over any of them performs an `O(K)` scan for this single account. Because the background service's shrink loop (`SHRINK_INTERVAL` = 1s) runs 50x more frequently than the clean loop (`CLEAN_INTERVAL` = 50s) [1](#0-0) , many shrink cycles can elapse against the same bloated `slot_list` before a `clean_accounts` pass prunes it back to length 1, so cost is not simply "linear in K, paid once" — it can be re-paid on every shrink cycle within that 50-second window, for every one of the K storages, i.e. up to `O(K)` work times `O(shrink cycles in the window)` times `O(K storages)`.

### Impact Explanation
This matches the "unprivileged attacker causing disproportionate CPU work" category: shrink cost for a fixed final account state (1 pubkey, small final footprint) scales with the historical number of rewrites `K`, not the final storage size, and can be paid repeatedly across multiple shrink cycles per clean interval. This is a CPU-exhaustion amplification in the shrink pass, scoped exactly to `load_accounts_index_for_shrink` as named in the question.

### Likelihood Explanation
Feasible with only normal transaction fees: an attacker pays for `K` write transactions to the same account across `K` slots, each of which must be flushed to storage (rooted + `add_root_and_flush_write_cache`). No special privileges are required; `shrink_ratio` defaults are typically satisfied naturally by any modest garbage ratio, and the 50x mismatch between shrink and clean interval is a fixed constant in the current code, not something requiring special config. However, the actual amplification factor is bounded by how many shrink cycles occur within one clean interval and by `should_not_shrink` gating (a storage isn't re-shrunk unless it's re-added as a shrink candidate), so the practical multiplier, while real, is bounded rather than unbounded/quadratic-without-limit.

### Recommendation
Either (a) reduce the `CLEAN_INTERVAL`/`SHRINK_INTERVAL` disparity so clean runs proactively before/alongside shrink for hot slots with abnormal ref counts, or (b) short-circuit `load_accounts_index_for_shrink`'s aliveness check to avoid a full `O(slot_list.len())` scan — e.g., cache/hint the last-known-alive index or bound `slot_list` iteration by using `ScanFilter::OnlyAbnormal`-aware fast paths that don't require linear re-verification on each shrink pass. Additionally, consider triggering an on-demand partial clean for candidates whose `ref_count` exceeds a threshold before queuing them for shrink.
