Based on my investigation, the ERC-20 emulation in the Wallet Contract explicitly reads the raw `u128` value from an `ERC20_TRANSFER_SELECTOR` calldata and forwards it verbatim as the `amount` argument to `ft_transfer` on the target NEP-141 contract, with no decimals normalization or validation at all.

### Title
Wallet Contract ERC-20 emulation forwards raw transfer amount without accounting for NEP-141 token decimals - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/eth_emulation.rs)

### Summary
The reported bug class is: a DeFi component computes/normalizes value assuming two tokens share the same decimals, when in fact decimals can differ, producing an incorrect calculation. The nearcore analog is in the Wallet Contract's Ethereum ERC-20 emulation layer, which translates an Ethereum `transfer(address,uint256)` call into a NEP-141 `ft_transfer` call by taking the raw `uint256 value` field and passing it straight through as the NEP-141 `amount` (a `u128`), with no knowledge of, or adjustment for, the actual `ft_metadata().decimals` of the target NEP-141 token.

### Finding Description
In `eth_emulation.rs`, the `ERC20_TRANSFER_SELECTOR` branch of `try_emulation` does: [1](#0-0) 

The comment even flags the core assumption: "We intentionally map to `u128` instead of `U256` because the NEP-141 standard is to use `u128`" — but nowhere is the token's `decimals` metadata consulted or the incoming `value` scaled. The raw `uint256` from the Ethereum-side transaction is used verbatim as the NEP-141 `amount` string embedded in the `ft_transfer` args: [2](#0-1) 

This is architecturally the same flaw as the reported issue: the code assumes the Ethereum-side unit (typically an 18-decimal ERC-20 convention that Ethereum tooling/wallets will use when constructing the `value` field for a token they believe follows ERC-20 conventions) and the NEP-141 token's actual `ft_metadata().decimals` (which is fully controlled by the arbitrary token contract deployer and is NOT required to be 18, or even the same as any other NEP-141 token) are equivalent, when they are not. Unlike the base-token (`$NEAR`) transfer path, which has an explicit, well-documented decimal-conversion constant `MAX_YOCTO_NEAR = 1_000_000` to bridge the 24-decimal $NEAR vs 18-decimal $ETH difference: [3](#0-2) 
the ERC-20/NEP-141 emulation path performs no analogous conversion or decimals check whatsoever for arbitrary fungible tokens.

### Impact Explanation
Any unprivileged Ethereum-tooling user (using an ETH wallet/relayer against their ETH-implicit Wallet Contract account) who submits an `ERC20 transfer(to, value)` calldata against a NEP-141 token whose `decimals` differ from what the wallet/tooling assumes will have the raw numeric `value` field forwarded 1:1 as the `ft_transfer` `amount`. Because the transaction-construction tooling (MetaMask, ethers.js, etc.) scales user-facing amounts by the token's on-chain-reported ERC-20-style decimals (often assumed 18, or whatever the front-end configured), while the actual NEP-141 amount is interpreted in the token's own base units, a decimals mismatch causes the literal numeric amount transferred to be off by orders of magnitude from what the user intended (e.g., transferring 10^12 times too much or too little of the token). This can result in unintended large-value transfers (loss of funds for the sender) or unintended dust transfers, and is directly reachable by a normal transaction signer with no special privileges — it only requires them to be an ETH-implicit Wallet Contract holder interacting with any NEP-141 contract via the emulation path.

### Likelihood Explanation
High likelihood of being triggered accidentally by any user/tooling that assumes standard ERC-20 18-decimals semantics when constructing the emulated transfer value for an arbitrary NEP-141 token, since the Wallet Contract performs no decimals lookup, no decimals-equality assertion, and no scaling for the `ft_transfer` amount path. This is trivially reachable via a single `rlp_execute` call carrying an ERC-20-style `transfer` calldata, requiring no validator/network/leaked-key access — it is a standard, unprivileged user-facing operation intended precisely to be used this way (per the emulation design).

### Recommendation
Before emulating the `ERC20 transfer` into `ft_transfer`, query (or otherwise obtain trusted) the target NEP-141 contract's `ft_metadata().decimals` and either (a) require/verify the ERC-20-facing decimals declared/assumed by the relayer/wallet match the NEP-141 token's actual decimals, or (b) explicitly document that the raw NEP-141 `amount` unit (not an assumed 18-decimals value) must be supplied by the caller, and have the relayer-facing API/tooling perform the scaling transparently using the token's real decimals, analogous to the explicit `MAX_YOCTO_NEAR` handling used for the base-token path.

### Proof of Concept
1. An ETH-implicit account holder wants to transfer NEP-141 token `T` (decimals = 6, e.g. a USDC-like token) using standard Ethereum wallet tooling that assumes 18-decimal ERC-20 semantics for constructing `transfer(to, value)` calldata for "1.0" token, producing `value = 10^18`.
2. The signed Ethereum transaction is relayed via `rlp_execute` to the Wallet Contract.
3. `eth_emulation::try_emulation` matches `ERC20_TRANSFER_SELECTOR`, decodes `value` as raw `u128 = 10^18`, and builds `ft_transfer` args with `"amount": "1000000000000000000"` verbatim: [4](#0-3) 
4. Because token `T` only has 6 decimals, `10^18` base units is `10^12` whole tokens instead of the intended `1` token — a 10^12x overtransfer (or the reverse, drastic undertransfer, depending on which decimal assumption the tooling used), with no on-chain check preventing this mismatch.
