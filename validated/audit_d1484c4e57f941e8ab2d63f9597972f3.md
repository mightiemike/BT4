### Title
L1 handler transactions are marked as consumed even when execution fails due to an invalid/non-existent target contract address, permanently freezing the L1-to-L2 message - (File: crates/apollo_batcher/src/block_builder.rs, crates/blockifier/src/transaction/l1_handler_transaction.rs)

### Summary
The external report's bug class is: a value-moving operation trusts an unvalidated destination address, and even when that address does not correspond to an existing account, the operation still reports/records success, permanently losing the transferred value. The sequencer analog is in the L1 handler transaction path: `L1HandlerTransaction::execute_raw` in [1](#0-0)  attempts to invoke an entry point on `tx.contract_address` without first validating that the target contract actually exists/is deployed, via `Executable::run_execute` in [2](#0-1) . When the target address is invalid/non-existent, the execution errors out and the transaction is treated as reverted — but the batcher still records the transaction hash in `consumed_l1_handler_tx_hashes`, as demonstrated by the test `failed_l1_handler_transaction_consumed` in [3](#0-2) , where an L1 handler transaction that fails with `StateError::OutOfRangeContractAddress` is nonetheless included in `result_block_artifacts.execution_data.consumed_l1_handler_tx_hashes`.

### Finding Description
An L1-to-L2 message (`L1HandlerTransaction`) carries a `contract_address` field that is supplied by the L1 event (`LogMessageToL2`), i.e., it originates from an L1 message sender and is not guaranteed to correspond to a deployed L2 contract — the exact analog of the unvalidated `_smartWallet` address in the original report.

`Executable::run_execute` for `L1HandlerTransaction` does:
```
let storage_address = tx.contract_address;
let class_hash = state.get_class_hash_at(storage_address)?;
...
execute_call.non_reverting_execute(state, context, remaining_gas)...
``` [4](#0-3) 

There is no check that `storage_address` corresponds to a deployed/existing contract before attempting the call. If it does not exist, execution fails and the transaction is wrapped as a reverted L1 handler transaction in `execute_raw`:
```
Err(execution_error) => {
    execution_state.abort();
    let receipt = TransactionReceipt::reverted_l1_handler(&tx_context, l1_handler_payload_size);
    Ok(l1_handler_tx_execution_info(None, receipt, Some(...)))
}
``` [5](#0-4) 

Crucially, this reverted-but-`Ok`-returning result is still processed by the batcher/block builder as a transaction whose L1 message must be marked consumed. The regression test explicitly asserts this behavior: even when the mocked executor returns `Err(TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress))` for the first of two L1 handler transactions, both transaction hashes end up in `consumed_l1_handler_tx_hashes` [6](#0-5) . Per the documented flow, once a hash is placed in `consumed_l1_handler_tx_hashes` it is committed via `commit_block(consumed_txs, ...)` and the L1 Provider transitions the message from `Pending` to `Committed` , i.e., the L1 message is permanently marked as consumed on the Starknet side regardless of whether the target contract existed and could process it.

### Impact Explanation
Because the message is marked "consumed" even though the intended L2 contract never received/executed the deposit or handler logic, any value or state update the L1 message was meant to deliver (e.g., a bridged deposit crediting a specific L2 contract) is permanently lost from the L2 perspective — the message cannot be resent or reprocessed since the sequencer's bookkeeping considers it already handled. This is a concrete freezing-of-funds condition reachable purely by an L1 message targeting a non-existent (e.g., mistyped, not-yet-deployed, or already-removed) L2 contract address — no privileged or malicious actor is required, matching the "unprivileged... L1 message" reachability criterion.

### Likelihood Explanation
Likelihood is realistic: any L1 bridge or dApp contract that sends a `LogMessageToL2` event to an L2 address that has not yet been deployed, was miscalculated, or is otherwise wrong will trigger this exact path. Address typos, off-by-one salt/class-hash errors when precomputing counterfactual addresses, or race conditions between deployment and L1 message delivery are common in bridging/deposit flows, making this more than a purely theoretical edge case.

### Recommendation
Before treating an L1 handler transaction as consumed (i.e., before including its hash in `consumed_l1_handler_tx_hashes`), the batcher/blockifier should distinguish between "genuinely executed" reverts (where the target contract exists but its logic rejected the call) and structural failures such as calling a non-existent/undeployed contract address (`StateError::OutOfRangeContractAddress` or missing class hash). For the latter category, the L1 message should not be marked consumed, allowing it to remain pending (and thus cancellable/reprocessable on L1) rather than permanently and silently discarded.

### Proof of Concept
1. An L1 bridge contract sends a `LogMessageToL2` event whose `to_address` does not correspond to any deployed L2 contract (e.g., a typo'd address or an address for a contract that has not yet been deployed).
2. The L1 Scraper/Provider converts this into an `L1HandlerTransaction` and adds it to the transaction manager as proposable, per .
3. During block building, `Executable::run_execute` is called with `storage_address = tx.contract_address` [4](#0-3) ; since the contract is not deployed, execution fails (e.g., `StateError::OutOfRangeContractAddress`).
4. As shown by `failed_l1_handler_transaction_consumed` [3](#0-2) , the transaction hash is still added to `consumed_l1_handler_tx_hashes` and committed via `commit_block`, permanently marking the L1 message consumed even though the intended recipient never received the funds/data.

impl<S: State> Executable<S> for L1HandlerTransaction {
    fn run_execute(
        &self,
        state: &mut S,
        context: &mut EntryPointExecutionContext,
        remaining_gas: &mut u64,
    ) -> TransactionExecutionResult<Option<CallInfo>> {
        let tx = &self.tx;
        let storage_address = tx.contract_address;
        let class_hash = state.get_class_hash_at(storage_address)?;
        let selector = tx.entry_point_selector;
        let execute_call = CallEntryPoint {
            entry_point_type: EntryPointType::L1Handler,
            entry_point_selector: selector,
            calldata: Calldata(Arc::clone(&tx.calldata.0)),
            class_hash: None,
            code_address: None,
            storage_address,
            caller_address: ContractAddress::default(),
            call_type: CallType::Call,
            initial_gas: *remaining_gas,
        };

        execute_call.non_reverting_execute(state, context, remaining_gas).map(Some).map_err(
            |error| TransactionExecutionError::ExecutionError {
                error: Box::new(error),
                class_hash,
                storage_address,
                selector,
            },
        )
    }

async fn failed_l1_handler_transaction_consumed() {

    helper.expect_successful_get_new_results(0);

    helper.mock_transaction_executor.expect_close_block().times(1).return_once(|_| {
        Ok(BlockExecutionSummary {
            state_diff: Default::default(),
            compressed_state_diff: None,
            bouncer_weights: BouncerWeights::empty(),
            casm_hash_computation_data_sierra_gas: CasmHashComputationData::default(),
            casm_hash_computation_data_proving_gas: CasmHashComputationData::default(),

            block_info: BlockInfo::create_for_testing(),
        })
    });

    let (_abort_sender, abort_receiver) = tokio::sync::oneshot::channel();

}
