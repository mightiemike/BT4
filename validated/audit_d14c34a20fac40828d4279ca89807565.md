### Title
Free UEA payload execution via missing CacheContext rollback in the direct `MsgExecutePayload` path - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
The bug class in the Pyth report is: a function pays out value/executes a privileged action "on the caller's behalf" without verifying that the caller actually supplied (or will supply) the funds for it, so the protocol's own funds/pool absorb the cost. In Push Chain, the closest reachable analog is the gas-fee-payment guarantee around `DerivedEVMCall`-based UEA execution: the protocol (module account, no private key) always executes the EVM call first via `CallUEAExecutePayload`/`CallExecuteUniversalTx`, and only afterwards tries to collect the gas cost from the UEA owner via `DeductGasFeesFromReceipt`. If that collection fails, the EVM execution must be rolled back — otherwise the protocol/module has paid for (and materialized the effects of) an execution nobody funded.

### Finding Description
Three of the four call sites that follow this "execute-then-bill" pattern deliberately wrap the EVM call and the fee deduction in an `sdk.Context.CacheContext()` so both operations commit or discard together:

- `ExecutePayloadV2` in [1](#0-0) 
- The CEA/smart-contract branch of `ExecuteInboundFundsAndPayload` in [2](#0-1) 
- The CEA/smart-contract branch of `ExecuteInboundGasAndPayload` in [3](#0-2) 

The explicit comment on all three states the reason: *"closes the free-execution gap when the UEA has no native UPC to cover gas"* — confirming that without a `CacheContext`, a failed fee deduction leaves the already-executed EVM state changes standing, i.e. free execution.

The fourth site — `ExecutePayload` (non-`V2`), which is the function backing the actual `MsgExecutePayload` message (the gasless, callable-by-anyone entry point documented in `x/uexecutor/README.md`) — does **not** use a `CacheContext`: [4](#0-3) 

It calls `k.CallUEAExecutePayload(sdkCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)` directly against the live `sdkCtx`, then calls `DeductGasFeesFromReceipt`, relying only on a code comment ("If deduction fails, return error so the entire Cosmos tx rolls back (including EVM state)") rather than the explicit cache-and-discard mechanism used everywhere else this exact hazard was previously identified and fixed (the fix is referenced elsewhere as `F-2026-16738`, see [5](#0-4) ).

`ExecutePayloadV2` is only referenced from the inbound execution flows (`execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`); it is never invoked from `msg_server.go`, meaning the `MsgExecutePayload` message handler goes through the un-cached `ExecutePayload` function instead.

### Impact Explanation
`MsgExecutePayload` is a gasless, unprivileged, callable-by-anyone message (per `app/txpolicy/gasless.go` and `x/uexecutor/README.md`'s authorization model, `Signer != Owner` is intentionally allowed). If the assumption in the code comment is wrong — i.e., if the fork's `DerivedEVMCall(commit=true)` for a UEA-owned account persists state in a way not fully covered by standard Cosmos SDK per-message branch/discard semantics (exactly the scenario the sibling fix explicitly protects against) — then an attacker can:
1. Submit `MsgExecutePayload` targeting a UEA/UniversalAccountId with zero native `upc` balance.
2. `CallUEAExecutePayload` executes the payload for real (mutating EVM/contract state, potentially triggering outbound creation via `CreateUniversalTxFromReceiptIfOutbound`).
3. `DeductGasFeesFromReceipt` fails with insufficient balance.
4. If the underlying EVM state changes are not actually rolled back, the attacker obtained free, unauthorized module-subsidized EVM execution and possibly unauthorized state transitions/outbound creation without ever paying for it — a direct "market/module funds absorb the cost instead of the caller" analog to the Pyth bug.

This falls squarely under the in-scope category "unauthorized UEA or CEA execution, unauthorized module-originated EVM execution, or unauthorized state transitions in universal execution flows," triggered by an ordinary unprivileged user with no validator or admin collusion required.

### Likelihood Explanation
Medium confidence, not fully confirmed. The evidence is a strong structural inconsistency: the exact hazard was independently identified and fixed with `CacheContext` in three of four structurally identical call sites, with comments explicitly naming the failure mode, but the fourth (and most directly attacker-reachable, since it needs no validator votes) path relies on an unverified assumption about standard Cosmos SDK message-level atomicity being sufficient for the fork's `DerivedEVMCall`. I was unable to inspect the fork's (`github.com/pushchain/evm`) internal commit semantics for `DerivedEVMCall` to confirm whether returning an error from the `MsgServer.ExecutePayload` handler actually discards previously-committed EVM state, or whether the same "free-execution gap" that motivated the other three fixes also applies here. This should be verified against the actual behavior of `DerivedEVMCall(commit=true)` in the forked EVM module before concluding this is exploitable end-to-end.

### Recommendation
Wrap `CallUEAExecutePayload` and `DeductGasFeesFromReceipt` in `msg_execute_payload.go`'s `ExecutePayload` inside an `sdk.Context.CacheContext()`, identical to the pattern already used in `ExecutePayloadV2`, and only call `writeCache()` when both the EVM call and fee deduction succeed. Alternatively, consolidate by having `MsgServer.ExecutePayload` call `ExecutePayloadV2` instead of maintaining a second, divergent, un-cached implementation.

### Proof of Concept
Conceptual (not independently executed against a live fork build):
1. Deploy/derive a UEA for an attacker-controlled `UniversalAccountId` with zero `upc` balance.
2. Submit `MsgExecutePayload` (gasless, no Cosmos fee required) with a `UniversalPayload` whose execution has an observable side effect (e.g. a state-mutating call similar to the "stateful recipient" pattern used in `test/integration/uexecutor/inbound_cea_smart_contract_test.go`).
3. Observe whether `ExecutePayload` returns `"gas fee deduction failed"` while the EVM state mutation performed by `CallUEAExecutePayload` nonetheless persists (check via `EVMKeeper.GetState`/contract storage after the failed tx, analogous to the assertions in the cited integration test but pointed at the direct-message path instead of the inbound-vote path).

If the mutation is observed to persist despite the returned error, this confirms the free-execution vulnerability; if it is discarded automatically by Cosmos SDK's own message branching, this is a documentation/consistency issue rather than an exploitable one.

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}
