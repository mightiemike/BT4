### Title
Unbounded per-cycle reward computation loop can make legitimately earned voting rewards uneconomical/impossible to withdraw - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The Splitter/RoyaltyVault bug centers on a per-event "window" accounting design that forces reward recipients to perform many expensive, individually-claimed operations to recover economically small amounts, making claiming their earned fees uneconomical or effectively unrecoverable. java-tron's voting-reward system has an analogous design flaw in its legacy ("old") per-cycle reward computation path: `MortgageService.computeReward` / `getOldReward`, reachable from an ordinary, unprivileged `WithdrawBalanceContract` transaction, iterates once per un-withdrawn cycle (and once per vote within each cycle) rather than using an O(1) accumulator, so a voter who does not withdraw frequently can end up with a withdrawal whose cost/complexity scales with the number of skipped cycles.

### Finding Description
`MortgageService.withdrawReward()` and `queryReward()` compute a voter's/witness's un-withdrawn reward by calling `computeReward(beginCycle, endCycle, accountCapsule)`: [1](#0-0) 

When `beginCycle` predates the new reward algorithm's effective cycle, this delegates to `getOldReward`: [2](#0-1) 

If the fast Vi-accumulator path (`allowOldRewardOpt`) is not active, `getOldReward` falls back to iterating `cycle` from `begin` to `end` one at a time, and for *each* cycle it calls `computeReward(cycle, votes)`, which itself loops over every vote the account holds for that cycle: [3](#0-2) 

This is precisely the same anti-pattern flagged in the source report: instead of an O(1) or O(votes) claim mechanism, the code forces an O(cycles × votes) computation whenever a delayed claim is attempted. `WithdrawBalanceActuator.execute()` is invoked by any anonymous account broadcasting a plain `WithdrawBalanceContract` transaction and unconditionally calls `mortgageService.withdrawReward(...)`, so this expensive path is directly reachable by any user, with no privileged actor required: [4](#0-3) 

The same expensive path is also reachable from inside a smart contract via the TVM `withdrawReward` opcode, which calls `VoteRewardUtil.withdrawReward` → the same cycle-scanning reward computation, this time metered by energy and executed as part of block/transaction processing: [5](#0-4) [6](#0-5) 

Note that the modern, activated network uses a precomputed Vi accumulator (`RewardViCalService` / `DelegationStore.getWitnessVi`) which is the correct O(1)-per-vote design and mitigates this for cycles after the new-algorithm activation cycle: [7](#0-6) 
However, the legacy per-cycle loop path in `getOldReward` remains present in the code and is exercised whenever `allowOldRewardOpt` is not enabled and an account's `beginCycle` is older than `newRewardCalStartCycle` — i.e., whenever a voter accumulates a long backlog of un-withdrawn cycles under the old algorithm before that optimization flag is turned on by governance, or on any deployment/testnet where the optimization proposal has not (yet) been activated.

### Impact Explanation
A voter (or a smart contract account using the TVM vote/reward interface) who does not withdraw rewards for a long time can accumulate a very large `endCycle - beginCycle` range under the pre-optimization algorithm. When they finally call `withdrawReward`/`queryReward`, node execution time (and, for the TVM path, energy cost) scales linearly with the number of skipped cycles multiplied by the number of votes cast. This can:
- Make the reward economically unviable to claim (fee/energy cost exceeds the reward, mirroring the original report's core impact), and/or
- Cause the withdrawing transaction to fail (revert on out-of-energy for the TVM path) or take excessive wall-clock time to execute for ordinary (non-TVM) `WithdrawBalanceContract` transactions, effectively freezing the user's legitimately earned rewards and creating a minor processing-time DoS vector for block-producing nodes that must execute this actuator.

This matches the report's risk class: value leakage/uneconomical recovery of legitimately earned funds due to a poorly-bounded per-unit accounting design, translated to java-tron's voting reward subsystem.

### Likelihood Explanation
Reachability is straightforward and requires no privileged role: any account can vote for witnesses and simply refrain from withdrawing for a long period, then submit a normal `WithdrawBalanceContract` transaction. The severity is bounded by whether `allowOldRewardOpt`/the new reward algorithm effective cycle have been activated on a given network at the time the backlog is accumulated; on networks or historical periods where those governance flags are not yet set, the vulnerable code path is live and unconditionally exercised by ordinary users' withdraw transactions.

### Recommendation
Ensure the O(1)/O(votes) Vi-accumulator reward computation (`RewardViCalService`/`DelegationStore` witness-Vi mechanism) is the only reward computation path, retiring the legacy cycle-by-cycle `getOldReward` loop entirely (or bounding the number of cycles a single withdrawal transaction may span, forcing partial/incremental withdrawals with an efficient checkpoint instead of unbounded per-cycle iteration). At minimum, cap the maximum number of un-withdrawn cycles processable in a single transaction and/or backfill Vi values for pre-optimization cycles so `getOldReward`'s linear scan is never required at withdrawal time.

### Proof of Concept
1. Deploy/attach to a java-tron network where `allowOldRewardOpt` and the new-reward-algorithm activation cycle have not been set (or simulate a long pre-activation backlog), matching the setup in `DelegationServiceTest`/`VoteTest.testRewardAlgorithmBenchmark` which explicitly benchmarks this exact scenario (73,000 cycles) and measures the cost difference between the old and new algorithms: [8](#0-7) 
2. Have an account vote for one or more witnesses, then let many cycles pass without withdrawing (`beginCycle` stays far behind `currentCycle`).
3. Submit a `WithdrawBalanceContract` transaction (or invoke the TVM `withdrawReward` opcode from a contract) for that account.
4. Observe that `MortgageService.computeReward`/`getOldReward` iterates once per skipped cycle (times votes per cycle), causing computation cost/time (and TVM energy cost) to grow linearly with the un-withdrawn cycle count, as demonstrated by the benchmark test's explicit "Old-*" vs "New-*" timing comparison.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
