### Title
Proof "variant"/sub-image tag is not cryptographically bound into the verified proof output — analogous to missing sub-image-id binding in aggregation proof verification - ([File: crates/starknet_proof_verifier/src/proof_verifier.rs])

### Summary
`verify_proof` accepts `ProofFacts` of the form `[PROOF_VERSION, VARIANT, program_hash, ...task_output]` but only cryptographically binds `[program_hash, ...task_output]` (as `output_preimage`) to the STARK proof. The `VARIANT` felt at index 1 — which downstream Cairo code (`execution_constraints.cairo`) trusts as an authoritative discriminator of the proof's semantic type (`VIRTUAL_SNOS`) — is stripped out before being passed to the circuit verifier and is therefore never checked by the cryptographic proof itself. This is the same class of bug as the Taiko fix: an aggregation/recursive proof must bind a "sub image id" (a discriminator of which program/circuit produced a given sub-result) into what the proof actually attests to; omitting it lets a verified proof for one program/context be relabeled and accepted as valid for a different, unintended context.

### Finding Description
`starknet_proof_verifier::verify_proof` (`crates/starknet_proof_verifier/src/proof_verifier.rs:126-157`) computes `output_preimage` via `reconstruct_output_preimage` (`crates/starknet_proof_verifier/src/proof_verifier.rs:108-121`), which explicitly documents and implements: [1](#0-0) 

Note that it "Skip[s] PROOF_VERSION_V* (index 0) and variant (index 1)" and only feeds `task_content = proof_facts.0[2..]` (i.e. `program_hash` and the OS output) into the value that `privacy_circuit_verify_v1::verify_recursive_circuit` checks against the proof: [2](#0-1) 

Meanwhile, the Starknet OS trusts the `proof_variant` field (index 1 of `proof_facts`) as an authoritative claim about what kind of proof this is, gating protocol-level checks on it: [3](#0-2) 

Because the variant byte is excluded from the value actually committed to by the ZK circuit, a party can take any proof that is valid for a given `(program_hash, task_output)` pair and swap the `proof_variant` field to a different constant, and `verify_proof` will still accept it — the cryptographic check is agnostic to what "kind" of proof it's being presented as. This is structurally identical to the Taiko bug: the aggregation/recursion layer failed to bind a sub-component's declared image/program identity into what the proof cryptographically attests, allowing the identity tag to be forged independently of the underlying proof.

### Impact Explanation
Today only one variant constant (`VIRTUAL_SNOS`) is defined and referenced (`ALLOWED_VIRTUAL_OS_PROGRAM_HASHES_LEN == 1` in `execution_constraints.cairo`), which limits immediate exploitability. However, the verifier and proof-facts format are explicitly designed to be extensible to multiple proof variants/circuits (the `ProgramOutput::try_into_proof_facts` API takes an arbitrary `program_variant: Felt` parameter, and `ProofHeader`/`VirtualOsOutputHeader` in the Cairo layer are versioned structures meant to support future variants such as aggregator outputs vs. per-transaction virtual-OS outputs). As soon as a second variant is introduced (which the codebase's own design anticipates), an attacker submitting a client-side-proven `Invoke` transaction (`proof_facts`/`proof` fields, reachable through the gateway's `run_proof_verification` path in `crates/apollo_transaction_converter/src/transaction_converter.rs:395-424`) could relabel a validly-proved output from one program/variant as belonging to another, bypassing the variant-specific semantic checks performed by the OS (e.g. `assert proof_header.proof_variant = VIRTUAL_SNOS`) without needing a genuine proof for that variant. This could let an unprivileged transaction sender have the OS accept forged/misattributed proof semantics, corrupting execution results committed into the block (wrong committed state/root) — a Medium/High severity issue depending on how additional variants are wired in.

### Likelihood Explanation
Currently low-to-moderate: exploitation requires a second proof variant to exist so that a valid `(program_hash, task_output)` pair produced under one variant's intended semantics can be replayed under a different variant's proof-facts tag without needing a new circuit proof. The vulnerability is latent but structurally present now, since the binding gap exists in `reconstruct_output_preimage`/`verify_proof` regardless of how many variants are currently deployed, and is directly reachable by any transaction sender who can submit proof facts via the gateway's client-side-proving path.

### Recommendation
Include the `proof_variant` felt inside `output_preimage` (the value actually passed to `privacy_circuit_verify_v1::verify_recursive_circuit`) so the ZK circuit binds the claimed variant to the proof, mirroring how `program_hash` is bound today. Concretely, modify `reconstruct_output_preimage` in `crates/starknet_proof_verifier/src/proof_verifier.rs` to include `proof_facts.0[1]` (variant) as part of the committed preimage rather than skipping it, and update `ProgramOutput::try_into_proof_facts` / the bootloader-side aggregator format consistently so that any consumer relying on `proof_variant` (e.g. `execution_constraints.cairo`'s `check_proof_facts`) can trust that the field is cryptographically authenticated by the proof itself, not just a self-declared metadata tag.

### Proof of Concept
1. Obtain (or generate) a valid `(proof_facts, proof)` pair for `program_variant = VIRTUAL_SNOS` via the transaction prover, as in `crates/starknet_transaction_prover/src/proving/virtual_snos_prover_test.rs:298-334`.
2. Mutate only `proof_facts.0[1]` (the variant felt) to a different, hypothetical variant constant, leaving `proof_facts.0[2..]` (program hash + task output) and the `proof` bytes untouched.
3. Call `starknet_proof_verifier::verify_proof(mutated_proof_facts, proof)` — it still returns `Ok(())` because `reconstruct_output_preimage` (`crates/starknet_proof_verifier/src/proof_verifier.rs:108-121`) discards index 1 before constructing the value checked by the circuit, demonstrated by the existing regression test `verify_proof_rejects_tampered_proof_facts` (`crates/starknet_proof_verifier/src/proof_verifier_test.rs:149-158`) which only shows tampering at index 2 (program hash) is caught — there is no analogous test asserting that tampering index 1 (variant) is caught, confirming the field is unchecked by the cryptographic verification path.
