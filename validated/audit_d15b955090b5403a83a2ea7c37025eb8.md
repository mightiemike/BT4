### Title
Timing side-channel in OOBE Quick Start handshake authentication token comparison - (File: chrome/browser/ash/login/oobe_quick_start/connectivity/handshake_helpers.cc)

### Summary
`handshake::VerifyHandshakeMessage` in the Chrome OS OOBE Quick Start path compares the decrypted authentication token against the expected token using a non-constant-time `std::string` equality operator. This exposes a timing side-channel analogous to CVE-2024-7010, allowing a network-proximate attacker to iteratively guess the authentication token by observing response timing differences.

### Finding Description
In `chrome/browser/ash/login/oobe_quick_start/connectivity/handshake_helpers.cc`, after decrypting the `AuthenticationPayload`, the code validates the contained `auth_string` with:

```cpp
if (auth_payload->auth_string() != auth_token) {
  QS_LOG(ERROR)
      << "AuthenticationPayload auth_string does not match auth token.";
  return VerifyHandshakeMessageStatus::kUnexpectedAuthPayloadAuthToken;
}
``` [1](#0-0) 

This is a plain `std::string` inequality comparison. The C++ standard library's `std::string::operator!=` typically performs a short-circuiting byte-by-byte comparison, returning early on the first mismatch. The function then returns a distinct `kUnexpectedAuthPayloadAuthToken` status, which is propagated through `Connection::OnHandshakeResponse` and recorded in metrics before the callback runs. [2](#0-1) 

The authentication token is a bearer-style secret exchanged during the OOBE Quick Start phone-to-Chromebook setup flow. The handshake message is received over `NearbyConnection` (Bluetooth/BLE/WiFi hotspot transport) and processed in the browser process.

### Impact Explanation
A timing side-channel on the authentication token comparison can allow an attacker who can observe or influence response timings to recover the token one byte at a time. Because the comparison fails faster when the prefix is wrong, the attacker can brute-force the token with complexity linear in token length rather than exponential. Successful recovery of the token lets the attacker complete the Quick Start handshake and impersonate the legitimate source device, potentially leading to unauthorized account setup or device provisioning.

### Likelihood Explanation
The attack is reachable from a single network payload: the attacker sends crafted handshake messages to the target Chromebook's `NearbyConnection` endpoint and measures the time until the `kUnexpectedAuthPayloadAuthToken` response path is taken. The Quick Start flow is designed to be initiated by a nearby phone, so an attacker within Bluetooth/WiFi range can deliver these payloads without user interaction beyond the initial discovery phase. The token space is small enough (advertising ID / PIN-like code) that byte-by-byte timing recovery is practical.

### Recommendation
Replace the `std::string` comparison with a constant-time comparison helper. Chromium already provides `crypto::SecureMemEqual` (used elsewhere for password hash comparison, e.g. in `shared_session_handler.cc`): [3](#0-2) 

Convert both `auth_payload->auth_string()` and `auth_token` to `base::span<const uint8_t>` and compare with `crypto::SecureMemEqual`. Additionally, ensure the failure path does not branch on the comparison result in a way that leaks timing through logging or metrics ordering.

### Proof of Concept
An attacker within Nearby Connections range repeatedly sends handshake messages with a guessed `auth_string` prefix. Because `std::string::operator!=` exits at the first mismatched byte, messages with a longer correct prefix take measurably longer to reject with `kUnexpectedAuthPayloadAuthToken` than messages with a shorter correct prefix. By iterating over all byte values at each position and selecting the one that maximizes rejection time, the attacker reconstructs the full `auth_token` and can then submit a valid handshake to complete device authentication.
