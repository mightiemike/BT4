### Title
Consensus-side L1Handler reconstruction hardcodes `paid_fee_on_l1 = Fee(1)`, bypassing the real L1-fee check performed by the proposer - (File: `crates/apollo_transaction_converter/src/transaction_converter.rs`)

### Summary
`TransactionConverter::convert_consensus_l1_handler_to_internal_l1_handler` reconstructs an executable `L1HandlerTransaction` on the validator side using a hardcoded `Fee(1)` instead of the fee actually paid on L1, which the proposer obtains from the `L1EventsScraper`/`L1EventsProvider`. This is analogous to the reported Allora bug class: a downstream consumer uses a stand-in/stored value instead of the value produced by the authoritative calculation, causing divergent accounting/validation outcomes between the party that computed the real value and the party that consumes the substitute.

### Finding Description
The proposer node ingests `LogMessageToL2` events from L1 via the `L1EventsScraper`, and constructs `ExecutableL1HandlerTransaction` (aka `starknet_api::executable_transaction::L1HandlerTransaction`) with the real `paid_fee_on_l1` taken from the L1 event value, as shown in `crates/apollo_integration_tests/tests/l1_events_scraper_end_to_end.rs:118-122` (`paid_fee_on_l1: Fee(fee.into())`). This real fee is later checked in `blockifier`'s L1-handler execution path: [1](#0-0) 

which rejects execution with `TransactionFeeError::InsufficientFee` only when `paid_fee_on_l1 == Fee(0)`.

However, when an `L1Handler` transaction travels through consensus as a `ConsensusTransaction` (i.e., when a validating node reconstructs the executable transaction from a proposed block instead of directly from its own L1 event scraper state), the converter discards the real value and substitutes a constant: [2](#0-1) 

The `ConsensusTransaction::L1Handler` variant carries only the raw `starknet_api::transaction::L1HandlerTransaction` fields (contract address, selector, calldata, nonce, version) — not `paid_fee_on_l1` — so the validating node has no way to recover the true fee at this point and the code explicitly stubs it with `Fee(1)`, marked by a `TODO(Gilad)` acknowledging the value is not yet wired through.

Because `Fee(1)` is always non-zero, every L1Handler transaction reconstructed this way will always pass the `paid_fee == Fee(0)` check in `l1_handler_transaction.rs`, regardless of what was truly paid on L1 for that message. This mirrors the analog bug class exactly: the function that performs the authoritative computation (the scraper reading the real L1-paid fee) is bypassed by a consumer that substitutes a different, non-representative value (a hardcoded constant) for a security-relevant, state-affecting parameter.

### Impact Explanation
`paid_fee_on_l1` is the only guard preventing execution of an L1-to-L2 message for which insufficient (zero) fee was paid on L1. Different nodes computing on the same underlying data end up with different validation outcomes:
- The **proposer**, which built the block using data straight from its own `L1EventsProvider`, has the correct `paid_fee_on_l1` and would reject (revert) an L1Handler transaction whose L1-paid fee is `Fee(0)`.
- Any **other honest node** that must reconstruct the same transaction from the `ConsensusTransaction` payload (e.g., during proposal validation, re-execution, or OS/Starknet-OS-style re-verification via `convert_consensus_tx_to_internal_consensus_tx` → `convert_consensus_l1_handler_to_internal_l1_handler`) will always see `Fee(1)`, and will never trigger the `InsufficientFee` revert path — potentially executing/accepting the L1 message differently than the proposer intended, or vice versa if there is any other execution-affected behavior tied to reverted vs. accepted state (e.g., differing state diffs, differing `TransactionExecutionInfo`, and differing receipts affecting the committed state root).

This is a state-divergence risk: an honest, correctly-behaving validator can compute a different execution result (accept vs. revert, and therefore a different state diff / block hash) than the proposer for the exact same underlying transaction, purely because of this hardcoded stand-in value replacing the real computation. This falls under "honest-node divergence / wrong committed root" impact categories.

### Likelihood Explanation
This path is reachable purely through the ordinary flow of L1-to-L2 messaging — a normal, unprivileged L1 message sender needs only to send a message to L2 that ends up with a `paid_fee_on_l1` of zero at the point the message would be processed (or more generally, any code path relying on the accuracy of `paid_fee_on_l1` beyond the current weak "any positive value passes" check will silently diverge). The `TODO(Gilad)` comment explicitly signals this is known/incomplete plumbing rather than a deliberate design choice, and the pattern is exercised on every consensus-relayed L1Handler transaction (`convert_consensus_tx_to_internal_consensus_tx`), which is a mainline transaction-lifecycle path, not a malicious-operator or p2p-only edge case.

### Recommendation
Ensure the real `paid_fee_on_l1` value survives the consensus round-trip so all nodes validate on the same, authoritative value:
- Either include `paid_fee_on_l1` in the `ConsensusTransaction::L1Handler` wire representation so any node reconstructing the executable transaction uses the real value, or
- Require the receiving node to independently look up `paid_fee_on_l1` from its own `L1EventsProvider`/`L1EventsScraper` state (keyed by `tx_hash`) rather than defaulting to a constant.
Remove the `Fee(1)` stand-in in `convert_consensus_l1_handler_to_internal_l1_handler` once the real value is threaded through, and add a regression test asserting that the fee-check outcome is identical between the proposer's locally-scraped `paid_fee_on_l1` and the value reconstructed by a validating node from the same consensus transaction.

### Proof of Concept
1. An L1 message sender calls `sendMessageToL2` on the Starknet core contract with `value = 0` (zero fee paid on L1) for a nonce `N`.
2. The proposer's `L1EventsScraper`/`L1EventsProvider` observes this and constructs `ExecutableL1HandlerTransaction { paid_fee_on_l1: Fee(0), .. }` (per `crates/apollo_integration_tests/tests/l1_events_scraper_end_to_end.rs:118-122` construction pattern), includes it in a proposed block, and the proposer's own execution reverts it as `TransactionFeeError::InsufficientFee` (`crates/blockifier/src/transaction/l1_handler_transaction.rs:103-113`).
3. A validating node receives the same transaction as part of the `ConsensusTransaction::L1Handler` payload during block validation/replay and calls `convert_consensus_tx_to_internal_consensus_tx` → `convert_consensus_l1_handler_to_internal_l1_handler`, which reconstructs the executable transaction with `paid_fee_on_l1 = Fee(1)` (`crates/apollo_transaction_converter/src/transaction_converter.rs:473-483`), regardless of the true L1-paid value of `0`.
4. When this validator executes the same L1Handler transaction, the `paid_fee == Fee(0)` check never triggers, so the transaction is treated as executable, producing a different accept/revert outcome and state diff than the proposer computed for the identical transaction — a concrete honest-node execution divergence traceable directly to this hardcoded substitution.

*(Note: I was unable to fully trace how/whether the batcher or `starknet_transaction_prover`'s `virtual_block_executor.rs` re-derives `paid_fee_on_l1` in every re-execution path given index/context-size limits; if additional callers of `convert_consensus_l1_handler_to_internal_l1_handler` independently source the correct fee elsewhere, the practical exposure may be narrower than described above. A full Devin session with complete repo access would be needed to enumerate every caller and confirm whether any of them are guarded against this substitution.)*
