## Analysis

Given the constraints (unprivileged-user analogs only in AccountsDB storage/index, cache flush/shrink/clean/purge, hashing, bucket map, or snapshot generation/rebuild), the closest analog to the Uniswap "hardcoded window/cardinality regardless of chain block-time" bug class is the hardcoded wall-clock intervals in the accounts background maintenance loop, which assume a fixed, legacy slot time even though the codebase now supports variable slot durations via `SlotParams`/slot-time-reduction feature gates.

### Title
Accounts background service uses wall-clock-hardcoded `CLEAN_INTERVAL`/`SHRINK_INTERVAL` that assume legacy 400ms slot time, decoupling cleaning/shrinking cadence from the actual (now variable) slot-time regime - (File: runtime/src/accounts_background_service.rs)

### Summary
`AccountsBackgroundService`'s main loop gates how often `clean_accounts()` and `shrink_candidate_slots()`/`shrink_ancient_slots()` run using fixed `Duration` constants (`CLEAN_INTERVAL = 50s`, `SHRINK_INTERVAL = 1s`). These constants were derived from an assumption baked into a code comment - that the default incremental snapshot interval of 100 slots takes ~40 seconds (i.e., 400ms/slot) - which is exactly the same class of defect as the reported issue: a fixed constant derived from one chain's/regime's block time, hardcoded and reused even after the block-time parameter changes.

### Finding Description
The relevant constants and their justifying comment are: [1](#0-0) 

The comment explicitly ties `CLEAN_INTERVAL` to "the default incremental snapshot interval is 100 slots, which ends up being 40 seconds plus buffer" - i.e., it assumes `ns_per_slot == 400_000_000` (400ms), the `LEGACY_SLOT_PARAMS` value: [2](#0-1) 

However, this repository now implements slot-time-reduction feature gates that change `ns_per_slot` down to 350ms, 300ms, 250ms, or 200ms at runtime, effective per-epoch: [3](#0-2) 

With `reduce_slot_time_to_200ms` active, 100 slots elapse in ~20 seconds instead of ~40 seconds - i.e., incremental snapshot requests (and the `max_clean_slot_inclusive` bound derived from them) now arrive roughly twice as often as the hardcoded, slot-time-agnostic `CLEAN_INTERVAL` of 50 seconds anticipates: [4](#0-3) 

Because `should_clean` is driven purely by `previous_clean_time.elapsed() > CLEAN_INTERVAL` (wall clock), not by slots processed or the actual configured slot time, the cadence of `flush_accounts_cache(force_flush, ...)` and `clean_accounts(...)` no longer tracks the real rate at which roots/snapshot requests are produced once slot time is reduced. The same applies to `SHRINK_INTERVAL = 1s` gating `shrink_candidate_slots()`/`shrink_ancient_slots()` - with faster slots, more slots and more storages accumulate per shrink cycle than the interval was tuned for.

This mirrors the reported bug precisely: a numeric constant hardcoded based on one "chain"/regime's timing characteristics (Base's 2s blocks / Solana's legacy 400ms slots) is reused unconditionally even though the underlying block-time parameter is chain-/regime-configurable (Celo's 5s blocks / Solana's reduced slot-time regimes), producing an under- or mis-sized window relative to what the logic actually needs.

### Impact Explanation
When slot time is reduced (200-350ms regimes), `AccountsBackgroundService` cleans and shrinks the accounts store less frequently relative to the rate blocks (and their associated dead/stale account data and shrink candidates) are produced, since the interval remains fixed in wall-clock time while slots-per-unit-time increases. This causes disproportionate build-up of uncleaned accounts data, `dirty_stores`, and shrink candidates relative to what the code was designed/tuned for, i.e., disproportionate storage and background CPU cost as the accumulated backlog is eventually processed. It is a storage/CPU-cost/design defect rather than a correctness bug: cleaning/shrinking are still called under stronger triggers (`should_aggressively_flush_cache`), so it does not directly cause consensus-affecting divergence, but it degrades the intended operating envelope for validators running under the new (or future) faster slot-time regimes.

### Likelihood Explanation
The slot-time reduction feature gates (`reduce_slot_time_to_350ms/300ms/250ms/200ms`) are present in the feature set and designed to be activated cluster-wide over time, so this scenario is directly reachable in normal operation once such a feature activates - no attacker action or malicious input is required, only the cluster's own configured evolution of slot time. It requires no special access and does not depend on adversarial behavior.

### Recommendation
Derive `CLEAN_INTERVAL` and `SHRINK_INTERVAL` from the currently effective slot time (e.g., via `Bank::ns_per_slot_at_slot`/`SlotParams`) and the configured incremental snapshot interval (in slots), rather than a fixed `Duration` constant, so the cleaning/shrinking cadence remains proportional to the real rate of slot production across all supported slot-time regimes.

### Proof of Concept
1. Activate `reduce_slot_time_to_200ms` (or any of the other slot-time-reduction feature gates) on a cluster/bank, as exercised in `runtime/src/bank/tests.rs::test_reduce_slot_time_range_duration`.
2. Observe that `Bank::ns_per_slot_at_slot` now returns 200,000,000ns instead of the legacy 400,000,000ns, so 100 slots (the default incremental snapshot interval) now elapse in ~20s instead of ~40s.
3. `AccountsBackgroundService`'s loop in `accounts_background_service.rs` still gates `should_clean` on `previous_clean_time.elapsed() > CLEAN_INTERVAL (50s)`, unrelated to the new, faster slot cadence, so multiple incremental-snapshot-driven root advances occur between clean cycles rather than the single cycle the comment/tuning assumed - reproducible by instrumenting `should_clean`/`previous_clean_time` timestamps against `bank.slot()` progression under the activated feature.
