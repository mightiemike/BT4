### Title
Unhandled shard-resolution error causes deterministic chunk-processing panic when draining a stale `GlobalContractDistribution` receipt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receiver_shard_id(&shard_layout)` and immediately `.unwrap()`s the result. For `GlobalContractDistribution` receipts, `Receipt::receiver_shard_id` can legitimately return `Err(EpochError::ShardingError(..))` when the receipt's `target_shard` cannot be resolved to any shard in the current layout or its split history (e.g. the receipt was delayed across more resharding events than the split-history lineage covers). The `.unwrap()` turns that recoverable error into a hard panic instead of a graceful rejection/propagation, which is reachable purely by a contract deployer submitting a `DeployGlobalContract` action combined with the network undergoing resharding while the receipt sits in the delayed queue.

### Finding Description
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-467`) resolves the receiving shard for a receipt. For all normal receipt kinds it maps `receiver_id` to a shard via `account_id_to_shard_id`, which cannot fail. For `GlobalContractDistribution` receipts, it instead uses `target_shard`, and if `target_shard` is not part of the *current* shard layout, it attempts `shard_layout.resolve_to_current_shard(target_shard)`. If that returns `None`, the function returns `Err(EpochError::ShardingError(...))` rather than panicking — the API is explicitly designed to be fallible for this case ( [1](#0-0) ).

However, the only caller that filters delayed receipts during resharding, `DelayedReceiptQueueWrapper::receipt_filter_fn`, discards that `Result` unsafely:

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [2](#0-1) 

This is invoked from the delayed-receipt pop path (`DelayedReceiptQueueWrapper::pop`) every time a receipt is drained from the delayed queue during `ReshardingV3`-style dynamic resharding ( [3](#0-2) ). This pop path executes on every chunk application, i.e. on every honest validator's node deterministically, so if `resolve_to_current_shard` cannot find the target shard's descendant (e.g. because the split-history lineage kept by the shard layout does not span far back enough, or a `GlobalContractDistribution` receipt sits delayed across more resharding generations than the layout retains ancestry for), all validators panic simultaneously while applying the same chunk — a transaction/action-triggered halt, not a benign single-node crash.

The repository's own regression test, `test_stale_global_contract_distribution_after_double_resharding` (`test-loop-tests/src/tests/global_contracts_distribution.rs:30-186`), specifically exercises exactly this scenario: it deploys a global contract, forces the receipt to be delayed across two consecutive shard splits, then asserts the chain does **not** stall — explicitly calling out that "If the vulnerability exists, processing the stale `GlobalContractDistribution` receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations" ( [4](#0-3) ). This test only validates behavior for **exactly two** resharding generations; it does not establish that `resolve_to_current_shard`'s split-history lineage is unbounded. If the split-history/ancestry retained by the shard layout is bounded (I could not fully verify the depth semantics of `resolve_to_current_shard` in `core/primitives/src/shard_layout/v3.rs` in the available context, due to index size limits truncating that file), then a receipt delayed across three or more resharding generations, or one crossing an epoch-config boundary where earlier layouts are pruned, would still hit the `None` branch and panic via the un-guarded `.unwrap()` — regardless of whether the two-generation case is fixed.

Additionally, `receipt_filter_fn` also `.unwrap()`s `self.epoch_info_provider.shard_layout(&self.epoch_id)`, adding a second unguarded fallible call on the same hot path.

### Impact Explanation
A panic inside `Runtime::apply` during delayed-receipt processing is not contract-execution failure (which would just fail the receipt and continue) — it is a Rust panic that aborts chunk application entirely. Because all honest validators process the same delayed-receipt queue deterministically, this manifests as a synchronized chain halt: every validator applying that chunk crashes at the same point, which matches the "transaction-triggered halt" impact bucket. This is reachable by an unprivileged contract deployer submitting a single `DeployGlobalContract` action (which produces a `GlobalContractDistribution` receipt) combined with dynamic resharding occurring while that receipt is delayed — no special privileges, validator status, or malicious peer/node behavior required.

### Likelihood Explanation
Reaching the `None` branch of `resolve_to_current_shard` requires: (1) dynamic resharding (`ReshardingV3`/`DynamicResharding`) to be active, and (2) a `GlobalContractDistribution` receipt remaining in the delayed queue across resharding generations beyond what the layout's retained split lineage covers (congestion, deliberate compute saturation of the target shard, or long delay windows can all cause this — the existing test artificially saturates compute to keep the receipt delayed across two splits). Triggering it deterministically requires influencing network congestion/timing around resharding events, which is plausible but requires some setup; it is not a one-line trivial trigger, but well within reach of a deployer combined with predictable resharding schedules or congestion.

### Recommendation
- Replace both `.unwrap()` calls in `receipt_filter_fn` with proper error propagation: change `receipt_filter_fn`'s signature (and its caller `pop`) to return `Result<bool, RuntimeError>` (or similar), converting `EpochError`/lookup failures into a `RuntimeError` variant instead of panicking.
- Ensure `resolve_to_current_shard` (or `receiver_shard_id`) is verified to preserve/rebuild lineage across an arbitrary number of resharding generations, not just two, or document and enforce the retention bound explicitly with a graceful degrade path (e.g., route the receipt to a diagnostic/garbage state rather than crash).
- Add a regression test that forces three or more sequential resharding events on the same target shard while a `GlobalContractDistribution` receipt is held in the delayed queue, verifying the chain continues to make progress.

### Proof of Concept
1. Deploy a contract via `DeployGlobalContract` from an account on shard `S_A`, generating a `GlobalContractDistribution` receipt with `target_shard = S_A`.
2. Saturate compute on `S_A` every block (e.g. repeated `burn_gas_raw` calls) so the distribution receipt is pushed into and remains in the delayed-receipt queue.
3. Trigger enough consecutive dynamic-resharding events (splitting `S_A` and its descendants) that the number of resharding generations crossed exceeds whatever ancestry `resolve_to_current_shard` retains for `target_shard`.
4. Stop saturating compute so the delayed queue drains and the stale receipt is popped via `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`.
5. If the split-history depth is exceeded, `receiver_shard_id` returns `Err(EpochError::ShardingError(...))`, `receipt_filter_fn`'s `.unwrap()` panics, and every validator applying that chunk crashes, halting the chain — mirrored by the existing `test_stale_global_contract_distribution_after_double_resharding` test pattern ( [5](#0-4) ), extended to a third resharding generation.

        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
