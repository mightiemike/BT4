### Title
Unbounded prefix-scan and sort in `getDelegatedResourceAccountIndex(V2)` allows resource-exhaustion DoS via anonymous RPC/HTTP query - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
The `initiateRetroactiveHoldFarming` bug class is "an unbounded loop, driven entirely by attacker-controlled state size, that a single call/transaction must fully process, with no cap on the number of iterations." The closest reachable analog in java-tron is `DelegatedResourceAccountIndexStore.getWithPrefix`, which is invoked by the public, unauthenticated `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` gRPC and HTTP endpoints. This method performs a full key-prefix scan of every delegation relationship for an address and sorts the entire result set in memory, with no maximum size enforced. Because the number of delegation relationships an account can accumulate is attacker-controlled (each cheap `FreezeBalanceContract`/`FreezeBalanceV2Contract` with a distinct receiver address adds one more index entry), an attacker can grow this list arbitrarily and force any subsequent read of that index to do unbounded work.

### Finding Description
`DelegatedResourceAccountIndexStore.getWithPrefix` builds the account's full "to" and "from" delegation lists by doing an unbounded `prefixQuery` and then sorting all matching entries: [1](#0-0) 

This is reached from the public API surface via `Wallet.getDelegatedResourceAccountIndex` / `getDelegatedResourceAccountIndexV2`: [2](#0-1) 

which is exposed directly to anonymous callers through gRPC: [3](#0-2) 

and through unauthenticated HTTP servlets (`GetDelegatedResourceAccountIndexServlet`/`V2Servlet`, also exposed on the Solidity/PBFT read nodes): [4](#0-3) 

The number of index entries scanned is directly proportional to how many distinct delegation relationships (`from`/`to` pairs) exist for the queried address, and each new relationship is trivially created via `FreezeBalanceActuator.delegateResource`, which appends a new key/entry per unique receiver with no cap on the count of distinct receivers: [5](#0-4) 

There is no equivalent size limit here to the ones already present elsewhere in the codebase for comparable attacker-controlled collections (e.g. `VoteWitnessActuator`'s `MAX_VOTE_NUMBER` check, `UnfreezeBalanceV2Actuator`'s `UNFREEZE_MAX_TIMES` check, or the JSON-RPC `jsonRpcMaxAddressSize` filter-address-count check), showing this class of "unbounded work driven by an attacker-grown list" is a recognized and normally-mitigated risk pattern in this codebase, but it is missing for the delegated-resource index scan/sort path.

### Impact Explanation
An attacker who accumulates a large number of delegation relationships for one address (by repeatedly freezing small balances to many distinct receiver addresses) can cause every subsequent read of that address's delegated-resource index to perform an expensive full-prefix key scan plus an in-memory sort over the entire, unbounded set. Because this endpoint is unauthenticated and reachable over gRPC and HTTP (including the Solidity/PBFT read-only nodes), repeated queries against such an address can consume disproportionate CPU/I/O on the serving node for each request, degrading the RPC-API service for other users — a DoS via RPC-API, analogous to the reported unbounded 10,000-iteration DoS pattern, but manifesting as unbounded per-query cost rather than exceeding the block gas limit.

### Likelihood Explanation
Growing the number of delegation relationships requires only ordinary `FreezeBalanceContract`/`FreezeBalanceV2Contract` transactions to distinct receiver addresses, each of which is a normal, permitted user operation with modest cost; there is no protocol-level cap on the number of distinct receivers/senders an account can accumulate over time. Any attacker with moderate patience and funds can build a large index and then repeatedly query it (or have others query it) to consume node resources, making this straightforward to trigger without any privileged access.

### Recommendation
Add a maximum size/limit check (mirroring the patterns already used for `MAX_VOTE_NUMBER`, `UNFREEZE_MAX_TIMES`, and `jsonRpcMaxAddressSize`) to bound how many delegation relationships are scanned/returned per query, or paginate `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` responses instead of loading and sorting the full, unbounded prefix-scan result set in a single call.

### Proof of Concept
1. From attacker-controlled account `A`, repeatedly submit `FreezeBalanceV2Contract` (or `FreezeBalanceContract`) delegating a small resource amount to N distinct newly created receiver addresses, each creating one more entry via `delegatedResourceAccountIndexStore.delegate(...)` as shown in `FreezeBalanceActuator.delegateResource`.
2. Once N is large (e.g., tens of thousands), call the public `GetDelegatedResourceAccountIndexV2` gRPC method (or the `/wallet/getdelegatedresourceaccountindexv2` HTTP endpoint) with address `A`.
3. Observe that `DelegatedResourceAccountIndexStore.getWithPrefix` performs a full prefix scan and `Comparator.comparing` sort over all N entries on every call, with cost scaling linearly (or worse) with N and no limit — repeated queries can be used to consume disproportionate node CPU/I/O, degrading API responsiveness for other clients.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
