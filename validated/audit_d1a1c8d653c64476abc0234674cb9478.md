## Title
Division-by-zero in `RepositoryImpl.calculateGlobalEnergyLimit` via unreliable `assert` guard - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

## Summary
The reported Solidity bug is a division-by-zero in a proportional/weight-based calculation reachable by ordinary users. The strongest analog in java-tron is `RepositoryImpl.calculateGlobalEnergyLimit()`, which relies on a Java `assert` statement to guard against a zero divisor before performing `totalEnergyLimit / totalEnergyWeight`. Because Java assertions are disabled by default in production JVMs (they require the `-ea` flag), this "guard" is a no-op at runtime, unlike the equivalent non-TVM code path in `EnergyProcessor`, which has a real `if (totalEnergyWeight <= 0) return 0;` check.

## Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule accountCapsule)` computes:

```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

assert totalEnergyWeight > 0;

if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))
      .longValueExact();
}
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [1](#0-0) 

Note that `assert` statements are stripped/disabled unless the JVM is started with `-ea`, which is not the standard java-tron production configuration. This means the intended check `totalEnergyWeight > 0` performs no actual validation in a normal node, and execution falls straight into the division.

By contrast, the parallel, non-TVM implementation in `EnergyProcessor.calculateGlobalEnergyLimit()` performs a real, functioning guard:
```java
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
``` [2](#0-1) 

This divergence mirrors the class of bug in the reported issue: a formula that appears protected against a zero denominator on paper (via a check that looks correct at a glance) but is actually non-functional at runtime, and a sibling code path in the same codebase shows what the correct fix looks like (an explicit runtime `if` check instead of an `assert`).

`calculateGlobalEnergyLimit` in `RepositoryImpl` is exercised from the TVM resource-repository layer used during contract execution (`VMActuator`) and native-contract processors (e.g., delegate/undelegate resource paths), which are reachable by any unprivileged account interacting with smart contracts or resource delegation. [3](#0-2) 

## Impact Explanation
If `totalEnergyWeight` (a global chain-state value tracking total frozen-for-energy balance) is ever zero — e.g., during specific network states or after all energy-frozen balances are unfrozen network-wide — any subsequent invocation of `calculateGlobalEnergyLimit` on the TVM path throws an `ArithmeticException` instead of gracefully returning `0`, as the parallel `EnergyProcessor` path does. This would cause reverts/failures for any account whose energy limit needs to be computed during contract execution, effectively denying legitimate contract calls and constituting an invalid-state/halt-style impact for the affected code path, consistent in class with the reported vote-weight division-by-zero (an unguarded/mis-guarded denominator reachable through normal user action).

## Likelihood Explanation
Likelihood depends on `totalEnergyWeight` actually reaching zero on a live network, which is not something an ordinary user can trivially force in isolation (it requires a specific aggregate network state). I could not fully confirm from the available index whether current validation elsewhere in the codebase (e.g., in freeze/unfreeze actuators) permanently prevents `totalEnergyWeight` from reaching zero once energy delegation/staking has occurred, so likelihood should be treated as conditional/uncertain rather than proven trivially triggerable. This uncertainty is due to index size limits on fully tracing all mutation sites of `totalEnergyWeight`; a full Devin session with complete repository access would be needed to trace every write path to `TotalEnergyWeight` and confirm reachability of the zero state in production.

## Recommendation
Replace the `assert totalEnergyWeight > 0;` guard in `RepositoryImpl.calculateGlobalEnergyLimit` (and the analogous `calculateGlobalNetLimit` if it has the same pattern) with an explicit runtime check that returns a safe default (e.g., `0`) when `totalEnergyWeight <= 0`, matching the guard already present and working correctly in `EnergyProcessor.calculateGlobalEnergyLimit`.

## Proof of Concept
Not independently reproducible from the indexed code alone — reproducing this would require constructing a scenario where `TotalEnergyWeight` is driven to zero (e.g., via a sequence of freeze/unfreeze operations across the network in a test harness) and then invoking a TVM contract call that triggers `RepositoryImpl.calculateGlobalEnergyLimit`, and observing the resulting `ArithmeticException`/division fault, analogous to the `castVote` PoC in the original report. This would need to be validated in a full test environment (e.g., `RepositoryImplHardenTest` or `CalculateGlobalLimitHardenTest`) since the index does not expose a pre-existing PoC test exercising the zero-weight branch on the TVM path.
