### Title
Miner-set shadow-block version bit bypasses Nakamoto signer-signature verification - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` contains an early-return special case, structurally identical to the reported `_requireValidAdjustmentInCurrentMode` bug: when a single self-reported boolean flag is true, the function skips the entire signature-collection/threshold-check logic and instead returns as if every signer in the reward set had signed. [1](#0-0) 

### Finding Description
`verify_signer_signatures` is supposed to enforce the core Nakamoto safety invariant: a block is only valid if signers holding ≥70% of signing weight actually produced a signature over it [2](#0-1) . Before doing any of that work, however, it checks `self.is_shadow_block()` and, if true, calls `get_shadow_signer_weight`, which simply sums the weight of every signer in the reward set and returns that as the "signing weight" — with no signature ever inspected [3](#0-2) .

`is_shadow_block()` is derived purely from the high bit of the block header's one-byte `version` field: `version & 0x80 != 0` [4](#0-3) . This is a field the block's *producer* sets, not something derived from privileged chain state, a signature, or an on-chain marker. The documentation states that legitimate shadow blocks are meant to be inserted only out-of-band, directly into the staging-blocks DB as part of an emergency schema upgrade, and are "neither mined nor relayed" [5](#0-4) . That is a documented *intent*, not a code-enforced invariant at the point `verify_signer_signatures` is called.

I searched the normal, network-facing block-acceptance paths — `stackslib/src/net/api/postblock_proposal.rs` (validate()) and `stackslib/src/net/relay.rs` (process_new_nakamoto_block/signature-checking path) — for any check that rejects a block whose `version` byte has the shadow bit set before signatures are verified, and found none (`is_shadow_block` does not appear in either file). `verify_signer_signatures` is invoked directly from these ordinary ingestion paths [6](#0-5)  and from `NakamotoChainState::accept_block`-style processing [7](#0-6) , both of which take an externally-supplied `NakamotoBlock`/`NakamotoBlockHeader` whose `version` field is attacker-controlled.

This maps exactly onto the reported bug class: an early return, gated on a flag that is not equivalent to a security check, causes the code to skip the real invariant (signer-weight/threshold verification against actual signatures) and substitute a value that always satisfies it (100% of reward-set weight, unconditionally). Just as the mintList flag in the Solidity report let an attacker bypass collateralization checks, the shadow-block version flag — if reachable through the normal block-processing path — would let a single miner bypass the entire 70%-signer-weight consensus requirement for a Nakamoto block, i.e., break the equality "a block's accepted signing weight == real cryptographic signatures from ≥70% of signer weight."

I was not able to fully verify, within the scope of this review, whether some *other* gate (e.g., strict header/version well-formedness checks earlier in the pipeline, or a chainstate-level constraint that only the internal shadow-insertion code path can ever construct/store a header with the high bit set) prevents an externally-submitted block from ever reaching `verify_signer_signatures` with `is_shadow_block()==true`. The tests I found (`stackslib/src/chainstate/nakamoto/tests/mod.rs:2132-2162`, `stackslib/src/chainstate/nakamoto/tests/node.rs:2517+`) only exercise shadow blocks created via the internal builder/staging-DB insertion API (`add_shadow_block`), not via the standard proposal/relay ingestion path, so they do not settle whether the network path independently blocks a spoofed version byte.

### Impact Explanation
If the version bit is in fact reachable via the standard block-proposal/relay path, this is a **Critical** finding: it allows a single unprivileged miner to have a self-produced, effectively unsigned block accepted as if it carried full signer consensus, i.e., a wrongful "valid block accepted" outcome and a signer-weight/threshold equality violation without needing any signer cooperation at all — a chain-split-capable defect. If (as the module's stated intent suggests, but which I could not fully confirm) the version bit is unreachable outside of the internal emergency-upgrade insertion code path, then this is not exploitable by an unprivileged party and would not qualify under the rules of this scan.

### Likelihood Explanation
Setting the header's `version` byte is trivial for anyone constructing a `NakamotoBlock` (miner or block-proposal submitter); no cryptographic or economic cost is associated with flipping bit 0x80. The likelihood hinges entirely on whether any other check in the ingestion pipeline independently rejects that bit for externally supplied blocks — a fact I could not conclusively establish from the available code paths (`is_shadow_block` does not appear anywhere in `postblock_proposal.rs` or `relay.rs`, which is suggestive but not proof of absence of a check elsewhere, e.g. in header well-formedness validation).

### Recommendation
- Do not let block-supplied data alone (`version` byte) decide whether the core signer-signature invariant is skipped in `verify_signer_signatures`.
- Gate the shadow-block signature bypass on a chainstate-verified fact (e.g., "this block/tenure was inserted via the internal shadow-block DB API, as recorded by `is_shadow_tenure`/`has_shadow_nakamoto_block_with_index_hash`") rather than on a self-reported header flag, before ever calling `get_shadow_signer_weight`.
- Explicitly reject any externally-received block (via `postblock_proposal.rs`/`net/relay.rs`) whose header has the shadow-version bit set, before signature verification, so `verify_signer_signatures`'s shadow branch is only ever reached for blocks that entered chainstate through the legitimate internal path.

### Proof of Concept
Not independently confirmed end-to-end due to the ambiguity noted above (whether the normal net/relay/postblock_proposal path rejects the shadow bit before reaching `verify_signer_signatures`). The mechanical trigger, if reachable, is:
1. Construct a `NakamotoBlock` with an arbitrary/no signer signatures.
2. Set `header.version |= 0x80` (as done for test purposes in `stackslib/src/chainstate/nakamoto/tests/mod.rs:2146`, `shadow_block_no_recipient.header.version |= 0x80`).
3. Submit it through the normal block-proposal/relay ingestion path.
4. `verify_signer_signatures` calls `is_shadow_block()` → true → returns `get_shadow_signer_weight` (full reward-set weight) without checking `self.signer_signature` at all [1](#0-0) , so the block is treated as fully signed regardless of actual signer participation.

    /// Get the signing weight of a shadow block
    pub fn get_shadow_signer_weight(&self, reward_set: &RewardSet) -> Result<u32, Error> {
        let Some(signers) = reward_set.signers() else {
            return Err(ChainstateError::InvalidStacksBlock(
                "No signers in the reward set".to_string(),
            ));
        };
        let shadow_weight = signers
            .iter()
            .fold(0u32, |acc, signer| acc.saturating_add(signer.weight));

        Ok(shadow_weight)
    }
