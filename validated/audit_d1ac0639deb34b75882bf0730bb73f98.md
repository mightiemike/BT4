### Title
Webhook X-Shopify-Shop-Domain header is not covered by HMAC verification, enabling cross-tenant webhook/admin-client forgery via replay - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`validateHmacFromRequestFactory` verifies the webhook HMAC by comparing it only against the raw request body (`validateHmacString(config, rawBody, hmac, HashFormat.Base64)`), never binding the result to the `X-Shopify-Shop-Domain` header value that `checkWebhooksHeaders`/`checkEventsHeaders` later extracts as `check.domain`. Because the shop domain used downstream in `authenticateWebhookFactory` (`ensureValidOfflineSession(params, check.domain)`) is read from an unauthenticated header, an attacker holding one valid `rawBody` + `X-Shopify-Hmac-Sha256` pair for their own shop can replay it with a different `X-Shopify-Shop-Domain` header and have it validated as authentic for the victim shop.

### Finding Description
- `validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` (lines 168-201) computes `createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64)` and compares it via `safeCompare` to the `X-Shopify-Hmac-Sha256` header. The domain header is not part of the signed material at all. [1](#0-0) 
- `validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` calls this HMAC check, and only after it succeeds does it call `checkWebhookHeaders`, which independently reads `X-Shopify-Shop-Domain` from the request headers and returns it as `domain` in the result — with no cryptographic tie to the verified body/HMAC. [2](#0-1) [3](#0-2) 
- `authenticateWebhookFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` trusts `check.domain` directly, using it both as `webhookContext.shop` and as the shop key passed to `ensureValidOfflineSession(params, check.domain)`, which loads/returns the stored offline session and access token for that shop and builds an authenticated `admin` client from it. [4](#0-3) [5](#0-4) [6](#0-5) 

Since the `apiSecretKey` is the app's single client secret shared across all shops that installed the app (not a per-shop key), the same HMAC value is valid for the same `rawBody` regardless of which shop it was originally sent for. An attacker who legitimately received one webhook delivery to their own shop's endpoint (a real `rawBody` + `X-Shopify-Hmac-Sha256` pair) can resend that exact body and HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. The HMAC check passes unchanged (it never looked at the domain header), `checkWebhooksHeaders`/`checkEventsHeaders` extract `domain: 'victim-shop.myshopify.com'` from the forged header, and `authenticateWebhookFactory` resolves `check.domain` to the victim shop, loading the victim's stored offline session and constructing an `admin` client authenticated as the victim — even though the payload content is the attacker's own webhook data.

### Impact Explanation
This breaks tenant isolation for the webhook authentication path: an unprivileged attacker who has one legitimately-received webhook for their own shop can force the app's webhook handler to run with `webhookContext.session`/`webhookContext.admin` bound to a different (victim) shop's offline access token. Any handler logic keyed on `webhookContext.shop`/`session`/`admin` (e.g. writing to the app's own database keyed by shop, or making Admin GraphQL/REST calls "on behalf of" that shop using the returned `admin` client) executes against the victim tenant using attacker-controlled trigger conditions. This maps to a cross-tenant session/data access (broken tenant isolation) impact class.

### Likelihood Explanation
Feasible for any attacker who: (1) has legitimately installed the target app on their own shop (a normal merchant), (2) can trigger at least one webhook delivery to their own endpoint and capture the raw body + `X-Shopify-Hmac-Sha256` header (trivial — install the app, trigger a supported event, log the incoming request), and (3) knows or can guess the victim's `*.myshopify.com` domain (public information). No secret, no MITM, no privileged role required. The replay itself is a single crafted HTTP POST to the same webhook route. Repeatable for any webhook topic the app subscribes to and for any victim shop with a stored offline session.

### Recommendation
Bind the shop domain to the HMAC-verified data instead of trusting it as a bare header. Either (a) include the `X-Shopify-Shop-Domain` header value in the HMAC-signed input verified by `validateHmacFromRequestFactory`/`validateHmacString`, or (b) cross-check `check.domain` against the shop identifier embedded in the verified payload body (most Shopify webhook payloads include the shop domain/id) and reject on mismatch, or (c) validate that `check.domain` corresponds to a shop for which this exact `(rawBody, hmac)` pair has not already been consumed for a different domain (replay/nonce tracking per webhook id). At minimum, reject requests where the previously-recorded webhook id + domain pairing used for delivery is inconsistent.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/domain-spoof.test.ts
import {shopifyApi, LATEST_API_VERSION} from '../../..';
import {testConfig} from '../../__tests__/test-config';
import * as ShopifyErrors from '../../error';

test('HMAC-valid body replayed with forged shop domain header passes validation for a different shop', async () => {
  const shopify = shopifyApi(testConfig());

  const rawBody = JSON.stringify({id: 1, order_number: 1});
  // Attacker legitimately received this hmac for their own shop ("attacker-shop.myshopify.com")
  const hmac = await shopify.utils.hmacSign(rawBody); // computed with the shared apiSecretKey

  const forgedRequest = new Request('https://app.example.com/webhooks', {
    method: 'POST',
    headers: {
      'X-Shopify-Topic': 'orders/create',
      'X-Shopify-Hmac-Sha256': hmac,
      'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // swapped from attacker-shop
      'X-Shopify-API-Version': LATEST_API_VERSION,
      'X-Shopify-Webhook-Id': 'whid-123',
    },
  });

  const result = await shopify.webhooks.validate({
    rawBody,
    rawRequest: forgedRequest,
  });

  // Vulnerable behavior: validation succeeds and reports the victim's domain
  expect(result.valid).toBe(true);
  if (result.valid) {
    expect(result.domain).toBe('victim-shop.myshopify.com');
  }
});
```
Expected (buggy) result: `result.valid === true` and `result.domain === 'victim-shop.myshopify.com'`, despite the HMAC never having been computed over or bound to that domain — downstream `authenticateWebhookFactory` would then load the victim's offline session and return an `admin` client authenticated as the victim shop.
