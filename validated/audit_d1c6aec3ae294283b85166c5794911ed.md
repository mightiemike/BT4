### Title
DeleteAccount with `beneficiary_id == account_id` permanently burns the account's balance instead of refunding it — ([File: runtime/runtime/src/actions.rs])

### Summary
This is a direct analog of the Unlock `transferFrom(_from == _recipient)` bug class: an operation that should be a no-op or safely rejected when the source and destination are the same instead destroys value, because the code path was written assuming the two identities differ.

### Finding Description
`action_delete_account` computes the account's remaining balance and, if positive, emits a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` before immediately removing the account from state: [1](#0-0) 

The function performs no check that `delete_account.beneficiary_id != account_id`. If a user (or a key/actor with delete permission on the account) submits a `DeleteAccountAction` with `beneficiary_id` set to the account's own id, the account is removed from state synchronously, and the payout is deferred to an asynchronous refund receipt addressed to that same (now-deleted) account id.

Refund receipts are explicitly barred from ever (re)creating an account — this is confirmed by the protocol behavior documented and tested around `implicit_creation_allowed`, where every account type is asserted to be non-creatable by a refund receipt: [2](#0-1) 

Since the beneficiary account no longer exists by the time the refund receipt executes, and a refund can never trigger implicit account creation, the transferred balance cannot be credited to any account. This mirrors the original report's root cause exactly: the code path assumes `from != to` (here, "the account being deleted" vs. "the account being paid out to") and silently destroys value when that assumption is violated, instead of validating it up front (the reporter's suggested fix was exactly such a `require(_from != _recipient)` guard).

### Impact Explanation
Any transaction signer with delete permission on an account (owner, or a full-access key holder) can trigger this by mistake or via a poorly-written contract/wallet integration that populates `beneficiary_id` from the account's own id (e.g., a "self-refund" placeholder). The result is unrecoverable, permanent loss of the account's entire remaining NEAR balance — a direct, concrete "permanently frozen/burned funds" outcome from a single submitted transaction, satisfying the required impact bar (no external attacker/validator/network assumption needed).

### Likelihood Explanation
Likelihood is bounded by the fact that a user or integrator must supply `beneficiary_id` equal to the deleting account's own id, which is a foreseeable but avoidable input-validation gap (same class as the original report). No malicious counterparty, validator, or network condition is required — a single mis-constructed `DeleteAccountAction` (from a wallet, SDK helper, or user) is sufficient, which is analogous to the "few things make me think it's valid" reasoning in the original report (protocol already validates other DeleteAccount preconditions, e.g. `DeleteAccountStaking`, but not this one).

### Recommendation
Add an explicit validation in `action_delete_account` (or earlier, at action validation time) rejecting `DeleteAccountAction` where `delete_account.beneficiary_id == *account_id`, returning an `ActionErrorKind` (e.g. a new `DeleteAccountBeneficiaryIsSelf` variant) instead of silently emitting a refund receipt that can never be delivered.

### Proof of Concept
1. Create/own an account `alice.near` with balance `B > 0` and no locked stake.
2. Submit a `DeleteAccountAction { beneficiary_id: "alice.near" }` from `alice.near` to itself (satisfying the "final action"/actor-permission checks in `runtime/runtime/src/actions.rs`).
3. `action_delete_account` removes `alice.near` from state and enqueues `Receipt::new_balance_refund("alice.near", B)`.
4. When that refund receipt is later processed, `alice.near` no longer exists; per the refund/implicit-creation rules (`implicit_creation_allowed`, refund case always `false`), the account is not recreated and the deposit cannot be credited.
5. Balance `B` is permanently lost — no account holds it and no error surfaces to alert the user beforehand.
