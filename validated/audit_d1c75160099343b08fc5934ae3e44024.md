## Analysis

The reported bug class is: an unprivileged, cheap public call can mutate shared state that another user's transaction depends on for a validation check, letting an attacker front-run and block/DOS a legitimate transaction. Mapped onto the sequencer, I found an analogous path in the Starknet gateway's "skip validation for post-deploy invoke" UX feature.

### Root cause

`skip_stateful_validations` in `crates/apollo_gateway/src/stateful_transaction_validator.rs` decides whether the gateway must run the account's `__validate__` entry point before admitting an `Invoke` transaction to the mempool: [1](#0-0) 

If the incoming invoke's nonce is `1` and the on-chain account nonce is `0`, the gateway only checks that *some* transaction for that sender already exists in the mempool or a recent block, via `account_tx_in_pool_or_recent_block`: [2](#0-1) 

It does not verify that the invoke transaction itself has a valid signature for that account — the whole point of the flag is `validate: !skip_validate`, which is then passed to `run_validate_entry_point`, which entirely omits the blockifier `validate()` call when `skip_validate` is true: [3](#0-2) 

### Exploitation path

1. A legitimate user broadcasts (or has pending) a `deploy_account` transaction for a fresh account (nonce 0 → 1).
2. An attacker, observing this in the mempool, immediately submits their own crafted `Invoke` transaction with `sender_address` = the victim account and `nonce = 1`, with **arbitrary calldata/signature** (any bytes satisfy stateless checks; only resource-bound/size checks in `stateless_transaction_validator.rs` need to be met).
3. Because `account_tx_in_pool_or_recent_block` returns true (the victim's own deploy_account tx is present), the gateway sets `skip_validate = true` and admits the attacker's spoofed invoke tx into the mempool **without ever checking its signature**.
4. This occupies the `(address=victim, nonce=1)` slot in the mempool. Any legitimate invoke from the victim at nonce 1 must now go through `validate_fee_escalation`, which requires out-bidding the attacker's declared tip/gas-price bounds or is rejected outright as `DuplicateNonce`: [4](#0-3) 

5. The attacker pays **nothing** for this: fees are only charged on successful execution, and `new_for_sequencing` always runs full validation (`validate: true`) at actual block-building time, so the spoofed tx will fail `__validate__` during execution and never get committed/charged: [5](#0-4) 

The attacker can repeat this every time it's evicted, cheaply and indefinitely griefing that specific account's first post-deployment transaction — the same "cheap unauthorized state interference blocks a legitimate pending action" pattern as the original `addCredit()` finding, but via mempool nonce-slot squatting instead of a lien hash.

### Title
Unsigned Invoke Front-Run of Post-Deploy Nonce Slot via `skip_stateful_validations` — (File: `crates/apollo_gateway/src/stateful_transaction_validator.rs`)

### Summary
The gateway's UX feature that skips `__validate__` for the first invoke after a `deploy_account` (nonce 1, account nonce 0) only checks that *any* transaction for the sender exists in the mempool/recent block, not that the invoke itself is properly authorized. An attacker can submit an unsigned/garbage invoke transaction at nonce 1 for any account whose `deploy_account` transaction is currently pending, causing it to be admitted to the mempool without signature validation.

### Finding Description
`skip_stateful_validations` (`crates/apollo_gateway/src/stateful_transaction_validator.rs:429-457`) and its caller `run_pre_validation_checks`/`run_validate_entry_point` gate whether the blockifier's `validate_tx` (which enforces the account's signature check) runs before mempool admission. The gate condition is purely `tx.nonce() == 1 && account_nonce == 0 && account_tx_in_pool_or_recent_block(sender)`; it never inspects whether the *invoke tx under evaluation* was produced by the legitimate account owner. Because `account_tx_in_pool_or_recent_block` (`crates/apollo_mempool/src/mempool.rs:697-700`) just checks presence of the sender's address in the mempool/state (satisfied by the victim's own pending `deploy_account`), an attacker can inject their own spoofed invoke at nonce 1 for that address and have it admitted with `validate: false`.

### Impact Explanation
This lets an unprivileged attacker occupy the nonce-1 slot of any freshly-deploying account for free (no valid signature needed, no fee ever charged since the tx will fail `__validate__` at actual block-execution time where `validate` is always enforced). The victim's genuine first transaction is blocked by mempool fee-escalation/duplicate-nonce rules (`validate_fee_escalation`, `crates/apollo_mempool/src/mempool.rs:760-792`) until it out-bids the attacker's declared (but never-paid) fee bounds, and the attacker can repeat this indefinitely and cheaply — a persistent, targeted DOS against specific accounts' onboarding transactions.

### Likelihood Explanation
Any node observing the p2p mempool or a `deploy_account` submission can react with a single crafted, near-free follow-up transaction; no privileged role, staking, or special access is required, matching the "unprivileged transaction sender" threat model.

### Recommendation
Do not rely solely on `account_tx_in_pool_or_recent_block` to justify skipping `__validate__`. Instead, tie the skip decision to the *specific* pending `deploy_account` transaction (e.g., require the invoke to reference/match the exact `deploy_account_tx_hash`, as already tracked in the legacy `native_blockifier::PyValidator::should_run_stateful_validations` path) so that only a transaction genuinely paired with the account's own deploy flow can bypass validation.

### Proof of Concept
1. Victim submits `deploy_account` tx for new account `A` (nonce 0→1); it enters the mempool.
2. Attacker immediately submits `Invoke` tx with `sender_address = A`, `nonce = 1`, arbitrary/garbage calldata and signature, satisfying only the stateless resource-bound checks.
3. Gateway's `skip_stateful_validations` returns `true` (deploy tx for `A` exists in pool), so `run_validate_entry_point` is invoked with `skip_validate = true`, and the attacker's tx is admitted to the mempool at `(A, nonce=1)` without any signature check.
4. Victim's real first invoke tx at nonce 1 is now rejected via `DuplicateNonce` or forced into a fee-escalation bidding war it need not otherwise engage in, while the attacker's tx will later fail execution (and cost nothing) once the sequencer actually builds a block and enforces `validate: true`.

async fn skip_stateful_validations(
    tx: &ExecutableTransaction,
    account_nonce: Nonce,
    mempool_client: SharedMempoolClient,
) -> StatefulTransactionValidatorResult<bool> {
    if let ExecutableTransaction::Invoke(ExecutableInvokeTransaction { tx, .. }) = tx {
        // check if the transaction nonce is 1, meaning it is post deploy_account, and the
        // account nonce is zero, meaning the account was not deployed yet.
        if tx.nonce() == Nonce(Felt::ONE) && account_nonce == Nonce(Felt::ZERO) {
            let account_address = tx.sender_address();
            debug!("Checking if deploy_account transaction exists for account {account_address}.");
            // We verify that a deploy_account transaction exists for this account. It is sufficient
            // to check if the account exists in the mempool since it means that either it has a
            // deploy_account transaction or transactions with future nonces that passed
            // validations.
            return mempool_client
                .account_tx_in_pool_or_recent_block(tx.sender_address())
                .await
                .map_err(|err| mempool_client_err_to_deprecated_gw_err(&tx.signature(), err))
                .inspect(|exists| {
                    if *exists {
                        debug!("Found deploy_account transaction for account {account_address}.");
                    } else {
                        debug!(
                            "No deploy_account transaction found for account {account_address}."
                        );
                    }
                });
        }

        &self,
        incoming_tx_reference: TransactionReference,
    ) -> MempoolResult<Option<TransactionReference>> {
        let TransactionReference { address, nonce, .. } = incoming_tx_reference;

        self.validate_no_delayed_declare_front_run(incoming_tx_reference)?;

        if !self.config.static_config.enable_fee_escalation {
            if self.tx_pool.get_by_address_and_nonce(address, nonce).is_some() {
                return Err(MempoolError::DuplicateNonce { address, nonce });
            };

            return Ok(None);
        }

        let Some(existing_tx_reference) = self.tx_pool.get_by_address_and_nonce(address, nonce)
        else {
            // Replacement irrelevant: no existing transaction with the same nonce for address.
            return Ok(None);
        };

        if !self.should_replace_tx(&existing_tx_reference, &incoming_tx_reference) {
            info!(
                "{existing_tx_reference} was not replaced by {incoming_tx_reference} due to \
                 insufficient fee escalation."
            );
            // TODO(Elin): consider adding a more specific error type / message.
            return Err(MempoolError::DuplicateNonce { address, nonce });
        }

        Ok(Some(existing_tx_reference))
    }
