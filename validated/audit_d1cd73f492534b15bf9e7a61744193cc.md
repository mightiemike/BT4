### Title
Zero-amount burn output accepted in prepare-phase/PoX-sunset block-commits allows free sortition wins - ([File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs])

### Summary
`LeaderBlockCommitOp::parse_pre_pox_waterfall_commits` validates the burn/PoX-fee amount for the reward-phase branch (rejecting `burn_fee == 0`) and the waterfall-commit path (`parse_pox_waterfall_commits`, rejecting `output_0.amount == 0`), but the prepare-phase / post-PoX-sunset branch does not perform the equivalent check, letting a block-commit with a burn output of amount `0` parse successfully with `burn_fee = 0`.

### Finding Description
In `parse_pre_pox_waterfall_commits`, the branch used for prepare-phase or post-PoX-sunset sortitions only validates that `output_0.address.is_burn()`, but never checks that `output_0.amount > 0`: [1](#0-0) 

By contrast, the sibling reward-phase branch explicitly rejects a zero total commitment: [2](#0-1) 

And the waterfall-commit parser explicitly rejects a zero-amount first output, with an accompanying regression test (`test_parse_pox_waterfall_rejects_zero_amount`): [3](#0-2) [4](#0-3) 

This inconsistency means a `LeaderBlockCommitOp` submitted during a PoX prepare phase (or after PoX sunset) can carry `burn_fee = 0` and still be accepted as a valid operation.

This zero-fee commit then enters `BurnSamplePoint::make_min_median_distribution`, which computes `burns`/`median_burn` directly from `commit.op.burn_fee()` with no floor above zero: [5](#0-4) 

Sortition winner selection is driven by `make_sortition_ranges`, which special-cases the single-candidate case: if the distribution has exactly one point, that point is given the *entire* probability range `[0, Uint256::max())`, irrespective of its `burns` value: [6](#0-5) 

During a prepare-phase or post-sunset sortition, the mining commitment window collapses to size 1 (`windowed_block_commits.len() == 1`, no windowing/smoothing): [7](#0-6) 

Consequently, if a miner is the sole submitter of a block-commit in a given prepare-phase burn block, and that commit's PoB output amount is `0`, the burn distribution for that sortition will contain a single `BurnSamplePoint` with `burns = 0`, which is nonetheless assigned the full sortition range and therefore guaranteed to win — breaking the equality that "sortition winner selection is weighted by/dependent on real committed burn."

### Impact Explanation
This is a minority-triggerable divergence in the sortition/VRF weighting logic: an unprivileged miner acting alone can win a prepare-phase (or post-sunset) sortition and obtain the associated block reward/coinbase for that tenure while spending effectively zero BTC, instead of paying `burn_fee` as intended by the burn-weighted lottery. This matches the "sortition winner not matching the burn-weight function" class and results in a reward mis-payment (a de-facto free/near-free block reward) — a High-severity outcome bounded to the miner reward for that sortition. It does not itself cause a state-root mismatch or block-validity divergence (the resulting Stacks block/tenure would still be validated normally by all nodes against the same burnchain data), but it undermines the economic assumption that PoB commits are burn-weighted at every sortition, including prepare-phase ones.

### Likelihood Explanation
Triggering requires only that an attacker be the sole (or dominant) committer during a prepare-phase (or post-PoX-sunset) burn block — no majority, no privileged key, and no cooperation from other parties is needed; a lone miner submitting a valid PoB transaction with a `0`-value burn output during a period when they expect to be uncontested (e.g. low-competition prepare-phase blocks) can exploit it directly.

### Recommendation
Add an explicit `amount == 0` check in `parse_pre_pox_waterfall_commits`'s prepare-phase/post-sunset branch (lines 317–352), mirroring the checks already present in the reward-phase branch (`burn_fee == 0`, lines 395–398) and in `parse_pox_waterfall_commits` (lines 283–286), rejecting the op with `op_error::ParseError`/`InvalidInput` when the sole burn output amount is zero.

### Proof of Concept
1. Miner constructs a `LeaderBlockCommitOp`-encoding Bitcoin transaction during a burn block that falls within the PoX prepare phase (or after PoX sunset), with a single valid burn-address output (`output_0.address.is_burn() == true`) but `output_0.amount == 0`.
2. `LeaderBlockCommitOp::parse_pre_pox_waterfall_commits` takes the prepare-phase branch (`stackslib/src/chainstate/burn/operations/leader_block_commit.rs:318-352`), which only checks `output_0.address.is_burn()`, not `amount > 0`, so the op parses successfully with `burn_fee = 0`.
3. Assuming no other block-commit lands in that same burn block (realistic during low-competition prepare-phase windows), `windowed_block_commits` has exactly one entry, so `make_min_median_distribution` produces a single `BurnSamplePoint` with `burns = 0`.
4. `make_sortition_ranges` assigns this lone point the full range `[Uint256::zero(), Uint256::max())` (`stackslib/src/chainstate/burn/distribution.rs:386-394`), guaranteeing it wins sortition regardless of the actual (zero) burn amount.
5. The miner is selected as the sortition winner and receives the tenure/coinbase reward for that block, having burned `0` satoshis, in violation of the burn-weighted lottery invariant.

    /// rejected: such an output is dust (non-standard on the Bitcoin network),
    /// and accepting it would let a miner commit at zero cost. A positive-amount
    /// output parses into a commit whose `burn_fee` carries that amount.
    #[test]
    fn test_parse_pox_waterfall_rejects_zero_amount() {
        fn recipient(amount: u64) -> Option<BurnchainRecipient> {
            let addr = StacksAddress::new(1, Hash160([1; 20])).unwrap();
            Some(BurnchainRecipient {
                address: PoxAddress::Standard(addr, None),
                amount,
            })
        }

        // zero-amount first output -> rejected as invalid input
        let output_0 = recipient(0);
        let outputs = vec![output_0.clone()];
        assert!(matches!(
            LeaderBlockCommitOp::parse_pox_waterfall_commits(&outputs, &output_0),
            Err(op_error::InvalidInput)
        ));

        // positive-amount first output -> parsed, burn_fee carries the amount
        let output_0 = recipient(10);
        let outputs = vec![output_0.clone()];
        let calc = LeaderBlockCommitOp::parse_pox_waterfall_commits(&outputs, &output_0)
            .expect("positive-amount waterfall commit should parse");
        assert_eq!(calc.burn_fee, 10);
    }
