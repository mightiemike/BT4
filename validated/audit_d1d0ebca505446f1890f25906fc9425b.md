The rounding-direction issue in the original report manifests here as a **unit-scaling division bug** that always rounds the effective gas price down to zero, causing the protocol to systematically undercharge (in fact, never charge) gas fees for `UniversalPayload` execution.

### Title
Gas fee for UEA/UniversalPayload execution always computes to zero due to erroneous double division by 1e18 in `CalculateGasCost` - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` in `x/uexecutor/keeper/fees.go` divides `baseFee.BigInt()` by `1e18` a second time before using it as the effective gas price. `sdkmath.LegacyDec.BigInt()` already returns the semantic (rounded) integer value of the Dec — it does not need to be divided by `1e18` again. Since on-chain base fees for EVM-style gas (populated by the feemarket module, mirroring go-ethereum's wei-scale gas price, e.g. `~1e9` "atto-upc" per gas unit as seen in genesis configs) are always vastly smaller than `1e18`, the additional division truncates the result to `0` in essentially every real deployment. `effectiveGasPrice` therefore becomes `0`, `gasCost` becomes `0`, and `DeductGasFeesFromReceipt` short-circuits (`if gasCost.Sign() <= 0 { return nil }`), skipping fee deduction/burn entirely for every payload execution.

### Finding Description [1](#0-0) 

`baseFee` is an EIP-1559-style price-per-gas-unit expressed in the smallest EVM denomination (atto-upc, analogous to wei), as confirmed by genesis configuration values such as `base_fee = "1000000000.000000000000000000"` [2](#0-1)  and by the EVM coin info configured with 18 decimals [3](#0-2) .

`baseFee.BigInt()` (from `cosmossdk.io/math.LegacyDec`) already resolves the Dec to its rounded semantic integer value — it does not carry a residual `1e18` scaling factor that needs to be divided out. The extra `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` call therefore divides an already-correct, small integer (typically on the order of `1e9`–`1e10` for realistic gas prices) by `1e18`, which truncates to `0` under Go's integer division for any base fee smaller than `1e18` upc-per-gas — i.e., essentially all realistic values.

`effectiveGasPrice` is set directly from this truncated `baseFeeBig` [4](#0-3) , so `gasCost = effectiveGasPrice * gasUsed` evaluates to `0` regardless of `gasUsed`.

`DeductGasFeesFromReceipt` — called from `ExecutePayload`, `MsgExecutePayload`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload` — then no-ops on non-positive gas cost: [5](#0-4) 

As a result, `DeductAndBurnFees` (which transfers coins from the payer's smart account to the module and burns them) is never invoked with a nonzero amount, meaning gas fees charged for actual EVM execution of universal payloads are never collected.

### Impact Explanation
This corrupts gas fee accounting for every universal-execution payload call reachable by an unprivileged, ordinary user: `MsgExecutePayload` and the payload-execution portions of gasless inbound flows (`ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`). Users can execute arbitrary EVM calls via their UEA and consume real EVM gas on Push Chain's own execution layer without ever having gas fees deducted or burned from their account, permanently depriving the protocol of the intended fee revenue and creating an unmetered execution surface (a form of free/unbounded resource consumption via ordinary user-submitted transactions). This matches the "gas fee accounting" corruption category in the allowed impact set, triggered purely by an unprivileged user's default payload-execution transaction — no privileged or malicious-validator assumption required.

### Likelihood Explanation
High. The bug fires deterministically on every call path that invokes `DeductGasFeesFromReceipt`/`CalculateGasCost`, for essentially any realistic base fee value (anything below `1e18` atto-upc-per-gas, i.e., any base fee below "1 full upc per gas unit," which is a practically unreachable price). It requires no special conditions, timing, or adversarial setup — a completely ordinary `MsgExecutePayload` transaction from any user triggers it.

### Recommendation
Remove the erroneous extra division by `1e18` in `CalculateGasCost` — use `baseFee.BigInt()` (or `baseFee.TruncateInt().BigInt()`/`RoundInt().BigInt()` as appropriate) directly as the atto-upc gas price without dividing again, and verify unit consistency end-to-end (the multiplication `effectiveGasPrice * gasUsed` should stay in atto-upc, with any conversion to whole `upc` performed only once, at the point where a bank `Coin` amount is constructed, matching the denomination actually used in `sdk.NewCoin` inside `DeductAndBurnFees`). Add a regression test asserting that a nonzero, realistic base fee (e.g., `1e9` atto-upc/gas) combined with nonzero `gasUsed` produces a strictly positive `gasCost` that is actually deducted and burned from the payer's account balance.

### Proof of Concept
1. Set `feemarket` base fee to a realistic value, e.g. `1_000_000_000` (1 gwei-equivalent in atto-upc), as done in the existing test harness (`params.BaseFee = math.LegacyNewDec(1000000000)`) [6](#0-5) .
2. Submit any `MsgExecutePayload` with `GasLimit`/`MaxFeePerGas` sufficient to allow the underlying EVM call to succeed and consume, e.g., `21000000` gas.
3. Call `k.CalculateGasCost(baseFee, maxFeePerGas, maxPriorityFeePerGas, receipt.GasUsed)` directly, or observe `DeductGasFeesFromReceipt` behavior end to end.
4. Observe: `baseFeeBig := baseFee.BigInt()` yields `1000000000`; `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` yields `0`; `gasCost = 0 * gasUsed = 0`; `DeductGasFeesFromReceipt` returns `nil` without calling `DeductAndBurnFees`. The payer's `upc` balance is unchanged before/after payload execution despite nonzero `receipt.GasUsed`, confirming gas fees are never collected for this execution path.

```go
func (k Keeper) CalculateGasCost(
	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,
	gasUsed uint64,
) (*big.Int, error) {
	baseFeeBig := baseFee.BigInt()
	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18
	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	// This division unwraps the LegacyDec encoding back to the actual upc amount.
	// Note: baseFee.BigInt() returns a reference to the internal big.Int; the in-place Div
	// mutates it, which is safe here since baseFee is a local value-type copy.
	baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```
