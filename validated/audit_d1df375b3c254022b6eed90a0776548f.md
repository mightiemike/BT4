Based on tracing the write-set-to-storage handoff, I found a concrete divergence between what gets hashed/persisted for a `TransactionInfo`/`WriteSet` and what the executor actually computed for hot-state promotion in block epilogue transactions.

### Title
Silently-dropped hotness promotions in `WriteSetV0` break write-set/hash/storage consistency for block epilogue transactions - (`File: types/src/write_set.rs`, `execution/executor/src/workflow/do_get_execution_output.rs`)

### Summary
`WriteSetV0::hotness` is marked `#[serde(skip)]`, so it is dropped both from the BCS bytes used to compute `CryptoHash` (feeding `TransactionInfo::state_change_hash`, which is folded into the transaction accumulator root) and from the bytes persisted to the `WriteSetSchema` on disk. However, `DoGetExecutionOutput::by_transaction_execution_unsharded` unconditionally calls `output.add_hotness(...)` on every `BlockEpilogue` transaction output using `payload.try_get_keys_to_make_hot()`, while the conversion of that write set into the serializable `WriteSetV1` form (where hotness *is* serialized) only happens if `onchain_config.hotness_in_epilogue()` is enabled.

### Finding Description [1](#0-0) 
`WriteSetV0` skips `hotness` and `extensions` from `serde`, explicitly documented as keeping "`TransactionInfo` hashes and the on-disk `WriteSet` format ... unaffected." [2](#0-1) 
`add_hotness` is invoked on every `BlockEpilogue` transaction's `TransactionOutput` unconditionally, based on `payload.try_get_keys_to_make_hot()`. The `into_v1()` conversion that would actually make the hotness bucket serializable/hashable/persistable only runs when `onchain_config.hotness_in_epilogue()` is true (`convert_write_sets_to_v1`). [3](#0-2) 
`into_v1()` is the only path that moves the hotness bucket into a form (`WriteSetV1`) that participates in serialization. [4](#0-3) 
The `write_set_hash` embedded into `TransactionInfo` (and thus into the transaction accumulator leaf, and the state proof chain) is `CryptoHash::hash(txn_output.write_set())` — computed *after* the above conversion step, so it silently omits hotness whenever the write set is left as `V0`. [5](#0-4) 
The persisted `WriteSet` bytes for the ledger's `WriteSetSchema` use plain `bcs::to_bytes(self)`, so a `V0` write set carrying hotness in memory is committed to disk with that hotness silently discarded.

The result: whenever `hotness_in_epilogue()` is (or becomes, via a race/misconfiguration/rollout window) `false` while the block epilogue payload still yields non-empty `try_get_keys_to_make_hot()`, the in-memory `TransactionOutput`'s write set carries hotness state that is completely invisible to (a) the hash embedded into the immutable, accumulator-committed `TransactionInfo`, and (b) the bytes durably persisted for later replay/restore/backup. Any downstream consumer that reconstructs effective state purely from the persisted `WriteSet` (replay, state-sync chunk application, backup/restore) will compute a different set of state mutations than what was originally executed and whose effects were folded into the ledger's committed root — a durable ledger-vs-hash mismatch.

### Impact Explanation
If hit, this breaks the fundamental invariant that "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged." The committed `WriteSet` and its hash diverge from the actual VM-computed effect. Any replay-based verification (backup/restore replay, chunk executor re-execution during state sync) would silently reconstruct a ledger state that omits the hot-state promotions the original execution applied, while the accumulator/transaction-info hash chain remains internally self-consistent (since it was computed from the same truncated write set) — making the corruption undetectable by standard proof verification, yet the durable ledger data differs from the correct VM result.

### Likelihood Explanation
I could not fully confirm, within the available indexed code, the exact invariant tying `onchain_config.hotness_in_epilogue()` to whether `BlockEpilogue::try_get_keys_to_make_hot()` can return non-empty data — this coupling is enforced by on-chain/governance logic I was not able to trace fully (`types/src/transaction/block_epilogue.rs`, `types/src/block_executor/config.rs`). If the two are always strictly synchronized (i.e., the payload can only contain hot-keys when the feature is simultaneously on for that same block), this is not exploitable. If there is any window (feature rollout/rollback, chunk replay of historical blocks with a payload from before but flag state computed differently, etc.) where they can diverge, the corruption above triggers deterministically and requires no privileged access — it's an ordinary block epilogue transaction.

### Recommendation
- Make `add_hotness`/write-set-V1-conversion unconditional and driven solely by whether the payload actually contains non-empty hotness keys, rather than gating the serialization-enabling conversion on a separate on-chain flag from the one that produces the payload.
- Alternatively, assert/invariant-check at the point of `add_hotness` that hotness is only ever added when the write set will subsequently be converted to `V1`, and fail loudly (not silently drop) otherwise.
- Add a round-trip test asserting that `WriteSet` hash and on-disk bytes are stable for any write set for which `add_hotness` was called, across both `hotness_in_epilogue()` on/off configurations.

### Proof of Concept
Conceptual repro (cannot execute without the full harness):
1. Construct a `BlockEpilogue` transaction whose payload's `try_get_keys_to_make_hot()` returns a non-empty set of `StateKey`s.
2. Execute it via `DoGetExecutionOutput::by_transaction_execution_unsharded` with `onchain_config.hotness_in_epilogue() == false`.
3. Observe: `output.write_set()` is `WriteSet::V0` with a populated in-memory `hotness` field (`add_hotness` was called), but `CryptoHash::hash(&write_set)` and `bcs::to_bytes(&write_set)` (as used by `WriteSetSchema::encode_value`) both omit the hotness bucket entirely (confirmed by `#[serde(skip)]` on `WriteSetV0::hotness`/`extensions`).
4. Any code path that persists this `WriteSet` and later replays it (e.g., `storage/aptosdb/src/backup/restore_utils.rs::save_transactions_impl`, or state-sync chunk replay) reconstructs state without the hot-state promotion, while the accumulator/`TransactionInfo` hash chain remains "valid" against the truncated data — a silent divergence from the original VM execution result.

**Uncertainty flagged:** I was unable to fully verify, within the indexed portion of the repo, whether `hotness_in_epilogue()` and the block-epilogue payload's hotness contents are guaranteed to always be co-determined (which would foreclose the divergence window). This is the key open question for confirming exploitability; a Devin session with full repo access could trace `types/src/transaction/block_epilogue.rs` and the consensus code that constructs `BlockEndInfo`/`try_get_keys_to_make_hot` to settle this.
