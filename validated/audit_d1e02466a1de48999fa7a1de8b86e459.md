### Title
Unbounded growth of the `delayed_declares` queue bypasses mempool capacity enforcement, enabling memory-exhaustion Denial of Service - (File: crates/apollo_mempool/src/mempool.rs)

### Summary
The Eclipse Milo advisory describes a resource-exhaustion bug where a control-flow path (closing a session with `deleteSubscriptions=False`) let the client keep growing server-side memory (subscriptions/monitored items) without the size limits that applied to the "happy path" being enforced. The Starknet sequencer mempool has an analogous, transaction-sender-reachable pattern: Declare transactions are diverted into a separate `delayed_declares` queue that is not subject to the same `capacity_in_bytes` admission check as normal transactions, and are later moved unconditionally into the bounded pool once their delay elapses.

### Finding Description
`Mempool::add_tx` routes every `Declare` transaction (in non-Echonet/"Starknet" mode) into a dedicated `AddTransactionQueue` called `delayed_declares` instead of the capacity-checked `tx_pool`: [1](#0-0) 

The admission control that enforces the mempool's total byte budget, `exceeds_capacity`/`handle_capacity_overflow`, is invoked from `add_tx_validations`, which runs *before* the decision to divert the transaction to `delayed_declares`: [2](#0-1) [3](#0-2) 

`delayed_declares` is a distinct `AddTransactionQueue` struct that keeps its own independent `size_in_bytes` accounting, separate from `tx_pool`'s: [4](#0-3) [5](#0-4) 

Metrics for the pool size and the delayed-declare queue are also tracked separately (`MEMPOOL_TOTAL_SIZE_BYTES` vs `MEMPOOL_DELAYED_DECLARES_SIZE`), reinforcing that they are two independently sized structures rather than one budget: [6](#0-5) 

Once a declare transaction's `declare_delay` elapses, `add_ready_declares` moves it straight into `tx_pool` via `add_tx_inner` — which performs no capacity check at all (it only asserts uniqueness and inserts): [7](#0-6) [8](#0-7) 

This mirrors the Milo bug class: a legitimate protocol feature (delaying declare promotion / deferring subscription cleanup) creates a secondary, uncapped accumulation path that sidesteps the resource limit meant to bound total memory usage. Just as Milo bypassed per-session/per-subscription/per-monitored-item caps via the `deleteSubscriptions=False` close-session path, the sequencer bypasses its `capacity_in_bytes` mempool cap via the declare-delay path.

### Impact Explanation
An attacker who can submit valid Declare transactions from many distinct funded accounts (a normal, unprivileged capability — declaring a class only requires a funded account and a valid nonce/signature, not special privilege) can flood `delayed_declares` with transactions whose combined byte size exceeds `capacity_in_bytes`, because that queue is not counted by `exceeds_capacity`. This can drive sequencer-node memory usage far beyond the configured mempool budget, leading to process memory exhaustion/crash — a Denial of Service that can make the network unable to confirm new transactions (matching the required "network unable to confirm new transactions" impact bar). Each account can also carry a large declared class payload (Sierra/CASM), amplifying the achievable memory footprint per submitted transaction.

### Likelihood Explanation
The path is reachable directly through the ordinary transaction submission flow (`add_tx`) available to any unprivileged sender with funded accounts; no operator/proposer/peer privilege or race condition is required. The only cost to the attacker is the resource bounds/fee required to have transactions admitted into `delayed_declares` per account, which is far cheaper than the amount of node memory that can be consumed, especially by using many distinct sender accounts and maximal-size class declarations.

### Recommendation
Include `delayed_declares.size_in_bytes()` (and its transaction count, if there is a separate per-account/per-queue cap) in the `exceeds_capacity` calculation in `Mempool::add_tx_validations`/`exceeds_capacity`, so admission to `delayed_declares` is governed by the same total mempool budget as `tx_pool`. Additionally, `add_ready_declares`/`add_tx_inner` should re-validate capacity (or reserve capacity at time of enqueue and consume it at promotion) before moving a declare transaction into `tx_pool`, so that promoted declares cannot silently exceed the configured limit.

### Proof of Concept
1. Fund N distinct accounts (N large enough that N × max-declare-tx-size > `capacity_in_bytes`), each holding a valid nonce-0 state.
2. From each account, submit a `Declare` transaction with a maximal-size class payload via the normal RPC/gateway path.
3. Since `should_delay_declare` is true for each (non-Echonet mode), every transaction is pushed into `delayed_declares` via `push_back` — `exceeds_capacity` only ever inspects `tx_pool`/`tx_queue` size, so none of these submissions are rejected even after cumulative size passes `capacity_in_bytes`.
4. Repeat submission continuously (well beyond `capacity_in_bytes` in aggregate) before `declare_delay` elapses.
5. Once `declare_delay` elapses, `add_ready_declares` unconditionally drains all of them into `tx_pool` via `add_tx_inner`, which performs no capacity check, pushing the mempool's real memory footprint far past its configured cap and exhausting sequencer-node memory.

Note: due to index size limits I was unable to view the exact body of `Mempool::size_in_bytes()` in `crates/apollo_mempool/src/mempool.rs` to conclusively confirm it excludes `delayed_declares` bytes; this conclusion is inferred from the independent `AddTransactionQueue` size tracking and separate metrics cited above. If further certainty is required, a Devin session with full file access should verify the exact `size_in_bytes()` implementation.

// A queue to hold transactions that are waiting to be added to the tx pool.
struct AddTransactionQueue {
    elements: VecDeque<(DateTime, AddTransactionArgs)>,
    // Keeps track of the total size of the transactions in this queue.
    size_in_bytes: u64,
}

impl AddTransactionQueue {
    fn new() -> Self {
        AddTransactionQueue { elements: VecDeque::new(), size_in_bytes: 0 }
    }

    fn push_back(&mut self, submission_time: DateTime, args: AddTransactionArgs) {
        self.size_in_bytes = self
            .size_in_bytes
            .checked_add(args.tx.total_bytes())
            .expect("Overflow when adding a transaction to AddTransactionQueue.");
        self.elements.push_back((submission_time, args));
    }

    fn pop_front(&mut self) -> Option<(DateTime, AddTransactionArgs)> {
        let removed_element = self.elements.pop_front();
        if let Some((_, args)) = &removed_element {
            self.size_in_bytes = self
                .size_in_bytes
                .checked_sub(args.tx.total_bytes())
                .expect("Underflow when removing a transaction from AddTransactionQueue.");
        }
        removed_element
    }

    fn front(&self) -> Option<&(DateTime, AddTransactionArgs)> {
        self.elements.front()
    }

    fn contains(&self, contract_address: ContractAddress, nonce: Nonce) -> bool {
        self.elements.iter().any(|(_, tx_args)| {
            let tx = &tx_args.tx;
            tx.contract_address() == contract_address && tx.nonce() == nonce
        })
    }

    fn len(&self) -> usize {
        self.elements.len()
    }

    fn size_in_bytes(&self) -> u64 {
        self.size_in_bytes
    }
}

    /// Validates an incoming transaction and handles fee escalation.
    fn add_tx_validations(
        &mut self,
        tx_reference: TransactionReference,
        tx: &InternalRpcTransaction,
        account_nonce: Nonce,
    ) -> MempoolResult<()> {
        self.validate_incoming_tx(tx_reference, account_nonce)?;
        let replaced_tx_reference = self.validate_fee_escalation(tx_reference)?;

        // The replaced transaction is still pooled, so its bytes still count toward
        // `size_in_bytes()`. Credit what its removal will free: a same-size bump nets to zero (no
        // overflow handling), and a larger replacement only needs room for the delta, consistent
        // with how a fresh next-nonce transaction is treated. The removal happens only after
        // capacity is confirmed below, so a rejected incoming transaction never strands the
        // account.
        let freed_bytes = replaced_tx_reference.map_or(0, |reference| {
            self.tx_pool
                .get_by_tx_hash(reference.tx_hash)
                .expect("Replacement target from pool must exist.")
                .total_bytes()
        });

        if self.exceeds_capacity(tx, freed_bytes) {
            self.handle_capacity_overflow(tx, account_nonce, freed_bytes)?;
        }

    fn add_tx_inner(&mut self, args: AddTransactionArgs) {
        let AddTransactionArgs { tx, account_state } = args;
        info!("Adding transaction to mempool.");
        trace!("{tx:#?}");

        let tx_reference = TransactionReference::new(&tx);

        // Pre-count this tx as stuck; update_accounts_with_gap will correct the count if this tx
        // resolves the gap.
        if self.accounts_with_gap.contains(&account_state.address) {
            self.n_stuck_txs += 1;
        }

        self.tx_pool
            .insert(tx)
            .expect("Duplicate transactions should cause an error during the validation stage.");

        let AccountState { address, nonce: incoming_account_nonce } = account_state;
        let account_nonce = self.state.resolve_nonce(address, incoming_account_nonce);

        if self.is_fifo() {
            // FIFO mode: add all transactions to the queue immediately, regardless of nonce.
            // Keep all transactions from the same address in the queue.
            self.insert_to_tx_queue(tx_reference);
        } else if tx_reference.nonce == account_nonce {
            // Fee mode: only add transactions with matching account nonce.
            // Remove queued transactions the account might have. This includes old nonce
            // transactions that have become obsolete; those with an equal nonce should
            // already have been removed via fee escalation (`remove_replaced_tx`).
            self.tx_queue.remove_by_address(address);
            self.insert_to_tx_queue(tx_reference);
        }
    }

    fn add_ready_declares(&mut self) {
        let now = self.clock.now();
        while let Some((submission_time, _args)) = self.delayed_declares.front() {
            if now - self.config.static_config.declare_delay < *submission_time {
                break;
            }
            let (_submission_time, args) =
                self.delayed_declares.pop_front().expect("Delay declare should exist.");
            self.add_tx_inner(args);
        }
        self.update_state_metrics();
    }

    // Returns true if adding the given transaction would exceed the mempool capacity, after
    // crediting `freed_bytes` that an accompanying removal (e.g. a fee-escalation replacement)
    // will free. `freed_bytes` is 0 when there is no such removal.
    fn exceeds_capacity(&self, tx: &InternalRpcTransaction, freed_bytes: u64) -> bool {
        // The to-be-removed transaction is still counted in `size_in_bytes()` here, so subtract
        // what its removal frees. `saturating_sub` guards the (impossible) underflow defensively.
        (self.size_in_bytes() + tx.total_bytes()).saturating_sub(freed_bytes)
            > self.config.static_config.capacity_in_bytes
    }
