### Title
Unbounded `contract.getTypeValue()` causes uncaught `IndexOutOfBoundsException` in permission-operations bit test - ([File: actuator/src/main/java/org/tron/core/utils/TransactionUtil.java], [File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java], [File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Finding Description
`checkPermissionOperations` in both `TransactionUtil.java` and `WalletUtil.java` computes `operations.byteAt(contractType / 8)` where `contractType = contract.getTypeValue()` and `operations` is a fixed 32-byte `ByteString` (checked only for `size() != 32`). [1](#0-0) [2](#0-1) 

`getTypeValue()` returns the raw protobuf int32 stored on the wire for the enum field `Transaction.Contract.type`. In proto3, enum wire values are not restricted to declared enum constants — an attacker can serialize a raw `Transaction` whose `Contract.type` field carries any int32 (e.g., 5000 or a negative number, surfacing as `ContractType.UNRECOGNIZED` when read via `getType()`, but `getTypeValue()` still returns the raw integer). Neither `checkPermissionOperations` nor its callers validate `contractType` against `[0,255]` before using it as a byte/bit index into the 32-byte `operations` blob, so `contractType/8` can be negative or ≥32, and `ByteString.byteAt` throws `IndexOutOfBoundsException` for out-of-range indices.

This is reached via `TransactionCapsule.checkPermission` → `checkPermissionOperations`, invoked from `TransactionCapsule.validateSignature` (used during transaction acceptance/signature validation) and `TransactionCapsule.addSign`: [3](#0-2) [4](#0-3) 

Critically, `checkPermission` is invoked at line 490 **before** signature-weight verification at line 491, so no valid signature is required to reach the vulnerable bit-test. `validatePubSignature`, the public wrapper used during transaction processing, only catches `SignatureException`, `PermissionException`, and `SignatureFormatException` — not the unchecked `IndexOutOfBoundsException` that `byteAt` throws: [5](#0-4) 

Additionally, if `permissionId == 2` and the referenced owner account does not exist, `validateSignature` synthesizes a default active `Permission` via `AccountCapsule.createDefaultActivePermission` (line 480-483) — meaning an attacker does not even need a real multisig-enabled victim account to reach the vulnerable code with a valid 32-byte `operations` field.

By contrast, `Wallet.getTransactionSignWeight` (`TransactionUtil.getTransactionSignWeight`, lines 199-276) wraps its call to `checkPermissionOperations` in a broad `catch (Exception ex)` at line 268-271, so that specific RPC path degrades gracefully to `OTHER_ERROR` rather than crashing — this path is not exploitable for a hard crash, only as intended by the question's title concern it is functionally "safe" due to the catch-all.

### Impact Explanation
The unguarded index computation reachable through `TransactionCapsule.validateSignature`/`validatePubSignature` (used in transaction validation prior to acceptance into the mempool/block) can throw an uncaught `IndexOutOfBoundsException` for a crafted transaction with an out-of-range `Contract.type` raw value and `permissionId` set to a value that resolves to a non-null `Permission` (e.g., `permissionId=2` with a non-existent or real account). Depending on where this exception surfaces (block-verification vs. RPC handler), this can manifest as a processing halt/DoS for that validation path, an unhandled exception bubbling out of transaction/block processing, or a divergence in error handling between the "safe" (`getTransactionSignWeight`) and "unsafe" (`validateSignature`) call sites.

### Likelihood Explanation
The precondition (an attacker-controlled or arbitrary owner address, plus `permissionId=2` triggering the synthesized default permission, or referencing a real account with a nonzero-permission-id multisig configuration) is easily satisfiable by an unprivileged attacker crafting a raw `Transaction` protobuf with a forged `Contract.type` field value outside the enum's declared range. No signature validity is required to reach the vulnerable line since `checkPermission` runs before weight-signature checks in `validateSignature`. This makes the bug reliably reproducible via standard transaction submission.

### Recommendation
In `checkPermissionOperations` (both `TransactionUtil.java` and `WalletUtil.java`) and in `TransactionCapsule.checkPermission`, validate `contractType` is within `[0, 255]` (and ideally corresponds to a value present in `ContractType.values()`) before computing `contractType/8` and calling `operations.byteAt(...)`; reject with a `PermissionException`/`ContractValidateException` otherwise. Ensure `validateSignature`/`validatePubSignature` also catch broad exceptions from this bit-test path defensively, consistent with `Wallet.getTransactionSignWeight`'s existing catch-all behavior.

### Proof of Concept
```java
// Pseudocode integration test using TransactionCapsule.validateSignature
Transaction.Contract contract = Transaction.Contract.newBuilder()
    .setTypeValue(5000)              // out-of-range enum wire value, beyond 0-255
    .setPermissionId(2)              // triggers AccountCapsule.createDefaultActivePermission
    .setParameter(Any.getDefaultInstance())
    .build();

Transaction trx = Transaction.newBuilder()
    .setRawData(Transaction.raw.newBuilder().addContract(contract).build())
    .build();

// Expect: PermissionException or ContractValidateException (safe rejection)
// Actual (pre-fix): IndexOutOfBoundsException thrown uncaught from
// TransactionCapsule.validateSignature -> checkPermission -> checkPermissionOperations -> ByteString.byteAt
assertThrows(IndexOutOfBoundsException.class, () ->
    TransactionCapsule.validateSignature(trx, hash, accountStore, dynamicPropertiesStore));
```
A fuzz test should iterate `setTypeValue` over `{-1, 256, Integer.MAX_VALUE, Integer.MIN_VALUE}` combined with `permissionId ∈ {2, <real multisig id>}` and assert that `checkPermissionOperations`/`checkPermission` always return a checked exception (`PermissionException`) rather than an unchecked `IndexOutOfBoundsException`.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public boolean validatePubSignature(AccountStore accountStore,

      throws ValidateSignatureException {

      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {

        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
