### Title
Deterministic-account identity spoofing via delegate action when `FixDelegatedDeterministicStateInit` is not yet active - ([File: runtime/runtime/src/action_validation.rs])

### Summary
Analogous to the Kong Mesh bug (an identity/label binding check that is only enforced under some paths, letting a caller claim another workload's identity), nearcore has a receiver-id binding check for deterministic accounts (`0s…` NEAR-deterministic account IDs, NEP-616) that ties an account's identity to `DeterministicAccountStateInit`. The receiver-id-must-equal-derived-id check (`InvalidDeterministicStateInitReceiver`) is validated in `validate_actions`/`validate_action` [1](#0-0) , but historically this check was not correctly applied on the delegate-action (meta-transaction) path, which is the exact analog of "the check is only enforced when a certain binding/path is used, and is skippable via another path." The fix is gated behind `ProtocolFeature::FixDelegatedDeterministicStateInit`, activating at protocol version 85 [2](#0-1) , while `MIN_SUPPORTED_PROTOCOL_VERSION` is 83 [3](#0-2) .

### Finding Description
A `DeterministicStateInitAction` creates/initializes a "deterministic account" whose `0s…` account ID is a hash commitment over the `DeterministicAccountStateInit` (code + data) that seeds it — `derive_near_deterministic_account_id` [4](#0-3) . The protocol's core invariant is that the receiver of this action must equal the ID derived from its own state-init payload, enforced via `InvalidDeterministicStateInitReceiver` and exercised by `test_validate_deterministic_state_init_receiver` [1](#0-0) .

The regression test `try_meta_tx_deterministic_receiver_exploit` documents precisely the "optional-binding" failure mode: an outer meta-transaction's receiver is checked against `derive(state_init)`, but when the inner action is wrapped in a `DelegateAction`, the *delegate action's* `receiver_id` (which is what actually becomes the effective receiver for the inner action per NEP-366 semantics) was not being checked consistently against the derived ID before the fix — allowing the state-init payload meant for one deterministic account (`det_account_b`) to be routed at a *different* deterministic account (`det_account_a`) [5](#0-4) . This is fixed by `ProtocolFeature::FixDelegatedDeterministicStateInit` — "Fixes the receiver-id check when creating a deterministic account from a delegated action" [2](#0-1) , which activates at protocol version 85.

Because `MIN_SUPPORTED_PROTOCOL_VERSION` is 83 [3](#0-2) , this binary still executes chunks at protocol versions 83 and 84, on which `FixDelegatedDeterministicStateInit` is inactive and the vulnerable, pre-fix receiver-check code path is live — exactly mirroring the Kong Mesh pattern where an identity-binding check ("workload label must match", here "receiver must match `derive(state_init)`") is enforced on the direct path but is bypassable via an alternate submission path (there: unbound token; here: delegate action) until the dedicated fix lands.

### Impact Explanation
If reachable (i.e., a live chunk is still processed at protocol version 83/84), a relayer/attacker can submit a `DelegateAction` whose outer receiver matches one deterministic account's derived ID while embedding a `DeterministicStateInitAction` state-init payload for a *different* target deterministic account, causing account state (code/data) belonging to one deterministic identity to be written under a different account ID than the one that commits to it. This breaks the core deterministic-account invariant ("account ID *is* a hash of its own state"), enabling state confusion/hijacking of an account identity a caller does not control — an invalid state transition relative to the protocol's committed derivation rule, and a potential source of divergence between nodes that disagree on which protocol version's fix is active during a rollout window.

### Likelihood Explanation
Likelihood is Medium: it requires the network (or a subset of nodes, e.g. during a staged protocol upgrade) to still be running at protocol version 83 or 84, which the codebase explicitly still supports (`MIN_SUPPORTED_PROTOCOL_VERSION = 83`). Any account signer capable of constructing a `DelegateAction` (no special privilege needed) can attempt this; it is a single-transaction attack. The window is bounded to unmigrated protocol versions, which lowers likelihood outside upgrade transition periods but is still a currently supported and reachable configuration.

### Recommendation
- Confirm that `ProtocolFeature::FixDelegatedDeterministicStateInit` is unconditionally enabled (i.e., raise `MIN_SUPPORTED_PROTOCOL_VERSION` past 85, or otherwise make the delegate-action receiver-vs-derived-id check unconditional rather than protocol-version-gated) so that no supported binary can process a chunk with the vulnerable behavior.
- Ensure the receiver-id check for `DeterministicStateInitAction` is applied uniformly regardless of whether the action arrives via a plain transaction or via `Action::Delegate`/`Action::DelegateV2`, checking against the delegate action's own `receiver_id` before any inner-action dispatch, with no path that skips this validation.
- Add/keep the regression test `try_meta_tx_deterministic_receiver_exploit` gated to run and assert rejection at all currently-supported protocol versions (including 83/84) rather than only at the latest version, so CI catches any future regression of this specific check.

### Proof of Concept
Based on the existing repository regression test, which demonstrates the exploit shape at pre-fix protocol versions:
1. Deploy a global contract usable as deterministic-account code.
2. Derive two distinct deterministic accounts `det_account_a` (small state) and `det_account_b` (big state) from two different `DeterministicAccountStateInit` payloads.
3. Initialize `det_account_b` normally and add a full-access key to it (`meta_tx_sender_signer`) via a cross-contract call.
4. Craft a `DelegateAction` with `sender_id = det_account_b`, `receiver_id = det_account_a`, signed by `meta_tx_sender_signer`, whose single inner action is `Action::DeterministicStateInit` carrying `state_init_b` (the state-init that derives to `det_account_b`, not `det_account_a`).
5. Wrap it in a transaction from an independent relayer targeting `det_account_b`, and submit.
6. On a protocol version where `FixDelegatedDeterministicStateInit` is inactive (v83/v84, within `MIN_SUPPORTED_PROTOCOL_VERSION` range), the receiver-id check meant to reject `state_init_b` being applied at `det_account_a` is not correctly enforced on this delegate path, per `try_meta_tx_deterministic_receiver_exploit` [5](#0-4) .

Note: I was not able to directly inspect the exact runtime code path for `action_deterministic_state_init`'s delegate-action handling (source not fully retrievable within tool/index limits) to confirm the precise current-state behavior on unpatched protocol versions; the analysis above is based on the documented protocol-feature gate, the `MIN_SUPPORTED_PROTOCOL_VERSION` value, and the existing exploit-shaped regression test. A Devin session with full repository access would be needed to confirm whether the vulnerable branch is still compiled/reachable or has been fully removed post-fix.

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

fn try_meta_tx_deterministic_receiver_exploit(
    protocol_version: ProtocolVersion,
) -> Result<FinalExecutionOutcomeView, InvalidTxError> {
    let mut env = TestEnv::setup_with_version(Balance::from_near(100), protocol_version);
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (_state_init_a, det_account_a) = env.new_deterministic_account_with_data(small());
    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.
    let user_signer = create_user_test_signer(&env.user_account());
    let storage_balance = env.balance_for_storage(state_init_b.clone());
    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),
        Gas::from_teragas(300),
        env.get_tx_block_hash(),
    );
    env.run_tx(add_key_tx);

    // Craft the exploit: outer_tx.receiver = det_account_b = derive(state_init_b).
    // Old check: det_account_b == derive(state_init_b) passes.
    // The delegate action targets det_account_a, which is the wrong account.
    // In no protocol version can this ever be allowed to be executed successfully.
    let relayer = env.independent_account();
    let relayer_signer = create_user_test_signer(&relayer);
    let inner_action = Action::DeterministicStateInit(Box::new(DeterministicStateInitAction {
        state_init: state_init_b,
        deposit: Balance::ZERO,
    }));
    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
        nonce: delegate_nonce,
        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),
    };
    let signed_delegate_action =
        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);
    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,
        vec![Action::Delegate(Box::new(signed_delegate_action))],
        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)
}
