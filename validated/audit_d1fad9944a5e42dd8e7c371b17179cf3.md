## Finding: `ensure_match_transaction_info` does not validate `state_checkpoint_hash` / `hot_state_checkpoint_hash`, silently accepting a divergent state root during replay verification

### Title
Replay-verification skips state-checkpoint-hash validation, allowing a corrupted/divergent state root to pass as a "successful" verified replay — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` (which is bound to a signed `LedgerInfo` via the transaction accumulator). This function checks status, gas, the write-set hash, and the event root hash, but never compares the locally computed state (or hot-state) checkpoint root against the authenticated `state_checkpoint_hash` / `hot_state_checkpoint_hash` fields carried in `TransactionInfo`.

### Finding Description [1](#0-0) 

Walking through `ensure_match_transaction_info`:
- It compares `self.status()` to the expected status derived from `txn_info.status()`.
- It compares `self.gas_used()` to `txn_info.gas_used()`.
- It compares `CryptoHash::hash(self.write_set())` to `txn_info.state_change_hash()`.
- It compares the locally computed event root hash to `txn_info.event_root_hash()`.

It never reads or compares `txn_info.state_checkpoint_hash()` (nor the V1 `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`) against anything computed from the replayed execution. The state-checkpoint hash is the Sparse-Merkle-Tree root summarizing the entire world state after a checkpoint transaction — it is the strongest state-commitment invariant carried in `TransactionInfo`, and it is what `TransactionInfo`'s own hash (and thus the transaction accumulator root, and thus the `LedgerInfo` signed by validators) is built from.

The code itself acknowledges the gap, but only in the context of the not-yet-enabled trading/position feature: [2](#0-1) 

That comment is scoped to the `position_state_checkpoint_hash` field and `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, but the code shows the omission is broader: `state_checkpoint_hash` and `hot_state_checkpoint_hash` — both used unconditionally on mainnet whenever a transaction is a checkpoint (end of block / epoch boundary) — are also never validated by this function.

`ensure_match_transaction_info` is used by tooling whose entire purpose is state-commitment integrity verification: `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `execution/executor/src/chunk_executor/mod.rs`.

### Impact Explanation
If the state produced by a local re-execution diverges from the state committed on-chain (e.g., due to a nondeterminism bug in the VM/executor, a storage corruption, or a malicious/buggy archive node serving crafted `TransactionOutput`/write-sets alongside a genuine, unrelated `TransactionInfo`+proof), `ensure_match_transaction_info` will still report success as long as the write-set hash, event root, gas, and status happen to match (or in cases where the divergence originates downstream of the write set — e.g., only in checkpoint/state-root aggregation rather than in the per-transaction write set). This defeats the core purpose of replay verification (used to audit historical execution correctness, in `replay_on_archive` and `chunk_executor`) because the strongest state-commitment field is never actually checked. This falls squarely under the specified "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category, since a bug here means state divergence during replay is undetected rather than caught and alarmed.

### Likelihood Explanation
This is a straightforward, deterministic code-review finding: the omission is present in every call site unconditionally (not gated behind a feature flag for the `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields, only the `position_state_checkpoint_hash` piece is flag-gated per the comment). It requires no attacker action to trigger — it is a missing-check bug that reduces the assurance value of an existing verification/replay tool whenever there is a pre-existing divergence between local execution and the authenticated ledger, whatever its root cause. I could not fully verify from the index whether every call site (e.g., `chunk_executor::mod.rs`) always separately verifies `state_checkpoint_hash` elsewhere; the executor's checkpoint pipeline (`DoStateCheckpoint`/`DoLedgerUpdate`) does independently recompute and compare hashes in some code paths (`get_state_checkpoint_hashes`, cited above), so the practical exposure is narrower for in-protocol block execution than for the standalone `replay_on_archive`/debugger tools that rely specifically on `ensure_match_transaction_info` as their check.

### Recommendation
Extend `ensure_match_transaction_info` to compute the actual state-checkpoint root (and hot-state root, where applicable) from local execution and compare it against `txn_info.state_checkpoint_hash()` / `txn_info.hot_state_checkpoint_hash()`, in addition to the existing checks. Until `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, also validate `position_state_checkpoint_hash` per the existing TODO, so the check is complete before that feature ships.

### Proof of Concept
Not independently exploitable without a pre-existing state-divergence source; the "proof" here is structural/code-level: any caller relying solely on `ensure_match_transaction_info` (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to certify that a replayed transaction produced the correct on-chain state will pass verification even if the resulting state-checkpoint root differs from the authenticated one, as demonstrated by the absence of any `state_checkpoint_hash`/`hot_state_checkpoint_hash` comparison in the function body at [3](#0-2) .

**Caveat:** I was not able to fully trace whether `execution/executor/src/chunk_executor/mod.rs`'s call site independently re-validates the state-checkpoint hash through a separate path before or after invoking this function, which would reduce (but not eliminate, given the standalone tool call sites) the practical severity. This should be confirmed by a deeper trace of `chunk_executor/mod.rs` before finalizing severity.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
