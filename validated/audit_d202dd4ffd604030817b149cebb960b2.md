### Title
Unbounded per-request store iteration causes CPU/DoS in `Wallet.getAssetIssueList()` / `Wallet.getExchangeList()` - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getAssetIssueList()` and `Wallet.getExchangeList()` iterate over the *entire* `AssetIssueStore`/`ExchangeStore` (via `getAllAssetIssues()` / `getAllExchanges()`) with no upper bound, and are exposed unauthenticated through gRPC (`GetAssetIssueList`, `ListExchanges`) and HTTP (`GetAssetIssueListServlet`, `ListExchangesServlet`). Like the `DydxFlashLoanAbstraction._requestFlashLoan` pattern (looping over `SoloMargin.getNumMarkets()` external calls with no cap), the cost of these calls scales with the size of an attacker-influenceable, ever-growing data set, with no cap comparable to the paginated variants that already exist in the codebase.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` streams every record in the asset-issue DB into a `List` [1](#0-0) , and `ExchangeStore.getAllExchanges()` does the same for the exchange DB, additionally sorting the full list on every call [2](#0-1) .

`Wallet.getAssetIssueList()` calls `getAllAssetIssues()` and then, for every single entry, additionally invokes `BandwidthProcessor.updateUsage(issueCapsule)` — an extra per-item computation layered on top of the unbounded iteration: [3](#0-2) 

`Wallet.getExchangeList()` similarly builds a response from the full, unbounded `getAllExchanges()` result: [4](#0-3) 

Both methods are reachable from anonymous, unauthenticated network entry points:
- gRPC `WalletSolidityApi.getAssetIssueList` / `Wallet.getAssetIssueList` [5](#0-4) 
- gRPC `listExchanges` [6](#0-5) 
- HTTP `GetAssetIssueListServlet` [7](#0-6) 
- HTTP `ListExchangesServlet` [8](#0-7) 

Notably, the codebase already recognizes this exact problem class and provides paginated alternatives — `getAssetIssueList(offset, limit)` capped by `ASSET_ISSUE_COUNT_LIMIT_MAX` [9](#0-8)  and `GetPaginatedAssetIssueList` / `GetPaginatedExchangeList` RPCs [10](#0-9)  — but the legacy unbounded `GetAssetIssueList` / `ListExchanges` endpoints remain fully wired up and are still the default call used in several places (e.g. `WalletApi.getAssetIssueList`, `WalletExtensionApi`) with no size cap.

Just as `SoloMargin.getNumMarkets()` growing over time (an external, uncontrolled factor) makes `_requestFlashLoan`'s loop increasingly expensive/eventually block-gas-limit-breaking, the number of on-chain assets/exchanges is an attacker-influenceable, monotonically growing quantity (anyone can pay to create a new `AssetIssueContract` or `ExchangeCreateContract`), so the cost of every single unauthenticated `GetAssetIssueList`/`ListExchanges` call grows without bound as the chain ages.

### Impact Explanation
Each unauthenticated call to these RPC/HTTP endpoints forces the node to materialize, sort (for exchanges), and serialize the entire asset-issue/exchange store into a response object. As on-chain state grows, per-call CPU, memory, and serialized-response size increase without bound. A small number of concurrent requests against a full/witness node can exhaust CPU/heap resources on the node servicing the RPC/HTTP API, degrading or denying service to other API consumers on that node. This is a node-level (RPC-API) availability issue, not a chain-consensus-breaking bug, since the endpoints are read-only queries and do not participate in block validation.

### Likelihood Explanation
High: these endpoints require no authentication, no signed transaction, and no special privileges — any network client that can reach the HTTP or gRPC API can trigger the full-store scan repeatedly at will. The presence of `RateLimiterServlet` on the HTTP path mitigates raw request rate but does not bound the cost of any individual accepted request, and the gRPC endpoints (`GetAssetIssueList`, `ListExchanges`) do not obviously share the same protection. Given that public/community full nodes commonly expose these APIs, the trigger surface is broad.

### Recommendation
- Deprecate/remove the unbounded `Wallet.getAssetIssueList()` and `Wallet.getExchangeList()` variants (or enforce a hard cap, similar to `ASSET_ISSUE_COUNT_LIMIT_MAX` / `MARKET_COUNT_LIMIT_MAX` already used elsewhere) so a single call can never materialize an unbounded number of records.
- Push callers toward the already-existing paginated RPCs (`GetPaginatedAssetIssueList`, `GetPaginatedExchangeList`), and consider making pagination mandatory (i.e., require offset/limit) for these list endpoints.
- Add explicit resource/CPU-time budgeting or per-request result caps at the servlet/gRPC handler level for any handler that walks an entire `TronStoreWithRevoking` iterator without pre-existing bounds.

### Proof of Concept
1. Deploy/connect to a full node exposing the default HTTP/gRPC API.
2. Repeatedly issue unauthenticated requests to `GET /wallet/getassetissuelist` (or gRPC `Wallet.GetAssetIssueList`) and `POST /wallet/listexchanges` (or gRPC `Wallet.ListExchanges`).
3. Observe that response time and CPU usage scale linearly with the total number of asset issues / exchanges currently on-chain (which any user can grow by submitting `AssetIssueContract` / `ExchangeCreateContract` transactions), with no per-request cap — confirmed by the absence of any limiting logic in `Wallet.getAssetIssueList()` [3](#0-2)  and `Wallet.getExchangeList()` [4](#0-3) , in contrast to the capped paginated counterparts.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }

    return Streams.stream(iterator())
        .map(Map.Entry::getValue)
        .sorted(
            (ExchangeCapsule a, ExchangeCapsule b) -> a.getCreateTime() <= b.getCreateTime() ? 1

import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;
import org.tron.api.GrpcAPI.AssetIssueList;
import org.tron.core.Wallet;

@Component
@Slf4j(topic = "API")
public class GetAssetIssueListServlet extends RateLimiterServlet {

  @Autowired
  private Wallet wallet;

  @Override
  protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    try {
      boolean visible = Util.getVisible(request);
      AssetIssueList reply = wallet.getAssetIssueList();
      if (reply != null) {
        response.getWriter().println(JsonFormat.printToString(reply, visible));
      } else {
        response.getWriter().println("{}");
      }
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  @Override
  protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    doGet(request, response);
  }
}
