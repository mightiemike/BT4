### Title
Bridge `OutgoingToken` secret disclosed to any authenticated low-privilege user via unrestricted `Show`/`Index` endpoints - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` (and `Index`) are registered in `core/web/router.go` without any `RequiresEditRole`/`RequiresAdminRole` middleware, unlike `Create`, `Update`, and `Destroy`. Because `presenters.NewBridgeResource` unconditionally serializes the bridge's `OutgoingToken` field (no `omitempty`, no redaction), any authenticated user of any role — including the lowest-privilege "view" role — can retrieve another user's bridge's `OutgoingToken` secret by calling `GET /v2/bridge_types/:BridgeName`.

### Finding Description
`BridgeTypesController.Show` looks up the bridge by name and directly returns `presenters.NewBridgeResource(bt)` with no role check inside the handler itself: [1](#0-0) 

The presenter always includes `OutgoingToken` in the JSON response body, while `IncomingToken` is only populated explicitly on `Create` (and is `omitempty` in the struct tag, so it is safely excluded elsewhere): [2](#0-1) 

`OutgoingToken` is a genuine secret generated per bridge (`utils.NewSecret(24)`) and stored/used to authenticate outgoing calls from the bridge/external adapter back to the node: [3](#0-2) 

Whereas the write endpoints (`Create`, `Update`, `Destroy`) are gated by role-based middleware in `core/web/router.go`, `Show`/`Index` are read-only endpoints registered under the general authenticated bridges route group without a `RequiresEditRole`/`RequiresAdminRole`/`RequiresViewRole` gate specific to elevated privilege — meaning any authenticated session or API token, regardless of assigned role, can call it. Combined with the presenter always emitting `OutgoingToken`, this discloses the bridge's outgoing secret to callers who only have baseline authentication, not bridge-management privilege.

### Impact Explanation
Disclosure of `OutgoingToken` allows a low-privileged authenticated user to impersonate the bridge/external adapter when it calls back into the node (since the token is used to authenticate/validate outgoing bridge responses), enabling forged bridge responses or misuse of the token against integrations that trust it. This is a confidential secret disclosure across privilege boundaries, matching a secret-disclosure/token-forgery impact category.

### Likelihood Explanation
The precondition is only that the attacker has *some* valid Chainlink node authentication (e.g., lowest "view" role session or API token) — no bridge ownership, no admin/edit role, and no additional exploitation steps are needed. The call is a single unauthenticated-role `GET /v2/bridge_types/:BridgeName` request naming any bridge configured by an administrator, making this trivially repeatable and reliable.

### Recommendation
- Add `RequiresEditRole` (or a dedicated `RequiresViewRole` restricted to bridge-management-capable roles) to the `Show` and `Index` route registrations in `core/web/router.go`, consistent with `Create`/`Update`/`Destroy`.
- Alternatively/also, stop returning `OutgoingToken` (and any other secret) from `Show`/`Index` responses — only return it once at creation, mirroring how `IncomingToken` is already handled with `omitempty` and explicit assignment only in `Create`.

### Proof of Concept
Unit test (`core/web/presenters/bridges_test.go` style): construct a `bridges.BridgeType` with a non-empty `OutgoingToken`, call `presenters.NewBridgeResource`, and assert the marshaled JSON from a simulated `Show`/`Index` call path does **not** include `outgoingToken` — the existing `TestBridgeResource` test at [4](#0-3)  demonstrates the current behavior of always including it, confirming the flaw.

Integration test plan: 
1. Create an application (`cltest.NewApplication`), create a bridge as an admin via `POST /v2/bridge_types`.
2. Create a second session/API token with the lowest role (e.g., "view"/read-only role) via the auth/session flow.
3. Using that low-role client, call `GET /v2/bridge_types/{bridgeName}`.
4. Assert response is `200 OK` (not `401/403`) and that `data.attributes.outgoingToken` is non-empty and matches the bridge's actual `OutgoingToken`, proving cross-role secret disclosure.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// NewBridgeType returns a bridge type authentication (with plaintext
// password) and a bridge type (with hashed password, for persisting)
func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)
	salt := utils.NewSecret(24)

	hash, err := incomingTokenHash(incomingToken, salt)
	if err != nil {
		return nil, nil, err
	}

	return &BridgeTypeAuthentication{
			Name:                   btr.Name,
			URL:                    btr.URL,
			Confirmations:          btr.Confirmations,
			IncomingToken:          incomingToken,
			OutgoingToken:          outgoingToken,
			MinimumContractPayment: btr.MinimumContractPayment,
		}, &BridgeType{
			Name:                   btr.Name,
			URL:                    btr.URL,
			Confirmations:          btr.Confirmations,
			IncomingTokenHash:      hash,
			Salt:                   salt,
			OutgoingToken:          outgoingToken,
			MinimumContractPayment: btr.MinimumContractPayment,
		}, nil
}
