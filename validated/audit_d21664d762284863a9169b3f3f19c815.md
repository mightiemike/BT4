### Title
Wallet Contract silently reinterprets a self-only `AddKey`/`DeleteKey` transaction as a token `Transfer` instead of rejecting it - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs])

### Summary
`parse_rlp_tx_to_action` in the NEAR Wallet Contract determines the NEAR action to execute from an emulated Ethereum transaction. When the calldata decodes as an `AddKey`/`DeleteKey` call (`ParsableTransactionKind::SelfNearNativeAction`, only meaningful for the current/self account) but the resolved `target` turns out to be a *different* eth-implicit account, the code does not reject the transaction. Instead, it silently discards the parsed `AddKey`/`DeleteKey` intent and substitutes a `Transfer` action that moves `tx.value` (converted to yoctoNEAR) to that other account, with no error surfaced to the signer. [1](#0-0) 

### Finding Description
`parse_tx_data` classifies `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` payloads as `ParsableTransactionKind::SelfNearNativeAction`, explicitly documented as "Near native actions where the receiver should be equal to the current account." [2](#0-1) [3](#0-2) 

In `parse_rlp_tx_to_action`, the branch handling `Ok((action, ParsableTransactionKind::SelfNearNativeAction))` checks `target_kind`. If `target_kind` is `TargetKind::EthImplicit(_)` (i.e., the resolved target is not the current account but some other wallet-contract-controlled account), the code assumes "such a transfer must have been the user's intent" and replaces the parsed `AddKey`/`DeleteKey` action with `Action::Transfer { receiver_id: target.to_string(), yocto_near: 0 }`, tagging it as an `EOABaseTokenTransfer`: [4](#0-3) 

This substitution happens without any error path — the same silent-substitution shape as the `wfCashERC4626` bug, where a `transferfCash=true` intent was silently replaced by a cash-out-and-send-underlying operation once `hasMatured()` was true, with no revert to inform the caller that the requested semantics could not be honored.

The final NEAR action is produced by `Action::try_into_near_action`, which converts the substituted `Transfer` action into a real `near_action::Action::Transfer` carrying `tx.value` (scaled by `MAX_YOCTO_NEAR`) as its deposit — i.e., real token value moves according to the reinterpreted action, not the one the calldata specified: [5](#0-4) [6](#0-5) 

### Impact Explanation
A signer who authored an Ethereum-style transaction intending to install or remove an access key on their own account (`AddKey`/`DeleteKey`) can have that transaction silently re-executed as a completely different action — a value-bearing `Transfer` to whatever account the relayer/target resolution designates — without any error being returned to the caller. Because `rlp_execute` is designed to never panic and report failures only through its `ExecuteResponse.error` field, the caller has no signal that their key-management intent was discarded and value was moved instead. This mirrors the core harm in the referenced finding: an action the caller expected to be rejected or to preserve one semantic (key installation, no value movement) instead results in unexpected value movement, with success reported and no indication anything unusual occurred.

### Likelihood Explanation
This code path is reachable by any unprivileged caller of the Wallet Contract's `rlp_execute`/transaction-relaying flow — no special privilege is required beyond submitting an Ethereum-encoded NEAR transaction whose `to`/`target` resolves to `TargetKind::EthImplicit` while the calldata parses as `AddKey`/`DeleteKey`. The relayer-supplied `target` is validated against `tx.to` via `validate_tx_relayer_data`, but that validation only confirms `target` is consistent with `to`, it does not confirm that `target` is appropriate for a `SelfNearNativeAction`. This makes the silent reinterpretation deterministic and reproducible whenever such a mismatch arises (whether from relayer error, wallet UI construction bugs, or crafted payloads), analogous to how `transferfCash` being silently ignored is deterministic whenever maturity has been reached.

### Recommendation
In `parse_rlp_tx_to_action` (`internal.rs`), when `ParsableTransactionKind::SelfNearNativeAction` is produced but `target_kind` is not `TargetKind::CurrentAccount`, return an error (e.g., a new `UserError::InvalidSelfActionTarget` or reuse `RelayerError::InvalidTarget`) instead of silently substituting a `Transfer` action. This preserves the same "reject instead of silently reinterpret" mitigation recommended for the analogous fCash finding.

### Proof of Concept
1. Construct a signed Ethereum-style transaction (`from` = the wallet contract's derived address) whose `data` field ABI-encodes an `addKey` call (`ADD_KEY_SELECTOR`) intended to add a new access key to the signer's own account, and whose `to`/`value` fields are set (by relayer or malformed wallet integration) such that `target` resolves to `TargetKind::EthImplicit(other_address)` rather than the signer's own account.
2. Submit this transaction through the Wallet Contract's `rlp_execute` entry point via `parse_rlp_tx_to_action`.
3. Observe that instead of an error (or the intended `AddKey` action), the contract executes `Action::Transfer` moving `tx.value` (scaled to yoctoNEAR) to `target`, and `ExecuteResponse.success` is `true` with no `error` set — the signer's key-management intent silently became a token transfer.
