### Title
Unbounded gzip decompression of deprecated-class program data allows memory-exhaustion DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
`decompress_program`, invoked when converting a feeder-gateway `DeprecatedContractClass` into `starknet_api::deprecated_contract_class::ContractClass`, performs base64-decoding followed by unbounded gzip decompression with no size or time limit, mirroring the CVE-2014-9637 GNU-patch bug class (crafted compressed input causing unbounded memory consumption).

### Finding Description
`decompress_program` decodes the base64 `compressed_program` string and decompresses it with `flate2::read::GzDecoder`, calling `decoder.read_to_end(&mut decompressed)` with **no size cap** and an explicit `// TODO(dan): add time and size limits.` comment marking the gap. [1](#0-0) 

This function is used by `user_deprecated_contract_class_to_sn_api`, which is on the path that converts a `DeprecatedContractClass` object (as received, e.g., from the feeder-gateway/writer transaction objects) into the internal `starknet_api` type: [2](#0-1) 

This is in clear contrast to the equivalent decompression path used for the P2P/protobuf class conversion and for the declare-transaction Sierra program decoding, both of which explicitly enforce a `MAX_..._PROGRAM_SIZE`/`max_size` bound via `decode_and_decompress_with_size_limit`, which caps the decompressed output using `.take(max_size + 1)`: [3](#0-2) [4](#0-3) [5](#0-4) 

A crafted, highly-compressible gzip "program" blob (classic decompression/zip-bomb) sent through this specific code path will therefore expand without bound in memory before any validation occurs, exactly the unbounded-allocation-from-crafted-compressed-input pattern in CVE-2014-9637.

### Impact Explanation
Unbounded decompression of attacker-controlled input can exhaust process memory, causing the node (or the specific service handling this conversion) to abort/OOM or become unresponsive, denying block/transaction processing capacity — a network-availability impact consistent with the required "network unable to confirm new transactions" outcome once this path is reachable from unauthenticated/attacker-supplied class data.

### Likelihood Explanation
Reachability is limited by the specific call site: `user_deprecated_contract_class_to_sn_api`/`decompress_program` is exercised on `DeprecatedContractClass` structures coming from the writer/feeder-gateway transaction objects module rather than from the primary gateway's declare-transaction validation path (which is separately size-limited via `decode_and_decompress_with_size_limit`/`max_sierra_program_size`/`max_size` checks, e.g. in `apollo_http_server`/`apollo_gateway`). I was unable to fully trace, within the available index, every concrete caller that supplies this struct with fully attacker-controlled bytes at runtime (e.g., whether it is reachable purely from an unprivileged declare transaction, or only from trusted feeder-gateway sync data) — this reduces confidence in the "single submitted transaction/declared class" reachability required by the rules. If the only production caller is trusted feeder-gateway sync data (not directly attacker/tx-controlled), this finding would not satisfy the required scope.

### Recommendation
Apply the same `decode_and_decompress_with_size_limit` (or a `.take(max_size)` cap plus explicit size check) used elsewhere in the codebase to `decompress_program`, bounding both the compressed and decompressed sizes, and address the existing `TODO(dan): add time and size limits` comment.

### Proof of Concept
Construct a `DeprecatedContractClass.compressed_program` value that is a small, highly-compressible gzip stream (e.g., gigabytes of zeros compressed to a few KB, similar to the zip-bomb pattern demonstrated in the codebase's own `zstd_decompressed_request_too_large` test for the HTTP server) and route it through `user_deprecated_contract_class_to_sn_api` → `decompress_program`; because no size limit is enforced at this call site (unlike the HTTP-server/gateway/protobuf paths), decompression proceeds unbounded and can exhaust available memory. [6](#0-5)

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}

#[tokio::test]
async fn zstd_decompressed_request_too_large() {
    // 10 KB of repeated bytes — compresses to ~50 bytes with zstd.
    let large_body = vec![b'a'; 10 * 1024];
    let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
    encoder.write_all(&large_body).unwrap();
    let compressed_body = encoder.finish().unwrap();

    // Limit between compressed size and decompressed size.
    // compressed_body is ~50 bytes; decompressed is 10240 bytes.
    let max_request_body_size = large_body.len() - 1;
    assert!(compressed_body.len() < max_request_body_size);

    let http_client = HttpClientServerSetupBuilder::new(unique_u16!())
        .with_max_request_body_size(max_request_body_size)
        .build()
        .await;

    let response = http_client.add_rpc_tx_with_zstd(compressed_body).await;

    assert_eq!(response.status(), StatusCode::PAYLOAD_TOO_LARGE);
}
