Confirmed: ordinary `SignedTransaction` binds signatures to `block_hash` (a recent block hash, which is chain-specific since block hashes diverge immediately between distinct networks/forks), via `pub block_hash` fields in `core/primitives/src/transaction.rs`. `DelegateAction`, by contrast, contains no such binding field.

### Title
Meta-transaction `DelegateAction` signatures lack chain/network binding, enabling cross-chain replay of relayed actions - (File: core/primitives/src/action/delegate.rs)

### Summary
`DelegateAction` (NEP-366 meta-transactions) is hashed and signed via the NEP-461 `SignableMessage` scheme, which only binds the signature to a NEP-number/on-chain discriminant and the action fields themselves — never to a chain identifier, genesis hash, or recent block hash. [1](#0-0) [2](#0-1) 

### Finding Description
`SignedDelegateAction::verify()` recomputes `delegate_action.get_nep461_hash()` from a `SignableMessage` built solely from the discriminant (NEP number + on-chain/off-chain flag) and the `DelegateAction` payload itself: `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`. [3](#0-2) [4](#0-3) 

By contrast, a normal `SignedTransaction` includes a `block_hash` field referencing a recent block on the chain it is meant for, which naturally diverges across independent NEAR-protocol chains (mainnet, testnet, or any forked/cloned network sharing the same genesis config) — this makes ordinary transactions non-replayable across chains. `DelegateAction` has no analogous field: no genesis hash, no chain id, no block hash. The only "freshness" constraints are `nonce` (checked against on-chain access-key state, which is independent per chain) and `max_block_height` (also chain-relative and typically set far in the future to tolerate relayer delay).

`validate_delegate_action_key` and `apply_delegate_action` only check nonce-monotonicity relative to the local chain's access key state and that `apply_state.block_height <= max_block_height`; they never verify anything that ties the signature to a specific network. [5](#0-4) [6](#0-5) 

### Impact Explanation
If the same account id and access-key public key exist on more than one NEAR-protocol-compatible chain (e.g., mainnet and a hard-fork/testnet/private deployment sharing genesis parameters, or any scenario where a user reuses the same implicit-account key pair across networks), a `SignedDelegateAction` that Alice signs intending it to be relayed on chain A can be captured and resubmitted by a relayer (or any party who obtains the delegate action) on chain B. As long as the access key's nonce on chain B has not yet reached the signed nonce and the local block height on chain B is below `max_block_height`, the action executes with Alice's authority and the relayer's own gas/deposit payment on chain B — an unintended, unauthorized action execution that Alice never intended for that network. This is unauthorized value movement/action execution triggered by transaction replay across chains, matching the reported bug class (missing chain binding in signed data), reachable directly by any meta-transaction sender/relayer.

### Likelihood Explanation
Likelihood depends on account/key reuse across multiple NEAR-protocol chains, which is a realistic scenario for users who use the same seed phrase/implicit account across mainnet, testnet, and community-run forks, and for relayer operators who may serve multiple networks. Because nothing in the protocol code prevents this reuse or binds the signature to a network, exploitation requires no special conditions beyond capturing a previously-signed `SignedDelegateAction` and having it accepted on a different but structurally-compatible chain.

### Recommendation
Bind the `DelegateAction` (and `DelegateActionV2`) signed payload to the target network by including a chain-specific value—e.g., the genesis hash or a protocol-defined chain id—inside the `SignableMessage`/`get_nep461_hash()` computation, analogous to how ordinary transactions bind to `block_hash`. This would make a signature computed for one network fail verification on any other network, closing off the cross-chain replay vector while preserving compatibility via a protocol/schema version bump.

### Proof of Concept
1. Deploy/observe two independent NEAR-protocol chains (e.g., a mainnet-genesis fork and a testnet clone) where account `alice.near` exists on both with the same access key (implicit account, same key material reused).
2. Alice signs a `DelegateAction{ sender_id: alice.near, receiver_id: ft.near, actions: [ft_transfer(bob, 1000)], nonce: N, max_block_height: H, public_key: K }` intending it for chain A only, per `SignedDelegateAction::sign` [7](#0-6) .
3. A relayer submits it as instructed on chain A; it succeeds.
4. The same relayer (or any observer of the delegate action, since it's transmitted off-chain to relayers) also wraps the identical `SignedDelegateAction` bytes into a transaction on chain B, where `alice.near`'s access key nonce is still below `N` and current block height is below `H`.
5. `apply_delegate_action` on chain B calls `signed_delegate_action.verify()`, which succeeds because the hash never included any chain-specific data [8](#0-7) ; the inner `ft_transfer` action executes on chain B without Alice's consent for that network.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,

    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
