## Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting execution/replay verification accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used to confirm that a locally-computed `TransactionOutput` (status, gas, write-set hash, event root) matches the persisted, accumulator-committed `TransactionInfo` for a version. The function itself documents that it deliberately omits comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that bind a transaction to the authenticated state/Merkle root. This is the same bug class as the GovNFT `maxBridge` report: a value that exists specifically to gate/validate an operation (here, checkpoint root equality) is computed but never actually checked, so the caller believes validation succeeded when a critical invariant was silently skipped.

## Finding Description [1](#0-0) 

The function computes and asserts equality for status, gas_used, and `write_set_hash` vs `txn_info.state_change_hash()`, and for the event root hash, but the closing comment explicitly states:

"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution. Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS."

This function is invoked from the chunk executor path and from `storage/db-tool/src/replay_on_archive.rs` [2](#0-1) [3](#0-2) , both of which are exactly the integrity-verification/replay contexts called out in the scope of this task ("committed state that differs from the correct VM result", "restore/replay divergence"). Because `state_checkpoint_hash` (the Sparse-Merkle/JMT state root committed in `TransactionInfo`) is never compared against what local re-execution produces, a corrupted, tampered, or buggy state-checkpoint hash bundled in a `TransactionInfo` can pass `ensure_match_transaction_info` even though the actual world-state root diverges from the one that would be produced by correct VM execution.

## Impact Explanation
`TransactionInfo.state_checkpoint_hash` is the field committed into the transaction accumulator and covered by consensus signatures/accumulator proofs — it is the authenticated binding between a version and its state root. A validation routine whose entire purpose is to confirm "the locally executed result matches the committed record" that skips this specific field means:
- Replay-verification tooling (`replay_on_archive`) can report success ("replay verified") for a version whose real state does not match what correct execution would produce, masking a state-divergence bug or corruption instead of catching it.
- Any consumer relying on `ensure_match_transaction_info` as their sole state-consistency gate (e.g., chunk executor commit-time sanity check) would similarly fail to detect a mismatched state/hot-state/position-state root between what was recomputed and what is already persisted.

This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Wrong ... state proof accepted as valid" impact categories: a state root that should have been rejected as inconsistent is instead accepted as matching.

## Likelihood Explanation
The gap is not hypothetical - it is explicitly acknowledged in the source comment as a known limitation ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), meaning the code authors are aware the check is incomplete but it currently ships unguarded for any caller not specifically gated by that feature. Likelihood of the check actually being relied on for state-root integrity is high, since `ensure_match_transaction_info` is the general-purpose "does execution output match committed info" assertion and its docstring implies exactly that broader guarantee. However, actual mainnet exploitability depends on whether an attacker/bug can produce a `TransactionInfo` with a valid accumulator inclusion proof but a wrong `state_checkpoint_hash` — this itself would typically also require a consensus/accumulator-level flaw, so this bug alone is primarily a **detection/defense-in-depth gap** rather than a directly exploitable state-corruption vector by an unprivileged actor. This lowers confidence that it independently rises to High/Critical without a companion bug that produces a mismatched checkpoint hash in the first place.

## Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present per the relevant feature flags) between the locally-recomputed output and `txn_info`, failing loudly on any mismatch, exactly as the existing in-code TODO recommends, before any caller (chunk executor, replay-verify tooling) treats a successful call as proof that execution reproduces the committed ledger state.

## Proof of Concept
No standalone PoC can be constructed purely from this function, since it requires a `TransactionInfo` with a mismatched checkpoint hash to already be admitted somewhere in the pipeline (e.g. via a bug in state-checkpoint computation, corrupted backup data, or a manufactured `TransactionInfo`). The concrete, reproducible fact is code-level: call `ensure_match_transaction_info` with a `TransactionOutput` and a `TransactionInfo` whose `state_checkpoint_hash` differs from the true root of `self.write_set()` applied to the parent state — the function returns `Ok(())` because it never reads `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` anywhere in its body [4](#0-3) .

Given the uncertainty about independent exploitability by an unprivileged party (this is a verification-gap rather than a directly forgeable state-commitment), I want to flag this explicitly: this finding is best understood as a **defense-in-depth / detection gap acknowledged in the code itself**, not a standalone critical exploit chain. If your bar requires a fully self-contained "wrong root accepted as valid by an unprivileged actor" proof without any companion bug, this analog may not clear that bar on its own.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
