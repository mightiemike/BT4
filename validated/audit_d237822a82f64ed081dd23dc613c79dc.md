### Title
`TransactionOutput::ensure_match_transaction_info()` skips verifying `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, letting replay-verify accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the authenticated-vs-computed comparator used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches the trusted `TransactionInfo` pulled from an authenticated backup/archive. The function checks status, gas, write-set hash, and event root hash, but explicitly does **not** compare the state-checkpoint-related hashes carried in `TransactionInfoV1` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) against the values computed by local re-execution. This is acknowledged in-code by a `TODO(trading-native)` comment.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  validates:
- kept-status equality
- gas_used equality
- write_set hash equality (`state_change_hash`)
- event root hash equality

but the comment block explicitly documents the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

The state checkpoint root, hot-state root, and native-position root are all part of the authenticated `TransactionInfoV1` that is committed into the transaction accumulator and covered by the ledger-info signature — this is precisely the "committed state that differs from the correct VM result" surface described in the prompt's State-Integrity Gate. These roots are produced separately by `DoStateCheckpoint::run` / `compute_position_checkpoint` ( [3](#0-2) ), independent from `assemble_transaction_infos`'s write-set/event hash computation ( [4](#0-3) ). `ensure_match_transaction_info` is the only cross-check tying a locally re-executed `TransactionOutput` back to the authenticated `TransactionInfo`, and it is invoked directly in the archive replay-verification loop:
```rust
if let Err(err) = executed_outputs[idx].ensure_match_transaction_info(
    version,
    &expected_txn_infos[idx],
    Some(&expected_writesets[idx]),
    Some(&expected_events[idx]),
) { ... }
``` [5](#0-4) 

Because state/hot-state/position checkpoint hashes are never touched by this function, any divergence between the locally recomputed state root and the archived/authenticated root — whether caused by a state-tree computation bug (e.g. in `LedgerStateSummary::update`, `PositionSlot`/`native_position_iter` handling, or hot-state root logic) or a non-deterministic/buggy state-checkpoint implementation — will pass replay verification silently. `expected_txn_infos[idx]` (the authenticated `TransactionInfo`) is only used for its `state_change_hash`, `event_root_hash`, `gas_used`, and `status` fields; its `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` accessors (defined at [6](#0-5) ) are never called by the comparator.

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`, aptos-debugger, and the CLI's replay verification) is one of the mechanisms operators and auditors rely on to detect state-root divergence from archived/backup data — i.e., to catch exactly the class of bug this whole task is scanning for ("committed state that differs from the correct VM result"). Because the comparator omits the checkpoint-hash checks, a state-root computation bug (in the main state tree, hot-state tree, or the newer native-position tree) that produces a wrong root but a correct write-set/event hash would go undetected by this tool, giving false confidence that a node's local execution/storage matches the authenticated chain state. This directly weakens the proof/commitment-integrity guarantee the report seeks: authenticated state roots are not actually being cross-checked at this control point.

### Likelihood Explanation
The gap is unconditional and always active — it is not behind any feature flag; the comment says it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying awareness that this needs closing prior to that feature going live, but as written the check is skipped for every replay-verify invocation, on both v0 and v1 `TransactionInfo`, whenever the state-checkpoint hash happens to already diverge for any reason (bug, storage corruption, or non-determinism). This is a real, always-reachable gap in a security tool's core check, not a hypothetical edge case, though its ultimate mainnet impact depends on some independent bug or corruption actually causing a state-root mismatch elsewhere (this comparator's flaw is that it wouldn't catch such a mismatch, not that it forges one itself).

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on either side) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, returning an error on mismatch, before any feature that commits these roots (`HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled in production.

### Proof of Concept
Not applicable as an exploit against a specific external actor — this is a verification-tooling gap. Conceptually: run `replay-on-archive` (or `aptos-debugger`) against a chunk where local state-checkpoint computation yields a different `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` than the authenticated `TransactionInfo`, while write_set hash, event root hash, gas, and status remain identical. `execute_and_verify` in `replay_on_archive.rs` will call `ensure_match_transaction_info`, which returns `Ok(())` despite the state-root divergence, so the tool reports the chunk replayed successfully. I was not able to construct or run an end-to-end test in this environment; the finding rests directly on the documented code gap and its exact call sites cited above.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
