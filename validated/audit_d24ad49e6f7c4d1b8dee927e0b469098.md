### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole binding check used by both the chunk-executor's execution-verification path and the `db-tool replay-on-archive`/`replay-verify` tooling to confirm that locally re-executed VM output matches the authenticated, on-disk `TransactionInfo` for a version. The function only compares status, gas, write-set hash, and event-root hash; it explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, which is acknowledged by an in-code `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks:
- execution status vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()`

but never checks `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`. The comment directly above the `Ok(())` states this is a known gap: "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution," and that the checkpoint hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [2](#0-1) .

This function is the integrity gate in two proof/replay-critical call sites:
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, used when re-executing chunks (e.g., state-sync/backup replay) to confirm local execution matches the trusted `TransactionInfo` list before commit [3](#0-2) .
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, the core correctness gate of the `replay-on-archive`/`replay-verify` mainnet-archive integrity tool [4](#0-3) .

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and the repurposed `position_state_checkpoint_hash` field, gated by feature flags `TRANSACTION_INFO_V1`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, and `HOT_STATE_ROOT_IN_TXN_INFO` [5](#0-4)  and [6](#0-5) . These roots are produced independently of the write-set hash (they summarize auxiliary Merkle structures such as the position/trading-native state tree and hot-state tree), so a bug or divergence in constructing those trees can corrupt the committed root while write-set/event hashes still match. Because `ensure_match_transaction_info` never compares these fields, such a divergence is silently accepted as a "successful" replay/verification.

### Impact Explanation
This breaks the proof/verification invariant that replay-verify and chunk-execution-verification must catch any divergence between locally recomputed ledger state and the authenticated on-chain commitment. Once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` are enabled (they are not in `default_features()` today [7](#0-6) , but are designed to be turned on), a corrupted or hard-fork-diverging state/position/hot-state root would pass `replay-on-archive`/`replay-verify` and chunk-executor execution verification undetected, defeating the purpose of these integrity tools on archived/replayed mainnet data. This is a proof-integrity gap, not a live consensus bypass (consensus itself still commits whatever the executor computes), but it removes the safety net that is relied upon to detect exactly this class of divergence during backup verification, replay-verify CI, and chunk-executor sync.

### Likelihood Explanation
The gap only becomes exploitable/relevant once the three checkpoint-hash-carrying feature flags are turned on together, which is stated in code as a pending rollout step. Until then, `TransactionInfo` is `V0` and carries no such extra roots to check, so the check is currently a no-op gap rather than an active one. Likelihood of triggering the missed-detection is tied directly to the rollout timeline of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`, and to any bug (intentional or accidental) in trading-native/hot-state tree construction during that window.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding execution output provides a comparable value (mirroring how `state_change_hash`/`event_root_hash` are checked), before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet, exactly as the existing TODO comment prescribes.

### Proof of Concept
Not directly exploitable today because the gating features are off by default; the "proof" here is the explicit code path:
1. Enable `TRANSACTION_INFO_V1` + `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (+ `HOT_STATE_ROOT_IN_TXN_INFO`).
2. Introduce any divergence between the locally recomputed position/hot-state Merkle root and the archived `TransactionInfoV1.position_state_checkpoint_hash`/`hot_state_checkpoint_hash` while keeping write set and events identical.
3. Run `replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify`) or chunk-executor `verify_execution` — both call `ensure_match_transaction_info`, which will return `Ok(())` despite the root mismatch, per [2](#0-1) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
