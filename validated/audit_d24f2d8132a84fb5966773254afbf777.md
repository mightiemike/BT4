## Title
Translated V1 events (e.g. `BurnTokenEvent`) computed from `latest_state_checkpoint_view()` instead of per-version state, causing `TranslatedV1EventSchema` entries to be permanently bound to the wrong ledger version - ([File: storage/indexer/src/event_v2_translator.rs])

### Summary
`IndexerReader::get_translated_v1_event_by_version_and_index` returns a `ContractEventV1` that was pre-computed and cached at indexing time in `TranslatedV1EventSchema`, keyed only by `(version, index)` [1](#0-0) . That value is produced once, during `process_a_batch`, by `translate_event_v2_to_v1` for `ContractEvent::V2` events (e.g. the `BurnToken` → `BurnTokenEvent` translation) and is written into the schema unconditionally, without any correlation between the state used for translation and the `version` key it's stored under [2](#0-1) .

### Finding Description
The `BurnTokenTranslator` (and every other V2→V1 translator) derives the synthetic `sequence_number` for the reconstructed `BurnTokenEvent` by reading the current `TokenStore.burn_events` counter via `engine.get_state_value_bytes_for_resource(...)`, which internally calls `main_db_reader.latest_state_checkpoint_view()` — i.e. the **latest** committed state of the whole DB at the moment the indexer thread runs, not the state as of the specific transaction `version` whose event is being translated: [3](#0-2) [4](#0-3) 

`process_a_batch` iterates through a whole batch of transactions (`batch_size` versions) that have already been fully committed to the main DB before the indexer starts translating any of them [5](#0-4) . When it reaches an early version `V` in the batch and needs to translate a `BurnToken` V2 event at `V`, `get_state_value_bytes_for_resource` returns the `TokenStore` resource as of the *current tip of the main DB* (which may already include effects of `V+1 … end_version` and beyond, since the main DB reader has no way to pin to `V`). The `burn_events` counter read is therefore a snapshot from a ledger version that can be strictly greater than `V`. The resulting `sequence_number` (`get_next_sequence_number`, seeded from `count()` of that future-state counter) is then baked into a `ContractEventV1` and permanently written to `TranslatedV1EventSchema` under key `(V, idx)` [6](#0-5) [7](#0-6) .

`get_translated_v1_event_by_version_and_index` simply performs a keyed lookup of that cached value and has no mechanism to validate that the cached translation's implicit sequence number is consistent with the state committed as of the requested `version`/`ledger_version`: [8](#0-7) 

Callers via `IndexerReader` (e.g. `api/src/context.rs`) only pass through `version`/`index`; there is no re-derivation or proof binding against the ledger version's Jellyfish Merkle state root at that specific version — the value returned is whatever was cached during indexing, computed from whichever state happened to be "latest" at cache-write time.

### Impact Explanation
This breaks the required invariant that "authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object." A client querying the translated-event API for version `V` receives a `BurnTokenEvent`-derived event whose `sequence_number` reflects the `TokenStore.burn_events` counter from a *different, later* ledger state than the one legitimately associated with version `V`. Any consumer relying on this API to reconstruct/verify a v1-style event stream (e.g. for indexing consistency checks, sequence-number-based deduplication, or downstream systems trusting monotonic per-key sequence numbers) will observe values that do not correspond to the state committed at version `V`. Because the mismatch is baked into a persisted schema entry, it is stable/reproducible and not a transient race — it represents a genuine state-response misbinding, not merely a presentation issue.

Note: this is scoped to the internal/optional DB indexer's translated-event convenience API (feature only active in "event_v2_translation" mode), not the primary consensus-critical, cryptographically-accumulator-proven event/transaction paths (`EventDb`, `TransactionInfo`, accumulator proofs) which remain correctly version-bound per the code reviewed (`storage/aptosdb/src/ledger_db/event_db.rs`, `types/src/transaction/mod.rs` proof verification). No cryptographic proof accompanies `get_translated_v1_event_by_version_and_index`'s result, so it cannot corrupt the accumulator/JMT proof chain, but it does return authenticated-looking, version-keyed data that is silently mis-derived.

### Likelihood Explanation
This will occur deterministically whenever a `BurnToken`/`MintToken`/similar V2 event is translated within a batch (`batch_size` transactions) that also contains subsequent mutations to the same underlying resource counter (e.g. multiple burns/mints of tokens under the same `TokenStore` in the same or a following version within the batch window, or simply because the indexer lags behind and processes many versions using one "latest" state read). Given typical `batch_size` configuration and real-world token burn/mint frequency, this is a normal-operation condition, not an edge case requiring adversarial timing — although some attacker-controlled trigger (rapid repeated burns from the same account) increases the observable divergence deterministically.

### Recommendation
- Translate each V2 event using the account/object resource state **as of the transaction's own version**, not `latest_state_checkpoint_view()`. Use `main_db_reader.state_view_at_version(version)` (or equivalent) inside `get_state_value_bytes_for_resource` / `get_state_value_bytes_for_object_group_resource`, passing the specific `version` being processed through `EventV2TranslationEngine`.
- Alternatively, if per-version state views are too costly, process translations strictly in commit order one version at a time (flushing/committing state after each version) so that "latest" is guaranteed to equal "as-of `version`" — but this conflicts with the current batched design and should be a bigger design change.
- Add validation/tests asserting that a translated event's implied sequence number matches `get_latest_sequence_number` (or the `EventSequenceNumberSchema` counter) as of the exact version being translated, not any later version.

### Proof of Concept
1. Configure a node with `enable_event_v2_translation = true` and a `batch_size` > 1.
2. Have an account whose `TokenStore` burns 2 tokens (v1 token module `BurnToken` V2 events) at consecutive versions `V1 < V2` inside the same indexer batch.
3. After indexing runs, call `IndexerReader::get_translated_v1_event_by_version_and_index(V1, idx)` (exposed via `api/src/context.rs`) and inspect the returned `ContractEventV1`'s `sequence_number` (which encodes `BurnTokenEvent`'s implied position).
4. Compare against the actual `TokenStore.burn_events.count()` as of the state root committed at ledger version `V1` (obtainable via `main_db_reader.state_view_at_version(V1)`). Because `BurnTokenTranslator::translate_event_v2_to_v1` used `latest_state_checkpoint_view()` (reflecting `V2`'s post-state) when originally computing and caching this entry, the returned `sequence_number` will match the counter *after* the `V2` burn, not the counter as of `V1` — demonstrating the returned event is bound to the wrong ledger version's state.

struct BurnTokenTranslator;
impl EventV2Translator for BurnTokenTranslator {
    fn translate_event_v2_to_v1(
        &self,
        v2: &ContractEventV2,
        engine: &EventV2TranslationEngine,
    ) -> Result<ContractEventV1> {
        let burn = BurnToken::try_from_bytes(v2.event_data())?;
        let struct_tag = StructTag::from_str("0x3::token::TokenStore")?;
        let (key, sequence_number) = if let Some(state_value_bytes) =
            engine.get_state_value_bytes_for_resource(burn.account(), &struct_tag)?
        {
            let token_store_resource: TokenStoreResource = bcs::from_bytes(&state_value_bytes)?;
            let key = *token_store_resource.burn_events().key();
            let sequence_number = engine
                .get_next_sequence_number(&key, token_store_resource.burn_events().count())?;
            (key, sequence_number)
        } else {
            // If the token store resource is not found, we skip the event translation to avoid panic
            // because the creation number cannot be decided.
            return Err(AptosDbError::from(anyhow::format_err!(
                "Token store resource not found"
            )));
        };
        let burn_event = BurnTokenEvent::new(burn.id().clone(), burn.amount());
        Ok(ContractEventV1::new(
            key,
            sequence_number,
            BURN_TOKEN_EVENT_TYPE.clone(),
            bcs::to_bytes(&burn_event)?,
        )?)
    }
