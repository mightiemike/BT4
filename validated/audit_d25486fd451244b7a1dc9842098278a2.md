Confirmed: `EVMHooks.PostTxProcessing` runs after every EVM tx on Push Chain and calls `AttachRescueOutboundFromReceipt` for any `RescueFundsOnSourceChain` log emitted by `UNIVERSAL_GATEWAY_PC`, with no gating on who submitted the underlying transaction — it is triggered by ordinary user EVM calls, not an admin/module path.

### Title
Any unprivileged caller can permanently lock a stuck UTX's rescue slot with attacker-chosen gas parameters, freezing the victim's funds - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`AttachRescueOutboundFromReceipt` attaches a `RESCUE_FUNDS` outbound to an existing, stuck `UniversalTx` whenever a `RescueFundsOnSourceChain` event is observed. The function only checks that the *target* UTX is rescue-eligible (failed CEA deposit, or a `REVERTED` `INBOUND_REVERT`); it never checks that the caller/event `Sender` is the UTX's original owner, and it takes `GasFee`/`GasPrice`/`GasLimit` directly from attacker-controlled event data. Combined with the "only one active rescue at a time" guard, this lets any unprivileged address permanently deny the legitimate owner the ability to rescue their own stuck funds.

### Finding Description
`AttachRescueOutboundFromReceipt` [1](#0-0)  decodes an event whose `Sender`, `GasFee`, `GasPrice`, and `GasLimit` fields are fully attacker-controlled [2](#0-1) , and locates the target UTX purely by `universalTxId` from the event, without verifying that `event.Sender` matches `originalUtx.InboundTx.Sender` (or any authorized recipient). The eligibility check only inspects the UTX's own inbound/outbound status [3](#0-2) .

Once eligible, the code enforces "only one active (PENDING/OBSERVED) rescue at a time" per UTX [4](#0-3) , then creates the `RESCUE_FUNDS` outbound using the attacker-supplied gas parameters verbatim [5](#0-4) . This handler is invoked from the standard EVM post-processing hook that runs after *every* EVM transaction on Push Chain [6](#0-5)  — i.e., it is reachable by any unprivileged address, not just the UTX owner.

This is the direct analog of the PoolTogether tier-DoS bug class: a cheap, unprivileged, repeatable action ("claim a losing prize" ↔ "call rescue with garbage/insufficient gas parameters") is used to keep a shared, single-slot piece of state ("largest tier claimed" ↔ "active rescue outbound") artificially occupied, denying the legitimate/honest party the outcome they need. Here, an attacker can call the rescue path for someone else's stuck UTX with a deliberately unusable `GasFee`/`GasPrice`/`GasLimit` (e.g., far too low for the destination chain, or a `GasToken`/denomination the relayer infra can't use), which:
- occupies the PENDING rescue slot for that UTX,
- prevents the true owner from submitting their own, correctly-priced rescue call (rejected by the duplicate guard) as long as the bogus PENDING/OBSERVED rescue persists,
- and can be re-triggered by the attacker again as soon as the bogus outbound resolves (e.g., after a signing-deadline timeout reverts it), at negligible attacker cost (one EVM call), re-locking the slot indefinitely.

### Impact Explanation
This is a permanent-freezing-of-user-funds scenario reachable by any unprivileged attacker: as long as the attacker keeps re-occupying the single rescue slot on a victim's stuck `UniversalTx` with unusable gas parameters, the legitimate owner can never get their own valid rescue outbound accepted, and the funds that are already stuck on the source chain remain permanently unrecoverable through the rescue path. This matches the in-scope impact category "permanent freezing... of user or protocol-controlled funds" and the "refund accounting"/"revert flow" invariant called out in the scope.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged role, validator collusion, or TSS compromise is required. The attacker only needs to know a victim's `universalTxId` (derivable/observable on-chain) and be able to call the `UniversalGatewayPC` contract on Push Chain to emit the `RescueFundsOnSourceChain` event with arbitrary gas parameters, which any address can do for the price of one EVM transaction. The only friction is that the attack must be repeated whenever the bogus rescue outbound resolves out of the PENDING/OBSERVED slot, but that resolution itself doesn't require attacker cooperation (it can happen via signing-deadline timeout), so a persistent attacker can keep the slot perpetually occupied at low, bounded cost.

### Recommendation
- Require that `event.Sender` (or a similarly authenticated identity) matches the original UTX's `InboundTx.Sender` or `RevertInstructions.FundRecipient` before allowing a rescue outbound to be attached — i.e., restrict who may initiate a rescue for a given UTX.
- Do not trust attacker-supplied `GasFee`/`GasPrice`/`GasLimit` directly; validate them against `uregistry` chain-config bounds (minimum viable gas for the destination chain) before accepting the rescue, similar to how normal outbound gas parameters should be sanity-checked.
- Consider allowing the legitimate owner's rescue call to supersede/replace a still-PENDING rescue created by an unauthorized sender, or track "rescue attempts per authorized sender" separately from the global single-slot guard so an unauthorized party cannot block the true owner.

### Proof of Concept
1. Victim's UTX becomes rescue-eligible (their CEA deposit failed, or their `INBOUND_REVERT` outbound reached `REVERTED`).
2. Attacker (not the UTX's sender) calls `UniversalGatewayPC`'s rescue function directly, passing the victim's `universalTxId`, the correct `PRC20` token, and deliberately unusable `GasFee`/`GasPrice`/`GasLimit` (e.g., `1 wei` gas fee).
3. `EVMHooks.PostTxProcessing` → `AttachRescueOutboundFromReceipt` decodes the event, finds the UTX eligible, sees no existing active rescue, and attaches a new `RESCUE_FUNDS` outbound in `PENDING` status using the attacker's unusable gas parameters [7](#0-6) .
4. The victim now attempts their own legitimate rescue call with correct gas parameters; it is rejected: `"rescue: UTX %s already has an active rescue outbound"` [4](#0-3) .
5. When the attacker's bogus outbound eventually fails/reverts (e.g., signing deadline elapses or the relay can't execute with the given gas), the attacker immediately repeats step 2 with a new unusable-gas rescue call, re-locking the slot before the victim can act — indefinitely denying the victim their rescue.

Note: verification that the on-chain `UniversalGatewayPC` Solidity contract itself imposes no `msg.sender == original UTX sender` restriction could not be completed since that contract's source is outside the indexed Go repository; this analysis is based on the Go-side event decoding and keeper logic, which independently perform no such check regardless of what the contract does.

func (k Keeper) AttachRescueOutboundFromReceipt(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalGatewayPC := strings.ToLower(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_GATEWAY_PC"].Address)

	evmChainID, err := utils.ExtractEvmChainID(ctx.ChainID())
	if err != nil {
		return fmt.Errorf("rescue: failed to extract EVM chain ID: %w", err)
	}
	pushChainCaip := fmt.Sprintf("eip155:%s", evmChainID)

	for _, lg := range receipt.Logs {
		if lg.Removed {
			continue
		}
		if strings.ToLower(lg.Address) != universalGatewayPC {
			continue
		}
		if len(lg.Topics) == 0 {
			continue
		}
		if strings.ToLower(lg.Topics[0]) != strings.ToLower(types.RescueFundsOnSourceChainEventSig) {
			continue
		}

		event, err := types.DecodeRescueFundsOnSourceChainFromLog(lg)
		if err != nil {
			return fmt.Errorf("failed to decode RescueFundsOnSourceChain: %w", err)
		}

		// The universalTxId in the event is a 0x-prefixed bytes32 matching our UTX key.
		originalUtxId := strings.TrimPrefix(event.UniversalTxId, "0x")

		originalUtx, found, err := k.GetUniversalTx(ctx, originalUtxId)
		if err != nil {
			return fmt.Errorf("rescue: failed to fetch UTX %s: %w", originalUtxId, err)
		}
		if !found {
			return fmt.Errorf("rescue: original UTX %s not found", originalUtxId)
		}
		if originalUtx.InboundTx == nil {
			return fmt.Errorf("rescue: UTX %s has no inbound tx", originalUtxId)
		}

// RescueFundsOnSourceChainEvent holds decoded data from the RescueFundsOnSourceChain
// event emitted by UniversalGatewayPC when a user initiates a rescue on the source chain.
type RescueFundsOnSourceChainEvent struct {
	UniversalTxId  string   // 0x-prefixed bytes32 — the original UTX whose funds are stuck
	PRC20          string   // 0x-prefixed address — PRC20 token whose counterpart is locked
	ChainNamespace string   // source chain namespace (e.g. "eip155")
	Sender         string   // 0x-prefixed address — user who initiated the rescue
	TxType         TxType   // always TxType_RESCUE_FUNDS
	GasFee         *big.Int // gas fee charged (in gas-token units)
	GasPrice       *big.Int // gas price on the source chain
	GasLimit       *big.Int // gas limit used for the rescue execution
}
