### Title
Missing zero-address (all-null-hash) validation allows irrecoverable loss of TRX/TRC10 funds in transfer actuators - (File: actuator/src/main/java/org/tron/core/actuator/TransferActuator.java, actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java, common/src/main/java/org/tron/common/utils/DecodeUtil.java)

### Summary
The original report flags `FarmingPool`'s constructor for accepting a zero address for a token parameter with no validation, risking permanent fund loss. The structural analog in java-tron is `DecodeUtil.addressValid(byte[])`, the sole address-format check used across `TransferActuator`, `TransferAssetActuator`, `CreateAccountActuator`, and `VMUtils.validateForSmartContract`. This function only checks address length and the network prefix byte — it never rejects an address whose 20-byte payload is all zero. [1](#0-0) 

### Finding Description
`TransferActuator.validate()` and `execute()` call `DecodeUtil.addressValid(toAddress)` to check the destination address, but this function does not reject a payload of all zero bytes (only prefix byte + length are validated). [2](#0-1) 
As a result, a `TransferContract` (or `TransferAssetContract`) whose `to_address` is `<prefix_byte><20 zero bytes>` passes validation, silently creates a brand-new on-chain account at that address, and credits it with the transferred TRX or TRC10 balance. [3](#0-2) [4](#0-3) 
The same missing check exists in the internal TVM transfer/validation path used by `CALL`/message-call value transfers, `VMUtils.validateForSmartContract`, which also only calls `DecodeUtil.addressValid`. [5](#0-4) 
Because TRON addresses are derived from ECDSA public-key hashes, no known private key can produce an all-zero 20-byte hash (this is the same class of address as Ethereum's canonical "burn"/`0x0` address). Unlike the officially designated `Blackhole` account (which is explicitly configured in genesis and is intentionally used to permanently sink burned fees), the all-zero-payload address is not a recognized burn destination — it is simply an address nobody can control, and the actuator will happily create an account there and lock funds forever. [6](#0-5) 

### Impact Explanation
Any unprivileged user who (via wallet bug, malicious dApp, phishing-crafted payload, or fat-fingered input) submits a `TransferContract`/`TransferAssetContract` with `to_address` equal to the zero-payload address will have their TRX or TRC10 tokens irrecoverably and permanently locked, since no private key exists for that address. This is a genuine, unrecoverable state/accounting divergence: value is removed from circulation outside of the sanctioned `Blackhole`/burn accounting path (`burnTrx`), meaning total-supply bookkeeping and any downstream tooling that assumes burns only occur via the blackhole mechanism will be inconsistent. [7](#0-6) 

### Likelihood Explanation
Reaching this path requires no special privilege — any account holder can submit a standard `TransferContract` or `TransferAssetContract` through the public API/wallet stack, and the validation logic (`DecodeUtil.addressValid`) is the only address check performed before the transfer executes and a new account is created. [8](#0-7) 
Since this depends on the address being genuinely the zero-payload value (not attacker-controlled by others, only self-inflicted or induced via crafted UI/QR code/malicious dApp), likelihood is low-to-moderate but the impact for any affected account is total and irreversible.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid` (or at each call site: `TransferActuator`, `TransferAssetActuator`, `CreateAccountActuator`, `VMUtils.validateForSmartContract`) that rejects addresses whose 20-byte payload (after the prefix byte) is entirely zero, mirroring how Solidity contracts commonly reject `address(0)`.

### Proof of Concept
1. Construct a `TransferContract` with `owner_address` = a funded account and `to_address` = `<addressPreFixByte><20 bytes of 0x00>`.
2. Submit through the standard TRX transfer RPC/gRPC path (`WalletGrpc`/`FullNodeHttpApiService`).
3. `TransferActuator.validate()` calls `DecodeUtil.addressValid(toAddress)`, which only checks length (21 bytes) and prefix byte — both are satisfied — and does not detect that the payload is all-zero. [1](#0-0) 
4. `TransferActuator.execute()` proceeds to `accountStore.get(toAddress)` returning `null`, creates a brand new `AccountCapsule` at the zero-payload address, and credits the transferred `amount` to it. [9](#0-8) 
5. Because no EC key hashes to an all-zero value, the funds at this newly created account are permanently unspendable — total loss.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
