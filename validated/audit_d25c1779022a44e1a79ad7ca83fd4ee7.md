Based on the investigation, I found a valid, closely analogous vulnerability in java-tron.

### Title
Precision loss in legacy (V1) bandwidth/energy resource-limit calculation due to floor-division of frozen balance before weight multiplication - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The external report describes a bug class where an amount is floor-divided/truncated *before* being used in a proportional (weight-based) calculation, causing small/fractional quantities to be systematically undercounted, so a party receives less of a promised, proportionally-computed benefit even though no funds are lost. Java-tron's legacy resource-limit calculation (`calculateGlobalLimitV1`) exhibits the exact same root-cause pattern: it computes `weight = frozeBalance / TRX_PRECISION` (integer division) and only afterwards multiplies by the `totalLimit/totalWeight` ratio, discarding any frozen balance that is not an exact multiple of `TRX_PRECISION` (1,000,000 sun) before the proportional calculation is even performed.

### Finding Description
`ResourceProcessor.calculateGlobalLimitV1` floors the frozen balance to whole TRX before computing the account's share of the network bandwidth/energy limit: [1](#0-0) 

This is invoked from `EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit` whenever `hardenCalculation()` is enabled but the network has not activated `supportUnfreezeDelay()` (i.e., pre-Stake-2.0 "V1" freeze accounting): [2](#0-1) [3](#0-2) 

By contrast, the maintainers' own "hardened" V2 replacement explicitly preserves fractional weight by multiplying the raw `frozeBalance` first and dividing by `TRX_PRECISION * totalWeight` only once, at the end — the same fix pattern the external report recommends (increase precision/multiplier before dividing): [4](#0-3) 

The codebase's own test suite documents the resulting discrepancy: for a frozen balance of `1.5 * TRX_PRECISION`, the V1 path yields `floor(1.5) * 25 = 25` while the precision-preserving V2 formula yields the correct `1.5 * 25 = 37` — a 32% shortfall solely due to premature truncation: [5](#0-4) 

The V1 formula is reached through ordinary, unprivileged `FreezeBalanceContract` broadcast transactions on any network where the Stake 2.0 (`supportUnfreezeDelay`) feature has not been activated — a normal state for private/consortium chains built on java-tron, or historically on TRON mainnet prior to the Stake 2.0 hard fork.

### Impact Explanation
Accounts whose total frozen-for-bandwidth or frozen-for-energy balance is not an exact multiple of 1 TRX (1,000,000 sun) — which routinely occurs from delegation/undelegation partial adjustments and multiple freeze operations over time — receive a systematically lower bandwidth/energy limit than their economic stake proportionally entitles them to. This matches the reported impact category: "contract/protocol fails to deliver the promised (proportional) resource allocation, but doesn't lose value," since the frozen TRX itself remains safe and correctly accounted; only the derived resource entitlement is under-computed.

### Likelihood Explanation
Any account can trigger this path simply by freezing TRX via the standard `FreezeBalanceContract` transaction type on a network where `supportUnfreezeDelay` is not yet enabled and `allowHardenResourceCalculation` is enabled — both are ordinary, anonymous, unprivileged RPC/broadcast operations, requiring no special permissions. The condition (fractional-TRX frozen balance) is common in practice due to repeated freeze/delegate/undelegate cycles.

### Recommendation
Apply the same fix already used for the V2 path to the V1 path: multiply `frozeBalance` by `totalLimit` first, then divide once by `(TRX_PRECISION * totalWeight)` using `BigInteger`, instead of first floor-dividing `frozeBalance` by `TRX_PRECISION` to derive `weight`. This eliminates the premature truncation and matches the precision-preserving approach in `calculateGlobalLimitV2`.

### Proof of Concept
Using `ResourceProcessor.calculateGlobalLimitV1` directly (as exercised by the existing test), with `totalEnergyLimit = 50_000_000_000`, `totalEnergyWeight = 2_000_000_000`, `frozeBalance = 1_500_000` (1.5 TRX):
- V1 (current): `weight = 1_500_000 / 1_000_000 = 1` → `1 * 50_000_000_000 / 2_000_000_000 = 25`
- Correct proportional value: `1.5 * 50_000_000_000 / 2_000_000_000 = 37.5` (V2 formula yields `37`)

This 32%+ shortfall is reproducible for any frozen balance that is not an exact multiple of `TRX_PRECISION`, as already confirmed by `testV1FlooredWeightVsV2FractionalWeight` in the repository's own test suite: [6](#0-5)

```java
  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```

```java
  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
```

```java
  @Test
  public void testV1FlooredWeightVsV2FractionalWeight() {
    dbManager.getDynamicPropertiesStore().saveTotalEnergyCurrentLimit(50_000_000_000L);
    dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(2_000_000_000L);
    long frozeBalance = 1_500_000L; // 1.5 x TRX_PRECISION

    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(1);

    // V1 path
    dbManager.getDynamicPropertiesStore().saveUnfreezeDelayDays(0);
    ownerCapsule.setFrozenForEnergy(frozeBalance, 0L);
    dbManager.getAccountStore().put(ownerCapsule.getAddress().toByteArray(), ownerCapsule);
    long v1New = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);

    // Legacy V1 expectation: floor(1.5) * 25.0 = 1 * 25 = 25
    Assert.assertEquals(25L, v1New);

    // V2 path with the same balance keeps the fractional weight
    long v2New = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    // Legacy V2 expectation: 1.5 * 25.0 = 37.5 -> 37
    Assert.assertEquals(37L, v2New);

    // And both must match their respective legacy doubles
    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(0);
    long v1Old = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);
    long v2Old = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    Assert.assertEquals(v1Old, v1New);
    Assert.assertEquals(v2Old, v2New);
  }
```
