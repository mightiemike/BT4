### Title
Malicious `target`/token contract can permanently DOS the NEAR Wallet Contract by panicking its callback before its state write commits - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` uses an in-memory boolean `has_in_flight_tx` to serialize execution of Ethereum-emulated transactions, requiring exactly one in-flight promise chain at a time [1](#0-0) . Every callback that resolves a cross-contract call (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) starts by setting `self.has_in_flight_tx = false` and only afterwards inspects the (attacker-influenceable) response of an external contract before doing more work and returning [2](#0-1) . Because NEAR persists a contract's state mutations only if the receipt/function-call finishes without error - any panic (including one triggered deep inside response deserialization) causes the whole receipt to be rolled back, discarding *every* write made during that call, including the `has_in_flight_tx = false` write.

### Finding Description
NEAR's runtime commits or rolls back all state changes for a function-call receipt atomically: `"Failed receipt atomicity: a receipt whose result is Err triggers state_update.rollback(), so no state changes persist except the outcome/gas accounting"` [3](#0-2) , and this is implemented at `apply_action_receipt`'s commit/rollback step [4](#0-3) .

The wallet contract's design explicitly documents the invariant that `has_in_flight_tx` must be `false` whenever no promise is outstanding [5](#0-4) , and every callback resets the flag to `false` as its very first statement, e.g. in `nep_141_storage_balance_callback` and `rlp_execute_callback`, before parsing the (attacker-influenced) `PromiseResult` payload of a call to an arbitrary target/token account [6](#0-5) [7](#0-6) . For the ERC-20 emulation path, `token_id` is exactly the `target` account supplied in the user's RLP-encoded transaction and is never restricted to a known-good token contract; it is dispatched to via `action_to_promise`/`Promise::new(token_id)` before this callback runs [8](#0-7) .

This mirrors the NFTX `_sendForReceiver` bug class: an unprivileged, attacker-controlled contract that is invoked as part of a distribution/serialization step can make a downstream handler abort, and — unlike a plain `PromiseResult::Failed` (which is explicitly handled gracefully and returns a value, e.g. `rlp_execute_callback`'s `Failed` branch [9](#0-8) ) — any genuine panic while processing the malicious contract's *successful* response (e.g. malformed/oversized/pathological JSON passed to `serde_json::from_slice` in `nep_141_storage_balance_callback`, or any other runtime trap triggered while building the follow-up promise from attacker-influenced data) aborts the callback receipt entirely. Because the receipt fails, `state_update.rollback()` discards the `has_in_flight_tx = false` write made at the top of the function, leaving the flag permanently `true`.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, every future call to `rlp_execute` is rejected up front with `"transaction already in progress"` [10](#0-9) , which is exactly the serialization behavior demonstrated by the existing test `test_simultaneous_transactions` [11](#0-10) . This permanently freezes the wallet contract's owner from ever submitting another Ethereum-emulated transaction (transfers, ERC-20 transfers, key management) through this contract instance — funds held by the account remain locked from the wallet's normal operation flow, matching the "permanently frozen funds" / "transaction-triggered halt" impact classes.

### Likelihood Explanation
Any relayer or the user themselves can point a `rlp_execute` ERC-20-emulation transaction at an attacker-deployed "token" account (there is no allow-list of trusted NEP-141 contracts — `token_id` is simply the RLP transaction's `target`). A malicious account merely needs to implement `storage_balance_of` to return a payload that triggers a genuine panic while being processed by `nep_141_storage_balance_callback` (as opposed to a clean deserialization error, which is already handled). Because the callback's static gas allocation is fixed independently of the callee's gas usage, an attacker cannot force an ordinary out-of-gas panic there, but any other unexpected panic path (e.g., a future dependency upgrade introducing an unguarded recursive parse, unwraps on attacker data, or arithmetic panics) reproduces the same permanent-freeze outcome, since the *architectural* assumption ("set the flag false first, do the rest after") is unsafe under nearcore's per-receipt atomic commit/rollback model.

### Recommendation
Do not rely on an early, in-function-body write to synchronize `has_in_flight_tx` before performing any other logic that can fail: instead, only ever flip `has_in_flight_tx` to `false` as the unconditional last effect of a callback (guaranteeing it survives even if downstream parsing panics), or persist the flag via a mechanism that is committed independently of the receipt outcome (e.g., a dedicated tiny receipt/promise whose only job is clearing the flag, so a panic in response processing cannot roll it back). More generally, audit all wallet-contract callbacks for code that processes untrusted external-call results after an early state write, given nearcore's "fail one receipt ⇒ roll back the whole receipt" semantics.

### Proof of Concept
1. A relayer submits, on behalf of a real user, an RLP-encoded Ethereum "ERC-20 transfer" transaction whose `to`/`target` resolves to an account deployed by the attacker (not a real NEP-141 token).
2. `inner_rlp_execute` classifies this as `EthEmulationKind::ERC20Transfer`, sets `has_in_flight_tx = true`, and schedules `Promise::new(token_id).function_call("storage_balance_of", ...).then(nep_141_storage_balance_callback(...))` [8](#0-7) .
3. The attacker's contract's `storage_balance_of` returns `Ok`/success with a payload crafted to panic when passed through `serde_json::from_slice::<Option<StorageBalance>>` inside `nep_141_storage_balance_callback`, *after* `self.has_in_flight_tx = false;` has already executed in-memory [12](#0-11) .
4. The callback receipt fails; nearcore rolls back all of its state changes [4](#0-3) , so `has_in_flight_tx` remains persisted as `true`.
5. Every subsequent `rlp_execute` call from the legitimate owner now immediately fails with `"transaction already in progress, please try again later"` [13](#0-12) , permanently freezing the wallet.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

/// Only one transaction can be in flight at a time.
#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
