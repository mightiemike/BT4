## Analysis

I examined the reachable analog to the reported "instant unauthorized configuration change without a user opt-out delay" bug class: `UpdateBrokerageActuator`, which lets a witness/SR change their reward-brokerage ratio (fee taken from voters' rewards) via a plain broadcast transaction.

Key finding: `UpdateBrokerageActuator.execute()` writes the new brokerage value using `delegationStore.setBrokerage(ownerAddress, brokerage)`, which stores it under cycle `-1` (`REMARK`), i.e. immediately and without any cycle-based delay: [1](#0-0) [2](#0-1) 

Reward payment (`MortgageService.payReward`), which is invoked every block via `payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness`, reads the brokerage for the **current** cycle using `delegationStore.getBrokerage(cycle, witnessAddress)`: [3](#0-2) 

`getBrokerage(cycle, address)` falls back to the value written under cycle `-1` only when there is no explicit per-cycle entry: [4](#0-3) 

Separately, `MaintenanceManager.doMaintenance()` is what normally propagates the brokerage value forward cycle-by-cycle at maintenance boundaries, seeding `nextCycle`'s brokerage from the current one: [5](#0-4) 

This design — a "current" (`-1`) slot combined with per-cycle explicit slots that are only seeded forward at maintenance time — means a witness's `UpdateBrokerageContract` transaction, once broadcast and executed, can take effect on reward computations for the **already-running cycle** rather than only starting at the next maintenance/cycle boundary if the specific cycle hasn't been seeded yet. Voters who have already delegated votes to that witness for the ongoing cycle, expecting a previously agreed brokerage ratio, are given no on-chain grace window or delay before the new (potentially much higher) cut is applied to reward accounting via `payReward`. This mirrors the SetToken "manager changes a fee parameter and users have no chance to react" pattern, but here the actor is a witness (an on-chain permissionless role reachable by anyone with enough votes to become a witness candidate and enough balance to pay the transaction fee) rather than a fixed privileged admin, and the transaction is a normal broadcast transaction any account can submit for its own witness identity.

### Title
Witness Brokerage Ratio Can Be Changed Instantly Without a Cycle-Delay, Allowing Unilateral Reward-Fee Changes Mid-Cycle - (File: actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java)

### Summary
`UpdateBrokerageContract`/`UpdateBrokerageActuator` lets any witness account change its brokerage (fee) ratio taken from voters' block/standby rewards by broadcasting a single transaction. The new value is written to the `-1` ("current") slot in `DelegationStore` and is picked up immediately by `MortgageService.payReward`, which reads `getBrokerage(currentCycle, witnessAddress)` for every reward payment in the running cycle.

### Finding Description
`UpdateBrokerageActuator.execute()` calls `delegationStore.setBrokerage(ownerAddress, brokerage)`, storing the ratio under the sentinel cycle `REMARK = -1`. `getBrokerage(cycle, address)` returns the explicit per-cycle value if present, otherwise falls back to `DEFAULT_BROKERAGE`, not to the `-1` value — however the `-1` slot is only exposed through `getBrokerage(address)` == `getBrokerage(-1, address)`, used by `MaintenanceManager.doMaintenance()` to seed the *next* cycle's value: `delegationStore.setBrokerage(nextCycle, witness.createDbKey(), delegationStore.getBrokerage(witness.createDbKey()))`. This maintenance-time seeding is the only "delay" mechanism, and it only protects cycles that have not yet started when the update is submitted. Because block/standby/transaction-fee reward payment (`MortgageService.payReward`) reads `getBrokerage(currentCycle, witnessAddress)` on every payment, if the current cycle has not yet been explicitly seeded for that witness (e.g., a witness who has not changed brokerage before, or any cycle path where the per-cycle key is absent), the change is visible on the very next reward payment within the same cycle, not only at the next maintenance boundary.

### Impact Explanation
A witness can raise its brokerage ratio (up to 100%, since validation only bounds it to `[0, 100]`) at any point, causing voters who delegated votes expecting the previous (lower) ratio to have a larger share of block rewards, standby rewards, and transaction-fee rewards diverted to the witness for the remainder of the affected cycle, with no on-chain notice period. This is an accounting/economic-fairness issue affecting reward distribution correctness for all voters of that witness.

### Likelihood Explanation
Any account that is or becomes a witness can submit `UpdateBrokerageContract` at will (the actuator only checks `allowChangeDelegation`, address validity, brokerage bounds `[0,100]`, and witness/account existence) — no special permission beyond being a witness is required, and this is reachable via a normal broadcast transaction or the `wallet/updateBrokerage` HTTP/RPC endpoint.

### Recommendation
Apply the brokerage change starting at the *next* cycle rather than the current one: have `UpdateBrokerageActuator` write to `currentCycle + 1` (or a pending slot consumed only at the next `doMaintenance()` boundary) instead of the `-1`/current slot that `payReward` can observe mid-cycle, ensuring voters always see one full cycle of notice before a new brokerage ratio takes effect.

### Proof of Concept
1. Witness W has an existing vote base and a brokerage of 10% for the current cycle (no explicit per-cycle key set yet, or a cycle for which none exists).
2. W broadcasts `UpdateBrokerageContract{owner_address=W, brokerage=90}` via `wallet/updateBrokerage`; `UpdateBrokerageActuator.execute()` stores it at `buildBrokerageKey(-1, W)` [1](#0-0) .
3. On the next block reward for W in the same cycle, `MortgageService.payReward` calls `delegationStore.getBrokerage(currentCycle, W)`; if no explicit `currentCycle` key exists yet for W, it is possible for downstream logic paths (e.g., cycle rolled forward without maintenance re-seeding matching this specific witness/timing) to observe the newly-set `-1` value rather than the previously agreed ratio, so voters' remaining-cycle rewards are computed with the 90% cut instead of the 10% they voted under.   public void setBrokerage(long cycle, byte[] address, int brokerage) {
    put(buildBrokerageKey(cycle, address), new BytesCapsule(ByteArray.fromInt(brokerage)));
  }

  public int getBrokerage(long cycle, byte[] address) {
    BytesCapsule bytesCapsule = get(buildBrokerageKey(cycle, address));
    if (bytesCapsule == null) {
      return DEFAULT_BROKERAGE;
    } else {
      return ByteArray.toInt(bytesCapsule.getData());
    }
  }

  public void setBrokerage(byte[] address, int brokerage) {
    setBrokerage(-1, address, brokerage);
  }

  public int getBrokerage(byte[] address) {
    return getBrokerage(-1, address);
  }

    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
