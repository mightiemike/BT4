### Title
Meta-transaction (`DelegateAction`) signatures omit any chain/network identifier, enabling cross-network replay of a signed delegate action - (File: `core/primitives/src/action/delegate.rs`)

### Summary
NEP-366 meta-transactions are signed via `SignableMessage`/`get_nep461_hash`, whose payload is built only from a NEP discriminant plus the `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). No `genesis_hash`, `chain_id`, or `network_id` is included in the signed bytes, mirroring the reported bug class where an EIP-712 signature omitted `chainID`, letting it be replayed on another chain.

### Finding Description
`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify` only check that the signature matches `delegate_action.get_nep461_hash()` against the embedded `public_key`: [1](#0-0) 

The signed payload is constructed with `SignableMessage`, whose only network-independent binding is a NEP discriminant (a constant distinguishing NEP-366/611 message types), not anything tied to a specific chain instance: [2](#0-1) [3](#0-2) 

The `DelegateAction` struct itself carries no chain-identifying field — only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`: [4](#0-3) 

Contrast this with ordinary `SignedTransaction`s, which are bound to a specific chain instance via `block_hash` (a hash of an actual block on that particular chain, checked against `transaction_validity_period`): [5](#0-4) 

`DelegateAction.max_block_height` is only a plain integer height bound, not a chain-specific hash, so it does not anchor the signature to one particular chain the way `block_hash` does for regular transactions. The only replay defense applied at execution time (`apply_delegate_action` → `validate_delegate_action_key`) is the sender's access-key nonce check and the `max_block_height` bound, both of which are evaluated purely against the local chain's own state: [6](#0-5) 

Consequently, the exact same signed `SignedDelegateAction` bytes are valid on any NEAR-protocol-compatible network (e.g., a second network sharing the same account IDs/keys, such as a cloned/forked chain, a redeployed testnet, or any environment where a user's account and access-key state happen to match) as long as the nonce and max-height checks pass there too — the signature itself carries nothing that scopes it to a single chain instance.

### Impact Explanation
If a relayer/attacker obtains a valid `SignedDelegateAction` (which is explicitly designed to be shared off-chain with a relayer for wrapping into a transaction), that same signed payload can be resubmitted, unmodified, on any other NEAR-compatible network where the sender account exists with a matching access key and nonce state. This can cause unauthorized execution of the delegated actions (e.g., token transfers, key additions, function calls) on a network the signer never intended to authorize for, resulting in unauthorized value movement or state changes attributable to the signer without their consent on that chain.

### Likelihood Explanation
The precondition (identical account/key/nonce state existing on two chains) is realistic in several concrete NEAR-ecosystem workflows: developers and users routinely reuse the same account name and key pair across `mainnet`, `testnet`, and custom/forked networks, and relayer infrastructure is explicitly designed to receive and forward user-signed `DelegateAction`s from users who may not control (or be aware of) which network the relayer ultimately submits to. Because the signed bytes are the entire authorization artifact handed to a third-party relayer, exploitation requires no special privilege beyond being that relayer or intercepting the delegate action, which is a normal, expected entity in the meta-transaction flow.

### Recommendation
Bind the NEP-366/611 signed message to the specific chain instance, e.g. by including the network's `genesis_hash` (or another chain-instance identifier available in `ApplyState`/`RuntimeConfig`) as part of the `SignableMessage`/`get_nep461_hash` payload, or as an explicit field of `DelegateAction`/`DelegateActionV2`, and reject verification/execution when it does not match the local chain's identifier.

### Proof of Concept
1. Deploy the same account (`alice.near`-equivalent) with the same public key and matching access-key nonce on two distinct NEAR-protocol networks (e.g., a custom testnet clone and another environment sharing seeded state).
2. Alice signs a `DelegateAction` (e.g., transferring funds or adding a full-access key) intended for use only on network A, and hands the `SignedDelegateAction` to a relayer as per the NEP-366 flow: [7](#0-6) 
3. The relayer (or an attacker who intercepts the delegate action) wraps the identical `SignedDelegateAction` bytes in an outer transaction and submits it to network B instead, as done in the test helper pattern: [8](#0-7) 
4. Because `verify()` only checks the signature against the NEP-366 discriminant-tagged action bytes (no chain identifier) and `apply_delegate_action` only checks nonce/`max_block_height` against network B's own state, the action executes successfully on network B despite Alice never authorizing use of her signature there: [9](#0-8)

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

**File:** docs/architecture/how/meta-tx.md (L40-52)
```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.
```
