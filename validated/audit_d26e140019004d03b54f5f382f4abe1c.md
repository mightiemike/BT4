### Title
`get_expected_burns` accepts non-canonical `burn_view_consensus_hash` snapshot as `expected_burn` - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoChainState::get_expected_burns` resolves a tenure-change block's `burn_view_consensus_hash` via `SortitionDB::get_block_snapshot_consensus`, a bare `SELECT * FROM snapshots WHERE consensus_hash = ?1` query with no canonicity filtering. Neither `get_expected_burns` nor the burn-view linkage check performed before it (`get_block_burn_view`) re-verifies that this consensus hash is on the node's currently canonical Bitcoin/PoX fork — only that it is a fork-consistent descendant of the parent block's already-accepted burn view.

### Finding Description
The broken equality: `header.burn_spent` (accepted) should equal the burn total of the block's *canonical* tenure snapshot, but the code only checks it equals `burn_view_sn.total_burn` for whatever snapshot row matches `burn_view_consensus_hash`, canonical or not.

- `get_expected_burns` (`stackslib/src/chainstate/nakamoto/mod.rs:2625-2648`) takes `&tenure_payload.burn_view_consensus_hash` and calls `SortitionDB::get_block_snapshot_consensus(sort_handle.sqlite(), burn_view_ch)`, which is implemented as `"SELECT * FROM snapshots WHERE consensus_hash = ?1"` (`stackslib/src/chainstate/burn/db/sortdb.rs:4955-4967`) — no `pox_valid`/ancestor check at all, unlike the sibling helpers `check_valid_consensus_hash` (`stackslib/src/chainstate/nakamoto/tenure.rs:614-637`) and `has_consensus_hash` (`stackslib/src/chainstate/burn/db/sortdb.rs:2657-2676`), which explicitly compute `get_ancestor_sort_id(...)` against the handle's canonical chain tip before trusting the snapshot.
- The only guard placed on `burn_view_consensus_hash` prior to this (the `get_block_burn_view` logic, mirrored in `contrib/stacks-inspect/src/lib.rs:1218-1286`) verifies that the *parent block's* burn view is an ancestor of the candidate `burn_view_ch`'s own fork history (`get_ancestor_sort_id(&handle, parent_burn_view_sn.block_height, &handle.context.chain_tip)`). This proves monotonic descent from the parent's burn view along *some* consistent Bitcoin/PoX history, but it does not prove `burn_view_ch` is on the fork the local node currently considers canonical. If two sortition histories with a common ancestor at/above the parent's burn-view height coexist in the sortdb (e.g., during a Bitcoin/PoX-fork window), an attacker can choose a `burn_view_ch` on the non-canonical branch; it will still pass the connectivity check and `get_expected_burns` will happily return that branch's `total_burn`.
- `common_validate_against_burnchain` (`stackslib/src/chainstate/nakamoto/mod.rs:1863-1898`) and the `append_block` inline check (`stackslib/src/chainstate/nakamoto/mod.rs:5138-5171`) then only compare `header.burn_spent` against this unvalidated `expected_burn` — they never re-derive or re-check canonicity of `burn_view_ch` itself.
- `validate_nakamoto_tenure_snapshot` (`stackslib/src/chainstate/nakamoto/mod.rs:2654-2697`) does enforce canonicity, but only for `block.header.consensus_hash` (the tenure-start sortition), not for `burn_view_consensus_hash`, which is a distinct field used specifically by tenure-extend blocks and can legitimately differ from `header.consensus_hash`.

### Impact Explanation
If exploited, a block whose committed burn total does not match its true (canonical) tenure's burn total can be accepted by `append_block`/`accept_block`. Because `header.burn_spent` propagates into consensus-relevant state and other nodes deterministically recompute the canonical burn view for the same tenure-change payload, a node that has (or later obtains) only the canonical branch of the fork will compute a different `expected_burn` and reject the block, while a node retaining the non-canonical branch accepts it — a tip/state divergence between honest nodes. This matches the Critical category (invalid block accepted by some nodes / non-reproducible state) since it corrupts the shared assumption that `burn_spent` reflects the canonical burn total.

### Likelihood Explanation
Exploitation requires a very specific precondition: the sortition DB must retain two extant sortition histories that share a common ancestor no earlier than the parent block's already-accepted burn view (i.e., an active/residual Bitcoin or PoX fork window), and the attacker must be actively mining the tenure-change block during that exact window. This is a narrow, transient timing condition rather than something the attacker can force at will, and it depends on real chain conditions (Bitcoin reorg/PoX-fork persistence in the DB) that are outside the attacker's control. It requires no more than a single miner slot / minority stake to craft the malicious tenure payload, but the enabling DB state is opportunistic, not attacker-controlled.

### Recommendation
In `get_expected_burns`, after resolving `burn_view_sn` via `get_block_snapshot_consensus`, additionally verify canonicity the same way `check_valid_consensus_hash`/`has_consensus_hash` do: compute `get_ancestor_sort_id`/`get_block_snapshot_by_height` relative to the sortition handle's true canonical tip (not merely relative to the candidate hash's own fork) and reject if the resolved sortition is not the canonical ancestor at that height. This closes the gap between the parent-descent check and true global canonicity.

### Proof of Concept
Rust integration test plan (two-fork harness):
1. Build a sortdb harness that produces two Bitcoin/PoX forks (Fork A canonical, Fork B non-canonical) diverging above the parent tenure's burn-view height, both persisted in the same sortition DB (as in `stackslib/src/burnchains/tests/mod.rs` fork-building helpers).
2. Process one or more Nakamoto blocks so a parent Stacks block has burn_view = snapshot on the common ancestor.
3. Construct a `NakamotoBlock` with a tenure-change payload whose `burn_view_consensus_hash` = the consensus hash of a snapshot on Fork B (non-canonical), and set `header.burn_spent` to Fork B's `total_burn` (deliberately different from Fork A's `total_burn` at the equivalent height).
4. Assert:
   - `SortitionDB::get_block_snapshot_consensus(sortdb.conn(), fork_b_ch)` succeeds and returns Fork B's `total_burn` (showing the DB happily returns non-canonical rows).
   - `NakamotoChainState::get_expected_burns(&sort_handle_rooted_at_fork_a_tip, chainstate.db(), &block)` returns `Some(fork_b_total_burn)` instead of erroring or matching Fork A's canonical total.
   - `NakamotoChainState::append_block(...)` (or `accept_block`) succeeds for this block even though `fork_b_total_burn != fork_a_canonical_total_burn`, demonstrating the divergence: two nodes holding only Fork A vs. only Fork B would compute different `expected_burn` and diverge on whether this block is valid.     pub(crate) fn get_expected_burns<SH: SortitionHandle>(
        sort_handle: &SH,
        chainstate_conn: &Connection,
        block: &NakamotoBlock,
    ) -> Result<Option<u64>, ChainstateError> {
        let burn_view_ch = if let Some(tenure_payload) = block.get_tenure_tx_payload() {
            &tenure_payload.burn_view_consensus_hash
        } else {
            // if there's no new tenure for this block, the burn total should be the same as its parent
            let parent_burns_opt =
                Self::get_block_header(chainstate_conn, &block.header.parent_block_id)?
                    .map(|parent| parent.anchored_header.total_burns());
            return Ok(parent_burns_opt);
        };
        let burn_view_sn =
            SortitionDB::get_block_snapshot_consensus(sort_handle.sqlite(), burn_view_ch)?
                .ok_or_else(|| {
                    warn!("Could not load expected burns -- no such burn view";
                          "burn_view_consensus_hash" => %burn_view_ch
                    );
                    ChainstateError::NoSuchBlockError
                })?;
        Ok(Some(burn_view_sn.total_burn))
    }

            ));
        };

    /// Is a consensus hash's sortition valid on the fork represented by this handle?
    /// Return Ok(true) if so
    /// Return Ok(false) if not (including if there is no sortition with this consensus hash)
    /// Return Err(..) on DB error
    pub fn has_consensus_hash(&self, consensus_hash: &ConsensusHash) -> Result<bool, db_error> {
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(self, consensus_hash)? else {
            // no sortition with this consensus hash
            return Ok(false);
        };

        let Some(expected_sortition_id) =
            get_ancestor_sort_id(self, sn.block_height, &self.context.chain_tip)?
        else {
            // no ancestor at this sortition height relative to this chain tip
            // (e.g. perhaps this consensus hash is in the "future" relative to this chain tip)
            return Ok(false);
        };

        Ok(sn.sortition_id == expected_sortition_id)
    }

    /// Check that a consensus hash is on the canonical burnchain fork
    /// Returns Some(corresponding snapshot) if so
    /// Returns None if it's not on the canonical fork
    pub(crate) fn check_valid_consensus_hash<SH: SortitionHandle>(
        sort_handle: &mut SH,
        ch: &ConsensusHash,
    ) -> Result<Option<BlockSnapshot>, ChainstateError> {
        // the target sortition must exist, and it must be on the canonical fork
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(sort_handle.sqlite(), ch)? else {
            // no sortition
            warn!("Invalid consensus hash: no such snapshot"; "consensus_hash" => %ch);
            return Ok(None);
        };
        let Some(ancestor_sn) = sort_handle.get_block_snapshot_by_height(sn.block_height)? else {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %ch);
            return Ok(None);
        };
        if ancestor_sn.sortition_id != sn.sortition_id {
            // not canonical
            return Ok(None);
        }
        Ok(Some(sn))
    }
