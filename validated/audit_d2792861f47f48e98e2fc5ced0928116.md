Based on the investigation, I found a valid analog in the codebase. Multiple operator-facing Go scripts under `core/scripts/` accept raw hex private keys directly as CLI flags (rather than via `.env`-only or prompt-based secure input), which will be captured verbatim in shell history whenever an operator supplies them on the command line, exactly matching the reported bug class.

### Title
Private key accepted as a plaintext CLI flag in gateway/reconciler operator scripts, exposing it to shell history - ([File: core/scripts/gateway/web_api_trigger/invoke_trigger.go])

### Summary
`core/scripts/gateway/web_api_trigger/invoke_trigger.go`, `core/scripts/gateway/client/send_request.go`, and `core/scripts/cre/reconciler/cmd.go` each define a `--private_key` / `-deployer-key` command-line flag that accepts a raw hex-encoded ECDSA private key as an argument. When an operator invokes these tools by typing the key directly on the command line (which the README for the gateway client explicitly shows as an option via `flag.String("private_key", ...)`), the full plaintext secret is persisted by the shell into `.bash_history`/`.zsh_history` (or equivalent), and can also leak via `ps`/process listings and shell job control while the process is running.

### Finding Description
In `invoke_trigger.go`, the flag is declared as:
`privateKey := flag.String("private_key", "65456ffb8af4a2b93959256a8e04f6f2fe0943579fb3c9c3350593aabb89023f", "Private key to sign the message with")` [1](#0-0) , and the value is only used as a `.env` fallback if empty, meaning a supplied CLI value takes precedence and is used directly to parse the key via `crypto.HexToECDSA(*privateKey)` [2](#0-1) . The sibling script `send_request.go` has the identical pattern: `privateKey := flag.String("private_key", "", "Private key to sign the message with")` [3](#0-2) , with the accompanying README explicitly documenting `.env` usage but the flag still accepting the key as a CLI argument [4](#0-3) . Separately, the CRE reconciler's `apply` command defines `--deployer-key` as a plaintext hex private key flag: `applyCmd.Flags().StringVar(&flagDeployerKey, "deployer-key", "", "hex private key for the on-chain deployer (defaults to the Anvil dev account)")` [5](#0-4) . This key is subsequently used to derive the deployer address and sign on-chain transactions, e.g. `deployerAddress(deployerKey string)` parses it with `ethcrypto.HexToECDSA(privateKeyHex)` [6](#0-5) . Notably, the reconciler's own maintainers-facing `TODO.md` flags this exact risk for the deployer key, stating the single `--deployer-key` (cmd.go:116) is used for every chain's transactor and workflow-owner derivation, and explicitly calls out "Never log the keys" as an open concern for the planned multi-key refactor [7](#0-6) , confirming this is a known-but-unaddressed root cause rather than a purely theoretical one.

### Impact Explanation
Any operator, CI job, or automation script that supplies these keys as CLI arguments causes signing keys (gateway client keys or on-chain deployer keys) to be written to shell history files and become visible to any local process listing during execution. Because the deployer key signs real on-chain transactions and controls the workflow-owner address on the registry chain, and the gateway client key signs authenticated requests to the Functions gateway (including S4 secret set/list operations), disclosure of these keys via history/process leakage constitutes a direct secret disclosure that can lead to unauthorized transaction signing or unauthorized gateway API access.

### Likelihood Explanation
Likelihood is moderate: these are internal/operator tooling scripts (not user-facing production node code), so exploitation requires local access to the operator's machine or its history/process table, or the operator running the tool interactively with the flag rather than via `.env`. However, the pattern is used in at least three separate scripts across the gateway-client and CRE-reconciler tooling, and the reconciler's own TODO explicitly flags the deployer key as sensitive and un-remediated, indicating real operational usage where the risk can materialize.

### Recommendation
- Remove the ability to pass private keys via CLI flags in `invoke_trigger.go`, `send_request.go`, and `cmd.go`; require them only via environment variables, `.env` files with restricted permissions, or a secrets manager.
- For `invoke_trigger.go`, remove the hardcoded default private key literal from the flag definition entirely, as it is currently baked into the source itself.
- For the reconciler's `--deployer-key`, follow through on the TODO's own recommendation to source keys from `PRIVATE_KEY_<CHAIN_ID>` env vars or a secret store, and never log or echo them.
- Where CLI flags must remain for backward compatibility, add prominent warnings and prefer reading from stdin or a file path instead of a raw value.

### Proof of Concept
```
go run core/scripts/gateway/web_api_trigger/invoke_trigger.go -private_key=65456ffb8af4a2b93959256a8e04f6f2fe0943579fb3c9c3350593aabb89023f -gateway_url http://localhost:5002
```
Running this from an interactive shell results in the full private key being written verbatim into `~/.bash_history` (or equivalent), and visible via `ps aux` while the process runs. The same applies to:
```
go run core/scripts/cre/reconciler apply --deployer-key=0x<hex-private-key>
```
