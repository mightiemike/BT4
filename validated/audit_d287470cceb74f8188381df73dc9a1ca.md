### Title
Silent skip of state-value proof verification on error in `DbStateView::get` - (File: storage/storage-interface/src/state_store/state_view/db_state_view.rs)

### Summary
`DbStateView`, constructed via `VerifiedStateViewAtVersion::verified_state_view_at_version`, is documented and intended to serve state reads that are cryptographically bound to a `state_root_hash` obtained from a transaction-info proof verified against a trusted `LedgerInfo`. However, the actual read path only performs the proof check inside an `if let Ok(...)` guard, so any error returned by the proof-fetching call causes verification to be silently skipped, and the function falls through to return the raw, unverified value anyway.

### Finding Description
`verified_state_view_at_version` establishes the trust anchor for a `DbStateView`: it verifies a `TransactionWithProof` against the caller-supplied `ledger_info`, extracts `state_checkpoint_hash` from the now-trusted `TransactionInfo`, and stores it as `maybe_verify_against_state_root_hash`. [1](#0-0) 

The actual value lookup in `DbStateView::get` is supposed to use that root hash to authenticate every returned value: [2](#0-1) 

The critical flaw is the control flow:
```rust
if let Ok((value, proof)) = self.db.get_state_value_with_proof_by_version(key, version) {
    proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
}
Ok(self.db.get_state_value_with_version_by_version(key, version)?)
```
If `get_state_value_with_proof_by_version` returns `Err` (for any reason — pruned proof/JMT node data, an internal storage error, a version whose merkle proof path is not retrievable, a transient I/O error, or any other backend condition unrelated to malicious input), the `if let Ok(...)` simply does not execute the `proof.verify(...)` branch and does not propagate the error. Execution falls straight through to the unconditional second call, `get_state_value_with_version_by_version`, which returns whatever raw value is currently stored — without any Merkle-proof check against `root_hash` at all.

This breaks the fundamental invariant that a `DbStateView` obtained from `verified_state_view_at_version` (i.e., a "verified" state view) only serves values authenticated against the trusted state root. Instead, the verification is best-effort and degrades to no-verification whenever the proof side-channel errors, while the caller has no way to detect that the returned value was unverified.

### Impact Explanation
Any consumer relying on `DbStateView`/`VerifiedStateViewAtVersion` to serve values that are cryptographically bound to a specific ledger version and root hash (e.g., tooling or components that build a "verified" view over a `DbReader` to answer state queries against an untrusted or partially-synced local store) can silently receive a value that was never checked against the accumulator/JMT proof. If the underlying storage returns stale, corrupted, or otherwise-diverged data for `get_state_value_with_version_by_version` while the proof-fetch path errors out (e.g. due to partial pruning, concurrent restore/compaction, or storage inconsistency), the caller will treat that unverified value as proof-verified, i.e., authenticated output that is not actually bound to the claimed version/root. This is a state-view/proof-binding integrity break as scoped by the "Authenticated API or state-view output bound to the wrong version, object, or proof context" pivot.

### Likelihood Explanation
This does not require a malicious peer; it only requires the local storage backend to return an `Err` from `get_state_value_with_proof_by_version` for a version/key combination while `get_state_value_with_version_by_version` still succeeds with a (possibly stale/incorrect) value — a realistic condition during pruning races, partial restores, or general backend errors, all of which are plausible in a long-running fullnode/validator. The comment in the code ("DB doesn't support returning proofs for buffered state, so only optionally verify proof") shows this fallback is an intentional design compromise, not a rare corner case, making the unverified path reachable in normal operation, not just adversarial conditions.

### Recommendation
Do not silently swallow errors from the proof-fetch call. Either:
- Propagate the error (fail closed) when a root hash is set and the proof cannot be obtained, instead of falling back to an unverified read; or
- Explicitly document and gate (via a distinct, opt-in code path) that verification is skipped, and ensure callers who need authenticated data cannot reach the fallback silently.

At minimum, change `if let Ok((value, proof)) = ... { proof.verify(...)? }` to propagate the `Err` case with `?` when `maybe_verify_against_state_root_hash` is `Some`, so verification failures (including inability to fetch a proof) cause the read to fail rather than silently degrading to unverified data.

### Proof of Concept
1. Construct a `DbStateView` via `verified_state_view_at_version(Some(v), ledger_info)`, which sets `maybe_verify_against_state_root_hash = Some(state_root_hash)`.
2. Arrange (or simulate, e.g., via a custom `DbReader` implementation or a real backend where pruning/partial-restore is in progress) for `get_state_value_with_proof_by_version(key, v)` to return `Err(..)` while `get_state_value_with_version_by_version(key, v)` still returns `Ok(Some((v', bad_value)))` for the same key/version (a case that is directly exercisable by implementing a test `DbReader` since `get()` only requires the trait boundary, and is documented as expected on the "buffered state" path in production).
3. Observe that `DbStateView::get` returns `Ok(Some((v', bad_value)))` with no error and no proof failure, even though `bad_value` was never checked against `state_root_hash`.

Note: due to index size limits I was only able to inspect `db_state_view.rs` directly; I could not fully trace every concrete caller of `verified_state_view_at_version` in this session, so I cannot confirm every downstream consumer's exposure — a Devin session with full repo access would be needed to enumerate call sites and confirm end-to-end mainnet impact with certainty.
