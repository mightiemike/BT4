## Finding confirmed by code inspection

The exploit hypothesis is correct: the `Proof<E>` struct's `hat_C: E::G1Affine` field (and every other curve-point field nested inside a PVSS `Transcript<P>`) is deserialized with **subgroup validation explicitly disabled**, because the whole `Transcript<P>`/`SharingProof<E>` tree is decoded through the `ark_de` serde shim, not through a directly-validated `CanonicalDeserialize::deserialize_compressed` call.

### Title
Subgroup-check bypass in PVSS `Transcript` deserialization allows off-curve-subgroup `hat_C` to reach the range-proof sigma-protocol verifier - (File: `crates/aptos-crypto/src/arkworks/serialization.rs`)

### Summary
`ark_de`, the serde deserialization helper used by `Transcript<P>` and `SharingProof<E>` for all Arkworks-typed fields, calls `CanonicalDeserialize::deserialize_with_mode(..., Validate::No)`: [1](#0-0) 

`Validate::No` propagates recursively through every derived `CanonicalDeserialize` impl on the path down to `dekart_univariate_v2::Proof<E>::hat_C`. In particular, `FirstProofItem`'s hand-written `CanonicalDeserialize` impl only invokes the subgroup-membership `check()` when `validate == Validate::Yes`: [2](#0-1) 

Since `Transcript<P>` marks its Arkworks fields with `#[serde(... deserialize_with = "ark_de")]`: [3](#0-2) 

and `SharingProof<E>::range_proof` is `dekart_univariate_v2::Proof<E>` whose `hat_C: E::G1Affine` field is declared with the ordinary derive macro: [4](#0-3) 

the entire chain (`Transcript` → `SharingProof` → `Proof` → `hat_C`) is decoded with `Validate::No`. On BLS12-381, `G1Affine` has a non-trivial cofactor, so a point can satisfy the short-Weierstrass curve equation (and thus pass the on-curve check baked into point decompression) while **not** lying in the prime-order subgroup used by the protocol. Such a point is only rejected when `Valid::check()` (the cofactor/subgroup check) runs — which is skipped here.

### Finding Description
`hat_C` subsequently flows unchanged into `pairing_for_verify`, where it is combined with the commitment and passed straight into the Okamoto-style two-term MSM sigma-protocol verifier: [5](#0-4) 

`two_term_msm::Homomorphism::verify` performs group arithmetic and an MSM-based linear-relation check over `E::G1` assuming all operands are in the correct prime-order subgroup — a foundational assumption for the soundness of Okamoto's proof of knowledge. If `hat_C` (equivalently `hatC_proj - comm_g1`, the sigma-protocol "statement") contains a component in the small cofactor subgroup, an adversarial dealer can craft `hat_C`, `pi_PoK` such that the linear equation checked by `verify` holds modulo the small subgroup's order without the prover actually knowing a valid witness for the honest (order-r) statement — the classic invalid-curve/small-subgroup confusion attack against Schnorr/Okamoto-style proofs.

### Impact Explanation
This breaks the binding property the range-proof sigma protocol is supposed to enforce between `hat_C` and `comm` (the polynomial commitment to the secret share chunks). A malicious PVSS dealer could construct a `Transcript<E>` whose `SharingProof.range_proof` passes verification even though the encrypted share chunks are not actually well-formed/in-range, letting a corrupted `range_proof_commitment` and inconsistent shares be accepted into committed DKG transcript state that other validators/consensus rely on for the randomness beacon.

### Likelihood Explanation
Exploitation only requires the ability to submit a `Transcript<E>`/`SharingProof<E>` byte blob that gets deserialized via `bcs`/serde using `ark_de` (i.e., any DKG dealer / any code path accepting serialized PVSS transcripts as "proof input"), plus off-curve-subgroup point construction, which is a standard, well-documented technique for cofactor > 1 curves like BLS12-381 G1.

### Recommendation
Force `Validate::Yes` for all Arkworks curve-point/proof fields deserialized from untrusted bytes, or add an explicit post-deserialization `Valid::check()` / subgroup-membership check on `hat_C` (and other curve points) in `dekart_univariate_v2::Proof::pairing_for_verify` before using them in the sigma-protocol verifier. At minimum, `ark_de` should not unconditionally hardcode `Validate::No`; provide a validating variant and use it for any type where subgroup membership is a soundness precondition, and audit all `#[serde(deserialize_with = "ark_de")]` usages in `crates/aptos-dkg`.

### Proof of Concept
1. Find `x` on the BLS12-381 G1 curve equation `y² = x³ + 4` that is on-curve but not a multiple of the subgroup generator (cofactor-torsion point) — standard invalid-curve point generation.
2. Encode this point in the compressed `G1Affine` format used by `hat_C`.
3. Construct a `Proof<E>`/`SharingProof<E>`/`Transcript<E>` byte blob embedding this `hat_C` plus a `pi_PoK` crafted to satisfy the linear equation modulo the small subgroup order.
4. Deserialize via `bcs::from_bytes::<Transcript<E>>` (routes through `ark_de`, `Validate::No`) — assert it succeeds without error (whereas `CanonicalDeserialize::deserialize_compressed` with default `Validate::Yes` on `hat_C` directly would reject it).
5. Call `Transcript::verify`/`pairing_for_verify` and show `two_term_msm::Homomorphism::verify` returns `Ok(())` despite the invalid-subgroup `hat_C`.

    fn deserialize_with_mode<R: Read>(
        mut reader: R,
        compress: Compress,
        validate: Validate,
    ) -> Result<Self, SerializationError> {
        // Read the discriminant tag
        let tag = u8::deserialize_with_mode(&mut reader, compress, validate)?;

        let item = match tag {
            0 => {
                let c = H::CodomainNormalized::deserialize_with_mode(reader, compress, validate)?;
                FirstProofItem::Commitment(c)
            },
            1 => {
                let f = F::deserialize_with_mode(reader, compress, validate)?;
                FirstProofItem::Challenge(f)
            },
            _ => return Err(SerializationError::InvalidData),
        };

        // Run validity check if requested
        if validate == Validate::Yes {
            item.check()?;
        }

        Ok(item)
    }
