## Finding Confirmed — Missing Length Invariant Enforcement in `merge_msm_inputs_with_scales`

### Title
Malformed `MsmInput` bypassing `new()` validation causes silent scalar truncation in `merge_msm_inputs_with_scales` — ([File: crates/aptos-crypto/src/arkworks/msm.rs])

### Summary
`MsmInput<B, S>` derives `CanonicalDeserialize`/`CanonicalSerialize` directly on its two public fields `bases: Vec<B>` and `scalars: Vec<S>` [1](#0-0) . The derive macro deserializes each `Vec` independently and performs no cross-field length check — that invariant is only enforced in the hand-written `MsmInput::new` constructor [2](#0-1) . Because both fields are `pub` and the derive path exists, any deserialization of raw bytes into an `MsmInput` (or a manual struct literal) can produce `bases.len() != scalars.len()` without ever running `new()`'s check.

### Finding Description
`merge_msm_inputs_with_scales` consumes a slice of `MsmInput`s and, for each one, zips `input.bases().iter()` with `input.scalars().iter()`: [3](#0-2) 

`Iterator::zip` silently stops at the shorter of the two iterators — it never errors. If a malformed `MsmInput` has more `bases` than `scalars` (or vice versa), the extra elements are dropped without any diagnostic, and the aggregation proceeds with a truncated pairing between bases and scalars.

The only validation guarding the function's return value is the trailing `MsmInput::new(bases, scalars)` call at line 93. This check is **vacuous** as a defense against this specific attack: `bases` and `scalars` here come from `agg.into_iter().unzip()`, i.e., they are derived from the same `HashMap<A, A::ScalarField>` and are therefore *always* the same length by construction — regardless of whether any input `MsmInput` was internally malformed. The final `new()` call can never catch a length mismatch introduced by a malformed *input*; it only would catch a bug in the aggregation logic itself, which does not exist here.

Therefore, the described proof-of-concept holds directly from the code: a struct literal `MsmInput { bases: vec![b1, b2], scalars: vec![s1] }` — constructed either directly (bypassing `new`) or via `CanonicalDeserialize::deserialize` from crafted bytes — passed into `merge_msm_inputs_with_scales` will silently drop `b2` from the aggregation instead of returning an error.

### Impact Explanation
Within this file's scope, this is a genuine logic defect: `merge_msm_inputs_with_scales` (and transitively `merge_msm_inputs`, used across `crates/aptos-dkg/src/pcs/shplonked.rs`, `crates/aptos-dkg/src/pvss/chunky/weighted_transcript.rs`, and `crates/aptos-dkg/src/sigma_protocol/traits.rs`) does not defensively validate the internal consistency of each `MsmInput` it merges, relying entirely on callers to have used `MsmInput::new` for every input, which is not enforced by the type system since the derive-based deserialization path exists in parallel and bypasses it.

### Likelihood Explanation
I was not able to confirm, within the scope of this review, a concrete unprivileged entry point where an `MsmInput` value is deserialized directly (via its derived `CanonicalDeserialize` impl) from attacker-controlled transaction/proof/API bytes and then fed straight into `merge_msm_inputs_with_scales` as part of DKG/PCS verification gating an on-chain write. Every call site I was able to inspect for `merge_msm_inputs`/`merge_msm_inputs_with_scales` (`fixed_base_msms.rs`, `weighted_transcript.rs`, `weighted_transcript_v2.rs`, `shplonked.rs`, `sigma_protocol/traits.rs`) appears to construct `MsmInput` values programmatically inside the verification logic rather than deserializing a serialized `MsmInput` wire type directly from untrusted transcript bytes, but I could not fully trace all of these call sites' upstream data provenance before running out of investigation budget.

### Recommendation
- Make `MsmInput`'s fields private and provide a custom `CanonicalDeserialize` implementation (instead of `#[derive(...)]`) that calls `MsmInput::new`/enforces `bases.len() == scalars.len()` at deserialization time, or add a post-deserialization validation hook used at every ingestion boundary.
- Add an explicit length check inside `merge_msm_inputs_with_scales`'s per-input loop (`if input.bases().len() != input.scalars().len() { bail!(...) }`) so the function is safe regardless of how its inputs were constructed, rather than relying on the vacuous final `new()` check.
