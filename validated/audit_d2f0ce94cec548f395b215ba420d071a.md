### Title
Precompile Signature Verification Is Not Bound to a Specific Transaction, Signer, or Recipient — Enabling Frontrunning of "Voucher-like" Signed Messages - (File: precompiles/src/secp256k1.rs, precompiles/src/ed25519.rs, precompiles/src/secp256r1.rs)

### Summary
The `secp256k1`, `ed25519`, and `secp256r1` precompile programs verify a `(pubkey, message, signature)` triple exists somewhere in the *current* transaction's instruction data, but the verification result is not bound in any way to the transaction's fee payer, its other signers, or any specific destination account. Because the raw signed payload is fully visible in the mempool before confirmation, it behaves exactly like the reported "voucher" — anyone who observes it can copy the precompile instruction verbatim into their own transaction and have it verify successfully, redirecting whatever privilege/benefit a downstream program grants on the basis of "this precompile instruction verified" to themselves instead of the intended recipient.

### Finding Description
`agave_precompiles::secp256k1::verify`, `ed25519::verify`, and `secp256r1::verify` each parse offsets out of the precompile instruction's own data and pull the signature/pubkey/message bytes from any instruction in the currently-processing transaction (`instruction_datas`), then cryptographically verify the signature: [1](#0-0) [2](#0-1) [3](#0-2) 

Nothing in this verification routine, nor in the calling path `verify_if_precompile` in `precompiles/src/lib.rs`, ties the successfully-verified signature to:
- the transaction's fee payer or any of its actual signers,
- a specific recipient/beneficiary account that will be credited by a subsequent instruction, or
- the identity of whoever submitted the transaction containing the precompile instruction. [4](#0-3) 

Because `(pubkey, message, signature)` are plain instruction data bytes, once a transaction carrying a precompile instruction is broadcast, this data is visible to the entire network before confirmation. This is structurally identical to the reported voucher issue: the voucher's validity depends only on "was this signed by the expected creator," never on who redeems it or to whom the resulting value is credited. Any program built on top of these precompiles that authorizes an action (mint, transfer, claim) purely because "the ed25519/secp256k1/secp256r1 program verified signer X's signature over message M in this transaction" — without independently re-checking that the transaction's actual signer/fee payer/destination account matches an address embedded in `M` — allows an attacker to extract the signed payload from a pending transaction (or from an intentionally shared "voucher" message+signature) and resubmit it in their own transaction ahead of the intended user, exactly as described in the report for `NFT721`/`NFT1155`/`NFTMarketSimple`.

### Impact Explanation
Programs that rely on the precompile's verification result as authorization are exposed to frontrunning/redirection: an attacker observing a pending transaction (or intercepting an off-chain-distributed signed voucher/message) can win the race to have their own transaction land first, claiming whatever asset, allowlist entry, or authorization the signature was meant to grant, at the expense of the intended recipient (denial of service to the legitimate user, and potential value/asset misdirection to the attacker). This maps to the "theft of funds / privilege escalation" class the report describes for the NFT vouchers, transplanted onto Agave's precompile-based signature-verification primitive that numerous on-chain programs use for the same authorization pattern.

### Likelihood Explanation
High for any unprivileged client: the precompile instruction data (including signature, pubkey, and message) is necessarily public once broadcast to the mempool, requiring no special access, and copying it into a new transaction and racing for inclusion is trivial. The precompile verification functions themselves place no restriction preventing this reuse — the vulnerability is only mitigated if the *consuming program* independently binds the message to the correct signer/recipient, which is not enforced by the platform.

### Recommendation
This is a design property of Agave's precompile programs rather than a bug fixable purely within `precompiles/src/{secp256k1,ed25519,secp256r1}.rs`, since the precompiles cannot know how downstream programs intend to use the verified signature. Nonetheless:
- Document and, where feasible, provide helper utilities/guidance so that programs consuming these precompiles are required to embed the intended fee payer/signer/recipient pubkey inside the signed message (`message_data`) itself, and verify that this embedded pubkey matches an actual signer/account of the enclosing transaction.
- Consider adding an explicit mechanism (e.g., an SVM-level check, as hinted at by `move_precompile_verification_to_svm`) for binding the precompile-verified data to the transaction's signers so that generic voucher-like reuse across transactions is caught earlier rather than left entirely to each consuming program's discipline.

### Proof of Concept
1. A program `P` authorizes `mint_to(destination)` whenever an `ed25519_program` instruction in the same transaction verifies that pubkey `K` (the "voucher issuer") signed a message `M` containing only `(asset_id, amount)` — but does *not* check that `K`'s message also commits to `destination`, and does not require `destination`'s owner to be a signer.
2. The voucher issuer signs `M = (asset_id, amount)` off-chain and gives it to user A, who builds a transaction: `[ed25519_verify(K, M, sig), P.mint_to(A)]` and broadcasts it.
3. Attacker B observes the pending transaction (or is separately given the same voucher), extracts `(K, M, sig)`, and submits their own transaction `[ed25519_verify(K, M, sig), P.mint_to(B)]` with higher priority fee.
4. `agave_precompiles::ed25519::verify` succeeds identically for B's transaction — the verify function only checks that `sig` is a valid signature by `K` over `M` found somewhere in B's own instruction list — per `precompiles/src/ed25519.rs:11-79`. `P.mint_to(B)` executes, and A's subsequent identical transaction now fails (e.g., due to a nonce/one-time-use check inside `P`), reproducing the exact frontrunning scenario described in the external report.

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
