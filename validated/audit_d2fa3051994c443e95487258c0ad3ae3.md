## Finding

### Title
Missing declared-class check in Starknet OS `execute_replace_class` causes state divergence from Blockifier - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The Starknet OS's Cairo implementation of the `replace_class` syscall unconditionally writes the caller-supplied `class_hash` into `contract_state_changes` without verifying that the class is actually declared. The Rust blockifier, which the sequencer uses to execute transactions and build blocks, performs this exact check before mutating state. The two execution engines therefore disagree on the outcome of a `replace_class` syscall with an undeclared class hash, producing a state/root divergence between the block the sequencer commits and the block the Starknet OS (used for proving/re-execution) would derive — directly analogous to the `Cooler.provideNewTermsForRoll` bug where a critical precondition check (verifying the referenced entity's valid/accepted state) was omitted before mutating stored state.

### Finding Description
Any deployed contract can invoke the `replace_class` syscall to change its own class hash. In the blockifier (native Rust execution used by the sequencer to build blocks), this is guarded: [1](#0-0) 

```rust
fn replace_class(...) -> DeprecatedSyscallResult<ReplaceClassResponse> {
    // Ensure the class is declared (by reading it).
    syscall_handler.state.get_compiled_class(request.class_hash)?;
    syscall_handler.state.set_class_hash_at(syscall_handler.storage_address, request.class_hash)?;
    ...
}
```

This is confirmed by tests that expect an "is not declared" error when replacing with an undeclared class hash: [2](#0-1) 

In contrast, the Starknet OS's Cairo implementation of the same syscall — used to re-execute the block and derive the committed state/program hash for proving — has no such check, and this is explicitly flagged as an omission in the code itself: [3](#0-2) 

```
// Replaces the class.
func execute_replace_class{...}(contract_address: felt) {
    ...
    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address, prev_value=cast(state_entry, felt), new_value=cast(new_state_entry, felt),
    );
    ...
    return ();
}
```

Note also there is no gas-cost-only "not enough gas" failure path for the declared-class check — the function always succeeds after the gas check, unconditionally committing the state change. The same missing check exists in the deprecated (Cairo0) syscall path: [4](#0-3) 

### Impact Explanation
A contract that calls `replace_class_syscall` with an undeclared class hash will:
- **In the blockifier (sequencer):** fail the syscall (`UndeclaredClassHash` error). If the contract does not gracefully handle the failed syscall (e.g., via `unwrap_syscall()`), the call/transaction reverts and no class-hash state change is recorded.
- **In the Starknet OS (proving/re-execution):** unconditionally succeed and record the state change, replacing the contract's class hash with an undeclared (arbitrary) value.

This is a concrete case of **honest-node/re-execution divergence**: the state diff, transaction success/revert status, and ultimately the committed state root / block hash computed by the OS during proving would differ from what the sequencer's blockifier committed on-chain. This can lead to proof generation failing against the actual committed block, or — if not caught — to an incorrect committed state root being accepted, undermining the integrity of state commitment. It maps directly to the "wrong committed root or block hash" / "honest-node divergence" impact categories.

### Likelihood Explanation
Reachable by any unprivileged contract deployer/caller: it only requires deploying a contract that calls `replace_class_syscall` with an arbitrary (undeclared) class hash argument, and issuing a single ordinary transaction to invoke it. This requires no special privileges, matching an attacker model of "a single submitted transaction / contract call."

### Recommendation
Add the missing declared-class check to `execute_replace_class` in `syscall_impls.cairo` (and the corresponding Cairo0 path in `deprecated_execute_syscalls.cairo`) before writing `contract_state_changes`, mirroring the blockifier's `get_compiled_class`/`is_declared` check, so that OS re-execution and blockifier execution produce identical results for this syscall on all inputs.

### Proof of Concept
1. Deploy a Cairo1 contract exposing an external function that calls `replace_class_syscall(some_undeclared_class_hash)` and does not panic on failure (e.g., matches on the `Result` and swallows the error, or simply ignores the return value if the API allows it).
2. Submit an ordinary invoke transaction calling that function with a class hash that was never declared.
3. Blockifier execution: `state.get_compiled_class` in `hint_processor.rs:801` (or the equivalent Cairo1 path in `syscall_base.rs`) fails with `UndeclaredClassHash`; contract-visible failure occurs and no class-hash mutation is committed (as demonstrated by `undeclared_class_hash` test in `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29`).
4. Starknet OS re-execution of the same transaction: `execute_replace_class` in `syscall_impls.cairo:881-920` performs no declared-class check and unconditionally updates `contract_state_changes` with the undeclared class hash — producing a different state diff/result than the blockifier for the identical transaction.
