### Title
`generate_index` aborts entire startup index generation on a single storage's scan failure instead of isolating the fault - (File: accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb::generate_index_for_slot` calls `storage.scan_accounts(...).expect("must scan accounts storage")` on each `AccountStorageEntry` while generating the accounts index at startup [1](#0-0) . This is invoked from worker threads spawned inside `generate_index`, each of which iterates over its assigned subset of storages via `storages_orderer.iter()` [2](#0-1) . If a single storage file is broken/corrupted/unreadable and `scan_accounts` returns an `Err`, the `.expect(...)` panics that worker thread. The main thread then observes the panicked `JoinHandle` and unconditionally panics the whole `generate_index` call for **all** slots/storages, not just the offending one:

```rust
for thread_handle in thread_handles {
    let Ok(thread_accum) = thread_handle.join() else {
        exit_logger.store(true, Ordering::Relaxed);
        panic!("index generation failed");
    };
    total_accum.accumulate(thread_accum);
}
``` [3](#0-2) 

This mirrors the bug class in the referenced report: a single broken/malfunctioning unit (there, one MoneyMarketAdapter; here, one account storage/AppendVec) causes an operation that should be independent per-unit (deposit/withdraw across all adapters; index generation across all storages) to fail entirely rather than degrading gracefully or isolating the faulty unit.

### Finding Description
`generate_index` is the startup routine that rebuilds the in-memory/disk `AccountsIndex` by scanning every `AccountStorageEntry` (append vec) found in `self.storage.all_storages()` [4](#0-3) . Work is fanned out across `num_cpus::get()` worker threads pulling storages from a shared concurrent consumer (`storages_orderer.iter()`), where each thread processes many storages in a loop by calling `self.generate_index_for_slot(...)` per storage [5](#0-4) .

Inside `generate_index_for_slot`, the storage's account data is scanned with:
```rust
let num_obsolete_accounts_skipped = storage
    .scan_accounts(reader, |offset, account| { ... })
    .expect("must scan accounts storage");
``` [1](#0-0) 

`scan_accounts` on the underlying `AccountsFile`/`AppendVec` can return an `Err` (e.g., `AccountsFileError`) for a storage file that is truncated, corrupted, or otherwise unreadable — a plausible "broken adapter" analog for a single storage among possibly tens of thousands loaded at startup. Because this path uses `.expect(...)` rather than propagating the error, any such failure panics the *worker thread*, not just aborting processing of that one storage.

The panic then propagates up through `thread::scope` to the join loop in `generate_index`:
```rust
for thread_handle in thread_handles {
    let Ok(thread_accum) = thread_handle.join() else {
        exit_logger.store(true, Ordering::Relaxed);
        panic!("index generation failed");
    };
    total_accum.accumulate(thread_accum);
}
``` [3](#0-2) 

Since each worker thread is processing a large, effectively random subset of *all* storages (via `AccountStoragesOrderer::with_random_order(&storages).into_concurrent_consumer()` [6](#0-5) ), one corrupted storage anywhere in the whole set is enough to panic the entire `generate_index` call — aborting index generation for every other (healthy) storage's work that hasn't been joined yet, and ultimately failing validator startup/snapshot-load entirely, rather than isolating the fault to the single bad storage (e.g., by skipping/quarantining it and continuing with the rest, or returning a structured error the caller can act on).

The `verify` pass later in the same function has an identical pattern (`scan_accounts_without_data(...).expect("must scan accounts storage")` inside a `par_iter().for_each`) [7](#0-6) , and other call sites of `scan_accounts`/`scan_accounts_without_data` in `accounts_db.rs` follow the same `.expect("must scan accounts storage")` convention (e.g. `scan_account_storage` [8](#0-7) ), so this is a systemic pattern rather than an isolated line.

### Impact Explanation
This is a startup-time/rebuild-path node panic caused by a single corrupted or unreadable append-vec/storage file among potentially many thousands, matching "node panic" and "disproportionate ... cost" categories called out in the validate rules — one broken input unit takes down index generation for all other healthy storages, rather than the fault being scoped to the single bad slot's data. In practice this could prevent a validator from completing startup/snapshot load entirely due to one damaged storage file (e.g., from a prior unclean shutdown, disk corruption, or partial write), when the rest of the account state is intact and could otherwise be indexed successfully.

### Likelihood Explanation
Likelihood depends on the probability of encountering a single corrupted/unreadable storage file among the (potentially very large) set of account storages loaded at startup — this can occur from disk corruption, unclean shutdown leaving a partially-written append vec, or filesystem issues, none of which require an on-chain adversary. Given that `generate_index` processes essentially every storage across the whole node's history in one atomic all-or-nothing call, the "blast radius" of any single bad storage is the entire startup, which is a meaningfully higher-likelihood, higher-impact scenario than an isolated single-slot failure would be.

### Recommendation
Rather than using `.expect("must scan accounts storage")` inside `generate_index_for_slot` and the `generate_index` `verify` pass, propagate scan errors per-storage (e.g., return a `Result` from `generate_index_for_slot`, or catch/log-and-skip a storage whose scan fails), and have the main aggregation loop in `generate_index` collect/report which specific slot(s)/storage id(s) failed instead of unconditionally panicking the whole call via `panic!("index generation failed")`. This would let index generation continue for all healthy storages and only fail (or explicitly quarantine) the specific broken one, analogous to the report's recommendation of wrapping each adapter call so that a single broken adapter does not block operations on the others.

### Proof of Concept
Conceptual reproduction (cannot be executed in this environment):
1. Start a validator/ledger-tool flow that calls `AccountsDb::generate_index` at startup with a set of on-disk account storages.
2. Corrupt or truncate one storage file's append-vec on disk (e.g., truncate mid-account so `scan_accounts` hits a malformed/short read and returns `Err`).
3. Run `generate_index`; the worker thread processing that storage panics at:
   `storage.scan_accounts(reader, |offset, account| {...}).expect("must scan accounts storage")` [1](#0-0) 
4. Observe that the panic propagates and the join loop in `generate_index` panics with `"index generation failed"` [3](#0-2) , aborting the whole index-generation call even though the vast majority of storages were healthy and scannable.
