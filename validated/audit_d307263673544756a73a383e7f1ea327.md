### Title
Unbounded per-address delegation list with O(n) linear search/removal in `DelegatedResourceAccountIndexCapsule` - (File: chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java)

### Summary
The legacy resource-delegation bookkeeping (`FreezeBalanceContract` / `UnfreezeBalanceContract` path, active when `supportAllowDelegateOptimization()` is disabled) maintains, per account, an unbounded `toAccounts`/`fromAccounts` list of delegatee/delegator addresses inside `DelegatedResourceAccountIndexCapsule`. Every freeze-with-delegation appends a new address to the list (bounded only by `contains()` de-dup), and every unfreeze performs a full linear scan/removal (`List.contains()` + `List.remove(ByteString)`) over that same list. This mirrors exactly the `PermissionsLib.revokeAuthorization` bug class: an attacker-controlled array that grows without bound and is later linearly searched/mutated.

### Finding Description
`DelegatedResourceAccountIndexCapsule` stores address lists with no size cap: [1](#0-0) 

`FreezeBalanceActuator.delegateResource` appends a new receiver/owner address to these lists via `contains()` + `addToAccount`/`addFromAccount` whenever a not-yet-seen counterparty is delegated to, with no bound on how many distinct counterparties can be added: [2](#0-1) 

On the unfreeze path, `UnfreezeBalanceActuator.execute` performs an `ArrayList` copy plus `contains`/`remove(ByteString)` linear scans over the same list to strip the counterparty out: [3](#0-2) 

This is functionally identical to `PermissionsLib.revokeAuthorization`'s bug class: an array that can grow to unbounded size through repeated authorized calls (`authorize`/`delegateResource`), later requiring an O(n) scan (`revokeAuthorization`/`unfreeze`) with no supporting index/mapping to avoid it.

### Impact Explanation
An attacker who controls (or repeatedly creates) many distinct receiver accounts can call `FreezeBalanceContract` with `receiver_address` set to a new, never-before-used address each time, each transaction appending one entry to `toAccountsList`/`fromAccountsList`. Because the minimum amount per freeze is only 1 TRX (`frozenBalance must be greater than or equal to 1 TRX`), the cost to grow this list to tens of thousands of entries is proportional only to the number of freeze transactions (bounded by bandwidth/energy cost of a transaction), not to a fixed value; over time the list for a given account can become very large. When that account later unfreezes any entry, `UnfreezeBalanceActuator` must copy and linearly scan the full (potentially huge) list inside a single block-execution transaction, increasing CPU work and block processing time for that transaction, i.e. a resource-exhaustion/DoS vector on block execution reachable from ordinary, unprivileged broadcast transactions (`FreezeBalanceContract`/`UnfreezeBalanceContract`).

### Likelihood Explanation
Likelihood is limited by two factors visible in the code: (1) this path is only active while `supportAllowDelegateOptimization()` is false — i.e. on chains/forks that have not yet enabled the "new" delegated-resource index (which replaces the list-based index with per-pair keys, see `delegatedResourceAccountIndexStore.delegate`/`convert`), and (2) `FreezeBalanceContract` itself becomes fully disabled once `supportUnfreezeDelay()` (freeze v2) is active, per the explicit check `"freeze v2 is open, old freeze is closed"`: [4](#0-3) 
So on mainnet/current forks where these flags are already turned on, the vulnerable list-growth path is not reachable. On any chain/testnet/fork state where these forward-compatibility flags are still off (or during historical replay of blocks before those forks activated), the path is fully reachable by any account via ordinary transactions, at TRX cost proportional to entries added.

### Recommendation
- Cap the number of distinct delegatees/delegators tracked per account in `DelegatedResourceAccountIndexCapsule` (similar to `UNFREEZE_MAX_TIMES` used for `UnfreezeBalanceV2`), or
- Always route delegation bookkeeping through the already-existing per-pair keyed index (`DelegatedResourceAccountIndexStore.delegate/unDelegate` with `FROM_PREFIX`/`TO_PREFIX`, or the V2 variant) instead of the flat `toAccountsList`/`fromAccountsList`, eliminating the need for `contains()`/`remove()` linear scans entirely (this is effectively what `supportAllowDelegateOptimization()` already does — consider making it mandatory/always-on rather than conditional).
- If backward compatibility requires keeping the list-based path, bound list growth explicitly in `FreezeBalanceActuator.delegateResource` validate/execute logic.

### Proof of Concept
Not exploitable against current mainnet configuration where `supportAllowDelegateOptimization()` and `supportUnfreezeDelay()` are enabled, since `FreezeBalanceActuator.validate()` rejects the contract outright once freeze v2 is active. On a chain/fork state where these flags are unset:
1. Attacker account `A` repeatedly broadcasts `FreezeBalanceContract` transactions with `frozen_balance = 1 TRX`, `resource = BANDWIDTH`, and a freshly generated `receiver_address` each time.
2. Each transaction appends one entry to `A`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` (per `FreezeBalanceActuator.delegateResource`, lines 328-332 above).
3. After accumulating N (e.g., tens of thousands) entries, `A` calls `UnfreezeBalanceContract` for any one delegation; `UnfreezeBalanceActuator.execute` copies the full list and performs `contains`/`remove` (O(N)) during block execution, as shown at lines 167-170 above.
This is a static code-path analysis based on the referenced files; a live gas/CPU-cost benchmark to confirm concrete DoS thresholds was not performed and is left for further investigation.
