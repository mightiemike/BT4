This confirms the analog: the legacy `DelegatedResourceAccountIndexStore` index (used pre-Freeze-V2/pre-optimization) has an unbounded array keyed by a victim address that any freezer can append to, with no dedup across distinct senders and no minimum-amount floor, mirroring the vesting bug class (attacker-controlled unbounded array tied to a victim, exposed through an unauthenticated read path).

### Title
Unbounded growth of `DelegatedResourceAccountIndex.fromAccounts`/`toAccounts` lists allows any account to bloat a victim's resource-delegation index, causing storage/RPC DoS - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` lets any account delegate a minimal frozen balance (as little as 1 TRX, the enforced minimum) to an arbitrary receiver address, and — when `DynamicPropertiesStore.supportAllowDelegateOptimization()` is false — appends the receiver's address/owner's address into a `DelegatedResourceAccountIndexCapsule` list stored under a single DB key per account, with no bound on list size. [1](#0-0)  Because the dedup check (`if (!fromAccountsList.contains(...))`) only prevents duplicate entries from the *same* sender address, an attacker can use many distinct freezer accounts to keep appending new entries into a single victim's `fromAccountsList`/`toAccountsList` indefinitely. [2](#0-1) 

### Finding Description
This closely parallels the reported Vesting.sol bug class: an unauthenticated/unprivileged actor can push entries into an array associated with a victim account without the victim's consent, and there is no minimum-amount floor or cap on entries to make the attack infeasible.

In `FreezeBalanceActuator.delegateResource()`, the owner (attacker) and receiver (victim) do not need any relationship — the receiver is not required to be `msg.sender`, and any account can be named as receiver as long as it is not a contract account with `AllowTvmConstantinople` enabled. [3](#0-2)  Each successful delegation (legacy/non-optimized branch) loads the receiver's full `DelegatedResourceAccountIndexCapsule`, appends a new `ByteString` to `fromAccounts`, and writes the whole capsule back. [4](#0-3)  The `DelegatedResourceAccountIndexCapsule` itself provides no size limit on `addFromAccount`/`addToAccount`. [5](#0-4) 

This index is served through unauthenticated RPC/HTTP/gRPC endpoints without pagination — `Wallet.getDelegatedResourceAccountIndex()` reads and returns the entire capsule for a queried address, wired up in `RpcApiService.getDelegatedResourceAccountIndex` and `GetDelegatedResourceAccountIndexServlet`. [6](#0-5) [7](#0-6) [8](#0-7)  As the list grows unbounded, each subsequent legacy delegate/undelegate touching that account, and every read of this account via the above APIs, requires deserializing/serializing an ever-larger protobuf list — the O(n) read-modify-write pattern combined with unauthenticated growth is the direct analog of the vesting `timelocks[]` unbounded-array bug.

### Impact Explanation
An attacker can grow a targeted victim account's `DelegatedResourceAccountIndex` list without bound, at the low cost of many minimal (1 TRX) freeze-and-delegate operations from disposable accounts. This causes:
- Growing on-disk/state storage tied to the victim account that is never pruned by the victim (removal only occurs when the *specific delegator* who created an entry fully unfreezes, per `UnfreezeBalanceActuator`'s index cleanup, which the attacker fully controls and need never trigger).
- Increasing cost (and eventual practical unavailability due to size/gas or serialization limits) of legacy freeze/delegate/undelegate operations that must load and rewrite the affected account's full index capsule.
- Unauthenticated `GetDelegatedResourceAccountIndex` RPC/HTTP/gRPC calls against the victim address returning increasingly large, unpaginated responses, degrading node resources for any caller and enabling a resource-exhaustion vector.

### Likelihood Explanation
The affected legacy delegation path (`FreezeBalanceActuator`, `ContractType.FreezeBalanceContract`) is validated with `if (dynamicStore.supportUnfreezeDelay()) { throw ... "freeze v2 is open, old freeze is closed"; }`, meaning this specific write path is disabled once a chain has activated Freeze V2 (`supportUnfreezeDelay`). [9](#0-8)  Thus the concrete exploitability of the *write* path depends on chain configuration: it is fully reachable on any java-tron network (private chain, testnet, or a mainnet snapshot) that has not activated `ALLOW_UNFREEZE_DELAY`/Freeze V2, or on any node still serving pre-migration state. Since the code, storage format, and unauthenticated read RPC remain present and un-capped regardless of configuration, this is a real design flaw rather than a purely theoretical one, but likelihood on a fully-upgraded mainnet is lower than on the original report (which had no such gating).

### Recommendation
- Enforce a hard cap on the number of entries in `DelegatedResourceAccountIndexCapsule.fromAccounts`/`toAccounts` (as the V2 optimized per-pair-key storage already implicitly avoids by not aggregating into one growing list).
- Add pagination to `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` similar to `GetPaginatedNowWitnessList`/`GetPaginatedProposalList`, rather than returning the full unbounded list in one unauthenticated response. [10](#0-9) 
- Since the legacy path is already deprecated behind `supportUnfreezeDelay()`, consider fully retiring/removing the unbounded-index code paths in `FreezeBalanceActuator`/`UnfreezeBalanceActuator`/`DelegatedResourceAccountIndexStore` for networks where Freeze V2 is permanently active, to eliminate residual risk on non-upgraded deployments.

### Proof of Concept
1. On a java-tron network where `supportUnfreezeDelay()` (Freeze V2) is not yet enabled, generate N disposable accounts, fund each with the minimum required (≥1 TRX, `TRX_PRECISION`). [11](#0-10) 
2. From each disposable account, broadcast a `FreezeBalanceContract` with `receiverAddress` set to the fixed victim address, and `frozenBalance` at the minimum 1 TRX, repeated for arbitrarily large N. [12](#0-11) 
3. Each transaction appends a new entry to the victim's `fromAccounts` list in `DelegatedResourceAccountIndexStore`, since each sender address is distinct and thus not filtered by the `contains()` dedup check. [4](#0-3) 
4. Query `GetDelegatedResourceAccountIndex` (gRPC/HTTP) for the victim's address, observing an unbounded, unpaginated response size growing linearly with N, and observe growing latency/cost for the victim's own subsequent legacy freeze/unfreeze operations that must rewrite the full capsule. [13](#0-12)
