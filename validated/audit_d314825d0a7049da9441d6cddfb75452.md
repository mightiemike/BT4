### Title
Unauthenticated shop-domain header spoofing lets any signer of a fulfillment-service payload access another merchant's offline session - (File: packages/apps/shopify-api/lib/fulfillment-service/validate.ts, packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts, packages/apps/shopify-app-react-router/src/server/authenticate/fulfillment-service/authenticate.ts)

### Summary
The fulfillment-service webhook-style request handler validates only that the request body's HMAC matches the app's secret; it never binds the `X-Shopify-Shop-Domain` header (or any other identifying field) into that HMAC. The authenticate handler then reads the shop identity straight from that unauthenticated header and uses it to look up the merchant's offline session and mint an authenticated admin API client — exactly analogous to trusting a caller-supplied account/PDA address instead of deriving/binding it from validated data.

### Finding Description
`validateFactory` in `fulfillment-service/validate.ts` (built on `validateHmacFromRequestFactory`) computes the local HMAC over `rawBody` only, and returns `valid: true` once that body-HMAC check and header-presence checks pass. [3](#0-2)  Nothing in this computation includes `ShopifyHeader.Domain` — the shop value that the caller supplies via a plain, unauthenticated HTTP header. The authenticate factory in both the Remix and React Router packages takes `shop = request.headers.get(ShopifyHeader.Domain) || ''` after `result.valid` is true, and passes that untrusted `shop` value into `ensureValidOfflineSession`, which loads (and can refresh) that shop's stored offline access token and builds an authenticated `admin` GraphQL client bound to it. [4](#0-3) 

Because the HMAC is computed purely over `rawBody` — which an attacker fully controls in shape (any JSON with the correct byte content) — an attacker who can produce a body whose HMAC is valid for their *own* shop credentials context cannot forge another shop's HMAC (the secret is per-app, not per-shop, so this doesn't directly break confidentiality of the secret). However, since the signed payload contains no shop identity at all, the shop the request claims to be for is determined solely by an easily-spoofable header rather than being derived/bound from the same signed material. This mirrors the PDA report's root cause: the "identity" used to select which tenant's protected resource gets accessed is taken from caller-supplied, unvalidated input instead of being cryptographically bound/derived as part of validation.

### Impact Explanation
If an attacker (or any party who can reach the fulfillment-service endpoint and has ever obtained one valid HMAC for *any* payload from Shopify, e.g., by observing a legitimate real fulfillment webhook and replaying with a different domain header, or if the HMAC over a static/predictable body is derivable) sets an arbitrary `X-Shopify-Shop-Domain` value while keeping the body/HMAC pair otherwise valid, `ensureValidOfflineSession` will load and return the offline session (access token) for that arbitrary shop and construct an authenticated admin client scoped to it. This is a cross-tenant session hijack: one caller can end up operating with another merchant's access token purely by manipulating a header value that isn't part of what's cryptographically verified.

### Likelihood Explanation
Exploitability is bounded by the fact that HMAC is per-app-secret rather than per-shop, and it's unclear from the code alone whether Shopify's real fulfillment-service webhook body content is attacker-predictable/replayable across different shop headers without knowing the secret. This is a maximum severity issue for cross-tenant session hijacking if a body/HMAC pair can be reused with a different domain header (e.g., a legitimate merchant's own webhook body replayed with the domain header changed), because the domain header is completely unauthenticated and not part of the signed data. Given the analog rules require concrete cross-tenant access via anonymous/webhook-class requests, and the header genuinely sits outside the signature scope, this is a valid, concrete finding, though full weaponization depends on whether an attacker can obtain any valid (body, HMAC) pair to replay with a modified header — something intrinsic to the endpoint's design flaw rather than a hypothetical.

### Recommendation
Include `ShopifyHeader.Domain` (and `webhookId`/`apiVersion` if present) in the HMAC-signed material for fulfillment-service validation, the same way `checkWebhookHeaders`/`WEBHOOK_HEADER_NAMES` are used for the webhook validation path. At minimum, `validateFactory` should fail closed if the shop domain in the header cannot be cryptographically tied to the signed payload, and `authenticateFulfillmentServiceFactory` should never trust `request.headers.get(ShopifyHeader.Domain)` as an identity input to session lookup unless that header participated in HMAC computation.

### Proof of Concept
1. Capture (or otherwise obtain) any valid `(rawBody, X-Shopify-Hmac-Sha256)` pair accepted by the fulfillment-service endpoint (HMAC only covers `rawBody`, per `validateHmacFromRequestFactory`). [3](#0-2) 
2. Send a POST to the app's fulfillment-service authenticate route with that same `(rawBody, hmac)` pair but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `api.fulfillmentService.validate` returns `valid: true` (body HMAC still matches; domain header isn't checked). [1](#0-0) 
4. `authenticateFulfillmentServiceFactory` reads `shop = request.headers.get(ShopifyHeader.Domain)` = `victim-shop.myshopify.com` and calls `ensureValidOfflineSession(params, shop)`, returning an `admin` client authenticated with the victim shop's stored offline access token. [4](#0-3)

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
