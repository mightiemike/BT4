### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists via repeated `FreezeBalanceContract` delegation causes read/write amplification DoS - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java, chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
The Llama finding shows a DoS class where an unprivileged actor can repeatedly trigger creation of unbounded per-account state that a system-critical, privileged operation must later fully load/iterate, without any cap on the number of created entries. Java-tron has an analogous unbounded-list pattern in the legacy (`!supportAllowDelegateOptimization`) resource-delegation index path: any account can call `FreezeBalanceContract` with a `receiver_address` to a large number of distinct addresses, and each call appends an entry to a single protobuf-encoded `DelegatedResourceAccountIndexCapsule` stored under the owner's key, with no maximum size check.

### Finding Description
`FreezeBalanceActuator.delegateResource()` handles the legacy (pre-"delegate optimization") code path: [1](#0-0) 

When `dynamicPropertiesStore.supportAllowDelegateOptimization()` is false, every `FreezeBalanceContract` call with a new `receiverAddress` reads the entire `DelegatedResourceAccountIndexCapsule` for the owner, appends the new receiver to `toAccountsList` (after an O(n) `contains` scan), and rewrites the whole capsule back to the store: [2](#0-1) 

There is no limit anywhere in `FreezeBalanceActuator.validate()`/`execute()` on how many distinct receiver addresses an owner (or how many owners a receiver) may accumulate in this list. Because the whole list is a single protobuf message value under one DB key, every subsequent freeze-and-delegate operation must deserialize and re-serialize an ever-growing byte array, and `Wallet`/API calls that expose this index (`getIndex`) also fully load it: [3](#0-2) [4](#0-3) 

A test in the codebase already demonstrates the pattern by adding 100 receivers to a single owner's index list: [5](#0-4) 

Note that java-tron already introduced a mitigation for this exact bug class — the "delegate optimization" (V2) storage layout stores each delegation as a separate key (`V2_FROM_PREFIX`/`V2_TO_PREFIX` + address pair) instead of a single growing list, exactly analogous to how the Llama team fixed their issue by adding a new checkpoint mechanism instead of an unbounded single-timestamp check: [6](#0-5) [7](#0-6) 

However, the legacy unbounded-list code path in `FreezeBalanceActuator` remains present and reachable whenever `supportAllowDelegateOptimization()` is not yet enabled (e.g., on chains/forks that have not activated this committee-governed parameter, or during any window before activation on a live network). On such deployments, this is a pure unprivileged, broadcast-transaction-reachable DoS vector: an attacker with a normal account and minimal TRX freeze amounts can grow this list indefinitely by freezing tiny amounts (`1_000_000` SUN minimum) with `delegate=true` to a large number of distinct receiver addresses (self-controlled or arbitrary valid addresses), causing the per-account index entries to grow unboundedly and each subsequent freeze/unfreeze/query operation on that account to become progressively slower (O(n) list scan + full re-serialization), analogous to the Llama report's O(n) unbounded action list degrading a critical operation.

### Impact Explanation
This is a state/DoS growth vector, not fund loss: it degrades performance of `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, and any RPC/API call reading `getDelegatedResourceAccountIndex` for the affected account, potentially causing large transaction-processing latency or storage bloat for that account/node — consistent with the "DoS via protocol implementation" acceptance criterion. It does not directly cause consensus divergence or key/asset compromise, keeping it at moderate severity, contingent on `supportAllowDelegateOptimization` not being active.

### Likelihood Explanation
Reachability requires only a normal broadcast `FreezeBalanceContract` transaction (any account, no special role) — fully unprivileged. However, exploitability is conditioned on the network not having activated `AllowDelegateOptimization`; since the newer V2 delegation path already fixes this in the current mainnet configuration, likelihood on already-activated networks is low, but the vulnerable code path remains live in the codebase for any chain/testnet/private deployment or activation-window scenario, and is not gated by any additional list-size check even when the optimization flag is off.

### Recommendation
- Cap the maximum number of entries allowed in `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` in the legacy path (mirroring `UNFREEZE_MAX_TIMES` style limits already used elsewhere, e.g. `UnfreezeBalanceV2Actuator`).
- Consider removing/deprecating the legacy unbounded-list code path entirely once `AllowDelegateOptimization` is universally active, or enforce the V2 storage scheme unconditionally for new delegations.
- Add validation in `FreezeBalanceActuator.validate()` to reject delegation to a new receiver once the owner's index list exceeds a safe threshold.

### Proof of Concept
Not independently executed; based on static analysis of `FreezeBalanceActuator.delegateResource()` and `DelegatedResourceAccountIndexCapsule`/`DelegatedResourceAccountIndexStore`. The existing unit test `testMultiFreezeDelegatedBalanceForBandwidth` in `FreezeBalanceActuatorTest.java` (adding 100 receivers to one owner index) demonstrates the unbounded-append mechanism; extending the receiver count in that test to a very large number (e.g. tens of thousands) with `supportAllowDelegateOptimization` disabled would reproduce escalating capsule size and processing cost per subsequent freeze call, mirroring the Llama report's action-creation DoS PoC pattern.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  public void delegateV2(byte[] from, byte[] to, long time) {

    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(V2_TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }
