### Title
Panic via unvalidated bytecode segment lengths in compiled class hash computation - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The `bytecode_hash`/`bytecode_hash_node` functions that compute a Cairo1 compiled class's hash use `assert_eq!` to check that the segment-length structure (`bytecode_segment_lengths`, a `NestedIntList`) is consistent with the actual bytecode length, instead of returning a `Result`. If a class's declared/compiled segment structure and its bytecode length diverge, this triggers a Rust panic rather than a graceful error, mirroring the TensorFlow advisory's root cause: a precondition between independently-supplied structural fields (there: indices/values/dense_shape of a sparse tensor; here: nested segment-length tree vs. bytecode length) is assumed but never validated before being consumed, leading to undefined-behavior-class failure (there a null dereference; here a Rust panic/abort).

### Finding Description
`bytecode_hash` calls `bytecode_hash_node` and then asserts that the total length consumed equals `bytecode.len()`: [1](#0-0) 

`bytecode_hash_node` itself, for leaf nodes, asserts that the number of felts actually pulled from the iterator equals the segment's declared length: [2](#0-1) 

Both of these are `assert_eq!` calls — a Rust panic, not a recoverable `Result::Err` — that fire whenever the `bytecode_segment_lengths` tree and the actual bytecode array are inconsistent (e.g., a leaf claims more felts than remain, or a node's children lengths do not sum to what the bytecode contains). Additionally, `HashableNestedIntList::get_segment_length` / `iter_children` also `panic!` if called on a mismatched node type: [3](#0-2) 

This hashing routine is invoked from `HashableCompiledClass::hash`, which is the code path used to (re)compute a compiled class hash for `CompiledClassV1`/CASM classes — precisely the check performed when a Declare transaction's provided `compiled_class_hash` is validated against the actual compiled artifact, and again whenever the Starknet OS / blockifier re-derives class hashes from a `CasmContractClass` for state commitment purposes.

### Impact Explanation
Unlike numeric-field validation on transaction size/version (which the gateway does perform, e.g. calldata/signature length checks in `stateless_transaction_validator.rs`), there is no check anywhere in this hashing path that `bytecode_segment_lengths` is structurally consistent with `bytecode` before invoking `hash()`. If any code path constructs or accepts a `CasmContractClass`/`CompiledClassV1` where the segment-length metadata does not exactly partition the bytecode (e.g., a corrupted/malformed class reaching hash computation, or a compiler/never-covered edge case producing a segment tree whose leaf lengths don't sum to the bytecode length), computing the hash panics. Because this hashing routine sits on the Declare validation / compiled-class-hash matching path and the OS re-execution/class-hash re-derivation path, a panic here is a process-level crash rather than a contained validation error — an availability impact (node crash / DoS, "network unable to confirm new transactions" if triggered widely) rather than silent corruption. This corresponds to CWE-476/assertion-failure class issues: an unvalidated structural precondition between two related fields is consumed without a bounds/consistency check, exactly as in the TensorFlow `SparseTensorSliceDataset` advisory (precondition between `indices`, `values`, `dense_shape` not validated before dereferencing).

### Likelihood Explanation
Likelihood is constrained by the fact that in the primary, well-tested flow, `bytecode_segment_lengths` is produced deterministically by the trusted Sierra→CASM compiler from a syntactically valid Sierra program, so a legitimate declare transaction should never produce mismatched data. However, the vulnerability class documented here is that this invariant is enforced only by convention/compiler correctness and not defensively checked at the point of use — the hashing code itself has no fallback and will always panic (rather than return an error) the moment any upstream invariant is violated, whether due to a compiler edge case, a future refactor, or an alternate code path that constructs a `CasmContractClass` from data that hasn't gone through the exact compiler validation gate. Given the strict rule set requiring reachability from a single transaction/declared class with concrete impact, I could not fully confirm within the available tool budget that an attacker-controlled Sierra program can *directly* produce a mismatched `bytecode_segment_lengths`/`bytecode` pair through the standard compilation pipeline (this would require deeper analysis of the `cairo-lang-starknet-classes` / `SierraToCasmCompiler` internals, which are external dependencies not fully indexed here).

### Recommendation
Replace the `assert_eq!`/`panic!` calls in `bytecode_hash`, `bytecode_hash_node`, and `HashableNestedIntList::get_segment_length`/`iter_children` with a `Result`-returning validation that checks the segment-length tree fully and exactly partitions the bytecode before hashing, returning a descriptive error (e.g., `InvalidBytecodeSegmentStructure`) on mismatch instead of panicking. This should be validated once, up front, whenever a `CasmContractClass`/`CompiledClassV1` is constructed from external or compiled input (declare transaction compilation output, deserialized storage/OS input), so that any inconsistency is converted into a rejected declare transaction rather than a process panic.

### Proof of Concept
Conceptually (cannot be run without full compiler context): construct a `CompiledClassV1`/`CasmContractClass` whose `bytecode` has `N` felts, but whose `bytecode_segment_lengths` is a `NestedIntList::Leaf(N+1)` (or a `Node` whose children's leaf lengths sum to more than `N`). Calling `.hash(&HashVersion::V1)` (or `V2`) on this class invokes `bytecode_hash` → `bytecode_hash_node`, which will execute `iter.take(len).collect_vec()` followed by `assert_eq!(data.len(), len)` at [4](#0-3)  and panic instead of returning an error, crashing the calling process.

pub trait HashableNestedIntList: Clone {
    /// Returns true if this is a leaf node, false if it's a node with children.
    fn is_leaf(&self) -> bool;

    /// Returns the segment length stored in a leaf node. Panics if called on a non-leaf.
    fn get_segment_length(&self) -> usize;

    /// Returns an iterator over child nodes if this is a node, panics if called on a leaf.
    fn iter_children(&self) -> impl Iterator<Item = &Self>;
}

impl HashableNestedIntList for NestedIntList {
    fn is_leaf(&self) -> bool {
        matches!(self, NestedIntList::Leaf(_))
    }

    fn get_segment_length(&self) -> usize {
        match self {
            NestedIntList::Leaf(segment_len) => *segment_len,
            NestedIntList::Node(_) => panic!("Called get_segment_length on a Node"),
        }
    }

    fn iter_children(&self) -> impl Iterator<Item = &Self> {
        match self {
            NestedIntList::Leaf(_) => panic!("Called iter_children on a Leaf"),
            NestedIntList::Node(children) => children.iter(),
        }
    }
}

fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
