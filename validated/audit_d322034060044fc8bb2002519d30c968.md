### Title
Unbounded recursion over attacker-influenced `NestedIntList` bytecode-segment structures causes uncatchable stack-overflow crash - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs], [File: crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs])

### Summary
Both compiled-class-hash computation and Starknet-OS bytecode-segment reconstruction recurse over a `NestedIntList` tree (`Leaf`/`Node`) with no maximum-depth check. This tree is derived from a `CasmContractClass`'s `bytecode_segment_lengths` field, which is produced by compiling a **user-submitted Sierra program** (a Cairo1 `DECLARE` transaction). Because the segmentation the Cairo compiler emits mirrors the nested function/branch structure of the submitted program, an attacker can craft a Sierra program whose compiled bytecode segmentation is deeply, single-child nested (`Node([Node([Node([...Leaf(1)...])])])`), driving these recursive Rust functions to nesting depths bounded only by the submitted code, not by any sequencer-enforced limit — the same bug class as CVE-2026-54888 in `mdex`.

### Finding Description
`NestedIntList` is a recursive enum (`Leaf(len)` / `Node(Vec<NestedIntList>)`) that describes how a contract's CASM bytecode is split into hashable/loadable segments. Two independent recursive functions walk it with no depth bound:

1. `bytecode_hash_node` in [1](#0-0)  recurses once per `Node` level via `node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child))`, with no depth guard. This is invoked from `bytecode_hash` ( [2](#0-1) ), which computes the `CompiledClassHash` for a freshly compiled class — i.e. it runs on the Sierra-to-CASM compiler's own output for a *declared* class.

2. `create_bytecode_segment_structure_inner` in [3](#0-2)  recurses identically, once per `NestedIntList::Node`, again with no depth guard. It is invoked from the Starknet OS hint `load_classes_and_create_bytecode_segment_structures` ( [4](#0-3) ), which runs during OS execution/re-execution of every block that contains the declared class — a step every sequencer, prover, and full node performs.

By contrast, a very similar structure `NestedFeltCounts` explicitly limits recursion (`assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.")` in [5](#0-4) ), showing the project is aware such structures can be deeply nested and normally bounds them — but this bound was not applied to `bytecode_hash_node` or `create_bytecode_segment_structure_inner`.

The `SierraCompilationConfig` only bounds total output size (`max_bytecode_size`, `max_memory_usage`, `max_cpu_time` — see [6](#0-5) ); none of these bound the *nesting depth* of `bytecode_segment_lengths`. Since a compiler-generated segment structure with a single leaf can still have arbitrarily many wrapping `Node` levels (each contributing negligible size) while the total bytecode size stays within `DEFAULT_MAX_BYTECODE_SIZE`, an attacker fully controls the recursion depth by crafting a program whose control-flow/function nesting is very deep (e.g. thousands of nested branches/functions), which the Cairo compiler will segment following that nesting.

### Impact Explanation
A stack overflow triggered inside these Rust recursive functions is a native SIGSEGV, not a catchable Rust panic; it will crash the entire OS process — the sequencer node process (during declare-transaction hash computation at gateway/mempool ingestion, per [7](#0-6) ) or the Starknet OS/prover re-execution process (during block validation, per [4](#0-3) ). This is a denial-of-service that can halt block production/validation network-wide once the malicious class is declared and needs to be (re-)compiled or (re-)executed by every node — satisfying "network unable to confirm new transactions."

### Likelihood Explanation
Reachable from a single, unprivileged `DECLARE` (Cairo1) transaction: the attacker submits a Sierra program engineered to compile into a deeply, linearly-nested `bytecode_segment_lengths` tree. The compiler binary itself (`cairo-lang`, external to this repo) determines the exact mapping from source structure to segment nesting, so I cannot fully verify from this repo alone how deep a nesting the compiler will actually emit for a given program size, or whether the compiler has its own internal recursion-depth safeguards (this part is external and not indexed here). This uncertainty should be resolved by a background agent that can build and run the actual `cairo-lang` compiler on a crafted program to confirm real nesting depth achievable within `DEFAULT_MAX_BYTECODE_SIZE`.

### Recommendation
Add explicit maximum-depth checks (mirroring the existing `segmentation_depth <= 1` assertion in `NestedFeltCounts::new_inner`) to both `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs`) and `create_bytecode_segment_structure_inner` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`), rejecting/erroring out on `NestedIntList` trees deeper than a small sequencer-enforced bound, and converting both functions to iterative (explicit stack/queue-based) traversal to remove reliance on native call-stack depth entirely.

### Proof of Concept
Not independently reproducible from this repo alone, because it requires driving the external `cairo-lang` Sierra→CASM compiler to emit a `bytecode_segment_lengths` value equivalent to a deeply nested chain such as:
```
NestedIntList::Node(vec![NestedIntList::Node(vec![NestedIntList::Node(vec![... NestedIntList::Leaf(1) ...])])])
```
with nesting depth in the thousands. Conceptually: submit a `DECLARE` transaction whose Sierra program contains thousands of nested branches/functions so the compiler-emitted segment tree is deeply nested; when `SierraCompiler::compile` ( [8](#0-7) ) computes `executable_class.hash(&HashVersion::V2)`, or when the class is later re-executed by the Starknet OS hint `load_classes_and_create_bytecode_segment_structures`, the unbounded recursion should exhaust the native stack and crash the process. Confirming the actual achievable nesting depth requires compiling a real crafted Sierra program with the pinned `cairo-lang` compiler version, which is outside the scope of static code inspection.

/// Computes the hash of the bytecode according to the provided segment structure.
/// The function iterates over the bytecode, partitioning it into segments as described
/// by the `HashableNestedIntList`. For each segment, it recursively computes a hash
/// using the provided `StarkHash` implementation. The final result is a hash representing the
/// entire bytecode structure, as required by Starknet's contract class hash computation.
fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
