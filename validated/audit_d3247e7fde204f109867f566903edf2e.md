### Title
Loss of excess attached deposit in `AddressRegistrar::register` due to missing overpayment refund - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `register` function in the NEAR wallet contract's `AddressRegistrar` only validates that the attached deposit is **at least** the required storage cost, but never refunds any excess deposit when the registration succeeds. Any caller who attaches more than the exact `required_deposit` permanently loses the difference, with no accounting or withdrawal path to recover it.

### Finding Description
`register` computes an exact `required_deposit` from `storage_byte_cost() * bytes_to_store` and only rejects the call if `given_deposit < required_deposit`: [1](#0-0) 

On the success path (`Entry::Vacant`), the mapping is inserted and the function returns without ever comparing `given_deposit` to `required_deposit` for a refund, or transferring back any excess: [2](#0-1) 

Notably, the contract itself demonstrates that it *knows* how to refund a deposit — the collision (`Entry::Occupied`) branch explicitly refunds the entire `given_deposit` back to `predecessor_account_id`: [3](#0-2) 

This asymmetry means the "success" path is the only one that silently keeps any surplus. Since `#[payable]` methods on NEAR simply credit the attached deposit to the contract account balance with no obligation for the contract to do anything with it, any yoctoNEAR above `required_deposit` becomes stuck in the contract with no owner/admin withdraw function defined anywhere in this contract, and no accounting field tracking "owed" refunds. This mirrors the referenced report's bug class exactly: a caller cannot query the exact required price beforehand via a view-only helper (there is no `fn required_deposit(account_id) -> NearToken`-style getter), so any caller who attaches a safety margin (or simply reuses the same deposit amount across different account IDs of varying byte length) overpays and never gets the difference back.

### Impact Explanation
Any unprivileged caller invoking `register` with `attached_deposit > required_deposit` permanently loses the excess amount — a direct, unauthorized value loss reachable from a single transaction/contract call, with no possible recovery mechanism in the contract. This qualifies as "permanently frozen funds" / concrete loss of funds for the caller.

### Likelihood Explanation
High likelihood in practice: `required_deposit` depends on the length of the `account_id` argument, which varies per call, so any caller/wallet UI that attaches a fixed or rounded deposit amount (a very common client-side pattern to avoid `Insufficient deposit` panics) will routinely overpay by some margin, and that margin is lost every single successful registration.

### Recommendation
Refund the excess deposit on the success path as well, mirroring the logic already used in the collision branch:
```rust
Entry::Vacant(entry) => {
    let address_str = format!("0x{}", hex::encode(address));
    entry.insert(account_id);
    let excess = given_deposit.saturating_sub(required_deposit);
    if excess > NearToken::from_yoctonear(0) {
        let refund_promise = env::promise_batch_create(&env::predecessor_account_id());
        env::promise_batch_action_transfer(refund_promise, excess);
    }
    Some(address_str)
}
```
Optionally also add a view function (e.g. `required_deposit(account_id: AccountId) -> NearToken`) so callers can compute the exact price before calling `register`, consistent with the recommendation in the referenced report.

### Proof of Concept
1. Caller computes (or guesses) `bytes_to_store = 20 + account_id.len()` and the current `storage_byte_cost()`.
2. Caller calls `register(account_id)` attaching `given_deposit = required_deposit + X` yoctoNEAR (e.g., attaching a generous fixed deposit to be safe against varying account_id lengths).
3. Since `given_deposit >= required_deposit`, the check at [4](#0-3)  passes.
4. The address is not previously registered, so execution enters the `Entry::Vacant` branch at [5](#0-4) , which inserts the mapping and returns `Some(address)` without ever transferring back the `X` yoctoNEAR excess.
5. The `X` yoctoNEAR remains credited to the `AddressRegistrar` contract account balance permanently, with no function in the contract able to move it back to the caller.
