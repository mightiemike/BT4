## Title
`sanitizeShop` fails to normalize case, allowing `getOfflineId` to derive divergent session IDs for the same shop domain - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

## Finding Description
`getOfflineId` builds a session ID by concatenating a static prefix with the output of `sanitizeShop(config)(shop, true)`: `` `offline_${sanitizeShop(config)(shop, true)}` `` [1](#0-0) . `sanitizeShop` validates the shop string against a regex `^[a-zA-Z0-9][a-zA-Z0-9-_]*\.(myshopify\.com|shopify\.com|myshopify\.io|shop\.dev)[/]*$` and, if it matches, returns the **original, unmodified string** (only the domain suffix segment is case-sensitively matched; the shop-name segment class `[a-zA-Z0-9-_]*` deliberately accepts both cases) [2](#0-1) . There is no `.toLowerCase()` call or Unicode/IDNA canonicalization anywhere in this function.

Consequently, `getOfflineId('Shop-A.myshopify.com')` and `getOfflineId('shop-a.myshopify.com')` produce two distinct strings (`offline_Shop-A.myshopify.com` vs `offline_shop-a.myshopify.com`), even though Shopify treats shop domains as effectively lowercase/case-insensitive identifiers for a single tenant (as confirmed by the existence of a dedicated case-sensitivity migration for session storage, `packages/apps/session-storage/shopify-app-session-storage-postgresql/src/migrations.ts`, which the maintainers added specifically to reconcile previously-inconsistent-case shop rows) [3](#0-2) .

However, I could not identify a reachable attacker-controlled path where this case divergence lets an unprivileged attacker forge or collide with another distinct shop's session row:
- Trailing dots and percent/punycode-encoded characters are rejected outright by the regex `^[a-zA-Z0-9][a-zA-Z0-9-_]*\.(...)[/]*$`, since a literal trailing `.` after the domain, or non-ASCII/percent-encoded bytes, do not match `[a-zA-Z0-9-_]` and the domain suffix must match one of the literal fixed strings exactly — these variants simply fail validation and `sanitizeShop` returns `null` (throwing `InvalidShopError` when `throwOnInvalid` is true) rather than being accepted with a different normalized form.
- Webhook-derived shop values reach `getOfflineId` indirectly via JWT `dest` claims decoded by `decodeSessionToken`, which are only trusted after JWT signature verification against `apiSecretKey` — an attacker without the secret cannot inject an arbitrary-case shop string into that path [4](#0-3) .
- The only path where an unprivileged actor could influence the literal case of the `shop` string is the OAuth `begin`/install URL that a user (merchant/browser) supplies themselves as a query parameter before the OAuth HMAC-protected callback occurs — i.e., the actor providing the mixed-case value is the shop owner acting on their own tenant, not an attacker impersonating a different tenant. This produces, at worst, self-inflicted session duplication/"split-brain" for that same shop's own offline session (two rows for one real store), not unauthorized cross-tenant read/write of a different legitimate shop's data, since two different real shops cannot share the same case-folded name (`Shop-A` and `shop-b` are simply different shops, not colliding identifiers).

## Impact Explanation
The realistic impact is confined to a single merchant's own tenant: if the same real shop is addressed with different letter-casing across two request paths (e.g., install URL vs. later API/embedded-app calls), the app may create two different offline `Session` rows for what should be one store, causing token/session inconsistency (a shop could appear "not installed" or use a stale/duplicate access token in one code path). This does not meet the bar of forged cross-tenant session access, token theft, or ID collision between two distinct legitimate shops, because no attacker-controlled, HMAC/JWT-unverified channel was found that lets one unprivileged party impersonate a *different* shop's exact-case domain string and collide with that other shop's derived ID.

## Likelihood Explanation
Low. Exploiting this requires an app (or its own users) to pass inconsistent letter-casing for the *same* shop domain across independent code paths, which is a data-hygiene issue rather than an attacker-forgeable, cross-tenant compromise. All paths that carry `shop`/`dest` values into `getOfflineId` from network input are gated by HMAC or JWT signature verification tied to `apiSecretKey`, which an unprivileged attacker does not possess.

## Recommendation
Although not exploitable as a cross-tenant vulnerability under the stated threat model, hardening `sanitizeShop` (packages/apps/shopify-api/lib/utils/shop-validator.ts) to lowercase (and, if applicable, IDNA/punycode-normalize and strip trailing dots from) the shop string before matching/returning it would eliminate the session-ID split-brain risk for a single tenant and make ID derivation deterministic regardless of casing supplied by callers.

## Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts (illustrative addition)
test('sanitizeShop does not normalize case', () => {
  const shopify = shopifyApi(testConfig());
  const upper = shopify.utils.sanitizeShop('Shop-A.myshopify.com');
  const lower = shopify.utils.sanitizeShop('shop-a.myshopify.com');
  expect(upper).not.toEqual(lower); // both are valid, non-identical outputs
});
```
This demonstrates the divergence described, but no request-level PoC could be constructed within the stated unprivileged-attacker threat model that turns this into a forged or cross-tenant session collision, since every network-input path into `getOfflineId` (JWT `dest`, HMAC-verified webhook headers, OAuth callback params) is cryptographically bound to the app secret before the shop value is trusted.

```typescript
export function sanitizeShop(config: ConfigInterface) {
  return (shop: string, throwOnInvalid = false): string | null => {
    let shopUrl = shop;
    const domainsRegex = [
      'myshopify\\.com',
      'shopify\\.com',
      'myshopify\\.io',
      'shop\\.dev',
    ];

    // Add domains from transformations (both source and target)
    if (config.domainTransformations) {
      domainsRegex.push(...getTransformationDomains(config));
    }

    const shopUrlRegex = new RegExp(
      `^[a-zA-Z0-9][a-zA-Z0-9-_]*\\.(${domainsRegex.join('|')})[/]*$`,
    );

    const shopAdminRegex = new RegExp(
      `^admin\\.(${domainsRegex.join('|')})/store/([a-zA-Z0-9][a-zA-Z0-9-_]*)$`,
    );

    const isShopAdminUrl = shopAdminRegex.test(shopUrl);
    if (isShopAdminUrl) {
      shopUrl = shopAdminUrlToLegacyUrl(shopUrl) || '';
    }

    const sanitizedShop = shopUrlRegex.test(shopUrl) ? shopUrl : null;
    if (!sanitizedShop && throwOnInvalid) {
      throw new InvalidShopError('Received invalid shop argument');
    }

    if (sanitizedShop && config.domainTransformations) {
      return applyDomainTransformations(sanitizedShop, config);
    }

    return sanitizedShop;
  };
```
