## Title
Replay-verification helper `ensure_match_transaction_info` silently skips state-checkpoint hash comparison, allowing state-root divergence to go undetected during replay - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by Aptos's offline replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, `aptos-move/cli`) to confirm that a freshly re-executed transaction output matches the previously-committed `TransactionInfo` fetched from a backup/archive. The function explicitly checks status, gas used, write-set hash, and event root hash, but its own inline `TODO` comment documents that it **does not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the authenticated `TransactionInfo`.

### Finding Description [1](#0-0) 

The function computes and compares:
- execution status,
- gas used,
- `write_set_hash` vs `txn_info.state_change_hash()`,
- `event_root_hash` vs `txn_info.event_root_hash()`.

It then returns `Ok(())` without ever comparing the locally-recomputed state (Sparse Merkle Tree) root against `txn_info.state_checkpoint_hash()` (or the hot-state / native-position checkpoint hash fields introduced by `TransactionInfoV1`). The comment makes the gap explicit:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This is the single call site used by the replay pipeline: `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes historical transactions and calls `ensure_match_transaction_info` per transaction, treating a returned `Ok(())` as proof the replay matched the archived, signature-authenticated `TransactionInfo`: [3](#0-2) 

Because `TransactionInfo` (both V0 and V1) is exactly the structure committed into the transaction accumulator and signed by validators — carrying `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` as the state-commitment fields — skipping their comparison means the verifier only checks write-set/event/gas/status equality but not the actual Merkle state root produced by execution: [4](#0-3) [5](#0-4) 

### Impact Explanation
`ensure_match_transaction_info` is the authoritative correctness gate for Aptos's replay-verify tooling, which exists specifically to detect VM/execution non-determinism or state-root divergence between historical, consensus-committed data and current-node re-execution (e.g., across VM upgrades, feature-flag rollouts such as the referenced `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, or hardware/serialization bugs). Because the function reports success even when the recomputed state (or hot-state/position-state) root diverges from the authenticated on-chain root, an operator relying on `replay_on_archive`/`aptos-debugger`/the CLI replay command would receive a false "replay succeeded" signal in exactly the scenario the tool is meant to catch: a hard-fork-only state divergence. This directly matches the in-scope "Hard-fork-only divergence during commit, replay, restore, or proof verification" category — the state-commitment invariant (replayed state root == authenticated state-checkpoint hash) is broken, and the corrupted/incorrect value that is not being checked is `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`.

This gap does not corrupt the live committed ledger (write-set/event checks still guard the executor→storage commit path elsewhere), so it is not a live consensus-halting or fund-loss bug; its impact is confined to false-negative detection in the replay/verification tooling used to certify state-root correctness before/around hard forks.

### Likelihood Explanation
The gap is 100% deterministic and unconditional whenever `ensure_match_transaction_info` is invoked (which is on every transaction processed by `replay_on_archive`, `aptos-debugger`, and the `aptos-move/cli` replay command) — no attacker interaction or special conditions are required beyond a genuine state-root divergence existing between archived and re-executed data (e.g., introduced by a bug in a new VM/feature). The comment in the code confirms this is a known, currently-unaddressed condition (gated behind not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), i.e., the maintainers are aware but the check is still missing today.

### Recommendation
In `ensure_match_transaction_info` (`types/src/transaction/mod.rs`), before returning `Ok(())`, recompute the resulting state root (and hot-state/position-state root where applicable) from the transaction output/committed state and compare it against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` (for `TransactionInfoV1`), returning an error on mismatch just as is done for the write-set and event root hashes.

### Proof of Concept
Not directly exploitable by an unprivileged network attacker (no consensus/state corruption is produced); the "PoC" is a code-level demonstration:
1. Given an archived transaction with `TransactionInfo.state_checkpoint_hash = H_correct`.
2. Locally re-execute the same transaction such that the resulting write set, events, gas, and status are identical to the archive but the resulting state root differs (`H_wrong` != `H_correct`) — e.g., due to a native code / feature-flag change affecting an unrelated piece of state.
3. Call `output.ensure_match_transaction_info(version, &txn_info, ..)`.
4. Observe the call returns `Ok(())` despite `H_wrong != H_correct`, because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared, as shown at [6](#0-5) , and reproduced through the replay path at [7](#0-6) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
