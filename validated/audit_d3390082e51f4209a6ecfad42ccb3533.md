### Title
Missing slippage protection in `ExchangeWithdrawActuator` allows front-run/MEV-style value extraction on TRC10 exchange withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeWithdrawContract` used for `wallet/exchangewithdraw` lets an exchange creator withdraw `quant` of one paired token from a TRC10 bancor-style exchange pool, receiving a proportional `anotherTokenQuant` of the counter-token, computed from the exchange's *current* pool balances at execution time. Unlike `ExchangeTransactionContract` (used for `exchangetransaction`), which carries an explicit `expected` field enforcing a caller-supplied minimum output, `ExchangeWithdrawContract` has **no minimum-output/slippage parameter at all**.

### Finding Description
`ExchangeTransactionActuator` implements proper slippage protection: the contract carries a caller-supplied `expected` field, and `doValidate()` rejects the transaction if the computed `anotherTokenQuant` is less than `tokenExpected`: [1](#0-0) 

In contrast, `ExchangeWithdrawContract`'s protobuf message only has `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field: [2](#0-1) 

`ExchangeWithdrawActuator.doValidate()` and `execute()` compute `anotherTokenQuant` purely from the exchange's live pool balances (`firstTokenBalance`/`secondTokenBalance`) at the moment the transaction is processed, using the bancor-style ratio math, with no way for the caller to specify or enforce a minimum acceptable amount of the counter-token: [3](#0-2) [4](#0-3) 

The only checks present are that `anotherTokenQuant > 0`, that the exchange has enough balance, and a "precision" rounding check — none of which protect the caller against the pool ratio shifting between when they sign/broadcast the transaction and when it actually lands in a block: [5](#0-4) 

This is structurally identical to the reported bug class: an AMM/exchange operation that computes an output amount from pool state but is hard-coded/omits a minimum-output guard, so it "will accept any amount of tokens, even close to worthless ones," exposing the caller to front-running.

### Impact Explanation
Because `ExchangeWithdrawContract` transactions are broadcast to the public mempool before block inclusion, and the payout ratio depends on the exchange's live `firstTokenBalance`/`secondTokenBalance` at execution time, another party (or the block-producing witness itself) can observe a pending withdraw and front-run it with `ExchangeTransactionContract` trades that shift the pool ratio unfavorably before the withdraw executes. Since the withdraw has no `expected`/minimum parameter, the withdraw actuator cannot reject an unfavorable outcome — the exchange creator receives whatever the manipulated ratio yields, resulting in a real loss of TRC10 token value for the withdrawing account. This is an accounting/asset-loss impact reachable purely via normal broadcast transactions, without any privileged actor.

### Likelihood Explanation
Likelihood is limited by the fact that only the exchange's *creator* can call `ExchangeWithdrawContract` (validated via `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), and the attacker needs enough capital/timing precision to move the pool ratio meaningfully within the target block window — analogous to Solana MEV/Jito bundling referenced in the source report, but on java-tron witnesses have direct block-packing control over TRC10 exchange transactions, making ordering manipulation straightforward for a witness or a well-resourced trader monitoring the mempool. [6](#0-5) 

### Recommendation
Add a caller-supplied minimum-output field (e.g. `expected`) to `ExchangeWithdrawContract`, mirroring `ExchangeTransactionContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` falls below the caller's specified minimum, consistent with the check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeWithdrawContract{exchange_id, token_id=A, quant=X}` expecting to receive `Y` of token B based on the current pool ratio.
2. Before this transaction is packed into a block, an attacker (or colluding witness) submits `ExchangeTransactionContract` trades against the same `exchange_id` that shift the `firstTokenBalance`/`secondTokenBalance` ratio unfavorably for token B.
3. When the withdraw executes, `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-manipulated balances: [7](#0-6) 
4. Because there is no `expected`/minimum parameter to check against, the withdraw succeeds and credits the creator with a reduced `anotherTokenQuant`, with no mechanism to abort the transaction, resulting in value loss compared to the ratio observed when the transaction was signed.
