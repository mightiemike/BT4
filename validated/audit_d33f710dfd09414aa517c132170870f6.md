### Title
Stale cached `cycle-total-weight` diverges from the live `.signers` weight, letting a sub-threshold minority finalize the DKG aggregate key - ([File: stackslib/src/chainstate/stacks/boot/signers-voting.clar])

### Summary
`signers-voting.clar`'s `get-and-cache-total-weight` caches the total signer weight for a reward cycle the first time it is computed, and never refreshes it. `vote-for-aggregate-public-key` uses this cached total (via `get-threshold-weight`) as the consensus denominator, while each individual vote's weight (`get-signer-weight`) is fetched live from `.signers`. If the `.signers` weight data for that reward cycle is written more than once (the reward-set/anchor-block resolution path in the coordinator explicitly allows overwriting previously-stored reward-cycle data once the true anchor block becomes known), the cached denominator and the live numerator can be computed against two different underlying `.signers` states — exactly the "stale cached value used to compute a ratio/threshold" bug class from the Ditto report, applied here to signer-weight-based consensus instead of an asset price.

### Finding Description
`get-and-cache-total-weight` in `stackslib/src/chainstate/stacks/boot/signers-voting.clar:103-109` is a memoizing cache:

```
(define-private (get-and-cache-total-weight (reward-cycle uint))
    (match (map-get? cycle-total-weight reward-cycle)
        total (ok total)
        (let ((signers (unwrap! (contract-call? .signers get-signers reward-cycle) ...))
                (total (fold sum-weights signers u0)))
            (map-set cycle-total-weight reward-cycle total)
            (ok total))))
``` [1](#0-0) 

Once cached, this value is never invalidated for the reward cycle. It feeds `get-threshold-weight`, the sole source of the consensus bar for finalizing a reward cycle's DKG aggregate public key:

```
(define-read-only (get-threshold-weight (reward-cycle uint))
    (let ((total-weight (default-to u0 (map-get? cycle-total-weight reward-cycle))))
        (/ (+ (* total-weight threshold-consensus) u99) u100)))
``` [2](#0-1) 

In `vote-for-aggregate-public-key`, each vote's weight is pulled live from `.signers` (`get-signer-weight` → `contract-call? .signers get-signer-by-index`), but the tally is compared against the *cached* `threshold-weight`: [3](#0-2) [4](#0-3) 

On the node side, the reward-cycle/signer-set data that `.signers` (and hence `get-signers`) reflects is not guaranteed to be written exactly once and never touched again. The coordinator's PoX-anchor-block resolution logic explicitly documents and implements overwriting previously-stored reward-cycle info once the true anchor block is later confirmed:

```
let need_to_store = if let Some(reward_cycle_info) = preprocessed_reward_set {
    // overwrite if we have an unknown anchor block
    !reward_cycle_info.is_reward_info_known()
} else {
    true
};
``` [5](#0-4) 

If the signer set/weights derived for a reward cycle change between the first vote (which populates `cycle-total-weight`) and a later vote in the same cycle (because the underlying reward-set computation resolved differently once more chain data was available), `get-threshold-weight` continues to gate consensus against the old, now-incorrect total. This breaks the intended equality:

`sum(weights of signers who voted for key) ≥ 70% * ACTUAL_current_total_signer_weight`

Instead the check enforces `≥ 70% * STALE_cached_total_signer_weight`, which is a strictly weaker (or stronger, if weight decreased) bound whenever the two totals diverge.

### Impact Explanation
If the true total weight has grown since caching (e.g., more/larger signers entered the set for that cycle as reward-set data was finalized), a set of signers holding strictly less than 70% of the real, current signer weight can push `new-total` over the stale `threshold-weight` and finalize (`map-set aggregate-public-keys`) the DKG key for the reward cycle. This is a "signer weight below threshold" divergence as flagged in-scope: the finalized aggregate key underpins Nakamoto block signing/verification for that reward cycle, so a wrongly-authorized minority can lock in a key that the true majority of signers did not actually approve, producing consensus disagreement about which aggregate key/blocks are valid for the cycle — bounded, minority-triggerable divergence in the signer-weight threshold path (High).

### Likelihood Explanation
Requires two conditions: (1) at least one vote is cast early enough to populate `cycle-total-weight` before the reward-set/anchor-block data for that cycle is later revised, and (2) the underlying `.signers`/reward-set weight assignment for the cycle is in fact rewritten after that point. Condition (2) is explicitly supported by the coordinator's own "overwrite if unknown anchor block" logic for reward-cycle info; whether this specific overwrite path can alter the *set of Nakamoto signer weights* already consumable via `.signers get-signers` for the *same* reward cycle in time to matter (i.e., before voting on that cycle's key concludes) is a timing property I could not fully verify with the tools available — the affected code paths that write `.signers` in Nakamoto (`pox_4_compute_and_update_signers` / `pox_5_compute_and_update_signers`) appear intended to run once per cycle transition. This limits confidence to "plausible but timing-dependent," rather than a demonstrated end-to-end trigger from the artifacts inspected.

### Recommendation
Do not cache `cycle-total-weight` across the whole voting window for a reward cycle without invalidation. Either drop the cache and recompute the total weight from `.signers get-signers` on every `get-threshold-weight`/vote call (paying the cost of a fresh call, as is already done for individual signer weights), or explicitly invalidate/refresh `cycle-total-weight` whenever `.signers` is rewritten for that reward cycle (e.g., have the Rust-side `update_signers` call into `signers-voting` to bust the cache, or version the cache key by a reward-set-generation counter).

### Proof of Concept
Conceptual sequence (Clarity/consensus-level, no code changes needed to demonstrate the mismatch, only two `.signers` writes for the same `reward-cycle`):
1. `.signers` is populated for `reward-cycle=N` with total weight `W1` (e.g., 100).
2. A signer calls `vote-for-aggregate-public-key` for cycle `N`; `get-and-cache-total-weight` caches `cycle-total-weight[N] = 100`, so `threshold-weight = 70`.
3. Before consensus is reached, the node's reward-cycle resolution overwrites `.signers` for cycle `N` (per `need_to_store` path in `coordinator/mod.rs`) such that the new true total weight is `W2 = 200` (threshold should now be `140`).
4. Because `cycle-total-weight[N]` is already cached at `100`, `get-threshold-weight` still returns `70`.
5. A coalition of signers whose live weights sum to `71` (35.5% of the real `W2=200`, but 71% of the stale `100`) casts a vote for a specific aggregate key; `new-total (71) >= threshold-weight (70)` passes, and the key is finalized despite representing well under the intended 70%-of-current-weight majority.
