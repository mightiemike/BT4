## Title
`ensure_match_transaction_info` never validates the state-checkpoint / hot-state / position state root, letting a replay with a wrong committed state root be reported as a successful match - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling to check that a locally re-executed `TransactionOutput` matches the on-chain, ledger-accumulator-committed `TransactionInfo`. It checks status, gas used, write-set hash, and event-root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` from the `TransactionInfo` against anything derived from the replay. The function's own comment acknowledges this gap.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  is documented to validate that "TransactionOutput does not match TransactionInfo" for replay/verify use cases. It performs exactly four checks:

- status vs `txn_info.status()` [2](#0-1) 
- gas used vs `txn_info.gas_used()` [3](#0-2) 
- write-set hash vs `txn_info.state_change_hash()` [4](#0-3) 
- event-root hash vs `txn_info.event_root_hash()` [5](#0-4) 

It never reads or checks `txn_info.maybe_state_checkpoint_hash()` / `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The code's own TODO comment states this explicitly: [6](#0-5) 

This means: the write-set *hash* is checked (so the individual write ops that were produced by the VM for that transaction are validated), but the state root produced by *applying* that write set to the JMT/state tree (`state_checkpoint_hash`, and, when the position/trading-native and hot-state features are enabled, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) is never validated. `state_checkpoint_hash` is exactly the accumulator-committed Merkle root that authenticates the entire ledger state at a checkpoint boundary — see how it's populated by the executor at commit time in `assemble_transaction_infos` (`maybe_state_checkpoint_hash`, `maybe_hot_state_checkpoint_hash`, `maybe_position_state_checkpoint_hash`) [7](#0-6) , and how it's later relied upon downstream as the authenticated root for fast-sync of the position/native-trading state tree [8](#0-7) .

`ensure_match_transaction_info` is invoked by the Move CLI's transaction-replay/gas-profiling/benchmark flow (`aptos-move/cli/src/commands.rs`) as the pass/fail gate that decides whether a locally replayed transaction "matches" the authenticated on-chain record: [9](#0-8) [10](#0-9) 

The comment further notes that this same comparator design is expected to be used by `db-tool`'s `replay_on_archive` verification tooling before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on — i.e. it is explicitly intended as (part of) the state-integrity gate for replay-verify, not just a CLI convenience.

### Impact Explanation
This breaks the "VM outputs, transaction infos ... must survive executor-to-storage handoff unchanged" and "replay paths ... must not reinterpret committed data into a different ledger state" invariants required by the state-integrity gate. A bug in state-tree application (JMT insertion, hot-state merge, or the trading-native/position state tree merge) that produces a *correct write-set hash* (the individual write ops are right) but an *incorrect resulting root* (e.g., wrong key ordering/sharding when merging into the JMT, a stale/duplicate leaf, or a race in `hot_state_updates`/`position_state_summary` construction) would go completely undetected by any tool relying on `ensure_match_transaction_info`. Replay-verify would report "success" even though the authenticated state root diverges from what local execution actually produced — precisely the scenario the code's own comment warns about for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

Because this is the exact comparator gating whether a discrepancy between local execution and the authenticated ledger state is surfaced, its silence on checkpoint hashes means state-root corruption (hard-fork-class divergence, or an execution/storage bug) can pass every automated check that uses this function, delaying or preventing detection of a wrong committed state root.

### Likelihood Explanation
The gap is not reachable by low-privilege on-chain actors to directly forge data (this is a verification-tool gap, not an execution/authorization bypass), so it does not by itself let anyone commit bad state to mainnet. Its significance is that it silently disables a proof-integrity check that other code paths and the codebase's own commentary treat as a prerequisite for safely enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` — meaning any latent state-root computation bug (state checkpoint hash, hot-state root, or position-state root) introduced elsewhere in the executor/storage pipeline would not be caught by this verification path even though the tooling and its callers assume it would be.

### Recommendation
Extend `ensure_match_transaction_info` to also compare, when present on `txn_info` and derivable from the replay: `state_checkpoint_hash` (state_checkpoint_hash of the replay against `txn_info.maybe_state_checkpoint_hash()`), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, mirroring the same "ensure!" pattern already used for gas/status/write-set/event-root. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this comparator being completed, as the existing TODO instructs.

### Proof of Concept
No dynamic PoC is provided; this is a static code-review finding based on direct inspection of `ensure_match_transaction_info` [11](#0-10)  showing the absence of any assertion on `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, confirmed by the author's own inline TODO acknowledging the gap, and by its call sites in `aptos-move/cli/src/commands.rs` that treat a clean return as proof of a correct replay.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    /// The expected snapshot root for the given kind at the target version, read
    /// from the target transaction info: main state's state checkpoint hash, or
    /// the committed position state root (guaranteed present once the position
    /// stage runs, per `snapshot_kind_applies_to_target`). All kinds share the
    /// target version, so this is taken from the target output, not a storage read.
    fn expected_snapshot_root(&mut self, kind: StateKind) -> Result<HashValue, Error> {
        let transaction_output_to_sync = self.get_transaction_output_to_sync()?;
        let target_transaction_info = transaction_output_to_sync
            .get_output_list_with_proof()
            .proof
            .transaction_infos
            .first()
            .ok_or_else(|| {
                Error::UnexpectedError("Target transaction info does not exist!".into())
            })?;
        match kind {
            StateKind::MainState => target_transaction_info
                .ensure_state_checkpoint_hash()
                .map_err(|error| {
                    Error::UnexpectedError(format!(
                        "State checkpoint must exist! Error: {:?}",
                        error
                    ))
                }),
            StateKind::Position => target_transaction_info
                .position_state_checkpoint_hash()
                .ok_or_else(|| Error::UnexpectedError("Missing position state root!".into())),
        }
