### Title
Unchecked `usize` subtraction of remaining VM steps can underflow and panic during transaction execution - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
`AccountTransaction::run_revertible` computes execution steps consumed for the revert-path receipt as a plain, unchecked `usize` subtraction: `n_allotted_execution_steps - execution_context.n_remaining_steps()`, unlike every other step-accounting operation in the same module which uses `saturating_sub`/`checked_sub`. This mirrors the Panoptic bug class: an arithmetic operation silently assumes an invariant (`remaining <= allotted`) instead of defensively clamping it, so if that invariant is ever violated the subtraction underflows.

### Finding Description
`n_allotted_execution_steps` is derived from `execution_context.subtract_validation_and_overhead_steps(...)`, which internally uses `saturating_sub` when lowering the step budget [1](#0-0) . After `run_execute` consumes steps via the VM's `RunResources`, the code computes:

```
let execution_steps_consumed =
    n_allotted_execution_steps - execution_context.n_remaining_steps();
``` [2](#0-1) 

This is a raw `usize` subtraction with no `checked_sub`/`saturating_sub` guard, in contrast to `subtract_steps`, which explicitly comments "Saturating, since subtracting more steps than remain would underflow" for an analogous computation [1](#0-0) . The code implicitly assumes `execution_context.n_remaining_steps()` after execution can never exceed the budget allotted before execution (`n_allotted_execution_steps`). All step-limiting paths I was able to inspect (`subtract_steps`, `cap_remaining_steps`, `set_remaining_steps`) only ever lower the remaining-step count, never raise it, so I could not find a concrete call path where remaining steps grow back above the allotted budget within the same `EntryPointExecutionContext` instance. I was not able to fully audit every recursive/inner-call and Cairo-native code path that might reset or reuse `vm_run_resources` in a way that could increase `n_remaining_steps()` beyond `n_allotted_execution_steps` (e.g., via `RunResources` handling in nested Cairo0/Cairo1/native execution) with the tools available.

### Impact Explanation
If reachable, this would be a **debug-assertion / overflow panic** during otherwise normal transaction execution (invoke transactions triggering the revertible-execution path), executed with data fully controlled by an unprivileged transaction sender. Because Rust `usize` subtraction underflow panics when overflow-checks are enabled (which appears to be the crate's convention, given the pervasive use of `checked_sub`/`saturating_sub`/explicit panics elsewhere in this very file and adjacent files), a triggering transaction could crash block-building/execution for any node processing it, which is a potential liveness/DoS issue for the sequencer's blockifier execution pipeline (a "network unable to confirm new transactions" class of impact) if a concrete trigger exists. Without a confirmed trigger, I cannot elevate this beyond a low-confidence, unconfirmed pattern-match.

### Likelihood Explanation
Low-to-uncertain. I found no confirmed reachable path where `execution_context.n_remaining_steps()` exceeds `n_allotted_execution_steps` after `run_execute`; every step-adjustment function I reviewed monotonically decreases the remaining step count. The similarity to the Panoptic bug is purely structural (an unguarded subtraction next to guarded siblings, based on an assumed invariant), not a demonstrated exploit.

### Recommendation
- Replace the raw subtraction with `n_allotted_execution_steps.saturating_sub(execution_context.n_remaining_steps())` (or `checked_sub` with an explicit panic message), consistent with the pattern already used in `subtract_steps` [3](#0-2) .
- Add a regression/fuzz test that exercises nested/recursive Cairo0, Cairo1, and (if enabled) Cairo-native call paths to confirm `n_remaining_steps()` can never exceed the pre-execution allotment, closing the residual uncertainty noted above.

### Proof of Concept
No concrete PoC could be constructed with available tooling; I could not find a call path that increases `n_remaining_steps()` above `n_allotted_execution_steps`, so I cannot confirm this is exploitable, only that the code lacks the same defensive guard used elsewhere for equivalent step arithmetic [2](#0-1) .

    /// Subtracts the given number of steps from the currently available run resources.
    /// Used for limiting the number of steps available during the execution stage, to leave enough
    /// steps available for the fee transfer stage.
    /// Returns the remaining number of steps.
    pub fn subtract_steps(&mut self, steps_to_subtract: usize) -> usize {
        // Saturating, since subtracting more steps than remain would underflow.
        let new_remaining_steps = self.n_remaining_steps().saturating_sub(steps_to_subtract);
        self.set_remaining_steps(new_remaining_steps)
    }
