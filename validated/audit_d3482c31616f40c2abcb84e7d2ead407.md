### Title
Unbounded growth of the delayed-declare transaction queue bypasses mempool capacity limits, enabling sequencer OOM - (File: `crates/apollo_mempool/src/mempool.rs`)

### Summary
The reported Xens CVE describes an unbounded queue (Xen watch-event queue) that a low-privilege actor can fill faster than a single consumer thread can drain it, causing an out-of-memory condition in the backend. The Apollo Sequencer mempool has a structurally analogous unbounded, capacity-unchecked queue: `Mempool::delayed_declares`, which buffers incoming `Declare` transactions for `declare_delay` seconds before they are moved into the capacity-tracked `tx_pool`.

### Finding Description
`Mempool` maintains two distinct transaction stores: [1](#0-0) 

`delayed_declares` is explicitly documented as excluded from `tx_pool` (the store that capacity accounting is built around): [1](#0-0) 

In `add_tx`, the transaction is first validated and its capacity impact checked via `add_tx_validations`, which calls `self.exceeds_capacity(tx, freed_bytes)` — a check performed against the pool's tracked size, not against `delayed_declares`: [2](#0-1) [3](#0-2) 

Only after this capacity check passes does `add_tx` decide whether the transaction is a `Declare` transaction to be delayed, and if so pushes it into the separate `delayed_declares` `AddTransactionQueue` — which tracks its own `size_in_bytes` but is never consulted by `exceeds_capacity`/`handle_capacity_overflow`: [4](#0-3) [5](#0-4) 

Because the capacity gate (`capacity_in_bytes`, from `MempoolStaticConfig`) is enforced only against `tx_pool`'s tracked bytes, and `delayed_declares` is a second, unbounded `VecDeque`-backed buffer that persists for `declare_delay` (default 60s) before draining, an unprivileged sender who can submit valid `Declare` transactions (from one or many funded accounts) can push transactions into `delayed_declares` continuously without ever triggering `MempoolError::MempoolFull`, since that queue's byte count is invisible to the capacity check. This mirrors the CVE's root cause: a single-consumer buffer that grows without a bound check while being fed by an external, comparatively cheap, message stream.

### Impact Explanation
If an attacker can sustain a submission rate of valid `Declare` transactions (across multiple accounts to satisfy nonce/one-per-account constraints) that exceeds the rate at which `add_ready_declares` drains `delayed_declares` into `tx_pool` after `declare_delay`, the sequencer process's memory usage from `delayed_declares` grows unbounded. This can lead to sequencer process OOM, halting mempool admission and block building — i.e., "a network unable to confirm new transactions," which is one of the accepted impact categories.

### Likelihood Explanation
Exploitability depends on the attacker's ability to sustain high per-second declare-tx throughput (bounded by declaration fee cost and gateway/mempool per-request overhead) for long enough to exhaust sequencer memory before the 60-second `declare_delay` drains the queue. This is a plausible but resource-dependent (fee-cost-gated) DoS vector rather than a trivial single-request trigger, since each enqueued item requires a valid, fee-paying `Declare` transaction to pass gateway/mempool validation.

### Recommendation
Include `delayed_declares.size_in_bytes()` in the capacity accounting used by `exceeds_capacity`/`handle_capacity_overflow`, or enforce an independent byte/count cap on `delayed_declares` so that the sum of `tx_pool` and `delayed_declares` never exceeds `capacity_in_bytes`.

### Proof of Concept
Not independently reproduced in a runnable form; the finding is based on static analysis of `crates/apollo_mempool/src/mempool.rs`. A conceptual PoC: repeatedly submit valid `Declare` transactions from many funded accounts to a sequencer node faster than `declare_delay` (60s default) allows `add_ready_declares` to drain them into `tx_pool`; observe that `MempoolError::MempoolFull` is never raised for these declares (since `exceeds_capacity` only inspects `tx_pool`) while `delayed_declares.size_in_bytes()` grows unbounded, increasing sequencer memory usage.

// A queue to hold transactions that are waiting to be added to the tx pool.
struct AddTransactionQueue {
    elements: VecDeque<(DateTime, AddTransactionArgs)>,
    // Keeps track of the total size of the transactions in this queue.
    size_in_bytes: u64,
}

impl AddTransactionQueue {
    fn new() -> Self {
        AddTransactionQueue { elements: VecDeque::new(), size_in_bytes: 0 }
    }

    fn push_back(&mut self, submission_time: DateTime, args: AddTransactionArgs) {
        self.size_in_bytes = self
            .size_in_bytes
            .checked_add(args.tx.total_bytes())
            .expect("Overflow when adding a transaction to AddTransactionQueue.");
        self.elements.push_back((submission_time, args));
    }

    fn pop_front(&mut self) -> Option<(DateTime, AddTransactionArgs)> {
        let removed_element = self.elements.pop_front();
        if let Some((_, args)) = &removed_element {
            self.size_in_bytes = self
                .size_in_bytes
                .checked_sub(args.tx.total_bytes())
                .expect("Underflow when removing a transaction from AddTransactionQueue.");
        }
        removed_element
    }

    /// Validates an incoming transaction and handles fee escalation.
    fn add_tx_validations(
        &mut self,
        tx_reference: TransactionReference,
        tx: &InternalRpcTransaction,
        account_nonce: Nonce,
    ) -> MempoolResult<()> {
        self.validate_incoming_tx(tx_reference, account_nonce)?;
        let replaced_tx_reference = self.validate_fee_escalation(tx_reference)?;

        // The replaced transaction is still pooled, so its bytes still count toward
        // `size_in_bytes()`. Credit what its removal will free: a same-size bump nets to zero (no
        // overflow handling), and a larger replacement only needs room for the delta, consistent
        // with how a fresh next-nonce transaction is treated. The removal happens only after
        // capacity is confirmed below, so a rejected incoming transaction never strands the
        // account.
        let freed_bytes = replaced_tx_reference.map_or(0, |reference| {
            self.tx_pool
                .get_by_tx_hash(reference.tx_hash)
                .expect("Replacement target from pool must exist.")
                .total_bytes()
        });

        if self.exceeds_capacity(tx, freed_bytes) {
            self.handle_capacity_overflow(tx, account_nonce, freed_bytes)?;
        }

        // Capacity is confirmed: this is the final, infallible mutation before the incoming
        // transaction is inserted by the caller.
        if let Some(existing_tx_reference) = replaced_tx_reference {
            self.remove_replaced_tx(existing_tx_reference);
        }

        Ok(())
    }

    pub fn add_tx(&mut self, args: AddTransactionArgs) -> MempoolResult<()> {
        // First remove old transactions from the pool.
        let mut account_nonce_updates = self.remove_expired_txs();
        if !self.is_fifo() {
            self.add_ready_declares();
        }

        let tx_reference = TransactionReference::new(&args.tx);
        self.add_tx_validations(tx_reference, &args.tx, args.account_state.nonce)
            .inspect_err(|err| self.log_add_tx_error(err, &args))?;

        MEMPOOL_TRANSACTIONS_RECEIVED.increment(
            1,
            &[(LABEL_NAME_TX_TYPE, InternalRpcTransactionLabelValue::from(&args.tx.tx).into())],
        );

        // May override a removed queued nonce with the received account nonce or the account's
        // state nonce.
        account_nonce_updates.insert(
            args.account_state.address,
            self.state.resolve_nonce(args.account_state.address, args.account_state.nonce),
        );

        let should_delay_declare =
            matches!(&args.tx.tx, InternalRpcTransactionWithoutTxHash::Declare(_))
                && !self.is_fifo();
        if should_delay_declare {
            self.delayed_declares.push_back(self.clock.now(), args);
        } else {
            self.add_tx_inner(args);
        }

        self.update_accounts_with_gap(account_nonce_updates);
        self.update_state_metrics();
        Ok(())
    }
