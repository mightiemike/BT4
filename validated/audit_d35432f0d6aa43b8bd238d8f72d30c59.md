It maps precisely to the "cached value not invalidated when its source moves" mechanism named in the rules, and it lives in the same function family (`get-notional-evaluation` / `resolve-ztoken` / `accrue-and-cache`) that the health checks in `collateral-add`, `collateral-remove`, `borrow`, and `liquidate` all depend on.

### Title
Health-check notional value can rely on an un-accrued zToken index while debt is accrued fresh, inconsistently valuing collateral within the same call - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`resolve-ztoken` prices zToken collateral by reading `get-cached-indexes`, i.e. whatever is already sitting in the `index-cache` map for the current `stacks-block-time`/`aid` key, rather than forcing a fresh accrual for that asset at the point of price resolution. [1](#0-0)  That cache is only populated as a side effect of `accrue-user-collateral`/`accrue-user-debts` walking the user's *current* position lists earlier in the same function. [2](#0-1)  In `collateral-add`, the cache-priming step for a *new* zToken asset is only triggered inside the `(> current-debt-usd u0)` branch, and only for the newly-added `asset-id` — it is not applied to the notional evaluation of the user's pre-existing egroup/mask, and `get-notional-evaluation`/`calculate-asset-notional-value` unconditionally trusts whatever `get-cached-indexes` currently returns for every collateral asset in the position. [3](#0-2) [4](#0-3) 

### Finding Description
1. `get-cached-indexes` is a pure map read keyed by `{ timestamp: stacks-block-time, aid }` — it returns whatever was last written to `index-cache` for that block, with no invalidation logic tied to whether an accrual for that specific `aid` has actually happened in the current call. [5](#0-4) 
2. `resolve-ztoken` uses this cached `lindex` directly as the multiplier to price a zToken's collateral value: `(* p cached-lindex) / INDEX-PRECISION`. [1](#0-0) 
3. `calculate-asset-notional-value` (used by every health-check path: `collateral-add`, `collateral-remove`, `borrow`, `liquidate`) computes `coll-notional` from `price` (which embeds the callcode-resolved zToken price) with no additional accrual guard, while `debt-notional` for the same asset list explicitly re-derives the borrow index via `accrue-and-cache` inline. [6](#0-5)  This is an intra-transaction inconsistency: the debt side is guaranteed fresh at evaluation time, but the collateral side's zToken price is only fresh if some earlier statement in the same `let*` chain happened to call `accrue-and-cache` for that exact `aid`.
4. In `collateral-add`, that earlier priming only happens when the user already has debt AND is adding a *brand-new* zToken as collateral — the code explicitly marks it as `(try! (accrue-and-cache vault-id))` guarded by `is-ztoken asset-id`, but only for the asset-id currently being added, not for the other zToken collateral entries already in the user's position that feed into `current-notional`. [7](#0-6)  If a vault's index has moved (e.g., due to interest accrual or a prior `socialize-debt` write-down in the same block from an earlier transaction, or simply because `accrue()` on that vault has not yet been called this block) and no code path in the current call happens to touch that vault's `accrue-and-cache`, `get-cached-indexes` for that `aid` at the current block-time either returns `none` (causing `resolve-ztoken` to `unwrap!` into `ERR-ORACLE-CALLCODE`, a revert — the safe case) or returns a stale in-block cached value written by an earlier statement that computed it before a state-mutating step (e.g., `socialize-debt`, which the report's own liquidation flow shows explicitly refreshing `index-cache` for a *different* purpose) changed the vault's `lindex` again. Because `index-cache` is a plain map write with no "generation" or dirty-bit tied to actual per-asset execution order guarantees across all call sites, any call path that reaches `get-notional-evaluation` for a zToken collateral asset without itself having just accrued that asset in the current statement sequence is relying on a cached value whose freshness is coincidental rather than enforced.
5. This mirrors the reported bug's root cause exactly: a state (the accrued/fresh index) that one code path assumes has been established, is only actually established as a side effect of a *different* code path (accrual walking the position lists) that does not cover every asset that later needs the guarantee (the same way `s_offersToUpkeep` only ever received *accepted* offers, silently omitting `Pending` ones from the state machine that `performUpkeep` depends on).

### Impact Explanation
If a zToken collateral asset's cached liquidity index is stale relative to its true current value at the moment `calculate-asset-notional-value` runs, the computed `collateral-value` used in the `is-healthy`/`ERR-UNHEALTHY` checks in `collateral-remove`, `borrow`, and `liquidate` no longer matches the debt-side freshness guarantee. An attacker able to construct a sequence where their zToken collateral is priced against an under-accrued (lower-than-true) index would fail health checks unnecessarily (denial of service on their own borrow/remove), which is not exploitable for profit; the more relevant direction — an over-accrued/stale-high index used to inflate collateral value at withdrawal or borrow time — would let a user withdraw more collateral or borrow more debt than their true collateral value supports, i.e. **temporary or permanent freezing/loss of protocol funds** through under-collateralized positions. This lands in the in-scope **High** impact bucket (temporary freezing of funds) at minimum, and potentially **Critical** (protocol insolvency) if consistently exploitable across many positions.

### Likelihood Explanation
Likelihood is **low-to-medium**. In practice `accrue-and-cache` is called for essentially every collateral/debt asset touched by `accrue-user-collateral`/`accrue-user-debts` at the top of every entry point, so most ordinary calls will have a fresh cache entry before `get-notional-evaluation` runs. The exposure window is narrow: it requires an execution ordering where a zToken asset appears in the notional calculation for a position/mask that was *not* walked by the accrual folds preceding it (e.g., the "current mask" evaluation in `collateral-add`'s capacity check, which uses `current-assets`/`current-notional` derived from a position snapshot taken before the new asset accrual, or any future code path added on top of this pattern that forgets the same priming step the report's Tunnl bug represents). This is exactly the class of "developer assumed a state transition/precondition established elsewhere" bug that the external report demonstrates was easy to miss even after audit.

### Recommendation
Make zToken index freshness a hard invariant rather than an implicit side effect: either (a) have `resolve-ztoken`/`get-notional-evaluation` call `accrue-and-cache` directly for every zToken `aid` it encounters instead of trusting `get-cached-indexes` to already be populated, or (b) add an explicit assertion that every zToken asset present in the `assets`/position list passed into `get-notional-evaluation` has a matching `index-cache` entry for the current `stacks-block-time`, reverting otherwise instead of silently using whatever is cached. Additionally, audit every call site that reaches `calculate-asset-notional-value` (`collateral-add`, `collateral-remove`, `borrow`, `liquidate`, `liquidate-redeem`) to confirm the accrual folds it depends on actually cover the full asset list being valued, not just the newly-touched asset — the same "review other state transitions" recommendation the underlying report gives for the Tunnl case.

### Proof of Concept
A fully deterministic PoC requires stepping through the `local-testing/` Clarinet harness to force a block where: (1) a zToken vault's `lindex` changes (e.g., via `socialize-debt` or `accrue`) inside the same block after a first transaction has already written an `index-cache` entry for that `aid`/timestamp, and (2) a second transaction's `collateral-add`/`borrow`/`liquidate` call reaches `get-notional-evaluation` for that zToken without itself calling `accrue-and-cache` for it beforehand (relying on the stale same-block cache entry from step 1). This would need to be verified experimentally against the actual test suite (e.g. `local-testing/tests/flows/collateral/collateral-add.test.ts`, `local-testing/tests/flows/liquidation/liquidation-basic.test.ts`) since the index cache key is `{timestamp, aid}` and Clarity's `stacks-block-time` is constant across all transactions in the same block, which is exactly the scenario needed to trigger the coincidental-staleness described above. I was not able to execute this against a live Clarinet instance from this context, so the PoC sequence above is a specification for a background Devin session to implement and confirm rather than a verified trace.
