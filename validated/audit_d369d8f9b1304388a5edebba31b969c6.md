## Analysis

**Binding claimed broken:** `ChunkAccessor::<S>::get(wtxid)` bytes == bytes the batch prover originally chunked for that same `wtxid`, where `wtxid = blob.wtxid()` is the actual Bitcoin `compute_wtxid()` of the DA reveal transaction carrying the `DataOnDa::Chunk` payload.

**Trace:**

In `run_l1_block`, chunk handling is intentionally unauthenticated: [1](#0-0) 
This stores `chunk` keyed by `blob.wtxid()` via `ChunkAccessor::<S>::insert`: [2](#0-1) 

The only way a chunk is later consumed is if a `DataOnDa::Aggregate(_, wtxids)` blob, signed and sent by the actual `batch_prover_da_public_key`, references that exact wtxid: [3](#0-2) 

For the attack to work, the attacker would need `blob.wtxid()` of their forged chunk transaction to be bit-for-bit identical to the `wtxid` of a chunk transaction the honest batch prover has broadcast (or will broadcast) and later references in a signed `Aggregate`. `wtxid = compute_wtxid()` is Bitcoin's SHA256d-based witness transaction hash, which commits to the entire serialized transaction, including its witness/script data carrying `borsh(DataOnDa::Chunk(body))`. This is confirmed in the DA service where wtxid is computed straight from the actual chunk transaction: [4](#0-3) , and the aggregate references the batch prover's own previously-computed chunk `wtxid`s: [5](#0-4) .

For the attacker's forged `DataOnDa::Chunk(attacker_bytes)` to occupy the same storage slot (`wtxid`) as the batch prover's genuine chunk, they must produce a distinct transaction whose `compute_wtxid()` collides with the honest prover's transaction wtxid — i.e., a first- or second-preimage/collision against SHA256d over the full transaction serialization (including the prover's own signature/witness data they do not control). This is not achievable by an unprivileged attacker without breaking the hash function, which is explicitly out of scope (no key compromise, no hash collision assumption, no majority hashrate). The "no check exists" for `blob.sender()` on `Chunk` is a deliberate design choice documented in code and docs — safety is derived from content-addressing by `wtxid`, not from sender authentication: [6](#0-5) .

Both sides of the equality remain equal before and after: an attacker's `DataOnDa::Chunk` blob always lands under **its own** wtxid, never under the wtxid of a distinct, honestly-broadcast transaction, because wtxid is a cryptographic commitment to the full transaction bytes. No demonstrable `cargo test` can construct two distinct transactions sharing an identical wtxid without breaking SHA256d.
