## Analysis

The TRST-H-3 pattern (attacker donates a negligible token amount to keep re-triggering an automated, gas-costing action against a victim who never consented and cannot opt out) has a direct analog in Push Chain's `isCEA` inbound-execution path.

### Root cause

For `isCEA` inbounds, the `Recipient` is an attacker-chosen address on Push Chain and there is no signature/authorization check comparable to the UEA's `executeUniversalTx` owner-signature verification — the contract itself is trusted to gate the call. When the recipient resolves to a deployed (non-UEA) smart contract, Push Chain unconditionally calls `executeUniversalTx` on it and, if that call does not revert, deducts a real `upc` gas fee from the *recipient contract's own account balance* via `DeductGasFeesFromReceipt`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The trigger for this whole flow is an inbound event on an *external* chain — something a completely unprivileged attacker can create cheaply and repeatedly (a dust-value transfer to the target's Push-Chain address, wrapped as `FUNDS_AND_PAYLOAD` or `GAS_AND_PAYLOAD` with `isCEA=true`). Honest Universal Validators will faithfully observe and vote this real event in (no malicious-validator assumption needed): [5](#0-4) 

There is no dust/minimum-amount threshold gating this path (confirmed — no `DUST`/`MinAmount` guard exists anywhere in the module), and the amount can even be zero as long as `IsCEA` is true and the recipient resolves to a contract: [6](#0-5) 

Each such inbound is processed and voted independently — nothing tracks or throttles repeated inbounds targeting the same CEA recipient, so the attacker can force unlimited repeated `executeUniversalTx` calls, each burning real gas from the victim contract's `upc` balance, as long as the target's `executeUniversalTx` does not revert on the attacker-controlled/no-op payload.

### Title
Unauthenticated, repeatable dust-value `isCEA` inbounds let an attacker drain a smart-contract recipient's `upc` gas balance over time - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/fees.go`)

### Summary
`isCEA` inbounds route to arbitrary attacker-chosen smart-contract recipients without any owner-signature check (unlike the UEA path) and without any minimum-amount/dust threshold. As long as the target's `executeUniversalTx` does not revert on the call, `DeductGasFeesFromReceipt` unconditionally deducts real `upc` gas fees from the recipient contract's own balance. Since the triggering inbound only requires a cheap dust-value transaction on an external chain, an attacker can repeat this indefinitely to drain a CEA-integrated contract's `upc` balance — the same "attacker donates a negligible amount to keep making the victim pay gas" pattern as TRST-H-3.

### Finding Description
1. An attacker sends a dust-value (or zero-value) transfer on any supported external chain, targeting a Push-Chain smart contract address as `Recipient`, with `TxType = FUNDS_AND_PAYLOAD` or `GAS_AND_PAYLOAD` and `IsCEA = true`.
2. Honest UVs faithfully observe and vote this genuine on-chain event; once quorum is reached, `ExecuteInboundFundsAndPayload` / `ExecuteInboundGasAndPayload` resolves the recipient, finds it is a deployed non-UEA contract (`isSmartContract = true`), and calls `CallExecuteUniversalTx` on it: [7](#0-6) 
3. If the contract's `executeUniversalTx` implementation does not revert on this attacker-influenced/no-op call, `DeductGasFeesFromReceipt` deducts and burns `upc` from the recipient's own account: [8](#0-7) 
4. Nothing enforces a minimum bridged amount, a per-recipient rate limit, or victim opt-in/consent before this repeated charge is applied — the contract owner cannot prevent being targeted.
5. Because the source-chain leg only costs the attacker a cheap dust transfer, they can force this cycle indefinitely, draining the recipient's `upc` balance over time while paying comparatively little themselves — the same asymmetric "donate dust, drain victim's gas balance" economics as the reported DCA bug.

### Impact Explanation
Any smart contract integrated as a Push Chain `isCEA` recipient can have its native `upc` balance drained by an unprivileged external attacker through repeated, cheap, dust-value cross-chain triggers, with each cycle producing a real, unconsented gas charge against the victim contract. This is a direct fund-drain/griefing impact against protocol/user-controlled funds reachable purely through ordinary unprivileged external-chain transactions and honest-validator voting, matching the in-scope "unauthorized module-originated EVM execution" / "corruption of gas fee accounting" categories.

### Likelihood Explanation
High feasibility: the attacker needs no special access — only the ability to send a dust transaction on any supported external chain to a known contract address, repeated at will. No malicious validator or privileged actor is required; honest UV consensus faithfully forwards the observation.

### Recommendation
Introduce a minimum bridged-amount/dust threshold below which `isCEA`-routed `executeUniversalTx` calls are not automatically triggered (mirroring the reported mitigation's `DUST_AMOUNT` gate), and/or require the CEA recipient to opt in to per-caller/per-amount execution policies, and/or rate-limit automatic gas-charging calls per recipient within a time window so a victim contract cannot be forced to pay for an unbounded number of attacker-triggered executions funded by negligible external-chain transfers.

### Proof of Concept
1. Deploy (or identify) a Push Chain smart contract that is registered/reachable as an `isCEA` recipient and holds `upc` for gas.
2. From an external chain, send a dust-value transfer (or zero-value payload-only transfer) to that contract's Push Chain address with a benign/no-op payload, submitted as a `FUNDS_AND_PAYLOAD` (or `GAS_AND_PAYLOAD`) bridge event.
3. Wait for honest UVs to reach quorum on `MsgVoteInbound`; observe `ExecuteInboundFundsAndPayload` invoke `CallExecuteUniversalTx` then `DeductGasFeesFromReceipt`, burning `upc` from the recipient.
4. Repeat step 2 indefinitely at low cost; observe the recipient contract's `upc` balance steadily decreasing with no way to opt out.

```go
// DeductGasFeesFromReceipt calculates and deducts gas fees from a recipient address
// based on the EVM receipt and universal payload parameters.
// Returns nil if receipt is nil (Go-level error, no EVM tx was created).
// Returns error with gas details if deduction fails (insufficient balance, etc).
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}

	k.Logger().Debug("gas fees deducted",
		"recipient", recipient.Hex(),
		"gas_used", receipt.GasUsed,
		"gas_cost", gasCost.String(),
	)
	return nil
```

```markdown
### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```
