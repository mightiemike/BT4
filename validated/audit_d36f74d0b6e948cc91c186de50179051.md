### Title
Truncating base-fee-to-upc conversion in `CalculateGasCost` systematically undercharges gas fees for `ExecutePayload` execution - (File: x/uexecutor/keeper/fees.go)

### Summary
`Keeper.CalculateGasCost` in `x/uexecutor/keeper/fees.go` converts the `feemarket` module's `baseFee` (an 18-decimal `sdkmath.LegacyDec`) to a whole-`upc` integer by doing a raw `big.Int` division by `1e18` **before** multiplying by `gasUsed`. This always truncates towards zero, discarding any sub-1-`upc` fractional price-per-gas-unit, and that discarded fraction is then effectively multiplied by (lost for) every unit of `gasUsed` in the transaction. This is the same class of bug as the GMX `getFundingAmountPerSizeDelta()` finding: a division/rounding operation is applied in a fixed, unconditional direction at the wrong point in the calculation (before scaling by a large multiplier) instead of after, amplifying what looks like negligible precision loss into a value proportional to `gasUsed`.

### Finding Description [1](#0-0) 

```go
func (k Keeper) CalculateGasCost(
	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,
	gasUsed uint64,
) (*big.Int, error) {
	baseFeeBig := baseFee.BigInt()
	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18
	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```

The in-line comment asserts `baseFee` is always an exact multiple of `1e18` (i.e. a whole `upc` amount) so the division is "safe." This assumption does not hold: `baseFee` is a standard `cosmos/evm` `feemarket` EIP-1559-style parameter (`sdkmath.LegacyDec`) that is adjusted every block by a percentage-based formula (e.g. multiplying/dividing by `(1 ± gasUsed/gasTarget/denominator)`), which routinely produces non-integer `LegacyDec` values. `Keeper.DeductGasFeesFromReceipt` reads this live value straight from `k.feemarketKeeper.GetBaseFee(sdkCtx)` [2](#0-1)  and passes it into `CalculateGasCost`, so any fractional component of the per-block base fee is silently floored to the nearest whole `upc` **before** the effective price is multiplied by `gasUsed`: [3](#0-2) 

Because the truncation happens on the *price-per-gas-unit* term rather than on the final total, the lost fraction (up to just under 1 `upc`) is effectively multiplied by `gasUsed`, which can be in the tens of millions for `MsgExecutePayload` calls (the codebase's own test fixtures use `GasLimit: "21000000"`). This mirrors the GMX defect exactly: a rounding operation applied at the wrong step of the formula (dividing/truncating before scaling instead of after) turns what looks like sub-unit precision loss into a value proportional to a large multiplier, and it happens unconditionally in one direction (always down, favoring the payer) rather than depending on context.

### Impact Explanation
`DeductGasFeesFromReceipt` is invoked from the unprivileged `MsgExecutePayload` / inbound execution flow (`x/uexecutor/keeper/execute_payload.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`) to burn the recipient's `upc` balance for gas consumed by `DerivedEVMCall`-routed universal execution. Every such execution undercharges the protocol-designated gas fee by `frac(baseFee) * gasUsed` upc, where `frac(baseFee)` is the discarded fractional part of the per-block base fee (up to ~1 upc). Since this occurs on every payload execution, for every user, and the discarded amount scales with `gasUsed` (which is attacker-controlled up to the payload's gas limit), this is a systematic, protocol-wide undercollection of gas fees — i.e., permanent loss of protocol-controlled fee revenue — that grows block over block as `baseFee` fluctuates fractionally under normal EIP-1559 adjustment. This matches the "material amount of funds can be lost" impact bar from the analog report.

### Likelihood Explanation
This is triggered by ordinary, unprivileged use of `MsgExecutePayload` — no privileged actor or malicious validator assumption is required. It happens automatically whenever the `feemarket` base fee is not an exact multiple of `1e18` at the block in which a payload executes, which is the expected steady-state behavior of a live EIP-1559 fee market (only genesis/test configurations that pin `base_fee` to a round integer value avoid it). Any user who executes payloads while base fee is fractional deterministically underpays.

### Recommendation
Compute the gas cost using the full-precision `LegacyDec` (or an equivalent high-precision integer representation) and multiply by `gasUsed` before rounding to the smallest `upc` unit, rounding up (ceiling) rather than down so the protocol/burn side is never shortchanged — analogous to correcting the GMX bug by moving the rounding mode to the final division instead of an intermediate divisor:

```go
gasCostDec := baseFee.MulInt64(int64(gasUsed))   // full precision, still in "atto-upc" units internally
gasCost := gasCostDec.Ceil().TruncateInt().BigInt()
```
or equivalently perform the multiplication in `big.Int` space at 18-decimal precision and only divide by `1e18` (rounding up) after multiplying by `gasUsed`.

### Proof of Concept
1. Set `feemarket` base fee to a fractional-`upc` value, e.g. `baseFee = 1_500_000_000_000_000_000 + 500_000_000_000_000_000` (i.e., `1.5` upc, `LegacyDec` raw value `1.5e18`).
2. Call `CalculateGasCost(baseFee, maxFeePerGas>=2, maxPriorityFeePerGas, gasUsed=21_000_000)`.
3. Correct expected cost (round up per-unit price to preserve funds): `ceil(1.5) * 21_000_000 = 2 * 21_000_000 = 42_000_000` upc (or, if instead computed as `1.5 * 21_000_000 = 31_500_000` exactly with rounding only at the very end, `31_500_000`).
4. Actual code path: `baseFeeBig.Div(1.5e18, 1e18) = 1` (integer truncation) → `gasCost = 1 * 21_000_000 = 21_000_000` upc.
5. Depending on which "correct" baseline is used, the shortfall is between `10,500,000` and `21,000,000` upc versus what should have been burned — for a single `ExecutePayload` call — demonstrating the truncate-before-multiply rounding error amplifies with `gasUsed`, exactly as in the GMX analog.
