## Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hashes during replay-verify, allowing a divergent state root to be accepted as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by chunk-executor replay-verify (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) and by CLI/debugger replay tooling (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger`) to confirm that locally re-executed VM output matches the trusted, previously-committed `TransactionInfo`. The check validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but — per an explicit code comment — it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, the fields that actually authenticate the resulting global state (JMT) root.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks:
- `status()` vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

It explicitly does **not** check the checkpoint hashes, and this is called out in the source itself: [2](#0-1) 

These skipped fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are exactly the fields that bind a `TransactionInfo` to the authenticated global state tree root, hot-state root, and native "position" state root — see the `TransactionInfoV1` builder fields [3](#0-2) .

This function is used as the sole correctness gate in the chunk-executor's `verify_execution`, which re-executes a batch of transactions against locally-derived state and compares the result to `transaction_infos` supplied externally (e.g., from a backup or state-sync source): [4](#0-3) 

Because the comparison omits the state/hot-state/position checkpoint hashes, a re-execution that produces the correct write set and events, but that ultimately gets applied to (or was derived from) a divergent state tree — e.g. due to a state-merkle corruption bug, an incorrect restore/reindex, or a manipulated input `TransactionInfo` list carrying a wrong `state_checkpoint_hash` for otherwise-matching write sets — would still be reported as a successful, matching replay by this tool.

### Impact Explanation
This breaks the "proof-binding" invariant explicitly called out in scope: authenticated ledger data (proof-bearing `TransactionInfo`) must stay bound to the correct state root, and replay/restore verification paths must not silently reinterpret or accept a wrong committed state. If the actual JMT state root (or hot-state/position root) diverges from what is really committed on-chain while write-set/event/gas/status all match, replay-verify tooling built on `ensure_match_transaction_info` (chunk-executor `verify_execution`, `db-tool replay-verify`, CLI/debugger transaction replay) will falsely report success, masking a real state-commitment divergence. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category, since it is exactly the class of bug that would let a corrupted state root pass automated verification undetected.

### Likelihood Explanation
This is a narrow, tooling-and-verification-only gap rather than a live consensus-path bug: the state-checkpoint hash for actual node commit is independently computed and appended into the transaction accumulator in the normal execution pipeline (`DoLedgerUpdate::run`, `DoStateCheckpoint`), so a normal validator/full-node commit path is not immediately affected by this particular comparator. The exposure is specifically in the verification tooling that relies on `ensure_match_transaction_info` as an integrity oracle (replay-verify, CLI/debugger transaction replay, `TransactionReplayer`). Likelihood of a triggering divergence (e.g., a state-merkle computation bug that preserves write-set/event hashes but flips the resulting root) is low-to-moderate but plausible given the code comment acknowledging the gap as a known, intentional limitation pending a TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS").

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check invoked wherever it's used for verification, e.g., `verify_execution` in `execution/executor/src/chunk_executor/mod.rs`) to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally computed state/hot-state/position roots whenever those values are available in the supplied `TransactionInfo`, rather than deferring this to a future feature flag.

### Proof of Concept
I could not construct/verify a concrete triggering scenario (e.g., a specific state-merkle bug or a replay-verify code path that never separately checks the state root) within the exploration performed, because full confirmation would require confirming that no other call site independently re-verifies the state/hot-state/position checkpoint hash before or after `ensure_match_transaction_info` is invoked in each of its callers (`chunk_executor::verify_execution`, CLI replay, debugger replay). This is a documented gap in the local code (the comment at [2](#0-1)  is explicit about it), but without tracing every caller path exhaustively I cannot fully rule out that state-root verification is enforced redundantly elsewhere for all uses. I recommend a Devin session with full repo/test access to (1) enumerate every caller of `ensure_match_transaction_info`, (2) confirm whether any of them independently validate `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, and (3) construct a reproducing test (e.g., feeding `verify_execution` a `TransactionInfo` with correct write-set/event/gas/status but a tampered `state_checkpoint_hash`) to confirm the false-positive "match" is actually reachable end-to-end.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
