## Analysis

Let me trace the full code path before rendering a verdict.

**Step 1 — The truncation in `from_input`** [1](#0-0) 

`extension.len() as u16` is an unchecked narrowing cast. Any extension slice whose length exceeds 65535 bytes silently wraps to a smaller value (e.g., 65536 → 0, 65537 → 1, etc.).

**Step 2 — The undersized arena allocation** [2](#0-1) [3](#0-2) 

Both `Leaf` and `Extension` node encoding call `EncodedExtensionHeader::from_input(extension)`, then allocate exactly `extension_header.flexible_data_length()` bytes — the truncated value — for the flexible region.

**Step 3 — The panic in `encode_flexible_data`** [4](#0-3) 

`copy_from_slice` requires source and destination to have **equal** lengths. The target slice is sized by the truncated `u16` length; the source is the full extension. This is an unconditional panic for any extension > 65535 bytes.

The `encode_flexible` caller in `RawEncoder` passes a subslice of exactly `header.flexible_data_length()` bytes: [5](#0-4) 

**Step 4 — Can an attacker reach this with a storage key?**

The nibble-encoded extension for a trie leaf/extension node is approximately `(trie_key_len / 2) + 1` bytes. For the extension to exceed 65535 bytes, the trie key must be ≥ ~131,070 bytes. The trie key for a `storage_write` is `account_id + key_type_byte + storage_key`, so the storage key alone needs to be ~128 KB.

Several protocol version configurations allow `max_length_storage_key` up to **4,194,304 bytes** (4 MB): [6](#0-5) 

The `storage_write` host function enforces this limit: [7](#0-6) 

A 128 KB storage key is well within the 4 MB limit, so the check passes and the key reaches the memtrie update path.

**Step 5 — Impact**

The panic occurs inside the memtrie node encoding during state transition. This crashes the node (or, if caught by a `catch_unwind` boundary, causes the block to fail to apply on every node that processes it). Because all honest nodes process the same transaction, the crash is deterministic and network-wide — a single crafted transaction halts the chain.

**Step 6 — Mitigating factors / guards**

There is **no guard** in `from_input` that checks `extension.len() <= u16::MAX`. The only upstream limit is `max_length_storage_key`, which at 4 MB is far above the 65535-byte threshold. Protocol version 66 snapshots show a 2 KB limit, which would prevent the attack for that version, but the vulnerability exists for all versions with a larger limit.

### Title
Silent u16 Truncation in `EncodedExtensionHeader::from_input` Causes Unconditional Node Panic on Large Storage Keys — (`core/store/src/trie/mem/flexible_data/extension.rs`)

### Summary
`EncodedExtensionHeader::from_input` casts `extension.len()` to `u16` without bounds checking. When a contract writes a storage key large enough to produce a nibble-encoded trie extension exceeding 65535 bytes, the stored length is silently truncated. The subsequent `encode_flexible_data` call panics unconditionally because `copy_from_slice` requires equal-length slices. Since all nodes process the same transaction, the panic is deterministic and crashes every node applying that block.

### Finding Description
In `extension.rs`, `from_input` stores the extension length as a `u16`:

```rust
fn from_input(extension: &[u8]) -> EncodedExtensionHeader {
    EncodedExtensionHeader { length: extension.len() as u16 }  // silent truncation
}
```

`flexible_data_length()` returns the truncated value, which is used to allocate the arena region. `encode_flexible_data` then calls:

```rust
target.raw_slice_mut().copy_from_slice(&extension);
```

where `target` has the truncated length and `extension` has the true length. Rust's `copy_from_slice` panics on length mismatch.

### Impact Explanation
Any node applying a block containing the malicious transaction panics during memtrie state transition. This is a deterministic, single-transaction network halt. No funds are directly stolen, but the chain is rendered inoperable until a patched binary is deployed.

### Likelihood Explanation
The attack requires only a deployed contract that calls `storage_write` with a key of ~128 KB or larger. This is a normal, unprivileged user action. The gas cost is non-trivial but affordable. The `max_length_storage_key` limit of 4 MB provides no protection against this specific threshold.

### Recommendation
Add an explicit bounds check in `from_input`:

```rust
fn from_input(extension: &[u8]) -> EncodedExtensionHeader {
    assert!(
        extension.len() <= u16::MAX as usize,
        "extension length {} exceeds u16::MAX", extension.len()
    );
    EncodedExtensionHeader { length: extension.len() as u16 }
}
```

Or, preferably, widen the `length` field to `u32` and update `flexible_data_length` accordingly. Additionally, enforce that the trie key length cannot produce an extension exceeding `u16::MAX` bytes at the protocol parameter level.

### Proof of Concept
1. Deploy a contract on a network with `max_length_storage_key ≥ 131,072`.
2. Have the contract call `env::storage_write` with a key of exactly 131,072 bytes (any value).
3. Submit the transaction. Every node applying the resulting chunk will panic in `EncodedExtensionHeader::encode_flexible_data` → `copy_from_slice` length mismatch, crashing the node process. [8](#0-7) [9](#0-8)
