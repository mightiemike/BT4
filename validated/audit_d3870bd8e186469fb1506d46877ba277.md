### Title
Unauthenticated state values committed during backup restore's KV-only phase can permanently corrupt `state_kv_db` without proof verification - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
The restore flow used to fast-bootstrap a node from a backup splits state-snapshot restoration into two independently-fetched phases: a `StateSnapshotRestoreMode::KvOnly` phase (raw KV values, from `kv_snapshot.manifest`) and a `StateSnapshotRestoreMode::TreeOnly` phase (leaf key/value hashes, from `tree_snapshot.manifest`), driven by `storage/backup/backup-cli/src/coordinators/restore.rs`. The `KvOnly` branch of `StateSnapshotRestore::add_chunk` writes the downloaded `(key, value)` pairs straight to `state_kv_db` while discarding the `SparseMerkleRangeProof` argument entirely — no cryptographic check ties these bytes to the trusted root hash before they land in durable storage.

### Finding Description
`StateSnapshotRestore::add_chunk` (`storage/aptosdb/src/state_restore/mod.rs:213-253`) dispatches on `self.restore_mode`: [1](#0-0) 

For `StateSnapshotRestoreMode::KvOnly` it calls only `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;` — the `proof: SparseMerkleRangeProof` parameter is never consulted. Contrast this with the `Default` mode, whose own inline comment states the intended invariant: *"verify proof -> write state_kv_db -> write state_merkle_db"*. `KvOnly` skips the verify step altogether.

This mode is exercised on the hot path in `storage/backup/backup-cli/src/coordinators/restore.rs:236-260` ("phase 1.a"): the coordinator selects a `kv_snapshot` (potentially a *different* backup manifest/version than the later `tree_snapshot`, since they are chosen independently — see lines 157-196) and restores it via `StateSnapshotRestoreController` with `restore_mode: StateSnapshotRestoreMode::KvOnly`. In `StateSnapshotRestoreController::run_impl` (`storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs:201-215`), the proof is downloaded (`storage.load_bcs_file(&chunk.proof)`) and passed into `receiver.add_chunk(blobs, proof)`, but for `KvOnly` receivers that proof is silently dropped as shown above — the raw `blobs` (attacker-/corruption-controlled if backup storage is compromised, or simply susceptible to disk/transfer bit-rot) are committed to `state_kv_db` unauthenticated.

Later, "phase 2" performs a `TreeOnly` restore against `tree_snapshot.manifest`, which validates a **separate** set of downloaded key/value-hash blobs (`storage/aptosdb/src/state_restore/mod.rs:219-226`, using `JellyfishMerkleRestore::verify_chunk`) against the trusted root hash from `TransactionInfoWithProof`. This verification only proves that *that manifest's* `(key_hash, value_hash)` pairs are included in the Merkle tree at `tree_snapshot.version` — it does not, and structurally cannot, re-validate the raw values already persisted to `state_kv_db` from the independent, unverified `kv_snapshot.manifest` download in phase 1. Because Sparse Merkle leaves store `hash(value)` rather than the raw value, nothing during or after restore ever recomputes and compares `hash(state_kv_db value)` against the tree leaf for the corresponding key at the version actually served by the KV store.

Net effect: after a complete phase-1+phase-2 restore, `state_kv_db` (the authoritative source for future transaction execution's state reads, `get_state_value`, and authenticated REST/API state responses) can contain a value for a given key/version that has never been checked against the proof-bearing root hash the node trusted (`txn_info_with_proof.verify(...)` in `restore.rs:127`), while the JMT built in phase 2 still reports the "expected" root hash from that same trusted `LedgerInfoWithSignatures`. The node's state view and its own Merkle root become mutually inconsistent, silently.

### Impact Explanation
This breaks the core proof/storage-pivot invariant explicitly called out in the task: "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "must preserve deterministic proof binding." A single corrupted or malicious backup blob (or storage-layer bit flip) delivered only to the KV manifest chunk can result in a node persisting a wrong balance/resource/module value that is never checked against any accepted proof, yet the node still believes (via the separately-verified tree) that its state matches the canonical root. This can propagate to execution (wrong VM inputs), to authenticated API responses (serving unproven data as if state-proven), and to any subsequent full-node/validator using this restored DB as its ground truth — a durable ledger-data corruption. This qualifies as a High/Critical state-commitment integrity issue per the gate's criteria ("Committed state that differs from the correct VM result or corrupts durable ledger data").

### Likelihood Explanation
Reaching `KvOnly` mode requires operating the backup-cli fast-restore coordinator path (`RestoreCoordinatorOpt`/`run_impl` in `coordinators/restore.rs`), which is a standard, commonly used way to bootstrap new full nodes/validators from an official or third-party backup store (`BackupStorage` trait, potentially S3/GCS or another network location, not necessarily controlled by the node operator). Any compromise or corruption of that storage medium — which is explicitly outside validator-privilege trust and not "malicious peer/node behavior" in the consensus sense — is sufficient; no cryptographic break is needed since the verification step is simply absent for this code path. This is a realistic, unprivileged trigger for anyone standing up a node from backups, which is routine operational practice.

### Recommendation
Do not allow raw state-value bytes to be written to `state_kv_db` without verifying them against the Sparse Merkle range proof for that chunk, even in `KvOnly` mode. Either (a) require `KvOnly` restore to still call `verify_chunk`-equivalent hash verification against a root hash supplied to the receiver (rather than silently trusting the KV manifest), or (b) after phase-1/phase-2 restore completes, add a full-state reconciliation pass that recomputes `hash(value)` for every key in `state_kv_db` at the target version and checks it against the corresponding JMT leaf established at that version, failing loudly (and refusing to mark the DB "restored") on any mismatch.

    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())
    }
