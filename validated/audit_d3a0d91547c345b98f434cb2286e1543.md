### Title
Unvalidated `DestExecData` length causes panic in `binary.BigEndian.Uint32` - ([File: core/capabilities/ccip/ccipsolana/extradatacodec.go])

### Summary
`ExtraDataDecoder.DecodeDestExecDataToMap` calls `binary.BigEndian.Uint32(destExecData)` on the raw `RampTokenAmount.DestExecData` field without checking that it is at least 4 bytes long, unlike the sibling function `DecodeExtraArgsToMap` which does enforce a `len(extraArgs) < 4` check. `binary.BigEndian.Uint32` panics with a slice-bounds-out-of-range error if given fewer than 4 bytes, and no `recover()` exists anywhere in the CCIP capability call path to contain this panic.

### Finding Description
`DecodeDestExecDataToMap` is: [1](#0-0) 

It is reached via `ExtraDataCodecRegistry.DecodeTokenAmountDestExecData` → per-chain-family codec: [2](#0-1) 

Callers that pass attacker-influenced `RampTokenAmount.DestExecData` bytes directly, with no prior length validation, include:
- `MessageHasherV1.Hash`, which loops over `msg.TokenAmounts` and calls `h.extraDataCodec.DecodeTokenAmountDestExecData(ta.DestExecData, ...)`: [3](#0-2) 
- `ExecutePluginCodecV1.Encode`, which calls the same decode on `tokenAmount.DestExecData` while building the execution report: [4](#0-3) 
- `EstimateProvider.CalculateMessageMaxGasWithError`, which iterates `msg.TokenAmounts` and calls the decode for gas estimation: [5](#0-4) 

`RampTokenAmount.DestExecData` is a variable-length byte field populated from cross-chain message content originating on the source chain (e.g. set by whatever party constructs/sends the CCIP message on the source chain, which for CCIP is generally permissionless — anyone can initiate a `ccipSend`-style message with attacker-chosen `DestExecData`). None of the three call sites, nor `extractDestGasAmountFromMap`, nor the registry layer perform a length check before invoking the codec. The only place that models an analogous length guard is `DecodeExtraArgsToMap` (line 37: `if len(extraArgs) < 4`), confirming this check was simply omitted for `DecodeDestExecDataToMap`. There is no `recover()` in the `core/capabilities/ccip` package, so a panic here is unhandled at this layer.

### Impact Explanation
An attacker who can get a CCIP message accepted from a Solana-family source chain (or any chain routed through this codec) with a `TokenAmounts[].DestExecData` field shorter than 4 bytes can cause a runtime panic anywhere `MessageHasherV1.Hash`, `ExecutePluginCodecV1.Encode`, or `EstimateProvider.CalculateMessageMaxGas(WithError)` is invoked on that message — i.e., during OCR message hashing, execute-plugin report encoding, and gas estimation. This is a repeatable denial-of-service against the affected node's CCIP plugin processing for that lane. The severity depends on whether an upstream caller (e.g., the OCR3 plugin runner or gas estimation flow) recovers panics at a higher level; within the `ccipsolana`/`ccip` packages themselves there is no recovery, so if the outer caller also lacks a recover, this can crash the plugin goroutine/process repeatedly for every affected message.

### Likelihood Explanation
Feasibility is high in principle: the precondition is only that an attacker can influence `DestExecData` on a source-chain-originated message with fewer than 4 bytes, which is a pure data-crafting exercise on the source chain side (no privileged keys or node compromise required). Whether this is fully "unprivileged and externally reachable end-to-end" depends on constraints imposed by the on-chain source contract/onramp encoding rules for `DestExecData` that are outside this repo (i.e., whether the source chain program enforces the field to always be ≥4 bytes before it is relayed) — this repo-level analysis cannot confirm or rule out such upstream validation, since it lives in on-chain program code, not in the Go relayer/plugin code reviewed here.

### Recommendation
Add a length guard mirroring `DecodeExtraArgsToMap`:
```go
func (d ExtraDataDecoder) DecodeDestExecDataToMap(destExecData cciptypes.Bytes) (map[string]any, error) {
	if len(destExecData) < 4 {
		return nil, fmt.Errorf("dest exec data too short: %d, should be at least 4 bytes", len(destExecData))
	}
	return map[string]any{
		svmDestExecDataKey: binary.BigEndian.Uint32(destExecData),
	}, nil
}
```

### Proof of Concept
Unit test in `core/capabilities/ccip/ccipsolana/extradatacodec_test.go`:
```go
func TestDecodeDestExecDataToMap_ShortInput(t *testing.T) {
	d := ExtraDataDecoder{}
	for _, n := range []int{0, 1, 2, 3} {
		data := make(cciptypes.Bytes, n)
		func() {
			defer func() {
				if r := recover(); r != nil {
					t.Fatalf("panic for length %d: %v", n, r)
				}
			}()
			_, err := d.DecodeDestExecDataToMap(data)
			require.Error(t, err, "expected graceful error for length %d, got none", n)
		}()
	}
}
```
Expected current behavior: the test panics (slice bounds out of range) for lengths 0–3, demonstrating the vulnerability; after the fix, it should return a non-nil error without panicking.
