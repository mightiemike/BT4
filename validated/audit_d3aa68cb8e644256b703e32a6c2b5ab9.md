### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify tooling accept a divergent state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the chunk-executor's replay/verify path (`verify_execution` in `execution/executor/src/chunk_executor/mod.rs`) and by `aptos-debugger`/`aptos-move/cli` to confirm that a locally re-executed transaction reproduces the exact result recorded on-chain. The function checks status, gas, write-set hash, and event-root hash, but a code comment explicitly documents that it does not check the state/hot-state checkpoint hash or `position_state_checkpoint_hash`, even though these are part of `TransactionInfo` and are included in what gets hashed into the transaction accumulator.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  validates:
- `status()` vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `write_set_hash` (hash of `self.write_set()`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It explicitly does **not** validate the state-checkpoint hash(es), and says so directly: [2](#0-1) 

This function is the sole correctness oracle used by `ChunkExecutor::verify_execution`, which re-executes a chunk of historical transactions through the VM and is expected to catch any divergence between the recorded `TransactionInfo` (and its checkpoint hashes) and what local re-execution actually produces: [3](#0-2) 

Because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared here, a discrepancy between the locally-computed state Merkle root (or hot-state/position-state root, gated by the `compute_trading_native_state_roots` on-chain config) and the historically committed root will not be flagged as an error by this check, even though those fields are part of `TransactionInfo` which is hashed and bound into the transaction accumulator that ledger info ultimately commits to.

### Impact Explanation
This breaks the "replay must reproduce the exact committed ledger state" invariant for one specific consumer: replay-verification tooling (`db-tool replay-verify`, `aptos-debugger`, and the CLI's replay path) that is relied upon to detect state-computation divergences (e.g. non-determinism bugs, JMT/hot-state computation bugs, or bugs requiring a hard fork) across historical chain data. If the executor's state-root computation silently diverges from the historically-recorded value at some version, `ensure_match_transaction_info` will report success anyway, because it only checks write-set/event hashes and status/gas — not the checkpoint hash that actually encodes the state root. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" bucket in the prompt's scope: a real state-root computation bug could pass replay-verification undetected, delaying or preventing detection of a consensus-breaking divergence.

Note the limiting factor: this does **not** corrupt any state actually committed to a live mainnet ledger by itself — the transaction accumulator root and `LedgerInfo` signatures used for consensus are computed independently and still bind the correct `state_checkpoint_hash` via `TransactionInfo::hash()`. The gap is specifically in the *offline verification tool's* blind spot, not in the on-chain accumulator/proof-verification path itself (`AccumulatorProof::verify`, `TransactionInfoWithProof::verify`, etc., which I confirmed do use the full `TransactionInfo` hash and therefore transitively include the checkpoint hash) [4](#0-3) .

### Likelihood Explanation
Low-to-moderate likelihood of independent exploitation by an unprivileged actor — this is not attacker-triggerable on its own; it is a latent gap that would only matter in conjunction with a separate, currently-unknown state-root computation bug. The code's own comment (`TODO(trading-native)`) acknowledges the gap is real and unresolved, and explicitly warns it must be fixed before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` [2](#0-1) , indicating maintainers are already aware this is incomplete/gated behavior rather than a novel discovery with proven exploitability today.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash()` (and, when `compute_trading_native_state_roots` is enabled, `hot_state_summary`/`position_state_checkpoint_hash`) computed locally against the corresponding fields on `txn_info`, mirroring the existing write-set/event-hash checks, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on for any replay/verify consumer.

### Proof of Concept
Not applicable as a standalone exploit — the finding is a documented, code-level verification gap (not a triggerable attack), confirmed by: [5](#0-4) [3](#0-2) 

---
**Caveat on confidence**: Given the tool-call budget, I was not able to fully trace whether any *consensus-critical* or *state-sync-critical* path (as opposed to purely offline `verify_execution`/`db-tool`/`aptos-debugger` replay tooling) also relies on `ensure_match_transaction_info` for committing state without independently re-deriving/checking the checkpoint hash elsewhere. If such a path exists, the severity would be materially higher (an actual wrong-root-accepted-as-committed scenario rather than a verification-tool blind spot). I could not confirm this within the available budget, so I report this as a bounded, tool-scoped finding rather than a full committed-state-corruption vulnerability.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
