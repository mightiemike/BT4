### Title
Orphaned `ReceivedData`/`PostponedReceipt`/`PromiseYield*` state is never storage-staked and can be permanently stranded, causing unbounded unaccounted trie growth - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`, `core/store/src/genesis/state_applier.rs`)

### Summary
The libde265 CVE is a class of bug where auxiliary metadata (slice headers) gets attached to a container object (the "finished picture") that no longer has an active owner, so the metadata is retained forever because the only cleanup path assumes the owner is still present. The closest reachable analog in nearcore is the receipt-matching subsystem: `ReceivedData`, `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, and `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries are all written into an account's trie subtree keyed by `receiver_id`, but — per the genesis storage accounting code — **none of these record types are ever charged against that account's `storage_usage`** [1](#0-0) . Their entire lifecycle correctness depends on the *paired* cleanup logic in `process_receipt`/`apply_action_receipt`, which only fires if the matching counterpart receipt (Data ↔ postponed Action, or PromiseResume ↔ PromiseYield) actually arrives at that same account. If the account is deleted (`DeleteAccount`) while such entries are outstanding, nothing in the delete path purges `PostponedReceipt*`, `ReceivedData`, or `PromiseYield*` keys for that account, and because those keys were never counted in `storage_usage`, the account-deletion size check (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`) never sees them either. The result: an attacker-controlled account can accumulate outstanding "waiting" receipt state, delete itself, and leave that state permanently orphaned in the trie — never storage-staked, never cleaned, and never chargeable to anyone — exactly mirroring "orphaned slice headers attached to a finished picture with no active image unit."

### Finding Description
Two protocol-level facts combine to create the leak:

1. **These records are explicitly excluded from storage accounting.** The `StorageComputer::process_record` function used to compute account storage size treats `PostponedReceipt` and `ReceivedData` state records as contributing **zero** bytes to any account's `storage_usage`: [2](#0-1) [3](#0-2) 
   The same is true at runtime — `check_storage_stake` only ever examines `account.storage_usage()` [4](#0-3) , and nothing in `process_action_receipt`/`process_receipt` increments `storage_usage` when writing `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, or `ReceivedData` [5](#0-4) [6](#0-5) .

2. **Cleanup is entirely conditional on the pairing partner arriving at the same account.** `process_receipt`'s `Data` arm unconditionally writes `ReceivedData` for `(account_id, data_id)`, and only cleans anything up *if* a matching `PostponedReceiptId` link is already present; otherwise "we do nothing else" and the entry is left in state indefinitely [7](#0-6) . Symmetrically, a `PromiseYield` receipt is simply stored and waits for an explicit `PromiseResume` to remove it [8](#0-7) , with the removal path (`remove_promise_yield_receipt`/`remove_promise_yield_status`) only reachable from the `PromiseResume` arm [9](#0-8) .

Because these entries are keyed by `receiver_id` in the trie (`TrieKey::PostponedReceipt`, `TrieKey::ReceivedData`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldTimeout`) but are not tied to the *existence* of the `Account` object itself, deleting the account via `DeleteAccountAction` does not remove them — there is no code path from `action_delete_account` that walks and purges `PostponedReceipt*`/`ReceivedData`/`PromiseYield*` state for the deleted account, and because these keys carry no storage-usage weight, the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` guard that limits how "big" a deletable account can be never accounts for them and can't block the deletion either. The `PromiseYieldTimeout` queue entry likewise still holds an `account_id`/`data_id` pointing at an account that may no longer exist by the time `resolve_promise_yield_timeouts` processes it [10](#0-9) .

This is structurally identical to the libde265 bug class: metadata (`ReceivedData`/postponed bookkeeping / promise-yield bookkeeping) is attached to a "picture" (an account) that can finish (be deleted) while the metadata has "no active image unit" (no live account) to reclaim it, and the only reclaim path assumes the owner is still there to eventually satisfy the pairing.

### Impact Explanation
Any unprivileged account owner can, at will and repeatedly:
1. Create a promise chain from their own contract that produces an outstanding `PostponedReceipt`/`ReceivedData` pair, or a `promise_yield_create` that produces `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries, targeting their own account.
2. Delete the account (`DeleteAccountAction`) before the counterpart (`Data`/`PromiseResume`) receipt is delivered/consumed.
3. Repeat under a fresh account id (accounts are cheap to create).

Each iteration leaves permanently orphaned trie entries for that (now-nonexistent) `receiver_id` that:
- consume space in the shard's trie/state forever (no TTL, no owner to charge, no mechanism to garbage-collect them since the responsible cleanup code paths are keyed off receiving the matching receipt, which will never come for a deleted account),
- are entirely unpriced by storage staking, so the attacker never pays ongoing rent for this growth, unlike normal account state,
- grow the state that every validator/RPC node must store and serve, increasing the effective state size used in state-sync/state-witness/trie proofs over time.

This is an unbounded, protocol-visible resource-growth (memory/disk) issue reachable purely through ordinary transaction/contract calls, matching the "unbounded heap growth via orphaned headers never freed" bug class in the report. I was not able to fully verify from the indexed code whether any later-added protocol feature (e.g., an account-deletion or promise-yield fix I could not locate in the excerpts available to me) purges these keys on `DeleteAccount`; the `actions.rs::action_delete_account` body itself was not retrievable from the index within my remaining tool budget, so I could not directly confirm the absence of a cleanup call there — this should be verified by reading `runtime/runtime/src/actions.rs` around `action_delete_account` (per the code-anchor table, roughly line 343) in a full checkout.

### Likelihood Explanation
High reachability (any signer/contract can trigger it with ordinary `FunctionCall`/`promise_then`/`promise_yield_create`/`DeleteAccount` actions, no special privilege), but the actual severity depends on per-iteration cost (account creation + tx fees) versus the amount of orphaned bytes each iteration leaves behind, and on whether `DeleteAccount` truly skips cleanup — which I could not fully confirm from the available excerpts.

### Recommendation
- On `action_delete_account`, scan for and remove any outstanding `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`/`ReceivedData`/`PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` entries keyed by the deleted account, or explicitly disallow deletion while such entries exist.
- Alternatively/additionally, incorporate these record types into `storage_usage` accounting so they are storage-staked like any other account data, preventing unbounded free growth and making `MAX_ACCOUNT_DELETION_STORAGE_USAGE` an effective backstop.
- Add a state-invariant check/test asserting that no `PostponedReceipt*`/`ReceivedData`/`PromiseYield*` key can exist for an account that no longer has an `Account` record, and add an integration test that creates a yield/postponed-receipt dependency, deletes the account, and asserts the dependent trie keys are gone.

### Proof of Concept
Not runnable from the index alone (requires a full checkout to confirm `action_delete_account`'s exact behavior and construct account-deletion timing), but the exploit sketch is:
1. Deploy a contract on account `victim.near`.
2. From `victim.near`, call a method that does `promise_then`/`promise_batch_then` (or `promise_yield_create`) creating an outstanding data dependency addressed to `victim.near` itself (`ReceivedData`/`PostponedReceipt` or `PromiseYieldReceipt` state written per `runtime/runtime/src/lib.rs:1662-1709` / `:1549-1553`).
3. In the same or a subsequent transaction, before the counterpart `Data`/`PromiseResume` receipt is delivered, submit `DeleteAccountAction` for `victim.near`.
4. Confirm via state dump / `EXPERIMENTAL_genesis_config`-style inspection that `TrieKey::PostponedReceipt`/`ReceivedData`/`PromiseYieldReceipt` entries under `victim.near` remain in state after the account record itself is gone, and that no future transaction can ever reclaim them.
5. Repeat with many freshly-created accounts to demonstrate unbounded, unpriced state growth.
