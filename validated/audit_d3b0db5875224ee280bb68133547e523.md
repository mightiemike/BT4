### Title
Single-miner VRF-seed grinding via unbound multi-key registration biases sortition winner selection - ([File: stackslib/src/chainstate/burn/sortition.rs])

### Summary
The Entropy.sol report describes providers/users biasing an RNG output because the final value is derived from party-controlled secrets that can be selectively chosen or withheld. Stacks' burnchain sortition has an analogous single-party grinding weakness: the seed that determines the *next* sortition's winner is the `new_seed` field of the *current* round's winning `LeaderBlockCommitOp`, which is simply `VRFSeed::from_proof(vrf_proof)` where `vrf_proof` is computed by the miner's own VRF private key over a fully public message (the current sortition hash). Because `LeaderKeyRegisterOp` places no limit on how many distinct VRF public keys a single miner may register and no binding requiring a specific key be used, a miner can pre-register many VRF keys, compute many candidate `new_seed` values for the same public message, and split burn across multiple self-submitted block-commits (one per candidate seed) to bias which seed becomes the entropy source for the following round if one of their commits wins.

### Finding Description
`BlockSnapshot::select_winning_block` picks the sortition winner using `sample_burn_distribution(dist, vrf_seed, sortition_hash)`, where `vrf_seed` is pulled from the *previous* round's winning commit via `get_last_vrf_seed`: [1](#0-0) 

The index used to select a winner is `sortition_hash.mix_VRF_seed(VRF_seed).to_uint256()`: [2](#0-1) 

The `new_seed` embedded in a miner's block-commit is simply the hash of a VRF proof the miner computes, unilaterally, over the current (fully public) sortition hash: [3](#0-2) 

Because the message being proven over (`burnchain_tip.block_snapshot.sortition_hash`) is public chain state and the VRF private key is entirely miner-controlled, the *value* of `new_seed` a miner produces is not a jointly-generated, unbiased random value — it is a value a single party can select from among as many candidates as they choose to prepare, purely by varying which registered VRF key they use.

`LeaderKeyRegisterOp` checking only rejects a key that is already registered; there is no cap on the number of distinct keys one entity may register, nor any requirement binding a commit to a *specific*, singly-known key at time of use: [4](#0-3) 

`check_common` in block-commit validation only verifies that *some* previously accepted `LeaderKeyRegisterOp` exists at the referenced `(key_block_ptr, key_vtxindex)` — it does not tie the commit's seed to a scarce, unpredictable-at-registration-time source: [5](#0-4) 

This is the direct structural analog of the Entropy.sol bug class: instead of two parties (user/provider) each contributing a secret whose reveal determines the outcome, here a *single* miner effectively plays both "provider" roles by holding many independently valid VRF keys and choosing, via differential burn allocation across multiple commits in the same round, which of several pre-computed seed candidates has the best chance of becoming binding for the next round's sortition — without needing majority hash power or any counterparty collusion.

### Impact Explanation
This lets a minority-stake miner bias the sortition seed that decides the *next* round's winner, i.e., a minority-triggerable divergence in the VRF/sortition process from the intended "one unbiased seed per round" model. It does not directly cause a reward double-payment, but it undermines the fairness guarantee of leader election that all downstream logic (block-reward allocation, tenure assignment) depends on — matching the "High: minority-triggerable sortition/VRF... divergence" impact tier.

### Likelihood Explanation
Likelihood is bounded by needing to actually win at least one round with a chosen candidate commit (probabilistic, weighted by burn amount) — the attacker does not need majority hash power, only patience and capital to register many keys and repeatedly bid with split commits across many burn blocks until a favorable grind succeeds. Registering many VRF keys is cheap (`LeaderKeyRegisterOp` is a low-cost OP_RETURN-style tx) and requires no special privilege.

### Recommendation
- Bind each `LeaderBlockCommitOp`'s VRF proof message to information not fully known at commit-construction time relative to a *specific*, previously-locked-in key (e.g., require the VRF key referenced by a commit to have been registered with a freshness/uniqueness constraint that prevents stockpiling many usable keys per round), or
- Incorporate an additional, harder-to-grind entropy source (e.g., mixing in the *next* burn block's hash, similar to Entropy's optional `blockhash` mode) so that no single miner's chosen VRF key alone determines the propagated seed.
- Document explicitly, as the Entropy report recommends, that the sortition-seed chain assumes a single honest miner per round contributes exactly one seed and does not defend against an entity registering many VRF keys to grind seed selection.

### Proof of Concept
1. Attacker registers `N` distinct VRF keypairs via `N` separate `LeaderKeyRegisterOp`s over time (cheap, no rate limit — see `leader_key_register.rs` checks only rejecting exact duplicate keys).
2. For round `R`, once the canonical `sortition_hash` for round `R` is public, the attacker computes `N` VRF proofs (one per registered key) over that same public message, yielding `N` candidate `new_seed` values (`VRFSeed::from_proof`).
3. Attacker submits multiple `LeaderBlockCommitOp`s in round `R`, each referencing a different one of its `N` registered keys/seeds, allocating more burn to the commit whose seed is more favorable for round `R+1`'s expected outcome (e.g., biasing which of the attacker's own future candidates is likelier to win round `R+1`, or degrading honest miners' win probability).
4. If any attacker commit wins round `R` (probability proportional to burn share, not requiring majority), the seed embedded in that specific commit — one selected from `N` grindable options — becomes the entropy input (`get_last_vrf_seed` → `mix_VRF_seed`) for round `R+1`'s winner selection, per `stackslib/src/chainstate/burn/sortition.rs:155-221`.

    /// Given the weighted burns, VRF seed of the last winner, and sortition hash, pick the next
    /// winner.  Return the index into the distribution *if there is a sample to take*.
    fn sample_burn_distribution(
        dist: &[BurnSamplePoint],
        VRF_seed: &VRFSeed,
        sortition_hash: &SortitionHash,
    ) -> Option<usize> {
        if dist.is_empty() {
            // no winners
            return None;
        }
        if dist.len() == 1 {
            // only one winner
            return Some(0);
        }

        let index = sortition_hash.mix_VRF_seed(VRF_seed).to_uint256();
        for (i, dist_elem) in dist.iter().enumerate() {
            if (dist_elem.range_start <= index) && (index < dist_elem.range_end) {
                debug!(
                    "Sampled {}: i = {}, sortition index = {}",
                    dist_elem.candidate.block_header_hash, i, &index
                );
                return Some(i);
            }
        }

        // should never happen
        panic!("FATAL ERROR: unable to map {} to a range", index);
    }

    fn get_last_vrf_seed(
        sort_tx: &mut SortitionHandleTx,
        block_header: &BurnchainBlockHeader,
    ) -> Result<VRFSeed, db_error> {
        let burn_block_height = block_header.block_height;

        // get the last winner's VRF seed in this block's fork
        let last_sortition_snapshot =
            sort_tx.get_last_snapshot_with_sortition(burn_block_height - 1)?;

        let vrf_seed = if last_sortition_snapshot.is_initial() {
            // this is the sentinal "first-sortition" block
            VRFSeed::initial()
        } else {
            // there may have been a prior winning block commit.  Use its VRF seed if possible
            sort_tx
                .get_block_commit(
                    &last_sortition_snapshot.winning_block_txid,
                    &last_sortition_snapshot.sortition_id,
                )?
                .expect("FATAL ERROR: no winning block commits in database (indicates corruption)")
                .new_seed
        };
        Ok(vrf_seed)
    }
