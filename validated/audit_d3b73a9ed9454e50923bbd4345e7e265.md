### Title
Market cancel/sell fee applied at execution time rather than order-creation time enables retroactive fee changes on outstanding orders - (File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java)

### Summary
Analogous to the SecondSwap `buyFee`/`sellFee` bug, java-tron's TRC10 market order book charges `MARKET_SELL_FEE` and `MARKET_CANCEL_FEE` at the moment an action (order creation or cancellation) is executed, using whatever fee value is currently stored in `DynamicPropertiesStore`, instead of a fee value fixed/snapshotted when the order was originally created. Since these fees are governance-controlled parameters that can be changed at any time via committee proposals, a user's order can be subject to a fee that did not exist (or was different) when they placed the order.

### Finding Description
`MarketCancelOrderActuator.calcFee()` reads the fee dynamically at cancel time: [1](#0-0) 

This fee is deducted from the account balance in `execute()`, using the live value of `MARKET_CANCEL_FEE` at the block in which the cancel transaction is processed, not the value that existed when the order (`MarketOrderCapsule`) was created via `MarketSellAssetActuator`: [2](#0-1) 

Similarly, `MarketSellAssetActuator.calcFee()` reads `MARKET_SELL_FEE` at order-placement time: [3](#0-2) 

The `MarketOrderCapsule` created for the order book does not persist the fee that applied at creation time; it only stores the trade parameters (tokens, quantities, price), so there is no snapshot to protect a maker order sitting in the book from a subsequent fee change.

Both `MARKET_SELL_FEE` and `MARKET_CANCEL_FEE` are governance parameters (`ProposalType.MARKET_SELL_FEE`, `ProposalType.MARKET_CANCEL_FEE`) that the committee can update via `ProposalService.process()`/`ProposalUtil.validator()` at any time, within the range `[0, 10_000_000_000L]`: [4](#0-3) 

Because order placement and order cancellation are two separate transactions that can be arbitrarily far apart in time (an order can sit unmatched in the book indefinitely, up to `MAX_ACTIVE_ORDER_NUM` per account), a user who places a sell order under one fee regime has no guarantee that the cancel fee will remain the same, or even predictable, by the time they decide to cancel.

### Impact Explanation
This mirrors the SecondSwap finding's core defect class: a fee parameter relevant to a user's already-committed on-chain state (an open listing / open order) is not fixed at creation but is instead re-evaluated at the time of a later, unrelated action. Concretely:
- A user opens a sell order when `MARKET_CANCEL_FEE` is 0 (a common default per `DynamicPropertiesStore` init logic).
- The committee later raises `MARKET_CANCEL_FEE` via proposal (up to 10,000 TRX equivalent).
- The user attempting to cancel their pre-existing order is now charged the new, unexpectedly higher fee — a fee they never agreed to and could not have known when submitting the order — with no fallback or protection mechanism.
- If the account balance is insufficient for the raised fee, cancellation reverts (`No enough balance !`), potentially trapping funds/tokens in an order indefinitely until the account is topped up.

This is a real, reachable divergence between user expectation and financial outcome for an unprivileged actor (any account that lists a market order), consistent with the "Impact" class of settlement/accounting surprise described in the report, though the magnitude is bounded by the parameter range and requires an actual governance proposal to pass.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a witness/committee proposal to change `MARKET_SELL_FEE` or `MARKET_CANCEL_FEE` (a normal, sanctioned governance action, not an attack), and (2) a user having an outstanding order at the time. Given TRON's committee actively tunes chain parameters via proposals, and market orders can remain open indefinitely, this is a realistic, if infrequent, occurrence rather than a purely theoretical one.

### Recommendation
Snapshot the applicable fee (at minimum the cancel fee, and optionally the sell fee) into the `MarketOrderCapsule`/proto at order-creation time, and have `MarketCancelOrderActuator.calcFee()` use the stored value from the order rather than re-reading the live `DynamicPropertiesStore` value. This guarantees the fee a user will pay to cancel is known and fixed at the time they place the order, consistent with the recommended mitigation in the original report (persisting `buyerFee`/`sellerFee` on the listing).

### Proof of Concept
1. Committee sets `MARKET_CANCEL_FEE = 0` (default init value per `DynamicPropertiesStore` initialization) [5](#0-4) .
2. User A submits `MarketSellAssetContract`, creating an open order via `MarketSellAssetActuator.execute()`; no cancel fee is stored on the order.
3. Committee passes a proposal raising `MARKET_CANCEL_FEE` to e.g. 10,000,000,000 sun (max allowed) via `ProposalUtil.validator()`/`ProposalService.process()`.
4. User A calls `MarketCancelOrderActuator.validate()`/`execute()` to cancel the still-open order; `calcFee()` now returns the new, much higher fee [1](#0-0) , which is deducted from User A's balance in `execute()` — a fee unknown to User A at the time they created the order, and potentially large enough to fail with "No enough balance !" if their balance is insufficient, locking the order/tokens until funded.
