### Title
Miner-side signer weight tally double-counts a flipped vote (reject→accept), corrupting the block approval/rejection threshold decision - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The external report concerns an on-chain oracle that can update a monotonic counter (`stoppedValidatorCounts`) without any invariant check tying new values to prior values or to a hard upper bound, letting the reporter corrupt a downstream picking/weighting algorithm. The closest reachable analog in this repo is the miner-side signer-response tally in `StackerDBListener`, which aggregates per-signer `Accepted`/`Rejected` weight into two counters, `total_weight_approved` and `total_weight_rejected`, that are used by `SigningCoordinator::gather_signatures` to decide whether a block is approved, rejected, or still pending. Just like the oracle case, this local tally has no invariant enforcing that a signer's weight can only be counted on one side at a time; a single signer (an unprivileged minority participant) can flip its vote from `Rejected` to `Accepted` and have its weight added into `total_weight_approved` a second time without ever being removed from `total_weight_rejected`.

### Finding Description
`BlockStatus` tracks, per proposed block, `responded_signers: HashSet<u32>` plus the two weight accumulators [1](#0-0) .

On `Rejected`, a slot's weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` succeeds (i.e., this is the first time that slot has responded at all): [2](#0-1) 

On `Accepted`, however, the gate is different: weight is added to `total_weight_approved` if the slot is not already present in `gathered_signatures` — a completely separate map from `responded_signers` — and then the code unconditionally inserts into both `gathered_signatures` and `responded_signers`: [3](#0-2) 

Because the `Accepted` branch never checks `responded_signers` (only `gathered_signatures`), a signer that has already been tallied as a rejecter (which put its `slot_id` into `responded_signers` and its weight into `total_weight_rejected`) is *not* blocked from later being tallied again as an accepter. Its weight is added to `total_weight_approved` with no corresponding subtraction from `total_weight_rejected`. The reverse order is correctly blocked: once a slot is in `responded_signers` (set by the accept path), a subsequent `Rejected` message for that slot fails `responded_signers.insert(slot_id)` and its weight is never added to `total_weight_rejected` [2](#0-1) .

The stale rejected weight is only ever cleared by `reset_rejections`, and that is invoked solely on a signature timeout in `SigningCoordinator::gather_signatures` [4](#0-3) , not whenever a signer's vote changes. So for the lifetime of a block proposal that has not yet timed out, `total_weight_rejected` can retain weight belonging to a signer who has since switched to `Accepted`, while that same weight is simultaneously present in `total_weight_approved`.

This breaks the intended invariant that a signer's weight should be attributed to exactly one side of the tally at any time (`total_weight_approved` and `total_weight_rejected` should be drawn from disjoint sets of slots), analogous to the reported bug where `stoppedValidatorCounts` could be set without enforcing monotonicity/bounds against the true underlying state.

This is precisely the decision the SigningCoordinator uses to determine `SignersRejected` vs. `Ok` (broadcast) vs. "keep waiting": [5](#0-4) 

### Impact Explanation
Because the reject-side tally can retain stale weight from a signer that has since approved, `total_weight_rejected` can be artificially inflated above the value a correct, single-vote-per-signer accounting would produce. This can push `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` to trip prematurely, causing the miner to conclude `SignersRejected` for a block that in reality is (or is about to be) approved by the true, non-double-counted distinct signer weight. This is a minority(single-signer)-triggerable divergence between the miner's local view of signer consensus and the signers' own state (each signer's local `signer.rs`/`SignerDb` correctly clears a stale rejection when a later signature is recorded — see `add_block_rejection_signer_addr`'s guard against rejecting once a signature exists, and the `reject_then_accept` test showing the rejection is cleared once a signature exists [6](#0-5) [7](#0-6) ). The miner-side aggregator in `stackerdb_listener.rs` lacks the equivalent protection, so it can incorrectly reject a block the signer network would otherwise approve, or otherwise diverge from the true weight state, causing the miner to abandon/retry the tenure and produce a different block than what the signer set would actually sign — a temporary tip/consensus disagreement between the miner and the true signer state. It does not corrupt on-chain state (the authoritative `verify_signer_signatures` check in `NakamotoBlockHeader` is unaffected), so it is bounded to the miner/coordinator's local liveness/consensus-tracking layer rather than causing a chain split.

### Likelihood Explanation
Triggering this requires only a single signer (no majority or collusion) to send a `Rejected` StackerDB message for a block and later legitimately change its vote to `Accepted` for the same block before the block times out — a scenario the signer protocol explicitly supports ("we do not change our votes on rejected blocks unless we receive a new block proposal ... allows us to reconsider," per the documented flow) [3](#0-2) . No special privileges, timing races beyond normal message ordering, or majority coordination are needed; a single signer can naturally exercise this vote-flip.

### Recommendation
In the `Accepted` branch of `stackerdb_listener.rs`, check `responded_signers` (or track per-slot vote state) symmetrically with the `Rejected` branch: if the slot previously contributed weight to `total_weight_rejected`, subtract that weight from `total_weight_rejected` before/while adding it to `total_weight_approved` (and vice versa for the reverse transition), so that a slot's weight is only ever counted on one side of the tally at a time — mirroring the invariant already enforced in `stacks-signer/src/signerdb.rs`'s `add_block_rejection_signer_addr`/`add_block_signature`.

### Proof of Concept
1. Coordinator proposes block `B` to a signer set with `total_weight = 100`, `weight_threshold = 70`.
2. Signer `S` (weight 5) sends `BlockResponse::Rejected(B)`. `responded_signers = {S}`, `total_weight_rejected = 5`.
3. 65 weight worth of other distinct signers approve `B`: `total_weight_approved = 65` (below threshold 70).
4. Signer `S` changes its mind and sends `BlockResponse::Accepted(B)` before any timeout/`reset_rejections` occurs.
5. In the `Accepted` branch, `block.gathered_signatures.contains_key(&S)` is `false` (this is `S`'s first `Accepted` message), so `total_weight_approved` becomes `65 + 5 = 70`, meeting `weight_threshold`. Meanwhile `total_weight_rejected` remains `5` (never decremented).
6. The coordinator now sees `total_weight_approved (70) >= weight_threshold (70)` and would broadcast the block as approved — while `total_weight_rejected` is stale-but-harmless here; conversely, construct the scenario the other way (more rejecters, one of which flips reject→accept late) so that `total_weight_rejected` stays inflated above the blocking-minority threshold even though the true, current distinct-signer rejection weight is below it, causing `gather_signatures` to return `SignersRejected` for a block that current signer weight would actually approve — demonstrating the tally's failure to enforce "one vote, one side" per signer.
