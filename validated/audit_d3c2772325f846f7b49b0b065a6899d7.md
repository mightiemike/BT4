### Title
Missing declared-class check in Starknet OS `execute_replace_class` diverges from Blockifier, enabling honest-node/proof state-root mismatch - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall omits the "class must be declared" check that the Rust Blockifier enforces for the identical syscall, creating a divergence between block execution (which determines the committed state diff) and Starknet OS re-execution (which proves that same block). This is analogous to the reported `ACCOUNT_VERSION` bug class: a value that gates an authorized state transition (there: account version equality; here: "is this class hash actually declared") is checked in one code path but silently skipped in the other, letting an unprivileged transaction reach a state mutation that should have been rejected.

### Finding Description
`execute_replace_class` in the OS program explicitly marks the missing check with a `TODO`, and proceeds to unconditionally overwrite the contract's `class_hash` in `contract_state_changes` with the caller-supplied `class_hash`, with no verification that this class hash was ever declared: [1](#0-0) 

By contrast, the Blockifier's Rust implementation of the same syscall (used to execute/build blocks and by full nodes/RPC) explicitly reads the compiled class before writing the new class hash, causing a `StateError::UndeclaredClassHash` (surfacing as "is not declared") when the class hash was never declared: [2](#0-1) 

This behavior is confirmed by the corresponding negative test, which shows Blockifier rejecting an undeclared class hash for `replace_class`: [3](#0-2) [4](#0-3) 

Because Blockifier is what actually executes transactions to build the block (and its state diff / revert status is committed on-chain), a transaction invoking `replace_class_syscall(undeclared_class_hash)` will be reverted by Blockifier (no state change applied, only fee charged). However, when the Starknet OS (SNOS) re-executes the same block to produce the STARK proof of validity, its Cairo `execute_replace_class` has no equivalent guard, so it will not revert on this input and will instead apply the class-hash change to `contract_state_changes`. Since SNOS output (state commitment) must match the block committed by the sequencer/Blockifier, this creates an execution divergence: SNOS computes a different final class hash / state root for the affected contract address than what Blockifier's execution and the committed block state diff say occurred.

### Impact Explanation
This is a state-commitment/proof-validity divergence reachable by any unprivileged account contract executing a single `replace_class` syscall with an undeclared class hash:
- The block as built and gossiped/committed by Blockifier shows the transaction reverted (unchanged class hash).
- SNOS re-execution (the source of truth used to generate/verify the block's validity proof and to reconstruct/verify the committed global state root) applies the class-hash change.

This falls under "wrong committed root or block hash" / "honest-node divergence" since two supposedly-equivalent execution engines (Blockifier vs. the OS Cairo program) disagree on whether the transaction succeeds and on the resulting state, for a scenario reachable purely from an unprivileged contract call.

### Likelihood Explanation
High likelihood of being triggerable: any contract can call the `replace_class` syscall (deprecated or new syscall interface) with an arbitrary, non-declared `class_hash` argument as ordinary calldata — no special privileges, prior state setup, or timing dependency is required. The only unknown is whether the new (non-deprecated) syscall handler in `syscall_base.rs` / `hint_processor.rs` (the Cairo1 execution path) enforces the same declared-class check as the deprecated handler; I was unable to fully confirm this given the tool-call limit, but the deprecated path's behavior and the explicit `TODO` comment in the shared OS Cairo function (used regardless of caller Cairo version) are enough to establish the vulnerability in the OS layer.

### Recommendation
Add the missing declared-class check in `execute_replace_class` in `syscall_impls.cairo` (and the deprecated OS equivalent, `execute_replace_class` in `deprecated_execute_syscalls.cairo`, if it shares the same gap), mirroring the Blockifier's `get_compiled_class` check, before allowing the `contract_state_changes` update. This should be done before removing the `TODO(Yoni, 1/1/2026)` marker, ensuring OS behavior always matches Blockifier's revert/no-op semantics for undeclared class hashes.

### Proof of Concept
1. Deploy any Cairo1 (or Cairo0) contract exposing the `replace_class_syscall` (e.g., the test contract's `test_replace_class`/`test_forbidden_syscall_in_virtual_mode` entry points shown in the codebase). [5](#0-4) 
2. Invoke it with an arbitrary `class_hash` value that was never declared on-chain.
3. Observe that Blockifier reverts this call with `"... is not declared"` (as in the existing test), producing a state diff with no class-hash change for the contract.
4. When Starknet OS (SNOS) re-executes the same block for proving, its Cairo `execute_replace_class` (missing the declared-class check per the `TODO`) applies the class-hash update to `contract_state_changes` regardless, producing a different state commitment for that contract than the one actually committed by Blockifier's execution — a concrete state-root/execution divergence between the sequencer and the OS proof.
