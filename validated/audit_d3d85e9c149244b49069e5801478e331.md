## Analysis

The Perennial bug class is: a governance-style function swaps a *mutable reference* (`collateral` address) with no check that dependent, already-in-flight user transactions built against the *old* reference are still consistent — allowing a race where the reference is quietly changed underneath a user's pending deposit/position, causing loss of funds.

nearcore has a directly analogous mutable-reference mechanism: `GlobalContractDeployMode::AccountId`. When a contract is deployed in this mode, code is stored under the *owner account id* rather than its hash, and "This allows the owner to update the contract for all its users" [1](#0-0) . Redeployment overwrites the code in place with no versioning tied to what any dependent transaction observed [2](#0-1) .

This mutable identifier is consumed by `DeterministicStateInitAction`, whose target account id is derived only from the *identifier value* `GlobalContractIdentifier::AccountId(owner)` — not from the actual code bytes currently stored under that owner [3](#0-2) [4](#0-3) . At execution time, `deploy_deterministic_account` simply calls `use_global_contract`, which binds whatever code currently exists at that identifier, with no comparison to what the signer expected when constructing/signing the transaction [5](#0-4) [6](#0-5) . The attached deposit is then settled onto that account afterward [7](#0-6) .

### Title
Frontrunning of `GlobalContractDeployMode::AccountId` code updates allows draining deposits sent to `DeterministicStateInitAction`-created accounts - (File: runtime/runtime/src/deterministic_account_id.rs)

### Summary
`DeterministicStateInitAction` derives its target account id purely from the `GlobalContractIdentifier` value (e.g. `AccountId(owner)`), not from the code bytes deployed under that identifier at signing time. Because `GlobalContractDeployMode::AccountId` lets `owner` overwrite its published global-contract code at any time with no validation against pending dependent transactions, an attacker can front-run a victim's signed `DeterministicStateInitAction` (which carries a deposit) by redeploying malicious code to `owner`, causing the victim's newly created account to be bound to attacker-controlled code that can then move out the deposited funds.

### Finding Description
A global contract deployed in `AccountId` mode is intentionally mutable: "This allows the owner to update the contract for all its users" [1](#0-0) . `action_deploy_global_contract` lets the owning account overwrite the code stored under its own `AccountId` identifier at will, with the new bytes replacing the old ones in the trie once the distribution receipt lands, and no check on outstanding transactions that reference the identifier [8](#0-7) [2](#0-1) .

A user can build a `DeterministicStateInitAction` whose `state_init.code` field is `GlobalContractIdentifier::AccountId(owner)`. The resulting account id is `derive_near_deterministic_account_id(state_init)`, a hash over the *identifier*, not over the code bytes currently live at `owner` [3](#0-2) . When the receipt executes, `action_deterministic_state_init` → `deploy_deterministic_account` → `use_global_contract` only checks that *some* code exists under the identifier at execution time and binds the account to it — it performs no comparison against the code the signer inspected when constructing the transaction [5](#0-4) [6](#0-5) . The deposit is then settled onto that (now attacker-controlled) account: `settle_state_init_deposit` tops it up to cover storage staking and refunds the remainder, leaving the deposit resident on the account [7](#0-6) [9](#0-8) .

This is the exact same structural flaw described in the report: a critical, permissionlessly-updatable reference (`collateral` address / here, `GlobalContractIdentifier::AccountId` code) can be swapped underneath a signed, in-flight user transaction that depended on the old value, with no on-chain validation tying the two together.

### Impact Explanation
An attacker who controls (or creates) an `owner` account that has published a global contract can:
1. Wait for a victim to observe the current (benign) code deployed at `owner` and sign a `DeterministicStateInitAction` with a deposit that derives an account id from `GlobalContractIdentifier::AccountId(owner)`.
2. Before the victim's receipt executes, submit `DeployGlobalContractAction{deploy_mode: AccountId}` from `owner` with malicious code (e.g. containing a backdoor that transfers the account's balance to `owner`).
3. Once the victim's `DeterministicStateInitAction` executes, the newly created account is bound to the attacker's malicious code and receives the victim's deposit.
4. The attacker then calls the backdoor method to drain the deposited balance.

This is a concrete unauthorized value-movement path reachable purely from unprivileged, ordinary account-owner transactions (no validator, node, or network-level privilege required).

### Likelihood Explanation
Any account owner can redeploy their `AccountId`-mode global contract at any time (permissionless, self-serve action), and `DeterministicStateInitAction` intentionally allows referencing a contract this way before the account is created — this is a normal, documented usage pattern (NEP-616), not an edge case. The only requirement for the attacker is to win a race against the victim's transaction ordering/inclusion, and global-contract distribution across shards is itself asynchronous and multi-block [10](#0-9) , widening the exploitation window.

### Recommendation
Bind the deterministic account id (or otherwise pin `DeterministicStateInitAction`) to the concrete code hash live at the moment the identifier was resolved, or require `use_global_contract`/`deploy_deterministic_account` to fail (rather than silently succeed) if the code found under an `AccountId` identifier does not match a hash the signer commits to. Alternatively, warn/disallow using mutable `AccountId`-mode identifiers as the `code` of a `DeterministicStateInitAction` that also carries a non-zero deposit, since the mutability defeats the "deterministic" guarantee the feature is meant to provide.

### Proof of Concept
1. `owner.near` deploys a benign global contract with `DeployGlobalContractAction{deploy_mode: GlobalContractDeployMode::AccountId}` [11](#0-10) .
2. Victim inspects the code, builds `DeterministicAccountStateInit::V1{code: GlobalContractIdentifier::AccountId(owner.near), data}`, derives `det_account` via `derive_near_deterministic_account_id` [12](#0-11) , and signs a `DeterministicStateInitAction` transaction attaching a deposit targeting `det_account`.
3. `owner.near` races the victim's transaction by submitting a second `DeployGlobalContractAction{deploy_mode: AccountId}` with malicious code containing a self-drain method; the redeployment overwrites the trie entry for `GlobalContractCode{AccountId(owner.near)}` [13](#0-12) , as demonstrated by `test_global_contract_update`, which shows a second deploy under `AccountId` mode fully replaces behavior for all accounts referencing it [14](#0-13) .
4. The victim's `DeterministicStateInitAction` then executes, binding `det_account` to the malicious code and settling the deposit onto it [5](#0-4) .
5. `owner.near` calls the backdoor method on `det_account` to transfer out the victim's deposited balance.

    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),

            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,

    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
    let already_delivered_shards = Vec::from_iter(already_delivered_shards);
    let predecessor_id = receipt.predecessor_id().clone();
    let next_receipt = global_contract_data.forward(next_shard, already_delivered_shards);

    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);

                receiver_account_id: next_receipt.receiver_id().clone(),
                shard_id: apply_state.shard_id,

/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

pub(crate) fn settle_state_init_deposit(
    account: &mut Account,
    deposit: Balance,
    account_id: &AccountId,
    receipt: &Receipt,
    config: &RuntimeConfig,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // Use attached deposit to satisfy storage staking requirements and refund
    // the rest.
    let deposit_refund = match check_storage_stake(account, account.amount(), config) {
        Ok(_) => {
            // no additional storage needed, refunding all
            deposit
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(missing_amount)) => {
            if missing_amount <= deposit {
                // use exactly as much as needed and refund the rest
                let new_balance = safe_add_balance(account.amount(), missing_amount)?;
                account.set_amount(new_balance);
                deposit.checked_sub(missing_amount).expect("just checked missing_amount <= deposit")
            } else {
                result.result = Err(ActionErrorKind::LackBalanceForState {
                    account_id: account_id.clone(),
                    amount: missing_amount,
                }
                .into());
                return Ok(());
            }
        }
        Err(StorageStakingError::StorageError(err)) => {
            return Err(RuntimeError::StorageError(StorageError::StorageInconsistentState(err)));
        }
    };

    if deposit_refund > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund));
    }

    Ok(())
}
