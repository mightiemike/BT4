## Finding

Local investigation converged on the same "checked-but-not-fully" integrity pattern as the AML report: a verification routine that is supposed to authenticate committed state against a trusted proof silently skips one of the fields it should validate.

### Title
`TransactionOutput::ensure_match_transaction_info` never validates state-checkpoint hashes, letting replay/chunk-execution accept an output whose state root diverges from the authenticated `TransactionInfo` — (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function used to authenticate a locally-produced `TransactionOutput` against the `TransactionInfo` obtained (with proof) from a peer/backup during chunk execution and replay. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as acknowledged by the code's own TODO comment.

### Finding Description [1](#0-0) 

The comment at the end of the function states plainly:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
This function is invoked from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — i.e., it is not confined to test/debug tooling; the chunk executor is on the state-sync / chunk-replay commit path. Its purpose is exactly to bind a locally computed `TransactionOutput` to the authenticated `TransactionInfo` (transaction hash, event root, write-set hash, gas, status), the same invariant class flagged in "Proof And Storage Pivots" — but it omits the state-checkpoint root fields, which are precisely the fields that represent the resulting ledger state after the transaction.

### Impact Explanation
If local execution produces a `TransactionOutput` whose write set, events, gas, and status all match the trusted `TransactionInfo`, but whose resulting state tree (state checkpoint hash / hot-state checkpoint hash / position-state checkpoint hash) differs from the authenticated value — due to a storage bug, non-determinism, or a hard-fork-only divergence in state-checkpoint construction — `ensure_match_transaction_info` will still return `Ok(())`. Any caller relying on this function (chunk executor during replay, `replay_on_archive` verification tooling) will treat the divergent output as verified and proceed to commit/accept it, masking a corrupted or forked state root rather than rejecting it. This is a state-commitment integrity gap: proof-bearing verification silently accepts wrong state roots.

### Likelihood Explanation
This is not a theoretical edge case triggered by attacker input — it's a structural gap in a verification routine that is unconditionally reached on every chunk/txn replay through `execution/executor/src/chunk_executor/mod.rs`; the missing check applies for every transaction, always, on every node performing chunk-execution/replay, whenever the state-checkpoint-hash computation itself is buggy or diverges. However, note this is gated as a known/acknowledged TODO tied to feature flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`position_state_checkpoint_hash`, meaning the aptos team is aware of the gap and has deferred it — I could not fully confirm (within available tool calls) whether `position_state_checkpoint_hash`/hot-state checkpoints are already validated elsewhere in the same call chain (e.g., in `LedgerUpdateOutput::ensure_transaction_infos_match` or in the accumulator-root check that happens after all txn infos are assembled) which could make this specific code path redundant/defense-in-depth rather than the sole gate. I was not able to trace `execution/executor-types/src/ledger_update_output.rs`'s `ensure_transaction_infos_match` in full within the remaining iterations to confirm whether it independently re-derives and checks the state-checkpoint hash from local state before the accumulator-root comparison, which would mitigate this gap.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the freshly computed output and the trusted `TransactionInfo`, as the existing TODO already recommends, before any state-checkpoint-dependent feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet. Confirm whether an equivalent check already exists independently in the ledger-update/accumulator-root verification path; if so, document that this function's gap is intentionally deferred to that later check, and if not, treat this as the sole integrity gate needing the fix.

### Proof of Concept
Not independently reproducible from static analysis alone — this requires a state-checkpoint-hash-producing bug (or hard-fork divergence) that leaves write-set/events/gas/status unaffected. I could not execute code to construct such a divergent `TransactionOutput` within this session; the finding rests on the function's documented behavior and its call sites, not a demonstrated exploit.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
