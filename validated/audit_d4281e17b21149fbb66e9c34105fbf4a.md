### Title
Wallet Contract pays relayer fee before verifying the underlying transfer succeeds, causing unconditional fund loss - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
In `inner_rlp_execute`, when an eth-implicit account's owner submits an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the wallet contract fires the relayer-fee transfer as an independent promise *before* it knows whether the main action promise (the actual base-token transfer or `ft_transfer`) will succeed. The fee payment is not gated on, nor reverted by, the result of the primary cross-contract call.

### Finding Description
`inner_rlp_execute` parses the RLP transaction into an `Action` plus a `TransactionKind`. For `EOABaseTokenTransfer`/`ERC20Transfer` kinds carrying a non-zero `fee`, the code immediately creates a standalone batch promise to pay the relayer: [2](#0-1) 

This fee-payment promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) is scheduled unconditionally and separately from the actual transfer/`ft_transfer` promise chain that is built afterward (`action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))`, line 469, or the ERC-20 `storage_balance_of` → `ft_transfer` chain at lines 445-457). Both promises are dispatched from the same receipt and neither is a callback of the other, so the runtime has no dependency between them — the fee transfer executes regardless of whether the subsequent action succeeds. The only failure-handling path that exists, `rlp_execute_callback`, only refunds the `caller_deposit` (the attached NEAR deposit passed into the call), not the `fee` that was already paid out to the relayer: [3](#0-2) 

Thus, if the token/`ft_transfer` call later fails (bad receiver, insufficient token balance, NEP-141 contract panic, storage-deposit failure, gas exhaustion, etc. — an external call whose outcome is not checked before compensating the relayer), the wallet owner has already paid the relayer's fee for a transfer that never happened.

### Impact Explanation
Every failed `ERC20Transfer`/`EOABaseTokenTransfer` with a non-zero fee results in unconditional, unrecoverable loss of the fee amount from the eth-implicit account's NEAR balance to the relayer, with no corresponding successful action. Because the eth-implicit account nonce is still incremented on parsing success (line 364), this loss is a direct byproduct of ordinary use of the Wallet Contract (NEP-518 eth-implicit accounts), reachable by any account holder submitting a normal RLP transaction through any relayer — no privileged access required.

### Likelihood Explanation
This is triggered by completely ordinary usage: any ERC-20/base-token transfer through the Wallet Contract with a nonzero fee that subsequently fails for any legitimate on-chain reason (receiver not registered and storage deposit insufficient, token contract rejecting the transfer, insufficient token balance, gas mis-estimation, or a malicious/careless relayer who nonetheless wants to be paid regardless of outcome) results in fee loss. No adversarial coordination beyond a relayer's normal transaction-submission role is required.

### Recommendation
Chain the fee-payment promise onto the success branch of the main action promise (or perform it inside `rlp_execute_callback` only after observing `PromiseResult::Successful`), rather than firing it unconditionally before the primary action executes. Alternatively, include the fee in the same batch/action set as the primary transfer so both succeed or fail atomically, and extend `CallerDeposit`-style refund tracking to cover the fee amount so it can be returned to the user if the underlying transfer fails.

### Proof of Concept
1. User signs an RLP `ERC20Transfer` (or `EOABaseTokenTransfer`) transaction via their Wallet Contract with `fee > 0` payable to the relayer.
2. Relayer submits it; `inner_rlp_execute` immediately creates and dispatches the fee-transfer promise at lines 382-383 to the relayer's account.
3. The subsequent `storage_balance_of` → `ft_transfer` (or transfer) promise chain fails on-chain for any reason (e.g., receiver's token storage deposit insufficient, or the token contract panics).
4. `rlp_execute_callback`/`nep_141_storage_balance_callback` reports failure and only refunds `caller_deposit` (if any) — the `fee` already sent to the relayer is never returned.
5. Net effect: the user's balance is permanently reduced by `fee`, with no successful transfer executed.
