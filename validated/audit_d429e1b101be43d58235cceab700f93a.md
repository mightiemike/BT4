### Title
Wallet Contract's `has_in_flight_tx` lock can be stranded `true` forever by an underfunded promise chain, permanently freezing the eth-implicit account — (`File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (deployed as a global contract behind every ETH-implicit account) uses a boolean `has_in_flight_tx` to serialize `rlp_execute` calls. The flag is set to `true` in the entry point and is only reset to `false` as the very first statement of each async callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`). If the *receipt* that runs a callback fails for any reason (e.g. the relayer under-funds the attached gas so the callback runs out of gas mid-execution), the entire receipt's state changes — including the `has_in_flight_tx = false` reset that already ran — are rolled back by the runtime's per-receipt atomicity rule. `has_in_flight_tx` is thus left permanently `true`, and every subsequent call to `rlp_execute` immediately short-circuits with "transaction already in progress", locking the account out of the wallet-contract flow forever. This is directly analogous to the Y2K report: a state-machine flag that should only be flipped after a successful "epoch"/tx-completion is instead committed unconditionally, and a caller (here, an underfunding relayer, no special privilege required) can force the flag into the "in-progress forever" state, permanently freezing the account's usable path for its funds.

### Finding Description
- `rlp_execute` sets `self.has_in_flight_tx = true` and returns a `Promise` chain (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:97-127`). [1](#0-0) 
- Every asynchronous callback resets the flag as its first line before doing anything else: `address_check_callback` (`self.has_in_flight_tx = false;` at line 140), `nep_141_storage_balance_callback` (line 202), `rlp_execute_callback` (line 280). [2](#0-1) [3](#0-2) [4](#0-3) 
- The contract's own doc comment states the invariant explicitly: `has_in_flight_tx` must be `true` while a mutable method has an outstanding promise and `false` otherwise. [5](#0-4) 
- The runtime's receipt-execution model rolls back *all* state changes of a receipt whose result is an error, keeping only gas accounting: "a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting." [6](#0-5) 

Because each callback's `has_in_flight_tx = false` write and its subsequent cross-contract calls all execute inside the *same* action receipt, any failure later in that same receipt (most plausibly running out of gas, since the callback's static gas budgets such as `RLP_EXECUTE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` are only just enough for the "happy path" and are combined with attacker/relayer-influenced `action.gas()`) causes the whole callback receipt, including the just-executed reset, to be discarded. `rlp_execute` is a public entry point that any relayer account can call for a signed Ethereum transaction — no special privilege is needed to trigger this path, mirroring "anyone can trigger" in the original report. [7](#0-6) 

### Impact Explanation
Once `has_in_flight_tx` is stranded `true`, `rlp_execute` unconditionally returns the "transaction already in progress" error for every future call on that eth-implicit account, without ever clearing the flag (there is no timeout/reset path): [8](#0-7) 
This permanently freezes the account's ability to move its NEAR balance through the wallet contract (the only supported path for ETH-implicit accounts to act), which matches the accepted "permanently frozen funds" impact class — analogous to the Y2K depositors whose funds get stuck once `triggerEndEpoch` is wrongly allowed on an empty vault.

### Likelihood Explanation
No validator, node, or protocol privilege is required. Any account acting as relayer for a validly-signed Ethereum transaction can submit it with an insufficient/edge-case gas attachment (or trigger any other failure inside the callback receipt, e.g. a cross-contract call to the address registrar/NEP-141 contract failing in an unexpected way after the reset line but before the receipt otherwise succeeds) to cause the callback receipt to fail after the `has_in_flight_tx = false` line has already executed. This is a normal transaction-construction choice (gas amount), reachable purely through the standard `SignedTransaction`/RPC submission path.

### Recommendation
Do not rely on an in-callback boolean reset that can be rolled back with the rest of the receipt. Instead: (1) reset `has_in_flight_tx` using a separate, unconditionally-succeeding receipt/promise (e.g., a dedicated `.then()` step with `PromiseResult`-independent cleanup that cannot itself fail), or (2) add a recovery/timeout mechanism allowing the flag to be cleared (e.g., by the account owner) if no callback resolves within a bounded number of blocks, or (3) ensure the callback's own gas budget is computed so it cannot run out of gas before the reset-plus-minimal-cleanup completes, and treat any deeper failure as isolated (not rolling back the flag reset) by structuring the reset as its own committed step prior to any fallible sub-call.

### Proof of Concept
1. Deploy the Wallet Contract as global contract and create an ETH-implicit account funded with NEAR, following the flow in `test_wallet_contract_interaction`. [9](#0-8) 
2. Craft a signed Ethereum transaction whose `to`/payload routes through `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(_) , .. }` or `ERC20Transfer`, so `rlp_execute` schedules a multi-step promise (`address_check_callback` or `nep_141_storage_balance_callback` followed by `rlp_execute_callback`). [10](#0-9) 
3. Submit the wrapping NEAR `FunctionCall` to `rlp_execute` with attached gas sufficient to enter the promise chain and flip `has_in_flight_tx = true`, but insufficient to let the final callback receipt finish after its `has_in_flight_tx = false` line executes (e.g., attach just enough gas to reach the last cross-contract call inside the callback, causing a gas-exceeded failure there).
4. Observe: the callback receipt fails, `state_update.rollback()` discards the `has_in_flight_tx = false` write along with everything else in that receipt. [6](#0-5) 
5. Call `rlp_execute` again with a legitimate, well-signed transaction (any nonce/gas): it now unconditionally returns `"Error: transaction already in progress, please try again later."` forever, because `has_in_flight_tx` is stuck `true` with no code path to reset it. [11](#0-10)
