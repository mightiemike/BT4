### Title
Chunk-executor replay verification (`ensure_match_transaction_info`) silently accepts a divergent position/hot-state checkpoint root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used by chunk replay/verification (`execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed/authenticated on-chain. The check validates status, gas, the write-set hash (`state_change_hash`) and the event root hash, but it does not validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried by `TransactionInfoV1`.

### Finding Description [1](#0-0) 

The function iterates over the fields it does check (status, gas_used, write_set hash, event_root_hash) but explicitly skips the state-checkpoint-family hashes, with a developer TODO acknowledging the gap: [2](#0-1) 

This means that if a locally recomputed state/hot-state/position-state checkpoint root diverges from the authenticated `TransactionInfoV1` (e.g., due to a bug in `DoStateCheckpoint`, a JMT/position-tree computation bug, a hard-fork behavioral divergence, or corrupted intermediate state), `ensure_match_transaction_info` still reports success as long as the write set and events match. This routine is exactly the proof/commitment invariant boundary described in the task ("Committed state that differs from the correct VM result... Wrong accumulator root, Merkle proof... accepted as valid... Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state").

### Impact Explanation
`ensure_match_transaction_info` is the sole consistency gate used by:
- `execution/executor/src/chunk_executor/mod.rs` when applying/verifying transaction chunks during state-sync/backup restore/replay,
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` for `replay-verify`/`db-tool replay_on_archive` tooling that is used to detect execution divergence (including hard-fork divergence) between historical execution and the currently running binary.

Because the checkpoint-hash family is skipped, a node or auditor running replay-verify against archived history can get a false "successful replay" result even though the locally computed state/hot-state/position-state root has silently diverged from the authenticated root stored in the ledger. This directly undermines the primary purpose of replay-verify — catching state-commitment divergence (including hard-fork-only divergence) before it propagates — which is explicitly in-scope per the report's "Hard-fork-only divergence during commit, replay, restore, or proof verification" criterion. If replay-verify is the safety net used to certify that a new binary reproduces historical ledger state bit-for-bit, this hole means a real divergence in the authenticated state-checkpoint root could pass undetected in an automated pipeline.

### Likelihood Explanation
The gap is unconditionally present in the comparator regardless of feature flags — it isn't gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`; it just isn't invoked for the `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields at all. The trigger requires a pre-existing (separate) bug that causes local state-checkpoint computation to diverge from the authenticated one; `ensure_match_transaction_info` itself does not cause corruption, but it is the safety check that fails to catch such corruption, silently masking downstream state-root divergence. I could not fully verify from the index whether any current mainnet path guarantees the checkpoint hash values are always correct independently (so this may only manifest given another latent bug), which limits the severity to "detection-gap" rather than a directly triggerable state-corruption bug on its own.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionInfo` variant) against locally recomputed values, consistent with the existing TODO comment in the code, before enabling any feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that relies on this comparator for correctness guarantees.

### Proof of Concept
Not independently reproducible as a standalone exploit — this is a verification-gap finding, not a directly triggerable corruption. Conceptual PoC: run replay-verify (`db-tool replay_on_archive` or `aptos-debugger`) against a chunk of transactions where the write set/events match but the position/hot-state checkpoint hash embedded in `TransactionInfoV1` differs from what local execution computes (e.g., inject a divergent hot-state root via a modified `DoStateCheckpoint` implementation in a test harness); `ensure_match_transaction_info` at [3](#0-2)  will return `Ok(())` despite the mismatch.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
