### Title
Webhook HMAC signature does not bind the shop domain, permitting cross-tenant webhook replay - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
This is the shopify-app-js analog of the "missing `chain.id`" bug class: a signature is validated without binding it to the security-scope context (network for the LP token bug; shop/tenant for this codebase), enabling a request that is valid in one context to be replayed and accepted in another.

### Finding Description
The HMAC that authenticates an inbound webhook is computed over the raw body only, using the app's single, shared `apiSecretKey`: [1](#0-0) 

`validateHmacString` hashes `rawBody` with `config.apiSecretKey` and compares it to the `X-Shopify-Hmac-Sha256` header value: [2](#0-1) 

Crucially, the `X-Shopify-Shop-Domain` header (the "tenant/chain" identifier) is **never** included in the signed material. It is only read afterward, out-of-band and unauthenticated, in `checkWebhooksHeaders`/`checkEventsHeaders`: [3](#0-2) 

Because the same `apiSecretKey` is used to sign webhooks for **every** shop that installs the app, a party who controls one shop (e.g., a merchant's own development/test store, or any store where they can trigger a webhook such as `products/create`) legitimately receives a `(rawBody, hmac)` pair that is valid under the app's secret. Since `domain` is not part of the signed data, that same body+HMAC pair remains valid if the `X-Shopify-Shop-Domain` header is swapped for an arbitrary victim shop domain — the HMAC check in `validateHmacFromRequestFactory` still succeeds because it never inspects `domain`: [4](#0-3) 

Downstream, the accepted `check.domain` value is trusted to look up and attach the **offline session/access token for that shop** and process the webhook as if it originated from the victim's store: [5](#0-4) 

This mirrors the LSD/`deployLPToken` bug precisely: the signed artifact lacks a scope-binding value (chain.id there, shop domain here), so a message valid in the attacker's own scope can be replayed into a victim's scope.

### Impact Explanation
An attacker who is themselves a merchant of the app (an unprivileged, single "shop"/tenant actor) can:
- Capture a validly-signed webhook body+HMAC from their own store.
- Replay it toward the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to any victim shop.
- Have the app accept it as an authentic Shopify request for the victim shop, causing `ensureValidOfflineSession`/session lookup to attach the **victim's** offline session and admin token to the (attacker-controlled-content) webhook processing pipeline.

This is a concrete "accepted forged Shopify request" / cross-tenant confusion: the app cannot distinguish "this webhook really came from shop X" from "this webhook body was signed for some shop and had its domain header changed," because domain is not cryptographically bound to the signature. Depending on the app's webhook handlers, this can lead to processing of attacker-chosen event payloads under a victim's session/admin context, data confusion between tenants, or triggering side effects (e.g., data writes, notifications, business logic) attributed to the wrong shop.

### Likelihood Explanation
Moderate-to-high. The attacker only needs their own store (any developer/partner account can create one) to legitimately trigger a webhook of a topic they want to abuse, capture the (body, hmac) pair via a network proxy, and re-POST it with a modified domain header at the app's public webhook endpoint. No secrets need to be leaked — the shared `apiSecretKey` is never exposed to the attacker; they merely reuse a validly-issued signature outside its intended scope, exactly analogous to a cross-chain replay.

### Recommendation
Bind the shop/tenant identity into the authenticated material instead of trusting the `X-Shopify-Shop-Domain` header out-of-band:
- Include the `domain` (and ideally `topic`/`webhook-id`) in the string that is HMAC'd/verified, or verify that the HMAC was computed together with these header values (similar to how OAuth callback HMACs cover the whole query string, see `generateLocalHmac`/`stringifyQueryForAdmin`): [6](#0-5) 
- Alternatively/additionally, reject webhooks whose `domain` does not match a shop with an active session/installation state consistent with when the webhook is claimed to have been generated, and rate-limit/dedupe by `webhook-id` scoped per domain to reduce replay windows.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a `products/create` webhook (or lets it fire from their own store), capturing the raw HTTP POST: `rawBody` and header `X-Shopify-Hmac-Sha256: <hmac>`.
2. Attacker resends this exact `(rawBody, hmac)` to the app's webhook endpoint, but replaces the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `validateHmacFromRequestFactory` in `hmac-validator.ts` only checks `hmac == HMAC(apiSecretKey, rawBody)`, which still matches (domain was never part of the signed input): [7](#0-6) 
4. `checkWebhooksHeaders` extracts `domain: 'victim-shop.myshopify.com'` unauthenticated and returns `{valid: true, domain, ...}`: [8](#0-7) 
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` and attaches the victim shop's offline session/admin client to the webhook context, believing the request is authentic for that shop: [9](#0-8) 

I was unable to fully trace whether every downstream app-facing handler (e.g., `shopify-app-express`'s `webhooks.process`) additionally re-derives/verifies domain from a separate trusted channel before dispatching to app-registered handlers; this would need direct verification in a live Devin session with full repository access, since the ask-only index may not contain every relevant handler file.

  return async (

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
