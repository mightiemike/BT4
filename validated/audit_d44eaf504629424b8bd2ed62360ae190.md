### Title
Silent long-overflow truncation in `MarketUtils.multiplyAndDivide` BigInteger fallback corrupts settlement quantities - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`multiplyAndDivide(a, b, c, disableMath)` falls back to `BigInteger` arithmetic only when `multiplyExact(a, b)` overflows, but the fallback returns `aBig.multiply(bBig).divide(cBig).longValue()` without checking that the *exact* mathematical result fits in a `long`. `BigInteger.longValue()` silently truncates to the low 64 bits instead of throwing, so if the true `a*b/c` exceeds `Long.MAX_VALUE`, the returned quantity is an arbitrary wrapped value rather than an error, breaking the deterministic accounting used in market order matching.

### Finding Description
`multiplyAndDivide` is defined at [1](#0-0) . It first tries `multiplyExact`/`floorDiv` and only on `ArithmeticException` switches to `BigInteger`, then converts back with `.longValue()`, which performs modulo-2^64 truncation instead of raising an error when the exact quotient does not fit in a `long`.

It is called from `MarketSellAssetActuator.matchSingleOrder` with attacker/maker order fields taken directly from stored `MarketOrderCapsule` values that originate from `MarketSellAssetContract` fields (`sellTokenQuantity`, `buyTokenQuantity`) validated only by `sellTokenQuantity <= quantityLimit` / `buyTokenQuantity <= quantityLimit` in `validate()` [2](#0-1) . The reachable call chain is `execute` → `matchOrder` → `matchSingleOrder` → `MarketUtils.multiplyAndDivide` [3](#0-2) .

An attacker who controls both a maker order (e.g. `makerSellQuantity` large, `makerBuyQuantity = 1`, the minimum allowed positive value per the `> 0` check) and a taker order with a large `takerSellRemainQuantity` can force `multiplyExact(takerSellRemainQuantity, makerSellQuantity)` to overflow (triggering the BigInteger path), while the *true* quotient (divided by `makerBuyQuantity = 1`) still exceeds `Long.MAX_VALUE`. In that case `.longValue()` does not return the correct saturated/error value — it returns a truncated/wrapped `long`, which can be a small, large, or even negative number unrelated to the real price ratio.

None of the existing guards (auth checks, `quantityLimit` cap, `ContractValidateException` on `ArithmeticException` in `validate()`) protect against this, because the overflow happens inside `execute()`'s matching logic, not in `validate()`, and the `catch (ArithmeticException ex)` in `multiplyAndDivide` intentionally swallows the overflow to fall into the truncating `BigInteger` path rather than propagating the error.

### Impact Explanation
A wrapped/truncated `takerBuyTokenQuantityRemain` desynchronizes the exchange-ratio invariant that the matching logic depends on. Depending on the wrapped sign/magnitude this can (a) cause a taker to receive a `buyToken`/TRX amount inconsistent with the maker's real price (mis-settlement), (b) drive `makerOrderCapsule.setSellTokenQuantityRemain`/`subtractExact` calls into further `ArithmeticException`s (causing the whole actuator to fail non-deterministically depending on truncated bit patterns), or (c) if the wrapped value is negative, flow into `addTrxOrToken` and subtract balance/assets instead of adding them, corrupting account state. This is a deterministic-accounting/invalid-state class issue reachable purely through market order fields controlled by an unprivileged sender.

### Likelihood Explanation
Exploitability depends on the configured `dynamicStore.getMarketQuantityLimit()` value that bounds `sellTokenQuantity`/`buyTokenQuantity` in `validate()` [4](#0-3) . I was not able to confirm the exact configured/default numeric value of this limit within the available tool budget, so I cannot state with certainty that the limit permits `a, b` values large enough (roughly > ~3.03×10^9 each, so that `a*b` alone overflows a signed 64-bit long) to reach the truncating branch through a full `execute()` call. If the configured limit is large (as is plausible for a token-quantity field meant to support asset units up to ~10^14–10^17), the overflow condition is trivially reachable by any account: create a maker order with `buyTokenQuantity = 1` and a large `sellTokenQuantity`, then a matching taker order with a large `sellTokenQuantity`. The bug in `multiplyAndDivide` itself is unconditionally reproducible as a pure function-level unit test regardless of that limit.

### Recommendation
In `MarketUtils.multiplyAndDivide`, after computing the `BigInteger` result, check `result.bitLength() > 63` (i.e., it doesn't fit in a signed `long`) and throw an `ArithmeticException`/domain-specific exception instead of calling `.longValue()` unconditionally, e.g.:
```java
BigInteger result = aBig.multiply(bBig).divide(cBig);
if (result.bitLength() > 63) {
  throw new ArithmeticException("multiplyAndDivide overflow");
}
return result.longValueExact();
```
Using `longValueExact()` (which throws `ArithmeticException` on truncation) instead of `longValue()` is the minimal fix, and the caller (`matchSingleOrder`) should treat this exception as a hard failure of the match rather than silently proceeding.

### Proof of Concept
```java
// MarketUtilsOverflowTest.java
import java.math.BigInteger;
import org.junit.Test;
import static org.junit.Assert.*;
import org.tron.core.capsule.utils.MarketUtils;

public class MarketUtilsOverflowTest {

  @Test
  public void multiplyAndDivide_silentlyTruncatesOnOverflow() {
    long a = 4_000_000_000L;      // > sqrt(Long.MAX_VALUE) ~ 3.037e9
    long b = 4_000_000_000L;
    long c = 1L;                  // minimum valid buyTokenQuantity

    // exact mathematical result
    BigInteger exact = BigInteger.valueOf(a).multiply(BigInteger.valueOf(b))
        .divide(BigInteger.valueOf(c));

    // true result does not fit into a long
    assertTrue(exact.bitLength() > 63);

    long actual = MarketUtils.multiplyAndDivide(a, b, c, true);

    // BUG: instead of throwing/rejecting, the function returns a
    // silently truncated value that diverges from the exact BigInteger result
    assertNotEquals(exact, BigInteger.valueOf(actual));
  }
}
```
Expected: the assertion `assertNotEquals(exact, BigInteger.valueOf(actual))` passes today, demonstrating the divergence between the exact price-ratio computation and the value actually used to settle `takerBuyTokenQuantityRemain` in `MarketSellAssetActuator.matchSingleOrder`. An integration-level PoC would additionally construct two `MarketSellAssetContract`s (maker with `buyTokenQuantity = 1`, large `sellTokenQuantity`; taker with matching large `sellTokenQuantity`) and assert that `MarketOrderDetail.getFillBuyQuantity()`/account balances after `execute()` do not correspond to the real price ratio — this part is dependent on the actual configured `MarketQuantityLimit`, which should be verified in the target environment before relying on the end-to-end contract path.
