### Title
Delegate-action (meta-transaction) balance refunds are routed to the malicious sender instead of the paying relayer, bypassing the relayer's fee/cost model - (File: `runtime/runtime/src/actions.rs`)

### Summary
When a relayer submits a NEP-366 meta-transaction (`Delegate`/`DelegateV2` action) on behalf of a sender, the relayer prepays all gas and any attached deposits for the inner actions. `apply_delegate_action` builds the inner receipt but never sets its `refund_to` field, so if the inner action fails on the receiver's shard, the deposit refund is sent to the `predecessor_id` (the sender who signed the `DelegateAction`) instead of to the relayer who actually paid for it. This lets a malicious sender who signs a meta-transaction with a deliberately-failing inner action redirect the relayer's paid deposit to themself, effectively bypassing the fee/cost obligation the relayer agreed to pay.

### Finding Description
`apply_delegate_action` in `runtime/runtime/src/actions.rs` constructs the receipt executed on the sender's shard for the inner actions of a `DelegateAction`: [1](#0-0) 

The predecessor of this new receipt is set to `sender_id` (the account that signed the `DelegateAction`, e.g. "Alice"), while all gas/deposit was actually prepaid by the relayer on the relayer's shard. The code comment explicitly documents the resulting risk:

> "Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit."

The generic refund path in `refund_unspent_gas_and_deposits` sends deposit refunds to `receipt.balance_refund_receiver()` which, for a plain `ActionReceipt`, is simply the receipt's predecessor: [2](#0-1) 

The protocol added an `ActionReceiptV2::refund_to` field and a `promise_set_refund_to` host function precisely to let a caller override this and route refunds to the real payer instead of the predecessor: [3](#0-2) [4](#0-3) 

That mechanism is used by contract-generated receipts (via `set_refund_to` in `receipt_manager.rs`) but `apply_delegate_action` never populates `refund_to` on the receipt it builds for the delegate action's inner actions — it still constructs a plain V1 `ActionReceipt`: [5](#0-4) 

This is a known, documented limitation of the protocol design: [6](#0-5) 

### Impact Explanation
A malicious account (the meta-transaction "sender") can craft a `DelegateAction` with an inner action that has an attached deposit but is guaranteed to fail on the receiver (e.g., calling a non-existent method, or a method that always panics/reverts). If a relayer submits this as a meta-transaction (paying the deposit and gas), the deposit is refunded to the sender's account instead of being returned to the relayer who paid it — a concrete unauthorized transfer of value from the relayer to the malicious sender via the on-chain state transition, not merely an off-chain trust issue. This directly parallels the referenced report's bug class: a fee/cost obligation that is supposed to fall on one party is silently redirected to another party by using an alternate code path (here, `Delegate` actions instead of a direct transaction) that lacks the fix (`refund_to`) already implemented and available elsewhere in the codebase.

### Likelihood Explanation
This is reachable with a single signed transaction/meta-transaction from any account acting as sender, requiring only that some relayer (which could be a naive/automated open relayer service) submits the crafted `DelegateAction`. No validator or node compromise is needed. The severity depends on relayer trust models, but any general-purpose or automated relayer accepting third-party `DelegateAction`s is exposed, and the code/documentation both flag this as a real, currently-unmitigated behavior for the `Delegate`/`DelegateV2` action path specifically (as opposed to contract-generated receipts, which already have the `refund_to` fix available).

### Recommendation
Set `refund_to` on the receipt created in `apply_delegate_action` to the relayer (`action_receipt.signer_id()`) when building the `ActionReceiptV2` for the delegate action's inner actions, mirroring how `promise_set_refund_to`/`receipt_manager::set_refund_to` already redirects refunds for contract-created receipts. This ensures deposit refunds for failed inner actions in a meta-transaction return to the party that actually paid (the relayer) rather than to the `DelegateAction` sender.

### Proof of Concept
1. Sender "Alice" (attacker) constructs a `DelegateAction` with `receiver_id` = some contract, and an inner `FunctionCall` action with `method_name` set to a non-existent method and a non-zero `deposit`.
2. Alice signs the `SignedDelegateAction` and gives it to a relayer, who wraps it in a `Delegate` action inside a transaction that the relayer signs and pays for (see `meta_tx` helper for the standard construction flow): [7](#0-6) 
3. `apply_delegate_action` runs on Alice's shard, creating the inner receipt with `predecessor_id = Alice`, `signer_id = relayer` (who paid), but no `refund_to`: [5](#0-4) 
4. The inner `FunctionCall` fails on the receiver shard because the method doesn't exist. `refund_unspent_gas_and_deposits` generates a deposit refund receipt sent to `balance_refund_receiver()`, which resolves to the predecessor `Alice`, not the relayer.
5. Alice's account balance increases by the deposit amount that the relayer paid, while the relayer's balance decreases by that same deposit — an unauthorized transfer of value from relayer to Alice, contradicting the intended "relayer pays / gets refunded on failure" model described in `docs/architecture/how/meta-tx.md`.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```

    /// Wrap the given actions in a delegate action and execute them.
    ///
    /// The signer signs the delegate action to be sent to the receiver. The
    /// relayer packs that in a transaction and signs it .
    fn meta_tx(
        &self,
        signer_id: AccountId,
        receiver_id: AccountId,
        relayer_id: AccountId,
        actions: Vec<Action>,
    ) -> Result<FinalExecutionOutcomeView, CommitError> {
        let inner_signer = create_user_test_signer(&signer_id);
        let user_nonce = self
            .get_access_key(&signer_id, &inner_signer.public_key())
            .expect("failed reading user's nonce for access key")
            .nonce;
        let delegate_action = DelegateAction {
            sender_id: signer_id.clone(),
            receiver_id,
            actions: actions
                .into_iter()
                .map(|action| NonDelegateAction::try_from(action).unwrap())
                .collect(),
            nonce: user_nonce + 1,
            max_block_height: 100,
            public_key: inner_signer.public_key(),
        };
        let signature = inner_signer.sign(delegate_action.get_nep461_hash().as_bytes());
        let signed_delegate_action = SignedDelegateAction { delegate_action, signature };

        self.sign_and_commit_actions(
            relayer_id,
            signer_id,
            vec![Action::Delegate(Box::new(signed_delegate_action))],
        )
    }
