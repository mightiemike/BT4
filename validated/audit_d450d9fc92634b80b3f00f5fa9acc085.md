### Title
Divergent global-agreement threshold rounding lets signers disagree on the active protocol version / burn view / current-miner state machine - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
`GlobalStateEvaluator::reached_agreement` (used by `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and `determine_global_state`) computes the 70% weight threshold with **floor** division, while `NakamotoBlockHeader::compute_voting_weight_threshold` (used to verify a block's actual signer-signature weight) computes the same nominal threshold with **ceiling** division. Both derive from the same constant, `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD`, but the rounding direction differs, so for certain `total_weight` values the two "≥70%" checks disagree by exactly one unit of weight.

### Finding Description
`reached_agreement` in `libsigner/src/v0/signer_state.rs`: [1](#0-0) 
computes:
```
vote_weight >= (total_weight * THRESHOLD) / 10   // integer division => floor
```

`NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs`: [2](#0-1) 
computes:
```
ceil((total_weight * THRESHOLD) / 10)
```
and this ceiling threshold is what `verify_signer_signatures` (the code that validates whether a Nakamoto block carries enough signer weight to be a valid block) enforces: [3](#0-2) 

Example with `THRESHOLD = 7` (70%) and `total_weight = 13`:
- `total_weight * THRESHOLD = 91`
- `reached_agreement` floor threshold = `91 / 10 = 9`
- `compute_voting_weight_threshold` ceiling threshold = `9 + 1 = 10` (since `91 % 10 != 0`)

So a signer whose accumulated agreement weight reaches exactly `9` is told by `reached_agreement` that the 70% supermajority has been reached (used for `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and the `SignerStateMachine` picked by `determine_global_state`), while the exact same weight distribution is *not* sufficient under `compute_voting_weight_threshold`'s stricter (ceiling) bound used to accept an actual block's signature set.

This is not the exact scenario in the external report, but it is the same bug class: an equality/threshold gate is evaluated against the wrong rounding rule (an "off-by-a-unit" boundary condition), analogous to `amount == tokenClaim` vs `amount == totalClaimed` — the check silently uses a looser/tighter bound than the canonical one, producing disagreement between two consumers of "the same" 70% concept.

### Impact Explanation
`determine_global_state` decides the *global* signer-set view (current miner, burn block view, active protocol version, tx replay set) that individual signers use to drive their local decisions (e.g., which tenure/miner they consider canonical, when to allow tenure-extend, etc.), separate from the strict cryptographic block-signature threshold enforced on-chain via `verify_signer_signatures`. Because the two thresholds are computed differently, a minority-sized set of signers (spanning the floor/ceiling gap) can cause `GlobalStateEvaluator` on one signer to declare "global agreement reached" for a burn view/current-miner/protocol version that the chain's actual block-acceptance logic would not (yet) treat as having reached the 70% signature bar. Signers operating on this premature/erroneous global-state view can diverge from signers who have not (or never) reach the same conclusion, producing temporary disagreement in which tenure/miner is treated as canonical among signers — a signer-side agreement/disagreement split bounded to the affected reward cycle's weight tally. This matches the "minority-triggerable signer weight ... static-validation divergence, temporary tip disagreement" High-severity class.

### Likelihood Explanation
The trigger condition requires only that `total_weight * 7 mod 10 != 0` (i.e., total signer weight not a multiple of 10 when scaled by 7), which is common for realistic signer set sizes/weights, and that the aggregated weight for a given update value lands exactly at the floor threshold. No majority collusion is needed — any subset of signers whose combined weight equals the floor bound (but not the ceiling bound) triggers the divergence purely through normal message propagation timing, making this a plausible, low-effort divergence rather than a contrived edge case.

### Recommendation
Unify the threshold computation: have `GlobalStateEvaluator::reached_agreement` (and `reached_disagreement`) call the same `NakamotoBlockHeader::compute_voting_weight_threshold` (or an equivalently ceiling-rounded shared helper) used for on-chain block signature verification, rather than maintaining a separately-implemented floor-rounded formula. Add a regression test asserting `reached_agreement(weight)` and `compute_voting_weight_threshold(total_weight) <= weight` agree for all `total_weight` in a swept range.

### Proof of Concept
1. Set up a signer set with `total_weight = 13` and `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`.
2. Have signers whose combined weight sums to `9` submit identical `StateMachineUpdate`s (e.g., agreeing on the same burn view / current miner) to a `GlobalStateEvaluator`.
3. Call `determine_global_burn_view()` / `determine_global_state()` — observe it returns `Some(..)`, i.e., `reached_agreement(9)` is `true` since `floor(13*7/10) = 9`.
4. Separately, construct/verify a Nakamoto block whose `signer_signature` accumulates the same `9` units of weight and pass it to `verify_signer_signatures` with `total_weight = 13` — observe it returns `Err(InvalidStacksBlock("Not enough signatures..."))` since `compute_voting_weight_threshold(13) = 10 > 9`.
5. This demonstrates that "70% agreement" as computed by the global state evaluator and "70% agreement" as enforced for block acceptance disagree at the same weight value, confirming the rounding-direction mismatch.

```rust
    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
```
