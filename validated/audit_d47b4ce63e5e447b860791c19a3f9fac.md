Based on my analysis, I found a genuine implicit/unenforced state-transition bug in the L1 handler transaction lifecycle, reachable purely by observing on-chain L1 events (which any unprivileged party can trigger by simply sending/consuming/cancelling L1→L2 messages on the L1 bridge contract — the "L1 message sender" role explicitly allowed by scope).

### Title
Implicit and unenforced state transitions in `TransactionRecord` allow a `Committed` L1 handler transaction to be silently downgraded to `Consumed`/`CancellationStartedOnL2` - (File: crates/apollo_l1_events/src/transaction_record.rs)

### Summary
`TransactionRecord::state` is a `TransactionState` enum meant to represent an authoritative, one-directional lifecycle (`Pending → Committed/Rejected/CancellationStartedOnL2/Consumed → ...`). However, several mutator methods (`mark_consumed`, `mark_cancellation_request`) unconditionally overwrite `self.state` without checking or enforcing which transitions are legal from the current state, mirroring the analog report's core issue: state transitions are implicit, derived from ad-hoc boolean flags (`committed`, `rejected`) rather than being validated against the state machine itself.

### Finding Description
`mark_consumed` sets `self.state = TransactionState::Consumed` unconditionally, even when the transaction is already `Committed`: [1](#0-0) 

Likewise, `mark_cancellation_request` decides whether to transition into `CancellationStartedOnL2` using the *state-derived* method `is_committed()` (`matches!(self.state, TransactionState::Committed)`) rather than the persistent boolean flag `self.committed`: [2](#0-1) [3](#0-2) 

Because `mark_consumed` can overwrite `state` from `Committed` to `Consumed` (this is entirely plausible operationally: an L1→L2 message is "consumed" on L1 shortly after/around the time the corresponding L2 tx is included in a block), the derived `is_committed()` check becomes `false` for a transaction that was, in fact, committed. The `committed: bool` flag (set permanently in `mark_committed`) is the real source of truth, but it is not consulted uniformly — `is_committed()`, `is_validatable()`, and `mark_cancellation_request` all key off the mutable `state` field instead: [4](#0-3) 

The comment on `mark_consumed` itself flags this as unresolved ("`TODO(guyn): check if this situation should be an error`"), which corroborates that these transitions are not deliberately enforced but only implicit side effects of call order — exactly the class of bug described in the external report.

Sequence to trigger from an unprivileged L1 message stream:
1. L1 event `LogMessageToL2` creates the L1 handler tx record (`Pending`).
2. Sequencer proposes/validates and commits the tx in a block → `mark_committed()` sets `state = Committed`, `committed = true`.
3. L1 event `ConsumedMessageToL2` for the same tx arrives (a very ordinary occurrence, since consumption on L1 typically follows or interleaves with L2 commitment) → `consume_tx` → `mark_consumed()` overwrites `state = Consumed` (the "committed" branch only logs a debug message; it does not skip the state overwrite): [5](#0-4) 
4. A subsequent L1 event `MessageToL2CancellationStarted` for the same hash arrives → `request_cancellation` → `mark_cancellation_request` checks `is_committed()`, which is now `false` (state is `Consumed`, not `Committed`) → the transition proceeds and **overwrites `state = CancellationStartedOnL2`** for a transaction that was already committed on L2.
5. In `TransactionManager::snapshot()`, this transaction is now (incorrectly) reported under `cancellation_started_on_l2` instead of `committed`: [6](#0-5) 
6. `update_time_based_state` will not further transition it to `CancelledOnL2` because it early-returns based on the boolean `committed` flag (`if self.committed { return; }`), so the record is now permanently stuck in the wrong state (`CancellationStartedOnL2`), diverging from the flag-based ground truth: [7](#0-6) 

### Impact Explanation
This mislabels a permanently, irrevocably committed L2 transaction as being in cancellation/consumed limbo purely within the `apollo_l1_events`/`TransactionManager` bookkeeping structures used by the batcher's `ProposeTransactionProvider`/`ValidateTransactionProvider` to decide L1-handler proposability and validation results (`is_proposable`, `is_validatable`, `validate_tx`'s `AlreadyIncludedOnL2` vs other statuses). However, `is_proposable()` gates strictly on `state == Pending`, so this specific corrupted terminal state (`Consumed`/`CancellationStartedOnL2`) does not by itself re-enable re-proposal or double-execution of the L1 handler transaction — the on-chain committed state (state root, receipts) is unaffected. The observable damage is confined to the L1 events provider's internal snapshot/monitoring view and possibly incorrect `ValidationStatus` classification returned by `validate_tx` for peers validating a re-proposed block containing the same tx hash (it would erroneously report the tx via the `_ => unreachable!()` branch in `validate_tx`, since `record.state` may now be a variant that branch doesn't expect for post-commit exclusion, e.g., `CancellationStartedOnL2` is not handled in the `!is_validatable()` match and would hit `unreachable!()`, causing a **panic in the batcher during block validation**): [8](#0-7) 

A panic during `validate_tx` (invoked from `ValidateTransactionProvider::get_txs` on the honest validation path for a block containing this transaction hash) would crash/abort the batcher process handling that validation — a service-unavailability outcome, not merely a cosmetic reporting error, and reachable purely through ordinary/adversarial L1 message traffic (no privileged role required).

### Likelihood Explanation
The precondition (an L1 handler tx being committed, then later observed as consumed, then observed with a cancellation-start event) is a plausible ordering of real L1 events that any external party interacting with the L1→L2 messaging bridge can induce or that occurs naturally under network/timing skew between the L1 event scraper and the sequencer's block production, without needing any privileged key. The exact panic path (`unreachable!()` in `validate_tx`) requires the extra step of a cancellation-request event racing after consumption/commitment, which is a narrower but still attacker-triggerable ordering via the bridge contract.

### Recommendation
Replace implicit, ad-hoc, flag-driven transitions with an explicit state-transition function that validates `(current_state, event) -> next_state` and rejects/ignores invalid transitions (e.g., no transition should be allowed out of `Committed` except no-ops), instead of having each `mark_*` method blindly overwrite `state`. Use the single source of truth (the `state` enum) consistently everywhere instead of maintaining parallel booleans (`committed`, `rejected`) that can desynchronize from `state`. Extend the `validate_tx` match in `transaction_manager.rs` to exhaustively handle all `TransactionState` variants instead of relying on `unreachable!()`.

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn consume_tx(
        &mut self,
        tx_hash: TransactionHash,
        consumed_at: BlockTimestamp,
        unix_now: u64,
    ) -> Result<(), BlockTimestamp> {
        self.clear_old_tx_from_consumed_queue(unix_now);

        let Some(record) = self.records.get(&tx_hash) else {
            debug!(
                "Attempted to consume an unknown transaction: {tx_hash}. This can happen if the \
                 transaction was too old to be scraped (e.g. it was created before we started \
                 scraping)."
            );
            return Ok(());
        };

        // Double consumption is a bug.
        if let Some(previously_consumed_at) = record.get_consumed_at_timestamp() {
            return Err(previously_consumed_at);
        }

        // Mark the transaction as consumed.
        self.with_record(tx_hash, |record| record.mark_consumed(consumed_at));
        Ok(())
    }

    pub(crate) fn snapshot(&self) -> TransactionManagerSnapshot {
        let mut snapshot = TransactionManagerSnapshot::default();

                    snapshot.rejected.push(tx_hash);

                        snapshot.rejected_staged.push(tx_hash);
                    }

                TransactionState::Committed => {
                    snapshot.committed.push(tx_hash);
