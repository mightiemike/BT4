### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash`, letting replay/verify tooling accept a wrong state root as matching - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by both the chunk executor's replay-verification path and the `db-tool replay-on-archive` CLI to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` recorded in the transaction accumulator. It compares status, gas, write-set hash, and event root hash, but it never compares `state_checkpoint_hash` (or the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields). This mirrors the report's core pattern — "the code that is supposed to guarantee an exact match between what was promised and what was actually produced does not check every relevant field" — except here the un-checked field is a state-commitment root rather than a token amount.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and checks only:
- transaction status
- gas used
- `write_set_hash` against `txn_info.state_change_hash()`
- `event_root_hash` against `txn_info.event_root_hash()`

There is an explicit TODO in the code acknowledging the gap: [2](#0-1) 

`state_checkpoint_hash` is the field on `TransactionInfo` that commits to the Sparse/Jellyfish Merkle root of the entire global state after the checkpoint transaction — it is the authenticated proof-bearing value that lets a verifier confirm the whole ledger's state matches what consensus committed. This function is invoked from two verification-critical call sites:

1. `storage/db-tool/src/replay_on_archive.rs`, inside `execute_and_verify`, which drives the `replay-verify` CI pipeline that gates protocol/VM upgrades by replaying historical mainnet transactions and asserting the output matches the archived, signed `TransactionInfo`: [3](#0-2) 

2. `execution/executor/src/chunk_executor/mod.rs`, used in the chunk executor's `VerifyExecutionMode` replay path (used for backup/fast-sync verification flows).

Because `ensure_match_transaction_info` never checks `state_checkpoint_hash`, a re-executed chunk whose write-set hash, event hash, gas, and status all match the authenticated `TransactionInfo` — but whose *resulting global state Merkle root* diverges (e.g., due to a state-application bug, non-deterministic VM behavior, or a bug in `write_set` application at storage-commit time) — will be reported as a successful, verified replay.

### Impact Explanation
This breaks the proof-binding invariant that authenticated `TransactionInfo` is supposed to guarantee: correctness of the entire post-transaction ledger state, not just the transaction's own write set and events. The state Merkle root check is the actual proof clients and light clients rely on (via `TransactionInfoListWithProof::verify`, which hashes the whole `TransactionInfo` including `state_checkpoint_hash`, per [4](#0-3) ). If a full node's local storage/state-tree construction diverges from the canonical result while write-set and event hashes coincidentally still hash-match (or if a bug affects only how prior-state + write-set is folded into the new Merkle root, not the write set's own hash), the replay-verify tool and the chunk-executor's verify-execution mode will not detect the divergence. This directly undermines the "replay/restore paths must not reinterpret committed data into a different ledger state" invariant, and could let a hard-fork-only or storage-application bug slip through the very tooling (`replay-verify` CI) designed to catch state-root divergence before a release ships.

### Likelihood Explanation
This is not an attacker-triggered exploit in the traditional sense (no external adversary directly controls the mismatch), but it is a real, locally-provable code defect: the verification function's design leaves an explicit, developer-acknowledged blind spot on the single most important committed value (the state root) in exactly the tool intended to catch state-root regressions. Any bug elsewhere in write-set-to-state application (storage commit, JMT construction, hot-state merge) that preserves the write set's own hash and event hashes but changes the resulting Merkle root would go undetected by CI or by the chunk executor's verify-execution path.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the actual computed values for the corresponding version, failing the replay when any of these do not match the authenticated `TransactionInfo`. This requires plumbing the locally computed checkpoint hash(es) into the comparator at both call sites (`replay_on_archive.rs` and the chunk executor's replay verifier).

### Proof of Concept
Not independently reproducible as a live exploit from this analysis alone — the finding is a code-level proof/audit gap rather than a directly triggerable transaction-level exploit. The self-contained root cause is verifiable by inspection: `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) has no comparison involving `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`, while `TransactionInfo`'s own hash (used in accumulator/Merkle proofs) does include these fields, per its `builder_v0`/`builder_v1` constructors at [5](#0-4) . Constructing a concrete PoC (e.g., a modified storage commit path that produces a wrong state root but identical write-set hash) would require executing code in a live Devin session, which is outside the scope of this read-only analysis.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
