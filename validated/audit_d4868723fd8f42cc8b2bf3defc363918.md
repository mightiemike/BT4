### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.fromAccounts`/`toAccounts` arrays enables gas/CPU griefing and DoS of legitimate freeze/unfreeze operations - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
When the `AllowDelegateOptimization` chain parameter is not enabled, java-tron falls back to a legacy resource-delegation indexing scheme that stores, for every account, a `repeated` protobuf list of counter-party addresses (`toAccounts` for delegators, `fromAccounts` for receivers) inside `DelegatedResourceAccountIndexCapsule`. Anyone can force entries into another account's `fromAccounts` list simply by delegating a minimal amount of frozen balance to that address via `FreezeBalanceContract` — no consent from the receiver is required. This is structurally identical to the RealWagmi `tokenIdToBorrowingKeys` bug: an unprivileged actor can pack a per-victim array that legitimate protocol code must scan/rebuild on every subsequent state-changing operation.

### Finding Description
`FreezeBalanceActuator.delegateResource()` (legacy branch, `dynamicPropertiesStore.supportAllowDelegateOptimization()==false`) inserts the delegator into the receiver's `fromAccountsList` unconditionally, with only a linear `contains()` duplicate check and no bound on the list size: [1](#0-0) 

Crucially, the `receiverAddress` is fully attacker-controlled and does not need to belong to the caller — anyone can freeze even the `MINIMUM` amount of TRX and delegate it to an arbitrary victim address, forcing an entry into that victim's `fromAccountsList` (and symmetrically into the delegator's own `toAccountsList`, but the delegator controls that cost themselves; the victim's list growth is imposed on them without consent).

`DelegatedResourceAccountIndexCapsule.addFromAccount`/`addToAccount` place no cap on list length: [2](#0-1) 

Every subsequent `UnfreezeBalanceActuator.execute()` call that fully unfreezes a delegation to/from the packed account must copy the entire list into an `ArrayList`, perform an O(n) linear `remove()`, and then rebuild/re-serialize the whole protobuf `repeated` field via `setAllToAccounts`/`setAllFromAccounts` (which internally does `clearFromAccounts().addAllFromAccounts(...)`): [3](#0-2) 

Unlike an EVM environment where computation cost is explicitly gas-metered per operation (making the original RealWagmi bug about the attacker forcing victims to pay disproportionate gas), java-tron's system contracts (`FreezeBalanceContract`/`UnfreezeBalanceContract`) charge a fixed bandwidth/fee cost independent of the size of the `fromAccounts`/`toAccounts` list being scanned and rewritten. This means the cost of processing an attacker-inflated list is not priced into the transaction fee at all — it is "underpriced public work": an attacker pays a fixed, minimal cost per injected entry (freezing the protocol minimum amount), while every legitimate account interaction later touching the packed list incurs unbounded, unpriced CPU/serialization cost, and the resulting larger `DelegatedResourceAccountIndex` value must be read/written/serialized to the database on every future freeze/unfreeze/delegate call for that address.

### Impact Explanation
This is an "underpriced public work" / DoS-style vulnerability:
- An unprivileged attacker can force arbitrarily large `fromAccounts` or `toAccounts` lists onto a targeted victim account for negligible, fixed cost (minimum freeze amount plus fixed transaction fee), with no requirement for the victim's consent.
- Every subsequent legitimate operation on the victim's delegated resources (`FreezeBalanceActuator.delegateResource`'s `contains()` duplicate check, `UnfreezeBalanceActuator`'s array copy/remove/rebuild) becomes progressively more expensive in CPU time and DB I/O without any corresponding increase in the transaction fee charged, since java-tron system contracts don't scale fees with loop iterations the way EVM gas does.
- This degrades node performance for processing transactions touching the victim account, and in the worst case could push transaction processing time high enough to affect block production/validation timing for blocks containing such transactions — a form of resource-exhaustion DoS against a specific, targeted account rather than a generic griefing of the whole network.
- This does not directly lock/steal funds (unlike the original Sherlock report, where the borrow itself became stuck), because unfreezing eventually succeeds once processed; the impact here is CPU/computation griefing and unpredictable processing latency for the targeted account's future freeze/delegate/unfreeze transactions.

### Likelihood Explanation
Exploitability depends on the `AllowDelegateOptimization` proposal not yet being active on the target chain/network (it is a committee-governed hard-fork switch, not a hardcoded default in the codebase, per `DynamicPropertiesStore`/`ProposalUtil` references). On any chain where this optimization proposal has not passed — which would include forked or private/consortium deployments and could include periods before the proposal was activated on mainnet — the legacy array-based code path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` remains fully reachable by any unprivileged account, and the attack costs only the minimum freeze amount plus standard transaction fees per injected entry.

### Recommendation
- Deprecate/remove the legacy array-based `DelegatedResourceAccountIndexCapsule.fromAccounts`/`toAccounts` code path in `FreezeBalanceActuator` and `UnfreezeBalanceActuator`, forcing all delegation indexing through the already-existing prefix-keyed `DelegatedResourceAccountIndexStore.delegate()/unDelegate()` scheme (which stores each relation under its own `FROM_PREFIX+from+to` / `TO_PREFIX+to+from` key, avoiding any per-account unbounded list).
- If backward compatibility with the legacy scheme must be retained, cap the maximum number of entries a single account's `fromAccounts`/`toAccounts` list can hold, and/or price the delegate/unfreeze transaction fee proportional to the size of the list being scanned/rebuilt.

### Proof of Concept
1. On a network where `AllowDelegateOptimization` has not been enabled via committee proposal, an attacker generates N throwaway accounts.
2. From each throwaway account, the attacker sends a `FreezeBalanceContract` transaction freezing the protocol minimum amount and delegating it to a single victim address (`receiver_address = victim`), reachable via `FreezeBalanceActuator.delegateResource()`.
3. Each call appends the attacker's throwaway address into the victim's `DelegatedResourceAccountIndexCapsule.fromAccounts` list (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:340-344`), with no size limit enforced.
4. After N such transactions, the victim's `fromAccounts` list contains N entries.
5. Any subsequent `UnfreezeBalanceContract` transaction that fully unfreezes a delegation involving the victim account triggers the O(n) copy/scan/rebuild in `UnfreezeBalanceActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java:174-182`), imposing unbounded, unpriced processing cost on the victim's transaction and the node processing it, for an attack cost that scales only with the fixed minimum-freeze-and-fee cost per entry.
