### Title
Token exchange accepts a session token for one shop while requesting an access token for a different, attacker-supplied `shop` - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`tokenExchange()` decodes the caller's session token only to validate its signature/expiry, then discards the decoded payload and uses a separately supplied `shop` string parameter to build the `/admin/oauth/access_token` request and the resulting `Session`. There is no check that the `shop` argument matches the `dest`/`iss` claim embedded in the verified session token.

### Finding Description
In `tokenExchange`, the session token is decoded purely for signature validation, and its result is dropped: [1](#0-0) 

The `shop` used for the actual exchange call and for building the returned `Session` (which is later stored under a `shop`/`sub`-derived id via `getJwtSessionId`/`getOfflineId`) comes exclusively from the `shop` function argument, sanitized only for format: [2](#0-1) 

The documented integration pattern explicitly sources this `shop` value from `req.query.shop`, a value fully controlled by the requester, independent of the session token's `dest` claim: [3](#0-2) 

This mirrors the ENS `NameWrapper` root cause: a privileged "child" property (here, the shop-boundness of a validly-signed session token) is supposed to constrain what the "parent" operation (the exchange/rewrap) can do, but the enforcing code path (`tokenExchange`) never re-checks that constraint — it only validates the token's cryptographic validity, not its binding to the shop being acted upon. Framework-level callers (`shopify-app-express`'s `performTokenExchange`, `shopify-app-remix`/`shopify-app-react-router`'s `token-exchange.ts` strategies) mitigate this correctly by deriving `shop` from the decoded token's `dest` claim rather than from user input, e.g.: [4](#0-3) [5](#0-4) 

However, `shopify.auth.tokenExchange` itself — the library-level primitive documented and exported for direct use — enforces no such binding, so any app that follows the documented pattern (taking `shop` from a query string rather than from the decoded token) is vulnerable.

### Impact Explanation
If an app built directly against `shopify.auth.tokenExchange` (following the documented usage) accepts `shop` from the URL/query string rather than deriving it from the verified token's `dest` claim, an attacker holding a valid session token for shop A (their own installed shop) could pass `shop=B.myshopify.com` and cause the app to call `https://B.myshopify.com/admin/oauth/access_token` with `subject_token` = the attacker's own token. Whether this succeeds depends entirely on Shopify's OAuth server-side enforcement (out of scope for this repo), but the shopify-app-js library itself performs no client-side validation preventing shop/token mismatch, creating a cross-tenant risk surface and violating the principle that a session token should only ever be exchangeable for the shop it was issued for.

### Likelihood Explanation
Likelihood is moderate-to-low: exploitability depends on (1) an app author following the documented pattern of sourcing `shop` from query params instead of the token payload (the official framework packages — express/remix/react-router — do this correctly internally), and (2) Shopify's backend token-exchange endpoint not independently rejecting a shop/token mismatch. The library provides no defense-in-depth against this misuse despite it being the documented usage pattern.

### Recommendation
In `tokenExchange()`, decode the session token, extract the shop from its `dest`/`iss` claim, and require that it match (or exclusively use) the caller-supplied `shop`, throwing an `InvalidOAuthError`/`InvalidJwtError` on mismatch — mirroring the reasoning applied to the ENS `wrap` fix ("check old/authoritative state even when re-establishing trust"). Concretely:
```ts
const payload = await decodeSessionToken(config)(sessionToken);
const tokenShop = sanitizeShop(config)(new URL(payload.dest).hostname, true)!;
if (tokenShop !== cleanShop) {
  throw new ShopifyErrors.InvalidJwtError('Session token shop does not match requested shop');
}
```
Update the documentation example to no longer suggest sourcing `shop` from `req.query.shop` independently of the token.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and obtains a valid App Bridge session token (`dest: https://shop-a.myshopify.com`).
2. App backend implements the documented pattern: `shop = sanitizeShop(req.query.shop)` and calls `shopify.auth.tokenExchange({ shop, sessionToken, requestedTokenType })`.
3. Attacker sends `GET /auth?shop=shop-b.myshopify.com` with `Authorization: Bearer <shop-a's session token>`.
4. `tokenExchange` decodes the token only for validity (discarding `dest`), builds the exchange request against `https://shop-b.myshopify.com/admin/oauth/access_token` using `subject_token` = the shop-a token, and constructs/stores a `Session` keyed to `shop-b`.
5. No code path in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` rejects the shop/token mismatch. [1](#0-0)
