### Title
Stuck Pending Inbounds Cannot Be Reverted if UniversalTx Key Collision Occurs - ([File: x/uexecutor/keeper/admin_revert.go])

### Summary
The `RevertStuckInbound` function, designed as an administrative escape hatch for stuck inbound transactions, contains a logic error that prevents recovery if a `UniversalTx` (UTX) record already exists for the same key. This creates a conflicting state where a ballot is `EXPIRED` (requiring a revert), but the recovery function reverts because it expects the UTX to not exist yet.

### Finding Description
In Push Chain, inbound transactions are voted on by Universal Validators. If a ballot for an inbound expires without reaching quorum, it becomes "stuck." The protocol provides an admin function `RevertStuckInbound` to manually trigger a refund (revert) for these stuck funds.

The vulnerability arises from the following check in `RevertStuckInbound`: [1](#0-0) 

This check explicitly reverts if a `UniversalTx` already exists for the derived `universalTxKey`. However, the `universalTxKey` is derived from `sha256(sourceChain:txHash:logIndex)`, which is the same key used during the normal voting process.

In the normal `VoteInbound` flow, a `UniversalTx` is created immediately upon ballot finalization: [2](#0-1) 

If an inbound ballot was previously driven to a terminal state (e.g., via `MarkBallotFinalized` or a race condition where some validators saw it as `PASSED` while others saw it as `EXPIRED`), or if a previous attempt to process the inbound created a UTX but failed to complete execution, the `UniversalTx` record will persist. 

When the admin attempts to use `RevertStuckInbound` to recover the funds associated with that `EXPIRED` ballot, the function will see the existing UTX and revert with "universal tx already exists for this inbound," making it impossible to attach the `INBOUND_REVERT` outbound required to release the funds. This is analogous to the external report where a recovery function reverts due to a state check that fails to account for the actual state of the object being recovered.

### Impact Explanation
This logic error disables the primary administrative mechanism for recovering user funds stuck in `EXPIRED` inbound ballots whenever a UTX record already exists. This leads to permanent freezing of user funds in the gateway contracts for those specific transactions, as the "escape hatch" is logically blocked.

### Likelihood Explanation
The likelihood is medium. While ballots typically either pass or expire cleanly, drift in validator eligibility or manual finalization by admins (using `MarkBallotFinalized`) can result in a state where a UTX exists but the ballot is `EXPIRED`. In these recovery scenarios, the admin is logically barred from completing the recovery.

### Recommendation
Modify `RevertStuckInbound` to handle existing `UniversalTx` records. Instead of reverting when a UTX exists, the function should:
1. Verify if the existing UTX already has a successful `PcTx` or an active `OutboundTx`.
2. If it is truly stuck (e.g., no successful execution), append the `INBOUND_REVERT` outbound to the *existing* UTX rather than attempting to create a new one.

### Proof of Concept
1. A user initiates an inbound transaction on an external chain.
2. Universal Validators vote, but due to network issues, the ballot does not reach quorum.
3. An admin manually marks the ballot as `PASSED` to try and force execution, which creates the `UniversalTx` record.
4. The execution fails (e.g., due to `NormalizeForTxType` failure), and the admin subsequently drives the ballot to `EXPIRED` using `RecomputeBallotQuorum` after validator set changes.
5. The admin now calls `RevertStuckInbound` to refund the user.
6. `RevertStuckInbound` checks `HasUniversalTx`, finds the record created in step 3, and reverts with `ErrInvalidRequest`, preventing the refund.
