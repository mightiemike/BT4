### Title
Unchecked `storeSession()` return value causes silent session persistence failure in OAuth callback and token-exchange flows - ([File: packages/apps/shopify-app-express/src/auth/auth-callback.ts])

### Summary
The `SessionStorage` interface defines `storeSession()` as returning `Promise<boolean>`, explicitly documented as "returns `true` if successfully stored, `false` otherwise" [1](#0-0) . Every OAuth callback and token-exchange code path across `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` calls `storeSession()` and discards this boolean without any check, then unconditionally proceeds as though the session was durably persisted.

### Finding Description
This is the same bug class as the reported `Timelock::executeTransaction()` issue: an operation that can complete "successfully" from the caller's point of view (no thrown exception) while its actual side effect (persisting the queued/session data) silently fails, and the caller has no way to detect or react to that failure.

In `authCallback()` (shopify-app-express), after a valid OAuth callback is processed, the session is stored but the return value is ignored, and execution immediately continues to webhook registration, setting `res.locals.shopify.session`, and firing the `afterAuth` hook — all treating the session as persisted: [2](#0-1) 

The identical unchecked pattern exists in the Remix auth-code-flow callback handler: [3](#0-2) 

And in the token-exchange strategies (shared logic duplicated in shopify-app-express, shopify-app-remix, and shopify-app-react-router), where both the offline and online session stores are unchecked before the code proceeds to fire the `afterAuth` hook and mark the request as authenticated: [4](#0-3) [5](#0-4) 

Notably, several bundled `SessionStorage` implementations can genuinely return `false` (or silently no-op) on failure — e.g. `PrismaSessionStorage.storeSession` catches non-P2002 errors internally in some code paths and reference/example implementations return `false` on write errors, per the documented contract: [6](#0-5) 

Because none of the framework packages check this boolean, a failed write (DB connection blip, constraint violation, disk/quota error, etc.) is indistinguishable from a successful one to the rest of the OAuth/token-exchange pipeline.

### Impact Explanation
When `storeSession()` returns `false` (or otherwise fails to persist), the current request still treats the shop as authenticated (webhooks registered, `afterAuth` hook fired, response redirected as a successful install/login) even though no session was actually written to storage. On the very next request, session lookup (`loadSession`) will find nothing, forcing the merchant back into the OAuth/token-exchange flow. If the underlying storage failure is systemic (e.g., a persistent DB issue for a given shop), this produces a repeating authentication loop that never converges — a functional denial of service of the auth handler for that shop, while webhooks may already have been registered against a session that no longer exists in storage, and the `afterAuth` hook (which apps commonly use to provision shop-specific state) may run multiple times or against inconsistent state.

### Likelihood Explanation
This code path is reachable by any single merchant/customer performing the standard OAuth install or embedded app token-exchange flow — no privileged actor or secret leakage is required. Any transient storage failure (which is realistic for network-backed session stores like MySQL/Postgres/Mongo/Redis/DynamoDB under load or during failover) triggers the bug deterministically for that request.

### Recommendation
Check the boolean result of every `storeSession()` call in the OAuth callback and token-exchange flows (`auth-callback.ts`, `auth-code-flow.ts`, `token-exchange.ts` in all three framework packages, and `perform-token-exchange.ts`). On `false`, treat it as a hard failure: log/error, respond with a 5xx or re-driveable error instead of proceeding to register webhooks, set `res.locals.shopify.session`/return the session, or invoke `afterAuth`. This mirrors the fix pattern for the reported Timelock bug — do not treat an ambiguous/failed success signal as authoritative proof the operation (session persistence) took effect.

### Proof of Concept
1. Configure any `SessionStorage` implementation whose backing store can return `false` from `storeSession()` (or wrap a real implementation to force a `false` return, simulating a transient DB failure).
2. Initiate the OAuth install flow for a shop; let `api.auth.callback()` succeed normally.
3. Observe that `authCallback()` (or `handleAuthCallbackRequest`/`authenticate()` in the Remix/React Router strategies) ignores the `false` result of `storeSession()` and proceeds to register webhooks, set the authenticated session on the response, and invoke `afterAuth`.
4. On the immediately following request from the same shop, session lookup (`loadSession`) returns `undefined`/inactive, forcing the shop back into the OAuth/token-exchange flow — repeatable indefinitely while the underlying storage failure persists, without any error surfaced to the operator that the session was never actually saved.
