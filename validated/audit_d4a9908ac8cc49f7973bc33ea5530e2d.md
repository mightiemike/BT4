## Title
`receipt_filter_fn` panics on stale `GlobalContractDistribution` receipts after repeated resharding, permanently halting the shard's delayed-receipt drain - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
This finding is analogous in bug *class* to the Malt `stabilize()` report: an internal computation makes a strict, unchecked assumption ("this lookup can never fail / this value can never move backwards") about data whose invariants are actually broken by an external, evolving process (shard-layout resharding, analogous to Uniswap's un-reverting `priceCumulative`). When the assumption breaks, the internal code takes the "unwrap and crash" path instead of gracefully erroring, and because the crash happens deterministically on every honest node re-processing the same delayed queue, it manifests as a **transaction-triggered chain halt** rather than a single reverted call.

### Finding Description
`DelayedReceiptQueueWrapper::receipt_filter_fn` (used by `pop`/`peek_iter` to determine whether a receipt popped from the persistent delayed-receipt queue still belongs to the current shard after a resharding split) computes the receipt's shard with: [1](#0-0) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

Both calls are `.unwrap()`-ed, i.e. checked/panicking operations, on the assumption that a receipt admitted into the delayed queue under an old shard layout can always be re-mapped to a shard under a *later* shard layout. This mirrors Solidity's checked-math assumption in `MaltDataLab` that `priceCumulative` only ever increases. In near, the "external, unchecked-invariant producer" is the **dynamic resharding pipeline**: a `GlobalContractDistribution` receipt carries a `target_shard` fixed at creation time under shard layout N. If the receipt sits in the delayed queue (e.g. because the shard is fully compute-saturated) across **two or more** resharding events (N → N+1 → N+2), `receiver_shard_id(&shard_layout_N+2)` can fail to resolve the now-stale `target_shard`, because the current shard-layout-remapping logic was only verified/tested for a single resharding generation.

This has already been identified and reproduced by the nearcore test authors themselves: [2](#0-1) 

```rust
assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

// Step 4: Stop saturating. Let the delayed queue drain.
// If the vulnerability exists, processing the stale GlobalContractDistribution
// receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
// to remap the old target_shard after two resharding generations.
...
assert!(
    head_height >= drain_end,
    "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
    head_height,
    drain_end
);
```

This is functionally identical to the Malt bug pattern:
- Malt: `priceCumulative - maltPriceCumulativeLast` assumes monotonic growth guaranteed by an *external, differently-governed* system (Uniswap V2 pool arithmetic semantics); when that assumption breaks, Solidity 0.8's checked subtraction reverts, and the revert is unconditional — `stabilize()` can never succeed again.
- nearcore: `receiver_shard_id(&shard_layout).unwrap()` assumes a receipt's `target_shard` can always be remapped forward, an invariant that is only guaranteed for a single resharding step but is actually governed by the (separately evolving) dynamic-resharding subsystem; when the assumption breaks across two reshardings, `.unwrap()` panics, and the panic is unconditional on any node draining that receipt out of the delayed queue.

### Impact Explanation
Draining the delayed-receipt queue for `GlobalContractDistribution` receipts is mandatory, on-path work performed by `process_delayed_receipts` (`runtime/runtime/src/lib.rs`) every time the shard has spare compute budget; it is not something a chunk producer can simply skip. Because the panic is a pure function of on-chain state (the delayed queue contents plus the shard layout), **every honest validator that applies the chunk containing this receipt will panic identically**, which is a transaction/receipt-triggered halt of chunk (and therefore block) production for the affected shard — validators cannot make progress until the state is manually patched. This satisfies the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Reaching this bug requires: (1) deploying a global contract (any account can do this, unprivileged), whose deployment creates a `GlobalContractDistribution` receipt targeting the deployer's shard; (2) that shard undergoing dynamic resharding at least twice while the receipt remains queued (achievable by saturating the shard's compute budget with ordinary function calls so the receipt stays in the delayed queue across epoch boundaries, exactly as the reproduction test does). None of these steps require a malicious validator, network-layer manipulation, or privileged access — they are all achievable purely through submitted transactions plus normal protocol-driven resharding, which nearcore's own dynamic resharding feature can trigger organically as shards grow. The corresponding regression test in the repository demonstrates this is a concretely reachable, reproducible scenario, not a hypothetical one.

### Recommendation
Replace the `.unwrap()`s in `receipt_filter_fn` with fallible handling that treats an unmappable stale receipt as a defined, recoverable condition rather than a panic — e.g., fall back to `StorageError::StorageInconsistentState`, or (preferably) maintain enough shard-lineage history/resharding-generation mapping so `receiver_shard_id` can always resolve targets created under any prior shard layout still present in a not-yet-drained delayed queue. This is the same fix philosophy the Malt report recommended: don't let an assumption inherited from evolving/asymmetric external state produce an unconditional revert/panic in the consuming code path — make the failure explicit and recoverable, or ensure the invariant is actually preserved across all valid state transitions (multiple sequential reshardings).

### Proof of Concept
See the existing repository test, which is a full end-to-end reproduction: [3](#0-2) 

Steps: deploy a global contract from an account, saturate the account's shard's compute budget every block via `burn_gas_raw` calls so the `GlobalContractDistribution` receipt is pushed into (and remains in) the delayed queue, force two sequential shard splits on that shard via `DynamicReshardingConfig::force_split_shards`, then stop saturating and let the delayed queue drain — the drain calls `receipt_filter_fn`, which panics in `receiver_shard_id(&shard_layout).unwrap()` on the now doubly-stale `target_shard`, halting head-height progress (`head_height < drain_end` in the test assertion).

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
