## Finding

### Title
Malicious meta-transaction sender can steal a relayer's attached deposit via failed-receipt balance refunds - ([File: runtime/runtime/src/lib.rs])

### Summary
In NEP-366 meta transactions, the relayer pays for gas and any attached token deposit of the inner actions, but the deposit-refund path routes failed-receipt refunds to the receipt's `predecessor_id` (the meta-tx sender), not to the account that actually funded the deposit (the relayer). A malicious sender can construct inner actions that are certain to fail on the receiver's shard (e.g. a `FunctionCall` to a non-existent method/account) with a large attached deposit, causing the relayer to pay the deposit while the failure refund routes the value back to the sender instead of the relayer, resulting in unauthorized value transfer from the relayer to the sender.

### Finding Description
When a `DelegateAction` is unpacked on the sender's shard, `apply_delegate_action` builds a new `Receipt` whose `predecessor_id` is set to `sender_id` and forwards the relayer-funded inner actions to the receiver: [1](#0-0) 

As the code comment states explicitly, all costs (attached deposits and gas) for the inner actions were pre-paid by the relayer, but any deposit refund on failure is sent to the predecessor of the newly created receipt — i.e. the sender, not the relayer: [2](#0-1) 

On the receiver's shard, if the receipt's actions fail, `refund_unspent_gas_and_deposits` creates a balance-refund receipt addressed to `receipt.balance_refund_receiver()`: [3](#0-2) 

`balance_refund_receiver()` returns the receipt's `refund_to` if explicitly set by the caller via `promise_set_refund_to`, otherwise it defaults to `predecessor_id()`: [4](#0-3) 

Because meta-transaction inner-action receipts carry `predecessor_id = sender_id` (set in `apply_delegate_action`), and the sender never calls `promise_set_refund_to` for a receipt they don't control, any deposit refund on failure of the relayer-funded inner action goes to the sender. This exact economic hazard is explicitly acknowledged in the project's own architecture docs: [5](#0-4) 

The doc explicitly states: "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard," mirroring the Cooler.sol pattern where an unprivileged initiator (the meta-tx sender/borrower analog) can cause value paid by another unaware party (the relayer/lender analog) to be returned to the initiator instead.

### Impact Explanation
A malicious meta-transaction sender can repeatedly craft `SignedDelegateAction`s whose inner action (e.g. `FunctionCall` to a non-existent method, or one designed to trigger `LackBalanceForState`/method-not-found on the receiver) attaches a large deposit and is guaranteed to fail on the receiver's shard. If a relayer signs and submits such meta-transactions without independently simulating/dry-running the exact receiver-side outcome (which is explicitly called out as a required but easy-to-miss mitigation in the docs), the relayer pays the deposit out of its own balance while the resulting deposit-refund receipt credits the sender's account, not the relayer's. This is concrete unauthorized value movement: NEAR balance that the relayer funded ends up permanently transferred to the sender with no corresponding service delivered, and it can be repeated to drain a relayer.

### Likelihood Explanation
This requires only an unprivileged transaction signer acting as a meta-transaction sender, using nothing beyond currently-supported primitives (`DelegateAction`, ordinary `FunctionCall`/`Transfer` inner actions). It is reachable from a single submitted transaction (the relayer's wrapping transaction, triggered by an off-chain relay request from the malicious sender) and does not require any validator, network, or operator privilege. The severity is bounded by relayer trust models and off-chain safeguards (some relayers may simulate transactions first), but the on-chain protocol itself provides no restriction preventing this, and the docs confirm this is a known, currently-unmitigated gap in the protocol's refund routing for meta transactions.

### Recommendation
Route balance refunds for meta-transaction inner-action receipts to the relayer (the original transaction signer who funded the deposit) rather than to the `sender_id`/predecessor by default — e.g., have `apply_delegate_action` set `refund_to` on the spawned receipt to the relayer account, mirroring how gas refunds already go to the signer. Alternatively, require relayers to use `promise_set_refund_to`/dry-run simulation as a mandatory safeguard, and clearly surface this constraint at the protocol level (e.g. a config option demanding refunds default to the fee payer) rather than relying purely on relayer-side trust and documentation.

### Proof of Concept
1. Alice (malicious sender) has no balance and uses a relayer.
2. Alice constructs a `DelegateAction` with `receiver_id = Bob` (an account/contract) and a single inner `FunctionCall` action to a non-existent method on `Bob`, with a large `deposit` attached, following the pattern in `check_meta_tx_fn_call`/`meta_tx` helpers: [6](#0-5) 
3. The relayer signs a transaction wrapping this `SignedDelegateAction`, thereby prepaying the attached deposit and gas (as shown in `apply_delegate_action`'s comment on relayer prepayment): [2](#0-1) 
4. On Bob's shard, the `FunctionCall` fails (method not found). `refund_unspent_gas_and_deposits` issues a deposit-refund receipt to `receipt.balance_refund_receiver()`, which resolves to the receipt's `predecessor_id`, i.e., Alice — not the relayer who funded the deposit.
5. Alice's balance increases by the deposit amount that the relayer paid; the relayer's balance decreases with no service rendered, confirming unauthorized value transfer from relayer to sender.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```

```rust
    ///
    /// The signer signs the delegate action to be sent to the receiver. The
    /// relayer packs that in a transaction and signs it .
    fn meta_tx(
        &self,
        signer_id: AccountId,
        receiver_id: AccountId,
        relayer_id: AccountId,
        actions: Vec<Action>,
    ) -> Result<FinalExecutionOutcomeView, CommitError> {
        let inner_signer = create_user_test_signer(&signer_id);
        let user_nonce = self
            .get_access_key(&signer_id, &inner_signer.public_key())
            .expect("failed reading user's nonce for access key")
            .nonce;
        let delegate_action = DelegateAction {
            sender_id: signer_id.clone(),
            receiver_id,
            actions: actions
                .into_iter()
                .map(|action| NonDelegateAction::try_from(action).unwrap())
                .collect(),
            nonce: user_nonce + 1,
            max_block_height: 100,
            public_key: inner_signer.public_key(),
        };
        let signature = inner_signer.sign(delegate_action.get_nep461_hash().as_bytes());
        let signed_delegate_action = SignedDelegateAction { delegate_action, signature };

        self.sign_and_commit_actions(
            relayer_id,
            signer_id,
            vec![Action::Delegate(Box::new(signed_delegate_action))],
        )
    }
```
