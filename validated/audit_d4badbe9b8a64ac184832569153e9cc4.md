## Summary

The IBC report's bug class — logic that incorrectly requires an "OPEN"/live state before allowing a settlement action that must also succeed in a non-open state (so in-flight value doesn't get stranded) — has a concrete analog in Push Chain's outbound-creation path in `x/uexecutor`.

## Title
Disabling outbound for a destination chain after PRC20 burn/lock but before outbound persistence permanently strands protocol funds - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`BuildOutboundsFromReceipt` hard-requires `IsChainOutboundEnabled` to be `true` at the moment the outbound record is built from an already-executed EVM receipt. If the destination chain is disabled between the moment a user's payload execution emits a `UniversalTxOutbound` event on the `UNIVERSAL_GATEWAY_PC` contract (which already burns/locks the PRC20 on Push Chain) and the moment the Cosmos-side keeper builds the corresponding `OutboundTx`, the function returns a hard error instead of still recording the outbound (in a state other than the "enabled" state) so it can later be replayed, reverted, or refunded once the chain is re-enabled.

### Finding Description
`BuildOutboundsFromReceipt` [1](#0-0)  decodes the `UniversalTxOutbound` log emitted by `UNIVERSAL_GATEWAY_PC` — which is only emitted after the EVM-side burn/lock of the PRC20 asset has already occurred inside the same EVM call — and then gates outbound-record creation on `IsChainOutboundEnabled` for the destination chain. If disabled, it returns `fmt.Errorf("outbound is disabled for chain %s", event.ChainId)` and **discards the event entirely**: no `OutboundTx` is appended to the `UniversalTx`, no entry is written to `PendingOutbounds`, and no revert/refund path is triggered.

This function is invoked from `AttachOutboundsToExistingUniversalTx` [2](#0-1)  and `CreateUniversalTxFromReceiptIfOutbound` [3](#0-2) , both of which are called after the module-originated `DerivedEVMCall` that executed the user's `executeUniversalTx` and already committed the EVM state change (burn/escrow of PRC20). Unlike the ballot/outbound lifecycle documented for observed outbounds — where `PendingOutbounds` entries are deliberately never removed on ballot expiry precisely to avoid losing track of in-flight funds [4](#0-3)  — this disabled-chain path has no equivalent preservation: the record is dropped outright rather than being retained in a non-`PENDING` state (e.g., analogous to `ABORTED`) for later reconciliation.

This is the same bug class as the IBC report: an action that legitimately needs to succeed (or at least be durably recorded) *regardless of* the "open"/enabled state of the counterpart (channel / destination chain) is instead hard-gated on that state being live, with no fallback path.

### Impact Explanation
If a chain admin (a privileged, in-scope-adjacent but not attacker-controlled actor) disables outbound for a destination chain — for maintenance, incident response, or any operational reason — any user payload that was already in flight (had already emitted the burn/outbound event on the EVM side in the same block/transaction) has its outbound event permanently discarded. The user's PRC20 has been burned/escrowed on Push Chain, but the destination-chain payout is never created and no revert/refund flow exists for this specific gap, resulting in a permanent loss of user funds. This matches the "permanent freezing/loss of user funds" impact category.

### Likelihood Explanation
This does not require any attacker action beyond ordinary use of the protocol (submitting a payload that produces an outbound). The trigger condition is that the destination chain's `IsOutboundEnabled` flag transitions to `false` between payload submission and processing of the receipt — an operationally plausible event (chain incident response, admin toggling `MsgUpdateChainConfig`) rather than a contrived edge case. Likelihood of the disable event itself is admin-controlled (out of scope on its own), but the **resulting fund loss for an ordinary user's already-in-flight transaction is an unprivileged, incidental consequence** the code fails to guard against — which is the essence of the reported bug class (support optimistic/edge-state operations without losing funds).

### Recommendation
When `IsChainOutboundEnabled` is `false` at outbound-build time, still create and attach the `OutboundTx` (e.g., with a distinct status such as `ABORTED`/`BLOCKED` and an `abort_reason`, mirroring the existing `AbortOutbound` pattern in `x/uexecutor/keeper/outbound.go`) rather than dropping the event, so operators can later re-enable the chain and resolve the record via a rescue/revert flow (similar to `RescueFundsOnSourceChain`/`AttachRescueOutboundFromReceipt`), instead of the funds vanishing from all UTX bookkeeping.

### Proof of Concept
1. Admin (or a race with `MsgUpdateChainConfig`) sets `ChainEnabled.IsOutboundEnabled = false` for chain `X`.
2. A user's previously-submitted `MsgExecutePayload`/inbound execution EVM call (already committed) emits a `UniversalTxOutbound` event targeting chain `X`, having already burned/locked the PRC20 asset inside the same EVM transaction (see `evm_hooks_and_outbound_test.go` `TestPostTxProcessing_WithSyntheticOutboundEvent/"outbound disabled returns error"` at [5](#0-4) , which demonstrates `PostTxProcessing` returning the "outbound is disabled" error for exactly this scenario).
3. `BuildOutboundsFromReceipt` returns an error and the outbound is never attached to the `UniversalTx`; `PendingOutbounds` never gets an entry.
4. No revert or rescue path exists for this specific case (rescue requires either a `FAILED` CEA deposit or a `REVERTED` `INBOUND_REVERT` outbound, per `AttachRescueOutboundFromReceipt` [6](#0-5) , neither of which applies here since the deposit succeeded and no revert outbound was ever created).
5. Funds are burned/escrowed with no on-chain record of an obligation to deliver them — permanent loss.

**Uncertainty / limitations:** I was not able to fully confirm within the available exploration whether the enclosing EVM call (`DerivedEVMCall`) and the Cosmos-side `BuildOutboundsFromReceipt` error are wrapped in a shared `CacheContext` that would roll back the EVM burn atomically with the Cosmos-side failure. If such a rollback exists, the "disabled" case would instead just fail the whole PC execution (recorded as a `FAILED` PCTx) rather than silently losing already-committed funds, which would reduce impact to a denial-of-service/inconvenience rather than fund loss. This distinction should be verified in the actual call sites (`msg_execute_payload.go`, EVM hooks `PostTxProcessing`) with a live Devin session before treating this as a confirmed fund-loss bug rather than a availability/edge-case bug.

func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
