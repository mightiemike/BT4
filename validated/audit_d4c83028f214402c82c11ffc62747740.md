### Title
Permanent node panic when the `AccountsFileId` (storage id) counter reaches `u32::MAX`, with no way to reset or bypass the check - (File: `accounts-db/src/accounts_db.rs`)

### Summary
The `AccountsDb::next_id` counter (an `AtomicU32` of type `AccountsFileId`) is incremented every time a new account storage (AppendVec) is created — including for every new slot and for every shrink operation. When this counter reaches `AccountsFileId::MAX`, `accounts_db.rs` panics with `"We've run out of storage ids!"` and there is no governance knob, config flag, or code path to disable, reset, or recover from this condition, mirroring the `GasThrottle`/`_FAST_GAS_ORACLE` analog where a single hardcoded, unremovable guard produces an unrecoverable failure.

### Finding Description
`AccountsDb` allocates a fresh storage id for every append vec it creates (one or more per slot, plus additional ids on every shrink of a slot's storage). The id space is a `u32` (`AccountsFileId`), and the allocator asserts/panics once the counter is exhausted rather than wrapping safely or reusing freed ids, as demonstrated by the dedicated regression tests: [1](#0-0) [2](#0-1) 

Both tests explicitly set `next_id` to `AccountsFileId::MAX` and confirm the resulting operation `#[should_panic(expected = "We've run out of storage ids!")]`. This is a hardcoded, load-bearing invariant baked directly into the storage-id allocation path in `accounts_db.rs` — analogous to the `validateGas` modifier hardcoded to always consult `_FAST_GAS_ORACLE`. Just as the Vader contracts provided no governance mechanism to disable the gas oracle check when it returned a poisoned value (zero), Agave provides no configuration, migration, or governance mechanism to disable, widen, or recover from the storage-id exhaustion check when the `u32` id space is consumed. Once the counter reaches `AccountsFileId::MAX`, every subsequent attempt to create a new account storage (which happens on essentially every new rooted slot and during background shrink/clean operations) will hit the same panic path deterministically.

### Impact Explanation
If the storage-id counter is driven to its maximum — whether through very long-lived validator uptime with no restart, an accelerated storage churn (e.g., pathological shrink/clean activity that repeatedly reallocates append vecs), or any bug that increments `next_id` faster than expected — the validator process will panic on the very next attempt to write a new account storage. Because this is a hard assertion baked into the allocation function with no alternate/reset code path, node operators have no way to disable the check, reuse freed ids, or otherwise keep the validator running once it is reached; the only recovery is a code change and rebuild, which is exactly the "no way to remove/disable after deployment" bug class from the source report, applied here as a node-panic condition instead of a swap-DOS condition.

### Likelihood Explanation
`u32::MAX` (~4.29 billion) ids is a large space, so under normal operating conditions this is unlikely to be hit purely through organic slot production. However, likelihood increases with: (a) validator uptime measured in years without restart (each restart, per the reconstruction path in `serde_snapshot.rs`, reads `next_append_vec_id` back from the snapshot and continues incrementing from there rather than resetting), and (b) any workload or bug that causes excessive shrink/clean cycles, each of which consumes additional storage ids beyond the one-per-slot baseline. The test suite treating this scenario as a first-class, deliberately-tested panic condition indicates the developers are aware this is a real (if slow) countdown to an unrecoverable failure state. [3](#0-2) 

### Recommendation
Add a mechanism to detect approaching exhaustion well before `AccountsFileId::MAX` (e.g., a warning/metric once the counter passes some high-water-mark fraction of the id space) and provide an operational path to recover, such as: reclaiming/reusing ids of storages that have since been fully removed, widening the id type in a future format, or otherwise avoiding a hard, unrecoverable panic as the only outcome.

### Proof of Concept
The existing regression tests directly demonstrate the unrecoverable panic: [1](#0-0) 
sets `db.next_id` to `AccountsFileId::MAX` and then performs normal slot-storage creation via `store_for_tests`/`add_root_and_flush_write_cache`, which panics with `"We've run out of storage ids!"` on the very next storage allocation — with no available flag, config, or governance action in the codebase to avoid or recover from this state.

#[test]
#[should_panic(expected = "We've run out of storage ids!")]
fn test_wrapping_storage_id() {
    let db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);

    let account = AccountSharedData::new(1, 0, AccountSharedData::default().owner());

    // set 'next' id to the max possible value
    db.next_id.store(AccountsFileId::MAX, Ordering::Release);
    let slots = 3;
    let keys = (0..slots).map(|_| Pubkey::new_unique()).collect::<Vec<_>>();
    // write unique keys to successive slots
    keys.iter().enumerate().for_each(|(slot, key)| {
        let slot = slot as Slot;
        db.store_for_tests((slot, [(key, &account)].as_slice()));
        db.add_root_and_flush_write_cache(slot);
    });
    assert_eq!(slots - 1, db.next_id.load(Ordering::Acquire));
    let ancestors = Ancestors::default();
    keys.iter().for_each(|key| {
        assert!(db.do_load_for_tests(&ancestors, key).is_some());
    });
}
