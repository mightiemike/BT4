### Title
Nested `WithdrawFromGasKey` inside a `Delegate`/`DelegateV2` meta-transaction bypasses the pending-transaction-queue balance accounting, allowing gas-key funds to be drained without being counted as spent - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
This is the same bug *class* as the FixedFeeSwap report: value can be moved through a "back door" path that the accounting/fee logic does not recognize, because the accounting logic only inspects the *primary*/expected operation (in FixedFeeSwap: `_swap()`; in nearcore: top-level transaction actions) and misses an economically equivalent alternate route (in FixedFeeSwap: deposit→withdraw through the LP token; in nearcore: a `WithdrawFromGasKey` action nested one level down inside a `Delegate`/`DelegateV2` meta-transaction).

### Finding Description
`PendingTransactionQueue::add_chunk_transactions` scans a submitted transaction's actions to keep the SPICE pending-transaction-queue's per-account/per-gas-key balance bookkeeping consistent with what has already been admitted but not yet applied. It only scans the **top-level** actions of the transaction for `WithdrawFromGasKey`: [1](#0-0) 

If a `WithdrawFromGasKey` action is instead nested inside a `Delegate`/`DelegateV2` action (a meta-transaction), the queue's scan never sees it, so it keeps treating the gas key balance as "funded" for admission purposes even though the nested withdrawal will drain it. This is exactly analogous to the FixedFeeSwap flaw: the protected operation (`_swap()` charging a fee / the queue's top-level scan enforcing accounting) is bypassed by an alternate, semantically-equivalent action (LP-token deposit+withdraw / nested `WithdrawFromGasKey`) that produces the same balance movement without going through the path that is actually checked.

The codebase's own inline documentation for the protocol feature `RejectWithdrawFromGasKeyInDelegate` confirms this root cause explicitly: [2](#0-1) 

The fix rejects any `WithdrawFromGasKey` nested in a `Delegate`/`DelegateV2` action list, at receipt-validation time, only once the `RejectWithdrawFromGasKeyInDelegate` protocol feature is active: [3](#0-2) 

The dedicated regression test (`test_reject_delegated_gas_key_withdraw_protocol_upgrade`) demonstrates the exploit directly: before the protocol upgrade, a relayer-submitted meta-transaction with an inner `WithdrawFromGasKey` action executes successfully and drains the sender's gas key balance, confirming the nested action bypasses the intended admission/accounting path: [4](#0-3) 

### Impact Explanation
An unprivileged account owner (the sender of the `Delegate` action, who need only get any relayer to submit the meta-transaction) could exploit this pre-fix behavior to drain their own gas key's prepaid balance through the nested path while the SPICE pending-transaction-queue continued to admit further transactions against the gas key as if it were still funded, based on stale/incorrect balance accounting. This is the same "unauthorized value movement via an alternate path that skips the intended accounting/fee check" class as FixedFeeSwap — it can lead to gas keys with insufficient real balance being treated as funded, causing incorrectly admitted transactions and potential incorrect gas-key balance bookkeeping in the SPICE queue.

### Likelihood Explanation
The action is directly reachable by any transaction signer through a normal meta-transaction (`Delegate`/`DelegateV2`) submitted via any relayer or the signer's own relayer role — no privileged, validator, or network-level capability is required. Its concrete reachability and reproducibility is demonstrated by the checked-in regression test that exercises exactly this scenario pre-upgrade.

### Recommendation
Confirm that `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is active at the current stable/mainnet `PROTOCOL_VERSION`. If it is still gated behind a future/nightly version not yet activated on mainnet, this is a live, exploitable window and the feature should be activated (or backported as a receipt-validation rule) as soon as possible. Additionally, consider hardening `PendingTransactionQueue::add_chunk_transactions` itself to recursively scan nested actions inside `Delegate`/`DelegateV2` (not just reject at validation time), so that future action kinds that touch gas-key balances cannot reintroduce the same top-level-only scanning gap.

### Proof of Concept
1. Attacker/account owner `alice` creates a gas key (`AddKey` with `AccessKey::gas_key_full_access`) and funds it via `TransferToGasKey`.
2. `alice` signs a `DelegateAction` whose `receiver_id == sender_id == alice` and whose single inner action is `Action::WithdrawFromGasKey(WithdrawFromGasKeyAction { public_key: gas_key, amount })`.
3. Any relayer (including one controlled by `alice`) wraps this in `Action::Delegate(signed_delegate)` and submits it as an ordinary transaction.
4. Pre-fix (protocol version below `RejectWithdrawFromGasKeyInDelegate`'s activation version), `PendingTransactionQueue::add_chunk_transactions` never records this nested `WithdrawFromGasKey` in `gas_key_costs`/`pending_accounts`, so the queue's admission bookkeeping for the gas key is wrong while the withdrawal itself succeeds and drains the gas key balance, exactly as shown in `test_reject_delegated_gas_key_withdraw_protocol_upgrade`: [5](#0-4)
