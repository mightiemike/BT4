### Title
Governance-controlled `UNFREEZE_DELAY_DAYS` feature flag can be toggled off, permanently locking users' already-delegated or already-matured funds - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator`, `WithdrawExpireUnfreezeActuator`, and `CancelAllUnfreezeV2Actuator` all gate their `validate()` on the dynamic property `unfreezeDelayDays`/`supportUnfreezeDelay()` (and `supportAllowCancelAllUnfreezeV2()`, which itself also depends on `getUnfreezeDelayDays() > 0`). This mirrors the reported bug class: a legitimate, ordinarily-unprivileged "unwind" operation (withdrawing/undelegating already-committed funds) is hard-gated behind a state flag that can be turned off after users have already committed funds under the assumption the feature stays enabled, permanently stranding those funds with no fallback path.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` requires the feature flag before allowing a user to withdraw balances that have already finished their unfreeze delay: [1](#0-0) 

`UnDelegateResourceActuator.validate()` similarly requires the same flag before a user can reclaim TRX that was delegated to another account (via `FreezeBalanceV2`/`DelegateResource`): [2](#0-1) 

`CancelAllUnfreezeV2Actuator.validate()` requires `supportAllowCancelAllUnfreezeV2()`, which is itself defined as `getAllowCancelAllUnfreezeV2() == 1L && getUnfreezeDelayDays() > 0`, i.e. it also collapses to false whenever `unfreezeDelayDays` is reset to 0: [3](#0-2) [4](#0-3) 

The committee proposal handler that sets `UNFREEZE_DELAY_DAYS` simply stores whatever value is proposed, with no restriction preventing it from being lowered back to `0` after having been enabled and used: [5](#0-4) 

Once `unfreezeDelayDays` is `0`, `supportUnfreezeDelay()` becomes `false` for every account, regardless of whether that account already has:
- Resources delegated via `FreezeBalanceV2`/`DelegateResource` that it wants to reclaim via `UnDelegateResource`.
- Unfrozen-but-not-yet-withdrawn balances in `unfrozenV2List` that have already passed their expiration time and are only waiting on a `WithdrawExpireUnfreezeContract` call.

In both cases, the actuator's `validate()` throws `ContractValidateException("Not support ... transaction, need to be opened by the committee")` before any of the withdraw/undelegate logic runs, and there is no partial success or `try/catch`-style fallback path (unlike the recommended fix in the referenced report). The result is that ordinary users who broadcast a normal, unprivileged `UnDelegateResourceContract` or `WithdrawExpireUnfreezeContract` transaction — the exact same operation that worked before the flag was toggled — get permanently rejected, and their TRX remains locked as delegated resource, or their already-matured unfreeze balance can never be credited back to their spendable balance.

### Impact Explanation
This is a direct funds-availability/DoS issue analogous to the MINTR-pause report: normal, unprivileged reclaim/withdraw transactions become permanently unexecutable once the gating dynamic property is toggled off, even though the underlying accounting state (delegated resource records, matured `unfrozenV2List` entries) still exists and represents real user-owned TRX. Users have no way to get their funds back through the normal contract path while the flag remains disabled, and there is no rescue/emergency mechanism in the actuators to bypass the check for already-committed positions.

### Likelihood Explanation
Triggering this requires only a single committee proposal to reduce `UNFREEZE_DELAY_DAYS` to `0` after it was previously enabled (or to disable `ALLOW_CANCEL_ALL_UNFREEZE_V2`-dependent behavior via the same flag) — the same class of "emergency/governance response backfiring on legitimate unwind operations" described in the original report. No code path prevents this regression, and the TVM-callable native contract analogs (`WithdrawExpireUnfreezeProcessor`, `UnDelegateResourceProcessor`) reachable from smart contracts inherit the same or related gating, so the condition is reachable both from normal RPC-submitted transactions and from contract execution.

### Recommendation
- Do not gate `WithdrawExpireUnfreezeContract`/`CancelAllUnfreezeV2Contract` execution on the *current* value of `unfreezeDelayDays`/`ALLOW_CANCEL_ALL_UNFREEZE_V2` for balances that were already committed while the feature was enabled; instead, track eligibility per-position (e.g., based on the unfreeze expiration timestamp already stored) so that toggling the feature off cannot strand already-earned withdrawals.
- Similarly, allow `UnDelegateResourceContract` to always succeed for a user's own already-delegated resources, independent of whether new delegations are currently permitted.
- Alternatively, prevent `UNFREEZE_DELAY_DAYS` from being reduced back to `0` (or below a value smaller than the current maximum outstanding lock period) once it has been enabled and used by any account.

### Proof of Concept
1. Committee approves `UNFREEZE_DELAY_DAYS = 14` via proposal, enabling `supportUnfreezeDelay()`.
2. User A calls `FreezeBalanceV2`, then `DelegateResource` to User B.
3. User A later wants to reclaim resource: before doing so, the committee approves a new proposal setting `UNFREEZE_DELAY_DAYS = 0`.
4. User A broadcasts `UnDelegateResourceContract`; `UnDelegateResourceActuator.validate()` now throws `ContractValidateException("Not support unDelegate resource transaction, need to be opened by the committee")` (`actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java:209-212`), and User A's TRX remains delegated indefinitely.
5. Equivalently, User C who had already called `UnfreezeBalanceV2` and whose `unfrozenV2List` entry has matured cannot call `WithdrawExpireUnfreezeContract` once `unfreezeDelayDays` is reset to 0, because `WithdrawExpireUnfreezeActuator.validate()` rejects it (`actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java:84-87`), leaving the matured balance permanently unwithdrawable through the normal contract path.
