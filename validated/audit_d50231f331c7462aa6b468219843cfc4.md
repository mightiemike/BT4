Based on the investigation, I found a concrete, code-confirmed integrity gap, but I want to be precise about what is proven versus what would need further tracing (specifically, where `ensure_match_transaction_info` is actually invoked and whether an unprivileged path can trigger it against corrupted position/trading-native state).

### Title
Replay/consistency check `ensure_match_transaction_info` ignores position-state checkpoint hash, allowing corrupted trading-native state root to pass verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to verify that a locally-produced `TransactionOutput` (write set, events, gas, status) matches an authenticated `TransactionInfo` fetched from storage/backup/network. The code contains an explicit acknowledged gap: it validates `write_set_hash`, `event_root_hash`, `gas_used`, and `status`, but does not validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` field that was introduced for the "trading-native" position state feature.

### Finding Description
`TransactionInfo` (v1 builder) now carries `maybe_position_state_checkpoint_hash`, populated in `assemble_transaction_infos` in `execution/executor/src/workflow/do_ledger_update.rs` from `position_state_checkpoint_hashes[i]`, which in turn is computed in `DoStateCheckpoint::compute_position_checkpoint` (`execution/executor/src/workflow/do_state_checkpoint.rs`) only `if execution_output.compute_trading_native_state_roots`. This root commits to the state of the `PositionSlot` Jellyfish-Merkle-like structure (native order/position book state) maintained alongside normal account state. [1](#0-0) [2](#0-1) 

However, `TransactionOutput::ensure_match_transaction_info` — the function used to cross-check computed output against the authenticated `TransactionInfo` (used by `aptos-move/cli/src/commands.rs` and `storage/db-tool/src/replay_on_archive.rs` for replay/verification tooling) — explicitly does **not** check `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. The code contains its own TODO admitting this: [3](#0-2) 

This means: if the trading-native position-state accumulator diverges (due to a local storage bug, a bug in `compute_position_checkpoint`'s incremental extend logic, a corrupted/incompletely-restored position Merkle tree, or a non-deterministic ordering bug in the `HashMap`-based `collect` closure used for position writes), the divergence is silently accepted by any replay-verify or archive-verification tool that relies on `ensure_match_transaction_info`, because that function only reasons about the legacy write-set/event/gas/status fields and never inspects the position checkpoint hash carried in the same `TransactionInfo`.

### Impact Explanation
This is a genuine state-commitment/proof-integrity gap under the required Impact Gate: replay/verification tooling (`replay_on_archive`, `aptos-move/cli`) is meant to detect when the authenticated ledger (from backup or archive) diverges from local re-execution. Because the position-state root is excluded from the comparison, a divergence in the trading-native position state — e.g. from the known-risky `collect` closure that folds writes into a `HashMap<HashValue, PositionSlot>` before insertion into the SMT (`do_state_checkpoint.rs` lines 129–144) — would not be caught, and the corrupted/incorrect committed position-state root would be treated as verified/consistent. This directly matches the "committed state that differs from the correct VM result... not caught" and "hard-fork-only divergence during commit/replay" impact categories, since if two nodes silently diverge on position state, tooling built specifically to catch such divergence (replay-verify) is blind to it.

### Likelihood Explanation
The likelihood is bounded by two factors that I could not fully verify within the available context:
1. Whether `compute_trading_native_state_roots` / trading-native feature is enabled on mainnet or is still gated off (it appears controlled by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag referenced in `types/src/on_chain_config/aptos_features.rs`).
2. Whether `ensure_match_transaction_info` is invoked anywhere in the actual consensus-critical execution/commit path (as opposed to only offline replay/verify tooling in `db-tool` and `aptos-move/cli`), which would change this from a tooling blind-spot into a consensus-safety gap.

Given the explicit developer TODO in the code acknowledging exactly this gap ("this comparator ignores the checkpoint hashes... so replay-verify tooling... can report a successful replay even when the authenticated position state root diverges from local execution"), the root cause is confirmed by the codebase itself rather than speculation. However, without confirming whether trading-native is live on mainnet and whether any consensus-path caller depends on this comparator for safety (versus only optional debugging tooling), I cannot elevate this past a tooling-integrity gap with likely-medium/uncertain-high severity.

### Recommendation
Extend `ensure_match_transaction_info` (and any equivalent comparators used in restore/replay paths) to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values whenever those fields are present in the `TransactionInfo`, closing the gap flagged by the existing TODO before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled broadly.

### Proof of Concept
Not independently reproducible from the indexed code alone — the concrete PoC would require constructing a `TransactionInfo` with a correct `write_set_hash`/`event_root_hash`/`gas_used`/`status` but a deliberately wrong `position_state_checkpoint_hash`, and showing `ensure_match_transaction_info` returns `Ok(())` (which is a direct, mechanical consequence of the code at [4](#0-3)  since that field is never read in the function body).
