## Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify/restore tooling accept a corrupted state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by the chunk-executor's `verify_execution` path (backing `db-tool replay-verify`, `replay-on-archive`, and backup-cli's `ReplayVerifyCoordinator`) to confirm that locally re-executed transactions match the trusted, accumulator-proven `TransactionInfo` list pulled from a backup/archive. This function explicitly skips comparing the recomputed state-checkpoint hashes against the trusted `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` fields, per its own TODO comment.

### Finding Description
`ensure_match_transaction_info` checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check the state checkpoint hashes: [1](#0-0) 

The function's own comment documents the gap: [2](#0-1) 

This method is used by the chunk executor's `verify_execution`, which is the sole mechanism `ReplayChunkVerifier`/CLI replay tooling use to confirm local re-execution matches trusted `TransactionInfo`s pulled from backup archives: [3](#0-2) [4](#0-3) 

By contrast, the primary (non-replay) apply-chunk path used for live state sync *does* thread `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` from the trusted `TransactionInfo`s into `DoStateCheckpoint::run()` as "known" values to validate against locally computed roots: [5](#0-4) 

So the live sync path is protected, but the `verify_execution`/replay-verify path (used specifically to detect state divergence during backup verification/replay, per the trait name `TransactionReplayer` and `VerifyExecutionMode`) is not: it can report a clean replay even when the locally computed state-tree root (main state, hot state, or "trading-native" position state) diverges from the trusted, accumulator-proven root carried in the `TransactionInfo`.

### Impact Explanation
Replay-verify and CLI replay tooling exist specifically to catch state-commitment bugs (e.g., a JMT/state-tree computation defect, an ordering bug, or a subtly incorrect hot-state/position-state update) by comparing locally recomputed roots against the immutably proven `TransactionInfo` chain. Because the checkpoint-hash fields are excluded from the comparison, a state root divergence — which is precisely the "hard-fork-only divergence during commit/replay/restore/proof verification" class this scan is meant to surface — would not be flagged by this specific integrity gate. This can mask genuine state-commitment corruption from operators who rely on `replay-on-archive`/`replay-verify` as their authoritative correctness check, allowing a divergent DB to be treated as verified when it silently is not (only the write-set/event/gas/status subset of the transaction result is confirmed, not the resulting global-state Merkle root).

### Likelihood Explanation
This is not a hypothetical omission — it is explicitly called out in the code's own TODO as a known, currently-unaddressed gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), confirming that the maintainers are aware the comparator is incomplete for at least the `position_state_checkpoint_hash` (trading-native) case, and by construction the same comparator also never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash` for any caller of `ensure_match_transaction_info`. Any real defect in state-checkpoint-hash computation on the replay path (rather than the live-execution `DoStateCheckpoint` path, which independently validates it) would go undetected specifically through this API.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when enabled) `position_state_checkpoint_hash` against the corresponding fields of the supplied `txn_info`, mirroring the "known checkpoint" validation already performed by `DoStateCheckpoint` in the primary apply-chunk path, so that `verify_execution`/replay-verify tooling cannot report success while the recomputed state root diverges from the trusted, accumulator-proven value.

### Proof of Concept
Not directly exploitable via a single crafted transaction from the identified code alone — the gap is a missing invariant check rather than a wrong-value write. Demonstrating it requires: (1) a divergence-inducing bug/version mismatch in state-checkpoint-root computation (JMT update, hot-state, or position-state) that is otherwise not exercised by the primary sync path's `DoStateCheckpoint` validation (i.e., surfaces only in the replay path, e.g., due to differing code paths between initial commit and CLI/db-tool replay), and (2) running `db-tool replay-verify`/`replay-on-archive`/`ReplayVerifyCoordinator` over that range, at which point `ensure_match_transaction_info` returns `Ok(())` despite the state-checkpoint hash mismatch, because that field is never inspected in the comparator.
