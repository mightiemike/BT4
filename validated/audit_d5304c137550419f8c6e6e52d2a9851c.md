### Title
Inconsistent delegatable-balance validation between `DelegateResourceActuator` and TVM-invoked `DelegateResourceProcessor` allows over-delegation of a frozen resource balance - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java)

### Summary
`DelegateResourceContract` can be executed via two independent code paths that both re-derive "how much frozen balance is still available to delegate" from the account's current usage, but they compute that availability differently. Like the Yearn `_creditAvailable` / `_debtOutstanding` mismatch, the same quantity ("delegatable credit") is calculated inconsistently depending on the calling context, letting one path allow a delegation that the other would reject.

### Finding Description
`DelegateResourceActuator.validate()` (invoked for ordinary top-level `DelegateResourceContract` transactions) computes the bandwidth usage baseline as: [1](#0-0) 

Note the conditional term: it adds `TransactionUtil.estimateConsumeBandWidthSize(...)` to `accountNetUsage` only "if (null != this.getTx() && this.getTx().isTransactionCreate())" before converting usage into an equivalent frozen-balance amount and checking it against the requested `delegateBalance`.

`DelegateResourceProcessor.validate()` (invoked when a smart contract triggers a native "delegate resource" operation from inside TVM execution) performs the analogous check but skips this extra term entirely: [2](#0-1) 

Both paths ultimately compute `frozenV2BalanceForBandwidth - v2NetUsage` and compare it to the requested `delegateBalance`, using the identical `getV2NetUsage` helper from `FreezeV2Util`. The only difference is whether the estimated bandwidth cost of "transaction creation" is folded into `accountNetUsage` before the conversion. Because `DelegateResourceProcessor` never adds this reservation, its computed `v2NetUsage` is smaller than the actuator's for the same account state, making `frozenV2BalanceForBandwidth - v2NetUsage` appear larger. This mirrors the Yearn bug pattern where one code path ("credit available") uses a stricter accounting of outstanding usage than the other path ("debt outstanding"), letting an actor exploit the more permissive path.

### Impact Explanation
A contract that programmatically triggers delegate-resource logic through the TVM native-contract path (`DelegateResourceProcessor`) is validated with a more permissive check than a user submitting the same operation as a direct `DelegateResourceContract` transaction (`DelegateResourceActuator`). This allows a contract-driven delegation to succeed and commit more of the owner's `FrozenV2BalanceForBandwidth` than the direct-transaction path would ever allow for the identical account state, understating the bandwidth reservation intended for "transaction create" costs. The owner account can end up with less real bandwidth headroom than accounting implies, which can degrade or block the owner's own subsequent transactions (resource starvation / self-DoS), analogous to the report's "vault extends more credit than warranted."

### Likelihood Explanation
Reaching `DelegateResourceProcessor` requires a smart contract to invoke the native delegate-resource operation from within TVM execution (a triggered contract call), which is a normal, permissionless, reachable path for any deployed contract; no privileged actor or leaked key is required. The divergence only manifests in the specific case where `isTransactionCreate()` would have added the extra reservation term in the actuator path, so it is conditional but deterministically reproducible by constructing account state where a "create" cost would apply.

### Recommendation
Unify the delegatable-balance computation into a single shared helper used identically by `DelegateResourceActuator.validate()`, `DelegateResourceProcessor.validate()`, and any other consumer (e.g., `FreezeV2Util.queryDelegatableResource`, `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`), ensuring the same usage-estimation terms (including the transaction-create bandwidth estimate where applicable) are applied consistently regardless of whether the operation originates from a direct transaction or a TVM-triggered native contract call. Add regression tests asserting parity between the actuator and native-contract validation results for identical account/dynamic-store states.

### Proof of Concept
1. Prepare an account `A` with `FrozenV2BalanceForBandwidth = X` and `NetUsage` such that, under the actuator's formula, adding the `estimateConsumeBandWidthSize` term would push `v2NetUsage` high enough that `X - v2NetUsage < delegateBalance` (i.e., a direct `DelegateResourceContract` transaction from `A` delegating `delegateBalance` would be rejected by `DelegateResourceActuator.validate()`, per [3](#0-2) ).
2. Deploy a contract that, when triggered, invokes the native delegate-resource path with the same `ownerAddress`/`delegateBalance` parameters, reaching `DelegateResourceProcessor.validate()` at [4](#0-3) , which omits the `estimateConsumeBandWidthSize` addition.
3. Observe that the TVM-triggered path succeeds (because `v2NetUsage` computed without the extra term is smaller, satisfying `FrozenV2BalanceForBandwidth - v2NetUsage >= delegateBalance`) while the equivalent direct transaction from step 1 would fail, confirming the two enforcement points disagree on the same account's delegatable balance for identical state.
