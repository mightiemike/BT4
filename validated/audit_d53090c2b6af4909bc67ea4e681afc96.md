### Title
Growth-gate in `check_flush_trigger` can defer index-bin eviction until the bin has silently doubled, causing a disproportionately large single-shot eviction burst - (File: accounts-db/src/accounts_index/in_mem_accounts_index.rs)

### Summary
`InMemAccountsIndex::check_flush_trigger` is the threshold check that decides whether an in-memory accounts-index bin should be flushed/evicted. Analogous to the StRSR bug, it uses a hard `high_water_mark` "gate" to decide whether to evict at all, and once the gate is crossed, it evicts in one shot down to a `low_water_mark`. Because the gate completely disables eviction while a bin is "still in initial growth" (`capacity < high_water_mark`), a bin whose backing hashmap has already silently doubled while under that same watermark can accumulate up to ~2x the intended `high_water_mark` of entries before eviction ever engages — mirroring the StRSR pattern where a rate can drift very close to (but technically not cross) a threshold, and a small subsequent change then triggers an outsized, one-shot correction instead of the intended small/incremental one.

### Finding Description
`check_flush_trigger` gates eviction entirely while `capacity < high_water_mark`: [1](#0-0) 

The function's own comments acknowledge the "backstop" scenario explicitly: the hashmap can already have doubled in size (well past the intended `high_water_mark`) by the time the "high count" trigger finally fires, because during the growth phase the free-entries trigger is intentionally suppressed: [2](#0-1) 

When eviction does fire, `max_evictions_for_threshold` computes the batch to evict in a single pass as `current_entries - low_water_mark`: [3](#0-2) 

Under normal steady-state operation, the intended per-cycle eviction size is bounded by `DEFAULT_NUM_ENTRIES_TO_EVICT` (10,000), i.e. the gap between `high_water_mark` and `low_water_mark`: [4](#0-3) [5](#0-4) 

But because the "still in initial growth" gate at line 1315-1319 blocks any eviction attempt while `capacity < high_water_mark` — even when free-entry headroom is already critically low due to tombstones — a bin can grow its backing HashMap all the way from just-under `high_water_mark` capacity to double that capacity (hashbrown grows by doubling) with zero eviction happening in between. Once capacity finally clears `high_water_mark`, the "backstop" `should_evict_based_on_count` check fires and `max_evictions_for_threshold` must evict roughly `(2 * high_water_mark) - low_water_mark` entries — many times larger than the designed `DEFAULT_NUM_ENTRIES_TO_EVICT` increment — in a single flush/evict pass while holding `map_internal`'s write lock repeatedly (chunked, but still processed synchronously in one background cycle): [6](#0-5) 

This is structurally the same pattern as the StRSR issue: a threshold-gated correction that is supposed to be small/incremental is instead deferred by design until the underlying quantity has already grown far past the nominal boundary, so the eventual correction is disproportionately large relative to what the watermark spacing (`num_entries_overhead` / `num_entries_to_evict`) was tuned for.

### Impact Explanation
This does not lose account data (evicted dirty entries are write-through / flushed to disk before removal at line 1510-1521), so it does not cause balance loss, stale reads, or hash divergence. The impact is limited to **disproportionate CPU/lock-contention cost**: a single background flush cycle can be forced to evict and rebuild (`reallocate_to_clear_tombstones`, lines 1457-1491) using far more entries than the configured `num_entries_to_evict`/`num_entries_overhead` budget intended, producing latency/CPU spikes in the accounts-index background thread that were specifically designed to be avoided by the watermark spacing.

### Likelihood Explanation
This requires `IndexLimit::Threshold` mode to be configured (not the default `InMemOnly`), and requires steady insert/tombstone churn that lets a bin's backing HashMap double while still below the configured `high_water_mark`, which is plausible under sustained write pressure to a hot bin given hashbrown's doubling growth strategy. It is a purely mechanical/timing condition, not attacker-triggerable via the network in an obviously exploitable way, so likelihood of significant real-world impact is limited to specific `Threshold` deployments.

### Recommendation
Do not fully gate eviction based on capacity alone; also account for the case where capacity has already jumped past a multiple of `high_water_mark` due to doubling, and clamp/split the resulting eviction batch (e.g., cap eviction per background cycle to `num_entries_to_evict`, iterating over multiple cycles) rather than evicting the entire backlog in one pass, matching the same spirit as Reserve's fix of adding an explicit, bounded, governance-triggered correction instead of relying on an all-or-nothing threshold crossing.

### Proof of Concept
1. Configure `IndexLimit::Threshold` with a given `high_water_mark`/`low_water_mark` (as in `test_check_flush_trigger_below_hwm_gate`, lines 2994-3029).
2. Continuously insert/remove entries into one bin such that hashbrown's capacity doubles (e.g., inserts crossing the 7/8 load factor) while `len()`/count stays just under `high_water_mark`, so `check_flush_trigger` keeps returning `false` per the gate at lines 1315-1319.
3. Insert one more entry that pushes `capacity` just over `high_water_mark`; `check_flush_trigger` now returns `true` via the "backstop" `high_count_triggered` path (lines 1321, 1332-1335).
4. `max_evictions_for_threshold` (bucket_map_holder.rs 148-159) computes `current_entries - low_water_mark`, which — because `current_entries` reflects the already-doubled bin — is far larger than `DEFAULT_NUM_ENTRIES_TO_EVICT`, causing a single flush/evict pass to process an outsized batch, contrary to the designed small/incremental eviction cadence.

    /// Decide whether this bin needs flushing/eviction. Returns true if the caller should proceed.
    ///
    /// Fires on either of two conditions:
    /// - Free-entry headroom is below the configured overhead. Tombstones left by prior evictions
    ///   reduce capacity without being included in len, so a rehash can be imminent before the
    ///   count crosses the high-water mark. This is the primary trigger in steady state.
    /// - Entry count exceeds the high-water mark. This is a backstop for the case where the
    ///   hashmap has already doubled in size, leaving plenty of headroom so the first condition
    ///   would not fire on its own.
    ///
    /// Returns false for bins still in initial growth (capacity below `high_water_mark`).
    fn check_flush_trigger(&self) -> bool {
        let (entries_in_bin, capacity) = {
            let map = self.map_internal.read().unwrap();
            (map.len(), map.capacity())
        };

        // Skip during initial growth: below HWM, low free entries reflect a not-yet-grown
        // table, not tombstones. If tombstones do force a doubling before len crosses HWM,
        // the count check catches it later once len grows past HWM.
        if let Some(thresholds) = &self.storage.threshold_entries_per_bin
            && capacity < thresholds.high_water_mark
        {
            return false;
        }

        let high_count_triggered = self.storage.should_evict_based_on_count(entries_in_bin);
        let low_free_entries_triggered = self
            .storage
            .should_evict_based_on_free_entries(capacity.saturating_sub(entries_in_bin));
        if !high_count_triggered && !low_free_entries_triggered {
            return false;
        }
        if low_free_entries_triggered {
            // Primary case: low free-entry headroom (typically from tombstones).
            Self::update_stat(&self.stats().evict_triggered_by_low_free_entries, 1);
        } else {
            // Backstop: bin is past the high-water mark while free-entry headroom
            // still has slack — typically because the hashmap doubled in size.
            Self::update_stat(&self.stats().evict_triggered_by_high_count, 1);
        }
        true

    /// Calculate maximum evictions to perform for threshold-based flushing
    /// Returns current_entries for Minimal disk index
    /// Returns the max_evictions for Threshold mode to bring count to the low water mark
    pub fn max_evictions_for_threshold(&self, current_entries: usize) -> NonZeroUsize {
        let evictions = match &self.threshold_entries_per_bin {
            None => current_entries,
            Some(threshold_entries_per_bin) => {
                // Low water mark: evict down to specified ratio of the per-bin threshold
                current_entries.saturating_sub(threshold_entries_per_bin.low_water_mark)
            }
        }
        .max(1);
        // SAFETY: evictions is ensured to be non-zero above.
        NonZeroUsize::new(evictions).unwrap()
    }
