### Title
Missing existence validation on `DeleteAccountAction.beneficiary_id` permanently burns account funds - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId`; it never checks that the account actually exists on chain before the account's remaining balance is dispatched to it as a refund. Because the beneficiary transfer is implemented as a system-generated *refund* receipt, and refund receipts can never trigger implicit account creation, sending funds to a non-existent (but validly formatted) `beneficiary_id` causes the transfer to fail and the tokens to be permanently burned instead of returned to anyone.

### Finding Description
`validate_delete_action` — the stateless validation run on every `DeleteAccount` action — only calls `validate_action_account_id(&action.beneficiary_id)`, which checks the string is a syntactically valid account id; it performs no state lookup to confirm the account exists: [1](#0-0) 

At execution time, `action_delete_account` unconditionally creates a balance-refund receipt addressed to `beneficiary_id` and then deletes the source account, without ever checking that `beneficiary_id` refers to an existing account: [2](#0-1) 

The balance transfer is built via `Receipt::new_balance_refund`, which makes it a **refund receipt** (`predecessor_id == "system"`). Refund receipts are handled specially in `check_account_existence`/`implicit_creation_allowed`: a refund can *never* implicitly create a receiving account, regardless of account type: [3](#0-2) 

If the beneficiary account does not exist, the `Transfer` action inside this refund receipt fails with `AccountDoesNotExist` (per `check_account_existence`'s `Action::Transfer` branch): [4](#0-3) 

Crucially, when a refund receipt fails, its deposit is not retried or bounced back — it is simply burned. This is explicit in the apply loop: [5](#0-4) 

and documented behavior: [6](#0-5) 

Since the source account has already been removed (`remove_account`) as part of `action_delete_account`, there is no way to recover: the account is gone and its balance is burned rather than delivered to the caller-specified beneficiary or refunded to anyone.

This mirrors the reported analog exactly: the "ownership"/destination field (`beneficiary_id`, analogous to `newOwner`) that controls where value flows is accepted with only a superficial format check, and never validated for actual existence before the state-changing/value-moving action commits irreversibly.

### Impact Explanation
A user error (typo'd or otherwise non-existent `beneficiary_id`) or a naive/careless wallet/relayer/dApp implementation results in **permanent, unrecoverable loss (burning) of the deleted account's entire remaining balance** with no way to recover the funds — the account no longer exists to retry, and the failed refund receipt's deposit is burned rather than bounced. This is a direct value-loss bug reachable by any ordinary transaction signer submitting a single `DeleteAccount` action, with no privileged access required.

### Likelihood Explanation
Likelihood is high in practice: `DeleteAccountAction` is a standard, frequently used action (e.g., closing lockup/vesting accounts, contract migrations, wallet cleanup), and nothing in the transaction/action validation path prevents specifying a nonexistent `beneficiary_id`. A single wrong character in an account id, an account that has not yet been created, or an account deleted in the same block causes silent, permanent fund loss rather than a rejected transaction. The bug is trivially reproducible with a standard `DeleteAccount` transaction and requires no adversarial conditions.

### Recommendation
Add a state-existence check for `beneficiary_id` before allowing `DeleteAccountAction` to execute (or at minimum before removing the source account), e.g., in `action_delete_account` (`runtime/runtime/src/actions.rs`) look up the beneficiary account and fail the action with a dedicated error (e.g. `BeneficiaryAccountDoesNotExist`) if it is not found, so the delete is rejected up front instead of silently burning the balance after the source account has already been destroyed.

### Proof of Concept
1. Create/fund a normal named account `alice.near` with balance `B`.
2. Submit a transaction from `alice.near` with a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "totally-nonexistent-account.near".parse().unwrap() })`, where `beneficiary_id` is syntactically valid but has never been created.
3. `validate_delete_action` passes (format is valid).
4. `action_delete_account` removes `alice.near` and queues a `Receipt::new_balance_refund` for `B` to `totally-nonexistent-account.near`.
5. That refund receipt executes as a `Transfer` action to a non-existent account; `check_account_existence`/`implicit_creation_allowed` reject account creation because the receipt is a refund, producing `AccountDoesNotExist`.
6. Per the refund-failure handling at `runtime/runtime/src/lib.rs:1047-1054`, the failed refund's deposit `B` is added to `stats.balance.other_burnt_amount` (burned) instead of being credited anywhere — `alice.near`'s funds are permanently lost. This can be observed by comparing pre/post total supply and confirming neither `alice.near` nor `totally-nonexistent-account.near` holds balance `B` afterward.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
