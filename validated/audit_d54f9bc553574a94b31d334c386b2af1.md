### Title
`receipt_filter_fn` panics on `.unwrap()` when a stale delayed receipt's target shard can't be mapped after two resharding generations - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874-878` unconditionally `.unwrap()`s the result of `receiver_shard_id(&shard_layout)` for every delayed receipt popped from or peeked in the delayed-receipt queue. This is the same class of bug as the external report: code assumes a lookup (there, a hardcoded 0.05% Uniswap pool; here, a receiver-shard mapping for a receipt's `receiver_id`/`target_shard`) will always succeed, and hard-fails (revert in the audit report, `panic!`/chunk-apply abort here) when that assumption breaks down under realistic conditions — specifically stale receipts surviving across multiple resharding events.

### Finding Description
`receipt_filter_fn` is used both by `pop()` (the hot path that drains the delayed receipt queue during normal chunk apply) and by `peek_iter()`: [1](#0-0) 

```
    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }
```

`pop()` calls this filter on every receipt dequeued from `DelayedReceiptQueue` [2](#0-1) , and the comment above it explicitly acknowledges the resharding-caused shard mismatch case but the code only handles a single-generation shard split (parent → child). It does **not** handle a receipt whose `target_shard`/`receiver_shard_id` predates two consecutive resharding generations — a shard id that is neither the current shard nor its immediate parent in the current `ShardLayout`, which `receiver_shard_id()` cannot resolve and therefore returns `Err`, which is then `.unwrap()`ed into a panic.

This is directly analogous to the reported Multipool bug: both are places where a downstream lookup (fee-tier pool / shard-layout ancestry mapping) is assumed to always resolve, but a legitimate, attacker-uncontrolled state (missing fee pool / multi-generation resharding) breaks that assumption, and the code fails hard instead of degrading gracefully.

A regression test already exists in the repository that specifically reproduces this exact scenario end-to-end: [3](#0-2) [4](#0-3) 

The test comment states plainly: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations."* The test drives: (1) deploy a global contract from a user on shard `S_A`, producing a `GlobalContractDistribution` receipt targeting `S_A`; (2) saturate compute on `S_A` so the receipt sits in the delayed-receipt queue; (3) force two sequential shard splits while the receipt remains delayed; (4) drain the queue and assert the chain does not stall — i.e. it asserts the absence of the panic. This test's existence and framing is strong first-party confirmation that this precise `receiver_shard_id()`/`receipt_filter_fn` unwrap path is a known-risky code location for exactly the double-resharding staleness case.

### Impact Explanation
Any unprivileged account can trigger this: an ordinary transaction that creates a receipt directed at a shard which then splits twice while that receipt is stuck in the delayed queue (e.g. by submitting a `DeployGlobalContract` action, which produces a `GlobalContractDistribution` receipt, or via congestion causing a normal cross-shard receipt to sit delayed) can, if `receiver_shard_id()` returns `Err` in the panicking branch, cause the chunk producer to panic while applying the chunk. A panic inside chunk application/`apply_transactions` on a validator node is a chunk-application failure — this maps to a transaction-triggered halt/chain-stall condition, one of the explicitly accepted impact categories (state-transition failure / transaction-triggered halt), not merely a resource/no-impact issue.

### Likelihood Explanation
Requires: (a) dynamic/V3 resharding enabled, (b) a receipt whose destination shard is force-split twice while the receipt is stuck in the delayed queue long enough to survive both splits without being re-derived/remapped in the intervening `forward_from_buffer`-style parent-tracking logic that only tracks a single generation of `parent_shard_ids` (`ReceiptSinkV2Info::parent_shard_ids` in the same file only records immediate split parents, not grandparents) [5](#0-4) . This requires sustained congestion/compute saturation across multiple epochs to keep the receipt delayed through two resharding events — feasible but requires deliberate resource use by the caller, hence Medium likelihood, matching the reporter's own severity classification style for the analogous Multipool issue.

### Recommendation
Do not `.unwrap()` the result of `receiver_shard_id()` in `receipt_filter_fn`. Instead, propagate the error (make `receipt_filter_fn`/`pop`/`peek_iter` fallible) or extend the "receipt belongs to which shard" resolution to walk up the resharding ancestry chain (grandparent, great-grandparent, etc.) so multi-generation-stale receipts still resolve to a valid shard rather than triggering `Err`/panic. At minimum, treat an unresolvable shard mapping as "does not belong to this shard" (filtered out, not retained, and not panicked on) rather than crashing chunk application.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` (lines 30–186) is essentially a ready-made PoC:
1. Deploy a test contract and then a `GlobalContractDistribution`-producing global contract deploy from a user on shard `S_A`.
2. Continuously submit `burn_gas_raw` transactions to saturate `S_A`'s compute budget every block, forcing the distribution receipt into the delayed-receipt queue and keeping it there.
3. Configure `DynamicReshardingConfig` to force-split `S_A` and then force-split one of its resulting children, producing two resharding generations while the receipt is still delayed.
4. Stop saturating and let the delayed queue drain; assert the chain head continues to advance (i.e., no panic/stall).

If `receipt_filter_fn`'s `.unwrap()` on `receiver_shard_id()` hits the `Err` branch for the twice-stale receipt, chunk application panics and the assertion `head_height >= drain_end` fails because the chain stalls — confirming the transaction-triggered halt.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }
