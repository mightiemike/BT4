### Title
Duplicate-address user-burn-support entries in `MinerPaymentSchedule` corrupt `calculate_miner_reward`'s address-based split, causing coinbase over-payment - ([File: stackslib/src/chainstate/stacks/db/accounts.rs])

### Summary
`calculate_miner_reward`'s user-reward branch (lines 825-838) identifies "this participant's own burn" and "everyone else's burn" purely by comparing `StacksAddress`, not by `vtxindex`. When two user-burn-support entries in the same tenure's `users` list share a `StacksAddress` but have distinct `vtxindex`, the `this_user` variable is overwritten (not summed) on every matching iteration, and `total_other` never counts either entry because both compare equal to `participant.address`. This makes every duplicate-address entry compute the *same* (wrong, larger) `this_user`/`burn_total` ratio, which is applied once per duplicate entry, producing a coinbase payout total that exceeds `coinbase_at_block`.

### Finding Description
The invariant that must hold is:
`sum(MinerReward::total() for miner_reward + all user_rewards) == coinbase_at_block + burnchain-proportional fee allocation`, never more.

In `calculate_miner_reward` (stackslib/src/chainstate/stacks/db/accounts.rs:804-845), for a user participant:
```
let mut this_user: u128 = 0;
let mut total_other: u128 = miner.burnchain_commit_burn as u128;
for user_support in users.iter() {
    if user_support.address != participant.address {
        total_other = total_other.checked_add(...)...
    } else {
        this_user = user_support.burnchain_commit_burn as u128;   // overwrite, not accumulate
    }
}
``` [1](#0-0) 

`find_mature_miner_rewards` (lines 1054-1068) calls `calculate_miner_reward` once *per user entry* (i.e., once per `vtxindex`), passing the full `users` slice each time: [2](#0-1) 

If two entries in `users` share `address = A` with `burnchain_commit_burn = 100` (vtxindex 5) and `= 200` (vtxindex 7):
- For every call where `participant.address == A` (both the vtxindex-5 and vtxindex-7 invocations), the loop sets `this_user = 100` then overwrites it to `this_user = 200` (last matching iteration wins, and iteration order follows the `ORDER BY vtxindex ASC` query used to populate the schedule, per `get_scheduled_block_rewards_at_block`) [3](#0-2) .
- `total_other` never receives a contribution from either duplicate entry (both compare equal to `participant.address`), so it stays at just `miner.burnchain_commit_burn`, omitting the real "other" burn that should have been counted.
- Consequently **both** vtxindex-5 and vtxindex-7 payouts are computed with the identical (wrong) ratio `coinbase * 200 / (miner_burn + 200)`, rather than `coinbase * 100 / total` and `coinbase * 200 / total` respectively, where `total = miner_burn + 100 + 200`.

Numeric example (`miner_burn = 100`): correct miner share is `coinbase*100/400 = 0.25*coinbase`; with the bug, miner share is `coinbase*100/(100+300)=0.25*coinbase` (miner-side computation sums all users correctly — line 817-823 does correctly sum `total_user` over all entries regardless of address, so the miner's own share is unaffected), but each of the two duplicate-address user payouts computes `coinbase*200/300 ≈ 0.667*coinbase`, and this is paid out **twice** (once per entry), totaling `1.333*coinbase`. Grand total `0.25 + 1.333 = 1.583*coinbase`, exceeding the coinbase pot by over 58%.

No existing guard catches this: `insert_matured_child_user_reward`'s assertions only check `vtxindex > 0` and that the reward `is_child()` [4](#0-3) ; they do not validate that the sum of matured rewards is bounded by the coinbase. `calculate_miner_reward` performs only overflow checks (`checked_add`/`checked_mul`), not a cross-participant conservation check.

The exploitability hinges on an unverified precondition: whether the burnchain layer that creates `MinerPaymentSchedule` rows from `UserBurnSupportOp`s (or whatever mechanism populates `users` for a tenure) permits two burn ops from the same `StacksAddress` with distinct `vtxindex` to be admitted into the `payments` table for one tenure. I was not able to fully confirm within available tool calls whether such duplicate-address admission is prevented upstream (e.g., in block-commit/op validation in `sortdb.rs`) or whether the `UserBurnSupportOp` mechanism is still an active, attacker-reachable path in this codebase's current epoch/consensus rules — grep results for `user_burn_support`/`UserBurnSupportOp` were sparse (only in `chainstate/burn/db/sortdb.rs` and `chainstate/burn/mod.rs`), suggesting this may be a legacy/rarely-exercised code path whose op-admission constraints I did not fully trace.

### Impact Explanation
If reachable, this is a Critical reward-theft/double-payment bug: STX minted for a tenure's coinbase would exceed the amount defined by protocol issuance rules, effectively creating STX out of thin air and crediting it to an attacker-controlled address (the duplicated `StacksAddress`). This affects all nodes identically (deterministic computation from chain state), so it would not itself cause a fork, but it is a direct violation of the coinbase-conservation invariant and constitutes block-reward theft/double-payment as defined in the Critical category.

### Likelihood Explanation
Feasibility depends entirely on the unverified precondition: can an unprivileged attacker, using only their own BTC, get two `MinerPaymentSchedule`/user-burn-support rows with the same `StacksAddress` but distinct `vtxindex` inserted for the same tenure? This requires confirming that (a) `UserBurnSupportOp` (or its successor mechanism) is still processed as a first-class reward-eligible burn op in current epochs, and (b) no uniqueness constraint on `(address)` within a tenure's payment schedule is enforced during op admission/validation. Without confirming these, I cannot assert this is currently exploitable in the live consensus path, only that the arithmetic bug exists in `calculate_miner_reward` as written.

### Recommendation
Fix `calculate_miner_reward`'s user branch to key on `vtxindex` (the actual unique identifier for a payment-schedule row) instead of, or in addition to, `address`, and change `this_user` to accumulate (`+=`) rather than overwrite in case duplicate addresses are ever encountered:
```rust
for user_support in users.iter() {
    if user_support.vtxindex != participant.vtxindex {
        total_other = total_other.checked_add(user_support.burnchain_commit_burn as u128)...;
    } else {
        this_user = this_user.checked_add(user_support.burnchain_commit_burn as u128)...;
    }
}
```
Additionally, enforce uniqueness of `address` per tenure at op-admission/insertion time if duplicate-address user-burn-support entries are not a supported/intended configuration, and add an invariant assertion in `find_mature_miner_rewards` that `miner_reward.total() + sum(user_rewards.total()) <= coinbase_at_block + fees` before persisting matured rewards.

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/db/accounts.rs` test module, alongside existing `calculate_miner_reward` tests):
1. Construct a `miner` `MinerPaymentSchedule` with `coinbase = C`, `burnchain_commit_burn = M`.
2. Construct two `users` entries with the *same* `address = A`, `vtxindex = 5, burn=100` and `vtxindex = 7, burn=200` respectively, via `make_dummy_miner_payment_schedule`.
3. Call `calculate_miner_reward` once for the miner participant and once per user entry (mirroring `find_mature_miner_rewards`'s loop).
4. Assert (equality to validate): `miner_reward.total() + user_reward_5.total() + user_reward_7.total() == C` (post-`checked_add`, no overflow panics).
5. Show the assertion fails — actual sum exceeds `C` — by computing expected values with the corrected keyed-by-`vtxindex` logic and comparing against the current buggy output, confirming the divergence and the magnitude of over-payment.
