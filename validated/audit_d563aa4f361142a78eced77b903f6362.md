### Title
Multi-outbound batch build aborts atomically on a single invalid/disabled entry, blocking unrelated valid withdrawals in the same transaction - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`BuildOutboundsFromReceipt` iterates over every `UniversalTxOutboundEvent` log emitted by the `UniversalGatewayPC` contract within a single EVM receipt and, on the first per-log validation failure (chain outbound disabled, or missing PRC20→external token mapping), immediately returns an error that discards *all* outbounds already built in that loop — not just the offending one. This mirrors the C4 finding's root cause: an operation that bundles multiple independent items in a single loop, where one item's failure (there: a paused reward token transfer; here: a disabled destination chain or unmapped PRC20) blocks the entire batch instead of being isolated.

### Finding Description
`BuildOutboundsFromReceipt` loops over `receipt.Logs`, decodes each `UniversalTxOutboundEvent`, and for each one calls `k.uregistryKeeper.IsChainOutboundEnabled` and `k.uregistryKeeper.GetTokenConfigByPRC20`. Any failure on either call causes an immediate `return nil, err` for the whole function [1](#0-0) , discarding outbounds already appended to the local `outbounds` slice for other, unrelated, valid log entries in the same receipt.

This function is invoked from two production entrypoints that process a single EVM transaction's receipt as a whole:
- `EVMHooks.PostTxProcessing`, called by the EVM module after every EVM transaction executes, via `CreateUniversalTxFromReceiptIfOutbound` [2](#0-1) 
- `ExecutePayload` (direct msg-based execution path), via the same `CreateUniversalTxFromReceiptIfOutbound` call [3](#0-2) 

Since a single EVM transaction can emit multiple `UniversalTxOutboundEvent` logs from `UniversalGatewayPC` (e.g., a UEA contract call that internally triggers withdrawals to several different destination chains/tokens in one call), an unprivileged user can construct a payload where one leg targets a chain with `IsChainOutboundEnabled == false` or an asset lacking a `TokenConfig` entry for that chain, while the other legs target perfectly valid, supported chains/tokens. The single bad leg causes the entire `BuildOutboundsFromReceipt` call — and hence the caller returning an error — to fail, which (given standard Cosmos SDK message-level state branching) causes the entire underlying message execution to be rolled back, including the otherwise-valid withdrawal legs.

### Impact Explanation
This is an unprivileged, user-reachable denial-of-service on the universal execution path: a user who batches multiple outbound-triggering actions into one call is completely blocked from executing any of them if just one leg references an unsupported/disabled chain or token mapping — even though the guarded invariants (chain enablement, token mapping) have nothing to do with the other legs. This falls under the explicitly in-scope "denial of service...reachable without privileged control" category, and is a direct structural analog of the VE3DRewardPool bug class: one bad/blocked item in a loop poisons an otherwise valid batch of independent operations.

### Likelihood Explanation
Reaching this requires only an ordinary user submitting a payload/contract call that emits multiple `UniversalTxOutboundEvent`s in one receipt targeting a mix of valid and invalid (disabled-chain or unmapped-token) destinations — no privileged access, malicious validator, or external chain compromise is needed. The trigger conditions (chain disabled, token unmapped for a given chain) are ordinary registry states that exist for any not-yet-onboarded or deprecated chain/asset.

### Recommendation
Change `BuildOutboundsFromReceipt` to process each log independently: skip/record a per-event failure (e.g., attach a `FAILED` marker or emit a warning event) instead of aborting the whole function, so that valid outbound events in the same receipt are still built and attached even when a sibling log fails validation. Alternatively, validate chain/token support pre-execution (before the EVM call that emits these events) rather than post-hoc during outbound extraction, so failures are surfaced before any state-changing action is taken.

### Proof of Concept
1. Registry has chain A (outbound enabled, PRC20 mapped) and chain B (outbound disabled, or PRC20 X not mapped for chain B).
2. User submits an `ExecutePayload` (or a UEA contract call) whose execution causes `UniversalGatewayPC` to emit two `UniversalTxOutboundEvent` logs in the same receipt: one valid withdrawal to chain A, one to chain B.
3. `CreateUniversalTxFromReceiptIfOutbound` → `BuildOutboundsFromReceipt` processes logs in order; upon reaching the chain-B log, `IsChainOutboundEnabled`/`GetTokenConfigByPRC20` fails and the function returns `nil, err` immediately [4](#0-3) , discarding the already-built chain-A outbound.
4. The caller (`ExecutePayload` or `EVMHooks.PostTxProcessing`) propagates the error, causing the whole message/transaction to fail, and the valid chain-A withdrawal is never attached as an outbound despite being fully valid on its own.
