### Title
Off-by-one cap bypass in `MarketOrderIdListCapsule.getAllOrder` allows `getMarketOrderListByPair` to return more orders than `MARKET_COUNT_LIMIT_MAX` - ([File: chainbase/src/main/java/org/tron/core/capsule/MarketOrderIdListCapsule.java])

### Summary
`MarketOrderIdListCapsule.getAllOrder(orderStore, limit)` is intended to cap the number of linked-list orders it returns to `limit`, mirroring the Allora bug class where an inner loop fails to stop exactly at the intended sample cap. The break condition checks `count > limit` *after* incrementing `count` post-append, causing the loop to append one more order than `limit` before breaking, exactly analogous to the reported `GetForecastScoresUntilBlock` inner-loop-exceeds-cap issue.

### Finding Description
In `getAllOrder`: [1](#0-0) 
the loop appends `makerOrderCapsule` to `result`, then increments `count`, and only afterward checks `count > limit` to break. This means when `count` reaches `limit` (not yet exceeding it), the loop still executes one more full iteration — appending an additional order — before the break condition trips on the following check. The cap is therefore off-by-one: exactly `limit + 1` orders can be returned instead of at most `limit`, the same defect pattern as the original report where the inner loop was not bound tightly to the intended maximum.

This function is invoked from `Wallet.getMarketOrderListByPair`, where the caller computes a "remaining budget" `MARKET_COUNT_LIMIT_MAX - countForOrder` and passes it as `limit` to `getAllOrder`, then adds `orderList.size()` back to `countForOrder`: [2](#0-1) 
Because `getAllOrder` silently returns one more element than requested on each call, `countForOrder` accumulates faster than the outer loop accounts for, but the outer loop's exit test (`MARKET_COUNT_LIMIT_MAX - countForOrder <= 0`) is evaluated with the *inflated* count and thus does eventually cap total growth — however, on each individual `pairPriceKey` iteration, the response ends up containing one more `MarketOrderCapsule` than the intended per-call limit, and in the boundary case where remaining budget is `0`, `getAllOrder` is still called with `limit = 0` and, due to the off-by-one, still appends one order (since `count > limit` is false until count reaches 1), returning data when zero was expected.

### Impact Explanation
This is a read-only market-data query (`GetMarketOrderListByPair` gRPC / `GetMarketOrderListByPairServlet` HTTP), reachable by any anonymous client. The impact is limited to a bounded, small (off-by-one per call) over-return of `MarketOrderCapsule` entries beyond the configured `MARKET_COUNT_LIMIT_MAX`, which can inflate response size and marginally increase per-request work (extra order lookups via `getNextCapsule`), rather than causing state corruption, fund loss, or consensus divergence, since this endpoint does not affect actuator state or reward accounting — it is a query-only path. It is a much weaker impact than the original Allora finding, where the miscounted loop directly fed into reward-fraction computation causing consensus-relevant discrepancies.

### Likelihood Explanation
Trivial to trigger — any client can call `GetMarketOrderListByPair` for any token pair with enough orders queued to exceed `MARKET_COUNT_LIMIT_MAX`, deterministically hitting the off-by-one every time count reaches the limit boundary.

### Recommendation
Change the break condition in `getAllOrder` to check the cap before appending, e.g. break when `count >= limit` prior to adding the element, or check `if (count == limit) break;` before the `result.add(...)` call, ensuring at most `limit` elements are ever added, matching the fix pattern recommended in the referenced report (cap the inner loop as tightly as the outer intended maximum).

### Proof of Concept
1. Populate a market pair's linked order list with more than `MARKET_COUNT_LIMIT_MAX` orders (or ensure the per-price remaining budget passed to `getAllOrder` is small, e.g. `limit = 0`).
2. Call `GetMarketOrderListByPair`/`GetMarketOrderListByPairServlet` for that pair.
3. Observe that `getAllOrder` returns `limit + 1` orders instead of `limit`: with `count` starting at 0, the loop body executes and appends before the `count > limit` check, so even `limit = 0` yields 1 returned order, and generally `limit` yields `limit + 1` orders — confirming the cap is bypassed by exactly one entry per invocation, as shown in [3](#0-2) .

    List<MarketOrderCapsule> result = new ArrayList<>();

    long count = 0;
    byte[] orderId = this.getHead();
    if (!ByteArray.isEmpty(orderId)) {
      MarketOrderCapsule makerOrderCapsule = orderStore.getUnchecked(orderId);
      while (makerOrderCapsule != null) {
        result.add(makerOrderCapsule);
        makerOrderCapsule = makerOrderCapsule.getNextCapsule(orderStore);
        count++;
        if (count > limit) {
          break;
        }
      }
    }
    return result;
  }
