### Title
PBFT sync-committee (witness list) selection uses a stale `nextMaintenanceTime` snapshot at maintenance-period boundaries, causing legitimate finality votes for boundary blocks to be rejected - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
Telepathy's `LightClient` picked the wrong sync committee for beacon blocks near a sync-committee period boundary because the circuit exported the slot of the *finalized* (nested) block rather than the slot of the *wrapping* block that determines the signing committee. java-tron's PBFT finality layer has the analogous defect: it decides which witness set (`beforeWitness` vs `currentWitness`) should have signed a given PBFT message by comparing a maintenance-time "epoch" tag to `MaintenanceManager.beforeMaintenanceTime`, but the epoch value attached to the block that actually triggers the maintenance switch is taken from a stale, pre-update local variable, so the comparison resolves to the wrong witness set exactly at the period boundary.

### Finding Description
`MaintenanceManager.applyBlock` computes `nextMaintenanceTime` from the store *before* checking whether maintenance is due: [1](#0-0) 

For the block that crosses the maintenance boundary (`flag == true`, `blockNum != 1`):
- `beforeMaintenanceTime` is set to the *old* `nextMaintenanceTime` value captured at the top of the method.
- `doMaintenance()` runs and the active witness set changes.
- `currentWitness` is refreshed to the *new* set.
- `consensusDelegate.updateNextMaintenanceTime(blockTime)` advances the store's `nextMaintenanceTime` to a new, later boundary.
- `pbftManager.srPrePrepare(blockCapsule, currentWitness, consensusDelegate.getNextMaintenanceTime())` is called with the freshly updated (future) time — this path is internally consistent.

However, `pbftManager.blockPrePrepare(blockCapsule, nextMaintenanceTime)` at the end of the method uses the **local** `nextMaintenanceTime` variable, which — for the boundary-crossing block — was captured before the update and therefore still equals the *old* boundary, i.e. it is numerically equal to `beforeMaintenanceTime` that was just set two lines above.

This "epoch" tag is later used by `PbftMessageHandle.getSrMinerList` and `PbftManager.verifyMsg` to select which witness set is expected to have signed the PBFT message: [2](#0-1) [3](#0-2) 

Both use the same boundary comparison `epoch > maintenanceManager.getBeforeMaintenanceTime()`. Because the boundary block's `epoch` equals `beforeMaintenanceTime` (not strictly greater), the comparison is false and the **old** (`beforeWitness`) set is selected instead of the new, correct signing committee for `blockPrePrepare`-driven flows on that exact block. This is the same class of defect as the reported issue: a state-transition boundary value (maintenance/period switch) is compared using a value captured from the wrong point in time, causing the validator/committee-selection logic to disagree with the actual signers for blocks at (or immediately after) the switch.

This logic is reachable from the network: PBFT messages arrive via `PbftMsgHandler.processMessage`, which calls `pbftManager.verifyMsg(msg)` using attacker/peer-supplied `msg.getEpoch()` and message signer, and any node (not just a privileged actor) can be a signer whose legitimate vote is misclassified: [4](#0-3) 
When `verifyMsg` returns false because the wrong witness list was consulted, the handler throws `P2pException.BAD_MESSAGE`, discarding a legitimately-signed finality vote.

### Impact Explanation
When a block coincides with a maintenance-period switch, honest SR PBFT votes for that block (via `blockPrePrepare`) are checked against the outgoing witness set instead of the set that is actually active/expected at that instant, causing valid votes to be rejected as "bad message" and dropped rather than counted. This degrades the reliability of the PBFT finality mechanism (used for fast/solid block confirmation and cross-checked by light/full nodes) precisely at maintenance-cycle boundaries, mirroring the delayed-finality/DoS effect described in the report (delayed message delivery due to failed signature verification against the wrong committee).

### Likelihood Explanation
Maintenance/period switches happen deterministically on every maintenance cycle (default every 6 hours in java-tron), so the boundary block condition is reached routinely, not as a rare edge case, making the mis-selection reproducible on every maintenance cycle boundary for the `blockPrePrepare` epoch path.

### Recommendation
Do not compute `blockPrePrepare`'s epoch argument from a `nextMaintenanceTime` local variable snapshotted before the maintenance update. Re-read `consensusDelegate.getNextMaintenanceTime()` immediately before calling `pbftManager.blockPrePrepare` (mirroring what is already done for `srPrePrepare`), or use a monotonically consistent epoch marker (e.g., the block's own timestamp/maintenance-cycle id) so that the same boundary block always resolves consistently to the correct witness set in both `getSrMinerList` and `verifyMsg`. Add unit/e2e tests that specifically construct a block that triggers the maintenance switch and verify PBFT prepare/commit messages for that exact block validate against the correct witness set.

### Proof of Concept
1. Configure a short maintenance interval in test config and drive the chain to the block `B` at which `nextMaintenanceTime <= B.timestamp` becomes true (the maintenance-switch block), with `blockNum != 1`.
2. Observe in `MaintenanceManager.applyBlock` that:
   - `beforeMaintenanceTime` is set to the pre-update `nextMaintenanceTime` value.
   - `pbftManager.blockPrePrepare(block, nextMaintenanceTime)` is invoked using the same stale local value, i.e., `epoch == beforeMaintenanceTime`.
3. Have an SR from the newly-activated witness set (post `doMaintenance()`) sign a `blockPrePrepare` PBFT message for block `B` and broadcast it.
4. On a receiving node, `PbftMsgHandler.processMessage` calls `pbftManager.verifyMsg(msg)`, which evaluates `epoch > beforeMaintenanceTime` → `false` (since `epoch == beforeMaintenanceTime`), so it checks the signer against `beforeWitness` (the old set) instead of `currentWitness`, causing the legitimate new-committee signer's vote to fail verification and be dropped with `P2pException.BAD_MESSAGE`.

  public void applyBlock(BlockCapsule blockCapsule) {
    long blockNum = blockCapsule.getNum();
    long blockTime = blockCapsule.getTimeStamp();
    long nextMaintenanceTime = consensusDelegate.getNextMaintenanceTime();
    boolean flag = consensusDelegate.getNextMaintenanceTime() <= blockTime;
    if (flag) {
      if (blockNum != 1) {
        updateWitnessValue(beforeWitness);
        beforeMaintenanceTime = nextMaintenanceTime;
        doMaintenance();
        updateWitnessValue(currentWitness);
      }
      consensusDelegate.updateNextMaintenanceTime(blockTime);
      if (blockNum != 1) {
        //pbft sr msg
        pbftManager.srPrePrepare(blockCapsule, currentWitness,
            consensusDelegate.getNextMaintenanceTime());
      }
    }
    consensusDelegate.saveStateFlag(flag ? 1 : 0);
    //pbft block msg
    if (blockNum == 1) {
      nextMaintenanceTime = consensusDelegate.getNextMaintenanceTime();
    }
    pbftManager.blockPrePrepare(blockCapsule, nextMaintenanceTime);
  }

  public boolean verifyMsg(PbftBaseMessage msg) {
    long epoch = msg.getPbftMessage().getRawData().getEpoch();
    List<ByteString> witnessList;
    if (epoch > maintenanceManager.getBeforeMaintenanceTime()) {
      witnessList = maintenanceManager.getCurrentWitness();
    } else {
      witnessList = maintenanceManager.getBeforeWitness();
    }
    return witnessList.contains(ByteString.copyFrom(msg.getPublicKey()));
  }
