### Title
Merchant Custom App Authentication Trusts Unauthenticated `shop` Query Parameter to Build Admin Sessions - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts])

### Summary
For merchant custom apps (`config.isEmbeddedApp === false`, `AppDistribution.ShopifyAdmin`/custom-app installs), `getSessionTokenContext()` derives the `shop` used to build the admin session directly from the raw, unauthenticated `shop` URL query parameter, with no JWT/session-token verification and no shop sanitization gate applied to that code path. This `shop` value flows unchanged into `MerchantCustomAuth.authenticate()`, which calls `api.session.customAppSession(shop)` to build a `Session` bound to the app's single static Admin API access token but with an attacker-controlled shop domain.

### Finding Description
In `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`, `getSessionTokenContext()` branches on `config.isEmbeddedApp`: [1](#0-0) 

When the app is embedded, `shop` is derived from `payload.dest`, i.e., from a cryptographically-verified session token (`validateSessionToken` → `api.session.decodeSessionToken`). But when the app is **not** embedded (the merchant custom app path), `shop` is taken straight from `url.searchParams.get('shop')` with no signature check at all.

The earlier gate `validateShopAndHostParams()`, which sanitizes/validates `shop` format, is only invoked for `config.isEmbeddedApp === true`: [2](#0-1) 

For non-embedded (merchant custom app) requests, that gate never runs, so `shop` is not even format-validated, let alone tied to the actual store the app is meant to serve.

This unauthenticated `shop` is then passed into `MerchantCustomAuth.authenticate()`: [3](#0-2) 

`customAppSession(shop)` builds a `Session` using the app's single, statically configured Admin API access token (`config.adminApiAccessToken`), but with `shop` set to whatever the request supplied — not to the shop the token was actually issued for. The resulting session is subsequently used to build the Admin API client (`createAdminApiContext`), which constructs outbound request URLs from `session.shop`.

This mirrors the `mintSynth()` bug class: a caller-supplied "destination" (`to` in the Solidity report, `shop` here) is used in place of a value cryptographically bound to the authenticated actor, letting an unprivileged caller redirect a privileged operation (spending real credentials) to an address/domain of their choosing.

### Impact Explanation
Because merchant custom apps are single-tenant and hold one long-lived Admin API access token for one real store, using an attacker-supplied `shop` value means the app's real access token can be attached to outbound Admin API requests targeting a domain the attacker chooses (e.g., `?shop=attacker-controlled.myshopify.com`). This is a credential-disclosure / SSRF-style vector: the app's genuine Admin API token is sent to a host outside the legitimate merchant's control, potentially leaking the token to an attacker or causing the app to act against a foreign/attacker shop.

### Likelihood Explanation
Any unauthenticated caller who can reach the app's admin routes and control the `shop` query parameter can trigger this — no signature, no prior session, and no privileged position are required, since the non-embedded branch performs no JWT validation and skips `validateShopAndHostParams`.

### Recommendation
For the merchant custom app strategy, do not derive `shop` from the raw request URL. Instead, bind the session's `shop` to the value configured for the app deployment (the shop the custom app was actually created for), or otherwise validate/sanitize and restrict the incoming `shop` parameter to match the app's configured store before calling `customAppSession(shop)`.

### Proof of Concept
1. Deploy a merchant custom app (`config.isEmbeddedApp = false`) with a real `adminApiAccessToken` configured for `real-shop.myshopify.com`.
2. Send an unauthenticated request to the app's admin route with `?shop=attacker-shop.myshopify.com`.
3. `getSessionTokenContext()` returns `shop = 'attacker-shop.myshopify.com'` without any validation.
4. `MerchantCustomAuth.authenticate()` calls `customAppSession('attacker-shop.myshopify.com')`, producing a session with the real access token but the attacker's shop domain.
5. Any subsequent Admin API call made through this session sends the real access token to `attacker-shop.myshopify.com`.
