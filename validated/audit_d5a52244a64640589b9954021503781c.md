### Summary
The premise that `get_microblock_pubkey_hash_height` could resolve a `Hash160` registration from a *different, disjoint fork* is false: all Clarity DB reads/writes (including `insert_microblock_pubkey_hash_height` and `get_microblock_pubkey_hash_height`) are routed through the MARF keyed at the currently-open chain tip, so a read on fork B can never see a write made only on fork A's history.

### Finding Description
`handle_poison_microblock` recovers `pubkh` from the two signed microblock headers via `check_microblock_header_signer`, then calls `env.global_context.database.get_microblock_pubkey_hash_height(&pubkh)`, which resolves to `ClarityDatabase::get_microblock_pubkey_hash_height` → `get_data(&key)`. This bottoms out in `PersistentWritableMarfStore::get_data` / `MarfedKV::get_data`, which call `self.marf.get(&self.chain_tip, key)` [1](#0-0)  — i.e., the lookup is a MARF trie traversal rooted at the tip of the fork currently being processed. `insert_microblock_pubkey_hash_height` (called from `StacksChainState::insert_microblock_pubkey_hash`/`finish_block` at each block's processing) writes into that same fork-indexed MARF at that block's height [2](#0-1) . Consequently a registration made while processing tenure X on fork A is simply not visible when evaluating a poison-microblock transaction included in a block on fork B, unless fork B shares that ancestry (in which case it's the same history, not a "wrong miner" collision).

The claimed scenario additionally requires two *distinct* miners to have both used literally the same microblock private key (so both produce the same `Hash160`), which is collusion/key-sharing between two miners — outside the stated attacker model ("holds no other signer's or miner's key"). Even in that colluding case, `mblock_pubk_height` from `get_microblock_pubkey_hash_height` is simply the height most recently registered for that key *within this fork's own ancestry*, and the slashing logic (`calculate_miner_reward`/`poison_microblock_commission`) diverts the coinbase belonging to whatever miner's payment schedule row exists at that specific height/consensus-hash in this fork's `payments` table [3](#0-2)  — i.e., the height correctly disambiguates to the actual block/miner that used the key at that point in the actual chain history being processed, not an unrelated miner on another fork.

### Impact Explanation
No reward-theft, chain-split, or wrong-party payment path exists through this mechanism: fork isolation in the MARF backing store prevents cross-fork key collisions, and same-fork key reuse (which would require key-sharing collusion outside the attacker model) still correctly targets the payment-schedule entry at the referenced height.

### Likelihood Explanation
Not applicable — the described precondition (cross-fork Hash160 collision visible to `get_microblock_pubkey_hash_height`) cannot occur given the MARF's fork-scoped key resolution, and the alternative same-key-reuse path requires possessing another miner's private key, which the attacker model excludes.
