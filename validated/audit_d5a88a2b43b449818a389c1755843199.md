### Title
Exchange pool owner can front-run/sandwich trader transactions via unthrottled `ExchangeInjectContract`/`ExchangeWithdrawContract` reserve changes - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, ExchangeWithdrawActuator.java, ExchangeTransactionActuator.java)

### Summary
Any ordinary account can create a bancor-style token/TRX liquidity pool (`Exchange`) via `ExchangeCreateContract`, and as the pool's `owner_address` can later submit `ExchangeInjectContract` or `ExchangeWithdrawContract` transactions that instantly and unconditionally change the pool's `firstTokenBalance`/`secondTokenBalance` reserves used by `ExchangeCapsule.transaction()` to price every other trader's `ExchangeTransactionContract`. There is no time lock, no minimum notice period, and no protection preventing the pool owner from adjusting reserves in the very same block immediately before or after a victim's swap to shift the effective exchange rate against them — the exact "front running / bad timing due to unwarned parameter change" bug class described in the report, mapped onto java-tron's exchange/market math subsystem instead of a governance-controlled parameter.

### Finding Description
`ExchangeCreateActuator.execute()` lets any funded account create an exchange pool, becoming its owner with no special system privilege beyond owning that specific pool's key. [2](#0-1) 

`ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()` then let that pool owner change `firstTokenBalance`/`secondTokenBalance` directly, and the new balances take effect immediately in the same block for any subsequent swap: [3](#0-2) [4](#0-3) 

`ExchangeTransactionActuator.execute()` computes another trader's swap output strictly against the *current* on-chain reserve state via `ExchangeCapsule.transaction()`, with no slippage guard beyond a simple `tokenExpected` floor check: [5](#0-4) [6](#0-5) 

Because block producers assemble transactions from the pending pool and a witness (or a colluding relay/observer) can see a pending `ExchangeTransactionContract` before it is packed, the pool owner can submit an `ExchangeInjectContract`/`ExchangeWithdrawContract` ordered immediately before the victim's transaction in the same block to shift `firstTokenBalance`/`secondTokenBalance` and thus the bancor-relay price computed in `ExchangeProcessor.exchange()` / `SafeExchangeProcessor.exchange()`, then reverse the balance change afterward — a classic sandwich attack enabled purely by the absence of any timelock or notice mechanism around reserve changes. [7](#0-6) 

### Impact Explanation
A victim trader relying on `tokenExpected` alone (rather than a tight, freshly-recomputed slippage bound) can receive materially less output than expected, or have their transaction fail (`ContractValidateException: "token required must greater than expected"`) after already committing to the trade intent, while the exchange owner extracts the spread. Because balances (TRX and TRC10 assets) move through `AccountCapsule` balance/asset fields, this is a genuine on-chain asset value transfer from unprivileged traders to whoever controls the pool at that moment — not merely a griefing/DoS issue.

### Likelihood Explanation
Exploiting this requires only: (1) creating or controlling an exchange pool (any account can do this, no governance/committee/witness role needed), and (2) observing pending `ExchangeTransactionContract` transactions targeting that pool and getting an inject/withdraw transaction ordered ahead of them in the same block — achievable by the pool creator themselves acting as, or colluding with, a block-producing witness, or simply via mempool-visibility timing given java-tron's public broadcast-then-pack transaction flow. No cryptographic key compromise or protocol-level bug is needed; it is purely a missing-timelock/notice design gap in the actuators, directly analogous to the reported issue.

### Recommendation
Introduce a mandatory delay/commit-reveal or minimum-block-height gap between an `ExchangeInjectContract`/`ExchangeWithdrawContract` and subsequent `ExchangeTransactionContract`s against the same pool, or bound the maximum single-block price impact any inject/withdraw can have; alternatively, require traders to specify a tight two-sided slippage bound (max/min output) validated against the reserve state at execution rather than only a lower bound, and consider disallowing inject/withdraw and trade against the same pool within one block.

### Proof of Concept
1. Account A creates an exchange pool for TRX/TokenX via `ExchangeCreateContract` (`ExchangeCreateActuator`), becoming the pool "owner."
2. Victim V broadcasts an `ExchangeTransactionContract` to swap TRX for TokenX with `expected` set to the currently-quoted output.
3. Before V's transaction is packed, A broadcasts an `ExchangeWithdrawContract` that pulls a large amount of TokenX reserve out of the pool, shifting the bancor-relay price unfavorably for V (`ExchangeWithdrawActuator.execute()`).
4. The block producer includes A's withdraw transaction before V's trade in the same block; V's swap executes against the now-worse reserves in `ExchangeCapsule.transaction()`, either yielding V less TokenX than anticipated or failing the `tokenExpected` check.
5. A immediately re-injects the withdrawn tokens via `ExchangeInjectContract` in a later block, restoring the pool and having captured the difference at V's expense — all without violating any protocol rule, because no timelock or notice period governs reserve changes.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
