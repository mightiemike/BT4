### Title
Per-Action Storage-Proof Limit Check Allows a Single Receipt to Exceed the Per-Receipt 4 MB Hard Limit by Splitting Reads Across Multiple `FunctionCall` Actions — (`runtime/runtime/src/lib.rs`, `runtime/near-vm-runner/src/logic/recorded_storage_counter.rs`, `runtime/runtime/src/ext.rs`)

---

### Summary

Before protocol version 86 (`EnforcePerReceiptStorageProofLimit`), the `per_receipt_storage_proof_size_limit` (4 MB) was enforced **per-action**, not per-receipt cumulatively. An unprivileged user could craft a receipt containing N `FunctionCall` actions, each reading just under 4 MB of state, generating up to N × 4 MB of storage proof in a single receipt — directly analogous to the external report's "split a large bet into many smaller ones" bypass.

---

### Finding Description

**Root cause — `runtime/runtime/src/lib.rs:835–842`**

When `EnforcePerReceiptStorageProofLimit` is **not** enabled (protocol versions 83–85), `storage_proof_size_before_receipt` is `None`:

```rust
let storage_proof_size_before_receipt =
    if ProtocolFeature::EnforcePerReceiptStorageProofLimit
        .enabled(apply_state.current_protocol_version)
    {
        Some(state_update.trie.recorded_storage_size_upper_bound())
    } else {
        None   // ← pre-PV86: no receipt-level snapshot
    };
```

This `None` is passed unchanged to every `apply_action` call in the receipt's action loop (line 865), and forwarded into `action_function_call` (`runtime/runtime/src/function_call.rs:74`) and then into `RuntimeExt`.

**Fallback in `runtime/runtime/src/ext.rs:322–324`**

```rust
fn storage_proof_size_before_receipt(&self) -> usize {
    self.storage_proof_size_before_receipt
        .unwrap_or_else(|| self.get_recorded_storage_size())
    //                  ^^^ when None: baseline resets to current total at each action
}
```

When `None`, the baseline for each action's `RecordedStorageCounter` is the **current cumulative proof size at the start of that action**, not the proof size at the start of the receipt. Each action therefore measures only its own incremental contribution.

**Enforcement in `runtime/near-vm-runner/src/logic/recorded_storage_counter.rs:13–33`**

```rust
pub fn new(initial_storage_size: usize, size_limit: usize) -> Self {
    Self { initial_storage_size, last_observed_storage_size: initial_storage_size, size_limit }
}
pub fn observe_size(&mut self, latest_storage_proof_size: usize) -> Result<(), VMLogicError> {
    let current_size = self.get_storage_size()?;   // = latest - initial
    if current_size > self.size_limit { ... RecordedStorageExceeded ... }
}
```

Because `initial_storage_size` is reset to the current total at the start of each action (not the start of the receipt), a receipt with 5 `FunctionCall` actions each reading ~1 MB passes the 4 MB check five times independently, generating 5 MB of cumulative proof — exceeding the intended hard limit.

**The test at `runtime/runtime/src/tests/apply.rs:1670–1674` explicitly documents this as a bug:**

```rust
// Before the fix (per-action limit): every action reads only ~1 MB, which is
// below the 4 MB limit, so the whole receipt succeeds even though it reads
// ~5 MB of state in total.
let status_before = apply_read_receipt(feature_version - 1);
assert_matches!(status_before, ExecutionStatus::SuccessValue(_));
```

---

### Impact Explanation

The `per_receipt_storage_proof_size_limit` (4 MB) is a **hard limit** on the storage proof a single receipt may generate, designed to keep `ChunkStateWitness` size bounded. The `main_storage_proof_size_soft_limit` (also 4 MB) is the chunk-level soft limit; the per-receipt hard limit is the backstop.

With the bypass, a single receipt with N `FunctionCall` actions can generate N × ~4 MB of storage proof. Combined with the soft limit, a chunk's state witness can reach (N × 4 MB) + 4 MB. For N = 5 (within `max_actions_per_receipt = 100`), this is ~24 MB — far exceeding the intended ~17 MB total witness budget. This constitutes a non-network-level DoS on stateless validation: chunk validators must process and verify a witness much larger than the protocol intended, and honest nodes running different protocol versions may diverge on whether the receipt is valid. The vulnerable code path remains in the production codebase for nodes running protocol versions 83–85 (`MIN_SUPPORTED_PROTOCOL_VERSION = 83`).

---

### Likelihood Explanation

Any unprivileged user can trigger this by submitting a transaction to a contract that reads large trie values (e.g., values written by `storage_write`). The attacker needs only to:
1. Write N large values (each ~1 MB) to contract storage in prior transactions.
2. Submit a receipt with N `FunctionCall` actions each calling a method that reads one of those values.

No special permissions, validator access, or privileged role is required. The `max_actions_per_receipt = 100` limit means up to ~400 MB of storage proof per receipt is theoretically possible, though gas limits constrain practical exploitation.

---

### Recommendation

The fix is already present and gated by `EnforcePerReceiptStorageProofLimit` (PV86): snapshot `recorded_storage_size_upper_bound()` **once** before the receipt's action loop and pass that single snapshot to all actions. This ensures `RecordedStorageCounter` measures the cumulative proof growth across the entire receipt, not per-action.

The fix at `runtime/runtime/src/lib.rs:835–842` correctly implements this. Ensure all nodes upgrade to PV86 to activate the fix, and consider removing the pre-PV86 fallback path once `MIN_SUPPORTED_PROTOCOL_VERSION` advances past 85.

---

### Proof of Concept

1. Deploy a contract with a method `read_1mb(key)` that calls `storage_read` on a 1 MB value.
2. Write 5 distinct 1 MB values under keys 0–4 via 5 separate transactions.
3. Submit a single transaction whose receipt contains 5 `FunctionCall` actions, each calling `read_1mb` with a different key.
4. On protocol version ≤ 85: all 5 actions succeed; the receipt generates ~5 MB of storage proof, exceeding the 4 MB hard limit without error.
5. On protocol version 86: the receipt fails with `RecordedStorageExceeded` after the cumulative proof crosses 4 MB.

This is confirmed by the existing test `test_per_receipt_storage_proof_size_limit` in `runtime/runtime/src/tests/apply.rs:1557–1688`.

```rust
impl RecordedStorageCounter {
    pub fn new(initial_storage_size: usize, size_limit: usize) -> Self {
        Self { initial_storage_size, last_observed_storage_size: initial_storage_size, size_limit }
    }

    /// Update the latest observed storage proof size and check if it exceeds the limit.
    /// Should be called after every trie operation.
    pub fn observe_size(&mut self, latest_storage_proof_size: usize) -> Result<(), VMLogicError> {
        self.last_observed_storage_size = latest_storage_proof_size;

        let current_size = self.get_storage_size()?;
        if current_size > self.size_limit {
            let limit_u64 = self.size_limit.try_into().map_err(|_| {
                VMLogicError::InconsistentStateError(InconsistentStateError::IntegerOverflow)
            })?;
            return Err(VMLogicError::HostError(HostError::RecordedStorageExceeded {
                limit: ByteSize::b(limit_u64),
            }));
        }

        Ok(())
    }
```
