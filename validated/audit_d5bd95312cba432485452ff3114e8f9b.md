### Title
Untrusted Sierra-to-native/CASM compilation subprocesses are isolated only by POSIX rlimits, not Seccomp-BPF - ([File: crates/apollo_compilation_utils/src/compiler_utils.rs])

### Summary
When a user declares a new class, the sequencer's gateway/sierra-compiler service compiles the attacker-supplied Sierra program to CASM (`SierraToCasmCompiler`) and, when Cairo-Native is enabled, to native machine code (`SierraToNativeCompiler`) by spawning an external compiler binary as a subprocess on fully attacker-controlled input [1](#0-0) [2](#0-1) . The only isolation applied to this subprocess is `ResourceLimits`, which sets POSIX rlimits (CPU time, file size, address space) via `pre_exec`/`setrlimit` [3](#0-2) . There is no Seccomp-BPF (or namespace/container) restriction on the syscalls available to this subprocess, matching the report's bug class exactly: a process handling untrusted, attacker-influenced input is protected only by coarse-grained controls (rlimits here, SELinux in the report) and not by fine-grained syscall filtering.

### Finding Description
The compilation flow is: `compile_with_args` in `apollo_compilation_utils/src/compiler_utils.rs` serializes the attacker-provided `ContractClass` to a temp file, spawns `Command::new(compiler_binary_path)` with that file as an argument, applies `ResourceLimits::apply` (rlimits only), and executes the compiler binary, capturing stdout/stderr [4](#0-3) . This is used by both the CASM compiler path (`SierraToCasmCompiler::compile`) [1](#0-0)  and the Cairo-Native compiler path (`SierraToNativeCompiler::compile`) [2](#0-1) , both of which operate on Sierra programs supplied via a DECLARE transaction from any unprivileged user. A code comment in the reexecution module explicitly acknowledges this design: "unlike the sequencer gateway (which compiles user-submitted classes in a resource-limited subprocess), no process isolation is needed" for chain-fetched classes [5](#0-4) , confirming that rlimits are the sequencer's sole isolation mechanism for this subprocess and that its own documentation frames rlimits as "process isolation."

The `ResourceLimits` struct only restricts CPU time, file size, and virtual-memory size [6](#0-5) ; it does not use Seccomp-BPF, `chroot`/namespaces, or capability dropping. If the external cairo-lang or cairo-native compiler binary contains a memory-safety bug reachable via a maliciously crafted Sierra program (e.g., in the LLVM/MLIR codegen backend used by cairo-native, or in the Python/Rust CASM compiler), an attacker who simply submits a DECLARE transaction can trigger memory corruption in that subprocess. Because the subprocess is not syscall-filtered, an attacker who achieves code execution there is not confined to a minimal syscall surface — they retain access to the full syscall table available to the sequencer's OS user (subject only to the rlimits set), including filesystem access, process spawning, and network syscalls, unlike a properly Seccomp-BPF-sandboxed compiler that would be restricted to a minimal allow-list (e.g., read/write/exit/mmap only).

### Impact Explanation
This subprocess runs with the same OS user privileges as the sequencer's gateway/sierra-compiler service and has access to whatever the OS-level permissions of that user allow (network sockets, other files on disk, etc.), since only CPU/file-size/memory rlimits are enforced, not a syscall allow-list. A single attacker-controlled DECLARE transaction can reach this code path with zero special privileges, since class declaration is open to any account. Successful exploitation of a memory-safety bug in the compiler backend would allow arbitrary code execution on the sequencer node under the compiler subprocess's privileges, which is a severe integrity/confidentiality risk to node operation (though it does not by itself alter consensus state — the compiler runs in the gateway/sierra-compiler service, isolated from the CASM/root computation, but a compromised host could still be used to disrupt the sequencer, exfiltrate secrets, or pivot to affect subsequent block building on that node).

### Likelihood Explanation
Likelihood depends on the existence of an exploitable memory-corruption bug in the external cairo-lang/cairo-native compiler toolchain reachable via a crafted Sierra program — this is plausible given that both are large, actively-developed native/JIT compiler toolchains (LLVM/MLIR-based for cairo-native) that parse fully attacker-supplied bytecode. The attack requires only a standard DECLARE transaction, so the entry point is trivially reachable by an unprivileged user; the main uncertainty is whether such a memory-safety bug currently exists in the shipped compiler binaries, which cannot be confirmed via static code review alone.

### Recommendation
Apply Seccomp-BPF (or an equivalent syscall allow-list / sandbox, e.g. via `libseccomp`, gVisor, or a minijail-style wrapper) to the compiler subprocess spawned in `compile_with_args`, restricting it to only the syscalls needed to read its input file, write output, and exit. Combine this with the existing rlimits, and consider running the compiler under a dedicated low-privilege user/namespace with no network access. Extra care must be taken whenever the compiler binaries (cairo-lang, cairo-native) are updated to ensure the required syscall set has not changed.

### Proof of Concept
1. An attacker crafts a Sierra `ContractClass` designed to trigger a memory-safety bug in the target compiler binary (CASM compiler or cairo-native AOT compiler) — e.g., an out-of-bounds write during MLIR/LLVM codegen for a pathological Sierra program.
2. The attacker submits a DECLARE transaction containing this class.
3. The gateway/sierra-compiler service calls `SierraToCasmCompiler::compile` or `SierraToNativeCompiler::compile`, which invokes `compile_with_args`, spawning the compiler binary on the attacker's file with only rlimits applied [4](#0-3) .
4. If the crafted input triggers memory corruption, the attacker gains code execution inside the subprocess, which is not restricted by any syscall filter and can perform any syscall permitted to the sequencer's OS user (subject to the rlimit caps only).

    /// Set all defined resource limits for the current process. Limits set to `None` are ignored.
    pub fn set(&self) -> io::Result<()> {
        [self.cpu_time.as_ref(), self.file_size.as_ref(), self.memory_size.as_ref()]
            .iter()
            .flatten()
            .try_for_each(|resource_limit| resource_limit.set())
    }

    /// Apply the resource limits to a given command object. This moves the [`ResourceLimits`]
    /// struct into a closure that is held by the given command. The closure is executed in the
    /// child process spawned by the command, right before it invokes the `exec` system call.
    pub fn apply(self, command: &mut Command) -> &mut Command {
        if self.cpu_time.is_none() && self.file_size.is_none() && self.memory_size.is_none() {
            return command;
        }
        unsafe {
            // The `pre_exec` method runs a given closure after the parent process has been forked
            // but before the child process calls `exec`.
            //
            // This closure runs in the child process after a `fork`, which primarily means that any
            // modifications made to memory on behalf of this closure will **not** be visible to the
            // parent process. This environment is often very constrained. Normal operations--such
            // as using `malloc`, accessing environment variables through [`std::env`] or acquiring
            // a mutex--are not guaranteed to work, because after `fork`, only one thread exists in
            // the child process, while there may be multiple threads in the parent process.
            //
            // This closure is considered safe for the following reasons:
            // 1. The [`ResourceLimits`] struct is fully constructed and moved into the closure.
            // 2. No heap allocations occur in the `set` method.
            // 3. `setrlimit` is an async-signal-safe system call, which means it is safe to invoke
            //   after `fork`. This is established in the POSIX `fork` specification:
            //   > ... the child process may only execute async-signal-safe operations until such
            //    time as one of the `exec` functions is called.
            //   (See <https://pubs.opengroup.org/onlinepubs/9699919799/functions/fork.html>)
            command.pre_exec(move || self.set())
        }
    }
