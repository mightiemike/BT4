### Title
Bitcoin fee-based mining-order manipulation of pre-signed council `BatchProofMethodId` reveals permanently discards a lower-activation-height, validly-signed method-id upgrade - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`LightClientProofCircuit::run_l1_block` processes `DataOnDa::BatchProofMethodId` blobs strictly in DA-scan order and enforces `activation_l2_height > last_activation_height` before validating signatures. If a council-signed upgrade for a higher activation height `H2` is DA-confirmed in an earlier L1 block than a council-signed upgrade for a lower activation height `H1` (achievable by an unprivileged party fee-bumping mining priority of the already-broadcast H2 reveal transaction), the later-processed H1 blob is silently and permanently skipped even though it carries a valid 3-of-5 council signature.

### Finding Description
The binding this code assumes is: for every council-signed body `(activation_l2_height, method_id)`, there exists a matching entry `(activation_l2_height, method_id) ∈ BatchProofMethodIdAccessor::get(..)`. This binding is broken purely by DA-inclusion reordering.

`verify_method_id_security_council` in `crates/light-client-prover/src/circuit/method_id_verifier.rs` only checks the cryptographic validity of the 3-of-5 signatures and does not order-independently establish which activation heights are "known-valid"; it is gated behind the height comparison and is never reached for a skipped blob. [2](#0-1) 

Exploit flow: the security council pre-signs and broadcasts two reveal transactions to the Bitcoin mempool — one for `(H1, method_id_A)` and one for `(H2, method_id_B)` with `H1 < H2`. An unprivileged attacker (allowed under the rules to "pay Bitcoin fees to inscribe or mine any Bitcoin transaction") fee-bumps/CPFP's the H2 transaction (or otherwise incentivizes a miner) so it confirms in an earlier L1 block than H1's transaction. `run_l1_block` processes L1 blocks in chain order, so it encounters H2 first, calls `BatchProofMethodIdAccessor::insert(H2, method_id_B, ..)`, setting `last_activation_height = H2`. When the block containing H1 is later processed, `H1 <= last_activation_height (H2)` is true, so the branch `continue`s before even checking `chain_id` or verifying signatures — `method_id_A` for `H1` is never inserted, permanently.

No existing guard prevents this: the only ordering check is against `last_activation_height` in accessor state, which is itself a function of DA processing order, not of the activation heights the council intended. The repo's own test suite exercises exactly this skip path and asserts it as intended behavior (`crates/light-client-prover/src/tests/mod.rs` lines 1146-1196: a lower-activation-height blob submitted after a higher one is dropped and the method id list "didn't change"). [3](#0-2) 

### Impact Explanation
Downstream, `process_complete_proof` selects the method id to verify a batch proof against via `binary_search_by_key` over the accessor's activation-height list keyed on the batch proof's `last_l2_height`:
```rust
let idx = match batch_proof_method_ids.binary_search_by_key(&batch_proof_output_last_l2_height, |(height, _)| *height) {
    Ok(idx) => idx,
    Err(idx) => idx.saturating_sub(1),
};
``` [4](#0-3) 
If `H1`'s entry is missing, any batch proof for the L2 range that should use `method_id_A` (activated at `H1`) instead resolves to whichever entry precedes `H1` in the (now-gapped) list, so `Z::verify` is invoked with the wrong method id and legitimately-produced proofs for that range can never verify. This is a true, council-authorized state transition/method-id upgrade made permanently unprovable, matching the Critical category "a true one made unprovable," and it is repeatable for any sequential council upgrade pair as long as an attacker can influence relative Bitcoin block inclusion order.

### Likelihood Explanation
Preconditions require the security council to broadcast two upgrade transactions to mempool before either confirms (an operational choice, but one explicitly granted as precondition in this question). Given that, the only attacker action needed is a routine, cheap fee-bump/CPFP on the higher-activation transaction to get it mined first — well within the stated attacker capability ("pay Bitcoin fees to inscribe or mine any Bitcoin transaction"), requires no signature forgery, no privileged role, and no majority hashrate. This is realistically feasible any time the council does not strictly serialize (wait for confirmation before broadcasting the next) its upgrade transactions.

### Recommendation
Do not gate acceptance of a `BatchProofMethodId` blob solely on comparison to the last *inserted* activation height, which is an artifact of DA processing order. Instead, either: (1) require the council to include a monotonically increasing nonce/sequence number in the signed body which is checked against a persisted "highest signed sequence" counter and always accept out-of-order entries as long as they don't decrease the sequence already covered, or (2) collect all `BatchProofMethodId` blobs seen within the processed window and insert them sorted by `activation_l2_height` rather than DA-arrival order, discarding a lower height only if a duplicate/replay of the exact same or already-applied height, not simply because a higher one for a subsequent upgrade was seen earlier.

3. Run `run_l1_block`/`native_circuit_runner.run` first with the H2 blob in block N, then with the H1 blob in block N+1.
