## Analysis

The C4 report's core bug pattern is: **canonical state is marked "done" (reward marked as claimed) *before* the actual value transfer completes**, and when the transfer silently fails due to a mismatch between two independently-maintained lists of "what's valid," the loss is permanent and undetectable (no revert, no distinct error signal).

I found a structurally identical pattern in Push Chain's `x/uexecutor` outbound-creation path.

### Root cause [1](#0-0) 

When a UEA payload executes successfully, `payloadPcTx.Status = "SUCCESS"` is recorded on the `UniversalTx` **unconditionally**, and only *afterward* does the code try to attach any outbound(s) produced by that execution via `AttachOutboundsToExistingUniversalTx`. If that call fails, the error is stuffed into a cosmetic `RevertError` string field with no other remediation: [2](#0-1) 

`AttachOutboundsToExistingUniversalTx` calls `BuildOutboundsFromReceipt`, which looks up destination-chain enablement and token config using data taken straight from the EVM withdraw event (`event.ChainId`, `event.Token`) rather than any independently-verified source: [3](#0-2) 

If `GetTokenConfigByPRC20(chain, token)` doesn't find a match (chain/token combination not registered in `x/uregistry`) or `IsChainOutboundEnabled` returns false, `BuildOutboundsFromReceipt` returns an error, which propagates up and is swallowed as a mere `RevertError` note — no `OutboundTx` is ever created, so it is never indexed into `PendingOutbounds`, never picked up by Universal Validators, never signed by TSS, and never broadcast: [4](#0-3) 

Same pattern repeats in the gas-and-payload path: [5](#0-4) 

### Why this mirrors the C4 finding

- Just like `p.userStates[user].rewards = 0` is set *before* confirming reward tokens actually match the hardcoded list, `PcTx.Status = "SUCCESS"` is written *before* confirming the resulting outbound was actually attached.
- Just like the reward-token mismatch (`PirexGmx`'s hardcoded list vs `PirexRewards`'s owner-editable list), here there are two independent sources of truth: the EVM gateway contract's withdraw event (attacker/user-influenced `ChainId`/`Token` fields) vs. `x/uregistry`'s `ChainConfigs`/`TokenConfigs`. A mismatch between them silently drops the outbound.
- Just like the C4 bug, there's no revert of the whole transaction and no distinguishable failure signal in the primary success-path fields — only a buried `RevertError` string, making the loss hard to detect operationally, exactly as the report's "hard to detect" point notes about the missing `Claim` revert.
- The underlying EVM-side withdraw/burn already occurred as part of the "successful" payload execution (that's how the gateway emits the `UniversalTxWithdraw` event in the first place), so once `BuildOutboundsFromReceipt` fails, the burned/withdrawn value has no corresponding release path on the destination chain and no automatic refund back to the user on Push Chain — this is a permanent loss.

### Reachability without privileged actors

An ordinary user submitting `MsgExecutePayload` (gasless, any-user message per `x/uexecutor/README.md`) can drive their own UEA to call the gateway contract's withdraw path with a `ChainId`/`Token` combination that doesn't correspond to an actually registered `TokenConfig` (e.g., valid PRC20 balance but a chain string uregistry never onboarded, or a PRC20/chain pairing that doesn't match what was registered). This requires no admin misconfiguration and no malicious validator — it's a plain mismatch between attacker-influenced event data and the registry, hit by the code's fail-open handling of `attachErr`. [6](#0-5) 

I don't have visibility into the Solidity-side `UniversalGatewayPC.withdraw()` validation logic (outside this repo's scope) to confirm whether it independently blocks unregistered chain/token pairs before emitting the event — that would need to be checked to fully confirm exploitability, but the Go-side handling itself has no defense-in-depth: it treats a failed outbound attachment as a non-fatal, silent bookkeeping note rather than rolling back or flagging the UTX as unresolved/failed.

```go
func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
```

```go
func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}
```
