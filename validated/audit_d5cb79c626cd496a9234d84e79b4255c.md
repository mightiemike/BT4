### Title
Intermediate `long` overflow in `execute()`'s `multiplyExact` diverges from `doValidate()`'s overflow-free `BigInteger` math, causing validator-approved `ExchangeInjectContract` transactions to deterministically fail at execution - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`doValidate()` computes `anotherTokenQuant` using `BigInteger.multiply()`/`divide()` (no intermediate cap) and only requires the *final* result to fit in a `long` via `longValueExact()`. `execute()` instead computes the exact same ratio using `multiplyExact(secondTokenBalance/firstTokenBalance, tokenQuant)` **before** dividing, so the intermediate product must itself fit in a `long`. Any input where `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) exceeds `Long.MAX_VALUE` but the quotient after dividing by the other balance fits in a `long` will pass `validate()` and then always throw `ArithmeticException` in `execute()`.

### Finding Description
In `doValidate()`: [1](#0-0) 
the ratio is computed with arbitrary-precision `BigInteger` arithmetic — `bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` — so the multiplication itself can never overflow; only the final `longValueExact()` on the already-divided result can throw, and that's caught and converted into a normal `ContractValidateException` at: [2](#0-1) 

In `execute()`, the same computation is instead done in raw `long` space, multiplying first and dividing second: [3](#0-2) 
`multiplyExact(secondTokenBalance, tokenQuant)` throws `ArithmeticException` whenever the *unreduced* product overflows `long`, even when the true mathematical ratio (product divided by `firstTokenBalance`) fits comfortably in a `long`.

Because the exchange's own balance-limit check only bounds each balance/quant individually and not their product: [4](#0-3) 
values near the balance limit (e.g. `secondTokenBalance ≈ 10^15`, `tokenQuant ≈ 10^15`, `firstTokenBalance ≈ 10^15`) make `secondTokenBalance * tokenQuant ≈ 10^30`, which vastly exceeds `Long.MAX_VALUE` (~9.2×10^18) and is caught by `multiplyExact` in `execute()`, while `BigInteger` computes `10^30 / 10^15 = 10^15` cleanly in `doValidate()`, passing all validation checks (`anotherTokenQuant > 0`, `newTokenBalance/newAnotherTokenBalance <= balanceLimit`, balance-sufficiency checks).

The attacker in this scenario must be the exchange's creator (enforced by the creator-address check at lines 175-177), since only the creator may call `ExchangeInjectContract`. Exchange creation itself is permissionless (`ExchangeCreateActuator`), so any unprivileged account that creates its own exchange with near-limit balances can trigger this divergence on its own contract calls.

### Impact Explanation
Every such transaction passes `validate()` (accepted into a block / considered valid by the mempool and consensus) but then unconditionally throws `ArithmeticException` inside `execute()`, causing `ContractExeException` and `code.FAILED` at: [5](#0-4) 
Since `calcFee()` returns `0`: [6](#0-5) 
no TRX fee is burned, but the transaction still consumes bandwidth/energy resources and occupies block space while guaranteed to fail, and legitimate liquidity injection into the exchange is impossible for these balance ranges — a deterministic validate/execute divergence (invariant violation) rather than a pure griefing-of-others vector, since only the exchange creator can trigger it against their own exchange.

### Likelihood Explanation
Fully deterministic and reproducible: any exchange whose balances/quant are chosen so that `secondTokenBalance * tokenQuant` (or the symmetric `firstTokenBalance * tokenQuant`) exceeds `Long.MAX_VALUE` while the true ratio fits in `long` will trigger this every time. Reaching such balances only requires creating an exchange and injecting liquidity up to values permitted by `dynamicStore.getExchangeBalanceLimit()`, which is attacker-controlled and requires no special privilege beyond being the exchange's own creator.

### Recommendation
Make `execute()`'s arithmetic consistent with `doValidate()` by using `BigInteger` (or `Math.multiplyHigh`/`Math.floorMod`-safe 128-bit emulation) for the same multiply-then-divide computation, or conversely have `doValidate()` compute the value the same way `execute()` does (checked `long` multiply before divide) so that both phases agree on success/failure for every input. The safest fix is to centralize the ratio computation in a single shared helper method used by both `validate()` and `execute()`.

### Proof of Concept
```java
// Java unit test (JUnit) — add to ExchangeInjectActuatorTest.java
@Test
public void validateExecuteArithmeticDivergence() throws Exception {
    dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);
    long exchangeId = 99;
    long firstBal = 1_000_000_000_000_000L;  // 10^15
    long secondBal = 1_000_000_000_000_000L; // 10^15
    long tokenQuant = 1_000_000_000_000_000L; // 10^15, injected into "firstTokenId"
    // secondBal * tokenQuant = 10^30 overflows long (Long.MAX_VALUE ~9.2e18)
    // but BigInteger result / firstBal = 10^15, fits in long comfortably

    ExchangeCapsule exchangeCapsule = new ExchangeCapsule(
        ByteString.copyFrom(ByteArray.fromHexString(OWNER_ADDRESS_FIRST)),
        exchangeId, 1000000, "1".getBytes(), "2".getBytes());
    exchangeCapsule.setBalance(firstBal, secondBal);
    dbManager.getExchangeV2Store().put(exchangeCapsule.createDbKey(), exchangeCapsule);

    // fund owner account with enough of "1" token and TRX for fee/limits (test-specific setup omitted)

    ExchangeInjectActuator actuator = new ExchangeInjectActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager())
        .setAny(getContract(OWNER_ADDRESS_FIRST, exchangeId, "1", tokenQuant));

    // validate() succeeds (BigInteger path, no overflow)
    Assert.assertTrue(actuator.validate());

    // execute() throws ContractExeException due to multiplyExact overflow
    TransactionResultCapsule ret = new TransactionResultCapsule();
    try {
        actuator.execute(ret);
        Assert.fail("Expected ContractExeException from execute() due to long overflow divergence");
    } catch (ContractExeException e) {
        Assert.assertTrue(e.getCause() instanceof ArithmeticException
            || e.getMessage().toLowerCase().contains("overflow"));
    }

    dbManager.getExchangeV2Store().delete(ByteArray.fromLong(exchangeId));
}
```
Expected assertion failure demonstrates: `validate()` returns `true` (no exception) while `execute()` throws `ContractExeException` wrapping an `ArithmeticException`, proving the two phases disagree on the same input.
