### Title
Missing Case Normalization in `sanitizeShop()` Enables Cross-Session Confusion for Shop Domains - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
The `sanitizeShop()` function's validation regex accepts uppercase characters in shop subdomains and does not normalize the shop value to lowercase before it is used to build session IDs and session-storage lookup keys throughout the library and all downstream `shopify-app-*` packages.

### Finding Description
`sanitizeShop()` validates shop domains using a regex that explicitly permits mixed-case input: [1](#0-0) 
The function returns the shop string unchanged (aside from admin-URL-to-legacy-URL conversion) — it never lowercases the value: [2](#0-1) 

This unsanitized-case `shop` string is subsequently used as the literal input to build session identifiers and lookup keys: [3](#0-2) 

These IDs/keys are then used for exact-match, case-sensitive lookups and comparisons across every session storage adapter (`findSessionsByShop` uses `eq(table.shop, shop)` / exact key equality) and in session validation logic that compares `session.shop !== shop`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because real Shopify shop hostnames are DNS names (case-insensitive at the network/HTTP layer), a `shop` value differing only in letter casing (e.g. `Test-Shop.myshopify.com` vs. `test-shop.myshopify.com`) will resolve to, and successfully complete OAuth/token-exchange with, the exact same underlying Shopify store, yet the library treats it as a **distinct tenant key** for session storage purposes (distinct `offline_<shop>` id, distinct `findSessionsByShop` results, distinct comparison in `validate-authenticated-session.ts`).

### Impact Explanation
An attacker who can influence the case of the `shop` query parameter passed to an app's install/auth entry point (a value the docs explicitly warn is often taken from "user inputs or URLs" — see `getOfflineId` warning) can cause a legitimate, valid OAuth flow to complete for the real shop but have the resulting access-token session persisted under a differently-cased, non-canonical session key. Concretely, `AppInstallations.delete()` (invoked by the shopify-app-express uninstall webhook handler) calls `findSessionsByShop(shopDomain)` with the canonical (webhook-provided) casing to purge all sessions for a shop on uninstall. Any session previously stored under an alternate-case variant of that same shop will not be matched by this exact-string lookup and will therefore survive the uninstall cleanup, leaving a stale, still-valid access token in storage for a shop that the merchant believes has fully uninstalled/revoked the app. This is a genuine session-storage/lookup defect reachable from a single merchant/installation flow, not a privileged-actor-only or theoretical issue.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires an attacker (or a misbehaving client/redirect) to get an app to process an installation/auth request with a non-canonically-cased `shop` parameter at least once before the legitimate uninstall occurs. Since `sanitizeShop()` deliberately accepts uppercase and the `shop` parameter is commonly sourced from URLs/query strings across all `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express` entry points, this condition is realistically reachable via a crafted install link.

### Recommendation
Normalize the shop domain to lowercase inside `sanitizeShop()` before it is returned (and before it is used to build any session ID or storage key), mirroring the report's recommended on-chain-analog fix: canonicalize the identifier once, at the boundary, so all downstream exact-match session lookups, comparisons, and storage keys are guaranteed consistent regardless of the casing supplied in the original request.

### Proof of Concept
1. App exposes `/auth?shop=<value>` (standard for `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router`).
2. Attacker sends `/auth?shop=Test-Shop.myshopify.com` (mixed case) for a shop that legitimately exists as `test-shop.myshopify.com`.
3. `sanitizeShop()` accepts it unchanged (regex allows `[a-zA-Z0-9]`), so OAuth begins and completes successfully against the real `test-shop.myshopify.com` store (DNS/HTTP is case-insensitive).
4. The resulting offline session is stored with id `offline_Test-Shop.myshopify.com` (per `getOfflineId`), a different key than the canonical `offline_test-shop.myshopify.com` that would be created/queried by normal (lowercase) flows and by the `APP_UNINSTALLED` webhook cleanup path (`AppInstallations.delete('test-shop.myshopify.com')` → `findSessionsByShop('test-shop.myshopify.com')`).
5. When the merchant uninstalls the app, the webhook-driven cleanup only deletes sessions keyed under the canonical lowercase shop string, leaving the `offline_Test-Shop.myshopify.com` session (with a valid access token) in storage.

```typescript
  public async findSessionsByShop(shop: string): Promise<Session[]> {
    await this.ready;

    const idKeysArrayString = await this.client.get(shop);
    if (!idKeysArrayString) return [];

    const idKeysArray = JSON.parse(idKeysArrayString);
    const results: Session[] = [];
    for (const idKey of idKeysArray) {
      const rawResult = await this.client.get(idKey, false);
      if (!rawResult) continue;

      const session = Session.fromPropertyArray(JSON.parse(rawResult), true);
      results.push(session);
    }

    return results;
  }
```

```typescript
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
```
