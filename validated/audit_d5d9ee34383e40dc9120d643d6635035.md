## Title
`DeleteAccountAction` balance refund can be front-run and permanently burnt by deleting the beneficiary account first - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally emits a balance-refund receipt to `beneficiary_id` without any guarantee that the beneficiary account will still exist by the time that receipt executes. If an attacker deletes the beneficiary account first (a normal, unprivileged transaction), the refund receipt fails and the entire transferred balance is permanently burnt instead of reaching anyone. This mirrors the Y2K `triggerNullEpoch`/`triggerEndEpoch` pattern: a value-moving operation is dispatched based on a precondition (target account/vault exists and can receive value) that a second, independently-triggerable transaction can invalidate first, causing funds to be irrecoverably lost.

### Finding Description
When `DeleteAccountAction` executes, the remaining account balance is unconditionally queued as a refund receipt to the configured beneficiary, with no existence check on `beneficiary_id` at execution time: [1](#0-0) 

The only "validation" performed on the beneficiary is that it must be a *syntactically* valid account ID; the docs confirm nothing else is verified: [2](#0-1) 

The refund is delivered as a separate `Receipt` whose `predecessor_id` is `"system"` — i.e., a refund receipt. Refund receipts are explicitly barred from creating any account, including implicit ones: [3](#0-2) [4](#0-3) 

Consequently, if `beneficiary_id` does not exist (or has just been deleted) when the refund receipt is applied, `check_account_existence` returns `AccountDoesNotExist`, the refund receipt's actions fail, and the runtime burns the deposit rather than returning it to anyone: [5](#0-4) 

This behavior is documented as the general policy for all refunds: [6](#0-5) 

Because the refund receipt to `beneficiary_id` is a distinct, asynchronously-delivered receipt (it is not part of the original transaction's atomic execution and can cross shards), there is a real window during which an adversary who controls the `beneficiary_id` account can submit an ordinary `DeleteAccount` transaction against their own account, racing to have it applied before the victim's refund receipt executes. Once the beneficiary account is gone, the victim's transferred balance is destroyed outright.

### Impact Explanation
This is a concrete, protocol-level mechanism for irrecoverable, unauthorized loss of user funds: a legitimate value transfer (a user closing their account and sending the residual balance to a chosen beneficiary) can be converted into a permanent burn by an unrelated third-party transaction that only touches the beneficiary's own account. No signature or permission over the victim's funds is required by the attacker — they need only control the account named as beneficiary and win an ordinary transaction race. The result is a state-level, protocol-accepted supply reduction that was never authorized by the victim, matching the "permanently frozen/burnt funds via a transaction-triggered path" impact class.

### Likelihood Explanation
The precondition is narrow but realistic: it requires the victim to name an account as `beneficiary_id` that the attacker also controls or can influence to be deleted in time (e.g., a shared/service account, an account the attacker was given control of, or a beneficiary the attacker can front-run because they can observe the pending `DeleteAccount` transaction in the mempool/chunk before it is applied on the beneficiary's shard). Given the asynchronous, cross-shard nature of the refund receipt, an attacker monitoring the network has a practical window to submit a competing `DeleteAccount` against the beneficiary account. This does not require any privileged, validator, or network-level capability — only two ordinary signed transactions from unprivileged accounts.

### Recommendation
Before emitting the beneficiary refund receipt in `action_delete_account`, or upon refund-receipt failure, avoid unconditional burning of the deleted account's balance to an account whose existence was never checked:
- Verify `beneficiary_id` account existence prior to committing the deletion, and/or
- On refund-receipt failure specifically for `DeleteAccount` balance transfers, redirect the amount to a canonical fallback (e.g., the protocol treasury) or make deletion transactionally atomic with the beneficiary transfer instead of a separate best-effort receipt, so failures cannot silently destroy user funds.

### Proof of Concept
1. Account `V` (victim) holds balance `B` and intends to delete itself with `beneficiary_id = A` (attacker-controlled account), submitting the `DeleteAccount` transaction as shown in the actions module: [1](#0-0) .
2. `V`'s transaction is converted into an action receipt that removes `V`'s account and queues a `Receipt::new_balance_refund(A, B)` to be delivered asynchronously (potentially on a different shard/chunk).
3. Attacker, observing this pending balance-refund receipt (or simply racing preemptively), submits an ordinary `DeleteAccount` transaction on account `A` with any beneficiary, so that `A` no longer exists by the time the refund receipt to `A` executes.
4. When the refund receipt executes, `check_account_existence` for the `Transfer` action against `A` returns `AccountDoesNotExist` (refunds cannot create accounts, per `implicit_creation_allowed`): [3](#0-2) .
5. Because the receipt's `predecessor_id` is `"system"`, the runtime treats the failure as a refund failure and burns the entire deposit `B` into `other_burnt_amount` instead of returning it to `V` or delivering it to `A`: [5](#0-4) .
6. `V`'s balance `B` is permanently destroyed with no recourse, solely as a result of the attacker's unrelated, unprivileged transaction on their own account.
