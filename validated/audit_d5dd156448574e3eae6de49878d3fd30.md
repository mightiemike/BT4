### Title
Uncontrolled recursion in `sort_json_value` / `serde_json::Value` deserialization during Cairo0 hinted class hash computation causes unrecoverable process crash - (File: `crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs`)

### Summary
`compute_cairo_hinted_class_hash` deserializes a declared Cairo0 contract's `abi`, `program.identifiers`, `program.reference_manager`, `program.hints`, and `AttributeScope` fields as raw, schema-less `serde_json::Value` trees, and then recursively walks/sorts them via `sort_json_value` with no depth limit and no stack-safety guard, analogous to the unguarded recursive `WriteValue()` in the reported Scriban advisory.

### Finding Description
`compute_cairo_hinted_class_hash` re-serializes the deprecated (Cairo0) `ContractClass` to a `serde_json::Value`, then calls `sort_json_value`, which recurses into every nested `Object`/`Array` with no depth bound: [1](#0-0) 
This value tree originates from attacker-controlled JSON structures embedded in the Cairo0 contract class the declare-transaction sender supplies — `abi` is untyped (`pub abi: serde_json::Value`), and `program.identifiers`, `program.reference_manager`, `program.hints`, `AttributeScope::accessible_scopes`, and `AttributeScope::flow_tracking_data` are also untyped `serde_json::Value`/`Vec<serde_json::Value>` fields: [2](#0-1) 
`compute_cairo_hinted_class_hash` performs the vulnerable path: `serde_json::to_value` → `sort_json_value` (unbounded recursion) → `serde_json::from_slice::<CairoContractDefinition>` (which itself recursively deserializes nested `Value`/`Object`/`Array` JSON, another unguarded recursive-descent parse) → re-serialization: [3](#0-2) 

Neither `sort_json_value`'s manual recursion nor `serde_json`'s internal `Value` (de)serialization recursion (used pervasively for the untyped fields) enforces a depth limit or calls anything analogous to Rust's `std::thread::stack_size`/guard-page mitigation. A deeply nested JSON array/object (e.g., `[[[[[...]]]]]]` nested to hundreds of thousands of levels) supplied inside the `abi`, `program.identifiers`, `program.hints`, or `AttributeScope` fields of a declared Cairo0 class will exhaust the call stack during either the `serde_json::from_slice` deserialization or the subsequent `sort_json_value` recursion, causing a Rust stack overflow. In Rust this manifests as an unrecoverable process abort (SIGSEGV via guard page / `fatal runtime error: stack overflow`) — just as `StackOverflowException` cannot be caught in .NET, a Rust stack overflow cannot be caught by `catch_unwind` and terminates the process.

This hint/utility is invoked from the Starknet OS deprecated-class-hash hint implementation (`crates/starknet_os/src/hints/hint_implementation/deprecated_compiled_class/class_hash.rs`, `crates/starknet_os/src/hints/class_hash.rs`), i.e., during Starknet OS (re-)execution/proving of blocks containing a `DECLARE` transaction for a Cairo0 class — a path reachable purely by submitting a `DECLARE` (V0/V1) transaction with a maliciously crafted contract class through the gateway.

### Impact Explanation
A successfully admitted `DECLARE` transaction (or one included/re-executed by the Starknet OS) referencing a Cairo0 class with a deeply nested `abi`/`identifiers`/`hints`/`reference_manager` JSON structure will crash the process performing hinted-class-hash computation (the sequencer's OS execution/re-execution component and any node computing this hash) with an unrecoverable stack overflow. This is a process-level denial of service: the affected node process aborts and cannot continue producing/validating/re-executing blocks, potentially halting block production/finalization for the network segment relying on that process — satisfying the "network unable to confirm new transactions" bar. It does not require any privileged actor: any DECLARE-transaction sender can supply the crafted class.

### Likelihood Explanation
Likelihood is moderate-to-high in principle (a single declare transaction can carry the payload), but is bounded by whatever transaction/class size limits the gateway enforces (`max_contract_class_object_size`, `MAX_CAIRO0_PROGRAM_SIZE = 4MB` decompressed limit seen in `apollo_protobuf::converters::class`) — a deeply nested JSON structure like repeated `[` characters is extremely compact (2 bytes per nesting level), so even a 4MB budget is more than sufficient to reach recursion depths that exceed typical thread stack sizes (typically ~2–8MB) well before hitting the byte-size cap. I was not able to fully confirm within the available context whether `apollo_gateway`'s stateless/stateful validators reject such structures prior to `compute_cairo_hinted_class_hash` being invoked (e.g., whether class-hash computation happens at gateway admission time versus only in OS re-execution), nor whether a JSON parsing-depth guard exists elsewhere in the pipeline that I did not locate. This uncertainty should be resolved by a deeper trace of the exact call path from gateway declare-tx admission through to `compute_cairo_hinted_class_hash`/OS hint execution.

### Recommendation
- Add an explicit recursion-depth counter to `sort_json_value` and reject/short-circuit (returning an error) once a configured maximum nesting depth (e.g., matching or below `serde_json`'s safe limits) is exceeded, mirroring the `ObjectRecursionLimit` pattern recommended in the referenced advisory.
- Validate/bound the maximum JSON nesting depth of the `abi`, `program.identifiers`, `program.hints`, `program.reference_manager`, and `AttributeScope` fields as early as possible in the declare-transaction validation pipeline (stateless gateway validation), before any recursive processing occurs, so malformed classes are rejected at admission rather than reaching OS execution.
- Consider running class-hash computation for untrusted, attacker-supplied classes in a way that fails safely on stack exhaustion (e.g., iterative traversal using an explicit stack/heap-allocated work list instead of native recursion) for both `sort_json_value` and the `serde_json::Value` (de)serialization of these untyped fields.

### Proof of Concept
Construct a Cairo0 `DECLARE` transaction whose contract class `abi` (or `program.identifiers` / `program.hints` / `program.reference_manager`) field is a deeply nested JSON array, e.g.:
```json
{
  "abi": [[[[[ ... nested ~500,000+ times ... ]]]]],
  "program": { "...": "..." },
  "entry_points_by_type": { ... }
}
```
Submitting this class through the gateway as a Cairo0 declare transaction and having it processed through `compute_cairo_hinted_class_hash` (either at admission time if invoked there, or during Starknet OS re-execution) will trigger unbounded recursion in `serde_json::from_slice::<CairoContractDefinition>` and/or `sort_json_value`, exhausting the stack and crashing the process — I was unable to execute this PoC directly (no code execution access), so this should be validated by a background agent with a running sequencer node/OS test harness.

/// Recursively sorts all JSON objects by their keys.
/// This ensures deterministic serialization regardless of the `preserve_order` feature in
/// serde_json.
fn sort_json_value(value: serde_json::Value) -> serde_json::Value {
    match value {
        serde_json::Value::Object(map) => {
            let sorted: BTreeMap<String, serde_json::Value> =
                map.into_iter().map(|(k, v)| (k, sort_json_value(v))).collect();
            serde_json::Value::Object(sorted.into_iter().collect())
        }
        serde_json::Value::Array(arr) => {
            serde_json::Value::Array(arr.into_iter().map(sort_json_value).collect())
        }
        other => other,
    }
}
