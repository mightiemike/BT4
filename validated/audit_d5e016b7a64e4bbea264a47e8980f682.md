### Title
Unbounded attacker-controlled `Inbound.RawPayload`/`VerificationData` lets a depositor prevent honest UVs from ever casting a matching `MsgVoteInbound`, permanently stalling ballot quorum and freezing bridged funds - (File: `x/uexecutor/types/msg_vote_inbound.go`, `x/uexecutor/types/inbound.go`, `x/uexecutor/types/keys.go`)

### Summary
`GetInboundBallotKey` hashes the entire `Inbound` message, including attacker-controlled, unbounded-length fields `RawPayload` and `VerificationData`, and every Universal Validator must independently submit a `MsgVoteInbound` carrying the exact same bytes to converge on that ballot key. Neither `MsgVoteInbound.ValidateBasic()` nor `Inbound.ValidateBasic()` places any length cap on these fields. A user who initiates a source-chain deposit event with an extremely large payload can make every subsequent `MsgVoteInbound` for that same event too large/expensive to include in a block, exactly analogous to the referenced bug where guardians had to resubmit an unbounded description string to reach the same hash the attacker had already produced cheaply once.

### Finding Description
`GetInboundBallotKey` (`x/uexecutor/types/keys.go:99-126`) computes the ballot identity as a digest over every consensus-relevant field of `Inbound`, explicitly including `utils.CanonicalizeHexBlob(inbound.VerificationData)` and `utils.CanonicalizeHexBlob(inbound.RawPayload)`. [1](#0-0) 

`MsgVoteInbound.ValidateBasic()` only checks that `Signer` parses and delegates to `Inbound.ValidateBasic()`. [2](#0-1) 

`Inbound.ValidateBasic()` deliberately validates only the minimal identity fields (`source_chain`, `tx_hash`, `sender`, `log_index`, `tx_type`) and explicitly defers payload/size validation to `ValidateForExecution`, which only runs after ballot finalization — never bounding the size of `RawPayload` or `VerificationData` at vote-ingress time. [3](#0-2) 

Because the vote message is gasless (in `IsGaslessTx`'s allowlist, `app/txpolicy/gasless.go:20`), and because `RawPayload`/`VerificationData` are populated straight from the source-chain event bytes that the depositing user fully controls (they craft the calldata/log data on the external gateway), a malicious depositor can emit an inbound event whose payload is deliberately sized to sit right at Push Chain's transaction-size / gas ceiling. `RecordInboundVote` (`x/uexecutor/keeper/inbound.go:14-32`) creates a `PendingInboundEntry`/ballot only on the *first successful* vote; if the first UV's vote transaction cannot even be included (oversized calldata or gas cost above the block/tx limits, further amplified because voting also runs `hashFields`/canonicalization and later ABI-decoding of the payload), the ballot never gets created at all.

The admin recovery path, `RevertStuckInbound` (`x/uexecutor/keeper/admin_revert.go:15-51`), strictly requires an existing ballot in `BALLOT_STATUS_EXPIRED`: [4](#0-3) 
If no ballot was ever created because no UV could get a vote transaction included, there is nothing for the admin to expire and nothing for `RevertStuckInbound` to act on (`TestRevertStuckInbound_BallotNotFound` explicitly demonstrates the "ballot for inbound not found" failure mode). [5](#0-4) 

This mirrors the external bug precisely: the party that must reproduce the exact hash input (here, every honest UV voting; there, the guardians cancelling) bears strictly higher calldata/gas cost than the attacker who produced the oversized data once, and there is no cap forcing the size to stay within what the "responder" can afford to resubmit.

### Impact Explanation
If exploited, funds a user deposits into the source-chain gateway for this inbound can become permanently stuck: they are already locked in the vault/gateway on the external chain, but Push Chain can never mint the PRC20/execute the payload (no quorum ever reached) and the built-in admin escape hatch (`RevertStuckInbound`) cannot fire because it depends on an `EXPIRED` ballot that never comes into existence. This matches the "permanent freezing of user-controlled funds" category in the allowed-impact list, triggered purely by an unprivileged user's own deposit/payload choice, with no relayer, validator, or admin misbehavior required.

### Likelihood Explanation
The attacker only needs to control the calldata of their own deposit/gateway event on any supported source chain — something any ordinary user submitting a `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound already does. No special privileges, collusion, or validator compromise are needed. The only uncertainty is the exact numeric threshold (Push Chain's configured max tx bytes / block gas limit, and the relative gas overhead the vote path adds via hashing/decoding vs. what a UV can still fit in a block) — I was not able to find an explicit `MaxTxBytes`/consensus-params value in the indexed slice of `app/app.go`, so the precise size at which this becomes practically exploitable is not fully confirmed from the available index and would need runtime/config verification (default CometBFT `max_bytes` is commonly in the low-single-digit MB range, well above a typical payload, but each additional matching `MsgVoteInbound` from *every* UV needing to carry the full block-limit-sized payload compounds the cost network-wide, which is the crux of the DoS-style bug class here).

### Recommendation
Enforce a strict maximum length on `Inbound.RawPayload` and `Inbound.VerificationData` (and any other unbounded byte/string fields folded into `GetInboundBallotKey`) inside `Inbound.ValidateBasic()`, rejecting inbounds whose payload exceeds a size that is comfortably votable by every UV within normal transaction/gas limits. Additionally, consider deriving the ballot key from a hash of the raw payload rather than the raw payload bytes themselves (so votes only need to carry a fixed-size commitment, not the full data), and/or extend `RevertStuckInbound`/`RecomputeBallotQuorum` (or an equivalent path) to also cover the "ballot never created" case so a stuck deposit can still be refunded by an admin.

### Proof of Concept
1. On a supported EVM/SVM source chain, a user calls the gateway's deposit-with-payload function, supplying a `FUNDS_AND_PAYLOAD` deposit whose payload is padded to be as large as feasible (e.g. hundreds of KB to a few MB of data), sized so that a Push Chain `MsgVoteInbound` embedding the equivalent `raw_payload` bytes will be right at or over the node's tx-size/gas ceiling once wrapped in `authz.MsgExec`, hashed via `GetInboundBallotKey`, and gas-metered through the ante pipeline.
2. Universal Validators observe this event and each attempt `MsgVoteInbound` (via `ExecVoteInbound`/`authz.MsgExec`) carrying the identical `RawPayload`; because `Inbound.ValidateBasic()` (`x/uexecutor/types/inbound.go:90-121`) never checks payload length, nothing prevents constructing the message, but node mempools/block builders reject or fail to include the oversized/over-gas transaction.
3. No UV vote lands → `RecordInboundVote` never runs → no `PendingInboundEntry`/ballot is ever created for this `utx_key`.
4. Admin attempts `MsgRevertStuckInbound`; `RevertStuckInbound` (`x/uexecutor/keeper/admin_revert.go:42-51`) fails with "ballot for inbound not found" (as shown by `TestRevertStuckInbound_BallotNotFound`), because there is no ballot to drive to `EXPIRED`.
5. The user's deposit remains locked on the source-chain gateway indefinitely, with no on-chain path (validator quorum or admin escape hatch) able to resolve it.

// ValidateBasic does minimal sanity checks needed to accept a vote.
// Only fields required to identify the inbound and create a UTX key are validated here.
// Execution-level validation (amount, addresses, payload, recipient) is deferred to
// ValidateForExecution so that invalid inbounds still produce an on-chain UTX record
// (with a failed PCTx / revert) instead of silently dropping the vote and leaving
// user funds stuck in the gateway.
func (p Inbound) ValidateBasic() error {
	// Validate source_chain (must follow CAIP-2 format) — needed for UTX key
	chain := strings.TrimSpace(p.SourceChain)
	if chain == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain cannot be empty")
	}
	if !strings.Contains(chain, ":") {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain must be in CAIP-2 format <namespace>:<reference>")
	}

	// Validate tx_hash — needed for UTX key
	if strings.TrimSpace(p.TxHash) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "tx_hash cannot be empty")
	}

	// Validate sender — needed for revert recipient fallback
	if strings.TrimSpace(p.Sender) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "sender cannot be empty")
	}

	// Validate log_index — needed for UTX key
	if strings.TrimSpace(p.LogIndex) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "log_index cannot be empty")
	}

	// Validate tx_type enum — needed to route execution
	if _, ok := TxType_name[int32(p.TxType)]; !ok || p.TxType == TxType_UNSPECIFIED_TX {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid tx_type: %v", p.TxType)
	}

	return nil
}
