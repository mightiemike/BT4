## #Vulnerability found for this question.

### Title
Missing Allowlist/Authorization Validation in `HandleLegacyUserMessage` of the Capabilities Gateway Handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The capabilities gateway `handler.HandleLegacyUserMessage` function forwards every incoming Web API trigger request to all DON member nodes without performing any sender allowlist check or rate-limiting, despite an explicit `// TODO: apply allowlist and rate-limiting here` comment marking the gap, and despite the same gateway package having sibling handlers (e.g. the Functions handler) that do enforce a sender allowlist check before forwarding.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` validates the payload's timestamp/staleness and method name, then immediately builds a request and sends it to every DON member without checking whether the message sender is authorized: [1](#0-0) 

The critical gap is explicitly called out in the code itself: [2](#0-1) 

This mirrors the `sellForLP` bug class exactly: a validation mechanism that exists and is applied elsewhere in the same trust boundary (allowlist checks) is missing from one specific request-handling path, allowing unauthorized/unvalidated input to reach privileged downstream logic (forwarding to all DON nodes, which then act on the message).

By contrast, the Functions gateway handler in the same package tree enforces the analogous check before forwarding to DON members: [3](#0-2) 

This shows the codebase's own established pattern — allowlist/authorization checks belong before message forwarding — which the capabilities handler's legacy path fails to apply, just as `isCrossChainAllowed` was established as the pattern for sid validation but omitted from `sellForLP`.

### Impact Explanation
Any unprivileged external caller reaching the gateway's `ProcessRequest` entrypoint (`core/services/gateway/gateway.go`, `ProcessRequest`) can submit a `web_api_trigger` legacy message that is routed to `HandleLegacyUserMessage` and gets broadcast to every DON node member, without any allowlist gate: [4](#0-3) 

Because the DON nodes then act on the forwarded webapi trigger payload (invoking workflow triggers), this allows unauthorized senders to inject trigger requests into the DON's capability execution pipeline — a workflow/job ingestion trust-boundary bypass, consistent with the "unauthorized privileged node action" / "unsafe workflow execution" impact classes.

### Likelihood Explanation
The gap is reachable directly from the public gateway HTTP entrypoint by any external, unauthenticated caller who can produce a validly-signed (but not necessarily allowlisted) `api.Message` — signature validity is checked via `msg.Validate()` but that only proves message integrity/sender identity, not authorization. No special privilege or node compromise is required, and the code path is explicitly marked incomplete via the TODO comment, indicating this is a known, still-open gap rather than a theoretical one.

### Recommendation
Add an allowlist (and rate-limiting) check for the message sender in `HandleLegacyUserMessage` before the request is validated further and forwarded to DON members — mirroring the pattern already used in `functionsHandler.HandleLegacyUserMessage` (`h.allowlist.Allow(sender)` check). This closes the parity gap between handlers in the same gateway package and ensures only authorized senders can inject trigger requests into DON capability execution.

### Proof of Concept
1. Craft a validly-signed legacy `api.Message` with `Body.Method = "web_api_trigger"`, an arbitrary sender address not on any allowlist, and a valid (non-stale) `TriggerRequestPayload.Timestamp`.
2. Send it to the gateway's JSON-RPC endpoint so it is routed through `gateway.ProcessRequest` → `handler.HandleLegacyUserMessage` for the `capabilities` handler.
3. Observe that the request passes staleness/method checks and is forwarded via `don.SendToNode` to all DON members (`core/services/gateway/handlers/capabilities/handler.go:416-419`), with no allowlist check ever invoked — confirming any sender can inject trigger requests into the DON regardless of authorization status. 		})

				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})

	if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {

func (h *functionsHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	sender := common.HexToAddress(msg.Body.Sender)
	if h.allowlist != nil && !h.allowlist.Allow(sender) {
		h.lggr.Debugw("received a message from a non-allowlisted address", "sender", msg.Body.Sender)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrNotAllowlisted.Error()).Inc()
		return ErrNotAllowlisted
	}
