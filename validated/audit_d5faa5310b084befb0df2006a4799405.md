### Title
`ValidateMultiSign` / `BatchValidateSign` precompiles sign over data with no chain-id domain separator, enabling cross-chain/cross-fork signature replay - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts let smart contracts verify off-chain ECDSA signatures against arbitrary caller-supplied data. Just like the GMX `Oracle` contract's `SALT`, the message hash these precompiles verify contains no chain-specific value at all (no `SALT`, no `block.chainid`), so a signature produced for one TRON-compatible network (mainnet, a testnet, or a post-hard-fork sibling chain) can be replayed verbatim on another network that shares the same account/permission state.

### Finding Description
`ValidateMultiSign.execute` builds the signed message as: [1](#0-0) 
i.e. `sha256(address || permissionId || data)`. There is no chain identifier, genesis block hash, or any other network-specific salt mixed into this hash. Off-chain signers construct and sign this exact hash (as shown in the test helper), then the precompile recovers the signer address purely from `address`, `permissionId`, and `data`: [2](#0-1) 

`BatchValidateSign.doExecute` similarly recovers signer addresses from a raw `hash` word supplied directly by the caller, with no chain binding whatsoever: [3](#0-2) 

Because the resulting signature is a pure function of `(address, permissionId, data)` (or an arbitrary caller-chosen `hash` for `BatchValidateSign`), it carries no information tying it to a specific TRON network. If java-tron undergoes a hard fork, or if the same account key/permission and same `data` payload exist on two java-tron-derived networks (e.g., mainnet vs. a fork, or two networks sharing genesis/account state), a signature collected for one chain's smart contract call can be replayed against the analogous smart contract call on the other chain, exactly analogous to the GMX `Oracle.SALT` issue where `block.chainid` was baked in only at construction time and not included per-signature.

### Impact Explanation
Any DApp/smart contract relying on `ValidateMultiSign` or `BatchValidateSign` for authorizing off-chain-signed actions (e.g., multisig approvals, meta-transactions, off-chain price/data attestations) can be tricked into accepting a signature that was legitimately produced for a different chain/fork context, because the precompile's signed payload provides no cross-chain replay protection. This can lead to unauthorized execution of privileged multisig-gated actions in contracts, corruption of contract-level accounting/state that depends on these precompiles, on any chain that shares account/key material with another java-tron network.

### Likelihood Explanation
Exploitability depends on external conditions (a hard fork occurring, or a signature scheme designer failing to add their own chain-id/domain-separator in `data`), which is exactly the same caveat as in the original GMX finding (rejected as low severity because keepers are semi-trusted and application-level domain separation is expected). Here, similarly, well-designed callers can add their own `chainid` into `data` before hashing, but the precompile itself provides no protection, unlike patterns such as EIP-712 domain separators.

### Recommendation
Document clearly (and ideally enforce at the precompile level) that callers of `ValidateMultiSign`/`BatchValidateSign` must embed `block.chainid` (or equivalent chain-specific identifier) into the `data`/`hash` they sign, so that recovered signatures cannot be replayed across java-tron-compatible networks or post-fork chains that share account state.

### Proof of Concept
1. On chain A, an off-chain signer signs `toSign = sha256(address || permissionId || data)` to authorize a multisig action for a contract that calls `ValidateMultiSign`. [4](#0-3) 
2. If chain A hard-forks into chain A' (or a separate network B shares the same account address/permission/data state), the identical `(address, permissionId, data, signature)` tuple can be submitted to the same contract deployed on chain A'/B.
3. `ValidateMultiSign.execute` recomputes the identical hash (no chain-specific input) and recovers the same signer address, so the signature validates successfully on the unintended chain, exactly as with the GMX oracle SALT replay scenario. [5](#0-4)
