### Title
Address squatting via `deploy_syscall(..., deploy_from_zero=true)` causes permanent DoS of `DeployAccount` for a target address, freezing pre-funded counterfactual balances - (File: `crates/blockifier/src/execution/syscalls/syscall_base.rs`, `crates/starknet_api/src/transaction.rs`, `crates/blockifier/src/execution/execution_utils.rs`)

### Summary
The Starknet contract-address formula is `hash(prefix, deployer_address, salt, class_hash, constructor_calldata)`. For `DeployAccount` transactions, `deployer_address` is always hard-coded to `0` [1](#0-0) . The exact same `deployer_address = 0` value is reachable by *any* unprivileged contract via the ordinary `deploy_syscall` when it passes `deploy_from_zero = true` [2](#0-1) . Consequently, anyone who can predict (or learn) the `(salt, class_hash, constructor_calldata)` triple of a future `DeployAccount` transaction can pre-occupy that exact contract address from an arbitrary invoke transaction, permanently blocking the legitimate `DeployAccount` transaction — the exact same "squat the deterministic address before the intended init/deposit lands" bug class described in the external Solana report (ATA `init` pre-creation DoS), applied here to Starknet's address-derivation/deploy mechanics.

### Finding Description
`calculate_contract_address` computes the address purely as a function of `(salt, class_hash, constructor_calldata, deployer_address)` [3](#0-2) . For `DeployAccount` transactions this is always evaluated with `deployer_address = ContractAddress(PatriciaKey::ZERO)` [1](#0-0) .

The generic `deploy` syscall available to *any* Cairo contract computes the deployed address the same way, and explicitly allows the caller to force `deployer_address_for_calculation = ContractAddress::default()` (i.e. zero) by setting `deploy_from_zero = true`: [4](#0-3) 

This means an attacker contract, invoked in a normal `invoke` transaction, can compute the same target address as a victim's future `DeployAccount` transaction and call `deploy_syscall(class_hash, salt, constructor_calldata, deploy_from_zero=true)` to actually instantiate a (throwaway) contract at that address first.

`execute_deployment` — used by both the deploy syscall path and the `DeployAccount` constructor path — rejects deployment to an address that already has a non-zero class hash, returning `StateError::UnavailableContractAddress`: [5](#0-4) 

This is confirmed by existing tests showing that a second deploy attempt to an already-occupied address fails permanently, both for the generic deploy syscall and specifically for `DeployAccount`: [6](#0-5) [7](#0-6) 

Because Starknet address derivation is fully deterministic and public (any observer can recompute it from a known `class_hash`/`salt`/`constructor_calldata`, e.g. common account-class + salt-equals-public-key conventions used by wallets), an attacker does not need any special privilege — a single ordinary invoke transaction from any deployed contract calling the `deploy` syscall (or via the network's Universal Deployer Contract pattern) suffices to squat the address before the legitimate `DeployAccount` transaction is submitted or included.

### Impact Explanation
Once the address is squatted, the intended `DeployAccount` transaction for that address will permanently fail with `StateError::UnavailableContractAddress` for as long as the squatting contract's class hash remains at that address — there is no legitimate mechanism to "retry" a `DeployAccount` transaction to a different address (the address is intrinsic to the salt/class_hash/calldata combination). Because many account-abstraction wallets follow the common UX pattern of pre-funding a counterfactual (not-yet-deployed) account address before submitting the actual `DeployAccount` transaction, any funds already transferred to that address become permanently unreachable: the intended account contract's logic (needed to authorize spending) can never be installed there, and the squatting contract (attacker-controlled, of arbitrary/empty class) has no relationship to the victim's keys. This satisfies "permanent freezing of funds" and "unauthorized account action is prevented forever for a specific address" — a Medium severity, permanent denial-of-service / fund-freezing analog to the reported ATA pre-creation bug.

### Likelihood Explanation
Likelihood is high for any counterfactual/precomputed address whose `(class_hash, salt, constructor_calldata)` becomes known or guessable before the `DeployAccount` transaction is submitted — this is routine for AA wallets that advertise a precomputed address to receive funds prior to first use. The attack requires only a single ordinary invoke transaction using the standard `deploy` syscall with `deploy_from_zero=true`, is provably reachable by any unprivileged transaction sender, and costs only ordinary Cairo execution fees.

### Recommendation
- Disallow `deploy_from_zero=true` deploys to addresses that are reserved for/consistent with the `DeployAccount` derivation scheme, or otherwise separate the address domains used by contract `deploy_syscall` (deployer-derived) from those reachable by `DeployAccount` (deployer=0), e.g. by mixing in a distinct domain separator/prefix for account deployments so that no ordinary contract-deploy call can collide with a `DeployAccount` address.
- Alternatively/additionally, document and mitigate at the wallet/SDK level by discouraging funding of counterfactual addresses before `DeployAccount` confirmation, since the underlying address-squatting primitive is inherent to the current deterministic address formula shared between `deploy_syscall(deploy_from_zero=true)` and `DeployAccount`.

### Proof of Concept
1. Victim wallet SDK precomputes `address = calculate_contract_address(salt, account_class_hash, ctor_calldata, ContractAddress::ZERO)` and displays it to the user to receive funds before deployment (standard AA UX).
2. Attacker observes/derives the same `(salt, account_class_hash, ctor_calldata)` (e.g., salt = known public key convention, class_hash = well-known account class) before the victim's `DeployAccount` transaction lands.
3. Attacker submits an ordinary `invoke` transaction from any already-deployed contract calling `deploy_syscall(class_hash=account_class_hash, contract_address_salt=salt, calldata=ctor_calldata, deploy_from_zero=true)`, exactly mirroring the address-derivation path exercised in [2](#0-1) .
4. This deploys an attacker-controlled (or empty) contract to `address`, matching the state check in [5](#0-4) .
5. The victim's subsequent `DeployAccount` transaction to the same address now fails permanently with `StateError::UnavailableContractAddress`, exactly as validated by the existing negative-flow test [7](#0-6) , and any funds already sent to `address` are permanently unreachable.

pub fn calculate_contract_address(
    salt: ContractAddressSalt,
    class_hash: ClassHash,
    constructor_calldata: &Calldata,
    deployer_address: ContractAddress,
) -> Result<ContractAddress, StarknetApiError> {
    let constructor_calldata_hash = Pedersen::hash_array(&constructor_calldata.0);
    let contract_address_prefix = format!("0x{}", hex::encode(CONTRACT_ADDRESS_PREFIX));
    let address = Pedersen::hash_array(&[
        Felt::from_hex(contract_address_prefix.as_str()).map_err(|_| {
            StarknetApiError::OutOfRange { string: contract_address_prefix.clone() }
        })?,
        *deployer_address.0.key(),
        salt.0,
        class_hash.0,
        constructor_calldata_hash,
    ]);
    let (_, address) = address.div_rem(&L2_ADDRESS_UPPER_BOUND);

    ContractAddress::try_from(address)
}
