### Title
Unbounded parallel Future submission to shared `sectionExecutor` in `LogBlockQuery.partialMatch` enables JSON-RPC log-query thread-pool exhaustion DoS - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Finding Description
`LogBlockQuery.partialMatch` collects all unique Bloom bit indexes for a section from the caller-supplied filter dimensions (contract addresses + up to 4 topic slots) and submits one `sectionExecutor.submit(...)` task per unique bit index before blocking on `Future.get()` for every one of them: [1](#0-0) 

This is invoked once per bloom section in the requested block range from `subMatch`, which itself is invoked once per condition dimension from `getPossibleBlock` — i.e., the total task volume submitted to the shared executor for a single `eth_getLogs` call scales with `(#sections in [minSection,maxSection]) × (#condition dimensions) × (#unique bit indexes per section)`: [2](#0-1) [3](#0-2) 

The `MAX_RESULT` guard that would reject overly broad queries is only checked at the very end, after all sections/conditions have already been computed and all executor tasks submitted and awaited: [4](#0-3) 

An unprivileged JSON-RPC caller controls both the block range (`fromBlock`/`toBlock`, which drives the number of sections) and the topic/address filter arrays (which drives the number of unique bit indexes per section) via `eth_getLogs`. I was not able to confirm, in the time available, whether `TronJsonRpcImpl` enforces a maximum block range or maximum topic/address array size before constructing `LogBlockQuery` — this repo area (`framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java`) showed hits for `LogFilterWrapper`/`sectionExecutor` usage but I could not fully inspect the method that validates filter parameters before this executor path is reached.

### Impact Explanation
If wide block ranges or high-cardinality topic/address filters are not rejected before this stage, multiple concurrent `eth_getLogs` calls can each submit large bursts of tasks (bounded per section by the fixed Bloom bit-space, but multiplied across sections and dimensions across a wide block range) into the shared `sectionExecutor`. This matches "DoS via RPC-API": legitimate concurrent JSON-RPC log queries (and potentially other consumers of the same executor) experience increased latency or starvation while the pool is saturated by attacker-driven submissions.

### Likelihood Explanation
Feasibility depends entirely on whether `TronJsonRpcImpl` caps the block range and/or topic-array size before calling into `LogBlockQuery`/`partialMatch` — a check I could not verify. If such caps exist and are reasonably small, the amplification is naturally bounded (per-section unique bit indexes cannot exceed the Bloom filter's fixed bit width, and sections are processed sequentially with blocking `Future.get()`, which limits how many tasks are truly in-flight at once). If no such bound exists on block range, an attacker could request a query spanning many sections, and combined with several concurrent connections, generate sustained executor load with no fee/energy cost since JSON-RPC read queries are not chain transactions and are not metered.

### Recommendation
- Verify and enforce, before constructing `LogBlockQuery`, a maximum allowed block range (`toBlock - fromBlock`) and a maximum allowed number of topic/address entries per filter dimension in `TronJsonRpcImpl`.
- Perform the `MAX_RESULT`/complexity check as early as possible (e.g., estimate task count from `getConditions()` output before submitting to `sectionExecutor`) rather than only after all work completes.
- Consider using a dedicated, size-capped, or per-request bounded executor/semaphore for `sectionExecutor` submissions so a single caller cannot dominate the shared pool, and add a global concurrent-request limiter for `eth_getLogs`.

### Proof of Concept
Not fully reproducible without confirming the absence of upstream validation in `TronJsonRpcImpl`. A concurrency test would need to:
1. Call `eth_getLogs` with `fromBlock=0`, `toBlock=<very large>`, and `topics` arrays populated with many distinct 32-byte values across all 4 topic slots, fired concurrently from several threads.
2. Simultaneously issue a lightweight control `eth_getLogs` call and measure its latency/queue depth on `sectionExecutor`.
3. Assert degraded latency for the control call correlates with the number of concurrent wide-filter calls.

This PoC's validity is contingent on confirming (via further code review of `TronJsonRpcImpl`, which I could not complete in this session) that no block-range or filter-size cap currently prevents the described amplification.

  private BitSet subMatch(int[][] bitIndexes) throws ExecutionException, InterruptedException {

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet subBitSet = new BitSet(capacity);

    for (int section = minSection; section <= maxSection; section++) {
      BitSet partialBitSet = partialMatch(bitIndexes, section);

      for (int i = partialBitSet.nextSetBit(0); i >= 0; i = partialBitSet.nextSetBit(i + 1)) {
        // operate on index i here
        if (i == Integer.MAX_VALUE) {
          break; // or (i+1) would overflow
        }
        int offset = (section - minSection) * SectionBloomStore.BLOCK_PER_SECTION + i;
        subBitSet.set(offset);
      }
    }

    return subBitSet;
  }
