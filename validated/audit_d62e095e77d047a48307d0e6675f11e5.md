### Title
GEiC/PWC frames enable full MojoJS bindings without checking the committed origin against the capability allowlist - ([File: chrome/browser/geic/geic_pwc_manager.cc])

### Summary
`GeicPwcManager::TabEntry::RenderFrameCreated()` and `GeicPwcManager::TabEntry::ReadyToCommitNavigation()` unconditionally call `RenderFrameHost::EnableMojoJsBindings(nullptr)` on the primary main frame of a `PrivilegedWebContents` (PWC), and `ChromeContentBrowserClient::ShouldAllowMojoJsBindingsForFrame()` grants the same capability to any outermost frame belonging to a PWC — in both cases the code comments explicitly acknowledge that this "exposes the entire Mojo interface surface" and that "the committed origin is not checked against the capability allowlist here." This is structurally the same bug class as the OneUptime report: a powerful host capability object (here, the entire browser-process Mojo IPC surface reachable via `Mojo.bindInterface()` from renderer JavaScript) is handed to script running in a frame before/without verifying that the content actually executing there is the trusted, allow-listed origin. [1](#0-0) 

### Finding Description
`ShouldAllowMojoJsBindingsForFrame()` returns `true` for the outermost main frame of any `PrivilegedWebContents`, with an explicit `TODO` stating the check is a "Prototype shortcut" that exposes the entire Mojo interface surface and does not check the committed origin against a capability allowlist: [2](#0-1) 

`GeicPwcManager::TabEntry::RenderFrameCreated()` and `GeicPwcManager::TabEntry::ReadyToCommitNavigation()` independently call `render_frame_host->EnableMojoJsBindings(/*features=*/nullptr)` on the primary-main-frame of the GEiC guest `PrivilegedWebContents`, again documented with the same caveat: MojoJS is enabled for the whole frame, and the origin is not checked at this point: [1](#0-0) 

`EnableMojoJsBindings(features=nullptr)` (unlike the `MediaAppUI` usage which passes a scoped `ExtraMojoJsFeatures`) turns on the generic `Mojo.bindInterface()` / `Mojo.createMessagePipe()` JS API for that renderer, giving any script executing in that frame's context the ability to bind arbitrary Mojo interfaces that are registered for that frame/process (via `PopulateChromeFrameBinders` and friends) — this is directly analogous to Playwright's live `browser` object being handed to untrusted VM code: a single powerful native capability object/API is exposed wholesale to script, and the security boundary is deferred to "check later" (in `BindGlicWebClientHandler()` for the origin check, per the code comment) rather than gating the exposure itself.

The `PrivilegedWebContents` (`pwc::`) construction does apply a `capability_allowlist`/`navigation_allowlist` via `FixedPwcPolicyDelegate` when the container is created, but the `TODO(crbug.com/539909218)` comments in both call sites explicitly state that this allowlist check is *not* re-validated against the frame's actual committed origin at the point where MojoJS is turned on — the check is deferred to `ReadyToCommitNavigation` (before commit) and to individual interface-binder logic. If the PWC's content ever navigates to (or is redirected to, or otherwise commits) something other than the intended `dev_url_`/allow-listed origin while this code path executes, the capability (MojoJS bindings, hence the full Mojo interface surface exposed to that frame) is granted regardless, mirroring the OneUptime pattern where `browser`/`page` objects were exposed regardless of what "customCode" actually did with them.

### Impact Explanation
If the origin actually committed in the PWC's main frame diverges from the allow-listed capability origin at the moment MojoJS bindings are enabled (e.g., due to a race between `ReadyToCommitNavigation`/`RenderFrameCreated` firing and navigation restrictions being fully enforced, or any other gap in the "stopgap" gating the authors themselves flag as incomplete), that frame's JavaScript gains the ability to call `Mojo.bindInterface()` against any Mojo interface registered for that render frame host in the browser process. Depending on which interfaces are bound for that process (`PopulateChromeFrameBinders`, feature-specific binders, `pwc::BindPrivilegedBridge`, `geic::BindGeicApi`, etc.), this is a full escalation from "content running inside a privileged/guest surface" to direct, unmediated browser-process IPC access — a sandbox/process-boundary bypass with the same severity class as classic MojoJS-based renderer compromises, since it collapses the security boundary between web content and privileged browser-process functionality onto a single, admittedly-unverified origin check performed later in the pipeline.

### Likelihood Explanation
This is not a purely theoretical concern: the authors' own comments mark this as a known, intentional stopgap ("Prototype shortcut... Gating on the outermost main frame is a stopgap while erikchen@ designs a scoped capability binding mechanism in follow-ups") rather than a hardened design, and it is exercised on every navigation of a GEiC-classified `PrivilegedWebContents` main frame (`ReadyToCommitNavigation`/`RenderFrameCreated` fire on every navigation, not just the first). The severity depends on whether the PWC's navigation/allowlist enforcement elsewhere in the (not fully indexed) `chrome/browser/pwc/` implementation is airtight; those files were not available in this index, so it cannot be fully confirmed here whether a redirect, `window.open`, or subframe-to-mainframe promotion could cause a non-allow-listed origin to be granted MojoJS while these callbacks still fire the binding enablement.

### Recommendation
Do not enable MojoJS bindings for a frame until its origin has been verified against the capability allowlist at that exact call site (not deferred to a later bind-time check in `BindGlicWebClientHandler()`/similar). Scope the Mojo interfaces exposed to only the specific APIs required (as `MediaAppUI` does via `ExtraMojoJsFeatures`) rather than passing `features=nullptr`, which exposes the entire registered Mojo surface. Re-validate the committed origin on every `DidFinishNavigation` and revoke/re-check bindings if the origin no longer matches the allowlist.

### Proof of Concept
Not independently reproducible from the indexed code alone (the `chrome/browser/pwc/` policy-delegate implementation enforcing `navigation_allowlist`/`capability_allowlist` was not present in the index, so the exact navigation path that would defeat it cannot be demonstrated here). The vulnerability is evidenced directly by the code's own acknowledgment:
- `chrome/browser/chrome_content_browser_client.cc:2277-2289` — "Enabling MojoJS for any PWC exposes the entire Mojo interface surface rather than only GeicApi, and the committed origin is not checked against the capability allowlist here."
- `chrome/browser/geic/geic_pwc_manager.cc:192-212` — same TODO repeated for both `RenderFrameCreated` and `ReadyToCommitNavigation`, both of which unconditionally call `EnableMojoJsBindings(/*features=*/nullptr)`. [1](#0-0) [2](#0-1) [3](#0-2)

void GeicPwcManager::TabEntry::RenderFrameCreated(
    content::RenderFrameHost* render_frame_host) {
  // TODO(crbug.com/539909218): Prototype shortcut. This exposes the entire
  // Mojo surface rather than only GeicApi, and the committed origin is not
  // checked against the capability allowlist here.

    render_frame_host->EnableMojoJsBindings(/*features=*/nullptr);
  }

  // checked against the capability allowlist here.

}

bool ChromeContentBrowserClient::ShouldAllowMojoJsBindingsForFrame(
    content::RenderFrameHost& render_frame_host) {
  content::WebContents* web_contents =
      content::WebContents::FromRenderFrameHost(&render_frame_host);
  if (web_contents && glic::IsGlicGuest(web_contents) &&
      !render_frame_host.GetParentOrOuterDocument()) {
    return true;
  }
  // TODO(crbug.com/539909218): Prototype shortcut. Enabling MojoJS for any PWC
  // exposes the entire Mojo interface surface rather than only GeicApi, and the
  // committed origin is not checked against the capability allowlist here.
  // Gating on the outermost main frame is a stopgap while erikchen@ designs a
  // scoped capability binding mechanism in follow-ups. We check
  // `!render_frame_host.GetParentOrOuterDocument()` rather than
  // `IsInPrimaryMainFrame()` because this predicate is consulted from
  // `ReadyToCommitNavigation` before the frame commits, where
  // lifecycle-dependent queries return false.
  if (!render_frame_host.GetParentOrOuterDocument() && web_contents &&
      pwc::PrivilegedWebContents::FromWebContents(web_contents)) {
    return true;
  }
