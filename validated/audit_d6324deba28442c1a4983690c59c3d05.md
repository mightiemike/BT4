### Title
Predictable `CREATE`-style contract address allows front-run DoS of contract deployment via mempool-visible pending transactions - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
In java-tron, the address of a to-be-deployed smart contract is deterministically derived from the pending transaction's raw data hash and the owner address [1](#0-0) . Because pending (unconfirmed) transactions are publicly retrievable from a node's mempool via `GetTransactionListFromPendingServlet`/related RPCs [2](#0-1) , an attacker can observe a pending `CreateSmartContract` transaction, compute the exact resulting contract address off-chain using the same formula, and pre-create an account at that address (e.g. via a trivial TRC transfer, which auto-creates the destination account) before the legitimate deployment transaction is packed into a block. When the deployment is finally executed, `VMActuator.create()` explicitly rejects contract creation if an account already exists at the predicted address, causing the legitimate deployment to permanently fail.

### Finding Description
`VMActuator.create()` computes the new contract address and unconditionally throws if any account/pool already resides there: [3](#0-2) 

The address itself is fully deterministic and computable by anyone who can see the raw (unsigned-content) transaction data, since it is `sha3omit12(txRawDataHash || ownerAddress)`: [1](#0-0) 

Because java-tron exposes pending/unconfirmed transactions through public HTTP/RPC endpoints (`GetTransactionListFromPendingServlet`, `getPendingSize`, etc.), a broadcast-but-unconfirmed `CreateSmartContract` transaction is visible to any observer before it's included in a block. An attacker can:
1. Watch the mempool for a `CreateSmartContract` transaction.
2. Compute the target contract address using the exact same `txRawDataHash + ownerAddress` formula.
3. Front-run with a cheap transaction that creates an account at that address — for instance a plain TRX transfer to a non-existent address auto-creates the account, as demonstrated by the "no exist -> create" behavior of `TransferActuator`: [4](#0-3) 
4. When the original `CreateSmartContract` transaction is finally executed, `rootRepository.getAccount(contractAddress) != null` is true, and `VMActuator.create()` throws `ContractValidateException`, permanently failing the deployment (the deployer would need to regenerate a new transaction with different raw data/timestamp to get a fresh address, and can be griefed again the same way).

This directly mirrors the reported `WeightedIndex`/`createV2Pool` bug class: a constructor/creation flow assumes exclusive control over a deterministically-derivable address and reverts unconditionally if that address is already occupied, letting any observer of the pending action grief the deployment.

### Impact Explanation
This is a denial-of-service against contract deployment: any user broadcasting a `CreateSmartContract` transaction can have their deployment griefed indefinitely by a low-cost attacker who merely front-runs with a cheap transfer to the predicted address. This can be used to target specific projects/tokens attempting to deploy at a "clean" moment, disrupt time-sensitive launches, or repeatedly block a victim's deployment attempts, which is a legitimate protocol-level availability issue reachable purely through normal broadcast transactions (no privileged access required).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the attacker to actively monitor the mempool and race a follow-up transaction into an earlier block slot than the victim's deployment, and it only pays off if the attacker specifically wants to block a particular deployer/deployment (opportunistic mass-griefing is not economically incentivized). This matches the "Low likelihood / High impact" characterization of the original report.

### Recommendation
Before rejecting a `CreateSmartContract` execution outright due to an existing account at the target address, distinguish between an address that already holds actual contract code/state (a true collision, extremely unlikely with a 20-byte hash) versus an address that was merely auto-created as an empty/normal account (e.g., via a TRX transfer). For the latter case, allow the deployment to proceed and only fail if genuine contract bytecode/storage already exists at that address, similar to the `isContractExist` check already used for the `CREATE2`/`allowTvmConstantinople` path: [5](#0-4) 
Apply the same "existing account but not yet a contract" tolerance to the top-level `VMActuator.create()` path instead of unconditionally throwing when any account record exists at the address.

### Proof of Concept
1. Alice signs and broadcasts a `CreateSmartContract` transaction `T` (deploying an index/factory-style contract).
2. Before `T` is confirmed, Bob queries the node's pending transaction pool (`GetTransactionListFromPendingServlet`) and retrieves `T`'s raw data and owner address.
3. Bob computes `predictedAddress = sha3omit12(txRawDataHash(T) || ownerAddress)` exactly as `WalletUtil.generateContractAddress` would.
4. Bob broadcasts a trivial TRX transfer to `predictedAddress`, which is included in an earlier block, auto-creating a normal account there.
5. When `T` executes, `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")`, permanently failing Alice's deployment attempt for that transaction.

```java
  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
```
