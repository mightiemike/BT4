### Title
Deposit mempool unconditionally removes fetched deposits regardless of on-chain execution success, causing silent, permanent loss of legitimate deposits - (File: crates/sequencer/src/runner.rs)

### Summary
`DepositDataMempool::fetch_deposits` returns a FIFO snapshot of pending deposits without any revalidation against current chain state [1](#0-0) , and the sequencer's `process_sys_txs` silently reverts and skips any deposit whose system transaction fails during block execution [2](#0-1) . Critically, after the block is committed, `remove_deposits` is called with the *entire original* `deposit_data` fetched at the top of `produce_l2_block_inner`, not with only the subset that actually succeeded and was included in the block [3](#0-2) , so any reverted deposit — including one caused by an earlier deposit in the same block mutating shared Bridge contract state — is permanently purged from the mempool with no retry and no cBTC credited.

### Finding Description
The binding that must hold is: for every legitimately presigned `Deposit` blob `d` fetched into a block, `d ∈ succeeded_txs(block) ⟺ d ∉ mempool_after_block`. In the actual code this binding is broken because `deposit_data` (used for removal) and the set of deposits actually applied successfully (`all_txs` inside `process_sys_txs`) are different variables that are allowed to diverge.

Trace:
1. `produce_l2_block_inner` fetches a FIFO batch via `fetch_deposits(limit_per_block)` into `deposit_data` [4](#0-3) .
2. `deposit_data` is passed through `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs`, which converts each deposit into a `SystemEvent::BridgeDeposit` and applies it on a checkpointed working set [5](#0-4) .
3. Inside `process_sys_txs`, if a deposit's system transaction reverts (`EvmSystemTransactionNotSuccessful`), the code explicitly reverts that working-set checkpoint and `continue`s to the next event — it does **not** re-add the deposit anywhere or mark it as failed for later retry [6](#0-5) . The failed deposit is simply absent from `all_txs`/the produced block.
4. After the block is committed, the sequencer calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the original, unfiltered `deposit_data` collected in step 1 — including deposits whose system transaction reverted in step 3 [3](#0-2) .
5. `remove_deposits` matches by `calc_tx_id` and unconditionally evicts every deposit present in the passed slice from `accepted_deposit_txs` and `pending_deposits` [7](#0-6) .

Because the deposit is removed from `pending_deposits` as well, re-submission of the exact same deposit blob via `citrea_sendRawDepositTransaction` is no longer blocked as a duplicate [8](#0-7) , but nothing in the system automatically retries it — the depositor (or Clementine on their behalf) must notice the failure and manually resubmit, and there is no signal that the deposit was silently dropped instead of included.

The attack surface for causing this revert does not require the attacker to forge a deposit — an attacker only needs their *own* legitimately-presigned deposit to land earlier in FIFO order and consume enough of the block's system-transaction budget/gas or otherwise cause a later deposit to fail (e.g. `EvmGasUsedExceedsBlockGasLimit` when many deposits are queued, or any other revert path reachable from `execute_multiple_tx` [9](#0-8) ). Regardless of the exact revert cause, the outcome is identical: the reverted deposit is unconditionally stripped from the mempool alongside the successful ones, with no distinction made between "included" and "fetched-but-reverted."

### Impact Explanation
Any deposit that reverts during block execution for any reason is permanently and silently dropped from the sequencer's mempool without retry, and the corresponding depositor's cBTC is never minted despite their BTC being irrevocably locked/moved on the Bitcoin side by Clementine's presigned `moveTx`. This is a Critical-severity funds-freezing bug: it does not require any privileged role, and can be triggered incidentally (block gas limits, deposit ordering) or deliberately by an attacker submitting their own valid deposits earlier in the FIFO queue to induce a later deposit's revert. The blast radius is per-deposit and repeatable across every block in which more than one deposit is queued and at least one reverts.

### Likelihood Explanation
Preconditions are modest: multiple deposits must be pending in the mempool simultaneously in the same L2 block, and at least one of them (not necessarily the attacker's) must revert during execution — which can happen for reasons unrelated to attacker intent (gas limits, and any other on-chain deposit validation edge case), not only deliberate interference. An attacker capable of submitting their own real deposits (regular BTC-locking cost) ahead of a targeted victim in FIFO order increases the likelihood of triggering a revert for the victim's deposit, but even without an attacker, this is a latent bug that discards legitimate deposits whenever any deposit fails mid-block.

### Recommendation
Track which deposits actually succeeded (i.e., were pushed into `all_txs` in `process_sys_txs`) separately from the deposits fetched, and only call `remove_deposits` with that successful subset. Return the list of applied deposit blobs (or their txids) alongside `all_txs`/receipts from `produce_and_run_system_transactions`/`process_sys_txs`, and use only that list at the removal call site in `produce_l2_block_inner`, leaving reverted deposits in `accepted_deposit_txs`/`pending_deposits` so they are retried in a subsequent block (or explicitly surfaced to the operator/Clementine for resubmission).

### Proof of Concept
```rust
// crates/sequencer/src/deposit_data_mempool.rs (new test)
#[test]
fn test_reverted_deposit_is_not_silently_dropped() {
    let mut mempool = DepositDataMempool::new();
    let attacker_deposit = hex::decode(DEPOSIT1).unwrap();
    let legit_deposit = hex::decode(DEPOSIT2).unwrap();

    mempool.add_deposit_tx(attacker_deposit.clone()).unwrap();
    mempool.add_deposit_tx(legit_deposit.clone()).unwrap();

    // Simulate fetch_deposits() being called for block production
    let fetched = mempool.fetch_deposits(2);
    assert_eq!(fetched, vec![attacker_deposit.clone(), legit_deposit.clone()]);

    // Simulate runner.rs behavior: only `attacker_deposit` succeeded on-chain
    // (legit_deposit reverted mid-block, e.g. due to gas limit / state interference),
    // so only the succeeded subset should be removed.
    let succeeded = vec![attacker_deposit.clone()];
    let removed = mempool.remove_deposits(&succeeded);
    assert_eq!(removed, 1);

    // BINDING: legit_deposit must still be retryable/present since it was never
    // actually included in a block.
    assert!(mempool.pending_deposits.contains(
        &DepositDataMempool::calc_tx_id(&legit_deposit).unwrap().to_vec()
    ));
    assert_eq!(mempool.accepted_deposit_txs.len(), 1);

    // Demonstrating the ACTUAL current bug: calling remove_deposits with the full
    // originally-fetched `fetched` (as runner.rs does today) removes legit_deposit too,
    // even though it was never included in the block.
    let mut mempool_buggy = DepositDataMempool::new();
    mempool_buggy.add_deposit_tx(attacker_deposit.clone()).unwrap();
    mempool_buggy.add_deposit_tx(legit_deposit.clone()).unwrap();
    let fetched_buggy = mempool_buggy.fetch_deposits(2);
    mempool_buggy.remove_deposits(&fetched_buggy); // current runner.rs behavior
    assert_eq!(mempool_buggy.accepted_deposit_txs.len(), 0); // legit deposit silently lost
}
```
This test demonstrates that under the current `runner.rs` logic (removal keyed on the unfiltered `deposit_data` fetched before dry-run, per [3](#0-2) ), a reverted-but-legitimate deposit is indistinguishable from a successfully included one and is permanently purged from the mempool.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
