## Analog Found: Unbounded `PendingInbounds.Walk` in ballot finalization hook grows with inbound activity, mirroring `settleFunding`'s per-market gas growth

### Title
Unbounded linear scan of `PendingInbounds` on every inbound ballot finalization scales with attacker-triggered deposit volume — ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
The external report's root cause is a function that iterates over an unbounded, ever-growing on-chain collection (markets) on every invocation, so its cost scales with protocol activity/growth until it threatens the block gas limit. Push Chain's `afterInboundBallotTerminal` hook has the same shape: every time an inbound ballot reaches a terminal state, it performs a full `PendingInbounds.Walk` over *all* currently-pending inbound audit-trail entries to locate the one owning that ballot ID, and this executes as part of the gasless `MsgVoteInbound` message path.

### Finding Description
`RecordInboundVote` creates one `PendingInboundEntry` per distinct `utx_key = sha256(source_chain:tx_hash:log_index)` [1](#0-0) . Any unprivileged external actor can cause new entries to be created simply by generating distinct source-chain gateway events (e.g. many small/dust deposits across supported chains); creating the entry itself requires no privilege on Push Chain — only an honest UV observing and voting on an externally-triggered event.

Every time a ballot for one of these entries reaches a terminal state (`PASSED`/`REJECTED`/`EXPIRED`), `x/uvalidator` invokes `AfterBallotTerminal`, which for `INBOUND_TX` ballots calls `afterInboundBallotTerminal`. This function does not know the entry's storage key from the ballot ID (ballot IDs are one-way digests), so it performs a full `PendingInbounds.Walk` over the entire pending set, scanning each entry's `Variants` to find a match: [2](#0-1) 

The code's own comment acknowledges the assumption this relies on: "the pending set is small and transient" [3](#0-2) . That assumption is not enforced anywhere — there is no cap on `PendingInbounds` size, and the only bound on how large it grows is the natural rate of inbound deposit volume across all supported source chains versus how fast ballots finalize/expire (`DefaultExpiryAfterBlocks`). As Push Chain onboards more source chains and users, this pending set — analogous to Hubble's growing set of markets — grows, and the per-terminal-ballot cost of this walk grows with it.

Critically, `MsgVoteInbound` (which triggers this whole flow) is in the gasless message allow-list [4](#0-3) , meaning there is no fee-based friction discouraging validators from processing these transactions and no economic signal that scales cost with the walk's size — the CPU/processing cost is simply absorbed by every honest validator node on every vote.

### Impact Explanation
This is a growth-scaling processing-cost issue directly analogous to `settleFunding`: as the number of concurrently-pending inbound entries increases (driven by ordinary, unprivileged deposit activity across an increasing number of supported chains), the cost of finalizing *any single* inbound ballot increases linearly with the total pending set size. In periods of high cross-chain deposit volume or across many chains, this can materially slow down transaction processing for all validators executing `MsgVoteInbound`, degrading throughput of the universal execution path without requiring any privileged actor — a denial-of-service class impact reachable purely through ordinary user deposit activity, which is in scope per the impact gate ("denial of service only when it is not network-level and is reachable without privileged control").

### Likelihood Explanation
Likelihood is moderate: it requires sustained/parallel deposit activity across chains sufficient to keep many entries pending simultaneously (bounded in the worst case by `DefaultExpiryAfterBlocks`), but no privileged access, validator collusion, or protocol flaw is needed — an attacker only needs to generate many cheap, distinct source-chain events. As the set of supported chains and daily active users grows over time (an explicit, expected trajectory for the protocol, mirroring Hubble's expected market growth), the baseline pending-set size — and therefore the cost of this walk — grows correspondingly, independent of any single attacker's effort.

### Recommendation
Avoid the linear `Walk` entirely by maintaining a secondary index from `ballotID -> utxKey` (set alongside `PendingInbounds.Set` in `RecordInboundVote`, cleared alongside removal), so `afterInboundBallotTerminal` can do an O(1) lookup instead of scanning the full pending set. Additionally, consider bounding the maximum size of `PendingInbounds` (or the maximum number of variants per entry) to give an explicit, enforced upper bound on per-call cost rather than relying on an informal assumption in a comment.

### Proof of Concept
1. An external, unprivileged actor issues many distinct small deposit transactions against the gateway contract on one or more supported source chains within a short window (each producing a unique `source_chain:tx_hash:log_index`).
2. Honest UVs observe and vote on each via `MsgVoteInbound`, each creating a new `PendingInboundEntry` via `RecordInboundVote` (x/uexecutor/keeper/inbound.go).
3. As votes accumulate and ballots begin finalizing, each terminal transition triggers `afterInboundBallotTerminal`, which performs a full `PendingInbounds.Walk` (x/uexecutor/keeper/ballot_hooks.go:86) across the now-large pending set.
4. As the number of concurrently in-flight entries N grows, each subsequent vote's finalization walk cost grows ~O(N), executed within the gasless (fee-less) `MsgVoteInbound` path — increasing per-tx processing time for every honest validator node without a corresponding economic cost to the actor generating the activity.

func (k Keeper) RecordInboundVote(
	ctx context.Context,
	inbound types.Inbound,
	voter string,
	ballotID string,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	height := uint64(sdkCtx.BlockHeight())
	utxKey := types.GetInboundUniversalTxKey(inbound)

	entry, err := k.PendingInbounds.Get(ctx, utxKey)
	if err != nil && !errors.Is(err, collections.ErrNotFound) {
		return err
	}
	if errors.Is(err, collections.ErrNotFound) {
		entry = types.PendingInboundEntry{
			UtxKey:          utxKey,
			CreatedAtHeight: height,
		}
	}

	// transient, and this hook only fires on terminal transitions.
	var (

		found  bool

	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {

			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})

		return err
