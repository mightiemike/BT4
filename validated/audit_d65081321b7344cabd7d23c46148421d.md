### Title
Webhook HMAC digest omits shop-domain binding, enabling cross-tenant payload replay - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`shopify.webhooks.validate` (used by `authenticateWebhookFactory` in shopify-app-remix/react-router) verifies webhook authenticity by HMAC-ing only the raw request body with the app's single shared `apiSecretKey` [2](#0-1) . The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers that identify which tenant/topic the payload belongs to are read separately from headers and merely checked for presence, never cryptographically bound into the digest [1](#0-0) . Because one app secret is shared across every shop that installs the app, a valid `(rawBody, hmac)` pair captured from shop A's webhook remains valid when resubmitted with a different `X-Shopify-Shop-Domain`/topic header claiming to originate from shop B — directly mirroring the reported bug class where a signed digest lacking a domain separator allows cross-domain replay.

### Finding Description
`validateFactory` calls `validateHmacFromRequestFactory`, which computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it to the `X-Shopify-Hmac-Sha256` header via `safeCompare` . Once that check passes, `checkWebhookHeaders` pulls `domain`, `topic`, `apiVersion`, and `webhookId` straight out of the (unsigned) headers and returns them as trusted fields consumed by app code [3](#0-2) . Downstream, `authenticateWebhookFactory` uses `check.domain` directly to load the offline session and dispatch the payload as belonging to that shop [4](#0-3) . Since `domain`/`topic`/`webhookId` are not part of the signed material, any entity that can capture one legitimate `(body, hmac)` pair for the app (e.g., a merchant who can see their own store's raw webhook deliveries, or logs/proxies) can resend that exact body/hmac pair with a forged `X-Shopify-Shop-Domain` header naming a different shop that has installed the same app. The signature still validates because the digest never committed to the domain.

### Impact Explanation
An attacker (a single merchant with access to their own app-installed shop's webhook traffic) can inject data attributed to another tenant shop into the app: e.g., replaying an `orders/create` or `app/uninstalled` payload while spoofing the domain header of a victim shop. Depending on how the app processes webhook payloads (billing changes, inventory sync, GDPR/uninstall cleanup, session invalidation), this enables cross-tenant data confusion/injection into another merchant's app state — a direct analog to the "cross-chain replay swap" impact in the report (wrong entity's authorization consumed for another entity's context).

### Likelihood Explanation
Medium: it requires the attacker to already have valid HMAC-signed webhook traffic (trivial for their own shop, since Shopify sends webhooks to any store that installs the app) and the ability to submit an HTTP POST to the app's public webhook endpoint with custom headers, which is unauthenticated and always reachable. No secret leakage or privileged access is required beyond being an ordinary installing merchant.

### Recommendation
Bind the domain (and ideally topic/webhookId) into the signed material, or otherwise cryptographically tie the header-derived shop identity to the payload — e.g., verify that the `domain` header matches a shop for which a legitimate session/subscription exists before trusting it, and/or require the webhook registration to record and check the originating shop against session storage rather than trusting the header value as-is for identity binding.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and `shop-b.myshopify.com` (both share the same `apiSecretKey`).
2. Capture a legitimate webhook delivery `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: H` for `shop-a`.
3. Resend the identical request to the app's webhook endpoint, changing `X-Shopify-Shop-Domain: shop-b.myshopify.com` (and topic/webhook-id if desired) while keeping body `B` and header `H` unchanged.
4. `validateHmacFromRequestFactory` recomputes HMAC over `rawBody` only, matches `H`, returns valid; `checkWebhookHeaders` returns `domain: 'shop-b.myshopify.com'` trusted as-is [5](#0-4) .
5. `authenticateWebhookFactory` loads `shop-b`'s offline session and processes shop-a's payload as if it belongs to shop-b [4](#0-3) .

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
