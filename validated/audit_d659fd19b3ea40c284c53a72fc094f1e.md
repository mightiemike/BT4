### Title
Unbounded recursion in transaction/receipt outcome traversal causes stack-overflow DoS on tx-status RPC queries - ([File: chain/chain/src/chain.rs])

### Summary
`Chain::get_recursive_transaction_results` walks the chain of execution outcomes produced by a transaction by recursing into every `receipt_ids` entry of each outcome, with no depth limit and no tail-call elimination. This function backs both `get_final_transaction_result` and `get_partial_transaction_result_option`, which are the core implementations behind the JSON-RPC transaction-status queries served by `view_client_actor.rs`. This mirrors the CVE-2017-9304 bug class: an attacker-controlled input (there, a crafted YARA rule; here, a transaction that produces a long chain of chained cross-contract-call receipts) drives unbounded native-stack recursion in a single function (`_yr_re_emit` there, `get_recursive_transaction_results` here), leading to stack exhaustion.

### Finding Description
`get_recursive_transaction_results` recurses once per hop in the receipt chain: [1](#0-0) 

Both public entry points call it directly with no maximum-depth guard: [2](#0-1) [3](#0-2) 

A NEAR transaction can trigger an arbitrarily long chain of sequential cross-contract-call receipts: a `FunctionCall` action can schedule a promise to another contract (or itself) which in turn schedules another promise, and so on, each such receipt being recorded with a `SuccessReceiptId` link to the next outcome (as consumed by `get_execution_status`, which follows the same `SuccessReceiptId` chain). Because each hop only needs to consume a small, fixed amount of gas relative to the per-block/per-chunk gas budget, and the chain can span many blocks (i.e., it is not bounded by a single block's gas limit), an attacker who fully controls the deployed contract logic and the submitted transaction can create outcome chains many thousands of receipts deep. There is no protocol-level cap on the *linear* length of such a receipt chain (only limits like `max_actions_per_receipt`, `max_total_prepaid_gas` per receipt, and congestion/bandwidth limits bound per-hop or per-block work — none limit total end-to-end receipt chain depth).

Any RPC caller who then queries the transaction status for this transaction (a standard, unauthenticated/unprivileged `tx` RPC call) causes the serving node to execute `get_recursive_transaction_results`, recursing to a depth proportional to the attacker-chosen chain length, exhausting the native call stack and crashing (or otherwise disrupting) the RPC-serving process — a remotely triggerable denial of service, directly analogous to the YARA `_yr_re_emit` stack-consumption bug.

### Impact Explanation
A successful trigger crashes the node process handling the RPC request (stack overflow typically aborts the process, since Rust cannot safely catch stack overflow). If this endpoint is served by the same node process that also performs chunk production/validation duties, this is a transaction-triggered denial of service against validator/RPC infrastructure, achievable by any unprivileged party who can submit a transaction and later issue a `tx` status RPC call.

### Likelihood Explanation
Likelihood is bounded by how easy it is in practice to produce a sufficiently deep receipt chain (thousands of chained cross-contract calls) purely from a single, unprivileged transaction plus follow-on self-scheduled calls, and by the native stack size configured for the serving process/thread. This requires multiple blocks (each hop is one receipt), so it is not a single-transaction, single-block attack, but the entire chain is initiated and fully controlled by an unprivileged attacker's contract, and no protocol limit bounds chain depth.

### Recommendation
Convert `get_recursive_transaction_results` in `chain/chain/src/chain.rs` to an iterative traversal (e.g. explicit worklist/queue) instead of recursive calls, and/or impose an explicit maximum traversal depth (returning a clear error once exceeded) so that the total recursion/iteration depth is bounded regardless of how deep an attacker-constructed receipt chain is.

### Proof of Concept
1. Deploy a contract whose method, when called, issues a `FunctionCall` promise back to itself (or to a chain of other deployed contracts) with minimal attached gas, and have that promise-continuation repeat the same self-scheduling pattern.
2. Submit an initial transaction invoking this method; let execution proceed over many blocks so the chain of `SuccessReceiptId`-linked execution outcomes grows very deep (e.g., tens of thousands of hops), which is achievable since chain length is not gas- or protocol-bounded per transaction.
3. From any unprivileged RPC client, call the standard transaction-status endpoint (`tx` / `EXPERIMENTAL_tx_status`-style RPC) for the original transaction hash, causing `Chain::get_final_transaction_result` → `get_recursive_transaction_results` to recurse to the full chain depth on the serving node.
4. Observe the RPC-serving node process crash (stack overflow) or become unresponsive, confirming the transaction-triggered stack-consumption DoS.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }
