## Analysis

CVE-2019-7620 is a DoS caused by processing an untrusted/unbounded network input without resource limits, crashing the service. The closest sequencer analog I found is an **unbounded gzip decompression routine reachable from RPC**, in contrast to the pattern used everywhere else in the codebase.

### Title
Unbounded Gzip Decompression in RPC `decompress_program` Enables Memory-Exhaustion DoS - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
`decompress_program` decodes a base64 string and decompresses it with `GzDecoder`, reading the *entire* decompressed output into memory with no size limit and no `.take()` bound, unlike every other decompression path in this codebase.

### Finding Description
`decompress_program` reads user-supplied, base64-encoded gzip data and decompresses it fully into a `Vec<u8>` before parsing it as JSON: [1](#0-0) 

The function itself carries a `// TODO(dan): add time and size limits.` comment acknowledging the gap. This is materially different from the pattern used elsewhere in the same codebase for the identical operation (decompressing an attacker-supplied compressed contract program), which explicitly bounds the decompressed size with `.take(max_size + 1)` and rejects oversized output: [2](#0-1) [3](#0-2) 

A small gzip payload can expand enormously (a classic "decompression bomb"): a few KB compressed can inflate to hundreds of MB or more. Because `decompress_program` reads to completion with `read_to_end` before any size check exists, the process must allocate and hold the entire decompressed buffer in memory regardless of size.

### Impact Explanation
An unauthenticated (or low-cost) caller of the affected RPC method can submit a maliciously crafted, small compressed "program" payload; the node will attempt to decompress it fully into memory. Repeated or large-scale submissions can exhaust process memory, causing the RPC/node process to slow to a crawl, be OOM-killed, or otherwise stop responding — directly analogous to the Logstash beats-input DoS in the CVE (unauthenticated crafted-input causes the service to stop responding). This differs from the deliberately bounded compressed-class ingestion paths used by the gateway/declare-transaction flow (`decode_and_decompress_with_size_limit`, capped e.g. at 4 MiB), which shows the project's own security model treats unbounded decompression of untrusted data as unacceptable.

### Likelihood Explanation
Medium-High: this code path is a self-contained utility invoked from RPC handling of a compiled/declared class payload (v0_8 API `mod.rs`, near `CompiledContractClass`), taking directly a base64 string field from a client-supplied request. No authentication, staking, or special privilege is required to reach it — it only requires the ability to submit an RPC call containing a compressed program field, which is functionally equivalent to any user submitting a declare-style payload or trace/estimate call bundling a class.

### Recommendation
Replace the unbounded `read_to_end` decompression in `decompress_program` with the same bounded pattern already used in `starknet_api::compression_utils::decode_and_decompress_with_size_limit` (or reuse that function directly): wrap the `GzDecoder` in `.take(max_size + 1)`, and return an explicit `SizeLimitExceeded` error if the output exceeds the configured maximum (consistent with `DEFAULT_MAX_SIERRA_PROGRAM_SIZE`/`MAX_CAIRO0_PROGRAM_SIZE` limits enforced elsewhere in the gateway and protobuf paths).

### Proof of Concept
1. Craft a gzip stream that decompresses from a few hundred bytes into hundreds of megabytes/gigabytes of repeated data (a textbook zip/gzip bomb).
2. Base64-encode it and submit it as the compressed program field to the RPC method that calls `decompress_program` (via a request containing a `CompiledContractClass`/declared class payload).
3. Observe the node's memory usage spike uncontrollably during `decoder.read_to_end(&mut decompressed, ...)` since no size cap exists, potentially triggering OOM and node unavailability; repeat concurrently to amplify impact.

**Caveat**: I was unable to fully trace, within tool budget, the exact public RPC method name(s) that call `decompress_program` (only usage inside `crates/apollo_rpc/src/v0_8/api/mod.rs` and its test file was confirmed) to state with certainty whether it is gated behind any additional request-size limits at the HTTP layer (e.g., `max_request_body_size`) that might partially mitigate the impact. A Devin session with full repo access would be needed to enumerate exact call sites in `api_impl.rs` and confirm end-to-end reachability and any outer size guard.

```rust
/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
```
