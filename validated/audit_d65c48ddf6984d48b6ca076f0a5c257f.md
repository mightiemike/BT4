### Title
Unchecked EVM revert status (`VmError`) on `DerivedEVMCall`/`CallEVM` receipts lets reverted on-chain actions be recorded as `SUCCESS` — (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/execute_payload.go`, `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
`x/uexecutor` drives every universal-execution and inbound-fulfillment path through `EVMKeeper.DerivedEVMCall` / `CallEVM`, which return a `*evmtypes.MsgEthereumTxResponse` receipt plus a Go `error`. [1](#0-0)  Throughout `x/uexecutor`, every caller treats a `nil` Go `error` as proof the underlying EVM call succeeded and immediately marks the corresponding `PCTx`/`UniversalTx` record as `"SUCCESS"`, attaches outbound transactions, and skips revert handling — without ever inspecting the receipt's on-chain execution status (the `VmError` field on `MsgEthereumTxResponse`, which is how the EVM signals that a call reverted). A repo-wide search shows **zero** references to `VmError` (or any revert-status field) anywhere in `x/uexecutor`, despite dozens of call sites that only branch on `err != nil`.

### Finding Description
This is the direct analog of the reported `ClaimAssessor.requestClaim` bug: a sub-call's real success/failure signal is discarded, and the caller proceeds as if it always succeeded.

- `ExecutePayloadV2` calls `CallUEAExecutePayload` and only checks `execErr`; if that's `nil` it commits the cache and logs "payload executed via UEA" using `receipt.Hash`/`receipt.GasUsed` without checking whether the UEA's `executeUniversalTx` call actually reverted on-chain. [2](#0-1) 
- `ExecutePayload` (the direct `MsgExecutePayload` handler) does the same: `execErr == nil` and `receipt != nil` is treated as full success, and it proceeds to build `PCTx{Status: "SUCCESS"}` and call `CreateUniversalTxFromReceiptIfOutbound` / `AttachRescueOutboundFromReceipt` from the receipt. [3](#0-2) 
- `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` follow the identical pattern for `depositPRC20`, `CallExecuteUniversalTx`, and `ExecutePayloadV2`: `payloadErr != nil` → `FAILED`, else → `SUCCESS`, with no on-chain revert check. [4](#0-3) [5](#0-4) 

If the fork's `CallEVM`/`DerivedEVMCall` (in the `pushchain/evm` fork, outside this repo, so I could not inspect its implementation directly) returns a `nil` Go error whenever the transaction was successfully *included* — even though the contract executed a `REVERT` (e.g., insufficient PRC20 balance in the UEA, a payload call that reverts inside `executeUniversalTx`, or a swap/autoswap failing minimum-out checks) — then every one of these call sites would incorrectly mark the `UniversalTx`/`PCTx` as `SUCCESS`, attach nonexistent outbounds, and skip the revert/refund path that `shouldRevert`/`buildRevertOutbound` is meant to trigger.

### Impact Explanation
If confirmed against the fork's actual `CallEVM`/`DerivedEVMCall` semantics, this breaks the canonical `UniversalTx` state invariant: an inbound whose funds were never actually deposited, or whose payload never actually executed, would be durably recorded as `SUCCESS` in `PcTx`, and downstream flows (`AttachOutboundsToExistingUniversalTx`, `CreateUniversalTxFromReceiptIfOutbound`) would build outbound transactions based on a receipt that shows an on-chain revert. This can lead to permanent loss of the user's expected funds/execution (no revert/refund path fires because `execErr == nil`), or fabricated outbound events based on state that never actually changed — corrupting canonical `UniversalTx` state and honest-UV finalization inputs, both explicitly in-scope impacts.

### Likelihood Explanation
Medium-to-uncertain. The trigger requires only an ordinary, unprivileged inbound whose target UEA/contract call reverts on-chain (e.g., a payload that calls a function that reverts, or insufficient balance for a swap) — fully reachable by a normal user/source-chain transaction, no privileged actor needed. The uncertainty is entirely in the fork: I could not verify from this repo whether `CallEVM`/`DerivedEVMCall` already internally treats a reverted execution as a Go `error` (in which case the current `err != nil` checks would already catch it and this would be a non-issue). The complete absence of any `VmError` handling anywhere in `x/uexecutor`, despite the receipt type exposing that field, is the strongest signal that this check was never intended to be delegated to the Go `error` return and is simply missing.

### Recommendation
After every `DerivedEVMCall`/`CallEVM` invocation (`CallUEAExecutePayload`, `depositPRC20`, `CallExecuteUniversalTx`, `CallPRC20DepositAutoSwap`, `CallUniversalCoreRefundUnusedGas`, factory calls), explicitly check the receipt's execution-status field (e.g., `receipt.VmError != ""` or equivalent `Failed()` semantics) in addition to the Go `error`, and treat a non-empty `VmError` identically to `execErr != nil` — i.e., route it into the existing `FAILED`/`shouldRevert` branches instead of `SUCCESS`.

### Proof of Concept
Conceptual (repo-only, cannot fully exercise the fork's EVM semantics here):
1. Submit an inbound (or `MsgExecutePayload`) whose `UniversalPayload` calls a UEA method that internally reverts (e.g., calls a target contract that always reverts).
2. If the fork's `DerivedEVMCall` returns `(receipt, nil)` for this case (receipt.VmError set, Go error nil) — as is common in cosmos-evm-style `ApplyMessage` wrappers for committed-but-reverted txs — then `ExecutePayloadV2`/`ExecuteInboundFundsAndPayload` will record `PCTx.Status = "SUCCESS"`, call `AttachOutboundsToExistingUniversalTx`, and skip `buildRevertOutbound`, even though the payload never executed on-chain.
