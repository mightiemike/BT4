## Title
Shared `last-update` clock is advanced when only one of two independent interest streams (`index`, `lindex`) actually changes, permanently discarding sub-threshold accrual on the other stream — (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
The `accrue` function in every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) shares a single `last-update` timestamp between two independently-rounded compounding indices: the borrow `index` and the liquidity `lindex`. The timestamp is only reset when at least one of the two indices actually changes value, but the reset discards the *entire* elapsed `time-delta` for both streams — including the one that had not yet crossed its own rounding threshold. Because the two streams round in different directions and at different magnitudes (borrow index rounds up, liquidity index rounds down, and liquidity rate is always ≤ borrow rate), an attacker can call any public entrypoint that triggers `accrue` at a cadence that keeps nudging `index` while `lindex` never crosses its rounding threshold, permanently discarding depositor yield.

### Finding Description
`accrue` computes the next values of both indices from a single shared `time-delta`: [1](#0-0) 

`calc-multiplier-delta` rounds the borrow-index multiplier **up** and the liquidity-index multiplier **down**: [2](#0-1) 

Because `calc-liquidity-rate` discounts the borrow rate by both utilization and `(1 - reserve-factor)`, the liquidity rate is always ≤ the borrow rate, so for the same `time-delta` the borrow-side `index` reaches its integer rounding threshold in `calc-index-next` (a floor division) strictly before the liquidity-side `lindex` does.

`accrue` then only persists `last-update` if *either* index changed — not only if *both* changed: [3](#0-2) 

```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
```

Since `index` moves first, each time it ticks (even by the smallest unit) `last-update` is unconditionally reset to `stacks-block-time`, even though `lindex`'s accumulated `time-delta` had not yet reached the threshold required to move `lindex` by even one unit. The next call to `accrue` then computes `next-liquidity-index` using a fresh, restarted `time-delta` starting from the new `last-update` — the sub-threshold portion of elapsed time that was building up toward `lindex`'s next tick is gone forever. If a caller repeats this cadence indefinitely, `lindex` can be made to advance far slower than it should (or never advance at all), even though the borrow side keeps correctly compounding and correctly extracting interest from borrowers into `total-assets`/`total-borrowed`.

This is the direct Clarity analog of the referenced Solidity bug class: a shared "clock" (`lastTimestamp` / here `last-update`) is advanced based on one signal (any change) while a second, independently rounded quantity (the liquidity yield owed to depositors) is silently starved of the fractional time it needed to accrue, because the clock reset discards it rather than carrying it forward.

### Impact Explanation
Every state-changing call into a vault (`deposit`, `redeem`, `system-borrow`, `system-repay`, etc.) invokes `accrue` first. An attacker (or even an innocuous high-frequency caller such as a bot or arbitrageur) who repeatedly triggers such calls at short intervals causes `last-update` to reset every time the (faster-moving) borrow `index` ticks, well before the (slower-moving) `lindex` accumulates enough delta to tick. The liquidity index underlying ztoken share value therefore permanently misses interest that borrowers are, in parallel, correctly paying — that value is stranded rather than distributed to depositors (it is not double counted or refunded later; the discarded `time-delta` for `lindex` is simply gone). This is a permanent freezing/loss of unclaimed yield owed to LP depositors, matching the in-scope "High" impact category (theft/permanent freezing of unclaimed yield).

### Likelihood Explanation
The exploit requires only sending ordinary, unprivileged transactions (any public vault entrypoint) at a chosen cadence — no special permissions, no DAO action, and no cross-user interference are required. The attacker only needs to observe the current `index`/`lindex`/`last-update` state (all readable) and choose call timing so that a call lands right after `index` has ticked but before `lindex` would have. Given `calc-multiplier-delta`'s round-up-vs-round-down asymmetry and the structural inequality `liquidity-rate ≤ borrow-rate`, this condition is not a rare edge case — it is the expected steady-state behavior whenever utilization or the reserve factor meaningfully discounts the liquidity rate relative to the borrow rate, which is normal operating condition for the vaults.

### Recommendation
Do not gate the `last-update` reset on "either index changed." Instead, track elapsed time per accrual stream independently, or only reset `last-update` when the elapsed time has been fully consumed by both streams (e.g., keep an internal remainder/carry for whichever stream did not tick, or use a single higher-precision multiplier calc that isn't subject to independent integer truncation per stream). Alternatively, always advance `last-update` on any accrue call and instead compute both multipliers using scaled arithmetic so that fractional time carries forward rather than being discarded — analogous to the original report's "scalar" mitigation for `noOfDays`.

### Proof of Concept
1. Vault has nonzero utilization so `interest-rate` (borrow rate) is materially higher than the effective `liquidity-rate` (borrow rate discounted by utilization × (1 - reserve-factor)) — see `calc-liquidity-rate` at [4](#0-3) .
2. Attacker calls a trivial state-changing entrypoint (e.g., `deposit` of the minimum unit) repeatedly, once per block, each call invoking `(try! (accrue))`.
3. Each call: `next-index` computes a `time-delta` since `last-update`; because the borrow-side multiplier rounds up (`mul-div-up`) and needs a smaller `extra` to move `idx` by one unit than `lindex` needs to move by one unit (round-down, smaller rate), `index` ticks on nearly every call while `lindex` does not.
4. Because `index` ticked, the shared condition `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` is true, so `last-update` is reset to `stacks-block-time` — even though `lindex`'s accumulated `time-delta` had not reached its own threshold.
5. Repeating step 2–4 indefinitely means `lindex`'s `time-delta` is reset to (near) zero on almost every call, so it essentially never accumulates enough delta to tick, permanently starving depositors of the liquidity yield that borrowers are simultaneously paying via the correctly-ticking `index`/`total-borrowed`/interest flow.
