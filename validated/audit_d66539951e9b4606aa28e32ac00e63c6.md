## Title
Exchange (TRC10 AMM) liquidity permanently locked if either pool-side balance reaches zero - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`java-tron`'s built-in Bancor-style TRC10 exchange (`ExchangeCreateActuator` / `ExchangeTransactionActuator` / `ExchangeWithdrawActuator`) implements the same "hard bound guard on the only exit path" pattern as the Isomorph vault. `ExchangeWithdrawActuator` is the sole actuator that lets a pool creator remove liquidity from an exchange pair, and its `doValidate()` unconditionally reverts the moment *either* side of the pool balance is exactly zero, without distinguishing which token the creator is actually trying to withdraw.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` contains: [1](#0-0) 

```java
if (firstTokenBalance == 0 || secondTokenBalance == 0) {
  throw new ContractValidateException("Token balance in exchange is equal with 0,"
      + "the exchange has been closed");
}
```

This check fires whenever *either* `firstTokenBalance` or `secondTokenBalance` is zero — even if the creator is trying to withdraw the *other*, still-nonzero token. The pool balances are mutated by `ExchangeTransactionActuator`, which lets any unprivileged account perform anonymous, broadcast-transaction swaps against the pool using the Bancor-curve math in `ExchangeCapsule.transaction`/`ExchangeProcessor`: [2](#0-1) 

Because the curve output is truncated to a `long` (`(long) issuedSupply` / `(long) exchangeBalance` in `ExchangeProcessor`), repeated or large trades can legitimately drive one side of the pool balance to exactly zero: [3](#0-2) 

Once that happens, `ExchangeWithdrawActuator` is the *only* actuator capable of returning pooled tokens to the creator — there is no alternate "close pool" or emergency-drain path in `ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`. The zero-balance guard then makes every future `ExchangeWithdrawContract` call from the creator revert with `"Token balance in exchange is equal with 0, the exchange has been closed"`, exactly mirroring the Isomorph bug: an unconditional bound check embedded in the only withdrawal path permanently traps the remaining, still-valuable balance of the non-zero token.

### Impact Explanation
Any TRC10 exchange pool where a public, anonymous swap transaction (`ExchangeTransactionContract`, processed by `ExchangeTransactionActuator`) drives one side's balance to exactly zero causes the creator's entire remaining stake of the other token to become permanently unrecoverable on-chain — an unrecoverable asset-lock/accounting corruption reachable purely through normal broadcast transactions, with no privileged action required to trigger it.

### Likelihood Explanation
Triggering requires only ordinary `ExchangeTransactionContract` swaps (unprivileged, anonymous), and the existing test suite already demonstrates the exact zero-balance state is reachable and explicitly validated against (`SameTokenNameCloseTokenBalanceZero` sets both balances to 0 and expects the revert): [4](#0-3) 

The `long` truncation in `ExchangeProcessor.exchangeFromSupply`/`exchangeToSupply` makes it plausible for a large or final trade to exactly zero out one balance while the other side is still nonzero, especially as pool depth shrinks near the end of a draining sequence of trades.

### Recommendation
In `ExchangeWithdrawActuator.doValidate()` / `execute()`, do not gate withdrawal of a nonzero-balance token on the *other* token's balance being nonzero. Track and allow independent draining of each side, or add a dedicated pool-closing path that lets the creator withdraw the residual nonzero token even when the counter-asset balance is zero, so that a skewed/zeroed pool state can never permanently strand the creator's remaining funds.

### Proof of Concept
1. Creator issues an exchange pool via `ExchangeCreateActuator` with `firstToken`/`secondToken` balances `B1`, `B2`.
2. Any unprivileged account repeatedly (or via one large trade) calls `ExchangeTransactionActuator` selling `firstToken`, driving `secondTokenBalance` to exactly `0` (feasible due to truncation in `ExchangeProcessor.exchangeFromSupply`), while `firstTokenBalance` remains large and positive.
3. Creator calls `ExchangeWithdrawActuator` to withdraw the remaining `firstTokenBalance`.
4. `doValidate()`'s check `secondTokenBalance == 0` throws `ContractValidateException("Token balance in exchange is equal with 0, the exchange has been closed")`, as reproduced by the existing `SameTokenNameCloseTokenBalanceZero` test, permanently blocking withdrawal of the still-positive `firstTokenBalance`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
