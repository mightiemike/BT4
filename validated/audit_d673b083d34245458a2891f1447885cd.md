### Title
Metering `Report.Settle` refunds an earmark that was never actually deducted, corrupting the CRE workflow credit balance - ([File: core/services/workflows/metering/metering.go])

### Summary
This is the analog of the "bad debt isn't cleared when the accumulator is lower than the debt" bug class: an all-or-nothing balance check (`balanceStore.Minus`) silently no-ops on failure instead of partially applying it, and the calling code does not account for that no-op, leaving the tracked balance out of sync with the true accounted state — in this case in the wrong direction (it inflates the balance instead of leaving bad debt uncleared).

### Finding Description
`ByResource`, a `DeductOpt` used to earmark local credit balance for a capability step, unconditionally records the requested earmark in `step.Deduction` before it knows whether the underlying deduction succeeded: [1](#0-0) 

`r.balance.Minus(bal)` is an all-or-nothing operation: if the requested amount exceeds the current balance it returns `ErrInsufficientBalance` and leaves `bs.balance` completely unmodified — exactly like the `clearBadDebt` all-or-nothing threshold check in the referenced report: [2](#0-1) 

When `Minus` fails this way, `ByResource` still returns with `step.Deduction` set to the *full requested amount* (via the `defer` that stores `step` into `r.steps[ref]` regardless of the error), even though the balance was never actually reduced.

Later, `Report.Settle` computes the real spend reported by nodes (`spentCredits`) and "refunds the difference between what local balance had been earmarked and the actual spend": [3](#0-2) 

This logic assumes `step.Deduction` credits were actually subtracted from the balance at `Deduct` time. If they were not (because `Minus` failed and no-opped), `Settle` still performs `r.balance.Add(step.Deduction.Sub(spentCredits))`, adding back credits that were never removed. When `spentCredits < step.Deduction` (the common case, since the deduction is normally an upper-bound earmark and the actual spend is smaller), this call injects `step.Deduction - spentCredits` credits into the balance out of thin air. The comment "invariant: spend exceeded reserve" only guards the opposite failure mode (spend > deduction), not this one.

The root cause matches the report's core pattern: an all-or-nothing pre-condition check (`accumulator >= badDebt` / `amount.GreaterThan(bs.balance)`) causes a downstream reconciliation step to either skip clearing state or, here, to over-credit state, because the code that performs the reconciliation doesn't verify that the earlier operation it depends on actually took effect.

### Impact Explanation
This causes the local, in-memory `Report` balance (used to gate subsequent `Deduct` calls and reported to the billing service as `CreditsConsumed` via `SendReceipt`) to diverge from the true spend. In the "insufficient balance" scenario, a workflow execution can end up crediting itself back funds that were never actually withdrawn from the balance, effectively allowing further capability invocations to be earmarked using credits that don't correspond to real billing service reservations. This is a data-integrity/misreporting bug in the billing/metering accounting path — it can let workflow executions proceed and be billed inconsistently with the amount actually reserved from the billing service, which is the class of impact explicitly listed as acceptable (misreporting/data tampering).

### Likelihood Explanation
`ByResource` is invoked from `core/services/workflows/v2/engine.go` as one of the `DeductOpt` code paths used to earmark spend for capability calls, and its `amount` parameter is not bounded to the current balance before `Minus` is called [4](#0-3) . Any workflow execution scenario where a requested deduction exceeds the currently available local balance (e.g., low remaining credits, or a capability requesting a larger earmark than what's left) will trigger this: `Minus` fails, `Deduct` returns `ErrInsufficientBalance` (which per the code/tests explicitly "does not block workflow execution" — see `metering_test.go` "happy path with zero reserve and insufficient balance does not block workflow execution"), and the subsequent `Settle` call still performs the erroneous `Add`. This does not require any special privilege — it is reachable through normal, unprivileged workflow execution whenever the local credit balance is exhausted or close to exhausted, which the code is explicitly designed to tolerate ("fail open, continue optimistically").

### Recommendation
`ByResource` (and any other `DeductOpt`) should not record `step.Deduction` as if it were subtracted when `balance.Minus` returns an error. Either:
1. Track whether the earmark actually succeeded (e.g., set `step.Deduction = decimal.Zero` when `Minus` fails, since nothing was actually reserved), or
2. Have `Minus`/`MinusAs` support a "clamp to zero" partial-application mode and record the amount actually subtracted (mirroring the report's own recommendation to clear "the maximum amount possible" rather than nothing), and use that actual value in `step.Deduction` for `Settle`'s refund calculation.

Either fix ensures `Settle`'s `r.balance.Add(step.Deduction.Sub(spentCredits))` never adds back credits that were never subtracted in the first place.

### Proof of Concept
1. Create a `Report`, call `Reserve` so the local balance is set to some small value (or zero, e.g., via a `successZeroReserveResponseWithRates`-style response as used in `metering_test.go`).
2. Call `report.Deduct("step1", ByResource(testUnitA, "", <amount whose converted balance exceeds current balance>))`. This returns `ErrInsufficientBalance`, and per the code, execution continues (as shown by the existing test `"happy path with zero reserve and insufficient balance does not block workflow execution"` at `metering_test.go:1440-1496`), and `r.steps["step1"].Deduction` is nonetheless set to the full requested (unmet) earmark.
3. Call `report.Settle("step1", metadata)` where the node-reported spend value is smaller than the requested `step.Deduction` amount (or zero).
4. Observe `r.balance.balance` after `Settle` — it will have increased by `step.Deduction - spentCredits`, even though `Minus` never subtracted anything from it in step 2. Compare `r.balance.Get()` before/after to confirm the balance grew without a corresponding actual reservation from the billing service.

func ByResource(
	spendType, capabilityID string,
	amount decimal.Decimal,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     capabilityID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		bal, err := r.balance.ConvertToBalance(spendType, amount)
		if err != nil {
			// Fail open, continue optimistically
			r.switchToMeteringMode(fmt.Errorf("failed to convert to balance [%s]: %w", spendType, err))
		}

		step.Deduction = bal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return []capabilities.SpendLimit{}, r.balance.Minus(bal)
	}

// Minus lowers the current credit balance.
func (bs *balanceStore) Minus(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	if amount.GreaterThan(bs.balance) {
		return ErrInsufficientBalance
	}

	bs.balance = bs.balance.Sub(amount)

	return nil
}
