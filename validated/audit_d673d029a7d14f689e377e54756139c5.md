### Title
Duplicate transaction IDs can be double-processed and committed into a single block due to `validateDup` relying solely on `TransactionCache`/`TransactionStore`, which are not updated until after a block's transactions finish executing - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
`Manager.validateDup` (and the `containsTransaction` helper it calls) only consults the `TransactionCache` bloom filter and `TransactionStore`, both of which are populated at the very end of `processBlock` via `updateTransHashCache`/`updateRecentTransaction`. Neither `pushTransaction`, `generateBlock`, nor `processBlock`'s own per-transaction loop cross-checks against `pendingTransactions`/`rePushTransactions` or against transactions already processed earlier in the same iteration, so the same signed transaction can be admitted twice into the pending queues and packed twice into the same block, with both copies executing successfully during block application before dedup state is updated.

### Finding Description
`validateDup` is defined as: [1](#0-0) 

`containsTransaction` returns `false` (not duplicate) whenever the tx ID is absent from both the `TransactionCache` bloom filter and `TransactionStore`. Crucially, these stores are only written for a block's transactions after the block's entire transaction loop has finished: [2](#0-1) 

`pushTransaction` adds a transaction to `pendingTransactions` after calling `processTransaction(trx, null)`, which itself calls `validateDup`. Nothing checks `pendingTransactions`/`rePushTransactions` for an existing entry with the same ID: [3](#0-2) 

If the same signed transaction is submitted twice before the first is committed to a block (e.g., via two separate P2P `TransactionsMessage`s, each of which only dedups *within* a single message via `TransactionsMsgHandler.check`'s `seen` set, not across messages), both copies can independently pass `validateDup` and land in `pendingTransactions` as two distinct `TransactionCapsule` objects sharing the same transaction ID. [4](#0-3) 

When a block is produced, `generateBlock` iterates `pendingTransactions`/`rePushTransactions` one entry at a time and calls `processTransaction(trx, blockCapsule)` for each, again gated only by `validateDup`, without deduping by transaction ID against transactions already added to `toBePacked` in the same loop: [5](#0-4) 

Because `transactionCache`/`TransactionStore` are still empty for this ID during packing, both duplicate entries can be processed and packed into `toBePacked`, producing a single block containing the same transaction ID twice. When this block is later applied via `processBlock`, the per-transaction loop again calls `processTransaction` (which re-invokes `validateDup`) for every transaction in `block.getTransactions()`, but `updateTransHashCache`/`updateRecentTransaction` (the calls that finally register the ID as seen) only run *after* the loop completes. Consequently both duplicate-ID transactions in the block are executed for real against persistent account state before the dedup structures are ever updated - resulting in double execution/double-settlement that is baked into the committed chain, not merely a transient pending-queue artifact.

### Impact Explanation
An attacker can cause the same signed transfer/contract call to be executed twice with real, permanent effect on chain state within (or before) a single block, because the dedup mechanism (`TransactionCache` + `TransactionStore`) is updated strictly after the block-level or pending-level processing loop finishes, not incrementally as each transaction is processed. This breaks the "one logical spend settles exactly once" invariant and can result in duplicated balance debits/credits or duplicated contract execution.

### Likelihood Explanation
This requires only unprivileged network access: an attacker submits the same fully-signed transaction via two separate P2P `TransactionsMessage`s (or two separate broadcast calls, if the API-layer `transactionIdCache` check in `Wallet.broadcastTransaction` is bypassed, disabled, or racy) before the first copy is committed. The per-message duplicate check in `TransactionsMsgHandler.check` only prevents duplicates *within one message*, not across messages, so this is straightforward and repeatable for any attacker who controls a real signed transaction (their own funds/contract calls).

### Recommendation
Make transaction admission dedup-aware of in-flight state, not just the committed `TransactionStore`/`TransactionCache`:
- Track "in-pending" transaction IDs (e.g., a synchronized `Set<Sha256Hash>` alongside `pendingTransactions`/`rePushTransactions`) and check/insert atomically in `pushTransaction`, rejecting a second submission of the same ID while the first is still pending or being packed.
- In `generateBlock`'s packing loop, track already-packed transaction IDs in a local `Set` and skip any subsequent entry with a duplicate ID.
- In `processBlock`'s per-transaction loop, maintain a local `Set<Sha256Hash>` of IDs already processed within the current block and reject/skip duplicates immediately, rather than relying solely on `TransactionCache`/`TransactionStore` state that isn't updated until after the loop.

### Proof of Concept
Integration test plan (JUnit, using `ManagerTest`/similar harness with an in-memory chain):
1. Fund test account A, construct a single signed `TransferContract` transaction `trx` from A to B for an amount within A's balance.
2. Create two independent `TransactionCapsule` instances from the identical serialized `trx` bytes (`trx1`, `trx2`), simulating two separate P2P submissions with the same ID.
3. Call `dbManager.pushTransaction(trx1)` — assert success, and assert `dbManager.getTxFromPending(txId)` returns it.
4. Call `dbManager.pushTransaction(trx2)` immediately after (before any block is produced) — assert that it is **currently accepted** (no `DupTransactionException`), demonstrating `validateDup` does not see the first pending copy.
5. Call `dbManager.generateBlock(...)` and inspect the resulting `BlockCapsule.getTransactions()` — assert (bug) that the transaction ID appears **twice**, or (expected/fixed behavior) that it appears only once.
6. Push the generated block via `dbManager.pushBlock(block)` and read account A's final balance — assert (bug) that the balance was debited twice for `trx`'s amount, versus (expected) exactly once.

Expected result under current code: steps 4-6 succeed without rejection and the balance is debited twice, confirming the double-execution/double-settlement bug. After applying the recommended fix, step 4 (or the packing/apply stage) should raise `DupTransactionException` for the second copy, and the balance should reflect only a single debit.

  private boolean containsTransaction(TransactionCapsule transactionCapsule) {
    return containsTransaction(transactionCapsule.getTransactionId().getBytes());
  }


  private boolean containsTransaction(byte[] transactionId) {
    if (transactionCache != null && !transactionCache.has(transactionId)) {
      // using the bloom filter only determines non-existent transaction
      return false;
    }

    return chainBaseManager.getTransactionStore()
        .has(transactionId);
  }

  private void check(PeerConnection peer, TransactionsMessage msg) throws P2pException {
    List<Transaction> list = msg.getTransactions().getTransactionsList();
    Set<Sha256Hash> seen = new HashSet<>(list.size() * 2);
    for (Transaction trx : list) {
      Sha256Hash id = new TransactionMessage(trx).getMessageId();
      if (!seen.add(id)) {
        throw new P2pException(TypeEnum.BAD_MESSAGE,
            "TransactionsMessage contains duplicate transaction: " + id);
      }
      Item item = new Item(id, InventoryType.TRX);
      if (!peer.getAdvInvRequest().containsKey(item)) {
        throw new P2pException(TypeEnum.BAD_MESSAGE,
            "trx: " + msg.getMessageId() + " without request.");
      }
      if (trx.getRawData().getContractCount() < 1) {
        throw new P2pException(TypeEnum.BAD_TRX,
            "tx " + item.getHash() + " contract size should be greater than 0");
      }
      for (ByteString sig : trx.getSignatureList()) {
        if (!SignUtils.isValidLength(sig.size())) {
          throw new P2pException(TypeEnum.BAD_TRX,
              "tx " + item.getHash() + " signature size is " + sig.size());
        }
      }
    }
