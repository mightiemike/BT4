The reported Solidity bug is a "wrong identity used for a privileged action" pattern: the function validates/collects from the *correct* party earlier, but then executes the sensitive operation (`_repay`) using a *different*, incorrect identity parameter instead of the one actually holding the already-collected funds. Searching shopify-app-js for the same bug class — a piece of code that authenticates one identity but then performs the privileged action using a separate, untrusted identity parameter — surfaces a real analog in `tokenExchange`.

### Title
Token exchange does not verify that the caller-supplied `shop` matches the session token's `dest`, allowing shop/session confusion - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`shopify.auth.tokenExchange()` decodes and cryptographically verifies the session token (proving it is a legitimately signed token for *some* shop), but it never checks that the decoded token's `dest` (its true, authenticated shop) matches the separately-supplied `shop` parameter. It then uses that unverified `shop` parameter — not the token's own `dest` — to build the OAuth request URL and to key/construct the resulting `Session` object.

### Finding Description
In `tokenExchange()`, the session token is decoded purely to validate its signature/expiry/audience, and the returned payload is discarded: [1](#0-0) 

The `shop` used for the actual privileged action (the outbound OAuth `/admin/oauth/access_token` request, and the identity baked into the returned `Session`) comes entirely from the caller-supplied `shop` argument, sanitized only for format — not cross-checked against `payload.dest`: [2](#0-1) 

`createSession` then keys the resulting `Session`'s `id` and `shop` fields directly from this same untrusted `shop` value, via `getOfflineId(shop)` / `getJwtSessionId(shop, ...)`: [3](#0-2) [4](#0-3) 

This is structurally the same root cause as the Solidity finding: an identity is properly authenticated/validated at one point (decoding the session token, analogous to collecting the correct asset shares), but a *different*, unverified identity/parameter is used for the actual sensitive operation and its bookkeeping (using `shop` instead of `payload.dest`, analogous to using `from` instead of `address(this)`).

Notably, this exact pattern is also what the package's own documentation recommends to app developers — deriving `shop` from the request's query string, independently of the session token: [5](#0-4) 

By contrast, the library's own internal middlewares (e.g. `performTokenExchange` in `shopify-app-express` and the `token-exchange` strategies in `shopify-app-remix`/`shopify-app-react-router`) correctly derive `shop` *from the decoded token's `dest`* before calling `tokenExchange`, so they are not affected: [6](#0-5) 

### Impact Explanation
If an app author follows the documented pattern (or any pattern where `shop` is taken from a source independent of the session token, e.g. a query parameter), an attacker who supplies a mismatched `shop` alongside a session token can cause the local `Session` object returned/stored by the library to be keyed and labeled with the attacker-chosen `shop` rather than the token's true, authenticated shop (`payload.dest`). Because `SessionStorage` keys sessions by this `id`/`shop`, this is a session-storage/tenant-confusion primitive: the resulting stored session record's identity does not match the actual authenticated tenant that produced the session token. The severity depends on whether Shopify's OAuth server independently rejects a `dest`/hostname mismatch for the outbound token exchange call, which shopify-app-js cannot control or verify — but the local defense-in-depth check (comparing `payload.dest` to `shop`) is missing entirely, unlike other flows in this same codebase (e.g. `getSessionTokenContext` in `shopify-app-remix`/`shopify-app-react-router`, which derives `shop` strictly from `payload.dest` after validation) — see: [7](#0-6) 

### Likelihood Explanation
This is reachable by any app author who wires `shopify.auth.tokenExchange()` up per the published documentation, and the resulting mismatch is directly controllable by an unprivileged party supplying an arbitrary `shop` value in a public-facing request (e.g. `req.query.shop`) alongside their own valid session token.

### Recommendation
After decoding the session token, verify that `new URL(payload.dest).hostname` matches the sanitized `shop` argument before proceeding, and throw `InvalidJwtError` (or similar) on mismatch — mirroring the pattern already used in `shopify-app-remix`/`shopify-app-react-router`'s `getSessionTokenContext`. Alternatively, derive `shop` exclusively from `payload.dest` inside `tokenExchange()` itself rather than accepting it as an independent caller-supplied parameter, removing the possibility of divergence.

### Proof of Concept
1. Attacker legitimately obtains a valid session token for `shop-a.myshopify.com` (its `aud` matches the app's API key, `dest` is `https://shop-a.myshopify.com`).
2. Attacker calls the app's `/auth` route (implemented per the documented pattern) with `?shop=shop-b.myshopify.com`, and the app's own session token header/param set to the token from step 1.
3. `tokenExchange()` decodes/validates the token successfully (signature is valid, `aud` matches) but never compares `payload.dest` to `shop`.
4. The library builds `https://shop-b.myshopify.com/admin/oauth/access_token` as the request target and constructs/returns a `Session` with `shop: 'shop-b.myshopify.com'` and `id: 'offline_shop-b.myshopify.com'` (or the online equivalent), regardless of the token's true origin — demonstrating the missing binding between the authenticated identity and the identity used for the sensitive session-creation/storage action.

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };

export function getJwtSessionId(config: ConfigInterface) {
