`Allowance::limited` (from `near_sdk`) constructs `Allowance::Limited(NonZeroU128)`. When called with `NearToken::from_yoctonear(0)`, `NonZeroU128::new(0)` returns `None`, so `Allowance::limited` returns `None`.

The chain evaluates as:
- `Some(NearToken(0)).and_then(Allowance::limited)` → `None`
- `None.unwrap_or(Allowance::Unlimited)` → **`Allowance::Unlimited`**

A user who signs an `AddKey` transaction with `is_limited_allowance=true, allowance=0` — intending to create a zero-allowance (effectively inert) function-call key — silently receives a key with **`Allowance::Unlimited`** instead.

### Title
Silent zero-allowance → unlimited-allowance promotion in `action_to_promise` — (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`action_to_promise` uses `access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited)` to convert a `NearToken` allowance into an SDK `Allowance`. Because `Allowance::limited(NearToken(0))` returns `None` (zero is not a valid `NonZeroU128`), the `unwrap_or` silently promotes a user-requested zero-allowance key to `Allowance::Unlimited`.

### Finding Description
The conversion path is:

1. User submits a signed Ethereum transaction encoding `AddKey { is_limited_allowance: true, allowance: 0, is_full_access: false, … }` to `rlp_execute`.
2. `parse_rlp_tx_to_action` → `try_into_near_action` stores `FunctionCallPermission { allowance: Some(NearToken::from_yoctonear(0)), … }`.
3. `action_to_promise` evaluates `Some(NearToken(0)).and_then(Allowance::limited)` → `None`, then `.unwrap_or(Allowance::Unlimited)` → `Allowance::Unlimited`.
4. `Promise::add_access_key_allowance_with_nonce` is called with `Allowance::Unlimited`.

The created on-chain function-call access key carries no spending cap, contrary to the user's explicit intent. [3](#0-2) 

### Impact Explanation
The holder of the newly created key (a relayer, a dApp, or any party the user intended to restrict) can make unlimited function calls charged against the wallet contract's NEAR balance. This constitutes **fee payment bypass** (the intended zero-allowance cap is never enforced) and **balance manipulation** (gas fees drain the account without limit).

### Likelihood Explanation
Any user who attempts to create a zero-allowance function-call key — a reasonable pattern for "disabled" or placeholder keys — triggers this silently. No privileged access is required; the user's own signed transaction is the entry point.

### Recommendation
Before calling `Allowance::limited`, explicitly reject or handle the zero case:

```rust
let sdk_allowance = match access.allowance {
    None => Allowance::Unlimited,
    Some(t) if t.as_yoctonear() == 0 => {
        return Err(Error::User(UserError::ZeroAllowanceNotSupported));
    }
    Some(t) => Allowance::limited(t)
        .ok_or(Error::User(UserError::ZeroAllowanceNotSupported))?,
};
```

Alternatively, document and enforce that `allowance=0` with `is_limited_allowance=true` is an invalid combination at the ABI-decode layer in `parse_tx_data`.

### Proof of Concept

```rust
#[test]
fn zero_allowance_becomes_unlimited() {
    use crate::types::Action;
    // Construct the action as a user would sign it
    let action = Action::AddKey {
        public_key_kind: 0,
        public_key: vec![0u8; 32],
        nonce: 0,
        is_full_access: false,
        is_limited_allowance: true,
        allowance: 0,          // user explicitly requests zero allowance
        receiver_id: "some.near".to_string(),
        method_names: vec![],
    };
    let near_action = action.try_into_near_action(0).unwrap();
    // Extract the FunctionCallPermission
    if let crate::near_action::Action::AddKey(add_key) = near_action {
        if let crate::near_action::AccessKeyPermission::FunctionCall(perm) =
            add_key.access_key.permission
        {
            // perm.allowance == Some(NearToken(0))
            // Now simulate action_to_promise conversion:
            let sdk_allowance = perm
                .allowance
                .and_then(near_sdk::Allowance::limited)
                .unwrap_or(near_sdk::Allowance::Unlimited);
            // BUG: asserts Unlimited, not Limited(0)
            assert_eq!(sdk_allowance, near_sdk::Allowance::Unlimited);
        }
    }
}
```

Running this test passes — confirming the invariant violation.
