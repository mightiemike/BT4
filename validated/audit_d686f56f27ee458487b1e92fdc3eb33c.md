### Title
Asset-name collision with the reserved TRX sentinel (`"_"`) allows a TRC10 token to alias as TRX in Exchange actuators - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
The externally reported bug class is: a privileged withdrawal function identifies "the vesting token" purely by comparing an *address/identifier* to a known constant, rather than validating the actual balance effect, allowing an aliased identifier for the same underlying asset to bypass the check. The same root-cause pattern exists in java-tron's Exchange subsystem: TRX is distinguished from a TRC10 token purely by comparing the token identifier byte array to the constant `TRX_SYMBOL_BYTES` (`"_"`), while `AssetIssueActuator.validate()` only blocks the *string* `"trx"` as an asset name/id, not the literal sentinel value `"_"` itself [1](#0-0) .

### Finding Description
`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` all decide whether a `tokenId` byte array refers to TRX or to a TRC10 asset with a simple `Arrays.equals(tokenID, TRX_SYMBOL_BYTES)` check [2](#0-1) . This check assumes the byte-string `"_"` can never legitimately be the identifier of a real TRC10 asset.

However, `AssetIssueActuator.validate()` — the actuator that lets any account issue a new TRC10 asset — only rejects the case-insensitive name `"trx"` [3](#0-2) . It does not reject an asset whose chosen name/id is exactly `"_"` (the TRX sentinel byte string used throughout the Exchange actuators), as long as `TransactionUtil.validAssetName` permits it and (in the `AllowSameTokenName == 0` regime) no existing asset is already keyed by that name in `AssetIssueStore` [4](#0-3) .

If such an asset can be created, every downstream Exchange actuator that relies on `Arrays.equals(tokenID, TRX_SYMBOL_BYTES)` to route balance mutations (TRX balance vs. `reduceAssetAmountV2`/`addAssetAmountV2` on the asset store) will misclassify the attacker's TRC10 token as TRX [2](#0-1) , [5](#0-4) . This is directly analogous to the reported bug: an identity/address check that is supposed to gate a balance-affecting operation is bypassed because two distinct entities (the reserved TRX sentinel and an attacker-mintable TRC10 asset id) can be made to collide, decoupling the check from the actual value being moved.

### Impact Explanation
If the collision is achievable, an attacker could create Exchange pairs and perform injects/withdraws/trades where the code path that is supposed to touch the attacker's TRC10 asset balance instead touches the account's real TRX balance (or vice-versa), corrupting exchange accounting (`ExchangeCapsule` balances vs. actual TRX/asset balances) and potentially allowing extraction of TRX while only ever spending/receiving the attacker-controlled TRC10 token, or causing legitimate exchange participants' withdrawals to fail due to balance mismatches — the same "vested/reserved funds become unavailable or misallocated" outcome described in the original report.

### Likelihood Explanation
This requires only two unprivileged, broadcastable transactions: an `AssetIssueContract` issuance naming the asset `"_"`, followed by normal `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` calls referencing that token id. No special privileges are needed. The actual likelihood hinges on whether `TransactionUtil.validAssetName` and the `AssetIssueStore` uniqueness check actually permit the literal byte-string `"_"` as a valid, previously-unused asset name/id — this could not be fully confirmed from the available index (the body of `TransactionUtil.validAssetName` and the exact bytes of `TRX_SYMBOL_BYTES` in `Parameter.java` were not retrievable in this pass), so likelihood is uncertain pending verification of those two constraints.

### Recommendation
- In `AssetIssueActuator.validate()`, explicitly reject any asset name/abbreviation/id equal to the raw `TRX_SYMBOL_BYTES` sentinel (`"_"`), not just the string `"trx"`.
- In the Exchange actuators, avoid relying solely on identifier equality to route balance changes; instead, explicitly special-case TRX only when the identifier byte-for-byte matches the sentinel *and* that sentinel is provably reserved (never issuable via `AssetIssueActuator`), and add defensive checks/tests asserting that no TRC10 asset can ever be issued with an id colliding with `TRX_SYMBOL_BYTES`.
- Add regression tests analogous to `assetIssueTRXNameTest` in `AssetIssueActuatorTest.java` that specifically attempt to issue an asset literally named `"_"` and verify rejection.

### Proof of Concept
1. Submit an `AssetIssueContract` transaction with `name = "_"` (and, depending on `AllowSameTokenName`, ensure no other asset currently occupies that key) — this is not blocked by the current name check, which only rejects `"trx"` [1](#0-0) .
2. Submit an `ExchangeCreateContract` (or Inject/Withdraw/Transaction) referencing `firstTokenId = "_"` for this newly issued asset.
3. Because `Arrays.equals(firstTokenID, TRX_SYMBOL_BYTES)` evaluates true, the actuator debits/credits the account's TRX balance via `accountCapsule.setBalance(...)` instead of the TRC10 asset balance via `reduceAssetAmountV2`/`addAssetAmountV2` [2](#0-1) , causing a mismatch between the `ExchangeCapsule`'s recorded token balance and the actual asset/TRX balances moved.

*Note: full confirmation requires inspecting `TransactionUtil.validAssetName` and `Parameter.ChainSymbol.TRX_SYMBOL_BYTES`'s exact byte value, which were not fully retrievable from the indexed codebase in this session — a Devin session with full repo access would be needed to verify these two preconditions precisely.*
