### Title
Rounding-to-zero of `remaining-debt-to-repay` causes full-balance collateral seizure instead of the calculated capped amount - (File: `mainnet/contracts/market/v0-4-market.clar`, function `liquidate`)

### Summary
In `liquidate`, after the liquidator's requested `debt-amount` is capped and scaled down through `scale-debt-for-liquidation`, the contract computes how much of the borrower's remaining collateral balance in that asset (`coll-remaining`) is still economically "worth" liquidating (`remaining-debt-to-repay`). If that USD-denominated computation rounds down to zero due to normalization/decimals rounding, the code silently treats the position as fully exhausted and swaps `coll-final` from the correctly capped `coll-final-raw` to the full `user-coll-balance` — seizing the entire remaining collateral balance for a debt repayment that only justified `coll-final-raw`.

### Finding Description
The relevant sequence in `liquidate` (`mainnet/contracts/market/v0-4-market.clar:1470-1486`):

1. `scaled-info` computes `coll-final-raw`, the collateral amount that is proportionally justified by the (possibly capped) `debt-final` being repaid [1](#0-0) .
2. `coll-remaining` is the leftover collateral balance after this liquidation: `(- user-coll-balance coll-final-raw)` [2](#0-1) .
3. `remaining-debt-to-repay` is derived from `coll-remaining`'s USD value (`normalize`), then divided down through BPS scaling and converted to scaled debt units, finally rounded via `mul-div-up` [3](#0-2) .
4. `coll-final` is then set to `user-coll-balance` (the *entire* remaining balance) whenever `remaining-debt-to-repay` evaluates to `u0`, instead of the deliberately capped `coll-final-raw` [4](#0-3) .

This mirrors the reported Behodler pattern exactly: a downstream value (`adjustedRectangle` there, `remaining-debt-to-repay` here) that is supposed to gate/limit a deduction can become zero through intermediate rounding/normalization of one of its inputs (`coll-remaining * coll-price` normalized to USD, then divided by `(+ BPS liq-penalty-max)`, then divided by `debt-price`, then divided by `borrow-index` — several successive `mul-div-down` roundings). When that chain rounds to zero, the code does not "deduct nothing and stop" (which would be safe) — it instead takes the branch meant for "no residual value left to protect" and substitutes the *full* uncapped balance (`user-coll-balance`) for the correctly capped value (`coll-final-raw`), exactly as `scxMinted`'s deduction being skipped led to the full pre-burn balance being used in the vulnerable line 230 of `Limbo.sol`.

The intent of this branch is understandable as a "dust sweep" (avoid leaving unliquidatable dust collateral behind), but the mechanism is unguarded: it fires whenever the *last* multi-step rounding in the chain lands on zero, regardless of how large `coll-remaining` (in raw token units) actually is, only requiring its final derived scaled-debt representation to round to zero. Because `debt-amount` — and consequently `debt-final` and `coll-final-raw` — is chosen by the liquidator (the caller of `liquidate`), an attacker can select `debt-amount` such that `coll-remaining` lands exactly in the rounding-to-zero window for the specific collateral asset's decimals/price/BPS-penalty combination, causing the contract to release the entire `user-coll-balance` for that asset while only paying for (repaying debt equal to) the smaller `coll-final-raw` portion.

### Impact Explanation
This lets a liquidator receive collateral beyond what is economically justified by the debt they repaid, for the differential window that rounds to zero — a extraction of value from the borrower (and the protocol's collateral backing) without commensurate repayment. Depending on the price/decimals/penalty parameters of a given collateral asset, the "dust window" that can be swept in a single call is bounded by the granularity of the successive `mul-div-down`/`div-bps-down` roundings (`v0-4-market.clar:1479-1485`), so magnitude varies per asset; regardless of size, it is an unconditional bypass of the intended proportional cap and constitutes theft of collateral belonging to the borrower/protocol in a single transaction. This falls under the in-scope Critical impact class: direct theft of user funds at rest.

### Likelihood Explanation
The trigger requires only that a permissionless liquidator (any `contract-caller` satisfying `is-eq contract-caller tx-sender`) picks a `debt-amount` that lands `coll-remaining`'s derived USD/scaled-debt value in the zero-rounding band for the target collateral asset — no privileged access, no multi-block timing, and no interaction with other users is required, satisfying the single-transaction-analog constraint. The liquidator fully controls `debt-amount`, `min-collateral-expected`, and the choice of `collateral-ft`/`debt-ft`, giving them the freedom to search for a value that produces `remaining-debt-to-repay = u0` off-chain before submitting the transaction.

### Recommendation
Do not use "rounds to zero" as a proxy for "no residual collateral to protect." Instead:
- Add an explicit minimum-value floor check (e.g., require `coll-remaining`'s raw token amount, not just its rounded scaled-debt derivative, to be below a defined dust threshold before sweeping it into `coll-final`), or
- Compute `remaining-debt-to-repay` with `mul-div-down` at every step consistently and only sweep the full balance when `coll-remaining` itself (in raw units) is provably below a fixed, asset-independent dust bound — not merely when a chained division happens to floor to zero.

### Proof of Concept
1. Attacker identifies a collateral asset whose `coll-decimals`/`coll-price` combination makes the chain `normalize(coll-remaining * coll-price, coll-decimals, false)` → `div-bps-down(_, BPS + liq-penalty-max)` → `mul-div-down(_, 10^debt-decimals, debt-price)` → `mul-div-down(_, INDEX-PRECISION, borrow-index)` → `mul-div-up(_, borrow-index, INDEX-PRECISION)` round to `u0` for a `coll-remaining` value that is still meaningfully large in raw token units (`v0-4-market.clar:1479-1485`).
2. Attacker calls `liquidate` on an eligible (unhealthy) `borrower` position, choosing `debt-amount` such that after `scale-debt-for-liquidation` caps `debt-final`/`coll-actual` into `coll-final-raw`, the resulting `coll-remaining = user-coll-balance - coll-final-raw` falls in that rounding-to-zero window (`v0-4-market.clar:1472-1476`).
3. `remaining-debt-to-repay` evaluates to `u0`, so `coll-final` is set to `user-coll-balance` instead of `coll-final-raw` (`v0-4-market.clar:1486`).
4. The liquidation executes: the attacker repays debt only proportional to `coll-final-raw`'s worth (via `debt-to-repay`, `v0-4-market.clar:1496`) but the `collateral-remove` call at `v0-4-market.clar:1506-1512` transfers the full `coll-final` = `user-coll-balance`, letting the attacker walk away with the unaccounted-for `coll-remaining` collateral for free.

```text
(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))
```
