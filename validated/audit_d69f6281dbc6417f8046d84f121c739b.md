### Title
Signature Malleability Enables Multisig Weight Double-Counting in `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, reachable from any TVM smart contract, deduplicates submitted signatures by tracking both the recovered signer address and the raw signature bytes in `executedSignList`. Because the underlying ECDSA recovery in `ECKey.recoverPubBytesFromSignature` does not enforce a canonical low-`s` (or otherwise reject the `(r, n-s, flipped v)` malleable twin of a signature), an attacker who observes one valid signature from a legitimate co-signer (e.g., in the mempool, exactly as described in the referenced report) can derive a second, byte-distinct signature that recovers to the *same* address, and submit both in a single call, causing that signer's weight to be counted twice toward the permission threshold.

### Finding Description
`ValidateMultiSign.execute()` loops over each supplied signature, recovers its signer address via `recoverAddrBySign`, and only skips weight accumulation when the exact byte-identical signature was seen before for that address: [1](#0-0) 

If the recovered address was already seen but the exact signature bytes differ (i.e., a malleable variant), the loop does *not* `continue` — it falls through, computes `weight` again, and adds it to `totalWeight`, effectively double-counting a single signer.

The root cause is that `ECKey.recoverPubBytesFromSignature` (used transitively by `recoverAddrBySign`) only checks that `r` and `s` are non-negative, with no canonical-form (low-`s`) enforcement: [2](#0-1) 

Given any valid ECDSA signature `(r, s, v)`, the pair `(r, n-s, v')` (where `v'` flips the recovery parity) is also a mathematically valid signature that recovers to the identical public key/address — this can be computed by anyone without the private key, matching the exact bug class from the external report (malleable signature bypassing "signature already used" replay protection keyed on raw signature bytes rather than a nonce/message digest).

### Impact Explanation
This precompile is used by TVM contracts to implement on-chain multisig/permission checks (`tron.validatemultisign` at address `0x...16`, called from Solidity). An attacker who has observed one valid signature from a legitimate signer (broadcast, logged, or otherwise leaked) can craft its malleable twin and submit both signatures in a single `ValidateMultiSign` call, inflating `totalWeight` and satisfying a multisig `permission.getThreshold()` using fewer genuine independent signers than required. This is a concrete authorization/accounting bypass for any contract relying on this precompile to gate privileged actions (e.g., withdrawal approval, admin actions) with an M-of-N key scheme.

### Likelihood Explanation
Likelihood is moderate: the attacker needs access to at least one valid signature already produced by a legitimate co-signer for the exact same permission/address/hash tuple (visible on submission or in application logs/mempool-like channels), and needs to compute the malleable twin (trivial arithmetic, no private key required). No special privilege is needed to call the precompile itself since it is callable from any TVM contract.

### Recommendation
Enforce canonical low-`s` signatures in `ECKey.recoverPubBytesFromSignature`/`ECDSASignature` validation (reject `s > CURVE.getN().shiftRight(1)`), matching common EIP-2 style canonicalization, and/or change `ValidateMultiSign`'s deduplication key to rely solely on the recovered address (as `TransactionCapsule.checkWeight` already does via `addMap.containsKey(base64Address)`), never allowing more than one weight contribution per unique recovered address regardless of the exact signature bytes presented. [3](#0-2) 

### Proof of Concept
1. Signer `A` produces a valid signature `sigA = (r, s, v)` over `hash` for permission `p` on account `addr`.
2. Attacker observes `sigA` (e.g., from a first submission attempt or shared channel).
3. Attacker computes `sigA' = (r, n - s, v ⊕ 1)`, a distinct byte sequence that still recovers to signer `A`'s address for `hash` (standard secp256k1 malleability, requires no private key).
4. Attacker calls the TVM contract's `validatemultisign(addr, permissionId, data, [sigA, sigA'])`.
5. In `ValidateMultiSign.execute()`, iteration 1 for `sigA` adds `A`'s weight; iteration 2 for `sigA'` recovers the same `recoveredAddr` but a different `sign` byte array, so the `continue` is skipped and `A`'s weight is added a second time, potentially crossing `permission.getThreshold()` with only one real signer's cooperation instead of the intended multiple. [4](#0-3) 

**Note on verification limits**: I was unable to inspect the full body of `recoverAddrBySign` and `ECDSASignature.validateComponents()` within the available tool budget to confirm with certainty that no canonical-`s` check exists anywhere in that call path (grep only returned file locations, not the surrounding logic). The conclusion above is based on the `recoverPubBytesFromSignature` code I did retrieve, which shows no such check at that layer. A Devin session with full file access would be needed to fully confirm/rule out a canonicalization check elsewhere in `validateComponents()`.
