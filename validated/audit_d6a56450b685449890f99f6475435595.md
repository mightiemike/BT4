### Title
`PoisonMicroblock` accepted for any two same-key, different-sequence microblock headers, allowing reward theft from honest miners - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` never checks that `mblock_header_1.sequence == mblock_header_2.sequence`; `check_microblock_header_signer` only verifies that both headers recover to the same public-key hash. Since every microblock in a normal, honest miner's stream is a distinct header signed by the same key, an attacker can take any two ordinary (non-conflicting) microblocks that a miner legitimately produced and submit them as a `PoisonMicroblock` transaction to have that miner's block slashed.

### Finding Description
The claimed invariant is: reward forfeiture should occur only when a report proves a *genuine equivocation* — two headers at the **same** sequence number with different content, signed by the same key (i.e. the miner forked its own stream). The code never enforces this equality.

- `check_microblock_header_signer` (lines 686-713) recovers `pkh1` from `mblock_header_1` and `pkh2` from `mblock_header_2` and only asserts `pkh1 == pkh2`: [1](#0-0) 

- `handle_poison_microblock` calls this signer check, then only validates that the pubkey hash was seen before and hasn't matured out (`MINER_REWARD_MATURITY` window): [2](#0-1) 

- It then unconditionally records a poison report keyed only on `mblock_header_1.sequence`, with no comparison against `mblock_header_2.sequence` anywhere in the function: [3](#0-2) 

Nowhere in this call path — `handle_poison_microblock` → `check_microblock_header_signer` → `insert_microblock_poison` — is there an assertion `mblock_header_1.sequence == mblock_header_2.sequence`, nor a check that the two headers actually conflict (same parent slot, different hash). Since a normal microblock stream from an honest miner consists of many distinct headers all signed by the same private key at increasing sequence numbers, any two such headers satisfy the only check performed (`pkh1 == pkh2`) despite representing zero fork/equivocation.

### Impact Explanation
An attacker who observes any two microblocks broadcast by an honest, actively-mining node (entirely public data, no privileged access needed) can package them as `PoisonMicroblock(h1, h2)` and get it accepted, causing that miner's public key hash to be marked poisoned and its coinbase reward diverted/forfeited to the reporting attacker. This is block-reward theft/mis-payment triggered by a non-privileged, unilateral actor against an innocent, fully honest miner — falling under the "block-reward theft/double-payment/loss" impact category. It is trivially repeatable against every active miner as long as their key/height is within the maturity window.

### Likelihood Explanation
No special preconditions are needed beyond normal, expected miner behavior (producing more than one microblock in a tenure, which is standard). The attacker needs no stake, no signer role, and no privileged access — merely the ability to read the miner's already-published microblocks and submit an ordinary transaction. This makes the attack highly feasible and repeatable at essentially zero cost.

### Recommendation
Add an explicit equivocation check in `handle_poison_microblock` (or in `check_microblock_header_signer`) requiring `mblock_header_1.sequence == mblock_header_2.sequence` and that the header hashes/signatures differ, before treating the pair as proof of a fork. Reject the transaction with `Error::InvalidStacksTransaction` if the sequence numbers differ, since that is not equivocation.

### Proof of Concept
Rust integration test plan (chainstate test harness, e.g. under `stackslib/src/chainstate/stacks/db/transactions.rs` test module or a full node integration test):
1. Set up a miner with a valid microblock private key; have it legitimately produce a 2-microblock stream: `mblock_seq0` (sequence 0) and `mblock_seq1` (sequence 1), both valid, non-conflicting, extending each other properly, and commit them to chainstate so `get_microblock_pubkey_hash_height` returns `Some(height)`.
2. Construct a `TransactionPayload::PoisonMicroblock(mblock_seq0.header, mblock_seq1.header)` transaction from an unrelated attacker principal and submit it via `StacksChainState::process_transaction_payload` / mempool acceptance path.
3. Assert on both sides of the equality:
   - **Before fix (bug)**: assert the transaction is `Ok(...)` and a `Value::Tuple` is returned with `sequence == 0`, and that `get_microblock_poison_report(height)` now returns `Some((attacker, 0))` — i.e., the honest miner's coinbase at `mblock_pubk_height` is now marked forfeited despite `mblock_seq0.sequence (0) != mblock_seq1.sequence (1)`.
   - **After fix (expected)**: assert the transaction is rejected with `Error::InvalidStacksTransaction` due to sequence mismatch, and no poison report is inserted.
