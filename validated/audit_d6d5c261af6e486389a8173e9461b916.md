## Finding: replay/verify integrity check silently ignores the state-checkpoint root, letting a state-root divergence pass as "verified"

### Title
Replay-verification (`ensure_match_transaction_info`) never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so a diverging state root is accepted as a valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
The Sushi report's core lesson is: a "success" check that omits a critical piece of authenticated state lets a caller believe an operation succeeded/matched when it actually did not. The Aptos-native analog is in `TransactionOutput::ensure_match_transaction_info`, the function used by the chunk executor's replay-verification path (and by `db-tool replay-verify`/`replay_on_archive`) to decide whether a freshly-executed transaction output matches a previously committed, quorum-signed `TransactionInfo`. This function checks status, gas, write-set hash and event root, but never checks the state-checkpoint hash fields that are actually part of the signed `TransactionInfo` and feed the ledger accumulator.

### Finding Description
`ensure_match_transaction_info` is the authoritative "did local execution reproduce the canonical, signed result" check: [1](#0-0) 

It validates `status`, `gas_used`, `write_set` hash (`state_change_hash`) and the event root, then returns `Ok(())` — it never compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against anything derived from the locally computed state. The code itself documents this gap: [2](#0-1) 

This function is the sole per-transaction consistency check in `ChunkExecutorInner::verify_execution`, which re-executes historical transactions with the VM and compares the fresh output against the recorded, backup-sourced `TransactionInfo`/write set/events before allowing the chunk to be applied and committed: [3](#0-2) 

The same primitive is used by `db-tool`'s archive replay/verify tooling, which is explicitly the operational safety net used to detect state-divergence bugs (e.g. before a software/feature upgrade) by replaying historical chain data and confirming the new binary reproduces the same committed state: [4](#0-3) 

Because the resulting Merkle state root (`state_checkpoint_hash`) is never part of the comparison, a bug that changes only how the state Merkle/JMT root is derived — while still producing an identical write-set — will be reported as "match" / "OK" by this tool, even though the two nodes would produce different signed `LedgerInfo` roots. This gap is now concretely exploitable by the newly-added trading-native/hot-state checkpoint fields, which are gated exactly by feature flags wired into `BlockExecutorConfigFromOnchain`: [5](#0-4) 

and by `TRANSACTION_INFO_V1`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`, which are permanent, activatable on-chain feature flags: [6](#0-5) 

These roots are assembled into the real, consensus-committed `TransactionInfo` in `assemble_transaction_infos`: [7](#0-6) 

So the fields do exist, are consensus-committed, and are hashed into the ledger accumulator — but the one function whose job is to confirm "local re-execution reproduces the authenticated ledger state" never checks them.

### Impact Explanation
This is a hard-fork/consensus-divergence detection gap: a validator or full-node operator running `replay-verify`/`replay_on_archive` (or `TransactionReplayer::verify_execution` during backup/state-sync replay) to validate a new software build before deployment will get a **false "replay OK"** even when the new build computes a different global state Merkle root (e.g., due to a bug in trading-native/hot-state checkpoint computation). If that build is then rolled out fleet-wide, validators would produce diverging `state_checkpoint_hash`/ledger roots and fail to reach consensus (chain halt) or, in a partial-rollout scenario, split into incompatible forks — exactly the class of impact called out as in-scope ("Hard-fork-only divergence during commit, replay, restore, or proof verification"; "Wrong ... state proof accepted as valid").

### Likelihood Explanation
Likelihood is tied to a real, permanent, already-wired-up on-chain feature path (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO`), not a hypothetical. The gap is triggered automatically any time replay-verify tooling is used against a build with a state-root computation bug for the checkpoint fields — no attacker action is required; this is a latent verification blind-spot that will silently under-report a real correctness defect once one exists, which is precisely the moment it is most needed.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally-derivable checkpoint hashes (`state_checkpoint_hash`, and where applicable `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against the expected `TransactionInfo`, rather than only the write-set/event/gas/status fields, before returning `Ok(())`. Until fixed, `db-tool`'s replay-verify output should not be treated as proof that `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`-derived state roots are correct.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` + `HOTNESS_IN_EPILOGUE` + `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on a test chain and record backup data (transactions, `TransactionInfo`s, write sets) as usual.
2. Introduce a change to the native-position/hot-state checkpoint hash derivation (e.g. altering `do_ledger_update.rs`'s `maybe_position_state_checkpoint_hash`/`maybe_hot_state_checkpoint_hash` computation) so it produces a different root while leaving the resource write set, events, gas and status identical.
3. Run `db-tool replay-on-archive verify` (or `ChunkExecutor::verify_execution` via backup replay) against the original backup with the modified binary.
4. Observe: `ensure_match_transaction_info` returns `Ok(())` because it never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, and the tool reports a successful, matching replay — despite the local build computing a different, consensus-breaking state root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
