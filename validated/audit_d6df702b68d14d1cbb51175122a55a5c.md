### Title
No sanity check on bancor-formula exchange result before applying it to TRC10/TRX pool reserves - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
Anyone can call `wallet/exchangetransaction` (broadcast an `ExchangeTransactionContract`), which is executed unprivileged by `ExchangeTransactionActuator`. The swap amount is computed by `ExchangeCapsule.transaction()`, which by default delegates to `ExchangeProcessor`, a double/`Math.pow`-based bancor-curve implementation. Unless the `AllowHardenExchangeCalculation` proposal has been activated (governance-gated, off by default), the resulting `buyTokenQuant` is applied to update pool reserves with plain `long` arithmetic and no invariant check that the computed amount does not exceed the actual reserve. This is structurally identical to the ibBTC `pricePerShare` bug: a computed rate/quantity (analogous to `pricePerShare`) is trusted and used directly to move funds out of a shared pool, with no sanity check that the value is internally consistent or bounded, and no check that it can never let a caller extract more than the pool holds.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`: [1](#0-0) 

Inside `ExchangeCapsule.transaction()`, when `hardenedCalc` is `false` (the default, since `allowHarden()` reflects a chain parameter that must be explicitly enabled via governance proposal), the non-hardened `ExchangeProcessor` is used, and the new reserve balances are computed with plain `long` addition/subtraction — no bound check that `buyTokenQuant <= buyTokenBalance`, and no check that the resulting balances are internally consistent: [2](#0-1) 

`ExchangeProcessor.exchange()` computes the trade amount purely with `double` arithmetic and `Math.pow`, which is inherently lossy for extreme reserve ratios or repeated small trades: [3](#0-2) 

By contrast, the project's own `SafeExchangeProcessor` (used only when `hardenedCalc == true`) demonstrates that this exact class of bug is real and was mitigated: it uses `BigDecimal`, checked (`Exact`) arithmetic, and rejects the trade with `ArithmeticException` if the resulting balances would go negative: [4](#0-3) [5](#0-4) 

`AbstractExchangeActuator.allowHarden()` shows this hardened, checked path is opt-in and gated by a dynamic property that must be turned on via chain governance — it is not the default behavior: [6](#0-5) 

The only user-facing protection in `ExchangeTransactionActuator.doValidate()` is a caller-supplied `expected` (slippage) minimum, which protects the *trader* from receiving too little — it does not protect the *pool* from paying out more than its true reserve when the underlying floating-point computation is imprecise: [7](#0-6) 

This mirrors the reported bug class precisely: a rate/quantity value (`pricePerShare` in the report, `buyTokenQuant` here) that is trusted implicitly, with no invariant enforcement (e.g. "computed value must never let output exceed reserve," analogous to "pricePerShare must never decrease"), before being used to move funds out of a pooled reserve that other unrelated users depend on.

### Impact Explanation
If the non-hardened bancor computation ever produces a `buyTokenQuant` value that is larger than what the true (rational/BigDecimal) bancor curve would yield — due to accumulated floating-point error in repeated trades, extreme reserve ratios, or an adversarially chosen sequence of trades that maximizes rounding drift — `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` silently proceeds without any exactness check in the non-hardened path (`hardenedCalc == false`), unlike the hardened path which throws on negative balances. This can degrade or drain one side of an `Exchange`/AMM pool (TRX or TRC10 asset), harming the exchange creator and any other traders relying on that pool's reserves, i.e., accounting corruption / asset drainage via an unprivileged, permissionless broadcast transaction (`ExchangeTransactionContract`).

### Likelihood Explanation
Likelihood is moderate, not certain: the non-hardened path is the *default* on any network/chain that has not activated the `AllowHardenExchangeCalculation` proposal, so the vulnerable code path is broadly reachable by any account issuing `wallet/exchangetransaction` calls without any privilege. However, actually engineering a sequence of trades that produces a favorable-enough floating-point drift to meaningfully drain a pool (rather than losing a few units to rounding against the attacker) requires careful analysis of `Math.pow`/double behavior across specific reserve magnitudes, and the project's own test suite (`ExchangeProcessorTest`) already documents measurable divergence between `ExchangeProcessor` (double) and `SafeExchangeProcessor`/strict-math results for the same inputs, evidencing that the discrepancy is real and non-trivial, but I could not verify from the available code whether the drift is exploitable at scale on any concrete deployed pool without a live/mainnet reserve-size analysis.

### Recommendation
- Make the hardened, invariant-checked exchange calculation (`SafeExchangeProcessor`, exact-arithmetic reserve updates) the default and unconditional path for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, rather than an opt-in governance parameter.
- Regardless of which processor is used, add an explicit invariant check after every trade: the computed `buyTokenQuant` must never exceed the current opposite-side reserve, and resulting balances must never go negative; reject the transaction with `ContractValidateException`/`ContractExeException` otherwise, mirroring the check already present in the hardened path (`ExchangeCapsule.java` lines 160-162) but applied unconditionally.
- Consider replacing/removing the `double`/`Math.pow`-based `ExchangeProcessor` entirely once the hardened path has been exercised in production, since its existence keeps a known-imprecise code path live for chains/pools that have not enabled the proposal.

### Proof of Concept
Not independently reproduced against a live pool (would require a numerical search for reserve/quant combinations that make `ExchangeProcessor.exchange()` diverge unfavorably from the exact bancor result at scale). The codebase itself demonstrates the divergence class: `ExchangeProcessorTest.testStrictMath` shows the non-strict and strict/hardened processors returning different results for identical inputs, and `ExchangeTransactionActuatorTest.hardenedExecuteOverflowThrowsArithmeticException` shows that once a pool balance is corrupted, the non-hardened path lacks the overflow/negative-balance guard that the hardened path enforces: [8](#0-7) [9](#0-8)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
