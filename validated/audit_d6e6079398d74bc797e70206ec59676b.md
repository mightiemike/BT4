### Title
Transaction-triggered node halt via `RuntimeError::UnexpectedIntegerOverflow` panic in chunk apply - ([File: chain/chain/src/runtime/mod.rs])

### Summary
`nearcore`'s runtime intentionally uses checked arithmetic (`checked_add`/`checked_sub`) throughout balance accounting to avoid the classic "unchecked overflow leads to corrupted balances" bug described in the report. However, instead of gracefully rejecting the offending transaction/receipt, several of these checks are wired to a hard `panic!` at the `apply()` call site, turning any reachable arithmetic overflow into a deterministic node crash (chunk-apply halt) rather than a contained error.

### Finding Description
The chunk-apply entrypoint converts the runtime's `RuntimeError::UnexpectedIntegerOverflow` variant directly into a Rust panic: [1](#0-0) 

This is analogous to the reported "Token Overflow → system halt" issue: instead of `safeMath` reverting a single malicious call, the runtime's checked-arithmetic protections revert a receipt/transaction locally but the *caller* (`apply()`'s error-mapping code) escalates any `UnexpectedIntegerOverflow` into a `panic!`, which aborts chunk production/validation for the whole node. `RuntimeError::UnexpectedIntegerOverflow` is produced from ordinary balance bookkeeping paths in `runtime/runtime/src/lib.rs` (e.g. staking/locked-balance updates in `update_validator_accounts`, gas-reward and burnt-amount accumulation), and from other checked-arithmetic call sites (`runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/deterministic_account_id.rs`) that return `StorageError::StorageInconsistentState`/`RuntimeError` on overflow rather than failing the specific action only.

The `TODO(#2152): process gracefully` comment directly above the panic confirms this is a known, unresolved gap: the intended fix (processing overflow gracefully) has not been implemented, and the current behavior is to crash the node process on any code path that surfaces `UnexpectedIntegerOverflow`.

### Impact Explanation
If any reachable combination of account balances/deposits/locked stake pushed through the checked-arithmetic accounting can reach a `u128` overflow (e.g., an account whose `amount()` + incoming `deposit`/`reward`/`return_stake` exceeds `u128::MAX`, or a staking/reward accumulation edge case in `update_validator_accounts`), the resulting `RuntimeError::UnexpectedIntegerOverflow` bubbles up to `apply()` and panics the calling thread. In a chunk-producing or validating node this manifests as a crash while applying a chunk built from a single (or a few) attacker-crafted transactions/receipts — a transaction-triggered halt matching the report's "system halt" impact category, without requiring any privileged/validator/network-level access; a normal signer or RPC-submitted transaction that leads to such a balance state is sufficient to reach this code.

### Likelihood Explanation
Reaching an actual `u128` overflow of NEAR balances (max supply is far below `u128::MAX`) requires an extreme, unrealistic accumulation of value in practice, and every reachable checked-arithmetic site in production code paths for `Transfer`/`FunctionCall`/deposit handling already fails per-action with a normal error rather than escalating to `UnexpectedIntegerOverflow` (see `action_transfer` returning `StorageError::StorageInconsistentState` handled per-receipt, not via the `UnexpectedIntegerOverflow` variant). The panic path is reachable only for specific bookkeeping computations (e.g., `update_validator_accounts`'s stake/reward math) whose triggering conditions are guarded by other protocol invariants (max stake, minted-reward bounds). I could not fully verify, with the tools available, a concrete unprivileged transaction sequence that drives one of these specific `checked_add`/`checked_sub` calls past `u128::MAX` or below zero without first tripping an earlier balance-sufficiency check — this bounds the confidence of the finding to a design-level "unhandled error escalates to panic" issue rather than a demonstrated exploit with a specific transaction payload.

### Recommendation
Per the `TODO(#2152)` already in the code, `RuntimeError::UnexpectedIntegerOverflow` should be converted into a normal chunk-apply failure (or per-receipt/per-transaction rejection) instead of `panic!`ing the process in `chain/chain/src/runtime/mod.rs`. At minimum, add defensive validation earlier in the transaction/receipt pipeline (verifier/cost calculation) to reject any transaction whose resulting balance arithmetic could overflow `u128`, so genuinely malformed or adversarial value combinations are rejected during validation rather than during chunk apply where a panic is currently the only fallback.

### Proof of Concept
Not independently reproduced. The analysis is based on tracing the `RuntimeError::UnexpectedIntegerOverflow` error variant from its production sites in [2](#0-1)  through to the panic in [3](#0-2) .
