### Title
Non-atomic read-modify-write of the per-shop session index enables lost updates in `KVSessionStorage`/`RedisSessionStorage`, causing stale access tokens to survive shop uninstall cleanup - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`, `packages/apps/session-storage/shopify-app-session-storage-redis/src/redis.ts`)

### Summary
`KVSessionStorage` and `RedisSessionStorage` maintain a secondary "shop → session ids" index that is updated with an unsynchronized read-then-write sequence, mirroring the reported `YuzuILP.updatePool()` non-atomic state update pattern. Concurrent calls to `storeSession`/`deleteSession` for the same shop race on this index, causing lost updates. Because the index (not the session record itself) drives shop-wide cleanup logic such as `AppInstallations.delete()` used on app uninstall, a lost update can leave a still-valid access-token session un-deleted after the merchant uninstalls the app.

### Finding Description
In `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`, `addShopIds`/`removeShopIds` perform:
```
const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
``` [1](#0-0) 
This is a classic get-then-put race: if two `storeSession` (or one `storeSession` and one `deleteSession`) calls for the same shop overlap, the second `put` overwrites the first's update, silently dropping an entry from the shop index. `RedisSessionStorage.addKeyToShopList`/`removeKeyFromShopList` have the identical pattern. [2](#0-1) 

Such overlapping calls are realistically triggered by the library itself: when `useOnlineTokens` is enabled, the offline OAuth callback immediately kicks off a second, online OAuth flow for the same shop, and multiple staff members can also complete OAuth concurrently for the same shop, each calling `storeSession`. [3](#0-2) 

The shop index feeds `findSessionsByShop`, which `AppInstallations.includes`/`delete` rely on exclusively (they never scan session storage directly) to decide which sessions to purge on `app/uninstalled`: [4](#0-3) 

If a session id is dropped from the index due to the race, `deleteSessions` is never invoked for that id, so the underlying session record (including its `accessToken`) remains fully readable via direct `loadSession(id)` lookups indefinitely after uninstall.

### Impact Explanation
An orphaned session record retains a live Shopify access token after the merchant uninstalls the app. Since the session's own data key is untouched by the index bug, any code path that still resolves that session id (e.g., stale server-side references, cached ids, or JWT-derived session ids for online tokens whose lifetime hasn't lapsed) can continue to authenticate and call the Admin API on behalf of a shop that has revoked the app relationship — a persistence/cross-tenant-trust issue analogous to the "stale poolSize" persisting incorrect state in the original report.

### Likelihood Explanation
Medium: the race requires two concurrent writes to the same shop's index, which the library's own "install offline then immediately begin online OAuth" flow, or ordinary multi-staff concurrent installs, can produce without any attacker action — no privileged access is required, and it is triggered purely by normal (or minimally accelerated) app installation traffic from anonymous/merchant-initiated OAuth requests.

### Recommendation
Replace the read-then-write index maintenance with an atomic primitive: for Redis use `SADD`/`SREM` (Redis sets) instead of get/parse/stringify/set; for the Cloudflare KV-backed storage, either move to a data store that supports atomic list mutation, or accept the KV backend's lack of transactions and instead derive shop membership by scanning/listing session keys with a `shop:` prefix rather than maintaining a separately-updated index that can drift out of sync with the source of truth.

### Proof of Concept
1. Two OAuth completions for the same shop occur close together (e.g., offline session created, and the library immediately begins the online-token flow per `auth-callback.ts`, or a second staff member installs concurrently).
2. Both trigger `storeSession` → `addShopIds`/`addKeyToShopList`, each reading the same pre-update index value.
3. Both writes complete, but the second `put`/`set` overwrites the first, so only one session id ends up recorded in the shop index even though both session records exist in the underlying store.
4. Merchant uninstalls the app; Shopify sends `app/uninstalled`; `AppInstallations.delete(shop)` calls `findSessionsByShop(shop)`, which only returns the id present in the (corrupted) index, and `deleteSessions` is invoked only for that id.
5. The other session — with a still-valid `accessToken` — remains in storage and can still be loaded via `loadSession(id)` after uninstall.

    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

  private async removeKeyFromShopList(shop: string, id: string) {
    const shopKey = shop;
    const idKey = this.client.generateFullKey(id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);
      const index = idKeysArray.indexOf(idKey);

      if (index > -1) {
        idKeysArray.splice(index, 1);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    }
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
