Based on my investigation, I found a concrete decompression-bomb pattern analogous to the Pillow DOS report.

### Title
Unbounded gzip decompression of client-supplied Cairo0 program allows memory-exhaustion DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The RPC API's `decompress_program` helper decompresses a base64+gzip-encoded Cairo0 `Program` supplied inside a client's `BroadcastedDeclareV1Transaction` / `DeprecatedContractClass` payload with no bound on the decompressed size or on decompression time, mirroring the Pillow CVE-2019-16865 pattern of unbounded expansion from a small crafted input.

### Finding Description
`decompress_program` reads the full decompressed byte stream into an unbounded `Vec<u8>` via `GzDecoder::read_to_end`, with an explicit `// TODO(dan): add time and size limits.` acknowledging the missing guard: [1](#0-0) 

This function is reachable from the JSON-RPC surface handling client-broadcast Cairo0 declare transactions (used by `estimate_fee`/`simulate_transactions`/trace flows that accept a `BroadcastedDeclareV1Transaction`/`DeprecatedContractClass`), which any unprivileged declarer can submit. A tiny gzip payload (a classic "zip bomb") can expand to a very large size in memory during `read_to_end`, since neither the compressed input size (bounded only by generic HTTP body size limits, not by decompressed size) nor the decompression ratio nor elapsed time is checked before or during decompression.

This differs from the gateway's `StatelessTransactionValidator`, which does enforce explicit size limits on Sierra (Cairo1) declare payloads such as `max_contract_bytecode_size` and `max_contract_class_object_size`: [2](#0-1) 
No equivalent check exists for the legacy Cairo0 program decompression path in the RPC layer.

### Impact Explanation
Repeated or single large decompression bomb requests can exhaust node memory, causing the RPC/execution service to OOM or hang, denying service to legitimate `estimate_fee`/`simulate_transactions` calls and potentially destabilizing the node process. This matches the CWE-770 (uncontrolled resource allocation) class from the reference Pillow advisory.

### Likelihood Explanation
The affected function is invoked directly on attacker-controlled base64/gzip data with no authentication or pre-decompression size checks, and the missing limit is explicitly flagged as a known gap in the code (`TODO(dan)`), making exploitation straightforward for any RPC caller able to submit `estimate_fee`/`simulate_transactions` requests with a Cairo0 declare transaction.

### Recommendation
Enforce a maximum decompressed size (and, if feasible, a decompression time budget) before/while calling `decoder.read_to_end`, e.g., by wrapping the reader with a size-limited reader (`Read::take`) bounded to the configured `max_contract_bytecode_size`/`max_contract_class_object_size`, and reject the request if the limit is exceeded, consistent with the Sierra path's existing size validations.

### Proof of Concept
1. Craft a Cairo0 `Program` whose JSON representation decompresses from a small gzip payload (few KB) to an extremely large output (hundreds of MB to GB) — a standard "zip bomb" construction.
2. Base64-encode the gzip bytes and submit it as the `program` field of a `BroadcastedDeclareV1Transaction`/`DeprecatedContractClass` in an RPC `estimate_fee` or `simulate_transactions` call.
3. `decompress_program` calls `GzDecoder::read_to_end` unboundedly, allocating memory proportional to the decompressed size, exhausting node memory or causing significant CPU/time consumption, with no limit rejecting the request beforehand. [1](#0-0)
