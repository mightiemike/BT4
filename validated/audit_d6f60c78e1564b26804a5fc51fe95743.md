### Title
Unbounded attacker-controlled `UniversalPayload.GasLimit` accepted into `DerivedEVMCall`, no cap enforced at the executor layer - (File: `x/uexecutor/types/universal_payload.go`, `x/uexecutor/keeper/evm.go`)

### Summary

### Finding Description
The external report's bug class is: a numeric field that drives resource consumption (SHA compression `count`) is validated only at a "friendly" call site, but a lower-level entry point accepts the same field with no upper-bound check, letting an attacker pick an arbitrarily large value and exhaust CPU/memory.

The Push Chain analog is `UniversalPayload.GasLimit`. `UniversalPayload.ValidateBasic()` only checks that `gas_limit` parses as a non-negative `uint256` string: [1](#0-0) 
There is no upper bound comparison against any protocol-level gas cap (`MaxTxGasWanted`, EVM block gas limit, etc.) anywhere in `ValidateBasic()` or `Inbound.ValidateForExecution()`: [2](#0-1) 

That unbounded string is later parsed straight into a `*big.Int` and passed as the explicit `gasLimit` argument to `DerivedEVMCall`, which is the fork's primitive for having a Cosmos module or user-derived address issue a "real" EVM transaction with an explicit gas limit: [3](#0-2) 

This call happens as part of `ExecutePayloadV2`, which is invoked both from the gasless `MsgExecutePayload` path and from inbound execution (`ExecuteInboundFundsAndPayload` / `ExecuteInboundGasAndPayload`) once a UV-vote quorum finalizes an inbound: [4](#0-3) [5](#0-4) 

Unlike the risc0 case, the `MsgExecutePayload`/`MsgVoteInbound` flows are gasless, whitelisted messages (`app/txpolicy/gasless.go`), so an unprivileged attacker can submit a `MsgExecutePayload` (any account may submit it — the UEA authenticates via `verificationData`, not the Cosmos signer) or, indirectly, get a payload attached to an inbound, in which the `UniversalPayload.GasLimit` field is fully attacker-controlled ASCII-decimal text with only a "parses as uint256, non-negative" check.

### Impact Explanation
I could not verify within the available index whether the fork's `DerivedEVMCall`/EVM keeper clamps the caller-supplied `gasLimit` against the chain's configured block gas limit or `MaxTxGasWanted` before executing the call. I searched for `MaxGasLimit`, `MAX_GAS`, `BlockGasLimit`, and `MaxTxGasWanted` in the repo and only found references inside `app/ante/ante_evm.go`, `app/ante/handler_options.go`, and `app/app.go` — none of which appear to be wired into the `x/uexecutor` derived-call path (that ante-level cap only applies to ordinary `MsgEthereumTx` transactions going through `NewEVMMonoDecorator`, not to `DerivedEVMCall` invoked internally by a keeper during message handling). If the underlying EVM execution engine (the `pushchain/evm` fork referenced in `DERIVED_TRANSACTIONS.md`) does not itself reject `gasLimit` values above the block gas limit before starting execution, then a caller-supplied `GasLimit` of, e.g., `2^256-1` could cause the EVM interpreter to run for an extremely long time (or attempt to allocate memory proportional to that limit) during processing of a single `MsgExecutePayload`/`MsgVoteInbound` message — synchronously, inside consensus-critical message handling, on every validator that processes that block. Because this executes deterministically on all honest nodes (not a single relayer/RPC node), it would materially slow or halt block production chain-wide — an unprivileged, non-network-level DoS reachable through the default gasless transaction path, matching the "Push Chain Allowed Impact Gate" scope for DoS.

### Likelihood Explanation
Likelihood cannot be conclusively established from the indexed code alone: this finding hinges entirely on whether `pushchain/evm`'s `DerivedEVMCall` implementation enforces its own internal cap on the `gasLimit` argument (analogous to how `sys_sha_buffer` capped `count` before calling `ecall_4`, while the raw `ecall_sha` ecall handler did not). That EVM-fork source is external to this repository and was not found in the index, so I cannot confirm whether the guard exists or not. Given this repository's own validation layer (`UniversalPayload.ValidateBasic`, `Inbound.ValidateForExecution`) performs no bound check, the root-cause pattern from the seed report is reproduced at the Push Chain layer; whether it is actually exploitable depends on an unverified downstream component.

### Recommendation
Add an explicit upper-bound check on `UniversalPayload.GasLimit` in `UniversalPayload.ValidateBasic()` (e.g., reject any value above the chain's configured max block/tx gas, mirroring `MAX_SHA_COMPRESS_BLOCKS` in the seed report), and independently clamp/validate the `gasLimit` parameter inside `CallUEAExecutePayload` / `DerivedEVMCall` before use, so that resource bounds are enforced at the lowest-level entry point rather than relying solely on a "friendly" caller.

### Proof of Concept
Not constructed — requires confirming whether the `pushchain/evm` fork's `DerivedEVMCall` internally caps `gasLimit` before use, which is outside the scope of the indexed repository content. Recommend a Devin session with full repository (and fork submodule) access to trace `DerivedEVMCall`'s implementation and attempt an end-to-end `MsgExecutePayload` with `UniversalPayload.GasLimit` set to a very large uint256 value to confirm resource exhaustion.

// CallUEAExecutePayload executes a universal payload through UEA
func (k Keeper) CallUEAExecutePayload(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	universal_payload *types.UniversalPayload,
	verificationData []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiUniversalPayload, err := types.NewAbiUniversalPayload(universal_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	gasLimit := new(big.Int)
	gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
	if !ok {
		return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		gasLimit,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"executeUniversalTx",
		abiUniversalPayload,
		verificationData,
	)
}

// ExecutePayloadV2 executes a universal payload through a UEA.
// The caller is responsible for resolving and validating ueaAddr before calling this function.
func (k Keeper) ExecutePayloadV2(ctx context.Context, evmFrom common.Address, ueaAddr common.Address, universalPayload *types.UniversalPayload, verificationData string) (*vmtypes.MsgEthereumTxResponse, error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Debug("execute payload v2",
		"uea", ueaAddr.Hex(),
		"from", evmFrom.Hex(),
	)

	// Step 1: Validate payload and verificationData early (fast-fail before EVM work)
	if _, err := types.NewAbiUniversalPayload(universalPayload); err != nil {
		return nil, errors.Wrapf(err, "invalid universal payload")
	}

	verificationDataVal, err := utils.HexToBytes(verificationData)
	if err != nil {
		return nil, errors.Wrapf(err, "invalid verificationData format")
	}

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}
