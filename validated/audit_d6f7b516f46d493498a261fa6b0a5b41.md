### Title
Incomplete account deletion on `SUICIDE`/`CREATE2` redeploy leaves stale storage rows in `StorageRowStore` - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.deleteContract()` removes an account's code, account record, and contract metadata, but never clears the account's key/value rows in `StorageRowStore`. If the address can be reused for a new contract (via `CREATE2` at the same address, which is explicitly supported and tested in this codebase), the new contract inherits the old contract's leftover storage slots, because storage row lookups are keyed by `sha3(address)` (or `sha3(address||trxHash)` for CREATE2), independent of the account's lifecycle in `AccountStore`/`ContractStore`. [1](#0-0) 

### Finding Description
This is the same bug class as the Sherlock M-6 report: a "delete" operation that is expected to fully wipe an account's associated data actually only clears a subset of the state, silently leaving nested/keyed data behind. In `RoleAccessControl.revokeAllRole()`, `delete self.accountRoles[account]` failed to clear an `EnumerableSet` because Solidity's `delete` doesn't recursively clear nested mapping-like structures. Java-tron's analog is `RepositoryImpl.deleteContract()`:

```java
@Override
public void deleteContract(byte[] address) {
  getCodeStore().delete(address);
  getAccountStore().delete(address);
  getContractStore().delete(address);
}
``` [1](#0-0) 

This is invoked from `TransactionTrace.finalization()` for every address in `ProgramResult.getDeleteAccounts()` after a `SUICIDE`/`SELFDESTRUCT`:
```java
for (DataWord contract : transactionContext.getProgramResult().getDeleteAccounts()) {
  deleteContract(contract.toTronAddress());
}
``` [2](#0-1) 

It never touches `StorageRowStore`, the store backing all `SLOAD`/`SSTORE` values for the contract. Storage rows are addressed by `compose(key, addrHash)` where `addrHash = sha3(address)` (or `sha3(address||trxHash)` for CREATE2 addresses):
```java
private byte[] compose(byte[] key, byte[] addrHash) { ... }
private static byte[] addrHash(byte[] address) {
  return Hash.sha3(address);
}
``` [3](#0-2) 

Because `deleteContract()` doesn't purge `StorageRowStore`, old rows for that address remain in the DB. When `createContractImpl()` is later invoked and the target account no longer exists (`existingAccount == null`, e.g. after a prior `SUICIDE`), it treats the address as brand new and does not clear any prior storage:
```java
AccountCapsule existingAccount = getContractState().getAccount(newAddress);
boolean contractAlreadyExists = existingAccount != null;
...
if (existingAccount == null) {
  deposit.createAccount(newAddress, "CreatedByContract", AccountType.Contract);
} else if (!contractAlreadyExists) {
  existingAccount.updateAccountType(AccountType.Contract);
  existingAccount.clearDelegatedResource();
  deposit.updateAccount(newAddress, existingAccount);
}
``` [4](#0-3) 

`Storage.commit()` only ever deletes a row when it is explicitly written to zero during execution (`row.isDirty()` and value is zero); it never proactively wipes all prior rows for an address on account creation/deletion:
```java
public void commit() {
  rowCache.forEach((DataWord rowKey, StorageRowCapsule row) -> {
    if (row.isDirty()) {
      if (new DataWord(row.getValue()).isZero()) {
        this.store.delete(row.getRowKey());
      } else {
        this.store.put(row.getRowKey(), row);
      }
    }
  });
}
``` [5](#0-4) 

Since java-tron's CREATE2 address for a non-Constantinople-era address (i.e., when the legacy `contractVersion == 0` path is used, `addrHash = sha3(address)` only, with no dependence on `trxHash`), a contract redeployed to a previously-destroyed address (whether through `CREATE` collision avoidance logic or `CREATE2`) can read pre-populated, attacker/previous-owner-controlled storage slots that were never wiped, because the "delete" of the old contract silently failed to clear the actual key/value data associated with that address.

### Impact Explanation
If a contract self-destructs and a new contract is deployed to that same address (a pattern explicitly supported and unit-tested via `Create2Test`/`FreezeTest#testCreate2SuicideToBlackHole`), the newly deployed contract may start execution with non-zero storage slots inherited from the destroyed contract instead of the expected zero-initialized storage. This can corrupt state assumptions baked into constructors (e.g., access-control/owner flags, balances, or initialization guards stored at fixed slots), potentially allowing unauthorized state (like a stale "admin"/initialized flag) to persist across contract lifecycles, mirroring the M-6 impact where a revoked privileged role kept operating on the system due to incomplete deletion.

### Likelihood Explanation
Requires a contract using `SELFDESTRUCT`/`SUICIDE` followed by redeployment to the identical address via `CREATE`/`CREATE2` (address collision or intentional resurrection pattern) — both of which are directly reachable by any user submitting ordinary `TriggerSmartContract`/`CreateSmartContract` transactions, with no privileged actor required. The codebase's own test suite (`Create2Test`, `FreezeTest#testCreate2SuicideToBlackHole`) demonstrates this exact self-destruct-then-redeploy-at-same-address scenario is a supported, reachable execution path.

### Recommendation
When `deleteContract()` removes an account (or when a new contract is created at an address with no live account record), explicitly clear all rows in `StorageRowStore` for that address (analogous to iterating and deleting the full range of that account's `addrHash` prefix), rather than relying solely on `AccountStore`/`ContractStore`/`CodeStore` deletion. Alternatively, ensure the storage-row deletion happens deterministically as part of the same commit that processes `ProgramResult.getDeleteAccounts()`.

### Proof of Concept
Conceptual PoC (matches existing test infrastructure in `Create2Test`/`FreezeTest`):
1. Deploy Contract A at address `X` via `CREATE2` with salt `S`; have it write non-zero values to storage slots (e.g., slot 0 = "adminFlag").
2. Call `SUICIDE`/`SELFDESTRUCT` on Contract A, triggering `Program.suicide()` → `ProgramResult.addDeleteAccount()` → `TransactionTrace.finalization()` → `RepositoryImpl.deleteContract(X)`, which removes the account/code/contract records but leaves `StorageRowStore` rows for `X` intact.
3. Redeploy a new Contract B to the same address `X` (same salt `S`, same init code hash, per `CREATE2` rules) whose constructor assumes storage slot 0 starts at zero (e.g., an uninitialized-owner check).
4. Read storage slot 0 for `X` — it will report Contract A's leftover non-zero value instead of Contract B's expected zero-initialized state, since `Storage.getValue()`/`compose()` key on `sha3(address)` unrelated to the account's create/delete lifecycle. [6](#0-5) [7](#0-6)
