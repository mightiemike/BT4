## Title
Unbounded pre-validation memory allocation via crafted borsh length fields in RPC-submitted transactions - (File: `chain/jsonrpc/src/api/transactions.rs`)

### Summary
The JSON-RPC transaction-submission path decodes an attacker-supplied base64 string directly into a `SignedTransaction` via Borsh with no upper bound on the encoded size or on any length field it declares, before any size/limit validation runs. This mirrors the CVE-2018-10958 bug class: a length value taken from untrusted input is used to drive a large memory allocation before the input is otherwise validated, risking an abort/OOM.

### Finding Description
`decode_signed_transaction` in `chain/jsonrpc/src/api/transactions.rs` does: [1](#0-0) 
```
fn decode_signed_transaction(value: String) -> Result<SignedTransaction, RpcParseError> {
    let bytes = near_primitives::serialize::from_base64(&value)...
    SignedTransaction::try_from_slice(&bytes)...
}
```
There is no byte-length cap applied to `bytes` before `try_from_slice` runs. `SignedTransaction`/`Transaction` are plain `#[derive(BorshDeserialize)]` structs whose `actions: Vec<Action>` field, and nested `Action` variants such as `DeployContractAction { code: Vec<u8> }` and `FunctionCallAction { args: Vec<u8> }`, are each length-prefixed with a 4-byte little-endian `u32`. [2](#0-1) 

Borsh's `Vec<u8>` fast-path deserialization allocates a buffer sized to the declared length *before* checking whether that many bytes actually exist in the input, so a tiny base64 payload can encode a header claiming a `Vec<u8>` (or `Vec<Action>`) of up to `u32::MAX` (~4 GiB) elements, forcing a large allocation attempt at decode time.

Only *after* successful deserialization does the code check size limits — `ValidatedTransaction::check_valid_for_config` computes `signed_tx.size_for_limits(...)` and compares against `max_transaction_size`: [3](#0-2) 

This is too late: the oversized allocation has already been attempted by the time this check runs.

By contrast, the peer-to-peer network layer already recognizes and mitigates exactly this bug class for the same `SignedTransaction` type, gating the raw bytes with `MAX_TRANSACTION_SIZE_BYTES` and `try_from_slice_with_limit` before Borsh-decoding: [4](#0-3) [5](#0-4) 

The JSON-RPC `decode_signed_transaction` entry point (reachable by any unauthenticated RPC caller via `broadcast_tx_async`/`broadcast_tx_commit`/`tx` status with an embedded `signed_tx_base64`) has no analogous gate.

### Impact Explanation
An unprivileged RPC caller can submit a small, well-formed base64 blob whose Borsh header declares an enormous `Vec` length for `actions`, `code`, or `args`. Rust's allocator will attempt to reserve that much memory in a single allocation before any subsequent byte is even read, which can abort the process (allocation-failure handler calls `abort()`) or, at smaller-but-still-large sizes, contribute to memory exhaustion when repeated concurrently — a transaction/RPC-triggered denial of service against a validator's or RPC node's process.

### Likelihood Explanation
High: this is reachable via standard, unauthenticated JSON-RPC methods (`broadcast_tx_async`, `broadcast_tx_commit`, `tx`) with a hand-crafted payload requiring no valid signature verification to reach the allocation (the allocation happens during Borsh decode, before signature checks or size limits are consulted).

### Recommendation
Apply the same defense used at the network layer: enforce an upper bound on the raw byte length of the RPC-submitted transaction (e.g., reuse or mirror `max_transaction_size` / `MAX_TRANSACTION_SIZE_BYTES`) before calling `SignedTransaction::try_from_slice`, analogous to `try_from_slice_with_limit`, so oversized encodings are rejected prior to allocation.

### Proof of Concept
Construct a minimal Borsh byte sequence representing a `SignedTransaction` where the `actions` vector (or a nested `DeployContractAction.code` / `FunctionCallAction.args`) declares a `u32` length of `0xFFFFFFFF` followed by no actual backing bytes; base64-encode it and submit via `broadcast_tx_async`/`broadcast_tx_commit`. `decode_signed_transaction` calls `SignedTransaction::try_from_slice` directly on the decoded bytes with no size gate, causing Borsh's `Vec` deserialization to attempt a multi-gigabyte allocation before any subsequent length/signature validation occurs.

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}
