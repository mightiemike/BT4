### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify tooling to accept a divergent state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info()` compares only status, gas used, write-set hash, and event root hash against a `TransactionInfo`, but explicitly and knowingly skips validation of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. This function is the sole correctness check used by `db-tool`'s `replay_on_archive` verifier, so any divergence limited to those checkpoint/state-root fields is silently accepted as a "passed" replay.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks four properties (status, gas, write-set hash, event root hash) but returns `Ok(())` without checking the state checkpoint hashes, with an explicit TODO acknowledging the gap: [2](#0-1) 

This function is invoked as the authoritative pass/fail gate in the `replay_on_archive` verifier used to validate that re-executed transactions match the historical, backed-up (and presumably consensus-committed) `TransactionInfo`: [3](#0-2) 

The `TransactionInfoV1` variant carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields, which are populated from the state-checkpoint/Merkle computations in `DoStateCheckpoint`/`DoLedgerUpdate`: [4](#0-3) [5](#0-4) 

Because these hashes bind the transaction info to the actual post-execution ledger/state Merkle roots (including the new "native position"/trading-native state tree gated by `compute_trading_native_state_roots`), a `replay_on_archive` run can report success even when the locally re-computed state root(s) diverge from the historical/authenticated root, as long as the write-set and event hashes still match.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... accepted as valid" and "authenticated API or state-view output bound to the wrong version, object, or proof context" invariants for the *verification tooling path*: an operator relying on `replay_on_archive` (or any other future caller of `ensure_match_transaction_info`) to certify that a backup/replay reproduces the authenticated ledger state can be given a false "OK" even though the state-checkpoint (and, once `compute_trading_native_state_roots` is enabled, the native-position state root) diverges. This is exactly the class of bug the FSD report illustrates: a check that appears to validate integrity of a value silently omits validating the actual field that matters, corrupting the trust guarantee of the verification step.

However, the impact is bounded by the fact that the on-chain commit path itself (accumulator/`TransactionInfo` hashing in `do_ledger_update.rs`, storage write in `aptosdb_writer.rs`, and proof verification in `types/src/proof/*`) is unaffected — the corrupted commitment never enters consensus or the accumulator; only the *verification/replay* utility is fooled. The code comment itself states this omission is deliberate pending `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which per `with_features` requires `transaction_info_v1` and `hotness_in_epilogue` features, i.e., this is tied to an in-development/experimental "trading-native"/position state feature not yet broadly active on mainnet: [6](#0-5) 

### Likelihood Explanation
Low-to-moderate today (feature-gated, and `replay_on_archive` is an offline verification tool, not a consensus/commit path), but the underlying gap is real and self-acknowledged in the code, and once `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` are enabled, replay-verify would silently miss divergences without further changes.

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against locally recomputed values before returning `Ok(())`, exactly as the existing TODO instructs, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` more broadly.

### Proof of Concept
Not independently exploitable as a mainnet consensus/commit-corruption bug at this time — it only affects the `replay_on_archive` debugging/verification tool, and the affected fields are only populated when experimental features (`transaction_info_v1` + `hotness_in_epilogue` + `compute_trading_native_state_roots`) are active. Concretely: run `db-tool replay-on-archive` against a backup where a transaction's write-set/events match but the `position_state_checkpoint_hash` (native-position Merkle root) in the historical `TransactionInfo` differs from what local re-execution would produce — `ensure_match_transaction_info` returns `Ok(())` and the tool reports the transaction as successfully verified, per [7](#0-6) .

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
```
