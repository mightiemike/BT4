### Title
Unbounded Memory Allocation via Attacker-Controlled Array Size in Deprecated Syscall Argument Parsing - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The bRPC CVE root cause is "memory for arrays or strings of corresponding sizes is allocated based on integers read from the network" without an upper bound, causing bad_alloc/DoS. The Starknet sequencer's deprecated (Cairo 0) syscall argument reader has the same pattern: it reads a size felt supplied by a contract, converts it to `usize`, and immediately uses it to pull a range of felts out of VM memory with no maximum-size check.

### Finding Description
`read_felt_array` in [1](#0-0)  reads `array_size` directly from Cairo VM memory (a felt fully controlled by the executing contract's code/calldata), converts it via `usize::try_from(array_size.to_biguint())?`, and passes it straight into `felt_range_from_ptr(vm, array_data_start_ptr, size)` with no maximum bound check performed before the conversion or the range read. This function is the parser used by `read_calldata` / `read_call_params`, which are invoked for every deprecated syscall that takes a calldata array (e.g. `call_contract`, `library_call`) as seen in [2](#0-1) . The Cairo 1 counterpart (`crates/blockifier/src/execution/syscalls/hint_processor.rs:860-879`) computes size as `array_data_end_ptr - array_data_start_ptr`, which is likewise attacker/contract chosen since both pointers are values the contract wrote to its own memory segment before invoking the syscall.

This is directly analogous to the bRPC Redis parser bug: an integer read from an untrusted source (there, the network; here, contract-controlled VM memory reachable from any transaction that deploys or invokes a Cairo 0 contract) is used to size a subsequent memory read/allocation without validation against a sane maximum, before any gas/fee accounting for that size is charged (gas cost for calldata length, e.g. via `get_linear_factor_length`, is computed only after the array has already been fully read out of memory).

### Impact Explanation
A malicious contract deployer/caller can supply an oversized `calldata_size`/array-size value to a deprecated syscall (`call_contract`, `library_call`, etc.) executed via any submitted Invoke/Declare/DeployAccount transaction. If the resulting range read attempts to materialize a very large `Vec<Felt>` (or trigger a large scan/copy across VM memory) before the corresponding gas cost is deducted, this can exhaust sequencer memory or CPU per single transaction, potentially crashing or stalling the node processing that transaction — a network-availability impact ("a network unable to confirm new transactions") consistent with the bRPC CVE class.

### Likelihood Explanation
Reachable trivially by any unprivileged party: declare and invoke a Cairo 0 contract that calls a syscall with a crafted large size argument (or crafted mismatched start/end array pointers for the Cairo 1 path). No special privileges beyond normal transaction submission are required.

### Recommendation
Add an explicit maximum bound check on `array_size` (and on `array_data_end_ptr - array_data_start_ptr` for the Cairo 1 path) in `read_felt_array` before performing the range read/allocation, rejecting the syscall with a `PreExecutionError`/`SyscallExecutorBaseError` if the requested size exceeds a sane protocol-defined limit (mirroring the `redis_max_allocation_size`-style fix upstream), and ensure gas/resource accounting for the array length is charged prior to (or bounded ahead of) the allocation.

### Proof of Concept
Not independently executed; conceptual PoC based on code reading: deploy a Cairo 0 contract whose entry point invokes `call_contract`/`library_call` with `calldata_size` set to a large felt value (e.g. close to `usize::MAX` after conversion) and a `calldata` pointer to a small/arbitrary memory segment, then submit an Invoke transaction that triggers this entry point; `read_felt_array` will attempt `felt_range_from_ptr` over that size before charging gas for it.

**Note on verification limits**: I was unable to retrieve the exact body of `felt_range_from_ptr` (in `crates/blockifier/src/execution/execution_utils.rs`) within the available tool budget to confirm precisely how it allocates/copies memory for the requested range (e.g., whether it uses `Vec::with_capacity(size)` directly). The finding above is based on the confirmed call chain and size derivation shown in the cited code, but full confirmation of the exact allocation mechanics inside `felt_range_from_ptr` would benefit from a follow-up session with direct file access.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
