### Title
`liquidity_cap` field on `TokenConfig` is declared but never enforced during PRC20 minting - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`x/uregistry`'s `TokenConfig.LiquidityCap` is documented as the "max supply cap for this token" [1](#0-0)  and is required to be a non-empty value by `ValidateBasic` [2](#0-1) , giving operators the impression this value is an enforced risk-management ceiling — the same pattern as the Canto `DefaultMaxSwapAmount` limit in the seed report. However, no code path in `x/uexecutor` (the module that actually mints PRC20 tokens on inbound execution) reads or checks this field before minting.

### Finding Description
The inbound execution flow resolves the token config purely to find the `NativeRepresentation.ContractAddress` (the PRC20 contract), never touching `LiquidityCap`: [3](#0-2) 

This `depositPRC20` helper feeds directly into `CallPRC20Deposit`, which issues a `DerivedEVMCall` to `depositPRC20Token` with the raw, validator-observed `amount` and no supply/limit check: [4](#0-3) 

The same absence of a cap check exists in the auto-swap deposit path (`CallPRC20DepositAutoSwap`) used by `ExecuteInboundGas` / `gasAndPayloadDepositAutoSwap`: [5](#0-4) [6](#0-5) 

A repository-wide search confirms `LiquidityCap`/`liquidity_cap` is referenced only in protobuf-generated accessors, `ValidateBasic` tests, and test fixtures — never in any keeper logic that performs minting, deposit, or accounting in `x/uexecutor`. There is no `GetLiquidityCap`, `ExceedsCap`, or `MaxSupply` check anywhere in the deposit/mint call graph.

### Impact Explanation
Because `Inbound.Amount` is attacker-influenced (it is the amount the attacker actually sent/observed on the source chain, which honest Universal Validators faithfully vote on and finalize through the generic ballot machine), an attacker who deposits or triggers an inbound event with an amount exceeding the token's declared `liquidity_cap` will have the full amount minted as PRC20 on Push Chain with no rejection, clamping, or revert. This breaks the accounting invariant the registry design implies: total minted PRC20 supply for a token should never exceed its cap. Unbounded minting relative to the backing/liquidity assumption can be leveraged to drain downstream systems that price or provide liquidity against these PRC20 tokens (e.g., the `UniversalCore` auto-swap/Uniswap-V3 pools referenced in `CallPRC20DepositAutoSwap`/`GetSwapQuote`), producing value that is not backed 1:1, i.e. unauthorized mint of protocol-controlled asset representation — squarely in scope under "unauthorized mint... of user or protocol-controlled funds" and "corruption of PRC20 or native asset accounting."

### Likelihood Explanation
Reachable via the ordinary, unprivileged user deposit path (an external-chain deposit event that honest validators vote on through `MsgVoteInbound`) — no privileged actor, malicious validator, or admin action is required. The only precondition is that a token config with a `liquidity_cap` value exists and the attacker can source (or claims to source, subject to external-chain confirmation) a large enough deposit. Likelihood is bounded by whatever real backing/vault checks exist on the source-chain gateway contract (outside this repo's scope), but within Push Chain's own scoped code there is no secondary defense — the cap is a purely decorative/administrative field.

### Recommendation
Enforce `TokenConfig.LiquidityCap` in the PRC20 deposit path: before calling `CallPRC20Deposit` / `CallPRC20DepositAutoSwap`, query the PRC20's current `totalSupply()` (or track cumulative minted amount in `x/uexecutor` state) and reject/clamp/revert the inbound if `currentSupply + amount > liquidityCap`, routing the excess through the existing revert/refund flow (`RevertInstructions`) rather than silently minting past the declared ceiling.

### Proof of Concept
Conceptually:
1. Admin registers a token with `liquidity_cap = "1000000"` (e.g., 1 USDC at 6 decimals) via `MsgAddTokenConfig`.
2. An external-chain event deposits (or is validator-observed as depositing) `amount = "1000000000000"` (1,000,000x the cap) of that token.
3. Honest Universal Validators vote and finalize the inbound via the standard ballot process (`MsgVoteInbound` → `RecordInboundVote` → ballot `PASSED`).
4. `ExecuteInboundFunds`/`ExecuteInboundGas` calls `depositPRC20` → `CallPRC20Deposit`, which mints the full `amount` of PRC20 to the recipient UEA with no reference to `tokenConfig.LiquidityCap` anywhere in the call chain shown above.
5. Total minted PRC20 supply now vastly exceeds the registry's declared cap, with no on-chain check having fired.

Note: I could not find any off-chain (`universalClient`) pre-filtering of amounts against `liquidity_cap` either — the search across the repo turned up zero non-generated, non-test references to the field outside `uregistry` accessors. If such enforcement exists in code not indexed here, this finding would need to be reassessed; a full-repository review via a Devin session would be needed to conclusively rule that out.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

// gasAndPayloadDepositAutoSwap handles the swap quote + deposit autoswap for GAS_AND_PAYLOAD.
func (k Keeper) gasAndPayloadDepositAutoSwap(
	sdkCtx sdk.Context,
	prc20AddressHex common.Address,
	ueaAddr common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	quoterAddr, err := k.GetUniversalCoreQuoterAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	wpcAddr, err := k.GetUniversalCoreWPCAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	fee, err := k.GetDefaultFeeTierForToken(sdkCtx, prc20AddressHex)
	if err != nil {
		return nil, err
	}

	quote, err := k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)
	if err != nil {
		return nil, err
	}

	// 5% slippage: minPCOut = quote * 95 / 100
	minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
	minPCOut.Div(minPCOut, big.NewInt(100))

	return k.CallPRC20DepositAutoSwap(sdkCtx, prc20AddressHex, ueaAddr, amount, fee, minPCOut)
}
