### Title
Unsanitized `shop` query parameter injected into CSP `frame-ancestors` header enables clickjacking bypass on bounce/exit-iframe pages - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/render-app-bridge.ts`)

### Summary
`renderAppBridge` builds the CSP header via `addDocumentResponseHeaders` using the raw `shop` query parameter taken straight from `request.url` without ever passing it through `api.utils.sanitizeShop`, unlike the equivalent `addDocumentResponseHeadersFactory` path which does sanitize it. Because this raw value is concatenated directly into the `frame-ancestors` CSP directive, an attacker can widen the CSP source list with arbitrary origins by including a space-separated value in `shop`, weakening the anti-clickjacking protection on the app's bounce-page/exit-iframe response.

### Finding Description
`renderAppBridge` reads the shop value directly: [1](#0-0) 

and forwards it unchanged into `addDocumentResponseHeaders`, which interpolates it into the `Content-Security-Policy: frame-ancestors` value: [2](#0-1) 

Contrast this with the sibling factory function in the same file, which explicitly sanitizes shop before use: [3](#0-2) 

`renderAppBridge` is reachable pre-validation on two routes in `authenticateAdmin`: the bounce-page path (`config.auth.patchSessionTokenPath`) and the exit-iframe path (`config.auth.exitIframePath`). Both handlers run *before* `validateShopAndHostParams` is invoked: [4](#0-3) [5](#0-4) 

So an unauthenticated attacker can send `GET <patchSessionTokenPath>?shop=evil.example%20https://attacker.example` to a public app instance. `URLSearchParams.get('shop')` URL-decodes this to `evil.example https://attacker.example`, which is inserted verbatim into the CSP value: `frame-ancestors https://evil.example https://attacker.example https://admin.shopify.com ...`. Because CSP source lists are whitespace-delimited, this adds `attacker.example` as a permitted framing origin for that response, alongside the intended shop domain.

Note: classic CRLF header-splitting is not achievable here because the Fetch-spec-compliant `Headers` implementation used by these runtimes rejects `\r`/`\n`/NUL bytes in header values, so `headers.set()` would throw rather than allow raw CRLF injection. The exploitable primitive is the CSP directive/source-list widening via unsanitized whitespace-separated tokens, not literal header splitting.

### Impact Explanation
This allows an attacker-chosen origin to be added to the `frame-ancestors` allow-list of the bounce/exit-iframe HTML response, undermining the page's clickjacking protection. An attacker can craft a link containing the malicious `shop` value and get a merchant/user to open it; the resulting response can then legitimately be framed by the attacker's page under the injected origin, in addition to (or instead of, if the actual shop token is invalid/omitted) the intended shop. This matches Shopify's "Clickjacking with a demonstrated security impact" bounty impact class, since it degrades a specific defense-in-depth control (frame-ancestors) via unsanitized user input, though the response body itself is limited to bootstrap script/redirect content rather than sensitive account data.

### Likelihood Explanation
Fully unauthenticated and reachable with a single crafted GET request — no secrets, tokens, or prior session state are required, and the bounce/exit-iframe code paths execute before any shop/host validation. The only requirement is that the target app is embedded (`config.isEmbeddedApp`) and reachable at its known bounce/exit-iframe path, both of which are default/standard configuration.

### Recommendation
In `render-app-bridge.ts`, sanitize the shop value the same way `addDocumentResponseHeadersFactory` does before calling `addDocumentResponseHeaders`, e.g. `api.utils.sanitizeShop(new URL(request.url).searchParams.get('shop') ?? '')`, so that non-conforming values are converted to `null` and excluded from the header entirely, consistent with the other call site. The same fix should be verified/applied in the `shopify-app-react-router` package's equivalent `render-app-bridge.ts`.

### Proof of Concept
```ts
// packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/__tests__/render-app-bridge.poc.test.ts
import {renderAppBridge} from '../render-app-bridge';

test('unsanitized shop widens CSP frame-ancestors', async () => {
  const config = {appUrl: 'https://my-app.example', isEmbeddedApp: true, apiKey: 'key'} as any;
  const request = new Request(
    'https://my-app.example/auth/session-token?shop=evil.example%20https://attacker.example',
  );

  let response: Response | undefined;
  try {
    renderAppBridge({config, logger: {debug: () => {}} as any, api: {} as any}, request);
  } catch (thrown) {
    response = thrown as Response;
  }

  const csp = response!.headers.get('Content-Security-Policy');
  // Expected (buggy) behavior: attacker.example is included as an allowed frame-ancestor
  expect(csp).toContain('https://attacker.example');
});
```
Expected result before fix: assertion passes, confirming `attacker.example` is injected into `frame-ancestors`. After applying `sanitizeShop`, the malformed shop value fails validation, `shop` becomes `null`, and no CSP `frame-ancestors` origin is set for the invalid value (falls through to the default deny/none policy for non-embedded, or omits the shop-specific origin).
