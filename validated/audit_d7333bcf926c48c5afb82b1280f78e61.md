### Title
Silent overflow via `BigInteger.longValue()` in vote-reward "Vi" accumulator computation instead of `longValueExact()` - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`, `chainbase/src/main/java/org/tron/core/service/RewardViCalService.java`)

### Summary
Same bug class as the PoolTogether `vaultPortion` issue: an unsafe/unchecked numeric narrowing conversion is used in a reward-accounting computation, where overflow silently produces a wrong value instead of reverting. In java-tron, the "Vi" (accumulated reward-per-vote) reward calculation multiplies an unbounded `BigInteger` delta by a vote count and then converts the result to `long` using `BigInteger.longValue()`, which silently truncates/wraps on overflow rather than throwing, unlike the `longValueExact()`/`SafeCast`-style checked conversions used elsewhere in the same codebase.

### Finding Description
The witness voting reward is accumulated as a `BigInteger` "Vi" value that is scaled by `DECIMAL_OF_VI_REWARD = 10^18` and grows monotonically across cycles without any upper bound check: [1](#0-0) 

When a user withdraws/queries their reward, the delta between two Vi snapshots is multiplied by the user's vote count and divided by `DECIMAL_OF_VI_REWARD`, then converted to `long` with the unchecked `.longValue()`: [2](#0-1) [3](#0-2) [4](#0-3) 

`BigInteger.longValue()` (unlike `.longValueExact()`, which is used correctly elsewhere in the codebase, e.g. `RepositoryImpl.divideCeilExact` and `calculateGlobalLimitV2`) discards all but the low-order 64 bits of the two's-complement representation and never throws — this is exactly the "silent overflow" pattern from the referenced report: the value cast is unsafely truncated, so if the true mathematical result exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, the computed `reward` becomes an arbitrary, unrelated value (potentially negative) instead of failing loudly. [5](#0-4) 

Because `deltaVi` accumulates indefinitely (there is no periodic reset/clamping of the Vi accumulator across the full cycle history), and low-vote-count witnesses divide by a small `voteCount` when accruing `deltaVi` (`reward * 10^18 / voteCount`), the magnitude of `deltaVi` can grow very large over many cycles/blocks for witnesses that receive rewards while having small vote totals: [6](#0-5) 
Multiplying that accumulated `deltaVi` again by `userVote` before dividing by `DECIMAL_OF_VI_REWARD` (line 106-107/225-226/166-167 in the cited files) reduces the safety margin further, since the multiplication happens before the division.

### Impact Explanation
If the accumulated `BigInteger` result overflows a signed 64-bit long during `.longValue()`, the reward paid out to a voter (via `adjustAllowance`) or the reward reported by `queryReward` can become a value bearing no relation to the correct reward — potentially wildly larger, or negative, corrupting account allowances (`AccountCapsule.setAllowance`). This directly corrupts on-chain reward accounting/state that is reachable by any account broadcasting an ordinary vote/freeze/unfreeze transaction, since `withdrawReward`/`computeReward` is invoked from `VoteWitnessProcessor`, `UnfreezeBalanceV2Actuator`/`Processor`, and TVM-triggered vote-related native contracts.

### Likelihood Explanation
Likelihood is lower than the original PoolTogether case because triggering this requires the Vi accumulator (scaled by 10^18) times a vote count to actually exceed `Long.MAX_VALUE` (~9.2×10^18) after the final division by `10^18` — i.e., it requires either an extremely long accumulation history for a low-vote witness, or extremely large reward/vote-count combinations that are somewhat bounded by real TRX supply and typical vote magnitudes seen in the codebase's own tests (values up to the tens of billions). This is a real defect (using `.longValue()` instead of `.longValueExact()` breaks the "fail loudly" invariant the rest of the reward-accounting code otherwise follows), but reaching an actual overflow in practice under realistic TRX supply/vote-count bounds is a longer-tail scenario than the original Solidity `int256`/`uint256` mismatch, which could be triggered with values that fit trivially in `uint256` but not `int256`.

### Recommendation
Replace `.longValue()` with `.longValueExact()` (which throws `ArithmeticException` on overflow, matching the pattern already used in `RepositoryImpl.divideCeilExact`/`calculateGlobalLimitV2` and `RewardViCalService`'s own `divideCeilExact`-style helpers) in:
- `MortgageService.computeReward(long, long, AccountCapsule)`
- `VoteRewardUtil.computeReward`
- `RewardViCalService.getNewRewardAlgorithmReward`

so that an out-of-range reward computation throws and can be handled explicitly (e.g., surfaced as an internal/consensus error) rather than silently truncating to an incorrect reward value.

### Proof of Concept
Conceptual reproduction (cannot be executed from this analysis environment, but the code path is deterministic):
1. Over many maintenance cycles, repeatedly call `DelegationStore.addReward(cycle, srAddress, someReward)` for a witness with a very small `witnessVote` (e.g., 1), causing `accumulateWitnessVi` to add `reward * 10^18 / 1` to the stored Vi each cycle — the stored `BigInteger` Vi grows without bound. [6](#0-5) 
2. Have an account vote for that witness with `userVote` large enough that `deltaVi.multiply(BigInteger.valueOf(userVote))` (before the `/DECIMAL_OF_VI_REWARD` division) exceeds `Long.MAX_VALUE * 10^18` in magnitude.
3. Call `MortgageService.withdrawReward(address)` (or `VoteRewardUtil.withdrawReward`) — the final `.longValue()` call truncates the BigInteger result, producing a wrong (possibly negative) `reward` that is passed into `adjustAllowance`, corrupting the account's `allowance` field. [7](#0-6)

  public BigInteger getWitnessVi(long cycle, byte[] address) {
    BytesCapsule bytesCapsule = get(buildViKey(cycle, address));
    if (bytesCapsule == null) {
      return BigInteger.ZERO;
    } else {
      return new BigInteger(bytesCapsule.getData());
    }
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }
