### Title
Backup restore path saves and replays `WriteSet`s that are never cryptographically bound to the verified `TransactionInfo.state_change_hash` - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
The transaction-restore/state-sync backup flow reads `TransactionChunk` records containing `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, Vec<ContractEvent>, WriteSet)` tuples from an untrusted backup store and only runs the `WriteSet`s through the accumulator/ledger-info proof for the `Transaction` and `TransactionInfo` — never for the `WriteSet` itself — before persisting them to the ledger DB or replaying them as KV updates.

### Finding Description
In `LoadedChunk::load` [1](#0-0) , each record is deserialized into `(txn, aux_info, txn_info, events, write_set)`, and `write_sets` is collected into its own `Vec<WriteSet>`.

Verification is then performed by constructing a `TransactionListWithProofV2` that carries `txns`, `event_vecs`, and `txn_infos` plus the `range_proof`/`ledger_info`, and calling `.verify(...)`: [2](#0-1) . Note that `write_sets` is **not** part of this struct and is not passed into `verify`.

`TransactionListWithProofV2`/`TransactionListWithProof::verify` (types/src/transaction/mod.rs) checks that (a) transaction hashes match `txn_info.transaction_hash()`, (b) the `TransactionInfo`s are anchored to the ledger via the accumulator range proof, and (c) events match `txn_info.event_root_hash()` — but it never checks `write_set` against `txn_info.state_change_hash()`. That write-set/state-change-hash cross-check only exists in the *output*-proof verification path (`TransactionOutputListWithProofV2::verify`), which is not used here: [3](#0-2)  shows the check that exists for outputs but is absent for the transaction-restore path.

After `LoadedChunk::load` returns, the unverified `write_sets` vector flows unchanged through `unpack()` and into the transaction-restore pipeline:
- Directly persisted via `restore_handler.save_transactions(..., write_sets_to_save)` for the pre-replay portion [4](#0-3) , which ultimately calls `restore_utils::save_transactions_impl`, writing the `WriteSet` into `WriteSetDb` and, when `kv_replay` is true, feeding it into `state_store.calculate_state_and_put_updates(&StateUpdateRefs::index_write_sets(...))` to derive and persist the new state tree [5](#0-4) .
- Or replayed via `handler.save_transactions_and_replay_kv(..., write_sets)` in the KV-only replay path [6](#0-5) .
- Or fed into `chunk_replayer.enqueue_chunks(txns, ..., write_sets, events, ...)` for full replay [7](#0-6) .

In all three paths, the only integrity guarantee available at the time these functions run is the accumulator proof over `TransactionInfo` (whose `state_change_hash` field is *supposed to* commit to the write set), but the actual `WriteSet` bytes taken from the backup file were never hashed and compared against that `state_change_hash`. Storage-level `WriteSetDb`/`save_transactions_impl` also perform no such check [8](#0-7) .

This is the direct analog of the reported oracle bug class: a value (`WriteSet`) that is supposed to be validated against a bound/commitment (`state_change_hash` in the accumulator-anchored `TransactionInfo`) is instead trusted as-is from an external, attacker-influenced source (the backup archive/storage backend), and used to build durable, committed ledger state.

### Impact Explanation
If the backup storage backend is compromised, or a backup archive is tampered with/corrupted in transit (a realistic threat model for restore/DR flows and state-sync-from-backup on nodes bootstrapping from a snapshot), an attacker can supply a `WriteSet` in a transaction chunk that does not match the accumulator-anchored `TransactionInfo` for that version while still passing all proof checks, because those checks never touch the write set. The result is durable ledger state (the state tree, `WriteSetDb`, and any KV replay outcome) diverging from the value that was actually authenticated by consensus/ledger-info signatures, i.e., committed state that differs from the correct historical VM result. Any node restoring from such a backup source would silently persist and serve incorrect state (through storage/API reads) despite having "verified" the proof, which is a high-severity state-commitment integrity break.

### Likelihood Explanation
Likelihood is limited to specific operational scenarios: it requires control over, or corruption of, the backup storage/transport (the `BackupStorage` trait implementation), which is an explicit trust boundary in the restore/verify/state-sync-from-backup tooling. It does not require any privileged on-chain actor and does not depend on consensus-honesty assumptions, so it is in scope as a local, unprivileged, storage/restore-path invariant break rather than a "malicious peer" or generic DoS.

### Recommendation
Before using the deserialized `write_sets` for persistence or replay in `LoadedChunk::load`, hash each `WriteSet` and assert it equals the corresponding `txn_infos[i].state_change_hash()`, mirroring the check already implemented for `TransactionOutputListWithProofV2::verify` (`write_set_hash == txn_info.state_change_hash()`). This should be enforced immediately after deserialization/proof verification, before `write_sets` is returned from `LoadedChunk::load`/`unpack()`, so no unverified write set ever reaches `save_transactions`, `save_transactions_and_replay_kv`, or `enqueue_chunks`.

### Proof of Concept
Conceptual PoC (cannot be executed without file/network access):
1. Produce a valid transaction backup chunk file for version `V` where `TransactionInfo` at `V` has `state_change_hash = H(WS_correct)` and the accompanying accumulator range proof correctly authenticates it against a legitimate `LedgerInfoWithSignatures`.
2. Replace only the `WriteSet` bytes for record `V` in the chunk with a different, attacker-chosen `WriteSet` `WS_evil` (leaving `Transaction`, `TransactionInfo`, and `events` untouched so `txn_hash`/`event_root_hash` checks still pass).
3. Run `TransactionRestoreController`/`LoadedChunk::load` against this tampered chunk: `txn_list_with_proof.verify(...)` succeeds because it never inspects `write_sets`.
4. `WS_evil` is persisted via `save_transactions`/`save_transactions_impl` into `WriteSetDb`, and (if `kv_replay`) is used to compute new state via `state_store.calculate_state_and_put_updates`, producing a state root that does not correspond to `H(WS_evil)` being validated against anything — the ledger now contains state derived from an unauthenticated write set at a version whose `TransactionInfo`/accumulator proof was valid only for `WS_correct`.

/// A helper function that saves the transactions to the given change set
pub(crate) fn save_transactions_impl(
    state_store: Arc<StateStore>,
    ledger_db: Arc<LedgerDb>,
    first_version: Version,
    txns: &[Transaction],
    persisted_aux_info: &[PersistedAuxiliaryInfo],
    txn_infos: &[TransactionInfo],
    events: &[Vec<ContractEvent>],
    write_sets: &[WriteSet],
    ledger_db_batch: &mut LedgerDbSchemaBatches,
    state_kv_batches: &mut ShardedStateKvSchemaBatch,
    kv_replay: bool,
) -> Result<()> {
    for (idx, txn) in txns.iter().enumerate() {
        ledger_db.transaction_db().put_transaction(
            first_version + idx as Version,
            txn,
            /*skip_index=*/ false,
            &mut ledger_db_batch.transaction_db_batches,
        )?;
    }

    for (idx, aux_info) in persisted_aux_info.iter().enumerate() {
        PersistedAuxiliaryInfoDb::put_persisted_auxiliary_info(
            first_version + idx as Version,
            aux_info,
            &mut ledger_db_batch.persisted_auxiliary_info_db_batches,
        )?;
    }

    for (idx, txn_info) in txn_infos.iter().enumerate() {
        TransactionInfoDb::put_transaction_info(
            first_version + idx as Version,
            txn_info,
            &mut ledger_db_batch.transaction_info_db_batches,
        )?;
    }

    ledger_db
        .transaction_accumulator_db()
        .put_transaction_accumulator(
            first_version,
            txn_infos,
            &mut ledger_db_batch.transaction_accumulator_db_batches,
        )?;

    ledger_db.event_db().put_events_multiple_versions(
        first_version,
        events,
        &mut ledger_db_batch.event_db_batches,
    )?;

    for (idx, txn_events) in events.iter().enumerate() {
        for event in txn_events {
            if let Some(event_key) = event.event_key() {
                if *event_key == new_block_event_key() {
                    LedgerMetadataDb::put_block_info(
                        first_version + idx as Version,
                        event,
                        &mut ledger_db_batch.ledger_metadata_db_batches,
                    )?;
                }
            }
        }
    }
    // insert changes in write set schema batch
    for (idx, ws) in write_sets.iter().enumerate() {
        WriteSetDb::put_write_set(
            first_version + idx as Version,
            ws,
            &mut ledger_db_batch.write_set_db_batches,
        )?;
    }

    if kv_replay && first_version > 0 && state_store.get_usage(Some(first_version - 1)).is_ok() {
        let (ledger_state, _hot_state_updates) = state_store.calculate_state_and_put_updates(
            &StateUpdateRefs::index_write_sets(first_version, write_sets, write_sets.len(), vec![]),
            &mut ledger_db_batch.ledger_metadata_db_batches, // used for storing the storage usage
            state_kv_batches,
        )?;
        // n.b. ideally this is set after the batches are committed
        state_store.set_state_ignoring_summary(ledger_state);
    }
