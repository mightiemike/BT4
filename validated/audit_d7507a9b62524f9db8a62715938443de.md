### Title
Starknet OS `execute_replace_class` Accepts Unvalidated/Undeclared Class Hash, Diverging from Blockifier's Declaration Check - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall (`execute_replace_class`) writes a contract's new `class_hash` into `contract_state_changes` without ever checking that the supplied class hash corresponds to a class that was actually declared. This is explicitly flagged by an unresolved `TODO` comment in the code, and it diverges from the blockifier's runtime enforcement of the same syscall, which does perform this check and rejects undeclared class hashes.

### Finding Description
In the blockifier (the sequencer's authoritative execution engine), `replace_class` is implemented in `crates/blockifier/src/execution/syscalls/syscall_base.rs:369-378`, which calls `self.state.get_compiled_class(class_hash)?` before allowing the class hash swap — returning an error (and reverting the call) if the class is undeclared: [1](#0-0) 
The equivalent Cairo0 (deprecated) syscall handler enforces the same check via `syscall_handler.state.get_compiled_class(request.class_hash)?`: [2](#0-1) 

However, the Starknet OS's own re-implementation of this syscall — used during OS re-execution / proof generation — performs no equivalent validation. In `execute_replace_class` (Cairo1 path), the code takes `class_hash` directly from the syscall request and writes it into the new `StateEntry` unconditionally, with an explicit acknowledged gap: [3](#0-2) 
```
    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
```
The identical omission exists in the deprecated (Cairo0) OS syscall path: [4](#0-3) 

This is the same bug class as the n8n report: a value taken from untrusted/attacker-influenced content (here, the `class_hash` argument supplied by a contract via the `replace_class` syscall, fully controllable by any contract's Cairo code, hence indirectly by any transaction sender or L1 message) is used to determine a target resource (a "class" resolution, analogous to an "origin") without verifying it against the expected/canonical source of truth (the declared-class registry), unlike the code path (blockifier) that is supposed to enforce this invariant.

The `contract_class_changes`/`contract_state_changes` dictionaries produced by OS execution directly feed the Patricia tree commitment computation (`compute_contract_state_commitment` / `state_update` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/state/state.cairo:47-113`), which determines the final global state root asserted by the OS output. Since the OS is the specification that the STARK proof attests to (independent of what the blockifier "actually" produced during sequencing), any check enforced only by the blockifier but not by the OS represents a soundness gap in the proof: the OS would accept and commit a state transition (a contract's class hash replaced by a hash for which no `DeclareTransaction` was ever committed) that the blockifier itself would never allow to succeed.

### Impact Explanation
Because the class-declaration check is asymmetric between the blockifier (enforced) and the OS (missing), the OS's definition of a "valid" state transition is broader than the actual protocol rule enforced during real block execution. This creates a genuine divergence between the state root the OS will accept/prove as valid and what would be produced by correct blockifier-based execution, i.e., a "wrong committed root" / honest-node divergence risk as required by the validation criteria — since the two independent implementations of the identical syscall (blockifier vs. OS) do not agree on what inputs are valid. A contract's class pointer could be committed to an undeclared/non-existent class hash under the OS's rules, corrupting that contract irrecoverably (permanent bricking, i.e., a form of permanent freezing of the affected account/contract's functionality) whenever this divergent path is exercised or relied upon by proving/verification infrastructure.

### Likelihood Explanation
The `class_hash` argument to `replace_class` is fully attacker-controlled calldata reachable from any account contract's `__execute__` logic (a single transaction can call `replace_class` with an arbitrary felt), and the missing check is unconditional (no special preconditions, gas cost aside). The only obstacle to observing divergence is that the sequencer's real (blockifier-driven) execution would revert such a call before it becomes part of the canonical state; the bug's practical exploitability therefore centers on the correctness of the OS as the standalone specification used for proof soundness, which is squarely in-scope of "Starknet OS re-execution."

### Recommendation
Add the missing declared-class check in the Starknet OS's `execute_replace_class` (and its deprecated Cairo0 counterpart), mirroring the blockifier's `get_compiled_class` check, before writing the new class hash into `contract_state_changes`/`contract_class_changes`. This should reject (or force a well-defined error path) for any `class_hash` that does not appear as a declared class in `contract_class_changes` or prior state, keeping the OS and blockifier semantics equivalent.

### Proof of Concept
1. Deploy an account/contract whose `__execute__` (or any external entry point) invokes `replace_class_syscall(new_class_hash)` with an arbitrary `new_class_hash` that has never been declared (no matching `DeclareTransaction` in `contract_class_changes`).
2. Under the blockifier, this call fails with `StateError::UndeclaredClassHash` (as demonstrated in the existing test `undeclared_class_hash` in `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29`), causing the call/transaction to revert — no state change ever occurs on-chain.
3. In the Starknet OS's `execute_replace_class` (`syscall_impls.cairo:881-920`), the identical syscall request, if fed independently as valid input to the OS's own execution/verification logic (which lacks the declaration check), would be accepted and would successfully write the undeclared `class_hash` into `contract_state_changes`, ultimately being committed via `compute_contract_state_commitment`/`state_update`, producing a state root inconsistent with what correct (blockifier-consistent) execution should ever allow.     pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }

    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
