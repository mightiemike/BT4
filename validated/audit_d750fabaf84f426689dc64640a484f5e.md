### Title
Wallet contract silently keeps an external caller's attached NEAR deposit on success instead of refunding unused amount - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
This is the closest reachable analog to the reported `FeeBuyback.submit` issue (accidental value sent by a caller is not accounted for and becomes permanently stuck): the NEAR Wallet Contract's `rlp_execute` entry point accepts an arbitrary `#[payable]` deposit from any external caller and only refunds that deposit when the resulting cross-contract promise **fails**. On success, the caller's tracked deposit is discarded with no logic to return any unspent/unused portion, similarly to how `FeeBuyback.submit` fails to check `msg.value == 0` for the ERC20 path and thus loses accidentally attached ETH.

### Finding Description
`WalletContract::rlp_execute` is `#[payable]`, so any predecessor (a relayer, another contract, or any transaction signer) can attach an arbitrary NEAR deposit when calling it: [1](#0-0) 

Internally, `inner_rlp_execute` records the caller's attached deposit into a `CallerDeposit` struct only for the purpose of refunding it later if the promise execution fails: [2](#0-1) [3](#0-2) 

The actual refund logic lives in `rlp_execute_callback`: [4](#0-3) 

Note that the `PromiseResult::Failed` branch explicitly refunds `caller_deposit` back to `account_id`, but the `PromiseResult::Successful` branch does nothing with `caller_deposit` at all — it is simply dropped. Nowhere in the codebase (`inner_rlp_execute`, `try_into_near_action`, `action_to_promise`) is the caller's raw `attached_deposit` value ever forwarded into the constructed Near action's own `deposit` field; the action's deposit is instead computed purely from the Ethereum transaction's ABI-encoded `yocto_near` field and the `tx.value` field: [5](#0-4) [6](#0-5) 

This means the NEAR deposit attached by an external, non-self caller of `rlp_execute` (e.g. a relayer app or any contract that is *not* the wallet's own eth-implicit account) is completely disconnected from the value actually moved by the emulated Ethereum transaction. If that promise chain later resolves successfully, the deposit is never returned to the caller and is never spent on anything either — it is simply absorbed into the wallet contract's balance, permanently unaccounted for from the caller's perspective. This is structurally identical to `FeeBuyback.submit`'s bug: value attached alongside an unrelated operation is retained by the contract instead of being refunded, because the code path lacks a "return unused/unrelated value" check on the success branch.

The project's own test, `test_caller_refunds`, only verifies the *failure* refund path and the case where "tokens are spent" (i.e., deposit fully consumed as gas/deposit for the target action) — it does not test a success case where the caller's deposit is not consumed by the action but simply silently retained: [7](#0-6) 

### Impact Explanation
Any account (not necessarily the wallet owner or the relayer with an access key) can call `rlp_execute` on any deployed wallet-contract eth-implicit account while attaching NEAR tokens. If the underlying promise chain succeeds — which is the expected/common case for a well-formed relayer transaction — that attached deposit is retained by the wallet contract forever, with no code path to reclaim it for the original caller. This is a direct, transaction-triggered loss of funds (frozen/lost value) for any caller who attaches a deposit to a successful call, matching the "concrete...permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires an external, non-self caller (`predecessor_account_id != current_account_id`) to attach a nonzero deposit to `rlp_execute` while the resulting emulated transaction succeeds. This is a very plausible real-world scenario, e.g. a naive third-party relayer/aggregator or user tooling that (mistakenly, or by convention copied from other NEAR payable methods) attaches a deposit "to be safe" or to cover potential storage costs, not realizing the wallet contract has no mechanism to spend or return it on the success path.

### Recommendation
On the `PromiseResult::Successful` branch of `rlp_execute_callback`, explicitly refund any tracked `caller_deposit` that was not consumed by the constructed action (or, more conservatively, always refund the full `caller_deposit` unless the protocol design intentionally wants it to be spent — in which case that intent should be surfaced and validated, similar to requiring `msg.value == 0` for token operations in the Solidity analog). At minimum, add an explicit accounting/validation step so unspent externally-attached deposits are never silently retained by the contract on success.

### Proof of Concept
1. Deploy the wallet contract at an eth-implicit account `0xabc...`.
2. Have some external account `attacker.near` (not the wallet's own account) call `rlp_execute(target, tx_bytes_b64)` attaching, e.g., 3 NEAR, where `tx_bytes_b64` encodes a valid, successful native action (e.g., a `Transfer` action with `yocto_near = 0` to some receiver), as in `create_rlp_execute_tx`/`create_signed_transaction` used by `test_caller_refunds`: [8](#0-7) 
3. Observe that the promise chain succeeds (`ExecuteResponse.success == true`), and check `attacker.near`'s balance decreased by ~3 NEAR while the wallet contract's balance increased by ~3 NEAR, with no refund receipt generated — analogous to the existing failure-path assertions in `test_caller_refunds`, but for the success path, which the current test suite does not cover.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
