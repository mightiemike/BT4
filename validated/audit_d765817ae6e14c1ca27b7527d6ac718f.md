### Title
Deploy-syscall address squatting permanently DoS's a user's future `deploy_account` transaction and freezes any pre-funded balance - (File: `crates/blockifier/src/execution/execution_utils.rs`)

### Summary
Contract addresses in Starknet are deterministic — computed from `salt`, `class_hash`, `constructor_calldata`, and `deployer_address`. Any unprivileged account can invoke the `deploy` syscall (via a normal `invoke` transaction) to pre-emptively deploy a contract at an address it can compute in advance, before the intended owner's `deploy_account` transaction lands. Because both `execute_deployment` (native execution) and the Starknet OS `deploy_contract` (re-execution) reject deployment to an address whose class hash is already non-default, the legitimate `deploy_account` transaction permanently fails once squatted, and this mirrors the reported bug class: a sequential/deterministic resource identifier that is assumed to be exclusively controlled by one actor, but can be raced and consumed by an unprivileged third party, causing the "rightful" mint/deploy to revert.

### Finding Description
`execute_deployment` allocates the deployed contract's address before invoking its constructor, and rejects the deployment if the address already has a non-default class hash: [1](#0-0) 

This function is reachable both from the low-level `deploy` syscall (`syscall_base.rs::deploy`, reachable by any contract via `invoke`) and from `deploy_account` transaction execution: [2](#0-1) 

The deployed address is fully deterministic given public inputs — for a `deploy_account` transaction, `deployer_address` is always `ContractAddress::ZERO`: [3](#0-2) 

Once a user broadcasts (or even signs and shares) a `deploy_account` transaction with a chosen `class_hash`, `contract_address_salt`, and `constructor_calldata`, any observer can compute the exact future address using the same `calculate_contract_address` formula and beat the legitimate transaction to it by calling the `deploy` syscall from an arbitrary contract with `deploy_from_zero=true` (setting `deployer_address` to zero to match the account-deployment formula) and the same `class_hash`/`salt`/`calldata`. The Starknet OS re-execution path enforces the exact same invariant, so this is not just a blockifier quirk but a protocol-level state assumption: [4](#0-3) 

When the real `deploy_account` transaction is subsequently executed, it fails with `StateError::UnavailableContractAddress`, as demonstrated in the existing test that intentionally exercises this exact negative flow: [5](#0-4) 

Since address occupancy is permanent (a contract, once deployed to an address, cannot be un-deployed), the attack cannot be retried by the victim with the same salt — the account can never be created at that address again.

### Impact Explanation
Funds sent to the precomputed account address in anticipation of deployment (a common flow: fund the future account address, then submit `deploy_account`) become permanently locked, because the account contract that would provide the interface/logic to move those funds can never be deployed to that address again once squatted. This satisfies "concrete loss or permanent freezing of funds" and "unauthorized account action" (the account owner is permanently denied the ability to activate their own precomputed address), which are explicitly in scope per the validation criteria.

### Likelihood Explanation
Any unprivileged account can trigger this by observing a `deploy_account` transaction's public parameters (`class_hash`, `contract_address_salt`, `constructor_calldata` are all included in the transaction and visible once broadcast/gossiped, or even leaked by the wallet's precomputation of the address that users are told to fund ahead of time) and racing it with a cheap `invoke` transaction that calls `deploy_syscall` with `deploy_from_zero=true` using identical parameters. No special privileges, staking, or node compromise are required — only a standard, unprivileged transaction sender able to reach `syscall_base.rs::deploy`.

### Recommendation
Consider one or more of:
1. Prevent externally-callable `deploy` syscalls with `deploy_from_zero=true` from squatting addresses that match the deterministic formula used by `deploy_account` (e.g., require `deployer_address` to be non-zero and derived from `msg.sender` unless explicitly permitted, or disallow `deploy_from_zero` entirely for third-party contracts).
2. Encourage/enforce wallets to include a nonce/commitment binding in the salt derivation that is not predictable/observable before the `deploy_account` transaction is included, reducing the front-running window.
3. At the very least, document this as a known limitation so wallets avoid funding precomputed addresses before deployment confirmation, and consider adding a recovery path (e.g., allow re-deriving a fresh salt without losing funds already sent) for squatted addresses.

### Proof of Concept
1. Wallet computes `deploy_account` address for `salt`, `class_hash`, `constructor_calldata` (deployer_address = 0) and shares/funds it, planning to submit the `deploy_account` transaction shortly after.
2. Attacker observes these parameters (from the pending/broadcast `deploy_account` transaction, or from any public sharing of the target address's precomputation inputs).
3. Attacker submits a cheap `invoke` transaction from an already-deployed contract calling the `deploy` syscall with `class_hash`, `contract_address_salt = salt`, `constructor_calldata`, `deploy_from_zero = true` — see `syscall_base.rs::deploy` (lines 400-410) which computes the identical address via `calculate_contract_address`.
4. `execute_deployment` succeeds for the attacker (address was previously unclaimed), setting the class hash at that address (`execution_utils.rs` lines 337-373).
5. Victim's `deploy_account` transaction now executes `execute_deployment` for the same address, finds `current_class_hash != ClassHash::default()`, and fails with `StateError::UnavailableContractAddress`, exactly as reproduced in the existing regression test at `transactions_test.rs` lines 2312-2338 — the account can never be deployed to that address again, permanently freezing any pre-sent funds.

impl<T: DeployTransactionTrait> CalculateContractAddress for T {
    /// Calculates the contract address for the contract deployed by a deploy account transaction.
    /// For more details see:
    /// <https://docs.starknet.io/architecture-and-concepts/smart-contracts/contract-address/>
    fn calculate_contract_address(&self) -> StarknetApiResult<ContractAddress> {
        // When the contract is deployed via a deploy-account transaction, the deployer address is
        // zero.
        const DEPLOYER_ADDRESS: ContractAddress = ContractAddress(PatriciaKey::ZERO);
        calculate_contract_address(
            self.contract_address_salt(),
            self.class_hash(),
            self.constructor_calldata(),
            DEPLOYER_ADDRESS,
        )
    }
}
