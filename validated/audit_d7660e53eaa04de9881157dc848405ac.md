### Title
Webhook Shop-Domain Header Not Authenticated by HMAC, Enabling Cross-Tenant Session Deletion via `APP_UNINSTALLED` Replay - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
Shopify webhook validation in this library authenticates only the raw request **body** via HMAC; the shop-identifying `X-Shopify-Shop-Domain` header is extracted and trusted afterward without being cryptographically bound to that HMAC. This mirrors the reported bug class (an authenticity/ownership check is performed on one field while a security-relevant related field is left unverified), and it is reachable from a single (attacker-controlled) merchant shop with no special privileges.

### Finding Description
`validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` computes and compares the HMAC solely over `rawBody` [1](#0-0) . The `validateFactory` webhook entry point in `packages/apps/shopify-api/lib/webhooks/validate.ts` calls this HMAC check and, only after it passes, separately reads header fields such as `domain`, `topic`, and `webhookId` via `checkWebhookHeaders`, none of which are part of the signed payload [2](#0-1) .

Because the shop domain is carried in an unsigned header, a request replaying a **previously-obtained valid (body, HMAC) pair** — which an attacker can legitimately produce by triggering a real webhook (e.g. `APP_UNINSTALLED`) on their own shop where the app is installed — will still pass HMAC validation even if the `X-Shopify-Shop-Domain` header is changed to name a different (victim) shop, since the header is not part of the signed content.

Downstream, `authenticateWebhookFactory` in the Remix/React Router adapters trusts `check.domain` directly to look up and act on that shop's session: `ensureValidOfflineSession(params, check.domain)` [3](#0-2) . In `shopify-app-express`, the built-in `APP_UNINSTALLED` handler goes further and **deletes all stored sessions for the shop named in the header** via `AppInstallations.delete(shopDomain)`, which calls `findSessionsByShop` / `deleteSessions` keyed purely on that domain string [4](#0-3) , and this handler is auto-registered for every app using the express package [5](#0-4) .

### Impact Explanation
An attacker who installs the target app on their own store (a normal, unprivileged single-merchant action) can trigger a genuine `APP_UNINSTALLED` webhook against their own shop, capturing a legitimately-signed `(body, hmac)` pair from Shopify. Because the domain header is outside the HMAC's scope, the attacker can resend that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop's domain. The request passes `validateHmacFromRequestFactory`'s check unchanged, and the built-in Express handler (`deleteAppInstallationHandler` → `AppInstallations.delete`) will delete the victim's stored offline/online sessions, forcing the victim's app instance into a de-authenticated state without their action — a denial-of-service against an unrelated tenant purely from an anonymous/attacker-controlled webhook replay.

### Likelihood Explanation
Likelihood is moderate-to-high for apps using `shopify-app-express`'s default `APP_UNINSTALLED` handling: the attacker needs only to install the app on any shop they control (a normal, unprivileged action available to any merchant) to obtain a valid signed webhook body/HMAC pair, then replay it with a modified header — no secret leakage, no MITM, and no privileged access are required. The main variable affecting exploitability is whether a given deployment's session storage's `findSessionsByShop`/webhook processing pipeline preserves header trust as shown (which is the default/library-provided behavior).

### Recommendation
- Bind the shop domain (and other security-relevant identifying headers such as `topic`/`webhook_id`) into the value that is HMAC-verified, or independently verify that the `X-Shopify-Shop-Domain` header matches a shop actually associated with the webhook subscription/session context before performing destructive actions.
- For the built-in `APP_UNINSTALLED` handler, avoid trusting the raw header value directly for session deletion; instead, cross-check against known/expected shop identifiers or require webhook-id uniqueness/replay tracking (e.g., reject webhook IDs seen more than once) to mitigate replay-based domain spoofing.
- Document/enforce webhook idempotency-key (`X-Shopify-Webhook-Id`) tracking to detect and reject replayed requests generally, independent of the domain-spoofing vector.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal merchant action).
2. Attacker uninstalls the app from their shop, causing Shopify to send a genuine `APP_UNINSTALLED` webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/records this legitimate request (e.g., via a proxy they control since it's their own webhook endpoint traffic).
4. Attacker resends a POST to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `validateHmacFromRequestFactory` validates HMAC(`B`) == `H` → passes, since domain is not part of the signed content [1](#0-0) .
6. The Express `APP_UNINSTALLED` handler calls `AppInstallations.delete('victim-shop.myshopify.com')`, deleting the victim's real sessions [4](#0-3) , despite the victim never uninstalling the app.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
