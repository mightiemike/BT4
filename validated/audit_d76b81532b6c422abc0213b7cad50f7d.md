## Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, letting replay-verify tooling accept a divergent committed state root - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the exact analog of the reported `IMultiSourceLoan.loan.hash()` bug: a struct field (`protocolFee`) that is authoritative for correctness is silently dropped from the equality/commitment check, letting a caller supply/accept a divergent value without the check ever failing. Here, the authoritative field is `TransactionInfo::state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), and the check that drops it is the function used by replay/verification tooling (`aptos-debugger`, `aptos-move/cli`, and `storage/db-tool/src/replay_on_archive.rs`) to confirm that a freshly re-executed transaction output matches the authenticated, on-chain `TransactionInfo`.

## Finding Description
`ensure_match_transaction_info` validates status, gas used, `state_change_hash` (write-set hash) and `event_root_hash` against the target `TransactionInfo`, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that summarize the actual global (Sparse/Jellyfish Merkle) state root after the transaction: [1](#0-0) 

The comment left in the code makes the gap explicit and self-admits the exact consequence: [2](#0-1) 

This function is invoked directly by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes historical transactions from backup and calls `ensure_match_transaction_info` to decide pass/fail of a replay: [3](#0-2) 

Because `write_set_hash` only commits to the write set *produced by this one transaction*, it does not commit to how that write set is folded into the running global state tree. A discrepancy that only manifests in the resulting state root — e.g. from a bug in `DoStateCheckpoint`/JMT commit logic, a storage-schema misinterpretation on restore, or divergent hot-state handling — produces an identical `state_change_hash` while producing a different `state_checkpoint_hash`/state root. `ensure_match_transaction_info` will still return `Ok(())` because it never compares the checkpoint hashes, so replay-verify, `aptos-debugger`, and `aptos-move/cli` (the tools whose entire purpose is to catch exactly this kind of divergence) will report success on a run whose committed durable state is actually different from the authenticated chain state.

## Impact Explanation
This directly hits the "State-Integrity Gate": committed state that differs from the correct VM result, and hard-fork-only divergence during replay/restore not being caught by the tool designed to catch it. Replay-verify is the last line of defense used to detect non-determinism/state-divergence bugs across releases before they reach mainnet or to validate that a synced archive node's history matches the canonical ledger. A bug that only affects the final state root (not the per-transaction write-set hash) — for example in state-checkpoint construction, hot-state merging, or JMT restore/commit — would silently pass this comparator, allowing an already-diverged database to be certified as correct. This is a systemic proof/verification-integrity gap in the authenticated-response validation path, matching the required "wrong … proof accepted as valid" and "hard-fork-only divergence during replay/restore" impact classes.

## Likelihood Explanation
The gap is unconditional and unprivileged: it is not guarded by a feature flag today (the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` flag mentioned in the TODO is aspirational future work per the comment, but the current comparator ignores `state_checkpoint_hash` regardless of that flag's state) — no privileged action is required, any caller of `ensure_match_transaction_info` (replay-verify workers, `aptos-debugger`, `aptos-move/cli`) inherits the gap automatically. Because the code and comment self-document the exact defect, awareness/likelihood of hitting an undetected divergence bug is high whenever an actual state-root-affecting bug exists elsewhere in the commit/restore pipeline (which this check is specifically supposed to catch).

## Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, when present/enabled, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) between the locally recomputed checkpoint and `txn_info`, mirroring the recommended fix pattern from the external report of including all authoritative fields in the comparison/hash before treating the two sides as equal. At minimum this should be enabled ahead of, not gated behind, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, since the write-set hash alone cannot detect divergence introduced downstream of write-set application.

## Proof of Concept
1. In `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, re-execute a historical block and obtain `executed_outputs[idx]` whose `write_set`/`events`/`gas_used`/`status` are byte-identical to the archived output for that version (this is expected in the non-buggy path). [4](#0-3) 
2. Suppose a bug (or a targeted storage/restore corruption) causes the *state checkpoint construction* stage (`DoStateCheckpoint`, invoked in `execution/executor/src/workflow/do_ledger_update.rs` prior to hashing into `TransactionInfo`) to produce a different `state_checkpoint_hash` for the same write set than what is recorded on-chain — e.g. because a JMT/hot-state merge logic diverges. [5](#0-4) 
3. `ensure_match_transaction_info` is called with the replay's `TransactionOutput` against the archived `expected_txn_info` (line 392 of `replay_on_archive.rs`). Since it checks only `status`, `gas_used`, `state_change_hash`, and `event_root_hash`, and never `state_checkpoint_hash`, the call returns `Ok(())` despite the divergent state root. [6](#0-5) 
4. `Verifier::run` reports zero failed transactions for this range, giving false assurance that the replayed/restored ledger state matches the authenticated chain, even though the actual committed state root differs — the exact analog of `repayLoan(loan.protocolFee=0)` bypassing the hash check in the source report.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
