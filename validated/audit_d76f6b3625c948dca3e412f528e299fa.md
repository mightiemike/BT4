### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Session/Payload Confusion - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The webhook validation pipeline verifies the HMAC over the raw request body only, while the `X-Shopify-Shop-Domain` header (the identifier later used to select *which shop's* offline session/access token to hand to the webhook handler) is read separately and never cryptographically tied to the signed content. This is the same root-cause pattern as H-5: a security-critical identifier (`mint_account` in the Solana report, `domain` header here) is trusted independently of the value that was actually authenticated (the transferred token / the signed body), enabling the identifier to be swapped without invalidating the signature check.

### Finding Description
`validateHmacFromRequestFactory` computes and checks the HMAC strictly against `rawBody`: [1](#0-0) 

`validateFactory` in `webhooks/validate.ts` runs that body-only HMAC check, and — independently of the HMAC result — pulls `domain`, `topic`, `apiVersion`, `webhookId`, etc. straight out of request headers via `checkWebhooksHeaders`/`getRequiredHeader`, with no linkage between the header values and the signed body: [2](#0-1) [3](#0-2) 

The header name mapping confirms `domain` is a plain header (`ShopifyHeader.Domain` / `ShopifyEventsHeader.Domain`), not part of the HMAC input: [4](#0-3) 

Downstream, the webhook authenticate handlers in `shopify-app-remix` and `shopify-app-react-router` take `check.domain` returned from the (only-body-verified) validation result and use it directly to look up and load an **offline session/access token for that shop**, then attach a live Admin API client authorized as that shop to the webhook context — driven by whatever `payload`/body the attacker actually sent: [5](#0-4) [6](#0-5) 

An existing test explicitly documents that the library treats `domain` as an unauthenticated header that has no bearing on HMAC validity — it only fails the case because the HMAC itself is wrong, not because the forged domain is detected: [7](#0-6) 

This mirrors the Sherlock H-5 root cause precisely: the whitelist/authorization check (`whitelist_entry` keyed on `mint_account` ⇄ here, session lookup keyed on `domain` header) is performed on a field that is never cross-validated against the field that was actually authenticated (the transferred SPL token / the signed webhook body). Anchor's account constraints proved `mint_account` is whitelisted but not that it's the token transferred; here, the HMAC proves the body came from a holder of `apiSecretKey`, but nothing proves the accompanying `domain` header matches which shop actually produced that HMAC.

### Impact Explanation
`apiSecretKey` is shared across every shop that installs the app (it's the app's client secret, not per-shop). Any merchant who has installed the app can trigger a legitimate webhook from their own store, capturing a **valid `(rawBody, X-Shopify-Hmac-Sha256)` pair** signed with the app's shared secret. Because `domain` is not bound to that signature, the merchant can replay the identical body+HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain that also has the app installed. The library will report `valid: true` with `domain = <victim shop>`, causing the app to:
- load the **victim's offline session/access token** from session storage, and
- hand the webhook handler an authenticated Admin API client for the victim, processing a payload the attacker fully controls.

This is a cross-tenant confusion that lets one merchant trigger app business logic (e.g., data resets on `app/uninstalled`, order/product processing logic) attributed to and authorized as a different, unrelated shop — directly analogous to the token-spoofing/economic-damage impact described in H-5, but manifesting as cross-tenant session/authorization confusion instead of asset misattribution.

### Likelihood Explanation
Requires only a single already-onboarded merchant (an allowed "single merchant" attacker per scope) with knowledge of a target shop's `.myshopify.com` domain (these are commonly discoverable/guessable) and the target also having the app installed — no leaked secrets, no MITM, and no privileged (staff/admin-of-the-library) access needed. This mirrors real Shopify webhook signing semantics (HMAC over body only), so it is a structural property of how `shopify-app-js` consumes Shopify's webhook headers rather than a transient bug, making it consistently reproducible whenever an app relies on `check.domain`/`shop` from `authenticate.webhook` to gate access to per-shop sessions.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` (or events equivalent) header as trusted merely because the body HMAC validates. At minimum:
- Cross-check that the resolved `domain` corresponds to a shop for which this exact webhook delivery was actually registered/expected (e.g., validate against the webhook subscription's target shop recorded at registration time, or require a per-shop secret/HMAC binding rather than a single shared `apiSecretKey`).
- Where feasible, bind the domain into the HMAC computation (or use topic+webhookId+domain uniqueness plus idempotency tracking) so a captured signature cannot be replayed with a different domain.
- Document clearly for consumers of `authenticate.webhook`/`shopify.webhooks.validate` that `domain` is unauthenticated relative to the HMAC and must not be used alone to authorize cross-shop session access without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any subscribed webhook (e.g., updates a product), causing Shopify to POST a signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(apiSecretKey, B)` per `validateHmacString`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)`.
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a shop known to have the app installed).
4. `shopify.webhooks.validate` runs `validateHmacFromRequestFactory`, which only checks `HMAC-SHA256(apiSecretKey, B) === H` — this still passes because `B` and `H` are unchanged; `checkWebhooksHeaders` independently returns `domain: 'victim-shop.myshopify.com'`.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)`, loading `victim-shop.myshopify.com`'s offline session/access token, and returns a webhook context with `admin` authorized as the victim shop but `payload = JSON.parse(B)` fully controlled by the attacker.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
