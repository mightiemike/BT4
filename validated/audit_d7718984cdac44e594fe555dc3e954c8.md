### Title
Session-storage lookup errors are forwarded verbatim to unauthenticated HTTP clients - ([File: packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts])

### Summary
`shopify-app-express`'s `validateAuthenticatedSession` middleware calls into the app's configured `SessionStorage` backend (Postgres, MySQL, MongoDB, Redis, Prisma, etc.) to load a session, and on failure sends the raw driver error message straight back to the HTTP client with `res.send(error.message)`. This is the same bug class as the Curio advisory: a backend/database error object is passed unfiltered into an HTTP error response, risking exposure of internal infrastructure details (hostnames, ports, driver-specific error text, and in the worst case connection string fragments) to a client that merely needs to trigger a storage-layer error.

### Finding Description
In `validateWithAuthCodeFlow`, the middleware first resolves a session id and then loads the session from storage: [1](#0-0) 

Both catch blocks in this function forward `error.message` (the raw exception thrown by the configured `SessionStorage` implementation) directly to the HTTP response:
- The `getCurrentId` failure path calls `handleSessionError`, whose default branch does `res.status(500); res.send(error.message);` [2](#0-1) 
- The `loadSession` failure path does the same directly inline. [3](#0-2) 

The bundled `SessionStorage` adapters build their connections from a URL containing plaintext credentials, then hand host/user/password/database individually to the underlying driver (e.g. `pg.Pool`, `mysql.createPool`) — mirroring the exact pattern flagged in the Curio report: [4](#0-3) [5](#0-4) 

Driver-level failures from `pg`/`mysql2`/MongoDB clients (connection refused, auth failure, malformed query, pool exhaustion, etc.) frequently include host, port, or other connection-string fragments in their `Error.message`. Because `validateAuthenticatedSession` propagates that message unfiltered to the HTTP response body, any request that reaches a protected route and manages to trip a storage error (e.g., a malformed/oversized session cookie value, a transient DB outage, or a pool-exhaustion condition induced by concurrent requests) will leak that detail to the requester — with no authentication of the *response consumer* required, since the whole point of this middleware is to run before a session is confirmed valid.

### Impact Explanation
An unauthenticated or minimally-authenticated network client hitting an app route wrapped by `validateAuthenticatedSession()` can receive verbose, driver-generated error text in the HTTP response when the app's session store experiences any error. Depending on the storage backend and specific driver error, this can reveal database hostnames/ports, internal query fragments, or other infrastructure details useful for follow-on attacks against the app's control-plane database — the same impact class described in the Curio advisory (CWE-209).

### Likelihood Explanation
The code path is reached on essentially every request to a protected app route before authentication is fully established (it runs to look up whether a session already exists). Any condition that causes the configured `SessionStorage.loadSession`/`getCurrentId` implementation to throw — transient DB issues, pool exhaustion, malformed session id, or a corrupted/oversized cookie value supplied by the client — results in the raw error text being sent back with a 500 status. This does not require valid Shopify authentication, only network access to a route guarded by the middleware, making the exposure straightforward to trigger repeatedly.

### Recommendation
Do not forward `error.message` from session-storage/database operations to the HTTP client. Log the full error server-side (as is already done via `config.logger.error`) and return a generic message (e.g., `"Internal Server Error"`) in `handleSessionError` and the `loadSession` catch block. Consider adding a centralized error-sanitization utility (similar to Curio's `errFilter`) applied to any error text before it is written to an HTTP response anywhere in `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router`.

### Proof of Concept
1. Configure an app with `PostgreSQLSessionStorage` (or any bundled DB-backed session storage) and mount `shopify.validateAuthenticatedSession()` on a route.
2. Send a request to that route with a manipulated cookie/session id (or trigger a DB outage/pool exhaustion) such that `config.sessionStorage.loadSession(sessionId)` throws.
3. Observe the HTTP 500 response body contains the raw driver error message (`res.send(error.message)` at `packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts:101`), which may include host/port or other connection details depending on the underlying driver's error formatting.
