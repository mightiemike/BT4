## Title
Replay-verify comparator never validates the state root, letting a state-divergent (hard-fork) execution pass as verified - (`File: types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the sole authenticity check used by chunk-executor verification and the `db-tool replay-verify` / `aptos-debugger` tooling to confirm that a freshly re-executed transaction matches the transaction info that was actually committed to the accumulator on mainnet. This function checks status, gas used, the write-set hash, and the event root hash, but it never compares the locally recomputed state root against `txn_info.state_checkpoint_hash()`. Any divergence in state-tree (JMT/SMT) computation — the exact class of bug that causes a hard fork — is invisible to this tool even though it is precisely what the tool exists to detect.

## Finding Description
`ensure_match_transaction_info` in [1](#0-0)  performs these checks only:
- `self.status()` vs `txn_info.status()`
- `self.gas_used()` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed event root vs `txn_info.event_root_hash()`

It never reads or compares `txn_info.state_checkpoint_hash()` — the field that carries the actual state Merkle root committed to the ledger at checkpoint boundaries. The function's own trailing comment acknowledges this gap explicitly:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
``` [2](#0-1) 

This is not limited to the not-yet-enabled trading-native feature: the plain `state_checkpoint_hash` (the primary state root used by all Aptos chains today) is likewise never checked anywhere in this function.

This comparator is the exact function relied upon by:
- `ChunkExecutor::verify_execution`, which re-executes a range of transactions and calls `ensure_match_transaction_info` to decide whether execution matches the archived, ledger-accumulator-authenticated `TransactionInfo` list [3](#0-2) .
- `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, the primary offline tool operators/auditors use to replay historical mainnet transactions and confirm no divergence exists (i.e., detect would-be hard forks before they become consensus incidents) [4](#0-3) .

Because neither caller independently checks `state_checkpoint_hash`, a bug that corrupts the state tree (e.g., in `DoStateCheckpoint`, JMT construction, or a resource-group/aggregator materialization bug) while leaving the write set, events, gas, and status byte-identical would be entirely undetected by replay-verify, even though the underlying committed state root — which is what light clients and state proofs are ultimately anchored to — has silently diverged from what the tool believes was verified.

## Impact Explanation
This breaks the "Hard-fork-only divergence during commit, replay, restore, or proof verification" invariant explicitly in scope. Replay-verify is Aptos's primary detection mechanism for confirming that historical execution over mainnet archive data reproduces the exact ledger state that was actually committed and signed by validators. Since the state root is not compared, a class of bugs that corrupt derived state (but not the write set/event content byte pattern under comparison, or that manifest only in the state-tree materialization stage rather than the write set itself) can pass replay-verify as "fully verified," giving false assurance that no chain-state divergence exists. This directly undermines the fork-detection guarantee that the whole tool is designed to provide, and could delay detection of a genuine state-integrity incident on mainnet.

## Likelihood Explanation
The check is unconditionally skipped for every invocation of `ensure_match_transaction_info` (there is no feature flag or code path that adds the state-checkpoint check elsewhere before or after this call in either the chunk executor or `db-tool`). Any state-root-affecting bug that does not also change the write set encoding will reliably evade detection every time these tools are run, so likelihood of the false-negative firing (given such a bug exists) is essentially deterministic — the gap is structural, not probabilistic.

## Recommendation
Extend `ensure_match_transaction_info` to also compare the locally recomputed state checkpoint hash (and, where applicable, hot-state/position-state checkpoint hashes) against `txn_info.state_checkpoint_hash()` (and the corresponding V1 fields) whenever the executed transaction is a checkpoint boundary, failing verification on mismatch just as it does today for the write-set and event-root hashes.

## Proof of Concept
1. Note that `ensure_match_transaction_info` only asserts on `status`, `gas_used`, `write_set_hash` (`state_change_hash`), and `event_root_hash`: [5](#0-4) .
2. `ChunkExecutor::verify_execution` (used by replay-verify workflows in `aptos-move/cli` and `aptos-move/aptos-debugger`) calls only this function to accept/reject a re-executed range against the archived `TransactionInfo`s: [3](#0-2) .
3. `storage/db-tool/src/replay_on_archive.rs`'s standalone `replay-verify` binary similarly calls only `ensure_match_transaction_info` per transaction to decide pass/fail: [4](#0-3) .
4. Construct (or trigger via a state-materialization bug) an execution result where the write set and events are byte-identical to the historical archive, but the state tree/JMT root produced by `DoStateCheckpoint` differs from the archived `state_checkpoint_hash`. Both `verify_execution` and `replay_on_archive`'s `Verifier` will report success (`Ok`), because no code path anywhere compares the computed root to `txn_info.state_checkpoint_hash()`, confirming replay-verify silently accepts a state-divergent replay.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
