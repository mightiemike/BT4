### Title
Meta-transaction (Delegate/DelegateV2) balance refunds route to `sender_id`, not the paying relayer, letting a delegator siphon relayer-funded deposits on receiver-shard failure - (File: `runtime/runtime/src/actions.rs`)

### Summary
When a relayer submits a `Delegate`/`DelegateV2` action on behalf of a sender ("Alice"), the relayer prepays gas and any attached deposit for the inner actions. The runtime executes the inner actions in a new receipt whose `predecessor_id` is set to `sender_id` (Alice), not the relayer. If that inner receipt fails on the receiver's shard, the protocol's standard deposit-refund rule sends the refunded balance to the receipt's `predecessor_id`/`balance_refund_receiver`, i.e., to Alice — even though the relayer is the one whose account actually paid for the attached deposit. This misdirects value away from the party that funded it, mirroring the Illuminate `redeem` bug class where "the wrong balance/party" receives funds instead of the actual payer.

### Finding Description
`apply_delegate_action` builds the inner receipt with `predecessor_id: sender_id.clone()`: [1](#0-0) 

The accompanying comment even flags the ownership mismatch explicitly: relayer prepays everything, but "if something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer": [2](#0-1) 

Deposit refunds are generated generically via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, and `balance_refund_receiver()` resolves to `refund_to` if set, otherwise falls back to `predecessor_id()`: [3](#0-2) [4](#0-3) 

Because the inner receipt's `predecessor_id` is Alice, any deposit attached to the inner action(s) that later fails to execute is refunded to Alice, not to the relayer who actually decremented their own account balance to fund the deposit. Gas refunds, by contrast, correctly go back to the relayer because they use `action_receipt.signer_id()` (the original transaction signer = relayer): [5](#0-4) 

This asymmetry (gas correctly refunded to relayer, deposit incorrectly refunded to sender) is exactly the bug pattern reported in Illuminate: the function checks/attributes the wrong account for a redemption/refund, so value ends up with the wrong party. The project's own documentation confirms this is a real, exploitable economic hazard rather than a benign accounting quirk: [6](#0-5) 

### Impact Explanation
A malicious "Alice" can construct a `DelegateAction`/`DelegateV2` whose inner action attaches a deposit and is crafted (or targeted) to fail on the receiver's shard (e.g., calling a nonexistent method, an account that doesn't exist, or a method that reliably errors). The relayer, who is contractually/pragmatically expected to be reimbursed by gas fees for meta-transaction relaying, instead has the attached deposit balance permanently redirected to Alice's account rather than back to the relayer. This is a concrete unauthorized value movement: NEAR tokens that were debited from the relayer's account end up credited to Alice's account with no consent or compensating mechanism from the relayer's side. Relayer operators who rely on meta-transactions for gasless UX are financially harmed at scale, since this can be repeated per-transaction and is entirely reachable by a single unprivileged sender crafting a signed delegate action, requiring no special privileges beyond normal account signing.

### Likelihood Explanation
Likelihood is high for any operator running a meta-transaction relayer service: any sender can sign a `DelegateAction` including an inner action with an attached deposit that reliably fails at the receiver shard (e.g., targeting a non-existent receiver, insufficient contract state, or a `FunctionCall` to a method that always panics). No colluding validator or special permission is required — only a normal signed transaction from the sender and normal relaying by the relayer, i.e., it is directly reachable through the standard transaction/receipt pipeline described in `runtime/runtime/src/actions.rs` and `runtime/runtime/src/lib.rs`.

### Recommendation
Clarify and fix deposit-refund attribution for delegated (meta-transaction) receipts: when a receipt originates from a `Delegate`/`DelegateV2` action, the balance/deposit refund on failure should go back to the actual payer of the deposit (the relayer/original transaction signer) rather than unconditionally to `predecessor_id` (the delegating sender), or at minimum the relayer should be able to opt out / be protected via the existing `refund_to` mechanism (`promise_set_refund_to`) being set automatically for delegate-originated receipts. Document explicitly protocol-level guarantees so relayer implementations do not rely on an economically unsafe default.

### Proof of Concept
1. Relayer submits a `SignedTransaction` from itself containing `Action::Delegate(signed_delegate_action)` where `signed_delegate_action` is signed by Alice and contains an inner `Action::FunctionCall` (or `Action::Transfer`) with a non-zero `deposit`, targeting a receiver/method that is guaranteed to fail (e.g., non-existent method on the target contract).
2. The relayer's shard processes the outer receipt, `apply_delegate_action` runs (`runtime/runtime/src/actions.rs:453-534`), consumes relayer-prepaid gas/fees, and forwards a new receipt with `predecessor_id = Alice`, `receiver_id = target contract`, carrying the inner deposit-bearing action.
3. On the receiver shard, the inner action fails as designed; `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1400-1416`) generates a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, and `balance_refund_receiver()` (`core/primitives/src/receipt.rs:428-430`) resolves to `predecessor_id` = Alice.
4. Result: the deposit that was originally debited from the relayer's balance when constructing the outer receipt is credited to Alice's account instead of the relayer's, confirmed by the documented behavior in `docs/architecture/how/meta-tx.md:225-242`.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
