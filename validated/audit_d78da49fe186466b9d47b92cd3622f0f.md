## Title
Zero-Cost Asset Extraction via Rounding-to-Zero in TRX Market Order Matching — (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the maker's compensation (`makerBuyTokenQuantityReceive`) using integer-truncating division (`MarketUtils.multiplyAndDivide`), the same rounding-to-zero pattern as the reported Curve `debt = unsafe_div(debt * frac, 10**18)` bug. In the "taker == maker" branch of the matcher, this value is used to fully close out the maker's remaining order **without any zero-value check**, while the sibling "taker > maker" branch explicitly guards against the same rounding case. This asymmetry lets a counterparty's remaining sell-side balance be consumed while the payer's own sell balance is left untouched, extracting tokens for zero payment.

### Finding Description
`MarketUtils.multiplyAndDivide` performs `floorDiv(a*b, c)`, which truncates fractional results to zero exactly like the Curve `unsafe_div(debt * frac, 10**18)` pattern: [1](#0-0) 

In `matchSingleOrder`, when the taker's converted buy amount exactly equals the maker's remaining sell amount, the code takes the "equal" branch: [2](#0-1) 

Here `makerBuyTokenQuantityReceive` is computed via `multiplyAndDivide` and can truncate to `0` when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`. Unlike the "taker > maker" branch just below it, which explicitly checks `if (makerBuyTokenQuantityReceive == 0) { ...return remainder to maker... }`: [3](#0-2) 

the "equal" branch performs **no such check**. It unconditionally sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` (fully consuming/closing the maker's remaining tokens) and computes `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive`. When `makerBuyTokenQuantityReceive == 0`, `takerSellTokenLeft` equals the taker's original remaining sell amount — i.e. the taker's payment is never deducted — yet the taker still receives `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the maker's full remaining tokens) via `addTrxOrToken`.

### Impact Explanation
A concrete reachable configuration: a maker order with `sellTokenQuantity = 3`, `buyTokenQuantity = 2`, and remaining sell quantity `makerSellRemainQuantity = 1`. A taker sends `takerSellRemainQuantity = 1`. Then:
- `takerBuyTokenQuantityRemain = floorDiv(1*3, 2) = 1`, which equals `makerSellRemainQuantity` → the vulnerable "equal" branch is taken.
- `makerBuyTokenQuantityReceive = floorDiv(1*2, 3) = 0`.
- The maker's order is closed (`sellTokenQuantityRemain` set to `0`, removed from order book) while the taker's sell balance (`takerSellTokenLeft = 1 - 0 = 1`) is untouched.
- The taker still receives the maker's 1 token via `addTrxOrToken`.

This is asset/accounting corruption in the on-chain TRC10/TRX order-matching engine, reachable by any account broadcasting a `MarketSellAssetContract` transaction — no privileged role required.

### Likelihood Explanation
Exploitability depends on finding or engineering maker orders whose remaining quantity and price ratio satisfy `remain * buyQty < sellQty`, which arises naturally from partial fills over time on any order with a skewed price ratio, and can also be deliberately engineered by an attacker controlling both sides (two attacker-controlled accounts) to grind a target order down to the vulnerable dust remainder before sweeping it for free. This mirrors exactly the reported bug class (rounding a payment/debt term to zero to bypass cost), just applied to the market/exchange matching engine instead of a lending controller.

### Recommendation
Add an explicit zero-check for `makerBuyTokenQuantityReceive` in the "taker == maker" branch (mirroring the existing guard in the "taker > maker" branch), returning the un-compensated remainder to the maker (or rejecting the match) instead of unconditionally zeroing `makerOrderCapsule`'s remaining balance.

### Proof of Concept
1. Account A creates a sell order: `sellTokenId = A_token`, `sellTokenQuantity = 3`, `buyTokenId = "_"` (TRX), `buyTokenQuantity = 2`.
2. Through prior partial fills (or direct setup in a test harness), bring the order's `sellTokenQuantityRemain` down to `1`.
3. Account B (attacker) submits `MarketSellAssetContract` selling `1` TRX for `A_token` that matches against A's order (`takerSellRemainQuantity = 1`).
4. In `matchSingleOrder`: `takerBuyTokenQuantityRemain = floorDiv(1*3,2) = 1 == makerSellRemainQuantity(1)` → "equal" branch executes; `makerBuyTokenQuantityReceive = floorDiv(1*2,3) = 0`.
5. Result: maker's order fully closed (loses 1 `A_token` for 0 TRX), taker receives 1 `A_token` while `takerSellTokenLeft` remains `1` (taker's TRX untouched) — verifiable via `MarketOrderCapsule.getSellTokenQuantityRemain()` and account balances before/after, as done in existing tests such as [4](#0-3) .

    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);

      // do nothing here, because we will use BigInteger to compute again
    }

  }
