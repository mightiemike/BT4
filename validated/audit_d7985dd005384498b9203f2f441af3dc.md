### Title
Receipt Size Limit Bypass via Post-Validation `output_data_receivers` Mutation in `promise_return` Path — (`File: runtime/runtime/src/lib.rs`)

---

### Summary

In `apply_action_receipt`, newly created receipts are validated against `max_receipt_size` (4 MiB) immediately after each action executes. However, when a contract uses `promise_return`, the runtime subsequently appends the parent receipt's `output_data_receivers` directly into the child receipt's action struct — **after** the size check has already passed. This post-validation mutation can push the child receipt's borsh-serialized size above `max_receipt_size`, producing an oversized receipt that is forwarded cross-shard and included in `ChunkStateWitness`. The bug is acknowledged in the codebase as issue #12606 and has a live workaround in the congestion-control forwarding path, confirming it is reachable in production.

---

### Finding Description

**Validation point** — `runtime/runtime/src/lib.rs` lines 867–878:

```rust
if new_result.result.is_ok() {
    if let Err(e) = new_result.new_receipts.iter().try_for_each(|receipt| {
        validate_receipt(
            &apply_state.config.wasm_config.limit_config,

```

`validate_receipt` in `NewReceipt` mode computes `borsh::object_length(receipt)` and rejects anything above `limit_config.max_receipt_size` (4,194,304 bytes).

**Post-validation mutation** — `runtime/runtime/src/lib.rs` lines 1031–1049:


When a contract calls `promise_return(promise_c)` and the parent receipt has non-empty `output_data_receivers` (i.e., it is itself a callback target), the runtime splices those receivers into receipt C's `output_data_receivers` field. Each `DataReceiver` is `{ data_id: CryptoHash (32 B), receiver_id: AccountId (variable) }`. Adding even one receiver to a receipt that was validated at exactly `max_receipt_size` produces a receipt that exceeds the limit.

A second variant exists on the **value-return path** (lines 1056–1068): when a contract returns a value of size `max_length_returned_data` (also 4 MiB), the runtime wraps it in a `DataReceipt` inside a `Receipt::V0`. The borsh envelope overhead (predecessor/receiver account IDs, receipt discriminant, `data_id` hash, length prefix) pushes the serialized size above `max_receipt_size` without any size check on the resulting `DataReceipt`-wrapped receipt.

**Workaround confirming reachability** — `runtime/runtime/src/congestion_control.rs` lines 413–427:

```rust
// There is a bug which allows to create receipts that are above the size limit.
// See https://github.com/near/nearcore/issues/12606
let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
if size > max_receipt_size {
    size = max_receipt_size;   // clamp to prevent receipts getting stuck
}
```

The `ExistingReceipt` mode in `validate_receipt` (verifier.rs lines 573–585) explicitly skips the size check and documents the same bug, so oversized receipts are accepted and executed by receiving shards.

---

### Impact Explanation

An unprivileged user deploys a contract that:
1. Creates a callback chain `A.then(B)` so that receipt A has a non-empty `output_data_receivers`.
2. Inside A's execution, creates a near-maximum-size receipt C (borsh length = `max_receipt_size`) and calls `promise_return(C)`.
3. The runtime appends A's `output_data_receivers` into C after validation, producing a receipt whose borsh length exceeds `max_receipt_size`.

The oversized receipt is forwarded cross-shard (the congestion-control workaround prevents it from being stuck but does not drop it), included in `ChunkStateWitness`, and processed by the receiving shard under `ExistingReceipt` mode. This inflates `ChunkStateWitness` beyond the intended 17 MiB ceiling documented in `docs/misc/state_witness_size_limits.md`. Repeated triggering can degrade stateless-validation throughput and cause chunk validators to time out on witness distribution — a non-network-level DoS fixable without a hardfork.

---

### Likelihood Explanation

The attack requires only a deployed contract and a function call — no privileged role, no validator access, no key compromise. The contract logic needed (`promise_create` + `promise_then` + `promise_return` with large args) is expressible in any NEAR SDK. The bug is already confirmed by two integration tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) that assert oversized receipts do appear in the chain. Likelihood is **high** for a motivated attacker.

---

### Recommendation

After `result.merge(new_result)` and after the `output_data_receivers` splice (lines 1031–1049), re-validate the mutated receipt's size before it is forwarded:

```rust
// After extending output_data_receivers:
let mutated_receipt = result.new_receipts.get(receipt_index as usize).unwrap();
let new_size: u64 = borsh::object_length(mutated_receipt).unwrap()
    .try_into().expect("receipt size overflow");
if new_size > limit_config.max_receipt_size {
    result.result = Err(ActionErrorKind::NewReceiptValidationError(
        ReceiptValidationError::ReceiptSizeExceeded {
            size: new_size,
            limit: limit_config.max_receipt_size,
        }
    ).into());
}
```

Apply the same post-construction size check to `DataReceipt`-wrapped receipts created on the value-return path (lines 1056–1068). Once the fix is in place, the `ExistingReceipt` size-skip and the congestion-control clamping workaround can be removed in a follow-up protocol upgrade.

---

### Proof of Concept

The existing integration test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` (lines 129–208) is a complete, runnable PoC:

1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_promise_return_method1` with `args_size = max_receipt_size − base_receipt_size`. This creates the promise DAG `A → B` where A internally does `promise_return(C)` and C's borsh size equals exactly `max_receipt_size`.
3. The runtime appends A's `output_data_receivers` into C after validation.
4. `assert_oversized_receipt_occurred` walks the chain and finds a receipt with `borsh::object_length > max_receipt_size` in the incoming receipt proofs — confirming the bypass.

```rust
fn test_max_receipt_size_promise_return() {

                deposit: Balance::ZERO,
```
