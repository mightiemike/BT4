## Title
`ensure_match_transaction_info` silently skips state-checkpoint hash verification, allowing corrupted committed state to pass replay-verify - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the sole integrity check used by `db-tool`'s `replay_on_archive` (and `aptos-debugger`) to validate that re-execution reproduces the authenticated, on-chain committed state — verifies transaction status, gas used, write-set hash, and event root hash, but **does not verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`** against the recomputed state. This is called out explicitly in the code's own TODO comment.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks:
- execution status (`self.status() == expected_txn_status`)
- gas used
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

It explicitly does **not** check the state-checkpoint hash fields, with the code's own comment stating: [2](#0-1) 

This function is the only correctness gate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` per output: [3](#0-2) . Because the checkpoint hash (the Sparse-Merkle-Tree root summarizing world state, and — per the newer field — the "trading-native"/position-state checkpoint root) is never compared, a divergence between locally recomputed world state and the state actually committed and signed into the authenticated `TransactionInfo`/ledger accumulator is **not detected** by this tool. `aptos-move/aptos-debugger/src/aptos_debugger.rs` also relies on the same function for its own replay/diff tooling.

### Impact Explanation
`state_checkpoint_hash` (and its V1 sibling `position_state_checkpoint_hash`, guarded by the `compute_trading_native_state_roots` on-chain config flag visible in `types/src/block_executor/config.rs` and `execution/executor-types/src/execution_output.rs`) is the authenticated summary of the entire Sparse Merkle world state / trading-native state root at that version — it is exactly the proof-integrity value that Merkle proofs and state-sync bootstrapping rely on being correct. A tool whose job is to prove "replay matches the authenticated chain" that silently omits this check means:
- A hard-fork-only or non-deterministic VM/storage bug that corrupts the world-state root (but leaves write-set bytes, gas, status and events unchanged, or where the divergence happens purely in checkpoint materialization) would pass `replay_on_archive` verification even though the actual state root committed on-chain diverges from what local execution now produces.
- This directly undermines the guarantee that "committed state differs from the correct VM result" detection tooling actually detects such differences — a false "verified" result for state root corruption.

This satisfies the required impact class (proof-integrity/replay verification silently accepting a wrong root), though the severity is bounded because this is a diagnostic/replay-verify tool rather than the live consensus commit path itself; it does not corrupt consensus-committed data by itself but defeats the tool meant to detect state-commit corruption bugs, which is a meaningful integrity gap for hard-fork-only divergence detection.

### Likelihood Explanation
The gap is deterministic and unconditional — every call to `ensure_match_transaction_info` (whenever invoked, including from `replay_on_archive` and `aptos_debugger`) skips checkpoint-hash validation, not merely under rare conditions. It requires no privileged access to trigger; it's an inherent property of the verification tool's logic. The comment in the source shows the maintainers are aware but have not fixed it as of this snapshot, which is why `replay_on_archive`/`replay-verify` cannot be relied upon to catch state-root divergence bugs.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the recomputed `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` (when `Some`) against `txn_info`'s corresponding fields, returning an error on mismatch, before enabling reliance on `compute_trading_native_state_roots` or trusting `replay_on_archive` as a state-root integrity check.

### Proof of Concept
1. Run `replay_on_archive` (or `aptos-debugger`) against an archived version range where the VM/storage produces a write-set, gas, status, and events identical to what's recorded, but the resulting Sparse Merkle Tree checkpoint root differs from the authenticated `state_checkpoint_hash` in the backed-up `TransactionInfo` (e.g. due to a state-store/JMK materialization bug that doesn't affect the write-set bytes themselves).
2. `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs:392-405` calls `ensure_match_transaction_info`, which checks status/gas/write_set_hash/event_root_hash only, per [4](#0-3) .
3. Since none of the four checked fields differ, the function returns `Ok(())`, and the divergent state-checkpoint root is never reported as a failed transaction — `replay_on_archive` reports success despite the state root mismatch.

Note: I was unable to fully trace whether `state_checkpoint_hash` is independently verified elsewhere in the live consensus/execution commit path (e.g., in `execution/executor/src/chunk_executor/mod.rs` or `db_bootstrapper/mod.rs`) within the remaining investigation budget; if such a check exists on the primary commit path, the impact is confined to the `replay_on_archive`/`aptos-debugger` tooling as described above rather than consensus-level state-commit integrity.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
