### Title
Liquidity cap on bridged tokens is stored but never enforced during PRC20 minting - (File: x/uexecutor/keeper/handler.go, x/uexecutor/keeper/evm.go)

### Summary
This is a native analog of the `mintableSupply` bug class: `TokenConfig.LiquidityCap` [1](#0-0)  is documented as the "max supply cap for this token" and is validated only for non-emptiness of its string format, never compared against a running total before Push Chain mints PRC20 representations of bridged inbound funds.

### Finding Description
`x/uregistry` accepts `LiquidityCap` as part of `TokenConfig` and only checks that the string is non-empty in `ValidateBasic`: [2](#0-1) 

On the execution side, when an inbound deposit is finalized by honest Universal Validators, `x/uexecutor` calls `depositPRC20`, which resolves the token config and mints PRC20 via `CallPRC20Deposit`/`DerivedEVMCall` with no reference to `LiquidityCap` anywhere in the mint path: [3](#0-2) [4](#0-3) 

Grepping the entire `x/uexecutor` keeper package for `LiquidityCap` returns zero matches, confirming the field is read nowhere in the deposit, `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, or `ExecuteInboundGasAndPayload` code paths. `ExecuteInboundFunds` unconditionally deposits `inbound.Amount` regardless of any configured cap: [5](#0-4) 

This means the on-chain Push Chain node code has no mechanism to track cumulative minted PRC20 supply per token against `LiquidityCap`, so an ordinary unprivileged user who repeatedly deposits (or has honest UVs observe) funds on the source chain can cause Push Chain to mint PRC20 far beyond the intended cap — this is directly analogous to the `VariableSupplyERC20Token::mint` bug where the cap variable exists in state but the enforcement logic is missing/broken.

### Impact Explanation
Unbounded PRC20 minting corrupts the accounting invariant between external-chain locked collateral and Push Chain's synthetic PRC20 representation. If the intended design is that PRC20 supply for a given token must never exceed `LiquidityCap` (e.g., to bound risk exposure or backing-collateral assumptions), the missing check allows synthetic asset over-issuance reachable purely from ordinary user deposits, matching the "corruption of PRC20 or native asset accounting" and "unauthorized mint" categories in scope.

### Likelihood Explanation
High, if `LiquidityCap` is intended to be an actively enforced ceiling rather than purely informational metadata: the only actions needed are ordinary user deposits on a supported source chain, which are then routed automatically through `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload` by honest, non-privileged validator voting — no admin/governance/relayer collusion is required.

### Recommendation
Track cumulative minted PRC20 supply per `chain:address` token key (e.g., a new keeper collection in `x/uregistry` or `x/uexecutor`), and in `depositPRC20`/`CallPRC20Deposit`/`CallPRC20DepositAutoSwap`, verify `runningMintedSupply + amount <= LiquidityCap` before issuing the `DerivedEVMCall`; reject or queue-for-refund inbound deposits that would exceed the cap, mirroring the `totalSupply + amount <= mintableSupply` fix pattern from the report.

### Proof of Concept
1. Register a `TokenConfig` with `LiquidityCap = "1000000"` for `eip155:11155111` USDC (as e2e/integration tests do, e.g. [6](#0-5) ).
2. Submit repeated inbound deposits (via honest UV votes, `MsgVoteInbound`) each with `Amount` up to arbitrarily large values, or many deposits summing well past `1000000`.
3. Each is processed by `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit`, minting PRC20 to the recipient with no check against `LiquidityCap` at any point in the Go-side keeper code.
4. Query the PRC20 `balanceOf`/aggregate supply — total minted PRC20 for that token config exceeds `LiquidityCap` with no error or rejection.

**Note on verification limits:** the actual PRC20/UniversalCore Solidity contracts (`depositPRC20Token`, etc.) referenced from `x/uexecutor/keeper/evm.go` live in a separate contracts repository (`core-contracts`, per `DERIVED_TRANSACTIONS.md` [7](#0-6) ) that is not present in this indexed repository. I was unable to confirm or rule out that the cap is instead enforced inside the Solidity contract itself; no `.sol` files were found in this repo's index at all. If a Devin session with full filesystem/contract access confirms the cap is enforced on-chain in Solidity, this finding should be downgraded/rejected. I recommend starting a full Devin session (with access to the `core-contracts` repo and its EVM contracts) to verify whether `LiquidityCap` enforcement exists at the Solidity layer before treating this as confirmed exploitable.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

func (k Keeper) ExecuteInboundFunds(ctx context.Context, utx types.UniversalTx) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("execute inbound funds: depositing PRC20",
		"utx_key", utx.Id,
		"source_chain", inbound.SourceChain,
		"recipient", inbound.Recipient,
		"amount", inbound.Amount,
		"is_cea", inbound.IsCEA,
	)

	receipt, err := k.depositPRC20(
		sdkCtx,
		inbound.SourceChain,
		inbound.AssetAddr,
		common.HexToAddress(inbound.Recipient), // recipient is inbound recipient
		inbound.Amount,
	)
