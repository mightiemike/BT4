The reported issue is a smart-contract-specific design flaw: a centralized `whenNotPaused` modifier controlled by a privileged admin blocks withdrawals in the Carapace `ProtectionPool.sol`. This is a contract-level admin/pause-toggle pattern that has no reachable analog in `nearcore` triggerable by an unprivileged transaction signer, contract deployer, meta-transaction sender, staker, or RPC caller.

I searched for pause-like mechanisms that could block user-initiated withdrawals/unstaking (`grep_search` for `is_paused`, `pause_sync`, `halt`, and semantic searches on staking withdrawal and protocol-upgrade gating). The closest constructs found are:
- Unstaking/staking lifecycle logic in `chain/epoch-manager` and `runtime/runtime`, which is governed by deterministic epoch-boundary rules, not an admin-togglable pause [1](#0-0) .
- Protocol version gating (`ProtocolFeature::enabled`), which is monotonic, validator-vote-driven, and not a pause switch reachable by a single unprivileged transaction [2](#0-1) .
- Adversarial/test-only chunk production modes (`AdvProduceChunksMode`), which are test-feature/operator-only and explicitly out of scope [3](#0-2) .

None of these constitute an unprivileged-reachable, admin-controlled pause that would freeze user withdrawals or funds, so there is no valid analog matching the required output criteria (unauthorized value movement, supply inflation, fee/gas bypass, state-root divergence, invalid state transition acceptance, receipt loss/duplication, permanently frozen funds, or transaction-triggered halt caused by an unprivileged actor).

```markdown
### Returning stake

`locked` is the number of tokens locked for staking, it's computed the following way:

- initially it's the value in genesis or `0` for new accounts
- on a staking proposal with a value higher than `locked`, it increases to that value
- at the start of each epoch it's recomputed:
    1. consider the most recent 3 epochs
    2. for non-slashed accounts, take the maximum of their stakes in those epochs
    3. if an account made a proposal in the block that starts the epoch, also take the maximum with the proposal value
    4. change `locked` to the resulting value (and update `amount` so that `amount + locked` stays the same)
```

```markdown
## Invariants & failure modes

- **Monotonic activation**: a feature enabled at version V is enabled at all `>= V` (`enabled` uses `>=`, `version.rs:591`). There is no de-activation mechanism; deprecated features remain enabled forever.
- **Config lookup must have a floor**: `get_config` panics `"Not found RuntimeConfig for protocol version {}"` if no stored key `<=` version exists (`config_store.rs:244`). Key `0` always exists, so any `version >= 0` is safe.
- **Diff chain integrity**: `apply_diff` errors (`WrongOldValue` etc., `parameter_table.rs:545`) if a diff's declared `old` value disagrees with the accumulated table — construction panics at startup rather than serving a wrong config (`config_store.rs:124-129`). A test asserts every `CONFIG_DIFFS` version has a matching yaml file and vice-versa (`all_configs_are_specified`, `config_store.rs:272`).
- **Schedule well-formedness**: the schedule must end at the client version and be strictly monotone in time and +1 in version, else `new_from_env_or_schedule` returns an error that `get_protocol_upgrade_schedule` `.unwrap()`s into a panic at startup (`version.rs:80-85`, `upgrade_schedule.rs:95-120`).
- **Version support floor**: `assert_supported_protocol_version` panics `"protocol version {v} is below minimum supported {MIN}"` for `< 83` (`core/primitives-core/src/version.rs:620-625`); view-only paths instead clamp up via `clamp_to_supported_protocol_version` (`version.rs:610-614`).
- **Under-voting ⇒ kickout**: validators announcing a version below the network's next version are kicked (`ProtocolVersionTooOld`, `chain/epoch-manager/src/lib.rs:595`). A minority (≤20% stake) voting for a new version cannot advance it — threshold is strict `>` (`lib.rs:577`).
```
