### Title
Unbounded per-cycle loop in the pre-optimization reward path lets an account's own `WithdrawReward`/`VoteWitness`/`Unfreeze` transaction grow without bound and become permanently un-executable - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.withdrawReward()` — invoked by ordinary, unprivileged account actions such as voting, unfreezing and withdrawing rewards — computes a voter's reward with `computeReward(beginCycle, endCycle, accountCapsule)`. When the "old reward optimization" flag (`ALLOW_OLD_REWARD_OPT`) has not been activated by governance (its default value is `0`), this delegates to `getOldReward()`, which iterates once per maintenance cycle between the account's last-processed cycle and the current cycle, with a nested per-vote loop inside each iteration. Because the number of maintenance cycles grows monotonically with wall-clock time (one cycle every `maintenanceTimeInterval`, default 6 hours) and is *never capped*, the size of this loop for an account that has not interacted with the chain for a long stretch (or that started voting before the "new reward algorithm" was enabled) grows unbounded, in exactly the same way `DyadXPv2.initialize()`'s loop over `dnftSupply` grows unbounded with the DNFT count. This is the same "loop bound tied to unbounded on-chain/temporal state" bug class as the referenced report.

### Finding Description
`VoteRewardUtil`/`MortgageService` compute rewards over the span `[beginCycle, endCycle)`: [1](#0-0) 

For any part of that span that lies before `newAlgorithmCycle`, and unless the `allowOldRewardOpt` governance flag has been switched on, the reward is computed by iterating **once per maintenance cycle**: [2](#0-1) 

```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
}
```

Each iteration of that outer loop itself iterates over the account's up-to-30 votes (`computeReward(cycle, votes)` at lines 171-188), so the total work is `O((endCycle - beginCycle) * votes.size())`. `allowOldRewardOpt` defaults to `0` (disabled) both in `CommonParameter`/`CommitteeConfig` and in `reference.conf`, and can only be turned on via a committee (governance) proposal that itself requires `allowNewRewardAlgorithm`/`allowNewReward`/`allowTvmVote` to already be enabled first: [3](#0-2) [4](#0-3) 

Until that (optional) proposal passes, this unbounded loop is the live, default execution path for `withdrawReward()`, which is called by ordinary, unprivileged users through normal actuators, e.g. `VoteWitnessActuator.countVoteAccount()`: [5](#0-4) 

and equivalently through `MortgageService.withdrawReward()`'s public entry point used by unfreeze/withdraw contracts: [6](#0-5) 

This mirrors the report's root cause precisely: a loop whose bound is a piece of state that only grows (DNFT supply in the report; elapsed maintenance cycles here), executed synchronously inside a single call/transaction with no batching, chunking, or pagination.

### Impact Explanation
An account that votes (or otherwise accrues a non-zero `beginCycle`) and then does not call any action that invokes `withdrawReward()` for a very long period accumulates a growing `endCycle - beginCycle` gap. When it finally does interact (vote again, unfreeze, or explicitly withdraw rewards), the actuator executes `getOldReward()`'s per-cycle loop for the entire gap. As the gap grows, the single transaction's runtime/resource consumption grows linearly and can eventually exceed practical processing limits for a single transaction inside block generation/validation, causing the transaction to repeatedly fail or be rejected — permanently blocking that account's ability to withdraw its own rewards, cast new votes, or unfreeze/undelegate resources tied to voting cleanup, i.e., a self-inflicted but real denial-of-service / fund-lock condition analogous to the reported "initialization becomes impossible" bug. This is a concrete, non-trusted-role, in-scope reachable code path (regular vote/unfreeze/withdraw actuators), not a mocked or purely theoretical construct.

### Likelihood Explanation
Likelihood is conditioned on the `ALLOW_OLD_REWARD_OPT` proposal not yet being active for the affected cycle range, which is the *default* on-chain configuration unless/until the community proposes and passes it. Any account that voted prior to `newAlgorithmCycle` and lets a large number of maintenance cycles elapse (6 hours per cycle by default, so a multi-year lull is on the order of thousands of cycles) before next touching vote/withdraw/unfreeze actuators will trigger the growing loop. This does not require any privileged action from the victim or an attacker; it is purely a function of elapsed chain time and normal user behavior (dormant voters), matching the report's "High" likelihood framing once the DNFT-count analog (here: elapsed cycles) grows large enough.

### Recommendation
- Ensure `getOldReward()`'s linear per-cycle loop is bounded, e.g., by proactively/automatically applying the cached Vi-based algorithm (`RewardViCalService`) regardless of the `allowOldRewardOpt` governance switch, or by capping/chunking the cycle range processed per transaction with the ability to resume across multiple transactions.
- Alternatively, make `allowOldRewardOpt` (or an equivalent optimization) mandatory/always-on rather than opt-in via proposal, since the unabridged path is unsafe by default for accounts with large idle periods.
- Add an explicit safety check/early precomputation step so that `withdrawReward()` cannot silently balloon into an unbounded-cost operation for a single caller-initiated transaction.

### Proof of Concept
Deterministic PoC requires simulating multi-year cycle progression, which cannot be executed via static analysis. The vulnerable mechanics are demonstrated directly by the code path:
1. Vote as an account before `newAlgorithmCycle` (`VoteWitnessActuator`/`VoteWitnessProcessor`), setting `beginCycle` far in the past.
2. Advance `dynamicPropertiesStore.getCurrentCycleNumber()` by many thousands of maintenance cycles without the account calling any reward/vote/unfreeze action, and without `ALLOW_OLD_REWARD_OPT` having been enabled.
3. Call `withdrawReward()` (via `WithdrawBalanceContract`, `VoteWitnessContract`, or `UnfreezeBalanceContract`); observe that `getOldReward()` executes a loop of size `endCycle - beginCycle`, with cost scaling linearly and unboundedly with the number of elapsed cycles — the same growth pattern as the reported `DyadXPv2.initialize()` loop over `dnftSupply`.   private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
