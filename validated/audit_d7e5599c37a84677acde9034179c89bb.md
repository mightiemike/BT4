### Title
Unbounded recursion in `get_recursive_transaction_results` allows a crafted transaction to crash the RPC/view-client process via stack overflow - (File: chain/chain/src/chain.rs)

### Summary
`get_recursive_transaction_results` in `chain/chain/src/chain.rs` walks the receipt tree produced by a transaction by recursively calling itself once for every `receipt_id` found in each execution outcome, with no maximum recursion-depth guard and no iterative/worklist implementation. [1](#0-0)  This function is the core of `get_final_transaction_result`, which builds the `FinalExecutionOutcomeView` returned by the JSON-RPC `tx` / `EXPERIMENTAL_tx_status` methods. [2](#0-1)  Because receipt-chain depth is only bounded by gas economics rather than an explicit protocol-level depth limit, an attacker can submit a single transaction that produces a very long chain of receipts (e.g. via self-recursive cross-contract promise calls, as demonstrated by the test contract's `max_self_recursion_delay`/`recurse` methods used in `test_evil_deep_recursion` and `slow_test_self_delay`). [3](#0-2) [4](#0-3)  When any RPC caller later queries the transaction's status, the recursive result-collection walks the whole receipt chain and can exhaust the call stack, crashing the node process that serves RPC.

### Finding Description
`get_recursive_transaction_results` fetches the outcome for a receipt id, appends it to `outcomes`, and then, for each `receipt_id` recorded in that outcome (i.e., each receipt spawned by processing the previous one), recursively calls itself again:
```
for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
    let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
    self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
}
``` [5](#0-4) 

There is no `max_depth` parameter, no iterative stack/queue rewrite (unlike other trie-traversal code in the codebase which was explicitly rewritten to avoid "potential stack overflows", e.g. `get_subtree_size` in `core/store/src/trie/trie_recording.rs`), and no cap on total outcomes collected before this function is called. This contrasts with the RPC's `ReceiptToTx` lookup, which enforces `RECEIPT_TO_TX_MAX_DEPTH` explicitly to bound recursion/iteration depth. [6](#0-5)  No analogous depth bound exists for `get_recursive_transaction_results`/`get_final_transaction_result`.

Receipt-chain depth in NEAR is not directly protocol-limited by a receipt-count/depth cap; it is only limited indirectly by gas economics (each hop consumes gas from the transaction's prepaid gas budget). A contract author fully controls this, as shown by the evil-contract test suite that specifically creates self-recursive cross-contract calls to maximize receipt chain depth within the gas budget (observed depths up to ~221 in the existing test, and this is only the executor-side WASM recursion limit test — cross-contract, block-spanning receipt chains driven by promises are not limited by a fixed protocol depth constant analogous to `RECEIPT_TO_TX_MAX_DEPTH`). [7](#0-6) 

The `tx`/`EXPERIMENTAL_tx_status` RPC entry point (any unauthenticated/any unprivileged RPC caller can invoke it for any known transaction hash) eventually reaches `Chain::get_final_transaction_result`, which unconditionally recurses over the full depth of the receipt tree.

### Impact Explanation
An unprivileged transaction sender can construct a transaction that spawns a long, single-branch chain of cross-contract receipts (self-recursive promises). Any subsequent RPC query for that transaction's status (which any RPC caller can trigger, including the attacker themselves) causes `get_recursive_transaction_results` to recurse to a depth proportional to the receipt chain length. Because this function has no depth ceiling and recurses per receipt without tail-call elimination, a sufficiently deep receipt chain will exhaust the thread stack and crash the process, causing a transaction-triggered halt/denial-of-service of the RPC/view-client component of any full node (validator, RPC node, or indexer) that serves `tx`/`EXPERIMENTAL_tx_status` for the affected transaction. This can degrade or take down RPC endpoints repeatedly and reproducibly for any node querying the crafted transaction, which is a legitimate reachable-from-a-single-transaction availability impact analogous to the reported ammonia uncontrolled-recursion CVE (stack exhaustion during recursive tree walking of attacker-influenced data).

### Likelihood Explanation
Likelihood is High for triggering the code path (crafting a deep receipt chain via cross-contract self-calls is straightforward and demonstrated in-repo by test helper contracts), but the severity depends on how deep a chain can practically be constructed within gas/economic constraints and how large the platform stack frame per recursive call is. This could not be fully confirmed without deeper investigation into: 
- The exact per-hop overhead (gas cost) for the cheapest possible receipt in a promise chain across multiple blocks, and thus the maximum feasible receipt-chain length attainable by a single funded transaction; and
- Whether any config (e.g., `save_tx_outcomes` requirements, GC/retention limits) constrains how far back such a chain can be queried.

These are areas the automated search could not conclusively verify from static code alone and would need dynamic/runtime confirmation (e.g., via a background agent building an actual devnet reproduction). The presence of intentional, explicit depth-limiting elsewhere in the same codebase for structurally similar recursive/iterative graph walks (e.g., `RECEIPT_TO_TX_MAX_DEPTH`, and the explicit non-recursive rewrite of `get_subtree_size` "to avoid any potential stack overflows") strongly suggests this is a recognized bug class in this codebase that was fixed elsewhere but missed here.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative implementation using an explicit worklist/queue (as already done for other node/graph traversals in this codebase, e.g. `get_subtree_size`), and/or add an explicit maximum depth or maximum total outcomes bound (analogous to `RECEIPT_TO_TX_MAX_DEPTH`) that fails gracefully with a bounded error instead of recursing without limit.

### Proof of Concept
1. Deploy a contract exposing a self-recursive cross-contract call chain (e.g. reuse the existing `max_self_recursion_delay` pattern from `runtime/near-test-contracts/test-contract-rs/src/lib.rs`, lines 887–921) and submit a transaction invoking it with maximum prepaid gas, so that it produces the deepest achievable single chain of receipts across multiple blocks.
2. Wait for the transaction's receipt chain to fully execute (or query mid-flight if `require_all_outcomes=false` variants are also reachable).
3. Issue a `tx` or `EXPERIMENTAL_tx_status` JSON-RPC request for the original transaction hash against a full/RPC node.
4. Observe that `Chain::get_final_transaction_result` → `get_recursive_transaction_results` recurses to the depth of the receipt chain; with a sufficiently deep chain this is expected to overflow the call stack and crash the node's process handling the RPC/view-client request. Exact minimum depth needed to overflow the stack was not empirically measured in this analysis and would require running the described PoC on a live/test node to confirm.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Returns FinalExecutionOutcomeView for the given transaction.
    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
