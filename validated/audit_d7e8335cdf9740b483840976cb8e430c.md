### Title
Reward-per-vote calculated with double-precision truncates fractional rewards on every cycle, causing systematic staker underpayment — (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The old SR voting-reward algorithm in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each voter's share of a witness's cycle reward using floating-point division (`voteRate = (double) userVote / totalVote`) and then accumulates it into a `long reward`. Just like the `StakingRewards.notifyRewardAmount` rounding-down bug described in the report, this per-unit rate calculation truncates fractional SUN on every single voting cycle, and the effect compounds because it is executed once per cycle, per witness, per voter, for the lifetime of the delegation.

### Finding Description
`computeReward(long cycle, List<Pair<byte[], Long>> votes)` is the "old" (pre-VI) reward algorithm: [1](#0-0) 

For every SR a voter voted for, it computes `voteRate = userVote / totalVote` as a `double` and multiplies by `totalReward`, adding the (truncated) result into a `long reward` accumulator. This is functionally identical to the reported bug pattern: a per-unit rate is derived via division that discards the remainder, and that discarded remainder is never recovered or redistributed anywhere — it is simply lost from the witness's `totalReward` pool for that cycle.

This routine is reachable through `getOldReward`, which is invoked from `computeReward(beginCycle, endCycle, accountCapsule)`, which is the core routine backing `withdrawReward`/`queryReward` — both called for every account/voter reward withdrawal on the chain: [2](#0-1) [3](#0-2) 

`getOldReward` falls back to the per-cycle double-based `computeReward(cycle, votes)` loop unless `ALLOW_OLD_REWARD_OPT` is enabled (a governance-gated on-chain parameter, default 0 in `reference.conf`), in which case it instead delegates to the fixed-point BigInteger VI-based algorithm in `RewardViCalService.getNewRewardAlgorithmReward`: [4](#0-3) 

Unlike the fixed-point `DECIMAL_OF_VI_REWARD`-scaled BigInteger arithmetic used by the newer algorithm (`DelegationStore.accumulateWitnessVi`, `RewardViCalService.accumulateWitnessVi`), the old per-cycle `double` calculation has no scaling factor to preserve sub-unit precision, and truncation losses accumulate across every cycle for the entire time a chain runs with `ALLOW_OLD_REWARD_OPT = 0` (the default) or before the corresponding hard fork/proposal is enabled on a given network.

### Impact Explanation
On any network (mainnet, private chain, or testnet) where `ALLOW_OLD_REWARD_OPT` has not been enabled by committee proposal, every reward withdrawal computed through the old algorithm systematically underpays voters by the sum of per-cycle floating-point truncation. Because rewards are computed and truncated per cycle, per SR, per voter, over potentially thousands of cycles, the aggregate lost rewards can become significant — directly mirroring the reported bug class where "the effect of the rounding is multiplied by the duration." This causes accounting/asset corruption for the staking reward pool: value that should have accrued to voters is neither paid to them nor explicitly reserved, so it is effectively burned/lost from circulation without record.

### Likelihood Explanation
This is reachable by any anonymous account: calling `WithdrawBalanceContract`/vote-reward withdrawal (`MortgageService.withdrawReward`/`queryReward`) or the corresponding TVM `VoteRewardUtil` reward-query paths trigger this computation without any privileged role. The vulnerable code path is the *default* behavior since `ALLOW_OLD_REWARD_OPT` defaults to `0`/disabled per `common/src/main/resources/reference.conf` line 853, so it is highly likely to be exercised, especially on any network that hasn't yet passed the specific governance proposal to switch to the optimized VI-based path for old cycles.

### Recommendation
Replace the `double`-based `voteRate` calculation in `MortgageService.computeReward(long cycle, ...)` with a fixed-point/BigInteger calculation analogous to the VI-based algorithm (e.g., scale `userVote * totalReward` before dividing by `totalVote`, similar to `DECIMAL_OF_VI_REWARD` usage), or accumulate and carry forward remainders per witness/cycle so truncated fractions are not permanently lost. Alternatively, make `ALLOW_OLD_REWARD_OPT` the default so all old-cycle reward computations always route through the BigInteger VI-based `getNewRewardAlgorithmReward` path rather than the double-precision fallback.

### Proof of Concept
1. Deploy/observe a network where `ALLOW_OLD_REWARD_OPT` has not been enabled (default `0`).
2. A witness accrues `totalReward` for a cycle, and multiple voters split votes such that `userVote / totalVote` is a fraction with poor floating-point representation (e.g., small integer ratios that don't divide evenly).
3. Call `MortgageService.withdrawReward`/`queryReward` (or the TVM `VoteRewardUtil.withdrawReward`) which internally invokes `getOldReward` → `computeReward(cycle, votes)`.
4. Observe that `reward` for each voter is truncated at line `reward += voteRate * totalReward;` [5](#0-4) , and summing all voters' rewards across many cycles yields a total strictly less than the sum of witness `totalReward` values recorded in `delegationStore`, with the shortfall growing with the number of cycles (duration), matching the reported bug's core mechanism.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
