Based on my investigation, this bug class (manipulating a derived metric using cost-free/zero-weight inputs to distort a fee/throttling mechanism) does have a genuine, explicitly-documented analog in nearcore's congestion-control system: `Data`, `PromiseResume`, and `GlobalContractDistribution` receipts are hard-coded to `Gas::ZERO` congestion gas, meaning a user can generate receipts that occupy delayed/outgoing-buffer space and consume shard bandwidth/memory while contributing nothing to the congestion metric that throttles other users' gas allowances.

### Title
Zero-congestion-gas receipts (Data/PromiseResume/GlobalContractDistribution) let an attacker distort per-shard congestion metrics used for gas throttling - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`compute_receipt_congestion_gas` assigns `Gas::ZERO` congestion gas to `Data`, `PromiseResume`, and `GlobalContractDistribution` receipts, while their `receipt_bytes` still count toward `memory_congestion` in `CongestionInfo`. [1](#0-0)  Because congestion is used to compute `outgoing_gas_limit`, which throttles gas that legitimate users' action receipts can consume when forwarded to a shard, an actor who can cheaply generate a large volume of these zero-gas-cost, byte-heavy receipts can push a target shard's congestion level up via the `memory_congestion` dimension without incurring the gas cost normally required to raise congestion, and without other senders being able to "see" that cost reflected in `delayed_receipts_gas`/`buffered_receipts_gas`.

### Finding Description
`CongestionControl::congestion_level` takes the max of four normalized fractions: incoming (delayed gas), outgoing (buffered gas), memory (receipt bytes), and missed-chunks. [2](#0-1)  The memory dimension is driven purely by `receipt_bytes`, independent of the (zero) congestion gas value assigned to `Data`/`PromiseResume`/`GlobalContractDistribution` receipts. The code comment for `Data` receipts explicitly states the "congestion control MVP does not account for data receipts or postponed receipts," and similarly for `PromiseResume`. [3](#0-2)  `outgoing_gas_limit(sender_shard)` interpolates between `max_outgoing_gas` and `min_outgoing_gas` based on `congestion_level`, and forces `Gas::ZERO` for non-allowed senders once fully congested. [4](#0-3)  Since Data receipts are naturally produced as the output of ordinary function-call return values (`ft_transfer_call`-style callbacks, cross-contract call outputs) and PromiseResume receipts are produced by `promise_yield_resume` host calls, a contract account under attacker control can be made to emit an outsized volume of large-payload Data/PromiseResume receipts cross-shard, at a gas cost that does not scale with their contribution to `receipt_bytes`.

### Impact Explanation
This does not by itself cause fund loss but it can bias a protocol-level fee/throttle mechanism (`outgoing_gas_limit`, `shard_accepts_transactions`) so that:
- legitimate transactions to the targeted shard get gas-limited or rejected (`RejectTransactionReason` once `congestion_level >= reject_tx_congestion_threshold`) at a lower true-cost than intended by the protocol's economic model, i.e., a cheaper-than-designed way to induce a "congested" state that throttles competitors' transaction admission. [4](#0-3) 

This is explicitly called out in the code as an accepted MVP limitation ("the congestion control MVP does not account for data receipts or postponed receipts") rather than an oversight, which weakens the case that it is an unknown/exploitable vulnerability versus an intentional trade-off. [5](#0-4) 

### Likelihood Explanation
Reachability requires a contract that returns large Data receipts or performs promise-yield/resume cycles across shards, which is achievable by any account calling a contract with a `FunctionCall` action — no special privilege needed. However, exploiting it meaningfully still requires enough volume of large receipts to move the `memory_congestion` fraction meaningfully relative to `max_congestion_memory_consumption`, which is a large threshold, bounding the practical severity.

### Recommendation
Because the zero-congestion-gas treatment for `Data`/`PromiseResume`/`GlobalContractDistribution` is a documented, intentional MVP simplification rather than an unnoticed defect, the appropriate fix (if pursued) would be to also charge congestion "weight" proportional to `receipt_bytes` for these receipt kinds directly in the gas-congestion computation (not just the separate memory dimension), or otherwise make the memory dimension resistant to being driven disproportionately by receipt kinds that carry no execution-gas cost.

### Proof of Concept
Not applicable — this is a documented design limitation in `compute_receipt_congestion_gas`, not a silent bug; there is no single-transaction PoC demonstrating unauthorized value movement, supply inflation, or state-root divergence, only a bounded and pre-acknowledged throttling-fairness effect.

    pub fn congestion_level(&self) -> f64 {
        let incoming_congestion = self.incoming_congestion();
        let outgoing_congestion = self.outgoing_congestion();
        let memory_congestion = self.memory_congestion();
        let missed_chunks_congestion = self.missed_chunks_congestion();

        incoming_congestion
            .max(outgoing_congestion)
            .max(memory_congestion)
            .max(missed_chunks_congestion)
    }

    pub fn outgoing_gas_limit(&self, sender_shard: ShardId) -> Gas {
        let congestion = self.congestion_level();

        if Self::is_fully_congested(congestion) {
            // Red traffic light: reduce to minimum speed
            if sender_shard == ShardId::from(self.info.allowed_shard()) {
                self.config.allowed_shard_outgoing_gas
            } else {
                Gas::ZERO
            }
        } else {
            mix_gas(self.config.max_outgoing_gas, self.config.min_outgoing_gas, congestion)
        }
