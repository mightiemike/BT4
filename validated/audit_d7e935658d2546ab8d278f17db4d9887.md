## Title
`ensure_match_transaction_info` skips checkpoint-hash verification, allowing replay-verify to accept a divergent state/hot-state/position-state root - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  is the integrity gate used by replay/verification tooling to confirm a locally-produced `TransactionOutput` matches the authenticated `TransactionInfo` retrieved from an archive/backup. It checks status, gas used, write-set hash, and event root hash, but explicitly does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are meant to bind the committed state root to the transaction accumulator leaf.

### Finding Description
`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as builder fields, as shown at [2](#0-1) . These are the authenticated bindings between a transaction's execution and the resulting Merkle/JMT state root that gets embedded into the accumulator (see how they are assembled during commit in `assemble_transaction_infos`: [3](#0-2) ).

However, `ensure_match_transaction_info` — the function used to validate a `TransactionOutput` against a `TransactionInfo` during replay — omits these checkpoint hash comparisons entirely. The code contains its own acknowledging TODO: [4](#0-3) 

This function is invoked by `storage/db-tool`'s `replay_on_archive` verification path (`execute_and_verify`, feeding `expected_txn_infos` built from backup data) at [5](#0-4) , and by the CLI's transaction replay command at [6](#0-5) . In both cases, the function is the sole line of defense confirming that locally-recomputed execution results match the trusted (accumulator-proven) `TransactionInfo`.

Because state/hot-state/position-state checkpoint hashes are skipped, a divergence in the JMT state root produced by local re-execution versus the authenticated on-chain checkpoint hash will not be flagged as a mismatch by this function. The write-set hash check alone does not substitute for a state-root check: `write_set_hash` covers the raw write operations for that single transaction, whereas `state_checkpoint_hash` (and the hot/position variants) reflect the full merkelized state after the checkpoint, which can diverge due to bugs in state-merklization, hot-state handling, or the newer position-state (native order book / "trading-native") tree without affecting the write-set hash at all.

### Impact Explanation
This is a genuine proof-integrity gap in the authenticated-verification path: replay-verify and CLI transaction verification are supposed to guarantee that "committed state differs from the correct VM result" is detected. With the checkpoint hash checks missing, a state-root divergence introduced by a bug in the merklization/commit path (e.g., in hot-state or position-state tree construction) would silently pass `replay_on_archive` and CLI replay verification, since only the write-set hash, event root, gas, and status are checked. This directly undermines the "hard-fork-only divergence during commit, replay, restore, or proof verification" category, since these tools exist specifically to catch storage/consensus divergence bugs before or after they ship.

### Likelihood Explanation
The gap is unconditional in the current code (not behind a feature flag) for both callers identified. The author's own comment ties the omission to `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (an on-chain feature flag found in `types/src/on_chain_config/aptos_features.rs` and referenced in `storage/aptosdb/src/db/aptosdb_reader.rs`), implying the checkpoint-hash verification was deliberately deferred as a known TODO rather than fixed. This is a real, self-acknowledged gap in the codebase, but I could not verify from the available index whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently active on mainnet or purely a future-facing flag, nor could I fully trace whether any other check upstream (e.g., inside `TransactionOutputListWithProofV2::verify`, which does verify against ledger-info-proven transaction infos but similarly does not check checkpoint hashes per the snippet at [7](#0-6) ) compensates for this. This limits my confidence in asserting current, unconditional mainnet exploitability versus a currently-inert TODO guarding an unreleased feature.

### Recommendation
Add explicit comparisons of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against the locally computed state roots in `ensure_match_transaction_info`, mirroring the pattern already used for `write_set_hash` and `event_root_hash`. Do this before enabling any feature (such as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that relies on the position-state root being authenticated, and audit `TransactionOutputListWithProofV2::verify` for the same omission.

### Proof of Concept
Not independently reproduced with a working exploit; this is based on direct code reading of the gate function and its two call sites (`storage/db-tool/src/replay_on_archive.rs` and `aptos-move/cli/src/commands.rs`), plus the author's own TODO comment confirming the exact missing checks and their consequence ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"). Due to index size limits, I could not fully inspect `TransactionOutputListWithProofV2::verify`'s full context or confirm the current activation status of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`; a full session with repo access would be needed to construct a concrete divergence scenario and confirm real-world reachability.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
