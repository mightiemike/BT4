## Analysis

The SEDA Tally VM bug is a generic "expensive work performed before affordability is verified" pattern. Push Chain has a direct analog in the `MsgExecutePayload` / `ExecutePayload` flow.

### Title
Full-cost EVM payload execution runs before fee affordability is checked, in a message class exempted from ante-level fee deduction - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
`ExecutePayload` runs the entire user-supplied EVM call (`CallUEAExecutePayload`, sized by an attacker-controlled `GasLimit` with no protocol maximum) directly against `sdkCtx` before it ever checks whether the payer (the UEA) can actually cover the resulting gas bill. The affordability check, `DeductGasFeesFromReceipt`, runs only after the EVM call has fully executed. `MsgExecutePayload` is also one of the message types exempted from the ante `DeductFeeDecorator`'s fee/balance checks (it's in the gasless allowlist), so this expensive execution can be triggered by transactions that never had a real, funded fee payer checked up front.

### Finding Description
In `x/uexecutor/keeper/msg_execute_payload.go`, `ExecutePayload`:
1. Validates the payload shape/format cheaply [1](#0-0) .
2. Resolves the UEA address, and only requires a non-zero balance gate when the UEA is **not yet deployed** [2](#0-1) . For an **already-deployed** UEA this gate is skipped entirely, regardless of its current balance.
3. Executes the full EVM call via `CallUEAExecutePayload` directly on `sdkCtx` (not inside a `CacheContext`, unlike the `ExecutePayloadV2` sibling function) [3](#0-2) , using a gas limit taken verbatim from the attacker-supplied payload [4](#0-3) .
4. Only *after* that execution completes does it attempt `DeductGasFeesFromReceipt` to bill the UEA for the gas actually used [5](#0-4) .

`UniversalPayload.ValidateBasic()` places no upper bound on `GasLimit` — it only checks that the string parses as a non-negative integer [6](#0-5) . Test fixtures use `GasLimit: "21000000"`, showing the field is meant to carry large caller-chosen values.

Compounding this, `MsgExecutePayload` is explicitly listed in the gasless message allowlist consulted by the ante handler's `DeductFeeDecorator`, which skips the normal `checkDeductFee`/balance check for the enclosing Cosmos tx entirely when all messages in the tx are gasless [7](#0-6) [8](#0-7) . So the one place that would normally verify the sender can pay for computation before it runs is bypassed for this exact message type.

This mirrors the SEDA finding precisely: the "can this party actually pay for the resource-intensive operation" check (there: VM gas-startup charge; here: `DeductGasFeesFromReceipt` against the UEA's UPC balance) is performed only after the expensive operation (there: WASM VM spin-up + several setup steps; here: a full EVM execution of the UEA's `executeUniversalTx`, up to an attacker-chosen `GasLimit`) has already run to completion.

### Impact Explanation
An unprivileged attacker can submit `MsgExecutePayload` transactions targeting an already-deployed UEA (their own, previously deployed and now drained) with a very large `GasLimit`, an arbitrarily crafted `Data` payload designed to be computationally heavy for the destination contract, and a `verificationData` that is well-formed enough to reach the execution step. Every honest validator/node must:
- Resolve the UEA address, fully execute the EVM call up to the attacker-declared gas limit (real CPU/storage work), and only then discover that the UEA's UPC balance is insufficient to pay the resulting `gasCost`.

Because `MsgExecutePayload` is in the ante-level gasless allowlist, this can be done without the normal fee-based cost/rate-limiting that would apply to standard-fee transactions, making repeated submission cheap relative to the real per-tx computational cost imposed on the network — a chain-slowdown / DoS vector reachable from ordinary unprivileged user transaction submission, matching the in-scope "denial of service...not network-level and...reachable without privileged control" impact category.

### Likelihood Explanation
Reachable via a single default `MsgExecutePayload` submission by any user with a deployed (but not currently funded) UEA — no validator collusion, no privileged role, and no external chain interaction is required. The only preconditions are (a) a UEA that is already deployed (trivial and free to arrange ahead of time while funded, then drain it) and (b) a syntactically valid `verificationData`/payload that passes `ValidateBasic` and gets far enough into `CallUEAExecutePayload` to consume gas before reverting or before fee deduction fails.

### Recommendation
- Verify the payer (UEA) can cover the worst-case gas cost of the requested `GasLimit`/`MaxFeePerGas` *before* invoking `CallUEAExecutePayload`, mirroring the SEDA fix of gating VM startup on available gas.
- Enforce a protocol-level maximum on `UniversalPayload.GasLimit` in `ValidateBasic`.
- Reconsider including `MsgExecutePayload` in the ante-level gasless allowlist, or add a pre-execution balance/affordability check equivalent to normal fee deduction for this message type.
- Wrap the EVM execution + fee deduction in `ExecutePayload` in a `CacheContext` consistently with `ExecutePayloadV2`, and perform the balance check on the *pre*-execution cached state before committing to the expensive call.

### Proof of Concept
1. Attacker deploys a UEA and briefly funds it (or it is otherwise already deployed) so the `isDeployed` gate at `msg_execute_payload.go:57-67` passes without a balance check.
2. Attacker drains the UEA to zero UPC balance.
3. Attacker submits `MsgExecutePayload` with a large `GasLimit` (e.g. `21000000`+) pointing at a computationally expensive `To`/`Data` target and valid-enough `verificationData` to pass early validation.
4. Every validator executes `CallUEAExecutePayload` to completion (full EVM cost paid in CPU time), then `DeductGasFeesFromReceipt` fails due to zero UEA balance, and the tx errors out — but the computational cost was already incurred by every node processing the tx, and because `MsgExecutePayload` is gasless at the ante layer, the attacker paid nothing for triggering it.
5. Repeat at scale to degrade block production performance.
