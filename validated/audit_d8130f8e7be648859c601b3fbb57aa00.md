### Title
User-Controlled PII (Account Name, Account ID, Witness URL) Stored Permanently On-Chain and Publicly Readable via RPC - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateAccountActuator.java])

### Summary
java-tron allows any account holder to write free-form byte strings into their on-chain `Account` record via `AccountUpdateContract` (`account_name`), `SetAccountIdContract` (`account_id`), and `WitnessUpdateContract`/`WitnessCreateContract` (`url`). These fields accept up to 200/32/256 bytes of largely unrestricted content and are permanently persisted in the account/witness store, then exposed unencrypted to any caller via `wallet/getaccount`, `wallet/listwitnesses`, and gRPC `GetAccount`/`ListWitnesses`. This mirrors the RocketDAO finding: a user-supplied identifier (there, an e-mail address) is stored on a public, immutable ledger and readable by anyone, enabling de-pseudonymization, correlation of on-chain addresses with personal identifiers, and downstream spam/phishing targeting.

### Finding Description
`UpdateAccountActuator.execute` takes the caller-supplied `accountName` bytes directly from the broadcast `AccountUpdateContract` and writes them into `AccountCapsule`/`AccountStore` without content filtering beyond a length/printability check: [1](#0-0) 
Validation only enforces that the name is "readable" ASCII within `MAX_ACCOUNT_NAME_LEN` (200 bytes); it does not restrict semantic content, so users can and do encode e-mail addresses, phone numbers, or other PII: [2](#0-1) 

Similarly, `SetAccountIdActuator` persists an arbitrary 8–32 byte "account_id" chosen by the user, indexed and immutable once set: [3](#0-2) 

And `WitnessUpdateActuator`/`WitnessCreateActuator` store a free-form `url` field (up to 256 bytes) supplied by the witness owner: [4](#0-3) [5](#0-4) 

All of these fields are part of the `Account`/`Witness` protobuf messages and are returned in full by unauthenticated read APIs, e.g. `wallet/getaccount` (`Wallet.getAccount`) and `wallet/listwitnesses` (`ListWitnessesServlet`), with no redaction or access control: [6](#0-5) [7](#0-6) 

Because the blockchain is immutable and globally replicated, once a user embeds PII in `account_name`, `account_id`, or a witness `url`, it can never be removed and is retrievable by any node operator or RPC client indefinitely — the same root cause as the RocketDAO `getMemberEmail`/`MemberDetails.Email` finding.

### Impact Explanation
Any anonymous RPC caller can enumerate accounts/witnesses and harvest `account_name`, `account_id`, and witness `url` fields, which may contain e-mail addresses, real names, or other identifying strings that users mistakenly (or are encouraged to) include for "public accountability" reasons (e.g., witness/SR candidates publishing contact info). This enables de-pseudonymization of TRON addresses, correlation across services, and targeted phishing/spam campaigns — directly analogous to the RocketDAO impact, though scoped to whatever PII users choose to embed rather than a mandatory field.

### Likelihood Explanation
High reachability: no privileged role is required — any funded account can call `AccountUpdateContract`/`SetAccountIdContract`, and any witness candidate can call `WitnessCreateContract`/`WitnessUpdateContract`. All corresponding read paths (`wallet/getaccount`, `wallet/listwitnesses`, gRPC equivalents) are unauthenticated and rate-limited only generically, not restricted by field sensitivity. The main mitigating factor is that this is opt-in (users choose what to put in these fields) rather than a mandatory PII field like RocketDAO's `member.email`, which lowers the automatic-exposure likelihood somewhat but does not eliminate the design risk.

### Recommendation
- Document clearly in wallet/CLI tooling that `account_name`, `account_id`, and witness `url` are public and immutable; warn against entering personal data.
- Consider stronger format constraints (e.g., disallow e-mail-like patterns) or reduce the maximum length further where feasible.
- For any future field intended for identity/contact info, avoid storing raw PII on-chain; instead store a hash or off-chain pointer with a separate, access-controlled disclosure mechanism.

### Proof of Concept
1. Attacker/any user account holder broadcasts an `AccountUpdateContract` with `account_name = "john.doe@example.com"` (valid because it is ≤200 printable bytes) — accepted by `UpdateAccountActuator.validate`/`execute`.
2. Any third party queries `POST /wallet/getaccount {"address": "<hex-address>"}` (`Wallet.getAccount`) and receives the account record including the embedded e-mail/name string in `account_name`, permanently and publicly.
3. Equivalently, a witness candidate sets `url` via `WitnessUpdateContract` to personal contact info; anyone calling `wallet/listwitnesses` (`ListWitnessesServlet`) retrieves it in cleartext.

  private static final int MAX_ACCOUNT_NAME_LEN = 200;
  private static final int MAX_ACCOUNT_ID_LEN = 32;
  private static final int MIN_ACCOUNT_ID_LEN = 8;
  private static final int MAX_ASSET_NAME_LEN = 32;
  private static final int MAX_TOKEN_ABBR_NAME_LEN = 5;
  private static final int MAX_ASSET_DESCRIPTION_LEN = 200;
  private static final int MAX_URL_LEN = 256;

  @Autowired
  private ChainBaseManager chainBaseManager;

  public static boolean validAccountName(byte[] accountName) {
    return validBytes(accountName, MAX_ACCOUNT_NAME_LEN, true);
  }

  public static boolean validAssetDescription(byte[] description) {
    return validBytes(description, MAX_ASSET_DESCRIPTION_LEN, true);
  }

  public static boolean validUrl(byte[] url) {
    return validBytes(url, MAX_URL_LEN, false);
  }

  public static boolean validAccountId(byte[] accountId) {
    return validReadableBytes(accountId, MAX_ACCOUNT_ID_LEN) && accountId.length >= MIN_ACCOUNT_ID_LEN;
  }

  public static boolean validAssetName(byte[] assetName) {
    return validReadableBytes(assetName, MAX_ASSET_NAME_LEN);
  }

  public static boolean validTokenAbbrName(byte[] abbrName) {
    return validReadableBytes(abbrName, MAX_TOKEN_ABBR_NAME_LEN);
  }

  private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
    if (ArrayUtils.isEmpty(bytes)) {
      return allowEmpty;
    }
    return bytes.length <= maxLength;
  }

  public Account getAccount(Account account) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    AccountCapsule accountCapsule = accountStore.get(account.getAddress().toByteArray());
    if (accountCapsule == null) {
      return null;
    }
    accountCapsule.importAllAsset();
    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    processor.updateUsage(accountCapsule);

    EnergyProcessor energyProcessor = new EnergyProcessor(
        chainBaseManager.getDynamicPropertiesStore(),
        chainBaseManager.getAccountStore());
    energyProcessor.updateUsage(accountCapsule);

    long genesisTimeStamp = chainBaseManager.getGenesisBlock().getTimeStamp();
    accountCapsule.setLatestConsumeTime(genesisTimeStamp
        + BLOCK_PRODUCED_INTERVAL * accountCapsule.getLatestConsumeTime());
    accountCapsule.setLatestConsumeFreeTime(genesisTimeStamp
        + BLOCK_PRODUCED_INTERVAL * accountCapsule.getLatestConsumeFreeTime());
    accountCapsule.setLatestConsumeTimeForEnergy(genesisTimeStamp
        + BLOCK_PRODUCED_INTERVAL * accountCapsule.getLatestConsumeTimeForEnergy());
    sortFrozenV2List(accountCapsule);
    return accountCapsule.getInstance();
  }
