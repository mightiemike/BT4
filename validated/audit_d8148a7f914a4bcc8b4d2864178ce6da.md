### Title
Disabled Tokens Can Still Be Minted as PRC20 Deposits — Missing `TokenConfig.Enabled` Check in Inbound Execution — (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/execute_inbound_funds.go`)

### Summary
`TokenConfig` in `x/uregistry` carries an explicit `enabled` field (`bool enabled = 6; // Whether this token is enabled for minting/bridging`) [1](#0-0)  intended to gate whether a token may be used for minting/bridging. However, every inbound execution path in `x/uexecutor` that resolves a token via `GetTokenConfig` — `depositPRC20` (used for FUNDS inbounds), `ExecuteInboundGas`, and `ExecuteInboundGasAndPayload` — only checks whether the lookup returned an error (i.e., whether the token is registered at all); none of them check the `Enabled` flag on the returned `TokenConfig` before minting PRC20 via `CallPRC20Deposit`. This is the same bug class as the CreditCaller report: a boolean/whitelist gate exists in the data model and is documented as the control that decides eligibility, but the code path that performs the privileged action (minting) never consults it.

### Finding Description
`GetTokenConfig` simply performs a keyed lookup and returns the config or a not-found error — it does not filter on `Enabled`: [2](#0-1) 

`depositPRC20`, which is the funds-minting entry point reached from `ExecuteInboundFunds`, retrieves the token config and immediately proceeds to mint PRC20 using its `NativeRepresentation.ContractAddress`, with no `Enabled` check anywhere in the function: [3](#0-2) 

`ExecuteInboundGas` and `ExecuteInboundGasAndPayload` follow the identical pattern — fetch `tokenConfig`, treat only the lookup `err` as the gating condition, then proceed to deposit/auto-swap regardless of the config's `Enabled` value: [4](#0-3) [5](#0-4) 

A grep across the entire `x/uexecutor` package confirms `TokenConfig.Enabled` is never referenced in any inbound-execution code path (the only two `.Enabled` hits in that package are unrelated, in `msg_execute_payload.go` / `msg_migrate_uea.go`, which reference a different `Enabled` struct, not `TokenConfig.Enabled`). `x/uregistry`'s own `MsgUpdateTokenConfig` handler only checks that the row exists before overwriting it with the caller-supplied config (including a caller-controlled `Enabled` field) — it performs no separate downstream enforcement either: [6](#0-5) 

Consequence: once a token has ever been registered (`AddTokenConfig`) with a `NativeRepresentation.ContractAddress` (a PRC20 contract deployed on Push Chain), setting `Enabled=false` via `MsgUpdateTokenConfig` — the documented, intended way to pull a token out of active bridging — does **not** actually stop new inbound deposits of that token from minting PRC20. An unprivileged user submitting deposits on the source chain, and honest Universal Validators voting `MsgVoteInbound` on the observed (real) event, will cause the core validator to execute the deposit and mint PRC20 to the recipient exactly as if the token were still enabled, because the enforcement gate that the config schema promises simply isn't wired into the execution path.

### Impact Explanation
This breaks the token-registry invariant that `Enabled=false` is the authoritative way to halt minting/bridging of a specific token (e.g., in response to a compromised source-chain contract, a depeg, a liquidity-cap breach, or a decision to sunset a token). Because token disabling is the primary lever `uregistry` exposes for incident response short of removing the whole token (`RemoveTokenConfig`, which is a heavier and stateful action), the practical effect is unauthorized/unintended PRC20 minting that the admin believed had been shut off — a direct violation of "corruption of PRC20 or native asset accounting ... token mapping" and "unauthorized mint" in the allowed-impact list. The severity is bounded by admin intent (this is not a from-genesis unregistered-token bypass, since `GetTokenConfig` still requires the token to have been registered at some point), but it is a real, reachable authorization gap: any user can keep depositing a token the protocol has flagged `Enabled=false`, and honest validators/nodes will process it without any way for the protocol to stop it short of full removal.

### Likelihood Explanation
High reachability, no privileged actor required: the trigger is an ordinary user depositing tokens on the source chain gateway exactly as they would for a normal, enabled token; honest Universal Validators observe and vote the event via the standard `MsgVoteInbound` path exactly as designed. The only precondition is that an admin has previously disabled a token config via the intended `MsgUpdateTokenConfig` workflow — this is a normal, expected admin action, not an attacker-controlled or privileged-compromise scenario, so it is squarely in-scope per the "unprivileged external attacker" framing (the admin action is legitimate governance behavior; the bug is that scoped node code fails to enforce it).

### Recommendation
Add an explicit `tokenConfig.Enabled` check immediately after every `GetTokenConfig` call in the inbound execution paths (`handler.go:depositPRC20`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, and any CEA/funds-and-payload variant that resolves a token config), returning a failed PCTx / triggering the standard revert flow when the token is disabled, mirroring the existing "missing token config" failure handling already tested in `execute_inbound_gas_test.go`.

### Proof of Concept
1. Admin registers a token via `MsgAddTokenConfig` with `Enabled=true` and a `NativeRepresentation.ContractAddress` pointing at a live PRC20.
2. Admin later calls `MsgUpdateTokenConfig` with `Enabled=false` on the same `(chain, address)` key (intending to halt further minting/bridging of this token), per `x/uregistry/keeper/msg_update_token_config.go`.
3. An ordinary (unprivileged) user deposits the same asset on the source chain gateway as before.
4. Honest Universal Validators observe the event and submit `MsgVoteInbound`; once quorum is reached, `x/uexecutor` executes the inbound (`ExecuteInboundFunds` → `depositPRC20`, or `ExecuteInboundGas`/`ExecuteInboundGasAndPayload` for GAS/FUNDS_AND_PAYLOAD types).
5. `GetTokenConfig` returns the config successfully (only `has`/not-found is checked); `Enabled=false` is never inspected; `CallPRC20Deposit` mints PRC20 to the recipient exactly as if the token were still enabled — the intended admin control has no effect.

*Note: This finding is derived from static code-path tracing across `x/uexecutor` and `x/uregistry`; I was not able to execute the integration test suite to empirically confirm the mint succeeds post-disable (no runtime access in this environment), so this should be validated with a concrete integration test (analogous to `execute_inbound_gas_test.go`'s "missing token config" test, but setting `Enabled=false` instead of removing the config) before remediation.*

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// UpdateTokenConfig updates an existing token configuration in the uregistry.
func (k Keeper) UpdateTokenConfig(ctx context.Context, tokenConfig *types.TokenConfig) error {
	storageKey := types.GetTokenConfigsStorageKey(tokenConfig.Chain, tokenConfig.Address)

	// Check if the token config exists
	if has, err := k.TokenConfigs.Has(ctx, storageKey); err != nil {
		return err
	} else if !has {
		return fmt.Errorf("token config for %s on chain %s does not exist", tokenConfig.Address, tokenConfig.Chain)
	}

	if err := k.TokenConfigs.Set(ctx, storageKey, *tokenConfig); err != nil {
		return err
	}
	k.Logger().Info("token config updated",
		"chain", tokenConfig.Chain,
		"token_address", tokenConfig.Address,
	)
	return nil
}
