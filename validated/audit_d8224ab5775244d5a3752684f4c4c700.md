## Analysis

I found a valid structural analog. In the Locke bug, `__abdicate()` clears the `gov` field but leaves `pendingGov`/`emergency_gov` intact, letting a leftover credential resurrect the revoked authority. The direct analog in this codebase is `invalidateAccessToken()`, used across `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` to revoke a session on a 401 from Shopify: it clears `session.accessToken` but never clears `session.refreshToken` / `session.refreshTokenExpires`, and `ensureOfflineTokenIsNotExpired` (or `ensureValidOfflineSession`) will still use that leftover `refreshToken` to silently re-mint a new valid access token — resurrecting a token the app just tried to revoke.

### Title
Access-token invalidation leaves `refreshToken` intact, allowing automatic resurrection of a revoked token - (File: packages/apps/shopify-app-remix/src/server/authenticate/helpers/invalidate-access-token.ts)

### Summary
`invalidateAccessToken()` is the "abdicate" analog here: it is called whenever the Admin API returns 401 to signal a token should be treated as dead. But it only nulls `accessToken`, leaving `refreshToken`/`refreshTokenExpires` on the persisted `Session`. Any code path that loads that same offline session and calls `ensureOfflineTokenIsNotExpired`/`ensureValidOfflineSession` will use the still-present `refreshToken` to fetch a brand-new access token, defeating the invalidation.

### Finding Description
`invalidateAccessToken` is implemented identically in three packages and only clears `accessToken`: [1](#0-0) [2](#0-1) [3](#0-2) 

It is invoked from client-error handlers (e.g., billing calls, `handleClientErrorFactory` for the token-exchange strategy) whenever a 401 is received, specifically to mark a compromised/invalid token as dead: [4](#0-3) [5](#0-4) 

However, `refreshToken`/`refreshTokenExpires` remain on the `Session` object in storage. When `expiringOfflineAccessTokens` is enabled, `ensureOfflineTokenIsNotExpired` will use exactly that leftover `refreshToken` — regardless of `accessToken` being cleared — to mint a fresh access token if the session is near/at expiry: [6](#0-5) [7](#0-6) 

The check gates only on `session.isExpired(...)` and `session.refreshToken` — it does not check whether `accessToken` is `undefined` (i.e., whether the session was explicitly invalidated). So the same leftover `refreshToken` that should have been revoked alongside the access token can independently regenerate a valid, usable offline session via `refreshToken()`/`/admin/oauth/access_token` refresh grant: [8](#0-7) 

This mirrors the Locke bug precisely: the "abdicate" action nulls one credential field (`gov`/`accessToken`) but leaves a second, independently-usable credential field (`pendingGov`/`refreshToken`) untouched, and separate application logic (`acceptGov`/`ensureOfflineTokenIsNotExpired`) later consumes that leftover field to restore the exact authority that was supposed to be revoked.

### Impact Explanation
The intent of `invalidateAccessToken` is to stop the app from using a token Shopify has told it is dead (401), typically as a precursor to forcing re-authentication via `respondToInvalidSessionToken`. If `expiringOfflineAccessTokens` is enabled and any code path (webhook handler, cron/background job, or a subsequent request through `validateAuthenticatedSession`/`ensureValidOfflineSession`) loads that same offline session before the app forces a fresh OAuth/token-exchange, it will transparently refresh and reuse the "invalidated" session — silently undermining the intended revocation and continuing to use a token flagged as compromised/unauthorized by Shopify. This does not directly expose new secrets to an attacker, but it defeats an explicit security control (server-initiated token invalidation), which is the same "revocation is not actually revocation" class of bug as the original finding.

### Likelihood Explanation
This triggers whenever: (1) `future.expiringOfflineAccessTokens` is on, (2) a stored offline session has both `accessToken` and `refreshToken`, (3) the Admin API 401s and `invalidateAccessToken` runs, and (4) any other request path loads and refreshes that same session before the app completes fresh authentication. Given `validateAuthenticatedSession`/`ensureValidOfflineSession`/webhook handlers all call `ensureOfflineTokenIsNotExpired` independently and don't coordinate with `invalidateAccessToken`, concurrent or subsequent requests during the same session lifecycle can realistically race this condition, especially in multi-instance/queue-processing deployments.

### Recommendation
When invalidating an access token due to a 401/unauthorized response, also clear `refreshToken` and `refreshTokenExpires` (not just `accessToken`) so `ensureOfflineTokenIsNotExpired`/`ensureValidOfflineSession` can no longer resurrect the session from a stale refresh token. Alternatively, add an explicit "revoked" flag to `Session` and have the refresh-token codepaths check it before trusting `refreshToken`.

### Proof of Concept
1. Enable `future: { expiringOfflineAccessTokens: true }` and store an offline session with both `accessToken` and `refreshToken` for a shop.
2. Trigger a 401 from the Admin API on a request path that calls `invalidateAccessToken` (e.g., `billing.createUsageRecord`, or any `handleClientErrorFactory` 401 branch in the token-exchange strategy) — this sets `accessToken = undefined` and persists the session, leaving `refreshToken` intact: [1](#0-0) 
3. Before the app completes a fresh OAuth/token exchange, trigger any code path that calls `ensureOfflineTokenIsNotExpired`/`ensureValidOfflineSession` for the same shop (e.g., a webhook handler using `shopify.ensureValidOfflineSession(shop)`, or a normal request through `validateAuthenticatedSession` with an expired offline session that still has a `refreshToken`).
4. Observe that `ensureOfflineTokenIsNotExpired` refreshes and stores a new, working `accessToken` using the leftover `refreshToken` — resurrecting the session that was supposed to be invalidated: [9](#0-8)

export async function ensureOfflineTokenIsNotExpired(
  session: Session,
  params: BasicParams,
  shop: string,
) {
  const {config} = params;
  if (
    config.future?.expiringOfflineAccessTokens &&
    session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY) &&
    config.distribution !== AppDistribution.ShopifyAdmin &&
    session.refreshToken
  ) {
    const offlineSession = await refreshToken(
      params,
      shop,
      session.refreshToken,
    );

    await config.sessionStorage!.storeSession(offlineSession);
    return offlineSession;
  }
  return session;
}

const RefreshTokenGrantType = 'refresh_token';

export function refreshToken(config: ConfigInterface): RefreshToken {
  return async ({shop, refreshToken}: RefreshTokenParams) => {
    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      refresh_token: refreshToken,
      grant_type: RefreshTokenGrantType,
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
  };
