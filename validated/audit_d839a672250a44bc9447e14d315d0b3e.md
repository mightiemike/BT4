### Title
JSON-RPC transaction decode path allocates memory from an attacker-controlled Borsh length prefix before any size validation - ([File: chain/jsonrpc/src/api/transactions.rs])

### Summary
The JSON-RPC transaction ingest path deserializes a base64-decoded, attacker-supplied byte blob directly with `SignedTransaction::try_from_slice(&bytes)` with no upper bound check on the decoded byte length before Borsh decoding begins [1](#0-0) . This mirrors the CVE-2026-9538 bug class exactly: a length/size field embedded in attacker-controlled input (Borsh's length-prefixed `Vec`/`String` encoding, analogous to Archive::Tar's 12-byte size field) drives an allocation with no upper bound enforced *before* decoding is attempted.

### Finding Description
nearcore's own network layer explicitly documents and fixes this exact bug class: `try_from_slice_with_limit` in `chain/network/src/network_protocol/proto_conv/util.rs:14-28` rejects a peer-supplied Borsh blob whose length exceeds a bound *before* calling `T::try_from_slice`, with the comment "so a maliciously inflated peer payload cannot force a large allocation at decode time" [2](#0-1) . This gate is applied to peer-supplied transactions via `MAX_TRANSACTION_SIZE_BYTES` (16 MiB) specifically to prevent "maliciously inflated transactions exhausting node memory at decode time" [3](#0-2) [4](#0-3) .

The JSON-RPC ingest path for `broadcast_tx_async`/`broadcast_tx_commit`/`send_tx`/`EXPERIMENTAL_tx_status` (`RpcSendTransactionRequest::parse` / `RpcTransactionStatusRequest::parse`) does **not** use this guard. It calls `decode_signed_transaction`, which base64-decodes the caller-supplied string and immediately calls `SignedTransaction::try_from_slice(&bytes)` with no length check against `max_transaction_size` or any other bound [5](#0-4) . The same unbounded pattern exists in `SignedTransaction`'s `serde::Deserialize` impl, used whenever a `SignedTransaction` is embedded in any JSON-RPC payload: it base64-decodes then calls `borsh::from_slice::<Self>` directly [6](#0-5) .

`Transaction`/`Action` types contain nested `Vec<u8>` fields (e.g. `FunctionCallAction::args`, `DeployContractAction::code`) whose Borsh encoding is a `u32` length prefix followed by the bytes. Borsh's `Vec<u8>` deserialization reads that length prefix and allocates a buffer sized to it before validating that the input actually contains that many bytes — the same "declared size drives allocation before the payload is verified" pattern as the CVE. An attacker can therefore submit a small HTTP/JSON-RPC request (well under any body-size limiter) whose base64-decoded Borsh bytes encode a small number of *outer* bytes but a length prefix inside a nested `Vec<u8>` field claiming up to `u32::MAX` (~4 GiB), forcing a multi-gigabyte allocation attempt on the RPC-handling thread purely from decoding, before `validate_transaction`'s `max_transaction_size` check ever runs (`runtime/runtime/src/verifier.rs` gates only after a `SignedTransaction` object already exists).

### Impact Explanation
Because JSON-RPC (`broadcast_tx_async`, `broadcast_tx_commit`, `send_tx`, `EXPERIMENTAL_tx_status`, and any endpoint accepting `signed_tx_base64`) is reachable by any unauthenticated RPC caller, this allows repeated, cheap requests that each attempt a large allocation, causing memory exhaustion / OOM or allocator thrashing on the RPC node, and in the worst case a node crash (denial of service) with no need for a valid signature or a real large payload to be transmitted over the wire.

### Likelihood Explanation
High confidence that the code path is unguarded (verified directly), moderate confidence on the exact severity of impact because:
- I could not fully verify the exact Borsh crate version's internal `Vec<u8>`/length-prefix allocation strategy (whether it uses `Vec::with_capacity(len)` unconditionally or a safer incremental/chunked read) within the available index, so the precise allocation size an attacker can force (versus a fail-fast bound check inside Borsh itself) is not 100% confirmed from this codebase alone.
- I also could not fully confirm the exact byte-size limit enforced by `RequestBodyLimitLayer` in `chain/jsonrpc/src/lib.rs`, which bounds the raw HTTP body but does not bound the *decoded* Borsh length-prefix values embedded within a small body.
- The explicit, purpose-built mitigation added on the peer-to-peer path (`try_from_slice_with_limit`, `MAX_TRANSACTION_SIZE_BYTES`) strongly indicates the nearcore team is aware this exact bug class is reachable through unbounded Borsh decode of transactions, but that same fix was not mirrored onto the JSON-RPC ingestion path.

### Recommendation
Apply the same guard used in the network layer to the JSON-RPC transaction decode path: bound `bytes.len()` (or better, decode with an explicit maximum, e.g. `try_from_slice_with_limit` gated at `max_transaction_size`/`MAX_TRANSACTION_SIZE_BYTES`) in `decode_signed_transaction` (`chain/jsonrpc/src/api/transactions.rs:71-76`) and in `SignedTransaction`'s `serde::Deserialize` impl (`core/primitives/src/transaction.rs:556-569`) before calling `try_from_slice`/`borsh::from_slice`.

### Proof of Concept
Conceptual PoC (not fully executable from the index alone, since exact Borsh internal allocation behavior for the installed version could not be verified):
1. Construct a minimal Borsh-encoded `SignedTransaction` byte buffer by hand (not via the normal serializer) where the outer structure is valid up to a `FunctionCallAction.args: Vec<u8>` field, but the 4-byte little-endian length prefix for that `Vec<u8>` is set to `0xFFFFFFFE` (~4 GiB) while the actual trailing bytes present are only a few dozen bytes.
2. Base64-encode this buffer and submit it via JSON-RPC `broadcast_tx_async` (`{"jsonrpc":"2.0","method":"broadcast_tx_async","params":["<base64>"] }`).
3. `decode_signed_transaction` calls `SignedTransaction::try_from_slice(&bytes)` directly with no size check [1](#0-0) ; Borsh reads the length prefix and attempts to allocate a buffer for it before discovering the buffer is truncated.
4. Repeating this request concurrently forces the RPC node to repeatedly attempt multi-gigabyte allocations from tiny requests, exhausting memory.

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}

/// Upper bound on the Borsh-encoded size of a peer-supplied transaction body,
/// enforced before the body is deserialized to mitigate maliciously inflated
/// transactions exhausting node memory at decode time. Set comfortably above
/// the largest valid transaction (`max_transaction_size`, historically 4 MiB)

const MAX_TRANSACTION_SIZE_BYTES: usize = 16 * MIB as usize;

const MAX_ROUTED_MESSAGE_SIZE_BYTES: usize = 64 * MIB as usize;

impl<'de> serde::Deserialize<'de> for SignedTransaction {
    fn deserialize<D>(deserializer: D) -> Result<Self, D::Error>
    where
        D: serde::Deserializer<'de>,
    {
        let signed_tx_base64 = <String as serde::Deserialize>::deserialize(deserializer)?;
        let signed_tx_borsh = from_base64(&signed_tx_base64).map_err(|err| {
            D::Error::custom(&format!("the value could not decoded from base64 due to: {}", err))
        })?;
        borsh::from_slice::<Self>(&signed_tx_borsh).map_err(|err| {
            D::Error::custom(&format!("the value could not decoded from borsh due to: {}", err))
        })
    }
}
