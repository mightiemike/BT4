# Analog Found

### Title
DAO `egroup` mask reassignment orphans existing positions, permanently blocking liquidation and partial collateral withdrawal - (File: `mainnet/contracts/registry/v0-egroup.clar`)

### Summary
`v0-egroup::update` lets the DAO relabel an egroup's risk-parameter bucket by deleting the old `MASK -> id` mapping and inserting a new one, with no check that live positions still reference the old mask. `v0-4-market.clar`'s `liquidate` and `collateral-remove` both resolve a position's egroup via `try! (get-egroup mask)` using the position's *current* collateral/debt bitmask. If that exact mask is no longer resolvable after a DAO update, both calls revert unconditionally — mirroring the reNFT `onStop` hook-disable bug, where a value fixed at position-creation time (the hook address / the egroup mask) is invalidated later by an admin action, and the exit path (`stopRent` / `liquidate`) has no fallback other than reverting.

### Finding Description
Each user position stores a bitmask combining enabled collateral and debt asset bits [1](#0-0) . To act on that position, the market resolves the corresponding egroup via `.v0-egroup resolve mask`, implemented with a strict-subset bucket search [2](#0-1) .

The DAO can call `update` on an existing egroup id to change its `MASK`. This function unconditionally deletes the previous mask's reverse-lookup entry and bucket membership, then inserts the new mask, with no check for outstanding positions still keyed to the old mask: [3](#0-2) 

If no other still-registered egroup mask happens to be a superset of a given position's exact mask, `find`/`resolve` for that mask permanently returns `ERR-NO-EGROUP-FOUND` going forward.

Both the liquidation path and the partial-collateral-withdrawal path depend on this resolution succeeding via `try!`, so either failure aborts the whole transaction:

- `liquidate`: `(group (try! (get-egroup mask)))` [4](#0-3) 
- `collateral-remove` (HAS-DEBT branch): `(current-group (try! (get-egroup position-mask)))` [5](#0-4) 

By contrast, `repay` never calls `get-egroup` at all [6](#0-5) , and `collateral-remove`'s NO-DEBT branch skips egroup/price resolution entirely [7](#0-6)  — so a borrower can still fully close out by repaying 100% of debt first. However, until that full repayment happens, both liquidation and partial collateral withdrawal for that mask are unconditionally bricked.

### Impact Explanation
This lands on two of the in-scope impact classes:
- **Temporary freezing of funds** — any borrower whose exact mask is orphaned cannot partially withdraw collateral while retaining debt; they are forced into an all-or-nothing repay to regain access.
- **Protocol insolvency (Critical)** — more severely, liquidators cannot liquidate an unhealthy position with the orphaned mask at all. If the collateral value later crashes, the position accrues bad debt that can never be seized via `liquidate`, directly threatening protocol solvency, exactly analogous to how the reNFT `onStop` disablement stranded lender assets with no path to recovery.

### Likelihood Explanation
This requires only a routine DAO governance action — updating an egroup's risk parameters/mask combination (e.g., to add/remove an asset from a risk bucket) — while positions are open under the old mask, with no requirement of any additional bug, oracle failure, or malicious behavior. `egroup::update` performs no liveness check against `market-vault` positions, so this can be triggered inadvertently during ordinary risk-parameter maintenance.

### Recommendation
Before allowing `egroup::update` to delete/replace a `MASK`, either:
1. Require the new registry to retain the old mask as a resolvable (super)set until all positions have migrated, or
2. Query `market-vault`/maintain a migration mechanism so existing positions get remapped to the new egroup atomically, or
3. Have `liquidate` and `collateral-remove` fall back to a conservative default egroup (e.g., the most restrictive) instead of hard-reverting when `resolve` fails, so liquidation and collateral exits are never fully blocked by a registry change.

### Proof of Concept
1. DAO registers egroup `#5` with `MASK = {collateral: STX, sBTC; debt: USDC}` via `v0-egroup::insert`.
2. Alice opens a position using exactly that mask: supplies STX+sBTC collateral, borrows USDC — `market::borrow` succeeds because `resolve` finds egroup `#5` [8](#0-7) .
3. DAO later calls `v0-egroup::update` on id `5`, changing its `MASK` to a different asset combination (e.g., adding a new collateral asset) as part of normal risk recalibration. This deletes the `reverse` entry for Alice's original mask and inserts the new one [9](#0-8) .
4. STX price drops, Alice's position becomes unhealthy. A liquidator calls `market::liquidate(alice, ...)`. `get-liquidation-position` returns Alice's original mask; `(try! (get-egroup mask))` now returns `ERR-NO-EGROUP-FOUND`, and the entire liquidation reverts [4](#0-3) .
5. Alice also cannot call `collateral-remove` for a partial withdrawal while debt remains, since it hits the same `try! (get-egroup position-mask)` failure [5](#0-4) .
6. The position is stuck unliquidatable while unhealthy, and Alice's only way out is a full repay-then-withdraw in two separate transactions — if she cannot/does not repay in time, bad debt accrues with no liquidation recourse.
