## Title
`ensure_match_transaction_info` skips checkpoint/hot-state root fields, letting corrupted `TransactionInfoV1` state roots pass replay-verification - ([File: types/src/transaction/mod.rs])

## Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the chunk executor's replay-verification path (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) to confirm that locally re-executed transaction outputs match the `TransactionInfo` records read from a backup/chunk stream before they are trusted and applied. The function explicitly does **not** check the `TransactionInfoV1` checkpoint/hot-state root fields.

## Finding Description
`ensure_match_transaction_info` compares status, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash between the locally computed `TransactionOutput` and the untrusted `TransactionInfo` supplied by the chunk/backup source, but the function's own trailing comment states this comparator intentionally "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)": [1](#0-0) 

This means that any additional authenticated root fields carried in `TransactionInfoV1` (hot-state root, and the trading-native/position state checkpoint hash gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` features) are not independently recomputed and cross-checked against the locally executed result during replay-verification. The check only guards write-set hash, event root, gas, and status — the newer commitment fields added to `TransactionInfoV1` are left unverified in this code path.

## Impact Explanation
If a value in one of these unchecked fields (hot-state root or trading-native/position-tree state root) were ever corrupted or diverges between the persisted/backed-up `TransactionInfo` and the actual VM re-execution result, the chunk executor's `verify_execution` (`execution/executor/src/chunk_executor/mod.rs`, lines 648-708) would report success anyway, since it only inspects the fields validated by `ensure_match_transaction_info`. This would let a divergent or hard-fork-only-different ledger state pass "verify-execution"/replay-verify tooling undetected, defeating one of the primary purposes of that tool (catching state-commitment divergence). This is precisely the kind of "authenticated API/proof-bearing response bound to the wrong ... proof context" gap called out in the Proof And Storage Pivots.

## Likelihood Explanation
Practical exploitability is low today: the fields in question (hot-state root, trading-native checkpoint hash) are gated behind features (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) that are not confirmed enabled on mainnet, and the code's own comment flags this as a known gap to close "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." I was not able to fully confirm, within the remaining tool budget, (a) the current activation status of these feature flags on mainnet, or (b) whether some other check elsewhere in `execution/executor/src/workflow/do_ledger_update.rs` (which does reference `position_state_checkpoint_hash` and `hot_state_root_hash` 13 times) independently validates these fields during normal block-commit (as opposed to the chunk-executor replay-verify path). I could not complete that trace before running out of iterations.

## Recommendation
Extend `ensure_match_transaction_info` to recompute and compare the hot-state root and position/trading-native state checkpoint hash whenever they are present in `TransactionInfoV1`, so that replay-verify and restore tooling cannot silently accept a `TransactionInfo` whose extended commitment fields diverge from the actual VM execution result. This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network, as the surrounding comment already recommends.

## Proof of Concept
Not independently constructible from the indexed code alone: the gap is explicit and self-documented in code (`types/src/transaction/mod.rs`, lines 2197-2203), but I could not confirm within this session whether an equivalent, independent check exists in `do_ledger_update.rs` for the normal (non-replay) commit path, nor the mainnet activation state of the gating features. Given this uncertainty, I present this as a documented-but-unverified gap rather than a fully proven, currently-exploitable defect — the strongest analog I could substantiate with local code, but not with full certainty of end-to-end impact.
