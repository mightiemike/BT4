### Title
`replay_on_archive`/`ensure_match_transaction_info` skips checkpoint-hash verification, letting a diverged state root pass replay-verify as authenticated - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by the replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`) to check that locally re-executed transaction outputs match the previously committed, signed `TransactionInfo` — only compares `status`, `gas_used`, `state_change_hash` (write set), and `event_root_hash`. It explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description
The comparator's own inline comment documents the gap: [1](#0-0) 

`ensure_match_transaction_info` performs field-by-field checks against the authenticated `TransactionInfo` (the leaf committed in the transaction accumulator and signed over by validators via the `LedgerInfo`), but the state-checkpoint-related hash fields carried by `TransactionInfoV1` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are never asserted against the locally recomputed state root: [2](#0-1) 

These checkpoint hashes are exactly the fields meant to bind a `TransactionInfo` to the resulting global/native state Merkle root at that version — the "Committed state that differs from the correct VM result" invariant the review scope calls out. Because they're excluded from the comparison, `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::verify`/`execute_and_verify` path (which drives `ensure_match_transaction_info` as its core pass/fail check when replaying archived transactions) can report success even though the locally computed state (Jellyfish Merkle / position-state) root diverges from the state root that was actually authenticated in the historical `LedgerInfoWithSignatures`.

### Impact Explanation
This weakens exactly the class of check the state-integrity gate is meant to protect: an authenticated, proof-bound value (the state checkpoint root recorded in `TransactionInfo` and covered by the accumulator/`LedgerInfo` signature) is not independently re-verified during replay. A regression in state computation (e.g., in a new "trading-native"/position-state feature gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, per the code's own TODO) that corrupts the durable state root would not be caught by replay-verify, since the tool only checks write-set/event/gas/status equality, not the checkpoint hash. This can mask hard-fork-relevant divergences between the historical committed ledger and a node's re-execution of it.

### Likelihood Explanation
The gap is intentional/known — the code has an explicit TODO acknowledging it — but it is live in the shipped comparator with no gating that prevents `replay_on_archive` from being relied upon as a full state-root check. The precondition for actual exploitation (a bug elsewhere that corrupts the checkpoint/position-state root) is external to this function, so this finding by itself is a detection-gap rather than a directly exploitable state corruption. I was not able to fully trace whether `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` are validated by some other path (e.g. within `chunk_executor`'s own execution pipeline before or independent of `ensure_match_transaction_info`), so I can't confirm this is the *only* line of defense — that would need further investigation of `execution/executor/src/chunk_executor/mod.rs`'s chunk-commit verification and `ReplayChunkVerifier`, which I did not have iterations left to fully inspect.

### Recommendation
Extend `ensure_match_transaction_info` to assert `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values whenever the transaction is a checkpoint boundary, consistent with how `state_change_hash` and `event_root_hash` are already checked, before enabling any state root computed via `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not independently constructible from static analysis alone — the divergence requires a separate root-cause bug in state/position-state root computation. The concrete, verifiable local fact is the code comment itself acknowledging that `ensure_match_transaction_info` "ignores the checkpoint hashes... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution": [1](#0-0) , combined with `storage/db-tool/src/replay_on_archive.rs`'s reliance on this exact comparison during archive replay-verification: [3](#0-2) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
