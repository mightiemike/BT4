`IsValidAddress(addr, utils.HEX)` calls `common.IsHexAddress(addr)`, which only checks hex format/length — it accepts `0x0000000000000000000000000000000000000000` as valid. So the `Inbound.Recipient` and `RevertInstructions.FundRecipient` validation paths (`x/uexecutor/types/inbound.go` `ValidateForExecution`) never reject the EVM zero address, mirroring the reported class of bug (an attacker-suppliable zero address slipping through address validation into a fund-moving flow).

### Title
Zero-address `RevertInstructions.FundRecipient` / `Inbound.Recipient` passes validation and permanently burns bridged PRC20 funds - (File: x/uexecutor/types/inbound.go, x/uexecutor/keeper/build_revert_outbound.go, x/uexecutor/keeper/outbound.go)

### Summary
`Inbound.ValidateForExecution` and the revert/refund construction path only check that `Recipient` / `RevertInstructions.FundRecipient` are non-empty and pass `common.IsHexAddress`, per [1](#0-0) . `common.IsHexAddress` (`utils/address.go`) accepts the literal zero address `0x000...000` as valid, per [2](#0-1) . This is the direct analog of the `yieldTrackers` zero-address gap: the array/field of destination addresses accepted from attacker-influenced external-chain input is never checked against the zero address before it is used to move funds.

### Finding Description
An inbound observation's `RevertInstructions.FundRecipient` field is populated from data an unprivileged external-chain caller supplies to the gateway/vault contract being watched by Universal Validators (it flows in as part of the `Inbound` message that UVs vote on, per `proto/uexecutor/v1/types.proto` `RevertInstructions`). The only validation performed anywhere in the pipeline is a non-empty string check:
- `buildRevertOutbound`: `if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" { recipient = inbound.RevertInstructions.FundRecipient }` [3](#0-2) 
- `handleFailedOutbound`: same non-empty-only check before calling `CallPRC20Deposit(ctx, prc20, common.HexToAddress(recipient), amount)` [4](#0-3) 
- `applyGasRefund`: same non-empty-only check before `CallUniversalCoreRefundUnusedGas` [5](#0-4) 

None of these paths reject `0x0000000000000000000000000000000000000000`. `common.HexToAddress` will happily parse it to the EVM zero address, and `CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas` will mint/transfer PRC20 tokens to that address — which is unrecoverable (there is no private key, no burn-recovery mechanism referenced anywhere in the codebase). The primary `Inbound.Recipient` field for `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound types has the identical gap: `utils.IsValidAddress(p.Recipient, utils.HEX)` only calls `common.IsHexAddress`, per [6](#0-5) , so `depositPRC20` in `execute_inbound_funds.go` can mint newly-bridged PRC20 directly to the zero address, per [7](#0-6) .

### Impact Explanation
Any PRC20 minted or refunded to the zero address is permanently and unrecoverably lost — this falls squarely within the in-scope "permanent loss of user or protocol-controlled funds" category. Because the value is honestly observed and voted on by honest UVs (the corruption is in the input, not in validator misbehavior), this is reachable purely through an ordinary user/attacker-controlled source-chain transaction, matching the "reachable from ordinary user deposits ... alone" allowed-impact criterion.

### Likelihood Explanation
The condition requires only that the external-chain event data (attacker-controlled `recipient` or `revertInstructions.fundRecipient` field encoded in the gateway/vault call) contain the zero address — trivially producible by any unprivileged caller of the source-chain gateway contract, with no special privileges, validator collusion, or race condition needed. The check that exists (`common.IsHexAddress`) gives a false sense of safety but structurally cannot catch this case since the zero address is syntactically a valid hex address.

### Recommendation
Add an explicit zero-address rejection alongside every hex-address validation used for fund-moving fields: reject `strings.EqualFold(addr, "0x0000000000000000000000000000000000000000")` (or compare against `common.Address{}` after `HexToAddress`) in:
- `Inbound.ValidateForExecution` for `Recipient` (`x/uexecutor/types/inbound.go`)
- `buildRevertOutbound`, `handleFailedOutbound`, and `applyGasRefund` before using `RevertInstructions.FundRecipient` (`x/uexecutor/keeper/build_revert_outbound.go`, `x/uexecutor/keeper/outbound.go`)

Treating a zero-address recipient the same as an "invalid recipient" (i.e., routing to a FAILED PCTx / fallback-to-sender path) closes the gap without changing the existing fallback semantics already implemented for `nil`/empty `RevertInstructions`.

### Proof of Concept
1. Attacker calls the external-chain gateway/vault contract to bridge funds to Push Chain, setting `revertInstructions.fundRecipient = "0x0000000000000000000000000000000000000000"` in the event payload (or, for the direct-loss variant, sets the inbound `recipient` field itself to the zero address where the source-chain event schema allows an arbitrary destination string).
2. Honest UVs observe the event exactly as emitted and vote `MsgVoteInbound` with this data; `ValidateBasic`/`Canonicalize` do not reject it (`Inbound.Canonicalize` only trims/canonicalizes, per [8](#0-7) ).
3. Ballot finalizes; execution reaches `ValidateForExecution`, which accepts the zero address because `common.IsHexAddress` returns `true` for it, per [6](#0-5)  and [2](#0-1) .
4. `depositPRC20`/`CallPRC20Deposit` (or, on a subsequent failed outbound/refund path, `handleFailedOutbound`/`applyGasRefund`) mints/transfers PRC20 to `0x000...000`, permanently destroying the corresponding bridged value with no recovery path in the codebase.
