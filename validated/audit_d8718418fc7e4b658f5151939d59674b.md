## Finding

### Title
Unconditional relayer-fee payment in `inner_rlp_execute` moves value even when the intended wallet action later fails — ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point emulates Ethereum transactions and pays the relayer a fee for delivering base-token/ERC-20 emulated transfers. This fee is dispatched as an independent promise **before** the outcome of the actual user-intended action (transfer / function call) is known, and it is never rolled back or conditioned on that action's success. This is the same bug class as the reported `WETHRouter.redeem()` issue: a value-moving step is executed on the optimistic assumption that a preceding/parallel operation succeeded, without checking (or being able to check, since receipts are asynchronous) that it actually did.

### Finding Description
In `inner_rlp_execute`, once the RLP transaction is parsed successfully, the code unconditionally schedules a transfer of the relayer's fee: [1](#0-0) 

This fee-refund promise is created via `env::promise_batch_create(&context.predecessor_account_id)` / `env::promise_batch_action_transfer` — a **separate receipt**, independent from the receipt(s) that will later perform the user's actual intended action (transfer, `ft_transfer`, function call, etc.), which is only constructed afterwards in the `match transaction_kind` block: [2](#0-1) 

Because these are two independent receipts dispatched to different receivers, NEAR's receipt execution model gives no atomicity between them: if the main action's receipt later fails (e.g. the `address_check_callback` determines the relayer sent to a target that is actually a registered named account, or the downstream cross-contract call fails), the failure is reported back via `rlp_execute_callback`/`address_check_callback` as `success: false`: [3](#0-2) 

but the relayer fee promise dispatched earlier in `inner_rlp_execute` has already executed and cannot be reverted. The only compensating logic that exists is a refund of the *caller's deposit* on failure (`rlp_execute_callback`, lines 296-312), which is a different value (the caller's attached deposit) and does not touch/undo the fee already paid to the relayer.

The code comments themselves acknowledge this design choice ("we do not increment the nonce... to allow another relayer to safely serve base token transfers... because the relayer will receive some compensation for sending the transaction") but do not account for the case where the relayer is the party that caused the failure (e.g. via the faulty-relayer/"Invalid target" path) and still collects payment.

### Impact Explanation
An external relayer submitting an `rlp_execute` NEAR transaction (a transaction any unprivileged account can send since no access key is required for relaying) can be paid its NEAR-gas-compensation fee out of the user's wallet contract balance even when the user's intended action (the actual token/base-currency transfer) does not occur. This is unauthorized value movement: the wallet's balance is drained by the fee while the user receives none of the intended service. Because the "invalid target" / faulty-relayer condition is reachable simply by supplying a target address that already resolves to a registered named account (a condition controllable by the relayer constructing the transaction), a relayer can systematically trigger it to collect fees on transactions it knows will fail, at the expense of Wallet Contract balances.

### Likelihood Explanation
Reachable directly from a single NEAR transaction call to `rlp_execute` (or via an access key granted to a relayer) — no privileged role, validator behavior, or network-level compromise is required. The relayer only needs to construct a target/fee combination that triggers the "faulty relayer" / address-check failure path after the fee-refund promise has already been dispatched, which is entirely under the relayer's control.

### Recommendation
Do not dispatch the relayer-fee transfer promise until the outcome of the user's intended action is known. Either:
- Chain the fee-payment promise with `.then(...)` after the main action promise so it only executes conditionally on (or with a check inside a callback of) the main action's success, or
- Move the fee transfer into the same batch/receipt as the main action so both share the same execution atomicity, or
- Perform the fee payment inside `rlp_execute_callback`/`address_check_callback`, gated on `PromiseResult::Successful`.

### Proof of Concept
1. Relayer (any account, no special privilege) submits `rlp_execute(target, tx_bytes_b64)` where the embedded Ethereum transaction is a base-token transfer with a non-zero `gas_price` (i.e. non-zero `fee`) and `target` is an eth-implicit account whose address happens to already be registered under a named NEAR account in the address registrar.
2. `inner_rlp_execute` parses this as `EOABaseTokenTransfer{ address_check: Some(address), fee }`; because `fee` is non-zero and predecessor != wallet, the fee-refund promise to the relayer fires immediately: [4](#0-3) 
3. The address-registrar lookup promise later resolves in `address_check_callback` finding `maybe_account_id.is_some()`, and since the relayer used its own account (not an access key), the callback returns `success: false, error: "Invalid target: target is address corresponding to existing named account_id"`: [5](#0-4) 
4. The intended base-token transfer never happens (whole `rlp_execute` call reports failure), yet the relayer has already been paid `fee` yoctoNEAR out of the wallet contract's balance from step 2, which is never reclaimed.

            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call

                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())

                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }

            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
