### Title
Unbounded witness reward-per-vote (`Vi`) inflation causes silent `long` truncation/corruption in vote-reward accounting - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
`DelegationStore.accumulateWitnessVi()` computes a cumulative "reward-per-vote" index (`Vi`) using a large fixed multiplier `DECIMAL_OF_VI_REWARD = 10^18`, dividing by the witness's total vote count for that cycle. This is structurally the same pattern as the reported `pointsPerShare` bug: a large precision multiplier combined with an attacker-influenceable, potentially tiny denominator (`voteCount`) that can drive the accumulated index arbitrarily high over many cycles. Later, when a user's reward is computed, this inflated `Vi` delta is multiplied by the user's own vote count and divided back down, then converted with `BigInteger.longValue()`, which — unlike Solidity's checked arithmetic — does not revert on overflow, it silently truncates to the low 64 bits, corrupting the computed reward value. [1](#0-0) [2](#0-1) 

### Finding Description
`accumulateWitnessVi()` is invoked every maintenance cycle for every witness: [3](#0-2) 

`deltaVi = reward * DECIMAL_OF_VI_REWARD / voteCount` is accumulated into `preVi` and stored per cycle as an unbounded `BigInteger`: [2](#0-1) 

Because `voteCount` (the witness's total vote weight for that cycle) can be very small relative to `reward`, and because this value compounds cycle over cycle (`preVi.add(deltaVi)`), `Vi` can be driven to an arbitrarily large `BigInteger` over time — analogous to how the audited contract's first minter inflates `pointsPerShare` via a tiny share denominator combined with a large `POINTS_MULTIPLIER`.

When any voter later withdraws their reward, the code recombines the inflated `Vi` delta with the user's own vote weight and divides by the same multiplier, then truncates to a `long` via `BigInteger.longValue()`: [4](#0-3) [5](#0-4) [6](#0-5) 

`BigInteger.longValue()` per the JDK contract does **not** throw on overflow — it silently returns only the low-order 64 bits of the value. This is the critical divergence from the Solidity analog (which reverts on `int256` overflow, causing a DoS). Here, instead of a revert, the computed `reward` (a `long`) can wrap to an arbitrary, potentially negative value that is then added directly to the account's on-chain allowance/balance: [7](#0-6) 

This reachable path starts from ordinary, unprivileged `VoteWitnessContract` broadcast transactions (`VoteWitnessActuator`/`VoteWitnessProcessor`) and reward-withdrawal paths (`WithdrawBalanceContract` → `MortgageService.withdrawReward`), i.e. it is triggerable by any network participant, not a privileged actor. [8](#0-7) 

### Impact Explanation
Because the failure mode is silent truncation rather than a revert, the consequence is accounting corruption rather than a clean DoS: a user's computed reward `long` can become drastically wrong (including negative), meaning `AccountCapsule.setAllowance()`/balance updates can be silently corrupted, allowing incorrect crediting/debiting of TRX reward balances network-wide. This is a state-consistency and asset-accounting risk affecting the reward subsystem used by every voter and witness, and (if replicated inconsistently, e.g. due to differing intermediate state) could also contribute to consensus divergence between nodes computing the same reward at different times.

### Likelihood Explanation
Exploitability depends on driving a witness's total `voteCount` low enough, for a cycle in which it still earns block-production reward, that the accumulated `Vi` — after further large vote inflows in later cycles — pushes `deltaVi.multiply(userVote)` past `Long.MAX_VALUE` even after dividing by `10^18`. On a production TRON mainnet with 27 top SRs requiring very large vote totals this is hard to engineer, but the same code and accounting mechanism is unprivileged, protocol-level, and reused by any java-tron-based chain (including permissioned/private or low-participation networks), where witnesses can realistically have very small vote totals for a cycle. The bug itself (lack of overflow checking in the `BigInteger.longValue()` conversion) is unconditionally present regardless of exploit difficulty.

### Recommendation
- Replace the unchecked `BigInteger.longValue()` conversions in `MortgageService.computeReward`, `VoteRewardUtil.computeReward`, and `RewardViCalService.getNewRewardAlgorithmReward` with a checked conversion (e.g. `longValueExact()` wrapped to fail safely, or explicit range checks) so that overflow is detected and handled deterministically instead of silently corrupting the value.
- Consider bounding/normalizing `Vi` accumulation, e.g. clamping minimum `voteCount` used in the division, or capping the maximum per-cycle `deltaVi`, to prevent low-vote cycles from causing disproportionate index inflation.
- Add invariant/sanity checks after reward computation (e.g., `reward >= 0` and `reward <= reasonable upper bound`) before crediting `AccountCapsule` allowance.

### Proof of Concept
1. A witness `W` has an extremely low total vote count for cycle `c` (e.g., `voteCount = 1`) yet still receives a block-production `reward` for that cycle (feasible on low-participation java-tron-based networks).
2. `DelegationStore.accumulateWitnessVi(c, W, 1)` computes `deltaVi = reward * 10^18 / 1`, adding a very large value into the cumulative `Vi(c, W)`. [9](#0-8) 
3. Over subsequent cycles, additional voters flood into `W` with large vote counts, driving up the witness's aggregate weight while the historical `Vi` delta remains inflated from step 2.
4. A voter who was present across the inflated cycle range calls withdraw/vote-again, triggering `computeReward`/`withdrawReward`, where `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD).longValue()` is computed. [10](#0-9) 
5. If the resulting `BigInteger` exceeds `Long.MAX_VALUE`, `longValue()` truncates silently to an arbitrary (possibly negative) `long`, which is added to the account's `allowance` field via `adjustAllowance`, corrupting the on-chain reward balance without any error or revert. [7](#0-6)

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;

    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();
