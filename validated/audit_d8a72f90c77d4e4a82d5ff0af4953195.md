### Title
Poison-microblock equivocation check compares full `block_hash()` (which includes the signature bytes) instead of the signed content, allowing a malleable resignature of a single microblock to be reported as equivocation - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`process_poison_microblock`'s validation in `transactions.rs` rejects a poison report only when `mblock_header_1.block_hash() == mblock_header_2.block_hash()`. Because `StacksMicroblockHeader::block_hash()` is computed over the fully serialized header, including the `signature` field, two headers with identical `prev_block`, `sequence`, and `tx_merkle_root` but different (malleated) signature encodings of the same digest produce different `block_hash()` values while still recovering to the same `pubkh`. This lets an attacker take a single legitimately-broadcast microblock, derive a second ECDSA signature `(r, n-s)` for the identical signed digest (standard signature malleability, no private key needed), and submit it as a "second, conflicting" microblock header in a `PoisonMicroblock` transaction.

### Finding Description
The equality the code relies on for detecting equivocation is `header_1.block_hash() != header_2.block_hash()` combined with `pubkh_1 == pubkh_2` and `sequence_1 == sequence_2`. This is intended to be equivalent to "the same key signed two distinct microblocks at the same sequence," but `block_hash()` is a hash of the *entire serialized header, including the signature field*, not of the signed digest (`prev_block`, `sequence`, `tx_merkle_root`) alone. ECDSA signatures are malleable: given a valid signature `(r, s)` over a digest, anyone can compute `(r, n-s)` with the recovery bit flipped and obtain another signature that recovers to the exact same public key over the exact same digest, without knowing the private key. If the attacker builds `mblock_header_2` as `mblock_header_1` with only the signature field replaced by this malleated encoding, `mblock_header_2.block_hash() != mblock_header_1.block_hash()` (since the signature bytes differ) even though `prev_block`, `sequence`, and `tx_merkle_root` — i.e., the actual microblock content — are identical, and `check_recover_pubkey` returns the same `pubkh` for both. The existing `block_hash()`-based guard therefore does not catch this case, and the transaction proceeds as if two conflicting microblocks were signed by the miner, when in fact only one microblock was ever produced.

### Impact Explanation
This allows an innocent, non-equivocating miner to be falsely flagged as having equivocated and slashed (per Stacks' poison-microblock forfeiture rules), which is a wrongful reward/penalty mis-payment triggerable by an attacker with no special privilege — matching the "poison or reward mis-payment" High/Critical impact category, since it directly causes an incorrect on-chain penalty against a specific victim miner without requiring majority stake.

### Likelihood Explanation
The attacker only needs to observe one broadcast microblock header signed by the target miner (public information) and perform a standard, well-known ECDSA malleability transform (`s' = n - s`, flip recovery id) to produce a second valid signature over the identical digest — no BTC spend, no signer/majority stake, and no privileged role is required. The only open question (which I could not fully confirm from source inspection due to tool-call limits) is whether the signature-recovery path (`check_recover_pubkey` / the underlying `libsecp256k1` recovery routine) enforces canonical low-S signatures during parsing; if it does, this specific malleability vector is closed at that layer, and the reported issue would not be exploitable. I was not able to locate and read the exact body of `process_poison_microblock` / `check_recover_pubkey` to confirm this before running out of tool budget.

### Recommendation
Have the poison-microblock validation logic compare the signed content directly — i.e., require that `(prev_block, sequence, tx_merkle_root)` differ between `header_1` and `header_2` (or that their signed digests differ) rather than (or in addition to) comparing `block_hash()`. Additionally, ensure the signature-recovery routine enforces canonical (low-S) signature parsing so that malleated signatures are rejected outright before pubkh comparison.

### Proof of Concept
Rust integration test outline: construct one `StacksMicroblockHeader` with a valid signature; derive a second `MessageSignature` by flipping `s -> n - s` and the recovery id over the identical sign-hash; build `header_2` identical to `header_1` except for the signature bytes; assert `header_1.block_hash() != header_2.block_hash()` (confirming the malleated header bypasses the existing hash-equality guard) while `header_1.check_recover_pubkey() == header_2.check_recover_pubkey()` and `prev_block`/`sequence`/`tx_merkle_root` are identical; submit both as a `PoisonMicroblock` transaction and assert whether `process_poison_microblock` incorrectly accepts it as equivocation.
