## Title
`GlobalContractDistribution` receipts can crash chunk producers via `.unwrap()` on `receiver_shard_id()` after double resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs` unconditionally calls `.unwrap()` on `receiver_shard_id(&shard_layout)` when deciding whether a delayed receipt belongs to the current shard. This is analogous to the ATS prefetch plugin crashing on attacker/network-influenced input: a receipt whose target shard cannot be remapped by the current shard layout causes an unrecoverable `panic!`, i.e. a transaction-triggered chunk-processing halt.

### Finding Description
`receipt_filter_fn` is used by `DelayedReceiptQueueWrapper::pop` and `peek_iter` to filter delayed receipts that "belong" to a shard after resharding: [1](#0-0) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

This is called on every delayed-receipt `pop()` and `peek_iter()` call, which runs during ordinary chunk apply for every shard, every block: [2](#0-1) 

A `GlobalContractDistribution` receipt records a `target_shard` computed under the shard layout in effect at creation time. If that receipt is delayed (pushed to the delayed-receipt queue because the shard ran out of compute) and the shard undergoes **two** resharding events before the receipt is processed, `receiver_shard_id()` may fail to remap the receipt's stale `target_shard` under the new (twice-split) shard layout, returning an `Err` that gets `.unwrap()`ed into a panic. This exact scenario is documented and specifically regression-tested in the repository: [3](#0-2) 

```rust

// to remap the old target_shard after two resharding generations.
...

    "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
    head_height,
    drain_end

```

The test (`test_stale_global_contract_distribution_after_double_resharding`) constructs exactly this scenario: an unprivileged account submits a `deploy_global_contract` transaction whose resulting `GlobalContractDistribution` receipt targets a shard that is deliberately configured (via `force_split_shards`) to be split twice before the receipt drains from the delayed queue: [4](#0-3) 

The reachable path is: unprivileged user submits a `DeployGlobalContract` action → runtime creates a `GlobalContractDistribution` receipt targeting the current shard layout's shard → congestion/compute pressure delays it → two shard splits occur while it's delayed → `process_delayed_receipts` calls `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` → `receiver_shard_id().unwrap()` panics.

### Impact Explanation
A panic inside `Runtime::apply` (via `process_delayed_receipts`) during ordinary chunk application halts chunk production/validation on the affected shard for every honest node applying that chunk — this is a transaction-triggered chain halt, not merely a single-node crash, since all validators executing the same delayed-receipt queue would hit the identical panic deterministically. This matches the "Impact: transaction-triggered halt" acceptance criterion. It does not directly cause unauthorized value movement but does cause loss of liveness for the shard.

### Likelihood Explanation
Triggering requires: (1) submitting a `DeployGlobalContract`/global contract action (available to any unprivileged account with sufficient balance), and (2) two resharding events occurring on the target shard while the resulting distribution receipt sits in the delayed-receipt queue (achievable by saturating the shard's compute budget to force the receipt into the delayed queue, and by the network reaching resharding boundaries). On networks with dynamic resharding enabled and active, an attacker who can predict or influence shard-split timing (e.g. a large/active shard likely to trigger a split) can engineer this without any special privileges, though it does require the two resharding events to occur — this makes it non-trivial to hit but not privileged-only, and it is protocol-visible congestion behavior that any account can attempt to line up.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (`?`) so a shard-layout remap failure returns a `RuntimeError`/`StorageError` instead of panicking, and ensure `GlobalContractDistribution` (and any other) receipts retain a stable remapping path across multiple sequential resharding generations (e.g., by tracking ancestry chains rather than only immediate parent/child shard IDs).

### Proof of Concept
The repository's own test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs:32-186` is the proof of concept: it deploys a global contract from an unprivileged account, saturates the target shard's compute to delay the resulting distribution receipt, forces two sequential shard splits on that shard via `DynamicReshardingConfig.force_split_shards`, then drains the delayed queue and asserts the chain does not stall — directly exercising the `receipt_filter_fn` panic path described in the test's own comments.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }
