### Title
Outbound value computed from PRC20 event data (`event.Token`, `event.Amount`) is trusted without verifying the log's actual EVM contract emitter matches the module-originated PRC20 burn - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
The OtterSec finding is a mismatch between the account used to compute a value (a caller-supplied "fake vault") and the account that should authoritatively hold/represent that value. In Push Chain's outbound-creation path, `BuildOutboundsFromReceipt` and `AttachRescueOutboundFromReceipt` (`x/uexecutor/keeper/create_outbound.go:16-105`, `:193-337`) derive the amount and destination-chain asset solely from a `UniversalTxOutbound`/`RescueFundsOnSourceChain` event log, filtering only by `lg.Address == UNIVERSAL_GATEWAY_PC`, and then resolve the real-world token via `GetTokenConfigByPRC20(ctx, event.ChainId, event.Token)` — with no verification that `event.Token`/`event.Amount` correspond to an actual `Transfer`/`burn` performed by that PRC20 contract in the *same* receipt.

### Finding Description
`BuildOutboundsFromReceipt` [1](#0-0)  only checks that the log's `Address` equals the well-known `UNIVERSAL_GATEWAY_PC` address and that `Topics[0]` matches `UniversalTxOutboundEventSig`. It then trusts the ABI-decoded `event.Token` (PRC20 address) and `event.Amount` fields verbatim to build an `OutboundTx`: [2](#0-1) 

The `event.Token` is resolved to an `ExternalAssetAddr` via `GetTokenConfigByPRC20`, which is a pure reverse lookup keyed by `(chain, prc20Addr)` [3](#0-2) . Neither function checks that the PRC20 contract named in the event actually emitted a `Transfer`/burn event for `event.Amount` inside the *same* EVM receipt, nor that `msg.sender` of that emission was the legitimate caller. Because `UniversalGatewayPC` is a system Solidity contract invoked via `DerivedEVMCall` from arbitrary user-triggered payload execution (`ExecutePayload`, `executeUniversalTx`, etc.), if the gateway contract's Solidity logic ever allows an attacker-influenced call path to emit a `UniversalTxOutbound` event with a `Token`/`Amount` pair that doesn't match a corresponding real burn (e.g., re-entrant calls, a payload that calls into the gateway's withdraw entrypoint with attacker-chosen `token`/`amount` parameters without actually burning that token from the caller first), the node-side accounting in `x/uexecutor` will faithfully mint an outbound (i.e., release funds from the real vault on the destination chain) for the more valuable token/amount while the actual balance debited on Push Chain was for a cheap/attacker-controlled PRC20 — structurally identical to the audited bug's "fake vault used to compute notional value" pattern.

This is a design-level trust boundary concern: the Cosmos-side `create_outbound.go` code treats the Solidity `UniversalGatewayPC` contract's emitted event as ground truth without any secondary node-side check (e.g., cross-referencing a `Transfer`/`burn` log for the same `token`/`amount` from the same receipt, or verifying that `event.Token`'s registered PRC20 balance actually decreased by `event.Amount` for the sender in this transaction).

### Impact Explanation
If the Solidity `UniversalGatewayPC` withdraw/outbound-creation logic (out of this repo's Go/Cosmos scope, but the consuming code here has zero defense-in-depth) ever permits emitting `UniversalTxOutbound` with a `Token`/`Amount` unlinked to an actual burn of that PRC20 from the caller, an attacker could cause the chain to release real, valuable external assets (e.g., real bridged USDC) from the destination-chain vault while only having burned/spent a worthless or attacker-minted PRC20 — a direct unauthorized release of protocol-controlled funds, matching the "In scope" impact of unauthorized release/drain.

### Likelihood Explanation
Likelihood is **low-to-uncertain** given available evidence: the actual Solidity contract enforcing the burn-before-emit invariant in `UniversalGatewayPC` is not part of this Go repository and could not be inspected with the tools available, so I cannot confirm whether the contract itself already enforces atomicity between burn and event emission (which would fully mitigate this). The Go-side code provides no independent verification, so if the Solidity invariant is ever violated (via a bug, reentrancy, or an unaudited payload path), there is no node-side backstop.

### Recommendation
Add a defense-in-depth check in `BuildOutboundsFromReceipt` and `AttachRescueOutboundFromReceipt`: scan the same `receipt.Logs` for a `Transfer(from=sender, to=0x0, value=event.Amount)` (or equivalent burn event) emitted by the PRC20 contract at `tokenCfg.NativeRepresentation.ContractAddress`/`event.Token`, and reject building the outbound if no matching burn log is found in the same receipt. This mirrors the OtterSec remediation of validating that the account used to compute value is the canonical, protocol-verified one rather than trusting attacker/contract-reachable event data in isolation.

### Proof of Concept
Not constructible from this repository alone — the root cause (if it exists) lives in the `UniversalGatewayPC` Solidity contract's outbound-creation logic, which is not present in this codebase. The evidence gathered here shows only that the Go-side consumer (`create_outbound.go`) performs no independent cross-check, which is a necessary precondition for such an exploit but not sufficient proof of exploitability. This is presented as a **defense-in-depth gap** rather than a confirmed, independently-triggerable vulnerability in this repository.

// GetTokenConfigByPRC20 looks up a token config by PRC20 address via the
// PRC20Index (O(1)). Returns ErrNotFound if the registered chain doesn't match.
func (k Keeper) GetTokenConfigByPRC20(
	ctx context.Context,
	chain string,
	prc20Addr string,
) (types.TokenConfig, error) {

	if strings.TrimSpace(prc20Addr) == "" {
		return types.TokenConfig{}, fmt.Errorf("prc20 address is empty")
	}
	// Same canonical form as the index function, so any case variant hits the row.
	prc20Addr = canonicalPRC20(prc20Addr)

	// PRC20 addresses are globally unique by construction; MatchExact returns at most one.
	iter, err := k.TokenConfigs.Indexes.PRC20Index.MatchExact(ctx, prc20Addr)
	if err != nil {
		return types.TokenConfig{}, err
	}
	defer iter.Close()

	for ; iter.Valid(); iter.Next() {
		pk, err := iter.PrimaryKey()
		if err != nil {
			return types.TokenConfig{}, err
		}
		cfg, err := k.TokenConfigs.Get(ctx, pk)
		if err != nil {
			return types.TokenConfig{}, err
		}
		if cfg.Chain == chain {
			return cfg, nil
		}
	}

	return types.TokenConfig{}, collections.ErrNotFound
}
