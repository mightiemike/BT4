### Title
Replay-verify integrity check ignores state/hot-state/position-state checkpoint hashes, allowing corrupted committed state roots to pass validation - (File: `types/src/transaction/mod.rs`)

### Summary
This is an Aptos-native analog to the reported Solidity issue: two independently-toggled mechanisms (here, the `HOT_STATE_ROOT_IN_TXN_INFO` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on-chain features, which each add a distinct checkpoint-hash field to `TransactionInfoV1`) can drift out of sync with the code path that is supposed to *validate* them. `TransactionOutput::ensure_match_transaction_info`, the function used by replay/debugger/verification tooling to confirm that a locally recomputed transaction output matches the authenticated on-chain `TransactionInfo`, deliberately skips comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates status, gas used, write-set hash (`state_change_hash`), and event root hash against the stored `TransactionInfo`, but the code itself documents that it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)": [2](#0-1) 

This comparator is used by mainnet-facing verification/auditing tooling: `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` all call `ensure_match_transaction_info` to confirm that a fresh VM re-execution reproduces the authenticated, already-committed ledger data. Because the state-checkpoint-related hash fields are excluded from the comparison, a divergence in the Sparse-Merkle-Tree state root, the hot-state root, or the position-state root between the archived/authenticated `TransactionInfo` and a freshly recomputed one is not detected by this check. These root hashes are exactly the fields written into `TransactionInfoV1` by `DoStateCheckpoint`/`DoLedgerUpdate` ( [3](#0-2)  and [4](#0-3) ), gated independently by two separate on-chain feature flags (`hot_state_root_in_txn_info`, `compute_trading_native_state_roots`), mirroring the two independently-mutable Solidity parameters (`tradeFee` / `acceptedCurrency`) in the seed report.

### Impact Explanation
Replay-verify and debugger tooling are the primary mechanism used to independently attest that historical/archived mainnet ledger data is authentic and matches actual VM execution. Because the state/hot-state/position-state checkpoint hashes are excluded from `ensure_match_transaction_info`, these tools will report a "successful" replay even if the authenticated state root diverges from the true VM-computed root — i.e., committed/archived state data that is wrong (corrupted, tampered, or produced by a buggy feature interaction) is accepted as valid by the tool meant to catch exactly that class of error. This directly matches the state-integrity gate's "committed state that differs from the correct VM result" and "wrong ... proof accepted as valid" criteria, scoped to the replay/verification/proof-binding path rather than the live consensus commit path.

### Likelihood Explanation
The gap is deterministic and always present whenever the tools are used (no attacker interaction with consensus needed); it becomes practically relevant whenever `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and/or `HOT_STATE_ROOT_IN_TXN_INFO` diverge between what a node computed historically and what a verifier recomputes (e.g., differing feature gating between the version archived and the version replayed, or storage/backfill bugs affecting only checkpoint hash fields). The code comment itself flags this as a known, currently-unaddressed gap that "must" be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," confirming the maintainers recognize it as a real, exploitable blind spot rather than a theoretical one.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) against locally recomputed values before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and generally for all replay-verify/debugger call sites, so that a corrupted or diverging state/hot-state/position-state root can never be silently accepted as a "matching" replay.

### Proof of Concept
1. Enable/replay a version range where `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `HOT_STATE_ROOT_IN_TXN_INFO`) was toggled between the time the data was archived and the time it's replayed, or otherwise corrupt only the `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` field of an archived `TransactionInfo`.
2. Run `storage/db-tool/src/replay_on_archive.rs` (or `aptos-debugger`) against this data; it calls `TransactionOutput::ensure_match_transaction_info` [5](#0-4) .
3. Because the function only checks `status`, `gas_used`, `state_change_hash` (write-set), and `event_root_hash`, and explicitly skips the checkpoint hashes [2](#0-1) , the replay reports success (`Ok(())`) despite the corrupted/diverged state root, demonstrating that authenticated state-commitment data can differ from the true VM result without detection by this integrity check.

I was unable to fully trace, within the available tool budget, every downstream consumer of the replay-verify success signal (e.g., whether any mainnet gating decision relies solely on this tool's pass/fail result) — this would need further confirmation via a live Devin session with full repository access.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
