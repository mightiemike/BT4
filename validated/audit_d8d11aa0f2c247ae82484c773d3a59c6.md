### Title
`TokenConfig.LiquidityCap` is stored but never enforced, allowing PRC20 supply to exceed the configured cap - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`uregistry.TokenConfig` carries a `LiquidityCap` field intended to bound the maximum synthetic PRC20 supply Push Chain will mint for a given external token [1](#0-0)  and this field is required to be non-empty by `ValidateBasic` [2](#0-1) . However, no code path in `x/uexecutor` (or anywhere else) ever reads `LiquidityCap` to compare it against cumulative minted/deposited supply before minting.

### Finding Description
The mint path for every inbound deposit flows through `depositPRC20` in `x/uexecutor/keeper/handler.go`, which fetches the `TokenConfig` only to resolve the PRC20 contract address, and unconditionally calls `CallPRC20Deposit` for the full inbound amount: [3](#0-2) . `CallPRC20Deposit` issues a `DerivedEVMCall` to `depositPRC20Token`, minting the requested amount with no upstream cap check [4](#0-3) . This same unconstrained pattern applies to `ExecuteInboundFunds` [5](#0-4)  and `ExecuteInboundFundsAndPayload` [6](#0-5) , both of which deposit whatever amount honest validators voted through on `MsgVoteInbound`, without ever consulting `tokenConfig.LiquidityCap` or any running-total-minted counter.

Because `x/uregistry` exposes `GetTokenConfig` purely as a lookup and never tracks per-token cumulative supply, there is no mechanism anywhere in the codebase capable of enforcing the cap even if a check were added at a single call site — the invariant is entirely absent from state.

### Impact Explanation
An unprivileged user can lock/deposit real funds on the external gateway chain in amounts that, once validated and voted by honest Universal Validators through the standard `MsgVoteInbound` flow, cause `x/uexecutor` to mint PRC20 supply that exceeds the admin-configured `LiquidityCap` for that token. This corrupts the intended PRC20 supply-accounting invariant (`liquidity_cap` is meant as a hard ceiling per the field's doc comment: "max supply cap for this token"), defeating the risk-limiting purpose the field exists for — e.g., capping exposure to a bridge/vault backing a synthetic asset. This is a "corruption of PRC20 ... accounting" as defined in the allowed-impact scope, reachable purely from ordinary user deposit flows with honest validators and honest nodes, no privileged actor required.

### Likelihood Explanation
High likelihood of triggerability: any user who can fund enough real value on the source chain (or repeatedly deposit smaller amounts across many inbounds) can accumulate PRC20 supply past `LiquidityCap` with no special access, since the check simply does not exist anywhere in the mint path.

### Recommendation
Track cumulative minted/circulating supply per `(chain, address)` token in `x/uregistry` or `x/uexecutor` state, and before calling `depositPRC20`/`CallPRC20Deposit`, compare the post-mint total against `tokenConfig.LiquidityCap`. Reject or partially process (and revert/refund the excess) inbound deposits that would breach the cap, consistently across `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGas`.

### Proof of Concept
1. Admin registers a `TokenConfig` for `eip155:11155111` USDC with `LiquidityCap = "1000000000000000000000000"` (i.e., 1,000,000 USDC at 6 decimals via `MsgAddTokenConfig`).
2. An attacker (or several colluding but individually unprivileged senders) locks funds on the real gateway/vault contract on Sepolia for a cumulative amount well beyond the cap, e.g. 10,000,000 USDC across many transactions.
3. Honest Universal Validators observe and vote each inbound event via `MsgVoteInbound`; quorum is reached honestly each time (as shown by the existing test flow in `test/integration/uexecutor/inbound_solana_test.go` lines 138-165, which demonstrates unconditional minting equal to `inbound.Amount` on every quorum-reached vote).
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full amount every time; nothing compares the running total to `tokenConfig.LiquidityCap`.
5. The on-chain PRC20 total supply for that token now exceeds `LiquidityCap` by 9x, with no rejection, no partial mint, and no error recorded in `PcTx` — the cap is silently unenforced, identical in nature to the original `maxMembers` bug: a config value that exists purely for external/backend validation and is never checked in the actual state-mutating path.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
