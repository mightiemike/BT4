### Title
Missing chain-id domain separator in `ValidateMultiSign` precompile hash construction enables cross-chain signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract builds the message hash that signers must sign purely from `account address || permissionId || data`, with no chain identifier. [1](#0-0)  This mirrors the reported `hashForKYC()` issue: a proof/signature is verified without incorporating a domain separator (chain id + verifying context), so a signature valid on one TRON-compatible network can be replayed unchanged on another.

### Finding Description
`ValidateMultiSign.execute()` decodes `address`, `permissionId`, and `data` from calldata, then computes the hash signers must have signed as:

```java
byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), combine);
``` [2](#0-1) 

For each supplied signature, it recovers the signer address via `recoverAddrBySign(sign, hash)` and accumulates permission key weight until the account's `Permission.threshold` is met, returning success/failure to the calling smart contract. [3](#0-2) 

None of `chain.id`, a genesis/network identifier, or the calling contract's address is folded into `hash`. The same off-chain signature (over `address || permissionId || data`) is therefore valid input to `ValidateMultiSign` on any TRON-protocol network where that account exists with an equivalent permission configuration — e.g. TRON mainnet vs. a testnet (Nile/Shasta) vs. any private/forked deployment of this java-tron codebase, which is exactly the class of "different context, same signature" cross-domain issue described in the report for `hashForKYC()`.

This differs from `TransactionCapsule.checkWeight`, which verifies signatures over full transaction raw data (already bound to a specific chain via `ref_block`/expiration fields baked into the signed bytes), so that path is not affected. [4](#0-3)  The vulnerable pattern is isolated to the `ValidateMultiSign` precompile's self-constructed hash.

### Impact Explanation
`ValidateMultiSign` is a public, general-purpose authorization primitive exposed to any smart contract (e.g. multisig wallets, custodial exchange contracts, gasless meta-transaction relays) that want to check whether a threshold of an account's permission keys signed some `data`. Because the signed hash carries no chain-scoping, an authorization signature collected/broadcast for one network can be replayed against a same-named account with equivalent permission setup on a different network sharing this codebase (mainnet/testnet/fork), letting an attacker satisfy the threshold check and trigger unauthorized actions gated by `validatemultisign()` in the victim contract on the other chain. This is a concrete auth/replay impact, consistent in class with the reported medium-severity `purchaseAllowed()` finding.

### Likelihood Explanation
Exploitability requires: (1) a dApp built on top of `ValidateMultiSign` for authorization, and (2) the same account/permission structure existing (or being replicable) on more than one TRON-protocol network. This is a realistic scenario given the multiple official TRON networks (mainnet/Nile/Shasta) and the prevalence of forked/private java-tron deployments, but it depends on external conditions (multi-network account reuse and application design) rather than being unconditionally exploitable on a single chain — so likelihood is moderate, matching the "Medium" severity of the referenced report.

### Recommendation
Include a domain-separator in the `ValidateMultiSign` hash construction, analogous to the `hashForKYC()` fix: mix in `chain.id` (and optionally the calling/verifying contract address) before hashing, e.g. `combine = merge(chainId, address, permissionId, data)`, so a signature produced for one network/context cannot be replayed on another. A minimal fix does not require full EIP-712 compliance, consistent with the cited resolution approach.

### Proof of Concept
1. Deploy the same account address with an identical `Permission` (same `permissionId`, same keys/weights/threshold) on two TRON-protocol networks that share this java-tron code (e.g. mainnet and a private fork/testnet).
2. Off-chain, have permission-key holders sign `sha256(address || permissionId || data)` as required by `ValidateMultiSign.execute()`. [1](#0-0) 
3. Submit that same set of signatures to a contract calling `validatemultisign(address, permissionId, data, signatures)` on Network A — it succeeds (`dataOne()` returned once threshold weight is reached). [5](#0-4) 
4. Replay the identical, unmodified signatures against the analogous contract/account on Network B; since the hash has no chain-id binding, it recovers to the same signer addresses and again satisfies the threshold, authorizing an action never intended for Network B.
