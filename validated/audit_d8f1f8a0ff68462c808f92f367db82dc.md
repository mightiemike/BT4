### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, allowing replay-verify to accept a divergent state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity comparator used by replay-verification tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, and the CLI's replay/simulate commands) to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` pulled from a backup/archive. It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This means the one field that actually commits to the global Merkleized state root at a checkpoint is silently excluded from the comparison, so a divergent state root produced by local execution is not detected by this check.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` is called with a locally computed `TransactionOutput` and the authenticated `txn_info: &TransactionInfo` obtained from a proof-backed source (backup archive, on-chain ledger, etc.). It performs four checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed `event_root_hash` vs `txn_info.event_root_hash()`

It then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()` (the JMT/global state root recorded at checkpoint boundaries), or, for `TransactionInfoV1`, `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`. The function's own inline TODO acknowledges the gap for the trading-native fields: [2](#0-1) 

but the comment understates the issue — the base `state_checkpoint_hash` field (present since V0, not just the new trading-native V1 additions) is likewise never validated anywhere in this function.

This comparator is the mechanism that callers such as `replay_on_archive` and `aptos-debugger` rely on to assert "my local re-execution produced the exact same result as what was cryptographically committed." Because `TransactionInfo` objects come from an accumulator-proof-verified source, their `state_checkpoint_hash` field is authentic; the bug is that the *local* recomputation is never checked against it here, so a bug in execution, storage schema handling, or a state root computed by an unexpected code path (e.g. `DoStateCheckpoint`, `commit_native_position`/`position_summary_at_commit`) that produces a wrong state root would pass `ensure_match_transaction_info` as long as the write set bytes/hash and events still match. [3](#0-2) 
shows `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are all separately-computed fields fed into `TransactionInfo`; none of that provenance is cross-checked by the comparator used for replay verification.

### Impact Explanation
This falls under the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result" categories. Replay-verify tooling (`replay_on_archive`, `aptos-debugger`) exists specifically to catch cases where local execution diverges from the authenticated ledger state — e.g., after a VM/consensus upgrade, a storage schema change, or a subtle non-determinism bug. Because the state-root fields are excluded from the check, such divergence in the actual committed state tree can go completely undetected by this tooling even though the write-set/event hashes match, silently hiding state-integrity corruption or hard-fork divergence that operators and auditors depend on this exact check to catch. The severity is High for tooling correctness/auditability of ledger integrity, though it does not directly corrupt live consensus state (the accumulator/ledger info signature check for the authenticated `TransactionInfo` list itself remains sound); the risk is that an actual state-root bug in execution would pass replay-verification silently.

### Likelihood Explanation
This is not a hypothetical: the function's own TODO comment confirms the authors are aware that `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-related checkpoint hashes are unchecked, and the same reasoning shows the base `state_checkpoint_hash` field is similarly excluded from any check in this function. Any caller (`replay_on_archive`, `aptos-debugger`, `cli/commands.rs`) that relies solely on `ensure_match_transaction_info` for its final source-of-truth comparison will not surface a state-root mismatch. Whether other independent checks (e.g., separate root-hash equality asserted elsewhere in each specific call site) close this gap could not be fully confirmed within the available search — that is an open question requiring inspection of `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs` call sites, which time did not permit tracing fully.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, and for `TransactionInfoV1`, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the locally computed values (requiring these hashes to be threaded into the function's inputs, similar to how `expected_write_set`/`expected_events` are passed). Do this before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, per the existing TODO, and add explicit test coverage asserting that a mismatched checkpoint hash causes this function to return an error.

### Proof of Concept
Not applicable as a runnable exploit — this is a missing-check integrity gap in a verification utility rather than an executable transaction-triggered bug. The proof of the gap is the code itself: `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) constructs no comparison for `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, so any test/tool that constructs a `TransactionOutput` whose replay yields a different state root than the authenticated `TransactionInfo` — while keeping status/gas/write-set-hash/event-hash identical — will observe `ensure_match_transaction_info` return `Ok(())`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
