### Title
Non-deterministic Fiat-Shamir challenge in `Transcript::verify` causes validator disagreement on DKG `ValidatorTransaction` execution — hard-fork-only divergence - ([File: crates/aptos-dkg/src/pvss/das/weighted_protocol.rs])

### Summary
`Transcript::verify` in the weighted DAS PVSS scheme derives all of its batching/challenge randomness (`sok_vrfy_challenge`, the LDT challenge, and `alphas_betas_and_gammas`) from `rand::thread_rng()` instead of a deterministic Fiat-Shamir transform over the transcript's own bytes. [1](#0-0) 
This verify routine is invoked, unmodified by any deterministic reseeding, from the VM's DKG-result validator-transaction handler `process_dkg_result_inner`, which every validator executes identically as part of deterministic replicated execution. [2](#0-1) 
The call chain runs through `RealDKG::verify_transcript` → `trx.main.verify(...)`. [3](#0-2) 

### Finding Description
The verifier batches many pairing equations (`V`/`V_hat` low-degree test, ElGamal encryption correctness, SoK verification) into one multi-pairing check using random linear-combination coefficients (`alphas`, `betas`, `gammas`, `sok_vrfy_challenge`), and a randomized low-degree test (`LowDegreeTest::random`). [4](#0-3) 
This batching technique is only sound if the challenge is unpredictable to whoever produced the transcript *before* the transcript is fixed (i.e., a Fiat-Shamir hash of the transcript, or an honest interactive verifier's private randomness that the prover cannot influence per-verification). Here the randomness is drawn fresh from `rand::thread_rng()` on every call, completely independent of the transcript bytes and independent across every validator process.

Because Aptos's DKG result is submitted as a `ValidatorTransaction::DKGResult` and is verified inside `process_dkg_result_inner`, which is executed by the VM as part of block execution (deterministic state-machine replication), *every* validator in the network must arrive at exactly the same `Ok`/`Err` outcome for the same `dkg_node.transcript_bytes` in order to compute the same state root. A crafted transcript that is malformed in exactly one term of the multi-pairing product (e.g., one incorrect `C[k]`, `R[k]`, or `V_hat[k]` entry) will only be caught by the batched check with probability `1 - negligible` when honest, deterministic Fiat-Shamir challenges are used, but with the *same* fixed forged transcript and independently-drawn random coefficients on different machines, the check `res == Gt::identity()` at line 376 can evaluate to true on some validators and false on others purely because they sampled different `alphas_betas_and_gammas` / `sok_vrfy_challenge` values. [5](#0-4) 

Since `verify_transcript` returning `Ok` vs `Err` directly determines whether `process_dkg_result_inner` proceeds to invoke `finish_with_dkg_result` (publishing DKG state on-chain, producing a real write-set) or aborts with `TranscriptVerificationFailed` (producing an abort/discard status with a different, empty write-set), the two outcomes commit **different transaction outputs and different resulting state roots** for byte-identical input across the validator set — a hard-fork-only divergence exactly matching the review's target impact. [6](#0-5) 

The same non-determinism problem also exists in the ChunkyDKG verification path, which explicitly instantiates `rand::thread_rng()` per call. [7](#0-6) 
though for ChunkyDKG the immediate caller shown (`deserialize_chunky_transcript_and_verify`) is used during the peer-to-peer transcript aggregation/gossip phase, not directly at VM execution time — I was not able to fully confirm within available context whether ChunkyDKG's final certified output undergoes a second, VM-side deterministic re-verification analogous to `process_dkg_result_inner` for the classic DKG path, or whether it's trusted once aggregated and signed. This is a caveat on the Chunky variant specifically; the classic `DefaultDKG`/weighted DAS path traced above is unambiguously in the deterministic VM execution path.

### Impact Explanation
This is a genuine state-integrity/hard-fork risk gated by the review criteria: an unprivileged submitter (any validator acting as DKG dealer, or in principle any entity able to get a `DKGTranscript` payload into a `ValidatorTransaction`) can craft a transcript malformed in exactly one pairing term such that `verify()`'s Ok/Err outcome is a coin flip governed only by each validator's local `thread_rng()` draw, not by the (fixed) transcript bytes. Because block execution requires identical VM outputs across all validators to reach the same state root, this can partition the validator set into subsets that commit different `VMStatus` / write-sets for the same input transaction — a consensus-breaking hard fork requiring manual intervention (exactly the "hard-fork-only divergence" impact called out in scope).

### Likelihood Explanation
The engineering effort to exploit this is non-trivial (must construct a transcript that is well-formed everywhere except a deliberately chosen single pairing term with a computable/bounded forgery probability against the multi-pairing batch check), but it does not require any privileged access or protocol violation beyond what an on-chain DKG dealer is already permitted to submit — the code comment in the source explicitly acknowledges the underlying design flaw ("Deriving challenges by flipping coins... Creates bad RNG risks but we deem that acceptable"), indicating the non-determinism is real and was a conscious, but under-analyzed, tradeoff rather than a theoretical concern. [8](#0-7) 

### Recommendation
Replace `rand::thread_rng()`-derived batching challenges in `Transcript::verify` (and the analogous `ChunkyTranscript::verify` call site) with a deterministic Fiat-Shamir transform: derive `sok_vrfy_challenge`, the LDT randomness, and `alphas_betas_and_gammas` via a cryptographic hash (using the scheme's own `dst()`/DST binding already defined at line 161-163) over the canonical serialization of the transcript and public inputs, so that `verify()` is a pure function of its inputs and produces identical results on every validator.

### Proof of Concept
Deterministic code-level proof (cannot be executed in this environment, but derivable directly from the source):
1. In `crates/aptos-dkg/src/pvss/das/weighted_protocol.rs::verify`, note that `rng = rand::thread_rng()` (line 305) feeds `random_scalars` (line 306) which supplies both `sok_vrfy_challenge` (line 308) and `alphas_betas_and_gammas` (line 333), and also seeds `LowDegreeTest::random` (line 320-326) — none of these are derived from `self` (the transcript) or from `pp`/`spks`/`eks`/`auxs`.
2. Construct a `Transcript` `T` where a single `C[k]` (or `R_hat[k]`/`V_hat[k]`) entry is replaced with an incorrect group element (e.g., not matching the discrete-log relation asserted by `slow_verify`'s per-index pairing check at lines 519-536), such that the forged term only affects the aggregate multi-pairing result through the random coefficient `gammas[k]` or `alphas_and_betas[k]`.
3. Call `T.verify(sc, pp, spks, eks, auxs)` `N` times in a loop (each call internally re-samples `thread_rng()`); because the forgery's contribution to the aggregate `res` in line 375-376 is `(forged_error) * coefficient`, and the coefficient is uniformly random and independent per call, `res == Gt::identity()` will hold only for specific random coefficient values, producing a non-deterministic mix of `Ok(())` and `Err(...)` results across repeated calls with the exact same `T` bytes — directly modeling what independent validators would observe when each executes `process_dkg_result_inner` with the same `dkg_node.transcript_bytes` during block replay.

    /// NOTE: this is used in VM.
    fn verify_transcript(
        params: &Self::PublicParams,
        trx: &Self::Transcript,
    ) -> anyhow::Result<()> {
        // Verify dealer indices are valid.
        let dealers = trx
            .main
            .get_dealers()
            .iter()
            .map(|player| player.id)
            .collect::<Vec<usize>>();
        let num_validators = params.session_metadata.dealer_validator_set.len();
        ensure!(
            dealers.iter().all(|id| *id < num_validators),
            "real_dkg::verify_transcript failed with invalid dealer index."
        );

        let all_eks = params.pvss_config.eks.clone();

        let addresses = params.verifier.get_ordered_account_addresses();
        let dealers_addresses = dealers
            .iter()
            .filter_map(|&pos| addresses.get(pos))
            .cloned()
            .collect::<Vec<_>>();

        let spks = dealers_addresses
            .iter()
            .filter_map(|author| params.verifier.get_public_key(author))
            .collect::<Vec<_>>();

        let aux = dealers_addresses
            .iter()
            .map(|address| (params.pvss_config.epoch, address))
            .collect::<Vec<_>>();

        trx.main.verify(
            &params.pvss_config.wconfig,
            &params.pvss_config.pp,
            &spks,
            &all_eks,
            &aux,
        )?;

        Ok(())
    }
