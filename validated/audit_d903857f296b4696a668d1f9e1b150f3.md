### Title
Non-deterministic wall-clock tenure-extend gate lets signers disagree on identical block validity - (File: stacks-signer/src/chainstate/v2.rs)

### Summary
The signer-side rule that permits a time-based tenure extension compares each signer's own local wall-clock time against a computed `extend_timestamp`, exactly the kind of unsynchronized boundary check flagged in the source report (`block.timestamp >= dueDate`). Because every signer evaluates this locally and independently, and it is a soft (off-chain) rule rather than a deterministic on-chain consensus check, different signers can reach different Accept/Reject verdicts for the exact same proposed block depending on the instant they receive/evaluate it relative to the deadline.

### Finding Description
When a miner proposes a "full" tenure-extend block, each signer independently computes:
```
let extend_timestamp = signer_db.calculate_full_extend_timestamp(...);
let epoch_time = get_epoch_time_secs();
let enough_time_passed = epoch_time >= extend_timestamp;
``` [4](#0-3) 
and rejects the proposal with `RejectReason::InvalidTenureExtend` if `!changed_burn_view && !enough_time_passed && !is_in_replay` [5](#0-4) . The identical logic (and identical race) exists in the legacy v1 signer path [6](#0-5) .

`extend_timestamp` is a deterministic function of chain data (tenure start time + idle timeout, per `calculate_full_extend_timestamp`/`calculate_tenure_extend_timestamp` in `stacks-signer/src/signerdb.rs:2186-2246`), but the comparison operand, `get_epoch_time_secs()`, is each node's own local wall clock, subject to clock skew and network/propagation delay. A small `tenure_idle_timeout_buffer_secs` (default 2s) is added purely to blunt clock skew [7](#0-6) , but this is a fixed offset, not a synchronization guarantee — it only shifts the boundary, it does not eliminate the race, exactly analogous to the report's critique that the smart contract's boundary check is impossible to synchronize precisely.

Crucially, the on-chain, consensus-critical validation of a tenure-extend block (`NakamotoChainState::is_wellformed_tenure_extend_block`, `check_nakamoto_tenure`) never re-checks this timing condition [3](#0-2) [2](#0-1) . Block acceptance is instead gated purely by whether the miner collects enough weighted signer signatures (threshold, e.g. 70%) approving the identical block. Because "enough_time_passed" is evaluated independently per-signer at slightly different wall-clock instants, an unprivileged, currently-active miner can simply keep re-proposing the same tenure-extend block near the boundary until it happens to capture signatures from just the subset of signers (by weight) whose local clocks have already crossed `extend_timestamp`, even while other signers — evaluating microseconds/seconds earlier — would still reject the exact same block. Once the signer weight threshold is met, the resulting signed block is treated by the network as fully valid, since chainstate-level validation never re-derives or enforces the timing gate.

### Impact Explanation
This produces a "validation verdict two nodes [signers] disagree on" for the identical proposed block, allowed under the High-impact bucket ("a minority-triggerable sortition/VRF/static-validation divergence... temporary tip disagreement"). The practical effect is that a miner can obtain a premature tenure extension that a majority of signers (evaluating slightly earlier) would have rejected, exploiting a race condition rather than compromising signer keys or requiring majority collusion — mirroring the report's core issue of an un-synchronizable timestamp boundary enabling one party to unilaterally realize an outcome (early extension / early claim) that the protocol intended to gate behind an elapsed-time threshold shared by all participants.

### Likelihood Explanation
Likelihood is moderate: it requires no privileged access — only a miner that already legitimately holds the current tenure, which can retry proposing the same or a re-signed extend block multiple times around the deadline (a normal, unprivileged, protocol-permitted action, especially since miners already have logic to retry proposals on rejection, per the `first_rejection_pause_ms`/`subsequent_rejection_pause_ms` retry configuration [8](#0-7) ). Achieving the exact quorum-crossing timing window across a 5-plus signer set under real-world clock/network jitter is plausible but not guaranteed on the first attempt, hence "minority-triggerable," not majority-dependent.

### Recommendation
Replace the local wall-clock (`get_epoch_time_secs()`) comparison with a canonical, deterministic timestamp derived from data all signers can agree on (e.g., the burn-chain block/header timestamp used to establish the sortition view, or a value embedded and attested to within the proposal itself and cross-checked against chain state), so that all signers evaluating the same block reach the same accept/reject verdict regardless of when they individually receive or process it. If wall-clock time cannot be entirely removed, widen and standardize the buffer to a value proven to exceed realistic p99 network/clock skew across the signer set, and/or require that once a signer has made a decision on a given block it must not later be overridden inconsistently (the codebase already caches decisions for old proposals, per `block_proposal_max_age_secs`; a similar "sticky decision" mechanism should be extended to the tenure-extend timing race to reduce non-determinism, though this only mitigates rather than eliminates the underlying non-deterministic gate).

### Proof of Concept
1. Configure a 5-signer testnet with `tenure_idle_timeout_secs = 1s`, `tenure_idle_timeout_buffer_secs` at its default of 2s (per `mainnet-signer-conf.toml`).
2. Let a miner hold a tenure and let it idle until `now` is within roughly ±network-jitter of the computed `extend_timestamp`.
3. Have the miner submit an identical full tenure-extend block proposal repeatedly (retrying on rejection, as already supported by miner retry logic).
4. Because each of the 5 signers independently calls `get_epoch_time_secs()` at slightly different real times upon receiving/evaluating the proposal, observe that on one retry, exactly the signers whose local evaluation time ≥ `extend_timestamp` (crossing the required signature weight) accept while others (evaluated microseconds earlier) reject the byte-for-byte identical block — demonstrating the non-deterministic, timing-dependent verdict divergence at `stacks-signer/src/chainstate/v2.rs:234-249` (mirrored in `v1.rs:376-391`).

**Uncertainty note:** I could not fully trace the miner-side retry/re-signing mechanics (whether an identical block hash can be resubmitted verbatim to different signers, or whether each retry produces a distinct signed block, which affects whether signatures from different rounds could be aggregated into one valid quorum). This affects exact exploitability but not the root-cause non-determinism itself, which is clearly demonstrated in the cited code.
