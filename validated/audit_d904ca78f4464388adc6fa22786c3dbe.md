### Title
Unbounded growth of `rePushTransactions`/`pendingTransactions` causes linear-scaling per-block work in `PendingManager.close()` - ([File: framework/src/main/java/org/tron/core/db/PendingManager.java])

### Finding Description
`PendingManager.close()` is invoked on every block-generation cycle (via `Manager`'s block production flow) and unconditionally performs three full linear scans: over `dbManager.getRePushTransactions()` to expire timed-out entries, over `dbManager.getPendingTransactions()` to re-queue every pending transaction into `rePushTransactions` via `txIteration()`, and over `dbManager.getPoppedTransactions()` doing the same. [1](#0-0) 

`txIteration()` re-inserts any transaction that has not yet exceeded `timeout` into `rePushTransactions` with no size cap or bound check before the `put()` call: [2](#0-1) 

Because an unprivileged attacker (any funded account, or many freshly-created accounts using free bandwidth) can broadcast transactions faster than a single block can include them, and because `pendingTransactions` entries that don't make it into a block within the current cycle are unconditionally re-queued into `rePushTransactions` (bounded only by the wall-clock `pendingTransactionTimeout`, not by count), the size of these collections is effectively attacker-controlled. Each subsequent `PendingManager.close()` call — which runs once per block-generation cycle — does `O(N)` work proportional to the size of these attacker-influenced queues, where `N` grows with sustained transaction flooding.

### Impact Explanation
This matches the "DoS via the TRON protocol implementation" / "DoS via RPC-API" impact class: sustained transaction flooding inflates `rePushTransactions`/`pendingTransactions`, increasing the constant per-block cost of `PendingManager.close()` linearly with attacker-controlled queue size. Because block generation calls this method on every cycle, this can delay block production cadence, and RPC/HTTP endpoints such as `GetPendingSizeServlet` and `GetTransactionListFromPendingServlet` (backed by `Manager.getPendingSize()`/`getTxListFromPending()`) would reflect this growing, un-pruned queue state. [3](#0-2) 

### Likelihood Explanation
I was unable to fully verify, within the available tool budget, (a) whether `Manager.java` enforces an independent maximum-size cap on `pendingTransactions`/`rePushTransactions` before or during transaction admission (e.g., in `pushTransaction`), and (b) the exact conditions under which transactions transition from `pendingTransactions` to `poppedTransactions`/`rePushTransactions` during normal (non-fork) operation. The `PendingManager.close()` and `txIteration()` code I inspected shows no explicit count-based cap, only a time-based expiry (`timeout`), which is consistent with the described unbounded-growth concern, but confirmation of the full admission path in `Manager.java` (41 matches for `rePush` that I could not fully review) is still needed before treating this as conclusively exploitable end-to-end. Given this gap, a full determination of attacker cost/feasibility is incomplete.

### Recommendation
Enforce a hard maximum size on `rePushTransactions` and `pendingTransactions` (reject/drop oldest entries once a configurable cap, e.g. `maxTransactionPendingSize`, is reached) prior to `put()` in `PendingManager.txIteration()`, and ensure `PendingManager.close()`'s per-cycle work is bounded independent of attacker-driven broadcast volume.

### Proof of Concept
Could not be fully constructed/verified due to inability to confirm the exact admission-path caps in `Manager.java` within the available investigation. A conclusive PoC would require a JUnit test that (1) reflection-injects or broadcasts a large number `N` of valid signed transactions such that they remain in `pendingTransactions` across a cycle, (2) invokes `PendingManager.close()` and measures wall-clock time as `N` grows, and (3) asserts unbounded (non-constant) growth in cost — this should be validated against the actual `Manager.java` push-transaction admission logic before being treated as a confirmed finding.

  private void txIteration(TransactionCapsule tx) {
    try {
      if (System.currentTimeMillis() - tx.getTime() < timeout) {
        dbManager.getRePushTransactions().put(tx);
        Metrics.gaugeInc(MetricKeys.Gauge.MANAGER_QUEUE, 1,
            MetricLabels.Gauge.QUEUE_REPUSH);
      } else {
        Metrics.counterInc(MetricKeys.Counter.TXS, 1,
            MetricLabels.Counter.TXS_FAIL, MetricLabels.Counter.TXS_FAIL_TIMEOUT);
        if (Args.getInstance().isOpenPrintLog()) {
          logger.warn("Timeout remove tx from pending, txId: {}.", tx.getTransactionId());
        }
      }
    } catch (InterruptedException e) {
      logger.error(e.getMessage());
      Thread.currentThread().interrupt();
    }
  }
