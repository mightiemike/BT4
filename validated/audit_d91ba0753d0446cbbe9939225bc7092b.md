## Summary

An Aptos-native analog to the Ribbon storage-layout composability bug exists in the transaction-output/`TransactionInfo` reconciliation logic used by chunk apply-by-outputs and replay-verify tooling. The comparator function that is supposed to guarantee a locally re-derived (or peer-supplied) `TransactionOutput` matches the accumulator-committed, signature-authenticated `TransactionInfo` silently skips comparing the state-checkpoint, hot-state-checkpoint, and position-state-checkpoint root hashes — fields that are part of `TransactionInfoV1` and are exactly the kind of "authenticated root bound to the wrong version/object" data the State-Integrity Gate calls out.

## Finding Description

`TransactionOutput::ensure_match_transaction_info` is the single-source-of-truth consistency check between an executed/received `TransactionOutput` and the `TransactionInfo` that is bound into the transaction accumulator (and therefore covered by validator signatures on a `LedgerInfo`). It checks status, gas, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`: [1](#0-0) 

The comment inline acknowledges this gap explicitly: [2](#0-1) 

This function is the authoritative reconciliation point used by:
- `execution/executor/src/chunk_executor/mod.rs` (apply-by-outputs / chunk commit path)
- `storage/db-tool/src/replay_on_archive.rs` (replay-verify tooling used to certify archived history against consensus-signed `TransactionInfo`s)
- `aptos-move/cli/src/commands.rs` [3](#0-2) 

Compare this to `TransactionOutputListWithProof::verify`, which is the proof-side verification invoked before outputs are queued for chunk apply. It only checks event root hash, write-set hash, gas, status, and transaction hash against the `TransactionInfo` supplied in the accumulator proof — it never touches `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` either: [4](#0-3) 

So neither the proof-verification layer (`TransactionOutputListWithProof::verify`) nor the post-apply reconciliation layer (`ensure_match_transaction_info`) validates that the locally recomputed (or peer-supplied) state/hot-state/position-state checkpoint roots match the value embedded in the accumulator-committed `TransactionInfo`. The `TransactionInfoV1` structure carries these roots specifically so they are "consensus-verified" per the feature-flag documentation for `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO`: [5](#0-4) 

Because these root hashes are never independently re-checked against the recomputed values by the two functions responsible for that job, a divergence between the locally materialized state (main state SMT, hot-state SMT, or the new native-position JMT) and the value actually committed on-chain in `TransactionInfoV1` would not be caught by either the proof-verify step or the post-execution `ensure_match_transaction_info` reconciliation.

## Impact Explanation

This breaks the invariant that "authenticated API or state-view output stay bound to the right ledger version, root, and object" and that "storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state." Concretely:

- During `enqueue_chunk_by_transaction_outputs` / chunk-apply (state sync via `apply_transaction_outputs`), a node accepts `TransactionOutput`s whose `write_set`/gas/events/status match, applies them to its local `LedgerWithSummary` (state summary, hot-state summary, and position-state summary), and commits — without ever confirming that the recomputed `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` in that summary equal what is bound into the accumulator-signed `TransactionInfoV1` for that version.
- `replay_on_archive` (the tool operators use to certify that archived history at a given version replays to the exact consensus-approved state) uses the same `ensure_match_transaction_info` comparator, so it can report a clean replay even when the position-state (or hot-state) root diverges from the authenticated ledger — exactly the scenario the code's own TODO warns about.
- The practical corrupted value is the locally persisted `position_state_summary` / hot-state root recorded as consistent with a given `Version`, when it in fact differs from the value the validator set actually signed for that version in `TransactionInfoV1.position_state_checkpoint_hash` / `hot_state_checkpoint_hash`.

This satisfies the State-Integrity Gate criteria: it is "committed state that differs from the correct VM result" and an "authenticated API or state-view output bound to the wrong ... root." As additional trading-native and hot-state features (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) are enabled, this gap directly undermines the integrity guarantee those features are meant to provide.

## Likelihood Explanation

The gap is unconditional code (not gated behind a feature flag) and is hit on every chunk-apply-by-outputs and every replay-verify run once `TransactionInfoV1` carries non-`None` checkpoint hashes. It requires no privileged access to trigger — a state-sync peer or archive source only needs to supply outputs whose committed value-write-set/events/gas/status match but whose net effect on the position-state or hot-state tree differs (e.g., through a JMT/summary computation bug or through a subtly non-conforming output ordering), and the divergence would go undetected by both the proof and reconciliation layers. The authors' own inline comment shows this is a known, unresolved limitation and explicitly says it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," indicating the current code is not safe for that rollout state.

## Recommendation

- Extend `TransactionOutput::ensure_match_transaction_info` to compare the recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) against the corresponding fields of the supplied `TransactionInfo`, failing loudly on mismatch just as it does for write-set/gas/status/events.
- Extend `TransactionOutputListWithProof::verify` (and its `TransactionListWithProof` sibling) similarly, so checkpoint-hash validation happens as early as possible (at proof-verification time), not only at commit/replay reconciliation time.
- Gate enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` on this fix landing, consistent with the existing inline TODO.

## Proof of Concept

Because this is a missing-check/logic-omission issue rather than a memory-safety bug, the PoC is a code-path trace rather than an exploit payload:
1. A node applies transaction outputs via `ChunkExecutor::enqueue_chunk_by_transaction_outputs`, which calls `TransactionOutputListWithProof::verify` — this checks write set/gas/status/events hashes only. [6](#0-5) 
2. The outputs are applied, and reconciliation with the locally recomputed output uses `ensure_match_transaction_info`, which likewise omits checkpoint-hash comparison. [1](#0-0) 
3. If the position-state (native-position JMT) or hot-state root computed locally after applying the write set diverges from `position_state_checkpoint_hash` / `hot_state_checkpoint_hash` actually signed into `TransactionInfoV1` for that version (e.g., due to an independent computation bug elsewhere, or a maliciously/erroneously constructed output stream from an untrusted archive/peer that nonetheless reproduces the same write-set/event/gas/status hashes), neither check fails, and the wrong root is accepted as consistent with the authenticated ledger state — confirmed by the code's own TODO acknowledging this exact scenario for `replay_on_archive`.

I was unable to inspect the full body of `execution/executor/src/chunk_executor/mod.rs` around its call to `ensure_match_transaction_info`, nor `storage/db-tool/src/replay_on_archive.rs`, within the available tool budget, so I cannot cite the exact call-site line numbers for those two files; this is noted as an open verification item for follow-up (the function names/imports were confirmed to exist there via `grep_search`, but source line-level context wasn't retrieved before the iteration limit was reached).

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    /// This method will ensure:
    /// 1. All transaction infos exist on the given `ledger_info`.
    /// 2. If `first_transaction_output_version` is None, the transaction output list is empty.
    ///    Otherwise, the list starts at `first_transaction_output_version`.
    /// 3. Events, gas, write set, status in each transaction output match the expected event root hashes,
    ///    the gas used and the transaction execution status in the proof, respectively.
    /// 4. The transaction hashes match those of the transaction infos.
    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_output_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction output versions match
        ensure!(
            self.get_first_output_version() == first_transaction_output_version,
            "First transaction and output version ({:?}) doesn't match given version ({:?}).",
            self.get_first_output_version(),
            first_transaction_output_version,
        );

        // Verify the lengths of the transactions and outputs match the transaction infos
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_outputs(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions and outputs ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_outputs(),
        );

        // Verify the events, write set, status, gas used and transaction hashes.
        self.transactions_and_outputs.par_iter().zip_eq(self.proof.transaction_infos.par_iter())
        .map(|((txn, txn_output), txn_info)| {
            // Check the events against the expected events root hash
            verify_events_against_root_hash(&txn_output.events, txn_info)?;

            // Verify the write set matches for both the transaction info and output
            let write_set_hash = CryptoHash::hash(&txn_output.write_set);
            ensure!(
                txn_info.state_change_hash() == write_set_hash,
                "The write set in transaction output does not match the transaction info \
                     in proof. Hash of write set in transaction output: {}. Write set hash in txn_info: {}.",
                write_set_hash,
                txn_info.state_change_hash(),
            );

            // Verify the gas matches for both the transaction info and output
            ensure!(
                txn_output.gas_used() == txn_info.gas_used(),
                "The gas used in transaction output does not match the transaction info \
                     in proof. Gas used in transaction output: {}. Gas used in txn_info: {}.",
                txn_output.gas_used(),
                txn_info.gas_used(),
            );

            // Verify the execution status matches for both the transaction info and output.
            ensure!(
                *txn_output.status() == TransactionStatus::Keep(txn_info.status().clone()),
                "The execution status of transaction output does not match the transaction \
                     info in proof. Status in transaction output: {:?}. Status in txn_info: {:?}.",
                txn_output.status(),
                txn_info.status(),
            );

            // Verify the transaction hashes match those of the transaction infos
            let txn_hash = txn.committed_hash();
            ensure!(
                txn_hash == txn_info.transaction_hash(),
                "The transaction hash does not match the hash in transaction info. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                txn_hash,
                txn_info.transaction_hash(),
            );
            Ok(())
        })
        .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_output_version())?;

        Ok(())
    }
