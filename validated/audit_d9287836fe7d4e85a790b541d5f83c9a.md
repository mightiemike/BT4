The `_checkBalances`-style asymmetry from the report (an invariant enforced in one execution path but silently skipped in a structurally parallel one) maps to `MigrateUEA` vs `ExecutePayload`: both call into UEA contracts as `evmFrom` derived from an arbitrary Cosmos `Signer`, both are gasless, but I could not find where `MigrateUEA`'s `signatureVal` is actually checked against the UEA owner before `CallUEAMigrateUEA` executes — the keeper only parses/format-validates the payload and signature, then immediately calls the EVM.

### Title
Unauthenticated/underverified `MsgMigrateUEA` may allow migration of a UEA implementation without owner authorization - (File: `x/uexecutor/keeper/msg_migrate_uea.go`)

### Summary
`x/uexecutor` keeper's `MigrateUEA` (invoked via the gasless `MsgMigrateUEA` message) parses the migration payload and signature but the Cosmos-layer code shown does not itself verify that `signatureVal` was produced by the UEA's owner before calling `CallUEAMigrateUEA`, which executes the EVM-side migration as `evmFrom` (an address the attacker fully controls via `Signer`).

### Finding Description
`MigrateUEA` in `x/uexecutor/keeper/msg_migrate_uea.go` [1](#0-0)  performs these steps: parse `migrationPayload` into ABI form, hex-decode `signature` into bytes, fetch chain config, resolve the UEA address via the factory, and confirm the UEA is deployed. It never independently authenticates `signatureVal` against the UEA owner's public key before invoking `k.CallUEAMigrateUEA(sdkCtx, evmFrom, ueaAddr, migrationPayload, signatureVal)` [2](#0-1) . `msg_server.go`'s `MigrateUEA` handler simply derives `evmFromAddress` from `msg.Signer` (fully attacker-controlled, since `MsgMigrateUEA` — like `MsgExecutePayload` — allows `Signer ≠ Owner` by design) and forwards to the keeper with no additional binding check [3](#0-2) . `MsgMigrateUEA` remains in the gasless whitelist, meaning any account (even a freshly created one, via the `AccountInitDecorator` gasless bootstrap path) can submit this message at zero cost [4](#0-3) .

This mirrors the report's bug class exactly: `_checkBalances` (the invariant guard) is applied in `_swap`/`_lpTokenSpecified` but omitted from the structurally similar `_reserveTokenSpecified`-driven deposit/withdraw path. Here, cryptographic authorization is the analogous invariant: it is enforced end-to-end for `ExecutePayload` (contract-side signature check against the immutable owner key, documented explicitly as the sole authorization gate in the README [5](#0-4) ) but the equivalent module-level or pre-flight check is not visible in the `MigrateUEA` keeper path before the EVM call is dispatched.

### Impact Explanation
If the EVM-side `CallUEAMigrateUEA`/contract's `migrateUEA` entry point does not itself enforce the signature check with the same rigor as `executeUniversalTx` (i.e., if it trusts the Cosmos module or `evmFrom` in any way, or if the signature check inside the contract can be satisfied trivially because the module never bound `signatureVal` to a specific, unforgeable owner assertion before submission), an attacker could migrate an arbitrary UEA to a malicious implementation, potentially compromising every future execution of that UEA (fund theft, unauthorized fund release, or unauthorized state transitions) — a direct hit on "unauthorized UEA execution" and "unauthorized module-originated EVM execution" in the impact gate.

### Likelihood Explanation
Likelihood is uncertain: I was not able to locate the source of `USigVerifier`/ECDSA verification for `UEA_EVM.sol` / `UEA_SVM.sol` migrateUEA in this repository index (the actual authentication logic lives in the separate `push-chain-core-contracts` repo referenced only by URL in the README, not in this indexed codebase) [6](#0-5) . If that contract enforces the same nonce/deadline/signature invariant for `migrateUEA` as it does for `executeUniversalTx`, this finding is a false positive — the module-level omission would be safe by the same "Signer ≠ Owner" argument documented for `ExecutePayload`. I could not confirm this from the indexed files alone.

### Recommendation
Confirm (or add, if missing) that the UEA contract's `migrateUEA` entry point performs an owner-key signature check over the migration payload with replay protection (nonce/deadline), exactly as `executeUniversalTx` does, and that this check is the actual authorization gate — matching the documented pattern. If no such check exists on the contract side, add explicit signature verification inside `x/uexecutor/keeper/msg_migrate_uea.go`'s `MigrateUEA` before calling `CallUEAMigrateUEA`, mirroring `ExecutePayload`'s reliance on contract-enforced authentication, and add an integration test analogous to `TestMsgServer_ExecutePayload`'s authorization tests for the migrate path.

```markdown
#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**
```
