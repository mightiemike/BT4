### Title
Unbounded `contractType` in `checkPermissionOperations` causes out-of-range bitmask indexing/undefined shift, enabling permission-check bypass or unhandled-exception DoS - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`checkPermissionOperations` computes a bit index into a fixed 32-byte `operations` bitmask using an attacker-controlled `contractType` value taken directly from the raw protobuf `Contract.type` field, without validating that it falls in the expected `[0,255]` range. This mirrors the reported `executeExchangeOrders` flaw: an arithmetic bit-index computation (`byteAt(contractType/8)`, `1 << (contractType % 8)`) is performed on an untrusted, unbounded integer, breaking the invariant that the operations-permission check reliably validates or rejects a contract type.

### Finding Description
`checkPermissionOperations` is implemented identically in two places: [1](#0-0) [2](#0-1) 

```java
int contractType = contract.getTypeValue();
boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
```

`operations` is checked to be exactly 32 bytes, but `contractType` comes from `contract.getTypeValue()` — the *raw* protobuf int stored on the wire for the `oneof`/enum `type` field of `Transaction.Contract`. Protobuf enum fields accept arbitrary `int32` values on the wire (unrecognized values are preserved as raw ints, not rejected at decode time), so an attacker who crafts a raw transaction can set this value to anything in the full `int32` range, not just a value in `[0,255]`.

Consequences of an out-of-range `contractType`:
- If `contractType/8 >= 32` (or negative), `operations.byteAt(...)` throws `IndexOutOfBoundsException`, an unchecked `RuntimeException` that is **not** declared/caught by `checkPermissionOperations` (which only declares `PermissionException`).
- If `contractType` is negative, Java's `%` operator preserves the sign of the dividend, and `1 << (negative % 8)` triggers Java's shift-amount masking (`shiftAmount & 31`), producing a shift result that does not correspond to any deliberately-designed bit position in the 32-byte bitmap. This is directly analogous to the reported `2 ** header.exchange` overflow silently producing an unintended (here, effectively attacker-influenced) bit pattern instead of throwing a validation error.

This function is reached from the transaction-signature/permission validation path used for every multi-signature (`permissionId != 0`) transaction: [3](#0-2) [4](#0-3) [5](#0-4) 

`validatePubSignature` only catches `SignatureException`, `PermissionException`, `SignatureFormatException` — it has no catch clause for the unchecked `IndexOutOfBoundsException` that `checkPermissionOperations` can throw, so the exception propagates uncaught out of the signature-validation routine used during transaction processing (`pushTransaction`/block validation), not merely inside gRPC entry points that generically catch `Exception`.

The size-32 check for `operations` itself is enforced when the account's permission is created (`AccountPermissionUpdateActuator.checkPermission`), but there is no corresponding bound check that `contractType` is within `[0,255]` before it is used to index into that fixed-size structure: [6](#0-5) 

### Impact Explanation
An attacker can broadcast a crafted transaction whose `Transaction.Contract.type` raw wire value is outside the intended `ContractType` enum range (e.g. very large or negative), for an account that has a non-zero multi-sig `permissionId`. This can:
- Cause an unhandled `IndexOutOfBoundsException` inside `validatePubSignature`/`validateSignature`, which is invoked during transaction/block processing rather than only at an RPC boundary with a catch-all — a potential DoS vector against nodes processing the transaction/block.
- Cause the permission bit check to evaluate against an unintended bit (due to Java's negative-modulo and shift-masking semantics) instead of failing validation deterministically, risking inconsistent permission-check results across code paths that use this same function differently, undermining the multi-sig authorization invariant.

### Likelihood Explanation
The `Transaction.Contract.type` field is fully attacker-controlled in a broadcast transaction (any account can submit `BroadcastTransaction` requests), and protobuf does not reject unknown enum values for this field. Any account configured with a multi-sig `Active` permission (a normal, supported account feature) is a valid trigger target. No privileged access or leaked keys are required — only the reachable RPC/broadcast path and normal account setup.

### Recommendation
Explicitly validate `contractType` is within `[0, 255]` (and ideally corresponds to a recognized `ContractType` enum value) before using it to index into the 32-byte `operations` bitmask in both `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`. Reject the transaction with a `PermissionException`/`ContractValidateException` if it is out of range, rather than performing unchecked arithmetic/bit-index/shift operations on untrusted input.

### Proof of Concept
1. Set up an account with an `Active` permission (`permissionId != 0`) with a bounded `operations` bitmask (32 bytes), as supported by `AccountPermissionUpdateActuator`.
2. Manually construct (bypassing the Java protobuf builder's enum restriction, e.g., via `CodedOutputStream`/raw bytes or a modified client) a `Transaction.Contract` whose `type` field wire value is set to an out-of-range integer (e.g., `100000` or a negative value) while keeping the rest of the transaction otherwise well-formed and referencing `permissionId` for the multi-sig account.
3. Broadcast the transaction (or otherwise route it through `TransactionCapsule.validateSignature`/`validatePubSignature`).
4. Observe `checkPermissionOperations` computing `operations.byteAt(contractType / 8)`, which throws `IndexOutOfBoundsException` uncaught by `validatePubSignature`, or produces an unintended bit result due to `1 << (contractType % 8)` shift-masking for negative `contractType`.

Note: I could not fully verify (due to indexer limits) every call site's exception-handling wrapper across the entire consensus/block-processing pipeline (e.g., whether `Manager.pushTransaction` or block-validation code has a catch-all for generic `RuntimeException` that would mask the DoS impact). Confirming the exact blast radius (crash vs. silently-rejected transaction) would require deeper tracing of all callers of `TransactionCapsule.validateSignature`/`validatePubSignature`, which a full Devin session with complete repository access could verify.
