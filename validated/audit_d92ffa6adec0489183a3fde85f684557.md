### Title
Unmetered per-call WASM instantiation cost (globals/data/element segments) enables gas-underpriced CPU exhaustion DoS - (File: runtime/near-vm-runner/src/wasmtime_runner/mod.rs)

### Summary
The OpenJPEG advisory describes resource exhaustion from a crafted input whose decode work is not properly bounded relative to the cost an attacker pays to trigger it. The analogous nearcore weakness is in the WASM contract runtime: every `FunctionCall` action re-instantiates the compiled module (`pre.instantiate`), which re-initializes all module globals, active data segments, and active element segments. The project's own gas estimator explicitly documents that this per-call work — for contracts with many globals, data segments, or element segments — is **not covered by gas** on this protocol version, while the shape-limiting protocol feature (`max_globals_per_contract`) that would cap it is only scheduled for a future nightly protocol version (157), not the currently active stable version (86).

### Finding Description
`WasmtimeVM`'s `run` path calls `pre.instantiate(&mut store)` on *every* invocation of a `FunctionCall` action, not just once at deploy time [1](#0-0) . Instantiation performs real work proportional to the module's declared globals/data-segments/element-segments, independent of the gas-metered WASM instruction stream.

The project's own runtime-params-estimator flags this exact gap: [2](#0-1) 

and measures it against contracts built specifically to be adversarial in this dimension: [3](#0-2) 

The only protocol-level defense against unbounded global counts, `max_globals_per_contract`, is not part of the active `LimitConfig` on the current release — it is only introduced as a nightly parameter change at protocol version 157: [4](#0-3) 

`core/parameters/res/runtime_configs/parameters.snap` (the currently active parameter table, PV86 lineage) has no `max_globals_per_contract` entry at all [5](#0-4) , and `prepare_v3`'s `PrepareContext` falls back to `u64::MAX` when the limit is unset: [6](#0-5) 

The only backstop that currently exists is Wasmtime's pooling-allocator `max_core_instance_size` (1 MiB), which rejects modules whose *VMContext* (16 bytes/global) would exceed that slot — but this only trips above roughly 65k globals; contracts with, e.g., 50,000 globals (≈800 KiB of VMContext, well under the 1 MiB cap) load and run successfully, exactly the case the estimator itself uses (`contract_with_num_globals(50_000)`) to characterize this "adversarial" but currently-legal shape [7](#0-6) . Because `max_contract_size` is 4 MiB and each `global` declaration in the wasm binary encoding costs only a few bytes, a contract can be deployed well within size limits while declaring tens of thousands of globals (and/or many active data/element segments), each of which must be re-materialized by Wasmtime on every single call.

### Impact Explanation
A regular, unprivileged account can deploy such a contract via a normal `DeployContractAction` (paying only the ordinary per-byte deploy fee for a small-to-moderate sized contract) and then repeatedly invoke it via cheap `FunctionCallAction`s. Because gas for a `FunctionCall` is dominated by wasm-instruction and `contract_loading_bytes` costs (proportional to *encoded* wasm size), and the estimator explicitly states the globals/segment re-initialization work is "not covered by gas," the attacker pays gas disproportionate to the real CPU cost imposed on every validator/chunk-producer that must apply the receipt (and every stateless-validation re-execution of the chunk). Because gas is meant to be the sole throttle on per-receipt compute, this is a fee/gas-bypass class issue that can be used to burn validator CPU cycles cheaply and repeatedly — a resource-exhaustion vector reachable from a single submitted transaction, matching the bug class in the OpenJPEG advisory (crafted, cheaply-triggerable input whose processing cost is disproportionate to attacker cost).

### Likelihood Explanation
Deploying a contract with tens of thousands of globals is trivial to construct (a WAT/wasm-encoder loop emitting `(global i32 (i32.const 0))` entries) and stays comfortably under `max_contract_size` (4 MiB) and under the Wasmtime `max_core_instance_size` backstop (1 MiB VMContext ⇒ ~65k globals). No special privilege, validator role, or malicious peer/node behavior is required — only an ordinary account able to deploy and call a contract. The gap is corroborated directly in-repo by the estimator's own documentation and adversarial test helpers, indicating the team is aware the cost exists but that the mitigating protocol feature (`max_globals_per_contract`) has not yet reached the currently active protocol version.

### Recommendation
- Backport/activate `max_globals_per_contract` (or an equivalent limit on data/element segment counts) to the currently active protocol version rather than leaving it nightly-only, and ensure `prepare_v3` enforces a finite default instead of `u64::MAX` when unset.
- Introduce/enable a gas fee proportional to declared globals count / active data-segment bytes / active element-segment entries charged at `FunctionCall` time (mirroring `AdversarialLoadManyGlobals`/`AdversarialLoadManyDataSegments`/`AdversarialLoadManyElementSegments` estimator findings), so the metered gas reflects real per-call instantiation cost.
- Add a regression test asserting that a contract near the size/shape limits cannot cause per-call wall-clock cost that is disproportionate to its charged gas.

### Proof of Concept
1. Build a wasm module (e.g., via `wasm-encoder`, following the pattern of `near_test_contracts::contract_with_num_globals`) declaring ~50,000 zero-initialized `i32` globals and a trivial exported `main` function, keeping the encoded module well under `max_contract_size` (4 MiB) and under the 1 MiB Wasmtime VMContext backstop.
2. Deploy the contract from an ordinary account via `DeployContractAction` (this cost is proportional to code *byte size*, which stays small since globals are compact in the binary format).
3. Submit repeated `FunctionCallAction`s invoking `main`. Each call causes `WasmtimeVM::run` → `pre.instantiate` to re-materialize all ~50,000 globals in VMContext — real CPU work that is not reflected in the wasm-instruction/`contract_loading_bytes` gas charged, per the estimator's own `AdversarialLoadManyGlobals` documentation.
4. Compare measured wall-clock/CPU cost per call (via the estimator's `measure_instantiation_overhead` methodology) against the gas actually burned to demonstrate the disproportion, analogous to `runtime/near-vm-runner/src/tests/runtime_errors.rs::test_max_core_instance_size_breached`, but using a globals count below the pooling-allocator backstop so the call succeeds repeatedly instead of aborting.
