### Title
Attached deposit is permanently lost (never refunded) on multiple `rlp_execute` error paths in the Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract::rlp_execute` entry point is `#[payable]` and tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the emulated action ultimately fails. However, several error-handling branches drop `caller_deposit` without ever creating a refund promise, permanently absorbing the caller's NEAR deposit into the wallet contract's balance. This mirrors the external report's root cause — a return/result value that should gate a fund-movement decision is silently ignored, causing an unconditional and unrecoverable loss of the caller's funds.

### Finding Description
`CallerDeposit::new` explicitly exists to remember an external (non-self) caller's `attached_deposit` so it can be refunded later: [1](#0-0) 

This value is threaded through the promise chain and is only ever refunded in one place — `rlp_execute_callback`, and only when the final cross-contract promise fails: [2](#0-1) 

But `caller_deposit` is computed immediately in `inner_rlp_execute`, before the parsing of the transaction is even attempted: [3](#0-2) 

Multiple branches that run *before* any promise referencing `caller_deposit` is created simply discard it on error, with no refund logic at all:
- Any `Err(e)` other than a `Relayer` error signed by the wallet itself returns a plain value with no promise and no refund: [4](#0-3) [5](#0-4) 

- Even a `Relayer` error is turned into a "ban relayer" promise that never references `caller_deposit`: [6](#0-5) 

- Inside `address_check_callback`, when the registrar reports an existing named account for the address but the signer is not the wallet itself, the function returns an error value directly, again dropping `caller_deposit` without a refund: [7](#0-6) 

- Inside `nep_141_storage_balance_callback`, if the `storage_balance_of` cross-contract call fails or returns unparsable data, the function again returns an error value directly without touching `caller_deposit`: [8](#0-7) 

Because `rlp_execute` and its callbacks are intentionally designed to never panic ("the reason that method should never panic is to ensure the contract's state can be changed even in error cases"), the deposit attached by the calling `FunctionCall` action is credited to the wallet contract's balance as soon as the call completes normally — NEAR's protocol-level refund-on-panic mechanism does not trigger because the method returns a normal (non-panicking) value in all of these cases. There is no code path that sends the deposit back to `predecessor_account_id` for any of the error cases listed above.

### Impact Explanation
Any external account (typically a relayer submitting a user's RLP-encoded transaction) that attaches a deposit to a `rlp_execute` call and hits one of the numerous readily-triggerable error conditions — invalid nonce, insufficient gas, invalid target/chain id, `ValueTooLarge`, unparsable ABI data against another Near account, a failing/erroring call to the address registrar, or a failing/erroring call to a token's `storage_balance_of` — will have that deposit permanently and irrecoverably absorbed into the Wallet Contract account. This is a direct, unauthorized-in-effect loss of the caller's NEAR funds with no way to reclaim them, matching the "permanently frozen funds" impact category.

### Likelihood Explanation
The `CallerDeposit` mechanism demonstrates the deposit-refund-on-failure design is an expected usage pattern (external callers attaching deposit, e.g. to cover NEP-141 storage costs or other fees). Many of the error conditions above (bad nonce due to a race between two relayers, gas mis-estimation, a target token contract with a broken/absent `storage_balance_of`, or the address registrar being temporarily unavailable) are realistic operational conditions rather than contrived edge cases, and are triggerable by any caller — no privileged access is required.

### Recommendation
Ensure every error-return path in `rlp_execute`, `address_check_callback`, and `nep_141_storage_balance_callback` that has a `caller_deposit` in scope creates a refund promise (as already done in `rlp_execute_callback` for the `PromiseResult::Failed` case) before returning the error `ExecuteResponse`, so the caller's deposit is never silently retained by the contract.

### Proof of Concept
1. A relayer account (`predecessor_account_id != current_account_id`) calls `rlp_execute(target, tx_bytes_b64)` attaching some non-zero NEAR deposit.
2. `CallerDeposit::new` captures `{ account_id: relayer, yocto_near: deposit }` since predecessor differs from the wallet.
3. The relayer supplies a transaction whose nonce no longer matches (e.g., because another relayer's transaction was already processed), causing `validate_tx_relayer_data` to return `Error::Relayer(RelayerError::InvalidNonce)`.
4. In `inner_rlp_execute`, this falls into the `Err(err) => return Err(err)` branch (nonce not incremented, `caller_deposit` discarded).
5. Back in `rlp_execute`, since the signer is the relayer (not `current_account_id`), the `Err(Error::Relayer(_))` branch condition `env::signer_account_id() == current_account_id` is false, so it falls to `Err(e) => PromiseOrValue::Value(e.into())`.
6. The call returns normally (no panic), so the attached deposit is credited to the wallet contract's balance and is never sent back to the relayer — the deposit is permanently lost.

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
    let pk = env::signer_account_pk();
    Promise::new(current_account_id).delete_key(pk).function_call_weight(
        "ban_relayer".into(),
        Vec::new(),

        Gas::from_tgas(1),
        GasWeight(1),
    )
