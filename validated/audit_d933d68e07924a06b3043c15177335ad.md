### Title
Architecture-dependent WASM backend selection (`replace_with_wasmtime_if_unsupported`) can cause execution-outcome divergence between honest validators - (File: `core/parameters/src/vm.rs`)

### Summary
`VMKind::replace_with_wasmtime_if_unsupported` silently substitutes `Wasmtime` for whatever backend the versioned parameter table specifies (`NearVm` on protocol versions prior to PV 84) whenever the node is not running on `x86_64`. [1](#0-0)  This means that, for any protocol version where the consensus-selected `vm_kind` is `NearVm`, x86_64 validators execute contract WASM through the NearVm backend while non-x86_64 validators (e.g. ARM) execute the exact same WASM through Wasmtime. This is directly analogous to the reported issue: code that is assumed to behave identically across "compatible" execution environments can, in practice, diverge at the opcode/runtime-semantics level (memory growth accounting, floating-point NaN payloads, bulk-memory/table op edge cases), producing different results for the same input.

### Finding Description
`Config::vm_kind` is a consensus parameter drawn from the versioned `RuntimeConfigStore`/parameter table, and is documented as having been `NearVm` for all protocol versions below PV 84, only switching to `Wasmtime` at PV 84 on the current 2.13.0 release. [2](#0-1)  Contract preparation and execution both key off this `vm_kind` value: `prepare_contract` chooses the `prepare_v3` pipeline "when `reftypes_bulk_memory` is set or `vm_kind == Wasmtime`", otherwise it silently falls back to `prepare_v2`. [3](#0-2) 

Independently of the consensus-configured `vm_kind`, `replace_with_wasmtime_if_unsupported` forces every non-x86_64 node to run Wasmtime instead of the configured backend (NearVm is explicitly x86_64-only). [1](#0-0)  The project's own documentation on VM correctness explicitly flags this exact hazard class: "the NEAR protocol adds a requirement that all executions of a Wasm program must be deterministic. In other words, it must not be possible to observe different execution results based on the environment within which the VM runs," and separately warns that floating-point NaN sign/payload behavior and non-standard rounding are areas where different WASM engines are known to diverge. [4](#0-3)  The protocol-model spec's own invariant section states plainly: "Gas values and the outcome (including a guest error) must be identical across validators; `VMRunnerError` … signals node-local corruption and should crash/challenge rather than diverge." [5](#0-4)  Yet `replace_with_wasmtime_if_unsupported` is precisely a mechanism that intentionally runs a *different* backend than the one selected by consensus parameters, on the assumption that Wasmtime and NearVm are behaviorally identical for every WASM program — the same "EVM-compatible" assumption the original report shows to be false for opcode semantics.

Because contract preparation itself branches on `vm_kind` (choosing `prepare_v2` vs `prepare_v3`, which apply different instrumentation/validation passes), a node forced onto Wasmtime by `replace_with_wasmtime_if_unsupported` while the consensus `vm_kind` is still `NearVm` would prepare code with `prepare_v2` (since `config.vm_kind` is unchanged — only the actual executing backend is swapped) but execute it on the Wasmtime runtime, which was only validated/tested against the `prepare_v3` pipeline. This mismatch between the preparation pipeline (keyed on the *logical* `vm_kind`) and the actual execution backend (silently swapped by architecture) creates a code path that was not exercised as a combination in the primary test/estimator matrix, and is the kind of latent cross-environment inconsistency the reported bug class targets.

### Impact Explanation
If any behavioral divergence exists between the NearVm and Wasmtime backends for some WASM program (float determinism, bulk-memory op edge cases, gas-metering rounding, or preparation-pipeline mismatches as described above), a single submitted transaction invoking a `FunctionCall` action against a maliciously or accidentally crafted contract could produce different `VMOutcome`s (balance, storage_usage, burnt/used gas, or aborted state) on x86_64 validators versus non-x86_64 validators. Because the outcome of contract execution feeds directly into state-root computation, this yields a state-root divergence between honest validators — an invalid state transition being accepted by one class of node and rejected/differently-applied by another, i.e., a consensus/chain-split condition triggerable by an ordinary transaction sender.

### Likelihood Explanation
Likelihood is constrained by two facts I could not fully verify from the indexed code: (1) on the current 2.13.0/PV-86 mainnet config, `vm_kind` is already `Wasmtime` for all nodes, so the NearVm/Wasmtime split currently only matters for historical protocol versions, non-mainnet chains, or any future config that reintroduces `NearVm`; and (2) I could not confirm from the available index whether any concrete, currently-triggerable behavioral difference between the two backends exists (e.g., a specific WAT snippet that yields different `VMOutcome`s) — I found only documentation asserting the requirement for determinism and identifying floating point/memory as historically risky areas, not a demonstrated discrepancy in this codebase. Given the size limits on the indexed content, I was not able to inspect `runtime/near-vm-runner/src/near_vm_runner/` in full nor cross-diff its bulk-memory/float handling against `wasmtime_runner`, so I cannot be fully certain whether such a discrepancy is exploitable today versus already mitigated by other invariants (e.g., a canary/fuzz-diff test suite).

### Recommendation
- Ensure that the *logical* `vm_kind` used by the preparation pipeline (`prepare_v2` vs `prepare_v3` selection) is never allowed to diverge from the *actual* execution backend chosen by `replace_with_wasmtime_if_unsupported`; either always use `prepare_v3` semantics when Wasmtime executes, or forbid backend substitution entirely for protocol versions where `vm_kind != Wasmtime`.
- Consider removing architecture-based backend substitution from the consensus-critical code path altogether, and instead make `NearVm`-only protocol versions require x86_64 validators (failing startup on unsupported architectures) so that no node silently executes a different backend than what consensus parameters specify.
- Expand the differential-fuzzing/test matrix (`with_vm_variants`) explicitly to cover "config says NearVm, but process forced to Wasmtime" as a first-class test configuration, not just the two backends independently.

### Proof of Concept
Conceptual PoC (backend selection code path, not an exploit binary):
1. Run a validator set where `RuntimeConfigStore` resolves `vm_kind = NearVm` for the active protocol version (true for any PV < 84 on this codebase). [2](#0-1) 
2. Include at least one non-x86_64 validator in the set. On that node, `VMKind::replace_with_wasmtime_if_unsupported` forces the Wasmtime backend regardless of the configured `NearVm`. [1](#0-0) 
3. An ordinary user submits a `FunctionCall` transaction deploying/invoking a WASM contract exercising an operation known to have engine-specific behavior (e.g., floating-point NaN-producing arithmetic, or bulk-memory/table instructions gated by `reftypes_bulk_memory`/`prepare_v2` vs `prepare_v3` differences). [3](#0-2) 
4. x86_64 validators execute via NearVm using the `prepare_v2` pipeline; the non-x86_64 validator executes the *same prepared bytecode* on the Wasmtime runtime, which the codebase's own test/spec commentary indicates was validated against `prepare_v3`/Wasmtime-specific semantics. [6](#0-5) 
5. Any resulting difference in `VMOutcome` (gas burnt, aborted status, returned data) propagates into differing state roots computed by the two validator classes, per the component's own stated determinism invariant. [5](#0-4)

In addition to this, the NEAR protocol adds a requirement that all executions of a Wasm program
must be deterministic. In other words, it must not be possible to observe different execution
results based on the environment within which the VM runs.

The Wasm specification claims fast, safe and portable semantics to be one of its design goals. Even
though Wasm specification does go to great lengths to make it possible to enable deterministic and
reproducible execution, it is not one of the foundational goals. Indeed, there are some parts of
the specification that allow for non-deterministic, non-reproducible execution.

A particularly troublesome area of the specification in this regard relates to the floating point
support. The specification permits floating point operations to return a `NaN` result which the
specification also permits to have multiple different bit representations and goes out of its way
to specify the sign of the `NaN` result to be non-deterministic. The determinism and
reproducibility requirements of the NEAR protocol make it necessary for the runtime to ensure NaN
signs and payloads are always deterministic.

Another detail to keep an eye out is whether the floating point results are being rounded
correctly. It is well known that the x87 co-processor does not necessarily round the results
correctly, so a special attention to how a runtime implements the floating point operations on the
32-bit x86 targets is warranted.
