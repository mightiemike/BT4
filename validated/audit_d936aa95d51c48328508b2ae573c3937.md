Based on the investigation, the closest on-chain analog to the `RewardJoin`/`StakeJoin` "one-way cage" bug is the `Status_ABORTED` terminal state in `x/uexecutor`'s outbound-finalization flow.

### Title
Outbound funds permanently stuck in `ABORTED` state with no on-chain recovery path when re-mint fails - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`x/uexecutor` models outbound-tx status as `PENDING -> OBSERVED -> REVERTED | ABORTED` [1](#0-0) . When a destination-chain outbound fails and the keeper tries to re-mint the bridged PRC20 back to the sender, a failure in that re-mint call permanently transitions the outbound to `Status_ABORTED` — described in the code only as "for manual intervention" [2](#0-1) , but no keeper method, message handler, or admin escape-hatch was found anywhere in `x/uexecutor` that resumes, retries, or otherwise unlocks an `ABORTED` outbound. This mirrors the `cage`/no-`uncage` pattern: a legitimate, reachable failure path flips a one-way switch that leaves user funds unrecoverable.

### Finding Description
`FinalizeOutbound` dispatches to `handleFailedOutbound` when UVs (honestly) vote that a destination-chain send failed [3](#0-2) . For `FUNDS`, `GAS_AND_PAYLOAD`, and `FUNDS_AND_PAYLOAD` outbound types, it attempts to re-mint the bridged amount back to the revert recipient via `CallPRC20Deposit` [4](#0-3) . If that call errors, the code calls `AbortOutbound`, which sets `OutboundStatus = Status_ABORTED` and removes the entry from `PendingOutbounds` [5](#0-4) [2](#0-1) .

Unlike the inbound side, which has an explicit admin recovery message (`RevertStuckInbound`) for stuck-ballot cases [6](#0-5) , and unlike `RESCUE_FUNDS`, which is a separate mechanism for stuck *inbound* funds attached via `AttachRescueOutboundFromReceipt` [7](#0-6) , there is no equivalent "un-abort" or retry entry point for an `OutboundTx` once it reaches `Status_ABORTED`. The type validator explicitly treats `Status_ABORTED` as terminal and internally set, requiring no further validation [8](#0-7) .

The re-mint call can fail for reasons squarely inside normal, unprivileged operation — most notably the token's `LiquidityCap` enforcement on the PRC20 representation. A user (or the aggregate of ordinary users) who has pushed a token's minted PRC20 supply close to its configured `LiquidityCap` can cause a legitimate revert re-mint to be rejected by the cap check, since `CallPRC20Deposit` mints new PRC20 supply the same way normal inbound deposits do, and is thus subject to the same cap. Because the destination-chain leg already failed (funds never delivered externally) and the compensating re-mint on Push Chain is rejected, the bridged value is neither on the destination chain nor restored on Push Chain — it is trapped in an `ABORTED` `OutboundTx` with only human/off-chain awareness (`abort_reason`, an event) and no on-chain remedy.

### Impact Explanation
This results in permanent loss/freezing of user funds: the PRC20 was already burned to create the outbound (matching an inbound execution that had already delivered/consumed the underlying asset), the destination-chain leg failed, and the automatic compensation re-mint also failed, with no code path to retry it. This matches the "Impact" category of permanent freezing/loss of user-controlled funds in the allowed-impact gate.

### Likelihood Explanation
Reaching `ABORTED` requires two conditions that are each individually reachable by an unprivileged user under honest-validator assumptions: (1) a legitimate destination-chain execution failure (achievable by targeting a reverting contract, insufficient gas parameters, etc., which honest UVs will correctly observe and vote as `success=false`), and (2) the re-mint call failing (e.g., liquidity cap saturation, which a user or set of users can approach through ordinary deposit activity). This is a multi-step but user-triggerable condition rather than a contrived edge case, giving it low-to-medium likelihood — comparable to the "low likelihood" rating in the original report.

### Recommendation
Add an on-chain recovery path for `Status_ABORTED` outbounds analogous to `RevertStuckInbound`/`RescueFunds` for inbounds — e.g., an admin- or governance-gated message that retries the PRC20 re-mint (or attaches a corrective outbound) for outbounds stuck in `ABORTED`, so that a transient or cap-related re-mint failure does not permanently strand user funds.

### Proof of Concept
Not independently executed; derived from static analysis of `x/uexecutor/keeper/outbound.go`, `x/uexecutor/types/outbound_tx.go`, and the absence of any `Status_ABORTED`-clearing method in `x/uexecutor/keeper/*.go` (verified via grep across the module for `RescueFunds`/`Status_ABORTED` usage). I could not exhaustively confirm the absence of a governance-level manual fix-up (e.g., a store-migration or upgrade handler used operationally) since such tooling may live outside `x/uexecutor` and wasn't found in the indexed code; this should be verified against the full `x/uexecutor` and `app/upgrades` directories in a live session before treating this as fully unmitigated.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}
