## Title
`ensure_match_transaction_info` silently skips checkpoint-hash validation, letting replay/debugger tooling accept a `TransactionOutput` whose state, hot-state, or native-position root diverges from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the local-execution proof-binding check used by replay/debug tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `execution/executor/src/chunk_executor/mod.rs`) to confirm that a locally re-executed transaction produced the same result as the one committed and authenticated on-chain via `TransactionInfo` (the leaf hashed into the transaction accumulator). The function validates `status`, `gas_used`, `write_set_hash` (`state_change_hash`), and `event_root_hash`, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are also committed into the accumulator/root that consensus and light clients rely on.

### Finding Description [1](#0-0) 

The comment in the function body is a direct, self-admitted acknowledgment of the gap:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

These checkpoint hashes are not incidental metadata — they are consensus-verified, proof-bearing fields:
- `state_checkpoint_hash` is derived from `LedgerStateSummary`/JMT root at checkpoint boundaries.
- `hot_state_checkpoint_hash` is gated by `HOT_STATE_ROOT_IN_TXN_INFO` and committed to the ledger accumulator per the feature-flag comment: "so it is committed to the ledger accumulator" [3](#0-2) .
- `position_state_checkpoint_hash` is the root of the new native-position Jellyfish-Merkle-like tree (`PositionStateWithSummary`), computed in `DoStateCheckpoint::compute_position_checkpoint` and bound into `TransactionInfoV1` via `assemble_transaction_infos` in `do_ledger_update.rs` [4](#0-3) , which is then hashed into the transaction accumulator (`InMemoryTransactionAccumulator::append`) [5](#0-4) .

Because all three checkpoint hashes feed the same `TransactionInfo::hash()` that becomes an accumulator leaf, any divergence in these fields between two nodes would normally be caught by transaction-info/accumulator-root comparison in the *live* commit path (`chunk_verifier.verify_chunk_result` in `chunk_executor/mod.rs`, which compares against `parent_accumulator`). However, `ensure_match_transaction_info` is a *separate*, weaker comparator that is called directly by ad-hoc replay/debug/verification tools operating on a pre-fetched `TransactionOutput` + `TransactionInfo` pair — it does not go through accumulator verification at all, and it only checks the four fields listed above. A `TransactionOutput` recomputed locally (e.g. by `aptos-debugger` replaying a transaction, or `db-tool replay_on_archive` scanning an archive) can therefore be accepted as "matching" even if its state root, hot-state root, or native-position root disagrees with what was actually authenticated in the archived/committed `TransactionInfo`.

### Impact Explanation
This breaks the "authenticated output must stay bound to the right root/version" invariant required for proof-integrity tooling: a tool built on `ensure_match_transaction_info` can report a **false-positive successful replay/verification** while the actual committed state root (or the new native-position root once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) silently diverged from local re-execution. This directly undermines archive/replay-verify workflows (`db-tool replay_on_archive`, CLI/debugger replay commands) that operators and auditors rely on to detect state divergence, non-determinism bugs, or storage corruption. Given that `position_state_checkpoint_hash` guards an entirely new state tree (native order book/position ledger) that is committed on-chain but not checked here, a bug in `DoStateCheckpoint::compute_position_checkpoint` or in the position JMT could go undetected by these tools even though the resulting root is wrong and durably committed.

### Likelihood Explanation
The gap is unconditional and always present in `ensure_match_transaction_info` — it is not behind a flag; the TODO explicitly says it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," which implies it has not yet been fixed while the feature is being rolled out. Any tool consumer using this comparator today already misses state/hot-state checkpoint divergences even without the position feature; once native-position state roots are turned on, the same code path also misses that root. This is a straightforward, always-reachable code-review-visible gap rather than a exploit requiring adversarial input — it is a verification-completeness bug in the codebase itself.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values whenever the corresponding feature is enabled and the fields are present (`TransactionInfo::V1`), returning an error on mismatch just as is done for `write_set_hash` and `event_root_hash`. This should be done before or as part of enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, per the existing TODO.

### Proof of Concept
Conceptual PoC (no live exploitation needed — the gap is directly visible in the diff of checked vs. unchecked fields):
1. Enable (or simulate) `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`TRANSACTION_INFO_V1` so `TransactionInfo::V1` carries a `position_state_checkpoint_hash`.
2. Craft/replay a `TransactionOutput` whose write set's `native_position_iter()` entries would, if correctly folded into the position JMT (`DoStateCheckpoint::compute_position_checkpoint`), produce a `position_state_checkpoint_hash` different from the one stored in the archived `TransactionInfo` (e.g., due to a bug in `PositionSlot`/`extend` logic, or a tampered/corrupted archive record for that field).
3. Call `TransactionOutput::ensure_match_transaction_info(version, txn_info, ..)` — as done by `storage/db-tool/src/replay_on_archive.rs` — with the divergent pair.
4. Observe it returns `Ok(())` because `status`, `gas_used`, `write_set_hash`, and `event_root_hash` still match, even though `position_state_checkpoint_hash` (and likewise `state_checkpoint_hash`/`hot_state_checkpoint_hash`) diverges — confirming that replay verification via this API cannot detect state/position root corruption.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
