### Title
Proposal `expires-at` window can collapse to zero against maturity `TIMELOCK`, permanently blocking execution of a matured DAO proposal - (File: `mainnet/contracts/dao/dao-multisig.clar`)

### Summary
`dao-multisig.clar`'s `propose` function computes a proposal's `expires-at` from `created-at + default-expiry-duration`, a value independent of the `TIMELOCK` (1-day maturity delay) used by `execute`. `set-default-expiry-duration` only guards `duration >= TIMELOCK`, not `duration > TIMELOCK`, so `expires-at` can be set exactly equal to `mature-at`, producing a zero-width (or, once block-time granularity is considered, potentially negative) window in which a non-urgent proposal is simultaneously "mature enough" and "not yet expired."

### Finding Description
`propose` fixes the proposal's expiry at creation time: `expiry = now + (var-get default-expiry-duration)` [1](#0-0) . `execute` independently derives maturity as `mature-at = created-at + TIMELOCK` [2](#0-1) , and requires both `stacks-block-time < expires-at` and (`stacks-block-time >= mature-at` OR `urgent`) to succeed.

`set-default-expiry-duration` only enforces `(>= duration TIMELOCK)` [3](#0-2) , not a strict `>`. If the DAO sets `default-expiry-duration` equal to `TIMELOCK` (the minimum allowed value), every subsequently created non-urgent proposal will have `expires-at == mature-at`. Because `execute`'s maturity check uses `>=` (inclusive of `mature-at`) but the expiry check uses `<` (exclusive of `expires-at`), and `mature-at == expires-at`, there is no value of `stacks-block-time` that satisfies both conditions simultaneously — the proposal transitions from "not yet mature" directly to "expired" with no executable window at all, exactly analogous to the referenced Bond Protocol bug where an option's rounded-down expiry could fall before (or coincide with) the epoch-end boundary it was meant to outlive.

This is a single-transaction/no-interference issue: it is purely a mismatch between two independently derived time bounds (`expires-at` fixed at creation from `default-expiry-duration`, `mature-at` derived from the separate constant `TIMELOCK`) that were not required to leave a strict positive gap.

### Impact Explanation
A proposal that reaches the required approval threshold can become permanently non-executable the instant it matures, forcing signers to re-propose and re-collect approvals. If the affected proposal governed a treasury withdrawal, unpausing of a market, or a parameter change needed to unblock stuck user funds (e.g., lifting a liquidation pause or restoring a Vault action), this manifests as a temporary freezing of funds/yield until a new proposal is created, approved, and matured — fitting the "temporary freezing of funds" High-impact category. The severity is bounded because it requires the DAO itself to configure `default-expiry-duration == TIMELOCK`, and only affects non-urgent proposals during the exact boundary block.

### Likelihood Explanation
Likelihood is moderate: it requires the DAO to call `set-default-expiry-duration` with the minimum allowed value (`TIMELOCK`, i.e. exactly 1 day), which is a legitimate, permitted governance action rather than an attack — the guard `>= TIMELOCK` explicitly allows this exact boundary value. Once configured this way, every subsequently created non-urgent proposal is affected deterministically, not probabilistically, since the boundary collapse happens on every proposal under that configuration.

### Recommendation
Change the guard in `set-default-expiry-duration` from `(>= duration TIMELOCK)` to `(> duration TIMELOCK)`, and additionally ensure a minimum buffer (e.g., `duration >= TIMELOCK + MIN-EXECUTION-WINDOW`) so that matured, sufficiently-approved proposals always retain a strictly positive window to be executed before expiring, mirroring the recommended fix in the referenced report (requiring the expiry to be at least some fixed amount longer than the maturity delay).

### Proof of Concept
1. DAO executor calls `set-default-expiry-duration(u86400)` (equal to `TIMELOCK`); this passes the `(>= duration TIMELOCK)` check [3](#0-2) .
2. A signer calls `propose(script, false)` at `now = T`. Stored proposal has `created-at = T`, `expires-at = T + 86400` [1](#0-0) .
3. Enough signers call `approve(id)` before `expires-at`, satisfying `< stacks-block-time expires-at` at approval time [4](#0-3) .
4. At `stacks-block-time = T + 86400`, `mature-at = T + 86400 = expires-at`. Any signer calling `execute(id, script)` finds `stacks-block-time < expires-at` is `false` (since `T+86400 < T+86400` is false), so `ERR-PROPOSAL-EXPIRED` fires regardless of approvals/threshold [2](#0-1) .
5. There is no block at which `stacks-block-time` is simultaneously `>= mature-at` and `< expires-at`; the proposal can never be executed non-urgently, and must be recreated from scratch, delaying any funds-affecting action it was meant to perform.

(define-public (approve (id uint))
  (let ((proposal   (unwrap-panic (map-get? proposals id)))
        (approvals  (get approvals proposal))
        (napprovals (unwrap-panic (as-max-len? (append approvals tx-sender) u20))))
    (try! (check-signer-auth))

    ;; Check expiration first (fail-fast)
    (asserts! (< stacks-block-time (get expires-at proposal)) ERR-PROPOSAL-EXPIRED)

    (asserts! (and
        (not (get executed proposal))
        (is-none (index-of approvals tx-sender))) 
      ERR-SANITY-PROPOSAL)
    
    (map-set proposals id (merge proposal { approvals: napprovals }))
    (ok true)))

(define-public (execute (id uint) (script <proposal-script>))
  (let ((proposal (unwrap-panic (map-get? proposals id)))
        (created-at (get created-at proposal))
        (expires-at (get expires-at proposal))
        (mature-at (+ created-at TIMELOCK))
        (current-threshold (var-get threshold))
        (approvals (len (get approvals proposal))))
    (try! (check-signer-auth))

    ;; check expiration
    (asserts! (< stacks-block-time expires-at) ERR-PROPOSAL-EXPIRED)

    (asserts! 
      (and
        (not (get executed proposal))
        (is-eq (contract-of script) (get script proposal))
        (>= approvals current-threshold)
        (or
          (>= stacks-block-time mature-at)
          (get urgent proposal)))
      ERR-SANITY-PROPOSAL)
