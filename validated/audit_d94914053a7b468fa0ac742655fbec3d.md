Confirmed: `ValidateForExecution` only requires `amount > 0` (any positive integer, no minimum) for `TxType_GAS` [1](#0-0) , and there is no check anywhere in `execute_inbound_gas.go` or `execute_inbound_gas_and_payload.go` that the Uniswap quote or `minPCOut` is non-zero before calling the auto-swap.

### Title
Zero-output AMM swap in gas-abstraction inbound silently burns bridged PRC20 principal for no PC — no revert or `quote > 0` check ([File: x/uexecutor/keeper/execute_inbound_gas.go])

### Summary
`ExecuteInboundGas` and `gasAndPayloadDepositAutoSwap` compute a slippage-protected minimum output (`minPCOut = quote * 95 / 100`) and then call `CallPRC20DepositAutoSwap` to deposit the bridged PRC20 and immediately swap it for native PC through the Uniswap-style `QuoterV2`/`UniversalCore` pair. Neither the fetched `quote` nor the computed `minPCOut` is checked to be strictly positive before the swap executes, and the resulting `PCTx` is marked `"SUCCESS"` as long as the EVM call itself does not revert.

### Finding Description
For `TxType_GAS` inbounds, `ValidateForExecution` only requires the amount to be a positive `uint256` — there is no minimum-amount floor [1](#0-0) . An ordinary unprivileged user (or an attacker forcing this on other users' behalf via a dust bridge event) can submit an inbound with `Amount = 1` (or any value small enough that Uniswap's `quoteExactInputSingle` truncates to `0` for the configured fee tier / pool price).

In `ExecuteInboundGas`, the flow is:
```go
quote, execErr = k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)
...
minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
minPCOut.Div(minPCOut, big.NewInt(100))
receipt, execErr = k.CallPRC20DepositAutoSwap(sdkCtx, prc20AddressHex, ueaAddr, amount, fee, minPCOut)
``` [2](#0-1) 

The identical pattern exists in `gasAndPayloadDepositAutoSwap` for `GAS_AND_PAYLOAD` inbounds [3](#0-2) . If `quote` is `0`, `minPCOut` is also `0`, which removes all slippage protection on the swap — the underlying AMM will accept any non-negative output, including `0`. Because the PRC20 principal is deposited and consumed by the swap regardless of the amount actually returned, the recipient UEA can end up with `0` native PC while the user's entire bridged asset has been irrecoverably spent into the pool.

Crucially, since `execErr == nil` on a successful (non-reverting) EVM call, `shouldRevert` stays `false`, the `PcTx` is recorded as `"SUCCESS"`, and no `INBOUND_REVERT` outbound is created to return funds to the source chain [4](#0-3) . The user has no path to recover their bridged funds: the UTX is marked successful, and no gas top-up was actually delivered.

This directly mirrors the H-8 bug class: a rounding/precision issue silently returns "zero assets" instead of reverting when the computed value from a ratio/quote calculation truncates to zero.

### Impact Explanation
This causes permanent loss of user-bridged funds under the "Allowed Impact Gate" category (permanent loss of user-controlled funds), triggerable purely by an ordinary user submitting a small-value `GAS` or `GAS_AND_PAYLOAD` inbound — no privileged actor, malicious validator, or malicious relayer is required. The loss is silent: the on-chain `UniversalTx` shows a `"SUCCESS"` PCTx, giving no indication to the user or explorers that no gas was actually delivered.

### Likelihood Explanation
Likelihood is moderate to high in practice for low-liquidity PRC20/gas-token pools or tokens with few on-chain decimals, where small but legitimate dust amounts (e.g., leftover balances, minimum bridge amounts on the source chain, or accidental small sends) are common. It requires no coordination and is reachable by any user through the standard inbound-voting → execution pipeline once quorum is reached by honest validators observing a genuinely small on-chain event.

### Recommendation
Before calling `CallPRC20DepositAutoSwap` (in both `ExecuteInboundGas` and `gasAndPayloadDepositAutoSwap`), require `quote.Sign() > 0` (and therefore `minPCOut.Sign() > 0` after applying slippage, or at minimum treat `minPCOut == 0` as an execution failure rather than a valid swap parameter). Treat a zero quote as an execution failure and route through the existing `shouldRevert`/`INBOUND_REVERT` path so the user's bridged asset is minted back to them on the source chain instead of being silently consumed for zero output.

### Proof of Concept
1. Configure/observe a `GAS` inbound on a source chain for a PRC20 whose Uniswap pool against `WPC` has a price such that `quoteExactInputSingle(amountIn=1)` (or any very small `amountIn`) returns `0` due to integer-division truncation in the AMM's constant-product math.
2. Submit (or have a user submit) that inbound; 3 of 4 validators vote it in (`reachGasQuorum`), matching the reachable quorum pattern used in `test/integration/uexecutor/execute_inbound_gas_test.go` [5](#0-4) .
3. `ExecuteInboundGas` fetches `quote = 0`, computes `minPCOut = 0`, and calls `CallPRC20DepositAutoSwap` with `minPCOut=0`.
4. The swap executes without reverting (since any output ≥ 0 satisfies `minPCOut=0`), the PRC20 principal is consumed, and the UEA receives `0` PC.
5. `pcTx.Status` is set to `"SUCCESS"`, no revert outbound is created, and the user's original bridged PRC20 balance is permanently gone with zero PC delivered.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
