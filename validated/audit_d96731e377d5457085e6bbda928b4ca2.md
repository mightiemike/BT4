## Title
Gas-limit DoS via unbounded `PendingInbounds` scan in ballot termination hook - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
The Union Finance bug class is "an attacker keeps growing an on-chain array with cheap/free entries, and a later user-facing function does a full for-loop over that array, causing gas-limit DoS." The Push Chain analog is `PendingInbounds`, a collection keyed by `utx_key` that grows by one entry every time a Universal Validator (UV) casts the *first* vote on a distinct inbound observation [1](#0-0) . Growth of this collection is ultimately driven by attacker-controlled input: any external-chain transaction that the gateway contract emits as a `UniversalTx`/inbound event becomes a new, distinct `utx_key` entry once an honest UV observes and votes on it — no minimum value, dedup-by-sender, or entry cap is enforced on-chain before the vote is recorded.

### Finding Description
`RecordInboundVote` idempotently appends a new `PendingInboundEntry`/`InboundVariant` for every unique `(utx_key, ballotID)` pair it sees [2](#0-1) . Because `utx_key = sha256(source_chain:tx_hash:log_index)`, an attacker can trivially mint an unbounded number of distinct keys simply by emitting many source-chain events (e.g. dust-value or zero-value deposits/gateway calls) — this costs only external-chain gas, not Push Chain gas, and requires no privileged role.

When any one of these ballots reaches a terminal state (PASSED/REJECTED/EXPIRED), `x/uvalidator` invokes the registered `BallotHooks.AfterBallotTerminal` callback, which for inbound ballots calls `afterInboundBallotTerminal` [3](#0-2) . That function performs a **full linear walk over the entire `PendingInbounds` collection** to locate the entry whose variant carries the terminating `ballotID`, because ballot IDs are one-way digests and are not otherwise indexed back to their owning `utx_key`: [4](#0-3) 

This is the same pattern as the reported bug: an attacker-inflatable collection (`vouchers[]` ↔ `PendingInbounds`) is iterated end-to-end (`for i := 0; i < vouchers[borrower].length; i++` ↔ `PendingInbounds.Walk`) inside a codepath that fires on ordinary, honest-validator-driven operations (`updateLocked()`/`registerMember()` ↔ every `MsgVoteInbound` that finalizes a ballot). The comment in the code explicitly assumes "the pending set is small and transient" [5](#0-4) , but nothing in `RecordInboundVote`, `VoteInbound`, or `x/uregistry` enforces that assumption — an attacker fully controls how many entries exist by choosing how many distinct source-chain events to generate.

Because `MsgVoteInbound` is a gasless message type (`app/txpolicy/gasless.go` allowlist) [6](#0-5) , UVs are not economically deterred from voting frequently, but every vote that finalizes a ballot still consumes real Push Chain execution time/gas proportional to `len(PendingInbounds)` for the `Walk`. As the attacker keeps the pending set large (by continuously emitting fresh source-chain events faster than they finalize, or simply by the natural backlog while many events are in flight), each subsequent honest `MsgVoteInbound` that finalizes any ballot degrades — this is the "gas limit DoS via unbounded operations" pattern applied to Push Chain's inbound voting/finalization hot path rather than Union's vouching hot path.

### Impact Explanation
If `PendingInbounds` is inflated to a large size, every ballot-finalizing `MsgVoteInbound` transaction thereafter pays an O(n) state-read cost for the `Walk`, scoped entirely to code invoked by honest Universal Validators processing ordinary, unprivileged user/attacker deposit events. In the worst case this can push individual vote transactions toward the gas/time budget for block inclusion, throttling or stalling inbound finalization for legitimate users' cross-chain deposits/payload executions system-wide — a non-network-level DoS reachable purely by an unprivileged external actor flooding cheap source-chain events, without compromising or assuming any malicious validator, relayer, or admin.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to sustain a volume of cheap external-chain transactions large enough that `PendingInbounds` stays inflated across many honest UV votes. This is straightforward on low-fee source chains (e.g. certain L2s/testnets), and nothing in `RecordInboundVote` restricts the number of distinct outstanding entries, requires a minimum transferred amount, or rate-limits entries per source address before they enter `PendingInbounds`.

### Recommendation
- Maintain a reverse index from `ballotID -> utx_key` (e.g. a `collections.Map`) so `afterInboundBallotTerminal` can do an O(1) lookup instead of walking the entire `PendingInbounds` collection.
- Alternatively/additionally, bound the number of concurrently pending `PendingInbounds` entries (or entries per source chain/sender), and/or require a minimum inbound value or per-source-chain rate limiting before an inbound is admitted into `PendingInbounds`.

### Proof of Concept
1. On a supported, cheap-fee source chain, repeatedly call the gateway contract to emit many distinct qualifying inbound events (e.g. dust-value deposits), each producing a unique `(source_chain, tx_hash, log_index)` triple and thus a unique `utx_key`.
2. Honest Universal Validators automatically observe and vote via `MsgVoteInbound` for each event, each first vote creating a new `PendingInboundEntry` via `RecordInboundVote` [2](#0-1) , growing `PendingInbounds` without bound as the attacker keeps submitting new events faster than they finalize.
3. As soon as any one ballot (potentially a legitimate user's unrelated inbound) reaches a terminal state, `afterInboundBallotTerminal` performs a full `PendingInbounds.Walk` over the now-large collection [7](#0-6) , incurring cost proportional to the attacker-inflated collection size on every subsequent finalizing vote, degrading inbound-finalization throughput for all users.
