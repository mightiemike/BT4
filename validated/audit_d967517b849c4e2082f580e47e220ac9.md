### Title
Merchant Custom App admin authentication trusts an unauthenticated `shop` query parameter, granting anyone the app's Admin API access token - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts`)

### Summary
For apps configured with `distribution: AppDistribution.ShopifyAdmin` (Shopify-Admin-distributed / "merchant custom" apps), `shopify.authenticate.admin(request)` never verifies the caller's identity. It reads `shop` straight from the URL query string and hands it to `MerchantCustomAuth.authenticate`, which unconditionally builds a `Session` carrying the app's single configured `adminApiAccessToken` for that shop, then returns a working `admin` GraphQL/REST client. This is structurally the same class of bug as the reference finding: a privileged operation (`payableCall` granting arbitrary calls with the account's assets) is missing the access-control check (`requiresApprovedCaller`) that its sibling method (`call`) enforces. Here, `authenticate.admin` for non-OAuth (`ShopifyAdmin`) distribution is missing the equivalent of a `requiresApprovedCaller`-style check (HMAC/session-token/signature validation) that the OAuth and token-exchange strategies perform for every other distribution type.

### Finding Description
In `getSessionTokenContext` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts:189-229`, identical code exists in `shopify-app-react-router`), the embedded-app branch validates a signed JWT session token: [1](#0-0) 

But when `config.isEmbeddedApp` is falsy (which is required/typical for `AppDistribution.ShopifyAdmin` merchant custom apps, per the CHANGELOG guidance to set `isEmbeddedApp: false`), the code falls through to: [2](#0-1) 

`shop` is taken directly from `url.searchParams.get('shop')` with **no HMAC validation, no session-token verification, and no signature check of any kind**.

That `shop` value flows into `strategy.authenticate(request, {session: existingSession, sessionToken, shop})` (`authenticate.ts:169-173`). For merchant custom apps, the selected strategy is `MerchantCustomAuth`: [3](#0-2) 

`respondToOAuthRequests` is a no-op ("Skipping OAuth request for merchant custom app"), and `authenticate` unconditionally calls `api.session.customAppSession(shop)`, which builds a `Session` using the shop string with no ownership/authenticity check: [4](#0-3) 

That session is then used to construct the `admin` client with the app's single statically configured Admin API access token (`config.adminApiAccessToken`), as documented: [5](#0-4) 

The library's own CHANGELOG explicitly acknowledges this design gap but frames it as the app developer's responsibility rather than enforcing it in the library: "These apps do not Authorize by OAuth... it is up to the developer of the app to add login and authentication functionality" (`packages/apps/shopify-app-remix/CHANGELOG.md:976-984`). Despite that caveat, `shopify.authenticate.admin()` — the function apps are told to call to "authenticate" a request — returns a fully functional, credentialed `admin` API context without performing any authentication of the request itself.

### Impact Explanation
Any anonymous HTTP request to a route protected by `shopify.authenticate.admin()` in a Shopify-Admin-distribution (merchant custom) app succeeds and returns a live `admin` API client backed by the app's real Admin API access token — regardless of who sent the request or what `shop` value they supplied. This is directly analogous to the reference vulnerability: a function meant to gate a privileged capability (spending assets / calling the Admin API on the merchant's behalf) is missing the authorization check that its sibling code path (the embedded/OAuth/token-exchange strategies) correctly performs. Any app built on this library for `AppDistribution.ShopifyAdmin` and relying on `authenticate.admin()` as its access-control boundary (a reasonable assumption given the function's name and its behavior in every other distribution mode) exposes full Admin API access (products, orders, customers, etc., scoped to whatever the token's scopes are) to any unauthenticated visitor.

### Likelihood Explanation
High for apps of this specific distribution type: no attacker-controlled secret, MITM, or privileged actor is required — a single unauthenticated HTTP GET/POST to any `authenticate.admin()`-protected route is sufficient. The behavior is 100% reachable by design (it is the sole non-OAuth code path), not an edge case. It is scoped to `AppDistribution.ShopifyAdmin` apps (a real, supported configuration), and the CHANGELOG shows the maintainers are aware developers must independently add authentication for this mode, meaning the library ships this behavior without a compensating control.

### Recommendation
For `AppDistribution.ShopifyAdmin` (`MerchantCustomAuth`), `shopify.authenticate.admin()` should not silently trust the `shop` query parameter as sufficient authentication. At minimum, the library should require and validate an authenticated signal (e.g., a signed session cookie set by an app-provided login flow, or a required session-token/HMAC check) before calling `api.session.customAppSession(shop)` and returning a credentialed `admin` client — mirroring the `requiresApprovedCaller`-equivalent checks already present in the embedded/token-exchange/OAuth strategies. At a minimum, `authenticate.admin()`'s documentation and typings should make it unmistakable (ideally via a compile-time or runtime guard) that this call performs no authentication for `ShopifyAdmin` distribution and must not be relied upon as an access-control boundary.

### Proof of Concept
1. Configure an app with `distribution: AppDistribution.ShopifyAdmin`, `isEmbeddedApp: false`, and a valid `adminApiAccessToken` (as in `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/__tests__/merchant-custom/authenticate.test.ts`).
2. Send an unauthenticated request: `GET {APP_URL}?shop=<any-string>` — no cookies, no Authorization header, no HMAC.
3. Observe `authenticate.admin(request)` resolves successfully (as demonstrated by the existing test): [6](#0-5) 

returning `session` and `admin`, both backed by the real `adminApiAccessToken`, with no verification that the caller is an authorized party for that shop/install.

*Note: I was not able to fully trace `packages/apps/shopify-app-remix/src/server/shopify-app.ts` (strategy-selection wiring) or `unauthenticatedAdminContextFactory`'s external callers within the indexed context, so I cannot rule out that some deployments add an additional guard upstream (e.g., in `shopify-app.ts`) before invoking `authenticate.admin`. This should be verified in a full checkout of the repository.*

### Making requests

API requests, either using `shopify.clients.Rest` or `shopify.clients.Graphql`, or using the REST resources, require a `session` parameter.  Since there are no sessions in a store-specific custom app, a `session` parameter needs to be created.

To create the session object, the `id`, `state` and `isOnline` properties must be populated but will be ignored.  Only the `shop` parameter is required when making the API requests from a store-specific custom app and the value must match the shop on which the custom app is installed.

The library provides a utility method to create such a session, `shopify.session.customAppSession`.
