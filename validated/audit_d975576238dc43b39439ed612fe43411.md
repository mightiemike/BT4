### Title
`many_ref_accounts_can_be_moved` underestimates required packed storages, allowing `PackedAncientStorage::pack` to place a many-ref account below its true newest-alive slot - (`accounts-db/src/ancient_append_vecs.rs`)

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` decides whether ancient-slot packing is safe by estimating the number of packed storages needed for multi-ref "newest alive" accounts using a single division of aggregate bytes (`alive_bytes / ideal_storage_size + 1`). The actual bin-packer, `PackedAncientStorage::pack`, cannot split individual accounts across storages, so multiple independent many-ref groups with awkward sizes can force more bins than the aggregate estimate predicts. When this happens, `write_packed_storages` maps the overflow bin(s) to a lower target slot than the safety check assumed, which can place a many-ref account's newest version into a slot below its own current slot.

### Finding Description
`combine_ancient_slots_packed_internal` computes `many_refs_newest` (one `AliveAccounts` group per original ancient slot containing pubkeys whose ref_count > 1 but for which that slot is the newest alive occurrence), sorts them descending by slot, and calls: [1](#0-0) 

`required_ideal_packed = alive_bytes / ideal_storage_size + 1` is only a lower-bound estimate assuming perfect packing of the aggregate byte total. It ignores that `PackedAncientStorage::pack` (called later at line 496) processes each `AliveAccounts` group sequentially and cannot split an individual account across bins: [2](#0-1) 

When a group's remaining accounts don't fit the current bin's leftover space, the packer closes the bin early (wasting the leftover space) and starts a new bin for the next group. With several independent many-ref groups whose sizes are each slightly larger than half of `ideal_storage_size`, this forces one bin per group in the worst case (`n` bins), while `many_ref_accounts_can_be_moved`'s formula predicts roughly `n/2 + 1` bins.

The check only verifies that `target_slots_sorted[len - required_ideal_packed]` (the smallest of the assumed-sufficient top slots) is >= the maximum slot among all many-ref groups. It does not re-verify against the *actual* bin count that `pack()` will produce. The only downstream guard, `pack.len() > accounts_to_combine.target_slots_sorted.len()` at line 506-509, checks the total bin count (including one-ref accounts chained afterward) against the total number of available target slots — it does not check that the many-ref-only portion still lands within the originally verified "highest_slot" threshold.

Because `write_packed_storages` zips `target_slots_sorted.iter().rev()` with `packed_contents` in the same order `pack()` produced them (highest-slot group's data goes to the highest target slot first), an extra/overflow bin caused by fragmentation is assigned to a lower target slot than assumed safe: [3](#0-2) 

If `target_slots_sorted` (the pool of "safe to move anywhere" one-ref slots processed in the same batch) contains a sufficiently low slot value, the overflow group's account can be written to a target slot below its own current/original slot — violating the documented invariant described directly in the surrounding code comments ("the highest slot # where an account exists defines the most recent account"): [4](#0-3) 

An attacker (unprivileged) can influence this by repeatedly rewriting the same pubkeys across many distinct old (ancient) slots with account sizes chosen to be just over half of the ideal packed-storage size, so multiple such pubkeys each occupy their own "many_refs_this_is_newest_alive" group in a future `combine_ancient_slots_packed` pass, while also writing many distinct single-write pubkeys in old slots to populate the "one-ref" `target_slots_sorted` pool with a wide slot range (including low slots).

### Impact Explanation
If a many-ref account's newest version is relocated to a slot lower than its true newest-alive slot, a subsequent `load()` at an intermediate ancestor slot (between the relocated packed slot and the account's true newest slot) can incorrectly return a stale (or, depending on layering with other slot-list entries, ambiguous) version of the account. This falls under stale/wrong-version account loads and potential bank-hash/capitalization divergence between nodes whose ancient-packing runs (which include a `can_randomly_shrink` random component and different batch timings) diverge — matching the "stale or wrong-version account loads" / "hash or capitalization divergence" bounty categories.

### Likelihood Explanation
This requires: (1) multiple independent many-ref pubkeys landing in the same ancient-slot combine batch with sizes engineered relative to the (cluster-computed, not fully attacker-known) `ideal_storage_size`, and (2) a favorable `target_slots_sorted` layout containing both very high slots (to pass the aggregate check) and very low slots (to receive the overflow bin). The attacker controls (1) directly through account writes but only indirectly influences (2), since `ideal_storage_size` and the exact set of ancient slots processed together depend on cluster-wide ancient-slot state, not solely the attacker's own accounts. This makes the bug a real, reachable logic defect in `many_ref_accounts_can_be_moved`, but exploitation to a guaranteed, reliably reproducible on-chain consensus mismatch requires a specific and somewhat improbable natural or engineered layout of ancient slots, so likelihood is moderate/low rather than trivially achievable on demand.

### Recommendation
Replace the aggregate byte-division estimate in `many_ref_accounts_can_be_moved` with a simulation of the actual bin assignment (e.g., run `PackedAncientStorage::pack` on `many_refs_newest` alone first, then verify per-produced-bin that its assigned target slot, according to the same reverse-order zip used by `write_packed_storages`, is >= the maximum origin slot of any account placed in that bin), rather than relying on a single division-based lower bound that ignores per-account bin-packing fragmentation across multiple groups.

### Proof of Concept
Rust unit test plan (extending existing tests in `accounts-db/src/ancient_append_vecs.rs`, e.g. near `test_many_ref_accounts_can_be_moved` and `test_pack_ancient_storages_varying`):

1. Construct `ideal_storage_size = 100` (as `NonZeroU64`).
2. Build 3 synthetic `AliveAccounts` many-ref groups (`many_refs_newest`), each with `bytes = 60` and slots `1000, 900, 800` respectively (descending, matching real sort order).
3. Call `AccountsDb::many_ref_accounts_can_be_moved(&many_refs_newest, &target_slots_sorted, &tuning)` with `target_slots_sorted = vec![500, 1001, 1002]`.
   - Expected (buggy) result: returns `true` (since `required_ideal_packed = 180/100+1 = 2`, and `target_slots_sorted[3-2]=1001 >= 1000`).
4. Call `PackedAncientStorage::pack(many_refs_newest.iter(), ideal_storage_size)` directly and assert `pack.len() == 3` (not 2 as the safety check assumed).
5. Simulate `write_packed_storages`'s reverse-zip mapping: `target_slots_sorted.iter().rev().zip(pack)` and assert that the third bin (containing the group with `slot = 800`) is mapped to `target_slot = 500`.
6. Assert `500 < 800`, demonstrating the invariant violation: `many_ref_accounts_can_be_moved` returned `true` even though the actual packing places an account below its own current slot.
7. (End-to-end variant) Using `create_db_with_storages_and_index`/`get_sample_storages` helpers already in the test module, construct real storages with pubkeys matching this exact byte/slot layout, run `combine_ancient_slots_packed_internal`, then call `AccountsDb::load` for the affected pubkey at an ancestor slot between 500 and 800, and assert the returned account data differs from (is staler than) the value written at slot 800 — proving a genuine stale read.

    /// accounts in `many_refs_newest` must be moved a slot >= each account's current slot.
    /// If that can be done, this fn returns true
    fn many_ref_accounts_can_be_moved(
        many_refs_newest: &[AliveAccounts<'_>],
        target_slots_sorted: &[Slot],
        tuning: &PackedAncientStorageTuning,
    ) -> bool {
        let alive_bytes = many_refs_newest
            .iter()
            .map(|alive| alive.bytes)
            .sum::<usize>();
        let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
        if alive_bytes == 0 {
            // nothing required, so no problem moving nothing
            return true;
        }
        if target_slots_sorted.len() < required_ideal_packed {
            return false;
        }
        let i_last = target_slots_sorted
            .len()
            .saturating_sub(required_ideal_packed);

        let highest_slot = target_slots_sorted[i_last];
        many_refs_newest
            .iter()
            .all(|many| many.slot <= highest_slot)
    }

    fn pack(
        mut accounts_to_combine: impl Iterator<Item = &'a AliveAccounts<'a>>,
        ideal_size: NonZeroU64,
    ) -> Vec<PackedAncientStorage<'a>> {
        let mut result = Vec::default();
        let ideal_size: u64 = ideal_size.into();
        let ideal_size = ideal_size as usize;
        let mut current_alive_accounts = accounts_to_combine.next();
        // starting at first entry in current_alive_accounts
        let mut partial_inner_index = 0;
        // 0 bytes written so far from the current set of accounts
        let mut partial_bytes_written = Saturating(0);
        // pack a new storage each iteration of this outer loop
        loop {
            let mut bytes_total = 0usize;
            let mut accounts_to_write = Vec::default();

            // walk through each set of alive accounts to pack the current new storage up to ideal_size
            let mut full = false;
            while !full && current_alive_accounts.is_some() {
                let alive_accounts = current_alive_accounts.unwrap();
                if partial_inner_index >= alive_accounts.accounts.len() {
                    // current_alive_accounts have all been written, so advance to next set from accounts_to_combine
                    current_alive_accounts = accounts_to_combine.next();
                    // reset partial progress since we're starting over with a new set of alive accounts
                    partial_inner_index = 0;
                    partial_bytes_written = Saturating(0);
                    continue;
                }
                let bytes_remaining_this_slot =
                    alive_accounts.bytes.saturating_sub(partial_bytes_written.0);
                let bytes_total_with_this_slot =
                    bytes_total.saturating_add(bytes_remaining_this_slot);
                let mut partial_inner_index_max_exclusive;
                if bytes_total_with_this_slot <= ideal_size {
                    partial_inner_index_max_exclusive = alive_accounts.accounts.len();
                    bytes_total = bytes_total_with_this_slot;
                } else {
                    partial_inner_index_max_exclusive = partial_inner_index;
                    // adding all the alive accounts in this storage would exceed the ideal size, so we have to break these accounts up
                    // look at each account and stop when we exceed the ideal size
                    while partial_inner_index_max_exclusive < alive_accounts.accounts.len() {
                        let account = alive_accounts.accounts[partial_inner_index_max_exclusive];
                        let account_size = account.stored_size();
                        let new_size = bytes_total.saturating_add(account_size);
                        if new_size > ideal_size && bytes_total > 0 {
                            full = true;
                            // partial_inner_index_max_exclusive is the index of the first account that puts us over the ideal size
                            // so, save it for next time
                            break;
                        }
                        // this account fits
                        partial_bytes_written += account_size;
                        bytes_total = new_size;
                        partial_inner_index_max_exclusive += 1;
                    }
                }

                if partial_inner_index < partial_inner_index_max_exclusive {
                    // these accounts belong in the current packed storage we're working on
                    accounts_to_write.push((
                        alive_accounts.slot,
                        // maybe all alive accounts from the current or could be partial
                        &alive_accounts.accounts
                            [partial_inner_index..partial_inner_index_max_exclusive],
                    ));
                }
                // start next storage with the account we ended with
                // this could be the end of the current alive accounts or could be anywhere within that vec
                partial_inner_index = partial_inner_index_max_exclusive;
            }
            if accounts_to_write.is_empty() {
                // if we returned without any accounts to write, then we have exhausted source data and have packaged all the storages we need
                break;
            }
            // we know the full contents of this packed storage now
            result.push(PackedAncientStorage {
                bytes: bytes_total as u64,
                accounts: accounts_to_write,
            });
        }
