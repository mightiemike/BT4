## Finding: Replay-verification comparator silently skips state-root checkpoint hashes

### Title
Replay-verify comparator (`TransactionOutput::ensure_match_transaction_info`) never validates `state_checkpoint_hash`, allowing a corrupted authenticated state root to pass verification - (`types/src/transaction/mod.rs`)

### Summary
The `MuteBond` report's core lesson is: a value that is supposed to gate/verify a critical outcome (`maxPurchaseAmount()`) is used without re-validating it against the caller's actual intent, so a stale/wrong value silently passes through and is accepted as correct. The Aptos-native analog found in `TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  is structurally similar: this function is the authenticated comparator used by replay/verification tooling to check that a freshly re-executed `TransactionOutput` matches the committed, ledger-accumulator-bound `TransactionInfo`. It checks status, gas, write-set hash, and event-root hash — but never checks `state_checkpoint_hash` (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), which is explicitly acknowledged by a `TODO(trading-native)` comment left in the code itself.

### Finding Description
`TransactionInfo` (V0/V1) carries `state_checkpoint_hash: Option<HashValue>` — the Merkle root of world state as of that transaction, which is part of the hashed leaf committed into the transaction accumulator and therefore cryptographically authenticated by ledger-info signatures (see the `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields in [2](#0-1) ). `ensure_match_transaction_info` is the function tooling calls after locally re-executing a transaction to assert that local execution reproduces the authenticated on-chain result. It validates `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash`, but explicitly returns `Ok(())` without ever comparing `self`'s locally-recomputed state root to `txn_info.state_checkpoint_hash()`: [3](#0-2) 

This comparator is relied upon by three independent integrity/audit tools as the sole cross-check between re-execution and the authenticated ledger record:
- `storage/db-tool/src/replay_on_archive.rs`, the archive replay-verification tool, which re-executes historical transactions from a backup/archive DB and calls `ensure_match_transaction_info` per transaction to flag divergence: [4](#0-3) 
- `aptos-move/cli/src/commands.rs` transaction simulation/replay path: [5](#0-4) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`

Because the state checkpoint hash is never validated, none of these tools can detect a divergence between the locally re-executed world-state root and the state root that was actually committed on-chain and signed into the ledger accumulator. All other output fields (status/gas/write-set/events) can match while the state root itself is wrong, and the comparator will still report success.

### Impact Explanation
This breaks the "authenticated API/proof-bearing response bound to the right root" invariant from the Proof And Storage Pivots: the `state_checkpoint_hash` is a proof-bearing, accumulator-committed field, yet the code path whose entire purpose is to verify committed state against independently recomputed state accepts any value for it. Concretely:
- Archive replay-verify (`db-tool replay_on_archive`) is a primary integrity tool operators/auditors run against mainnet archival data to detect any historical divergence (bugs, non-determinism, or tampering) between committed ledger state and correct VM execution. With this gap, a corrupted or malicious `state_checkpoint_hash` in stored history — or a state-root-affecting execution bug that leaves write-set/events/gas/status unchanged — is invisible to this tool.
- This directly matches the required impact "Wrong accumulator root... or state proof accepted as valid" — the authenticated `state_checkpoint_hash` is effectively unauthenticated in this verification path, and "Hard-fork-only divergence during commit, replay ... or proof verification" is also implicated: two nodes/tools could believe they've verified identical history while their post-transaction state roots actually diverge.

### Likelihood Explanation
The gap is unconditional (not behind a feature flag) for the main `state_checkpoint_hash`; it applies to every call of `ensure_match_transaction_info`, which is the standard/only integrity check performed by `replay_on_archive`, the CLI simulate/replay commands, and the debugger. No privileged access or malicious peer behavior is required — any operator running the standard replay-verify tool against an archive with a subtly wrong state root would get a false "verified" result. The TODO comment confirms the maintainers are aware only of the trading-native (`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) omission, but the code shows the pre-existing, mainnet-relevant `state_checkpoint_hash` field is also skipped.

### Recommendation
In `ensure_match_transaction_info`, add a check that recomputes/receives the local state-checkpoint root (when the transaction is a checkpoint boundary) and compares it against `txn_info.state_checkpoint_hash()`, failing with a descriptive `ensure!` similar to the existing write-set/event-root checks, before any of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-style hot/position checks are added. At minimum, the well-established main `state_checkpoint_hash` should be validated unconditionally to restore the integrity guarantee that `replay_on_archive`/CLI-simulate/`aptos-debugger` are supposed to provide.

### Proof of Concept
1. Take (or construct) a backup/archive with one transaction whose stored `TransactionInfo.state_checkpoint_hash` is altered/corrupted (e.g., off-by-one nibble) while `write_set`, `events`, `gas_used`, and `status` remain byte-identical to the value a correct VM execution would produce.
2. Run `storage/db-tool/src/replay_on_archive.rs` (`cargo run --bin db-tool -- replay-on-archive --start-version ... --end-version ...`) against that archive.
3. Observe `Verifier::execute_and_verify` -> `ensure_match_transaction_info` ( [6](#0-5) ) returns `Ok(())` and the tool reports zero failed transactions, despite the state root mismatch — demonstrating the authenticated state-checkpoint proof field is never actually checked by the verification pipeline.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
