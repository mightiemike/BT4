### Title
`TransactionOutput::ensure_match_transaction_info` omits state-checkpoint hash checks, letting replay-verify tooling accept a divergent authenticated state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the sole comparator used by `storage/db-tool/src/replay_on_archive.rs` to validate that locally re-executed transaction outputs match the authenticated (validator-signed) `TransactionInfo` pulled from archive/backup [2](#0-1) . It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the Sparse-Merkle/JMT world-state root and the new native-trading position-state root [3](#0-2) .

### Finding Description
`TransactionInfoV1`/`V0` carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as the authenticated commitments to world state, hot-state, and (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) native-position state [4](#0-3) , and these are populated by `assemble_transaction_infos` in the executor's ledger-update path as first-class, consensus-committed fields [5](#0-4) . However `ensure_match_transaction_info` — the function that db-tool's replay-verify uses to decide whether a re-executed transaction "matches" the archived, ledger-info-authenticated `TransactionInfo` — never compares any of the three checkpoint-hash fields to values recomputed from the freshly executed state. This is explicitly acknowledged in-code:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [6](#0-5) 

`storage/db-tool/src/replay_on_archive.rs::execute_and_verify` calls exactly this comparator as the pass/fail gate after re-executing a chunk via `AptosVMBlockExecutor`, with no supplementary check of state/position roots elsewhere in that function [7](#0-6) . `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a real, currently-being-rolled-out feature flag (`FeatureFlag = 122`) whose doc explicitly says it "commits [the native-position state root] to `TransactionInfoV1`, so it is consensus-verified" [8](#0-7) . This means the field is meant to be an authenticated, security-relevant commitment, yet the tooling built to detect divergence in exactly this kind of committed root silently ignores it.

### Impact Explanation
Any bug in VM execution, in the native-position/hot-state state-checkpoint-hash computation path, or a non-determinism between validator execution and archive-replay execution that only manifests in the world-state/hot-state/position-state root (and not in the write-set hash, events, gas, or status) will pass `replay_on_archive` undetected. Since this tool is precisely the mechanism intended to catch and hard-fault on any divergence between recorded ledger history and re-execution (i.e., to detect state-commitment corruption or non-determinism before it can cause consensus/chain-split issues), silently accepting a wrong state/position root undermines the core proof-and-storage invariant that "committed state that differs from the correct VM result... must be detected," directly matching the in-scope "hard-fork-only divergence during commit, replay, restore" category. This is a state-integrity/verification gap, not merely a cosmetic omission, because it is the authenticated root binding storage/replay to the correct ledger state that goes unchecked.

### Likelihood Explanation
The gap is deterministic and code-confirmed (not speculative): the comparator is unconditionally missing the three checkpoint-hash checks regardless of feature-flag state, and the code comment shows the authors are aware but have not yet fixed it, explicitly naming `db-tool`'s `replay_on_archive` as the affected consumer. It would trigger any time execution diverges specifically in checkpoint/position state (e.g. from a native-trading state computation bug, a hot-state promotion bug, or any other logic error confined to state-tree assembly) while write sets/events/gas/status still happen to match — a realistic failure mode for a new state root computation path (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) still being staged for rollout.

### Recommendation
Extend `ensure_match_transaction_info` to also recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on the `TransactionInfo` variant) against values derived from the locally executed state, and fail replay verification on mismatch — as the existing TODO already specifies — before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `HOT_STATE_ROOT_IN_TXN_INFO` are enabled on any environment where `replay_on_archive` is relied upon as an integrity check.

### Proof of Concept
1. Enable (or simulate, in a test binary) `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` and produce an archived `TransactionInfoV1` whose `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` corresponds to a specific native-position/hot-state tree.
2. Introduce (or simulate via a modified executor build) a divergence purely in the native-position/hot-state root computation (write set, events, gas, and status remain identical to the archived record).
3. Run `storage/db-tool/src/replay_on_archive::Opt::run` over that version range; `execute_and_verify` calls `ensure_match_transaction_info` [9](#0-8) , which returns `Ok(())` because it never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` [10](#0-9) , so the tool reports the replay as successful despite the state-root divergence.
