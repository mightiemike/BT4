### Title
Unchecked subtraction in `AccountStorageReader::new` can panic (underflow) when tombstone bytes exceed computed alive bytes - (File: accounts-db/src/account_storage_reader.rs)

### Summary
`AccountStorageReader::new` computes `num_alive_bytes` by subtracting obsolete-account bytes and (optionally) tombstone bytes from a storage's total byte length using plain `-` operators instead of `checked_sub`/`saturating_sub`. This mirrors the Perennial `claimAmount > _totalAssetsAtEpoch` unsigned-underflow bug class: a derived "amount owed" value is subtracted from a base total without a guard that the subtrahend cannot exceed the base, so if the invariant is ever violated, the subtraction underflows.

### Finding Description
In `AccountStorageReader::new`: [1](#0-0) 
computes `num_alive_bytes = num_total_bytes - storage.get_obsolete_bytes(snapshot_slot)` using raw subtraction, and later: [2](#0-1) 
does `num_alive_bytes -= tombstone_offsets.len() * tombstone_stored_size` when `TombstonesFilter::Exclude` is requested — again with no `checked_sub`/`saturating_sub` guard.

Both subtractions assume `storage.get_obsolete_bytes(snapshot_slot) <= num_total_bytes` and `tombstone_offsets.len() * tombstone_stored_size <= num_alive_bytes` always hold. These invariants depend on `obsolete_accounts` and `tombstone_offsets` bookkeeping in `AccountStorageEntry` staying perfectly consistent with the storage's actual on-disk contents across the shrink/clean/tombstone-carry-forward lifecycle described in `account_storage_entry.rs`: [3](#0-2) 
Tombstones are carried forward by shrink into new storages, and obsolete accounts are marked separately by clean/shrink. This reader is exercised when snapshots are archived (`snapshots/src/archive.rs` uses `AccountStorageReader` to stream storage contents while excluding obsolete/tombstone bytes), so any bookkeeping drift between `num_alive_bytes`/`get_obsolete_bytes` and the tombstone/obsolete offset sets would trigger a debug-and-release-mode panic (subtract-with-overflow on `usize` panics in all build configurations, not only debug, since this is explicit `-`, not `wrapping_sub`).

This is structurally the same "unsigned amount subtracted from a total without validating amount <= total" pattern as the Perennial `_rebalancePosition`/`claimAmount` bug, but here it lives in the snapshot-archival hot path of `accounts-db`.

### Impact Explanation
If `get_obsolete_bytes(snapshot_slot)` ever returns a value larger than `storage.accounts.len()`, or if `tombstone_offsets.len() * tombstone_stored_size` exceeds the already-reduced `num_alive_bytes`, the subtraction panics with an unsigned-integer-underflow abort. Because `AccountStorageReader` is used during snapshot archive creation (`snapshots/src/archive.rs`), a panic here would crash the validator process during snapshot generation — a node-panic / availability impact rather than silent balance corruption, since Rust's default arithmetic panics on overflow/underflow for both debug and release builds when using bare `-` on unsigned integers only in debug builds by default; in release builds without overflow-checks, this would instead wrap silently, producing a nonsensical `num_alive_bytes` and corrupting the archived snapshot's account count computed in `Read::read` (which relies on `num_total_bytes` and offsets), because `AccountsFile::new_from_file` later re-derives the account count from the truncated stream length. I could not verify from the available code whether the workspace builds with `overflow-checks = true` in release profile; this determines whether the effect is a panic (DoS) or silent wraparound leading to a corrupted/mismatched snapshot (hash/capitalization divergence upon reload). Either outcome maps to accepted impact categories (node panic, or honest-node snapshot mismatch).

### Likelihood Explanation
I was unable to fully verify, within the available tool budget, whether `get_obsolete_bytes` and the tombstone-offset bookkeeping can actually drift from `storage.accounts.len()`/`num_alive_bytes` under real production sequences (e.g., ZLSR accounts transitioning to tombstones concurrently with obsolete-marking, or reopening a storage read-only mid-shrink). The code comment in `account_storage_entry.rs` explicitly acknowledges a similar double-counting race for zero-lamport single-ref accounts becoming obsolete twice, suggesting these offset sets are known to be delicate under concurrent clean/shrink; whether that specific race can push `get_obsolete_bytes` or tombstone byte totals past their bases is not proven here — this is a "hint," not a proven root cause, consistent with the analog nature of this bug class.

### Recommendation
Replace the two bare subtractions in `AccountStorageReader::new` with `checked_sub` (panicking with a clear diagnostic on violation, or explicitly asserting the invariant with a descriptive message) or `saturating_sub` with an accompanying `debug_assert!`/invariant check, matching the pattern already used elsewhere in `accounts_db.rs` (e.g., `checked_sub(...).expect("capitalization cannot underflow")` at `accounts_db.rs:6108-6111`). This turns a potential undiagnosed underflow/wrap into either a controlled early error or a clear panic message that pinpoints the invariant violation, rather than an opaque arithmetic panic or silent data corruption in the snapshot archive stream.

### Proof of Concept
I could not construct a concrete, verified sequence of AccountsDb operations (clean/shrink/tombstone-carry-forward/mark-obsolete) that provably drives `storage.get_obsolete_bytes(snapshot_slot) > storage.accounts.len()` or `tombstone_offsets.len() * tombstone_stored_size > num_alive_bytes` in this codebase within the scope of this analysis. This would require deeper tracing of `mark_accounts_obsolete`, `batch_insert_tombstone_offsets`, and the shrink/clean interaction described in `account_storage_entry.rs:36-53`, which was not completed. This report should be treated as a code-pattern analog (unchecked subtraction of a derived "claim/obsolete amount" from a total) rather than a fully proven exploit, consistent with the analog-scan instructions when a concrete underflow trigger cannot be demonstrated with the available context.
