### Title
`ensure_match_transaction_info` skips state-checkpoint hash validation, allowing state-root divergence to pass replay/restore verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` fetched from a peer/archive. It checks status, gas used, write-set hash, and event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the Sparse-Merkle-Tree state root. This gap is explicitly acknowledged in the code itself.

### Finding Description [1](#0-0) 

The function computes and checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (hash of `self.write_set()`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but then returns `Ok(())` without validating `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` against anything derived from the locally recomputed state. The comment directly in the code states: [2](#0-1) 

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

`state_checkpoint_hash` is the field that binds a `TransactionInfo` (and hence the transaction accumulator / `LedgerInfo`) to the actual Sparse Merkle Tree root of the resulting global state — this is the exact proof-binding invariant called out in the "Proof And Storage Pivots": *"Accumulators, Jellyfish Merkle structures, versioned state views ... must preserve deterministic proof binding."* Skipping this check means the one place designed to catch a state-root mismatch between local execution and an externally-supplied, ledger-info-signed `TransactionInfo` silently accepts the mismatch as long as the write-set hash, events, gas and status happen to match.

Write-set hash matching does not imply state-root matching: `state_change_hash` is a hash of the transaction's own write set, independent of the base state it was applied to. Two different underlying JMT/SMT states (e.g., due to a bug in the state-view fed to the VM, or a corrupted/malicious archive that serves a different account state at an earlier version) can produce the same write set for a given transaction while yielding a different resulting state-checkpoint root. `ensure_match_transaction_info` cannot detect that divergence because it never inspects `state_checkpoint_hash` at all.

`ensure_match_transaction_info` is called from `execution/executor/src/chunk_executor/mod.rs` and `storage/db-tool/src/replay_on_archive.rs`, both of which are on the chunk-executor / replay-verify path used to validate transaction outputs against transaction infos obtained during state sync / archive replay (i.e., against untrusted/external data before it is trusted as matching the canonical ledger). I could not fully trace those two call sites in this session (tool budget exhausted) to confirm whether an independent, redundant state-root check exists elsewhere in the same call chain; that is the main residual uncertainty.

### Impact Explanation
If no other code path independently re-verifies `state_checkpoint_hash` at the same point, a node/tool going through chunk-executor or `replay_on_archive` verification could accept a chunk of transactions whose locally computed state root differs from the authenticated one signed into the `LedgerInfo`/accumulator, without raising an error. This is a hard-fork-class/replay-integrity issue: it undermines the guarantee that "committed state differs from the correct VM result" is always caught during replay or restore, which is explicitly in scope as a State-Integrity Gate impact ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

### Likelihood Explanation
This is not an attacker-triggered state mutation on live mainnet consensus (that path is protected by the normal VM/consensus agreement), but it is a real, low-effort-to-trigger gap in the verification tooling itself: any divergence between locally recomputed state and the authenticated checkpoint (bug-induced non-determinism, storage bit-rot, or a malicious archive/bootstrap peer in restore flows) will not be flagged by this function today, as the code's own TODO admits. Likelihood of the underlying divergence occurring is unknown/low, but the detection mechanism meant to catch it is confirmed broken by inspection, independent of any external hypothesis.

### Recommendation
Extend `ensure_match_transaction_info` to also verify the recomputed state checkpoint hash (when the local execution produces one, i.e., on checkpoint transactions) against `txn_info.state_checkpoint_hash()`, and similarly validate `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` when those are populated, before any downstream trading-native or replay-verify logic treats the comparison as authoritative.

### Proof of Concept
Not applicable as a live exploit — this is a verification-logic gap discovered by static review of `ensure_match_transaction_info`. The self-documented TODO comment in the file is the direct evidence: the function returns `Ok(())` for a `TransactionOutput`/`TransactionInfo` pair whose write set, events, gas, and status match but whose `state_checkpoint_hash` fields differ, since those fields are never read or compared in the function body.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
