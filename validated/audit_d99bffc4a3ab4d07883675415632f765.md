### Title
SPICE Pending Transaction Queue Under-Counts a `WithdrawFromGasKey` Nested Inside a `DelegateAction`, Allowing a Meta-Transaction Sender to Drain a Gas Key the Queue Still Treats as Funded - (File: `chain/client/src/pending_transaction_queue.rs`)

### Summary
Analogous to the 0x0DEX exploit — where an attacker manipulated pool-state parameters (forced balance via `selfdestruct`, crafted ring/withdrawal amounts) so the contract's internal accounting no longer matched real deposited value, letting it authorize withdrawals beyond what was actually escrowed — nearcore's SPICE `PendingTransactionQueue` computes a gas key's "available balance" from only the **top-level** actions of a submitted transaction. A `WithdrawFromGasKey` action nested inside a `Delegate`/`DelegateV2` action's inner action list is invisible to this accounting, so the queue's `paid_from_gas_key` commitment diverges from the gas key's real, in-flight balance. This is fixed by protocol feature `RejectWithdrawFromGasKeyInDelegate`, but that feature only activates at protocol version **87**, while `STABLE_PROTOCOL_VERSION`/base config in this tree is **86** — i.e., on the currently stable/deployed protocol version, the hole is open.

### Finding Description
`PendingTransactionQueue::check_pending` tracks per-gas-key pending withdrawal amounts by scanning `tx.transaction.actions()` and matching `Action::WithdrawFromGasKey`: [1](#0-0) 

This loop only iterates the transaction's *own* top-level actions. It does not recurse into a `Delegate`/`DelegateV2` action's inner `actions()` list. Consequently, if a meta-transaction (`DelegateAction`) is submitted whose inner actions include `WithdrawFromGasKey`, the queue's `session_gas_key_withdrawals`/`pending_gas_key_cost` tracking never sees it, and `paid_from_gas_key` remains understated: [2](#0-1) 

That `paid_from_gas_key` value is fed into `PendingConstraints`, which the runtime's ephemeral gas-key charging path (`verify_and_charge_gas_key_tx_ephemeral`) subtracts from the gas key's on-chain balance to compute `available_gas_key_balance`: [3](#0-2) 

Because the pending withdrawal inside the delegate was never counted, a second (or several) pending gas-key transaction can be admitted by the RPC/chunk-producer as if the gas key still held its full balance, when in fact a delegate-nested `WithdrawFromGasKey` is about to (or already did) drain it. The code comment in `version.rs` explicitly documents this root cause and the fix: [4](#0-3) 

The protocol feature that closes this hole, `RejectWithdrawFromGasKeyInDelegate`, activates only at protocol version 87: [5](#0-4) 

The existing regression test confirms the pre-fix behavior lets the nested withdrawal execute and drain the gas key, and that action-validation only starts rejecting it once the protocol version crosses into the fixed range: [6](#0-5) [7](#0-6) 

This is directly analogous to the 0x0DEX bug class: an attacker-controlled parameter/path (here, nesting `WithdrawFromGasKey` inside a `Delegate` action) bypasses the component responsible for keeping an internal accounting invariant (available gas-key balance) synchronized with real on-chain state, letting a value-moving operation be admitted against stale/incorrect accounting.

### Impact Explanation
An attacker who controls a gas key (their own account's gas key, or one they've been granted authority over via a relayer flow) can submit: (1) a meta-transaction/`DelegateAction` whose inner actions include `WithdrawFromGasKey` to drain the gas key's prepaid balance, and (2) concurrently, one or more ordinary gas-key transactions that the pending-transaction queue still admits believing the gas key is fully funded, because the nested withdrawal was invisible to `paid_from_gas_key` accounting. This can result in transactions being admitted into a chunk that the runtime later cannot actually satisfy from the (now-drained) gas key balance, or — depending on ordering/execution — successful double use of the same prepaid balance for both the withdrawal and a subsequent gas-key transaction's cost, i.e. unauthorized value movement / an accounting-integrity violation for the gas key's prepaid pot. Because gas key balances back real NEAR-token value transferable back to the account (`action_withdraw_from_gas_key` credits `account.amount()`), this is a token-accounting bypass reachable by a single meta-transaction sender, not merely a resource/DoS issue. This satisfies "concrete unauthorized value movement" / "invalid state transition acceptance" thresholds for Medium/High severity.

### Likelihood Explanation
The path is reachable by any unprivileged party who can submit a `DelegateAction` (meta-transaction, NEP-366/gas-keys feature) with a nested `WithdrawFromGasKey`, and simultaneously submit ordinary gas-key transactions through the standard RPC submission path — no validator or node compromise required, purely client-observable transaction crafting. The bug is explicitly acknowledged and root-caused by the nearcore team in the source comment itself, and a dedicated regression test exists that reproduces exactly this drain scenario pre-fix. The only mitigating factor is that the fix (`RejectWithdrawFromGasKeyInDelegate`) is scheduled/gated at protocol version 87, and this codebase's `STABLE_PROTOCOL_VERSION`/documented baseline is 86 — meaning the vulnerable window exists on the currently-stable protocol version until the v87 upgrade activates.

### Recommendation
Backport/expedite activation of `RejectWithdrawFromGasKeyInDelegate` (or an equivalent fix) to the currently stable protocol version rather than leaving it gated at v87. Independently of the protocol-version gate, harden `PendingTransactionQueue::check_pending` to recursively scan `Delegate`/`DelegateV2` inner actions (mirroring how `total_deposit`/`total_prepaid_gas` already recurse into `delegate_inner_action`) so gas-key withdrawal accounting cannot be bypassed by nesting inside a delegate action, independent of when the protocol-level rejection activates.

### Proof of Concept
The existing test demonstrates the exploit path end-to-end pre-fix: [8](#0-7) 
1. Create a gas key and fund it (`AddKey` + `TransferToGasKey`).
2. Craft a `DelegateAction` whose inner action is `WithdrawFromGasKey` for `WITHDRAW_AMOUNT`, signed by the gas key, sent via a relayer.
3. Submit it through the normal RPC/pending-transaction-queue path — pre-fix, `execute_tx` succeeds and the gas key balance decreases by `WITHDRAW_AMOUNT`, confirming the nested withdrawal was neither blocked nor accounted for by the queue's gas-key balance tracking, exactly matching the documented root cause in `version.rs:461-465`.

#[test]
fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
    init_test_logger();

    if !ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(PROTOCOL_VERSION) {
        return;
    }

    let new_protocol = ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version();
    let old_protocol = new_protocol - 1;
    assert!(
        old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION,
        "no supported protocol version still admits a delegated WithdrawFromGasKey, so there is \
         nothing left to test here - remove this test"
    );

    let sender = create_account_id("alice");
    let relayer = create_account_id("relayer");
    let epoch_length = 10;

    // Boundary "mm": "alice" lands on the first shard, "relayer" on the second,
    // so the delegate receipt crosses a shard on its way to the sender.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(old_protocol)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(new_protocol))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .add_user_account(&sender, Balance::from_near(1_000))
        .add_user_account(&relayer, Balance::from_near(1_000))
        .build();

    let gas_key: Signer =
        InMemorySigner::from_seed(sender.clone(), KeyType::ED25519, "gas_key").into();
    let add_key_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::AddKey(Box::new(AddKeyAction {
            public_key: gas_key.public_key(),
            access_key: AccessKey::gas_key_full_access(1),
        }))],
    );
    env.rpc_runner().run_tx(add_key_tx, Duration::seconds(10));

    let fund_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: gas_key.public_key(),
            deposit: Balance::from_near(10),
        }))],
    );
    env.rpc_runner().run_tx(fund_tx, Duration::seconds(10));

    // Before the upgrade the nested withdrawal is admitted and moves balance out
    // of the gas key, which is the hole this rule closes.
    assert_eq!(
        env.rpc_node().protocol_version_at_head(),
        old_protocol,
        "expected to start pre-upgrade"
    );
    let (_, balance_before) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let outcome = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect("delegated withdrawal admitted pre-upgrade");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::SuccessValue(_),
        "pre-upgrade delegated withdrawal should execute",
    );
    let (_, balance_after) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    assert_eq!(
        balance_after,
        balance_before.checked_sub(WITHDRAW_AMOUNT).unwrap(),
        "the nested withdrawal should have drained the gas key",
    );
