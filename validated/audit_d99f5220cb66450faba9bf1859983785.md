## Finding

I identified a state-integrity gap in the Aptos executor's transaction-output verification routine, independent of the original Solidity report but matching the same bug class: a value that should participate in a solvency/consistency check is silently excluded from the comparison, allowing a state that should be rejected to be accepted as valid.

### Title
Replay-verification skips state/hot-state/position checkpoint hash comparison, allowing a divergent state root to pass as valid - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (db backup `replay_on_archive`, `replay_verify`, the CLI debugger, and the chunk executor's `VerifyExecutionMode`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` that is bound to the ledger accumulator/`LedgerInfo`. It checks status, gas, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` compares four fields between the locally produced `TransactionOutput` and the trusted, previously-committed `TransactionInfo`: execution status, gas used, write-set hash (`state_change_hash`), and event root hash. The function contains its own acknowledgement that it omits the checkpoint hash fields: [2](#0-1) 

This function is invoked from:
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, used by `VerifyExecutionMode` when replaying a chunk during backup/replay-verify to confirm re-executed outputs match trusted `TransactionInfo`s.
- `aptos-move/cli/src/commands.rs`, the CLI's transaction replay/debug command. [3](#0-2) [4](#0-3) 

`TransactionInfoV1` (used once `TRANSACTION_INFO_V1` is enabled) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (via the repurposed reserved field) `position_state_checkpoint_hash`, all of which are part of the object that is hashed into the transaction accumulator and thus authenticated by validator signatures on the `LedgerInfo`. [5](#0-4) 

Because `ensure_match_transaction_info` never re-derives and compares these checkpoint hashes against the locally computed state, a locally re-executed chunk whose state/hot-state/position-state root diverges from the authenticated root (due to a bug, non-determinism, or a malicious/compromised historical state) will still pass verification as long as status, gas, write-set hash, and event root happen to match. The comment ties this directly to the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag, which is defined and wired into `BlockExecutorConfigFromOnchain` but not yet in the default feature set. [6](#0-5) [7](#0-6) 

### Impact Explanation
This falls under the "proof-integrity" and "replay" categories called out in the task: replay verification (`db-tool`'s `replay_on_archive`/`replay_verify`, the CLI debugger) is one of the primary mechanisms for detecting that historical/archived data — including data served by full/archive nodes to light clients and other consumers — has not diverged from the consensus-committed state. With this gap, a state root divergence in the tracked checkpoint trees (state, hot-state, and eventually native-position trees under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) would not be flagged by `verify_execution`/`ensure_match_transaction_info`, so tooling built on this invariant would falsely report a clean, non-divergent replay even though the local ledger state differs from the authenticated one. That is precisely the "state that differs from the correct VM result... accepted as valid" pattern the task calls out, manifesting during the replay/verification path rather than during the primary consensus-commit path (where root binding is separately enforced via `LedgerInfo.executed_state_id`).

### Likelihood Explanation
The gap is unconditional in current code — it doesn't require the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` flag to be relevant, since `state_checkpoint_hash`/`hot_state_checkpoint_hash` already exist on `TransactionInfoV0`/`V1` today and are also skipped. Any divergence in state-checkpoint computation (e.g., a bug in `DoStateCheckpoint`, hot-state promotion logic, or future position-tree logic) that still yields matching write-set/event hashes and status/gas would be silently accepted by replay-verify. The likelihood of an actual on-chain execution divergence occurring is separate from this bug; this finding is about the verifier's inability to catch such a divergence when it does occur, which is a real, currently-present gap in the shipped comparator function, not a hypothetical future state.

### Recommendation
Add locally-recomputed checkpoint-hash comparisons (state, hot-state, and position-state, where applicable/known) to `ensure_match_transaction_info`, gated on which `TransactionInfo` variant/feature set is active, before allowing `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any reliance on `TransactionInfoV1`'s checkpoint fields for verification) to be treated as authoritative. At minimum, when the checkpoint hash is known/derivable from the state computed during replay, it should be compared and mismatches should fail verification exactly as the write-set/event checks do.

### Proof of Concept
Not executable as a standalone PoC since it is a verification-omission bug rather than a state-corrupting computation bug: the flaw is structural — `ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2204` simply never reads `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` nor recomputes/compares them against any locally derived value, as evidenced by the four explicit `ensure!` checks present (status, gas, write-set hash, event root hash) and the total absence of any corresponding check for the checkpoint hash fields, confirmed by the developers' own inline TODO comment describing exactly this gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
