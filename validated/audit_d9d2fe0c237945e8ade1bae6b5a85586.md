### Title
First-ever Nakamoto tenure-change's `previous_tenure_end` is not validated against the canonical epoch2 chain tip - ([File: stackslib/src/chainstate/nakamoto/tenure.rs])

### Summary
`NakamotoChainState::check_first_nakamoto_tenure_change` (invoked from `check_nakamoto_tenure` when `get_ongoing_tenure` returns `None`, i.e. for the very first Nakamoto block) only verifies that `previous_tenure_end` resolves to *some* locally-stored epoch2 header whose `consensus_hash` matches `prev_tenure_consensus_hash`, and that `previous_tenure_blocks == 1`. It never checks that this epoch2 header is the canonical/heaviest epoch2 tip. The signer-side heuristic in `postblock_proposal.rs`/`chainstate/v1.rs` that could catch this is also structurally unable to, for reasons explained below.

### Finding Description
The claimed equality is: `tenure_payload.previous_tenure_end == <canonical epoch2 tip at the Nakamoto activation boundary>`. What is actually checked in `check_first_nakamoto_tenure_change` (`stackslib/src/chainstate/nakamoto/tenure.rs:553-612`) is only:
1. `tenure_payload.cause.expects_sortition()`
2. `Self::get_block_header(headers_conn, &tenure_payload.previous_tenure_end)` succeeds — this is a raw lookup by `StacksBlockId` (i.e. `hash(consensus_hash, block_hash)`) against whatever this node happens to have stored, with **no canonicality filter**.
3. `previous_tenure_blocks == 1`
4. `prev_tenure_consensus_hash == parent_header.consensus_hash`
5. `parent_header` is an epoch2 header.

None of these confirm that `parent_header` is the epoch2 chain's actual canonical tip (the one selected by epoch2's heaviest-work fork-choice rule, exposed via `NakamotoChainState::get_canonical_block_header`). The caller, `check_nakamoto_tenure` (`tenure.rs:653-770`), only calls `check_valid_consensus_hash` (canonical-burnchain-fork check) for `tenure_consensus_hash` and `burn_view_consensus_hash` — never for `prev_tenure_consensus_hash` in the first-tenure branch.

Downstream, `NakamotoChainState::append_block` (`stackslib/src/chainstate/nakamoto/mod.rs:5026-5114`) and `process_next_nakamoto_block` (`mod.rs:2355-2392`) resolve the parent purely by `get_block_header(..., &block.header.parent_block_id)` — an unconditional DB lookup, not a canonical-tip lookup — and only assert self-consistency (`parent_block_id` matches, height+1 matches). There is no assertion anywhere in this path that the referenced epoch2 block is `NakamotoChainState::get_canonical_block_header`'s result at the moment the Nakamoto epoch begins.

The signer-side heuristic `check_block_has_valid_parent` (`stackslib/src/net/api/postblock_proposal.rs:474-524`, explicitly annotated "DO NOT CALL FROM CONSENSUS CODE") is the only other candidate guard. For a tenure-start block it calls `check_block_builds_on_highest_block_in_tenure` with `tenure_id = parent_header.consensus_hash` — i.e. the epoch2 parent's *own* consensus hash. Since exactly one epoch2 block exists per consensus hash/sortition, `find_highest_known_block_header_in_tenure` trivially returns that very same block, so the height-equality check always passes regardless of which epoch2 fork it belongs to. It is a no-op for this specific case. Additionally, the signer's `check_proposal` (`stacks-signer/src/chainstate/v1.rs:136-203`) gates its parent-tenure-choice validation on `signer_db.get_canonical_tip()` returning `Some(tip)`; for the very first Nakamoto block there is no prior Nakamoto tip in `signer_db`, so this entire validation branch is skipped.

Exploit flow: an attacker (single miner slot, minority stake) who at some point produced a competing epoch2 block that legitimately won its own sortition (and is therefore validly stored by any node that once tracked that fork) can, upon eventually winning a Nakamoto-era sortition, submit a `TenureChangePayload` with `previous_tenure_end`/`prev_tenure_consensus_hash` pointing at that losing epoch2 tip instead of the true canonical epoch2 tip. Neither the node-side consensus checks nor the signer-side heuristics reject this, so if a signer supermajority (composed of honest signers unaware of this gap) has the referenced header locally, they would sign it.

### Impact Explanation
If accepted, the Nakamoto chain's genesis block would be built atop a non-canonical epoch2 ancestor. Any node that never stored that specific losing epoch2 header (most honest nodes that never observed the losing fork) could never process this block (`process_next_nakamoto_block` requires the parent header to be present), causing a permanent inability to converge — a deep, irreconcilable state-root/tip divergence between nodes that did and did not retain the abandoned epoch2 fork data. This matches the Critical category ("a chain split or deep fork... an invalid block accepted... network-wide").

### Likelihood Explanation
Exploitability depends on a strict precondition that could not be fully confirmed from the available code: whether `get_canonical_block_header`/epoch2 fork-choice truly permits two distinct, both-sortition-won epoch2 anchored blocks to coexist near the Nakamoto activation boundary (i.e., a genuine Stacks-level fork without needing a Bitcoin-level reorg), and whether the signer supermajority would realistically retain and serve the losing fork's header rather than have pruned/never fetched it. I was not able to verify from the indexed code whether epoch2's `validate_anchored_block_burnchain`/fork-choice logic can produce two competing, independently-sortition-won tips at the exact boundary height without a burnchain reorg, which is required for the "microblock-fork tip" precondition in the prompt to be realizable by an unprivileged single-miner attacker. This uncertainty means the likelihood of this being practically triggerable (rather than merely a latent gap in the validation code) is not conclusively established from the retrieved context.

### Recommendation
In `check_first_nakamoto_tenure_change` (and/or `check_nakamoto_tenure`'s first-tenure branch), additionally require that `parent_header`/`tenure_payload.previous_tenure_end` equals the actual canonical epoch2 chain tip as computed by `NakamotoChainState::get_canonical_block_header` at the sortition immediately preceding the Nakamoto-activation sortition, not merely any locally-stored epoch2 header sharing the claimed consensus hash. Likewise, extend the signer's `check_block_has_valid_parent`/`check_proposal` logic to explicitly validate the epoch2-to-Nakamoto boundary case against the node's canonical epoch2 tip rather than trivially matching the parent's own tenure.

### Proof of Concept
Rust integration test plan (two-node/two-fork harness), modeled on `stackslib/src/chainstate/nakamoto/coordinator/tests.rs`:
1. Build a `TestPeer` and mine epoch2 blocks up to just before the Nakamoto activation height, producing two competing epoch2 chain tips `A` (canonical, higher total work) and `B` (non-canonical, lower total work) both won by legitimate sortitions and both stored in the node's headers table.
2. Assert `NakamotoChainState::get_canonical_block_header(chainstate.db(), sortdb).unwrap().unwrap().index_block_hash() == A.index_block_hash()` (i.e., `A != B` and `A` is canonical).
3. Construct the first-ever `TenureChangePayload` with `previous_tenure_end = B.index_block_hash()`, `prev_tenure_consensus_hash = B.consensus_hash`, `previous_tenure_blocks = 1`, `cause = BlockFound`.
4. Call `NakamotoChainState::check_first_nakamoto_tenure_change(chainstate.db(), &tenure_change_payload)` and observe it returns `Ok(Some(..))` (the bug: it should return `Ok(None)` because `B != A`).
5. Build and attempt to `append_block`/`process_next_nakamoto_block` a Nakamoto block whose `parent_block_id == B.index_block_hash()`; assert whether it is accepted (documenting the equality `previous_tenure_end == A.index_block_hash()` is violated on acceptance) versus a second, honest node that never stored `B` and therefore stalls forever on this block, demonstrating the tip divergence between the two nodes.
