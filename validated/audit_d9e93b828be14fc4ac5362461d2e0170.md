## Title
Session storage errors leak raw exception details (potentially including database connection/credential info) to unauthenticated HTTP responses - (File: `packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts`)

### Summary
`shopify-app-express`'s authenticated-session middleware forwards raw `error.message` values from the pluggable `SessionStorage` backend (Postgres/MySQL/MongoDB/Redis adapters) directly into the HTTP response body whenever `loadSession()` throws, or whenever `getCurrentId()` throws an error that isn't a known `InvalidJwtError`. This mirrors the exact CWE-209/CWE-532 bug class described in the Curio advisory: verbose driver/database errors are surfaced verbatim to HTTP clients instead of being sanitized before sending.

### Finding Description
In `validateWithAuthCodeFlow`, when the configured `SessionStorage` throws during `loadSession(sessionId)`, the raw driver error message is sent as the response body: [1](#0-0) 

Similarly, `handleSessionError`, invoked when `api.session.getCurrentId()` throws any error other than `InvalidJwtError`, sends `error.message` straight to the client for both 401 and the default 500 branch: [2](#0-1) 

This is confirmed by the package's own test, which asserts the storage error text is echoed verbatim in the response: [3](#0-2) 

The officially-shipped `SessionStorage` adapters construct their DB connections from URLs that embed plaintext credentials (`postgres://username:password@host/database`, `mysql://username:password@host/database`, `mongodb://username:password@host/`, `redis://username:password@host/database`), exactly the pattern flagged in the Curio report: [4](#0-3) [5](#0-4) 

Any exception surfaced by the underlying `pg`/`mysql2`/`mongodb`/`redis` client (connection errors, auth failures, timeouts, driver-level parse errors) is not sanitized anywhere in this middleware chain before being written to `res.send()`, so any information the driver embeds in its `Error.message` (hostnames, ports, usernames, and in some drivers/misconfigurations, connection-string fragments) is disclosed to the caller.

### Impact Explanation
An app request that reaches `validateAuthenticatedSession` (every route protected by `shopify-app-express`'s admin auth middleware) and causes the session-storage layer to throw — due to a transient DB outage, connection pool exhaustion, network blip, or a malformed session id/shop value causing a driver-level error — will return the raw internal error text to the HTTP client instead of a generic message. Depending on the driver and error path, this can disclose internal database hostnames, ports, usernames, and other infrastructure fingerprinting information that aids an attacker in targeting the app's control-plane database, directly analogous to the credential exposure described in the Curio advisory.

### Likelihood Explanation
The code path is reached during ordinary, low-privilege usage: any authenticated (or even just cookie/JWT-bearing) request into an Express-based Shopify app that hits a session-storage hiccup will trip this branch — no special exploitation technique beyond triggering (or waiting for) a storage error is required, and the test suite documents the exact verbatim pass-through behavior as intended functionality rather than an anomaly.

### Recommendation
- Never `res.send(error.message)`/`res.send(error)` for session-storage or session-id-resolution errors. Log the full error server-side (`config.logger.error`) and return a generic message (e.g., `'Internal Server Error'`) to the client, mirroring the approach already used elsewhere in the same file for `performTokenExchange`'s catch-all handler (`res.status(500).send('Internal Server Error')`), see `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts:163-164`.
- Apply the same sanitization to `handleSessionError`'s default branch.
- Consider masking credentials in adapter-level connection configuration (e.g., set password via a separate config field instead of embedding it in the URL passed to the driver) so it can never appear in thrown errors, consistent with the Curio remediation's connection-string masking approach.

### Proof of Concept
1. Configure a `shopify-app-express` app with any RDBMS-backed `SessionStorage` adapter (e.g., `PostgreSQLSessionStorage`).
2. Send an authenticated request (valid session cookie or bearer JWT) to any route wrapped by `shopify.validateAuthenticatedSession()`.
3. Cause `sessionStorage.loadSession()` to throw (e.g., temporarily block DB connectivity, exhaust the connection pool, or supply a session id causing a driver-level error).
4. Observe the HTTP response body contains the raw driver `Error.message` (as reproduced by the existing test `'returns a 500 if the storage throws an error'`, which asserts `response.error.text === 'Storage error'`), which in real deployments could include internal database host/user details or driver connection diagnostics.

function handleSessionError(_req: Request, res: Response, error: Error) {
  switch (true) {
    case error instanceof InvalidJwtError:
      res.status(401);
      res.send(error.message);
      break;
    default:
      res.status(500);
      res.send(error.message);
      break;
  }
}
