### Title
Protocol treasury account self-deletion causes a permanent, protocol-wide chain halt at every subsequent epoch boundary - (File: `runtime/runtime/src/lib.rs`)

### Summary
The reported bug is a "push-payment" denial of service: a fixed, protocol-level fee recipient (`creator`/`beneficiary`/`vault`) that becomes unusable (blacklisted/self-destructing) blocks all future execution because the code unconditionally assumes the recipient can always receive funds and has no fallback. `nearcore` has a structurally identical pattern in `update_validator_accounts`: the genesis-configured `protocol_treasury_account` is treated as an account that must always exist and be able to receive its epoch reward. Unlike every other token-flow in the runtime (refunds, contract rewards), which explicitly tolerate a missing/gone recipient by burning the amount, the treasury-reward credit path has no such fallback — it hard-fails with a fatal `StorageInconsistentState` error if the account is gone.

### Finding Description
At every epoch boundary, `Runtime::apply` builds a `ValidatorAccountsUpdate` containing `protocol_treasury_account_id` (set from `self.genesis_config.protocol_treasury_account`) [1](#0-0) . This is passed into `update_validator_accounts`, which for the treasury account does:

```rust
if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
    if !validator_accounts_update.stake_info.contains_key(account_id) {
        let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Protocol treasury account {} is not found",
                account_id
            ))
        })?;
        ...
``` [2](#0-1) 

If the treasury account does not exist, this returns a fatal `StorageError::StorageInconsistentState`, which is exactly the class of error the codebase documents as unrecoverable/state-corruption-level ("FATAL: staking invariant does not hold...") elsewhere in the same function [3](#0-2) .

Crucially, the protocol treasury account is an ordinary account, not a specially protected system account. `check_actor_permissions` allows `DeleteAccount` whenever `actor_id == account_id` and the account has zero locked stake — with no special-case exemption for the treasury account:
```rust
Action::DeleteAccount(_) => {
    if actor_id != account_id { return Err(ActionErrorKind::ActorNoPermission{...}.into()); }
    let account = account.as_ref().unwrap();
    if !account.locked().is_zero() {
        return Err(ActionErrorKind::DeleteAccountStaking{...}.into());
    }
}
``` [4](#0-3) 

So a single, ordinary, self-signed `DeleteAccount` transaction from the treasury account's own key (the same unprivileged capability every account holder has) permanently removes that account from state. On the very next epoch-boundary chunk, every honest validator, applying the identical deterministic state transition, will independently hit the same `Ok_or_else` failure in `update_validator_accounts` — this is not a divergence bug but a uniform, protocol-wide fatal error triggered by one submitted transaction.

This mirrors the reported bug class precisely: a fixed recipient address in a mandatory, unconditional "push" payment has no failure-tolerant path, so once that recipient becomes unusable, every future run of the code path (here: every future epoch transition, i.e. chunk application) fails.

### Impact Explanation
Unlike gas/deposit refunds and contract-reward crediting elsewhere in the runtime — which explicitly special-case a missing recipient (burn the deposit refund on failure; drop the contract reward and let it accrue to validators instead) documented at [5](#0-4)  and [6](#0-5)  — the protocol-treasury reward credit has no equivalent fallback. A fatal error here is returned from `Runtime::apply`, the top-level per-chunk state-transition function [7](#0-6) . Because chunk application must be deterministic and every honest node runs it, this is a transaction-triggered halt: the chain cannot progress past the next epoch boundary for the shard holding the treasury account, since every node's runtime will hit the identical fatal condition. This satisfies the "transaction-triggered halt" acceptance bar — a single submitted transaction (self-deletion of one's own account) permanently freezes chain progress, which also effectively freezes all funds network-wide.

### Likelihood Explanation
The deleting party is the entity that legitimately controls the treasury account's access key — the same unprivileged capability any account owner has over their own account (self-`DeleteAccount`, zero locked stake required). No elevated privilege, leaked key, or malicious validator/node behavior is needed; it is a standard, always-available action (`DeleteAccount`) applied to a specific, protocol-significant account ID. The likelihood of triggering depends only on whether the operator of that specific account ever issues (accidentally or otherwise) a self-delete transaction, but the code path itself provides zero defense-in-depth against it, whereas comparable token-flow paths in the same codebase (refunds, contract rewards) do defend against a missing recipient.

### Recommendation
In `update_validator_accounts` (`runtime/runtime/src/lib.rs:1807-1834`), do not treat a missing `protocol_treasury_account_id` account as a fatal `StorageInconsistentState`. Follow the same pattern already used for refunds/contract rewards elsewhere in the runtime: if the treasury account does not exist, skip crediting it (optionally burning or redirecting the reward, e.g. adding it to `tx_burnt_amount`/validator pool) instead of returning an unrecoverable error. This removes the single point of failure and brings this code path in line with the rest of the runtime's "recipient may be gone" handling philosophy.

### Proof of Concept
1. On any nearcore-based chain, identify/control the account referenced by `genesis_config.protocol_treasury_account` (e.g. via testnet/local chain configuration where this is a normal, unstaked account).
2. Submit a normal `DeleteAccount` transaction signed by that account's own key, with `locked == 0` (satisfies `check_actor_permissions`), naming any valid `beneficiary_id`.
3. Wait for the next epoch boundary. `EpochManager`/`process_state_update` will populate `ValidatorAccountsUpdate.protocol_treasury_account_id` for the chunk producing shard [1](#0-0) .
4. `Runtime::apply` → `update_validator_accounts` calls `get_account(state_update, account_id)?.ok_or_else(...)` on the now-deleted account and returns `Err(StorageError::StorageInconsistentState(...))` [8](#0-7) .
5. Every validator applying this chunk hits the identical fatal error deterministically, halting chain progress at that epoch boundary.
