Confirmed: the sequencer's deposit mempool removal is unconditional on the *whole fetched batch*, not on which individual deposits actually succeeded when applied as system transactions.

### Title
Sequencer purges all fetched deposits from `DepositDataMempool` even when some fail during system-transaction execution, permanently forfeiting valid Bitcoin deposits - (File: `crates/sequencer/src/runner.rs`)

### Summary
`DepositDataMempool::remove_deposits()` is called with the entire batch of deposits that was fetched for the block (`deposit_data`), not with the subset that was actually applied successfully as `BridgeDeposit` system transactions. Any deposit whose system transaction failed to apply is silently dropped from the mempool forever, exactly analogous to the reported Beanstalk issue where a shared "processed" marker (`lastStem`) was advanced for state beyond what was actually settled, forfeiting the unprocessed portion.

### Finding Description
In `produce_l2_block_inner`, the sequencer fetches a batch of pending deposits from the mempool without removing them: [1](#0-0) 

These are later turned into `BridgeDeposit` system events and executed one by one in `process_sys_txs`. When a deposit's system transaction fails on-chain (`EvmSystemTransactionNotSuccessful`), the working set is reverted and the loop simply `continue`s to the next event — the deposit is *not* included in the produced block: [2](#0-1) 

However, after the block is finalized, the sequencer removes deposits from the mempool using the original, unfiltered `deposit_data` list — i.e., every deposit that was *fetched*, not every deposit that was *actually applied*: [3](#0-2) 

`DepositDataMempool::remove_deposits` has no notion of "success" — it simply strips any matching txid out of `accepted_deposit_txs` and `pending_deposits`, and once removed, the deposit can never be re-added under the same txid unless externally resubmitted (which requires knowledge/action outside the sequencer's control, since the RPC submission is the only path that calls `add_deposit_tx`): [4](#0-3) [5](#0-4) 

This breaks the binding "every valid Bitcoin move-transaction deposit accepted into the mempool eventually results in cBTC credited on L2 (or remains retryable)." Instead, a deposit that reverts on-chain for a reason other than "already spent" (for example, a transient failure such as insufficient EVM gas headroom, `verifySigInTx` failing due to a witness/proof mismatch that is later correct, or any other revert path inside `Bridge.deposit()` besides the recipient-call failure, which is caught and redirected to `failedDepositVault` rather than reverting) is permanently evicted from the mempool without the underlying Bitcoin deposit ever being credited.

### Impact Explanation
This crosses the custody boundary: a real Bitcoin-side deposit transaction exists (has been included and proven in the mempool), but the corresponding cBTC credit on Citrea is never issued because the pending record is discarded on the very first failed attempt. This is a "Bitcoin deposit that actually happened" not matched by a corresponding cBTC credit, causing funds to become permanently unrecoverable via the deposit mempool path (Critical: funds permanently frozen).

### Likelihood Explanation
The revert path is reachable any time `Bridge.deposit()` reverts for a reason other than the guarded recipient-call failure — this can occur for ordinary, non-malicious reasons (e.g., a signature/proof edge case, gas exhaustion inside the system-transaction budget, or reentry ordering issues), making this a systemic reliability/correctness bug rather than a contrived edge case, since it will fire on the very first failed deposit application and requires no attacker action.

### Recommendation
Only remove the deposits that were actually applied (i.e., not reverted) from the mempool. `process_sys_txs` should track and return which `BridgeDeposit` events succeeded (it already has this information via the `is_deposit` and revert branch at `crates/sequencer/src/runner.rs:1653-1697`), and `produce_l2_block_inner` should call `remove_deposits` only with that successfully-applied subset instead of the full `deposit_data` batch fetched at `crates/sequencer/src/runner.rs:516-520`.

### Proof of Concept
1. Submit a valid Bitcoin deposit's move-transaction data to the sequencer's deposit RPC so it is accepted into `DepositDataMempool` via `add_deposit_tx`.
2. Have block production fetch this deposit (`fetch_deposits`) and attempt to apply it as a `BridgeDeposit` system transaction in `process_sys_txs`.
3. Trigger a revert of `Bridge.deposit()` for any reason other than the recipient-call failure (e.g. a proof/witness edge case causing `verifySigInTx` or `validateAndCheckInclusion` to fail) — `process_sys_txs` reverts the working set and skips inclusion of that event (`crates/sequencer/src/runner.rs:1678-1697`).
4. Observe that after block production, `remove_deposits(&deposit_data)` is still called with the original, full fetched list at `crates/sequencer/src/runner.rs:636-643`, evicting the failed deposit's txid from `pending_deposits`/`accepted_deposit_txs`.
5. The deposit is now gone from the mempool; unless the exact same raw payload is resubmitted externally, the Bitcoin depositor's cBTC is never credited, even though their Bitcoin-side deposit transaction is real and irreversible.

```rust
    /// Removes specific deposits from the mempool after they have been successfully included in a block
    ///
    /// # Arguments
    /// * `deposits_to_remove` - The deposits that were successfully included
    ///
    /// # Returns
    /// The number of deposits actually removed
    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
```

```rust
    /// Adds a new deposit transaction to the mempool
    ///
    /// # Arguments
    /// * `req` - Raw deposit transaction data to be added
    ///
    /// # Returns
    /// `true` if the deposit was added, `false` if it was already pending
    #[instrument(level = "trace", skip_all, ret)]
    pub fn add_deposit_tx(&mut self, req: Deposit) -> anyhow::Result<bool> {
        let txid = Self::calc_tx_id(&req)?;

        debug!("Adding deposit with tx: {}", hex::encode(txid));

        // Check if deposit is already pending
        if !self.pending_deposits.insert(txid.to_vec()) {
            tracing::debug!("Deposit already pending in mempool");
            return Ok(false);
        }

        self.accepted_deposit_txs.push_back(req);
        SM.deposit_data_mempool_txs_inc.increment(1);
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        Ok(true)
    }
```
