## Analog Found

### Title
Permanent freezing of bridged user funds when `IsCEA` inbound deposit fails — no revert outbound is ever created - ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go], [File: x/uexecutor/keeper/execute_inbound_gas_and_payload.go])

### Summary
The Push Chain analog of the Juicebox NFT-delegate bug is in the universal execution "isCEA" (custom execution address) deposit flow. Just as the NFT delegate silently `return`s without minting when the optional `prices` conversion path is unset, Push Chain's `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` silently `return nil` without creating any `INBOUND_REVERT` outbound when a deposit fails on the `IsCEA` branch — even though the underlying source-chain funds were already validated and voted-in by honest validators as a real inbound.

### Finding Description
Both execution functions explicitly special-case the `IsCEA` branch to skip revert creation: [1](#0-0) 

and [2](#0-1) 

In these branches, `execErr` can be set (e.g. `"recipient must be a valid hex address when isCEA is true"`, `"failed to verify UEA: %w"`, `"depositPRC20 failed: %w"`, `"depositAutoSwap failed: %w"`), but `shouldRevert` is never set to `true`. Control then falls to the shared failure-handling block: [3](#0-2) 

Since `shouldRevert` is `false`, `buildRevertOutbound` is never invoked, no `INBOUND_REVERT` `OutboundTx` is attached to the `UniversalTx`, and the function returns `nil`. The `UniversalTx` is left permanently in a `FAILED` PCTx state with no compensating mint and no revert path back to the source chain. This mirrors the NFT-delegate pattern exactly: an optional/edge condition (`IsCEA`) causes an early, silent `return` that skips the "make the user whole" step, even though the inbound event itself (the real, quorum-verified deposit on the source chain) is legitimate and was already accepted by honest validators via `MsgVoteInbound` ballot finalization.

The only other fund-recovery mechanism in the module, `AttachRescueOutboundFromReceipt`, operates on rescue events emitted by a successfully executed `executeUniversalTx` receipt — it does not apply here because no PRC20 was ever minted/deposited in these failure branches: [4](#0-3) 

There is no other retry/admin path found in `x/uexecutor` that revisits a `FAILED` PCTx from an `IsCEA` inbound to reattempt deposit or issue a revert.

### Impact Explanation
A user (or a relayer acting on a user's real deposit) who bridges funds via a payment/gateway path that is voted in as `IsCEA=true` loses their bridged asset permanently if any of the following occur on the Push Chain side: the specified recipient string isn't `0x`-prefixed, the `CallFactoryGetOriginForUEA` EVM call errors transiently, or the PRC20 deposit/auto-swap EVM call fails for any reason (e.g., gas estimation edge case, contract-level revert, sequencing issue). In all these cases the already-validated inbound (funds already escrowed/burned on the source chain per the honest-validator ballot) results in: no PRC20 minted on Push Chain, and no `INBOUND_REVERT` outbound to return the funds on the source chain. This is a permanent freezing/loss of user funds triggered purely by the deposit's execution outcome — not by any malicious validator, peer, or admin behavior.

### Likelihood Explanation
This does not require any privileged actor. Any depositor who sets `IsCEA=true` for their inbound (a normal, user-reachable code path) with a recipient value that fails validation, or whose deposit call reverts for a legitimate reason (e.g. destination PRC20 contract issue, temporary EVM state condition, or the recipient/UEA factory call erroring), triggers the silent-failure path. Given the deliberate `// isCEA failures never create an INBOUND_REVERT outbound.` design comment in both files, this is a systematic, reproducible gap rather than a rare race condition.

### Recommendation
Do not blanket-exempt the `IsCEA` path from revert creation. At minimum, when `execErr != nil` in the `IsCEA` branch and no deposit has actually succeeded (no funds moved), set `shouldRevert = true` and build a revert outbound so the user's already-verified source-chain funds are returned. If certain `IsCEA` sub-cases are intentionally non-refundable (e.g., ambiguous recipient with no clear return address), that decision should be scoped narrowly and documented with an explicit fallback (e.g., default `FundRecipient` back to `inbound.Sender`) rather than skipping revert creation for the entire `IsCEA` failure surface.

### Proof of Concept
1. A depositor sends funds on a supported source chain, having the gateway construct an `Inbound` with `IsCEA = true` and `Recipient` set to a value that does not start with `"0x"` (or any condition causing `CallFactoryGetOriginForUEA`/`depositPRC20`/`gasAndPayloadDepositAutoSwap` to return an error).
2. Honest validators vote and the inbound reaches quorum via `MsgVoteInbound`, creating the `UniversalTx`.
3. `ExecuteInboundFundsAndPayload` (or `ExecuteInboundGasAndPayload`) enters the `IsCEA` branch, sets `execErr`, but never sets `shouldRevert`.
4. The failure-handling block at [3](#0-2)  skips `buildRevertOutbound` because `shouldRevert == false`, and returns `nil`.
5. The `UniversalTx` remains with a `FAILED` PCTx entry and no `OutboundTx` of type `INBOUND_REVERT`, permanently stranding the user's bridged funds with no mint and no path back to the source chain.
