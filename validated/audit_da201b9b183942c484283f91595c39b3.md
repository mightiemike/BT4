### Title
Attached deposit on `rlp_execute` is permanently stuck when the emulated transaction resolves to `SelfBaseTokenTransfer` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `rlp_execute` entry point of the NEAR Wallet Contract is `#[payable]`, so any predecessor (relayer or arbitrary caller) can attach a NEAR deposit to it. That deposit is tracked as `CallerDeposit` so it can be refunded if the downstream cross-contract action fails. However, when the wrapped Ethereum transaction is classified as `EthEmulationKind::SelfBaseTokenTransfer`, the contract skips creating any cross-contract promise and calls `rlp_execute_callback` directly. That callback's "no promise results" branch (`n == 0`) unconditionally returns success and never inspects or refunds `caller_deposit`, so the attached deposit is silently absorbed by the wallet contract with no code path to return it.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the deposit attached to the outer NEAR transaction whenever the predecessor differs from the wallet's own account id: [1](#0-0) [2](#0-1) 

For most transaction kinds (`FunctionCall`, `Transfer` to another account, ERC-20 emulation, etc.) the code builds a real cross-contract `Promise` via `action_to_promise` and chains it with `.then(ext.rlp_execute_callback(caller_deposit))`, so a failure of that promise is observed by the callback and the caller is refunded: [3](#0-2) 

But for `TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer)`, the code comments that "self transfers are no-ops" and calls `rlp_execute_callback` directly, with no preceding promise: [4](#0-3) 

`rlp_execute_callback` handles this "no promise" case (`env::promise_results_count() == 0`) as an unconditional success and never even reads `caller_deposit`: [5](#0-4) 

Since `rlp_execute` is `#[payable]`, an external predecessor (any account, including a malicious or simply naive relayer/user) is free to attach an arbitrary NEAR deposit to the `rlp_execute` call itself while presenting an Ethereum-emulated transaction that resolves to `SelfBaseTokenTransfer` (a self-to-self transfer, which is a legitimate, easily-constructible Ethereum transaction type per `parse_rlp_tx_to_action`/`internal.rs`): [6](#0-5) 

In this path there is no `Promise` created to consume the deposit and no refund is attempted—the attached deposit is credited to the wallet contract's on-chain balance (standard NEAR receipt semantics) and stays there permanently, with no contract method exposed to reclaim it on behalf of the original caller. This is the direct analog of the reported `BaseAsyncSwapper.swap()` bug: value is required/attached for an operation, the code path that is actually taken neither uses that value for its intended purpose nor provides any mechanism (a `receive()`/refund) to return it, so it becomes permanently stuck in the contract.

### Impact Explanation
Funds attached by a relayer or any third-party account calling `rlp_execute` are permanently locked inside the Wallet Contract whenever the wrapped transaction is (or can be crafted to be) a `SelfBaseTokenTransfer`. This satisfies the "permanently frozen funds" impact category: the deposit is not lost through gas or fees but through a code path that discards the caller's ability to recover it, and it is reachable by any account able to submit a signed transaction/function call to a deployed Wallet Contract instance (no special privilege required).

### Likelihood Explanation
Likelihood is high for anyone who understands the contract's promise/callback wiring: attaching a NEAR deposit to `rlp_execute` while supplying an RLP-encoded Ethereum transaction that targets the wallet's own address (self base-token transfer) is trivial to construct, and nothing in `rlp_execute`'s validation rejects a non-zero attached deposit for this transaction kind.

### Recommendation
In the `SelfBaseTokenTransfer` branch of `inner_rlp_execute` (and more generally, anywhere `rlp_execute_callback` is invoked without a preceding cross-contract promise), explicitly issue a refund transfer of `caller_deposit` back to its `account_id` before/while calling `rlp_execute_callback`, mirroring the refund logic already present in the `PromiseResult::Failed` branch of `rlp_execute_callback`. Alternatively, reject/refund any non-zero attached deposit up front when the resolved transaction kind is `SelfBaseTokenTransfer`, since that kind never needs one.

### Proof of Concept
1. Deploy/target an existing eth-implicit Wallet Contract account `W` (address `0xW`).
2. As any account `A` (`A != W`), submit a NEAR transaction calling `W.rlp_execute(target=W, tx_bytes_b64=<RLP tx>)` with a non-zero attached deposit `d` (allowed since `rlp_execute` is `#[payable]`).
3. Craft the inner Ethereum transaction so `tx.to == 0xW` (self) and its calldata is not parseable as a Near-native action or emulation selector, so `parse_rlp_tx_to_action` resolves `TargetKind::CurrentAccount` and returns `TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer)` (see `internal.rs` lines 139-148).
4. `inner_rlp_execute` computes `caller_deposit = Some(CallerDeposit { account_id: A, yocto_near: d })` (since `A != W`) and dispatches directly to `ext.rlp_execute_callback(caller_deposit)` with no intervening promise.
5. `rlp_execute_callback` sees `env::promise_results_count() == 0`, returns `success: true` immediately, and never refunds `d` to `A`.
6. `d` remains part of `W`'s balance permanently; account `A` has no way to reclaim it through the Wallet Contract's public interface.
