### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant offline-session/Admin-API access - (File: `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` and `packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts`)

### Summary
Webhook authentication validates the request's HMAC over the raw body only, but then uses the unverified `X-Shopify-Shop-Domain` / `shopify-shop-domain` header value to look up and hand back the offline session (and a live Admin API client) for that shop. This is structurally identical to the Shelter bug: a check is performed against one thing (here, the HMAC over the body, analogous to `claimed[msg.sender]`), while the identity actually used to fetch/act on state (`check.domain`, analogous to `_to`) is taken from a separate, attacker-influenced field that the check does not bind to.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` computes and checks the webhook HMAC only over `rawBody`: [1](#0-0) 

The shop domain is read straight from the `X-Shopify-Shop-Domain` header, with no cryptographic binding to the HMAC: [2](#0-1) 

`authenticateWebhookFactory` (shopify-app-remix and shopify-app-react-router) then takes that unverified `check.domain` and uses it directly to load the shop's offline session and build an authenticated Admin API client, exposing both to the caller: [3](#0-2) [4](#0-3) 

`ensureValidOfflineSession` → `createOrLoadOfflineSession` → `getOfflineId(shop)` performs no additional verification that the caller is entitled to that `shop`; the library's own docs explicitly warn about this pattern ("This method does not perform any validation on the shop parameter... You should never read the shop from user inputs or URLs"): [5](#0-4) [6](#0-5) 

Because Shopify signs webhook HMACs with the app's single shared API secret (the same secret used for every shop that installs the app), any merchant who installs the app can capture a genuine, validly-signed webhook delivered to their own store. Since the HMAC covers only the body — not headers — that attacker can replay the same body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `validateFactory` will report the HMAC as valid (it only checks body integrity), and `authenticateWebhookFactory` will happily load and return the victim shop's offline session and an authenticated `admin` client scoped to the victim.

### Impact Explanation
This is a cross-tenant compromise: a low-privilege actor (any merchant who has installed the app, i.e., an unprivileged, anonymous-to-the-victim attacker) can obtain access to another merchant's offline access token/session and a fully working Admin API client, exactly the class of "accepted forged Shopify request" / "cross-tenant access" outcome called for in the validation rules. The severity mirrors the original report: the check exists (HMAC), but the actor identity used to fetch/act on victim state is taken from an unbound, attacker-controlled input.

### Likelihood Explanation
Exploitation requires the attacker to (1) install the vulnerable app on their own store to obtain a legitimately-signed webhook body+HMAC pair, and (2) know or guess the victim's `*.myshopify.com` domain (public information) to replay the request with a swapped header. No secret material needs to be leaked and no MITM is required — the attacker fully controls their own webhook deliveries and can forward them with a modified header to the app's public webhook endpoint. This is realistically reachable by any app-installing merchant.

### Recommendation
Bind the shop identity to the signature verification instead of trusting the header independently:
- Prefer deriving the shop from a source that is itself cryptographically verified (e.g., only trust `X-Shopify-Shop-Domain` when the webhook is delivered via Shopify's Events system with signed headers, or cross-check the domain against the app's own record of shops that have valid HMAC-verified installs).
- At minimum, verify that the offline session returned for `check.domain` was created via a previously-authenticated OAuth/token-exchange flow for that same shop, and reject/alert on any webhook whose declared domain does not match an app-verified relationship, rather than blindly trusting the header once the body HMAC passes.
- Consider including the domain header in the HMAC computation path (or validating it against Shopify's public app-webhook topology) so header tampering cannot be decoupled from body integrity checks.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a legitimate webhook POST with body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(apiSecretKey, B)`).
2. Attacker replays the same request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `validateFactory`/`validateHmacFromRequestFactory` recomputes HMAC over `B` only, matches `H`, and returns `valid: true` with `domain: 'victim-shop.myshopify.com'` [7](#0-6) .
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loads the victim's stored offline session, and returns `{ shop: 'victim-shop.myshopify.com', session, admin }` to the app's webhook route handler, giving the attacker's request path a live Admin API client for the victim shop [8](#0-7) .

# shopify.session.getOfflineId

Builds a session id that can be used to load an offline session, if there was a [`auth.begin`](../auth/begin.md) call to create one.

**Warning**: This method **_does not_** perform any validation on the `shop` parameter because it is meant for background tasks.
You should **_never_** read the shop from user inputs or URLs.

  const session = await getSessionFromStorage(offlineSessionId);

}

import {AppDistribution, BasicParams} from '../types';

export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
}
