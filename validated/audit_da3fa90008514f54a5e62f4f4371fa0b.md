### Title
Unbounded growth of the per-shop session-id index in `KVSessionStorage` leads to DoS of session lookup/uninstall paths - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage.addShopIds()` appends a session id to a shop-scoped list on every `storeSession()` call without checking for duplicates or bounding the list size. Because OAuth flows repeatedly call `storeSession()` with deterministic session ids (offline sessions use `offline_${shop}`), every re-authentication of the same shop/user grows this list forever. `findSessionsByShop()` then iterates the entire list on every call, one `namespace.get` per id, which is functionally the same anti-pattern as the reported `getLockedCount` issue: an ever-growing, request-triggerable collection that is fully iterated on a hot path.

### Finding Description
`storeSession` writes the session and then calls `addShopIds`: [1](#0-0) 

`addShopIds` simply concatenates the new id(s) onto whatever list already exists, with no de-duplication and no cap: [2](#0-1) 

Contrast this with the Redis adapter's equivalent (`addKeyToShopList`), which explicitly checks `if (!idKeysArray.includes(idKey))` before pushing — the KV adapter is missing this guard.

`findSessionsByShop` reads the (potentially huge) id array and does a `namespace.get` for every entry: [3](#0-2) 

Session ids for offline access tokens are deterministic per shop (`offline_${shop}`), computed in `getOfflineId`: [4](#0-3) 

`storeSession` is invoked on every completed OAuth callback, both in `shopify-app-express`'s `authCallback` and in `shopify-app-remix`'s `handleAuthCallbackRequest`: [5](#0-4) [6](#0-5) 

Because the offline (and, per merchant-user, the online) session id is the *same* every time OAuth completes for that shop/user, each re-authentication (which a merchant can trigger simply by re-visiting the app's `/auth` endpoint — `ensureInstalledOnShop` redirects to `redirectToAuth` whenever no valid session is found) appends a duplicate id to the shop's KV list rather than replacing/deduplicating it: [7](#0-6) 

Over time (repeated OAuth grants, scope updates, expired-token re-auth, or an attacker/merchant intentionally looping the OAuth begin→callback flow for a shop they control) the `shop:<shop>` KV value grows without bound. `findSessionsByShop` is called by `AppInstallations.includes`/`AppInstallations.delete`, which are used both during install checks and during `APP_UNINSTALLED` webhook processing (`deleteAppInstallationHandler`): [8](#0-7) [9](#0-8) 

### Impact Explanation
Cloudflare KV values are size-limited (25 MB) and KV write/read operations have consistency/rate characteristics that degrade with value size. An ever-growing, duplicate-laden id array in the `shop:<shop>` key means:
- `findSessionsByShop` performs an unbounded, linearly growing number of `namespace.get` calls per invocation, which slows or eventually fails (KV limits) — a denial-of-service of the install-check and uninstall-cleanup code paths for that shop.
- `AppInstallations.delete`, invoked from the `APP_UNINSTALLED` webhook handler, may fail to load/delete all sessions if the KV value becomes malformed/oversized, leaving stale sessions and blocking correct cleanup.
- This directly parallels the original bug class: an iteratively-read collection that grows without bound as a side effect of ordinary, repeatable actions, eventually threatening the availability of an auth-adjacent operation.

### Likelihood Explanation
No privileged or attacker-exotic action is required — simply re-running the standard OAuth flow (which any merchant, or anyone who can trigger `/auth` for a shop, can do) repeatedly appends to the list. This happens naturally over the lifetime of an app (scope updates force re-auth, session expiry, uninstall/reinstall cycles) and can be *accelerated* deliberately by any actor able to invoke the app's public auth begin/callback endpoints for a given shop.

### Recommendation
In `addShopIds`, de-duplicate the id before appending (mirroring the check already present in the Redis adapter's `addKeyToShopList`), e.g. build the array via a `Set` before storing to KV. Additionally, consider capping list growth or transitioning to a data structure that supports removal of superseded session ids rather than pure append.

### Proof of Concept
1. Configure an app to use `KVSessionStorage`.
2. Complete OAuth for a shop `test.myshopify.com` (offline flow), producing session id `offline_test.myshopify.com`, which is appended to KV key `shop:test.myshopify.com`.
3. Force re-authentication (e.g., visit the app's `/auth?shop=test.myshopify.com` again, or trigger a scope/token expiry that causes `ensureInstalledOnShop` to redirect to `redirectToAuth`), completing OAuth callback again.
4. Observe that `storeSession` is called again with the *same* session id `offline_test.myshopify.com`, and `addShopIds` appends it again to the KV array — inspect the raw KV value for key `shop:test.myshopify.com` and confirm duplicate entries accumulate with each re-auth cycle instead of staying at length 1.
5. Repeating this loop N times grows the KV array to N duplicate entries; `findSessionsByShop('test.myshopify.com')` then performs N `namespace.get` calls, demonstrating the unbounded linear cost growth on every subsequent call to `AppInstallations.includes`/`delete`.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
