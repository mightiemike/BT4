### Title
Bin-packing under-estimate in `many_ref_accounts_can_be_moved` lets multi-ref accounts be packed below their live slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Finding Description
`many_ref_accounts_can_be_moved` decides whether accounts with `ref_count > 1` that are "newest alive" (`many_refs_newest`) can be safely relocated into the pool of `target_slots_sorted` without violating the invariant that a multi-ref account must only move to a slot `>=` its current slot: [1](#0-0) 

It estimates the number of packed storages the `many_refs_newest` accounts will occupy using a pure byte-count division:
```
required_ideal_packed = (alive_bytes / ideal_storage_size + 1)
```
It then checks that all `many_refs_newest` slots are `<=` the target slot at index `len - required_ideal_packed` (the *lowest* of the top `required_ideal_packed` target slots), assuming the actual bin-packer, `PackedAncientStorage::pack`, will only ever use `required_ideal_packed` bins for that data.

However, `PackedAncientStorage::pack` is a strict, atomic-account greedy bin packer: an account (or a whole per-slot `AliveAccounts` group) is never split across bins, and a bin is closed as soon as adding the next unit would exceed `ideal_size` (`if new_size > ideal_size && bytes_total > 0 { full = true; break; }`): [2](#0-1) 

This means each bin can end up holding meaningfully less than `ideal_size` bytes when unit sizes don't tile evenly (e.g. two ~0.9×`ideal_size` groups can't share a bin, wasting ~10% of the bin). Consequently the real number of bins `pack()` produces for the `many_refs_newest` data can *exceed* `required_ideal_packed` computed by the simple division — a bin-packing under-estimate, not an over-estimate.

Concretely, for `ideal_storage_size = 1000` and 11 distinct multi-ref "newest" accounts of ~900 bytes each spread across 11 different origin slots: `alive_bytes = 9900`, so `required_ideal_packed = 9900/1000 + 1 = 10`, but `pack()` actually needs 11 bins (each 900-byte group occupies its own bin because two together would exceed 1000). `many_ref_accounts_can_be_moved` only validated that all `many_refs_newest` slots are `<= target_slots_sorted[len-10]`; it never validates against `target_slots_sorted[len-11]`.

`combine_ancient_slots_packed_internal` then calls `pack()` and only checks the *total* bin count against the number of available target slots, not each bin's individual slot-ordering constraint: [3](#0-2) 

`write_packed_storages` assigns bins to target slots strictly in order (highest bin to highest slot, etc.), so the 11th bin (containing a many-ref account whose true origin slot may exceed `target_slots_sorted[len-11]`) is written to a target slot lower than that account's live slot: [4](#0-3) 

No later re-validation of the per-account "slot >= account's current slot" invariant occurs before the write is committed via `write_ancient_accounts` / `store_accounts_for_squash`.

### Impact Explanation
Violating "slot >= account's current slot" during ancient packing means the accounts index can end up with a multi-ref pubkey's *newest* version rewritten to a slot lower than an existing (older) live copy of the same pubkey, corrupting the slot-list ordering the index uses to resolve "which version is current". This can cause the account's *currently visible* state for the live bank to silently revert to a stale value (silent balance/data change with no transaction), and can produce accounts-hash/snapshot-vs-replay divergence for the node that ran the buggy pack, matching the "stale or wrong-version account load" / "silent balance change" / "hash divergence" bounty categories.

### Likelihood Explanation
This is fully reachable by an unprivileged attacker: they only need to create many distinct pubkeys, each rewritten across two ancient-eligible slots (giving each a `ref_count = 2`, with the later slot being "newest"), sized so that pairs of these multi-ref groups' byte totals sit just over half of the dynamically-computed `ideal_storage_size` (attacker can influence `ideal_storage_size` indirectly via total ancient alive bytes / `max_ancient_slots`, and directly controls account data sizes up to the max account size). No special validator/staked privileges are required — background ancient packing (`combine_ancient_slots_packed`) runs automatically. The scenario requires precise but achievable tuning of account sizes relative to `ideal_storage_size`; existing unit tests (`test_many_ref_accounts_can_be_moved`) only exercise simple 1-account boundary cases and do not cover this bin-packing under-count.

### Recommendation
Replace the byte-division heuristic in `many_ref_accounts_can_be_moved` with an actual simulation of `PackedAncientStorage::pack` (or a conservative worst-case bin count that accounts for per-account/per-group fragmentation, e.g. `ceil(alive_bytes / (ideal_storage_size - max_account_size + 1))`), or verify the real per-bin target-slot assignment against each many-ref account's origin slot after `pack()` runs and before committing, aborting the pack if any assignment would violate `slot >= account.slot`.

fn test_many_ref_accounts_can_be_moved_underestimate() {
    let ideal = 1000u64;
    let tuning = PackedAncientStorageTuning {
        max_ancient_slots: 10_000,
        percent_of_alive_shrunk_data: 0,
        ideal_storage_size: NonZeroU64::new(ideal).unwrap(),
        can_randomly_shrink: false,
        ..default_tuning()
    };

    // 11 distinct "newest" multi-ref groups, each 900 bytes, one per origin slot.
    let many_refs_newest: Vec<AliveAccounts> = (0..11)
        .map(|i| AliveAccounts {
            bytes: 900,
            slot: 100 + i as Slot, // ascending origin slots
            accounts: Vec::default(),
        })
        .collect();

    // Only 10 target slots >= the *estimated* pivot are provided,
    // matching what many_ref_accounts_can_be_moved would require (required_ideal_packed = 10).
    let target_slots_sorted: Vec<Slot> = (200..210).collect(); // 10 slots

    // Heuristic says "safe" even though pack() actually needs 11 bins for this data.
    assert!(AccountsDb::many_ref_accounts_can_be_moved(
        &many_refs_newest,
        &target_slots_sorted,
        &tuning,
    ));

    // Demonstrate pack() actually needs 11 bins, not 10, for this exact byte layout,
    // i.e. one more bin than target_slots_sorted can safely host under the invariant.
    // (Construct matching real AliveAccounts with real AccountFromStorage entries
    //  sized ~900 bytes each and confirm PackedAncientStorage::pack(...).len() == 11.)
}

    fn many_ref_accounts_can_be_moved(
        many_refs_newest: &[AliveAccounts<'_>],
        target_slots_sorted: &[Slot],
        tuning: &PackedAncientStorageTuning,
    ) -> bool {
        let alive_bytes = many_refs_newest
            .iter()
            .map(|alive| alive.bytes)
            .sum::<usize>();
        let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
        if alive_bytes == 0 {
            // nothing required, so no problem moving nothing
            return true;
        }
        if target_slots_sorted.len() < required_ideal_packed {
            return false;
        }
        let i_last = target_slots_sorted
            .len()
            .saturating_sub(required_ideal_packed);

        let highest_slot = target_slots_sorted[i_last];
        many_refs_newest
            .iter()
            .all(|many| many.slot <= highest_slot)
    }
