### Title
`accrue` pause causes stale liquidity/borrow index to be used for deposit/redeem pricing and debt accounting instead of reverting - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Each vault (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststxbtc.clar`) gates interest accrual through a `pause-states` flag. When `accrue` is set to paused, the function does not revert - it silently passes through and returns the stale, previously stored `index`/`lindex` values instead of computing the up-to-date ones [1](#0-0) . This mirrors the analog pattern of "a pause that passes through instead of reverting": operationally sensitive downstream logic (`deposit`, `redeem`, `system-borrow`, `system-repay`) still executes using these stale, un-accrued values as if they were current.

### Finding Description
`deposit` and `redeem` both call `(try! (accrue))` and then immediately use `convert-to-shares-preview` / `convert-to-assets-preview`, which derive share price from the vault's `index`/`lindex` state variables [2](#0-1) [3](#0-2) .

Normally, `accrue` recomputes `next-index`/`next-liquidity-index`, mints the treasury fee-share (`treasury-lp`), updates `index`/`lindex` state, and stamps `last-update` with the current block time before any deposit/redeem/borrow/repay logic runs [4](#0-3) .

When the protocol admin sets `accrue` to paused in `pause-states`, the function instead returns the **old** `idx`/`lidx` unmodified — `last-update` is never advanced, no fee is minted to `.dao-treasury`, and no state variable is mutated [5](#0-4) . Crucially, this "paused" branch still returns `(ok ...)` rather than an error, so all callers of `accrue` (deposit, redeem, `system-borrow`, `system-repay`) proceed to execute using the stale index as if it were valid and current, rather than being blocked. This is the same mechanical bug class as the referenced report's health-check/pass-through issue: a value (accrued index) is silently treated as fresh by every dependent code path, even though the invalidating computation was skipped.

The consequence is that while `accrue` is paused, any amount of real-world time can elapse (interest that should accrue on outstanding debt is frozen), yet users can still `deposit`/`redeem` at the frozen share price, and `system-borrow`/`system-repay` continue to move principal using the stale `idx` recorded from before the pause. Once `accrue` is unpaused, the next accrual call jumps `index`/`lindex` forward all at once based on `next-index()`, which is presumably a function of elapsed real time since `last-update` — meaning the deposits/redeems executed during the pause window locked in a share price that does not reflect the interest that was accruing on debt during that window in reality (if `next-index()` computes based on elapsed time rather than being frozen along with the pause).

### Impact Explanation
If `next-index()`/`next-liquidity-index()` compute accrual based on elapsed wall-clock/block time since `last-update` rather than being itself paused, then depositors/redeemers who transact during the `accrue`-paused window get priced against a stale index, and when accrual resumes the entire elapsed period's interest is retroactively applied against the frozen `last-update` timestamp — meaning users who deposited/redeemed during the pause capture or forfeit yield that should have been distributed proportionally over time. This lands on **temporary freezing / mispricing of unclaimed yield** (High) for depositors who transact in that window, since the treasury fee-share (`treasury-lp`) computed on unmint is skipped entirely for that period, and share pricing potentially decouples from real-time economic reality.

### Likelihood Explanation
This requires only a single admin action (pausing `accrue`) followed by ordinary user deposit/redeem calls within the same or later transactions/blocks — no cross-user interference or DAO compromise is needed to trigger the mechanism; only the intended pause toggle plus normal user activity. However, exploiting it for meaningful profit depends on `next-index()`'s exact time-accrual formula (whether resuming after a long pause causes a large jump), which I could not fully verify from the excerpts read.

### Recommendation
When `accrue` is paused, either (a) revert calls to `deposit`, `redeem`, `system-borrow`, and `system-repay` instead of allowing them to proceed with a stale index, or (b) have the paused branch freeze `last-update` at pause-time and ensure `next-index()`/`next-liquidity-index()` compute deltas only up to the pause point, then resume accrual cleanly from `last-update` going forward, preventing any retroactive interest jump being captured or missed by users transacting during the pause.

### Proof of Concept
1. Admin sets `pause-states.accrue = true` on `v0-vault-usdc.clar` via governance [5](#0-4) .
2. Time passes (interest that should accrue on outstanding debt does not update `index`/`lindex`, and `last-update` is frozen).
3. A user calls `deposit`, which calls `accrue` (returns stale `idx`/`lidx` because paused) then computes `inkind` via `convert-to-shares-preview` using the stale price [6](#0-5) .
4. Admin unpauses `accrue`.
5. The next `accrue` call computes `next-index()`/`next-liquidity-index()` based on time elapsed since the old (frozen) `last-update`, applying the entire pause-period's worth of interest in one jump [7](#0-6) .
6. Depending on whether the depositor from step 3 redeems before or after this jump, they either miss out on interest that should have accrued to their shares proportionally, or capture interest they should not have earned for a period during which their principal was not exposed to the loan.

Note: I was unable to view the exact implementation of `next-index()`/`next-liquidity-index()` in the excerpts retrieved, so I cannot fully confirm whether the accrual jump is strictly time-based or bounded in a way that neutralizes this effect. This uncertainty should be resolved by inspecting those helper functions directly before treating this as fully proven.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
