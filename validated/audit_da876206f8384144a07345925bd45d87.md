### Title
Unbounded full-table `PendingInbounds.Walk` scan in ballot-terminal hook enables attacker-amplified gas growth on the honest-validator finalization path - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
`afterInboundBallotTerminal` performs a full, unindexed `Walk` over the entire `PendingInbounds` collection every time *any* inbound ballot reaches a terminal state, in order to find the entry whose `Variants[].BallotId` matches the finalized ballot. This is the same bug class as Sherlock M-14 (`BondAggregator.liveMarketsBy`): an unbounded loop over a collection whose size is attacker-influenced, executed synchronously in a state-transition/consensus path rather than paginated.

### Finding Description
`RecordInboundVote` [1](#0-0)  creates a new `PendingInbounds` entry keyed by `utxKey = sha256(source_chain:tx_hash:log_index)` on the first vote for each distinct source-chain event, and a new entry is created independently for every inbound observed on any enabled external chain by honest UVs. Removal from `PendingInbounds` only happens either on ballot PASS (in `VoteInbound`) or when *all* variants of an entry reach a terminal ballot state via `BallotHooks.afterInboundBallotTerminal` [2](#0-1) .

That hook fires synchronously inside `VoteOnInboundBallot`/`CheckIfFinalizingVote`'s finalization call chain — i.e., as part of ordinary Cosmos SDK message processing (`MsgVoteInbound`) during block execution, not an off-chain view query. To locate the entry owning a given finalized `ballotID`, it does: [3](#0-2) 
a full `Walk` over every key in `PendingInbounds`, with no secondary index from `ballotID -> utxKey`. The code comment explicitly assumes "the pending set is small and transient" [4](#0-3) , which is an unverified scaling assumption exactly analogous to the Sherlock report's assumption that `marketCounter` stays small.

Because a `PendingInbounds` entry persists until **all** of its ballot variants terminate (any still-`PENDING` variant keeps the whole entry alive, per the `for _, v := range entry.Variants` PENDING check [5](#0-4) ), an unprivileged external attacker who triggers many real (even low-value/near-zero) gateway events across the enabled external chains causes honest UVs to observe and vote on them, growing `PendingInbounds` without an enforced upper bound. Every subsequent ballot finalization (including finalizations of *unrelated* inbounds) then pays the cost of walking the full, growing map, turning a single terminal-vote transaction into an O(n) operation where n is attacker-influenced. Unlike the Solidity case there's no fixed 50M-gas view-call ceiling, but Cosmos SDK deliver-tx execution is still block-gas-metered, so this degrades into higher and higher per-tx gas costs for ordinary `MsgVoteInbound` submissions as the pending set grows, eventually risking gas-limit exhaustion / failed tx execution for UV votes on the consensus-critical inbound path, purely from unprivileged, honest-validator-observed user activity.

### Impact Explanation
This does not itself let an attacker steal or mint funds, but it degrades the universal-execution finalization path (`MsgVoteInbound` -> `VoteOnInboundBallot` -> `CheckIfFinalizingVote` -> `BallotHooks.AfterBallotTerminal`) for all UVs, on every terminal ballot, as a function of total historical concurrent pending inbounds. In the worst case this can push individual vote-finalizing transactions toward or past the block gas limit, causing `MsgVoteInbound` finalization to fail/be un-includable and stalling processing of legitimate crosschain inbounds — a DoS on the finalization path reachable purely via unprivileged, honest, ordinary user deposit activity across the several external chains Push Chain supports.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: growing `PendingInbounds` requires generating many concurrent real events on enabled external chains that honest UVs must actually observe and vote on (there is a real, if small, per-event cost on the source chain), and normal ballot finalization removes entries quickly under healthy quorum. However, no cap exists on the number of concurrently-pending inbounds or in-flight variants, and slow/never-finalizing ballots (e.g., using chains/tokens/observations that stay contentious or below quorum until expiry) can keep entries alive for the full `expiryAfterBlocks` window, so the set can be inflated cheaply relative to its blast radius (degrading unrelated inbound processing for the whole network).

### Recommendation
Replace the full `PendingInbounds.Walk` scan in `afterInboundBallotTerminal` with a direct secondary index (`ballotID -> utxKey`) so lookup is O(1)/O(log n) instead of O(n), analogous to the BondAggregator fix's approach of avoiding unbounded loops in a frequently-invoked path. Alternatively/additionally, bound the number of concurrently-open `PendingInbounds` entries or variants (or shard the walk with pagination + multi-block processing) so a single terminal-ballot hook invocation cannot grow linearly with total pending inbound count.

### Proof of Concept
1. An attacker triggers N distinct low-value gateway events across the several enabled external chains (each producing a unique `source_chain:tx_hash:log_index`).
2. Honest UVs observe and vote on each via `MsgVoteInbound`, each creating a new `PendingInbounds` entry via `RecordInboundVote`.
3. As long as at least one variant across these N entries stays un-finalized (e.g., some ballots deliberately kept below quorum or slow to converge), `PendingInbounds` retains all N entries.
4. Any *other*, unrelated inbound ballot reaching a terminal state now triggers `afterInboundBallotTerminal`, which walks all N (plus any additional legitimate) entries in `PendingInbounds` to find the one matching its `ballotID` — an O(N) operation executed inside ordinary `MsgVoteInbound` transaction processing.
5. Repeating this while N grows increases the gas cost of every subsequent inbound-ballot finalization, degrading (and at sufficient N, threatening to exceed block gas limits for) the finalization path for all UVs and users.

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
	if !found {
		// Entry was already cleared (e.g. the consensus-success path in
		// VoteInbound already removed it before this hook fires), or the
		// ballot does not belong to a tracked inbound. Nothing to do.
		return nil
	}
