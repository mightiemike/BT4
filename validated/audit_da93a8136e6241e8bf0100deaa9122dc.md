### Title
Malicious cross-contract target can panic the Wallet Contract's callback and permanently brick the account (`has_in_flight_tx` stuck `true`) - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (an eth-implicit-account contract that emulates EOA Ethereum transactions on NEAR) guards against concurrent/replayed transactions with an in-memory flag `has_in_flight_tx`, which is only cleared inside asynchronous callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`). Because NEAR reverts *all* state changes of a function call if that call's execution fails (e.g. panics or runs out of allocated gas) — even changes made at the very start of the function — any panic/OOG inside these callbacks after the promise chain has been dispatched leaves `has_in_flight_tx` permanently `true`, since the earlier reset (`self.has_in_flight_tx = false;`) is rolled back along with everything else. This is directly analogous to the Cooler `onRepay` callback bug: an externally-controlled callback participant (here, the arbitrary cross-contract `target`, e.g. an attacker-deployed NEP-141 token or the address registrar) can cause the callback to fail in a way that leaves the "borrower" (the wallet contract owner) permanently unable to transact.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` before returning a `Promise`, with an explicit invariant comment that it must be reset to `false` by the callback: [1](#0-0) 

The reset happens as the *first* statement inside each callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`): [2](#0-1) [3](#0-2) [4](#0-3) 

For the `ERC20Transfer` and address-check flows, the *target* of the cross-contract call that feeds `env::promise_result(0)` into the callback is attacker-influenceable: it is the `token_id`/`target` account decoded from the user-signed RLP transaction, and its `storage_balance_of` / registrar `lookup` result is deserialized inside the callback via `serde_json::from_slice`: [5](#0-4) [6](#0-5) 

Each callback is only prepaid a fixed, small static gas budget (`ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `RLP_EXECUTE_CALLBACK_GAS`): [7](#0-6) 

If the target contract's response causes the callback's deserialization/logic to exceed its allocated gas (or to panic for any other reason, e.g. malformed/oversized payload), the callback receipt fails. Per NEAR's execution model, a failed function-call execution discards *all* state mutations performed during that call — including the `has_in_flight_tx = false;` write made at its start — so the flag remains `true` in the persisted contract state after the failed receipt. Since `rlp_execute` unconditionally rejects any further transaction while `has_in_flight_tx` is `true`: [8](#0-7) 

there is no other code path in the contract that resets this flag once it is stuck. The account becomes permanently unable to execute *any* further `rlp_execute` call — a total denial of service on the wallet, freezing all assets/actions reachable only through this contract's interface.

### Impact Explanation
This is directly triggerable by a single externally-influenced transaction: a wallet owner (or a relayer acting on the owner's signed RLP tx) interacting with an attacker-controlled `target` (e.g., a fake NEP-141 token, or exploiting the fixed address-registrar path if it is ever compromised/upgraded) can cause the associated callback receipt to fail after `has_in_flight_tx` was set but before it can be durably reset. Because the reset is rolled back with the rest of the failed call's state, the contract becomes permanently unable to process new user transactions (`rlp_execute` always short-circuits with the "already in progress" error), permanently freezing the account's use of the wallet contract — an unauthorized, unrecoverable denial of access analogous to freezing funds. This is a High severity, permanent-freeze class bug reachable purely by a legitimate contract call/transaction, with no privileged access required.

### Likelihood Explanation
Likelihood is moderate-to-high: any user or relayer who submits an ERC-20-style transfer transaction (`EthEmulationKind::ERC20Transfer`) that targets an untrusted/attacker-deployed token contract exercises this exact callback path. An attacker need only ensure the `storage_balance_of` response (or any promise-chain failure inside the callback) causes the callback's execution to fail after entry — a realistic condition given that a malicious contract fully controls the shape/size of its response and the callback's static gas budget is small and fixed.

### Recommendation
Do not rely on a flag that is only cleared as the *first* action of a callback whose subsequent logic can still fail. Instead:
- Reset `has_in_flight_tx` via a mechanism that survives a failing callback (e.g., persist the "cleared" state change before any code that can panic/exceed gas, or use a separate always-succeeding cleanup callback attached with `promise_and`/`then` that runs regardless of the primary callback's success, similar to a guaranteed "finally" receipt).
- Bound/validate the size and structure of untrusted cross-contract responses before deserialization, and ensure callbacks have enough gas headroom (or fail closed by resetting the flag even under `#[private]` panic-catching) so no external target contract can cause a state-reverting failure that leaves `has_in_flight_tx` stuck.
- Add a recovery path (e.g., an owner-only, gas/nonce based mechanism) to unstick `has_in_flight_tx` if this can only be fully avoided by validating this analysis further with a live/instrumented test in a Devin session, since gas-based OOG triggering depends on precise cost accounting that could not be fully confirmed from static review alone.

### Proof of Concept
1. Deploy a malicious NEP-141 token contract whose `storage_balance_of` method returns a very large or maximally-sized successful result payload (bounded by the protocol's max register/return size).
2. As the wallet owner (or via an authorized relayer), submit an RLP-encoded Ethereum transaction whose `target` is this malicious token, decoded as an `EthEmulationKind::ERC20Transfer`.
3. `rlp_execute` → `inner_rlp_execute` sets up the promise chain and the top-level call sets `has_in_flight_tx = true` [9](#0-8) 
then dispatches to `nep_141_storage_balance_callback` with static gas `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`.
4. Because the malicious token's response is crafted to make deserialization/processing inside `nep_141_storage_balance_callback` exceed its prepaid gas (or otherwise panic), the callback execution fails.
5. All state writes from that failed callback execution — including the `self.has_in_flight_tx = false;` performed at its start — are discarded by NEAR's all-or-nothing state commit for a failed function call.
6. Any subsequent call to `rlp_execute` by the legitimate owner now immediately returns the "transaction already in progress" error forever, since `has_in_flight_tx` remains `true` in persisted state with no code path to clear it.

Note: full confirmation that a crafted payload can be made to exceed the specific callback's prepaid gas (rather than merely fail for other content-validation reasons) would require gas-profiling in a running testnet/sandbox environment, which was not available during this review — a Devin session with access to the runtime/tests would be needed to execute and measure this precisely.
