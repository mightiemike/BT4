Based on my research, I found a strong structural analog to the reported bug class in java-tron's price-history mechanism.

### Title
Energy/Bandwidth/Memo fee price-history strings are appended without ordering, breaking the reverse-scan lookup that assumes chronological order - ([File: framework/src/main/java/org/tron/core/consensus/ProposalService.java])

### Summary
The Otter Audits report describes a class of bug where an append-only sequence (`vote_ledgers`) is assumed sorted for a positional-lookup algorithm (binary search), but the append operation (`push_back`) does not enforce that invariant, so an out-of-order insertion silently corrupts all subsequent lookups. java-tron has a structurally identical pattern in its `ENERGY_FEE`/`TRANSACTION_FEE`/`MEMO_FEE` price-history strings: entries are appended as `timestamp:price` pairs via simple string concatenation, and the lookup function assumes the list is in ascending timestamp order, scanning it backward and returning the first entry whose timestamp is less than the query timestamp.

### Finding Description
When a committee proposal changing `ENERGY_FEE`, `TRANSACTION_FEE`, or `MEMO_FEE` is approved and takes effect, `ProposalService.process` appends a new `expirationTime:value` entry to the corresponding history string by simple concatenation, with no sorting or validation that the new `expirationTime` is greater than the previous entries' timestamps: [1](#0-0) [2](#0-1) [3](#0-2) 

The consumer of this history, `parseEnergyFee` (and its bandwidth/memo analogs in `JsonRpcApiUtil`), assumes the list is monotonically increasing in timestamp and walks it **backward**, returning the first entry it finds whose timestamp is strictly less than the requested timestamp: [4](#0-3) 

`expirationTime` for a proposal is set at proposal-creation time (`proposalCapsule.getExpirationTime()`), which is `now + proposal window` at the time the proposal was created — not the time the proposal is actually applied. Because multiple proposals of the same type can be created, approved, and take effect in different orders/timings (e.g., a longer-window proposal created earlier but approved later than a shorter-window proposal created later but approved sooner), the resulting `expirationTime` values appended to the history string are **not guaranteed to be monotonically increasing** when concatenation happens at `process()` time (which occurs at maintenance-time application of the proposal, not at proposal-approval time in a fixed order). This is the same root-cause pattern as the reported bug: an append-only structure relied upon to be sorted for a positional/ordered lookup algorithm, but the append path performs no sort or ordering check.

### Impact Explanation
If the price-history string becomes unordered, `parseEnergyFee`/the bandwidth analog will return an incorrect historical fee for a given past timestamp, since the backward scan exits at the first (by list-order, not necessarily by time) entry less than the requested time rather than the true fee that was in effect at that timestamp. This is used by the JSON-RPC layer (`eth_estimateGas`/fee-related endpoints via `JsonRpcApiUtil`) to reconstruct historical resource pricing for a specific block/timestamp. An incorrect result here is a public-facing, unprivileged-user-observable divergence (wrong reported historical energy/bandwidth fee) rather than a consensus-critical accounting error, since it does not affect the live `saveEnergyFee`/`saveTransactionFee` value used for real fee deduction — only the historical reconstruction exposed via JSON-RPC.

### Likelihood Explanation
This requires: (1) a committee/governance actor creating multiple fee-change proposals with overlapping windows, and (2) the proposals being approved/applied in an order where the later-applied proposal has a smaller `expirationTime` than an earlier-applied one. Since proposal creation, approval quorum timing, and application at maintenance boundaries are governed by committee action (a trusted-role process), triggering this ordering anomaly in practice requires either abnormal committee timing or specific proposal-expiration configuration — it is not exploitable by a fully unprivileged actor. This tempers the practical likelihood significantly compared to the original report's context.

### Recommendation
When appending to `EnergyPriceHistory`/`BandwidthPriceHistory`/`MemoFeeHistory` in `ProposalService.process`, either (a) validate that the new `expirationTime` is strictly greater than the last recorded timestamp before appending, or (b) parse the history into a list of pairs, insert in sorted order, and re-serialize, so the invariant relied upon by `parseEnergyFee`'s backward-scan lookup is always maintained.

  public static long parseEnergyFee(long timestamp, String energyPriceHistory) {
    String[] priceList = energyPriceHistory.split(",");

    for (int i = priceList.length - 1; i >= 0; i--) {
      String[] priceArray = priceList[i].split(":");
      long time = Long.parseLong(priceArray[0]);
      long price = Long.parseLong(priceArray[1]);
      if (timestamp > time) {
        return price;
      }
    }

    return -1;
  }
