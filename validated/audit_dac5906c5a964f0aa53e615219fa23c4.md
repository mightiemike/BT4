### Title
Unbounded per-vote ballot-expiry scan lets unprivileged cross-chain deposits blow up gas/compute cost of every subsequent vote - ([File: x/uvalidator/keeper/ballot.go])

### Summary
Every time a new ballot is created for an inbound, outbound, or TSS event, `CreateBallot` first calls `ExpireBallotsBeforeHeight`, which walks **every currently active ballot** (`k.ActiveBallotIDs`, shared across all ballot types) and does a `k.Ballots.Get` for each before persisting the new ballot. This is the same class of bug as the SKALE `nodeExit` report: a single user-reachable transaction path performs O(n) work over a state set that an unprivileged attacker fully controls the growth of, with no cap on how large that set can get.

### Finding Description
`x/uexecutor/keeper/msg_vote_inbound.go` → `VoteOnInboundBallot` (`x/uexecutor/keeper/voting.go:11-71`) is invoked from `VoteInbound` whenever a validator observes a cross-chain deposit. It calls `k.uvalidatorKeeper.VoteOnBallot` → `GetOrCreateBallot` → `CreateBallot`: [1](#0-0) 

`CreateBallot` unconditionally runs `ExpireBallotsBeforeHeight(ctx, blockHeight)` before storing the new ballot: [2](#0-1) 

This function iterates the *entire* `ActiveBallotIDs` key set — which holds active ballots for inbound, outbound, and TSS-key events together — fetching each `Ballot` record individually to check its expiry height. There is no upper bound on the number of concurrently active ballots: every unique `(source_chain, tx_hash, log_index)` inbound observation produces its own ballot key (`types.GetInboundBallotKey`), and inbound observation events are fully attacker-controlled — an external, unprivileged actor can generate large numbers of cheap deposit transactions on any registered source chain, each of which honest universal validators will faithfully observe and vote on via `VoteInbound` (`x/uexecutor/keeper/msg_vote_inbound.go:18-158`), each producing a new distinct ballot key.

Because `CreateBallot` runs the full-set `ExpireBallotsBeforeHeight` scan on **every single new ballot's creation** (i.e., on the first vote for every new unique event), the per-transaction cost of processing an honestly-submitted validator vote grows linearly with however many active ballots currently exist. An attacker can cheaply inflate the active-ballot count (each ballot lives until `DefaultExpiryAfterBlocks` elapse or quorum is reached) by flooding source chains with small deposits faster than ballots expire, driving the active set arbitrarily large before the expiry window closes. Every subsequent honest vote (from any validator, on any chain) then pays the full O(n) scan cost, deterministically, on all nodes (this executes inside the state machine, so all validators redundantly pay the same cost to stay in consensus) — this is the direct analog of the SKALE `nodeExit`/`_startRotation` pattern where an attacker-independent, protocol-mandated cleanup loop over an unboundedly-growable collection is embedded inside an otherwise cheap user-triggered operation.

The related `x/uexecutor/keeper/ballot_hooks.go` `afterInboundBallotTerminal` hook (fired from `MarkBallotFinalized`/`MarkBallotExpired`) has the same shape: it does a full, un-paginated `k.PendingInbounds.Walk` over all pending inbound entries to locate the one matching a terminal ballot ID, on every single ballot finalization/expiry: [3](#0-2) 

Both scans are triggered purely by ordinary user deposit/withdraw traffic combined with honest validator voting — no privileged actor or malicious validator is required.

### Impact Explanation
As the number of concurrently pending/active ballots grows (attacker-controlled via cheap external-chain deposits), the deterministic compute cost paid by every honest validator node for processing each new vote transaction grows unbounded. This can:
- Materially slow down or stall block production/consensus progress as all validators redundantly execute the same growing O(n) scan for every vote transaction (state-machine-level, non-network DoS reachable by an unprivileged party).
- Cause votes to become prohibitively expensive/slow near block time or gas budgets, delaying finalization of legitimate user inbound/outbound transactions and, transitively, delaying fund settlement.

This does not appear to directly cause fund loss/mint/burn corruption by itself, but it does meet the "denial of service... reachable without privileged control" allowed-impact category, mirroring the original report's core concern (unbounded per-item iteration risking hitting a hard resource limit at attacker-controlled scale).

### Likelihood Explanation
Medium. Triggering requires sustained, cheap activity on external chains (source-chain deposits are typically low-cost) faster than the `DefaultExpiryAfterBlocks` window clears out old ballots; no special access is needed and honest validators/nodes are assumed. The severity scales with how large `DefaultExpiryAfterBlocks` is and how cheap it is to generate many distinct source-chain events — both of which favor an attacker with modest capital, since the exact values are configured in `x/uexecutor/types/constants.go` (not fully inspected here due to remaining tool budget).

### Recommendation
- Bound or amortize the active-ballot expiry scan: cap `ExpireBallotsBeforeHeight` to a fixed maximum number of ballots processed per call (paginate), or move expiry sweeping to `EndBlock` with a hard per-block cap instead of running a full scan synchronously inside every `CreateBallot`.
- Replace the linear `ActiveBallotIDs` scan with an expiry-height-indexed structure (e.g., a secondary index keyed by expiry height) so only ballots that are actually due for expiry are touched, independent of total active-ballot count.
- Apply the same fix to `afterInboundBallotTerminal`'s full `PendingInbounds.Walk` — index pending inbound entries by ballot ID instead of linear-scanning on every terminal transition.
- Add a maximum-active-ballots-per-source-chain (or global) cap/backpressure so an attacker cannot unboundedly inflate the active/pending sets.

### Proof of Concept
Conceptual (not executed, given available tooling):
1. Attacker submits many small, distinct deposit transactions on a registered source chain (cheap on that external chain), each with a unique `tx_hash`/`log_index`.
2. Honest universal validators observe each and call `MsgVoteInbound` → `VoteInbound` → `VoteOnInboundBallot` → `GetOrCreateBallot` → `CreateBallot`, each creating a new, distinct ballot key and adding to `ActiveBallotIDs`.
3. Before the `DefaultExpiryAfterBlocks` window elapses for earlier ballots, the attacker keeps the injection rate high enough that `ActiveBallotIDs` accumulates to a large N.
4. Every subsequent `CreateBallot` call (for the next new deposit or outbound/TSS event) now runs `ExpireBallotsBeforeHeight`, iterating and `Ballots.Get`-fetching all N active ballots — an O(N) cost paid by every validator node processing that vote transaction, repeated for every new vote thereafter, compounding total chain-wide compute cost.

```go
// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
```
