### Title
Replay/consistency check `TransactionOutput::ensure_match_transaction_info` omits state/hot-state/position checkpoint hash validation - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant-check function used by replay/verify tooling (`aptos-debugger`, `aptos-move/cli`, `storage/db-tool/src/replay_on_archive.rs`) to confirm that a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` obtained from an accumulator-proof-backed source (e.g., archive/backup). It checks status, gas, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally computed checkpoint roots. This mirrors the external report's bug class: a caller-supplied/derived value (here, the checkpoint roots embedded in the authenticated `TransactionInfo`) is accepted without validating it against the correct local context (the actual computed state root), letting a divergent commitment be silently reported as "matching."

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates transaction status, gas used, write-set hash, and event root hash against the passed-in `txn_info: &TransactionInfo`, but the function body contains no comparison at all for `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`. The function's own trailing comment makes this explicit: [2](#0-1) 

This states that the comparator "ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and instructs future maintainers to "Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — but the field feeding this gate, `compute_trading_native_state_roots`, already exists and is wired through the execution pipeline (`execution/executor/src/workflow/do_state_checkpoint.rs` lines 62-75, `execution/executor/src/workflow/do_ledger_update.rs` lines 58-127, `execution/executor-types/src/execution_output.rs`, `types/src/block_executor/config.rs`), and `position_state_checkpoint_hash` is already a first-class field of `TransactionInfoV1` (constructed at [3](#0-2) ) and included in accumulator-proof-verified `TransactionInfo` objects sourced from backup/archive.

This function is invoked from `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — all tools whose entire purpose is to confirm that locally re-executed VM output reproduces the authenticated, accumulator-proof-backed commitment. Because the checkpoint-hash fields are skipped, none of these tools can detect a divergence in `state_checkpoint_hash` (the merkle root of the whole account/resource state), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` between local execution and the archived/authenticated ledger.

### Impact Explanation
This breaks the "committed state must equal the correct VM result" and "replay/restore paths must not reinterpret committed data into a different ledger state" invariants required by the state-integrity gate. Concretely:
- A replay tool operator could re-execute a transaction range and receive a "verification passed" result even though the locally computed state (or position-state, once the trading-native feature is enabled) root differs from the one embedded in the authenticated `TransactionInfo` fetched from backup/archive storage.
- This masks exactly the class of divergence that `state_checkpoint_hash`/`position_state_checkpoint_hash` exists to catch — VM nondeterminism, an execution bug, or a corrupted archive — turning what should be a hard failure into a silent pass.
- Since `position_state_checkpoint_hash` is gated behind the not-yet-enabled `compute_trading_native_state_roots` feature flag (confirmed via `types/src/on_chain_config/aptos_features.rs` and `types/src/block_executor/config.rs`), the position-state portion of this gap has no live mainnet impact today; however, `state_checkpoint_hash` and `hot_state_checkpoint_hash` are always populated (not feature-gated) and are also silently skipped by this same function, so the gap already applies to the core state root on every call site today.

### Likelihood Explanation
This is not an attacker-triggerable exploit against consensus; it is a latent correctness gap in a replay/verification utility. It requires no privileged access to trigger — any operator running the replay/debugger tools relies on this function as the ground-truth check — but it only manifests impact when there is an actual underlying state divergence (execution bug, VM nondeterminism, or corrupted archive data) to detect. The code's own inline TODO comment confirms the authors are aware of and have explicitly flagged this gap as unresolved.

### Recommendation
Extend `ensure_match_transaction_info` to also assert that the locally computed `state_checkpoint_hash` (and, when available, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) equal the corresponding fields on `txn_info`, mirroring the existing checks for write-set hash and event root hash. Since the checkpoint hash is only known when the transaction is a checkpoint boundary, the check should be conditioned similarly to `get_state_checkpoint_hashes` in `execution/executor/src/workflow/do_state_checkpoint.rs`, and callers (`replay_on_archive`, `aptos-debugger`, `cli/commands.rs`) should pass through the locally computed checkpoint hash(es) so the comparison can be performed at the transaction-output level rather than deferred.

### Proof of Concept
No PoC transaction/exploit is provided because this is a detection gap in offline verification tooling, not an on-chain/consensus-exploitable path: it cannot alter committed ledger state or be triggered by an unprivileged network participant. The concrete corrupted-value trace is: local `state_checkpoint_hash`/`position_state_checkpoint_hash` (computed by `DoStateCheckpoint::run`) diverges from `txn_info.state_checkpoint_hash()`/`txn_info.position_state_checkpoint_hash()` (the authenticated value from the accumulator-proof-backed `TransactionInfo`) → `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) returns `Ok(())` regardless → replay/verify tools (`replay_on_archive.rs`, `aptos_debugger.rs`, `cli/commands.rs`) report success despite the mismatch.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
