Confirmed root cause at `runtime/runtime/src/lib.rs:1047-1054`: when a receipt's predecessor is `"system"` (i.e., a refund receipt) and its execution fails, the deposit is unconditionally burned into `stats.balance.other_burnt_amount` rather than returned to anyone. `Receipt::new_balance_refund` (used by `action_delete_account`) always uses `predecessor_id: "system"` [1](#0-0) , so any beneficiary transfer generated by `DeleteAccount` is treated as a "refund" for this purpose.

### Title
DeleteAccount funds are permanently burned when `beneficiary_id` does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` transfers the deleted account's entire remaining balance to a user-supplied `beneficiary_id` without validating that the account exists, via `Receipt::new_balance_refund`. Because that helper stamps the receipt's predecessor as `"system"`, the runtime treats it as an unconditional "refund" receipt. If the beneficiary account does not exist, `Transfer` fails with `AccountDoesNotExist`, and the runtime's refund-failure path burns the entire deposit instead of returning it to anyone.

### Finding Description
`action_delete_account` computes the deleted account's balance and, if positive, pushes a system-refund receipt to the attacker/user-chosen `beneficiary_id` with no existence check: [2](#0-1) 

`Receipt::new_balance_refund` always sets `predecessor_id: "system"`: [3](#0-2) 

`check_account_existence` rejects a `Transfer` to a nonexistent account unless implicit creation is allowed, and `implicit_creation_allowed` explicitly forbids account creation by refund receipts ("Refund can never create an account"): [4](#0-3) 

This is confirmed by the existing test `refund_may_not_create_universal_account`, which asserts that a refund to a missing account fails with `AccountDoesNotExist` rather than creating the account: [5](#0-4) 

When that failure occurs, `apply_action_receipt` explicitly burns the deposit for any system-predecessor (refund) receipt that fails, instead of routing it anywhere recoverable: [6](#0-5) 

The `beneficiary_id` is fully attacker/user-controlled and reachable through a standard signed transaction (`DeleteAccountAction`) or through a contract's cross-contract promise (`promise_batch_action_delete_account`): [7](#0-6) 

This mirrors the referenced Foundation bug class exactly: a fee/value recipient supplied by an untrusted party can point to an address/account that cannot receive funds, and instead of falling back or refunding the sender, the protocol permanently destroys the value.

### Impact Explanation
Any account holder can delete their own account and specify a `beneficiary_id` pointing to a named account that does not exist (e.g., a typo, an account that was itself deleted earlier in the same or a prior chunk, or one that was never created). The account's entire NEAR balance is unconditionally and irreversibly burned rather than returned to the actor who initiated the deletion or to the deleted account's rightful controller. This is a direct, protocol-level loss of user funds (deflationary supply effect) triggerable by an ordinary unprivileged transaction signer — no validator or node compromise required. Given `DeleteAccount` is also reachable from within a smart contract via `promise_batch_action_delete_account`, a poorly-audited or malicious contract could also cause depositors' funds to be burned this way.

### Likelihood Explanation
High likelihood: this requires only a single ordinary `DeleteAccountAction` transaction (or an equivalent contract-issued promise) with a `beneficiary_id` set to a nonexistent account — trivially reachable by any signer with an existing account, and easily triggered accidentally (typoed or already-deleted beneficiary) as well as maliciously.

### Recommendation
Before creating the beneficiary transfer in `action_delete_account`, validate that `beneficiary_id` refers to an existing account (or otherwise supports implicit-account creation for that transfer). If the beneficiary does not exist, fail the `DeleteAccount` action outright (returning an error such as `AccountDoesNotExist` before any state mutation) rather than emitting a system-refund receipt whose failure silently burns the funds. Alternatively, allow such a refund receipt to fall back to creating the beneficiary account (bypassing the "refund can never create an account" restriction specifically for delete-account payouts) so the tokens are preserved.

### Proof of Concept
1. Create account `alice.near` with balance `N > 0` and no locked stake.
2. Submit a transaction with a single `DeleteAccountAction { beneficiary_id: "definitely-not-an-existing-account.near" }` signed by `alice.near`, targeting `alice.near`.
3. `action_delete_account` removes `alice.near` and enqueues `Receipt::new_balance_refund("definitely-not-an-existing-account.near", N)` (predecessor `"system"`) per `runtime/runtime/src/actions.rs:380-386`.
4. When that receipt executes, `check_account_existence`/`implicit_creation_allowed` reject the transfer since a refund can never create an account, causing the receipt to fail with `AccountDoesNotExist`.
5. `runtime/runtime/src/lib.rs:1047-1054` observes `receipt.predecessor_id().is_system()` and `result.result.is_err()`, and adds the full deposit `N` to `stats.balance.other_burnt_amount` — the funds are gone permanently, credited to no account (test `refund_may_not_create_universal_account` at `runtime/runtime/src/tests/apply.rs:6880-6926` demonstrates the same failure path for a generic balance-refund receipt to a missing account).

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
