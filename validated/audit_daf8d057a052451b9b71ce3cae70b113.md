### Title
Unvalidated `DeleteAccountAction.beneficiary_id` causes permanent, silent burning of an account's entire balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId`; it never checks that the account actually exists. The remaining balance of the deleted account is paid out via a system-generated refund receipt targeting `beneficiary_id`. If that account does not exist, the refund receipt fails, and because refund receipts are explicitly forbidden from creating accounts, the funds are not returned to anyone — they are unconditionally burned. This mirrors the reported Gitcoin bug class: an address field is accepted without existence/liveness validation, and value that should reach a real recipient becomes permanently unrecoverable because the fallback/error path has no way to return it to a valid owner.

### Finding Description
`action_delete_account` computes the deleted account's balance and, instead of transferring it directly, appends a system refund receipt for the beneficiary: [1](#0-0) 

The only validation ever performed on `beneficiary_id` is the generic `AccountId` syntax check quoted in the runtime spec (`InvalidAccountId`); there is no existence check: [2](#0-1) 

The payout is built with `Receipt::new_balance_refund`, which is a `system`-predecessor receipt — i.e. a refund, not an ordinary transfer: [3](#0-2) 

Refund receipts are categorically barred from creating new accounts, regardless of account-id type: [4](#0-3) 

Consequently, when the balance-refund `Transfer` action targets a `beneficiary_id` that does not exist, `check_account_existence` rejects the transfer with `AccountDoesNotExist`, and the refund receipt itself fails: [5](#0-4) 

When a system (refund) receipt's execution fails, the runtime does not retry, re-refund, or hold the value — it unconditionally adds the entire deposit to `other_burnt_amount`, permanently removing it from circulation: [6](#0-5) 

This exact mechanism is confirmed by an existing regression test showing a refund to a non-existent (even syntactically-valid) account fails and does not create the account, and by a comment in the delete-account test suite that explicitly notes: "the beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund [and be burned]": [7](#0-6) [8](#0-7) 

### Impact Explanation
Any unprivileged transaction signer who submits a `DeleteAccountAction` (directly or via a `Delegate`/meta-transaction) with a `beneficiary_id` that is syntactically valid but does not correspond to a live account causes the entirety of their account's remaining native-token balance to be permanently and silently destroyed — the `DeleteAccountAction` itself still reports success, and the loss only becomes visible one block later when the refund receipt fails and is burned instead of paid out. This is a real, protocol-level, irreversible loss of funds (deflationary token burn with no recovery path), directly analogous to the reported class: an address field that is accepted without an existence check leads to funds becoming permanently unrecoverable once the corresponding operation executes.

### Likelihood Explanation
The precondition is trivial to trigger by mistake (a typo'd or freshly-derived-but-unregistered `beneficiary_id`, e.g. an implicit/eth-implicit/named account that was never funded/created), and the protocol performs no existence check at validation or execution time to warn the caller beforehand. The bug is entirely self-inflicted by the account being deleted (the beneficiary is chosen by the same signer/delegate whose account is deleted), so it cannot be weaponized to steal a third party's funds — it only destroys the deleting account's own balance. This limits it to accidental/careless use rather than an attacker-driven exploit against victims, which reduces the practical severity relative to the original report (where an operator's misconfiguration locked funds belonging to many third-party donors).

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` refers to an existing (and, for named accounts, initialized) account, and reject the `DeleteAccountAction` at validation/execution time with an explicit error (e.g. `BeneficiaryAccountDoesNotExist`) if it does not. Alternatively, change the refund path so that a failed balance-refund receipt is retried or credited to a well-known fallback (e.g. treated like a validator/treasury reward) instead of being unconditionally burned, so a bad `beneficiary_id` cannot silently destroy the deleted account's tokens.

### Proof of Concept
1. Create account `alice.near` with balance `B`.
2. `alice.near` submits `DeleteAccount { beneficiary_id: "nonexistent.near" }` (an account that has never been created).
3. The delete succeeds (`alice.near` is removed); the runtime enqueues `Receipt::new_balance_refund("nonexistent.near", B)`.
4. In the next chunk, this system receipt executes `Transfer` to `nonexistent.near`; `check_account_existence` returns `AccountDoesNotExist` because refunds cannot implicitly create accounts (`implicit_creation_allowed` returns `false` for `is_refund == true`).
5. Because the receipt's `predecessor_id` is `system`, the runtime's refund-failure branch adds `B` to `stats.balance.other_burnt_amount` — `B` is permanently burned; `nonexistent.near` is never created, and `alice.near` no longer exists to reclaim the funds.
6. Total supply decreases by `B` with no error surfaced to the original transaction beyond the earlier `SuccessValue` status of the `DeleteAccount` receipt.
