### Title
Unbounded duplicate accumulation in `KVSessionStorage` shop-session-id index leads to permanent DoS of session storage/auth for a shop - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends a session id to the shop's session-id index on every `storeSession` call without checking whether that id is already present in the index. Because `storeSession` (and therefore `addShopIds`) can be invoked repeatedly for the same session id — during normal token-exchange/OAuth re-authentication flows, and more aggressively under Cloudflare KV's documented eventual consistency — the per-shop id array grows with duplicate entries indefinitely. This mirrors the reported Bribe.sol pattern: an accumulator (`totalVoting`) is incremented on every "deposit"-like operation but is never deduplicated/decremented to reflect that the same underlying position was already accounted for, and the resulting value drift eventually causes irreversible loss (here: storage that can grow past KV's value-size limits, permanently breaking session read/write for that shop).

### Finding Description
`KVSessionStorage.storeSession` always calls `addShopIds(session.shop, [session.id])` after writing the session record: [1](#0-0) 

`addShopIds` simply concatenates the new id(s) onto whatever list is already stored for the shop, with no check for existing membership: [2](#0-1) 

`removeShopIds` does filter duplicates out correctly on delete, but only once `deleteSession` is explicitly called for that id: [3](#0-2) 

The session-storage consumers (`performTokenExchange` in `shopify-app-express`, and the equivalent flows in `shopify-app-remix`/`shopify-app-react-router`) call `storeSession` any time a valid, active session cannot be found for the shop/user, which happens whenever the offline/online token is missing or has expired: [4](#0-3) 

Because `storeSession` is triggered from a re-derived (`getOfflineId`/`getJwtSessionId`) but always identical id for the same shop/user, repeated invocations — whether from normal repeated re-auth, or from races caused by KV's eventual consistency (a `loadSession` immediately after a `storeSession` on a different edge node can still read "not found," causing another concurrent token-exchange + `storeSession`) — each append the same id again. There is no dedup, size cap, or idempotency guard in `addShopIds` itself.

### Impact Explanation
The `shop:<shop>` KV entry is a JSON array that grows monotonically with duplicate ids and is never pruned except by an exact-match `deleteSession`/`deleteSessions` call. Cloudflare KV values are capped (documented 25 MiB limit); once the shop's id-index value approaches/exceeds that limit, subsequent `namespace.put` calls in `addShopIds`/`storeSession` will fail, and `findSessionsByShop` will return a bloated/duplicated list. This permanently degrades or breaks:
- future `storeSession` calls for that shop (auth/token-exchange flow errors out, matching the "DoS of an auth handler" impact class),
- `findSessionsByShop`-driven bulk session invalidation (e.g. on `app/uninstalled` webhook), since it duplicates entries and can throw when writing back a shrunk list once it exceeds size limits.

This is directly analogous to the Bribe.sol issue: an accounting value (`totalVoting` / the shop id index) is incremented on every call of a normal, unprivileged action without a corresponding correctness check, and repeated benign or adversarial invocation inflates it until the system can no longer correctly account for/serve the underlying data, resulting in a permanent, unrecoverable degradation (frozen rewards there; frozen session storage/auth here).

### Likelihood Explanation
Reachable by a single unprivileged actor (a merchant/user of the installed app) without any secret or privileged access: simply causing repeated token-exchange calls for the same shop (e.g., multiple browser tabs/instances hitting the app around session expiry, or automated rapid app reloads) is enough to trigger the race due to KV's documented eventual consistency, and nothing in the code prevents or bounds the resulting duplication. No cryptographic material needs to be forged and no MITM is required. Likelihood is moderate: it requires either sustained normal usage over a long period or deliberately generated concurrent requests exploiting the KV replication delay window, but the `KVSessionStorage` adapter is a shipped, first-party package intended for production use on Cloudflare Workers, where this consistency behavior is expected.

### Recommendation
In `addShopIds`, deduplicate before writing (e.g., use a `Set` or check `shopIds.includes(id)` before appending), and consider capping/pruning the per-shop id list or moving to a data structure that supports safe idempotent membership updates (e.g., storing session ids as individual KV keys under a shop-prefixed namespace and using `list({prefix})` instead of a single growing JSON array).

### Proof of Concept
1. Configure an embedded app to use `KVSessionStorage` with `future.tokenExchange` enabled.
2. Simulate two concurrent requests for the same shop where `loadSession(offlineId)` both return `undefined` (representable in tests by directly invoking `storeSession` twice in a row for the same `session.id`/`shop`, as would happen when Cloudflare KV read-after-write consistency lags behind a concurrent write from a sibling edge location):
```ts
const storage = new KVSessionStorage(namespace);
const session = new Session({id: 'offline_shop.myshopify.com', shop: 'shop.myshopify.com', ...});
await storage.storeSession(session);
await storage.storeSession(session); // simulate a second concurrent/duplicate token-exchange
const raw = await namespace.get<string[]>('shop:shop.myshopify.com', 'json');
console.log(raw); // ['offline_shop.myshopify.com', 'offline_shop.myshopify.com'] -- duplicate entries accumulate
```
3. Repeating step 2 in a loop demonstrates the array growing without bound, eventually exceeding KV's per-value size limit and causing `addShopIds`/`storeSession` to throw for that shop going forward.

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async removeShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(
      key,
      JSON.stringify(shopIds.filter((id) => !ids.includes(id))),
    );
  }
