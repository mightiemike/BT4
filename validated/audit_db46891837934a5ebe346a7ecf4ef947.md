## Title
Hardcoded ETH-implicit global-contract hash is used unchecked to bind new accounts, risking permanent loss of wallet functionality if it drifts from the deployed WASM - (File: `runtime/near-wallet-contract/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
This is the same bug class as the Uniswap "wrong init code hash" finding: a critical hash constant that is supposed to identify a specific piece of deployed code is hand-copied as a literal instead of being derived/verified from the actual artifact, and is then used, unchecked, to bind new accounts to that code. If the literal ever drifts from the real deployed global contract (e.g. the embedded `wallet_contract_mainnet.wasm`/`wallet_contract_testnet.wasm` is rebuilt/updated but the hardcoded byte array is not, exactly the kind of manual-sync mistake the Uniswap report describes), every newly created ETH-implicit account is permanently bound to a contract that does not exist in state, and the deposited funds in that account become unusable.

### Finding Description
`eth_wallet_global_contract_hash` in `runtime/near-wallet-contract/src/lib.rs` returns a **hardcoded** `CryptoHash` literal for `chains::MAINNET`/`chains::TESTNET`, unlike the `LOCALNET` branch which derives the hash dynamically from the embedded WASM (`*LOCALNET.read_contract().hash()`): [1](#0-0) 

This literal is consumed directly, without any existence check, by `action_implicit_account_creation_transfer` when creating a new ETH-implicit account: [2](#0-1) 

Compare this to the normal `UseGlobalContract` action path, which does validate that the referenced global contract actually exists in the trie before binding an account to it (`state_update.contains_key(&key, ...)` → `GlobalContractDoesNotExist` on failure): [3](#0-2) 

But ETH-implicit account creation bypasses this safety check entirely — it unconditionally sets `AccountContract::Global(global_contract_hash)` using the hardcoded constant. Later, when resolving the contract for a function call, `GlobalContractAccessExt::hash` for the `CodeHash` variant simply returns the stored hash as-is with no verification it maps to real code in the trie: [4](#0-3) 

So if `eth_wallet_global_contract_hash` for mainnet/testnet ever fails to match the actual global contract code hash deployed on-chain (a plausible outcome any time the embedded WASM file is rebuilt without also recomputing and updating this literal — precisely the class of mistake in the referenced Uniswap V2 report, where a stale/incorrect hardcoded hash silently produced a wrong derived value), the runtime will accept the account creation, but subsequent lookups for the actual code will fail to find any contract at that hash.

### Impact Explanation
Every ETH-implicit account created while the constant is stale gets `AccountContract::Global(<nonexistent-hash>)`. Because ETH-implicit accounts:
- can never receive a full access key (only the Wallet Contract can authorize actions for them),
- can only be operated through the Wallet Contract's `rlp_execute` logic,

a missing/mismatched global contract code means the account can never execute any transaction, add a relayer key, transfer out funds, or be deleted. Any NEAR sent to such accounts (the whole point of ETH-implicit accounts — bridging Ethereum-style wallets to NEAR) becomes permanently frozen, matching the "permanently frozen funds" impact category. This also produces state divergence risk between nodes if some validators/RPC nodes are running builds with different (correctly vs. incorrectly synced) constant values, since account state (`AccountContract::Global(hash)`) is consensus-critical.

### Likelihood Explanation
This requires no attacker action — it is a systemic risk triggered purely by an engineering process error (rebuilding/updating the embedded wallet contract WASM without recomputing the hardcoded `eth_wallet_global_contract_hash` constant for `MAINNET`/`TESTNET`), which is exactly analogous to how the Uniswap library shipped a stale/incorrect init code hash literal. Given there is no automated on-chain (or even build-time) assertion tying `eth_wallet_global_contract_hash` to the currently embedded/deployed global contract hash, and the account-creation path deliberately skips the existence check that the `UseGlobalContract` action otherwise enforces, the class of bug is directly reachable the next time the Wallet Contract WASM is upgraded.

### Recommendation
- Add a build-time or startup assertion that `eth_wallet_global_contract_hash(chain_id)` equals the hash of the actually embedded/expected deployed global contract WASM for `MAINNET`/`TESTNET`, the same way `LOCALNET` already derives it dynamically instead of hardcoding it.
- Have `action_implicit_account_creation_transfer` perform the same existence check as `use_global_contract` (verify the `GlobalContractCode` trie key exists) before binding a brand-new ETH-implicit account to `AccountContract::Global(global_contract_hash)`, so any future drift fails loudly (or is refused) instead of silently producing unusable accounts.

### Proof of Concept
1. Suppose the embedded `res/wallet_contract_mainnet.wasm` is updated (new build) but the hardcoded byte array in `eth_wallet_global_contract_hash` (`chains::MAINNET` arm) is not updated to the new hash — analogous to the Uniswap library shipping an outdated/incorrect init code hash after Uniswap V2 was redeployed.
2. A user sends a `Transfer` to a fresh ETH-implicit account id (`0x...`). `action_implicit_account_creation_transfer` creates the account with `AccountContract::Global(<stale-hash>)`, per `runtime/runtime/src/actions.rs:255-269`.
3. No check is performed that a `GlobalContractCode` entry for `<stale-hash>` exists in the trie (contrast with `use_global_contract`'s `contains_key` check in `runtime/runtime/src/global_contracts.rs:84-90`).
4. Any subsequent `rlp_execute` FunctionCall to that account resolves via `RuntimeContractIdentifier::resolve`/`GlobalContractAccessExt::hash`, which returns the stale hash unconditionally (`runtime/runtime/src/contract_code.rs:92-95`); actually fetching the code then fails because no such contract is stored, and the call cannot succeed.
5. The account has no access key and no working code, so the deposited NEAR is permanently unrecoverable.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }
