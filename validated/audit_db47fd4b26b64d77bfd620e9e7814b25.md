## Title
Missing verification that session-token `dest` matches the caller-supplied `shop` in `tokenExchange` - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`shopify.auth.tokenExchange()` accepts `shop` and `sessionToken` as two independent parameters. It calls `decodeSessionToken()` only to confirm the token's signature/audience/expiry are valid, but it never checks that the token's `dest` claim (the shop the token was actually issued for) matches the `shop` value supplied by the caller. Every other session-token consuming path in this codebase (the admin `authenticate()` flows and `getCurrentSessionId`) strictly derives `shop` *from* the verified token's `dest`, never from an independently supplied value, which is exactly the invariant `tokenExchange` fails to enforce.

### Finding Description
In `token-exchange.ts`, the flow is: [1](#0-0) 

`decodeSessionToken(config)(sessionToken)` is awaited only for its side effect of throwing on an invalid token; its return value (the payload, containing `dest`) is discarded: [2](#0-1) 

The `shop` argument is instead sanitized independently and used to build the outbound request URL and the resulting `Session.shop`: [3](#0-2) 

Contrast this with the "correct" path used everywhere else in the library, where `shop` is *never* taken from user input once a session token is present — it is derived strictly from the verified token's `dest`: [4](#0-3) [5](#0-4) 

The library's own documentation for `tokenExchange` instructs developers to source `shop` from the request's query string (attacker/browser-controlled), separately from the session token: [6](#0-5) 

This mirrors the reported bug class exactly: a validation invariant ("the shop identity must come from/agree with the verified token") is enforced in the primary/registration-equivalent code paths but is missing in a secondary, semantically-equivalent function that is part of the same public API surface (`tokenExchange`, and the sibling `migrateToExpiringToken`/`refreshToken`, which have the identical pattern of using a bare `shop` string to build the request URL without any token-binding check).

### Impact Explanation
Because `sanitizeShop` restricts `shop` to `*.myshopify.com`/`*.shopify.com`/etc. domains, this is not an arbitrary-host SSRF, but it does break the shop/session binding: a caller that follows the documented pattern (using `req.query.shop`) can present a validly-signed session token for shop A together with an attacker-chosen `shop=B` value. `tokenExchange` will happily perform the OAuth token-exchange POST against `https://B.myshopify.com/admin/oauth/access_token` using shop A's session token as `subject_token`, and — if the request succeeds — will construct and return/store a `Session` whose `shop` field is `B`, i.e., a cross-tenant session-storage entry keyed to the wrong shop while never having cryptographically confirmed that the presented token actually belongs to shop B. This is a session-storage integrity/cross-tenant issue: the library itself provides no defense-in-depth check to prevent shop/token confusion, unlike the rest of its own session-token handling code.

### Likelihood Explanation
Reachable from a single, unprivileged actor: any user of an embedded app with a browser can manipulate the `shop` query parameter of a request while the app's App Bridge session token (bound to their real shop) is attached, if the app implements `tokenExchange` per the shipped documentation example. No secrets, MITM, or privileged access are required — only the ability to send a normal HTTP request with an attacker-controlled `shop` value.

### Recommendation
In `tokenExchange` (and equivalently in `refreshToken`/`migrateToExpiringToken` if they accept independently-supplied `shop`), capture the decoded payload and assert that `new URL(payload.dest).hostname` equals the sanitized `shop` argument before proceeding, throwing `InvalidJwtError`/`InvalidOAuthError` on mismatch — mirroring the pattern already used in `authenticate.ts` and `session-utils.ts`, and update the documentation example to derive `shop` from the token's `dest` rather than from `req.query.shop`.

### Proof of Concept
1. App implements `/auth` per the documented example: `const shop = shopify.utils.sanitizeShop(req.query.shop, true);` then `shopify.auth.tokenExchange({ sessionToken, shop, requestedTokenType })`.
2. A user of shop `a.myshopify.com` loads the embedded app and obtains a legitimate App-Bridge session token whose `dest` is `https://a.myshopify.com`.
3. The user (or a script running in their session) sends `GET /auth?shop=b.myshopify.com` with `Authorization: Bearer <token-for-a>`.
4. `tokenExchange` decodes/verifies the token (valid signature/audience), ignores that `payload.dest` is `a.myshopify.com`, and issues `POST https://b.myshopify.com/admin/oauth/access_token` with `subject_token` = the shop-A token, then builds/stores a `Session` with `shop: "b.myshopify.com"`.
5. No point in the library's `tokenExchange` code path checks `payload.dest === shop`, unlike `authenticate.ts`'s `getSessionTokenContext`, which never allows such mismatch.

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
  };

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
