## Title
Missing declared-class validation in Starknet OS `replace_class` syscall causes execution divergence from blockifier — (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/deprecated_execute_syscalls.cairo` and `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The Ref.Finance incident stemmed from a bug introduced in a contract "patch" — a mismatch between the intended upgraded logic and what was actually deployed/executed, which attackers exploited by driving the contract into a state its logic did not correctly handle. The sequencer analog is a divergence between two supposedly-equivalent implementations of the `replace_class` syscall: the Rust blockifier (the sequencer's actual execution engine) enforces that a contract may only replace its class hash with a hash that has been previously declared, while the Cairo Starknet OS (which independently re-executes transactions to produce the proven state transition) does not enforce this check at all.

### Finding Description
The Rust blockifier's `replace_class` implementation explicitly validates the target class hash before applying the state change: [1](#0-0) 

Tests confirm this is a hard requirement — calling `replace_class` with an undeclared class hash, or attempting to replace a Cairo1 (V1) class with a Cairo0 (V0) class, is rejected: [2](#0-1) [3](#0-2) 

However, the Cairo implementation of the same syscall inside the Starknet OS program — the code that independently re-executes transactions to compute the block's committed state and is proven on L1 — performs no such validation. Both the deprecated (Cairo0) and current syscall execution paths simply overwrite the contract's class hash in `contract_state_changes` unconditionally: [4](#0-3) [5](#0-4) 

The OS code even carries an explicit acknowledgment of the missing check: [6](#0-5) 

Because the OS is a from-scratch Cairo re-implementation of the state transition function (it does not simply trust the blockifier's precomputed state diff for syscall outcomes — it independently computes them from transaction calldata via `dict_update`), any transaction path reaching `replace_class` with an undeclared (or a downgraded V1→V0) class hash will succeed silently in the OS while the blockifier rejects/reverts the same call. This is directly reachable by an unprivileged transaction sender: any contract can expose an entry point that calls `replace_class_syscall` with attacker-controlled input (as seen in the feature-contract test helper), and any account can invoke it via a normal transaction: [7](#0-6) 

### Impact Explanation
This is an execution-logic divergence between the sequencer's blockifier (used to build/validate blocks) and the Starknet OS (used to produce the proven state commitment). A transaction that calls `replace_class` with an undeclared class hash would be reverted by blockifier but accepted (state mutated) by the OS. Since the OS's output feeds the committed state root/proof that is ultimately verified on L1, this can lead to a wrong committed state root and honest-node divergence: any node that trusts the OS-computed state (or a prover generating proofs from the OS logic) can produce a result inconsistent with what the actual sequencer/blockifier would compute for the same block, and a contract could end up pointing to a class hash with no backing declared code (unauthorized/undefined contract logic at that address).

### Likelihood Explanation
The bug is trivially reachable: it requires only a normal contract exposing a call to `replace_class_syscall`/`ReplaceClass` and any unprivileged transaction invoking it with an undeclared or otherwise-invalid class hash — no special privileges, no malicious operator, and no non-standard component are needed. The lack of the check is explicitly documented via a TODO in the codebase, confirming it is a known, currently-unaddressed gap rather than a hypothetical one.

### Recommendation
Add the same declared-class (and V1/V0 downgrade) validation performed in the Rust blockifier's `replace_class` handling into the Cairo OS's `execute_replace_class` implementations (both `deprecated_execute_syscalls.cairo` and `syscall_impls.cairo`), asserting that the requested `class_hash` exists in `contract_class_changes`/declared-classes state before applying the state entry update, and rejecting (reverting) the syscall otherwise, matching blockifier's error semantics exactly.

### Proof of Concept
1. Deploy a Cairo1 contract exposing an entry point that calls `replace_class_syscall(class_hash)` with a caller-supplied `class_hash` (pattern shown in `test_contract.cairo`'s `test_forbidden_syscall_in_virtual_mode`/`test_replace_class`).
2. Submit a transaction invoking this entry point with a class hash that has never been declared on-chain.
3. Under blockifier (sequencer execution), the syscall handler calls `get_compiled_class`, which fails, causing the syscall/transaction to revert — confirmed by `syscall_tests/replace_class.rs::undeclared_class_hash`.
4. Under the Starknet OS's Cairo `execute_replace_class` (both `deprecated_execute_syscalls.cairo:307-329` and `syscall_impls.cairo:881-920`), no such check exists — the state entry for the contract is unconditionally updated with the undeclared class hash and execution continues successfully, diverging from step 3's outcome.

    contract_address, syscall_ptr: ReplaceClass*

    alloc_locals;
    let class_hash = syscall_ptr.class_hash;

    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(

    );
    assert [revert_log] = RevertLogEntry(selector=CHANGE_CLASS_ENTRY, value=state_entry.class_hash);
    let revert_log = &revert_log[1];

    return ();
}
