## Analog Found: Wallet Contract's `has_in_flight_tx` Flag Can Get Permanently Stuck, Freezing Funds

### Title
Wallet Contract's in-flight transaction gate can be permanently stuck `true` on callback failure, freezing all future transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The external report describes a state-gating modifier (`onlyWhenVaultIsOn`) that blocks a legitimate, unprivileged user action (`redeemRewardsGame`) once the contract enters an "off" state, with no path to recover. The nearcore analog is the `WalletContract::has_in_flight_tx` boolean gate: `rlp_execute` [1](#0-0)  immediately refuses to process any further transaction from the account owner whenever this flag is `true`, exactly mirroring the vault's binary on/off gate blocking a rightful redeem call.

### Finding Description
The `WalletContract` struct declares the invariant explicitly: `has_in_flight_tx` must be `true` exactly while a promise is outstanding, and `false` otherwise [2](#0-1) . Every code path that resets the flag to `false` does so as the *first statement* inside a `#[private]` callback — `address_check_callback` [3](#0-2) , `nep_141_storage_balance_callback` [4](#0-3) , `rlp_execute_callback` [5](#0-4) , and `ban_relayer` [6](#0-5) .

These callbacks are scheduled with hard-coded, statically-sized gas budgets computed at the call site: `RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, and `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` [7](#0-6) . If the actual callback receipt fails for any reason — e.g., insufficient gas because the budget under-provisions for a larger-than-expected `target` account id, JSON payload, or attached `action.gas()`, or any other unexpected VM-level `FunctionCallError` — NEAR receipt execution is atomic: a failed function-call receipt commits **no** state changes at all. Since the flag-reset statement is inside the very receipt that fails, `has_in_flight_tx` never gets reset back to `false`.

Once stuck at `true`, every subsequent call to `rlp_execute` — the sole entry point for the ETH-implicit account owner to move funds or interact with any contract through this wallet — is short-circuited at the very first check and returns an error response without doing anything [8](#0-7) . There is no other method exposed to the account owner to reset the flag (the callbacks are `#[private]`, only callable by the contract itself via promise resolution).

### Impact Explanation
This directly parallels the reported bug class: a single state-gate boolean, once flipped by an edge-case failure, permanently denies the legitimate signer/owner the ability to perform any further protocol operation through the account — a durable denial of service that freezes the account's $NEAR (and any assets reachable only via the wallet contract, e.g. NEP-141 tokens) with no recovery path short of a new deployment. This satisfies the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Reachable by an ordinary, unprivileged transaction/RPC path: any relayer or the account owner itself submits an `rlp_execute` call (the only mutating entrypoint). The trigger condition — a callback receipt failing due to gas under-provisioning or any other runtime-level failure between successful promise scheduling and the reset statement's execution — is a narrow edge case dependent on exact gas accounting margins, so likelihood is plausible but not trivially reproducible without crafting inputs that push the callback's actual execution cost above its statically reserved budget.

### Recommendation
- Do not gate a stuck-forever invariant on a single receipt's success; use a mechanism resilient to partial failure, e.g. reset the flag in a way that is guaranteed to run regardless of the wrapped action's outcome (which the current design already partially achieves for `PromiseResult::Failed` inside the *action* promise, but not for failure of the *callback receipt itself*).
- Add a generous safety margin / dynamically-computed upper bound to the static gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) so that the callback that resets `has_in_flight_tx` cannot itself run out of gas.
- Provide an owner-callable recovery method (e.g., a full-access-key-gated `force_clear_in_flight` or a timeout-based auto-clear keyed off block height) so a stuck flag can be cleared without redeploying the contract.

### Proof of Concept
1. Deploy the wallet contract for an ETH-implicit account as in `integration-tests/src/tests/features/wallet_contract.rs` [9](#0-8) .
2. Craft an RLP-encoded Ethereum transaction whose target/action forces the ERC-20 transfer path, which schedules `nep_141_storage_balance_callback` with a fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget [10](#0-9) .
3. Arrange for the callback's actual execution cost to exceed the statically reserved gas (e.g., via a large `receiver_id`/large deposit args or by racing wasm compilation costs at the edge of the budget), causing the callback receipt itself to fail with an out-of-gas error.
4. Observe that `has_in_flight_tx` remains `true` in contract state (because the failed receipt rolled back the `self.has_in_flight_tx = false` write).
5. Any subsequent `rlp_execute` call from the legitimate owner/relayer now unconditionally returns `"transaction already in progress, please try again later"` [8](#0-7)  forever, with the account's funds inaccessible through the wallet contract.
