### Title
Asymmetric-rounding index update lets `accrue()` permanently strand lender interest via a "clock advanced only on change" invalidation - (File: `mainnet/contracts/vault/v0-vault-usdh.clar` and equivalent `v0-vault-*.clar` vaults)

### Summary
`accrue()` only refreshes `last-update` when at least one of the two indices (`index`, borrower debt index, or `lindex`, lender liquidity index) actually changes, but it computes those two indices with opposite rounding directions. Because the smaller-magnitude liquidity-rate multiplier can round down to "no change" while the debt index still changes, `last-update` gets reset to the current time and the liquidity index's un-accrued time window for that period is permanently discarded — lenders earn less than the model implies, in the same "call `addInterest`/`accrue` infrequently → interest under-accrual" fashion described in the source Fraxlend report, but mechanically realized as a clock-advanced-only-on-change bug rather than a linear-vs-compound issue.

### Finding Description
Each vault computes two multiplicative indices from a single `interest-rate()` value:

- Debt index multiplier rounds **up**: [1](#0-0) 

- Liquidity index multiplier rounds **down**: [2](#0-1) 

Both share the same `calc-multiplier-delta` helper, whose only difference is the `round-up` flag: [3](#0-2) 

`accrue()` then updates `index` and `lindex` independently, but advances the shared `last-update` timestamp **only if at least one of them actually changed** (using an `or`, not requiring both to change): [4](#0-3) 

Because `next-index` rounds up and `next-liquidity-index` rounds down from the exact same `time-delta`/`rate`, there exist small time deltas (e.g. frequent small calls to `accrue`, or `system-borrow`/`system-repay`, which themselves call `accrue()` before mutating state) for which `next` (debt index) differs from `idx` but `nliq` (liquidity index) rounds back down to the same value as `lidx`. In that case the `if (or ...) (var-set last-update stacks-block-time) false)` branch still fires (because the debt-index changed), resetting `last-update` to the current block time even though the liquidity index made no progress. The elapsed time that should have counted toward the liquidity index's next `time-delta` is discarded — it is never reflected in the `time-delta` used by any future call to `next-liquidity-index`, since that function always computes `(- stacks-block-time (var-get last-update))` off the now-advanced clock. This is a clean instance of "clock advanced only on change" invalidation: the shared clock (`last-update`) is invalidated (fast-forwarded) by an event tied to one index's state, while a second dependent value (the liquidity index) that did not actually change is silently treated as up to date.

This directly parallels the reported Fraxlend root cause — `addInterest` under-accruing interest when not called with sufficiently fine granularity — but here it is not a compounding-frequency artifact; it is a permanent loss caused by the rounding-asymmetric multiplier combined with a single shared "did anything change" gate for the clock reset. Every borrow/repay/accrue call in the affected window (any caller can trigger `accrue()` — it is a `define-public` with no `check-caller-auth` gate at all) can trigger this reset, so on protocols/pairs where debt-index granularity is finer than liquidity-index granularity (any time small nominal rates or short deltas are common, e.g., low-utilization vaults or frequent small operations), the pattern recurs on essentially every call, continuously shaving lender-side accrual.

### Impact Explanation
This causes a High-severity impact under "theft/permanent freezing of unclaimed yield": lenders (share holders of `zft`) permanently lose a portion of the interest they are economically entitled to, since the discarded time delta for the liquidity index is never recovered — the clock has already moved forward for future calculations. Because `accrue()` is public and callable by anyone with no cooldown, an attacker (or just organic frequent activity) can repeatedly trigger many such micro-accrual calls, systematically depressing the effective liquidity rate compared to what utilization/rate curves promise, without ever compromising the borrow side (whose rounding direction favors the protocol/borrowers being charged, not under-charged). This does not require any privileged access, DAO action, or oracle manipulation — it is purely a function of call cadence and the intrinsic rounding asymmetry in `calc-multiplier-delta`.

### Likelihood Explanation
Likelihood is high in low-utilization or slow-moving vaults where nominal per-call rates are small: the debt-index rounding-up bias makes it far more likely to detect a nonzero delta than the liquidity-index rounding-down bias for the same `time-delta`. Any economic actor calling `system-borrow`/`system-repay`/`accrue` at a moderate cadence (which is normal usage, not an attack precondition) will trigger this divergence repeatedly over the vault's lifetime, and no explicit user action beyond ordinary protocol interaction is required.

### Recommendation
Do not gate the shared `last-update` timestamp on a combined `or` of two independently-rounded indices. Either:
1. Maintain separate `last-update-borrow` / `last-update-liquidity` timestamps advanced independently for each index's own change condition, or
2. Always advance `last-update` unconditionally each time `accrue()` runs (removing the "only on change" gate entirely) so that no index's un-rounded time contribution is ever silently dropped, or
3. Use identical (not opposite) rounding direction for both multipliers, or accumulate the discarded remainder rather than resetting the clock when only one index changed.

### Proof of Concept
1. Vault has non-trivial `principal-scaled` and `total-borrowed` so utilization > 0, and `interest-rate()` returns a rate small enough that, at low utilization, `calc-liquidity-rate` (which also multiplies by `util-pct` and `(1 - reserve-factor)`) yields a materially smaller number than the raw borrow rate: [5](#0-4) .
2. Caller repeatedly calls `system-borrow`/`system-repay` (or bare `accrue`) at short intervals. Each call computes `next-index` (rounds up) and `next-liquidity-index` (rounds down) from the same `time-delta` via `mul-div-up`/`mul-div-down` respectively: [6](#0-5) .
3. For a range of small `time-delta` values, `next` (debt index) ≠ `idx` (because rounding up crosses an integer boundary sooner) while `nliq` == `lidx` (rounding down stays at the same integer).
4. Inside `accrue()`, the guard `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` evaluates true solely because of the debt-index change, so `last-update` is reset to `stacks-block-time`: [7](#0-6) .
5. The liquidity-index's un-rounded partial time contribution for that interval is lost forever; the next `next-liquidity-index` call computes `time-delta` from the new (post-reset) `last-update`, never recovering the discarded interval. Repeating steps 2-4 across many calls compounds the shortfall, permanently reducing the yield realized by lenders versus the nominal rate curve, mirroring the underlying-report's quantified gap between infrequent vs. frequent accrual (e.g., ~4-10% shortfall magnitude class), but here caused by clock-reset asymmetry rather than pure linear-accrual granularity.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
