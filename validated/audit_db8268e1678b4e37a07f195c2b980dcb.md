## Finding: Unbounded gzip decompression in RPC declare-transaction path

### Title
Denial-of-service via unbounded gzip decompression of user-supplied Cairo0 program in RPC declare transaction handling - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The `apollo_rpc` crate decompresses the attacker-controlled `program` field of a Cairo0 (`DeprecatedContractClass`) declare transaction with no bound on the size of the decompressed output, unlike every other decompression path in this codebase. This is the same bug class as CVE-2026-22776 (cpp-httplib): compressed input size is limited, but the resulting decompressed buffer is not, allowing a "zip bomb" to exhaust memory with a small payload.

### Finding Description
`decompress_program` reads the whole gzip stream into an unbounded `Vec<u8>` via `read_to_end`, with an explicit `// TODO(dan): add time and size limits.` marker acknowledging the gap: [1](#0-0) 

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which converts a client-submitted, base64+gzip-encoded `compressed_program` field of a Declare V1 (Cairo0) transaction before it is forwarded (e.g., to the gateway or used for RPC-side processing): [2](#0-1) 

This stands in contrast to every other decompression entry point in the codebase, all of which enforce a hard cap on decompressed size:
- The Sierra-program decompression path used by the gateway explicitly bounds decompression with `.take(max_size + 1)`: [3](#0-2) 
- The p2p class converter uses the same size-limited helper with an explicit 4MB cap: [4](#0-3) 
- Storage-layer decompression uses `zstd::bulk::decompress(data, MAX_DECOMPRESSED_SIZE)` with a fixed 256MB ceiling: [5](#0-4) 
- The HTTP server itself was hardened against exactly this bug class, wrapping decompression in a body-limited layer with a comment referencing zip bombs: [6](#0-5) 

`decompress_program` is the one path that was missed.

### Impact Explanation
An unprivileged client submitting a Declare V1 transaction to the RPC node's `add_declare_transaction` handling path can supply a small, highly-compressible gzip payload as the Cairo0 `program`. Because there is no cap on decompressed size, a compact payload can expand to a very large in-memory buffer (classic gzip bombs achieve compression ratios in the thousands), exhausting the RPC process's memory and causing it to crash or become unresponsive, denying service for legitimate transaction submission/serving on that node.

### Likelihood Explanation
The vulnerable code path is reached directly by any external caller submitting a legacy (Cairo0) declare transaction; no special privileges, prior state, or race conditions are required. Given that all sibling decompression call sites already enforce size limits, this is a straightforward oversight rather than a defense-in-depth gap, making exploitation trivial with a single crafted request.

### Recommendation
Bound `decompress_program`'s output the same way `decode_and_decompress_with_size_limit` does elsewhere in the codebase — e.g., wrap the `GzDecoder` read with `.take(max_size + 1)` and reject the input if the resulting size exceeds the configured maximum (mirroring `crates/starknet_api/src/compression_utils.rs`), then reuse that shared helper instead of the ad hoc unbounded decompression in `apollo_rpc`.

### Proof of Concept
1. Construct a `program.json`-equivalent JSON body of arbitrary large size (e.g., repeated data), gzip-compress it (achieving a small compressed size, e.g., a few KB) and base64-encode it.
2. Submit a JSON-RPC `starknet_addDeclareTransaction` (or any endpoint constructing a `BroadcastedDeclareV1Transaction`) with this payload as the `contract_class.program` field.
3. The RPC node calls `user_deprecated_contract_class_to_sn_api` → `decompress_program`, which fully decompresses the payload into memory with no size check, consuming resources proportional to the (attacker-chosen) decompressed size rather than the small compressed size accepted by upstream body-size limits. fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}

pub(crate) const MAX_DECOMPRESSED_SIZE: usize = 1 << 28; // 256 MB
// The compression level to use. Higher levels are slower but compress better.
const COMPRESSION_LEVEL: i32 = zstd::DEFAULT_COMPRESSION_LEVEL;

/// Returns the compressed data in a vector.
///
/// # Arguments
/// * data - bytes to compress.
///
/// # Errors
/// Returns [`std::io::Error`] if any read error is encountered.
pub fn compress(data: &[u8]) -> Result<Vec<u8>, std::io::Error> {
    zstd::bulk::compress(data, COMPRESSION_LEVEL)
}

/// Serialized and then compress object.
///
/// # Arguments
/// * object - the object to serialize and compress.
///
/// # Errors
/// Returns [`StorageSerdeError`] if any error is encountered in the serialization or compression.
pub fn serialize_and_compress(object: &impl StorageSerde) -> Result<Vec<u8>, StorageSerdeError> {
    let mut buf = Vec::new();
    object.serialize_into(&mut buf)?;
    Ok(compress(buf.as_slice())?)
}

/// Decompress data and returns it as bytes in a vector.
///
/// # Arguments
/// * data - bytes to decompress.
///
/// # Errors
/// Returns [`std::io::Error`] if any read error is encountered.
pub fn decompress(data: &[u8]) -> Result<Vec<u8>, std::io::Error> {
    zstd::bulk::decompress(data, MAX_DECOMPRESSED_SIZE)
}
