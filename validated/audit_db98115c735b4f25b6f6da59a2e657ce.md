### Title
Silent loss of tombstone (zero-lamport tombstone) records during ancient-slot squashing can resurrect logically-dead accounts - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
The Halborn report describes a signature-replay bug where a previously-used, now-superseded authorization (`Signature`) could be replayed to resurrect a *revoked* state (a previously-revoked TSS key becomes valid again) because the contract never recorded that the signature/state-transition had already been consumed. The underlying bug class is: **a record that logically supersedes/kills an older piece of state is not durably and unconditionally enforced, so the old state can become "live" again.**

In `agave`'s AccountsDB, the analogous mechanism is the "tombstone" — a zero-lamport, single-ref marker that records that a pubkey's account has died and must not be treated as alive when its storage is later rewritten (shrunk or ancient-combined). If a tombstone fails to propagate/carry forward during the ancient-storage squash path, an old (already-dead) account version can silently become reachable again, i.e. "resurrected," which is a stale/wrong-version account load and a capitalization/hash divergence bug class — the closest legitimate in-scope analog to "replaying" a revoked credential.

### Finding Description
`AccountsDb` uses per-slot storage rewriting (shrink and ancient-slot combining/squashing) to compact accounts files. When an account is found to be dead (zero lamports, single reference) during collection for shrink/squash, it is turned into a "tombstone" that must be preserved so the dead state is not lost when the storage is rewritten — otherwise a stale, previously-superseded (but still physically present in an older, not-yet-dropped storage) version of the account could become the "latest" visible version again. Existing tests explicitly guard against this resurrection scenario:

- `test_shrink_does_not_resurrect_dead_account` [1](#0-0)  asserts that after clean reclaims an older slot's account version and the account subsequently dies, a later shrink of the storage that still physically holds the reclaimed data must not bring it back to life.
- `test_accounts_clean_after_snapshot_restore_then_old_revives` [2](#0-1)  is a regression test named explicitly around "old revives" — verifying that after a snapshot round-trip, a pubkey's earlier value does not resurface once its later, dead state was purged.

The ancient-slot squash path (`finish_combine_ancient_slots_packed_internal`) collects a `tombstones_to_carry_forward` list per slot being squashed and only defends the invariant that this list must be empty for ancient squashing with a **`debug_assert!`**, not a `require`/panic that is also enforced in release builds: [3](#0-2) 

The comment states plainly: "The squash write path has no tombstone handling, so a non-empty list here would be silently lost." In other words, the code acknowledges that if this invariant is ever violated, the tombstone (the "revocation" record for a dead account) is *silently dropped* rather than causing a hard failure — and because `debug_assert!` compiles to a no-op in release builds, a release validator would take this silent-loss path instead of crashing loudly, exactly the way the Gateway contract silently accepted a stale/replayed signature instead of rejecting it.

This mirrors the smart-contract bug precisely at the design level: 
- Gateway: a state transition (revoke) is recorded via a signature, but the contract never marks that signature/authorization as consumed, so replaying it resurrects the revoked key.
- AccountsDb ancient squash: a state transition (death) is recorded as a tombstone that must be *carried forward*, but the invariant that guarantees this only fails loudly in debug builds; in release builds, if the precondition (`ancient squash only runs on slots far older than the latest full snapshot, where tombstones are purgeable”) is ever violated (e.g., due to a change in `latest_full_snapshot_slot` bookkeeping, a race between `set_latest_full_snapshot_slot`/`set_last_swept_full_snapshot_slot`, or a future code path that queues an unexpectedly "young" slot for ancient squashing), the tombstone is dropped and the older, superseded account version becomes reachable through remaining slot-list/storage state — the account is effectively resurrected without validator awareness.

### Impact Explanation
If the invariant is ever violated in a release binary (no panic, since `debug_assert!` does nothing there), a zero-lamport ("dead") account could be silently omitted from being marked dead, letting the accounts index / storage continue to reflect an older, non-zero-lamport version of that account as valid. This is exactly the "concrete stale or wrong-version account loads" / "silent balance change" class of impact called out in scope: a previously-revoked account state re-emerges as live, which — if it diverges between nodes doing/not doing the same squash timing — could also produce accounts-hash/capitalization divergence between honest nodes (replay vs. snapshot mismatch).

### Likelihood Explanation
The condition is explicitly gated by a *documented invariant* ("ancient squash only runs on slots far older than the latest full snapshot, where tombstones are purgeable") that is enforced only via `debug_assert!`, meaning:
- In non-debug (production/release) validator builds the safety net is entirely absent — if the invariant is ever broken by a future refactor, a race in updating `latest_full_snapshot_slot`/`last_swept_full_snapshot_slot`, or an edge case in slot selection for ancient combining, there is zero runtime protection, and the failure mode is a *silent* correctness bug rather than a crash.
- Likelihood of the underlying precondition itself being violated today is not established by available evidence — this is a latent structural weakness (missing production-time enforcement of a stated safety invariant) rather than a demonstrated end-to-end triggering path.

### Recommendation
Replace the `debug_assert!` guarding `tombstones_to_carry_forward.is_empty()` in `finish_combine_ancient_slots_packed_internal` with a hard runtime check (`assert!`/explicit error handling) that is enforced in release builds as well, so any violation of the "no tombstones during ancient squash" precondition fails loudly (or is safely handled by actually carrying the tombstone forward) instead of silently dropping the dead-account marker.

### Proof of Concept
No working end-to-end trigger was found or constructed; this is a structural analysis of the `debug_assert!`-only enforcement of a documented invariant in `finish_combine_ancient_slots_packed_internal` [3](#0-2) , contrasted with the existing regression tests (`test_shrink_does_not_resurrect_dead_account`, `test_accounts_clean_after_snapshot_restore_then_old_revives`) that show the project already treats "resurrection of dead accounts" as a serious, previously-encountered bug class. Demonstrating an actual violation of the precondition (i.e., getting a non-empty `tombstones_to_carry_forward` into the ancient squash path in a release build) would require further investigation into `latest_full_snapshot_slot`/ancient-slot-selection race conditions, which was not completed due to tool-call limits.

/// A pubkey whose account has died must stay dead when a storage holding a clean-reclaimed
/// older version of it is later shrunk.
#[test]
fn test_shrink_does_not_resurrect_dead_account() {
    let accounts = AccountsDb::default_for_tests();
    let pubkey = Pubkey::new_unique();
    let pubkey2 = Pubkey::new_unique();
    let pubkey3 = Pubkey::new_unique();
    let account = AccountSharedData::new(1, 0, &Pubkey::default());
    let zero_lamport_account = AccountSharedData::new(0, 0, &Pubkey::default());

    // Slot 1: pubkey's original version, pubkey2 to keep the storage alive later, and
    // pubkey3 as dead weight so shrink always sees the storage as worth rewriting
    accounts.store_for_tests((
        1,
        [
            (&pubkey, &account),
            (&pubkey2, &account),
            (&pubkey3, &account),
        ]
        .as_slice(),
    ));
    accounts.add_root(1);
    accounts.flush_rooted_accounts_cache_without_clean();

    // Slot 2: newer versions, flushed without clean so the slot 1 entries stay in the slot lists
    accounts.store_for_tests((2, [(&pubkey, &account), (&pubkey3, &account)].as_slice()));
    accounts.add_root(2);
    accounts.flush_rooted_accounts_cache_without_clean();

    // Clean reclaims the superseded slot 1 versions, leaving only the slot 2 entries
    accounts.clean_accounts_for_tests();
    accounts.accounts_index.get_and_then(&pubkey, |entry| {
        assert_eq!(entry.unwrap().slot_list_lock_read_len(), 1);
        (false, ())
    });

    // Slot 3: the account dies
    accounts.store_for_tests((3, [(&pubkey, &zero_lamport_account)].as_slice()));
    accounts.add_root_and_flush_write_cache(3);

    // Shrink slot 1's storage, which still physically holds pubkey's reclaimed version
    accounts.shrink_slot_forced(1);

    // The account should stay dead
    let loaded = accounts.do_load_for_tests(&Ancestors::default(), &pubkey);
    assert!(loaded.is_none_or(|(account, _slot)| account.lamports() == 0));
    // Only pubkey2 survives the rewrite of slot 1's storage
    assert!(accounts.contains(&pubkey2));
    assert_eq!(accounts.alive_account_count_in_slot(1), 1);

    // Clean's reclaims released the refs for the superseded slot 1 and slot 2 versions, leaving
    // the zero-lamport version single-ref. With no full snapshot retaining it, the final clean
    // fully purges the pubkey.
    accounts.clean_accounts_for_tests();
    assert!(!accounts.contains(&pubkey));
}

        accounts.store_for_tests((current_slot, [(&pubkey1, &account2)].as_slice()));
        accounts.add_root_and_flush_write_cache(current_slot);

        // Ref count is 1 as the older version in the previous slot was marked obsolete
        assert_eq!(accounts.accounts_index.ref_count_from_storage(&pubkey1), 1);

        // C: Yet more update to trigger lazy clean of step A
        current_slot += 1;

    /// finish shrink operation on slots where a new storage was created
    /// drop root and storage for all original slots whose contents were combined into other storages
    fn finish_combine_ancient_slots_packed_internal(
        &self,
        accounts_to_combine: AccountsToCombine<'_>,
        mut write_ancient_accounts: WriteAncientAccounts,
        metrics: &mut SquashStatsSub,
    ) {
        let mut dropped_roots = Vec::with_capacity(accounts_to_combine.accounts_to_combine.len());
        for shrink_collect in accounts_to_combine.accounts_to_combine {
            let slot = shrink_collect.slot;

            // Ancient squash only runs on slots far older than the latest full snapshot, where
            // tombstones are purgeable and `shrink_collect` drops them rather than carrying them
            // forward. The squash write path has no tombstone handling, so a non-empty list here
            // would be silently lost; assert the invariant at the point that loss would occur.
            debug_assert!(
                shrink_collect.tombstones_to_carry_forward.is_empty(),
                "ancient squash reached a carry-forward tombstone at slot {slot}",
            );
