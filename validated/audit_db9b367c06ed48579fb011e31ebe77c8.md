## Finding: `AccountInitDecorator` omits pubkey-to-address binding check, allowing signature forgery for first-use gasless signers

### Title
Missing pubkey-to-address binding in `AccountInitDecorator.verifySignatureForNewAccount` allows unauthorized account creation and message execution for any not-yet-used address - (File: `app/ante/account_init_decorator.go`)

### Summary
`AccountInitDecorator.AnteHandle` special-cases first-use gasless transactions (signer has no on-chain account yet) by verifying the signature itself and then **short-circuiting the entire remaining ante chain** — it returns `ctx, nil` directly instead of calling `next(...)`. [1](#0-0) 

### Finding Description
The normal Cosmos SDK ante pipeline binds a signature to an address via `SetPubKeyDecorator`, which explicitly checks `sdk.AccAddress(pubKey.Address()) == signerAddress` before accepting a pubkey for that signer. In the Push Chain ante chain, `NewAccountInitDecorator` runs **before** `ante.NewSetPubKeyDecorator`/`ante.NewSigVerificationDecorator`: [2](#0-1) 

For the first-use branch (account does not exist), `AccountInitDecorator` never calls `next`, so `SetPubKeyDecorator`, `ValidateSigCountDecorator`, `SigGasConsumeDecorator`, `SigVerificationDecorator`, and `IncrementSequenceDecorator` are **all skipped**. Instead, its own `verifySignatureForNewAccount` is the sole gatekeeper: [3](#0-2) 

Critically, `verifySignatureForNewAccount` takes `newAccAddr` from `sigTx.GetSigners()` (derived from the message body's signer field, e.g. a `Signer`/`Creator` string in `MsgVoteInbound`), but the pubkey used for cryptographic verification is taken directly from the transaction's own `SignatureData` (`sig.PubKey`) with **no check that `sdk.AccAddress(pubKey.Address())` equals `newAccAddr`**: [4](#0-3) 

Since the message content (which contains the claimed signer address) is part of the signed bytes, an attacker can:
1. Generate an arbitrary, unrelated keypair (`pubKey_X`/`privKey_X`).
2. Craft a gasless message (e.g. `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`, `MsgExecutePayload`, `MsgMigrateUEA` — the full gasless whitelist) whose signer field is set to a **victim address that has never sent a transaction** (e.g. a freshly keygen'd Universal Validator hot key, which by design of this feature has no account yet — see `app/README.md` line 182: "lets a freshly-keygen'd Universal Validator hot key vote on its very first tx, without anyone first having to fund it").
3. Sign the tx with `privKey_X` and set `SignerInfo.PublicKey = pubKey_X` in `AuthInfo`.
4. `authsigning.VerifySignature` succeeds because it only checks that the signature bytes are valid under `pubKey_X` — it never checks that `pubKey_X` corresponds to the victim address embedded in the message.
5. `AccountInitDecorator` then creates the account for the victim address (`aid.ak.NewAccountWithAddress(ctx, newAccAddr)`) and returns success, bypassing the rest of ante verification, allowing baseapp to execute the forged message as if it were authentically submitted/signed by the victim address. [5](#0-4) 

This confirms the exploit idea in the question: the ante-level state transition (account creation + acceptance into execution) happens before the attacker is bound to actually holding the private key of the claimed signer, breaking the stated invariant that only the true key holder should create the first account state and reach downstream gasless execution.

### Impact Explanation
Because the gasless whitelist covers Universal Validator voting messages (`MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, TSS process/migration votes) and user-facing `MsgExecutePayload`/`MsgMigrateUEA`, this allows an unprivileged attacker to inject a forged "vote" or "execution" attributed to any address that has not yet transacted on-chain, without needing that address's private key. For UV votes this can corrupt ballot tallying (forged/mismatched vote accepted with honest validators/nodes), potentially contributing to false quorum on inbound/outbound/chain-meta/TSS state, which maps directly to in-scope impacts (forged ballot/chain-meta/TSS state accepted through user-reachable flows, unauthorized state transitions). For `MsgExecutePayload`/`MsgMigrateUEA`, it could allow unauthorized execution attributed to a UEA-owning address that hasn't yet transacted.

### Likelihood Explanation
High for any address that is a valid target of the gasless whitelist and has not yet sent a transaction — this is exactly the intended use case the decorator was built for (fresh UV hot keys), so the attack window (targeting a UV's very first vote, front-running it) is realistic and directly reachable by an ordinary user submitting a standard Cosmos transaction through the default ante pipeline. I was unable to fully verify (within available tool budget) whether the `x/uexecutor`/`x/utss` message handlers perform an additional secondary check (e.g., verifying `msg.Signer` is a currently-registered Universal Validator and rejecting non-UV signers) that would gate the ultimate impact — such a check would still not prevent the account creation itself but could limit which addresses are consequential to forge. This should be confirmed against `x/uexecutor/keeper/msg_vote_inbound.go` and `x/uvalidator/keeper/validator.go` (`IsUniversalValidator`) during remediation triage.

### Recommendation
In `AccountInitDecorator.verifySignatureForNewAccount`, after obtaining `pubKey := sig.PubKey`, add the same binding check performed by upstream `SetPubKeyDecorator`: require `bytes.Equal(pubKey.Address(), newAccAddr)` (or equivalently `sdk.AccAddress(pubKey.Address()).Equals(newAccAddr)`), rejecting the transaction with `sdkerrors.ErrInvalidPubKey` if it does not match, before performing `authsigning.VerifySignature`.

### Proof of Concept
A Go ante test analogous to the existing `account_init_decorator_test.go` scaffolding would: build a `MsgVoteInbound` (or other gasless-whitelisted message) with `Signer` set to address `A` (which has no `HasAccount` entry), sign the tx using an unrelated keypair `B` whose `SignerInfo.PublicKey` is `pubKey_B`, and call `AccountInitDecorator.AnteHandle`. Expected (buggy) result: `verifySignatureForNewAccount` returns `nil` (signature "verifies" against `pubKey_B` even though `pubKey_B` does not hash to address `A`), the decorator creates account `A` with sequence 1, and returns success — meaning the forged tx is accepted for onward execution without requiring `A`'s actual private key. [6](#0-5)

```go
func (aid AccountInitDecorator) verifySignatureForNewAccount(ctx sdk.Context, tx sdk.Tx, simulate bool) error {
	sigTx, ok := tx.(authsigning.Tx)
	if !ok {
		return errorsmod.Wrap(sdkerrors.ErrTxDecode, "invalid transaction type")
	}

	// stdSigs contains the sequence number, account number, and signatures.
	// When simulating, this would just be a 0-length slice.
	sigs, err := sigTx.GetSignaturesV2()
	if err != nil {
		return err
	}

	signers, err := sigTx.GetSigners()
	if err != nil {
		return err
	}

	// check that signer length and signature length are the same
	if len(sigs) != len(signers) {
		return errorsmod.Wrapf(sdkerrors.ErrUnauthorized, "invalid number of signer;  expected: %d, got %d", len(signers), len(sigs))
	}

	newAccAddr := sdk.AccAddress(signers[0])
	for _, sig := range sigs {
		pubKey := sig.PubKey
		if pubKey == nil {
			return errorsmod.Wrap(sdkerrors.ErrInvalidPubKey, "pubkey is not provided in signature")
		}

		// retrieve signer data
		chainID := ctx.ChainID()
		var accSequence uint64 = 0
		var accNum uint64 = 0

		// no need to verify signatures on recheck tx
		if !simulate && !ctx.IsReCheckTx() && ctx.IsSigverifyTx() {
			anyPk, _ := codectypes.NewAnyWithValue(pubKey)

			signerData := txsigning.SignerData{
				Address:       newAccAddr.String(),
				ChainID:       chainID,
				AccountNumber: accNum,
				Sequence:      accSequence,
				PubKey: &anypb.Any{
					TypeUrl: anyPk.TypeUrl,
					Value:   anyPk.Value,
				},
			}
			adaptableTx, ok := tx.(authsigning.V2AdaptableTx)
			if !ok {
				return fmt.Errorf("expected tx to implement V2AdaptableTx, got %T", tx)
			}
			txData := adaptableTx.GetSigningTxData()
			ctx.Logger().Debug("account init decorator: verifying signature for new account",
				"address", newAccAddr.String(),
				"chain_id", chainID,
				"acc_num", accNum,
				"sequence", accSequence,
			)
			err = authsigning.VerifySignature(ctx, pubKey, signerData, sig.Data, aid.signModeHandler, txData)
			if err != nil {
				var errMsg string
				if OnlyLegacyAminoSigners(sig.Data) {
					// If all signers are using SIGN_MODE_LEGACY_AMINO, we rely on VerifySignature to check account sequence number,
					// and therefore communicate sequence number as a potential cause of error.
					errMsg = fmt.Sprintf("signature verification failed; please verify account number (%d), sequence (%d) and chain-id (%s)", accNum, accSequence, chainID)
				} else {
					errMsg = fmt.Sprintf("signature verification failed; please verify account number (%d) and chain-id (%s): (%s)", accNum, chainID, err.Error())
				}
				ctx.Logger().Debug("account init decorator: signature invalid for new account",
					"address", newAccAddr.String(),
					"chain_id", chainID,
				)
				return errorsmod.Wrap(sdkerrors.ErrUnauthorized, errMsg)

			}
		} else {
			ctx.Logger().Debug("account init decorator: skipping signature verification",
				"address", newAccAddr.String(),
				"simulate", simulate,
				"is_recheck_tx", ctx.IsReCheckTx(),
				"is_sigverify_tx", ctx.IsSigverifyTx(),
			)
		}
	}
	return nil
```
