### Title
Front-runnable `initialize()` on `BurnMintERC20Transparent`/`BurnMintERC20PausableFreezableTransparent` implementation contracts allows griefing of CCIP token proxy deployment - (File: `deployment/ccip/changeset/v1_6_1/cs_transparent_upgradeable_proxy.go`)

### Summary
Chainlink's CCIP deployment tooling deploys upgradeable ERC-20 token implementations (`BurnMintERC20Transparent`, `BurnMintERC20PausableFreezableTransparent`) and later, in a separate transaction/changeset, deploys a `TransparentUpgradeableProxy` pointing at that implementation while packing an `initialize(name, symbol, decimals, maxSupply, preMint, defaultAdmin)` call for the proxy constructor to delegatecall. This mirrors the Unlock Protocol `PublicLock.initialize()` bug class: an implementation/template contract is deployed in one step and only initialized in a later, separate step, leaving a window where an unprivileged actor can call `initialize()` directly against the implementation before the intended proxy-deployment step consumes it.

### Finding Description
`DeployBurnMintERC20Transparent` deploys the token implementation contract with no initialization or ownership set in the same transaction: [1](#0-0) 

Later, a distinct changeset, `DeployTransparentUpgradeableProxy`, packs and sends the `initialize(...)` calldata as part of deploying the `TransparentUpgradeableProxy`, referencing the previously deployed implementation address (`config.BurnMintERC20Transparent`): [2](#0-1) 

Because these are two independently-submitted transactions/changesets (potentially executed at different times, by different keys, or via MCMS timelock proposals), there is a window during which the implementation contract sits deployed and un-initialized on-chain. The codebase itself acknowledges this exact risk: `TransparentUpgradeableProxyChangesetConfig.Validate` explicitly checks whether the implementation's `Symbol()` is already non-empty before proceeding, treating a non-empty symbol as evidence the implementation was "already initialized" by someone else and erroring out rather than proceeding: [3](#0-2) 

This is precisely analogous to the reported bug class: `Unlock.sol`'s `setLockTemplate()` calls `PublicLock.initialize()` on a template deployed separately, and because `PublicLock.initialize()` has no access control tied to the intended caller, an attacker can front-run it, forcing the team to redeploy the template. Here, the CCIP deployment pipeline separates "deploy implementation" from "call initialize via proxy constructor," and the presence of a defensive "already initialized" check in `Validate` demonstrates that the underlying `initialize()` function on the ERC-20 implementation is *not* restricted to the deployer/proxy — any account that observes the freshly-deployed, not-yet-initialized implementation address on a public mempool can call `initialize()` directly and claim `defaultAdmin`/minter-burner roles before the legitimate `DeployTransparentUpgradeableProxy` changeset executes.

### Impact Explanation
If a malicious actor front-runs by calling `initialize()` on the bare implementation contract with attacker-controlled parameters (setting themselves as `defaultAdmin`), the subsequent `DeployTransparentUpgradeableProxy` changeset will fail at `Validate` (`BurnMintERC20Transparent at %s is already initialized`), forcing the operator to redeploy a fresh implementation contract and repeat the whole flow. Because this affects CCIP token-pool onboarding infrastructure (address book / on-chain state tracked in `stateview.LoadChainState`), repeated griefing can stall or delay token deployment for CCIP lanes, and it costs the attacker far less gas than deploying and initializing a new implementation costs the legitimate operator — the same asymmetric griefing/DoS impact called out in the original report. This does not corrupt already-deployed proxies (proxy storage is separate from implementation storage under the transparent-proxy pattern), so the worst-case impact is deployment disruption/griefing rather than a live protocol compromise, matching the "disagreed severity" nature of the analog report.

### Likelihood Explanation
Likelihood depends on: (1) implementation deployment and proxy-deployment being observable as separate public transactions (which the two-changeset design in `cs_burn_mint_erc20_transparent.go` and `cs_transparent_upgradeable_proxy.go` confirms), and (2) `initialize()` lacking access control tied to the deployer/proxy, which the defensive check in `Validate` (lines 81-98) strongly implies since it must guard against exactly this externally-triggered state. Any party monitoring pending transactions or newly-deployed, uninitialized `BurnMintERC20Transparent` contract addresses in the address book/mempool could exploit this with a simple front-run transaction, requiring no privileged access.

### Recommendation
- Have the ERC-20 implementation constructor call `_disableInitializers()` (OpenZeppelin `Initializable` pattern) so the implementation itself can never be initialized outside of a proxy's delegatecall context.
- Alternatively, restrict `initialize()` to only be callable by a known/precomputed proxy address or the deployer key, and/or combine the implementation deployment and proxy deployment (with `initialize` calldata) into a single atomic transaction so there is no observable window for front-running.
- Where changesets must remain split (e.g., implementation reuse across multiple proxies), add a check immediately after implementation deployment to detect and fail-fast if the implementation was tampered with, and treat such a tampered implementation as non-reusable/burned rather than retrying against the same address.

### Proof of Concept
1. Run the `v1_5` changeset to deploy `BurnMintERC20Transparent`: `deployment/ccip/changeset/v1_5/cs_burn_mint_erc20_transparent.go` lines 74-90 deploys the implementation with no initializer call.
2. Before the `v1_6_1` `DeployTransparentUpgradeableProxy` changeset executes (`cs_transparent_upgradeable_proxy.go` lines 160-199), an attacker observes the new implementation address in a block explorer/mempool and sends a transaction directly calling `initialize(attackerName, attackerSymbol, decimals, maxSupply, preMint, attackerAddress)` on the implementation contract.
3. When the legitimate changeset later runs, `TransparentUpgradeableProxyChangesetConfig.Validate` calls `implementation.Symbol()` and finds it non-empty (set by the attacker), returning the error `"BurnMintERC20Transparent at %s is already initialized for %s token on %s"` (`cs_transparent_upgradeable_proxy.go` lines 96-98), aborting the deployment and forcing the operator to redeploy a new implementation contract, repeating the cycle at the attacker's discretion.
