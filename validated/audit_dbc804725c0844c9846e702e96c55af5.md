### Title
Gateway skips `max_l2_gas_amount` bound check for Declare transactions, allowing a class declarer to submit unbounded L2 gas resource bounds - (File: crates/apollo_gateway/src/stateless_transaction_validator.rs)

### Summary
`StatelessTransactionValidator::validate_resource_bounds` enforces `max_l2_gas_amount` on Invoke and DeployAccount transactions, but explicitly skips this check for Declare transactions, leaving `resource_bounds.l2_gas.max_amount` unbounded (up to `u64::MAX`) for any submitted Declare transaction.

### Finding Description
`validate_resource_bounds` runs as part of stateless gateway validation, reachable by any unprivileged sender submitting an `RpcTransaction`. The function checks that resource bounds are non-zero and that `l2_gas.max_price_per_unit` meets `min_gas_price`, then attempts to cap `l2_gas.max_amount` at `self.config.max_l2_gas_amount` — but it deliberately no-ops this cap for Declare transactions: [1](#0-0) 

This is the direct analog of the external report's root cause: a bound (`firstBuyFee`/here `max_l2_gas_amount`) that is supposed to constrain a specific actor's resource/economic parameter is never validated for one code path (Declare), letting that actor (the class declarer) submit values the protocol explicitly intended to restrict via `StatelessTransactionValidatorConfig::max_l2_gas_amount`: [2](#0-1) 

The comment `// TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.` confirms the gap is unaddressed rather than an intentional design decision explained elsewhere in the validator.

### Impact Explanation
Because the stateless gateway is the boundary defense against oversized resource-bound fields before more expensive stateful/blockifier processing, a Declare transaction can carry an arbitrarily large `l2_gas.max_amount` (bounded only by `u64::MAX` and the requirement that `max_possible_fee(tip) != 0`, which is trivially satisfied). This bypasses the protocol-level assumption enforced everywhere else that `l2_gas.max_amount <= max_l2_gas_amount` (1.21B by default), and propagates an out-of-policy resource-bounds value into subsequent stateful fee/balance and bouncer accounting paths that are designed around bounded configuration values. Given that later fee-bound consistency checks (e.g. `check_fee_bounds`/`FeeCheckReport`) trust that gateway-side static caps already filtered obviously-out-of-policy values, this discrepancy between Declare and other tx types is a real correctness gap in gateway admission logic, though it is a Medium (not higher) severity issue since actually consuming the declared bound still requires the sender to cover `max_possible_fee` with real balance (blockifier's `verify_can_pay_committed_bounds`), which limits practical exploitation to accounts with proportionally large balances.

### Likelihood Explanation
High likelihood of reachability: any account capable of submitting a Declare transaction (an ordinary, unprivileged flow) triggers this code path with no special conditions, and the omission is unconditional (not behind a feature flag), i.e. every Declare transaction passes through the gateway with `max_l2_gas_amount` unchecked.

### Recommendation
Remove the special-case exemption for `RpcTransaction::Declare` in `validate_resource_bounds`, and apply the same `max_l2_gas_amount` bound check for Declare transactions as for Invoke/DeployAccount:
```rust
if resource_bounds.l2_gas.max_amount.0 > self.config.max_l2_gas_amount {
    return Err(StatelessTransactionValidatorError::MaxGasAmountTooHigh {
        gas_amount: resource_bounds.l2_gas.max_amount,
        max_gas_amount: self.config.max_l2_gas_amount,
    });
}
```
If Declare transactions require a different (e.g., higher) ceiling due to Sierra-to-CASM compilation costs, introduce an explicit `max_l2_gas_amount_declare` config value rather than skipping validation entirely.

### Proof of Concept
1. Construct an `RpcTransaction::Declare` (V3) with `resource_bounds.l2_gas.max_amount = u64::MAX` (or any value far exceeding `StatelessTransactionValidatorConfig::max_l2_gas_amount`, default `1_210_000_000`), and `l2_gas.max_price_per_unit >= min_gas_price` so the zero-bounds and min-price checks pass.
2. Submit it through the gateway's `StatelessTransactionValidator::validate`. Because `tx` matches `RpcTransaction::Declare(_)` in `validate_resource_bounds`, the `max_l2_gas_amount` branch is skipped entirely: [1](#0-0) 
3. Compare with an equivalent Invoke transaction with the same oversized `l2_gas.max_amount`, which is correctly rejected with `StatelessTransactionValidatorError::MaxGasAmountTooHigh`. The Declare transaction instead proceeds to stateful validation, demonstrating the class-declarer bypass of the intended `max_l2_gas_amount` restriction.
