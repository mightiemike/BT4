### Title
Meta-transaction v0 hash format collides with real deprecated Invoke-V0 transaction hash, enabling cross-context signature replay - (File: `crates/blockifier/src/execution/syscalls/syscall_base.rs`)

### Summary
The `meta_tx_v0` syscall computes its "meta-transaction hash" using exactly the same hash function, prefix, and field layout as a genuine, on-chain `InvokeTransactionV0` transaction hash. There is no domain separator distinguishing "a hash meant to authorize execution only through the `meta_tx_v0` relay path" from "a hash of a real standalone V0 invoke transaction". This is the sequencer-side analog of the reported "untyped data signing" bug class: signatures/hashes with no domain tag are reusable across unrelated contexts.

### Finding Description
`SyscallHintProcessor::meta_tx_v0` (`crates/blockifier/src/execution/syscalls/syscall_base.rs:286-367`) computes the hash to place into the inner `TxInfo.transaction_hash` field as: [1](#0-0) 
using `InvokeTransactionV0::calculate_transaction_hash(chain_id, version_zero)`. This is the identical code path used to compute the hash of a genuine, user-submitted `InvokeTransactionV0` transaction (`crates/starknet_api/src/transaction_hash.rs:301-334`), which chains `INVOKE`, version, `contract_address`, `entry_point_selector`, hashed `calldata`, `max_fee`, and `chain_id` — the exact same fields, in the exact same order, as the meta-tx hash.

The Cairo-side OS implementation (`crates/apollo_starknet_os_program/.../transaction_hash.cairo`, function `compute_meta_tx_v0_hash`, lines 294-315) similarly reuses `deprecated_get_transaction_hash` with `tx_hash_prefix=INVOKE_HASH_PREFIX, version=0`, matching the real V0 invoke hash format field-for-field.

`execute_meta_tx_v0` (`crates/apollo_starknet_os_program/.../execution/syscall_impls.cairo:284-390`) then invokes the target contract's `__execute__` (only `__execute__`, never `__validate__`) using this synthetic `TxInfo`, with `caller_address = ORIGIN_ADDRESS` (address 0) — the same caller address the OS uses for a genuine top-level transaction's `__execute__` call. Consequently, from inside `__execute__`, there is no way for an account contract to distinguish:
- a real, standalone `InvokeTransactionV0` that was broadcast and executed on-chain, from
- a `meta_tx_v0` relay call constructed by an arbitrary caller contract that supplies the exact same `(contract_address, selector, calldata)` triple and reuses a signature that was produced/observed for the former.

Because `max_fee` is hardcoded to `0`, `version` to `0`, and there is no nonce field at all in this hash (`nonce=0` is hardcoded in the `TxInfo`, and the V0 invoke hash format for non-deprecated V0 excludes nonce as well), any historically valid, publicly-visible `(transaction_hash, signature)` pair for an `InvokeTransactionV0` targeting entry point `__execute__` can be replayed indefinitely through `meta_tx_v0` by any calling contract, with no way for the target account to detect that the "transaction" is not a fresh, uniquely-authorized action — unless the account contract itself implements independent replay protection (e.g., its own nonce inside calldata), which is not enforced by the sequencer/OS and cannot be relied upon generically.

### Impact Explanation
Any contract that is called into via `meta_tx_v0` and whose `__execute__` logic checks `tx_info.signature`/`tx_info.transaction_hash` against an expected authorization (the intended purpose of this syscall) is exposed to hash/signature reuse across two distinct execution contexts that the protocol itself does not separate: standalone top-level V0 invoke execution vs. meta-tx relay execution invoked by an arbitrary, unprivileged caller contract. Because the hash format is bit-for-bit identical between these two contexts, a single signed authorization can be replayed by any unprivileged transaction sender through a malicious intermediate contract, to trigger unauthorized execution/re-execution of the same call on the target account — a form of unauthorized account action reachable from a single submitted transaction. This satisfies "unauthorized account action" under the given validation rules.

### Likelihood Explanation
Reachability is trivial and fully unprivileged: any account can deploy a contract that calls the `meta_tx_v0` syscall (available in both Native and VM `blockifier` execution — `crates/blockifier/src/execution/native/syscall_handler.rs:408-439`, `crates/blockifier/src/execution/syscalls/hint_processor.rs:664-683`) with attacker-chosen `(contract_address, selector, calldata, signature)` and no privileged role is required. The only precondition is that the attacker can obtain or observe a valid `(transaction_hash, signature)` pair for the targeted `(contract_address, selector=__execute__, calldata)` triple, which the underlying hash format's lack of domain separation makes readily reusable from any source that produces the same hash shape (a real historical V0 invoke tx, or another account's meta-tx flow). Actual severity is bounded by how many account implementations rely on signature verification for this hash shape without additional replay protection, but the sequencer/OS design itself provides no domain separation to prevent it — this is a structural (protocol-level), not account-specific, weakness.

### Recommendation
Introduce an explicit domain separator (a distinct hash prefix, e.g. `META_TX_V0_HASH_PREFIX` distinct from `INVOKE_HASH_PREFIX`, or an EIP-712-style typed-data domain including a `meta_tx` tag) so that the hash computed inside `execute_meta_tx_v0`/`meta_tx_v0` can never collide with the hash of a genuine standalone transaction of any version/type. Additionally consider binding the hash to the immediate calling contract (`caller_execution_info.contract_address`) so a signature crafted for relay by one caller contract cannot be replayed by a different unprivileged caller contract targeting the same `(contract_address, selector, calldata)`.

### Proof of Concept
1. Deploy `ContractA` implementing `__execute__` that authorizes an action solely by checking `tx_info.transaction_hash` was signed by its owner (a typical "meta-tx enabled" account pattern), reachable through the `meta_tx_v0` relay only.
2. Deploy `ContractB`, controlled by an attacker, which calls the `meta_tx_v0` syscall with `contract_address = ContractA`, `entry_point_selector = EXECUTE_ENTRY_POINT_SELECTOR`, and a `calldata`/`signature` pair equal to those of a previously broadcast, now-included `InvokeTransactionV0` targeting `ContractA` (whose hash and signature are publicly visible on-chain, per `crates/starknet_api/src/transaction_hash.rs:301-334`).
3. Because `compute_meta_tx_v0_hash`/`InvokeTransactionV0::calculate_transaction_hash` (`crates/blockifier/src/execution/syscalls/syscall_base.rs:317-328`) reproduce the identical hash for this `(contract_address, selector, calldata, chain_id, max_fee=0, version=0)` tuple, `ContractA`'s `__execute__` receives `tx_info.transaction_hash` identical to the original transaction hash and `tx_info.signature` equal to the original valid signature, and treats the call as re-authorized — even though the actual top-level submitted transaction was invoked by `ContractB` and is unrelated to the original authorization.
4. Repeat unlimited times (no nonce is present in the meta-tx hash), demonstrating unbounded unauthorized replay through a single unprivileged transaction sender path.

Note: full confirmation that a concrete shipped account contract in this codebase is vulnerable to this specific replay (versus theoretical/account-design-dependent) could not be completed within the available exploration; the structural hash-collision root cause and syscall reachability are confirmed directly in code, per citations above.
