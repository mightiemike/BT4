### Title
Unsynchronized `HashMap` shared between block-import thread and HTTP request thread can throw `ConcurrentModificationException` in `NodeInfoService.setCheatWitnessInfo` - (File: `framework/src/main/java/org/tron/core/services/NodeInfoService.java`)

### Summary
`WitnessProductBlockService.cheatWitnessInfoMap` is a plain, unsynchronized `HashMap` that is mutated by the block-import thread in `validWitnessProductTwoBlock` and iterated over via `entrySet()` in `NodeInfoService.setCheatWitnessInfo`, which is reachable from the public, unauthenticated `GET /wallet/getnodeinfo` HTTP endpoint. Concurrent access from an attacker flooding this endpoint while blocks are being imported can race with the map mutation and throw an uncaught `ConcurrentModificationException` (or, in rarer cases, corrupt the iteration) inside the servlet-handling call stack.

`getNodeInfo()` is exposed through the unauthenticated HTTP servlet `GetNodeInfoServlet` (backing `wallet/getnodeinfo`), as well as gRPC (`RpcApiService`) and JSON-RPC (`TronJsonRpcImpl`) surfaces, none of which require any privileged role, signed transaction, or special configuration to call. Because block imports (and therefore `validWitnessProductTwoBlock` writes, whenever a double-production event occurs) happen continuously on any running node, and `getnodeinfo` reads race against those writes with no lock, a `put()` on the map concurrent with an in-progress `entrySet()` iteration in another thread can trigger structural-modification detection in `HashMap`, throwing `ConcurrentModificationException` from within the request-handling thread.

### Impact Explanation
This is a DoS-via-RPC-API class issue: an uncaught `ConcurrentModificationException` propagating out of `setCheatWitnessInfo` during an HTTP request would cause that request to fail (likely surfacing a stack trace/error to the caller depending on servlet exception handling), and repeated triggering under load could cause exception-driven overhead on the request-handling thread pool. It does not lead to key leakage, fund theft, or consensus divergence, but it is a legitimate node-crash/stall-adjacent robustness bug reachable purely through public RPC polling combined with the double-block-production condition, which is an internal state exercised by normal validator behavior.

### Likelihood Explanation
Exploitability requires the race window: the map must actually be mutated (i.e., `validWitnessProductTwoBlock` must detect an actual double-production event, which is not attacker-controlled and is rare in practice) at the same time a caller is iterating it via `getnodeinfo`. An attacker can cheaply flood `getnodeinfo` requests to maximize the number of concurrent reads, but cannot force the write side to occur — this makes practical, reliable exploitation dependent on witness misbehavior actually occurring, not purely attacker-triggerable at will. This significantly lowers real-world likelihood compared to a fully attacker-controlled race, even though the underlying code has a genuine unsynchronized-map defect.

### Recommendation
Use a thread-safe map (e.g., `ConcurrentHashMap`) for `cheatWitnessInfoMap`, or synchronize both the writer in `validWitnessProductTwoBlock` and the reader in `queryCheatWitnessInfo`/`setCheatWitnessInfo`, or have `queryCheatWitnessInfo()` return an immutable snapshot copy (e.g., built under a lock) rather than the live map reference.

### Proof of Concept
```java
@Test
public void testConcurrentModificationOnCheatWitnessInfoMap() throws Exception {
  WitnessProductBlockService service = new WitnessProductBlockService();
  Field field = WitnessProductBlockService.class.getDeclaredField("cheatWitnessInfoMap");
  field.setAccessible(true);
  Map<String, WitnessProductBlockService.CheatWitnessInfo> map =
      (Map<String, WitnessProductBlockService.CheatWitnessInfo>) field.get(service);

  AtomicBoolean cmeThrown = new AtomicBoolean(false);
  ExecutorService pool = Executors.newFixedThreadPool(2);

  Runnable writer = () -> {
    for (int i = 0; i < 100_000; i++) {
      map.put("key" + i, new WitnessProductBlockService.CheatWitnessInfo());
    }
  };

  Runnable reader = () -> {
    for (int i = 0; i < 100_000; i++) {
      try {
        for (Map.Entry<String, WitnessProductBlockService.CheatWitnessInfo> e :
            service.queryCheatWitnessInfo().entrySet()) {
          e.getValue().toString();
        }
      } catch (ConcurrentModificationException e) {
        cmeThrown.set(true);
      }
    }
  };

  pool.submit(writer);
  pool.submit(reader);
  pool.shutdown();
  pool.awaitTermination(10, TimeUnit.SECONDS);

  Assert.assertTrue("Expected ConcurrentModificationException due to unsynchronized HashMap access",
      cmeThrown.get());
}
```
This demonstrates that concurrent reads (as performed by `NodeInfoService.setCheatWitnessInfo` on every `getnodeinfo` call) racing against writes (as performed by `validWitnessProductTwoBlock`) on the shared unsynchronized `HashMap` reliably produce `ConcurrentModificationException`.

  public void validWitnessProductTwoBlock(BlockCapsule block) {
    try {
      BlockCapsule blockCapsule = historyBlockCapsuleCache.getIfPresent(block.getNum());
      if (blockCapsule != null && Arrays.equals(blockCapsule.getWitnessAddress().toByteArray(),
          block.getWitnessAddress().toByteArray()) && !Arrays.equals(block.getBlockId().getBytes(),
          blockCapsule.getBlockId().getBytes())) {
        String key = ByteArray.toHexString(block.getWitnessAddress().toByteArray());
        if (!cheatWitnessInfoMap.containsKey(key)) {
          CheatWitnessInfo cheatWitnessInfo = new CheatWitnessInfo();
          cheatWitnessInfoMap.put(key, cheatWitnessInfo);
        }
        cheatWitnessInfoMap.get(key).clear().setTime(System.currentTimeMillis())
            .setLatestBlockNum(block.getNum()).add(block).add(blockCapsule).increment();
      } else {
        historyBlockCapsuleCache.put(block.getNum(), new BlockCapsule(block.getInstance()));
      }
    } catch (Exception e) {
      logger.error("valid witness same time product two block fail! blockNum: {}, blockHash: {}",
          block.getNum(), block.getBlockId().toString(), e);
    }
  }
