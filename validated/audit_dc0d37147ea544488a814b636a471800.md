### Title
WebAuthn login challenge can be destroyed by an attacker with only a valid password, causing denial-of-service of MFA login for the targeted account - (File: core/sessions/webauthn.go)

### Finding Description
The WebAuthn login challenge is stored in a single in-memory map keyed only by `user.Email + "-authentication"` [1](#0-0)  with no per-browser-session or per-attempt isolation. `GetWebauthnSession` reads and deletes ("consumes") this entry via `store.take(key)` *before* any cryptographic validation is performed [2](#0-1) , and `FinishWebAuthnLogin` calls `GetWebauthnSession` immediately after successfully parsing the submitted `WebAuthnData` body, prior to calling `webAuthn.ValidateLogin` [3](#0-2) .

An attacker who knows a valid email+password (e.g. a leaked/weak password) but does not possess the victim's hardware key can reach `CreateSession` through the public `/sessions` endpoint, which has no rate limiting on this path [4](#0-3) . Because password verification happens before the WebAuthn step in `CreateSession` [5](#0-4) , the attacker's request reaches `FinishWebAuthnLogin` as long as they submit *any* structurally valid (but cryptographically bogus) `protocol.CredentialAssertionResponse` JSON — this is base64/JSON data the attacker can construct without any secret, since `protocol.ParseCredentialRequestResponseBody` only validates structure, not signatures [6](#0-5) . Once parsing succeeds, `GetWebauthnSession` unconditionally deletes the outstanding challenge for that email via `take()`, and only afterward does `ValidateLogin` reject the bogus signature. The net effect: the attacker's forged attempt fails, but the shared challenge slot for the victim's email is destroyed.

If the legitimate victim is mid-login (challenge already created via `BeginWebAuthnLogin`, which is triggered whenever `sr.WebAuthnData == ""` in `CreateSession` [7](#0-6) ), the victim's subsequent genuine signed assertion will call `GetWebauthnSession` and find nothing (`take` returns `ok=false`), producing `"assertion not in challenge store"` and forcing the victim to restart the WebAuthn flow [8](#0-7) . Since the attacker can repeat this at will (no rate limit observed on `CreateSession`/`/sessions`), they can repeatedly invalidate the victim's in-flight challenge and deny completion of MFA login for that account.

### Impact Explanation
This is a repeatable, low-cost denial-of-service against the MFA login step of a specific targeted account: an attacker who only knows (or brute-forces/leaks) a password — without ever possessing the hardware security key — can prevent the legitimate account owner from ever completing WebAuthn login, by racing/spamming forged `CreateSession` requests that consume the shared one-shot challenge slot. It does not grant the attacker access to the account (their own forged assertion still fails `ValidateLogin`), so this is an availability impact (denial of key login functionality) rather than an authentication bypass or credential/secret disclosure.

### Likelihood Explanation
Preconditions are limited to knowledge of a valid email+password for an MFA-enabled account (explicitly allowed as a precondition in the audit scope) and network access to the public session-creation endpoint. No signature forgery, hardware key, or race-perfect timing is strictly required for repeated disruption — the attacker can simply keep destroying the challenge slot for the target account at will since `BeginWebAuthnLogin`/`FinishWebAuthnLogin` share one global slot per email and there is no visible rate limiting in `SessionsController.Create` or `CreateSession`. This is easily repeatable and low-cost, making the likelihood high given the stated precondition.

### Recommendation
- Bind the stored WebAuthn challenge to the specific login attempt (e.g., a per-attempt/session-cookie-scoped nonce or a random request ID returned alongside the challenge and required on the finishing request) instead of keying solely by email, so unrelated requests for the same email cannot consume each other's challenge.
- Alternatively/additionally, only delete the stored challenge from `WebAuthnSessionStore` after `ValidateLogin` succeeds (or after a bounded number of failed attempts / expiry), rather than unconditionally on first read in `GetWebauthnSession`.
- Add rate limiting / lockout on repeated failed `CreateSession` WebAuthn attempts per account and per source IP.

### Proof of Concept
Integration test in `core/sessions` (or `core/sessions/localauth`):
1. Register a user with a WebAuthn credential (mirroring existing tests in `core/sessions/localauth/orm_test.go`).
2. Call `sessions.BeginWebAuthnLogin(user, uwas, sr)` to populate the challenge under `user.Email + "-authentication"` in a shared `WebAuthnSessionStore`.
3. Simulate the attacker: build a syntactically valid `protocol.CredentialAssertionResponse` JSON (arbitrary/garbage but structurally parseable credential ID, client data JSON with type `"webauthn.get"`, authenticator data, signature) and call `sessions.FinishWebAuthnLogin(user, uwas, sr)` with it. Assert this call returns an error from `ValidateLogin` (bad signature) but succeeds in reaching/consuming the store.
4. Immediately call `sessions.FinishWebAuthnLogin` again with the victim's real, correctly-signed assertion for the original challenge. Assert the error is `"assertion not in challenge store"`, proving the legitimate response can no longer be validated because the attacker's failed attempt already destroyed the one-shot challenge.

func (store *WebAuthnSessionStore) GetWebauthnSession(key string) (data webauthn.SessionData, err error) {
	assertion, ok := store.take(key)
	if !ok {
		err = pkgerrors.New("assertion not in challenge store")
		return
	}
	err = json.Unmarshal([]byte(assertion), &data)
	return
}

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
