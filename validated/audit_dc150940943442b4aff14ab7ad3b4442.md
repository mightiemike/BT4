### Title
Transactions can be permanently un-includable when marginal bouncer weight exceeds fixed block capacity - ([File: crates/blockifier/src/bouncer.rs])

### Summary
The Balancer/Tokemak report describes a class of bug where a user-requested amount is checked against a resource that is externally/rigidly capped (pool `cash`), and if the request can never be fully satisfied by that fixed capacity, the whole operation permanently reverts with no partial-fulfillment fallback. The sequencer's block-building bouncer has an analogous rigid-capacity check: `Bouncer::try_update` computes a transaction's marginal `BouncerWeights` and rejects the transaction outright — with `TransactionExecutorError::TransactionTooLarge` — if those weights alone exceed `bouncer_config.block_max_capacity`, a fixed, static limit that is independent of chain growth or configuration adjustments a user can control.

### Finding Description
`Bouncer::try_update` computes marginal weights for the transaction and adds them to the block's accumulated weights via `checked_add`, then checks room with `self.bouncer_config.has_room(next_accumulated_weights)`. If the tx's own weight already exceeds the configured `block_max_capacity` (independent of any other transaction in the block), it can never be admitted, in any block, ever, because the capacity check is against a fixed constant (`BouncerConfig::block_max_capacity`) rather than any per-transaction accommodation. [1](#0-0) 

This mirrors the reported issue: just as the Balancer pool's `cash` balance is a hard, externally-bounded ceiling that a withdraw request cannot influence, `block_max_capacity` is a fixed ceiling baked into node configuration that a transaction's resource usage (state diff size, message segment length, event count, sierra/proving gas, etc.) cannot be partially satisfied against — the whole transaction is rejected, not partially processed. The test suite explicitly demonstrates this "transaction too large" permanent-rejection path both at the raw bouncer level and via the `TransactionExecutor`: [2](#0-1) [3](#0-2) 

The `BouncerConfig::within_max_capacity_or_err` helper documents exactly this behavior — returning `TransactionExecutionError::TransactionTooLarge` whenever a transaction's weights don't fit inside `block_max_capacity`, regardless of what else is (or isn't) in the block: [4](#0-3) 

Because `block_max_capacity` is a static configuration value (not derived from the amount of work a specific transaction legitimately needs and not something a sender can adapt around beyond staying under the limit), any transaction whose intrinsic resource footprint (e.g., very large state diff from many storage writes, or many emitted events/messages) exceeds this ceiling is permanently unable to be sequenced by any node using this configuration — a structural, ceiling-bound DoS analogous to the Balancer `cash`-bound withdraw revert.

### Impact Explanation
A transaction meeting `block_max_capacity` alone can never be included in any block produced by a compliant sequencer, regardless of how many other transactions accompany it (even zero). This is a **network unable to confirm** a specific, otherwise valid transaction — the analog of "the withdrawal transaction from the user will get reverted" in the original report. If a user's legitimately state-heavy operation (e.g., contract deploying many storage slots, or emitting many events in one call) requires more capacity than the network's static config, it results in permanent inability to execute that transaction, i.e., permanent freezing of the requested state transition (and any funds/logic gated behind it).

### Likelihood Explanation
Reaching this path requires only submitting a single ordinary transaction (invoke/declare/deploy) whose resource footprint (state diff size, event count, message segment length, sierra/proving gas) is large enough to exceed the fixed `block_max_capacity`. No special privileges, ordering, or malicious actors are needed — it is purely a function of one transaction's own computed weight vs. a static ceiling that any unprivileged transaction sender can inadvertently or intentionally trigger.

### Recommendation
Because `block_max_capacity` is an operator-configured, protocol-level safety limit (distinct from Balancer's externally-controlled liquidity), the most direct mitigation is to ensure that gateway/mempool validation rejects (with a clear, actionable error) any transaction whose resource bounds already imply it cannot fit `block_max_capacity`, *before* it is admitted into the mempool — so users get immediate feedback rather than a transaction that lingers and is repeatedly rejected at block-building. Additionally, consider exposing `block_max_capacity` and the derived per-resource limits clearly so that resource-bound validation at the gateway (`crates/starknet_gateway` or equivalent) can pre-filter transactions before they consume mempool/bouncer cycles, preventing a class of transactions from being an unremovable "TransactionTooLarge" burden on the block builder.

### Proof of Concept
The existing regression test demonstrates the exact rejection path (a transaction whose marginal `sierra_gas` alone exceeds `block_max_capacity.sierra_gas`, independent of block state) resulting in a permanent, non-recoverable `TransactionTooLarge` error: [2](#0-1) 

Similarly, `test_execute_txs_bouncing` in `transaction_executor_test.rs` shows a transaction emitting `max_n_events_in_block + 1` events is rejected with `TransactionTooLarge` even as the sole transaction submitted, and remains rejected regardless of resetting/re-running the bouncer: [5](#0-4) 

**Note on completeness:** I was unable to fully trace the exact call graph of `get_tx_weights`/`verify_tx_weights_within_max_capacity` (referenced by tests but whose implementation body I could not open within the available iterations) to confirm whether any gateway-level pre-check exists elsewhere in the repo that would filter out oversized transactions before they reach the bouncer. This limits full certainty about whether this is only a block-builder-level rejection (recoverable by resubmission with smaller resource footprint) versus a truly unavoidable dead-end for a given transaction's fixed calldata/state-diff shape. A Devin session with full repository access could confirm this by locating `fn get_tx_weights` and `fn verify_tx_weights_within_max_capacity` in `crates/blockifier/src/bouncer.rs` and checking gateway-side validation for equivalent capacity pre-checks.

    pub fn within_max_capacity_or_err(
        &self,
        weights: BouncerWeights,
    ) -> TransactionExecutionResult<()> {
        if self.block_max_capacity.has_room(weights) {
            Ok(())
        } else {
            Err(TransactionExecutionError::TransactionTooLarge {
                max_capacity: Box::new(self.block_max_capacity),
                tx_size: Box::new(weights),
            })
        }
    }

#[rstest]
fn test_transaction_too_large_sierra_gas_based(block_context: BlockContext) {
    let mut state = test_state(&block_context.chain_info, Fee(0), &[]);
    let mut transactional_state = TransactionalState::create_transactional(&mut state);
    let block_max_capacity = BouncerWeights { sierra_gas: GasAmount(20), ..Default::default() };
    let bouncer_config = BouncerConfig { block_max_capacity, ..Default::default() };

    // Use gas amount > block_max_capacity's.
    let exceeding_gas = GasAmount(30);
    let execution_summary = ExecutionSummary::default();
    let builtin_counters = CairoPrimitiveCounterMap::default();
    let tx_resources = TransactionResources {
        computation: ComputationResources { sierra_gas: exceeding_gas, ..Default::default() },
        ..Default::default()
    };
    let tx_state_changes_keys = transactional_state.to_state_diff().unwrap().state_maps.keys();

    let result = verify_tx_weights_within_max_capacity(
        &transactional_state,
        &execution_summary,
        &builtin_counters,
        &tx_resources,
        &tx_state_changes_keys,
        &bouncer_config,
        &block_context.versioned_constants,
        GasAmount::ZERO,
    )
    .map_err(TransactionExecutorError::TransactionExecutionError);

    let expected_weights = BouncerWeights {
        sierra_gas: exceeding_gas,
        n_txs: 1,
        proving_gas: exceeding_gas,
        ..BouncerWeights::empty()
    };

    assert_matches!(result, Err(
        TransactionExecutorError::TransactionExecutionError(
            TransactionExecutionError::TransactionTooLarge { max_capacity, tx_size }
        )
    )  if *max_capacity == bouncer_config.block_max_capacity && *tx_size == expected_weights);
}

#[rstest]
#[case(false, false)]
#[case(true, false)]
#[case(true, true)]
fn test_execute_txs_bouncing(#[case] concurrency_enabled: bool, #[case] external_pool: bool) {
    let config = TransactionExecutorConfig::create_for_testing(concurrency_enabled);
    let max_n_events_in_block = 10;
    let block_context = BlockContext::create_for_bouncer_testing(max_n_events_in_block);

    let TestInitData { state, account_address, contract_address, .. } = create_test_init_data(
        &block_context.chain_info,
        CairoVersion::Cairo1(RunnableCairo1::Casm),
    );

    let pool = if external_pool {
        Some(Arc::new(WorkerPool::start(&config.get_worker_pool_config())))
    } else {
        None
    };

    let mut tx_executor = TransactionExecutor::new_with_pool(state, block_context, config, pool);

    let txs: Vec<Transaction> = [
        emit_n_events_tx(1, account_address, contract_address, nonce!(0_u32)),
        // Transaction too big.
        emit_n_events_tx(
            max_n_events_in_block + 1,
            account_address,
            contract_address,
            nonce!(1_u32),
        ),
        emit_n_events_tx(8, account_address, contract_address, nonce!(1_u32)),
        // No room for this in block - execution should halt.
        emit_n_events_tx(2, account_address, contract_address, nonce!(2_u32)),
        // Has room for this one, but should not be processed at all.
        emit_n_events_tx(1, account_address, contract_address, nonce!(3_u32)),
    ]
    .into_iter()
    .map(Transaction::Account)
    .collect();

    // Run.
    let results = tx_executor.execute_txs(&txs, None);

    // Check execution results.
    let expected_offset = 3;
    assert_eq!(results.len(), expected_offset);

    assert!(results[0].is_ok());
    assert_matches!(
        results[1].as_ref().unwrap_err(),
        TransactionExecutorError::TransactionExecutionError(
            TransactionExecutionError::TransactionTooLarge { .. }
        )
    );
