### Title
Selfdestructed contracts leave stale persistent storage that is not cleaned up on contract removal - (File: chainbase/src/main/java/org/tron/core/db/TransactionTrace.java)

### Summary
When a smart contract self-destructs via `SUICIDE`/`SUICIDE2`, java-tron's post-execution cleanup (`TransactionTrace.deleteContract`, mirrored by `RepositoryImpl.deleteContract`) removes the contract's ABI, code, account, and contract-metadata records, but never clears the contract's key/value storage rows in `StorageRowStore`. This mirrors the reported borg-core bug class: an entity is "removed" from the system (contract marked destroyed / removed from whitelist) but associated state (storage slots / method policies) is left behind and becomes reachable again if the same identity (contract address / whitelisted contract) is reintroduced later.

### Finding Description
`TransactionTrace.deleteContract` is the function invoked at the end of every VM transaction whose result contains delete-accounts (i.e., contracts that executed `SELFDESTRUCT`): [1](#0-0) [2](#0-1) 

It only issues deletes on `abiStore`, `codeStore`, `accountStore`, and `contractStore`. The identical logic exists in the in-VM repository layer: [3](#0-2) 

Neither path touches `StorageRowStore`, which persists every SSTORE'd slot for a contract address: [6](#0-5) 

Storage row keys are derived from `addrHash(address)`, i.e., purely a hash of the contract address for ordinary `CREATE` deployments (only `CREATE2`-created contracts mix in the deployment transaction hash via `generateAddrHash`): [7](#0-6) 

Contract addresses for `CREATE` are derived from `(sender, nonce)`: [8](#0-7) 

If a contract self-destructs and the same creator/nonce combination is later used to deploy a brand-new contract to the same address, that new contract's storage reads (`SLOAD`) will transparently return whatever values were left by the destroyed contract, since `Storage.getValue` falls straight through to `StorageRowStore.get(compose(key, addrHash))` for any slot not already dirtied in the current execution: [9](#0-8) 

This is the exact analog of the reported bug: "removal" (self-destruct / `removeContract`) clears the top-level record (`allowed`/`fullAccess` flags, or account/contract/code entries) but leaves subordinate state (`policy[_contract].methods`, or storage rows) intact and reachable if the identity is reused.

### Impact Explanation
A newly deployed contract that assumes fresh/zeroed storage (a very common Solidity assumption, e.g. uninitialized `mapping`/`bool` defaults) can silently inherit stale values — balances-like accounting variables, ownership flags, access-control booleans, reentrancy locks, or paused-state flags — from a previous, unrelated contract that occupied the same address before self-destructing. This can lead to authorization bypass, incorrect accounting, or logic bypass in the new contract without any code path in the new contract writing that value, i.e., an invalid-state/divergence condition purely due to unclean removal semantics.

### Likelihood Explanation
Exploitation requires an attacker to control both the destroyed contract and the ability to redeploy to the same derived address (same sender address and same nonce value, achievable by deploying, destroying, and immediately redeploying with a matching nonce, or via `CREATE2`-adjacent address reuse patterns where `generateAddrHash` collisions are engineered). This is a non-privileged, purely on-chain sequence of ordinary transactions (deploy, self-destruct, redeploy), reachable by any user, matching the "unprivileged-user analog" requirement.

### Recommendation
When a contract is removed via self-destruct, iterate and delete all associated `StorageRowStore` entries for that address (or maintain a per-address index of storage keys to allow full purge), mirroring the recommendation from the original report to fully clean all subordinate state (policies/storage) when an entity is removed, rather than only clearing top-level flags/records.

### Proof of Concept
Conceptual reproduction (would need a Devin session to write/execute against a running java-tron node):
1. Deploy contract `A` from address `X` with nonce `n` to derived address `addr = generateContractAddress(X, n)`; have `A`'s constructor/logic `SSTORE` a nonzero value into slot `S`.
2. Call `A.SUICIDE()`, triggering `TransactionTrace.deleteContract(addr)`, which deletes account/code/contract/abi records but leaves `StorageRowStore` entry for `(addrHash(addr), S)`.
3. From address `X`, with nonce again equal to `n` (e.g., by resetting nonce indirectly through re-deployment sequencing, or engineering an address collision through repeated deploy/destroy cycles), deploy a new, unrelated contract `B` to the same `addr`.
4. Have `B` perform `SLOAD(S)` without ever writing to `S` first; observe it returns the stale nonzero value left by `A`, demonstrating the leaked/reachable stale state from the "removed" contract.

  private byte[] compose(byte[] key, byte[] addrHash) {
    if (contractVersion == 1) {
      key = Hash.sha3(key);
    }
    byte[] result = new byte[key.length];
    arraycopy(addrHash, 0, result, 0, PREFIX_BYTES);
    arraycopy(key, PREFIX_BYTES, result, PREFIX_BYTES, PREFIX_BYTES);
    return result;
  }

  // 32 bytes
  private static byte[] addrHash(byte[] address) {
    return Hash.sha3(address);
  }

  private static byte[] addrHash(byte[] address, byte[] trxHash) {
    if (ByteUtil.isNullOrZeroArray(trxHash)) {
      return Hash.sha3(address);
    }
    return Hash.sha3(ByteUtil.merge(address, trxHash));
  }

  public void generateAddrHash(byte[] trxId) {
    // update addreHash for create2
    addrHash = addrHash(address, trxId);
  }

@Component

    super(dbName);
  }

  @Override
  public StorageRowCapsule get(byte[] key) {

  }
