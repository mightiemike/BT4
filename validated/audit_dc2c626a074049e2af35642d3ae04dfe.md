Based on my investigation, I've confirmed the mechanics of the strongest reachable analog to the reported bug class in this codebase.

### Title
Global-contract owner can front-run pending function calls by redeploying `AccountId`-mode code in the same chunk, changing execution semantics for already-submitted deposits/calls - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
The Teller report describes a privileged party (market owner) front-running a borrower's already-submitted transaction by changing a parameter (payment default duration) with no timelock, so the borrower's transaction executes against terms it never agreed to, letting the owner extract value. The reachable nearcore analog is `GlobalContractDeployMode::AccountId`: any account that deploys a global contract under this mode can redeploy new code for that same `AccountId` identifier at any time, and because of `GlobalContractSameChunkCallFix`, this redeployment can be observed by a `FunctionCall` receipt executing in the very same chunk. A dependent account's `UseGlobalContract`/`FunctionCall` receipts resolve the contract code dynamically from trie state at execution time, not at submission time, so the code that actually runs can differ from the code the caller inspected/expected when constructing and signing their transaction with an attached deposit.

### Finding Description
`DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` associates a global contract with the deploying account id rather than a fixed code hash — explicitly documented as mutable: "This allows the owner to update the contract for all its users" [1](#0-0) . Deploying again with the same `AccountId` identifier simply increments a nonce and overwrites the `TrieKey::GlobalContractCode` entry in `apply_distribution_current_shard` [2](#0-1) , with the freshness check only enforcing a monotonic nonce (`incoming_nonce < stored_nonce` rejected, but the same-or-higher nonce always overwrites) [3](#0-2) .

A dependent account only stores a `GlobalByAccount(id)` pointer via `UseGlobalContractAction` [4](#0-3) ; the actual code is resolved fresh at every `FunctionCall` execution through `RuntimeContractIdentifier::resolve`, which reads whatever code hash is currently stored under `GlobalContractCode{AccountId}` in the trie [5](#0-4) . There is no per-transaction pinning of the code version the caller intended to invoke.

Critically, `GlobalContractSameChunkCallFix` was added specifically to make a same-chunk deploy-then-call sequence succeed, by recording the just-deployed code in the in-memory contract tracker so it is visible to a call in the same chunk even without a warm compiled-contract cache [6](#0-5) , confirmed by the dedicated regression test `test_global_contract_same_chunk_call_succeeds_with_cold_cache` which deploys, uses, and calls the global contract all within one `apply` invocation and asserts the call executes against the just-deployed code [7](#0-6) . This is the direct mechanical enabler of the front-run: the owner's redeploy transaction, if included in the same chunk as (or any chunk prior to) a victim's pending `FunctionCall`, is guaranteed to take effect for that victim's call — there is no timelock, no minimum-effective-height, and no opt-in confirmation step analogous to a bid/loan-acceptance flow.

This mirrors the Teller bug class precisely: an account that other unprivileged users have chosen to depend on (via `UseGlobalContractAction`, analogous to selecting a market) can unilaterally and instantly change the code (analogous to the payment-default-duration parameter) that governs the execution of a transaction the victim already signed and submitted, extracting value the victim did not consent to.

### Impact Explanation
A victim who calls a function on an account using `GlobalByAccount` code (e.g. one that accepts an attached deposit and performs some domain logic) can have that deposit misappropriated if the owner front-runs with a redeploy that changes the method's behavior (e.g. redirecting the deposit or logic outcome) before the victim's `FunctionCall` executes in the same or a later chunk. Because deposits and prepaid gas are already debited from the victim's account balance at the point the receipt is created and code is resolved dynamically at execution, this is a genuine unauthorized value-movement vector rather than a resource-only griefing bug, satisfying the "concrete unauthorized value movement" bar.

### Likelihood Explanation
Reachable purely through normal, permissionless transactions: any account can deploy a `GlobalContractDeployMode::AccountId` contract, get other unprivileged users to opt in via `UseGlobalContractAction`, and later resubmit `DeployGlobalContractAction` with updated code timed to land in the same chunk as a victim's pending call — no validator, network, or operator privilege is required, only normal transaction submission and gas-price/inclusion timing that any RPC caller controls.

### Recommendation
Consider pinning the global contract code hash/version referenced by a receipt at the time the `UseGlobalContractAction`/`FunctionCall` receipt is created (rather than re-resolving dynamically at execution), or requiring a minimum activation delay (number of blocks) before a redeployed `AccountId`-mode global contract becomes callable, giving dependents a window to react. At minimum, document and warn integrators that `AccountId`-mode global contracts carry an unbounded, untimed rug-pull risk for any in-flight receipt targeting a dependent account, and steer security-sensitive use cases toward the immutable `CodeHash` deploy mode.

### Proof of Concept
1. Account `owner` deploys global contract V1 (`GlobalContractDeployMode::AccountId`) with a benign `pay(deposit)` method that forwards `deposit` to `msg.predecessor`.
2. Account `victim` submits `UseGlobalContractAction(AccountId(owner))` then a `FunctionCall("pay")` with an attached deposit, expecting V1 semantics.
3. Before `victim`'s `FunctionCall` receipt is applied (same chunk is sufficient per `GlobalContractSameChunkCallFix`, see `test_global_contract_same_chunk_call_succeeds_with_cold_cache` [8](#0-7) ), `owner` submits `DeployGlobalContractAction` V2 that rewrites `pay` to instead forward the deposit to `owner` itself.
4. `apply_distribution_current_shard` overwrites `GlobalContractCode{AccountId(owner)}` and records the deploy for same-chunk visibility [9](#0-8) .
5. `victim`'s `FunctionCall` executes against V2 (resolved dynamically via `RuntimeContractIdentifier::resolve` [5](#0-4) ), and the deposit is redirected to `owner` instead of the semantics `victim` signed up for — with no protocol-level timelock or confirmation step preventing it.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

// Checks if the incoming nonce is fresh and updates the stored nonce. Returns
// true if the nonce is fresh, false if it's stale. The nonce is set
// immediately and the freshness check allows the same nonce (>=).
fn check_and_update_nonce(
    global_contract_data: &GlobalContractDistributionReceipt,
    identifier: &GlobalContractCodeIdentifier,
    state_update: &mut TrieUpdate,
) -> Result<bool, RuntimeError> {
    let nonce_key = TrieKey::GlobalContractNonce { identifier: identifier.clone() };
    let stored_nonce = get_nonce(state_update, &nonce_key)?;
    let incoming_nonce = global_contract_data.nonce();

    // Allow the same nonce since the nonce is updated immediately when
    // initiating distribution to prevent multiple distributions with the same
    // nonce from being initiated.
    if incoming_nonce < stored_nonce {
        return Ok(false);
    }

    set_nonce(state_update, nonce_key, incoming_nonce);
    Ok(true)
}

/// Reproduces the problem fixed by `GlobalContractSameChunkCallFix`.
/// Deploying a global contract and calling it in the same chunk should work, even without contract
/// cache.
#[test]
fn test_global_contract_same_chunk_call_succeeds_with_cold_cache() {
    let owner: AccountId = "global_owner.near".parse().unwrap();
    let user = alice_account();
    let (runtime, tries, root, mut apply_state, signers, epoch_info_provider) = setup_runtime(
        vec![user.clone(), owner.clone()],
        Balance::from_near(1_000_000),
        Balance::from_near(500_000),
        Gas::from_teragas(1000),
    );
    let user_signer = signers[0].clone();
    // A cache that never serves the artifact, forcing the same-chunk call to
    // depend on the recorded deploy (or on committed storage, which is absent).
    apply_state.cache = Some(Box::new(NoContractRuntimeCache));

    let code = ContractCode::new(near_test_contracts::trivial_contract().to_vec(), None);

    // 1) Distribute the global contract (AccountId identifier mode).
    let distribution_receipt = Receipt::new_global_contract_distribution(
        owner.clone(),
        GlobalContractDistributionReceipt::new(
            GlobalContractIdentifier::AccountId(owner.clone()),
            apply_state.shard_id,
            vec![],
            code.code().to_vec().into(),
            0,
        ),
    );

    // 2) Point the user account at the global contract.
    let use_receipt = create_receipt_with_actions(
        user.clone(),
        user_signer.clone(),
        vec![Action::UseGlobalContract(Box::new(UseGlobalContractAction {
            contract_identifier: GlobalContractIdentifier::AccountId(owner),
        }))],
    );

    // 3) Call the global contract from the user account, in the same chunk.
    let call_receipt = create_receipt_with_actions(
        user,
        user_signer,
        vec![Action::FunctionCall(Box::new(FunctionCallAction {
            method_name: "main".to_string(),
            args: vec![],
            gas: Gas::from_teragas(10),
            deposit: Balance::ZERO,
        }))],
    );

    let apply_result = runtime
        .apply(
            tries.get_trie_for_shard(ShardUId::single_shard(), root),
            &None,
            &apply_state,
            &[distribution_receipt, use_receipt, call_receipt.clone()],
            SignedValidPeriodTransactions::empty(),
            &epoch_info_provider,
            Default::default(),
        )
        .unwrap();

    // The same-chunk call must execute, not degrade to a CodeDoesNotExist no-op.
    let call_outcome = apply_result
        .outcomes
        .iter()
        .find(|outcome| outcome.id == *call_receipt.receipt_id())
        .expect("function call outcome should be present");
    assert_matches!(

        ExecutionStatus::SuccessValue(_),
        "same-chunk call to a just-distributed global contract must succeed with a cold cache"
