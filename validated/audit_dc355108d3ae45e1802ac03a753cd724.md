### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the invariant check used by `db-tool replay-on-archive` and the chunk executor's replay verifier to confirm a locally re-executed transaction matches the authenticated, backed-up `TransactionInfo` — validates only `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash`. It explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which are the fields that actually authenticate the Merkle/JMT state root of the ledger at that version.

### Finding Description
`ensure_match_transaction_info` is the sole per-transaction gate that decides whether locally computed execution results are accepted as consistent with an externally supplied, presumably-authenticated `TransactionInfo` (e.g., pulled from a backup or an epoch-ending ledger info-anchored source). It checks execution status, gas used, the write-set hash against `state_change_hash`, and the event root hash — but the function's own comment documents that it deliberately skips the checkpoint hashes: [1](#0-0) 

Specifically: [2](#0-1) 

These `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields are exactly the values that bind a `TransactionInfo` (and hence the accumulator leaf built from it) to the Sparse-Merkle/Jellyfish-Merkle state root at that version — the write-set-hash and event-root-hash checks say nothing about whether the *cumulative* state tree produced by applying that write set actually matches the expected root. A transaction can therefore pass this check even if the locally rebuilt state tree (state root, hot-state root, or position-state root) is wrong, so long as the individual write set and events for that one transaction happen to match.

This check is directly used in the replay-verify tool's core execute-and-verify loop: [3](#0-2) 

and referenced from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/cli/src/commands.rs`, and `aptos-move/aptos-debugger/src/aptos_debugger.rs`, all of which rely on this exact function as their correctness oracle for accepting replayed/rebuilt ledger state.

Aptos DB's own reader supports a feature-gated (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) position-state summary/root mechanism (`storage/aptosdb/src/db/aptosdb_reader.rs`, `position_buffered_state::PositionLedgerStateWithSummary`), showing that `position_state_checkpoint_hash` is a real, security-relevant root that can diverge independently of the write set of any single transaction — precisely the scenario the code comment warns about.

### Impact Explanation
If the underlying state tree construction (state Merkle root, hot-state root, or the newer position-state root) has any divergence bug — from a JMT construction bug, an execution-output aggregation bug, or a malicious/corrupted backup source that supplies correct per-txn write sets/events but a forged checkpoint hash lineage — `ensure_match_transaction_info` will report success. This means:
- `replay-on-archive` (the tool operators/auditors use to authenticate historical ledger state against backups) can silently certify a chain segment as correctly replayed even though the state root diverges from the correct VM result.
- Any caller depending on this function as an integrity oracle (chunk executor replay verification, CLI, debugger) inherits the same blind spot.

This matches the required "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated ... output bound to the wrong version, object, or proof context" impact classes: a downstream root-of-trust operation accepts an incorrect state-commitment as valid.

### Likelihood Explanation
The gap is explicit and documented in-code (not speculative), and the feature it interacts with (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` / position-state roots) exists in the codebase and is under active development, per the TODO. The likelihood of an attacker being able to *exploit* it depends on being able to influence the backup/replay source’s per-transaction write set and events while diverging the state root construction — this requires a corrupted or adversarial backup input, or a genuine (accidental) divergence bug in state root computation elsewhere in the codebase, which this check would then fail to catch. I could not fully trace whether `chunk_executor/mod.rs`'s own commit path (as opposed to `replay_on_archive.rs`) independently re-derives and checks the state root through a separate mechanism (e.g., `DoStateCheckpoint`/ledger info comparison) before final commit, which would reduce impact to the specific replay-verify/debugging tools rather than the live consensus/state-sync commit path. This limits confidence that the gap is reachable on the primary consensus commit path versus being confined to auditing/replay tooling.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the expected `TransactionInfo`) against values computed from actual local execution/state-checkpoint output, rather than relying solely on per-transaction write-set and event hashes. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-dependent replay-verify paths so they cannot report success while these root fields remain unchecked, and update `replay_on_archive.rs` to fail loudly (not silently pass) when checkpoint hashes are absent-but-expected.

### Proof of Concept
Local code proof (no live network needed): call `TransactionOutput::ensure_match_transaction_info` with a `TransactionOutput` whose `write_set`/`events` match `expected_write_set`/`expected_events` (and thus match `state_change_hash`/`event_root_hash`), but whose corresponding `TransactionInfo`'s `state_checkpoint_hash` (or `position_state_checkpoint_hash`) differs from the actual root that would be produced by applying `write_set` to the prior state tree. The function returns `Ok(())` unconditionally because the checkpoint-hash fields are never read in the comparison body: [4](#0-3) 
This is confirmed by the call site in `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs:392-397`, which treats a non-error return as full verification success for that transaction.

**Uncertainty**: I was unable to verify within the available context whether the live block-execution commit path (as opposed to the offline replay-verify tool) uses a separate, independent state-root comparison before persisting to `AptosDB`, which would determine whether this gap is confined to auditing tooling or also affects the primary consensus/state-sync commit flow. A Devin session with full repository access would be needed to trace `DoStateCheckpoint`, `chunk_executor::apply_chunk`, and the state-sync bootstrapper's use of ledger-info-derived roots to conclusively establish whether this gap is reachable on the mainnet commit path or restricted to the replay-verify/debugger tools.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
