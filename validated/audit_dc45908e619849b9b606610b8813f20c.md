## Title
`ALLOW_HARDEN_RESOURCE_CALCULATION` converts silently-overflow-tolerant bandwidth/energy accounting into checked arithmetic that throws `ArithmeticException`, halting transaction/block processing once activated - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The external report's bug class is: code written assuming silent integer overflow/underflow (Uniswap's `currentCumulativePrices`) breaks once the arithmetic is switched to a variant that reverts on overflow (Solidity ≥0.8). The same structural pattern exists in java-tron's resource-accounting code, where an `ALLOW_HARDEN_RESOURCE_CALCULATION` chain parameter switches bandwidth/energy usage math from ordinary `long` arithmetic (which wraps silently on overflow) to `BigInteger`/`StrictMathWrapper` exact arithmetic that throws `ArithmeticException` on overflow.

### Finding Description
`RepositoryImpl.increase()` computes a decayed sliding-window average of resource usage [1](#0-0) . When `hardenResourceCalculation()` is true, the average is computed with `BigInteger` and converted back with `longValueExact()`/`StrictMathWrapper.addExact`, both of which throw `ArithmeticException` if the true mathematical result does not fit in a `long` [2](#0-1) . The same pattern is repeated in `usageToBalance()`, `calculateGlobalEnergyLimit()`, `BandwidthProcessor.calculateGlobalNetLimit`, and `EnergyProcessor.updateAdaptiveTotalEnergyLimit` — all gated by the same flag. Tests in the repo explicitly document this divergence: `RepositoryImplHardenTest.testIncreaseOverflowDetectedWithHardening` shows the hardened path throwing `ArithmeticException` for values that the legacy path silently tolerates (`testIncreaseOverflowSilentWithoutHardening` completes without error on the identical inputs) [3](#0-2) . `CalculateGlobalLimitHardenTest` shows the same for the global bandwidth/energy limit and adaptive multiplier calculations [4](#0-3) [5](#0-4) .

This is the same root cause class as the report: switching to "checked"/exact arithmetic in code paths that previously (and by design, given the on-chain accounting relies on values wrapping/rounding rather than aborting) tolerated overflow turns previously-successful operations into thrown exceptions. `RepositoryImpl.increase()`/`getUsage()`/`usageToBalance()` and the bandwidth/energy limit calculators are executed on every account bandwidth/energy consumption and recovery computation — i.e., inside ordinary, unprivileged user transaction processing (any TRX/TRC10/TVM transaction that consumes bandwidth or energy), not in a privileged-only code path.

`ALLOW_HARDEN_RESOURCE_CALCULATION` is a normal chain-parameter proposal gated only by a fork-block-version check (`VERSION_4_8_2`) with no other precondition, and once passed cannot be reset (self-guards against re-proposing) [6](#0-5) , meaning this is a real activatable network-wide behavior change, not a hypothetical/test-only toggle.

### Impact Explanation
Once `ALLOW_HARDEN_RESOURCE_CALCULATION` is enacted by SR governance, any account/global state that drives these formulas into a numeric range where the exact `BigInteger` result exceeds `Long.MAX_VALUE` (e.g., very large frozen balances, large `totalNetWeight`/`totalEnergyWeight` combined with small denominators, or adaptive-limit multiplier interactions as shown in the test with `Long.MAX_VALUE` target limits) will cause `ArithmeticException` to propagate out of core resource-accounting paths used on every transaction (bandwidth/energy consumption, `getAccountLeftEnergyFromFreeze`, `getAccountEnergyUsage`, `calculateGlobalEnergyLimit`, `updateAdaptiveTotalEnergyLimit`). This can produce transaction processing failures/reverts or, if hit during block-level maintenance-cycle recalculation (adaptive limits, global net/energy limit), a chain-wide processing halt/consensus divergence, which is a critical availability impact for a resource-accounting subsystem that every unprivileged user transaction depends on.

### Likelihood Explanation
Likelihood is moderate: it requires (1) SR governance to actually enact `ALLOW_HARDEN_RESOURCE_CALCULATION`, and (2) account/global state to reach the specific numeric boundary that overflows a 64-bit `long` under the exact arithmetic. Large frozen-balance/weight values are realistic on a live chain with billions of TRX in stake, and the existing test suite (`CalculateGlobalLimitHardenTest`, `RepositoryImplHardenTest`) already demonstrates these boundary conditions are reachable with plausible values (e.g., `Long.MAX_VALUE/4` frozen balance), not solely adversarially engineered ones.

### Recommendation
For any resource-accounting formula gated by `allowHardenResourceCalculation()`, avoid `longValueExact()`/`addExact` failing hard on overflow; instead clamp/saturate to `Long.MAX_VALUE` (or otherwise fail closed in a way that does not abort transaction/block processing), and add explicit upper-bound validation on the chain parameters/state (frozen balance, `totalNetWeight`, `totalEnergyWeight`, adaptive multiplier) that feed these calculations so the exact arithmetic path cannot exceed 64-bit range during normal operation. Add regression tests around the maintenance-cycle path (adaptive resource limit updates) specifically, since that runs unconditionally during block processing rather than only within a single actuator's `try/catch`.

### Proof of Concept
Existing repository tests already reproduce the divergence deterministically:
- `RepositoryImplHardenTest.testIncreaseOverflowDetectedWithHardening` / `testIncreaseOverflowSilentWithoutHardening` [3](#0-2)  — identical `lastUsage = Long.MAX_VALUE/10` input succeeds under legacy arithmetic and throws `ArithmeticException` under the hardened path.
- `CalculateGlobalLimitHardenTest.testGlobalNetLimitOverflowDetectedWithHardening` [4](#0-3)  and `testUpdateAdaptiveLimitMultiplierOverflowDetected` [5](#0-4)  — both assert `ArithmeticException` is thrown from core resource-limit calculators once hardening is enabled, for state values that are plausible on a production chain (large frozen balances / `Long.MAX_VALUE`-scale energy limits).

  private long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenResourceCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay, VMConfig.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }

  private long getUsage(long usage, long windowSize) {
    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(usage)
          .multiply(BigInteger.valueOf(windowSize))
          .divide(BigInteger.valueOf(precision))
          .longValueExact();
    }
    return usage * windowSize / precision;
  }

  private boolean hardenResourceCalculation() {
    return VMConfig.allowHardenResourceCalculation();
  }
