### Title
`liquidate-multi()` partial-failure absorption strands seized collateral and un-socialized bad debt when `liquidate()` aborts after committed sub-calls - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi()` maps `call-liquidate()` over a list of positions without checking or propagating each result, and always returns `(ok ...)` for the whole batch [1](#0-0) . `call-liquidate()` invokes the public `liquidate()` function directly, in-contract (not via `contract-call?`) [2](#0-1) . Because `liquidate()`'s early state-mutating steps are performed through discrete `contract-call?`s to `.v0-market-vault`, and only the *later* bad-debt-socialization step can abort via `asserts!`, a failure there returns `(err ...)` from `liquidate()` without unwinding the already-committed earlier `contract-call?`s — since the enclosing transaction (`liquidate-multi`) still returns `ok` overall. This is the same bug class as the referenced report: a step that fails after partial state has already been durably committed, with no mechanism to roll back or retry that partial state, silently strands value.

### Finding Description
`liquidate()` performs its state-mutating operations in strict sequence via separate `contract-call?` boundaries:

1. `vault-system-repay` pulls the debt token from the liquidator and repays the vault [3](#0-2) .
2. `debt-remove-scaled` reduces the borrower's tracked scaled debt by `scaled-to-remove` [4](#0-3) .
3. `collateral-remove` transfers `coll-final` collateral to the liquidator [5](#0-4) .

Each of these is its own `contract-call?` to `.v0-market-vault`, so each commits independently as soon as it returns `ok`.

Only *after* these three calls succeed does `liquidate()` check `no-collateral-left` and, if true, attempt to socialize the residual (uncollateralized) debt via a `fold` over `socialize-debt-asset`, gated by an `asserts!`: [6](#0-5) 

`socialize-debt-asset` itself calls `vault-socialize-debt`, refreshes the index cache, and calls `debt-remove-scaled` for the residual — each guarded with `unwrap!` that sets `{success: false}` on failure rather than aborting the fold immediately [7](#0-6) . If any of these sub-steps fails (e.g., `debt-remove-scaled` on the residual debt fails, or `vault-socialize-debt` fails for a bad-debt-list entry), the fold accumulator flips to `success: false`, and the subsequent `asserts!` fires `ERR-BAD-DEBT-SOCIALIZATION-FAILED`, causing `liquidate()` to return `(err ...)`.

When `liquidate()` is invoked directly at the top level (a normal single `liquidate` call/transaction), this `err` return causes the entire transaction — including the earlier successful `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` — to be rolled back by Stacks' standard atomic-transaction semantics. But when invoked through `liquidate-multi`, the calling chain is `liquidate-multi -> (map call-liquidate positions) -> call-liquidate -> (liquidate ...)`, all within the same contract and with no intervening `contract-call?` boundary above `liquidate()`. `liquidate-multi` unconditionally wraps the whole `map` result in `ok` [8](#0-7) , so the transaction as a whole succeeds. Because Stacks/Clarity's rollback-on-error guarantee is scoped to the top-level transaction result (and to individual `contract-call?` boundaries, not to arbitrary in-contract function calls whose `Response` is merely collected and ignored), the state changes committed in steps 1–3 for that specific position are **not** undone even though `liquidate()`'s own logical result for that entry is `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.

### Impact Explanation
For the affected position: the collateral-backed portion of the liquidation fully executes (liquidator pays down debt and receives collateral), but the residual bad debt is neither removed from the borrower's tracked obligation nor socialized into the vault's `lindex` write-down. The borrower is left with zero collateral and outstanding (unrecoverable) debt that the vault's accounting still treats as healthy, live debt continuing to accrue interest. This inflates the vault's reported total assets beyond what is actually recoverable, silently breaking the assets-vs-liabilities invariant that depositor share pricing depends on — a form of protocol insolvency that manifests later as depositors being unable to redeem their full share value (permanent/temporary freezing of funds for depositors). This matches the report's core bug class ("failed step leaves earlier, already-committed effects unreversed") applied to Zest's batch-liquidation entry point, which is exactly the "fold that absorbs failure" / "multi-step entry point that strands value on abort" analog called out as in-scope.

### Likelihood Explanation
`liquidate-multi` is designed and documented to tolerate per-position failures without reverting the batch ("Failed liquidations return error codes but don't revert entire batch") [9](#0-8) . Any liquidator batching multiple undercollateralized positions where at least one position triggers the "no collateral left" bad-debt path can hit this window; the socialization fold has multiple `unwrap!` points (`vault-socialize-debt`, `vault-accrue`, `debt-remove-scaled`) any of which failing (e.g. due to a pause state, a stale/failed price resolve during `vault-accrue`, or a mask/user-id mismatch) reaches this state. No attacker collusion or DAO compromise is required — it can occur from ordinary liquidation bot batching under adverse (but plausible) sub-call conditions.

### Recommendation
In `call-liquidate`, explicitly check the result of `liquidate(...)`; if it errors, ensure no partial vault-side mutation for that position is left committed — e.g., restructure `liquidate()` so the bad-debt-socialization step (and the `asserts!` gating it) happens *before* any irreversible transfers (`collateral-remove`, `vault-system-repay`), or make the whole per-position flow atomic by wrapping it in its own `contract-call?` boundary (calling `liquidate` via `(contract-call? .v0-4-market liquidate ...)`) so a failure at any step rolls back that position's entire liquidation instead of leaving partial state.

### Proof of Concept
1. A borrower's position becomes liquidatable and, once liquidated, will leave `no-collateral-left = true` with a nonzero residual/bad debt (`debt-updated > 0`).
2. A liquidator calls `liquidate-multi` with a list including this position.
3. Inside `call-liquidate -> liquidate`: `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` all succeed and commit (collateral is sent to the liquidator, matched debt removed) [10](#0-9) .
4. The subsequent `fold socialize-debt-asset` fails on one of its `unwrap!` calls (e.g. `vault-socialize-debt` returns an err because of a pause flag or index mismatch), setting `success: false` [7](#0-6) .
5. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fires, and `liquidate()` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [6](#0-5) .
6. `call-liquidate` returns this err value unchecked into the `map`; `liquidate-multi` returns `(ok (list ... (err ERR-BAD-DEBT-SOCIALIZATION-FAILED) ...))` [11](#0-10) .
7. The transaction succeeds (top-level `ok`), so steps from (3) remain permanently committed: the liquidator keeps the seized collateral and the matched debt reduction, but the borrower's residual bad debt is never removed nor socialized into the vault's lindex, leaving the vault's tracked debt overstated relative to recoverable value.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
