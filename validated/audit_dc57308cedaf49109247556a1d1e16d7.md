### Title
Non-deterministic `java.lang.Math.pow` in `ContractStateCapsule.catchUpToCycle` causes dynamic-energy-factor divergence across CPU architectures/JDKs when `allowStrictMath=0` - ([File: chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java])

### Summary
When the chain parameter `allowStrictMath` is 0 (the historical/default state until activated by governance), `ContractStateCapsule.catchUpToCycle` computes `decreasePercent` with `Maths.pow(base, cycleCount, false)`, which on different platforms resolves to different `MathWrapper.pow` implementations — a raw, non-deterministic `java.lang.Math.pow` on x86 versus a hardcoded historical lookup table with `StrictMath.pow` fallback on ARM. An unprivileged attacker who simply times `TriggerSmartContract` calls across multiple maintenance cycles can force `cycleCount`/base combinations that are absent from the ARM correction table, producing different `getEnergyFactor()` results (and thus different `contract_state` values and energy charges) on nodes with different CPU architectures for the identical transaction history.

### Finding Description
`ContractStateCapsule.catchUpToCycle` computes the dynamic-energy decrease factor via: [1](#0-0) 
which delegates to `Maths.pow(a, b, useStrictMath)`: [2](#0-1) 
When `useStrictMath` (`VMConfig.allowStrictMath()`) is `false`, this calls `MathWrapper.pow`, which has two divergent implementations shipped for different CPU architectures. On x86 it is a raw, unguaranteed `Math.pow`: [3](#0-2) 
On ARM it is patched with a hardcoded table of historically-observed `(a, b) -> result` triples recorded from real mainnet blocks, falling back to `StrictMath.pow` only for unrecorded inputs: [4](#0-3) 
The existence of this ARM-specific correction table is itself evidence that `java.lang.Math.pow` has previously produced architecture-dependent results in production for this exact code path, which is why the project introduced `allowStrictMath`/`disableJavaLangMath` chain parameters loaded via `ConfigLoader` into `VMConfig`: [5](#0-4) 
The call site is reached from ordinary contract execution via `Program.updateContextContractFactor`, invoked while running any TVM contract once `allowDynamicEnergy` is enabled: [6](#0-5) 
An unprivileged account can send ordinary `TriggerSmartContract` transactions against any dynamic-energy-enabled contract, letting `energyUsage` stay below/above `threshold` across several maintenance cycles to make `cycleCount = newCycle - lastCycle` take an attacker-chosen value (simply by waiting/spacing calls), and the base `1 - increaseFactor/DECREASE_DIVISION/precisionFactor` is fixed by chain governance parameters. The attacker only controls `cycleCount` (the exponent), which is enough to hit `(base, cycleCount)` pairs not present in the ARM hardcoded table, forcing that node onto the `StrictMath.pow` fallback while x86 nodes use raw `Math.pow` — producing different double results for identical input, hence different `(long) ((getEnergyFactor() + precisionFactor) * decreasePercent) - precisionFactor` outcomes. No existing check (signature/permission checks, `ForkController` gates, energy accounting) constrains the floating-point result of this computation; the `allowStrictMath` fork flag is precisely the intended remediation, but is off until activated by governance.

### Impact Explanation
This maps to TRON bounty's **consensus divergence** class: nodes running different CPU architectures (or JDK builds with differing `Math.pow` intrinsics) can compute different `getEnergyFactor()` for the same block/transaction history, leading to different energy costs charged to identical calls and a diverging `contract_state` value in the state trie/DB — a chain split risk that requires no privileged role, only ordinary funded-account transactions.

### Likelihood Explanation
Preconditions are realistic and outside attacker control but plausible in the wild: `allowDynamicEnergy=1` and `allowStrictMath=0` describe the network state before the strict-math hard fork is activated by committee vote, which is the default/historical state on any given network prior to activation. Once that state holds, exploitation only requires an unprivileged account to send normal `TriggerSmartContract` transactions timed across several maintenance cycles — no elevated fees beyond normal energy/bandwidth costs, fully repeatable, and requires no signature bypass or privileged address.

### Recommendation
Activate/require `allowStrictMath=1` (and `disableJavaLangMath=1`) as an enforced consensus precondition rather than an optional governance toggle, or unify all platforms on `StrictMath.pow` unconditionally for this dynamic-energy calculation so no architecture-dependent lookup table is needed; remove the historical ARM patch table entirely once `StrictMath` is mandatory everywhere, since it only covers previously-observed inputs and does not protect against new attacker-selected `(base, cycleCount)` pairs.

### Proof of Concept
```java
// JUnit demonstrating that identical (base, cycleCount) inputs can diverge across
// the two shipped MathWrapper implementations when useStrictMath=false.
@Test
public void testCrossPlatformPowDivergence() {
  double base = 1 - (double) 5000L / Constant.DYNAMIC_ENERGY_DECREASE_DIVISION
      / Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
  long cycleCount = 7L; // attacker selects by spacing TriggerSmartContract calls across 7 cycles

  // x86 build path
  double x86Result = x86.org.tron.common.math.MathWrapper.pow(base, cycleCount);
  // ARM build path (falls back to StrictMath only if (base, cycleCount) not in hardcoded table)
  double armResult = arm.org.tron.common.math.MathWrapper.pow(base, cycleCount);

  // With allowStrictMath=0 these can differ in the low mantissa bits for inputs
  // not present in MathWrapper's hardcoded correction table, causing
  // ContractStateCapsule.catchUpToCycle to produce different getEnergyFactor()
  // on x86 vs ARM nodes for the identical transaction sequence.
  Assert.assertNotEquals(Double.doubleToLongBits(x86Result),
      Double.doubleToLongBits(armResult));
}
```
Request-level reproduction: an attacker broadcasts `TriggerSmartContract` transactions against a contract with `allowDynamicEnergy=1` spaced so that `cycleCount>1` at the next call, while the network has `allowStrictMath=0`; nodes on x86 vs ARM (or differing JDK builds) will persist different `energy_factor` values in `contract_state`, verifiable via `Program.updateContextContractFactor` → `ContractStateCapsule.catchUpToCycle`.
