### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` permanently burns the deleted account's balance when the beneficiary does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction.beneficiary_id` is only checked for syntactic validity as an `AccountId` (yielding `InvalidAccountId` if malformed) but nothing verifies that the beneficiary account actually *exists*. When the delete executes, the entire remaining balance is unconditionally routed to a refund receipt addressed to `beneficiary_id`; if that account does not exist, the refund fails and the funds are permanently burned rather than returned to the signer or any recoverable party.

### Finding Description
`action_delete_account` computes the account's remaining balance and unconditionally pushes a balance-refund receipt to the (unverified) `beneficiary_id`, then deletes the source account: [1](#0-0) 

This refund receipt is a system-predecessor ("refund") receipt. When it is later processed as a `Transfer` action against `beneficiary_id`, `check_account_existence` requires `implicit_creation_allowed`, which explicitly forbids refunds from creating any account: [2](#0-1) 

So if `beneficiary_id` is a valid-format account ID that simply does not exist (never registered, mistyped, or since deleted), the refund transfer fails with `AccountDoesNotExist`. Per the refund-failure handling in the apply loop, a failed refund's deposit is burned rather than returned anywhere: [3](#0-2) 

This is also documented as expected behavior in the protocol spec ("If the execution of a refund fails, the refund amount is burnt") and acknowledged directly in the test suite, where a passing test must first *create* the beneficiary account or the deletion's balance transfer would bounce back and burn: [4](#0-3) [5](#0-4) 

The only validation performed on `beneficiary_id` at the action-validation layer is a well-formedness check (`InvalidAccountId`) per the runtime spec docs — there is no existence check: [6](#0-5) 

### Impact Explanation
Any account owner (an unprivileged transaction signer) submitting a `DeleteAccount` action with a `beneficiary_id` that is well-formed but does not correspond to an existing account will have their entire remaining account balance irrecoverably burned instead of transferred. This is a direct, protocol-level "loss of funds to an unchecked destination" analogous to the reported `address(0)` issue — the destination account is never validated to exist before the value transfer is committed to, and by the time the transfer fails, the source account has already been deleted, so there is no path to recover or retry.

### Likelihood Explanation
This requires no privileged access and no cooperation from other parties — a single signed `DeleteAccountAction` transaction with an arbitrary (mistyped, unregistered, or previously-deleted) `beneficiary_id` account triggers the loss. This is easy to trigger accidentally (typo in beneficiary account, forgetting the beneficiary needs to be created first, or beneficiary account being deleted between signing and inclusion) and there is no user-facing warning enforced by the protocol before the action executes.

### Recommendation
Before creating the balance-refund receipt in `action_delete_account`, or as part of `check_actor_permissions`/`check_account_existence` validation for `DeleteAccount`, verify that `beneficiary_id` corresponds to an existing account (or restrict it to accounts known to exist, e.g. by requiring an existence check with an explicit error such as `BeneficiaryAccountDoesNotExist`) before allowing the deletion to proceed and burn state. Alternatively, disallow burning on refund failure specifically for the deletion’s own balance payout, and instead reject the `DeleteAccount` action outright if the beneficiary does not exist.

### Proof of Concept
1. Account `alice` holds a balance and has no locked stake.
2. `alice` signs a transaction containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })` where `nonexistent.near` is a syntactically valid but never-created account ID.
3. `action_delete_account` runs successfully (per `runtime/runtime/src/actions.rs:380-386`), removes `alice`'s account, and emits a `Receipt::new_balance_refund(&"nonexistent.near", alice_balance)`.
4. When this refund receipt is processed, `check_account_existence` rejects the `Transfer` since `implicit_creation_allowed` returns `false` for refunds (`runtime/runtime/src/actions.rs:929-933`), producing `AccountDoesNotExist`.
5. Per `runtime/runtime/src/lib.rs:1047-1054`, because the refund's predecessor is `system` and the result is an error, `alice_balance` is added to `other_burnt_amount` — permanently destroyed, matching the behavior confirmed by the existing test `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6870-6927`) and the note in `delete_after_init_removes_account` (`runtime/runtime/src/tests/apply.rs:6355-6357`).
