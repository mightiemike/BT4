### Title
ETH-implicit account creation trusts a hardcoded `eth_wallet_global_contract_hash` constant with no on-chain existence check, permanently bricking accounts and freezing deposits if the hash is wrong - (File: `runtime/near-wallet-contract/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
When the `EthImplicitGlobalContract` protocol feature is active, any unprivileged signer can create an ETH-implicit account simply by sending a `Transfer` to a `0x…` account ID. Account creation is handled by `action_implicit_account_creation_transfer`, which sets the new account's contract to `AccountContract::Global(global_contract_hash)`, where `global_contract_hash` comes from the hardcoded constant `eth_wallet_global_contract_hash(chain_id)`. This is functionally identical to the reported bug class: a compile-time/hardcoded hash constant is trusted to reference a deployed artifact (there, `POOL_INIT_CODE_HASH` for a CREATE2 pool address; here, the wallet-contract global-code hash for an `AccountContract::Global` reference), with no verification that the referenced object actually exists at creation time.

### Finding Description
`eth_wallet_global_contract_hash` in `runtime/near-wallet-contract/src/lib.rs:89-105` returns hardcoded `CryptoHash` byte arrays for `MAINNET`/`MOCKNET`/`TESTNET` (and derives it from an embedded WASM for other chains): [1](#0-0) 

This value is consumed directly in the implicit-account-creation path, `action_implicit_account_creation_transfer`, for the `EthImplicitAccount` branch: [2](#0-1) 

The account is created with `AccountContract::Global(global_contract_hash)` unconditionally — there is no check in this function (or in `GlobalContractAccessExt::hash`) that a global contract with that exact code hash has actually been distributed/exists on-chain: [3](#0-2) 

`GlobalContractIdentifier::CodeHash(hash).hash()` simply echoes the hash back with no existence check (only the `AccountId` identifier variant does a trie lookup). The actual code-existence check only happens later, at contract-fetch/prepare time, via `ContractStorage::get`, which just returns `None` when the trie is missing the value: [4](#0-3) 

The project's own test suite demonstrates the exact failure mode this constant enables: using/calling a global-contract identifier whose code hash does not correspond to any deployed contract fails with `ActionErrorKind::GlobalContractDoesNotExist` (for `UseGlobalContract`) or produces a code-not-found/no-op outcome for `FunctionCall`: [5](#0-4) 

For ETH-implicit accounts specifically, per the protocol docs, once created these accounts "can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added": [6](#0-5) 

Combining these facts: if the hardcoded `eth_wallet_global_contract_hash` constant for a chain ever does not match the code hash of the global wallet contract actually deployed/distributed for that chain (e.g. stale value after a wallet-contract upgrade, or a value simply never matching what governance deployed), then:
1. Any user can still trigger creation of the ETH-implicit account by a plain `Transfer` (this path performs no code-existence validation).
2. The created account permanently references a `Global` code hash for which no contract exists in the trie/global-contract distribution.
3. Every subsequent interaction with the account (via `rlp_execute` on the Wallet Contract, or any `FunctionCall`) fails, because the runtime cannot resolve the contract code for that hash.
4. Because ETH-implicit accounts cannot be deleted and cannot have a full-access key added, there is no path for the depositor/owner to recover the attached balance.

This is precisely analogous to the reported bug: the periphery contract computed a pool address using a wrong hardcoded init-code hash, so `mint()` (and effectively all liquidity operations) reverted against a pool that could never be resolved correctly — a hardcoded hash constant broke the mapping from action to deployed code, making the intended operation permanently unusable.

### Impact Explanation
This maps to the accepted impact category "permanently frozen funds": a `Transfer` action that creates an account is a normal, unprivileged, single-transaction-reachable operation. If the hardcoded global-contract hash constant is stale/incorrect for a given chain/version, every newly created ETH-implicit account on that chain would be unusable — the account can receive a deposit but the depositor/owner has no way to spend, transfer out, or even delete the account afterward, since ETH-implicit accounts are restricted to the Wallet Contract's own interface (which can never execute because its code cannot be resolved), and neither `DeleteAccount` nor `AddKey`(FullAccess) is available on this account type. This is a systemic, protocol-level single point of failure: one wrong constant across an entire class of accounts (all `0x…` accounts on that chain), rather than a per-account issue.

### Likelihood Explanation
Likelihood is inherently tied to whether the hardcoded value is kept in lockstep with whatever global contract deployment actually exists on each network. Because:
- The value is a raw byte array baked into source code (`runtime/near-wallet-contract/src/lib.rs:92-102`), with no runtime/on-chain cross-check against the actual global contract's registered code hash, and
- Account creation via `Transfer` performs no existence check before committing the account with `AccountContract::Global(hash)`,

any mismatch between this constant and the genuinely-deployed wallet global contract (introduced by human error during a wallet-contract version bump, chain migration, or genesis misconfiguration) is silently exploitable by ordinary users continuing to create (and fund) ETH-implicit accounts, with no protocol-level safeguard to prevent or flag it. The existing unit test `test_eth_wallet_global_contract_hash_values` only checks the constant's self-consistency against expected literal strings — it does not, and cannot, verify the constant matches whatever is actually deployed on a live network.

### Recommendation
- Before or during ETH-implicit account creation, verify that a global contract exists at `eth_wallet_global_contract_hash(chain_id)` (e.g. by checking `TrieKey::GlobalContractCode` for a `CodeHash` identifier) rather than blindly trusting the constant.
- Consider deriving the constant at genesis/config load time from the deployed global contract's read hash (as is already done for `LOCALNET` via `LOCALNET.read_contract().hash()`), instead of hand-copied literal byte arrays for `MAINNET`/`TESTNET`, eliminating the possibility of divergence.
- Add integration/test-loop coverage that deploys the exact production wallet-contract WASM for a chain and asserts its resulting code hash equals the hardcoded constant, failing CI if they diverge.
- If a mismatch is ever detected in production, provide a recovery mechanism (e.g., an allowed one-time re-pointing of `AccountContract::Global` for affected accounts) so deposits are not unconditionally unrecoverable.

### Proof of Concept
1. Assume/introduce a scenario where `eth_wallet_global_contract_hash(chain_id)` (`runtime/near-wallet-contract/src/lib.rs:89-105`) returns a hash `H` that does not correspond to any global contract actually distributed on the network for that `chain_id` (e.g., simulate by deploying the global wallet contract under a different code, or bumping the wallet contract version without updating this constant).
2. As an ordinary user, submit a `Transfer` action targeting a fresh `0x…` (ETH-implicit) account ID. This is processed by `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:255-269`), which creates the account with `AccountContract::Global(H)` and the transferred deposit, with no check that `H` resolves to any code.
3. Attempt any interaction with the account — an `rlp_execute` relayed transaction or any `FunctionCall` to it. Contract resolution goes through `RuntimeContractIdentifier::resolve`/`GlobalContractAccessExt::hash` (`runtime/runtime/src/contract_code.rs:36-106`) which returns `H` unchanged, and then `ContractStorage::get(H)` (`core/store/src/contract.rs:155-180`) returns `None` because no contract with hash `H` exists — the call cannot execute (mirrors the behavior asserted in `test_use_non_existent_global_contract`, `test-loop-tests/src/tests/global_contracts.rs:55-68`, which shows `GlobalContractDoesNotExist`/failed execution is the concrete, observable outcome of referencing a non-existent global-contract hash).
4. Because ETH-implicit accounts cannot be deleted and cannot receive a `FullAccess` key (`docs/DataStructures/Account.md:119-123`), the deposit from step 2 is now permanently unreachable — there is no valid action sequence that can move or reclaim it.

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }

    pub fn get(&self, code_hash: CryptoHash) -> Option<ContractCode> {
        {
            let guard = self.tracker.lock();
            // The tracker may be finalized before the receipt preparation pipeline calls this function.
            // In this case we should skip checking the tracker and directly read from the storage.
            // Note that this does not cause any correctness issue, because the pipeline stops processing when
            // it hits a new deployment, so the contract requested by the pipeline will not be in the committed or
            // uncommitted deployment list.
            if let Some(tracker) = guard.as_ref()
                && let Some(contract) = tracker.get(code_hash.into())
            {
                return Some(ContractCode::new(contract.code().to_vec(), Some(code_hash)));
            }
        }

        match self.storage.retrieve_raw_bytes(&code_hash) {
            Ok(raw_code) => Some(ContractCode::new(raw_code.to_vec(), Some(code_hash))),
            Err(StorageError::MissingTrieValue(MissingTrieValue { context, hash: _ })) => {
                metrics::STORAGE_MISSING_CONTRACTS_COUNT
                    .with_label_values(&[context.metrics_label()])
                    .inc();
                None
            }
            Err(_) => None,
        }
    }
