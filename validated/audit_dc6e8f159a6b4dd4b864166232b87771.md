### Title
Unguarded `assert` allows division-by-zero / infinite-energy-limit corruption in `RepositoryImpl.calculateGlobalEnergyLimit` - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` computes an account's TVM energy limit by dividing `energyWeight * totalEnergyLimit` by `totalEnergyWeight`, guarding the zero-denominator case only with a Java `assert` statement, which is compiled out and does nothing unless the JVM is started with `-ea`. This is directly analogous to the reported `ExternalBribe.earned` bug, where a reward numerator is divided by a checkpoint `supply` value that is never checked for zero.

### Finding Description
In `RepositoryImpl.calculateGlobalEnergyLimit`, the network-wide `totalEnergyWeight` is read from `DynamicPropertiesStore` and used as a divisor with no runtime zero-check — only `assert totalEnergyWeight > 0;` protects the division: [1](#0-0) 

In production Java deployments, `assert` statements are disabled by default (the `-ea` JVM flag is not typically set for node operation), so this check is a no-op. If `totalEnergyWeight` ever becomes `0` (e.g., a scenario where all TRX previously frozen for energy is unfrozen network-wide), execution falls straight through to the division:
- When `hardenResourceCalculation()` is enabled, the `BigInteger` division by zero throws `ArithmeticException`, an uncaught runtime exception during TVM energy accounting.
- When `hardenResourceCalculation()` is disabled, the calculation uses `double` division `(double) totalEnergyLimit / totalEnergyWeight`, which evaluates to `Infinity` rather than throwing, and the subsequent multiplication/cast to `long` yields `Long.MAX_VALUE` (or another huge, incorrect value) as the account's energy limit.

Compare this to the sibling functions `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` and `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2`, all of which contain explicit runtime `if (totalEnergyWeight == 0) return 0;` (or `<= 0`) guards before dividing: [2](#0-1) [3](#0-2) 

The `RepositoryImpl` copy of this logic in the actuator/VM module lacks that concrete guard entirely, relying solely on the disabled `assert`. This mirrors the root cause of the reported issue exactly: a divisor derived from dynamic, potentially-zero on-chain state is not defensively checked before being used as a denominator.

### Impact Explanation
This method is used from `VMActuator` (`getAccountEnergyLimitWithFixRatio`/`getAccountEnergyLimitWithFloatRatio`) to compute how much energy a contract-calling account may spend when a `TriggerSmartContract` transaction is executed: [4](#0-3) 
This is reachable by any anonymous user broadcasting a smart-contract-triggering transaction. If `totalEnergyWeight` reaches `0`:
- With hardened resource calculation enabled, every TVM contract call by an account with frozen-for-energy balance throws an uncaught `ArithmeticException` while processing a block/transaction, causing a **DoS of transaction/block processing** on affected nodes (potential consensus impact if the exception propagates during block validation).
- With hardened resource calculation disabled, the account is granted an effectively unlimited energy limit (`Long.MAX_VALUE`), corrupting resource/energy metering and letting a caller execute unbounded TVM computation for free — an **accounting/resource-metering corruption**.

### Likelihood Explanation
Likelihood is low, matching the report's classification, because `totalEnergyWeight` dropping to exactly `0` requires an extreme network condition (all TRX frozen for energy being unfrozen), which is unusual on a live mainnet but is a state that is not structurally prevented by validation logic and could occur on smaller networks, testnets, or via coordinated mass-unfreezing. The lack of a concrete guard (unlike the parallel `EnergyProcessor`/`BandwidthProcessor` code paths) means this is a latent defect regardless of how rarely the zero condition triggers.

### Recommendation
Replace the ineffective `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check mirroring the guards already present in `EnergyProcessor`/`BandwidthProcessor`, e.g. `if (totalEnergyWeight <= 0) { return 0; }` before performing either the `BigInteger` or `double` division.

### Proof of Concept
1. Drive (or simulate in a test) `DynamicPropertiesStore.saveTotalEnergyWeight(0)` — reachable in principle if all accounts network-wide unfreeze their energy-frozen balances.
2. Freeze some TRX for energy on an account (`FreezeBalanceContract`) so `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`.
3. Trigger a smart contract call (`TriggerSmartContractContract`) from that account, causing `VMActuator` to invoke `RepositoryImpl.calculateGlobalEnergyLimit(account)`.
4. With `allowHardenResourceCalculation` on, observe `ArithmeticException: / by zero` thrown from the `BigInteger` divide at `RepositoryImpl.java:981` (uncaught, propagating out of transaction processing). With it off, observe the returned energy limit is `Long.MAX_VALUE`-scale instead of the proportionally correct value, verifiable analogous to the existing parity tests in `CalculateGlobalLimitHardenTest.java` and `RepositoryImplHardenTest.java` that already test the guarded sibling paths but do not cover this unguarded `RepositoryImpl` method.     long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();

          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public void testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio() {

    AccountCapsule account = new AccountCapsule(

        AccountType.Normal, 0L);

    VMConfig.initAllowHardenResourceCalculation(0);

    long resultNew = repository.calculateGlobalEnergyLimit(account);

        .multiply(java.math.BigInteger.valueOf(totalEnergyLimit))
        .divide(java.math.BigInteger.valueOf(totalEnergyWeight))
