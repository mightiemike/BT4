### Title
Workflow/CRESettings job proposals are auto force-approved, silently replacing existing running workflow jobs - (File: core/services/feeds/service.go)

### Summary
`ProposeJob` in the Feeds/Job-Distributor ingestion path silently force-approves and replaces an already-running `job.Workflow` / `job.CRESettings` job whenever a new proposal is ingested for it, bypassing the "already exists" safety check that the same code path enforces for every other job type.

### Finding Description
`ProposeJob` accepts an incoming job spec (from a registered Feeds Manager / Job Distributor connection) and creates a pending proposal. For most job types the proposal stays `Pending` until a privileged UI user calls `ApproveSpec` explicitly, and `ApproveSpec` refuses to replace an existing job for the same contract/external ID unless the caller passes `force=true` (enforced via `authenticateUserCanEdit` on the GraphQL mutation) — see `ErrJobAlreadyExists` returned when `!force`: [1](#0-0) 

However, for `job.Workflow` and `job.CRESettings` types, `ProposeJob` bypasses this entirely by calling `ApproveSpec` with `force` hard-coded to `true` immediately upon ingestion, with no operator confirmation step: [2](#0-1) 

Inside `ApproveSpec`, when `existingJobID` is resolved for a `job.Workflow` type (matched by owner+name via `FindJobIDByWorkflow`, not by external job ID), the `force=true` path deletes the currently running job and creates the new one without any additional check that the replacement is intentional: [3](#0-2) [4](#0-3) 

This is the direct analog of the reported bug class: just as `addAsset` could be called twice to silently overwrite `assetInfoOf[_asset].assetAggregator` without any "already set" check, a second `ProposeJob` call for the same workflow identity silently overwrites the running job configuration without the "already exists" guard that protects every other job type in the identical code path.

### Impact Explanation
Any entity able to push a job proposal through the ingestion channel (Feeds Manager gRPC connection / Job Distributor) for a workflow or CRE-settings job can silently replace a production workflow job's configuration (pipeline, targets, triggers) on the node without any operator review or explicit force confirmation. Because approval is automatic and unconditional for these two job types, this can be used to swap out trusted workflow logic, redirect data/report handling, or cause unexpected cancellation/re-creation of a running job — impacting misreporting/unsafe workflow execution on the affected node.

### Likelihood Explanation
Likelihood depends on who can reach `ProposeJob` for a given node's Feeds Manager connection. Once a Feeds Manager/Job Distributor relationship exists (a routine, expected trust boundary for CRE/workflow job distribution), no further per-proposal authorization step is required for workflow/CRESettings types — unlike all other job types, which require a UI operator's explicit force action. This makes the class of bug directly and easily reachable through the standard, intended job/workflow ingestion path, differing only from other job types by the missing guard.

### Recommendation
Apply the same "already exists" guard used for other job types to `job.Workflow` and `job.CRESettings`: when `ProposeJob` finds an existing job matching the workflow identity, do not auto-force-approve; require the same explicit-force semantics (or an equivalent proposal-review step) so an existing running workflow spec cannot be silently replaced by a subsequent proposal.

### Proof of Concept
1. A workflow job is approved and running on the node (matched by owner+name in `FindJobIDByWorkflow`).
2. The same Feeds Manager/Job Distributor connection sends a new `ProposeJob` request with the same workflow owner+name but different pipeline/spec content.
3. `ProposeJob` detects `jobType == job.Workflow` and calls `s.ApproveSpec(ctx, specID, true)` unconditionally.
4. `ApproveSpec` finds `existingJobID` via `FindJobIDByWorkflow`, and because `force=true`, deletes the existing job and creates the new one immediately — with no `ErrJobAlreadyExists` check and no manual confirmation, unlike the identical scenario for OCR/OCR2/other job types in the same function.
