### Title
Unbounded per-account asset count enables O(n) CPU cost on every public getAccount request via `AccountCapsule.importAllAsset()` - (chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java)

### Summary
`Wallet.getAccount()` and `Wallet.getAccountById()` unconditionally call `accountCapsule.importAllAsset()` on every request to `/wallet/getaccount`, `/walletsolidity/getaccount`, and their PBFT/Solidity variants, before returning the account. When asset optimization is active, this triggers a full DB prefix scan of every asset the account holds (`AccountAssetStore.getAllAssets`), whose cost is O(n) in the number of distinct TRC10 assets held by the target address, while the attacker can grow `n` cheaply and the read requests are only throttled by a flat QPS rate limiter, not by asset count.

### Finding Description
`Wallet.getAccount(Account account)` fetches a fresh `AccountCapsule` from `AccountStore.get()` and calls `accountCapsule.importAllAsset()` before returning the reply: [1](#0-0) 

`AccountCapsule.importAllAsset()` guards with a per-instance `flag` field, but that flag is only meaningful within a single object's lifetime — every HTTP/gRPC request deserializes a brand-new `AccountCapsule` from the account store (`account.parseFrom(data)`), so `flag` is always `false` at the start of every request: [2](#0-1) 

`importAllAsset()` delegates to `AssetUtil.importAllAsset`, which (when asset optimization is enabled) calls `accountAssetStore.getAllAssets(account)`: [3](#0-2) 

`AccountAssetStore.getAllAssets` performs a `prefixQuery` over the account-asset key-value store keyed by `address || assetId`, iterating one DB entry per distinct asset the account holds when `account.getAssetOptimized()` is true: [4](#0-3) 

The public entrypoint `GetAccountServlet` (mapped to `/wallet/getaccount`, and reused by `/walletsolidity/getaccount`, `GetAccountOnPBFTServlet`, `GetAccountOnSolidityServlet`) is unauthenticated and simply forwards the parsed address to `wallet.getAccount(...)`: [5](#0-4) 

The only throttling in front of this handler is `RateLimiterServlet.service()`, which enforces a flat QPS/IP-based permit check independent of the account being queried or the number of assets it holds: [6](#0-5) 

An attacker can issue many cheap `AssetIssueContract`s and then send `TransferAssetContract` transactions moving 1 unit of each asset to a target address. Each such transfer causes the account's asset holdings to eventually be migrated into per-asset keys in `AccountAssetStore` (gated by the `AllowAssetOptimization` hard-fork flag), so subsequent `getAllAssets` prefix scans grow linearly with the number of distinct assets. From that point, every unauthenticated `getAccount` call against that address costs O(n) DB-scan work server-side, while the attacker's own per-request query cost stays O(1) (flat request rate limit, no cost scaling with `n`). Because the flag caching in `AccountCapsule` never persists across requests (a new capsule object is constructed on every call), the O(n) work repeats on every single public read, not just once.

### Impact Explanation
Repeated public reads against a poisoned address force the node to perform unbounded, materially underpriced iteration work (`AccountAssetStore.getAllAssets` prefix scan) on every call, scaling linearly with attacker-created asset count `n`. This allows a low-cost, repeatable CPU-exhaustion/DoS vector against full nodes and solidity nodes serving the public `getAccount` API family, degrading node responsiveness for all API consumers.

### Likelihood Explanation
Preconditions are attacker-controllable and inexpensive: issuing TRC10 assets and transferring 1 unit of each to a target address only costs the flat `AssetIssueContract` fee and bandwidth/fee for `TransferAssetContract`s, both O(1) per issued asset from the attacker's perspective, requiring no privileged role. The exploit is fully repeatable — asset counts persist on-chain permanently, so the degraded cost applies to every future public read of that address indefinitely, and the attack requires the asset-optimization hard fork (`AllowAssetOptimization`) to be active, which is the standard current network state.

### Recommendation
Cap or paginate the per-account asset import: either enforce/verify a maximum number of distinct assets an account may hold (bound `n`), or avoid doing a full O(n) DB scan on every read request — e.g., cache the imported asset map keyed by account state/version so repeated reads within a block or time window don't re-scan, or move the cost onto the account holder (e.g., charging bandwidth/energy proportional to asset count when `getAccount`-style reads are served, or restricting free/public API asset-map expansion by returning paginated results instead of full asset map on demand).

  public Map<String, Long> getAllAssets(Protocol.Account account) {
    Map<String, Long> assets = new HashMap<>();
    if (account.getAssetOptimized()) {
      Map<WrappedByteArray, byte[]> map = prefixQuery(account.getAddress().toByteArray());
      map.forEach((k, v) -> {
        byte[] assetID = ByteArray.subArray(k.getBytes(),
                account.getAddress().toByteArray().length, k.getBytes().length);
        assets.put(ByteArray.toStr(assetID), Longs.fromByteArray(v));
      });
    }
    account.getAssetV2Map().forEach((k, v) -> assets.put(k, v));
    return assets;
  }
