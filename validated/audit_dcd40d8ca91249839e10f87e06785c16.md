### Title
`resolve_promise_yield_timeouts` processes an unbounded user-inflatable queue without incrementing the compute counter, making the compute-limit guard a no-op — (`File: runtime/runtime/src/lib.rs`)

---

### Summary

`resolve_promise_yield_timeouts` is the last phase of `Runtime::apply`. It walks the `PromiseYieldTimeout` trie queue and, for every entry whose `expires_at ≤ block_height`, performs multiple trie reads/writes and forwards a synthetic `PromiseResume` receipt. The function carries a compute-limit guard at the top of its loop, but **never increments `total.compute` for any work it performs**. Because `total.compute` is only advanced by `process_receipt_with_metrics` calls in the earlier phases (local → delayed → incoming), the guard is a dead check whenever those phases consumed little or no gas. The only real bound that remains is the storage-proof-size check (`check_proof_size_limit_exceed()`). An unprivileged user can pre-populate the timeout queue with many entries all expiring at the same block height, forcing that chunk to drain the queue up to the proof-size ceiling without any gas accounting, bypassing the compute limit that governs every other phase of chunk execution.

`total.compute` is a field of `TotalResourceGuard` that is incremented exclusively inside `process_receipt_with_metrics` (called from `process_local_receipts`, `process_delayed_receipts`, `process_incoming_receipts`). `resolve_promise_yield_timeouts` borrows `total` but never calls `total.add(gas, compute)` or any equivalent. If the three earlier phases consumed zero or negligible gas (e.g., the chunk carries no transactions or receipts), `total.compute` remains 0 when the timeout loop starts, and `0 >= compute_limit` is always false. The loop then runs until the storage-proof-size ceiling is hit — a ceiling that is measured in bytes of trie witness data, not in gas units, and that is substantially more permissive than the gas limit for the kind of work done here (sequential trie key reads and small receipt writes).

**Per-iteration work (all unaccounted)**

Each loop iteration performs:
1. `get::<PromiseYieldTimeout>(state_update, &queue_entry_key)` — trie read
2. `state_update.contains_key(&promise_yield_key, …)` — trie read
3. `get_pure(state_update, &promise_yield_key)` — trie read (when `save_receipt_to_tx`)
4. `receipt_sink.forward_or_buffer_receipt(resume_receipt, …)` — congestion-info update + possible trie write
5. `state_update.remove(queue_entry_key)` — trie delete

None of these operations touch `total.compute`. [1](#0-0) [2](#0-1) 

**How the queue is populated by an unprivileged user**

Any account can call the `promise_yield_create` host function from a contract. Each call enqueues one `PromiseYieldTimeout { account_id, data_id, expires_at }` entry into the persistent trie queue via `enqueue_promise_yield_timeout`. [3](#0-2) [4](#0-3) 

The `expires_at` value is `block_height + yield_timeout_length_in_blocks` (a protocol-defined constant). An attacker who controls many accounts can issue `promise_yield_create` calls across many chunks, all targeting the same future block height, accumulating an arbitrarily large batch of entries that all become eligible for processing simultaneously.

**The compute-limit invariant is broken for this phase**

Every other receipt-processing phase in `process_receipts` checks `total.compute >= compute_limit` *and* increments `total.compute` for each receipt processed, so the guard is live. `resolve_promise_yield_timeouts` checks the same guard but never advances the counter, making the guard permanently false for any chunk where the earlier phases left gas on the table. [5](#0-4) [6](#0-5) 

---

### Impact Explanation

A chunk whose earlier phases consumed little gas (e.g., a chunk with no transactions and no incoming receipts — a normal occurrence on lightly-loaded shards) will drain the entire expired portion of the `PromiseYieldTimeout` queue in a single apply call, bounded only by the storage-proof-size limit. The storage-proof-size limit is measured in bytes of trie witness data; given that each timeout entry is small (~100 bytes), many thousands of entries can be processed before the proof-size ceiling is reached. This causes:

1. **Chunk apply time proportional to queue depth** — validators processing the chunk spend wall-clock time on trie I/O that is not accounted for by the gas/compute budget, potentially causing them to miss the block-production deadline for the next height.
2. **Repeated slowdown across consecutive chunks** — entries not drained in one chunk (because the proof-size limit was hit) remain in the queue and are retried in the next chunk, so the attacker's pre-loaded queue degrades multiple consecutive chunks.
3. **Congestion-info corruption risk** — `forward_or_buffer_receipt` updates the shard's `CongestionInfo` for each synthetic `PromiseResume` receipt created; a large burst of timeout-generated receipts can push the shard into a congested state, throttling legitimate cross-shard traffic.

The impact falls under the "denial of service — non-network-level, fixable without a hardfork" category of the allowed impact gate.

---

### Likelihood Explanation

- **Unprivileged trigger**: any account that can deploy and call a contract can invoke `promise_yield_create`. No validator or admin role is required.
- **Cost to attacker**: proportional to the number of yields created (gas per `promise_yield_create` call). The attacker can spread the cost across many blocks/chunks before the target block.
- **Amplification**: the attacker pays gas once per yield entry; the victim chunk pays trie-I/O cost per entry *without* that cost being reflected in the gas limit, so the attacker's gas expenditure does not fully cover the validator's processing cost.
- **Timing control**: `expires_at` is deterministic (`block_height + constant`), so the attacker can precisely target a specific block height.

---

### Recommendation

Add compute/gas accounting inside `resolve_promise_yield_timeouts` for each timeout processed, so that `total.compute` is incremented and the existing guard becomes live:

```rust
// Inside the loop, after processing each entry:
let timeout_processing_cost = /* a fixed fee per timeout, e.g. config.fees.fee(ActionCosts::...) */;
total.add(timeout_processing_cost, timeout_processing_cost)
    .map_err(|_| RuntimeError::UnexpectedIntegerOverflow("yield_timeout".into()))?;
if total.compute >= compute_limit {
    break;
}
```

Alternatively, introduce a hard per-chunk cap on the number of timeout entries processed (e.g., `MAX_YIELD_TIMEOUTS_PER_CHUNK`), independent of the compute counter, so that even a chunk with zero prior gas usage cannot drain an arbitrarily large queue.

### Proof of Concept

1. Deploy a contract on account `attacker.near` that calls `promise_yield_create` with `expires_at = TARGET_BLOCK`.
2. From N distinct accounts, each call the contract once per chunk over several chunks, accumulating N timeout entries all expiring at `TARGET_BLOCK`. N can be in the thousands given typical gas limits.
3. At `TARGET_BLOCK`, submit a chunk with no transactions and no incoming receipts to the target shard.
4. `process_receipts` calls `resolve_promise_yield_timeouts` with `total.compute = 0`. The guard `0 >= compute_limit` is false. The loop processes all N expired entries (up to the proof-size ceiling) without any gas accounting.
5. Observe that chunk apply time for `TARGET_BLOCK` is significantly elevated compared to a normal chunk, and that the shard's `CongestionInfo` reflects a large burst of buffered `PromiseResume` receipts. [7](#0-6) [8](#0-7) [3](#0-2)

```rust
fn resolve_promise_yield_timeouts(
    processing_state: &mut ApplyProcessingReceiptState,
    receipt_sink: &mut ReceiptSink,
    compute_limit: u64,
) -> Result<ResolvePromiseYieldTimeoutsResult, RuntimeError> {
    let mut state_update = &mut processing_state.state_update;
    let total = &mut processing_state.total;
    let apply_state = &processing_state.apply_state;

    let mut promise_yield_indices: PromiseYieldIndices =
        get(state_update, &TrieKey::PromiseYieldIndices)?.unwrap_or_default();
    let initial_promise_yield_indices = promise_yield_indices.clone();
    let mut new_receipt_index: usize = 0;

    let mut processed_yield_timeouts = vec![];
    let yield_processing_start = std::time::Instant::now();
    while promise_yield_indices.first_index < promise_yield_indices.next_available_index {
        if total.compute >= compute_limit || state_update.trie.check_proof_size_limit_exceed() {
            break;
        }

        let queue_entry_key =
            TrieKey::PromiseYieldTimeout { index: promise_yield_indices.first_index };

        let queue_entry =
            get::<PromiseYieldTimeout>(state_update, &queue_entry_key)?.ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "PromiseYield timeout queue entry #{} should be in the state",
                    promise_yield_indices.first_index
                ))
            })?;

        // Queue entries are ordered by expires_at
        if queue_entry.expires_at > apply_state.block_height {
            break;
        }

        // Check if the yielded promise still needs to be resolved
        let promise_yield_key = TrieKey::PromiseYieldReceipt {
            receiver_id: queue_entry.account_id.clone(),
            data_id: queue_entry.data_id,
        };
        if state_update.contains_key(&promise_yield_key, AccessOptions::DEFAULT)? {
            let new_receipt_id = create_receipt_id_from_receipt_id(
                &queue_entry.data_id,
                apply_state.block_height,
                new_receipt_index,
            );
            new_receipt_index += 1;

            // Create a PromiseResume receipt to resolve the timed-out yield.
            let resume_receipt = Receipt::V0(ReceiptV0 {
                predecessor_id: queue_entry.account_id.clone(),
                receiver_id: queue_entry.account_id.clone(),
                receipt_id: new_receipt_id,
                receipt: ReceiptEnum::PromiseResume(DataReceipt {
                    data_id: queue_entry.data_id,
                    data: None,
                }),
            });

            // Record a ReceiptToTx entry for the new resume receipt. The parent is the
            // yield receipt that is being timed out.
            if processing_state.apply_state.save_receipt_to_tx {
                let yield_receipt: Receipt = get_pure(state_update, &promise_yield_key)?
                    .expect("promise yield receipt should exist since contains_key was true");
                processing_state.receipt_to_tx.push((
                    new_receipt_id,
                    ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                        origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                            parent_receipt_id: *yield_receipt.receipt_id(),
                            parent_predecessor_id: yield_receipt.predecessor_id().clone(),
                        }),
                        receiver_account_id: queue_entry.account_id.clone(),
                        shard_id: processing_state.apply_state.shard_id,
                    }),
                ));
            }

            // The receipt is destined for the local shard and will be placed in the outgoing
            // receipts buffer. It is possible that there is already an outgoing receipt resolving
            // this yield if `yield_resume` was invoked by some receipt which was processed in
            // the current chunk. The ordering will be maintained because the receipts are
            // destined for the same shard; the timeout will be processed second and discarded.
            receipt_sink.forward_or_buffer_receipt(
                resume_receipt,
                apply_state,
                &mut state_update,
            )?;
        }

        processed_yield_timeouts.push(queue_entry);
        state_update.remove(queue_entry_key);
        // Math checked above: first_index is less than next_available_index
        promise_yield_indices.first_index += 1;
    }
    processing_state.metrics.yield_timeouts_done(
        processed_yield_timeouts.len() as u64,
        yield_processing_start.elapsed(),
        total.gas,
        total.compute,
    );
    Ok(ResolvePromiseYieldTimeoutsResult {
        initial_promise_yield_indices,
        promise_yield_indices,
        processed_yield_timeouts,
    })
}
```

```rust
// Enqueues given timeout to the PromiseYield timeout queue
pub fn enqueue_promise_yield_timeout(
    state_update: &mut TrieUpdate,
    promise_yield_indices: &mut PromiseYieldIndices,
    account_id: AccountId,
    data_id: CryptoHash,
    expires_at: BlockHeight,
) {
    set(
        state_update,
        TrieKey::PromiseYieldTimeout { index: promise_yield_indices.next_available_index },
        &PromiseYieldTimeout { account_id, data_id, expires_at },
    );
    promise_yield_indices.next_available_index = promise_yield_indices
        .next_available_index
        .checked_add(1)
        .expect("Next available index for PromiseYield timeout queue exceeded the integer limit");
}
```
