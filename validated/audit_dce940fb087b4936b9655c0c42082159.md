Confirms `replay_on_archive.rs` never references `state_checkpoint_hash`/`hot_state_checkpoint_hash` — the only correctness check it performs is via `ensure_match_transaction_info`, which itself skips those fields.

### Title
Replay-verify tooling accepts divergent state roots because `ensure_match_transaction_info` never validates state-checkpoint hashes - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness oracle used by Aptos's authenticated replay/audit tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, and `aptos-move/cli`'s local-simulation replay command) to confirm that a transaction re-executed by the local VM produced the same result as what is recorded in the network-certified, accumulator-proven `TransactionInfo`. The function checks status, gas used, write-set hash, and event-root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) . This is a direct structural analog of the "missing storage gap" bug class from the external report: a field that must be preserved/verified across a boundary (there, storage layout across upgrades; here, state-root binding across replay) is silently omitted, so corruption is masked rather than caught.

### Finding Description
`ensure_match_transaction_info` is documented by its own TODO to have this exact gap: [2](#0-1) 

This function is invoked as the terminal correctness gate in the replay-verify pipeline used to validate mainnet/testnet archive data end-to-end: [3](#0-2) 

That pipeline reads `expected_txn_infos` (the network-certified `TransactionInfo`, sourced from backup/archive and implicitly trusted as authenticated), re-executes each transaction with the local VM, and calls `ensure_match_transaction_info` per-transaction to confirm the local output matches the archived, proof-bound record. Because `state_checkpoint_hash` (the JMT/global state root recorded at every checkpoint boundary since genesis) is never compared, a VM or storage bug that produces a wrong Merkle/state root — while incidentally leaving write-set bytes, event hashes, gas, and status unchanged, or occurring on a transaction where the write set differs but the checkpoint hash coincidentally isn't cross-checked — would not be caught by `replay-verify`/`replay-on-archive`. The same helper is also used interactively by the CLI's transaction-replay command and by `aptos-debugger`'s mismatch printer, so operators/auditors relying on either tool to sanity-check historical state transitions get a false "match" despite a genuine state-root divergence [4](#0-3) [5](#0-4) .

Separately (and part of why the gap is more than theoretical), the in-progress "trading-native"/position-state-root work already anticipates this: the `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` fields exist in `TransactionInfo` and are actively computed and compared during live chunk-executor commit (`execution/executor/src/chunk_executor/mod.rs` lines 374-394, `DoStateCheckpoint`), but that live-commit check is a *different* code path (`DoStateCheckpoint`/`get_state_checkpoint_hashes`) than the one used for offline replay-verify, so the gap is specific to the audit/replay tooling and does not protect it.

### Impact Explanation
This breaks the "authenticated API or state-view output bound to the wrong version/root" and "replay/restore path must not reinterpret committed data into a different ledger state" invariants: the whole purpose of replay-verify against archived, proof-authenticated `TransactionInfo`s is to detect exactly this class of divergence (a node/VM computing a different state root than what was actually committed and signed by validators). With this check missing, a state-root-corrupting bug (in execution, in the Merkle accumulator, in JMT update logic, or in a future hard fork) can pass `replay-verify`/`replay-on-archive` clean, giving false confidence that historical execution is byte-for-byte correct when the state tree has silently diverged. This is a high-impact gap in the last line of defense used to certify mainnet archive integrity, though it is a detection/verification gap rather than a live consensus-breaking bug by itself — it does not itself corrupt state, but it can hide the fact that state has been corrupted.

### Likelihood Explanation
The missing check is unconditional and always active whenever `ensure_match_transaction_info` is called (not gated behind a feature flag) — the TODO comment only discusses gating the *fix*, not the presence of the bug. Any consumer of this function (replay-verify, replay-on-archive, CLI debugger) is affected today. Likelihood of the underlying state-root bug it fails to catch is separate/lower, but the detection gap itself is 100% reproducible and trivial to demonstrate.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived checkpoint hash(es) against `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` when applicable) whenever the transaction is a checkpoint boundary, mirroring the validation already done in `DoStateCheckpoint`/`get_state_checkpoint_hashes` for the live commit path, so that replay-verify tooling cannot report success while the state root diverges.

### Proof of Concept
1. Take any transaction that is a state-checkpoint boundary (block end) in an archived backup.
2. Suppose local execution/storage produces a JMT root that differs from the one baked into the archived `TransactionInfo.state_checkpoint_hash` (e.g., due to a latent Merkle-tree bug), while status/gas/write-set-hash/event-root remain byte-identical (plausible since state root is a separate accumulation over the resulting state, not solely a function of this transaction's own write set).
3. Run `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` (as invoked by `aptos-debugger aptos-db replay-on-archive`), or the CLI replay command in `aptos-move/cli/src/commands.rs`.
4. `ensure_match_transaction_info` at [1](#0-0)  returns `Ok(())` because it never inspects `state_checkpoint_hash`, so the tool reports the replay as successful despite the state-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
