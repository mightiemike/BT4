### Title
Governance feature-gate (`supportUnfreezeDelay`) inconsistently enforced between `WithdrawExpireUnfreezeActuator` and `WithdrawExpireUnfreezeProcessor` (native contract callable from TVM) - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`)

### Summary
The external report's bug class is a control (here, the Solidity `whenNotPaused` modifier) that is applied to one set of state-mutating functions but omitted from functionally-equivalent sibling functions, allowing the guarded action to still be executed through the unguarded path. The direct analog in java-tron is the `supportUnfreezeDelay()` governance/hard-fork gate: it is checked in the ordinary transaction path (`WithdrawExpireUnfreezeActuator`) but is absent from the equivalent logic reachable from smart-contract execution (`WithdrawExpireUnfreezeProcessor`).

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly rejects the transaction unless the committee-controlled dynamic property is enabled: [1](#0-0) 

The equivalent business logic, `WithdrawExpireUnfreezeProcessor`, which is invoked from the TVM (`org.tron.core.vm.program.Program`, referenced 9 times) so that a smart contract can trigger the same state transition, performs account/balance validation but never checks `dynamicStore.supportUnfreezeDelay()`: [2](#0-1) 

Both code paths ultimately perform the same mutation — moving amounts from `unfrozenV2List` into `balance` — via `execute()`: [3](#0-2) 

This is structurally identical to the reported issue: one execution surface (`LiquidityPool`/`WithdrawExpireUnfreezeActuator`) enforces the gate while a parallel surface with the same effect (`KangarooVault`/`WithdrawExpireUnfreezeProcessor`) does not.

### Impact Explanation
`supportUnfreezeDelay` is a committee/hard-fork-controlled switch meant to gate whether the unfreeze-delay withdrawal feature is active on the network. If a contract can call into the native `WithdrawExpireUnfreezeProcessor` path before or independent of the gate's activation state, it can execute withdrawals that the direct-transaction path would reject. Depending on how/when the feature is toggled (e.g., temporarily disabled after being found buggy, similar to an emergency pause), nodes could diverge in accepted state depending on which path is exercised, or funds could move via a path the protocol intended to keep closed — a consensus-relevant discrepancy and a bypass of an operator-controlled safety switch.

### Likelihood Explanation
Reachability depends on whether the TVM/precompiled-contract layer independently checks `supportUnfreezeDelay` before invoking `WithdrawExpireUnfreezeProcessor.execute()`. There is a `supportUnfreezeDelay` reference inside `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`, so the precompiled-contract entry point may already gate contract availability at that layer — I could not fully confirm within available tool calls whether that check covers every call path into `WithdrawExpireUnfreezeProcessor.validate()`/`execute()`, or only contract registration/whitelisting. This uncertainty should be resolved by tracing all callers of `WithdrawExpireUnfreezeProcessor` and confirming the gate is enforced at every entry, not only the actuator's.

### Recommendation
Add an explicit `dynamicStore.supportUnfreezeDelay()` check inside `WithdrawExpireUnfreezeProcessor.validate()` (mirroring the actuator's check) so the guard is enforced regardless of entry point, rather than relying solely on an upstream precompiled-contract gate that may not cover all invocation paths.

### Proof of Concept
1. Committee has not yet enabled `supportUnfreezeDelay` (or disables it again via proposal).
2. A direct `WithdrawExpireUnfreezeContract` transaction is rejected by `WithdrawExpireUnfreezeActuator.validate()` with "Not support WithdrawExpireUnfreeze transaction..." [1](#0-0) 
3. A smart contract instead triggers the equivalent native operation through the TVM path that reaches `WithdrawExpireUnfreezeProcessor.validate()`/`execute()`, which contains no equivalent check [2](#0-1) , potentially succeeding where the direct transaction failed.

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
