### Title
Unchecked integer overflow in TRC10 asset accounting during full-balance transfer (SUICIDE) - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Finding Description
`MUtil.transferAllToken` is invoked from `Program.java`'s `suicide` handling to move all remaining TRC10 asset balances from a self-destructing contract (`fromAddress`) to a beneficiary (`toAddress`). Unlike the single-token path `MUtil.transferToken`, which calls `VMUtils.validateForSmartContract(deposit, fromAddress, toAddress, tokenId.getBytes(), amount)` — a method that explicitly guards against overflow via `addExact(assetBalance, amount, VMConfig.disableJavaLangMath())` [1](#0-0)  — the `transferAllToken` path performs the addition directly with plain `+` and no bounds checking at all: [2](#0-1) 

Since `toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount` is a raw `long` addition, if `toAddress`'s existing balance for `tokenId` plus `amount` (the full balance from `fromAddress`) exceeds `Long.MAX_VALUE`, the result silently wraps around to a negative (or otherwise incorrect) value with no exception thrown and no validation performed anywhere in this call path.

An attacker can:
1. Legitimately accumulate a TRC10 asset balance on an account they control (`toAddress`) at or near `Long.MAX_VALUE` for a given `tokenId`, through ordinary transfers.
2. Deploy/control a contract (`fromAddress`) holding a nonzero balance of the same `tokenId`.
3. Trigger the contract's self-destruct (SUICIDE opcode) with beneficiary set to `toAddress`.
4. `transferAllToken` adds the contract's remaining asset balance into `toAddress`'s balance without an overflow check, causing the stored balance to wrap.

### Impact Explanation
This corrupts TRC10 asset accounting (`VALUE_CONSERVATION` invariant violation): the attacker's own balance can wrap to a small or negative value, and more importantly, on the next legitimate operation touching that balance, downstream logic that assumes non-negative/monotonic balances could be exploited to fabricate value out of thin air, matching the "asset/accounting corruption" impact class in the bounty scope.

### Likelihood Explanation
The precondition — controlling an account with a TRC10 balance near `Long.MAX_VALUE` — is not trivial to reach organically (it requires accumulating an enormous amount of a token, which for most real assets with limited total supply is infeasible, since TRC10 total supply is itself capped and tracked; an attacker would need to control essentially the entire supply of a token they issue themselves, or find a token with total supply near `Long.MAX_VALUE`). If the attacker issues their own TRC10 token with total supply near `Long.MAX_VALUE` and holds it themselves, this becomes fully feasible and repeatable at the cost of a single asset issuance and a SUICIDE-capable contract deployment (bounded by transaction fees and energy for contract deployment).

### Recommendation
Add an overflow-safe addition (e.g. `Maths.addExact` used elsewhere) in `MUtil.transferAllToken` before writing `toBuilder.putAssetV2(tokenId, ...)`, mirroring the check already present in `VMUtils.validateForSmartContract`, and throw/handle appropriately (e.g., abort the SUICIDE transfer or cap the transferred amount) instead of silently wrapping.

### Proof of Concept
```java
// In a test extending existing MUtil/actuator test setup:
@Test
public void testTransferAllTokenOverflow() {
  byte[] fromAddress = ...; // contract account
  byte[] toAddress = ...;   // attacker account
  String tokenId = "1000001";

  // toAddress pre-loaded to near Long.MAX_VALUE for tokenId
  toAccountCapsule.addAssetAmountV2(tokenId.getBytes(), Long.MAX_VALUE - 1, dynamicStore, assetStore);
  // fromAddress (contract) holds 5 units of same tokenId
  fromAccountCapsule.addAssetAmountV2(tokenId.getBytes(), 5, dynamicStore, assetStore);

  deposit.putAccountValue(fromAddress, fromAccountCapsule);
  deposit.putAccountValue(toAddress, toAccountCapsule);

  MUtil.transferAllToken(deposit, fromAddress, toAddress);

  long resultBalance = deposit.getAccount(toAddress)
      .getAssetMapV2().get(tokenId);

  // Expected: exception thrown OR balance capped;
  // Actual (bug): resultBalance wraps to a small/negative number instead of throwing
  Assert.assertTrue("balance should not overflow/wrap", resultBalance >= Long.MAX_VALUE - 1);
}
```

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
