### Title
TOCTOU race in JWT replay-cache check-then-record allows one legitimate signed JWT to authorize two concurrent requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and only later calls `h.jwtCache.recordUsage(claims.ID)` after the authorized-key lookup succeeds, with no atomic check-and-set between the two operations. Two concurrent `Authorize()` calls carrying the same valid signed JWT (same `jti`, same digest/params, since the digest is cryptographically bound to the JWT signature) can both pass `isReplay` before either commits via `recordUsage`, allowing the single JWT to authorize two requests instead of exactly one.

### Finding Description
`Authorize` performs verification and replay-protection in three separate steps:
1. `utils.VerifyRequestJWT(token, *req)` verifies the ECDSA signature and validates that `claims.Digest` equals the digest of `*req` [1](#0-0) , meaning the signature binds `jti` to a specific request payload — an attacker without the signer's private key cannot forge a new signature for different `Params` while keeping the same `jti` valid.
2. `h.jwtCache.isReplay(claims.ID)` takes an `RLock`, reads `cache[jti]`, and releases the lock [2](#0-1) .
3. Only after the authorized-key lookup succeeds does `h.jwtCache.recordUsage(claims.ID)` take a `Lock` and write `cache[jti] = time.Now()` [3](#0-2) .

Between steps 2 and 3 there is no held lock, so an attacker who replays the exact same signed JWT (same `jti`, and necessarily the same request body/`Params`, since the digest is signed together with `jti`) via two concurrent gateway JSON-RPC requests can have both goroutines observe `isReplay == false` and both proceed to `recordUsage`, both returning a valid `*gateway.AuthorizedKey`. This violates the intended invariant "each `jti` authorizes exactly one request", enforced only by the non-atomic check-then-act sequence at [4](#0-3) .

Note: because `VerifyRequestJWT` ties `claims.Digest` to the exact request content, the attacker cannot vary `Params` while reusing the token's `jti` — a differently-shaped request with the same `jti` would fail digest validation before reaching the replay check. The exploitable race is therefore concurrent replay of the identical captured request (same `jti` and same `Params`), not an attacker-modified payload; the impact (double execution) is unchanged.

### Impact Explanation
A network observer or any party who can capture one legitimate signed JWT+request pair (e.g., via request logging, proxy, retry-capable client, or simple duplication of a captured HTTP call) can fire it twice concurrently at the gateway and get the underlying HTTP-trigger-authorized workflow action executed twice instead of once, since `WorkflowMetadataHandler.Authorize` will return a valid `*gateway.AuthorizedKey` for both. This is a double-execution/duplicate-authorization bug for HTTP-trigger workflow actions gated by JWT replay protection.

### Likelihood Explanation
Exploitability requires only capturing one previously-issued, still-valid (unexpired) signed JWT/request pair and sending it twice in quick succession/concurrently — no additional privilege, key material, or protocol violation is needed. The race window is small (time between the `RLock` release in `isReplay` and the `Lock` acquisition in `recordUsage`, which spans an authorized-key map lookup) but is reliably triggerable with concurrent goroutines/requests in a controlled test or with sufficiently fast duplicate network requests.

### Recommendation
Make replay-check-and-record atomic: acquire a single `Lock` covering both operations, e.g. add a `checkAndSet(jti string) bool` method on `jwtReplayCache` that under one lock checks existence and inserts if absent, returning whether it was already present, and call it once in `Authorize` (ideally right after JWT verification, before the authorized-key lookup) instead of separate `isReplay`/`recordUsage` calls.

### Proof of Concept
Integration/unit test in `core/services/gateway/handlers/capabilities/v2`:
1. Construct one valid signed JWT for a given `jsonrpc.Request` and register the corresponding workflow ID/authorized key.
2. Launch two goroutines that both call `h.Authorize(workflowID, token, req)` concurrently with the same `token`/`req`.
3. Assert exactly one call returns `(*gateway.AuthorizedKey, nil)` and the other returns an error (`"JWT token has already been used..."`).
4. As currently implemented, due to the TOCTOU window between `isReplay` and `recordUsage`, the test should observe both goroutines succeeding under race conditions (run with `go test -race -count=100` to reliably surface the race), demonstrating violation of the exactly-once invariant.

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}
```

```go
func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
