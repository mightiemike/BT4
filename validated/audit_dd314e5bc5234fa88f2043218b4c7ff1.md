Based on my research, I found the key analog: `CallerDeposit::new()` in `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs:180-191`, which tracks an external caller's full `attached_deposit` for potential refund, but the refund logic in `rlp_execute_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:296-317`) only refunds the caller when the promise **fails** — and only refunds `yocto_near` (the full originally attached deposit), never the *excess* between what the caller attached and what the inner action actually needed.

### Title
Wallet Contract permanently retains excess attached deposit on successful execution instead of refunding the unused portion - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` is an Ethereum-transaction-emulation wrapper contract on NEAR. When an external (non-owner) caller invokes `rlp_execute` with `#[payable]` and attaches a NEAR deposit intended to fund the `yocto_near`/`value` field of the wrapped Ethereum-style action, the contract records the *entire* attached deposit via `CallerDeposit::new` [1](#0-0) , but only refunds it back to the caller if the resulting cross-contract promise **fails**; if it succeeds, the full deposit is kept even if the actual action consumed less than what was attached.

### Finding Description
`inner_rlp_execute` computes `caller_deposit = CallerDeposit::new(&context)` from `env::attached_deposit()` [2](#0-1) . This captures the entire deposit sent by an external predecessor (not the wallet owner) as a single lump sum to be refunded — there is no computation, anywhere in the flow, comparing the attached deposit against the actual `yocto_near`/`deposit` value required by the decoded action (`FunctionCall`, `Transfer`, etc.) obtained via `parse_rlp_tx_to_action` [3](#0-2) .

In `rlp_execute_callback`, the refund is conditioned strictly on failure:
```rust
match env::promise_result(0) {
    PromiseResult::Failed => {
        if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
            // refund the entire recorded deposit
        }
    }
    PromiseResult::Successful(value) => { /* no refund logic at all */ }
}
``` [4](#0-3) 

This exactly mirrors the Footium `mintPlayers`/`_validateMintingParams` bug class: the check only validates a lower bound (`if msg.value < totalFee`) and the excess is silently absorbed rather than returned. Here, the wallet contract only validates that the transaction succeeds or fails as a whole — it never checks or refunds any positive difference between `attached_deposit` and the amount actually forwarded in the promise's action (`action.deposit` / `action.gas` cost). The contract's own test `test_caller_refunds` explicitly documents this behavior: "External caller does not get a refund when their tokens are spent" even though the assertion only checks `>=` the deposit amount was consumed, not that it was fully consumed [5](#0-4) .

### Impact Explanation
Any unprivileged external caller (not the wallet owner, reachable via a `predecessor_id != current_account_id` call to `rlp_execute`, which is `#[payable]` and callable by any RPC/transaction sender) who attaches more NEAR than the wrapped action's `deposit`/`yocto_near` actually requires will permanently lose the excess — it is neither transferred to the receiver (only the decoded `action.deposit` is forwarded via `action_to_promise`, see `Action::Transfer(action) => Promise::new(target).transfer(action.deposit)` [6](#0-5) ) nor refunded to the caller on success. The excess remains locked in the wallet contract's own account balance, unreachable and unrecoverable by the external caller who transacted, matching "concrete unauthorized value movement" / "permanently frozen funds" criteria.

### Likelihood Explanation
Likelihood is moderate: it requires an external, non-owner caller to submit an RLP-encoded Ethereum-style transaction to `rlp_execute` while over-attaching NEAR relative to the action's real cost (e.g., a relayer or dApp integration miscalculating the deposit, or a caller intentionally over-funding to guarantee success and expecting excess back, as is standard practice in many EVM-style patterns). No privileged access or protocol-level control is needed — a single `FunctionCall` transaction from any RPC caller triggers the vulnerable path.

### Recommendation
Track and refund the *difference* between `attached_deposit` and the actual `deposit`/`yocto_near` consumed by the decoded action, not just an all-or-nothing refund tied to promise success/failure. Specifically, in `inner_rlp_execute`, compute `excess = attached_deposit.saturating_sub(action_required_deposit)` and issue a transfer of `excess` back to `predecessor_account_id` regardless of whether the downstream promise succeeds, mirroring how `refund_unspent_gas_and_deposits` in the core runtime always refunds excess prepaid amounts [7](#0-6) .

### Proof of Concept
1. Deploy `near-wallet-contract` (`WalletContract`) for some eth-implicit account.
2. As an external (non-owner) account, call `rlp_execute(target, tx_bytes_b64)` with `#[payable]` attaching, e.g., 5 NEAR (`deposit_amount`), while the RLP-encoded Ethereum transaction encodes a `Transfer` action whose `yocto_near`/derived `value` requires far less than 5 NEAR (per `MAX_YOCTO_NEAR` scaling logic in `internal.rs` lines 22-31, 250-266).
3. `CallerDeposit::new` records the entire 5 NEAR as `caller_deposit.yocto_near` [1](#0-0) .
4. The downstream promise (`action_to_promise` → `Promise::new(target).transfer(action.deposit)`) only forwards the small decoded `action.deposit`, not the full 5 NEAR attached.
5. The promise succeeds; `rlp_execute_callback` hits `PromiseResult::Successful` and performs **no refund** [8](#0-7) .
6. The caller's excess NEAR (5 NEAR minus the small transferred amount) remains stuck in the wallet contract's balance, confirmed by the existing test `test_caller_refunds`'s second assertion block, which only checks the caller lost `>= deposit_amount`, never checking or expecting any partial refund [5](#0-4) .

        result: &mut ActionReceiptResult,

        created_account: bool,

        let total_deposit = total_deposit(&action_receipt.actions())?;
        let prepaid_gas = total_prepaid_gas(&action_receipt.actions())?
            .checked_add(total_prepaid_send_fees(config, &action_receipt.actions())?.gas)
            .ok_or(IntegerOverflowError)?;
        let prepaid_exec_gas =
            total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
                .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee())
                .ok_or(IntegerOverflowError)?;
        let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
        let gross_gas_refund = if result.result.is_err() {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_burnt)
                .unwrap()
        } else {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_used)
                .unwrap()

        let refund_penalty: Gas = config.fees.gas_penalty_for_gas_refund(gross_gas_refund);

            gas_purchase_price

        let refund_penalty_amount = safe_gas_to_balance(penalty_gas_price, refund_penalty)?;

        // Refund for the leftover gas that was not used by this receipt.
        let unused_gas_balance_refund = safe_gas_to_balance(gas_purchase_price, gross_gas_refund)?
