## Title
Replay-verify's `TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, allowing a diverged state/position root to pass as "verified" - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2204` is the function used to assert that a locally-recomputed `TransactionOutput` (from execution or replay) matches an already-authenticated `TransactionInfo` (the leaf object bound into the transaction accumulator and covered by consensus signatures / accumulator proofs). It checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` — a fact the code itself documents in a `TODO(trading-native)` comment. [1](#0-0) [2](#0-1) 

## Finding Description
The state/hot-state/position checkpoint hashes are exactly the fields that bind the recomputed Sparse-Merkle/Jellyfish-Merkle state roots to the committed `TransactionInfo`, which in turn is accumulator-hashed and covered by the `LedgerInfo` signature (this is the same invariant enforced elsewhere by `DoStateCheckpoint::get_state_checkpoint_hashes`, which does perform this exact comparison during normal chunk execution: `get_state_checkpoint_hashes` in `execution/executor/src/workflow/do_state_checkpoint.rs:192-234` calls `ensure!(known[idx] == Some(computed_last_checkpoint_hash), ...)`). [3](#0-2) 

However, `ensure_match_transaction_info` is a *separate*, weaker comparator used by tooling that only has a `TransactionOutput` and a `TransactionInfo` in hand (not a full state tree), most notably `aptos-move/cli/src/commands.rs`'s replay/verification path. Because this function omits the checkpoint-hash comparisons, any tool relying on it to validate a replayed/local execution against a backup or archive's authenticated `TransactionInfo` will report success even if the recomputed state root (and, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, the recomputed native-position state root) diverges from the one baked into the signed `TransactionInfo`/`LedgerInfo`. This is a direct violation of the "proof-bearing responses/replay must not reinterpret committed data into a different ledger state" invariant: replay-verify is precisely the pivot meant to catch a wrong-root regression, and this comparator is blind to it for the fields that matter most.

## Impact Explanation
This does not itself corrupt committed mainnet state (the full-node commit/consensus/state-sync paths use `DoStateCheckpoint`, which does the correct check via `get_state_checkpoint_hashes`). The impact is scoped to the *replay-verification/backup-verification* tooling path that uses `ensure_match_transaction_info`: it can silently pass even when local execution produces a different state (or, with the new native-trading-position feature, position-state) root than what was authenticated on-chain. That means:
- A divergent-execution bug (VM nondeterminism, hard-fork-only inconsistency, a bad backup, or a compromised/buggy state store) that changes the resulting state root would not be caught by this specific comparator, undermining a tool whose entire purpose is state-commitment integrity verification.
- It is explicitly flagged by the code authors themselves as a gap to close "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", i.e., they acknowledge this becomes an active integrity gap once that feature ships.

Given this is confined to auxiliary verification tooling (not the executor's live commit path, which is separately protected), and requires the untrusted input to also produce a valid write-set/event-hash match while diverging only in checkpoint roots, I assess this as Medium severity rather than Critical/High — it is a real gap in a state-integrity check but does not by itself let an attacker corrupt consensus-committed state.

## Likelihood Explanation
Low-to-Medium likelihood of exploitation as a directed attack (an attacker would need to control a backup/replay source and craft a `TransactionOutput` that matches write-set/event hashes but has a different final state root, which is a strong constraint since `state_change_hash` covers the write set). It is more likely to matter as a silent-failure mode: a genuine consensus/state divergence (e.g., a hard-fork-only bug in the JMT/position-state pipeline, or a corrupted backup file) would go undetected by `db replay-verify`-style tooling using this function, giving false confidence in a compromised database.

## Recommendation
Add `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` comparisons to `ensure_match_transaction_info`, mirroring the checks already performed in `DoStateCheckpoint::get_state_checkpoint_hashes`, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled network-wide, as the existing TODO already recommends.

2.
