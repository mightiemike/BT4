### Title
Slow-POST body read in `TriggerSmartContractServlet.doPost` can hold servlet worker threads indefinitely, enabling Slowloris-style DoS - (File: `framework/src/main/java/org/tron/core/services/http/TriggerSmartContractServlet.java`)

### Summary
`doPost` reads the entire HTTP body via a blocking, line-by-line call `request.getReader().lines().collect(Collectors.joining(...))` before `Util.checkBodySize` is ever invoked, so the size cap is enforced only after the read completes. Because the read is blocking and unbounded in time (bounded only by Jetty's per-read idle timeout, which a trickling client can keep resetting), an attacker who drips body bytes slowly can occupy a servlet thread and the rate-limiter permit for that connection well beyond normal request duration.

### Finding Description
`TriggerSmartContractServlet.doPost` (lines 53-56) calls `request.getReader().lines().collect(...)` to materialize the whole POST body before calling `Util.checkBodySize(contract)`. [1](#0-0) 

This pattern is repeated across essentially every write-type servlet in this package (`TransferServlet`, `ParticipateAssetIssueServlet`, etc.), so it is a systemic pattern, not isolated to this file.

The request enters through `RateLimiterServlet.service`, which acquires a per-endpoint and global rate-limiter permit *before* calling `super.service(req, resp)` (which eventually invokes `doPost`), and only releases the permit in the `finally` block after `doPost` returns. [2](#0-1) 

So the rate-limiter permit, and the underlying Jetty worker thread, are held for the entire duration of the slow body read.

On the transport side, `HttpService.initServer`/`initContextHandler` constructs a plain `new Server(this.port)` (default Jetty connector, default idle timeout, no async/NIO read-timeout customization) and wraps the context in a `SizeLimitHandler` that only rejects requests whose body ultimately *exceeds* `maxRequestSize` — it does not bound how long the body may take to arrive. [3](#0-2) 

A `ConnectionLimit` bean is only added when `maxHttpConnectNumber > 0` is configured; whether this is enabled by default could not be fully confirmed from the index, but even when enabled it caps concurrent TCP connections, not per-request body-read duration. [4](#0-3) 

Jetty's connector idle timeout only fires when *no* bytes are received within the timeout window; an attacker who sends a single byte just before each idle-timeout interval elapses (classic Slowloris/slow-POST technique) resets the timer indefinitely, so the connection — and the servlet thread blocked inside `request.getReader().lines()` — can be held open far longer than any legitimate request would take, with no application-level cap on total read time.

### Impact Explanation
This maps to the "DoS via RPC-API" bounty impact class. With enough concurrent slow-drip connections to `/wallet/triggersmartcontract` (and similarly-structured endpoints), an attacker can exhaust Jetty's worker thread pool and/or the configured connection limit, causing legitimate HTTP API requests to stall or be rejected. The impact is bounded to availability of the HTTP JSON-RPC/API layer; it does not affect consensus, asset accounting, or the P2P/block-processing path.

### Likelihood Explanation
This requires only unprivileged network access to the node's HTTP API port (default-exposed service, no authentication, no funded account or signed transaction required), which satisfies the "unprivileged attacker" constraint. The attack is inexpensive to mount (many concurrent slow connections from commodity infrastructure) and is fully repeatable. It is, however, a generic characteristic of blocking-I/O servlet containers without an explicit application-level maximum-request-duration/read-timeout control, rather than a defect unique to the business logic in this servlet; feasibility in production also depends on Jetty's default connector idle-timeout value and whatever `maxHttpConnectNumber`/thread-pool sizing is configured, which bound (but do not eliminate) the achievable thread-exhaustion window.

### Recommendation
- Enforce a maximum total time (and/or minimum throughput) for reading the request body, e.g., via Jetty's `ServerConnector` idle timeout tuned tightly, or by wrapping the input stream with a byte-count/time-based watchdog that aborts slow reads.
- Move `Util.checkBodySize` (or an equivalent Content-Length pre-check) ahead of the body read so oversized/abusive requests are rejected before consuming a thread for the full read.
- Consider switching high-traffic write endpoints to Jetty's async I/O (non-blocking `ReadListener`) so a single stalled client does not pin a container thread, and ensure `maxHttpConnectNumber`/thread pool queue sizing plus per-IP connection caps are enabled by default to bound the number of simultaneous slow connections.

### Proof of Concept
Integration-style JUnit/manual PoC:
```java
// Pseudocode / manual reproduction against the running HTTP API
// 1. Open N (e.g. 300) sockets to <node>:8090/wallet/triggersmartcontract
// 2. Send headers: "POST /wallet/triggersmartcontract HTTP/1.1\r\nHost: x\r\nContent-Length: 100000\r\n\r\n"
// 3. Then write 1 body byte every (idleTimeout - 1) seconds, indefinitely, on each connection
// 4. Concurrently issue a normal, well-formed request to /wallet/triggersmartcontract
// Expected (vulnerable) result: once N >= server thread pool capacity, the normal
// request blocks/times out because all worker threads are parked inside
// request.getReader().lines() for the slow-drip connections, confirming that
// Util.checkBodySize's post-hoc check does not bound the read duration.
```
Note: exact numeric thresholds (Jetty default idle timeout, `maxHttpConnectNumber`/thread-pool size in the shipped default config) could not be fully verified from the indexed code, so the concrete time-to-exhaustion depends on the deployed defaults.
