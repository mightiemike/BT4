### Title
`TransactionOutput::ensure_match_transaction_info` never validates the state-checkpoint root hash, letting `replay_on_archive` accept a wrong state root as a successful replay — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by the archive replay-verification tool (`storage/db-tool/src/replay_on_archive.rs`) to confirm that locally re-executed transactions match the *authenticated* `TransactionInfo` pulled from a backup/archive (which is bound to a signed `LedgerInfo`). The function checks `status`, `gas_used`, `write_set_hash`, and `event_root_hash`, but never compares `state_checkpoint_hash` (the Sparse/Jellyfish Merkle root of the world state), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is exactly analogous to the seed report's pattern: a derived/aggregate committed value (there, `totalSupply`; here, the state root) is consumed for a security-relevant computation while a component that should feed into it is silently dropped, so the check passes even though it should not.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  is documented to assert that a `TransactionOutput` matches its `TransactionInfo`. Its body only validates four fields: [2](#0-1) 

It never checks `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The code itself documents this gap explicitly: [3](#0-2) 

This function is invoked by the archive-replay tool at the exact point where a freshly re-executed transaction output is compared against the archived, signature-backed `TransactionInfo`: [4](#0-3) 

Because `write_set_hash` only covers the write ops emitted by *that* transaction, it does not capture divergence in the derived Merkle root of the overall state tree (e.g., bugs in JMT/hot-state merge, sharded-JMT top-level assembly, or state restore paths — several of which exist in this codebase, such as `storage/aptosdb/src/sharded_jmt_merkle_db.rs`, `storage/aptosdb/src/state_store/hot_state.rs`, and the JMT restore path in `storage/jellyfish-merkle/src/restore/mod.rs`). If any of these produce a state root that differs from the correct one while still emitting a syntactically identical write set, `ensure_match_transaction_info` will report success anyway, since the state root is simply never inspected.

### Impact Explanation
`replay_on_archive` and its callers exist specifically to catch state-commitment divergence between a locally re-executed chain and the authenticated on-chain record stored in a backup archive — i.e., it is a proof/commitment-integrity gate as described in the task's scope ("Wrong accumulator root … proof accepted as valid", "Authenticated API or state-view output bound to the wrong version, object, or proof context"). With this gap, a state root computed by a different (or buggy, or tampered) execution/storage pipeline can pass replay verification as long as per-transaction write sets and events match, even though the actual committed ledger state diverges from the correct VM result. This directly undermines the ability to detect a hard-fork-class state-commitment bug via replay/backup verification tooling, which is one of the explicit acceptance categories in this task.

### Likelihood Explanation
The gap is unconditional (not just the `position_state_checkpoint_hash` mentioned in the TODO) — `state_checkpoint_hash` and `hot_state_checkpoint_hash` are also never validated, in every call to this function, regardless of feature flags. Any latent bug in the state-tree/hot-state/JMT restore layers (a broad and complex surface, several parts of which were reviewed in this investigation, e.g. `HotStateAccumulator`, `try_merge` in `storage/aptosdb/src/state_store/hot_state.rs`, and `calculate_top_levels` in `sharded_jmt_merkle_db.rs`) would silently escape detection by this specific check.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between the locally computed state-checkpoint hash(es) and `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` whenever these are present in the authenticated `TransactionInfo`, instead of only comparing `write_set_hash` and `event_root_hash`.

### Proof of Concept
1. In `replay_on_archive`, feed an archived chunk whose backed `TransactionInfo` has a correct `state_checkpoint_hash` for version `V`.
2. Have the local execution/storage layer produce, for the same version, an *incorrect* state-checkpoint root (e.g., due to a bug in hot-state merge or JMT restore) while still emitting the same per-transaction write set and events (a plausible scenario for bugs in the layer above the raw write set application, such as hot-state, sharded top levels, or restore-path fold logic).
3. `execute_and_verify` at [5](#0-4)  calls `ensure_match_transaction_info`, which only checks `status`, `gas_used`, `write_set_hash`, `event_root_hash` — all of which still match.
4. The tool reports a successful replay for version `V` even though the true committed state root diverges from the correct one.

**Caveat on verification completeness:** I located a second, parallel check path — `LedgerUpdateOutput::ensure_transaction_infos_match` in `execution/executor-types/src/ledger_update_output.rs`, used by `ChunkResultVerifier`/`ReplayChunkVerifier` for the backup-restore replay flow (`storage/backup/backup-cli/src/coordinators/replay_verify.rs`) — but I was unable to read its implementation before running out of tool calls. It is possible that this second path performs a full `TransactionInfo` (or its hash) comparison that *would* catch a state-root mismatch, which would mean the described gap is confined to the `replay_on_archive` tool specifically rather than all replay-verification flows. This should be confirmed before treating the impact as applying uniformly across all replay/restore tooling.
