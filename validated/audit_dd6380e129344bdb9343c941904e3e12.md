### Title
Missing declared-class validation in Starknet OS `execute_replace_class` causes OS/blockifier execution divergence, risking wrong committed state root - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Cairo Starknet OS implementation of the `replace_class` syscall does not verify that the target `class_hash` corresponds to an actually declared contract class before writing it into `contract_state_changes`, whereas the Rust blockifier's concrete execution of the same syscall does perform this check and rejects undeclared/incompatible classes. This is directly analogous to the reported bug class: a privileged/whitelist-style check that exists in one code path but is not cross-validated against the actual value used, allowing a mismatch between what is recorded/committed and what should have been enforced.

### Finding Description
The OS's `execute_replace_class` function explicitly contains a `TODO` acknowledging the missing check: [1](#0-0) 

It takes the caller-supplied `class_hash` from `ReplaceClassRequest`, and unconditionally writes it into the contract's `StateEntry` via `dict_update`, with no check that the class was ever declared in the class-hash-to-compiled-class mapping (`contract_class_changes` / declared classes).

In contrast, the concrete (blockifier) Rust implementation of the same syscall enforces this invariant: [2](#0-1) 

and the deprecated syscall handler does the same via `get_compiled_class`: [3](#0-2) 

Both blockifier paths call `state.get_compiled_class(class_hash)` (which fails with `UndeclaredClassHash` if the class was never declared) before mutating the contract's class hash; the native/VM syscall paths error out and the transaction reverts (or the call fails) if the class hash is undeclared, as validated by existing tests: [4](#0-3) [5](#0-4) 

Because the Starknet OS is the component that performs re-execution to produce the canonical state commitment/root that is proven and ultimately trusted by the network (analogous to "Starknet OS re-execution" in the accepted scope), any divergence between what the concrete sequencer execution (blockifier) accepts/rejects and what the OS accepts/rejects during re-execution is a serious correctness issue — exactly the class of bug described in the H-5 report, where a whitelist/validity check exists in one place (blockifier: `get_compiled_class` before `set_class_hash_at`) but is missing where it matters for the canonically-committed outcome (the OS's `execute_replace_class`).

### Impact Explanation
If a contract invokes `replace_class` with a `class_hash` that has never been declared (or is otherwise invalid, e.g. a Cairo 0 class hash being installed into what the OS treats as a Cairo 1-only replace path), the blockifier used by the sequencer to actually execute/build the block will reject this operation (transaction fails/reverts, and the class-hash state change is never applied). However, the Starknet OS, which re-executes the block to compute the final committed state root, does not perform the equivalent check and will happily accept the class-hash update into `contract_state_changes`.

This produces a genuine state-commitment divergence: the state actually applied and gossiped by the sequencer (via blockifier) differs from the state the OS commits to and proves. Since the OS output (state diffs / roots) is what is ultimately verified and trusted as the canonical Starknet state, this can lead to:
- A wrong committed state root / block hash relative to what the sequencer node believes it executed (honest-node divergence between the execution layer and OS/proving layer).
- A contract silently having its class hash pointed at an undeclared/invalid class in the proven state, which could make the contract permanently unusable (undeclared class => execution of any subsequent call to that contract fails when the class is fetched), effectively a form of permanent freezing of that account/contract's functionality once such state is committed — reachable directly from a single unprivileged Invoke transaction executing a Cairo 1 contract calling `replace_class` with an arbitrary felt as class hash.

This satisfies the Medium/High severity acceptance bar: potential for "wrong committed root or block hash" / "honest-node divergence" and account/contract "unauthorized" or effectively frozen state, from a fully unprivileged transaction sender's call into any contract that exposes a `replace_class` syscall path (a standard Cairo 1 capability, not an admin-only feature).

### Likelihood Explanation
Likelihood is high in terms of reachability: `replace_class` is a standard Starknet syscall available to any Cairo 1 contract; an attacker only needs to deploy (or find) a contract exposing a call path to `replace_class_syscall` with a caller-controlled `class_hash` argument (the codebase's own test contracts, e.g. `test_replace_class`, demonstrate this is a normal, commonly exposed pattern) and pass an arbitrary/undeclared felt. No special privileges, staking, or node-operator access is required — this is reachable from a single ordinary transaction sent by any user, which matches the "unprivileged transaction sender" reachability requirement. The only uncertainty is exactly how block-building and OS re-execution are orchestrated in this fork (i.e., whether some upstream guard elsewhere in the pipeline effectively prevents the undeclared class hash from ever reaching the OS's `contract_state_changes` write) — I could not fully verify whether such an external guard exists given the remaining tool budget; the explicit `TODO(Yoni, 1/1/2026)` comment in the source strongly suggests this is a known, currently-unaddressed gap rather than an intentional, already-mitigated design.

### Recommendation
Add the equivalent declared-class check in the Cairo OS's `execute_replace_class` (and the deprecated syscall variant in `deprecated_execute_syscalls.cairo`) that the Rust blockifier already performs: before applying `dict_update` to `contract_state_changes` with the new `class_hash`, assert that the class hash is present in the block's declared-class facts (`contract_class_changes` / OS input's declared classes), mirroring `state.get_compiled_class(class_hash)` in `syscall_base.rs`. This restores parity between blockifier's concrete execution and the OS's re-execution, eliminating the possibility of state-commitment divergence for this syscall.

### Proof of Concept
1. Deploy (or use an existing) Cairo 1 contract that exposes a `replace_class`-calling entry point with an attacker-controlled `class_hash` argument, e.g., the `test_replace_class` pattern used throughout the codebase's own tests (`blockifier_test_utils/resources/feature_contracts/cairo1/test_contract.cairo`, `syscall_tests/replace_class.rs`).
2. Submit an Invoke transaction that calls this entry point with a `class_hash` felt value that has never been declared on-chain (e.g., an arbitrary constant such as `1234`).
3. Observe: in the concrete blockifier execution used by the sequencer, this fails with `UndeclaredClassHash`/"is not declared" (as shown by the existing test `undeclared_class_hash` in `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs`), so the sequencer does not apply this state change and/or reverts the transaction.
4. During Starknet OS re-execution of the same block/transaction (used to build the state diff / commitment that is proven), `execute_replace_class` in `syscall_impls.cairo` performs no equivalent check and will apply the state update (`dict_update` on `contract_state_changes`) regardless, producing a different final state (and hence commitment/root) for this contract's class hash than what blockifier's concrete execution produced.
5. This constitutes a concrete divergence between the two "authoritative" execution paths on a fund/permission-relevant piece of state (a contract's class hash), matching the exact anatomy of the reported H-5 bug: a validity check enforced in one execution path (Solana whitelist/mint check, here Rust blockifier's declared-class check) is silently skipped in the path that determines the recorded/committed outcome (ZetaChain node parsing, here Starknet OS state commitment).

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
