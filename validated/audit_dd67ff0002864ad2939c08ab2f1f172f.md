### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` RPC methods bypass `Auth` and mutate sequencer state - (File: `crates/sequencer/src/rpc.rs`)

### Summary
The sequencer's JSON-RPC server exposes `citrea_haltCommitments` and `citrea_resumeCommitments`, which directly control whether the sequencer publishes `SequencerCommitment`s to the DA layer. Neither method is included in the RPC `Auth` middleware's protected-method allowlist, so any unauthenticated network caller can invoke them without an API key, unlike the backup-related endpoints that are correctly gated.

### Finding Description
The sequencer defines and implements `halt_commitments`/`resume_commitments` as plain RPC methods that forward `SequencerRpcMessage::HaltCommitments`/`ResumeCommitments` to the runner, which toggles the `halt_commitment_tx` signal consumed by the commitment-production loop. [1](#0-0) [2](#0-1) [3](#0-2) 

All sequencer RPC methods share the same server and middleware stack. The `Auth` middleware only checks membership in `PROTECTED_METHODS`, which contains exactly `backup_create`, `backup_validate`, `backup_info`. For every other method, including `citrea_haltCommitments` and `citrea_resumeCommitments`, the request is passed straight through to the handler with no API-key check whatsoever: [4](#0-3) 

This is the same class of defect as the reported `Governance::cancel` bug: a state-mutating entry point that is supposed to be privileged (commitment publishing is a core sequencer operation) is left reachable by an unauthorized caller because the guard that should apply to it was never wired in. The binding broken here is: *sequencer-controlled DA submission versus what any anonymous caller can force* — i.e., an unprivileged actor can flip an internal sequencer control flag that only the sequencer operator should control.

### Impact Explanation
Calling `citrea_haltCommitments` from any client that can reach the sequencer's RPC endpoint stops the sequencer from posting new `SequencerCommitment`s to Bitcoin indefinitely (until someone calls `citrea_resumeCommitments`, which is equally unauthenticated but also usable by the attacker to keep re-halting). Because the light-client and batch-proof pipeline, and ultimately bridge withdrawals, depend on sequencer commitments being regularly posted to L1, an attacker can stall checkpointing/finality of the rollup on Bitcoin without needing any sequencer, prover, or operator key — purely through a missing entry in the `Auth` middleware's allowlist.

### Likelihood Explanation
Exploitation only requires network access to the sequencer's JSON-RPC port and knowledge of the method name (which is defined in the public RPC trait), no credentials, no signatures, and no privileged role. This is a straightforward, high-likelihood issue if the sequencer RPC port is reachable by anything other than a fully trusted, isolated caller.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other sequencer-control method with equivalent operational sensitivity) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs` so they require the configured `api_key`, consistent with how `backup_create`/`backup_validate`/`backup_info` are already protected.

### Proof of Concept
1. Start a sequencer node with its RPC server bound to a reachable interface (default config, no API key required for non-backup methods).
2. As an unauthenticated client, call:
```
curl -X POST http://<sequencer-rpc>:PORT -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}'
```
3. Observe (via `SequencerRpcMessage::HaltCommitments` forwarding in `crates/sequencer/src/runner.rs`) that the commitment service is halted; the sequencer log will show `"Sequencer: Halted commitments via RPC"`. No API key or authentication was required for this state-changing call, unlike `backup_create`, which returns `401 Cannot access protected method` without one. [5](#0-4)

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
