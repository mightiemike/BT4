### Title
Stale `AccountIndexStore` mapping after account rename permanently blocks reuse of old name - ([File: chainbase/src/main/java/org/tron/core/store/AccountIndexStore.java])

### Summary
`UpdateAccountActuator.execute()` writes the new name into `AccountIndexStore` via `put(account)` but never removes the old name entry, so after a rename the old name key continues to resolve to the renaming account's address forever. Once `DynamicPropertiesStore.getAllowUpdateAccountName()` reverts to `0` (the default/enforced state), the stale entry permanently blocks any other account from ever registering that name via `validate()`'s `accountIndexStore.has(accountName)` check.

### Finding Description
`UpdateAccountActuator.execute()` performs: [1](#0-0) 
It sets the new name on the `AccountCapsule`, persists it in `AccountStore`, and calls `accountIndexStore.put(account)`, which only inserts a `newName -> address` mapping and does not delete the previous `oldName -> address` mapping: [2](#0-1) 

`validate()` only blocks a rename to an already-indexed name when `getAllowUpdateAccountName() == 0`: [3](#0-2) 

Exploit flow (unprivileged, entirely attacker-controlled once `AllowUpdateAccountName` is `1`):
1. Account A is created with name `X`, `execute()` calls `accountIndexStore.put(A)` → `X -> A`.
2. With `AllowUpdateAccountName == 1`, A broadcasts `AccountUpdateContract` renaming to `Y`. `validate()` passes (the "already existed" and "name is existed" checks are both gated on `== 0`). `execute()` sets A's name to `Y` and calls `accountIndexStore.put(A)` → adds `Y -> A`, but `X -> A` is never deleted.
3. Later, if `AllowUpdateAccountName` reverts to `0` (its default/normal governance state), any third account C attempting to claim name `X` hits `chainBaseManager.getAccountIndexStore().has(accountName)` returning `true` for `X` (stale entry), so `validate()` throws `"This name is existed"`, permanently denying `X` to anyone, even though A no longer holds it.

The unit test suite itself demonstrates awareness of this leftover state by manually issuing cleanup calls after tests that perform renames, e.g. `dbManager.getAccountIndexStore().delete(accountTest.getBytes())` and `dbManager.getAccountIndexStore().delete(ACCOUNT_NAME.getBytes())`, which would not be necessary if `execute()` cleaned up stale index entries itself: [4](#0-3) 

### Impact Explanation
Once a name is used and then abandoned via rename, it becomes permanently unclaimable by any other account while `AllowUpdateAccountName == 0`, effectively freezing that identity/name slot forever with no owner-recovery path (the vacated name maps to an address that no longer uses it, and there is no delete/actuator path to clear it). This is a persistent, unrecoverable state-integrity defect in the account-index namespace, reachable purely through normal `AccountUpdateContract` transactions.

### Likelihood Explanation
The only precondition is that `AllowUpdateAccountName` is `1` at rename time (a chain-wide dynamic property, not attacker-controlled, but the question stipulates this state as given) and that it can later be `0` (its typical/default state) when a third party tries to reuse the name. Given the precondition, exploitation is fully deterministic and repeatable by any account holder issuing a standard rename transaction — no special privileges are required beyond owning the account being renamed.

### Recommendation
In `UpdateAccountActuator.execute()`, before writing the new name, delete the old index entry if it currently points to this account, e.g. capture `account.getAccountName()` prior to `setAccountName(...)` and call `chainBaseManager.getAccountIndexStore().delete(oldName)` (guarding against deleting an entry that another account may have since claimed under permissive mode) before calling `put(account)` with the new name.

### Proof of Concept
```java
// Extends UpdateAccountActuatorTest
@Test
public void staleIndexBlocksReuseAfterRename() throws Exception {
  // Step 1: create account A with name X, rename to Y under permissive mode
  dbManager.getDynamicPropertiesStore().saveAllowUpdateAccountName(1);
  UpdateAccount(ACCOUNT_NAME, OWNER_ADDRESS);      // A: "" -> X
  UpdateAccount(ACCOUNT_NAME_1, OWNER_ADDRESS);    // A: X -> Y

  // Old name X is still indexed to A even though A no longer holds it
  Assert.assertTrue(dbManager.getAccountIndexStore().has(ACCOUNT_NAME.getBytes()));

  // Step 2: revert to enforced mode and let a different account C try to claim X
  dbManager.getDynamicPropertiesStore().saveAllowUpdateAccountName(0);
  AccountCapsule accountC = new AccountCapsule(
      ByteString.copyFrom(ByteArray.fromHexString(OWNER_ADDRESS_1)),
      ByteString.EMPTY, AccountType.Normal);
  dbManager.getAccountStore().put(accountC.getAddress().toByteArray(), accountC);

  TransactionResultCapsule ret = new TransactionResultCapsule();
  UpdateAccountActuator actuatorC = new UpdateAccountActuator();
  actuatorC.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getContract(ACCOUNT_NAME, OWNER_ADDRESS_1)); // C tries to claim "X"

  try {
    actuatorC.validate();
    Assert.fail("Expected validate() to reject reuse, proving name X is permanently unclaimable");
  } catch (ContractValidateException e) {
    Assert.assertEquals("This name is existed", e.getMessage());
    // Confirms X is blocked for C despite A no longer holding X
  }
}
```
