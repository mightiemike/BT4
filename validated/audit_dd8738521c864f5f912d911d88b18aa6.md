### Title
Deposit Refund Sent to DelegateAction Sender Instead of Relayer on Inner Receipt Failure — (File: `runtime/runtime/src/actions.rs`)

### Summary

In NEAR's meta-transaction (NEP-366) system, when a relayer submits a `DelegateAction` that carries an attached deposit and the inner action fails on the receiver's shard, the deposit refund is sent to the `DelegateAction` sender (Alice), not the relayer who actually paid for it. This is the direct nearcore analog of the external bug: an authorized third party acts on behalf of another, pays the cost, but the refund flows to the wrong address.

### Finding Description

In `apply_delegate_action` (`runtime/runtime/src/actions.rs`), the inner receipt spawned from a `DelegateAction` is constructed as:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // Alice — the DelegateAction signer
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(),  // Relayer
        signer_public_key: action_receipt.signer_public_key().clone(),
        ...
    }),
});
``` [1](#0-0) 

When this inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` in `runtime/runtime/src/lib.rs` issues a deposit refund:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [2](#0-1) 

`balance_refund_receiver()` resolves to `predecessor_id` when no `refund_to` override is present:

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [3](#0-2) 

Because the inner receipt uses `ReceiptEnum::Action` (V1, not V2), `refund_to()` always returns `None`:

```rust
ReceiptEnum::Action(_) | ... => &None,
ReceiptEnum::ActionV2(action_receipt_v2) | ... => &action_receipt_v2.refund_to,
``` [4](#0-3) 

So `balance_refund_receiver()` returns `predecessor_id` = Alice. The relayer, who funded the deposit, receives nothing.

The code comment in `apply_delegate_action` explicitly acknowledges this:

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. … Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit." [5](#0-4) 

The architecture documentation confirms the financial risk:

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is Alice and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard**." [6](#0-5) 

### Impact Explanation

An unprivileged user (Alice) can craft a `DelegateAction` with a large attached deposit targeting a call that is guaranteed to fail (e.g., calling a non-existent method on a contract, or a contract that always panics). The relayer pays the deposit when converting the transaction to a receipt. When the inner receipt fails, the full deposit is refunded to Alice, not the relayer. The relayer suffers a net loss equal to the attached deposit; Alice gains that amount at zero cost beyond signing a message.

This satisfies the "stealing or loss of funds" and "balance manipulation" impact categories. The attacker is unprivileged (any account holder), the trigger is a standard JSON-RPC transaction submission, and the root cause is entirely within nearcore's runtime execution path.

### Likelihood Explanation

Any account that can produce a valid `DelegateAction` signature can exploit this. The relayer has no on-chain mechanism to verify that the inner action will succeed before committing the deposit. The attack requires only: (1) Alice signs a `DelegateAction` with a large deposit to a failing call; (2) the relayer submits it. No privileged access, no validator control, no network-level capability is needed.

### Recommendation

The inner receipt created in `apply_delegate_action` should be constructed as `ReceiptEnum::ActionV2(ActionReceiptV2 { ..., refund_to: Some(relayer_id), ... })` where `relayer_id` is the `predecessor_id` of the outer action receipt (i.e., the relayer's account). This mirrors the fix applied in the Axelar report: add an explicit "refund to" address that tracks who actually paid, separate from who the action is attributed to.

Gas refunds already correctly flow to the signer (relayer) via `Receipt::new_gas_refund(&action_receipt.signer_id(), ...)`. The same separation must be applied to deposit refunds. [7](#0-6) 

### Proof of Concept

1. Alice has zero NEAR but a valid account and key.
2. Alice crafts a `DelegateAction`: `sender_id = alice`, `receiver_id = some_contract`, `actions = [FunctionCall { method = "always_panics", deposit = 100 NEAR }]`.
3. Alice signs it and sends it off-chain to a relayer.
4. The relayer wraps it in a transaction (relayer is `signer_id`), paying the 100 NEAR deposit from its own balance.
5. On Alice's shard, `apply_delegate_action` creates an inner receipt with `predecessor_id = alice`, `signer_id = relayer`.
6. On `some_contract`'s shard, the function call panics. `refund_unspent_gas_and_deposits` fires:
   - Gas refund → `signer_id` = relayer ✓
   - Deposit refund → `balance_refund_receiver()` = `predecessor_id` = **Alice** ✗
7. Alice's balance increases by 100 NEAR. The relayer's balance is permanently reduced by 100 NEAR.

The test `test_gas_key_refund` in `test-loop-tests/src/tests/gas_keys.rs` (lines 298–394) confirms the deposit-refund-to-predecessor behavior for the analogous gas-key path, and the integration test comment at line 357 explicitly notes "deposit was deducted when the tx was converted to a receipt, then refunded when the function call failed" — back to the account (predecessor), not the gas payer. [8](#0-7)
