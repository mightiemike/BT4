Confirmed: across `shopify-app-remix` and `shopify-app-react-router`, every unauthenticated HTTP request-authentication handler (webhook, flow, fulfillment-service, and app proxy) calls `await request.text()` to buffer the **entire** raw request body into memory *before* any HMAC/signature validation is performed, and none of these code paths impose any request size limit. This contrasts with `shopify-app-express`, which explicitly bounds body size via `express.text({type: '*/*', limit: '500kb'})` in `processWebhooks`.

#### Title
Unbounded request body buffering before HMAC validation in Remix/React Router webhook, flow, and fulfillment-service authenticate handlers - (File: `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts`, and their React Router equivalents)

#### Summary
The `authenticate.webhook`, `authenticate.flow`, and `authenticate.fulfillmentService` handlers in `@shopify/shopify-app-remix` and `@shopify/shopify-app-react-router` read the entire incoming HTTP request body into memory via `await request.text()` before performing any HMAC/signature check, and impose no maximum body size. An anonymous attacker who knows (or guesses) an app's public webhook/flow/fulfillment-service callback URL can send POST requests with arbitrarily large bodies, forcing the app server to buffer each one fully in memory, leading to memory exhaustion and process crash/OOM-kill — directly analogous to the Covenant Signer DoS (unbounded request size before authentication).

#### Finding Description
In `authenticateWebhookFactory` [1](#0-0) , the handler only validates that the method is `POST` and then immediately calls `const rawBody = await request.text();` before calling `api.webhooks.validate`. The HMAC check happens only *after* the full body has already been read into memory [2](#0-1) . The same pattern exists in the React Router package [3](#0-2) , and in the flow and fulfillment-service authenticate handlers for both packages [4](#0-3) [5](#0-4) .

None of these call sites configure a body size limit on `request.text()`, nor is any limit imposed by the underlying Fetch `Request` object itself in Node.js runtimes. This is unlike the Express package, `processWebhooks` in `@shopify/shopify-app-express` explicitly applies `express.text({type: '*/*', limit: '500kb'})` before processing [6](#0-5) , so the Express package is not affected the same way. These endpoints are reachable by anonymous requests (no authentication is required to reach them — that's the point of the handler), and the callback URLs (`/webhooks`, flow/fulfillment-service callback paths) are typically fixed, discoverable routes in a merchant's app.

#### Impact Explanation
An attacker sending large POST bodies repeatedly to a discoverable webhook/flow/fulfillment-service endpoint can cause the Node.js process serving the Remix/React Router app to buffer arbitrarily large strings in memory prior to any authentication check, potentially exhausting available memory and crashing the process (OOM kill), taking the app offline for all merchants served by that process — the same failure mode described in the Covenant Signer report.

#### Likelihood Explanation
High: these endpoints are unauthenticated by design (webhooks/flow/fulfillment-service calls arrive from Shopify without a prior session), the callback URLs are typically static and easily guessable/discoverable from the app's configuration, and no size limiting exists at this layer for Remix/React Router deployments.

#### Recommendation
Impose a maximum request body size before calling `request.text()` in `authenticateWebhookFactory`, `authenticateFlowFactory`, and `authenticateFulfillmentServiceFactory` for both `shopify-app-remix` and `shopify-app-react-router` (e.g., check `Content-Length` header and/or stream-read with an enforced byte cap, rejecting with `413 Payload Too Large` if exceeded), mirroring the `limit: '500kb'` protection already applied in `shopify-app-express`.

#### Proof of Concept
```ts
// Any Remix/React Router app using @shopify/shopify-app-remix or
// @shopify/shopify-app-react-router with a mounted webhook/flow/
// fulfillment-service route, e.g. app/routes/webhooks.tsx:
//
// export const action = async ({ request }) => {
//   await authenticate.webhook(request);
//   ...
// };

// Attacker script (analogous to the covenant-signer PoC):
import grequests

url = 'https://victim-app.example.com/webhooks'
huge_body = 'a' * 500_000_000  # 500 MB body, no HMAC required to trigger buffering
headers = {'X-Shopify-Hmac-Sha256': 'invalid', 'X-Shopify-Topic': 'orders/create',
           'X-Shopify-Shop-Domain': 'test.myshopify.com'}

rs = [grequests.post(url, data=huge_body, headers=headers) for _ in range(10)]
grequests.map(rs)
# Each request causes `await request.text()` to fully buffer 500MB in the
# Node process before HMAC validation fails, and repeated concurrent
# requests exhaust process memory, crashing the app server.
```

export function processWebhooks({
  api,
  config,
}: ApiAndConfigParams): ProcessWebhooksMiddleware {
  return function ({webhookHandlers}: ProcessWebhooksMiddlewareParams) {
    mountWebhooks(api, config, webhookHandlers);

    return [
      express.text({type: '*/*', limit: '500kb'}),
      async (req: Request, res: Response) => {
        await process({
          req,
          res,
          api,
          config,
        });
      },
    ];
  };
}
