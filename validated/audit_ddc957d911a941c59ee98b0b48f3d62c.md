### Title
Fund migration signing verification recomputes balance independently, causing exact-hash mismatch and stalled migration when old-TSS balance drifts between coordinator signing and validator verification — ([File: universalClient/tss/sessionmanager/sessionmanager.go])

### Summary
`liquidateAccount`'s bug class is: a value that changes with external/on-chain state (block-dependent interest accrual) is required to match *exactly* between two independently computed points in time, and any drift between those two computations causes the whole operation to fail. Push Chain's fund-migration TSS signing flow has the same structural pattern: the coordinator computes a signing hash from the **old TSS address's live native balance** at setup time, and each participating validator later **independently re-queries the same balance** to verify that the coordinator's hash is legitimate. Because the old TSS address's balance is a public, permissionlessly-writable value (anyone can send native tokens to any address), it can drift between the two queries, causing the verification hash comparison to fail and the migration signing round to be rejected.

### Finding Description
`TxBuilder.GetFundMigrationSigningRequest` builds the migration sweep transaction using `balance - gasCost - l1GasFee`, where `balance` is either a caller-supplied value or freshly queried via RPC (`tb.rpcClient.GetBalance`): [1](#0-0) 

The coordinator calls this once at signing-setup time via `createFundMigrationSignSetup` → `buildFundMigrationTransaction(ctx, eventData, assignedNonce, nil /* query chain for balance */)`, explicitly querying the chain for the live balance: [2](#0-1) 

`buildFundMigrationTransaction` documents that when a `claimedAmount` is supplied, the balance is *reconstructed deterministically* (amount + gas + L1 fee) specifically "used by the ACK verify path to rebuild the hash deterministically without racing a successful sweep": [3](#0-2) 

However, `SessionManager.verifyFundMigrationSigningRequest` — the function each validator uses to independently confirm the coordinator's proposed signing hash before participating in the DKLS signing round — builds `migrationFundData` **without setting `Balance`** at all, meaning it always falls into the RPC-query branch of `GetFundMigrationSigningRequest`, re-querying the *current* on-chain balance of the old TSS address rather than reconstructing the balance the coordinator used: [4](#0-3) 

The comparison is a strict byte-equality check on the signing hash (and a redundant strict equality on `TSSFundMigrationAmount`), with no tolerance band: [5](#0-4) 

Because the old TSS address's native balance is a public destination that **anyone can send funds to** (a plain, permissionless native-asset transfer requires no privilege), an unprivileged actor can alter that balance in between (a) the coordinator's `GetFundMigrationSigningRequest` balance query at setup time and (b) each validator's independent balance re-query at verification time. Any change (even a tiny dust deposit) changes `maxTransfer` and therefore the computed transaction, its hash, and the `TSSFundMigrationAmount`, causing `verifyFundMigrationSigningRequest` to reject the signing request with `"fund migration signing hash mismatch"` even though the coordinator behaved correctly and honestly.

This differs from `handleFundMigrationSignSetup`'s subsequent ACK-based reconciliation flow (`buildFundMigrationTransaction` with `claimedAmount`) which was clearly designed to solve exactly this race by pinning the balance deterministically — but `verifyFundMigrationSigningRequest` in `sessionmanager.go` does not use that reconstruction path at all, so the fix that exists elsewhere in the codebase for this exact hazard is bypassed on the verification path.

### Impact Explanation
This does not directly cause fund loss, but it breaks the honest-validator finalization path for TSS fund migration: an unprivileged party can grief the migration-signing consensus by simply sending native tokens (even dust) to the well-known old TSS address at any point after `FundMigrationInitiated` and before the signing round completes. Every honest validator's independently recomputed hash will then diverge from the coordinator's hash, causing `verifyFundMigrationSigningRequest` to reject the setup and abort that signing attempt, repeatedly, for as long as the attacker keeps perturbing the balance (this costs the attacker only gas/dust value on the source chain). This stalls fund migration (a "wrong TSS event"/migration outcome scenario per the required impact list), delaying or indefinitely blocking recovery of TSS-controlled funds during a genuine key rotation, which is a availability/state-safety issue reachable by an ordinary unprivileged actor without any node/validator compromise.

### Likelihood Explanation
High. Sending native currency to a known public address (the old TSS address, derivable from `OldTssPubkey` in the `FundMigrationInitiated` event, which is emitted on-chain) requires no special access and costs only a normal transfer fee. Fund migration windows can span multiple network round-trips (setup message broadcast, DKLS signing rounds among participants), giving ample time for an attacker who is watching for `FundMigrationInitiated` events to interject a balance-altering transaction before validators finish their independent verification.

### Recommendation
Make `verifyFundMigrationSigningRequest` use the same deterministic-balance reconstruction (`claimedAmount`) mechanism that `buildFundMigrationTransaction` already implements for its ACK-verify path, rather than re-querying the live chain balance. Alternatively, have the coordinator carry the exact balance/amount it used to sign inside the setup message (already partly done via `UnsignedSigningReq.TSSFundMigrationAmount`) and have validators verify the *coordinator-supplied* amount is internally consistent (positive, correctly derived nonce, hash reproducible from that fixed amount) instead of independently re-deriving the balance from a live, attacker-influenceable RPC read.

### Proof of Concept
1. Monitor the chain for a `FundMigrationInitiated` event exposing `OldTssPubkey`/derived old TSS address for a given external chain.
2. Immediately after the coordinator queries the old TSS balance (`GetFundMigrationSigningRequest`, RPC branch) and broadcasts the setup message with its computed `SigningHash`/`TSSFundMigrationAmount`, send a small native-token transfer to the old TSS address from any unprivileged wallet.
3. Each validator's `SessionManager.verifyFundMigrationSigningRequest` re-queries the balance (now changed) via `builder.GetFundMigrationSigningRequest` and recomputes a different `maxTransfer`/hash.
4. The strict `bytes.Equal(signingReq.SigningHash, req.SigningHash)` check fails on every honest validator, rejecting the setup with `"fund migration signing hash mismatch"`, and the signing round for that migration attempt is aborted. [6](#0-5) 

Note: I was unable to fully trace the coordinator's ACK-retry logic in `universalClient/tss/coordinator/msg_handler.go` (which references `claimedAmount`) within the remaining budget to confirm whether a retry with reconstructed balance eventually succeeds after some number of failed rounds; if such a retry-and-reconcile mechanism exists and converges reliably, the practical impact may be reduced to a bounded delay rather than indefinite stall. This should be verified by reviewing `msg_handler.go`'s ACK handling in a follow-up session.

func (c *Coordinator) createFundMigrationSignSetup(ctx context.Context, eventData []byte, partyIDs []string, assignedNonce *uint64) ([]byte, *common.UnsignedSigningReq, error) {
	var migrationData utsstypes.FundMigrationInitiatedEventData
	if err := json.Unmarshal(eventData, &migrationData); err != nil {
		return nil, nil, fmt.Errorf("failed to unmarshal fund migration event data: %w", err)
	}

	// Load old keyshare as a sanity check; keyID bytes are derived from the string.
	if _, err := c.keyshareManager.Get(migrationData.OldKeyID); err != nil {
		return nil, nil, fmt.Errorf("failed to load keyshare for old keyId %s: %w", migrationData.OldKeyID, err)
	}
	keyIDBytes := deriveKeyIDBytes(migrationData.OldKeyID)

	signingReq, err := c.buildFundMigrationTransaction(ctx, eventData, assignedNonce, nil /* query chain for balance */)
	if err != nil {
		return nil, nil, fmt.Errorf("failed to build fund migration transaction: %w", err)
	}

	participantIDs := make([]byte, 0, len(partyIDs)*10)
	for i, partyID := range partyIDs {
		if i > 0 {
			participantIDs = append(participantIDs, 0)
		}
		participantIDs = append(participantIDs, []byte(partyID)...)
	}

	setupData, err := session.DklsSignSetupMsgNew(keyIDBytes, nil, signingReq.SigningHash, participantIDs)
	if err != nil {
		return nil, nil, fmt.Errorf("failed to create fund migration sign setup: %w", err)
	}

	return setupData, signingReq, nil
}

// buildFundMigrationTransaction parses event data and returns the signing
// request for sweeping old-TSS funds to the current TSS. If claimedAmount is
// non-nil, the balance is reconstructed as amount + gas + L1 instead of
// queried from chain — used by the ACK verify path to rebuild the hash
// deterministically without racing a successful sweep.
func (c *Coordinator) buildFundMigrationTransaction(ctx context.Context, eventData []byte, assignedNonce *uint64, claimedAmount *big.Int) (*common.UnsignedSigningReq, error) {
	if assignedNonce == nil {
		return nil, fmt.Errorf("assigned nonce is required for fund migration transaction")
	}
	var migrationData utsstypes.FundMigrationInitiatedEventData
	if err := json.Unmarshal(eventData, &migrationData); err != nil {
		return nil, fmt.Errorf("unmarshal fund migration event data: %w", err)
	}
	oldTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.OldTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive old TSS address: %w", err)
	}
	currentTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.CurrentTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive current TSS address: %w", err)
	}
	if c.chains == nil {
		return nil, fmt.Errorf("chains manager not configured")
	}
	client, err := c.chains.GetClient(migrationData.Chain)
	if err != nil {
		return nil, fmt.Errorf("get client for chain %s: %w", migrationData.Chain, err)
	}
	builder, err := client.GetTxBuilder()
	if err != nil {
		return nil, fmt.Errorf("get tx builder for chain %s: %w", migrationData.Chain, err)
	}

	gasPrice := new(big.Int)
	gasPrice.SetString(migrationData.GasPrice, 10)
	l1GasFee := new(big.Int)
	l1GasFee.SetString(migrationData.L1GasFee, 10)

	var balance *big.Int
	if claimedAmount != nil {
		// balance = amount + gas + L1; inverse of computeFundMigrationTransfer
		balance = new(big.Int).Set(claimedAmount)
		balance.Add(balance, new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(migrationData.GasLimit)))
		if l1GasFee.Sign() > 0 {
			balance.Add(balance, l1GasFee)
		}
	}
