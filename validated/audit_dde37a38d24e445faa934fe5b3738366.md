### Title
Inconsistent enforcement of the `supportUnfreezeDelay` control switch between `WithdrawExpireUnfreezeActuator` and `WithdrawExpireUnfreezeProcessor` - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`)

### Summary
The committee-controlled `supportUnfreezeDelay` feature switch is meant to gate whether `WithdrawExpireUnfreeze` operations (withdrawal of previously unfrozen TRX after its unfreeze-delay period) are allowed on the chain. The switch is enforced in the standard transaction path (`WithdrawExpireUnfreezeActuator`) but is missing in the TVM native-contract path (`WithdrawExpireUnfreezeProcessor`) that is reachable from any smart contract, allowing the control to be bypassed — the same class of bug as the GoGoPool `whenNotPaused` inconsistency, where a gate applied to one entry point (`withdrawGGP`) was missing on an equivalent code path (`claimAndRestake`).

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly checks the DAO/committee-controlled feature flag before allowing the withdrawal to proceed: [1](#0-0) 

This means when the committee has not enabled `supportUnfreezeDelay` (i.e., the unfreeze-delay/new resource model feature is not yet activated on the network), regular transactions calling `WithdrawExpireUnfreezeContract` are rejected with `ContractValidateException`.

However, the equivalent TVM-native code path, `WithdrawExpireUnfreezeProcessor`, which performs the identical state mutation (crediting the account balance with the matured unfrozen amount and clearing the corresponding `UnFreezeV2` entries), has no such check in its `validate()` method: [2](#0-1) 

This processor is invoked from within TVM execution (native contract call path exposed via `OperationActions.java`/`OperationRegistry.java`, referencing `withdrawExpireUnfreeze`), meaning any unprivileged user who deploys or calls a smart contract can trigger the withdrawal logic while completely bypassing the `supportUnfreezeDelay` gate that the same operation is subject to when submitted as a normal transaction.

This is structurally identical to the reported GoGoPool issue: a control switch (`whenNotPaused` / `supportUnfreezeDelay`) is enforced on one function (`withdrawGGP` / `WithdrawExpireUnfreezeActuator`) but not on a functionally equivalent alternate entry point (`claimAndRestake` / `WithdrawExpireUnfreezeProcessor`) that reaches the same underlying state-mutating logic.

### Impact Explanation
The impact is a divergence/invalid-state issue rather than direct fund theft: it breaks the intended committee governance control over when the unfreeze-delay withdrawal feature becomes active. If the switch is meant to be off (feature not yet rolled out, or intentionally disabled after being found problematic), TVM callers can still exercise the functionality, undermining the network's controlled feature-activation guarantee and creating inconsistent behavior between the actuator-based and TVM-based code paths that operate on the same account state.

### Likelihood Explanation
The TVM native-contract call is reachable by any unprivileged user capable of deploying/invoking a smart contract, requiring no special privileges — only that the target account has expired/unfrozen balances pending withdrawal. The condition under which this materializes (the committee flag being off while normal actuator withdrawal is blocked) requires that `supportUnfreezeDelay` is disabled at the time, which is a normal operational/config state rather than a rare edge case.

### Recommendation
Add the same `supportUnfreezeDelay` (or equivalent `AllowNewResourceModel`/unfreeze-delay) check to `WithdrawExpireUnfreezeProcessor.validate()` in `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`, mirroring the check already present in `WithdrawExpireUnfreezeActuator.validate()`, so both entry points enforce the committee-controlled feature gate consistently. More generally, audit all `nativecontract/*Processor.java` classes against their `actuator/*Actuator.java` counterparts for parity of feature-flag/committee-switch checks.

### Proof of Concept
1. Committee has `supportUnfreezeDelay` disabled (default/initial state, or explicitly turned off via proposal).
2. A regular transaction submitting `WithdrawExpireUnfreezeContract` is rejected: [1](#0-0) 
3. A user instead deploys/calls a smart contract that triggers the TVM native `withdrawExpireUnfreeze` opcode path, which routes to `WithdrawExpireUnfreezeProcessor.validate()`/`execute()` — this path performs no `supportUnfreezeDelay` check and successfully withdraws the matured unfrozen balance: [3](#0-2) 
4. The withdrawal succeeds via TVM despite being blocked at the actuator layer, demonstrating the same control-bypass inconsistency described in the reference report.

    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");

      logger.debug(e.getMessage(), e);

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
