The guard in `submit_promise_resume_data` is broken. Here is the precise trace:

**First call** with a given `data_id` where a `PromiseYield` receipt exists: [1](#0-0) 

- `has_promise_yield_receipt` → `true` (receipt key exists in trie)
- `has_promise_yield_status` → `true` (status key exists, value = `Yielded`)
- `create_promise_resume_receipt` is called → first `PromiseResume` receipt emitted
- `set_promise_yield_status` overwrites the status key with `ResumeInitiated`

**Second call** with the same `data_id` in the same function call execution:

- `has_promise_yield_receipt` → **still `true`** — the receipt is never removed from the trie by `submit_promise_resume_data`
- `has_promise_yield_status` → **still `true`** — `has_promise_yield_status` only checks key *existence*, not the value [2](#0-1) 

The key `TrieKey::PromiseYieldStatus { receiver_id, data_id }` still exists (now holding `ResumeInitiated`), so `contains_key` returns `true` again. The guard passes, and a **second `PromiseResume` receipt is created** for the same `data_id`.

The fix would require reading the actual status value (via `get_promise_yield_status`) and only proceeding when it equals `Yielded`, not merely checking key existence.

---

**On the consensus divergence claim specifically:** Both `PromiseResume` receipts are emitted as output of the same deterministic execution, so all honest nodes produce the same two receipts. There is no node-level divergence in receipt *creation*. The downstream impact when those two receipts are *processed* depends on how the runtime handles a second `PromiseResume` for an already-resumed `data_id` — which could be a `StorageInconsistentState` or a silent no-op, but it would be uniform across all nodes since receipt processing order is also deterministic.

### Title
Double `PromiseResume` Receipt Creation via Existence-Only Guard in `submit_promise_resume_data` — (`runtime/runtime/src/ext.rs`)

### Summary
`submit_promise_resume_data` guards against duplicate resume by checking whether a `PromiseYieldStatus` key *exists* in the trie, but does not check its *value*. After the first call sets the status to `ResumeInitiated`, the key still exists, so a second call with the same `data_id` passes the guard and emits a second `PromiseResume` receipt.

### Finding Description
In `RuntimeExt::submit_promise_resume_data` (`runtime/runtime/src/ext.rs`, lines 402–426), the duplicate-resume guard is:

```rust
if has_yield_receipt_in_state || has_yield_status_in_state {
    self.receipt_manager.create_promise_resume_receipt(data_id, data);
    set_promise_yield_status(..., PromiseYieldStatus::ResumeInitiated);
    return Ok(true);
}
```

`has_promise_yield_status` calls `trie.contains_key(...)` — it returns `true` for any status value, including `ResumeInitiated`. After the first call, the status key is overwritten to `ResumeInitiated` but not removed. The `PromiseYieldReceipt` key is also never removed by this function. Both checks therefore return `true` on the second call, and a second `PromiseResume` receipt is unconditionally created. [3](#0-2) 

### Impact Explanation
Two `PromiseResume` receipts for the same `data_id` are emitted. When processed, the yield callback is triggered twice for the same yield point. If the callback handles funds or state transitions, this constitutes **contract execution flow breakage** and potential **unauthorized double execution** of the callback, which can lead to fund loss or state corruption depending on the callback's logic.

### Likelihood Explanation
Any deployed contract can call `promise_yield_resume` (host function `promise_yield_resume`) twice with the same `data_id` in a single function call. No privileged role is required. The attacker only needs to deploy a contract and submit a transaction — a fully unprivileged path.

### Recommendation
Replace the existence check with a value check. Use `get_promise_yield_status` and only proceed if the returned value is `PromiseYieldStatus::Yielded`:

```rust
let status = get_promise_yield_status(self.trie_update, &self.account_id, data_id)
    .map_err(wrap_storage_error)?;
let is_resumable = status == Some(PromiseYieldStatus::Yielded)
    || has_promise_yield_receipt(self.trie_update, self.account_id.clone(), data_id)
        .map_err(wrap_storage_error)?;
if is_resumable { ... }
```

This ensures that once `ResumeInitiated` is written, subsequent calls return `false` without creating additional receipts.

### Proof of Concept
1. Deploy a contract with a method that:
   - Calls `promise_yield_create` to obtain a `data_id`
   - Calls `promise_yield_resume(data_id, payload1)` → returns `1`
   - Calls `promise_yield_resume(data_id, payload2)` again → also returns `1` (bug: should return `0`)
2. Apply the resulting receipts and observe that two `PromiseResume` receipts are present in the output for the same `data_id`.
3. Observe the yield callback is invoked twice. [4](#0-3)
