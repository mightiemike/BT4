### Title
Legacy TRC10 exchange (bancor-relay) actuators can silently overflow/underflow the `Math.pow`-based fixed-point calculation, corrupting exchange balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The `FixedPointMath.pow` bug pattern (an unsafe intermediate multiplication/exponentiation in fixed-point math that silently overflows and yields wrong results instead of reverting) has a direct analog in java-tron's legacy Bancor-relay exchange math used by `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`. These actuators are reachable by any address via a broadcast transaction (`ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) and, when the hardened path is not used, perform the core supply/exchange math with raw `double` (IEEE-754) arithmetic via `Maths.pow`/`StrictMathWrapper.pow`, with no overflow or range checks, silently producing wrong results instead of failing.

### Finding Description
`ExchangeCapsule.transaction` selects between a hardened processor (`SafeExchangeProcessor`, using `BigDecimal` and `StrictMathWrapper.addExact`/`subtractExact` with `ArithmeticException` on overflow) and the legacy `ExchangeProcessor`, which performs the Bancor-formula exponentiation entirely with unchecked `double` math: [1](#0-0) 

```java
private long exchangeToSupply(long balance, long quant) {
  ...
  double issuedSupply = -supply * (1.0
      - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
  ...
}
private long exchangeFromSupply(long balance, long supplyQuant) {
  ...
  double exchangeBalance = balance
      * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
  ...
}
``` [2](#0-1) 

Just as `FixedPointMath.pow` computes `y*ln(x)` with an unsafe typecast/multiplication that can silently overflow before being fed to `exp`, this code computes `base ** 2000.0` (and `base ** 0.0005`) with raw `double` exponentiation and no bounds/overflow checking. `double` arithmetic can silently produce `Infinity`, `NaN`, or severely rounded results for extreme ratios of `quant`/`balance`, and the result is then narrowed with a plain `(long)` cast: [3](#0-2) 
`(long) Double.NaN == 0`, `(long) Double.POSITIVE_INFINITY == Long.MAX_VALUE`, and intermediate precision loss in `double` can flip results wildly compared to the mathematically correct fixed-point value — mirroring the reported bug class where `y*ln(x)` overflow silently yields `exp(0)=1e18` instead of a huge value.

This legacy path is still selected whenever `allowHardenExchangeCalculation()` is false (default off until enabled by a chain proposal) as gated in `AbstractExchangeActuator.allowHarden()`: [4](#0-3) 
and it's invoked directly from `ExchangeTransactionActuator.execute`/`doValidate`: [5](#0-4) 
and similarly from `ExchangeCapsule.transaction` invoked by `ExchangeInjectActuator`/`ExchangeWithdrawActuator` code paths that construct `new ExchangeProcessor(supply, useStrictMath)` when `hardenedCalc` is false: [1](#0-0) 

The developers themselves recognized correctness issues in this exact code — the presence of `SafeExchangeProcessor`, `allowHardenExchangeCalculation`, and dedicated overflow tests (`testHardenedOverflowDetection`, `testStrictMath` showing `anotherTokenQuant != result` between hardened and legacy paths) is strong internal evidence that the legacy `double`-based `pow` computation is known to diverge/overflow silently: [6](#0-5) 

### Impact Explanation
When the hardened flag is disabled (which is the historical/default behavior before the proposal is activated on a given network), any user broadcasting `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transactions against a TRC10 Bancor-relay exchange pair drives balances through `ExchangeProcessor`'s unchecked `double` power computation. Extreme but attacker-controllable ratios of `quant` to `balance` (e.g., very large injection/withdrawal relative to a thin pool, or repeated small operations that shift the ratio toward the edge of `double` precision) can cause the `pow` result to silently collapse to `0`/`1`/`Infinity`/`NaN`, producing an `anotherTokenQuant` that is wildly inconsistent with the correct Bancor formula. Downstream, `exchangeCapsule.setBalance(...)` persists these corrupted balances, and the actuator moves real TRX/TRC10 asset balances (`accountCapsule.setBalance`, `reduceAssetAmountV2`/`addAssetAmountV2`) based on this bogus quantity — i.e., an attacker could extract disproportionate value from an exchange pool or corrupt the pool's balances, an asset/accounting corruption analogous to the reported high-severity bug.

### Likelihood Explanation
Reachable by any unprivileged account via a normal broadcast transaction — no special permission is needed to call `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` against any existing TRC10 exchange pair. Exploitability is bounded by whether `allowHardenExchangeCalculation()` is active on the target network (a chain-committee-controlled proposal); on any deployment where this proposal has not been activated, the legacy unchecked-`double` path is live. TRC10 exchanges (Bancor-relay AMM) are a legacy, low-traffic feature, which somewhat reduces real-world exploitation incentive, but the code path remains present and reachable.

### Recommendation
1. Make `allowHardenExchangeCalculation()` (routing to `SafeExchangeProcessor`) the mandatory, non-optional path for all exchange actuators, removing the legacy `ExchangeProcessor` double-based computation entirely, or gate it behind strict range/overflow validation before use.
2. In any remaining `double`-based computation, explicitly check for `Double.isNaN`/`Double.isInfinite`/out-of-range results after `Maths.pow` and reject the transaction (throw `ArithmeticException`/`ContractValidateException`) rather than silently truncating via `(long)` cast.
3. Extend `SafeExchangeProcessor`'s `BigDecimal`-based approach (already reviewed for overflow via `StrictMathWrapper.addExact`) to fully replace `ExchangeProcessor`, and add fuzz/property tests comparing extreme ratio inputs between the two processors to detect divergence, similar to the existing `testStrictMath` test that already documents `anotherTokenQuant != result`.

### Proof of Concept
Conceptually mirroring the reported Solidity PoC: choose `firstTokenBalance`/`secondTokenBalance` and `tokenQuant` such that the ratio `quant/newBalance` fed into `Maths.pow(base, 2000.0, useStrictMath)` in `exchangeFromSupply` produces a `double` result at or near `Infinity`/`NaN` (e.g., `base` very close to a value where `base^2000` overflows `double`'s ~1.8e308 range, or `base` computed with catastrophic cancellation from `BigDecimal`→`double` narrowing). Broadcasting the corresponding `ExchangeTransactionContract` on a network where `allowHardenExchangeCalculation()` is false would drive `exchangeCapsule.transaction(...)` through `ExchangeProcessor.exchangeFromSupply`, producing an `anotherTokenQuant` inconsistent with the true Bancor-formula output — directly analogous to the reported `test_pow()` case where `y*ln(x)` overflow causes `2.0 ** y` to incorrectly resolve to `1e18`. The existing repository test `testStrictMath` in `ExchangeProcessorTest.java` already empirically demonstrates that legacy (`useStrictMath=false`) and strict (`useStrictMath=true`)/hardened results diverge (`assertNotEquals(anotherTokenQuant, result)`), confirming that the unhardened `pow`-based path is numerically unreliable: [7](#0-6)
