### Title
Stale Governance Parameter Validation Allows Non-Monotonic `MAX_DELEGATE_LOCK_PERIOD` Regression - (File: `framework/src/main/java/org/tron/core/consensus/ProposalService.java`)

### Summary
Committee proposals in java-tron are validated once against the current chain state at creation time in `ProposalUtil.validator()`, but the validated value is applied unconditionally at execution time (during maintenance, potentially days later) in `ProposalService.process()` without re-checking that the underlying condition still holds. For `MAX_DELEGATE_LOCK_PERIOD` this allows a stale, lower value to silently override a more recent, validly-approved higher value, breaking the monotonic-increase invariant the validator itself enforces.

### Finding Description
`ProposalUtil.validator()` enforces, at proposal-creation time only, that a new `MAX_DELEGATE_LOCK_PERIOD` value must be strictly greater than the value currently stored in `DynamicPropertiesStore`: [1](#0-0) 

This check reads `dynamicPropertiesStore.getMaxDelegateLockPeriod()` at the moment the proposal is submitted via `ProposalCreateActuator.validate()`: [2](#0-1) 

However, the proposal is not executed immediately. It is only executed by `ProposalController.processProposal()` once it accumulates approvals from ≥70% of active witnesses and reaches its `expirationTime`, which can be up to `proposalExpireTime` (default 3 days, i.e. up to ~12 six-hour maintenance cycles) after creation: [3](#0-2) 

When `processProposal()` finally applies the value, `ProposalService.process()` performs no re-validation — it unconditionally overwrites the store with the value captured at creation time: [4](#0-3) 

This is the direct analog of the reported bug class: a governance parameter (`success_amount`/config value cached at proposal-creation time) is validated against stale state and executed later without confirming the invariant still holds against the *current* state, unlike other proposal types in the same switch statement (`REMOVE_THE_POWER_OF_THE_GR`, `ALLOW_MULTI_SIGN`, `ALLOW_ADAPTIVE_ENERGY`, `ALLOW_MARKET_TRANSACTION`, `ALLOW_CANCEL_ALL_UNFREEZE_V2`) which do add an idempotency/state guard before applying: [5](#0-4) [6](#0-5) 

`MAX_DELEGATE_LOCK_PERIOD` has no such guard.

### Impact Explanation
`MAX_DELEGATE_LOCK_PERIOD` governs the maximum resource-delegation lock period accepted by `DelegateResourceContract` logic tied to `UNFREEZE_DELAY_DAYS`/lock-period features. Because the applied value at execution time is never re-checked against the value that may have been set by a more recent, validly-approved proposal in between, a proposal created early (when the cap was low) but confirmed/executed later can retroactively decrease the cap below a value the committee has since deliberately raised via a subsequent proposal. This is a concrete state-divergence/invalid-state issue: the on-chain parameter no longer reflects the latest validly-approved governance decision, and this happens deterministically through the normal proposal lifecycle, not a theoretical edge case.

### Likelihood Explanation
Exploitation only requires the normal governance mechanics already present in the codebase: any witness (owner of a witness account, per `chainBaseManager.getWitnessStore().has(ownerAddress)` in `ProposalCreateActuator.validate()`) can create a proposal, and overlapping/competing proposals awaiting approval across maintenance cycles are an expected occurrence given `proposalExpireTime` defaults to 3 days. No additional privilege beyond the standard witness/committee proposal flow is required — this makes the scenario realistically reachable, not merely theoretical.

### Recommendation
Re-validate parameter-specific invariants inside `ProposalService.process()` immediately before applying the value (mirroring the pattern already used for `REMOVE_THE_POWER_OF_THE_GR`/`ALLOW_MULTI_SIGN`/etc.), e.g. for `MAX_DELEGATE_LOCK_PERIOD`:
```java
case MAX_DELEGATE_LOCK_PERIOD: {
  long current = manager.getDynamicPropertiesStore().getMaxDelegateLockPeriod();
  if (entry.getValue() > current) {
    manager.getDynamicPropertiesStore().saveMaxDelegateLockPeriod(entry.getValue());
  }
  break;
}
```
More generally, adopt a governance-state versioning approach (as recommended in the analogous TON report) or systematically add execution-time re-validation for every `ProposalType` whose creation-time validity depends on other mutable `DynamicPropertiesStore` fields, so stale proposals cannot silently regress previously-approved, more restrictive/permissive governance decisions.

### Proof of Concept
1. Assume `MAX_DELEGATE_LOCK_PERIOD` current value = 50 (in blocks).
2. Witness creates Proposal A with `MAX_DELEGATE_LOCK_PERIOD = 100`. Validator passes (`100 > 50`). Proposal A is stored `PENDING` with `expirationTime` up to 3 days out (`ProposalCreateActuator.execute()`).
3. Before A gets 70% witness approval, another witness creates Proposal B with `MAX_DELEGATE_LOCK_PERIOD = 200`. Validator passes (`200 > 50`). B quickly gets 70% approval and is processed at the next maintenance cycle by `ProposalController.processProposal()` → `ProposalService.process()`, setting the stored value to 200.
4. Later, Proposal A also reaches 70% approval and its `expirationTime`. `ProposalController.processProposal()` calls `ProposalService.process()`, which executes the `MAX_DELEGATE_LOCK_PERIOD` case unconditionally (`ProposalService.java:355-358`), overwriting the store back down to 100 — silently reverting the committee's more recent, validly-approved decision (200) without any check against the current on-chain value.

  public void processProposals() {
    long latestProposalNum = manager.getDynamicPropertiesStore().getLatestProposalNum();
    if (latestProposalNum == 0) {
      logger.info("latestProposalNum is 0, return");
      return;
    }

    long proposalNum = latestProposalNum;

    ProposalCapsule proposalCapsule = null;

    while (proposalNum > 0) {
      try {
        proposalCapsule = manager.getProposalStore()
            .get(ProposalCapsule.calculateDbKey(proposalNum));
      } catch (Exception ex) {
        logger.error("", ex);
        proposalNum--;
        continue;
      }

      if (proposalCapsule.hasProcessed()) {
        logger
            .info("Proposal has processed, id:[{}], skip it and before it",
                proposalCapsule.getID());
        //proposals with number less than this one, have been processed before
        break;
      }

      if (proposalCapsule.hasCanceled()) {
        logger.info("Proposal has canceled, id:[{}], skip it", proposalCapsule.getID());
        proposalNum--;
        continue;
      }

      long currentTime = manager.getDynamicPropertiesStore().getNextMaintenanceTime();
      if (proposalCapsule.hasExpired(currentTime)) {
        processProposal(proposalCapsule);
        proposalNum--;
        continue;
      }

      proposalNum--;
      logger.info("Proposal has not expired, id:[{}], skip it", proposalCapsule.getID());
    }
    logger.info("Processing proposals done, oldest proposal[{}]", proposalNum);
  }
