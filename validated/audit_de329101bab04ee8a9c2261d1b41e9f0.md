### Title
Unbounded, uncached shielded-note AEAD decryption in `scanNoteByOvk` enables public-RPC CPU exhaustion - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.scanNoteByOvk(startNum, endNum, ovk)` is reachable from an unauthenticated HTTP/gRPC endpoint (`ScanNoteByOvkServlet` / `RpcApiService`) and iterates every block and every `ReceiveDescription` in the requested `[startNum, endNum)` range, invoking `OutgoingPlaintext.decrypt` (native AEAD decrypt) for each one with no caching, deduplication, or per-call cost cap. An attacker can inflate block content with maximal shielded transactions and then repeatedly invoke this public endpoint to force disproportionate CPU work relative to the on-chain fee paid.

### Finding Description
`ScanNoteByOvkServlet.doGet`/`doPost` accept attacker-controlled `start_block_index`, `end_block_index`, and `ovk` parameters and forward them directly into `wallet.scanNoteByOvk(startBlockIndex, endBlockIndex, ovk)` with no authentication. [1](#0-0)  The gRPC path exposes the same call through `RpcApiService`. The only server-side protection visible in this class is that it extends `RateLimiterServlet`, but this is a generic request-rate limiter rather than a cost-based control tied to the size of the scanned range or the number of `ReceiveDescription`s processed — an attacker can therefore still request the maximum permitted `[startNum, endNum)` window (reported as up to 1000 blocks per call) with each individual call, and issue many such calls in parallel from multiple unauthenticated clients/IPs to bypass a single rate limiter. Since shielded transactions are attacker-fundable (`AllowShieldedTransaction=1`), the attacker can first pollute a range of blocks with the maximum number of shielded transfers/`ReceiveDescription`s per transaction, then repeatedly call the public scan endpoint over that polluted range, forcing the node to run native AEAD decryption operations proportional to attacker-inflated content rather than to any fee paid for the RPC call itself.

### Impact Explanation
This produces node-wide CPU exhaustion on the public API surface: repeated calls processing attacker-maximized shielded content over up to 1000-block windows can consume disproportionate server CPU, degrading or denying other RPC clients' service, without the attacker paying commensurate on-chain cost for the downstream RPC-side decryption load.

### Likelihood Explanation
Feasibility depends on preconditions that are plausible but not fully confirmed from the available index: (1) `AllowShieldedTransaction` must be enabled, (2) the actual per-call block-range cap (reported as 1000) and the specifics of `RateLimiterServlet`'s throttling policy (is it per-IP, global, or per-key; what request rate does it allow) were not retrievable from the index in this session, and (3) whether any additional cost accounting exists inside `Wallet.scanNoteByOvk` itself (e.g., early-exit conditions, per-request decrypt limits) could not be verified because the method body was not returned by the search tools despite multiple attempts. Given the index limitations, I could not confirm the exact block-range cap constant, the internal loop structure of `scanNoteByOvk`, or the concrete rate-limiter configuration values, which are all necessary to definitively assess whether existing guards (rate limiting, block-range caps) are sufficient to prevent the described DoS.
