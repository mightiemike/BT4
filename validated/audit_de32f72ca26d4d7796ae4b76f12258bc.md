## Finding Confirmed

### Title
`StateStorageUsage` becomes non-deterministic between sharded and sequential execution because `CrossShardStateView::get_usage()` always discards the base view's real usage — ([File: aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_state_view.rs])

### Summary
The sharded block executor's `TStateView` implementation for `CrossShardStateView` hard-codes `get_usage()` to return `StateStorageUsage::new_untracked()` instead of delegating to the underlying, DB-backed `base_view`. Every VM invocation inside the sharded executor (both per-shard sub-blocks and the "global" round) is executed against this view (wrapped further by `AggregatorOverriddenStateView`), so any Move code that reads storage usage during sharded execution silently gets `Untracked` (`items=0, bytes=0`) instead of the true accumulated usage that the same block would see under the sequential executor.

### Finding Description
`CrossShardStateView` is used as the base state view for `AptosVMBlockExecutorWrapper::execute_block` for both shard sub-blocks and the global round: [1](#0-0) 

Its `get_usage()` implementation ignores `base_view` entirely: [2](#0-1) 

This is the exact resolver ultimately reached by the Move-level native `get_state_storage_usage_only_at_epoch_beginning`: [3](#0-2) 

The native's own doc comment warns that the returned value is only correct/deterministic "if called from the first transaction of the block because the execution layer guarantees a fresh state view then": [4](#0-3) 

`0x1::state_storage::on_new_block` calls this native exactly once per epoch change (triggered by the block prologue, i.e. the first transaction of the epoch-boundary block), and persists the result into the `StateStorageUsage` resource that is committed to the ledger and later read by `storage_gas` to recompute gas parameters: [5](#0-4) 

Under sequential (non-sharded) execution, this native reads the real DB-backed `StateView::get_usage()`, producing a `Tracked{items, bytes}` value reflecting actual storage. Under sharded execution, because the state view chain always terminates in `CrossShardStateView::get_usage() -> Untracked`, the same call always yields `items=0, bytes=0`, regardless of shard partitioning or the real write set. This means the `StateStorageUsage` resource value written to the ledger at epoch boundaries is a function of *which executor implementation ran the block*, not of the block's actual content — the exact "committed value differs depending on partitioning rather than the actual write set" scenario described in the question.

### Impact Explanation
`StateStorageUsage.usage` is committed on-chain state (a `write_resource` change under `0x1::state_storage::StateStorageUsage`, visible in transaction outputs/API goldens), and it feeds `storage_gas::on_reconfig`'s gas-parameter recalculation. If one execution path (sharded) and another (sequential) can be used to independently produce the "canonical" output for the same block/version — e.g., during replay, state sync verification, or a validator running with sharded execution enabled versus one without — they will compute different write sets for this resource, hence different transaction/state roots and diverging proof material for the same ledger version. This is exactly a hard-fork-only divergence between execution engines that should be output-identical, corrupting the deterministic proof binding for the affected version.

### Likelihood Explanation
The trigger condition (epoch-boundary block, i.e., the block whose first transaction changes `epoch`) is not attacker-controlled in timing, but it is a deterministic, always-occurring condition on every epoch change, and every transaction present in that block is subject to this divergence path if the block is executed by the sharded executor. No malicious input is required — this is a structural determinism bug in `CrossShardStateView`, present whenever the sharded execution path (used in production tooling / benchmark and potentially any future validator use of sharded execution) processes an epoch-changing block.

### Recommendation
Fix `CrossShardStateView::get_usage()` to delegate to `self.base_view.get_usage()` instead of hard-coding `Untracked`, ensuring the storage-usage view seen by the VM is identical regardless of shard partitioning. Add a differential test that executes the same block (including an epoch-boundary/on_new_block transaction) through both the sharded and sequential executors and asserts identical `StateStorageUsage`/write-set outputs at the same version, as suggested in the proof idea.

### Proof of Concept
1. Construct a block whose first transaction crosses an epoch boundary (triggers `state_storage::on_new_block`), with a state that has non-trivial usage (`Tracked{items>0, bytes>0}`).
2. Execute the block via the sequential executor: `state_storage::on_new_block` will store the real `Tracked` usage in the `StateStorageUsage` resource.
3. Execute the identical block via `ShardedBlockExecutor` (any shard count, or via the global executor path) using `CrossShardStateView`: `get_usage()` always returns `Untracked`, so `get_state_storage_usage_only_at_epoch_beginning()` returns `items=0, bytes=0`, and the persisted `StateStorageUsage` resource differs from step 2's result.
4. Compare the two committed `StateStorageUsage` write-set values / resulting state roots at the same version — they diverge, confirming that partitioning/executor choice (not the actual write set) determines the committed value. [2](#0-1) [6](#0-5)

fn native_get_usage(
    context: &mut SafeNativeContext,
    _ty_args: &[Type],
    _args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    assert!(_ty_args.is_empty());
    assert!(_args.is_empty());

    context.charge(STATE_STORAGE_GET_USAGE_BASE_COST)?;

    let ctx = context.extensions().get::<NativeStateStorageContext>();
    let usage = ctx.resolver.get_usage().map_err(|err| {
        PartialVMError::new(StatusCode::VM_EXTENSION_ERROR)
            .with_message(format!("Failed to get state storage usage: {}", err))
    })?;

    Ok(smallvec![Value::struct_(Struct::pack(vec![
        Value::u64(usage.items() as u64),
        Value::u64(usage.bytes() as u64),
    ]))])
}
