Analysis complete. I found a genuine analog to the external bug's core pattern — an integrity-check function that decodes/validates one part of a committed artifact while silently skipping validation of another, security-critical part.

### Title
`TransactionOutput::ensure_match_transaction_info` never validates the state/hot-state/position checkpoint root hashes, letting replay-verify accept a divergent committed state root as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole function used by all replay/verification tooling (`db-tool replay-on-archive`, `aptos-debugger`, and the `aptos move replay`/simulate CLI paths) to confirm that a locally re-executed transaction reproduces the transaction result that was actually committed to the chain (`TransactionInfo`). It checks status, gas, the write-set hash (`state_change_hash`) and the event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the actual global Jellyfish Merkle state root at that version.

### Finding Description
`TransactionInfoV0`/`TransactionInfoV1` carry `state_checkpoint_hash` (and, when features are on, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) as the periodically-committed Sparse/Jellyfish Merkle root of the *entire* global state as of that transaction. [1](#0-0) [2](#0-1) 

`ensure_match_transaction_info` verifies status, gas, `state_change_hash` (write-set hash, which only covers the local write set of the one transaction) and `event_root_hash`, but the comment explicitly documents that it stops there and never checks the checkpoint hashes, calling out that this defeats replay-verify's ability to catch a divergent "trading-native" position state root: [3](#0-2) 

Crucially, `state_change_hash` is a hash of the write set produced by *this* transaction, not of the resulting global state tree. A single write op can be identical while the actual Merkle tree constructed from all accumulated state (e.g., due to a bug in JMT node placement, hotness bucket handling, or the new `position_state_checkpoint_hash`/"trading-native" state root logic) diverges from what was committed. Because gas/status/event/write-set hash can all match while the state root differs, this class of bug is invisible to this comparator.

This function is exactly the safety-net comparator used by:
- `storage/db-tool/src/replay_on_archive.rs`, comparing re-executed output against `expected_txn_infos` pulled from the already-committed local DB, per-chunk, and treating an `Ok(())` result as "no divergence": [4](#0-3) 
- `aptos-move/cli/src/commands.rs`, used both for user transactions and system transactions when replaying against a fetched `TransactionInfo`: [5](#0-4) [6](#0-5) 

By contrast, the *live* commit path (`DoStateCheckpoint`/`DoLedgerUpdate`) does independently recompute and cross-check `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` against freshly computed hashes when driving consensus/chunk execution: [7](#0-6) [8](#0-7) 

So the checkpoint-hash cross-check exists and is enforced during live chunk-execution/state-sync, but is missing specifically from the offline replay/debugger comparator that operators and tooling rely on to detect nondeterminism/state divergence bugs against already-committed archival history.

### Impact Explanation
This is a "hard-fork-only divergence during commit, replay ... proof verification" scenario per the state-integrity gate: `replay_on_archive` and the CLI replay/debugger tools are the primary mechanisms used to detect nondeterminism bugs (e.g. VM upgrade regressions, JMT/hot-state bugs, position-state-root bugs) before/around a hard fork by re-executing archived history and diffing against the already-committed `TransactionInfo`. Because `ensure_match_transaction_info` never compares the checkpoint root hashes, a transaction whose write set, events, gas, and status happen to match but whose actual state root diverges (the class of bug this comparator exists to catch) will be reported as a clean, verified replay. This silently masks state-root divergence that the state-integrity gate explicitly calls out as high/critical (undetected wrong state root accepted as "verified"), directly undermining confidence in replay-verify results used to certify archival/backup data and pre-fork audits.

### Likelihood Explanation
No privileged access or attacker interaction is required to trigger the gap — it is a structural omission in the comparator itself, hit on every single invocation of replay/verify tooling. It only manifests when an actual state-root-affecting bug/regression exists elsewhere (e.g., in JMT construction, hot-state promotion, or trading-native/position-state logic) but does not affect write-set bytes, events, gas, or status — a realistic class of subtle nondeterminism bugs that replay-verify is specifically built to catch. The bug is 100% deterministic and reproducible in code review (no need for a live exploit), and the TODO comment already documents the developers' own awareness of the exact gap (checkpoint hash exclusion, tied to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally recomputed output and the expected `TransactionInfo`, when these are present/expected. In particular, when the checkpoint hash is expected to have been produced at that version (i.e., a checkpoint boundary), require an exact match rather than skipping unconditionally; gate the position/hot-state checks on the relevant feature flags to avoid false positives, but do not skip them once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled.

### Proof of Concept
Code-level trace (no live network needed to demonstrate the logic gap):
1. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes a chunk of archived transactions and calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` on each output, treating `Ok(())` as verified. [9](#0-8) 
2. `ensure_match_transaction_info` only asserts equality on `status`, `gas_used`, `state_change_hash` (hash of the write set) and `event_root_hash`; it never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. [10](#0-9) 
3. Construct (or imagine) a re-executed `TransactionOutput` whose write set/events/gas/status are byte-identical to the archived transaction's outputs, but whose derived global Merkle state root (as would be computed by `DoStateCheckpoint`) differs from the `state_checkpoint_hash` stored in the archived `TransactionInfo` — e.g., due to a nondeterministic hot-state promotion or trading-native state-root computation bug elsewhere in the stack. `ensure_match_transaction_info` returns `Ok(())` for this output, and `replay_on_archive` reports the chunk as fully verified with no error, even though the state roots genuinely diverge.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
