### Title
OAuth callback shop-parameter confusion: HMAC-validated `shop` differs from the `shop` used for token exchange and session creation - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
In the OAuth `callback` handler, a duplicated `shop` query parameter is resolved inconsistently: the value used for **HMAC/state validation** is the *last* occurrence of `shop` (via `Object.fromEntries`), while the value used to **build the access-token exchange URL and construct the resulting session** is the *first* occurrence (via `URLSearchParams.get()`). This is the same bug class as the Arrakis M‑3 finding: a security check performed on an aggregated/collapsed representation of grouped inputs does not protect the individual raw value that is actually acted upon afterward.

### Finding Description
`callback()` in [1](#0-0)  extracts `shop` for logging via `query.get('shop')!`, which returns the **first** value if `shop` appears more than once in the querystring.

For HMAC/state validation, the code instead builds `authQuery` via: [2](#0-1) 
`Object.fromEntries(query.entries())` collapses duplicate keys by keeping the **last** occurrence, so `authQuery.shop` (the value actually hashed and compared against the incoming `hmac` in `validQuery`) can differ from the `shop` obtained by `query.get('shop')`.

Later, the code re-reads `query.get('shop')!` again (the **first** value, not the HMAC-validated `authQuery.shop`) to build the token-exchange target and to create the session: [3](#0-2) 

So if an attacker crafts a callback URL containing two `shop` params — the legitimate, correctly-signed shop value as the *second* occurrence (so it is what gets HMAC-validated) and an attacker-chosen shop as the *first* occurrence — HMAC validation in `validQuery`/`validateHmac` succeeds (because it operates on the last-value-collapsed `authQuery`, unchanged from what Shopify actually signed), but `cleanShop` and the session's `shop` field are derived from the *first*, attacker-controlled value: [4](#0-3) 
Note that this "normalizeQuery" duplicate-parameter hardening (which explicitly rejects repeated `shop`/`hmac`/`timestamp`/`signature`, per the CHANGELOG's `857c598` app-proxy hardening) is only applied when `signator === 'appProxy'`; the `admin` signator path used by the OAuth callback has no such rejection of duplicate `shop`/`hmac`/`timestamp` values, so this inconsistency is not covered by the existing hardening.

### Impact Explanation
This breaks the intended invariant that "the shop identity cryptographically validated by Shopify's HMAC is the shop identity the app acts on." The access-token POST request is sent to `https://${cleanShop}/admin/oauth/access_token` using the attacker-controlled first `shop` value, and the resulting `Session` object is created with `shop: cleanShop` — an unauthenticated value — while the state-cookie/HMAC checks were actually performed against a different (legitimately signed) shop value in `authQuery`. Whether this is fully exploitable to install/associate a session cross-tenant depends on Shopify's own server-side binding between the OAuth `code` and the shop/redirect URI (an external system this report cannot verify), which limits confirmed impact to a shop-identity confusion in the app's own logging/session-shop bookkeeping unless Shopify's token endpoint also fails to bind the code strictly to the original shop.

### Likelihood Explanation
Requires an attacker to get their crafted duplicate-`shop` callback URL invoked (e.g., by luring a merchant to click a manipulated OAuth callback link, or via an open-redirect/CSRF-style delivery of the callback URL) while a valid state cookie is present for that browser session. It does not require a leaked secret or MITM, and the request path is an unauthenticated `GET /auth/callback` endpoint, so likelihood is plausible but conditioned on how strictly Shopify's own access-token endpoint validates `code` against `shop`, which cannot be confirmed from this codebase alone.

### Recommendation
Resolve `shop` (and other security-relevant OAuth query fields: `hmac`, `state`, `timestamp`, `code`) from a single, consistently-normalized parse of the querystring, and reject the request outright if any of these parameters appear more than once — mirroring the `APP_PROXY_SINGLE_VALUE_PARAMS` duplicate-rejection already implemented for the `appProxy` signator in `normalizeQuery` ( [5](#0-4) ) — for the `admin` signator path as well. Ensure the same resolved `shop` value is used for HMAC validation, token exchange, and session creation in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`.

### Proof of Concept
1. Attacker constructs: `GET /auth/callback?shop=evilshop.myshopify.com&code=<code>&state=<state>&timestamp=<ts>&shop=victim-shop.myshopify.com&hmac=<hmac signed by Shopify for the victim-shop query>` (attacker appends their own `shop` value first, before the legitimately-Shopify-signed parameters).
2. `query.get('shop')` (used for `cleanShop`/session creation, [6](#0-5) ) returns `evilshop.myshopify.com` (first occurrence).
3. `Object.fromEntries(query.entries())` (used for HMAC validation, [2](#0-1) ) resolves `shop` to `victim-shop.myshopify.com` (last occurrence) — matching the value Shopify actually signed, so HMAC validation passes.
4. The subsequent token exchange request and session creation use `cleanShop = "evilshop.myshopify.com"` ( [3](#0-2) ) despite the HMAC having validated a different shop value.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
