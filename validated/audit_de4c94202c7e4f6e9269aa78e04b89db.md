Based on my investigation, I found a genuine local-code integrity issue in the native-position write-set replay path.

## Title
Native-position write-set data is dropped on serialization, causing `replay_position_after_snapshot` to silently skip position updates on restart — ([File: storage/aptosdb/src/db/aptosdb_native_position.rs])

## Summary
`WriteSet`'s `extensions` field (which carries the `Extension::NativePosition` bucket used to update the "position" Merkle/state structure) is explicitly marked `#[serde(skip)]` on both `WriteSetV0` and is documented as being dropped from the on-disk `WriteSet` format. [1](#0-0)  Yet the restart/restore replay path `replay_position_after_snapshot` reconstructs pending position updates purely by reading persisted write sets back from `write_set_db()` and calling `write_set.native_position_iter()` on the deserialized result. [2](#0-1) 

## Finding Description
The `Extension::NativePosition` bucket is populated once per `WriteSet` at VM-output materialization time via `add_native_positions` [3](#0-2) , and is read back via `native_position_iter()` [4](#0-3) . However, both `WriteSetV0.extensions` and `WriteSetV0.hotness` are annotated `#[serde(skip)]`, with an explicit comment stating this is "so `TransactionInfo` hashes and the on-disk `WriteSet` format are unaffected" [1](#0-0) . This means that when a `TransactionOutput`'s write set is persisted to the ledger DB via `commit_write_sets`/`put_write_set` (which calls into `WriteSet`'s `Serialize` impl through BCS) [5](#0-4) , the `NativePosition` extension is never actually written to disk.

On database restart, `replay_position_after_snapshot` is invoked whenever the persisted JMT "position" snapshot lags the overall commit progress (`snapshot_next_version <= v_overall`) [6](#0-5) . This function fetches the write sets in the gap from `write_set_db().get_write_sets(...)` — i.e., deserializes them from disk — and then iterates `write_set.native_position_iter()` to build `pending_leaf_updates` used to extend the in-memory/JMT position pipeline [2](#0-1) . Because the extension was never serialized, every deserialized write set in this gap will report `native_position_iter()` as empty, so `pending_leaf_updates` is empty and the function short-circuits at `if pending_leaf_updates.is_empty() { return Ok(()); }` [7](#0-6)  — silently skipping the replay instead of failing loudly, exactly the "unchecked side-effect, next step proceeds anyway" pattern the external report describes for `transferFrom`.

The result: the persisted position Merkle tree/state snapshot is left stale (missing all leaf updates from the un-replayed version range) while `OverallCommitProgress`/other ledger metadata reports the ledger as fully caught up to `v_overall`. Any subsequent proof, hash, or read served against the position structure at or beyond `snapshot_next_version` would then be based on stale/incorrect data relative to what the DB claims to be committed at.

## Impact Explanation
If native-position data (used for whatever proof/positioning subsystem consumes `PositionMerkleDb`/`PositionStateStore`) is silently dropped from replay after a node restart, any node that restarts (crash, planned reboot, resync) between a position-affecting commit and the next merkle snapshot checkpoint will have a divergent position Merkle root from a node that never restarted, or from the correct VM-derived state. This is a durable-state corruption of a proof-bearing structure surviving executor→storage handoff, matching the "wrong accumulator/Merkle root" and "committed state differs from correct VM result" impact classes.

## Likelihood Explanation
This triggers deterministically whenever a node restarts (or performs restore/replay) while the persisted merkle snapshot for native positions is behind `OverallCommitProgress`, which is a normal and frequent operational occurrence (not adversarial) — no privileged access or malicious behavior is required, only a restart during normal operation combined with any native-position writes in the un-persisted-snapshot version range.

## Recommendation
Persist the `Extension::NativePosition` bucket (or an equivalent side-channel) so it survives round-tripping through `write_set_db`, or replay position updates from the actual VM/transaction-output layer (not the serde-stripped, disk-deserialized `WriteSet`) so `replay_position_after_snapshot` gets a real gap-list, and add an explicit invariant check that fails loudly (instead of silently returning `Ok(())`) if it detects that replay should have found updates but found none.

## Proof of Concept
1. Execute transactions across several versions where at least one write set contains `Extension::NativePosition` entries added via `add_native_positions`.
2. Allow the block executor / checkpoint pipeline to commit these to `write_set_db` (which serializes via BCS, dropping the skipped `extensions` field) while the position merkle snapshot has not yet advanced past those versions.
3. Restart the node (or otherwise trigger `open_internal`'s restart-catchup logic) so `replay_position_after_snapshot` runs for the version gap containing those writes.
4. Observe that `write_set.native_position_iter()` on the values returned by `get_write_sets` yields no entries (since extensions were never serialized), causing `pending_leaf_updates` to be empty and the function to return early without replaying the actual position updates — leaving the persisted position structure permanently missing those updates even though `OverallCommitProgress` reports the ledger as fully committed to that version.

**Note on confidence:** I could not fully trace the non-restart ("hot path") commit flow that presumably writes `NativePositionOp` data directly into `PositionDb`/`PositionMerkleDb` at commit time (outside of `write_set_db`), since I ran out of tool budget before locating `commit_native_position` or the direct commit-time consumer of `native_position_iter()` in the block-execution/commit pipeline (only two other call sites exist: `execution/executor/src/workflow/do_state_checkpoint.rs` and the file cited above). If that hot-path writer independently and durably persists position data outside `write_set_db` (e.g., directly into `PositionDb`/`PositionMerkleDb` at original commit time, with `write_set_db` only used as an auxiliary/backup replay source), then the restart-catchup path being empty may be a harmless no-op rather than data loss, and this finding would not hold. Confirming this requires reading `execution/executor/src/workflow/do_state_checkpoint.rs` and any position-committer code path that I was unable to fetch in the time available.

    /// Commits write sets starting from `first_version` to the database.
    pub(crate) fn commit_write_sets(
        &self,
        first_version: Version,
        transaction_outputs: &[TransactionOutput],
    ) -> Result<()> {
        let _timer = OTHER_TIMERS_SECONDS.timer_with(&["commit_write_sets"]);

        let chunk_size = transaction_outputs.len() / 4 + 1;
        let batches = transaction_outputs
            .par_chunks(chunk_size)
            .enumerate()
            .map(|(chunk_idx, chunk)| {
                let mut batch = self.db().new_native_batch();
                let chunk_first_version = first_version + (chunk_idx * chunk_size) as Version;

                chunk.iter().enumerate().try_for_each(|(i, txn_out)| {
                    Self::put_write_set(
                        chunk_first_version + i as Version,
                        txn_out.write_set(),
                        &mut batch,
                    )
                })?;
                Ok(batch)
            })
            .collect::<Result<Vec<_>>>()?;
