### Title
`LiquidityCap` on `TokenConfig` is never enforced during PRC20 minting on inbound deposits - (File: `x/uexecutor/keeper/handler.go`)

### Summary
The reported sNote bug is a cap that exists in code but is trivially bypassed because it's only checked per-call, not cumulatively. Push Chain has a structurally similar (and stronger) analog: `TokenConfig.LiquidityCap` [1](#0-0)  is stored and validated as non-empty at config-write time [2](#0-1) , but it is never read or checked anywhere in the deposit/mint execution path.

### Finding Description
`depositPRC20` is the function that mints PRC20 tokens for an inbound deposit. It fetches the `TokenConfig` (which carries `LiquidityCap`) purely to resolve the PRC20 contract address, and then calls `CallPRC20Deposit` with the attacker/source-chain-supplied `amountStr` without any comparison against `tokenConfig.LiquidityCap` or the token's current minted supply: [3](#0-2) 

A repo-wide search of the keeper packages for any use of `LiquidityCap`/`liquidity_cap` returns zero matches outside of protobuf marshal/unmarshal code and tests — confirming the field is dead data from the enforcement perspective. `CallPRC20Deposit` itself (in `x/uexecutor/keeper/evm.go`) is the `DerivedEVMCall`-based mint helper and likewise contains no cap check.

### Impact Explanation
This corrupts PRC20 accounting invariants in the same conceptual category as the sNote finding: a documented, per-token maximum-supply/collateralization guarantee (`liquidity_cap`) that stakeholders and integrators rely on for risk bounding is not actually enforced by the code, so it provides zero real protection. Unlike the sNote case (where an attacker at least needs several transactions to exceed 50%), here a single inbound deposit — or any number of inbound deposits — can mint PRC20 supply for a token in unlimited excess of its configured `liquidity_cap`, with honest Universal Validators faithfully voting in the (attacker-controlled) deposit amount observed on the source chain. This is an unprivileged, externally-reachable path (deposit funds on the source-chain gateway, wait for honest UV quorum) that leads to unauthorized/uncapped PRC20 minting — squarely in the "corruption of PRC20 accounting" / "unauthorized mint" allowed-impact bucket.

### Likelihood Explanation
High. No privileged action, no validator collusion, and no protocol malfunction is required — only a legitimate large (or repeated) deposit on the source chain that is observed and voted on normally. The bug is a missing check, not a race condition, so it triggers deterministically on any deposit whose PRC20-mint total would exceed the configured cap.

### Recommendation
Track cumulative minted supply per PRC20 (or read current `totalSupply` from the PRC20 contract) and enforce `amount + currentSupply <= tokenConfig.LiquidityCap` inside `depositPRC20` (or `CallPRC20Deposit`) before issuing the `DerivedEVMCall` mint, rejecting/queuing inbounds that would exceed the cap, analogous to fixing the sNote issue by tracking cumulative withdrawals against the 50% threshold rather than checking it per call.

### Proof of Concept
1. Admin registers a `TokenConfig` for `USDC.eth` with `liquidity_cap = 1,000,000e6`.
2. Attacker deposits an amount on the source-chain gateway that, combined with prior deposits, would mint PRC20 far in excess of `1,000,000e6` (or simply a single deposit larger than the cap).
3. Honest Universal Validators observe and vote the inbound (`MsgVoteInbound`) faithfully — quorum reached — `depositPRC20` executes and calls `CallPRC20Deposit` with the full amount.
4. No check against `tokenConfig.LiquidityCap` exists in `depositPRC20` [3](#0-2)  or in `CallPRC20Deposit`, so the mint succeeds unconditionally, leaving PRC20 total supply above the declared cap.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
