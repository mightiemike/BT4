### Title
Unbounded prefix-scan + full sort in `DelegatedResourceAccountIndexStore.getIndex`/`getV2Index` allows attacker-amplified RPC/HTTP CPU-DoS - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`getIndex`/`getV2Index` perform an unbounded `prefixQuery` over all delegation-index rows for an address and then fully sort the results by timestamp on every call, with cost proportional to the number of distinct delegation partners for that address. Because `DelegateResourceContract.calcFee()` returns `0` (only bandwidth is consumed) an attacker can cheaply create a very large number of distinct delegation-index rows for one address and then repeatedly invoke the unauthenticated `wallet/getdelegatedresourceaccountindex(v2)` RPC/HTTP endpoints, and the node's request-rate limiting is a flat per-endpoint/global QPS token bucket that does not account for the O(n log n) cost of each such request.

### Finding Description
`getWithPrefix` (used by both `getIndex` at line 106-112 and `getV2Index` at line 114-116) calls `this.prefixQuery(key)` twice and then sorts each resulting list with `Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp)`: [1](#0-0) 

This is reachable from unauthenticated clients through `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`, which are exposed via gRPC (`RpcApiService`, `RpcApiServiceOnSolidity`, `RpcApiServiceOnPBFT`) and HTTP (`GetDelegatedResourceAccountIndexServlet`, and its Solidity/PBFT variants) with no address ownership or authentication requirement: [2](#0-1) [3](#0-2) 

The number of rows behind the prefix (`FROM_PREFIX`/`TO_PREFIX` or `V2_FROM_PREFIX`/`V2_TO_PREFIX` + address) is directly driven by how many distinct `DelegateResourceContract` delegations the attacker's own account has issued, since each delegation writes a new key via `delegateV2`: [4](#0-3) 

`DelegateResourceActuator.calcFee()` returns 0, meaning the attacker pays no TRX fee for creating each delegation row — only bandwidth/energy from freezing balance and the transaction's bandwidth cost apply, and delegation to N different receiver addresses is limited only by having N funded receiver accounts and by staying within available frozen balance for bandwidth/energy: [5](#0-4) [6](#0-5) 

Once N such rows exist for the attacker's address, `RateLimiterServlet.service` gates the HTTP path with a flat per-endpoint (`IRateLimiter`) and global (`GlobalRateLimiter`) QPS-based token acquisition that has no notion of the downstream store-scan/sort cost — it treats every request to the same servlet as equal cost regardless of N: [7](#0-6) 

So once the attacker builds a large N (e.g. via repeated `DelegateResourceContract` calls), every subsequent anonymous call to `getdelegatedresourceaccountindex`/`getdelegatedresourceaccountindexv2` (or the gRPC equivalents, which have no rate limiter shown in `RpcApiService` at all) costs the server O(n log n) CPU for prefix scan + sort, while the rate limiter only throttles by request count, not by cost.

### Impact Explanation
This maps to "DoS via RPC-API affecting full node responsiveness for all clients." Repeated cheap calls against a large-N attacker address force the node to repeatedly execute an unbounded `prefixQuery` and `Collections.sort`-style operation, consuming CPU disproportionate to a single request's token cost and degrading responsiveness for all RPC/HTTP clients sharing that node.

### Likelihood Explanation
Preconditions are attacker-affordable: build N delegation index rows using ordinary funded accounts and `DelegateResourceContract` (free of TRX fee, gated only by bandwidth/energy and needing frozen balance), then issue a burst of anonymous `getdelegatedresourceaccountindex(v2)` calls. The HTTP path is protected only by a flat QPS rate limiter that is agnostic to N, and the gRPC path (`RpcApiService.getDelegatedResourceAccountIndex(V2)`) has no rate limiting logic visible at all in the reviewed handlers, making the attack straightforwardly repeatable at low cost.

### Recommendation
Bound the number of scanned/sorted entries per query (e.g., cap `prefixQuery` result size or paginate), and/or make the HTTP/gRPC rate limiters cost-aware (e.g., weight tokens by known/estimated row count for the queried address) rather than treating all requests to an endpoint as equal cost. Consider caching or precomputing sorted indices incrementally on delegate/undelegate rather than recomputing on every read.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());

    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);

  private void delegateResource(byte[] ownerAddress, byte[] receiverAddress, boolean isBandwidth,
                                long balance, boolean lock, long lockPeriod) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicPropertiesStore = chainBaseManager.getDynamicPropertiesStore();
    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();

    // 1. unlock the expired delegate resource
    long now = chainBaseManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, now);

    //modify DelegatedResourceStore
    long expireTime = 0;
    if (lock) {
      expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
    }
    byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, lock);
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore.get(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
    }

    if (isBandwidth) {
      delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress,
        dynamicPropertiesStore.getLatestBlockHeaderTimestamp());

    //modify AccountStore for receiver
    AccountCapsule receiverCapsule = accountStore.get(receiverAddress);
    if (isBandwidth) {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(balance);
    } else {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForEnergy(balance);
    }
    accountStore.put(receiverCapsule.createDbKey(), receiverCapsule);
  }
