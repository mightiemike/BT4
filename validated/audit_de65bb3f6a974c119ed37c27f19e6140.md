## Title
Deposits proceed for disabled (unregistered-for-transfer) tokens because `TokenConfig.Enabled` is never checked before minting PRC20 — ([File: x/uexecutor/keeper/handler.go])

### Summary
The external report describes a contract that lets users deposit funds and play without verifying registration, even though registration is the mechanism that is supposed to gate eligibility (e.g., age check). The Push Chain analog is in the inbound deposit path: `x/uregistry` maintains a `TokenConfig.Enabled` flag that is meant to gate whether a given source-chain asset is allowed to be bridged/minted as PRC20, but the deposit-minting helper `depositPRC20` only fetches the `TokenConfig` and reads its `NativeRepresentation` — it never checks the `Enabled` field before calling `CallPRC20Deposit` to mint PRC20 to the recipient.

### Finding Description
`VoteInbound` in `x/uexecutor/keeper/msg_vote_inbound.go` checks `IsChainInboundEnabled` (chain-level gate) before creating/executing a UTX [1](#0-0) , but there is no equivalent per-token gate. When execution proceeds, `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` call `k.depositPRC20(...)` for the non-CEA/UEA/EOA paths [2](#0-1) . `depositPRC20` itself only does:

```go
tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
...
prc20Address := tokenConfig.NativeRepresentation.ContractAddress
...
return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
``` [3](#0-2) 

`GetTokenConfig` in `x/uregistry/keeper/keeper.go` is a plain collection lookup that returns whatever `TokenConfig` is stored, with no filtering on the `Enabled` field [4](#0-3) . `ExecuteInboundGasAndPayload` follows the identical pattern: it fetches `tokenConfig` via `GetTokenConfig` and immediately uses `tokenConfig.NativeRepresentation.ContractAddress` to deposit/auto-swap, again without inspecting `Enabled` [5](#0-4) .

Grepping the `x/uexecutor` package for any check of `tokenConfig.Enabled` before minting turns up no hits in the deposit/execution code paths — the only `Enabled`-adjacent references in `x/uexecutor` are in `msg_execute_payload.go` (chain-level `IsInboundEnabled`, not token-level) and `msg_migrate_uea.go`, neither of which is the deposit-minting path. This mirrors the reported bug class exactly: a "registration"-equivalent gate (`TokenConfig.Enabled`, set by governance/admin via `AddTokenConfig`/`UpdateTokenConfig` to control which assets are eligible for bridging) exists in the registry but is not consulted by the code path that actually performs the privileged action (minting PRC20 on Push Chain).

### Impact Explanation
If a token is registered in `x/uregistry` (so a `TokenConfig` row and PRC20 mapping exist) but is administratively disabled (`Enabled = false` — e.g., because it was delisted, is unsafe, or hasn't completed onboarding), an inbound observed by Universal Validators for that asset will still be minted as PRC20 to the recipient's UEA once the (honest) UV quorum votes it in, because the deposit path never re-checks `Enabled`. This corrupts PRC20/native asset accounting invariants: value is minted for an asset the registry says should not be transactable, potentially bypassing liquidity caps, safety pauses, or compliance-driven disablement that `Enabled` is meant to enforce. It falls within the "corruption of PRC20 or native asset accounting … token mapping" and "unauthorized mint" impact categories in scope.

### Likelihood Explanation
Reaching this path requires only an ordinary user's deposit on a source chain plus honest Universal Validators observing and voting the inbound through the standard flow (`MsgVoteInbound` → ballot finalization → `ExecuteInbound*`) — no privileged or malicious validator behavior is needed. The only precondition is that governance/admin has configured a `TokenConfig` with `Enabled=false` for an asset that is still discoverable/tracked (e.g., a delisted or paused token), which is a normal registry-management scenario, not a privileged-attacker assumption on the reporting side.

### Recommendation
Add an explicit check of `tokenConfig.Enabled` in `depositPRC20` (`x/uexecutor/keeper/handler.go`) and in the token-config lookup step of `ExecuteInboundGasAndPayload` (`x/uexecutor/keeper/execute_inbound_gas_and_payload.go`), returning an error (and following the existing revert/failed-PCTx handling used for other execution validation failures) when the token is disabled, mirroring the existing chain-level `IsChainInboundEnabled` gate.

### Proof of Concept
1. Registry admin adds a `TokenConfig` for `eip155:11155111` / some USDC-like asset with `Enabled=false` (e.g., delisted after initial testing) while a `NativeRepresentation.ContractAddress` (PRC20 contract) still exists from before delisting.
2. A user deposits that asset on the source chain; honest Universal Validators observe it and submit `MsgVoteInbound` for a `FUNDS` or `FUNDS_AND_PAYLOAD` inbound with that `AssetAddr`.
3. Quorum is reached; `VoteInbound` passes the chain-level `IsChainInboundEnabled` check (chain itself is fine) and calls `ExecuteInbound` → `ExecuteInboundFundsAndPayload` → `k.depositPRC20`.
4. `depositPRC20` fetches the disabled `TokenConfig`, does not check `Enabled`, and proceeds to `CallPRC20Deposit`, minting PRC20 to the recipient despite the asset being disabled in the registry.

Note: I was not able to fully confirm from the index whether `Enabled` is enforced anywhere else in the mint/transfer lifecycle (e.g., inside the PRC20/Handler EVM contract itself, which is out of the scoped Go node code) — if the Solidity `depositPRC20Token` handler independently checks token enablement, this could reduce/negate the impact. This would need to be verified in `push-chain-core-contracts` or via a live Devin session with full repository access, since some contract-level logic may not be captured by the index.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
