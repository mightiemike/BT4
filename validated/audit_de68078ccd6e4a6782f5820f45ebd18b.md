### Title
`liquidity_cap` on `TokenConfig` is defined but never enforced before minting PRC20 on inbound execution — (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/evm.go`)

### Summary
The `TokenConfig.LiquidityCap` field [1](#0-0)  is meant to bound the maximum synthetic supply mintable for a bridged token, analogous to the `MAX_SANE_AMOUNT`/`totalShares` cap in the Euler `maxMint` report. However, across the entire `x/uexecutor` minting path (`depositPRC20` → `CallPRC20Deposit` → `DerivedEVMCall`), no code reads or checks `LiquidityCap` before minting. This mirrors the reported bug class — a supply/liquidity cap that exists conceptually in state but is not consulted at the point of mint — except here the check is entirely absent rather than merely imprecise.

### Finding Description
`depositPRC20` fetches the `TokenConfig` for a source-chain asset and directly proceeds to call `CallPRC20Deposit` with the attacker/validator-observed amount, with no comparison against `tokenConfig.LiquidityCap`: [2](#0-1) 

`CallPRC20Deposit` issues a `DerivedEVMCall` to `depositPRC20Token` on the Universal Core handler contract with the raw `amount`, again with no cap enforcement: [3](#0-2) 

A grep across `x/uexecutor/keeper/*.go` for `Liquidity`/`liquidity` returns zero matches, confirming the field is written and validated only at config-creation time (`ValidateBasic` requires it be non-empty) [4](#0-3)  but is never read anywhere in the inbound execution / minting flow that actually creates PRC20 balance.

Because inbound `FUNDS`/`GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` amounts are attacker-influenced (a user can bridge from an external chain in amounts they control, subject only to honest-validator observation of a real on-chain deposit), an ordinary unprivileged user can, through repeated normal bridging with no need for validator collusion, mint PRC20 supply past whatever `liquidity_cap` the registry admin configured for that token — since the value is never consulted.

### Impact Explanation
This directly corrupts PRC20 accounting/token-mapping invariants ("Registry and accounting path… must not misroute value or attach the wrong asset semantics") in the allowed-impact scope. An admin-set `liquidity_cap` is a risk control (e.g., bounding synthetic-asset exposure per external token/vault). Because it's silently unenforced, unbounded PRC20 minting is possible relative to the actual custodied/bridged collateral, up to whatever the external chain vault or lock mechanism allows, which can lead to backing-mismatch / effectively unauthorized mint of PRC20 supply beyond the protocol's own stated per-token risk ceiling. Severity is bounded by the fact that PRC20 minting still requires a real, validator-observed inbound event (it isn't a free unauthorized mint out of thin air) — but the specific invariant "supply must stay under `liquidity_cap`" is completely broken for any unprivileged user driving ordinary inbound volume.

### Likelihood Explanation
High likelihood of reachability: any user bridging assets through the standard inbound flow can cause supply to grow without bound, and there's no adversarial complexity required (no malicious validators or admin needed) — it triggers on the default transaction submission / inbound execution path with honest validators. The only preconditions are (a) an admin has configured a `liquidity_cap` intending it to be enforced, and (b) cumulative bridged volume for a token exceeds that configured cap, which is plausible given the field is 1,000,000-unit example values already checked into config files (`config/testnet-donut/*/tokens/*.json`) [5](#0-4) .

### Recommendation
Enforce `LiquidityCap` in the minting path before calling `CallPRC20Deposit`: query the PRC20's current `totalSupply()` (or track cumulative minted amount in `x/uexecutor` state), compute `remainingCap = LiquidityCap - totalSupply`, and cap/reject the deposit similarly to the corrected `maxMint`/`maxDeposit` pattern in the source report — i.e., `mintable = min(amount, remainingCap)`, and record a failed/partial PCTx (with revert/refund per the existing `handleFailedOutbound`-style flow) when the inbound amount would push supply over the cap, rather than silently minting the full requested amount.

### Proof of Concept
1. Admin registers a `TokenConfig` for `eip155:11155111` USDC with `liquidity_cap = "1000000000000000000000000"` (1,000,000 tokens at 18/6 decimals as configured).
2. Users repeatedly bridge USDC deposits from Ethereum Sepolia through the standard gateway → `MsgVoteInbound` → quorum → `VoteInbound` → `depositPRC20` path, each observed honestly by validators.
3. Cumulative minted PRC20 supply surpasses `1000000000000000000000000` because `depositPRC20`/`CallPRC20Deposit` never checks `tokenConfig.LiquidityCap` against current or resulting supply — verified by the absence of any `Liquidity`-related check in `x/uexecutor/keeper/handler.go` and `evm.go`, and by the fact that a full-repo grep for `Liquidity` in `x/uexecutor/keeper` returns no results.
4. No error, no cap enforcement, no partial mint occurs — supply exceeds the configured risk ceiling using nothing but ordinary user bridging.

Note: I could not locate `PRC20.sol` itself within the indexed repository (it appears to live in a separate contracts submodule referenced by `e2e-tests/setup.sh`), so I could not confirm whether the PRC20 contract itself has any independent supply-cap enforcement at the Solidity level. Given the index size limits, some file contents (e.g. the actual `PRC20.sol` mint function) may not be available — a Devin session with full repository/submodule access would be needed to confirm whether the cap is instead enforced purely at the contract level and simply duplicated (unused) in `x/uregistry`.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
