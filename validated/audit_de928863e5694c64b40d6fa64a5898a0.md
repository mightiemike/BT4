### Title
Missing witness-address deduplication in `VoteWitnessActuator` allows duplicate vote entries and rounding-based reward accounting inconsistency - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
The Solidity report describes an unprivileged actor injecting a duplicate entry into a list (`_validators[virtualId]`) that is later iterated for reward accounting, causing the reward pool tracking variable to be overstated due to repeated per-entry rounding. The same bug class is reachable in java-tron: `VoteWitnessActuator` — the actuator that processes user-submitted `VoteWitnessContract` transactions — never deduplicates witness addresses across the submitted vote entries before persisting them, while the parallel TVM-invoked path (`VoteWitnessProcessor`) explicitly performs this merge. This asymmetry lets an ordinary account holder create duplicate per-witness `Vote` entries that are stored and later iterated one-by-one during reward computation, exploiting integer-division flooring to extract more reward than intended.

### Finding Description
`VoteWitnessActuator.validate()` only checks vote count positivity and that the total sum of votes does not exceed the voter's `tronPower`; it never rejects duplicate `voteAddress` entries in the submitted list. [1](#0-0) 

`countVoteAccount()` then persists every submitted `Vote` entry as-is, one call per entry, with no merging of entries that target the same witness: [2](#0-1) 

This is directly comparable to the TVM-invoked equivalent, `VoteWitnessProcessor`, which the developers explicitly hardened against this exact scenario by merging duplicate witness entries into a `voteMap` before persisting ("merge vote for same witness"): [3](#0-2) 

Because `VoteWitnessActuator` lacks this same merge step, a user can submit a single `VoteWitnessContract` containing multiple `Vote` entries for the *same* witness address (e.g., splitting 1000 votes into several smaller entries), staying within the total `tronPower` cap, and have all of them stored as separate entries in `AccountCapsule`'s and `VotesCapsule`'s vote lists.

Reward computation later iterates these vote lists per-entry and applies integer (flooring) division for each entry independently: [4](#0-3) [5](#0-4) 

Since `reward += deltaVi.multiply(userVote).divide(DECIMAL_OF_VI_REWARD)` floors on every iteration, splitting one large vote into several smaller duplicate entries for the same witness reduces the cumulative flooring loss compared to a single computation over the full vote amount — i.e., `floor(a) + floor(b) >= floor(a+b)`. This lets the voter capture a rounding-based reward surplus, an accounting inconsistency that mirrors the root cause of the referenced report (duplicate list entries feeding a reward-distribution loop that accumulates per-entry residuals).

### Impact Explanation
This breaks the intended invariant that reward accrual for a given witness/voter pair is a deterministic function of the aggregate vote amount for that cycle. By duplicating vote entries for the same witness, an unprivileged account can systematically extract small amounts of extra `allowance` (reward) beyond what its true voting power should yield, at the expense of the shared reward pool computed via `DelegationStore`/`MortgageService`. This is a state/accounting divergence in a core consensus-adjacent reward mechanism (vote rewards), not merely cosmetic — repeated across many cycles/accounts it becomes a real leakage vector against protocol-held reward funds, analogous to the `validatorPoolRewards` overstatement in the original report.

### Likelihood Explanation
High likelihood of reachability: any account holder can submit a `VoteWitnessContract` with duplicate witness addresses across separate `Vote` entries — this requires no special privilege, only that the total votes stay within `tronPower` and `MAX_VOTE_NUMBER`. The magnitude of gain per transaction is bounded (limited by the number of allowed vote entries and per-entry flooring loss, at most a few "drops" per split per cycle), but it is systematically repeatable every voting/reward cycle, and the discrepancy exists purely due to a missing dedup step that the codebase's own TVM-path implementation shows was recognized as necessary.

### Recommendation
Mirror the dedup logic already present in `VoteWitnessProcessor` inside `VoteWitnessActuator.countVoteAccount()`/`validate()`: merge multiple `Vote` entries targeting the same witness address into a single aggregated entry (e.g., via a `Map<ByteString, Long>` as done in `VoteWitnessProcessor.execute()`) before computing the total sum check and before persisting to `AccountCapsule`/`VotesCapsule`. This ensures reward computation always operates on one entry per witness per account, eliminating the rounding-based reward surplus.

### Proof of Concept
1. Attacker account freezes balance to obtain `tronPower` of, say, 1000 TRX-equivalent votes.
2. Attacker submits a `VoteWitnessContract` via `VoteWitnessActuator` (normal transaction, not through TVM) containing two `Vote` entries both pointing to the same witness `W`: `{W, 500}` and `{W, 500}`.
3. `validate()` at [1](#0-0)  passes because the sum (1000) does not exceed `tronPower`, and no duplicate-address check exists.
4. `countVoteAccount()` at [2](#0-1)  stores both entries verbatim into `accountCapsule`'s and `votesCapsule`'s vote lists (two separate `Vote{W,500}` entries instead of one `Vote{W,1000}`).
5. At the next reward cycle, `MortgageService`/`VoteRewardUtil` iterate the vote list per entry, computing `floor(deltaVi*500/DECIMAL) + floor(deltaVi*500/DECIMAL)` instead of `floor(deltaVi*1000/DECIMAL)`, yielding a reward that can exceed the single-entry computation due to reduced flooring loss — demonstrating the accounting inconsistency.
