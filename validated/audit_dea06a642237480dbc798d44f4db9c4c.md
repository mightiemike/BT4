## Analog Found

### Title
Unconditional `.unwrap()` on `receiver_shard_id()` in the delayed-receipt filter causes a chunk-halting panic when a `GlobalContractDistribution` receipt's `target_shard` cannot be resolved to a current shard - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The CVE describes a crash that occurs when a second protocol event arrives after a first one has already put the session into a failure/negotiation state, and the handler does not gracefully tolerate that stale/unexpected state — it just crashes. The nearcore analog is `DelayedReceiptQueueWrapper::receipt_filter_fn`, which pops a delayed receipt and unconditionally calls `.unwrap()` on the fallible result of `Receipt::receiver_shard_id`. If a `GlobalContractDistribution` receipt sits in the delayed queue across shard-layout transitions and its `target_shard` can no longer be resolved to a shard in the current layout (or its known split history), `receiver_shard_id` returns `Err(EpochError::ShardingError(..))`, and the `.unwrap()` turns that ordinary, reachable error into a panic during `Runtime::apply`.

### Finding Description
`Receipt::receiver_shard_id` for `ReceiptEnum::GlobalContractDistribution` tries to remap the receipt's `target_shard` into the current shard layout via `shard_layout.resolve_to_current_shard(target_shard)`, and explicitly returns an `Err` when this fails: [1](#0-0) 

That error is a **designed, expected, reachable outcome** — not an invariant violation — as shown by the doc comment "the target shard may be from an arbitrarily old layout ... resolve_to_current_shard will find a shard descendant in the current layout" and the explicit error path when it cannot.

However, the only caller of this function in the runtime, `receipt_filter_fn` (used every time a delayed receipt is popped for processing), discards that `Result` with `.unwrap()`: [2](#0-1) 

This function is invoked unconditionally for every delayed receipt during `Runtime::apply`, on the standard receipt-processing path reachable by any account that deploys a global contract: [3](#0-2) 

`GlobalContractDistribution` receipts are created and forwarded shard-by-shard purely from a `DeployGlobalContract` action submitted by an ordinary contract deployer: [4](#0-3) 

If chunk congestion causes such a receipt to sit in the delayed queue while the shard layout goes through resharding transitions the split-history mapping cannot fully account for (e.g., a resharding history gap, an epoch where the layout version regresses below `ShardLayoutV3`, or any other scenario `resolve_to_current_shard` was not built to handle), `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics, aborting `Runtime::apply` for the whole shard.

Notably, the codebase already contains a targeted regression test acknowledging this exact class of bug (stale `GlobalContractDistribution` receipts surviving repeated resharding and panicking in `receipt_filter_fn`): [5](#0-4) 

While `ShardLayoutV3::resolve_to_current_shard` was hardened to walk the *full* split history (not just the most recent split) to fix the specific double-resharding case covered by that test: [6](#0-5) 

the underlying design flaw — `receipt_filter_fn` treating a legitimate, documented `Err` return as an unwrap-able invariant — remains. `resolve_to_current_shard` explicitly documents that it returns `None` "if the shard ID is absent from both the current layout and the split history," and `build_shard_split_map` deliberately truncates history collection whenever a layout version older than V3 is encountered: [7](#0-6) 

meaning any V1/V2-to-V3 boundary, non-contiguous split history, or future edge case in shard-layout evolution can reproduce the same unwrap-panic that the fixed double-resharding test was written to catch — this is the same "first failure state handled, but a subsequent occurrence of the same condition still crashes" pattern as CVE-2021-21375.

### Impact Explanation
A panic inside `Runtime::apply` while draining the delayed-receipt queue halts chunk application on the affected shard for every node applying that chunk. Because delayed receipts are processed deterministically and identically by all honest validators, this is not a per-node crash but a **network-wide, transaction/receipt-triggered halt** of the shard — the receiver-side attack path listed as in-scope ("a transaction-triggered halt").

### Likelihood Explanation
Reaching this bug requires: (1) submitting a `DeployGlobalContract` action, entirely available to any unprivileged account, and (2) that its `GlobalContractDistribution` receipt be delayed (e.g., via chunk compute saturation, which any account can also help trigger with cheap high-gas calls) across shard-layout transitions such that `resolve_to_current_shard` cannot map `target_shard` back to the current layout. The existence of a dedicated regression test in the repository for the "double resharding" variant of this exact panic path demonstrates it is a realistic, previously-triggered condition, not merely theoretical. The core `.unwrap()` remains present as a systemic weak point even though the particular history-truncation bug that motivated the test appears to have been narrowly patched at the `ShardLayoutV3` level.

### Recommendation
Change `receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs` to propagate `receiver_shard_id`'s `Err` as a `RuntimeError` (or `StorageInconsistentState`) instead of `.unwrap()`ing it, and thread that error through `DelayedReceiptQueueWrapper::pop`'s `Result` return type so callers handle it without panicking. Additionally, audit all other call sites of `receiver_shard_id` for the same unwrap pattern, and consider making `resolve_to_current_shard` failure modes protocol-versioned/gated so that a receipt that cannot be resolved is either safely dropped/refunded or permanently retained rather than causing a hard halt.

### Proof of Concept
The repository's own test demonstrates the trigger sequence conceptually: deploy a global contract from an account whose shard is force-split, saturate that shard's compute budget every block so the resulting `GlobalContractDistribution` receipt is pushed to the delayed queue, force a second shard split so the layout's split-history bookkeeping is stressed, then stop saturating and let the delayed queue drain — the receipt's `target_shard` may no longer resolve, causing `receipt_filter_fn`'s `.unwrap()` to panic and halt the chain: [8](#0-7) 

**Uncertainty note:** I could not fully verify (due to tool-call limits) whether the specific double-resharding scenario covered by the existing test is fully closed for all shard-layout-version transition edge cases (e.g., V1/V2 → V3 boundaries, or epoch-config history gaps), or whether additional exploitable paths to a `None`/`Err` from `resolve_to_current_shard`/`receiver_shard_id` still exist in production configurations. The core issue — that `receipt_filter_fn` treats a documented, reachable `Err` as an unwrap-able invariant — is confirmed directly from the source shown above.
