### Title
Native Sapling proving-context leak on malformed shielded-proof input in `ShieldedTRC20ParametersBuilder.build` - ([File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java])

### Summary
An unprivileged caller of the public HTTP API `/wallet/createshieldedcontractparameters` (backed by `CreateShieldedContractParametersServlet` → `Wallet.createShieldedContractParameters`) can repeatedly submit `PrivateShieldedTRC20Parameters` whose `rcm`/`alpha`/`path` fields have correct byte lengths but invalid field-element encodings. This causes `JLibrustzcash.librustzcashSaplingSpendProof`/`librustzcashSaplingOutputProof` to return `false`, which is converted into a `ZksnarkException` inside `generateSpendProof`/`generateOutputProof`. Unlike `ZenTransactionBuilder.build`, which frees the native proving context (`ctx`) in a `finally` block, `ShieldedTRC20ParametersBuilder.build(boolean withAsk)` allocates `ctx` via `librustzcashSaplingProvingCtxInit()` but only wraps the proof-generation logic in `try { ... } catch (Exception e) { throw new ZksnarkException(...); }` with no visible `finally` that calls `librustzcashSaplingProvingCtxFree(ctx)` on the exception path, risking a repeatable native memory leak rather than a JVM crash.

### Finding Description
The reachable path is: `CreateShieldedContractParametersServlet.doPost` [1](#0-0)  → `Wallet.createShieldedContractParameters` (gated only by `checkAllowShieldedTransactionApi()`, no other auth) [2](#0-1)  → `builder.build(true)` [3](#0-2) .

Inside `ShieldedTRC20ParametersBuilder`, `generateSpendProof`/`generateOutputProof` only validate that `cm`/`nf`/`pkD` are non-empty; they do not validate that `rcm`, `alpha`, or `path` encode valid field elements — that check happens only inside the native `librustzcashSaplingSpendProof`/`librustzcashSaplingOutputProof` calls, which return `boolean` rather than throwing, and a `false` return is converted to `ZksnarkException("Spend proof failed")` / `ZksnarkException("Output proof failed")` [4](#0-3) [5](#0-4) . Both methods are annotated "Note: should call librustzcashSaplingProvingCtxFree in the caller" [6](#0-5) [7](#0-6) , indicating the design expects the caller to always free `ctx`.

In `build(boolean withAsk)`, the proof-generation switch (`MINT`/`TRANSFER`/`BURN`) calls these methods and is wrapped only in `try { ... } catch (Exception e) { throw new ZksnarkException(...); }` [8](#0-7) , with no `finally` block visible in this handler that calls `librustzcashSaplingProvingCtxFree(ctx)` — contrasting with the correct pattern in `ZenTransactionBuilder.build`, which explicitly frees `ctx` in a `finally` clause regardless of success or failure [9](#0-8) . Consequently, whenever an attacker supplies a spend/receive note with a correctly-sized but invalid `rcm`/`alpha` (or malformed Merkle `path`) that makes the native proof call fail, the `ZksnarkException` unwinds the stack without releasing the native proving-context handle allocated by `librustzcashSaplingProvingCtxInit()`.

`Util.processError` in the servlet only serializes the exception to an HTTP error response; it performs no native resource cleanup [10](#0-9) , so the leak is not mitigated at the API boundary. The claim that native calls throw uncaught exceptions or crash the JVM is not supported by the code — `librustzcashSaplingSpendProof`/`librustzcashSaplingOutputProof`/`librustzcashSaplingBindingSig` are boolean-returning JNA bindings whose failures are deliberately converted into checked `ZksnarkException`s [11](#0-10) , which propagate correctly through `Wallet.createShieldedContractParameters` (declared to throw `ZksnarkException`) to the servlet's generic `catch (Exception e) { Util.processError(e, response); }`.

### Impact Explanation
Each rejected request that reaches native proof generation but fails validation (correct-length, invalid-encoding `rcm`/`alpha`/`path`) leaks one native Sapling proving context. An unprivileged attacker can automate high-volume POSTs to `/wallet/createshieldedcontractparameters` with such malformed-but-well-formed-length inputs, causing cumulative native (off-heap) memory growth over time, potentially degrading node stability/availability (resource exhaustion) without requiring any authentication or on-chain cost beyond HTTP requests (subject to rate limiting).

### Likelihood Explanation
Preconditions: `allowShieldedTransactionApi=true` (a documented node operator toggle for that endpoint) and no other authentication, matching the stated precondition. The attack is fully unprivileged, repeatable, and rate-limited only by `RateLimiterServlet`'s generic QPS-based limiter (no per-user/session accounting) [12](#0-11) , so an attacker can sustain the leak at the allowed QPS. Feasibility of crafting "correct length, invalid encoding" `rcm`/`alpha` values is straightforward since `valid32Params`/`validParamLength` in `LibrustzcashParam` only check byte-array length, not field-element validity, so the native reject path (returning `false`) is easy to trigger deterministically.

### Recommendation
Wrap the proof-generation logic in `ShieldedTRC20ParametersBuilder.build(boolean withAsk)` in a `try/finally` that unconditionally calls `JLibrustzcash.librustzcashSaplingProvingCtxFree(ctx)`, mirroring the pattern already used in `ZenTransactionBuilder.build`. Additionally, consider validating `rcm`/`alpha` are canonical field-element encodings in Java before invoking the native proof functions, to fail fast without touching the native context allocation path.

  protected void service(HttpServletRequest req, HttpServletResponse resp)
      throws ServletException, IOException {

    RuntimeData runtimeData = new RuntimeData(req);
    IRateLimiter rateLimiter = container.get(KEY_PREFIX_HTTP, getClass().getSimpleName());

    // Check per-endpoint first to avoid consuming global IP/QPS quota for requests
    // that would be rejected by the per-endpoint limiter anyway. acquirePermit()
    // chooses blocking or non-blocking semantics based on rate.limiter.apiNonBlocking.
    boolean perEndpointAcquired = rateLimiter == null || rateLimiter.acquirePermit(runtimeData);
    boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);

    String contextPath = req.getContextPath();
    String url = Strings.isNullOrEmpty(req.getServletPath())
        ? MetricLabels.UNDEFINED : contextPath + req.getServletPath();
    // int64_as_string is honored only on GET requests (URL query). POST is intentionally
    // unsupported because reading the body here would consume request.getReader() and
    // break downstream servlets that read it themselves.
    if ("GET".equalsIgnoreCase(req.getMethod())) {
      JsonFormat.setInt64AsString(Util.getInt64AsString(req));
    }
    try {
      resp.setContentType("application/json; charset=utf-8");

      if (acquireResource) {
        Histogram.Timer requestTimer = Metrics.histogramStartTimer(
            MetricKeys.Histogram.HTTP_SERVICE_LATENCY, url);
        super.service(req, resp);
        Metrics.histogramObserve(requestTimer);
      } else {
        resp.getWriter()
            .println(Util.printErrorMsg(new IllegalAccessException("lack of computing resources")));
      }
    } catch (ServletException | IOException | BadMessageException e) {
      throw e;
    } catch (Exception unexpected) {
      logger.error("Http Api {}, Method:{}. Error：", url, req.getMethod(), unexpected);
    } finally {
      // CRITICAL: this clear pairs with the setInt64AsString call above. Removing it
      // will leak int64_as_string state across requests on reused Tomcat threads,
      // producing intermittent quoted/unquoted output that is very hard to debug.
      JsonFormat.clearInt64AsString();
      // Release whenever the per-endpoint permit was acquired (covers both the normal
      // completion path and the case where GlobalRateLimiter rejected the request).
      if (rateLimiter instanceof IPreemptibleRateLimiter && perEndpointAcquired) {
        ((IPreemptibleRateLimiter) rateLimiter).release();
