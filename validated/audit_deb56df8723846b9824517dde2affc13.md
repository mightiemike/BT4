The strongest analog I found is in the OAuth **token exchange** implementation of `@shopify/shopify-api`, where the core library trusts a caller-supplied `shop` parameter instead of deriving it from the already-validated session token, mirroring the "missing internal validation, relies on caller-supplied data" pattern of the reference `sync()` bug.

### Title
Token Exchange does not verify the `shop` parameter matches the session token's `dest` claim - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
`shopify.auth.tokenExchange()` decodes and cryptographically validates the caller-supplied `sessionToken` (signature, audience, expiry) but discards the decoded payload and never checks that its `dest` (the shop the token was actually issued for) matches the separately caller-supplied `shop` argument used to build the OAuth token-exchange request. [1](#0-0) 

### Finding Description
`tokenExchange()` calls `await decodeSessionToken(config)(sessionToken);` purely to validate the token's signature/audience/expiry, then throws away the returned payload. It immediately builds the token-exchange request body using the independently-supplied `shop` argument (sanitized via `sanitizeShop`), not the token's own `dest` field: [2](#0-1) 

`decodeSessionToken` only validates the JWT signature, `aud` (API key), and standard `exp`/`nbf` claims — it never asserts anything about `dest`: [3](#0-2) 

The official `tokenExchange` documentation explicitly shows an integration pattern where `shop` is taken from an independent, attacker-influenced source (`req.query.shop`) and `sessionToken` from the `Authorization` header/URL param — two unrelated inputs combined without any cross-check inside the library: [4](#0-3) 

This is analogous to the reported `Pools.sync()` issue: a function that is supposed to only be invoked with already-validated/consistent data (there: tokens actually transferred by the Router; here: a `shop` value that actually matches the presented session token) instead accepts the caller's version of that data with no internal consistency check, delegating the "real" enforcement entirely to an external component (there: none present; here: hopefully Shopify's `/admin/oauth/access_token` endpoint validating `dest` against the target shop domain).

Note that the higher-level framework packages (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) do NOT exhibit this gap in their own call sites — they all derive `shop` from `payload.dest` after validating the token before calling `tokenExchange`/`exchangeToken`: [5](#0-4) [6](#0-5) 

However, `shopify.auth.tokenExchange` is a documented, standalone public API of `@shopify/shopify-api` intended to be called directly by app developers building custom auth flows (per its own docs), and the library itself provides no defense-in-depth check that `shop` and the token's `dest` agree.

### Impact Explanation
If any app built directly on `@shopify/shopify-api` (bypassing the safer wrapper packages) derives `shop` from request input (e.g. a query string) independently of the session token — as the library's own documentation demonstrates — an attacker holding a valid session token for **their own** installed shop could submit that token alongside a `shop` parameter naming a **different**, victim shop. The library would issue a token-exchange POST to `https://{victim-shop}/admin/oauth/access_token` using the attacker's session token as `subject_token`. Whether this succeeds depends entirely on Shopify's OAuth server correctly rejecting the shop/token mismatch; the shopify-app-js library itself provides no such guarantee, meaning it is not defense-in-depth safe and pushes 100% of this cross-tenant validation onto trusting the remote endpoint's behavior.

### Likelihood Explanation
Likelihood is limited primarily to apps that use the raw `shopify.auth.tokenExchange` API directly (as shown in its own docs) with a `shop` value sourced independently from the session token, rather than the maintained wrapper packages, which already derive `shop` safely from the validated token. This reduces exploitability in the "batteries-included" packages but leaves a real gap in the core library's public contract and documented usage pattern.

### Recommendation
In `tokenExchange()`, capture the decoded payload from `decodeSessionToken` and assert that `new URL(payload.dest).hostname` equals the sanitized `shop` argument before constructing the OAuth request, throwing an `InvalidJwtError`/`InvalidShopError` on mismatch — mirroring the pattern already used internally by `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router`. Update the `tokenExchange` reference docs to no longer suggest sourcing `shop` from an independent, unauthenticated source.

### Proof of Concept
1. App using `@shopify/shopify-api` directly implements `/auth` as shown in the official docs, taking `shop` from `req.query.shop` and `sessionToken` from the `Authorization` header. [4](#0-3) 
2. Attacker installs the app on `attacker-shop.myshopify.com` and obtains a valid, signed session token for that shop from App Bridge.
3. Attacker calls `/auth?shop=victim-shop.myshopify.com` with `Authorization: Bearer <attacker's session token>`.
4. `tokenExchange()` validates the token's signature/audience only, ignores `dest`, and issues the token-exchange POST to `https://victim-shop.myshopify.com/admin/oauth/access_token` with the attacker's token as `subject_token`. [2](#0-1) 
5. Outcome depends on Shopify's remote validation of the `dest`/shop binding, which is outside shopify-app-js's control — the library provides no local safeguard.

```typescript
export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(

      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );
```

```typescript
export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
```
