### Title
Unbounded Recursive Receipt-Chain Traversal in `get_final_transaction_result` Enables RPC-Triggered Stack-Overflow DoS - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` (the internal helper backing `Chain::get_final_transaction_result`, i.e. the `tx` / `EXPERIMENTAL_tx_status` JSON-RPC resolver) recurses once per receipt produced by a transaction's execution chain, with **no depth or node-count limit**. An unprivileged transaction signer who builds a long chain of dependent receipts (e.g. via repeated self cross-contract calls / `yield_create`+`yield_resume` chains spread over many cheap blocks) and then triggers an RPC query for the originating transaction hash can force the serving node into unbounded recursion, risking a stack-overflow abort of the whole node process. This is analogous to CVE-2025-32947, where a crafted object graph fed to a public endpoint caused unbounded traversal and made the server unresponsive.

### Finding Description
`get_recursive_transaction_results` walks the receipt-outcome DAG by recursively calling itself for every `receipt_id` referenced by an outcome, with no bound on recursion depth: [1](#0-0) 

This is invoked directly by the public API `get_final_transaction_result`, documented as waiting "for the end of execution of all corresponding receipts" for a given transaction hash — the standard implementation behind transaction-status RPC calls: [2](#0-1) 

Nothing in this call path enforces a maximum recursion depth or total outcome count. This stands in stark contrast to the newer, similar `ReceiptToTx` traversal, which was explicitly hardened with a hard `MAX_DEPTH = 1000` limit and a dedicated `DepthExceeded` error precisely to prevent this class of bug: [3](#0-2) 

An attacker can grow a receipt chain arbitrarily long over time (not bounded by a single chunk's gas limit) using self cross-contract calls or `PromiseYield`/`PromiseResume` callback chains — each hop is cheap and spans a separate block/receipt, so gas metering only bounds the depth achievable *within one chunk*, not the depth of the historical DAG that accumulates across many blocks. Existing evidence in the codebase shows that even *within a single chunk*, gas-bounded self-recursion via cross-contract calls already reaches depths of 56–221 hops: [4](#0-3) 

Chaining this pattern across many blocks (paying only ordinary transaction fees, no privileged access required) lets an attacker construct a receipt-outcome chain orders of magnitude deeper, well beyond what unmetered recursive Rust code with no explicit depth check can safely traverse.

### Impact Explanation
Because `get_recursive_transaction_results` has no depth guard, a sufficiently deep receipt chain forces the serving node (any RPC node, or a validator's own view-client path since `Chain` is shared by clients) into deep recursive stack growth. In Rust, exceeding the thread's stack causes an unrecoverable process abort (SIGSEGV / stack overflow), not a catchable panic — this crashes the entire node process, not just the handling request/thread. Since `tx`/`EXPERIMENTAL_tx_status` is a standard, unauthenticated JSON-RPC call reachable by anyone who knows a transaction hash, this constitutes a transaction-triggered denial-of-service against any node that serves that RPC method and is asked to resolve the crafted transaction's status — matching the "transaction-triggered halt" impact class.

### Likelihood Explanation
Likelihood is High for causing a crash on any node that serves RPC status queries for the crafted transaction, since:
- No privileged role is required — any account able to sign and submit transactions can build the receipt chain.
- The mechanism (repeated self cross-contract calls, or yield/resume chains) is fee-bounded but otherwise unrestricted and already demonstrated to reach substantial depth within a single chunk.
- Extending the chain across many blocks removes the single-chunk gas ceiling on total depth.
- No existing code path enforces a bound analogous to the `MAX_DEPTH` used in the sibling `ReceiptToTx` feature.

### Recommendation
Add an explicit maximum traversal depth / total-outcome-count bound to `get_recursive_transaction_results` (mirroring the `ReceiptToTx` `MAX_DEPTH` pattern), and/or convert the recursive traversal into an iterative one with an enforced upper bound, returning a `DepthExceeded`-style error to the RPC caller once the limit is reached, rather than recursing without limit.

### Proof of Concept
1. As an ordinary funded account, deploy/call a contract method that on each invocation issues a new cross-contract call to itself (or `yield_create` immediately followed, in a subsequent transaction, by `yield_resume` that itself issues another `yield_create`), forming a long linear chain of receipts spread over many blocks (each transaction is inexpensive and requires no special privileges).
2. Repeat step 1 to accumulate a receipt-outcome chain whose length substantially exceeds a safe native stack recursion depth (achievable cheaply since each hop only costs ordinary transaction/gas fees and is not bounded by a single chunk's gas limit).
3. Call the `tx` (or `EXPERIMENTAL_tx_status`) JSON-RPC method against the original transaction hash on a node that tracks the relevant shard(s).
4. The serving node recursively resolves the chain via `get_recursive_transaction_results`/`get_final_transaction_result`; once the chain length exceeds the safe stack depth, the node process crashes with a stack overflow.

Note: I was not able to fully trace, within the remaining investigation budget, the exact RPC handler wiring (`chain/client/src/view_client_actor.rs`) that calls `get_final_transaction_result`, nor precisely quantify the maximum achievable chain depth across blocks (bounded only by attacker willingness to pay ordinary fees over time) — a Devin session with full repository access would be needed to confirm the exact call path and empirically determine the minimum chain length required to trigger a stack overflow on a production build.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Returns FinalExecutionOutcomeView for the given transaction.
    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }
