No revoke/remove function exists for the WorkflowRegistry allowlist entries (`AllowlistRequest` is the only mutator found in the codebase's usage, aside from natural expiry-based pruning). This is a valid analog to the reported bug class.

### Title
Workflow owners cannot revoke an `AllowlistRequest`-approved request digest before its expiry, leaving privileged Vault operations authorized for a signed but subsequently-untrusted request - (File: `core/services/workflows/syncer/v2/workflow_registry.go`)

### Summary
The `WorkflowRegistry` V2 contract exposes `AllowlistRequest(requestDigest, expiryTimestamp)`, which lets an allowed workflow-owner signer authorize a specific JSON-RPC request digest to be executed against the CRE Vault gateway (secrets create/update/delete/list, etc.) until `expiryTimestamp`. This is functionally identical to the `approvedHashes` pattern from the referenced report: a user pre-approves a hash (here, a request digest) that a relying system (`AllowListBasedAuth`) will treat as authorization proof. No mechanism exists to revoke that approval once submitted on-chain, only to wait out the expiry window.

### Finding Description
`AllowlistRequest` writes an entry keyed by `requestDigest` with an `Owner` and `ExpiryTimestamp` into on-chain storage [1](#0-0) . The off-chain `AllowListBasedAuth.AuthorizeRequest` treats any request matching an allowlisted, non-expired digest as authorized for privileged Vault operations, deriving the authorized owner purely from the on-chain record: [2](#0-1) . The synced allowlist is only pruned when a request's `ExpiryTimestamp` passes; there is no code path (contract call, changeset, or operation) anywhere in the repo that removes or invalidates an already-allowlisted digest before expiry: [3](#0-2) . The `UserAllowlistRequestOp`/`UserAllowlistRequest` changeset likewise only wraps the add operation, with no corresponding revoke counterpart, unlike `UserLinkOwner`/`UserUnlinkOwner` which do have a symmetric pair: [4](#0-3) [5](#0-4) .

Expiry windows observed in tests/tooling range from 1 hour to 48 hours, and are fully attacker/operator-configurable up to `uint32` max: [6](#0-5) [7](#0-6) .

### Impact Explanation
If a workflow owner allowlists a request digest and then discovers the corresponding request body was crafted maliciously, contains a compromised secret payload, or was generated by tooling that is later found to be compromised, they have no way to withdraw that authorization. Anyone who reconstructs the exact JSON-RPC request matching the allowlisted digest (which is derived from the request body, not secret material) can submit it to the Vault gateway within the expiry window and have it treated as authorized, since `AllowListBasedAuth` performs no additional freshness or intent check beyond digest match and expiry: [8](#0-7) . This can result in unauthorized privileged Vault secret operations (create/update/delete secrets) being executed for the owner during the outstanding window, matching the "unauthorized privileged node action / secret disclosure" impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to obtain the exact plaintext request body corresponding to the pre-approved digest (e.g., via leaked tooling output, a compromised CI pipeline that generated the request, or social engineering), and act within the expiry window (which can be tens of hours). The lack of any revoke path means the affected owner has zero remediation options once they realize the approved digest should not be trusted — they must simply wait for it to expire while remaining exposed the entire time.

### Recommendation
Add a revoke capability to the `WorkflowRegistry` V2 contract, e.g. a `revokeAllowlistedRequest(bytes32 requestDigest)` function restricted to the digest's `Owner` (or an allowed signer for that owner), that removes/zeroes the corresponding on-chain entry. Correspondingly add:
- A `UserRevokeAllowlistRequestOp` / `UserRevokeAllowlistRequest` changeset mirroring the existing `UserAllowlistRequestOp`/`UserAllowlistRequest`.
- Ensure `workflowRegistry.syncAllowlistedRequests` picks up removals promptly (not just expiry-based pruning) so `AllowListBasedAuth` stops honoring revoked digests immediately.

### Proof of Concept
1. Workflow owner signs and calls `AllowlistRequest(requestDigest, expiry=now+48h)` for a `vault.secrets.create` request, as shown in the test helper: [1](#0-0) .
2. Owner later determines the corresponding request body/tooling is compromised and wants to invalidate the approval.
3. No contract function or changeset exists to remove the entry; `w.allowListedRequests` in the syncer only drops entries once `ExpiryTimestamp` has passed: [9](#0-8) .
4. Any party possessing the plaintext request matching `requestDigest` can submit it to the Vault gateway and pass `AllowListBasedAuth.AuthorizeRequest` until the original 48-hour expiry lapses: [2](#0-1) .

func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}

	if time.Now().UTC().Unix() > int64(allowlistedRequest.ExpiryTimestamp) {
		authorizedRequestStr := string(allowlistedRequest.RequestDigest[:])
		r.lggr.Debugw("AllowListBasedAuth authorization expired", "method", req.Method, "requestID", req.ID, "authorizedRequestStr", authorizedRequestStr, "expiryTimestamp", allowlistedRequest.ExpiryTimestamp)
		return nil, errors.New("request authorization expired")
	}

	digestKey := string(allowlistedRequest.RequestDigest[:])
	r.lggr.Debugw("AllowListBasedAuth authorization succeeded", "method", req.Method, "requestID", req.ID, "authorizedRequestStr", digestKey, "owner", allowlistedRequest.Owner.Hex(), "expiryTimestamp", allowlistedRequest.ExpiryTimestamp)
	return &AuthResult{
		workflowOwner: allowlistedRequest.Owner.Hex(),
		digest:        digestKey,
		expiresAt:     int64(allowlistedRequest.ExpiryTimestamp),
	}, nil

// UserAllowlistRequest allows a user to request allowlist status
type UserAllowlistRequest struct{}

type UserAllowlistRequestInput struct {
	ExpiryTimestamp uint32 `json:"expiryTimestamp"`
	RequestDigest   string `json:"requestDigest"`

	ChainSelector             uint64                   `json:"chainSelector"`             // Chain Selector
	MCMSConfig                *crecontracts.MCMSConfig `json:"mcmsConfig,omitempty"`      // MCMS configuration
	WorkflowRegistryQualifier string                   `json:"workflowRegistryQualifier"` // Qualifier to identify the specific workflow registry
}

func (u UserAllowlistRequest) VerifyPreconditions(e cldf.Environment, config UserAllowlistRequestInput) error {
	if config.ExpiryTimestamp == 0 {
		return errors.New("expiry timestamp cannot be zero")
	}
	if len(config.RequestDigest) == 0 {
		return errors.New("request digest cannot be empty")
	}
	return nil
}
