### Title
Attacker-controlled `version` high-bit lets a normal P2P-submitted block hijack the shadow-block signer-weight bypass in `verify_signer_signatures` - (File: `stackslib/src/chainstate/nakamoto/mod.rs`, `stackslib/src/chainstate/nakamoto/shadow.rs`)

### Summary
`NakamotoBlockHeader::verify_signer_signatures` trusts `self.is_shadow_block()` — a check on a single bit (`version & 0x80`) of an attacker-fully-controlled header field — to unconditionally short-circuit and return the full reward-set signing weight via `get_shadow_signer_weight`, skipping the entire signature-recovery/threshold loop. The intended safety net (that shadow blocks may only enter chainstate through `NakamotoStagingBlocksTx::add_shadow_block`, which enforces tenure-emptiness invariants) is not re-checked at the point where `verify_signer_signatures` is invoked for blocks obtained through the ordinary storage path.

### Finding Description
The broken equality: `total_weight_signed` returned by `verify_signer_signatures` should equal the weight actually backed by recovered, valid signer signatures. Instead, for any header where `version & 0x80 != 0`: [1](#0-0) 

calls [2](#0-1) 

which returns the **sum of all signer weights**, regardless of `self.signer_signature` contents. `is_shadow_block()`/`is_shadow_block_version()` is nothing more than a bitmask test on a header field the block producer fully controls: [3](#0-2) 

Header-version validation (`version_includes_problematic_txs`, `expected_version_for_epoch`) explicitly masks off this high bit and treats it as orthogonal to the epoch/version classification, and this is confirmed by tests showing a "shadow v1 header is valid in Epoch 4.0" and a "shadow v0 header is valid before Epoch 4.0" — i.e., the bit is structurally accepted independent of how the block arrived: [4](#0-3) 

The only place that enforces that a shadow-flagged block is legitimately shadow-sourced is the dedicated ingestion function `add_shadow_block`, which checks that the tenure is empty or already a recognized shadow tenure before storing with a hardcoded `signing_weight = u32::MAX`: [5](#0-4) [6](#0-5) 

However, the generic block-acceptance code path that computes `signing_weight` from `verify_signer_signatures` and then stores it via `store_block_if_better` with a caller-supplied `obtain_method` does not perform any equivalent cross-check between `obtain_method` and `self.is_shadow_block()`: [7](#0-6) 

Because this function accepts a generic `NakamotoBlockObtainMethod` (used for normally downloaded/pushed/uploaded blocks as well as shadow-inserted ones), a block that arrives over the ordinary relay/storage path but whose `version` byte has bit `0x80` set will be routed into the `is_shadow_block()` branch of `verify_signer_signatures` and reported as fully signed, even with zero real `signer_signature` entries.

Additionally, the shadow-specific burnchain validator explicitly skips miner-signature and VRF-proof verification ("unlike normal blocks, we do not need to verify the VRF proof or miner signature"), further relaxing validation for any block dispatched down this path purely because of the version bit: [8](#0-7) 

`check_tenure_tx` (shared by both paths) still requires the block's `consensus_hash` to correspond to a real, won tenure, which limits this to an attacker who is a legitimate single miner for that tenure — matching the specified threat model (single miner, no majority stake needed).

### Impact Explanation
An attacker who is a legitimate single miner for a tenure can craft a block with `header.version |= 0x80` and an empty/insufficient `signer_signature` vector. If this block reaches the generic accept/store path (not `add_shadow_block`), `verify_signer_signatures` reports full reward-set weight, `store_block_if_better` will treat it as fully signed and can select it as the best block for that tenure/height over a legitimately (properly threshold-)signed competing block. This can cause honest nodes to accept a block that never actually cleared the 70% signer-weight threshold — an "invalid block accepted" condition, and can lead to tip disagreement between nodes/signers that reject the block via the proper signer protocol versus a node's local chainstate that stored it through this path. This matches the Critical category ("an invalid block accepted... network-wide").

### Likelihood Explanation
Preconditions: attacker holds a single miner slot (able to win a sortition and legitimately construct a tenure's block), fully controls the wire-format `version` byte of their own header, and needs no signer key material, no majority stake, and no additional privileged role. The main open question — and the primary source of uncertainty in this finding — is whether the specific code path that stores network/relay-obtained blocks (the function at `mod.rs:2917-2937`) is actually reachable with `obtain_method != Shadow` from `stackslib/src/net/relay.rs` for attacker-supplied blocks, and whether an earlier burnchain-validation dispatch (not fully inspected here) independently rejects a shadow-flagged header for blocks not inserted via `add_shadow_block`. This could not be fully confirmed within the available context/tool budget; the `net/relay.rs` shadow-related call sites were located but not fully read.

### Recommendation
Enforce an explicit, non-bypassable invariant at every point that reads `is_shadow_block()` for consensus-weight purposes: a block must only be treated as a shadow block if it was stored via `NakamotoBlockObtainMethod::Shadow` (i.e., through `add_shadow_block`). Concretely, in the generic accept/store function, reject any block where `block.is_shadow_block() != matches!(obtain_method, NakamotoBlockObtainMethod::Shadow)` before calling `verify_signer_signatures`, and/or have `verify_signer_signatures` take an explicit `is_shadow_insertion: bool` parameter derived from the caller's storage context rather than trusting the header bit alone.

### Proof of Concept
Rust integration test plan (two-node/local chainstate harness):
1. Set up a chainstate with a reward set of several signers with weights summing to `W`, threshold `0.7 * W`.
2. Construct a normal (non-shadow-sourced) `NakamotoBlock` for a tenure the attacker/miner legitimately won: valid `consensus_hash`, valid tenure-change tx, but `signer_signature = vec![]` (or signatures summing to less than the threshold).
3. Set `block.header.version |= 0x80`.
4. Submit the block through the ordinary network ingestion/storage path (i.e., whatever function processes blocks received via P2P — NOT `add_shadow_block`), with `obtain_method` set to `Downloaded`/`Pushed`.
5. Assert on both sides of the equality:
   - Actual real signer weight backing the block (sum of weights of signers whose signatures are present and valid) = `0` (or below threshold).
   - `signing_weight` recorded by the store/accept function (derived from `verify_signer_signatures`) = `W` (full reward-set weight).
6. Assert these two values differ, and assert the block is nonetheless accepted/stored as "better" than a properly, fully-signed competing block — demonstrating the invalid-block-accepted condition.
7. If the harness instead rejects the block (e.g., because an obtain-method/shadow-bit cross-check exists upstream that this investigation could not locate), the test should assert rejection with an error identifying that check, which would falsify this finding.

    /// Get the signing weight of a shadow block
    pub fn get_shadow_signer_weight(&self, reward_set: &RewardSet) -> Result<u32, Error> {
        let Some(signers) = reward_set.signers() else {
            return Err(ChainstateError::InvalidStacksBlock(
                "No signers in the reward set".to_string(),
            ));
        };
        let shadow_weight = signers
            .iter()
            .fold(0u32, |acc, signer| acc.saturating_add(signer.weight));

        Ok(shadow_weight)
    }
