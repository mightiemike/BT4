### Title
LDAP `CreateSession` does not reject empty passwords before `conn.Bind`, enabling authentication bypass via RFC4513 "unauthenticated bind" - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` forwards `sr.Password` directly to `conn.Bind(searchBaseDN, sr.Password)` with no check that the password is non-empty. Per RFC 4513 §5.1.2, many LDAP servers treat a simple bind with a zero-length password as an "unauthenticated bind" and return a success result regardless of whether the supplied DN/user actually exists with that identity being validated, which the code then treats as a fully authenticated login for the target user's real role.

### Finding Description
The login flow is: `core/web/sessions_controller.go` `SessionsController.Create` binds the raw JSON body into a `clsessions.SessionRequest` (`sr.Email`, `sr.Password`) with no validation that `sr.Password` is non-empty [1](#0-0) , then calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`, which for LDAP-configured deployments dispatches to `ldapAuthenticator.CreateSession`.

Inside `CreateSession`, the code builds the bind DN from the attacker-controlled email and calls `conn.Bind(searchBaseDN, sr.Password)` unconditionally, with no guard for `sr.Password == ""`: [2](#0-1) 

If `conn.Bind` returns `nil` (no error), the code proceeds to call `l.FindUser(ctx, escapedEmail)` to fetch the target user's real assigned role from the LDAP group memberships, and on success writes a new row into `ldap_sessions` with that user's real role and returns a valid session ID: [3](#0-2) 

Per RFC 4513 §5.1.2, a simple bind request with a non-empty DN but a zero-length password is defined as an "unauthenticated bind"; many directory server configurations (this is a well-documented, historically common misconfiguration/default behavior in several LDAP implementations) will process such a bind as a *successful* result without validating that the caller actually knows the target account's password. The `go-ldap` client library used here (`github.com/go-ldap/ldap/v3`) does not special-case this — it is the responsibility of application code to reject empty-password binds, which this code does not do. No other check (role check, replay check, rate limit, or password-length validation) exists between the HTTP request and the `conn.Bind` call to block this.

### Impact Explanation
If the upstream LDAP server permits unauthenticated binds (a real, non-hypothetical server behavior/config governed by RFC 4513, not by this codebase), an unprivileged attacker who merely knows or guesses a valid user's email/DN (which may be discoverable, e.g. admin emails) can submit `POST /sessions` with `password: ""` and receive a fully valid `ldap_sessions` session cookie carrying that user's real role (potentially `UserRoleAdmin`). This is a full authentication bypass and privilege escalation to admin, with resulting node compromise: workflow/job creation, spec management, and secret access available to Admin-role sessions.

### Likelihood Explanation
Exploitability depends entirely on the LDAP server-side configuration allowing unauthenticated/anonymous binds for non-empty-DN + empty-password requests. This is not guaranteed for every deployment (e.g. Active Directory rejects it by default in many configurations), but it is a documented, non-trivial fraction of LDAP deployments, and Chainlink's code provides zero application-layer defense-in-depth against it — the fix is a one-line check that any conforming application to this attack class implements. Given the sensitivity of node admin access, this is a legitimate, low-effort-if-triggerable, high-impact gap.

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`), reject the bind attempt immediately if `sr.Password == ""` (or below a minimum length) before ever calling `conn.Bind`, treating it the same as an authentication failure and falling through to `localLoginFallback`/error path. This closes the RFC4513 unauthenticated-bind bypass regardless of server-side configuration.

### Proof of Concept
Unit test in `core/sessions/ldapauth/ldap_test.go` using the existing `LDAPClient`/`LDAPConn` mocks:
1. Configure a mock `LDAPConn` whose `Bind(dn, password)` returns `nil` (success) whenever `password == ""`, mimicking an LDAP server that performs an RFC4513 unauthenticated bind for the target DN.
2. Call `ldapAuthenticator.CreateSession(ctx, sessions.SessionRequest{Email: "victim-admin@example.com", Password: ""})`.
3. Assert that:
   - The mock `Bind` is never invoked with an empty password (expected fix behavior), or
   - Alternatively, assert that `CreateSession` returns an error and does **not** insert a row into `ldap_sessions`, even when the mocked `Bind` returns success for an empty password.
4. Currently (pre-fix), this test would show `CreateSession` returning a valid, non-empty session ID for the admin email despite `sr.Password == ""`, confirming the bypass.
