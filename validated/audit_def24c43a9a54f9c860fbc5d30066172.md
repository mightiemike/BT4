### Title
Adversarial account-size selection defeats `max_resulting_storages` bound in ancient packing, causing disproportionate storage-write and I/O cost per packing pass - (File: `accounts-db/src/ancient_append_vecs.rs`)

### Summary
`PackedAncientStorage::pack()` uses a simple "next-fit" style greedy bin-packing loop that never revisits or reorders account groups once it advances past them, while the pre-pack admission control (`AncientSlotInfos::truncate_to_max_storages` / `filter_by_smallest_capacity`) estimates the number of resulting storages using only `ceil(total_alive_bytes / ideal_storage_size)`, i.e. it assumes perfect packing efficiency. An unprivileged attacker who sizes many ancient-eligible slots' alive bytes to just over half of `ideal_storage_size` can make the real greedy packer produce close to 2x the number of storages the estimate predicted, silently exceeding the intended `max_resulting_storages` cap and forcing more storage-write operations per pass than the tuning knob was designed to bound.

### Finding Description
The admission-control estimate is computed in `AncientSlotInfos::truncate_to_max_storages`: [1](#0-0) 

This only checks `cumulative_bytes.div_ceil(ideal_storage_size)` against `tuning.max_resulting_storages`, which is a lower bound on the number of storages that would result from an *optimal* bin packing, not the number the actual algorithm will produce.

The actual packer, `PackedAncientStorage::pack`, walks each `AliveAccounts` group (one per ancient slot) in order and only fills the "current" output storage; once a group's remaining bytes don't fit, it seals the current storage and starts fresh, without ever going back to combine leftover space with a later group: [2](#0-1) 

This is a classic "Next-Fit" bin-packing strategy, whose textbook worst case produces up to ~2x the optimal number of bins when item sizes are adversarially chosen (e.g., each item/group sized just over `ideal_size/2`, so no two groups ever combine). Because an attacker fully controls account data sizes (and thus each slot's total alive bytes, via `AppendVec::calculate_stored_size`), they can craft many slots whose alive-byte total is `ideal_storage_size/2 + 1` each. The admission-control estimate divides this by `ideal_storage_size`, admitting roughly `2 * max_resulting_storages` such slots into a single packing pass (since `ceil(N*(ideal/2+1) / ideal) <= max_resulting_storages` allows `N ~ 2 * max_resulting_storages`). The real greedy pack then produces close to `N` storages (near 1 storage per slot, because pairs never combine), i.e. roughly double the intended `max_resulting_storages`.

The only post-pack safety check in `combine_ancient_slots_packed_internal` is: [3](#0-2) 

This compares `pack.len()` against `accounts_to_combine.target_slots_sorted.len()` (the number of input slots being combined), not against `tuning.max_resulting_storages`. In the pure one-ref case, `pack.len()` is bounded above by the number of input `AliveAccounts` groups, which equals `target_slots_sorted.len()`, so this guard can never trigger in the pathological scenario described — the packer proceeds to actually write out all the excess storages via `write_packed_storages`, defeating the stated purpose of the tuning knob ("limit the max # of output storages to prevent packing from running too long", per the comment at `PackedAncientStorageTuning::max_resulting_storages`, line 51-52).

### Impact Explanation
This causes the ancient-packing pass invoked from `combine_ancient_slots_packed` (fixed `max_resulting_storages: 10`) to actually write up to ~2x as many resulting storages as intended, and to perform the expensive `get_unique_accounts_from_storage_for_combining_ancient_slots` scan over more slots than the safety limit was meant to admit. Since this pass runs periodically from the accounts background service, an attacker who keeps producing newly-ancient slots with these pathological byte sizes forces the validator to repeat this inflated-cost packing pass indefinitely, at a cost proportional to roughly double what the `max_resulting_storages` bound was designed to cap, for the price of ordinary account creation/rent. This falls into the "disproportionate storage and CPU cost relative to fees paid" category rather than a correctness/consensus bug — no stale reads, no balance/hash divergence, and no panic were found; the guard simply fails to enforce its own resource-cost invariant.

### Likelihood Explanation
The attacker requires no privileges: only the ability to create accounts with chosen data sizes and to let them age into ancient slots (a normal, unprivileged, repeatable operation). Precisely hitting `ideal_storage_size/2 + 1`-sized slot totals across many slots is straightforward since `get_ancient_append_vec_capacity()` and `AppendVec::calculate_stored_size` are both public/derivable, making the attack mechanically simple to reproduce, though it requires patience to age enough slots into "ancient" status and consistent effort to keep re-triggering it as new ancient slots are produced.

### Recommendation
Enforce `max_resulting_storages` as a hard cap on the actual output of `PackedAncientStorage::pack`, not just as an approximate pre-filter on the sum of alive bytes. For example, after computing `pack`, compare `pack.len()` directly against `tuning.max_resulting_storages` (in addition to `target_slots_sorted.len()`) and abort/retry with a smaller slot batch if exceeded. Alternatively, replace the "next-fit" packer with a decreasing best-fit/first-fit strategy that reorders groups by size to bound fragmentation, or size the pre-pack admission estimate more conservatively (e.g., `2 * ceil(total_bytes / ideal_size)`) to account for the worst-case fragmentation of the current algorithm.

### Proof of Concept
Rust unit test (add to `accounts-db/src/ancient_append_vecs.rs` test module, alongside `test_pack_ancient_storages_varying`):
```rust
#[test]
fn test_pack_ancient_storages_pathological_fragmentation_exceeds_max_resulting_storages() {
    // Craft N slots, each with total alive bytes = ideal_size/2 + 1,
    // so no two slots' accounts can be combined into one output storage.
    let ideal_size: u64 = 10_000;
    let per_slot_bytes = ideal_size / 2 + 1;
    let max_resulting_storages = 10u64;

    // N chosen so ceil(N*per_slot_bytes / ideal_size) <= max_resulting_storages,
    // i.e. admission control would allow this batch through.
    let num_slots = ((max_resulting_storages * ideal_size) / per_slot_bytes) as usize; // ~ 2 * max_resulting_storages

    let (db, storages, slots, _infos) = get_sample_storages(num_slots, Some(per_slot_bytes as usize));
    let original_results = storages
        .iter()
        .map(|store| db.get_unique_accounts_from_storage(store))
        .collect::<Vec<_>>();
    let slots_vec = slots.collect::<Vec<_>>();
    let accounts_to_combine = original_results
        .iter()
        .zip(slots_vec.iter().cloned())
        .map(|(accounts, slot)| AliveAccounts {
            accounts: accounts.stored_accounts.iter().collect::<Vec<_>>(),
            bytes: per_slot_bytes as usize,
            slot,
        })
        .collect::<Vec<_>>();

    // sanity: admission estimate would allow this within max_resulting_storages
    let total_bytes: usize = accounts_to_combine.iter().map(|a| a.bytes).sum();
    let estimated_storages = (total_bytes as u64).div_ceil(ideal_size);
    assert!(estimated_storages <= max_resulting_storages);

    let result = PackedAncientStorage::pack(
        accounts_to_combine.iter(),
        NonZeroU64::new(ideal_size).unwrap(),
    );

    // Assert the real packer produces more storages than max_resulting_storages,
    // demonstrating the estimate/guard is bypassed.
    assert!(
        result.len() as u64 > max_resulting_storages,
        "expected pathological packing to exceed max_resulting_storages ({}), got {}",
        max_resulting_storages,
        result.len()
    );
}
```
Expected result: the assertion passes, showing `PackedAncientStorage::pack` produces more resulting storages than `max_resulting_storages`, confirming the admission-control estimate in `truncate_to_max_storages` does not bound the actual packer output for adversarially-sized accounts.
