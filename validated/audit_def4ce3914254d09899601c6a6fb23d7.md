### Title
Unchecked slice indexing in `NestedFeltCounts::new_inner` causes out-of-bounds panic/DoS on malformed CASM bytecode segment lengths - (File: crates/blockifier/src/execution/contract_class.rs)

### Summary
`NestedFeltCounts::new_inner`, used when converting a `VersionedCasm` (the compiled Cairo1 class produced for a declared contract) into `CompiledClassV1`, indexes directly into the bytecode slice based on attacker/compiler-influenced segment length values with no bounds check. This mirrors the CVE-2018-11377 bug class (crafted input driving an unchecked buffer index in an opcode/segment analyzer, causing an out-of-bounds read and crash) but here the sink is a Rust slice index, so the effect is a panic (process abort) rather than memory corruption.

### Finding Description
`get_bytecode_segment_lengths()` on a `CasmContractClass` returns a `NestedIntList` describing how the class bytecode is split into segments (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:199-204`), and that structure is later turned into `NestedFeltCounts` for Blake2 hash-cost estimation: [1](#0-0) 

Specifically, for a `NestedIntList::Leaf(len)`, the code does: [2](#0-1) 
`bytecode[..*len]` — if `len` exceeds the remaining bytecode slice length, this is an out-of-bounds slice operation that panics ("range end index … out of range for slice of length N"), and similarly `bytecode[total_felt_count..]` can panic if `total_felt_count` exceeds `bytecode.len()`.

This function is invoked from `TryFrom<VersionedCasm> for CompiledClassV1`, which is exercised whenever a class is loaded/compiled for execution: [3](#0-2) 

Notably, the analogous code path used inside the Starknet OS hint system (`create_bytecode_segment_structure` / `create_bytecode_segment_structure_inner`) explicitly validates that the computed total length matches the bytecode length and returns a graceful `OsHintError::AssertionFailed` instead of panicking: [4](#0-3) 

The blockifier-side `NestedFeltCounts::new`/`new_inner` has no equivalent guard before slicing — it only asserts *after* the fact that `consumed_felts == bytecode.len()` (`crates/blockifier/src/execution/contract_class.rs:156-159`), which is too late if an intermediate `Leaf` length already caused an out-of-range slice panic.

### Impact Explanation
If the `bytecode_segment_lengths` metadata attached to a compiled class is ever inconsistent with the actual bytecode length — whether via a Sierra→CASM compiler edge case that miscalculates segment boundaries, or via any code path that constructs a `CasmContractClass`/`VersionedCasm` with attacker-influenced segment metadata — converting it to `CompiledClassV1` panics instead of returning a `Result` error. In a sequencer process this can crash the executing node/thread, which is a denial-of-service condition consistent with the CVE class (crafted input causing an out-of-bounds access and application crash). Because block execution and state-transition validity depend on consistent handling of declared classes across all honest nodes, an uncaught panic during class loading in the execution path risks halting block production/re-execution rather than being cleanly rejected.

### Likelihood Explanation
Likelihood is limited by the fact that, for classes declared normally, `bytecode_segment_lengths` is derived by the sequencer's own trusted Sierra-to-CASM compiler rather than being a raw field an attacker submits directly in a `DECLARE` transaction. Exploitability therefore hinges on finding (or already having) a Sierra program that triggers a compiler miscalculation of segment lengths — this was not verified against the current `cairo-lang-starknet-classes` compiler version in this codebase, and no direct external-input path setting `bytecode_segment_lengths` to an arbitrary value was found during this investigation. This is a real code-quality/defense-in-depth gap (unlike the OS hint counterpart, blockifier's version can panic on malformed input), but confirming full end-to-end reachability from a single declare transaction requires further analysis of the compiler's segment-length computation, which is outside what index search can verify.

### Recommendation
Make `NestedFeltCounts::new`/`new_inner` fallible (return `Result` instead of panicking), mirroring the defensive check already present in `create_bytecode_segment_structure` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs:261-270`): validate that each `Leaf(len)` does not exceed the remaining bytecode slice before indexing, and propagate an error (e.g. `ProgramError`/`PreExecutionError`) up through `TryFrom<VersionedCasm> for CompiledClassV1` rather than allowing an unguarded slice-index panic to propagate.

### Proof of Concept
Construct a `CasmContractClass` (or a `VersionedCasm`) whose `bytecode` has length `N` but whose `bytecode_segment_lengths` field contains a `NestedIntList::Leaf(len)` with `len > N` (or an inner `Node` whose children's cumulative lengths exceed `N` partway through). Convert it via `CompiledClassV1::try_from((class, sierra_version))` — this calls `NestedFeltCounts::new(&class.get_bytecode_segment_lengths(), &class.bytecode)` (`crates/blockifier/src/execution/contract_class.rs:667-668`), which panics on `bytecode[..*len]` inside `new_inner` (`crates/blockifier/src/execution/contract_class.rs:172`) instead of returning an error.

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

/// Creates the bytecode segment structure from the given bytecode and bytecode segment lengths.
pub(crate) fn create_bytecode_segment_structure(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
) -> Result<BytecodeSegmentNode, OsHintError> {
    let (structure, total_len) =
        create_bytecode_segment_structure_inner(bytecode, bytecode_segment_lengths, 0);
    // Sanity checks.
    if total_len != bytecode.len() {
        return Err(OsHintError::AssertionFailed {
            message: format!(
                "Invalid length bytecode segment structure: {}. Bytecode length: {}.",
                total_len,
                bytecode.len()
            ),
        });
    }

    Ok(structure)
}
