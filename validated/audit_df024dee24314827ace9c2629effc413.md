### Title
Unbounded delegation index list causes linear-scan gas-free state bloat and DoS risk in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
When resource delegation is done through the legacy (non-optimized) code path, `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` grow without any per-account bound, and every subsequent freeze/unfreeze that touches the index must copy and linearly scan the *entire* list, mirroring the TokensFarm `_removeParticipant()` unbounded-array-iteration bug class.

### Finding Description
`FreezeBalanceActuator.delegateResource()` appends a new receiver to `ownerIndexCapsule`'s `toAccountsList` (and correspondingly to `fromAccountsList` on the receiver side) whenever `supportAllowDelegateOptimization()` is `false`: [1](#0-0) 
There is no limit on the number of distinct receiver addresses a single owner account can accumulate in this list — an attacker can call `FreezeBalanceContract` with a tiny `frozen_balance` against many distinct freshly-created receiver addresses, growing `toAccountsList` arbitrarily large (as demonstrated by the test that already builds a 100-entry `toAccountsList`): [2](#0-1) 

Later, when the delegated balance for a receiver drops to zero (via `UnfreezeBalanceActuator`), the code reconstructs the *entire* list into a new `ArrayList`, does an `O(n)` `List.remove(Object)` linear scan/shift, and rewrites the whole capsule back to the store: [3](#0-2) 
`DelegatedResourceAccountIndexCapsule.removeToAccount`/`removeFromAccount` have the same pattern — copy full list, `contains()` scan, `remove()` scan, rewrite: [4](#0-3) 

This is structurally the same defect described in the external report: an on-chain array that is only ever appended to (never bounded, and only lazily shrunk element-by-element), so the cost of a single user-triggered operation (unfreeze) scales linearly with the *total historical size* of the array rather than being O(1) or bounded. Just as `TokensFarm._removeParticipant()` could run out of per-transaction gas as a user's stake list grew, an account that delegates resources to a very large number of distinct receiver addresses forces every subsequent unfreeze/undelegate touching that index to pay for a full list copy + linear scan + full-object rewrite, with `calcFee()` for both `FreezeBalanceActuator` and `UnfreezeBalanceActuator` returning `0`: [5](#0-4) 
i.e., the actual state-write/CPU cost is not charged proportionally to list size, so the attacker does not pay for the resources they consume.

### Impact Explanation
Because this is state-store manipulation rather than TVM bytecode execution, there is no EVM/TVM "out of gas" abort as in the original Solidity bug — instead the impact manifests as: (1) unbounded growth of a protobuf-serialized list stored per account, increasing per-account state size without bound and without proportional resource charge, and (2) linear-time list copy/scan/rewrite cost on every subsequent freeze/unfreeze touching that account's index, which is not billed to the caller. Repeated abuse by one or more accounts could bloat account index objects and slow down block processing (since every full node must perform the same O(n) work deterministically), representing a resource-exhaustion/DoS vector against block-processing latency rather than a fund-theft or consensus-divergence bug.

### Likelihood Explanation
This path is only exercised when `supportAllowDelegateOptimization()` returns `false`, i.e., on chains/genesis configurations where the `ALLOW_DELEGATE_OPTIMIZATION` proposal has not been activated. On networks where this proposal is already enabled (which appears to be the case for TRON mainnet for a long time), the optimized `delegate`/`unDelegate`/`convert` key-based scheme is used instead and this list-growth path is not reachable in normal operation, except through the lazy `convert()` migration of legacy accounts, which itself iterates the full legacy list once. This substantially lowers the practical likelihood for already-optimized deployments, but the code path remains present and reachable for any chain/private network that has not activated the proposal, or during migration.

### Recommendation
- Enforce an explicit maximum number of distinct delegation receivers/senders tracked per account in the legacy `DelegatedResourceAccountIndexCapsule` path, rejecting further `FreezeBalanceContract` delegations to new receivers once the cap is reached.
- Ensure `calcFee()`/energy charges in `FreezeBalanceActuator` and `UnfreezeBalanceActuator` scale with the size of the index list being modified, or otherwise bound the list size so that removal/copy operations remain O(1)/O(log n).
- Consider fully retiring the legacy list-based index format (forcing `supportAllowDelegateOptimization()` to always be true) so the unbounded-list code path can no longer be triggered on any network.

### Proof of Concept
1. On a chain where `ALLOW_DELEGATE_OPTIMIZATION` is not yet activated, have account `A` freeze balance and, in the same or successive `FreezeBalanceContract` transactions, delegate small amounts to `N` distinct freshly generated receiver addresses `R_1 … R_N` (as shown feasible for `N=100` in the actuator's own test) — each call appends one entry to `A`'s `toAccountsList` via `ownerIndexCapsule.addToAccount(...)`. [2](#0-1) 
2. Repeat with larger `N` (e.g., tens of thousands) to grow the list far beyond any typical bound; no validation code rejects this.
3. Trigger an `UnfreezeBalanceContract` for one of the delegations once its lock period ends; `UnfreezeBalanceActuator` will copy the full `toAccountsList`/`fromAccountsList`, perform an `O(N)` scan/removal, and rewrite the whole list back to the store, at a fixed (zero) declared fee. [3](#0-2)

  public void removeFromAccount(ByteString fromAccount) {

      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addToAccounts(toAccount)
        .build();
  }

  public void removeToAccount(ByteString toAccount) {
    if (getToAccountsList().contains(toAccount)) {
      List<ByteString> toList = new ArrayList<>(getToAccountsList());
      toList.remove(toAccount);
      setAllToAccounts(toList);
    }
  }
