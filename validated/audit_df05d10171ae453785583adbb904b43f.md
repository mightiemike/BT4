### Title
Unordered / unsynchronized concurrent token-exchange writes can race and leave a stale offline/online session stored, causing repeated re-authentication failures (DoS of the auth handler) - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts])

### Summary
The `TokenExchangeStrategy.authenticate()` flow (and its equivalents in `shopify-app-express`'s `performTokenExchange` and `shopify-app-react-router`'s `createTokenExchangeStrategy`) performs a "check-then-act" sequence — check whether a stored session is active, and if not, call `api.auth.tokenExchange()` and then `config.sessionStorage.storeSession()` — with no locking, versioning, or ordering guarantee between the check and the write, and no de-duplication of the exchange+store step itself (only the `afterAuth` hook is protected against duplicate execution via `IdempotentPromiseHandler`). This mirrors the `PermitC` "unordered nonces" bug class: multiple valid, independently-signed tokens (Shopify session tokens/JWTs, each individually valid within their ~1 minute validity window) can be exchanged concurrently, and the order in which their `storeSession()` calls complete — not the order they were issued or intended to apply — determines which access token ends up persisted.

### Finding Description
In `authenticate()`, the "is session active" check and the write are not atomic: [1](#0-0) 

The offline (and optionally online) token exchange results are persisted via independent, unsynchronized `storeSession` calls: [2](#0-1) 

The same unsynchronized pattern exists in `shopify-app-express`'s middleware: [3](#0-2) 

and in `shopify-app-react-router`: [4](#0-3) 

Only the `afterAuth` side effect is explicitly protected against concurrent re-execution using `IdempotentPromiseHandler`, keyed on the raw `sessionToken` string: [5](#0-4) [6](#0-5) 

This shows the maintainers were aware that concurrent calls with re-usable/valid tokens are a real risk for this handler, but the mitigation was applied only to the `afterAuth` hook — not to the token-exchange-and-store step itself, nor to the initial "no active session" race window. Because `decodeSessionToken` only validates signature/`exp`/`nbf`/`aud` and has no single-use (`jti`) tracking, a still-valid session token can legitimately be presented to the endpoint multiple times concurrently (e.g., multiple embedded-app iframe loads, App Bridge retries, or a client re-issuing the request during network flakiness), each triggering an independent `exchangeToken` + `storeSession` pair whose completion order is not guaranteed to match request order.

### Impact Explanation
If two (or more) concurrent token-exchange flows race, whichever `storeSession()` call resolves last wins, regardless of which access token is actually the most recent/most privileged one from Shopify's perspective. Consequences:
- A newer, correctly-scoped offline/online access token can be overwritten by a stale one from a request that started earlier but finished later, leaving the app's persisted session unusable and forcing the admin handler to keep re-entering the "No valid session found" branch — a denial-of-service loop against the auth handler for that shop/user.
- In `useOnlineTokens` configurations, the offline and online `storeSession` calls run back-to-back without transactional guarantees; a slow/failed offline store interleaved with a fast online store (or vice versa, depending on custom `SessionStorage` implementations) can leave the storage in an inconsistent state (e.g., online session present without the offline session it should depend on).

### Likelihood Explanation
Exploitability requires the ability to trigger multiple concurrent authenticate requests with valid (or overlapping-validity) session tokens against the same shop — achievable by an ordinary merchant/user's browser (e.g., duplicate iframe loads, App Bridge retry behavior, flaky network causing client-side retries) or by a malicious script running in an adjacent frame that can read/replay a session token within its short validity window. No privileged access or leaked long-lived secret is required, only observation/replay of a short-lived, otherwise-valid bearer JWT plus request-timing manipulation, which is consistent with the "MEV/race condition via unordered execution" bug class from the source report.

### Recommendation
- Serialize the "check-then-exchange-then-store" sequence per session id (e.g., using the same `IdempotentPromiseHandler`-style mutual exclusion already used for `afterAuth`, keyed by the resolved offline/online session id rather than the raw token) so concurrent requests for the same shop/user converge on a single exchange+store operation.
- Have `SessionStorage.storeSession` implementations (or a wrapper around them) reject/ignore writes for a session id when a newer session (by `exp`/issued time) is already stored, similar to enforcing a strictly increasing "nonce"/timestamp ordering rather than accepting last-write-wins.
- Consider tracking used `jti` values from `decodeSessionToken` payloads for the token-exchange endpoint to prevent the same token from concurrently starting more than one exchange.

### Proof of Concept
1. A merchant's embedded app is opened in two frames/tabs (or a malicious/adjacent script captures a session token via a shared page and races it), each holding a still-valid App Bridge session token for the same shop within its validity window.
2. Both requests hit the admin endpoint concurrently. Both see `session.isActive(...)` as false (no session yet, or one nearing `WITHIN_MILLISECONDS_OF_EXPIRY`), entering the "No valid session found" branch in `authenticate()`.
3. Both independently call `api.auth.tokenExchange` and then `config.sessionStorage.storeSession(offlineSession)` (and `onlineSession` if `useOnlineTokens`).
4. Because there is no lock/ordering guarantee, request B's `storeSession` can complete after request A's, persisting whichever token happened to finish last — independent of freshness/correctness — leaving the merchant's stored session in an unpredictable, potentially broken state that repeatedly fails subsequent `session.isActive` checks (DoS of the auth handler).

    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
