## Title
`nep_141_storage_balance_callback`/`address_check_callback` drop `caller_deposit` refund when an external contract returns an unexpected response format - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEP-141/ERC-20 emulation path in the NEAR Wallet Contract attaches a caller's NEAR deposit and promises to refund it if the emulated cross-contract call fails. However, that refund logic is only implemented in `rlp_execute_callback`'s `PromiseResult::Failed` branch. The two upstream callbacks that also consume `caller_deposit` — `address_check_callback` and `nep_141_storage_balance_callback` — silently drop `caller_deposit` and return an `ExecuteResponse::success:false` without ever issuing the refund whenever the called external contract (the address registrar, or an arbitrary NEP-141/target account chosen by the relayer's transaction data) returns data that does not deserialize into the expected type.

### Finding Description
`CallerDeposit` is created in `inner_rlp_execute` to track a non-self caller's attached deposit so it can be refunded if the resulting cross-contract call fails: [1](#0-0) 

The refund is correctly performed in `rlp_execute_callback`, but only for the `PromiseResult::Failed` case: [2](#0-1) 

However, for ERC-20 transfers that require checking whether the receiver is registered with the NEP-141 token (a multi-step promise chain), the intermediate callback `nep_141_storage_balance_callback` also carries `caller_deposit`, but only forwards/refunds it when the promise result is a `PromiseResult::Failed`. If the promise instead *succeeds* but returns a JSON payload that fails to deserialize into `Option<StorageBalance>` (e.g., a non-standard or malicious NEP-141-like contract at `target` — controlled entirely by the transaction data supplied to `rlp_execute`), the function returns immediately with an error response and **never triggers any refund path**: [3](#0-2) 

The same pattern exists in `address_check_callback`, which is exercised for base-token (EOA) transfers to another eth-implicit account (target is again resolved from attacker/relayer-supplied transaction data going through the address registrar). If the registrar's response is `PromiseResult::Successful` but the JSON body is not the expected `Option<AccountId>`, the function returns an error `ExecuteResponse` and drops `caller_deposit` without refunding it: [4](#0-3) 

This is the direct analog of the reported ERC-20 issue: the wallet contract's cross-contract-call handling code hard-codes an assumption about the exact response format/behavior of an external contract (a bool-parity assumption in the original report vs. a `serde_json`-decodable `Option<StorageBalance>`/`Option<AccountId>` assumption here). When a called contract does not conform to that assumption (returns different/unexpected JSON, or is simply not a standard NEP-141/registrar implementation), the code takes an unhandled branch that silently discards value that was supposed to be returned to the original caller, instead of guaranteeing a refund the way the final callback does.

### Impact Explanation
Whenever a user/relayer transaction attaches a NEAR deposit to a wallet-contract-emulated ERC-20 transfer (`rlp_execute` → `ERC20Transfer` path with non-zero `attached_deposit` from a third-party predecessor) or to an EOA base-token transfer requiring an address-registrar lookup, and the target contract responds with any payload that isn't the exact expected shape, the attached deposit becomes permanently stuck in the Wallet Contract account with no code path left to reclaim it (the transaction ends, `has_in_flight_tx` resets to `false`, and `caller_deposit` is dropped). This matches the "permanently frozen funds" impact category, and is directly reachable by an ordinary transaction signer/relayer without any special privilege — they only need to name (or the wallet contract owner need only interact with) a contract that returns a non-conforming success payload for `storage_balance_of` or the registrar's `lookup`.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any non-standard NEP-141-like contract, a contract that changes its `storage_balance_of`/`lookup` response schema, or a malicious contract deliberately crafted to return unexpected but successful JSON, will trigger this path. Because `target` for the ERC-20 transfer emulation is attacker/relayer controlled (the wallet owner signs an Ethereum-style tx specifying the ERC-20 contract to interact with), a malicious or buggy relayer/target can deterministically induce this loss whenever a caller attaches a deposit alongside such a call.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, route every early-return failure branch (including JSON-deserialization failures on `PromiseResult::Successful`) through the same refund logic used in `rlp_execute_callback`'s `PromiseResult::Failed` arm — i.e., always issue `env::promise_batch_create`/`promise_batch_action_transfer` back to `caller_deposit.account_id` before returning the failing `ExecuteResponse`, rather than only doing so for `rlp_execute_callback`'s terminal state.

### Proof of Concept
1. A caller (non-self predecessor) submits an ERC-20 emulated transfer via `rlp_execute` with `target` pointing to a contract implementing `storage_balance_of` but returning a JSON body incompatible with `Option<StorageBalance>` (e.g. returns `{}` or a different schema) on success, while attaching a non-zero NEAR deposit.
2. `inner_rlp_execute` creates `CallerDeposit` (`types.rs:180-191`) and schedules `storage_balance_of` → `nep_141_storage_balance_callback`.
3. The `storage_balance_of` promise resolves as `PromiseResult::Successful` but with a payload that fails `serde_json::from_slice::<Option<StorageBalance>>` (`lib.rs:211-220`).
4. The callback returns `ExecuteResponse{success:false, ...}` immediately; `caller_deposit` is dropped without any refund promise being created, permanently locking the attached deposit in the Wallet Contract account.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
