### Title
Missing deduplication of vote addresses in `VoteWitnessActuator` allows duplicate `Vote` entries in account/votes storage - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
`VoteWitnessActuator`, the actuator executed for a normal (non-TVM) `VoteWitnessContract` broadcast by any account, does not check whether the `votes` list submitted by the caller contains the same `vote_address` more than once. This is directly analogous to the UMA `Registry.registerContract` bug, where an unchecked repeated-address array is written verbatim into per-entity storage, producing duplicate/inconsistent list entries.

### Finding Description
In `VoteWitnessActuator.validate()` [1](#0-0) , the code iterates `contract.getVotesList()` and validates each `Vote` individually (valid address, positive count, existing witness) and sums up vote counts to compare against `tronPower`, but it never verifies that `vote.getVoteAddress()` values are distinct across the list — unlike `AccountPermissionUpdateActuator.checkPermission`, which explicitly does a `.distinct()` check and rejects duplicate key addresses [2](#0-1) .

Because of this gap, a transaction can contain multiple `Vote` entries for the same witness address whose counts sum to no more than the voter's `tronPower`. In `countVoteAccount()` (the `execute()` path), each `Vote` in the contract is appended, unmerged, directly onto both the account and the `VotesCapsule`: [3](#0-2) 

`AccountCapsule.addVotes()` simply appends a new `Vote` entry to the repeated `votes` field with no dedup/merge logic: [4](#0-3) 

`VotesCapsule.addNewVotes()` behaves identically for the `newVotes` list: [5](#0-4) 

This is the same bug class as the UMA report: the "for" loop writes into per-key storage (`account.votes`, `votes.newVotes`) once per array element without deduplicating, leaving duplicated entries for the same key.

Notably, the codebase itself demonstrates awareness that this must be fixed at write time: the TVM-native equivalent `VoteWitnessProcessor.execute()` (used by the `voteWitness` precompiled/native TVM opcode) explicitly builds a `Map<ByteString, Long> voteMap` and merges duplicate witness addresses ("merge vote for same witness") before writing votes, and even removes zero-count votes via the iterator: [6](#0-5) 

The plain transaction-broadcast path (`VoteWitnessActuator`, reachable by any account via `wallet/votewitnessaccount` HTTP or `VoteWitness`/`VoteWitness2` gRPC) lacks this merge step entirely, so it is inconsistent with its own TVM counterpart and allows the account's `votes` repeated field, and the `VotesCapsule.newVotes` repeated field, to contain multiple entries keyed to the same witness address.

### Impact Explanation
While `MaintenanceManager.countVote()` and `Wallet.countVote()` aggregate `oldVotes`/`newVotes` via a `Map<ByteString, Long>` using `containsKey`/`getOrDefault` accumulation [7](#0-6) [8](#0-7) , meaning the final witness vote-count tally sums duplicate entries correctly, other logic that assumes one `Vote` entry per witness per account can be affected:
- `AccountCapsule.getVotesList()` is iterated and re-processed elsewhere (e.g., `UnfreezeBalanceV2Actuator.updateVote`, `UnfreezeBalanceProcessor`) by iterating per-vote and re-emitting a new `Vote` per list entry proportionally scaled to remaining tron power; duplicate entries for the same witness produce multiple separate `Vote` records post-scaling instead of one, growing the list unnecessarily and complicating any code that expects at most one entry per witness address (e.g., reward/withdraw calculations keyed by witness address, `MortgageService`).
- The account's votes list can grow unbounded relative to `MAX_VOTE_NUMBER` semantics being effectively bypassed for per-witness allocation granularity (the count check is on list size, not distinct witnesses), which can be leveraged to bloat on-chain storage (repeated `Vote` protobuf entries) for a fixed resource cost, a mild state-bloat/DoS vector.
- It represents a data-integrity/consistency break between the TVM-native vote path (deduplicating) and the classic actuator path (not deduplicating) for functionally identical voting operations, which is inconsistent behavior a wallet or third-party tool relying on "one vote entry per witness address" invariant could misinterpret.

This does not appear to allow outright double-counting of voting power (the tron-power sum check still holds, and downstream tallying uses map accumulation), so the impact is state inconsistency / bloat rather than direct fund loss or consensus divergence.

### Likelihood Explanation
Any account holding TRX/tron power can submit a `VoteWitnessContract` with duplicate `vote_address` entries via `wallet/votewitnessaccount` (HTTP), or `VoteWitness`/`VoteWitness2` (gRPC), with no privileged role required — unlike the original UMA finding this is fully exploitable by anonymous/unprivileged users. It requires no more code interaction than crafting a transaction with a `VoteWitnessContract.votes` list that repeats the same address.

### Recommendation
In `VoteWitnessActuator.validate()`, reject vote lists containing duplicate `vote_address` entries (mirroring the `.distinct()` check in `AccountPermissionUpdateActuator.checkPermission`), or alternatively merge duplicate entries in `countVoteAccount()` using the same `Map<ByteString, Long>` accumulation pattern already implemented in `VoteWitnessProcessor.execute()`, so the classic actuator path and TVM-native path behave consistently.

### Proof of Concept
1. Freeze balance for `OWNER_ADDRESS` to obtain sufficient `tronPower` (e.g., via `FreezeBalanceContract`), as in `VoteWitnessActuatorTest.getRepeateContract` test helper which already builds a `VoteWitnessContract` with the same `vote_address` repeated N times [9](#0-8) .
2. Submit a `VoteWitnessContract` where `votes` contains two entries both with `vote_address = WITNESS_ADDRESS`, each with `vote_count` such that the sum is ≤ tronPower (e.g., 5 and 5).
3. `actuator.validate()` passes because per-entry checks succeed and the sum (10) ≤ tronPower; no duplicate-address check exists.
4. `actuator.execute()` calls `accountCapsule.addVotes(WITNESS_ADDRESS, 5)` twice, producing two separate `Vote` entries for the same witness in `AccountCapsule.getVotesList()`, and likewise two entries in `VotesCapsule.getNewVotes()`, instead of a single merged `Vote(WITNESS_ADDRESS, 10)` as would be produced by the TVM-native `VoteWitnessProcessor` path.
5. Inspect `dbManager.getAccountStore().get(OWNER_ADDRESS).getVotesList()` to confirm two entries exist for the same `vote_address`, demonstrating the storage inconsistency (list size ≠ distinct witnesses voted for).

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
