### Title
Receipt Size Invariant Bypass via `promise_return` + Post-Validation `output_data_receivers` Mutation — (`runtime/runtime/src/lib.rs`)

### Summary

An unprivileged user can deploy a contract that causes the runtime to emit an action receipt whose borsh-serialized size exceeds `max_receipt_size` (4 MiB). The root cause is that `apply_action_receipt` appends `output_data_receivers` to a returned receipt **after** `validate_receipt(..., NewReceipt)` has already been called on it. The oversized receipt bypasses the size invariant, inflates the `ChunkStateWitness` beyond the intended 17 MiB ceiling, and corrupts the bandwidth scheduler's accounting. This is a non-network-level DoS reachable from ordinary user-submitted transactions. The bug is acknowledged in the codebase as issue #12606 but has no protocol-level fix deployed.

---

### Finding Description

**Invariant broken:** Every receipt emitted by the runtime must satisfy `borsh_size(receipt) <= max_receipt_size` (currently 4,194,304 bytes, set at protocol version 69).

**Root cause — `promise_return` path:**

In `apply_action_receipt` (`runtime/runtime/src/lib.rs`), actions are executed one by one and each newly created receipt is validated immediately:

```rust
if new_result.result.is_ok() {
    if let Err(e) = new_result.new_receipts.iter().try_for_each(|receipt| {
        validate_receipt(
            &apply_state.config.wasm_config.limit_config,
            receipt,
            apply_state.current_protocol_version,
            ValidateReceiptMode::NewReceipt,   // ← size check happens here
        )
    }) { ... }
}
result.merge(new_result)?;
``` [1](#0-0) 

After all actions complete, the runtime handles `output_data_receivers`. When the contract called `promise_return(receipt_index)`, the runtime **mutates** the already-validated receipt by appending the parent receipt's `output_data_receivers` to it:

```rust
if !action_receipt.output_data_receivers().is_empty() {
    if let Ok(ReturnData::ReceiptIndex(receipt_index)) = result.result {
        // Modifying a new receipt instead of sending data
        match result.new_receipts.get_mut(receipt_index as usize)...receipt_mut() {
            ReceiptEnum::Action(new_action_receipt) | ... => new_action_receipt
                .output_data_receivers
                .extend_from_slice(&action_receipt.output_data_receivers()),
            ...

    }
``` [2](#0-1) 

No size re-check is performed after this mutation. The receipt is then forwarded directly to `receipt_sink.forward_or_buffer_receipt`.

**Root cause — `value_return` path:**

When a contract calls `value_return` with data of size `max_length_returned_data` (4 MiB), the runtime creates a `DataReceipt` whose `data` field is 4 MiB. The borsh encoding of the full `Receipt` wrapper adds overhead (predecessor/receiver account IDs, receipt_id, discriminant bytes), pushing the total above `max_receipt_size`. `validate_data_receipt` only checks `data_len <= max_length_returned_data`, not the total receipt size:

```rust
fn validate_data_receipt(limit_config: &LimitConfig, receipt: &DataReceipt)
    -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded { ... });
    }
    Ok(())
}
``` [3](#0-2) 

The `validate_receipt(..., NewReceipt)` size check only applies to `Action`/`PromiseYield` receipts created during action execution; `DataReceipt`s created in the output-data phase at lines 1056–1068 are never passed through `validate_receipt` at all. [4](#0-3) 

**Downstream handling of oversized receipts:**

The codebase acknowledges the bug and applies a workaround in `try_forward`: the actual size is clamped to `max_receipt_size` for the forwarding-limit comparison, so the receipt is not permanently stuck. However, the actual bytes transmitted exceed the granted bandwidth:

```rust

// See https://github.com/near/nearcore/issues/12606
if size > max_receipt_size {
    size = max_receipt_size;   // ← accounting uses clamped value, real bytes are larger
}
``` [5](#0-4) 

Incoming receipts on the receiving shard are validated with `ExistingReceipt` mode, which explicitly skips the size check:

---

### Impact Explanation

1. **ChunkStateWitness inflation**: The `ChunkStateWitness` is designed to stay under 17 MiB. An oversized receipt of ~4 MiB + overhead pushes the witness beyond this ceiling, potentially causing chunk validators to reject the chunk or produce divergent results.

2. **Bandwidth scheduler accounting corruption**: `try_forward` debits `max_receipt_size` bytes from the outgoing limit but transmits more. The bandwidth grant for the `(sender, receiver)` shard link is consumed faster than accounted for, starving legitimate receipts on that link.

3. **Congestion memory accounting**: `buffer_receipt` stores the actual borsh size in `own_congestion_info.receipt_bytes`, but `try_forward` uses the clamped size when decrementing the outgoing limit. This creates an asymmetry that can cause the congestion level's `memory` fraction to diverge from the forwarding budget.

4. **Contract execution flow breakage**: The `max_receipt_size` invariant — a hard protocol limit — is violated on every execution of the affected pattern.

---

### Likelihood Explanation

- **Trigger**: Any unprivileged user can deploy a WASM contract. The `promise_return` path requires a cross-contract call pattern (A calls B, B calls `promise_return(C)` where C is near-max-size). The `value_return` path requires only a single contract call with a large return value.
- **Gas cost**: The attacker pays gas proportional to the receipt size (`new_data_receipt_byte` fee per byte per receiver). At current mainnet rates this is non-trivial but affordable.
- **Reproducibility**: The test `test_max_receipt_size_value_return` and `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` confirm the oversized receipt reaches the network on every run. [8](#0-7) 

---

### Recommendation

**Short term:** After the `output_data_receivers` mutation at `lib.rs:1041–1047`, re-run `validate_receipt(..., NewReceipt)` on the mutated receipt. If it now exceeds `max_receipt_size`, set `new_result.result = Err(ActionErrorKind::NewReceiptValidationError(...))` and roll back, consistent with how other per-action validation failures are handled.

**For the `value_return` / `DataReceipt` path:** Pass newly created `DataReceipt`s through `validate_receipt(..., NewReceipt)` (including the total-receipt-size check) before appending them to `result.new_receipts`.

Both fixes require a protocol upgrade (hardfork) because they change which receipts are accepted as valid outputs of chunk application.

---

### Proof of Concept

```
1. Deploy a contract with two methods:
   - `setup()`: calls `promise_create(self, "large_noop", large_args)` where
     `large_args.len() == max_receipt_size - base_receipt_size`,
     then calls `promise_then(promise_a, self, "callback", ...)`.
     This creates DAG: [A(large_args)] -then-> [B(callback)].

2. Call `setup()`. The runtime:
   a. Validates receipt A (size == max_receipt_size - ε). Passes.
   b. Validates receipt B. Passes.

3. When receipt A executes, the contract calls `promise_return(C)` where C
   is another near-max-size receipt. The runtime:
   a. Validates C (size == max_receipt_size - ε). Passes.
   b. Appends B's output_data_receivers to C. C's size now exceeds max_receipt_size.
   c. No re-validation. C is forwarded.

4. The receiving shard receives C with size > max_receipt_size.
   validate_receipt(..., ExistingReceipt) skips the size check.
   C is executed normally.

5. assert_oversized_receipt_occurred() confirms the invariant was violated.
```
