### Title
Missing max_l2_gas_amount validation for Declare transactions in stateless gateway validator - (File: crates/apollo_gateway/src/stateless_transaction_validator.rs)

### Summary
`StatelessTransactionValidator::validate_resource_bounds` enforces `config.max_l2_gas_amount` as an upper bound on `resource_bounds.l2_gas.max_amount` for Invoke and DeployAccount transactions, but explicitly skips this check for Declare transactions, leaving a `TODO` noting the check should be "considered" in the future. This mirrors exactly the reported bug class: a max-bound constant exists in configuration but is not enforced for one of the reachable code paths.

### Finding Description
In `validate_resource_bounds`:
```rust
// TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.
if let RpcTransaction::Declare(_) = tx {
} else if resource_bounds.l2_gas.max_amount.0 > self.config.max_l2_gas_amount {
    return Err(StatelessTransactionValidatorError::MaxGasAmountTooHigh { ... });
}
``` [1](#0-0) 

For Invoke/DeployAccount transactions the sequencer bounds `max_amount` for the `l2_gas` resource to `self.config.max_l2_gas_amount`, a value that other subsystems (bouncer sizing, mempool priority queue ordering, fee-price estimation) implicitly assume is bounded. Declare transactions, however, are exempted from this check by an explicit branch that does nothing before the comparison for other tx types. This is a direct, unfiltered analog of the reported bug: a documented maximum bound (`max_l2_gas_amount`) exists but a specific transaction path (Declare, submittable by any unprivileged sender) bypasses it entirely, with the code comment itself acknowledging the gap is intentional/deferred, same as the “temporarily removed and will be rewritten in the future” language in the report.

An unprivileged L2 declare-transaction sender can therefore submit a Declare transaction with an arbitrarily large `l2_gas.max_amount` (up to the type's numeric limit), which is accepted by the stateless gateway validator without complaint, whereas the identical field on an Invoke transaction would be rejected.

### Impact Explanation
An unbounded `max_amount` on a Declare transaction's resource bounds propagates into subsequent stages that assume this value is capped by `max_l2_gas_amount`:
- The value feeds `ValidResourceBounds::AllResources(resource_bounds).max_possible_fee(...)`, which is used to gate account balance requirements before admission and to size prioritization/eviction logic in the mempool (fee-escalation percentage comparisons, priority-queue ordering) — see `crates/apollo_mempool_config/src/config.rs` and the resource-bounds validation flag threaded through `mempool_config.static_config.validate_resource_bounds`.
- It also affects declared-class resource accounting downstream (bouncer weights, execution resource estimates) since Declare transactions are treated identically to other v3 transactions elsewhere in resource-bounds handling except for this one skipped check.

Because the check is skipped only for Declare, a malicious but otherwise unprivileged submitter can create Declare transactions whose resource-bound fields diverge from the invariant the rest of the system relies on, creating an inconsistency window that other components were not designed to handle. This can manifest as incorrect fee/balance gating or unexpected admission/priority behavior for Declare transactions specifically, which is a real, reachable correctness gap tied to a documented but unenforced bound — directly analogous to the reported "Absence of Checks for Max TTL" bug class (a max constant defined but not enforced on a specific write path).

I was not able to fully trace, within the available tool budget, the exact numeric overflow or fee-bypass consequence (e.g., whether `max_possible_fee` computation can overflow with an extreme `max_amount`, or whether the bouncer/mempool logic that consumes this unbounded value has its own independent bounding that would neutralize the impact). This residual uncertainty should be validated by a deeper trace of `ValidResourceBounds::max_possible_fee` and bouncer weight computation in `crates/blockifier` before treating the severity as confirmed rather than a strong lead.

### Likelihood Explanation
High reachability: any address able to submit an RPC Declare transaction (unprivileged, no special role) can set an arbitrary `l2_gas.max_amount` today, since the gateway's stateless validator is the sole check exempting Declare from this specific bound. No special preconditions, race conditions, or privileged access are required — a single crafted Declare transaction is sufficient to exercise the gap on every gateway node running the default configuration.

### Recommendation
Remove the special-casing for `RpcTransaction::Declare` in `validate_resource_bounds` and apply the same `max_l2_gas_amount` upper-bound check uniformly to Declare transactions, using either the same `config.max_l2_gas_amount` or a Declare-specific maximum if Declare transactions are expected to require materially more L2 gas budget than Invoke/DeployAccount. Add regression tests mirroring the existing `test_invalid_max_l2_gas_amount` cases for the Declare transaction type to prevent regressions. [2](#0-1) 

### Proof of Concept
1. Submit an RPC Declare (V3) transaction to the gateway with `resource_bounds.l2_gas.max_amount` set to a value far exceeding `StatelessTransactionValidatorConfig::max_l2_gas_amount` (e.g. `u64::MAX` or any value `> max_l2_gas_amount`), while all other fields (e.g. `max_price_per_unit`) remain valid.
2. Observe that `StatelessTransactionValidator::validate` → `validate_resource_bounds` takes the `if let RpcTransaction::Declare(_) = tx {}` branch and returns `Ok(())` without evaluating the `max_amount` bound, unlike the equivalent Invoke transaction which would be rejected with `StatelessTransactionValidatorError::MaxGasAmountTooHigh`. [3](#0-2) 
3. The transaction is accepted into the mempool/gateway pipeline with an unbounded gas-amount resource bound attached to the Declare transaction, violating the invariant maintained for all other transaction types.

    fn validate_resource_bounds(
        &self,
        tx: &RpcTransaction,
    ) -> StatelessTransactionValidatorResult<()> {
        if !self.config.validate_resource_bounds {
            return Ok(());
        }

        let resource_bounds = *tx.resource_bounds();
        // The resource bounds should be positive even without the tip.
        if ValidResourceBounds::AllResources(resource_bounds).max_possible_fee(Tip::ZERO) == Fee(0)
        {
            return Err(StatelessTransactionValidatorError::ZeroResourceBounds { resource_bounds });
        }

        if resource_bounds.l2_gas.max_price_per_unit.0 < self.config.min_gas_price {
            return Err(StatelessTransactionValidatorError::MaxGasPriceTooLow {
                gas_price: resource_bounds.l2_gas.max_price_per_unit,
                min_gas_price: self.config.min_gas_price,
            });
        }

        // TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.
        if let RpcTransaction::Declare(_) = tx {
        } else if resource_bounds.l2_gas.max_amount.0 > self.config.max_l2_gas_amount {
            return Err(StatelessTransactionValidatorError::MaxGasAmountTooHigh {
                gas_amount: resource_bounds.l2_gas.max_amount,
                max_gas_amount: self.config.max_l2_gas_amount,
            });
        }

        Ok(())
    }
