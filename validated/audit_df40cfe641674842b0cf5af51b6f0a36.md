## Title
`replay_on_archive`/`replay-verify` accepts corrupted state, hot-state, and native-position checkpoint roots because `TransactionOutput::ensure_match_transaction_info` never compares them - (File: `types/src/transaction/mod.rs`)

### Summary
The db-tool `replay-verify` / `replay_on_archive` path re-executes archived transactions and calls `TransactionOutput::ensure_match_transaction_info` to confirm the freshly-computed `TransactionOutput` matches the backed-up, ledger-accumulator-authenticated `TransactionInfo`. That function checks status, gas, the write-set hash (`state_change_hash`) and the event root, but does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as the code itself documents. This means a divergence in the committed state Merkle root (main state, hot state, or the new native-position state) between the archived, authenticated ledger and what local execution actually produces is silently accepted by the verifier.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` is the single authenticity check used by the archive replay-verify tool to confirm that re-executing an already-committed, backed-up transaction reproduces the exact result that was accumulator-proved and shipped in the backup: [1](#0-0) 

The function ends with an explicit acknowledgment of the gap: [2](#0-1) 

It never calls `TransactionInfo::state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` for comparison — only `state_change_hash` (the write-set hash) and `event_root_hash` are checked, alongside `status`/`gas_used`. This is invoked directly from `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which is the tool operators run to prove that an archived/backed-up ledger segment is a faithful, non-corrupted replay of consensus-committed execution: [3](#0-2) 

Because `state_checkpoint_hash` is the field that binds a `TransactionInfo` (and therefore the transaction accumulator leaf, and therefore the ledger-info-signed accumulator root) to the actual JellyfishMerkle state root at that version, skipping this comparison means: if a backup/archive segment's `TransactionInfo.state_checkpoint_hash` (or, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state-in-txn-info are enabled, the `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) does not match what local re-execution produces — due to a backup corruption, a bug in incremental hot-state/position-state root computation, or a discrepancy between the write-set that was stored and the state the VM actually produced — `replay-verify` will report success anyway. The write-set hash check alone is not sufficient because the state root also depends on hashing/positioning within the JMT/hot-state tree, which is separate machinery (`storage/aptosdb/src/state_store`, `state-store/hot_state`, and now the new `position_state_summary`/`ProvablePositionStateSummary` machinery seen in `execution/executor/src/workflow/mod.rs` and `execution/executor-types/src/state_checkpoint_output.rs`).

### Impact Explanation
Replay-verify is the mechanism operators and auditors rely on to certify that an archived/backed-up copy of the ledger is a bit-for-bit faithful reproduction of the authenticated chain state — i.e., that no corruption or divergence exists between what consensus committed (proved by the accumulator/ledger-info signatures) and what is stored/served from that archive. Silently ignoring the state root fields means a corrupted or diverged state tree in a backup/archive (which downstream systems, fast-sync bootstrappers, and node operators trust for restore) can pass verification as "correct" even though the actual account/resource state, hot-state root, or (once enabled) the native-position order-book state, is wrong. This is exactly the class of "committed state that differs from the correct VM result" and "authenticated proof context bound to the wrong root" that the state-integrity gate calls out, since state_checkpoint_hash is precisely the field verified elsewhere (e.g., `TransactionInfoWithProof::verify`, state-snapshot restore root checks) as the trusted binding between a ledger version and its Merkle root.

### Likelihood Explanation
This is not attacker-triggerable on a live consensus/mainnet node in the sense of an unprivileged network attack — it requires an existing divergence between a backup archive's write-sets/txn-infos and true execution (e.g. backup corruption, a state-root computation bug introduced by the new hot-state/position-state features, or bit-rot), which is a low-but-nonzero real-world event for archive/backup pipelines. The severity of not detecting it, given operators depend on `replay-verify` as the last line of defense for exactly this class of problem, keeps this Medium/High rather than purely theoretical; likelihood of the *check itself* being silently absent is 100% (it's in the shipped code, not a hypothetical), the residual likelihood is in a real archive actually diverging on those hashes and the verifier being relied upon to catch it.

### Recommendation
Extend `ensure_match_transaction_info` to compute the state-checkpoint hash of the resulting state and compare it against `txn_info.state_checkpoint_hash()`, and, if `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are present on the expected `TransactionInfo`, verify those as well (gated appropriately by whichever executor context has access to the computed checkpoint hashes at that point in the pipeline). At minimum, `replay_on_archive`'s `execute_and_verify` should independently re-derive and check these checkpoint hashes for state-checkpoint transactions before reporting a chunk as verified, and the TODO comment should be resolved before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled in production, as the comment itself warns.

### Proof of Concept
Not exploitable via a standalone runnable PoC without an actual diverging backup, since the bug is an omission in a verification comparison rather than an attacker-reachable state transition. Conceptually: 1) take any archived chunk and its `TransactionInfo`, 2) flip `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) to an arbitrary wrong value while leaving `state_change_hash`/`event_root_hash`/`status`/`gas_used` untouched, 3) run `replay_on_archive`'s `execute_and_verify` (or `aptos-debugger`'s equivalent path calling `ensure_match_transaction_info`) against the real write-set/events; the call returns `Ok(())` despite the state root mismatch, because the comparison never inspects those fields — confirmed by direct code inspection of the function body at `types/src/transaction/mod.rs:2139-2203`.

**Note on completeness:** I was not able to fully trace whether any *other* independent state-root check exists elsewhere in the `replay_on_archive`/`db-tool` pipeline that might compensate for this gap (e.g., a separate JMT root recomputation step outside of `ensure_match_transaction_info`); the code and its own inline comment strongly suggest no such compensating check exists today, but a full trace of every call site of `AptosVMBlockExecutor::execute_block`'s output in the backup/replay tools would be needed to rule this out with certainty.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
