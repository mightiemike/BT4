### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash validation, letting replay-verify tooling accept a diverged state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by the chunk-executor's `verify_execution` path, e.g. `db-tool`'s `replay_on_archive`/replay-verify tooling) checks transaction status, gas used, write-set hash, and event root hash against the `TransactionInfo`, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is acknowledged in-code by a `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  is the function used by `ChunkExecutor::verify_execution` (called from the replay/verify tooling path) to confirm that locally-recomputed transaction output matches the persisted/authenticated `TransactionInfo`: [2](#0-1) 

The function validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

But it explicitly skips the checkpoint-hash fields, as stated in its own comment: [3](#0-2) 

Meanwhile, `TransactionInfo` (V1) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as authenticated fields that are supposed to bind the accumulator leaf to the actual JMT/position-state root at that version [4](#0-3) . These hashes are the ones normally reconciled against locally computed roots in `update_ledger` via `known_state_checkpoints` / `known_position_state_checkpoints` passed into `DoStateCheckpoint::run()` [5](#0-4) , but `verify_execution`'s per-transaction comparator (`ensure_match_transaction_info`) is a separate, weaker check that does not perform this reconciliation for the state/hot-state/position checkpoint hashes.

### Impact Explanation
If the locally-recomputed state (JMT) root, hot-state root, or position-state root diverges from what is committed in the authenticated `TransactionInfo` (e.g., due to a bug in state-merge logic, or a "trading-native" position-state computation bug gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), the `verify_execution`/replay-verify path — whose entire purpose is to catch exactly this kind of divergence — will report success. This is an authenticated-proof-integrity gap: replay/verify tooling used to attest correctness of historical execution (`db-tool`'s `replay_on_archive`) can silently pass over a wrong committed state root, masking a hard-fork-class state divergence instead of flagging it. This matches the "Wrong ... state proof accepted as valid" / "Hard-fork-only divergence during ... replay" categories in scope.

### Likelihood Explanation
The gap is real and unconditional in `ensure_match_transaction_info` today (it never checks these three hashes, regardless of feature flags), but the *practical* trigger — an actual state root divergence occurring during transaction execution — requires a separate bug (e.g., in the yet-unshipped `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`hot_state_root_in_txn_info` computation) to exist. On its own, the missing check is a verification/detection gap in tooling, not by itself a way to corrupt consensus-committed state (the normal commit path in `update_ledger` still reconciles `known_state_checkpoints`/`known_position_state_checkpoints` against `DoStateCheckpoint`). Its independent, exploitable impact is therefore limited to weakening the replay-verify safety net rather than directly corrupting mainnet state.

### Recommendation
Extend `ensure_match_transaction_info` to also assert `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present), and `position_state_checkpoint_hash` (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`hot_state_root_in_txn_info` is enabled) against locally recomputed values, exactly as the code's own `TODO(trading-native)` comment specifies, before those features are turned on in production.

### Proof of Concept
Not applicable as an end-to-end mainnet exploit — the finding is a code-level detection gap: `ensure_match_transaction_info` at [6](#0-5)  returns `Ok(())` without comparing `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` to any locally recomputed value, which can be confirmed purely by reading the function body and its own TODO comment — no additional local root-cause bug that would corrupt the checkpoint hash itself was found in the explored code.

**Caveat:** I could not fully trace whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`hot_state_root_in_txn_info` are currently enabled on mainnet or gated behind an unshipped feature, which materially affects real-world likelihood; this should be verified before treating this as high/critical rather than a hardening/tooling issue.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
