### Title
Missing Self-Recipient Check in `redeem` Lets a User Send Underlying Back to the Vault, Corrupting the `assets` Accounting Variable - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`redeem` in the Zest v0 vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) lets a caller pass an arbitrary `recipient` principal without checking whether it equals the vault contract itself. `transfer` in the same file explicitly guards against this ( `(asserts! (not (is-eq current-contract to)) ERR-TOKENIZED-VAULT-PRECONDITIONS)` ), but `redeem` has no equivalent guard. If `recipient` is set to the vault's own contract address, the underlying asset never actually leaves the vault's balance, yet the vault still decrements its internal `assets` accounting variable as if it had. This is the same bug class as the reported `StakingPool.sol` finding: a value tracking "liquidity that left the pool" is updated based on the recipient parameter, without validating that the recipient is not the pool itself.

### Finding Description
`redeem` burns the caller's shares, sends `inkind` underlying to `recipient` via `send-underlying`, and then unconditionally does: [1](#0-0) 

Compare this to `transfer`, in the same contract, which explicitly forbids `to` being the vault's own address: [2](#0-1) 

No such `(asserts! (not (is-eq recipient current-contract)) ...)` guard exists in `redeem` (nor in `deposit`, which has the symmetric issue in reverse — see below). Because `send-underlying` moves funds from the vault to `recipient`, when `recipient` is the vault's own principal, the on-chain token/STX balance of the vault does not decrease (self-transfer), but `(var-set assets (- current-assets inkind))` still executes, permanently reducing the vault's tracked `assets` variable relative to its true balance.

This mirrors the report's root cause exactly: a state variable meant to track "liquidity leaving the pool" (`assets` here, `updateInterestRates(...,0,amountToUnstake)` there) is updated unconditionally based on the destination parameter, without accounting for the destination being the pool/vault itself.

### Impact Explanation
`assets` feeds directly into `total-assets`, `utilization`, `interest-rate`, and `convert-to-assets-preview`/`convert-to-shares-preview` used by every subsequent `deposit`/`redeem`/borrow/repay call: [3](#0-2) 

Once `assets` is understated relative to the vault's real balance, the vault's exchange rate (assets-per-share) computed for all *other* depositors is skewed — subsequent redeemers receive less underlying per share than they are entitled to, i.e. legitimate suppliers' claims on the real balance are frozen/misallocated. The corrupted `assets` value also lowers `get-available-assets`, artificially inflating measured `utilization` and thus the interest rate charged to borrowers and paid to suppliers, corrupting the reserve/treasury interest split going forward. This lands on the in-scope impact class of temporary/permanent freezing of unclaimed yield for other suppliers (their shares are undervalued against the vault's true underlying balance) — analogous to the "unclaimed yield/temporary freezing of funds" category used to justify the original report's Medium severity.

### Likelihood Explanation
The action requires only a single transaction: any holder of vault shares (zft) can call `redeem` with `recipient` set to the vault contract's own principal (`current-contract`). No special privileges, multi-block timing, or DAO compromise are needed — it is directly reachable by any user, similar to the original report's unstake-to-self scenario.

### Recommendation
Add the same self-recipient guard already used in `transfer` to `redeem` (and `deposit`, symmetrically):
```clarity
(asserts! (not (is-eq recipient current-contract)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
```
placed among the other `asserts!` checks in `redeem`, before `send-underlying`/`var-set assets` execute.

### Proof of Concept
1. User holds `amount` zft shares in `v0-vault-stx` and calls `redeem(amount, min-out, recipient: .v0-vault-stx)` — i.e., passes the vault's own contract principal as `recipient`.
2. `redeem` computes `inkind` via `convert-to-assets-preview`, burns the user's shares with `ft-burn? zft amount account`, then calls `(send-underlying inkind recipient)`.
3. `send-underlying` (as-contract transfer of the underlying asset to `recipient`) sends the underlying back to the vault itself — the vault's actual on-chain balance is unchanged.
4. `redeem` then executes `(var-set assets (- current-assets inkind))`, decrementing the tracked `assets` variable even though no assets actually left the contract.
5. All later calls to `total-assets`, `utilization`, `interest-rate`, and share-to-asset conversion now operate on an `assets` value that understates the vault's true underlying balance, skewing interest rates and the exchange rate applied to other suppliers' shares. [1](#0-0) [2](#0-1)
