## Title
Malformed but regex-valid `host` param causes an unhandled exception (DoS) in the authentication request path via `sanitizeHost`/`decodeHost` - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

## Summary
This is a structural analog of the reported bug class: an edge-case input value that passes an initial "looks fine" check but is not actually safe for the next, unguarded operation, causing that downstream call to throw/revert instead of failing gracefully — bricking the operation for legitimate/adversarial input rather than returning a controlled error.

## Finding Description
`sanitizeHost` first validates the incoming `host` value with a permissive base64 charset regex, then immediately feeds the value into `decodeHost`, which calls `atob` with no length/format validation and no surrounding `try/catch`: [1](#0-0) [2](#0-1) 

The regex `^[0-9a-zA-Z+/]+={0,2}$` only checks the character set and up to two trailing `=` characters; it does **not** enforce that the base64 payload length is valid (i.e., a multiple of 4, or that the final group contains at least 2 characters). A base64 string whose length modulo 4 equals `1` (e.g. a single character like `"A"`, or 5, 9, … characters) satisfies the regex but is not decodable — `atob` throws an uncaught `DOMException`/`InvalidCharacterError` for such input. This mirrors the reported pattern exactly: a value that "looks fine" per an upstream check (non-zero/non-empty, matching a shape) is passed unguarded into a primitive operation (`unstake`, `exchange_underlying`, here `atob`) that reverts/throws on that specific edge case.

This `sanitizeHost` path is reachable by any anonymous request to the embedded-admin authentication entry point, since `host` is attacker-controlled query-string input processed before a session even exists: [3](#0-2) [4](#0-3) 

The calling `authenticateAdmin` function only special-cases errors that are already `Response` instances; any other thrown error (such as the raw `atob` exception) is simply re-thrown, so it is not converted into the app's normal, controlled "invalid host" response path: [5](#0-4) 

## Impact Explanation
An unauthenticated request with a specially-crafted `host` query parameter (length such that base64 padding is malformed) causes an unhandled exception deep in the authentication pipeline instead of the intended `null`/"invalid host" response. Because the exception is not a `Response`, it propagates out of the `authenticate.admin` entry point uncaught by the library's own error handling, which:
- Produces an uncontrolled 500 for a normal request path that is otherwise supposed to gracefully render the App Bridge bounce or redirect to login on invalid params, and
- Depending on the host framework/dev-mode configuration, risks leaking a stack trace/internal error details to an anonymous caller.

This is a denial-of-service / error-handling gap in a request-authentication handler reachable by any anonymous request, matching the class of "zero/edge-value not guarded before a downstream primitive that reverts."

## Likelihood Explanation
Trivial to trigger: any unauthenticated GET request to an embedded app's document/auth route with `?host=<single-or-length%4==1-char base64 string>` reaches `sanitizeHost` before any session or shop validation succeeds. No secrets, privileged access, or race conditions are required.

## Recommendation
- Validate base64 length constraints (length is a multiple of 4, or the regex only allows valid trailing group sizes) before calling `atob` in `sanitizeHost`.
- Wrap the `atob`/`URL` construction in `sanitizeHost` in a `try/catch` and treat any decode failure as an invalid host (return `null` / throw `InvalidHostError` consistently with the rest of the function), rather than letting a raw exception escape.
- Ensure `authenticateAdmin`/`authenticate.admin` catches all synchronous validation errors from `validateShopAndHostParams` and converts them into the same controlled "invalid params" response used for other invalid-shop/host cases.

## Proof of Concept
1. Send an anonymous GET request to an embedded app's authenticated route with a malformed but regex-valid host value, e.g.:
   `GET /?shop=test-shop.myshopify.com&host=A`
2. `validateShopAndHostParams` calls `api.utils.sanitizeHost(url.searchParams.get('host')!)` → `sanitizeHost` → `base64regex.test('A')` returns `true` → `decodeHost('A')` → `atob('A')` throws `InvalidCharacterError`.
3. The exception is not a `Response`, so it bypasses the library's normal invalid-host handling and propagates out of `authenticate.admin`, producing an unhandled server error instead of the expected controlled response.

        shop,
        host: url.searchParams.get('host'),
      });

  }
}

        shop,
