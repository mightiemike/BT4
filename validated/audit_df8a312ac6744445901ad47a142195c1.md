### Title
Unchecked zero-amount revert-mint in `handleFailedOutbound` can permanently strand an outbound as `ABORTED` - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`handleFailedOutbound` re-mints bridged funds back to the revert recipient on a failed outbound for `TxType_FUNDS`, `TxType_GAS_AND_PAYLOAD`, and `TxType_FUNDS_AND_PAYLOAD`, but never checks that `outbound.Amount` is non-zero before calling `CallPRC20Deposit`. If the PRC20 handler contract (`UniversalCore.depositPRC20Token`) reverts on a zero-value mint/transfer — the exact bug class described in the referenced OTLM report — the outbound is permanently marked `ABORTED` instead of `REVERTED`, requiring manual admin intervention.

### Finding Description
Outbounds are built two ways: (1) `buildRevertOutbound` for pre-execution inbound failures, which always carries the original non-zero inbound amount, and (2) `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:16-105`), which decodes an `Amount` directly from an on-chain `UniversalTxOutbound` event emitted by user/UEA-executed payload logic and stores it verbatim into `OutboundTx.Amount` at line 72, with **no call to `ValidateBasic()`** anywhere in the attach path (`AttachOutboundsToExistingUniversalTx` → `attachOutboundsToUtx`, `x/uexecutor/keeper/create_outbound.go:141-155, 339-407`). `ValidateBasic()` is the only guard in the codebase that rejects `bi.Sign() <= 0` for `FUNDS`/`FUNDS_AND_PAYLOAD` outbound amounts (`x/uexecutor/types/outbound_tx.go:56-62`), and it is never invoked in this flow.

A user submitting a `MsgExecutePayload` (any unprivileged account, gasless) can drive a UEA to emit a `UniversalTxOutbound` event with `amount = 0` (e.g. a swap/DEX contract call whose payload emits an outbound intent with zero bridged value, or simply a contract that always calls the gateway with `amount=0`). This zero-amount outbound is attached to the UTX and voted PENDING → observed FAILED by honest UVs. `FinalizeOutbound` → `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go:102-147`) then unconditionally parses `outbound.Amount` and calls `k.CallPRC20Deposit(ctx, prc20, recipient, amount)` with `amount = 0`, with no `Sign() > 0` check anywhere in this function, in contrast to every inbound-side call site which explicitly guards `amount.Sign() > 0` before depositing.

If `depositPRC20Token` on the `UniversalCore`/PRC20 handler reverts on a zero-value call (a realistic assumption per the referenced OTLM bug class, and unverified/unenforced by this Cosmos-side code), `CallPRC20Deposit` returns an error, and `handleFailedOutbound` immediately calls `k.AbortOutbound(...)`, marking the outbound `Status_ABORTED` — a terminal state per the README (`x/uexecutor/README.md:161`) that "requires manual intervention."

### Impact Explanation
This causes a state-machine outcome (`ABORTED`) that removes the outbound from normal automated processing and requires privileged/manual remediation, for a condition entirely reachable by an unprivileged user crafting a payload that emits a zero-amount `UniversalTxOutbound`. This matches the "denial of service... reachable without privileged control" and "corruption of ... UniversalTx state" categories in scope. It is not a fund-theft or fund-loss primitive by itself (no funds are actually lost — nothing was meant to be minted since amount is 0), but it does produce an incorrect/unrecoverable UTX/outbound state purely from unprivileged, honest-validator-observed input, which the module's own design otherwise carefully guards against everywhere else in the inbound path.

### Likelihood Explanation
Reachability depends on whether the actual Solidity `depositPRC20Token`/PRC20 mint function reverts on `amount=0` — this repository (a Cosmos SDK Go module) does not contain that Solidity source, so this cannot be fully confirmed from the scanned code alone; it is inferred by analogy to the referenced bug class and by the fact that every other call site in this same Go codebase (`execute_inbound_funds_and_payload.go:69,89,144`; `execute_inbound_gas_and_payload.go:77,91,146`) explicitly guards `amount.Sign() > 0` before depositing, strongly suggesting the underlying contract is known/assumed not to tolerate zero-value deposits. The trigger itself (a payload emitting a `UniversalTxOutbound` with `amount=0` and later voted FAILED) is fully within reach of an unprivileged user and honest UV voting.

### Recommendation
1. Add a zero-amount check in `handleFailedOutbound` before calling `CallPRC20Deposit`, mirroring the inbound-side pattern: skip the mint call entirely when `amount.Sign() == 0` and go straight to marking the outbound `REVERTED`.
2. Call `OutboundTx.ValidateBasic()` (or an equivalent amount check) inside `attachOutboundsToUtx`/`BuildOutboundsFromReceipt` before attaching contract-emitted outbounds, consistent with the validation already present for inbound `ValidateForExecution()`.

### Proof of Concept
1. Deploy/drive a UEA via `MsgExecutePayload` whose payload logic causes the gateway to emit a `UniversalTxOutbound` event with `amount = 0` (e.g. a `PAYLOAD`-style contract call incorrectly tagged/encoded as `FUNDS`/`FUNDS_AND_PAYLOAD`, or a swap contract that emits a zero-value bridge intent as a side effect of its own logic) for `TxType_FUNDS` or `TxType_FUNDS_AND_PAYLOAD`.
2. `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:69-91`) decodes this into an `OutboundTx{Amount:"0", TxType: FUNDS}` and `attachOutboundsToUtx` stores it without validation.
3. Honest UVs broadcast/observe the destination tx fails and vote `MsgVoteOutbound(success=false)`, reaching quorum.
4. `FinalizeOutbound` → `handleFailedOutbound` parses `amount = 0` and calls `CallPRC20Deposit(ctx, prc20, recipient, 0)`.
5. If the underlying `depositPRC20Token` handler reverts on `amount=0` (per the referenced OTLM bug-class assumption), `err != nil`, and `handleFailedOutbound` calls `k.AbortOutbound(...)`, permanently setting `outbound.OutboundStatus = Status_ABORTED` — confirmable by querying the UTX via `GetUniversalTx` and observing `OutboundTx[].outbound_status == ABORTED` and non-empty `abort_reason`.
