### Title
Legacy (non-hardened) Bancor-style exchange math in `ExchangeCapsule.transaction` allows exchange reserves to go negative / be over-credited when `allowHardenExchangeCalculation` is disabled - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction` uses a double-precision Bancor formula (`ExchangeProcessor`) to compute `buyTokenQuant`, then updates pool balances with plain `long` arithmetic and only performs the "new balance must be >= 0" sanity check when `hardenedCalc` is `true`. When `allowHardenExchangeCalculation()` is `0` (the legacy/default path), an attacker who creates a low-liquidity exchange and crafts `sellTokenQuant` can exploit floating-point rounding in the Bancor curve to receive a `buyTokenQuant` that exceeds the actual `secondTokenBalance`/`firstTokenBalance`, silently driving a pool reserve negative and extracting more value than was deposited.

The post-transaction sanity check that rejects negative balances is gated behind `hardenedCalc`: [2](#0-1) 

`hardenedCalc` is supplied by `AbstractExchangeActuator.allowHarden()`, which simply forwards the value of the `allowHardenExchangeCalculation` dynamic chain parameter: [3](#0-2) 

`ExchangeTransactionActuator.doValidate()` and `execute()` both call `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`: [4](#0-3) [5](#0-4) 

`ExchangeProcessor` performs the Bancor relay-token math entirely in `double`: [6](#0-5) 

`validate()` only checks: token id valid, `tokenQuant > 0`, `tokenExpected > 0`, non-zero pool balances, `firstTokenBalance/secondTokenBalance + tokenQuant <= exchangeBalanceLimit`, and that the caller has sufficient asset/TRX balance and that the computed `anotherTokenQuant >= tokenExpected`. Crucially, `validate()` never checks that the *other* pool side's balance remains non-negative when `hardenedCalc` is false — that check only exists inside `transaction()` and is itself skipped unless `hardenedCalc` is `true`. Since `allowHardenExchangeCalculation` is a governance-gated dynamic property (defaults to disabled/legacy behavior until a committee proposal activates it), any chain that has not yet activated this proposal runs the vulnerable legacy path for every `ExchangeTransactionContract`.

An unprivileged account can: (1) broadcast `ExchangeCreateContract` to create a pool with deliberately small `firstTokenBalance`/`secondTokenBalance` deposits, then (2) broadcast one or more `ExchangeTransactionContract`s with `sellTokenQuant` values chosen to bias the double-precision Bancor rounding, since the entire computation (`Math.pow`-based relay/supply calc) is IEEE-754 floating point and does not exactly reproduce the intended constant-relay-supply invariant. This exact risk is acknowledged in-repo by the addition of `SafeExchangeProcessor` (BigInteger-exact implementation) and the `hardenedCalc` post-check — features that only take effect once the corresponding chain parameter is turned on.

### Impact Explanation
If floating-point rounding can be steered to make `buyTokenQuant` exceed the actual counter-side reserve, the attacker extracts more TRX/TRC10 than was deposited into the pool they created, and the exchange's tracked `secondTokenBalance`/`firstTokenBalance` becomes negative or otherwise inconsistent with real backing assets. This corrupts global asset accounting (`AccountStore`/`AssetIssueStore` balances no longer conserved against the exchange's recorded reserves), matching a "created/destroyed value" / accounting-corruption bounty class.

### Likelihood Explanation
Precondition is that `allowHardenExchangeCalculation` has not been activated on the chain (default/legacy state) — this is the documented default gate, not a non-default node configuration; no privileged role is needed to create an exchange or send a transaction against it. Cost to the attacker is only the normal transaction fee and self-funded deposits for the pool they create. Exploitability magnitude is bounded in this codebase by the `exchangeBalanceLimit` dynamic parameter enforced in `doValidate()` (`tokenBalance + tokenQuant <= balanceLimit`), which constrains how far `sellTokenQuant`/reserve values can be pushed toward the double-precision boundary; I was not able to verify in this session the exact default value of `exchangeBalanceLimit` or run a concrete differential fuzz/PoC against `ExchangeProcessor` vs. `SafeExchangeProcessor` to confirm a divergence larger than a few smallest-unit rounding errors. The presence of `SafeExchangeProcessor` and the gated negative-balance check strongly indicate the maintainers already identified and partially mitigated this class of issue, consistent with historical rounding-based exchange abuse in early TRON exchange code.

### Recommendation
- Make the negative-balance / conservation check unconditional in `ExchangeCapsule.transaction`, not gated on `hardenedCalc`, so both math paths reject a transaction that would drive a reserve negative.
- Deprecate/retire the double-based `ExchangeProcessor` legacy path entirely (always use `SafeExchangeProcessor`/BigInteger-exact math), independent of the `allowHardenExchangeCalculation` proposal state, since the "hardened" behavior is strictly safer and its absence has no legitimate use case.
- If backward compatibility must be preserved for existing chain state prior to activation, add an additional always-on check in `ExchangeTransactionActuator.doValidate()`/`execute()` that rejects any `anotherTokenQuant` greater than the current counter-side pool balance.

          secondTokenBalance,

          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;

          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
