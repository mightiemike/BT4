## Finding

### Title
Receipt-size limit bypass via post-validation mutation of `output_data_receivers` — ([File: runtime/runtime/src/lib.rs])

### Summary
Squid's CVE-2019-12519 is a check-then-grow bug: a bounded stack buffer is validated once, then a subsequent "push" path grows it without re-checking the bound, causing an overflow. nearcore has the same bug class in `apply_action_receipt`: a newly created receipt is validated against `max_receipt_size` at creation time, but is later mutated — by appending `output_data_receivers` or wrapping a large `ReturnData::Value` into a new `Data` receipt — with **no re-validation** of the size limit afterward.

### Finding Description
In `apply_action_receipt` (`runtime/runtime/src/lib.rs`), after each action executes, any receipt it created is checked once via `validate_receipt(..., ValidateReceiptMode::NewReceipt)`: [1](#0-0) 

But later, once the loop over `action_receipt.output_data_receivers()` runs, the already-validated receipt (looked up by `receipt_index` in `result.new_receipts`) is mutated in place by extending `output_data_receivers`, or new `Data` receipts carrying the full function return value are appended to `result.new_receipts` — with no subsequent size check: [2](#0-1) 

This is the same "validate-then-grow-without-recheck" pattern as Squid's `ESIExpression::Evaluate`: the size bound (`max_receipt_size`) is a hard limit meant to keep `ChunkStateWitness` under ~21 MiB, but the growth step that runs after the check is unbounded, so the final receipt can legally exceed `max_receipt_size` after passing validation.

The repository's own test suite documents this as a live, currently-unfixed bug, explicitly referencing `near/nearcore#12606`: [3](#0-2) 

Two concrete exploitation paths are exercised in the tests:
1. **Promise-return path** — a promise DAG `A -then-> B` where `A` creates promise `C` and calls `promise_return`; `C`'s receipt is built at exactly `max_receipt_size`, then `output_data_receivers` is appended after the size check, pushing it over the limit: [4](#0-3) 
2. **Value-return path** — a contract returns a value as large as `max_receipt_size`; it gets wrapped in a `Data` receipt whose total size then exceeds the limit: [5](#0-4) 

Both tests call `assert_oversized_receipt_occurred`, which scans the chain for an incoming receipt whose serialized size exceeds `max_receipt_size` and asserts that such a receipt is found — i.e., the tests assert the presence of the bug, not its absence: [6](#0-5) 

### Impact Explanation
`max_receipt_size` exists specifically to keep receipts (and thus `ChunkStateWitness`) within the ~21 MiB total-size budget documented in `docs/misc/state_witness_size_limits.md`: [7](#0-6) 

Since the size-bound enforcement is bypassable at the last step of receipt construction, an unprivileged contract caller can force the runtime to accept and forward receipts larger than the configured hard limit. This can:
- Break the invariant chunk producers/validators rely on for state-witness size budgeting, risking oversized `ChunkStateWitness` that violate hard limits validators are supposed to enforce (`docs/misc/state_witness_size_limits.md` "Validating the limits" section), which can cause validators to disagree on whether a chunk is valid (endorsement/state-transition divergence between honest nodes that apply the size check differently or at different points).
- Allow cross-shard receipts that exceed the size assumptions baked into congestion-control/bandwidth-scheduler sizing, since those limits (e.g., `outgoing_receipts_usual_size_limit`) are computed assuming `max_receipt_size` is actually enforced.
- Potentially cause a transaction-triggered halt/rejection loop if downstream code (chunk production, RPC serialization, or gossip) has fixed buffers or hard assumptions keyed on `max_receipt_size` and panics or fails hard when receiving an oversized receipt.

This satisfies the "state-root divergence between honest nodes" / "invalid state transition acceptance" bar from the validation rubric, since the limit is a **hard limit** ("anything else is considered invalid") that is silently violated post-validation.

### Likelihood Explanation
High likelihood of reachability: both exploitation paths require only a single unprivileged contract call from a standard `FunctionCall` action (`promise_return`, `promise_then`, or simply returning a large value), no special permissions, validator status, or network position needed. The bug is deterministic — not a race condition — as demonstrated by the existing, passing test cases in the repository itself.

### Recommendation
After mutating `output_data_receivers` on an already-validated new receipt, or after appending `Data` receipts carrying return values, re-run `validate_receipt` (or at minimum a size-only check against `max_receipt_size`) on the finally mutated receipt before it is committed to `result.new_receipts`, and reject/fail the action (`ReceiptSizeExceeded`) if the post-mutation size exceeds the limit. This should happen in `runtime/runtime/src/lib.rs` immediately after the `output_data_receivers`-handling block (lines ~1152–1190) and before the receipt is forwarded via the `ReceiptSink`.

### Proof of Concept
The repository's own tests are a working PoC:
- `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs:130-208`): builds a receipt at exactly `max_receipt_size`, triggers `output_data_receivers` growth via a promise `then`/`promise_return` chain, and asserts (`assert_oversized_receipt_occurred`) that an oversized incoming receipt is produced.
- `test_max_receipt_size_value_return` (`test-loop-tests/src/tests/max_receipt_size.rs:216-267`): returns a value of size `max_receipt_size` from a contract call, which is wrapped into a `Data` receipt exceeding the limit, again asserted via `assert_oversized_receipt_occurred`. [3](#0-2)

                gas: Gas::ZERO,
                deposit: Balance::ZERO,

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
