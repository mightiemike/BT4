### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting replay-verify tooling accept a divergent authenticated state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/cli/src/commands.rs`) to check that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` stored/proven in the ledger. It checks status, gas, write-set hash, and event-root hash, but explicitly skips the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields carried in `TransactionInfoV1`.

### Finding Description
This mirrors the in3-server bug class: a verification routine that is supposed to strictly enforce an authenticated-response invariant instead performs a partial/loose check, silently accepting values it should reject. [1](#0-0)  shows `ensure_match_transaction_info` checking `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash` against the authenticated `TransactionInfo`. Immediately after, a `TODO(trading-native)` comment states plainly: [2](#0-1)  "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

`TransactionInfoV1` carries these three checkpoint hashes as first-class, hashed fields of the authenticated `TransactionInfo` object stored in the accumulator: [3](#0-2) . The accessor `state_checkpoint_hash()` exists and is used elsewhere for real verification (e.g. `TransactionInfoWithProof`/state view binding), [4](#0-3) , confirming these are meant to be authenticated, not incidental fields — yet the one function whose job is to confirm re-executed output equals the authenticated record does not compare them.

The consumer, `storage/db-tool/src/replay_on_archive.rs`, calls exactly this function as its sole correctness gate after re-executing a chunk of transactions from an archived DB: [5](#0-4) . If it returns `Ok(())`, the tool reports the replay as matching the authenticated ledger.

### Impact Explanation
The `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields are exactly the authenticated Sparse-Merkle/JMT-style state roots that bind a `TransactionInfo` (and therefore the transaction accumulator entry signed by validators) to a specific state. A divergence here means local execution produced a genuinely different world state than what was actually committed/authenticated on-chain, while `ensure_match_transaction_info` still reports success because it only checks the write-set hash, not the resulting checkpoint root. This directly matches the "Committed state that differs from the correct VM result" and "authenticated API or state-view output bound to the wrong version/root" categories in the state-integrity gate: replay/verification tooling built specifically to catch exactly this class of divergence is blind to it for the new checkpoint-hash fields as soon as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-style native position roots (or any divergent hot/position state root) come into play.

### Likelihood Explanation
The gap is unconditional in the code (not gated behind the feature flag) — it applies to every call of `ensure_match_transaction_info`, but its real-world materialization depends on `position_state_checkpoint_hash`/hot-state roots actually diverging between execution and the authenticated ledger, which the code comment states will happen once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled. I was not able to fully confirm within available iterations whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet or still a to-be-activated feature flag (`types/src/on_chain_config/aptos_features.rs` and `aptos-move/framework/move-stdlib/sources/configs/features.move` reference it, but I could not verify its activation status before running out of tool budget). If the flag is not yet active on mainnet, the bug is a real, self-acknowledged gap but currently latent; if it is active, the impact is immediate for any replay/verify user relying on this check as ground truth.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present in the `TransactionInfo` variant) against the locally computed equivalents before returning `Ok(())`, exactly as the existing `TODO(trading-native)` comment recommends, rather than deferring the fix to a future point tied to feature-flag activation.

### Proof of Concept
Not applicable as a runnable exploit — the vulnerable code path is a comparator function whose incompleteness is self-documented in the repository (the `TODO(trading-native)` comment at [6](#0-5) ). A conceptual PoC: construct a `TransactionOutput` whose write set, events, gas, and status match a given `TransactionInfoV1`, but whose actually-committed state (post-execution) has a different `position_state_checkpoint_hash`/hot-state root than the one embedded in that `TransactionInfoV1`; calling `ensure_match_transaction_info` on this pair returns `Ok(())`, and `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` reports the chunk as verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
