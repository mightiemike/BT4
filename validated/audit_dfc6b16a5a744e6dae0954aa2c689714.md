### Title
`Network::Nightly` and `Network::TestNetworkWithForks` collide to chain_id 5665, defeating the cross-network replay guard on `BatchProofMethodId` upgrades - (`crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same constant `5665`. The `chain_id` field inside a `BatchProofMethodIdBody` is part of the exact byte string that the security council signs and that `verify_method_id_security_council` re-hashes, so a body/signature set produced for one of these two networks serializes and verifies identically on the other, provided the same council public keys are configured for both deployments.

### Finding Description
The binding that `run_l1_block` is supposed to enforce is:
`citrea_network_to_chain_id(network_the_body_was_signed_for) == citrea_network_to_chain_id(network_this_circuit_is_running_under)` implying `network_the_body_was_signed_for == network_this_circuit_is_running_under`.

In practice the function only compares the numeric `chain_id`, and: [1](#0-0) 
maps `Network::Nightly => 5665` and `Network::TestNetworkWithForks => 5665` — the same value. So the check at [2](#0-1) 
passes for either network whenever the numeric chain_id in the inscribed `BatchProofMethodIdBody` is `5665`, regardless of which of the two networks it was actually minted for.

Since `BatchProofMethodIdBody::serialize()` (whose bytes are what the council signs and what `verify_method_id_security_council` re-verifies) includes this same `chain_id` field, a signature produced over a body meant for `TestNetworkWithForks` is byte-for-byte and hash-for-hash identical to one meant for `Nightly` with the same `method_id`/`activation_l2_height`. `verify_method_id_security_council` at [3](#0-2) 
only checks the ECDSA signatures against `msg` and the `initial_da_pubkeys` array passed in as a runtime parameter to `run_l1_block`; it has no independent knowledge of which network the message was intended for. If the same 5 council public keys (`method_id_upgrade_authority_da_public_keys`) are configured for both a `Nightly` deployment and a `TestNetworkWithForks` deployment (both being pre-mainnet/staging environments operated by the same team), the signature check succeeds identically for a replayed body. Once both checks pass, `BatchProofMethodIdAccessor::insert` executes unconditionally at [4](#0-3) 
for any `activation_l2_height` greater than the last recorded one, replacing the method ID used to verify all future batch proofs on that deployment.

No other guard closes this gap: the `activation_l2_height <= last_activation_height` check at line 539 only prevents strict replays of old activation heights, not cross-network confusion, and there is no separate "network" discriminant carried in the signed payload — chain_id is the only field meant to serve that purpose, and it collides.

### Impact Explanation
If exploited, an attacker who merely inscribes a previously-signed `DataOnDa::BatchProofMethodId` blob on Bitcoin can cause a light-client-proof-verified `run_l1_block` execution on a differently-intended network (Nightly vs TestNetworkWithForks) to accept a method-id upgrade the security council never authorized for that specific deployment. This is a method-id upgrade accepted without proper authorization for the target network, matching the "sequencer commitment or method-id upgrade accepted that was never authorised" Critical category. The blast radius is confined to whichever of these two networks shares reused council keys and the colliding chain_id — this affects every honest node/light-client-prover instance tracking that deployment's JMT state, and is repeatable for every future signed body as long as the constant collision persists.

### Likelihood Explanation
The precondition is that the security council has, at some point, produced a valid signed `BatchProofMethodIdBody` for `TestNetworkWithForks` (a plausible normal operational event for a staging/test network) and that the target `Nightly` deployment shares the same council public keys in its `method_id_upgrade_authority_da_public_keys` configuration (unverified from static analysis — this is a deployment-configuration fact I could not directly confirm from the repo, since these keys are passed in as runtime/config parameters rather than hardcoded per network in this repo). The attacker's only cost is normal Bitcoin inscription fees; no privileged role is required. However, whether this is truly exploitable end-to-end depends entirely on that key-reuse assumption, which is a deployment/ops decision outside this repository's source — I could not verify from the code whether Nightly and TestNetworkWithForks deployments actually share security council keys in practice.

### Recommendation
Ensure `citrea_network_to_chain_id` returns a distinct value for every `Network` variant, including `TestNetworkWithForks` (e.g., use a value like `56650` or another value never used by any real deployment), so that a signed body cannot pass the chain_id check on any network other than the one it was actually minted for. As defense in depth, also ensure that `method_id_upgrade_authority_da_public_keys` are never reused verbatim between distinct network deployments (Nightly vs TestNetworkWithForks vs Testnet, etc.).

```rust
    // This currently fails: both equal 5665.
    assert_ne!(
        nightly, test_net,
        "Network::Nightly and Network::TestNetworkWithForks collide on chain_id {}, \
         allowing a BatchProofMethodIdBody signed for one network to pass the \
         `circuit_chain_id != batch_proof_method_id.body.chain_id` check on the other.",
        nightly
    );
}
```
Running `cargo test -p light-client-prover nightly_and_test_network_chain_ids_must_differ` demonstrates the constant collision documented at [1](#0-0) . Full end-to-end exploitation additionally requires confirming (outside this repo, via deployment config) that a live `Nightly` node and a `TestNetworkWithForks` node share identical `method_id_upgrade_authority_da_public_keys`, which I could not verify from source alone.
