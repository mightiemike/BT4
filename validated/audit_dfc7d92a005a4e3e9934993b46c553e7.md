## Title
Reachable panic (`.unwrap()`) in `DelayedReceiptQueueWrapper::receipt_filter_fn` when a stale `GlobalContractDistribution` receipt cannot be remapped after resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::pop` filters delayed receipts by comparing `receiver_shard_id()` to the current shard using `receipt_filter_fn`, which calls `.unwrap()` on the `Result<ShardId, EpochError>` returned by `Receipt::receiver_shard_id`. [1](#0-0)  For `GlobalContractDistribution` receipts, `receiver_shard_id` resolves a possibly-stale `target_shard` via `ShardLayout::resolve_to_current_shard`, which itself can return `None` — turning into an `Err(EpochError::ShardingError(...))` — when the recorded target shard is not present in the current layout's split history. [2](#0-1)  If that error path is hit inside `receipt_filter_fn`, the `.unwrap()` converts a recoverable protocol condition into a Rust panic that aborts chunk application on every validator/chunk-producer processing that shard.

### Finding Description
Any account holder can call `DeployGlobalContractAction`, which spawns a `GlobalContractDistribution` receipt carrying a `target_shard` snapshot of the current shard layout at deploy time (`runtime/runtime/src/global_contracts.rs`, `initiate_distribution`). [3](#0-2)  This receipt is forwarded/hopped shard by shard, and if the receiver shard is congested/over the compute budget, it is pushed into the persistent **delayed receipts queue** for later draining (`process_incoming_receipts` → `DelayedReceiptQueueWrapper::push`). [4](#0-3) 

When the queue is later drained, `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, which unconditionally `.unwrap()`s `receiver_shard_id(&shard_layout)`:
```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [1](#0-0) 

`receiver_shard_id` for `GlobalContractDistribution` receipts attempts `shard_layout.resolve_to_current_shard(target_shard)` when the stored `target_shard` no longer exists in the current layout, returning `Err(EpochError::ShardingError(...))` if resolution fails: [2](#0-1) . This unwrapped `Err` is exactly the failure mode the repository's own regression test (`test_stale_global_contract_distribution_after_double_resharding`) was written to reproduce/guard against — the test explicitly documents: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations."* [5](#0-4) 

The scenario an unprivileged transaction signer can trigger: deploy a global contract from an account whose shard will subsequently be split by (dynamic) resharding, then keep the receiving shard's chunk fully saturated with compute so the distribution receipt sits in the delayed queue across multiple resharding boundaries. Because `resolve_to_current_shard` only walks forward through the `shards_split_map` recorded in the *current* layout, a chain of splits deep enough (or a shard whose split lineage was dropped/pruned) leaves the historical `target_shard` unresolvable, causing `Err` and thus the `.unwrap()` panic in every honest node applying that chunk. This is a validator/chunk-producer level panic, not merely a client-side one — `pop()` (and therefore `receipt_filter_fn`) executes as part of ordinary chunk application (`process_delayed_receipts`), which every validator applying that shard's chunk must run identically.

### Impact Explanation
A panic inside chunk application on `pop()` aborts the node process (or the apply task) applying that shard's chunk. Because the delayed receipt is persisted state (not something a single malicious relay can drop), *every* honest validator/chunk producer assigned to that shard hits the identical panic when draining the queue, producing a **transaction-triggered chain halt** for the affected shard — the receipt cannot be skipped, retried differently, or garbage-collected away by any node, since the same deterministic state transition is required by all of them. This matches the CWE-476 (NULL/invalid dereference leading to crash) bug class from the referenced Consul advisory, but reached here through an ordinary, permissionless transaction (global contract deployment) combined with resharding rather than any privileged/administrator action. Severity is Medium-to-High depending on how easy it is in practice to keep a receiving shard saturated across two dynamic-resharding events long enough for the receipt to remain undelivered.

### Likelihood Explanation
Exploitability requires: (1) dynamic resharding (`ProtocolFeature::DynamicResharding`) to be enabled — the repo's own test gates on this, noting static (V2) layouts don't carry full split history so the bug there is different/absent; (2) an attacker-controlled account to deploy a global contract targeting a shard about to be split; (3) enough chunk-compute saturation to keep the distribution receipt delayed across (at least) two resharding boundaries so that its recorded `target_shard` falls outside the tracked split lineage. This is a non-trivial but realistic scenario for any network running dynamic resharding with normal transaction traffic (deploy-and-saturate is entirely within reach of a single account with gas to spend), and the codebase's own regression test demonstrates the exact reproduction steps, confirming reachability from ordinary user actions rather than any operator/validator-only path.

### Recommendation
- Replace the `.unwrap()` calls in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`) with a propagated `RuntimeError`/`StorageInconsistentState`-style error (mirroring how `validate_receipt` failures on dequeue are already handled at `runtime/runtime/src/lib.rs:2500`), so an unresolvable receipt shard causes controlled failure/handling rather than an uncontrolled panic.
- Ensure `ShardsSplitMapV3`/`shards_ancestor_map` retains (or is proven to always retain) full split lineage across arbitrarily many resharding generations, or make `resolve_to_current_shard` failures result in a well-defined protocol action (e.g., routing to a deterministic fallback shard) instead of an error that has no safe handling path at the call site.
- Add defense-in-depth so that any `GlobalContractDistribution` receipt whose `target_shard` cannot be resolved is still deterministically routable (e.g., always resolvable to *some* current shard) rather than permitted to reach a state where every node must panic identically.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` is itself the proof-of-concept construction: [6](#0-5) 
1. Configure dynamic resharding to force-split, sequentially, the shard containing the `deploy_user` and then a second, unrelated shard.
2. From `deploy_user`, submit `DeployGlobalContractAction`, creating a `GlobalContractDistribution` receipt whose `target_shard` equals the pre-split shard.
3. Saturate that shard's chunk compute every block with `burn_gas_raw` calls so the distribution receipt is forced into the delayed-receipts queue and remains there while both resharding events complete.
4. Stop saturating and let the delayed queue drain; if the described bug is present, `Runtime::process_delayed_receipts` → `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` panics while calling `.unwrap()` on the `Err` from `receiver_shard_id`, halting chain progress for that shard (the test asserts head height keeps advancing past the drain point, which would fail/panic otherwise).

I could not fully verify from static code review alone whether the currently-present `resolve_to_current_shard` fix (walking the *full* `shards_split_map`, not just the most recent split) fully closes this gap for every possible resharding depth/order, or whether there remain edge cases (e.g., epoch/shard-layout pruning, non-contiguous split histories) where `resolve_to_current_shard` still returns `None` and the `.unwrap()` panics survive. This uncertainty stems from not being able to execute the test suite or trace every resharding-config edge case in this review; a Devin session with full repo/test execution access would be needed to confirm whether the panic is still triggerable in the current `patrichyt/nearcore--002` state or has already been fully mitigated.

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
