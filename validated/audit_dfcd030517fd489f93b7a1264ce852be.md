### Title
Missing domain separation in TVM `validatemultisign`/`batchvalidatesign` precompiles enables cross-contract signature replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, exposed to any TVM smart contract at TRON precompile addresses `0x9`/`0xa`, verify an off-chain ECDSA signature against a hash that is bound only to the target account address, its permission id, and an arbitrary `data` payload chosen by the calling contract — it never incorporates the identity of the calling TVM contract itself. This mirrors the “Affiliate keys can be reused” bug class: a signature produced for one consumer of the primitive can be replayed verbatim against any other consumer that reconstructs the same `(address, permissionId, data)` tuple, because the primitive provides no way to bind an approval to “this specific contract instance.”

### Finding Description
`ValidateMultiSign.execute()` computes the signed hash as: [1](#0-0) 

`address` is the target TRON account, `permissionId` selects one of its permissions, and `data` is arbitrary bytes supplied by the *calling contract's caller* — none of these fields identify which smart contract invoked the precompile. The recovered signer addresses are then checked against the target account's `Permission` weights: [2](#0-1) 

`BatchValidateSign` has the same structural gap: the hash it verifies against is taken directly from caller-supplied `words[0]` with no binding to the invoking contract: [3](#0-2) 

Because all TRON transactions and their calldata are public, any attacker can observe a valid `(address, permissionId, data, signature)` tuple that was submitted to authorize an action in one dApp ("Contract A") and resubmit the identical tuple to a second, independently deployed dApp ("Contract B") that also calls `validatemultisign`/`batchvalidatesign` with the same account/permission and a `data` value it does not itself bind to its own contract address. The precompile has no mechanism analogous to including the "AffiliateValidator" contract address in the signed hash, so it cannot distinguish "signed for Contract A" from "signed for Contract B."

This is architecturally identical to the reported bug class: the KYC/operator signature in `AffiliateValidator.addKey` was valid for any instance of the contract sharing the same operator because the signed hash omitted the contract's own address; here the TVM signature-verification precompile similarly omits the invoking contract's address from the hash it verifies.

### Impact Explanation
Any TVM contract built on top of `validatemultisign`/`batchvalidatesign` to implement off-chain multisig approvals (e.g., custodial withdrawal approval, order confirmation, delegated authorization) is vulnerable to cross-contract signature replay if the `data` payload it hashes is not itself uniquely scoped to that specific contract's address/nonce/domain. An attacker who reuses a captured approval on a second, unrelated contract can obtain an "approved" (weight ≥ threshold) result without ever having the account holder authorize that specific contract's action — leading to unauthorized account/permission-gated operations being accepted by that dApp's logic.

### Likelihood Explanation
Exploitability depends on whether a downstream TVM contract fails to embed its own contract address (or another unique domain tag) into `data` before calling the precompile — a real risk given the AffiliateValidator precedent shows this exact omission occurs in practice even in audited production Solidity code. Since precompile calldata and all prior on-chain approvals are public, and any address can deploy a contract that calls these fixed-address precompiles, the attack requires no privileged access — only a second contract reusing the same authorization convention.

### Recommendation
Document and/or enforce that any consumer of `validatemultisign`/`batchvalidatesign` must include the calling contract's own address (and ideally a chain id and nonce/expiration) inside `data` before it is hashed, exactly as recommended for `AffiliateValidator`. Consider hardening the precompile itself so that the hash it verifies incorporates `msg.sender`/`getContextAddress()` of the calling contract by default (or provide a variant that does), removing reliance on every dApp author independently remembering to domain-separate.

### Proof of Concept
1. Contract A calls `validatemultisign(userAddr, 2, dataX, sigs)` where `dataX` encodes only business fields (e.g., `abi.encode(amount, orderId)`), and the account owner signs `sha256(userAddr || 2 || dataX)` off-chain to approve a withdrawal in Contract A. This transaction (and its calldata/signatures) is publicly visible on-chain. [4](#0-3) 
2. An attacker deploys Contract B, which independently reconstructs the identical `dataX` (e.g., because both dApps use the same off-the-shelf order-encoding scheme) and calls `validatemultisign(userAddr, 2, dataX, sigs)` with the captured `sigs`.
3. Because the hash computed by the precompile depends only on `(userAddr, permissionId, dataX)` and not on Contract A vs. Contract B, `recoverAddrBySign` recovers the same signer addresses and `TransactionCapsule.getWeight` reports sufficient weight, so `ValidateMultiSign` returns `dataOne()` (approved) in Contract B, even though the account owner never intended to authorize anything in Contract B. [5](#0-4)
