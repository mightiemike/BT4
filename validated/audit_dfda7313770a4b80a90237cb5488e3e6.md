Ancient-slot squash silently drops carry-forward tombstones in release builds, resurrecting zero-lamport accounts on incremental-snapshot rebuild - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
`combine_ancient_slots_packed` (ancient-storage squash) reuses the same `shrink_collect` path as ordinary shrink to separate alive accounts from zero-lamport "tombstones" that must be carried forward when a slot is newer than the latest full snapshot. Unlike the regular shrink path (`shrink_storage`), the ancient-squash write path (`write_packed_storages` / `write_ancient_accounts`) has no logic to write `tombstones_to_carry_forward` into the new packed storage. The only safeguard against this loss is a `debug_assert!`, which is compiled out in release/production builds, in `finish_combine_ancient_slots_packed_internal`. If that invariant is ever violated in production, the old storage (and its tombstone bytes) is dropped anyway via `remove_old_stores_shrink`, exactly analogous to `blacklistProtocol()` zeroing state and dropping funds without confirming that the "claim"/carry-forward step actually completed first.

### Finding Description
`shrink_collect` (shared by ordinary shrink and ancient squash) computes `tombstones_to_carry_forward` for any zero-lamport single-ref account whose slot is newer than `latest_full_snapshot_slot` (`can_purge_zero_lamport_single_ref_after_shrink` returns `false`) [2](#0-1) . Tombstones exist specifically because once an account is dropped from the primary index, an incremental snapshot must still be able to observe/propagate the zero-lamport deletion instead of letting an older, still-funded full-snapshot version "come back from the dead" on rebuild [3](#0-2) .

The ordinary shrink path (`shrink_storage`) explicitly rewrites these tombstones into the new storage via `store_tombstones` before dropping the old one [4](#0-3) .

The ancient-squash path does not do this. `finish_combine_ancient_slots_packed_internal` documents the gap directly and relies solely on a debug-only assertion: [1](#0-0) 

Because `debug_assert!` is a no-op in release builds (which is how validators actually run), if this invariant is ever violated — e.g., a race or a future change that causes ancient-squash to be scheduled against a slot that still holds a not-yet-purgeable tombstone (`slot` above `latest_full_snapshot_slot`) — the code proceeds directly to `remove_old_stores_shrink`, which drops the old storage (and hence the tombstone bytes) with no rewrite (`mark_dirty_dead_stores` → `drop(dead_storages)`) [5](#0-4) . This mirrors the M-27 pattern precisely: an operation commits an irreversible cleanup step (dropping old storage / zeroing allocation) without first verifying that a required settlement step (carrying the tombstone forward / claiming rewards) fully completed, guarded only by a soft/no-op check.

The guarding condition, `can_purge_zero_lamport_single_ref_after_shrink`, is a simple slot comparison against a globally mutable `latest_full_snapshot_slot` [6](#0-5) ; `shrink_collect` reads this once when collecting tombstones, and ancient squash's slot-selection (`get_sorted_potential_ancient_slots`) uses a different, epoch-based `oldest_non_ancient_slot` criterion entirely decoupled from `latest_full_snapshot_slot` [7](#0-6) . The test suite (`test_shrink_collect_carries_forward_existing_tombstones`, `test_incremental_snapshots_handle_tombstones`) only validates the ordinary shrink path plus the pure `shrink_collect` computation; there is no equivalent end-to-end test proving ancient squash never encounters a non-empty `tombstones_to_carry_forward` list in production, only the design comment claiming it "only runs on slots far older than the latest full snapshot."

### Impact Explanation
If the invariant is violated, the incremental snapshot for the affected epoch would fail to carry the zero-lamport deletion. On honest-node replay/restart from full+incremental snapshot, the account would be resurrected with its pre-zero (funded) balance from the older full snapshot — a silent balance change and a capitalization/hash divergence between the live bank state and the state rebuilt from snapshots (an honest-node snapshot-vs-replay mismatch), exactly the class of impact called out as acceptable ("silent balance change, hash/capitalization divergence, honest-node snapshot-vs-replay mismatch").

### Likelihood Explanation
This requires the safety invariant asserted in `finish_combine_ancient_slots_packed_internal` to actually be violated, which the current code's slot-selection logic is designed to prevent (`shrink_ancient_slots` only considers slots `< oldest_non_ancient_slot`, generally much older than `latest_full_snapshot_slot`). I could not find a concrete code path in this snapshot of the repository that currently violates the invariant; the risk is that the only enforcement mechanism is a `debug_assert!` that provides zero protection in the release binaries validators actually run, so any future refactor, race between snapshot bookkeeping and ancient-slot selection, or edge case in `get_oldest_non_ancient_slot`/epoch schedule handling would silently corrupt state instead of panicking loudly. This is a latent defense-in-depth gap rather than a demonstrated exploit in the current code, so likelihood is assessed as low but the blast radius (silent capitalization corruption) is high.

### Recommendation
Replace the `debug_assert!` in `finish_combine_ancient_slots_packed_internal` with a hard `assert!` (or an explicit error path) so any violation panics in all builds rather than silently discarding tombstone bytes, consistent with how other correctness-critical invariants in `accounts_db.rs` (e.g., `write_accounts_to_storage`) use full `assert!`/`panic!` rather than `debug_assert!`. Additionally, either (a) make ancient squash carry forward `tombstones_to_carry_forward` the same way ordinary shrink does via `store_tombstones`, removing the need to rely on slot-selection invariants entirely, or (b) have `combine_ancient_slots_packed`'s slot selection explicitly filter out any slot where `can_purge_zero_lamport_single_ref_after_shrink` is false, rather than relying on the epoch-based `oldest_non_ancient_slot` heuristic to always be conservative enough relative to `latest_full_snapshot_slot`.
