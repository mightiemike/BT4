## Analysis Result

### Title
Front-Runnable Account ID Squatting Causes Denial of Service in `SetAccountIdActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
The `SetAccountIdContract` allows any account to permanently bind an arbitrary, attacker-chosen `accountId` byte string to their address. The uniqueness check is performed against a global index (`AccountIdIndexStore`) at validation time, with no reservation or address-binding of the id prior to broadcast. This mirrors the reported `loanId`-front-running pattern: a user announces an intended unique identifier in a public transaction, and an attacker can observe it in the mempool and race to claim the same identifier first, causing the legitimate user's transaction to fail and the account-id claim to be lost.

### Finding Description
In `validate()`, the actuator checks two conditions before allowing an account id to be set: whether the caller's own account already has an id set, and whether the requested `accountId` already exists in the global `accountIdIndexStore`: [1](#0-0) 

If the id is free, `execute()` writes it to the account and to the shared `AccountIdIndexStore` index: [2](#0-1) 

Because Tron transactions are broadcast to the P2P mempool before being included in a block (see `Wallet.broadcastTransaction`), an attacker monitoring the network can see a victim's pending `SetAccountIdContract` transaction containing a specific `accountId`, and submit their own transaction with the same `accountId` (from the attacker's own address) with a higher priority/earlier propagation. If the attacker's transaction is packed first, `accountIdIndexStore.has(accountId)` will be `true` when the victim's transaction is validated, causing it to fail with `"This id has existed"`: [3](#0-2) 

This is structurally identical to the reported bug: a user-chosen, application-meaningful identifier (`loanId` in the report, `accountId` here) is checked for prior existence in a global store, and the check-then-set pattern is exploitable by front-running because there is no commit-reveal, no per-address namespacing, and no ownership binding of the id before the claiming transaction executes.

The test suite explicitly documents this exact "id squatting" scenario as intended/expected behavior rather than a defended-against attack: [4](#0-3) 

### Impact Explanation
An attacker can grief any user who broadcasts a `SetAccountIdContract` transaction with a distinctive/desired `accountId` (these ids are used by exchanges and integrators to identify deposit accounts). By front-running with the same `accountId` bytes, the attacker permanently squats that identifier in the global index. The victim's transaction fails validation, wasting their transaction submission effort, and the victim can never claim their intended id again since `accountIdIndexStore` entries are never removed. This is a pure griefing/DoS impact with no direct fund loss but permanent denial of a specific desired identifier to the legitimate claimant — the same impact category ("Griefing") described in the source report.

### Likelihood Explanation
Exploitation requires only observing pending transactions in the mempool and being able to get a transaction packed before the victim's — routine front-running capability available to any network participant/miner-adjacent actor, with no special privilege required. The cost to the attacker is a single low-fee `SetAccountIdContract` transaction (fee is `0` per `calcFee()`), making this cheap and repeatable against any target `accountId`.

### Recommendation
Consider decoupling id "intent" from id "claim" (e.g., commit-reveal for account id registration), or scope uniqueness checks with a stake/deposit and time-lock so front-running has a cost, or simply document that `accountId` is not a race-safe, first-come primitive and should not be relied on for value-bearing identification (e.g., exchange deposit matching) without off-chain reservation.

### Proof of Concept
1. Alice submits `SetAccountIdContract{ownerAddress: Alice, accountId: "MYBRAND"}`, intending to claim the id `"MYBRAND"`.
2. Bob observes Alice's pending transaction in the mempool and immediately submits `SetAccountIdContract{ownerAddress: Bob, accountId: "MYBRAND"}`.
3. Bob's transaction is packed first; `accountIdIndexStore.has("MYBRAND")` becomes `true` as shown in `execute()`: [5](#0-4) 
4. Alice's transaction is then validated and fails with `ContractValidateException("This id has existed")` at the check: [3](#0-2) 
5. Alice can never claim `"MYBRAND"` for her account; the id is permanently held by Bob, who has no legitimate use for it — a pure griefing outcome.
