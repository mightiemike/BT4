### Title
`ensure_match_transaction_info` in `TransactionOutput` never validates `state_checkpoint_hash`, letting `db-tool replay-on-archive` accept a corrupted/divergent state root as "verified" - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the single correctness check used by `storage/db-tool/src/replay_on_archive.rs` to confirm that a locally re-executed transaction matches the trusted, accumulator-proof-backed `TransactionInfo` pulled from a backup/archive. The function checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and `event_root_hash`, but it never compares the recomputed state root (`state_checkpoint_hash`, and on V1 also `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the expected `TransactionInfo`. This is analogous to the ELFI bug: a code path that is supposed to reconcile/verify a derived quantity against an authoritative value silently no-ops on the very field that matters, letting a divergent state persist undetected.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) , and it validates status, gas, write-set hash and event root hash: [2](#0-1) 

Critically, the function's own TODO comment admits the gap: [3](#0-2) 

It explicitly states that "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." The comment frames this only in terms of the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature (confirmed present in `types/src/on_chain_config/aptos_features.rs`), but the code shows the gap is broader: the function *never* checks the baseline `state_checkpoint_hash` field either — for any transaction, on any build, this field is not part of the equality check at all.

The sole caller of this method for archival state validation is `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs`, which drives the entire pass/fail decision of a replay-verify run purely off this comparator's `Result`: [4](#0-3) 

`state_checkpoint_hash` is the state Merkle root committed into the `TransactionInfo` leaf of the transaction accumulator — the exact field that db-tool's own `check_txn_info_hashes` command treats as security-critical: [5](#0-4) 
Yet the parallel "replay and verify VM re-execution matches archive" tool has no equivalent check on the state root at all.

### Impact Explanation
This breaks the "authenticated proof-bearing responses must stay bound to the right ledger version, root, and object" invariant for the `replay-on-archive` tool: an archive whose account/resource *values* were subtly corrupted (via a backend bug, corrupted backup file, or malicious backup host) while write-set/event bytes for a given transaction happen to hash correctly, or more realistically where re-execution genuinely diverges from the historical state root, would be reported as "verified" by this tool with no state-root mismatch ever raised. Because this is one of the primary tools operators and auditors use to confirm the integrity of an archived/restored ledger against independent VM re-execution, a wrong state root can silently pass as "matches transaction info," undermining confidence in restore/replay-verify results for the whole chain history. It does not corrupt live consensus-committed state (execution/consensus paths compute and gate on `state_checkpoint_hash` separately via `do_state_checkpoint.rs`/accumulator), but it defeats a dedicated state-integrity verification tool that operators rely on to catch exactly this class of divergence, and it applies unconditionally (not gated behind the trading-native feature flag) since `state_checkpoint_hash` is unconditionally skipped.

### Likelihood Explanation
High likelihood of being triggered in practice for any of: a genuinely buggy VM/executor change that alters computed state without changing the write-set bytes hash comparison outcome for the sampled transactions, a corrupted/tampered backup source, or storage-layer bugs affecting state application but not event/write-set serialization. The comment in the code itself confirms the authors are aware the checkpoint-hash comparison is missing, but as written today it applies to *all* uses of `ensure_match_transaction_info`, not just the future trading-native feature, so it is live in the current `replay_on_archive` tool.

### Recommendation
Add `state_checkpoint_hash` (and, when V1/relevant feature is active, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) comparisons to `ensure_match_transaction_info`, using the recomputed root from the ledger update / state-checkpoint output for the given version, and fail the replay-verify check (as `execute_and_verify` already does for the other fields) when they don't match.

### Proof of Concept
Conceptual (no test harness available in this scan): construct a `TransactionOutput` whose `write_set` and `events` reproduce byte-identical `state_change_hash`/`event_root_hash` to the expected `TransactionInfo`, but whose *value contents* would materialize into a different state root than the archived `state_checkpoint_hash` (e.g., replaying with a VM/version that computes a different but equally-serializable state value, or a backup file where accompanying committed `TransactionInfo.state_checkpoint_hash` was corrupted independently of the write set entry used for replay). Calling `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ..)` in `replay_on_archive.rs` returns `Ok(())` because `state_checkpoint_hash` is never read from either side, so `db-tool replay-on-archive` reports the range as verified despite the divergent state root.
