### Title
Missing bounds validation on attacker-controlled array length in `extractBytesArray`/`extractSigArray` causes unbounded allocation DoS in `ValidateMultiSign` / `BatchValidateSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The zkSync finding centers on `bootloader::sendCompressedBytecode` decoding attacker-influenced offsets/lengths without validating them against the expected layout before using them to size/allocate data, allowing the operator to smuggle unaccounted data. The java-tron analog is in the ABI-array decoding helpers used by the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts: an attacker-controlled 256-bit word is read via `intValueSafe()` and used directly as an array length for allocation, before any sanity check against the real size of the supplied calldata is performed.

### Finding Description
`extractBytesArray` and `extractSigArray` read the "array length" field directly from attacker-supplied calldata and immediately use it to allocate a Java array: [1](#0-0) 

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    ...
```

`len` is derived only from `offset > words.length - 1` bound check on the *offset*, not on the *value* stored there. Nothing prevents `words[offset]` from encoding an arbitrary large 256-bit integer that `intValueSafe()` converts into a large positive `int` (or, depending on its overflow behavior, an unexpected/negative value), which is then fed straight into `new byte[len][]`. The same pattern exists in `extractSigArray` and `extractBytes32Array`: [2](#0-1) 

These helpers are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, both of which are reachable precompiled contracts callable by any smart contract via `CALL`/`STATICCALL` — no privileged role required: [3](#0-2) 

The only downstream bound-check (`signatures.length > MAX_SIZE`) happens *after* the array has already been allocated and populated, i.e. after the damage from an oversized allocation has already occurred: [4](#0-3) 

There is a partial, feature-flagged mitigation added for TIP-854 (`isValidAbiEncoding`), but it only validates that `data.length` is consistent with a fixed head + `k` items shape — it does **not** validate that the decoded `len` word actually equals `k`, nor is it active unless `VMConfig.allowTvmOsaka()` is enabled: [5](#0-4) [6](#0-5) 

This mirrors the zkSync root cause: an offset/length field is trusted and used for sizing/allocation before being cross-checked against the actual calldata structure, and the "safe" guard that exists is incomplete/gated.

### Impact Explanation
An attacker can craft a transaction calling `ValidateMultiSign` or `BatchValidateSign` with a manipulated "signature/address array length" word so that `len` decodes to an extremely large value. `new byte[len][]` will then attempt to allocate a huge array, which can throw `OutOfMemoryError` or `NegativeArraySizeException` deep inside precompiled-contract execution. Depending on how these exceptions propagate through the VM's execution path (only `ValidateMultiSign`'s inner permission-check block has a `catch (Throwable t)`; the extraction call at lines 1072-1074 is outside that try/catch), this can crash/halt transaction processing for the node executing it, representing an invalid-state/halt condition triggerable by any unprivileged contract caller — directly analogous to the "operator can pass unchecked offset/length data to break invariants" class of bug from the report.

### Likelihood Explanation
Both precompiles are permissionless entry points reachable from any TVM contract (no special role needed), and constructing calldata with an arbitrary 256-bit "length" word is trivial for any user submitting a transaction, making this straightforward to trigger by any actor able to submit contract calls.

### Recommendation
- In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate the decoded `len` against a reasonable upper bound (e.g., `MAX_SIZE`) and against the actual remaining calldata size *before* allocating any array, not after.
- Extend `isValidAbiEncoding` (and make it unconditional, not gated behind `allowTvmOsaka()`) to also verify that the decoded array-length word matches the number of items actually derivable from `data.length`, closing the same "offset/length not cross-checked against real payload" gap the zkSync report describes.
- Wrap the extraction calls (lines 1072-1074 and the `BatchValidateSign` equivalent) in the same defensive `try/catch` used for the permission-check block so unexpected exceptions do not propagate uncontrolled.

### Proof of Concept
1. Build calldata for `validatemultisign(bytes32,uint256,bytes,bytes[])` (or `batchvalidatesign`) where the dynamic array's length word (the word at the offset pointed to by the array's own offset field) is set to a very large value, e.g. `0x00000000000000000000000000000000000000000000000000000000FFFFFF` (16,777,215), while the offset field itself passes the `offset > words.length - 1` guard.
2. Call the precompile through a simple contract using `STATICCALL`/`CALL` to address `0x66`/`0x67` (`ValidateMultiSign`/`BatchValidateSign`).
3. Execution reaches `extractBytesArray`/`extractSigArray`, which executes `new byte[len][]` with the attacker-supplied `len`, causing excessive memory allocation before the later `signatures.length > MAX_SIZE` check can reject it.
