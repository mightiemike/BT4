### Title
`DeleteAccount` permanently burns gas-key balances instead of refunding them to the beneficiary - (File: `runtime/runtime/src/actions.rs`)

### Summary
When an account with funded gas keys is deleted via `DeleteAccountAction`, `action_delete_account` refunds only the account's main `amount()` to the `beneficiary_id`, while the sum of all gas-key balances is unconditionally destroyed (added to `tokens_burnt`) rather than being included in the beneficiary refund, as long as the sum is at or under `GasKeyInfo::MAX_BALANCE_TO_BURN`. This mirrors the reported bug class: an irrevocable "close" action (`OngoingBounty` closing / `DeleteAccount`) that permanently strands/destroys a leftover balance that was never fully swept out before the closing action executed.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) computes `gas_key_balance_to_burn` via `compute_gas_key_balance_sum` and, if it does not exceed `GasKeyInfo::MAX_BALANCE_TO_BURN`, adds it directly to `result.tokens_burnt` (`runtime/runtime/src/actions.rs:370-391`) instead of folding it into the `Receipt::new_balance_refund` sent to `delete_account.beneficiary_id` at line 385. Only `account_ref.amount()` (the "main" balance) is ever refunded to the beneficiary; gas-key balances are treated purely as burn material with no path to recovery. [1](#0-0) 

The same one-way burn (never refund) pattern exists in the single-key-delete path, `delete_gas_key` (`runtime/runtime/src/access_keys.rs:93-134`), which burns `gas_key_info.balance` whenever it is below the threshold. [2](#0-1) 

This is documented as intended, deliberate behavior in the protocol-model spec ("Gas-key deletion burns ≤ 1 NEAR: … otherwise the balance is burned (added to `tokens_burnt`, not refunded)"), and is exercised by tests (`test_delete_account_burns_gas_key_balances`, `test_delete_account_gas_key_balance_at_threshold`) that explicitly assert the burned amount equals the deposited gas-key balances rather than being refunded. [3](#0-2) [4](#0-3) 

The `OngoingBounty` analogy is direct: a bounty issuer (equivalent to the account owner deleting/closing their account) can trigger a terminal, irreversible "close" transaction (`DeleteAccountAction`/`DeleteKeyAction` for a gas key) while funds are still parked in a sub-ledger (`_payoutVolume` leftover / `GasKeyInfo.balance`) that the closing logic does not sweep to the intended recipient — instead it is unconditionally destroyed.

### Impact Explanation
Every gas-key balance up to `GasKeyInfo::MAX_BALANCE_TO_BURN` (documented threshold ≤ 1 NEAR per key, and the same cap applied to the aggregate sum on account deletion) that remains on a gas key at the moment of key deletion or account deletion is permanently destroyed rather than returned to the account owner or the deletion's designated `beneficiary_id`. This is a genuine, protocol-level, permanent loss of user funds triggered by an ordinary, unprivileged transaction (`DeleteKeyAction` or `DeleteAccountAction`, both directly reachable by any signer holding a full-access key on their own account). Unlike the `OngoingBounty` case (attacker-adjacent issuer error), here the loss can also occur unintentionally: any wallet/dApp flow that deletes an account or rotates/removes a gas key without first draining its balance to zero causes silent, irreversible token destruction, with no corrective path once the transaction is applied and state is committed.

### Likelihood Explanation
High likelihood of accidental triggering: gas keys are a new (v85, `GasKeys` feature) primitive intended to hold spendable balances for meta-transaction-style gas sponsorship (`TransferToGasKey`/`WithdrawFromGasKey`). Typical account/gas-key lifecycle tooling (wallets, relayers) that deletes stale keys or deletes an account for cleanup is likely to leave non-zero, sub-1-NEAR residual balances, which this code path silently burns instead of refunding. No attacker collusion, privileged role, or malicious peer is needed — a single unprivileged transaction signer suffices to trigger the loss (either against their own funds or, in automated account-closure flows, on behalf of end users who are the true fund owners).

### Recommendation
Include the computed gas-key balance sum (and per-key balance on `DeleteKeyAction`) in the refund receipt sent to the beneficiary (`Receipt::new_balance_refund`) instead of, or in addition to being capped for burning; alternatively, require gas-key balances to be withdrawn to zero (via `WithdrawFromGasKey`) before allowing `DeleteKeyAction`/`DeleteAccountAction` to succeed, mirroring how `DeleteAccountAction` already refuses accounts with non-zero locked stake. If burning small residual dust is intentional for storage-cost/DoS reasons, the threshold and the burn-vs-refund tradeoff should at minimum be surfaced to users before signing (client-side warnings) and reduced from full-NEAR-scale amounts to genuinely dust-level amounts.

### Proof of Concept
1. Create account `alice.near` with a full-access key.
2. Call `AddKey` to add a gas key, then `TransferToGasKey` to fund it with, e.g., `0.9 NEAR` (`transfer_to_gas_key`, tested in `access_keys.rs`).
3. Submit `DeleteKeyAction` for that gas key (or `DeleteAccountAction` with `beneficiary_id = bob.near`).
4. Observe: `action_result.tokens_burnt == 0.9 NEAR` (as asserted by `test_delete_account_burns_gas_key_balances` / `test_delete_account_gas_key_balance_at_threshold`), and no receipt refunds this amount to `alice.near` or `bob.near` — the `0.9 NEAR` is permanently removed from total supply, unrecoverable by any party.     fn test_delete_account_burns_gas_key_balances() {
        let (account_id, public_key, access_key) = test_account_keys();

            .map(|i| PublicKey::from_seed(KeyType::ED25519, &format!("gas_key_{i}")))

        let mut account = get_account(&state_update, &account_id).unwrap().unwrap();
        for public_key in &public_keys {
            add_gas_key_to_account(&mut state_update, &mut account, &account_id, public_key);

        // Fund each gas key with different amounts
        let deposit_amounts = [
            Balance::from_yoctonear(100_000),
            Balance::from_yoctonear(200_000),
            Balance::from_yoctonear(300_000),
        ];
        for (public_key, amount) in public_keys.iter().zip(deposit_amounts.iter()) {
            transfer_to_gas_key(&mut state_update, &account_id, public_key, *amount);
        }
        state_update.commit(StateChangeCause::InitialState);

        let action_result = test_delete_account(
            &account_id,
            AccountContract::from_local_code_hash(CryptoHash::default()),
            100,
            PROTOCOL_VERSION,
            &mut state_update,
        );
        assert!(action_result.result.is_ok());

        // Verify total burned balance equals sum of all gas key balances
        let expected_burnt =
            deposit_amounts.iter().fold(Balance::ZERO, |acc, x| acc.checked_add(*x).unwrap());
        assert_eq!(action_result.tokens_burnt, expected_burnt);
