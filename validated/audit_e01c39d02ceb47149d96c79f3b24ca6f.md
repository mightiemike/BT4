### Title
Unbounded native recursion in compiled-class-hash bytecode segment hashing crashes the sequencer on a crafted DECLARE class - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
`bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recurses over a `NestedIntList`/`HashableNestedIntList` bytecode-segment structure with no recursion-depth bound. This structure is derived from the CASM produced by compiling an attacker-submitted Sierra class, and the hashing call runs natively in the sequencer's own process (not inside the resource-limited compiler subprocess). A crafted class that yields a deeply nested segment structure can overflow the native stack and crash the process computing/validating the compiled class hash.

### Finding Description
`SierraCompiler::compile` in `crates/apollo_compile_to_casm/src/lib.rs` (lines 60-74) invokes the Sierra→CASM compiler in a subprocess with CPU/memory `ResourceLimits` (see `crates/apollo_compile_to_casm/src/compiler.rs`), but the subsequent hash computation:
```
let executable_class = self.compiler.compile(class)?;   // subprocess, resource-limited
let executable_class_hash = executable_class.hash(&HashVersion::V2);  // NOT resource-limited, runs in main process
``` [1](#0-0) 
happens back in the calling (unsandboxed) process. `hash()` calls into `hash_inner` → `bytecode_hash` → `bytecode_hash_node`:
```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
{
    if node.is_leaf() { ... }
    else {
        let inner_nodes = node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child)).collect_vec();
        ...
    }
}
``` [2](#0-1) 
There is no depth limit or iterative rewrite here — recursion depth equals the nesting depth of `bytecode_segment_lengths` (a `NestedIntList` produced by the Cairo compiler from the Sierra program's function/branch structure, per `get_bytecode_segment_lengths`): [3](#0-2) 

This same `hash()`/`HashableCompiledClass` trait is invoked directly and unbounded in multiple reachable code paths beyond the gateway's initial declare-compile flow, e.g. `DeclareTransaction::check_compile_class_hash_v2_declaration` in `crates/starknet_api/src/executable_transaction.rs` (lines 226-244), which is called from blockifier's `run_execute` for `DeclareTransaction` (`crates/blockifier/src/transaction/transactions.rs` lines 155-193) during transaction execution/block building — i.e., every time a DECLARE transaction executes with `block_casm_hash_v1_declares` enabled, this recursive hash is recomputed in the sequencer's block-production process, not just the gateway's compile subprocess. This is structurally analogous to CVE-2020-13164: unbounded recursion driven by attacker-controlled nested data (there, a directory-graph cycle in NFS; here, a deeply-nested bytecode segment tree from a crafted Sierra/CASM class) crashes the process handling untrusted input.

### Impact Explanation
A crash of the sequencer process while executing/building a block containing the malicious DECLARE transaction constitutes a network-availability impact: any process performing this hash computation (gateway compile step, or block-building/re-execution during `try_declare`/`check_compile_class_hash_v2_declaration`) can be brought down by a stack overflow, which is not caught by Rust's panic machinery (stack overflow aborts the process, unlike catchable panics). If this hash recomputation occurs during block building/validation (not just gateway pre-checks), a single such DECLARE transaction reaching that stage can crash the sequencer's block-production pipeline, potentially affecting the network's ability to confirm new transactions until the offending class/tx is filtered out.

### Likelihood Explanation
Reachable from a single, unprivileged, ordinary DECLARE transaction/class declaration — no special permissions needed. The attacker only needs to craft a Sierra program whose compiled bytecode segmentation is deeply nested (e.g., through many nested function calls/branches) so that `bytecode_segment_lengths` becomes a deeply nested `NestedIntList::Node` tree. The exact required nesting depth to exhaust a native thread stack is unverified in this analysis — this is the key uncertainty, since typical OS default stack sizes (several MB per thread) may require thousands of nesting levels of `bytecode_hash_node`, and it's unclear how deep the compiler's segment-splitting heuristics can be driven purely through Sierra program structure within existing bytecode-size limits (`max_bytecode_size`, `DEFAULT_MAX_BYTECODE_SIZE`). This bounds the practical exploitability and should be validated empirically (e.g., by measuring recursion depth per byte of code achievable through nested control-flow constructs) before treating this as confirmed exploitable at Medium/High severity.

### Recommendation
Convert `bytecode_hash_node` (and equivalently `create_bytecode_segment_structure_inner` / `BytecodeSegmentNode::hash` in `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`) to an iterative, explicit-stack algorithm, or impose and enforce a strict maximum nesting depth for `bytecode_segment_lengths` before hashing, rejecting classes whose segment structure exceeds a safe bound. Additionally, consider running class-hash computation under the same resource-limited/sandboxed execution as the Sierra→CASM compilation step, so a stack overflow there cannot crash the parent sequencer process.

### Proof of Concept
Not independently verified in this analysis; would require constructing a Sierra contract (within existing `max_bytecode_size` limits) whose compiled CASM produces a `bytecode_segment_lengths` `NestedIntList` with recursion depth sufficient to exhaust the default native stack (typically requiring measurement/experimentation against the compiler's actual segment-splitting behavior, e.g. via deeply nested `if`/match branches or nested function calls), then submitting it as a DECLARE transaction and observing a process crash (SIGSEGV/stack overflow) rather than a graceful compilation error during hash computation in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`.

```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
