Based on my investigation, I found a concrete analog to the `AssetLock` "decreasing lock end time" bug class in the legacy freeze/resource-lock actuators of java-tron.

### Title
Freezing additional balance can decrease an account's existing resource-lock expire time - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.execute()` (and its TVM-native-contract twin `FreezeBalanceProcessor.execute()`) recompute `expireTime = now + frozenDuration * FROZEN_PERIOD` on every freeze call and unconditionally overwrite the account's stored expiration via `AccountCapsule.setFrozenForBandwidth/setFrozenForEnergy/setFrozenForTronPower`, without ever comparing the new expire time to the account's existing (potentially longer) expire time.

### Finding Description
When a user adds more frozen balance to an already-frozen position, the balance is accumulated (`frozenBalance + accountCapsule.getFrozenBalance()` / `getEnergyFrozenBalance()` / `getTronPowerFrozenBalance()`), but the expire time is simply replaced with the newly computed `now + duration`: [1](#0-0) [2](#0-1) 

The same pattern is duplicated in the TVM native contract path used by `freeze()` opcode: [3](#0-2) 

The setters themselves blindly overwrite the stored `expireTime` field with whatever value is passed in, with no guard against decreasing it: [4](#0-3) [5](#0-4) [6](#0-5) 

Critically, `validate()` only checks that the submitted `frozenDuration` falls within `[minFrozenTime, maxFrozenTime]` — it never checks the new expire time against the account's *existing* expire time: [7](#0-6) 

This is the exact same root cause pattern as the `AssetLock.sol` finding: a "top-up" operation recomputes and replaces the lock/expire timestamp without taking the maximum of old and new expiry.

Notably, java-tron's own codebase demonstrates awareness of this bug class: `DelegateResourceActuator.validate()` explicitly added a `validRemainTime()` guard specifically to prevent a new (shorter) lock period from reducing an existing lock's remaining time for the newer V2 lock-delegation flow: [8](#0-7) [9](#0-8) 

However, this protective check was never applied to the older `FreezeBalanceActuator`/`FreezeBalanceProcessor` freeze-in-place paths (BANDWIDTH/ENERGY/TRON_POWER self-freeze), which remain exposed to the same class of issue.

### Impact Explanation
If `minFrozenTime` and `maxFrozenTime` can differ (this is governance-configurable via `DynamicPropertiesStore`, and `needCheckFrozeTime` can even be disabled entirely for test/config purposes via `CommonParameter.getCheckFrozenTime()`), a user holding a long-locked freeze position (e.g., frozen for governance/vote-locking or resource-guarantee purposes) can submit a follow-up `FreezeBalanceContract` with a smaller `frozenDuration`, which will silently shorten their previously-committed lock/expire time system-wide for that resource type. This undermines any invariant/expectation that frozen TRX for BANDWIDTH/ENERGY/TRON_POWER remains locked for at least as long as originally committed, and could be leveraged to unfreeze/reclaim balance earlier than the protocol intended for that freeze operation.

### Likelihood Explanation
The `FreezeBalanceActuator`/`FreezeBalanceProcessor` code paths are directly reachable by any unprivileged account (no special role required) — freezing is a routine, permissionless user operation, and the vulnerable code is exercised on every repeated freeze call to the same resource type. The exact severity depends on the currently configured `minFrozenTime`/`maxFrozenTime` values and whether `needCheckFrozeTime` is enabled in production, which I was not able to fully confirm from the index (values are read via `dynamicStore.getMinFrozenTime()`/`getMaxFrozenTime()` and are configurable, but I could not verify current on-chain/default configuration within the remaining tool budget).

### Recommendation
In `FreezeBalanceActuator.execute()` and `FreezeBalanceProcessor.execute()`, when accumulating additional frozen balance onto an existing frozen position, compute the new expire time as `Math.max(existingExpireTime, now + duration)` rather than unconditionally overwriting it — mirroring the `validRemainTime()` protection already implemented in `DelegateResourceActuator`.

### Proof of Concept
1. Account A calls `FreezeBalanceContract` with `frozenDuration = maxFrozenTime` (e.g., a long lock), resulting in `accountCapsule.setFrozenForBandwidth(balance, now + maxFrozenTime*FROZEN_PERIOD)`.
2. Later, Account A calls `FreezeBalanceContract` again for BANDWIDTH with a small additional `frozenBalance` and `frozenDuration = minFrozenTime` (a shorter duration, still passing the `validate()` range check at `FreezeBalanceActuator.java:203-214`).
3. `execute()` recomputes `expireTime = now + minFrozenTime*FROZEN_PERIOD` and calls `accountCapsule.setFrozenForBandwidth(newFrozenBalanceForBandwidth, expireTime)`, which overwrites the previously far-future expire time with the earlier one at `FreezeBalanceActuator.java:88-93`.
4. The full frozen balance (original + new) becomes unfreezable at the new, earlier expire time — effectively shortening the original lock commitment.

  private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime,
      long now) throws ContractValidateException {
    long remainTime = expireTime - now;
    if (lockPeriod * BLOCK_PRODUCED_INTERVAL < remainTime) {
      throw new ContractValidateException(
          "The lock period for " + resourceCode.name() + " this time cannot be less than the "
              + "remaining time[" + remainTime + "ms] of the last lock period for "
              + resourceCode.name() + "!");
    }
  }
