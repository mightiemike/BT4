### Title
Replay-verify skips state/hot-state/position checkpoint-hash comparison, allowing silent state-root divergence to pass as a successful replay - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the chunk executor's replay-verification path (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` pulled from backup/replay data. The function itself contains a `TODO` acknowledging that it "ignores the checkpoint hashes," meaning a state-root divergence between local re-execution and the authenticated ledger can go undetected by this verification path.

### Finding Description
`ensure_match_transaction_info` checks status, gas used, write-set hash, and event-root hash against the supplied `TransactionInfo`, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`: [1](#0-0) 

This function is invoked from `verify_execution` in the chunk executor's replay-verify tool (`db-tool`'s `replay_on_archive` flow), which re-executes historical transactions and compares the freshly computed `TransactionOutput` against the on-disk/backup `TransactionInfo` for each version: [2](#0-1) 

By contrast, the authenticated proof-verification path used when *ingesting* backup data (`TransactionOutputListWithProofV2::verify`) also omits the checkpoint-hash comparison between `txn_output` and `txn_info`, relying instead on `self.proof.verify(ledger_info, ...)` to bind the `TransactionInfo` (including its checkpoint hash) to the accumulator root that is itself signed by validators: [3](#0-2) 

The critical gap is in `verify_execution`/`ensure_match_transaction_info`: this is the code path that is supposed to catch *local execution divergence* from the canonically committed ledger during replay-verify (e.g., auditing a full node's VM/state-store logic against historical, signature-verified data). Since the state checkpoint hash — the actual Merkle root of post-transaction state, which is the strongest state-commitment invariant — is never recomputed and compared here, a bug that produces the exact same write set, events, gas, and status but writes them into the wrong keys/values combination in a way that state-tree materialization diverges (or, more realistically, any JMT/hot-state root computation bug in the executor) would not be flagged by `verify_execution`.

### Impact Explanation
This affects the state-proof integrity guardrail that operators and node runners rely on: `db-tool replay-verify` is the standard tool for confirming that a local Aptos node's execution/storage stack reproduces the exact canonical ledger state from historical signed data (used for auditing backups, validating new client implementations, and building trust in bootstrap/fast-sync paths). Silently passing verification despite a genuine state-root divergence means an underlying hard-fork-class bug (e.g., in JMT computation, hot-state checkpointing, or position-state materialization) could go undetected by the one mechanism designed to catch exactly that class of bug. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" category, because the divergence would only manifest between two implementations/versions of the state-computation logic, not within a single execution.

### Likelihood Explanation
Likelihood of the checkpoint-hash divergence itself is low (it requires an independent state-computation bug), but the likelihood that such a bug would go **undetected** by replay-verify is effectively certain given the current code — the code comment itself documents that this is a known, intentional gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"). This is a verification-tooling gap rather than a live consensus-safety violation, since validators independently compute and check the state-checkpoint hash during normal block execution and voting; the exposure is specifically to replay-verify/audit tooling and to any downstream consumer that trusts a "successful replay" result as proof of state-root correctness.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, where enabled, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the locally computed checkpoint and the `TransactionInfo` supplied for verification, and thread the locally computed checkpoint hash into `verify_execution` so a genuine mismatch causes replay-verify to fail loudly instead of silently succeeding.

### Proof of Concept
Not independently reproducible from static analysis alone — the code path is a comparison-omission (missing assertion) rather than an exploitable transaction sequence. The concrete defect is that `ensure_match_transaction_info` at [4](#0-3)  never reads or compares `txn_info.state_checkpoint_hash()` even though `TransactionInfo` carries that field, and `verify_execution` at [2](#0-1)  is the only caller wiring locally re-executed output into this check during replay. Demonstrating impact would require injecting a state-materialization bug (e.g., patching the JMT/hot-state update logic) and showing that `db-tool replay-verify` still reports success on the affected version range — this would need a running Devin session with build/test infrastructure to confirm empirically, which is outside what static code review can prove.
