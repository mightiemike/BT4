### Title
Integer truncation in standby-witness reward distribution silently loses TRX every maintenance cycle - ([File: consensus/src/main/java/org/tron/consensus/dpos/IncentiveManager.java])

### Summary
`IncentiveManager.reward(...)` distributes a fixed `totalPay` amount among the top-127 standby witnesses proportionally to their vote counts, using floating-point division followed by a truncating `(long)` cast inside a loop. Each witness's share is floored independently, and the leftover remainder (the difference between `totalPay` and the sum of all floored shares) is never accounted for, credited, or burned. This is a direct analog of the reported bug: a total amount split across N recipients by proportional share, where per-recipient integer truncation leaves a remainder unaccounted for.

### Finding Description
`IncentiveManager.reward` computes `eachVotePay = totalPay / voteSum` conceptually and, for each witness, does `pay = (long) (voteCount * ((double) totalPay / voteSum))`, then credits `pay` to the witness account's allowance: [1](#0-0) 

The same pattern exists in the newer reward path, `MortgageService.payStandbyWitness`, which computes `eachVotePay = (double) totalPay / voteSum` once and then, per witness, truncates `pay = (long) (w.getVoteCount() * eachVotePay)`: [2](#0-1) 

`totalPay` is a fixed configured value (`getWitness127PayPerBlock()` / `getWitnessStandbyAllowance()`), representing the exact amount that is supposed to be fully distributed among the 127 standby witnesses each maintenance cycle. Because each witness's share is truncated toward zero independently (via `(long)` cast) rather than tracking and redistributing the cumulative rounding error, `sum(pay_i) <= totalPay` almost always, with the deficit growing with the number of witnesses and being silently dropped — never credited to any account and never explicitly burned via `dynamicPropertiesStore.burnTrx(...)` or similar. This mirrors the reported Strategy.sol issue where `toSend = assets * share / 1000` truncates per-lender and the remainder is left unprocessed.

### Impact Explanation
This causes a permanent, recurring token/accounting divergence: the amount the protocol intends to pay out to standby witnesses each cycle (`totalPay`) is systematically greater than what is actually credited, with the shortfall permanently and silently disappearing from expected issuance rather than being accounted for anywhere in the ledger (no burn record, no carry-over to next cycle, no residual credited to any address). Over many maintenance cycles (which run automatically, roughly every 6 hours on mainnet) this is a state-accounting/invalid-issuance-style bug: the actual total paid to standby witnesses diverges from the value implied by chain parameters, and no mechanism recovers or accounts for the difference.

### Likelihood Explanation
This code path executes automatically and unconditionally in every maintenance cycle (`MaintenanceManager.doMaintenance` → `incentiveManager.reward(...)`, and `payStandbyWitness` in the active reward algorithm) whenever there are standby witnesses with nonzero votes — no privileged role or attacker action is required to trigger it. The truncation occurs essentially every cycle whenever `voteCount * totalPay` isn't perfectly divisible by `voteSum` for all 127 witnesses, which is the common case given real-world vote distributions.

### Recommendation
Track the cumulative amount already distributed and pay the last recipient (or accumulate rounding remainders) the residual, e.g. `remaining = totalPay; for each witness except the last: pay = floor(voteCount*totalPay/voteSum); remaining -= pay; credit(pay); credit last witness remaining;` Alternatively, use integer (BigInteger) arithmetic throughout and explicitly credit the truncation remainder to a defined account (e.g., blackhole/burn) so that `sum(pay_i) + remainder == totalPay` always holds and is explicitly accounted for in the ledger.

### Proof of Concept
Given 3 standby witnesses with `voteCount = [1, 1, 1]` (`voteSum = 3`) and `totalPay = 10`:
1. `eachVotePay = 10/3 = 3.333...`
2. For each witness: `pay = (long)(1 * 3.333...) = 3`
3. Total credited = `3 + 3 + 3 = 9`
4. `totalPay (10) - 9 = 1` is silently lost every cycle this vote distribution recurs — never credited to any witness, never burned, and not reflected anywhere in the accounting state. [3](#0-2)
