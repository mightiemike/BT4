Based on the investigation, I found a concrete analog in this codebase: a divergence between how the **Blockifier** (native sequencer execution) and the **Starknet OS** (Cairo-based re-execution/proving) parse an "empty span" argument passed into syscalls (`emit_event_syscall`, `library_call_syscall`) — the same *"one environment supports the construct, the other does not"* bug class as the EIP-1167/zkSync opcode issue.

### Title
Blockifier vs Starknet OS divergence on null (`felt-zero`) empty-span syscall arguments causes OS re-execution failure - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
`TxInfo.account_deployment_data` is built by the OS as a `Span<felt252>` with `cast(0, felt*)` start/end pointers when a `DeployAccount` V3 transaction carries no deployment data. When a Cairo1 contract forwards this raw span into `emit_event_syscall` or `library_call_syscall`, the Blockifier's request-reading logic accepts the "null" (felt-zero, felt-zero) span as a valid empty span, but the equivalent Cairo code path in the Starknet OS dereferences the same felt-zero pointer expecting a relocatable, and aborts.

### Finding Description
The regression is documented directly in the test-fixture comment: [1](#0-0) . This shows that forwarding `tx_info.account_deployment_data` (empty for `DeployAccount` V3) through `emit_event_syscall`/`library_call_syscall` produces two equal felt-zero endpoints, and while "native Blockifier (relocatable endpoints) succeeds," an OS build that does `cast(0, felt*)` "aborts with 'Expected relocatable' (STARKNET-96)."

On the Blockifier side, the fix/acceptance of null empty spans is explicit and tested: [2](#0-1) , and for the deprecated (Cairo0) parser as well: [3](#0-2) .

The relevant syscall-argument construction path on the OS side lives in `syscall_impls.cairo`, which builds `ExecutionInfo`/call parameters (including forwarded calldata spans) that are later dereferenced by `contract_call_helper` / `execute_library_call`: [4](#0-3) . The transaction-hash/transaction_impls code that populates `account_deployment_data` for the OS's `TxInfo` struct is in `transaction_impls.cairo`, referenced 40 times in that file, confirming this field is OS-constructed and thus subject to the `cast(0, felt*)` construction described in the fixture comment.

### Impact Explanation
If the Starknet OS genuinely still aborts on this null-span pattern (as asserted by the fixture comment and the dedicated `STARKNET-96` regression tests), then a transaction that the sequencer's Blockifier executes successfully and includes in a block will fail when the Starknet OS re-executes it during proving. This is a direct instance of the "honest-node divergence" / "network unable to confirm new transactions" class: the sequencer commits a block whose transactions cannot be proven by the OS, blocking state commitment for that block and potentially halting the chain's ability to progress until the divergence is patched or the offending transaction/class is excluded.

### Likelihood Explanation
This is reachable by *any* unprivileged account deployer: a `DeployAccount` V3 transaction naturally has empty `account_deployment_data`, and any account/contract constructor (or any call reachable during validation/execution) that forwards `tx_info.account_deployment_data` into `emit_event_syscall` or `library_call_syscall` — a completely ordinary and permitted Cairo1 pattern — triggers the divergence. The bug class was serious enough to warrant a dedicated feature contract (`empty_span_emitting_account.cairo`) and dedicated unit tests (`null_empty_span.rs`), and a tracking ID (`STARKNET-96`), which indicates the project treats it as a materially exploitable/critical correctness issue, not a purely theoretical one.

### Recommendation
Ensure the Starknet OS Cairo code that decodes span/array syscall arguments treats two syntactically-equal `felt` endpoints (including `cast(0, felt*)`) as a valid empty span *without* first requiring them to be relocatable, matching the Blockifier's `read_felt_array` semantics validated in `null_empty_span.rs`. Add an explicit OS-side (Cairo) unit/integration test mirroring `empty_span_emitting_account.cairo` through actual Starknet OS re-execution (not just Blockifier) to close the parity gap and prevent regressions.

### Proof of Concept
1. Submit a `DeployAccount` V3 transaction for an account contract whose constructor executes exactly the pattern in `empty_span_emitting_account.cairo` — read `tx_info.account_deployment_data` (empty for V3) and forward it as calldata into `emit_event_syscall` and `library_call_syscall`. [5](#0-4) 
2. The Blockifier executes this successfully during sequencing/block-building because it accepts felt-zero/felt-zero as an empty span, per `read_felt_array` (validated in `null_empty_span.rs`).
3. When the Starknet OS re-executes the same block to produce the proof, its Cairo decoding logic for the equivalent span (`cast(0, felt*)`) fails with "Expected relocatable," aborting OS execution for a transaction the sequencer already committed. [6](#0-5) 

Note: I could not directly execute the Starknet OS Cairo program to independently confirm the abort still reproduces on the current `main` tree (only the test-fixture comment and the `STARKNET-96`-tagged tests were available via the index) — this should be verified by running the `starknet_os_flow_tests` (which also reference `STARKNET-96`, per the grep results) against `empty_span_emitting_account.cairo` in a full Devin session, since the code that executes this scenario end-to-end may exceed what is indexed here.

fn vm_with_deprecated_array(
    array_size: MaybeRelocatable,
    data_ptr: MaybeRelocatable,
) -> (VirtualMachine, Relocatable) {
    let mut vm = VirtualMachine::new(false, false);
    let array_ptr = vm.add_memory_segment();
    vm.load_data(array_ptr, &[array_size, data_ptr]).unwrap();
    (vm, array_ptr)
}
