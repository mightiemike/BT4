## Finding: Caller deposit is permanently lost when a NEP‑141 token's `storage_balance_of` call fails or returns malformed data in the Wallet Contract

### Title
Caller deposit not refunded when `storage_balance_of` call fails/returns unexpected data in ETH-wallet-contract ERC-20 emulation - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The reported bug class is: a heuristic used to gate an action based on a probe call to another contract (a `token0()` low-level call) can fail for legitimate, non-malicious counter-parties, and the failure path leaves value permanently stuck with no recovery. The NEAR ETH-wallet-contract (`near-wallet-contract`) contains an analogous pattern: before forwarding an ERC‑20 (NEP‑141) transfer, it probes the target token with `storage_balance_of` to decide whether a `storage_deposit` is needed. This probe's two error branches ("call failed" / "unexpected response format") do not refund the relayer's `caller_deposit`, unlike the sibling `rlp_execute_callback` which explicitly does refund on the same class of failure.

### Finding Description
`nep_141_storage_balance_callback` [1](#0-0)  issues a cross-contract probe to the token's `storage_balance_of` and inspects the raw promise result:
- If `PromiseResult::Failed` (e.g. the token doesn't implement `storage_balance_of`, panics, or is out of gas), it returns an `ExecuteResponse::error` immediately.
- If `PromiseResult::Successful` but the bytes don't deserialize as `Option<StorageBalance>` (e.g. any token that is not a byte-perfect NEP‑141 implementation), it also returns immediately with an error.

Neither of these early-return branches refunds `caller_deposit`, even though `caller_deposit` represents NEAR that the relayer attached specifically to be refunded to the relayer's account after the wallet completes (successfully or not) [2](#0-1) .

Contrast this with `rlp_execute_callback`, the sibling callback used for the "happy path" and for the base-transfer/address-registrar path, which explicitly refunds `caller_deposit` on `PromiseResult::Failed`: [3](#0-2) 

Because the nonce is already incremented before the `storage_balance_of` probe is issued (in `inner_rlp_execute`, for any transaction kind other than `EOABaseTokenTransfer` with an address check) [4](#0-3) , the user's ERC‑20-transfer transaction is consumed (cannot be replayed) as soon as it hits this code path, so there is no retry that could recover the deposit. Any legitimate NEP‑141-like token that is not a byte-perfect implementation of the standard (e.g. one whose `storage_balance_of` panics for an unregistered account instead of returning `null`, or one that returns a slightly different JSON shape) will always land in one of the un-refunded error branches, permanently trapping the relayer's attached NEAR in the wallet contract with no on-chain recovery path — the same shape of bug as the reported "token0()/fallback heuristic locks non-conforming but legitimate tokens' funds forever."

### Impact Explanation
Funds attached by a relayer (`caller_deposit`, sized to cover the wallet's expected gas/refund needs) are permanently frozen in the wallet contract instance whenever the emulated ERC‑20 target token: (a) does not implement `storage_balance_of` and the call fails, or (b) returns a response that does not deserialize into `Option<StorageBalance>`. Since the transaction is unprivileged (any relayer using the public `rlp_execute` entry point on a NEAR ETH-implicit account) and the nonce is already consumed by the time the flow reaches this callback, there is no way to retry or recover the lost deposit — this constitutes permanently frozen funds triggered by an ordinary transaction, matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
This is reachable by any relayer/user emulating an ERC-20 `transfer` through the ETH-wallet-contract's `rlp_execute` for any token account that isn't a strict, standards-compliant NEP-141 implementation (a very common situation, since many FT contracts implement variants of `storage_balance_of` inconsistently, or simply don't implement it at all, similar to how many ERC20-like tokens on Ethereum implement/omit `token0()` or a fallback in idiosyncratic ways). No attacker privileges are required — a normal relayer operating in good faith against a non-conforming token triggers the loss.

### Recommendation
Mirror the refund logic from `rlp_execute_callback` inside both early-return branches of `nep_141_storage_balance_callback` (`PromiseResult::Failed` and the JSON-deserialize failure case): refund `caller_deposit` to its `account_id` before returning the `ExecuteResponse` error, exactly as done at [5](#0-4) .

### Proof of Concept
1. Deploy an ETH-implicit account with the wallet contract as its global contract, funded, and with a relayer key added (as in `test_wallet_contract_interaction` / the ERC20 emulation test harness) [6](#0-5) .
2. Deploy a "token" contract that does not implement `storage_balance_of` at all (or implements it but returns a JSON shape other than `Option<StorageBalance>`, e.g. returns a bare object instead of `null`/`{...}` per the NEP-141 spec).
3. As the relayer, submit an RLP-encoded ERC‑20 `transfer(address,uint256)` transaction (selector `ERC20_TRANSFER_SELECTOR`) targeting that token, attaching a `caller_deposit` (non-zero NEAR) via `rlp_execute` [7](#0-6) .
4. Observe: the wallet issues `storage_balance_of` to the token; the call fails or its result fails to deserialize; `nep_141_storage_balance_callback` returns an error `ExecuteResponse` without refunding `caller_deposit` [2](#0-1) .
5. Confirm the relayer's attached deposit is not returned (balance check before/after), and the transaction's nonce has already been incremented, so it cannot be resubmitted to recover the funds.
