### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by the HMAC signature, allowing cross-tenant webhook replay to resolve a victim shop's real offline session - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` verifies the webhook HMAC solely over `rawBody` and then reads the `X-Shopify-Shop-Domain` header verbatim into the `domain` field of the returned `WebhookValidationValid` object, without any check that `domain` corresponds to the shop that actually produced the HMAC-signed body. Downstream, `authenticateWebhookFactory` (`shopify-app-remix`/`shopify-app-react-router`) passes this unverified `check.domain` directly into `ensureValidOfflineSession(params, check.domain)`, which loads the real, stored offline session (with a live access token) for whatever shop domain was supplied in the header.

### Finding Description
`checkWebhooksHeaders` reads `domain` from `WEBHOOK_HEADER_NAMES[WebhookType.Webhooks].domain` (the `X-Shopify-Shop-Domain` header) purely via `getRequiredHeader`, with no cryptographic binding to the request body or HMAC: [1](#0-0) 

The HMAC check that gates `valid: true` is computed only over `rawBody`, via `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — the domain header is never included in the HMAC input: [2](#0-1) 

Because Shopify computes the webhook HMAC using the app's `apiSecretKey`, which is shared across every shop that installs the app (it is not per-shop), a delivery captured from the attacker's own (legitimately installed) dev/test shop has a valid HMAC purely as a function of `rawBody` and the shared secret — independent of which shop it was delivered to. An attacker who owns a dev shop can therefore take one genuine webhook delivery (`rawBody` + `X-Shopify-Hmac-SHA256`) and resubmit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim's `*.myshopify.com` domain. `validateFactory` returns `valid: true` with `domain` set to the forged victim domain.

`process.ts`'s `callWebhookHandlers` then passes `webhookCheck.domain` straight to `handler.callback(...)` as the shop domain, with no re-verification: [3](#0-2) 

More critically, in the higher-level `shopify-app-remix`/`shopify-app-react-router` packages, `authenticateWebhookFactory` uses this same unverified `check.domain` to look up a real session: [4](#0-3) 

`ensureValidOfflineSession` -> `createOrLoadOfflineSession` computes `api.session.getOfflineId(shop)` from the attacker-controlled `shop` string and loads the corresponding session directly from `sessionStorage`: [5](#0-4) 

If a genuine offline session exists for the victim shop, the webhook handler is invoked with `session`/`admin` bound to the **victim's real access token**, even though the request body/topic/payload are entirely attacker-controlled (subject only to being a validly-formed, HMAC-consistent body from the attacker's own shop).

### Impact Explanation
This breaks tenant isolation for webhook processing: an app built on this library will execute registered webhook handlers — including any `admin.graphql`/`admin.rest` calls those handlers make — under the *victim* shop's live access token and session, triggered by a request whose payload the attacker fully controls (subject to `HMAC(rawBody)` matching the shared secret, which is trivially satisfiable by replaying/crafting a delivery through the attacker's own shop). Concrete scoped impact: cross-tenant webhook processing with the wrong shop's session context, matching Shopify's "cross-tenant data/state access" bounty class. The severity depends heavily on what a given app's webhook handler does with the payload (e.g., if a `PRODUCTS_UPDATE` handler in the target app writes attacker-supplied payload fields to the shop via Admin API using the resolved session, the attacker can mutate victim shop data).

### Likelihood Explanation
Preconditions are low-privilege and realistic: attacker needs only their own dev/test shop with the target app installed (any merchant can install most public apps), can trigger or observe at least one real webhook delivery for a topic the target app has a handler for, and needs the target app to already have an offline session stored for a known/targetable victim shop domain (victim must also have the app installed). No secrets, MITM, or app-developer privileges are required — this is a pure unprivileged replay against the public webhook endpoint. The main constraint is that the attacker needs to guess or otherwise learn a valid victim `myshopify.com` domain with the app installed, which is a much weaker barrier than needing the API secret.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header (or any header) as an authenticated identifier. Either:
1. Include the domain (and other identity-relevant headers) as part of the HMAC-verified data, or
2. Require host apps/the library to cross-check the resolved `domain` against an independent, trusted record — e.g., verify that a session/webhook subscription was registered for that exact `webhookId`/topic combination for that domain (Shopify webhook IDs are unique per delivery) before using it to key session storage lookups, and/or reject the request if the shop implied by the payload contents (where available) conflicts with the header.
3. At minimum, document explicitly in `validate.ts`/`process.ts` that `domain` is unauthenticated header data and must not be used directly to resolve sessions without additional shop-membership verification, and correct `ensureValidOfflineSession`'s call sites in `shopify-app-remix`/`shopify-app-react-router` webhook authenticate flows accordingly.

```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/validate-domain-forgery.test.ts
import {validateFactory} from '../validate';
import {createSHA256HMAC} from '../../../runtime/crypto';
import {HashFormat} from '../../../runtime/crypto/types';
import {testConfig} from '../../__tests__/test-config'; // adjust to actual test helper

test('accepts a valid HMAC with a forged X-Shopify-Shop-Domain header', async () => {
  const config = testConfig(); // uses a fixed apiSecretKey shared by all shops
  const rawBody = JSON.stringify({id: 1, title: 'attacker-controlled payload'});

  // HMAC computed by Shopify for the attacker's own shop delivery,
  // using the shared app secret — valid regardless of shop.
  const hmac = await createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64);

  const validate = validateFactory(config);
  const result = await validate({
    rawBody,
    rawRequest: {
      method: 'POST',
      url: '/webhooks',
      headers: {
        'X-Shopify-Hmac-Sha256': hmac,
        'X-Shopify-Topic': 'products/update',
        'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // forged, not the attacker's shop
        'X-Shopify-API-Version': '2024-01',
        'X-Shopify-Webhook-Id': 'forged-webhook-id',
      },
      body: rawBody,
    },
  });

  expect(result.valid).toBe(true);
  // domain is attacker-controlled/forged, yet marked valid
  expect((result as any).domain).toBe('victim-shop.myshopify.com');
});
```

```typescript
import {AppDistribution, BasicParams} from '../types';

export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
}
```
