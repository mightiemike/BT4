### Title
Divergent vote-reallocation logic between TVM native-contract path and normal transaction path for UnfreezeBalanceV2 causes non-deterministic VotesCapsule state - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java])

### Summary
`UnfreezeBalanceV2Processor.updateVote()` (reached via the TVM `UNFREEZEBALANCEV2` opcode) contains an extra guard `!VMConfig.allowTvmVote()` that is absent from `UnfreezeBalanceV2Actuator.updateVote()` (the normal-transaction path). Because `allowTvmVote` (`allowTvmFreeze`'s vote-adjustment flag) and `allowTvmFreezeV2` (the flag gating the `UNFREEZEBALANCEV2` opcode itself, see `OperationRegistry.appendFreezeV2Operations`) are independent, separately-toggled committee parameters, an unprivileged attacker can reach two logically-equivalent unfreeze operations whose resulting `VotesCapsule`/`AccountCapsule` vote lists differ depending only on which entrypoint (opcode vs. broadcast transaction) they use.

### Finding Description

`UnfreezeBalanceV2Processor.updateVote` (actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java:207-216), reached from the TVM `UNFREEZEBALANCEV2` opcode via `Program.unfreezeBalanceV2` → `UnfreezeBalanceV2Processor.execute`, adds an extra short-circuit: [2](#0-1) 

The `UNFREEZEBALANCEV2` opcode itself is gated only by `VMConfig.allowTvmFreezeV2`, not by `allowTvmVote`: [3](#0-2) 

`allowTvmVote` and `allowTvmFreezeV2` are distinct committee-controlled proposal flags in `VMConfig.Snapshot` (`allowTvmVote` at line 30, `allowTvmFreezeV2` at line 34), each independently toggled via `initAllowTvmVote`/`initAllowTvmFreezeV2`: [4](#0-3) 

In any network state where `allowTvmFreezeV2 = true` (opcode reachable) but `allowTvmVote = false`, an attacker's contract invoking `UNFREEZEBALANCEV2` will skip the entire vote-reallocation block in `UnfreezeBalanceV2Processor.updateVote`, leaving the account's stale `VotesList`/`VotesCapsule` untouched (over-representing voting power relative to remaining frozen TRX), whereas the exact same unfreeze performed through a normal `UnfreezeBalanceV2Contract` broadcast transaction always executes `UnfreezeBalanceV2Actuator.updateVote`, correctly recalculating and shrinking the account's votes and `VotesCapsule.newVotes`. This is a genuine independent-duplicate-logic divergence — the two implementations are not derived from a shared helper, so this guard was added to one copy and never mirrored to the other.

### Impact Explanation
Given identical starting `AccountCapsule` state and identical unfreeze parameters, the choice of execution path (opcode vs. transaction) produces different `VotesCapsule`/`AccountCapsule.VotesList` results — breaking the deterministic-execution/one-time-settlement invariant the question tests for. Concretely, under the `allowTvmFreezeV2=true, allowTvmVote=false` configuration window, an attacker can retain votes disproportionate to their remaining frozen (voting-power-backing) balance by performing unfreezes exclusively through the TVM opcode path instead of the normal transaction path, inflating their effective voting weight relative to actual locked stake until `allowTvmVote` is turned on (at which point some other path finally reconciles votes, but in the interim consensus/vote tallies are computed from stale, over-stated vote counts).

### Likelihood Explanation
This requires a specific but plausible historical/config precondition: `allowTvmFreezeV2` enabled while `allowTvmVote` disabled. Both are independent committee proposal parameters (not attacker-controlled), so exploitability depends on network configuration state, not on any privilege the attacker holds. Given the flags were introduced as separate features (freeze-v2 TVM opcodes vs. TVM vote support), there is a realistic window — e.g. on any network/testnet that activates TVM FreezeV2 opcodes before activating TVM vote reallocation — during which this divergence is directly triggerable by any account holding votes and calling a contract that invokes `UNFREEZEBALANCEV2`.

### Recommendation
Remove the `!VMConfig.allowTvmVote()` guard from `UnfreezeBalanceV2Processor.updateVote`, or (better) factor `updateVote`/`updateTotalResourceWeight`/`unfreezeExpire` into a single shared implementation used by both `UnfreezeBalanceV2Actuator` and `UnfreezeBalanceV2Processor`, so any future feature-flag change is applied uniformly to both code paths and cannot silently diverge again.

### Proof of Concept
Java differential test plan (framework/src/test):
1. Set `VMConfig.initAllowTvmFreezeV2(1L)` and `VMConfig.initAllowTvmVote(0L)`.
2. Create an `AccountCapsule` with a non-empty `VotesList` (e.g. votes summing to more than the account's `AllTronPower`/`TronPower` after unfreeze) and sufficient `FrozenV2` balance for `BANDWIDTH`.
3. Snapshot the account bytes (`accountCapsule.getInstance().toByteArray()`).
4. Path A: call `new UnfreezeBalanceV2Actuator().execute(ret)` via `AccountStore`/`VotesStore`, capture resulting `AccountCapsule` bytes and `VotesCapsule` from `votesStore`.
5. Reset the account/votes stores to the snapshot.
6. Path B: build `UnfreezeBalanceV2Param`, call `new UnfreezeBalanceV2Processor().execute(param, repo)` via a `Repository` wrapping the same stores, capture resulting `AccountCapsule` bytes and `VotesCapsule` via `repo.getVotes`.
7. Assert `Assert.assertEquals(pathA_accountBytes, pathB_accountBytes)` and `Assert.assertEquals(pathA_votesCapsule, pathB_votesCapsule)`.
8. Expect failure: Path A's `VotesList` is recalculated/shrunk while Path B's `VotesList` is left unchanged, demonstrating the divergence.
