### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay/debug verification accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk-executor replay verification, `aptos-debugger`, `aptos-move-cli` replay, and `db-tool`'s `replay_on_archive` to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` taken from a signed `LedgerInfo`/backup. It checks status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

and this verification routine is wired into the real replay/verification call sites that are supposed to catch state divergence:
- Chunk executor's execution-verification path (`verify_execution`), used during state-sync/replay-verify to detect if re-executing a chunk of transactions produces a different result than the trusted, already-committed `TransactionInfo`s: [4](#0-3) 
- `db-tool`'s `replay_on_archive`, whose entire purpose is to re-execute archived transactions and confirm they reproduce the exact recorded ledger state: [5](#0-4) 
- `aptos-debugger` and the Move CLI's transaction-replay/simulation commands use the same call: [6](#0-5) [7](#0-6) 

Because the write-set hash comparison only proves that the *set of key/value writes* produced by re-execution matches what was originally committed, it does not prove that applying those writes into the Sparse/Jellyfish Merkle state tree (or the "position" state tree referenced by `position_state_checkpoint_hash`) yields the same root that was authenticated in the original `TransactionInfo`. A bug in state-tree construction, hot-state merge logic, or the newer "position" (trading-native) state tree could produce a write set that is byte-identical yet, when folded into the tree, yields a different root hash — and this checker would report success anyway.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... accepted as valid" invariant specifically for the verification tooling meant to catch exactly that class of bug. If a bug exists anywhere in state-checkpoint root computation (state SMT update, hot-state root, or the new position/trading-native state root under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), replay-verify, `db-tool replay_on_archive`, and `aptos-debugger`/CLI replay would all silently report success even though the authenticated state root diverges from what local execution actually computes. This directly undermines the primary safety mechanism operators rely on to detect ledger-state corruption during backup verification, disaster recovery, and hard-fork rollout validation — a state/proof-integrity impact in scope per the task's gate ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

### Likelihood Explanation
The gap is unconditional (not behind a feature flag) — it always skips checkpoint-hash comparison regardless of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`'s value, per the code comment. It requires a pre-existing, separate bug in state-root computation to actually manifest as a real corruption; on its own it is a detection-gap rather than a corruption-causing bug. This lowers likelihood of independent exploitation (no attacker can single-handedly leverage this to corrupt state), but it means any future or latent state-root computation bug becomes essentially undetectable by the tooling that exists specifically to catch it, which is a legitimate high-severity gap in defense-in-depth for the class of "hard-fork-only divergence."

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the re-executed output/state-checkpoint computation and the trusted `TransactionInfo`, at least when those hashes are present (i.e., on checkpoint-producing transactions), before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on mainnet, as already flagged in the code's own TODO.

### Proof of Concept
Not independently constructible as a standalone exploit: the gap is a missing check, not a memory/logic bug that a caller can trigger to corrupt data by itself. Demonstrating real impact requires combining it with a separate state-root computation defect (e.g., in `DoStateCheckpoint`, hot-state merge, or the position/trading-native SMT update), which is outside the scope verified here. The verifiable, in-repo evidence is the code and comment cited above, plus the confirmed call sites where this check is the sole state-root safety net during replay/verification (`chunk_executor::verify_execution`, `db-tool::replay_on_archive::execute_and_verify`, `aptos-debugger::print_mismatches`, CLI replay). No feature-flag gating around the skipped comparisons was found in `types/src/transaction/mod.rs`, `aptos_features.rs`, or `aptosdb_reader.rs`/`aptosdb_writer.rs` (only `COMPUTE_TRADING_NATIVE_STATE_ROOTS` references were located, not consumed to conditionally enable the missing checks in this function) — I could not fully trace every consumer of that feature flag within the tool-call budget available, so it remains possible (but unconfirmed) that some other code path enforces checkpoint-hash equality outside this function.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
