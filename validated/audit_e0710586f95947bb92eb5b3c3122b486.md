### Title
Delegated `WithdrawFromGasKey` bypasses the SPICE Pending Transaction Queue's gas-key balance accounting, permitting admission of transactions the queue believes are unfunded — (File: `chain/client/src/pending_transaction_queue.rs`)

### Summary
The report describes a fee/charge-bypass bug class: a privileged accounting path (`withdrawLend()`) enforces a fee, but an alternate execution path (`liquidate()`) reaches the same balance-reducing effect without going through the fee-charging code, letting a user drain funds while the accounting system believes it is still solvent/consistent. The nearcore analog is the SPICE `PendingTransactionQueue`'s gas-key balance tracking: it only inspects the *top-level* actions of a submitted transaction for `Action::WithdrawFromGasKey` to update its `pending_gas_key_costs` accounting, but the same action reachable through a nested `Action::Delegate`/meta-transaction bypasses this scan entirely, letting the queue keep admitting further gas-key transactions against a balance that has already been drained.

### Finding Description
`PendingTransactionQueue::add_chunk_transactions` and `PendingTxSession::check_pending` are responsible for keeping an in-memory ledger of gas-key balances consumed by uncertified (included-but-not-yet-executed) chunks, so that the RPC admission layer can reject a subsequent gas-key transaction whose funding is already spoken for by a transaction sitting in an earlier, not-yet-certified chunk.

Both of these scan only the *outer* transaction's top-level actions for `Action::WithdrawFromGasKey`: [1](#0-0) [2](#0-1) 

If the `WithdrawFromGasKey` action instead appears nested inside a `Delegate` action's inner action list (a meta-transaction/relayed transaction), the outer scan never sees it, so `pending_gas_key_costs`/`session_gas_key_withdrawals` are never incremented for that withdrawal — even though the withdrawal executes and drains the gas key's balance when the receipt is applied.

This exact gap is documented and has already been closed in this codebase by a dedicated protocol feature, `RejectWithdrawFromGasKeyInDelegate`, whose doc-comment states the root cause verbatim: [3](#0-2) 

and a companion feature disabling `DelegateV2` from gas keys for essentially the same class of PTQ-blind-spot reason: [4](#0-3) 

A dedicated regression test exercises exactly this scenario and confirms the pre-fix behavior: pre-upgrade, a `Delegate` action carrying an inner `WithdrawFromGasKey` executes successfully and drains the gas key balance; only after `RejectWithdrawFromGasKeyInDelegate` activates does action validation reject the nested action at admission time: [5](#0-4) [6](#0-5) 

Because the fix is gated behind a `ProtocolFeature` that must be voted in and activated at a specific protocol version, the vulnerability is live on any deployment (including today's production/stable chain state prior to the feature's activation height) where `RejectWithdrawFromGasKeyInDelegate` has not yet been enabled. In that window, an attacker fully controls the exploit: sign an outer `Delegate` action (self-relayed or via any relayer) whose inner action is `WithdrawFromGasKey`, submit it while other gas-key transactions from the same key are pending in uncertified chunks, and the PTQ's `paid_from_gas_key` snapshot will under-report the true committed spend, since it never accounted for the nested withdrawal.

### Impact Explanation
The PTQ's whole purpose is to prevent double-spending of a gas key's balance across multiple uncertified (SPICE-pipelined) chunks before they are actually applied by the runtime. If the withdrawal amount silently escapes the queue's bookkeeping:
- The queue can admit additional gas-key transactions that, combined with the hidden withdrawal, exceed the gas key's real balance, i.e., it will provide `TxVerdict::Admit` verdicts based on stale/incorrect `paid_from_gas_key` figures (`runtime/runtime/src/verifier.rs`, `verify_and_charge_gas_key_tx_ephemeral`), a fee/balance-accounting bypass consistent with "unauthorized value movement" / accepted invalid state that later has to be reconciled at actual chunk application (where the runtime does correctly deduct the balance) — but by then the admission-layer safety property is already violated, and the chain can end up over-admitting transactions relative to available funds, which is the direct analog of the Blueberry report's "charge is skipped, but the balance change still happens."
- This is a state-transition/consistency bug in transaction admission specific to the SPICE pending-transaction pipeline, reachable purely by a signed meta-transaction from an unprivileged account — no validator or node compromise required.

### Likelihood Explanation
High, in any deployment window where `RejectWithdrawFromGasKeyInDelegate` (and its sibling `RejectDelegateV2`) have not yet been activated: any account holding a gas key and the ability to sign a `Delegate` action can trigger this by simply nesting `WithdrawFromGasKey` inside the delegate's inner actions and submitting it alongside other gas-key transactions in the SPICE pending window. The behavior is proven by the codebase's own pre-upgrade regression assertion, which explicitly executes this and confirms the balance is drained without being tracked.

### Recommendation
Ensure `RejectWithdrawFromGasKeyInDelegate` (and `RejectDelegateV2`) are activated at protocol versions at or below the network's current live/stable version, and audit the PTQ scanning logic (`add_chunk_transactions`, `check_pending`) to recursively scan into `Delegate`/`DelegateV2` inner actions for `WithdrawFromGasKey` (and any other gas-key-balance-affecting action) rather than relying solely on rejecting the action at validation time — defense in depth in case a future action type reintroduces a similarly-nested bypass.

### Proof of Concept
The codebase's own test demonstrates the exploit path end-to-end pre-upgrade: [7](#0-6) 
constructs a `DelegateAction` whose sole inner action is `WithdrawFromGasKey`, signed and relayed via `Action::Delegate`. Pre-upgrade execution: [5](#0-4)

/// Build a meta transaction whose inner action withdraws from the sender's own
/// gas key. The delegate is signed by the sender's plain access key, since a
/// gas key cannot sign a V1 delegate action.
fn delegated_withdraw_tx(
    env: &TestLoopEnv,
    sender: &AccountId,
    relayer: &AccountId,
    gas_key: &Signer,
) -> SignedTransaction {
    let sender_signer = create_user_test_signer(sender);
    let delegate_action = DelegateAction {
        sender_id: sender.clone(),
        receiver_id: sender.clone(),
        actions: vec![
            Action::WithdrawFromGasKey(Box::new(WithdrawFromGasKeyAction {
                public_key: gas_key.public_key(),
                amount: WITHDRAW_AMOUNT,
            }))
            .try_into()
            .unwrap(),
        ],
        nonce: env.rpc_node().get_next_nonce(sender),
        max_block_height: 1_000_000,
        public_key: sender_signer.public_key(),
    };
    let signed_delegate = SignedDelegateAction::sign(&sender_signer, delegate_action);
    env.rpc_node().tx_from_actions(
        relayer,
        sender,
        vec![Action::Delegate(Box::new(signed_delegate))],
    )
}
