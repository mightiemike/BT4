Based on my investigation, I found a directly analogous bug class in nearcore: an incomplete/stale mapping check used to gate processing of receipts pulled from a queue that other users' transactions depend on, which can `.unwrap()`-panic and halt the chain — the structural equivalent of the Sherlock report's incomplete `_isInvalidRewardToken` allowlist causing a permanent revert of a shared batch operation (`reinvestReward`).

### Title
Stale shard mapping in delayed-receipt filtering can panic on `receiver_shard_id().unwrap()` during resharding, halting chunk application - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` and `peek_iter` unconditionally call `.unwrap()` on `receiver_shard_id(&shard_layout)` when filtering delayed receipts that "belong" to the current shard after a resharding event [1](#0-0) . This mirrors the reported bug class: a validation/allowlist function that is assumed complete but can fail for a legitimately reachable input, causing a revert that blocks a shared, permissionless operation (there, `reinvestReward`; here, delayed-receipt processing during `apply()` which every shard must perform every chunk, triggered by ordinary user transactions).

### Finding Description
`pop()` and `peek_iter()` in `DelayedReceiptQueueWrapper` (used from `Runtime::apply` on every chunk, `runtime/runtime/src/lib.rs:1902`) drain the on-disk `DelayedReceiptQueue` and use `receipt_filter_fn` to decide whether a given delayed receipt belongs to the current shard, since after a shard split the queue is duplicated across both child shards and contains receipts for the sibling [2](#0-1) . The filter computes `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()` — if this call ever returns `Err` for a receipt honestly present in the queue (e.g., a `GlobalContractDistribution` receipt whose `target_shard` no longer maps cleanly onto the *current* `shard_layout` after two successive resharding generations), the `unwrap()` panics inside `apply()`, which the caller in `chain/chain/src/runtime/mod.rs` propagates as a hard `panic!` rather than a recoverable error (`RuntimeError::ReceiptValidationError(e) => panic!("{}", e)` at `chain/chain/src/runtime/mod.rs:372`, and the same pattern for unexpected error variants at line 368) [3](#0-2) . This is a chunk-processing halt reachable purely by the combination of (a) ordinary user transactions saturating a shard's compute so a receipt lands in the delayed queue, and (b) the network's own resharding schedule advancing — no operator/validator misbehavior required.

A regression test in this very tree, `test_stale_global_contract_distribution_after_double_resharding`, documents exactly this scenario: it deliberately saturates gas on a shard to force a `GlobalContractDistribution` receipt into the delayed queue across two resharding events and asserts the chain does not stall — explicitly citing a prior panic in `receipt_filter_fn()`/`receiver_shard_id()` failing to remap the old target shard after two resharding generations [4](#0-3) . The comment states the vulnerability was real ("If the vulnerability exists, processing the stale ... receipt will panic in receipt_filter_fn()") and the test is designed to catch a *regression* of it, i.e., today's `.unwrap()` calls at `congestion_control.rs:876` and `congestion_control.rs:919` are exactly the code path that historically panicked; the current test only proves it currently doesn't reproduce under this specific double-split, single-target scenario, not that `receiver_shard_id()` is now infallible in all resharding chains/timings (e.g. three or more successive splits within the delayed-queue retention window, or other cross-shard receipt kinds with the same "old parent shard id no longer resolvable" property).

### Impact Explanation
If `receiver_shard_id()` returns `Err` for any receipt that legitimately reaches the delayed queue across resharding boundaries not covered by the existing fix/test, `Runtime::apply` panics, and the panic is escalated to a hard process abort at `chain/chain/src/runtime/mod.rs:372` rather than gracefully failing the chunk — this is a transaction/receipt-triggered halt of chunk application, matching the "transaction-triggered halt" acceptance criterion. Because the delayed queue and resharding schedule are shared, deterministic protocol state, an unhandled panic here would occur identically on every honest node applying the same chunk, causing the chain to stop advancing for the affected shard(s) — a liveness failure indistinguishable in severity from the reported DOS of `reinvestReward` (a permissionless, shared batch operation that all further participants depend on).

### Likelihood Explanation
Likelihood is Medium: the specific single-target-shard, two-resharding-generation scenario is already covered by a fix and regression test in this codebase [5](#0-4) , reducing the practical window. However, the root-cause pattern — an `.unwrap()` on a fallible shard-remapping call inside a filter that gates processing of a *shared, protocol-level* receipt queue — remains present verbatim in `receipt_filter_fn`/`peek_iter` [1](#0-0) , and any resharding/receipt-kind combination not anticipated by the existing test would reproduce the same class of chain halt with only ordinary user transactions as the trigger (gas-saturating a shard to force delayed receipts, combined with the network's own resharding cadence).

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` and `peek_iter` with explicit error propagation (`Result`-returning filter, using `try_filter`/`filter_map` with logging) so that a shard-remapping failure degrades to a recoverable `RuntimeError` (or is proven, via an exhaustive protocol-level invariant, to never occur for any receipt kind that can be queued across an arbitrary number of resharding generations) instead of panicking inside `apply()`. Extend the existing regression test in `test-loop-tests/src/tests/global_contracts_distribution.rs` to cover three-or-more successive resharding generations and additional receipt kinds (not just `GlobalContractDistribution`) that can sit in the delayed queue.

### Proof of Concept
Exercised today by `test_stale_global_contract_distribution_after_double_resharding`: deploy a global contract on an account, saturate the shard's chunk compute budget every block via `burn_gas_raw` so the resulting `GlobalContractDistribution` receipt is pushed to the delayed-receipt queue, force two sequential dynamic-resharding splits (the first targeting the shard holding the receipt), then drain the delayed queue and assert the chain height still advances past the drain point rather than stalling from a panic in `receipt_filter_fn()`/`receiver_shard_id()` [6](#0-5) .

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per

    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();

        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(

                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);

    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
