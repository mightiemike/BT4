### Title
Underpriced CPU via `estimateenergy` binary search amplifies constant-call cost per HTTP request without a matching rate-limit weight - (File: `framework/src/main/java/org/tron/core/services/http/EstimateEnergyServlet.java`)

### Summary
`EstimateEnergyServlet.doPost` calls `Wallet.estimateEnergy`, which performs a "two-times" probe plus a `log2(maxFeeLimit/energyFee)` binary search, invoking `cleanContextAndTriggerConstantContract` → `callConstantContract` → `VMActuator.execute` on every iteration, each of which can run up to `constantCallTimeoutMs` (or `maxCpuTimeOfOneTx`) of CPU time. `RateLimiterServlet` throttles this endpoint purely by request count/QPS, not by the CPU actually consumed, so a single POST can cost dramatically more CPU than the "one unit" the rate limiter accounts for.

### Finding Description
The call chain is: `EstimateEnergyServlet.doPost` (`framework/src/main/java/org/tron/core/services/http/EstimateEnergyServlet.java:33-77`) → `Wallet.estimateEnergy` (`framework/src/main/java/org/tron/core/Wallet.java:2986-3087`) → `cleanContextAndTriggerConstantContract` (`Wallet.java:3089-3101`) → `triggerConstantContract` → `callConstantContract` (`Wallet.java:3139-3200`), which builds a `VMActuator` and calls `vmActuator.execute(context)`.

`Wallet.estimateEnergy` performs:
- An initial probe at `high = dps.getMaxFeeLimit()` (`Wallet.java:3006-3017`, with a retry loop up to `estimateEnergyMaxRetry` on `Program.OutOfTimeException`).
- An optional "doubling" probe (`Wallet.java:3028-3049`).
- A binary search loop `while (low + TRX_PRECISION < high)` (`Wallet.java:3051-3072`) that runs `O(log2(maxFeeLimit/TRX_PRECISION))` iterations, each with its own retry loop on `OutOfTimeException`.
- A final re-run at the converged `high` (`Wallet.java:3075-3076`).

Each iteration is a full VM execution bounded by `constantCallTimeoutMs` (`VMActuator.calculateCpuLimitInUs`, `actuator/src/main/java/org/tron/core/actuator/VMActuator.java:704-710`). If an attacker crafts a contract whose execution time is deterministically just under this timeout for every `feeLimit`/energy value the binary search tries (e.g., a loop bounded by gas that always burns close to the full time budget regardless of the exact energy value tested, or one that intentionally throws `OutOfTimeException` and gets retried up to `estimateEnergyMaxRetry` times), each binary-search iteration consumes near-maximum CPU. With dozens of iterations (bounded by `log2(maxFeeLimit/energyFee)` plus up to `estimateEnergyMaxRetry` retries per iteration on timeout), a single HTTP POST can trigger many multiples of the CPU cost of one `triggerconstantcontract` call.

`RateLimiterServlet.service` (`framework/src/main/java/org/tron/core/services/http/RateLimiterServlet.java:103-152`) enforces cost purely via `IRateLimiter.acquirePermit` (QPS- or permit-based), consulted once per HTTP request regardless of how much internal work that request triggers. There is no accounting tying the rate-limit weight of `EstimateEnergyServlet` to the number of VM executions it may run internally, and the reference configuration (`common/src/main/resources/reference.conf:454-521`) has no dedicated (lower) QPS entry for `EstimateEnergyServlet`; absent an explicit `http` entry, it falls back to the same `DefaultBaseQqsAdapter`/`global.api.qps = 1000` default as cheap read-only endpoints, and the same default that would presumably apply to `TriggerConstantContractServlet`. Thus the per-request CPU cost is not reflected in the per-request rate-limit weight.

### Impact Explanation
This allows an unprivileged remote attacker with only HTTP access to a public FullNode to consume disproportionate CPU per request (potentially tens of times the cost of a single constant-contract call, bounded by the number of binary-search iterations times `constantCallTimeoutMs`, further multiplied by `estimateEnergyMaxRetry` retries on timeout). At the node's configured QPS budget for this endpoint, aggregate CPU usage can significantly exceed what the rate limiter is designed to bound, degrading the node's ability to serve other requests/process blocks — a resource-exhaustion / DoS-adjacent condition against the specific node, not a chain-consensus violation (constant calls never touch chain state — `callConstantContract` runs in an isolated `RepositoryImpl.createRoot` context and is discarded).

### Likelihood Explanation
Preconditions are realistic and attacker-controlled: `vm.estimateEnergy=true` and `vm.supportConstant=true` are common FullNode/public-RPC configurations enabling this exact feature. The attacker needs only to deploy or reuse a public contract with a loop whose length is tunable via `TriggerSmartContract.data`, and can iterate the attack indefinitely from a single IP subject only to the endpoint's QPS cap. No special privileges, keys, or governance access are required — this matches the constraints for HTTP/public-API input.

### Recommendation
- Give `EstimateEnergyServlet` (and its PBFT/Solidity counterparts) a distinctly lower rate-limit weight than `TriggerConstantContractServlet` in `reference.conf`'s `rate.limiter.http` list (e.g., `GlobalPreemptibleAdapter` with a small concurrent-permit cap, or a much lower `qps`), reflecting its amplified internal cost.
- Bound the total wall-clock/CPU budget for the whole `estimateEnergy` binary search (sum across all iterations), not just per-iteration `constantCallTimeoutMs`, and abort with a clear error once exceeded.
- Cap `estimateEnergyMaxRetry` tightly and/or make retries consume the shared per-request time budget rather than restarting a fresh full-timeout window each time.
- Consider a per-IP concurrency limiter (`GlobalPreemptibleAdapter`) specifically for `EstimateEnergyServlet` in addition to QPS, to prevent parallel amplification.
