**Analysis:**

Every prologue entry point in `aptos-move/framework/aptos-framework/sources/transaction_validation.move` — `script_prologue`, `script_prologue_extended`, `multi_agent_script_prologue(_extended)`, `fee_payer_script_prologue(_extended)`, `unified_prologue(_v2)`, `unified_prologue_fee_payer(_v2)`, and `versioned_prologue` — takes `chain_id: u8` as a required, non-optional positional parameter and forwards it unconditionally into the single `prologue_common` function, which performs the identical `assert!(chain_id::get() == chain_id, error::invalid_argument(PROLOGUE_EBAD_CHAIN_ID));` check at the same call site in every branch. On the Rust side, `run_script_prologue` in `aptos-move/aptos-vm/src/transaction_validation.rs` constructs every argument list — for the AA/fee-payer path, the multi-agent path, the fee-payer path, and the plain script path, with or without the simulation-enhancement feature — always including `MoveValue::U8(chain_id.id())` derived from the same `txn_data.chain_id()` at a fixed position matching the corresponding Move function's signature. Because Move entry function calls via `execute_function_bypass_visibility` require argument lists that exactly match the target function's fixed arity and BCS-decodable types, an unprivileged caller cannot "omit" the `chain_id` argument or substitute a conflicting encoding for one execution mode without the transaction failing at argument deserialization/type-checking before `prologue_common` ever executes — it cannot silently bypass the chain-id assert in one mode while it fires in another. There is no code path where the chain-id argument is optional, computed differently per mode, or skipped conditionally; the check is single-sourced from `txn_data.chain_id()` in Rust and single-sited in `prologue_common` in Move for all script/multi-agent/fee-payer/orderless/unified/versioned variants, so the parameterized differential you describe has no basis in the actual control flow.
