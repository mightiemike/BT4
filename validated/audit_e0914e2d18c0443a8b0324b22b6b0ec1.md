### Title
Loaded-accounts-data-size cost model uses only the declared low limit, letting an attacker force real oversized account I/O while paying and being billed for a tiny declared size - ([File: cost-model/src/cost_model.rs], [File: svm/src/account_loader.rs])

### Summary
`CostModel::get_estimated_execution_cost` prices `loaded_accounts_data_size_cost` solely from the *declared* `ComputeBudgetInstruction::SetLoadedAccountsDataSizeLimit` value (sanitized/clamped only against the maximum, never checked against actual referenced account sizes), while `load_transaction_accounts`/`increase_calculated_data_size` only detects the real oversized load after each account has already been fully read from accounts-db/cache. Worse, the post-execution cost-tracker correction that is supposed to true-up the estimate also clamps the reported `loaded_accounts_data_size` to the declared limit, so the extra I/O the leader actually performed is never billed even retroactively.

### Finding Description
An attacker crafts a transaction that includes:
- `ComputeBudgetInstruction::set_compute_unit_limit(small)`
- `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit(32 * 1024)` (or any small value)
- one or more account references (writable or read-only, no special privilege needed) to existing large accounts (up to 10 MiB) or accounts resolved via an Address Lookup Table.

At packing/banking-stage time, `ComputeBudgetInstructionDetails::sanitize_and_convert_to_compute_budget_limits` only clamps the requested value down to `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`, it never inspects true account sizes: [1](#0-0) 

`CostModel::get_estimated_execution_cost` then derives `loaded_accounts_data_size_cost` purely from this declared (attacker-controlled, small) value: [2](#0-1) 

`CostModel::calculate_cost` (the function used by banking-stage/`QosService` to make packing decisions) uses this estimate: [3](#0-2) 

At execution time, `load_transaction_accounts` loads each account from accounts-db/cache (real I/O) *before* checking whether the running total exceeds the declared limit: [4](#0-3) [5](#0-4) 

`increase_calculated_data_size` only rejects *after* the byte count has already been added, i.e. after the large account has already been read: [6](#0-5) 

Critically, the conversion used to report `loaded_accounts_data_size` for both `Loaded` and `FeesOnly` outcomes clamps the *actual* bytes loaded down to the declared (small) limit: [7](#0-6) [8](#0-7) 

This clamped value then feeds directly back into the post-execution cost-tracker "truth-up" step (`QosService::remove_or_update_costs` → `CostTracker::update_execution_cost`), so even the retroactive correction never reflects the real bytes read from storage: [9](#0-8) [10](#0-9) 

No existing check closes this gap: sanitization only bounds the declared limit from above (`MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`), it does not validate declared limit against actual account sizes (which are unknown pre-load); and the runtime enforcement is necessarily incremental/after-the-fact since sizes are only known once accounts are fetched.

### Impact Explanation
This does not cause direct loss of funds or consensus divergence, but it is a genuine Metering Totality violation: an unprivileged attacker can force the leader to perform real, potentially multi-megabyte account reads from accounts-db/cache per transaction while being priced (both at packing time and, due to the `.min(limit)` clamp, even at post-execution correction time) as if only a few KB were loaded. Because this is cheap and repeatable — one such transaction per slot per referenced large account, and can be parallelized across many large accounts/slots — it creates an asymmetric I/O-amplification vector against leaders (resource-consumption / liveness-degradation category), without the cost model or block-cost accounting ever capturing the true cost.

### Likelihood Explanation
Preconditions are trivial: no special access is needed, only knowledge of any existing account close to the 10 MiB account-size ceiling (many large program/state accounts are public) or an attacker-controlled account inflated to near this size, plus one compute-budget instruction and one system/no-op instruction. Cost to the attacker is a single transaction fee; the transaction is always sanitizable (declared limit ≥1 is valid) and always ends in a normal `MaxLoadedAccountsDataSizeExceeded` failure that still gets included/fee-charged, so it can be resubmitted arbitrarily many times per block by different fee payers to keep the underestimation persistent and repeatable.

### Recommendation
- When accounting for `FeesOnly`/failed loads due to `MaxLoadedAccountsDataSizeExceeded`, report and bill the *actual* bytes loaded before the limit was hit (drop the `.min(requested_loaded_accounts_data_size_limit)` clamp in `LoadedTransactionDataSize`'s `From<..> for u32` for the failure path), so the post-execution cost-tracker correction (`update_execution_cost`) reflects the true I/O performed.
- Consider having banking-stage cost estimation account for a worst-case per-account size (e.g., using `MAX_PERMITTED_DATA_LENGTH` for referenced accounts of unknown size, or checking a cached/last-known size from accounts-db metadata) rather than trusting the attacker-declared `loaded_accounts_data_size_limit` alone for packing decisions.

### Proof of Concept
SVM/bank integration test:
1. Create a bank and store one existing account with data length close to `MAX_PERMITTED_DATA_LENGTH` (e.g. ~10 MiB), owned by a simple program.
2. Build a transaction: `set_compute_unit_limit(small)`, `set_loaded_accounts_data_size_limit(32 * 1024)`, plus an instruction referencing the large account (read-only) and a trivial payer transfer.
3. Compute `let est = CostModel::calculate_cost(&tx, &bank.feature_set);` and assert `est.loaded_accounts_data_size_cost()` equals the cost for ~32 KiB (a few pages), far below the actual account size.
4. Execute the transaction via `load_execute_and_commit_transactions`; assert the committed result is `Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)`.
5. Instrument/measure (or assert via a modified `LoadedTransactionDataSize` test hook) that the internal `loaded_accounts_data_size` counter before clamping exceeded the declared limit by approximately the large account's size (i.e., the full account was read), while the value fed into `CostModel::calculate_cost_for_executed_transaction`/`update_execution_cost` remains capped at the declared 32 KiB limit — demonstrating the discrepancy between real I/O performed and cost charged both at packing time and after execution.

    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }

    fn increase_calculated_data_size(
        &mut self,
        data_size_delta: usize,
        error_metrics: &mut TransactionErrorMetrics,
    ) -> Result<()> {
        // this branch is unreachable in practice (though not by construction),
        // since it would imply an account >4gb in size
        let Ok(data_size_delta) = u32::try_from(data_size_delta) else {
            self.loaded_accounts_data_size = u32::MAX;
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            return Err(TransactionError::MaxLoadedAccountsDataSizeExceeded);
        };

        self.loaded_accounts_data_size = self
            .loaded_accounts_data_size
            .saturating_add(data_size_delta);

        if self.loaded_accounts_data_size > self.requested_loaded_accounts_data_size_limit {
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)
        } else {
            Ok(())
        }
    }

    pub fn update_execution_cost(
        &mut self,
        estimated_tx_cost: &TransactionCost<impl TransactionWithMeta>,
        actual_execution_units: u64,
        actual_loaded_accounts_data_size_cost: u64,
    ) {
        let actual_load_and_execution_units =
            actual_execution_units.saturating_add(actual_loaded_accounts_data_size_cost);
        let estimated_load_and_execution_units = estimated_tx_cost
            .programs_execution_cost()
            .saturating_add(estimated_tx_cost.loaded_accounts_data_size_cost());
        match actual_load_and_execution_units.cmp(&estimated_load_and_execution_units) {
            std::cmp::Ordering::Equal => (),
            std::cmp::Ordering::Greater => {
                self.add_transaction_execution_cost(
                    estimated_tx_cost,
                    actual_load_and_execution_units - estimated_load_and_execution_units,
                );
            }
            std::cmp::Ordering::Less => {
                self.sub_transaction_execution_cost(
                    estimated_tx_cost,
                    estimated_load_and_execution_units - actual_load_and_execution_units,
                );
            }
        }
    }
