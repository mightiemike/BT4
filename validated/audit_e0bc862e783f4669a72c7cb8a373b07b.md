### Title
`WithdrawExpireUnfreezeProcessor` (TVM native contract) omits the `supportUnfreezeDelay()` feature-gate enforced by the transaction-level actuator - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java])

### Summary
`WithdrawExpireUnfreezeContract` is only meant to be usable after the committee has enabled the unfreeze-delay feature (`UNFREEZE_DELAY_DAYS` proposal), which is enforced in the transaction-broadcast actuator via `dynamicStore.supportUnfreezeDelay()`. The TVM-reachable equivalent used by `withdrawExpireUnfreeze()` in `Program.java` (invoked from contract execution) does not perform this same check, and also uses a slightly looser validation condition than the actuator.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly requires the feature to be enabled before any state can be touched: [1](#0-0) 

It also rejects the operation when there is nothing to withdraw using a strict `<= 0` check: [2](#0-1) 

By contrast, the TVM-native path — reachable from any smart contract via the `withdrawExpireUnfreeze` opcode — does not check `supportUnfreezeDelay()` at all in its `validate()`: [3](#0-2) 

and it uses a weaker `< 0` bound (allowing a zero-amount "no-op" withdrawal to pass validation, unlike the actuator's `<= 0`): [4](#0-3) 

This processor is called directly from TVM contract execution via `Program.withdrawExpireUnfreeze()`, without any surrounding feature-flag check at the call site either: [5](#0-4) 

This is structurally the same bug class as the report: a withdraw-style function is reachable (here, via TVM contract call rather than direct broadcast transaction) without the same state/feature-readiness check that the "normal" entry point enforces, because the checks were duplicated across two code paths and only one was kept in sync.

### Impact Explanation
In the current default configuration, `unfreezeDelayDays` defaults to `0`, and `supportUnfreezeDelay()` gates the entire "unfreeze with delay" balance model. If a chain has not yet enabled `UNFREEZE_DELAY_DAYS`, `UnfreezeBalanceV2` records would not normally use delayed expiry semantics enforced elsewhere, so `unfrozenV2List` on accounts would in practice be empty until the feature and its companion contracts are permissioned/enabled together via `ProposalService` (`UNFREEZE_DELAY_DAYS` case enables `FreezeBalanceV2`, `UnfreezeBalanceV2`, `WithdrawExpireUnfreeze`, `DelegateResource`, `UnDelegateResource` contract types together): [6](#0-5) 

Because of this, real-world exploitability is likely mitigated by the fact that the `UnfreezeBalanceV2Contract` type itself would not yet be permitted for broadcast before the same proposal is passed, and `unfrozenV2List` would be empty absent it — meaning `getTotalWithdrawUnfreeze` would typically return 0, making the missing gate a defense-in-depth/invariant gap rather than a directly exploitable fund-drain today. However, I was unable to fully verify whether TVM-internal native contract calls (unlike top-level broadcast transactions) are also subject to the `ContractType` permission-bit gating from `addSystemContractAndSetPermission`, since that mechanism is primarily documented for actuators dispatched from transactions, not for internally-invoked TVM native contracts reached via opcodes. If TVM native-contract dispatch is not subject to the same permission check, a contract could invoke `withdrawExpireUnfreeze()` even when the feature/contract type has not been enabled by governance, which would violate the intended invariant that this operation only becomes available after the corresponding hard-fork/proposal state is active — directly analogous to the reported "before staking starts" issue.

### Likelihood Explanation
Low-to-moderate. It requires (a) a permissionless smart contract to call the TVM `withdrawExpireUnfreeze` opcode, and (b) the account to already have entries in `unfrozenV2List` with expired timestamps despite `supportUnfreezeDelay()` being false — a state that should not normally arise given how `UnfreezeBalanceV2` populates that list. The main risk is around fork-transition windows or unusual account states, not a straightforward general-purpose exploit.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check (or equivalent) to `WithdrawExpireUnfreezeProcessor.validate()`, and align the zero-amount check to `<= 0` to match `WithdrawExpireUnfreezeActuator`. More broadly, audit all TVM native-contract `Processor` classes for parity with their corresponding transaction `Actuator` classes' feature-flag gates, since these gates are the intended mechanism for restricting execution to post-hardfork/post-proposal states — exactly the class of check the original report recommends adding explicitly rather than relying on incidental invariants.

### Proof of Concept
Not independently reproducible from static analysis alone — a working PoC would require: (1) a private/testnet chain where `UNFREEZE_DELAY_DAYS` proposal has not been passed (`supportUnfreezeDelay() == false`), (2) an account holding stale `unfrozenV2` entries with `unfreezeExpireTime <= now` (state that would need to originate from before the feature was disabled, or via a bug in an unrelated code path), and (3) a contract invoking the `withdrawExpireUnfreeze` native opcode to confirm it bypasses the `supportUnfreezeDelay()` gate that the actuator enforces. I was not able to confirm from the available code whether the `ContractType` permission-bit system independently blocks this call path before the proposal passes, which is necessary to establish full exploitability — flagging this as an open verification item for further engineering review.

    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);

    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
