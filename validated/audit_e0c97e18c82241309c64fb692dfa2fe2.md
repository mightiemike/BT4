### Title
Cheap ReceiveDescription CEnc/COut size check is deferred until after expensive spend-proof verification, enabling CPU-amplification DoS in ShieldedTransferActuator.validate() - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
In `checkProof()`, the loop calling the expensive native `JLibrustzcash.librustzcashSaplingCheckSpend` for every `SpendDescription` runs before the cheap `CEnc`/`COut` size validation for `ReceiveDescription`s. An attacker who possesses at least one currently-valid, unspent shielded note (whose `SpendDescription` passes `merkleRootExist`/`nullifierStore.has()` and the expensive `checkSpend` crypto check) can repeatedly broadcast transactions that reuse that same valid `SpendDescription` paired with a deliberately malformed `ReceiveDescription`, forcing full spend-proof verification on every node's `validate()` call before the transaction is rejected for a size mismatch that could have been checked essentially for free.

### Finding Description
`ShieldedTransferActuator.validate()` calls `checkReceiver()` (lines 382-391) which only bounds `receiveDescriptionCount` to `[1,2]` and does not check `CEnc`/`COut` sizes. The actual size check only happens deep inside `checkProof()` at lines 309-312, *after* the spend loop at lines 293-306 has already invoked `JLibrustzcash.librustzcashSaplingCheckSpend` for each `SpendDescription`: [1](#0-0) 

The preceding cheap checks in `validate()` (`merkleContainer.merkleRootExist`, `nullifierStore.has()`) only verify that the spend's anchor exists and the nullifier is not yet recorded on chain — they do **not** consume the nullifier; the nullifier is only persisted to `nullifierStore` inside `executeShielded()` at block-execution time: [2](#0-1) 

This means a single genuinely valid `SpendDescription` (crafted once by an attacker who owns real, spendable shielded value) can be embedded, byte-for-byte identical, into many different candidate transactions, each paired with a different (or identically) malformed `ReceiveDescription` (wrong `CEnc`/`COut` size). Because the transaction never reaches `execute()` (it fails validation), the nullifier is never actually recorded, so the same valid spend can be reused indefinitely across separate broadcast attempts. Each attempt causes every validating node to:
1. Pass cheap checks (`merkleRootExist`, `nullifierStore.has()`) — inexpensive.
2. Enter `checkProof()`, allocate a verification context, and run the full native pairing-based `librustzcashSaplingCheckSpend` (expensive, real zk-SNARK verification) — succeeds since the spend is valid.
3. Only then check `CEnc`/`COut` sizes for the receive and reject with `ZkProofValidateException`.

Since the fee (`Commons.adjustAssetBalanceV2` to the blackhole) is only deducted in `execute()`, and `execute()` is never reached when `validate()` throws, the attacker pays no protocol fee for the wasted spend-proof verification work; they only bear the ordinary bandwidth/net cost of broadcasting the transaction bytes, not a cost proportional to the CPU-expensive crypto operation performed.

### Impact Explanation
This is a CPU-amplification Denial-of-Service against the TRON protocol implementation: an unprivileged attacker (any node that once legitimately received a shielded note) can force every validating node in the network to repeatedly execute expensive zk-SNARK spend-proof verification (elliptic-curve pairing operations) for transactions that are trivially detectable as invalid via a cheap length check, without paying a fee proportional to that cost. Repeated over many broadcasts this degrades node CPU availability and violates fee/cost proportionality (FAITHFUL_METERING), corresponding to the "DoS via the TRON protocol implementation" bounty class.

### Likelihood Explanation
Preconditions: the attacker needs one genuine spendable shielded note (obtainable through a normal shielded transfer to themselves, a one-time modest cost) and no special privileges. The attack is fully repeatable: the same valid `SpendDescription` bytes can be reused across arbitrarily many transactions (varying only the malformed `ReceiveDescription`, which changes the transaction hash and message content, avoiding trivial duplicate-tx-hash rejection) since the spend's nullifier is never actually committed to `nullifierStore` unless a transaction is executed in a block. This makes the attack cheap to mount and easy to automate; the only limiting factor would be network-level bandwidth/net-usage throttling on transaction broadcast, not the fee/energy model tied to the actuator itself.

### Recommendation
Move the `CEnc`/`COut` size checks (currently at lines 309-312) into `checkReceiver()` in `validate()` (lines 382-391), or at minimum to the very start of `checkProof()` before the spend-verification loop, so malformed/oversized ciphertexts are rejected before any expensive native crypto calls are performed. This restores the "cheap structural checks before expensive native calls" ordering invariant.

### Proof of Concept
```java
// Pseudocode/JUnit outline (adapted from ShieldedReceiveTest.java patterns in the repo)
@Test
public void testCheapCheckOrderingAmplification() throws Exception {
  // 1. Build one genuinely valid SpendDescription `validSpend` from a real shielded note
  //    the attacker controls (via a prior legitimate shielded deposit/transfer).

  // 2. Repeat N times:
  for (int i = 0; i < N; i++) {
    ReceiveDescription badReceive = ReceiveDescription.newBuilder()
        .setNoteCommitment(randomCm(i))     // unique per iteration to avoid dedup
        .setCEnc(ByteString.copyFrom(new byte[ZC_ENCCIPHERTEXT_SIZE - 1])) // malformed size
        .setCOut(ByteString.copyFrom(new byte[ZC_OUTCIPHERTEXT_SIZE]))
        .build();

    ShieldedTransferContract contract = ShieldedTransferContract.newBuilder()
        .addSpendDescription(validSpend)   // identical valid spend reused each time
        .addReceiveDescription(badReceive)
        .build();

    long t0 = System.nanoTime();
    assertThrows(ContractValidateException.class, () -> actuator.validate());
    long elapsed = System.nanoTime() - t0;

    // Assert: elapsed time is dominated by librustzcashSaplingCheckSpend invocation
    // (verify via instrumentation/mocking JLibrustzcash to count invocations),
    // i.e., checkSpend is called before the CEnc/COut size check fails.
    assertTrue(checkSpendInvocationCounter.get() == i + 1);
  }
}
```
Expected result: `librustzcashSaplingCheckSpend` is invoked once per rejected transaction (N times total) even though every transaction is guaranteed to fail on a cheap length check, demonstrating that expensive verification work is performed before an avoidable, cheap rejection — confirming the ordering defect described.
