## Title
Replay verification silently ignores `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, allowing divergent hot-state/position roots to pass `ensure_match_transaction_info` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  only checks transaction status, gas used, `state_change_hash` (write-set hash), and `event_root_hash`. It explicitly does not check the `hot_state_checkpoint_hash` or `position_state_checkpoint_hash` fields carried by `TransactionInfo::V1(TransactionInfoV1)`, as the code's own TODO comment states: [2](#0-1) .

### Finding Description
`ensure_match_transaction_info` is the function used by chunk executor / replay-verify tooling to authenticate that a locally re-executed `TransactionOutput` matches the `TransactionInfo` committed on-chain (used from `execution/executor/src/chunk_executor/mod.rs`, `db-tool/src/replay_on_archive.rs`, `aptos-debugger`, and CLI commands per the earlier grep). `TransactionInfo` is an enum with `V0`/`V1` variants [3](#0-2) , and `TransactionInfoV1` adds fields for `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` that are populated depending on the on-chain feature flags `hot_state_root_in_txn_info` / `compute_trading_native_state_roots` in `BlockExecutorConfigFromOnchain` [4](#0-3) . However, the comparator function only asserts equality on `write_set_hash`/`state_change_hash` and `event_root_hash`; it never reads or compares `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` before returning `Ok(())`.

Because these checkpoint hash fields are never validated, a replayed/verified output whose hot-state root or trading-native "position" state root diverges from what is recorded in the authenticated `TransactionInfo::V1` will still be reported as matching, as long as the write-set and events hash the same.

### Impact Explanation
This is a proof/authenticated-response integrity gap: replay-verify tooling (`db-tool`'s `replay_on_archive`, chunk executor's transaction-info verification path) is a proof-bearing verification step meant to bind local re-execution results to the authenticated ledger commitment. Silently ignoring `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` means this verification path can incorrectly certify a match even when the hot-state root or position-state root diverges — i.e., the authenticated response ("replay succeeded / matches") is misbound to the wrong internal ledger object/root.

That said, the fields being ignored only carry meaningful data when the corresponding on-chain features (`hot_state_root_in_txn_info`, `compute_trading_native_state_roots`) are enabled, both gated behind `transaction_info_v1` [5](#0-4) . The code comment itself flags this as a known, not-yet-closed gap to be fixed "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS" [6](#0-5) , indicating these features are not yet active on mainnet. Since these state roots are not part of committed consensus-verified state (they don't affect the primary state root/accumulator that underlies consensus-committed transactions), this does not corrupt committed mainnet state or bypass consensus/BFT-verified proofs — it only weakens an offline/tooling replay-verification check for a feature that is explicitly gated off today.

### Likelihood Explanation
Low on current mainnet: this only manifests once `transaction_info_v1`, `hot_state_root_in_txn_info`, or `compute_trading_native_state_roots` on-chain features are turned on, which per the code's own guard logic and comments has not happened yet. The gap is real in the code today, but it's a latent tooling-verification weakness tied to unreleased features, not an exploitable path against currently-active mainnet consensus or storage-committed state.

### Recommendation
Extend `ensure_match_transaction_info` to compare `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` from `TransactionInfo::V1` against freshly computed hot-state/position roots whenever those fields are present, before any feature that populates them is enabled on mainnet, exactly as the existing TODO comment recommends.

### Proof of Concept
1. Enable (in a test/local config) `transaction_info_v1` and `hot_state_root_in_txn_info` in `BlockExecutorConfigFromOnchain`.
2. Construct a `TransactionInfo::V1` record whose `hot_state_checkpoint_hash` is set to some hash `H1`.
3. Construct a `TransactionOutput` whose actual freshly-computed hot state hashes to `H2 != H1`, but whose `write_set` and `events` hash to the same `state_change_hash`/`event_root_hash` values recorded in the `TransactionInfo`.
4. Call `output.ensure_match_transaction_info(version, &txn_info, None, None)`.
5. Observe the call returns `Ok(())` despite `H1 != H2`, because the function body [7](#0-6)  never reads or compares the checkpoint hash fields.

This confirms the described gap exists in the current code, gated behind not-yet-enabled on-chain features, and documented by the authors themselves as an open TODO.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
