### Title
Unbounded growth of the per-shop session-id index can permanently deny future session storage/lookup for a shop - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage` maintains one KV value per shop (`shop:<shop>`) that is an ever-growing JSON array of session ids. Every call to `storeSession` unconditionally appends the new session id to this array without deduplication or any size bound. Because online-access-token sessions are created with a fresh, unique session id on every OAuth authorization, an attacker (a single merchant/app user, or anyone able to drive the app's OAuth begin/callback flow repeatedly) can keep growing this shared array without limit until the underlying KV value size limit is hit, permanently breaking session storage and lookup for that shop — the same class of "unbounded, permissionless write to shared accounting state eventually causing overflow/size-limit failure and a permanent lock" described in the source report, just manifesting as a KV value-size ceiling instead of a `uint96` overflow.

### Finding Description
`storeSession` always calls `addShopIds`, which reads the current id list, appends the new id(s), and writes the whole array back with no cap and no check for duplicates: [1](#0-0) [2](#0-1) 

`findSessionsByShop` and `deleteSession`/`removeShopIds` also depend on being able to read/rewrite this single blob: [3](#0-2) 

Every online-access-token OAuth flow produces a brand-new session with a distinct id (offline sessions are deterministic `offline_${shop}`, but online sessions are not, so re-running the online OAuth flow repeatedly for the same shop generates a new, never-reused id each time). Since `addShopIds` never dedupes or evicts stale ids, and the OAuth begin/callback endpoints that ultimately call `storeSession` are reachable by any user of the app (a "single merchant" actor per the allowed threat model, no elevated privilege required), the attacker can drive unbounded growth of the `shop:<shop>` array purely by repeatedly authenticating online.

### Impact Explanation
KV-backed stores (e.g., Cloudflare Workers KV) enforce a hard maximum size per value. Once the `shop:<shop>` array exceeds that limit, `namespace.put` in `addShopIds` will throw, and because `storeSession` awaits `addShopIds` after already writing the session record, the whole `storeSession` call rejects. This breaks the OAuth callback for that shop going forward (no session can ever be persisted again), and `findSessionsByShop` will also start failing to read/parse the oversized blob — a durable denial-of-service of the auth/session-storage handler for that tenant, mirroring the "permanently locked pool" outcome in the report, scoped to session storage of the targeted shop.

### Likelihood Explanation
No cryptographic bypass or privileged access is required — only the ability to repeatedly trigger the online OAuth flow for an installed app, which is standard, unauthenticated-by-design behavior of the auth begin/callback handlers. The only cost to the attacker is the number of round trips needed to exceed the KV per-value size limit, which is easily scriptable.

### Recommendation
- Deduplicate session ids before writing (`Set` semantics) instead of blindly concatenating.
- Cap the number of ids retained per shop and prune expired/replaced sessions on write (e.g., drop online sessions whose `expires` has passed).
- Consider restructuring storage so the shop-to-session index is not a single unbounded blob (e.g., one KV key per `shop`+`session id` pair with a prefix scan/list operation), removing the single-point growth/size-limit failure mode entirely.

### Proof of Concept
1. Install the app and complete online OAuth authorization for a shop, repeating the online-token OAuth begin/callback flow N times (each run creates a new unique online session id and calls `storeSession`).
2. Each call appends to `shop:<shop>` via `addShopIds` without dedup: [1](#0-0) 
3. After enough repetitions, the `shop:<shop>` value exceeds the KV backend's per-value size limit; the next `namespace.put` call inside `addShopIds` throws, causing `storeSession` (and therefore the OAuth callback handler) to fail for that shop from then on, and `findSessionsByShop` to fail to enumerate sessions for the shop.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private getShopSessionIdsKey(shop: string): string {
    return `shop:${shop}`;
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async removeShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(
      key,
      JSON.stringify(shopIds.filter((id) => !ids.includes(id))),
    );
  }
