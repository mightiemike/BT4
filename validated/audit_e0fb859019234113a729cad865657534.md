## Analysis: Misleading "getter" with accounting side-effects in TVM energy budgeting [1](#0-0) 

### Title
`getAccountEnergyLimitWithFixRatio` silently mutates and persists account energy-usage accounting despite its "getter" name - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
Mirroring the UMA report's `_getLatestFundingRate`/`getPrice` pattern (a function that reads as a pure getter but silently performs state-changing side-effects), `VMActuator.getAccountEnergyLimitWithFixRatio` is named and used as if it merely computes/returns an account's available energy for a TVM `CALL`, but for accounts under the Freeze V2 model it also mutates the caller's `AccountCapsule` energy-usage window and **commits it to the repository** as a side-effect.

### Finding Description
The function signature and call sites treat it purely as a query used to size the energy budget for a nested `CALL`: [2](#0-1) 

However, when `VMConfig.allowTvmFreezeV2()` is enabled, the same call:
1. Instantiates an `EnergyProcessor` and calls `updateUsage(account)`, which recomputes and overwrites `account.setEnergyUsage(...)` in-memory.
2. Sets `account.setLatestConsumeTimeForEnergy(now)`.
3. Calls `energyProcessor.increase(...)` and re-assigns `account.setEnergyUsage(...)` again with the *merged* usage that includes the energy reserved for this call.
4. Finally calls `rootRepository.updateAccount(account.createDbKey(), account)`, persisting these mutations to the repository: [3](#0-2) 

None of this is hinted at by the method name `getAccountEnergyLimitWithFixRatio`, which reads like a pure accessor (analogous to `getPrice`/`_getLatestFundingRate` in the original report). A developer modifying call-graph logic around TVM `CALL` opcode handling (e.g., adding a retry, a pre-check, or reusing this helper to simply "peek" at an account's available energy) could invoke it more than once per transaction — or in a code path that should be side-effect-free (e.g., a dry-run/validation branch) — and unintentionally cause the account's energy-usage window and `latestConsumeTimeForEnergy` to be advanced/persisted multiple times, diverging from the intended semantics of the sliding-window resource model implemented in `ResourceProcessor.increase`/`recovery`: [4](#0-3) [5](#0-4) 

### Impact Explanation
Energy accounting underlies TVM resource pricing/settlement for every smart-contract-invoking transaction. A misuse of this mis-named "getter" (e.g., calling it more than once for the same `CALL` while computing/re-computing budgets, or reusing it in a future refactor for a read-only estimate such as `triggerConstantContract`) would silently advance and persist the caller account's `energyUsage` and `latestConsumeTimeForEnergy`, producing incorrect resource-accounting state (double-consumption or premature exhaustion of frozen energy) without any indication in the calling code that a write occurred. This falls into the "accounting"/"invalid-state divergence" impact bucket referenced in the validation criteria, since it can desynchronize an account's tracked energy usage from its actual on-chain resource entitlement.

### Likelihood Explanation
The function is invoked from within `VMActuator`'s `call()` handling of `CALL`-family opcodes, which is exercised by any unprivileged user submitting a transaction that triggers a smart contract performing an internal message call — a very common, fully public code path. The side-effect is currently gated behind a single call site as far as could be confirmed, so exploitation requires either an existing but unverified second invocation path or a future code change that reuses this "getter" believing it to be side-effect free (exactly the failure mode the original UMA report warns about). I was not able to fully trace all reachable call sites of this method within the available tool budget to confirm a second, currently-existing invocation in the same transaction; this should be verified with a full call-graph review before treating this as an actively exploitable bug versus a latent maintainability/accounting-safety hazard.

### Recommendation
Split `getAccountEnergyLimitWithFixRatio` into a pure read-only computation (`calculateAccountEnergyLimit`) and an explicit mutating/committing step (e.g., `consumeAndPersistCallerEnergy`), so that callers cannot invoke the persistence side-effect unintentionally. At minimum, rename the method to make the write behavior explicit (e.g., `getAndConsumeAccountEnergyLimitWithFixRatio`) and add documentation/comments noting that it commits to `rootRepository`.

### Proof of Concept
Not applicable as a standalone exploit — this is a code-hygiene/accounting-safety finding, consistent with the "no PoC, code-pattern" nature of the original UMA report. The concrete evidence is the function body itself: [1](#0-0)

  public long getAccountEnergyLimitWithFixRatio(AccountCapsule account, long feeLimit,
      long callValue) {

    long sunPerEnergy = VMConstant.SUN_PER_ENERGY;
    if (rootRepository.getDynamicPropertiesStore().getEnergyFee() > 0) {
      sunPerEnergy = rootRepository.getDynamicPropertiesStore().getEnergyFee();
    }

    long leftFrozenEnergy = rootRepository.getAccountLeftEnergyFromFreeze(account);
    if (VMConfig.allowTvmFreeze() || VMConfig.allowTvmFreezeV2()) {
      receipt.setCallerEnergyLeft(leftFrozenEnergy);
    }

    long energyFromBalance = max(account.getBalance() - callValue, 0,
        VMConfig.disableJavaLangMath()) / sunPerEnergy;
    long availableEnergy = addExact(leftFrozenEnergy, energyFromBalance,
        VMConfig.disableJavaLangMath());

    long energyFromFeeLimit = feeLimit / sunPerEnergy;
    if (VMConfig.allowTvmFreezeV2()) {
      long now = rootRepository.getHeadSlot();
      EnergyProcessor energyProcessor =
          new EnergyProcessor(
              rootRepository.getDynamicPropertiesStore(),
              ChainBaseManager.getInstance().getAccountStore());
      energyProcessor.updateUsage(account);
      account.setLatestConsumeTimeForEnergy(now);
      receipt.setCallerEnergyUsage(account.getEnergyUsage());
      receipt.setCallerEnergyWindowSize(account.getWindowSize(ENERGY));
      receipt.setCallerEnergyWindowSizeV2(account.getWindowSizeV2(ENERGY));
      account.setEnergyUsage(
          energyProcessor.increase(account, ENERGY,
              account.getEnergyUsage(), min(leftFrozenEnergy, energyFromFeeLimit,
                  VMConfig.disableJavaLangMath()), now, now));
      receipt.setCallerEnergyMergedUsage(account.getEnergyUsage());
      receipt.setCallerEnergyMergedWindowSize(account.getWindowSize(ENERGY));
      rootRepository.updateAccount(account.createDbKey(), account);
    }
    return min(availableEnergy, energyFromFeeLimit, VMConfig.disableJavaLangMath());

  }

      long lastUsage, long usage, long lastTime, long now) {
    if (dynamicPropertiesStore.supportAllowCancelAllUnfreezeV2()) {
      return increaseV2(accountCapsule, resourceCode, lastUsage, usage, lastTime, now);
    }
    long oldWindowSize = accountCapsule.getWindowSize(resourceCode);
    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(this.precision);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision),
          BigInteger.valueOf(oldWindowSize));
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision),
          BigInteger.valueOf(this.windowSize));
    } else {
      averageLastUsage = divideCeil(lastUsage * this.precision, oldWindowSize);
      averageUsage = divideCeil(usage * this.precision, this.windowSize);
    }

    if (lastTime != now) {
      if (lastTime + oldWindowSize > now) {
        long delta = now - lastTime;
        double decay = (oldWindowSize - delta) / (double) oldWindowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }

    long newUsage = getUsage(averageLastUsage, oldWindowSize, averageUsage, this.windowSize);
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      long remainUsage = getUsage(averageLastUsage, oldWindowSize);
      if (remainUsage == 0) {
        accountCapsule.setNewWindowSize(resourceCode, this.windowSize);
        return newUsage;
      }
      long remainWindowSize = oldWindowSize - (now - lastTime);
      long newWindowSize = getNewWindowSize(remainUsage, remainWindowSize, usage,
          windowSize, newUsage);
      accountCapsule.setNewWindowSize(resourceCode, newWindowSize);
    }

  }
