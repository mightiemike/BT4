## Finding Confirmed

### Title
Hot-state Sparse Merkle Tree updates are sorted by raw `StateKey` instead of key-hash order, violating `batch_update_sorted_uniq`'s precondition and corrupting the hot state root - (File: `storage/storage-interface/src/state_store/state_summary.rs`)

### Summary
`StateSummary::update_hot_state_summary` builds the list of hot-state SMT updates and sorts them by `*k` (the raw `StateKey`), whereas the parallel `update_global_state_summary` path — operating on the exact same kind of updates and feeding the same `batch_update_sorted_uniq` API — explicitly sorts by `k.crypto_hash_ref()` because the function's own comment states the precondition: *"shards are ordered by the first nibble of the key hash. `batch_update_sorted_uniq` can be called if within each shard items are sorted by key hash."* [1](#0-0) [2](#0-1) 

### Finding Description
Both `update_hot_state_summary` and `update_global_state_summary` call `SparseMerkleTree::batch_update_sorted_uniq`, a batch-insertion algorithm whose correctness depends on the input list being pre-sorted by the position each key occupies in the Merkle trie — i.e., sorted by the key's cryptographic hash (`crypto_hash_ref()`), not by the key's own `Ord` implementation. The cold/global path honors this at line 216 (`.sorted_by_key(|(k, _v)| k.crypto_hash_ref())`). The hot-state path at line 183 instead sorts with `.sorted_by_key(|(k, _)| *k)`, ordering by the raw `StateKey` value.

For any batch of hot-state insertions/evictions whose `StateKey` ordering diverges from their crypto-hash ordering (which is the general case, since a cryptographic hash is not order-preserving with respect to the key's own byte/`Ord` representation), the items handed to `batch_update_sorted_uniq` are not actually sorted in hash order despite the algorithm assuming they are. Because the algorithm consumes the pre-sorted list to walk/build the trie without independently re-verifying ordering by hash, feeding it items out of hash order can silently produce a tree whose root hash does not correctly reflect the update set (or, depending on internal implementation details of `batch_update_sorted_uniq`, cause an incorrect merge/skip of subtrees).

### Impact Explanation
This directly maps to the "Wrong accumulator root / Merkle proof" gate: the resulting `hot_state_summary` root (`StateSummary::hot_root_hash`) can diverge from the value a correct, hash-sorted implementation would produce for the identical input updates. Any two nodes processing the same hot-state update batch through this code path will compute an incorrect and non-deterministically-matching root relative to nodes that (hypothetically) sort correctly, or relative to a reference implementation — this is a hard-fork-class divergence class of bug if the hot root is used in any binding/consensus-sensitive context, and at minimum corrupts the internal state-authentication artifact `StateSummary` produces for the hot half of state. [3](#0-2) 

### Likelihood Explanation
This triggers deterministically whenever the batch of hot-state insertions/evictions in a shard contains `StateKey`s whose natural ordering differs from their hash ordering — which is essentially every non-trivial batch, since the point of a cryptographic hash is that it is not order-preserving over the key's own representation. The precondition violation is unconditional on the code path, not attacker-crafted; it is a latent correctness bug reachable purely through ordinary state writes/evictions that flow into the hot-state layer, i.e., unprivileged transaction execution results feeding this code, no privileged/operator trust required.

### Recommendation
Change line 183 to sort by hash, matching the cold path:
```rust
.sorted_by_key(|(k, _)| k.crypto_hash_ref())
```
Additionally add an assertion (debug-mode invariant) inside `batch_update_sorted_uniq` or immediately before invoking it that verifies the input is strictly sorted by hash, so any future path that violates this precondition fails loudly rather than silently corrupting the root.

### Proof of Concept
1. Construct two `StateKey`s `k1`, `k2` such that `k1 < k2` under `StateKey`'s own `Ord`, but `crypto_hash(k1) > crypto_hash(k2)` (trivial to find by brute force, since hash order is unrelated to `Ord` order).
2. Insert both into a hot-state shard's `insertions` map with distinct values, so that `hot_updates` contains `[(k1, Some(h1)), (k2, Some(h2))]`.
3. Run `update_hot_state_summary`: line 183 sorts by `*k`, producing order `[k1, k2]` — the reverse of hash order.
4. Independently compute a reference hot root by sorting the same two updates by `crypto_hash_ref()` (i.e., `[k2, k1]`) and feeding that to `batch_update_sorted_uniq`.
5. Assert `hot_smt_result.root_hash() != reference_root_hash` — demonstrating the produced hot root diverges from the correct, hash-sorted result for identical input data.

**Note on scope/severity uncertainty:** I was not able to fully trace, within the tool budget available, whether `StateSummary::hot_root_hash()` is consumed by any consensus-critical, proof-serving, or client-authenticated code path versus being used purely as an internal performance-cache artifact for the "hot state" working set. If the hot root is purely an execution-layer optimization never exposed via authenticated APIs, proofs, or consensus commitments, the practical severity is reduced even though the code defect itself (violating `batch_update_sorted_uniq`'s sort precondition) is real and should be fixed. I recommend verifying all consumers of `hot_root_hash()` / `hot_state_summary` to confirm whether this corruption can reach an authenticated response or consensus-bound commitment.
