### Title
Long-overflow of `ExchangeCapsule` balances via `ExchangeInjectActuator` when `ALLOW_HARDEN_EXCHANGE_CALCULATION` is at its default (0) - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the new exchange balances with `addExact()`, which is overridden in `AbstractExchangeActuator` to fall back to plain, non-strict `x + y` whenever `allowHardenExchangeCalculation()` returns `0` (the chain default). An attacker who controls enough of a token's balance (e.g., the creator of their own TRC10 asset with a large total supply) can pick `tokenQuant` so that `firstTokenBalance + tokenQuant` overflows a `long`, both bypassing the `balanceLimit` check in `doValidate()` and committing a wrapped/negative balance to the persisted `ExchangeCapsule` in `execute()`.

### Finding Description
`AbstractExchangeActuator.addExact/subtractExact` intentionally hide `AbstractActuator`'s `Maths`-based `addExact`/`subtractExact` with a version gated by the exchange-specific flag: [1](#0-0) 

When `allowHardenExchangeCalculation()==0` (the default until a proposal changes it), `addExact`/`subtractExact` reduce to plain `+`/`-`, with no overflow detection, unlike `StrictMathWrapper.addExact` which would throw `ArithmeticException`.

`doValidate()` computes `anotherTokenQuant` exactly via `BigInteger` (protected from overflow by `longValueExact()`), but computes `newTokenBalance`/`newAnotherTokenBalance` — used for the `balanceLimit` check — via the overridable `addExact`: [2](#0-1) 

If `firstTokenBalance + tokenQuant` overflows a `long` under plain `+`, the result wraps to a negative number, which is trivially `<= balanceLimit`, so the check silently passes instead of rejecting the transaction.

`execute()` then repeats the identical non-strict computation and commits it directly to the persisted `ExchangeCapsule`: [3](#0-2) 

This means the same overflow occurs deterministically in both `doValidate()` and `execute()` (so it is not a validate/execute mismatch causing non-determinism by itself, but a genuine unguarded overflow path), and the corrupted (wrapped/negative) balance is written into on-chain state via `Commons.putExchangeCapsule(...)`. Because `allowHardenExchangeCalculation` is a `DynamicPropertiesStore` proposal-controlled flag, nodes that have not yet activated the corresponding hardening proposal will accept and commit this corrupted state, while a node that has activated it would compute via `StrictMathWrapper.addExact` and throw `ArithmeticException`, causing a validation/consensus divergence between differently-configured (but each individually "honest") node states during a proposal rollout window.

The attacker needs actual ownership of `tokenQuant` amount of the injected token (checked via `accountCapsule.assetBalanceEnoughV2` / `accountCapsule.getBalance()`), so to trigger the overflow the attacker must hold a token balance on the order of `Long.MAX_VALUE - firstTokenBalance` (~9.2×10^18). This is feasible for the creator of a custom TRC10 token who mints/holds a near-`Long.MAX_VALUE` total supply of their own asset (a legitimate, permissionless, unprivileged action), then creates/uses an Exchange pairing that asset as `firstTokenID` with a small `firstTokenBalance`, and injects a `tokenQuant` chosen to overflow `firstTokenBalance + tokenQuant`.

### Impact Explanation
A successful overflow corrupts the persisted `ExchangeCapsule.firstTokenBalance`/`secondTokenBalance` to a wrapped/negative `long`, producing invalid AMM state. Subsequent trades (`ExchangeTransactionActuator`/`ExchangeWithdrawActuator`) against this exchange would operate on nonsensical balances, potentially enabling mispriced trades, fund draining from the exchange pool, or a state that differs across nodes depending on whether they have activated `ALLOW_HARDEN_EXCHANGE_CALCULATION`, which is a chain state-divergence/consensus risk during proposal activation windows.

### Likelihood Explanation
Requires: (1) `ALLOW_HARDEN_EXCHANGE_CALCULATION==0` (true by default), and (2) attacker controlling/holding an asset balance near `Long.MAX_VALUE` (achievable by issuing one's own TRC10 asset with an extreme total supply, a permissionless action subject only to `AssetIssueActuator` validation, not admin-gated). Given these preconditions, the exploit is deterministic and repeatable — it is a straightforward arithmetic overflow, not a race condition.

### Recommendation
Do not gate exchange balance-affecting arithmetic (`addExact`/`subtractExact` inside `AbstractExchangeActuator`) behind a togglable dynamic property that defaults to unsafe behavior. Always use `StrictMathWrapper`/checked arithmetic for exchange balance updates (or clamp with sanity bounds derived from `exchangeBalanceLimit` before performing the addition), so overflow always throws `ArithmeticException` in `doValidate()` regardless of `allowHardenExchangeCalculation`, and ensure `execute()` cannot commit an unchecked wrapped value even when the flag is at its default value.

### Proof of Concept
```java
// Framework test - actuator/src/test/java/org/tron/core/actuator/ExchangeInjectActuatorTest.java style
@Test
public void testOverflowWithDefaultAllowHardenExchangeCalculation() throws Exception {
  // 1. Ensure ALLOW_HARDEN_EXCHANGE_CALCULATION is default (0) - do not set it.
  dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);

  // 2. Issue a TRC10 asset with a huge totalSupply (attacker-controlled, permissionless)
  long hugeSupply = Long.MAX_VALUE - 1000L;
  // ... create asset via AssetIssueActuator so attacker account owns hugeSupply of tokenId "A"

  // 3. Create Exchange pairing tokenId "A" (firstToken, small balance, e.g. 100L) with TRX (secondToken)
  //    via ExchangeCreateActuator, using the attacker account as creator.

  // 4. Attacker calls ExchangeInjectActuator with tokenId == firstTokenID ("A"),
  //    tokenQuant chosen so firstTokenBalance(100L) + tokenQuant overflows long:
  long tokenQuant = Long.MAX_VALUE - 50L; // firstTokenBalance(100) + tokenQuant overflows past Long.MAX_VALUE

  ExchangeInjectActuator actuator = new ExchangeInjectActuator();
  actuator.setChainBaseManager(chainBaseManager)
      .setAny(getContract(ownerAddress, exchangeId, "A".getBytes(), tokenQuant));

  boolean validateResult = actuator.validate(); // EXPECTED (bug): returns true, no ArithmeticException
  Assert.assertTrue(validateResult);

  TransactionResultCapsule ret = new TransactionResultCapsule();
  actuator.execute(ret);

  ExchangeCapsule capsule = chainBaseManager.getExchangeStore().get(ByteArray.fromLong(exchangeId));
  // EXPECTED (bug): committed firstTokenBalance is wrapped/negative instead of throwing
  Assert.assertTrue(capsule.getFirstTokenBalance() < 0);
}
```
Expected result on an unpatched node (`allowHardenExchangeCalculation()==0`): `validate()` returns `true` and `execute()` commits a negative `firstTokenBalance` to the `ExchangeCapsule`. On a node with the flag enabled, the same call throws `ArithmeticException` from `StrictMathWrapper.addExact`, demonstrating the divergence.
