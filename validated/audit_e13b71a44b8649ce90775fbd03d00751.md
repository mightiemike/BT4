### Title
Legacy (non-hardened) `ExchangeCapsule.transaction()` path allows exchange reserve balances to go negative without any guard, and `ExchangeTransactionActuator` never validates `anotherTokenQuant` against the actual opposing reserve - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeTransactionActuator.doValidate()`/`execute()` compute the counter-asset amount (`anotherTokenQuant`) purely from the double-precision Bancor formula in `ExchangeProcessor` and only check that it is **not less than** the caller-supplied `expected` minimum [1](#0-0) . There is no check anywhere in `doValidate()` or `execute()` that `anotherTokenQuant` does not exceed the exchange's current opposing reserve, unlike `ExchangeWithdrawActuator`, which explicitly enforces `"exchange balance is not enough"` [2](#0-1) . `ExchangeCapsule.transaction()` only rejects negative resulting balances when the `hardenedCalc` (harden) flag is true; in the legacy/default arithmetic path balances are updated with plain `+`/`-` and no negativity check is performed at all [3](#0-2) .

### Finding Description
The reachable call path is: attacker broadcasts an `ExchangeTransactionContract` → `Wallet`/HTTP `/wallet/exchangetransaction` → `ExchangeTransactionActuator.validate()`/`execute()`. Inside `execute()`, `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` computes the counter-asset amount and mutates `firstTokenBalance`/`secondTokenBalance` in one step [4](#0-3) .

Inside `ExchangeCapsule.transaction()`, the amount is derived from `ExchangeProcessor.exchange()`, a double-precision Bancor-style calculation using `Math.pow` and `(long)` truncation [5](#0-4) . When `hardenedCalc` (`allowHarden()`, gated by the `allowHardenExchangeCalculation` chain parameter) is `false`, the new balances are computed with plain primitive arithmetic and the guard `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...` is skipped entirely, meaning negative balances are silently accepted [6](#0-5) .

Separately, `doValidate()` in `ExchangeTransactionActuator` never checks that `anotherTokenQuant` (the amount to be credited to the attacker) does not exceed the current reserve of the token being bought; it only enforces a lower bound via `tokenExpected` [1](#0-0) . Contrast this with `ExchangeWithdrawActuator.doValidate()`, which explicitly checks `firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant` before allowing the operation [7](#0-6) . The absence of an equivalent check in the transaction actuator, combined with the unguarded legacy arithmetic path in `ExchangeCapsule.transaction()`, means a maliciously crafted `quant` near a reserve boundary combined with `expected=0` can drive `secondTokenBalance` (or `firstTokenBalance`) negative while the attacker's own account is still credited the full `anotherTokenQuant` via `addAssetAmountV2`/`setBalance` [8](#0-7) .

The codebase's own test suite confirms this exact class of defect was identified and later mitigated by the harden mode: `testHardenedTransactionNegativeBalanceThrows` and `hardenedExecuteOverflowThrowsArithmeticException` demonstrate that the hardened path (`SafeExchangeProcessor` + `StrictMathWrapper` + explicit `< 0` check) throws where the legacy path would not [9](#0-8) .

### Impact Explanation
If `allowHardenExchangeCalculation` is not active on the network (its default/off state could not be conclusively confirmed from the indexed files), an attacker who owns a small amount of one asset in an exchange pair can call `/wallet/exchangetransaction` with `quant` chosen so that the Bancor double-math output for `anotherTokenQuant` exceeds the actual opposing reserve, driving that reserve negative while still being credited the computed amount in their own account. This corresponds to the TRON bounty "asset/accounting corruption" impact class — the exchange's internal ledger no longer conserves reserves, and subsequent participants trading against or withdrawing from the same pair will compute against a corrupted (negative) balance.

### Likelihood Explanation
Exploitability depends entirely on the runtime value of the `allowHardenExchangeCalculation` proposal parameter, which I was not able to confirm as on or off by default from the available indexed source (`DynamicPropertiesStore.java` default value was not retrievable within the tool budget). If it is off, the attack requires only an ordinary funded account, one signed transaction, and no special privileges — the `firstTokenBalance == 0` guard is the only precondition preventing zero-reserve pairs, and there is no bound check preventing `anotherTokenQuant` from exceeding the counter reserve. If harden mode is already active (as the extensive dedicated hardening code and tests suggest may be the mainnet-intended state), this specific defect is already mitigated and the finding would only apply to legacy/pre-hardening chain states or sidechains that have not activated the proposal.

### Recommendation
1. In `ExchangeTransactionActuator.doValidate()`, add an explicit check that `anotherTokenQuant` does not exceed the current balance of the counter-asset in the exchange (mirroring `ExchangeWithdrawActuator`'s `"exchange balance is not enough"` check), independent of the harden flag.
2. Make the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard in `ExchangeCapsule.transaction()` unconditional (not gated on `hardenedCalc`), so legacy-mode calculations cannot silently produce negative reserves.
3. Consider enabling `allowHardenExchangeCalculation` unconditionally by default (retiring the legacy double-math path) given it has already been fully implemented and tested.

### Proof of Concept
```java
// Add to ExchangeCapsuleTest.java (legacy, non-hardened path)
@Test
public void legacyTransactionCanProduceNegativeReserve() throws Exception {
  ExchangeCapsule capsule = new ExchangeCapsule(
      ByteString.copyFromUtf8("owner"), 200L, 0L,
      "abc".getBytes(), "def".getBytes());
  // Small, near-boundary reserves typical of a thin/newly created pair
  capsule.setBalance(1_000L, 1_000L);

  // hardenedCalc = false (legacy/default path), no <0 guard is applied
  long buyQuant = capsule.transaction("abc".getBytes(), Long.MAX_VALUE / 2, true, false);

  // Demonstrates the reserve conservation invariant is violated:
  // secondTokenBalance goes negative with no exception thrown.
  Assert.assertTrue("Reserve should not go negative but did",
      capsule.getSecondTokenBalance() < 0);
}
```
This shows `ExchangeCapsule.transaction()` in legacy mode has no protection against reserve underflow; the corresponding actuator-level PoC would be a signed `ExchangeTransactionContract` with a similarly sized `quant` (bounded by `getExchangeBalanceLimit()`) and `expected=0`, broadcast against a thinly-reserved exchange pair, followed by asserting `ExchangeCapsule.getSecondTokenBalance() < 0` post-execution via `ExchangeTransactionActuator.execute()`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
