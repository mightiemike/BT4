### Title
Receipt Size Limit Bypass via Post-Validation `output_data_receivers` Mutation in `promise_return` Path — (`File: runtime/runtime/src/lib.rs`)

---

### Summary

In `apply_action_receipt`, newly created receipts are validated against `max_receipt_size` (4 MiB) immediately after each action executes. However, when a contract uses `promise_return` (returning a `ReceiptIndex`), the runtime **mutates the already-validated receipt** by appending `output_data_receivers` from the parent receipt to it. This post-validation mutation can push the receipt's serialized size above `max_receipt_size`. An unprivileged user who can deploy and call a contract can exploit this to create oversized receipts that propagate through the network, inflating `ChunkStateWitness` beyond its 17 MiB design limit. The bug is acknowledged in the codebase as issue #12606 but remains unpatched.

---

### Finding Description

The receipt size check in `validate_receipt` is gated on `ValidateReceiptMode::NewReceipt`: [1](#0-0) 

This check runs inside the per-action loop in `apply_action_receipt`: [2](#0-1) 

After the loop completes and all receipts have passed size validation, the runtime handles the `promise_return` case. If the contract returned a `ReceiptIndex` (i.e., called `promise_return`), the runtime **extends the already-validated receipt's `output_data_receivers`** with those from the parent receipt: [3](#0-2) 

This mutation happens entirely outside the validation loop. A contract can craft a receipt whose size is exactly at `max_receipt_size` (4,194,304 bytes), pass validation, and then have `output_data_receivers` appended — each `DataReceiver` adds ~50–100 bytes — pushing the final receipt above the limit.

A second variant exists via `value_return`: returning a value of exactly `max_length_returned_data` bytes (4 MiB) passes the host-function check, but the resulting `DataReceipt` wrapping that value in a borsh envelope exceeds `max_receipt_size`.

The codebase explicitly acknowledges both variants as a known bug: [4](#0-3) 

The workaround in `try_forward` clamps the oversized receipt's size to `max_receipt_size` for admission-limit purposes so it does not get stuck, but does **not** prevent the oversized receipt from being created and forwarded: [5](#0-4) 

Incoming receipts are validated with `ExistingReceipt` mode (which skips the size check), so the oversized receipt is accepted and executed on the receiving shard: [6](#0-5) 

The test suite confirms that oversized receipts are created and propagated in both the `promise_return` and `value_return` scenarios: [7](#0-6) [8](#0-7) 

---

### Impact Explanation

The `ChunkStateWitness` size design target is 17 MiB. The `max_receipt_size` limit of 4 MiB is a hard component of that budget: [9](#0-8) 

An oversized receipt (e.g., 4 MiB + N bytes of `output_data_receivers`) inflates the witness beyond the intended ceiling. If an attacker repeatedly triggers this across multiple shards, the aggregate witness size can exceed what validators can distribute and verify within block time, constituting a non-network-level denial of service against chunk validation. This is fixable without a hardfork by re-validating receipt size after the `output_data_receivers` mutation.

---

### Likelihood Explanation

Any unprivileged user who can deploy a WASM contract (standard on NEAR mainnet) can trigger this. The attack requires:
1. Deploy a contract with a method that creates a near-max-size receipt and calls `promise_return` on it.
2. Call that method from a transaction that has a callback (so the parent receipt has non-empty `output_data_receivers`).

No privileged role, validator access, or key compromise is required. The test contract `max_receipt_size_promise_return_method2` in the repository demonstrates the exact pattern: [10](#0-9) 

---

### Recommendation

After the `output_data_receivers` extension at lines 1031–1049 of `runtime/runtime/src/lib.rs`, re-validate the mutated receipt's size before it is forwarded. Specifically, after the `extend_from_slice` calls, compute `borsh::object_length` of the modified receipt and return a `NewReceiptValidationError::ReceiptSizeExceeded` if it exceeds `limit_config.max_receipt_size`. This mirrors the existing check in `validate_receipt` and closes the post-validation mutation window.

---

### Proof of Concept

The existing integration test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` is a complete proof of concept: [11](#0-10) 

It constructs a receipt sized exactly at `max_receipt_size`, triggers `promise_return` so that `output_data_receivers` are appended post-validation, and then calls `assert_oversized_receipt_occurred` to confirm that a receipt exceeding `max_receipt_size` was observed in the chain — proving the bypass is reachable from ordinary unprivileged user actions.

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
