### Title
Attacker-crafted nonce-gap transactions crash the entire sequencer process via an unrecoverable `assert_eq!` panic in mempool staging - ([File: crates/apollo_mempool/src/mempool.rs])

### Summary
Analogous to the pwndoc `UnhandledPromiseRejection` bug (an unvalidated input path reaches a fatal, unguarded assertion that terminates the whole backend), the sequencer node installs a global panic hook that calls `std::process::exit(1)` on **any** panic anywhere in the process [1](#0-0) . This converts what would normally be an isolated, per-task Tokio panic into a full-node Denial of Service. The mempool's FIFO/Echonet admission path allows an unprivileged sender to enqueue transactions whose nonces are not contiguous, and later staging logic contains a hard `assert_eq!` that only holds under a contiguous-nonce invariant, producing a reachable panic → process exit.

### Finding Description
1. `apollo_node`'s `main` installs a panic hook that calls `std::process::exit(1)` after any panic, in addition to Tokio's default per-task unwind behavior: [1](#0-0) . This means a panic that would otherwise only fail one request/task instead kills the entire sequencer node — precisely the "any unhandled failure anywhere ends the whole backend" bug class described in the pwndoc report.
2. In FIFO/Echonet mempool mode, transactions from the same account are enqueued to the ready queue **regardless of nonce**, unlike the fee-priority mode where only the next-expected nonce is queued: [2](#0-1) . This is explicitly called out by the code's own comment and by a related (already-patched) eviction bug for the same reason: [3](#0-2) .
3. `Mempool::get_txs` pops a "ready chunk" straight from this FIFO queue and, for every popped transaction, calls `MempoolState::stage`, which asserts that any two consecutive stagings for the same address are nonce-contiguous: [4](#0-3) [5](#0-4) .
4. Because the FIFO queue only orders by arrival timestamp/block-number bucket (not by nonce), it can return the same address's nonce-0 and nonce-2 transactions in the same chunk while nonce-1 is absent/delayed. When `stage` is called first for nonce 0 (`next_nonce = 1`) and then for nonce 2 (`next_nonce = 3`), the assertion `try_increment_nonce(existing_nonce)? == next_nonce` (`try_increment_nonce(1) == 3`) fails, triggering `assert_eq!(..., "Staged nonce should be an increment of an existing nonce.")`, an unrecoverable panic.
5. Given the global exit-on-panic hook, this panic does not merely fail a batching attempt — it terminates the mempool component's task tree and the whole node process, per `run_component_servers`'s design where any server ending is already treated as fatal: [6](#0-5) .

### Impact Explanation
A single account controlled by an unprivileged attacker can submit two (or more) transactions with a nonce gap that both get admitted into the FIFO mempool queue. When the batcher subsequently calls `get_txs` to build a proposal, the node panics and, due to the global `exit(1)` panic hook, the entire sequencer process terminates. This matches the "network unable to confirm new transactions" bar in the validation rules: the affected node stops producing/validating blocks entirely until restarted, and if such a transaction propagates to multiple sequencers, all of them can be knocked out in sequence — a network-wide liveness DoS from a single crafted transaction.

### Likelihood Explanation
Likelihood depends on the FIFO/Echonet behavior mode being enabled in the deployed configuration (`BehaviorMode::Echonet`), since fee-priority mode does not enqueue nonce-gapped transactions and is therefore not affected. Where Echonet mode is active, the attack requires no special privileges — only submitting two ordinary transactions from an account with a nonce gap, both of which pass gateway validation (nonce-gap checks in the gateway allow a configurable gap: `max_allowed_nonce_gap`) and mempool admission (FIFO mode has no such nonce-contiguity check before queuing).

### Recommendation
- Do not allow `MempoolState::stage` to hard-panic on a broken invariant; convert the `assert_eq!` into a proper `MempoolResult` error path (as is already done for `try_increment_nonce` failures) so the caller (`get_txs`) can reject/skip the offending transaction instead of crashing.
- In the FIFO/Echonet queue, either enforce nonce-contiguity before admitting a chunk to `get_txs`, or de-duplicate/split cross-nonce-gap batches per address so `stage` never observes a discontinuity.
- Reconsider (or scope) the global `set_exit_process_on_panic` hook in `apollo_node::main`: an unexpected panic in one component (e.g., mempool) should not necessarily be fatal to the whole node if it can be contained and the component restarted, especially for invariant violations reachable from untrusted transaction input.

### Proof of Concept
1. Configure a mempool with `BehaviorMode::Echonet` (FIFO mode).
2. As an ordinary account holder, submit transaction A: `nonce = 0`.
3. Submit transaction B from the same account: `nonce = 2` (skip nonce 1). Under the current `add_tx_validations` / `validate_incoming_tx` logic, this is not a duplicate and is not less than the account's known nonce, so it can be admitted; FIFO mode enqueues it directly regardless of the gap (`crates/apollo_mempool/src/mempool.rs:605-617`).
4. Ensure `update_tx_block_metadata` places A and B in the same timestamp/block-number bucket so `FifoTransactionQueue::pop_ready_chunk` returns both in the same call.
5. Trigger `Mempool::get_txs`. The loop stages A (`next_nonce=1`, `staged[addr]=1`) then stages B (`next_nonce=3`); the check `try_increment_nonce(1) == 3` fails, panicking at `crates/apollo_mempool/src/mempool.rs:122-126`.
6. Because of `set_exit_process_on_panic` (`crates/apollo_node/src/main.rs:21-28`), this panic calls `std::process::exit(1)`, killing the sequencer node.

Note: I was not able to fully confirm within the tool budget how `TxBlockMetadata` (timestamp/block_number) is assigned to transactions in a live Echonet deployment (whether it is attacker-influenced or externally-supplied by a synced source chain), which affects exact reachability/likelihood of step 4; this would need further verification in a live/staging environment or with the full source of `apollo_mempool_p2p`/Echonet ingestion code.
