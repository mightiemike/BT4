Confirmed: `get_block_info_by_version` returns `last_version = committed_version` (the storage's latest ledger version) whenever the queried version's block is the *last* block, i.e. when there's no next block yet indexed [1](#0-0) . This confirms the reported `ledger_version` and the version used for the encryption-key resource lookup can genuinely diverge whenever the internal indexer lags behind storage.

### Title
`LedgerInfo.txn_encryption_key` bound to a stale internal-indexer version while `ledger_version` reports the newer storage version - ([File: api/src/context.rs])

### Summary
`Context::get_latest_internal_indexer_ledger_info` clamps the internal indexer's persisted version to `last_storage_version`, but then uses two *different* versions for two fields of the same authenticated `LedgerInfo` response: it fetches `encryption_key_hex` at the clamped `latest_version`, while it reports `ledger_version` as `block_end_version` — a value that is derived from storage's committed version, not from `latest_version` itself.

### Finding Description
In `get_latest_internal_indexer_ledger_info`: [2](#0-1) 

- `latest_version` is clamped: `latest_version = min(indexer_version, last_storage_version)`.
- `self.db.get_block_info_by_version(latest_version)` returns `(_, block_end_version, new_block_event)` — the *start*, *end* and block-event of the block containing `latest_version`.
- `AptosDbInternal::to_api_block_info` sets `last_version` to `committed_version` (the DB's actual latest committed version) whenever the block containing `latest_version` is the newest block on chain: [3](#0-2) . This means `block_end_version` can be strictly greater than `latest_version` whenever the internal indexer has not yet caught up to the end of the currently-committing block (a routine, non-malicious condition — internal indexer sync is asynchronous and per-transaction, per the code comment "The internal indexer version can be ahead of the storage committed version since it syncs to db's latest synced version" [4](#0-3) ).
- `get_encryption_key(latest_version)` is called with the *clamped, potentially stale* `latest_version`, not `block_end_version`: [5](#0-4) .
- The resulting `LedgerInfo` is constructed via `LedgerInfo::new_ledger_info(..., block_end_version, ..., encryption_key_hex)`, where the positional `ledger_version` field is filled with `block_end_version`: [6](#0-5)  and [7](#0-6) .

So the API's `ledger_version` field and the `txn_encryption_key` field of the same `LedgerInfo` object are computed at two different ledger versions (`block_end_version` vs. `latest_version`), whenever `latest_version < block_end_version`. If a reconfiguration transaction (which rotates `PerEpochEncryptionKeyResource` via `on_new_epoch`, see `aptos-move/framework/aptos-framework/sources/decryption.move:140-164`) lands between `latest_version` and `block_end_version`, the client is told a `ledger_version`/epoch that reflects post-reconfiguration state while `txn_encryption_key` reflects the pre-reconfiguration key — a genuine misbinding between the reported version and the returned encrypted-transaction key material in an authenticated API response used specifically to choose the key for encrypted transaction submission.

By contrast, `get_latest_storage_ledger_info` uses the *same* version consistently for both the block lookup and the encryption key lookup: [8](#0-7) , confirming that the internal-indexer path is the one with the inconsistent version binding.

### Impact Explanation
This affects `GET /v1` (and any handler calling `get_latest_ledger_info`, which prefers the internal-indexer path when enabled — see `get_latest_ledger_info` at [9](#0-8) ). A client relying on the reported `epoch`/`ledger_version` to pick the correct chunky-DKG encryption key for an encrypted-transaction submission could be handed a stale key during the transient window near an epoch boundary while the indexer is catching up mid-block. This is an authenticated-response misbinding (wrong version bound to wrong resource value) that falls within the "Authenticated API or state-view output bound to the wrong version, object, or proof context" impact category. It does not corrupt committed ledger state, accumulator roots, or proofs — only the API's version binding of the derived-config `encryption_key_hex` field.

### Likelihood Explanation
This requires no privileged action or malicious peer — it is triggered purely by normal asynchronous internal-indexer catch-up timing colliding with a normal epoch-changing reconfiguration transaction, both of which occur routinely on mainnet whenever the internal indexer feature and `allow_encrypted_txns_submission`/chunky-DKG are enabled. The window is narrow (the indexer must be lagging exactly within the last block of an epoch when queried) but is a deterministic, reproducible consequence of the code path.

### Recommendation
Use the same version for both the block-info lookup and the encryption-key lookup, or fetch the encryption key at `block_end_version` (the version actually reported as `ledger_version`) rather than at the clamped `latest_version`, so the `txn_encryption_key` field always reflects the state at the reported `ledger_version`.

### Proof of Concept
1. Start a node with internal indexer and `allow_encrypted_txns_submission`/chunky-DKG enabled.
2. Artificially slow down internal-indexer catch-up (e.g., via the existing `wait_for_internal_indexer_caught_up` polling pattern used in tests) so that `get_latest_internal_indexer_ledger_version()` reports a version inside the last block of epoch N while storage has already committed the epoch-N→N+1 reconfiguration transaction as `block_end_version`.
3. Call `GET /v1` and observe `LedgerInfo.ledger_version`/`epoch` reflect the post-reconfiguration state (via `block_end_version`/`new_block_event`) while `txn_encryption_key` (fetched via `get_encryption_key(latest_version)`) still reflects the pre-reconfiguration `PerEpochEncryptionKeyResource` value.
4. Assert failure: `encryption_key_hex` does not match the `PerEpochEncryptionKeyResource` committed at the reported `ledger_version`.

    pub fn get_latest_storage_ledger_info<E: ServiceUnavailableError>(
        &self,
    ) -> Result<LedgerInfo, E> {
        let ledger_info = self
            .get_latest_ledger_info_with_signatures()
            .context("Failed to retrieve latest ledger info")
            .map_err(|e| {
                E::service_unavailable_with_code_no_info(e, AptosErrorCode::InternalError)
            })?;

        let (oldest_version, oldest_block_height) = self.get_oldest_version_and_block_height()?;
        let (_, _, newest_block_event) = self
            .db
            .get_block_info_by_version(ledger_info.ledger_info().version())
            .context("Failed to retrieve latest block information")
            .map_err(|e| {
                E::service_unavailable_with_code_no_info(e, AptosErrorCode::InternalError)
            })?;

        let encryption_key_hex = self
            .get_encryption_key(ledger_info.ledger_info().version())
            .unwrap_or(None)
            .map(hex::encode);

        Ok(LedgerInfo::new(
            &self.chain_id(),
            &ledger_info,
            oldest_version,
            oldest_block_height,
            newest_block_event.height(),
            encryption_key_hex,
        ))
    }
