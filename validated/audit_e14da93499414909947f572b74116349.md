## Analysis

The withdrawQueue bug class ("one paused item at the front of a list blocks processing of everything else, causing a full revert instead of partial success") maps onto `BuildOutboundsFromReceipt` in `x/uexecutor/keeper/create_outbound.go`.

### Finding

`BuildOutboundsFromReceipt` iterates over every `UniversalTxOutbound` log emitted by the `UniversalGatewayPC` contract in a single EVM receipt (a single payload execution can emit multiple such logs, one per destination chain/action): [1](#0-0) 

For each log, it checks `IsChainOutboundEnabled` for that log's destination chain, and if disabled, it immediately does `return nil, fmt.Errorf(...)` — discarding the `outbounds` slice built so far, including any outbounds destined for other, fully-enabled chains that were already successfully parsed earlier in the loop, and skipping any remaining logs after it too.

This return value propagates up through `AttachOutboundsToExistingUniversalTx`: [2](#0-1) 

which is called after payload execution in both `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`: [3](#0-2) 

By this point, the deposit (PRC20 mint) has already committed and the payload's `executeUniversalTx` EVM call has already been executed and committed on Push Chain (`payloadPcTx.Status = "SUCCESS"` is recorded regardless). If `attachErr` occurs, the code only records `utx.RevertError = attachErr.Error()` on the UTX — no outbound at all is created, not even for the destination chains whose config was enabled.

### Impact

If a user's payload triggers multiple outbound events to different destination chains in one transaction (e.g., a payload that unlocks funds on both `eip155:11155111` and `eip155:1`), and one of those chains happens to have outbound disabled (registry-level pause/config state, not attacker-controlled), the entire `BuildOutboundsFromReceipt` call fails and **none** of the outbounds are attached — including the ones targeting enabled chains whose funds should have been released. The PC-side EVM state (the gateway contract's emitted events / internal bookkeping) already reflects that these outbound intents happened, but the UTX/`PendingOutbounds` state that drives the TSS-signing pipeline never gets populated for any of them. This is a temporary DoS on legitimate, enabled-chain fund releases caused by an unrelated disabled chain, and it also leaves the UTX in an inconsistent state (deposit/payload executed, but no outbound record and no revert path either — `RevertError` is just an informational string field, not a retriggering mechanism per the `README.md` note that `PendingOutbounds`/UTX mutation is append-only and stuck outbounds require manual/governance resolution).

### Verification status

I could not fully trace what operational recovery path (if any) exists once `utx.RevertError` is set in this scenario — the README documents that stuck/expired inbound ballots have `RevertStuckInbound` for admin recovery, but I found no equivalent for this specific "attach outbounds partially failed" case within the code I retrieved. This bears confirming with a deeper look at `x/uexecutor/keeper/admin_revert.go` and any related query/repair message handlers before treating this as fully unrecoverable, since I could not complete that trace within the given iteration budget.

### Title
Single disabled destination chain silently drops all outbounds from a multi-outbound receipt - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`BuildOutboundsFromReceipt` aborts and discards all parsed outbounds — including those destined for enabled chains — the moment it encounters one `UniversalTxOutbound` log whose destination chain has `IsOutboundEnabled = false`, mirroring the reported Ion Protocol pattern where one paused pool in a queue blocks withdrawal from all other active pools.

### Finding Description
`BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:16-105`) loops over all `UniversalTxOutbound` events in a receipt and builds an `OutboundTx` for each. On hitting a log for a chain with outbound disabled, it returns `nil, err` immediately [4](#0-3) , wiping out any outbounds already accumulated for other (enabled) chains in `outbounds` and never processing subsequent logs. This function is invoked post-execution, after the deposit and payload EVM call have already committed [3](#0-2) , so the failure only prevents the bookkeeping (`PendingOutbounds`/`UTX.OutboundTx`) from being created — it cannot roll back the already-executed payload.

### Impact Explanation
A user submitting a single payload that triggers multiple `UniversalTxOutbound` events to different destination chains can have all of them silently dropped if any one destination chain is outbound-disabled, even though the others are fully enabled and should be picked up by UVs for TSS signing and relay. This causes funds/state intended for release on enabled chains to become stuck with no outbound record, matching the reported medium-severity temporary DoS pattern.

### Likelihood Explanation
This requires an unprivileged user to submit (or have submitted on their behalf) a payload/inbound that produces multiple outbound events in one receipt while the registry happens to have one destination chain disabled — a state that is admin-controlled but not attacker-controlled, so the trigger condition (multi-outbound payload + one disabled chain) is plausible in normal operation, not requiring privileged action from the attacker.

### Recommendation
In `BuildOutboundsFromReceipt`, skip/log outbound events for disabled destination chains instead of aborting the whole loop with `return nil, err`; continue building and returning outbounds for all enabled chains, and separately track/report the skipped ones (e.g., as failed outbound records) so operators can recover them.

### Proof of Concept
Not independently executed; derived from static code tracing of `BuildOutboundsFromReceipt` and its callers (`AttachOutboundsToExistingUniversalTx`, `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload`). A concrete PoC would require constructing an EVM receipt with two `UniversalTxOutbound` logs for two different destination chains, disabling outbound for one via `uregistry`, and asserting via `GetUniversalTx` that the outbound for the still-enabled chain is missing — analogous to the existing test `TestOutbound_ChainEnabled` in `test/integration/uexecutor/chain_enabled_test.go`, extended to the multi-log case.
