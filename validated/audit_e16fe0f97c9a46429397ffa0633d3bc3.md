## Analog Found

### Title
Missing enforced invariant between `account_creation_charge` and `min_gas_purchase_price` allows bypass of the account-creation anti-spam fee - (File: `runtime/runtime/src/lib.rs`)

### Summary
The original Compound-style finding is a missing runtime check that `liquidationFactor <= storeFrontPriceFactor`, an economic invariant between two independently-settable parameters that, if violated, is silently exploitable by ordinary users to drain protocol value. The nearcore analog is the invariant between `min_gas_purchase_price` and `account_creation_charge` (plus the `create_account` exec-gas fee): the code assumes `min_gas_purchase_price * create_account_gas_cost >= account_creation_charge`, but this is enforced only by a `debug_assert!`, which is compiled to a no-op in release builds actually run on mainnet/testnet.

### Finding Description
`RuntimeConfig::account_creation_charge` and `RuntimeConfig::min_gas_purchase_price` are independent parameters loaded from the versioned parameter tables with no cross-field validation in `TryFrom<&ParameterTable> for RuntimeConfig` [1](#0-0) .

The correctness of the account-creation charge mechanism depends on the invariant `min_gas_purchase_price * create_account_gas_cost >= account_creation_charge`, which is explicitly documented as required in multiple places [2](#0-1) [3](#0-2) .

However, in the actual runtime path `refund_unspent_gas_and_deposits`, this invariant is checked only via `debug_assert!`, not via any error path or clamp: [4](#0-3) 

`debug_assert!` compiles to a no-op when `debug_assertions` is disabled, which is the case for release builds used in production. If the invariant is ever violated — e.g., a future protocol-version parameter update raises `account_creation_charge` or the `create_account` exec fee without proportionally raising `min_gas_purchase_price` (or lowers `min_gas_purchase_price`) — the code does not fail safely by rejecting the configuration or the transaction; instead `amount_to_charge` (desired `account_creation_charge` minus already-burned cost) is silently clamped by `amount_actually_charged = min(amount_to_charge, burned_gas_refund)`, so any account-creating transaction is charged **less** than the protocol-intended `account_creation_charge`.

### Impact Explanation
This is a fee-bypass scenario reachable by any ordinary transaction signer: normal `CreateAccount` actions and implicit-account creation via transfer both call `refund_unspent_gas_and_deposits` with `created_account = true` under `AccountCostIncrease` [5](#0-4) . If the parameter invariant is violated by a config/parameter update (analogous to governance setting `liquidationFactor > storeFrontPriceFactor` in the original report), every user creating an account thereafter systematically underpays the anti-spam/state-cost charge the protocol relies on to price state growth, letting users create accounts cheaper than intended at the protocol's expense — a concrete fee/gas bypass rather than a benign rounding issue.

### Likelihood Explanation
Likelihood depends on a future parameter change breaking the invariant (similar to how the original bug required a governance-set `liquidationFactor`), but unlike the Compound case, nearcore has zero enforced protection: no `InvalidConfigError` is raised at config-load time, and the only guard (`debug_assert!`) is inert in production binaries. Any parameter-table edit (as already seen in `85.yaml` where both `min_gas_purchase_price` and `account_creation_charge` are bumped together by hand) that fails to keep the two values consistent would silently degrade the anti-spam charge with no test or runtime failure surfacing the issue in production.

### Recommendation
Replace the `debug_assert!` sanity checks in `refund_unspent_gas_and_deposits` with a hard validation at config-construction time (in `TryFrom<&ParameterTable> for RuntimeConfig` or `RuntimeConfig::new`) that returns `InvalidConfigError` if `min_gas_purchase_price * create_account_gas_cost < account_creation_charge`, so a misconfigured parameter set can never be loaded into a running node, mirroring the "liquidationFactor ≤ storeFrontPriceFactor" fix pattern from the source report.

### Proof of Concept
1. Modify a runtime-config parameter file (e.g. a future `NN.yaml` protocol-version diff) to raise `account_creation_charge` or the `create_account` `execution` fee without proportionally raising `min_gas_purchase_price`.
2. Node loads this config; no validation error is raised because checks are `debug_assert!`-only and release builds have `debug_assertions` disabled.
3. Any user submits a `CreateAccount` transaction (or an implicit-account-creating transfer) with gas purchased at exactly `min_gas_purchase_price`.
4. In `refund_unspent_gas_and_deposits`, `amount_to_charge` (derived from the now-inconsistent `desired_cost`) exceeds what `burned_gas_refund` can cover; `amount_actually_charged = min(amount_to_charge, burned_gas_refund)` silently charges less than `account_creation_charge` intends [6](#0-5) , letting the account creator pay less than the protocol-designated cost with no error or panic surfaced.

        // If an account was created, charge more to cover its cost.
        if created_account && ProtocolFeature::AccountCostIncrease.enabled(protocol_version) {
            // This is how much creating an account should cost
            let desired_cost = config.account_creation_charge;

            let create_account_gas_cost =
                config.fees.fee(ActionCosts::create_account).exec_fee().gas;
            // The cost of the gas that was burned already
            let burned_cost = safe_gas_to_balance(gas_burn_price, create_account_gas_cost)?;

            // We would like to charge as much as needed to reach desired_cost
            let amount_to_charge = desired_cost.saturating_sub(burned_cost);

            // We can't charge more than `burned_gas_refund`.
            // `burned_gas_refund < amount_to_charge` could happen for receipts where the gas was
            // purchased in protocol versions before `ProtocolFeature::AccountCostIncrease`, at a lower
            // gas price that isn't enough to cover the cost of creating an account.
            let amount_actually_charged = std::cmp::min(amount_to_charge, burned_gas_refund);

            // sanity check: purchasing gas at `min_gas_purchase_price` should be enough to cover
            // the cost of creating an account.
            debug_assert!(
                safe_gas_to_balance(config.min_gas_purchase_price, create_account_gas_cost)
                    .unwrap()
                    >= desired_cost
            );

            // sanity check: as long as the purchase price is high enough, there should always be
            // enough refund balance to cover the cost of creating an account.
            if gas_purchase_price >= config.min_gas_purchase_price {
                debug_assert!(burned_gas_refund >= amount_to_charge);
            }

            // Subtract `amount_actually_charged` from the refund.
            gas_refund_result.create_account_charge = amount_actually_charged;
            burned_gas_refund = burned_gas_refund
                .checked_sub(amount_actually_charged)
                .expect("burned_gas_refund >= amount_actually_charged checked above");
