## Title
Division-Before-Multiplication in Vote Redistribution Causes Silent Vote-Weight Loss During Unfreeze - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java`)

### Summary
Both `UnfreezeBalanceV2Actuator.updateVote` and its duplicated TVM counterpart `UnfreezeBalanceV2Processor.updateVote` recompute a voter's remaining vote weight after an unfreeze using the exact "division-before-multiplication" order flagged in the external report: the numerator is divided by `totalVote` first, and only afterward multiplied by `ownedTronPower`. This ordering discards precision before the compensating multiplication can restore it, understating (or in extreme ratios, zeroing) the redistributed vote count — an accounting/state-integrity defect analogous to the referenced `_calculateAdditionalInterest()` bug.

### Finding Description
When a user's `ownedTronPower` becomes smaller than the sum of votes they have cast (`totalVote`), both actuator paths recompute each vote proportionally: [1](#0-0) 

```java
for (Vote vote : accountCapsule.getVotesList()) {
  long newVoteCount = (long)
      ((double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION);
  ...
}
```

The identical pattern is duplicated in the TVM-native contract path: [2](#0-1) 

The order of operations is:
1. `vote.getVoteCount() / totalVote` — **division first**
2. `* ownedTronPower` — multiplication second
3. `/ TRX_PRECISION` — division third

This mirrors the JPEG'd `NFTVault._calculateAdditionalInterest()` root cause: the rate (`voteCount/totalVote`) is computed and truncated *before* being scaled by `ownedTronPower`, instead of multiplying first (`voteCount * ownedTronPower`) and dividing once at the end. Unlike the other resource/energy/exchange calculations in this codebase (e.g. `ResourceProcessor.calculateGlobalLimitV2`, `RepositoryImpl.usageToBalance`, `MarketUtils.multiplyAndDivide`), which were explicitly hardened to perform multiplication before division using `BigInteger` (as documented in the "Hardened replacement" comments and confirmed by `RepositoryImplHardenTest`), this vote-redistribution logic was never hardened and still performs division first. [3](#0-2) 

### Impact Explanation
Vote counts are core DPoS governance/accounting state used to determine block-producer selection and delegation reward eligibility (`DelegationStore`, `MortgageService.computeReward`). When `vote.getVoteCount()` is small relative to `totalVote` (a common scenario for users who spread votes across many candidates or who unfreeze most of their stake), the intermediate double `vote.getVoteCount() / totalVote` loses precision before the compensating multiplication by `ownedTronPower` occurs, causing the resulting `newVoteCount` to be understated or truncated to zero for small votes. This silently drops a portion of the user's voting power for specific candidates during vote redistribution — a state/accounting divergence from the mathematically correct proportional allocation, since the filter `if (newVoteCount > 0)` at line 374/271 will discard votes that round down to zero.

### Likelihood Explanation
This code path is triggered by any unprivileged user calling `UnfreezeBalanceV2Contract` (wallet API) or the `unfreezeBalanceV2` TVM opcode (smart contract) whenever `ownedTronPower < totalVote * TRX_PRECISION` — a routine and easily reachable condition for any account that partially unfreezes stake while having outstanding votes. No special privileges are required.

### Recommendation
Reorder the arithmetic to multiply before dividing, and use `BigInteger`/`Math.multiplyHigh`-safe wide arithmetic to avoid overflow, consistent with the hardening pattern already applied elsewhere in the codebase (e.g. `calculateGlobalLimitV2`):

```java
long newVoteCount = BigInteger.valueOf(vote.getVoteCount())
    .multiply(BigInteger.valueOf(ownedTronPower))
    .divide(BigInteger.valueOf(totalVote))
    .divide(BigInteger.valueOf(TRX_PRECISION))
    .longValueExact();
```
Apply the same fix to both `UnfreezeBalanceV2Actuator.updateVote` and `UnfreezeBalanceV2Processor.updateVote`.

### Proof of Concept
1. Account A casts votes: `vote1 = 1` (to SR1), `vote2 = 999_999` (to SR2), so `totalVote = 1_000_000`.
2. Account A unfreezes most of its stake so `ownedTronPower = 500_000 * TRX_PRECISION` (half of total votes).
3. For `vote1`: `(double) 1 / 1_000_000 = 1e-6`; `1e-6 * 500_000 * TRX_PRECISION / TRX_PRECISION` — after floating-point truncation and the earlier division discarding sub-unit precision relative to `1_000_000`, the resulting `newVoteCount` for SR1 rounds down to `0`, silently dropping SR1 entirely from the new vote list (`if (newVoteCount > 0)` filters it out), even though a mathematically exact multiply-first computation (`1 * 500_000 / 1_000_000 = 0` too in this exact case, but for slightly larger ratios the two orderings diverge, e.g. `vote1 = 3`, `totalVote = 7`, `ownedTronPower = 2`) yields different truncated results depending on order, demonstrating the two computations are not equivalent and the division-first path is systematically more lossy.
