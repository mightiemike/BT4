### Title
`DelegateAction` Inner Signature Lacks Chain-Specific Binding, Enabling Cross-Fork Replay of Meta-Transactions — (`File: core/primitives/src/action/delegate.rs`)

### Summary

`DelegateAction` (NEP-366 meta transactions) produces a user signature that covers only a fixed NEP discriminant and the action payload. Neither a `chain_id` nor a `block_hash` is included in the signed bytes. If NEAR undergoes a hard fork, any relayer who observed a `DelegateAction` on one chain can replay the identical inner signature on the forked chain, causing the user's funds to be transferred on both chains without additional user consent.

### Finding Description

The outer `SignedTransaction` that carries a `DelegateAction` includes a `block_hash` field, which binds the relayer's transaction to a specific chain state: [1](#0-0) 

However, the inner `DelegateAction` — the struct the *user* signs — contains only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`: [2](#0-1) 

The hash that the user actually signs is computed by `get_nep461_hash()`: [3](#0-2) 

`SignableMessage` wraps only a fixed `discriminant` (the NEP-366 integer constant) and the message body: [4](#0-3) 

The discriminant is a constant derived from the NEP number alone — it contains no chain identity: [5](#0-4) 

Therefore the bytes that are hashed and signed are:

```
SHA256( borsh( NEP_366_DISCRIMINANT || sender_id || receiver_id || actions || nonce || max_block_height || public_key ) )
```

There is no `chain_id` and no `block_hash` anywhere in this payload. The same is true for `DelegateActionV2` / `VersionedDelegateActionPayload`: [6](#0-5) 

The `max_block_height` field provides a *time* bound but not a *chain* bound — block heights are identical on both sides of a fork up to the fork point.

Signature verification in `SignedDelegateAction::verify()` and `VersionedSignedDelegateAction::verify()` checks only that the signature matches the NEP-461 hash of the payload; it has no awareness of which chain is executing: [7](#0-6) 

### Impact Explanation

If NEAR undergoes a hard fork at block height H:

1. Both chains share identical account state (balances, nonces, access keys) up to height H.
2. A `DelegateAction` signed before the fork with `max_block_height > H` has a valid nonce on **both** chains.
3. A relayer (or any observer of the original transaction) can wrap the same `DelegateAction` bytes in a new outer `SignedTransaction` referencing a valid `block_hash` from the forked chain and submit it.
4. The runtime on the forked chain calls `apply_delegate_action`, which calls `signed.verify()`, which succeeds because the inner signature is chain-agnostic.
5. The user's tokens are transferred on the forked chain without any additional authorization from the user.

The user suffers an unauthorized fund transfer on the forked chain — a direct loss of funds.

### Likelihood Explanation

NEAR uses BFT-based finality (Nightshade), so accidental forks are rare. However, contentious protocol upgrades or emergency hard forks are not impossible, and the NEAR ecosystem already runs multiple networks (mainnet, testnet, betanet) that share account-name space and key material. The attack requires only that an observer of the original meta-transaction resubmit it on the other chain; no privileged access is needed.

### Recommendation

**Short term:** Include a chain-specific binding in the `DelegateAction` signed payload. The simplest option is to add a `chain_id: String` field to `DelegateAction` and `DelegateActionV2`, include it in the borsh-serialized bytes that `get_nep461_hash()` hashes, and validate it against the executing chain's genesis `chain_id` inside `apply_delegate_action`. Alternatively, add a `block_hash` field (analogous to the outer transaction) so the inner signature is bound to a specific chain history.

**Long term:** Standardize the chain-binding requirement in NEP-461/NEP-483 so all future signable message types include a chain identifier by default.

### Proof of Concept

```
Pre-conditions:
  - NEAR forks at block height H; both chains have identical state at H.
  - Alice has 100 NEAR on both chains.
  - Alice previously signed a DelegateAction (nonce=N, max_block_height=H+1000)
    authorizing a transfer of 100 NEAR to Bob, submitted via relayer on chain A.

Attack steps:
1. Attacker (any observer) extracts the SignedDelegateAction bytes from chain A.
2. Attacker constructs a new SignedTransaction on chain B:
     - outer signer: any account with funds on chain B (attacker's own)
     - outer block_hash: any recent block hash from chain B
     - actions: [ the original SignedDelegateAction ]
3. Attacker submits the transaction to chain B's RPC.
4. Runtime calls apply_delegate_action → SignedDelegateAction::verify() →
   get_nep461_hash() produces the same hash as on chain A (no chain binding) →
   signature check passes.
5. Alice's nonce N is consumed on chain B; 100 NEAR is transferred to Bob on chain B.

Result: Alice loses 100 NEAR on chain B without having authorized it.
        The only cost to the attacker is the outer transaction gas on chain B.
``` [7](#0-6) [8](#0-7)

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
