### Title
Unbounded O(m) linear scan in `UnfreezeBalanceActuator.execute` via attacker-inflated `DelegatedResourceAccountIndexStore` index, at zero metered cost - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java])

### Summary
When the legacy delegation-index path is active (`supportDR()==true`, `supportAllowDelegateOptimization()==false`), an attacker can create many throwaway accounts that each delegate BANDWIDTH/ENERGY to the same victim receiver via `FreezeBalanceContract`, inflating `receiverIndexCapsule.getFromAccountsList()` to size m. A single `UnfreezeBalanceContract` call then triggers an O(m) `ArrayList.remove` scan in `UnfreezeBalanceActuator.execute`, while `calcFee()` always returns 0, decoupling the cost from the induced CPU work.

### Finding Description
`FreezeBalanceActuator.delegateResource` (lines 319–345 of `FreezeBalanceActuator.java`) appends a new entry to `receiverIndexCapsule`'s `fromAccountsList` for every distinct owner that delegates to the same receiver, when `supportAllowDelegateOptimization()` is false [1](#0-0) . There is no bound on the size of this list — any number of distinct funded accounts can each add one entry.

Later, `UnfreezeBalanceActuator.execute` retrieves this same `receiverIndexCapsule` and does:
```java
List<ByteString> fromAccountsList = new ArrayList<>(receiverIndexCapsule.getFromAccountsList());
fromAccountsList.remove(ByteString.copyFrom(ownerAddress));
``` [2](#0-1) 

This copies and linearly scans the list, an O(m) operation, and `calcFee()` for this actuator unconditionally returns 0 [3](#0-2) , so the fee charged is independent of m. No `validate()` check limits the size of `fromAccountsList` or the number of distinct delegators to a receiver [4](#0-3) .

### Impact Explanation
This matches "DoS via the TRON protocol implementation" in scope: a legitimate transaction from any of the m attacker accounts forces every validating node to perform O(m) work processing a single, zero-fee `UnfreezeBalanceContract`, with no accounting for the cost. If m is large enough this can measurably slow block validation for all nodes replaying the transaction — a resource-exhaustion vector paid for by attacker-controlled cheap inputs, imposed onto an arbitrary victim's index entry without their consent.

### Likelihood Explanation
The precondition is that the chain has `supportDR()==true` and has NOT enabled `supportAllowDelegateOptimization()` — this is the legacy code path guarded by a hard fork/proposal switch (`ALLOW_DELEGATE_OPTIMIZATION`) referenced in `DynamicPropertiesStore.java` and `ProposalUtil.java`. On networks/testnets where this optimization proposal has not been activated, the attack is fully reachable by an unprivileged party: create m funded accounts (only bounded by TRX needed to satisfy `frozenBalance >= 1 TRX` per `FreezeBalanceActuator.validate` at line 191-193), each broadcast `FreezeBalanceContract(receiver=victim)`, then have one broadcast `UnfreezeBalanceContract`. However, on any chain where `supportAllowDelegateOptimization()` is already enabled (which appears to be the intended fix path, replacing the legacy list with `convert`/`delegate`/`unDelegate` APIs), this legacy branch is dead code and the vector does not apply. I could not verify from the available index whether `ALLOW_DELEGATE_OPTIMIZATION` is enabled by default on mainnet at the current codebase state — this affects whether the vulnerable branch is actually reachable in production today.

### Recommendation
- Enforce a maximum size on `fromAccountsList`/`toAccountsList` in `DelegatedResourceAccountIndexCapsule`, rejecting further delegations once the cap is reached (in `FreezeBalanceActuator.validate`).
- Meter the cost of `UnfreezeBalanceActuator.execute` proportionally to list size (e.g., charge fee or bandwidth/energy based on `fromAccountsList.size()`), rather than a flat `calcFee() == 0`.
- Prefer migrating fully to the optimized delegate index (`supportAllowDelegateOptimization`) and deprecating/disabling the legacy list-based index entirely to remove this scaling issue.

// Preconditions: dynamicStore.saveAllowDelegateResource(1) [supportDR=true],

for (int i = 0; i < m; i++) {
  createFundedAccount(ownerAddress_i, 2 * TRX_PRECISION);
  FreezeBalanceContract fc = FreezeBalanceContract.newBuilder()
      .setOwnerAddress(ownerAddress_i)
      .setFrozenBalance(TRX_PRECISION)
      .setFrozenDuration(3)
      .setReceiverAddress(victimAddress)
      .setResource(ResourceCode.BANDWIDTH)
      .build();
  new FreezeBalanceActuator().setChainBaseManager(...).execute(...); // grows receiverIndexCapsule.fromAccountsList to i+1
}

// Now trigger the O(m) scan cheaply:
long start = System.nanoTime();
UnfreezeBalanceContract uc = UnfreezeBalanceContract.newBuilder()
    .setOwnerAddress(ownerAddress_0)
    .setReceiverAddress(victimAddress)
    .setResource(ResourceCode.BANDWIDTH)
    .build();
new UnfreezeBalanceActuator().setChainBaseManager(...).execute(...);
long elapsed = System.nanoTime() - start;

// Assertions:
assertTrue(elapsed scales roughly linearly with m, when repeated for m = 1k, 10k, 100k);
assertEquals(0, new UnfreezeBalanceActuator().calcFee()); // fee remains 0 regardless of m
```
Expected result: wall-clock time for `execute()` grows linearly with m while the charged fee stays at 0, confirming unmetered O(m) CPU cost, contingent on the legacy (`supportAllowDelegateOptimization()==false`) index path being active.
