### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The reported bug class is that a caller-supplied identifier (`address` in `previewRedeem`) is used to select security/pricing-relevant configuration without that identifier itself being authenticated/bound to the request, letting an attacker skew an outcome that should be tied to a verified identity. The same structural flaw exists in shopify-app-js's webhook authentication path: the HMAC signature that "authenticates" an inbound webhook only covers the raw request body, while the `X-Shopify-Shop-Domain` header — the value that determines *which tenant's* offline session and access token get loaded and attached to the webhook payload — is never included in the HMAC computation.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC purely from `rawBody` and compares it to the `X-Shopify-Hmac-Sha256` (or `shopify-hmac-sha256`) header: [1](#0-0) 

The shop domain used downstream is read separately as an ordinary header, with no cryptographic binding to the signed body: [2](#0-1) 

That unauthenticated `domain` value flows directly into `authenticateWebhookFactory`, which uses it to look up (or create) the offline session for that shop and attach an authenticated `admin` client to the webhook context: [3](#0-2) [4](#0-3) 

Because the app's `apiSecretKey` is shared across every shop that installs the app (it's an app-level, not a shop-level, secret), any merchant that installs the app can obtain a body+HMAC pair that is valid for that shared secret (e.g., by triggering a webhook against their own store, or via the app's own test/notification tooling). Since the domain header is not part of the signed data, that same `(rawBody, hmac)` pair remains "valid" if replayed with a different `X-Shopify-Shop-Domain` value. This is directly analogous to the `PreviewRedeem` bug: a value (`address` / `domain`) that determines which configuration/tenant is used for a sensitive computation is accepted from the caller without being tied to the piece of data that was actually authenticated (the price oracle account / the HMAC signature).

### Impact Explanation
An attacker who can produce one valid `(body, hmac)` pair for the shared app secret (trivially available to any shop that has installed the app, since they can trigger their own webhooks) can forge the `X-Shopify-Shop-Domain` header to point at a victim shop. `ensureValidOfflineSession`/`createOrLoadOfflineSession` will then load or create the *victim's* offline session and hand back an authenticated `admin` API client scoped to the victim's access token, alongside attacker-chosen payload contents. This is cross-tenant session/context confusion in the webhook authentication handler — the app processes attacker-controlled data as if it originated from, and should act on behalf of, a different merchant.

### Likelihood Explanation
Any single installed merchant (an unprivileged, ordinary app user) can generate a legitimately-signed body for the shared secret and then merely swap one header value, requiring no secret leakage, no MITM, and no privileged access — matching the "single merchant" reachable-actor bar.

### Recommendation
Bind the shop domain (and other routing-relevant headers such as topic/api-version/webhook-id) into the HMAC-signed material, or otherwise cryptographically verify that the `X-Shopify-Shop-Domain` header matches the shop that Shopify actually signed for, before using it to select/load a session in `checkWebhooksHeaders`/`checkEventsHeaders` (`packages/apps/shopify-api/lib/webhooks/validate.ts`) and `authenticateWebhookFactory` (`packages/apps/shopify-app-remix/.../authenticate/webhooks/authenticate.ts`).

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger any webhook topic (or use the Shopify CLI webhook trigger) to obtain a legitimately signed `(rawBody, X-Shopify-Hmac-Sha256)` pair from Shopify for the app's shared `apiSecretKey`.
2. Replay a POST to the app's webhook endpoint using that exact `rawBody`/HMAC pair, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `validateHmacFromRequestFactory` (`hmac-validator.ts:168-201`) validates successfully because it only checks the body hash, not the domain.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` with `check.domain === "victim.myshopify.com"`, loading/creating the victim's offline session and attaching an `admin` client authorized with the victim's access token to process the attacker-supplied payload.
